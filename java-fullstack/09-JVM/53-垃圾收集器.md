## 概述

垃圾收集器是 GC 的具体实现。JVM 提供了 7 种主流收集器，每种有不同的设计目标——有的追求吞吐量，有的追求低延迟。JDK 9 起 G1 是默认，JDK 21 起分代 ZGC 成为新选择。

## 收集器全景图

```
新生代收集器                    老年代收集器
───────────                    ───────────
Serial     ─────搭配────→     Serial Old
Parallel Scavenge ──搭配──→  Parallel Old
ParNew     ─────搭配────→     CMS (已废弃，JDK 14 移除)
                              (JDK 9 默认) G1  ← 同时管理新生代和老年代
                                            ZGC   ← JDK 11 实验性，JDK 21 分代生产可用
                                            Shenandoah ← Red Hat 维护
                                            Epsilon ← JDK 11 不回收 GC（调试用）
```

| 收集器 | 目标 | 算法 | STW | JDK 版本 |
|--------|------|------|-----|----------|
| Serial | 最小内存占用 | 复制(Young) / 标记-整理(Old) | 全程 | 1.3+ |
| Parallel | 最高吞吐量 | 复制 / 标记-整理 | 全程 | 1.4+ |
| CMS | 低延迟 | 标记-清除 | 两次短暂暂停 | 1.5-14 |
| G1 | 可控延迟 | 分区+复制 | 多次极短暂停 | 7+，9 默认 |
| ZGC | 极低延迟(<1ms) | 染色指针+并发整理 | < 1ms | 11+(实验)/15(生产)/21(分代) |
| Shenandoah | 低延迟 | 并发整理 | 极短 | 12+ |
| Epsilon | 不回收 | 无 GC | 无 | 11+ |

## Serial / Serial Old

最简单、最古老的收集器——单线程工作，GC 时所有用户线程停止：

```
串行 GC 工作流程：
[线程1] [线程2] [线程3]    ← 全部暂停（STW）
          │
    [GC 线程（单线程工作）]
          │
[线程1] [线程2] [线程3]    ← 恢复运行
```

```bash
-XX:+UseSerialGC  # 启用
```

适用：客户端应用、嵌入式设备（内存 < 100MB）、单核 CPU。优点是不占 CPU，没有线程切换开销。

## Parallel Scavenge / Parallel Old

JDK 8 默认——多线程并行 GC，目标：**吞吐量最大化**（吞吐量 = 用户代码时间 / 总时间）：

```
并行 GC 工作流程：
[线程1] [线程2] [线程3]    ← 全部暂停
          │
[GC1] [GC2] [GC3] [GC4]   ← 多线程并行 GC
          │
[线程1] [线程2] [线程3]    ← 恢复
```

```bash
-XX:+UseParallelGC    # 新生代 Parallel Scavenge + 老年代 Serial Old
-XX:+UseParallelOldGC # 新生代 Parallel Scavenge + 老年代 Parallel Old

# 关键参数
-XX:MaxGCPauseMillis=200   # 最大 GC 暂停目标
-XX:GCTimeRatio=99         # GC 时间占比目标 (1/1+99 = 1%)
-XX:ParallelGCThreads=4    # GC 线程数
```

适用：后台批处理、科学计算——不在乎单次暂停，在乎整体吞吐。

## CMS（Concurrent Mark Sweep）

JDK 14 已移除，但其设计思想影响了 G1。目标：**低延迟**——GC 的大部分工作和用户线程并发执行：

```
CMS 的四个阶段：
1. 初始标记 (STW，极短)   —— 标记 GC Roots 直接关联的对象
2. 并发标记               —— 从 GC Roots 开始遍历对象图（与用户线程并发）
3. 重新标记 (STW，短)     —— 修正并发标记期间变动的引用
4. 并发清除               —— 回收垃圾（与用户线程并发）
```

CMS 的致命缺陷（导致被 G1 取代）：
- 标记-清除算法 → **内存碎片**
- Concurrent Mode Failure → 退化为 Serial Old（长时间 STW）
- 对 CPU 资源敏感（并发占用 CPU）

## G1（Garbage First）

JDK 9+ 默认——把堆切成若干 **Region**，优先回收垃圾最多的 Region（Garbage First）：

```
G1 的堆布局：
┌──┬──┬──┬──┬──┬──┬──┬──┐
│E │S │O │E │O │H │E │E │   E=Eden, S=Survivor, O=Old, H=Humongous
├──┼──┼──┼──┼──┼──┼──┼──┤
│O │E │E │E │O │S │O │E │   每个 Region 大小 1-32MB（通过 -XX:G1HeapRegionSize 设置）
└──┴──┴──┴──┴──┴──┴──┴──┘
```

### G1 的关键概念

```
RSet (Remembered Set)：每个 Region 都有自己的 RSet
  → 记录"谁引用了我"（外部 Region → 本 Region 内的对象）
  → 做局部回收时不需要扫描整个堆

Humongous Region：专门存放大对象
  → 超过 Region 大小 50% 的对象进入 Humongous Region
  → 占用连续的 Region

CSets (Collection Set)：本次 GC 要回收的 Region 集合
```

### G1 的工作模式

```
Young GC（Minor GC 的 G1 版）：
  Eden 区满了 → 只回收年轻代 Region → 暂停短

Mixed GC：
  全局并发标记完成后 → 回收一部分年轻代 + 一部分老年代 Region
  逐步回收老年代（不是一次性 Full GC）

Full GC：
  G1 也避免不了 Full GC，但频率远低于 CMS
  触发：Mixed GC 来不及回收、Humongous 分配失败
```

### G1 关键参数

```bash
-XX:+UseG1GC                        # 启用 G1
-XX:MaxGCPauseMillis=200            # 期望最大暂停时间（软目标）
-XX:G1HeapRegionSize=4m             # Region 大小（2 的幂，1-32MB）
-XX:InitiatingHeapOccupancyPercent=45  # 堆占用 45% 触发并发标记
-XX:G1NewSizePercent=5              # 新生代最小占比
-XX:G1MaxNewSizePercent=60          # 新生代最大占比
```

## ZGC

ZGC 是 JDK 11 引入的实验性 GC，JDK 15 生产可用，JDK 21 支持分代。目标：**暂停时间 < 1ms**（JDK 21 做到 < 0.1ms），无论堆多大。

### ZGC 的核心技术

```
染色指针（Colored Pointers）：在 64 位指针中嵌入 GC 元数据
  ┌──────┬──────────────────────────────────────────┬─────┐
  │ 未使用 │              对象地址                     │标记  │
  └──────┴──────────────────────────────────────────┴─────┘
  4 位                             42 位            4 位

读屏障（Load Barrier）：每次读引用时检查指针颜色
  → 如果是已回收的，触发重定位
  → 杜绝了并发整理期间的漏标

并发整理：一边移动对象、一边更新引用，全程与用户线程并发
```

### ZGC 关键参数

```bash
-XX:+UseZGC                    # 启用 ZGC
-XX:+ZGenerational             # JDK 21+ 启用分代 ZGC（默认）
-Xms2g -Xmx2g                  # 堆大小（支持 TB 级）
-XX:ConcGCThreads=4            # 并发 GC 线程数
```

### ZGC 的限制（JDK 21 前）

```
- 不支持分代（JDK 21 已支持）
- 不支持压缩指针（-XX:+UseCompressedOops 与 ZGC 不兼容）
- 不支持类卸载（JDK 21 已支持）
```

## Shenandoah

Red Hat 贡献的低延迟 GC——和 ZGC 目标相同但实现不同：

```bash
-XX:+UseShenandoahGC  # 启用（主要是 OpenJDK）
```

核心区别：ZGC 用染色指针，Shenandoah 用**转发指针**（Brooks Pointer）——每个对象头有额外的转发指针，重定位时通过它找到新位置。

## GC 选择指南

```
选择流程：

堆很小（< 100MB）、单核？
  └── Serial GC

追求吞吐量（批处理、科学计算）？
  └── Parallel GC

低延迟、堆 < 十GB量级？
  └── G1（JDK 9+ 默认，无需手动选）

极低延迟（< 1ms）、堆很大？
  └── ZGC（JDK 21+ 推荐）

极低延迟、非 Oracle JDK？
  └── Shenandoah

调试/测试（不回收）？
  └── Epsilon
```

| 选择矩阵 | 低延迟 | 高吞吐 | 小内存 |
|----------|--------|--------|--------|
| JDK 8 | CMS | Parallel | Serial |
| JDK 11 | G1 | Parallel | Serial |
| JDK 17 | G1 / ZGC | Parallel | Serial |
| JDK 21 | G1 / ZGC(分代) | Parallel | Serial |

## 应用场景实战

### 场景一：G1 的 Mixed GC 频率调优

```bash
# 问题：Mixed GC 滞后，老年代回收不及时 → Full GC
# 方案：降低 IHOP 阈值，更早触发并发标记

-XX:InitiatingHeapOccupancyPercent=35  # 从默认 45 降到 35
-XX:G1MixedGCLiveThresholdPercent=85   # Region 中存活 >85% 则不回收
```

### 场景二：大对象分配优化

```bash
# G1 大对象（> HeapRegionSize 的 50%）直接进入 Humongous Region
# 如果大对象频繁分配和释放，可能导致 Full GC

# 增大 Region 大小
-XX:G1HeapRegionSize=8m  # 默认会根据堆大小自动计算（2MB-32MB）
```

### 场景三：GC 日志对比

```bash
# 对比不同 GC 在同一负载下的表现
# Parallel:
java -XX:+UseParallelGC -Xlog:gc*:file=parallel.log ... 

# G1:
java -XX:+UseG1GC -Xlog:gc*:file=g1.log ...

# ZGC:
java -XX:+UseZGC -Xlog:gc*:file=zgc.log ...
```

## 最佳实践与踩坑记录

### 常见问题表

| 问题 | 原因 | 修复 |
|------|------|------|
| CMS Concurrent Mode Failure | 并发回收速度 < 分配速度 | 增大老年代、降低 CMS 触发阈值、或升级 G1 |
| G1 Full GC 频繁 | Mixed GC 跟不上分配 | 降低 IHOP、增大堆、减少 Humongous 分配 |
| ZGC 内存占用高 | 染色指针需要额外空间 | ZGC 实际用 ~内存×1.3 的虚拟地址空间 |
| GC 停顿仍很长 | GC 线程太少 | 增加 `ConcGCThreads` 或 `ParallelGCThreads` |

### JDK 版本推荐

```
JDK 8  →  Parallel（默认）/ CMS（需手动启用）
JDK 11 →  G1（默认）/ ZGC（实验性）
JDK 17 →  G1（默认）/ ZGC（生产可用）
JDK 21 →  G1（默认）/ 分代 ZGC（强烈推荐！）
```

## 总结

- 7 种收集器：Serial(单线程)→ Parallel(吞吐)→ CMS(低延迟，已废弃)→ G1(平衡，默认)→ ZGC/Shenandoah(极低延迟)→ Epsilon(不回收)
- G1 把堆分区为 Region，优先回收垃圾最多的（Garbage First），通过 RSet 做局部回收
- ZGC 用染色指针 + 读屏障 + 并发整理做到 < 1ms 暂停
- 选 GC = 看延迟需求：批处理用 Parallel，在线服务用 G1，实时系统用 ZGC
- Full GC 是万不得已——合理配置参数让 GC 在 Minor/Mixed 阶段完成大部分工作
