## 概述

类加载机制是 JVM 把 `.class` 文件从磁盘/网络/运行时生成加载到内存、并完成连接和初始化的整个过程。理解类加载是理解 Spring Boot 的 FatJar、Tomcat 的多应用部署、热部署/热替换等技术的基础。

## 类加载的五个阶段

```
加载(Loading) → 验证(Verification) → 准备(Preparation)
                                      → 解析(Resolution)
                                      → 初始化(Initialization)

其中：验证、准备、解析统称为"链接(Linking)"
```

### 1. 加载（Loading）

- 通过类的全限定名获取二进制字节流（class 文件、jar、网络、动态生成）
- 将字节流转换为方法区的运行时数据结构
- 在堆中生成 `java.lang.Class` 对象作为入口

```java
// 三种触发加载的方式
Class<?> c1 = Class.forName("com.example.User");      // 会初始化
Class<?> c2 = User.class;                              // 会初始化
Class<?> c3 = ClassLoader.getSystemClassLoader()
    .loadClass("com.example.User");                    // 不会初始化（只加载）
```

### 2. 验证（Verification）

确保字节码符合 JVM 规范，不会破坏虚拟机安全：

- **文件格式验证**：魔数 0xCAFEBABE、版本号是否支持
- **元数据验证**：是否有父类、是否继承了 final 类
- **字节码验证**：类型转换是否合法、跳转指令是否越界
- **符号引用验证**：引用的类/方法是否存在

### 3. 准备（Preparation）

为**静态变量**分配内存并设置**零值**：

```java
public static int value = 123;  // 准备阶段: value = 0（零值）
                                 // 初始化阶段: value = 123

public static final int CONST = 456;  // 准备阶段: CONST = 456（常量直接赋值）
```

### 4. 解析（Resolution）

将常量池中的**符号引用**替换为**直接引用**（内存地址/偏移量）：

```
符号引用：字面量描述 → "com/example/User", "getName:()String"
直接引用：内存中的实际位置 → 0x7f8a1234, vtable offset 12
```

### 5. 初始化（Initialization）

执行类构造器 `<clinit>()`——所有静态变量赋值和静态代码块按声明顺序执行：

```java
public class Example {
    static int a = 1;
    static {
        a = 10;
        b = 20;       // 可以赋值后面的变量
        // System.out.println(b);  // 但不能访问（非法前向引用）
    }
    static int b = 2;
}
// <clinit>() 执行顺序：
// a = 1 → a = 10, b = 20 → b = 2
// 最终：a = 10, b = 2
```

触发初始化的六种情况（主动引用）：
1. `new`、`getstatic`、`putstatic`、`invokestatic`
2. `java.lang.reflect` 反射调用
3. 初始化子类时先初始化父类
4. 虚拟机启动时指定的主类
5. `MethodHandle` 解析
6. JDK 8+ 接口的 default 方法实现类初始化

## 类加载器体系

JDK 9+ 的三层类加载器体系：

```
Bootstrap ClassLoader (引导类加载器)
    │  加载 <JAVA_HOME>/lib 下的核心类（rt.jar 已不存在，改用 jmod）
    │  由 C++ 实现，getClassLoader() 返回 null
    │  加载 java.lang.String、java.util.HashMap 等
    ▼
Platform ClassLoader (平台类加载器，JDK 9 前叫 Extension ClassLoader)
    │  加载 <JAVA_HOME>/lib/ext 或 java.ext.dirs（JDK 9 前）
    │  JDK 9+ 加载平台模块
    ▼
Application ClassLoader (应用类加载器，也叫 System ClassLoader)
    │  加载 -classpath / -cp 指定的类
    │  我们写的代码都在这里
```

| 加载器 | JDK 8 名称 | JDK 9+ 名称 | 加载路径 |
|--------|-----------|-------------|----------|
| Bootstrap | Bootstrap | Bootstrap | `jmods/` 下的核心模块 |
| 扩展/平台 | Extension | Platform | 平台模块 |
| 应用 | Application/System | Application/System | `-classpath` |

## 双亲委派模型

当一个类加载器收到类加载请求时，它**不自己先加载**，而是委派给父加载器：

```
请求加载 com.example.User
    │
    ▼
Application ClassLoader
    │  委派给父加载器
    ▼
Platform ClassLoader
    │  委派给父加载器
    ▼
Bootstrap ClassLoader
    │  尝试加载（java.lang.* 等核心类）
    │  找不到 → 向下传递
    ▼
Platform ClassLoader
    │  尝试加载（平台模块）
    │  找不到 → 向下传递
    ▼
Application ClassLoader
    │  尝试加载（classpath）
    │  找不到 → ClassNotFoundException
```

**为什么这样设计？**
1. **避免重复加载**：父加载器加载过的类不再加载
2. **安全**：防止核心类被篡改（不能自定义一个 `java.lang.String` 替代）

### 源码实现

```java
// ClassLoader.loadClass() 简化逻辑
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 1. 检查是否已加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                if (parent != null) {
                    // 2. 委派父加载器
                    c = parent.loadClass(name, false);
                } else {
                    // 3. Bootstrap 加载
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器找不到是正常的
            }
            if (c == null) {
                // 4. 父加载器找不到，自己尝试
                c = findClass(name);
            }
        }
        if (resolve) resolveClass(c);
        return c;
    }
}
```

## 破坏双亲委派

历史上有三次"破坏"双亲委派模型的情况——但不是 bug，是有意为之：

### 1. JDBC 的 SPI（JDK 1.6 前）

JDBC 的接口（`java.sql.Driver`）由 Bootstrap 加载，但实现类（`com.mysql.cj.jdbc.Driver`）在 classpath 中。Bootstrap 找不到实现类 → 引入**线程上下文类加载器**（Thread Context ClassLoader）来解决。

### 2. Tomcat 的类隔离

Tomcat 需要支持多个 Web 应用，每个应用的类独立：

```
Bootstrap
  └── System
        ├── Common (共享：Tomcat 自身 + 所有应用)
        │     ├── Catalina (Tomcat 容器)
        │     └── Shared  (所有 Web 应用共享)
        └── Webapp1 ← 优先用自己的类（破坏委派）
        └── Webapp2 ← 优先用自己的类（破坏委派）
```

每个 WebappClassLoader 加载自己 `/WEB-INF/classes` 和 `/WEB-INF/lib` 的类，相互隔离。

### 3. OSGi / 模块化

OSGi 和 JDK 9 模块化系统有自己的类加载图（不再是树状）。

## 自定义 ClassLoader

继承 `ClassLoader`，重写 `findClass()`：

```java
public class MyClassLoader extends ClassLoader {
    private final String classPath;

    public MyClassLoader(String classPath) {
        this.classPath = classPath;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            // 从文件系统读取 .class 文件
            String fileName = classPath + "/" + name.replace('.', '/') + ".class";
            byte[] bytes = Files.readAllBytes(Path.of(fileName));
            
            // 调用 defineClass 将字节数组转为 Class 对象
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}

// 使用
MyClassLoader loader = new MyClassLoader("/path/to/classes");
Class<?> clazz = loader.loadClass("com.example.ExternalPlugin");
Object instance = clazz.getDeclaredConstructor().newInstance();
```

## 类隔离

类隔离的本质：**不同 ClassLoader 加载的同名类在 JVM 中是不同的类**。

```java
// 两个加载器分别加载同一个类文件
MyClassLoader loader1 = new MyClassLoader("/path/version1");
MyClassLoader loader2 = new MyClassLoader("/path/version2");

Class<?> c1 = loader1.loadClass("com.example.Plugin");
Class<?> c2 = loader2.loadClass("com.example.Plugin");

System.out.println(c1 == c2);  // false —— 不同加载器加载的同名类不是同一个类！
```

应用场景：同时运行两个不同版本的同一个 jar 包（比如 Kafka client 0.10 和 2.8 共存）。

## 线程上下文类加载器

```java
// 获取/设置当前线程的上下文类加载器
ClassLoader ctxLoader = Thread.currentThread().getContextClassLoader();
Thread.currentThread().setContextClassLoader(myLoader);
```

线程上下文类加载器默认是 Application ClassLoader——它是 SPI 机制的核心：Bootstrap 加载的接口代码，通过 TCCL 获取到 Application ClassLoader，从而能够加载 classpath 中的实现类。

```java
// JDBC 加载 Driver 的简化逻辑
ServiceLoader<Driver> loader = ServiceLoader.load(Driver.class);
// 内部使用 Thread.currentThread().getContextClassLoader()
```

## 应用场景实战

### 场景一：加密 Class 解密加载

```java
public class DecryptClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] encrypted = readEncryptedClass(name);
        byte[] decrypted = decrypt(encrypted);   // 自定义解密
        return defineClass(name, decrypted, 0, decrypted.length);
    }
}
```

### 场景二：从数据库加载类

```java
public class DBClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = jdbcTemplate.queryForObject(
            "SELECT bytecode FROM class_store WHERE name = ?",
            byte[].class, name
        );
        return defineClass(name, bytes, 0, bytes.length);
    }
}
```

## 最佳实践与踩坑记录

### 常见问题表

| 问题 | 原因 | 修复 |
|------|------|------|
| ClassNotFoundException | 类不在 classpath 中 | 检查依赖和 classpath |
| NoClassDefFoundError | 编译时存在，运行时找不到 | 检查运行时的 classpath |
| NoSuchMethodError | 编译时和运行时 jar 版本不一致 | 排查依赖冲突（mvn dependency:tree） |
| ClassCastException（同名类） | 不同 ClassLoader 加载的同名类 | 确保同一 ClassLoader |
| Metaspace OOM | 类加载过多 | 限制 `-XX:MaxMetaspaceSize`；检查类加载器泄漏 |

### 关键规则

```
1. 一个类的唯一标识 = 全限定名 + ClassLoader
2. 父加载器对子加载器加载的类不可见（向下不可见）
3. spi/provider 模式需要线程上下文类加载器
4. 自定义 ClassLoader 应该重写 findClass()，不要重写 loadClass()
5. 类隔离 = 不同 ClassLoader 加载同名类 = 不同的类
```

## 总结

- 类加载五阶段：加载 → 验证 → 准备 → 解析 → 初始化
- 三层类加载器：Bootstrap → Platform → Application
- 双亲委派：向上委派，逐级尝试；核心类优先由父加载器加载
- SPI 的"破坏"：接口由 Bootstrap 加载，实现由 TCCL 加载
- 自定义 ClassLoader 重写 `findClass()`，调用 `defineClass()`
- 类隔离 = 不同 ClassLoader 加载的同名类 = 不同的类 = 版本隔离
