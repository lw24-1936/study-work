## 存储引擎

**问题：InnoDB 和 MyISAM 的区别？**

| 维度 | InnoDB | MyISAM |
|------|--------|--------|
| 事务 | 支持 | 不支持 |
| 锁粒度 | 行锁 + 表锁 | 只表锁 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 支持（redo log） | 不支持 |
| MVCC | 支持 | 不支持 |
| 索引 | 聚簇索引 | 非聚簇索引 |
| 适用 | 业务表（默认） | 只读、日志 |

```text
InnoDB 是 MySQL 5.5.5+ 默认引擎，支持事务、行锁、MVCC，业务场景首选。
MyISAM 查询快但不支持事务、崩溃不安全，基本弃用。
```

## 索引与 B+Tree

**问题 1：为什么用 B+Tree 不用 B-Tree？**

```text
B+Tree 的优势：
1. 非叶子节点只存索引键（不存数据），一页存更多键，树更矮（IO 次数少）
2. 叶子节点用链表连接，范围查询快（顺序遍历）
3. 查询稳定（数据都在叶子节点，每次查询 IO 次数一致）
```

```text
为什么不用二叉树/红黑树/哈希：
二叉树 —— 退化成链表，树太高
红黑树 —— 树高仍高，磁盘 IO 多
哈希 —— 无法范围查询、无法排序
```

**问题 2：聚簇索引和非聚簇索引？**

```text
聚簇索引（主键索引）—— 叶子节点存完整数据行
非聚簇索引（二级索引）—— 叶子节点存主键值

查询流程（回表）：
二级索引 → 找到主键 → 回表 → 聚簇索引找完整数据
```

**问题 3：索引类型有哪些？**

```text
1. 主键索引（唯一，聚簇）
2. 唯一索引（unique，值唯一）
3. 普通索引（无限制）
4. 前缀索引（长字符串取前缀建索引）
5. 联合索引（多列，遵循最左前缀）
6. 全文索引（FULLTEXT，文本搜索）
```

**问题 4：什么是覆盖索引和索引下推？**

```text
覆盖索引 —— 查询字段都在索引里，无需回表（Using index）。
索引下推（ICP）—— 联合索引中，部分条件先在存储引擎层过滤，
减少回表次数（MySQL 5.6+）。
```

**问题 5：索引失效的场景？**

```text
1. 索引列用函数（WHERE DATE(create_time) = ...）
2. 隐式类型转换（varchar 字段用数字比较，如 phone = 13800138000）
3. LIKE 前缀模糊（LIKE '%xx'）
4. OR 条件（部分列无索引，导致全表扫）
5. 联合索引违反最左前缀
6. 索引列参与运算（WHERE id + 1 = 10）
7. 使用 !=、<>、NOT IN、IS NULL 时优化器可能放弃索引
```

**问题 6：联合索引的最左前缀原则？**

```text
联合索引 (a, b, c)：
命中：WHERE a、WHERE a AND b、WHERE a AND b AND c、WHERE a AND c（a 走索引，c 部分）
失效：WHERE b（跳过 a）、WHERE c

原理：B+Tree 先按 a 排序，a 相同再按 b 排序，跳过最左列无法用索引。
```

## MVCC

**问题 1：什么是 MVCC？**

```text
MVCC（多版本并发控制）：
1. 每条记录有多个版本（版本链）
2. 通过隐藏列实现（DB_TRX_ID 事务 ID、DB_ROLL_PTR 回滚指针）
3. 读操作不加锁，读到一致快照（快照读）
4. 实现读不阻塞写
```

```text
MVCC 的实现依赖：
1. 隐藏列 —— DB_TRX_ID（最近修改事务）、DB_ROLL_PTR（回滚指针）、DB_ROW_ID
2. undo log —— 记录旧版本（版本链）
3. Read View —— 可见性判断（活跃事务列表）
```

**问题 2：MVCC 的可见性判断？**

```text
Read View 记录：当前活跃事务列表、最小事务 ID、下一个事务 ID。

判断一条记录是否可见：
1. 记录的事务 ID < 最小活跃事务 ID → 已提交，可见
2. 记录的事务 ID >= 下一个事务 ID → 未开始，不可见
3. 在活跃列表里 → 未提交，不可见（沿 undo log 版本链找可见版本）
```

**问题 3：MVCC 解决什么问题？**

```text
1. 读不阻塞写（快照读不加锁）
2. 解决脏读、不可重复读（RR 隔离级别下）
3. 提高并发（读不加锁，写仍加锁）

注意：MVCC 解决的是快照读，当前读（SELECT ... FOR UPDATE）仍走锁。
```

## 事务

**问题 1：事务的 ACID？**

```text
A（Atomicity）原子性 —— 要么全成功，要么全失败（undo log）
C（Consistency）一致性 —— 事务前后数据保持一致
I（Isolation）隔离性 —— 事务间隔离（锁 + MVCC）
D（Durability）持久性 —— 提交后永久保存（redo log）
```

**问题 2：隔离级别？**

```text
1. 读未提交（Read Uncommitted）—— 脏读
2. 读已提交（Read Committed）—— 不可重复读
3. 可重复读（Repeatable Read）—— MySQL 默认，通过 MVCC 解决幻读（快照读）
4. 串行化（Serializable）—— 全部解决，性能最差
```

**问题 3：脏读、不可重复读、幻读？**

```text
脏读 —— 读到其他事务未提交的数据
不可重复读 —— 同一事务两次读结果不同（其他事务修改已提交）
幻读 —— 同一事务两次查询行数不同（其他事务插入/删除）
```

**问题 4：隔离级别的实现？**

```text
读未提交 —— 无锁，直接读最新
读已提交 —— 每次查询生成新 Read View（MVCC）
可重复读 —— 事务内第一次查询生成 Read View，复用（MVCC）
串行化 —— 读加共享锁，写加排他锁
```

## 锁

**问题 1：MySQL 的锁类型？**

```text
按粒度：
1. 表锁 —— 锁整张表（DDL、MyISAM）
2. 行锁 —— 锁行（InnoDB 默认）
3. 间隙锁（Gap Lock）—— 锁区间（防幻读）
4. 临键锁（Next-Key Lock）—— 行锁 + 间隙锁（RR 级别默认）

按模式：
1. 共享锁（S）—— 读锁，可并发读
2. 排他锁（X）—— 写锁，独占
3. 意向锁（IS/IX）—— 表级，标记行级锁意图
```

**问题 2：乐观锁和悲观锁？**

```text
悲观锁 —— 认为会冲突，先加锁（SELECT ... FOR UPDATE）
乐观锁 —— 认为不冲突，更新时检查（版本号/CAS）
```

```java
// 乐观锁：版本号
UPDATE product SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = #{oldVersion} AND stock > 0;
```

**问题 3：死锁如何避免？**

```text
1. 按固定顺序加锁（统一锁获取顺序）
2. 缩小事务范围，减少锁持有时间
3. 使用乐观锁
4. 死锁发生后 MySQL 自动检测并回滚一方，应用层重试
```

## 日志与两阶段提交

**问题 1：redo log、undo log、binlog 的区别？**

| 日志 | 作用 | 所属 | 用途 |
|------|------|------|------|
| redo log | 物理日志，记录数据页修改 | InnoDB | 崩溃恢复（持久性） |
| undo log | 逻辑日志，记录旧值 | InnoDB | 回滚 + MVCC |
| binlog | 逻辑日志，记录 SQL/行变更 | MySQL Server | 主从复制、数据恢复 |

```text
redo log —— 循环写（两个文件），WAL 技术，先写日志再写磁盘
binlog —— 追加写，归档
```

**问题 2：两阶段提交（2PC）？**

```text
为什么需要：redo log 和 binlog 是两个文件，要保证两者一致。

流程：
1. prepare 阶段 —— 写入 redo log（prepare 状态）
2. 提交阶段 —— 写 binlog
3. commit —— redo log 标记 commit

崩溃恢复：redo log 是 prepare 且 binlog 完整 → 提交；
redo log 是 prepare 但 binlog 不完整 → 回滚。
保证主从数据一致。
```

## SQL 优化

**问题 1：如何定位慢 SQL？**

```text
1. 开启慢查询日志（slow_query_log + long_query_time = 1）
2. 找到慢 SQL
3. EXPLAIN 分析执行计划
4. 优化（加索引、改写 SQL）
```

**问题 2：EXPLAIN 关注什么？**

```text
type —— 访问类型（system > const > eq_ref > ref > range > index > ALL）
key —— 实际使用的索引（NULL 表示没走索引）
rows —— 预估扫描行数
Extra —— Using index（覆盖索引，好）/ Using filesort（文件排序，需优化）/ Using temporary（临时表，需优化）
```

**问题 3：SQL 优化的常见手段？**

```text
1. 避免 SELECT *（用覆盖索引）
2. 索引列不做运算（函数、隐式转换）
3. 深分页用延迟关联（先查 id 再回表）
4. 避免 OR（用 UNION ALL 或 IN）
5. 批量操作（批量插入）
6. 大数据量分批处理
```

**问题 4：count(*) 如何优化？**

```text
count(*) —— 统计行数（InnoDB 选最小索引遍历，非全表）
count(字段) —— 忽略 NULL
count(1) —— 等价 count(*)

优化：
1. 用 count(*) 而非 count(字段)
2. 精确计数要求高时维护计数表/缓存（如 Redis 计数）
3. 估算可查 information_schema.tables 的 table_rows（不精确）
```

**问题 5：深分页如何优化？**

```text
SELECT * FROM t LIMIT 1000000, 20   # 慢，要扫前 100 万行

优化（延迟关联）：
SELECT * FROM t
WHERE id >= (SELECT id FROM t ORDER BY id LIMIT 1000000, 1)
ORDER BY id LIMIT 20;
```

## 主从复制

**问题 1：主从复制的原理？**

```text
1. 主库写 binlog
2. 从库 IO 线程拉取 binlog，写入 relay log（中继日志）
3. 从库 SQL 线程重放 relay log
4. 异步复制（默认），从库可能延迟
```

```text
半同步复制：主库提交后等至少一个从库确认收到 binlog 才返回（减少丢数据）。
```

**问题 2：读写分离？**

```text
主库写，从库读：
1. 应用层路由（中间件 ShardingSphere、MyCat）
2. 主从延迟问题 —— 读可能读到旧数据

解决延迟：
1. 强制走主库（关键读）
2. 半同步复制减少延迟
3. 延迟检测，延迟时切主库
```

## 分库分表

**问题 1：为什么要分库分表？**

```text
单表数据量大（千万级）时：
1. 查询慢（B+Tree 变深、内存放不下）
2. 单库连接数、IO、容量瓶颈

分库 —— 分散到多个库（容量、连接数）
分表 —— 单库多表（单表数据量控制）
```

**问题 2：分库分表的方式？**

```text
1. 垂直分库 —— 按业务拆（用户库、订单库、商品库）
2. 垂直分表 —— 按字段拆（大字段独立、热点字段独立）
3. 水平分库分表 —— 按行拆分，同表数据分到多库多表

水平拆分策略：
1. 取模 —— hash(key) % N（扩容要重新分布）
2. 范围 —— 按时间/ID 范围（扩容简单，可能热点）
3. 一致性哈希 —— 虚拟节点减少扩容迁移
```

**问题 3：分库分表带来的问题？**

```text
1. 跨库 JOIN 困难（冗余字段、应用层聚合）
2. 分布式事务（跨库事务难保证）
3. 全局唯一 ID（雪花算法、号段模式）
4. 分页、排序跨分片聚合
5. 扩容数据迁移

用中间件解决：ShardingSphere、MyCat。
```

**问题 4：分库分表后全局 ID 如何生成？**

```text
1. 雪花算法（Snowflake）—— 时间戳 + 机器号 + 序列号，趋势递增，分布式唯一
2. 号段模式（Leaf）—— 批量取号段，减少数据库访问
3. 数据库自增表 —— 单独 ID 表（有性能瓶颈）
4. Redis 自增 / UUID（无序，影响索引）
```
