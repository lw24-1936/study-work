## 线程基础

**问题 1：线程的创建方式？**

```text
1. 继承 Thread，重写 run()
2. 实现 Runnable（推荐，任务与线程分离）
3. 实现 Callable（有返回值，可抛异常，配合 Future）
4. 线程池（实际开发主流，不手动 new 线程）
```

```java
// Callable + FutureTask
Callable<Integer> task = () -> { return 42; };
FutureTask<Integer> ft = new FutureTask<>(task);
new Thread(ft).start();
Integer result = ft.get();   // 阻塞获取结果
```

**问题 2：start() 和 run() 的区别？**

```text
start() —— 启动新线程，JVM 调用 run()（异步）
run() —— 普通方法调用，当前线程执行（同步，不启动新线程）
```

**问题 3：线程的状态及转换？**

```text
NEW（新建）→ start() → RUNNABLE（可运行，含就绪+运行中）
RUNNABLE ←→ BLOCKED（获取 synchronized 锁失败进入，获得锁退出）
RUNNABLE ←→ WAITING（wait/join/LockSupport.park，需 notify/其他线程结束唤醒）
RUNNABLE ←→ TIMED_WAITING（sleep/带超时的 wait/join）
RUNNABLE → TERMINATED（run 执行完）
```

**问题 4：sleep 和 wait 的区别？**

| 维度 | sleep | wait |
|------|-------|------|
| 来源 | Thread 静态方法 | Object 方法 |
| 锁 | 不释放锁 | 释放锁 |
| 唤醒 | 时间到自动醒 | notify/notifyAll 唤醒 |
| 位置 | 任意位置 | 必须在 synchronized 内 |

**问题 5：线程中断？**

```text
interrupt() 只是设置中断标志，不真正中断线程。
线程应通过 isInterrupted() 检查标志，配合阻塞方法的 InterruptedException 响应中断。
```

## synchronized

**问题 1：synchronized 的原理？**

```text
synchronized 基于对象头的 monitor（监视器）：
1. 进入同步块 → 获取对象的 monitor（monitorenter 指令）
2. 同一时刻只有一个线程持有 monitor
3. 退出同步块 → 释放 monitor（monitorexit 指令）
4. monitor 依赖操作系统的互斥量（Mutex Lock），重量级时涉及用户态内核态切换
```

**问题 2：synchronized 的锁升级？**

```text
锁升级过程（JDK 6 优化，不可逆）：
无锁 → 偏向锁 → 轻量级锁 → 重量级锁

1. 偏向锁 —— 只有一个线程访问，对象头记录线程 ID，加锁解锁无需 CAS
2. 轻量级锁 —— 竞争不激烈，线程在栈帧建锁记录，CAS 自旋尝试
3. 重量级锁 —— 竞争激烈，自旋失败膨胀为 monitor，未获锁线程阻塞（OS 调度）
```

```text
锁升级的条件：出现竞争且自旋仍无法获得锁时升级。
自旋锁：不阻塞线程，空转重试，避免线程切换开销，适合锁持有时间短的场景。
```

**问题 3：synchronized 的用法？**

```java
// 1. 修饰实例方法（锁 this）
public synchronized void method() { }

// 2. 修饰代码块（锁指定对象）
synchronized (obj) { }

// 3. 修饰静态方法（锁 Class 对象）
public static synchronized void method() { }
```

**问题 4：synchronized 锁的是什么？**

```text
实例方法 → 锁当前实例对象（this）
静态方法 → 锁类的 Class 对象
代码块 → 锁括号里的对象
不同对象上的 synchronized 不互斥。
```

## volatile

**问题 1：volatile 的作用？**

```text
volatile 保证：
1. 可见性 —— 修改立即写回主内存，其他线程立即可见（JMM：read/load/use 与 write 关联）
2. 有序性 —— 禁止指令重排（内存屏障）

不保证：
1. 原子性 —— i++ 这类复合操作仍不安全（读-改-写三步）
```

```java
volatile boolean flag = true;

// 线程 A 修改 flag，线程 B 立即可见
// 双重检查锁单例的 instance 用 volatile 防止重排
```

**问题 2：双重检查锁单例为什么要 volatile？**

```java
public class Singleton {
    private static volatile Singleton instance;   // 必须 volatile

    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

```text
new Singleton() 分三步：
1. 分配内存
2. 初始化对象
3. 将引用指向内存（instance 赋值）

无 volatile 时 2 和 3 可能重排，其他线程看到 instance 非 null 但对象未初始化完成，
拿到半初始化对象 → 出错。volatile 禁止该重排。
```

**问题 3：volatile 和 synchronized 的区别？**

```text
volatile —— 只保证可见性和有序性，不保证原子性，轻量，修饰变量
synchronized —— 保证可见性、有序性、原子性，重量，修饰方法/代码块
```

## CAS 与 AQS

**问题 1：CAS 是什么？**

```text
CAS（Compare And Swap）比较并交换，无锁原子操作：
1. 读取内存当前值 V
2. 与预期值 A 比较
3. 相等 → 更新为新值 B；不等 → 重试（自旋）

底层依赖 CPU 的 cmpxchg 指令，由 Unsafe 类提供（native）。
```

```java
// AtomicInteger 的 incrementAndGet 本质就是 CAS 自旋
AtomicInteger ai = new AtomicInteger(0);
ai.incrementAndGet();
```

```text
CAS 的缺点：
1. ABA 问题 —— 值 A→B→A，CAS 以为没变，实际变过
   解决：加版本号（AtomicStampedReference / AtomicMarkableReference）
2. 自旋开销 —— 竞争激烈时自旋浪费 CPU
3. 只能保证单个变量原子性
```

**问题 2：AQS 是什么？**

```text
AQS（AbstractQueuedSynchronizer）是并发框架的基石：
1. state（int volatile）—— 同步状态（锁重入次数、信号量计数）
2. CLH 队列 —— 未获取到锁的线程排队等待（双向链表）
3. 模板方法模式 —— acquire/release 骨架，tryAcquire/tryRelease 由子类实现

基于 AQS 的组件：ReentrantLock、ReentrantReadWriteLock、CountDownLatch、
Semaphore、CyclicBarrier、ThreadPoolExecutor 的 Worker。
```

## Lock 与 synchronized

**问题 1：ReentrantLock 和 synchronized 的区别？**

| 维度 | synchronized | ReentrantLock |
|------|-------------|---------------|
| 实现 | JVM 关键字，monitor | JDK 类，AQS |
| 加锁释放 | 自动 | 手动 lock/unlock（finally 中 unlock） |
| 公平锁 | 非公平 | 可公平可非公平（构造参数） |
| 可中断 | 不可 | lockInterruptibly() |
| 尝试加锁 | 不可 | tryLock()/tryLock(time) |
| Condition | 单个等待队列 | 多个 Condition 精确唤醒 |
| 可重入 | 是 | 是 |

```java
ReentrantLock lock = new ReentrantLock(true);   // true = 公平锁
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();                               // 必须 finally 释放
}
```

**问题 2：公平锁和非公平锁？**

```text
公平锁 —— 按队列顺序获取锁，线程不会饿死，但吞吐低（要唤醒队列头）
非公平锁 —— 新线程可直接抢占，吞吐高，可能饥饿
synchronized 非公平，ReentrantLock 默认非公平。
```

**问题 3：什么是可重入锁？**

```text
可重入锁：同一线程可多次获取同一把锁（synchronized、ReentrantLock 都支持）。
原理：记录持有线程 + 重入次数，重入次数归零才真正释放。

可重入的必要性：父类 synchronized 方法调用子类 synchronized 方法，
同一线程重入不死锁。
```

**问题 4：读写锁 ReentrantReadWriteLock？**

```text
读锁共享、写锁互斥，适合读多写少：
1. 读锁 —— 多个线程可同时持有（只要无写锁）
2. 写锁 —— 独占
3. 写锁可降级为读锁，读锁不能升级为写锁
```

## ThreadLocal

**问题 1：ThreadLocal 的原理？**

```text
每个 Thread 有一个 ThreadLocalMap，key 是 ThreadLocal 对象（弱引用），
value 是线程私有值。

Thread → ThreadLocalMap → Entry(ThreadLocal, value)
线程之间互不干扰，实现线程隔离。
```

```java
ThreadLocal<User> userHolder = new ThreadLocal<>();
userHolder.set(user);
User u = userHolder.get();
userHolder.remove();   // 用后必须 remove
```

**问题 2：ThreadLocal 的内存泄漏？**

```text
原因：
ThreadLocalMap 的 Entry 中，key（ThreadLocal）是弱引用，value 是强引用。
ThreadLocal 对象被 GC 后，key 变 null，但 value 仍被 Entry 强引用，
且 Entry 被 Thread 的 ThreadLocalMap 引用，Thread 存活（线程池）则 value 无法回收。

解决：
1. 用后调用 remove()，删除 Entry（最根本）
2. ThreadLocal 定义成 static，避免频繁创建
3. get/set 时也会清理 key 为 null 的脏 Entry
```

**问题 3：ThreadLocal 的应用场景？**

```text
1. 数据库连接/Session 管理（每个线程独立连接）
2. 请求上下文传递（用户信息、traceId）
3. 日期格式化工具（SimpleDateFormat 非线程安全，用 ThreadLocal 隔离）
4. Spring 事务管理（@Transactional 用 ThreadLocal 保存连接）
```

## ThreadPoolExecutor

**问题 1：线程池的 7 个参数？**

```java
new ThreadPoolExecutor(
    corePoolSize,       // 核心线程数（常驻）
    maximumPoolSize,    // 最大线程数
    keepAliveTime,      // 非核心线程空闲存活时间
    unit,               // 时间单位
    workQueue,          // 任务队列（阻塞队列）
    threadFactory,      // 线程工厂（命名线程）
    handler);           // 拒绝策略
```

**问题 2：线程池的执行流程？**

```text
1. 当前线程数 < corePoolSize → 创建核心线程执行（即使有空闲核心线程也新建）
2. 核心线程满 → 任务放入 workQueue 排队
3. 队列满 → 创建非核心线程（到 maximumPoolSize）
4. 线程数 = maximumPoolSize 且队列满 → 执行拒绝策略
```

```text
常见误解：不是队列一有任务就先建线程，而是核心线程满了才入队。
所以 corePoolSize=0 时，任务先入队，队列满了才建线程。
```

**问题 3：拒绝策略有哪些？**

```text
1. AbortPolicy —— 抛 RejectedExecutionException（默认）
2. CallerRunsPolicy —— 由调用者线程执行（不丢弃，可降级保护）
3. DiscardPolicy —— 静默丢弃
4. DiscardOldestPolicy —— 丢弃队列最老的任务，再重试提交
```

**问题 4：线程池参数如何设置？**

```text
CPU 密集型 → corePoolSize = CPU 核数 + 1（减少上下文切换）
IO 密集型 → corePoolSize = CPU 核数 × 2（或核数 / (1 - 阻塞系数)，阻塞系数约 0.8-0.9）

更准确：根据任务类型压测，观察 CPU 利用率、队列积压、拒绝次数动态调整。
```

**问题 5：为什么不推荐 Executors 创建线程池？**

```text
1. FixedThreadPool / SingleThreadPool —— 用无界 LinkedBlockingQueue，任务无限堆积 OOM
2. CachedThreadPool —— 最大线程数 Integer.MAX_VALUE，线程无限创建 OOM

应手动 new ThreadPoolExecutor，显式指定有界队列和拒绝策略。
```

**问题 6：线程池如何监控？**

```text
1. getPoolSize()/getActiveCount()/getQueue().size() 观测
2. 继承 ThreadPoolExecutor 重写 beforeExecute/afterExecute 记录耗时
3. 接入监控平台（线程池参数动态调整：美团动态线程池思路）
```

## CompletableFuture

**问题 1：CompletableFuture 的作用？**

```text
CompletableFuture（JDK 8）异步编程工具，解决 Future 的缺点：
Future 只能阻塞 get，无法回调、无法组合。
CompletableFuture 支持链式回调、异常处理、多任务组合。
```

```java
CompletableFuture.supplyAsync(() -> fetchData())
    .thenApply(data -> process(data))       // 转换
    .thenAccept(result -> save(result))     // 消费
    .exceptionally(e -> handleError(e));    // 异常兜底
```

**问题 2：CompletableFuture 的核心方法？**

```text
创建：supplyAsync（有返回值）、runAsync（无返回值）
转换：thenApply（有返回值）、thenAccept（消费）、thenRun（执行）
组合：thenCompose（依赖前一个结果）、thenCombine（合并两个结果）
聚合：allOf（全部完成）、anyOf（任一完成）
异常：exceptionally（兜底）、handle（无论成败都处理）
```

**问题 3：CompletableFuture 的线程池？**

```text
不传线程池 → 默认 ForkJoinPool.commonPool()（守护线程，核心数-1）
传线程池 → 用自定义线程池（生产环境推荐，避免影响其他任务）
```

## 原子类

**问题 1：原子类有哪些？**

```text
基本类型：AtomicInteger、AtomicLong、AtomicBoolean
数组：AtomicIntegerArray、AtomicLongArray
引用：AtomicReference、AtomicStampedReference（带版本号解决 ABA）
累加器：LongAdder、DoubleAdder（JDK 8，高并发下性能更好）
```

**问题 2：AtomicInteger 的原理？**

```text
基于 CAS + volatile：
1. 内部 value 用 volatile 修饰，保证可见性
2. incrementAndGet() 用 CAS 自旋更新
```

```java
AtomicInteger ai = new AtomicInteger(0);
ai.incrementAndGet();    // CAS：expect 0 → update 1
ai.compareAndSet(1, 2);  // 若当前是 1 则设为 2
```

**问题 3：LongAdder 为什么比 AtomicLong 快？**

```text
AtomicLong 高并发下 CAS 竞争激烈，自旋重试多，性能下降。
LongAdder 用分段累加（base + Cell[]），线程分散到不同 Cell 累加，
最后 sum() 汇总，减少竞争，适合高并发计数（并发下精确值可稍延迟）。
```

## 并发工具类

**问题：CountDownLatch、CyclicBarrier、Semaphore 的区别？**

| 工具 | 作用 | 可复用 | 等待方向 |
|------|------|--------|---------|
| CountDownLatch | 一个/多个线程等 N 个任务完成 | 否（一次性） | 主线程等子任务 |
| CyclicBarrier | N 个线程互相等待到齐再一起走 | 是（可循环） | 线程互相等 |
| Semaphore | 控制同时访问资源的线程数（限流） | 是 | 获取许可 |

```java
// CountDownLatch：主线程等 3 个子任务
CountDownLatch latch = new CountDownLatch(3);
latch.countDown();   // 子任务完成 -1
latch.await();       // 主线程阻塞直到 0

// CyclicBarrier：3 个线程到齐后一起执行
CyclicBarrier barrier = new CyclicBarrier(3, () -> doSomething());
barrier.await();

// Semaphore：最多 5 个线程同时访问
Semaphore semaphore = new Semaphore(5);
semaphore.acquire();  // 获取许可（可阻塞）
semaphore.release();  // 释放许可
```

## 死锁

**问题 1：死锁的四个必要条件？**

```text
1. 互斥 —— 资源一次只能被一个线程持有
2. 持有并等待 —— 持有资源的同时等待其他资源
3. 不可剥夺 —— 持有的资源不能被强制抢占
4. 循环等待 —— 线程间形成资源等待环

四个条件同时满足才死锁，破坏任一即可避免。
```

**问题 2：死锁如何排查？**

```text
1. jstack <pid> 查看线程栈，找 BLOCKED 线程和锁信息
2. jconsole / jvisualvm 图形化检测死锁
3. 分析线程 dump 中 "Found one Java-level deadlock"
```

**问题 3：如何避免死锁？**

```text
1. 按固定顺序加锁（破坏循环等待）
2. 加锁超时（tryLock(time)，破坏持有并等待）
3. 减少锁粒度，缩短锁持有时间
4. 用无锁结构（CAS）或并发容器替代
```

## happens-before

**问题：什么是 happens-before 规则？**

```text
happens-before 是 JMM 定义的可见性规则，前一个操作的结果对后一个操作可见。
核心规则：
1. 程序顺序规则 —— 单线程内，前面的操作 happens-before 后面的
2. volatile 规则 —— volatile 写 happens-before 后续 volatile 读
3. 锁规则 —— unlock happens-before 后续 lock
4. 传递性 —— A hb B，B hb C，则 A hb C
5. start 规则 —— 线程 start() 前的操作 hb 线程内任意操作
6. join 规则 —— 线程内操作 hb join() 返回后的操作
```

```text
作用：编译器和处理器可重排指令，但必须遵守 happens-before，保证正确同步的程序可见性。
```
