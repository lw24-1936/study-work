## JVM 内存结构

**问题 1：JVM 运行时内存区域？**

```text
1. 堆（Heap）—— 对象实例，GC 主战场，线程共享
2. 虚拟机栈（Stack）—— 方法调用、局部变量、栈帧，线程私有
3. 方法区（Method Area）—— 类信息、常量、静态变量，线程共享（JDK 8 元空间）
4. 程序计数器（PC）—— 当前指令地址，线程私有（唯一不 OOM 的区域）
5. 本地方法栈 —— native 方法，线程私有
6. 直接内存（Direct Memory）—— NIO 堆外内存，不受堆大小限制
```

**问题 2：堆的结构？**

```text
堆分新生代和老年代（分代假设：大部分对象朝生夕死）：
1. 新生代（Young）—— Eden + Survivor0 + Survivor1（默认 8:1:1）
2. 老年代（Old）—— 长期存活对象

对象分配流程：
Eden 分配 → Minor GC 存活 → Survivor 来回拷贝（年龄 +1）
→ 年龄到 15（默认）→ 晋升老年代
```

**问题 3：JDK 8 的内存变化？**

```text
JDK 7 之前：方法区 = 永久代（PermGen，堆内，有 -XX:MaxPermSize 上限）
JDK 8 之后：方法区 = 元空间（Metaspace，本地内存，默认无上限）

变化原因：
1. 永久代容量固定，类加载多易 OOM
2. 元空间用本地内存，动态扩展
3. 字符串常量池从永久代移到堆（JDK 7 起）
```

**问题 4：栈溢出和堆溢出的区别？**

```text
StackOverflowError —— 栈溢出（递归过深、无限调用链）
OutOfMemoryError: Java heap space —— 堆溢出（对象过多、内存泄漏）
OutOfMemoryError: Metaspace —— 元空间溢出（动态生成类过多）
OutOfMemoryError: Direct buffer memory —— 直接内存溢出
```

## 对象创建与内存布局

**问题 1：对象的创建过程？**

```text
1. 类加载检查 —— 常量池能否定位到类符号引用，类是否已加载
2. 分配内存 —— 指针碰撞（规整）或空闲列表（碎片），可能触发 GC
3. 内存初始化 —— 分配到的空间初始化为零值
4. 设置对象头 —— 哈希码、GC 分代年龄、类型指针等
5. 执行 <init> —— 构造方法初始化
```

```text
并发分配内存的解决：
CAS + 失败重试；TLAB（线程本地分配缓冲，每个线程在 Eden 预分配一块）。
```

**问题 2：对象的内存布局？**

```text
对象 = 对象头 + 实例数据 + 对齐填充

1. 对象头（Mark Word + 类型指针）：
   Mark Word —— 哈希码、GC 分代年龄、锁状态标志、偏向线程 ID
   类型指针 —— 指向类元数据（确定对象是哪个类的实例）
   数组对象还有长度字段
2. 实例数据 —— 各字段（含父类字段），相同宽度字段放在一起
3. 对齐填充 —— 保证对象大小是 8 字节的整数倍
```

**问题 3：什么是指针压缩？**

```text
64 位 JVM 默认开启指针压缩（-XX:+UseCompressedOops）：
对象引用从 8 字节压缩到 4 字节（堆小于 32G 时生效），节省内存。
堆超过 32G 关闭压缩，指针变 8 字节，内存占用上升。
```

## GC 垃圾回收

**问题 1：如何判断对象可回收？**

```text
1. 引用计数法 —— 有引用 +1，无引用 -1，计数为 0 回收
   缺点：循环引用无法回收（A 引用 B，B 引用 A）
2. 可达性分析 —— 从 GC Roots 出发遍历引用链，不可达的对象回收（JVM 主流）
```

```text
GC Roots 有哪些：
1. 虚拟机栈中引用的对象（局部变量）
2. 方法区静态变量引用的对象
3. 常量引用的对象
4. JNI（本地方法栈）引用的对象
5. 被 synchronized 持有的对象
```

**问题 2：GC 算法有哪些？**

```text
1. 标记-清除（Mark-Sweep）—— 标记存活，清除未标记，产生碎片
2. 标记-复制（Mark-Copy）—— 存活对象复制到另一区，无碎片但浪费空间（新生代）
3. 标记-整理（Mark-Compact）—— 存活对象向一端移动，无碎片（老年代）
```

**问题 3：Minor GC、Major GC、Full GC？**

```text
Minor GC —— 新生代 GC（频繁，快，STW 短）
Major GC —— 老年代 GC（通常伴随 Minor GC，CMS 单独回收老年代）
Full GC —— 整个堆 + 方法区 GC（慢，STW 长，尽量避免）
```

```text
触发 Full GC 的场景：
1. 老年代空间不足
2. 元空间不足
3. System.gc() 显式调用
4. Minor GC 后晋升对象太多，老年代放不下
```

**问题 4：GC 的吞吐量和停顿时间？**

```text
吞吐量 = 运行用户代码时间 / (运行用户代码时间 + GC 时间)
停顿时间 = 单次 GC 的 STW 时长

两者是矛盾：追求吞吐量选 Parallel，追求低延迟选 G1/ZGC。
```

## 垃圾收集器

**问题 1：常见的垃圾收集器？**

```text
新生代：Serial（单线程）、ParNew（多线程，配合 CMS）、Parallel Scavenge（吞吐优先）
老年代：Serial Old、CMS（低延迟，已废弃）、Parallel Old
整堆：G1（JDK 9+ 默认）、ZGC（JDK 15 正式）、Shenandoah
```

**问题 2：CMS 的特点和问题？**

```text
CMS 目标：最短停顿时间，四阶段：
1. 初始标记（STW，标记 GC Roots 直接关联）
2. 并发标记（与用户线程并发）
3. 重新标记（STW，修正并发期间变化）
4. 并发清除（与用户线程并发）

问题：
1. 并发标记占用 CPU
2. 产生浮动垃圾，预留空间不足触发 Concurrent Mode Failure → 退化 Serial Old
3. 标记-清除产生碎片，碎片化严重时触发 Full GC
JDK 9 标记废弃，JDK 14 移除。
```

**问题 3：Parallel 收集器？**

```text
Parallel Scavenge + Parallel Old（JDK 8 默认）：
1. 多线程并行 GC，吞吐优先
2. 目标参数 -XX:MaxGCPauseMillis / -XX:GCTimeRatio
3. 适合后台批处理、对停顿不敏感的场景
```

## 类加载与双亲委派

**问题 1：类加载过程？**

```text
类加载的 5 个阶段：
加载 → 验证 → 准备 → 解析 → 初始化

加载 —— 读字节码生成 Class 对象
验证 —— 校验字节码合法性（文件格式、元数据、字节码、符号引用）
准备 —— 分配内存，静态变量赋默认值（零值）
解析 —— 符号引用转直接引用
初始化 —— 执行静态代码块、静态变量赋值（<clinit>）
```

**问题 2：双亲委派模型？**

```text
双亲委派：类加载请求先委派给父加载器，父加载器能加载则父加载，否则子加载。

加载器层次：
Bootstrap ClassLoader（启动类加载器，加载 rt.jar 核心类）
→ Platform/Extension ClassLoader（扩展类加载器，加载扩展类）
→ Application ClassLoader（应用类加载器，加载 classpath）
→ 自定义 ClassLoader
```

```java
// loadClass 核心逻辑
ClassLoader parent = getParent();
if (parent != null) {
    c = parent.loadClass(name, false);   // 先委派父加载器
}
if (c == null) {
    c = findClass(name);                  // 父加载不了，自己加载
}
```

**问题 3：为什么用双亲委派？**

```text
1. 避免重复加载 —— 父加载器加载过，子不重复加载（每个类只加载一次）
2. 安全 —— 防止篡改核心类（自定义 java.lang.String 不会被加载，核心类由 Bootstrap 加载）
```

**问题 4：如何破坏双亲委派？**

```text
1. SPI（JDBC）—— 核心类接口由 Bootstrap 加载，实现类由应用类加载器加载，
   Bootstrap 加载的类无法委派给子加载器，用线程上下文类加载器（Thread Context ClassLoader）反向加载
2. Tomcat —— 每个 Web 应用独立类加载器，先自己加载再委派父加载器（WebappClassLoader）
3. 热部署/热替换 —— OSGi 每个模块独立类加载器
```

## G1 与 ZGC

**问题 1：G1 的特点？**

```text
G1（Garbage First，JDK 9+ 默认）：
1. 区域化 —— 堆分成多个大小相等的 Region（1M-32M），不要求连续
2. 可预测停顿 —— 设置 -XX:MaxGCPauseMillis 停顿目标
3. 优先回收垃圾最多的 Region（Garbage First 由来）
4. Region 逻辑上分 Eden/Survivor/Old/Humongous（大对象）

过程：
年轻代收集 → 并发标记 → 混合回收（回收部分老年代 Region）。
```

```text
G1 的关键技术：
1. RSet（记忆集）—— 记录跨 Region 引用，避免全堆扫描
2. SATB（快照标记）—— 并发标记期间的一致性
```

**问题 2：ZGC 的特点？**

```text
ZGC（JDK 11 实验，JDK 15 正式）：
1. 极低停顿 —— 目标 < 10ms（亚毫秒到几毫秒），停顿与堆大小无关
2. 染色指针（Colored Pointers）—— 指针本身存标记信息，并发标记/重分配
3. 读屏障 —— 并发移动对象时修正引用
4. 适合大堆（TB 级）+ 低延迟场景

JDK 21 分代 ZGC，进一步优化。
```

**问题 3：G1 和 ZGC 如何选择？**

```text
小堆、吞吐优先 → Parallel
4G 以上、可预测停顿 → G1
超大堆、极低延迟 → ZGC
JDK 8 遗留系统 → CMS（已废弃）或 Parallel
```

## 引用类型

**问题：强引用、软引用、弱引用、虚引用？**

| 类型 | 回收时机 | 用途 |
|------|---------|------|
| 强引用 | 永不回收（GC Roots 可达） | 普通 new 对象 |
| 软引用 SoftReference | 内存不足时回收 | 缓存（图片缓存） |
| 弱引用 WeakReference | 下次 GC 必回收 | ThreadLocal key、WeakHashMap |
| 虚引用 PhantomReference | 随时回收，仅通知 | 对象回收跟踪、直接内存清理 |

```java
SoftReference<byte[]> soft = new SoftReference<>(new byte[1024*1024]);
WeakReference<Object> weak = new WeakReference<>(obj);
// WeakHashMap：key 弱引用，key 被 GC 后 Entry 自动清除
```

## OOM 排查

**问题 1：OOM 如何排查？**

```text
1. 开启 HeapDump：-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=xxx
2. 导出堆转储文件（或 jmap -dump:format=b,file=heap.hprof <pid>）
3. MAT / JProfiler 分析（Dominator Tree 找大对象、泄漏对象）
4. 定位泄漏源（集合未清理、静态缓存无限增长、连接未关闭）
5. 修复 + 验证
```

**问题 2：常见 OOM 类型？**

```text
1. Java heap space —— 堆内存不足（大对象、内存泄漏）
2. Metaspace —— 元空间不足（动态生成类过多）
3. GC overhead limit exceeded —— GC 时间占比过高（内存不足反复 GC）
4. Direct buffer memory —— 直接内存不足（NIO 未释放）
5. StackOverflowError —— 栈溢出（递归过深）
6. unable to create new native thread —— 线程数达上限（线程泄漏）
```

**问题 3：内存泄漏的常见原因？**

```text
1. 静态集合持有对象（static Map 只增不减）
2. 连接/流未关闭（数据库连接、IO 流）
3. ThreadLocal 未 remove（线程池场景）
4. 监听器/回调未注销
5. 单例持有短生命周期对象
```

**问题 4：JVM 常用排查工具？**

```text
jps —— 查看 Java 进程
jstack —— 线程栈（排查死锁、CPU 高）
jmap —— 堆内存 dump
jstat —— GC 统计（jstat -gcutil <pid> 1000）
jinfo —— JVM 参数
jconsole/jvisualvm —— 图形化监控
Arthas —— 阿里在线诊断（trace、watch、heapdump）
```

## JVM 调优

**问题 1：常用 JVM 参数？**

```text
堆：-Xms（初始堆）-Xmx（最大堆）-Xmn（新生代）-Xss（栈大小）
元空间：-XX:MetaspaceSize -XX:MaxMetaspaceSize
GC 日志：-Xlog:gc（JDK 9+）
HeapDump：-XX:+HeapDumpOnOutOfMemoryError
垃圾收集器：-XX:+UseG1GC / -XX:+UseZGC
停顿目标：-XX:MaxGCPauseMillis
```

**问题 2：JVM 调优的思路？**

```text
1. 明确目标 —— 低延迟还是高吞吐
2. 选收集器 —— 吞吐选 Parallel，低延迟选 G1/ZGC
3. 设堆大小 —— -Xms = -Xmx（避免动态扩容），-Xmn 合理
4. 观察 GC 日志 —— 停顿时间、频率、回收效果
5. 逐步调整，一次只改一个参数，对比效果
6. 优先解决代码问题（内存泄漏、对象创建），再调参数
```

## 逃逸分析与栈上分配

**问题：什么是逃逸分析？**

```text
逃逸分析：分析对象的作用域，判断对象是否逃出方法/线程。

对象未逃逸 → 可优化：
1. 栈上分配 —— 对象分配在栈帧，方法结束自动销毁，无需 GC
2. 标量替换 —— 对象拆成基本类型成员，分配到栈
3. 同步消除 —— 无竞争的锁可去掉

逃逸分析默认开启（-XX:+DoEscapeAnalysis），是 JIT 优化。
```

```text
注意：栈上分配受 JVM 实现限制，实际对象仍多在堆上分配，但配合 TLAB 降低分配成本。
```
