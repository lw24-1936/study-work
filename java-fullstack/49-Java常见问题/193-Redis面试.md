## 数据结构

**问题 1：Redis 有哪些数据类型？**

```text
基础类型：
1. String —— 字符串（最基础）
2. List —— 列表（队列、栈）
3. Set —— 集合（去重）
4. Hash —— 哈希（对象）
5. ZSet —— 有序集合（排行榜）

扩展类型：
6. Bitmap —— 位图（签到、布隆）
7. HyperLogLog —— 基数统计（UV，误差约 0.81%）
8. Geo —— 地理位置（附近的人）
9. Stream —— 消息流（消费者组，5.0+）
```

**问题 2：各数据类型的应用场景？**

```text
String —— 缓存、计数器、分布式锁、session
List —— 消息队列、最新列表、栈
Set —— 去重、共同好友、点赞集合
Hash —— 对象存储、购物车
ZSet —— 排行榜、延迟队列（score 存时间戳）
Bitmap —— 签到、活跃统计
HyperLogLog —— UV 统计
Geo —— 附近的人、距离计算
```

**问题 3：Redis 为什么快？**

```text
1. 内存操作 —— 数据在内存
2. 单线程（命令执行单线程）—— 无锁竞争、无上下文切换
3. IO 多路复用 —— epoll，一个线程处理多个连接
4. 高效数据结构 —— SDS、跳表、压缩列表

Redis 6.0 引入多线程，但只用于网络 IO 读写和协议解析，
命令执行仍是单线程（保持原子性，避免锁）。
```

## 底层数据结构

**问题 1：Redis 的底层数据结构？**

```text
1. SDS（简单动态字符串）—— 带长度的字符串，O(1) 取长度，二进制安全
2. 双向链表（listNode）
3. 压缩列表（ziplist）—— 连续内存，省空间（小数据用，7.0 后 listpack 替代）
4. 哈希表（dict）—— 渐进式 rehash
5. 整数集合（intset）
6. 跳表（skiplist）—— ZSet 用，O(log n) 范围查询
```

**问题 2：各类型的底层编码？**

```text
String —— SDS（int/embstr/raw）
List —— quicklist（3.2+，linkedlist + ziplist 组合）
Hash —— ziplist/listpack + hashtable（小数据用压缩，大数据用哈希表）
Set —— intset + hashtable
ZSet —— ziplist/listpack + skiplist + dict
```

**问题 3：跳表和红黑树的区别？为什么 ZSet 用跳表？**

```text
1. 跳表实现简单（红黑树复杂）
2. 范围查询天然有序（跳表遍历链表即可）
3. 插入删除无需复杂的旋转平衡
跳表用多层索引实现 O(log n) 查找，层数随机。
```

## 持久化

**问题 1：RDB 和 AOF 的区别？**

| 维度 | RDB | AOF |
|------|-----|-----|
| 原理 | 快照（全量内存 dump） | 追加写命令（增量日志） |
| 文件 | dump.rdb | appendonly.aof |
| 恢复速度 | 快（直接加载快照） | 慢（重放命令） |
| 数据丢失 | 可能丢最近快照后的数据 | 更少（取决于同步策略） |
| 性能 | 高（fork 子进程写） | 较低（追加写） |
| 体积 | 小（压缩） | 大（命令日志） |

```text
RDB 触发：save（阻塞）/ bgsave（fork 子进程，写时复制）/ 配置定时。
AOF 同步策略：always（每命令）/ everysec（每秒，默认）/ no（OS 决定）。
```

**问题 2：持久化策略怎么选？**

```text
1. 只用 RDB —— 恢复快，可能丢数据
2. 只用 AOF —— 数据安全，性能较低、文件大
3. 混合持久化（Redis 4.0+，推荐）—— AOF 重写时用 RDB 快照 + 增量 AOF，
   兼顾恢复速度和数据安全
```

**问题 3：AOF 重写机制？**

```text
AOF 文件持续增长，重写（rewrite）把冗余命令合并成最小命令集：
1. fork 子进程根据当前内存数据生成新 AOF（不是读旧 AOF）
2. 重写期间新命令写入 AOF 重写缓冲
3. 重写完成后追加缓冲，替换旧文件
目的：压缩 AOF 体积，加快恢复。
```

## 过期策略与淘汰策略

**问题 1：Redis 的过期删除策略？**

```text
惰性删除 + 定期删除：
1. 惰性删除 —— 访问 key 时检查是否过期，过期则删（省 CPU，可能残留）
2. 定期删除 —— 定期随机抽查一批 key 删除过期（平衡 CPU 和内存）

两者结合，不采用定时删除（每个 key 定时器开销太大）。
```

**问题 2：内存淘汰策略有哪些？**

```text
1. noeviction —— 不淘汰，写满报错（默认）
2. allkeys-lru —— 所有 key 里淘汰最久未使用（常用）
3. volatile-lru —— 有过期时间的 key 里淘汰最久未使用
4. allkeys-lfu —— 所有 key 里淘汰最不常用（4.0+，常用）
5. volatile-lfu —— 有过期时间的 key 里淘汰最不常用
6. allkeys-random / volatile-random —— 随机淘汰
7. volatile-ttl —— 淘汰剩余 TTL 最短的
```

```text
LRU vs LFU：
LRU 按最近访问时间（可能淘汰偶尔访问的热点）
LFU 按访问频率（更适合热点缓存）
缓存场景通常选 allkeys-lru 或 allkeys-lfu。
```

## 缓存问题

**问题 1：缓存穿透、击穿、雪崩？**

```text
1. 穿透 —— 查不存在的数据（每次都打数据库）
   解决：布隆过滤器（先判断可能存在）、缓存空值（短期）
2. 击穿 —— 热点 key 过期（瞬时大量请求打数据库）
   解决：互斥锁（只让一个请求重建）、热点 key 永不过期（逻辑过期）
3. 雪崩 —— 大量 key 同时过期或 Redis 宕机（数据库被打垮）
   解决：随机过期时间（打散）、多级缓存、高可用集群
```

**问题 2：缓存和数据库的一致性？**

```text
Cache Aside（旁路缓存）模式：
1. 读：先查缓存，未命中查数据库，写缓存
2. 写：先更新数据库，再删缓存（不是更新缓存）

为什么删缓存不更新缓存：
删除简单，更新可能并发覆盖（两个写请求顺序错乱）。
```

```text
一致性增强方案：
1. 延迟双删 —— 删缓存 → 更新库 → 延迟再删一次（应对读重建的旧数据）
2. 订阅 binlog（Canal）—— 数据库变更后异步删缓存
3. 强一致场景直接读库，或加分布式锁
```

**问题 3：缓存更新策略？**

```text
1. Cache Aside（旁路）—— 应用层控制，最常用
2. Read Through —— 读时缓存层自动加载
3. Write Through —— 写时同步更新缓存和库
4. Write Behind —— 写时异步更新（延迟写库）
```

## 分布式锁

**问题 1：Redis 分布式锁的实现？**

```text
用 SET NX PX 实现：
SET lock:key value NX PX 10000

1. NX —— 不存在才设置（互斥）
2. PX —— 过期时间（防死锁）
3. value 用唯一标识（UUID），解锁时校验身份
4. 解锁用 Lua 脚本（原子性：校验 value + 删除）
```

```lua
-- 原子解锁：只删自己加的锁
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

```text
手写 Redis 锁的问题：
1. 不可重入
2. 不可续期（业务超时锁过期）
3. 主从切换可能丢锁（主挂，从无锁）

推荐 Redisson（可重入 + 看门狗续期 + 公平锁 + 红锁）。
```

**问题 2：Redisson 的看门狗机制？**

```text
看门狗（Watchdog）自动续期：
1. 获取锁后启动看门狗线程
2. 默认每 10 秒（锁超时 30 秒的 1/3）续期，续到 30 秒
3. 业务执行完释放锁，看门狗停止
解决业务执行时间超过锁过期时间的问题。
```

**问题 3：Redisson 的锁类型？**

```text
1. 可重入锁（ReentrantLock）—— 同线程可重入
2. 公平锁（FairLock）—— 按请求顺序获取
3. 联锁（MultiLock）—— 同时锁多个资源
4. 红锁（RedLock）—— 多个独立 Redis 节点，多数成功才算加锁
5. 读写锁（ReadWriteLock）
6. 信号量（RSemaphore）、闭锁（RCountDownLatch）
```

## 集群

**问题 1：Redis 的集群方案？**

```text
1. 主从复制 —— 读写分离，主写从读（数据冗余，无自动故障转移）
2. Sentinel 哨兵 —— 高可用，监控 + 自动故障转移（无分片）
3. Cluster 集群 —— 分片 + 高可用（数据分布 + 故障转移，3.0+）
```

**问题 2：主从复制的原理？**

```text
1. 从节点发 psync 请求
2. 全量复制 —— 主生成 RDB 快照发给从，从加载
3. 增量复制 —— 主把后续写命令发给从（偏移量 offset 对齐）
4. 复制积压缓冲（repl_backlog）支持断线续传

主从延迟：异步复制，从节点数据可能落后主节点。
```

**问题 3：Sentinel 哨兵的原理？**

```text
哨兵监控主从节点：
1. 主观下线 —— 单个哨兵认为主挂了（ping 超时）
2. 客观下线 —— 多数哨兵（quorum）认为主挂了
3. 选举 leader 哨兵执行故障转移
4. 选新主（从节点升级），通知其他从和客户端
```

**问题 4：Redis Cluster 的分片？**

```text
1. 16384 个槽（slot）
2. 每个节点负责一部分槽（hash slot）
3. key 通过 CRC16(key) % 16384 计算槽
4. 相同 hash tag（{xxx}）的 key 落在同一槽，可做批量操作
5. 节点间 gossip 协议通信，主从高可用
```

**问题 5：主从 + 哨兵 + 集群的区别？**

```text
主从复制 —— 数据冗余（读写分离），无自动故障转移
哨兵 —— 高可用（自动故障转移），无分片，单机容量
集群 —— 分片 + 高可用（水平扩展 + 故障转移）
```

## Redis 事务与 Lua

**问题 1：Redis 事务？**

```text
Redis 事务（MULTI/EXEC/DISCARD/WATCH）：
1. MULTI 开启事务，命令入队
2. EXEC 顺序执行队列命令
3. 不支持回滚（某命令失败，其他命令继续执行）

WATCH 实现乐观锁：监控 key，EXEC 前 key 被改则事务取消。
```

**问题 2：Lua 脚本的作用？**

```text
Lua 脚本在 Redis 内部原子执行：
1. 原子性 —— 脚本执行期间其他命令不插入
2. 减少网络开销 —— 多条命令一次发送
3. 复用 —— EVALSHA 缓存脚本

典型应用：原子解锁、限流、扣减库存（检查 + 扣减原子）。
```

**问题 3：管道 Pipeline？**

```text
Pipeline 批量发送命令，减少 RTT（网络往返）：
1. 客户端一次发送多条命令，服务端顺序执行，一次返回
2. 不是原子操作（命令间可插入其他客户端命令）
3. 适合批量读写，不适合依赖前序结果的场景
```

## 大 key 与热 key

**问题 1：大 key 的危害和解决？**

```text
危害：
1. 网络阻塞（单次读取数据量大）
2. 内存分布不均
3. 删除阻塞（DEL 大 key 阻塞主线程）

解决：
1. 拆分 —— 大 Hash/List 拆成多个小 key
2. 避免存大对象 —— 存 ID 而非完整对象
3. 删除用 UNLINK（异步删除）
4. 定期扫描 --bigkeys 排查
```

**问题 2：热 key 的危害和解决？**

```text
危害：热点 key 请求集中到单节点，该节点 CPU/网络打满，集群不均衡。

解决：
1. 本地缓存（Caffeine/Guava）—— 热点 key 缓存在应用本地
2. 热 key 复制多份（key 加随机后缀分散到不同节点）
3. 读写分离，从节点分摊读压力
```
