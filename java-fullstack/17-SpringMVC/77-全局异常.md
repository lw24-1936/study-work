## 概述

Spring MVC 的异常处理机制让 Controller 层的异常可以集中管理，避免每个方法都写 try-catch。核心是 `@ExceptionHandler` 和 `@ControllerAdvice`。

```text
异常处理分层：

Controller 方法抛异常
      ↓
@ExceptionHandler（Controller 内局部）
      ↓（未处理）
@ControllerAdvice + @ExceptionHandler（全局）
      ↓（未处理）
DefaultHandlerExceptionResolver（Spring 默认）
      ↓（仍未处理）
Servlet 容器（500 / error 页面）
```

目标：
1. 统一异常处理逻辑，Controller 方法保持干净
2. 统一错误响应格式（状态码 + 错误码 + 提示信息）
3. 避免堆栈信息泄露给客户端
4. 记录完整异常日志用于排查

## @ExceptionHandler 局部处理

`@ExceptionHandler` 标注的方法可以处理**当前 Controller** 内抛出的指定类型异常。

```java
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        return userService.findById(id)
            .orElseThrow(() -> new UserNotFoundException(id));
    }

    // 局部异常处理：只作用于本 Controller
    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<Result<Void>> handleNotFound(UserNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(Result.error(404, e.getMessage()));
    }
}
```

局部处理的局限：每个 Controller 都要写重复的异常处理代码。要全局统一，用 `@ControllerAdvice`。

## @ControllerAdvice 全局处理

`@ControllerAdvice` 是 `@Component` 的特殊形式，其标注的类中的 `@ExceptionHandler` 方法会**全局**生效（作用于所有 Controller）。

### 基本用法

```java
@RestControllerAdvice  // = @ControllerAdvice + @ResponseBody
public class GlobalExceptionHandler {

    // 处理业务异常
    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<Result<Void>> handleBusiness(BusinessException e) {
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(Result.error(e.getCode(), e.getMessage()));
    }

    // 处理资源不存在
    @ExceptionHandler(NotFoundException.class)
    public ResponseEntity<Result<Void>> handleNotFound(NotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(Result.error(404, e.getMessage()));
    }

    // 处理参数校验异常
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Result<Void>> handleValidation(MethodArgumentNotValidException e) {
        String message = e.getBindingResult().getFieldErrors().stream()
            .map(err -> err.getField() + ": " + err.getDefaultMessage())
            .collect(Collectors.joining("; "));
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(Result.error(400, message));
    }

    // 兜底：处理所有未捕获的异常
    @ExceptionHandler(Exception.class)
    public ResponseEntity<Result<Void>> handleGeneric(Exception e) {
        log.error("系统异常", e);  // 记录完整堆栈
        // 不泄露内部错误信息给客户端
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(Result.error(500, "系统繁忙，请稍后重试"));
    }
}
```

### @ControllerAdvice 的限定范围

```java
// 只处理指定包下的 Controller
@ControllerAdvice("com.example.api")

// 只处理指定注解标注的 Controller
@ControllerAdvice(annotations = RestController.class)

// 只处理指定的 Controller 类
@ControllerAdvice(assignableTypes = {UserController.class, OrderController.class})

// 组合使用
@ControllerAdvice(basePackages = "com.example.api", annotations = RestController.class)
```

### 可处理的常见异常类型

| 异常类型 | 触发场景 |
|---------|---------|
| BusinessException（自定义） | 业务规则违反 |
| MethodArgumentNotValidException | @Valid 校验失败 |
| ConstraintViolationException | @Validated 参数校验失败 |
| HttpMessageNotReadableException | JSON 解析失败 / 参数类型错误 |
| MissingServletRequestParameterException | 缺少必填参数 |
| MethodArgumentTypeMismatchException | 参数类型不匹配 |
| HttpRequestMethodNotSupportedException | HTTP 方法不支持 |
| NoHandlerFoundException | 404（需配置） |
| AccessDeniedException | Spring Security 权限不足 |

## 统一响应与错误码设计

### 统一响应体

```java
public class Result<T> {
    private int code;         // 错误码
    private String message;   // 提示信息
    private T data;           // 数据

    public Result(int code, String message, T data) {
        this.code = code;
        this.message = message;
        this.data = data;
    }

    public static <T> Result<T> success(T data) {
        return new Result<>(0, "success", data);
    }

    public static <T> Result<T> error(int code, String message) {
        return new Result<>(code, message, null);
    }
}
```

### 错误码设计

错误码是异常处理的核心，好的错误码设计能让问题定位更高效：

```text
错误码结构：模块（2位）+ 类别（1位）+ 序号（2位）
例如：40001 = 用户模块 + 参数错误 + 序号

类别约定：
1xx = 参数错误
2xx = 业务规则错误
3xx = 权限错误
4xx = 资源不存在
9xx = 系统错误
```

```java
// 错误码枚举
public enum ErrorCode {
    SUCCESS(0, "成功"),

    // 通用
    PARAM_ERROR(10001, "参数错误"),
    PARAM_MISSING(10002, "缺少必填参数"),
    PARAM_TYPE_ERROR(10003, "参数类型错误"),

    // 用户模块
    USER_NOT_FOUND(20401, "用户不存在"),
    USER_ALREADY_EXISTS(20201, "用户名已存在"),
    USER_PASSWORD_ERROR(20202, "密码错误"),

    // 权限
    UNAUTHORIZED(30301, "未登录"),
    FORBIDDEN(30302, "无权限"),

    // 系统
    SYSTEM_ERROR(90999, "系统繁忙，请稍后重试");

    private final int code;
    private final String message;
    // 构造器和 getter
}
```

### 自定义业务异常

```java
public class BusinessException extends RuntimeException {
    private final int code;

    public BusinessException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.code = errorCode.getCode();
    }

    public BusinessException(int code, String message) {
        super(message);
        this.code = code;
    }

    public int getCode() { return code; }
}
```

### 完整示例

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusiness(BusinessException e) {
        return Result.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValidation(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
            .map(f -> f.getField() + f.getDefaultMessage())
            .collect(Collectors.joining(", "));
        return Result.error(ErrorCode.PARAM_ERROR.getCode(), msg);
    }

    @ExceptionHandler(Exception.class)
    public Result<Void> handleGeneric(Exception e) {
        log.error("系统异常", e);
        return Result.error(ErrorCode.SYSTEM_ERROR.getCode(),
            ErrorCode.SYSTEM_ERROR.getMessage());
    }
}
```

## ProblemDetail 与 RFC 7807

### RFC 7807 标准

RFC 7807（Problem Details for HTTP APIs）定义了 HTTP API 错误响应的标准格式。Spring 6 / Spring Boot 3 内置支持。

```json
{
  "type": "https://example.com/errors/user-not-found",  // 错误类型 URI
  "title": "用户不存在",                                  // 简短标题
  "status": 404,                                         // HTTP 状态码
  "detail": "ID 为 123 的用户不存在",                      // 详细说明
  "instance": "/api/users/123"                           // 出错请求的 URI
}
```

### ProblemDetail 类

Spring 6 提供 `org.springframework.http.ProblemDetail` 类：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ProblemDetail handleNotFound(UserNotFoundException e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
            HttpStatus.NOT_FOUND, e.getMessage());
        pd.setTitle("用户不存在");
        pd.setType(URI.create("https://example.com/errors/user-not-found"));
        pd.setProperty("userId", e.getUserId());  // 自定义字段
        return pd;
    }

    @ExceptionHandler(BusinessException.class)
    public ProblemDetail handleBusiness(BusinessException e) {
        ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setTitle("业务错误");
        pd.setDetail(e.getMessage());
        pd.setProperty("code", e.getCode());  // 业务错误码
        return pd;
    }
}
```

### 开启 ProblemDetail 响应

```yaml
# application.yml —— 开启后，Spring 内置异常（404、400 等）也返回 ProblemDetail 格式
spring:
  mvc:
    problemdetails:
      enabled: true
```

开启后，Spring 默认异常（如参数类型错误）会返回 ProblemDetail 格式的响应，而不是默认的 `{timestamp, status, error, path}` 格式。

## ErrorResponse 接口

`ErrorResponse` 是 Spring 6 引入的接口，是 `ProblemDetail` 的补充抽象，专门用于表达错误响应：

```java
public interface ErrorResponse {
    HttpStatusCode getStatusCode();
    ProblemDetail getBody();
}
```

### 自定义 ErrorResponse

```java
public class MyErrorResponse implements ErrorResponse {

    private final HttpStatusCode statusCode;
    private final ProblemDetail body;

    public MyErrorResponse(HttpStatusCode statusCode, String title, String detail, int bizCode) {
        this.statusCode = statusCode;
        this.body = ProblemDetail.forStatusAndDetail(statusCode, detail);
        this.body.setTitle(title);
        this.body.setProperty("code", bizCode);
    }

    @Override
    public HttpStatusCode getStatusCode() { return statusCode; }

    @Override
    public ProblemDetail getBody() { return body; }
}
```

### ErrorResponseException

Spring 6 提供了 `ErrorResponseException` 作为可直接抛出的异常：

```java
@GetMapping("/user/{id}")
public User getUser(@PathVariable Long id) {
    throw new ErrorResponseException(
        HttpStatus.NOT_FOUND,
        ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, "用户不存在"),
        null  // cause
    );
}
```

### ErrorResponse vs ProblemDetail

| 维度 | ProblemDetail | ErrorResponse |
|------|---------------|---------------|
| 定位 | 响应体数据 | 异常/响应接口 |
| 作用 | 定义错误响应的 JSON 结构 | 定义异常的 HTTP 状态码 + 响应体 |
| 使用 | 直接作为返回值 | 实现后抛出/返回 |
| 关系 | ErrorResponse 内部用 ProblemDetail | 包装 ProblemDetail |

## 异常处理优先级

当多个 @ExceptionHandler 都能处理同一异常时，按以下优先级：

1. **异常类型最精确匹配**：`@ExceptionHandler(NullPointerException.class)` 优先于 `@ExceptionHandler(RuntimeException.class)`
2. **局部优先于全局**：Controller 内的 @ExceptionHandler 优先于 @ControllerAdvice
3. **@Order 排序**：多个 @ControllerAdvice 中，@Order 值小的优先

```java
// 精确匹配优先
@ExceptionHandler(FileNotFoundException.class)   // 优先匹配 FileNotFoundException
public Result handleFileNotFound(...) { ... }

@ExceptionHandler(IOException.class)             // FileNotFoundException 是 IOException 子类
public Result handleIO(...) { ... }

// 兜底
@ExceptionHandler(Exception.class)               // 最后兜底
public Result handleAll(...) { ... }
```

Spring 选择最接近异常类型的处理器（按继承树向上找最近的匹配）。

## 应用场景实战

### 场景 1：完整的全局异常处理体系

```java
// 1. 错误码枚举
public enum ErrorCode {
    SUCCESS(0, "成功"),
    PARAM_ERROR(10001, "参数错误"),
    USER_NOT_FOUND(20401, "用户不存在"),
    ORDER_STATE_ERROR(20201, "订单状态不允许该操作"),
    UNAUTHORIZED(30301, "未登录"),
    SYSTEM_ERROR(90999, "系统繁忙");

    private final int code;
    private final String message;
    // 构造器 + getter
}

// 2. 业务异常
public class BusinessException extends RuntimeException {
    private final int code;
    public BusinessException(ErrorCode ec) { super(ec.getMessage()); this.code = ec.getCode(); }
    public BusinessException(int code, String msg) { super(msg); this.code = code; }
    public int getCode() { return code; }
}

// 3. 全局异常处理器
@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    // 业务异常
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusiness(BusinessException e) {
        log.warn("业务异常：code={}, msg={}", e.getCode(), e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    // 参数校验异常（@Valid）
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
            .map(f -> f.getField() + ": " + f.getDefaultMessage())
            .collect(Collectors.joining("; "));
        return Result.error(ErrorCode.PARAM_ERROR.getCode(), msg);
    }

    // JSON 解析异常
    @ExceptionHandler(HttpMessageNotReadableException.class)
    public Result<Void> handleJson(HttpMessageNotReadableException e) {
        return Result.error(ErrorCode.PARAM_ERROR.getCode(), "请求体格式错误");
    }

    // 缺少参数
    @ExceptionHandler(MissingServletRequestParameterException.class)
    public Result<Void> handleMissing(MissingServletRequestParameterException e) {
        return Result.error(10002, "缺少参数：" + e.getParameterName());
    }

    // 方法不支持
    @ExceptionHandler(HttpRequestMethodNotSupportedException.class)
    public Result<Void> handleMethod(HttpRequestMethodNotSupportedException e) {
        return Result.error(10004, "不支持的请求方法：" + e.getMethod());
    }

    // 兜底
    @ExceptionHandler(Exception.class)
    public Result<Void> handleAll(Exception e) {
        log.error("未捕获异常", e);
        return Result.error(ErrorCode.SYSTEM_ERROR.getCode(),
            ErrorCode.SYSTEM_ERROR.getMessage());
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. **异常分类处理，不要一个 Exception 兜底**。业务异常、参数异常、权限异常、系统异常分开处理，错误码才准确。

2. **系统异常不泄露内部信息**。堆栈信息只记录到日志，返回给客户端的是通用提示（"系统繁忙"），防止泄露数据库表结构、SQL、代码路径等敏感信息。

3. **日志记录完整堆栈**。兜底异常必须 `log.error("...", e)` 记录完整堆栈，否则生产问题无法排查。

4. **错误码集中在枚举**。避免魔法数字散落各处，便于统一管理和维护。

5. **traceId 贯穿异常响应**。在响应中带上 traceId，配合日志系统快速定位问题：

```java
@ExceptionHandler(Exception.class)
public Result<Void> handleAll(Exception e) {
    String traceId = MDC.get("traceId");
    log.error("系统异常，traceId={}", traceId, e);
    return Result.error(90999, "系统繁忙（traceId: " + traceId + "）");
}
```

### 踩坑记录

**坑 1：@ExceptionHandler 只对 Controller 层生效**

```java
// Service 中抛的异常，如果没有被 Controller 捕获，
// 会向上传播到 Controller 层才能被 @ExceptionHandler 处理
// 但 @Async 异步方法、定时任务、MQ 消费者中的异常不会被处理
```

`@ControllerAdvice` 只能捕获 MVC 请求处理链中的异常。异步任务、定时任务中的异常需要单独处理。

**坑 2：异常处理中再抛异常**

```java
@ExceptionHandler(Exception.class)
public Result<Void> handle(Exception e) {
    // 如果这里再抛异常（如 JSON 序列化失败），会导致递归处理或白屏
    return Result.error(500, e.getMessage());
}
```

兜底处理器要足够健壮，内部不能依赖可能失败的操作。

**坑 3：404 异常默认不被处理**

```java
// Spring MVC 默认对未匹配的 URL（NoHandlerFoundException）不抛异常，
// 而是由容器返回 404
// 要处理需要配置：
```

```yaml
spring:
  mvc:
    throw-exception-if-no-handler-found: true
  web:
    resources:
      add-mappings: false
```

配置后，未匹配的 URL 会抛 NoHandlerFoundException，可以被全局异常处理器捕获。

**坑 4：@ExceptionHandler 方法签名错误**

```java
// 方法必须能接收异常参数，且返回类型要能被处理
@ExceptionHandler(BusinessException.class)
public String handle(BusinessException e) {  // 返回 String 会被当成视图名！
    return "error";
}
```

在 `@RestControllerAdvice` 中返回对象会被序列化为 JSON；但在 `@ControllerAdvice`（非 Rest）中返回 String 会被当成视图名。用 `@RestControllerAdvice` 避免歧义。

**坑 5：多个 @ExceptionHandler 匹配的歧义**

```java
@ExceptionHandler(RuntimeException.class)
public Result handleRuntime(...) { ... }

@ExceptionHandler(Exception.class)
public Result handleAll(...) { ... }
// NullPointerException 同时匹配两个，Spring 选择最近的（RuntimeException）
```

Spring 按继承树选最近匹配，但如果两个异常类型无关（并列），会抛 AmbiguousExceptionHandlerException。确保异常处理器类型不产生歧义。

**坑 6：@Valid 校验异常类型记混**

```java
// @RequestBody + @Valid → MethodArgumentNotValidException
// @RequestParam/@PathVariable + @Validated → ConstraintViolationException
```

两种校验异常类型不同，全局处理器要分别处理，否则校验失败会走到 500 兜底。
