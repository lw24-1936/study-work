## 为什么需要构建工具

没有构建工具之前，Java 项目的日常：

1. 从网上下载 jar，复制到 `lib/` 目录
2. jar A 依赖 jar B，jar B 又依赖 jar C——手动解决依赖传递
3. 两个 jar 依赖同一个库的不同版本——爆 `NoSuchMethodError`
4. 编译、运行测试、打包——每一步都要手动敲命令

构建工具管的事：**依赖管理、编译、测试、打包、发布**。Java 生态里主要剩两个选手：Maven 和 Gradle。Ant 还剩一些遗留项目在用，新项目不选它。

## Maven 核心概念

Maven 的设计哲学：**约定优于配置**。源码放 `src/main/java`，测试放 `src/test/java`，资源放 `src/main/resources`——你按约定放，Maven 不用额外配置就知道怎么编译。

### 安装

```bash
# macOS
brew install maven

# Ubuntu
sudo apt install maven

# 手动安装
wget https://dlcdn.apache.org/maven/maven-3/3.9.9/binaries/apache-maven-3.9.9-bin.tar.gz
sudo tar -xzf apache-maven-3.9.9-bin.tar.gz -C /usr/local
# 然后配 M2_HOME 和 PATH
```

验证：

```bash
mvn --version
```

### 项目骨架

```
my-project/
├── pom.xml                     # 项目对象模型，Maven 的全部配置
├── src/
│   ├── main/
│   │   ├── java/               # 源码
│   │   └── resources/          # 配置文件、模板等
│   └── test/
│       ├── java/               # 测试代码
│       └── resources/          # 测试用配置
└── target/                     # 构建输出（自动生成，.gitignore）
```

一个最小 pom.xml：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
         http://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0.0</version>
    <packaging>jar</packaging>
</project>
```

## Maven 坐标与依赖

### 坐标（GAV）

Maven 通过三个值唯一定位一个构件：

```xml
<groupId>com.example</groupId>      <!-- 组织/公司标识，约定是倒置域名 -->
<artifactId>my-app</artifactId>       <!-- 项目/模块名 -->
<version>1.0.0</version>             <!-- 版本号 -->
```

GAV 合在一起就是坐标：`com.example:my-app:1.0.0`。

### 仓库

Maven 的仓库分三层：

```
本地仓库 (~/.m2/repository)
    ↑ 没找到，往上层找
远程仓库（公司私服，如 Nexus/Artifactory）
    ↑ 没找到，往上层找
中央仓库 (repo.maven.apache.org)
```

- **中央仓库**：Maven 默认的公共仓库，全球最大的 Java 构件库
- **私服**：公司内部搭建的仓库代理，缓存中央仓库的构件，同时托管公司内部发布的私有构件
- **本地仓库**：你机器上的 `~/.m2/repository`，下载过的 jar 缓存到这里

配置镜像（加速国内下载）：

```xml
<!-- ~/.m2/settings.xml -->
<mirrors>
    <mirror>
        <id>aliyun</id>
        <mirrorOf>central</mirrorOf>
        <name>Aliyun Maven Mirror</name>
        <url>https://maven.aliyun.com/repository/public</url>
    </mirror>
</mirrors>
```

### 依赖管理

```xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
        <version>3.2.5</version>
        <!-- scope 默认 compile -->
    </dependency>
</dependencies>
```

### Maven Scope

Scope 控制依赖在什么阶段可用：

| Scope | 编译 | 测试 | 运行时 | 打包到最终 jar | 典型用途 |
|-------|------|------|--------|---------------|----------|
| `compile` | 需要 | 需要 | 需要 | 需要 | 默认值，大部分依赖 |
| `provided` | 需要 | 需要 | 需要 | 不需要 | Servlet API，容器提供 |
| `runtime` | 不需要 | 需要 | 需要 | 需要 | JDBC 驱动，编译时不需要 |
| `test` | 不需要 | 需要 | 不需要 | 不需要 | JUnit, Mockito |
| `system` | 需要 | 需要 | 需要 | 不需要 | 本地 jar（不推荐） |
| `import` | — | — | — | — | 导入 BOM，在 dependencyManagement 里用 |

最常见的使用：

```xml
<!-- 编译时需要 API，运行时由 Tomcat 提供 -->
<dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <scope>provided</scope>
</dependency>

<!-- 运行时才需要驱动类 -->
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>
```

### 依赖传递与冲突解决

Maven 自动解析传递性依赖——A 依赖 B，B 依赖 C，你只需要声明 A，C 自动引入。

**依赖冲突原则：**

- **最短路径优先**：A → B → C(v1) vs A → D → E → C(v2)，选 v1
- **先声明优先**：路径深度相同时，pom.xml 里先写的依赖胜出
- **显式声明覆盖**：你自己写的直接依赖优先级最高

排查冲突：

```bash
# 打印依赖树
mvn dependency:tree

# 只看冲突的
mvn dependency:tree -Dverbose | grep "omitted for conflict"
```

排除传递依赖：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-tomcat</artifactId>
        </exclusion>
    </exclusions>
</dependency>
<!-- 换成 Undertow -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-undertow</artifactId>
</dependency>
```

## Maven 生命周期与插件

### 三套生命周期

Maven 内置三套独立的生命周期：clean、default、site。日常只用前两个。

**clean 生命周期：**

| 阶段 | 作用 |
|------|------|
| `pre-clean` | 清理前准备 |
| `clean` | 删除 target/ 目录 |
| `post-clean` | 清理后处理 |

**default 生命周期（最常用）：**

| 阶段 | 作用 |
|------|------|
| `validate` | 验证项目结构 |
| `compile` | 编译 src/main/java |
| `test` | 运行单元测试 |
| `package` | 打包（jar/war） |
| `verify` | 集成测试校验 |
| `install` | 安装到本地仓库（~/.m2） |
| `deploy` | 发布到远程仓库 |

执行后面的阶段会自动执行前面的所有阶段。`mvn package` 会先执行 `validate → compile → test → package`。

常用命令：

```bash
mvn clean                    # 清理
mvn compile                  # 只编译
mvn test                     # 编译 + 运行测试
mvn package                  # 编译 + 测试 + 打包（跳过测试用 -DskipTests）
mvn package -DskipTests      # 打包但跳过测试
mvn install                  # 安装到本地仓库
mvn clean package            # 先清理再打包
```

### Maven Plugin

生命周期的每个阶段都是由插件完成的。比如 `compile` 阶段绑定的是 `maven-compiler-plugin`，`package` 阶段绑定的是 `maven-jar-plugin`。

没有插件，Maven 只是个空壳——生命周期只是定义了阶段，干活的是插件。

常用插件配置：

```xml
<build>
    <plugins>
        <!-- 指定 Java 版本 -->
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.13.0</version>
            <configuration>
                <source>17</source>
                <target>17</target>
                <encoding>UTF-8</encoding>
            </configuration>
        </plugin>

        <!-- 打包成可执行 jar -->
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-jar-plugin</artifactId>
            <configuration>
                <archive>
                    <manifest>
                        <mainClass>com.example.App</mainClass>
                    </manifest>
                </archive>
            </configuration>
        </plugin>
    </plugins>
</build>
```

Spring Boot 项目用 `spring-boot-maven-plugin` 替代 maven-jar-plugin，它能打 fat jar（包含所有依赖），`java -jar` 直接跑。

## Maven Profile

Profile 用于不同环境的差异化配置——开发环境连本地 MySQL，测试环境连测试库，生产环境连生产库。

```xml
<profiles>
    <profile>
        <id>dev</id>
        <properties>
            <env>development</env>
            <db.url>jdbc:mysql://localhost:3306/dev_db</db.url>
        </properties>
        <activation>
            <activeByDefault>true</activeByDefault>
        </activation>
    </profile>
    <profile>
        <id>prod</id>
        <properties>
            <env>production</env>
            <db.url>jdbc:mysql://prod-db:3306/prod_db</db.url>
        </properties>
    </profile>
</profiles>
```

激活 profile：

```bash
mvn package -P prod          # 用 prod 配置打包
mvn package -P dev,test      # 同时激活多个
```

配合 Spring Boot 的 `application-{profile}.yml`，Maven 负责构建时变量，Spring 负责运行时配置——各管各的，不要混在一起。

### settings.xml 里的 Profile

`~/.m2/settings.xml` 可以定义全局 profile，所有项目生效：

```xml
<settings>
    <profiles>
        <profile>
            <id>jdk17</id>
            <properties>
                <maven.compiler.source>17</maven.compiler.source>
                <maven.compiler.target>17</maven.compiler.target>
            </properties>
        </profile>
    </profiles>
    <activeProfiles>
        <activeProfile>jdk17</activeProfile>
    </activeProfiles>
</settings>
```

## Maven BOM

BOM（Bill of Materials）是一份依赖版本清单，不是实际的依赖。你把 BOM 写在 `dependencyManagement` 里，实际的 dependency 就不用写版本号。

```xml
<dependencyManagement>
    <dependencies>
        <!-- Spring Boot BOM -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-dependencies</artifactId>
            <version>3.2.5</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
        <!-- Spring Cloud BOM -->
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>2023.0.2</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <!-- 不用写版本，由 BOM 统一管理 -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
</dependencies>
```

好处：
- 集中管理版本号，改一处全部生效
- 避免同系列库的版本不一致
- Spring Boot 的 BOM 已经帮你校验了兼容性

## Gradle 基础

Gradle 用 Groovy DSL 或 Kotlin DSL 写构建脚本，比 Maven 的 XML 更灵活。Spring 项目的构建从 Maven 迁移到 Gradle 是一大趋势（Spring 源码本身已用 Gradle）。

### 安装

```bash
# macOS
brew install gradle

# sdkman
sdk install gradle 8.10
```

### 项目结构

和 Maven 一样（同一个"约定优于配置"），只是构建文件从 `pom.xml` 换成 `build.gradle` 或 `build.gradle.kts`。

### build.gradle.kts（Kotlin DSL）

```kotlin
plugins {
    java
    id("org.springframework.boot") version "3.2.5"
    id("io.spring.dependency-management") version "1.1.4"
}

group = "com.example"
version = "1.0.0"

java {
    sourceCompatibility = JavaVersion.VERSION_17
}

repositories {
    mavenCentral()
    // 国内加速
    maven { url = uri("https://maven.aliyun.com/repository/public") }
}

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
    testImplementation("org.springframework.boot:spring-boot-starter-test")
    compileOnly("org.projectlombok:lombok")
    annotationProcessor("org.projectlombok:lombok")
}
```

Gradle 的 scope 对应：

| Gradle 配置 | Maven Scope | 说明 |
|------------|-------------|------|
| `implementation` | `compile`（已弃用） | 编译和运行时可用，但不传递给下游 |
| `api` | `compile` | 编译和运行时可用，传递给下游（java-library 插件） |
| `compileOnly` | `provided` | 只编译时可用 |
| `runtimeOnly` | `runtime` | 只运行时可用 |
| `testImplementation` | `test` | 只测试时可用 |
| `annotationProcessor` | — | 注解处理器（Lombok、MapStruct） |

`implementation` 和 `api` 的关键区别：`implementation` 的依赖不会暴露给使用你的库的项目——这能大幅加快编译速度（依赖变化时只重编译当前模块，不级联下游）。

### Gradle Wrapper

Wrapper 是一组脚本文件（`gradlew` / `gradlew.bat` + `gradle/wrapper/`），让项目自带构建工具版本——新 clone 的项目不用装 Gradle，运行 `./gradlew build` 会自动下载指定版本的 Gradle。

```bash
# 生成 Wrapper
gradle wrapper --gradle-version 8.10

# 之后始终用 wrapper 运行
./gradlew build
./gradlew test
```

Wrapper 的核心价值：CI 环境和团队所有成员的 Gradle 版本保持一致，避免"我机器上能跑"的问题。

### Gradle Plugin

Gradle 插件对应 Maven 插件：

```kotlin
plugins {
    id("org.springframework.boot") version "3.2.5"
    id("com.google.cloud.tools.jib") version "3.4.2"  // 构建 Docker 镜像
    id("org.sonarqube") version "5.0.0.4638"           // 代码质量
}
```

### 多模块项目（Gradle）

```kotlin
// settings.gradle.kts
rootProject.name = "my-app"
include("core", "web", "admin")

// build.gradle.kts（根项目）
subprojects {
    apply(plugin = "java")
    // 公共配置
}

// core/build.gradle.kts
dependencies {
    implementation("org.springframework.boot:spring-boot-starter")
}
```

## Maven vs Gradle 对比

| 维度 | Maven | Gradle |
|------|-------|--------|
| 构建文件 | pom.xml（XML） | build.gradle(.kts)（Groovy/Kotlin） |
| 灵活性 | 低，约定重于配置 | 高，脚本式可编程 |
| 学习曲线 | 低 | 中 |
| 构建速度 | 慢（无增量编译） | 快（增量编译 + 构建缓存 + 并行） |
| 依赖管理 | 固定生命周期 | 可定制任务图 |
| 多模块 | pom 聚合 + 继承 | 直接引用 |
| 社区生态 | 极大，几乎所有 Java 项目 | 快速增长 |
| Android | 已废弃 | 官方构建工具 |
| Spring 项目 | 广泛使用 | Spring 源码、新项目推荐 |

选择建议：新项目优先用 Gradle（Kotlin DSL），接手 Maven 的存量项目不必迁移。如果团队对 Maven 更熟悉，Maven 也没问题——没必要为了用 Gradle 而用 Gradle。

---

两个构建工具的核心思想都一样：**声明你要什么，而不是手写怎么做**。你声明依赖和插件，构建工具自动处理传递、编译、打包——你把精力放在业务代码上。
