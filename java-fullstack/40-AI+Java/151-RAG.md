## 概述

RAG（Retrieval-Augmented Generation，检索增强生成）让 LLM 基于外部知识回答问题，解决 LLM 的知识局限和幻觉问题。

```text
RAG 解决的问题：
1. 知识局限 —— LLM 不知道私有/最新数据
2. 幻觉 —— LLM 编造不存在的信息
3. 不可溯源 —— 回答没有依据
```

```text
RAG 的核心思想：
先从知识库检索相关内容，再把内容作为上下文给 LLM，
让 LLM 基于真实资料回答。
```

```text
RAG vs 微调（Fine-tuning）：
RAG —— 检索外部知识（灵活、即时更新、成本低）
微调 —— 训练模型（改变模型本身，成本高）
```

## RAG 工作流程

### 两大阶段

```text
阶段 1：索引（离线）
文档加载 → 文本切分 → 向量化（Embedding）→ 存储向量库

阶段 2：检索 + 生成（在线）
用户提问 → 向量化 → 相似性检索 → 拼接上下文 → LLM 回答
```

```text
完整流程：
                    ┌─────────────────────┐
                    │  文档（PDF/网页/DB）  │
                    └──────────┬──────────┘
                               │ Document Loader
                    ┌──────────▼──────────┐
                    │  文本切分（Chunks）   │
                    └──────────┬──────────┘
                               │ Embedding
                    ┌──────────▼──────────┐
                    │  向量数据库（存储）   │
                    └──────────┬──────────┘
                               │
用户提问 → Embedding → 相似性检索 → 相关片段
                               │
                    ┌──────────▼──────────┐
                    │  拼接上下文 + Prompt  │
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
                    │  LLM 生成回答        │
                    └─────────────────────┘
```

## Text Splitter 文本切分

文本切分把长文档切成小块（chunk），便于向量化和检索。

### 为什么切分

```text
1. 向量化限制 —— Embedding 模型有输入长度限制
2. 检索精度 —— 小块检索更精确
3. 上下文控制 —— 小块拼接到 prompt 不会超限
```

### 切分策略

```text
1. 固定大小切分 —— 按固定字符数（如 500 字符）
2. 重叠切分 —— 块之间有重叠（如 50 字符），保留上下文
3. 语义切分 —— 按段落、句子切分
```

```java
// Spring AI 文本切分
TokenTextSplitter splitter = new TokenTextSplitter(
    500,    // 块大小
    50,     // 重叠
    5,      // 最小块大小
    10000,  // 最大 token
    false);
List<Document> chunks = splitter.split(documents);
```

### 切分大小的影响

```text
块太大 —— 检索不精确，上下文超限
块太小 —— 信息碎片化，丢失上下文

经验值：300-800 字符/块，重叠 10-20%
```

## Embedding 与向量化

Embedding 把文本转成向量，用于相似性计算（详见 149）。

### 向量化流程

```java
// 每个 chunk 向量化
List<Document> chunks = splitter.split(documents);
for (Document chunk : chunks) {
    float[] vector = embeddingModel.embed(chunk.getContent());
    // 存储到向量库
    vectorStore.add(chunk, vector);
}
```

## Retriever 检索

Retriever 检索与问题最相关的文档片段。

### 相似性检索

```java
// 相似性搜索（向量相似度）
List<Document> results = vectorStore.similaritySearch(
    SearchRequest.query(question)
        .withTopK(5)          // 返回前 5 个
        .withSimilarityThreshold(0.7));  // 相似度阈值
```

### 检索策略

```text
1. 相似性检索 —— 向量相似度（最常用）
2. 关键词检索 —— BM25（关键词匹配）
3. 混合检索 —— 向量 + 关键词结合
```

## Reranker 重排序

Reranker 对检索结果重新排序，提升最相关结果的排名。

### 为什么需要 Reranker

```text
向量检索的问题：相似度高的不一定最相关（语义相似 ≠ 相关）

Reranker 的作用：用更精确的模型重新排序检索结果
```

### Reranker 流程

```text
1. 向量检索（粗筛）—— 召回 20-50 个候选
2. Reranker 重排序（精排）—— 选最相关的 3-5 个
```

### Reranker 模型

```text
1. Cohere Rerank
2. bge-reranker（开源）
3. cross-encoder 模型
```

## 应用场景实战

### 场景 1：企业知识库问答

```java
@Service
public class KnowledgeBaseService {

    @Autowired
    private VectorStore vectorStore;
    @Autowired
    private ChatClient chatClient;

    public String answer(String question) {
        // 1. 检索相关文档
        List<Document> docs = vectorStore.similaritySearch(
            SearchRequest.query(question).withTopK(3));

        // 2. 拼接上下文
        String context = docs.stream()
            .map(Document::getContent)
            .collect(Collectors.joining("\n\n"));

        // 3. 带上下文回答
        return chatClient.prompt()
            .system("根据以下资料回答问题，资料中没有的就说不知道：\n\n" + context)
            .user(question)
            .call()
            .content();
    }
}
```

### 场景 2：文档索引（离线处理）

```java
@Service
public class DocumentIndexService {

    @Autowired
    private VectorStore vectorStore;
    @Autowired
    private EmbeddingModel embeddingModel;

    public void indexDocument(String path) {
        // 1. 加载
        DocumentReader reader = new PagePdfDocumentReader(path);
        List<Document> docs = reader.get();

        // 2. 切分
        TokenTextSplitter splitter = new TokenTextSplitter(500, 50, 5, 10000, false);
        List<Document> chunks = splitter.split(docs);

        // 3. 向量化 + 存储
        vectorStore.add(chunks);
    }
}
```

### 场景 3：客服知识库

```text
1. 客服文档（FAQ、产品手册）→ 索引
2. 用户提问 → 检索相关 FAQ
3. LLM 基于 FAQ 回答
4. 找不到相关文档 → 转人工
```

## 最佳实践与踩坑记录

### 最佳实践

1. **块大小 300-800 字符**。太小碎片化，太大不精确。

2. **重叠 10-20%**。保留上下文连贯性。

3. **检索 topK 5-10**。太少信息不足，太多上下文超限。

4. **prompt 明确"不知道"**。检索不到相关内容时，让 LLM 说不知道，而不是编造。

5. **Reranker 提升精度**。高精度场景加 Reranker。

### 踩坑记录

**坑 1：块太大或太小**

```text
块太大（2000 字符）—— 检索不精确，上下文超限
块太小（50 字符）—— 信息碎片，回答不完整
```

块大小 300-800 字符，重叠 10-20%。

**坑 2：检索结果直接拼接超限**

```text
检索 10 个块，每个 500 字符，共 5000 字符，加上 prompt 超限
```

控制 topK 和块大小，保证上下文在窗口内。

**坑 3：LLM 编造（不设"不知道"）

```text
检索不到相关内容，LLM 也强行回答（幻觉）
```

prompt 明确"资料没有就说不知道"。

**坑 4：向量库和 Embedding 维度不匹配**

```text
Embedding 模型输出 1536 维，向量库配置 1024 维，存储失败
```

确认维度一致。

**坑 5：文档更新后索引不更新**

```text
文档改了，向量库还是旧的，检索到过期内容
```

文档更新时同步更新索引，或定期重建。

**坑 6：忽略元数据**

```text
检索结果没有来源信息，无法溯源
```

Document 存元数据（来源、页码），回答时引用来源。
