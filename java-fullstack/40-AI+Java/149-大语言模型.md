## 概述

理解 LLM 的核心概念是使用 AI 的基础，本篇覆盖 Transformer、Token、Prompt 等关键概念。

## Transformer 架构

Transformer 是现代 LLM 的基础架构，核心是注意力机制（Attention）。

### Transformer 的结构

```text
Transformer = 编码器（Encoder）+ 解码器（Decoder）

核心组件：
1. Self-Attention（自注意力）—— 理解词与词的关系
2. Multi-Head Attention（多头注意力）—— 多个注意力并行
3. Feed-Forward（前馈网络）—— 非线性变换
4. Positional Encoding（位置编码）—— 词的顺序信息
```

### 注意力机制

```text
Self-Attention 的作用：
计算每个词和其他词的相关性，理解上下文

例："苹果很好吃" 和 "苹果手机很好用"
"苹果" 在两个句子里含义不同，
注意力机制根据上下文（"吃" vs "手机"）理解含义
```

### Transformer 的意义

```text
1. 并行计算 —— 比 RNN 快（RNN 顺序处理）
2. 长距离依赖 —— 注意力机制理解远距离关系
3. 可扩展 —— 规模可无限扩展
```

## Token 分词

Token 是 LLM 处理文本的基本单位（不是字符，不是单词）。

### Token 是什么

```text
Token = 文本切分的最小单位（可能是词、子词、字符）
```

```text
"我喜欢吃苹果" 的分词：
中文：可能切分为 [我, 喜欢, 吃, 苹果]（4 个 token）
英文 "I like apples"：切分为 [I, like, apple, s]（子词切分）
```

### Token 的意义

```text
1. 计费单位 —— API 按 token 计费
2. 上下文窗口 —— 上下文用 token 数衡量
3. 处理限制 —— 模型有 token 上限
```

```text
经验值：
1 个中文字 ≈ 1-2 个 token
1 个英文单词 ≈ 1-2 个 token
1000 token ≈ 750 个英文单词 ≈ 500 个中文字
```

## Context Window 上下文窗口

上下文窗口是模型一次能处理的最大 token 数。

### 上下文窗口的意义

```text
1. 输入限制 —— 单次请求的 token 上限
2. 记忆长度 —— 模型能"记住"多长的对话
```

```text
主流模型的上下文窗口：
GPT-4o —— 128K tokens
Claude 3 —— 200K tokens
DeepSeek —— 64K/128K tokens
```

### 上下文窗口的应对

```text
超长文本的应对：
1. 截断 —— 只取最近的内容
2. 摘要 —— 压缩历史对话
3. RAG —— 检索相关片段（详见 151）
```

## Prompt 提示词

Prompt 是给模型的指令，决定模型的输出质量。

### Prompt 的要素

```text
好的 Prompt 包含：
1. 角色 —— 你是谁（"你是 Java 专家"）
2. 任务 —— 做什么（"帮我写一个..."）
3. 上下文 —— 背景信息
4. 格式 —— 输出格式要求
5. 示例 —— few-shot 示例
```

### Prompt 技巧

```text
1. 明确具体 —— 越具体越好
2. 提供示例 —— few-shot learning
3. 分步思考 —— "一步步思考"（Chain of Thought）
4. 设定角色 —— 角色扮演
5. 指定格式 —— 明确输出格式
```

```text
差 Prompt："写代码"
好 Prompt："你是 Java 专家，帮我写一个线程安全的单例模式，
使用双重检查锁，包含注释，输出完整代码"
```

## Temperature 与 Top-P

Temperature 和 Top-P 控制模型输出的随机性。

### Temperature（温度）

```text
Temperature 控制输出的随机性（0-2）：
0 —— 确定性（每次都一样，适合代码/事实）
0.7 —— 平衡（默认，适合对话）
1.5 —— 随机（创意写作，可能胡言乱语）
```

```text
使用建议：
代码生成、数学 → 0（或接近 0）
通用对话 → 0.7
创意写作 → 1.0+
```

### Top-P（核采样）

```text
Top-P 控制候选词的范围（0-1）：
只从累积概率达到 P 的词中采样

Top-P = 0.9 → 只考虑概率最高的 90% 的词
```

### Temperature vs Top-P

```text
Temperature —— 调整概率分布（改变随机性）
Top-P —— 截断候选词（限制范围）

通常调一个即可（不要同时调两个）
```

## Embedding 向量

Embedding 把文本转成向量，表示语义。

### Embedding 是什么

```text
Embedding = 文本 → 高维向量（如 1536 维）

"苹果" → [0.1, -0.3, 0.5, ...]
"香蕉" → [0.2, -0.2, 0.4, ...]（语义接近，向量接近）
"电脑" → [-0.5, 0.8, 0.1, ...]（语义远，向量远）
```

### Embedding 的用途

```text
1. 语义搜索 —— 找语义相似的文本（向量相似度）
2. RAG —— 检索相关文档（详见 151）
3. 聚类 —— 相似文本分组
4. 推荐 —— 相似内容推荐
```

### 向量相似度

```text
1. 余弦相似度 —— 角度（最常用）
2. 欧氏距离 —— 距离
3. 点积 —— 内积
```

## Function Calling 函数调用

Function Calling 让模型调用外部函数，获取实时数据或执行操作。

### Function Calling 是什么

```text
模型不直接回答，而是输出"要调用哪个函数 + 参数"，
应用执行函数，把结果返回给模型。
```

```text
流程：
用户："北京今天天气怎么样？"
模型：识别要调用 getWeather(city="北京") 函数
应用：执行 getWeather，得到"晴，25 度"
模型：综合结果回答"北京今天晴，25 度"
```

### Function Calling 的价值

```text
1. 获取实时数据 —— 天气、股价、数据库查询
2. 执行操作 —— 下单、发邮件
3. 弥补模型局限 —— 模型没有实时数据、不能执行操作
```

### Function Calling 示例

```java
// 定义函数（JSON Schema）
// {"name": "getWeather", "parameters": {"city": "string"}}

// 模型返回：
// {"function": "getWeather", "arguments": {"city": "北京"}}

// 应用执行函数，把结果返回模型
String result = weatherService.getWeather("北京");
```

## 最佳实践与踩坑记录

### 最佳实践

1. **代码/事实用低温（0）**。保证确定性。

2. **Prompt 要具体**。角色、任务、格式、示例。

3. **长对话管理上下文**。超限截断或摘要。

4. **敏感操作要人工确认**。Function Calling 执行操作前确认。

5. **Embedding 缓存**。重复文本的向量缓存复用。

### 踩坑记录

**坑 1：温度过高胡言乱语**

```text
temperature=1.5，模型输出幻觉、胡言乱语
```

事实/代码场景用低温，创意场景才调高。

**坑 2：Prompt 太模糊**

```text
"帮我写点东西" —— 太模糊，输出质量差
```

Prompt 要具体（角色、任务、格式、示例）。

**坑 3：上下文超限**

```text
长对话累计 token 超过上下文窗口，报错或截断
```

管理上下文（截断、摘要），或用长上下文模型。

**坑 4：Function Calling 直接执行危险操作**

```text
模型调用 deleteUser 函数，直接执行，可能误删
```

危险操作要人工确认，函数要校验权限。

**坑 5：Embedding 维度不匹配**

```text
不同模型的 Embedding 维度不同（1536 vs 1024），混用报错
```

Embedding 模型和向量库维度要一致。

**坑 6：把 LLM 当数据库**

```text
用 LLM 存储和查询事实，可能幻觉（编造）
```

事实查询用数据库/RAG，LLM 用于理解和生成。
