## 概述

分布式锁是在分布式环境下，控制多个服务实例对共享资源并发访问的机制。

```text
为什么需要分布式锁：
单机环境下，synchronized / ReentrantLock 可以控制并发
分布式环境下，多个服务实例（多进程）无法用 JVM 锁，
需要外部协调机制（Redis、Zookeeper、数据库）实现跨进程的锁
```

```text
典型场景：
1. 防止重复下单（同一用户同时点两次提交）
2. 防止超卖（库存扣减的并发控制）
3. 定时任务防重（多个实例同时跑定时任务）
4. 幂等控制
```

## 分布式锁的设计目标

一个好的分布式锁需要满足：

```text
1. 互斥性 —— 同一时刻只有一个客户端持有锁
2. 无死锁 —— 持锁者崩溃后，锁能自动释放（过期时间）
3. 可重入 —— 同一客户端可重复获取（可选）
4. 高可用 —— 锁服务本身不能单点故障
5. 高性能 —— 获取/释放锁的开销小
```

## Redis 实现分布式锁

Redis 是最常用的分布式锁实现，基于 `SET NX PX` 原子命令。

### 加锁

```java
// SET key value NX PX 过期毫秒
// NX：key 不存在才设置（互斥）
// PX：设置过期时间（防死锁）

String script = "SET lock:order:123 uuid-abc NX PX 30000";
// 返回 OK 表示加锁成功，返回 nil 表示锁已被持有
```

```java
// Spring Data Redis 实现
public boolean tryLock(String key, String value, long expireMillis) {
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent(key, value, expireMillis, TimeUnit.MILLISECONDS);
    return Boolean.TRUE.equals(success);
}
```

### 解锁（Lua 脚本保证原子性）

```java
// 为什么用 Lua：
// 解锁需要"判断 value + 删除 key"两步，
// 如果分开执行，中间可能误删别人的锁

String luaScript =
    "if redis.call('get', KEYS[1]) == ARGV[1] then " +
    "    return redis.call('del', KEYS[1]) " +
    "else " +
    "    return 0 " +
    "end";

Long result = redisTemplate.execute(
    new DefaultRedisScript<>(luaScript, Long.class),
    Collections.singletonList(key),
    value);
```

### 完整实现

```java
@Component
public class RedisDistributedLock {

    @Autowired
    private StringRedisTemplate redisTemplate;

    // 加锁
    public boolean tryLock(String key, String value, long expireSeconds) {
        return Boolean.TRUE.equals(redisTemplate.opsForValue()
            .setIfAbsent(key, value, expireSeconds, TimeUnit.SECONDS));
    }

    // 解锁（Lua 原子）
    public boolean unlock(String key, String value) {
        String script = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                        "return redis.call('del', KEYS[1]) else return 0 end";
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(script, Long.class),
            Collections.singletonList(key), value);
        return Long.valueOf(1).equals(result);
    }
}
```

```java
// 使用
String lockKey = "lock:order:" + orderId;
String lockValue = UUID.randomUUID().toString();

try {
    if (!redisLock.tryLock(lockKey, lockValue, 30)) {
        throw new BusinessException("操作频繁，请稍后重试");
    }
    // 执行业务逻辑
    processOrder(orderId);
} finally {
    redisLock.unlock(lockKey, lockValue);
}
```

### 手写 Redis 锁的问题

```text
1. 锁过期问题 —— 业务执行超过锁过期时间，锁提前释放，其他线程拿到锁
2. 不可重入 —— 同一线程重复加锁会失败
3. 不可续期 —— 无法自动延长锁的有效期
4. 释放锁的 value 判断 —— 必须保证 value 唯一（UUID），否则误删
```

这些问题的完整解决方案就是 Redisson。

## Redisson 分布式锁

Redisson 是 Redis 的 Java 客户端，提供了完整的分布式锁实现，解决了手写锁的所有问题。

### 引入依赖

```xml
<dependency>
    <groupId>org.redisson</groupId>
    <artifactId>redisson-spring-boot-starter</artifactId>
    <version>3.27.0</version>
</dependency>
```

### 基本使用

```java
@Autowired
private RedissonClient redissonClient;

public void doSomething(String key) {
    RLock lock = redissonClient.getLock(key);

    try {
        // tryLock(等待时间, 持有时间, 时间单位)
        if (lock.tryLock(3, 30, TimeUnit.SECONDS)) {
            // 加锁成功，执行业务
            processBusiness();
        } else {
            throw new BusinessException("获取锁失败");
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    } finally {
        // 释放锁（判断是否当前线程持有）
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

### Redisson 的核心特性

```text
1. 可重入锁 —— 同一线程可重复加锁（内部计数器）
2. 看门狗（Watchdog）—— 自动续期，锁默认 30 秒，每 10 秒自动续期到 30 秒
3. 公平锁 —— 按申请顺序获取（FairLock）
4. 读写锁 —— 读读共享，读写互斥（ReadWriteLock）
5. 联锁 —— 多个锁同时加锁（MultiLock）
6. 红锁 —— 多节点 Redis 的锁（RedLock）
```

### 看门狗机制

```java
// 不指定持有时间时，启用看门狗
RLock lock = redissonClient.getLock("lock:order");
lock.lock();   // 默认 30 秒过期，看门狗每 10 秒续期到 30 秒

// 指定持有时间时，看门狗不生效
lock.lock(30, TimeUnit.SECONDS);  // 30 秒后自动释放，不续期
```

```text
看门狗解决"锁提前释放"问题：
1. 加锁时设置 30 秒过期
2. 后台线程每 10 秒检查，如果锁还被持有，续期到 30 秒
3. 业务执行多久，锁就自动续多久
4. 业务崩溃，看门狗停止，锁 30 秒后自动释放
```

### 公平锁和读写锁

```java
// 公平锁：按申请顺序获取
RLock fairLock = redissonClient.getFairLock("lock:fair");
fairLock.lock();

// 读写锁：读读共享，读写互斥
RReadWriteLock rwLock = redissonClient.getReadWriteLock("lock:rw");
RLock readLock = rwLock.readLock();    // 读锁（可并发）
RLock writeLock = rwLock.writeLock();   // 写锁（互斥）
```

## Zookeeper 实现分布式锁

Zookeeper 通过临时顺序节点实现分布式锁，可靠性更高（强一致）。

### 实现原理

```text
基于临时顺序节点 + Watch 机制：

1. 每个客户端在锁节点下创建临时顺序节点
   /lock/lock-0000000001
   /lock/lock-0000000002

2. 检查自己是否是序号最小的节点
   是 → 获取锁
   否 → 监听前一个节点的删除事件

3. 前一个节点删除（释放锁）→ 自己被唤醒，检查是否最小

4. 临时节点：客户端崩溃后节点自动删除（自动释放锁）
```

### Curator 实现

```java
// 引入 Curator（Zookeeper 的 Java 客户端）
@Autowired
private CuratorFramework curatorFramework;

public void doSomething(String lockPath) {
    InterProcessMutex lock = new InterProcessMutex(curatorFramework, lockPath);

    try {
        if (lock.acquire(3, TimeUnit.SECONDS)) {
            // 加锁成功，执行业务
            processBusiness();
        }
    } catch (Exception e) {
        throw new RuntimeException(e);
    } finally {
        try {
            lock.release();
        } catch (Exception e) {
            // 释放失败
        }
    }
}
```

### Zookeeper 锁 vs Redis 锁

| 维度 | Zookeeper | Redis |
|------|-----------|-------|
| 一致性 | 强一致（CP） | 最终一致（AP，可能丢锁） |
| 可靠性 | 高（临时节点自动释放） | 依赖过期时间 |
| 性能 | 较低（节点创建/删除） | 高（内存操作） |
| 实现复杂度 | 简单（Curator 封装） | 手写复杂（Redisson 简单） |
| 适用场景 | 对可靠性要求极高 | 对性能要求高 |

## 数据库实现分布式锁

数据库也可以实现分布式锁，但性能和可靠性较差，一般用于兜底或简单场景。

### 基于唯一索引

```sql
CREATE TABLE distributed_lock (
    lock_key VARCHAR(64) PRIMARY KEY,  -- 锁的唯一 key（唯一索引保证互斥）
    lock_value VARCHAR(64),            -- 持有者标识
    expire_time DATETIME               -- 过期时间
);
```

```java
// 加锁：insert 成功 = 加锁成功（唯一索引保证互斥）
public boolean tryLock(String key, String value, long expireSeconds) {
    try {
        jdbcTemplate.update(
            "INSERT INTO distributed_lock(lock_key, lock_value, expire_time) VALUES(?, ?, ?)",
            key, value, new Date(System.currentTimeMillis() + expireSeconds * 1000));
        return true;
    } catch (DuplicateKeyException e) {
        return false;   // 已存在，加锁失败
    }
}

// 解锁：删除（需校验 value）
public void unlock(String key, String value) {
    jdbcTemplate.update(
        "DELETE FROM distributed_lock WHERE lock_key = ? AND lock_value = ?",
        key, value);
}
```

### 基于 SELECT FOR UPDATE

```java
// 悲观锁：事务内 SELECT ... FOR UPDATE
@Transactional
public void doSomething(String key) {
    // 锁定记录，其他事务阻塞
    String lock = jdbcTemplate.queryForObject(
        "SELECT lock_key FROM distributed_lock WHERE lock_key = ? FOR UPDATE",
        String.class, key);
    // 执行业务
}
```

### 数据库锁的缺点

```text
1. 性能差 —— 数据库操作比 Redis/ZK 慢
2. 无自动释放 —— 需要定时清理过期锁
3. 连接占用 —— 悲观锁占用数据库连接
4. 单点 —— 数据库本身是单点（需高可用方案）
```

## 四种方案对比

| 方案 | 可靠性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|---------|
| Redis 手写 | 中 | 高 | 高（坑多） | 学习/简单场景 |
| Redisson | 高 | 高 | 低（封装好） | 通用（推荐） |
| Zookeeper | 最高 | 低 | 中（Curator） | 高可靠场景 |
| 数据库 | 中 | 低 | 低 | 兜底/无中间件 |

```text
选型建议：
1. 有 Redis → Redisson（性能好，功能全）
2. 有 Zookeeper → Curator（可靠性最高）
3. 都没有 → 数据库兜底
4. 生产环境优先 Redisson
```

## 应用场景实战

### 场景 1：防止重复下单（Redisson）

```java
@Service
public class OrderService {

    @Autowired
    private RedissonClient redissonClient;

    public Order createOrder(OrderRequest request) {
        String lockKey = "lock:order:" + request.getUserId();
        RLock lock = redissonClient.getLock(lockKey);

        try {
            if (!lock.tryLock(3, 10, TimeUnit.SECONDS)) {
                throw new BusinessException("操作频繁，请稍后重试");
            }

            // 检查是否已下单（幂等）
            Order existing = orderMapper.findByUserIdAndTime(request);
            if (existing != null) {
                return existing;
            }

            // 创建订单
            Order order = new Order();
            order.setUserId(request.getUserId());
            orderMapper.insert(order);
            return order;

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException(e);
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### 场景 2：防止库存超卖（Redis 锁）

```java
@Service
public class InventoryService {

    @Autowired
    private RedissonClient redissonClient;

    public boolean deductStock(Long productId, int quantity) {
        String lockKey = "lock:stock:" + productId;
        RLock lock = redissonClient.getLock(lockKey);

        try {
            if (!lock.tryLock(3, 10, TimeUnit.SECONDS)) {
                return false;
            }

            // 查询库存
            int stock = inventoryMapper.getStock(productId);
            if (stock < quantity) {
                return false;  // 库存不足
            }

            // 扣减库存
            inventoryMapper.deduct(productId, quantity);
            return true;

        } catch (InterruptedException e) {
            return false;
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### 场景 3：定时任务防重（多实例）

```java
@Component
public class ScheduledTask {

    @Autowired
    private RedissonClient redissonClient;

    @Scheduled(cron = "0 0 2 * * ?")   // 每天凌晨 2 点
    public void syncData() {
        String lockKey = "lock:task:sync-data";
        RLock lock = redissonClient.getLock(lockKey);

        // 多实例部署时，只有一个实例能拿到锁执行任务
        if (lock.tryLock()) {
            try {
                // 执行定时任务
                syncService.sync();
            } finally {
                if (lock.isHeldByCurrentThread()) {
                    lock.unlock();
                }
            }
        } else {
            log.info("其他实例正在执行，跳过");
        }
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. **生产环境用 Redisson，不手写**。手写锁的坑（续期、可重入、误删）Redisson 都解决了。

2. **锁的粒度要细**。锁 key 精确到业务对象（订单 ID、商品 ID），不要用全局大锁。

3. **锁要有超时兜底**。即使有看门狗，也要有最坏情况的过期时间，防止死锁。

4. **finally 里释放锁**。业务异常也要释放锁，否则死锁。

5. **释放锁前判断持有者**。`isHeldByCurrentThread()` 判断，防止误释放。

### 踩坑记录

**坑 1：锁过期时间小于业务执行时间**

```java
redisLock.tryLock(key, value, 5);  // 锁 5 秒过期
// 业务执行 30 秒，锁在第 5 秒就释放了
// 其他线程拿到锁，并发执行
```

锁过期时间要大于业务最大执行时间，或用 Redisson 看门狗自动续期。

**坑 2：value 不唯一导致误删**

```java
redisLock.tryLock(key, "1", 30);  // 所有线程都用 value="1"
// 线程 A 的锁过期，线程 B 拿到锁（value 也是 "1"）
// 线程 A 执行完释放锁，删掉了 B 的锁
```

value 必须唯一（UUID），解锁时校验 value，防止误删。

**坑 3：解锁非原子操作**

```java
if (redisTemplate.opsForValue().get(key).equals(value)) {  // 判断
    redisTemplate.delete(key);                              // 删除（中间可能被其他线程修改）
}
// 判断和删除之间，锁可能已经过期并被其他线程获取，误删别人的锁
```

解锁必须用 Lua 脚本保证"判断 + 删除"原子性。

**坑 4：可重入问题**

```java
// 手写 Redis 锁不可重入
public void methodA() {
    lock(key);      // 第一次加锁成功
    methodB();      // 方法 B 也调用 lock(key)，同一线程重复加锁
    // 手写锁：第二次加锁失败（key 已存在），死锁
}
```

需要可重入时用 Redisson（内部计数器实现）。

**坑 5：Redisson 锁释放异常**

```java
lock.unlock();   // 如果锁已过期（被其他线程持有），unlock 抛 IllegalMonitorStateException
```

释放前用 `lock.isHeldByCurrentThread()` 判断，或 try-catch。

**坑 6：Redis 主从切换丢锁**

```text
Redis 主从异步复制，主节点宕机时，未同步的锁数据丢失，
从节点升级为主后，锁可能被两个客户端同时持有
```

对锁可靠性要求极高时，用 RedLock（多节点）或 Zookeeper。
