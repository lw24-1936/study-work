## 概述

分布式事务是跨多个服务/数据库的事务，保证多个操作的原子性。这是分布式系统中最复杂的问题之一。

```text
为什么需要分布式事务：
单机事务（本地事务）：一个数据库内，ACID 保证
分布式事务：跨服务、跨数据库的操作要保证一致性

典型场景：下单流程
1. 订单服务创建订单（订单库）
2. 库存服务扣减库存（库存库）
3. 账户服务扣减余额（账户库）
三个操作要么全成功，要么全失败
```

```text
分布式事务的难点：
1. 网络不可靠 —— 消息可能丢失、超时
2. 没有全局时钟 —— 无法确定操作顺序
3. 部分失败 —— 某些服务成功，某些失败
```

## 分布式事务的挑战

### 本地事务 vs 分布式事务

```text
本地事务（单库）：
BEGIN;
UPDATE orders SET status = 'PAID' WHERE id = 1;
UPDATE inventory SET stock = stock - 1 WHERE product_id = 100;
COMMIT;
// 一个数据库，一个事务，要么全成功要么全回滚

分布式事务（跨库/跨服务）：
订单服务：UPDATE orders ...（订单库）
库存服务：UPDATE inventory ...（库存库）
// 两个服务，两个数据库，无法用本地事务保证原子性
```

### 核心问题

```text
1. 原子性 —— 如何保证多个操作要么全成功要么全失败
2. 一致性 —— 如何保证各服务数据最终一致
3. 隔离性 —— 如何避免中间状态被读到
```

### 解决方案分类

```text
强一致方案：
- XA（两阶段提交）
- Seata AT 模式

最终一致方案：
- TCC
- Saga
- 本地消息表
- Outbox
- 事务消息（RocketMQ）
```

## XA 两阶段提交

XA 是数据库层面的分布式事务标准，基于两阶段提交（2PC）。

### 两阶段提交流程

```text
阶段 1（准备 Prepare）：
协调者询问所有参与者："能不能提交？"
各参与者执行操作但不提交，锁定资源，回复"可以"或"不可以"

阶段 2（提交 Commit/回滚 Rollback）：
所有参与者都"可以" → 协调者通知所有参与者"提交"
任一参与者"不可以" → 协调者通知所有参与者"回滚"
```

```text
        协调者（Coordinator）
        │
        ├── 阶段1：准备（Prepare）
        │   ├──> 参与者1：执行+锁定，回复"就绪"
        │   ├──> 参与者2：执行+锁定，回复"就绪"
        │   └──> 参与者3：执行+锁定，回复"就绪"
        │
        ├── 阶段2：提交（Commit）
        │   ├──> 参与者1：提交
        │   ├──> 参与者2：提交
        │   └──> 参与者3：提交
```

### XA 的优缺点

```text
优点：
1. 强一致 —— 所有参与者要么都提交要么都回滚
2. 标准规范 —— 数据库原生支持

缺点：
1. 同步阻塞 —— 参与者锁定资源等待协调者指令
2. 单点故障 —— 协调者故障，事务悬挂
3. 性能差 —— 两阶段 + 资源锁定，吞吐低
4. 不支持跨服务 —— 主要在同构数据库间使用
```

### XA 的适用场景

```text
- 同构数据库（都是 MySQL）跨库事务
- 对强一致要求极高的场景（金融核心）
- 数据量小、事务时间短

不适用：
- 高并发、低延迟场景
- 跨异构系统（不同数据库、不同服务）
```

## TCC 补偿事务

TCC（Try-Confirm-Cancel）是业务层面的分布式事务，通过补偿实现最终一致。

### TCC 的三个阶段

```text
Try（尝试）：
预留资源（如冻结库存、锁定资金），执行业务检查

Confirm（确认）：
所有 Try 成功，执行真正的业务操作（扣减冻结的资源）

Cancel（取消）：
某个 Try 失败，回滚所有已 Try 的资源（释放冻结）
```

```text
以转账为例（A 转 100 给 B）：

Try 阶段：
A 账户冻结 100 元（余额不变，冻结额 +100）
B 账户冻结 -100 元（预增）

Confirm 阶段：
A 账户扣除冻结的 100 元（余额 -100）
B 账户增加 100 元（余额 +100）

Cancel 阶段（任一 Try 失败）：
A 账户解冻 100 元
B 账户撤销预增
```

### TCC 代码示例

```java
// 冻结服务接口（TCC 三个方法）
public interface AccountTccService {

    @TccAction(name = "transfer", type = TccActionType.TRY)
    boolean tryTransfer(Long fromId, Long toId, BigDecimal amount);

    @TccAction(name = "transfer", type = TccActionType.CONFIRM)
    boolean confirmTransfer(Long fromId, Long toId, BigDecimal amount);

    @TccAction(name = "transfer", type = TccActionType.CANCEL)
    boolean cancelTransfer(Long fromId, Long toId, BigDecimal amount);
}
```

```java
// Try：冻结资金
public boolean tryTransfer(Long fromId, Long toId, BigDecimal amount) {
    // 检查余额并冻结
    return accountMapper.freeze(fromId, amount);
}

// Confirm：确认转账
public boolean confirmTransfer(Long fromId, Long toId, BigDecimal amount) {
    // 扣除冻结金额
    return accountMapper.confirm(fromId, amount);
}

// Cancel：取消转账
public boolean cancelTransfer(Long fromId, Long toId, BigDecimal amount) {
    // 解冻金额
    return accountMapper.unfreeze(fromId, amount);
}
```

### TCC 的优缺点

```text
优点：
1. 性能好 —— 不锁定资源，预留即可
2. 最终一致 —— 补偿机制保证一致性

缺点：
1. 侵入性强 —— 每个业务要写 Try/Confirm/Cancel 三个方法
2. 实现复杂 —— 补偿逻辑容易出错
3. 需要考虑空回滚、悬挂、幂等
```

```text
适用场景：
- 资金、库存等需要预留资源的场景
- 对一致性要求高、愿意投入开发成本
```

## Saga 事务

Saga 将长事务拆分为多个本地事务，每个本地事务配一个补偿操作。

### Saga 模式

```text
Saga = 一串本地事务 + 对应的补偿事务

正常流程：
T1 → T2 → T3 → ... → Tn

失败补偿（逆向执行）：
T1 → T2（失败）→ C2 → C1

每个 Ti 是本地事务，Ci 是 Ti 的补偿操作
```

```text
以订单流程为例：
T1 = 创建订单      C1 = 取消订单
T2 = 扣减库存      C2 = 恢复库存
T3 = 扣减余额      C3 = 恢复余额

T1 成功 → T2 成功 → T3 失败
→ C3（恢复余额）→ C2（恢复库存）→ C1（取消订单）
```

### Saga 的两种实现

```text
编排式（Choreography）：
各服务通过消息事件驱动，无中心协调者
服务 A 发事件 → 服务 B 消费 → 发事件 → 服务 C 消费

控制式（Orchestration）：
中心协调者（编排器）指挥各服务执行
协调器调用服务 A → 调用服务 B → 调用服务 C
```

### Saga 的优缺点

```text
优点：
1. 松耦合 —— 各服务独立，通过事件/命令通信
2. 无锁定 —— 各本地事务独立提交
3. 适合长事务 —— 不长时间占用资源

缺点：
1. 中间状态可见 —— 数据可能处于不一致的中间态
2. 补偿可能失败 —— 需要重试和人工介入
3. 没有隔离性 —— 并发读可能读到中间状态
```

## 本地消息表

本地消息表是最终一致性的经典方案，通过"业务 + 消息"同库事务保证可靠性。

### 核心思想

```text
1. 业务操作和消息记录在同一个本地事务中
   BEGIN;
   UPDATE orders SET status = 'PAID';
   INSERT INTO message(内容, 状态='待发送');
   COMMIT;
   // 业务和消息要么都成功，要么都失败

2. 后台定时任务扫描"待发送"消息，发送到 MQ

3. 消费者消费消息，执行业务，回调确认

4. 定时任务清理已确认的消息
```

### 表结构

```sql
CREATE TABLE local_message (
    id BIGINT PRIMARY KEY,
    topic VARCHAR(64),           -- 消息主题
    message_body TEXT,           -- 消息内容
    status VARCHAR(16),          -- 待发送/已发送/已消费/失败
    retry_count INT DEFAULT 0,   -- 重试次数
    create_time DATETIME,
    update_time DATETIME
);
```

### 实现

```java
@Service
public class OrderService {

    @Transactional   // 业务 + 消息同一事务
    public void createOrder(Order order) {
        // 1. 业务操作
        orderMapper.insert(order);

        // 2. 写本地消息表
        LocalMessage message = new LocalMessage();
        message.setTopic("order-created");
        message.setBody(JSON.toJSONString(order));
        message.setStatus("待发送");
        messageMapper.insert(message);
        // 事务提交后，消息和业务一起落库
    }
}
```

```java
// 定时任务：扫描并发送消息
@Component
public class MessageSender {

    @Scheduled(fixedDelay = 5000)
    public void sendMessages() {
        List<LocalMessage> messages = messageMapper.findByStatus("待发送");
        for (LocalMessage message : messages) {
            try {
                rabbitTemplate.convertAndSend(message.getTopic(), message.getBody());
                messageMapper.updateStatus(message.getId(), "已发送");
            } catch (Exception e) {
                messageMapper.incrementRetry(message.getId());
            }
        }
    }
}
```

### 本地消息表的优缺点

```text
优点：
1. 实现简单 —— 不用额外组件
2. 可靠性高 —— 业务和消息原子落库
3. 最终一致 —— 定时重发保证

缺点：
1. 侵入业务 —— 业务代码要写消息表
2. 消息延迟 —— 定时扫描有延迟
3. 消息表膨胀 —— 需要定期清理
```

## Outbox 模式

Outbox（发件箱）模式是本地消息表的变体，是事务性发件箱的标准实现。

### Outbox vs 本地消息表

```text
本地消息表：
- 业务表 + 消息表（两张表，同一事务）
- 定时任务扫描消息表发送

Outbox 模式：
- 业务表 + Outbox 表（两张表，同一事务）
- 通过 CDC（Change Data Capture）监听 Outbox 表变化，发送消息
- 或定时任务轮询 Outbox 表
```

### Outbox 表结构

```sql
CREATE TABLE outbox (
    id BIGINT PRIMARY KEY,
    aggregate_type VARCHAR(64),   -- 聚合类型（如 Order）
    aggregate_id BIGINT,          -- 聚合 ID
    event_type VARCHAR(64),       -- 事件类型（OrderCreated）
    payload TEXT,                 -- 事件内容（JSON）
    created_at DATETIME
);
```

### Outbox 实现

```java
@Service
public class OrderService {

    @Transactional   // 业务 + outbox 同一事务
    public void createOrder(Order order) {
        // 1. 业务操作
        orderMapper.insert(order);

        // 2. 写 outbox
        OutboxEvent event = new OutboxEvent();
        event.setAggregateType("Order");
        event.setAggregateId(order.getId());
        event.setEventType("OrderCreated");
        event.setPayload(JSON.toJSONString(order));
        outboxMapper.insert(event);
    }
}
```

```java
// 通过 Debezium（CDC）监听 outbox 表变化，发送到 Kafka
// 或定时任务轮询
```

### Outbox 的优缺点

```text
优点：
1. 可靠 —— 业务和事件原子落库
2. 解耦 —— 事件发送与业务分离
3. 可追踪 —— outbox 表记录所有事件

缺点：
1. 需要 CDC 工具（Debezium）或轮询
2. 事件可能重复（消费者要幂等）
```

## 事务消息（RocketMQ）

RocketMQ 提供事务消息，是本地消息表的"托管版"，不用自己维护消息表。

### 事务消息流程

```text
1. 发送 half 消息（半消息，消费者不可见）
2. 执行本地事务（业务操作）
3. 本地事务成功 → 提交消息（消费者可见）
   本地事务失败 → 回滚消息（消费者不可见）
4. 若步骤 3 超时未确认，MQ 回查本地事务状态
```

```text
生产者                 RocketMQ              消费者
   │ 发送 half 消息        │                    │
   │─────────────────────>│                    │
   │ 执行本地事务          │                    │
   │─────────────────────>│（消息暂不可见）     │
   │ 提交/回滚消息         │                    │
   │─────────────────────>│ 提交后消息可见       │
   │                      │───────────────────>│ 消费
```

### RocketMQ 事务消息实现

```java
@Service
public class OrderTransactionProducer {

    @Autowired
    private RocketMQTemplate rocketMQTemplate;

    public void sendOrderMessage(Order order) {
        rocketMQTemplate.sendMessageInTransaction(
            "order-topic",                          // topic
            MessageBuilder.withPayload(order).build(),  // 消息
            order                                  // 业务参数（回查用）
        );
    }
}

// 事务监听器（执行本地事务 + 回查）
@RocketMQTransactionListener
public class OrderTransactionListener implements RocketMQLocalTransactionListener {

    @Override
    public RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        // 执行本地事务
        try {
            Order order = (Order) arg;
            orderMapper.insert(order);   // 本地业务
            return RocketMQLocalTransactionState.COMMIT;   // 提交消息
        } catch (Exception e) {
            return RocketMQLocalTransactionState.ROLLBACK;  // 回滚消息
        }
    }

    @Override
    public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
        // MQ 回查本地事务状态
        Long orderId = Long.parseLong((String) msg.getHeaders().get("orderId"));
        Order order = orderMapper.findById(orderId);
        return order != null
            ? RocketMQLocalTransactionState.COMMIT
            : RocketMQLocalTransactionState.ROLLBACK;
    }
}
```

### 事务消息的优缺点

```text
优点：
1. 简单 —— 不用自己维护消息表
2. 可靠 —— MQ 保证事务消息的投递
3. 最终一致 —— 回查机制兜底

缺点：
1. 依赖 RocketMQ —— 其他 MQ（RabbitMQ/Kafka）不支持
2. 回查实现要准确 —— 回查逻辑错误会导致消息错投
```

## Seata

Seata 是阿里开源的分布式事务解决方案，提供 AT、TCC、Saga、XA 四种模式。

### Seata 架构

```text
Seata 三个角色：
1. TC（Transaction Coordinator）—— 事务协调者（Seata Server）
2. TM（Transaction Manager）—— 事务管理器（发起事务的服务）
3. RM（Resource Manager）—— 资源管理器（参与事务的服务）
```

```text
                TC（Seata Server）
                │  │  │
        ┌───────┘  │  └───────┐
        │          │          │
   TM/RM       TM/RM       TM/RM
   (订单服务)   (库存服务)   (账户服务)
```

### AT 模式（最常用）

```text
AT 模式 = 两阶段提交 + 数据快照（undo log）

阶段 1（一阶段）：
各服务执行本地事务，同时记录 undo log（数据快照），
本地事务提交（不等待全局确认）

阶段 2（二阶段）：
全局提交 → 删除 undo log
全局回滚 → 用 undo log 恢复数据
```

```java
// 全局事务发起方
@Service
public class OrderService {

    @GlobalTransactional   // 开启全局事务（Seata）
    public void createOrder(OrderDTO dto) {
        // 本地操作
        orderMapper.insert(dto.toOrder());
        // 远程调用（参与全局事务）
        inventoryClient.deduct(dto.getItems());
        accountClient.deduct(dto.getUserId(), dto.getAmount());
    }
}
```

```java
// 参与方（库存服务）—— 普通本地事务，自动参与全局事务
@Service
public class InventoryService {

    @Transactional   // 普通本地事务，Seata 自动代理
    public void deduct(List<Item> items) {
        items.forEach(item -> inventoryMapper.deduct(item.getProductId(), item.getQuantity()));
    }
}
```

### AT 模式的优缺点

```text
优点：
1. 侵入性低 —— 业务代码只需加 @GlobalTransactional
2. 自动回滚 —— undo log 自动补偿
3. 性能较好 —— 一阶段就提交本地事务，不长时间锁资源

缺点：
1. 需要 undo log 表 —— 每个库都要建 undo_log 表
2. 隔离性弱 —— 全局事务提交前，其他事务可能读到已提交的中间态
3. 依赖 Seata Server —— 需要部署和维护
```

### Seata 四种模式对比

| 模式 | 侵入性 | 性能 | 一致性 | 适用场景 |
|------|--------|------|--------|---------|
| AT | 低 | 中 | 弱一致 | 通用（推荐） |
| TCC | 高 | 高 | 强一致 | 资金、库存 |
| Saga | 中 | 高 | 最终一致 | 长事务、跨系统 |
| XA | 低 | 低 | 强一致 | 同构数据库 |

## 方案对比与选型

| 方案 | 一致性 | 侵入性 | 性能 | 复杂度 | 适用场景 |
|------|--------|--------|------|--------|---------|
| XA | 强一致 | 低 | 差 | 低 | 同构库、金融核心 |
| TCC | 强一致 | 高 | 好 | 高 | 资金、库存 |
| Saga | 最终一致 | 中 | 好 | 中 | 长事务、跨系统 |
| 本地消息表 | 最终一致 | 中 | 好 | 低 | 异步解耦 |
| Outbox | 最终一致 | 低 | 好 | 中 | 事件驱动 |
| 事务消息 | 最终一致 | 低 | 好 | 低 | RocketMQ 场景 |
| Seata AT | 弱一致 | 低 | 好 | 低 | 通用（推荐） |

```text
选型建议：
1. 大多数场景 → 最终一致（本地消息表 / 事务消息）
2. 强一致要求 → Seata AT / TCC
3. 资金场景 → TCC（预留 + 补偿）
4. 简单异步解耦 → 本地消息表 / Outbox
5. 有 RocketMQ → 事务消息
```

## 应用场景实战

### 场景 1：下单流程（Seata AT）

```java
// 订单服务（全局事务发起方）
@Service
public class OrderService {

    @GlobalTransactional
    public Order createOrder(OrderDTO dto) {
        // 1. 创建订单
        Order order = new Order();
        order.setUserId(dto.getUserId());
        orderMapper.insert(order);

        // 2. 扣减库存（远程，参与全局事务）
        inventoryClient.deduct(dto.getItems());

        // 3. 扣减余额（远程，参与全局事务）
        accountClient.deduct(dto.getUserId(), dto.getAmount());

        return order;
        // 任一步失败，全局回滚（订单删除、库存恢复、余额恢复）
    }
}
```

### 场景 2：订单状态同步（本地消息表）

```java
@Service
public class OrderService {

    @Transactional
    public void payOrder(Long orderId) {
        // 1. 更新订单状态
        orderMapper.updateStatus(orderId, "PAID");

        // 2. 写本地消息表
        LocalMessage message = new LocalMessage();
        message.setTopic("order-paid");
        message.setBody(String.valueOf(orderId));
        message.setStatus("待发送");
        messageMapper.insert(message);
    }
}

// 库存服务消费消息
@Component
public class OrderPaidConsumer {
    @RabbitListener(queues = "order-paid-queue")
    public void handle(Long orderId) {
        // 发货等后续操作
        deliveryService.deliver(orderId);
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. **优先最终一致，避免强一致**。分布式事务强一致方案复杂且性能差，能用最终一致的用最终一致。

2. **本地消息表是性价比最高的方案**。实现简单、可靠性高，适合大多数异步解耦场景。

3. **Seata AT 是侵入性最低的强一致方案**。需要强一致时优先 Seata AT。

4. **资金场景用 TCC**。预留资源 + 补偿，避免资金不一致。

5. **所有方案都要幂等**。分布式事务的重试、回查都可能重复执行，业务必须幂等。

### 踩坑记录

**坑 1：分布式事务滥用**

```text
所有跨服务操作都用分布式事务（Seata/XA），
导致系统复杂度爆炸，性能下降
```

大部分场景最终一致（消息 + 补偿）就够了，只有资金等核心场景才需要强一致。

**坑 2：本地消息表消息丢失**

```java
// 消息发送成功，但更新消息状态失败
rabbitTemplate.send(message);
// 这里抛异常，消息已发但状态还是"待发送"，会重复发送
```

消息状态更新要处理，消费端幂等兜底（重复消息不影响业务）。

**坑 3：TCC 的空回滚和悬挂**

```text
空回滚：Try 没执行（网络超时），Cancel 却执行了（要处理这种场景）
悬挂：Cancel 先到，Try 后到（Try 要判断是否已回滚）
```

TCC 实现要考虑空回滚、悬挂、幂等三个边界情况。

**坑 4：Seata undo log 表缺失**

```text
使用 Seata AT 模式，但业务库没建 undo_log 表，
运行时报错
```

每个参与 Seata AT 的数据库都要建 undo_log 表。

**坑 5：事务消息回查逻辑错误**

```java
@RocketMQTransactionListener
public class Listener {
    @Override
    public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
        // 回查逻辑错误，本地事务已提交但回查返回 ROLLBACK
        // 导致消息没发出去，但业务已执行，数据不一致
    }
}
```

回查逻辑必须准确判断本地事务状态，否则导致数据不一致。

**坑 6：长事务占用资源**

```text
分布式事务（XA/Seata）执行时间长，长时间锁定资源
导致数据库连接耗尽、锁等待
```

事务尽量短，耗时操作（RPC、文件 IO）放在事务外，或改用最终一致方案。
