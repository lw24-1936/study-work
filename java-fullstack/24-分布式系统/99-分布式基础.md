## 概述

分布式系统是由多台独立计算机组成的系统，这些计算机通过网络通信、协同工作，对外表现为一个整体。

```text
为什么需要分布式系统：
1. 单机性能上限 —— CPU、内存、磁盘有物理极限
2. 高可用 —— 单机故障导致整个系统不可用
3. 水平扩展 —— 分布式可以横向加机器
4. 业务拆分 —— 微服务化，各模块独立演进
```

```text
分布式系统的核心问题：
一致性（Consistency）—— 数据在多个副本间如何保持一致
可用性（Availability）—— 系统如何持续可用
分区容错（Partition Tolerance）—— 网络故障时系统如何应对
```

## 分布式系统的挑战

### 1. 网络不可靠

```text
网络是分布式系统的最大不确定因素：
1. 消息延迟 —— 网络传输有延迟
2. 消息丢失 —— 网络丢包
3. 消息乱序 —— 消息到达顺序不一致
4. 网络分区 —— 节点间无法通信
```

### 2. 时钟不一致

```text
各节点的时钟可能不同步：
1. 无法依赖物理时钟做全局排序
2. 需要逻辑时钟（Lamport 时钟、向量时钟）
```

### 3. 部分失败

```text
分布式系统中，部分节点失败是常态，不是异常：
1. 某节点宕机，其他节点正常
2. 无法区分"节点挂了"还是"网络慢了"
```

### 4. 数据一致性

```text
多个副本的数据如何保持一致：
1. 强一致 —— 任何时刻读到的都是最新数据
2. 最终一致 —— 经过一段时间后数据一致
```

## CAP 定理

CAP 定理是分布式系统的基石理论，由 Eric Brewer 在 2000 年提出。

### CAP 的三个维度

```text
C（Consistency）一致性：
所有节点在同一时刻看到的数据是一致的（读操作总能读到最新写入）

A（Availability）可用性：
每个请求都能在合理时间内得到响应（不保证是最新数据）

P（Partition Tolerance）分区容错：
网络分区（节点间通信中断）时，系统仍能继续运行
```

### CAP 的核心结论

```text
CAP 定理：一个分布式系统最多只能同时满足三个特性中的两个，
不可能三者兼得。

关键：网络分区（P）是不可避免的（网络故障一定会发生），
所以实际是 CP 和 AP 之间的权衡。
```

```text
        C（一致性）
       / \
      /   \
     /     \
    /       \
   P ——————— A（可用性）
   分区容错

分区必然发生（P 必选），所以：
CP 系统：分区时牺牲可用性，保证一致性
AP 系统：分区时牺牲一致性，保证可用性
```

### CP vs AP

**CP（一致性 + 分区容错）**：

```text
分区发生时，为了保证一致性，拒绝写入或拒绝响应。

典型：Zookeeper、Etcd、Consul、Nacos（CP 模式）

场景：金融交易、配置管理（一致性优先）
```

**AP（可用性 + 分区容错）**：

```text
分区发生时，为了保证可用性，允许返回旧数据。

典型：Eureka、Nacos（AP 模式）、Cassandra

场景：服务注册、购物车（可用性优先）
```

### 为什么 P 必选

```text
网络分区（P）是物理现实，无法避免：
- 网线断了、交换机故障、机房断电、网络拥塞

既然 P 必然发生，系统必须处理分区，
所以只能在 C 和 A 之间选择。
```

## BASE 理论

BASE 理论是对 CAP 中 AP 方案的延伸，是最终一致性的理论基础。

### BASE 的含义

```text
BA（Basically Available）基本可用：
系统出现故障时，允许损失部分可用性（如响应变慢、部分功能降级）

S（Soft State）软状态：
允许系统存在中间状态，该状态不影响系统整体可用性
（数据副本可以暂时不一致）

E（Eventually Consistent）最终一致性：
系统中的所有副本，经过一段时间后最终达到一致
```

```text
BASE vs ACID：
ACID（事务）—— 强一致，数据库事务的四个特性
BASE（分布式）—— 最终一致，分布式系统的妥协

ACID：原子性、一致性、隔离性、持久性（单机数据库）
BASE：基本可用、软状态、最终一致（分布式系统）
```

### BASE 的实践

```text
1. 基本可用 —— 秒杀时降级（关掉非核心功能）、限流
2. 软状态 —— 订单状态"支付中"是中间状态
3. 最终一致 —— 库存扣减通过消息异步同步，最终一致
```

## 一致性模型

一致性模型描述数据在多个副本间如何保持一致。

### 强一致性（Strong Consistency）

```text
任何时刻，任何节点读到的都是最新写入的数据。

实现：分布式事务（XA）、Paxos/Raft 共识算法

代价：性能差、可用性低（分区时不可用）
```

```text
场景：银行转账、余额扣减
要求：读到的余额必须是最新的
```

### 弱一致性（Weak Consistency）

```text
不保证任何时刻读到最新数据，但经过一段时间后（最终）会一致。

实现：消息队列异步同步、定时任务对账

优点：性能好、可用性高
```

### 最终一致性（Eventual Consistency）

最终一致性是弱一致性的特例，是 BASE 理论的核心：

```text
系统保证：如果没有新的更新，最终所有副本会达到一致。

实现方式：
1. 消息队列异步同步
2. 定时任务对账补偿
3. 本地消息表 + 定时重发
```

### 一致性模型对比

| 模型 | 读到的数据 | 性能 | 典型实现 |
|------|-----------|------|---------|
| 强一致 | 总是最新 | 差 | XA 事务、Raft |
| 最终一致 | 可能旧，最终一致 | 好 | 消息异步同步 |
| 弱一致 | 不保证 | 最好 | DNS、缓存 |

## CAP 与 BASE 的关系

```text
CAP 和 BASE 是从不同维度描述分布式系统：

CAP：
- 理论层面，说明"鱼和熊掌不可兼得"
- 分区发生时，必须在 C 和 A 之间选择

BASE：
- 实践层面，提供 AP 方案的落地指导
- "放弃强一致，追求最终一致"

关系：
CAP 选择了 AP（牺牲强一致），
BASE 就是 AP 方案的实现指导（怎么做到最终一致）
```

```text
选择策略：
1. 核心数据（钱、订单）—— 强一致（CP）
2. 非核心数据（缓存、计数）—— 最终一致（AP）
3. 大部分场景 —— BASE 最终一致，配合补偿
```

## 常见中间件的 CAP 选择

| 中间件 | CAP 选择 | 说明 |
|--------|---------|------|
| Zookeeper | CP | 强一致，Leader 选举期间不可用 |
| Etcd | CP | 强一致（Raft） |
| Consul | CP | 强一致 |
| Nacos | CP/AP 可切换 | 默认 AP，可切 CP |
| Eureka | AP | 最终一致，可用性优先 |
| Redis Cluster | AP | 主从异步复制，可能丢数据 |
| MySQL 主从 | AP | 主从复制延迟 |
| Kafka | AP（可配 CP） | 副本同步有延迟 |

## 应用场景实战

### 场景 1：注册中心的 CAP 选择

```text
服务注册中心的选择：
Eureka（AP）：
- 分区时，服务仍可注册和查询（可能拿到旧实例）
- 保证注册中心高可用

Zookeeper（CP）：
- 分区时，Leader 选举期间注册中心不可用
- 保证实例列表强一致

实践：
注册中心用 AP（Nacos 默认 AP），
因为短暂的不一致（读到已下线实例）可通过重试解决，
但注册中心不可用会导致整个微服务不可用。
```

### 场景 2：订单系统的最终一致

```text
下单流程（最终一致）：
1. 创建订单（订单服务）
2. 扣减库存（库存服务）—— 通过消息异步通知
3. 库存扣减结果通过消息回传
4. 订单状态最终更新为"已扣库存"或"库存不足"

中间状态：订单"待确认"，库存"扣减中"
最终状态：订单和库存一致
```

### 场景 3：缓存的一致性策略

```text
缓存和数据库的最终一致（Cache Aside）：
1. 读：先读缓存，未命中读库，写缓存
2. 写：先更新数据库，再删除缓存
3. 删除失败：重试或延迟双删

结果：缓存和数据库最终一致（短暂不一致）
```

## 最佳实践与踩坑记录

### 最佳实践

1. **核心数据强一致，非核心数据最终一致**。钱、订单用强一致，缓存、计数用最终一致。

2. **注册中心用 AP**。注册中心不可用比短暂不一致更致命。

3. **最终一致必须配补偿**。最终一致不是"不管了"，要有对账和补偿机制。

4. **明确系统的 CAP 选择**。设计阶段就要明确一致性要求，而不是事后补救。

5. **减少强一致的范围**。强一致性能差，能最终一致的不用强一致。

### 踩坑记录

**坑 1：误以为 CAP 是"三选二"**

```text
错误理解：CAP 三个特性随便选两个
正确理解：P 是必选的（网络分区必然发生），
实际是"分区发生时，选 C 还是选 A"
```

CAP 不是自由三选二，P 是前提条件。

**坑 2：用强一致解决所有问题**

```text
所有数据都要求强一致，导致系统性能差、可用性低
实际大部分场景（缓存、计数、统计）最终一致就够了
```

按数据重要性分级一致性要求。

**坑 3：忽略了网络延迟**

```text
设计时假设网络是可靠的、零延迟的，
实际网络有延迟、丢包、乱序
```

分布式设计要考虑网络不确定性，超时、重试、幂等是标配。

**坑 4：最终一致没有补偿机制**

```text
"最终一致"变成了"永远不一致"，
消息丢了、消费失败都没有补偿，数据一直不一致
```

最终一致要有对账、补偿、重试机制兜底。

**坑 5：混淆"强一致"和"实时一致"**

```text
强一致 = 任何时刻读到的都是最新（分布式事务保证）
实时一致 = 数据实时同步（不一定是强一致）

有些系统追求"实时"但不需要"强一致"（如点赞数，实时+最终一致）
```

**坑 6：注册中心用 CP 导致雪上加霜**

```text
微服务本身出问题时，注册中心（CP）恰好也在选举不可用，
服务发现失败，故障扩大
```

注册中心优先 AP，保证自身高可用。
