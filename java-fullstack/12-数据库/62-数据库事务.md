## 概述

事务是数据库操作的原子单元——一组 SQL 要么全部执行成功，要么全部回滚。没有事务，数据库在面对并发和故障时无法保证数据一致性。

## ACID 特性

### Atomicity（原子性）

事务中的所有操作是一个整体。要么全部成功，要么全部失败回滚。

实现机制：Undo Log。回滚时通过 Undo Log 把数据恢复到事务开始前的状态。

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- 都执行
-- 如果第二条 UPDATE 失败，整个事务 ROLLBACK
```

### Consistency（一致性）

事务执行前后，数据库都处于一致状态——满足所有约束（主键、外键、CHECK、触发器）。

一致性更多是业务层面的概念，由原子性 + 隔离性 + 持久性共同保证。例如转账前后总金额不变，这是业务规则，数据库本身并不知道。

### Isolation（隔离性）

多个并发事务之间互相不可见。一个事务的执行不应被其他事务干扰。

实现机制：锁 + MVCC。不同隔离级别有不同的隔离强度。这是事务最复杂的部分——后面重点展开。

### Durability（持久性）

事务一旦提交，修改永久保存，即使系统崩溃也不丢失。

实现机制：Redo Log。提交时写 Redo Log，崩溃后通过重放 Redo Log 恢复。

## 隔离级别

SQL 标准定义了四种隔离级别，隔离强度递增：

| 级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|------|------|-----------|------|------|
| Read Uncommitted | 可能 | 可能 | 可能 | 最高 |
| Read Committed | 不可能 | 可能 | 可能 | 高 |
| Repeatable Read | 不可能 | 不可能 | 可能（InnoDB 通过 Gap Lock 解决） | 中 |
| Serializable | 不可能 | 不可能 | 不可能 | 最低 |

MySQL 默认隔离级别是 Repeatable Read，Oracle 和 PostgreSQL 默认是 Read Committed。

### 设置隔离级别

```sql
-- 查看当前隔离级别
SELECT @@transaction_isolation;     -- MySQL 8.0+
SELECT @@tx_isolation;              -- MySQL 5.x

-- 设置全局隔离级别
SET GLOBAL transaction_isolation = 'READ-COMMITTED';

-- 设置当前会话
SET SESSION transaction_isolation = 'REPEATABLE-READ';

-- Spring Boot 配置
-- spring.datasource.hikari.transaction-isolation=TRANSACTION_READ_COMMITTED
```

### Read Uncommitted（读未提交）

最低隔离级别。一个事务可以读到其他事务未提交的修改。

```
时间线：
事务A: UPDATE user SET age=20 WHERE id=1;  -- 未提交
事务B: SELECT age FROM user WHERE id=1;     -- 读到 20
事务A: ROLLBACK;                            -- 回滚，age 恢复 18
事务B: -- 基于 age=20 继续处理，逻辑错误（脏读）
```

几乎不用于生产环境。

### Read Committed（读已提交）

一个事务只能读到其他事务已提交的修改。解决了脏读。

每次 SELECT 都创建新的 Read View，读的是最新已提交版本。

```
事务A: SELECT age FROM user WHERE id=1;  → 18
事务B: UPDATE user SET age=20 WHERE id=1; COMMIT;
事务A: SELECT age FROM user WHERE id=1;  → 20（不可重复读）
```

同一事务内两次读取结果不同——不可重复读。

### Repeatable Read（可重复读）

MySQL 默认级别。事务开始后，读到的数据始终一致。解决了不可重复读。

事务开始时创建 Read View，后续 SELECT 都用这个 Read View——所以同一事务内多次读取结果相同。

但 Repeatable Read 仍可能发生幻读：

```
事务A: SELECT * FROM user WHERE age>18;       → 返回 5 行
事务B: INSERT INTO user(name,age) VALUES('x',20); COMMIT;
事务A: SELECT * FROM user WHERE age>18;       → 还是 5 行（快照读，不出现幻读）
事务A: UPDATE user SET name='y' WHERE age>18;  → 影响了 6 行！（当前读，幻读）
事务A: SELECT * FROM user WHERE age>18;       → 返回 6 行（更新后数据变了）
```

InnoDB 通过 Next-Key Lock（Record Lock + Gap Lock）在 RR 级别下基本解决了幻读——当前读（SELECT ... FOR UPDATE）会加间隙锁，阻止其他事务插入满足条件的行。

### Serializable（串行化）

最高隔离级别。所有事务串行执行。读加共享锁，写加排他锁。

```sql
-- 事务A
SELECT * FROM user WHERE age>18;  -- 加共享锁

-- 事务B
INSERT INTO user VALUES (...);     -- 阻塞，等待事务A释放锁
```

并发度极低，性能最差，很少使用。

## 并发问题：脏读 / 不可重复读 / 幻读

### 脏读（Dirty Read）

读到其他事务未提交的数据。

```
A: 修改 age 18→20（未提交）
B: 读 age=20
A: ROLLBACK → age 回到 18
B 基于 20 做的判断是错的
```

### 不可重复读（Non-Repeatable Read）

同一事务内两次读取同一行，得到不同值（被其他事务修改）。

```
A: 读 age=18
B: 修改 age→20 并提交
A: 再读 age=20
```

### 幻读（Phantom Read）

同一事务内两次范围查询，第二次多出一些行（被其他事务插入）。

```
A: SELECT COUNT(*) WHERE age>18 → 5 行
B: INSERT age=20 并提交
A: SELECT COUNT(*) WHERE age>18 → 6 行（多了 1 行）
```

三者区别：
- 脏读：读到未提交的修改（UPDATE）
- 不可重复读：同一行被修改，值变了（UPDATE）
- 幻读：范围结果集变多了或少了（INSERT / DELETE）

## MVCC 与隔离级别实现

不同隔离级别下 MVCC 的 Read View 生成时机不同：

### Read Committed 下

每次快照读（普通 SELECT）都生成新的 Read View。所以能读到其他事务已提交的最新数据。

```
A: SELECT → 创建 Read View
B: 修改并提交
A: SELECT → 创建新 Read View → 看到 B 的修改
```

### Repeatable Read 下

事务第一次快照读时生成 Read View，后续复用。所以看不到其他事务的提交。

```
A: SELECT → 创建 Read View（复用到底）
B: 修改并提交
A: SELECT → 复用 Read View → 看不到 B 的修改
```

### 快照读 vs 当前读（再回顾）

```sql
-- 快照读：使用 Read View，不加锁
SELECT * FROM user WHERE id = 1;

-- 当前读：读最新版本，加锁
SELECT * FROM user WHERE id = 1 FOR UPDATE;
SELECT * FROM user WHERE id = 1 FOR SHARE;   -- 8.0+，原名 LOCK IN SHARE MODE
UPDATE user SET ... WHERE ...;
DELETE FROM user WHERE ...;
INSERT INTO user ...;  -- 隐式加插入意向锁
```

当前读一定读最新已提交版本，不受 MVCC Read View 限制。

## 锁机制

### 按粒度

**行锁（Row Lock）**：InnoDB 默认粒度。锁具体行，并发度高。

**表锁（Table Lock）**：锁整张表。MyISAM 默认，DDL 操作时使用。

**页锁（Page Lock）**：BDB 引擎使用，InnoDB 不用。

**间隙锁（Gap Lock）**：锁索引间隙（一个范围），防止插入。

### 按模式

**共享锁（S 锁，Shared Lock）**：允许其他事务读，不允许写。

```sql
SELECT ... FOR SHARE;   -- 加 S 锁
```

**排他锁（X 锁，Exclusive Lock）**：不允许其他事务读写。

```sql
SELECT ... FOR UPDATE;  -- 加 X 锁
UPDATE ...;             -- 加 X 锁
DELETE ...;             -- 加 X 锁
INSERT ...;             -- 加插入意向锁（特殊的 Gap Lock）
```

### 锁兼容性

|  | S 锁 | X 锁 |
|--|------|------|
| S 锁 | 兼容 | 不兼容 |
| X 锁 | 不兼容 | 不兼容 |

### InnoDB 的三种行锁算法

**Record Lock**：单行记录锁。精确锁住索引项。

**Gap Lock**：间隙锁。锁住一个开区间（如 (3, 5)），阻止插入。

**Next-Key Lock**：Record Lock + 其前面的 Gap Lock。锁住一个左开右闭区间（如 (3, 5]）。

```sql
-- id 索引有值：1, 3, 5
-- Next-Key Lock: (-∞,1], (1,3], (3,5], (5,+∞)

-- REPEATABLE READ 下：
SELECT * FROM user WHERE id = 3 FOR UPDATE;
-- 触发 Next-Key Lock: (1,3] + Record Lock: 3
-- 实际锁定区间 (1,5)，不能插入 id=2,4

SELECT * FROM user WHERE id > 3 FOR UPDATE;
-- 触发 Next-Key Lock: (3,5], (5,+∞)
-- 不能插入 id=4,6...
```

### 死锁

两个事务互相等待对方持有的锁：

```
A: UPDATE user SET age=20 WHERE id=1;  -- 锁 id=1
B: UPDATE user SET age=25 WHERE id=2;  -- 锁 id=2
A: UPDATE user SET age=20 WHERE id=2;  -- 等待 B 释放 id=2 的锁
B: UPDATE user SET age=25 WHERE id=1;  -- 等待 A 释放 id=1 的锁 → 死锁
```

InnoDB 检测到死锁后，回滚其中一个事务（持有最少行级排他锁的事务），抛出 `Deadlock found when trying to get lock` 错误。

避免死锁：
- 所有事务按相同顺序访问资源（先锁 id=1 再锁 id=2）
- 尽量缩短事务
- 索引优化减少锁范围

## 悲观锁

悲观锁假设冲突一定会发生，先加锁再操作。

```sql
-- 数据库层面
START TRANSACTION;
SELECT balance FROM account WHERE id = 1 FOR UPDATE;  -- 排他锁
-- 业务判断余额是否足够
UPDATE account SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

Java + MyBatis 示例：

```java
@Select("SELECT stock FROM product WHERE id = #{id} FOR UPDATE")
int getStockForUpdate(Long id);

@Transactional
public void deductStock(Long productId, int quantity) {
    int stock = mapper.getStockForUpdate(productId);  // SELECT ... FOR UPDATE
    if (stock < quantity) {
        throw new BizException("库存不足");
    }
    mapper.updateStock(productId, stock - quantity);
}
```

悲观锁的优点：简单直接，一定能保证一致性。

缺点：
- 锁冲突时阻塞，并发度低
- 可能导致死锁
- 持有锁的时间长（SELECT ... FOR UPDATE 到 COMMIT 之间）

## 乐观锁

乐观锁假设冲突很少发生，提交时才检查冲突。通常用版本号实现。

```sql
-- 表设计
ALTER TABLE product ADD COLUMN version INT DEFAULT 0;

-- 更新时带上版本号
UPDATE product
SET stock = stock - 10, version = version + 1
WHERE id = 1 AND version = 0;   -- version 不匹配则更新 0 行

-- 影响行数 = 0 说明版本号已变（被别人更新过），重试
```

Java 实现（MyBatis-Plus 内置乐观锁）：

```java
@Entity
public class Product {
    @Id
    private Long id;
    private Integer stock;

    @Version     // MyBatis-Plus 的版本号注解
    private Integer version;
}

// 使用时直连调用
@Transactional
public void deductStock(Long productId, int quantity) {
    Product p = productMapper.selectById(productId);
    if (p.getStock() < quantity) throw new BizException("库存不足");
    p.setStock(p.getStock() - quantity);

    int rows = productMapper.updateById(p);
    if (rows == 0) {
        throw new RetryException("版本冲突，请重试");   // 调用方重试
    }
}
```

CAS（Compare And Swap）模式的重试策略：

```java
public void deductWithRetry(Long productId, int quantity) {
    int retry = 0;
    while (retry < 3) {
        try {
            deductStock(productId, quantity);
            return;
        } catch (RetryException e) {
            retry++;
            Thread.sleep(50L * retry);  // 退避重试
        }
    }
    throw new BizException("扣库存失败，请稍后重试");
}
```

乐观锁 vs 悲观锁：

|  | 乐观锁 | 悲观锁 |
|--|--------|--------|
| 实现方式 | 版本号 / 时间戳 | SELECT FOR UPDATE |
| 冲突频率 | 低频（读多写少） | 高频 |
| 吞吐量 | 高 | 低 |
| 重试 | 需要业务层重试 | 数据库层排队 |
| 死锁 | 无 | 可能 |
| 适用 | 库存扣减、计数器 | 银行转账 |

## 分布式事务概述

单机事务由数据库的 ACID 保证。跨服务的分布式事务需要额外方案。

### XA 两阶段提交

```
协调者 → 参与者1：prepare
        参与者2：prepare
        所有 prepare OK → commit
        任一失败 → rollback
```

问题：同步阻塞、单点故障、数据不一致（commit 阶段部分成功）。

### Seata（阿里开源）

- **AT 模式**：自动生成回滚 SQL，业务无侵入。需要全局锁 + undo_log 表
- **TCC 模式**：Try（预留资源）→ Confirm（提交）→ Cancel（回滚），业务需实现三方法
- **Saga 模式**：长事务拆成多个本地事务，每个本地事务有对应的补偿操作

### 最终一致性方案

- **本地消息表**：事务内写业务数据 + 消息表，定时任务扫描发送
- **事务消息**：RocketMQ 的事务消息（半消息 → 执行本地事务 → 提交/回滚）
- **可靠消息 + 最大努力通知**：MQ + 重试 + 死信队列 + 人工兜底

分布式事务将在第 24 篇《分布式系统》中详细展开。

## 应用场景实战

### 场景一：商品库存扣减（乐观锁）

```java
@Service
public class StockService {

    @Transactional
    public Result deduct(Long productId, int quantity) {
        for (int i = 0; i < 3; i++) {
            Product p = productMapper.selectById(productId);
            if (p.getStock() < quantity) {
                return Result.fail("库存不足");
            }
            p.setStock(p.getStock() - quantity);
            int rows = productMapper.updateById(p);  // 带 version
            if (rows > 0) {
                // 扣减成功，记录流水
                stockLogMapper.insert(new StockLog(productId, quantity));
                return Result.ok();
            }
            // rows == 0，版本冲突，重试
        }
        return Result.fail("系统繁忙，请稍后重试");
    }
}
```

### 场景二：转账（悲观锁 + 死锁预防）

```java
@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    // 按 id 排序，固定加锁顺序，避免死锁
    Long first = Math.min(fromId, toId);
    Long second = Math.max(fromId, toId);

    Account a1 = accountMapper.selectForUpdate(first);
    Account a2 = accountMapper.selectForUpdate(second);

    // 根据实际顺序处理转账
    Account from = a1.getId().equals(fromId) ? a1 : a2;
    Account to   = a1.getId().equals(toId)   ? a1 : a2;

    if (from.getBalance().compareTo(amount) < 0) {
        throw new BizException("余额不足");
    }
    from.setBalance(from.getBalance().subtract(amount));
    to.setBalance(to.getBalance().add(amount));

    accountMapper.updateById(from);
    accountMapper.updateById(to);
}
```

关键：`Math.min(fromId, toId)` 保证不管 `(A→B)` 还是 `(B→A)`，加锁顺序都是先小 ID 再大 ID，避免交叉等锁导致的死锁。

### 场景三：@Transactional 失效排查

Spring 事务注解失效的常见原因：

```java
// 1. 非 public 方法
@Transactional
private void doSomething() {}  // 失效！（CGLIB 代理只能拦截 public）

// 2. 同类内部调用
@Service
public class UserService {
    public void methodA() {
        this.methodB();  // 失效！没走代理，直接调用 this
    }
    @Transactional
    public void methodB() {}
}

// 3. 异常被 catch
@Transactional
public void save() {
    try {
        userMapper.insert(user);
        int i = 1 / 0;          // 抛异常
    } catch (Exception e) {
        log.error("error", e);  // catch 掉了，事务不回滚
    }
}

// 4. rollbackFor 未指定
@Transactional  // 只回滚 RuntimeException 和 Error，不回滚受检异常
@Transactional(rollbackFor = Exception.class)  // 全部异常都回滚
```

## 最佳实践与踩坑记录

**实践 1：事务尽量短**

长时间持有事务会导致锁竞争、连接池耗尽、主从延迟。不要把 RPC 调用、文件 IO 放事务里。

**实践 2：隔离级别选择**

互联网项目通常使用 Read Committed——SQL Server/Oracle 的默认级别，性能好，配合乐观锁处理并发冲突。金融系统用 Repeatable Read 或 Serializable。

**实践 3：spring 事务传播行为**

```java
@Transactional(propagation = Propagation.REQUIRED)     // 默认：有则加入，无则新建
@Transactional(propagation = Propagation.REQUIRES_NEW) // 挂起当前，新建独立事务
@Transactional(propagation = Propagation.NESTED)        // 嵌套事务（需要 SavePoint 支持）
```

**踩坑 1**：长事务导致 Undo Log 无法清理，undo 表空间越来越大。

**踩坑 2**：`SELECT ... FOR UPDATE` 的 WHERE 条件必须走索引，否则锁全表。

**踩坑 3**：MySQL 默认 `autocommit=1`，每条 SQL 是一个事务。开启长事务需要显式 START TRANSACTION 或用 Spring 的 @Transactional。

**踩坑 4**：分布环境下乐观锁可能 ABA 问题——版本号不会 ABA（只增不减），但标记位（如状态字段）可能。方案：加版本号。
