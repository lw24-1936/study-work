## 概述

数据库是有组织的数据集合，DBMS（Database Management System）是管理这个集合的软件。RDBMS（Relational Database Management System）特指基于关系模型的数据库管理系统——目前生产环境的主流选择（MySQL、PostgreSQL、Oracle、SQL Server）。

搞 Java 开发必须理清这几个概念：

```
数据 → 数据库（DB）→ 数据库管理系统（DBMS）→ 关系型数据库管理系统（RDBMS）
                                          → NoSQL 数据库（MongoDB、Redis…）
```

## 核心概念：DB / DBMS / RDBMS

### DB（Database，数据库）

一组有组织的数据的集合。物理上表现为磁盘上的文件，逻辑上由表（Table）、视图（View）、存储过程等对象组成。

一个 MySQL 实例中可以有多个数据库，每个数据库是独立的命名空间：

```sql
-- 查看所有数据库
SHOW DATABASES;

-- 创建数据库
CREATE DATABASE shop CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 切换数据库
USE shop;
```

### DBMS（Database Management System）

管理数据库的软件层，负责：

- **数据定义**：通过 DDL 定义表结构、约束、索引
- **数据操纵**：通过 DML 增删改查数据
- **数据控制**：权限管理、并发控制、故障恢复
- **查询优化**：解析 SQL、生成执行计划、选择最优路径

常见 DBMS 对比：

| DBMS | 类型 | 适用场景 | 许可证 |
|------|------|----------|--------|
| MySQL | RDBMS | Web 应用、中小型系统 | GPL/商业 |
| PostgreSQL | RDBMS | 复杂查询、GIS、分析 | BSD |
| Oracle | RDBMS | 金融、大型企业 | 商业 |
| SQL Server | RDBMS | Windows 生态、.NET | 商业 |
| MongoDB | NoSQL 文档型 | 灵活 schema、日志 | SSPL |
| Redis | NoSQL KV 型 | 缓存、计数、队列 | BSD |

### RDBMS（Relational Database Management System）

基于关系模型的 DBMS。核心特征：

1. **数据以表（Table）组织** —— 二维结构，行=记录（Record/Row），列=字段（Column/Field）
2. **表之间通过外键建立关系** —— 一对一、一对多、多对多
3. **通过 SQL 操作数据** —— 声明式语言，告诉 DBMS "要什么"而不是"怎么取"
4. **遵循 ACID 事务特性** —— 保证数据一致性

## 数据模型

数据模型定义了数据的组织方式和操作规则。数据库设计经历了三代演变：

### 层次模型（Hierarchical Model）

数据用树形结构组织，每个子节点只有一个父节点。IBM 的 IMS 是代表。

```
公司
├── 部门A
│   ├── 员工1
│   └── 员工2
└── 部门B
    └── 员工3
```

限制很明显：无法表达多对多关系，查询必须从根节点开始逐层遍历。

### 网状模型（Network Model）

允许子节点有多个父节点，用指针实现。表达能力强于层次模型，但结构复杂，数据独立性差。

### 关系模型（Relational Model）

1970 年 E.F.Codd 提出，用二维表表示实体和关系。这是目前所有主流 RDBMS 的基石。

核心思想：
- 数据与关系都用表表示
- 通过外键关联表
- 用关系代数（选择、投影、连接）操作数据

## 关系模型

### 基本术语

| 术语 | 形式化名称 | 说明 |
|------|-----------|------|
| 表（Table） | 关系（Relation） | 一张二维表 |
| 行（Row） | 元组（Tuple） | 一条记录 |
| 列（Column） | 属性（Attribute） | 一个字段 |
| 取值范围 | 域（Domain） | 列的数据类型和约束 |
| 表的定义 | 关系模式（Schema） | 表名(列名1, 列名2, ...) |

### 关系的三种类型

```sql
-- 一对一（1:1）：一个用户有一个身份证
CREATE TABLE user (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);
CREATE TABLE id_card (
    id INT PRIMARY KEY,
    number VARCHAR(18),
    user_id INT UNIQUE,        -- UNIQUE 保证一对一
    FOREIGN KEY (user_id) REFERENCES user(id)
);

-- 一对多（1:N）：一个部门有多个员工
CREATE TABLE dept (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);
CREATE TABLE emp (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    dept_id INT,
    FOREIGN KEY (dept_id) REFERENCES dept(id)
);

-- 多对多（M:N）：一个学生选多门课，一门课有多个学生
-- 通过中间表实现
CREATE TABLE student (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);
CREATE TABLE course (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);
CREATE TABLE student_course (
    student_id INT,
    course_id INT,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES student(id),
    FOREIGN KEY (course_id) REFERENCES course(id)
);
```

### 关系完整性约束

**实体完整性**：主键不能为空且唯一。通过 `PRIMARY KEY` 保证。

**参照完整性**：外键值必须引用存在的主键值，或为 NULL。通过 `FOREIGN KEY` 保证。

**用户定义完整性**：业务规则约束，如年龄 0-150、性别只能是 M/F。通过 `CHECK`、`DEFAULT`、`NOT NULL` 保证。

```sql
CREATE TABLE employee (
    id INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    age INT CHECK (age > 0 AND age < 150),
    gender CHAR(1) CHECK (gender IN ('M', 'F')),
    salary DECIMAL(10,2) DEFAULT 0,
    dept_id INT,
    FOREIGN KEY (dept_id) REFERENCES dept(id)
);
```

## ER 模型

ER（Entity-Relationship）模型是数据库概念设计的工具。用图形化方式描述实体、属性和关系，是需求 → 表结构的桥梁。

### 三个核心元素

**实体（Entity）**：现实世界中的对象。用矩形表示。
- 强实体：独立存在（如"学生"）
- 弱实体：依赖其他实体存在（如"订单明细"依赖"订单"）

**属性（Attribute）**：实体的特征。用椭圆表示。
- 简单属性：不可再分（年龄）
- 复合属性：可分解（地址 = 省 + 市 + 区）
- 派生属性：由其他属性计算得出（"年龄"可由"出生日期"导出）
- 多值属性：一个属性有多个值（一个人有多个手机号）
- 键属性：唯一标识实体（学号），用下划线标出

**关系（Relationship）**：实体间的关联。用菱形表示。
- 联系类型：1:1、1:N、M:N
- 参与约束：全部参与（双线）vs 部分参与（单线）

### ER 图转关系模式

转换规则：

1. **强实体** → 独立表，键属性 → 主键
2. **弱实体** → 独立表，主键 = 强实体主键 + 自身部分键
3. **1:1 关系** → 任选一方添加外键（加 UNIQUE 约束）
4. **1:N 关系** → 在 N 方添加外键指向 1 方主键
5. **M:N 关系** → 新建中间表，主键 = 双方主键组合
6. **多值属性** → 独立表，包含所属实体主键 + 属性值
7. **复合属性** → 拆成多个简单属性列

### 设计示例：电商订单系统

```
实体：
  User(用户)：id, name, email, phone
  Product(商品)：id, name, price, stock
  Order(订单)：id, order_no, create_time, total_amount

关系：
  User --(下)--> Order：1:N        → Order 表加 user_id 外键
  Order --(包含)--> OrderItem：1:N → OrderItem 表加 order_id 外键
  Product --(属于)--> OrderItem：1:N → OrderItem 表加 product_id 外键
```

最终表结构：

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE,
    phone VARCHAR(20)
);

CREATE TABLE product (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(200) NOT NULL,
    price DECIMAL(10,2) NOT NULL,
    stock INT DEFAULT 0
);

CREATE TABLE `order` (    -- order 是关键字，需反引号
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_no VARCHAR(32) UNIQUE NOT NULL,
    user_id BIGINT NOT NULL,
    total_amount DECIMAL(12,2) NOT NULL,
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES user(id)
);

CREATE TABLE order_item (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    unit_price DECIMAL(10,2) NOT NULL,
    FOREIGN KEY (order_id) REFERENCES `order`(id),
    FOREIGN KEY (product_id) REFERENCES product(id)
);
```

## 主键

主键（Primary Key）唯一标识表中每一行。一个表只能有一个主键，可以是单列或多列组合（复合主键）。

### 主键设计要求

1. **唯一性**：不能重复
2. **非空**：不允许 NULL
3. **不变性**：建好后不应修改
4. **尽量短**：影响索引大小和 JOIN 性能

### 主键生成策略

**自增 ID（Auto Increment）**：

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY AUTO_INCREMENT
);
```

优点：简单、有序、节省空间。适合单机。
缺点：分库分表时冲突；暴露数据量。

**UUID**：

```sql
CREATE TABLE user (
    id CHAR(36) PRIMARY KEY
);
-- Java: UUID.randomUUID().toString()
```

优点：全局唯一。
缺点：字符串占空间大；无序导致 B+Tree 页分裂；不适合作为 InnoDB 聚簇索引。

**雪花算法（Snowflake）**：

```
[1位 未使用][41位 毫秒时间戳][10位 机器ID][12位 序列号]
```

优点：全局唯一、趋势递增、性能高。
缺点：依赖机器时钟，时钟回拨需要处理。

**数据库号段**：

一次从数据库取一个号段（如 1000 个 ID），应用内分配。Leaf 框架采用此模式。

### 复合主键

```sql
-- 订单明细表，用 (order_id, product_id) 作为主键
CREATE TABLE order_item (
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT,
    PRIMARY KEY (order_id, product_id)
);
```

复合主键的列顺序影响查询效率——把查询频率高的列放前面。

## 外键

外键（Foreign Key）定义表与表之间的关系。子表的外键引用父表的主键（或唯一键）。

### 外键约束行为

```sql
CREATE TABLE emp (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    dept_id INT,
    CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id)
        REFERENCES dept(id)
        ON DELETE RESTRICT    -- 默认：父表行有子引用时禁止删除
        ON UPDATE CASCADE     -- 父表主键更新时子表外键同步更新
);
```

常见引用操作：

| 策略 | DELETE 行为 | UPDATE 行为 |
|------|------------|------------|
| RESTRICT / NO ACTION | 禁止删除父行 | 禁止更新父键 |
| CASCADE | 级联删除子行 | 级联更新外键 |
| SET NULL | 外键置 NULL | 外键置 NULL |
| SET DEFAULT | 外键置默认值 | 外键置默认值 |

### 外键的权衡

物理外键（数据库层面 FOREIGN KEY 约束）：

- 保证数据一致性，不会出现"悬空引用"
- 锁竞争——父行有未提交事务时，子行的外键检查会被阻塞
- 分库分表后无法使用

逻辑外键（应用层面维护关系，不加 FOREIGN KEY 约束）：

- 灵活，不受数据库限制
- 数据一致性靠应用保证
- 互联网公司普遍采用

实际项目中，互联网业务几乎不用物理外键。数据一致性靠事务 + 应用层校验，关系靠字段名约定（user_id、order_id）和索引保证 JOIN 性能。

## 索引基础

索引是数据库的目录——加速查找，但增加写入开销。

### 为什么需要索引

一张没有索引的表，查询时只能全表扫描（Full Table Scan）——逐行比对，O(n)。加了索引后，可以用 B+Tree 快速定位，O(log n)。

```sql
-- 没有索引
SELECT * FROM user WHERE email = 'test@example.com';
-- 全表扫描，100 万行就是 100 万次磁盘 IO

-- 加了索引
CREATE INDEX idx_email ON user(email);
-- B+Tree 查找，约 3-4 次磁盘 IO
```

### 索引类型

**主键索引**：自动创建，唯一且非空

```sql
PRIMARY KEY (id)
```

**唯一索引**：值唯一，允许一个 NULL

```sql
CREATE UNIQUE INDEX idx_email ON user(email);
```

**普通索引**：无唯一限制

```sql
CREATE INDEX idx_name ON user(name);
```

**复合索引**：多列组合

```sql
CREATE INDEX idx_dept_name ON emp(dept_id, name);
```

**全文索引**：文本搜索

```sql
CREATE FULLTEXT INDEX idx_content ON article(title, content);
```

### 索引的代价

- 占用磁盘空间（索引本身也是一棵树）
- INSERT / UPDATE / DELETE 时需要同时维护索引
- 一个表不建议超过 5-6 个索引

## 事务概念

事务是一组操作要么全部成功要么全部失败的工作单元。

银行转账是最经典的例子——A 扣钱和 B 加钱必须是一个事务：

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- 都成功
-- 或
ROLLBACK; -- 回滚
```

事务的 ACID 特性将在第 62 章《数据库事务》中详细展开，这里先建立基本概念：

- **A（Atomicity 原子性）**：要么全做，要么全不做
- **C（Consistency 一致性）**：事务前后数据满足所有约束
- **I（Isolation 隔离性）**：并发事务互不干扰
- **D（Durability 持久性）**：提交后数据不丢失

## 应用场景实战

### 场景一：博客系统数据库设计

需求：用户可以发表文章，文章可以有多个标签。

ER 分析：
- User 和 Article：1:N
- Article 和 Tag：M:N（通过中间表）

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL UNIQUE,
    nickname VARCHAR(100),
    avatar VARCHAR(255),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE article (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200) NOT NULL,
    content TEXT,
    author_id BIGINT NOT NULL,
    status TINYINT DEFAULT 0 COMMENT '0=草稿 1=已发布',
    view_count INT DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_author_id (author_id),
    INDEX idx_created_at (created_at),
    INDEX idx_status_created (status, created_at)
);

CREATE TABLE tag (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(30) NOT NULL UNIQUE
);

CREATE TABLE article_tag (
    article_id BIGINT NOT NULL,
    tag_id INT NOT NULL,
    PRIMARY KEY (article_id, tag_id),
    INDEX idx_tag_id (tag_id)
);
```

关键设计点：
- `idx_status_created` 复合索引：列表查询常用 `WHERE status=1 ORDER BY created_at`
- `updated_at` 用 `ON UPDATE CURRENT_TIMESTAMP` 自动更新时间
- M:N 中间表的主键是双方 ID 组合，同时给 tag_id 单独建索引

### 场景二：权限系统 RBAC 设计

RBAC（Role-Based Access Control）是最通用的权限模型：

```
User ──M:N── Role ──M:N── Permission
```

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL
);

CREATE TABLE role (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(30) NOT NULL UNIQUE,
    description VARCHAR(200)
);

CREATE TABLE permission (
    id INT PRIMARY KEY AUTO_INCREMENT,
    code VARCHAR(100) NOT NULL UNIQUE COMMENT '权限编码，如 user:create',
    name VARCHAR(100) NOT NULL
);

CREATE TABLE user_role (
    user_id BIGINT NOT NULL,
    role_id INT NOT NULL,
    PRIMARY KEY (user_id, role_id)
);

CREATE TABLE role_permission (
    role_id INT NOT NULL,
    permission_id INT NOT NULL,
    PRIMARY KEY (role_id, permission_id)
);
```

## 最佳实践与踩坑记录

**实践 1：命名规范**

- 表名：小写 + 下划线，单数/复数统一（个人偏好复数：users, orders）
- 字段名：小写 + 下划线，见名知意
- 主键统一用 `id`，外键用 `关联表_id`
- 索引名：`idx_表名_字段名`，唯一索引用 `uk_表名_字段名`
- 时间字段：`xxx_at`（created_at, updated_at, deleted_at）

**实践 2：字段类型选择**

- 状态字段用 TINYINT 而非 VARCHAR（占 1 字节 vs 多字节）
- 金额用 DECIMAL(18,2) 而非 FLOAT/DOUBLE（避免浮点精度问题）
- IP 地址用 INT UNSIGNED（4 字节）+ INET_ATON()/INET_NTOA()
- 定长字符串用 CHAR，变长用 VARCHAR
- 长文本（>5000 字）用 TEXT 并独立存储，主表只放概要

**实践 3：范式 vs 反范式**

```sql
-- 范式化（3NF）：无冗余，数据一致性好
-- 查询时需要 JOIN
SELECT u.name, COUNT(o.id)
FROM user u JOIN `order` o ON u.id = o.user_id
GROUP BY u.id;

-- 反范式化：冗余统计字段，牺牲一致性换查询性能
ALTER TABLE user ADD COLUMN order_count INT DEFAULT 0;
SELECT name, order_count FROM user;   -- 无需 JOIN
```

互联网系统通常混合使用：核心数据遵循 3NF，统计/展示字段适当冗余。

**踩坑 1**：自增 ID 用尽。INT 上限约 21 亿，高并发表要直接用 BIGINT。

**踩坑 2**：滥用外键。物理外键在 DDL 操作、数据迁移、分库分表时是绊脚石。生产环境用逻辑外键 + 索引。

**踩坑 3**：uuid 做主键。InnoDB 的聚簇索引按主键排序存储数据，随机 UUID 导致大量页分裂和磁盘碎片。使用自增或雪花 ID。
