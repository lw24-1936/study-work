## 概述

代码规范是团队协作的基础，统一的规范让代码可读、可维护、少 bug。

```text
代码规范的价值：
1. 可读性 —— 统一风格，易理解
2. 可维护 —— 降低维护成本
3. 少 bug —— 规范避免常见错误
4. 协作 —— 团队协作顺畅
```

## 命名规范

### Java 命名规范

```text
类名 —— 大驼峰（UserService、OrderController）
方法名 —— 小驼峰（getUserById、createOrder）
变量名 —— 小驼峰（userId、orderList）
常量 —— 全大写 + 下划线（MAX_SIZE、DEFAULT_PAGE_SIZE）
包名 —— 全小写（com.example.project）
```

### 命名原则

```text
1. 见名知意 —— 名字表达含义（userId 而非 u）
2. 不用拼音 —— 用英文（order 而非 dingdan）
3. 不用缩写 —— 完整单词（userService 而非 us）
4. 布尔用 is/has —— isActive、hasPermission
```

```java
// 好的命名
public List<Order> getPendingOrders(Long userId);

// 坏的命名
public List<Order> getData(Long u);   // 含糊
```

## 注释规范

### 注释原则

```text
1. 好的代码自解释 —— 优先写清晰的代码，而非靠注释
2. 注释解释"为什么" —— 不是"做什么"（代码已说明做什么）
3. 类和方法写文档注释 —— Javadoc
```

```java
/**
 * 订单服务
 */
public class OrderService {

    /**
     * 创建订单
     * @param userId 用户 ID
     * @return 订单
     */
    public Order create(Long userId) {
        // 为什么用 Redis 而不是数据库：高并发下扣库存要原子性
        redisTemplate.opsForValue().decrement("stock");
        // ...
    }
}
```

### 注释规范

```text
1. 类、方法写 Javadoc（/** */）
2. 复杂逻辑写行注释（解释为什么）
3. 不要写废话注释（// 设置 name）
4. 及时更新注释（改代码同步改注释）
```

## 异常规范

### 异常处理规范

```text
1. 不要吞异常 —— 捕获后要处理或抛出
2. 不要用异常控制流程 —— 异常是异常情况
3. 用具体的异常类型 —— 不用笼统的 Exception
4. 异常信息要明确 —— 便于排查
```

```java
// 坏的：吞异常
try {
    doSomething();
} catch (Exception e) {
    // 什么都不做，异常被吞
}

// 好的：处理或抛出
try {
    doSomething();
} catch (IOException e) {
    log.error("处理失败", e);   // 记录日志
    throw new BusinessException("处理失败", e);   // 包装抛出
}
```

### 业务异常

```java
// 自定义业务异常
public class BusinessException extends RuntimeException {
    private int code;
    public BusinessException(int code, String message) {
        super(message);
        this.code = code;
    }
}

// 使用
if (user == null) {
    throw new BusinessException(404, "用户不存在");
}
```

## 日志规范

### 日志规范

```text
1. 用占位符 {} —— 不用字符串拼接
2. 日志级别合理 —— debug/info/warn/error
3. 敏感信息脱敏 —— 密码、手机号
4. 异常日志带堆栈
```

```java
// 好的：占位符
log.info("用户 {} 创建订单 {}", userId, orderId);

// 坏的：字符串拼接
log.info("用户 " + userId + " 创建订单 " + orderId);

// 坏的：日志泄露敏感信息
log.info("用户登录：{}", user);   // user 含密码

// 好的：脱敏
log.info("用户登录：{}", user.getUsername());
```

### 日志级别

```text
debug —— 调试信息（开发用）
info —— 关键业务（登录、下单）
warn —— 警告（可恢复异常）
error —— 错误（异常）
```

## API 与数据库规范

### API 规范

```text
1. RESTful —— 资源 + HTTP 方法（详见 130）
2. 统一响应 —— 所有接口统一格式
3. 参数校验 —— @Valid 校验
4. 状态码正确 —— 201/204/4xx
```

### 数据库规范

```text
1. 表名 —— 小写 + 下划线（sys_user）
2. 字段名 —— 小写 + 下划线（user_id）
3. 主键 —— 自增 id 或雪花 id
4. 必备字段 —— create_time、update_time
5. 索引命名 —— idx_字段名
```

```sql
CREATE TABLE sys_user (
    id BIGINT PRIMARY KEY,
    username VARCHAR(64) NOT NULL,
    dept_id BIGINT,
    create_time DATETIME,
    update_time DATETIME,
    INDEX idx_username (username)
);
```

## Git 规范

### 分支规范

```text
main —— 主分支（生产）
develop —— 开发分支
feature/xxx —— 功能分支
bugfix/xxx —— 修复分支
hotfix/xxx —— 紧急修复
```

### Commit 规范

```text
Commit message 格式：
<type>(<scope>): <subject>

type：
feat —— 新功能
fix —— 修复
docs —— 文档
refactor —— 重构
test —— 测试
chore —— 构建/工具
```

```bash
git commit -m "feat(user): 添加用户查询接口"
git commit -m "fix(order): 修复订单超卖问题"
```

## 最佳实践与踩坑记录

### 最佳实践

1. **见名知意**。命名表达含义，不缩写。

2. **注释解释为什么**。不是复述代码。

3. **异常要处理**。不吞异常，不滥用异常。

4. **日志用占位符 + 脱敏**。性能 + 安全。

5. **Commit 语义化**。feat/fix/docs 清晰。

### 踩坑记录

**坑 1：拼音命名**

```java
public class dingdanService { ... }   // 拼音，难读
```

用英文命名。

**坑 2：吞异常**

```java
catch (Exception e) { }   // 吞异常，问题难排查
```

处理或抛出，至少记录日志。

**坑 3：日志字符串拼接**

```java
log.info("user " + name);   // 拼接，浪费性能
```

用占位符 {}。

**坑 4：日志泄露敏感信息**

```java
log.info("登录：{}", user);   // 密码泄露
```

脱敏后打印。

**坑 5：用异常控制流程**

```java
// 用异常判断业务（如用户不存在抛异常）
try {
    user = findUser(id);
} catch (UserNotFoundException e) {
    // 正常业务也用异常，性能差
}
```

正常业务用返回值判断，异常是异常情况。

**坑 6：废话注释**

```java
// 设置名字
user.setName(name);   // 注释是废话
```

注释解释为什么，不重复代码。
