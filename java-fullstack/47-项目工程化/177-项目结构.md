## 概述

项目结构是代码组织的骨架，好的结构让项目清晰、可维护、可扩展。

```text
项目结构的演进：
单模块（简单）→ 按层分包（中等）→ 多模块（复杂）→ DDD 分层（大型）
```

## 单模块 vs 多模块

### 单模块

```text
单模块：一个 Maven 模块，按包分层

适合：简单项目、微服务单个服务
```

```text
src/main/java/com/example/project/
├── controller/
├── service/
├── repository/
├── entity/
├── config/
└── common/
```

### 多模块

```text
多模块：多个 Maven 模块，按职责/领域拆分

适合：大型单体、多个服务共享代码
```

```text
优点：
1. 模块解耦 —— 各模块独立
2. 复用 —— 公共模块复用
3. 独立构建 —— 按需构建
4. 职责清晰 —— 边界明确

缺点：
1. 复杂度 —— 模块间依赖管理
2. 构建慢 —— 多模块构建
```

## Maven 多模块

### 多模块结构

```text
parent（父 POM，统一版本管理）
├── common（公共模块：工具、常量）
├── domain（领域模块：实体、接口）
├── infrastructure（基础设施：数据库、外部集成）
├── application（应用模块：业务逻辑）
└── interfaces（接口模块：Controller、API）
```

### 父 POM

```xml
<!-- parent/pom.xml -->
<groupId>com.example</groupId>
<artifactId>parent</artifactId>
<version>1.0.0</version>
<packaging>pom</packaging>

<modules>
    <module>common</module>
    <module>domain</module>
    <module>infrastructure</module>
    <module>application</module>
    <module>interfaces</module>
</modules>

<dependencyManagement>
    <!-- 统一依赖版本管理 -->
</dependencyManagement>
```

### 模块依赖

```xml
<!-- application/pom.xml：依赖 domain -->
<dependency>
    <groupId>com.example</groupId>
    <artifactId>domain</artifactId>
    <version>1.0.0</version>
</dependency>
```

```text
依赖关系：
interfaces → application → domain
                      infrastructure → domain
（依赖单向，domain 是核心，不依赖其他）
```

## DDD 分层结构

DDD 分层结构让领域层独立（详见 157-DDD）。

### 四层结构

```text
interfaces/      接口层（Controller、DTO）
application/     应用层（用例编排、事务）
domain/          领域层（核心业务，无外部依赖）
infrastructure/  基础设施层（实现领域接口）
```

```text
各层职责 + 依赖方向：
interfaces → application → domain ← infrastructure

关键：domain 是核心，不依赖任何其他层
（依赖倒置：domain 定义接口，infrastructure 实现）
```

### 分层示例

```java
// domain 层（核心，无外部依赖）
// domain/Order.java —— 领域实体
// domain/OrderRepository.java —— 仓储接口（端口）

// infrastructure 层（实现领域接口）
// infrastructure/JpaOrderRepository.java —— 实现 OrderRepository

// application 层（用例编排）
// application/OrderService.java —— 调用领域对象和仓储

// interfaces 层（接口）
// interfaces/OrderController.java —— 接收请求
```

## 模块划分实践

### 按层划分（传统）

```text
按技术层划分模块：
controller 模块、service 模块、dao 模块

缺点：跨业务改一个功能要改多个模块
```

### 按领域划分（DDD）

```text
按业务领域划分模块：
user 模块、order 模块、product 模块

优点：业务内聚，按业务独立演进
```

### 按层 + 领域结合（推荐）

```text
大型项目：
- 按领域划分顶层模块（user、order、product）
- 每个领域内按层划分（interfaces、application、domain）

中小项目：
- 单模块 + 按层分包（最简单）
```

### 选型建议

```text
1. 简单项目/微服务单服务 → 单模块按层分包
2. 大型单体 → 多模块按领域划分
3. DDD 项目 → 四层结构（interfaces/application/domain/infrastructure）
```

## 最佳实践与踩坑记录

### 最佳实践

1. **依赖单向**。上层依赖下层，领域层不依赖其他层。

2. **模块边界清晰**。每个模块职责单一。

3. **统一版本管理**。父 POM 统一依赖版本。

4. **按领域划分**。大型项目按业务领域分模块。

5. **避免循环依赖**。模块间不能循环依赖。

### 踩坑记录

**坑 1：模块循环依赖**

```text
A 模块依赖 B，B 也依赖 A，循环依赖，编译失败
```

依赖单向，用依赖倒置（接口）解耦。

**坑 2：领域层依赖框架**

```java
// domain 层依赖 Spring 注解，不纯净
@Service
public class Order { ... }
```

领域层纯 POJO，框架依赖放 infrastructure。

**坑 3：过度拆分模块**

```text
拆成几十个模块，依赖管理复杂，构建慢
```

按需拆分，简单项目单模块够用。

**坑 4：公共模块过大**

```text
common 模块什么都放，变成"垃圾堆"
```

common 只放真正的公共代码，业务代码放各自模块。

**坑 5：按层划分导致跨层修改**

```text
按层分模块（controller/service/dao 分模块），改一个功能跨多个模块
```

按领域划分（业务内聚）。

**坑 6：版本管理混乱**

```text
各模块各自声明依赖版本，版本不一致
```

父 POM 统一版本（dependencyManagement）。
