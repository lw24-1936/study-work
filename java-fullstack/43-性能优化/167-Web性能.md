## 概述

Web 性能优化关注 HTTP 请求链路，从连接、传输、缓存到响应，全面提升 Web 应用性能。

```text
Web 请求链路：
客户端 → DNS → 连接（TCP/TLS）→ 请求 → 服务器处理 → 响应 → 渲染
```

```text
Web 性能的优化方向：
1. 减少连接开销 —— Keep-Alive、连接池
2. 减少传输 —— 压缩、CDN
3. 减少请求 —— 缓存、合并
4. 减少等待 —— 异步、批量
```

## HTTP 优化

### HTTP 版本演进

```text
HTTP/1.0 —— 每请求一个连接（慢）
HTTP/1.1 —— Keep-Alive 连接复用 + 管道化
HTTP/2 —— 多路复用（一个连接并行多个请求）+ 头部压缩
HTTP/3 —— QUIC（基于 UDP，更快握手）
```

### HTTP/2 的优势

```text
1. 多路复用 —— 一个连接并发多个请求（解决队头阻塞）
2. 头部压缩 —— HPACK 压缩请求头
3. 服务器推送 —— 主动推送资源
```

```yaml
# Spring Boot 启用 HTTP/2
server:
  http2:
    enabled: true
```

## Keep-Alive 与连接池

### Keep-Alive 连接复用

```text
Keep-Alive：TCP 连接复用，避免每次请求都握手

无 Keep-Alive：每次请求都建立/断开连接（慢）
有 Keep-Alive：连接复用，省去握手开销
```

### 连接池

```text
连接池：复用连接，避免频繁创建/销毁

应用场景：
1. 数据库连接池（HikariCP）
2. HTTP 连接池（RestTemplate 的连接池）
3. Redis 连接池（Lettuce）
```

```java
// RestTemplate 连接池配置
HttpClientBuilder builder = HttpClients.custom()
    .setMaxConnTotal(100)          // 最大连接数
    .setMaxConnPerRoute(50);       // 每个路由最大连接数
```

### 连接池的价值

```text
1. 复用连接 —— 省去握手开销
2. 限制连接数 —— 防止连接耗尽
3. 提升吞吐 —— 并发请求能力
```

## CDN 加速

CDN（Content Delivery Network）把静态资源分发到就近节点，加速访问。

### CDN 的作用

```text
1. 就近访问 —— 用户访问最近的节点（快）
2. 减轻源站压力 —— 静态资源走 CDN
3. 高可用 —— 源站故障 CDN 兜底
```

### CDN 的使用

```text
1. 静态资源（图片、JS、CSS）上 CDN
2. 动态内容不缓存（或短缓存）
3. 配置缓存策略（Cache-Control）
```

```text
使用 CDN 的场景：
图片、视频、静态文件、前端资源
```

## 缓存策略

### 浏览器缓存

```text
HTTP 缓存头：
1. Cache-Control: max-age=3600 —— 缓存 1 小时
2. ETag —— 内容指纹，对比判断是否变化
3. Last-Modified —— 最后修改时间
```

```java
// Spring 设置缓存头
@GetMapping("/static")
public ResponseEntity<Resource> staticResource() {
    return ResponseEntity.ok()
        .cacheControl(CacheControl.maxAge(1, TimeUnit.HOURS))   // 缓存 1 小时
        .body(resource);
}
```

### 缓存层次

```text
1. 浏览器缓存 —— 静态资源
2. CDN 缓存 —— 静态资源
3. 应用缓存 —— Redis（热点数据）
4. 数据库缓存 —— 查询缓存
```

## Compression 压缩

压缩减少传输体积，加快响应。

### Gzip 压缩

```yaml
server:
  compression:
    enabled: true
    mime-types: application/json,text/html,text/plain
    min-response-size: 1024    # 超过 1KB 才压缩
```

### 压缩的价值

```text
JSON/文本压缩率 70-80%
1MB 的 JSON 压缩后 200-300KB，传输快 3-4 倍
```

```text
注意：
1. 压缩有 CPU 开销（权衡）
2. 图片/视频已压缩，不必再 gzip
3. 小响应不必压缩
```

## Async 与 Batch

### Async 异步

```text
异步：非关键操作异步处理，不阻塞主流程
```

```java
// 异步处理（非关键流程）
@Async
public CompletableFuture<Void> sendNotification(Long userId) {
    // 发送通知（异步，不阻塞主流程）
    notificationService.send(userId);
    return CompletableFuture.completedFuture(null);
}
```

```text
异步场景：
1. 发通知、发邮件 —— 非关键流程
2. 日志记录 —— 不阻塞业务
3. 消息推送 —— 异步处理
```

### Batch 批量

```text
批量：合并多次操作，减少往返
```

```java
// 批量插入（一次插入 1000 条，而不是逐条）
List<User> users = getUsers();
userMapper.batchInsert(users);   // 一次插入，快几十倍
```

```text
批量场景：
1. 批量插入 —— 合并 insert
2. 批量查询 —— 避免 N+1
3. 批量更新 —— 合并 update
```

## 应用场景实战

### 场景 1：接口响应优化

```text
接口慢的优化：
1. 开启 gzip 压缩（减少传输）
2. 热点数据 Redis 缓存（减少数据库查询）
3. 非关键流程异步（减少等待）
4. N+1 查询改批量（减少查询次数）
```

### 场景 2：静态资源优化

```text
1. 静态资源上 CDN
2. 设置缓存头（Cache-Control）
3. 图片压缩、懒加载
4. 开启 HTTP/2
```

## 最佳实践与踩坑记录

### 最佳实践

1. **开启 gzip 压缩**。文本/JSON 压缩率 70-80%。

2. **静态资源上 CDN**。就近访问 + 减轻源站压力。

3. **设置缓存头**。静态资源长缓存，动态内容短缓存。

4. **非关键流程异步**。发通知、日志异步处理。

5. **批量操作**。批量插入、批量查询。

### 踩坑记录

**坑 1：忽略 gzip 压缩**

```text
接口返回大 JSON，没开 gzip，传输慢
```

开启压缩（JSON/文本压缩率 70-80%）。

**坑 2：图片也 gzip**

```text
对图片 gzip 压缩，没效果还浪费 CPU（图片已压缩）
```

gzip 只用于文本/JSON，图片/视频不压缩。

**坑 3：缓存策略错误**

```text
动态接口设置长缓存，用户看到旧数据
```

动态内容短缓存或不缓存，静态资源长缓存。

**坑 4：连接池耗尽**

```text
连接池太小，高并发时连接耗尽，请求超时
```

合理设置连接池大小，监控使用率。

**坑 5：同步处理非关键操作**

```text
发邮件、记日志同步处理，阻塞主流程
```

非关键操作异步处理。

**坑 6：N+1 查询**

```text
循环里逐条查询，N 次数据库往返
```

批量查询（IN 查询）替代循环查询。
