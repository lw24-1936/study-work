## 概述

数据库是多数应用的性能瓶颈，数据库性能优化是后端性能优化的核心。

```text
数据库性能优化的层次：
1. SQL 优化 —— 优化慢查询（最直接）
2. 索引优化 —— 建立合适索引
3. 连接池优化 —— 连接复用
4. 架构优化 —— 分库分表、读写分离
```

## SQL 优化

### 避免 SELECT *

```sql
-- 慢：查询所有字段
SELECT * FROM users WHERE id = 1;

-- 快：只查需要的字段（减少传输、可用覆盖索引）
SELECT name, age FROM users WHERE id = 1;
```

### 避免隐式类型转换

```sql
-- 慢：phone 是 varchar，用数字比较导致隐式转换，索引失效
SELECT * FROM users WHERE phone = 13800138000;

-- 快：类型匹配
SELECT * FROM users WHERE phone = '13800138000';
```

### 避免函数作用于索引列

```sql
-- 慢：函数作用于索引列，索引失效
SELECT * FROM orders WHERE DATE(create_time) = '2026-01-01';

-- 快：范围查询用索引
SELECT * FROM orders WHERE create_time >= '2026-01-01' AND create_time < '2026-01-02';
```

### 避免 OR 导致索引失效

```sql
-- 慢：OR 可能导致索引失效（视情况）
SELECT * FROM users WHERE id = 1 OR name = '张三';

-- 快：用 UNION 或分开查询
SELECT * FROM users WHERE id = 1
UNION
SELECT * FROM users WHERE name = '张三';
```

### 分页优化（深分页）

```sql
-- 慢：OFFSET 大时，扫描大量行
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;

-- 快：用 id 定位（延迟关联）
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;
```

## 索引优化

### 索引设计原则

```text
1. 选择性高的列建索引（区分度大）
2. 联合索引最左前缀原则
3. 覆盖索引减少回表
4. 避免过多索引（影响写入）
```

### 联合索引最左前缀

```sql
-- 联合索引 (a, b, c)
CREATE INDEX idx_abc ON table(a, b, c);

-- 命中索引（最左前缀）
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3

-- 不命中（跳过 a）
WHERE b = 2        -- 失效
WHERE c = 3        -- 失效
WHERE b = 2 AND c = 3  -- 失效
```

### 覆盖索引

```sql
-- 覆盖索引：查询字段都在索引里，不用回表
CREATE INDEX idx_name_age ON users(name, age);

SELECT name, age FROM users WHERE name = '张三';
-- name、age 都在索引里，不用回表查数据行（快）
```

### EXPLAIN 分析执行计划

```sql
EXPLAIN SELECT * FROM users WHERE name = '张三';
```

```text
关注 EXPLAIN 的字段：
type —— 访问类型（const > eq_ref > ref > range > index > ALL）
key —— 实际使用的索引
rows —— 扫描行数
Extra —— Using index（覆盖索引）/ Using filesort（需优化）
```

## 慢 SQL 排查

### 慢查询日志

```sql
-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;   -- 超过 1 秒记录
```

### 排查流程

```text
1. 开启慢查询日志
2. 找到慢 SQL
3. EXPLAIN 分析执行计划
4. 优化（加索引、改写 SQL）
5. 验证（对比优化前后耗时）
```

## 连接池优化

### 连接池参数

```yaml
spring:
  datasource:
    hikari:           # HikariCP（默认）
      maximum-pool-size: 20        # 最大连接数
      minimum-idle: 10             # 最小空闲连接
      connection-timeout: 30000    # 获取连接超时
      idle-timeout: 600000         # 空闲超时
```

### 连接池优化原则

```text
1. 合理设置最大连接数 —— 太大数据库扛不住，太小请求排队
2. 连接复用 —— 避免频繁创建/销毁连接
3. 监控连接池 —— 关注等待、超时
```

```text
最大连接数经验值：
连接数 ≈ 数据库最大连接数 / 应用实例数
（如 MySQL 200，4 个实例 → 每实例 50）
```

## 分库分表与读写分离

### 读写分离

```text
主库（写）→ 同步 → 从库（读）

写操作 → 主库
读操作 → 从库（读多写少场景，分担压力）
```

### 分库分表

```text
数据量大到单库单表扛不住时：

垂直分库 —— 按业务分库（用户库、订单库）
垂直分表 —— 按字段分表（热点字段拆分）
水平分库 —— 按规则分库（userId 取模）
水平分表 —— 按规则分表（订单表拆成 N 张）
```

```text
分库分表工具：ShardingSphere、MyCat
```

### 分库分表的问题

```text
1. 跨库 join —— 拆分成多次查询
2. 分布式事务 —— 用最终一致性
3. 全局 ID —— 用分布式 ID（雪花算法）
4. 分页 —— 合并排序
```

## 应用场景实战

### 场景 1：慢 SQL 优化

```sql
-- 优化前（全表扫描）
SELECT * FROM orders WHERE user_id = 123 AND status = 'PAID';
-- 无索引，扫描 100 万行

-- 优化后（建联合索引）
CREATE INDEX idx_user_status ON orders(user_id, status);
-- 走索引，扫描几十行，快几百倍
```

### 场景 2：深分页优化

```sql
-- 优化前：OFFSET 100000，慢
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;

-- 优化后：id 定位
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;
```

## 最佳实践与踩坑记录

### 最佳实践

1. **先 EXPLAIN 再优化**。分析执行计划，定位问题。

2. **选择性高的列建索引**。区分度大的字段。

3. **联合索引注意最左前缀**。字段顺序很重要。

4. **避免索引列做运算**。函数、隐式转换导致索引失效。

5. **读多写少用读写分离**。分担主库压力。

### 踩坑记录

**坑 1：索引列使用函数**

```sql
WHERE DATE(create_time) = '2026-01-01'   -- 索引失效
```

用范围查询替代函数。

**坑 2：隐式类型转换**

```sql
WHERE phone = 13800138000   -- phone 是 varchar，隐式转换，索引失效
```

保持类型一致。

**坑 3：索引过多**

```text
每个表十几个索引，写入慢（每次写都要维护索引）
```

只建必要的索引（按查询场景）。

**坑 4：忽略连接池**

```text
连接池太小，请求排队超时；太大，数据库连接耗尽
```

合理设置，监控连接池。

**坑 5：深分页性能差**

```text
LIMIT 100000, 20 扫描大量行
```

用 id 定位（延迟关联）。

**坑 6：分库分表后 join 失败**

```text
分库后跨库 join 无法执行，SQL 报错
```

拆分查询，或用数据冗余避免跨库 join。
