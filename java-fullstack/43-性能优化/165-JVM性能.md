## 概述

JVM 性能优化是通过调整内存分配和 GC 策略，让应用运行更快、更稳定。

```text
JVM 性能优化的目标：
1. 减少 GC 停顿 —— 降低延迟
2. 提升吞吐 —— 单位时间处理更多请求
3. 避免 OOM —— 保证稳定性
```

```text
优化思路：
1. 先监控（GC 日志、jstat、jmap）
2. 分析瓶颈（GC 频繁？内存泄漏？）
3. 调整参数（堆大小、GC 选择）
```

## JVM 内存结构

### 运行时内存区域

```text
JVM 内存结构：
1. 堆（Heap）—— 对象实例（GC 管理）
2. 栈（Stack）—— 方法调用、局部变量（线程私有）
3. 方法区（Method Area）—— 类信息、常量
4. 程序计数器（PC）—— 指令位置
5. 本地方法栈 —— native 方法
```

### JDK 8 前后对比

```text
JDK 8 之前：方法区 = 永久代（PermGen）
JDK 8 之后：方法区 = 元空间（Metaspace，本地内存）

Metaspace 好处：不再有 PermGen OOM，动态扩展
```

## Heap 堆

堆是 GC 管理的主要区域，分新生代和老年代。

### 堆的结构

```text
堆（Heap）
├── 新生代（Young Generation）
│   ├── Eden（伊甸园）—— 对象诞生地
│   ├── Survivor 0（S0）
│   └── Survivor 1（S1）
└── 老年代（Old Generation）—— 长期存活对象
```

### 对象分配流程

```text
1. 新对象 → Eden
2. Eden 满 → Minor GC，存活对象 → Survivor
3. 对象在 Survivor 间多次复制，年龄增长
4. 年龄达到阈值（默认 15）→ 老年代
5. 老年代满 → Major GC / Full GC
```

### 堆大小参数

```bash
-Xms2g    # 初始堆大小（建议 = Xmx，避免扩容）
-Xmx2g    # 最大堆大小
-Xmn1g    # 新生代大小
-XX:SurvivorRatio=8   # Eden:S0:S1 = 8:1:1
```

## Stack 栈与 Metaspace

### Stack 栈

```text
栈（线程私有）：
1. 每个线程一个栈
2. 栈帧 —— 方法调用的局部变量、操作数栈
3. StackOverflowError —— 栈深度超限（递归过深）
```

```bash
-Xss512k   # 线程栈大小（默认 1M）
```

### Metaspace 元空间

```text
元空间（本地内存）：
1. 存储类元数据、方法信息
2. JDK 8 后替代永久代
3. OOM: Metaspace —— 类加载过多
```

```bash
-XX:MaxMetaspaceSize=512m   # 元空间上限
```

## GC 垃圾回收优化

### GC 算法

```text
1. 标记-清除（Mark-Sweep）—— 有碎片
2. 标记-复制（Mark-Copy）—— 新生代用（快，浪费空间）
3. 标记-整理（Mark-Compact）—— 老年代用（无碎片，慢）
```

### 常见 GC 收集器

| 收集器 | 特点 | 适用 |
|--------|------|------|
| Serial | 单线程，STW | 小应用 |
| Parallel | 多线程，高吞吐 | 批处理 |
| CMS | 低延迟（已废弃） | - |
| G1 | 区域化，可预测停顿 | 大堆（默认） |
| ZGC | 极低延迟 | 大堆低延迟 |

### GC 选择

```bash
# JDK 8：大堆用 G1
-XX:+UseG1GC

# JDK 11+：默认 G1
# JDK 15+：低延迟用 ZGC
-XX:+UseZGC
```

### GC 优化思路

```text
1. 减少对象创建 —— 复用对象、避免装箱
2. 减少大对象 —— 大对象直接进老年代（-XX:PretenureSizeThreshold）
3. 调大新生代 —— 减少 Minor GC 频率
4. 选择合适的 GC —— 低延迟 G1/ZGC，高吞吐 Parallel
```

## JIT 编译与逃逸分析

### JIT 编译

```text
JIT（Just-In-Time）编译器：
1. 热点代码（频繁执行）编译成机器码
2. 比解释执行快几十倍
3. C1（Client）/ C2（Server）编译器
```

```text
热点检测：方法调用次数 + 循环回边次数
超过阈值触发 JIT 编译
```

### 逃逸分析

```text
逃逸分析：分析对象是否逃出方法
1. 不逃逸 → 栈上分配（不用 GC）
2. 不逃逸 → 标量替换（拆成基本类型）
3. 线程内 → 锁消除
```

```java
public void test() {
    // 对象不逃逸，可能栈上分配（优化）
    User user = new User();
    user.setName("张三");
    // user 只在本方法使用，不逃逸，JIT 可能优化掉堆分配
}
```

### JIT 的优化

```text
1. 内联 —— 小方法内联到调用处
2. 逃逸分析 —— 栈上分配、锁消除
3. 标量替换 —— 对象拆成基本类型
4. 死代码消除 —— 删除无用代码
```

## JVM 参数调优

### 常用参数

```bash
# 堆内存
-Xms2g -Xmx2g

# 新生代
-Xmn1g

# 元空间
-XX:MaxMetaspaceSize=512m

# GC 选择
-XX:+UseG1GC

# GC 日志
-Xlog:gc*:gc.log

# OOM 时导出堆
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/tmp/heapdump.hprof
```

### 生产环境推荐配置

```bash
# 常见 Java 应用（4G 内存）
-Xms2g -Xmx2g \
-XX:MaxMetaspaceSize=512m \
-XX:+UseG1GC \
-XX:MaxGCPauseMillis=200 \
-XX:+HeapDumpOnOutOfMemoryError \
-XX:HeapDumpPath=/tmp/heapdump.hprof \
-Xlog:gc*:gc.log
```

## 应用场景实战

### 场景 1：GC 频繁排查

```text
现象：GC 频繁，CPU 高，响应慢

排查：
1. jstat -gcutil 查看 GC 频率
2. 分析 GC 日志（Full GC 频繁说明堆不够）
3. 定位对象创建热点（jmap + MAT）

优化：
1. 调大堆内存
2. 减少对象创建
3. 换 GC（CMS → G1）
```

### 场景 2：内存泄漏排查

```text
现象：内存持续增长，最终 OOM

排查：
1. -XX:+HeapDumpOnOutOfMemoryError 导出堆
2. MAT 分析（大对象、泄漏对象）
3. 定位泄漏源（集合未清理、监听器未移除）

优化：
1. 修复泄漏
2. 集合及时清理
3. 弱引用（WeakReference）
```

### 场景 3：jstat 监控 GC

```bash
# 每 1 秒输出 GC 情况
jstat -gcutil <pid> 1000

# 输出：S0 S1 E O M YGC YGCT FGC FGCT
# 关注：E（Eden 使用率）、O（老年代使用率）、FGC（Full GC 次数）
```

## 最佳实践与踩坑记录

### 最佳实践

1. **-Xms 和 -Xmx 相同**。避免堆动态扩容的开销。

2. **大堆用 G1**。JDK 9+ 默认，可预测停顿。

3. **开启 GC 日志**。生产环境必开，便于排查。

4. **开启 HeapDump**。OOM 时导出堆，事后分析。

5. **先监控再调优**。用 jstat/jmap/GC 日志定位问题。

### 踩坑记录

**坑 1：堆设置过大或过小**

```text
堆过大 —— 单次 GC 停顿长
堆过小 —— GC 频繁，吞吐低
```

根据应用内存需求合理设置（监控后调整）。

**坑 2：忽略 Metaspace**

```text
动态生成类多（反射、动态代理），Metaspace OOM
```

设置 -XX:MaxMetaspaceSize，或排查类加载泄漏。

**坑 3：盲目换 GC**

```text
不分析就换 ZGC，可能更糟（ZGC 适合大堆低延迟）
```

根据场景选 GC：高吞吐 Parallel，低延迟 G1/ZGC。

**坑 4：对象创建过多**

```text
循环里频繁 new 对象，GC 压力大
```

复用对象、避免装箱、懒加载。

**坑 5：大对象直接进老年代**

```text
大对象（大数组、大字符串）直接进老年代，频繁 Full GC
```

控制对象大小，或 -XX:PretenureSizeThreshold 调整。

**坑 6：不监控就调优**

```text
凭感觉调 JVM 参数，可能更差
```

先监控（GC 日志、jstat），用数据说话。
