## 概述

API 设计是定义接口规范，好的 API 设计让接口清晰、一致、易用、可维护。

```text
好的 API 设计标准：
1. 一致性 —— 命名、格式、风格统一
2. 可预测 —— 遵循 REST 规范，行为可预期
3. 简洁 —— URI 简洁，不冗余
4. 文档清晰 —— 配合 OpenAPI 文档
```

## REST 设计原则

REST（Representational State Transfer）是 API 设计的架构风格。

### REST 的核心约束

```text
1. 资源导向 —— 一切皆资源（用户、订单、商品）
2. 无状态 —— 请求之间无会话状态
3. 统一接口 —— 用 HTTP 方法操作资源
4. 表述性 —— 资源有多种表示（JSON、XML）
```

### RESTful 设计

```text
资源用名词（复数），操作用 HTTP 方法：

GET    /api/users        —— 获取用户列表
GET    /api/users/1      —— 获取单个用户
POST   /api/users        —— 创建用户
PUT    /api/users/1      —— 更新用户（全量）
PATCH  /api/users/1      —— 更新用户（部分）
DELETE /api/users/1      —— 删除用户
```

### 好的 vs 坏的 API 设计

```text
坏的设计（动词导向）：
POST /api/getUser
POST /api/deleteUser
POST /api/updateUser

好的设计（资源导向）：
GET    /api/users/1
DELETE /api/users/1
PUT    /api/users/1
```

## URI 设计规范

### 命名规范

```text
1. 用小写字母 —— /api/users（不用 /api/Users）
2. 用连字符 —— /api/user-profiles（不用 /api/user_profiles）
3. 资源用复数名词 —— /api/users（不用 /api/user）
4. 层级表示关系 —— /api/users/1/orders
5. 不用文件扩展名 —— /api/users（不用 /api/users.json）
```

### 层级关系

```text
父资源/子资源：
GET /api/users/1/orders        —— 用户 1 的订单
GET /api/orders/1/items        —— 订单 1 的明细
```

```text
层级不宜过深（最多 2-3 层）：
/api/users/1/orders/1/items/1/payments  —— 太深，难维护
```

### 过滤、分页用查询参数

```text
GET /api/users?status=active        —— 过滤
GET /api/users?page=1&size=20       —— 分页
GET /api/users?sort=age,desc        —— 排序
```

## HTTP Method 使用

### 方法语义

| 方法 | 语义 | 幂等 | 安全 |
|------|------|------|------|
| GET | 查询 | 是 | 是 |
| POST | 创建 | 否 | 否 |
| PUT | 全量更新 | 是 | 否 |
| PATCH | 部分更新 | 否 | 否 |
| DELETE | 删除 | 是 | 否 |

```text
幂等：多次执行结果一致（GET/PUT/DELETE）
安全：不修改资源（只有 GET）
```

### PUT vs PATCH

```text
PUT —— 全量更新（替换整个资源）
PATCH —— 部分更新（只更新提供的字段）

PUT /api/users/1
{ "name": "张三", "age": 20, "email": "a@b.com" }   // 完整数据

PATCH /api/users/1
{ "age": 21 }   // 只更新年龄
```

### 方法使用错误示例

```text
错误：
GET  /api/users/delete?id=1    —— GET 用于删除（违反语义）
POST /api/users/1              —— POST 用于更新

正确：
DELETE /api/users/1
PUT   /api/users/1
```

## 状态码使用

### 常用状态码

| 状态码 | 含义 | 场景 |
|--------|------|------|
| 200 | OK | 查询/更新成功 |
| 201 | Created | 创建成功 |
| 204 | No Content | 删除成功（无响应体） |
| 400 | Bad Request | 参数错误 |
| 401 | Unauthorized | 未认证 |
| 403 | Forbidden | 无权限 |
| 404 | Not Found | 资源不存在 |
| 409 | Conflict | 资源冲突 |
| 422 | Unprocessable | 语义错误 |
| 500 | Internal Error | 服务器错误 |
| 503 | Service Unavailable | 服务不可用 |

### 状态码的正确使用

```java
@PostMapping("/users")
@ResponseStatus(HttpStatus.CREATED)   // 201 创建成功
public User create(@RequestBody User user) { ... }

@DeleteMapping("/users/{id}")
@ResponseStatus(HttpStatus.NO_CONTENT)  // 204 删除成功
public void delete(@PathVariable Long id) { ... }
```

```text
常见错误：
1. 一切成功都返回 200（创建应 201，删除应 204）
2. 业务错误返回 200 + 错误码（应 4xx）
3. 未找到返回 500（应 404）
```

## JSON 响应格式

### 统一响应体

```json
{
  "code": 0,           // 0 成功，非 0 失败
  "message": "成功",
  "data": { ... }      // 业务数据
}
```

```java
// 统一响应类
public class ApiResponse<T> {
    private int code;        // 0 成功，非 0 错误码
    private String message;  // 提示信息
    private T data;          // 数据

    public static <T> ApiResponse<T> success(T data) {
        return new ApiResponse<>(0, "成功", data);
    }

    public static <T> ApiResponse<T> error(int code, String message) {
        return new ApiResponse<>(code, message, null);
    }
}
```

### 命名规范

```text
JSON 字段用 camelCase：
{ "userId": 1, "createdAt": "2026-01-01" }

不用 snake_case：
{ "user_id": 1, "created_at": "2026-01-01" }
```

### 空值处理

```text
1. null 字段 —— 保留（明确表示无值）或省略（减少体积）
2. 空数组 —— 返回 []（不是 null）
3. 空对象 —— 返回 {}（不是 null）
```

```java
// Jackson 配置：不序列化 null
objectMapper.setSerializationInclusion(JsonInclude.Include.NON_NULL);
```

## 分页、排序、过滤

### 分页（Pagination）

```text
分页参数：
page —— 页码（从 1 或 0 开始）
size —— 每页大小
```

```text
GET /api/users?page=1&size=20
```

```json
// 分页响应格式
{
  "code": 0,
  "data": {
    "list": [ ... ],        // 当前页数据
    "total": 100,           // 总条数
    "page": 1,              // 当前页
    "size": 20,             // 每页大小
    "totalPages": 5         // 总页数
  }
}
```

### 排序（Sorting）

```text
排序参数：sort=字段,方向

GET /api/users?sort=age,desc
GET /api/users?sort=name,asc&sort=age,desc   // 多字段排序
```

### 过滤（Filtering）

```text
过滤参数：字段=值

GET /api/users?status=active
GET /api/users?age_gte=18&age_lte=30    // 范围过滤
GET /api/products?category=手机&price_lte=5000
```

### 常见操作符

```text
_eq  —— 等于（默认）
_ne  —— 不等于
_gt  —— 大于
_gte —— 大于等于
_lt  —— 小于
_lte —— 小于等于
_like —— 模糊
_in  —— 在列表中
```

## 应用场景实战

### 场景 1：完整的 RESTful API 设计

```text
用户资源：
GET    /api/users               # 列表（分页/排序/过滤）
GET    /api/users/{id}          # 详情
POST   /api/users               # 创建
PUT    /api/users/{id}          # 更新
DELETE /api/users/{id}          # 删除

订单资源（嵌套）：
GET    /api/users/{id}/orders   # 用户的订单
POST   /api/users/{id}/orders   # 创建订单
```

### 场景 2：统一响应 + 状态码

```java
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping
    public ApiResponse<Page<User>> list(
            @RequestParam(defaultValue = "1") int page,
            @RequestParam(defaultValue = "20") int size,
            @RequestParam(required = false) String status) {
        Page<User> result = userService.list(page, size, status);
        return ApiResponse.success(result);
    }

    @GetMapping("/{id}")
    public ApiResponse<User> get(@PathVariable Long id) {
        return ApiResponse.success(userService.get(id));
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public ApiResponse<User> create(@Valid @RequestBody UserDTO dto) {
        return ApiResponse.success(userService.create(dto));
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. **资源用复数名词，操作用 HTTP 方法**。`GET /api/users` 而非 `POST /api/getUsers`。

2. **统一响应格式**。所有接口用统一的 ApiResponse 结构。

3. **正确使用状态码**。创建 201、删除 204、错误 4xx。

4. **分页参数统一**。page/size，响应含 total。

5. **版本管理**。`/api/v1/users`，避免破坏性变更。

### 踩坑记录

**坑 1：GET 请求带 body**

```text
GET 请求带 body，很多网关、代理不支持，body 可能被丢弃
```

查询参数用 query string，不用 body。

**坑 2：URI 用动词**

```text
/api/getUser、/api/deleteUser —— 动词导向，不符合 REST
```

用资源 + HTTP 方法：`GET /api/users/1`、`DELETE /api/users/1`。

**坑 3：状态码滥用 200**

```text
错误也返回 200 + code 字段，客户端无法用 HTTP 状态码判断
```

业务错误用 4xx，配合 code 字段说明具体错误。

**坑 4：分页参数不统一**

```text
有的接口 page/size，有的 offset/limit，客户端适配困难
```

统一分页参数（page/size），响应统一（list/total）。

**坑 5：返回 null 而不是空数组**

```json
{ "list": null }    // 应该返回 []
```

空列表返回 []，空对象返回 {}，不要返回 null。

**坑 6：URI 大小写不一致**

```text
/api/Users 和 /api/users 是两个不同的接口，混乱
```

URI 统一小写，用连字符分隔。
