## 概述

企业级设计模式是解决企业应用（高并发、分布式、持久化）常见问题的模式，比 GoF 23 种模式更贴近实际业务。

```text
企业级模式的来源：
Martin Fowler 的《企业应用架构模式》
（Patterns of Enterprise Application Architecture）
```

```text
企业级模式分类：
1. 事务模式 —— 事务边界、并发控制
2. 持久化模式 —— 数据访问、对象映射
3. 缓存模式 —— 缓存策略
4. 消息模式 —— 异步、可靠传输
5. 领域模式 —— 领域逻辑组织
```

## 事务模式

### 事务脚本（Transaction Script）

```text
事务脚本：一个方法处理一个业务操作（简单直接）
适合：简单业务
```

```java
@Service
public class OrderService {
    @Transactional
    public void createOrder(OrderDTO dto) {
        // 一个事务方法完成整个业务
        orderMapper.insert(dto);
        stockMapper.decrease(dto);
        // ...
    }
}
```

### 领域模型（Domain Model）

```text
领域模型：业务逻辑在领域对象里（复杂业务，配合 DDD）
```

```java
public class Order {
    private List<OrderItem> items;

    public void addItem(Product product, int quantity) {
        // 业务逻辑在领域对象里
        items.add(new OrderItem(product, quantity));
    }
}
```

### 事务脚本 vs 领域模型

| 维度 | 事务脚本 | 领域模型 |
|------|---------|---------|
| 复杂度 | 简单 | 复杂 |
| 业务逻辑位置 | Service | 领域对象 |
| 适用 | 简单 CRUD | 复杂业务（DDD） |

## 持久化模式

### Repository（仓储）

```text
Repository：数据访问的抽象，隔离领域和持久化
```

```java
// Repository 接口（领域层定义）
public interface OrderRepository {
    Order save(Order order);
    Optional<Order> findById(Long id);
}

// 实现（基础设施层）
@Repository
public class JpaOrderRepository implements OrderRepository {
    @Autowired
    private JpaOrderDao dao;
    // ...
}
```

### DAO（Data Access Object）

```text
DAO：数据访问对象，封装数据库操作
```

```java
@Repository
public class OrderDao {
    @Autowired
    private JdbcTemplate jdbcTemplate;

    public Order findById(Long id) {
        return jdbcTemplate.queryForObject("SELECT * FROM orders WHERE id = ?", Order.class, id);
    }
}
```

### Repository vs DAO

```text
DAO —— 面向数据表（技术导向，简单 CRUD）
Repository —— 面向领域（领域导向，聚合存取）

简单项目用 DAO/MyBatis，DDD 项目用 Repository
```

### 工作单元（Unit of Work）

```text
工作单元：跟踪对象变更，事务提交时统一持久化
```

```java
// JPA 的 EntityManager 就是工作单元
// 对象修改后，事务提交时自动 flush 到数据库
@Transactional
public void updateUser(Long id) {
    User user = entityManager.find(User.class, id);
    user.setName("新名字");   // 修改，提交时自动更新（工作单元跟踪变更）
}
```

## Factory 与 Specification 模式

### Factory 工厂模式

工厂模式在领域建模中封装复杂对象的创建（详见 160-创建型设计模式）。

```java
// 领域工厂：封装复杂聚合的创建
public class OrderFactory {
    public Order createOrder(User user, List<CartItem> items) {
        Order order = new Order(user.getId());
        for (CartItem item : items) {
            order.addItem(item.getProduct(), item.getQuantity());
        }
        order.calculateTotal();
        return order;
    }
}
```

```text
领域工厂的价值：
1. 封装复杂创建逻辑 —— 聚合创建可能涉及多个步骤
2. 保证聚合一致性 —— 创建时就满足不变量
3. 隔离创建细节 —— 客户端不用关心创建过程
```

### Specification 规格模式

Specification 把业务规则封装成可组合的对象，用于查询和校验。

```java
// 规格接口
public interface Specification<T> {
    boolean isSatisfiedBy(T t);
    Specification<T> and(Specification<T> other);
    Specification<T> or(Specification<T> other);
}

// 具体规格：VIP 用户
public class VipSpecification implements Specification<User> {
    public boolean isSatisfiedBy(User user) {
        return user.getLevel() >= 3;
    }
}

// 组合规格：VIP 且活跃
Specification<User> vipAndActive =
    new VipSpecification().and(new ActiveSpecification());
```

```text
Specification 的价值：
1. 业务规则复用 —— 规则独立封装，可组合
2. 查询过滤 —— 灵活组合查询条件
3. 校验 —— 业务规则校验
（Spring Data JPA 的 Specification 就是这种模式）
```

## 依赖注入

依赖注入（DI）是企业级应用的核心，把依赖的创建和管理交给容器（详见 71-Spring基础）。

```java
// 构造器注入（推荐）
@Service
public class OrderService {
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
```

```text
依赖注入的价值：
1. 解耦 —— 依赖接口不依赖实现
2. 可测试 —— 便于 mock 依赖
3. 生命周期管理 —— 容器管理 Bean

依赖倒置原则（DIP）：
高层模块不依赖低层模块，都依赖抽象（配合 DI 实现）
```

## 缓存模式

### 缓存模式类型（详见 105-分布式缓存）

```text
1. Cache Aside（旁路缓存）—— 最常用
2. Read Through —— 读时缓存自动加载
3. Write Through —— 写时同步更新缓存
4. Write Behind —— 写时异步更新缓存
```

### Cache Aside（旁路缓存）

```java
public User getUser(Long id) {
    // 1. 查缓存
    User user = redis.get("user:" + id);
    if (user != null) return user;

    // 2. 缓存未命中，查数据库
    user = userMapper.selectById(id);

    // 3. 写入缓存
    redis.set("user:" + id, user);
    return user;
}
```

## 消息模式

### 消息模式类型（详见 22-SpringMessaging）

```text
1. 点对点 —— 一条消息一个消费者
2. 发布-订阅 —— 一条消息多个消费者
3. 可靠传输 —— 消息不丢失（确认、重试、死信）
```

### 事务性发件箱（Outbox）

```text
Outbox 模式：业务和消息写同一个事务，保证一致性
（详见 102-分布式事务）
```

```java
@Transactional
public void createOrder(Order order) {
    orderMapper.insert(order);
    // 同一事务写 outbox 表
    outboxMapper.insert(new OutboxEvent("OrderCreated", order));
}

// 后台任务读取 outbox，发送消息
```

## 领域模式

### 领域模式类型（详见 157-DDD）

```text
1. 实体（Entity）—— 有标识的对象
2. 值对象（Value Object）—— 无标识、不可变
3. 聚合（Aggregate）—— 一致性边界
4. 领域服务（Domain Service）—— 跨聚合逻辑
5. 领域事件（Domain Event）—— 领域事实
```

### 分层架构

```text
表现层 → 应用层 → 领域层 → 基础设施层

领域层是核心，不依赖其他层
```

## 企业级模式总结

| 模式 | 用途 | 场景 |
|------|------|------|
| 事务脚本 | 简单业务 | CRUD |
| 领域模型 | 复杂业务 | DDD |
| Repository | 领域数据访问 | DDD |
| DAO | 数据访问 | 简单项目 |
| 工作单元 | 变更跟踪 | JPA |
| Cache Aside | 缓存 | 最常用 |
| Outbox | 消息一致性 | 分布式事务 |

```text
使用建议：
1. 简单项目 —— 事务脚本 + DAO + Cache Aside
2. 复杂项目 —— 领域模型 + Repository + DDD
3. 分布式 —— Outbox + 消息 + 缓存模式
```

## 最佳实践与踩坑记录

### 最佳实践

1. **简单用事务脚本，复杂用领域模型**。不滥用 DDD。

2. **缓存用 Cache Aside**。最常用，简单可靠。

3. **消息一致性用 Outbox**。避免分布式事务。

4. **数据访问用 Repository 隔离**。领域不依赖具体持久化。

### 踩坑记录

**坑 1：简单业务过度设计**

```text
简单 CRUD 也用领域模型 + DDD，复杂度高收益低
```

简单用事务脚本，复杂才用领域模型。

**坑 2：缓存和数据库不一致**

```text
Cache Aside 更新时只删缓存不更新，或更新顺序错误
```

先更新数据库，再删缓存（详见 21-SpringCache）。

**坑 3：消息和业务不一致**

```text
业务成功但消息没发出去（或反过来），数据不一致
```

用 Outbox 模式（业务和消息同事务）。

**坑 4：Repository 泄漏技术细节**

```java
public interface OrderRepository {
    List<Order> findByStatusAndType(String status, String type);
    // 技术细节泄漏到领域层
}
```

Repository 面向领域，不暴露技术细节。
