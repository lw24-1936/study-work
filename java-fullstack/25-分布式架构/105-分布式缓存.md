## 概述

分布式缓存是部署在多台机器上的缓存系统，提供高性能、高可用、可扩展的缓存能力。

```text
为什么需要分布式缓存：
1. 单机缓存容量有限 —— 内存有上限
2. 单机缓存不可靠 —— 单点故障数据丢失
3. 分布式缓存可水平扩展 —— 加机器扩容
4. 高可用 —— 主从、集群保证不宕机
```

```text
典型方案：
Redis —— 最主流（本文以 Redis 为例）
Memcached —— 简单 KV 缓存
```

## 缓存架构演进

Redis 的分布式架构从简单到复杂演进：

```text
单机 → 主从复制 → 哨兵 Sentinel → Cluster 集群
```

### 1. 单机模式

```text
单机 Redis：一个实例
优点：简单
缺点：单点故障、容量有限
```

### 2. 主从复制

```text
一主多从：主写从读
解决：读性能、数据备份
未解决：主节点单点（写）、故障自动切换
```

### 3. Sentinel 哨兵

```text
主从 + 哨兵：哨兵监控主从，自动故障转移
解决：主节点故障自动切换
未解决：容量（单主写）、水平扩展
```

### 4. Cluster 集群

```text
分片集群：多主多从，数据分片
解决：水平扩展、容量、高可用
```

```text
演进总结：
单机（简单）→ 主从（读扩展）→ 哨兵（高可用）→ 集群（全面扩展）
```

## 主从复制

### 主从架构

```text
        主节点（Master）—— 写操作
       /          \
      /            \
   从节点1        从节点2 —— 读操作
   (数据副本)     (数据副本)
```

### 主从复制流程

```text
1. 从节点连接主节点，发送 SYNC/PSYNC
2. 主节点执行 RDB 快照，发送给从节点
3. 从节点加载快照，追平数据
4. 之后主节点的写命令实时同步到从节点
```

### 主从配置

```bash
# 从节点配置
redis.conf:
  replicaof 192.168.1.1 6379   # 指定主节点
```

```yaml
# Spring Boot 主从配置
spring:
  data:
    redis:
      master:
        host: 192.168.1.1
        port: 6379
      slave:
        host: 192.168.1.2
        port: 6379
```

### 主从复制的局限

```text
1. 主节点单点 —— 写操作都到主节点
2. 无自动故障转移 —— 主挂了要手动切换
3. 复制延迟 —— 从节点数据可能滞后
4. 异步复制 —— 可能丢数据
```

## Sentinel 哨兵

Sentinel 是 Redis 的高可用方案，监控主从节点并自动故障转移。

### Sentinel 架构

```text
        Sentinel 集群（哨兵）
        ┌────┐ ┌────┐ ┌────┐
        │哨兵1│ │哨兵2│ │哨兵3│
        └────┘ └────┘ └────┘
           │      │      │
           └──────┴──────┘（监控）
                  │
         ┌────────┴────────┐
         │  主节点（Master）│
         └────────┬────────┘
              ┌───┴───┐
          从节点1   从节点2
```

### Sentinel 的核心功能

```text
1. 监控 —— 周期性检查主从节点是否正常
2. 通知 —— 节点故障时通知管理员
3. 自动故障转移 —— 主节点故障，自动选举新主
4. 配置提供 —— 客户端通过 Sentinel 获取主节点地址
```

### 故障转移流程

```text
1. Sentinel 发现主节点下线（主观下线 → 客观下线）
2. Sentinel 选举 Leader（Raft 算法）
3. Leader 从从节点中选举新主节点
4. 其他从节点切换到新主节点
5. 通知客户端新主节点地址
```

### Sentinel 配置

```properties
# sentinel.conf
sentinel monitor mymaster 192.168.1.1 6379 2   # 监控主节点，2 个哨兵同意才判定下线
sentinel down-after-milliseconds mymaster 30000  # 30 秒无响应判定下线
sentinel failover-timeout mymaster 180000         # 故障转移超时
```

### Sentinel 的局限

```text
1. 单主写 —— 写性能受限于单节点
2. 无法水平扩展 —— 数据全量复制，容量受限
3. 客户端要感知切换 —— 需要哨兵客户端
```

## Redis Cluster 集群

Redis Cluster 是 Redis 官方的分布式方案，数据分片 + 主从高可用。

### Cluster 架构

```text
Redis Cluster：16384 个槽（slot），数据按槽分布

        主节点A（槽 0-5460）
        ├── 从节点A1
        主节点B（槽 5461-10922）
        ├── 从节点B1
        主节点C（槽 10923-16383）
        ├── 从节点C1
```

### 数据分片

```text
分片规则：
slot = CRC16(key) % 16384

每个 key 通过哈希映射到 16384 个槽之一，
槽分布在不同主节点上。
```

```text
key 与槽的关系：
1. 普通 key：整个 key 哈希
2. 带 hash tag 的 key：只哈希 {tag} 部分
   user:{1001}:name → 只哈希 1001
```

### Cluster 的特点

```text
1. 水平扩展 —— 加节点自动迁移槽
2. 高可用 —— 主从自动故障转移
3. 去中心化 —— 节点间 gossip 通信，无中心节点
4. 客户端重定向 —— MOVED/ASK 重定向
```

### Cluster 配置

```yaml
spring:
  data:
    redis:
      cluster:
        nodes:
          - 192.168.1.1:6379
          - 192.168.1.2:6379
          - 192.168.1.3:6379
        max-redirects: 3
```

### Cluster 的限制

```text
1. 多 key 操作限制 —— 跨槽的多 key 操作不支持（mget、mset）
2. 事务限制 —— 跨槽的事务不支持
3. 需要 hash tag —— 多 key 要同槽，用 hash tag
```

### 三种架构对比

| 维度 | 主从 | Sentinel | Cluster |
|------|------|----------|---------|
| 写能力 | 单点 | 单点 | 多主（分片） |
| 读能力 | 多从 | 多从 | 多主多从 |
| 故障转移 | 手动 | 自动 | 自动 |
| 水平扩展 | 否 | 否 | 是 |
| 复杂度 | 低 | 中 | 高 |
| 数据量 | 单机内存 | 单机内存 | 分片总和 |
| 适用 | 小规模 | 中规模 | 大规模 |

## 一致性 Hash

一致性 Hash 是分布式缓存（和负载均衡）的核心数据分布算法。

### 普通哈希的问题

```text
普通哈希：hash(key) % N（N 为节点数）

问题：节点增减时，大量 key 重新映射（缓存雪崩）

例：3 个节点 hash(key) % 3
加一个节点 → hash(key) % 4
大部分 key 的映射结果改变，缓存大面积失效
```

### 一致性 Hash 原理

```text
1. 将哈希空间组织成一个环（0 ~ 2^32-1）
2. 节点和 key 都哈希到环上的位置
3. key 沿环顺时针找到第一个节点，就是该 key 的归属节点
```

```text
        0
        │
  节点A ●
       / \
      /   \
  ●key1  ●key2
    /       \
   ●节点C   ●节点B
        │
      2^32-1

key1 顺时针找到节点 C → key1 归属节点 C
key2 顺时针找到节点 B → key2 归属节点 B
```

### 节点增减的影响

```text
增加节点 D（在 A 和 C 之间）：
只有 A 到 D 之间的 key 需要重新映射到 D，
其他 key 不受影响（影响范围小）
```

```text
对比：
普通哈希：节点增减影响大部分 key
一致性哈希：只影响相邻节点间的 key（约 1/N）
```

### 虚拟节点

```text
问题：节点少时，哈希分布不均匀（数据倾斜）

解决：虚拟节点
每个真实节点对应多个虚拟节点，分散在环上，
key 映射到虚拟节点，再对应到真实节点。
```

```java
// 一致性哈希实现（含虚拟节点）
public class ConsistentHash {
    private final SortedMap<Integer, String> ring = new TreeMap<>();
    private final int virtualNodes;   // 每个真实节点的虚拟节点数

    public ConsistentHash(int virtualNodes) {
        this.virtualNodes = virtualNodes;
    }

    public void addNode(String node) {
        for (int i = 0; i < virtualNodes; i++) {
            int hash = hash(node + "#" + i);
            ring.put(hash, node);
        }
    }

    public String getNode(String key) {
        if (ring.isEmpty()) return null;
        int hash = hash(key);
        // 顺时针找到第一个节点
        SortedMap<Integer, String> tailMap = ring.tailMap(hash);
        int nodeHash = tailMap.isEmpty() ? ring.firstKey() : tailMap.firstKey();
        return ring.get(nodeHash);
    }

    private int hash(String key) {
        // 使用 MurmurHash 等均匀哈希
        return key.hashCode();
    }
}
```

## 缓存读写模式

缓存的读写模式决定缓存和数据库如何协作。

### 1. Cache Aside（旁路缓存，最常用）

```text
读：
1. 先读缓存，命中返回
2. 未命中读数据库
3. 写回缓存

写：
1. 先更新数据库
2. 再删除缓存（不是更新缓存）
```

```java
// Cache Aside 实现
public User getUser(Long id) {
    // 1. 读缓存
    String key = "user:" + id;
    User cached = cache.get(key);
    if (cached != null) return cached;

    // 2. 读数据库
    User user = userMapper.findById(id);

    // 3. 写缓存
    if (user != null) {
        cache.set(key, user, 30 * 60);
    }
    return user;
}

public void updateUser(User user) {
    // 1. 更新数据库
    userMapper.update(user);
    // 2. 删除缓存
    cache.delete("user:" + user.getId());
}
```

```text
为什么写时删缓存而不是更新缓存：
1. 更新缓存可能写脏数据（并发写）
2. 删缓存简单，下次读时重建
3. 缓存可能不是简单映射（涉及计算）
```

### 2. Read Through（读穿透）

```text
读：
缓存层自动加载数据库数据（缓存未命中时，缓存层负责查库）

与 Cache Aside 的区别：
Cache Aside 应用层负责查库写缓存，
Read Through 缓存层（CacheProvider）负责查库写缓存
```

```java
// Read Through：缓存层封装加载逻辑
public class ReadThroughCache {
    public User get(Long id) {
        // 缓存层自动加载（应用不感知数据库）
        return cache.get(id, () -> userMapper.findById(id));
    }
}
```

### 3. Write Through（写穿透）

```text
写：
应用写缓存，缓存层同步写数据库

特点：
1. 应用只和缓存交互，不直接操作数据库
2. 写缓存和写数据库同步完成
```

```java
public void saveUser(User user) {
    // 写缓存（缓存层同步写数据库）
    cache.put(user.getId(), user, () -> userMapper.update(user));
}
```

### 4. Write Behind（写回，异步）

```text
写：
应用写缓存，缓存层异步批量写数据库

特点：
1. 写入性能高（异步）
2. 数据可能丢失（异步未刷盘就宕机）
```

### 四种模式对比

| 模式 | 读流程 | 写流程 | 复杂度 | 一致性 |
|------|--------|--------|--------|--------|
| Cache Aside | 应用查库写缓存 | 应用更新库删缓存 | 低 | 最终一致 |
| Read Through | 缓存层查库 | - | 中 | 强一致 |
| Write Through | - | 缓存层同步写库 | 中 | 强一致 |
| Write Behind | - | 缓存层异步写库 | 高 | 弱一致（可能丢） |

```text
选型建议：
大多数项目用 Cache Aside（简单、可控）
需要强一致的读用 Read Through
需要高性能写用 Write Behind（配合持久化）
```

public class ShardedCache {

    private final ConsistentHash consistentHash;

    public ShardedCache() {
        consistentHash = new ConsistentHash(100);  // 每个节点 100 个虚拟节点
        // 添加缓存节点
        consistentHash.addNode("cache-1");

### 场景 3：Cache Aside 完整实现

```java
@Service
public class ProductCacheService {

    @Autowired
    private StringRedisTemplate redisTemplate;

    public Product getProduct(Long id) {
        String key = "product:" + id;

        // 1. 读缓存
        String json = redisTemplate.opsForValue().get(key);
        if (json != null) {
            return JSON.parseObject(json, Product.class);
        }

        // 2. 读数据库
        Product product = productMapper.findById(id);

        // 3. 写缓存（加随机过期时间防雪崩）
        if (product != null) {
            long ttl = 30 * 60 + new Random().nextInt(5 * 60);
            redisTemplate.opsForValue().set(key, JSON.toJSONString(product), ttl, TimeUnit.SECONDS);
        }
        return product;
    }

    public void updateProduct(Product product) {
        // 1. 先更新数据库
        productMapper.update(product);
        // 2. 再删除缓存
        redisTemplate.delete("product:" + product.getId());
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. **写时删缓存（Cache Aside），不更新缓存**。避免并发写脏数据。

2. **缓存过期时间加随机值**。防止批量 key 同时过期导致雪崩。

3. **大 key 拆分**。单个 key 过大影响性能，拆成多个小 key 或 Hash。

4. **多 key 操作注意 hash tag**。Cluster 模式下，跨槽的多 key 操作会失败。

5. **一致性哈希用虚拟节点**。节点少时避免数据倾斜。

### 踩坑记录

**坑 1：先删缓存再更新库导致脏数据**

```java
// 错误顺序
cache.delete(key);          // 1. 先删缓存
userMapper.update(user);    // 2. 再更新库
// 中间有请求读到旧数据，写回缓存，造成脏数据
```

正确：先更新数据库，再删缓存。

**坑 2：Cluster 模式跨槽操作失败**

```java
// Cluster 模式下，mget 多个 key 跨槽会报错
List<String> values = redisTemplate.opsForValue().multiGet(Arrays.asList("key1", "key2", "key3"));
// 如果 key1、key2、key3 在不同槽，报 CROSSSLOT error
```

多 key 操作要用 hash tag 保证同槽，或逐个操作。

**坑 3：主从复制延迟导致读旧数据**

```java
// 写入主节点后，立即从从节点读，读到旧数据（复制延迟）
redisTemplate.opsForValue().set("key", "new");
String value = slaveRedisTemplate.opsForValue().get("key");  // 可能读到旧值
```

对一致性敏感的场景，写后强制读主节点。

**坑 4：一致性哈希节点少导致倾斜**

```text
3 个节点直接哈希到环上，分布不均匀，
某个节点承担过多 key（数据倾斜）
```

用虚拟节点（每个真实节点多个虚拟节点）均匀分布。

**坑 5：缓存穿透导致数据库压力**

```java
// 查询不存在的 key，每次都穿透缓存查数据库
public User getUser(Long id) {
    User user = cache.get("user:" + id);
    if (user != null) return user;
    return userMapper.findById(id);   // 不存在的 id 每次都查库
}
```

缓存空值或用布隆过滤器防止穿透。

**坑 6：缓存和数据库双写不一致**

```text
更新数据库成功，删除缓存失败（网络抖动），
导致缓存和数据库长期不一致
```

删除缓存失败要重试，或用延迟双删、订阅 binlog 同步。
