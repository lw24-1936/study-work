## 概述

高并发是指系统在同一时间处理大量请求的能力。高并发系统设计的核心是：在保证系统稳定性的前提下，尽可能提高吞吐量、降低响应时间。

```text
高并发系统的目标：
1. 高吞吐 —— 单位时间处理尽可能多的请求
2. 低延迟 —— 单个请求快速响应
3. 稳定性 —— 流量高峰不崩溃
```

```text
高并发系统的典型场景：
- 电商大促（双十一秒杀）
- 抢票系统（12306）
- 秒杀活动
- 直播打赏
- 热点新闻（微博热搜）
```

## 高并发核心指标

理解并区分这些指标是高并发设计的基础。

### QPS（Queries Per Second）

```text
QPS：每秒查询数，每秒处理的请求数量。

计算：QPS = 总请求数 / 时间（秒）

例：10 万个请求在 100 秒内完成，QPS = 1000
```

### TPS（Transactions Per Second）

```text
TPS：每秒事务数，每秒完成的事务数量（一个事务可能包含多个请求）。

区别：QPS 关注请求，TPS 关注业务事务
例：一个下单事务 = 创建订单 + 扣库存 + 扣款（3 个请求，1 个事务）
```

### 并发量

```text
并发量：同一时刻正在处理的请求数量。

与 QPS 的关系：
QPS = 并发量 / 平均响应时间

例：并发量 100，平均响应时间 0.1 秒，QPS = 1000
```

### 响应时间（RT）

```text
响应时间：从请求发出到收到响应的时间。

组成：
响应时间 = 网络传输 + 服务处理 + 排队等待

关注指标：
- 平均响应时间（均值，受极端值影响）
- 百分位响应时间（P99、P95，更真实）
```

```text
P99 = 99% 的请求响应时间低于该值
例：P99 = 500ms，表示 99% 的请求在 500ms 内完成
```

### 吞吐量（Throughput）

```text
吞吐量：单位时间处理的数据量或请求数。

吞吐量 ≈ QPS（请求数维度）
吞吐量 = 每秒处理的数据量（数据维度，如 MB/s）
```

### 指标关系

```text
核心关系：
QPS = 并发量 / 平均响应时间
吞吐量 = QPS（请求维度）

优化方向：
1. 提高 QPS → 提高并发量 或 降低响应时间
2. 降低响应时间 → 缓存、异步、优化算法
3. 提高并发量 → 加机器、异步化（释放线程）
```

### 常见量级

```text
普通系统：QPS 几十 ~ 几百
中型系统：QPS 几百 ~ 几千
大型系统：QPS 几万 ~ 几十万
顶级系统（双十一）：QPS 百万级
```

## 限流

限流是保护系统的第一道防线，控制进入系统的请求速率。

### 四种限流算法

**1. 计数器（固定窗口）**

```text
原理：固定时间窗口内计数，超过阈值拒绝
问题：窗口临界点突发（如 0.9s 和 1.1s 之间突破阈值）
```

```java
// 简单计数器限流
public class CounterLimiter {
    private long windowStart = System.currentTimeMillis();
    private int count = 0;
    private final int limit = 100;
    private final long windowMs = 1000;

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        if (now - windowStart > windowMs) {
            windowStart = now;   // 新窗口
            count = 0;
        }
        if (count >= limit) {
            return false;
        }
        count++;
        return true;
    }
}
```

**2. 滑动窗口**

```text
原理：将时间窗口细分为多个小窗口，滑动统计
解决：计数器算法的临界突发问题
```

```java
// 滑动窗口（用 Redis ZSet 实现）
public boolean tryAcquire(String key, int limit, long windowMs) {
    long now = System.currentTimeMillis();
    long windowStart = now - windowMs;

    // 删除窗口外的记录
    redisTemplate.opsForZSet().removeRangeByScore(key, 0, windowStart);

    // 统计窗口内的请求数
    Long count = redisTemplate.opsForZSet().zCard(key);
    if (count >= limit) {
        return false;
    }

    // 记录当前请求
    redisTemplate.opsForZSet().add(key, UUID.randomUUID().toString(), now);
    redisTemplate.expire(key, windowMs, TimeUnit.MILLISECONDS);
    return true;
}
```

**3. 漏桶（Leaky Bucket）**

```text
原理：请求进入漏桶，以固定速率流出（处理）
特点：平滑输出速率，突发请求被"缓存"在桶里
问题：桶满则溢出（拒绝），无法应对突发流量
```

```java
// 漏桶算法
public class LeakyBucket {
    private final int capacity;      // 桶容量
    private final int rate;          // 流出速率（每秒）
    private int water = 0;           // 当前水量
    private long lastLeakTime = System.currentTimeMillis();

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        // 漏水（按速率流出）
        int leaked = (int) ((now - lastLeakTime) / 1000.0 * rate);
        if (leaked > 0) {
            water = Math.max(0, water - leaked);
            lastLeakTime = now;
        }
        // 加水
        if (water >= capacity) {
            return false;   // 桶满，拒绝
        }
        water++;
        return true;
    }
}
```

**4. 令牌桶（Token Bucket）**

```text
原理：以固定速率生成令牌，请求需拿到令牌才能处理
特点：允许一定程度的突发（桶里的令牌可以积累）
对比漏桶：漏桶控制输出速率，令牌桶控制输入速率
```

```java
// 令牌桶算法
public class TokenBucket {
    private final int capacity;      // 桶容量（令牌数）
    private final int rate;          // 生成速率（每秒）
    private double tokens;           // 当前令牌数
    private long lastRefillTime = System.currentTimeMillis();

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        // 补充令牌
        double refill = (now - lastRefillTime) / 1000.0 * rate;
        tokens = Math.min(capacity, tokens + refill);
        lastRefillTime = now;

        // 取令牌
        if (tokens < 1) {
            return false;
        }
        tokens--;
        return true;
    }
}
```

### 限流算法对比

| 算法 | 平滑度 | 突发处理 | 复杂度 | 适用场景 |
|------|--------|---------|--------|---------|
| 计数器 | 差（临界突发） | 不支持 | 低 | 简单场景 |
| 滑动窗口 | 好 | 部分支持 | 中 | 精确限流 |
| 漏桶 | 好（恒定速率） | 不支持 | 低 | 恒定速率输出 |
| 令牌桶 | 好 | 支持（可积累） | 低 | 通用（推荐） |

### 限流的实现层次

```text
1. 网关层限流 —— 入口限流（Gateway/Sentinel）
2. 服务层限流 —— 接口限流（Sentinel/Resilience4j）
3. 应用层限流 —— 业务限流（如验证码、防刷）
```

## 熔断与降级

熔断和降级是高并发系统的"保护机制"。

### 熔断（Circuit Breaker）

```text
熔断：下游服务故障时，直接快速失败，不再调用故障服务
（详细内容见 98-服务容错）
```

### 降级（Fallback）

```text
降级：系统压力大或部分功能故障时，关闭非核心功能，保证核心功能可用
```

```text
降级策略：
1. 关闭非核心功能 —— 推荐、评论、日志
2. 返回默认值/缓存 —— 列表返回空、详情返回缓存
3. 功能降级 —— 实时推荐降级为热门推荐
4. 页面降级 —— 完整页面降级为静态页
```

### 熔断 vs 降级 vs 限流

| 手段 | 触发条件 | 目的 |
|------|---------|------|
| 限流 | 流量超阈值 | 控制入口流量 |
| 熔断 | 下游故障 | 快速失败，防止扩散 |
| 降级 | 系统压力大 | 牺牲非核心，保核心 |

## 排队削峰

排队削峰用消息队列缓冲流量，把瞬时高峰"削平"为持续处理。

### 削峰原理

```text
瞬时流量高峰（如秒杀）：
直接打到后端 → 后端崩溃

引入消息队列：
请求 → 消息队列（缓冲）→ 后端按能力消费
```

```text
流量         直接处理（后端崩溃）
  ████
  ████  → 后端处理能力上限 ──────
  ████
  ████

流量         队列削峰（平滑处理）
  ████
  ████  → 队列缓冲 → 后端匀速消费 ──────
  ████
  ████
```

### 削峰实现

```java
// 秒杀请求进入消息队列，后端匀速消费
@Service
public class SeckillService {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    // 接收秒杀请求，写入队列（快速返回）
    public Result submitSeckill(Long userId, Long productId) {
        // 先限流/校验，然后入队
        SeckillRequest request = new SeckillRequest(userId, productId);
        rabbitTemplate.convertAndSend("seckill.queue", request);
        return Result.success("排队中");   // 快速返回，不阻塞
    }
}

// 消费者匀速处理
@Component
public class SeckillConsumer {
    @RabbitListener(queues = "seckill.queue", concurrency = "10")  // 10 个消费者匀速处理
    public void handle(SeckillRequest request) {
        seckillService.doSeckill(request);
    }
}
```

## 异步化

异步化是提高并发能力的关键手段，把耗时操作从主流程中剥离。

### 同步 vs 异步

```text
同步：请求 → 处理（含耗时操作）→ 返回（线程被占用）
异步：请求 → 快速返回 → 耗时操作后台执行（线程释放）
```

```java
// 同步：注册时同步发邮件（阻塞 3 秒）
public User register(User user) {
    userMapper.insert(user);
    emailService.send(user.getEmail());   // 阻塞 3 秒
    return user;   // 3 秒后才返回
}

// 异步：注册快速返回，邮件异步发送
public User register(User user) {
    userMapper.insert(user);
    // 异步发邮件
    emailProducer.sendAsync(user.getEmail());
    return user;   // 立即返回
}
```

### 异步化的手段

```text
1. 线程池 —— @Async 异步方法
2. 消息队列 —— 削峰 + 异步解耦
3. 响应式编程 —— WebFlux 非阻塞
4. CompletableFuture —— 异步编排
```

```java
// @Async 异步
@Service
public class EmailService {
    @Async
    public void sendEmail(String to) {
        // 异步执行，不阻塞主线程
        mailSender.send(to);
    }
}
```

```java
// CompletableFuture 异步编排
public OrderDetail getDetail(Long orderId) {
    CompletableFuture<Order> orderFuture = CompletableFuture.supplyAsync(() -> orderMapper.find(orderId));
    CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> userClient.getUser(orderId));
    CompletableFuture<List<Item>> itemsFuture = CompletableFuture.supplyAsync(() -> itemMapper.findByOrder(orderId));

    // 三个异步并行，全部完成后再组装
    return CompletableFuture.allOf(orderFuture, userFuture, itemsFuture)
        .thenApply(v -> new OrderDetail(orderFuture.join(), userFuture.join(), itemsFuture.join()))
        .join();
}
```

### 异步化的注意事项

```text
1. 线程池配置 —— 异步需要线程池，默认线程池可能不够用
2. 事务边界 —— 异步方法不在原事务中（事务上下文不传递）
3. 上下文传递 —— ThreadLocal（用户信息、traceId）不传递
4. 异常处理 —— 异步异常要捕获，否则静默丢失
```

## 高并发系统设计思路

### 分层优化

```text
客户端层：CDN、缓存、减少请求
网关层：限流、鉴权、负载均衡
服务层：缓存、异步、池化、降级
数据层：分库分表、读写分离、缓存
```

### 经典优化手段

```text
1. 缓存 —— 减少数据库压力（Redis）
2. 异步 —— 释放线程（消息队列）
3. 限流 —— 控制流量（令牌桶）
4. 熔断降级 —— 保护系统（Sentinel）
5. 池化 —— 复用资源（连接池、线程池）
6. 分库分表 —— 数据层扩展
7. 读写分离 —— 数据库负载均衡
8. 无状态化 —— 便于水平扩展
```

## 应用场景实战

### 场景 1：秒杀系统设计

```text
秒杀系统的完整方案：
1. 前端：按钮防重复、验证码
2. 网关：限流（令牌桶）、防刷
3. 服务：Redis 预扣库存（原子操作）
4. 队列：削峰，异步下单
5. 数据库：最终一致性
```

```java
@Service
public class SeckillService {

    @Autowired
    private StringRedisTemplate redisTemplate;

    // Redis 原子扣库存（高性能，避免数据库压力）
    public Result seckill(Long productId, Long userId) {
        String stockKey = "seckill:stock:" + productId;

        // 原子扣减库存（Lua 脚本）
        Long stock = redisTemplate.opsForValue().decrement(stockKey);
        if (stock < 0) {
            // 库存不足，回滚
            redisTemplate.opsForValue().increment(stockKey);
            return Result.error("已抢完");
        }

        // 入队异步下单
        rabbitTemplate.convertAndSend("seckill.order.queue", new SeckillOrder(userId, productId));
        return Result.success("抢购成功，处理中");
    }
}
```

public class RateLimiter {

## 最佳实践与踩坑记录

### 最佳实践

1. **限流在入口做**。网关层统一限流，服务层精细限流。

2. **异步化要有线程池隔离**。不同业务用不同线程池，防止相互影响。

3. **削峰用消息队列**。消息队列天然支持削峰，配合消费速率控制。

4. **关注 P99 而不是平均值**。平均值被极端值污染，P99 更能反映真实体验。

5. **降级要提前预案**。大促前明确降级方案，而不是故障时临时决定。

### 踩坑记录

**坑 1：计数器限流的临界突发**

```java
// 固定窗口计数器：0.9s~1.0s 和 1.0s~1.1s 两个窗口，
// 各放行 limit 个请求，实际 0.2 秒内放了 2*limit 个请求
```

用滑动窗口或令牌桶解决临界突发问题。

**坑 2：异步丢失上下文**

```java
@Async
public void sendNotification() {
    // 获取不到当前用户（ThreadLocal 不传递）
    String userId = SecurityContextHolder.getContext().getAuthentication().getName();
    // userId 为 null！
}
```

异步方法要用参数传递上下文，或用专用线程池传递 ThreadLocal。

**坑 3：异步方法的事务失效**

```java
@Async
@Transactional
public void updateAsync() {
    // 异步方法在新线程，事务上下文不传递，@Transactional 不生效
}
```

异步 + 事务的组合要谨慎，事务不跨线程。

**坑 4：消息队列削峰后消费积压**

```text
削峰把压力转移到队列，但消费者处理能力不足，
消息在队列堆积，延迟越来越长
```

消费者要有足够的并发处理能力，或动态扩容消费者。

**坑 5：QPS 指标理解错误**

```text
混淆 QPS 和 TPS：一个下单事务可能包含多个请求，
TPS 和 QPS 不是一回事
```

明确业务关注的是 QPS 还是 TPS，压测时要区分。

**坑 6：只优化单点，忽略全链路**

```text
只优化了应用层，但数据库、网络、网关仍是瓶颈，
整体 QPS 上不去
```

高并发是全链路优化，找到真正的瓶颈（压测定位）。
