## 概述

高可用（High Availability，HA）是指系统在部分组件故障时，仍能持续提供服务的能力。

```text
高可用的目标：
减少系统不可用时间，保证服务持续可用

核心思想：
1. 冗余 —— 关键组件有备份（主从、集群）
2. 故障转移 —— 故障时自动切换到备份
3. 快速恢复 —— 故障后快速恢复服务
```

```text
高可用 vs 高并发：
高可用 —— 关注"不宕机"（可靠性）
高并发 —— 关注"扛流量"（性能）
两者常结合：既要扛得住流量，又要保证不宕机
```

## 高可用衡量指标

### 可用性百分比

```text
可用性 = 正常运行时间 / 总时间

99%     —— 每年宕机 3.65 天
99.9%   —— 每年宕机 8.76 小时（3 个 9）
99.99%  —— 每年宕机 52.6 分钟（4 个 9）
99.999% —— 每年宕机 5.26 分钟（5 个 9）
```

### 常见可用性等级

| 等级 | 可用性 | 年宕机时间 | 说明 |
|------|--------|-----------|------|
| 2 个 9 | 99% | 3.65 天 | 基础 |
| 3 个 9 | 99.9% | 8.76 小时 | 常见业务 |
| 4 个 9 | 99.99% | 52.6 分钟 | 高要求 |
| 5 个 9 | 99.999% | 5.26 分钟 | 金融核心 |

### MTBF / MTTR

```text
MTBF（Mean Time Between Failures）—— 平均无故障时间
MTTR（Mean Time To Repair）—— 平均修复时间

可用性 = MTBF / (MTBF + MTTR)

提高可用性：
1. 提高 MTBF（减少故障）—— 提高组件质量
2. 降低 MTTR（快速恢复）—— 自动化故障转移
```

## 主从复制

主从复制是最基础的冗余方案，一个主节点 + 多个从节点。

### 主从架构

```text
        主节点（Master）—— 处理写操作
       /     |     \
      /      |      \
   从节点1  从节点2  从节点3 —— 复制主节点数据，处理读操作
```

```text
工作方式：
1. 写操作 → 主节点
2. 主节点将数据同步到从节点
3. 读操作 → 从节点（读写分离）
4. 主节点故障 → 从节点升级为主（故障转移）
```

### 主从复制的类型

```text
同步复制：主节点等从节点确认后才返回（强一致，性能差）
异步复制：主节点不等从节点确认（性能好，可能丢数据）
半同步复制：至少一个从节点确认（折中）
```

### 主从的优缺点

```text
优点：
1. 读写分离 —— 读压力分摊到从节点
2. 数据备份 —— 从节点是天然备份
3. 故障转移 —— 主挂从升

缺点：
1. 主节点仍是单点（写操作）
2. 复制延迟 —— 从节点数据可能滞后
3. 主从切换可能丢数据（异步复制）
```

## 集群

集群是主从的扩展，多节点协同工作，提供更高的可用性和扩展性。

### 集群架构

```text
集群 = 多个节点组成，共同提供服务

类型：
1. 主从集群 —— 一主多从（MySQL 主从、Redis 主从）
2. 对称集群 —— 节点平等，无主从（部分 NoSQL）
3. 分片集群 —— 数据分片，多主多从（Redis Cluster、MongoDB 分片）
```

### 集群的关键问题

```text
1. 数据分布 —— 数据如何分布到各节点（一致性哈希、分片）
2. 节点协调 —— 节点间如何协同（选举、共识）
3. 故障检测 —— 如何发现节点故障（心跳）
4. 数据一致性 —— 多副本如何一致（Raft、Paxos）
```

### 集群 vs 主从

| 维度 | 主从 | 集群 |
|------|------|------|
| 写能力 | 单点（主） | 多节点（分片） |
| 扩展性 | 只读扩展 | 读写都扩展 |
| 复杂度 | 低 | 高 |
| 数据分布 | 全量复制 | 分片分布 |
| 典型 | MySQL 主从 | Redis Cluster、Kafka |

## 故障转移 Failover

故障转移（Failover）是系统自动检测故障并切换到备用节点的能力。

### 故障转移流程

```text
1. 故障检测 —— 心跳检测发现主节点故障
2. 主从切换 —— 从节点中选举新主节点
3. 流量切换 —— 客户端/负载均衡切换到新主节点
4. 服务恢复 —— 系统恢复正常服务
```

### 自动 vs 手动故障转移

```text
自动故障转移：
- 监控系统检测故障 → 自动切换
- 优点：恢复快（秒级/分钟级）
- 缺点：误判风险（网络抖动导致误切换）

手动故障转移：
- 人工确认故障后手动切换
- 优点：可控、避免误判
- 缺点：恢复慢（依赖人工）
```

### 常见故障转移方案

| 组件 | 故障转移方案 |
|------|-------------|
| MySQL | MHA、MGR、Orchestrator |
| Redis | Sentinel 自动切换 |
| Nginx | Keepalived VIP 漂移 |
| 微服务 | 注册中心剔除 + 负载均衡 |
| Kafka | ISR 副本选举 |

## 容错机制

高可用的容错机制（部分已在 98-服务容错讲过，这里聚焦高可用视角）。

### 重试

```text
重试：瞬时故障（网络抖动、超时）时自动重试

注意：
1. 重试次数限制（3 次左右）
2. 重试间隔（退避策略，避免雪崩）
3. 幂等（重试可能重复执行）
4. 只对幂等操作重试
```

### 超时

```text
超时：限制请求等待时间，防止无限等待

注意：
1. 超时时间合理（太短误判，太长占用资源）
2. 全链路超时协调（上游超时 > 下游超时）
```

### 熔断

```text
熔断：故障累积后快速失败（见 98-服务容错）
```

### 降级

```text
降级：压力大时牺牲非核心功能（见 103-高并发）
```

### 容错机制的组合

```text
完整容错链：
超时（限制等待）→ 重试（瞬时故障）→ 熔断（持续故障）→ 降级（兜底）
```

## 健康检查

健康检查是高可用的基础，系统通过健康检查发现故障。

### 健康检查类型

```text
1. 存活检查（Liveness）—— 进程是否存活
   - 进程存在、端口通、心跳正常

2. 就绪检查（Readiness）—— 是否可服务
   - 依赖可用（数据库、缓存连接正常）

3. 深度健康检查 —— 业务级检查
   - 实际执行一个查询，验证业务可用
```

### Spring Boot 健康检查

```java
@Component
public class DatabaseHealthIndicator implements HealthIndicator {
    @Override
    public Health health() {
        try {
            // 检查数据库连接
            jdbcTemplate.queryForObject("SELECT 1", Integer.class);
            return Health.up().build();
        } catch (Exception e) {
            return Health.down().withDetail("error", e.getMessage()).build();
        }
    }
}
```

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true   # 启用存活/就绪探针
```

```text
Kubernetes 使用健康检查：
livenessProbe  —— 存活探针（失败则重启容器）
readinessProbe —— 就绪探针（失败则摘除流量）
```

### 健康检查的应用

```text
1. 负载均衡 —— 健康检查失败，摘除实例
2. 注册中心 —— 心跳失败，剔除服务
3. 容器编排 —— 探针失败，重启/摘流量
4. 监控告警 —— 健康检查失败，触发告警
```

## 高可用架构设计

### 分层冗余

```text
接入层：Nginx + Keepalived（VIP 漂移）
网关层：多实例 + 负载均衡
服务层：多实例 + 注册中心
数据层：主从/集群 + 故障转移
```

### 无状态化

```text
无状态服务：不保存会话数据，便于水平扩展和故障转移
会话数据放外部（Redis/Session 共享）

有状态服务（数据库）：
用主从/集群保证高可用
```

### 异地多活

```text
异地多活：多个机房同时提供服务
- 同城双活：同城市两个机房
- 两地三中心：异地灾备

这是高可用的最高级形态，成本高，仅核心系统采用
```

### 高可用设计原则

```text
1. 冗余 —— 关键组件至少 2 个（消除单点）
2. 自动故障转移 —— 故障自动切换，不依赖人工
3. 健康检查 —— 及时发现故障
4. 快速恢复 —— MTTR 最小化
5. 容错设计 —— 超时/重试/熔断/降级
6. 无状态化 —— 便于水平扩展
```

## 应用场景实战

### 场景 1：MySQL 高可用（主从 + 故障转移）

```text
架构：
主库（写）←→ 从库1（读）←→ 从库2（读）
    ↑
   MHA/Orchestrator（监控 + 自动故障转移）

主库故障：
1. 监控发现主库心跳失败
2. 自动选举新主库（从库中选）
3. 应用切换到新主库
4. 从库重新同步
```

```yaml
# 应用读写分离配置
spring:
  datasource:
    # 写库
    master:
      url: jdbc:mysql://master:3306/db
    # 读库
    slave:
      url: jdbc:mysql://slave:3306/db
```

### 场景 2：服务高可用（多实例 + 健康检查）

```yaml
# 服务多实例部署
# 实例 1：192.168.1.1:8080
# 实例 2：192.168.1.2:8080
# 实例 3：192.168.1.3:8080

management:
  endpoint:
    health:
      show-details: always
  endpoints:
    web:
      exposure:
        include: health
```

```text
高可用保障：
1. 3 个实例注册到 Nacos
2. 健康检查失败，Nacos 剔除故障实例
3. 负载均衡自动切换到健康实例
4. 故障实例恢复后重新注册
```

### 场景 3：Nginx + Keepalived 高可用

```text
        VIP（虚拟 IP）
           │
    ┌──────┴──────┐
    │  Nginx 主   │ ←→ │  Nginx 备   │
    │ (Keepalived)│    │ (Keepalived)│
    └──────┬──────┘    └──────┬──────┘
           │                  │
       后端服务集群
```

```text
Keepalived 原理：
1. 主 Nginx 持有 VIP
2. 主 Nginx 故障，VIP 漂移到备 Nginx
3. 流量自动切到备 Nginx
```

## 最佳实践与踩坑记录

### 最佳实践

1. **消除单点**。所有关键组件至少 2 个，没有单点故障。

2. **健康检查要"真"检查**。不只检查进程存活，要检查依赖（数据库、缓存）是否可用。

3. **故障转移要演练**。定期演练主从切换，验证切换流程。

4. **超时和重试配合**。超时控制等待，重试应对瞬时故障，两者结合。

5. **监控告警完善**。故障要能及时发现（监控）和通知（告警）。

### 踩坑记录

**坑 1：主从复制延迟导致数据不一致**

```text
写入主库后，立即从从库读取，可能读到旧数据（复制延迟）
```

写入后强制读主库，或容忍短暂不一致。

**坑 2：异步复制丢数据**

```text
主库宕机，未同步到从库的数据丢失（异步复制）
```

关键数据用半同步复制，或接受少量数据丢失（配合对账）。

**坑 3：故障转移误判**

```text
网络抖动导致心跳超时，误判主库故障，触发切换
切换后又发现主库正常，出现双主（脑裂）
```

故障转移要有仲裁机制（多数派），避免脑裂。

**坑 4：健康检查过于简单**

```java
// 只检查进程存活，不检查依赖
// 数据库连接池耗尽，但进程还在，健康检查误判为"健康"
return Health.up().build();   // 永远返回健康，没意义
```

健康检查要检查依赖（数据库、缓存、消息队列）。

**坑 5：重试导致雪崩**

```text
下游故障，大量请求重试，放大流量，导致雪崩
```

重试要有退避策略（指数退避）+ 熔断配合。

**坑 6：单点组件没有冗余**

```text
Nacos、网关、配置中心等基础设施单点部署，
故障时整个系统不可用
```

基础设施（注册中心、网关、配置中心）也要集群部署。
