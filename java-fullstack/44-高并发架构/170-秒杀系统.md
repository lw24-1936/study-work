## 概述

秒杀系统是高并发场景的集大成者，融合了限流、缓存、消息队列、分布式锁、防超卖等技术。

```text
秒杀的特点：
1. 瞬时高并发 —— 开抢瞬间流量是平时的几十倍
2. 读多写少 —— 大量查询，少量下单
3. 库存有限 —— 库存少，竞争激烈
4. 不能超卖 —— 卖出的不能超过库存
```

## 秒杀的挑战

```text
秒杀的核心挑战：
1. 流量洪峰 —— 瞬时流量击垮系统
2. 库存竞争 —— 并发扣库存导致超卖
3. 刷子 —— 恶意刷单、脚本抢购
4. 重复提交 —— 用户重复下单
```

```text
秒杀的技术方案：
流量削峰 + Redis 缓存 + MQ 异步 + 限流 + 分布式锁 + 防超卖
```

## 流量削峰

流量削峰是秒杀的第一道防线，把瞬时流量打散。

### 削峰手段

```text
1. 限流 —— 网关层限制请求量
2. 排队 —— 请求入队列，按能力处理
3. 预约/秒杀令牌 —— 提前发令牌，有令牌才能抢
4. 动静分离 —— 静态页面 CDN，动态接口才到后端
```

### 秒杀令牌

```text
秒杀令牌：提前发放抢购资格，有令牌才能参与秒杀

1. 用户在秒杀前领取令牌
2. 秒杀时校验令牌
3. 没有令牌的请求直接拒绝（拦截大部分流量）
```

### MQ 削峰

```text
请求 → MQ（缓冲）→ 消费者按库存能力处理

瞬时 10 万请求 → MQ 缓冲 → 库存 1 万，消费者只处理 1 万
```

## Redis 与 MQ 的运用

### Redis 的作用

```text
1. 缓存 —— 商品信息、库存预热
2. 原子扣库存 —— DECR 原子操作
3. 分布式锁 —— 防重复
4. 限流 —— 令牌桶
```

```java
// Redis 预热库存
redisTemplate.opsForValue().set("stock:1001", 100);

// Redis 原子扣库存（防超卖的核心）
Long stock = redisTemplate.opsForValue().decrement("stock:1001");
if (stock < 0) {
    // 库存不足，回滚 + 秒杀失败
    redisTemplate.opsForValue().increment("stock:1001");
    throw new SecKillException("已售罄");
}
```

### MQ 的作用

```text
1. 削峰 —— 缓冲请求
2. 异步 —— 下单异步处理（扣库存、生成订单、发通知）
3. 解耦 —— 下单、库存、通知解耦
```

## 限流与防刷

### 限流

```java
// 接口限流（令牌桶）
RateLimiter limiter = RateLimiter.create(10000);   // 每秒 1 万

public Result seckill(Long userId, Long goodsId) {
    if (!limiter.tryAcquire()) {
        return Result.error("系统繁忙，请稍后再试");
    }
    // 秒杀逻辑
}
```

### 防刷

```text
防刷手段：
1. 限购 —— 一人只能买一件（Redis 记录）
2. 风控 —— 识别异常用户（频率、IP）
3. 验证码 —— 增加刷单成本
4. 令牌 —— 有令牌才能抢
```

```java
// 限购：一人一件
String key = "seckill:user:" + userId;
Boolean first = redisTemplate.opsForValue().setIfAbsent(key, "1", 24, TimeUnit.HOURS);
if (!Boolean.TRUE.equals(first)) {
    return Result.error("每人限购一件");
}
```

## 防超卖

防超卖是秒杀的核心，保证卖出的不超过库存。

### 防超卖方案对比

| 方案 | 原理 | 问题 |
|------|------|------|
| 悲观锁 | SELECT FOR UPDATE | 性能差 |
| 乐观锁 | 版本号 CAS | 冲突重试 |
| Redis 原子 | DECR 原子操作 | 推荐 |
| 数据库条件更新 | WHERE stock > 0 | 兜底 |

### Redis 原子扣库存（推荐）

```java
// Redis DECR 原子操作，天然防超卖
Long stock = redisTemplate.opsForValue().decrement("stock:" + goodsId);
if (stock < 0) {
    redisTemplate.opsForValue().increment("stock:" + goodsId);
    throw new SecKillException("已售罄");
}
```

### 数据库条件更新（兜底）

```sql
-- 条件更新：库存 > 0 才更新，天然防超卖
UPDATE goods SET stock = stock - 1 WHERE id = 1001 AND stock > 0;
-- 返回影响行数 0 说明库存不足
```

## 幂等与分布式锁

### 幂等

```text
幂等：重复请求不重复扣库存（防重复提交）
```

```java
// 幂等：Redis 记录已处理
String idempotentKey = "seckill:" + userId + ":" + goodsId;
Boolean first = redisTemplate.opsForValue()
    .setIfAbsent(idempotentKey, "1", 24, TimeUnit.HOURS);
if (!Boolean.TRUE.equals(first)) {
    return Result.error("请勿重复提交");
}
```

### 分布式锁

```text
分布式锁：保证同一时刻只有一个请求处理（详见 100）
```

```java
// Redisson 分布式锁
RLock lock = redissonClient.getLock("seckill:lock:" + goodsId);
try {
    if (lock.tryLock(3, 10, TimeUnit.SECONDS)) {
        // 扣库存
    }
} finally {
    lock.unlock();
}
```

## 完整架构设计

```text
秒杀系统完整架构：

用户 → CDN（静态页面）
     → 网关（限流）
     → 秒杀令牌校验（没令牌直接拒）
     → 秒杀接口（Redis 原子扣库存 + 限购 + 幂等）
     → MQ（异步下单）
     → 消费者（数据库扣库存兜底 + 生成订单）
     → 通知用户
```

```text
关键设计：
1. 库存预热 —— 秒杀前把库存加载到 Redis
2. 动静分离 —— 静态页面 CDN，动态接口才到后端
3. 分层限流 —— 网关限流 + 接口限流 + 令牌
4. Redis 原子扣库存 —— 防超卖
5. MQ 异步下单 —— 削峰 + 解耦
6. 数据库兜底 —— 条件更新防超卖
```

## 最佳实践与踩坑记录

### 最佳实践

1. **库存预热到 Redis**。秒杀前加载，Redis 原子扣库存。

2. **MQ 异步下单**。扣库存成功后才异步生成订单。

3. **分层限流**。网关 + 接口 + 令牌多层防护。

4. **限购 + 幂等**。防刷、防重复提交。

5. **数据库兜底**。条件更新（WHERE stock > 0）防超卖。

### 踩坑记录

**坑 1：数据库直接扣库存超卖**

```java
// 先查再更新，并发时超卖
int stock = selectStock();   // 查到 1
if (stock > 0) {
    update(stock - 1);   // 两个请求都查到 1，都更新，超卖
}
```

用 Redis 原子扣库存，或数据库条件更新（WHERE stock > 0）。

**坑 2：Redis 扣库存后数据库不一致**

```text
Redis 扣了库存，但数据库没扣（MQ 消费失败），数据不一致
```

数据库兜底 + 对账 + 补偿。

**坑 3：秒杀请求直接打到数据库**

```text
没有缓存和 MQ，瞬时流量直接打数据库，数据库崩
```

Redis 预热 + MQ 削峰。

**坑 4：忽略幂等导致重复下单**

```text
用户重复点击，重复扣库存、重复下单
```

幂等设计（Redis 记录已处理）。

**坑 5：限购被绕过**

```text
同一用户多个账号刷单，绕过限购
```

风控（IP、设备指纹）+ 验证码。

**坑 6：分布式锁性能差**

```text
每个请求都加分布式锁，锁竞争激烈，性能差
```

优先用 Redis 原子操作（DECR），分布式锁只在必要场景用。
