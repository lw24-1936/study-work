## 概述

高并发是系统在大量用户同时访问时仍能稳定运行的能力，理解核心指标是做高并发设计的基础。

```text
高并发系统设计的三步：
1. 明确目标 —— 要支持多少并发（指标）
2. 评估容量 —— 现有系统能扛多少
3. 设计优化 —— 补齐短板，达到目标
```

## 核心指标

### QPS 与 TPS

```text
QPS（Queries Per Second）—— 每秒查询数
TPS（Transactions Per Second）—— 每秒事务数
```

```text
QPS vs TPS：
QPS —— 侧重查询（读）
TPS —— 侧重事务（写，一个事务可能多次查询）

通常 QPS ≥ TPS
```

### RT 响应时间

```text
RT（Response Time）—— 响应时间（从请求到响应）

关注指标：
平均响应时间 —— 平均值（可能被长尾拉高）
P95 —— 95% 请求的响应时间
P99 —— 99% 请求的响应时间（长尾）
```

### Throughput 吞吐量

```text
吞吐量 = 单位时间处理的请求数（即 QPS/TPS）
```

### Concurrency 并发量

```text
并发量 = 同一时刻正在处理的请求数

并发量 vs QPS：
并发量 = QPS × 平均响应时间（Little's Law）
```

## 指标之间的关系

### Little's Law

```text
并发量 = QPS × 平均响应时间

例：QPS = 1000，平均响应时间 = 200ms
并发量 = 1000 × 0.2 = 200（同时 200 个请求在系统中）
```

### QPS 与响应时间

```text
QPS 和响应时间相互影响：
响应时间越长 → 相同并发下 QPS 越低

优化响应时间 = 提升 QPS
```

### 指标示例

```text
电商大促的目标：
QPS = 10 万（峰值）
平均响应时间 < 200ms
P99 < 500ms
错误率 < 0.1%
```

## 容量评估

### 容量评估方法

```text
1. 单机压测 —— 测出单机能扛的 QPS
2. 计算所需机器 —— 目标 QPS / 单机 QPS
3. 预留冗余 —— 预留 30-50% 冗余
```

```text
例：
目标 QPS = 10 万
单机 QPS = 5000（压测得到）
需要机器 = 100000 / 5000 = 20 台
预留冗余 → 部署 26-30 台
```

### 容量评估的维度

```text
1. 应用层 —— 单机 QPS
2. 数据库 —— 连接数、QPS
3. 缓存 —— 命中率、内存
4. 网络 —— 带宽
```

```text
瓶颈通常在数据库：
应用能扛 5000 QPS，但数据库只能扛 1000 QPS
→ 数据库是瓶颈，需要缓存/读写分离
```

## 压测与验证

### 压测工具

```text
1. JMeter —— 通用压测（详见 129）
2. Gatling —— 高并发
3. wrk —— 轻量 HTTP 压测
```

### 压测流程

```text
1. 确定压测目标（QPS、响应时间）
2. 设计压测场景（读/写/混合）
3. 从小并发逐步加（找到拐点）
4. 监控系统指标（CPU、内存、数据库）
5. 分析瓶颈，优化后重新压测
```

```bash
# wrk 压测
wrk -t 10 -c 100 -d 60s http://localhost:8080/api/users
# 10 线程，100 连接，压测 60 秒
```

### 压测注意事项

```text
1. 压测环境独立（不影响生产）
2. 压测机不是瓶颈（多台压测机）
3. 预热（JIT、连接池）
4. 关注 P99（不只平均值）
```

## 应用场景实战

### 场景 1：容量评估

```text
目标：双 11 活动，峰值 QPS 预计 5 万

评估：
1. 压测单机 QPS = 4000
2. 需要机器 = 50000 / 4000 = 13 台
3. 预留 50% 冗余 → 20 台
4. 数据库评估：需要缓存 + 读写分离
```

### 场景 2：瓶颈定位

```text
压测发现 QPS 上不去（1000 就卡住）：

分析：
1. 监控 CPU —— 应用 CPU 低，说明不是应用瓶颈
2. 监控数据库 —— 数据库连接耗尽
3. 结论：数据库是瓶颈

优化：
1. 热点数据加缓存
2. 读写分离
3. 优化慢 SQL
```

## 最佳实践与踩坑记录

### 最佳实践

1. **先压测再上线**。知道系统能扛多少。

2. **关注 P99**。平均值掩盖长尾问题。

3. **预留冗余**。容量评估留 30-50% 冗余。

4. **分层评估**。应用、数据库、缓存分别评估。

5. **瓶颈通常在数据库**。优先优化数据库 + 缓存。

### 踩坑记录

**坑 1：只看平均响应时间**

```text
平均 100ms，但 P99 是 5 秒（长尾严重）
```

关注 P95/P99。

**坑 2：压测机成为瓶颈**

```text
单机压测 1 万并发，压测机先扛不住，结果不准
```

多台压测机，或确认压测机不是瓶颈。

**坑 3：没预热就压测**

```text
第一次压测结果差（JIT 没编译、连接池没建）
```

压测前预热。

**坑 4：忽略数据库瓶颈**

```text
只优化应用，数据库扛不住，整体 QPS 上不去
```

瓶颈通常在数据库，优先优化数据库 + 缓存。

**坑 5：容量评估不留冗余**

```text
评估刚好够用，流量超预期就崩
```

预留 30-50% 冗余。

**坑 6：并发量和 QPS 混淆**

```text
100 并发 ≠ 100 QPS（并发量是同时处理数，QPS 是每秒处理数）
```

理解并发量 = QPS × 响应时间的关系。
