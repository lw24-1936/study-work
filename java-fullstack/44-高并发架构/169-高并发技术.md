## 概述

高并发技术是应对海量请求的技术手段，从缓存、异步到限流、分库分表，构成完整的高并发技术体系。

```text
高并发技术全景：
请求 → CDN → 网关（限流）→ 应用（缓存/异步）→ 数据库（分库分表/读写分离）
```

## 缓存

缓存是高并发第一道防线，减轻数据库压力（详见 21-SpringCache、105-分布式缓存）。

### 缓存层次

```text
1. 浏览器缓存 —— 静态资源
2. CDN 缓存 —— 静态资源就近
3. 应用本地缓存 —— Caffeine（进程内）
4. 分布式缓存 —— Redis（跨进程）
```

### 缓存的使用

```java
// 多级缓存（本地 + Redis）
public User getUser(Long id) {
    // 1. 本地缓存（Caffeine，最快）
    User user = caffeineCache.get(id);
    if (user != null) return user;

    // 2. Redis 缓存
    user = redisTemplate.opsForValue().get("user:" + id);
    if (user != null) {
        caffeineCache.put(id, user);
        return user;
    }

    // 3. 数据库
    user = userMapper.selectById(id);
    if (user != null) {
        redisTemplate.opsForValue().set("user:" + id, user);
    }
    return user;
}
```

### 缓存的三大问题

```text
1. 穿透 —— 查不存在的数据（布隆过滤器、缓存空值）
2. 击穿 —— 热点 key 过期（互斥锁、永不过期）
3. 雪崩 —— 大量 key 同时过期（随机过期时间）
```

## 异步与消息队列

### 异步

```text
异步：非关键流程异步处理，快速响应
```

```java
// 同步：创建订单 + 发通知 + 记日志（慢）
// 异步：创建订单（快速返回），通知和日志异步处理
@Async
public void sendNotification(Long userId) { ... }
```

### 消息队列削峰

```text
消息队列削峰：请求先入队列，消费者按能力处理

瞬时 10 万请求 → 消息队列（缓冲）→ 消费者按 1 万/秒处理
```

```text
消息队列的作用：
1. 削峰 —— 缓冲瞬时流量
2. 解耦 —— 服务间解耦
3. 异步 —— 异步处理
```

## 限流、熔断、降级

### 限流

```text
限流：控制请求量，保护系统（详见 103）
```

```text
限流算法：
1. 计数器 —— 简单
2. 滑动窗口 —— 平滑
3. 漏桶 —— 恒定速率
4. 令牌桶 —— 允许突发（最常用）
```

```java
// 令牌桶限流（Guava RateLimiter）
RateLimiter limiter = RateLimiter.create(1000);   // 每秒 1000 个

public void handle() {
    if (limiter.tryAcquire()) {   // 获取令牌
        process();
    } else {
        reject();   // 限流
    }
}
```

### 熔断

```text
熔断：故障服务快速失败，防止级联（详见 98）
```

### 降级

```text
降级：服务不可用时返回兜底结果
```

```java
@SentinelResource(value = "getUser", fallback = "getUserFallback")
public User getUser(Long id) {
    return userService.get(id);
}

public User getUserFallback(Long id, Throwable t) {
    return new User(id, "默认用户");   // 降级返回默认值
}
```

## 分库分表与读写分离

### 读写分离

```text
主库写，从库读（读多写少场景）
```

### 分库分表

```text
数据量大的表拆分（详见 166）：
水平分表 —— 订单表拆成 16 张
垂直分库 —— 按业务拆库
```

### 分库分表工具

```yaml
# ShardingSphere 配置
sharding:
  tables:
    orders:
      actual-data-nodes: ds.orders_$->{0..15}   # 16 张表
      table-strategy:
        inline:
          sharding-column: user_id
          algorithm-expression: orders_$->{user_id % 16}
```

## 技术选型总结

| 问题 | 技术 | 作用 |
|------|------|------|
| 数据库压力大 | 缓存（Redis） | 减轻数据库 |
| 瞬时流量大 | 消息队列 | 削峰 |
| 请求过多 | 限流 | 保护系统 |
| 服务故障 | 熔断/降级 | 防级联 |
| 数据量大 | 分库分表 | 拆分数据 |
| 读多写少 | 读写分离 | 分担压力 |
| 静态资源慢 | CDN | 就近加速 |

```text
高并发技术的组合：
CDN + 网关限流 + 缓存 + 异步 + 消息队列 + 分库分表

不是所有技术都用，按需选择：
小流量 → 缓存 + 异步够用
大流量 → 全链路优化（缓存 + MQ + 分库分表 + 限流）
```

## 最佳实践与踩坑记录

### 最佳实践

1. **缓存优先**。能缓存的都缓存，减轻数据库。

2. **非关键流程异步**。发通知、日志异步。

3. **瞬时流量用消息队列削峰**。秒杀、大促。

4. **服务间调用设超时**。防止级联故障。

5. **按需选择技术**。不盲目堆技术，按流量规模选。

### 踩坑记录

**坑 1：缓存和数据库不一致**

```text
更新数据库后缓存没更新，读到旧数据
```

先更新数据库，再删缓存（Cache Aside）。

**坑 2：缓存穿透击穿雪崩**

```text
没处理缓存三大问题，缓存失效时数据库被打垮
```

布隆过滤器、互斥锁、随机过期时间。

**坑 3：异步丢失重要操作**

```text
关键操作也异步，失败没感知
```

关键操作同步，非关键才异步。

**坑 4：限流误伤正常用户**

```text
限流阈值太低，正常用户被拒
```

合理设置阈值，用令牌桶允许突发。

**坑 5：分库分表后跨库查询**

```text
分库后跨库 join 失败
```

拆分查询，避免跨库 join。

**坑 6：盲目堆技术**

```text
小流量也上全套高并发技术，复杂度高
```

按需选择，先简单后复杂。
