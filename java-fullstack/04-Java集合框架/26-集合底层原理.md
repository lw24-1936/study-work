## 概述

集合框架的强大不在于 API 统一，而在于底层数据结构的精妙选择——知道 ArrayList 什么时候扩容、HashMap 的 hash 怎么算、ConcurrentHashMap 为什么 JDK 8 抛弃了分段锁——面试不怯场，线上不出事。

本篇聚焦四大核心：ArrayList 扩容、HashMap 全流程、ConcurrentHashMap 演进、Fail-Fast 机制。

## ArrayList 扩容机制

`ArrayList` 底层是一个 `Object[] elementData`，扩容是它最核心的操作：

### 初始化

```java
// JDK 7+：无参构造 → 空数组（懒初始化）
List<String> list = new ArrayList<>();  // elementData = EMPTY_ELEMENTDATA（一个 static final 空数组）

// 第一次 add 时：容量 → 10（DEFAULT_CAPACITY）
list.add("a");

// 指定容量：不懒初始化
List<String> list2 = new ArrayList<>(100);  // elementData = new Object[100]
```

### 扩容流程

```java
// 源码简化版
public boolean add(E e) {
    ensureCapacityInternal(size + 1);  // 确保容量
    elementData[size++] = e;            // 放入元素
    return true;
}

private void ensureCapacityInternal(int minCapacity) {
    // 如果是空数组，取 max(10, minCapacity)
    if (elementData == EMPTY_ELEMENTDATA) {
        minCapacity = Math.max(DEFAULT_CAPACITY, minCapacity);
    }
    if (minCapacity - elementData.length > 0) {
        grow(minCapacity);
    }
}

private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1);  // 1.5 倍
    if (newCapacity - minCapacity < 0) {
        newCapacity = minCapacity;    // 还不够就用需要的
    }
    if (newCapacity - MAX_ARRAY_SIZE > 0) {
        newCapacity = hugeCapacity(minCapacity); // 接近 Integer.MAX_VALUE
    }
    elementData = Arrays.copyOf(elementData, newCapacity);  // 复制
}
```

扩容公式：**新容量 = 旧容量 + 旧容量 / 2**（`oldCapacity >> 1`），即 1.5 倍。

```
初始 10 → 15 → 22 → 33 → 49 → 73 → ...
```

注意：扩容使用 `Arrays.copyOf()`，底层是 `System.arraycopy()`——**JNI 实现的批量内存复制**，比循环赋值快一个数量级。

### 最大容量

最大容量是 `Integer.MAX_VALUE - 8`（约 21.47 亿），-8 是因为某些 VM 在数组头存储一些元数据。如果这个容量还不够，取 `Integer.MAX_VALUE`。

实际中，一个 ArrayList 存 21 亿个对象引用，仅引用数组就需要约 16GB 内存，早就 OOM 了——这是理论上的上限。

## LinkedList 链表结构

`LinkedList` 是**双向链表**，每个节点持有前后引用：

```java
// Node 内部类（简化）
private static class Node<E> {
    E item;
    Node<E> next;
    Node<E> prev;

    Node(Node<E> prev, E element, Node<E> next) {
        this.item = element;
        this.next = next;
        this.prev = prev;
    }
}

// LinkedList 自身持有头尾引用
transient Node<E> first;
transient Node<E> last;
```

### 插入/删除到底多快

```java
// addFirst —— O(1)，直接改 first 引用
void linkFirst(E e) {
    Node<E> f = first;
    Node<E> newNode = new Node<>(null, e, f);
    first = newNode;
    if (f == null) last = newNode;
    else f.prev = newNode;
    size++;
}

// add(index, e) —— 需要先找到位置节点 O(n)，然后插入 O(1)
// get(index) —— 从头或尾开始遍历，O(n/2) → O(n)
```

所以 "LinkedList 插入快" 只在**头尾**成立。中间插入需要先遍历 O(n) 再插入 O(1)，和 ArrayList 的 O(n) 移动元素一样，实际运行中 ArrayList 因为连续内存还更快。

## HashMap 原理深度解析

这是面试和实际中最常涉及的知识点。

### 1. 哈希计算

```java
// 源码
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

为什么右移 16 位：把 hashCode 的高位信息混入低位——因为计算桶索引时用的是 `(n - 1) & hash`，当 n（桶数量）较小时，高位信息会被掩码切掉。让高位参与异或运算，减少碰撞。

### 2. 桶索引计算

```java
// 不是取模 %，而是位运算 &（快得多）
int index = (table.length - 1) & hash;

// 前提：table.length 必须是 2 的幂
// 16 - 1 = 15 = 0b1111
// hash & 15 等价于 hash % 16，但速度快
```

### 3. 存储结构

JDK 7：数组 + 单向链表（头插法）
JDK 8：数组 + 单向链表 + 红黑树（尾插法）

```
table (Node[]):
[0] → (Node) → (Node)         ← 链表
[1] → (TreeNode) ← (TreeNode) ← 红黑树
      /         \
[2] → (Node)
...
[15] → null
```

Node 结构：

```java
static class Node<K,V> {
    final int hash;
    final K key;
    V value;
    Node<K,V> next;  // 链表的下一个
}
```

### 4. put 流程

```
1. 计算 hash(key)
2. table 为 null 或 length=0 → resize() 初始化
3. index = (n-1) & hash
4. table[index] 为空 → 直接放
5. 不为空：
   a. 第一个节点 key 相等 → 替换
   b. 第一个节点是 TreeNode → 走红黑树的 putTreeVal
   c. 否则遍历链表：
      - 找到相同 key → 替换
      - 遍历完没找到 → 尾插
      - 插入后链表长度 >= 8 → treeifyBin（转红黑树）
6. size > threshold → resize() 扩容
```

### 5. resize（扩容）

扩容条件：`size > threshold`，其中 `threshold = capacity * loadFactor`（默认 16 × 0.75 = 12）。

```java
// 扩容流程
final Node<K,V>[] resize() {
    // 1. 新容量 = 旧容量 × 2
    // 2. 新阈值 = 旧阈值 × 2
    // 3. 创建新数组
    // 4. 迁移元素：
    //    - 单节点：直接 rehash → 新 index
    //    - 链表：拆分为 lo（留在原位）和 hi（移到 index+oldCap）
    //    - 红黑树：类似拆分 + 可能退化
}
```

JDK 8 扩容优化——不再每个元素重新 hash，利用 2 的幂特性：

```java
// 旧索引 = hash & (oldCap - 1)
// 新索引 = hash & (newCap - 1) = hash & (oldCap * 2 - 1)

// 只多了一位（最高位），新索引可能的位置只有两个：
// - 留在原位：hash & oldCap == 0  → index 不变
// - 移到高位：hash & oldCap != 0  → index = oldIndex + oldCap
```

这就是为什么迁移时只需要把链表拆成 lo 和 hi 两个链表——不需要为每个元素重新计算索引。

### 6. JDK 7 头插法死循环问题

JDK 7 的 `resize()` 在迁移链表时用头插法（倒序），多线程并发 put 可能导致链表成环，CPU 100%。JDK 8 改为尾插法（保持顺序），解决了死循环问题——但多线程 put 仍可能丢数据，并发场景必须用 ConcurrentHashMap。

## 红黑树化与退化

### 树化条件

链表长度达到 **8** 且数组长度 >= **64** 时，链表转为红黑树：

```java
static final int TREEIFY_THRESHOLD = 8;
static final int MIN_TREEIFY_CAPACITY = 64;

// 如果数组长度 < 64，优先扩容而不是树化
```

为什么是 8：

```
概率：理想情况下（hash 分布均匀），链表长度达到 8 的概率约 0.00000006（泊松分布）
说明：正常情况下不应该出现 8 个碰撞——出现了说明 hashCode 写得有问题
```

### 退化条件

红黑树在以下情况退化为链表：
1. `resize()` 时树拆分后节点数 <= **6**
2. `remove()` 后树节点太少（<= 6）

```
链表 ←→ 红黑树的临界点：
  链表长度 >= 8 && 数组长度 >= 64 → 树化
  树节点数量 <= 6 → 退化
```

中间值 7 作为缓冲——避免在 7-8 之间反复转换。

## HashSet 与 TreeMap 原理

### HashSet = HashMap 的包装

```java
// HashSet 内部
private transient HashMap<E,Object> map;
private static final Object PRESENT = new Object();

public boolean add(E e) {
    return map.put(e, PRESENT) == null;  // 元素当 key，PRESENT 当 value
}

public boolean contains(Object o) {
    return map.containsKey(o);
}

public boolean remove(Object o) {
    return map.remove(o) == PRESENT;
}
```

一个 HashSet 的 add 就是一次 HashMap 的 put——元素作为 key，所有 key 共享同一个 value 哨兵对象。

### TreeMap 与 TreeSet

`TreeMap` 和 `TreeSet` 底层都是红黑树。TreeMap 的 `Entry` 有 left、right、parent 三个引用和 color 标记。

```java
// TreeMap Entry
static final class Entry<K,V> {
    K key;
    V value;
    Entry<K,V> left;
    Entry<K,V> right;
    Entry<K,V> parent;
    boolean color = BLACK;
}
```

`TreeSet` 则是 `TreeMap` 的薄包装——元素做 key，value 用一个共享的 PRESENT 哨兵。

## ConcurrentHashMap 演进

### JDK 7：分段锁（Segment）

```java
// 默认 16 个 Segment，每个 Segment 管理一部分桶
// Segment 继承 ReentrantLock
// put 时只锁目标 Segment，不同 Segment 的并发 put 不互斥

ConcurrentHashMap<K,V>
├── Segment[0] (ReentrantLock) → HashEntry[] → 链表
├── Segment[1] (ReentrantLock) → HashEntry[] → 链表
├── ...
└── Segment[15] → HashEntry[] → 链表
```

默认并发级别 16，即最多 16 个线程同时写入不互斥。

### JDK 8：CAS + synchronized 桶锁

```java
// 抛弃 Segment，直接对桶头节点加锁
// put 流程：
//  1. 计算桶索引
//  2. 桶为空 → CAS 尝试放置（不加锁）
//  3. 桶不为空 → synchronized(桶头节点) → 插入链表/红黑树
//  4. 扩容时多线程协同迁移（不阻塞读）
```

JDK 8 的关键改进：
- **CAS 无锁插入**：桶为空时用 CAS，不竞争
- **细化锁粒度**：锁桶头节点，不是整个 Segment
- **红黑树**：长链转红黑树，O(log n) 查找
- **协同扩容**：迁移时可以多线程参与，`sizeCtl` 控制扩容状态

### key/value 为什么不能为 null

ConcurrentHashMap 设计者 Doug Lea 的解释：在并发环境中，`get(key)` 返回 null 没法区分是 "key 不存在" 还是 "value 就是 null"。非并发场景确实可以通过 `containsKey` 区分的，但并发场景下 `containsKey` 和 `get` 之间状态可能变化——这就是二义性。不如直接禁止 null。

## Fail-Fast 与 Fail-Safe

### Fail-Fast（快速失败）

`ArrayList`、`HashMap` 等非并发集合的迭代器——遍历时如果集合被**结构性修改**（除了迭代器自身的 remove），立即抛 `ConcurrentModificationException`：

```java
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
for (String s : list) {
    if (s.equals("b")) {
        list.remove(s);     // ConcurrentModificationException！
    }
}

// 原理：集合有一个 modCount 计数器
// 迭代器创建时用 expectedModCount = modCount 记录快照
// 每次 next() 检查 expectedModCount == modCount，不相等就抛异常
```

正确做法：

```java
// 1. 用迭代器的 remove
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().equals("b")) {
        it.remove();  // OK
    }
}

// 2. JDK 8+ 用 removeIf
list.removeIf(s -> s.equals("b"));

// 3. 并发环境用 CopyOnWriteArrayList
```

### Fail-Safe（安全失败）

`ConcurrentHashMap`、`CopyOnWriteArrayList` 的迭代器——遍历时如果集合被修改，**不抛异常**，而是基于**快照**遍历：

```java
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();
map.put("a", 1);
map.put("b", 2);

for (String key : map.keySet()) {
    map.put("c", 3);      // 不抛异常！迭代看到的是创建迭代器时的快照
}
```

注意：Fail-Safe 迭代器保证不抛异常，但不保证看到最新数据（弱一致性）。ConcurrentHashMap 的迭代器反映的是**创建时或某个时间点**的数据。

## Iterator 与 Spliterator

### Iterator

```java
public interface Iterator<E> {
    boolean hasNext();
    E next();
    default void remove() { throw new UnsupportedOperationException(); }
    default void forEachRemaining(Consumer<? super E> action) { ... }
}
```

增强 for 循环 `for (E e : collection)` 编译后等价于 Iterator 遍历。

### Spliterator（JDK 8+）

Spliterator 是**可分割的迭代器**，用于并行流的拆分：

```java
public interface Spliterator<T> {
    boolean tryAdvance(Consumer<? super T> action);  // 逐个迭代
    Spliterator<T> trySplit();                        // 拆分成两半（用于并行）
    long estimateSize();                              // 估算剩余元素数
    int characteristics();                            // 特性（ORDERED, SIZED, SUBSIZED 等）
}

// ArrayList 的 Spliterator
// trySplit 把前半部分分出去，后半部分留着继续处理
// 这样 ForkJoinPool 可以多线程并行处理
```

ArrayList 的 Spliterator 拆分是 O(1)（二分法），LinkedList 是 O(n)（因为无法直接跳到中间）。

## 应用场景实战

### 场景一：正确使用 HashMap 预分配容量

```java
// 错误：直接 new HashMap<>() —— 要存 10000 个元素
// 默认 16，经 7 次扩容才能装下（16→24→36→54→81→121→...）

// 正确：预估容量
int expectedSize = 10000;
int capacity = (int) (expectedSize / 0.75f) + 1;  // 13334
Map<String, User> map = new HashMap<>(capacity);
// 一次扩容都不用！
```

### 场景二：安全遍历删除

```java
Map<String, Integer> map = new HashMap<>();
map.put("a", 1);
map.put("b", 2);
map.put("c", 3);

// JDK 8+ 一步
map.entrySet().removeIf(e -> e.getValue() < 3);

// 或迭代器
Iterator<Map.Entry<String, Integer>> it = map.entrySet().iterator();
while (it.hasNext()) {
    if (it.next().getValue() < 3) {
        it.remove();
    }
}
```

### 场景三：理解 ArrayList modCount 的价值

```java
// modCount 不止是快速失败 —— 也是 subList 能工作的保证
List<String> list = new ArrayList<>(List.of("a", "b", "c", "d"));
List<String> sub = list.subList(1, 3);

// 原列表每次修改 modCount++
// subList 持有原列表的引用，每次操作都检查 modCount
list.add("e");
// sub.get(0);  // ConcurrentModificationException！
// 因为 list.add 修改了 modCount，subList 检测到不一致
```

## 最佳实践与踩坑记录

### 常见问题表

| 问题 | 原因 | 修复 |
|------|------|------|
| HashMap 扩容导致 CPU 飙高 | 大 HashMap 扩容时迁移元素耗时 | 预估容量，预分配；考虑用 `ConcurrentHashMap` |
| 遍历时修改集合抛 CME | fail-fast 机制 | 用 Iterator.remove() 或 removeIf() |
| HashMap key 用可变对象找不到 | key 被修改后 hashCode 变了 | key 用不可变对象 |
| JDK 7 HashMap 多线程死循环 | 头插法 + 并发 resize | 升级 JDK 8 或使用 ConcurrentHashMap |
| ArrayList 频繁中间插入 | 每次 O(n) 移动元素 | 考虑 LinkedList 或重新设计 |

### 关键经验

- **HashMap 预分配容量**：`capacity = expectedSize / 0.75 + 1`，避免扩容
- **不要在遍历中修改**：fail-fast 是保护不是 bug
- **key 用不可变对象**：`String`、`Integer`、`LocalDate` 天然不可变
- **并发场景必用 ConcurrentHashMap**：不要指望 `Collections.synchronizedMap`
- **参数调优**：HashMap 构造函数里指定容量，不是用于缩容——是给扩容多留点缓冲

## 总结

- ArrayList：数组 + 1.5 倍扩容 + System.arraycopy 复制
- HashMap JDK 8：数组 + (链表|红黑树)，链表长度 >= 8 且桶数 >= 64 时树化
- HashMap 索引 = `(n-1) & hash`，hash = `hashCode() ^ (hashCode >>> 16)`
- ConcurrentHashMap JDK 8：CAS（空桶）+ synchronized（非空桶头节点），分段锁已成历史
- Fail-Fast：modCount 检测并发修改；Fail-Safe：基于快照，不保证最新数据
- 迭代器安全删除：`Iterator.remove()` 或 `removeIf()`；增强 for 里不能调集合的 remove/add
