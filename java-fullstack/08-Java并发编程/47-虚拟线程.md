## 概述

虚拟线程（Virtual Thread）是 JDK 21 正式发布的革命性特性（来自 Project Loom）——它改变了 Java 的并发模型，让"每请求一线程"从反模式变成了最佳实践。

核心改变：平台线程（Platform Thread）是 OS 线程的 1:1 映射，昂贵且稀缺。虚拟线程由 JVM 调度，轻量且几乎无限（百万级）。

```
JDK 21 之前：
  每个请求 → 一个平台线程（OS 线程）
  线程数 = 几百到几千（内存限制）
  阻塞 = 平台线程被挂起（OS 调度）

JDK 21 虚拟线程：
  每个请求 → 一个虚拟线程（由 JVM 管理）
  虚拟线程数 = 可以上百万
  阻塞 = 虚拟线程"挂载"到不同的平台线程（JVM 调度）
```

## 平台线程 vs 虚拟线程

| 维度 | 平台线程 | 虚拟线程 |
|------|----------|----------|
| 调度者 | OS 内核 | JVM（协程式） |
| 创建成本 | ~1ms + ~1MB 栈 | ~1μs + 几百字节 |
| 数量上限 | 几千（栈内存受限） | 百万级 |
| 阻塞代价 | OS 上下文切换（昂贵） | 栈帧换出到堆（轻量） |
| 线程名 | 用户指定 | 自动命名 |
| 是否为 daemon | 用户指定 | **始终是 daemon** |
| 优先级 | 支持（但不可靠） | 不支持（setPriority 无效果） |
| ThreadGroup | 支持 | 不支持（始终为 null） |

## 创建虚拟线程

```java
// 方式一：Thread.ofVirtual()
Thread vThread = Thread.ofVirtual()
    .name("virtual-worker-1")
    .start(() -> {
        System.out.println("虚拟线程: " + Thread.currentThread());
    });
vThread.join();  // 等待完成

// 方式二：Thread.startVirtualThread（快捷）
Thread vThread2 = Thread.startVirtualThread(() -> {
    System.out.println("快捷创建虚拟线程");
});

// 方式三：ThreadFactory
ThreadFactory factory = Thread.ofVirtual()
    .name("vthread-", 0)
    .factory();

Thread t = factory.newThread(() -> System.out.println("from factory"));
t.start();

// 方式四：Thread.Builder（构建器模式）
Thread vThread3 = Thread.ofVirtual()
    .name("custom")
    .unstarted(() -> System.out.println("未启动"));  // 不自动 start
vThread3.start();
```

关键点：
- 虚拟线程**总是 daemon**——主线程退出后虚拟线程也会终止
- 不需要线程池——创建成本极低，直接 `new` 就可以
- `getName()` 会自动生成名字（如 `virtual-thread-1`）

## Executors.newVirtualThreadPerTaskExecutor

虚拟线程的革命性意义在于："**一个任务一个线程**"变成了可行的架构：

```java
// 每次 submit 都创建一个新的虚拟线程
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // 提交 10000 个任务——每个任务一个虚拟线程
    for (int i = 0; i < 10000; i++) {
        int taskId = i;
        executor.submit(() -> {
            try {
                Thread.sleep(1000);  // 在虚拟线程中阻塞——不影响平台线程
                System.out.println("任务 " + taskId + " 完成");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
    }
}  // try-with-resources 自动等待所有任务完成并关闭
```

对比传统方式：

```java
// 传统：线程池限制并发
ExecutorService pool = Executors.newFixedThreadPool(100);  // 最多 100 并发
pool.submit(() -> blockingIoCall());  // 阻塞了线程池中的线程！
// 100 个线程全部阻塞在 IO → 池满了 → 新任务排队

// 虚拟线程：没有池限制
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
executor.submit(() -> blockingIoCall());  // 阻塞只影响这个虚拟线程
// 平台线程去执行其他虚拟线程了——资源利用最大化
```

## 虚拟线程的工作原理

虚拟线程运行时"挂载"（mount）到一个平台线程（称为 carrier thread）：

```
                    JVM 调度器
                        │
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
    [Carrier-1]    [Carrier-2]    [Carrier-3]   ← 少量平台线程
         │              │              │
    ┌────┴────┐    ┌────┴────┐    ┌────┴────┐
  VT-1 VT-2  VT-3  ...    ...    ...      VT-N  ← 大量虚拟线程

VT 执行 → 挂载到 Carrier
VT 阻塞（IO/sleep） → unmount，Carrier 去执行其他 VT
VT 解除阻塞 → 等待任意 Carrier 重新 mount
```

关键机制：
- 虚拟线程的栈存储在**堆上**（不是 OS 栈），可以动态增长缩小
- 阻塞时栈帧保留在堆中，Carrier 被释放
- 解除阻塞时从堆恢复栈帧，重新挂载到任意 Carrier

## 适用场景与不适用场景

### 适用（强推荐）

```
✓ 大量并发 IO 任务（HTTP 请求处理、数据库查询）
✓ "一个请求一个线程"模式（Servlet、Spring MVC）
✓ 大量短生命周期的并发任务
✓ 阻塞式的 API 调用（无需改为响应式编程）
```

### 不适用

```
✗ CPU 密集型任务（不需要阻塞，虚拟线程优势无法发挥）
✗ 被 synchronized 保护的长时间操作（会 pin 住 Carrier）
✗ 需要线程局部变量做缓存的场景（每个任务一个线程 → 不适合缓存）
✗ 需要精确控制线程优先级的场景（虚拟线程无优先级）
✗ 本地方法调用（JNI 会 pin 住 Carrier）
```

## 虚拟线程陷阱

### 陷阱一：synchronized 会 pin 住 Carrier

```java
// 危险：synchronized 中做阻塞操作
// 虚拟线程在 synchronized 块内阻塞时，Carrier 线程被"钉住"（pinned）
// 不能被释放去执行其他虚拟线程！

synchronized (lock) {
    Thread.sleep(1000);        // Carrier 被 pin 了！
    // 或 blockingIoCall();
}

// 解决方法：用 ReentrantLock 替代 synchronized
lock.lock();
try {
    Thread.sleep(1000);        // Carrier 可以正常释放
} finally {
    lock.unlock();
}
```

JDK 在逐步解决这个问题，但 JDK 21 中仍然存在。JDK 24+ 完全消除了这个限制。

### 陷阱二：线程池缓存

```java
// 错误：把虚拟线程放入池中（违背设计初衷）
// ExecutorService pool = Executors.newFixedThreadPool(100, Thread.ofVirtual().factory());

// 正确：每个任务一个新虚拟线程
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
```

虚拟线程创建成本极低，池化反而限制了并发度。

### 陷阱三：ThreadLocal 滥用

```java
// 虚拟线程场景下，ThreadLocal 的语义变了
// 传统：线程数少 → ThreadLocal 做缓存合理
// 虚拟线程：线程数多 → ThreadLocal 会浪费大量内存

// 替代方案：用 ScopedValue（JDK 21 预览，JDK 24 正式）
```

### 陷阱四：主线程不等待

```java
// 虚拟线程是 daemon，主线程退出时它们也会终止
Thread.startVirtualThread(() -> {
    sleep(5000);
    System.out.println("可能不会打印");
});
// 主线程立即退出 → 虚拟线程也跟着终止
```

## 应用场景实战

### 场景一：高并发 HTTP 服务

```java
// 传统：Tomcat 线程池最多 200 线程 → 200 并发
// 虚拟线程：每个请求一个虚拟线程 → 无限制（受限于 CPU/内存）

// Spring Boot 3.2+ 配置：
// spring.threads.virtual.enabled=true
```

### 场景二：批量数据导出

```java
public void exportAllUsers() {
    List<Long> userIds = userRepository.findAllIds();  // 10 万个用户
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
        for (Long id : userIds) {
            executor.submit(() -> {
                byte[] pdf = generatePdf(id);    // 生成 PDF
                uploadToOss(id, pdf);            // 上传 OSS（网络 IO）
            });
        }
    }  // 等待全部完成
}
```

### 场景三：并发调用多个微服务

```java
public OrderDetail getOrderDetail(Long orderId) {
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
        Future<User> userFuture = executor.submit(() -> userService.getUser(orderId));
        Future<Product> productFuture = executor.submit(() -> productService.getProduct(orderId));
        Future<Logistics> logisticsFuture = executor.submit(() -> logisticsService.query(orderId));

        return new OrderDetail(
            userFuture.get(),
            productFuture.get(),
            logisticsFuture.get()
        );
    }
}
```

## 最佳实践与踩坑记录

### 迁移清单

```
[ ] 替换 Executors.newFixedThreadPool → Executors.newVirtualThreadPerTaskExecutor
[ ] 替换 synchronized → ReentrantLock（阻塞路径上）
[ ] 检查 ThreadLocal 用量 → 考虑 ScopedValue
[ ] 确保主线程等待虚拟线程完成（join 或 try-with-resources）
[ ] 设置合理的并发上限（Semaphore 限制并发数）
[ ] JVM 参数监控：-Djdk.tracePinnedThreads=full（检测 pinned 线程）
```

### 并发限流

```java
// 虽然虚拟线程无限制，但下游资源（数据库连接、API 限流）有限
// 用 Semaphore 做并发控制
Semaphore semaphore = new Semaphore(100);  // 最多 100 并发

try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10000; i++) {
        executor.submit(() -> {
            semaphore.acquire();
            try {
                callDatabase();
            } finally {
                semaphore.release();
            }
        });
    }
}
```

### 常见问题表

| 问题 | 原因 | 修复 |
|------|------|------|
| 虚拟线程被 pinned | synchronized 内阻塞 | 换 ReentrantLock |
| 程序不等待虚拟线程 | 虚拟线程是 daemon | join() 或用 try-with-resources |
| 内存增长 | 大量 ThreadLocal | 换 ScopedValue 或手动清理 |
| 性能不如平台线程 | CPU 密集型任务不适合虚拟线程 | 继续保持平台线程 |

## 总结

- 虚拟线程 = JVM 管理的轻量线程，创建成本极低（μs 级），支持百万并发
- `Thread.ofVirtual().start(task)` 创建虚拟线程，`Executors.newVirtualThreadPerTaskExecutor()` 创建"每任务一线程"的 Executor
- 适合 IO 密集型（HTTP、数据库、消息队列），不适合 CPU 密集型
- 虚拟线程阻塞时自动释放 Carrier 线程，实现非阻塞的高效调度
- 两大陷阱：synchronized pinning + ThreadLocal 膨胀
- 虚拟线程让"一个请求一个线程"回归——不再需要响应式编程来规避线程瓶颈
