## 项目背景

在线支付系统是所有商业系统的「收银台」：电商下单、知识付费、SaaS 续费、线下扫码，钱从用户口袋到商户账户，中间隔着支付渠道（支付宝、微信支付）、银行、清算机构，任何一环出错都可能造成「钱收了订单没成立」或「退款退了两次」。这个系统的本质不是「调用一下支付接口」，而是把「下单 → 支付 → 回调 → 退款 → 对账」这条资金链路做成安全、可靠、可追溯的状态机。选择它作为综合实战项目，是因为支付场景把安全（验签）、幂等、分布式事务、对账这些后端最硬核的主题全部串了起来。

业务痛点：

```text
1. 资金错账：回调重复通知导致订单状态重复处理，用户付了一次钱订单显示两次支付
2. 伪造回调：攻击者构造假回调报文，骗过校验后系统直接发货
3. 回调丢失：网络抖动导致支付成功通知没收到，用户付了钱订单还挂着「待支付」
4. 退款混乱：用户退款后系统崩溃，退款单状态不明，重复退款或漏退款
5. 对账靠人工：每天财务手工拉取渠道账单与本地订单核对，慢且易漏
6. 渠道耦合：业务代码里直接写支付宝/微信 SDK 调用，切换渠道就要改业务
7. 商户接入繁琐：每个商户都要单独对接，没有统一的接入与签名规范
```

目标用户与核心诉求：

```text
1. 业务方（电商/内容平台）：统一下单、支付发起、回调处理要简单可靠
2. 财务人员：日对账自动化，差错自动发现，账单可追溯
3. 商户（平台模式）：自助接入、独立查询账单与退款
4. 运营人员：支付成功率、退款率等指标可视化
5. 安全团队：验签、防重放、资金链路审计一个都不能少
```

项目要解决的核心问题一句话概括：把支付渠道差异封装在网关层，用验签、幂等、对账三道防线保证「每一分钱都准确、每一笔账都可对、每一次回调都不重不漏」。

## 功能介绍

功能按资金流转阶段拆分：商户接入、支付发起、回调处理、退款、对账、风控与查询。

```text
一、商户管理
1. 商户入驻 —— 商户注册、资质审核、渠道签约信息录入
2. 商户密钥 —— 生成商户签名密钥（appKey/appSecret），支持轮换
3. 商户余额 —— 交易流水、可结算余额、提现记录（平台模式）

二、统一下单
1. 下单接口 —— 业务方传入金额/商品/商户号，生成平台支付订单
2. 订单号生成 —— 平台订单号 + 渠道订单号（trade_no）双轨管理
3. 渠道路由 —— 按商户配置自动选择支付宝或微信支付

三、支付发起
1. 支付宝当面付/网站支付 —— 生成二维码（qr_code）或跳转链接（form/redirect）
2. 微信 Native/JSAPI —— 返回 code_url 或拉起小程序支付参数
3. 支付状态查询 —— 主动查单接口，兜底回调丢失场景

四、支付回调
1. 回调接入 —— 支付宝/微信异步通知统一入口
2. 验签 —— RSA2/SHA256 签名校验，拒绝伪造报文
3. 幂等处理 —— 同一笔通知重复到达只处理一次
4. 金额校验 —— 回调金额与本地订单金额必须一致，防篡改

五、退款管理
1. 退款申请 —— 全额/部分退款，业务方幂等提交
2. 原路退回 —— 调用渠道退款接口，资金退回用户原支付账户
3. 退款回调 —— 渠道退款结果通知，更新退款单状态
4. 退款查询 —— 兜底查询渠道退款状态，自动补单

六、对账与差错
1. 日对账 —— 每日拉取渠道账单，与本地支付/退款记录逐笔核对
2. 差错处理 —— 长款（渠道有本地无）/短款（本地有渠道无）自动标记
3. 差错工单 —— 差错记录进入人工处理队列，处理后销账
4. 对账报表 —— 对账结果日报，财务导出留档

七、平台管理
1. 支付单查询 —— 全渠道支付/退款单检索，操作日志审计
2. 支付统计 —— 支付成功率、渠道占比、退款率大盘
3. 限流与风控 —— 单商户频率限制、大额订单二次确认
```

## 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 开发框架 | Spring Boot 2.7/3.x | 生态成熟，回调接口与定时任务支持完善 |
| 持久层 | MyBatis-Plus | 支付单/退款单/对账记录标准单表 CRUD |
| 数据库 | MySQL 8.0 | 资金数据强一致存储，事务是硬要求 |
| 缓存 | Redis | 幂等标记、防重放 nonce、分布式锁、渠道凭据缓存 |
| 支付 SDK | alipay-sdk-java / wechatpay-java | 官方 SDK 封装了签名与报文解析 |
| 加密工具 | Hutool / BouncyCastle | 签名、摘要、Base64、RSA 工具集 |
| 定时任务 | XXL-Job | 日对账、超时关单、退款补单等批量任务调度 |
| 前端 | Vue 3 + Element Plus | 管理后台与商户工作台 |
| 构建 | Maven | 依赖管理标准工具 |

选型说明：

```text
1. 官方 SDK 而非自己写 HTTP：支付渠道的签名、加密、报文格式经常变，官方 SDK 及时跟进
2. 回调验签用官方验签工具类，但验签后的业务校验（金额、订单号、商户号）必须自己写，一条都不能省
3. Redis 承担幂等：回调处理前 SET NX 一个 process key，天然去重；退款同理
4. 对账必须独立于业务：对账任务与支付流程解耦，即使支付代码有 bug，对账也能发现
```

## 架构设计

系统分层与请求链路：

```text
┌─────────────────────────────────────────────────────────────┐
│  业务方（电商/APP/SaaS）        用户（扫码/跳转/拉起支付）      │
└──────────────┬──────────────────────────────┬──────────────┘
               │ 统一下单/退款 API             │ 用户支付
┌──────────────▼──────────────────────────────▼──────────────┐
│                    Spring Boot 支付应用层                    │
│  ┌───────────┐  ┌───────────┐  ┌───────────┐ ┌──────────┐  │
│  │ 商户接入   │  │ 支付服务   │  │ 回调处理   │ │ 退款服务  │  │
│  │ (签名校验) │  │ (下单/路由)│  │ (验签幂等) │ │ (原路退回)│  │
│  └───────────┘  └───────────┘  └───────────┘ └──────────┘  │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ 渠道适配层：AlipayChannel / WechatChannel（策略工厂） │    │
│  └─────────────────────────────────────────────────────┘    │
└───────┬────────────────┬───────────────┬────────────────────┘
        │                │               │
┌───────▼───────┐  ┌─────▼──────┐  ┌─────▼─────────────────────┐
│    MySQL      │  │   Redis    │  │ 支付渠道（异步通知回调）     │
│ 支付单/退款单/ │  │ 幂等标记/锁 │  │ 支付宝  /  微信支付         │
│ 对账/商户表    │  │ nonce 防重放│  │ (异步通知 -> 本系统回调接口) │
└───────────────┘  └────────────┘  └───────────────────────────┘
```

支付回调处理链路（渠道异步通知 → 订单状态更新）：

```text
1. 支付宝/微信服务器向回调接口 POST 通知报文（明文参数 + 签名）
2. Controller 接收原始报文，不解析直接交给验签服务
3. 验签服务用渠道公钥验证签名（支付宝 RSA2 / 微信平台证书），失败直接拒绝
4. 验签通过后解析报文，校验关键字段：商户号、订单号、金额、状态
5. 金额校验：渠道返回金额与本地 pay_order 金额 compareTo 必须为 0，不一致记差错并告警
6. 幂等处理：Redis SET NX process:{orderNo}，获取不到说明正在处理或已处理
7. 事务内更新支付单状态为已支付，写入支付时间，通知业务方（MQ 或回调业务系统）
8. 返回「SUCCESS」给渠道；返回其他内容渠道会按策略重试
```

Redis Key 设计：

```text
1. pay:process:{payOrderNo}       回调幂等标记（SET NX EX 120s），存在即已处理/处理中
2. refund:process:{refundNo}      退款回调幂等标记，同上
3. pay:nonce:{channel}:{nonce}    回调防重放：nonce 已消费则拒绝（TTL 1 小时）
4. pay:order:{payOrderNo}         支付单缓存（高频查询），TTL 10 分钟，状态变更即删
5. lock:refund:{payOrderNo}       同一支付单并发退款分布式锁
6. lock:settle:{date}:{channel}   日对账任务分布式锁，防止多实例重复拉单
7. pay:close:queue                待关闭的过期支付单（ZSet，score=过期时间戳），定时扫描
8. rate:merchant:{merchantId}     商户接口调用限流计数器（滑动窗口）
```

## 核心实现

### 1. 统一下单（渠道路由 + 支付发起）

```java
@Service
public class PayOrderService {

    @Autowired
    private PayOrderMapper payOrderMapper;
    @Autowired
    private MerchantMapper merchantMapper;
    @Autowired
    private PayChannelFactory channelFactory;

    /**
     * 统一下单：创建支付单并调用渠道生成支付参数
     * 返回结果按渠道区分：支付宝为 qrCode/form，微信为 codeUrl/jsapi 参数
     */
    @Transactional(rollbackFor = Exception.class)
    public PayResult createOrder(PayCreateDTO dto) {
        // 1. 校验商户状态
        Merchant merchant = merchantMapper.selectById(dto.getMerchantId());
        if (merchant == null || merchant.getStatus() != 1) {
            throw new BusinessException("商户不存在或已冻结");
        }
        // 2. 幂等校验：同一业务订单号只允许存在一笔有效支付单
        Long exist = payOrderMapper.selectCount(new LambdaQueryWrapper<PayOrder>()
                .eq(PayOrder::getMerchantId, dto.getMerchantId())
                .eq(PayOrder::getBizOrderNo, dto.getBizOrderNo())
                .in(PayOrder::getStatus, 0, 1));
        if (exist != null && exist > 0) {
            throw new BusinessException("该业务订单已存在进行中的支付单");
        }
        // 3. 创建支付单（状态待支付，带过期时间）
        PayOrder order = new PayOrder();
        order.setPayOrderNo(genPayOrderNo());   // PAY + 年月日 + 序号
        order.setMerchantId(merchant.getId());
        order.setBizOrderNo(dto.getBizOrderNo());
        order.setChannel(dto.getChannel());
        order.setAmount(dto.getAmount());
        order.setStatus(0);
        order.setExpireTime(LocalDateTime.now().plusMinutes(15));
        payOrderMapper.insert(order);
        // 4. 按渠道路由到适配器发起支付
        PayChannel channel = channelFactory.getChannel(dto.getChannel());
        ChannelPayResult channelResult = channel.precreate(order, merchant);
        // 5. 回填渠道返回的支付参数并返回
        return new PayResult(order.getPayOrderNo(), channelResult.getPayParams());
    }

    /**
     * 主动查询渠道支付状态（兜底：回调丢失时业务方查单）
     * 查到已支付则走与回调相同的状态更新逻辑（复用，保证路径一致）
     */
    public void queryPayStatus(String payOrderNo) {
        PayOrder order = payOrderMapper.selectOne(
                new LambdaQueryWrapper<PayOrder>().eq(PayOrder::getPayOrderNo, payOrderNo));
        if (order == null || order.getStatus() != 0) {
            return;
        }
        Merchant merchant = merchantMapper.selectById(order.getMerchantId());
        PayChannel channel = channelFactory.getChannel(order.getChannel());
        ChannelQueryResult result = channel.query(order, merchant);
        if (result.isPaid()) {
            processPaid(order, result.getChannelTradeNo(), result.getPaidTime());
        }
    }
}
```

```java
@Service
public class PayNotifyService {

    @Autowired
    private PayOrderMapper payOrderMapper;
    @Autowired
    private PayNotifyMapper notifyMapper;
    @Autowired
    private MerchantMapper merchantMapper;
    @Autowired
    private PayChannelFactory channelFactory;
    @Autowired
    private StringRedisTemplate stringRedisTemplate;

    private static final String PROCESS_KEY = "pay:process:";

    /**
     * 回调统一处理（支付宝示例）
     * 四道防线：验签 -> 业务字段校验 -> 金额校验 -> 幂等
     */
    public boolean handleNotify(int channel, Map<String, String> params) {
        String payOrderNo = params.get("out_trade_no");
        String tradeNo = params.get("trade_no");     // 渠道交易号
        String amount = params.get("total_amount");
        String tradeStatus = params.get("trade_status");
        String sign = params.get("sign");
        // 1. 记录原始报文（审计留痕）
        PayNotify record = new PayNotify();
        record.setPayOrderNo(payOrderNo);
        record.setChannel(channel);
        record.setNotifyBody(JSON.toJSONString(params));
        record.setSign(sign);
        notifyMapper.insert(record);

        // 2. 验签：失败直接拒绝
        PayOrder order = payOrderMapper.selectOne(new LambdaQueryWrapper<PayOrder>()
                .eq(PayOrder::getPayOrderNo, payOrderNo));
        if (order == null) {
            record.setVerifyResult(0);
            notifyMapper.updateById(record);
            return false;
        }
        Merchant merchant = merchantMapper.selectById(order.getMerchantId());
        PayChannel payChannel = channelFactory.getChannel(channel);
        if (!payChannel.verifyNotify(JSON.toJSONString(params), sign, merchant)) {
            record.setVerifyResult(0);
            notifyMapper.updateById(record);
            log.warn("回调验签失败: {}", payOrderNo);
            return false;
        }
        record.setVerifyResult(1);
        notifyMapper.updateById(record);

        // 3. 幂等：SET NX 拿不到锁说明这笔单正在处理或已处理过
        Boolean first = stringRedisTemplate.opsForValue()
                .setIfAbsent(PROCESS_KEY + payOrderNo, "1", Duration.ofMinutes(2));
        if (!Boolean.TRUE.equals(first)) {
            record.setProcessResult(2);   // 重复通知
            notifyMapper.updateById(record);
            return true;                  // 已处理过，返回成功让渠道停止重试
        }
        try {
            // 4. 金额校验：渠道金额与本地金额必须一致（防篡改核心）
            if (new BigDecimal(amount).compareTo(order.getAmount()) != 0) {
                log.error("回调金额不一致: order={}, channel={}, local={}",
                        payOrderNo, amount, order.getAmount());
                return false;
            }
            // 5. 仅处理待支付单；已支付单直接幂等返回
            if (order.getStatus() == 0 && "TRADE_SUCCESS".equals(tradeStatus)) {
                processPaid(order, tradeNo);
            }
            record.setProcessResult(1);
            notifyMapper.updateById(record);
            return true;
        } finally {
            stringRedisTemplate.delete(PROCESS_KEY + payOrderNo);
        }
    }

    /**
     * 支付成功落库：状态流转 + 通知业务方
     * 用条件更新保证并发下只有一个线程能把 0->1
     */
    @Transactional(rollbackFor = Exception.class)
    public void processPaid(PayOrder order, String channelTradeNo) {
        int rows = payOrderMapper.updatePaid(order.getPayOrderNo(),
                channelTradeNo, LocalDateTime.now());
        if (rows == 0) {
            return;   // 已被其他路径处理，幂等返回
        }
        // 通知业务方（电商订单状态流转），MQ 异步发送
        notifyBiz(order);
    }
}
```

### 4. 退款（原路退回 + 幂等）

```java
@Service
public class RefundService {

    @Autowired
    private PayRefundMapper refundMapper;
    @Autowired
    private PayOrderMapper payOrderMapper;
    @Autowired
    private MerchantMapper merchantMapper;
    @Autowired
    private PayChannelFactory channelFactory;
    @Autowired
    private StringRedisTemplate stringRedisTemplate;

    private static final String REFUND_LOCK = "lock:refund:";

    /**
     * 发起退款：校验退款金额不超过已支付金额，调用渠道原路退回
     * 幂等：同一 bizRefundNo 只允许建一笔退款单
     */
    @Transactional(rollbackFor = Exception.class)
    public String applyRefund(RefundCreateDTO dto) {
        // 1. 幂等：业务方退款号唯一
        Long exist = refundMapper.selectCount(new LambdaQueryWrapper<PayRefund>()
                .eq(PayRefund::getBizRefundNo, dto.getBizRefundNo()));
        if (exist != null && exist > 0) {
            throw new BusinessException("退款单已存在，请勿重复提交");
        }
        PayOrder order = payOrderMapper.selectOne(new LambdaQueryWrapper<PayOrder>()
                .eq(PayOrder::getPayOrderNo, dto.getPayOrderNo()));
        if (order == null || order.getStatus() != 1) {
            throw new BusinessException("支付单不存在或未支付成功");
        }
        // 2. 累计已退金额校验：总退款不能超过实付
        BigDecimal refunded = refundMapper.sumRefunded(dto.getPayOrderNo(), 1);
        BigDecimal totalRefund = (refunded == null ? BigDecimal.ZERO : refunded)
                .add(dto.getRefundAmount());
        if (totalRefund.compareTo(order.getAmount()) > 0) {
            throw new BusinessException("累计退款金额超过支付金额");
        }
        // 3. 创建退款单（处理中）
        PayRefund refund = new PayRefund();
        refund.setRefundNo(genRefundNo());   // RFD + 年月日 + 序号
        refund.setPayOrderNo(order.getPayOrderNo());
        refund.setBizRefundNo(dto.getBizRefundNo());
        refund.setMerchantId(order.getMerchantId());
        refund.setRefundAmount(dto.getRefundAmount());
        refund.setRefundReason(dto.getRefundReason());
        refund.setStatus(0);
        refundMapper.insert(refund);

        // 4. 加锁防同一支付单并发退款（同一单多笔退款要串行）
        String lockKey = REFUND_LOCK + order.getPayOrderNo();
        Boolean locked = stringRedisTemplate.opsForValue()
                .setIfAbsent(lockKey, "1", Duration.ofSeconds(30));
        if (!Boolean.TRUE.equals(locked)) {
            throw new BusinessException("该订单正在退款处理中");
        }
        try {
            // 5. 调用渠道退款（原路退回）
            Merchant merchant = merchantMapper.selectById(order.getMerchantId());
            PayChannel channel = channelFactory.getChannel(order.getChannel());
            ChannelRefundResult result = channel.refund(refund, merchant);
            refund.setChannelRefundNo(result.getChannelRefundNo());
            refundMapper.updateById(refund);
            return refund.getRefundNo();
        } finally {
            stringRedisTemplate.delete(lockKey);
        }
    }

    /**
     * 退款结果处理（渠道退款回调/主动查询共用）
     * 只有「处理中」状态的退款单才能流转到成功，天然幂等
     */
    @Transactional(rollbackFor = Exception.class)
    public void handleRefundResult(String refundNo, boolean success) {
        int rows = refundMapper.updateResult(refundNo,
                success ? 1 : 2, LocalDateTime.now());
        if (rows == 0) {
            return;   // 状态已流转，幂等
        }
        if (success) {
            // 退款成功后：支付单累计退款等于实付金额则置为已退款
            refundMapper.updatePayOrderRefundedStatus(refundNo);
        }
    }
}
```

### 5. 日对账（拉单 + 逐笔核对 + 差错标记）

```java
@Service
public class ReconciliationService {

    @Autowired
    private SettleBillMapper billMapper;
    @Autowired
    private SettleDetailMapper detailMapper;
    @Autowired
    private PayOrderMapper payOrderMapper;
    @Autowired
    private StringRedisTemplate stringRedisTemplate;

    private static final String SETTLE_LOCK = "lock:settle:";

    /**
     * 日对账主流程（定时任务每日凌晨触发）
     * 步骤：下载渠道账单 -> 解析 -> 逐笔与本地比对 -> 标记差错
     */
    public void dailyReconcile(LocalDate billDate, int channel, Long merchantId) {
        String lockKey = SETTLE_LOCK + billDate + ":" + channel + ":" + merchantId;
        Boolean locked = stringRedisTemplate.opsForValue()
                .setIfAbsent(lockKey, "1", Duration.ofHours(2));
        if (!Boolean.TRUE.equals(locked)) {
            return;   // 其他实例正在对账
        }
        try {
            // 1. 幂等：当天已对账完成直接跳过
            SettleBill bill = billMapper.selectOne(new LambdaQueryWrapper<SettleBill>()
                    .eq(SettleBill::getBillDate, billDate)
                    .eq(SettleBill::getChannel, channel)
                    .eq(SettleBill::getMerchantId, merchantId));
            if (bill != null && bill.getStatus() == 3) {
                return;
            }
            if (bill == null) {
                bill = new SettleBill();
                bill.setBillDate(billDate);
                bill.setChannel(channel);
                bill.setMerchantId(merchantId);
                bill.setStatus(1);
                billMapper.insert(bill);
            }
            // 2. 下载并解析渠道账单（支付宝账单为 CSV，微信为加密文件）
            List<BillLine> lines = downloadAndParse(bill, billDate, channel);
            bill.setTotalCount(lines.size());
            bill.setTotalAmount(lines.stream()
                    .map(BillLine::getAmount).reduce(BigDecimal.ZERO, BigDecimal::add));
            bill.setStatus(2);
            billMapper.updateById(bill);

            // 3. 逐笔核对
            int match = 0;
            int diff = 0;
            for (BillLine line : lines) {
                SettleDetail detail = compare(line, bill.getId());
                if (detail.getDiffType() == 0) {
                    match++;
                } else {
                    diff++;
                    log.warn("对账差错: {} 类型={}", line.getBizNo(), detail.getDiffType());
                }
                detailMapper.insert(detail);
            }
            // 4. 补查「本地有、渠道无」的短款：本地当天支付成功但账单里没有
            diff += checkLocalMissing(bill.getId(), billDate, channel, merchantId);
            bill.setMatchCount(match);
            bill.setDiffCount(diff);
            bill.setStatus(3);
            billMapper.updateById(bill);
        } finally {
            stringRedisTemplate.delete(lockKey);
        }
    }

    /**
     * 单笔核对：渠道记录 vs 本地记录
     * diffType：0 一致 / 1 长款（渠道有本地无）/ 2 短款（本地有渠道无）/ 3 金额不符
     */
    private SettleDetail compare(BillLine line, Long billId) {
        SettleDetail detail = new SettleDetail();
        detail.setBillId(billId);
        detail.setBizNo(line.getBizNo());
        detail.setChannelTradeNo(line.getChannelTradeNo());
        detail.setChannelAmount(line.getAmount());
        detail.setBizType(line.getBizType());

        if (line.getBizType() == 1) {
            // 支付核对：按平台支付单号找本地记录
            PayOrder order = payOrderMapper.selectOne(
                    new LambdaQueryWrapper<PayOrder>()
                            .eq(PayOrder::getPayOrderNo, line.getBizNo()));
            if (order == null) {
                detail.setDiffType(1);   // 长款：渠道有、本地无
            } else if (order.getAmount().compareTo(line.getAmount()) != 0) {
                detail.setDiffType(3);   // 金额不符
                detail.setLocalAmount(order.getAmount());
            } else {
                detail.setLocalAmount(order.getAmount());
                detail.setDiffType(0);   // 一致
            }
        }
        // 退款核对逻辑类似：按退款单号找本地 pay_refund 记录
        return detail;
    }
}
```

### 6. 商户接入签名工具（业务方调用 API 的签名校验）

```java
@Component
public class MerchantSignUtil {

    /**
     * 业务方调用支付/退款接口时的签名规则：
     * 参数按 key 字典序拼接 + appKey + 时间戳 + nonce，MD5 摘要
     * 服务端用商户 appSecret 重算比对，防篡改、防重放
     */
    public String sign(Map<String, String> params, String appSecret) {
        String content = params.entrySet().stream()
                .filter(e -> e.getValue() != null && !e.getValue().isEmpty())
                .sorted(Map.Entry.comparingByKey())
                .map(e -> e.getKey() + "=" + e.getValue())
                .collect(Collectors.joining("&"));
        String raw = content + "&key=" + appSecret;
        return DigestUtils.md5Hex(raw).toUpperCase();
    }

    /**
     * 服务端验签 + 防重放
     * timestamp 超过 5 分钟拒绝；nonce 在 Redis 中已存在则拒绝（重放）
     */
    public boolean verify(Map<String, String> params, String appSecret,
                          StringRedisTemplate redis) {
        String sign = params.get("sign");
        String timestamp = params.get("timestamp");
        String nonce = params.get("nonce");
        // 1. 时间窗校验
        long diff = Math.abs(System.currentTimeMillis() - Long.parseLong(timestamp));
        if (diff > 5 * 60 * 1000L) {
            return false;
        }
        // 2. nonce 防重放（同一签名参数只允许用一次）
        Boolean first = redis.opsForValue()
                .setIfAbsent("pay:nonce:api:" + nonce, "1", Duration.ofHours(1));
        if (!Boolean.TRUE.equals(first)) {
            return false;
        }
        // 3. 重算签名比对
        return sign.equals(sign(params, appSecret));
    }
}
```

## 实际应用场景

### 场景一：电商平台接入支付（支付宝当面付 + 微信 Native）

某电商平台上线支付功能，用户扫码支付订单：

```text
1. 平台注册商户，配置支付宝 appId/密钥与微信 mchId/证书，渠道信息加密入库
2. 用户提交订单，业务系统调用统一下单接口，生成平台支付单（待支付，15 分钟过期）
3. 系统按用户端类型路由：PC 端生成支付宝二维码，小程序端拉起微信 JSAPI 支付
4. 用户扫码付款，渠道异步通知回调，验签通过后订单状态流转为已支付
5. 业务方收到 MQ 通知，把电商订单置为已支付并触发仓库发货
6. 用户申请退款，退款单走渠道原路退回，用户 1-3 个工作日到账
7. 次日凌晨定时任务拉取渠道账单日对账，财务确认无差错
```

### 场景二：SaaS 平台的商户聚合支付（多商户模式）

SaaS 平台下挂几百个小商户，平台统一收款、按商户分账：

```text
1. 每个子商户入驻：生成 appKey/appSecret，配置自己的渠道收款信息
2. 子商户调用平台统一 API（签名 + nonce 防重放），完成下单支付
3. 平台按 merchant_id 隔离数据：各商户只能查自己的账单与退款
4. 日对账按「日期 + 渠道 + 商户」三维度跑任务，差错自动生成工单
5. 财务在后台看对账日报，长款单人工核实后销账，短款单发起渠道补查
6. 商户密钥定期轮换，旧密钥宽限期后强制失效
7. 平台按商户维度统计支付成功率与退款率，异常商户触发风控冻结
```

### 场景三：内容知识付费的会员订阅续费

知识付费平台卖会员，用户支付成功自动开通权益：

```text
1. 用户购买年费会员，业务侧创建支付单并跳转支付宝收银台
2. 支付成功回调后，系统幂等处理并通知业务系统开通会员权益
3. 回调因网络原因延迟 2 小时到达，期间用户反复点「开通」：幂等锁保证只开通一次
4. 用户支付成功但权益未到账，客服查 pay_notify 表定位：回调已验签成功，业务通知 MQ 消费失败，重试后到账
5. 月末财务对账：渠道账单显示 500 笔成功，本地 498 笔已支付，2 笔差错定位为超时关单后被支付，人工补单
6. 用户申请退款，退款单创建后渠道处理中，渠道回调确认后退款成功，权益同步回收
```

## 最佳实践与踩坑记录

### 最佳实践

1. 验签是回调的第一道门：渠道公钥（平台证书）必须安全存储，验签失败直接拒绝并记录日志，绝不能跳过
2. 回调业务处理必须幂等：Redis SET NX + 数据库条件更新（WHERE status = 0）双保险，重复通知只生效一次
3. 金额校验不能省：回调金额必须与本地支付单金额 compareTo 相等，这是防篡改的最后一道防线
4. 渠道适配层（策略工厂）隔离 SDK：业务代码只依赖 PayChannel 接口，新增渠道不改业务
5. 主动查单兜底：回调可能丢失，定时任务 + 业务方查单接口双通道，保证最终一致
6. 退款必须「先建单、后调渠道」：退款单落库（处理中）再调渠道，渠道结果回来更新状态，全程可追溯
7. 对账独立于业务链路：即使支付代码有 bug，日对账也能发现差错，对账逻辑越简单越好，别搞复杂规则

### 踩坑记录

```text
坑 1：验签跳过导致被刷单
结论：攻击者构造假回调报文，系统直接发货。
原因：开发时图省事把验签代码注释掉了，以为内网环境不需要。
解法：验签写死在回调入口，不允许通过配置关闭；上线前用渠道沙箱 + 伪造报文
     做安全测试；pay_notify 表验签失败记录留痕，告警监控。

坑 2：回调重复处理导致订单金额翻倍入账
结论：用户付一次钱，系统记了两次支付。
原因：渠道重试通知到达时，上一笔事务还没提交完，应用层幂等锁没拦住，
     状态判断读到旧值。
解法：应用层锁 + 数据库条件更新（UPDATE ... WHERE status = 0）双保险；
     受影响行数为 0 说明已处理，直接返回成功。

坑 3：回调金额被篡改没发现
结论：用户改报文金额支付 1 分钱，系统按全价发货。
原因：只验签没校验金额，攻击者用自己的签名密钥重放报文。
解法：验签通过后必须校验 out_trade_no、total_amount、merchant_id 与本地支付单
     完全一致，任一不符记差错并拒绝。

坑 4：退款重复提交
结论：同一笔订单退了两次款，用户收到双倍退款。
原因：退款接口没有幂等，客服手抖点了两次。
解法：业务方退款号（biz_refund_no）唯一索引强制幂等；同一支付单加分布式锁
     串行退款；退款前校验「累计已退 + 本次 <= 实付金额」。

坑 5：对账发现大量长款
结论：渠道账单有的交易，本地系统查无此单。
原因：支付单超时自动关闭后用户仍支付成功，回调时订单已关闭被直接忽略。
解法：超时关单前先查一次渠道状态，确认未支付才关；关闭后到达的成功回调
     进入「补单流程」：重新建立支付单或标记异常人工处理。

坑 6：微信回调解密失败
结论：微信支付回调一直报签名/解密错误。
原因：回调报文是 AES-256-GCM 加密的，直接用明文解析。
解法：微信渠道用官方 wechatpay-java 的 NotificationParser 解密后再验签；
     调试时把原始 body 完整记录到 pay_notify 表，方便排查。

坑 7：对账任务多实例重复执行
结论：同一天的对账跑了三遍，账单重复入库。
原因：定时任务在多台服务器都触发了，没有分布式锁。
解法：对账任务加 Redis 分布式锁 + settle_bill 表唯一索引（日期+渠道+商户）
     双保险；状态为「已完成」的直接跳过。
```
