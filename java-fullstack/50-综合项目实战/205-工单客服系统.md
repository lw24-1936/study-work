## 项目背景

工单客服系统是企业服务客户的标准入口：客户提交问题，坐席受理处理，全程可追踪、有时效承诺（SLA）、有满意度闭环。选它做综合实战项目，是因为它是「业务规则密集」型系统的代表：状态机流转、智能分派、SLA 时效、多渠道接入、统计报表，几乎覆盖了企业级后台系统的全部典型设计手法。技术栈以 Spring Boot + MySQL + Redis 为主干，状态机管流转、定时任务管 SLA、Redis 管待办计数与提醒去重。

业务痛点：

```text
1. 客户问题散落在电话、邮件、微信群，没有统一入口，问题容易漏处理
2. 工单状态靠口头交接，处理到哪一步没人说得清，客户反复催单
3. 紧急问题没有时效保障：高优先级工单和普通工单一样排队，客户流失
4. 分派靠人工点名：忙的人更忙、闲的人更闲，响应速度不稳定
5. 处理过程无记录：内部沟通和客户回复混在一起，事后追溯无据可查
6. 服务质量无法度量：没有首次响应时长、解决时长、满意度数据，改进无方向
```

目标用户与核心诉求：

```text
1. 客户：多渠道提交问题、随时查看处理进度、回复补充材料、处理完给评价
2. 坐席：待办列表清晰、SLA 提醒及时、内部备注与客户回复分开、沟通记录完整
3. 组长/管理员：技能组分派、超时升级干预、统计报表（响应时长/解决率/满意度）
```

项目要解决的核心问题一句话概括：让每个客户问题都有唯一工单号、清晰状态、明确责任人、可量化的时效承诺和可追溯的处理记录。

## 功能介绍

功能按角色拆成三个端：客户自助端、坐席工作台、管理后台。

```text
一、客户自助端（客户视角）
1. 提交工单 —— 网页/App 填写标题与问题描述，选择问题类型与优先级
2. 进度查询 —— 凭工单号+手机号查看状态流转历史与处理回复
3. 补充回复 —— 待补充状态下的工单可追加材料与说明
4. 满意度评价 —— 工单解决后打分（1-5 星）+ 评价内容

二、坐席工作台（坐席视角）
1. 待办列表 —— 我的工单（新建/处理中/待补充），按优先级与 SLA 剩余时间排序
2. 工单处理 —— 受理、请求补充、标记解决、关闭，全程状态机校验
3. 沟通记录 —— 客户可见的回复与内部备注分开，支持 @同事
4. 转派 —— 处理不了转给同技能组其他坐席或组长
5. SLA 提醒 —— 接近/超过时限的工单高亮 + 站内信提醒

三、管理后台（组长/管理员视角）
1. 智能分派 —— 按技能组匹配 + 坐席负载最低自动分派
2. 技能组管理 —— 售后组/技术组/投诉组，坐席归属维护
3. SLA 规则 —— 按优先级配置首次响应时限与解决时限，超时自动升级
4. 超时干预 —— 升级到组长/经理，督办入口
5. 统计报表 —— 按状态/优先级/坐席/渠道统计，响应时长与解决率排行
6. 满意度分析 —— 低分工单回访清单，评价分布趋势
```

## 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 开发框架 | Spring Boot 2.7/3.x | 生态成熟，@Scheduled 定时任务开箱即用 |
| 数据库 | MySQL 8.0 | 工单、客户、坐席、流转日志、SLA 规则落库 |
| 缓存 | Redis | 待办计数、未读数、提醒去重、超时大屏实时计数 |
| 状态机 | 自研轻量状态机（枚举 + 流转表） | 工单状态有限且固定，自研比引入框架更轻更可控 |
| 定时任务 | Spring @Scheduled + 分布式锁 | 每分钟扫描 SLA 超时工单；多实例部署加锁防重复扫描 |
| 消息通知 | 站内信（Redis List）+ 短信/邮件（模板） | 通知通道解耦，失败不阻塞主流程 |
| 鉴权 | Spring Security + JWT | 客户端与坐席端两套认证体系 |
| 前端 | Vue 3 + Element Plus | 工单表格、流转时间线组件成熟 |
| 构建 | Maven | 依赖管理标准工具 |

选型说明：

```text
1. 状态机自研而非 Flowable：工单流转只有 5 个状态、8 类动作，用枚举 + 流转矩阵最直观；
   若未来要做审批流、多级会签再平滑迁移 Flowable（见相关文档）
2. SLA 扫描用 Spring 定时任务 + Redis 分布式锁：单机先跑，多实例部署时抢锁防重复提醒
3. Redis 管三类计数：坐席待办数（分派用）、工单未读数（工作台角标）、超时工单数（大屏）
4. 分派策略「技能组 + 负载最低」不需要规则引擎：负载取 Redis 计数，冷启动查库兜底
```

## 架构设计

系统分层与工单生命周期：

```text
┌──────────────────────────────────────────────────────────────┐
│                   客户端（客户/坐席/管理员）                     │
│   网页客服中心   电话/邮件接入    坐席工作台    管理后台/大屏     │
└───────────────┬──────────────────────────────────────────────┘
                │ 多渠道接入（网页/电话/邮件/APP）
┌───────────────▼──────────────────────────────────────────────┐
│                      Spring Boot 应用层                       │
│  ┌─────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────────┐  │
│  │Controller│ │TicketSvc │ │ 状态机    │ │ SlaScanTask 定时 │  │
│  └─────────┘ └──────────┘ └──────────┘ └──────────────────┘  │
└───────┬──────────────────┬──────────────────┬────────────────┘
        │                  │                  │
┌───────▼───────┐  ┌───────▼────────┐  ┌──────▼──────────────┐
│     MySQL     │  │     Redis      │  │   通知通道（外部）     │
│ 工单/客户/坐席/ │  │ 待办计数/未读数/ │  │ 站内信/短信/邮件/企微  │
│ 流转日志/SLA   │  │ 提醒去重/大屏   │  │                    │
└───────────────┘  └────────────────┘  └─────────────────────┘
```

工单全生命周期链路：

```text
1. 客户通过网页/电话/邮件提交问题，系统按渠道生成工单，状态=新建，分配业务编号
2. 分派服务按问题类型匹配技能组，组内选在线且负载最低的坐席，坐席待办计数 +1
3. 坐席点开工单受理：新建 -> 处理中，记录首次响应时间（SLA 计时停止）
4. 需要客户补充材料：处理中 -> 待补充，通知客户；客户回复后自动回到处理中
5. 问题解决：处理中 -> 已解决，记录解决时间，邀请客户评价
6. 客户确认并打分：已解决 -> 已关闭；客户不满意则重新打开回到处理中
7. 全程每个流转写操作日志；SLA 定时任务每分钟扫描，超时工单提醒并升级组长/经理
```

SLA 超时扫描链路：

```text
1. 工单创建/分派时按优先级从 sla_rule 计算两个截止时间：首响截止、解决截止
2. SlaScanTask 每 60 秒扫描：已分派未首响且超过首响截止 -> 首响超时
3. 处理中/待补充且超过解决截止 -> 解决超时
4. 超时工单先过 Redis Set 去重（同一工单只提醒一次）
5. 站内信推给处理人，短信/邮件升级到组长与经理
6. 超时工单总数写入 Redis，管理大屏实时展示
```

## 核心实现

### 1. 状态机：流转校验矩阵

```java
/**
 * 工单状态与事件定义
 * 状态：1新建 2处理中 3待补充 4已解决 5已关闭
 */
public enum TicketEvent {
    ASSIGN,          // 分派
    ACCEPT,          // 受理（首次响应）
    REQUEST_INFO,    // 请求补充
    SUPPLY_INFO,     // 客户补充信息
    RESOLVE,         // 标记解决
    REOPEN,          // 重新打开（客户不满意）
    CONFIRM_CLOSE,   // 客户确认关闭
    FORCE_CLOSE      // 强制关闭（超时/管理员）
}

@Component
public class TicketStateMachine {

    // 合法流转表：fromStatus -> 允许的 toStatus 集合
    private static final Map<Integer, Set<Integer>> TRANSITIONS = new HashMap<>();

    static {
        TRANSITIONS.put(1, new HashSet<>(Arrays.asList(2, 5)));    // 新建 -> 处理中/已关闭
        TRANSITIONS.put(2, new HashSet<>(Arrays.asList(3, 4, 5))); // 处理中 -> 待补充/已解决/已关闭
        TRANSITIONS.put(3, new HashSet<>(Arrays.asList(2, 5)));    // 待补充 -> 处理中/已关闭
        TRANSITIONS.put(4, new HashSet<>(Arrays.asList(2, 5)));    // 已解决 -> 处理中(重开)/已关闭
        TRANSITIONS.put(5, Collections.emptySet());                // 已关闭为终态
    }

    /**
     * 校验流转是否合法：非法流转直接抛业务异常
     * 所有状态变更必须经过本方法，杜绝绕过状态机的直接 UPDATE
     */
    public void check(Integer from, Integer to, String action) {
        if (from == null) {
            return;  // 初始创建
        }
        Set<Integer> allowed = TRANSITIONS.getOrDefault(from, Collections.emptySet());
        if (!allowed.contains(to)) {
            throw new BizException(String.format(
                    "非法流转：状态 %s 不能流转到 %s（动作 %s）", from, to, action));
        }
    }

    /** 事件到目标状态的映射 */
    public Integer targetStatus(TicketEvent event) {
        switch (event) {
            case ACCEPT:        return 2;  // 受理进入处理中
            case REQUEST_INFO:  return 3;  // 请求补充进入待补充
            case SUPPLY_INFO:   return 2;  // 客户补充后回到处理中
            case RESOLVE:       return 4;  // 解决
            case REOPEN:        return 2;  // 重开回到处理中
            case CONFIRM_CLOSE:
            case FORCE_CLOSE:   return 5;  // 关闭
            default:            return 2;
        }
    }
}
```

### 2. 工单服务：创建、分派、流转

```java
@Service
public class TicketService {

    @Autowired
    private TicketMapper ticketMapper;
    @Autowired
    private TicketStateMachine stateMachine;
    @Autowired
    private DispatchService dispatchService;
    @Autowired
    private SlaService slaService;
    @Autowired
    private NotificationService notificationService;
    @Autowired
    private OperationLogMapper operationLogMapper;

    /**
     * 创建工单（多渠道入口统一走这里）：落库 -> 分派 -> 算 SLA -> 通知
     */
    @Transactional
    public Ticket create(TicketCreateDTO dto) {
        Ticket ticket = new Ticket();
        ticket.setTicketNo(genTicketNo());          // 业务编号：日期 + 序列
        ticket.setCustomerId(dto.getCustomerId());
        ticket.setTitle(dto.getTitle());
        ticket.setContent(dto.getContent());
        ticket.setChannel(dto.getChannel());
        ticket.setPriority(dto.getPriority());
        ticket.setStatus(1);                        // 新建
        ticketMapper.insert(ticket);
        // 智能分派（未匹配到坐席则留在技能组队列等待人工认领）
        dispatchService.dispatch(ticket);
        // 按优先级计算 SLA 截止时间
        slaService.initDeadline(ticket);
        // 通知技能组：有新工单待处理
        notificationService.notifyNewTicket(ticket);
        return ticket;
    }

    /**
     * 状态流转统一入口：状态机校验 + 权限校验 + 日志 + 通知
     * 所有流转必须走这里，禁止在 Mapper 层直接改 status
     */
    @Transactional
    public void transition(Long ticketId, TicketEvent event, Long operatorId, String remark) {
        Ticket ticket = ticketMapper.selectById(ticketId);
        Integer from = ticket.getStatus();
        Integer to = stateMachine.targetStatus(event);
        // 1. 状态机校验
        stateMachine.check(from, to, event.name());
        // 2. 权限校验：处理人与管理员可流转，客户只能补充/确认/重开
        checkPermission(ticket, event, operatorId);
        // 3. 更新状态与关键时间点
        if (event == TicketEvent.ACCEPT && ticket.getFirstResponseTime() == null) {
            ticket.setFirstResponseTime(new Date());  // 首次响应计时停止
        }
        if (event == TicketEvent.RESOLVE) {
            ticket.setResolveTime(new Date());
        }
        ticket.setStatus(to);
        ticketMapper.updateById(ticket);
        // 4. 流转日志
        operationLogMapper.insert(OperationLog.of(
                ticketId, from, to, event.name(), operatorId, remark));
        // 5. 通知相关方（客户或组长）
        notificationService.notifyStatusChange(ticket, from, to);
    }

    /** 权限校验：坐席/组长/管理员操作自己的工单，客户操作自己的工单 */
    private void checkPermission(Ticket ticket, TicketEvent event, Long operatorId) {
        if (ticket.getCustomerId().equals(operatorId)) {
            // 客户侧允许的动作：SUPPLY_INFO / REOPEN / CONFIRM_CLOSE
            if (event != TicketEvent.SUPPLY_INFO
                    && event != TicketEvent.REOPEN
                    && event != TicketEvent.CONFIRM_CLOSE) {
                throw new BizException("客户无权执行该操作");
            }
            return;
        }
        // 坐席侧：只能操作分派给自己的工单
        if (!ticket.getAssigneeId().equals(operatorId)
                && !isManagerOrLeader(operatorId)) {
            throw new BizException("该工单不属于当前处理人");
        }
    }

    /** 生成业务编号：20260819 + 6 位序列 */
    private String genTicketNo() {
        return "TK" + new SimpleDateFormat("yyyyMMdd").format(new Date())
                + String.format("%06d", ticketMapper.countToday() + 1);
    }
}
```

### 3. 智能分派：技能组匹配 + 负载最低

```java
@Service
public class DispatchService {

    @Autowired
    private SupportUserMapper supportUserMapper;
    @Autowired
    private TicketMapper ticketMapper;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    /**
     * 智能分派三步：
     * 1. 按问题类型/渠道匹配技能组（简化：按优先级映射，生产可按关键词配置）
     * 2. 组内过滤在线坐席
     * 3. 选当前待办数最少的人（负载均衡）
     */
    public SupportUser dispatch(Ticket ticket) {
        Long groupId = matchGroup(ticket);
        if (groupId == null) {
            return null;  // 无匹配技能组，留在队列等人认领
        }
        ticket.setSkillGroupId(groupId);
        // 在线 + 组内坐席，按负载升序取第一个
        List<SupportUser> candidates = supportUserMapper.selectOnlineByGroup(groupId);
        SupportUser best = candidates.stream()
                .min(Comparator.comparingInt(u -> currentLoad(u.getId())))
                .orElse(null);
        if (best != null) {
            ticket.setAssigneeId(best.getId());
            ticketMapper.updateById(ticket);
            // 待办计数 +1（Redis，分派与计数同事务思想，此处简化）
            redisTemplate.opsForHash().increment("ticket:todo:count",
                    best.getId().toString(), 1);
        }
        return best;
    }

    /**
     * 当前负载：Redis 计数优先（实时），冷数据查库兜底
     * 负载 = 新建 + 处理中 + 待补充的工单数
     */
    private int currentLoad(Long userId) {
        Object c = redisTemplate.opsForHash().get("ticket:todo:count", userId.toString());
        if (c != null) {
            return Integer.parseInt(c.toString());
        }
        return ticketMapper.countByAssigneeAndStatuses(userId,
                Arrays.asList(1, 2, 3));
    }

    /** 技能组匹配：高/紧急进投诉组，其余按渠道进对应组（简化示例） */
    private Long matchGroup(Ticket ticket) {
        if (ticket.getPriority() >= 3) {
            return supportUserMapper.findGroupIdByName("投诉组");
        }
        if (ticket.getChannel() == 1) {          // 网页
            return supportUserMapper.findGroupIdByName("售后组");
        }
        return supportUserMapper.findGroupIdByName("技术组");
    }
}
```

### 4. SLA 服务：截止时间计算

```java
@Service
public class SlaService {

    @Autowired
    private SlaRuleMapper slaRuleMapper;

    /**
     * 创建/分派时按优先级规则计算两个 SLA 截止时间并落库
     * 计算一次存库，扫描任务只做范围查询，避免扫描时现算
     */
    public void initDeadline(Ticket ticket) {
        SlaRule rule = slaRuleMapper.selectByPriority(ticket.getPriority());
        if (rule == null) {
            return;  // 未配置规则则不计时
        }
        Date now = new Date();
        ticket.setSlaFirstResponseDeadline(
                DateUtils.addMinutes(now, rule.getFirstResponseMinutes()));
        ticket.setSlaSolveDeadline(
                DateUtils.addMinutes(now, rule.getSolveMinutes()));
        ticketMapper.updateById(ticket);
    }

    /** 判断是否已过首响截止（供列表排序/高亮用） */
    public boolean firstResponseOverdue(Ticket t) {
        return t.getFirstResponseTime() == null
                && t.getSlaFirstResponseDeadline() != null
                && t.getSlaFirstResponseDeadline().before(new Date());
    }
}
```

### 5. SLA 定时扫描：超时提醒与升级

```java
@Component
public class SlaScanTask {

    @Autowired
    private TicketMapper ticketMapper;
    @Autowired
    private NotificationService notificationService;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    /**
     * 每 60 秒扫描一次 SLA 超时工单
     * Redis Set 去重：同一工单同一类型只提醒一次，升级一次
     * 多实例部署时用分布式锁保证只有一个实例在扫
     */
    @Scheduled(cron = "0 * * * * ?")
    public void scan() {
        Date now = new Date();
        int overdueCount = 0;
        // 1. 首响超时：已分派、未首响、过首响截止
        List<Ticket> noResponse = ticketMapper.selectOverdueFirstResponse(now);
        for (Ticket t : noResponse) {
            String dedupKey = "sla:notify:first:" + t.getId();
            if (Boolean.TRUE.equals(redisTemplate.opsForValue()
                    .setIfAbsent(dedupKey, "1", 1, TimeUnit.DAYS))) {
                notificationService.notifySlaOverdue(t, "首次响应超时");
                escalate(t);   // 升级组长/经理
                overdueCount++;
            }
        }
        // 2. 解决超时：处理中/待补充且过解决截止
        List<Ticket> noSolve = ticketMapper.selectOverdueSolve(now);
        for (Ticket t : noSolve) {
            String dedupKey = "sla:notify:solve:" + t.getId();
            if (Boolean.TRUE.equals(redisTemplate.opsForValue()
                    .setIfAbsent(dedupKey, "1", 1, TimeUnit.DAYS))) {
                notificationService.notifySlaOverdue(t, "解决超时");
                escalate(t);
                overdueCount++;
            }
        }
        // 3. 超时总数写 Redis，管理大屏实时读取
        redisTemplate.opsForValue().set("sla:overdue:count", overdueCount);
    }

    /** 升级：工单转给组长，坐席待办 -1，组长待办 +1 */
    private void escalate(Ticket ticket) {
        SupportUser leader = supportUserMapper.selectLeader(ticket.getSkillGroupId());
        if (leader == null) {
            return;
        }
        redisTemplate.opsForHash().increment("ticket:todo:count",
                leader.getId().toString(), 1);
        if (ticket.getAssigneeId() != null) {
            redisTemplate.opsForHash().increment("ticket:todo:count",
                    ticket.getAssigneeId().toString(), -1);
        }
        ticket.setAssigneeId(leader.getId());
        ticketMapper.updateById(ticket);
    }
}
```

```java
@Service
public class TicketCommentService {

        }
        TicketComment comment = new TicketComment();
        comment.setTicketId(ticketId);
        comment.setUserId(userId);
        comment.setContent(content);
        comment.setIsInternal(isInternal ? 1 : 0);
        ticketCommentMapper.insert(comment);
        // 正式回复通知客户；内部备注通知同组坐席
        if (isInternal) {
            notificationService.notifyGroup(ticket.getSkillGroupId(), "工单有新内部备注");
        } else {
            notificationService.notifyCustomer(ticket, "您的工单有新回复");
        }
    }

    /**
     * 客户回复：待补充状态下客户补充后自动流转回处理中
     * 这是状态机与业务联动的典型场景
     */
    @Transactional
    public void customerReply(Long ticketId, Long customerId, String content) {
        Ticket ticket = ticketMapper.selectById(ticketId);
        if (!ticket.getCustomerId().equals(customerId)) {
            throw new BizException("无权回复该工单");
        }
        TicketComment comment = new TicketComment();
        comment.setTicketId(ticketId);
        comment.setUserId(customerId);
        comment.setContent(content);
        comment.setIsInternal(0);
        ticketCommentMapper.insert(comment);
        // 待补充 -> 处理中（状态机自动校验），并通知处理人
        if (ticket.getStatus() == 3) {
            ticketService.transition(ticketId, TicketEvent.SUPPLY_INFO,
                    customerId, "客户补充信息");
        }
        notificationService.notifyAssignee(ticket, "客户已回复工单");
    }
}
```

```java
@Service
public class NotificationService {

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

        }
        // 3. 邮件模板抄送
        if (leader != null) {
            mailSender.send(leader.getEmail(), "SLA 超时提醒",
                    renderTemplate(ticket, type));
        }
    }

    public void notifyNewTicket(Ticket ticket) {

                ticket.getSkillGroupId());

            redisTemplate.opsForList().leftPush("notice:user:" + u.getId(),
                    JSON.toJSONString(Notice.of(ticket, "新工单待认领")));
        }
    }

    public void notifyStatusChange(Ticket ticket, Integer from, Integer to) {

                    "您的工单 " + ticket.getTicketNo() + " 状态更新为 " + statusName(to));

        for (SupportUser u : users) {
            redisTemplate.opsForList().leftPush("notice:user:" + u.getId(), msg);
        }
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 所有状态变更必须走状态机统一入口，禁止在 Mapper 层直接 UPDATE status：否则非法流转、日志缺失、通知漏发全都会发生
2. 流转日志与状态更新放同一事务：先改状态再记日志，任何一步失败整体回滚，审计永远完整
3. SLA 截止时间在建单/分派时算好落库：扫描任务只做 `deadline < now` 范围查询，不要扫描时现算
4. 定时扫描一定要去重（Redis setIfAbsent + TTL）：任务重启、多实例、扫到同一工单只提醒一次
5. 分派负载计数放 Redis，冷数据查库兜底：Redis 计数实时且零压力，重启丢失后从 MySQL 重建
6. 客户可见回复与内部备注分表字段隔离：内部讨论永远不泄露给客户，这是客服系统的信任底线
7. 定时任务多实例部署必须加分布式锁：SLA 扫描、批量通知这类任务抢锁执行，防止重复发送

### 踩坑记录

```text
坑 1：状态被直接改坏
结论：工单从「已关闭」被改成「处理中」，流转日志里却查不到记录。
原因：有人绕过 Service 直接 UPDATE 了 status 字段。
解法：状态字段只允许通过状态机方法修改；数据库加 CHECK 约束兜底；审计日志关联查询对账。

坑 2：SLA 提醒重复轰炸
结论：客户和组长收到十几条超时短信。
原因：每分钟扫描一次，同一个超时工单每次都被扫到并通知。
解法：Redis setIfAbsent + TTL 做提醒去重，同一工单同类型 24 小时内只通知一次。

坑 3：首次响应时间被重复覆盖
结论：工单被转派后 first_response_time 变了，SLA 统计失真。
原因：受理动作每次流转都写 first_response_time。
解法：只在首次受理时写入（`if (firstResponseTime == null)`），转派/重开不再覆盖。

坑 4：分派后坐席离职，工单无人处理
结论：工单卡在新建状态，SLA 一路超时到升级都无人接。
原因：分派时没校验坐席状态，离职/禁用的坐席仍在候选池。
解法：候选池只选 status=在线 的坐席；分派后定时任务检查工单「超时未首响」自动重新分派。

坑 5：客户重复提交同一问题
结论：一个网络故障被 20 个客户各建一单，坐席被刷屏。
原因：多渠道入口各自建单，没有查重。
解法：建单前按「客户 + 手机号 + 标题相似度」查重，命中直接关联已有工单并提示客户。

坑 6：满意度统计口径漂移
结论：月报满意度一会高一会低，对不上。
原因：有的工单关闭前评价，有的关闭后评价，统计时点不一致。
解法：统一在 CONFIRM_CLOSE 前必须评价（或默认评价窗口 24 小时）；报表按关闭时间所在月聚合。
```
