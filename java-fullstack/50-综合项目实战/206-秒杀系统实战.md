## 项目背景

秒杀系统（Seckill System）是高并发场景的经典代表：短时间内大量用户同时抢购限量商品（如双 11 爆品、限时折扣、演唱会门票），瞬时流量可达平时的几百上千倍。秒杀系统的本质不是「卖出商品」，而是在「超大规模瞬时流量」下保证三件事：不超卖（库存准确）、不重复（一人一件）、不雪崩（系统扛住）。它几乎串起了高并发技术的全部要点：限流、缓存、消息队列、分布式锁、幂等、防超卖、熔断降级，是学习高并发架构的最佳实战载体。

业务痛点：

```text
1. 瞬时流量冲击：开抢瞬间流量暴涨，普通下单接口直接被打挂，影响正常业务
2. 超卖风险：并发扣库存没有原子保护，库存 100 件可能卖出 1000 单
3. 一人多单：脚本/黄牛批量抢购，真实用户抢不到，活动失去意义
4. 数据库压力：直接对 MySQL 扣库存，行锁竞争激烈，吞吐量上不去
5. 系统雪崩：秒杀接口异常拖垮整个应用，正常查询也跟着不可用
6. 重复提交：用户连点、网络重试导致同一请求被处理多次，订单重复
7. 恶意刷量：无防护时被脚本瞬间扫空库存，活动效果归零
```

目标用户与核心诉求：

```text
1. 电商运营：发起秒杀活动，配置商品、库存、时间、限购规则
2. 普通用户：开抢瞬间快速下单，体验流畅不卡顿、不重复扣款
3. 平台技术：保证系统在高并发下不雪崩、不超卖、数据最终一致
```

项目要解决的核心问题一句话概括：用「Redis 扛流量、MQ 削峰、数据库最终落账」的分层架构，让秒杀接口在百万级瞬时流量下依然稳定、不超卖、不重复。

## 功能介绍

功能按角色与模块拆分：秒杀活动管理（运营端）、抢购入口（用户端）、订单落库（异步处理端）、系统治理（平台端）。

```text
一、运营端（活动管理）
1. 活动创建 —— 配置商品、秒杀价格、活动起止时间、总库存
2. 库存预热 —— 活动开始前把库存从 MySQL 预载到 Redis（预热脚本）
3. 活动上下架 —— 手动/定时启停秒杀活动
4. 数据看板 —— 实时抢购进度（已抢/剩余）、成交转化、峰值 QPS

二、用户端（抢购入口）
1. 商品详情页 —— 秒杀倒计时、当前状态（未开始/进行中/已售罄）
2. 抢购下单 —— 点击抢购，快速返回「成功/排队中/已售罄」
3. 限购控制 —— 每人限购 N 件，超限直接拒绝
4. 订单查询 —— 抢购结果异步通知，订单中心可查

三、异步处理端（订单落库）
1. 消息消费 —— MQ 消费者把抢购消息转成正式订单
2. 订单创建 —— 校验库存快照、生成订单号、写订单表
3. 失败补偿 —— 消费失败重试，最终进死信队列人工处理
4. 库存回补 —— 用户超时未支付时自动回补 Redis 库存

四、平台端（系统治理）
1. 限流 —— 接口级令牌桶限流，超限返回「系统繁忙」
2. 防刷 —— 同一用户/同一 IP 频控，黑名单拦截
3. 熔断降级 —— 依赖异常时快速失败，保底返回降级文案
4. 监控 —— QPS、成功率、RT 指标大盘
```

## 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 开发框架 | Spring Boot 2.7/3.x | 生态成熟，快速搭建 |
| 缓存/库存 | Redis（String/Lua/Set） | 原子扣减、内存级吞吐，扛住瞬时流量 |
| 消息队列 | RabbitMQ / Kafka | 异步削峰，把峰值流量转成平稳落库 |
| 分布式锁 | Redisson | 跨节点互斥，保证扣库存/发券原子性 |
| 限流 | Guava RateLimiter / Sentinel | 单机令牌桶，集群级用 Sentinel |
| 熔断降级 | Sentinel / Resilience4j | 依赖故障快速失败，保护主链路 |
| 数据库 | MySQL 8.0 | 订单、活动配置等最终落账 |
| 前端 | Vue 3 + 倒计时组件 | 秒杀页倒计时与状态轮询 |

选型说明：

```text
1. Redis 做库存载体而非 MySQL：扣库存是高频写操作，MySQL 行锁下每秒只能处理几千，Redis 单机可到十万级
2. Lua 脚本保证「检查-扣减」原子性：先判断库存足够再 DECR，一个脚本完成，避免并发超卖
3. MQ 削峰是架构核心：抢购接口只做「Redis 预扣 + 发消息」，真正的订单创建由消费者异步处理，接口 RT 从几百毫秒降到个位数毫秒
4. 限流要分层：接口入口限流（防整体打挂）+ 用户级限购（防一人多单）+ IP 频控（防脚本刷量）
5. 秒杀链路不依赖 MySQL 实时读：活动配置预热进 Redis，详情页读缓存，MySQL 只做最终落账
```

## 架构设计

系统分层与请求链路：

```text
┌──────────────────────────────────────────────────────────────┐
│                    客户端（浏览器/App）                        │
│        秒杀页倒计时    抢购按钮    订单查询    结果轮询         │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS
┌───────────────────────────▼──────────────────────────────────┐
│                  接入层：Nginx + 网关                         │
│       限流（令牌桶）→ 防刷（IP 频控）→ 路由到秒杀服务           │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│                   秒杀服务（无状态集群）                       │
│   ┌────────────┐  ┌────────────┐  ┌──────────────────────┐  │
│   │ 活动校验    │  │ 用户限购    │  │ Redis 原子扣库存(Lua) │  │
│   │ (Redis缓存) │  │ (Redis Set)│  │  + 分布式锁(Redisson)│  │
│   └────────────┘  └────────────┘  └──────────────────────┘  │
│                       │ 扣减成功                              │
│                       ▼                                      │

┌───────────────────────────▼──────────────────────────────────┐
│               订单消费者（独立服务/模块）                      │
│   ┌────────────┐  ┌────────────┐  ┌──────────────────────┐  │
│   │ 消费消息    │  │ 生成订单号  │  │ 写订单表 + 状态机     │  │
│   │ (幂等去重)  │  │ (雪花ID)   │  │ (待支付/已支付/已取消) │  │
│   └────────────┘  └────────────┘  └──────────────────────┘  │
└───────────────────────────┬──────────────────────────────────┘
                            │
                    ┌───────▼───────┐
                    │  MySQL 落账    │
                    │ 订单表/库存表  │
                    └───────────────┘
```

抢购请求链路（用户点击抢购那一刻）：

```text
1. Nginx/Gateway 限流：令牌桶判断是否放行，超限直接 429「系统繁忙」
2. 秒杀服务校验活动：Redis 查活动状态（未开始/进行中/已结束），非法请求拦截
3. 用户限购校验：SETNX seckill:user:{userId}:{actId}，已存在则「每人限购一件」
4. Redis Lua 原子扣库存：脚本内「检查库存 > 0 → DECR」，返回剩余量
5. 扣减成功 → 发送 MQ 消息（userId + activityId + goodsId + 快照库存）
6. 接口立即返回「抢购成功，排队出单中」（RT 约 3-8ms）
7. 订单消费者收到消息：幂等校验 → 生成订单号 → 写订单表（待支付）
8. 用户收到「下单成功」通知，进入支付流程
9. 支付超时未付（如 15 分钟）→ 定时任务取消订单 + Redis 库存回补 +1
```

降级链路（依赖故障时）：

```text
1. Redis 不可用 → 秒杀入口直接降级为「活动暂停」（保底文案），不再尝试扣库存
2. MQ 堆积 → 消费者告警，订单创建延迟，但 Redis 库存已扣，不会超卖
3. 数据库慢查询 → Sentinel 熔断订单查询接口，降级返回「订单处理中，请稍后查询」
4. 全链路监控指标：QPS / 成功率 / RT / MQ 积压数，任一超标触发告警
```

## 核心实现

### 1. 库存预热：活动开始前把库存载入 Redis

```java
@Service
public class StockPreheatService {

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private SeckillActivityMapper activityMapper;

    /**
     * 活动开始前调用（运营手动触发或定时任务）
     * 把 MySQL 库存载入 Redis，后续扣减全部走 Redis
     */
    public void preheat(Long activityId) {
        SeckillActivity act = activityMapper.selectById(activityId);
        if (act == null) {
            throw new BizException("活动不存在");
        }
        String stockKey = "seckill:stock:" + activityId;
        // 只允许预热一次：SETNX 成功才写入，避免重复预热覆盖已扣库存
        Boolean first = redisTemplate.opsForValue()
                .setIfAbsent(stockKey, act.getTotalStock());
        if (!Boolean.TRUE.equals(first)) {
            throw new BizException("库存已预热，请勿重复操作");
        }
        // 活动信息预热（详情页读缓存）
        redisTemplate.opsForValue().set(
                "seckill:activity:" + activityId, act, 24, TimeUnit.HOURS);
        log.info("秒杀活动 {} 库存预热完成：{}", activityId, act.getTotalStock());
    }
}
```

### 2. Lua 原子扣库存（防超卖核心）

```java
@Service
public class StockDeductService {

    @Autowired
    private StringRedisTemplate redisTemplate;

    /**
     * Lua 脚本：检查库存 > 0 才扣减，原子执行
     * 返回值：剩余库存（>=0 成功，<0 失败）
     */
    private static final String DEDUCT_LUA =
            "if redis.call('get', KEYS[1]) and tonumber(redis.call('get', KEYS[1])) > 0 " +
            "then " +
            "  return redis.call('decr', KEYS[1]) " +
            "else " +
            "  return -1 " +
            "end";

    public long deductStock(Long activityId) {
        String stockKey = "seckill:stock:" + activityId;
        Long result = redisTemplate.execute(
                new DefaultRedisScript<>(DEDUCT_LUA, Long.class),
                Collections.singletonList(stockKey));
        return result == null ? -1 : result;
    }

    /** 库存回补（订单取消/支付超时） */
    public void restoreStock(Long activityId) {
        redisTemplate.opsForValue().increment("seckill:stock:" + activityId);
    }
}
```

### 3. 抢购主流程（限流 + 限购 + 扣库存 + 发消息）

```java
@Service
public class SeckillService {

    @Autowired
    private StockDeductService stockDeductService;
    @Autowired
    private RabbitTemplate rabbitTemplate;
    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private RateLimiter limiter;   // Guava 单机令牌桶，集群用 Sentinel

    /**
     * 抢购入口：整条链路只做「轻操作」，毫秒级返回
     * 1. 限流 → 2. 活动校验 → 3. 用户限购 → 4. Redis 扣库存 → 5. 发 MQ
     */
    public Result<SeckillResultVO> seckill(Long userId, Long activityId) {
        // 1. 接口限流（令牌桶）
        if (!limiter.tryAcquire()) {
            return Result.error(429, "系统繁忙，请稍后再试");
        }

        // 2. 活动状态校验（读缓存，不查库）
        SeckillActivity act = getActivityFromCache(activityId);
        if (act == null || act.getStatus() != 1) {
            return Result.error("活动未开始或已结束");
        }
        long now = System.currentTimeMillis();
        if (now < act.getStartTime().getTime() || now > act.getEndTime().getTime()) {
            return Result.error("不在活动时间内");
        }

        // 3. 用户限购（SETNX 幂等，一人一单）
        String limitKey = "seckill:user:" + activityId + ":" + userId;
        Boolean first = redisTemplate.opsForValue()
                .setIfAbsent(limitKey, "1", 24, TimeUnit.HOURS);
        if (!Boolean.TRUE.equals(first)) {
            return Result.error("您已参与过该活动，每人限购一件");
        }

        // 4. Redis 原子扣库存（Lua，防超卖）
        long stockLeft = stockDeductService.deductStock(activityId);
        if (stockLeft < 0) {
            // 扣减失败回滚限购标记，允许用户下次活动再抢
            redisTemplate.delete(limitKey);
            return Result.error("手慢了，商品已售罄");
        }

        // 5. 发 MQ 消息，异步落订单（削峰）
        SeckillMessage msg = new SeckillMessage(userId, activityId, act.getGoodsId());
        rabbitTemplate.convertAndSend("seckill.exchange", "seckill.order", msg);

        // 6. 立即返回（RT 毫秒级）
        return Result.success(new SeckillResultVO("抢购成功，排队出单中"));
    }
}
```

### 4. 订单消费者（幂等 + 落库）

```java
@Component
public class SeckillOrderConsumer {

    @Autowired
    private SeckillOrderMapper orderMapper;
    @Autowired
    private SeckillLimitLogMapper limitLogMapper;
    @Autowired
    private IdGenerator idGenerator;   // 雪花 ID

    /**
     * 消费抢购消息，创建订单
     * 幂等：unique key (user_id, activity_id) 防重复插入
     */
    @RabbitListener(queues = "seckill.order.queue")
    @Transactional(rollbackFor = Exception.class)
    public void consume(SeckillMessage msg) {
        // 1. 幂等校验：同一用户同一活动只能有一单（DB 唯一键兜底）
        int exist = orderMapper.countByUserAndActivity(msg.getUserId(), msg.getActivityId());
        if (exist > 0) {
            log.warn("重复消费，跳过：user={}, activity={}", msg.getUserId(), msg.getActivityId());
            return;
        }

        // 2. 生成订单
        SeckillOrder order = new SeckillOrder();
        order.setOrderNo(idGenerator.nextId());
        order.setUserId(msg.getUserId());
        order.setActivityId(msg.getActivityId());
        order.setGoodsId(msg.getGoodsId());
        order.setStatus(0);  // 待支付
        orderMapper.insert(order);

        // 3. 限购记录落库（对账）
        SeckillLimitLog limitLog = new SeckillLimitLog();
        limitLog.setUserId(msg.getUserId());
        limitLog.setActivityId(msg.getActivityId());
        limitLog.setOrderNo(order.getOrderNo());
        limitLogMapper.insert(limitLog);

        // 4. 已售库存 +1（对账用）
        activityMapper.incrSold(msg.getActivityId());
    }
}
```

### 5. 支付超时自动取消 + 库存回补

```java
@Component
public class OrderTimeoutTask {

    @Autowired
    private SeckillOrderMapper orderMapper;
    @Autowired
    private StockDeductService stockDeductService;

    /**
     * 每 30 秒扫描待支付超过 15 分钟的订单，取消并回补库存
     * 注意：只回补 Redis 库存，MySQL sold_stock 减 1（对账一致）
     */
    @Scheduled(fixedDelay = 30 * 1000)
    public void cancelTimeoutOrders() {
        LocalDateTime deadline = LocalDateTime.now().minusMinutes(15);
        List<SeckillOrder> timeoutOrders =
                orderMapper.selectTimeoutOrders(deadline);
        for (SeckillOrder order : timeoutOrders) {
            // 乐观更新：状态 0->2，只成功一次
            int rows = orderMapper.cancelIfPending(order.getId());
            if (rows == 1) {
                // 回补 Redis 库存
                stockDeductService.restoreStock(order.getActivityId());
                // 回补对账库存
                activityMapper.decrSold(order.getActivityId());
                // 删除限购标记，允许用户重新参与
                redisTemplate.delete("seckill:user:" +
                        order.getActivityId() + ":" + order.getUserId());
                log.info("订单 {} 超时取消，库存回补", order.getOrderNo());
            }
        }
    }
}
```

### 6. 防刷：IP 频控 + 黑名单

```java
@Component
public class AntiBrushFilter extends OncePerRequestFilter {

    @Autowired
    private StringRedisTemplate redisTemplate;

    /**
     * 每个 IP 每秒最多 5 次秒杀请求，超限拦截
     * 连续触发阈值进黑名单（1 小时）
     */
    @Override
    protected void doFilterInternal(HttpServletRequest request,
            HttpServletResponse response, FilterChain chain) throws IOException, ServletException {
        String ip = getClientIp(request);
        String key = "seckill:ip:" + ip;
        Long count = redisTemplate.opsForValue().increment(key);
        if (count == 1) {
            redisTemplate.expire(key, 1, TimeUnit.SECONDS);
        }
        if (count > 5) {
            // 连续超频标记黑名单
            redisTemplate.opsForValue().increment("seckill:black:" + ip);
            redisTemplate.expire("seckill:black:" + ip, 3600, TimeUnit.SECONDS);
            response.setStatus(429);
            response.getWriter().write("{\"code\":429,\"msg\":\"请求过于频繁\"}");
            return;
        }
        chain.doFilter(request, response);
    }
}
```

## 实际应用场景

### 场景一：电商平台 618 限时秒杀

某电商平台 618 大促，爆款手机限量 5000 台，开抢瞬间涌入 50 万用户：

```text
1. 活动前 1 小时运营配置活动：商品、秒杀价、5000 库存、限购 1 件
2. 活动前 10 分钟执行预热脚本：库存 5000 载入 Redis，活动信息写缓存
3. 开抢瞬间：50 万请求打到秒杀服务，网关限流放行 5 万 QPS，其余快速失败
4. 每笔请求：限购校验 → Lua 扣库存 → 发 MQ，接口平均 RT 5ms
5. 订单消费者平稳落库：5000 单在 1 分钟内全部生成（MQ 削峰后的平稳速率）
6. 未抢到的 49.95 万人收到「已售罄」，无一人因系统崩溃体验中断
7. 500 单超时未支付，定时任务自动取消并回补库存，可二次开抢
8. 运营看板：实时显示已抢 4500/剩余 500，峰值 QPS、成功率一目了然
```

票务平台发售 2 万张演唱会门票，黄牛脚本与真实用户同场竞争：

```text
4. 抢购成功者 15 分钟内必须支付，超时释放回流
5. 回流票再次开抢，提升门票利用率
```


## 最佳实践与踩坑记录

### 最佳实践

1. 库存载体用 Redis 而非 MySQL：扣库存是高频写，Redis 原子操作（Lua）才能扛住瞬时流量，MySQL 只做最终落账
2. 接口只做「轻操作」：限流/限购/扣库存/发消息全部毫秒级，订单创建异步化，接口 RT 从几百毫秒降到个位数毫秒
3. 幂等要双层：Redis SETNX 挡第一层（限购标记），DB 唯一键（user_id + activity_id）兜底第二层，防重复订单
4. 库存回补必须对称：取消订单时 Redis 库存 +1、MySQL sold_stock -1、删限购标记，三处一致才不留脏数据
5. 预热脚本要幂等：SETNX 防止重复预热覆盖已扣库存，预热失败不影响活动
6. 降级预案提前演练：Redis 挂了秒杀入口降级为「活动暂停」，MQ 积压告警，数据库慢查询熔断
7. 秒杀活动单独部署：独立服务/独立数据库，秒杀流量隔离，不拖垮正常交易链路

### 踩坑记录

```text
坑 1：超卖
结论：库存 100 卖出了 150 单。
原因：用「先查后扣」的非原子操作，并发下两个请求同时读到库存 1。
解法：改用 Lua 脚本原子扣减（检查-扣减一个脚本完成），或 Redis DECR 后判断负数回滚。

坑 2：重复下单
结论：同一用户点一次抢购按钮生成多张订单。
原因：前端连点 + 网络重试，后端没有幂等保护。
解法：Redis SETNX 限购标记 + DB 唯一键 (user_id, activity_id) 双层幂等。

坑 3：预热后库存被覆盖
结论：活动开始后库存数量不对。
原因：预热脚本没有幂等保护，运维重复执行把已扣的库存重置了。
解法：预热用 SETNX（存在即不覆盖），并加「仅活动开始前可预热」状态校验。

坑 4：MQ 消费重复
结论：部分订单重复创建。
原因：消费者重试（ack 超时/重启）导致同一条消息消费两次。
解法：消费端幂等（DB 唯一键 + 先查后插），重复消息直接跳过。

坑 5：超时取消把已支付订单取消了
结论：用户已支付但订单显示已取消。
原因：定时任务扫描「待支付超时」时，竞态窗口内用户刚好完成支付。
解法：取消用乐观更新（UPDATE ... SET status=2 WHERE id=? AND status=0），影响行数为 0 说明已支付，跳过。

坑 6：单机限流在集群下失效
结论：部署 5 个实例后限流形同虚设。
原因：Guava RateLimiter 是进程内令牌桶，每台机器独立计数。
解法：集群环境换 Sentinel/Redis Lua 分布式限流，或按实例配额分摊。

坑 7：秒杀拖垮正常业务
结论：秒杀高峰正常下单接口也变慢。
原因：秒杀与正常业务共用应用和数据库，流量互相干扰。
解法：秒杀独立部署 + 独立数据库 + 独立 MQ，流量隔离。
```
