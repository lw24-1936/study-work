## 项目背景

短链接服务（Short URL Service）是互联网基础设施级的经典业务：把冗长的 URL 压缩成 6-8 位短码，访问时通过 302 重定向跳回原地址。短信营销、社交分享、广告投放追踪、二维码场景里短链接无处不在。它看起来简单（一个重定向而已），但真正做到高可用、高并发、防刷、可统计，需要把「全局发号、Redis 缓存、布隆过滤器、异步统计」这些高并发技术完整串起来，是学习分布式 ID 与缓存体系的最佳实战载体。

业务痛点：

```text
1. 长链接在短信里放不下：一条短信内容空间有限，长 URL 动辄上百字符，直接挤爆文案
2. 分享体验差：微博/微信等平台对链接长度和域名有风控，长链接容易被折叠、被拦截
3. 无法统计：原始链接没有任何访问数据，投放效果全靠猜，渠道好坏说不清
4. 无法管理：链接发出去就失控，不能禁用、不能设置有效期、不能防滥用
5. 域名被拉黑：个别违规内容导致整个域名被平台屏蔽，没有短链中转就无法快速换域名止损
6. 高并发脆弱：爆款内容瞬间百万访问，长链接直连源站，源站扛不住直接打挂
```

目标用户与核心诉求：

```text
1. 运营/市场人员：生成短链投放到短信、广告、海报二维码，看 PV/UV 评估渠道效果
2. 开发者：为 App 分享、微信内嵌页、短信模板接入短链生成 API，按量计费或自建
3. 普通用户：发朋友圈、论坛帖时把长链接转短，排版美观且不被平台折叠
```

项目要解决的核心问题一句话概括：把长链接变成「短、可统计、可控生命周期、能扛高并发」的短码，同时保证发号不重复、跳转不穿透数据库、统计不拖慢跳转。

## 功能介绍

功能按角色与模块拆分：用户端（生成与管理）、跳转引擎（核心入口）、统计端（数据报表）、管理端（系统治理）。

```text
一、用户端（短链接生成与管理）
1. 长链接转短链接 —— 自动生成 6-8 位短码，返回完整短链接
2. 自定义短码 —— 用户可指定个性化短码（如 s.t.cn/vip），系统校验占用与保留字
3. 链接管理 —— 我的短链接列表，可查看、禁用、删除、设置过期时间
4. 过期设置 —— 创建时指定有效期，过期后短码自动失效，防永久滥用

二、跳转引擎（核心入口）
1. 短码跳转 —— GET /{shortCode} 返回 302 + Location 长链接
2. 缓存加速 —— 短码到长链接的映射优先走 Redis，命中率 99% 以上
3. 防穿透 —— 布隆过滤器拦截不存在的短码，非法请求不打数据库
4. 防击穿 —— 热点短码缓存失效时互斥锁重建，避免瞬间打爆 DB

三、统计端（访问数据分析）
1. PV 统计 —— 每个短链接的访问次数，精确计数（Redis INCR）
2. UV 统计 —— 去重访客数，HyperLogLog 近似统计
3. 每日趋势 —— 按天查看 PV/UV 曲线，判断投放效果
4. 访问明细 —— IP、User-Agent、Referer 来源记录（异步落库）

四、管理端（系统治理）
1. 用户管理 —— 短链用户的注册、配额、封禁
2. 链接审计 —— 全站短链接列表，发现违规链接立即禁用
3. 域名管理 —— 支持多个短链域名绑定与切换
4. 全站统计 —— 总短链数、总访问量、TOP 链接排行
```

## 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 开发框架 | Spring Boot 2.7/3.x | 生态成熟，起步快，社区资料多 |
| 持久层 | MyBatis-Plus | 短链主表、日志表标准 CRUD，复杂查询走 XML |
| 数据库 | MySQL 8.0 | 短链映射、号段、访问日志落库，事务与唯一索引兜底 |
| 缓存 | Redis | 短码映射缓存、布隆过滤器（BitMap）、PV 计数、UV 去重、互斥锁 |
| 全局发号 | 雪花算法 + DB 号段 | 短码唯一性的根基，两种方案可切换 |
| 布隆过滤器 | Redis BitMap 自实现 | 百万级短码存在性预判，内存开销约 1MB 级 |
| 前端 | Vue 3 + Element Plus | 短链管理后台与统计报表 |
| 构建 | Maven | 依赖管理标准工具 |

选型说明：

```text
1. 短码来源选「发号器 + Base62 编码」而非随机生成：确定性唯一、无碰撞重试、可反解校验
2. 布隆过滤器用 Redis BitMap 而非 Guava 本地实现：多实例共享同一份位图，容量可预估
3. 缓存 + 布隆双防线：布隆拦截「不存在的短码」，缓存拦截「存在但热门的短码」，互斥锁防击穿
4. 跳转用 302 而非 301：301 会被浏览器/CDN 缓存跳转结果，之后不再请求短链服务，统计全丢
5. UV 用 HyperLogLog：百万级 UV 内存 12KB 以内，标准误差 0.81%，统计场景完全可接受
```

请求链路示例（用户创建短链接）：

```text
1. 前端 POST /api/short-link，传 longUrl 和可选的 customCode
2. Controller 收参 -> LinkService.createShortLink
3. 自定义短码：校验长度/字符集/保留字，布隆过滤器预判是否已占用
4. 自动短码：DB 号段发号器取一个全局 id -> Base62 编码成 6-8 位短码
5. link_info 落库（short_code 唯一索引兜底，防极端并发冲突）
6. 短码写入布隆过滤器，后续跳转直接用位图判定存在性
7. 返回完整短链接 s.t.cn/{shortCode} 给前端
```

请求链路示例（用户访问短码跳转）：

```text
1. 浏览器请求 https://s.t.cn/{shortCode}
2. 布隆过滤器判定：位图命中为 0 -> 短码必然不存在，直接 404，不打 DB
3. 查 Redis 缓存 short:link:{code}：命中直接返回长链接（99% 请求止步于此）
4. 缓存未命中 -> 抢互斥锁（SETNX）-> 只让一个线程查 MySQL link_info
5. 查不到：写 60s 空值缓存（防穿透）；查到：写 12h 缓存后释放锁
6. 校验 expire_time，已过期则写空值缓存并返回 404
7. 响应 302 + Location 长链接，浏览器发起跳转
8. 异步统计：PV 走 Redis INCR，UV 走 HyperLogLog，明细日志落库
```

## 核心实现

### 1. 短码生成：Base62 编码工具

短码本质是把发号器产生的全局递增 id 编码成更短的字符串：10 进制转 62 进制后，6 位可表示 568 亿个短码，7 位 3.5 万亿，完全够用。编码可逆，还支持用短码反解出 id 做校验。

```java
package com.example.shorturl.util;

/**
 * Base62 编码工具：10 进制与 62 进制互转
 * 字符集：数字 + 小写字母 + 大写字母，避免歧义字符
 */
public class ShortCodeUtil {

    // 62 个字符，顺序固定保证可逆
    private static final String CHARS =
            "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
    private static final char[] CHAR_ARRAY = CHARS.toCharArray();
    private static final int BASE = 62;

    /**
     * 10 进制 long 转 62 进制短码
     * 例：encode(1000000) = "4c92"
     */
    public static String encode(long num) {
        if (num == 0) {
            return "0";
        }
        StringBuilder sb = new StringBuilder();
        while (num > 0) {
            sb.append(CHAR_ARRAY[(int) (num % BASE)]);
            num /= BASE;
        }
        // 余数是从低位到高位累积的，需要反转
        return sb.reverse().toString();
    }

    /**
     * 62 进制短码转回 10 进制（校验短码合法性用）
     */
    public static long decode(String code) {
        long num = 0;
        for (int i = 0; i < code.length(); i++) {
            num = num * BASE + CHARS.indexOf(code.charAt(i));
        }
        return num;
    }
}
```

### 2. 全局发号器：DB 号段模式

号段模式的核心思想：不再每发一个 id 就 UPDATE 一次数据库，而是一次从 DB 取一段（如 10000 个 id）放内存，内存发完再取下一段。DB 更新频率降低一万倍，且内存发号零网络开销。多实例并发取号段时用乐观锁（version）保证每段不重不漏。

```java
package com.example.shorturl.id;

/**
 * DB 号段发号器：内存缓存一段 id，耗尽后去 DB 取新号段
 * 乐观锁保证多实例并发取号段不冲突
 */
@Component
public class SegmentIdGenerator {

    // 当前可发的下一个 id（含），号段上限（不含）
    private volatile long currentId;
    private volatile long maxId;
    // 剩余量低于阈值时提前预取，避免发到边界再阻塞
    private static final int PREFETCH_THRESHOLD = 1000;

    @Autowired
    private IdSegmentMapper idSegmentMapper;

    /**
     * 取下一个全局唯一 id
     * synchronized 保证单实例内线程安全
     */
    public synchronized long nextId() {
        if (currentId >= maxId || maxId - currentId < PREFETCH_THRESHOLD) {
            fetchNewSegment();
        }
        return currentId++;
    }

    /**
     * 从 DB 取新号段：乐观锁更新 max_id
     * UPDATE 影响行数为 0 说明被其他实例抢先，循环重试
     */
    private void fetchNewSegment() {
        while (true) {
            IdSegment segment = idSegmentMapper.selectByBizType("short_link");
            long newMaxId = segment.getMaxId() + segment.getStep();
            int rows = idSegmentMapper.updateMaxId(
                    segment.getId(), segment.getMaxId(), newMaxId, segment.getVersion());
            if (rows == 1) {
                // 本实例独占 [segment.maxId, newMaxId) 区间
                currentId = segment.getMaxId();
                maxId = newMaxId;
                return;
            }
            // version 冲突：其他实例已取号段，重新读再试
        }
    }
}
```

对应 Mapper 的乐观锁 SQL：

```sql
-- 乐观锁取号段：version 不匹配则更新失败（影响行数为 0）

SET max_id = #{newMaxId}, version = version + 1
WHERE id = #{id} AND max_id = #{oldMaxId} AND version = #{version}
```

### 3. 全局发号器：雪花算法（备选方案）

雪花算法不依赖 DB，单机内存发号：41 位时间戳 + 10 位机器号 + 12 位序列号，单机每秒可发 409.6 万个 id。与号段方案相比省掉 DB 依赖，但要求机器时钟不回拨。

```java
package com.example.shorturl.id;

/**
 * 雪花算法发号器：64 位 long
 * 结构：1 符号位 + 41 时间戳 + 10 机器号 + 12 序列号
 */
@Component
public class SnowflakeIdGenerator {

    // 起始时间戳（2021-01-01），可自定义
    private static final long EPOCH = 1609430400000L;
    // 机器号占 10 位，范围 0-1023
    private final long workerId;
    // 序列号占 12 位，掩码 4095
    private static final long SEQUENCE_MASK = ~(-1L << 12);
    // 时间戳左移 22 位（10 机器号 + 12 序列号）
    private static final long WORKER_SHIFT = 12L;
    private static final long TIMESTAMP_SHIFT = 22L;

    private long lastTimestamp = -1L;
    private long sequence = 0L;

    public SnowflakeIdGenerator(@Value("${snowflake.worker-id}") long workerId) {
        if (workerId < 0 || workerId > 1023) {
            throw new IllegalArgumentException("workerId 必须在 0-1023 之间");
        }
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();
        // 时钟回拨保护：回拨超过 5 秒直接拒绝，短暂回拨自旋等待
        if (timestamp < lastTimestamp) {
            long offset = lastTimestamp - timestamp;
            if (offset > 5000) {
                throw new RuntimeException("时钟回拨超过 5 秒，拒绝发号");
            }
            while (timestamp < lastTimestamp) {
                timestamp = System.currentTimeMillis();
            }
        }
        if (timestamp == lastTimestamp) {
            // 同一毫秒内：序列号递增，用尽则等待下一毫秒
            sequence = (sequence + 1) & SEQUENCE_MASK;
            if (sequence == 0) {
                timestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }
        lastTimestamp = timestamp;
        // 组装 64 位 id
        return ((timestamp - EPOCH) << TIMESTAMP_SHIFT)
                | (workerId << WORKER_SHIFT)
                | sequence;
    }

    private long waitNextMillis(long lastTimestamp) {
        long timestamp = System.currentTimeMillis();
        while (timestamp <= lastTimestamp) {
            timestamp = System.currentTimeMillis();
        }
        return timestamp;
    }
}
```

两种发号方案对比：

```text
1. DB 号段：依赖 DB 但可靠、可持久化，取号段后内存零成本发号，适合短链这种大并发发号场景
2. 雪花算法：无 DB 依赖、吞吐更高，但强依赖服务器时钟，分布式部署需要规划好 workerId
3. 本项目默认号段方案，雪花作为高可用备选；两者产出的 id 都经 Base62 编码成短码
```

### 4. 创建短链接：自定义短码校验 + 发号落库

```java
package com.example.shorturl.service;

/**
 * 短链接业务：创建、校验、缓存管理
 */
@Service
public class LinkService {

    // 缓存 key 前缀
    private static final String LINK_KEY_PREFIX = "short:link:";

    // 保留字：用户不能自定义这些短码，避免与系统路径冲突
    private static final Set<String> RESERVED_CODES = Set.of(
            "admin", "api", "login", "register", "stat", "manage", "favicon", "ws");

    @Autowired
    private LinkMapper linkMapper;
    @Autowired
    private SegmentIdGenerator segmentIdGenerator;
    @Autowired
    private BloomFilterService bloomFilterService;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    /**
     * 创建短链接
     * 短码来源二选一：用户自定义（需校验）或发号器自动生成
     */
    public String createShortLink(CreateLinkRequest req) {
        String shortCode = req.getCustomCode();
        if (StringUtils.hasText(shortCode)) {
            // 1. 自定义短码：长度、字符集、保留字三重校验
            validateCustomCode(shortCode);
            // 2. 布隆过滤器快速预判是否已存在（大概率命中，省一次 DB 查询）
            if (bloomFilterService.mightContain(shortCode)
                    && linkMapper.selectByCode(shortCode) != null) {
                throw new BizException("短码已被占用，换个试试");
            }
        } else {
            // 3. 自动生成：号段发号器取全局 id -> Base62 编码
            long id = segmentIdGenerator.nextId();
            shortCode = ShortCodeUtil.encode(id);
        }
        // 4. 落库：short_code 唯一索引兜底，极端并发冲突时抛 DuplicateKeyException
        LinkInfo link = new LinkInfo();
        link.setShortCode(shortCode);
        link.setLongUrl(req.getLongUrl());
        link.setUserId(req.getUserId());
        link.setExpireTime(req.getExpireTime());
        linkMapper.insert(link);
        // 5. 加入布隆过滤器，跳转时位图直接命中
        bloomFilterService.add(shortCode);
        return shortCode;
    }

    /**
     * 自定义短码校验：4-16 位，仅数字字母，避开保留字
     */
    private void validateCustomCode(String code) {
        if (code.length() < 4 || code.length() > 16) {
            throw new BizException("短码长度需在 4-16 位之间");
        }
        if (!code.matches("[a-zA-Z0-9]+")) {
            throw new BizException("短码仅支持数字和字母");
        }
        if (RESERVED_CODES.contains(code.toLowerCase())) {
            throw new BizException("该短码为系统保留字");
        }
    }
}
```

### 5. 短码跳转：缓存 + 互斥锁防击穿

跳转链路是短链服务的生命线，必须做到：不存在的短码不进 DB（布隆过滤器）、热门的短码尽量不查 DB（缓存）、缓存失效瞬间不压垮 DB（互斥锁）。

```java
package com.example.shorturl.service;

/**
 * 跳转服务：短码解析为长链接
 * 三道防线：布隆过滤器（防穿透）-> 缓存（扛流量）-> 互斥锁（防击穿）
 */
@Service
public class RedirectService {

    private static final String LINK_KEY = "short:link:";
    private static final String LOCK_KEY = "short:lock:";
    private static final String EMPTY = "EMPTY";

    @Autowired
    private LinkMapper linkMapper;
    @Autowired
    private BloomFilterService bloomFilterService;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    /**
     * 解析短码为长链接，查不到返回 null
     */
    public String resolve(String shortCode) {
        // 1. 布隆过滤器：位图判定不存在 -> 直接返回，不打 DB
        if (!bloomFilterService.mightContain(shortCode)) {
            return null;
        }
        String key = LINK_KEY + shortCode;
        // 2. 有限次重试拿锁，避免递归导致栈溢出
        for (int i = 0; i < 5; i++) {
            Object cached = redisTemplate.opsForValue().get(key);
            if (cached != null) {
                // 空值占位：说明短码不存在或已过期
                return EMPTY.equals(cached) ? null : (String) cached;
            }
            String lockKey = LOCK_KEY + shortCode;
            if (tryLock(lockKey)) {
                try {
                    // 3. 拿到锁后二次查缓存（双检），避免重复查库
                    cached = redisTemplate.opsForValue().get(key);
                    if (cached != null) {
                        return EMPTY.equals(cached) ? null : (String) cached;
                    }
                    // 4. 查库重建缓存
                    LinkInfo link = linkMapper.selectByCode(shortCode);
                    if (link == null || isExpired(link)) {
                        // 布隆误判或已过期：写 60s 空值缓存防穿透
                        redisTemplate.opsForValue().set(key, EMPTY, 60, TimeUnit.SECONDS);
                        return null;
                    }
                    redisTemplate.opsForValue().set(key, link.getLongUrl(), 12, TimeUnit.HOURS);
                    return link.getLongUrl();
                } finally {
                    unlock(lockKey);
                }
            }
            // 5. 没抢到锁：说明别的线程正在重建，短暂等待后重试
            sleepQuietly(50);
        }
        // 6. 重试超限：直接查库兜底，保证可用性
        LinkInfo link = linkMapper.selectByCode(shortCode);
        return link == null || isExpired(link) ? null : link.getLongUrl();
    }

    private boolean isExpired(LinkInfo link) {
        return link.getExpireTime() != null && link.getExpireTime().before(new Date());
    }

    // Redis SETNX 互斥锁，5 秒自动过期防死锁
    private boolean tryLock(String key) {
        Boolean ok = redisTemplate.opsForValue()
                .setIfAbsent(key, "1", 5, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(ok);
    }

    private void unlock(String key) {
        redisTemplate.delete(key);
    }

    private void sleepQuietly(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

### 6. 布隆过滤器：Redis BitMap 实现

布隆过滤器的原理：用 k 个哈希函数把元素映射到位数组的 k 个位并置 1。判断存在性时只要有一位是 0 就必然不存在；全为 1 只能说可能存在（有误判率，误判方向是「把不存在的判成存在」，因此判定存在后必须回源查库）。100 万条数据、1% 误判率只需要约 1.2MB 内存。

```java
package com.example.shorturl.service;

/**
 * 布隆过滤器：基于 Redis BitMap 实现
 * 作用：拦截「不存在的短码」请求，防止恶意刷量穿透到 DB
 */
@Service
public class BloomFilterService {

    // 预估元素量 100 万，误判率 1%
    private static final long EXPECTED_INSERTIONS = 1_000_000L;
    private static final double FPP = 0.01;
    private static final String BLOOM_KEY = "short:bloom";

    // 位数组长度：m = -n*ln(p) / (ln2)^2
    private static final long BIT_SIZE = (long) (-EXPECTED_INSERTIONS * Math.log(FPP)
            / (Math.log(2) * Math.log(2)));
    // 哈希函数个数：k = m/n * ln2
    private static final int HASH_COUNT = (int) Math.ceil(
            (double) BIT_SIZE / EXPECTED_INSERTIONS * Math.log(2));

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private LinkMapper linkMapper;

    /**
     * 服务启动时预热：把存量短码全部写入布隆过滤器
     * 否则重启后位图为空，所有请求都会穿透到 DB
     */
    @PostConstruct
    public void init() {
        long offset = 0;
        int batchSize = 5000;
        while (true) {
            List<String> codes = linkMapper.selectCodesByPage(offset, batchSize);
            if (codes.isEmpty()) {
                break;
            }
            codes.forEach(this::add);
            offset += batchSize;
        }
    }

    /**
     * 写入：k 个哈希函数分别计算位位置并置 1
     */
    public void add(String code) {
        for (int i = 0; i < HASH_COUNT; i++) {
            long bit = Math.abs(hash(code, i)) % BIT_SIZE;
            redisTemplate.opsForValue().setBit(BLOOM_KEY, bit, true);
        }
    }

    /**
     * 判定：任一位为 0 必然不存在；全为 1 可能存在（误判需回源查库确认）
     */
    public boolean mightContain(String code) {
        for (int i = 0; i < HASH_COUNT; i++) {
            long bit = Math.abs(hash(code, i)) % BIT_SIZE;
            Boolean exists = redisTemplate.opsForValue().getBit(BLOOM_KEY, bit);
            if (exists == null || !exists) {
                return false;
            }
        }
        return true;
    }

    /**
     * 双重哈希：h_i(x) = h1(x) + i * h2(x)，k 个哈希之间相互独立
     */
    private long hash(String code, int i) {
        int h1 = code.hashCode();
        int h2 = h1 >>> 16;
        return h1 + (long) i * h2;
    }
}
```

### 7. 访问统计与过期清理

统计必须与跳转解耦：跳转是同步关键路径，统计是异步旁路。PV 用 INCR 精确计数，UV 用 HyperLogLog 近似去重，两者都先落 Redis，定时任务批量刷入 MySQL。

```java
package com.example.shorturl.service;

/**
 * 访问统计：PV 精确计数（INCR），UV 近似去重（HyperLogLog）
 */
@Service
public class VisitStatService {

    private static final String PV_KEY = "short:pv:";
    private static final String UV_KEY = "short:uv:";

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private LinkVisitLogMapper visitLogMapper;

    /**
     * 访问埋点：跳转成功后异步调用，不阻塞响应
     * 按天分 key：short:pv:{code}:{date}
     */
    @Async
    public void recordVisit(String shortCode, String ip, String ua, String referer) {
        String today = LocalDate.now().toString();
        // 1. PV：当天计数 +1
        redisTemplate.opsForValue().increment(PV_KEY + shortCode + ":" + today);
        // 2. UV：HyperLogLog 以 IP 去重，单 key 内存约 12KB，百万 UV 无压力
        redisTemplate.opsForHyperLogLog().add(UV_KEY + shortCode + ":" + today, ip);
        // 3. 明细日志落库（量大会话可改走 MQ 异步批量）
        LinkVisitLog log = new LinkVisitLog();
        log.setShortCode(shortCode);
        log.setIp(ip);
        log.setUa(ua);
        log.setReferer(referer);
        visitLogMapper.insert(log);
    }

    /**
     * 查询某日统计：PV 精确值，UV 为近似值（标准误差 0.81%）
     */
    public VisitStatVO getDailyStat(String shortCode, String date) {
        VisitStatVO vo = new VisitStatVO();
        Object pv = redisTemplate.opsForValue().get(PV_KEY + shortCode + ":" + date);
        vo.setPv(pv == null ? 0 : Long.parseLong(pv.toString()));
        vo.setUv(redisTemplate.opsForHyperLogLog().size(UV_KEY + shortCode + ":" + date));
        return vo;
    }
}
```

### 8. 跳转 Controller

```java
package com.example.shorturl.controller;

/**
 * 短链接控制器：创建 + 跳转
 */
@RestController
public class ShortLinkController {

    @Autowired
    private LinkService linkService;
    @Autowired
    private RedirectService redirectService;
    @Autowired
    private VisitStatService visitStatService;

    /**
     * 创建短链接：POST /api/short-link
     */
    @PostMapping("/api/short-link")
    public Result<String> create(@RequestBody CreateLinkRequest request) {
        String shortCode = linkService.createShortLink(request);
        return Result.ok("https://s.t.cn/" + shortCode);
    }

    /**
     * 短码跳转：GET /{shortCode}
     * 302 临时重定向，浏览器每次都会重新请求短链，统计才准确
     */
    @GetMapping("/{shortCode}")
    public void redirect(@PathVariable("shortCode") String shortCode,
                         HttpServletRequest request, HttpServletResponse response) {
        String longUrl = redirectService.resolve(shortCode);
        if (longUrl == null) {
            response.setStatus(HttpServletResponse.SC_NOT_FOUND);
            return;
        }
        response.setStatus(HttpServletResponse.SC_FOUND);
        response.setHeader("Location", longUrl);
        // 异步统计：不阻塞 302 响应
        visitStatService.recordVisit(shortCode, request.getRemoteAddr(),
                request.getHeader("User-Agent"), request.getHeader("Referer"));
    }
}
```

## 实际应用场景

### 场景一：短信营销系统

电商大促时给千万用户发营销短信，短信有字数限制，且链接不能太长：

```text
1. 运营在后台导入商品活动页长链接，批量调用创建接口生成短链
2. 短信文案里拼入短链：s.t.cn/8x2Kq，整条短信控制在 70 字以内
3. 用户点击短链：布隆过滤器命中 -> Redis 缓存命中 -> 302 跳到活动页，耗时毫秒级
4. 千万级并发点击时，99% 请求被 Redis 缓存扛住，DB 无压力
5. 运营看统计报表：该批次短链的 PV/UV、分时趋势，评估短信转化效果
6. 活动结束：运营把短链批量禁用或设置过期时间，防止链接被继续滥用
7. 财务审计：从访问日志表导出点击明细，核对短信服务商的送达与转化数据
```

### 场景二：社交平台分享与域名风控

内容平台作者分享外链，平台对外链有域名风控，作者用短链中转：

```text
1. 作者在平台内把外链转成平台短链，平台对长链接做安全扫描
2. 违规链接被检测后：平台侧禁用该短链，同时封禁源域名
3. 分享到微信/微博：短链不触发外链拦截，点击体验顺畅
4. 链接被恶意举报：运营一键禁用短码，已发出的链接全部失效
5. 平台统计所有短链的分享次数与点击率，反哺内容推荐
6. 域名被拉黑时：平台切换备用短链域名，存量短码迁移到新域名继续可用
```

### 场景三：广告投放渠道追踪

市场部在多个渠道投放广告（朋友圈、抖音、百度、信息流），需要评估每个渠道的效果：

## 最佳实践与踩坑记录

### 最佳实践

1. 短码生成用「发号器 + Base62 编码」而非随机字符串：确定性唯一、无碰撞重试、短码可反解校验
2. 布隆过滤器 + 空值缓存双防线：布隆拦截不存在的短码，空值缓存兜底布隆误判，两道防线防穿透
3. 缓存击穿用互斥锁（SETNX）重建缓存，注意双检（拿到锁后二次查缓存）避免重复查库
4. 跳转与统计解耦：跳转是同步关键路径，统计走 @Async 异步，统计故障不影响跳转
5. 跳转用 302 而非 301：301 会被浏览器缓存跳转结果，后续访问不再请求短链服务，统计丢失且无法禁用
6. 自定义短码必须校验长度、字符集、保留字，防止用户占用系统路径（如 /admin）
7. 号段发号器设置预取阈值（剩余量低于 1000 提前取号段），避免发到边界时同步阻塞

### 踩坑记录

```text
坑 1：随机短码碰撞
结论：随机生成的 6 位短码在高并发下频繁撞车，重试逻辑复杂且影响性能。
原因：随机算法靠概率保证唯一，数据量越大碰撞概率越高，没有确定性保证。
解法：改用「全局发号器 + Base62 编码」，id 天然唯一，短码无碰撞；DB 唯一索引兜底。

坑 2：布隆过滤器误判导致真实链接 404
结论：布隆过滤器把不存在的短码判为存在，回源查库后返回 404，服务正常；但把存在的判为不存在会直接 404。
原因：布隆过滤器误判方向是「可能存在」，正常流程不会误杀真实链接；问题出在过滤器未预热（重启后位图为空）。
解法：服务启动时 @PostConstruct 全量预热存量短码；判定存在后回源查库二次确认。

坑 3：热点短码缓存击穿
结论：爆款短链缓存过期瞬间，大量并发请求同时穿透到 DB，DB 连接打满。
原因：缓存过期后第一个请求还没重建完成，后续请求全部打到数据库。
解法：SETNX 互斥锁让同一短码只有一个线程重建缓存，其余线程等待后重试；生产可再叠加逻辑过期方案。

坑 4：号段发号器并发超发
结论：多实例部署后出现重复 id，短码冲突。
原因：多个实例同时 UPDATE id_segment 的 max_id，没有版本控制，互相覆盖。
解法：UPDATE 语句带 version 条件（乐观锁），影响行数为 0 则重试；保证每次只有一个实例拿到号段。

坑 5：雪花算法时钟回拨
结论：服务器 NTP 校时导致时钟回拨，生成重复 id。
原因：雪花 id 依赖时间戳，时间回拨后同一毫秒的序列号会重复。
解法：回拨超过阈值（如 5 秒）直接拒绝发号并告警；短暂回拨自旋等待时间追平；或切换号段方案。

坑 6：UV 统计内存爆炸
结论：用 Redis Set 存 UV，每天一个 key 塞几百万个 IP，内存暴涨。
原因：Set 结构每个成员都存完整字符串，百万级 UV 内存占用以 GB 计。
解法：改用 HyperLogLog，单 key 固定 12KB 内存即可统计百万级 UV，误差 0.81% 完全可接受。
```
