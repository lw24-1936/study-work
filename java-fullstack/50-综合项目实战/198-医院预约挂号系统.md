## 项目背景

医院预约挂号系统是医疗信息化里流量最大、并发最高、业务规则最复杂的系统之一。热门三甲医院的专家号放出后几秒钟就被抢空，号贩子用脚本批量抢占再高价转卖；高峰期挂号请求 QPS 上千，直接操作 MySQL 扣减号源必然超卖；患者反复抢号失败、到医院排长队，体验极差。这个项目把「高并发库存扣减」和「业务状态机」两个硬核问题揉在一起：号源预扣、定时放号、取消回补、黑名单防刷，每个环节都有明确的工程解法，是理解「Redis 原子操作 + MQ 异步化 + 分布式锁」组合拳的最佳载体。

业务痛点：

```text
1. 号源超卖：热门科室号源秒空，但并发请求下 MySQL 直接 UPDATE 库存会出现同一号源被多人约到
2. 号贩子刷号：脚本批量抢占号源再高价倒卖，真实患者约不到号
3. 放号时间不统一：各科室自己定放号规则，患者记不住时间，错过放号窗口
4. 爽约率高：约了号不到院，号源被浪费，医生空等
5. 窗口排队严重：现场挂号长队，交叉感染风险高，患者时间成本大
6. 取消预约号源不回流：号源一旦放出，取消后不能及时回到池中，造成浪费
```

目标用户与核心诉求：

```text
1. 患者：提前预约专家号、随时查询号源余量、到点收到放号提醒、线上取消预约
2. 医生：管理自己的出诊排班、设置号源数量、停诊时通知已约患者
3. 医院运营/信息科：统一放号策略、号源池管理、黑名单治理、挂号数据统计
4. 财务/窗口：线下窗口号与线上号统一管理，对账清晰
```

项目要解决的核心问题一句话概括：让号源像商品库存一样被精确管控——不超卖、不浪费、可回补、防刷号，同时把挂号高峰的数据库压力用 Redis 消化掉。

## 功能介绍

功能按角色拆成三个端：患者端（挂号）、医生端（排班）、管理端（号源管控）。

```text
一、患者端
1. 科室/医生查询 —— 按科室、医院、医生姓名、职称检索
2. 排班查询 —— 查看某医生未来 7 天出诊安排与剩余号源
3. 预约挂号 —— 选日期时段提交预约，Redis 预扣号源，MQ 异步落库
4. 放号提醒 —— 订阅心仪医生的放号时间，到点推送提醒
5. 取消预约 —— 就诊日前一天 24 点前可线上取消，号源自动回流
6. 我的预约 —— 待就诊/已就诊/已取消/爽约记录，电子挂号单（二维码）

二、医生端
1. 排班管理 —— 维护出诊日期、时段（上午/下午）、号源总量
2. 号源调整 —— 加号、停诊（停诊自动通知已约患者并退号）
3. 出诊记录 —— 查看当日已约患者名单与联系方式

三、管理端
1. 科室管理 —— 科室增删改查、排序、简介
2. 医生管理 —— 医生信息、职称、所属科室、出诊状态
3. 放号策略 —— 统一配置放号周期（提前 N 天）、放号时间点
4. 号源池监控 —— 各排班号源余量实时视图，异常告警
5. 黑名单管理 —— 刷号/恶意占号账号封禁与解封
6. 统计报表 —— 挂号量趋势、科室热度、爽约率、取消率
```

## 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 开发框架 | Spring Boot 2.7/3.x | 生态成熟，起步快 |
| 持久层 | MyBatis-Plus | 科室/医生/排班/预约记录单表 CRUD，复杂统计走自定义 SQL |
| 数据库 | MySQL 8.0 | 预约记录与排班落库，事务保证状态变更原子性 |
| 缓存与计数 | Redis | 号源池（预扣/回补原子操作）、幂等门闩、风控计数 |
| 分布式锁 | Redisson | 定时放号、取消回补等跨实例互斥场景 |
| 消息队列 | RabbitMQ | 预扣成功后异步落库，削峰 + 解耦 + 失败重试 |
| 定时任务 | XXL-Job / Spring @Scheduled | 每日定点放号、号源对账、爽约标记 |
| 前端 | Vue 3 + Element Plus / 小程序 | 医院公众号/H5 场景为主 |
| 鉴权 | Spring Security + JWT | 患者/医生/管理员三角色 |

选型说明：

```text
1. 号源扣减用 Redis Lua 脚本而非 MySQL 行锁：挂号高峰 QPS 上千，Redis 单线程原子性天然防超卖，MySQL 行锁在热点行上会排队打爆连接池
2. 预扣与落库分离：Redis 预扣成功即响应成功，落库走 MQ 异步消费，高峰期削峰；消费失败自动重试，最终一致
3. 定时放号用 Redisson 分布式锁：多实例部署时保证同一时刻只有一个实例执行放号，防止号源被重复初始化
4. 预约记录用状态机管理：待就诊/已就诊/已取消/爽约四态，非法流转直接拒绝，防止取消后又被标记就诊这类脏数据
```

```text
                           │ HTTP / JSON（JWT 鉴权）
┌──────────────────────────▼────────────────────────────────────┐

│  ┌─────────────┐ ┌─────────────┐ ┌────────────┐ ┌───────────┐ │
│  │ Controller  │ │   Service   │ │   Mapper   │ │  MQ 消费者│ │
│  │ 挂号/取消/   │ │ 预扣/状态机/ │ │ 排班/预约/  │ │ 异步落库/ │ │
│  │ 排班/黑名单  │ │ 风控/提醒    │ │ 黑名单     │ │ 停诊通知  │ │
│  └─────────────┘ └─────────────┘ └────────────┘ └───────────┘ │
└──────┬──────────────────┬──────────────────┬──────────────────┘
       │                  │                  │
┌──────▼──────┐   ┌───────▼────────┐   ┌─────▼───────┐
│   MySQL     │   │     Redis      │   │  RabbitMQ   │
│ 科室/医生/   │   │ 号源池/幂等门闩/ │   │ 落库队列/    │

└─────────────┘   └────────────────┘   └─────────────┘
```

请求链路示例（患者预约挂号）：

```text
1. 前端 POST /api/registration，JWT 校验患者身份
2. Service 校验：黑名单拦截 -> 排班存在且已放号 -> 就诊日未过期
3. Redis setIfAbsent 抢幂等门闩（用户+排班维度，30 秒 TTL），抢到才继续
4. Lua 脚本原子预扣号源：DECR reg:stock:{scheduleId}，库存不足返回失败并释放门闩
5. 预扣成功发 MQ 消息（reg.order.queue），立即返回「预约成功」
6. 消费者异步写 registration 表 + 排班已约数 +1（唯一键防重）
7. 落库失败自动重试，重试仍失败进死信队列人工处理，号源对账任务兜底
```

放号链路（每天 20:00 放第 8 天号源）：

```text
1. 定时任务触发，Redisson tryLock 抢「放号锁」，抢不到说明其他实例在做，直接返回
2. 查未来第 8 天所有排班，逐条把号源总量写入 Redis（reg:stock:{scheduleId}）
3. 排班状态置为已放号，已约数从 MySQL 回读并扣除（补发场景）
4. 读取放号提醒订阅表，对订阅了这些医生/科室的患者发推送
5. 释放分布式锁
```

## 核心实现

### 1. 号源预扣：Redis Lua 脚本原子扣减

```java
@Component
public class StockDeductScript {

    /**
     * Lua 脚本：原子完成「查库存 -> 扣减 -> 用户计数」三步
     * 脚本在 Redis 单线程内执行，天然无竞态，杜绝超卖
     */
    public static final String SCRIPT =
            "local stock = tonumber(redis.call('GET', KEYS[1]) or '-1') " ..
            "if stock < 0 then return -1 end " ..        // -1：号源未初始化
            "if stock <= 0 then return -2 end " ..       // -2：已约满
            "redis.call('DECR', KEYS[1]) " ..            // 扣减号源
            "redis.call('INCR', KEYS[2]) " ..            // 用户当日挂号次数 +1
            "redis.call('EXPIRE', KEYS[2], 86400) " ..   // 计数 24 小时有效
            "return redis.call('GET', KEYS[1])";         // 返回剩余号源

    public static final DefaultRedisScript<Long> INSTANCE = new DefaultRedisScript<>(SCRIPT, Long.class);
}
```

### 2. 预约挂号：预扣 + MQ 异步落库

```java
@Service
public class RegistrationService {

    private static final String STOCK_KEY = "reg:stock:";
    private static final String USER_KEY = "reg:user:";
    private static final String DONE_KEY = "reg:done:";

    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private RabbitTemplate rabbitTemplate;
    @Autowired
    private ScheduleMapper scheduleMapper;
    @Autowired
    private BlacklistService blacklistService;

    /**
     * 预约挂号主流程：黑名单校验 -> 幂等门闩 -> Lua 预扣 -> MQ 落库
     * 响应路径上不碰 MySQL 写操作，挂号高峰完全由 Redis 消化
     */
    public Long register(RegisterDTO dto) {
        // 1. 黑名单与风控校验
        if (blacklistService.isBlocked(dto.getUserId())) {
            throw new BizException("账号已被限制挂号，请 24 小时后再试");
        }
        // 2. 排班校验：必须存在且已放号
        DoctorSchedule schedule = scheduleMapper.selectById(dto.getScheduleId());
        if (schedule == null || schedule.getStatus() != 1) {
            throw new BizException("排班不存在或未放号");
        }
        // 3. 幂等门闩：同用户同排班 30 秒内只放行一次
        //    门闩先于扣减，扣减失败时释放门闩，保证号源不流失
        String doneKey = DONE_KEY + dto.getUserId() + ":" + dto.getScheduleId();
        Boolean first = redisTemplate.opsForValue().setIfAbsent(doneKey, "1", 30, TimeUnit.SECONDS);
        if (!Boolean.TRUE.equals(first)) {
            throw new BizException("请勿重复提交");
        }
        // 4. Lua 原子预扣号源
        Long result = redisTemplate.execute(StockDeductScript.INSTANCE,
                List.of(STOCK_KEY + dto.getScheduleId(), USER_KEY + dto.getUserId()));
        if (result == null || result < 0) {
            redisTemplate.delete(doneKey); // 释放门闩，允许稍后重试
            throw new BizException(result != null && result == -1 ? "号源未初始化" : "号源已约满");
        }
        // 5. 发 MQ 异步落库，接口立即返回成功
        rabbitTemplate.convertAndSend("reg.exchange", "reg.order", dto);
        return schedule.getId();
    }
}
```

### 3. 异步落库：MQ 消费者

```java
@Component
@RabbitListener(queues = "reg.order.queue")
public class RegistrationConsumer {

    @Autowired
    private RegistrationMapper registrationMapper;
    @Autowired
    private ScheduleMapper scheduleMapper;

    /**
     * 预扣成功后异步落库：写 registration 表 + 排班已约数 +1
     * 消费失败 RabbitMQ 自动重试；重试仍失败进死信队列人工处理
     */
    @RabbitHandler
    public void onMessage(RegisterDTO dto) {
        // 幂等：registration 表有 (user_id, schedule_id) 唯一键，重复消费插入直接报错
        Registration reg = new Registration();
        reg.setRegNo(OrderNoGenerator.next("REG"));
        reg.setUserId(dto.getUserId());
        reg.setDoctorId(dto.getDoctorId());
        reg.setScheduleId(dto.getScheduleId());
        reg.setDepartmentId(dto.getDepartmentId());
        reg.setVisitDate(dto.getVisitDate());
        reg.setTimeSlot(dto.getTimeSlot());
        reg.setFee(dto.getFee());
        reg.setStatus(0); // 待就诊
        registrationMapper.insert(reg);
        // 已约数 +1（乐观锁：UPDATE ... SET booked_count = booked_count + 1）
        scheduleMapper.incrBooked(dto.getScheduleId());
    }
}
```

### 4. 取消预约：状态机流转 + 号源回补

```java
@Service
public class CancelRegistrationService {

    private static final String STOCK_KEY = "reg:stock:";

    @Autowired
    private RegistrationMapper registrationMapper;
    @Autowired
    private ScheduleMapper scheduleMapper;
    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private RegistrationStatusMachine statusMachine;

    /**
     * 取消预约：状态机校验 -> 号源回补 -> 状态落库
     * 就诊当日 0 点后不允许线上取消，防止号源回流后无人接诊
     */
    public void cancel(Long registrationId, Long userId) {
        Registration reg = registrationMapper.selectById(registrationId);
        if (reg == null || !reg.getUserId().equals(userId)) {
            throw new BizException("预约记录不存在");
        }
        // 1. 状态机校验：只有 待就诊(0) 允许流转到 已取消(2)
        statusMachine.transit(reg.getStatus(), RegistrationStatus.CANCELED);
        // 2. 时间规则：就诊日 0 点后不可线上取消
        LocalDate today = LocalDate.now();
        if (!reg.getVisitDate().isAfter(today)) {
            throw new BizException("就诊当日不可线上取消，请到窗口办理");
        }
        // 3. 回补 Redis 号源：INCR 原子操作，取消即回流
        redisTemplate.opsForValue().increment(STOCK_KEY + reg.getScheduleId());
        // 4. 状态落库 + 已约数 -1
        reg.setStatus(2);
        reg.setCancelTime(new Date());
        registrationMapper.updateById(reg);
        scheduleMapper.decrBooked(reg.getScheduleId());
        // 5. 释放幂等门闩，允许该用户重新预约同排班
        redisTemplate.delete("reg:done:" + userId + ":" + reg.getScheduleId());
    }
}
```

### 5. 预约状态机

```java
@Component
public class RegistrationStatusMachine {

    /**
     * 状态机：0待就诊 -> 1已就诊 / 2已取消 / 3爽约
     * 已就诊/已取消/爽约均为终态，不允许再流转
     * 所有状态变更入口（就诊/取消/标记爽约）统一走此处校验
     */
    private static final Map<Integer, Set<Integer>> TRANSITIONS = Map.of(
            0, Set.of(1, 2, 3),  // 待就诊可到：已就诊/已取消/爽约
            1, Set.of(),         // 已就诊终态
            2, Set.of(),         // 已取消终态
            3, Set.of()          // 爽约终态
    );

    public void transit(int from, int to) {
        Set<Integer> allowed = TRANSITIONS.getOrDefault(from, Set.of());
        if (!allowed.contains(to)) {
            throw new BizException("非法的预约状态流转：" + from + " -> " + to);
        }
    }
}
```

### 6. 黑名单防刷

```java
@Service
public class BlacklistService {

    private static final String FAIL_KEY = "reg:fail:";
    private static final String BLACK_KEY = "blacklist:";

    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private BlacklistMapper blacklistMapper;

    /**
     * 防刷规则：
     * 1. 1 小时内挂号失败（号源满）达到 10 次 -> 拉黑 24 小时（疑似脚本刷号）
     * 2. 近 7 天爽约 2 次 -> 拉黑 7 天
     */
    public boolean isBlocked(Long userId) {
        // Redis 缓存优先
        String key = BLACK_KEY + userId;
        if (redisTemplate.opsForValue().get(key) != null) {
            return true;
        }
        // 数据库兜底（Redis 重启/缓存失效后仍能拦截）
        return blacklistMapper.countActive(userId) > 0;
    }

    /**
     * 记录一次挂号失败（号源已满），累计触发阈值进黑名单
     */
    public void recordFail(Long userId) {
        String key = FAIL_KEY + userId;
        Long count = redisTemplate.opsForValue().increment(key);
        if (count != null && count == 1) {
            redisTemplate.expire(key, 1, TimeUnit.HOURS); // 1 小时窗口
        }
        if (count != null && count >= 10) {
            addBlacklist(userId, "1小时挂号失败超10次", 24);
        }
    }

    /**
     * 拉黑：写库 + 写 Redis（TTL 与解封时间一致）
     */
    public void addBlacklist(Long userId, String reason, int hours) {
        Blacklist bl = new Blacklist();
        bl.setUserId(userId);
        bl.setReason(reason);
        bl.setDurationHours(hours);
        bl.setExpireTime(new Date(System.currentTimeMillis() + hours * 3600_000L));
        blacklistMapper.insert(bl);
        redisTemplate.opsForValue().set(BLACK_KEY + userId, "1", hours, TimeUnit.HOURS);
    }
}
```

### 7. 定时放号 + 放号提醒

```java
@Component
public class ScheduleReleaseTask {

    @Autowired
    private RedissonClient redissonClient;
    @Autowired
    private ScheduleMapper scheduleMapper;
    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private RemindService remindService;

    /**
     * 每天 20:00 放第 8 天号源（预约周期 7 天）
     * Redisson 分布式锁保证多实例部署时只有一台执行放号
     */
    @Scheduled(cron = "0 0 20 * * ?")
    public void release() {
        RLock lock = redissonClient.getLock("reg:release:lock");
        boolean acquired = false;
        try {
            // tryLock(等待5秒, 持有30秒)：抢不到说明其他实例正在放号
            acquired = lock.tryLock(5, 30, TimeUnit.SECONDS);
            if (!acquired) {
                return;
            }
            LocalDate releaseDate = LocalDate.now().plusDays(8);
            List<DoctorSchedule> schedules = scheduleMapper.selectByDate(releaseDate);
            for (DoctorSchedule s : schedules) {
                // 初始化号源池：剩余号 = 总量 - 已约数（补放号场景）
                int remain = s.getTotalCount() - s.getBookedCount();
                String key = "reg:stock:" + s.getId();
                redisTemplate.opsForValue().set(key, String.valueOf(Math.max(remain, 0)));
                // 状态置为已放号
                scheduleMapper.updateStatus(s.getId(), 1);
            }
            // 放号提醒：通知订阅了这些医生/科室的患者
            remindService.notifyRelease(releaseDate, schedules);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            log.error("放号任务被中断", e);
        } finally {
            if (acquired) {
                lock.unlock();
            }
        }
    }

    /**
     * 每小时对账：Redis 号源与 MySQL 已约数核对，发现不一致以 MySQL 为准重设
     * 兜底 MQ 消息丢失、Redis 重启等异常场景
     */
    @Scheduled(cron = "0 30 * * * ?")
    public void reconcile() {
        List<DoctorSchedule> schedules = scheduleMapper.selectReleased();
        for (DoctorSchedule s : schedules) {
            String key = "reg:stock:" + s.getId();
            String remain = redisTemplate.opsForValue().get(key);
            int expect = s.getTotalCount() - s.getBookedCount();
            if (remain == null || Integer.parseInt(remain) != expect) {
                redisTemplate.opsForValue().set(key, String.valueOf(Math.max(expect, 0)));
            }
        }
    }
}
```

## 实际应用场景

### 场景一：三甲医院公众号放号高峰

某三甲医院每日 20:00 放号，热门专家号 30 秒内抢空，高峰期挂号接口 QPS 约 1500：

```text
1. 信息科配置放号策略：提前 7 天、每天 20:00 统一放号，各科室排班由医生提前录入
2. 20:00 放号任务触发，Redisson 锁保证单实例执行，号源总量写入 Redis 号源池
3. 患者 20:00 点击挂号：黑名单校验 -> 幂等门闩 -> Lua 预扣，全程 Redis，单请求耗时毫秒级
4. 预扣成功即返回「挂号成功」，MQ 消费者异步写库，高峰期 MySQL 写压力被削平
5. 号贩子脚本 1 小时失败 10 次被风控拉黑，24 小时内无法挂号
6. 未抢到的患者订阅放号提醒，次日 20:00 前收到推送提醒
7. 对账任务每小时核对 Redis 号源与 MySQL 已约数，异常自动修正
```

### 场景二：社区卫生服务中心分时段预约

社区医院号源少、老年患者多，重点是时段管理和流程简单：

```text
1. 全科门诊按 30 分钟一个时段放号，每个时段 5 个号，患者选时段预约
2. 老年患者由家属代约，或到现场由导诊员在窗口终端代挂（source=窗口）
3. 预约成功后短信通知就诊时间与取号窗口，提前 15 分钟到场即可
4. 爽约记录进入风控：近 7 天爽约 2 次自动拉黑 7 天，号源优先给守约患者
5. 停诊场景：医生临时停诊，系统自动给已约患者发通知并退号，号源不浪费
6. 月底统计各时段就诊率，低峰时段号源缩减，优化医生出诊安排
```

### 场景三：体检中心与疫苗接种预约

体检中心按天限量、疫苗接种按批次放号，与门诊挂号共用一套号源池逻辑：

```text
1. 运营配置「体检套餐」为特殊排班：每天总量 200，分上午 120 / 下午 80
2. 到点放号后公众号推送提醒，订阅用户一键进入预约页
3. 疫苗批次到货时临时放号：管理员手动触发放号任务，号源立即上线
4. 预约即锁定当日名额，爽约号源自动回流，第二日可被再约
5. 黑名单规则复用：批量注册小号抢疫苗号被风控拦截
6. 数据报表看各批次预约率与到场率，指导下一批疫苗备货量
```

## 最佳实践与踩坑记录

### 最佳实践

1. 号源扣减必须走 Redis Lua 脚本：把「查-扣-记」三步放进一个脚本，Redis 单线程执行保证原子性，比「GET + 判断 + DECR」三步分开做安全得多
2. 幂等门闩先于扣减：setIfAbsent 抢到门闩才允许扣号源，扣减失败要释放门闩；门闩放后面会导致重复请求各扣一次号源
3. 预扣成功即响应，落库异步化：写 MySQL 的耗时从请求路径上拿掉，高峰期 QPS 能力提升一个数量级；消费失败靠 MQ 重试 + 定时对账兜底
4. 状态变更统一走状态机：预约状态机定义合法的流转集合，任何入口（取消/就诊/爽约）先校验再落库，杜绝脏状态
5. 分布式锁只锁互斥动作不锁业务：放号锁、取消锁都是短临界区（秒级），业务逻辑放锁内执行完再释放；避免把锁当万能药包住整个事务
6. Redis 与 MySQL 双写一致性用「对账任务」兜底：每小时比对号源余量与已约数，不一致以 MySQL 为准重设，容忍短暂不一致换取高峰性能
7. 风控计数全部 Redis 化：失败次数、当日挂号次数都是高频 INCR，落库会放大写压力；只有触发拉黑才写库

### 踩坑记录

```text
坑 1：号源超卖
结论：并发请求下同一号源被多个患者约到。
原因：先 GET 库存再 DECR 两步操作之间有竞态窗口，多个请求同时读到库存 1。
解法：改用 Lua 脚本原子扣减；脚本内完成查-判-扣，Redis 单线程执行无竞态。

坑 2：预扣成功但落库失败，号源凭空消失
结论：Redis 号源减了，MySQL 没有预约记录，号源流失。
原因：MQ 消费失败重试耗尽进死信队列，没有补偿。
解法：消费者幂等 + 死信队列人工处理；每小时对账任务以 MySQL 为准重设 Redis 号源，双保险。

坑 3：幂等门闩放在扣减之后
结论：重复提交时号源被扣两次。
原因：门闩在预扣之后才设置，两个请求都完成了扣减。
解法：门闩前置；扣减失败（号源满）时释放门闩，允许用户重试其他时段。

坑 4：多实例部署放号任务重复执行
结论：同一个排班号源被初始化两次，库存翻倍。
原因：定时任务在每个实例上都触发，没有互斥。
解法：Redisson tryLock 抢锁，抢不到直接返回；锁持有时间要大于任务执行时间。

坑 5：取消预约后号源不回流
结论：患者取消后号源没有回到池中，号源浪费。
原因：只改了状态，忘了 INCR 回补 Redis 号源。
解法：取消流程固定顺序：状态机校验 -> INCR 回补 -> 状态落库 -> 已约数 -1 -> 释放幂等门闩，顺序写死在代码里并加注释。

坑 6：Redis 重启后号源池丢失
结论：Redis 重启后 GET 返回 nil，所有排班「号源未初始化」。
原因：号源池没有持久化，也没有重建机制。
解法：放号对账任务每小时全量重设；Redis 配置 AOF 持久化；启动时扫描已放号排班重建号源池。
```
