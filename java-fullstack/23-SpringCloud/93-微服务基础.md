## 概述

微服务是一种架构风格，将单体应用拆分为一组小型、独立部署的服务。每个服务围绕业务能力组织，独立开发、独立部署、独立扩展。

```text
微服务的定义（Martin Fowler）：
"微服务架构是一种将单一应用开发为一组小型服务的方法，
每个服务运行在独立的进程中，服务间通过轻量级机制通信，
围绕业务能力构建，可独立部署。"
```

## 架构演进：单体 → SOA → 微服务

### 1. 单体架构（Monolithic）

```text
单体架构：所有功能打包在一个应用里，一个进程、一个数据库。
```

```text
单体应用
├── 用户模块
├── 订单模块
├── 商品模块
├── 支付模块
└── 库存模块   （都在一个 war/jar 里，共享一个数据库）
```

**优点**：
- 开发简单，部署方便
- 事务管理简单（本地事务）
- 调用无网络开销

**缺点**：
- 代码耦合，一处改动影响全局
- 无法独立扩展（只能整体扩容）
- 技术栈锁定
- 部署慢（改一行代码要部署整个应用）

### 2. SOA（面向服务架构）

```text
SOA：将功能拆分为服务，通过企业服务总线（ESB）集成。
```

**与微服务的区别**：
- SOA 服务粒度粗，微服务粒度细
- SOA 依赖 ESB（重量级），微服务轻量级通信（HTTP/RPC）
- SOA 服务间共享数据库，微服务独立数据库

### 3. 微服务（Microservices）

```text
微服务：按业务能力拆分，每个服务独立部署、独立数据库、独立扩展。
```

```text
微服务架构
├── 用户服务（独立数据库）
├── 订单服务（独立数据库）
├── 商品服务（独立数据库）
├── 支付服务（独立数据库）
└── 网关（统一入口）
```

### 三种架构对比

| 维度 | 单体 | SOA | 微服务 |
|------|------|-----|--------|
| 服务粒度 | 一个应用 | 粗粒度 | 细粒度 |
| 数据库 | 共享 | 共享 | 独立 |
| 通信 | 方法调用 | ESB | HTTP/RPC |
| 部署 | 整体部署 | 服务部署 | 独立部署 |
| 扩展 | 整体扩展 | 服务扩展 | 精细扩展 |
| 复杂度 | 低 | 中 | 高 |

## 微服务的核心特性

### 1. 服务独立部署

每个服务独立打包、独立部署、独立升级，互不影响。

### 2. 服务独立数据库

每个服务拥有自己的数据库，数据隔离，避免跨服务耦合。

### 3. 轻量级通信

服务间通过 HTTP/REST 或 RPC（gRPC、Dubbo）通信。

### 4. 围绕业务能力组织

按业务领域拆分（用户、订单、商品），而不是按技术分层。

### 5. 自动化部署

每个服务独立 CI/CD 流水线，自动化测试和部署。

## 服务拆分

服务拆分是微服务设计中最核心、最困难的决策。

### 拆分原则

```text
1. 单一职责 —— 一个服务只做一件事
2. 高内聚 —— 相关功能放一起
3. 低耦合 —— 服务间依赖最小化
4. 按业务边界 —— 按领域（订单、用户）而非技术分层
```

### 拆分策略

```text
按业务能力拆分：
用户服务、订单服务、商品服务、支付服务、库存服务

按领域驱动设计（DDD）拆分：
识别聚合根、限界上下文，按限界上下文划分服务
```

### 拆分粒度

```text
太大：退化成单体，失去微服务优势
太小：服务爆炸，运维成本高

经验法则：
- 一个服务 = 一个小团队能维护的规模
- 服务数量 = 团队数量（康威定律）
- 2 Pizza 团队（一个服务不超过一个 2 个披萨喂饱的团队）
```

### 拆分示例

```text
电商系统拆分：
├── 用户服务    —— 注册、登录、用户信息
├── 商品服务    —— 商品、分类、库存
├── 订单服务    —— 下单、订单状态
├── 支付服务    —— 支付、退款
├── 库存服务    —— 库存扣减、恢复
└── 网关        —— 统一入口
```

## 服务治理

服务治理是微服务架构的基础设施，解决服务间协作问题。

### 服务治理的内容

```text
1. 服务注册与发现 —— 服务如何找到彼此
2. 负载均衡      —— 请求如何分发到多个实例
3. 配置管理      —— 配置如何统一管理
4. 服务网关      —— 请求如何统一入口
5. 服务容错      —— 服务故障如何处理
6. 链路追踪      —— 请求如何追踪
7. 服务监控      —— 服务如何监控
```

### Spring Cloud 对应组件

| 服务治理 | Spring Cloud 组件 | 说明 |
|---------|------------------|------|
| 注册发现 | Nacos / Eureka | 服务注册中心 |
| 负载均衡 | Spring Cloud LoadBalancer | 客户端负载均衡 |
| 配置管理 | Nacos Config / Spring Cloud Config | 配置中心 |
| 服务网关 | Spring Cloud Gateway | 统一入口 |
| 服务容错 | Resilience4j / Sentinel | 熔断降级 |
| 服务调用 | OpenFeign | 声明式 HTTP 调用 |
| 链路追踪 | Micrometer Tracing / SkyWalking | 调用链追踪 |

## 服务注册与发现

服务注册与发现是微服务的基础，解决"服务如何找到彼此"。

### 问题

```text
传统单体：服务地址固定，写死在配置里
微服务：服务实例动态变化（扩容、缩容、故障），地址不固定
```

### 注册与发现流程

```text
1. 服务启动 → 向注册中心注册（服务名 + 地址）
2. 服务调用方 → 向注册中心查询服务地址列表
3. 调用方 → 负载均衡选择一个实例调用
4. 服务下线/故障 → 注册中心剔除（心跳检测）
```

```text
服务A（提供者）          注册中心           服务B（消费者）
     │ 注册(IP:8081)        │                    │
     │─────────────────────>│                    │
     │                      │  查询"服务A"地址    │
     │                      │<───────────────────│
     │                      │  返回 [8081,8082]  │
     │                      │───────────────────>│
     │<──调用(负载均衡)──────│                    │
```

### 两种发现模式

```text
客户端发现（Client-side Discovery）：
消费者直接查注册中心，自己负载均衡（Nacos + LoadBalancer）

服务端发现（Server-side Discovery）：
消费者请求负载均衡器，由负载均衡器转发（Kubernetes Service）
```

### 心跳与健康检查

```text
1. 心跳机制：服务定期向注册中心发心跳，超时未发则剔除
2. 健康检查：注册中心主动探测服务健康状态
3. 服务下线：优雅下线时主动注销
```

## 微服务的挑战

微服务不是银弹，带来了一系列新的复杂度：

```text
1. 分布式复杂性 —— 网络延迟、分布式事务、数据一致性
2. 运维复杂度 —— 部署、监控、日志、排查都更复杂
3. 数据一致性 —— 跨服务事务需要分布式方案
4. 测试复杂度 —— 集成测试、契约测试
5. 服务间通信 —— 网络故障、超时、重试
6. 组织复杂度 —— 团队协作、接口契约
```

### 何时该用微服务

```text
适合微服务：
- 团队规模大（多个团队并行开发）
- 业务复杂，模块独立
- 需要独立扩展
- 需要快速迭代

不适合微服务：
- 创业初期（MVP 阶段）
- 团队小（< 10 人）
- 业务简单
- 追求快速交付

建议：先单体，业务复杂后再拆分
```

## Spring Cloud 全景

Spring Cloud 是构建微服务的一站式解决方案。

### 核心组件

```text
Spring Cloud Netflix（已大部分进入维护模式）
├── Eureka（注册发现，被 Nacos 替代）
├── Ribbon（负载均衡，被 LoadBalancer 替代）
├── Hystrix（熔断，被 Resilience4j 替代）
└── Zuul（网关，被 Gateway 替代）

Spring Cloud Alibaba（国内主流）
├── Nacos（注册发现 + 配置中心）
├── Sentinel（限流熔断）
├── Seata（分布式事务）
└── RocketMQ（消息）

Spring Cloud 官方
├── Gateway（网关）
├── OpenFeign（服务调用）
├── LoadBalancer（负载均衡）
├── Config（配置中心）
└── Circuit Breaker（熔断抽象）
```

### 场景 2：服务注册发现配置

```yaml
# 服务提供者配置（Nacos）
spring:
  application:
    name: order-service    # 服务名（注册到 Nacos 的名字）
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
```

```java
// 服务提供者
@SpringBootApplication
@EnableDiscoveryClient   // 启用服务注册发现
public class OrderApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderApplication.class, args);
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. **先单体后微服务**。业务不复杂时不要过早拆分，微服务的复杂度成本很高。

2. **按业务能力拆分，不按技术分层**。订单服务（含 controller/service/dao）优于"controller 服务 + service 服务"。

3. **服务间通信优先同步 HTTP + 异步消息**。查询用 REST，状态变更通知用消息。

4. **每个服务独立数据库**。数据隔离是微服务的基础，共享数据库会导致耦合。

5. **服务要有健康检查**。注册中心依赖健康检查剔除故障实例。

### 踩坑记录

**坑 1：服务拆分过细**

```text
把用户服务拆成"用户查询服务"+"用户写服务"，服务数量爆炸
运维成本远超收益，接口调用链极长
```

按业务能力（领域）拆分，不要按读写/技术拆分。

**坑 2：跨服务强一致事务**

```java
// 订单服务和库存服务之间强一致事务
// 分布式事务复杂且性能差，应该用最终一致（消息 + 补偿）
```

跨服务用最终一致性（消息队列 + 补偿），避免分布式事务。

**坑 3：服务间同步调用链过长**

```text
用户请求 → 网关 → 订单服务 → 用户服务 → 库存服务 → 支付服务
同步调用链 5 层，一个服务慢，整个链路超时
```

缩短调用链，能异步的用消息异步化。

**坑 4：没有服务降级**

```text
下游服务故障，上游没有降级，导致雪崩
```

服务调用要配熔断降级（Resilience4j/Sentinel）。

**坑 5：注册中心单点故障**

```text
Nacos 单机部署，挂了整个微服务不可用
```

注册中心要集群部署，保证高可用。

**坑 6：服务接口没有版本管理**

```text
订单服务改了接口，用户服务还按旧接口调用，运行时才报错
```

服务间接口要版本管理，兼容性变更，或契约测试。
