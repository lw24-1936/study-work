## 概述

服务容错是微服务架构的"安全气囊"，保护系统在部分服务故障时依然可用。

```text
服务容错解决的问题：
1. 服务雪崩 —— 一个服务故障导致整个系统崩溃
2. 故障隔离 —— 局部故障不扩散到全局
3. 快速失败 —— 故障时快速返回，不拖垮调用方
4. 优雅降级 —— 故障时提供降级方案
```

```text
容错的常见手段：
1. 超时（Timeout）    —— 限制调用时长，避免无限等待
2. 重试（Retry）      —— 瞬时故障重试
3. 限流（RateLimiter）—— 控制流量，保护服务
4. 熔断（Circuit Breaker）—— 故障累积后快速失败
5. 降级（Fallback）   —— 故障时返回兜底结果
6. 隔离（Bulkhead）   —— 资源隔离，防止相互影响
```

## 服务雪崩

### 什么是服务雪崩

```text
服务雪崩：一个服务故障，引发级联故障，最终整个系统不可用。

示例：
服务 A 依赖服务 B，B 故障响应慢
→ A 的线程被 B 拖住（等待 B 响应）
→ A 的线程池耗尽，A 也无法响应
→ 依赖 A 的服务 C、D 也被拖垮
→ 级联扩散，整个系统雪崩
```

```text
服务 A（线程池满）→ 服务 B（故障）
     ↑                    ↓
服务 C（也被拖垮）← 服务 D（调用 A 超时）
```

### 雪崩的成因

```text
1. 服务故障（响应慢/宕机）
2. 流量突增（超出服务处理能力）
3. 依赖链过长（级联风险大）
4. 资源耗尽（线程池、连接池满）
```

### 防雪崩的手段

```text
超时 → 不让请求无限等待
限流 → 控制入口流量
熔断 → 故障时快速失败，不继续调用
降级 → 返回兜底结果
隔离 → 防止资源相互影响
```

## Circuit Breaker 熔断器

熔断器是服务容错的核心模式，模拟电路中的保险丝。

### 熔断器状态机

```text
        ┌──────────────┐
        │   关闭(Closed) │  ← 正常状态，请求正常通过
        └──────┬───────┘
               │ 失败率超过阈值
               ▼
        ┌──────────────┐
        │   打开(Open)   │  ← 熔断状态，请求直接失败（快速失败）
        └──────┬───────┘
               │ 冷却时间到
               ▼
        ┌──────────────┐
        │  半开(HalfOpen)│  ← 放行少量请求试探
        └──────┬───────┘
               │ 试探成功 → 关闭
               │ 试探失败 → 打开
               ▼
           回到关闭/打开
```

### 三个状态

| 状态 | 说明 | 行为 |
|------|------|------|
| Closed（关闭） | 正常状态 | 请求正常通过，统计失败率 |
| Open（打开） | 熔断状态 | 请求直接失败（不调用下游） |
| Half-Open（半开） | 试探状态 | 放行少量请求，成功则关闭，失败则再打开 |

### 熔断的关键参数

```text
1. 失败率阈值（failureRateThreshold）—— 失败率超过多少熔断（如 50%）
2. 最小请求数（minimumNumberOfCalls）—— 达到多少请求才开始统计
3. 熔断时长（waitDurationInOpenState）—— 熔断后多久进入半开
4. 滑动窗口（slidingWindowSize）—— 统计窗口大小
```

## Resilience4j

Resilience4j 是 Spring Cloud 官方推荐的容错库，提供熔断、限流、重试、隔离、超时等能力。

### 引入依赖

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>
</dependency>
```

### 1. CircuitBreaker（熔断）

```yaml
resilience4j:
  circuitbreaker:
    instances:
      user-service:
        sliding-window-size: 10          # 滑动窗口大小
        minimum-number-of-calls: 5       # 最小请求数
        failure-rate-threshold: 50       # 失败率阈值（50%）
        wait-duration-in-open-state: 10s # 熔断后等待时间
        permitted-number-of-calls-in-half-open-state: 3  # 半开状态放行数
```

```java
@Service
public class UserService {

    @Autowired
    private CircuitBreakerFactory circuitBreakerFactory;

    public User getUser(Long id) {
        CircuitBreaker breaker = circuitBreakerFactory.create("user-service");
        return breaker.run(
            () -> userClient.getUser(id),       // 正常调用
            throwable -> fallbackUser(id)       // 降级
        );
    }
}
```

```java
// 注解方式
@CircuitBreaker(name = "user-service", fallbackMethod = "fallbackUser")
public User getUser(Long id) {
    return userClient.getUser(id);
}

public User fallbackUser(Long id, Throwable t) {
    // 降级逻辑
    return new User(id, "服务不可用");
}
```

### 2. Retry（重试）

```yaml
resilience4j:
  retry:
    instances:
      user-service:
        max-attempts: 3              # 最大重试次数
        wait-duration: 1s            # 重试间隔
        retry-exceptions:            # 哪些异常重试
          - java.net.SocketTimeoutException
```

```java
@Retry(name = "user-service", fallbackMethod = "fallback")
public User getUser(Long id) {
    return userClient.getUser(id);
}
```

### 3. RateLimiter（限流）

```yaml
resilience4j:
  ratelimiter:
    instances:
      api-limiter:
        limit-for-period: 100        # 每个周期允许的请求数
        limit-refresh-period: 1s     # 刷新周期
        timeout-duration: 0s         # 等待超时
```

```java
@RateLimiter(name = "api-limiter", fallbackMethod = "rateLimitFallback")
public Result process() {
    // ...
}
```

### 4. Bulkhead（隔离）

```yaml
resilience4j:
  bulkhead:
    instances:
      user-service:
        max-concurrent-calls: 10     # 最大并发调用数
        max-wait-duration: 10ms      # 最大等待时间
```

```java
@Bulkhead(name = "user-service", fallbackMethod = "bulkheadFallback")
public User getUser(Long id) {
    return userClient.getUser(id);
}
```

### 5. Timeout（超时）

```yaml
resilience4j:
  timelimiter:
    instances:
      user-service:
        timeout-duration: 3s         # 超时时间
```

```java
@TimeLimiter(name = "user-service", fallbackMethod = "timeoutFallback")
public CompletableFuture<User> getUser(Long id) {
    // 异步调用
}
```

### 五种模式总结

| 模式 | 解决的问题 | 关键参数 |
|------|-----------|---------|
| CircuitBreaker | 故障累积后快速失败 | 失败率阈值、熔断时长 |
| Retry | 瞬时故障 | 重试次数、间隔 |
| RateLimiter | 流量控制 | 限流阈值 |
| Bulkhead | 资源隔离 | 最大并发数 |
| TimeLimiter | 调用超时 | 超时时间 |

## Sentinel

Sentinel 是阿里巴巴开源的流量防护组件，比 Resilience4j 功能更丰富，更适合国内场景。

### 引入依赖

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-sentinel</artifactId>
</dependency>
```

### 配置

```yaml
spring:
  cloud:
    sentinel:
      transport:
        dashboard: localhost:8080   # Sentinel 控制台地址
      eager: true                   # 启动时初始化
```

### 注解方式

```java
@Service
public class UserService {

    // 限流：QPS 超过 10 触发限流
    @SentinelResource(value = "getUser", blockHandler = "getUserBlocked", fallback = "getUserFallback")
    public User getUser(Long id) {
        return userClient.getUser(id);
    }

    // 限流/降级处理
    public User getUserBlocked(Long id, BlockException e) {
        // 被限流或熔断
        return new User(id, "请求过于频繁");
    }

    // 异常降级处理
    public User getUserFallback(Long id, Throwable t) {
        return new User(id, "服务异常");
    }
}
```

### 控制台规则

```text
Sentinel 控制台可配置：
1. 流控规则 —— QPS、线程数、关联、链路
2. 降级规则 —— RT、异常比例、异常数
3. 热点规则 —— 热点参数限流
4. 系统规则 —— 系统级保护（LOAD、RT、CPU）
5. 授权规则 —— 黑白名单
```

### Sentinel vs Resilience4j

| 维度 | Resilience4j | Sentinel |
|------|-------------|----------|
| 来源 | Spring Cloud 官方 | 阿里巴巴 |
| 功能 | 熔断、限流、重试、隔离 | 熔断、限流、热点、系统保护 |
| 控制台 | 无（需集成） | 有（可视化） |
| 规则动态配置 | 有限 | 强大（控制台实时） |
| 适用场景 | 通用 | 国内、需可视化管控 |

## Fallback 降级

降级是故障时的兜底方案，保证服务"可用"（返回降级结果）。

### 降级策略

```text
1. 返回默认值 —— 返回兜底数据（如默认用户）
2. 返回缓存 —— 返回上次成功的缓存结果
3. 返回空列表 —— 列表接口降级返回空
4. 快速失败 —— 直接抛错（至少不拖垮调用方）
5. 降级页面 —— 前端展示降级提示
```

### 降级实现

```java
@Service
public class UserService {

    @Autowired
    private StringRedisTemplate redisTemplate;

    @CircuitBreaker(name = "user-service", fallbackMethod = "getUserFallback")
    public User getUser(Long id) {
        return userClient.getUser(id);
    }

    // 降级：优先返回缓存，无缓存返回默认
    public User getUserFallback(Long id, Throwable t) {
        // 1. 尝试从缓存获取
        String cached = redisTemplate.opsForValue().get("user:" + id);
        if (cached != null) {
            return JSON.parseObject(cached, User.class);
        }
        // 2. 返回默认用户
        User user = new User();
        user.setId(id);
        user.setUsername("服务暂不可用");
        return user;
    }
}
```

### 降级的层次

```text
服务内降级：方法级降级（熔断、限流触发）
服务间降级：调用下游失败时降级
网关降级：网关层降级（限流、熔断）
页面降级：前端降级提示
```

## 应用场景实战

### 场景 1：完整的容错配置（Resilience4j）

```yaml
resilience4j:
  circuitbreaker:
    instances:
      user-service:
        sliding-window-size: 20
        failure-rate-threshold: 50
        wait-duration-in-open-state: 10s
        permitted-number-of-calls-in-half-open-state: 3
  retry:
    instances:
      user-service:
        max-attempts: 3
        wait-duration: 1s
  timelimiter:
    instances:
      user-service:
        timeout-duration: 3s
```

```java
@Service
public class UserService {

    @CircuitBreaker(name = "user-service", fallbackMethod = "fallback")
    @Retry(name = "user-service")
    public User getUser(Long id) {
        return userClient.getUser(id);
    }

    public User fallback(Long id, Throwable t) {
        log.error("调用 user-service 失败：{}", t.getMessage());
        return cachedOrDefault(id);
    }
}
```

### 场景 2：网关限流保护（Sentinel）

```yaml
spring:
  cloud:
    sentinel:
      transport:
        dashboard: localhost:8080
      scg:
        fallback:
          mode: response
          response-status: 429
          response-body: '{"code":429,"msg":"请求过于频繁"}'
```

```yaml
# 网关路由集成 Sentinel 限流
spring:
  cloud:
    gateway:
      routes:
        - id: user-service
          uri: lb://user-service
          predicates:
            - Path=/api/user/**
          filters:
            - name: Sentinel
```

### 场景 3：Feign 降级（服务间容错）

```java
@FeignClient(name = "user-service", fallbackFactory = UserClientFallbackFactory.class)
public interface UserClient {
    @GetMapping("/users/{id}")
    User getUser(@PathVariable("id") Long id);
}

@Component
public class UserClientFallbackFactory implements FallbackFactory<UserClient> {
    @Override
    public UserClient create(Throwable cause) {
        return id -> {
            // 降级：返回默认用户
            log.warn("调用 user-service 降级，原因：{}", cause.getMessage());
            User user = new User();
            user.setId(id);
            user.setUsername("服务不可用");
            return user;
        };
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. **容错配置要分层**。网关层限流、服务间熔断、服务内降级，层层防护。

2. **降级要返回有意义的数据**。降级返回默认值/缓存，而不是空，让前端能展示。

3. **超时时间要合理**。超时太短导致误判，太长导致资源占用。普通接口 3-5 秒。

4. **熔断阈值要调优**。失败率阈值太低（如 20%）会频繁熔断，太高（如 90%）起不到保护。

5. **降级要记录日志**。降级发生要告警，说明下游有问题，不能静默。

### 踩坑记录

**坑 1：fallback 方法签名错误**

```java
@CircuitBreaker(name = "user-service", fallbackMethod = "fallback")
public User getUser(Long id) { ... }

// fallback 方法签名必须与业务方法一致（参数 + 返回值 + Throwable）
public User fallback(Long id, Throwable t) { ... }   // 正确

public String fallback(Long id) { ... }              // 错误：返回类型不一致
```

fallback 方法的参数（+Throwable）和返回类型必须与业务方法兼容。

**坑 2：熔断和重试的顺序**

```text
如果同时配置重试和熔断，执行顺序影响结果：
重试在熔断内 → 熔断统计的是重试后的结果
熔断在重试外 → 熔断触发后不再重试

建议：重试针对瞬时故障，熔断针对持续故障，合理配置
```

**坑 3：降级返回 null 导致 NPE**

```java
public User fallback(Long id, Throwable t) {
    return null;   // 降级返回 null，调用方没处理，NPE
}
```

降级要返回有意义的数据（默认值/缓存），不要让调用方拿到 null。

**坑 4：Sentinel 规则不持久化**

```text
Sentinel 控制台配置的规则默认存储在内存，
服务重启后规则丢失
```

生产环境配置规则持久化（推模式，规则存 Nacos/数据库）。

**坑 5：限流阈值设置不合理**

```yaml
resilience4j:
  ratelimiter:
    instances:
      api:
        limit-for-period: 10     # 每秒 10 个，正常流量都 100，误伤大量请求
```

限流阈值要基于实际流量和压测结果设置，不能拍脑袋。

**坑 6：忘记配置超时**

```java
@FeignClient(name = "user-service")
public interface UserClient { ... }
// 没配置超时，默认可能很长，下游故障时线程一直等待，拖垮服务
```

服务间调用必须配置超时，且配合熔断，防止无限等待。
