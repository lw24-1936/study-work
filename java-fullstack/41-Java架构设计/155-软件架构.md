## 概述

软件架构是系统的顶层设计，决定系统的结构、组件关系、技术选型，影响系统的可维护性、可扩展性。

```text
架构解决的核心问题：
1. 组织代码 —— 如何划分模块、分层
2. 管理依赖 —— 模块之间如何依赖
3. 解耦 —— 如何降低耦合，提升扩展性
4. 演进 —— 架构如何适应需求变化
```

```text
好的架构特征：
1. 高内聚低耦合 —— 模块内紧密，模块间松耦合
2. 可维护 —— 易理解、易修改
3. 可扩展 —— 加功能不改现有代码
4. 可测试 —— 模块可独立测试
```

## 架构风格

### 常见架构风格

| 架构风格 | 核心思想 | 适用 |
|---------|---------|------|
| 分层架构 | 按层次组织 | 传统企业应用 |
| 六边形架构 | 端口适配器隔离 | 领域驱动 |
| 微服务 | 按业务拆分服务 | 大型复杂系统 |
| 事件驱动 | 事件解耦 | 高并发、异步 |
| 单体架构 | 一个应用 | 简单小应用 |

## 分层架构

分层架构是最经典的架构风格，按职责分层，上层依赖下层。

### 经典三层

```text
表现层（Controller）→ 业务层（Service）→ 数据层（Repository/DAO）
```

```text
各层职责：
表现层 —— 接收请求、参数校验、返回响应
业务层 —— 业务逻辑、事务
数据层 —— 数据存取
```

### 分层架构的优缺点

```text
优点：
1. 职责清晰 —— 各层各司其职
2. 易理解 —— 结构简单
3. 易测试 —— 分层隔离

缺点：
1. 层间耦合 —— 上层强依赖下层
2. 改动传递 —— 底层改动影响所有上层
3. 领域逻辑分散 —— 业务逻辑可能散落各层
```

## 六边形架构

六边形架构（端口适配器架构）把核心业务和外部依赖隔离。

### 六边形架构的思想

```text
核心：业务逻辑（领域）在中心，外部依赖通过端口/适配器接入

端口（Port）—— 定义的接口（业务需要的抽象）
适配器（Adapter）—— 实现接口，连接外部
```

```text
        ┌─────────────────┐
        │   领域（核心）    │
        └────────┬────────┘
      Port（端口，接口）
    ┌─────┴─────┐
  输入适配器   输出适配器
  （Controller）（Repository 实现）
  外部：Web    外部：数据库
```

### 六边形架构的价值

```text
1. 领域独立 —— 核心业务不依赖外部（数据库、框架）
2. 易替换 —— 换数据库/框架，改适配器即可
3. 可测试 —— 领域可独立测试
```

```java
// 端口（领域定义的接口）
public interface OrderRepository {
    Order save(Order order);
    Optional<Order> findById(Long id);
}

// 适配器（实现端口，连接数据库）
@Repository
public class JpaOrderRepository implements OrderRepository {
    @Autowired
    private JpaOrderDao dao;
    // 实现接口，连接 JPA
}
```

## MVC、MVP 与 MVVM

三者是表现层的组织模式，解决 UI 和业务逻辑的分离。

### MVC（Model-View-Controller）

```text
Model（模型）—— 数据 + 业务逻辑
View（视图）—— 展示
Controller（控制器）—— 接收输入，协调 Model 和 View
```

```text
MVC 流程：
用户 → Controller → Model → View → 用户

Spring MVC 就是 MVC：Controller + Service（Model）+ 模板（View）
```

### MVP（Model-View-Presenter）

```text
MVP 是 MVC 的变体，Presenter 替代 Controller：
1. View 不直接访问 Model（完全隔离）
2. Presenter 是 View 和 Model 的中间人
3. View 更薄，逻辑都在 Presenter（便于测试）
```

### MVVM（Model-View-ViewModel）

```text
MVVM 引入 ViewModel，用数据绑定：
1. ViewModel 持有 View 的状态
2. 数据绑定（双向）自动同步 View 和 ViewModel
3. 前端框架（Vue/React）常用
```

### 三者对比

| 模式 | 中间层 | 特点 | 场景 |
|------|--------|------|------|
| MVC | Controller | 经典，简单 | 后端 Web |
| MVP | Presenter | View 完全隔离 | 桌面/Android |
| MVVM | ViewModel | 数据绑定 | 前端框架 |

```text
后端 Java 开发主要用 MVC（Spring MVC），
前端开发主要用 MVVM（Vue/React），
MVP 在 Android/桌面开发常见。
```

## Clean Architecture 与 Onion Architecture

两者是分层架构的进阶，核心思想都是"依赖指向内层"。

### Onion Architecture（洋葱架构）

```text
洋葱架构：核心领域在最内层，外层依赖内层

层次（从内到外）：
领域模型（Domain Model）→ 领域服务 → 应用服务 → 基础设施/UI
```

```text
核心规则：依赖只能从外层指向内层
（内层不知道外层的存在）
```

### Clean Architecture（整洁架构）

```text
Clean Architecture 是 Robert Martin 提出，和洋葱架构思想一致：

依赖规则：
1. 源代码依赖只能指向内层
2. 内层的圆不依赖外层的圆
3. 外层的变更不影响内层
```

```text
层次（从内到外）：
实体（Entities）→ 用例（Use Cases）→ 接口适配器 → 框架/驱动
```

### 三者的共同点

```text
分层架构 / 六边形 / 洋葱 / 整洁架构的共同思想：
1. 核心业务独立 —— 领域不依赖框架、数据库
2. 依赖倒置 —— 依赖指向抽象（内层）
3. 可测试 —— 核心可独立测试
4. 可替换 —— 换框架/数据库不影响核心
```

## 微服务架构

微服务架构把系统拆成多个独立的小服务（详见 156）。

### 微服务的核心

```text
1. 按业务拆分 —— 每个服务一个业务域
2. 独立部署 —— 服务独立开发、部署、扩展
3. 独立数据 —— 每个服务独立数据库
4. 服务通信 —— 服务间通过 API/消息通信
```

```text
微服务的优缺点：
优点：独立部署、技术异构、弹性扩展、故障隔离
缺点：分布式复杂性、运维成本高、数据一致性难
```

## 事件驱动架构

事件驱动架构通过事件解耦服务，适合高并发、异步场景。

### 事件驱动架构的思想

```text
服务之间不直接调用，而是通过事件通信：
服务 A 发布事件 → 事件总线 → 服务 B/C 订阅处理
```

```text
        ┌──────────┐
        │ 订单服务  │ ──发布"订单已创建"事件──→ 消息队列
        └──────────┘                              │
                                ┌─────────┬───────┴────────┐
                                │         │                │
                           ┌────▼───┐ ┌───▼────┐      ┌────▼───┐
                           │库存服务 │ │通知服务 │      │统计服务 │
                           └────────┘ └────────┘      └────────┘
```

### 事件驱动架构的价值

```text
1. 解耦 —— 发布者不知道订阅者
2. 异步 —— 非关键流程异步处理
3. 弹性 —— 新增消费者不影响现有服务
```

## 架构选型

### 选型考量

```text
1. 系统规模 —— 小系统单体，大系统微服务
2. 团队规模 —— 小团队单体，大团队微服务
3. 业务复杂度 —— 复杂业务 DDD + 六边形
4. 性能要求 —— 高并发事件驱动
```

### 架构演进

```text
单体 → 模块化单体 → 微服务 → 事件驱动/服务网格

不要过度设计：小项目直接用微服务是灾难
从单体开始，需求复杂了再拆分
```

## 最佳实践

1. **从单体开始**。小项目别急着微服务，复杂了再拆。

2. **高内聚低耦合**。模块内紧密，模块间松耦合。

3. **面向接口编程**。依赖抽象（接口），不依赖具体实现。

4. **领域独立**。核心业务不依赖框架、数据库（六边形架构）。

5. **架构要演进**。架构随需求演进，不一蹴而就。
