## 概述

微服务架构把单体系统拆分成多个独立的小服务，每个服务独立开发、部署、扩展。

```text
微服务 vs 单体：
单体 —— 一个应用，所有功能在一起
微服务 —— 多个服务，按业务拆分
```

```text
微服务架构的完整技术栈（Spring Cloud）：
服务注册发现 —— Nacos
服务通信 —— OpenFeign / RestTemplate
服务网关 —— Gateway
服务容错 —— Resilience4j / Sentinel
服务配置 —— Nacos Config
服务追踪 —— Sleuth / SkyWalking
```

## 服务拆分

服务拆分是微服务的第一步，按业务域拆分单体。

### 拆分原则

```text
1. 单一职责 —— 每个服务一个业务职责
2. 高内聚 —— 相关功能在一个服务
3. 低耦合 —— 服务间依赖少
4. 独立数据 —— 每个服务独立数据库
```

### 拆分示例

```text
电商单体 → 微服务拆分：
用户服务（注册、登录、用户信息）
商品服务（商品管理、库存）
订单服务（下单、订单管理）
支付服务（支付、退款）
```

### 拆分的度

```text
拆得太粗 —— 还是大单体（没拆到位）
拆得太细 —— 服务太多，运维成本高（过度拆分）

经验：先按业务域拆，团队能独立负责为准
```

## 服务注册与发现

服务注册与发现让服务实例动态管理（详见 94-Nacos）。

### 注册与发现流程

```text
1. 服务启动 → 注册到注册中心（Nacos）
2. 调用方 → 从注册中心获取服务实例列表
3. 调用方 → 负载均衡选择一个实例调用
4. 服务下线 → 注册中心移除实例
```

```text
注册中心：Nacos、Eureka、Consul、Zookeeper
主流选择：Nacos（阿里，功能全）
```

## 服务通信

服务间通信有同步（HTTP/RPC）和异步（消息）两种方式。

### 通信方式对比

| 方式 | 协议 | 场景 | 代表 |
|------|------|------|------|
| REST | HTTP | 通用 | OpenFeign |
| RPC | 二进制 | 高性能 | Dubbo |
| 消息 | 异步 | 解耦、削峰 | RocketMQ |

### OpenFeign（同步通信）

```java
@FeignClient(name = "user-service")
public interface UserClient {
    @GetMapping("/api/users/{id}")
    User getUser(@PathVariable Long id);
}

// 调用
User user = userClient.getUser(1L);
```

### 异步通信（消息）

```text
订单创建 → 发布事件 → 库存服务/通知服务异步处理
（解耦，削峰，详见 91-RabbitMQ）
```

## 服务网关

服务网关是微服务的统一入口（详见 95-Gateway）。

### 网关的职责

```text
1. 路由 —— 请求转发到对应服务
2. 鉴权 —— 统一身份认证
3. 限流 —— 保护后端服务
4. 日志 —— 统一请求日志
5. 灰度 —— 灰度发布
```

```yaml
# Gateway 路由配置
spring:
  cloud:
    gateway:
      routes:
        - id: user-service
          uri: lb://user-service
          predicates:
            - Path=/api/users/**
```

## 服务容错

服务容错防止服务故障级联（详见 98-服务容错）。

### 容错机制

```text
1. 熔断 —— 故障服务快速失败，防止级联
2. 降级 —— 服务不可用时返回兜底结果
3. 重试 —— 临时故障重试
4. 限流 —— 控制请求量
5. 超时 —— 防止长时间等待
```

## 服务配置与监控

### 服务配置（Nacos Config）

```text
配置中心集中管理配置：
1. 配置集中 —— 统一管理
2. 动态刷新 —— 改配置不重启
3. 环境隔离 —— 开发/测试/生产
```

### 服务监控

```text
1. 日志 —— 集中日志（ELK）
2. 指标 —— 监控指标（Prometheus + Grafana）
3. 追踪 —— 链路追踪（SkyWalking）
4. 告警 —— 异常告警
```

## 应用场景实战

### 场景 1：微服务完整架构

```text
电商微服务架构：
        ┌──────────┐
        │  Gateway  │（统一入口：路由/鉴权/限流）
        └────┬─────┘
      ┌──────┼──────┐
   ┌──▼──┐ ┌──▼──┐ ┌──▼──┐
   │用户  │ │订单  │ │商品  │  （服务）
   └──┬──┘ └──┬──┘ └──┬──┘
      │  Nacos（注册中心 + 配置中心）
      │  消息队列（异步通信）
      │  Sentinel（容错）
```

### 场景 2：微服务拆分决策

```text
拆分前评估：
1. 业务复杂度 —— 业务多、团队大才拆
2. 团队规模 —— 一个服务一个团队
3. 运维能力 —— 微服务运维成本高

结论：小项目/小团队用单体，大了再拆
```

## 最佳实践与踩坑记录

### 最佳实践

1. **不要过早微服务**。单体够用就别拆，复杂了再拆。

2. **服务要独立部署**。每个服务独立数据库、独立部署。

3. **服务间异步通信优先**。能异步的不用同步调用。

4. **统一技术栈**。避免每个服务技术栈不同，运维复杂。

5. **完善的监控**。微服务分布式，必须要有日志、追踪、监控。

### 踩坑记录

**坑 1：过早微服务化**

```text
小项目直接上微服务，分布式复杂性（网络、一致性）远超收益
```

从单体开始，业务复杂、团队大了再拆。

**坑 2：服务拆得太细**

```text
几百个微服务，运维成本爆炸
```

按业务域拆分，不要过度拆分。

**坑 3：分布式事务处理不当**

```text
跨服务事务用强一致性，性能差、复杂度高
```

优先用最终一致性（消息 + 补偿），详见 102-分布式事务。

**坑 4：忽略服务间超时**

```text
同步调用不设超时，服务故障时线程堆积
```

所有服务间调用都要设超时。

**坑 5：共享数据库**

```text
多个服务共享一个数据库，数据耦合，无法独立演进
```

每个服务独立数据库。

**坑 6：缺少链路追踪**

```text
微服务调用链长，出问题难定位
```

必须上链路追踪（SkyWalking 等）。
