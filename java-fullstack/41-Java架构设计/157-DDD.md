## 概述

DDD（Domain-Driven Design，领域驱动设计）是以业务领域为核心的软件设计方法，让代码结构反映业务模型。

```text
DDD 解决的核心问题：
1. 业务复杂 —— 复杂业务逻辑难以用传统 CRUD 表达
2. 业务和技术脱节 —— 代码看不懂业务
3. 沟通困难 —— 业务人员和技术人员说不到一块
```

```text
DDD 的两大层面：
1. 战略设计 —— 划分限界上下文（大方向）
2. 战术设计 —— 建模（实体、值对象、聚合）
```

## 战略设计

战略设计解决"如何划分业务边界"，核心是限界上下文。

### 战略设计的要素

```text
1. 领域（Domain）—— 业务范围
2. 子域（Subdomain）—— 领域的子集
3. 限界上下文（Bounded Context）—— 业务边界
4. 上下文映射（Context Map）—— 上下文之间的关系
```

### 子域分类

```text
1. 核心域（Core Domain）—— 核心竞争力（重点投入）
2. 支撑域（Supporting）—— 支撑核心域
3. 通用域（Generic）—— 通用能力（可外包/采购）
```

```text
电商的例子：
核心域 —— 交易（订单、支付）
支撑域 —— 库存、物流
通用域 —— 用户认证（可用现成的）
```

## 限界上下文

限界上下文是 DDD 最重要的概念，定义业务边界和模型边界。

### 限界上下文是什么

```text
限界上下文 = 一个业务边界，边界内模型一致，边界外模型可以不同
```

```text
关键：同一个"概念"在不同上下文可以有不同的含义

例：电商中的"商品"
商品上下文：商品（名称、价格、规格）
库存上下文：商品（库存量、仓库位置）
物流上下文：商品（重量、体积、运输）

三个上下文的"商品"是不同的模型
```

### 上下文映射关系

```text
1. 共享内核 —— 共享部分模型
2. 客户-供应商 —— 一方依赖另一方
3. 防腐层（ACL）—— 隔离外部模型
4. 开放主机服务 —— 提供 API 给其他上下文
```

## 战术设计

战术设计解决"如何在限界上下文内建模"，核心是实体、值对象、聚合。

### 战术设计的构建块

| 构建块 | 说明 | 特点 |
|--------|------|------|
| Entity 实体 | 有唯一标识 | 可变 |
| Value Object 值对象 | 无标识，值相等 | 不可变 |
| Aggregate 聚合 | 实体+值对象的组合 | 一致性边界 |
| 领域服务 | 不属于实体的业务逻辑 | 无状态 |
| 领域事件 | 领域发生的事实 | 不可变 |
| Repository | 聚合的存取 | 持久化 |

## Entity 实体

实体是有唯一标识的对象，标识在生命周期内不变。

### 实体的特征

```text
1. 有唯一标识（ID）
2. 可变（属性会变化）
3. 通过标识判断相等
```

```java
public class User {
    private Long id;          // 唯一标识
    private String name;
    private String email;

    // 通过 id 判断相等
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User)) return false;
        return id.equals(((User) o).id);
    }
}
```

## Value Object 值对象

值对象没有唯一标识，通过属性值判断相等，是不可变的。

### 值对象的特征

```text
1. 无唯一标识
2. 不可变（创建后不修改）
3. 通过属性判断相等
```

```java
// 金额（值对象）
public class Money {
    private final BigDecimal amount;   // 不可变（final）
    private final String currency;

    public Money(BigDecimal amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }

    // 不可变：运算返回新对象
    public Money add(Money other) {
        return new Money(amount.add(other.amount), currency);
    }

    // 通过值判断相等
    @Override
    public boolean equals(Object o) {
        Money money = (Money) o;
        return amount.equals(money.amount) && currency.equals(money.currency);
    }
}
```

### 实体 vs 值对象

| 维度 | 实体 | 值对象 |
|------|------|--------|
| 标识 | 有（ID） | 无 |
| 可变性 | 可变 | 不可变 |
| 相等 | 按 ID | 按值 |
| 例子 | User、Order | Money、Address、日期 |

## Aggregate 聚合与聚合根

聚合是一组相关实体和值对象的组合，聚合根是聚合的入口。

### 聚合的意义

```text
聚合定义一致性边界：
1. 聚合内保证一致性（一起修改）
2. 跨聚合通过聚合根访问
3. 一次事务只修改一个聚合
```

### 聚合根

```text
聚合根 = 聚合的入口，外部只能通过聚合根访问聚合内部
```

```java
// 订单聚合（聚合根 = Order）
public class Order {          // 聚合根
    private Long id;
    private Long userId;
    private List<OrderItem> items;   // 订单明细（聚合内部）

    // 聚合根控制内部对象的修改
    public void addItem(Product product, int quantity) {
        items.add(new OrderItem(product, quantity));
        recalculateTotal();   // 聚合内保持一致性
    }
}
```

```text
聚合的设计原则：
1. 通过聚合根访问 —— 外部不直接访问聚合内部对象
2. 聚合要小 —— 聚合太大难以保证一致性
3. 聚合间通过 ID 引用 —— 不直接引用其他聚合对象
```

## 领域服务与领域事件

### 领域服务

领域服务是不属于任何实体/值对象的业务逻辑。

```text
什么时候用领域服务：
业务逻辑涉及多个聚合，不属于单个实体
```

```java
// 领域服务：转账（涉及两个账户聚合）
public class TransferService {
    public void transfer(Account from, Account to, Money amount) {
        from.debit(amount);    // 扣款
        to.credit(amount);     // 入账
    }
}
```

### 领域事件

领域事件是领域内发生的事实，用于解耦和异步。

```java
// 领域事件
public class OrderCreatedEvent {
    private Long orderId;
    private Long userId;
    private Date createdAt;
}

// 发布领域事件
eventPublisher.publish(new OrderCreatedEvent(order.getId(), ...));

// 订阅领域事件
@EventListener
public void onOrderCreated(OrderCreatedEvent event) {
    // 发通知、扣库存等
}
```

### 应用服务（Application Service）

应用服务是应用层的编排者，协调领域对象完成用例（不属于领域层）。

```java
// 应用服务：编排用例（在 application 层，不是 domain 层）
@Service
public class OrderApplicationService {

    @Autowired
    private OrderRepository orderRepository;
    @Autowired
    private OrderFactory orderFactory;

    @Transactional
    public Long createOrder(Long userId, List<CartItemDTO> items) {
        // 1. 用工厂创建聚合
        Order order = orderFactory.createOrder(userId, items);
        // 2. 持久化（通过仓储）
        orderRepository.save(order);
        // 3. 发布领域事件
        eventPublisher.publish(new OrderCreatedEvent(order.getId(), userId));
        return order.getId();
    }
}
```

### 领域服务 vs 应用服务 vs 领域事件

| 概念 | 层次 | 职责 |
|------|------|------|
| 领域服务 | 领域层 | 跨聚合的业务规则 |
| 应用服务 | 应用层 | 编排用例、事务边界 |
| 领域事件 | 领域层 | 领域事实（解耦/异步） |

```text
关键区分：
领域服务 —— 纯业务逻辑（无事务、无持久化，在 domain 层）
应用服务 —— 编排（事务、调仓储，在 application 层）

应用服务调用领域服务 + 仓储 + 发布领域事件
```

## 应用场景实战

### 场景 1：电商订单 DDD 建模

```text
限界上下文：订单上下文

聚合：
- Order（聚合根）—— 订单 + 订单明细
- 关联：通过 userId 引用用户（跨聚合用 ID）

实体：
- Order（有 id）
- OrderItem（有 id）

值对象：
- Money（金额）
- Address（收货地址）

领域服务：
- PricingService（价格计算）

领域事件：
- OrderCreatedEvent（订单创建）
```

### 场景 2：DDD 分层结构

```text
DDD 项目结构：
domain/            # 领域层（核心，无外部依赖）
  model/           # 实体、值对象、聚合
  service/         # 领域服务
  repository/      # 仓储接口（端口）
  event/           # 领域事件
application/       # 应用层（编排用例）
infrastructure/    # 基础设施层（实现仓储、外部集成）
interfaces/        # 接口层（Controller、DTO）
```

## 最佳实践与踩坑记录

### 最佳实践

1. **先战略后战术**。先划分限界上下文，再建模。

2. **聚合要小**。聚合太大难以保证一致性。

3. **跨聚合用 ID 引用**。不直接引用其他聚合对象。

4. **领域层不依赖框架**。领域层纯净（六边形架构）。

5. **复杂业务才用 DDD**。简单 CRUD 用 DDD 是过度设计。

### 踩坑记录

**坑 1：简单业务过度设计**

```text
简单的 CRUD 系统也用 DDD，增加复杂度，收益低
```

DDD 适合复杂业务，简单场景用分层架构。

**坑 2：聚合太大**

```text
一个聚合包含几十个实体，事务范围大，性能差
```

聚合要小，一次事务只改一个聚合。

**坑 3：值对象设计成可变**

```java
public class Money {
    private BigDecimal amount;   // 可变（没 final），值对象应不可变
    public void setAmount(BigDecimal a) { this.amount = a; }
}
```

值对象要不可变（final + 无 setter）。

**坑 4：领域层依赖框架**

```java
// 领域层直接依赖 Spring 注解，不纯净
@Service
public class Order { ... }
```

领域层不依赖框架（纯 POJO），框架依赖放基础设施层。

**坑 5：限界上下文划分不清**

```text
多个团队改同一个上下文，职责不清，冲突
```

限界上下文要清晰，一个团队负责一个上下文。

**坑 6：跨聚合直接引用**

```java
public class Order {
    private User user;   // 直接引用 User 聚合，耦合
}
```

跨聚合用 ID 引用（userId），不直接引用对象。
