## 概述

性能测试评估系统的性能表现（响应时间、吞吐量、稳定性），发现性能瓶颈。

```text
为什么做性能测试：
1. 评估容量 —— 系统能扛多少并发
2. 发现瓶颈 —— 定位慢查询、资源不足
3. 验证优化 —— 优化前后对比
4. 大促准备 —— 提前验证峰值承载
```

## 性能测试类型

### 负载测试（Load Test）

```text
负载测试：模拟正常/预期负载，验证系统在目标负载下的表现
```

### 压力测试（Stress Test）

```text
压力测试：持续增加负载，直到系统崩溃，找到极限
```

### 稳定性测试（Soak Test）

```text
稳定性测试：长时间运行（24h+），发现内存泄漏、资源耗尽
```

### 基准测试（Benchmark）

```text
基准测试：测量代码/方法级别的性能（JMH）
```

```text
测试类型对比：
负载测试 —— 目标负载下能否满足指标
压力测试 —— 极限在哪（什么时候崩）
稳定性测试 —— 长期运行是否稳定
基准测试 —— 方法级性能（微基准）
```

## 核心指标

### 响应时间（RT）

```text
平均响应时间、P95、P99
P99 = 99% 的请求响应时间低于该值
```

### 吞吐量（QPS/TPS）

```text
QPS = 每秒请求数
TPS = 每秒事务数
```

### 错误率

```text
错误率 = 失败请求 / 总请求
生产环境错误率应 < 0.1%
```

### 资源使用

```text
CPU、内存、磁盘 IO、网络
瓶颈通常是 CPU 或数据库
```

## JMeter

JMeter 是最流行的性能测试工具（Apache 开源），图形界面 + 命令行。

### JMeter 特点

```text
1. 图形界面 —— 可视化配置
2. 多协议 —— HTTP、JDBC、FTP、TCP
3. 分布式 —— 多机压测
4. 插件丰富 —— 各种监听器、报告
```

### JMeter 测试元素

```text
Thread Group（线程组）—— 模拟用户
HTTP Request（HTTP 请求）—— 请求定义
Timer（定时器）—— 请求间隔
Listener（监听器）—— 结果收集
Assertion（断言）—— 响应验证
```

### JMeter 压测步骤

```text
1. 创建线程组（用户数、循环次数）
2. 添加 HTTP 请求（URL、参数）
3. 添加监听器（聚合报告）
4. 运行测试
5. 分析结果
```

```bash
# 命令行压测（无界面）
jmeter -n -t test.jmx -l result.jtl

# 生成 HTML 报告
jmeter -n -t test.jmx -l result.jtl -e -o report/
```

### 常用场景配置

```text
并发用户：100（线程数）
循环次数：10（或持续时间 60 秒）
Ramp-up：10 秒（逐步增加到 100 用户）
```

## Gatling

Gatling 是基于 Scala 的性能测试工具，用代码定义场景。

### Gatling 特点

```text
1. 代码定义 —— 场景用 Scala DSL 编写
2. 高性能 —— 基于 Akka，单机模拟高并发
3. 报告优秀 —— 自动生成 HTML 报告
```

### 测试场景（Scala）

```scala
class UserSimulation extends Simulation {

  val httpProtocol = http
    .baseUrl("http://localhost:8080")
    .header("Content-Type", "application/json")

  val scenario = scenario("用户查询")
    .exec(http("get_user")
      .get("/api/users/1")
      .check(status.is(200)))

  setUp(
    scenario.inject(
      rampUsers(100).during(10)   // 10 秒增加到 100 用户
    )
  ).protocols(httpProtocol)
}
```

### JMeter vs Gatling vs Locust

| 维度 | JMeter | Gatling | Locust |
|------|--------|---------|--------|
| 语言 | 图形界面 | Scala | Python |
| 并发能力 | 中 | 高 | 高 |
| 学习曲线 | 低（界面） | 中（代码） | 低（Python） |
| 报告 | 一般 | 优秀 | 一般 |
| 适用 | 通用 | 高并发 | Python 团队 |

## JMH 基准测试

JMH（Java Microbenchmark Harness）是 Java 微基准测试框架，精确测量方法性能。

### 为什么需要 JMH

```text
普通计时的问题：
1. JIT 预热 —— 前几次执行慢（未编译）
2. 死代码消除 —— 未使用的结果被优化掉
3. 测量误差 —— 简单 System.currentTimeMillis 不准确

JMH 解决这些问题：预热、防止优化、精确测量
```

### 依赖

```xml
<dependency>
    <groupId>org.openjdk.jmh</groupId>
    <artifactId>jmh-core</artifactId>
    <version>1.37</version>
</dependency>
```

### 基本用法

```java
@BenchmarkMode(Mode.AverageTime)     // 平均时间
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 3, time = 1)    // 预热 3 次
@Measurement(iterations = 5, time = 1)  // 测量 5 次
@State(Scope.Benchmark)
public class StringConcatBenchmark {

    @Benchmark
    public String stringBuilder() {
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < 100; i++) {
            sb.append(i);
        }
        return sb.toString();
    }

    @Benchmark
    public String stringConcat() {
        String s = "";
        for (int i = 0; i < 100; i++) {
            s += i;   // 每次创建新对象
        }
        return s;
    }
}
```

### 常用注解

```text
@BenchmarkMode —— 测量模式（AverageTime/Throughput/SampleTime）
@OutputTimeUnit —— 时间单位
@Warmup —— 预热（JIT 编译）
@Measurement —— 测量
@State —— 状态（Benchmark/Thread/Group）
@Setup/@TearDown —— 初始化/清理
```

### JMH 的应用

```text
1. 比较算法性能（StringBuilder vs +）
2. 比较数据结构（ArrayList vs LinkedList）
3. 验证优化效果
4. 框架选型参考
```

## 应用场景实战

### 场景 1：接口压测（JMeter）

```text
目标：测试 /api/users 接口在 100 并发下的表现

配置：
- 线程数：100
- Ramp-up：10 秒
- 持续时间：60 秒

关注指标：
- 平均响应时间 < 500ms
- P99 < 1000ms
- 错误率 < 0.1%
```

### 场景 2：数据库慢查询定位

```text
压测发现响应时间飙升：
1. 查看慢查询日志（慢 SQL）
2. EXPLAIN 分析执行计划
3. 添加索引
4. 重新压测验证
```

### 场景 3：方法性能对比（JMH）

```java
@Benchmark
public void stringConcat() {
    String s = "";
    for (int i = 0; i < 1000; i++) {
        s += "a";   // 每次创建新 String，O(n²)
    }
}

@Benchmark
public void stringBuilder() {
    StringBuilder sb = new StringBuilder();
    for (int i = 0; i < 1000; i++) {
        sb.append("a");   // O(n)
    }
}
// 结果：StringBuilder 快几百倍
```

## 最佳实践与踩坑记录

### 最佳实践

1. **压测环境隔离**。压测在独立环境（避免影响生产/开发）。

2. **压测从低并发开始**。逐步加并发，找到拐点。

3. **关注 P99 而不是平均值**。平均值掩盖长尾延迟。

4. **压测要监控资源**。CPU、内存、数据库、网络一起监控。

5. **JMH 要预热**。JIT 预热后才能测到真实性能。

### 踩坑记录

**坑 1：压测结果不准确（没预热）**

```text
第一次压测结果很差，因为 JIT 没预热、连接池没建立
```

压测前预热（先跑一轮），或 JMH 配置 @Warmup。

**坑 2：压测打爆生产环境**

```text
直接对生产环境压测，导致生产事故
```

压测在独立环境，或生产环境低负载压测（限流保护）。

**坑 3：只看平均响应时间**

```text
平均响应时间 100ms，但 P99 是 5 秒（长尾严重）
```

关注 P95/P99，平均值会掩盖长尾问题。

**坑 4：压测客户端成为瓶颈**

```text
压测机性能不足（单机模拟 10000 并发），结果不准
```

分布式压测（多台压测机），或确认压测机不是瓶颈。

**坑 5：JMH 死代码消除**

```java
@Benchmark
public void test() {
    compute();   // 结果没使用，JIT 优化掉，测了个寂寞
}
```

JMH 用 @State 和返回值消费结果，防止死代码消除。

**坑 6：忽略数据库连接池**

```text
压测时连接池配置太小，成为瓶颈，误判应用慢
```

压测时关注连接池，必要时调大。
