## 概述

用户画像是对真实用户的抽象建模，通过标签体系刻画用户的人口属性、行为偏好与价值特征；分群则是基于画像标签把用户划分为同质化群体，以便精细化运营。Cohort、Retention、Churn、LTV、RFM 是从不同视角衡量用户生命周期的核心分析模型，构成用户运营的数据底座。
```text
用户画像与分群知识框架
- 画像：标签体系（基础属性 / 行为 / 偏好 / 价值）→ 宽表
- 分群：规则分群 / RFM 分群 / 聚类分群
- 生命周期：Cohort（队列）→ Retention（留存）→ Churn（流失）→ LTV（价值）
- RFM：最近消费 R / 频次 F / 金额 M 三维交叉划分价值
- 落地：标签仓库（数仓 dws 层）→ 分群服务 → 精准触达
```

## 用户画像

用户画像把分散在各业务系统中的用户信息整合成统一、可理解、可计算的特征集合，通常沉淀为数仓中的「标签宽表」。标签分为基础属性（性别、年龄、地域）、行为标签（活跃度、消费频次）、偏好标签（品类偏好、价格带）与价值标签（LTV、RFM 分层）四类。画像质量取决于标签口径的一致性与数据新鲜度，是后续所有分群与运营动作的前提。
```text
用户画像标签体系
- 基础属性：性别 / 年龄 / 城市等级 / 注册时间
- 行为标签：最近活跃 / 订单数 / 消费金额 / 浏览时长
- 偏好标签：品类偏好 / 价格带偏好 / 触达渠道偏好
- 价值标签：RFM 分层 / LTV 分层 / 流失风险等级
- 存储形态：dws 层用户宽表，按日 / 按小时刷新
```
```sql
-- 构建用户画像基础标签宽表（Hive / Spark SQL）
CREATE TABLE IF NOT EXISTS dws_user_profile_1d (
    user_id           BIGINT        COMMENT '用户ID',
    gender            STRING        COMMENT '性别',
    age_bucket        STRING        COMMENT '年龄段',
    city_level        STRING        COMMENT '城市等级',
    reg_date          STRING        COMMENT '注册日期',
    last_active_date  STRING        COMMENT '最近活跃日期',
    total_orders      BIGINT        COMMENT '累计订单数',
    total_amount      DECIMAL(18,2) COMMENT '累计消费金额'
) COMMENT '用户画像日表';

INSERT OVERWRITE TABLE dws_user_profile_1d
SELECT
    u.user_id,
    u.gender,
    CASE
        WHEN u.age < 20              THEN '20岁以下'
        WHEN u.age BETWEEN 20 AND 29 THEN '20-29岁'
        WHEN u.age BETWEEN 30 AND 39 THEN '30-39岁'
        ELSE '40岁及以上'
    END AS age_bucket,
    u.city_level,
    u.reg_date,
    MAX(o.order_date) AS last_active_date,
    COUNT(o.order_id) AS total_orders,
    SUM(o.pay_amount) AS total_amount
FROM dim_user u
LEFT JOIN dwd_order_detail o
    ON u.user_id = o.user_id
GROUP BY u.user_id, u.gender, u.age_bucket, u.city_level, u.reg_date;
```

## 分群

分群（Segmentation）是按一个或多个维度把用户划分为内部相似、外部差异的群体，是精细化运营的基础。常见的分群方式有规则分群（基于 if-else 的业务规则）、RFM 分群（基于消费行为三维划分）与聚类分群（基于 KMeans 等算法自动发现群体）。分群结果通常输出为「用户-群组」映射表，供营销、推荐、风控等下游系统消费。
```text
分群三类方法
- 规则分群：可解释、可复用，依赖业务经验设定阈值
- RFM 分群：基于消费行为，客观但仅覆盖交易维度
- 聚类分群：自动发现群体，但群组语义需人工解释
- 输出物：user_id -> segment_id 映射，附群组人数与画像摘要
```
```sql
-- 基于消费与活跃度的规则分群
SELECT
    user_id,
    total_amount,
    total_orders,
    last_active_days,
    CASE
        WHEN total_amount >= 10000 THEN '高价值用户'
        WHEN total_amount >= 1000  THEN '中价值用户'
        WHEN total_orders  >= 1    THEN '低价值用户'
        ELSE '新注册未转化'
    END AS value_segment,
    CASE
        WHEN last_active_days <= 7  THEN '活跃'
        WHEN last_active_days <= 30 THEN '沉默'
        ELSE '流失风险'
    END AS activity_segment
FROM (
    SELECT
        user_id,
        total_amount,
        total_orders,
        DATEDIFF(CURRENT_DATE, last_active_date) AS last_active_days
    FROM dws_user_profile_1d
) t;
```

## Cohort

Cohort（队列 / 同期群）是把具有共同起始特征的用户归为一组，例如「同一注册月的用户」或「首次下单月的用户」。Cohort 分析追踪同一队列在不同时间段的行为变化，用来剥离时间混杂因素、准确评估产品改动或运营活动对特定群体的长期影响，是留存分析的根基。
```text
Cohort 分析要点
- 队列定义：注册月 / 首购月 / 首次激活日
- 观察指标：留存率 / 复购率 / 累计贡献收入
- 输出形态：队列 x 时间偏移的矩阵（下三角）
- 用途：衡量拉新质量、对比不同渠道用户长期价值
```
```sql
-- 按首购月划分队列，统计各队列在后续月份的活跃用户数
WITH first_order AS (
    SELECT
        user_id,
        MIN(DATE_FORMAT(order_date, 'yyyy-MM')) AS cohort_month
    FROM dwd_order_detail
    GROUP BY user_id
),
monthly_active AS (
    SELECT DISTINCT
        user_id,
        DATE_FORMAT(order_date, 'yyyy-MM') AS active_month
    FROM dwd_order_detail
)
SELECT
    f.cohort_month,
    a.active_month,
    CAST(months_between(
        CAST(concat(a.active_month, '-01') AS DATE),
        CAST(concat(f.cohort_month, '-01') AS DATE)
    ) AS INT) AS month_idx,
    COUNT(DISTINCT f.user_id) AS active_users
FROM first_order f
JOIN monthly_active a ON f.user_id = a.user_id
WHERE a.active_month >= f.cohort_month
GROUP BY f.cohort_month, a.active_month
ORDER BY f.cohort_month, month_idx;
```

## Retention

留存率（Retention）衡量新增用户在一段时间后仍然活跃的比例，是产品健康度的核心指标。常见的口径有次日留存、7 日留存、30 日留存，计算方式为「第 N 天仍活跃的新增用户数 / 第 0 天新增用户数」。留存反映的是产品对用户的长期吸引力，比单纯的拉新量更能预示增长质量。
```text
留存率计算要点
- 次日留存：新用户第 1 天是否回来
- 7 日 / 30 日留存：衡量中期 / 长期粘性
- 分母口径：必须是新增用户（当日新注册 / 首次活跃）
- 分子口径：第 N 天有活跃行为（登录 / 下单 / 播放）
```
```sql
-- 次日 / 7日留存率计算（基于下单活跃）
WITH base AS (
    SELECT
        user_id,
        DATE_FORMAT(order_date, 'yyyy-MM-dd') AS active_date
    FROM dwd_order_detail
),
retained AS (
    SELECT
        b1.active_date,
        COUNT(DISTINCT b1.user_id) AS dau,
        COUNT(DISTINCT IF(b2.user_id IS NOT NULL, b1.user_id, NULL)) AS day1_retained,
        COUNT(DISTINCT IF(b3.user_id IS NOT NULL, b1.user_id, NULL)) AS day7_retained
    FROM base b1
    LEFT JOIN base b2
        ON b1.user_id = b2.user_id
       AND b2.active_date = date_add(b1.active_date, 1)
    LEFT JOIN base b3
        ON b1.user_id = b3.user_id
       AND b3.active_date = date_add(b1.active_date, 7)
    GROUP BY b1.active_date
)
SELECT
    active_date,
    dau,
    ROUND(day1_retained / dau, 4) AS day1_retention,
    ROUND(day7_retained / dau, 4) AS day7_retention
FROM retained
ORDER BY active_date;
```

## Churn

流失（Churn）指用户停止使用产品的现象，通常以「最近 N 天无任何活跃行为」来定义。流失分析的目标是提前识别流失风险用户并采取挽留动作，常见做法是基于活跃度、消费频次、投诉等特征建立流失预警模型，输出流失概率与风险分层，供客服和营销团队精准触达。
```text
流失分析要点
- 流失定义：如 30 天 / 90 天无登录、无下单
- 风险分层：正常 / 沉默 / 流失风险 / 已流失
- 预警特征：活跃间隔拉长、消费频次下降、客诉增多
- 动作：发放优惠券、专属客服、召回 push
```
```sql
-- 识别流失风险用户
SELECT
    user_id,
    last_active_date,
    DATEDIFF(CURRENT_DATE, last_active_date) AS inactive_days,
    CASE
        WHEN DATEDIFF(CURRENT_DATE, last_active_date) > 90 THEN '已流失'
        WHEN DATEDIFF(CURRENT_DATE, last_active_date) > 30 THEN '流失风险'
        ELSE '正常'
    END AS churn_status
FROM dws_user_profile_1d
ORDER BY inactive_days DESC;
```

## LTV

LTV（Lifetime Value，用户生命周期价值）是一个用户从进入到流失期间为企业贡献的总收益（或利润）。简化口径常用「人均累计消费金额」近似，完整口径则要按队列计算累计收入并考虑留存曲线与获客成本。LTV 与获客成本 CAC 的对比（LTV / CAC）是判断商业模式健康度的关键指标。
```text
LTV 计算要点
- 简化口径：LTV = 累计收入 / 队列人数
- 完整口径：LTV = 各期 ARPU x 各期留存率 之和
- 关键比值：LTV / CAC > 3 通常视为健康
- 分队列计算：不同渠道 / 不同时间拉新的 LTV 差异大
```
```sql
-- 按注册月队列计算人均累计消费（LTV 曲线）
SELECT
    DATE_FORMAT(reg_date, 'yyyy-MM') AS cohort_month,
    COUNT(DISTINCT user_id)          AS cohort_size,
    SUM(total_amount)                AS total_revenue,
    ROUND(SUM(total_amount) / COUNT(DISTINCT user_id), 2) AS ltv_per_user
FROM dws_user_profile_1d
GROUP BY DATE_FORMAT(reg_date, 'yyyy-MM')
ORDER BY cohort_month;
```

## RFM

RFM 模型用三个维度刻画客户价值：R（Recency，最近一次消费距今）、F（Frequency，消费频次）、M（Monetary，消费金额）。对三个维度分箱打分（通常 1~5 分）后组合成 RFM 分层，可识别「重要价值客户」「重要唤回客户」等典型群体，是零售与电商行业应用最广的客户分群模型。
```text
RFM 模型要点
- R：最近消费越近，价值越高（R 分越高代表越近）
- F：消费频次越高，忠诚度越高
- M：消费金额越高，贡献越大
- 打分：按分位数（如 NTILE(5)）或业务阈值分箱
- 分层：高分高价值、低分流失风险、交叉组合定义策略
```
```sql
-- RFM 模型：三维打分与客户分层
WITH rfm AS (
    SELECT
        user_id,
        DATEDIFF(CURRENT_DATE, MAX(order_date)) AS recency_days,
        COUNT(DISTINCT order_id)                AS frequency,
        SUM(pay_amount)                         AS monetary
    FROM dwd_order_detail
    GROUP BY user_id
),
rfm_scored AS (
    SELECT
        user_id,
        recency_days,
        frequency,
        monetary,
        NTILE(5) OVER (ORDER BY recency_days DESC) AS r_score,
        NTILE(5) OVER (ORDER BY frequency ASC)     AS f_score,
        NTILE(5) OVER (ORDER BY monetary ASC)      AS m_score
    FROM rfm
)
SELECT
    user_id,
    r_score, f_score, m_score,
    CONCAT(r_score, f_score, m_score) AS rfm_cell,
    CASE
        WHEN r_score >= 4 AND f_score >= 4 AND m_score >= 4 THEN '重要价值客户'
        WHEN r_score >= 4 AND f_score >= 4 THEN '重要唤回客户'
        WHEN r_score >= 4 THEN '重要发展客户'
        WHEN f_score >= 4 AND m_score >= 4 THEN '重要保持客户'
        WHEN m_score >= 4 THEN '重要挽留客户'
        ELSE '一般客户'
    END AS rfm_segment
FROM rfm_scored;
```

## 应用场景实战

### 场景一：电商 RFM 分层 + 差异化触达

某电商平台要对存量用户做价值分层并设计差异化运营策略。先基于近一年订单数据计算 RFM 三维打分，划分出 8 类客户，再把分层结果写入用户标签表供营销系统调用，对不同群体发放不同权益。
```sql
-- 步骤1：计算 RFM 并写入分层标签表
CREATE TABLE IF NOT EXISTS dws_user_rfm_segment (
    user_id     BIGINT COMMENT '用户ID',
    r_score     INT    COMMENT 'R 得分 1-5',
    f_score     INT    COMMENT 'F 得分 1-5',
    m_score     INT    COMMENT 'M 得分 1-5',
    segment     STRING COMMENT 'RFM 分层'
) COMMENT '用户 RFM 分层表';

INSERT OVERWRITE TABLE dws_user_rfm_segment
SELECT
    user_id, r_score, f_score, m_score,
    CASE
        WHEN r_score >= 4 AND f_score >= 4 AND m_score >= 4 THEN '重要价值'
        WHEN r_score >= 4 AND f_score >= 4 THEN '重要唤回'
        WHEN m_score >= 4 THEN '重要挽留'
        WHEN r_score <= 2 AND f_score <= 2 AND m_score <= 2 THEN '流失边缘'
        ELSE '一般'
    END AS segment
FROM (
    SELECT
        user_id,
        NTILE(5) OVER (ORDER BY recency_days DESC) AS r_score,
        NTILE(5) OVER (ORDER BY frequency ASC)     AS f_score,
        NTILE(5) OVER (ORDER BY monetary ASC)      AS m_score
    FROM (
        SELECT
            user_id,
            DATEDIFF(CURRENT_DATE, MAX(order_date)) AS recency_days,
            COUNT(DISTINCT order_id)                AS frequency,
            SUM(pay_amount)                         AS monetary
        FROM dwd_order_detail
        WHERE order_date >= date_sub(CURRENT_DATE, 365)
        GROUP BY user_id
    ) rfm
) scored;

-- 步骤2：查看各分层人数分布
SELECT
    segment,
    COUNT(1) AS user_cnt
FROM dws_user_rfm_segment
GROUP BY segment
ORDER BY user_cnt DESC;
```

### 场景二：新用户 Cohort 留存监控

运营团队需要监控不同拉新渠道的新用户长期留存质量，以优化投放预算分配。按「首购月」划分队列，计算各队列第 1、3、6 个月的留存率，横向对比渠道质量。
```sql
-- 首购月队列 + 分渠道留存率对比
WITH first_order AS (
    SELECT
        user_id,
        channel,
        MIN(DATE_FORMAT(order_date, 'yyyy-MM')) AS cohort_month
    FROM dwd_order_detail
    GROUP BY user_id, channel
),
monthly_active AS (
    SELECT DISTINCT
        user_id,
        DATE_FORMAT(order_date, 'yyyy-MM') AS active_month
    FROM dwd_order_detail
),
cohort_size AS (
    SELECT cohort_month, channel, COUNT(DISTINCT user_id) AS size
    FROM first_order
    GROUP BY cohort_month, channel
)
SELECT
    f.cohort_month,
    f.channel,
    c.size AS cohort_size,
    CAST(months_between(
        CAST(concat(a.active_month, '-01') AS DATE),
        CAST(concat(f.cohort_month, '-01') AS DATE)
    ) AS INT) AS month_idx,
    COUNT(DISTINCT f.user_id) AS retained,
    ROUND(COUNT(DISTINCT f.user_id) / c.size, 4) AS retention_rate
FROM first_order f
JOIN monthly_active a ON f.user_id = a.user_id
JOIN cohort_size c ON f.cohort_month = c.cohort_month AND f.channel = c.channel
WHERE a.active_month >= f.cohort_month
GROUP BY f.cohort_month, f.channel, c.size, CAST(months_between(
    CAST(concat(a.active_month, '-01') AS DATE),
    CAST(concat(f.cohort_month, '-01') AS DATE)
) AS INT)
ORDER BY f.cohort_month, f.channel, month_idx;
```

## 最佳实践与踩坑记录

### 最佳实践

1. 标签口径先行：画像宽表的所有字段必须先定义统一口径（如「活跃」= 当日有登录），否则不同团队算出的画像互相矛盾。
2. 分层结果落表而非落库外：RFM、分群结果写入数仓 dws 层，由统一服务对外提供，避免下游各自重复计算导致口径漂移。
3. 队列用「首次行为时间」而非注册时间：首购月比注册月更能反映真实转化时点，注册时间易受历史数据迁移污染。
4. RFM 分箱用分位数而非固定阈值：固定阈值会随业务体量变化失真，NTILE 分箱保证每层样本均衡、可长期复用。
5. 留存分母与分子口径一致：留存率的分子必须严格是分母子集，跨表 join 时要避免脏数据放大或缩小。
6. 定期刷新并保留历史：画像与分层表按日刷新并留存快照，便于回溯分析某次运营动作的真实效果。
7. 敏感字段脱敏后再对外：画像宽表含手机号等敏感信息时，对外服务层必须做脱敏与权限隔离。

### 踩坑记录
```text
坑 1：LTV 用「总流水/总用户」一次性算出，忽略时间因素
  结论：会把新老用户混在一起，严重高估老队列价值
  原因：新队列还没走过完整生命周期，累计收入被低估，拉低整体均值
  解法：必须按队列分组分别计算 LTV，并标注「观察时长」，同比队列才可比

坑 2：留存计算时分子分母表不同源，留存率出现 > 100%
  原因：活跃表是去重后的宽口径，新增表口径更窄，join 后分母被低估
  解法：统一用同一张明细表派生分子分母，或先核对两表口径再计算

坑 3：RFM 的 R 直接用「最近一次下单日期」排序，忽略时间方向
  原因：recency 越小越「近」，排序方向搞反会导致高价值被标成低分
  解法：R 打分用 ORDER BY recency_days DESC（越近分越高），F/M 用 ASC

坑 4：分群阈值写死在 SQL 里，业务一变就要改代码
  原因：把运营策略硬编码进 ETL，缺乏可配置的标签平台
  解法：把分群规则抽到配置表或标签平台，SQL 只做数据准备与落表

坑 5：聚类分群直接上线，不做群组语义解释
  原因：KMeans 结果是无语义的簇，直接触达会发错权益
  解法：对每个簇抽样做画像摘要（均值/众数），人工命名后再交付运营
```
