## 概述

指标体系是把业务目标翻译成一组可度量、可计算、口径统一的量化指标集合，是企业经营分析的「统一语言」。它通过「原子指标 + 派生指标 + 复合指标」的三层模型组织指标，用业务口径锁定每个指标的精确定义，用指标血缘追踪来源，用指标版本管理口径演进。指标体系的建设目标是「一处定义、处处复用、口径唯一」。

```text
指标体系三层模型：
┌──────────────────────────────────────────────────────┐
│  复合指标   由多个派生/原子指标运算而成（如 GMV/用户数）  │
├──────────────────────────────────────────────────────┤
│  派生指标   原子指标 + 统计周期 + 业务限定 + 维度         │
│             （如「近 7 天北京地区支付金额」）            │
├──────────────────────────────────────────────────────┤
│  原子指标   不可再拆的业务度量（如支付金额、订单数）       │
└──────────────────────────────────────────────────────┘
```

## 原子指标

原子指标是不能再拆分的、最基础的业务度量，通常对应事实表中的一个可聚合字段或计数。它只回答「度量什么」，不包含时间、地区等修饰限定，如「支付金额」「订单数」「支付用户数」。原子指标是派生指标与复合指标的构建基石，其定义的准确性决定了整个指标体系的可靠性。

```text
原子指标要点：
- 定义：不可再拆的业务度量，对应事实表可聚合字段
- 组成：指标名 + 度量逻辑（聚合方式 SUM/COUNT/DISTINCT）
- 示例：支付金额、订单数、支付用户数、退款金额
- 归属：归属于某个业务域与事实表，是血缘的起点
```

可运行示例：定义原子指标及其聚合逻辑。

```sql
-- 原子指标：支付金额 = 事实表中 status='paid' 的 amount 求和
SELECT SUM(amount) AS pay_amount
FROM dwd.dwd_orders
WHERE dt = '2026-08-13'
  AND status = 'paid';

-- 原子指标：支付用户数 = 去重后的 user_id 计数
SELECT COUNT(DISTINCT user_id) AS pay_users
FROM dwd.dwd_orders
WHERE dt = '2026-08-13'
  AND status = 'paid';
```

## 派生指标

派生指标是在原子指标基础上，叠加「统计周期 + 业务限定 + 统计粒度」而成的可对外使用的指标。它把一个原子度量放到具体的业务语境中，回答「在什么时间、什么范围、按什么维度，度量值是多少」。派生指标是业务真正看板上的指标，其口径必须精确到每个修饰词的取值。

```text
派生指标要点：
- 公式：派生指标 = 原子指标 + 统计周期 + 业务限定 + 统计粒度
- 统计周期：当日、近 7 天、近 30 天、累计等
- 业务限定：地区、渠道、品类等过滤条件
- 统计粒度：按日/月，按地区/渠道等维度聚合
```

可运行示例：定义「近 7 天北京地区支付金额」派生指标。

```sql
-- 派生指标：近 7 天北京地区支付金额（原子指标 pay_amount + 周期 + 地域限定）
SELECT SUM(o.amount) AS pay_amount_7d_beijing
FROM dwd.dwd_orders o
JOIN dim.dim_user u ON o.user_id = u.user_id
WHERE o.dt BETWEEN '2026-08-07' AND '2026-08-13'
  AND o.status = 'paid'
  AND u.city = '北京';
```

## 复合指标

复合指标是由多个原子指标或派生指标通过四则运算、比值等组合而成的指标，用来表达「率」和「均」类业务含义。它本身通常没有独立的物理存储，而是在查询时基于底层指标实时计算，如「客单价 = 支付金额 / 支付用户数」「转化率 = 下单用户数 / 访问用户数」。复合指标让指标体系能表达更丰富的业务洞察。

```text
复合指标要点：
- 定义：由多个原子/派生指标运算组合而成
- 常见形态：比率（转化率）、均值（客单价）、占比（品类占比）
- 计算时机：查询时基于底层指标实时计算，避免冗余存储
- 注意：分母为 0 的兜底，避免除零异常
```

可运行示例：定义「客单价」复合指标并处理除零。

```sql
-- 复合指标：客单价 = 支付金额 / 支付用户数
SELECT
  SUM(amount) / NULLIF(COUNT(DISTINCT user_id), 0) AS arpu
FROM dwd.dwd_orders
WHERE dt = '2026-08-13'
  AND status = 'paid';

-- 复合指标：支付转化率 = 支付用户数 / 访问用户数
SELECT
  COUNT(DISTINCT CASE WHEN status = 'paid' THEN user_id END)
    / NULLIF(COUNT(DISTINCT user_id), 0) AS pay_rate
FROM dwd.dwd_orders
WHERE dt = '2026-08-13';
```

## 业务口径

业务口径是每个指标「精确定义」的文字化与规则化描述，是消除「数据打架」的根本手段。它明确指标的统计范围、过滤条件、时间规则、去重逻辑、单位与异常处理方式，例如「GMV」的口径要写清是否含退款、是否含运费、按支付时间还是下单时间统计。口径只有沉淀成文档与规则，才能被一致执行。

```text
业务口径要点：
- 统计范围：包含/排除哪些数据（是否含退款、含运费）
- 时间规则：按下单时间还是支付时间统计
- 去重逻辑：是否去重、按什么字段去重
- 单位与精度：金额单位、小数位、四舍五入规则
- 异常处理：分母为 0、缺失值、异常值如何处理
```

可运行示例：用 SQL 落实「GMV」口径（按下单时间、含运费、不含已退款）。

```sql
-- 口径：GMV 按下单时间统计，含运费，剔除已退款订单
SELECT SUM(amount + COALESCE(freight, 0)) AS gmv
FROM dwd.dwd_orders
WHERE dt = '2026-08-13'
  AND status <> 'refunded';
```

## 指标血缘

指标血缘记录指标从「源表字段 → 原子指标 → 派生/复合指标 → 报表」的完整依赖链路，用于回答「这个指标从哪来、被谁引用、改动影响谁」。它使指标可追溯、可审计，是指标治理的核心资产。当上游口径变更时，通过血缘可以快速定位所有受影响的下游指标与报表。

```text
指标血缘要点：
- 来源追溯：指标由哪些源表字段、哪些逻辑加工而来
- 影响分析：上游变更会影响哪些下游指标与报表
- 存储方式：通过 SQL 解析 + 指标平台登记自动生成血缘
- 价值：口径变更影响评估、指标治理、问题根因定位
```

可运行示例：用 SQL 解析展示指标与源字段的依赖关系。

```sql
-- 展示「客单价」指标的血缘依赖（元数据表示例）
SELECT
  metric_name,
  source_table,
  source_column,
  dependency_type
FROM meta.metric_lineage
WHERE metric_name = '客单价'
ORDER BY dependency_type;
-- 结果示意：
-- 客单价 <- dwd_orders.amount（原子指标：支付金额）
-- 客单价 <- dwd_orders.user_id（原子指标：支付用户数）
```

## 指标版本

指标版本用于管理指标口径随业务变化的演进过程，记录每个指标「在什么时间、因什么原因、从什么口径变成了什么口径」。当业务规则调整（如退款口径变化）时，指标不直接覆盖，而是发布一个新版本，历史版本保留用于对账与回溯。指标版本保障了指标口径变更的可控、可回滚与可审计。

```text
指标版本要点：
- 版本化：口径变更发布新版本，历史版本保留
- 变更原因：记录变更动机、发起人、生效时间
- 对账能力：同指标不同版本可对账，解释数值差异
- 回滚：新版本有问题时可回退到历史版本
```

可运行示例：管理指标版本与口径变更记录。

```sql
-- 指标版本表，记录口径变更历史
CREATE TABLE meta.metric_version (
  metric_id     BIGINT,
  version       INT,
  caliber       STRING,      -- 口径描述
  change_reason STRING,
  effective_dt  STRING,
  created_by    STRING
);

-- 发布新版本：GMV 口径从「含退款」调整为「不含退款」
INSERT INTO meta.metric_version VALUES
  (101, 1, 'GMV 含已退款订单', '初始口径', '2026-01-01', 'zhangsan'),
  (101, 2, 'GMV 不含已退款订单', '业务要求剔除退款', '2026-08-01', 'lisi');

-- 查询某指标的历史版本
SELECT version, caliber, effective_dt FROM meta.metric_version
WHERE metric_id = 101 ORDER BY version;
```

## 应用场景实战

### 场景一：电商核心指标看板搭建

某电商需要搭建经营看板，覆盖 GMV、支付用户数、客单价、支付转化率四大核心指标。通过指标平台统一口径，用 SQL 落地指标，避免各团队重复定义。

```sql
-- 核心指标统一口径落地（DWS 层汇总表）
CREATE TABLE dws.dws_order_metrics_daily (
  dt            STRING,
  gmv           DECIMAL(20,2),  -- 复合指标：GMV
  pay_users     BIGINT,         -- 原子指标：支付用户数
  arpu          DECIMAL(20,2),  -- 复合指标：客单价
  pay_rate      DECIMAL(10,4)   -- 复合指标：支付转化率
);

INSERT INTO dws.dws_order_metrics_daily
SELECT
  dt,
  SUM(amount + COALESCE(freight, 0))                              AS gmv,
  COUNT(DISTINCT user_id)                                         AS pay_users,
  SUM(amount + COALESCE(freight, 0)) / NULLIF(COUNT(DISTINCT user_id), 0) AS arpu,
  COUNT(DISTINCT user_id) / NULLIF(SUM(visit_cnt), 0)             AS pay_rate
FROM dwd.dwd_orders
WHERE dt = '2026-08-13'
  AND status <> 'refunded'
GROUP BY dt;
```

### 场景二：指标口径变更的影响分析与对账

某公司调整了 GMV 口径（不再计入退款订单），需要评估该变更对下游报表的影响，并做新旧口径对账。通过指标血缘定位受影响报表，通过版本化对账解释数值差异。

```sql
-- 1. 通过血缘定位依赖 GMV 的下游指标与报表
SELECT downstream_metric, report_name
FROM meta.metric_lineage
WHERE source_metric = 'GMV';

-- 2. 新旧口径对账：旧口径含退款 vs 新口径不含退款
SELECT
  SUM(amount + COALESCE(freight, 0)) AS gmv_old,              -- 含退款
  SUM(CASE WHEN status <> 'refunded' THEN amount + COALESCE(freight, 0) ELSE 0 END) AS gmv_new
FROM dwd.dwd_orders
WHERE dt = '2026-08-13';
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一处定义、多处引用：指标统一在指标平台定义，报表、API、大屏只做引用，杜绝各团队私下重复计算。
2. 口径必须书面化：每个指标落地一份「口径说明书」，写清范围、时间规则、去重逻辑与异常处理。
3. 原子指标先行：先把原子指标定义清楚，派生与复合指标基于原子指标组合，避免口径层层失真。
4. 血缘自动采集：通过 SQL 解析自动生成指标血缘，而非依赖人工登记，保证血缘准确完整。
5. 版本化变更：口径变更走版本流程，保留历史、记录原因，支持对账与回滚。
6. 指标分层管理：核心指标与过程指标分级管理，核心指标变更需评审，过程指标可灵活调整。
7. 命名规范化：指标名遵循「业务域 + 度量 + 统计周期」的命名规范，便于检索与理解。

### 踩坑记录

```text
坑 1：同名词不同口径导致「数据打架」
  结论：运营与财务报出的 GMV 不一致，业务互不认可。
  原因：两个团队对 GMV 的口径定义不同（是否含退款、是否含运费）。
  解法：指标统一到指标平台，锁定唯一口径，其他系统只引用不重算。

坑 2：分母为 0 导致报表报错
  结论：转化率、客单价等复合指标在无数据时出现除零异常。
  原因：复合指标直接做除法，未处理分母为 0 的情况。
  解法：使用 NULLIF(分母, 0) 或 CASE WHEN 兜底，除零时返回 NULL 或 0。

坑 3：去重口径不一致导致用户数虚高
  结论：同一用户多笔订单时，用户数被重复计算。
  原因：计算用户数时未用 COUNT(DISTINCT user_id)，或去重字段选错。
  解法：明确去重字段与去重逻辑，统一使用 COUNT(DISTINCT 主键字段)。

坑 4：口径变更未版本化导致历史对账困难
  结论：GMV 口径调整后，历史数据与当前数据无法对齐解释。
  原因：直接覆盖指标定义，未保留历史版本与变更记录。
  解法：口径变更走版本流程，保留历史版本，支持新旧口径对账。

坑 5：指标血缘缺失导致变更影响无法评估
  结论：上游表字段调整后，下游报表大面积出错，无法快速定位。
  原因：未建设指标血缘，依赖关系靠人肉梳理。
  解法：通过 SQL 解析自动采集血缘，变更前做影响分析。
```
