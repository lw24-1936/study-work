## 概述

Hadoop 生态是围绕 HDFS（存储）和 YARN（调度）生长出的一整套组件：Hive 提供 SQL 查询、HBase 提供海量随机读写、Sqoop 做关系库导入导出、Oozie 做工作流调度、ZooKeeper 做分布式协调、Flume 做日志采集、Ranger/Atlas/Knox 做安全与治理。理解这些组件的定位和协作关系，才能搭建一个完整可用的企业级大数据平台。

```text
Hadoop 生态组件分类：
1. 查询计算 —— Hive（SQL on Hadoop）、HBase（NoSQL 宽列）
2. 数据集成 —— Sqoop（关系库 <-> HDFS）、Flume（日志采集）
3. 调度协调 —— Oozie（工作流调度）、ZooKeeper（分布式协调）
4. 安全治理 —— Ranger（权限）、Atlas（元数据/血缘）、Knox（网关）
```

```text
各组件在平台中的位置：
数据源 -> Flume/Sqoop 采集 -> HDFS/Hive 存储 -> Hive/Spark 计算
        -> 结果输出 -> Oozie 调度编排整个流程
横切：ZooKeeper 做协调，Ranger/Atlas/Knox 做安全治理
```

## 核心概念

Hadoop 生态由查询计算、数据集成、调度协调、安全治理四类组件构成，下面逐个拆解 9 个核心组件的定位与用法。

### Hive

Hive 是 Hadoop 生态的数据仓库工具，把 SQL（HiveQL）翻译成 MapReduce/Tez/Spark 任务在 Hadoop 上执行，让熟悉 SQL 的人也能处理海量数据。它管理元数据（表结构、分区，存于 Metastore），数据存 HDFS，是离线数仓的标准入口。如今 Hive 主要承载 SQL 元数据管理和批处理，计算引擎逐步转向 Spark。

```text
Hive 要点：
1. SQL on Hadoop —— HiveQL 翻译成分布式计算任务
2. Metastore —— 元数据（库/表/分区/列）存独立的关系库
3. 分区表 —— 按日期等分区，查询裁剪分区提升性能
4. 计算引擎 —— 可切换 MapReduce/Tez/Spark
```

```sql
-- Hive 建表与查询
CREATE TABLE orders (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2)
) PARTITIONED BY (dt STRING)
STORED AS PARQUET;

-- 按分区查询（自动裁剪分区）
SELECT user_id, SUM(amount) AS total
FROM orders
WHERE dt = '2024-08-14'
GROUP BY user_id;
```

```text
详见 08.1-Hive 架构与表管理 / 08.2-Hive SQL 与查询优化
```

### HBase

HBase 是构建在 HDFS 上的分布式宽列 NoSQL 数据库，面向海量行的随机读写与范围扫描，弥补 HDFS「不适合随机读写」的短板。数据按行键（RowKey）字典序排序、按 Region 切分分布，支持十亿行规模的秒级点查，是 Hadoop 生态里实时查询明细数据的标准存储。

```text
HBase 要点：
1. 行键排序 —— 数据按 RowKey 字典序存储，RowKey 设计决定性能
2. Region —— 表按 RowKey 范围切分成 Region，分布到 RegionServer
3. 列族 —— 列按列族组织，列族下可动态加列（稀疏宽表）
4. 随机读写 —— 弥补 HDFS 只适合顺序读的短板
```

```shell
# HBase Shell
create 'users', 'info'
put 'users', '1001', 'info:name', 'alice'
get 'users', '1001'
scan 'users', {STARTROW => '1000', ENDROW => '2000'}
```

```text
详见 05.6-NoSQL 中 HBase 章节
```

### Sqoop

Sqoop 是 Hadoop 生态的数据导入导出工具，用于在关系型数据库（MySQL/Oracle/PostgreSQL）和 HDFS/Hive/HBase 之间批量搬运数据。它基于 MapReduce 并行传输，支持全量和增量（按时间戳/主键）同步，是离线数仓「从业务库拉数据」的经典工具（现逐步被 DataX/SeaTunnel 等替代）。

```text
Sqoop 要点：
1. 关系库 <-> HDFS —— 双向批量传输
2. 并行传输 —— 底层用 MapReduce 并行拉取
3. 增量同步 —— 按时间戳/主键做增量导入
4. Hive 集成 —— 导入后自动建 Hive 表
```

```shell
# 从 MySQL 导入到 HDFS
sqoop import \
  --connect jdbc:mysql://mysql-host:3306/db \
  --username root --password pass \
  --table orders \
  --target-dir /data/raw/orders \
  --num-mappers 4

# 增量导入（按时间戳）
sqoop import \
  --connect jdbc:mysql://mysql-host:3306/db \
  --username root --password pass \
  --table orders \
  --target-dir /data/raw/orders \
  --incremental append \
  --check-column order_id \
  --last-value 1000000
```

### Oozie

Oozie 是 Hadoop 生态的工作流调度引擎，用 XML 定义 DAG（有向无环图）工作流，编排 Hive/MapReduce/Spark/Shell 等任务的依赖关系和执行顺序。它支持定时调度（Coordinator）和条件分支，是 Hadoop 时代离线任务编排的标准工具（现逐步被 Airflow/DolphinScheduler 取代）。

```text
Oozie 要点：
1. 工作流 —— XML 定义 DAG，编排多个任务的依赖顺序
2. 定时调度 —— Coordinator 按时间/cron 触发工作流
3. 任务类型 —— 支持 MapReduce/Hive/Spark/Shell/Pig 等
4. 容错 —— 任务失败重试，支持条件分支
```

```xml
<!-- workflow.xml：Hive -> Spark 的 DAG -->
<workflow-app name="etl-flow" xmlns="uri:oozie:workflow:0.5">
  <start to="hive-node"/>
  <action name="hive-node">
    <hive xmlns="uri:oozie:hive-action:0.2">
      <script>etl.sql</script>
    </hive>
    <ok to="spark-node"/>
    <error to="fail"/>
  </action>
  <action name="spark-node">
    <spark xmlns="uri:oozie:spark-action:0.1">
      <master>yarn-cluster</master>
      <class>com.example.AggJob</class>
    </spark>
    <ok to="end"/>
    <error to="fail"/>
  </action>
  <kill name="fail"><message>ETL failed</message></kill>
  <end name="end"/>
</workflow-app>
```

### ZooKeeper

ZooKeeper 是分布式协调服务，提供分布式环境下的「一致性的配置存储 + 命名服务 + 分布式锁 + 选举」等协调原语。它用 ZAB 协议保证强一致，数据存内存、持久化到磁盘，是 Hadoop 生态几乎所有组件（HBase、Kafka、YARN HA、Hive）做主备选举和配置管理的依赖。

```text
ZooKeeper 要点：
1. 强一致 —— ZAB 协议，数据一致可靠
2. 数据模型 —— 类文件系统的树形节点（znode），支持监听（watch）
3. 典型用途 —— 主备选举、分布式锁、配置中心、服务发现
4. 奇数节点 —— 集群通常 3/5 个节点，过半存活即可用
```

```shell
# ZooKeeper 客户端操作
zkCli.sh
create /config "value"               # 创建节点
get /config                          # 读取节点
set /config "new-value"              # 更新节点
ls /                                  # 查看子节点
```

```text
ZooKeeper 的典型应用：
1. HBase —— 存储元数据位置、RegionServer 注册
2. Kafka —— Broker 注册、Controller 选举、元数据
3. YARN HA —— ResourceManager 主备选举
4. 分布式锁 —— 临时顺序节点实现
```

### Flume

Flume 是分布式日志采集系统，把分布在多台服务器上的日志实时采集、聚合、传输到 HDFS/HBase/Kafka。它以 Agent 为单元，由 Source（数据源）、Channel（缓冲通道）、Sink（目的地）三段组成，可靠地传输海量日志，是大数据平台「日志入湖」的经典入口。

```text
Flume 要点：
1. Agent 架构 —— Source + Channel + Sink 三段式
2. 可靠传输 —— Channel 缓冲，事务保证不丢
3. 多级 Agent —— 采集 -> 聚合 -> 落地的多级拓扑
4. 目的地 —— HDFS/HBase/Kafka 等
```

```text
# flume.conf：采集日志到 Kafka
agent.sources = s1
agent.sources.s1.type = spooldir
agent.sources.s1.spoolDir = /data/logs

agent.channels = c1
agent.channels.c1.type = memory
agent.channels.c1.capacity = 10000

agent.sinks = k1
agent.sinks.k1.type = org.apache.flume.sink.kafka.KafkaSink
agent.sinks.k1.kafka.topic = logs

agent.sources.s1.channels = c1
agent.sinks.k1.channel = c1
```

### Ranger

Apache Ranger 是 Hadoop 生态的统一安全授权框架，提供集中式的权限管理：对 HDFS/Hive/HBase/Kafka 等组件做细粒度的策略授权（行级、列级过滤和脱敏），并做审计。它让安全策略集中管理、统一下发，是企业级大数据平台做权限管控的标准组件。

```text
Ranger 要点：
1. 统一授权 —— 一个控制台管理所有组件的权限策略
2. 细粒度 —— 支持行级/列级权限、数据脱敏（masking）
3. 审计 —— 记录所有访问行为，满足合规
4. 插件机制 —— 各组件装 Ranger 插件，策略实时生效
```

```text
Ranger 管理的典型策略：
1. Hive —— 库/表/列的 select/insert 权限
2. HDFS —— 目录/文件的读写权限
3. HBase —— 表/列族的读写权限
4. 脱敏 —— 对身份证/手机号等敏感列做掩码
```

### Atlas

Apache Atlas 是 Hadoop 生态的元数据管理与数据治理平台，自动采集各组件（Hive/HBase/Kafka/Spark）的元数据，建立数据资产目录和数据血缘（lineage），支持数据分类、标签、审计。它是「数据在哪、怎么流转、谁在用」的统一视图，是数据治理的基础设施。

```text
Atlas 要点：
1. 元数据采集 —— 自动从 Hive/HBase/Kafka 等采集元数据
2. 数据血缘 —— 追踪数据从源到报表的完整流转链路
3. 分类标签 —— 数据分类（PII/敏感）和业务标签
4. 数据治理 —— 支撑数据资产盘点、影响分析、合规
```

```text
Atlas 的核心价值：
1. 数据血缘 —— 字段级血缘，回答「这个指标怎么算出来的」
2. 资产目录 —— 统一检索数据资产，找数方便
3. 影响分析 —— 改了某表，哪些下游受影响
4. 合规审计 —— 敏感数据分布与流转可查
```

### Knox

Apache Knox 是 Hadoop 集群的 REST API 网关，提供统一的访问入口和认证，对外暴露 HDFS/Hive/HBase 等的 REST 接口，内部转发到集群。它解决「集群服务端口多、认证复杂」的问题，让外部应用通过一个安全的网关访问 Hadoop，配合 Kerberos/LDAP 做统一认证。

```text
Knox 要点：
1. 统一网关 —— 一个入口代理所有 Hadoop 组件的 REST 接口
2. 认证集成 —— 支持 LDAP/Kerberos/SAML 等认证
3. 简化访问 —— 外部应用不直接连各组件端口，统一走 Knox
4. 安全边界 —— 集群边界的安全网关，配合防火墙使用
```

```text
Knox 的典型场景：
1. 外部 BI 工具通过 Knox 访问 Hive（JDBC/HTTP）
2. Web 应用通过 Knox REST API 访问 HDFS/HBase
3. 统一认证，避免每个组件单独暴露端口
```

## 工作原理

Hadoop 生态的工作方式可以概括为「数据从哪来、存哪、怎么算、谁来调度、谁来协调与治理」。理解一条数据在生态里如何流动，就理解了整套体系的运作方式。

```text
端到端数据流（离线 + 实时两条链路）：
离线：业务库 --Sqoop--> HDFS/Hive(ODS) --Hive SQL--> DWD/DWS/ADS --Sqoop--> 报表库
实时：业务日志 --Flume--> Kafka --Flink/Spark--> HDFS/HBase
调度：Oozie 定时触发离线链路；ZooKeeper 协调各组件 HA 与元数据
治理：Ranger 管权限、Atlas 管元数据/血缘、Knox 管网关入口
```

```text
各组件核心工作机制：
1. Hive —— SQL 解析为 AST，生成逻辑/物理执行计划，翻译成 MapReduce/Tez/Spark 任务跑在 YARN 上
2. HBase —— 写入先落 WAL 再写 MemStore，刷盘成 HFile；读走 MemStore + BlockCache + HFile 三层
3. Sqoop —— 把导入任务拆成多个 Map 任务，每个 Map 用 JDBC 拉一部分数据并行写入 HDFS
4. Oozie —— 解析 workflow.xml 的 DAG，按依赖顺序提交 action，Coordinator 按时间/cron 触发
5. ZooKeeper —— ZAB 协议保证写请求在多数派节点落盘才算成功，节点变更通过 watch 通知客户端
6. Flume —— Source 读数据 -> Channel 事务缓冲 -> Sink 消费；memory/file channel 决定可靠性
7. Ranger —— 组件插件向 Ranger Admin 拉取策略并本地缓存，访问时本地鉴权 + 异步上报审计
8. Atlas —— 组件 Hook 捕获元数据变更 -> 发 Kafka -> Atlas 消费入库 -> 构建血缘图
9. Knox —— 对外统一 HTTPS 入口，认证后反向代理转发到集群内部各组件 REST 接口
```

## 常用命令与配置

```shell

hive -e "SELECT count(*) FROM orders"                 # 执行单条 SQL

```

## 配置文件解析

```xml
<!-- hbase-site.xml 关键配置 -->
<configuration>
  <property>
    <name>hbase.rootdir</name>                    <!-- HBase 数据在 HDFS 的根目录 -->
    <value>hdfs://mycluster/hbase</value>
  </property>
  <property>
    <name>hbase.zookeeper.quorum</name>           <!-- 依赖的 ZooKeeper 集群 -->

  <property>
    <name>hbase.regionserver.handler.count</name> <!-- 每个 RegionServer 的 RPC 处理线程数 -->
    <value>30</value>
  </property>

```

```text
# zoo.cfg 关键配置
tickTime=2000               # 心跳与超时的基本时间单位（毫秒）
```

```text

agent.sinks.k1.type = hdfs             # Sink 类型
```

## 应用场景实战

### 场景一：搭建一个完整的离线数仓数据链路

```text
业务 MySQL
   |
   | Sqoop 全量/增量导入
   v
HDFS（原始数据 ODS）
   |
   | Hive SQL 清洗加工（DWD/DWS）
   v
Hive 表（结果 ADS）
   |
   | Sqoop 导出
   v
报表 MySQL（供 BI 查询）

调度编排：Oozie 定时触发整个流程
安全治理：Ranger 管权限，Atlas 管血缘
```

```shell
# 典型的一天调度脚本（简化）
# 1. Sqoop 增量拉取
sqoop import --connect jdbc:mysql://db/orders --incremental append ...

# 2. Hive 清洗加工
hive -f dwd_order.sql
hive -f dws_user_order.sql

# 3. Sqoop 导出结果
sqoop export --connect jdbc:mysql://report/ads --table daily_gmv ...
```

### 场景二：日志实时入湖 + 下游消费

```text
业务服务器日志
   |
   | Flume 实时采集（Source -> Channel -> Sink）
   v
Kafka（日志缓冲队列，ZooKeeper 协调）
   |
   | 消费（Spark/Flink）
   v
HDFS/Hive（归档 + 分析）
```

```text
# Flume 采集日志到 Kafka
agent.sources.s1.type = taildir
agent.sources.s1.filegroups = f1
agent.sources.s1.filegroups.f1 = /data/logs/*.log
agent.sinks.k1.type = org.apache.flume.sink.kafka.KafkaSink
agent.sinks.k1.kafka.topic = app-logs
```

### 场景三：HBase 订单明细随机查询

```text
场景：订单明细表存 HBase，客服/风控按订单号做秒级点查
设计：RowKey = 订单号（或日期前缀 + 订单号），列族 info 存订单字段
```

```shell
# 按日期范围扫描某天的订单
scan 'order_detail', {STARTROW => '202408140000', ENDROW => '202408149999'}
```

### 场景四：ZooKeeper 分布式锁

```text
场景：多个计算任务并发写同一份结果文件，用 ZooKeeper 临时顺序节点做互斥锁
原理：每个客户端在 /locks 下创建临时顺序节点，序号最小的获得锁，用完删除节点触发下一个
```

```shell
# 客户端 A 抢锁
zkCli.sh
create -e -s /locks/lock- ""        # 创建临时顺序节点，返回 /locks/lock-0000000001
ls /locks                            # 查看所有节点，序号最小者持锁
# 释放锁：删除自己的节点（或会话断开自动删除，临时节点特性）
delete /locks/lock-0000000001
```

## 性能与调优

```text
Hive 调优：
1. 分区裁剪 + 分桶 —— where 命中分区，大幅减少扫描量
2. 小文件合并 —— ORC/Parquet + 合适块大小，避免 NameNode 元数据压力
3. 执行引擎切 Tez/Spark，比默认 MapReduce 快数倍
4. 列式存储 + 谓词下推（ORC/Parquet），减少 IO

HBase 调优：
1. RowKey 打散（加盐/反转），避免热点 Region
2. 预分区（pre-split），避免自动 split 抖动
3. MemStore 与 BlockCache 内存配比，配合 GC 调优
4. 批量写（BufferedMutator），减少 RPC 次数

ZooKeeper 调优：
1. dataDir 与事务日志分离到独立磁盘
2. 奇数节点（3/5），过半即可用
3. 会话超时（sessionTimeout）别设太短，避免频繁重连

Flume 调优：
1. 关键数据用 file channel，吞吐要求高用 memory channel
2. batchSize 与 channel capacity 匹配，避免频繁刷盘
3. 多级 Agent 聚合，减少最终落地点

Sqoop 调优：
1. num-mappers 控制并行度，避免压垮源库
2. 增量导入替代全量，减少无效传输
3. --direct 走原生工具（如 mysqldump），绕过 JDBC 提速
```

## 安全与权限

```text
生态安全体系（三层）：
1. 认证 —— Kerberos 做集群内身份认证（确认「你是谁」）
2. 授权 —— Ranger 做细粒度权限（确认「你能访问什么」）
3. 审计 —— Ranger/Atlas 记录访问行为（确认「谁做了什么」）

Ranger 授权要点：
- HDFS/Hive/HBase/Kafka 统一策略管理
- 行级/列级过滤 + 数据脱敏（masking）
- 插件本地缓存策略，鉴权在组件侧执行，策略实时生效

Knox 网关要点：
- 统一 HTTPS 入口，外部不直连集群各组件端口
- 集成 LDAP/Kerberos 认证
- topology 定义后端服务路由

ZooKeeper 安全：
- 生产开启 SASL 认证，限制 clientPort 网络访问
```

## 故障排查

```text
排查思路（从下往上）：组件进程 -> 依赖服务（ZooKeeper/HDFS）-> 日志 -> 配置

常见故障与定位：
1. Hive 查询慢/卡住 —— 看 YARN 任务是否排队、执行计划是否有数据倾斜
2. HBase RegionServer 宕机 —— 看 HBase Master 日志，Region 是否自动迁移到其它节点
3. ZooKeeper 无法选举 —— 检查过半节点是否存活、网络是否分区
4. Sqoop 导入失败 —— 检查源库连接、账号权限、目标目录
5. Flume 数据丢失 —— 检查 channel 类型（memory 会丢）、sink 是否阻塞
```

```shell
# 常用排查命令

```

## 常见问题

```text
Q1: Hive 和 HBase 有什么区别，分别适合什么场景？
A: Hive 是 SQL 数据仓库，适合离线批量分析（大表扫描、聚合）；HBase 是 NoSQL 宽列库，适合海量明细的随机读写和点查。两者常组合：Hive 做分析、HBase 存明细。

Q2: ZooKeeper 为什么推荐奇数节点？
A: ZooKeeper 靠「过半存活」保证可用与一致，N 个节点可容忍 (N-1)/2 个故障。3 节点容 1 台挂、4 节点也只容 1 台挂，4 比 3 多一台却不多容错，纯浪费，所以用奇数。

Q3: Sqoop 增量导入怎么选 check-column？
A: 数据只增不改用自增主键（append 模式），数据会更新用时间戳（lastmodified 模式）。check-column 要有索引，否则全表扫描。

Q4: Flume memory channel 和 file channel 怎么选？
A: memory channel 快但不持久化，Agent 崩溃丢数据；file channel 持久化但慢。关键数据用 file channel 或直接 Sink 到 Kafka 缓冲，日志量极大的场景用 memory + Kafka 兜底。

Q5: HBase RowKey 为什么不能直接用递增时间戳？
A: 递增 RowKey 会让新数据永远写进最后一个 Region，造成热点，单个 RegionServer 成为瓶颈。要加盐（前缀散列）或反转时间戳打散。

Q6: Oozie 和 Airflow/DolphinScheduler 怎么选？
A: Oozie 是 Hadoop 原生、XML 定义工作流，与 Hive/MapReduce 集成深但笨重；Airflow 用 Python 定义 DAG、生态活跃；DolphinScheduler 可视化、易用。新项目优先 Airflow/DolphinScheduler，存量 Hadoop 集群用 Oozie。

Q7: Ranger 和 Knox 有什么区别？
A: Ranger 管「授权」（谁能访问什么数据，行级/列级/脱敏），Knox 管「入口」（统一网关 + 认证，代理 REST 接口）。两者配合：Knox 做认证入口，Ranger 做细粒度授权。
```

## 面试题

```text
1. 简述 Hadoop 生态的组件和各自职责。
   答：存储 HDFS、调度 YARN、计算 MapReduce/Spark、SQL 数仓 Hive、NoSQL 明细 HBase、数据集成 Sqoop/Flume、调度 Oozie、协调 ZooKeeper、安全治理 Ranger/Atlas/Knox。

2. Hive 的架构包含哪些部分？SQL 是怎么执行的？
   答：元数据存 Metastore（独立关系库）；SQL 经解析器生成 AST，语义分析生成逻辑计划，优化后转物理计划，翻译成 MapReduce/Tez/Spark 任务提交 YARN 执行。Metastore 是 Hive 的元数据命脉。

3. HBase 为什么能实现海量随机读写？
   答：RowKey 字典序 + Region 切分，点查能直接定位到某个 Region；写入走 WAL + MemStore 内存缓冲，读走 BlockCache 缓存 + HFile；底层 HDFS 只做顺序追加，随机性由 LSM 结构消化。

4. ZooKeeper 的 ZAB 协议是怎么保证一致的？
   答：写请求由 leader 发起，用两阶段提交向 follower 广播，多数派（过半）落盘后才返回成功；崩溃恢复时用 ZXID 保证新 leader 拥有最新已提交事务。

5. Sqoop 底层是怎么并行传输的？
   答：把导入拆成多个 Map 任务，每个 Map 用 JDBC 连接源库，按主键范围（split-by）各拉一段数据，并行写入 HDFS，无 Reduce 阶段。

6. Flume 的 Source/Channel/Sink 分别负责什么？
   答：Source 采集数据源（spool/taildir/avro），Channel 做缓冲和事务（memory/file），Sink 把数据写到目的地（HDFS/Kafka/HBase）。三段式解耦采集、缓冲、落地。

7. Ranger 和 Kerberos 的区别？
   答：Kerberos 解决「认证」（你是谁，身份可信），Ranger 解决「授权」（你能访问什么，权限策略）。Kerberos 是身份层，Ranger 是权限层，配合使用。

8. Atlas 是怎么实现数据血缘的？
   答：各组件（Hive/Spark/Sqoop）装 Atlas Hook，执行任务时捕获输入输出表和字段，通过 Kafka 异步上报 Atlas，入库后构建实体图，血缘就是图上的有向边。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 元数据（Hive Metastore）用独立关系库并备份，它是数仓的命脉
2. ZooKeeper 集群用奇数节点（3/5），过半存活才可用
3. HBase RowKey 设计先想清访问模式，避免热点
4. Sqoop 增量导入用时间戳/自增主键，避免全量重复拉取
5. 权限统一用 Ranger 管理，别各组件各配一套
6. 数据血缘用 Atlas 自动采集，支撑治理和影响分析
7. 集群对外访问统一走 Knox 网关，配合 Kerberos 认证
8. HBase 提前预分区 + RowKey 打散，避免自动 split 抖动
9. Flume 关键日志用 file channel 或 Kafka 缓冲，别裸用 memory channel
10. Oozie 工作流参数外置到 job.properties，别把路径写死在 workflow.xml

### 踩坑记录

```text
坑 1：Hive Metastore 没备份导致元数据丢失
结论：Metastore 损坏，所有表定义丢失，数据「看得见读不了」。
原因：元数据存关系库但没做备份和高可用。
解法：Metastore 关系库做主从 + 定期备份，元数据是数仓命脉。

坑 2：ZooKeeper 配偶数节点导致可用性下降
结论：偶数节点时一个节点挂掉可能导致「不过半」，服务不可用。
原因：ZooKeeper 依赖过半存活，偶数节点浪费且容错差。
解法：用奇数节点（3/5/7），过半即可用。

坑 3：Sqoop 全量导入没去重导致数据重复
结论：重复导入产生重复数据，下游统计翻倍。
原因：每次全量导入追加到目标目录，无去重机制。
解法：用增量导入（append/lastmodified），或全量导入前清空目标。

坑 4：HBase RowKey 递增时间戳导致热点
结论：写入集中单个 Region，吞吐上不去。
原因：递增 RowKey 让新数据永远写同一 Region。
解法：RowKey 前置散列/反转，打散写入热点。

坑 5：Flume 用 memory channel 导致数据丢失
结论：Agent 崩溃时内存里的日志丢失。
原因：memory channel 无持久化，进程挂掉数据就没了。
解法：关键数据用 file channel（持久化），或改用 Kafka 缓冲。

坑 6：Hive 默认 MapReduce 引擎导致查询慢
结论：查询耗时长、资源利用率低。
原因：默认 MR 每次任务都要落盘、启动开销大。
解法：切 Tez/Spark 引擎，配合 ORC/Parquet 列式存储。

坑 7：ZooKeeper 会话超时设太短导致频繁重连
结论：客户端频繁 session 过期重连，watch 丢失。
原因：sessionTimeout 太小，GC 停顿或网络抖动就超时。
解法：sessionTimeout 设合理值（如 30s），客户端做好重连和 watch 重建。

坑 8：Sqoop 导出字段类型不匹配报错或精度丢失
结论：导出失败或数值精度丢失。
原因：Hive 与目标库字段类型不一致（DECIMAL 精度、NULL 值）。
解法：导出前统一字段类型，用 --input-null-string/--input-null-non-string 处理 NULL。
```
