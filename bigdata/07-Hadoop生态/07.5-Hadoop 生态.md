## 概述

Hadoop 生态是围绕 HDFS（存储）和 YARN（调度）生长出的一整套组件：Hive 提供 SQL 查询、HBase 提供海量随机读写、Sqoop 做关系库导入导出、Oozie 做工作流调度、ZooKeeper 做分布式协调、Flume 做日志采集、Ranger/Atlas/Knox 做安全与治理。理解这些组件的定位和协作关系，才能搭建一个完整可用的企业级大数据平台。

```text
Hadoop 生态组件分类：
1. 查询计算 —— Hive（SQL on Hadoop）、HBase（NoSQL 宽列）
2. 数据集成 —— Sqoop（关系库 <-> HDFS）、Flume（日志采集）
3. 调度协调 —— Oozie（工作流调度）、ZooKeeper（分布式协调）
4. 安全治理 —— Ranger（权限）、Atlas（元数据/血缘）、Knox（网关）
```

```text
各组件在平台中的位置：
数据源 -> Flume/Sqoop 采集 -> HDFS/Hive 存储 -> Hive/Spark 计算
        -> 结果输出 -> Oozie 调度编排整个流程
横切：ZooKeeper 做协调，Ranger/Atlas/Knox 做安全治理
```

## Hive

Hive 是 Hadoop 生态的数据仓库工具，把 SQL（HiveQL）翻译成 MapReduce/Tez/Spark 任务在 Hadoop 上执行，让熟悉 SQL 的人也能处理海量数据。它管理元数据（表结构、分区，存于 Metastore），数据存 HDFS，是离线数仓的标准入口。如今 Hive 主要承载 SQL 元数据管理和批处理，计算引擎逐步转向 Spark。

```text
Hive 要点：
1. SQL on Hadoop —— HiveQL 翻译成分布式计算任务
2. Metastore —— 元数据（库/表/分区/列）存独立的关系库
3. 分区表 —— 按日期等分区，查询裁剪分区提升性能
4. 计算引擎 —— 可切换 MapReduce/Tez/Spark
```

```sql
-- Hive 建表与查询
CREATE TABLE orders (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2)
) PARTITIONED BY (dt STRING)
STORED AS PARQUET;

-- 按分区查询（自动裁剪分区）
SELECT user_id, SUM(amount) AS total
FROM orders
WHERE dt = '2024-08-14'
GROUP BY user_id;
```

```text
详见 08.1-Hive 架构与表管理 / 08.2-Hive SQL 与查询优化
```

## HBase

HBase 是构建在 HDFS 上的分布式宽列 NoSQL 数据库，面向海量行的随机读写与范围扫描，弥补 HDFS「不适合随机读写」的短板。数据按行键（RowKey）字典序排序、按 Region 切分分布，支持十亿行规模的秒级点查，是 Hadoop 生态里实时查询明细数据的标准存储。

```text
HBase 要点：
1. 行键排序 —— 数据按 RowKey 字典序存储，RowKey 设计决定性能
2. Region —— 表按 RowKey 范围切分成 Region，分布到 RegionServer
3. 列族 —— 列按列族组织，列族下可动态加列（稀疏宽表）
4. 随机读写 —— 弥补 HDFS 只适合顺序读的短板
```

```shell
# HBase Shell
create 'users', 'info'
put 'users', '1001', 'info:name', 'alice'
get 'users', '1001'
scan 'users', {STARTROW => '1000', ENDROW => '2000'}
```

```text
详见 05.6-NoSQL 中 HBase 章节
```

## Sqoop

Sqoop 是 Hadoop 生态的数据导入导出工具，用于在关系型数据库（MySQL/Oracle/PostgreSQL）和 HDFS/Hive/HBase 之间批量搬运数据。它基于 MapReduce 并行传输，支持全量和增量（按时间戳/主键）同步，是离线数仓「从业务库拉数据」的经典工具（现逐步被 DataX/SeaTunnel 等替代）。

```text
Sqoop 要点：
1. 关系库 <-> HDFS —— 双向批量传输
2. 并行传输 —— 底层用 MapReduce 并行拉取
3. 增量同步 —— 按时间戳/主键做增量导入
4. Hive 集成 —— 导入后自动建 Hive 表
```

```shell
# 从 MySQL 导入到 HDFS
sqoop import \
  --connect jdbc:mysql://mysql-host:3306/db \
  --username root --password pass \
  --table orders \
  --target-dir /data/raw/orders \
  --num-mappers 4

# 增量导入（按时间戳）
sqoop import \
  --connect jdbc:mysql://mysql-host:3306/db \
  --username root --password pass \
  --table orders \
  --target-dir /data/raw/orders \
  --incremental append \
  --check-column order_id \
  --last-value 1000000
```

## Oozie

Oozie 是 Hadoop 生态的工作流调度引擎，用 XML 定义 DAG（有向无环图）工作流，编排 Hive/MapReduce/Spark/Shell 等任务的依赖关系和执行顺序。它支持定时调度（Coordinator）和条件分支，是 Hadoop 时代离线任务编排的标准工具（现逐步被 Airflow/DolphinScheduler 取代）。

```text
Oozie 要点：
1. 工作流 —— XML 定义 DAG，编排多个任务的依赖顺序
2. 定时调度 —— Coordinator 按时间/cron 触发工作流
3. 任务类型 —— 支持 MapReduce/Hive/Spark/Shell/Pig 等
4. 容错 —— 任务失败重试，支持条件分支
```

```xml
<!-- workflow.xml：Hive -> Spark 的 DAG -->
<workflow-app name="etl-flow" xmlns="uri:oozie:workflow:0.5">
  <start to="hive-node"/>
  <action name="hive-node">
    <hive xmlns="uri:oozie:hive-action:0.2">
      <script>etl.sql</script>
    </hive>
    <ok to="spark-node"/>
    <error to="fail"/>
  </action>
  <action name="spark-node">
    <spark xmlns="uri:oozie:spark-action:0.1">
      <master>yarn-cluster</master>
      <class>com.example.AggJob</class>
    </spark>
    <ok to="end"/>
    <error to="fail"/>
  </action>
  <kill name="fail"><message>ETL failed</message></kill>
  <end name="end"/>
</workflow-app>
```

## ZooKeeper

ZooKeeper 是分布式协调服务，提供分布式环境下的「一致性的配置存储 + 命名服务 + 分布式锁 + 选举」等协调原语。它用 ZAB 协议保证强一致，数据存内存、持久化到磁盘，是 Hadoop 生态几乎所有组件（HBase、Kafka、YARN HA、Hive）做主备选举和配置管理的依赖。

```text
ZooKeeper 要点：
1. 强一致 —— ZAB 协议，数据一致可靠
2. 数据模型 —— 类文件系统的树形节点（znode），支持监听（watch）
3. 典型用途 —— 主备选举、分布式锁、配置中心、服务发现
4. 奇数节点 —— 集群通常 3/5 个节点，过半存活即可用
```

```shell
# ZooKeeper 客户端操作
zkCli.sh
create /config "value"               # 创建节点
get /config                          # 读取节点
set /config "new-value"              # 更新节点
ls /                                  # 查看子节点
```

```text
ZooKeeper 的典型应用：
1. HBase —— 存储元数据位置、RegionServer 注册
2. Kafka —— Broker 注册、Controller 选举、元数据
3. YARN HA —— ResourceManager 主备选举
4. 分布式锁 —— 临时顺序节点实现
```

## Flume

Flume 是分布式日志采集系统，把分布在多台服务器上的日志实时采集、聚合、传输到 HDFS/HBase/Kafka。它以 Agent 为单元，由 Source（数据源）、Channel（缓冲通道）、Sink（目的地）三段组成，可靠地传输海量日志，是大数据平台「日志入湖」的经典入口。

```text
Flume 要点：
1. Agent 架构 —— Source + Channel + Sink 三段式
2. 可靠传输 —— Channel 缓冲，事务保证不丢
3. 多级 Agent —— 采集 -> 聚合 -> 落地的多级拓扑
4. 目的地 —— HDFS/HBase/Kafka 等
```

```text
# flume.conf：采集日志到 Kafka
agent.sources = s1
agent.sources.s1.type = spooldir
agent.sources.s1.spoolDir = /data/logs

agent.channels = c1
agent.channels.c1.type = memory
agent.channels.c1.capacity = 10000

agent.sinks = k1
agent.sinks.k1.type = org.apache.flume.sink.kafka.KafkaSink
agent.sinks.k1.kafka.topic = logs

agent.sources.s1.channels = c1
agent.sinks.k1.channel = c1
```

## Ranger

Apache Ranger 是 Hadoop 生态的统一安全授权框架，提供集中式的权限管理：对 HDFS/Hive/HBase/Kafka 等组件做细粒度的策略授权（行级、列级过滤和脱敏），并做审计。它让安全策略集中管理、统一下发，是企业级大数据平台做权限管控的标准组件。

```text
Ranger 要点：
1. 统一授权 —— 一个控制台管理所有组件的权限策略
2. 细粒度 —— 支持行级/列级权限、数据脱敏（masking）
3. 审计 —— 记录所有访问行为，满足合规
4. 插件机制 —— 各组件装 Ranger 插件，策略实时生效
```

```text
Ranger 管理的典型策略：
1. Hive —— 库/表/列的 select/insert 权限
2. HDFS —— 目录/文件的读写权限
3. HBase —— 表/列族的读写权限
4. 脱敏 —— 对身份证/手机号等敏感列做掩码
```

## Atlas

Apache Atlas 是 Hadoop 生态的元数据管理与数据治理平台，自动采集各组件（Hive/HBase/Kafka/Spark）的元数据，建立数据资产目录和数据血缘（lineage），支持数据分类、标签、审计。它是「数据在哪、怎么流转、谁在用」的统一视图，是数据治理的基础设施。

```text
Atlas 要点：
1. 元数据采集 —— 自动从 Hive/HBase/Kafka 等采集元数据
2. 数据血缘 —— 追踪数据从源到报表的完整流转链路
3. 分类标签 —— 数据分类（PII/敏感）和业务标签
4. 数据治理 —— 支撑数据资产盘点、影响分析、合规
```

```text
Atlas 的核心价值：
1. 数据血缘 —— 字段级血缘，回答「这个指标怎么算出来的」
2. 资产目录 —— 统一检索数据资产，找数方便
3. 影响分析 —— 改了某表，哪些下游受影响
4. 合规审计 —— 敏感数据分布与流转可查
```

## Knox

Apache Knox 是 Hadoop 集群的 REST API 网关，提供统一的访问入口和认证，对外暴露 HDFS/Hive/HBase 等的 REST 接口，内部转发到集群。它解决「集群服务端口多、认证复杂」的问题，让外部应用通过一个安全的网关访问 Hadoop，配合 Kerberos/LDAP 做统一认证。

```text
Knox 要点：
1. 统一网关 —— 一个入口代理所有 Hadoop 组件的 REST 接口
2. 认证集成 —— 支持 LDAP/Kerberos/SAML 等认证
3. 简化访问 —— 外部应用不直接连各组件端口，统一走 Knox
4. 安全边界 —— 集群边界的安全网关，配合防火墙使用
```

```text
Knox 的典型场景：
1. 外部 BI 工具通过 Knox 访问 Hive（JDBC/HTTP）
2. Web 应用通过 Knox REST API 访问 HDFS/HBase
3. 统一认证，避免每个组件单独暴露端口
```

## 应用场景实战

### 场景一：搭建一个完整的离线数仓数据链路

```text
业务 MySQL
   |
   | Sqoop 全量/增量导入
   v
HDFS（原始数据 ODS）
   |
   | Hive SQL 清洗加工（DWD/DWS）
   v
Hive 表（结果 ADS）
   |
   | Sqoop 导出
   v
报表 MySQL（供 BI 查询）

调度编排：Oozie 定时触发整个流程
安全治理：Ranger 管权限，Atlas 管血缘
```

```shell
# 典型的一天调度脚本（简化）
# 1. Sqoop 增量拉取
sqoop import --connect jdbc:mysql://db/orders --incremental append ...

# 2. Hive 清洗加工
hive -f dwd_order.sql
hive -f dws_user_order.sql

# 3. Sqoop 导出结果
sqoop export --connect jdbc:mysql://report/ads --table daily_gmv ...
```

### 场景二：日志实时入湖 + 下游消费

```text
业务服务器日志
   |
   | Flume 实时采集（Source -> Channel -> Sink）
   v
Kafka（日志缓冲队列，ZooKeeper 协调）
   |
   | 消费（Spark/Flink）
   v
HDFS/Hive（归档 + 分析）
```

```text
# Flume 采集日志到 Kafka
agent.sources.s1.type = taildir
agent.sources.s1.filegroups = f1
agent.sources.s1.filegroups.f1 = /data/logs/*.log
agent.sinks.k1.type = org.apache.flume.sink.kafka.KafkaSink
agent.sinks.k1.kafka.topic = app-logs
```

## 最佳实践与踩坑记录

### 最佳实践

1. 元数据（Hive Metastore）用独立关系库并备份，它是数仓的命脉
2. ZooKeeper 集群用奇数节点（3/5），过半存活才可用
3. HBase RowKey 设计先想清访问模式，避免热点
4. Sqoop 增量导入用时间戳/自增主键，避免全量重复拉取
5. 权限统一用 Ranger 管理，别各组件各配一套
6. 数据血缘用 Atlas 自动采集，支撑治理和影响分析
7. 集群对外访问统一走 Knox 网关，配合 Kerberos 认证

### 踩坑记录

```text
坑 1：Hive Metastore 没备份导致元数据丢失
结论：Metastore 损坏，所有表定义丢失，数据「看得见读不了」。
原因：元数据存关系库但没做备份和高可用。
解法：Metastore 关系库做主从 + 定期备份，元数据是数仓命脉。

坑 2：ZooKeeper 配偶数节点导致可用性下降
结论：偶数节点时一个节点挂掉可能导致「不过半」，服务不可用。
原因：ZooKeeper 依赖过半存活，偶数节点浪费且容错差。
解法：用奇数节点（3/5/7），过半即可用。

坑 3：Sqoop 全量导入没去重导致数据重复
结论：重复导入产生重复数据，下游统计翻倍。
原因：每次全量导入追加到目标目录，无去重机制。
解法：用增量导入（append/lastmodified），或全量导入前清空目标。

坑 4：HBase RowKey 递增时间戳导致热点
结论：写入集中单个 Region，吞吐上不去。
原因：递增 RowKey 让新数据永远写同一 Region。
解法：RowKey 前置散列/反转，打散写入热点。

坑 5：Flume 用 memory channel 导致数据丢失
结论：Agent 崩溃时内存里的日志丢失。
原因：memory channel 无持久化，进程挂掉数据就没了。
解法：关键数据用 file channel（持久化），或改用 Kafka 缓冲。
```
