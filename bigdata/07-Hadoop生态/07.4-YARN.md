## 概述

YARN（Yet Another Resource Negotiator）是 Hadoop 的资源管理与调度层，把集群的 CPU、内存统一抽象成「Container」进行分配，让 MapReduce、Spark、Flink 等多个计算框架共享同一套集群资源。它解决了 Hadoop 1.x 里「计算与资源调度耦合」的问题，使集群成为通用的「数据操作系统」，是 Hadoop 2.x 之后最核心的架构升级。

```text
YARN 的核心价值：
1. 资源统一调度 —— CPU/内存抽象成 Container，全局分配
2. 多框架共存 —— MapReduce/Spark/Flink/Tez 共享集群
3. 计算与调度解耦 —— 应用逻辑（AM）与资源管理（RM）分离
4. 弹性利用 —— 按需申请资源，提高集群利用率
```

```text
YARN 任务提交流程：
1. Client 向 ResourceManager 提交应用
2. RM 分配第一个 Container 启动 ApplicationMaster
3. AM 向 RM 申请执行任务所需的 Container
4. RM 调度 Container 到各 NodeManager
5. AM 在各 Container 里启动具体任务
6. 任务完成，AM 注销并释放资源
```

## 核心概念

YARN 把「资源管理」和「应用逻辑」彻底拆开：ResourceManager 管全局资源，NodeManager 管单机资源，ApplicationMaster 管单个应用的任务编排，Container 是资源分配的最小单元，Scheduler 决定「资源分给谁」，Capacity/Fair 是两种主流调度策略。下面逐个拆解。

### ResourceManager

ResourceManager（RM）是 YARN 的全局资源总管（主节点），负责接收应用提交、管理所有 NodeManager 的资源、调度 Container 分配。它由两个核心组件组成：Scheduler（调度器，只负责分配）和 ApplicationsManager（应用管理，管理 AM 生命周期）。RM 是 YARN 的单点，通常配 HA。

```text
ResourceManager 职责：
1. 资源管理 —— 汇总各 NodeManager 上报的资源，维护全局资源视图
2. 调度分配 —— 按调度策略把 Container 分配给各应用
3. 应用管理 —— 接收提交、启动/监控 ApplicationMaster
4. 节点管理 —— 跟踪 NodeManager 心跳，标记失效节点
```

```xml
<!-- yarn-site.xml：ResourceManager 关键配置 -->
<configuration>
  <!-- RM 高可用 -->
  <property>
    <name>yarn.resourcemanager.ha.enabled</name>
    <value>true</value>
  </property>
  <!-- RM 地址 -->
  <property>
    <name>yarn.resourcemanager.address</name>
    <value>rm1.example.com:8032</value>
  </property>
  <!-- 调度器：Capacity / Fair -->
  <property>
    <name>yarn.resourcemanager.scheduler.class</name>
    <value>org.apache.hadoop.yarn.server.resourcemanager.scheduler.capacity.CapacityScheduler</value>
  </property>
</configuration>
```

### NodeManager

NodeManager（NM）是每台计算节点的代理（从节点），负责向 RM 上报本机资源（心跳）、监控本机 Container 的运行、管理 Container 的生命周期。它是 YARN 在每台机器上的「执行者」，RM 分配的资源最终由 NM 落地执行。

```text
NodeManager 职责：
1. 资源上报 —— 定期心跳向 RM 汇报本机 CPU/内存/磁盘
2. Container 管理 —— 启动、监控、销毁分配给本机的 Container
3. 资源隔离 —— 用 cgroup 隔离各 Container 的 CPU/内存
4. 健康检查 —— 监控本地磁盘/进程健康，异常时上报 RM
```

```xml
<!-- yarn-site.xml：NodeManager 资源配置 -->
<configuration>
  <!-- NM 可用内存（MB） -->
  <property>
    <name>yarn.nodemanager.resource.memory-mb</name>
    <value>49152</value>
  </property>
  <!-- NM 可用 CPU 核数 -->
  <property>
    <name>yarn.nodemanager.resource.cpu-vcores</name>
    <value>16</value>
  </property>
  <!-- 本地目录（中间数据、Container 工作目录） -->
  <property>
    <name>yarn.nodemanager.local-dirs</name>
    <value>/data/yarn/local1,/data/yarn/local2</value>
  </property>
</configuration>
```

### ApplicationMaster

ApplicationMaster（AM）是每个应用自己的「协调者」，每个应用启动一个 AM，负责向 RM 申请资源、与 NM 协作启动任务、监控任务进度、处理失败重试。AM 让「应用逻辑」和「资源调度」彻底解耦——不同框架（MapReduce/Spark/Flink）有各自的 AM 实现，但共享同一套 RM/NM。

```text
ApplicationMaster 职责：
1. 申请资源 —— 根据任务需求向 RM 申请 Container
2. 启动任务 —— 在分配到的 Container 里启动具体任务
3. 监控进度 —— 跟踪任务执行状态，处理失败与重试
4. 释放资源 —— 任务完成后归还 Container 并注销
```

```text
不同框架的 AM 实现：
MapReduce —— MRAppMaster（管理 Map/Reduce 任务）
Spark —— ApplicationMaster（管理 Executor）
Flink —— JobManager（YARN 模式下作为 AM）
框架不同，AM 逻辑不同，但都跑在 YARN 的统一调度之上
```

### Container

Container 是 YARN 的资源抽象单元，封装了「一定量的 CPU 和内存」以及运行环境（依赖、环境变量、工作目录）。所有任务都运行在 Container 里，资源以 Container 为单位申请和分配。Container 是 YARN 资源隔离与调度的最小粒度。

```text
Container 要点：
1. 资源封装 —— 包含 CPU 核数 + 内存大小 + 运行环境
2. 调度单位 —— 资源以 Container 为单位分配和回收
3. 资源隔离 —— NM 用 cgroup 隔离各 Container 的资源
4. 生命周期 —— 由 NM 管理：启动、监控、销毁
```

```yaml
# 提交 Spark 应用时，executor 就是一组 Container
spark-submit \
  --master yarn \
  --deploy-mode cluster \
  --num-executors 4 \
  --executor-memory 4g \      # 每个 executor Container 4G 内存
  --executor-cores 2          # 每个 executor Container 2 核
  my_job.py
```

```text
资源计算示例：
节点 16 核 48G，每 Container 2 核 4G
该节点最多容纳 min(16/2, 48/4) = 8 个 Container
```

### Scheduler

Scheduler 是 ResourceManager 里的调度器组件，负责把资源（Container）按某种策略分配给各应用。它只做「分配」，不监控任务执行、不处理失败（那些由 AM 负责）。YARN 提供三种调度器：FIFO（先进先出，简单但易饿死）、Capacity（容量调度，多队列配额，默认）、Fair（公平调度，按权重共享）。

```text
调度器对比：
1. FIFO —— 单队列先来先服务，简单但后面任务可能饿死
2. Capacity —— 多队列，每队列固定容量配额，队列内 FIFO，默认推荐
3. Fair —— 多队列按权重公平共享，空闲资源可被借用，适合多租户
```

```text
调度器职责边界：
Scheduler 只负责「把资源分配给谁」
不负责：任务执行监控、失败重试、进度跟踪
这些由 ApplicationMaster 负责（调度与应用逻辑解耦）
```

### Capacity

Capacity Scheduler 是 YARN 默认的多队列调度器，把集群资源划分成多个队列，每个队列有「容量配额」（如队列 A 占 60%、B 占 40%），队列内任务按 FIFO 排队。它保证关键业务队列的资源下限，空闲时资源可被其他队列借用（弹性），是多租户隔离的标准方案。

```text
Capacity 调度器要点：
1. 队列配额 —— 每队列有最小容量百分比，保证资源下限
2. 队列内 FIFO —— 同队列任务按提交顺序执行
3. 弹性借用 —— 队列空闲时资源可借给其他队列，忙时回收
4. 层级队列 —— 支持父子队列，进一步细分（如 A 下分 a1、a2）
```

```xml
<!-- capacity-scheduler.xml：队列配置 -->
<configuration>
  <property>
    <name>yarn.scheduler.capacity.root.queues</name>
    <value>prod,dev</value>
  </property>
  <!-- prod 队列占 70%，dev 占 30% -->
  <property>
    <name>yarn.scheduler.capacity.root.prod.capacity</name>
    <value>70</value>
  </property>
  <property>
    <name>yarn.scheduler.capacity.root.dev.capacity</name>
    <value>30</value>
  </property>
  <!-- 单用户最多用队列的 50% -->
  <property>
    <name>yarn.scheduler.capacity.root.prod.user-limit-factor</name>
    <value>0.5</value>
  </property>
</configuration>
```

### Fair

Fair Scheduler 是多队列的公平调度器，按「公平份额」把资源平均（或按权重）分配给各应用/队列，避免某个大任务独占资源饿死小任务。它支持抢占（preemption）——当某个队列占用超过其公平份额且其他队列有需求时，可抢占超额资源。适合多租户、多用户共享的集群。

```text
Fair 调度器要点：
1. 公平份额 —— 资源按权重公平分配，无任务独占
2. 抢占 —— 超额占用可被抢占，保证公平性
3. 动态平衡 —— 新任务加入时资源自动重新分配
4. 多租户友好 —— 适合多团队共享、需要公平的集群
```

```xml
<!-- fair-scheduler.xml：公平调度配置 -->
<configuration>
  <property>
    <name>yarn.scheduler.fair.allocation.file</name>
    <value>/etc/hadoop/fair-scheduler.xml</value>
  </property>
  <property>
    <name>yarn.scheduler.fair.preemption</name>
    <value>true</value>
  </property>
</configuration>
```

```text
Capacity vs Fair 选择：
Capacity —— 需要强资源隔离、保证关键业务资源下限（生产常用）
Fair —— 需要公平共享、多团队混合、追求资源利用率
```

## 工作原理

YARN 一次应用运行是「提交 → 分配 AM → AM 申请 Container → 执行 → 回收」的闭环，核心是 RM/NM/AM 三者通过心跳和 RPC 协同：

1. **应用提交**：Client 向 RM 的 ApplicationsManager 提交应用，RM 在某个 NM 上分配第一个 Container 启动 ApplicationMaster。
2. **资源申请**：AM 启动后根据任务需求向 RM 的 Scheduler 申请 Container；RM 汇总所有 NM 心跳上报的资源，按调度策略（Capacity/Fair）把 Container 分配给它。
3. **任务启动**：AM 拿到 Container 后，与对应 NM 通信，在 Container 里启动具体任务（Map/Reduce task、Spark Executor 等）。
4. **监控与容错**：NM 监控 Container 运行，任务失败由 AM 决定重试或放弃；AM 自己挂了由 RM 重启；NM 挂了 RM 把其上的任务标记失败、重新调度。
5. **回收注销**：任务全部完成，AM 释放 Container 并向 RM 注销，整个应用结束。

```text
YARN 三组件协同关系：
RM（全局大脑）-- 心跳/资源上报 --> NM（单机执行者）
RM（分配 Container）-- RPC --> AM（应用协调者）
AM（启动任务）-- RPC --> NM（拉起 Container）
```

```text
心跳与资源模型：
1. NM 定期（默认 1s）向 RM 心跳，上报本机可用 CPU/内存/Container 状态
2. RM 超过阈值（默认 10 分钟）收不到心跳，判定该 NM 失效，其上任务重新调度
3. 资源以 Container 为粒度分配：<memory, vcores>，NM 用 cgroup 做硬隔离
```

## 常用命令与配置

```shell
# 查看所有节点与资源状态
yarn node -list -all

# 查看集群队列及其容量、使用情况
yarn queue -status prod

# 查看应用列表（按状态过滤）
yarn application -list
yarn application -list -appStates RUNNING
yarn application -list -appStates ACCEPTED

# 查看单个应用状态与诊断信息
yarn application -status application_202408141200_0001

# 杀掉一个应用
yarn application -kill application_202408141200_0001

# 拉取应用完整日志
yarn logs -applicationId application_202408141200_0001

# 实时查看集群/队列资源使用（类似 top）
yarn top
yarn top -queue prod

# RM 管理命令（HA 切换、查看状态）
yarn rmadmin -getServiceState rm1
yarn rmadmin -transitionToActive rm1
```

```text
提交应用时指定队列：
hadoop jar my-job.jar com.example.Job -Dmapreduce.job.queuename=prod.etl
spark-submit --master yarn --queue prod.etl my_job.py
```

## 配置文件解析

YARN 的配置集中在 `yarn-site.xml`（RM/NM 行为）和 `capacity-scheduler.xml`/`fair-scheduler.xml`（调度策略）。

```xml
<!-- yarn-site.xml：YARN 核心配置 -->
<configuration>
  <!-- RM 地址与 HA -->
  <property>
    <name>yarn.resourcemanager.address</name>
    <value>rm1.example.com:8032</value>
  </property>
  <property>
    <name>yarn.resourcemanager.ha.enabled</name>
    <value>true</value>
  </property>
  <!-- 调度器类型 -->
  <property>
    <name>yarn.resourcemanager.scheduler.class</name>
    <value>org.apache.hadoop.yarn.server.resourcemanager.scheduler.capacity.CapacityScheduler</value>
  </property>
  <!-- NM 单机资源：内存（MB）与 CPU 核 -->
  <property>
    <name>yarn.nodemanager.resource.memory-mb</name>
    <value>49152</value>
  </property>
  <property>
    <name>yarn.nodemanager.resource.cpu-vcores</name>
    <value>16</value>
  </property>
  <!-- NM 本地目录：Container 工作目录与中间数据，多盘逗号分隔 -->
  <property>
    <name>yarn.nodemanager.local-dirs</name>
    <value>/data/yarn/local1,/data/yarn/local2</value>
  </property>
  <!-- 日志聚合：任务日志集中到 HDFS，方便事后排查 -->
  <property>
    <name>yarn.log-aggregation-enable</name>
    <value>true</value>
  </property>
  <!-- 单 Container 可申请的最大内存（MB） -->
  <property>
    <name>yarn.scheduler.maximum-allocation-mb</name>
    <value>16384</value>
  </property>
</configuration>
```

```text
内存配置要点：
1. 单 Container 内存上限 = yarn.scheduler.maximum-allocation-mb，下限 = minimum-allocation-mb
2. Container 内存应是 minimum-allocation-mb 的整数倍，否则向上取整
3. NM 内存要留出系统开销（约 20%），别把物理内存全分给 YARN
4. vcores 是逻辑核，与物理核对齐即可，别超分太多
```

## 应用场景实战

### 场景一：多租户集群的队列规划

```text
需求：一个集群服务 生产任务 + 开发调试，生产不能受影响

Capacity Scheduler 规划：
root
├── prod（70%，生产队列）
│   ├── etl（离线 ETL）
│   └── rt（实时任务）
└── dev（30%，开发队列）
    ├── test
    └── adhoc

配置要点：
1. prod 最小容量 70%，保证生产资源下限
2. dev 空闲时 prod 可借用，但 dev 忙时可回收
3. 单用户 limit-factor 防单个用户占满队列
4. 提交时指定队列：--queue prod.etl
```

```shell
# 指定队列提交任务
spark-submit --master yarn --queue prod.etl my_etl.py
hadoop jar my-job.jar com.example.Job --queue prod.etl
```

### 场景二：排查 YARN 任务资源不足

```shell
# 1. 查看集群资源与队列状态
yarn node -list -all
yarn queue -status prod

# 2. 查看应用状态与资源申请
yarn application -list
yarn application -status <app_id>

# 3. 查看应用日志定位问题
yarn logs -applicationId <app_id>

# 4. 常见问题：资源不足排队、Container 被抢占、内存超限被杀
```

### 场景三：配置队列 ACL 与资源上限，验证多租户隔离

```xml
<!-- capacity-scheduler.xml：给 prod 队列加 ACL 和资源上限 -->
<configuration>
  <property>
    <name>yarn.scheduler.capacity.root.prod.capacity</name>
    <value>70</value>
  </property>
  <!-- 队列最大容量：即使集群空闲，prod 最多用到 85% -->
  <property>
    <name>yarn.scheduler.capacity.root.prod.maximum-capacity</name>
    <value>85</value>
  </property>
  <!-- 提交 ACL：只有 data_group 能往 prod 队列提交 -->
  <property>
    <name>yarn.scheduler.capacity.root.prod.acl_submit_applications</name>
    <value>data_group</value>
  </property>
  <!-- 管理 ACL：只有管理员能 kill 队列里的应用 -->
  <property>
    <name>yarn.scheduler.capacity.root.prod.acl_administer_queue</name>
    <value>yarn_admin</value>
  </property>
</configuration>
```

```shell
# 刷新队列配置（改完 capacity-scheduler.xml 后执行）
yarn rmadmin -refreshQueues

# 验证：非授权用户提交到 prod 队列会被拒
# data_user 提交成功
yarn application -list -appStates RUNNING
# 其他用户提交报 AccessControlException，证明隔离生效
```

## 性能与调优

YARN 调优的核心是「把物理资源合理折算成可调度的 Container，避免浪费和超分」。

```text
资源折算调优：
1. 每核内存 —— 常见配 1 核 : 2~4G，如 16 核 64G 节点，vcores=16、memory=49152（48G，留 16G 系统开销）
2. 最小/最大 Container —— minimum-allocation-mb 默认 1024，maximum-allocation-mb 默认 8192，按任务大小放宽
3. 内存整数倍 —— 申请 1.5G 会被向上取整到 2G，造成浪费，尽量按最小粒度的整数倍申请
4. 别超分 vcores —— 逻辑核超过物理核太多会导致 CPU 争抢，任务反而变慢
```

```text
调度器调优：
1. Capacity —— 队列配额按业务重要性划分，设 user-limit-factor 防单用户占满
2. Fair —— 设抢占（preemption），避免长任务饿死其他队列
3. 队列数量 —— 别建太多层级队列，调度开销和管理成本都上升
4. 延迟调度 —— 允许等一小段时间把任务调度到数据所在节点（数据局部性）
```

```text
日志与 IO 调优：
1. 开启日志聚合（yarn.log-aggregation-enable）—— 集中到 HDFS，事后排查方便
2. local-dirs 配多块盘 —— Container 工作目录与中间数据并行 IO
3. log-dirs 与 local-dirs 分开 —— 日志别和中间数据抢盘
```

## 安全与权限

```text
YARN 安全要点：
1. Kerberos 认证 —— 安全集群中 Client、NM、RM 都需认证，提交前 kinit
2. 队列 ACL —— acl_submit_applications 限制谁能提交，acl_administer_queue 限制谁能管理队列
3. Delegation Token —— 长任务由 AM 持 token 访问 HDFS，避免频繁认证与凭证外泄
4. 资源隔离 —— cgroup 硬隔离 Container 的 CPU/内存，防止一个任务打爆节点
5. Web UI 安全 —— RM Web UI 暴露队列/应用信息，生产要加认证或网络隔离
6. 审计日志 —— 应用提交、队列操作、Container 分配都进审计，用于安全追溯
```

```shell
# 安全集群中先认证再提交
kinit -kt /etc/security/keytabs/data.keytab data_user
spark-submit --master yarn --queue prod.etl my_job.py
```

## 故障排查

```text
常见故障与排查方向：

故障 1：应用一直 ACCEPTED 排队不运行
排查：yarn queue -status <队列> 看队列容量是否用满；看是否有大任务占满资源；看队列最大容量限制；资源不足就等或调大配额。

故障 2：Container 内存超限被 NM 杀死
排查：yarn logs 看 Container 日志里的 "Container killed by NodeManager"；JVM 堆 + 堆外内存超了 Container 内存上限，调大 Container 内存或减小堆。

故障 3：NodeManager 心跳丢失被标记 UNHEALTHY
排查：看 NM 本地磁盘是否满（默认磁盘满 90% 判不健康）；看 local-dirs 是否只读或挂载失败；看 NM 进程是否存活。

故障 4：RM 挂了集群无法提交调度
排查：是否配了 RM HA；看 ZKFC/ZooKeeper 状态；未配 HA 需手动重启 RM，并尽快补上 HA。

故障 5：任务频繁被抢占（Fair 调度）
排查：看 fair-scheduler 的 preemption 配置与队列公平份额；被抢占说明该队列超额占用，可调整权重或关抢占。
```

```shell
# 排查标准流程
yarn application -status <app_id>       # 看诊断信息（Diagnostics 字段）
yarn logs -applicationId <app_id>       # 拉日志定位具体错误
yarn node -list -all                    # 看节点状态（RUNNING/UNHEALTHY）
yarn queue -status <队列>                # 看队列容量与使用率
```

## 常见问题

```text
Q1: ResourceManager 挂了影响什么？NodeManager 挂了呢？
A: RM 挂整个集群无法提交/调度新应用（已运行的不受影响，但 AM 申请不到资源）；NM 挂只影响该节点的 Container，其上任务被重新调度到别的节点。

Q2: 任务一直 ACCEPTED 不运行是什么原因？
A: 队列资源被占满、任务在排队；或队列 maximum-capacity 限制；或 NM 资源不足。用 yarn queue -status 和 yarn node -list 排查。

Q3: Capacity 和 Fair 调度器怎么选？
A: 要强隔离、保证关键业务资源下限选 Capacity（生产默认）；要多团队公平共享、追求利用率选 Fair。多数生产集群用 Capacity。

Q4: Container 内存怎么算才不会 OOM？
A: JVM 堆 + 堆外（Metaspace、Direct Buffer、Native 内存）都要算进 Container 内存，一般 executor-memory 取堆的 1.2~1.5 倍留足余量。

Q5: 怎么查看一个应用的日志？
A: yarn logs -applicationId <app_id> 拉聚合日志；若没开日志聚合，去对应 NM 的 userlogs 目录找。

Q6: ApplicationMaster 和 ResourceManager 的分工是什么？
A: RM 管全局资源分配（谁拿多少 Container），AM 管单个应用内部（申请资源、启动任务、监控重试）。AM 让不同框架共享同一套 RM/NM。

Q7: 为什么要把内存和 vcores 都配，只配一个不行吗？
A: 只配内存不配 vcores 会导致 CPU 无限超分，多个任务抢 CPU 争抢反而变慢；两者一起构成 Container 的资源约束，cgroup 才能硬隔离。
```

## 面试题

```text
1. 简述 YARN 的架构和一次应用提交流程。
   答：RM（资源总管）+ NM（单机执行）+ AM（应用协调）+ Container（资源单元）。流程：Client 提交 → RM 分配第一个 Container 启 AM → AM 向 RM 申请 Container → RM 调度到 NM → AM 在 Container 里启动任务 → 完成后 AM 注销释放资源。

2. Container 是什么？为什么用 Container 抽象资源？
   答：Container 封装一定量 CPU + 内存 + 运行环境的资源单元，是分配和隔离的最小粒度。用 Container 把资源从「固定槽位」变成「按需申请的弹性单元」，让多框架共享集群。

3. Capacity 和 Fair 调度器的区别？
   答：Capacity 每队列固定容量配额、队列内 FIFO、可弹性借用，保证关键业务下限；Fair 按公平份额/权重动态分配、支持抢占，追求公平与利用率。

4. ApplicationMaster 的作用？它怎么实现「计算与调度解耦」？
   答：AM 负责单个应用的任务编排（申请资源、启动任务、监控重试），不同框架有自己的 AM 实现但共享同一套 RM/NM。这样 YARN 只做通用资源调度，应用逻辑由各框架 AM 负责。

5. YARN 相比 Hadoop 1.x 的 JobTracker 有什么改进？
   答：JobTracker 既做资源管理又做任务调度监控，单点瓶颈、扩展性差、只支持 MapReduce；YARN 把两者拆成 RM（资源）和 AM（应用），支持多框架、可扩展性大幅提升。

6. 如何估算一个 Spark 应用需要多少 YARN 资源？
   答：按数据量估算 executor 数与内存，再折算 Container：总内存 = executor 数 × (executor-memory + overhead)，总核 = executor 数 × executor-cores，加上 driver 的资源，对照队列容量判断能否放下。

7. 什么情况下需要配 YARN 队列的 user-limit-factor？
   答：队列内某个用户提交大量任务可能占满整个队列，饿死同队列其他用户；设 user-limit-factor 限制单用户最大占用比例，保证队列内用户公平。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产用 Capacity Scheduler，按业务划分队列并设配额
2. ResourceManager 必须配 HA（Active/Standby），消除单点
3. NodeManager 本地目录配多块盘，提升中间数据 IO
4. Container 内存预留合理余量，避免 JVM 堆超限被 NM 杀掉
5. 单用户设 user-limit-factor，防止个别用户占满队列
6. 开启日志聚合（yarn.log-aggregation-enable），方便事后排查
7. 监控队列资源使用率，及时调整配额

### 踩坑记录

```text
坑 1：RM 单点故障导致整个集群调度瘫痪
结论：RM 挂掉，所有任务无法提交/调度，集群不可用。
原因：未配置 ResourceManager HA。
解法：配 RM HA（Active/Standby + ZooKeeper 选举）。

坑 2：Container 内存超限被 NodeManager 杀死
结论：任务运行中途被杀，日志显示 OOM 或 Container killed。
原因：JVM 堆 + 堆外内存超过 Container 分配的内存上限。
解法：Container 内存留足余量（如 executor-memory 1.5 倍于堆），调堆外参数。

坑 3：用 FIFO 调度导致长任务饿死短任务
结论：一个大任务占满资源，后续所有任务排队等待。
原因：FIFO 先来先服务，无抢占和公平机制。
解法：换 Capacity/Fair 调度器，多队列隔离。

坑 4：队列配额没设 user-limit 导致单用户占满队列
结论：某用户提交大量任务占满队列，同队列其他用户饿死。
原因：队列内未限制单用户资源上限。
解法：设 user-limit-factor 限制单用户最大占用比例。

坑 5：本地目录单盘导致 Container 工作目录 IO 瓶颈
结论：任务中间数据读写慢，节点磁盘成瓶颈。
原因：NM 本地目录只配一个盘，IO 无法并行。
解法：local-dirs 配多块盘，分散中间数据 IO。
```
