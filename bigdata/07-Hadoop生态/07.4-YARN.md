## 概述

YARN（Yet Another Resource Negotiator）是 Hadoop 的资源管理与调度层，把集群的 CPU、内存统一抽象成「Container」进行分配，让 MapReduce、Spark、Flink 等多个计算框架共享同一套集群资源。它解决了 Hadoop 1.x 里「计算与资源调度耦合」的问题，使集群成为通用的「数据操作系统」，是 Hadoop 2.x 之后最核心的架构升级。

```text
YARN 的核心价值：
1. 资源统一调度 —— CPU/内存抽象成 Container，全局分配
2. 多框架共存 —— MapReduce/Spark/Flink/Tez 共享集群
3. 计算与调度解耦 —— 应用逻辑（AM）与资源管理（RM）分离
4. 弹性利用 —— 按需申请资源，提高集群利用率
```

```text
YARN 任务提交流程：
1. Client 向 ResourceManager 提交应用
2. RM 分配第一个 Container 启动 ApplicationMaster
3. AM 向 RM 申请执行任务所需的 Container
4. RM 调度 Container 到各 NodeManager
5. AM 在各 Container 里启动具体任务
6. 任务完成，AM 注销并释放资源
```

## ResourceManager

ResourceManager（RM）是 YARN 的全局资源总管（主节点），负责接收应用提交、管理所有 NodeManager 的资源、调度 Container 分配。它由两个核心组件组成：Scheduler（调度器，只负责分配）和 ApplicationsManager（应用管理，管理 AM 生命周期）。RM 是 YARN 的单点，通常配 HA。

```text
ResourceManager 职责：
1. 资源管理 —— 汇总各 NodeManager 上报的资源，维护全局资源视图
2. 调度分配 —— 按调度策略把 Container 分配给各应用
3. 应用管理 —— 接收提交、启动/监控 ApplicationMaster
4. 节点管理 —— 跟踪 NodeManager 心跳，标记失效节点
```

```xml
<!-- yarn-site.xml：ResourceManager 关键配置 -->
<configuration>
  <!-- RM 高可用 -->
  <property>
    <name>yarn.resourcemanager.ha.enabled</name>
    <value>true</value>
  </property>
  <!-- RM 地址 -->
  <property>
    <name>yarn.resourcemanager.address</name>
    <value>rm1.example.com:8032</value>
  </property>
  <!-- 调度器：Capacity / Fair -->
  <property>
    <name>yarn.resourcemanager.scheduler.class</name>
    <value>org.apache.hadoop.yarn.server.resourcemanager.scheduler.capacity.CapacityScheduler</value>
  </property>
</configuration>
```

## NodeManager

NodeManager（NM）是每台计算节点的代理（从节点），负责向 RM 上报本机资源（心跳）、监控本机 Container 的运行、管理 Container 的生命周期。它是 YARN 在每台机器上的「执行者」，RM 分配的资源最终由 NM 落地执行。

```text
NodeManager 职责：
1. 资源上报 —— 定期心跳向 RM 汇报本机 CPU/内存/磁盘
2. Container 管理 —— 启动、监控、销毁分配给本机的 Container
3. 资源隔离 —— 用 cgroup 隔离各 Container 的 CPU/内存
4. 健康检查 —— 监控本地磁盘/进程健康，异常时上报 RM
```

```xml
<!-- yarn-site.xml：NodeManager 资源配置 -->
<configuration>
  <!-- NM 可用内存（MB） -->
  <property>
    <name>yarn.nodemanager.resource.memory-mb</name>
    <value>49152</value>
  </property>
  <!-- NM 可用 CPU 核数 -->
  <property>
    <name>yarn.nodemanager.resource.cpu-vcores</name>
    <value>16</value>
  </property>
  <!-- 本地目录（中间数据、Container 工作目录） -->
  <property>
    <name>yarn.nodemanager.local-dirs</name>
    <value>/data/yarn/local1,/data/yarn/local2</value>
  </property>
</configuration>
```

## ApplicationMaster

ApplicationMaster（AM）是每个应用自己的「协调者」，每个应用启动一个 AM，负责向 RM 申请资源、与 NM 协作启动任务、监控任务进度、处理失败重试。AM 让「应用逻辑」和「资源调度」彻底解耦——不同框架（MapReduce/Spark/Flink）有各自的 AM 实现，但共享同一套 RM/NM。

```text
ApplicationMaster 职责：
1. 申请资源 —— 根据任务需求向 RM 申请 Container
2. 启动任务 —— 在分配到的 Container 里启动具体任务
3. 监控进度 —— 跟踪任务执行状态，处理失败与重试
4. 释放资源 —— 任务完成后归还 Container 并注销
```

```text
不同框架的 AM 实现：
MapReduce —— MRAppMaster（管理 Map/Reduce 任务）
Spark —— ApplicationMaster（管理 Executor）
Flink —— JobManager（YARN 模式下作为 AM）
框架不同，AM 逻辑不同，但都跑在 YARN 的统一调度之上
```

## Container

Container 是 YARN 的资源抽象单元，封装了「一定量的 CPU 和内存」以及运行环境（依赖、环境变量、工作目录）。所有任务都运行在 Container 里，资源以 Container 为单位申请和分配。Container 是 YARN 资源隔离与调度的最小粒度。

```text
Container 要点：
1. 资源封装 —— 包含 CPU 核数 + 内存大小 + 运行环境
2. 调度单位 —— 资源以 Container 为单位分配和回收
3. 资源隔离 —— NM 用 cgroup 隔离各 Container 的资源
4. 生命周期 —— 由 NM 管理：启动、监控、销毁
```

```yaml
# 提交 Spark 应用时，executor 就是一组 Container
spark-submit \
  --master yarn \
  --deploy-mode cluster \
  --num-executors 4 \
  --executor-memory 4g \      # 每个 executor Container 4G 内存
  --executor-cores 2          # 每个 executor Container 2 核
  my_job.py
```

```text
资源计算示例：
节点 16 核 48G，每 Container 2 核 4G
该节点最多容纳 min(16/2, 48/4) = 8 个 Container
```

## Scheduler

Scheduler 是 ResourceManager 里的调度器组件，负责把资源（Container）按某种策略分配给各应用。它只做「分配」，不监控任务执行、不处理失败（那些由 AM 负责）。YARN 提供三种调度器：FIFO（先进先出，简单但易饿死）、Capacity（容量调度，多队列配额，默认）、Fair（公平调度，按权重共享）。

```text
调度器对比：
1. FIFO —— 单队列先来先服务，简单但后面任务可能饿死
2. Capacity —— 多队列，每队列固定容量配额，队列内 FIFO，默认推荐
3. Fair —— 多队列按权重公平共享，空闲资源可被借用，适合多租户
```

```text
调度器职责边界：
Scheduler 只负责「把资源分配给谁」
不负责：任务执行监控、失败重试、进度跟踪
这些由 ApplicationMaster 负责（调度与应用逻辑解耦）
```

## Capacity

Capacity Scheduler 是 YARN 默认的多队列调度器，把集群资源划分成多个队列，每个队列有「容量配额」（如队列 A 占 60%、B 占 40%），队列内任务按 FIFO 排队。它保证关键业务队列的资源下限，空闲时资源可被其他队列借用（弹性），是多租户隔离的标准方案。

```text
Capacity 调度器要点：
1. 队列配额 —— 每队列有最小容量百分比，保证资源下限
2. 队列内 FIFO —— 同队列任务按提交顺序执行
3. 弹性借用 —— 队列空闲时资源可借给其他队列，忙时回收
4. 层级队列 —— 支持父子队列，进一步细分（如 A 下分 a1、a2）
```

```xml
<!-- capacity-scheduler.xml：队列配置 -->
<configuration>
  <property>
    <name>yarn.scheduler.capacity.root.queues</name>
    <value>prod,dev</value>
  </property>
  <!-- prod 队列占 70%，dev 占 30% -->
  <property>
    <name>yarn.scheduler.capacity.root.prod.capacity</name>
    <value>70</value>
  </property>
  <property>
    <name>yarn.scheduler.capacity.root.dev.capacity</name>
    <value>30</value>
  </property>
  <!-- 单用户最多用队列的 50% -->
  <property>
    <name>yarn.scheduler.capacity.root.prod.user-limit-factor</name>
    <value>0.5</value>
  </property>
</configuration>
```

## Fair

Fair Scheduler 是多队列的公平调度器，按「公平份额」把资源平均（或按权重）分配给各应用/队列，避免某个大任务独占资源饿死小任务。它支持抢占（preemption）——当某个队列占用超过其公平份额且其他队列有需求时，可抢占超额资源。适合多租户、多用户共享的集群。

```text
Fair 调度器要点：
1. 公平份额 —— 资源按权重公平分配，无任务独占
2. 抢占 —— 超额占用可被抢占，保证公平性
3. 动态平衡 —— 新任务加入时资源自动重新分配
4. 多租户友好 —— 适合多团队共享、需要公平的集群
```

```xml
<!-- fair-scheduler.xml：公平调度配置 -->
<configuration>
  <property>
    <name>yarn.scheduler.fair.allocation.file</name>
    <value>/etc/hadoop/fair-scheduler.xml</value>
  </property>
  <property>
    <name>yarn.scheduler.fair.preemption</name>
    <value>true</value>
  </property>
</configuration>
```

```text
Capacity vs Fair 选择：
Capacity —— 需要强资源隔离、保证关键业务资源下限（生产常用）
Fair —— 需要公平共享、多团队混合、追求资源利用率
```

## 应用场景实战

### 场景一：多租户集群的队列规划

```text
需求：一个集群服务 生产任务 + 开发调试，生产不能受影响

Capacity Scheduler 规划：
root
├── prod（70%，生产队列）
│   ├── etl（离线 ETL）
│   └── rt（实时任务）
└── dev（30%，开发队列）
    ├── test
    └── adhoc

配置要点：
1. prod 最小容量 70%，保证生产资源下限
2. dev 空闲时 prod 可借用，但 dev 忙时可回收
3. 单用户 limit-factor 防单个用户占满队列
4. 提交时指定队列：--queue prod.etl
```

```shell
# 指定队列提交任务
spark-submit --master yarn --queue prod.etl my_etl.py
hadoop jar my-job.jar com.example.Job --queue prod.etl
```

### 场景二：排查 YARN 任务资源不足

```shell
# 1. 查看集群资源与队列状态
yarn node -list -all
yarn queue -status prod

# 2. 查看应用状态与资源申请
yarn application -list
yarn application -status <app_id>

# 3. 查看应用日志定位问题
yarn logs -applicationId <app_id>

# 4. 常见问题：资源不足排队、Container 被抢占、内存超限被杀
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产用 Capacity Scheduler，按业务划分队列并设配额
2. ResourceManager 必须配 HA（Active/Standby），消除单点
3. NodeManager 本地目录配多块盘，提升中间数据 IO
4. Container 内存预留合理余量，避免 JVM 堆超限被 NM 杀掉
5. 单用户设 user-limit-factor，防止个别用户占满队列
6. 开启日志聚合（yarn.log-aggregation-enable），方便事后排查
7. 监控队列资源使用率，及时调整配额

### 踩坑记录

```text
坑 1：RM 单点故障导致整个集群调度瘫痪
结论：RM 挂掉，所有任务无法提交/调度，集群不可用。
原因：未配置 ResourceManager HA。
解法：配 RM HA（Active/Standby + ZooKeeper 选举）。

坑 2：Container 内存超限被 NodeManager 杀死
结论：任务运行中途被杀，日志显示 OOM 或 Container killed。
原因：JVM 堆 + 堆外内存超过 Container 分配的内存上限。
解法：Container 内存留足余量（如 executor-memory 1.5 倍于堆），调堆外参数。

坑 3：用 FIFO 调度导致长任务饿死短任务
结论：一个大任务占满资源，后续所有任务排队等待。
原因：FIFO 先来先服务，无抢占和公平机制。
解法：换 Capacity/Fair 调度器，多队列隔离。

坑 4：队列配额没设 user-limit 导致单用户占满队列
结论：某用户提交大量任务占满队列，同队列其他用户饿死。
原因：队列内未限制单用户资源上限。
解法：设 user-limit-factor 限制单用户最大占用比例。

坑 5：本地目录单盘导致 Container 工作目录 IO 瓶颈
结论：任务中间数据读写慢，节点磁盘成瓶颈。
原因：NM 本地目录只配一个盘，IO 无法并行。
解法：local-dirs 配多块盘，分散中间数据 IO。
```
