## 概述

MapReduce 是 Hadoop 的分布式批处理编程模型，把海量数据处理抽象成 Map（映射转换）和 Reduce（归约聚合）两个阶段，框架自动完成数据切分、并行执行、shuffle 传输、排序和容错。程序员只需实现 Mapper/Reducer 逻辑，无需关心分布式细节。虽然 Spark/Flink 已取代其计算地位，但 MapReduce 的「分而治之 + shuffle」思想仍是所有大数据计算框架的基石。
```text
MapReduce 执行流程：
1. 输入分片 —— 按 HDFS 块切分输入，每个分片一个 Map 任务
2. Map —— 逐条处理记录，输出中间 <key, value>
3. Shuffle —— 按 key 分区、排序、传输到 Reducer
4. Reduce —— 对同一 key 的 value 列表聚合，输出结果
5. 输出 —— 结果写回 HDFS
```
```text
核心设计思想：
1. 分而治之 —— 数据分片并行处理，天然可水平扩展
2. 键值对抽象 —— 一切数据抽象成 <key, value>，统一处理
3. 框架兜底 —— 并行、容错、负载均衡全由框架负责
4. 数据局部性 —— Map 任务调度到数据所在节点，减少网络传输
```

## 核心概念

MapReduce 的核心概念围绕一条数据流水线展开：Map 端依次经过 Mapper（处理记录）、Combiner（本地聚合）、Partitioner（分区）、Spill（溢写）、Sort（排序）、Merge（合并），数据跨网络完成 Shuffle 后到达 Reduce 端，再经 Merge 排序交给 Reducer 聚合，Counter 则贯穿全程做观测统计。下面逐个拆解。

### Mapper

Mapper 是 Map 阶段的任务，输入一个分片，逐条处理记录并输出中间键值对。它继承 Mapper 类，实现 map 方法；输入 key 是偏移量、value 是一行/一条记录，输出 key/value 由业务定义。Mapper 之间完全独立并行，输出会被 shuffle 阶段按 key 分组。
```text
Mapper 要点：
1. 并行独立 —— 每个分片一个 Map 任务，互不依赖
2. 键值转换 —— 输入 <offset, line> -> 输出 <业务key, 业务value>
3. 数据局部性 —— 优先在数据所在节点执行，省网络
4. 输出中间态 —— 输出落本地磁盘（不是 HDFS），供 shuffle 使用
```
```java
// WordCount Mapper
public static class WordCountMapper
        extends Mapper<LongWritable, Text, Text, IntWritable> {
    private final static IntWritable one = new IntWritable(1);
    private Text word = new Text();
    @Override
    public void map(LongWritable key, Text value, Context context)
            throws IOException, InterruptedException {
        // value 是一行文本，切分后逐词输出
        for (String w : value.toString().split("\\s+")) {
            if (w.isEmpty()) continue;
            word.set(w);
            context.write(word, one);   // <词, 1>
        }
    }
}
```

### Reducer

Reducer 是 Reduce 阶段的任务，接收 shuffle 之后「同一 key 的 value 列表」，做聚合计算输出最终结果。它继承 Reducer 类，实现 reduce 方法。Reduce 任务数量由 job 配置决定，每个 Reducer 处理一组 key 分区。Reduce 输出写回 HDFS。
```text
Reducer 要点：
1. 按 key 聚合 —— 输入是 <key, Iterable<value>>，同一 key 的值已聚齐
2. 数量可配 —— mapreduce.job.reduces 决定 Reduce 任务数
3. 输出落 HDFS —— 最终结果写 HDFS，是持久化产物
4. 可选 —— 纯 Map 任务（如 ETL 过滤）可不设 Reducer
```
```java
// WordCount Reducer
public static class WordCountReducer
        extends Reducer<Text, IntWritable, Text, IntWritable> {
    private IntWritable result = new IntWritable();
    @Override
    public void reduce(Text key, Iterable<IntWritable> values, Context context)
            throws IOException, InterruptedException {
        int sum = 0;
        for (IntWritable v : values) {
            sum += v.get();            // 累加同一词的所有 1
        }
        result.set(sum);
        context.write(key, result);    // <词, 总数>
    }
}
```

### Combiner

Combiner 是 Map 端的「本地 Reduce」，在 shuffle 之前对 Map 输出做局部聚合，减少需要传输和排序的数据量。它本质是一个 Reducer，但运行在 Map 端、只处理本 Map 任务的局部数据。Combiner 必须满足「结合律/交换律」才能保证结果正确（如求和、计数可以，求平均不可以直接做）。
```text
Combiner 要点：
1. 本地聚合 —— 在 Map 端先聚合，减少 shuffle 数据量
2. 复用 Reducer —— 常用 Reducer 类作为 Combiner（求和/计数场景）
3. 可结合性 —— 必须满足 a op b 可结合交换，否则结果错
4. 框架可选调用 —— 框架可能调用 0 次或多次，不能依赖其副作用
```
```java
// 设置 Combiner（复用 Reducer 做本地求和）
job.setCombinerClass(WordCountReducer.class);
// 反面例子：求平均不能直接用 Combiner
// 直接对平均值做 Combiner 会得到错误结果（平均的平均 != 总平均）
```
```text
Combiner 正确性条件：
1. 运算满足结合律：(a op b) op c = a op (b op c)
2. 运算满足交换律：a op b = b op a
3. 求和/计数/最大值/最小值 —— 满足，可用
4. 平均值/中位数 —— 不满足，需改写（先 sum + count 再除）
```

### Partitioner

Partitioner 决定 Map 输出的每个键值对发往哪个 Reducer（分区），默认按 key 的 hash 对 Reducer 数量取模。自定义 Partitioner 可以控制数据分布，用于解决数据倾斜、保证特定 key 落到特定 Reducer。分区是 shuffle 的第一步。
```text
Partitioner 要点：
1. 分区函数 —— 输入 key，输出分区号（0 ~ numReducers-1）
2. 默认实现 —— HashPartitioner：(key.hashCode() & MAX) % numReducers
3. 数据倾斜 —— 默认 hash 可能让热点 key 集中到某 Reducer，需自定义
4. 全局排序 —— 自定义范围分区可实现全局有序输出
```
```java
// 自定义 Partitioner：按用户 ID 取模分区
public static class UserPartitioner extends Partitioner<Text, IntWritable> {
    @Override
    public int getPartition(Text key, IntWritable value, int numPartitions) {
        int userId = Integer.parseInt(key.toString());
        return userId % numPartitions;   // 同用户落到同一 Reducer
    }
}
// 设置 Partitioner
job.setPartitionerClass(UserPartitioner.class);
```

### Shuffle

Shuffle 是 Map 输出到 Reduce 输入之间的数据重分布过程，是 MapReduce 性能的关键瓶颈。它包含：Map 端分区、环形缓冲区 spill 到磁盘、合并排序，Reduce 端拉取、归并。Shuffle 涉及大量磁盘 IO 和网络传输，是 MapReduce 最慢、最值得优化的环节。
```text
Shuffle 全流程：
Map 端：
1. Map 输出写入环形内存缓冲区（默认 100MB）
2. 缓冲达到阈值（80%）触发 spill，分区 + 排序后溢写磁盘
3. 多次 spill 后合并（merge）成一个有序文件
Reduce 端：
4. Reduce 通过 HTTP 拉取属于自己分区的数据（copy）
5. 内存不足时溢写，最终归并（merge）排序
6. 分组后交给 reduce 方法处理
```
```text
Shuffle 优化方向：
1. 调大缓冲区（mapreduce.task.io.sort.mb）减少 spill 次数
2. 用 Combiner 减少传输量
3. 调大并行复制线程，加速 copy 阶段
4. 压缩 Map 中间输出，省网络
```

### Sort

Sort（排序）是 MapReduce 的核心机制：Map 输出在 spill 时按 key 排序，Reduce 端归并排序后，同一 key 的数据连续排列，保证 reduce 方法收到的是有序、按 key 分组的数据。排序是框架保证的，也是 shuffle 代价的主要来源。
```text
Sort 要点：
1. Map 端排序 —— spill 前对缓冲区数据按 key 排序
2. Reduce 端归并 —— 对拉取到的多个有序流做归并排序
3. 分组前提 —— 排序后同 key 连续，才能正确分组
4. 二次排序 —— 自定义 key 的 compareTo 实现组内按 value 排序
```
```text
排序发生在哪里：
1. Map 输出 spill —— 按 key 排序写磁盘
2. Map 端 merge —— 归并多个 spill 文件
3. Reduce 端 merge —— 归并各 Map 传来的有序数据
排序贯穿整个 shuffle，是 MapReduce 最大的开销之一
```

### Spill

Spill（溢写）是 Map 端内存缓冲区写满后，把数据「溢写」到本地磁盘的过程。溢出前会先按 key 排序、按分区划分，写成一个有序的分区文件。Spill 次数越多，磁盘 IO 越多、后续 merge 越重，因此调大缓冲区减少 spill 是重要优化。
```text
Spill 要点：
1. 触发 —— 环形缓冲区达到阈值（默认 80%）开始 spill
2. 过程 —— 分区 + 排序 + 溢写磁盘（可配压缩）
3. 异步 —— spill 与 Map 继续处理并行，缓冲是环形设计
4. 多次 spill —— 大分片会产生多个 spill 文件，需 merge
```
```text
相关配置：
mapreduce.task.io.sort.mb  —— 环形缓冲区大小（默认 100MB）
mapreduce.map.sort.spill.percent —— spill 阈值（默认 0.8）
mapreduce.map.output.compress —— 是否压缩中间输出
```

### Merge

Merge（合并）是把多个 spill 文件（或 Reduce 端拉取的多个数据流）归并成一个有序文件的过程。Map 端在 spill 全部完成后 merge 成一个大文件供 Reduce 拉取；Reduce 端把各 Map 传来的数据 merge 成有序流再分组。Merge 是多路归并排序，是 shuffle 正确性的保障。
```text
Merge 要点：
1. Map 端 merge —— 合并多个 spill 文件为一个有序文件
2. Reduce 端 merge —— 合并多个 Map 传来的有序数据流
3. 多路归并 —— 同时归并多个有序流，保持全局有序
4. 内存磁盘混合 —— 数据量大时内存 + 磁盘多轮归并
```
```text
Map 端 merge 时机：
1. spill 文件数达到阈值（默认 3）时后台归并
2. Map 全部输出完成后，最终 merge 成一个文件
Reduce 端 merge：
1. copy 阶段边拉取边归并
2. 内存不足溢写磁盘，最后统一归并
```

### Counter

Counter 是 MapReduce 的计数器机制，用于统计任务的运行信息（如处理了多少条记录、多少脏数据），由框架自动聚合所有任务的值，任务结束后汇总展示。它是观察任务运行状况、做数据质量校验的轻量手段，比打印日志更高效、可汇总。
```text
Counter 要点：
1. 框架内置 —— 如 Map input records、Reduce output records
2. 自定义 —— context.getCounter(组, 名).increment(n) 累加
3. 自动聚合 —— 框架汇总所有 Map/Reduce 任务的计数
4. 用途 —— 数据质量校验、进度观察、调试统计
```
```java
// 自定义 Counter 统计脏数据
public static class CleanMapper
        extends Mapper<LongWritable, Text, Text, IntWritable> {
    @Override
    public void map(LongWritable key, Text value, Context context)
            throws IOException, InterruptedException {
        String line = value.toString();
        if (line == null || line.isEmpty() || !line.contains(",")) {
            // 脏数据计数
            context.getCounter("DATA_QUALITY", "INVALID_RECORDS").increment(1);
            return;
        }
        // 正常处理...
        context.getCounter("DATA_QUALITY", "VALID_RECORDS").increment(1);
    }
}
```

## 工作原理

MapReduce 一次作业的执行是「分片 → Map → Shuffle → Reduce → 输出」的五阶段流水线，全程由框架调度、监控与容错：

1. **输入分片**：JobClient 根据 InputFormat 把输入文件按 HDFS 块（默认 128MB）切成多个 InputSplit，每个分片启动一个 Map 任务。分片大小决定 Map 任务数，也决定并行度。
2. **Map 阶段**：每个 Map 任务读自己分片的数据，逐条调 map()，输出中间键值对到环形缓冲区。ResourceManager 会优先把 Map 任务调度到数据所在节点（数据局部性），减少跨机架网络传输。
3. **Shuffle 阶段**：Map 端 spill/排序/merge 后，Reduce 端通过 HTTP 拉取属于自己的分区数据，归并排序后按 key 分组。这是性能瓶颈所在，涉及大量磁盘 IO 和网络 IO。
4. **Reduce 阶段**：每个 Reducer 对自己负责的一组 key 逐条调 reduce()，输出最终结果写回 HDFS。
5. **容错机制**：任务失败自动重试（默认 4 次），Map 任务因输出在本地、重试成本低；慢任务由「推测执行」（speculative execution）在别的节点启动副本，先完成的算数，避免单个慢任务拖死整批作业。
```text
MapReduce 数据流动全景：
输入 HDFS 块 -> InputSplit -> Map -> 环形缓冲区 -> (Combiner) -> Partitioner
  -> spill 排序 -> merge -> HTTP copy -> merge 排序 -> 按 key 分组 -> Reduce -> 输出 HDFS
```
```text
框架兜底的三个机制：
1. 数据局部性 —— Map 任务移动到数据，减少网络传输
2. 推测执行 —— 慢任务在别处启动备份，先完成者胜出
3. 失败重试 —— 任务失败自动重跑，Map 输出本地可重算
```

## 配置文件解析

MapReduce 的运行参数主要在 `mapred-site.xml` 里，可被 `-D` 参数和代码里 `conf.set()` 覆盖（优先级：代码 > -D 命令行 > 配置文件 > 默认值）。
```xml
<!-- mapred-site.xml：MapReduce 关键配置 -->
<configuration>
  <!-- 默认 Reduce 任务数，生产按数据量设 -->
  <property>
    <name>mapreduce.job.reduces</name>
    <value>8</value>
  </property>
  <!-- 环形缓冲区大小（MB），调大减少 spill -->
  <property>
    <name>mapreduce.task.io.sort.mb</name>
    <value>200</value>
  </property>
  <!-- spill 阈值，缓冲区用到 80% 触发溢写 -->
  <property>
    <name>mapreduce.map.sort.spill.percent</name>
    <value>0.80</value>
  </property>
  <!-- 压缩 Map 中间输出，省 shuffle 网络 -->
  <property>
    <name>mapreduce.map.output.compress</name>
    <value>true</value>
  </property>
  <!-- 中间输出压缩算法 -->
  <property>
    <name>mapreduce.map.output.compress.codec</name>
    <value>org.apache.hadoop.io.compress.SnappyCodec</value>
  </property>
  <!-- 启用推测执行（默认开启，对慢任务做备份） -->
  <property>
    <name>mapreduce.map.speculative</name>
    <value>true</value>
  </property>
</configuration>
```

## 应用场景实战

### 场景一：完整 WordCount 作业
```java
// 完整可运行的 WordCount
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.IntWritable;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.Reducer;
import org.apache.hadoop.mapreduce.lib.input.FileInputFormat;
import org.apache.hadoop.mapreduce.lib.output.FileOutputFormat;
public class WordCount {
    public static class TokenizerMapper
            extends Mapper<LongWritable, Text, Text, IntWritable> {
        private final static IntWritable one = new IntWritable(1);
        private Text word = new Text();
        public void map(LongWritable key, Text value, Context context)
                throws java.io.IOException, InterruptedException {
            for (String w : value.toString().split("\\s+")) {
                if (w.isEmpty()) continue;
                word.set(w);
                context.write(word, one);
            }
        }
    }
    public static class IntSumReducer
            extends Reducer<Text, IntWritable, Text, IntWritable> {
        private IntWritable result = new IntWritable();
        public void reduce(Text key, Iterable<IntWritable> values, Context context)
                throws java.io.IOException, InterruptedException {
            int sum = 0;
            for (IntWritable v : values) sum += v.get();
            result.set(sum);
            context.write(key, result);
        }
    }
    public static void main(String[] args) throws Exception {
        Configuration conf = new Configuration();
        Job job = Job.getInstance(conf, "word count");
        job.setJarByClass(WordCount.class);
        job.setMapperClass(TokenizerMapper.class);
        job.setCombinerClass(IntSumReducer.class);   // 本地聚合
        job.setReducerClass(IntSumReducer.class);
        job.setOutputKeyClass(Text.class);
        job.setOutputValueClass(IntWritable.class);
        FileInputFormat.addInputPath(job, new Path(args[0]));
        FileOutputFormat.setOutputPath(job, new Path(args[1]));
        System.exit(job.waitForCompletion(true) ? 0 : 1);
    }
}
```

```shell
# 提交作业
hadoop jar order-agg.jar com.example.OrderAggregator \
  -Dmapreduce.job.reduces=8 \

  /data/raw/orders /data/dwd/order_agg
```
```text
作业设计：
1. Mapper —— 解析订单行，输出 <user_id, amount>
2. Combiner —— 本地累加每个用户的金额（减少 shuffle 量）
3. Partitioner —— 按 user_id 取模分区，同用户聚合到同 Reducer
4. Reducer —— 对同一用户的金额列表求和，输出总消费
5. Counter —— 统计有效/无效记录，校验数据质量
```

### 场景三：Top N 热门商品统计

Top N 是典型的多阶段 MapReduce 场景。直接在 Mapper 输出全量 <商品, 次数> 再让单 Reducer 排序，shuffle 数据量太大；正确做法是「Map 端局部 TopN + 单 Reducer 全局 TopN」，把每个 Map 任务只保留本地前 N 条再传出去，shuffle 量从「全量」降到「Map 数 × N」。
```java
// TopN：每个 Map 先取本地前 N，单 Reducer 再取全局前 N
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.IntWritable;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.Reducer;
import org.apache.hadoop.mapreduce.lib.input.FileInputFormat;
import org.apache.hadoop.mapreduce.lib.output.FileOutputFormat;
import java.io.IOException;
import java.util.Map;
import java.util.TreeMap;
public class TopNProducts {
    public static class TopNMapper
            extends Mapper<LongWritable, Text, Text, IntWritable> {
        private TreeMap<Integer, String> localTop = new TreeMap<>();
        private static final int N = 10;
        public void map(LongWritable key, Text value, Context context) {
            // 输入：商品ID,点击次数
            String[] parts = value.toString().split(",");
            if (parts.length < 2) return;
            int cnt = Integer.parseInt(parts[1].trim());
            localTop.put(cnt, parts[0].trim());
            if (localTop.size() > N) localTop.remove(localTop.firstKey());
        }
        @Override
        protected void cleanup(Context context)
                throws IOException, InterruptedException {
            for (Map.Entry<Integer, String> e : localTop.entrySet()) {
                context.write(new Text(e.getValue()), new IntWritable(e.getKey()));
            }
        }
    }
    public static class TopNReducer
            extends Reducer<Text, IntWritable, Text, IntWritable> {
        private TreeMap<Integer, String> globalTop = new TreeMap<>();
        private static final int N = 10;
        public void reduce(Text key, Iterable<IntWritable> values, Context context) {
            for (IntWritable v : values) {
                globalTop.put(v.get(), key.toString());
                if (globalTop.size() > N) globalTop.remove(globalTop.firstKey());
            }
        }
        @Override
        protected void cleanup(Context context)
                throws IOException, InterruptedException {
            for (Map.Entry<Integer, String> e : globalTop.descendingMap().entrySet()) {
                context.write(new Text(e.getValue()), new IntWritable(e.getKey()));
            }
        }
    }
    public static void main(String[] args) throws Exception {
        Configuration conf = new Configuration();
        Job job = Job.getInstance(conf, "top n products");
        job.setJarByClass(TopNProducts.class);
        job.setMapperClass(TopNMapper.class);
        job.setReducerClass(TopNReducer.class);
        job.setOutputKeyClass(Text.class);
        job.setOutputValueClass(IntWritable.class);
        job.setNumReduceTasks(1);   // 全局 TopN 需要单 Reducer
        FileInputFormat.addInputPath(job, new Path(args[0]));
        FileOutputFormat.setOutputPath(job, new Path(args[1]));
        System.exit(job.waitForCompletion(true) ? 0 : 1);
    }
}
```

## 性能与调优

MapReduce 的性能瓶颈几乎都在 Shuffle 阶段，调优核心是「减少 spill 次数、减少 shuffle 数据量、减少数据倾斜」。
```text
Shuffle 调优参数：
1. mapreduce.task.io.sort.mb —— 环形缓冲区，默认 100MB，调大到 200~300MB 减少 spill
2. mapreduce.map.sort.spill.percent —— spill 阈值，默认 0.8，可提到 0.9
3. mapreduce.map.output.compress —— 开启中间输出压缩，省网络（用 Snappy/LZ4，快）
4. mapreduce.reduce.shuffle.parallelcopies —— 并行 copy 线程，默认 5，可提到 10~20
5. mapreduce.reduce.shuffle.input.buffer.percent —— Reduce 端 shuffle 内存占比
```
```text
任务数量调优：
1. Reducer 数量 —— 经验值：每个 Reducer 处理 1GB 左右数据，太少单点慢、太多小文件多
2. Map 任务数 —— 由分片决定，小文件多会导致 Map 爆炸，需先合并
3. 纯 Map 任务 —— ETL 过滤类场景 setNumReduceTasks(0)，跳过 shuffle 直接落盘
4. Combiner —— 求和/计数/最大最小必加，shuffle 数据量可降一个数量级
```
```text
数据倾斜治理：
1. 定位 —— 看作业各 Reducer 处理记录数/耗时差异，或 Counter 分分区统计
2. 打散热点 key —— 热点 key 加随机后缀，聚合时再去后缀二次聚合
3. 自定义 Partitioner —— 按业务字段均匀分区，替代默认 hash
4. 倾斜 key 单独处理 —— 把热点 key 单独一个作业，非热点走正常流程
```

## 安全与权限

MapReduce 作业跑在 YARN + HDFS 之上，安全由底层共同保证：
```text
安全要点：
1. HDFS 权限 —— 作业以提交用户身份读写 HDFS，输入/输出路径需有对应权限，输出目录不能已存在
2. Kerberos 认证 —— 安全集群中提交作业需先 kinit 获取 TGT，否则提交被拒
3. 队列权限 —— YARN 队列可配 ACL，限制哪些用户/组能提交到该队列（如 prod 队列只允许数据组）
4. Delegation Token —— 长任务由 AM 持有 token 访问 HDFS，避免反复认证
5. 审计日志 —— 作业提交、队列、输入输出路径都会进审计，用于追溯谁跑过什么
6. 中间数据 —— Map 中间输出在本地磁盘，注意本地目录权限，避免跨用户窥探
```
```shell
# 安全集群中提交作业前先认证
kinit -kt /etc/security/keytabs/data.keytab data_user
hadoop jar job.jar com.example.Job /in /out
```

## 故障排查
```text
常见故障与排查方向：
故障 1：作业卡在 Map 0% 或进度长期不动
排查：yarn logs -applicationId <id> 看 Map 任务日志；查输入路径是否存在、格式是否匹配 InputFormat；看是否数据局部性差、网络拥塞。
故障 2：单个 Reducer 极慢，其他已完成
排查：数据倾斜——看各 Reducer 的 input records 差异，热点 key 单独打散；或该 Reducer 所在节点磁盘/网络异常。
故障 3：任务反复失败重试后整体失败
排查：yarn logs 看异常栈；常见是 OOM（调大 map/reduce 内存）、类缺失（jar 没打依赖）、输出目录已存在（先删）。
故障 4：Map 任务 OOM
排查：mapreduce.map.memory.mb 设太小；或 Mapper 里缓存了大对象/列表，改为流式处理或 spill 到磁盘。
故障 5：作业慢且大量推测执行任务
排查：看是否数据倾斜或慢节点；倾斜要治理数据，慢节点要找 NM 健康状态，可对纯计算任务关闭推测执行。
```
```shell
# 排查标准流程
yarn application -status <app_id>        # 看状态、进度、诊断信息
yarn logs -applicationId <app_id>        # 拉全部日志定位异常栈
mapred job -status <job_id>              # 看计数器与任务明细
hdfs dfs -ls <输出路径>                   # 输出目录已存在会直接报错
```

## 常见问题
```text
Q1: MapReduce 为什么慢？现在还有必要用吗？
A: 慢在 shuffle 大量磁盘 IO + 每阶段落盘、不能复用中间结果。批处理新场景用 Spark/Flink 更快，但 MapReduce 的编程思想（分而治之、key/value、shuffle）是所有大数据框架的根基，理解它才能理解 Spark 的 groupByKey/reduceByKey。
Q2: Combiner 什么情况下不能用？
A: 运算不满足结合律/交换律时不能用，如求平均、求中位数。求平均要改成 Combiner 输出 (sum, count)，Reduce 阶段再 sum/count。
Q3: 数据倾斜怎么定位和解决？
A: 看作业各 Reducer 的 input records 与耗时差异定位热点分区；解决用「热点 key 加随机后缀」「自定义 Partitioner」「倾斜 key 单独处理」。
Q4: 小文件太多会怎样？怎么处理？
A: 每个小文件一个分片一个 Map 任务，任务数爆炸、调度开销巨大。处理：上传前合并小文件，或用 CombineFileInputFormat 把多个小文件合成一个分片。
Q5: 为什么输出目录不能提前存在？
A: FileOutputFormat 为了防误覆盖，要求输出目录不存在。提交前先 hdfs dfs -rm -r 删除旧输出目录。
Q6: 二次排序（Secondary Sort）怎么实现？
A: 自定义复合 key（主 key + 次 key），实现 WritableComparable 的 compareTo 先比主 key 再比次 key，再配自定义 GroupingComparator 让 reduce 只按主 key 分组，这样组内 value 已按次 key 有序。
Q7: 推测执行是什么？什么时候该关？
A: 框架对慢任务在别的节点启动备份任务、先完成者胜出，避免慢节点拖死整批。对幂等性差（有外部副作用）的任务要关闭，否则重复执行可能出问题。
```

## 面试题
```text
1. 简述 MapReduce 的执行流程，Shuffle 发生在哪？
   答：输入分片 → Map → Shuffle（Map 端 spill/排序/merge，跨网络传 Reduce 端，Reduce 端 merge/排序/分组）→ Reduce → 输出。Shuffle 是 Map 输出到 Reduce 输入的中间环节，是性能瓶颈。
2. Combiner 和 Reducer 有什么区别？
   答：Combiner 是 Map 端的本地 Reducer，只处理本 Map 任务局部数据、减少 shuffle 量，框架可能调用 0 次或多次；Reducer 处理全局同 key 数据、保证最终结果。Combiner 必须满足结合律交换律。
3. MapReduce 怎么解决数据倾斜？
   答：热点 key 加随机后缀打散后二次聚合、自定义 Partitioner 按业务均匀分区、倾斜 key 单独作业处理。
4. MapReduce 和 Spark 的核心区别？
   答：MapReduce 每阶段落盘、中间结果不复用、无 DAG 优化，延迟高；Spark 基于内存 + DAG 调度、中间结果缓存复用，迭代计算快得多。但两者 shuffle 思想一致。
5. 为什么 MapReduce 不适合迭代计算？
   答：每次迭代都要重新读写 HDFS、shuffle 落盘，磁盘 IO 开销大，不像 Spark 能把中间 RDD 缓存在内存复用。
6. 小文件过多对 MapReduce 有什么影响？怎么解决？
   答：每个小文件一个 Map 任务，任务数爆炸、调度开销大。解决：合并小文件或用 CombineFileInputFormat 合并分片。
7. 推测执行的原理和适用场景？
   答：框架检测到慢任务后在空闲节点启动备份、先完成者胜出，解决慢节点拖累。适用于计算密集、幂等的任务；有外部副作用的任务要关闭。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 能用 Combiner 就用（求和/计数/最大最小），大幅减少 shuffle 数据量
2. 调大环形缓冲区（io.sort.mb）减少 spill 次数
3. Map 中间输出开启压缩，省网络传输
4. 数据倾斜时自定义 Partitioner 打散热点 key
5. Reducer 数量按数据量合理设置（太少单点慢，太多小文件多）
6. 用 Counter 做数据质量校验，别只靠日志
7. 避免在 Mapper/Reducer 里做耗时操作（网络请求、大对象），保持无状态

### 踩坑记录
```text
坑 1：求平均直接套 Combiner
结论：最终结果错误，平均的平均不等于总平均。
原因：Combiner 在 Map 端做局部平均，reduce 再平均，破坏正确性。
解法：Combiner 输出 (sum, count)，reduce 阶段 sum 汇总再除，或不用 Combiner。
坑 2：热点 key 导致数据倾斜
结论：某 Reducer 处理量是其他数倍，作业整体被最慢任务拖死。
原因：默认 hash 分区让热点 key（如 null、热门值）集中到一个 Reducer。
解法：自定义 Partitioner 打散热点 key，或热点 key 加随机后缀。
坑 3：小文件过多导致 Map 任务爆炸
结论：成千上万个 Map 任务，调度开销巨大，作业极慢。
原因：每个小文件一个分片一个 Map 任务，任务数远超需要。
解法：合并小文件，或用 CombineFileInputFormat 合并小文件分片。
坑 4：spill 频繁导致磁盘 IO 打满
结论：Map 阶段磁盘 IO 成瓶颈，作业变慢。
原因：缓冲区太小，spill 频繁，多次溢写磁盘。
解法：调大 io.sort.mb，开启中间输出压缩，减少 spill 次数。
坑 5：Reducer 数量设 0 但业务需要聚合
结论：结果未聚合，直接输出 Map 中间结果，数据错误。
原因：setNumReduceTasks(0) 导致跳过 Reduce 阶段。
解法：纯过滤/转换任务才设 0，需要聚合必须设 Reducer。
```
