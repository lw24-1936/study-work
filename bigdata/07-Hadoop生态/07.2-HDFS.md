## 概述

HDFS（Hadoop Distributed File System）是 Hadoop 生态的分布式文件系统，专为大文件顺序读写、一次写入多次读取（write-once-read-many）设计。它把大文件切块分布到集群多台机器上，靠副本保证容错，靠元数据与数据分离的架构支撑海量存储。HDFS 是数据湖、离线数仓底层存储的基石，也是 Iceberg/Hudi/Delta 等表格式默认的存储底座。

```text
HDFS 的核心设计取舍：
1. 大文件优先 —— 块默认 128MB，为顺序大文件吞吐优化，不适合海量小文件
2. 一次写多次读 —— 不支持随机写和并发写，追加为主
3. 元数据分离 —— 元数据在 NameNode 内存，数据在 DataNode 磁盘
4. 副本容错 —— 每块默认 3 副本，机架感知放置，坏盘自动恢复
5. 就近读取 —— 客户端优先读本地/同机架的副本，省网络
```

## NameNode 与 DataNode

HDFS 采用主从架构：NameNode 是主节点，管理文件系统的命名空间（目录树）和块的映射关系（文件 -> 块 -> DataNode 位置），全部元数据常驻内存以支撑高吞吐；DataNode 是从节点，负责实际存储块数据，定期向 NameNode 汇报心跳（默认 3 秒）和块报告（Block Report）。

```text
NameNode / DataNode 职责划分：
1. NameNode —— 目录树、块映射、副本管理，元数据在内存 + fsimage/edits 持久化
2. DataNode —— 存块数据、响应读写请求、心跳汇报、执行复制/删除指令
3. 客户端 —— 先从 NameNode 拿块位置，再直接和 DataNode 传数据（不经过 NameNode）
4. SecondaryNameNode —— 定期合并 edits 到 fsimage，减轻 NameNode 恢复压力（非热备）
```

```xml
<!-- hdfs-site.xml 关键配置 -->
<configuration>
  <!-- 副本数，生产默认 3 -->
  <property>
    <name>dfs.replication</name>
    <value>3</value>
  </property>
  <!-- 块大小，单位字节，默认 128MB -->
  <property>
    <name>dfs.blocksize</name>
    <value>134217728</value>
  </property>
  <!-- NameNode 元数据目录 -->
  <property>
    <name>dfs.namenode.name.dir</name>
    <value>/hadoop/hdfs/namenode</value>
  </property>
  <!-- DataNode 数据目录（多个盘逗号分隔） -->
  <property>
    <name>dfs.datanode.data.dir</name>
    <value>/data/disk1,/data/disk2</value>
  </property>
</configuration>
```

## Block 与副本机制

文件被切分成固定大小的块（Block，默认 128MB，Hadoop 1.x 是 64MB），每块独立存储、独立复制。块大小影响寻址开销与任务并行度：块太小元数据膨胀，块太大单个任务处理时间过长。副本机制是 HDFS 容错的核心——每块默认 3 副本，分布在至少两个机架上，一个副本坏掉后 NameNode 会调度 DataNode 自动补副本。

```text
块与副本要点：
1. 块是抽象概念 —— 一个 200MB 文件存成 128MB + 72MB 两个块，不占满磁盘空间
2. 副本放置 —— 第一副本本地/同机架，第二副本同机架不同节点，第三副本跨机架
3. 块大小权衡 —— 大块减少寻址和元数据，但降低并行度和故障恢复粒度
4. 副本因子 —— 关键数据可调高，临时/可再生数据调低（如 2 副本）
```

```shell
# 查看块与副本信息
hdfs fsck /user/hive/warehouse -files -blocks -locations

# 手动设置副本数
hdfs dfs -setrep -w 3 /user/hive/warehouse/db.db/orders

# 查看单个文件块信息
hdfs fsck /path/to/file -files -blocks
```

## Rack Awareness 机架感知

机架感知是 HDFS 副本放置和 MapReduce 任务调度的前提：集群要知道每台机器属于哪个机架，才能把副本分散到不同机架、把计算调度到数据所在机架。副本放置策略是「本地 -> 同机架 -> 跨机架」，既保证容错（机架断电不丢数据）又保证局部性（读本地副本）。

```text
机架感知要点：
1. 副本跨机架 —— 至少一个副本放不同机架，防止整机架故障丢数据
2. 数据局部性 —— 计算任务优先调度到数据所在节点/机架，减少跨机架流量
3. 自定义拓扑 —— 通过 topology.py 脚本把 IP 映射到机架 ID（/rack1、/rack2）
4. 跨机架带宽珍贵 —— 放置策略刻意让多数副本在同机架、少数跨机架，平衡容错与带宽
```

```python
# 自定义机架拓扑脚本（core-site.xml 里 net.topology.script.file.name 指向它）
import sys

rack_map = {
    "192.168.1.10": "/rack1",
    "192.168.1.11": "/rack1",
    "192.168.1.20": "/rack2",
    "192.168.1.21": "/rack2",
}

for line in sys.stdin:
    ip = line.strip()
    print(rack_map.get(ip, "/default-rack"))
```

## HA 高可用

HDFS 1.x 的 NameNode 是单点故障——它挂了整个集群不可用。HA 引入两个 NameNode（Active + Standby），通过共享的 JournalNode 集群同步元数据（Active 写 edits 到 JournalNode，Standby 读 edits 保持同步），ZooKeeper 负责故障检测和自动切换（ZKFC 监控 NameNode 健康，失败时触发 failover）。

```text
HA 架构要点：
1. Active/Standby —— 同一时刻只有一个 Active 对外服务
2. JournalNode —— 奇数个（如 3）组成的共享编辑日志，Quorum 写入保证一致性
3. ZKFC —— ZooKeeper Failover Controller，监控 NameNode 并触发自动切换
4. 自动 failover —— Active 崩溃后 Standby 秒级接管，客户端无感（配合 RPC 重试）
5. 脑裂防护 —— Fencing 机制（如 SSH 强制 kill、共享存储锁）防止两个 NameNode 同时写
```

```xml
<!-- hdfs-site.xml HA 关键配置 -->
<configuration>
  <property>
    <name>dfs.nameservices</name>
    <value>mycluster</value>
  </property>
  <property>
    <name>dfs.ha.namenodes.mycluster</name>
    <value>nn1,nn2</value>
  </property>
  <property>
    <name>dfs.namenode.rpc-address.mycluster.nn1</name>
    <value>nn1.example.com:8020</value>
  </property>
  <property>
    <name>dfs.namenode.rpc-address.mycluster.nn2</name>
    <value>nn2.example.com:8020</value>
  </property>
  <!-- JournalNode 地址列表 -->
  <property>
    <name>dfs.namenode.shared.edits.dir</name>
    <value>qjournal://jn1:8485;jn2:8485;jn3:8485/mycluster</value>
  </property>
</configuration>
```

## Federation 联邦

Federation 解决单 NameNode 的扩展瓶颈（内存、命名空间、元数据 QPS）。它用多个 NameNode 各管一部分命名空间（Namespace），共享所有 DataNode 的存储池——每个 NameNode 独立维护自己的目录树和块池（Block Pool），互不干扰。客户端通过 ViewFS 或挂载表把不同路径路由到不同 NameNode。

```text
Federation 要点：
1. 多 NameNode —— 每个管一个命名空间，横向扩展元数据容量和吞吐
2. 共享 DataNode —— 所有 DataNode 同时为所有 NameNode 的块池服务
3. 块池隔离 —— 各 NameNode 的块独立编号，互不冲突
4. 与 HA 正交 —— 每个联邦命名空间可再配 HA，两者叠加使用
5. 适用场景 —— 单集群元数据超 10 亿文件、NameNode RPC 成为瓶颈时
```

## Snapshot 快照

快照是某个目录在某一时刻的只读镜像，基于 Copy-on-Write（写时复制）实现——快照本身不复制数据，只在文件被修改时才记录差异，因此创建快照是 O(1) 的瞬时操作。快照用于数据备份、误删恢复、回滚和做 Spark/Hive 的数据版本管理。

```text
快照要点：
1. 瞬时创建 —— 只记录元数据指针，不复制数据块
2. 写时复制 —— 原文件变更时保留旧块，快照可还原到创建时刻
3. 允许快照的目录 —— 需先对该目录执行 allowSnapshot 开启
4. 恢复 —— 可整体回滚目录，也可单独复制快照里的文件
```

```shell
# 开启目录快照
hdfs dfsadmin -allowSnapshot /user/hive/warehouse/db.db

# 创建快照
hdfs dfs -createSnapshot /user/hive/warehouse/db.db snap_20240814

# 查看快照
hdfs dfs -ls /user/hive/warehouse/db.db/.snapshot/snap_20240814

# 从快照恢复误删文件
hdfs dfs -cp /user/hive/warehouse/db.db/.snapshot/snap_20240814/orders /user/hive/warehouse/db.db/orders
```

## 应用场景实战

### 场景一：小文件合并上传

```shell
# 海量小文件会压垮 NameNode 内存，先本地合并再上传
# 1. 本地用 tar 或 SequenceFile 合并小文件
tar -cf batch_20240814.tar /data/logs/*.log

# 2. 上传合并后的文件
hdfs dfs -put batch_20240814.tar /data/raw/logs/

# 3. 或用 Hadoop Archive（HAR）把小文件打成归档
hadoop archive -archiveName logs.har -p /data/raw/logs /data/raw/archive

# 4. 查看 NameNode 元数据占用，评估小文件问题
hdfs dfsadmin -report | grep -A 5 "Name:"
```

### 场景二：副本不足检测与修复

```shell
# 1. 全量健康检查，找出副本不足或损坏的块
hdfs fsck / -files -blocks -locations -racks 2>&1 | grep -E "MISSING|UNDER REPLICATED|CORRUPT"

# 2. 查看当前副本状态统计
hdfs fsck / -blocks 2>&1 | tail -20

# 3. 对副本不足的目录强制触发复制
hdfs dfs -setrep -w 3 /data/raw/

# 4. 进入安全模式排查时，先离开安全模式
hdfs dfsadmin -safemode get
hdfs dfsadmin -safemode leave
```

## 最佳实践与踩坑记录

### 最佳实践

1. 块大小保持默认 128MB，除非明确是超大数据集可调到 256MB
2. 生产副本数 3，机架感知配置正确，确保副本跨机架
3. NameNode 元数据目录配多个盘做 RAID 或直接多目录冗余
4. 定期做 fsck 检查块健康和副本状况
5. 海量小文件先合并再入 HDFS，或改用 HBase/对象存储
6. 重要目录开快照，配合定时快照做数据备份
7. 升级/高危操作前先进入安全模式（safemode）保护元数据

### 踩坑记录

```text
坑 1：海量小文件撑爆 NameNode
结论：NameNode 内存耗尽，集群变慢甚至不可用。
原因：每个文件/块在 NameNode 内存约占 150-200 字节元数据，百万小文件就吃上百 MB。
解法：本地合并、HAR 归档、改用 SequenceFile/Parquet，或迁移到对象存储 + 表格式。

坑 2：副本数设置过高导致存储成本翻倍
结论：存储成本暴涨，写入吞吐下降。
原因：副本数 4/5 时每份数据存多份，且写入要同步多副本。
解法：默认 3 副本，可再生数据（日志中间态）可降到 2 甚至用纠删码（EC）。

坑 3：忽略机架感知导致副本全在同一机架
结论：机架断电时数据全丢。
原因：未配置 topology 脚本，HDFS 把不同机架机器当同机架放置副本。
解法：配置 net.topology.script.file.name，验证副本确实跨机架。

坑 4：误删文件后才发现没快照
结论：数据无法恢复，只能从备份或重新生成。
原因：未开启目录快照，删除操作直接进 edits 不可逆。
解法：重要目录 allowSnapshot + 定时 createSnapshot，删除用 trash 机制（延迟删除）。

坑 5：写副本超时误判为 DataNode 故障
结论：NameNode 频繁把健康节点标记为死节点，触发无谓的副本复制。
原因：网络抖动或磁盘慢导致 DataNode 心跳超时，NameNode 误判。
解法：调大 dfs.namenode.heartbeat.recheck-interval 和超时阈值，排查网络/磁盘。
```
