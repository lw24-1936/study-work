## 概述

HDFS（Hadoop Distributed File System）是 Hadoop 生态的分布式文件系统，专为大文件顺序读写、一次写入多次读取（write-once-read-many）设计。它把大文件切块分布到集群多台机器上，靠副本保证容错，靠元数据与数据分离的架构支撑海量存储。HDFS 是数据湖、离线数仓底层存储的基石，也是 Iceberg/Hudi/Delta 等表格式默认的存储底座。

```text
HDFS 的核心设计取舍：
1. 大文件优先 —— 块默认 128MB，为顺序大文件吞吐优化，不适合海量小文件
2. 一次写多次读 —— 不支持随机写和并发写，追加为主
3. 元数据分离 —— 元数据在 NameNode 内存，数据在 DataNode 磁盘
4. 副本容错 —— 每块默认 3 副本，机架感知放置，坏盘自动恢复
5. 就近读取 —— 客户端优先读本地/同机架的副本，省网络
```

## 核心概念

HDFS 的六个核心概念：NameNode 与 DataNode（主从架构）、Block 与副本机制（切块容错）、Rack Awareness（机架感知）、HA（高可用）、Federation（联邦）、Snapshot（快照）。

### NameNode 与 DataNode

HDFS 采用主从架构：NameNode 是主节点，管理文件系统的命名空间（目录树）和块的映射关系（文件 -> 块 -> DataNode 位置），全部元数据常驻内存以支撑高吞吐；DataNode 是从节点，负责实际存储块数据，定期向 NameNode 汇报心跳（默认 3 秒）和块报告（Block Report）。

```text
NameNode / DataNode 职责划分：
1. NameNode —— 目录树、块映射、副本管理，元数据在内存 + fsimage/edits 持久化
2. DataNode —— 存块数据、响应读写请求、心跳汇报、执行复制/删除指令
3. 客户端 —— 先从 NameNode 拿块位置，再直接和 DataNode 传数据（不经过 NameNode）
4. SecondaryNameNode —— 定期合并 edits 到 fsimage，减轻 NameNode 恢复压力（非热备）
```

```xml
<!-- hdfs-site.xml 关键配置 -->
<configuration>
  <!-- 副本数，生产默认 3 -->
  <property>
    <name>dfs.replication</name>
    <value>3</value>
  </property>
  <!-- 块大小，单位字节，默认 128MB -->
  <property>
    <name>dfs.blocksize</name>
    <value>134217728</value>
  </property>
  <!-- NameNode 元数据目录 -->
  <property>
    <name>dfs.namenode.name.dir</name>
    <value>/hadoop/hdfs/namenode</value>
  </property>
  <!-- DataNode 数据目录（多个盘逗号分隔） -->
  <property>
    <name>dfs.datanode.data.dir</name>
    <value>/data/disk1,/data/disk2</value>
  </property>
</configuration>
```

### Block 与副本机制

文件被切分成固定大小的块（Block，默认 128MB，Hadoop 1.x 是 64MB），每块独立存储、独立复制。块大小影响寻址开销与任务并行度：块太小元数据膨胀，块太大单个任务处理时间过长。副本机制是 HDFS 容错的核心——每块默认 3 副本，分布在至少两个机架上，一个副本坏掉后 NameNode 会调度 DataNode 自动补副本。

```text
块与副本要点：
1. 块是抽象概念 —— 一个 200MB 文件存成 128MB + 72MB 两个块，不占满磁盘空间
2. 副本放置 —— 第一副本本地/同机架，第二副本同机架不同节点，第三副本跨机架
3. 块大小权衡 —— 大块减少寻址和元数据，但降低并行度和故障恢复粒度
4. 副本因子 —— 关键数据可调高，临时/可再生数据调低（如 2 副本）
```

```shell
# 查看块与副本信息
hdfs fsck /user/hive/warehouse -files -blocks -locations

# 手动设置副本数
hdfs dfs -setrep -w 3 /user/hive/warehouse/db.db/orders

# 查看单个文件块信息
hdfs fsck /path/to/file -files -blocks
```

### Rack Awareness 机架感知

机架感知是 HDFS 副本放置和 MapReduce 任务调度的前提：集群要知道每台机器属于哪个机架，才能把副本分散到不同机架、把计算调度到数据所在机架。副本放置策略是「本地 -> 同机架 -> 跨机架」，既保证容错（机架断电不丢数据）又保证局部性（读本地副本）。

```text
机架感知要点：
1. 副本跨机架 —— 至少一个副本放不同机架，防止整机架故障丢数据
2. 数据局部性 —— 计算任务优先调度到数据所在节点/机架，减少跨机架流量
3. 自定义拓扑 —— 通过 topology.py 脚本把 IP 映射到机架 ID（/rack1、/rack2）
4. 跨机架带宽珍贵 —— 放置策略刻意让多数副本在同机架、少数跨机架，平衡容错与带宽
```

```python
# 自定义机架拓扑脚本（core-site.xml 里 net.topology.script.file.name 指向它）
import sys

rack_map = {
    "192.168.1.10": "/rack1",
    "192.168.1.11": "/rack1",
    "192.168.1.20": "/rack2",
    "192.168.1.21": "/rack2",
}

for line in sys.stdin:
    ip = line.strip()
    print(rack_map.get(ip, "/default-rack"))
```

### HA 高可用

HDFS 1.x 的 NameNode 是单点故障——它挂了整个集群不可用。HA 引入两个 NameNode（Active + Standby），通过共享的 JournalNode 集群同步元数据（Active 写 edits 到 JournalNode，Standby 读 edits 保持同步），ZooKeeper 负责故障检测和自动切换（ZKFC 监控 NameNode 健康，失败时触发 failover）。

```text
HA 架构要点：
1. Active/Standby —— 同一时刻只有一个 Active 对外服务
2. JournalNode —— 奇数个（如 3）组成的共享编辑日志，Quorum 写入保证一致性
3. ZKFC —— ZooKeeper Failover Controller，监控 NameNode 并触发自动切换
4. 自动 failover —— Active 崩溃后 Standby 秒级接管，客户端无感（配合 RPC 重试）
5. 脑裂防护 —— Fencing 机制（如 SSH 强制 kill、共享存储锁）防止两个 NameNode 同时写
```

```xml
<!-- hdfs-site.xml HA 关键配置 -->
<configuration>
  <property>
    <name>dfs.nameservices</name>
    <value>mycluster</value>
  </property>
  <property>
    <name>dfs.ha.namenodes.mycluster</name>
    <value>nn1,nn2</value>
  </property>
  <property>
    <name>dfs.namenode.rpc-address.mycluster.nn1</name>
    <value>nn1.example.com:8020</value>
  </property>
  <property>
    <name>dfs.namenode.rpc-address.mycluster.nn2</name>
    <value>nn2.example.com:8020</value>
  </property>
  <!-- JournalNode 地址列表 -->
  <property>
    <name>dfs.namenode.shared.edits.dir</name>
    <value>qjournal://jn1:8485;jn2:8485;jn3:8485/mycluster</value>
  </property>
</configuration>
```

### Federation 联邦

Federation 解决单 NameNode 的扩展瓶颈（内存、命名空间、元数据 QPS）。它用多个 NameNode 各管一部分命名空间（Namespace），共享所有 DataNode 的存储池——每个 NameNode 独立维护自己的目录树和块池（Block Pool），互不干扰。客户端通过 ViewFS 或挂载表把不同路径路由到不同 NameNode。

```text
Federation 要点：
1. 多 NameNode —— 每个管一个命名空间，横向扩展元数据容量和吞吐
2. 共享 DataNode —— 所有 DataNode 同时为所有 NameNode 的块池服务
3. 块池隔离 —— 各 NameNode 的块独立编号，互不冲突
4. 与 HA 正交 —— 每个联邦命名空间可再配 HA，两者叠加使用
5. 适用场景 —— 单集群元数据超 10 亿文件、NameNode RPC 成为瓶颈时
```

```xml
<!-- hdfs-site.xml：Federation 多命名空间配置（ViewFS 挂载路由） -->
<configuration>
  <!-- 两个命名空间，各配自己的 NameNode -->
  <property>
    <name>dfs.nameservices</name>
    <value>ns1,ns2</value>
  </property>
  <property>
    <name>dfs.ha.namenodes.ns1</name>
    <value>nn1</value>
  </property>
  <property>
    <name>dfs.ha.namenodes.ns2</name>
    <value>nn2</value>
  </property>
  <!-- 用 ViewFS 把不同路径挂载到不同命名空间 -->
  <property>
    <name>fs.viewfs.mounttable.default.link./data/warehouse</name>
    <value>hdfs://ns1/data/warehouse</value>
  </property>
  <property>
    <name>fs.viewfs.mounttable.default.link./data/ods</name>
    <value>hdfs://ns2/data/ods</value>
  </property>
</configuration>
```

### Snapshot 快照

快照是某个目录在某一时刻的只读镜像，基于 Copy-on-Write（写时复制）实现——快照本身不复制数据，只在文件被修改时才记录差异，因此创建快照是 O(1) 的瞬时操作。快照用于数据备份、误删恢复、回滚和做 Spark/Hive 的数据版本管理。

```text
快照要点：
1. 瞬时创建 —— 只记录元数据指针，不复制数据块
2. 写时复制 —— 原文件变更时保留旧块，快照可还原到创建时刻
3. 允许快照的目录 —— 需先对该目录执行 allowSnapshot 开启
4. 恢复 —— 可整体回滚目录，也可单独复制快照里的文件
```

```shell
# 开启目录快照
hdfs dfsadmin -allowSnapshot /user/hive/warehouse/db.db

# 创建快照
hdfs dfs -createSnapshot /user/hive/warehouse/db.db snap_20240814

# 查看快照
hdfs dfs -ls /user/hive/warehouse/db.db/.snapshot/snap_20240814

# 从快照恢复误删文件
hdfs dfs -cp /user/hive/warehouse/db.db/.snapshot/snap_20240814/orders /user/hive/warehouse/db.db/orders
```

## 工作原理

HDFS 的核心工作机制围绕「元数据与数据分离」展开：NameNode 只存元数据（目录树 + 块映射），数据流不经过 NameNode，客户端直接与 DataNode 交互。写入走流水线（Pipeline），读取就近选择副本；DataNode 周期性心跳汇报存活、块报告汇报持有的块，NameNode 据此感知集群、调度副本复制与删除。

```text
写数据流程（流水线）：
1. 客户端向 NameNode 请求建文件，NameNode 检查权限/路径后分配块并返回 DataNode 列表
2. 客户端连第一个 DataNode，建立 dn1 → dn2 → dn3 的流水线
3. 数据按 64KB packet 逐级写入，每级写本地缓存并转发下游
4. 全部副本落盘后逐级回传 ACK，客户端收到才算写成功
5. 写满一个块再申请下一块；全部写完 NameNode 持久化元数据
```

```text
读数据流程：
1. 客户端向 NameNode 请求文件块位置
2. NameNode 按「距离」排序返回 DataNode 列表（本地 > 同机架 > 跨机架）
3. 客户端连最近的 DataNode 直接读块
4. 依次读完所有块；读不经过 NameNode，NameNode 只负责指路
```

```text
心跳与块报告：
心跳 Heartbeat —— DataNode 每 3 秒向 NameNode 报一次存活
块报告 Block Report —— 周期汇报本机所有块，NameNode 据此重建块映射
超时判死 —— 连续 10 分钟（默认）没心跳，NameNode 标记节点 Dead
副本复制 —— 发现副本不足（节点挂/坏盘）自动调度补副本
```

```text
HA 故障切换流程：
1. ZKFC 监控 Active NameNode 健康（通过 ZooKeeper 会话）
2. Active 崩溃/失联，ZK 会话超时，锁释放
3. Standby 的 ZKFC 抢到 ZK 锁，触发 fencing 隔离旧 Active
4. Standby 读尽 JournalNode edits、切换为 Active
5. 客户端 RPC 重试自动连到新 Active，无感切换
```

## 常用命令与配置

HDFS 的日常操作分「文件操作」「管理命令」「健康检查」三类：文件操作用 hdfs dfs 做增删查改，管理命令用 hdfs dfsadmin 管节点/安全模式/拓扑，健康检查用 hdfs fsck 查块健康与副本。

```shell
# 文件操作
hdfs dfs -ls /                      # 列目录
hdfs dfs -mkdir -p /data/raw        # 建目录
hdfs dfs -put local.log /data/raw/  # 上传
hdfs dfs -get /data/raw/a.txt ./    # 下载
hdfs dfs -cat /data/raw/a.txt       # 查看内容
hdfs dfs -appendToFile tail.log /data/raw/big.log   # 追加（HDFS 只支持追加）
hdfs dfs -setrep -w 3 /data/raw/    # 改副本数并等待完成
hdfs dfs -du -h /                   # 空间占用

# 管理命令
hdfs dfsadmin -report               # 节点/容量/块健康报告
hdfs dfsadmin -safemode get         # 安全模式状态
hdfs dfsadmin -safemode leave       # 离开安全模式
hdfs dfsadmin -printTopology        # 打印机架拓扑
hdfs dfsadmin -setBalancerBandwidth 104857600   # 设置平衡带宽（字节/秒）

# 健康检查
hdfs fsck / -files -blocks -locations -racks   # 块健康 + 机架分布
hdfs fsck / -list-corruptfileblocks             # 列出损坏块
```

```shell
# 快照命令
hdfs dfsadmin -allowSnapshot /data/db           # 开目录快照
hdfs dfs -createSnapshot /data/db snap_20240814 # 创建快照
hdfs dfs -ls /data/db/.snapshot/                # 列出快照
hdfs dfs -renameSnapshot /data/db snap_a snap_b # 重命名
hdfs dfs -deleteSnapshot /data/db snap_20240814 # 删除快照

# 纠删码（EC）命令
hdfs ec -enablePolicy -policy RS-6-3-1024k     # 启用 EC 策略
hdfs ec -setPolicy -path /data/cold -policy RS-6-3-1024k  # 目录应用 EC
hdfs ec -getPolicy -path /data/cold            # 查看策略

# 配额命令
hdfs dfsadmin -setQuota 100 /data/db           # 名称配额（文件数）
hdfs dfsadmin -setSpaceQuota 1T /data/db       # 空间配额
```

## 配置文件解析

HDFS 的配置集中在 hdfs-site.xml（HDFS 自身）和 core-site.xml（全局，含机架感知）。核心字段含义如下。

```xml
<!-- hdfs-site.xml 核心字段 -->
<configuration>
  <!-- 副本数 -->
  <property>
    <name>dfs.replication</name>
    <value>3</value>
  </property>
  <!-- 块大小（字节），默认 128MB -->
  <property>
    <name>dfs.blocksize</name>
    <value>134217728</value>
  </property>
  <!-- NameNode 元数据目录 -->
  <property>
    <name>dfs.namenode.name.dir</name>
    <value>/hadoop/hdfs/namenode</value>
  </property>
  <!-- DataNode 数据目录 -->
  <property>
    <name>dfs.datanode.data.dir</name>
    <value>/data/disk1,/data/disk2</value>
  </property>
  <!-- DataNode 心跳间隔（秒），默认 3 -->
  <property>
    <name>dfs.heartbeat.interval</name>
    <value>3</value>
  </property>
</configuration>
```

```xml
<!-- hdfs-site.xml HA 相关字段 -->
<configuration>
  <!-- 命名服务名 -->
  <property>
    <name>dfs.nameservices</name>
    <value>mycluster</value>
  </property>
  <!-- 两个 NameNode -->
  <property>
    <name>dfs.ha.namenodes.mycluster</name>
    <value>nn1,nn2</value>
  </property>
  <!-- 各 NameNode RPC 地址 -->
  <property>
    <name>dfs.namenode.rpc-address.mycluster.nn1</name>
    <value>nn1.example.com:8020</value>
  </property>
  <property>
    <name>dfs.namenode.rpc-address.mycluster.nn2</name>
    <value>nn2.example.com:8020</value>
  </property>
  <!-- JournalNode 共享 edits -->
  <property>
    <name>dfs.namenode.shared.edits.dir</name>
    <value>qjournal://jn1:8485;jn2:8485;jn3:8485/mycluster</value>
  </property>
  <!-- 自动 failover -->
  <property>
    <name>dfs.ha.automatic-failover.enabled</name>
    <value>true</value>
  </property>
</configuration>
```

```text
字段含义速查：
dfs.replication      副本数，3 是容错与成本平衡点
dfs.blocksize        块大小，128MB，超大文件可调 256MB
dfs.namenode.name.dir   元数据目录，多目录做冗余（元数据丢了集群就废）
dfs.datanode.data.dir   数据目录，多盘并行提升吞吐
dfs.heartbeat.interval  心跳间隔，3 秒，影响故障发现速度
dfs.namenode.shared.edits.dir  JournalNode 地址，HA 元数据同步通道
```

## 应用场景实战

### 场景一：小文件合并上传

```shell
# 海量小文件会压垮 NameNode 内存，先本地合并再上传
# 1. 本地用 tar 或 SequenceFile 合并小文件
tar -cf batch_20240814.tar /data/logs/*.log

# 2. 上传合并后的文件
hdfs dfs -put batch_20240814.tar /data/raw/logs/

# 3. 或用 Hadoop Archive（HAR）把小文件打成归档
hadoop archive -archiveName logs.har -p /data/raw/logs /data/raw/archive

# 4. 查看 NameNode 元数据占用，评估小文件问题
hdfs dfsadmin -report | grep -A 5 "Name:"
```

### 场景二：副本不足检测与修复

```shell
# 1. 全量健康检查，找出副本不足或损坏的块
hdfs fsck / -files -blocks -locations -racks 2>&1 | grep -E "MISSING|UNDER REPLICATED|CORRUPT"

# 2. 查看当前副本状态统计
hdfs fsck / -blocks 2>&1 | tail -20

# 3. 对副本不足的目录强制触发复制
hdfs dfs -setrep -w 3 /data/raw/

# 4. 进入安全模式排查时，先离开安全模式
hdfs dfsadmin -safemode get
hdfs dfsadmin -safemode leave
```

### 场景三：冷数据用纠删码降低存储成本

```shell
# 1. 查看可用的 EC 策略
hdfs ec -listPolicies

# 2. 给冷数据目录启用 RS-6-3-1024k 策略（6 数据块 + 3 校验块，冗余 50%）
hdfs ec -setPolicy -path /data/warehouse/cold -policy RS-6-3-1024k

# 3. 验证策略已生效
hdfs ec -getPolicy -path /data/warehouse/cold

# 4. 对比：3 副本存 1GB 占 3GB，EC(6+3) 存 1GB 只占 1.5GB，省一半空间
```

## 性能与调优

HDFS 性能调优围绕「存储吞吐」和「元数据容量」两条线。存储侧关键是块大小、副本数与磁盘并行度；元数据侧关键是 NameNode 堆内存与命名空间规模。冷数据用纠删码替代多副本是近年最重要的降本手段。

```text
存储侧调优：
1. 块大小 —— 128MB 起步，超大文件 256MB 减少元数据和寻址；小文件反而要先合并
2. 副本数 —— 热数据 3 副本，冷数据用 EC（RS-6-3 冗余 50% 省一半空间）
3. NameNode 堆 —— 每百万块约需 1GB 堆，堆不够就加内存或拆命名空间（Federation）
4. DataNode 多盘 —— 数据目录多盘并行，读写吞吐随盘数线性提升
5. 平衡器 —— 定期跑 balancer 平衡节点数据分布，避免热点节点
```

```text
读写调优：
1. 写吞吐 —— 大块 + 流水线 + 本地短回路读（short-circuit local read）
2. 读吞吐 —— 数据局部性优先，任务调度到数据所在节点
3. 平衡带宽 —— dfsadmin -setBalancerBandwidth 控制平衡速率，别影响业务
4. 磁盘分层 —— DataNode 用 HDD 存冷数据、SSD 存热数据（分层存储）
```

```shell
# 平衡节点数据分布（默认 10% 阈值）
hdfs balancer -threshold 10

# 控制平衡带宽（100MB/s）
hdfs dfsadmin -setBalancerBandwidth 104857600
```

## 安全与权限

HDFS 的权限模型是 POSIX 风格（属主/属组/其他 + rwx）+ 扩展 ACL，配合 Kerberos 认证做身份鉴权。对落盘数据可用加密区（Encryption Zone，透明数据加密，密钥由 KMS 管理）防止磁盘被盗泄密；误删防护靠快照 + 回收站。

```shell
# 1. 文件权限（POSIX 风格 rwxr-xr-x + 属主属组）
hdfs dfs -chmod 750 /data/db/
hdfs dfs -chown hive:hive /data/db/

# 2. ACL 细粒度授权
hdfs dfs -getfacl /data/sensitive/
hdfs dfs -setfacl -m user:alice:r-x /data/sensitive/

# 3. 加密区（透明数据加密，配合 KMS）
hdfs key create mykey                 # 创建密钥（KMS）
hdfs crypto -createZone -keyName mykey -path /data/encrypted   # 建加密区
hdfs crypto -listZones                # 查看加密区

# 4. 回收站（延迟删除，误删可恢复）
hdfs dfs -ls /user/hive/.Trash/
```

```text
安全加固要点：
1. Kerberos 认证 —— 未认证客户端拒绝访问，防伪装用户
2. POSIX 权限 + ACL —— 目录最小权限，敏感数据单独授权
3. 加密区 —— 落盘数据透明加密（KMS 管密钥），防磁盘被盗泄密
4. 回收站 —— fs.trash.interval 延迟删除，误删可恢复
5. 审计日志 —— NameNode 审计日志记录所有操作，可追溯
```

## 故障排查

HDFS 故障排查从「集群状态 → 存储健康 → 具体块」逐层定位。先看节点是否全活、是否卡安全模式，再看块是否健康、副本是否齐全，最后定位到具体文件或块。

```shell
# 1. NameNode 卡安全模式
hdfs dfsadmin -safemode get     # 确认是否 safemode
hdfs dfsadmin -safemode leave   # 副本满足后手动离开
hdfs fsck / -files -blocks      # 查副本不足的块

# 2. DataNode 掉线
hdfs dfsadmin -report           # 看 Dead 节点
tail -f $HADOOP_LOG_DIR/hdfs-hadoop-datanode-*.log   # 看 DataNode 日志

# 3. 损坏块
hdfs fsck / -list-corruptfileblocks   # 列损坏块
# 定位后删除或从副本/快照恢复

# 4. 写入失败/慢
hdfs dfsadmin -report | grep -E "Dead|Decommission"  # 节点是否掉线/退役中
df -h                           # DataNode 磁盘是否写满
hdfs dfs -du -h /data/          # 看目录占用

# 5. 客户端读写卡住（Lease 未释放）
hdfs debug recoverLease -path /data/raw/a.txt -retries 3
```

```text
三类典型故障：
1. 卡安全模式 —— 副本不足/NameNode 刚重启，等副本恢复或 leave
2. 块损坏 —— fsck 定位，从其他副本自动修复，全坏则从快照/备份恢复
3. 元数据损坏 —— NameNode 挂且 fsimage/edits 损坏，用 JournalNode/SecondaryNameNode 恢复
```

## 常见问题

```text
Q1: HDFS 为什么不支持随机写和并发写？
A: HDFS 为高吞吐顺序写设计，一个文件同一时刻只允许一个写者，写完后只能追加不能改。随机写需要复杂的锁和一致性，会牺牲吞吐。要更新用重写 + 原子替换，或 HBase/Hudi 等支持更新的存储。

Q2: 块大小为什么是 128MB，能改吗？
A: 128MB 是「吞吐 vs 并行度 vs 元数据」的平衡：块大寻址开销小、元数据少，但并行度低、故障恢复粒度粗。能改（dfs.blocksize），超大文件可 256MB，但已存文件不受影响。

Q3: 副本数 3 的含义？为什么不是 2 或 4？
A: 3 副本 = 容忍 2 个副本同时坏仍有一份可用（容错 N-1）。2 副本容忍 1 个坏，风险偏高；4 副本存储成本 +33% 收益有限。3 是容错与成本的平衡点。

Q4: SecondaryNameNode 是 NameNode 的热备吗？
A: 不是。它只定期合并 edits 到 fsimage（checkpoint），减轻 NameNode 恢复压力，不能接管服务。真正的热备是 HA 里的 Standby NameNode。

Q5: 快照会复制数据吗？为什么创建快照是瞬时的？
A: 不复制。快照基于 Copy-on-Write，只记录元数据指针，文件被修改时才保留旧块，所以创建是 O(1) 瞬时操作，不占额外空间（只随修改增量增长）。

Q6: Federation 和 HA 有什么区别？
A: HA 解决「单点可用性」——一个命名空间配两个 NameNode 主备切换；Federation 解决「容量扩展」——多个 NameNode 各管一个命名空间，共享 DataNode。两者正交，可叠加（每个联邦命名空间再配 HA）。

Q7: 为什么小文件会压垮 NameNode？
A: 每个文件/块在 NameNode 内存占 150-200 字节元数据，百万小文件吃上百 MB 堆，NameNode 内存先于磁盘成为瓶颈。且小文件多导致块多、寻址多、Map 任务多，整体变慢。
```

## 面试题

```text
1. HDFS 的读写流程（写一个文件的全过程）？
   答：客户端向 NameNode 请求建文件，NameNode 检查权限并分配块、返回 DataNode 列表；客户端建立 dn1 → dn2 → dn3 流水线，数据按 packet 逐级写入；每块写完 ACK 回传，写满再申请下一块；全部写完关闭流，NameNode 持久化元数据。

2. NameNode 挂了怎么办？怎么保证高可用？
   答：不配 HA 时 NameNode 是单点，挂了集群不可用。HA 方案：两个 NameNode（Active + Standby）+ JournalNode 集群共享 edits（Active 写、Standby 读保持同步）+ ZKFC 故障检测自动切换 + fencing 防脑裂。

3. 副本放置策略是什么？为什么这样放？
   答：第一副本放客户端所在节点（或随机），第二副本放同机架不同节点，第三副本放不同机架。多数副本在同机架保证写带宽和读局部性，至少一个副本跨机架保证机架断电不丢数据。

4. 机架感知有什么用？
   答：两个用途：(1) 副本放置——副本跨机架分布防整机架故障丢数据；(2) 任务调度——MapReduce/Spark 把计算调度到数据所在机架，减少跨机架带宽消耗。

5. HDFS 的一致性模型是怎样的？
   答：一次写多次读（write-once-read-many）。文件创建后只能追加不能改，写完后对其他读者可见；正在写的数据对读者不可见（除非 sync）。适合离线批处理，不适合低延迟随机读写。

6. 纠删码（EC）和副本有什么区别？什么时候用 EC？
   答：副本是整块复制（3 副本冗余 200%），读写快但成本高；EC 是条带化 + 校验块（RS-6-3 冗余 50%），省空间但恢复时 CPU 开销大、随机读慢。冷数据、归档数据用 EC，热数据用副本。

7. 快照的实现原理？和备份的区别？
   答：快照是 Copy-on-Write 的只读镜像，只记元数据指针、修改时才复制差异块，瞬时创建、空间高效、可快速回滚；备份是全量/增量拷贝数据到别处，耗时长、占空间、用于灾难恢复。两者配合使用。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 块大小保持默认 128MB，除非明确是超大数据集可调到 256MB
2. 生产副本数 3，机架感知配置正确，确保副本跨机架
3. NameNode 元数据目录配多个盘做 RAID 或直接多目录冗余
4. 定期做 fsck 检查块健康和副本状况
5. 海量小文件先合并再入 HDFS，或改用 HBase/对象存储
6. 重要目录开快照，配合定时快照做数据备份
7. 升级/高危操作前先进入安全模式（safemode）保护元数据

### 踩坑记录

```text
坑 1：海量小文件撑爆 NameNode
结论：NameNode 内存耗尽，集群变慢甚至不可用。
原因：每个文件/块在 NameNode 内存约占 150-200 字节元数据，百万小文件就吃上百 MB。
解法：本地合并、HAR 归档、改用 SequenceFile/Parquet，或迁移到对象存储 + 表格式。

坑 2：副本数设置过高导致存储成本翻倍
结论：存储成本暴涨，写入吞吐下降。
原因：副本数 4/5 时每份数据存多份，且写入要同步多副本。
解法：默认 3 副本，可再生数据（日志中间态）可降到 2 甚至用纠删码（EC）。

坑 3：忽略机架感知导致副本全在同一机架
结论：机架断电时数据全丢。
原因：未配置 topology 脚本，HDFS 把不同机架机器当同机架放置副本。
解法：配置 net.topology.script.file.name，验证副本确实跨机架。

坑 4：误删文件后才发现没快照
结论：数据无法恢复，只能从备份或重新生成。
原因：未开启目录快照，删除操作直接进 edits 不可逆。
解法：重要目录 allowSnapshot + 定时 createSnapshot，删除用 trash 机制（延迟删除）。

坑 5：写副本超时误判为 DataNode 故障
结论：NameNode 频繁把健康节点标记为死节点，触发无谓的副本复制。
原因：网络抖动或磁盘慢导致 DataNode 心跳超时，NameNode 误判。
解法：调大 dfs.namenode.heartbeat.recheck-interval 和超时阈值，排查网络/磁盘。
```
