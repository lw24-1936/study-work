## 概述

Consumer 是 Kafka 的消费客户端，以「拉模式」主动从 Broker 拉取消息，通过消费者组实现水平扩展与负载均衡。消费进度由 Offset 提交管理，配合提交时机与再均衡策略，可以在「至少一次」「至多一次」「精确一次」三种语义间权衡，是实时计算、数据同步等场景的数据入口。

```text
核心特征：
- 拉模式 poll：消费速率由消费者控制，避免推送压垮
- 组模型：组内分摊分区，跨组广播
- 进度可回溯：按 Offset 任意重放历史数据
- 语义可选：提交策略决定 at-least/at-most/exactly-once
```

## 知识点章节

### Poll

Poll 是 Consumer 拉取消息的核心动作，通过 `poll(Duration)` 从订阅的分区拉取一批记录。内部完成网络请求、自动提交、再均衡回调与心跳等逻辑，单次 poll 必须在一个会话周期内完成，否则会被判定为失联而触发再均衡。

```text
要点：
- poll 返回 ConsumerRecords，按分区组织
- max.poll.records 控制单次拉取条数（默认 500）
- 处理耗时需小于 max.poll.interval.ms（默认 5 分钟）
- 循环调用 poll 驱动心跳与提交，勿长时间阻塞
```

```java
import org.apache.kafka.clients.consumer.*;
import java.time.Duration;
import java.util.*;
public class PollConsumer {
    public static void main(String[] args) {
        Properties p = new Properties();
        p.put("bootstrap.servers", "localhost:9092");
        p.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        p.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        p.put("group.id", "poll-group");
        p.put("max.poll.records", 500);           // 单次最多 500 条
        p.put("max.poll.interval.ms", 300000);    // 处理超时阈值
        try (KafkaConsumer<String, String> c = new KafkaConsumer<>(p)) {
            c.subscribe(List.of("order.pay.success"));
            while (true) {
                ConsumerRecords<String, String> rs = c.poll(Duration.ofMillis(200));
                for (ConsumerRecord<String, String> r : rs) {
                    System.out.printf("partition=%d offset=%d %s=%s%n",
                        r.partition(), r.offset(), r.key(), r.value());
                }
            }
        }
    }
}
```

### Commit

Commit 是把消费进度（Offset）持久化到 `__consumer_offsets` 内部主题的动作，决定「重启后从哪继续消费」。提交方式分自动提交与手动提交，手动又分同步 `commitSync` 与异步 `commitAsync`，提交时机直接影响消息是否可能丢失或重复。

```text
要点：
- 自动提交：enable.auto.commit=true，按 auto.commit.interval.ms 定时提交
- 手动同步 commitSync：阻塞直到提交成功，可靠性高
- 手动异步 commitAsync：非阻塞，失败需回调重试
- 提交滞后于实际处理 → at-least-once；提前提交 → at-most-once
```

```java
import org.apache.kafka.clients.consumer.*;
import java.time.Duration;
import java.util.*;
public class ManualCommitConsumer {
    public static void main(String[] args) {
        Properties p = new Properties();
        p.put("bootstrap.servers", "localhost:9092");
        p.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        p.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        p.put("group.id", "manual-group");
        p.put("enable.auto.commit", "false");   // 关闭自动提交
        try (KafkaConsumer<String, String> c = new KafkaConsumer<>(p)) {
            c.subscribe(List.of("order.pay.success"));
            while (true) {
                ConsumerRecords<String, String> rs = c.poll(Duration.ofMillis(200));
                for (ConsumerRecord<String, String> r : rs) {
                    process(r);   // 业务处理
                }
                c.commitSync();   // 处理完一批后手动同步提交
            }
        }
    }
    static void process(ConsumerRecord<String, String> r) { /* 业务逻辑 */ }
}
```

### Rebalance

Rebalance（再均衡）是消费者组重新分配分区的过程：当组内成员增减、订阅 Topic 变化或分区数变化时，协调器会触发再均衡，把分区重新分配给存活成员。再均衡期间组内消费者暂停消费，是消费延迟与重复的常见来源。

```text
要点：
- 触发：成员加入/退出、订阅变更、分区扩容
- 策略：Range、RoundRobin、Sticky、CooperativeSticky
- 期间组内分区停止消费，产生短暂停顿
- Sticky 策略尽量减少分区迁移，Cooperative 增量再均衡不停顿
```

```java
Properties p = new Properties();
p.put("bootstrap.servers", "localhost:9092");
p.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
p.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
p.put("group.id", "rebalance-group");
p.put("partition.assignment.strategy", "org.apache.kafka.clients.consumer.CooperativeStickyAssignor");
p.put("session.timeout.ms", 10000);       // 会话超时
p.put("heartbeat.interval.ms", 3000);     // 心跳间隔
// 再均衡监听器：分区撤销/分配回调
try (KafkaConsumer<String, String> c = new KafkaConsumer<>(p)) {
    c.subscribe(List.of("order.pay.success"), new ConsumerRebalanceListener() {
        public void onPartitionsRevoked(Collection<TopicPartition> ps) { /* 提交偏移 */ }
        public void onPartitionsAssigned(Collection<TopicPartition> ps) { /* 初始化 */ }
    });
}
```

### Exactly-Once 语义保证

Exactly-Once（精确一次）指消息被处理且仅被处理一次，端到端既不丢也不重。Kafka 侧靠「幂等 Producer + 事务 + 事务性提交 Offset」实现流内精确一次；端到端（含外部系统）精确一次还需下游支持幂等写入或原子写入，仅靠 Kafka 无法单独保证。

```text
要点：
- 三种语义：at-most-once / at-least-once / exactly-once
- 流内精确一次：enable.idempotence + 事务 + read_committed
- 关键配置：isolation.level=read_committed 过滤未提交事务消息
- 端到端精确一次需下游幂等，如唯一键 upsert
```

```java
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.TopicPartition;
import java.time.Duration;
import java.util.*;
public class EosConsumer {
    public static void main(String[] args) {
        Properties cp = new Properties();
        cp.put("bootstrap.servers", "localhost:9092");
        cp.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        cp.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        cp.put("group.id", "eos-group");
        cp.put("enable.auto.commit", "false");
        cp.put("isolation.level", "read_committed");   // 只读已提交事务
        KafkaConsumer<String, String> c = new KafkaConsumer<>(cp);
        Properties pp = new Properties();
        pp.put("bootstrap.servers", "localhost:9092");
        pp.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        pp.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        pp.put("transactional.id", "eos-consumer-tx-1");
        KafkaProducer<String, String> producer = new KafkaProducer<>(pp);
        producer.initTransactions();
        c.subscribe(List.of("input.topic"));
        while (true) {
            ConsumerRecords<String, String> rs = c.poll(Duration.ofMillis(200));
            if (rs.isEmpty()) continue;
            producer.beginTransaction();
            try {
                for (ConsumerRecord<String, String> r : rs) {
                    producer.send(new ProducerRecord<>("output.topic", r.key(), transform(r.value())));
                }
                // 把消费 Offset 与结果写入放进同一事务原子提交
                Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
                for (TopicPartition tp : rs.partitions()) {
                    long last = rs.records(tp).get(rs.records(tp).size() - 1).offset();
                    offsets.put(tp, new OffsetAndMetadata(last + 1));
                }
                producer.sendOffsetsToTransaction(offsets, cp.getProperty("group.id"));
                producer.commitTransaction();
            } catch (Exception e) {
                producer.abortTransaction();
            }
        }
    }
    static String transform(String v) { return v.toUpperCase(); }
}
```

## 应用场景实战

### 场景一：订单实时对账（手动提交 + 死信处理）

目标：消费订单消息做对账，处理失败的消息进入死信 Topic，成功后手动提交，保证至少一次且失败可追溯。

```java
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.clients.producer.*;
import java.time.Duration;
import java.util.*;
public class ReconciliationConsumer {
    public static void main(String[] args) {
        Properties cp = new Properties();
        cp.put("bootstrap.servers", "localhost:9092");
        cp.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        cp.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        cp.put("group.id", "recon-group");
        cp.put("enable.auto.commit", "false");
        KafkaConsumer<String, String> c = new KafkaConsumer<>(cp);
        Properties pp = new Properties();
        pp.put("bootstrap.servers", "localhost:9092");
        pp.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        pp.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        KafkaProducer<String, String> dead = new KafkaProducer<>(pp);
        c.subscribe(List.of("order.pay.success"));
        while (true) {
            ConsumerRecords<String, String> rs = c.poll(Duration.ofMillis(200));
            for (ConsumerRecord<String, String> r : rs) {
                try {
                    reconcile(r.value());      // 对账逻辑
                } catch (Exception e) {
                    dead.send(new ProducerRecord<>("order.dead", r.key(), r.value()));
                }
            }
            c.commitSync();                   // 整批处理完再提交
        }
    }
    static void reconcile(String v) { /* 对账业务 */ }
}
```

### 场景二：历史数据回溯重放

目标：消费组需要从指定时间点或最早位置重放历史数据，用于数据修复或新算法回填。

```shell
# 1. 停止消费组并查看当前进度
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group recon-group
# 2. 重置到最早位置（回填全量历史）
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group recon-group --topic order.pay.success \
  --reset-offsets --to-earliest --execute
# 3. 按时间点重置（回溯到 2026-08-14 00:00:00）
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group recon-group --topic order.pay.success \
  --reset-offsets --to-datetime 2026-08-14T00:00:00.000 --execute
# 4. 重新启动消费应用完成重放
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产环境关闭自动提交（`enable.auto.commit=false`），在业务处理成功后手动提交，保证至少一次。
2. 单条处理耗时控制在 `max.poll.interval.ms` 的 1/3 以内，超长任务用线程池异步化并拆分批次。
3. 幂等设计兜底：即使 Kafka 侧重复投递，靠业务唯一键（如订单号）去重，从根本上避免重复影响。
4. 消费失败用「重试 Topic + 死信 Topic」分层处理，避免无限重试阻塞主流程。
5. 再均衡用 `CooperativeStickyAssignor`，减少分区迁移与消费停顿；监听器里做好撤销时提交。
6. 监控消费 Lag、`records-lag-max` 与再均衡次数，Lag 持续上涨是消费能力不足的预警。
7. 需要精确一次时优先「Kafka 流内事务 + 下游幂等 upsert」，不要指望单靠消费端配置达成端到端精确一次。

### 踩坑记录

```text
坑 1：消费偶发重复，重启后消息重放
结论：自动提交或「先处理部分再提交」导致提交位置落后于实际进度。
原因：提交是异步定时或批处理中途崩溃，已处理消息的 Offset 未提交。
解法：关闭自动提交，处理完一批立即 commitSync；业务侧按唯一键幂等。
坑 2：消费者被反复踢出组，日志频繁 Rebalance
结论：poll 处理耗时超过 max.poll.interval.ms，被协调器判定失联。
原因：单批消息处理时间过长，心跳线程无法在间隔内完成 poll 循环。
解法：调大 max.poll.interval.ms，或减小 max.poll.records 并异步处理。
坑 3：新增消费者后旧消费者仍持有全部分区
结论：使用 Range 或 RoundRobin 时再均衡需时间生效，且可能触发全量重分配。
原因：再均衡有协调延迟，且某些策略会大范围迁移分区。
解法：改用 CooperativeStickyAssignor 增量再均衡，减少停顿与重复。
坑 4：seek 后消费位置不生效
结论：在 poll 之前或再均衡之后 seek，会被自动提交或重新分配覆盖。
原因：seek 只影响当前分配的分区，再均衡后需在 onPartitionsAssigned 中重新 seek。
解法：在再均衡监听器的 onPartitionsAssigned 回调中执行 seek。
坑 5：read_committed 下消费不到消息
结论：isolation.level 设为 read_committed 后，未提交事务的消息不会返回。
原因：事务未提交或长时间挂起，消息被隔离过滤。
解法：排查上游事务是否正常 commit，必要时设置 transaction.timeout.ms 兜底超时。
```
