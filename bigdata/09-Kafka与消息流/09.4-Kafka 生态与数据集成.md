## 概述

Kafka 不只是消息队列，围绕它发展出了一整套流处理与数据集成生态。Kafka Streams 提供流计算库，Kafka Connect 打通外部系统的数据搬运，Schema Registry 统一管理数据契约，Debezium 与 CDC 实现数据库变更捕获，MirrorMaker 完成跨集群复制，安全机制保障端到端访问控制。

```text
生态全景：
- 流处理：Kafka Streams / ksqlDB
- 数据集成：Kafka Connect（Source / Sink）
- 数据契约：Schema Registry（Avro / Protobuf / JSON Schema）
- 变更捕获：CDC / Debezium
- 跨集群：MirrorMaker 2
- 安全：SSL / SASL / ACL
```

## 知识点章节

### Kafka Streams

Kafka Streams 是一个内嵌的流处理库（非独立集群），直接在应用进程内消费 Kafka 消息、做有状态或无状态计算、再把结果写回 Kafka。它提供 DSL 与 Processor API，支持窗口、聚合、连接与本地状态存储，通过 Kafka 的消费组实现水平扩展与容错。

```text
要点：
- 库而非平台：以普通 Java 应用方式部署
- DSL 操作：filter / map / groupBy / join / windowed
- 状态存储：本地 RocksDB + changelog Topic 备份
- 精确一次：配合事务实现流内 exactly-once
```

```java
import org.apache.kafka.common.serialization.Serdes;
import org.apache.kafka.streams.*;
import org.apache.kafka.streams.kstream.*;
import java.util.Properties;

public class WordCountApp {
    public static void main(String[] args) {
        Properties p = new Properties();
        p.put(StreamsConfig.APPLICATION_ID_CONFIG, "wordcount-app");
        p.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        p.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.String().getClass());
        p.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.String().getClass());

        StreamsBuilder b = new StreamsBuilder();
        KStream<String, String> text = b.stream("input.words");
        KTable<String, Long> counts = text
            .flatMapValues(v -> java.util.Arrays.asList(v.toLowerCase().split("\\W+")))
            .groupBy((k, v) -> v)
            .count();
        counts.toStream().to("output.counts", Produced.with(Serdes.String(), Serdes.Long()));

        KafkaStreams ks = new KafkaStreams(b.build(), p);
        ks.start();
        Runtime.getRuntime().addShutdownHook(new Thread(ks::close));
    }
}
```

### Kafka Connect

Kafka Connect 是 Kafka 自带的数据集成框架，用 Source Connector 把外部系统的数据导入 Kafka，用 Sink Connector 把 Kafka 数据导出到下游，无需写代码即可完成数据搬运。它以 Worker 进程运行（独立或分布式），通过 REST 接口管理连接器实例。

```text
要点：
- Source：外部系统 → Kafka；Sink：Kafka → 外部系统
- 独立模式（standalone）与分布式模式（distributed）
- 配置驱动：连接器名 + connector.class + tasks.max
- 常见连接器：JDBC、S3、Elasticsearch、HDFS
```

```yaml
# config/connect-standalone.properties（示意）
bootstrap.servers: localhost:9092
key.converter: org.apache.kafka.connect.json.JsonConverter
value.converter: org.apache.kafka.connect.json.JsonConverter
offset.storage.file.filename: /tmp/connect.offsets
```

```shell
# 启动分布式 Connect Worker
bin/connect-distributed.sh config/connect-distributed.properties

# 注册一个 JDBC Source 连接器（MySQL 表 → Kafka）
curl -X POST -H "Content-Type: application/json" localhost:8083/connectors \
  -d '{
    "name": "mysql-source-orders",
    "config": {
      "connector.class": "io.confluent.connect.jdbc.JdbcSourceConnector",
      "connection.url": "jdbc:mysql://localhost:3306/shop",
      "connection.user": "root",
      "connection.password": "secret",
      "mode": "timestamp",
      "timestamp.column.name": "updated_at",
      "topic.prefix": "mysql-orders-",
      "table.whitelist": "orders"
    }
  }'

# 查看 / 删除连接器
curl -s localhost:8083/connectors/mysql-source-orders/status
curl -X DELETE localhost:8083/connectors/mysql-source-orders
```

### Schema Registry

Schema Registry 是集中管理数据模式（Schema）的服务，主要与 Avro/Protobuf/JSON Schema 配合，为每条 Kafka 消息关联一个版本化的 Schema ID。生产者在消息头写入 Schema ID，消费者按 ID 拉取对应 Schema 反序列化，实现「写入校验 + 读取兼容」的数据契约治理。

```text
要点：
- 集中存储 Schema 版本，支持兼容性校验
- 消息体只带 Schema ID，不冗余 Schema 文本
- 兼容策略：BACKWARD / FORWARD / FULL / NONE
- 生产端校验新 Schema 兼容性，防止破坏性变更
```

```shell
# 注册一个 Avro Schema（subject：topic-value）
curl -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  localhost:8081/subjects/order-value/versions \
  -d '{"schema": "{\"type\":\"record\",\"name\":\"Order\",\"fields\":[{\"name\":\"orderId\",\"type\":\"string\"},{\"name\":\"amount\",\"type\":\"double\"}]}"}'

# 查看最新版本与兼容性
curl -s localhost:8081/subjects/order-value/versions/latest
curl -X POST -H "Content-Type: application/json" \
  localhost:8081/compatibility/subjects/order-value/versions/latest \
  -d '{"schema": "{\"type\":\"record\",\"name\":\"Order\",\"fields\":[{\"name\":\"orderId\",\"type\":\"string\"}]}"}'
```

### CDC

CDC（Change Data Capture，变更数据捕获）是捕获数据库增删改操作并实时对外输出的技术，常用于数据库到数据湖/数仓/缓存的实时同步。它比轮询快照更实时、侵入更小，核心手段是解析数据库事务日志（如 MySQL binlog、PostgreSQL WAL），把行级变更转为事件流。

```text
要点：
- 捕获 INSERT / UPDATE / DELETE 行级变更
- 基于 binlog / WAL / redo log 解析，非轮询
- 低延迟、低侵入，不影响业务库性能
- 输出事件含 before / after 镜像与操作类型
```

```sql
-- MySQL 开启 binlog（ROW 格式）是 CDC 的前提
-- 在 my.cnf 中配置
-- [mysqld]
-- server-id=1
-- log-bin=mysql-bin
-- binlog_format=ROW
-- binlog_row_image=FULL
SHOW VARIABLES LIKE 'binlog_format';
SHOW MASTER STATUS;
```

### Debezium

Debezium 是构建在 Kafka Connect 之上的 CDC 引擎，通过 Source Connector 读取 MySQL、PostgreSQL、MongoDB、Oracle 等数据库的日志，把行级变更转成标准化事件写入 Kafka。它内置快照 + 增量捕获、故障恢复与 schema 变更事件，是 Kafka 生态里 CDC 的事实标准实现。

```text
要点：
- 基于 Kafka Connect 运行，输出到 Kafka Topic
- 事件结构：op / before / after / source / ts_ms
- 首次做一致性快照，之后增量读日志
- 支持 DDL 变更事件与多库多表过滤
```

```yaml
# config/mysql-connector.json（示意）
name: shop-mysql-connector
config:
  connector.class: io.debezium.connector.mysql.MySqlConnector
  database.hostname: localhost
  database.port: 3306
  database.user: debezium
  database.password: dbz
  database.server.id: 1
  database.include.list: shop
  table.include.list: shop.orders
  topic.prefix: dbserver1
  database.history.kafka.bootstrap.servers: localhost:9092
  database.history.kafka.topic: schema-changes.shop
```

```shell
# 注册 Debezium 连接器
curl -X POST -H "Content-Type: application/json" localhost:8083/connectors \
  -d @config/mysql-connector.json

# 消费 CDC 事件（op 字段标识 c=create u=update d=delete）
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic dbserver1.shop.orders --from-beginning
```

### MirrorMaker

MirrorMaker 2（MM2）是 Kafka 官方的跨集群复制工具，用于数据中心容灾、云迁移与多地域聚合。它基于 Kafka Connect 实现，在源与目标集群之间复制 Topic、消费组 Offset 与配置，并自动处理 Topic 重命名（加源集群前缀）防止循环复制。

```text
要点：
- MM2 基于 Connect 框架，取代旧版 MM1
- 复制 Topic 数据 + 消费组 Offset 迁移
- 源集群别名前缀避免死循环复制
- 支持 active-active 双活与单向容灾
```

```yaml
# config/connect-mirror-maker.properties（示意）
clusters: dc1, dc2
dc1.bootstrap.servers: dc1-kafka:9092
dc2.bootstrap.servers: dc2-kafka:9092
dc1->dc2.enabled: true
dc2->dc1.enabled: false
replication.factor: 3
topics: order\..*
groups: .*
```

```shell
# 启动 MirrorMaker 2（单向 dc1 → dc2）
bin/connect-mirror-maker.sh config/connect-mirror-maker.properties

# 目标集群消费复制后的 Topic（前缀 dc1.）
bin/kafka-console-consumer.sh --bootstrap-server dc2-kafka:9092 \
  --topic dc1.order.pay.success --from-beginning
```

### 安全

Kafka 安全体系覆盖认证、加密、授权三个层面：SSL 负责传输加密与可选的双向认证，SASL（PLAIN/SCRAM/GSSAPI/OAUTHBEARER）负责客户端身份认证，ACL 负责细粒度的资源授权，整体由 KRaft 或 ZooKeeper 保存安全元数据。

```text
要点：
- 认证：SASL_SSL（认证 + 加密）为生产标配
- 加密：SSL/TLS 保护传输数据
- 授权：ACL 控制 Topic/Group 的读写与创建
- 支持 JAAS 配置与多监听器隔离内外网
```

```yaml
# config/server.properties 安全相关（示意）
listeners: SASL_SSL://:9093
advertised.listeners: SASL_SSL://broker1:9093
security.inter.broker.protocol: SASL_SSL
sasl.enabled.mechanisms: SCRAM-SHA-256
ssl.keystore.location: /etc/kafka/secrets/broker.keystore.jks
ssl.keystore.password: changeit
ssl.key.password: changeit
ssl.truststore.location: /etc/kafka/secrets/broker.truststore.jks
ssl.truststore.password: changeit
authorizer.class.name: org.apache.kafka.metadata.authorizer.StandardAuthorizer
super.users: User:admin
```

```shell
# 创建 SCRAM 用户
bin/kafka-configs.sh --bootstrap-server localhost:9093 \
  --alter --add-config 'SCRAM-SHA-256=[password=secret]' \
  --entity-type users --entity-name alice

# 授予 ACL：alice 对 order.* 主题的读写权限
bin/kafka-acls.sh --bootstrap-server localhost:9093 \
  --add --allow-principal User:alice \
  --operation Read --operation Write --topic 'order.*'
```

## 应用场景实战

### 场景一：MySQL 订单表 CDC 实时入湖

目标：用 Debezium 捕获 MySQL `orders` 表的变更，经 Kafka 落到数据湖，实现秒级数据同步。

```shell
# 1. 注册 Debezium MySQL 连接器（首次会做一致性快照）
curl -X POST -H "Content-Type: application/json" localhost:8083/connectors \
  -d '{
    "name": "shop-orders-cdc",
    "config": {
      "connector.class": "io.debezium.connector.mysql.MySqlConnector",
      "database.hostname": "mysql-host",
      "database.port": 3306,
      "database.user": "debezium",
      "database.password": "dbz",
      "database.include.list": "shop",
      "table.include.list": "shop.orders",
      "topic.prefix": "cdc"
    }
  }'

# 2. 注册 S3 Sink 连接器（Kafka → 数据湖对象存储）
curl -X POST -H "Content-Type: application/json" localhost:8083/connectors \
  -d '{
    "name": "s3-sink-orders",
    "config": {
      "connector.class": "io.confluent.connect.s3.S3SinkConnector",
      "topics": "cdc.shop.orders",
      "s3.bucket.name": "datalake-bucket",
      "s3.region": "cn-north-1",
      "flush.size": 1000,
      "format.class": "io.confluent.connect.s3.format.parquet.ParquetFormat"
    }
  }'

# 3. 观察 CDC 事件流与 Sink 任务状态
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic cdc.shop.orders --from-beginning
curl -s localhost:8083/connectors/s3-sink-orders/status
```

### 场景二：跨地域双集群容灾复制

目标：生产集群（dc1）实时复制订单主题到灾备集群（dc2），并在故障时快速切换消费。

```shell
# 1. 启动 MirrorMaker 2 复制 dc1 → dc2
bin/connect-mirror-maker.sh config/connect-mirror-maker.properties

# 2. 在 dc2 验证复制后的 Topic 与消费组
bin/kafka-topics.sh --bootstrap-server dc2-kafka:9092 --list | grep '^dc1\.'
bin/kafka-consumer-groups.sh --bootstrap-server dc2-kafka:9092 \
  --describe --group dc1.order-consumer-group

# 3. 容灾切换：把消费应用指向 dc2，从复制 Offset 继续消费
#    消费主题改为 dc1.order.pay.success，group.id 保持原值
```

## 最佳实践与踩坑记录

### 最佳实践

1. 数据集成优先用 Kafka Connect，避免为每个同步需求手写胶水代码，统一运维与监控。
2. Schema 一律纳入 Schema Registry 管理，生产端设置 BACKWARD 兼容，防止破坏下游消费者。
3. CDC 必须开启数据库日志（ROW 格式 binlog / WAL），并给连接器账号最小权限（只读 + 复制权限）。
4. Debezium 首次快照会锁表，大表用 `snapshot.mode=when_needed` 或分时快照，避免影响业务库。
5. MirrorMaker 只复制必要 Topic，用 `topics` 正则收敛范围，避免无关数据拖垮目标集群。
6. 生产集群强制启用 SASL_SSL + ACL，按最小权限给每个客户端账号授权，禁用匿名访问。
7. 跨集群复制注意 Offset 同步与 `offset-syncs.topic` 健康，容灾演练定期验证切换流程。

### 踩坑记录

```text
坑 1：Debezium 首次快照把大表锁住
结论：默认 snapshot.mode=initial 会对表加锁，大表快照期间写入阻塞。
原因：一致性快照需要读锁保证数据一致，表越大锁时间越长。
解法：低峰期执行，或用 snapshot.mode=when_needed 复用已有快照，必要时停业务切换。

坑 2：Schema 变更导致消费者反序列化报错
结论：生产端发布不兼容 Schema 后，旧消费者按新 Schema 解析失败。
原因：消息头 Schema ID 指向新版本，而消费者本地缓存的旧 Schema 不兼容。
解法：Schema Registry 设 BACKWARD 兼容策略，生产端升级前先让消费端升级到兼容版本。

坑 3：MM2 复制后消费组 Offset 不对齐
结论：切换灾备集群后消费位置与源集群不一致，出现重复或丢失。
原因：MM2 的 Offset 同步有延迟，切换瞬间未同步到最新提交位置。
解法：切换前确认 offset-syncs 主题同步到位，业务按唯一键幂等兜底。

坑 4：开启 SSL 后客户端报 CertificateException
结论：客户端不信任 Broker 证书导致握手失败。
原因：Broker 使用了自签名证书，客户端 truststore 未导入该 CA。
解法：把 CA 证书导入客户端 truststore，或统一使用受信 CA 签发。

坑 5：Connect 任务卡死且不重试
结论：Sink 连接器写入失败后任务进入 FAILED，不会自动恢复。
原因：Connect 任务失败默认不自动重启，需手动或通过 REST 重启。
解法：配置 errors.tolerance 与重试策略，监控任务状态并自动重启 FAILED 任务。

坑 6：CDC 连接器账号权限过大或不足
结论：权限不足导致读取日志失败，权限过大存在安全风险。
原因：读取 binlog/WAL 需要 REPLICATION SLAVE 等特定权限。
解法：按 Debezium 文档分配最小权限集，仅授予 SELECT + REPLICATION SLAVE + RELOAD。
```
