## 概述

Kafka 是一个分布式的、基于发布订阅模型的流式消息平台，最初由 LinkedIn 开发并开源。它以「追加写日志」的方式持久化消息，凭借顺序读写、零拷贝与分区并行三大设计，实现了海量数据下的高吞吐与低延迟，成为大数据体系中事实标准的数据总线。

```text
核心特征：
- 分布式：多 Broker 组成集群，水平扩展存储与吞吐
- 持久化：消息落盘（Log），不依赖内存缓存
- 高吞吐：顺序写 + 零拷贝（sendfile）+ 批量读写
- 可回放：Consumer 按 Offset 任意回溯消费
```

## 知识点章节

### Broker

Broker 是 Kafka 集群中的一个服务节点，本质是一个独立的进程（JVM），负责接收生产者写入、服务消费者读取、管理分区副本以及和集群其他节点协调。多个 Broker 组成集群，通过 `broker.id` 区分，元数据由 KRaft 控制器或 ZooKeeper 维护。

```text
要点：
- 一个 Broker = 一个 Kafka 服务进程 = 一个节点
- broker.id 在集群内唯一
- Broker 承担分区 Leader 的读写职责
- 生产建议单机一个 Broker 实例，独立磁盘
```

```shell
# 启动一个 Broker（KRaft 模式，单节点）
export KAFKA_HEAP_OPTS="-Xmx1g -Xms1g"
bin/kafka-server-start.sh -daemon config/server.properties
# 查看 Broker 元数据（KRaft）
bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status
```

### Topic

Topic 是消息的逻辑分类，类似数据库中的「表」或文件系统中的「文件夹」。生产者向指定 Topic 写消息，消费者订阅 Topic 读消息，一个 Topic 在物理上被切分为若干 Partition 以支持并行。

```text
要点：
- Topic 是逻辑概念，Partition 是物理概念
- 命名建议：业务域.模块.事件，如 order.pay.success
- 每个 Topic 可配置分区数、副本数、保留策略
```

```shell
# 创建 3 分区 3 副本的 Topic
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic order.pay.success --partitions 3 --replication-factor 3
# 列出全部 Topic / 查看详情
bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic order.pay.success
```

### Partition

Partition 是 Topic 的物理分片，每个分区是一个有序的、不可变的消息序列，内部用自增 Offset 标识消息位置。分区是 Kafka 并行度的基本单位：分区数决定了单 Topic 的最大消费与写入并行度，分区之间消息无全局顺序保证。

```text
要点：
- 分区内有序，跨分区无序
- 分区数决定吞吐上限与消费并行度
- 分区数只能增加不能减少
- 消息按 key 哈希（或轮询）路由到具体分区
```

```shell
# 扩容分区（不能缩容）
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic order.pay.success --partitions 6
```

### Replica

Replica 是分区的副本，同一个分区的多个副本分布在不同的 Broker 上，用于容灾。副本分为 Leader 与 Follower，`replication.factor` 决定副本数量，副本数不能超过 Broker 数。

```text
要点：
- 副本数 = replication-factor，建议 ≥ 3
- 副本分布在不同 Broker，避免单点故障
- Leader 负责读写，Follower 只做同步备份
- 副本是「多副本」机制的最小单元
```

```yaml
# 创建 Topic 时指定副本数与分区数
# config/topic-create.yaml（示意）
topic: order.pay.success
partitions: 3
replication-factor: 3
min.insync.replicas: 2
```

### Producer

Producer 是消息生产者，负责把消息发送到指定 Topic 的某个分区。Producer 内部包含序列化器、分区器、批量发送缓冲与重试机制，默认异步批量发送以换取高吞吐。

```text
要点：
- 通过 key 决定分区，无 key 则轮询
- 内置 acks、retries、batch 等可靠性与吞吐参数
- 发送是异步的，调用 send 返回 Future
```

```java
import org.apache.kafka.clients.producer.*;
import java.util.Properties;
public class SimpleProducer {
    public static void main(String[] args) {
        Properties p = new Properties();
        p.put("bootstrap.servers", "localhost:9092");
        p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        try (KafkaProducer<String, String> producer = new KafkaProducer<>(p)) {
            producer.send(new ProducerRecord<>("order.pay.success", "k1", "v1"));
        }
    }
}
```

### Consumer

Consumer 是消息消费者，通过订阅 Topic 拉取消息。消费者属于某个消费者组，以「拉模式」（poll）从 Broker 主动拉取数据，消费进度通过 Offset 记录，支持回溯与重复消费。

```text
要点：
- 拉模式（poll），消费速率由消费者自己控制
- 每个分区同一时刻只能被组内一个消费者消费
- 消费是幂等可重放的，进度靠 Offset 保存
```

```java
import org.apache.kafka.clients.consumer.*;
import java.time.Duration;
import java.util.*;
public class SimpleConsumer {
    public static void main(String[] args) {
        Properties p = new Properties();
        p.put("bootstrap.servers", "localhost:9092");
        p.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        p.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        p.put("group.id", "order-consumer-group");
        try (KafkaConsumer<String, String> c = new KafkaConsumer<>(p)) {
            c.subscribe(List.of("order.pay.success"));
            while (true) {
                for (ConsumerRecord<String, String> r : c.poll(Duration.ofMillis(100))) {
                    System.out.println(r.key() + "=" + r.value());
                }
            }
        }
    }
}
```

### Group

消费者组是 Kafka 消费模型的核心：同一组内的消费者共同消费订阅的 Topic，组内不同消费者分摊不同分区，实现水平扩展与负载均衡；不同组之间相互独立，各自维护消费进度。

```text
要点：
- 组内消费者数 ≤ 分区数才有意义（多出的会空闲）
- 不同 Group 可重复消费同一 Topic（广播语义）
- 组协调靠 group.id 与 Consumer Group Coordinator
```

```shell
# 查看消费者组及其消费进度
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-consumer-group
```

### Offset

Offset 是分区内消息的唯一顺序编号（从 0 开始递增），也是消费进度的核心载体。消费者通过提交 Offset 记录「消费到哪了」，Broker 端在 `__consumer_offsets` 内部 Topic 中保存每个组的提交位置。

```text
要点：
- Offset 是分区内自增整数，标识消息位置
- 提交位置存于 __consumer_offsets 内部主题
- 提交方式：自动提交 / 手动同步 / 手动异步
- 可 seek 到任意 Offset 回溯或跳过消息
```

```shell
# 查看组消费进度（CURRENT-OFFSET / LOG-END-OFFSET / LAG）
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-consumer-group
# 重置消费位置到最早
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group order-consumer-group --topic order.pay.success --reset-offsets --to-earliest --execute
```

### Log

Log 是分区在磁盘上的物理存储抽象：一个分区对应一个 Log，Log 由若干 Segment 文件构成，消息以追加方式写入当前活跃 Segment。Log 采用顺序写，配合 Page Cache 与零拷贝获得极高性能。

```text
要点：
- 一个分区 = 一个 Log 目录（如 order.pay.success-0）
- Log 只追加写，不修改、不随机写
- 老 Segment 按保留策略（时间/大小）清理
```

```shell
# 查看分区日志目录结构
ls -la /var/lib/kafka/data/order.pay.success-0/
# 输出：00000000000000000000.log / .index / .timeindex 等
```

### Segment

Segment 是 Log 的滚动分片文件，默认 1GB 或按时间滚动成一个新文件。每个 Segment 由一个 `.log` 数据文件、`.index` 偏移索引和 `.timeindex` 时间索引组成，Segment 使日志可分段清理与快速定位。

```text
要点：
- 默认 log.segment.bytes=1GB 滚动
- 命名规则：以起始 Offset 命名的 20 位数字
- 清理以 Segment 为单位，非活跃段才可删除/压缩
- 活跃段是当前正在写入的最后一个 Segment
```

```yaml
# 关键段参数
log.segment.bytes: 1073741824      # 1GB 滚动
log.retention.hours: 168            # 保留 7 天
log.retention.bytes: -1             # 不按大小限制
log.cleanup.policy: delete          # delete / compact
```

### Index

Index 是 Segment 的稀疏索引文件，用于加速消息查找。偏移索引记录「相对 Offset → 物理位置」的映射，时间索引记录「时间戳 → 相对 Offset」，通过二分查找快速定位消息，避免顺序扫描整个 Segment。

```text
要点：
- .index 存 offset→position 稀疏映射
- .timeindex 存 timestamp→offset 映射
- 稀疏写入（log.index.interval.bytes 控制）
- 定位消息：二分索引 + 顺序扫描小范围
```

```shell
# 解析 Segment 数据（查看消息内容与索引）
bin/kafka-dump-log.sh --files /var/lib/kafka/data/order.pay.success-0/00000000000000000000.log
bin/kafka-dump-log.sh --index-sanity-check \
  --files /var/lib/kafka/data/order.pay.success-0/00000000000000000000.index
```

### ISR

ISR（In-Sync Replicas，同步副本集合）是与 Leader 保持同步的副本集合，Leader 本身也在 ISR 中。当 Follower 落后超过 `replica.lag.time.max.ms` 时会被移出 ISR，追上后重新加入；`min.insync.replicas` 与 acks 配合决定写入的可用性下限。

```text
要点：
- ISR 是「跟上 Leader 进度」的副本集合
- 落后判定：replica.lag.time.max.ms（默认 30s）
- min.insync.replicas 决定最小确认副本数
- ISR 收缩会触发部分副本不可用，需监控
```

```shell
# 查看分区 Leader/Replicas/ISR 分布
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic order.pay.success
# 输出列：Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
```

### Leader-Follower

每个分区的副本中只有一个 Leader 对外提供读写，其余副本为 Follower。Follower 持续从 Leader 拉取消息同步数据，当 Leader 宕机时，控制器会从 ISR 中选举新 Leader 完成故障转移。

```text
要点：
- Leader 负责读写，Follower 被动同步
- Follower 通过 Fetch 请求持续复制数据
- Leader 故障 → 从 ISR 中选新 Leader
```

```shell
# 观察分区 Leader 变更（选举）
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic order.pay.success
```

### Replication

Replication 是副本间数据同步机制：Follower 定期向 Leader 发 Fetch 请求拉取新数据，通过 HW（High Watermark）与 LEO（Log End Offset）两个水位线保证只有被 ISR 确认的消息才对消费者可见。副本机制保证 `replication-factor - 1` 个节点故障仍不丢数据。

```text
要点：
- LEO：本副本日志末尾位置；HW：已提交可见位置
- 消息只有推进到 HW 才对 Consumer 可见
- acks=all 等待所有 ISR 副本确认才返回
```

### KRaft

KRaft 是 Kafka 自 2.8 引入、3.x 起替代 ZooKeeper 的新一代元数据架构，把元数据管理直接内置于 Kafka 内部，通过 Raft 协议选举控制器并维护元数据日志，解决了 ZooKeeper 模式的元数据瓶颈与部署复杂度。

```text
要点：
- 3.3+ 支持生产可用，3.5+ 正式移除 ZooKeeper
- 控制器进程内嵌，基于 Raft 选主
- 元数据以内部日志 __cluster_metadata 存储
```

```shell
# 初始化 KRaft 存储并生成集群 UUID
bin/kafka-storage.sh random-uuid
bin/kafka-storage.sh format -t <UUID> -c config/server.properties
# 启动 KRaft 模式的 Broker
bin/kafka-server-start.sh -daemon config/server.properties
```

## 应用场景实战

### 场景一：从零搭建一个三节点 KRaft 集群

目标：在一台机器上用三个端口模拟三个 Broker，创建带 3 副本的 Topic，验证副本分布与 ISR。

```shell
# 1. 复制三份配置，分别改端口与日志目录
for i in 1 2 3; do
  cp config/server.properties config/server-$i.properties
done
# 2. 修改 server-1/2/3 的关键项（示意）
#    broker.id=1 / 2 / 3
#    listeners=PLAINTEXT://:9092 / 9093 / 9094
#    log.dirs=/var/lib/kafka/data-1 / data-2 / data-3
#    controller.quorum.voters=1@localhost:9092,2@localhost:9093,3@localhost:9094
# 3. 初始化并启动三个节点
bin/kafka-storage.sh random-uuid > /tmp/uid
bin/kafka-storage.sh format -t $(cat /tmp/uid) -c config/server-1.properties
bin/kafka-storage.sh format -t $(cat /tmp/uid) -c config/server-2.properties
bin/kafka-storage.sh format -t $(cat /tmp/uid) -c config/server-3.properties
bin/kafka-server-start.sh -daemon config/server-1.properties
bin/kafka-server-start.sh -daemon config/server-2.properties
bin/kafka-server-start.sh -daemon config/server-3.properties
# 4. 创建 3 副本 Topic 并查看 Leader 与 ISR 分布
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic demo.trade --partitions 3 --replication-factor 3
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic demo.trade
```

### 场景二：消息写入、回溯与副本故障演练

目标：用控制台工具完成端到端读写，验证 Offset 回溯与副本 Leader 切换行为。

```shell
# 1. 生产消息
bin/kafka-console-producer.sh --bootstrap-server localhost:9092 \
  --topic demo.trade --property parse.key=true --property key.separator=:
# 交互输入：  order:1001  order:1002  （Ctrl+C 退出）
# 2. 消费并打印分区与 Offset
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic demo.trade --from-beginning \
  --property print.key=true --property print.partition=true --property print.offset=true
# 3. 停掉一个 Broker 观察 ISR 收缩与 Leader 迁移
bin/kafka-server-stop.sh config/server-2.properties
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic demo.trade
# 4. 验证数据完整性：重启节点后重新消费，确认消息仍在
bin/kafka-server-start.sh -daemon config/server-2.properties
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic demo.trade --from-beginning --timeout-ms 3000
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分区数按「目标吞吐 / 单分区吞吐」估算，单分区吞吐约 10~50 MB/s，先评估再定分区数。
2. 生产环境副本数一律设为 3，并配置 `min.insync.replicas=2`，配合 `acks=all` 保证不丢。
3. 按业务域规划 Topic 命名（域.模块.事件），避免一个 Topic 塞入多类事件造成消费耦合。
4. 分区是并行度上限，但过多分区会增加元数据开销与故障恢复时间，避免盲目上千分区。
5. 保留策略按数据价值配置 `retention.ms` 与 `retention.bytes`，重要链路启用日志压缩（compact）。
6. 监控每个分区的 ISR 收缩、Under-Replicated 分区数与消费 Lag，ISR 频繁抖动通常是磁盘或网络问题。
7. 新集群优先采用 KRaft 模式，ZooKeeper 模式仅在存量迁移场景保留。

### 踩坑记录

```text
坑 1：副本数大于 Broker 数导致 Topic 创建失败
结论：replication-factor 不能超过可用 Broker 数量，否则创建报错。
原因：副本必须分布在不同 Broker，无法把同一分区的两个副本放在同一节点。
解法：先扩容 Broker 数量，或将 replication-factor 降到 ≤ Broker 数。
坑 2：ISR 频繁收缩导致 acks=all 写入变慢或失败
结论：Follower 落后超过 replica.lag.time.max.ms 会被踢出 ISR。
原因：磁盘 IO 抖动、网络延迟或 Follower 消费能力不足导致同步滞后。
解法：增大 replica.lag.time.max.ms 或 replica.fetch.wait.max.ms，排查磁盘/网络瓶颈。
坑 3：重启 Broker 后分区长时间不可用
结论：控制器选举与元数据恢复需要时间，期间该 Broker 上的 Leader 不可写。
原因：unclean.leader.election.enable 默认关闭，ISR 为空时拒绝选主，宁可用性受损也不丢数据。
解法：保持 ISR 健康，避免长时间停节点；必要时开启 unclean 选举（牺牲一致性）。
坑 4：误用 --delete 删 Topic 但数据仍在
结论：Topic 删除是异步的，且需 delete.topic.enable=true 才真正执行。
原因：删除走后台清理线程，物理 Segment 文件延迟删除。
解法：删除后轮询 --list 确认，必要时手动清理 log.dirs 下残留目录。
坑 5：把业务顺序依赖寄托在跨分区有序
结论：Kafka 只保证单分区有序，跨分区不保证顺序。
原因：多个分区并行写入与消费，天然无全局顺序。
解法：需要全局顺序时用单分区，或按 key 路由让同类消息进同一分区。
```
