## 概述

Producer 是 Kafka 的消息生产客户端，负责把业务数据序列化后按分区策略发送到 Broker。它通过「批量 + 压缩 + 异步」三件套在吞吐上做到极致，又通过 acks、重试、幂等与事务在可靠性上提供从「至多一次」到「精确一次」的多档语义，是 Kafka 生态中被调优最频繁的组件。

```text
核心能力：
- 异步发送：send 立即返回，后台批量投递
- 批量缓冲：按时间/大小聚合消息成 Batch
- 可靠性：acks + retries + idempotence 组合
- 精确一次：事务跨分区保证原子性
```

## 知识点章节

### Batch

Batch 是 Producer 端聚合多条消息后一次性发送的批量单元。Producer 内部用 `RecordAccumulator` 按分区缓冲消息，当满足 `linger.ms` 或 `batch.size` 任一条件时，把同一分区的缓冲刷成一个 Batch 发往 Broker，用一次网络往返换取多条消息的吞吐。

```text
要点：
- batch.size：单个 Batch 的最大字节数（默认 16KB）
- linger.ms：等待凑批的最大延迟（默认 0，即立即发送）
- 同一分区才可凑批，跨分区不合并
- 增大 batch 可提高吞吐，但增加端到端延迟
```

```java
Properties p = new Properties();
p.put("bootstrap.servers", "localhost:9092");
p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
// 批量配置：32KB 批 + 最多等 10ms 凑批
p.put("batch.size", 32768);
p.put("linger.ms", 10);
KafkaProducer<String, String> producer = new KafkaProducer<>(p);
```

### Compression

Compression 是 Producer 端对 Batch 的压缩能力，可选 gzip、snappy、lz4、zstd 等。压缩在 Broker 端原样存储，由 Consumer 解压，既节省网络带宽又节省磁盘空间，代价是消耗一定的 CPU。

```text
要点：
- compression.type 可选 none/gzip/snappy/lz4/zstd
- 压缩粒度是 Batch，凑批越大压缩率越高
- lz4/zstd 压缩比与速度均衡，生产最常用
- Broker 默认不解压（compression.type=producer 透传）
```

```java
Properties p = new Properties();
p.put("bootstrap.servers", "localhost:9092");
p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("compression.type", "lz4");      // 生产常用 lz4
p.put("batch.size", 65536);            // 大 Batch 提升压缩率
KafkaProducer<String, String> producer = new KafkaProducer<>(p);
```

### Acks

Acks 控制 Producer 认为「写入成功」需要多少个副本确认，是可靠性与延迟的核心权衡开关。`acks=0` 不等待确认（最快最易丢），`acks=1` 等 Leader 确认（默认），`acks=all` 等所有 ISR 副本确认（最可靠）。

```text
要点：
- acks=0：不等待，可能丢消息，吞吐最高
- acks=1：Leader 落盘即返回，Leader 宕机可能丢
- acks=all：全部 ISR 确认才返回，配合 min.insync.replicas
- 生产默认 acks=all + min.insync.replicas=2
```

```java
Properties p = new Properties();
p.put("bootstrap.servers", "localhost:9092");
p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("acks", "all");                   // 等待所有 ISR 确认
p.put("enable.idempotence", true);      // acks=all 时默认开启幂等
KafkaProducer<String, String> producer = new KafkaProducer<>(p);
```

### Retry

Retry 是 Producer 对可重试异常的自动重发机制。网络抖动、Leader 切换等临时错误会触发重试，配合 `retries` 与 `retry.backoff.ms` 控制重试次数与间隔；为避免重试打乱分区内顺序，Kafka 默认开启幂等（`max.in.flight.requests.per.connection` 限制）。

```text
要点：
- retries 默认 int 最大值（新版本），旧版本默认 0
- retry.backoff.ms 默认 100ms，指数退避
- 可重试：超时、NotLeader、网络异常
- 不可重试：序列化失败、消息过大（RecordTooLarge）
```

```java
Properties p = new Properties();
p.put("bootstrap.servers", "localhost:9092");
p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("retries", 3);                       // 最多重试 3 次
p.put("retry.backoff.ms", 200);            // 重试间隔 200ms
p.put("delivery.timeout.ms", 120000);      // 含重试的总投递超时
KafkaProducer<String, String> producer = new KafkaProducer<>(p);
```

### Idempotence

Idempotence 是 Producer 的幂等能力：给每条消息分配 ProducerID + 序列号，Broker 据此去重，保证「重试不会产生重复消息」。开启后在同一会话内对同一分区做到「至少一次 + 不重复」，即单分区内精确一次。

```text
要点：
- enable.idempotence=true 开启（acks=all 时默认开）
- 靠 PID（ProducerID）+ 递增 sequence 去重
- 只保证单 Producer 单会话单分区内不重复
- 跨会话、跨分区仍需事务才能精确一次
```

```java
Properties p = new Properties();
p.put("bootstrap.servers", "localhost:9092");
p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("acks", "all");
p.put("enable.idempotence", true);   // 开启幂等，需 acks=all
KafkaProducer<String, String> producer = new KafkaProducer<>(p);
```

### Transaction

Transaction 让 Producer 能把多条跨分区的消息作为一个原子单元提交，配合 Consumer 的 `read_committed` 实现端到端精确一次。开启事务后必须用 `beginTransaction`、`sendOffsetsToTransaction`、`commitTransaction` 控制事务边界，需要 `transactional.id`。

```text
要点：
- 需要唯一 transactional.id（跨重启保持）
- 流程：initTransactions → begin → send → commit/abort
- 与消费者配合时 sendOffsetsToTransaction 原子提交 offset
- 幂等是事务的前置条件，事务覆盖幂等
```

```java
import org.apache.kafka.clients.producer.*;
import java.util.Properties;
public class TxProducer {
    public static void main(String[] args) {
        Properties p = new Properties();
        p.put("bootstrap.servers", "localhost:9092");
        p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        p.put("transactional.id", "order-tx-producer-1");  // 唯一事务 ID
        KafkaProducer<String, String> producer = new KafkaProducer<>(p);
        producer.initTransactions();
        try {
            producer.beginTransaction();
            producer.send(new ProducerRecord<>("order.pay.success", "o1", "paid"));
            producer.send(new ProducerRecord<>("order.log", "o1", "log"));
            producer.commitTransaction();
        } catch (Exception e) {
            producer.abortTransaction();
        } finally {
            producer.close();
        }
    }
}
```

## 应用场景实战

### 场景一：高吞吐异步发送 + 回调统计

目标：批量发送 10 万条日志，开启压缩与幂等，通过回调统计成功与失败数。

```java
import org.apache.kafka.clients.producer.*;
import java.util.Properties;
import java.util.concurrent.atomic.AtomicLong;
public class HighThroughputProducer {
    public static void main(String[] args) {
        Properties p = new Properties();
        p.put("bootstrap.servers", "localhost:9092");
        p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        p.put("acks", "all");
        p.put("compression.type", "lz4");
        p.put("batch.size", 65536);
        p.put("linger.ms", 5);
        p.put("buffer.memory", 33554432);   // 32MB 缓冲
        KafkaProducer<String, String> producer = new KafkaProducer<>(p);
        AtomicLong ok = new AtomicLong(), fail = new AtomicLong();
        for (int i = 0; i < 100_000; i++) {
            producer.send(new ProducerRecord<>("app.log", "key-" + i, "msg-" + i),
                (meta, e) -> {
                    if (e == null) ok.incrementAndGet();
                    else fail.incrementAndGet();
                });
        }
        producer.flush();
        System.out.println("ok=" + ok.get() + " fail=" + fail.get());
        producer.close();
    }
}
```

### 场景二：订单事务写入两个 Topic

目标：一笔订单的「支付成功」与「流水日志」必须同时成功或同时失败，用事务保证原子性。

```java
import org.apache.kafka.clients.producer.*;
import java.util.Properties;
public class OrderTxProducer {
    public static void main(String[] args) {
        Properties p = new Properties();
        p.put("bootstrap.servers", "localhost:9092");
        p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        p.put("transactional.id", "order-service-001");
        KafkaProducer<String, String> producer = new KafkaProducer<>(p);
        producer.initTransactions();
        String orderId = "ORDER-20260814-001";
        try {
            producer.beginTransaction();
            producer.send(new ProducerRecord<>("order.pay.success", orderId, "{\"amount\":99.9}"));
            producer.send(new ProducerRecord<>("order.accounting", orderId, "{\"type\":\"debit\"}"));
            producer.commitTransaction();
            System.out.println("事务提交成功: " + orderId);
        } catch (Exception e) {
            producer.abortTransaction();
            System.err.println("事务回滚: " + orderId);
        } finally {
            producer.close();
        }
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产默认 `acks=all` + `enable.idempotence=true`，可靠性优先，吞吐可后续按需放开。
2. 压缩首选 `lz4` 或 `zstd`，配合 32KB 以上的 `batch.size` 与 5~10ms 的 `linger.ms` 提升压缩率。
3. 消息大小按 `max.request.size` 与 Broker 端 `message.max.bytes` 双重限制，大报文走对象存储 + 引用。
4. 分区策略显式指定 key，让同类业务（如同一订单）落到同一分区，保证局部有序与关联。
5. 回调中只做轻量统计与日志，避免在回调里做耗时 IO 阻塞发送线程。
6. 监控 `record-send-rate`、`record-error-rate`、`batch-size-avg` 与 `bufferpool-wait-time` 四个核心指标。
7. 需要跨分区/跨 Topic 原子性时用事务，但要意识到事务会增加延迟并降低吞吐约 20%~30%。

### 踩坑记录

```text
坑 1：开启幂等却把 retries 设很大导致消息顺序乱
结论：老版本中 retries>0 且 max.in.flight>1 时重试可能打乱顺序。
原因：多条在途请求并发重试，后发先至覆盖先发消息的位置。
解法：新版本开启幂等后自动约束 in-flight=5 且保序；否则把 max.in.flight.requests.per.connection 设为 1。
坑 2：acks=all 写入偶发超时但消息其实已落盘
结论：Leader 已写入但确认响应丢失，Producer 触发重试造成重复。
原因：网络抖动导致响应丢失，客户端误判失败而重发。
解法：开启幂等去重；或业务侧设计为幂等消费（唯一键去重）。
坑 3：linger.ms 设太大导致延迟飙升
结论：凑批等待时间过长，低流量场景端到端延迟显著增加。
原因：linger.ms 是每条消息最多等待的时间，与 batch.size 联动。
解法：按延迟预算设定 linger.ms，低延迟链路设 0~5ms，吞吐链路设 10~50ms。
坑 4：消息超过 max.request.size 抛 RecordTooLargeException
结论：单条消息或单个 Batch 超过限值直接失败，重试无效。
原因：默认 max.request.size=1MB，Broker 端 message.max.bytes 默认约 1MB。
解法：大报文拆分或改用对象存储外链；确需调大需同步调 Broker 与 Consumer 两端参数。
坑 5：未配置 transactional.id 直接 initTransactions 报错
结论：使用事务必须先设置唯一 transactional.id，否则抛 ConfigException。
原因：事务靠 transactional.id 识别生产者实例并恢复未完成事务。
解法：为每个事务生产者分配稳定且全局唯一的 transactional.id。
```
