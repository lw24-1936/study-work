## 概述

分布式系统的一切协作都建立在网络上：HDFS 的数据复制、Spark 的 Shuffle、Kafka 的生产消费、各组件间的 RPC 调用，全是网络通信。理解 TCP 的可靠传输、IP 的路由、HTTP 的应用协议、DNS 的解析、TLS 的加密、负载均衡与 CDN 的分流，才能理解大数据系统的性能瓶颈（网络带宽、延迟、连接数）和故障（分区、丢包、超时）。

```text
网络分层与大数据的关系：
应用层（HTTP/RPC） -> 传输层（TCP/UDP） -> 网络层（IP） -> 链路层
大数据组件：Kafka 用 TCP、HDFS 用 RPC、Shuffle 用 TCP 长连接。
```

## TCP

TCP（传输控制协议）提供可靠的、面向连接的字节流传输，靠三次握手建立连接、四次挥手断开、确认重传保证可靠、滑动窗口做流量控制、拥塞控制避免网络拥塞。大数据组件几乎都跑在 TCP 上（Kafka、HDFS、Spark Shuffle），TCP 的连接管理、缓冲区和 Nagle 算法直接影响吞吐与延迟。

```text
TCP 要点：
1. 三次握手 —— SYN -> SYN+ACK -> ACK，建立连接；四次挥手断开
2. 可靠传输 —— 序列号 + 确认 + 超时重传，保证不丢不乱
3. 滑动窗口 —— 流量控制，接收方窗口大小限制发送速率
4. 拥塞控制 —— 慢启动、拥塞避免，防止打爆网络
5. TIME_WAIT —— 主动关闭方等 2MSL，大量短连接会堆积该状态
```

```shell
# 观察 TCP 连接状态
ss -tan | awk '{print $1}' | sort | uniq -c

# 用 tcpdump 抓 TCP 三次握手
tcpdump -i any tcp and port 9092 -c 20

# 调整 TCP 参数（高吞吐场景）
sysctl -w net.core.somaxconn=4096
sysctl -w net.ipv4.tcp_tw_reuse=1
```

## IP

IP（网际协议）负责跨网络的主机寻址与路由，是无连接、尽力而为的协议——不保证送达、不保证顺序。IP 地址（IPv4/IPv6）标识主机，路由表决定数据包怎么跳转。大数据集群里，IP 与主机名映射、网段规划、跨机架带宽都是 IP 层的现实问题。TCP 建立在 IP 之上，弥补 IP 的不可靠。

```text
IP 要点：
1. 寻址 —— IP 地址唯一标识主机，子网掩码划分网段
2. 路由 —— 路由器按路由表转发，跨网段通信
3. 无连接 —— 尽力而为，可靠交给上层 TCP
4. 私网 —— 10.x/172.16.x/192.168.x 私有地址，集群内网互访
```

```shell
# 查看 IP 与路由
ip addr show
ip route show

# 追踪路由路径
traceroute 8.8.8.8

# 测试主机名解析与连通
ping -c 3 node2
```

## HTTP

HTTP（超文本传输协议）是应用层协议，基于请求-响应模型，方法有 GET/POST/PUT/DELETE，状态码 2xx 成功/3xx 重定向/4xx 客户端错/5xx 服务端错。REST API 是大数据系统对外交互的主流（HDFS WebHDFS、Kafka REST Proxy、各种组件的管理 API）。HTTP/1.1 复用连接、HTTP/2 多路复用、HTTP/3 基于 QUIC/UDP。

```text
HTTP 要点：
1. 请求行 —— 方法 + 路径 + 版本；头 + 空行 + body
2. 状态码 —— 200 OK、301/302 重定向、404 不存在、500 服务错误
3. 幂等性 —— GET/PUT/DELETE 幂等，POST 不幂等，重试时要区分
4. 版本 —— 1.1 长连接、2 多路复用、3 QUIC 减少握手
```

```shell
# 用 curl 调试 HTTP API
curl -i http://localhost:9870/webhdfs/v1/?op=LISTSTATUS
curl -X GET -H "Content-Type: application/json" http://localhost:8080/api/health
curl -X POST -d '{"name":"demo"}' -H "Content-Type: application/json" http://localhost:8080/api/topic
```

## HTTPS

HTTPS = HTTP + TLS 加密，解决 HTTP 明文传输的窃听、篡改、冒充三大问题。握手阶段用非对称加密协商对称密钥，之后用对称加密传输数据（兼顾安全与性能）。大数据平台对外暴露的 API、管控面、对象存储访问都用 HTTPS。证书由 CA 签发，验证服务器身份。

```text
HTTPS 要点：
1. 加密 —— 非对称（RSA/ECDHE）协商密钥 + 对称（AES）加密数据
2. 证书 —— CA 签发，含公钥与域名，验证服务器身份
3. 握手 —— ClientHello -> ServerHello -> 证书 -> 密钥交换，多一次 RTT
4. 端口 —— 默认 443，与 HTTP 的 80 区分
```

```shell
# 用 openssl 查看 HTTPS 证书
echo | openssl s_client -connect www.example.com:443 -servername www.example.com 2>/dev/null | openssl x509 -noout -subject -dates

# 用 curl 忽略/验证证书
curl -k https://self-signed.example.com   # 忽略证书校验（仅测试）
curl https://example.com/api/health       # 正常校验证书
```

## DNS

DNS（域名系统）把域名解析成 IP 地址，是「分布式系统的地址簿」。解析过程：浏览器/客户端 -> 本地缓存 -> 递归 DNS 服务器 -> 根域 -> 顶级域 -> 权威 DNS，逐级查询。大数据里，主机名与 IP 的映射（/etc/hosts 或内部 DNS）决定节点互访；DNS 故障会表现为「连不上、解析慢」，是常见故障源。

```text
DNS 要点：
1. 层级 —— 根 -> 顶级域(.com) -> 权威域，逐级委托
2. 记录类型 —— A（域名到 IPv4）、AAAA（IPv6）、CNAME（别名）、MX（邮件）
3. 缓存 —— 各级缓存加速，但改 DNS 后要等 TTL 过期
4. 内部 DNS —— 集群内主机名互访靠 /etc/hosts 或内网 DNS
```

```shell
# 解析域名
dig www.example.com
nslookup www.example.com
host www.example.com

# 指定 DNS 服务器查询
dig @8.8.8.8 www.example.com

# 修改本地 hosts（集群节点互访）
echo "192.168.1.10 node1" >> /etc/hosts
```

## TLS

TLS（传输层安全协议）是 HTTPS 的底层加密协议，提供机密性（加密）、完整性（防篡改）、身份认证（证书）三大保障。握手协商协议版本、加密套件、交换密钥；之后用对称加密高效传输。TLS 1.2 是主流，TLS 1.3 简化握手（1-RTT）并废弃弱算法。大数据组件间通信（Kafka SSL、HDFS 加密）也用 TLS。

```text
TLS 要点：
1. 三大保障 —— 机密性（对称加密）、完整性（MAC/HMAC）、认证（证书链）
2. 握手 —— 协商版本/套件、证书验证、密钥交换（ECDHE 前向保密）
3. 版本 —— TLS 1.2 主流，1.3 更快更安全，禁用 SSLv3/TLS1.0
4. 密钥 —— 会话密钥对称加密，前向保密保证历史数据不因密钥泄露被解密
```

```yaml
# Kafka broker 启用 SSL（server.properties 关键项）
listeners: SSL://:9093
ssl.keystore.location: /var/ssl/kafka.keystore.jks
ssl.keystore.password: changeit
ssl.key.password: changeit
ssl.truststore.location: /var/ssl/kafka.truststore.jks
ssl.truststore.password: changeit
```

## RPC

RPC（远程过程调用）让调用远程服务像调用本地函数一样，屏蔽网络细节。实现要点是序列化（参数编码）、传输（TCP/HTTP）、服务发现（注册中心）。大数据组件内部大量用 RPC：HDFS 的 NameNode RPC、HBase 的 RPC、gRPC/Thrift 是通用框架。RPC 的核心问题是「如何让跨进程调用透明、高效、可靠」。

```text
RPC 要点：
1. 透明化 —— 本地调用与远程调用接口一致，stub 代理屏蔽网络
2. 序列化 —— 参数/返回值编码，Protobuf/Thrift 高效紧凑
3. 传输 —— TCP 长连接复用，或 HTTP/2（gRPC）
4. 服务发现 —— 注册中心（ZooKeeper/etcd）维护服务地址
```

```text
RPC 调用链路：
客户端 stub -> 序列化请求 -> 网络传输 -> 服务端 stub -> 反序列化 -> 执行 -> 序列化响应 -> 回传
```

```shell
# 用 grpcurl 调试 gRPC 服务（列出方法）
grpcurl -plaintext localhost:50051 list
grpcurl -plaintext localhost:50051 describe package.Service
```

## 负载均衡

负载均衡把流量分发到多个后端实例，提升可用性与吞吐。分四层（L4，按 IP/端口转发，如 LVS、云 SLB）和七层（L7，按 HTTP 内容路由，如 Nginx、HAProxy）。大数据里负载均衡用于：多 NameNode 的客户端访问、Kafka REST、Trino/Presto 协调节点、各种管控 API 的高可用。常见算法：轮询、加权、最少连接、一致性哈希。

```text
负载均衡要点：
1. L4 vs L7 —— L4 按连接转发（快，不看内容），L7 按 URL/Header 路由（灵活）
2. 算法 —— 轮询、加权轮询、最少连接、源地址哈希（会话保持）
3. 健康检查 —— 探测后端存活，自动摘除故障节点
4. 大数据 —— Trino 协调节点、多 NN 联邦、Kafka 多 broker 客户端负载
```

```yaml
# Nginx 七层负载均衡配置
upstream trino_backend {
    least_conn;
    server 192.168.1.10:8080 max_fails=3 fail_timeout=30s;
    server 192.168.1.11:8080 max_fails=3 fail_timeout=30s;
}

server {
    listen 80;
    location / {
        proxy_pass http://trino_backend;
        proxy_set_header Host $host;
    }
}
```

## CDN

CDN（内容分发网络）把静态内容缓存到离用户最近的边缘节点，减少延迟与源站压力。核心是「就近访问 + 缓存 + 回源」。大数据场景里，CDN 服务于数据产品的前端资源、报表、以及面向用户的批量数据下载（如导出文件）。DNS 把用户解析到最近的 CDN 节点，节点有缓存则直接返回，否则回源拉取。

```text
CDN 要点：
1. 边缘节点 —— 全球/全国分布，用户就近访问
2. 缓存 —— 静态资源缓存到边缘，命中率高则源站压力小
3. 回源 —— 缓存未命中时向源站拉取，源站是最终数据源
4. 刷新 —— 内容更新后需刷新缓存或等 TTL 过期
```

```text
CDN 访问流程：
用户 -> DNS 解析到最近边缘节点 -> 命中缓存直接返回 -> 未命中回源拉取并缓存 -> 返回用户
```

## 应用场景实战

### 场景一：排查 Spark Shuffle 阶段的网络瓶颈

```shell
# 1. 观察 Shuffle 阶段网络吞吐
sar -n DEV 1 10

# 2. 观察 TCP 连接数与重传（重传率高说明网络拥塞）
ss -s
nstat -az | grep -i retrans

# 3. 抓包看是否有大量重传/乱序
tcpdump -i any 'tcp[13] & 0x12 != 0' -c 100

# 4. 结论：重传高 -> 网络拥塞/带宽不足，考虑增大带宽或减少 Shuffle 数据量
```

### 场景二：给 Trino 集群配置负载均衡与健康检查

```yaml
# Nginx 负载均衡多个 Trino 协调节点 + 健康检查
upstream trino {
    least_conn;
    server trino-coordinator-1:8080 max_fails=2 fail_timeout=20s;
    server trino-coordinator-2:8080 max_fails=2 fail_timeout=20s;
}

server {
    listen 80;
    location / {
        proxy_pass http://trino;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_read_timeout 600s;
    }
}
```

```shell
# 验证负载均衡生效
for i in $(seq 1 10); do
  curl -s http://trino-lb/v1/info | grep nodeId
done
```

## 最佳实践与踩坑记录

### 最佳实践

1. 短连接频繁建连的服务调大 somaxconn、开启 tcp_tw_reuse，避免 TIME_WAIT 堆积
2. 高吞吐传输关闭 Nagle（TCP_NODELAY），小包低延迟场景尤其重要
3. 对外 API 一律 HTTPS，内部服务间通信也逐步上 TLS
4. DNS 解析失败先查 /etc/hosts 与 resolv.conf，再查内部 DNS 服务
5. 负载均衡配健康检查，故障节点自动摘除，避免请求打到挂掉的实例
6. RPC 用长连接复用 + 高效序列化（Protobuf），避免每次握手
7. 静态资源与大文件下载走 CDN，减轻源站与集群出口压力

### 踩坑记录

```text
坑 1：大量 TIME_WAIT 导致无法新建连接
结论：服务报 Cannot assign requested address，新连接建立失败。
原因：短连接高频建连，主动关闭方堆积大量 TIME_WAIT 状态。
解法：开启 tcp_tw_reuse、调大本地端口范围、改长连接复用。

坑 2：跨机房大文件传输吞吐上不去
结论：单条 TCP 连接传输速度远低于带宽上限。
原因：高延迟（RTT 大）下 TCP 拥塞窗口爬升慢，单连接带宽利用率低。
解法：多连接并行传输、调大 TCP 缓冲、用 UDP/专线加速。

坑 3：HTTPS 证书过期导致服务不可用
结论：客户端握手失败，所有 HTTPS 请求报证书错误。
原因：证书到期未续期，或未配置自动续期。
解法：证书到期监控告警，用 ACME 自动续期（Let's Encrypt）。

坑 4：负载均衡未配健康检查导致请求打到死节点
结论：部分请求超时或失败，用户体验时好时坏。
原因：后端实例挂掉但未从 LB 摘除，流量仍被分发过去。
解法：配置主动健康检查（max_fails + fail_timeout），自动摘除故障节点。
```
