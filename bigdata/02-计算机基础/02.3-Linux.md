## 概述

Linux 是大数据集群的事实标准操作系统——几乎所有 Hadoop/Spark/Flink/Kafka 都跑在 Linux 上。日常运维、排障、部署都离不开 Linux 命令：管进程、控权限、查网络、看日志、配服务自启（systemd）、定时任务（cron）、资源上限（ulimit）。本章按「大数据工程师最常用的 Linux 技能」组织，每项都配可直接执行的命令。

```text
Linux 大数据工程师必备技能：
1. 进程管理 —— ps/top/kill，定位与处理任务进程
2. 权限 —— chmod/chown，控制数据与脚本访问
3. 网络 —— 端口、连通性、流量排查
4. 日志 —— journalctl/tail，服务排障的第一现场
```

## 进程管理

进程管理是排障的起点：用 ps/top 看进程状态与资源占用，用 kill 发信号终止或优雅退出，用 nice 调整优先级。大数据作业往往是长驻的 JVM 进程，掌握「找到进程 -> 看资源 -> 优雅停止」的闭环是基本素养。信号是关键：SIGTERM（15）优雅退出、SIGKILL（9）强杀、SIGSTOP/SIGCONT 暂停恢复。

```text
进程管理要点：
1. ps aux —— 看所有进程，grep 过滤，awk 提取 PID
2. top/htop —— 实时看 CPU/内存占用，按 M/P 排序
3. kill —— 默认发 SIGTERM，-9 强杀，优雅退出留给进程清理资源
4. nice/renice —— 调优先级，后台批处理任务降低优先级避免抢占
```

```shell
# 找到并优雅停止一个 Java 任务
PID=$(pgrep -f "CoarseGrainedExecutorBackend")
kill -15 $PID          # 发 SIGTERM，让进程优雅退出
sleep 5
kill -9 $PID 2>/dev/null || true   # 仍未退出则强杀

# 看进程资源与线程
top -p $PID
ps -o pid,ppid,%cpu,%mem,rss,etime,comm -p $PID

# 后台跑任务并降低优先级
nice -n 10 ./etl_job.sh &
```

## 权限

Linux 权限模型基于「用户/组/其它」三组 + 「读(r)/写(w)/执行(x)」三位，用 chmod/chown 管理。大数据集群多用户共用，权限直接关系到数据安全——谁能读 HDFS 数据、谁能执行脚本。特殊位（setuid/setgid/sticky）和 ACL 用于更细粒度控制。理解 umask 才能预知新建文件的默认权限。

```text
权限要点：
1. 三位权限 —— r=4 w=2 x=1，chmod 755 即 rwxr-xr-x
2. chown —— 改属主属组，chown user:group file
3. umask —— 新建文件默认权限的掩码，默认 022 即新建文件 644
4. 特殊位 —— sticky bit（/tmp，防删他人文件）、setuid（以文件属主身份执行）
5. ACL —— setfacl 给单个用户/组单独授权，突破 u/g/o 三组限制
```

```shell
# 权限操作示例
chmod 755 script.sh          # 属主可读写执行，其它人可读执行
chmod -R 750 /data/warehouse # 递归改目录
chown -R hdfs:hadoop /data/warehouse

# 查看权限与 umask
ls -la /data/warehouse
umask

# ACL：给单个用户单独授权
setfacl -m u:analyst:rx /data/warehouse
getfacl /data/warehouse
```

## 网络

网络排障是分布式系统的重头戏：端口是否监听（ss/netstat）、连通性（ping/telnet/nc）、流量与丢包（tcpdump/iftop）。大数据组件间靠网络通信，端口冲突、防火墙拦截、网络分区是高频故障。掌握「查端口 -> 测连通 -> 抓包」三板斧能定位 80% 的网络问题。

```text
网络排查要点：
1. ss -tlnp —— 看谁在监听哪些 TCP 端口
2. telnet/nc —— 测端口连通性（nc -zv host port）
3. curl —— 测 HTTP 服务可达性与响应
4. tcpdump —— 抓包分析协议细节，定位丢包/重传
```

```shell
# 端口与连通性
ss -tlnp | grep 9092
nc -zv localhost 9092
curl -s http://localhost:8080/health

# 抓包：抓 9092 端口的 TCP 握手
tcpdump -i any port 9092 -c 20

# 查看网络连接与状态统计
ss -s
netstat -tn | awk '{print $6}' | sort | uniq -c
```

## 日志

日志是服务排障的第一现场。传统服务写文本日志到 /var/log（用 tail/fgrep 查看），systemd 管理的服务用 journalctl 查。大数据组件的日志分散在各节点的 logs 目录（如 Spark/Flink 的 executor 日志），排查时按「时间 + 关键字 + 上下文」定位。日志轮转（logrotate）防止磁盘被写满。

```text
日志要点：
1. tail -f —— 实时跟踪日志，排查在线问题
2. journalctl -u xxx —— 查 systemd 服务日志
3. grep -A/-B —— 取关键字前后上下文，还原故障现场
4. logrotate —— 按大小/时间轮转压缩，防止磁盘写满
```

```shell
# 实时跟踪并过滤
tail -f /var/log/app.log | grep --line-buffered "ERROR"

# 查 systemd 服务日志（时间范围 + 关键字）
journalctl -u spark-worker --since "10:00" --until "11:00" | grep -i oom

# 取关键字上下文
grep -B 5 -A 10 "OutOfMemoryError" /var/log/spark/*.log

# logrotate 配置示例
cat > /etc/logrotate.d/app <<'EOF'
/var/log/app/*.log {
    daily
    rotate 7
    compress
    missingok
}
EOF
```

## systemd

systemd 是 Linux 现代初始化系统与服务管理器，负责启动系统、管理服务（启停、自启、依赖）、收集日志。大数据服务（如 HDFS 的 DataNode、Kafka）部署到裸机时，常用 systemd unit 管理，保证开机自启、崩溃自动拉起。核心命令是 systemctl，核心文件是 .service unit。

```text
systemd 要点：
1. unit 类型 —— service（服务）、timer（定时）、socket、target（运行级别）
2. 生命周期 —— systemctl start/stop/restart/enable/disable/status
3. enable —— 开机自启（建软链接到 multi-user.target）
4. Restart —— unit 里 Restart=on-failure 实现崩溃自动拉起
```

```ini
# /etc/systemd/system/kafka.service
[Unit]
Description=Apache Kafka
After=network.target

[Service]
Type=simple
User=kafka
ExecStart=/opt/kafka/bin/kafka-server-start.sh /opt/kafka/config/server.properties
ExecStop=/opt/kafka/bin/kafka-server-stop.sh
Restart=on-failure
LimitNOFILE=100000

[Install]
WantedBy=multi-user.target
```

```shell
# 启用并启动服务
systemctl daemon-reload
systemctl enable kafka
systemctl start kafka
systemctl status kafka
```

## cron

cron 是 Linux 的定时任务调度器，用 crontab 表达式在指定时间执行命令。大数据里常用于定时跑批（每日凌晨跑 ETL）、定时清理过期数据、定时做健康检查。crontab 格式是「分 时 日 月 周」，注意它的环境变量与交互 shell 不同，脚本里要写全路径。cron 适合简单定时，复杂依赖用专门调度器（见 28 章）。

```text
cron 要点：
1. 格式 —— 分(0-59) 时(0-23) 日(1-31) 月(1-12) 周(0-7)，* 表示任意
2. 环境 —— cron 不加载用户 profile，脚本用绝对路径，显式 source 环境
3. 日志 —— 输出重定向到文件，否则丢失；失败不易感知
4. 适用 —— 简单定时任务；复杂 DAG 依赖用 Airflow/DolphinScheduler
```

```shell
# 编辑 crontab
crontab -e

# 每天凌晨 2 点跑 ETL，日志重定向
0 2 * * * /opt/etl/run_etl.sh >> /var/log/etl.log 2>&1

# 每小时做一次健康检查
0 * * * * /opt/ops/health_check.sh

# 查看已配置的定时任务
crontab -l
```

## ulimit

ulimit 设置进程的资源上限——最常用的是文件描述符数（-n）和核心转储（-c）。大数据组件（Kafka、Elasticsearch、Flink）大量开 socket 和文件，默认 1024 的 fd 上限经常不够，需要调高。它是「资源限制」在 shell 层的体现，与 cgroups 互补（ulimit 管数量上限，cgroups 管用量配额）。

```text
ulimit 要点：
1. -n —— 最大打开文件描述符数，网络密集服务要调高（如 100000）
2. -u —— 最大进程/线程数，高并发服务需要调高
3. -c —— core dump 大小，unlimited 便于崩溃后分析
4. 持久化 —— 写进 /etc/security/limits.conf，仅当前 shell 的 ulimit 不持久
```

```shell
# 查看当前限制
ulimit -n      # 文件描述符
ulimit -a      # 全部限制

# 临时调高（当前 shell 生效）
ulimit -n 100000

# 持久化配置
cat >> /etc/security/limits.conf <<'EOF'
kafka  soft  nofile  100000
kafka  hard  nofile  100000
kafka  soft  nproc   65536
EOF
```

## 应用场景实战

### 场景一：部署一个大数据服务为 systemd 服务并配置资源限制

```shell
# 1. 写 unit 文件（以上面 kafka.service 为例）
cat > /etc/systemd/system/kafka.service <<'EOF'
[Unit]
Description=Apache Kafka
After=network.target

[Service]
Type=simple
User=kafka
ExecStart=/opt/kafka/bin/kafka-server-start.sh /opt/kafka/config/server.properties
Restart=on-failure
LimitNOFILE=100000

[Install]
WantedBy=multi-user.target
EOF

# 2. 启用并验证
systemctl daemon-reload && systemctl enable --now kafka
systemctl status kafka

# 3. 验证 fd 限制是否生效
cat /proc/$(systemctl show -p MainPID --value kafka)/limits | grep "open files"
```

### 场景二：搭建每日定时数据清理任务

```shell
# 1. 写清理脚本（删除 30 天前的日志并记录）
cat > /opt/ops/clean_old_logs.sh <<'EOF'
#!/bin/bash
DIR=/data/logs
find $DIR -type f -mtime +30 -name "*.log" -delete
echo "$(date '+%F %T') 清理完成" >> /var/log/cleanup.log
EOF
chmod +x /opt/ops/clean_old_logs.sh

# 2. 配置 cron 每天凌晨 3 点执行
crontab -e
# 加入：0 3 * * * /opt/ops/clean_old_logs.sh >> /var/log/cleanup.log 2>&1

# 3. 验证 cron 是否注册成功
crontab -l
```

## 最佳实践与踩坑记录

### 最佳实践

1. 停止服务先 SIGTERM 优雅退出，超时再 SIGKILL，给进程清理资源的机会
2. 生产服务用 systemd 管理，配 Restart=on-failure 与 LimitNOFILE
3. 大数据组件的 fd 上限至少调到 65536，网络密集服务 100000
4. 日志统一轮转（logrotate），关键日志重定向保留，避免磁盘写满
5. cron 脚本用绝对路径、显式加载环境变量、输出重定向
6. 权限遵循最小化原则，按用户/组分配，敏感数据单独授权
7. 网络排障按「查端口 -> 测连通 -> 抓包」顺序，先易后难

### 踩坑记录

```text
坑 1：服务用 nohup 裸跑，机器重启后不自动拉起
结论：服务挂了或重启后无人拉起，业务中断。
原因：没有纳入 systemd 管理，缺自动拉起与自启机制。
解法：写成 systemd unit，Restart=on-failure + enable 开机自启。

坑 2：Kafka 启动报 Too many open files
结论：高并发下 Kafka 无法新建连接/文件，服务异常。
原因：默认 fd 上限 1024，网络密集的 Kafka 很快耗尽。
解法：limits.conf 和 unit 的 LimitNOFILE 调到 100000 并重启生效。

坑 3：cron 任务不执行且无日志
结论：定时任务静默失败，排查无门。
原因：脚本用了相对路径或依赖交互 shell 的环境变量，且输出未重定向。
解法：脚本用绝对路径、显式 source 环境、输出重定向到日志文件。

坑 4：chmod 777 一把梭导致数据安全隐患
结论：任何用户都能读写数据，存在误删/泄露风险。
原因：图省事用最大权限，破坏最小权限原则。
解法：按属主/组分配权限（如 750），敏感数据用 ACL 单独授权。
```
