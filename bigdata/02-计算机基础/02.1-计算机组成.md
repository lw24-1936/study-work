## 概述

计算机组成研究「一台机器如何把指令和数据变成计算」。对大数据工程师而言，理解 CPU 缓存、内存层级、磁盘 IO 和中断 DMA，直接决定了能不能写出高性能的 Spark/Flink 作业——所谓「计算密集型 vs IO 密集型」「顺序读 vs 随机读」都源于硬件特性。本章讲清各硬件的职责与协作方式，为性能优化（31 章）打基础。

```text
冯诺依曼架构的核心部件协作：
CPU（计算）<-> Cache（高速缓存）<-> 内存（主存）<-> 磁盘/网络（外部 IO）
指令与数据都存内存，CPU 逐条取指、译码、执行。
```

## CPU

CPU（中央处理器）是执行指令的核心，由控制单元（取指译码）、算术逻辑单元 ALU（计算）和寄存器（暂存）组成。性能由主频、核心数、流水线、分支预测、超线程决定。大数据计算多为 CPU 密集型（压缩解压、哈希、序列化），CPU 核心数直接决定任务并行度。现代 CPU 通过指令级并行（超标量）和多核并行提升吞吐。

```text
CPU 关键概念：
1. 主频 —— 每秒时钟周期，决定单指令快慢，但受功耗墙限制不再线性提升
2. 核心数 —— 真正并行执行的任务数，Spark/Flink 的 executor 核数对应它
3. 流水线 —— 把指令拆成多级重叠执行，提升吞吐，分支会打断流水线
4. 超线程 —— 一个物理核模拟两个逻辑核，提升利用但不是真并行
```

```c
// 用 C 演示 CPU 密集型计算：求 1..N 的质数个数
#include <stdio.h>
#include <stdbool.h>

int main() {
    int n = 1000000, count = 0;
    for (int i = 2; i <= n; i++) {
        bool prime = true;
        for (int j = 2; j * j <= i; j++) {
            if (i % j == 0) { prime = false; break; }
        }
        if (prime) count++;
    }
    printf("primes <= %d : %d\n", n, count);
    return 0;
}
```

## GPU

GPU（图形处理器）最初用于图形渲染，因「海量简单核心并行计算」的特性成为通用计算（GPGPU）的主力。CPU 是「少而强」的核心（十几到几十个，擅长复杂逻辑与分支），GPU 是「多而弱」的核心（成千上万个，擅长大规模同质数据并行）。大数据里 GPU 用于加速向量化计算、ML 训练（CUDA）、以及 RAPIDS 等 GPU 数据框架。

```text
CPU 与 GPU 对比：
1. 核心 —— CPU 十几到几十个复杂核心，GPU 成千上万个简单核心
2. 擅长 —— CPU 串行逻辑/分支，GPU 数据并行（矩阵、向量）
3. 吞吐 —— GPU 单精度浮点吞吐远高于 CPU，适合 ML 训练/推理
4. 大数据 —— Spark 3.x 支持 GPU 调度（RAPIDS），加速 SQL/ETL
```

```python
# 用 NumPy 演示 GPU 擅长的向量化并行（在 GPU 上对应 CUDA 内核）
import numpy as np
import time

a = np.random.rand(10_000_000)
b = np.random.rand(10_000_000)
t0 = time.time()
c = a + b          # 向量化：底层一次算 1000 万个元素
print("向量化加法耗时: %.4f 秒" % (time.time() - t0))
```

## 内存

内存（RAM，主存）是 CPU 直接访问的易失性存储，速度远快于磁盘、容量远小于磁盘。数据必须先加载进内存才能被 CPU 计算，所以内存容量决定「一次能装下多少数据」。大数据计算的内存模型（Spark/Flink 的堆内堆外）和「内存不足 OOM」的根源都在这里。内存分堆（JVM heap）、栈（函数调用）、以及堆外内存（Direct Memory）。

```text
内存要点：
1. 易失性 —— 断电丢失，持久化必须落到磁盘
2. 层级 —— L1/L2/L3 Cache -> 主存 -> 磁盘，速度逐级下降、容量逐级上升
3. 堆 vs 栈 —— 对象在堆（GC 管理），局部变量在栈（函数返回自动释放）
4. 大数据 OOM —— 内存不够放中间结果，需调 executor 内存或减少数据量
```

```java
// Java：演示堆内存分配与 OOM 风险
import java.util.ArrayList;
import java.util.List;

public class MemoryDemo {
    public static void main(String[] args) {
        List<byte[]> list = new ArrayList<>();
        try {
            while (true) {
                list.add(new byte[1024 * 1024]); // 每次分配 1MB 堆内存
            }
        } catch (OutOfMemoryError e) {
            System.out.println("堆内存耗尽，已分配 " + list.size() + " MB");
        }
    }
}
```

## Cache

Cache（高速缓存）是 CPU 与主存之间的高速小容量存储器，用「时间局部性 + 空间局部性」原理缓存热点数据。现代 CPU 分 L1/L2（每核私有）/L3（多核共享）三级。缓存命中率决定程序快慢——顺序访问、连续内存布局命中率高，随机访问、跨大步长命中率低。大数据里列式存储、顺序扫描快，正是因为对缓存友好。

```text
Cache 要点：
1. 局部性 —— 时间局部性（刚访问的还会访问）、空间局部性（相邻的也会访问）
2. 缓存行 —— 一次加载 64 字节，连续访问相邻数据命中率高
3. 命中率 —— 顺序读 >> 随机读，这是列式存储、Parquet 快的原因之一
4. 伪共享 —— 多线程写同一缓存行会互相失效，需要 padding 对齐
```

```c
// C：演示顺序访问 vs 随机访问的缓存效应
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define N 100000000

int main() {
    int *arr = (int *)malloc(N * sizeof(int));
    long sum = 0;
    clock_t t0, t1;

    // 顺序访问：缓存友好
    t0 = clock();
    for (int i = 0; i < N; i++) sum += arr[i];
    t1 = clock();
    printf("顺序访问: %ld ms\n", (t1 - t0) * 1000 / CLOCKS_PER_SEC);

    // 大步长随机访问：缓存不友好
    t0 = clock();
    for (int i = 0; i < N; i += 64) sum += arr[i];
    t1 = clock();
    printf("跨步访问: %ld ms\n", (t1 - t0) * 1000 / CLOCKS_PER_SEC);

    free(arr);
    return 0;
}
```

## 磁盘

磁盘是持久化存储，分机械硬盘 HDD（磁头寻道，顺序快随机慢）和固态硬盘 SSD（无机械部件，随机读也快）。大数据存储（HDFS、数据湖）大量依赖磁盘，IO 吞吐是离线计算的瓶颈。HDD 顺序读写可达上百 MB/s，但随机读写因磁头寻道只有几 MB/s；SSD 随机性能高一个数量级。

```text
磁盘要点：
1. HDD —— 顺序读快、随机读慢（磁头寻道），适合大文件顺序扫描
2. SSD —— 随机读快，寿命受擦写次数限制，适合热数据、缓存
3. 吞吐 vs IOPS —— 吞吐（MB/s）看顺序，IOPS（每秒操作数）看随机
4. 大数据 —— HDFS 假设顺序读写，列式格式（Parquet）为顺序扫描优化
```

```shell
# 用 dd 测磁盘顺序写吞吐
dd if=/dev/zero of=./testfile bs=1M count=1024 oflag=direct

# 用 fio 测随机读 IOPS
fio --name=randread --rw=randread --bs=4k --size=1G \
    --numjobs=4 --ioengine=libaio --direct=1 --runtime=30

# 查看磁盘 IO 情况
iostat -x 1
```

## IO

IO（输入输出）指数据在内存与外部设备（磁盘、网络）间的传输。IO 分阻塞/非阻塞、同步/异步、缓冲/直接等模式。大数据系统是 IO 密集型的——读写 HDFS、Shuffle 网络传输、落盘持久化都消耗大量 IO。理解 IO 模型（select/poll/epoll、mmap、零拷贝）才能理解 Kafka/Netty 高性能的底层。

```text
IO 关键概念：
1. 阻塞 vs 非阻塞 —— 阻塞 IO 等数据返回才继续，非阻塞立即返回轮询
2. 零拷贝 —— sendfile/mmap 免去用户态与内核态的数据拷贝，Kafka 快的关键
3. 顺序 vs 随机 —— 顺序 IO 远快于随机 IO，大数据设计尽量顺序化
4. 缓冲 —— 攒批写入减少系统调用，提升吞吐（Kafka 批处理同理）
```

```java
// Java：NIO 非阻塞文件通道读文件
import java.nio.ByteBuffer;
import java.nio.channels.FileChannel;
import java.nio.file.Paths;
import java.nio.file.StandardOpenOption;

public class NIODemo {
    public static void main(String[] args) throws Exception {
        FileChannel ch = FileChannel.open(
            Paths.get("/etc/hosts"), StandardOpenOption.READ);
        ByteBuffer buf = ByteBuffer.allocate(1024);
        int n = ch.read(buf);       // 非阻塞读
        buf.flip();
        byte[] data = new byte[n];
        buf.get(data);
        System.out.println(new String(data));
        ch.close();
    }
}
```

## 中断

中断是硬件/软件通知 CPU「有事件需要处理」的机制，让 CPU 不必轮询等待慢速设备（键盘、网卡、磁盘）。外设准备好数据后发中断，CPU 暂停当前任务、保存现场、执行中断处理程序，再恢复。中断让 CPU 与 IO 设备并行工作，是操作系统多任务和 IO 管理的基础。大数据里网卡中断、磁盘中断的均衡（IRQ affinity）影响网络吞吐。

```text
中断要点：
1. 硬中断 —— 外设（网卡/磁盘）发给 CPU 的硬件信号
2. 软中断 —— 内核触发的异步处理（如网络收包下半部），在中断上下文执行
3. 中断处理 —— 分上半部（快速响应）与下半部（延后处理，如 softirq）
4. IRQ 亲和 —— 把网卡中断绑定到特定 CPU 核，避免单核被打满
```

```shell
# 查看中断分布（/proc/interrupts）
cat /proc/interrupts | head -20

# 查看网卡中断号并设置亲和性（绑定到 CPU 0）
grep eth0 /proc/interrupts
echo 1 > /proc/irq/$(grep eth0 /proc/interrupts | awk -F: '{print $1}')/smp_affinity

# 查看软中断情况
cat /proc/softirqs
```

## DMA

DMA（直接存储器访问）允许外设直接把数据搬到内存，不经过 CPU 逐字节搬运。CPU 只需发起一次 DMA 请求，数据搬运由 DMA 控制器完成，完成后以中断通知 CPU。这让大量数据 IO（磁盘读写、网卡收发）几乎不占用 CPU，是高性能存储与网络的基础。零拷贝技术正是建立在 DMA 之上。

```text
DMA 要点：
1. 原理 —— 外设 <-> 内存 直接传数据，CPU 只发指令不搬数据
2. 好处 —— 释放 CPU，让计算与 IO 并行，大幅提升吞吐
3. 与中断配合 —— DMA 传完触发中断，CPU 才介入处理结果
4. 零拷贝 —— DMA + 内核直接转发，避免用户态拷贝，Kafka/Netty 高性能来源
```

```text
有 DMA vs 无 DMA 的磁盘读流程对比：
无 DMA：CPU 从磁盘控制器逐字节读到寄存器，再写到内存（CPU 全程占用）
有 DMA：CPU 配置 DMA 控制器 -> DMA 直接把磁盘数据搬到内存 -> 完成后中断通知 CPU
```

## 应用场景实战

### 场景一：判断作业是 CPU 密集还是 IO 密集，指导资源分配

```shell
# 1. 观察作业运行时的资源使用
top -p <pid>          # 看 %CPU 与内存
iostat -x 1          # 看磁盘 %util 与 IOPS
sar -n DEV 1         # 看网卡吞吐

# 2. 结论判断
#    CPU 密集：%CPU 接近核心数满载，磁盘/网络空闲 -> 加大 CPU 核数
#    IO  密集：磁盘 %util 接近 100%，CPU 空闲 -> 加大磁盘吞吐/换 SSD/优化顺序读
```

### 场景二：用缓存行对齐优化多线程累加（避免伪共享）

```java
// Java：演示伪共享与 padding 优化
public class FalseSharing {
    static class Counter {
        volatile long value = 0L;
    }

    static class PaddedCounter {
        volatile long value = 0L;
        long p1, p2, p3, p4, p5, p6, p7; // 填充到独立缓存行
    }

    public static void main(String[] args) throws Exception {
        test(new Counter[4]);
        test(new PaddedCounter[4]);
    }

    static void test(Counter[] cs) throws Exception {
        Thread[] ts = new Thread[cs.length];
        for (int i = 0; i < cs.length; i++) {
            final int idx = i;
            ts[i] = new Thread(() -> {
                for (int j = 0; j < 100_000_000; j++) cs[idx].value++;
            });
        }
        long t0 = System.nanoTime();
        for (Thread t : ts) t.start();
        for (Thread t : ts) t.join();
        System.out.println("耗时(ms): " + (System.nanoTime() - t0) / 1_000_000);
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 写作业前先判断是 CPU 密集还是 IO 密集，据此分配资源
2. 数据访问尽量顺序化，利用缓存和磁盘顺序读的优势
3. 大表扫描用列式存储（Parquet/ORC），只读需要的列，对缓存友好
4. 避免伪共享：多线程频繁写的共享变量用 padding 对齐缓存行
5. 关注磁盘 IOPS 而非只看容量，随机读多的场景优先 SSD
6. 网卡/磁盘中断绑定 CPU 核（IRQ affinity），避免单核瓶颈
7. 内存不够先想「能不能只处理需要的列/分区」，而不是无脑加内存

### 踩坑记录

```text
坑 1：随机读小文件导致 HDFS 集群吞吐暴跌
结论：同样的数据量，随机读比顺序读慢一个数量级。
原因：机械盘磁头频繁寻道，且每次小读都打断顺序 IO。
解法：小文件合并、用列式格式、数据按分区组织保证顺序扫描。

坑 2：Spark 作业 OOM 却以为内存不够
结论：加 executor 内存也不管用，仍频繁 OOM。
原因：数据倾斜导致单分区数据量超单核内存，或 shuffle 中间数据过大。
解法：排查倾斜（加盐/两阶段聚合）、减少 shuffle、调整分区数。

坑 3：忽略伪共享导致多线程性能不升反降
结论：多线程累加共享变量，性能远低于预期。
原因：多个线程写同一缓存行的不同变量，缓存行反复失效。
解法：变量填充到独立缓存行（padding）或改用独立内存区域。

坑 4：用 CPU 核数评估 GPU 任务性能
结论：GPU 任务按 CPU 核数配置，GPU 利用率极低。
原因：GPU 是海量并行核心，瓶颈在 GPU 利用率与显存带宽而非 CPU 核。
解法：GPU 任务按 GPU 数量/显存配置，保证数据批次喂满 GPU。
```
