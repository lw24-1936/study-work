## 概述

操作系统是硬件与应用程序之间的抽象层，负责进程管理、内存管理、文件系统与设备驱动。大数据组件（JVM、Docker、Kubernetes）都运行在 OS 之上，理解进程/线程模型、虚拟内存和 cgroups/namespace，才能理解 Spark executor、容器资源隔离、K8s 调度的底层机制。本章聚焦大数据工程最相关的几个 OS 概念。

```text
操作系统的核心职责：
1. 进程/线程管理 —— 调度 CPU，实现多任务并发
2. 内存管理 —— 虚拟内存隔离进程地址空间
3. 文件系统 —— 统一磁盘/网络的存储抽象
4. 资源隔离 —— cgroups/namespace 是容器技术（Docker/K8s）的基石
```

## 进程

进程是程序的一次运行实例，是资源分配的基本单位——拥有独立的地址空间、文件描述符表、信号处理等资源。进程通过 fork/exec 创建，通过信号和 IPC（管道、共享内存、消息队列）通信。进程间内存隔离，一个进程崩溃不影响其它进程。大数据里每个 executor、每个 container 都是一个进程。

```text
进程要点：
1. 资源单位 —— 独立地址空间、PID、文件描述符、环境变量
2. 生命周期 —— fork 创建子进程、exec 替换程序、exit 退出、父进程 wait 回收
3. 状态 —— 运行/就绪/阻塞/僵尸（Zombie，退出后未被父进程回收）
4. 通信 —— 管道、信号、共享内存、socket（跨主机）
```

```shell
# 查看进程树与状态
ps aux | grep java
pstree -p

# 用 fork/exec 演示进程创建（shell 里 & 与 wait）
sleep 10 &
PID=$!
echo "子进程 PID: $PID"
wait $PID
echo "子进程结束"

# 查看僵尸进程
ps aux | awk '$8=="Z" {print $0}'
```

## 线程

线程是进程内的执行流，是 CPU 调度的基本单位。同一进程的多个线程共享地址空间、文件描述符等资源，但有独立的栈和寄存器。线程切换成本远低于进程切换（不用切换地址空间），因此高并发服务多用线程。JVM 的线程、Spark 的 task（跑在线程池里）、Kafka 的网络线程都是线程。

```text
线程要点：
1. 调度单位 —— CPU 调度的是线程，进程是资源容器
2. 共享 vs 独立 —— 共享堆/全局变量，独立栈/寄存器/线程局部存储
3. 切换成本 —— 线程切换免于切换页表，比进程切换便宜
4. 并发问题 —— 共享内存带来竞态，需锁（mutex）、原子操作、CAS
```

```java
// Java：多线程累加演示竞态与同步
public class ThreadDemo {
    static int counter = 0;

    public static void main(String[] args) throws Exception {
        Thread t1 = new Thread(() -> { for (int i = 0; i < 100000; i++) counter++; });
        Thread t2 = new Thread(() -> { for (int i = 0; i < 100000; i++) counter++; });
        t1.start(); t2.start();
        t1.join(); t2.join();
        // 无同步时结果通常 < 200000（竞态丢失更新）
        System.out.println("counter = " + counter);
    }
}
```

## 虚拟内存

虚拟内存为每个进程提供独立、连续的地址空间，通过页表把虚拟地址映射到物理地址。它的好处：进程隔离（一个进程无法读写别的进程内存）、按需加载（不用的页不占物理内存）、支持换页（内存不足时把冷页换到磁盘 swap）。页表由硬件 MMU 在每次访存时查，TLB 缓存热门页表项加速。

```text
虚拟内存要点：
1. 页表 —— 虚拟页 -> 物理页的映射，MMU 硬件查表
2. 进程隔离 —— 各进程独立页表，互不可见，是内存安全的基础
3. 缺页中断 —— 访问未加载的页触发，OS 从磁盘换入
4. swap —— 物理内存不够时把冷页换出到磁盘，性能骤降的信号
5. JVM —— Java 堆在虚拟内存里分配，GC 与缺页交互影响性能
```

```shell
# 查看进程虚拟内存与物理内存（VSZ/RSS）
ps -eo pid,vsz,rss,comm | grep java

# 查看系统内存与 swap
free -h

# 查看进程内存映射（mmap 区域）
cat /proc/$(pgrep -f java | head -1)/smaps | head -30
```

## 文件系统

文件系统把磁盘块组织成目录树和文件，提供统一的读写接口。Linux 核心是 VFS（虚拟文件系统），让不同的底层文件系统（ext4、xfs、tmpfs、以及网络文件系统如 HDFS 的 FUSE）对上层透明。inode 存文件元数据（大小、权限、块指针），文件名只是目录项指向 inode。大数据里理解「文件系统 POSIX 语义 vs HDFS/对象存储的非 POSIX 语义」很关键。

```text
文件系统要点：
1. inode —— 文件元数据（权限/大小/块指针），与文件名分离
2. VFS —— 统一抽象，支持挂载多种文件系统
3. 页缓存 —— 读写经过内核页缓存加速，是顺序读快的原因
4. 非 POSIX —— HDFS/对象存储不支持随机写/rename 语义，区别于本地文件系统
```

```shell
# 查看 inode 与磁盘使用
df -h
df -i          # 看 inode 是否耗尽
ls -li         # 看文件的 inode 号

# 创建并挂载 tmpfs（内存文件系统）
mkdir -p /mnt/ramdisk
mount -t tmpfs -o size=1G tmpfs /mnt/ramdisk
```

## 系统调用

系统调用是用户态程序请求内核服务的唯一入口——读写文件、创建进程、网络收发、内存映射都要通过它。用户态与内核态的切换有开销，所以高性能系统尽量减少系统调用次数（批量 IO、零拷贝、io_uring）。理解系统调用能读懂 strace 输出，排查「程序卡在哪」。

```text
系统调用要点：
1. 入口 —— 用户态陷入内核态（int 0x80 / syscall 指令），内核执行后返回
2. 开销 —— 每次调用有上下文切换成本，高频调用要批量化
3. 常见 —— read/write/open/close/fork/exec/mmap/ioctl
4. 观测 —— strace 追踪系统调用，定位性能瓶颈
```

```shell
# 追踪程序的系统调用
strace -c ls /          # 统计各类系统调用次数与耗时
strace -e trace=open,read java -version   # 只看 open 和 read
```

```c
// C：直接调用系统调用写文件
#include <unistd.h>
#include <fcntl.h>

int main() {
    int fd = open("/tmp/test.txt", O_WRONLY | O_CREAT, 0644);
    write(fd, "hello\n", 6);   // write 系统调用
    close(fd);
    return 0;
}
```

## cgroups

cgroups（Control Groups）是 Linux 内核的资源限制机制，能把进程分组并限制每组的 CPU、内存、IO、网络带宽。它是 Docker 和 Kubernetes 资源隔离的基石——容器里的 CPU/内存限制，本质是给容器进程设了 cgroup。大数据里 YARN 也用它限制 container 资源，防止单个任务吃光整机。

```text
cgroups 要点：
1. 资源类型 —— cpu（配额）、memory（上限）、blkio、net_cls
2. 层级 —— 挂载在 /sys/fs/cgroup，子目录对应一个资源组
3. 容器基石 —— Docker 的 --cpus/--memory 就是写 cgroup 参数
4. 限流价值 —— 防止单个进程 OOM 拖垮整机，是资源隔离的底线
```

```shell
# 手动创建一个 cgroup 并限制 CPU
mkdir -p /sys/fs/cgroup/cpu/demo
echo 50000 > /sys/fs/cgroup/cpu/demo/cpu.cfs_quota_us   # 限制 50% CPU
echo 100000 > /sys/fs/cgroup/cpu/demo/cpu.cfs_period_us
echo $PID > /sys/fs/cgroup/cpu/demo/tasks               # 把进程加入

# 用 systemd-run 快速限制一个命令的 CPU/内存
systemd-run --scope -p CPUQuota=50% -p MemoryMax=512M ./myjob.sh
```

## namespace

namespace 是 Linux 内核的视图隔离机制，让不同进程看到独立的「系统视图」——PID（进程号）、Network（网卡）、Mount（文件系统）、UTS（主机名）、IPC、User（用户）。每个 namespace 里的进程都以为自己是独立的系统。容器技术 = cgroups（限制资源）+ namespace（隔离视图）。K8s 的 Pod 共享一个网络 namespace，因此容器间用 localhost 通信。

```text
namespace 要点：
1. 类型 —— PID/NET/MNT/UTS/IPC/USER，隔离不同的系统资源视图
2. 容器基石 —— 容器本质是「独立 namespace + 受限 cgroup」的进程
3. Pod 网络 —— K8s 同一 Pod 容器共享 NET namespace，用 localhost 互访
4. 与 cgroups 分工 —— namespace 管「看不见」，cgroups 管「用多少」
```

```shell
# 用 unshare 快速体验 namespace 隔离
unshare --pid --fork --mount-proc bash -c "echo 隔离进程 PID=$$"
# 在新 PID namespace 里，当前进程看到的 PID 是 1

# 查看进程所属的 namespace
ls -l /proc/$$/ns
```

## 应用场景实战

### 场景一：诊断 Spark executor 进程的 CPU/内存限制与使用

```shell
# 1. 找到 executor 进程
jps | grep CoarseGrainedExecutorBackend
PID=<executor_pid>

# 2. 查看进程虚拟内存与物理内存
cat /proc/$PID/status | grep -E "VmRSS|VmSize|Threads"

# 3. 查看该进程所在 cgroup 的内存限制（容器环境）
cat /proc/$PID/cgroup

# 4. 查看线程数（判断是否线程泄漏）
ls /proc/$PID/task | wc -l
```

### 场景二：用 systemd-run 给一个批处理任务做资源隔离

```shell
# 给数据导入任务限制 CPU 和内存，避免影响线上服务
systemd-run --scope \
  -p CPUQuota=200% \
  -p MemoryMax=2G \
  -p MemorySwapMax=0 \
  ./etl_import.sh

# 观察限制是否生效
systemd-cgtop    # 实时看各 cgroup 的资源使用
```

## 最佳实践与踩坑记录

### 最佳实践

1. 排查「程序卡住」先用 strace 看卡在哪个系统调用
2. 内存频繁 swap 说明物理内存不足，优先加内存或减数据，而非依赖 swap
3. 容器里跑 JVM 要设 -Xmx 略小于容器内存上限，避免 cgroup OOM
4. 用 cgroups 给批处理任务限资源，防止影响同机在线服务
5. 理解线程共享堆，多线程共享数据结构要加锁或改无锁结构
6. 线上服务关注线程数和文件描述符数，防止资源泄漏耗尽
7. 区分「文件系统」语义，写代码别假设 HDFS/对象存储支持随机写

### 踩坑记录

```text
坑 1：容器里 JVM 按宿主机内存设置堆导致 OOM
结论：容器被杀（OOMKilled），但容器内存限制是 2G，宿主机是 64G。
原因：JVM 默认按宿主机物理内存算默认堆大小，超过容器 cgroup 限制。
解法：显式设 -Xmx 小于容器内存上限，或用 JVM 容器感知参数。

坑 2：僵尸进程堆积导致无法再 fork
结论：系统报「fork: retry: Resource temporarily unavailable」。
原因：子进程退出后父进程未 wait 回收，僵尸进程占用 PID 资源。
解法：父进程正确处理 SIGCHLD，或让 init 进程（PID 1）接管孤儿进程。

坑 3：文件描述符泄漏导致服务不可用
结论：服务报「Too many open files」，无法建立新连接。
原因：代码打开文件/socket 未关闭，fd 用尽。
解法：排查 lsof -p PID，用 try-with-resources 或 finally 关闭资源。

坑 4：把 HDFS 当本地文件系统用随机写
结论：程序在 HDFS 上频繁 rename/append，性能极差甚至报错。
原因：HDFS 不支持随机写，只支持追加，POSIX 语义不成立。
解法：HDFS 上只做顺序写/追加，随机更新场景改用 HBase/表格式。
```
