## 概述

算法工程是把「正确的算法」变成「高性能、可维护、健壮」的代码的工程实践。算法正确只是第一步，真正的问题是：它到底快不快（Benchmark）、慢在哪里（Profiling）、能不能利用多核（并行）、改坏了怎么办（测试）、数据边界和规模变化时会不会崩（边界与数据规模）。大数据场景下，算法常运行在千万/亿级数据上，工程素养决定算法能否落地。

```text
算法工程五件事：
1. Benchmark —— 客观测量性能，别靠感觉
2. Profiling  —— 定位瓶颈，优化要打在痛点上
3. 并行        —— 利用多核/多机加速
4. 测试        —— 保证正确性，防止回归
5. 边界与规模 —— 空/单元素/溢出/大数据的健壮性
```

## Benchmark

Benchmark（基准测试）是客观测量代码性能的手段：在统一条件下重复运行、取统计量（中位数/均值），避免单次运行的偶然波动。核心原则是「测量而非猜测」——优化前先测基线，优化后再测对比。常用工具：Python 的 timeit、pytest-benchmark；大数据用 JMH（Java）、各引擎的 TPC-DS 基准。注意预热 JIT、排除 GC/IO 干扰。

```text
Benchmark 要点：
1. 测基线 —— 优化前先量化现状，才能证明优化有效
2. 重复 + 统计 —— 多次运行取中位数，抵抗波动
3. 预热 —— 排除 JIT 编译、缓存冷启动的干扰
4. 对比 —— 同数据同条件下比，才有意义
```

```python
import time
import timeit

def sum_loop(n):
    s = 0
    for i in range(n):
        s += i
    return s

def sum_builtin(n):
    return sum(range(n))

# timeit 自动重复并取最优，测量更稳
t1 = timeit.timeit("sum_loop(100000)", globals=globals(), number=100)
t2 = timeit.timeit("sum_builtin(100000)", globals=globals(), number=100)
print(f"手写循环: {t1:.4f}s / 100 次")
print(f"内置 sum: {t2:.4f}s / 100 次")
print(f"内置快 {t1 / t2:.1f} 倍")
```

## Profiling

Profiling（性能剖析）是找出代码「时间花在哪」的技术：按函数统计调用次数和耗时（cProfile）、按行统计（line_profiler）、按内存统计（memory_profiler）。原则是「先 profile 再优化」——没有数据支撑的优化往往打在无关痛痒的地方。典型发现：热点函数、重复计算、不必要的内存分配、频繁的 IO 或序列化。

```text
Profiling 要点：
1. 先定位再优化 —— 90% 时间往往花在 10% 的代码上
2. 工具 —— cProfile（函数级）、line_profiler（行级）、memory_profiler（内存）
3. 关注 —— 热点函数、调用次数异常、内存峰值
4. 大数据 —— 关注 shuffle、序列化、GC 停顿
```

```python
import cProfile
import pstats
import io

def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

def workload():
    total = 0
    for _ in range(50):
        total += fib(20)
    return total

pr = cProfile.Profile()
pr.enable()
workload()
pr.disable()

s = io.StringIO()
ps = pstats.Stats(pr, stream=s).sort_stats('cumulative')
ps.print_stats(5)   # 打印累计耗时前 5 的函数
print(s.getvalue())
```

## 并行

并行（Parallelism）用多核/多机同时计算来加速：多线程（共享内存，受 GIL 限制，适合 IO 密集）、多进程（独立内存，适合 CPU 密集）、以及大数据的分布式并行（MapReduce/Spark 把任务拆到多机）。并行的关键是「任务可拆分 + 结果可合并」，要注意数据竞争、负载均衡、通信开销——并行不是免费的，小任务并行反而更慢。

```text
并行要点：
1. 多线程 vs 多进程 —— IO 密集用线程，CPU 密集用进程（Python 受 GIL 限制）
2. 拆分与合并 —— map（拆分）+ reduce（合并）
3. 代价 —— 线程/进程创建、通信、锁竞争都有开销
4. 大数据 —— 分布式并行，关注数据倾斜与 shuffle
```

```python
from multiprocessing import Pool

def is_prime(n):
    if n < 2:
        return False
    for i in range(2, int(n ** 0.5) + 1):
        if n % i == 0:
            return False
    return True

def count_primes_serial(nums):
    return sum(1 for n in nums if is_prime(n))

def count_primes_parallel(nums, workers=4):
    with Pool(workers) as pool:
        return sum(pool.map(is_prime, nums))

nums = list(range(2, 200000))
import time
t0 = time.perf_counter(); s = count_primes_serial(nums); t1 = time.perf_counter()
print(f"串行: {t1 - t0:.3f}s, 素数 {s} 个")
t0 = time.perf_counter(); p = count_primes_parallel(nums); t1 = time.perf_counter()
print(f"并行(4进程): {t1 - t0:.3f}s, 素数 {p} 个")
```

## 测试

测试（Testing）用自动化断言保证算法正确性：单元测试（测单个函数）、边界测试（空输入、单元素、重复值）、随机测试（对拍——用暴力解法验证优化解法）、回归测试（防止改动破坏旧功能）。大数据算法测试的难点是「结果难手算」，常用「小数据跑暴力解对拍」和「属性测试」（如排序后有序、去重后无重复）来验证。

```text
测试要点：
1. 单元测试 —— 每个函数配断言，覆盖正常 + 边界
2. 对拍 —— 用朴素解法验证高效解法的正确性
3. 属性测试 —— 验证不变量（排序后有序、哈希查找等于遍历）
4. 回归测试 —— 改动后跑全量测试防退化
```

```python
import random

def quick_sort(a):
    if len(a) <= 1:
        return a
    pivot = a[0]
    return (quick_sort([x for x in a[1:] if x <= pivot]) +
            [pivot] + quick_sort([x for x in a[1:] if x > pivot]))

def test_quick_sort():
    # 边界测试
    assert quick_sort([]) == []
    assert quick_sort([1]) == [1]
    assert quick_sort([2, 1]) == [1, 2]
    assert quick_sort([1, 1, 1]) == [1, 1, 1]
    # 对拍：随机数据对比 Python 内置排序
    for _ in range(100):
        arr = [random.randint(-100, 100) for _ in range(random.randint(0, 50))]
        assert quick_sort(arr) == sorted(arr)
    print("全部测试通过")

test_quick_sort()
```

## 边界与数据规模

边界与数据规模关注算法的健壮性：空输入、单元素、重复元素、极大/极小值、整数溢出、内存上限。算法在 n=10 时正确，不代表 n=10 亿时能跑——要考虑溢出（int 转 long）、内存（O(n) 空间放不下）、耗时（O(n²) 不可行）、浮点精度。大数据尤其要关注「数据量翻倍时算法是否还成立」，这决定算法能否上线。

```text
边界与数据规模要点：
1. 边界 —— 空/单元素/重复/负值/极值/相等值
2. 溢出 —— 大数求和/乘积用 long，防 int 溢出
3. 内存 —— O(n) 空间在亿级数据下可能爆内存
4. 规模 —— n 翻倍时，O(n²) 耗时翻 4 倍，O(2ⁿ) 直接不可行
```

```python
def sum_safe(nums):
    """用 Python 大整数天然防溢出，演示边界处理。"""
    return sum(nums)

def binary_search_safe(arr, target):
    """处理空数组、单元素、找不到等边界。"""
    if not arr:                      # 空数组
        return -1
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = lo + (hi - lo) // 2    # 防 mid 溢出
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

# 边界测试
print(binary_search_safe([], 5))          # -1 空数组
print(binary_search_safe([5], 5))         # 0  单元素
print(binary_search_safe([1, 3, 5], 2))   # -1 找不到
print(sum_safe([2**60, 2**60]))           # 大数求和，Python 不溢出
```

## 应用场景实战

### 场景一：优化一个慢函数（profile → 定位 → 优化 → 验证）

```python
import time

def slow_contains(haystack, needles):
    """O(n*m)：列表 in 是 O(n)，套循环变 O(n²)。"""
    found = 0
    for n in needles:
        if n in haystack:        # 列表 in 是线性扫描
            found += 1
    return found

def fast_contains(haystack, needles):
    """O(n+m)：先转 set，in 变 O(1)。"""
    hset = set(haystack)
    return sum(1 for n in needles if n in hset)

haystack = list(range(10000))
needles = list(range(0, 10000, 2))

t0 = time.perf_counter(); slow_contains(haystack, needles); t1 = time.perf_counter()
print(f"优化前: {t1 - t0:.4f}s")
t0 = time.perf_counter(); fast_contains(haystack, needles); t1 = time.perf_counter()
print(f"优化后: {t1 - t0:.4f}s")

# 正确性验证：两者结果一致
assert slow_contains(haystack, needles) == fast_contains(haystack, needles)
print("结果一致，优化有效")
```

### 场景二：并行加速 + 对拍验证大数据统计

```python
from multiprocessing import Pool

def chunk_unique_count(chunk):
    """单个分片的去重计数。"""
    return len(set(chunk))

def distributed_unique_count(data, workers=4):
    """分片并行去重计数，再合并（近似，跨片重复未去）。"""
    chunk_size = len(data) // workers
    chunks = [data[i:i + chunk_size] for i in range(0, len(data), chunk_size)]
    with Pool(workers) as pool:
        return sum(pool.map(chunk_unique_count, chunks))

# 小数据对拍：验证分片逻辑正确（这里示意，实际跨片需再合并）
data = [1, 2, 3, 4, 5, 1, 2, 3]
print("串行精确去重 =", len(set(data)))
print("分片并行求和 =", distributed_unique_count(data, workers=2))
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先 profile 找到热点再优化，别凭感觉乱改
2. 优化前测基线、优化后测对比，用数据说话
3. Python 里 CPU 密集用多进程而非多线程（GIL 限制）
4. 算法上线前做边界测试（空/单/重复/极值）和随机对拍
5. 大数据先算量级：O(n²) 在亿级不可行，必须降复杂度
6. 大数求和/乘积防溢出，用 long 或语言的大整数类型

### 踩坑记录

```text
坑 1：不 profile 直接优化
结论：优化了半天，总耗时几乎没变。
原因：改的地方不是热点，90% 时间花在别处。
解法：先 cProfile/line_profiler 定位热点函数，再针对性优化。

坑 2：Python 用多线程加速 CPU 密集任务
结论：加了线程反而更慢，或几乎没有加速。
原因：GIL 全局锁让 CPU 密集的 Python 线程无法真正并行。
解法：CPU 密集用 multiprocessing 多进程，IO 密集才用多线程。

坑 3：基准测试不预热导致误判
结论：把 JIT 编译/缓存冷启动的耗时算进去，结论失真。
原因：首次运行包含编译、加载、缓存建立等一次性开销。
解法：先预热几次再计时，或取多次运行的稳定值。

坑 4：大数据规模下忽略内存和溢出
结论：n=10 亿时 O(n) 的中间数组把内存撑爆，int 求和溢出。
原因：小数据测试没问题，但规模放大后空间和溢出都成问题。
解法：上大数据前评估空间复杂度，求和用 long，考虑流式/分片处理。
```
