## 概述

哈希（Hash）是把任意长度的数据映射到固定长度「指纹」的函数，核心价值是把 O(n) 的查找加速到平均 O(1)。哈希表是它最经典的应用，而布隆过滤器、布谷鸟哈希、HyperLogLog 则是在「大数据 + 内存有限」约束下发展出的空间换精度/换时间的极致优化——分别解决「是否存在」「如何更省空间地判存在」「如何用极少内存估去重基数」。这些是分布式系统（Redis、Cassandra、HBase、大数据精确去重）的底层基石。

```text
哈希家族四兄弟的分工：
1. Hash Table   —— 精确 O(1) 查找，标准键值存储
2. Bloom Filter —— 空间极省地判断「可能存在」，有误判（假阳性）
3. Cuckoo Hash  —— 最坏情况 O(1) 查找，无冲突链
4. HyperLogLog  —— 用 KB 级内存估计亿级去重基数（近似）
```

## Hash Table

哈希表（Hash Table）通过哈希函数把键映射到桶下标，实现平均 O(1) 的插入、查找、删除。核心是处理「冲突」：两个键映射到同一桶时，用链地址法（桶里挂链表/红黑树）或开放寻址法（线性探测找下一个空位）。负载因子（元素数/桶数）是性能关键，过高则冲突加剧退化到 O(n)。Python 的 dict、Redis、HashMap 都是哈希表。

```text
哈希表要点：
1. 平均 O(1) 查找，最坏 O(n)（冲突全聚一堆）
2. 冲突解决 —— 链地址法（链表/红黑树）与开放寻址法（线性探测/二次探测）
3. 负载因子 —— 一般超过 0.7~0.75 就扩容，保持低冲突
4. 扩容 rehash —— 桶翻倍后所有键要重新哈希，是偶发昂贵操作（摊销 O(1)）
```

```python
class HashTable:
    """链地址法实现的简化哈希表。"""
    def __init__(self, capacity=8):
        self.capacity = capacity
        self.buckets = [[] for _ in range(capacity)]
        self.size = 0

    def _hash(self, key):
        return hash(key) % self.capacity

    def put(self, key, value):
        idx = self._hash(key)
        for i, (k, v) in enumerate(self.buckets[idx]):
            if k == key:
                self.buckets[idx][i] = (key, value)
                return
        self.buckets[idx].append((key, value))
        self.size += 1

    def get(self, key):
        idx = self._hash(key)
        for k, v in self.buckets[idx]:
            if k == key:
                return v
        return None

    def remove(self, key):
        idx = self._hash(key)
        self.buckets[idx] = [(k, v) for k, v in self.buckets[idx] if k != key]

ht = HashTable()
for k, v in [("a", 1), ("b", 2), ("c", 3)]:
    ht.put(k, v)
print("get('b') =", ht.get("b"))
print("get('x') =", ht.get("x"))   # None
```

## Bloom Filter

布隆过滤器（Bloom Filter）用「一个位数组 + 多个哈希函数」判断元素「是否可能存在」：插入时把 k 个哈希位置置 1，查询时检查 k 个位是否都为 1。它只会有「假阳性」（说不存在的一定不存在，说存在的可能不存在），绝无假阴性。空间极省——10 亿元素约 1.4GB（1% 误判率），适合做缓存穿透防护、HBase 的 Block Cache、爬虫 URL 去重的第一道过滤。

```text
布隆过滤器要点：
1. 假阳性无假阴性 —— 误判只会「把不存在当存在」，不会漏掉存在的
2. 不支持删除 —— 删一个元素可能误删别的元素的位（可用计数布隆）
3. 参数 —— 位数组大小 m、哈希函数个数 k 决定误判率
4. 误判率公式 —— p ≈ (1 - e^(-kn/m))^k，最优 k = (m/n)·ln2
```

```python
import hashlib

class BloomFilter:
    def __init__(self, size, hash_count):
        self.size = size
        self.hash_count = hash_count
        self.bits = [0] * size

    def _hashes(self, item):
        """用双重哈希派生 k 个哈希值，避免实现 k 个独立哈希函数。"""
        h1 = int(hashlib.md5(item.encode()).hexdigest(), 16)
        h2 = int(hashlib.sha256(item.encode()).hexdigest(), 16)
        for i in range(self.hash_count):
            yield (h1 + i * h2) % self.size

    def add(self, item):
        for pos in self._hashes(item):
            self.bits[pos] = 1

    def contains(self, item):
        return all(self.bits[pos] == 1 for pos in self._hashes(item))

bf = BloomFilter(size=64, hash_count=3)
for url in ["http://a.com", "http://b.com", "http://c.com"]:
    bf.add(url)

print("已插入的 URL 判定 =", bf.contains("http://a.com"))   # True
print("未插入的 URL 判定 =", bf.contains("http://z.com"))   # 大概率 False（可能误判）
```

## Cuckoo Hash

布谷鸟哈希（Cuckoo Hash）用两个哈希函数和两张哈希表，插入时把新元素放进一张表；若位置被占，就把原位置的元素「踢」到它在另一张表的位置，如此递归驱逐，像布谷鸟把别的鸟蛋推出巢。它保证查找最坏 O(1)（最多查两个位置），无冲突链。若驱逐陷入循环，则扩容重哈希。适合读多写少、对最坏延迟敏感的缓存（如 CPU 缓存、路由器查表）。

```text
布谷鸟哈希要点：
1. 最坏 O(1) 查找 —— 每个元素只在两个固定位置之一
2. 驱逐机制 —— 插入时踢走占位者，被踢者搬到自己的另一位置
3. 循环与扩容 —— 驱逐次数超阈值说明表太满，需扩容重哈希
4. 负载因子 —— 一般控制 < 0.5，保证驱逐成功概率高
```

```python
class CuckooHash:
    def __init__(self, size=8):
        self.size = size
        self.t1 = [None] * size
        self.t2 = [None] * size
        self.MAX_EVICT = 16

    def _h1(self, key):
        return hash(("h1", key)) % self.size

    def _h2(self, key):
        return hash(("h2", key)) % self.size

    def put(self, key):
        for _ in range(self.MAX_EVICT):
            p1 = self._h1(key)
            if self.t1[p1] is None:
                self.t1[p1] = key
                return True
            p2 = self._h2(key)
            if self.t2[p2] is None:
                self.t2[p2] = key
                return True
            # 两个位置都满：随机踢走 t1[p1]，把被踢者当新 key 继续
            victim, self.t1[p1] = self.t1[p1], key
            key = victim
        return False   # 驱逐循环，应触发扩容重哈希

    def lookup(self, key):
        return self.t1[self._h1(key)] == key or self.t2[self._h2(key)] == key

ch = CuckooHash()
for k in ["red", "green", "blue", "yellow"]:
    ch.put(k)
print("lookup('green') =", ch.lookup("green"))    # True
print("lookup('black') =", ch.lookup("black"))    # False
```

## HyperLogLog

HyperLogLog（HLL）用极小的内存估计一个集合的「不同元素数量」（基数）。原理：对每个元素算哈希值，观察哈希二进制里「最长前导 0 的位数」，位数越大说明见到的不同元素越多，据此用调和平均估计基数。标准 HLL 用 2^14 个桶、约 12KB 内存即可估计数十亿基数，标准误差约 0.81%。它是 Redis 的 PFADD、Spark 的 approx_count_distinct、Druid/ClickHouse 去重估数的底层。

```text
HyperLogLog 要点：
1. 只估基数，不存元素 —— 内存 O(m)，与数据量无关
2. 精度 —— 标准误差 ≈ 1.04/√m，m 个桶；12KB 桶时约 0.81%
3. 原理 —— 哈希值前导 0 位数反映「见过多少不同值」，桶+调和平均修正方差
4. 可合并 —— 多个 HLL 按桶取最大值即可合并，天然适合分布式去重
```

```python
import math
import random

def count_leading_zeros(x, bits=32):
    if x == 0:
        return bits
    return bits - x.bit_length()

class SimpleHLL:
    """用单一估计器演示前导零估计基数的思想（真实 HLL 用多桶+调和平均）。"""
    def __init__(self, bits=32):
        self.bits = bits
        self.max_zeros = 0

    def add(self, item):
        h = hash(item) & ((1 << self.bits) - 1)
        zeros = count_leading_zeros(h, self.bits)
        self.max_zeros = max(self.max_zeros, zeros)

    def estimate(self):
        # 观察到的最大前导零 + 1，用 2^max 估计基数
        return 2 ** self.max_zeros

# 模拟：插入不同规模的数据，观察估计值与真实值的量级
hll = SimpleHLL()
for i in range(1000):
    hll.add(f"user-{i}")
print(f"真实基数 1000，估计 ≈ {hll.estimate()}")
```

## 应用场景实战

### 场景一：用布隆过滤器做缓存穿透防护

```python
import hashlib

class CacheWithBloom:
    """先问布隆过滤器，再查缓存/数据库，拦截不存在的 key。"""
    def __init__(self, size=256, k=4):
        self.bloom = BloomFilter(size, k)
        self.cache = {}          # 模拟 Redis
        self.db = {"user:1": "Alice", "user:2": "Bob"}   # 模拟数据库

    def warmup(self):
        for key in self.db:
            self.bloom.add(key)

    def get(self, key):
        if not self.bloom.contains(key):
            return "MISS（布隆判定不存在，直接拦截，不打 DB）"
        if key in self.cache:
            return self.cache[key]
        if key in self.db:
            self.cache[key] = self.db[key]
            return self.db[key]
        return "MISS"

cw = CacheWithBloom()
cw.warmup()
print(cw.get("user:1"))        # 命中
print(cw.get("user:999"))      # 布隆拦截，不查库
```

### 场景二：用 HLL 估算海量日志的独立访客数

```text
场景：统计某日亿级日志中的独立设备数（UV），精确去重需上 GB 内存。

方案：
1. 每个数据分区（shard）维护一个 HLL 结构
2. 分区内把每个设备 ID 哈希后 add 进 HLL
3. 汇总时合并各分区的 HLL（按桶取最大值）
4. 用合并后的 HLL 估计全局 UV，误差约 1%

收益：内存从 GB 级降到 KB~MB 级，代价是可接受的近似误差。
这也是 Redis PFCOUNT、Spark approx_count_distinct 的原理。
```

```python
# 分布式去重的简化演示：合并两个分区的 HLL
class MergeableHLL:
    def __init__(self, bits=32):
        self.bits = bits
        self.max_zeros = 0

    def add(self, item):
        h = hash(item) & ((1 << self.bits) - 1)
        self.max_zeros = max(self.max_zeros, count_leading_zeros(h, self.bits))

    def merge(self, other):
        self.max_zeros = max(self.max_zeros, other.max_zeros)

    def estimate(self):
        return 2 ** self.max_zeros

shard1, shard2 = MergeableHLL(), MergeableHLL()
for i in range(500):
    shard1.add(f"device-{i}")
for i in range(300, 800):        # 与 shard1 有 200 个重叠
    shard2.add(f"device-{i}")

shard1.merge(shard2)
print(f"分区1 估计 ≈ {shard1.estimate() if False else 2 ** shard1.max_zeros}")
print(f"合并后全局估计 ≈ {shard1.estimate()}（真实 = 800）")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 需要精确判断存在性用哈希表；只需「大概率存在」且内存敏感用布隆过滤器
2. 布隆过滤器按误判率反推参数：k = (m/n)·ln2，m = -n·ln(p)/(ln2)²
3. 哈希表负载因子控制在 0.75 以内，避免冲突退化
4. 去重计数（UV/独立用户）用 HLL 近似，明确告知业务误差而非假装精确
5. 布隆过滤器不支持删除，需要删除时用计数布隆（Counting Bloom Filter）
6. 分布式去重让各分片算 HLL 再合并，避免全局去重的 shuffle 开销

### 踩坑记录

```text
坑 1：把布隆过滤器的「可能存在」当成「一定存在」
结论：误判导致业务逻辑错误（如误放行不存在的订单）。
原因：布隆有假阳性，contains 返回 True 不代表元素真的在集合里。
解法：布隆只能做「第一道拦截」，需要精确结果时用哈希表二次确认。

坑 2：布隆过滤器位数组太小导致误判率爆表
结论：误判率远超预期，拦截形同虚设。
原因：m/n 太小，位数组很快全置 1，几乎所有查询都返回 True。
解法：先按数据量和目标误判率算 m 和 k，别拍脑袋定大小。

坑 3：用 HLL 估计小基数（<几百）误差极大
结论：基数很小时 HLL 估计偏差大，甚至荒谬。
原因：HLL 依赖「足够多样本」让前导零分布符合理论，小基数下失真。
解法：小基数用 Linear Counting 修正，或基数小直接精确计数。

坑 4：哈希函数质量差导致哈希表退化
结论：冲突全聚到少数桶，查找退化成 O(n)。
原因：哈希函数分布不均，或取模用了 2 的幂导致低位相关键冲突。
解法：用质量好的哈希（如带种子的 xxHash/Murmur），桶数取质数或用掩码+扰动。
```
