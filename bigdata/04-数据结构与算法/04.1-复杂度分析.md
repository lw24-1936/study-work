## 概述

复杂度分析是评估算法「随输入规模增长，时间和空间开销如何增长」的方法，是选型、优化和面试的根基。它不关心具体机器上的绝对耗时，只关心增长趋势——用渐近记号（Big-O、Ω、Θ）描述。大数据场景下，O(n²) 与 O(n log n) 的差别在亿级数据上意味着「分钟」和「天」的差距，因此复杂度意识是写大数据代码的第一素养。

```text
三种渐近记号的含义：
1. Big-O  O(f(n)) —— 上界：算法最坏不会超过 f(n) 的增长速度
2. Ω      Ω(f(n)) —— 下界：算法至少需要 f(n) 的增长速度
3. Θ      Θ(f(n)) —— 紧确界：上界和下界一致，精确描述增长速度
```

```python
import time

def benchmark(fn, sizes):
    """测量不同规模下的耗时，观察增长趋势。"""
    for n in sizes:
        data = list(range(n))
        t0 = time.perf_counter()
        fn(data)
        t1 = time.perf_counter()
        print(f"n={n:>8}  耗时 {t1 - t0:.6f}s")

# O(n) 与 O(n^2) 的对比：后者规模翻倍耗时约翻 4 倍
def linear(data):
    s = 0
    for x in data:
        s += x
    return s

def quadratic(data):
    s = 0
    for i in data:
        for j in data[:100]:
            s += i * j
    return s

benchmark(linear, [100_000, 200_000, 400_000])
benchmark(quadratic, [100, 200, 400])
```

## Big-O

Big-O 表示算法的渐近上界：存在常数 c 和 n₀，使 n ≥ n₀ 时 T(n) ≤ c·f(n)，记 T(n) = O(f(n))。它描述「最坏情况」的增长上限，是最常用的复杂度记号。分析时只保留最高阶项并忽略常数系数——O(3n²+5n+7) 简化为 O(n²)。常见量级从快到慢：O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ)。

```text
常见 Big-O 量级与直觉：
1. O(1)       —— 常数，与输入无关（哈希查找、数组下标）
2. O(log n)   —— 每次规模减半（二分查找、平衡树）
3. O(n)       —— 遍历一遍（线性扫描）
4. O(n log n) —— 分治 + 线性合并（归并/快排平均）
5. O(n²)      —— 双重循环（朴素两两比较、冒泡）
6. O(2ⁿ)      —— 指数，穷举所有子集（n 稍大即不可行）
```

```python
# 不同复杂度的典型实现与量级标注
def o1_example(arr, i):
    return arr[i]                       # O(1)：下标访问

def ologn_example(arr, target):         # O(log n)：二分查找
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

def on_example(arr):                    # O(n)：求和
    return sum(arr)

def onlogn_example(arr):                # O(n log n)：排序
    return sorted(arr)

def on2_example(arr):                   # O(n²)：两两比较找重复
    n = len(arr)
    for i in range(n):
        for j in range(i + 1, n):
            if arr[i] == arr[j]:
                return True
    return False
```

## Ω

Ω（大 Omega）表示渐近下界：存在常数 c 和 n₀，使 n ≥ n₀ 时 T(n) ≥ c·f(n)，记 T(n) = Ω(f(n))。它描述「至少要多快/多慢」，常用于说明问题的固有难度——例如基于比较的排序最优也是 Ω(n log n)，任何比较排序都不可能突破这个下界（因为 n 个元素的排列有 n! 种，需 log₂(n!) ≈ n log n 次比较才能区分）。

```text
Ω 下界要点：
1. 下界描述「不可能比这更快」，是问题的理论极限
2. 比较排序下界 Ω(n log n) —— 决策树模型证明
3. 求无序数组最大值下界 Ω(n) —— 每个元素至少要看一眼
4. 下界不等于某算法的实际性能，而是「所有同类算法」的共性约束
```

```python
import math

def comparison_sort_lower_bound(n):
    """比较排序下界：log2(n!) ≈ n log2 n - 1.44n。"""
    return n * math.log2(n) - 1.44 * n

for n in [10, 100, 1000, 10000]:
    print(f"n={n:>5}  比较次数下界 ≈ {comparison_sort_lower_bound(n):.0f}")

# 说明：任何基于比较的排序，最坏情况下至少需要这么多次比较
# 这就是为什么 O(n log n) 的排序已经是最优，无法做到 O(n)
```

## Θ

Θ（大 Theta）表示渐近紧确界：同时满足 T(n) = O(f(n)) 和 T(n) = Ω(f(n))，记 T(n) = Θ(f(n))。它是「精确」的增长描述——算法最坏和最好（或上下界）增长一致时，用 Θ 最准确。例如线性扫描无论什么输入都恰好遍历 n 次，是 Θ(n)；而归并排序最坏与最好都是 n log n 量级，是 Θ(n log n)，但快排最好 O(n log n)、最坏 O(n²)，只能说 O(n²) 而不能说 Θ(n log n)。

```text
Θ 紧确界要点：
1. Θ(f(n)) 当且仅当同时有 O(f(n)) 和 Ω(f(n))
2. 表示「精确量级」，比单独的上界/下界更严格
3. 归并排序 Θ(n log n) —— 最好最坏一致
4. 快排只能说 O(n²)、最好 Ω(n log n)，不能给 Θ
```

```python
# 归并排序：无论输入如何，总是 Θ(n log n)
def merge_sort(arr):
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left = merge_sort(arr[:mid])
    right = merge_sort(arr[mid:])
    # 线性合并
    merged, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            merged.append(left[i]); i += 1
        else:
            merged.append(right[j]); j += 1
    merged += left[i:] + right[j:]
    return merged

# 已排序、逆序、随机三种输入，归并都是 Θ(n log n)，无退化
for arr in [[1,2,3,4,5], [5,4,3,2,1], [3,1,4,2,5]]:
    print(merge_sort(arr))
```

## 摊销分析

摊销分析（Amortized Analysis）不分析单次操作的代价，而是分析「一系列操作的总代价平均摊到每次操作」。适合「偶尔昂贵、大多廉价」的结构：动态数组扩容、栈的多重弹出、并查集的路径压缩。常见三种方法：聚合分析（直接算总代价）、记账法（每次操作预存「信用」）、势能法（用势能函数刻画结构状态）。结论如「动态数组 push 摊销 O(1)」。

```text
摊销分析要点：
1. 摊销 ≠ 平均 —— 摊销是「最坏情况下序列操作的均摊」，不是概率平均
2. 动态数组 —— 满时扩容一倍，单次扩容 O(n)，但摊销每次 push 仍是 O(1)
3. 记账法 —— 廉价操作预付费，补贴之后的昂贵操作
4. 势能法 —— 势能增量 = 摊销代价 - 实际代价，总势能非负保证上界成立
```

```python
# 动态数组扩容的摊销分析演示
class DynamicArray:
    def __init__(self):
        self.capacity = 1
        self.size = 0
        self.data = [None] * 1
        self.copy_ops = 0        # 累计拷贝元素次数

    def push(self, x):
        if self.size == self.capacity:
            self._resize(self.capacity * 2)
        self.data[self.size] = x
        self.size += 1

    def _resize(self, new_cap):
        new_data = [None] * new_cap
        for i in range(self.size):
            new_data[i] = self.data[i]
            self.copy_ops += 1   # 每拷贝一个元素计一次
        self.data = new_data
        self.capacity = new_cap

arr = DynamicArray()
n = 1000
for i in range(n):
    arr.push(i)

# 总拷贝次数约 2n，摊到每次 push 是 O(1)
print(f"插入 {n} 次，总拷贝 {arr.copy_ops} 次，摊销 {arr.copy_ops / n:.2f} 次/操作")
```

## 应用场景实战

### 场景一：为「查重」选择 O(n²) 还是 O(n)

```python
import time, random

def has_duplicate_naive(arr):
    """O(n²)：两两比较。"""
    n = len(arr)
    for i in range(n):
        for j in range(i + 1, n):
            if arr[i] == arr[j]:
                return True
    return False

def has_duplicate_hash(arr):
    """O(n)：哈希集合。"""
    seen = set()
    for x in arr:
        if x in seen:
            return True
        seen.add(x)
    return False

n = 5000
data = list(range(n)) + [0]     # 构造重复元素
t0 = time.perf_counter(); has_duplicate_naive(data); t1 = time.perf_counter()
print(f"O(n²) 查重耗时 {t1 - t0:.4f}s")
t0 = time.perf_counter(); has_duplicate_hash(data); t1 = time.perf_counter()
print(f"O(n)  查重耗时 {t1 - t0:.4f}s")
```

### 场景二：用复杂度预估大数据任务的可行性

```text
数据规模 n = 1 亿（10^8），单机每秒处理 10^8 次简单操作：

O(n)         → 1 秒         ✓ 可行
O(n log n)   → ~27 秒       ✓ 可行
O(n²)        → 10^16 次     ✗ 约 3 年，不可行
O(2ⁿ)        → 天文数字     ✗ 完全不可行

结论：面对亿级数据，只接受 O(n) 或 O(n log n) 的算法；
      O(n²) 必须用哈希/索引/排序优化，否则无法落地。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分析复杂度只留最高阶项、去常数，写 O(n log n) 而不是 O(3n log n + 5n)
2. 区分最坏、平均、最好情况，面试和文档里默认说最坏（Big-O）
3. 大数据选型先算量级：n 是千万/亿级时，只考虑 O(n) 和 O(n log n)
4. 空间复杂度同样重要，哈希表 O(n) 空间在内存受限时可能不如 O(1) 的原地算法
5. 动态扩容、字符串拼接这类「偶发昂贵」的操作，用摊销分析而不是单次分析
6. 用实际 benchmark 验证理论复杂度，防止「常数太大」让低复杂度算法反而不实用

### 踩坑记录

```text
坑 1：把 log 的底数当回事
结论：纠结 O(log₂n) 和 O(log₁₀n) 的区别，徒增困扰。
原因：换底公式 log_a n = log_b n / log_b a，底数差异只是常数倍，Big-O 里忽略。
解法：一律写 O(log n)，底数不影响渐近量级。

坑 2：误把 Python 的 in 当 O(1) 用在列表上
结论：x in list 是 O(n) 线性扫描，套循环里变成 O(n²)，代码慢到崩溃。
原因：list 的成员判断遍历元素；只有 dict/set 的 in 才是 O(1) 哈希查找。
解法：频繁成员判断用 set/dict；必须用列表时先排序再二分。

坑 3：忽略字符串拼接的摊销成本
结论：循环里 s += x 在大字符串下从 O(n) 退化成 O(n²)。
原因：字符串不可变，每次 += 都拷贝整个字符串，累计 O(n²)。
解法：用列表收集再 ''.join(parts)，摊销 O(n)。

坑 4：只看时间复杂度忽略常数因子
结论：理论上 O(n log n) 的算法在 n 小时反而比 O(n²) 慢。
原因：大 O 隐藏常数，递归/内存分配等常数开销在小规模下占主导。
解法：小规模数据直接 benchmark 实测，别盲目迷信低复杂度。
```
