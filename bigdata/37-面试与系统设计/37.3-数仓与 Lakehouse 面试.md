## 概述

数仓与 Lakehouse 面试考察「数据怎么建模、怎么存储、怎么演进」。核心主线：从传统数仓建模（维度建模、分层、SCD）到实时数仓（CDC、流批一体），再到 Lakehouse（数据湖 + 数仓能力的融合）。这部分问题考察「数据架构的演进思维」——不仅要知道「怎么做」，还要知道「为什么从 A 演进到 B」。本主题按「核心概念 + 高频面试题（含参考答案）+ 关键代码」组织。

```text
数仓与 Lakehouse 面试的考察主线：
1. 建模 —— 维度建模、分层设计、SCD 处理历史变化
2. 实时 —— 实时数仓分层、CDC 同步、流批结合
3. 演进 —— 数仓 → 数据湖 → Lakehouse 的架构演进
4. 实践 —— 拉链表、宽表、指标口径、成本与性能
```

## 数仓建模面试

数仓建模考察「怎么把业务数据组织成可分析的结构」。核心概念：维度建模（Kimball，星型/雪花模型）、数仓分层（ODS/DWD/DWS/ADS）、事实表与维度表、宽表设计。建模方法对比：范式建模（Inmon，消除冗余）vs 维度建模（Kimball，面向分析、反规范化）。高频题：星型与雪花模型区别、为什么分层、事实表类型、宽表 vs 多表 join。

```text
数仓建模高频面试题：
1. 星型 vs 雪花模型 —— 维度是否规范化，星型冗余少 join，雪花规范化省空间
2. 为什么要分层 —— 解耦、复用、口径统一、便于追溯
3. 事实表类型 —— 事务/周期快照/累积快照事实表
4. 维度建模 vs 范式建模 —— 面向分析 vs 面向事务，冗余换性能
5. 宽表 vs 多表 —— 宽表查询快但冗余大，多表灵活但 join 成本高
```

```text
数仓分层（面试必背）：
ODS（贴源层）：原始数据，保持与源一致
DWD（明细层）：清洗、去重、维度退化，明细数据
DWS（汇总层）：轻度汇总，按主题聚合
ADS（应用层）：面向报表/指标的最终结果
```

```sql
-- 维度建模：DWD 订单明细表 + 维度表关联
CREATE TABLE dwd_order_detail (
    order_id      BIGINT,
    user_id       BIGINT,
    product_id    BIGINT,
    amount        DECIMAL(18,2),
    order_time    TIMESTAMP,
    dt            STRING          -- 分区字段
) PARTITIONED BY (dt);

-- 事实表（订单）与维度表（用户）关联做分析
SELECT u.city, COUNT(o.order_id) AS order_cnt, SUM(o.amount) AS total_amt
FROM dwd_order_detail o
JOIN dim_user u ON o.user_id = u.user_id
WHERE o.dt = '2026-08-14'
GROUP BY u.city;
```

## SCD 面试

SCD（Slowly Changing Dimension，缓慢变化维）处理「维度属性随时间变化」的问题，如用户从「普通会员」升级为「VIP」。处理策略：SCD Type 0（不变化）、Type 1（覆盖，丢历史）、Type 2（新增行，保留历史）、Type 3（增加列，保留前值）、Type 4（历史表分离）、Type 6（混合，1+2+3 结合）。高频题：SCD 有哪些类型、Type 1 和 Type 2 区别、什么时候用 Type 2。

```text
SCD 高频面试题：
1. SCD 是什么 —— 维度属性随时间缓慢变化，需记录变化历史
2. Type 1 vs Type 2 —— 覆盖丢历史 vs 新增行保留历史
3. Type 2 怎么标识 —— 代理键 + 生效/失效时间 + 当前标记（is_current）
4. Type 3 —— 增加「原值」列，只保留最近一次变化
5. 什么时候用 Type 2 —— 需要追溯历史变化的维度（如会员等级）
```

```text
SCD 各类型对比（面试必背）：
Type 0：保留原值，永不更新 —— 生日、身份证号
Type 1：直接覆盖，不保留历史 —— 手机号、收货地址
Type 2：新增行 + 时间戳，保留全历史 —— 会员等级、部门
Type 3：加列存前值，只保留上一次 —— 少量变化的属性
```

```sql
-- SCD Type 2：用户会员等级变更（保留历史）
CREATE TABLE dim_user_scd2 (
    user_sk        BIGINT,          -- 代理键（唯一标识一行）
    user_id        BIGINT,          -- 业务键
    member_level   STRING,
    start_date     DATE,            -- 生效时间
    end_date       DATE,            -- 失效时间（9999-12-31 表示当前有效）
    is_current     BOOLEAN          -- 当前标记
);

-- 新增变更：关闭旧记录，开启新记录
UPDATE dim_user_scd2 SET end_date = '2026-08-14', is_current = FALSE
WHERE user_id = 1001 AND is_current = TRUE;

INSERT INTO dim_user_scd2 VALUES
(2002, 1001, 'VIP', '2026-08-14', '9999-12-31', TRUE);
```

## 拉链表面试

拉链表是 SCD Type 2 在数仓中的工程实现，用「生效时间 + 失效时间」记录一条记录在时间轴上的多个状态版本，既保留历史又避免数据膨胀。核心：每条记录有 start_date/end_date，当前有效记录的 end_date 为「9999-12-31」；变更时「关旧开新」。高频题：拉链表原理、为什么用拉链表（省空间）、拉链表怎么更新、拉链表 vs 全量快照。

```text
拉链表高频面试题：
1. 拉链表是什么 —— 用时间区间记录维度变化历史，Type 2 的实现
2. 为什么用拉链表 —— 相比每日全量快照，只存变化，大幅省存储
3. 怎么更新 —— 变化时关闭旧记录（改 end_date）、插入新记录
4. 怎么查某天状态 —— where start_date <= '某天' and end_date > '某天'
5. 拉链表 vs 全量快照 —— 省空间但查询复杂，快照简单但冗余大
```

```text
拉链表 vs 每日全量快照（面试必背）：
全量快照：每天存一份全量，简单但 90% 数据重复
拉链表：只存「变化」记录，用时间区间表示状态，存储大幅缩减
适用：变化缓慢的维度（用户等级、状态），不适合高频变化字段
```

```sql
-- 拉链表更新：全量比对，关旧开新
-- 1. 关闭已变化的旧记录
UPDATE dim_user_zip a
SET end_date = '2026-08-13'
WHERE a.end_date = '9999-12-31'
  AND EXISTS (
      SELECT 1 FROM ods_user_today b
      WHERE a.user_id = b.user_id AND a.member_level != b.member_level
  );

-- 2. 插入变化的新记录
INSERT INTO dim_user_zip
SELECT b.user_id, b.member_level, '2026-08-14', '9999-12-31'
FROM ods_user_today b
WHERE NOT EXISTS (
    SELECT 1 FROM dim_user_zip a
    WHERE a.user_id = b.user_id AND a.member_level = b.member_level
      AND a.end_date = '9999-12-31'
);
```

## 实时数仓面试

实时数仓是在传统离线数仓基础上引入实时计算，实现「秒级/分钟级」数据新鲜度。核心概念：实时分层（ODS/DWD/DWS/ADS 的实时化）、Lambda 架构（批 + 流双链路）与 Kappa 架构（纯流）、流批一体（Flink 统一）、实时指标计算。高频题：Lambda vs Kappa、实时数仓怎么分层、实时和离线怎么保证口径一致、实时数仓的挑战（数据延迟、一致性、成本）。

```text
实时数仓高频面试题：
1. Lambda vs Kappa —— 批流双链路（维护成本高）vs 纯流（重放补数）
2. 实时分层 —— ODS(DWD)/DWS/ADS 实时化，DWD 明细、DWS 聚合
3. 口径一致性 —— 实时与离线用同一套模型和口径，对账校验
4. 实时数仓挑战 —— 乱序、延迟、状态大、回放补数难
5. 实时 vs 离线 —— 新鲜度 vs 准确性，实时用于监控、离线用于出报表
```

```text
Lambda 与 Kappa 架构（面试必背）：
Lambda：离线批处理（准确）+ 实时流处理（快）双链路，结果合并
  优点：各自最优；缺点：两套代码、口径难一致
Kappa：只保留流处理，用「消息队列重放」做历史重算
  优点：一套代码；缺点：重放计算成本高、历史大状态难处理
```

```text
实时数仓分层（面试必背）：
ODS：Kafka 原始 topic（CDC/埋点数据）
DWD：明细层（清洗、关联维表、打宽）
DWS：汇总层（预聚合、去重，如每分钟 UV/PV）
ADS：应用层（结果写 Redis/MySQL/OLAP 供查询）
```

## CDC 面试

CDC（Change Data Capture，变更数据捕获）捕获数据库的增量变更（Insert/Update/Delete），实时同步到下游。实现方式：基于查询（轮询时间戳/版本，有延迟）、基于日志（Binlog/Redo Log，低延迟高保真）。主流工具：Flink CDC、Debezium、Canal。高频题：CDC 原理、全量 + 增量怎么结合、CDC 怎么保证顺序和一致性、Flink CDC 和 Canal 区别。

```text
CDC 高频面试题：
1. CDC 是什么 —— 捕获数据库增量变更，同步到下游
2. 基于日志 vs 基于查询 —— Binlog 低延迟 vs 轮询有延迟有漏改风险
3. 全量 + 增量 —— 先全量快照，再从 binlog 位点接增量（无缝衔接）
4. 顺序保证 —— 按主键 + 事务顺序处理，binlog 本身有序
5. Flink CDC —— 集成到 Flink，全增量一体化，支持断点续传
```

```text
CDC 同步流程（面试必背）：
1. 全量阶段：快照读取存量数据（一致性快照，记录 binlog 位点）
2. 增量阶段：从记录位点开始消费 binlog，捕获增删改
3. 下游写入：按主键 upsert 到目标表，保证幂等
4. 断点续传：保存位点，失败后从位点恢复
```

```yaml
# Flink CDC 同步 MySQL 到数据湖（示例配置）

  port: 3306
  username: root

sink:

  path: hdfs:///warehouse/order_db/order_info
  write.format: parquet
```

## Lakehouse 面试

Lakehouse 是「数据湖 + 数仓」的融合架构：数据湖的低成本存储 + 数仓的 ACID 事务、Schema 演进、高性能查询。核心组件：Iceberg、Hudi、Delta Lake 三大开放表格式。核心能力：ACID 事务、时间旅行（Time Travel）、Schema 演进、增量读取。高频题：Lakehouse 和传统数仓区别、三大表格式对比、为什么需要 ACID、时间旅行原理。

```text
Lakehouse 高频面试题：
1. Lakehouse 是什么 —— 湖仓一体，湖的低成本 + 仓的事务与管理
2. 为什么需要 ACID —— 并发写入、读一致性、支持 upsert/删除
3. 时间旅行 —— 通过快照/snapshot 回溯历史版本数据
4. 三大表格式 —— Iceberg/Hudi/Delta，元数据层 + 数据文件
5. Lakehouse vs 传统数仓 —— 存储计算分离、开放格式、成本低
```

```text
三大表格式对比（面试必背）：
Iceberg：通用表格式，Schema 演进强，生态广（Spark/Flink/Trino）
Hudi：面向增量 upsert，强调流式写入与数据服务（MOR/COW）
Delta Lake：与 Spark 深度集成，事务日志 + 版本管理
共同点：都是「元数据 + 数据文件」的开放表格式，实现 ACID 与时间旅行
```

```sql
-- Iceberg 时间旅行：查询历史版本
SELECT * FROM orders
FOR SYSTEM_VERSION AS OF '2026-08-14 10:00:00';   -- 按时间点

SELECT * FROM orders
FOR SYSTEM_VERSION AS OF 1234567890;               -- 按快照 ID
```

## 应用场景实战

### 场景一：手撕「SCD Type 2 拉链表更新」

面试题：用户维度表每天同步，会员等级会变化，设计拉链表并写出「关旧开新」的更新逻辑。

```sql
-- 拉链表结构
CREATE TABLE dim_user_zip (
    user_id      BIGINT,
    member_level STRING,
    start_date   DATE,
    end_date     DATE,          -- 9999-12-31 表示当前有效
    is_current   INT            -- 1 当前有效，0 已失效
);

-- 每日更新：关旧（等级变化的旧记录）
UPDATE dim_user_zip a
SET end_date = '2026-08-13', is_current = 0
WHERE a.is_current = 1
  AND a.member_level != (
      SELECT member_level FROM ods_user b WHERE b.user_id = a.user_id
  );

-- 开新（插入变化后的新记录）
INSERT INTO dim_user_zip
SELECT b.user_id, b.member_level, '2026-08-14', '9999-12-31', 1
FROM ods_user b
WHERE NOT EXISTS (
    SELECT 1 FROM dim_user_zip a
    WHERE a.user_id = b.user_id AND a.member_level = b.member_level
      AND a.is_current = 1
);
```

### 场景二：手撕「实时数仓每分钟 UV 统计」

面试题：用 Flink SQL 实现实时数仓的每分钟 UV（按用户去重）统计。

```sql
-- 实时数仓 DWS 层：每分钟 UV 去重统计
CREATE TABLE ods_user_visit (
    user_id   BIGINT,
    page_id   STRING,
    event_time TIMESTAMP(3),
    WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND
) WITH (
    'connector' = 'kafka',
    'topic' = 'ods_user_visit',
    'format' = 'json'
);

-- 用 ROW_NUMBER 或窗口去重计算 UV
SELECT
    TUMBLE_START(event_time, INTERVAL '1' MINUTE) AS window_start,
    COUNT(DISTINCT user_id) AS uv
FROM ods_user_visit
GROUP BY TUMBLE(event_time, INTERVAL '1' MINUTE);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 答建模题先讲「为什么分层」，再讲「每层做什么」，体现架构思维
2. SCD 和拉链表要结合讲：拉链表是 SCD Type 2 的工程实现，用时间区间存历史
3. Lambda/Kappa、三大表格式这类「对比题」，用「结构 + 优缺点 + 适用场景」结构回答
4. CDC 题把「全量 + 增量 + 断点续传」串成完整流程，体现落地能力
5. 实时数仓题强调「口径一致性」和「对账」，这是工程实践的重点

### 踩坑记录

```text
坑 1：SCD Type 1 和 Type 2 记反
结论：答「Type 1 保留历史、Type 2 覆盖」。
原因：只背名字没理解「1 覆盖、2 加行」的本质。
解法：记牢「Type 1 覆盖丢历史、Type 2 新增行保留历史、Type 3 加列」。

坑 2：拉链表的 end_date 用 NULL 而不是 9999-12-31
结论：当前有效记录用 NULL 标记，查询时需要额外判断 IS NULL。
原因：没理解「9999-12-31」作为「当前有效」哨兵值的约定。
解法：统一用 9999-12-31 表示当前有效，查询只需 between 即可。

坑 3：实时数仓只讲快，不讲口径一致性
结论：答「实时就是快」，忽略实时离线口径不一致的问题。
原因：没意识到实时与离线双链路的口径对账是工程难点。
解法：强调「统一模型 + 口径对账 + 数据补偿」保证一致性。

坑 4：CDC 只答「读 Binlog」不讲全量衔接
结论：答不出「存量数据怎么同步」。
原因：忽略了 CDC 需要「全量快照 + 增量衔接」的完整方案。
解法：完整流程 = 一致性快照（记录位点）→ 从位点接增量 → 断点续传。

坑 5：把 Lakehouse 答成「数据湖」
结论：混淆数据湖和湖仓一体，答不出 ACID/时间旅行。
原因：没理解 Lakehouse 的核心是「给数据湖加上事务与表管理」。
解法：Lakehouse = 数据湖存储 + ACID 事务 + Schema 演进 + 时间旅行。
```
