## 概述

大数据岗位的系统设计面试，考的是「从需求到架构」的完整能力：数据平台（离线/实时数仓）、推荐系统、搜索系统、日志系统、Lakehouse。答题套路是「澄清需求 → 估算规模 → 分层架构 → 关键技术选型 → 权衡与演进」。面试官看重的是「为什么这样选」和「瓶颈怎么解决」，而不是背架构图。本主题每个知识点都给出「设计思路 + 架构图 + 高频面试题」，架构图用 ```text 绘制。

```text
系统设计面试的答题套路：
1. 澄清需求 —— 数据量/QPS/延迟/一致性要求
2. 估算规模 —— 存储量、吞吐量、机器数
3. 分层架构 —— 采集/存储/计算/服务 各层职责
4. 技术选型 —— 为什么选 A 不选 B，给出理由
5. 权衡演进 —— 瓶颈、容错、扩展、成本
```

## 数据平台设计

数据平台设计面试考「离线数仓 + 数据服务」的整体架构：数据源接入（业务库/日志）→ 采集（Sqoop/Canal/Flume）→ ODS 层 → DWD/DWS/ADS 分层建模 → 调度 → 数据服务（API/报表）。高频题：设计一个电商数据平台、数仓怎么分层、怎么保证数据质量、元数据管理怎么做。答题要点是「先画分层架构，再讲每层的存储和计算引擎」。

```text
数据平台分层架构：
数据源 → 采集 → 存储 → 计算 → 服务
  │        │       │       │       │
 业务库    Canal   ODS     Hive    API
 日志      Flume   DWD     Spark   BI 报表
 埋点      SDK     DWS     Flink   指标平台
                   ADS     Trino   数据 API
```

```text
数据平台高频面试题：
1. 数仓怎么分层 —— ODS/DWD/DWS/ADS，每层职责不同
2. 技术选型 —— Hive 离线批处理、Spark 复杂计算、Trino 即席查询
3. 数据质量怎么保证 —— 规则校验、血缘追踪、监控告警
4. 元数据管理 —— Atlas/DataHub 统一管理表和血缘
5. 调度系统 —— DolphinScheduler/Airflow 管理任务依赖
```

## 实时平台设计

实时平台设计面试考「实时数仓 + 实时计算」：数据源（业务变更/埋点）→ CDC 采集（Canal/Flink CDC）→ Kafka 消息缓冲 → Flink 实时计算 → 实时存储（ClickHouse/HBase）→ 实时服务（秒级指标/大屏）。高频题：设计一个实时指标平台、怎么保证 Exactly-Once、怎么处理乱序和延迟数据、实时数仓和离线数仓怎么统一。答题要点是「Kafka + Flink + OLAP」三件套 + 水位线/状态/Checkpoint 容错。

```text
实时平台架构：
业务库 → Flink CDC → Kafka → Flink 计算 → 实时存储 → 服务
  │                    │          │            │          │
 binlog               缓冲解耦   窗口/聚合      ClickHouse  大屏
 埋点 → 网关 → Kafka   幂等       状态/水位线    Redis       告警
```

```text
实时平台高频面试题：
1. 为什么用 Kafka —— 削峰填谷、解耦、多消费者、消息回溯
2. Exactly-Once 怎么保证 —— Checkpoint + 两阶段提交 + 幂等写
3. 乱序/延迟怎么处理 —— 水位线 + 延迟等待 + 侧输出流
4. 实时存储选型 —— ClickHouse 分析、Redis 缓存、HBase 明细
5. 实时 vs 离线统一 —— Lambda vs Kappa 架构
```

## 推荐系统设计

推荐系统设计面试考「召回—排序—重排」漏斗的工程化落地：离线（特征+样本+模型训练）→ 在线（召回+排序+重排服务）→ 特征平台（实时特征+离线特征）。高频题：设计一个短视频推荐系统、召回怎么做的、怎么支持实时兴趣、多目标怎么融合。答题要点是「漏斗 + 特征平台 + 模型服务」三层，重点讲清「在线链路低延迟」和「实时特征」。

```text
推荐系统架构：
在线：请求 → 召回 → 粗排 → 精排 → 重排 → 返回
              │       │       │       │
           双塔/CF  向量ANN  DeepFM  多样性/去重
离线：特征平台 → 样本拼接 → 模型训练 → 模型推送
实时：用户行为 → Kafka → 实时特征 → 在线模型
```

```text
推荐系统设计高频面试题：
1. 召回怎么设计 —— 多路召回（协同过滤/向量/热门）合并
2. 怎么支持实时兴趣 —— 实时行为特征 + 在线更新
3. 特征平台怎么设计 —— 离线特征/实时特征统一存储和读取
4. 多目标怎么融合 —— 加权/MMOE/排序公式
5. 冷启动怎么处理 —— 内容画像 + 探索流量
```

## 搜索系统设计

搜索系统设计面试考「离线索引 + 在线检索」：离线（爬虫/数据同步 → 文档处理 → 倒排索引构建）→ 在线（Query 理解 → 召回 → 相关性排序 → 重排）。高频题：设计一个商品搜索系统、倒排索引怎么构建、怎么支持实时更新、相关性怎么打分。答题要点是「索引构建 + 检索链路」两端，重点讲清「倒排索引结构」和「Query 理解 + 排序」。

```text
搜索系统架构：
离线：数据源 → 清洗/分词 → 索引构建（ES/Lucene）→ 索引分发
在线：Query → 理解（分词/纠错/改写）→ 召回（倒排）→ 排序（BM25/LTR）→ 返回
实时：商品变更 → 消息队列 → 增量索引更新
```

```text
搜索系统设计高频面试题：
1. 倒排索引怎么构建 —— 词项 → 文档列表，支持增量更新
2. 为什么用 ES —— 分布式倒排索引 + 近实时搜索
3. 相关性怎么打分 —— BM25 + 业务因子（销量/热度）
4. 怎么支持实时更新 —— 增量索引 + 段合并
5. Query 理解怎么做 —— 分词、纠错、同义词、意图识别
```

## 日志系统设计

日志系统设计面试考「采集 → 传输 → 存储 → 检索」链路：应用日志 → 采集 Agent（Filebeat/Fluentd）→ Kafka 缓冲 → 处理（Logstash/Flink）→ 存储（Elasticsearch/ClickHouse）→ 检索展示（Kibana）。高频题：设计一个日志分析系统、怎么支撑高吞吐写入、怎么保证不丢日志、日志怎么检索。答题要点是「采集解耦 + Kafka 缓冲 + ES 检索」三段，重点讲清「高吞吐」和「检索」两个难点。

```text
日志系统架构：
应用 → Filebeat → Kafka → Logstash → Elasticsearch → Kibana
  │       │         │         │           │            │
  落盘   轻量采集   削峰解耦   解析/清洗     倒排检索      可视化
  防丢   多路传输   多消费者    字段抽取      分片存储      告警
```

```text
日志系统设计高频面试题：
1. 怎么支撑高吞吐 —— 采集落盘 + Kafka 缓冲 + 批量写入
2. 怎么保证不丢日志 —— Filebeat 落盘确认 + Kafka 持久化
3. 为什么用 ES 存储 —— 倒排索引 + 全文检索 + 聚合
4. 日志怎么检索 —— 倒排索引 + 时间分片 + 字段过滤
5. 冷热分离怎么做 —— 热数据 ES、冷数据对象存储
```

## Lakehouse 设计

Lakehouse 设计面试考「数据湖 + 数仓融合」：对象存储（S3/HDFS）作为统一底座，开放表格式（Iceberg/Hudi/Delta Lake）提供 ACID、Schema 演进、时间旅行，上层计算引擎（Spark/Flink/Trino）统一访问。高频题：设计一个 Lakehouse、为什么用 Iceberg、怎么保证 ACID、怎么做增量读取。答题要点是「存储计算分离 + 开放表格式」核心思想，重点讲清「表格式解决什么问题」。

```text
Lakehouse 架构：
计算层：Spark / Flink / Trino / Presto（同一份数据多种引擎）
  │
表格式：Iceberg / Hudi / Delta Lake（元数据 + ACID + 演进）
  │
存储层：对象存储 S3 / HDFS / OSS（廉价、可扩展）
  │
治理层：数据目录 + 权限 + 血缘 + 质量
```

```text
Lakehouse 设计高频面试题：
1. 为什么用 Lakehouse —— 湖的低成本 + 仓的 ACID/性能
2. Iceberg 解决什么问题 —— ACID、Schema 演进、时间旅行、隐藏分区
3. 怎么保证 ACID —— 快照隔离 + 乐观并发 + 元数据提交
4. 增量读取怎么做 —— Iceberg 快照 + Hudi 增量视图
5. 湖仓怎么选型 —— 看更新需求（CDC 选 Hudi，分析选 Iceberg）
```

## 应用场景实战

### 场景一：设计一个「实时指标平台」

```text
需求：电商大促，秒级统计 GMV、下单量、UV，支撑大屏和告警。

架构设计：
1. 采集：业务库 binlog → Flink CDC → Kafka（订单/支付主题）
2. 计算：Flink 消费 Kafka，做窗口聚合（1 分钟滚动窗口）
   - 状态存储：RocksDB 状态后端
   - 容错：Checkpoint（Exactly-Once）
   - 乱序：水位线 + 允许迟到 + 侧输出流
3. 存储：聚合结果写 ClickHouse（按分钟粒度）
4. 服务：指标 API 读 ClickHouse + Redis 缓存最新值
5. 对账：离线数仓 T+1 对账，修正实时误差

关键点：Kafka 削峰、Flink 状态容错、ClickHouse 秒级聚合、
        幂等写（去重）、水位线处理乱序。
```

### 场景二：设计一个「短视频推荐系统」

```text
需求：日活千万，Feed 流推荐，用户刷到喜欢的内容。

架构设计：
1. 召回（多路）：双塔向量召回（ANN）+ 协同过滤 + 热门兜底
   - 向量索引：HNSW（百万级候选，毫秒级返回）
2. 粗排：轻量模型过滤到百级候选
3. 精排：DeepFM/多目标模型，输出点击率/时长/完播率
4. 重排：多样性打散、去重、广告插入
5. 特征平台：离线特征（画像）+ 实时特征（最近行为）
6. 模型服务：模型线上化 + A/B 实验评估

关键点：多路召回保召回率、ANN 保低延迟、多目标融合、
        实时特征捕捉短期兴趣、A/B 实验驱动迭代。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 答题先「澄清需求 + 估算规模」，别直接画架构图
2. 架构图用「分层 + 数据流向」表达，每层标注技术选型
3. 每个选型都要给「为什么」，如「Kafka 用于削峰解耦」
4. 主动讲「瓶颈和演进」，如「数据量大后怎么分片、怎么扩容」
5. 用「Lambda vs Kappa」展示对架构演进的深度理解

### 踩坑记录

```text
坑 1：直接背架构图，不澄清需求
结论：答错方向，比如要求低延迟却设计了离线批处理。
原因：系统设计第一步是澄清「数据量/QPS/延迟/一致性」。
解法：先问清需求再设计，边设计边确认规模假设。

坑 2：技术选型只报名字不说理由
结论：被追问「为什么用 Flink 不用 Spark Streaming」答不出。
原因：选型理由才是考察重点，不是背组件清单。
解法：每个选型都补一句「因为 X 场景需要 Y 特性，所以选 Z」。

坑 3：忽略容错和一致性
结论：设计出「单点故障 + 丢数据」的架构。
原因：只画了主链路，没考虑 Exactly-Once、Checkpoint、副本。
解法：主动讲「容错：Checkpoint/副本/重试，一致性：幂等/两阶段提交」。

坑 4：实时和离线混为一谈
结论：把实时指标和离线报表用同一套链路设计。
原因：没理解「实时秒级 vs 离线 T+1」的延迟和成本差异。
解法：明确「实时用 Kafka+Flink+OLAP，离线用 Hive/Spark 批处理」。

坑 5：只讲存储不检索
结论：日志/搜索设计里忽略了「怎么查」。
原因：只关注写入吞吐，忘了检索是系统的核心能力。
解法：日志系统讲「倒排索引 + 字段过滤」，搜索系统讲「相关性排序」。
```
