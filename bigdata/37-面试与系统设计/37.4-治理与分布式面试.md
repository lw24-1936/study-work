## 概述

治理与分布式面试覆盖两类「进阶」考察：一是数据治理（数据质量、元数据、血缘、规范），考察「数据平台的工程化与规范化能力」；二是分布式系统（CAP、一致性、共识、事务），考察「底层理论功底」，以及由此延伸的性能优化与容量规划（考察「生产环境的实战经验」）。这部分问题常出现在中高级岗位和系统设计环节。本主题按「核心概念 + 高频面试题（含参考答案）+ 关键代码」组织。

```text
治理与分布式面试的考察主线：
1. 数据质量 —— 质量维度、规则、监控、修复
2. 数据治理 —— 元数据、血缘、规范、安全、成本
3. 分布式系统 —— CAP、一致性、共识、分布式事务
4. 性能优化 —— SQL/存储/计算/网络优化方法论
5. 容量规划 —— 估算、扩容、资源治理
```

## 数据质量面试

数据质量考察「怎么保证数据的准确、完整、及时」。核心概念：质量维度（准确性、完整性、一致性、及时性、唯一性、有效性）、质量规则（空值检查、唯一性检查、范围检查、一致性校验）、质量监控（事前/事中/事后）、数据质量平台（规则配置 + 自动校验 + 告警）。高频题：数据质量有哪些维度、怎么设计质量监控、数据质量问题怎么定位修复、质量平台怎么建设。

```text
数据质量高频面试题：
1. 质量六维度 —— 准确性/完整性/一致性/及时性/唯一性/有效性
2. 质量规则类型 —— 空值/唯一/范围/格式/引用完整性/业务规则
3. 监控时机 —— 事前（源头校验）、事中（ETL 检查）、事后（结果监控）
4. 问题定位 —— 血缘回溯 + 规则命中 + 分层排查
5. 质量平台 —— 规则配置化 + 自动执行 + 告警 + 质量报告
```

```text
数据质量六维度（面试必背）：
准确性：数据与真实值一致（金额正确）
完整性：无缺失（必填字段不为空）
一致性：跨表/跨系统口径一致（同名同义）
及时性：数据按时产出（T+1 不延迟）
唯一性：无重复记录（主键唯一）
有效性：符合格式与范围（日期格式、枚举合法）
```

```sql
-- 数据质量规则示例：空值检查 + 唯一性检查
SELECT COUNT(*) AS null_cnt
FROM dwd_order_detail
WHERE amount IS NULL OR user_id IS NULL;        -- 空值检查

SELECT order_id, COUNT(*) AS dup_cnt
FROM dwd_order_detail
GROUP BY order_id
HAVING COUNT(*) > 1;                             -- 唯一性检查（重复主键）
```

## 数据治理面试

数据治理是「对数据资产进行规划、管理和控制的体系」，覆盖数据质量、元数据、数据血缘、数据安全、数据成本、数据规范全生命周期。核心概念：元数据管理（技术/业务元数据）、数据血缘（表/字段级血缘，追踪数据流向）、数据目录（资产的检索与发现）、数据安全（权限、脱敏、审计）、成本治理（存储/计算成本）。高频题：数据治理包含什么、元数据和血缘的作用、怎么建设数据治理体系、数据成本怎么优化。

```text
数据治理高频面试题：
1. 数据治理范围 —— 元数据、血缘、质量、安全、成本、规范
2. 元数据作用 —— 描述数据（是什么、在哪、谁负责），支撑检索与血缘
3. 血缘作用 —— 追踪数据从源到表的流向，影响分析与问题定位
4. 成本治理 —— 存储治理（冷热分层、压缩）计算治理（调度优化、资源）
5. 治理体系 —— 组织 + 制度 + 平台 + 运营四位一体
```

```text
数据治理四大支柱（面试必背）：
组织：数据治理委员会、数据 owner、数据管理员
制度：命名规范、口径定义、质量 SLA、权限审批
平台：元数据/血缘/质量/目录/审计等工具支撑
运营：质量报告、成本分析、问题闭环、持续改进
```

```text
数据血缘的作用（面试必背）：
1. 影响分析 —— 上游表变更影响哪些下游表
2. 问题定位 —— 数据异常回溯到源头
3. 口径追溯 —— 指标怎么算出来的，源是什么
4. 合规审计 —— 数据流向可审计，满足监管要求
```

## 分布式系统面试

分布式系统考察「多机协同的理论基础」。核心概念：CAP 定理（一致性、可用性、分区容错性三者不可兼得）、BASE 理论（基本可用、软状态、最终一致）、一致性模型（强一致/最终一致/因果一致）、分布式共识（Paxos/Raft）、分布式事务（2PC/3PC/TCC/Saga）。高频题：CAP 定理、Raft 选举过程、2PC 和 TCC 区别、一致性哈希、分布式锁。

```text
分布式系统高频面试题：
1. CAP 定理 —— 分区发生时，一致性和可用性只能选一个
2. Raft 选举 —— 任期 + 投票，多数派选出 Leader
3. 2PC vs TCC —— 资源层两阶段 vs 业务层 Try/Confirm/Cancel
4. 一致性哈希 —— 环上定位，节点增减只影响局部，虚拟节点均衡
5. 分布式锁 —— Redis setnx + 过期，或 ZooKeeper 临时顺序节点
```

```text
CAP 定理（面试必背）：
C（一致性）：所有节点同一时刻数据一致
A（可用性）：每个请求都能得到响应（不保证最新）
P（分区容错）：网络分区发生时系统仍能工作
结论：P 必须满足，C 与 A 二选一（如 ZK 选 CP，Eureka 选 AP）
```

```text
分布式事务方案（面试必背）：
2PC：协调者 + 参与者，prepare/commit 两阶段，同步阻塞
TCC：Try（预留）/Confirm（确认）/Cancel（回滚），业务层实现
Saga：长事务拆成多个本地事务 + 补偿，最终一致
消息事务：本地事务 + 消息表/事务消息，异步最终一致
```

```java
// 分布式锁：Redis setnx + 过期时间（防止死锁）
public boolean tryLock(String key, String value, long expireSeconds) {
    // SET key value NX EX seconds，原子操作
    String result = jedis.set(key, value,
        new SetParams().nx().ex(expireSeconds));
    return "OK".equals(result);
}

public void unlock(String key, String value) {
    // Lua 脚本保证「判断 value + 删除」原子性，避免误删别人的锁
    String script = "if redis.call('get', KEYS[1]) == ARGV[1] " +
                    "then return redis.call('del', KEYS[1]) else return 0 end";
    jedis.eval(script, Collections.singletonList(key),
               Collections.singletonList(value));
}
```

## 性能优化面试

性能优化考察「系统变慢后怎么系统性地定位和解决」。核心方法论：先监控定位瓶颈（CPU/IO/网络/内存），再针对性优化。覆盖 SQL 优化（索引、执行计划、谓词下推）、存储优化（列式、压缩、分区）、计算优化（并行度、数据倾斜、Shuffle）、网络优化（广播、本地化）。高频题：慢查询怎么排查、数据倾斜怎么解决、并行度怎么定、GC 调优。

```text
性能优化高频面试题：
1. 慢查询排查 —— EXPLAIN 看执行计划 → 定位全表扫描/倾斜/join 顺序
2. 数据倾斜 —— 加盐、Map 端预聚合、广播小表、Skew Join
3. 并行度怎么定 —— 分区数 = 核数 * 2~3 倍，避免过多小任务
4. 存储优化 —— 列式存储 + 压缩 + 分区裁剪 + 谓词下推
5. GC 调优 —— 堆内存、垃圾回收器选择、避免大对象
```

```text
性能优化方法论（面试必背）：
1. 定位 —— 监控指标（CPU/内存/IO/网络/GC）确定瓶颈类型
2. 分层 —— 是 SQL 问题、计算问题、存储问题还是网络问题
3. 对症 —— SQL 看执行计划，计算看倾斜/并行度，存储看格式/分区
4. 验证 —— 优化前后对比基准测试，确认收益
```

```text
数据倾斜的常见场景与解法（面试必背）：
场景：group by/join 的某个 key 数据量极大（如热点用户）
解法：
  1. 加盐打散 —— 大 key 加随机前缀，先局部聚合再去盐
  2. Map 端预聚合 —— reduceByKey 替代 groupByKey，先 map 端合并
  3. 广播小表 —— 小表 broadcast，避免 shuffle join 倾斜
  4. 单独处理 —— 大 key 单独走一条链路，其余正常处理
```

## 容量规划面试

容量规划考察「怎么估算资源、怎么设计扩容、怎么治理成本」。核心概念：容量估算（数据量、QPS、存储、计算资源）、弹性扩容（水平/垂直、自动伸缩）、资源治理（利用率、成本优化）、容量模型（存储增长预测、计算峰值预测）。高频题：怎么估算集群规模、存储怎么规划、怎么降低成本、什么时候扩容。

```text
容量规划高频面试题：
1. 集群规模估算 —— 数据量 / 单机存储 = 节点数，再加副本和安全余量
2. 存储规划 —— 冷热分层、压缩比、副本数、数据保留周期
3. 计算资源 —— 按峰值任务量 + 并行度估算核数
4. 成本优化 —— 低利用率资源回收、弹性伸缩、Spot 实例
5. 扩容时机 —— 监控阈值（存储 70%、CPU 持续 80%）触发扩容
```

```text
存储容量估算公式（面试必背）：
总存储 = 日均数据量 × 保留天数 × 副本数 × (1 / 压缩比) × 安全系数
示例：日均 10TB，保留 30 天，3 副本，压缩比 3，安全 1.3
总存储 ≈ 10 × 30 × 3 / 3 × 1.3 = 390TB
节点数 = 390TB / 单机可用容量（如 10TB）≈ 39 台
```

```text
成本治理手段（面试必背）：
1. 存储治理 —— 冷数据转低频/归档存储、删除过期数据、提高压缩比
2. 计算治理 —— 调度错峰、合并小任务、降低冗余计算
3. 资源治理 —— 回收低利用率集群、弹性伸缩、Spot 实例
4. 生命周期 —— 制定数据保留策略（热/温/冷分级）
```

## 应用场景实战

### 场景一：手撕「一致性哈希实现」

面试题：实现一个简单的一致性哈希，支持节点增减。

```python
import hashlib
import bisect

class ConsistentHash:
    def __init__(self, nodes, virtual_nodes=150):
        self.virtual_nodes = virtual_nodes
        self.ring = {}                      # 哈希值 -> 真实节点
        self.sorted_keys = []
        for node in nodes:
            self.add_node(node)

    def _hash(self, key):
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def add_node(self, node):
        for i in range(self.virtual_nodes):
            key = self._hash(f"{node}#{i}")    # 虚拟节点
            self.ring[key] = node
            bisect.insort(self.sorted_keys, key)

    def get_node(self, key):
        if not self.ring:
            return None
        h = self._hash(key)
        idx = bisect.bisect(self.sorted_keys, h)   # 顺时针找第一个节点
        if idx == len(self.sorted_keys):
            idx = 0                                 # 环形回绕
        return self.ring[self.sorted_keys[idx]]

ch = ConsistentHash(["node1", "node2", "node3"])
print(ch.get_node("user_1001"))   # 同一 key 始终命中同一节点
```

### 场景二：手撕「数据倾斜的 Spark 解决方案」

面试题：订单表按用户聚合，某大客户占了 50% 数据导致严重倾斜，怎么解决。

```scala
// 方案：大 key 加盐打散，两阶段聚合
val orders = spark.read.parquet("orders")

// 阶段一：加随机盐，先局部聚合（打散大 key）
val salted = orders
  .withColumn("salt", (rand() * 100).cast("int"))   // 100 份盐
  .withColumn("salted_uid", concat(col("user_id"), lit("_"), col("salt")))

val partial = salted.groupBy("salted_uid")
  .agg(sum("amount").as("partial_sum"))

// 阶段二：去盐，全局聚合
val result = partial
  .withColumn("user_id", split(col("salted_uid"), "_")(0))
  .groupBy("user_id")
  .agg(sum("partial_sum").as("total_amount"))

// 备选：小表广播 join 避免 shuffle 倾斜
```

## 最佳实践与踩坑记录

### 最佳实践

1. 数据质量题用「六维度 + 规则 + 监控时机 + 定位修复」完整框架回答
2. 数据治理题强调「组织/制度/平台/运营」四位一体，不要只讲工具
3. 分布式题把 CAP、Raft、2PC/TCC、一致性哈希串成「理论体系」，展示底层功底
4. 性能优化题遵循「定位 → 分层 → 对症 → 验证」方法论，结合具体踩坑案例
5. 容量规划题用「估算公式 + 扩容阈值 + 成本治理」结构，体现量化思维

### 踩坑记录

```text
坑 1：CAP 定理答成「三者选二」
结论：误以为 CAP 是「一致性、可用性、分区容错三选二」。
原因：没理解 P（分区容错）是分布式系统的客观存在，必须满足。
解法：正确表述「分区发生时，C 和 A 只能选一个，P 必须满足」。

坑 2：数据治理只讲「元数据和血缘」
结论：把治理窄化为工具建设，忽略组织和制度。
原因：没理解治理是「组织 + 制度 + 平台 + 运营」的体系。
解法：完整回答治理四支柱，突出运营闭环和 owner 机制。

坑 3：性能优化上来就调参数
结论：不做定位就盲目调并行度/内存，可能更慢。
原因：没遵循「先定位瓶颈，再对症优化」的方法论。
解法：先看监控指标和执行计划，确定是 SQL/计算/存储/网络哪类问题。

坑 4：容量估算忽略副本和压缩比
结论：按「原始数据量」估算，实际存储需求严重低估。
原因：忘了 HDFS 3 副本和压缩比的放大/缩减作用。
解法：总存储 = 日均量 × 保留天数 × 副本数 ÷ 压缩比 × 安全系数。

坑 5：分布式锁用 setnx 不设过期时间
结论：持锁进程崩溃后锁永不释放，造成死锁。
原因：没考虑「锁的过期」和「释放时的原子性」。
解法：setnx + expire 合并为原子命令，释放用 Lua 脚本校验 value 再删除。
```
