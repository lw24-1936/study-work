## 概述

大数据工程师的成长，本质是把「计算机基础 + 数学 + 分布式系统 + 数据工程 + 工程素养」串成一条可落地的学习路径，并配一套能随时跑起来的开发环境。本主题回答两个问题：该按什么顺序学、用什么工具链练。核心思路是「先搭环境、边学边做、以项目驱动」——环境是前提，知识点是本知识库的其它篇章。

```text
学习路线的三条主线：
1. 计算机与数学基础 —— 操作系统、网络、数据结构、概率统计、线性代数（地基）
2. 大数据技术栈 —— Hadoop 生态、Spark、Flink、Kafka、数仓、数据湖（核心）
3. 工程与算法 —— 工程规范、调度、治理、MLOps、分布式算法（进阶）
```

## 大数据与算法全栈能力模型

大数据工程师的能力模型可以拆成四个象限：底层系统（存储与计算）、数据工程（加工与建模）、算法（分析与挖掘）与工程素养（规范与运维）。面试和晋升考察的往往是「系统 + 工程」的深度，而非某个 API 的记忆。理解这个模型，才能知道自己每一阶段在补哪个象限的短板。

```text
能力模型四象限：
1. 系统底层 —— OS、网络、分布式理论、存储格式、列式/行式原理
2. 数据工程 —— SQL、数仓建模、ETL、实时计算、数据治理、数据湖
3. 算法分析 —— 概率统计、机器学习、A/B 实验、因果推断、可视化
4. 工程素养 —— Git、容器、调度、CI/CD、可观测性、代码规范
```

## 学习阶段与先修关系

学习有清晰的先修依赖，跳级会事倍功半。阶段一打地基（计算机基础 + 数学 + SQL），阶段二学核心引擎（Hadoop/Spark/Flink/Kafka），阶段三进专项（数仓、数据湖、实时、治理），阶段四做综合项目。每阶段都要配对应的可运行实验，而不是只看书。

```text
四阶段与先修关系：
阶段一 基础 —— 计算机基础(02) + 数学(03) + SQL(05) —— 无先修，入口
阶段二 核心 —— HDFS/MapReduce/YARN(07) + Spark(10) + Flink(11) + Kafka(09)
阶段三 专项 —— 数仓(13) + 数据湖(14) + 实时数仓(16) + 治理(27) + 优化(31)
阶段四 实战 —— 综合项目(38) + 面试(37) + 论文(35)

先修示例：学 Spark 前先懂 HDFS/YARN；学 Flink 前先懂 Kafka；学数据湖前先懂数仓建模。
```

## Linux Shell 与 Git

Linux Shell 是大数据工程师的默认工作环境——所有集群操作、脚本、排查都在命令行完成；Git 是代码与文档的版本管理底座。Shell 核心是「管道 + 文本处理 + 权限 + 进程」，Git 核心是「分支 + 提交 + 合并 + 回滚」。这两项是后面所有实验环境操作的前提。

```text
Shell 与 Git 要点：
1. 管道 —— cmd1 | cmd2 把前一个输出喂给后一个，配合 grep/awk/sed 处理文本
2. 变量与循环 —— $VAR、for/while、$?（上条命令退出码）、&& 与 || 串联
3. Git 三区 —— 工作区/暂存区/仓库，git add -> commit -> push
4. 分支 —— git checkout -b feat/xxx 开分支，merge/rebase 合并
```

```shell
# Shell：统计日志中 ERROR 出现的次数
grep -c "ERROR" /var/log/app.log

# 管道 + awk：取第 5 列求和
awk '{sum += $5} END {print sum}' metrics.txt

# Git 基础工作流
git init
git add .
git commit -m "feat: 初始化数仓项目"
git checkout -b feature/dwd-layer
git push origin feature/dwd-layer
```

## Java Python 与 Scala

大数据三巨头：Java 是 Hadoop/Hive/Flink 的主体语言，性能与生态最强；Scala 是 Spark 的原生语言，函数式风格适合批处理；Python 是数据分析和算法的主流，PySpark/PyFlink 让数据工程师用 Python 写计算。掌握 Java 语法 + Python 数据分析 + 认识 Scala 即可入门。

```text
语言分工：
1. Java —— Hadoop/Hive/Flink 主体，强类型、JVM 生态，大数据基础设施首选
2. Scala —— Spark 原生，融合面向对象与函数式，collect/map/filter 表达力强
3. Python —— 数据分析/算法/胶水语言，PySpark/PyFlink 桥接，库生态最丰富
```

```java
// Java：经典 Hello World 与流式处理风格
import java.util.List;
import java.util.stream.Collectors;

public class Demo {
    public static void main(String[] args) {
        List<Integer> nums = List.of(1, 2, 3, 4, 5);
        List<Integer> squares = nums.stream()
                .map(x -> x * x)
                .collect(Collectors.toList());
        System.out.println(squares);
    }
}
```

```python
# Python：数据分析风格的平方和
nums = [1, 2, 3, 4, 5]
squares = [x * x for x in nums]
print(squares)
print(sum(squares))
```

```scala
// Scala：函数式风格
val nums = List(1, 2, 3, 4, 5)
val squares = nums.map(x => x * x)
println(squares)
```

## IDE 与 Jupyter Notebook

IDE（IntelliJ IDEA 之于 Java/Scala、VS Code 之于多语言）负责大型工程的编辑、调试与重构；Jupyter Notebook 负责交互式数据分析与原型验证。数据工程师的日常是「Notebook 里做探索、IDE 里写工程」。两者配合使用，而不是二选一。

```text
工具选择：
1. IntelliJ IDEA —— Java/Scala 开发标配，重构、调试、Maven/Gradle 集成强
2. VS Code —— 多语言轻量编辑器，Remote-SSH 连远程开发机，插件生态大
3. Jupyter —— 交互式 Python/SQL 探索，单元可单独重跑，适合分析与教学
4. 远程开发 —— 大数据环境多在 Linux 服务器，用 Remote-SSH 或 Notebook 远程内核
```

```shell
# 安装并启动 Jupyter（远程服务器）
pip install jupyterlab
jupyter lab --ip 0.0.0.0 --port 8888 --no-browser

# 安装 Jupyter 的 SQL 内核，方便在 Notebook 里写 SQL
pip install ipython-sql
```

```python
# Notebook 里加载 SQL 扩展并查询
# %load_ext sql
# %sql postgresql://user:pass@localhost:5432/db
# %sql SELECT count(*) FROM orders;
```

## Maven Gradle Poetry 与 uv

构建与依赖管理工具把「编译、打包、依赖解析、发布」自动化。Java/Scala 用 Maven 或 Gradle（pom.xml / build.gradle），Python 用 Poetry 或 uv（pyproject.toml）。它们的核心职责一致：锁定依赖版本、复现构建、管理多模块工程。uv 是新一代 Python 包管理器，速度快、直接取代 pip/venv。

```text
构建工具要点：
1. Maven —— 约定优于配置，pom.xml 声明依赖，仓库从 Maven Central 拉取
2. Gradle —— Groovy/Kotlin DSL，增量构建快，Android 与 Spark 工程常用
3. Poetry —— pyproject.toml 管理依赖 + 虚拟环境，可复现
4. uv —— Rust 实现，秒级安装，一条命令替代 pip/venv/pip-tools
```

```xml
<!-- Maven：pom.xml 声明 Spark 依赖 -->
<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example</groupId>
  <artifactId>spark-job</artifactId>
  <version>1.0.0</version>
  <dependencies>
    <dependency>
      <groupId>org.apache.spark</groupId>
      <artifactId>spark-core_2.12</artifactId>
      <version>3.5.0</version>
    </dependency>
  </dependencies>
</project>
```

```shell
# uv：初始化并管理 Python 项目
uv init my-project
cd my-project
uv add pandas numpy
uv run python -c "import pandas; print(pandas.__version__)"
```

## Docker 与 Compose

Docker 把应用和依赖打包成镜像，保证「本地能跑、集群也能跑」的环境一致性；Docker Compose 用 YAML 一次性编排多个容器（如 Hadoop 集群的 NameNode + DataNode）。大数据本地实验几乎全部依赖 Docker——它让单机模拟分布式集群成为可能，是学习环境的基础设施。

```text
Docker 与 Compose 要点：
1. 镜像与容器 —— 镜像是只读模板，容器是运行实例；Dockerfile 定义镜像构建
2. 网络 —— 同一 Compose 项目内容器可用服务名互相访问
3. 卷挂载 —— -v 挂载本地目录，持久化数据、共享代码
4. Compose —— docker-compose.yml 声明多服务，docker compose up -d 一键启动
```

```yaml
# docker-compose.yml：本地启动一个 PostgreSQL
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: postgres
    ports:
      - "5432:5432"
    volumes:
      - ./data:/var/lib/postgresql/data
```

```shell
# 启动与查看
docker compose up -d
docker compose ps
docker compose logs postgres
docker compose down
```

## Hadoop Spark Flink Kafka 本地环境

本地环境的目标是「零集群成本跑通核心组件」。最省事的方式是用现成的 docker-compose 编排或官方提供的单机版：Hadoop 用单节点伪分布式、Spark 用 local 模式、Flink 用 local 集群、Kafka 用单 broker。也可以用发行版（如 CDH/HDP 的容器化版本）或云上托管集群练手。

```text
本地环境方案：
1. Hadoop —— 单机伪分布式（单节点跑 NameNode + DataNode），或 hadoop 官方 docker
2. Spark —— spark-shell --master local[*]，本地并行模拟多 executor
3. Flink —— start-cluster.sh 起本地 JobManager + TaskManager
4. Kafka —— 单 broker（KRaft 模式无需 ZooKeeper），docker 拉起最方便
```

```shell
# Spark local 模式交互式运行
spark-shell --master local[4]

# Flink 本地集群
./bin/start-cluster.sh
./bin/flink run -c com.example.WordCount target/app.jar

# Kafka（KRaft 单节点，用官方镜像）
docker run -d --name kafka -p 9092:9092 \
  -e KAFKA_CFG_NODE_ID=0 \
  -e KAFKA_CFG_PROCESS_ROLES=controller,broker \
  -e KAFKA_CFG_LISTENERS=PLAINTEXT://:9092 \
  -e KAFKA_CFG_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092 \
  -e KAFKA_CFG_CONTROLLER_QUORUM_VOTERS=0@localhost:9093 \
  bitnami/kafka:3.6
```

## Kubernetes 数据平台环境

Kubernetes（K8s）是容器编排的事实标准，企业数据平台（Spark on K8s、Flink on K8s、Trino、数据湖）越来越多跑在 K8s 上。学习环境用 minikube 或 kind 在单机起一个 K8s 集群，理解 Pod/Service/Deployment/Helm 几个核心抽象即可，真实平台再上云（EKS/GKE/ACK）。

```text
K8s 核心抽象：
1. Pod —— 最小调度单元，一个或多个容器的组合
2. Deployment —— 声明式管理无状态应用的副本数、滚动更新
3. Service —— 稳定的访问入口，负载均衡到后端 Pod
4. Helm —— K8s 的包管理器，用 Chart 一键部署整套组件（如 Spark operator）
```

```yaml
# 一个最简单的 Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
```

```shell
# 用 kind 起本地集群并部署
kind create cluster --name bigdata
kubectl apply -f nginx-deployment.yaml
kubectl get pods
# 用 Helm 部署 Spark operator
helm repo add spark-operator https://kubeflow.github.io/spark-operator
helm install spark-operator spark-operator/spark-operator
```

## 工程规范

工程规范让「个人实验」升级为「可协作、可维护的工程」。核心包括：目录结构统一、代码风格（linter/formatter）、提交信息规范（Conventional Commits）、分支策略、Code Review 与 CI/CD。规范不是负担，是规模化协作的前提，也是面试中「工程素养」的考察点。

```text
工程规范要点：
1. 提交规范 —— feat/fix/docs/refactor 前缀 + 简短描述，便于生成 changelog
2. 代码风格 —— Java 用 checkstyle/spotless，Python 用 black/flake8，Scala 用 scalafmt
3. 分支策略 —— main 稳定分支 + feature 分支 + PR 合入
4. CI/CD —— 提交触发自动测试/构建，保证质量门槛
```

```yaml
# .github/workflows/ci.yml 最小 CI
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -r requirements.txt
      - run: pytest
```

## 最佳实践与踩坑记录

### 最佳实践

1. 环境先行：先花一天把 Docker/本地引擎跑通，再开始学，边学边跑
2. 学习以项目驱动，每个知识点配一个最小可运行示例，不只看书
3. 依赖用工具锁定（Maven/pyproject.toml），保证环境可复现
4. 提交信息遵循 Conventional Commits，方便回溯与生成 changelog
5. 本地用 Docker Compose 模拟集群，避免在宿主机装一堆互相冲突的组件
6. Python 项目优先用 uv，比 pip/venv 快且依赖解析稳定
7. 代码提交前跑 linter 和测试，把质量门槛前移

### 踩坑记录

```text
坑 1：直接在宿主机装 Hadoop/Spark 导致版本冲突
结论：组件之间 JDK 版本、依赖互相干扰，环境越来越乱。
原因：大数据组件版本矩阵复杂，裸机安装难以隔离。
解法：用 Docker Compose 或发行版容器隔离，每个实验一个独立环境。

坑 2：Python 项目不锁依赖导致「我这能跑你那不行」
结论：同事/CI 复现失败，排查半天发现版本漂移。
原因：requirements.txt 未固定版本，或根本没提交锁文件。
解法：用 uv/Poetry 生成 lock 文件并提交，安装用锁定版本。

坑 3：Jupyter 远程内核连不上
结论：本地 Notebook 无法连接远程服务器内核，报连接超时。
原因：服务器防火墙未放行端口，或内核监听在 127.0.0.1。
解法：内核监听 0.0.0.0，放行端口，配置 token 鉴权。

坑 4：git commit 信息随意导致无法回溯
结论：一段时间后看 log 全是「update」「fix」，不知道改了什么。
原因：没有提交规范，凭感觉写信息。
解法：统一 feat/fix/docs 前缀 + 描述，可用 commitlint 校验。

坑 5：K8s 本地集群（minikube）内存不足
结论：Pod 频繁 OOM，调度失败。
原因：minikube 默认内存较小，跑 Spark/Flink 不够。
解法：minikube start --memory 8192 --cpus 4，按需调大。
```
