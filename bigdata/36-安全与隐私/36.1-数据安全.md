## 概述

数据安全贯穿数据全生命周期，核心目标是保障数据的机密性、完整性与可用性，并满足《数据安全法》《个人信息保护法》等合规要求。其技术体系从「分类分级」定基调，到「权限、加密、密钥管理、脱敏、令牌化」做防护，再到「审计」做追溯，形成事前预防、事中控制、事后追责的闭环。

```text
数据安全技术体系
- 定级：数据分类分级（L1 公开 ~ L4 核心）
- 防护：权限（RBAC/ABAC）+ 加密（静态/传输）+ 密钥管理（KMS）
- 降敏：脱敏（掩码/哈希）+ Tokenization（令牌化）
- 追溯：审计（谁在何时对什么数据做了什么）
- 目标：机密性 + 完整性 + 可用性 + 合规
```

## 数据分类分级

数据分类分级是数据安全的基础工程：先按业务属性「分类」（如个人数据、交易数据、日志数据），再按泄露危害程度「分级」（公开 / 内部 / 敏感 / 核心）。不同级别对应不同的存储、访问、脱敏与加密策略。分类分级的依据是《数据安全法》与《个人信息保护法》，结果需沉淀为字段级的元数据规则。

```text
数据分类分级要点
- 分类维度：按主题（个人/交易/日志）+ 按来源（采集/加工/衍生）
- 分级维度：泄露后对个人/企业的危害程度
- 常见四级：L1 公开 / L2 内部 / L3 敏感 / L4 核心
- 敏感示例：手机号、身份证、银行卡、精确地址、生物特征
- 落地：字段级打标，驱动下游脱敏与加密策略
```

```yaml
# 数据分类分级规则配置（示意）
levels:
  - id: L1
    name: 公开
    description: 泄露无危害，可公开传播
  - id: L2
    name: 内部
    description: 泄露轻微影响内部运营
  - id: L3
    name: 敏感
    description: 泄露危害个人权益或商业利益
  - id: L4
    name: 核心
    description: 泄露造成严重危害（密钥、口令哈希）
rules:
  - field: mobile
    level: L3
    pattern: "^1[3-9]\\d{9}$"
  - field: id_card
    level: L3
    pattern: "^\\d{17}[0-9Xx]$"
  - field: bank_card
    level: L3
    pattern: "^\\d{16,19}$"
  - field: password_hash
    level: L4
```

## 权限

权限控制决定「谁能访问什么数据、能做什么操作」，是数据安全的第一道闸门。主流模型有 RBAC（基于角色的访问控制，用户—角色—权限三层）与 ABAC（基于属性的访问控制，结合主体、客体、环境属性动态判定）。大数据平台普遍支持库表级、列级、行级三级细粒度授权，遵循最小权限原则。

```text
权限控制要点
- 最小权限：仅授予完成任务所需的最小权限
- RBAC：用户绑定角色，角色绑定权限，便于批量管理
- ABAC：按属性（部门/时段/数据级别）动态判定，更灵活
- 细粒度：库级 -> 表级 -> 列级 -> 行级（分区/脱敏视图）
- 工具：Ranger / Sentry 等集中式授权组件
```

```sql
-- 最小权限示例：只授予只读角色
GRANT SELECT ON TABLE dws_user_profile_1d TO ROLE analyst_readonly;

-- 列级 + 行级权限：通过视图暴露脱敏后的有限字段
CREATE VIEW v_order_public AS
SELECT
    order_id,
    user_id,
    mask(mobile)   AS mobile_masked,
    order_status,
    pay_amount
FROM dwd_order_detail
WHERE dt >= date_sub(CURRENT_DATE, 30);
```

## 加密

加密把明文数据转换成密文，是保护机密性的核心手段，分为静态加密（At Rest，磁盘/文件/列级）与传输加密（In Transit，链路层）。常见算法：对称加密 AES（快，用于大数据量）、非对称加密 RSA/ECC（用于密钥交换与签名）。数据加密必须与密钥管理配套，否则「加密了但密钥裸奔」等于白加密。

```text
加密核心要点
- 静态加密：磁盘加密（存储层）、文件加密、列级加密（应用层）
- 传输加密：TLS 1.2+，防止链路窃听
- 对称加密 AES-256：速度快，适合海量数据加密
- 非对称加密 RSA/ECC：公钥加密私钥解密，用于密钥交换与数字签名
- 哈希：单向不可逆，用于口令存储与完整性校验（非加密）
```

```shell
# 使用 openssl 做 AES-256-GCM 文件加密（示意）
openssl enc -aes-256-gcm -in user_data.csv -out user_data.csv.enc -k "your-secret"

# 生成 RSA 密钥对
openssl genpkey -algorithm RSA -out private_key.pem -pkeyopt rsa_keygen_bits:2048
openssl rsa -pubout -in private_key.pem -out public_key.pem

# 计算文件哈希做完整性校验
sha256sum user_data.csv
```

## 密钥管理

密钥管理（Key Management）解决「密钥如何生成、存储、轮转、销毁」的问题，是加密体系可信的根基。最佳实践是引入 KMS（密钥管理服务）集中托管密钥，并采用信封加密：用根密钥 KEK 加密数据密钥 DEK，密文 DEK 随数据存储，解密时先用 KEK 解开 DEK 再解数据。密钥需定期轮转并保留历史版本以解密存量数据。

```text
密钥管理要点
- 密钥与数据分离存储，密钥绝不硬编码在代码/配置里
- KMS 集中托管：生成、轮转、撤销、审计一体化
- 密钥分级：KEK（根密钥）加密 DEK（数据密钥）
- 信封加密：密文 DEK 随数据存储，KEK 只存于 KMS
- 轮转：定期轮换，保留旧版本解密历史数据
- 权限：加解密操作本身也要鉴权与审计
```

```yaml
# KMS 密钥策略示意
keys:
  - alias: root-kek
    type: AES_256
    rotation_days: 365
    usage: wrap_key
  - alias: app-payment-dek
    type: AES_256
    rotation_days: 90
    usage: encrypt_data
    wrapped_by: root-kek
policy:
  allow_encrypt: [service:order]
  allow_decrypt: [service:order, service:risk]
  allow_admin: [role:security-admin]
```

## 脱敏

脱敏（Masking）在保留数据可用性的前提下隐藏敏感信息，分为静态脱敏（数据落库/导出前改写，用于测试开发环境）与动态脱敏（查询时实时改写，不改动底层数据）。常见算法包括掩码、截断、哈希、加噪、替换。脱敏的核心原则是「用得到多少就给多少」，最小化敏感信息暴露面。

```text
脱敏方式要点
- 静态脱敏：落库前改写，供测试/开发/外发使用
- 动态脱敏：查询时实时脱敏，底层明文不变
- 算法：掩码、截断、哈希、加噪、替换、泛化
- 规则示例：手机号 138****1234，身份证保留前 6 后 4
- 注意：哈希脱敏可能被彩虹表反推，需加盐
```

```sql
-- Hive 常见脱敏函数
SELECT
    mobile,
    mask(mobile)                              AS masked_mobile,
    mask_show_first_n(mobile, 3)              AS show_first3,
    mask_show_last_n(id_card, 4)              AS show_last4,
    mask_hash(id_card)                        AS hashed_id,
    CONCAT(SUBSTR(mobile, 1, 3), '****', SUBSTR(mobile, 8, 4)) AS manual_mask
FROM dwd_user_info;
```

## Tokenization

Tokenization（令牌化 / 标记化）用随机生成的、本身不含信息的令牌（Token）替换敏感值，明文存于独立的令牌库。它与加密的本质区别在于：令牌不可逆、无法从令牌反推出明文，只能通过强鉴权访问令牌库还原。令牌化常用于卡号、身份证号等需保留格式或需跨系统流转的场景，可与保留格式加密（FPE）结合。

```text
Tokenization 要点
- 用随机令牌替换敏感值，令牌本身无信息量
- 与加密区别：令牌不可逆，需查令牌库才能还原
- 令牌库与业务数据物理隔离，独立加密存储
- 适用：卡号、身份证号等需保留格式/跨系统使用的字段
- 变体：保留格式加密（FPE）可保持长度与格式不变
```

```text
Tokenization 流程示意
原始值  手机号 13812345678
   │  调用 Tokenization 服务（强鉴权）
   ▼
令牌    tok_a1b2c3d4（随机无意义串）
   │  业务表只存令牌
   ▼
还原    业务侧持令牌调令牌库 -> 返回明文（仅授权方）
令牌库  tok_a1b2c3d4 -> 13812345678（库内 AES 加密存储）
```

## 审计

审计（Audit）完整记录「谁在何时对什么数据做了什么操作」的 4W 信息，是事后追溯与合规举证的关键。审计日志必须与业务日志分离、防篡改（append-only、哈希链），并按《数据安全法》《网络安全法》要求留存。通过对审计日志的分析可发现异常批量导出、越权访问、非工作时间访问等风险行为并触发告警。

```text
审计要点
- 4W：谁（who）何时（when）对什么数据（what）做了什么（how）
- 日志防篡改：append-only、哈希链、独立存储
- 合规留存：按法规要求保存规定期限（如不少于 6 个月）
- 风险发现：异常批量导出、越权访问、非工作时间访问
- 与告警联动：命中规则自动触发安全告警
```

```sql
-- 审计日志分析：统计高频批量导出行为
SELECT
    user_name,
    COUNT(1)         AS access_cnt,
    SUM(row_count)   AS total_rows
FROM audit_access_log
WHERE action IN ('export', 'select')
  AND dt >= '2026-08-01'
GROUP BY user_name
HAVING SUM(row_count) > 100000
ORDER BY total_rows DESC;
```

## 应用场景实战

### 场景一：订单敏感字段分级脱敏落库

某电商平台建设订单安全宽表，需要把手机号、身份证、银行卡三类敏感字段按级别分别处理：手机号动态脱敏、身份证保留前 6 后 4、银行卡令牌化，供下游风控与分析在「不接触明文」的前提下使用。

```sql
-- 订单数据分级脱敏落库
INSERT OVERWRITE TABLE dws_order_secure
SELECT
    order_id,
    mask_show_first_n(mobile, 3)                    AS mobile_masked,
    CONCAT(SUBSTR(id_card, 1, 6), '********', SUBSTR(id_card, 15, 4)) AS id_card_masked,
    mask_hash(bank_card)                            AS bank_card_token,
    order_status,
    pay_amount
FROM dwd_order_detail
WHERE dt = '2026-08-14';
```

```yaml
# 配套分级策略（示意）
fields:
  - name: mobile
    level: L3
    strategy: dynamic_mask
    rule: "mask_show_first_n(mobile, 3)"
  - name: id_card
    level: L3
    strategy: partial_mask
    rule: "前6后4保留，中间掩码"
  - name: bank_card
    level: L3
    strategy: tokenization
    rule: "令牌化 + 令牌库独立存储"
  - name: pay_amount
    level: L2
    strategy: none
```

### 场景二：越权访问检测与告警

安全团队需要从审计日志中发现越权访问行为：某用户访问了其未被授权的数据对象。将访问日志与授权表做反连接，找出「有访问记录但无授权记录」的可疑行为，生成告警清单。

```sql
-- 越权访问检测：访问了但无授权的对象
SELECT
    a.user_name,
    a.action,
    a.object_name,
    a.access_time,
    a.row_count
FROM audit_access_log a
LEFT JOIN access_authorization z
    ON a.user_name = z.user_name
   AND a.object_name = z.object_name
WHERE a.dt = '2026-08-14'
  AND z.user_name IS NULL
ORDER BY a.access_time DESC;
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分类分级先行：先完成字段级分级打标，再据此配置脱敏、加密与权限策略，避免「一刀切」。
2. 密钥永不硬编码：密钥一律进 KMS，代码与配置中只存密钥引用/别名，杜绝明文密钥入库。
3. 采用信封加密：用 KEK 加密 DEK，密文 DEK 随数据存储，兼顾安全与轮转效率。
4. 动态脱敏优先：分析场景优先用动态脱敏，明文不落地，从源头减少泄露面。
5. 权限最小化 + 定期复核：默认拒绝，按需授予，季度性清理僵尸账号与冗余权限。
6. 审计日志独立防篡改：审计日志与业务日志分离、append-only，并做哈希链校验完整性。
7. 敏感数据默认不入测试环境：测试开发一律用静态脱敏后的数据，禁止真实明文流入非生产环境。

### 踩坑记录

```text
坑 1：加密了数据但密钥写死在应用配置里
  结论：加密形同虚设，配置泄露即全部明文泄露
  原因：只关注「加密」动作，忽略了密钥管理的配套
  解法：密钥接入 KMS 托管，应用只引用密钥别名，密钥轮转透明化

坑 2：哈希脱敏用无盐 MD5，被彩虹表反推
  结论：看似脱敏的哈希值可被轻易还原出手机号/身份证
  原因：手机号、身份证取值空间小，彩虹表可穷举
  解法：加随机盐再哈希（如 HMAC-SHA256 + 每字段独立盐）

坑 3：静态脱敏只脱了明文字段，忘了脱敏派生字段
  原因：脱敏只覆盖了原始列，未处理由它 join/拼接出的衍生列
  解法：以「敏感源字段」为种子追踪血缘，下游派生字段一并纳入脱敏

坑 4：令牌化后业务系统直接连接令牌库批量还原
  原因：令牌库访问权限过大，令牌化的不可逆性被绕过
  解法：令牌库只对授权服务开放最小化接口，还原操作单独审计与限流

坑 5：审计日志与业务日志放同一张表，被运维误删
  原因：未做物理隔离，日常清理业务日志时连带删除审计记录
  解法：审计日志独立存储、append-only，并设置保留期与只读策略
```
