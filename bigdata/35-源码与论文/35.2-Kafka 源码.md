## 概述

Kafka 是 Scala/Java 写的分布式消息系统，源码结构清晰：Producer 负责「异步批量发送 + 重试 + 幂等」，Consumer 负责「拉取 + 消费位移管理 + 再均衡」，Broker 负责「日志存储 + 分区副本 + 请求处理」，Replication 保证「副本同步与故障转移」，KRaft 是去掉 ZooKeeper 的新一代元数据管理。读 Kafka 源码能深入理解「顺序写日志」「零拷贝」「零管理消息」这些高性能设计。

```text
Kafka 源码模块（kafka 项目）：
core —— Broker、日志、副本、Controller、协调器
clients —— Producer/Consumer/Admin 客户端
connect —— Kafka Connect
streams —— Kafka Streams 流处理
metadata —— KRaft 元数据（新架构）
```

## Producer 源码

Producer 源码核心是「异步批量发送」：KafkaProducer.send() 不直接发，而是把消息放进 RecordAccumulator（每个分区一个队列），Sender 线程批量取出、按 broker 分组、压缩后发出去。关键类：KafkaProducer（入口）、RecordAccumulator（缓冲区）、Sender（发送线程）、NetworkClient（网络 IO）。幂等（idempotence）靠「生产者 ID + 序列号」去重，事务靠事务协调器。

```text
Producer 关键类与流程：
1. KafkaProducer —— send() 入队 RecordAccumulator（按分区）
2. RecordAccumulator —— 批次缓冲（batch），按 batch.size / linger.ms 聚批
3. Sender 线程 —— 取出就绪批次，按 broker 分组，压缩后发送
4. NetworkClient —— 异步 IO，处理响应和重试
5. 幂等 —— PID + sequence 去重，保证 exactly-once 语义
```

```text
Producer 发送流程（源码层面）：
send() → 拦截器 → 序列化 → 分区器 → RecordAccumulator 缓冲
       → Sender 批量发送 → broker 确认（acks）→ 回调/重试
```

```java
// Producer 异步批量发送的核心机制（简化示意）
public void send(String topic, String key, String value) {
    // 1. 序列化 key/value
    // 2. 分区器选择分区
    int partition = partitioner.partition(topic, key, null, null, value);
    // 3. 追加到 RecordAccumulator 对应分区的批次
    RecordAccumulator.RecordAppendResult result =
        accumulator.append(topic, partition, key, value, callback);
    // 4. 批次满或到时间，Sender 线程批量发送
    if (result.batchIsFull) sender.wakeup();
}
```

## Consumer 源码

Consumer 源码核心是「拉取模式 + 位移管理」：Consumer 主动 poll() 拉取消息，用 ConsumerCoordinator 管理消费组（心跳、再均衡），用 SubscriptionState 记录各分区的消费位移（offset）。再均衡（Rebalance）由 GroupCoordinator（broker 端）协调：组成员变化时触发，用分区分配策略（Range/RoundRobin/Sticky）重新分配分区。

```text
Consumer 关键类与流程：
1. KafkaConsumer —— poll() 拉取消息入口
2. ConsumerCoordinator —— 组管理（心跳、加入组、同步组）
3. Fetcher —— 从 broker 拉取数据，管理消费位置
4. SubscriptionState —— 记录各分区 offset、消费状态
5. GroupCoordinator（broker 端）—— 协调再均衡、分配分区
```

```text
Consumer 拉取与位移流程：
poll() → Fetcher 按订阅分区拉取 → 本地缓存返回
       → 消费后手动/自动 commit offset → 位移写 __consumer_offsets
再均衡：组成员变化 → GroupCoordinator 触发 → 停止消费 → 重新分配分区 → 恢复消费
```

## Broker 源码

Broker 源码核心是「日志存储 + 请求处理」：Log 管理一个分区的分段日志（Segment），每个 Segment 是「.log 数据文件 + .index 稀疏索引」，顺序追加写入。请求处理用「Reactor 多线程模型」——Acceptor 线程接收连接，Processor 线程处理网络 IO，KafkaRequestHandler 线程池处理业务请求。零拷贝（sendfile）让数据从磁盘直接到网卡，是 Kafka 高性能的关键。

```text
Broker 关键组件：
1. Log —— 分区日志，分段（Segment）管理，顺序追加
2. Segment —— .log 数据 + .index 稀疏索引 + .timeindex
3. KafkaApis —— 处理 Produce/Fetch 等请求
4. SocketServer —— Reactor 模型（Acceptor + Processor + Handler）
5. Page Cache —— 依赖 OS 页缓存，读多走缓存
```

```text
Reactor 线程模型：
Acceptor（1 个）→ Processor（N 个，处理 IO）→ RequestQueue → Handler 线程池（M 个，处理业务）
零拷贝：Produce 写 Page Cache，Fetch 用 sendfile 直接发送
```

```text
日志分段结构：
partition-0/
├── 00000000000000000000.log     # 数据文件（顺序追加）
├── 00000000000000000000.index   # 偏移量 → 位置的稀疏索引
├── 00000000000000000000.timeindex # 时间戳 → 偏移量
```

## Replication 复制源码

Replication 源码是 Kafka 高可用的核心：每个分区有 Leader 和多个 Follower 副本，Leader 处理读写，Follower 从 Leader 拉取同步（ISR 机制）。Controller（控制器）负责分区副本的管理——Leader 选举、副本分配、故障转移。ISR（In-Sync Replicas）是「与 Leader 保持同步的副本集合」，只有当 acks=all 且 ISR 都确认才提交。

```text
Replication 关键机制：
1. Leader/Follower —— Leader 读写，Follower 从 Leader 拉取同步
2. ISR —— 与 Leader 同步的副本集，LEO/HW 控制可见性
3. Controller —— 分区 Leader 选举、副本分配、故障转移
4. 副本拉取 —— Follower 用 ReplicaFetcherThread 持续拉取
```

```text
HW 与 LEO（副本同步核心概念）：
LEO（Log End Offset）—— 副本日志的末尾偏移
HW（High Watermark）—— ISR 中最小的 LEO，消费者只能读到 HW 之前
Leader 提交 = 更新 HW，Follower 同步到 HW 后对消费者可见
```

## KRaft 源码

KRaft 是 Kafka 3.x 起的新架构，用「内置的 Raft 协议」替代 ZooKeeper 管理元数据：Controller 角色内置到 Broker 里（不再单独依赖 ZK），元数据（Topic、分区、副本）通过 Raft 日志在 Controller 节点间复制，保证一致性。它简化了部署（少一个 ZK 集群）、提升了元数据吞吐、支持更大规模集群。

```text
KRaft 要点：
1. 去 ZooKeeper —— 元数据用内置 Raft 协议管理
2. Controller 内置 —— Controller 角色在 Broker 里，Raft 选举
3. 元数据日志 —— 元数据变更以 Raft 日志复制，保证一致
4. 优势 —— 部署简化、元数据吞吐提升、故障恢复更快
```

```text
KRaft 架构对比：
旧：Broker + ZooKeeper（元数据 + Controller 选举）
新：Broker（内含 Controller 角色，Raft 管理元数据）
元数据日志 = __cluster_metadata topic，Raft 复制
```

## 应用场景实战

### 场景一：Producer 幂等与重试排查

```text
问题：消息重复消费
源码层面分析：
1. acks 配置 —— acks=0/1 时 leader 故障可能丢或重复
2. 幂等未开 —— enable.idempotence=false 时重试会重复
3. 消费者未幂等 —— 消费端没做去重
解法：producer 开幂等 + acks=all；consumer 端做幂等（按消息 key 去重）
```

### 场景二：消费积压定位

```text
消费积压的源码层面原因：
1. 分区数不足 —— 消费者数 > 分区数，多余消费者闲置
2. 单条处理慢 —— poll 后的业务处理慢，拉取频率下降
3. 位移提交失败 —— 提交失败导致重复消费或卡住
```

```shell
# 查看消费组积压
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
    --group my-group --describe
# 输出里的 LAG 列就是积压量
```

## 最佳实践与踩坑记录

### 最佳实践

1. 读 Kafka 源码先理解「顺序写日志 + Page Cache + 零拷贝」这三大性能支柱
2. Producer 重点读 RecordAccumulator 的批量缓冲和 Sender 线程
3. Consumer 重点读 ConsumerCoordinator 的再均衡流程
4. Broker 重点读 Log 的分段存储和 Reactor 网络模型
5. 结合监控（ISR 收缩、消费积压）回看源码，理解为什么

### 踩坑记录

```text
坑 1：以为 Kafka 是「先到先得」的消息队列
结论：对分区内有序、跨分区无序的语义理解错误。
原因：Kafka 只保证「单分区内有序」，不保证全局有序。
解法：需要全局有序就单分区，或业务上按 key 分区保证同 key 有序。

坑 2：位移提交理解错，导致丢消息或重复
结论：消费位移提交时机不对，消息丢或重复。
原因：先提交后处理（丢）、先处理后提交（重复），没搞清 at-least/exactly-once。
解法：at-least-once 用「先处理后提交」，exactly-once 用事务或幂等。

坑 3：忽略 ISR 收缩
结论：副本跟不上 leader，acks=all 时写入卡住。
原因：Follower 同步慢被踢出 ISR，ISR 只剩 leader，可靠性下降。
解法：监控 ISR 数量，排查 follower 慢的原因（磁盘/网络/GC）。

坑 4：再均衡频繁导致消费抖动
结论：消费组频繁 rebalance，消费暂停、延迟飙升。
原因：心跳超时、处理时间超过 max.poll.interval.ms 触发再均衡。
解法：调大心跳和 poll 间隔，业务处理异步化。
```
