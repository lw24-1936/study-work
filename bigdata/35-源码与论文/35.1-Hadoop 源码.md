## 概述

读 Hadoop 源码是理解分布式系统设计的捷径——HDFS 展示了「元数据与数据分离 + 副本容错」的经典架构，YARN 展示了「资源调度与任务执行解耦」的设计，MapReduce 展示了「分而治之 + 容错重试」的计算模型。本主题梳理三大组件的源码结构和关键执行流程，作为读源码的路线图，而不是逐行讲解。

```text
读 Hadoop 源码的价值：
1. HDFS —— 理解 NameNode 元数据管理、DataNode 副本机制、写流水线
2. YARN —— 理解 ResourceManager 调度、ApplicationMaster 生命周期
3. MapReduce —— 理解 Job 切分、Shuffle、容错重试
```

```text
Hadoop 源码模块划分（hadoop 项目）：
hadoop-common —— 公共库（RPC、配置、序列化）
hadoop-hdfs —— NameNode/DataNode/Client
hadoop-yarn —— ResourceManager/NodeManager/ApplicationMaster
hadoop-mapreduce —— MR 框架与 Job 执行
```

## HDFS 源码

HDFS 源码核心在 hadoop-hdfs 模块，三个关键类：NameNode（元数据管理）、DataNode（数据存储）、DFSClient（客户端）。NameNode 用 FSNamesystem 管理目录树和块映射，用 FSEditLog 记录变更（edits 日志）+ FSImage 做快照，DataNode 用 DataXceiver 处理数据读写请求，DFSClient 通过 RPC 与 NameNode 交互获取块位置、再直接连 DataNode 传数据。

```text
HDFS 关键类与职责：
1. NameNode —— 元数据入口，RPC 服务 + FSNamesystem（核心状态）
2. FSNamesystem —— 目录树、块映射、副本管理、租约管理
3. FSEditLog / FSImage —— edits 日志 + 命名空间快照，持久化元数据
4. DataNode —— DataXceiver 处理读写、BlockPoolManager 管理块、心跳上报
5. DFSClient —— 客户端，读：拿块位置→连 DataNode；写：建流水线→发数据
```

```text
HDFS 写流程（源码层面）：
DFSClient.create()
  → NameNodeRpcServer.create() 分配块、建租约、返回块位置
  → DFSOutputStream 建 DataStreamer 流水线（DN1 → DN2 → DN3）
  → 数据按 packet 流式发送，逐级 ack
  → 写完 close()，NameNode completeFile() 提交
```

```java
// HDFS 读文件的核心流程（简化示意，非真实源码）
// DFSClient.open() → 拿 LocatedBlocks → 逐个 DataNode 读
public void readFile(Path path) throws IOException {
    // 1. RPC 调用 NameNode 拿块位置
    LocatedBlocks blocks = namenode.getBlockLocations(path.toString(), 0, Long.MAX_VALUE);
    // 2. 遍历每个块，就近选 DataNode 读
    for (LocatedBlock block : blocks.getLocatedBlocks()) {
        DatanodeInfo[] nodes = block.getLocations();  // 副本所在 DataNode
        // 3. 建立连接读取块数据（优先本地/同机架副本）
        readBlock(nodes[0], block);
    }
}
```

## YARN 源码

YARN 源码核心是「资源调度」与「任务执行」的解耦：ResourceManager（RM）负责全局资源调度，NodeManager（NM）负责单节点资源管理和容器执行，ApplicationMaster（AM）负责单个应用的执行协调。RM 内部有 Scheduler（调度器，如 Capacity/Fair）和 ApplicationManagerService（应用生命周期），NM 用 ContainerManager 管理容器生命周期。

```text
YARN 关键组件与源码结构：
1. ResourceManager —— Scheduler（资源分配）+ ApplicationManagerService（应用管理）
2. Scheduler —— CapacityScheduler / FairScheduler，分配 Container
3. NodeManager —— ContainerManager（启动/监控容器）+ 心跳上报
4. ApplicationMaster —— 应用主控，向 RM 申请资源、与 NM 协作启 Container
5. Container —— 资源抽象（CPU + 内存），任务运行的最小单位
```

```text
YARN 应用提交与执行流程：
1. Client 向 RM 提交应用，RM 分配第一个 Container 启动 AM
2. AM 向 RM 注册，按需申请资源（Container）
3. RM 的 Scheduler 分配 Container，返回给 AM
4. AM 通知对应 NM 启动 Container，NM 拉起任务进程
5. 任务完成后 AM 注销，RM 回收资源
```

```text
CapacityScheduler 层级队列：
root
├── production（70% 容量）—— 生产任务
├── adhoc（20% 容量）—— 临时查询
└── default（10% 容量）—— 默认
每个队列可再分子队列，按容量占比 + 抢占策略调度
```

## MapReduce 源码

MapReduce 源码核心在 hadoop-mapreduce-client：JobClient 提交作业，ResourceManager 启动 MRAppMaster（MR 的 AM），它把 Job 切分成 MapTask 和 ReduceTask 分配到各节点执行。关键流程是 Shuffle——Map 输出按分区写到本地磁盘（spill/merge），Reduce 拉取自己分区的数据（copy/sort/merge）再 reduce。容错靠「任务失败重试 + 推测执行」。

```text
MapReduce 关键流程（源码层面）：
1. Job 提交 —— JobClient 提交，RM 启动 MRAppMaster
2. 任务切分 —— InputFormat.getSplits() 切分输入，决定 MapTask 数
3. Map 阶段 —— Mapper.map() 处理每个 split，输出到环形缓冲区
4. Shuffle —— Map 端 spill/merge + Reduce 端 copy/sort/merge
5. Reduce 阶段 —— Reducer.reduce() 聚合，OutputFormat 写结果
```

```text
Map 端 Shuffle 细节：
1. Map 输出先写环形缓冲区（默认 100MB，阈值 80% 触发 spill）
2. spill 时按分区 + 分区内排序，写到本地磁盘
3. 多次 spill 合并（merge）成一个大文件
4. 可选 Combiner 在 spill/merge 时做局部聚合
```

```text
Reduce 端 Shuffle 细节：
1. copy —— Reduce 从各 Map 节点拉取自己分区的数据
2. sort/merge —— 多路归并排序
3. reduce —— 按键分组，调用 reduce() 聚合
```

## 应用场景实战

### 场景一：定位 HDFS 写慢问题（源码层面分析）

```text
HDFS 写慢排查思路（结合源码）：
1. 写流水线 —— 副本数多、跨机架副本多，写延迟高
2. 块太小 —— 块 size 小则 NameNode 元数据多、请求频繁
3. DataNode 磁盘慢 —— 检查 DataXceiver 的磁盘 IO
4. 网络拥塞 —— 流水线跨机架传输带宽不足
```

```shell
# 排查命令
hdfs dfsadmin -report          # 看 DataNode 状态和磁盘
hdfs fsck / -files -blocks     # 看块分布
# 结合 metrics 看 DataXceiver 队列长度、写吞吐
```

### 场景二：YARN 任务排队分析

```text
YARN 任务排队慢的源码层面原因：
1. 队列容量满 —— CapacityScheduler 里队列已占满，任务 pending
2. 资源碎片 —— 剩余资源不足以满足单个 Container 需求
3. AM 启动慢 —— AM 容器分配慢，应用迟迟起不来
```

```shell
# 看队列状态
yarn queue -status production
yarn application -list -appStates RUNNING,ACCEPTED
```

## 最佳实践与踩坑记录

### 最佳实践

1. 读源码先读「数据流」再读「控制流」——先搞清数据怎么流动，再看状态机
2. HDFS 重点读 FSNamesystem（元数据核心）和 DataStreamer（写流水线）
3. YARN 重点读 Scheduler 接口和 CapacityScheduler 的分配逻辑
4. MapReduce 重点读 Shuffle（MapOutputBuffer 和 Reduce 的 copy 阶段）
5. 配合日志和 metrics 读源码，别干读——遇到问题回头印证

### 踩坑记录

```text
坑 1：把 NameNode 当数据存储节点
结论：以为 NameNode 存数据，扩容时给 NameNode 加大磁盘。
原因：NameNode 只存元数据（内存），DataNode 才存数据块。
解法：扩容数据存储加 DataNode，NameNode 扩容加内存。

坑 2：调参不看源码默认值
结论：凭感觉调副本数、块大小、缓冲区，效果差。
原因：参数间有联动（块大小 vs 元数据 vs 并行度），单看一个参数会误判。
解法：读对应参数的源码上下文，理解它影响什么再调。

坑 3：忽略 Shuffle 是 MapReduce 的性能瓶颈
结论：只优化 map/reduce 逻辑，性能上不去。
原因：Shuffle 的 spill/merge/copy 是大头，磁盘和网络密集。
解法：关注 Shuffle 参数（缓冲区大小、spill 阈值、combiner）。

坑 4：读 HDFS 写流程忽略租约机制
结论：文件写一半进程挂了，文件损坏或锁死。
原因：租约（lease）未正常释放，其他客户端无法写同一文件。
解法：理解租约的续约和恢复机制，写失败后处理租约释放。
```
