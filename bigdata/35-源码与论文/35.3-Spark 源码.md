## 概述

Spark 源码是理解「分布式计算引擎」设计的范本：RDD 提供「弹性分布式数据集」的惰性计算抽象，Scheduler 负责「DAG 切分 + 任务调度」，Shuffle 实现「跨节点数据重分布」，Catalyst 是「SQL 优化器」，Tungsten 是「内存/代码生成优化」，AQE 是「运行时自适应优化」。读 Spark 源码重点是理解「惰性求值 + 血缘容错 + 窄/宽依赖」这套核心模型。

```text
Spark 源码模块（spark 项目）：
core —— RDD、DAG Scheduler、Task Scheduler、Shuffle
sql —— Catalyst、Tungsten、DataFrame/Dataset、AQE
streaming —— Structured Streaming
```

```text
Spark 程序执行流程（源码层面）：
Action 触发 → DAGScheduler 切 Stage（按宽依赖）→ 提交 TaskSet
→ TaskScheduler 分配到 Executor → 执行 Task（Shuffle 读写）→ 结果返回
```

## Scheduler 调度源码

Scheduler 是 Spark 的执行编排核心，分两层：DAGScheduler（高层，把 RDD 血缘图切分成 Stage）和 TaskScheduler（低层，把 Task 分配到具体 Executor）。DAGScheduler 遇到宽依赖（ShuffleDependency）就切一个新 Stage，窄依赖合并在同一 Stage 里；TaskScheduler 负责资源分配、任务下发、失败重试和推测执行。

```text
Scheduler 关键组件：
1. DAGScheduler —— RDD 血缘 → DAG → Stage 切分（按宽依赖边界）
2. TaskScheduler —— Stage → TaskSet → 分配到 Executor
3. SchedulerBackend —— 与 Cluster Manager 交互，管理 Executor
4. Stage —— 一个 Stage 内是窄依赖链，Stage 间是宽依赖（Shuffle）
```

```text
Stage 切分规则：
- 窄依赖（map/filter/union）→ 同一 Stage
- 宽依赖（groupByKey/reduceByKey/join）→ 切新 Stage
- 每个 Shuffle 是 Stage 边界，父 Stage 产出 Shuffle 数据给子 Stage
```

## RDD 源码

RDD（Resilient Distributed Dataset）是 Spark 的核心抽象：一个不可变、可分区、可并行计算的集合。源码核心是「惰性求值 + 血缘（lineage）容错」——Transformation（map/filter）只记录操作不执行，Action（count/collect）触发计算；每个 RDD 记录「父 RDD + 如何计算」（血缘），分区丢失时按血缘重算。依赖分窄依赖（父分区 → 一个子分区）和宽依赖（父分区 → 多个子分区）。

```text
RDD 核心概念（源码层面）：
1. RDD 抽象 —— 五大属性：分区列表、计算函数、依赖、分区器、首选位置
2. 惰性求值 —— Transformation 不执行，Action 才触发
3. 血缘 —— 每个 RDD 记录父 RDD + 计算函数，用于容错重算
4. 依赖 —— 窄依赖（pipeline 优化）+ 宽依赖（Shuffle 边界）
5. 持久化 —— cache/persist，避免重复计算
```

```scala
// RDD 核心抽象（简化示意）
abstract class RDD[T] {
  def getPartitions: Array[Partition]          // 分区列表
  def compute(partition: Partition): Iterator[T] // 计算函数
  def getDependencies: Seq[Dependency[_]]      // 依赖（窄/宽）
  def getPartitioner: Option[Partitioner]      // 分区器
  def getPreferredLocations(p: Partition): Seq[String] // 首选位置
}
```

## Shuffle 源码

Shuffle 是 Spark 跨分区重分布数据的机制，是性能瓶颈所在。Shuffle 写端（Map 端）把数据按分区写到本地磁盘（Shuffle Write），读端（Reduce 端）拉取自己分区的数据（Shuffle Read）。关键实现有 Hash Shuffle（早期，小文件多）、Sort Shuffle（默认，排序合并）、Tungsten-Sort Shuffle（堆外内存排序）。Shuffle 由 ShuffleManager 接口抽象，可插拔。

```text
Shuffle 关键机制：
1. Shuffle Write —— Map 端按分区写数据（Bypass/Sort/Tungsten-Sort）
2. Shuffle Read —— Reduce 端拉取 + 聚合自己分区的数据
3. 数据落盘 —— 中间数据写本地磁盘，靠磁盘换内存
4. 优化 —— map-side combine（预聚合）、bypass 机制（少分区免排序）
```

```text
Shuffle 三种实现：
1. Hash Shuffle —— 每分区一个文件，小文件爆炸（已弃用）
2. Sort Shuffle —— 默认，排序合并写一个文件 + 索引
3. Tungsten-Sort —— 堆外内存 + 二进制排序，性能更高
```

## Catalyst 优化器源码

Catalyst 是 Spark SQL 的查询优化器，基于「树 + 规则」的框架：SQL 解析成逻辑计划（AST），经过多轮规则优化（谓词下推、列裁剪、常量折叠）得到优化后的逻辑计划，再转成物理计划（选择 join 策略、算子实现），最后生成 RDD 执行计划。它用 TreeNode 表示查询树，用 Rule 做模式匹配改写。

```text
Catalyst 优化流程：
1. Parser —— SQL → Unresolved Logical Plan（AST）
2. Analyzer —— 绑定表和列，解析成 Resolved Logical Plan
3. Optimizer —— 规则优化（谓词下推、列裁剪、常量折叠）
4. Planner —— 转 Physical Plan（选 Join 策略、算子实现）
5. Codegen —— 生成 Java 代码执行
```

```text
Catalyst 核心优化规则：
- Predicate Pushdown —— 谓词下推到数据源
- Column Pruning —— 只读需要的列
- Constant Folding —— 常量折叠
- Join Reorder —— 调整 join 顺序（基于统计信息）
```

## Tungsten 源码

Tungsten 是 Spark 的执行引擎优化：用「堆外内存 + 二进制格式」替代 JVM 对象（减少 GC 压力），用「整阶段代码生成」（Whole-Stage Codegen）把多个算子合并成一个函数（减少虚函数调用和内存往返）。它是 Spark 2.x 性能大幅提升的关键，配合 Parquet 列式存储发挥最大威力。

```text
Tungsten 核心优化：
1. 堆外内存 —— 直接管理内存，减少 JVM GC
2. 二进制编码 —— 数据用紧凑二进制格式，减少对象开销
3. 代码生成 —— Whole-Stage Codegen 合并算子，减少虚函数调用
4. Cache 友好 —— 紧凑布局提升 CPU 缓存命中
```

```text
Whole-Stage Codegen 原理：
多个算子（filter + map + aggregate）合并成一个 Java 函数
→ 消除算子间的虚函数调用和中间对象
→ 数据在寄存器/缓存里流转，大幅提速
```

## AQE 源码

AQE（Adaptive Query Execution）是 Spark 3.0 的运行时自适应优化：查询执行中根据「中间结果的实际统计」动态调整执行计划——动态合并分区（减少小分区）、动态切换 Join 策略（小表转广播）、动态处理数据倾斜（倾斜分区拆分）。它解决「优化器基于估算统计、实际数据可能偏离」的老问题。

```text
AQE 三大动态优化：
1. 动态合并分区 —— 把过多的小分区合并，减少任务数
2. 动态切换 Join —— 运行时发现某侧很小，转广播 Join
3. 动态处理倾斜 —— 倾斜分区拆分 + 多路 join
```

```text
AQE 原理：
- 执行到 Shuffle 边界时，物化中间结果，读取实际统计
- 用实际统计（而非估算）重优化剩余计划
- 关键参数：spark.sql.adaptive.enabled=true
```

## 应用场景实战

### 场景一：SQL 慢查询的 Catalyst 层面分析

```sql
-- 用 EXPLAIN 看优化后的执行计划
EXPLAIN COST SELECT u.city, SUM(o.amount)
FROM orders o JOIN users u ON o.user_id = u.user_id
WHERE o.dt = '2024-08-14'
GROUP BY u.city;
-- 检查：谓词是否下推、join 策略（广播/SMJ）、分区裁剪、是否 AQE 生效
```

### 场景二：Shuffle 慢的源码层面定位

```text
Shuffle 慢的源码层面原因：
1. 数据倾斜 —— 某分区数据量远超其他，单任务拖后腿
2. 小文件多 —— 分区数过多，Shuffle 写小文件
3. 序列化慢 —— 用 Java 序列化而非 Kryo
4. 磁盘慢 —— Shuffle 中间数据落盘，磁盘是瓶颈
```

## 最佳实践与踩坑记录

### 最佳实践

1. 读 Spark 源码先吃透「惰性求值 + 血缘 + 宽窄依赖」三个核心概念
2. 理解 Stage 切分（宽依赖边界）就能解释大部分执行计划问题
3. SQL 优化问题看 Catalyst 的 EXPLAIN 计划，别瞎猜
4. Shuffle 性能问题看数据倾斜和分区数，这是大头
5. AQE 默认开启，配合 EXPLAIN 看它做了哪些动态调整

### 踩坑记录

```text
坑 1：把 Transformation 当立即执行
结论：中间结果没有物化，重复计算导致慢。
原因：没理解惰性求值，以为每个 Transformation 都执行了。
解法：需要复用的中间结果 cache/persist，理解 Action 才触发计算。

坑 2：宽窄依赖分不清导致 Stage 数失控
结论：join/groupBy 多导致 Stage 多、Shuffle 频繁，性能差。
原因：宽依赖（Shuffle）是 Stage 边界，join 多 Stage 就多。
解法：减少不必要的 Shuffle（先过滤再 join、用广播 join 小表）。

坑 3：忽略数据倾斜
结论：某个 task 跑得极慢，整体任务卡住。
原因：某 key 的数据量远超其他，单分区处理不过来。
解法：加盐打散、AQE 倾斜处理、自定义分区器。

坑 4：EXPLAIN 只看物理计划不看 AQE 实际计划
结论：优化建议基于估算，与实际执行不符。
原因：AQE 会运行时改计划，静态 EXPLAIN 看不到最终执行。
解法：看 AQE 生效后的实际执行（Spark UI 里的最终计划）。
```
