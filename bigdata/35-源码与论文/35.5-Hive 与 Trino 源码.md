## 概述

Hive 和 Trino 都是「SQL on 大数据」的查询引擎，但架构取向不同：Hive 是「SQL 翻译成 MapReduce/Tez/Spark 任务」的批处理引擎，Trino 是「SQL 翻译成流水线执行计划」的内存计算引擎。两者都遵循「Parser（解析）→ Analyzer（语义分析）→ Planner（逻辑计划）→ Optimizer（优化）→ Executor（执行）」的经典 SQL 引擎流水线，读它们的源码能理解「SQL 引擎是如何一条 SQL 变成分布式执行计划的」。

```text
SQL 引擎的通用流水线：
Parser（SQL → AST）→ Analyzer（语义分析，绑定表列）→ Planner（AST → 逻辑计划）
→ Optimizer（规则/CBO 优化）→ Executor（逻辑计划 → 物理执行）
```

```text
Hive vs Trino 执行取向：
Hive —— 编译成 MR/Tez/Spark 作业，落盘中间结果，批处理
Trino —— 编译成流水线执行计划，内存中间结果，交互式
```

## Hive Parser 解析器

Hive 的 Parser 用 ANTLR 解析 SQL：SQL 文本经过词法分析（tokenize）和语法分析（parse）生成 AST（抽象语法树）。AST 是「树形结构」表示的 SQL 语句（每个节点是一个语法元素，如 SELECT、WHERE、JOIN）。Hive 的语法文件是 HiveLexer.g 和 HiveParser.g（ANTLR 语法），AST 节点对应 HiveParser 里定义的 token 类型。

```text
Hive Parser 要点：
1. 工具 —— ANTLR 生成词法/语法分析器
2. 输出 —— AST（抽象语法树）
3. 语法文件 —— HiveLexer.g（词法）+ HiveParser.g（语法）
4. AST 节点 —— TOK_SELECT、TOK_WHERE、TOK_JOIN 等
```

```text
SQL 解析流程：
SELECT a, b FROM t WHERE c > 10
  → 词法分析（拆 token）
  → 语法分析（生成 AST）
  → TOK_QUERY
     ├── TOK_SELECT (a, b)
     ├── TOK_FROM (t)
     └── TOK_WHERE (c > 10)
```

## Hive Planner 与 Optimizer

Hive 的 Planner 把 AST 转成「逻辑执行计划」（Operator 树），Optimizer 对逻辑计划做优化。SemanticAnalyzer 是核心：它遍历 AST，生成 MapReduce 算子（TableScan、Filter、Select、GroupBy、Join 等 Operator），并做类型检查。优化分两类：规则优化（谓词下推、列裁剪、常量折叠）和 CBO（Cost-Based Optimizer，基于统计信息选 join 顺序和策略，用 Calcite 实现）。

```text
Hive Planner/Optimizer 要点：
1. SemanticAnalyzer —— AST → Operator 树（逻辑计划）
2. Operator —— TableScan/Filter/Select/GroupBy/Join 等
3. 规则优化 —— 谓词下推、列裁剪、分区裁剪
4. CBO —— 基于统计信息（Calcite），选 join 顺序/策略
```

```text
Hive 执行计划生成：
AST → SemanticAnalyzer → Operator 树（逻辑）
→ 优化（规则 + CBO）→ 编译成 MapReduce/Tez/Spark 任务（物理）
→ 提交 YARN 执行
```

## Hive 执行引擎

Hive 的逻辑计划最终编译成「可执行任务」：早期编译成 MapReduce 作业（每个 Operator 对应 map/reduce 阶段），现在默认 Tez（DAG 执行引擎，比 MR 快），也支持 Spark 引擎。执行引擎把 Operator 树翻译成 DAG（有向无环图），每个算子（GroupBy、Join）对应一个 DAG 顶点，交给 YARN 执行。

```text
Hive 执行引擎要点：
1. MapReduce —— 最早，每步落盘，慢
2. Tez —— 默认，DAG 执行，中间结果内存传递
3. Spark —— 内存计算，迭代快
4. 编译 —— Operator 树 → DAG → 提交 YARN
```

```text
Hive 执行引擎演进：
MR（每步落盘，慢）→ Tez（DAG，快）→ Spark（内存，迭代快）
配置：hive.execution.engine=tez|mr|spark
```

## Trino Parser 解析器

Trino 的 Parser 也是 ANTLR 实现，把 SQL 解析成 AST，但 AST 节点比 Hive 更细粒度（Statement、Query、Select、Relation 等），因为 Trino 直接面向交互式查询、需要更精细的语法支持（如复杂子查询、窗口函数、联邦查询）。Trino 的 AST 是「不可变树」，后续 Analyzer 在 AST 上做语义分析。

```text
Trino Parser 要点：
1. 工具 —— ANTLR 4，生成解析器
2. 输出 —— AST（不可变语法树）
3. 细粒度 —— Statement/Query/Select/Relation 等节点
4. 支持 —— 完整 SQL 方言 + 联邦查询语法
```

## Trino Planner 与 Optimizer

Trino 的 Planner 把 AST 转成「逻辑执行计划」（Plan 树），Optimizer 用「基于规则的优化器（IterativeOptimizer）」逐条应用优化规则（谓词下推、列裁剪、join 重排、谓词合并）。Trino 是「纯内存 + 规则优化」为主（不像 Hive 有 Calcite CBO），优化规则以「迭代收敛」方式应用，直到计划不再变化。执行计划是「树形 pipeline」，节点间用「page 流」传递数据。

```text
Trino Planner/Optimizer 要点：
1. Analyzer —— AST 语义分析（绑定表列、类型检查）
2. Planner —— AST → 逻辑 Plan 树
3. IterativeOptimizer —— 迭代应用优化规则直到收敛
4. 规则 —— 谓词下推、列裁剪、join 重排、常量折叠
```

```text
Trino 优化特点：
- 规则驱动（IterativeOptimizer），非 CBO
- 谓词下推到 Connector（数据源层裁剪）
- 全内存流水线，中间结果以 page 流传递
```

## Trino Connector 连接器

Trino 的 Connector 是「联邦查询」的核心：一个 Connector 对应一种数据源（Hive、Iceberg、Kafka、MySQL、MongoDB），提供「元数据（表结构）+ 数据读取（分片 Split）+ 下推（谓词/列）」。Catalog 是 Connector 的实例（一个 Catalog 配一个数据源的连接）。查询时 Trino 把「表名」解析到具体 Catalog/Schema，通过 Connector 读取数据。

```text
Trino Connector 要点：
1. Connector —— 数据源插件，提供元数据 + 数据读取
2. Catalog —— Connector 的实例（如 hive、iceberg、mysql 各一个）
3. Split —— 数据分片，并行读取的基本单元
4. 下推 —— 谓词/列裁剪下推到数据源，减少读取
```

```text
Trino 联邦查询：
SELECT * FROM hive.db.t1 JOIN mysql.db.t2 ON ...
  → hive Connector 读 t1，mysql Connector 读 t2
  → Trino 内存里 join，返回结果
```

## 应用场景实战

### 场景一：Hive 慢查询的执行计划分析

```sql
-- 看 Hive 执行计划
EXPLAIN SELECT u.city, SUM(o.amount) FROM orders o JOIN users u
ON o.user_id = u.user_id WHERE o.dt = '2024-08-14' GROUP BY u.city;

-- 检查：是否谓词下推、是否走 Map Join、分区裁剪是否生效
```

### 场景二：Trino 联邦查询调优

```text
Trino 联邦查询慢的排查：
1. 下推是否生效 —— 谓词/列是否下推到 Connector（没下推就全量拉）
2. 数据倾斜 —— join 键倾斜，单节点内存爆
3. 内存不足 —— 全内存执行，数据量大 OOM
4. 解法 —— 开谓词下推、调 join 分布策略、加内存
```

## 最佳实践与踩坑记录

### 最佳实践

1. 读 SQL 引擎源码，先把「Parser → Analyzer → Planner → Optimizer → Executor」流水线搞清
2. Hive 重点读 SemanticAnalyzer（AST → Operator 树）和编译成 MR/Tez 的部分
3. Trino 重点读 IterativeOptimizer（规则优化）和 Connector SPI（联邦查询）
4. 调优先看 EXPLAIN，理解执行计划再动手
5. 理解「下推」（谓词/列裁剪）是 SQL 引擎优化的核心

### 踩坑记录

```text
坑 1：Hive 没开 CBO，join 顺序差
结论：大表 join 大表没选好顺序，执行慢。
原因：没开 CBO，只用规则优化，join 顺序不优化。
解法：开 hive.cbo.enable=true，配统计信息收集。

坑 2：Trino 联邦查询没下推谓词
结论：全量拉数据到 Trino 内存，慢且 OOM。
原因：Connector 不支持或没开谓词下推。
解法：确认 Connector 支持谓词下推，检查执行计划是否下推。

坑 3：混淆 Hive（批处理）和 Trino（交互式）的适用场景
结论：用 Hive 跑交互查询慢，用 Trino 跑超大批处理 OOM。
原因：两者取向不同，Hive 落盘批处理、Trino 内存交互。
解法：批处理用 Hive/Spark，交互查询用 Trino。

坑 4：Hive 小表 join 大表没走 Map Join
结论：join 慢，走了 Reduce 端 join。
原因：小表没识别为 Map Join，走了 shuffle。
解法：开 hive.auto.convert.join=true，小表自动 Map Join。
```
