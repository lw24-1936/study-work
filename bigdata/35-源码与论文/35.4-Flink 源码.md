## 概述

Flink 是真正的流式计算引擎，源码设计围绕「有状态流处理」展开：Runtime 负责「作业图（JobGraph → ExecutionGraph）的生成与调度」，Network 负责「算子间的数据传输（背压、缓冲）」，State 负责「状态管理（Keyed State、State Backend）」，Checkpoint 负责「分布式快照（Barrier 对齐），保证 exactly-once」，Watermark 负责「事件时间与水印传播」。读 Flink 源码重点是理解「分布式快照」和「背压」这两个流式计算的核心难题。

```text
Flink 源码模块（flink 项目）：
runtime —— 作业调度、Task 执行、状态、Checkpoint
streaming —— DataStream API
network —— 数据传输（背压、缓冲）
state-backends —— RocksDB/Heap 状态后端
table —— Flink SQL
```

## Runtime 运行时源码

Flink Runtime 核心是「作业图的三层转换」：StreamGraph（API 层）→ JobGraph（优化后，算子链合并）→ ExecutionGraph（调度层，可并行的子任务）。JobManager 的 Scheduler 负责把 ExecutionGraph 部署到 TaskManager 执行，TaskManager 的 Task 是执行单元，Slot 是资源单元（一个 Slot 跑一个并行子任务）。算子链（Chaining）把能合并的算子串成一条流水线，减少数据序列化和线程切换。

```text
Runtime 关键组件：
1. StreamGraph —— 用户 API 生成的逻辑图（StreamNode + StreamEdge）
2. JobGraph —— 优化后（算子链合并），提交给集群
3. ExecutionGraph —— 调度层，展开成并行子任务（ExecutionVertex）
4. Scheduler —— 分配子任务到 Slot，处理失败重启
5. Task —— TaskManager 上的执行单元，一个 Task 跑一个算子链
```

```text
三层图转换：
StreamGraph（API）→ JobGraph（算子链）→ ExecutionGraph（并行展开）
JobManager 持有 ExecutionGraph，TaskManager 执行 Task（算子链）
```

## Network 网络栈源码

Flink Network 是算子间数据传输层，核心是「背压（Backpressure）机制」：下游算子处理不过来时，通过「有限容量的缓冲池」反向传导压力，上游算子减慢速度。实现基于 Credit-based Flow Control——下游给上游发放「信用额度」（可用的 buffer 数），上游只能发送有额度的数据。背压是流式系统区别于批处理的核心难题，Flink 的解决方式是自然的逐级反压。

```text
Network 关键机制：
1. 缓冲池 —— 每个 Task 有有限数量的 Buffer，作为背压的「闸门」
2. Credit 机制 —— 下游按空闲 Buffer 数给上游发信用，控制流量
3. 背压传导 —— 下游慢 → Buffer 满 → 不给信用 → 上游停发
4. 数据分区 —— keyBy（哈希分区）、rebalance（轮询）、broadcast
```

```text
背压传导流程：
下游 Task 处理慢 → 下游 Buffer 满 → 不发 credit
→ 上游 Task 拿不到 credit → 停发数据 → 上游也慢
→ 逐级传导到 Source，Source 放慢读取速度
```

## State 状态源码

Flink State 是「有状态流处理」的核心：Keyed State（按键组织，每个 key 独立状态）和 Operator State（按算子组织）。State 存储在 State Backend 里——Heap（内存）或 RocksDB（磁盘 + 内存）。Keyed State 用「键组（Key Group）」分区，key 哈希到固定键组，键组再分配到并行子任务，保证「同一个 key 的状态始终在同一子任务」。State 的读写经 StateBackend 抽象，RocksDB 后端把状态落磁盘，支撑超大状态。

```text
State 关键机制：
1. Keyed State —— ValueState/ListState/MapState，按 key 组织
2. Operator State —— 按算子组织，用于 Source 位移等
3. Key Group —— key → 键组 → 子任务，状态分区的基础
4. State Backend —— Heap（内存）/ RocksDB（磁盘），状态存储
5. TTL —— 状态过期清理，防止状态无限增长
```

```text
Key Group 分配：
key.hashCode() → keyGroup（哈希取模最大键组数）
keyGroup → subtask（键组范围分配到并行子任务）
好处：并行度变化时键组重分配，状态不丢
```

## Checkpoint 源码

Checkpoint 是 Flink 的分布式快照机制，保证 exactly-once。核心是「Barrier（栅栏）对齐」：JobManager 定期注入 Checkpoint Barrier 到数据流，Barrier 随数据流向下游传播，算子收到所有上游的 Barrier 后做「本地状态快照」，全图完成后就是一致快照。对齐（Alignment）保证「快照瞬间所有算子的状态一致」。Unaligned Checkpoint 跳过对齐（把在途数据也存进快照），降低背压下的快照延迟。

```text
Checkpoint 关键机制：
1. Barrier 注入 —— JobManager 在 Source 注入栅栏
2. Barrier 对齐 —— 算子等齐所有上游 Barrier，再快照本地状态
3. 状态快照 —— 各算子快照自己的 State（异步，写到 State Backend）
4. 完成 —— 全部算子快照完，Checkpoint 成功（可恢复点）
5. Unaligned —— 跳过对齐，存 in-flight 数据，降延迟
```

```text
Barrier 对齐流程：
算子收到 barrier(n)（来自上游 A）
→ 停止处理上游 A 的后续数据（缓冲）
→ 等上游 B、C 的 barrier(n) 都到
→ 对齐完成，快照本地状态，继续处理
```

## Watermark 源码

Watermark 是 Flink 事件时间的核心机制：一个带时间戳的「水位标记」，声明「时间戳小于 watermark 的事件都已到达」，随数据流传播。算子用 watermark 判断「是否触发窗口计算」（watermark ≥ 窗口结束时间才触发）。Watermark 生成（Source 端）和传播（下游取各上游的最小值）是关键逻辑，迟于 watermark 的数据（迟到数据）走侧输出或丢弃。

```text
Watermark 关键机制：
1. 生成 —— Source 按事件时间生成（周期/标点两种）
2. 传播 —— 下游取所有上游 watermark 的最小值
3. 触发 —— watermark ≥ 窗口结束时间，触发窗口计算
4. 迟到数据 —— 迟于 watermark 的数据，侧输出或丢弃
```

```text
Watermark 传播：
上游 A 的 wm = 10:05，上游 B 的 wm = 10:03
下游 wm = min(10:05, 10:03) = 10:03（取最小，保证不误判）
```

## 应用场景实战

### 场景一：背压定位

```text
背压的源码层面定位：
1. 看 Flink UI 的 Backpressure 指标（绿色正常、红色高压）
2. 高压算子 —— 处理慢（CPU 密集、外部 IO 慢）
3. 传导链 —— 从高压算子向上游追，找根因
4. 解法 —— 提高并行度、优化算子逻辑、增加 buffer
```

### 场景二：Checkpoint 超时排查

```text
Checkpoint 超时的源码层面原因：
1. 状态太大 —— 快照写状态耗时（RocksDB 增量快照可缓解）
2. 背压导致对齐慢 —— Barrier 在背压处堆积，无法对齐
3. 外部系统慢 —— 快照要 flush 外部 Sink 的状态
解法：增量 Checkpoint、Unaligned Checkpoint、优化状态大小
```

## 最佳实践与踩坑记录

### 最佳实践

1. 读 Flink 源码先吃透「Checkpoint Barrier 对齐」和「背压 Credit 机制」两个核心
2. 理解三层图（StreamGraph/JobGraph/ExecutionGraph）就能看懂调度
3. State 问题看 Key Group 和 State Backend 选型
4. 背压问题看 Network 的 Credit 机制和 Buffer 配置
5. 事件时间问题看 Watermark 的生成和传播

### 踩坑记录

```text
坑 1：把 Flink 当微批处理
结论：按批处理的思维写流式程序，状态和窗口理解错。
原因：没理解「持续的有状态流」，把窗口当微批。
解法：理解事件时间、watermark、状态的流式语义。

坑 2：State 无限增长导致 OOM
结论：状态越积越大，TaskManager 内存耗尽。
原因：没配 State TTL，历史状态不清理。
解法：给有生命周期的状态配 TTL，定期清理。

坑 3：忽略背压导致整个链路变慢
结论：一个慢算子拖慢全链路，吞吐下降。
原因：背压逐级传导，根因在一个算子。
解法：定位高压算子，提高并行度或优化逻辑。

坑 4：Checkpoint 对齐慢导致超时
结论：Checkpoint 频繁失败或超时。
原因：背压时 Barrier 无法对齐，快照卡住。
解法：用 Unaligned Checkpoint，或先解决背压问题。

坑 5：Watermark 没配好导致窗口不触发或早触发
结论：窗口计算延迟或丢数据。
原因：watermark 生成策略不对（太保守延迟、太激进丢数据）。
解法：按业务乱序程度配 watermark 生成器（BoundedOutOfOrderness）。
```
