## 概述

Lakehouse 表格式（Iceberg/Hudi/Delta）的源码核心都是「元数据管理」：如何用「元数据文件 + 数据文件」的分层结构，在对象存储上实现 ACID 事务、版本管理、时间旅行。Iceberg 用「metadata.json → manifest list → manifest → data files」三层，Hudi 用「Timeline + 文件组」，Delta 用「Transaction Log（JSON）」。读它们的源码能理解「如何在无事务的对象存储上造出事务语义」。

```text
三种表格式的元数据核心：
Iceberg —— metadata.json（表版本）+ manifest（文件清单），快照式
Hudi —— Timeline（动作时间线）+ 文件组，增量式
Delta —— Transaction Log（JSON 追加），日志式
```

```text
共同挑战：
在「只支持追加/覆盖、无事务」的对象存储上
实现「多文件原子提交 + 版本管理 + 并发控制」
```

## Iceberg Metadata 元数据

Iceberg 的 metadata.json 是表的「版本根」：记录表结构（schema）、分区规格、当前快照、快照历史。每次写操作生成新的 metadata.json（版本号 +1），通过 Catalog 的「当前 metadata 指针」定位。元数据是「不可变 + 追加」的——旧 metadata.json 保留，用于时间旅行和回滚。表的完整状态 = 当前 metadata + 它引用的 manifest list。

```text
metadata.json 核心字段（源码层面）：
1. table-uuid —— 表的全局唯一标识
2. schema / partition-spec —— 表结构 + 分区规格（带 id，支持演进）
3. current-snapshot-id —— 当前快照
4. snapshots —— 快照历史（时间旅行）
5. metadata-log —— 历史 metadata 文件（回滚）
```

```text
Iceberg 表状态定位：
Catalog（表名 → 当前 metadata.json 路径）
  → metadata.json（当前快照 ID + 快照历史）
  → manifest list（快照的文件清单）
  → manifest（数据文件 + 列统计）
  → data files（Parquet/ORC）
```

## Iceberg Snapshot 与 Manifest

Snapshot（快照）是 Iceberg 表在某一时刻的「文件集合视图」，Manifest 是「数据文件清单」。每次提交产生一个新 Snapshot，它引用一组 Manifest；每个 Manifest 记录一批数据文件的位置和列级统计（min/max/null 计数）。查询时从 Snapshot 出发，读 Manifest 的列统计做文件级裁剪，只读命中的数据文件。Snapshot 不可变，新提交复用未变的 Manifest/文件（增量）。

```text
Snapshot 与 Manifest 要点：
1. Snapshot —— 不可变的文件集合视图，提交时创建
2. Manifest —— 数据文件清单 + 列级统计（裁剪依据）
3. Manifest List —— 快照包含的 manifest 列表 + 分区统计
4. 增量 —— 新快照只引用变化的 manifest/文件，未变复用
```

```text
查询裁剪链：
谓词 (dt='2024-08-14')
→ manifest list 按分区统计跳过无关 manifest
→ manifest 按列 min/max 跳过无关 data file
→ data file 内 Parquet row group 裁剪
```

## Iceberg Commit 提交

Iceberg 的 Commit（提交）是「原子更新表的当前快照」的过程：写操作先把数据写成新的 Parquet 文件，再写新的 Manifest，最后「原子地」更新 Catalog 里指向 metadata.json 的指针。并发控制用「乐观锁（CAS）」——提交时带上「期望的当前快照 ID」，若与 Catalog 里的不一致（被别的提交抢先），则冲突重试。这个「原子指针更新」是关键，其余都是不可变文件的追加。

```text
Commit 要点（源码层面）：
1. 写数据文件 → 写 Manifest → 写 metadata.json（新版本）
2. 原子更新 —— Catalog 里「当前 metadata 指针」CAS 更新
3. 乐观并发 —— 带上期望快照 ID，冲突则重试
4. 幂等 —— 提交失败可重试，不产生脏数据
```

```text
Commit 流程：
1. 写数据（新 Parquet 文件）
2. 生成 Manifest（引用新文件）
3. 生成 metadata.json v2（current-snapshot 指向新快照）
4. Catalog CAS 更新指针（v1 → v2），失败重试
```

## Hudi Timeline

Hudi 的 Timeline（时间线）是 Hudi 的元数据核心：记录表上所有动作（commit、deltacommit、compaction、clean）的时间序列，存在 .hoodie 目录下。每个动作是一个 Instant，有 requested/inflight/completed 三态。Timeline 是 Hudi 实现「事务性、恢复、增量拉取」的基础——读表先读 Timeline 确定当前状态，写表通过 Timeline 的 Instant 状态实现幂等和并发控制。

```text
Hudi Timeline 要点：
1. 位置 —— .hoodie/ 目录
2. Instant —— 一个动作的时间点（commit/compaction/clean）
3. 三态 —— requested → inflight → completed
4. 用途 —— 事务性、故障恢复、增量拉取、并发控制
```

```text
.hoodie/ 结构：
.hoodie/
├── hoodie.properties          # 表配置
├── 20240814100000.commit      # 完成的 commit（COW）
├── 20240814110000.deltacommit # MOR 增量提交
└── 20240814120000.inflight    # 进行中的动作（恢复用）
```

## Delta Transaction Log

Delta 的 Transaction Log（事务日志）是 Delta 的元数据核心：存在 _delta_log 目录下，每次提交追加一个 JSON 文件（000000.json、000001.json...），记录这次操作「新增/删除的 Parquet 文件 + 统计 + schema 变更」。读表时重放日志得到当前文件清单；为加速，定期把日志合并成 checkpoint（Parquet 格式快照）。并发用「乐观并发」——提交时对比版本号，冲突重试。

```text
Delta Transaction Log 要点：
1. 位置 —— _delta_log/ 目录
2. 格式 —— 每次提交一个 JSON（版本号命名）
3. 内容 —— add/remove 的文件 + 统计 + schema 变更
4. checkpoint —— 定期合并日志为 Parquet 快照
5. 并发 —— 乐观并发（版本号 CAS），冲突重试
```

```text
_delta_log/ 结构：
_delta_log/
├── 000000.json       # 第一个版本
├── 000001.json       # 第二个版本（追加）
├── 000010.checkpoint.parquet  # 检查点（合并前 10 个版本）
└── _last_checkpoint  # 最近的检查点位置
```

## 应用场景实战

### 场景一：Iceberg 时间旅行排查数据问题

```sql
-- 数据被误改，用 Iceberg 快照追溯
-- 1. 看快照历史
SELECT * FROM db.orders.snapshots;
-- 2. 对比两个快照的数据差异（定位误改）
-- 3. 回滚到误改前的快照
CALL db.system.rollback_to_snapshot('db.orders', <snapshot-id>);
```

### 场景二：Delta 表文件清理排查

```text
Delta 表存储膨胀排查：
1. 看 _delta_log 版本数 —— 版本过多说明没 checkpoint
2. VACUUM 没跑 —— 软删除文件堆积
3. 解法 —— 定期 VACUUM + 依赖自动 checkpoint
```

## 最佳实践与踩坑记录

### 最佳实践

1. 读 Lakehouse 源码，重点是「如何用不可变文件 + 原子指针更新实现事务」
2. Iceberg 重点读 metadata.json 的三层引用和 CAS 提交
3. Hudi 重点读 Timeline 的 Instant 三态和恢复机制
4. Delta 重点读 Transaction Log 的重放和 checkpoint
5. 理解「元数据与数据分离」是三种表格式的共同设计

### 踩坑记录

```text
坑 1：直接读数据文件目录绕过元数据
结论：读到半成品或旧版本数据。
原因：表格式的数据文件是「追加 + 软删除」，元数据决定可见性。
解法：始终通过表格式接口读，别直接 list 数据文件。

坑 2：忽略元数据文件的清理
结论：metadata.json / manifest / _delta_log 无限增长。
原因：每次提交都产生新元数据文件，不清理会膨胀。
解法：定期 expire_snapshots / VACUUM / checkpoint。

坑 3：多写者并发提交冲突
结论：提交失败或数据覆盖。
原因：乐观并发下，多个写者同时提交，版本冲突。
解法：依赖 CAS 重试机制，或业务上串行化写入。

坑 4：把 checkpoint 当「数据备份」
结论：误以为 checkpoint 是数据快照，删了数据文件。
原因：checkpoint 只是元数据日志的合并，不含数据。
解法：数据备份用快照/时间旅行，checkpoint 只管元数据。
```
