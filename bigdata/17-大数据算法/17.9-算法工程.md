## 概述

算法工程（Algorithm Engineering）是把「理论算法」变成「生产可用的高性能实现」的工程方法。它不研究新算法，而是用工程手段回答：这个算法在真实大数据上跑得动吗？瓶颈在哪？内存/磁盘/网络够不够？结果准不准？它涵盖复杂度分析（时间/空间/I/O/网络四类）、性能测量（Benchmark/Profiling）、容量规划（数据规模估算）、精度控制（误差分析）、以及分布式特有的并行化和故障恢复。算法工程的终极目标是「在给定的硬件和成本约束下，让算法以可接受的精度和延迟落地」。

```text
算法工程关注的核心问题：
1. 跑得动吗 —— 时间复杂度/空间复杂度是否可接受
2. 瓶颈在哪 —— CPU / 内存 / 磁盘 I/O / 网络，哪个是短板
3. 资源够吗 —— 数据规模 vs 内存/磁盘/网络带宽的估算
4. 结果准吗 —— 近似算法的误差是否在业务可接受范围
5. 稳不稳 —— 并行化的正确性、故障恢复能力
```

```text
四种复杂度：时间复杂度（CPU 计算量）、空间复杂度（内存占用）、
I/O 复杂度（磁盘读写次数，外存核心）、网络复杂度（节点传输量，分布式核心）。
```

## 时间复杂度

时间复杂度描述算法运行时间随输入规模 N 增长的趋势，用大 O 记号（上界）、Ω（下界）、Θ（紧界）表达，忽略常数和低阶项。大数据场景里，O(N)、O(N log N) 通常可接受，O(N²) 及以上在 N 达到亿级时基本不可行。分析时关注最坏情况、平均情况和均摊复杂度（如动态数组扩容的均摊 O(1)）。工程上「大 O 相同」的算法，常数项（缓存友好性、内存访问模式）能差几十倍，所以理论复杂度只是起点。

```text
时间复杂度要点：
1. 记号 —— O 上界、Ω 下界、Θ 紧界，忽略常数和低阶项
2. 增长趋势 —— O(1) < O(log N) < O(N) < O(N log N) < O(N²) < O(2^N)
3. 大数据红线 —— N 亿级时，O(N²) 基本不可行
4. 均摊 —— 动态数组扩容均摊 O(1)，别只看单次最坏
```

```python
import time

def measure(func, data):
    start = time.perf_counter()
    func(data)
    return time.perf_counter() - start

data = list(range(100000))
# O(N)：线性，规模翻倍耗时翻倍
print(f"线性 O(N) 耗时 {measure(sum, data)*1000:.2f}ms")
# O(N²)：平方，规模翻倍耗时翻 4 倍
print(f"平方 O(N²) 耗时 {measure(lambda d: [sum(d) for _ in d], data[:2000])*1000:.2f}ms（仅 2000 元素）")
```

## 空间复杂度

空间复杂度描述算法运行所需的额外内存（或含输入的总内存）随规模 N 的增长。大数据算法对空间极度敏感——能 O(1) 就别 O(N)，能 O(N) 就别 O(N log N)。这也是「近似算法/流式算法」存在的根本原因：精确解需要 O(N) 内存存全量数据，N 是亿级时内存直接爆炸，所以用 O(1/ε) 的 sketch 换有误差的近似结果。工程上要区分「原地算法」（in-place，不额外开空间）和需要额外缓冲区的情况。

```text
空间复杂度要点：
1. 增长 —— O(1) < O(log N) < O(N) < O(N log N)
2. 大数据红线 —— 亿级数据 O(N) 内存往往不可行
3. 近似动机 —— 精确 O(N) 内存 → 近似 O(1/ε) 内存 + 误差
4. 原地算法 —— 不额外开数组，空间 O(1)，如原地排序
```

```python
import sys

n = 1_000_000
data = list(range(n))
print(f"全量列表内存: {sys.getsizeof(data)/1e6:.1f} MB（O(N)）")

total = 0
for x in range(n):          # O(1) 空间：只存累加器
    total += x
print(f"流式求和内存: O(1)，只存累加器，不存全量")
```

## IO Complexity

I/O 复杂度衡量算法读写磁盘/外存的次数（以「块」为单位），是外存算法和数据库的核心指标——磁盘一次随机 I/O 约 10ms，比内存访问慢 5~6 个数量级。外排序的 I/O 复杂度 O(N/B · log_{M/B}(N/B))，B+ 树查找 I/O 复杂度 O(log_t N)（等于树高）。优化的核心是「顺序 I/O 替代随机 I/O」「增大块大小 B」「减少 I/O 轮数」。大数据的列式存储、LSM 树、Parquet 都是围绕降低 I/O 复杂度设计的。

```text
I/O 复杂度要点：
1. 单位 —— 一次「块」读写计一次 I/O（块大小 B）
2. 成本 —— 一次随机 I/O ≈ 10ms，比内存慢 5~6 个数量级
3. 外排序 —— O(N/B · log_{M/B}(N/B)) 次 I/O
4. 优化 —— 顺序 I/O 替代随机 I/O、增大块、减少轮数
```

```python
n = 10_000_000
B = 64 * 1024              # 64KB 块
random_ios = n             # 逐条写 = n 次随机 I/O
seq_ios = n // B           # 按块写 = n/B 次顺序 I/O
print(f"逐条随机写 I/O {random_ios:,} 次 vs 按块顺序写 I/O {seq_ios:,} 次")
print(f"相差 {random_ios/seq_ios:.0f} 倍 —— 顺序 I/O 是外存性能关键")
```

## Network Complexity

网络复杂度衡量分布式算法中节点间传输的数据量，是分布式计算的「第一成本」——网络带宽（Gbps 级）比内存带宽（GB/s 级）慢几个数量级，跨机传输还有序列化、延迟开销。Shuffle 的数据量、Broadcast 的复制次数、聚合的中间结果传输量都属于网络复杂度。优化方向：Map 端局部聚合减少 Shuffle、协同分区免 Shuffle、数据压缩、减少网络往返（批处理而非逐条）。

```text
网络复杂度要点：
1. 单位 —— 节点间传输的字节数/记录数
2. 成本 —— 网络带宽比内存带宽慢几个数量级，还有延迟
3. 大头 —— Shuffle 数据量、Broadcast 复制、中间结果传输
4. 优化 —— Combiner 减 Shuffle、协同分区、压缩、批处理
```

```python
def shuffle_bytes(records, size, nodes, with_combiner=False):
    if with_combiner:                     # Combiner 后每节点只传一份
        return nodes * size
    return records * size                 # 否则每条记录都传

n, size, nodes = 100_000_000, 100, 100
without = shuffle_bytes(n, size, nodes)
with_c = shuffle_bytes(n, size, nodes, with_combiner=True)
print(f"无 Combiner 传 {without/1e9:.1f} GB，有 Combiner 传 {with_c/1e6:.1f} MB")
```

## Benchmark

Benchmark（基准测试）是「在受控条件下测量算法/系统性能」的方法，用于选型、调优、回归验证。关键原则：① 数据规模要贴近真实（用小数据测不出真实瓶颈）；② 多次运行取统计值（中位数/分位数，别只看平均值）；③ 预热（warm-up）排除 JIT/缓存冷启动影响；④ 隔离变量（每次只改一个参数）；⑤ 记录环境（硬件、版本、数据特征）。大数据常用的基准有 TPC-H/TPC-DS（数仓）、Sort Benchmark（排序）、YCSB（KV 存储）。

```text
Benchmark 要点：
1. 贴近真实 —— 数据规模、分布要像生产，小数据会误导
2. 统计值 —— 多次取中位数/P95，别只看平均值
3. 预热 —— warm-up 排除 JIT 和缓存冷启动
4. 隔离变量 —— 一次只改一个参数，A/B 对比
```

```python
import time, statistics, random

def benchmark(func, data, warmup=3, runs=10):
    for _ in range(warmup):          # 预热
        func(data)
    times = []
    for _ in range(runs):
        s = time.perf_counter()
        func(data)
        times.append(time.perf_counter() - s)
    return statistics.median(times)

data = list(range(100000))
random.shuffle(data)
print(f"排序中位数延迟 {benchmark(sorted, data)*1000:.2f}ms（预热+多次取中位数）")
```

## Profiling

Profiling（性能剖析）是「定位程序时间/内存花在哪」的方法，回答「瓶颈到底在哪个函数、哪行代码」，是优化的前提——不剖析就优化等于盲人摸象。分两类：采样型 profiler（定期采样调用栈，开销小，适合找热点函数）和插桩型 profiler（统计每函数精确耗时，开销大但精确）。Python 用 cProfile，Java 用 JProfiler/async-profiler，Go 用 pprof。核心产出是「热点函数排行」和「调用关系火焰图」。

```text
Profiling 要点：
1. 目的 —— 定位热点函数/瓶颈，别凭感觉优化
2. 采样型 —— 定期采样调用栈，开销小，找热点
3. 插桩型 —— 精确统计每函数耗时，开销大但准
4. 产出 —— 热点排行 + 火焰图，指导优化
```

```python
import cProfile, pstats, io

def slow(n):
    return sum(i * i for i in range(n))   # 热点函数

pr = cProfile.Profile()
pr.enable()
for _ in range(50):
    slow(200000)
pr.disable()

s = io.StringIO()
pstats.Stats(pr, stream=s).sort_stats("cumulative").print_stats(2)
print(s.getvalue())
```

## 数据规模估算

数据规模估算（容量规划）是在写代码前，先估算「数据量、内存、磁盘、网络」能不能撑住，避免上线后才发现内存不够、磁盘爆满。核心是「单位换算」和「量级估算」：1 亿条记录 × 每条 200 字节 = 20GB；10 亿用户去重需要 O(N) 内存存 ID 不可行 → 用 HLL 几 KB 近似。工程上常用「2 的幂近似」（2^10≈10^3）快速心算量级，判断方案可行性，这是大数据算法工程师的基本功。

```text
数据规模估算要点：
1. 先算量级 —— 记录数 × 单条大小 = 总数据量
2. 换算单位 —— KB/MB/GB/TB，2^10≈10^3 快速心算
3. 对号入座 —— 内存够吗？磁盘够吗？网络带宽够吗？
4. 提前决策 —— 不够就上近似算法、分区、外存，别等上线崩
```

```python
def estimate(records, record_bytes):
    total = records * record_bytes
    for unit in ["B", "KB", "MB", "GB", "TB", "PB"]:
        if total < 1024 or unit == "PB":
            return f"{total:.1f} {unit}"
        total /= 1024

print(f"10 亿条日志（每条 200B）≈ {estimate(1_000_000_000, 200)}")
print("去重：精确需存 10 亿 ID（GB 级），HLL 近似只需几 KB（误差 1%）")
```

## 精度与误差分析

精度与误差分析是「近似算法」的配套工程——用近似结果前，必须量化「误差有多大、概率多高」，否则近似结果不能用于决策。核心概念：绝对误差（估计值 - 真实值）、相对误差（绝对误差/真实值）、置信区间（结果落在某范围的概率）。sketch 类算法通常提供 (ε, δ) 保证：「以 1-δ 的概率，误差不超过 ε」。工程上要「把误差换算成业务影响」——1% 的 UV 误差对 1 亿 UV 是 ±100 万，能不能接受要业务拍板。

```text
精度与误差分析要点：
1. 绝对误差 —— |估计 - 真实|，相对误差 —— 绝对误差/真实值
2. (ε, δ) 保证 —— 以 1-δ 概率，误差 ≤ ε
3. 误差 vs 内存 —— 误差减半通常要 4 倍内存
4. 业务换算 —— 把误差换算成业务影响，判断可否接受
```

```python
import math

for k in [100, 400, 1600, 6400, 25600]:
    err = 1.0 / math.sqrt(k)      # sketch 相对误差 ≈ c/√k
    print(f"桶数 k={k:>6} → 相对误差 {err*100:.2f}%（桶数 ×4 误差才减半）")

uv = 100_000_000
print(f"1% 误差对 1 亿 UV = ±{uv*0.01:,.0f}（业务能否接受？）")
```

## 并行化

并行化是把算法拆成可同时执行的子任务，用多核/多机加速。核心挑战不在「拆」，而在「拆得对、合得好」：① 可并行性——子任务间无依赖才能并行（Amdahl 定律：串行部分 s 决定加速上限，加速比 ≤ 1/s）；② 数据划分——负载均衡，别让某个核/节点干等；③ 同步开销——锁竞争、线程切换、通信会吃掉并行收益；④ 正确性——并发访问共享状态要加锁或用无锁/不可变结构。大数据框架（Spark/Flink）已把并行化封装好，算法工程师要理解其数据分区与并行度调优。

```text
并行化要点：
1. Amdahl 定律 —— 串行部分 s 决定加速上限，加速比 ≤ 1/s
2. 可并行性 —— 子任务无依赖才能并行
3. 负载均衡 —— 数据划分均匀，别让某核/节点干等
4. 同步开销 —— 锁竞争、通信会吃掉并行收益
```

```python
def amdahl(f, p):
    s = 1 - f                        # 串行比例
    return 1 / (s + (1 - s) / p)     # 加速比 S

for f in [0.5, 0.9, 0.99]:
    print(f"并行比例 {f*100:.0f}%，8 核加速比 = {amdahl(f, 8):.2f}")
print("结论：串行部分哪怕 1%，加速比上限也只有 100 倍")
```

## 故障恢复

故障恢复是分布式/长任务算法「在部分节点/任务失败后能继续正确完成」的能力。大数据作业跑几小时甚至几天，硬件故障、网络抖动、OOM 几乎必然发生，所以「能自动重算」比「追求零故障」更现实。核心手段：① 幂等（重算不产生副作用）；② Checkpoint（定期保存中间状态，失败从检查点恢复而非重头）；③ 重试与退避（瞬时故障重试，指数退避）；④ 任务级容错（MapReduce 失败的任务重跑，Flink 从 checkpoint 恢复状态）。核心原则是「状态可重建、结果不重复」。

```text
故障恢复要点：
1. 前提 —— 长任务故障几乎必然发生，重算比零故障现实
2. 幂等 —— 重算不产生重复/副作用
3. Checkpoint —— 定期存中间状态，失败从检查点恢复
4. 重试退避 —— 瞬时故障重试，指数退避避免雪崩
```

```python
import time, random

def resilient(stages, checkpoint_every=2):
    state = {}
    for i, stage in enumerate(stages):
        for attempt in range(3):          # 最多重试 3 次
            if random.random() < 0.3:     # 30% 概率瞬时故障
                print(f"{stage} 第 {attempt+1} 次失败，退避重试")
                time.sleep(0.2 * (2 ** attempt))
                continue
            state[stage] = f"done_{stage}"
            print(f"{stage} 完成")
            break
        if (i + 1) % checkpoint_every == 0:
            print(f"  -> Checkpoint: {list(state.keys())}")
    return state

resilient(["读取", "清洗", "聚合", "写入"])
```

```python
def capacity_plan(records, record_bytes, memory_gb, use_approx=False):
    total_gb = records * record_bytes / (1024**3)
    if use_approx:
        return "近似算法：内存几 KB，可行（误差 1%~2%）"
    return (f"精确算法：需 {total_gb:.1f}GB ≤ {memory_gb}GB，可行"
            if total_gb <= memory_gb else

```

### 场景二：用 Profiling 定位并优化热点

```python
import cProfile, pstats, io

def hot(n):                          # 热点：纯 Python 循环
    s = 0
    for i in range(n):
        s += i * i
    return s

def optimized(n):                    # 优化：内建 sum + 生成器
    return sum(i * i for i in range(n))

pr = cProfile.Profile()
pr.enable()
for _ in range(50):
    hot(200000)
pr.disable()
s = io.StringIO()
pstats.Stats(pr, stream=s).sort_stats("cumulative").print_stats(2)
print(s.getvalue())
print("优化方向：用内建函数/向量化替代纯 Python 循环（热点函数）")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 写代码前先做数据规模估算，判断内存/磁盘/网络是否可行
2. 优化前先 Profiling，定位热点再动手，别凭感觉优化
3. Benchmark 要预热 + 多次取中位数，数据规模贴近生产
4. 近似算法一定做误差分析，把误差换算成业务影响再决策
5. 大数据场景优先考虑 I/O 和网络复杂度，CPU 往往不是瓶颈
6. 长任务必做 Checkpoint 和幂等重试，别假设零故障
7. 并行化先算 Amdahl 上限，串行部分大时并行收益有限

### 踩坑记录

```text
坑 1：用小数据 Benchmark 就下结论
结论：算法在测试集飞快，上线后在大数据上崩溃或极慢。
原因：小数据下 I/O、内存、缓存效应都测不出，瓶颈没暴露。
解法：Benchmark 用贴近生产的数据规模和分布，测真实瓶颈。

坑 2：只看平均延迟忽略长尾
结论：P99 延迟是 P50 的几十倍，用户体验差。
原因：平均值被大量正常请求拉低，掩盖了极少数慢请求。
解法：看 P95/P99 分位数，长尾才是真实用户体验。

坑 3：忽略 I/O 复杂度只优化 CPU
结论：CPU 优化半天，磁盘 I/O 瓶颈没动，性能没提升。
原因：大数据场景磁盘/网络是主要瓶颈，CPU 反而空闲。
解法：先 Profiling 确认瓶颈在哪，大概率在 I/O 或 Shuffle。

坑 4：近似结果没做误差分析直接当精确值用
结论：业务把 1% 误差当精确，导致决策偏差甚至事故。
原因：sketch 是近似，误差随内存减小而增大。
解法：明确误差范围和置信度，换算成业务影响，必要时加桶数。

坑 5：长任务没做 Checkpoint，失败重头再来
结论：跑了 8 小时的作业失败后从头跑，成本翻倍。
原因：没有中间状态保存，失败只能全量重算。
解法：定期 Checkpoint，失败从检查点恢复；任务级容错。

坑 6：并行化忽略 Amdahl 定律
结论：加了 100 核，加速比只有 2 倍，资源浪费。
原因：串行部分占比高，并行度再高也到不了加速上限。
解法：先优化串行部分，再并行化；评估加速上限再投入。
```
