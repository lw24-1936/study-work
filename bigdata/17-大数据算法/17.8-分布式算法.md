## 概述

分布式算法是把「一台机器算不完」的问题拆到多台机器上并行计算，再合并结果的算法。它的核心挑战不在单机算力，而在「数据怎么分（Partitioning）、机器怎么协调、网络怎么传数据（Shuffle）、结果怎么聚合」。分布式计算的成本模型里，网络传输（Shuffle）往往比 CPU 更贵，所以好的分布式算法要「数据局部性好、Shuffle 少、负载均衡」。MapReduce、Spark、Flink 的底层都是这些分布式算法原语的组合。

```text
分布式算法的核心关注点：
1. 数据分布 —— 数据怎么分到各节点（分区/哈希）
2. 通信 —— 节点间数据传输（Shuffle/Broadcast），网络是主要成本
3. 协调 —— 各节点并行计算，最后聚合
4. 负载均衡 —— 避免某节点数据过多（数据倾斜）拖慢整体
```

```text
单机关注 CPU/内存，分布式关注 Shuffle 数据量、网络带宽、节点间负载
均衡，关键指标是并行度、数据倾斜、网络开销。
```

## Partitioning

分区（Partitioning）是把一个大数据集按某种规则切分成多个子集，分布到不同节点/分区并行处理，是分布式计算的起点。常见分区策略：范围分区（按键的区间切，适合有序/范围查询）、哈希分区（按哈希值取模，均匀但无序）、轮询分区（Round-Robin，顺序均匀）、自定义分区（按业务键）。好的分区让「相关的数据聚在一起」、各分区大小均衡，是避免数据倾斜和减少 Shuffle 的前提。

```text
分区策略要点：
1. 范围分区 —— 按键区间切，支持范围查询，易倾斜（热点键）
2. 哈希分区 —— hash(key) % N，均匀但丢失顺序
3. 轮询分区 —— 轮流分配，绝对均匀，无局部性
4. 自定义 —— 按业务（地区/用户 ID）分，同键聚合
```

```python
def hash_partition(records, num_partitions):
    """哈希分区：hash(key) % N"""
    parts = [[] for _ in range(num_partitions)]
    for key, val in records:
        parts[hash(key) % num_partitions].append((key, val))
    return parts

def range_partition(records, num_partitions):
    """范围分区：按 key 排序后切成 N 段"""
    sorted_records = sorted(records, key=lambda x: x[0])
    n = len(sorted_records)
    step = (n + num_partitions - 1) // num_partitions
    return [sorted_records[i:i+step] for i in range(0, n, step)]

records = [(f"k{i}", i) for i in range(100)]
hp = hash_partition(records, 4)
rp = range_partition(records, 4)
print("哈希分区大小:", [len(p) for p in hp], "| 范围分区大小:", [len(p) for p in rp])
```

## Consistent Hashing

一致性哈希解决「分布式缓存在节点增减时尽量少迁移数据」的问题：把节点和键都哈希到一个环上（0~2^32-1），键落到「顺时针第一个节点」。这样增删一个节点，只影响环上相邻的一小段键，迁移量从「几乎全部」降到「1/N」。配合「虚拟节点（每个物理节点映射多个环上位置）」解决节点少时环上分布不均的问题。它是分布式缓存（Memcached、Redis Cluster）、分布式存储的经典数据分布算法。

```text
一致性哈希要点：
1. 哈希环 —— 节点和键都映射到 [0, 2^32) 环
2. 归属 —— 键顺时针落到第一个节点
3. 迁移少 —— 增删节点只影响相邻段，迁移 O(K/N)
4. 虚拟节点 —— 每物理节点多个环位置，解决分布不均
```

```python
import hashlib

def _h(key):
    return int(hashlib.md5(str(key).encode()).hexdigest(), 16)

class ConsistentHash:
    def __init__(self, nodes, virtual_nodes=3):
        self.vnodes = {}          # 虚拟节点位置 -> 物理节点
        self.ring = []
        for node in nodes:
            for i in range(virtual_nodes):
                pos = _h(f"{node}#v{i}")
                self.vnodes[pos] = node
                self.ring.append(pos)
        self.ring.sort()

    def get_node(self, key):
        h = _h(key)
        import bisect
        idx = bisect.bisect_right(self.ring, h)
        if idx == len(self.ring):
            idx = 0
        return self.vnodes[self.ring[idx]]

ch = ConsistentHash(["node1", "node2", "node3"], virtual_nodes=3)
from collections import Counter
c = Counter(ch.get_node(f"key{i}") for i in range(1000))
print("键分布:", dict(c))   # 三节点较均衡
```

## Rendezvous Hashing

Rendezvous Hashing（最高随机权重哈希，HRW）是另一种「键到节点」的映射：对每个键，计算它到所有节点的哈希权重 w(k, n) = hash(k, n)，选权重最高的节点。它的最大优势是「最小化迁移」——增删节点时，只有原本映射到被删节点、或新映射到新节点的键才迁移，其他键完全不动；且不需要像一致性哈希那样维护环结构，实现简单。适合节点数不多、且节点列表动态变化的场景（如多机房副本选择、对象存储副本定位）。

```text
Rendezvous Hashing 要点：
1. 映射 —— 选 hash(key, node) 权重最高的节点
2. 最小迁移 —— 增删节点只影响极少数键（最优迁移）
3. 简单 —— 无环结构、无需排序，纯哈希计算
4. 适用 —— 节点数少、列表动态变化的场景
```

```python
import hashlib

def hrw_weight(key, node):
    return int(hashlib.md5(f"{key}:{node}".encode()).hexdigest(), 16)

def rendezvous_get(key, nodes):
    return max(nodes, key=lambda n: hrw_weight(key, n))

nodes = ["n1", "n2", "n3", "n4"]
print("键 k1 ->", rendezvous_get("k1", nodes), "| 键 k2 ->", rendezvous_get("k2", nodes))

# 验证最小迁移：去掉一个节点后，多数键映射不变
nodes_new = ["n1", "n2", "n4"]
unchanged = sum(1 for i in range(1000)
                if rendezvous_get(f"k{i}", nodes) == rendezvous_get(f"k{i}", nodes_new))
print(f"删节点后 {unchanged}/1000 键映射不变（最小迁移）")
```

## MapReduce

MapReduce 是分布式批计算的经典编程模型：把计算抽象成 Map（对每条记录做变换，输出中间键值对）和 Reduce（对同键的中间值聚合）两个阶段，框架负责把中间结果按键 Shuffle 到各 Reduce 任务。用户只需写 map 和 reduce 两个函数，框架自动处理分区、Shuffle、排序、容错。它是 Hadoop 的核心，也是「分布式聚合」的通用范式——WordCount 是最小示例。其思想（按键分组 + 分区聚合）贯穿 Spark、Flink 等所有分布式框架。

```text
MapReduce 要点：
1. Map —— 逐条变换，产出 (k, v) 中间对
2. Shuffle —— 框架按键把中间对分发到各 Reduce
3. Reduce —— 同键值聚合，输出结果
4. 容错 —— 中间结果落盘，任务失败可重算
```

```python
from collections import defaultdict

def mapreduce(data, mapper, reducer):
    """MapReduce 模型：map -> shuffle(按键分组) -> reduce"""
    intermediate = defaultdict(list)
    for record in data:
        for k, v in mapper(record):
            intermediate[k].append(v)
    return {k: reducer(k, vs) for k, vs in intermediate.items()}

# WordCount
def mapper(line):
    return [(word, 1) for word in line.split()]

def reducer(word, counts):
    return sum(counts)

lines = ["hello world", "hello mapreduce", "world of mapreduce"]
print("WordCount:", mapreduce(lines, mapper, reducer))
```

## Distributed Join

分布式连接（Distributed Join）在多节点上做两个大表的 join，是分布式计算最贵的操作之一。策略取决于数据分布：① Shuffle Join（Sort-Merge/Hash Join）——两表按连接键哈希/排序重分布到同一节点，再本地 join，通用但 Shuffle 数据量大；② Broadcast Join——小表广播到所有节点，大表本地 join，避免 Shuffle，适合「一大一小」；③ 协同分区（Co-Partition）——两表预先按相同键分区，无需 Shuffle 直接本地 join，最省。选错策略会导致 Shuffle 爆炸或内存溢出。

```text
分布式连接策略要点：
1. Shuffle Join —— 两表按键重分布再本地 join，通用但 Shuffle 大
2. Broadcast Join —— 小表广播，大表本地 join，避免 Shuffle
3. 协同分区 —— 预先同键分区，免 Shuffle，最省
4. 选型 —— 看表大小和是否已分区，权衡 Shuffle 与内存
```

```python
def broadcast_join(large, small):
    """Broadcast Join：小表广播成字典，大表本地查"""
    lookup = dict(small)
    return [(k, v, lookup.get(k)) for k, v in large]

def shuffle_join(left, right):
    """Shuffle Join 简化：按键哈希重分布到同一桶，再本地 join"""
    from collections import defaultdict
    buckets = defaultdict(lambda: ([], []))
    for k, v in left:
        buckets[hash(k) % 4][0].append((k, v))
    for k, v in right:
        buckets[hash(k) % 4][1].append((k, v))
    result = []
    for (l_items, r_items) in buckets.values():
        r_map = defaultdict(list)
        for k, v in r_items:
            r_map[k].append(v)
        for k, v in l_items:
            for rv in r_map[k]:
                result.append((k, v, rv))
    return result

orders = [("u1", "o100"), ("u2", "o200")]
users = [("u1", "张三"), ("u2", "李四")]
print("Broadcast Join:", broadcast_join(orders, users))
```

## Distributed Aggregation

分布式聚合在多个节点上并行算聚合量（SUM/COUNT/AVG/分位数等），关键是「分阶段聚合减少传输」：先在 Map 端做局部聚合（Combiner/Partial Aggregation），把「每条记录一份」压缩成「每个节点一份」，再 Shuffle 到 Reduce 端做全局聚合。可交换可结合的聚合（SUM/COUNT）能完美用 Combiner；AVG 要传「和 + 计数」；分位数/去重需要 sketch（t-digest/HLL）合并。分层聚合把网络传输从 O(N) 降到 O(节点数)，是分布式聚合的性能关键。

```text
分布式聚合要点：
1. 局部聚合 —— Map 端先聚合，减少 Shuffle 数据量
2. 可结合性 —— SUM/COUNT 可结合，AVG 传 (sum, count) 对
3. 近似 —— 分位数用 t-digest、去重用 HLL，可合并
4. 分层 —— 树形多级聚合，网络传输 O(节点数) 而非 O(N)
```

```python
from collections import defaultdict

def distributed_sum(partitions):
    """两阶段聚合：各分区局部求和 -> 全局求和"""
    local_sums = [sum(p) for p in partitions]   # Map 端局部聚合
    return sum(local_sums)                       # Reduce 端全局聚合

def distributed_avg(partitions):
    """AVG 需传 (sum, count)，不能只传均值"""
    local = [(sum(p), len(p)) for p in partitions]
    total_sum = sum(s for s, _ in local)
    total_cnt = sum(c for _, c in local)
    return total_sum / total_cnt if total_cnt else 0

parts = [[1, 2, 3], [4, 5], [6, 7, 8, 9]]
print("分布式求和:", distributed_sum(parts), "| 分布式均值:", distributed_avg(parts))
```

## Shuffle

Shuffle 是分布式计算里「按键把数据从 Map 端重分布到 Reduce 端」的过程，是 MapReduce/Spark 里最昂贵、最容易出性能问题的环节。它包含：Map 端按分区函数写中间结果（可先落盘）、网络传输到对应 Reduce 节点、Reduce 端按需排序/归并。Shuffle 的数据量决定了作业性能——数据倾斜、大量小文件、不必要的 Shuffle 都是性能杀手。优化方向：减少 Shuffle 数据（Combiner/过滤）、减少 Shuffle 次数（合并操作）、避免 Shuffle（协同分区/广播）。

```text
Shuffle 要点：
1. 过程 —— Map 端分区写盘 -> 网络传输 -> Reduce 端归并
2. 成本 —— Shuffle 数据量是分布式作业的主要成本
3. 优化 —— Combiner 减数据、合并 Shuffle、协同分区免 Shuffle
4. 风险 —— 数据倾斜、小文件、磁盘/网络瓶颈
```

```python
from collections import defaultdict

def shuffle(mapper_outputs, num_reducers):
    """模拟 Shuffle：Map 输出按键哈希分发到各 Reducer"""
    reducers = defaultdict(list)
    for k, v in mapper_outputs:
        reducers[hash(k) % num_reducers].append((k, v))
    return reducers

# 两个 Map 任务输出中间对，Shuffle 到 3 个 Reducer
map1 = [("a", 1), ("b", 1), ("a", 1)]
map2 = [("b", 1), ("c", 1), ("a", 1)]
shuffled = shuffle(map1 + map2, 3)
for r, items in shuffled.items():
    print(f"Reducer {r}: {items}")
```

## Broadcast

广播（Broadcast）是「把一份小数据复制到所有节点内存」的操作，让每个节点本地访问而无需反复网络传输或 Shuffle。它解决「大表 join 小表」「全局配置/字典分发」的场景——把小表广播后，大表在本地查小表，避免 Shuffle。广播的数据必须是「小」的（能装进每个节点内存），否则内存溢出。Spark 的 broadcast join、Flink 的 broadcast state 都是这个思想。

```text
广播要点：
1. 语义 —— 一份数据复制到所有节点，本地访问
2. 用途 —— 大表 join 小表、全局字典/配置分发
3. 收益 —— 避免 Shuffle，网络只传一份
4. 前提 —— 广播数据必须小，能装进每节点内存
```

```python
def broadcast_join_big(large_stream, small_dict):
    """广播小字典到「每个节点」（模拟），大表本地查"""
    # 假设每个节点都持有一份 small_dict 的副本
    results = []
    for k, v in large_stream:
        if k in small_dict:
            results.append((k, v, small_dict[k]))
    return results

dim = {"u1": "张三", "u2": "李四", "u3": "王五"}     # 维度表（小）
fact = [("u1", 100), ("u2", 200), ("u1", 150), ("u4", 50)]  # 事实表（大）
print("广播 Join 结果:", broadcast_join_big(fact, dim))
```

## Data Skew Handling

数据倾斜（Data Skew）是分布式计算的经典难题：某个键的数据量远超其他键，导致「负责该键的分区/Reduce 任务」成为瓶颈，拖慢整个作业（木桶效应）。常见场景：热点用户、空值/null 键、少数大客户。处理手段：① 加盐（Salt）——给热点键加随机前缀打散，再二次聚合；② 两阶段聚合（局部聚合 + 全局聚合）；③ 单独处理热点键；④ 用随机前缀把空值打散。核心是「把热点键的数据均匀拆到多个任务」。

```text
数据倾斜处理要点：
1. 本质 —— 某键数据量过大，单个任务成瓶颈
2. 来源 —— 热点用户、null/空键、少数大客户
3. 加盐 —— 热点键加随机前缀打散，再二次聚合
4. 两阶段 —— 局部聚合 + 全局聚合，稀释热点
```

```python
from collections import defaultdict

def skewed_sum_with_salt(records, num_salt=3):
    """加盐两阶段聚合：热点键打散再合并"""
    # 阶段一：加盐打散，局部聚合
    local = defaultdict(int)
    for key, val in records:
        salted = f"{key}#{hash(key) % num_salt}"   # 热点键加盐
        local[salted] += val
    # 阶段二：去盐，全局聚合
    global_sum = defaultdict(int)
    for salted, val in local.items():
        key = salted.rsplit("#", 1)[0]
        global_sum[key] += val
    return dict(global_sum)

# 模拟倾斜：键 "hot" 数据量极大
records = [("hot", 1) for _ in range(10000)] + [("cold", 1) for _ in range(10)]
result = skewed_sum_with_salt(records, num_salt=10)
print("加盐聚合结果:", result)
```

## 应用场景实战

### 场景一：一致性哈希实现分布式缓存扩容

```python
import hashlib, bisect

class CacheCluster:
    def __init__(self, nodes, vnodes=5):
        self.nodes = nodes
        self.vnodes = vnodes
        self.ring = []
        self.node_of = {}
        for n in nodes:
            for i in range(vnodes):
                pos = int(hashlib.md5(f"{n}:{i}".encode()).hexdigest(), 16)
                self.ring.append(pos)
                self.node_of[pos] = n
        self.ring.sort()

    def locate(self, key):
        h = int(hashlib.md5(str(key).encode()).hexdigest(), 16)
        idx = bisect.bisect_right(self.ring, h)
        return self.node_of[self.ring[idx % len(self.ring)]]

cluster = CacheCluster(["cache-a", "cache-b", "cache-c"])
from collections import Counter
c = Counter(cluster.locate(f"user{i}") for i in range(10000))
print("缓存节点分布:", dict(c))

# 扩容：加一个节点，验证迁移比例小
old = Counter(cluster.locate(f"user{i}") for i in range(10000))
cluster2 = CacheCluster(["cache-a", "cache-b", "cache-c", "cache-d"])
new = Counter(cluster2.locate(f"user{i}") for i in range(10000))
migrated = sum(1 for i in range(10000)
               if cluster.locate(f"user{i}") != cluster2.locate(f"user{i}"))
print(f"扩容后迁移 {migrated}/10000 键（一致性哈希迁移少）")
```

### 场景二：MapReduce 模型统计日志词频

```python
from collections import defaultdict

def mapreduce_wordcount(logs):
    def mapper(line):
        return [(w, 1) for w in line.lower().split()]
    intermediate = defaultdict(list)
    for line in logs:
        for k, v in mapper(line):
            intermediate[k].append(v)
    return {k: sum(vs) for k, vs in intermediate.items()}

logs = [
    "error timeout error retry",
    "timeout retry error",
    "success success",
]
print("日志词频:", mapreduce_wordcount(logs))
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分区策略选哈希（均匀）还是范围（有序查询）要看查询模式，别一刀切
2. 分布式缓存/存储用一致性哈希或 Rendezvous Hashing，节点增减迁移最小
3. 大表 join 小表用 Broadcast Join，避免 Shuffle；两表都大才 Shuffle Join
4. 分布式聚合一定做 Map 端局部聚合（Combiner），把网络传输降一个数量级
5. 能协同分区就协同分区，彻底免 Shuffle
6. 热点键用加盐 + 两阶段聚合处理，别让单任务拖垮全作业

### 踩坑记录

```text
坑 1：一致性哈希不配虚拟节点
结论：节点少时环上分布严重不均，某节点负载是其他几倍。
原因：物理节点在环上位置稀疏且不均匀，键都挤到个别节点。
解法：每个物理节点映射多个虚拟节点，让环上分布均匀。

坑 2：大表 join 大表误用 Broadcast Join
结论：广播大表导致所有节点内存溢出，作业崩溃。
原因：广播数据要复制到每个节点内存，大表远超单节点内存。
解法：两表都大用 Shuffle Join，只有小表才广播。

坑 3：分布式 AVG 直接聚合均值
结论：结果错误（各节点均值再平均 ≠ 全局均值）。
原因：AVG 不可直接结合，需要 (sum, count) 一起传。
解法：传 (sum, count) 对，Reduce 端 sum/count 再除。

坑 4：忽略数据倾斜，热点键拖垮作业
结论：单 Reduce 任务处理 90% 数据，作业卡几小时。
原因：热点键都进同一分区，单任务成瓶颈（木桶效应）。
解法：加盐打散热点键，两阶段聚合；或单独处理热点键。

坑 5：Shuffle 前不做 Combiner
结论：网络传输 O(N) 条中间记录，Shuffle 成为瓶颈。
原因：Map 端输出全量中间对，没有局部聚合压缩。
解法：可结合聚合加 Combiner，把传输降到 O(节点数)。

坑 6：null/空键全进同一分区
结论：空值记录大量聚集，某分区严重倾斜。
原因：null 键哈希相同，全落同一 Reduce。
解法：给 null 加随机前缀打散，或过滤/单独处理空值。
```
