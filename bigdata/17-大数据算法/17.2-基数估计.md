## 概述

基数估计（Cardinality Estimation）是估算一个多重集中「不同元素的数量」（去重后的计数，即 DISTINCT COUNT）的算法。精确去重需要 O(n) 内存存所有见过的元素，在海量数据（十亿级 UV）下不可行。基数估计用「极小的固定内存（几 KB）」换「有误差的近似结果」，误差通常 1%~2%，是 UV/DAU 统计、日志去重、查询优化器（估算 join 结果行数）的核心技术。

```text
基数估计的核心权衡：
1. 精确去重 —— O(n) 内存，n 是不同元素数，海量不可行
2. 近似估计 —— O(1) 固定内存（几 KB），误差 1%~2%
3. 场景 —— UV/DAU、日志去重、查询优化器、图算法去重
4. 代表算法 —— Linear Counting、HyperLogLog、KMV、Theta Sketch
```

```python
# 问题：1 亿条日志里有多少不同用户？精确去重要存 1 亿个 ID
# 近似：几 KB 内存即可估计，误差 2% 内
```

## Linear Counting 线性计数

Linear Counting 是最早的基数估计算法：维护一个 m 位的位图（初始全 0），对每个元素哈希到某一位并置 1；统计位图中「0 的个数」V，用公式 n ≈ -m·ln(V/m) 估计基数。它空间 O(m)，误差与位图填充率有关——位图太满（接近全 1）时估计失真，所以适合「基数远小于位图大小 m」的场景。

```text
Linear Counting 要点：
1. 结构 —— m 位位图，元素哈希置位
2. 估计 —— n ≈ -m·ln(V/m)，V 是空位（0）的个数
3. 空间 —— O(m)，m 需远大于基数（填充率 < 1）
4. 局限 —— 基数接近 m 时误差骤增，需预先知道基数量级
```

```python
import random
import math

def linear_counting(elements, m):
    bitmap = [0] * m
    for e in elements:
        h = hash(e) % m
        bitmap[h] = 1
    V = bitmap.count(0)          # 空位个数
    if V == 0:
        return float('inf')      # 位图满了，估计失效
    return -m * math.log(V / m)

data = [f"user_{random.randint(0, 10000)}" for _ in range(100000)]
est = linear_counting(data, 20000)   # m 需远大于基数
print(f"Linear Counting 估计基数 {est:.0f}（真实约 10000）")
```

## HyperLogLog

HyperLogLog（HLL）是应用最广的基数估计算法：把元素哈希成二进制串，用「哈希值前导零的个数 + 1」（ρ）作为「稀有度」指标，分桶记录每个桶的最大 ρ，用调和平均估计基数 n ≈ α·m²/(Σ 2^(-ρ_j))。它只需 m·log₂(64) 位内存（m=2^14 时约 12KB），误差约 1.04/√m（m=2^14 时约 0.8%），是 Redis、Spark、Presto 等内置的近似去重实现。

```text
HyperLogLog 要点：
1. 原理 —— 哈希值前导零个数服从几何分布，最大前导零反映基数
2. 分桶 —— m 个桶，每桶记最大 ρ，调和平均合并
3. 空间 —— m=2^14 时约 12KB，几乎不随数据量增长
4. 误差 —— 约 1.04/√m，m=2^14 时约 0.8%
5. 可合并 —— 各桶取 max 即可合并多个 HLL（分布式聚合）
```

```python
import random
import math

class HyperLogLog:
    def __init__(self, p=14):       # p 决定桶数 m = 2^p
        self.p = p
        self.m = 1 << p
        self.registers = [0] * self.m

    def _rho(self, h, p):
        # 取哈希值后 (64-p) 位，数前导零
        return (h & (0xFFFFFFFFFFFFFFFF >> p)).bit_length() + 1

    def add(self, x):
        h = hash(x) & 0xFFFFFFFFFFFFFFFF
        j = h >> (64 - self.p)       # 前 p 位选桶
        self.registers[j] = max(self.registers[j], self._rho(h, self.p))

    def estimate(self):
        alpha = 0.7213 / (1 + 1.079 / self.m)   # 修正系数
        Z = sum(2.0 ** (-r) for r in self.registers)
        E = alpha * self.m * self.m / Z
        return int(E)

hll = HyperLogLog(p=14)
true = 100000
for _ in range(500000):   # 50 万条记录，10 万不同用户
    hll.add(f"user_{random.randint(0, true-1)}")
print(f"HLL 估计基数 {hll.estimate()}（真实 {true}，误差约 1%）")
```

## HLL++

HLL++ 是 Google 对 HyperLogLog 的工程化改进（HyperLogLog in Practice），是 BigQuery 和许多开源实现的默认版本。它补了 HLL 的几个短板：小基数时用偏差纠正表（bias correction）修正估计、极小基数（<5m/2）时退化为 Linear Counting、大基数（接近 2^64）时用 64 位哈希、稀疏表示（基数小时用字典存储而非全量桶数组）省内存。

```text
HLL++ 相对 HLL 的改进：
1. 小基数修正 —— 用实测偏差表纠正，小基数更准
2. 极小基数 —— 退化为 Linear Counting
3. 稀疏表示 —— 基数小时存稀疏字典，省内存
4. 64 位哈希 —— 支持超大基数（>10 亿）不失真
```

```python
# HLL++ 的关键：小基数偏差修正 + 稀疏表示（概念示意）
def hllpp_estimate(registers, m):
    # 朴素 HLL 估计
    alpha = 0.7213 / (1 + 1.079 / m)
    Z = sum(2.0 ** (-r) for r in registers)
    E = alpha * m * m / Z
    V = sum(1 for r in registers if r == 0)   # 空桶数
    if E <= 2.5 * m and V > 0:
        E = -m * math.log(V / m)              # 小基数退化为 Linear Counting
    return int(E)
```

## KMV

KMV（K-th Minimum Value）是另一种基数估计思路：对每个元素算哈希，维护「最小的 k 个哈希值」，用第 k 小的哈希值 U_k 估计基数 n ≈ (k-1)/U_k。它把哈希空间 [0,1) 均匀铺开，不同元素数 n 对应「最小 k 个哈希值」的期望分布。KMV 空间 O(k)，误差约 1.3/√(k-2)，实现比 HLL 直观，且天然支持「两个集合的交集基数」估计。

```text
KMV 要点：
1. 原理 —— 维护最小的 k 个哈希值，n ≈ (k-1)/U_k
2. 空间 —— O(k)，k 是保留的哈希值个数
3. 误差 —— 约 1.3/√(k-2)
4. 优势 —— 直观、支持交集基数（两集合合并最小的 k 个即可）
```

```python
import random
import heapq

def kmv_estimate(stream, k):
    heap = []                     # 维护最小的 k 个哈希值（用负值做最大堆）
    for x in stream:
        h = random.random()       # [0,1) 均匀哈希
        if len(heap) < k:
            heapq.heappush(heap, -h)
        elif h < -heap[0]:
            heapq.heapreplace(heap, -h)
    U_k = -heap[0]                # 第 k 小的哈希值
    return (k - 1) / U_k if U_k > 0 else float('inf')

true = 50000
stream = (f"u{random.randint(0, true-1)}" for _ in range(200000))
est = kmv_estimate(stream, 200)
print(f"KMV 估计基数 {est:.0f}（真实 {true}）")
```

## Theta Sketch

Theta Sketch 是 Apache DataSketches 库的基数估计结构，是 KMV 的工程化演进：维护一个「哈希值上限阈值 θ」，只保留哈希值 < θ 的元素，θ 随数据增长而下降。它支持「集合运算」——两个 Theta Sketch 求并集/交集基数，是 KMV 的「取最小 k」思想 + 阈值化的推广，广泛用于广告投放去重、漏斗分析、跨平台 UV 合并。

```text
Theta Sketch 要点：
1. 思想 —— 阈值 θ 过滤哈希值，保留 < θ 的元素
2. 集合运算 —— 并集/交集基数可直接合并计算
3. 误差 —— 类似 KMV，约 1/√k 量级
4. 库 —— Apache DataSketches 标准实现，Spark/Presto 集成
```

```python
import random

class ThetaSketch:
    def __init__(self, k=256):
        self.k = k
        self.theta = 1.0
        self.values = set()

    def add(self, x):
        h = random.random()
        if h < self.theta:
            self.values.add(h)
            if len(self.values) > self.k:
                # 超容量，缩小 theta，淘汰大哈希值
                sorted_vals = sorted(self.values)
                self.theta = sorted_vals[self.k]
                self.values = set(sorted_vals[:self.k])

    def estimate(self):
        if self.theta >= 1.0:
            return len(self.values)
        return len(self.values) / self.theta

ts = ThetaSketch(k=256)
true = 80000
for _ in range(300000):
    ts.add(random.randint(0, true-1))
print(f"Theta Sketch 估计基数 {ts.estimate():.0f}（真实 {true}）")
```

## Distinct Count 误差分析

近似基数估计的误差服从「相对标准误差 ≈ c/√k」的规律（c 是常数、k 是桶数/保留值数）：桶越多误差越小、但内存越大。HLL 约 1.04/√m，KMV 约 1.3/√(k-2)。误差是「相对误差」——1% 误差对 1 亿基数是 ±100 万。选择桶数时按「可接受的误差」反推：要 1% 误差，HLL 用 m=2^14 桶（12KB），要 0.5% 用 m=2^16（更大内存）。

```text
误差分析要点：
1. 相对误差 —— 约 c/√k，与基数大小无关、只与桶数 k 有关
2. 桶数 ↔ 误差 —— 桶数翻 4 倍，误差减半
3. 内存 ↔ 误差 —— 误差减半要 4 倍内存
4. 选型 —— 按可接受误差选桶数：1% → m=2^14，0.5% → m=2^16
```

```python
import math

def hll_error(m):
    return 1.04 / math.sqrt(m)

for m in [2**10, 2**12, 2**14, 2**16, 2**18]:
    print(f"m={m:6d} 桶 → 相对标准误差 {hll_error(m)*100:.2f}%")
```

## 应用场景实战

### 场景一：十亿级日志的 UV 统计

```python
# 用 HLL 统计一天的独立访客 UV（内存几 KB，误差 <1%）
import random

class UVCounter:
    def __init__(self):
        self.p = 14
        self.m = 1 << self.p
        self.regs = [0] * self.m

    def add(self, uid):
        h = hash(uid) & 0xFFFFFFFFFFFFFFFF
        j = h >> (64 - self.p)
        rho = (h & (0xFFFFFFFFFFFFFFFF >> self.p)).bit_length() + 1
        self.regs[j] = max(self.regs[j], rho)

    def count(self):
        alpha = 0.7213 / (1 + 1.079 / self.m)
        Z = sum(2.0 ** (-r) for r in self.regs)
        return int(alpha * self.m * self.m / Z)

uv = UVCounter()
for _ in range(10000000):          # 1000 万次访问
    uv.add(random.randint(1, 2000000))   # 200 万不同用户
print(f"UV ≈ {uv.count()}（真实约 200 万，内存 {len(uv.regs)*1} 字节）")
```

### 场景二：两个 HLL 合并算「总 UV」（分布式聚合）

```python
# 各分区算各自的 HLL，合并时逐桶取 max
def merge_hll(a, b):
    return [max(x, y) for x, y in zip(a.regs, b.regs)]

# 分区 1、2 各自统计，合并算并集 UV
# 这正是 Spark/Presto 里 approx_count_distinct 的分布式原理
```

## 最佳实践与踩坑记录

### 最佳实践

1. 精确去重不可行时用 HLL，误差 1% 内、内存几 KB
2. 桶数按误差需求选：1% 用 m=2^14，别盲目加大（内存 4 倍才换误差减半）
3. 需要集合运算（并集/交集）用 KMV/Theta Sketch
4. 分布式聚合用 HLL 的「逐桶取 max 合并」特性
5. 小基数场景用 HLL++（自动退化为 Linear Counting，更准）
6. 哈希函数要均匀（64 位），否则估计偏差大

### 踩坑记录

```text
坑 1：小基数用 HLL 误差巨大
结论：几百个不同元素的集合，HLL 估计误差几十%。
原因：HLL 的大数近似在小基数失效，偏差修正缺失。
解法：用 HLL++（小基数退化为 Linear Counting）或直接精确去重。

坑 2：哈希函数不均匀导致估计偏差
结论：估计值系统性偏大或偏小。
原因：哈希值分布不均，前导零分布偏离几何分布假设。
解法：用高质量 64 位哈希（MurmurHash3、xxHash），别用语言内置 hash。

坑 3：把基数估计当精确值用
结论：业务逻辑依赖精确去重数，出 bug。
原因：HLL 是近似，1% 误差在千万基数下是 ±10 万。
解法：明确近似边界，需精确的场景用精确去重或说明误差范围。

坑 4：误以为内存随数据量增长
结论：担心数据量大内存不够，选了过大的桶数浪费内存。
原因：HLL 内存只由桶数决定，与数据量无关。
解法：按误差需求定桶数，数据量再大内存不变。

坑 5：合并 HLL 时逐桶取 min 而非 max
结论：合并后估计严重偏低。
原因：HLL 合并语义是「保留每个桶的最大前导零」，取 min 会丢失稀有哈希。
解法：合并用逐桶 max，别用 min 或求和。
```
