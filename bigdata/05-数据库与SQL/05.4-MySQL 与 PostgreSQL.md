## 概述

MySQL 和 PostgreSQL 是两款最主流的开源关系型数据库，也是大数据生态里业务库（OLTP）的事实标准——MySQL 以简单、成熟、生态广见长，PostgreSQL 以功能强大、扩展性好、对复杂查询和 JSON/GIS 支持佳著称。理解它们底层的 InnoDB 存储引擎、MVCC、WAL、索引、事务、锁与复制机制，是设计可靠业务库、做 CDC 同步、排查线上问题的基石。

```text
MySQL 与 PostgreSQL 的核心机制：
1. InnoDB —— MySQL 默认存储引擎，B+ 树 + 行锁 + 事务 + 崩溃恢复
2. MVCC —— 多版本并发控制，读不阻塞写、写不阻塞读的关键
3. WAL —— 先写日志再写数据，崩溃后靠日志恢复，写性能的关键
4. Redo/Undo —— 重做日志（恢复已提交）与回滚日志（撤销未提交）
5. 索引 —— B+ 树为主，决定查询性能的上限
6. 事务 —— ACID 隔离级别，InnoDB 默认可重复读
7. 锁 —— 行锁/间隙锁/表锁，并发控制的另一面
8. 复制 —— 主从同步，读扩展与高可用的基础
```

```sql
-- 示例表
CREATE TABLE users (
    id       BIGINT PRIMARY KEY AUTO_INCREMENT,
    name     VARCHAR(64) NOT NULL,
    city     VARCHAR(64),
    balance  DECIMAL(12, 2) DEFAULT 0,
    created  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    KEY idx_city (city)
);
```

## InnoDB

InnoDB 是 MySQL 5.5 之后的默认存储引擎，也是目前唯一支持事务（ACID）、行级锁、外键和崩溃恢复的 MySQL 引擎。它用 B+ 树作为主键索引（聚簇索引），数据本身按主键顺序存储；二级索引存主键值，回表取数。InnoDB 是 MySQL 高性能高可靠的代名词，MyISAM 等旧引擎已基本被淘汰。

```text
InnoDB 要点：
1. 聚簇索引 —— 主键 B+ 树叶子节点直接存整行数据，主键查询最快
2. 二级索引 —— 叶子节点存主键值，命中后需「回表」查主键索引
3. 事务与行锁 —— 支持 ACID 事务和行级锁，并发高
4. Buffer Pool —— 内存缓存页，读写都先过它，是性能核心
5. 崩溃恢复 —— 靠 redo log 保证已提交数据不丢
```

```sql
-- 查看表使用的存储引擎
SHOW TABLE STATUS LIKE 'users';
SHOW ENGINES;

-- 建表显式指定 InnoDB
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    KEY idx_user (user_id)
) ENGINE = InnoDB;
```

## MVCC

MVCC（Multi-Version Concurrency Control）多版本并发控制，通过为每行维护多个版本，让读操作读到「事务开始时的快照」而不阻塞写，写操作也不阻塞读。InnoDB 用「隐藏字段（事务 ID + 回滚指针）+ Undo Log + ReadView」实现：每个事务看到的是一致性快照，实现「读已提交/可重复读」隔离级别下的无锁读。

```text
MVCC 要点：
1. 隐藏列 —— 每行有 DB_TRX_ID（最近修改事务）、DB_ROLL_PTR（指向 undo 版本链）
2. ReadView —— 读时根据活跃事务列表判断某版本是否可见
3. 版本链 —— 同一行被多次修改形成 undo 版本链，读时沿链找可见版本
4. 快照读 —— 普通 SELECT 走 MVCC，不加锁，是「读不阻塞写」的本质
```

```text
MVCC 可见性判断（简化）：
某版本可见当且仅当：
1. 该版本由当前事务自己修改 —— 可见
2. 该版本事务已提交且早于 ReadView —— 可见
3. 该版本事务未提交或晚于 ReadView —— 不可见，沿 undo 链往前找
```

```sql
-- 演示：事务 A 读到快照，不受事务 B 未提交修改影响
-- 会话 A
START TRANSACTION;
SELECT balance FROM users WHERE id = 1;   -- 读到 100

-- 会话 B（此时未提交）
UPDATE users SET balance = 200 WHERE id = 1;

-- 会话 A 再读（可重复读级别下仍读到 100）
SELECT balance FROM users WHERE id = 1;   -- 100，MVCC 快照
COMMIT;
```

## WAL

WAL（Write-Ahead Logging）预写日志：数据修改先顺序写日志，再异步刷入数据页。这样既保证崩溃后能重放日志恢复数据（持久性），又把随机写转换成顺序写（性能）。MySQL 的 redo log 和 PostgreSQL 的 WAL 都是这个思想——它是几乎所有现代数据库写入性能与可靠性的共同基石。

```text
WAL 要点：
1. 先日志后数据 —— 修改先写 redo/WAL，数据页延后落盘
2. 顺序写优势 —— 日志追加写是顺序 IO，比随机刷数据页快一个量级
3. 崩溃恢复 —— 重启时重放日志，把已提交但未落盘的数据补上
4. 提交即持久 —— 事务提交时强制刷日志（fsync），保证不丢
```

```text
事务提交的 WAL 流程：
1. 修改 Buffer Pool 中的数据页（内存）
2. 写 redo log（先写 redo buffer，提交时 fsync 到磁盘）
3. 后台线程异步把脏页刷回数据文件（checkpoint）
4. 崩溃时：数据页可能丢，但 redo log 完整，重放即可恢复
```

## Redo

Redo Log（重做日志）记录「物理层面的页修改」，用于崩溃后重放，把已提交事务的修改恢复到磁盘。它是循环写、固定大小的几个文件，写满后触发 checkpoint 把脏页刷盘并回收空间。Redo 保证持久性（D），是 InnoDB「已提交不丢」的根本保障。

```text
Redo 要点：
1. 物理日志 —— 记录「哪个页哪个偏移改成了什么」，重放快
2. 循环写 —— 固定大小文件组，覆盖写，靠 checkpoint 腾空间
3. 提交刷盘 —— innodb_flush_log_at_trx_commit=1 时每次提交 fsync，最安全
4. 与 Binlog 区别 —— Redo 是 InnoDB 层的崩溃恢复日志，Binlog 是 Server 层的主从复制日志
```

```text
innodb_flush_log_at_trx_commit 取值：
0 —— 每秒刷一次，宕机可能丢 1 秒数据（最快，最不安全）
1 —— 每次提交都 fsync（默认，最安全）
2 —— 每次提交写 OS 缓存，每秒刷盘（折中）
```

## Undo

Undo Log（回滚日志）记录「修改前的旧值」，用于事务回滚和 MVCC 的多版本。事务回滚时按 undo 记录把数据改回原状；MVCC 的版本链也依赖 undo 里的旧版本。Undo 是保证原子性（A）和一致性读（C 的一部分）的关键，同时支持「读不阻塞写」。

```text
Undo 要点：
1. 逻辑日志 —— 记录「如何撤销」，如把某行某列从 X 改回旧值
2. 回滚 —— 事务失败时沿 undo 把修改全部撤销
3. MVCC 版本链 —— undo 里的旧版本构成版本链，供快照读
4. 清理 —— 已提交且无活跃事务引用后由 purge 线程回收
```

```sql
-- 事务回滚依赖 undo：回滚后数据回到原值
START TRANSACTION;
UPDATE users SET balance = balance - 50 WHERE id = 1;   -- 100 -> 50
SELECT balance FROM users WHERE id = 1;                -- 50
ROLLBACK;                                              -- 靠 undo 撤销
SELECT balance FROM users WHERE id = 1;                -- 回到 100
```

## 索引

索引是加速查询的数据结构，MySQL/PostgreSQL 都以 B+ 树为主（PostgreSQL 还支持 Hash、GIN、GiST、BRIN）。B+ 树索引让等值、范围、前缀查询从 O(n) 降到 O(log n)，但会拖慢写入、占用空间。索引设计是关系库调优的第一课——选对列、选对顺序、避免冗余和失效。

```text
索引要点：
1. B+ 树 —— 叶子节点有序且互联，支持等值和范围，树高低（3~4 层即可存千万级）
2. 最左前缀 —— 联合索引 (a,b,c) 只有走 a、ab、abc 才生效，跳列失效
3. 回表 —— 二级索引查到主键后还要回聚簇索引取整行，覆盖索引可避免
4. 索引失效 —— 对列做函数、前导通配、隐式类型转换都会导致不走索引
```

```sql
-- 联合索引最左前缀
CREATE INDEX idx_user_city ON users (user_id, city);

-- 走索引（前缀匹配）
SELECT * FROM users WHERE user_id = 100 AND city = '北京';

-- 不走索引（跳过最左列）
SELECT * FROM users WHERE city = '北京';

-- 覆盖索引：查询列都在索引里，不回表
CREATE INDEX idx_city_name ON users (city, name);
SELECT city, name FROM users WHERE city = '上海';
```

## 事务

事务是一组要么全做、要么全不做的操作，保证 ACID：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。隔离级别决定并发事务之间的可见性：读未提交、读已提交、可重复读、串行化。MySQL InnoDB 默认可重复读，PostgreSQL 默认读已提交。

```text
事务隔离级别要点：
1. 读未提交 —— 能读到别的事务未提交的数据（脏读）
2. 读已提交 —— 只读已提交，可避免脏读，但有不可重复读/幻读
3. 可重复读 —— 同一事务内多次读结果一致（快照），InnoDB 默认
4. 串行化 —— 完全串行执行，无并发问题但性能最差
```

```sql
-- 查看与设置隔离级别
SELECT @@transaction_isolation;                 -- MySQL
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- PostgreSQL
SHOW transaction_isolation;
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 显式事务
START TRANSACTION;
UPDATE users SET balance = balance - 100 WHERE id = 1;
UPDATE users SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

## 锁

锁是并发控制的手段，与 MVCC 互补：MVCC 解决「读不阻塞写」，锁解决「写写冲突」和「需要加锁的读」。InnoDB 锁按粒度分行锁、间隙锁（Gap Lock）、临键锁（Next-Key Lock，行锁+间隙锁）和表锁；按类型分共享锁（S）和排他锁（X）。死锁由 InnoDB 自动检测并回滚其中一个事务。

```text
锁要点：
1. 行锁 —— 锁住索引记录，并发粒度最细
2. 间隙锁 —— 锁住索引记录之间的范围，防幻读（可重复读下默认开启）
3. 临键锁 —— 行锁 + 间隙锁的组合，InnoDB 默认行级锁形态
4. 死锁 —— 两事务互相等待对方锁，InnoDB 检测到后回滚其中一个
```

```sql
-- 显式加锁读
SELECT * FROM users WHERE id = 1 FOR UPDATE;      -- 排他锁，写用
SELECT * FROM users WHERE id = 1 FOR SHARE;        -- 共享锁，读用（MySQL 8+）

-- 查看当前锁与死锁
SHOW ENGINE INNODB STATUS;                        -- 含最近一次死锁信息
SELECT * FROM performance_schema.data_locks;      -- 当前持有的锁
```

## 复制

复制（Replication）把主库的变更同步到从库，用于读扩展、高可用和数据备份。MySQL 传统复制基于 binlog（二进制日志），从库通过 IO 线程拉取 binlog、SQL 线程重放；MySQL 8.0 的 Group Replication 和 PostgreSQL 的流复制/逻辑复制是更现代的形态。复制也是 CDC（如 Debezium 解析 binlog）的基础。

```text
复制要点：
1. 主从结构 —— 一主多从，主库写、从库读，读写分离
2. binlog 复制 —— 从库重放 binlog 事件，异步/半同步两种
3. 异步 vs 半同步 —— 异步主库不等从库（可能丢数据），半同步等至少一个从库确认
4. 逻辑复制 —— PostgreSQL 逻辑复制、MySQL 8 的 GTID，支持表级/行级过滤
```

```sql
-- MySQL 从库配置要点（my.cnf）
-- server-id 唯一、开启 binlog、配置 relay log
-- CHANGE MASTER TO ...; START SLAVE;  SHOW SLAVE STATUS;
SHOW SLAVE STATUS\G

-- PostgreSQL 流复制：主库配置
-- wal_level = replica, max_wal_senders = 8, hot_standby = on
-- 从库用 pg_basebackup 建基础备份后持续同步
```

```text
主从复制链路（MySQL 异步复制）：
主库写 binlog
   |  (从库 IO 线程拉取)
   v
从库 relay log
   |  (从库 SQL 线程重放)
   v
从库数据
```

## 应用场景实战

### 场景一：转账事务（保证原子性与一致性）

```sql
-- 从 A 转 100 给 B，要么都成功要么都失败
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- 校验余额不为负，为负则回滚
SELECT balance INTO @b FROM accounts WHERE id = 1;
IF @b < 0 THEN
    ROLLBACK;
ELSE
    COMMIT;
END IF;
```

### 场景二：读写分离 + 主从延迟排查

```text
读写分离架构：
业务写请求 -> 主库（写）
业务读请求 -> 从库（读，可多个从库负载均衡）
问题：主从复制有延迟，刚写入的数据立刻读从库可能读不到

排查步骤：
1. SHOW SLAVE STATUS 看 Seconds_Behind_Master（主从延迟秒数）
2. 关键读（如订单详情页刚下单后）强制走主库
3. 非关键读容忍延迟，或加延迟阈值判断
```

```sql
-- 查看主从延迟
SHOW SLAVE STATUS\G
-- 关注字段：Seconds_Behind_Master, Relay_Log_Pos, Exec_Master_Log_Pos
```

## 最佳实践与踩坑记录

### 最佳实践

1. 主键用自增 BIGINT 或有序 ID，避免随机主键导致 B+ 树页分裂
2. 联合索引遵循最左前缀，先等值后范围列
3. 事务尽量短，避免长事务拖慢 Undo 回收和锁持有
4. 生产开启 innodb_flush_log_at_trx_commit=1 + sync_binlog=1，保证不丢数据
5. 大表加索引/改结构用在线 DDL（pt-online-schema-change / gh-ost），避免锁表
6. 读写分离时对「写后立即读」的关键路径强制走主库
7. 慢查询开 slow_query_log，配合 EXPLAIN 持续优化

### 踩坑记录

```text
坑 1：长事务导致 Undo 无限膨胀
结论：Undo 表空间暴涨，甚至撑爆磁盘。
原因：长事务未提交，其 undo 版本链被 MVCC 持续引用，purge 无法回收。
解法：监控长事务，缩短事务，及时提交/回滚。

坑 2：隐式类型转换导致索引失效
结论：查询突然变全表扫描，性能暴跌。
原因：WHERE varchar_col = 123 触发列类型转换，无法走索引。
解法：保持比较两侧类型一致，或用显式 CAST。

坑 3：读从库读到「刚写入但未同步」的数据
结论：用户下单后立刻查不到订单，报「数据丢失」。
原因：异步复制存在延迟，写后立即读从库读不到新数据。
解法：写后读关键路径强制走主库，或半同步复制 + 延迟监控。

坑 4：大表直接 ALTER TABLE 导致锁表
结论：线上业务长时间阻塞，甚至服务不可用。
原因：MySQL 部分 DDL 会锁表，大表执行耗时长。
解法：用 gh-ost / pt-online-schema-change 在线改表，或低峰期操作。

坑 5：随机 UUID 做主键导致写入性能下降
结论：插入变慢，页分裂频繁，索引碎片化。
原因：随机主键插入位置随机，B+ 树频繁分裂。
解法：用自增/有序 ID 做主键，UUID 存普通列或做二级索引。
```
