## 概述

高级 SQL 是在标准 SQL 基础之上，针对复杂分析场景的进阶语法：用递归 CTE 遍历层级结构、用 Rollup/Cube/Grouping Sets 一次查询产出多粒度汇总、用 Pivot 做行列转换、用执行计划定位性能瓶颈。这些能力在 Hive、Spark SQL、ClickHouse、PostgreSQL 中都有实现（方言略有差异），是数仓分析与报表开发的必修技能。

```text
高级 SQL 的核心能力：
1. Recursive CTE —— 自引用展开树/图/层级，替代传统存储过程的递归
2. Rollup —— 按分组键的「前缀」逐级上卷（a,b -> a -> 总计）
3. Cube —— 分组键所有子集的全组合聚合，产出多维立方体
4. Grouping Sets —— 显式指定要聚合的分组组合，最灵活可控
5. Pivot —— 行转列（长表转宽表），报表透视的标配
6. 执行计划 —— 看懂优化器如何执行查询，调优 SQL 的入口
```

```sql
-- 示例表：销售明细
CREATE TABLE sales (
    region   STRING,   -- 区域
    product  STRING,   -- 品类
    month    STRING,   -- 月份
    amount   DECIMAL(10, 2)
);
```

## Recursive CTE 递归查询

递归 CTE 用 WITH RECURSIVE 定义，由「种子查询（起点）+ UNION ALL 递归查询（自引用）」两部分组成，引擎反复执行递归部分直到不再产生新行。它把「层级展开」从应用程序/存储过程搬进 SQL，用于组织树、商品类目树、物料清单（BOM）、图的最短路径等场景。

```text
递归 CTE 要点：
1. 结构 —— 种子查询 UNION ALL 递归查询，递归部分必须引用 CTE 自身
2. 终止 —— 必须有终止条件，否则无限递归（引擎通常有最大递归深度保护）
3. UNION ALL —— 递归 CTE 必须用 UNION ALL（UNION 去重会破坏递归语义）
4. 深度控制 —— 自增 level 列既记录层级，也可作终止条件
```

```sql
-- 展开员工组织树：从 CEO 逐层向下找所有下属
WITH RECURSIVE org_tree AS (
    -- 种子：顶层（无上级）
    SELECT id, name, manager_id, 1 AS level
    FROM employees
    WHERE manager_id IS NULL
    UNION ALL
    -- 递归：找当前层每个人的直接下属
    SELECT e.id, e.name, e.manager_id, t.level + 1
    FROM employees e
    INNER JOIN org_tree t ON e.manager_id = t.id
    WHERE t.level < 10          -- 深度保护，防死循环
)
SELECT id, name, level FROM org_tree ORDER BY level, id;
```

```sql
-- 商品类目树：从「手机」类目向下展开所有子类目
WITH RECURSIVE cat_tree AS (
    SELECT id, name, parent_id, 0 AS depth
    FROM category
    WHERE name = '手机'
    UNION ALL
    SELECT c.id, c.name, c.parent_id, t.depth + 1
    FROM category c
    INNER JOIN cat_tree t ON c.parent_id = t.id
)
SELECT id, name, depth FROM cat_tree;
```

## Rollup 上卷

ROLLUP 在 GROUP BY 基础上，额外产出「按分组键前缀」的逐级小计和总计行。例如 GROUP BY ROLLUP(a, b) 会产出 (a,b)、(a)、(总计) 三组结果，最后一行对全表做总计。它把「多个 UNION ALL 的聚合查询」压缩成一次扫描，适合报表的分级小计（区域 -> 城市 -> 总计）。

```text
Rollup 要点：
1. 前缀上卷 —— GROUP BY ROLLUP(a,b,c) 产出 (a,b,c)/(a,b)/(a)/() 四级
2. 总计行 —— 分组键全部为 NULL 的那行是总计（用 GROUPING 区分真实 NULL）
3. 一次扫描 —— 相比手工 UNION ALL 多个聚合，只扫一次表，性能好
4. 顺序敏感 —— 上卷顺序与列顺序强相关，先粗后细的层级要写对
```

```sql
-- 区域 x 品类销售额，并自动产出「区域小计」和「总计」行
SELECT region, product, SUM(amount) AS total
FROM sales
GROUP BY ROLLUP(region, product);

-- 等价的手写 UNION ALL（对比理解 Rollup 做了什么）
SELECT region, product, SUM(amount) FROM sales GROUP BY region, product
UNION ALL
SELECT region, NULL,     SUM(amount) FROM sales GROUP BY region
UNION ALL
SELECT NULL,   NULL,     SUM(amount) FROM sales;
```

## Cube 多维聚合

CUBE 产出分组键的「所有子集组合」的聚合结果，是完整的多维立方体。GROUP BY CUBE(a, b) 产出 (a,b)/(a)/(b)/() 四组——比 Rollup 多了 (b) 这种「跳过前缀」的组合。它对应 OLAP 里的多维分析，代价是结果行数按 2^n 增长，维度多时结果爆炸，需谨慎使用。

```text
Cube 要点：
1. 全子集 —— n 个分组键产出 2^n 组聚合结果
2. 维度爆炸 —— 维度 > 5 时结果量巨大，慎用或改 Grouping Sets 按需裁剪
3. 多维分析 —— 任意维度切片/上卷都能从结果里取到
4. GROUPING —— 用 GROUPING(col) 区分「上卷产生的 NULL」与「真实 NULL」
```

```sql
-- 区域 x 品类 x 月份 的全组合汇总
SELECT region, product, month, SUM(amount) AS total
FROM sales
GROUP BY CUBE(region, product, month);

-- 用 GROUPING 函数标记哪些列被上卷（1 表示该列被聚合折叠）
SELECT region, product, month, SUM(amount) AS total,
       GROUPING(region)  AS g_region,
       GROUPING(product) AS g_product,
       GROUPING(month)   AS g_month
FROM sales
GROUP BY CUBE(region, product, month);
```

## Grouping Sets 分组集合

GROUPING SETS 显式列出「要产出哪些分组」，是 Rollup/Cube 的通用超集——Rollup 和 Cube 都是 Grouping Sets 的语法糖。它既不强制前缀上卷（比 Rollup 灵活），也不会全组合爆炸（比 Cube 可控），是工程上最推荐的多粒度聚合写法。

```text
Grouping Sets 要点：
1. 显式指定 —— 括号里列清楚每个分组维度，产出完全可控
2. 等价关系 —— ROLLUP(a,b) = GROUPING SETS((a,b),(a),())；CUBE(a,b) = GROUPING SETS((a,b),(a),(b),())
3. 空组 —— () 表示全表总计
4. 性能 —— 一次扫描产出多组，远优于多次 GROUP BY 再 UNION ALL
```

```sql
-- 只产出需要的三种分组：区域x品类、区域、总计
SELECT region, product, SUM(amount) AS total
FROM sales
GROUP BY GROUPING SETS ((region, product), (region), ());

-- 等价于 ROLLUP(region, product)
SELECT region, product, SUM(amount) AS total
FROM sales
GROUP BY GROUPING SETS ((region, product), (region), ());
```

## Pivot 行列转换

Pivot 把「长表」里的某一列取值转成「宽表」的多个列（行转列），是报表透视的标准操作。标准 SQL 没有 PIVOT 关键字（Spark SQL、Oracle、SQL Server 有），在 Hive/MySQL 里通常用「CASE WHEN + GROUP BY」或「条件聚合」实现。Unpivot 是反向操作（列转行）。

```text
Pivot 要点：
1. 行转列 —— 分组键留作行，被透视列的每个取值变成一列，度量值做聚合
2. 朴素实现 —— 条件聚合 SUM(CASE WHEN col='x' THEN val END) 是通用写法
3. 动态列 —— 取值数量不确定时需动态拼 SQL（Spark 的 pivot 支持动态）
4. Unpivot —— 列转行，宽表拆回长表，用 UNION ALL 或 UNPIVOT
```

```sql
-- 把「区域 x 品类」长表转成「区域一行、品类一列」的宽表（CASE 写法）
SELECT region,
       SUM(CASE WHEN product = '手机' THEN amount ELSE 0 END) AS 手机,
       SUM(CASE WHEN product = '电脑' THEN amount ELSE 0 END) AS 电脑,
       SUM(CASE WHEN product = '平板' THEN amount ELSE 0 END) AS 平板
FROM sales
GROUP BY region;

-- Spark SQL 原生 PIVOT 写法（方言）
SELECT * FROM (
    SELECT region, product, amount FROM sales
) PIVOT (
    SUM(amount) FOR product IN ('手机', '电脑', '平板')
);
```

## 执行计划

执行计划（EXPLAIN）展示查询优化器如何把 SQL 翻译成物理执行步骤：扫描方式（全表/索引）、JOIN 算法（hash/nested-loop）、是否下推过滤、是否发生 shuffle 等。读懂执行计划是 SQL 调优的核心——先看计划，再谈优化，避免盲目加索引、盲目改 SQL。

```text
执行计划要点：
1. 看什么 —— 扫描类型、JOIN 顺序与算法、谓词下推、shuffle/排序节点
2. 关键信号 —— 全表扫描（大表）、笛卡尔积、类型隐式转换、无谓 shuffle
3. 引擎差异 —— MySQL 用 EXPLAIN、PostgreSQL 用 EXPLAIN ANALYZE、Spark 用 explain()
4. 先 ANALYZE —— EXPLAIN ANALYZE 会真正执行并给出实际耗时/行数，比估算更准
```

```sql
-- MySQL：查看执行计划
EXPLAIN SELECT o.order_id, u.name
FROM orders o
JOIN users u ON o.user_id = u.user_id
WHERE o.amount > 100;

-- PostgreSQL：真正执行并输出实际统计
EXPLAIN ANALYZE
SELECT region, SUM(amount) FROM sales GROUP BY region;
```

```text
MySQL EXPLAIN 关键列解读：
type    —— 访问类型，从好到差：const > eq_ref > ref > range > index > ALL
           出现 ALL（全表扫描）且行数大时，优先考虑加索引
key     —— 实际用到的索引，为 NULL 表示没走索引
rows    —— 估算扫描行数，越大越慢
Extra   —— Using filesort（额外排序）/ Using temporary（临时表）都是待优化信号
```

## 应用场景实战

### 场景一：一次性产出区域报表的多级小计

```sql
-- 报表要求：区域小计 + 品类小计 + 总计，一张查询全出来
SELECT region, product, SUM(amount) AS total,
       GROUPING(region)  AS g_region,
       GROUPING(product) AS g_product
FROM sales
WHERE month = '2024-08'
GROUP BY GROUPING SETS ((region, product), (region), (product), ())
ORDER BY g_region, g_product, total DESC;
```

### 场景二：展开商品类目树并统计每个类目（含子类目）的销量

```sql
-- 先递归展开类目树，再关联销售明细，按「祖先类目」聚合
WITH RECURSIVE cat_tree AS (
    SELECT id, name, parent_id, id AS root_id
    FROM category
    UNION ALL
    SELECT c.id, c.name, c.parent_id, t.root_id
    FROM category c
    INNER JOIN cat_tree t ON c.parent_id = t.id
)
SELECT ct.root_id, c2.name AS root_name, SUM(s.amount) AS total_sales
FROM cat_tree ct
JOIN category c2 ON ct.root_id = c2.id
JOIN sales s ON s.product = ct.name
GROUP BY ct.root_id, c2.name
ORDER BY total_sales DESC;
```

## 最佳实践与踩坑记录

### 最佳实践

1. 多粒度汇总优先用 GROUPING SETS，比 Cube 可控、比 Rollup 灵活
2. 递归 CTE 务必写死递归深度上限，防止数据异常导致死循环
3. 用 GROUPING(col) 区分上卷 NULL 与真实 NULL，否则口径混乱
4. 报表透视用条件聚合（CASE WHEN）实现 Pivot，跨引擎通用
5. 调优前先 EXPLAIN，用执行计划说话，不凭感觉改 SQL
6. Cube 维度控制在 4 个以内，超出用 Grouping Sets 按需裁剪
7. 大表聚合尽量让引擎一次扫描产出多组（Rollup/Cube/Sets），避免多次 UNION ALL

### 踩坑记录

```text
坑 1：递归 CTE 用 UNION 而非 UNION ALL
结论：递归报错或结果不完整。
原因：UNION 去重会破坏递归迭代，且部分引擎直接禁止。
解法：递归 CTE 必须用 UNION ALL 连接种子与递归部分。

坑 2：Cube 维度过多导致结果爆炸
结论：5 个维度产出 32 组结果，10 个维度 1024 组，查询超时甚至 OOM。
原因：Cube 结果按 2^n 增长，维度一多量级失控。
解法：改用 Grouping Sets 只保留需要的分组组合。

坑 3：上卷行与真实 NULL 混淆
结论：总计行和「region 本身为 NULL 的行」混在一起，报表统计出错。
原因：上卷产生的分组键 NULL 与数据里真实的 NULL 无法靠肉眼区分。
解法：用 GROUPING(col) 标记，或对 NULL 做 COALESCE 兜底。

坑 4：只看 EXPLAIN 不看 ANALYZE 导致误判
结论：估算行数与实际偏差大，调优方向跑偏。
原因：EXPLAIN 是优化器估算，统计信息过期时与实际执行差异巨大。
解法：用 EXPLAIN ANALYZE 拿真实耗时/行数，并定期更新统计信息。

坑 5：Pivot 时对 NULL 不做兜底导致列缺值
结论：某区域某品类无销售时，透视列直接为 NULL，下游算占比出错。
原因：CASE WHEN 未命中时返回 NULL，而非 0。
解法：条件聚合用 ELSE 0 兜底，或外层 COALESCE(col, 0)。
```
