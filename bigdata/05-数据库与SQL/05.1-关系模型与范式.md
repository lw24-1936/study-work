## 概述

关系模型（Relational Model）由 E.F. Codd 于 1970 年提出，把数据组织成「表（关系）」，每行是元组、每列是属性，通过主键唯一标识行、通过外键建立表间关联。范式（Normal Form）是一套消除数据冗余和更新异常的规范化规则，反范式则是为查询性能有目的地「加回冗余」。主外键和约束是关系模型落地的机制——它们共同决定了数据库设计的正确性与质量。

```text
关系模型与范式的核心概念：
1. 关系模型 —— 表/元组/属性/主键/外键，用集合和关系代数描述
2. 范式     —— 1NF→2NF→3NF→BCNF，逐步消除冗余和异常
3. 反范式   —— 为性能引入冗余，数仓常用
4. 主外键   —— 主键唯一标识，外键建立关联和引用完整性
5. 约束     —— 主键/外键/唯一/非空/检查/默认，保证数据合法
```

```sql
-- 关系模型的落地：一张表就是一个「关系」
CREATE TABLE student (
    student_id   INT,          -- 属性（列）
    name         VARCHAR(50),
    age          INT,
    class_id     INT
);
-- 一行 = 一个元组；student_id 唯一标识一行（主键）
```

## 关系模型

关系模型用「关系（表）」表示实体和联系，理论基础是关系代数（选择、投影、连接、并、差、笛卡尔积）和关系演算。它强调数据的逻辑结构独立于物理存储——用户看到的是表，不必关心底层如何存。关系模型三大完整性：实体完整性（主键非空唯一）、参照完整性（外键引用存在的主键）、用户定义完整性（业务约束）。

```text
关系模型要点：
1. 表 = 关系，行 = 元组，列 = 属性
2. 关系代数 —— 选择(σ)/投影(π)/连接(⋈)/并/差/笛卡尔积
3. 完整性 —— 实体完整性、参照完整性、用户定义完整性
4. 逻辑独立 —— 屏蔽物理存储细节
```

```sql
-- 关系代数在 SQL 里的对应
-- 选择 σ（WHERE）、投影 π（SELECT 列）、连接 ⋈（JOIN）
SELECT s.name, c.class_name          -- 投影
FROM student s
JOIN class c ON s.class_id = c.class_id   -- 连接
WHERE s.age >= 18;                   -- 选择
```

## 范式

范式（Normal Form）是消除数据冗余、避免更新/插入/删除异常的规范化规则，从低到高依次是 1NF、2NF、3NF、BCNF、4NF、5NF。1NF 要求属性原子（列不可再分）；2NF 要求非主属性完全依赖主键（消除部分依赖）；3NF 要求非主属性不传递依赖主键（消除传递依赖）；BCNF 则要求每个决定因素都是候选键。业务库通常设计到 3NF/BCNF。

```text
范式递进关系：
1. 1NF —— 列原子化，不存「数组/集合」在一个字段里
2. 2NF —— 非主属性完全依赖主键，消除部分依赖（复合主键的坑）
3. 3NF —— 非主属性不依赖其他非主属性，消除传递依赖
4. BCNF —— 所有决定因素都是候选键，3NF 的加强
5. 目标 —— 业务库到 3NF/BCNF，减少冗余和异常
```

```sql
-- 反例：不满足 2NF（非主属性只依赖部分复合主键）
CREATE TABLE order_item_bad (
    order_id   INT,
    product_id INT,
    product_name VARCHAR(50),   -- 只依赖 product_id，与 order_id 无关 → 部分依赖
    quantity   INT,
    PRIMARY KEY (order_id, product_id)
);

-- 规范化到 2NF/3NF：拆成订单明细 + 商品表
CREATE TABLE product (
    product_id   INT PRIMARY KEY,
    product_name VARCHAR(50)
);
CREATE TABLE order_item (
    order_id   INT,
    product_id INT,
    quantity   INT,
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (product_id) REFERENCES product(product_id)
);

-- 反例：不满足 3NF（传递依赖）
CREATE TABLE student_bad (
    student_id INT PRIMARY KEY,
    class_id   INT,
    class_name VARCHAR(50),   -- 依赖 class_id，而 class_id 依赖 student_id → 传递依赖
    name       VARCHAR(50)
);
```

## 反范式

反范式（Denormalization）是「有意引入冗余」以换取查询性能：把经常一起查询的表合并、预存计算结果、冗余字段减少 JOIN。它牺牲写性能（冗余要同步更新）和存储，换取读性能。业务库尽量规范化保证一致性，数仓/OLAP 则大量反范式（宽表、预聚合），因为分析场景读远多于写、且能容忍最终一致。

```text
反范式要点：
1. 目的 —— 减少 JOIN、减少计算，加速查询
2. 手段 —— 冗余列、预聚合、宽表、合并表
3. 代价 —— 冗余需同步，写放大，一致性难保证
4. 场景 —— 数仓宽表、报表表、缓存、OLAP
```

```sql
-- 规范化：用户和订单分开，查订单要 JOIN 用户
SELECT o.order_id, u.name, o.amount
FROM orders o JOIN users u ON o.user_id = u.user_id;

-- 反范式：订单宽表冗余用户信息，免 JOIN
CREATE TABLE orders_wide AS
SELECT o.order_id, o.user_id, u.name, u.city, o.amount
FROM orders o JOIN users u ON o.user_id = u.user_id;
-- 查订单直接读宽表，无需 JOIN
SELECT order_id, name, amount FROM orders_wide;
```

## 主外键

主键（Primary Key）唯一标识一行，要求非空且唯一，一个表只能有一个（可以是复合主键）。外键（Foreign Key）引用另一张表的主键，建立表间关联并保证参照完整性——外键值必须存在于被引用表的主键中（或为 NULL）。主键通常用自增整数或 UUID（代理键），外键用于表达「订单属于哪个用户」「明细属于哪个订单」这类关系。

```text
主外键要点：
1. 主键 —— 非空 + 唯一，唯一标识一行
2. 外键 —— 引用别表主键，保证参照完整性
3. 代理键 vs 业务键 —— 数仓常用无业务含义的代理键做主键
4. 级联 —— ON DELETE CASCADE / SET NULL 定义删除行为
```

```sql
-- 主键与外键的完整示例
CREATE TABLE department (
    dept_id   INT PRIMARY KEY,           -- 主键
    dept_name VARCHAR(50) NOT NULL
);

CREATE TABLE employee (
    emp_id    INT PRIMARY KEY,           -- 主键
    emp_name  VARCHAR(50) NOT NULL,
    dept_id   INT,
    FOREIGN KEY (dept_id)                -- 外键引用 department
        REFERENCES department(dept_id)
        ON DELETE SET NULL               -- 部门删除时员工 dept_id 置空
);

-- 复合主键
CREATE TABLE order_item (
    order_id   INT,
    product_id INT,
    quantity   INT,
    PRIMARY KEY (order_id, product_id)   -- 复合主键
);
```

## 约束

约束（Constraint）是数据库层面对数据合法性的强制规则，在写入时自动校验，是保证数据质量的最后一道防线。常见约束：主键（非空唯一）、外键（参照完整）、唯一（UNIQUE）、非空（NOT NULL）、检查（CHECK）、默认值（DEFAULT）。约束让「脏数据」在入库时就被拦截，而不是等到查询出错才发现。

```text
约束要点：
1. NOT NULL —— 列不允许空值
2. UNIQUE —— 列值唯一（可多个 NULL）
3. CHECK —— 自定义条件校验（如 age >= 0）
4. DEFAULT —— 缺省默认值
5. 约束在写入时校验，是数据质量的防线
```

```sql
CREATE TABLE account (
    account_id INT PRIMARY KEY,
    username   VARCHAR(50) NOT NULL UNIQUE,     -- 非空 + 唯一
    email      VARCHAR(100) UNIQUE,
    age        INT CHECK (age >= 0 AND age <= 150),  -- 检查约束
    status     VARCHAR(20) DEFAULT 'active',    -- 默认值
    balance    DECIMAL(10, 2) CHECK (balance >= 0)
);

-- 违反约束的插入会被拒绝
-- INSERT INTO account (account_id, username, age)
-- VALUES (1, NULL, 20);            -- 违反 NOT NULL
-- INSERT INTO account (account_id, username, age)
-- VALUES (2, 'alice', -5);         -- 违反 CHECK
```

## 应用场景实战

### 场景一：把一个不规范的表规范化到 3NF

```sql
-- 原始表：一张表塞了学生、班级、课程、成绩，冗余严重
CREATE TABLE raw_enrollment (
    student_id   INT,
    student_name VARCHAR(50),
    class_id     INT,
    class_name   VARCHAR(50),
    course_id    INT,
    course_name  VARCHAR(50),
    score        INT
);

-- 规范化：拆成 学生、班级、课程、成绩 四张表
CREATE TABLE student (
    student_id   INT PRIMARY KEY,
    student_name VARCHAR(50),
    class_id     INT
);
CREATE TABLE class (
    class_id   INT PRIMARY KEY,
    class_name VARCHAR(50)
);
CREATE TABLE course (
    course_id   INT PRIMARY KEY,
    course_name VARCHAR(50)
);
CREATE TABLE score (
    student_id INT,
    course_id  INT,
    score      INT,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES student(student_id),
    FOREIGN KEY (course_id) REFERENCES course(course_id)
);
-- 收益：班级改名只改一处；不会出现「同一学生两处名字不一致」
```

### 场景二：为报表性能做反范式（宽表 + 预聚合）

```sql
-- 规范化的事实表 + 维度表（查询要多次 JOIN）
-- fact_order JOIN dim_user JOIN dim_product JOIN dim_date

-- 反范式：预聚合宽表，直接服务报表
CREATE TABLE ads_user_order_1d (
    dt           STRING,
    user_id      BIGINT,
    user_name    STRING,       -- 冗余用户信息
    city         STRING,       -- 冗余城市
    order_cnt    BIGINT,       -- 预聚合：订单数
    gmv          DECIMAL(18,2),-- 预聚合：成交额
    PRIMARY KEY (dt, user_id)
);
-- 报表直接 SELECT，无需 JOIN，查询亚秒级返回
```

## 最佳实践与踩坑记录

### 最佳实践

1. 业务库（OLTP）设计到 3NF/BCNF，消除冗余和更新异常
2. 数仓/OLAP 大胆反范式（宽表 + 预聚合），用冗余换查询性能
3. 主键优先用无业务含义的代理键（自增/UUID），业务键单独存
4. 外键保证参照完整性，但高并发写入场景可关闭外键改用应用层校验
5. 关键字段加 NOT NULL 和 CHECK 约束，把脏数据挡在库外
6. 规范化要适度——过度拆分导致查询 JOIN 爆炸，性能反而差

### 踩坑记录

```text
坑 1：复合主键中非主属性只依赖部分键
结论：出现部分依赖，更新时数据不一致（违反 2NF）。
原因：如订单明细表主键是 (order_id, product_id)，商品名只依赖 product_id。
解法：把只依赖部分主键的属性抽到独立的表，消除部分依赖。

坑 2：用业务字段（如手机号）当主键
结论：业务字段变更导致主键更新，关联表全部要级联改。
原因：业务键可能变化/复用，不适合做稳定主键。
解法：用无业务含义的代理键做主键，业务字段加唯一约束即可。

坑 3：外键约束导致高并发写入性能暴跌
结论：大表批量写入被外键校验拖慢。
原因：每条插入都要查被引用表校验存在性，高并发下成瓶颈。
解法：互联网高并发场景常移除外键，由应用层保证参照完整性。

坑 4：过度规范化导致查询 JOIN 爆炸
结论：一个简单查询要 JOIN 七八张表，慢且难维护。
原因：为了「纯 3NF」过度拆分，忘了查询侧的成本。
解法：读多写少时反范式冗余，或建宽表/视图屏蔽复杂 JOIN。
```
