## 概述

数据库原理是分布式存储与数据处理系统的理论根基：CAP/PACELC 告诉我们分布式系统在一致性、可用性、分区容错之间必须做取舍；分片与复制是水平扩展的两大手段；读写分离是一致性与吞吐的折中；一致性模型则定义了「读到什么」的强弱程度。理解这些原理，才能在设计分库分表、主从架构、分布式数据库和消息系统时做出正确取舍。

```text
数据库原理核心命题：
1. CAP —— 分布式系统无法同时满足一致性、可用性、分区容错，只能三选二
2. PACELC —— CAP 的精细化：分区发生时选 A 还是 C，无分区时选延迟还是一致性
3. 分片 —— 数据水平切分到多节点，解决单机容量与吞吐上限
4. 复制 —— 数据多副本冗余，解决可用性与读扩展
5. 读写分离 —— 主写从读，读吞吐扩展，代价是复制延迟
6. 一致性 —— 从强一致到最终一致的光谱，决定数据可见性语义
```

```text
分布式系统设计的基本矛盾：
数据分布（分片/复制）带来横向扩展能力
   <--->  同时带来一致性、延迟、复杂度问题
所有架构都是在这两者之间找平衡点
```

## CAP

CAP 定理（Brewer 提出，Gilbert/Lynch 证明）：一个分布式系统在「一致性（Consistency）、可用性（Availability）、分区容错（Partition Tolerance）」三者中最多同时满足两个。由于网络分区在分布式系统中不可避免（P 必须选），实际选择是「分区发生时，选一致性（CP）还是可用性（AP）」。

```text
CAP 三要素：
1. Consistency —— 一致性：所有节点同一时刻读到相同数据
2. Availability —— 可用性：每个请求都能得到（非错误的）响应
3. Partition Tolerance —— 分区容错：网络分区发生时系统仍能工作
```

```text
CAP 的实践解读：
1. P 必选 —— 网络分区无法避免，分布式系统必须容忍分区
2. CP 系统 —— 分区时牺牲可用性保证一致（HBase、ZooKeeper、etcd）
3. AP 系统 —— 分区时牺牲一致性保证可用（Cassandra、DynamoDB、多数 NoSQL）
4. CA 系统 —— 只在无分区时成立（单机数据库，如单机 MySQL）
```

## PACELC

PACELC 是 CAP 的扩展与修正，指出「分区（P）不是常态，延迟（Latency）与一致性（Consistency）的权衡才是日常」：分区发生时在 A/C 间选（PAC），无分区时在 L（低延迟）/C（一致性）间选（ELC）。它更贴近真实系统——大部分时间系统正常，此时「每次读都要强一致」还是「读副本图快」才是常见抉择。

```text
PACELC 解读：
PAC（有分区）—— 选 A（可用）还是 C（一致）
ELC（无分区，else）—— 选 L（低延迟）还是 C（强一致）
```

```text
典型系统的 PACELC 归类：
PA/EL —— 高可用优先（Cassandra：分区可用 + 正常时低延迟最终一致）
PC/EC —— 强一致优先（HBase/ZooKeeper：分区一致 + 正常时也强一致）
PA/EC —— 分区可用 + 正常时强一致（MongoDB 多数派写）
```

## 分片

分片（Sharding）把一张大表按某种规则水平切分到多个节点，每个节点存一部分数据，解决单机容量和写入吞吐的上限。分片方式有范围分片、哈希分片、一致性哈希等；分片键的选择决定数据是否均匀、查询是否跨片。分片带来跨片查询、跨片事务、数据再平衡等复杂度。

```text
分片要点：
1. 分片键 —— 决定数据如何分布，要选高基数、读写均衡的字段
2. 哈希分片 —— 按分片键哈希取模分布，均匀但范围查询需跨片
3. 范围分片 —— 按分片键区间分布，范围查询友好但易热点
4. 一致性哈希 —— 节点增减只影响局部数据，迁移量小
```

```text
分库分表（ShardingSphere/MyCat 常见做法）：
水平分表 —— 单表按 user_id % N 拆成 N 张表
水平分库 —— 拆出的表分布到多个库
垂直拆分 —— 按业务域拆库（订单库/用户库/库存库）
```

```sql
-- 分片示意：按 user_id 哈希分 4 片
-- 逻辑表 orders，物理表 orders_0 ~ orders_3
-- user_id % 4 = 0 -> orders_0，= 1 -> orders_1，依此类推
SELECT * FROM orders WHERE user_id = 1001;   -- 路由到 orders_1 (1001 % 4 = 1)
```

## 复制

复制（Replication）把数据同步成多份副本，分布到不同节点，用于容灾（单点故障不影响可用）、读扩展（多副本分散读）和数据备份。复制分同步、异步、半同步三种；主从复制（一主多从）是最常见形态，多主复制和无主复制（如 Dynamo 风格）是更复杂的形态。

```text
复制要点：
1. 同步复制 —— 主库等所有从库确认才返回，强一致但延迟高
2. 异步复制 —— 主库不等从库，延迟低但可能丢数据
3. 半同步复制 —— 主库等至少一个从库确认，折中
4. 多副本读 —— 从库分担读压力，是读写分离的基础
```

```text
主从复制 vs 多主 vs 无主：
主从 —— 单主写多从读，简单，写有单点瓶颈
多主 —— 多节点可写，需冲突解决（版本向量/CRDT）
无主 —— 客户端写多个副本，按法定人数（Quorum）读，Dynamo/Cassandra 风格
```

## 读写分离

读写分离是把写请求路由到主库、读请求路由到从库的架构模式，基于主从复制实现。它用多个从库分担读压力，提升读吞吐，代价是「复制延迟」——从库数据可能落后主库，导致「写后立即读从库读不到」的一致性问题。常见于读多写少的业务。

```text
读写分离要点：
1. 主写从读 —— 写走主库，读走从库，读可水平扩展
2. 复制延迟 —— 从库落后主库，关键读需强制走主库
3. 中间件 —— MySQL 生态用 ProxySQL/MaxScale/MyCat 做路由
4. 适用 —— 读多写少；写多或强一致读多的场景慎用
```

```text
读写分离路由策略：
1. 写请求 -> 主库
2. 普通读 -> 从库（负载均衡）
3. 关键读（事务内/写后立即读）-> 主库
4. 延迟敏感读 -> 判断主从延迟，超阈值回主库
```

## 一致性

一致性描述「分布式系统里，读操作能看到什么」的程度，从强到弱形成一个光谱：强一致（线性一致，读到最新值）、顺序一致、因果一致、最终一致（只要不再写入，最终所有副本收敛到同一值）。强一致易理解但代价高，最终一致性能好但需业务容忍短暂不一致。

```text
一致性模型光谱（强 -> 弱）：
1. 线性一致（Linearizability）—— 读总返回最新已提交值，行为像单机
2. 顺序一致 —— 所有操作按某个全局顺序，读可能读到旧值
3. 因果一致 —— 有因果关系的操作保证顺序，无关操作可乱序
4. 最终一致 —— 停止写入后最终收敛一致，期间可能读到旧值
```

```text
实现最终一致的常见手段：
1. 版本向量（Vector Clock）—— 检测并发冲突
2. 读修复（Read Repair）—— 读时发现副本不一致就修复
3. 反熵（Anti-entropy）—— 后台定期对比副本差异
4. Quorum —— 读写法定人数保证多数派一致（W + R > N）
```

## 应用场景实战

### 场景一：电商订单库的分库分表设计

```text
需求：订单表海量增长，单库写不下、查不动

方案：按 user_id 哈希分库分表
- 8 个库（db_0 ~ db_7），每库 16 张表（orders_0 ~ orders_15）
- 路由规则：库 = user_id % 8，表 = (user_id / 8) % 16
- 保证同用户订单在同库同表，用户维度查询不跨片

查询路径：
按 user_id 查 -> 精确路由到单库单表
按 order_id 查 -> 需基因法（order_id 嵌入 user_id 分片信息）或全局索引
```

```text
分片键设计关键：
1. 高频查询字段做分片键（如按 user_id 查订单）
2. 分片键低基数字段会导致数据倾斜，避免
3. 跨片查询（按非分片键查）需全局索引或基因法，复杂度高
4. 分片数提前规划，避免后期频繁扩容迁移
```

### 场景二：用户资料服务的读写分离 + 缓存

```text
架构：
写请求 -> 主库（更新后失效/更新缓存）
读请求 -> 本地缓存 -> Redis -> 从库 -> 主库（兜底）

一致性保障：
1. 更新主库后主动失效 Redis 缓存
2. 关键读（个人中心「我的资料」）走主库
3. 普通读（他人主页）走从库，容忍秒级延迟
4. 主从延迟监控告警，延迟过高时读切主库
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先判断「分区容错是否可放弃」，再谈 CAP 取舍（单机可 CA，分布式必选 CP/AP）
2. 分片键选高基数 + 高频查询字段，避免数据倾斜和跨片查询
3. 复制优先用半同步，平衡延迟与数据安全
4. 读写分离对「写后立即读」的关键路径强制走主库
5. 明确一致性要求——强一致用 CP 系统/Quorum，能容忍延迟用最终一致
6. 用版本向量/CRDT 处理多写冲突，别靠时间戳硬排
7. 分片数预留余量，用一致性哈希降低扩容迁移成本

### 踩坑记录

```text
坑 1：以为 CAP 是「三选二」就随便放弃一致性
结论：过度追求可用性导致数据错乱，业务出事故。
原因：误读 CAP，实际是「分区时选 A 还是 C」，且无分区时还有延迟/一致权衡。
解法：按 PACELC 建模，分区时选 C 还是 A 取决于业务对数据正确性的容忍度。

坑 2：分片键选低基数字段导致热点
结论：某几个分片数据/流量爆表，其余分片空闲。
原因：低基数分片键（如 status、type）无法均匀散列。
解法：选高基数字段，或加 hash 前缀/复合分片键。

坑 3：读写分离下写后立即读从库读不到
结论：用户「刚改了资料刷新看不到」，被投诉数据丢失。
原因：异步复制延迟，从库还没同步到最新数据。
解法：关键读走主库，或半同步复制 + 延迟监控 + 兜底。

坑 4：把最终一致当强一致用
结论：读到旧数据导致业务逻辑错判。
原因：没区分一致性模型，拿 AP 系统（Cassandra）当强一致库用。
解法：明确业务一致性要求，强一致场景换 CP 系统或用 Quorum 读写。

坑 5：多主复制不处理写冲突
结论：两个节点同时改同一数据，最终以「后写覆盖」丢失更新。
原因：多主/无主复制下并发写无天然仲裁，需显式冲突解决。
解法：用版本向量/LWW（Last-Write-Wins）/CRDT 显式解决冲突。
```
