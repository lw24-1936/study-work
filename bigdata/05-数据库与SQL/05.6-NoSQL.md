## 概述

NoSQL（Not Only SQL）是相对于关系型数据库的一类存储系统，为特定场景放弃 ACID 和关系模型，换取水平扩展、高性能、灵活 schema。按数据模型分四类：键值（Redis）、文档（MongoDB）、宽列（Cassandra/HBase）、图，另有专用时序数据库。NoSQL 是大数据架构里「高并发缓存、海量明细、宽表存储」的主力，与关系库互补而非替代。

```text
NoSQL 的分类与代表：
1. 键值存储 —— Redis（内存缓存/计数/分布式锁）
2. 文档存储 —— MongoDB（灵活 schema 的 JSON 文档）
3. 宽列存储 —— Cassandra / HBase（海量行、动态列、按行键分布）
4. 云托管键值 —— DynamoDB（AWS Serverless 键值/文档）
5. 时序数据库 —— InfluxDB / TimescaleDB / TDengine（指标监控）
```

```text
选型核心问题：
1. 是否需要事务/强一致？需要 -> 关系库；可容忍最终一致 -> NoSQL
2. 数据模型是固定表结构还是灵活文档/键值？
3. 写入/读取吞吐要求多高？需要水平扩展到多少节点？
4. 访问模式是点查（KV）、范围扫描（宽列）还是多维分析（OLAP）？
```

## Redis

Redis 是内存键值数据库，支持 string/list/set/zset/hash/stream 等丰富数据结构，单线程事件循环 + 内存操作带来极高吞吐（单机十万级 QPS）。它广泛用于缓存、会话、计数、排行榜、分布式锁、消息队列等场景，是大数据系统里「热数据加速」的标准组件。

```text
Redis 要点：
1. 内存存储 —— 数据在内存，持久化靠 RDB 快照 + AOF 日志
2. 丰富数据结构 —— zset 做排行榜、hash 做对象、list 做队列、string 做计数
3. 过期与淘汰 —— key 设 TTL，内存满按 LRU/LFU 策略淘汰
4. 高可用 —— 主从复制 + 哨兵（Sentinel）+ 集群（Cluster 分片）
```

```shell
# 常用命令
redis-cli SET user:1001 "alice"
redis-cli GET user:1001
redis-cli EXPIRE user:1001 3600          # 过期时间
redis-cli INCR page:view:20240814        # 原子计数
redis-cli ZADD leaderboard 100 alice 90 bob
redis-cli ZREVRANGE leaderboard 0 9      # 排行榜 top10
```

```python
import redis

r = redis.Redis(host='localhost', port=6379, db=0)
r.set('user:1001', 'alice', ex=3600)
r.incr('page:view:20240814')
# 分布式锁（SET NX EX）
locked = r.set('lock:order:1', 'token', nx=True, ex=30)
```

## MongoDB

MongoDB 是文档数据库，以 BSON（二进制 JSON）存储灵活 schema 的文档，支持嵌套文档和数组，适合字段多变的场景（用户画像、商品、日志）。它通过副本集（Replica Set）做高可用、分片（Sharding）做水平扩展，用二级索引和聚合管道做查询分析。

```text
MongoDB 要点：
1. 文档模型 —— 集合（collection）+ 文档（document），schema 灵活可嵌套
2. 副本集 —— 一主多从，主写从读，自动故障转移
3. 分片 —— 按 shard key 把数据分布到多个分片，水平扩展
4. 聚合管道 —— $match/$group/$lookup 等 stage 做类 SQL 的聚合
```

```javascript
// 插入文档（Mongo Shell 语法）
db.users.insertOne({
    user_id: 1001,
    name: "alice",
    city: "北京",
    tags: ["vip", "frequent"],
    profile: { age: 28, gender: "F" }
});

// 聚合管道：按城市统计用户数
db.users.aggregate([
    { $match: { "profile.age": { $gte: 18 } } },
    { $group: { _id: "$city", cnt: { $sum: 1 } } },
    { $sort: { cnt: -1 } }
]);
```

## Cassandra

Apache Cassandra 是分布式宽列数据库，采用「无中心 + 一致性哈希」的 P2P 架构，所有节点对等，数据按分区键（Partition Key）哈希分布到各节点并多副本存储。它以「写入快、线性扩展、无单点」著称，牺牲强一致换可用性（AP 系统），适合海量写入、多数据中心、对可用性要求极高的场景（如消息、时序、用户行为）。

```text
Cassandra 要点：
1. 无中心 —— 所有节点对等，无 master，任何节点都能读写
2. 一致性哈希 —— 分区键哈希决定数据落在哪个节点（Token Ring）
3. 可调一致性 —— 读写时指定 QUORUM/ONE/ALL 等一致性级别
4. LSM-Tree —— 写先到内存 Memtable + 提交日志，再刷成 SSTable
```

```sql
-- Cassandra CQL：建表与查询
CREATE KEYSPACE demo WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 3};

CREATE TABLE demo.user_events (
    user_id    BIGINT,
    event_time TIMESTAMP,
    event_name TEXT,
    PRIMARY KEY (user_id, event_time)
) WITH CLUSTERING ORDER BY (event_time DESC);

-- 按用户查询最近事件（分区键点查 + 聚簇键范围）
SELECT * FROM demo.user_events
WHERE user_id = 1001 AND event_time > '2024-08-01';
```

## HBase

Apache HBase 是构建在 HDFS 之上的分布式宽列数据库，面向海量行的随机读写与范围扫描，是 Hadoop 生态的 NoSQL 主力。数据按行键（RowKey）字典序排序、按 Region 切分分布，列动态可扩展且按列族（Column Family）组织。它牺牲了 SQL 和事务，换取对十亿行规模表的高吞吐点查与扫描。

```text
HBase 要点：
1. 行键排序 —— 数据按 RowKey 字典序存储，RowKey 设计决定访问性能
2. Region —— 表按 RowKey 范围切分成 Region，分布到 RegionServer
3. 列族 —— 列按列族组织，列族下可动态加列（稀疏宽表）
4. LSM 架构 —— 写 MemStore -> HFile（HDFS），读合并内存与磁盘
```

```shell
# HBase Shell 操作
create 'users', 'info'
put 'users', '1001', 'info:name', 'alice'
put 'users', '1001', 'info:city', 'beijing'
get 'users', '1001'
scan 'users', {STARTROW => '1000', ENDROW => '2000'}
```

```java
// HBase Java API：写一行
Configuration conf = HBaseConfiguration.create();
try (Connection conn = ConnectionFactory.createConnection(conf);
     Table table = conn.getTable(TableName.valueOf("users"))) {
    Put put = new Put(Bytes.toBytes("1001"));
    put.addColumn(Bytes.toBytes("info"), Bytes.toBytes("name"), Bytes.toBytes("alice"));
    table.put(put);
}
```

## DynamoDB

Amazon DynamoDB 是 AWS 的 Serverless 键值/文档数据库，由《Dynamo》论文（一致性哈希、向量时钟、Hinted Handoff）的工程化而来。它完全托管、按吞吐或按需计费，主键分分区键和排序键（可选），支持全局二级索引（GSI）和 DynamoDB Streams（变更流，常用于 CDC 和事件驱动）。

```text
DynamoDB 要点：
1. Serverless —— 无需管理服务器，自动扩缩，按需计费
2. 主键 —— 分区键（必选，哈希分布）+ 排序键（可选，同分区内排序）
3. GSI —— 全局二级索引，支持按非主键属性查询
4. Streams —— 变更流，触发 Lambda 或做 CDC 同步
```

```json
// DynamoDB 表定义（分区键 + 排序键）
{
  "TableName": "orders",
  "KeySchema": [
    { "AttributeName": "user_id", "KeyType": "HASH" },
    { "AttributeName": "order_id", "KeyType": "RANGE" }
  ],
  "AttributeDefinitions": [
    { "AttributeName": "user_id", "AttributeType": "N" },
    { "AttributeName": "order_id", "AttributeType": "S" }
  ]
}
```

## 时序数据库

时序数据库专为「带时间戳的指标数据」优化：按时间分片、列式压缩、自动降采样（Downsample）、时间范围聚合。代表有 InfluxDB、TimescaleDB（PostgreSQL 扩展）、TDengine。它们解决监控指标、IoT 传感器、金融行情、APM 等「海量时间序列」的写入与查询问题，比通用数据库压缩比高一个量级。

```text
时序数据库要点：
1. 时间分片 —— 数据按时间区间分片，旧数据冷热分层
2. 高压缩 —— 时间戳差分 + 数值编码，压缩比可达 10:1 以上
3. 降采样 —— 自动按分钟/小时/天聚合，保留多粒度
4. 标签索引 —— 按 tag（维度标签）过滤，按时间聚合
```

```sql
-- InfluxDB（InfluxQL）
SELECT MEAN(cpu_usage)
FROM metrics
WHERE host = 'web-01' AND time > now() - 1h
GROUP BY time(1m);

-- TimescaleDB（PostgreSQL 扩展，用超表）
CREATE TABLE metrics (time TIMESTAMPTZ NOT NULL, host TEXT, cpu DOUBLE PRECISION);
SELECT create_hypertable('metrics', 'time');

SELECT time_bucket('1 minute', time) AS bucket, AVG(cpu)
FROM metrics
WHERE host = 'web-01' AND time > now() - interval '1 hour'
GROUP BY bucket ORDER BY bucket;
```

## 应用场景实战

### 场景一：Redis 做热点数据缓存 + 排行榜

```python
import redis

r = redis.Redis(host='localhost', port=6379)

# 1. 缓存用户信息（TTL 1 小时），命中则跳过 DB
def get_user(user_id):
    cached = r.get(f"user:{user_id}")
    if cached:
        return cached
    # 模拟查数据库
    name = query_db(user_id)
    r.set(f"user:{user_id}", name, ex=3600)
    return name

# 2. 实时排行榜（zset）
def record_score(user_id, score):
    r.zadd("leaderboard", {user_id: score})

def top10():
    return r.zrevrange("leaderboard", 0, 9, withscores=True)
```

### 场景二：HBase 做海量用户行为明细存储

```shell
# 表设计：RowKey = user_id 反转 + 时间戳，同用户行为聚在一起，倒序扫描最新
create 'user_behavior', 'b'
put 'user_behavior', '0000001001_20240814120000', 'b:event', 'purchase'

```

## 最佳实践与踩坑记录

### 最佳实践

1. Redis key 设计带业务前缀和过期时间，避免内存无限增长
2. Redis 用集群模式分片，别单机扛所有热数据
3. MongoDB 分片键选读写都均衡的字段，避免热点分片
4. HBase/Cassandra 的 RowKey/分区键设计决定一切，先设计访问模式再设计键
5. 缓存注意穿透/击穿/雪崩（空值兜底、互斥锁、随机过期）
6. 时序数据按时间分片 + 降采样，控制保留周期
7. NoSQL 多牺牲强一致，业务上要能接受最终一致，别当关系库用

### 踩坑记录

```text
坑 1：Redis 热 key 导致单分片被打爆
结论：某热门 key 的请求集中到单个分片，延迟飙升。
原因：集群模式下同 key 永远落同一分片，热点无法分散。
解法：热点 key 加随机后缀打散，或用本地缓存 + 多级缓存。

坑 2：缓存雪崩
结论：大量 key 同时过期，请求瞬间全打到数据库，压垮 DB。
原因：为一批 key 设了相同 TTL，同一时刻集中失效。
解法：TTL 加随机抖动，或热点数据永不过期 + 异步刷新。

坑 3：HBase RowKey 设计成递增时间戳导致热点
结论：写入集中在单个 Region，吞吐上不去，出现 Region 热点。
原因：递增 RowKey 让新数据永远写同一个 Region。
解法：RowKey 前置反转/散列（如 user_id 反转或加 hash 前缀）。

坑 4：MongoDB 分片键选低基数字段
结论：数据分布不均，某分片巨大，查询和存储都倾斜。
原因：低基数分片键无法均匀散列，chunk 无法均衡。
解法：选高基数 + 查询常用字段做分片键，或用哈希分片键。

坑 5：把 NoSQL 当关系库用强求事务
结论：跨分区事务要么不支持要么性能极差，逻辑复杂易错。
原因：NoSQL 大多牺牲 ACID 换扩展性，跨分区事务代价高。
解法：单分区内原子操作可用，跨分区一致性交给应用层或换关系库。
```
