## 概述

OLAP（联机分析处理）引擎是面向大规模数据多维分析、复杂聚合、即席查询的专用系统，解决的是「对海量数据做秒级交互式分析」的问题。它们与 OLTP（MySQL/PostgreSQL）的差异在于：面向列式存储、向量化执行、分布式并行、预聚合/物化，牺牲单条写入延迟换取海量扫描的吞吐。主流分开源（ClickHouse、StarRocks/Doris、Druid、Pinot、DuckDB）和云原生（Snowflake、BigQuery、Redshift）两大阵营。

```text
OLAP 引擎选型维度：
1. 存储模型 —— 列式为主，部分支持行列混合（StarRocks/Doris 主键模型）
2. 查询延迟 —— 亚秒到秒级，适合交互式看板、即席分析
3. 数据规模 —— 单机（DuckDB）到千亿行分布式（ClickHouse/Doris）
4. 更新能力 —— 从纯追加（Druid 段不可变）到支持 UPSERT（StarRocks/Doris 主键模型）
5. 部署形态 —— 自建开源 vs 云托管 Serverless
```

```text
引擎速览：
ClickHouse —— 单机性能极致的列存，MergeTree 家族，适合日志/明细分析
StarRocks —— 对标 Doris，MPP 架构，主键模型支持实时更新，实时数仓常用
Doris    —— Apache 顶级项目，StarRocks 的前身分支，物化视图强
Druid    —— 预聚合 + 时序索引，专为实时 OLAP 与高并发查询设计
Pinot    —— LinkedIn 开源，与 Druid 同源，支持离线+实时双摄取
DuckDB   —— 进程内嵌入式 OLAP，单机分析「SQLite 之于 OLTP」
Snowflake/BigQuery/Redshift —— 云原生数仓，存算分离 + Serverless
```

## ClickHouse

ClickHouse 是俄罗斯 Yandex 开源的列式 OLAP 数据库，以「单机性能极致」著称——向量化执行、MergeTree 引擎族、数据压缩、主键稀疏索引。它面向「大批量追加写入 + 海量扫描聚合」的只读分析场景，是日志分析、用户行为明细、监控指标存储的热门选择。

```text
ClickHouse 要点：
1. MergeTree —— 核心引擎族，按主键排序 + 分区 + 后台合并（Merge）
2. 列式 + 向量化 —— 按列压缩存储，SIMD 向量化计算，扫描快
3. 稀疏索引 —— 主键每 8192 行一个标记，索引小、适合大范围扫描
4. 写入模型 —— 适合批量追加，频繁单条 UPDATE/DELETE 不擅长（用 Mutation）
```

```sql
-- 建表：用户行为明细
CREATE TABLE events (
    event_date  Date,
    user_id     UInt64,
    event_name  String,
    amount      Float64
) ENGINE = MergeTree
PARTITION BY toYYYYMM(event_date)
ORDER BY (event_date, user_id);

-- 海量扫描聚合：各事件每日统计
SELECT event_name, count(), sum(amount)
FROM events
WHERE event_date BETWEEN '2024-08-01' AND '2024-08-31'
GROUP BY event_name
ORDER BY count() DESC;
```

## StarRocks

StarRocks 是鼎石科技主导的 MPP 分析型数据库（源自 Doris 分支），面向实时数仓场景。它支持主键模型（Primary Key Table）实现实时 UPSERT，配合明细/聚合/更新/主键四种表模型和物化视图，能同时服务高并发点查和大规模聚合。它是当前国内实时数仓和指标平台最常用的 OLAP 引擎之一。

```text
StarRocks 要点：
1. MPP 架构 —— FE（前端：元数据/查询规划）+ BE（后端：存储/计算）
2. 主键模型 —— 支持实时 UPSERT/DELETE，解决实时数仓的更新难题
3. 物化视图 —— 异步物化视图透明加速聚合查询
4. 存算分离 —— 新版本支持存算分离，存储下沉到对象存储
```

```sql
-- 主键模型表：实时订单指标，按主键 upsert
CREATE TABLE order_agg (
    order_date  DATE,
    user_id     BIGINT,
    order_cnt   BIGINT SUM,
    gmv         DECIMAL(20,2) SUM
) ENGINE = OLAP
PRIMARY KEY (order_date, user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 16;

-- 实时聚合查询
SELECT order_date, SUM(order_cnt) AS total_cnt, SUM(gmv) AS total_gmv
FROM order_agg
WHERE order_date = '2024-08-14'
GROUP BY order_date;
```

## Doris

Apache Doris 是百度开源后捐赠给 Apache 的 MPP 分析型数据库，是 StarRocks 的前身同源项目。它同样采用 FE/BE 架构，支持多种表模型、物化视图、Colocation Join（同分片表本地 Join）等，以易用性和丰富的物化视图著称，适合报表、多维分析、即席查询。

```text
Doris 要点：
1. 表模型 —— Duplicate（明细）/ Aggregate（聚合）/ Unique（主键更新）
2. Colocation Join —— 分片键一致的表本地 Join，避免数据 shuffle
3. 物化视图 —— Rollup 物化视图，查询自动路由到最优视图
4. 兼容性 —— 高度兼容 MySQL 协议，BI 工具直连
```

```sql
-- 聚合模型表：自动按维度聚合
CREATE TABLE sales_agg (
    region   VARCHAR(32),
    product  VARCHAR(32),
    amount   DECIMAL(20,2) SUM
) ENGINE = OLAP
AGGREGATE KEY (region, product)
DISTRIBUTED BY HASH(region) BUCKETS 8;

-- 查询自动聚合
SELECT region, SUM(amount) FROM sales_agg GROUP BY region;
```

## Druid

Apache Druid 是为「实时摄取 + 预聚合 + 高并发低延迟查询」设计的分布式时序 OLAP 数据库。它把数据按时间分段（Segment），对指定维度做预聚合（rollup），用倒排索引（Bitmap）加速过滤，查询走预聚合结果而非原始明细，因此能支撑上千 QPS 的亚秒查询。适合实时监控、用户行为分析、广告统计。

```text
Druid 要点：
1. Segment —— 按时间分片，段内不可变，新数据新段，后台合并
2. 预聚合 —— 摄入时按维度 rollup，大幅减少存储与查询量
3. Bitmap 索引 —— 维度值用位图索引，过滤/AND/OR 极快
4. 架构 —— Historical（历史段）/ MiddleManager（实时摄入）/ Broker（查询路由）/ Coordinator（协调）
```

```json
// 实时摄入（Kafka index）关键配置片段
{
  "type": "kafka",
  "dataSchema": {
    "dataSource": "clicks",
    "timestampSpec": { "column": "ts", "format": "iso" },
    "dimensionsSpec": { "dimensions": ["user_id", "event", "region"] },
    "metricsSpec": [
      { "type": "count", "name": "count" },
      { "type": "longSum", "name": "amount", "fieldName": "amount" }
    ],
    "granularitySpec": { "segmentGranularity": "HOUR", "queryGranularity": "MINUTE" }
  }
}
```

## Pinot

Apache Pinot 是 LinkedIn 开源的实时分布式 OLAP 数据库，与 Druid 设计思路高度相似（列式、按时间分段、Bitmap 索引、实时+离线摄取），但更强调「实时 + 离线」双摄取路径和极低延迟。它支撑了 LinkedIn/Uber 的用户画像、内部指标、实时看板等场景。

```text
Pinot 要点：
1. 双摄取 —— 实时（Kafka）+ 离线（Hadoop/Spark 批构建 Segment）
2. Star-Tree 索引 —— 物化聚合结果加速大范围聚合
3. Upsert —— 支持主键去重/更新（较新版本）
4. 组件 —— Controller（协调）/ Broker（查询）/ Server（存段）/ Minion（后台任务）
```

```json
// Pinot 表配置：实时 + 离线双摄取
{
  "tableName": "events",
  "tableType": "REALTIME",
  "segmentsConfig": { "replication": "3", "schemaName": "events" },
  "tableIndexConfig": {
    "streamConfigs": {
      "streamType": "kafka",
      "stream.kafka.topic.name": "events",
      "stream.kafka.consumer.type": "lowLevel"
    }
  }
}
```

## DuckDB

DuckDB 是「进程内」嵌入式 OLAP 数据库，类比 SQLite 之于 OLTP——不需要服务器，作为一个库嵌进 Python/Java/Node 应用里，对本地 Parquet/CSV 文件直接做列式向量化分析。它是数据分析师单机处理 GB~TB 级数据、替代 pandas 内存瓶颈的利器，也常用于把 Parquet 直接查询作为轻量数仓。

```text
DuckDB 要点：
1. 嵌入式 —— 无服务器，单文件或内存，一条 import 即可用
2. 列式向量化 —— 与 ClickHouse 类似向量化执行引擎
3. 直接读文件 —— 直接查询 Parquet/CSV/JSON，无需导入
4. 单机场景 —— 适合单机分析、本地 ETL、Jupyter 环境
```

```python
import duckdb

# 直接查询 Parquet 文件，无需导入
con = duckdb.connect()
result = con.execute("""
    SELECT region, SUM(amount) AS total
    FROM 'data/sales.parquet'
    GROUP BY region
    ORDER BY total DESC
""").fetchall()
print(result)
```

```sql
-- DuckDB SQL：直接对 CSV 做聚合
SELECT event_name, count(*) AS cnt
FROM read_csv_auto('events.csv')
GROUP BY event_name
ORDER BY cnt DESC LIMIT 10;
```

## Snowflake

Snowflake 是云原生数仓的开创者，核心是「存算分离」——存储、计算、云服务三层独立扩展，数据存对象存储，计算是独立的虚拟仓库（Virtual Warehouse），按需启停按秒计费。它把数仓做成了 SaaS，免运维、弹性强，是云上数仓的标杆，也催生了整个 Lakehouse 和存算分离浪潮。

```text
Snowflake 要点：
1. 存算分离 —— 存储（对象存储）/计算（虚拟仓库）/服务（元数据）三层分离
2. 虚拟仓库 —— 计算集群按规模（XS~6XL）动态扩缩，可挂起省成本
3. 半结构化 —— 原生支持 VARIANT 类型，直接查 JSON
4. Time Travel —— 自动保留历史版本，误删可回溯
```

```sql
-- 创建虚拟仓库并查询
CREATE WAREHOUSE my_wh WITH WAREHOUSE_SIZE = 'MEDIUM';
USE WAREHOUSE my_wh;

-- 直接查询 JSON 半结构化数据（VARIANT）
SELECT data:user_id::string  AS user_id,
       data:amount::number   AS amount
FROM events_json
WHERE data:event::string = 'purchase';
```

## BigQuery

Google BigQuery 是 GCP 的 Serverless 数仓，与 Snowflake 一样是存算分离的托管服务，主打「完全无服务器 + 按查询数据量计费 + 与 GCS 数据湖无缝集成」。它对超大表做秒级扫描，内置 ML（BigQuery ML）和外部表（直接查 GCS 上的 Parquet），是 GCP 数据生态的查询中心。

```text
BigQuery 要点：
1. Serverless —— 无服务器概念，按扫描字节计费（或按 slot 容量计费）
2. 列式存储 —— 内部 Capacitor 列式格式，强压缩
3. 外部表 —— 直接查 GCS 上的 Parquet/CSV，湖仓一体
4. BigQuery ML —— 用 SQL 直接训练/预测模型
```

```sql
-- 标准聚合（与标准 SQL 几乎一致）
SELECT region, SUM(amount) AS total
FROM `project.dataset.sales`
WHERE dt = '2024-08-14'
GROUP BY region;

-- 创建外部表，直接查 GCS 上的 Parquet
CREATE EXTERNAL TABLE sales_ext
OPTIONS (format = 'PARQUET', uris = ['gs://bucket/sales/*.parquet']);
```

## Redshift

Amazon Redshift 是 AWS 的云数仓，是早期大规模并行（MPP）数仓的代表。它采用「共享存储 + 多计算节点」的集群架构，用列式存储、分片键（Dist Key）和排序键（Sort Key）优化，后来演进为 Redshift Spectrum（直接查 S3）和 Serverless 形态。它与 S3、Glue 深度集成，是 AWS 生态的查询中心。

```text
Redshift 要点：
1. MPP 集群 —— Leader 节点 + 多个 Compute 节点，分布式并行查询
2. 分片键 —— Dist Key 决定数据在节点间分布，影响 Join 是否要重分布
3. 排序键 —— Sort Key 决定数据排序，影响范围扫描和压缩
4. Spectrum —— 直接查 S3 上的数据，无需全部加载进集群
```

```sql
-- 建表并指定分布键与排序键
CREATE TABLE sales (
    order_id   BIGINT,
    region     VARCHAR(32),
    amount     DECIMAL(20,2),
    dt         DATE
)
DISTKEY(region)          -- 分布键：同 region 数据同节点，Join 本地化
SORTKEY(dt);             -- 排序键：按日期排序，范围扫描快

SELECT region, SUM(amount) FROM sales WHERE dt = '2024-08-14' GROUP BY region;
```

## 应用场景实战

### 场景一：实时数仓指标用 StarRocks 主键模型承载

```sql
-- 实时明细流按主键 upsert 进主键模型表，供看板秒级查询
CREATE TABLE rt_metric (
    dt          DATE,
    dim         VARCHAR(64),
    metric_val  BIGINT SUM
) ENGINE = OLAP
PRIMARY KEY (dt, dim)
DISTRIBUTED BY HASH(dim) BUCKETS 32;

-- 看板查询：实时指标
SELECT dim, SUM(metric_val) AS v
FROM rt_metric
WHERE dt = '2024-08-14'
GROUP BY dim;
```

### 场景二：日志明细分析用 ClickHouse

```sql
-- 埋点明细表（MergeTree）
CREATE TABLE events (
    event_date  Date,
    user_id     UInt64,
    event_name  String,
    props       String
) ENGINE = MergeTree
PARTITION BY toYYYYMM(event_date)
ORDER BY (event_date, event_name, user_id);

-- 漏斗/聚合分析：各事件 UV、PV
SELECT event_name,
       uniqExact(user_id) AS uv,
       count()            AS pv
FROM events
WHERE event_date = '2024-08-14'
GROUP BY event_name
ORDER BY uv DESC;
```

## 最佳实践与踩坑记录

### 最佳实践

1. 明细分析选 ClickHouse，实时更新选 StarRocks/Doris，预聚合高并发选 Druid/Pinot
2. 单机/本地分析用 DuckDB，直接查 Parquet 别搬进 pandas
3. StarRocks/Doris 主键模型表的分桶键选高基数列，避免数据倾斜
4. ClickHouse 分区粒度按天/月，避免分区过多导致元数据膨胀
5. 云数仓（Snowflake/BigQuery）注意按扫描量计费，查询加分区过滤和 LIMIT 省成本
6. Druid/Pinot 摄入时合理 rollup，维度别全量细粒度（避免存储/查询双爆）
7. 高频看板查询走物化视图/预聚合，别每次全量扫明细

### 踩坑记录

```text
坑 1：ClickHouse 频繁单条 UPDATE
结论：更新极慢，Mutantion 堆积，查询延迟升高。
原因：ClickHouse 为批量追加设计，UPDATE 走后台重写（Mutation）。
解法：改用主键模型引擎（ReplacingMergeTree）或换 StarRocks/Doris。

坑 2：StarRocks/Doris 分桶键选错导致数据倾斜
结论：某节点数据量是其他节点数倍，查询长尾拖慢整体。
原因：分桶键低基数（如 status 只有几个值），数据集中在少数桶。
解法：选高基数列做分桶键，或加随机前缀打散。

坑 3：Druid/Pinot 维度粒度过细导致预聚合失效
结论：rollup 几乎不起作用，存储和查询量等于明细，性能差。
原因：高基数列（如 user_id）设为维度，预聚合无法合并。
解法：高基数列用指标或单独的 sketch 结构，维度保持低基数。

坑 4：BigQuery/Snowflake 不分区过滤导致账单爆表
结论：按月账单暴涨，一条全表扫描烧掉大量费用。
原因：按扫描字节计费，无分区过滤即全表扫描。
解法：查询强制加分区列过滤，建分区/聚簇表，设费用告警。

坑 5：DuckDB 处理超过内存的数据直接 OOM
结论：单机处理几十 GB 数据内存耗尽崩溃。
原因：DuckDB 是单机嵌入式，内存受单机限制。
解法：数据分区处理，或迁到分布式引擎（ClickHouse/Spark）。
```
