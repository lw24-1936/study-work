## 概述

维度建模的核心之一，是处理「维度属性会随时间变化」的问题。一个用户的等级会升、一个商品的类目会调、一个门店的地址会搬——这些变化如果直接覆盖维度表，就会丢失历史、扭曲历史事实的统计口径。缓慢变化维（Slowly Changing Dimension，SCD）就是一套「既保留历史又能反映现状」的维度更新策略，其中 SCD2 拉链表是数仓最常用的方案。

```text
维度变化的本质矛盾：
1. 要现状 —— 分析「当前用户等级」时希望看到最新值
2. 要历史 —— 分析「去年下单时用户是什么等级」时希望看到当时的值
3. 直接覆盖 —— 丢了历史，历史统计口径被污染
4. 无限保留 —— 每变一次加一行，表膨胀且查询复杂
5. 平衡点 —— SCD 各策略就是在现状、历史、复杂度之间取舍
```

```text
常见 SCD 策略速览：
1. SCD0 保留原值 —— 永不更新，适合固定属性（生日、身份证号）
2. SCD1 直接覆盖 —— 只保留最新值，适合可纠正属性（拼写错误）
3. SCD2 增加新行 —— 保留全量历史版本，用有效期标记（最常用）
4. SCD3 增加列 —— 只保留「当前 + 上一次」两个值，历史有限
5. 混合策略 —— 同一维度表里不同属性用不同 SCD 策略
```

## SCD 0/1/2/3

SCD0（保留原值）：维度加载后永不更新，即使源系统变了也不改，适合「生来不变」的属性如出生日期、身份证号、首次注册时间。SCD1（直接覆盖）：维度属性变化时直接 UPDATE 覆盖旧值，只保留最新状态，简单但丢失历史，适合确实需要纠正的属性（如姓名的错别字）。SCD2（增加新行）：属性变化时插入一行新记录，用代理键区分版本、用生效/失效时间标记有效期，完整保留历史，是维度建模的默认选择。SCD3（增加列）：在原行上增加「当前值」和「前值」两列，只保留最近一次变化，适合「偶尔需要对比上一次」的属性。

```text
SCD0 要点：
1. 策略 —— 首次加载后永不更新，源变化也不理会
2. 适用 —— 真正的不可变属性：出生日期、身份证、首单时间
3. 优点 —— 最简单，无历史维护成本
4. 缺点 —— 若属性实际会变，会导致错误数据
5. 实现 —— 加载时判断已存在则跳过
```

```text
SCD1 要点：
1. 策略 —— 属性变化直接 UPDATE 覆盖
2. 适用 —— 纠错型属性（错别字、格式规范化）
3. 优点 —— 简单，表不膨胀
4. 缺点 —— 历史丢失，历史报表口径会随现状漂移
5. 实现 —— INSERT ... ON DUPLICATE KEY UPDATE 或 MERGE 覆盖
```

```text
SCD2 要点：
1. 策略 —— 变化时插入新版本行，旧行置失效
2. 关键字段 —— 代理键（区分版本）、有效开始/结束时间、当前版本标记
3. 适用 —— 需要精确历史回溯的属性（等级、地址、类目）
4. 优点 —— 历史完整，可回溯任意时点状态
5. 缺点 —— 表随变化膨胀，查询需过滤「当前版本」条件
```

```text
SCD3 要点：
1. 策略 —— 加一列存「前值」，原列存「当前值」
2. 适用 —— 只需对比「当前 vs 上一次」的属性
3. 优点 —— 不增行，查询简单
4. 缺点 —— 只保留一次历史，多次变化就丢了更早的值
5. 实现 —— 变化时先把当前值搬到 prev 列，再更新当前列
```

```sql
-- SCD1 示例：直接覆盖
UPDATE dim_user SET city = '上海' WHERE user_key = 1001;

-- SCD2 示例：插入新版本，旧版本置失效
-- 旧行置失效
UPDATE dim_user
SET is_current = 0, end_date = '2024-08-14'
WHERE user_key = 1001 AND is_current = 1;

-- 插入新版本行（代理键自增）
INSERT INTO dim_user (user_key, user_id, city, start_date, end_date, is_current)
VALUES (2002, 1001, '上海', '2024-08-14', '9999-12-31', 1);

-- SCD3 示例：保留前值
UPDATE dim_user
SET prev_city = city, city = '上海'
WHERE user_id = 1001;
```

## 拉链表

拉链表是 SCD2 的工程化落地：每行记录携带「生效开始日期（start_date）」和「生效结束日期（end_date，默认 9999-12-31）」，表示该版本属性在某个时间区间内有效。查询某历史时点的状态只需 `WHERE date BETWEEN start_date AND end_date`。相比每天全量快照，拉链表只在维度变化时才新增行，存储省、又能精确回溯，是数仓处理慢变维的标准方案。

```text
拉链表核心字段：
1. 代理键（surrogate key） —— 区分同一业务键的不同版本行
2. 业务键（business key） —— 源系统主键，如 user_id
3. 生效开始日期 start_date —— 该版本何时开始生效
4. 生效结束日期 end_date —— 该版本何时失效（9999-12-31 表示当前有效）
5. 当前版本标记 is_current —— 冗余字段，加速「查当前」的过滤
```

```text
拉链表的三种构造方式：
1. 全量快照对比 —— 拿当日全量快照与昨日拉链做 diff，找出新增/变化/关闭
2. 增量 + 关链 —— 只处理变化的记录，把旧版本关链、新版本开链
3. 流式 CDC —— 用 binlog 变更事件实时维护拉链（近实时数仓常用）
```

```sql
-- 创建拉链表结构
CREATE TABLE dim_user_zip (
    user_key   BIGINT,          -- 代理键
    user_id    BIGINT,          -- 业务键
    name       STRING,
    tier       STRING,          -- 会缓慢变化的属性
    city       STRING,
    start_date DATE,            -- 生效开始
    end_date   DATE,            -- 生效结束
    is_current INT              -- 1 当前 0 历史
);

-- 查询某历史时点的用户等级（回溯 2024-06-01）
SELECT user_id, tier, city
FROM dim_user_zip
WHERE '2024-06-01' BETWEEN start_date AND end_date;

-- 查询当前所有有效用户
SELECT user_id, tier FROM dim_user_zip WHERE is_current = 1;
```

## 快照表

快照表是「每天把维度（或事实）的完整状态存一份」的表，按日期分区，`dt=2024-08-14` 就是那一天的完整镜像。它实现简单、查询直观，但存储膨胀严重（每维每日一份）。快照表常用于「周期快照事实表」（如每日账户余额、每日库存量）和「每日维度全量快照」（在数据量不大、历史回溯频繁时替代拉链表）。它和拉链表的区别是：快照表存「每天的状态全集」，拉链表只存「变化发生的版本」。

```text
快照表要点：
1. 定义 —— 按 dt 分区，每天一份完整状态镜像
2. 适用 —— 周期快照事实（余额、库存）、小维度每日快照
3. 优点 —— 查询简单直观，天然支持任意时点对比
4. 缺点 —— 存储随天数线性膨胀，冗余大
5. 与拉链表对比 —— 快照表「以天为粒度存全集」，拉链表「以变化为粒度存版本」
```

```sql
-- 每日维度快照表
CREATE TABLE dim_user_snapshot (
    dt STRING,          -- 快照日期分区
    user_id BIGINT,
    tier STRING,
    city STRING
) PARTITIONED BY (dt);

-- 每日生成快照
INSERT OVERWRITE TABLE dim_user_snapshot PARTITION (dt='2024-08-14')
SELECT user_id, tier, city FROM ods_user WHERE dt = '2024-08-14';

-- 对比两天用户等级变化
SELECT a.user_id, a.tier AS yesterday_tier, b.tier AS today_tier
FROM dim_user_snapshot a
JOIN dim_user_snapshot b
  ON a.user_id = b.user_id AND a.dt='2024-08-13' AND b.dt='2024-08-14'
WHERE a.tier <> b.tier;
```

## 全量/增量

全量同步是每天把源表的完整数据抽取覆盖到数仓（`INSERT OVERWRITE` 当天分区），实现简单、能自愈（数据漂移可自我修正），但数据量大时抽取成本和存储成本高。增量同步只抽取「变化的那部分数据」（新增+修改+删除，靠 CDC 或时间戳+水位线识别），写入成本低，但需要处理 upsert/merge 和删除语义，还要考虑迟到数据补录。数仓实践中：维表常用「全量快照对比」构造拉链，事实表常用「增量 append + 分区覆盖」的组合。

```text
全量同步要点：
1. 方式 —— 每天全量拉取源表，覆盖当天分区
2. 优点 —— 实现简单、自愈、口径易核对
3. 缺点 —— 大表抽取慢、存储膨胀、带宽压力大
4. 适用 —— 小维度表、对一致性要求高的场景
```

```text
增量同步要点：
1. 方式 —— 只抽取变化数据（CDC / 更新时间戳水位线）
2. 优点 —— 抽取快、资源省、近实时
3. 缺点 —— 需处理 upsert/删除/迟到补录，复杂度高
4. 适用 —— 大事实表、需要低延迟同步的场景
```

```sql
-- 全量：覆盖写入当天分区
INSERT OVERWRITE TABLE dwd_order PARTITION (dt='2024-08-14')
SELECT * FROM ods_order WHERE dt = '2024-08-14';

-- 增量：按更新时间戳抽取增量，再 MERGE 进目标表
MERGE INTO dwd_order t
USING (
    SELECT * FROM ods_order
    WHERE update_time >= '${last_watermark}'
) s
ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET t.amount = s.amount, t.status = s.status
WHEN NOT MATCHED THEN INSERT (order_id, amount, status) VALUES (s.order_id, s.amount, s.status);
```

## 历史回溯

历史回溯指「查询过去某一时点的数据状态」，是数仓区别于业务库的核心能力之一。业务库只存现状，数仓通过拉链表/快照表/分区快照保存历史，让分析师能回答「去年双十一那天用户是什么等级」「三个月前这个商品在哪个类目」。历史回溯的实现依赖：拉链表的 `BETWEEN start_date AND end_date`、快照表的 `dt=历史日期` 分区、以及 SCD2 对历史版本的完整保留。

```text
历史回溯要点：
1. 时点查询 —— 拉链表按时间区间查，快照表按 dt 分区查
2. 区间统计 —— 统计某段时间内的状态，需按时间区间关联维度版本
3. 回溯事实 —— 事实表里的金额/数量是「当时值」，维度是「当时版本」
4. 口径一致 —— 回溯时必须用历史版本维度，不能用当前维度，否则口径错
5. 回补/重刷 —— 源数据修复后需重刷历史分区，保证历史可修正
```

```text
历史回溯的典型问题：
1. 用当前维度关联历史事实 —— 口径漂移，历史报表跟着变
2. 拉链表断链 —— 关链/开链逻辑错误，出现时间区间重叠或真空
3. 分区删除 —— 误删历史分区导致无法回溯
4. 时区/边界 —— start_date 与 end_date 边界含不含端点（闭开区间约定）
```

```sql
-- 回溯：查「2024-06-01」时点的用户等级，关联当天事实
SELECT u.user_id, u.tier, SUM(f.amount) AS gmv
FROM dwd_order f
JOIN dim_user_zip u
  ON f.user_id = u.user_id
 AND f.dt = '2024-06-01'
 AND '2024-06-01' BETWEEN u.start_date AND u.end_date
GROUP BY u.user_id, u.tier;

-- 用快照表回溯历史
SELECT user_id, tier
FROM dim_user_snapshot
WHERE dt = '2024-06-01';
```

## 应用场景实战

### 场景一：用拉链表维护用户等级维度（SCD2）

```sql
-- 1. 建拉链表
CREATE TABLE dim_user_zip (
    user_key BIGINT, user_id BIGINT, tier STRING,
    start_date DATE, end_date DATE, is_current INT
);

-- 2. 每日 ETL：用当日全量快照对比昨日拉链，处理变化
-- 新增或变化：关旧链、开新链
INSERT INTO dim_user_zip
SELECT ROW_NUMBER() OVER (ORDER BY user_id) + 100000 AS user_key,
       user_id, tier, DATE '2024-08-14' AS start_date,
       DATE '9999-12-31' AS end_date, 1 AS is_current
FROM ods_user WHERE dt = '2024-08-14';

-- 3. 关闭已变化的旧链（tier 变化或 user 消失）
UPDATE dim_user_zip
SET end_date = DATE '2024-08-14', is_current = 0
WHERE is_current = 1
  AND (user_id, tier) NOT IN (
      SELECT user_id, tier FROM ods_user WHERE dt = '2024-08-14'
  );

-- 4. 查询当前等级分布
SELECT tier, COUNT(*) AS cnt FROM dim_user_zip WHERE is_current = 1 GROUP BY tier;
```

### 场景二：周期快照事实表（每日账户余额）

```sql
-- 每日账户余额快照事实表
CREATE TABLE fact_account_balance_daily (
    dt STRING, account_id BIGINT, balance DECIMAL(18,2)
) PARTITIONED BY (dt);

-- 每天从账户流水累加出余额快照
INSERT OVERWRITE TABLE fact_account_balance_daily PARTITION (dt='2024-08-14')
SELECT '2024-08-14', account_id, SUM(amount) AS balance
FROM dwd_account_transaction
WHERE trans_date <= '2024-08-14'
GROUP BY account_id;

-- 历史回溯：查 6 月 1 日余额
SELECT account_id, balance
FROM fact_account_balance_daily
WHERE dt = '2024-06-01';
```

## 最佳实践与踩坑记录

### 最佳实践

1. 需要精确历史回溯的属性用 SCD2 拉链表，仅需纠错的属性用 SCD1
2. 拉链表用代理键区分版本，业务键单独保留，end_date 用 9999-12-31 表示当前
3. 冗余 is_current 字段，加速「查当前版本」的过滤，避免反复比对 end_date
4. 拉链表约定区间为「左闭右开」或「闭区间」并全仓统一，避免边界歧义
5. 大维度（亿级）不宜每日全量快照，改用拉链或增量维护
6. 快照表适合小维度和周期快照事实，控制每日快照的存储成本
7. 历史回溯查询务必用「当时维度版本」关联「当时事实」，防止口径漂移

### 踩坑记录

```text
坑 1：拉链表出现时间区间重叠
结论：同一 user_id 同时有多行 is_current=1，查询当前状态返回多条。
原因：关链和开链不是原子操作，或增量关链条件漏写，旧行没失效。
解法：关链与开链放同一事务/同一批任务，加唯一约束「业务键+当前版本」防重叠。

坑 2：用当前维度关联历史事实导致口径漂移
结论：历史报表的用户等级跟着现在变，去年数据算出来是今年的口径。
原因：回溯时误用 is_current=1 的当前维度，而非历史时点版本。
解法：历史分析一律用 BETWEEN start_date AND end_date 取当时版本。

坑 3：SCD1 覆盖后无法回答「当时是什么」
结论：领导问「3 个月前这个用户什么等级」，发现只有当前值，无法回溯。
原因：对需要历史的属性用了直接覆盖策略。
解法：评估属性是否需回溯，需回溯的改 SCD2，已覆盖的用快照表兜底重建。

坑 4：end_date 边界含不含当天产生歧义
结论：相邻两个版本在交界日同时命中，统计重复计数。
原因：团队对「生效区间闭开」约定不一致，有人用 <= 有人用 <。
解法：全仓统一闭开区间约定（start 闭、end 开），文档化并代码校验。

坑 5：每日全量快照导致存储爆炸
结论：亿级维度每天全量快照，数月后存储翻倍、查询变慢。
原因：用快照表处理大维度，没区分「变化频率」与「数据量」。
解法：大维度改拉链表（只存变化版本），快照表仅用于小维度或周期快照事实。
```
