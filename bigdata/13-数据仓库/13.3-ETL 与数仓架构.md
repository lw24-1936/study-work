## 概述

ETL（Extract-Transform-Load）是数仓的「血液管道」——把分散在业务库、日志、文件里的数据抽取出来，清洗转换，加载进数仓。数仓架构则在更高层面回答「数据怎么组织、怎么流动、怎么服务」：从早期的 ETL 批处理，到 Lambda/Kappa 实时架构，到 Medallion 分层和 Lakehouse、Data Mesh/Data Fabric 这些现代范式。理解 ETL 和架构演进，是设计企业级数据平台的基础。

```text
ETL 与数仓架构的关系：
1. ETL 是管道 —— 解决「数据怎么搬、怎么洗、怎么装」的工程问题
2. 数仓架构是蓝图 —— 解决「数据怎么分层、怎么流动、怎么服务」的设计问题
3. ETL 服务于架构 —— 架构定了分层和流向，ETL 负责落地搬运
4. 架构随需求演进 —— 从批到流、从仓库到湖仓一体、从集中到联邦
```

```text
数据架构演进主线：
1. 传统 ETL 数仓（批处理 + 分层）
2. Lambda 架构（批 + 流双轨，解决实时性）
3. Kappa 架构（纯流，简化 Lambda 的重复逻辑）
4. 数据湖（先存后治，Schema-on-Read）
5. Lakehouse（湖仓一体，湖的灵活 + 仓的治理）
6. Data Mesh / Data Fabric（去中心化 / 智能编织，解决组织规模问题）
```

## ETL/ELT

ETL（Extract-Transform-Load）是先抽取、再在中间层转换、最后加载进数仓，转换发生在专门的 ETL 引擎里，源和目标都不承担计算。ELT（Extract-Load-Transform）是先抽取、直接加载进数仓（通常是数据湖/湖仓），再在数仓内部用 SQL/Spark 做转换，利用数仓强大的计算能力。现代大数据普遍从 ETL 转向 ELT：因为目标端（数仓/湖仓）计算能力强、存储便宜，先落地再转换更灵活、可重算。

```text
ETL 特点：
1. 顺序 —— 抽取 -> 转换 -> 加载，转换在中间层完成
2. 适用 —— 目标端计算弱（如早期数据库）、需严格控制加载数据的场景
3. 优点 —— 加载前就清洗干净，目标端数据质量高
4. 缺点 —— 转换逻辑耦合在 ETL 工具里，重算需重抽，灵活性差
```

```text
ELT 特点：
1. 顺序 —— 抽取 -> 加载 -> 转换，转换在数仓内完成
2. 适用 —— 目标端是强计算的数据湖/湖仓（Spark/Trino/SQL 引擎）
3. 优点 —— 原始数据先落地，可反复重算，转换用 SQL 易维护
4. 缺点 —— 原始数据量大时加载和存储成本高，需治理
```

```sql
-- ELT 风格：原始数据先落地 ODS，再用 SQL 在数仓内转换
-- 第一步（Load）：贴源加载
INSERT INTO ods_order SELECT * FROM raw_order WHERE dt = '${bizdate}';

-- 第二步（Transform）：在数仓内用 SQL 清洗转换出 DWD
INSERT INTO dwd_order_detail
SELECT order_id, user_id, amount,
       CASE WHEN status IN ('paid','shipped') THEN 'paid' END AS status_norm
FROM ods_order
WHERE dt = '${bizdate}' AND order_id IS NOT NULL;
```

```text
ETL vs ELT 的选择：
1. 目标端是湖仓/强计算引擎 -> ELT
2. 目标端是传统数据库、需加载前清洗 -> ETL
3. 看重可重算、可审计 -> ELT（原始数据保留）
4. 看重加载速度与网络 -> ETL（先压缩清洗再传）
5. 现实多是混合 —— 轻量清洗在管道，重转换在数仓内
```

## CDC

CDC（Change Data Capture，变更数据捕获）是识别并捕获源数据库数据变化（INSERT/UPDATE/DELETE）的技术，是增量同步和实时数仓的基础。它比「全量快照对比」更高效、延迟更低。实现分两类：基于日志的 CDC（读 MySQL binlog、PG WAL，捕获物理/逻辑变更，对源库影响小、精度高，主流方案）和基于查询的 CDC（轮询时间戳/版本号或触发器的模拟方式，简单但延迟和开销较大）。详见 15.1-CDC 原理与工具。

```text
CDC 要点：
1. 目标 —— 捕获每行数据的增删改，产出变更事件流
2. 日志型 —— 读 binlog/WAL，低延迟低侵入，主流（Debezium/Canal）
3. 查询型 —— 轮询时间戳/版本列，或触发器记录变更表
4. 输出 —— 每条变更带操作类型（+U/-U/+I/-D）和变更前后值
5. 用途 —— 实时同步、实时数仓、缓存失效、审计、数据集成
```

```text
CDC 事件模型（Debezium 风格）：
1. Create（+I） —— 新增一行，带完整新值
2. Update（+U/-U） —— 更新，带修改前（before）和修改后（after）值
3. Delete（-D） —— 删除，带被删行的旧值
4. 每条事件含 —— 表名、主键、变更时间戳、事务边界
5. 下游消费 —— 转成 upsert/merge 写目标，或进 Kafka 供多路复用
```

```json
{
  "op": "u",
  "before": { "user_id": 1001, "tier": "silver" },
  "after":  { "user_id": 1001, "tier": "gold" },
  "ts_ms": 1723600000000,
  "source": { "db": "biz", "table": "user_profile" }
}
```

## Full/Incremental

全量（Full）与增量（Incremental）是数据抽取的两种基本模式。全量是每次把源表完整数据抽取一遍，简单可靠但成本高；增量是只抽取自上次同步以来变化的数据，高效低延迟但需依赖 CDC 或时间戳水位线识别变化。实际工程几乎总是「首次全量 + 后续增量」的组合：先全量初始化，再靠增量持续追平，必要时定期全量兜底修复数据漂移。

```text
全量同步要点：
1. 方式 —— 完整抽取源表，覆盖目标分区/表
2. 时机 —— 首次初始化、数据漂移修复、小表每日同步
3. 优点 —— 简单自愈，口径易核对
4. 缺点 —— 大表成本高、延迟大
```

```text
增量同步要点：
1. 方式 —— 只抽变化数据（CDC / update_time > 水位线）
2. 时机 —— 大表日常同步、近实时场景
3. 优点 —— 高效低延迟
4. 缺点 —— 需处理 upsert/删除/迟到，复杂度高
5. 水位线 —— 记录上次同步到的最大 update_time 或 binlog 位点
```

```sql
-- 增量抽取：按更新时间戳水位线
SELECT * FROM source_order
WHERE update_time >= '${last_watermark}'
ORDER BY update_time;

-- 记录新水位线，下次从这继续
-- last_watermark = max(update_time) of this batch
```

```shell
# 全量初始化：一次性 dump + 加载
mysqldump --single-transaction biz orders > orders_full.sql

# 后续增量：用 CDC 工具持续捕获变更
# 详见 15.1-CDC 原理与工具 与 15.2-数据集成工具与同步语义
```

## Upsert/Merge

Upsert（Update + Insert）是增量同步写入目标表的核心操作：数据存在则更新，不存在则插入，主键冲突时以新数据为准。Merge 是其 SQL 表达（`MERGE INTO ... WHEN MATCHED ... WHEN NOT MATCHED`）。在数仓里，维表用 upsert 维护现状、事实表用 upsert 支持「迟到数据修正」（同主键重复到达时覆盖）。传统 Hive 不支持行级 upsert，需借助 Iceberg/Hudi/Delta 等表格式或改写为「全量重建分区」。

```text
Upsert 语义要点：
1. 定义 —— 存在则更新、不存在则插入，以主键判定
2. Merge 语法 —— WHEN MATCHED THEN UPDATE / WHEN NOT MATCHED THEN INSERT
3. 删除支持 —— WHEN MATCHED THEN DELETE（配合 CDC 的删除事件）
4. 幂等 —— 同一条数据重复 upsert 结果不变，这是可靠同步的基石
5. 依赖 —— 需要主键 + 支持行级更新的存储（表格式/数据库）
```

```sql
-- MERGE 示例：CDC 变更事件写入目标表
MERGE INTO dwd_user t
USING (
    SELECT user_id, tier, city, op FROM cdc_user_events
) s
ON t.user_id = s.user_id
WHEN MATCHED AND s.op = 'd' THEN DELETE
WHEN MATCHED THEN UPDATE SET t.tier = s.tier, t.city = s.city
WHEN NOT MATCHED AND s.op <> 'd' THEN
    INSERT (user_id, tier, city) VALUES (s.user_id, s.tier, s.city);
```

```sql
-- 传统 Hive 无行级 upsert：用「全量重建分区」模拟
-- 1. 当日增量 append 到临时区
-- 2. 用 ROW_NUMBER 去重取最新
-- 3. 覆盖写回分区
INSERT OVERWRITE TABLE dwd_user PARTITION (dt='2024-08-14')
SELECT user_id, tier, city FROM (
    SELECT user_id, tier, city,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY update_time DESC) AS rn
    FROM (
        SELECT * FROM dwd_user WHERE dt = '2024-08-14'
        UNION ALL
        SELECT * FROM ods_user_delta WHERE dt = '2024-08-14'
    ) t
) x WHERE rn = 1;
```

## 数据校验

数据校验是 ETL 的「质检环节」，回答「同步后的数据和源数据一致吗、完整吗」。核心校验维度：条数（count 对账）、关键字段值（sum/min/max/抽样比对）、主键唯一性、空值率、口径一致性。校验通常在加载后自动跑，产出「校验报告」，不一致则阻断或告警。校验是数据质量治理的第一道防线，详见 27.1-数据质量维度与规则。

```text
数据校验的维度：
1. 条数校验 —— 源表行数 vs 目标表行数（含分区行数）
2. 值校验 —— 关键度量 SUM/AVG/MIN/MAX 或抽样字段比对
3. 主键校验 —— 目标表主键是否唯一（去重后行数应等于原行数）
4. 完整性校验 —— 空值率、枚举合法性、日期范围是否越界
5. 时效校验 —— 数据是否按时产出（SLA 监控）
```

```sql
-- 条数对账：源与目标
SELECT 'source' AS side, COUNT(*) AS cnt FROM ods_order WHERE dt='2024-08-14'
UNION ALL
SELECT 'target' AS side, COUNT(*) AS cnt FROM dwd_order WHERE dt='2024-08-14';

-- 主键唯一性校验（应返回 0 行）
SELECT order_id, COUNT(*) FROM dwd_order WHERE dt='2024-08-14'
GROUP BY order_id HAVING COUNT(*) > 1;

-- 度量值对账
SELECT SUM(amount) FROM ods_order WHERE dt='2024-08-14';  -- 源
SELECT SUM(amount) FROM dwd_order WHERE dt='2024-08-14';  -- 目标，二者应相等
```

## Lambda

Lambda 架构用「批处理层 + 速度层」双轨解决「既要全量精确、又要实时低延迟」的矛盾：批处理层（Batch Layer）离线处理全量历史数据，产出精确但延迟高的结果（T+1）；速度层（Speed Layer）实时处理增量数据，产出近似但延迟低的结果（秒级）；服务层（Serving Layer）把两层结果合并对外查询。代价是同一套业务逻辑要写两遍（批 + 流），维护成本高、口径难统一。

```text
Lambda 架构三层：
1. Batch Layer —— 离线全量批处理（Spark/Hive），精确、T+1 延迟
2. Speed Layer —— 实时增量处理（Flink/Storm），近似、秒级延迟
3. Serving Layer —— 合并两层结果，对外提供统一查询
```

```text
Lambda 架构要点：
1. 优点 —— 兼顾精确性与实时性，批层兜底流层误差
2. 缺点 —— 逻辑双写（批一套流一套），口径难统一、维护成本翻倍
3. 适用 —— 实时性要求高且需要历史精确数据的场景
4. 合并 —— 服务层对「流层覆盖窗口内 + 批层覆盖窗口外」做拼接
5. 典型 —— 实时大盘（流算当天）+ 历史报表（批算历史）双轨
```

```text
Lambda 架构示意：
        [源数据]
       /        \
  Batch Layer   Speed Layer
  (离线全量)     (实时增量)
       \        /
     Serving Layer（合并）
           |
       查询/BI
```

## Kappa

Kappa 架构是对 Lambda 的简化：只保留一条「流处理」链路，所有数据（历史 + 实时）都当流处理。它把数据存进可重放的日志/消息系统（如 Kafka），历史重算就是「重放」这条流——用同一套流处理代码，先回放历史数据算出基线，再持续处理实时数据。Kappa 消除了 Lambda 的逻辑双写问题，但要求存储可重放、流处理引擎有足够吞吐处理全量历史。

```text
Kappa 架构要点：
1. 单链路 —— 只有流处理，没有独立的批处理层
2. 可重放 —— 历史数据以日志形式可重新消费（Kafka/消息队列）
3. 重算 —— 改逻辑后，回放历史数据重建结果，同一套代码
4. 优点 —— 逻辑单一、口径统一、架构简单
5. 缺点 —— 回放全量历史耗时，对存储吞吐和引擎能力要求高
```

```text
Kappa vs Lambda：
1. 逻辑 —— Kappa 一套代码，Lambda 批流两套
2. 复杂度 —— Kappa 简单，Lambda 复杂
3. 历史重算 —— Kappa 靠回放，Lambda 靠批层重跑
4. 精确性 —— Lambda 批层兜底更稳，Kappa 依赖回放完整性
5. 选择 —— 实时为主、历史可重放用 Kappa；批流都重且历史巨大用 Lambda
```

```text
Kappa 架构示意：
[源数据] -> [Kafka 可重放日志] -> [流处理引擎(Flink)] -> [结果存储]
                    ^                                  |
                    +------ 改逻辑后回放历史重算 -------+
```

## Medallion

Medallion（奖牌架构，Bronze/Silver/Gold 三层）是 Databricks 提出的数据湖分层范式，是数仓分层（ODS/DWD/DWS）在湖仓上的现代表达。Bronze（铜层）贴源存储原始数据；Silver（银层）清洗、去重、统一口径、可跨业务复用；Gold（金层）面向具体业务聚合出最终结果。它与 ODS-DWD-DWS-ADS 思想同源，命名更贴近「数据逐步提纯」的隐喻，是 Lakehouse 的事实标准分层。

```text
Medallion 三层：
1. Bronze 铜层 —— 原始数据贴源落地，保留全字段，只做最小处理
2. Silver 银层 —— 清洗 + 去重 + 口径统一 + 维度对齐，可复用
3. Gold 金层 —— 面向业务的聚合/汇总，直接服务报表与产品
```

```text
Medallion 要点：
1. 与数仓分层对应 —— Bronze~ODS，Silver~DWD，Gold~DWS/ADS
2. 逐层提纯 —— 每层数据质量递增、口径逐步统一
3. 银层是核心 —— 银层做得好，金层和下游都省事
4. 湖仓落地 —— 每层用表格式（Delta/Iceberg）存 Parquet 文件
5. 可重算 —— 原始数据在铜层保留，上层可随时重刷
```

```text
Medallion 分层示意：
Bronze（原始） -> Silver（清洗复用） -> Gold（业务聚合）
   raw_orders      cleaned_orders        sales_by_region
   raw_events      dedup_events          kpi_dashboard
```

## Lakehouse

Lakehouse（湖仓一体）融合了数据湖和数据仓库的优点：底层用廉价对象存储存开放格式数据（Parquet + Iceberg/Delta/Hudi 表格式），上层提供数据仓库才有的 ACID 事务、Schema 管理、索引、Time Travel 等治理能力。它解决了「数据湖便宜但缺治理、数仓治理好但贵且封闭」的对立，是当前大数据架构的主流方向。详见 14.1-数据湖概述 与 14.5-Lakehouse 实践。

```text
Lakehouse 核心能力：
1. 开放存储 —— 数据存对象存储，Parquet 开放格式，不锁定厂商
2. ACID 事务 —— 表格式提供原子提交、并发控制
3. Schema 管理 —— Schema 演进、约束、类型校验
4. Time Travel —— 时间旅行查询历史版本
5. 批流一体 —— 同一张表既支持批写也支持流写（MERGE/CDC）
```

```text
Lakehouse vs 数仓 vs 数据湖：
1. 数据湖 —— 便宜灵活，但缺事务和治理，易成数据沼泽
2. 数据仓库 —— 治理强，但存储封闭昂贵、难存非结构化数据
3. Lakehouse —— 湖的存储 + 仓的治理，二者兼得
4. 关键技术 —— 表格式（Iceberg/Hudi/Delta）是 Lakehouse 的基石
5. 引擎 —— Spark/Trino/Flink 等统一读写同一份湖上数据
```

## Data Mesh

Data Mesh（数据网格）是面向「大规模组织」的去中心化数据架构思想：把数据所有权从集中式数据团队下放到各业务域（Domain），每个域对自己的数据产品负责（像微服务对 API 负责一样），通过「数据产品」对外提供服务，并建立联邦计算治理（Federated Computational Governance）保证跨域互操作。它解决的是「中央数据团队成为瓶颈、平台僵化」的组织问题，而非纯技术问题。

```text
Data Mesh 四大原则：
1. 域所有权 —— 数据由产生它的业务域拥有和负责
2. 数据即产品 —— 数据以「产品」形态对外发布，有 SLA、文档、契约
3. 自助平台 —— 提供自助式数据基础设施，降低域团队门槛
4. 联邦治理 —— 全局标准 + 域自治，计算型治理自动执行
```

```text
Data Mesh 适用性：
1. 适用 —— 多业务域的大组织，中央团队已成为瓶颈
2. 不适用 —— 小团队、单一业务，集中式更简单高效
3. 代价 —— 需要组织变革，不是装个工具就能落地
4. 技术支撑 —— 数据目录、数据契约、自助平台是必备组件
5. 与 Lakehouse 互补 —— Mesh 管组织，Lakehouse 管存储与表格式
```

## Data Fabric

Data Fabric（数据编织）是一种强调「智能元数据驱动」的数据架构：通过统一的元数据层和知识图谱，把分散在多个数据源（库、湖、仓、SaaS）的数据编织起来，提供自动化的数据发现、集成、治理和编排。与 Data Mesh 的「去中心化组织」不同，Data Fabric 更偏「技术层自动化」——用主动元数据（Active Metadata）和 AI 自动化数据集成与管理，让用户无需关心数据在哪。

```text
Data Fabric 核心特征：
1. 元数据驱动 —— 主动元数据 + 知识图谱是核心
2. 自动化集成 —— 自动发现数据源、自动映射、自动编排
3. 虚拟化 —— 数据可留在原处，通过虚拟层/联邦查询访问
4. 智能治理 —— AI 辅助分类、血缘、策略执行
5. 统一访问 —— 屏蔽底层异构，提供一致的数据访问体验
```

```text
Data Fabric vs Data Mesh：
1. 维度 —— Fabric 是技术架构，Mesh 是组织架构
2. 核心 —— Fabric 靠元数据自动化，Mesh 靠域所有权
3. 治理 —— Fabric 集中自动化，Mesh 联邦自治
4. 关系 —— 二者可互补：Mesh 的域 + Fabric 的自动化编织
5. 落地 —— Fabric 偏工具（元数据平台+联邦查询），Mesh 偏组织变革
```

### 场景二：实时数仓的 Kappa 架构落地

```text
用 Kappa 架构：Kafka 存可重放日志，Flink 流处理，Iceberg 存结果。
改口径后回放 Kafka 历史数据重算，一套代码批流通吃。
```

```sql
-- Flink SQL：消费 Kafka 实时计算 GMV，写 Iceberg
CREATE TABLE order_events (
    order_id BIGINT, amount DECIMAL(10,2), event_time TIMESTAMP(3)
) WITH ('connector'='kafka', 'topic'='orders', 'format'='json');

CREATE TABLE gmv_result (
    dt STRING, gmv DECIMAL(18,2), PRIMARY KEY (dt) NOT ENFORCED
) WITH ('connector'='iceberg', 'catalog-name'='hive_catalog');

INSERT INTO gmv_result
SELECT DATE_FORMAT(event_time, 'yyyy-MM-dd') AS dt, SUM(amount) AS gmv
FROM order_events
GROUP BY DATE_FORMAT(event_time, 'yyyy-MM-dd');
```

```text
口径变更重算：改 SQL 后，从 Kafka 最早 offset 回放，重算历史结果，
同一套 Flink 代码无需额外批处理任务（Kappa 优势）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 现代湖仓优先 ELT：原始数据先落地，转换在数仓内用 SQL 完成，可重算可审计
2. 大表用「首次全量 + CDC 增量」，小表可每日全量，权衡成本与延迟
3. upsert 写入统一走 MERGE，保证幂等，主键冲突以新数据为准
4. 每层加载后必跑数据校验（条数 + 度量 + 主键唯一），不一致告警阻断
5. 架构选型：实时为主且历史可重放用 Kappa，批流并重用 Lambda，组织大了再考虑 Mesh
6. 湖仓分层用 Medallion（Bronze/Silver/Gold），与 ODS/DWD/DWS 思想对齐
7. 所有管道记录水位线/位点，保证断点续跑和可重放

### 踩坑记录

```text
坑 1：增量同步丢了更新事件导致数据陈旧
结论：目标表数据迟迟不更新，源已改目标还是旧值。
原因：只按 update_time 抽增量，漏了「只更新未插入」的记录或水位线推进错误。
解法：优先用 CDC 捕获全部增删改，水位线取「本批最大时间」而非当前时间。

坑 2：非幂等 upsert 导致重复同步后数据翻倍
结论：重跑一次任务，目标表度量值变成两倍。
原因：增量写入用 INSERT 而非 MERGE，重复数据直接追加。
解法：统一用主键 MERGE/UPSERT，保证幂等，重复执行结果一致。

坑 3：Lambda 双写导致批流口径不一致
结论：实时大盘和离线报表对同一个指标算出两个数。
原因：批处理和流处理各写一套逻辑，口径/边界/时区不一致。
解法：抽公共指标定义，批流共用同一套计算规则，或改用 Kappa 消除双写。

坑 4：ELT 原始数据无治理成数据沼泽
结论：原始层堆积海量垃圾数据，存储暴涨、无人能懂。
原因：先落地后转换但没做分层、保留期、权限治理。
解法：Bronze 层设保留期和访问控制，定期归档，配合元数据目录管理。

坑 5：数据校验只在加载时做，忽略漂移
结论：同步时对账通过，几天后源和目标悄悄不一致。
原因：源数据后续被修改/删除，目标未感知，校验是一次性的。
解法：校验做成周期性任务（日/周），配合 CDC 持续追平，漂移自动修复。
```
