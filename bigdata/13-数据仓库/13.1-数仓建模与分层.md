## 概述

数仓建模解决的核心问题：把面向「事务处理」的源数据，重构成面向「分析查询」的结构。它分两层工作——分层（把数据按加工粒度组织成 ODS/DWD/DWS/ADS 等层）和建模（用星型/雪花模型组织事实与维度）。好的建模让分析师写查询简单、让数据口径统一、让加工链路可维护。这是离线数仓和实时数仓共同的方法论基础。

```text
数仓建模的核心目标：
1. 口径统一 —— 同一指标只有一个定义，避免各部门各算各的
2. 查询简单 —— 维度建模后分析师用简单 JOIN 即可取数
3. 链路清晰 —— 分层明确数据流向，问题可追溯、可复用
4. 适应变化 —— 维度缓慢变化可回溯，历史数据不丢失
5. 性能可控 —— 宽表 + 预聚合，把复杂计算前移到离线层
```

```text
数仓分层（ODS -> DWD -> DWS -> ADS）：
ODS 操作数据层 —— 贴源存储，保留原始粒度，只做清洗不做加工
DWD 明细数据层 —— 数据清洗 + 维度退化 + 事实对齐，统一口径
DWS 汇总数据层 —— 按主题轻度汇总（日/周粒度），面向通用分析
ADS 应用数据层 —— 面向具体报表/产品的结果表，可直接取数
```

## OLTP 与 OLAP

OLTP（联机事务处理）是业务系统的数据库——面向高并发、低延迟的单条记录增删改查，强调事务一致性（ACID），表结构高度规范化以减少冗余；OLAP（联机分析处理）是数仓——面向大批量数据的复杂查询和聚合分析，强调读吞吐和历史回溯，表结构反规范化以换取查询性能。两者优化目标相反，这是数仓必须与业务库分离的根本原因。

```text
OLTP 与 OLAP 对比：
1. 用户 —— OLTP 面向业务操作（下单、转账），OLAP 面向分析（报表、决策）
2. 操作 —— OLTP 单条增删改查，OLAP 大批量扫描聚合
3. 一致性 —— OLTP 强事务 ACID，OLAP 最终一致、允许回补
4. 建模 —— OLTP 3NF 规范化，OLAP 星型/雪花反规范化
5. 规模 —— OLTP GB 级、毫秒延迟，OLAP PB 级、秒级响应
```

## 数仓分层：ODS-DWD-DWS-ADS

分层是数仓最通用的组织方式（阿里 OneData 体系推广了这套命名）。ODS 贴源存储、保持原始粒度；DWD 做清洗、统一口径、维度退化，是「明细事实」层；DWS 按主题做轻度汇总，是「宽表」层；ADS 面向具体应用出结果。每层职责单一，上层只依赖直接下层，避免跨层依赖导致的链路混乱。

```text
分层职责与依赖：
1. ODS —— 贴源，字段尽量与源一致，加分区（dt）和入库时间戳
2. DWD —— 清洗（去重/补缺/格式统一）+ 维度关联退化 + 口径统一
3. DWS —— 主题宽表，按天/用户/商品等维度预聚合，服务 80% 常规查询
4. ADS —— 报表/看板/接口的最终结果表，粒度与展示一一对应
5. 依赖原则 —— 严格单向依赖，禁止 ADS 反向读 ODS 或跨两层跳读
```

```sql
-- 分层示例：订单主题从 ODS 到 ADS
-- ODS：贴源，保留原始字段
CREATE TABLE ods_order (
    order_id STRING, user_id STRING, amount DECIMAL(10,2),
    status STRING, created_at STRING, dt STRING
);

-- DWD：清洗 + 类型规范化，统一口径（status 转标准枚举）
CREATE TABLE dwd_order_detail AS
SELECT CAST(order_id AS BIGINT) AS order_id,
       CAST(user_id AS BIGINT) AS user_id,
       amount,
       CASE WHEN status IN ('paid','shipped') THEN 'paid'
            WHEN status = 'refunded' THEN 'refunded' END AS status,
       CAST(created_at AS TIMESTAMP) AS created_at,
       dt
FROM ods_order
WHERE dt = '${bizdate}' AND order_id IS NOT NULL;

-- DWS：按用户按天汇总
CREATE TABLE dws_user_order_1d AS
SELECT user_id, dt,
       COUNT(*) AS order_cnt,
       SUM(amount) AS gmv
FROM dwd_order_detail
WHERE dt = '${bizdate}'
GROUP BY user_id, dt;
```

## 数据集市

数据集市（Data Mart）是面向特定业务部门或主题的子集数仓，如「市场部集市」「销售集市」。它从企业级数仓（DW）的 DWS/ADS 层抽取，针对一个部门的分析需求裁剪字段和粒度。数据集市解决「大而全的数仓难用」的问题——让每个团队只看到自己关心的、口径已经对齐的数据。

```text
数据集市要点：
1. 面向主题 —— 一个集市对应一个业务域（销售、库存、营销）
2. 依赖数仓 —— 从 DW 统一出口取数，不直接连业务库
3. 独立与共享 —— 独立存储和权限，共享统一口径和维度
4. 两种模式 —— 独立型（从 DW 抽取重建）与从属型（DW 里的逻辑视图/分区）
```

## 星型模型与雪花模型

星型模型是维度建模的经典形态：一个中心事实表，周围一圈维度表，每个维度表只与事实表关联（形似星）。雪花模型在星型基础上把维度表再规范化，拆成多层（如「商品维度」拆出「品类维度」）。星型查询简单、性能好，是默认选择；雪花节省存储、维度更规范，但查询要更多 JOIN。

```text
星型 vs 雪花：
1. 结构 —— 星型维度表单层，雪花维度表多层规范化
2. JOIN —— 星型 JOIN 少、查询快，雪花 JOIN 多、稍慢
3. 冗余 —— 星型维度表有冗余（如品类名重复存），雪花无冗余
4. 维护 —— 星型维度宽表维护简单，雪花层级更新需级联
5. 选择 —— 数仓默认星型；维度层级复杂且变更频繁时局部雪花
```

```text
星型模型（订单主题）：
         dim_user（用户维）
              |
dim_date（日期维）— fact_order（事实） — dim_product（商品维）
              |
        dim_store（门店维）

雪花模型：dim_product 再拆出 dim_category（品类维）
fact_order — dim_product — dim_category
```

## 事实表与维度表

事实表记录「发生了什么事」——可度量的业务事件（一笔订单、一次点击），特点是行数巨大、持续增长、包含度量值（金额/数量）和一堆维度外键。维度表描述「谁、什么、何时、何地」——业务实体的属性（用户、商品、时间），特点是行数相对少、变化慢、包含描述性文本。事实表通过外键引用维度表，两者 JOIN 完成分析。

```text
事实表与维度表要点：
1. 事实表 —— 度量值（可加/半可加/不可加）+ 维度外键，主键常是维度外键组合
2. 维度表 —— 代理键 + 业务键 + 描述属性，主键是代理键（surrogate key）
3. 粒度 —— 事实表粒度（一行代表什么）是建模第一决策，粒度定了口径才定
4. 事实类型 —— 事务事实（每笔交易）、周期快照事实（每日余额）、累积快照事实（订单生命周期）
```

```sql
-- 事实表（事务型）
CREATE TABLE fact_order (
    order_id BIGINT,       -- 业务键
    user_key BIGINT,       -- 维度代理键
    product_key BIGINT,
    date_key BIGINT,
    amount DECIMAL(10,2),  -- 可加度量
    quantity INT           -- 可加度量
);

-- 维度表
CREATE TABLE dim_user (
    user_key BIGINT,       -- 代理键（无业务含义，自增）
    user_id BIGINT,        -- 业务键
    name STRING,
    city STRING,
    register_date DATE
);
```

## 退化维与公共维

退化维（Degenerate Dimension）是「退化进事实表里的维度」——那些只有标识、没有属性描述的维度（如订单号、发票号），保留在事实表中而不单独建维度表。公共维（Conformed Dimension）是跨事实表共享的一致维度（如「日期维」「用户维」），多个事实表引用同一个维度，保证跨主题分析时维度口径一致。

```text
退化维与公共维要点：
1. 退化维 —— 无属性可描述（订单号只有个 ID），建维度表无意义，直接留事实表
2. 公共维 —— 多个事实表共享，是全仓口径统一的基石（如统一日期维）
3. 一致维度 —— 公共维的关键：维度的属性、取值、编码全仓一致
4. 慢变维 —— 公共维常配 SCD 策略处理属性变化（见 13.2-维度建模与缓慢变化维）
```

## 应用场景实战

### 场景一：设计一个电商订单主题的星型模型

```sql
-- 维度表
CREATE TABLE dim_user (
    user_key BIGINT, user_id BIGINT, name STRING,
    city STRING, register_date DATE
);
CREATE TABLE dim_product (
    product_key BIGINT, product_id BIGINT, product_name STRING,
    category STRING, price DECIMAL(10,2)
);
CREATE TABLE dim_date (
    date_key BIGINT, full_date DATE, year INT, month INT, day INT, week INT
);

-- 事实表：一笔订单一行，引用各维度代理键
CREATE TABLE fact_order (
    order_id BIGINT,           -- 退化维
    user_key BIGINT,           -- -> dim_user
    product_key BIGINT,        -- -> dim_product
    date_key BIGINT,           -- -> dim_date
    amount DECIMAL(10,2),
    quantity INT
);

-- 分析查询：各城市各品类销售额
SELECT u.city, p.category, SUM(f.amount) AS sales
FROM fact_order f
JOIN dim_user u ON f.user_key = u.user_key
JOIN dim_product p ON f.product_key = p.product_key
JOIN dim_date d ON f.date_key = d.date_key
WHERE d.year = 2024
GROUP BY u.city, p.category;
```

### 场景二：从业务库同步到分层数仓

```text
业务 MySQL（订单库、用户库）
        |
        |  全量 + 增量（binlog CDC）
        v
ODS 层（ods_order / ods_user，贴源，按 dt 分区）
        |
        |  清洗 + 维度退化 + 口径统一
        v
DWD 层（dwd_order_detail，status 标准化、字段类型统一）
        |
        |  主题汇总：按 用户 x 天 聚合
        v
DWS 层（dws_user_order_1d，订单数 / GMV 等指标）
        |
        |  报表口径裁剪
        v
ADS 层（ads_user_value_report，直接供 BI 报表）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 建模前先定事实表粒度，粒度决定一切，粒度错了后面全错
2. 默认用星型模型，维度层级复杂再考虑局部雪花
3. 事实表用代理键关联维度，业务键单独保留
4. 公共维全仓统一（日期维、用户维），避免各主题口径打架
5. 分层严格单向依赖，禁止跳层和反向依赖
6. ODS 贴源不加工，DWD 只清洗不改业务含义
7. 事实表分区按日期（dt），大表必须分区

### 踩坑记录

```text
坑 1：事实表粒度含糊
结论：同一张表一会一行一单、一会一行一单商品，指标怎么算都不对。
原因：建模时没明确「一行代表什么」，后期混入不同粒度的数据。
解法：先写清粒度声明，凡不同粒度的事件拆不同事实表。

坑 2：维度表用业务键当主键
结论：维度更新后历史事实对不上，无法追溯。
原因：业务键可能被复用/变化，直接当主键无法表达维度变更历史。
解法：用无业务含义的代理键（surrogate key）做主键，业务键存属性列。

坑 3：公共维没统一导致跨主题对不上
结论：销售报表和用户分析里的「城市」口径不一致，总数对不齐。
原因：各主题各自建了维表，取值/编码/更新时间不同。
解法：建全仓统一公共维（日期维、用户维），各事实表强制引用。

坑 4：ADS 层直接读 ODS 绕过中间层
结论：口径不一致，同一指标多处实现，改一处漏一处。
原因：图省事跨层取数，破坏了分层依赖原则。
解法：强制依赖规范，ADS 只读 DWS/DWD，用工具做血缘校验。
```
