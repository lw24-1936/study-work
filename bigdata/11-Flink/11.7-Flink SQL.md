## 概述

Flink SQL 是构建在 Flink 流批统一引擎之上的声明式 SQL 层，让用户用熟悉的 SQL 语法编写流处理与批处理作业。它的核心思想是把「无界的流」抽象成「不断变化的动态表」，把流的每条记录看成表的一次插入或更新，从而用关系代数的思维表达流计算。Flink SQL 屏蔽了 DataStream API 的底层细节，大幅降低实时计算的开发门槛。

```text
Flink SQL 的核心机制：
1. 流表二元性 —— 流可以看成动态表，动态表的变更日志可以看成流
2. 动态表 —— 持续插入、更新、删除的表，是流计算的关系抽象
3. 变更日志 —— 用 +I/-U/+U/-D 标记每行变更，驱动下游更新
4. 统一 —— 同一套 SQL 既能跑批也能跑流，无需改代码
```

```sql
-- Flink SQL 一条流式聚合 SQL
SELECT
    TUMBLE_START(ts, INTERVAL '1' MINUTE) AS win_start,
    user_id,
    COUNT(*) AS cnt
FROM clicks
GROUP BY TUMBLE(ts, INTERVAL '1' MINUTE), user_id;
```

## Dynamic Table

动态表（Dynamic Table）是 Flink SQL 最核心的抽象：它是随时间不断变化的表，流上的每一条记录都是对这张表的一次修改（插入、更新或删除）。对动态表执行连续查询（Continuous Query），会得到一张新的动态表，而这张新表的变更日志就是查询的输出流。理解了「流即表」的二元性，就能理解为什么一条 SQL 能同时表达批处理和流处理。

```text
动态表要点：
1. 本质 —— 流上每条记录 = 动态表的一次 Insert/Update/Delete
2. 连续查询 —— 对动态表不断求值，输出结果表的变更流
3. 静态表特例 —— 批处理的有限表是动态表的特例（无后续变更）
4. 转换 —— 动态表的 changelog 转成流，就是输出
```

```sql
-- 把 Kafka 订单流定义成动态表
CREATE TABLE orders (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10, 2),
    ts         TIMESTAMP(3),
    WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH (
    'connector' = 'kafka',
    'topic' = 'orders',
    'properties.bootstrap.servers' = 'localhost:9092',
    'format' = 'json'
);

-- 对动态表做连续聚合，输出结果是新的动态表
SELECT user_id, SUM(amount) AS total_amount
FROM orders
GROUP BY user_id;
```

## Changelog

变更日志（Changelog）描述动态表的变更流，它用 RowKind 标记每一行是哪种变更：+I（插入）、-U（更新前值）、+U（更新后值）、-D（删除）。聚合、去重、双流 join 等算子产生的都是带 changelog 语义的结果流。当结果要写入 Kafka 等外部系统时，需要 upsert 模式的连接器（如 upsert-kafka）把 changelog 转成可幂等消费的消息，否则下游会拿到重复数据。

```text
Changelog 要点：
1. RowKind —— +I 插入 / -U 更新前 / +U 更新后 / -D 删除
2. 产生来源 —— 聚合、窗口、去重、双流 join、维表 join
3. 下游消费 —— upsert-kafka 按主键输出 insert/update/delete 消息
4. 注意 —— 普通 append-only 连接器接不下带更新的 changelog
```

```sql
-- 结果表用 upsert-kafka 承载 changelog
CREATE TABLE user_total (
    user_id      BIGINT,
    total_amount DECIMAL(10, 2),
    PRIMARY KEY (user_id) NOT ENFORCED
) WITH (
    'connector' = 'upsert-kafka',
    'topic' = 'user-total',
    'properties.bootstrap.servers' = 'localhost:9092',
    'key.format' = 'json',
    'value.format' = 'json'
);

-- 聚合产生 changelog，按主键 upsert 到 Kafka
INSERT INTO user_total
SELECT user_id, SUM(amount)
FROM orders
GROUP BY user_id;
```

## Catalog

Catalog（元数据目录）是 Flink 管理元数据（表、数据库、视图、函数）的仓库，作用类似关系数据库里的 catalog/schema。Flink 内置内存 Catalog（GenericInMemoryCatalog），也支持 Hive Catalog、JDBC Catalog、自定义 Catalog。有了 Catalog，建表语句可以复用、统一管理，SQL 里也能用 `catalog.db.table` 三级命名引用表，是工程化开发的基础设施。

```text
Catalog 要点：
1. 作用 —— 集中管理表、库、视图、函数的元数据
2. 类型 —— 内存 / Hive / JDBC / 自定义
3. 三级命名 —— catalog.database.table 定位表
4. 优势 —— 元数据复用、统一授权、跨作业共享表定义
```

```sql
-- 创建并使用 Hive Catalog
CREATE CATALOG hive_catalog WITH (
    'type' = 'hive',
    'hive-conf-dir' = '/etc/hive/conf',
    'default-database' = 'ods'
);

USE CATALOG hive_catalog;
USE ods;

-- 三级命名引用表
SELECT * FROM hive_catalog.ods.orders LIMIT 10;

-- 列出当前 catalog 的表
SHOW TABLES;
```

## Connector

连接器（Connector）负责把动态表接到外部系统——数据从哪里读、写到哪里，都由连接器决定。Flink 提供 Kafka、JDBC、Filesystem、HBase、Elasticsearch、数据湖（Iceberg/Hudi）等大量连接器，通过建表语句的 WITH 子句配置。连接器与序列化格式（json/csv/avro/debezium-json 等）是解耦的：连接器管「往哪读写」，格式管「数据怎么编解码」。

```text
Connector 要点：
1. 职责 —— 表的 source/sink 与外部系统对接
2. 配置 —— WITH 子句指定 connector 类型和参数
3. 格式解耦 —— format 与 connector 分离，自由组合
4. 常见 —— Kafka / JDBC / Filesystem / HBase / ES / Iceberg
```

```sql
-- JDBC 连接器：读写 MySQL
CREATE TABLE mysql_users (
    user_id   BIGINT,
    user_name STRING,
    city      STRING,
    PRIMARY KEY (user_id) NOT ENFORCED
) WITH (
    'connector' = 'jdbc',
    'url' = 'jdbc:mysql://localhost:3306/shop',
    'table-name' = 'users',
    'username' = 'root',
    'password' = 'password'
);

-- Filesystem 连接器：写 Parquet 到 HDFS
CREATE TABLE fs_orders (
    order_id BIGINT,
    amount   DECIMAL(10, 2)
) WITH (
    'connector' = 'filesystem',
    'path' = 'hdfs://namenode:8020/warehouse/orders',
    'format' = 'parquet'
);
```

## Temporal Join

时态连接（Temporal Join）把流与「版本化维表」按事件时间进行关联：以事件发生的时刻为准，取该时刻维表里那一行主键对应的最新版本。它解决的是「订单事件要和下单当时的最新商品信息关联，而不是现在的商品信息」这一历史正确性问题。语法上使用 `FOR SYSTEM_TIME AS OF`，维表必须是版本表（有主键 + 时间属性，通常是 CDC 出来的 changelog 流）。

```text
Temporal Join 要点：
1. 语义 —— 按事件时间取维表历史版本，保证历史正确
2. 维表要求 —— 版本表：主键 + 时间属性（CDC 流天然具备）
3. 语法 —— FOR SYSTEM_TIME AS OF t.proc_time（事件时间或处理时间）
4. 对比 —— 相比 Lookup Join，能还原历史时点的维表状态
```

```sql
-- 版本化维表（CDC 流，带主键和时间属性）
CREATE TABLE products (
    product_id   BIGINT,
    name         STRING,
    price        DECIMAL(10, 2),
    update_ts    TIMESTAMP(3),
    PRIMARY KEY (product_id) NOT ENFORCED,
    WATERMARK FOR update_ts AS update_ts - INTERVAL '5' SECOND
) WITH (
    'connector' = 'kafka',
    'topic' = 'products',
    'properties.bootstrap.servers' = 'localhost:9092',
    'format' = 'debezium-json'
);

-- 订单流按事件时间关联下单时的商品信息
SELECT
    o.order_id,
    o.ts,
    p.name,
    p.price
FROM orders AS o
LEFT JOIN products FOR SYSTEM_TIME AS OF o.ts AS p
    ON o.product_id = p.product_id;
```

## Interval Join

区间连接（Interval Join）把两条流按事件时间在一定时间区间内进行匹配，例如「订单流与支付流在订单生成后 30 分钟内关联」。它依赖两条流都定义了水位线，Flink 据此清理过期状态。区间连接的下界可以防止「未来数据」被错误匹配，上界决定状态需要保留多久，因此要按业务语义设置合理区间，避免状态无限膨胀。

```text
Interval Join 要点：
1. 语义 —— 两条流按事件时间在 [下界, 上界] 区间内匹配
2. 前提 —— 两条流都要有水位线（watermark）
3. 下界 —— 过滤过早的匹配（如支付早于订单则忽略）
4. 上界 —— 决定状态保留时长，过大会撑爆状态
```

```sql
-- 订单流与支付流在 30 分钟内关联
SELECT
    o.order_id,
    p.pay_id,
    p.pay_amount
FROM orders o, payments p
WHERE o.order_id = p.order_id
  AND p.ts BETWEEN o.ts AND o.ts + INTERVAL '30' MINUTE;
```

## Lookup Join

维表查询连接（Lookup Join）把流与「外部数据库维表」（如 MySQL、HBase）按当前处理时间即时查询关联：每条流记录都去外部维表查一次，取维表的「当前」值。它不维护历史版本，适合维表数据保存在外部数据库、且对历史正确性要求不高的场景。由于每条记录都要查一次外部库，通常配合缓存（cache）降低对维表的压力。

```text
Lookup Join 要点：
1. 语义 —— 按处理时间查询外部维表的当前值
2. 适用 —— 维表在外部 DB（MySQL/HBase），无需历史版本
3. 性能 —— 每条记录一次查询，必须配缓存
4. 对比 —— Temporal Join 还原历史，Lookup Join 只取当下
```

```sql
-- 订单流 lookup 关联 MySQL 用户维表（带缓存）
SELECT
    o.order_id,
    u.user_name,
    u.city
FROM orders AS o
LEFT JOIN mysql_users FOR SYSTEM_TIME AS OF o.proc_time AS u
    ON o.user_id = u.user_id;

-- 维表配置缓存（lookup.cache）
-- 'lookup.cache' = 'PARTIAL'
-- 'lookup.max-retries' = '3'
```

## 应用场景实战

### 场景一：订单实时大宽表

```text
目标：把订单流、用户维表、商品维表、支付流关联成一张实时大宽表
链路：Kafka 订单流 → Temporal Join 商品维表 → Lookup Join 用户维表
      → Interval Join 支付流 → 写入 Kafka/ClickHouse
```

```sql
-- 1. 订单流关联商品维表（事件时间，历史正确）
CREATE VIEW order_with_product AS
SELECT o.order_id, o.user_id, o.product_id, p.name AS product_name,
       p.price, o.ts
FROM orders AS o
LEFT JOIN products FOR SYSTEM_TIME AS OF o.ts AS p
    ON o.product_id = p.product_id;

-- 2. 再关联支付流（区间连接，30 分钟内）
SELECT
    op.order_id,
    op.user_id,
    op.product_name,
    op.price,
    py.pay_amount,
    py.pay_ts
FROM order_with_product AS op
LEFT JOIN payments AS py
    ON op.order_id = py.order_id
   AND py.ts BETWEEN op.ts AND op.ts + INTERVAL '30' MINUTE;
```

### 场景二：实时指标聚合到结果表

```text
目标：每分钟统计各商品销售额，实时写入下游供大屏/报表消费
链路：Kafka 订单流 → 动态表 → 滚动窗口聚合 → upsert-kafka 结果表
```

```sql
-- 结果表（upsert-kafka 承载聚合 changelog）
CREATE TABLE product_sales (
    window_start TIMESTAMP(3),
    product_id   BIGINT,
    sales_amount DECIMAL(10, 2),
    PRIMARY KEY (window_start, product_id) NOT ENFORCED
) WITH (
    'connector' = 'upsert-kafka',
    'topic' = 'product-sales',
    'properties.bootstrap.servers' = 'localhost:9092',
    'key.format' = 'json',
    'value.format' = 'json'
);

-- 滚动窗口聚合，实时写入
INSERT INTO product_sales
SELECT
    TUMBLE_START(ts, INTERVAL '1' MINUTE) AS window_start,
    product_id,
    SUM(price) AS sales_amount
FROM orders
GROUP BY TUMBLE(ts, INTERVAL '1' MINUTE), product_id;
```

## 最佳实践与踩坑记录

### 最佳实践

1. 双流关联前一定定义水位线，Interval Join 靠水位线清理过期状态
2. 维表关联优先用 Temporal Join 还原历史，Lookup Join 只用于外部维表
3. Lookup Join 必须开启缓存，并设置合理的 TTL 和最大重试次数
4. 结果表承载 changelog 时用 upsert-kafka，并声明主键
5. 用 Catalog 统一管理表元数据，避免建表语句散落在各作业里
6. Interval Join 上界按业务 SLA 设置（如支付窗口 30 分钟），不要无脑放大
7. 生产环境用 Hive/Iceberg Catalog 持久化元数据，不用内存 Catalog

### 踩坑记录

```text
坑 1：Interval Join 的两条流没有水位线
结论：作业状态无限增长，最终 OOM 崩溃。
原因：没有水位线就无法判断状态何时过期，无法清理。
解法：两条流都定义 WATERMARK，且水位线延迟合理。

坑 2：聚合结果写入普通 Kafka 连接器产生重复数据
结论：下游收到重复的聚合结果，指标算错。
原因：聚合输出是 changelog，普通 append 连接器会重发多条。
解法：改用 upsert-kafka 并声明主键。

坑 3：Temporal Join 的维表不是版本表
结论：报错「非版本表不支持 FOR SYSTEM_TIME AS OF」。
原因：Temporal Join 要求维表有主键和时间属性（changelog 源）。
解法：维表用 CDC 源（debezium-json）建表，含 PRIMARY KEY 和时间字段。

坑 4：Lookup Join 没开缓存导致维表被打爆
结论：维表数据库 QPS 飙升，甚至拖垮业务库。
原因：每条流记录都实时查询一次外部维表。
解法：配置 lookup.cache=PARTIAL 并设置合理的 cache TTL。

坑 5：水位线延迟设得过大导致 join 迟迟不出结果
结论：Interval Join 输出严重滞后。
原因：水位线延迟越大，等待时间越长，状态保留也越多。
解法：按业务可接受的乱序程度设水位线，如 5~10 秒。
```
