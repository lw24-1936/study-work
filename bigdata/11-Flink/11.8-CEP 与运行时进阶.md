## 概述

CEP（Complex Event Processing，复杂事件处理）用于从事件流中识别有特定时序关系的模式序列，如「登录后 5 分钟内连续 3 次密码错误」。Flink CEP 提供基于 Pattern API 的模式匹配能力，是实时风控、异常检测的核心工具。而 Backpressure、Network Buffer、Chaining、Slot Sharing 则是 Flink 运行时保证高性能与稳定性的关键机制，理解它们才能真正调优 Flink 作业。

```text
本章覆盖的两个维度：
1. CEP —— 用 Pattern API 表达时序模式，做复杂事件匹配
2. 运行时 —— 背压、网络缓冲、算子链、槽共享四大运行时机制
3. 源码 —— 从 JobGraph 到 ExecutionGraph 的作业执行流程
```

```java
// 一段 Flink CEP 模式匹配的骨架
Pattern<LoginEvent, ?> pattern = Pattern.<LoginEvent>begin("fail")
    .where(e -> e.type.equals("fail"))
    .times(3)
    .within(Time.minutes(5));

PatternStream<LoginEvent> patternStream = CEP.pattern(stream, pattern);
patternStream.select(new PatternSelectFunction<>() {
    @Override
    public String select(Map<String, List<LoginEvent>> pattern) {
        return "连续 3 次登录失败: " + pattern.get("fail");
    }
});
```

## CEP

CEP 让用户在事件流上定义「模式」——由若干条件加上时序约束（先后、次数、时间窗口）组成，一旦事件序列满足模式就触发告警或输出。Flink CEP 的 Pattern API 支持 begin/next/followedBy/where/times/within 等算子，底层用 NFA（非确定有限自动机）匹配状态机。它擅长风控（盗刷、撞库）、异常检测（设备故障）、业务流程监控等场景。

```text
CEP 要点：
1. 模式 —— begin 起始 + where 条件 + times 次数 + within 时间窗
2. 时序关系 —— next（严格相邻）/ followedBy（非严格先后）
3. 底层 —— NFA 状态机逐事件匹配，超时事件可侧输出
4. 应用 —— 风控、异常检测、复杂业务流程监控
```

```java
// 检测「连续 3 次登录失败」的完整示例
DataStream<LoginEvent> logins = env.fromElements(
    new LoginEvent("u1", "fail", 1000L),
    new LoginEvent("u1", "fail", 2000L),
    new LoginEvent("u1", "fail", 3000L),
    new LoginEvent("u1", "success", 4000L)
).keyBy(LoginEvent::getUserId);

Pattern<LoginEvent, ?> pattern = Pattern.<LoginEvent>begin("fail")
    .where(e -> "fail".equals(e.getType()))
    .times(3)
    .within(Time.minutes(5));

CEP.pattern(logins, pattern)
   .select(new PatternSelectFunction<LoginEvent, String>() {
       @Override
       public String select(Map<String, List<LoginEvent>> matches) {
           return matches.get("fail").get(0).getUserId() + " 连续 3 次登录失败";
       }
   })
   .print();
```

## Backpressure

背压（Backpressure）是流处理系统里「下游处理不过来时反向传导给上游减速」的机制。Flink 靠「信用制（credit-based）」网络栈天然支持背压：下游算子向数据源发放信用（credit），上游只有在有信用额度时才发送数据，下游消费慢则信用发放慢，上游自然减速。背压是 Flink 稳定性的保障，但长期高背压往往意味着算子倾斜或资源不足，需要定位优化。

```text
Backpressure 要点：
1. 本质 —— 下游慢 → 上游减速，防止数据在内存/网络中堆积
2. 机制 —— 信用制：下游发 credit，上游按额度发送
3. 定位 —— Web UI 看 backpressured 状态（OK/LOW/HIGH）
4. 根因 —— 通常是数据倾斜、状态 IO 慢、资源不足
```

```shell
# 通过 Flink REST API 查看作业背压状态
curl "http://localhost:8081/jobs/<job-id>/vertices/<vertex-id>/backpressure"
```

## Network Buffer

网络缓冲（Network Buffer）是 Flink 任务间传输数据的缓冲区，属于网络栈的一部分。数据在 task 之间通过缓冲池（BufferPool）中的 buffer 传递，每个 buffer 默认 32 KB。合理的 buffer 数量直接决定吞吐量和内存占用：过多占用堆内存，过少则吞吐下降。背压的信用机制正是建立在 buffer 之上的——有多少空 buffer 就有多少 credit。

```text
Network Buffer 要点：
1. 作用 —— task 间数据交换的缓冲，默认每个 32 KB
2. 管理 —— BufferPool 按需申请、用完回收
3. 参数 —— taskmanager.memory.network 控制网络内存总量
4. 关系 —— 信用额度 = 可用的空 buffer 数量
```

```yaml
# flink-conf.yaml 网络内存配置示例
taskmanager.memory.network.min: 64mb
taskmanager.memory.network.max: 1gb
taskmanager.memory.network.fraction: 0.1
```

## Chaining

算子链（Operator Chaining）是 Flink 把「数据只在 task 内传递、无跨网络 shuffle」的相邻算子合并成一个 task 的优化。链内的算子在同一线程内用对象引用直接传递数据，省去序列化、反序列化和网络开销，大幅提升性能。只有满足「并行度相同、单向下游、无 shuffle」等条件的算子才能被 chain，可以用 disableChaining 强制打断。

```text
Chaining 要点：
1. 作用 —— 把无 shuffle 的相邻算子合并成一个 task
2. 收益 —— 省序列化/网络开销，同一线程内直接传对象
3. 条件 —— 并行度一致、单向下游、无 rebalance/keyBy
4. 控制 —— startNewChain / disableChaining / 全局关闭
```

```java
// 算子链的开启与打断
DataStream<String> mapped = source
    .map(x -> x + "_mapped")       // 与 source chain 在一起
    .map(x -> x.toUpperCase())
    .disableChaining()             // 打断，后续算子另起 task
    .keyBy(s -> s)
    .sum(0);

// 全局关闭算子链
env.disableOperatorChaining();
```

## Slot Sharing

槽共享（Slot Sharing）允许同一作业中「不同算子」的任务共享同一个 TaskManager 的 slot，只要它们不在同一个算子实例上。这样即使某个算子并行度很高、另一个很低，也能均匀分配到 slot 里，提高资源利用率。默认开启（slotSharingGroup 为 "default"），可以通过 slotSharingGroup 把算子分到不同共享组，实现资源隔离。

```text
Slot Sharing 要点：
1. 作用 —— 不同算子共享 slot，提高资源利用率
2. 默认 —— 全部算子一个共享组，均匀摊到各 slot
3. 隔离 —— slotSharingGroup 自定义分组，隔离资源
4. 注意 —— slot 数 = 作业最大并行度，不是各算子并行度之和
```

```java
// 把算子分到不同 slot 共享组做资源隔离
DataStream<String> heavy = source
    .map(x -> expensiveOp(x))
    .slotSharingGroup("heavy");

DataStream<String> light = source
    .map(x -> cheapOp(x))
    .slotSharingGroup("light");
```

## Flink 源码

Flink 源码层面，一个作业从提交到运行要经历「StreamGraph → JobGraph → ExecutionGraph → 物理执行」的转换。StreamGraph 是用户 API 层的数据流图，JobGraph 是优化后（算子链合并）的作业图，ExecutionGraph 是调度层的并行执行图，最终映射到 TaskManager 上真实运行的 Task。理解这条转换链路，就能理解算子链、槽分配、故障恢复到底发生在哪一层。

```text
Flink 源码要点：
1. StreamGraph —— API 层 DAG，每个算子一个节点
2. JobGraph —— 优化后 DAG，算子链合并成 JobVertex
3. ExecutionGraph —— 调度层，JobVertex 展开成并行子任务
4. 执行 —— ExecutionVertex 映射到 TaskManager 的 slot 上跑 Task
```

```java
// 从代码角度理解图的生成（伪代码，展示转换流程）
// 1. StreamGraph 由 StreamExecutionEnvironment 生成
StreamGraph streamGraph = streamEnv.getStreamGraph();

// 2. JobGraph 由 StreamingJobGraphGenerator 生成（含算子链合并）
JobGraph jobGraph = StreamingJobGraphGenerator
    .createJobGraph(streamGraph);

// 3. 提交后 JobMaster 把 JobGraph 转成 ExecutionGraph
// ExecutionGraph 中 JobVertex 按并行度展开为 ExecutionVertex
```

## 应用场景实战

### 场景一：实时风控——异常登录检测

```text
目标：检测同一用户 5 分钟内连续 3 次登录失败并告警
链路：Kafka 登录事件流 → keyBy 用户 → CEP 模式匹配 → 告警输出
```

```java
// 完整的风控 CEP 作业
DataStream<LoginEvent> logins = env
    .addSource(new FlinkKafkaConsumer<>("login-events",
        new LoginEventSchema(), props))
    .keyBy(LoginEvent::getUserId);

Pattern<LoginEvent, ?> risk = Pattern.<LoginEvent>begin("fail")
    .where(e -> "fail".equals(e.getType()))
    .times(3)
    .consecutive()
    .within(Time.minutes(5));

CEP.pattern(logins, risk)
   .select((PatternSelectFunction<LoginEvent, Alert>)
       matches -> new Alert(
           matches.get("fail").get(0).getUserId(), "连续登录失败"))
   .addSink(new AlertSink());

env.execute("login-risk-cep");
```

### 场景二：背压定位与算子链调优

```text
目标：定位背压根因并通过调整算子链、slot 共享组优化吞吐
排查：Web UI 定位 backpressured=HIGH 的算子 → 分析是否数据倾斜
```

```shell
# 1. 查看作业各算子背压状态
curl "http://localhost:8081/jobs/<job-id>/vertices/<vertex-id>/backpressure"

# 2. 查看异常算子是否数据倾斜（subtask 数据量不均）
curl "http://localhost:8081/jobs/<job-id>/vertices/<vertex-id>/subtasks/metrics"
```

```text
优化手段：
1. 数据倾斜 —— 加盐打散 key 或两阶段聚合
2. 算子链 —— 把轻量算子与重算子拆开，避免互相拖累
3. slot 共享组 —— 重算子单独分组，避免挤占轻算子资源
4. 网络缓冲 —— 适当调大 taskmanager.memory.network
```

## 最佳实践与踩坑记录

### 最佳实践

1. CEP 模式里用 within 限定时间窗，防止 NFA 状态无限增长
2. 高吞吐场景慎用 CEP，NFA 状态匹配是 CPU 密集操作，先评估成本
3. 生产环境默认开启算子链和 slot 共享，除非有明确隔离需求
4. 定位背压先看是否数据倾斜，而不是盲目加资源
5. 网络内存按作业规模设置，过小导致吞吐瓶颈，过大浪费堆内存
6. 读源码从 StreamGraph→JobGraph→ExecutionGraph 主线入手，不要陷进细节

### 踩坑记录

```text
坑 1：CEP 模式不设 within 导致状态无限增长
结论：NFA 状态越积越多，内存耗尽 OOM。
原因：没有时间窗口，永不超时的事件一直保留在状态机里。
解法：每个模式加 within，并配置超时侧输出（OutputTag）。

坑 2：keyBy 的 key 没有考虑数据倾斜导致背压
结论：某个 subtask 长期 HIGH 背压，吞吐上不去。
原因：热点 key 集中到一个并行实例，处理不过来。
解法：热点 key 加盐打散，或改用两阶段聚合。

坑 3：乱用 disableChaining 导致性能下降
结论：频繁跨网络传输，吞吐大幅下降。
原因：打断算子链后，数据要走序列化和网络栈。
解法：只在需要资源隔离或单独扩并行度时才打断链。

坑 4：slot 数理解错误导致资源浪费
结论：为每个算子都预留了 slot，申请了过多资源。
原因：误以为 slot 数 = 各算子并行度之和。
解法：slot 数 = 作业最大并行度，默认共享组下即可。

坑 5：网络缓冲配置过小导致吞吐瓶颈
结论：高吞吐场景下网络成为瓶颈，CPU 打不满。
原因：network memory 太小，可用 buffer 太少，信用额度不足。
解法：调大 taskmanager.memory.network，并观察吞吐变化。
```
