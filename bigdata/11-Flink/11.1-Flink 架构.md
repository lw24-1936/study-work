## 概述

Flink 是一个分布式流处理引擎，采用主从架构：JobManager 是控制节点，负责作业调度、协调 Checkpoint 与故障恢复；TaskManager 是工作节点，负责执行具体任务并交换数据。用户编写的 DataStream/SQL 程序经过 JobGraph（逻辑图）与 ExecutionGraph（物理图）两级转换，最终以「算子 + 槽位」的形式运行在集群上。理解这套架构是调优并行度、定位反压与故障的基石。

```text
Flink 架构核心：
1. 主从结构 —— JobManager（控制）+ TaskManager（执行）
2. 三级图 —— StreamGraph -> JobGraph -> ExecutionGraph -> 物理执行
3. 资源抽象 —— Slot 是 TaskManager 上的资源单位，算子链共享 Slot
4. 容错 —— JobManager 协调 Checkpoint，TaskManager 上报状态
5. 数据交换 —— 算子间通过网络/内存传输，上下游解耦
```

```text
Flink 运行时进程拓扑（standalone 视角）：
客户端(提交 Jar) -> JobManager(Dispatcher/JobMaster/ResourceManager)
                        |
              +---------+---------+
              |                   |
         TaskManager         TaskManager
         (Slots + Tasks)    (Slots + Tasks)
```

## JobManager

JobManager 是 Flink 集群的「大脑」，一个 Flink 作业对应一个 JobMaster，而 JobManager 进程内还包含 ResourceManager 与 Dispatcher。JobMaster 负责作业级调度（把 ExecutionGraph 的顶点派发到 TaskManager）、协调 Checkpoint/恢复、管理作业生命周期；ResourceManager 负责向集群（YARN/K8s）申请与释放 TaskManager 资源；Dispatcher 负责接收作业提交、拉起 JobMaster 并提供 Web UI。

```text
JobManager 要点：
1. JobMaster —— 单作业调度与 Checkpoint 协调，一个作业一个
2. ResourceManager —— 申请/释放 TaskManager（Slot），对接 YARN/K8s
3. Dispatcher —— 接收提交、启动 JobMaster、暴露 REST 接口与 Web UI
4. 高可用 —— JobManager 可配多实例，靠 ZooKeeper 选主（leader 选举）
5. 故障恢复 —— 从最近 Checkpoint 重启，重新派发 Task
```

```yaml
# flink-conf.yaml 中 JobManager 相关关键配置
jobmanager.rpc.address: localhost          # JobManager RPC 地址
jobmanager.rpc.port: 6123
jobmanager.memory.process.size: 1600m      # JobManager 进程总内存
jobmanager.memory.heap.size: 1024m         # JVM 堆内存
jobmanager.memory.off-heap.size: 128m      # 堆外内存
high-availability: zookeeper               # 高可用模式
high-availability.zookeeper.quorum: zk1:2181,zk2:2181,zk3:2181
```

## TaskManager

TaskManager 是 Flink 的工作节点（Worker），一个进程内可运行多个 Slot，每个 Slot 承载一条算子链（Task）。它负责执行用户算子逻辑、管理本地状态（含 RocksDB）、在算子之间做数据交换（网络传输与本地内存缓冲）、向 JobManager 心跳上报。TaskManager 的数量与每个 TaskManager 的 Slot 数共同决定集群的总并行能力。

```text
TaskManager 要点：
1. 资源容器 —— 一个 JVM 进程，内含内存、CPU、网络等多维资源
2. 多 Slot —— 每个 Slot 是资源子集，可跑一个 Task（算子链）
3. 数据交换 —— 与上下游 TaskManager 通过 Netty 网络栈传输数据
4. 状态存储 —— 管理本地状态后端（Heap/RocksDB）与 Checkpoint 数据
5. 心跳 —— 定期向 JobManager 上报健康与 Slot 状态
```

```yaml
# flink-conf.yaml 中 TaskManager 相关关键配置
taskmanager.memory.process.size: 4096m     # TaskManager 进程总内存
taskmanager.memory.managed.size: 1024m     # 托管内存（给 RocksDB 等）
taskmanager.memory.network.min: 64m        # 网络缓冲最小值
taskmanager.numberOfTaskSlots: 2           # 每个 TaskManager 的 Slot 数
taskmanager.cpu.cores: 2.0                 # 分配的 CPU 核数
```

## Slot

Slot 是 TaskManager 内的资源切分单位，是 Flink 调度的最小粒度。每个 Slot 拥有该 TaskManager 内存与 CPU 的固定份额，同一 TaskManager 内的 Slot 之间内存隔离（但 CPU 按核数共享）。默认 Flink 允许 Slot Sharing：同一作业的不同算子链（只要不在同一算子链上）可以共享一个 Slot，从而让不同算子错峰使用资源，提高利用率。

```text
Slot 要点：
1. 资源单位 —— 一个 Slot 承载一个 Task（一条完整算子链）
2. 数量 —— taskmanager.numberOfTaskSlots 决定每 TM 的 Slot 数
3. Slot Sharing —— 不同算子共享 Slot，默认开启，提升利用率
4. 并行度关系 —— 作业总所需 Slot = 最大并行度（共享组下）
5. 隔离性 —— 内存隔离、CPU 共享，跨 Slot 互不影响
```

```yaml
# 并行度与 Slot 的关系示例
# 作业最大并行度 8，每个 TM 2 个 Slot -> 需要 4 个 TaskManager
parallelism.default: 8
taskmanager.numberOfTaskSlots: 2
```

```java
// 在代码里为不同算子设置并行度（并行度 <= 总 Slot 数）
DataStream<String> stream = env.socketTextStream("localhost", 9999);

stream
    .map(String::toUpperCase).setParallelism(4)   // map 算子并行度 4
    .keyBy(s -> s)                                 // keyBy 之后
    .sum(0).setParallelism(8);                     // 聚合算子并行度 8

// 最终 Slot 需求取决于最大并行度（此例为 8）
```

## Operator

Operator 是 Flink 计算逻辑的最小单元，对应数据流上的一个变换（map、filter、keyBy、window、sink 等）。多个算子若满足「一对一、并行度相同」等条件，会被合并成一条算子链（Operator Chain），作为一个 Task 在同一个线程里执行，省去序列化与网络传输开销。算子通过 StreamGraph 中的边连接，构成完整数据流。

```text
Operator 要点：
1. 种类 —— Source / Transformation / Sink 三大类
2. 算子链 —— 相邻算子满足条件则合并为 Task，减少开销
3. 禁用链 —— disableChaining() 可强制打断算子链
4. 并行度 —— 每个算子可独立设置并行度
5. 状态 —— KeyedState 算子按 key 分区维护状态
```

```java
import org.apache.flink.streaming.api.datastream.DataStream;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;

StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.setParallelism(1);

DataStream<String> text = env.socketTextStream("localhost", 9999);

DataStream<WordCount> counts = text
    .flatMap((String line, Collector<WordCount> out) -> {
        for (String w : line.split(" ")) {
            out.collect(new WordCount(w, 1));
        }
    }).returns(WordCount.class)
    .keyBy(wc -> wc.word)                          // keyBy 打断算子链
    .sum("count");

counts.print();                                    // Sink 算子

env.execute("OperatorDemo");
```

## JobGraph

JobGraph 是 Flink 作业经过客户端优化后、提交给 JobManager 的「逻辑执行图」。它在 StreamGraph 基础上做了算子链合并：把可以链式执行的相邻算子合并成一个 JobVertex（对应一个 Task），并在 JobVertex 之间插入中间结果集（IntermediateDataSet）与数据分发模式。JobGraph 是提交到集群的形态，也是 Checkpoint 协调的基本单位之一。

```text
JobGraph 要点：
1. 来源 —— 由 StreamGraph 优化而来，合并了算子链
2. JobVertex —— 一条算子链对应一个 JobVertex（一个 Task）
3. IntermediateDataSet —— JobVertex 之间的中间数据，带分发模式
4. 分发模式 —— FORWARD / REBALANCE / HASH / BROADCAST 等
5. 序列化 —— JobGraph 会被序列化后发给 JobManager 调度
```

```java
// 查看生成的 JobGraph / 执行计划
// 方式一：在代码里打印执行计划（未执行前）
System.out.println(env.getExecutionPlan());   // 输出 JSON 格式的 StreamGraph

// 方式二：Web UI 的 JobGraph 页可视化查看算子链与 JobVertex
// 观察 map 与 flatMap 是否被合并为一条算子链（一个 JobVertex）

// 强制打断算子链，观察 JobGraph 顶点数变化
counts.disableChaining();   // 把上游算子链打断，形成独立 JobVertex
```

## ExecutionGraph

ExecutionGraph 是 JobManager 上的「物理执行图」，是实际被调度的形态。JobMaster 拿到 JobGraph 后，把每个 JobVertex 按并行度展开成多个 ExecutionVertex（每个对应一个并行子任务），并实例化为可调度、可重试的 Execution，同时注入中间结果分区（IntermediateResultPartition）等物理细节。ExecutionGraph 是调度、Checkpoint、故障恢复（重启 Execution）的载体。

```text
ExecutionGraph 要点：
1. 来源 —— JobMaster 对 JobGraph 展开并行度而来
2. ExecutionVertex —— JobVertex 按并行度展开，一个并行子任务一个
3. Execution —— 一次具体执行尝试，可重试（对应一个 Task 实例）
4. IntermediateResultPartition —— 中间结果分区，对应一次 Shuffle 输出
5. 状态机 —— CREATED -> SCHEDULED -> DEPLOYING -> RUNNING -> FINISHED/FAILED
```

```java
// 并行度如何影响 ExecutionGraph 顶点数量
// 若 JobGraph 有 3 个 JobVertex，并行度分别为 2 / 4 / 2
// 则 ExecutionGraph 有 2 + 4 + 2 = 8 个 ExecutionVertex

StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.setParallelism(4);   // 默认并行度 4

DataStream<String> s = env.fromElements("a", "b", "c", "d");
s.map(String::toUpperCase)      // 并行度 4 -> 4 个 ExecutionVertex
 .keyBy(x -> x)
 .sum(0);                       // 并行度 4 -> 4 个 ExecutionVertex

// 重启策略决定了 Execution 的重试行为
env.setRestartStrategy(
    RestartStrategies.fixedDelayRestart(3, Time.seconds(10)));
```

## 应用场景实战

### 场景一：估算集群 Slot 需求并规划并行度

```yaml
# 场景：实时统计每个用户的订单金额，峰值 QPS 高，需要合理规划资源
# 作业拓扑：Source(1) -> map(并行度 A) -> keyBy -> 聚合(并行度 B) -> Sink(B)
# 结论：Slot Sharing 下，作业所需 Slot = max(A, B)

# flink-conf.yaml 规划示例
parallelism.default: 8            # 默认并行度 8
taskmanager.numberOfTaskSlots: 4 # 每 TM 4 个 Slot
# 需要 TaskManager 数 = ceil(8 / 4) = 2
```

```java
// 代码里对齐并行度与 Slot 规划
StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

DataStream<Order> orders = env
    .addSource(new OrderSource())          // 并行度 1
    .setParallelism(1);

DataStream<Order> enriched = orders
    .map(o -> enrich(o))                    // 并行度 8
    .setParallelism(8);

enriched.keyBy(Order::getUserId)
    .process(new AggProcess())              // 并行度 8（与 map 共享 Slot）
    .setParallelism(8)
    .addSink(new OrderSink());              // 并行度 8

// 因 Slot Sharing，所需 Slot = 8，配 2 个 TM * 4 Slot 即可
env.execute("slot-planning-demo");
```

### 场景二：通过执行计划定位算子链与反压来源

```java
// 打印执行计划，检查算子是否被合理链化
StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.setParallelism(1);

DataStream<String> stream = env.socketTextStream("localhost", 9999);
stream
    .flatMap((String s, Collector<String> out) -> {
        for (String w : s.split(" ")) out.collect(w);
    }).returns(String.class)
    .map(w -> new Tuple2<>(w, 1)).returns(Types.TUPLE(Types.STRING, Types.INT))
    .keyBy(t -> t.f0)
    .sum(1)
    .print();

// 未执行前打印 JSON 执行计划，确认算子链结构
System.out.println(env.getExecutionPlan());
env.execute("plan-demo");

// 运行后：在 Web UI 的「反压」页看哪个算子出现反压（红色），
// 结合 JobGraph 定位是哪个 JobVertex 处理不过来，再针对性调并行度
```

## 最佳实践与踩坑记录

### 最佳实践

1. 并行度按「数据量 + 算子复杂度」评估，最终 Slot 数 = 最大并行度（Slot Sharing 下）
2. 保持默认 Slot Sharing，让不同算子错峰共享资源，提升集群利用率
3. 读作业先看 Web UI 的 JobGraph 与反压页，再决定调哪个算子
4. 高吞吐场景适当调大 taskmanager.memory.network 与 managed 内存
5. 生产必须开启 JobManager 高可用（ZooKeeper/K8s），避免单点故障
6. 能用算子链就用算子链（默认开启），省序列化与网络开销；仅在需隔离时才 disableChaining
7. 重启策略配合 Checkpoint 配置，保证故障可自动恢复

### 踩坑记录

```text
坑 1：并行度大于总 Slot 数导致作业无法调度
结论：作业一直处于 SCHEDULED/未运行，迟迟不启动。
原因：并行度超出集群可用 Slot，资源不足无法派发 Task。
解法：降低并行度或增加 TaskManager / Slot 数。

坑 2：忽略 Slot Sharing 导致资源规划错误
结论：按「所有算子并行度之和」申请资源，严重超配。
原因：默认开启 Slot Sharing，所需 Slot 是最大并行度而非总和。
解法：理解共享机制，按最大并行度规划 Slot 数量。

坑 3：keyBy 前的算子链被误判打断
结论：JobGraph 顶点变多，任务数膨胀、开销增大。
原因：不了解算子链合并条件，误用导致链断裂。
解法：保持默认链化，仅真正需要（如热点算子隔离）才打断。

坑 4：TaskManager 内存配置不合理导致频繁 OOM
结论：Task 运行中反复报内存溢出，作业重启。
原因：托管内存/堆内存给得太小，状态与缓冲撑爆。
解法：按状态大小与吞吐调 taskmanager.memory.process.size 及各分项。

坑 5：网络缓冲不足导致高吞吐下反压
结论：数据流频繁反压，吞吐上不去。
原因：taskmanager.memory.network.min 过小，算子间缓冲不够。
解法：调大网络缓冲内存，并检查下游算子处理能力。
```
