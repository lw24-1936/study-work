## 概述

Flink 是事件驱动的流处理引擎，而"时间"是流计算中最核心也最容易出错的概念。不同数据源、不同网络路径都会让事件到达 Flink 的顺序与真实发生顺序不一致，因此 Flink 提供了三种时间语义与水位线机制，用来在"低延迟"与"结果准确"之间做权衡。理解时间语义与水位线是掌握窗口、状态与 checkpoint 一切机制的前提。

```text
要点：
- 三种时间语义：Processing Time、Event Time、Ingestion Time
- Event Time 结果确定且可重现，是离线与实时结果对齐的唯一选择
- Watermark 是"事件时间进度"的度量，驱动 Event Time 窗口触发
- 水位线允许乱序但产生延迟，Late 数据需要 allowedLateness 或 Side Output 兜底
- Timestamp 由 WatermarkStrategy 中的 TimestampAssigner 抽取
```

## Processing Time

Processing Time（处理时间）指数据到达算子、被执行的那一刻，所用的是算子所在机器的系统时钟。它不依赖数据本身携带的任何时间信息，因此实现最简单、延迟最低、吞吐最高，几乎不需要任何协调。代价是结果不具备确定性：同样的数据，运行两次、换一台机器，结果都可能不同，无法复现。

```text
要点：
- 时钟来源：算子所在 TaskManager 的机器系统时间
- 优点：零协调开销、低延迟、无需关心乱序
- 缺点：结果不确定、不可重现，无法做历史回放
- 适用：实时监控、告警、低延迟大盘、对结果精确性要求不高的场景
- 是 Flink 的默认时间语义（未显式指定时）
```

使用 Processing Time 时无需分配时间戳与水位线，直接定义窗口即可：

```java
DataStream<String> input = env.socketTextStream("localhost", 9999);

input
    .flatMap((String line, Collector<Tuple2<String, Long>> out) -> {
        for (String word : line.split(" ")) {
            out.collect(Tuple2.of(word, 1L));
        }
    }).returns(Types.TUPLE(Types.STRING, Types.LONG))
    .keyBy(t -> t.f0)
    // 默认即为 Processing Time，滚动窗口 10 秒
    .window(TumblingProcessingTimeWindows.of(Time.seconds(10)))
    .sum(1)
    .print();

env.execute("processing-time-demo");
```

## Event Time

Event Time（事件时间）指事件在真实世界中发生的时刻，通常以时间戳字段的形式内嵌在数据记录里。Flink 依据这个字段推进时间，因此无论数据何时到达、以什么顺序到达，计算出的结果都与事件真实发生的时间线一致，是确定性、可重现的。这也是离线数仓与实时数仓结果能够对账、幂等回放的基础，绝大多数需要精确统计的场景都应使用 Event Time。

```text
要点：
- 时钟来源：数据记录内嵌的事件时间戳字段
- 优点：结果确定、可重现，可回放历史数据，离线实时结果一致
- 缺点：需要处理乱序与迟到，需要水位线机制，有一定延迟
- 适用：精确聚合、对账、双流 join、状态计算等绝大多数生产场景
- 依赖 Watermark 推进事件时间，是流批一体统一语义的基石
```

Event Time 需要为流分配时间戳与水位线，并在定义窗口时使用事件时间窗口：

```java
DataStream<OrderEvent> orders = env
    .addSource(new FlinkKafkaConsumer<>("orders",
            new OrderEventDeserializer(), props));

orders
    // 分配事件时间戳并生成有界乱序水位线
    .assignTimestampsAndWatermarks(
            WatermarkStrategy.<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(5))
                    .withTimestampAssigner((event, ts) -> event.getEventTime()))
    .keyBy(OrderEvent::getUserId)
    .window(TumblingEventTimeWindows.of(Time.minutes(1)))
    .sum("amount")
    .print();

env.execute("event-time-demo");
```

## Ingestion Time

Ingestion Time（摄取时间）指事件进入 Flink Source 的时刻，由 Source 算子为每条记录自动打上时间戳。它在数据源与 Flink 之间引入了统一的时间基准，不需要在数据里携带业务时间戳，也不依赖下游机器时钟。相比 Event Time 它无法容忍真正的乱序（无法知道事件真实发生顺序），相比 Processing Time 它多了一点分配开销，但结果在"同一批输入"下相对稳定，介于两者之间。

```text
要点：
- 时钟来源：Source 算子摄取数据时的本地时钟，自动分配
- 优点：无需业务时间戳字段，时间戳分配开销小，结果比 Processing Time 稳定
- 缺点：无法表达事件真实发生顺序，仍受 Source 消费顺序影响
- 适用：无法改造数据源、又希望时间基准相对统一的过渡场景
- 配置：通过 WatermarkStrategy.forBoundedOutOfOrderness + withIdleness 配合
```

Ingestion Time 通过为 Source 设置"自动生成水位线"的策略来启用：

```java
DataStream<String> input = env.socketTextStream("localhost", 9999);

input
    .assignTimestampsAndWatermarks(
            // 使用摄取时间语义：按摄取时刻作为事件时间
            WatermarkStrategy.<String>forBoundedOutOfOrderness(Duration.ofSeconds(2))
                    .withTimestampAssigner((event, ts) -> System.currentTimeMillis()))
    .keyBy(line -> line)
    .window(TumblingEventTimeWindows.of(Time.seconds(10)))
    .sum(1)
    .print();

env.execute("ingestion-time-demo");
```

## Timestamp

Timestamp（时间戳）是 Event Time 语义下每条记录的事件时间值，由 TimestampAssigner 从记录中抽取。旧版本使用 AscendingTimestampExtractor 或 BoundedOutOfOrdernessTimestampExtractor 直接实现，新版本统一收敛到 WatermarkStrategy.withTimestampAssigner 接口。时间戳单位是毫秒，抽取逻辑必须稳定——同一条记录无论重放多少次，抽出的时间戳必须一致，否则水位线与窗口结果都会错乱。

```text
要点：
- 抽取接口：WatermarkStrategy.withTimestampAssigner(SerializableTimestampAssigner)
- 单位是毫秒（epoch millis），负数时间戳表示事件早于 1970 年
- 必须幂等稳定：重放时同一事件抽出相同时间戳
- 历史遗留：AscendingTimestampExtractor、BoundedOutOfOrdernessTimestampExtractor 已弃用
- 时间戳与水印在 Source 或 assignTimestampsAndWatermarks 处一次性分配
```

自定义时间戳抽取的几种典型写法：

```java
// 1) 单调递增时间戳（数据源保证有序时）
WatermarkStrategy.<OrderEvent>forMonotonousTimestamps()
        .withTimestampAssigner((event, ts) -> event.getEventTime());

// 2) 有界乱序时间戳（允许最多 5 秒乱序）
WatermarkStrategy.<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(5))
        .withTimestampAssigner((event, ts) -> event.getEventTime());

// 3) 显式实现 TimestampAssigner（用于字段解析、单位换算等复杂逻辑）
SerializableTimestampAssigner<OrderEvent> assigner = (event, recordTimestamp) -> {
    // 假设 eventTime 是字符串，解析为毫秒
    return Long.parseLong(event.getEventTimeStr());
};
```

## Watermark

Watermark（水位线）是 Flink 用来衡量"事件时间已经推进到哪里"的特殊记录，它随数据流一起流动。一条时间戳为 T 的水位线声明："事件时间早于 T 的所有数据（理论上）都已到达"，后续窗口看到水位线越过窗口结束时间即可触发计算。水位线由 WatermarkGenerator 生成，分周期性（periodic，默认每 200ms 检查一次）与断点式（punctuated，每条记录判断）两种，是平衡乱序容忍度与处理延迟的核心旋钮。

```text
要点：
- 语义：表示"早于 T 的事件都已到齐"，用于推进事件时间、触发窗口
- 生成方式：Periodic（周期性，默认）与 Punctuated（断点式，按事件）
- 乱序容忍：forBoundedOutOfOrderness 的 maxOutOfOrderness 即水位线滞后量
- 多并行度：取所有 SubTask 水位线的最小值作为算子水位线
- 空闲流：withIdleness 防止空闲分区阻塞整体水位线推进
```

自定义周期性水位线生成器，实现"事件时间 - 固定延迟"：

```java
public class BoundedOutOfOrdernessGenerator
        implements WatermarkGenerator<OrderEvent> {

    private final long maxOutOfOrderness = 5000; // 5 秒
    private long currentMaxTimestamp = Long.MIN_VALUE;

    @Override
    public void onEvent(OrderEvent event, long eventTimestamp, WatermarkOutput output) {
        // 持续记录看到的最大事件时间
        currentMaxTimestamp = Math.max(currentMaxTimestamp, eventTimestamp);
    }

    @Override
    public void onPeriodicEmit(WatermarkOutput output) {
        // 周期性发射：当前最大时间 - 允许乱序量
        output.emitWatermark(new Watermark(currentMaxTimestamp - maxOutOfOrderness));
    }
}
```

## Late

Late（迟到数据）指事件时间已经落后于当前水位线、本该被某窗口处理却来晚了的数据。默认情况下，窗口在水位线越过结束时间后就触发计算并销毁，迟到的数据会被直接丢弃。Flink 提供两条兜底路径：一是 allowedLateness 让窗口触发后继续保留一段时间，迟到数据到来时增量更新结果；二是 Side Output 把真正无法处理的迟到数据旁路输出，避免数据静默丢失。

```text
要点：
- 定义：eventTime < currentWatermark 且所属窗口已触发的数据
- 默认行为：直接丢弃，不产生任何输出（静默丢失）
- 兜底一：allowedLateness 保留窗口、迟到触发增量计算
- 兜底二：sideOutputLateData 将迟到数据写入旁路输出流
- 迟到的根因是水位线"提前"了，需结合乱序容忍度一起设计
```

使用 allowedLateness 与 Side Output 处理迟到数据：

```java
OutputTag<OrderEvent> lateTag = new OutputTag<OrderEvent>("late") {};

SingleOutputStreamOperator<String> result = orders
        .assignTimestampsAndWatermarks(
                WatermarkStrategy.<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(5))
                        .withTimestampAssigner((e, ts) -> e.getEventTime()))
        .keyBy(OrderEvent::getUserId)
        .window(TumblingEventTimeWindows.of(Time.minutes(1)))
        .allowedLateness(Time.minutes(2))   // 窗口触发后继续保留 2 分钟
        .sideOutputLateData(lateTag)         // 仍迟到的数据写入旁路
        .sum("amount");

// 拿到迟到数据单独处理，避免静默丢失
DataStream<OrderEvent> lateStream = result.getSideOutput(lateTag);
lateStream.print("late-data");
```

## Out-of-order

Out-of-order（乱序）指数据到达 Flink 的顺序与它们的事件时间顺序不一致。乱序在网络传输、多分区并行消费、多数据源合并、Kafka 多分区等场景几乎必然存在，是流处理必须面对的现实。水位线机制的本质就是对乱序的"声明式容忍"：通过让水位线滞后于最大事件时间一个上限，告诉引擎"最多乱序多少时间"，在乱序与延迟之间取得平衡。

```text
要点：
- 来源：网络抖动、Kafka 多分区乱序消费、多源合并、背压重发
- 本质：到达顺序 != 事件时间顺序
- 处理：水位线滞后 maxOutOfOrderness 来吸收乱序
- 上限选择：滞后越大结果越准但延迟越高，需按业务可接受延迟定
- 超上限的乱序即为 Late 数据，需 allowedLateness 或 Side Output 兜底
```

乱序容忍量的选取直接影响准确性与延迟，下面演示两种极端配置：

```java
// 场景 A：乱序很小，水位线滞后 1 秒，追求低延迟
WatermarkStrategy.<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(1));

// 场景 B：允许 5 分钟乱序，追求结果准确（如对账、结算）
WatermarkStrategy.<OrderEvent>forBoundedOutOfOrderness(Duration.ofMinutes(5));

// 场景 C：配合空闲检测，防止某分区长时间无数据阻塞水位线
WatermarkStrategy.<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(5))
        .withIdleness(Duration.ofMinutes(1)); // 1 分钟无数据即视为空闲
```

## 应用场景实战

### 场景一：实时订单延迟告警（Processing Time）

监控系统需要以极低延迟统计每分钟的订单量，一旦超过阈值立即告警。这类场景不要求精确对账，优先保证告警及时性，因此使用 Processing Time 最合适——零协调、延迟最低。

```java
public class OrderAlertJob {
    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env =
                StreamExecutionEnvironment.getExecutionEnvironment();

        DataStream<OrderEvent> orders = env
                .addSource(new FlinkKafkaConsumer<>("orders",
                        new OrderEventDeserializer(),
                        kafkaProps()));

        orders
                .keyBy(OrderEvent::getChannel)
                .window(TumblingProcessingTimeWindows.of(Time.minutes(1)))
                .aggregate(new CountAggregator(), new AlertWindowFunction())
                .filter(alert -> alert.count > 1000)
                .addSink(new AlertSink());

        env.execute("order-alert-processing-time");
    }
}
```

```java
// 聚合函数：统计数量
public class CountAggregator
        implements AggregateFunction<OrderEvent, Long, Long> {
    @Override
    public Long createAccumulator() { return 0L; }

    @Override
    public Long add(OrderEvent value, Long acc) { return acc + 1; }

    @Override
    public Long getResult(Long acc) { return acc; }

    @Override
    public Long merge(Long a, Long b) { return a + b; }
}
```

### 场景二：分钟级 GMV 精确统计与离线对账（Event Time + 水位线）

实时数仓需要分钟级 GMV（成交总额），且要求与离线数仓次日计算结果误差在容忍范围内。必须使用 Event Time：按订单成交时间而非到达时间聚合，并容忍一定乱序与迟到，保证结果可重现、可对账。

```java
public class GmvJob {
    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env =
                StreamExecutionEnvironment.getExecutionEnvironment();

        OutputTag<OrderEvent> lateTag = new OutputTag<OrderEvent>("late") {};

        DataStream<OrderEvent> orders = env
                .addSource(new FlinkKafkaConsumer<>("order_pay",
                        new OrderEventDeserializer(), kafkaProps()))
                .assignTimestampsAndWatermarks(
                        WatermarkStrategy.<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(30))
                                .withTimestampAssigner((e, ts) -> e.getPayTime())
                                .withIdleness(Duration.ofMinutes(2)));

        SingleOutputStreamOperator<GmvResult> gmv = orders
                .keyBy(OrderEvent::getShopId)
                .window(TumblingEventTimeWindows.of(Time.minutes(1)))
                .allowedLateness(Time.minutes(5))
                .sideOutputLateData(lateTag)
                .aggregate(new GmvAggregator(), new GmvWindowFunction());

        gmv.addSink(new HBaseSink("realtime_gmv"));
        gmv.getSideOutput(lateTag).print("late-order");

        env.execute("gmv-event-time");
    }
}
```

```java
// GMV 聚合：SUM(amount)
public class GmvAggregator
        implements AggregateFunction<OrderEvent, Double, Double> {
    @Override
    public Double createAccumulator() { return 0.0; }

    @Override
    public Double add(OrderEvent value, Double acc) {
        return acc + value.getAmount();
    }

    @Override
    public Double getResult(Double acc) { return acc; }

    @Override
    public Double merge(Double a, Double b) { return a + b; }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 对账类、统计类、join 类作业一律使用 Event Time；只有告警、实时监控等纯延迟敏感场景才用 Processing Time。
2. 时间戳抽取要幂等稳定，抽取字段单位统一为毫秒，避免秒/毫秒混用导致窗口错位。
3. 乱序容忍量 maxOutOfOrderness 按业务可接受延迟设置，通常取"数据源最大可见乱序"的 1.5~2 倍。
4. 多分区数据源（尤其 Kafka）必须配置 withIdleness，防止单个空闲分区卡死全局水位线。
5. 迟到数据永远不要静默丢弃：要么 allowedLateness，要么 sideOutputLateData，保证数据可审计。
6. 水位线滞后与 allowedLateness 是两层机制：前者决定窗口何时首次触发，后者决定触发后窗口保留多久。
7. 测试时用 Min 水位线语义校验：多并行度下算子水位线等于所有 SubTask 水位线的最小值。

### 踩坑记录

```text
坑 1：窗口一直不触发
结论：Event Time 窗口看不到任何输出。
原因：没分配时间戳与水位线，事件时间停在 Long.MIN_VALUE，永远越不过窗口结束时间。
解法：在 keyBy 之前调用 assignTimestampsAndWatermarks 并正确实现 TimestampAssigner。

坑 2：Kafka 某分区没数据导致全流卡住
结论：水位线长期不前进，窗口大量积压不触发。
原因：多并行度下取各 SubTask 水位线最小值，空闲分区水位线停在原地拉低了整体。
解法：配置 WatermarkStrategy.withIdleness，空闲超时后该分区不再参与最小值计算。

坑 3：结果与离线对不上，且误差随重放变化
结论：同一份数据两次跑出不同结果。
原因：误用了 Processing Time 或 Ingestion Time，时钟基准随机器/运行时刻漂移。
解法：统一改为 Event Time 语义，按业务事件时间聚合。

坑 4：窗口触发后数据被静默丢弃
结论：部分订单没有进入任何统计。
原因：迟到数据在窗口触发后被默认丢弃，没有配置 allowedLateness 或 Side Output。
解法：按业务需求设置 allowedLateness，并用 sideOutputLateData 兜底旁路输出。

坑 5：水位线滞后设得过大，实时性极差
结论：结果很准但延迟几分钟甚至更久，实时指标失去意义。
原因：maxOutOfOrderness 按最大极端乱序设置，而非业务可接受延迟。
解法：在准确性与延迟间取平衡，极端迟到数据交给 Side Output 单独补偿。
```
