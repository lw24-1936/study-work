## 概述

状态（State）是有状态流处理的核心：没有状态，Flink 就只是一个逐条转换的管道，无法做聚合、去重、双流 join 等需要"记住历史"的计算。状态由算子维护，随数据流持续更新，并通过 checkpoint 机制持久化以支持故障恢复。Flink 的状态分为 Keyed State 与 Operator State 两大类，下面细分 ValueState、ListState、MapState 等多种结构，理解其适用场景与访问方式是写出正确作业的前提。

```text
要点：
- 状态是流计算"记住历史"的载体，聚合/去重/join 都依赖它
- 两大类：Keyed State（按 key 分区）与 Operator State（按算子实例分区）
- Keyed State 细分：Value / List / Map / Reducing / Aggregating
- 状态靠 Checkpoint 持久化，靠 State Backend（内存或 RocksDB）存储
```

## Keyed State

Keyed State（键控状态）是与某个具体 key 绑定的状态，只能在 keyBy 之后的 KeyedStream 上使用。Flink 内部把相同 key 的数据路由到同一算子实例，每个 key 拥有独立、互不可见的一份状态，访问时无需关心数据分布，就像本地变量一样读写。它随 key 的生命周期存在，key 不再出现后其状态可被 TTL 或定时器清理，是流计算中最常用的状态类型。

```text
要点：
- 前提：必须在 keyBy 之后的 KeyedStream 上，通过 RuntimeContext 获取
- 隔离性：每个 key 一份独立状态，逻辑上等同"本地变量"
- 生命周期：随 key 存在，需用 TTL 或 clear 主动清理
- 典型场景：累加求和、去重、会话状态、按 key 的自定义计数
```

```java
public class CountWithKeyedState extends RichFlatMapFunction<OrderEvent, Tuple2<String, Long>> {
    private ValueState<Long> countState;
    @Override
    public void open(Configuration parameters) {
        countState = getRuntimeContext().getState(
                new ValueStateDescriptor<>("order-count", Long.class));
    }
    @Override
    public void flatMap(OrderEvent event, Collector<Tuple2<String, Long>> out) throws Exception {
        Long current = countState.value();
        current = (current == null ? 0L : current) + 1;
        countState.update(current);
        out.collect(Tuple2.of(event.getUserId(), current));
    }
}
```

## Operator State

Operator State（算子状态）是与算子实例（SubTask）绑定的状态，每个并行实例持有一份，不区分 key。它主要用于 Source 与 Sink 这类无法或无需按 key 分区的算子，最典型的是保存 Kafka 消费 offset。因为状态按实例划分，扩缩容时需要重新分配状态，需实现 ListCheckpointed 或 CheckpointedFunction 接口来定义快照与恢复逻辑。

```text
要点：
- 绑定对象：算子并行实例（SubTask），与 key 无关
- 典型用途：Source 保存 Kafka offset、Sink 保存幂等状态
- 重分布：扩缩容时状态在实例间重新分配，由 redistribute 策略决定
- 接口：实现 CheckpointedFunction 或 ListCheckpointed 定义快照/恢复
```

```java
public class OffsetSource extends RichParallelSourceFunction<OrderEvent>
        implements CheckpointedFunction {
    private volatile boolean running = true;
    private long offset = 0;
    private ListState<Long> offsetState;
    @Override
    public void run(SourceContext<OrderEvent> ctx) throws Exception {
        while (running) { ctx.collect(new OrderEvent(offset++)); Thread.sleep(100); }
    }
    @Override
    public void snapshotState(FunctionSnapshotContext context) throws Exception {
        offsetState.clear(); offsetState.add(offset);
    }
    @Override
    public void initializeState(FunctionInitializationContext context) throws Exception {
        offsetState = context.getOperatorStateStore()
                .getListState(new ListStateDescriptor<>("offset", Long.class));
        if (context.isRestored()) { for (Long v : offsetState.get()) offset = v; }
    }
    @Override
    public void cancel() { running = false; }
}
```

## ValueState

ValueState（值状态）是最基础的单值状态，每个 key 只保存一个值，通过 value() 读取、update() 写入。它适合保存"每个 key 的最新一条信息"，例如最新登录时间、累加值、标志位等。读取时可能为 null（首次访问），写入会整体覆盖旧值；存的是对象引用，修改后必须显式 update() 才能被框架感知。

```text
要点：
- 语义：每个 key 保存单个值，value() 读、update(T) 写、clear() 清
- 首次访问 value() 返回 null，需判空处理
- 必须 update 才生效：直接改对象字段 Flink 感知不到
- 适用：最新值、累加计数、去重标志、会话起始时间
```

```java
public class LastLoginFunction extends RichFlatMapFunction<LoginEvent, LoginEvent> {
    private ValueState<Long> lastLoginState;
    @Override
    public void open(Configuration parameters) {
        lastLoginState = getRuntimeContext().getState(
                new ValueStateDescriptor<>("last-login", Long.class));
    }
    @Override
    public void flatMap(LoginEvent event, Collector<LoginEvent> out) throws Exception {
        Long last = lastLoginState.value();
        if (last != null && event.getTs() - last < 60_000) out.collect(event);
        lastLoginState.update(event.getTs());
    }
}
```

## ListState

ListState（列表状态）保存一个元素列表，支持 add、addAll、update、get 等操作，适合累积多条记录，例如窗口内收集的事件、待处理的缓冲队列等。get() 返回可迭代的列表视图，迭代后修改不会自动写回，需要重新 add/update。在 RocksDB 后端下，读是完整反序列化整个列表，元素过多时要关注性能。

```text
要点：
- 语义：每个 key 一个列表，add/addAll 追加、update 覆盖、get 迭代
- 迭代后不会自动回写，需显式 add/update 修改
- RocksDB 下 get 会反序列化整个列表，元素过多有性能风险
- 适用：窗口内元素收集、缓冲队列、待发送记录缓存
```

```java
public class BatchSinkFunction extends RichSinkFunction<OrderEvent> {
    private ListState<OrderEvent> bufferState;
    @Override
    public void open(Configuration parameters) {
        bufferState = getRuntimeContext().getListState(
                new ListStateDescriptor<>("buffer", OrderEvent.class));
    }
    @Override
    public void invoke(OrderEvent value, Context context) throws Exception {
        bufferState.add(value);
        int c = 0;
        for (OrderEvent e : bufferState.get()) c++;
        if (c >= 100) flush();
    }
    private void flush() throws Exception {
        for (OrderEvent e : bufferState.get()) { /* 批量写入下游 */ }
        bufferState.clear();
    }
}
```

## MapState

MapState（映射状态）保存键值对集合，支持 put、get、remove、contains、iterate 等操作，且单个 key 的读写只反序列化对应条目，无需整体加载。相比"用 ListState 存对象再遍历查找"，MapState 在需要按子键随机访问时性能与内存都更优，尤其适合大状态、RocksDB 后端的场景，是精确去重、字典、按维度累积统计的推荐结构。

```text
要点：
- 语义：每个 key 一个 Map，put/get/remove/contains/entries 操作
- 优势：随机访问单个条目，不整体反序列化，适合大状态
- 对比：比 ListState 遍历查找更高效，比 ValueState 能存多键
- 适用：精确去重、维度字典、按子键累加、用户特征表
```

```java
public class DedupFunction extends RichFlatMapFunction<OrderEvent, OrderEvent> {
    private MapState<String, Long> seenState;
    @Override
    public void open(Configuration parameters) {
        seenState = getRuntimeContext().getMapState(
                new MapStateDescriptor<>("seen", String.class, Long.class));
    }
    @Override
    public void flatMap(OrderEvent event, Collector<OrderEvent> out) throws Exception {
        if (seenState.contains(event.getOrderId())) return;
        seenState.put(event.getOrderId(), event.getTs());
        out.collect(event);
    }
}
```

## ReducingState

ReducingState（归约状态）在每次 add 时用用户提供的 ReduceFunction 把新值与当前状态归约成一个值，状态里始终只保存归约结果。它省去了"读出来-算-写回去"的手工逻辑，保证状态单调归约、内存占用恒定。适合累加、求最大最小值等可结合（associative）的聚合。

```text
要点：
- 语义：add(T) 时用 ReduceFunction 归约，只保存一个归约结果
- 省心：无需手动 value()+update，框架自动归约
- 要求：ReduceFunction 必须满足结合律，否则结果不确定
- 适用：累加求和、求最大/最小、计数、最新值
```

```java
public class MaxAmountFunction extends RichFlatMapFunction<OrderEvent, OrderEvent> {
    private ReducingState<OrderEvent> maxState;
    @Override
    public void open(Configuration parameters) {
        maxState = getRuntimeContext().getReducingState(
                new ReducingStateDescriptor<>("max-amount",
                        (a, b) -> a.getAmount() >= b.getAmount() ? a : b,
                        OrderEvent.class));
    }
    @Override
    public void flatMap(OrderEvent event, Collector<OrderEvent> out) throws Exception {
        maxState.add(event);
        out.collect(maxState.get());
    }
}
```

## AggregatingState

AggregatingState（聚合状态）与 ReducingState 类似，但通过 AggregateFunction 支持输入、累加器、输出三种不同类型，归约逻辑更灵活。累加器类型可以自定义（如 Tuple、POJO），中间只保存累加器，输出时才 getResult 得到结果。适合"输入是明细、状态是中间累加器、输出是统计值"这类形态多样的聚合。

```text
要点：
- 语义：add(T) 时用 AggregateFunction 聚合，保存中间累加器
- 三类型：IN（输入）、ACC（累加器）、OUT（输出）可各不相同
- 优势：比 ReducingState 灵活，累加器结构可自定义
- 适用：求均值、去重计数、多指标联合累加
```

```java
public class AvgAmountFunction extends RichFlatMapFunction<OrderEvent, Tuple2<String, Double>> {
    private AggregatingState<OrderEvent, Double> avgState;
    @Override
    public void open(Configuration parameters) {
        avgState = getRuntimeContext().getAggregatingState(
                new AggregatingStateDescriptor<>("avg-amount",
                        new AggregateFunction<OrderEvent, Tuple2<Long, Double>, Double>() {
                            @Override public Tuple2<Long, Double> createAccumulator() { return Tuple2.of(0L, 0.0); }
                            @Override public Tuple2<Long, Double> add(OrderEvent v, Tuple2<Long, Double> acc) { return Tuple2.of(acc.f0 + 1, acc.f1 + v.getAmount()); }
                            @Override public Double getResult(Tuple2<Long, Double> acc) { return acc.f1 / acc.f0; }
                            @Override public Tuple2<Long, Double> merge(Tuple2<Long, Double> a, Tuple2<Long, Double> b) { return Tuple2.of(a.f0 + b.f0, a.f1 + b.f1); }
                        },
                        TypeInformation.of(new TypeHint<Tuple2<Long, Double>>() {})));
    }
    @Override
    public void flatMap(OrderEvent event, Collector<Tuple2<String, Double>> out) throws Exception {
        avgState.add(event);
        out.collect(Tuple2.of(event.getUserId(), avgState.get()));
    }
}
```

## Broadcast State

Broadcast State（广播状态）是一种特殊的 Operator State，用于把一份小数据（规则表、维度表、配置）广播到所有并行实例，并与主流做 connect 关联。它由 BroadcastStream（通过 broadcast() 产生）与主流的 connect 而成，在 BroadcastProcessFunction 中通过 getBroadcastState 读写。广播状态随 checkpoint 持久化，适合"规则实时下发 + 主流实时匹配"的动态规则场景。

```text
要点：
- 本质：把规则/维度等小数据集广播到每个并行实例的 Operator State
- 组成：主流 keyedStream.connect(broadcastStream)，broadcastStream 由 broadcast() 产生
- 特性：随 checkpoint 持久化，恢复时广播状态可还原
- 适用：动态规则匹配、实时维度 join、黑白名单下发
```

```java
MapStateDescriptor<String, BlacklistRule> ruleDesc =
        new MapStateDescriptor<>("blacklist", String.class, BlacklistRule.class);
DataStream<UserAction> actions = env.addSource(new UserActionSource());
BroadcastStream<BlacklistRule> broadcastRules =
        env.addSource(new BlacklistRuleSource()).broadcast(ruleDesc);
actions.keyBy(UserAction::getUserId)
        .connect(broadcastRules)
        .process(new BlacklistFilterFunction(ruleDesc))
        .print();
```

```java
public class BlacklistFilterFunction
        extends BroadcastProcessFunction<UserAction, BlacklistRule, UserAction> {
    private final MapStateDescriptor<String, BlacklistRule> ruleDesc;
    public BlacklistFilterFunction(MapStateDescriptor<String, BlacklistRule> ruleDesc) { this.ruleDesc = ruleDesc; }
    @Override
    public void processBroadcastElement(BlacklistRule rule, Context ctx, Collector<UserAction> out)
            throws Exception { ctx.getBroadcastState(ruleDesc).put(rule.getUserId(), rule); }
    @Override
    public void processElement(UserAction action, ReadOnlyContext ctx, Collector<UserAction> out)
            throws Exception {
        if (ctx.getBroadcastState(ruleDesc).get(action.getUserId()) == null) out.collect(action);
    }
}
```

## 应用场景实战

### 场景一：实时 UV 精确去重（MapState + 状态 TTL）

统计某活动页的实时累计 UV，需要按访客 ID 去重且长期累积。用 KeyedState 的 MapState 保存"已见访客集合"，并配 TTL 让过期访客自动清理，避免状态无限增长。

```java
public class RealTimeUvJob {
    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
        env.addSource(new FlinkKafkaConsumer<>("visit", new VisitEventDeserializer(), kafkaProps()))
                .keyBy(VisitEvent::getPageId).flatMap(new UvDedupFunction())
                .keyBy(VisitEvent::getPageId).process(new UvCountFunction())
                .addSink(new RedisSink("realtime_uv"));
        env.execute("realtime-uv-job");
    }
    public static class UvDedupFunction extends RichFlatMapFunction<VisitEvent, VisitEvent> {
        private transient MapState<String, Boolean> seenState;
        @Override
        public void open(Configuration parameters) {
            MapStateDescriptor<String, Boolean> desc =
                    new MapStateDescriptor<>("seen", String.class, Boolean.class);
            StateTtlConfig ttl = StateTtlConfig.newBuilder(Time.hours(24))
                    .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
                    .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired).build();
            desc.enableTimeToLive(ttl);
            seenState = getRuntimeContext().getMapState(desc);
        }
        @Override
        public void flatMap(VisitEvent value, Collector<VisitEvent> out) throws Exception {
            if (!seenState.contains(value.getUserId())) {
                seenState.put(value.getUserId(), true);
                out.collect(value);
            }
        }
    }
    public static class UvCountFunction extends KeyedProcessFunction<String, VisitEvent, Long> {
        private transient ValueState<Long> uvState;
        @Override
        public void open(Configuration parameters) {
            uvState = getRuntimeContext().getState(new ValueStateDescriptor<>("uv", Long.class));
        }
        @Override
        public void processElement(VisitEvent value, Context ctx, Collector<Long> out)
                throws Exception {
            Long uv = uvState.value();
            uvState.update((uv == null ? 0L : uv) + 1);
            out.collect(uvState.value());
        }
    }
}
```

### 场景二：实时规则引擎（Broadcast State）

风控系统需要把不断更新的风控规则实时下发到作业，主流交易数据按规则动态判定。用 Broadcast State 广播规则，BroadcastProcessFunction 做匹配，规则变更即时生效且随 checkpoint 可恢复。

```java
public class RuleEngineJob {
    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
        MapStateDescriptor<String, Rule> ruleDesc =
                new MapStateDescriptor<>("rules", String.class, Rule.class);
        DataStream<Transaction> txns = env.addSource(new TransactionSource());
        BroadcastStream<Rule> broadcast = env.addSource(new RuleSource()).broadcast(ruleDesc);
        txns.keyBy(Transaction::getAccountId).connect(broadcast)
                .process(new RuleMatchFunction(ruleDesc))
                .filter(Transaction::isSuspicious)
                .addSink(new AlertSink());
        env.execute("rule-engine-job");
    }
}
```

```java
public class RuleMatchFunction extends BroadcastProcessFunction<Transaction, Rule, Transaction> {
    private final MapStateDescriptor<String, Rule> ruleDesc;
    public RuleMatchFunction(MapStateDescriptor<String, Rule> ruleDesc) { this.ruleDesc = ruleDesc; }
    @Override
    public void processBroadcastElement(Rule rule, Context ctx, Collector<Transaction> out)
            throws Exception { ctx.getBroadcastState(ruleDesc).put(rule.getRuleId(), rule); }
    @Override
    public void processElement(Transaction txn, ReadOnlyContext ctx, Collector<Transaction> out)
            throws Exception {
        for (Rule rule : ctx.getBroadcastState(ruleDesc).values()) {
            if (rule.matches(txn)) txn.setSuspicious(true);
        }
        out.collect(txn);
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优先用 Keyed State，仅 Source/Sink 无法按 key 分区时才用 Operator State，降低扩缩容复杂度。
2. 随机访问大集合时用 MapState 而非 ListState，避免整体反序列化带来的性能与内存问题。
3. 状态必须设置 TTL，尤其是去重、会话、特征类长期累积的状态，防止无限膨胀。
4. ValueState 存的是对象引用，修改字段后务必重新 update()，否则改动不纳入 checkpoint。
5. 状态后端选型：状态小、延迟敏感用内存 HashMapStateBackend；状态大、需增量 checkpoint 用 RocksDB。
6. ReducingState / AggregatingState 的归约函数必须满足结合律，否则结果不确定。

### 踩坑记录

```text
坑 1：状态改了却没生效，恢复后丢失
结论：作业运行正常，但故障恢复后状态回退。
原因：拿到 ValueState 里的对象后直接改字段，没调用 update()，框架感知不到变更。
解法：修改状态对象后必须显式 update()，或改用不可变对象每次新建。

坑 2：状态无限增长导致 OOM
结论：长时间运行后 TaskManager 内存持续上涨直至崩溃。
原因：去重、累积类状态没有设置 TTL，历史 key 永不过期。
解法：用 StateTtlConfig 设置 TTL，并配合定时器或 clear 主动清理。

坑 3：MapState 与 ListState 选错导致性能问题
结论：换用 ListState 后反而更慢、内存更大。
原因：ListState 每次 get 都整体反序列化整个列表，大状态下代价极高。
解法：需要随机访问的场景坚持用 MapState，只有顺序遍历才考虑 ListState。

坑 4：广播流规则不生效或不同实例不一致
结论：部分算子实例没收到规则，结果错乱。
原因：广播流未用 broadcast() 转换，或 processElement 用了可写状态而非只读视图。
解法：主流 connect 前对规则流调 broadcast(descriptor)，processElement 用 ReadOnlyContext。

坑 5：ReduceFunction 不满足结合律导致结果漂移
结论：同一作业多次运行结果不一致。
原因：归约函数依赖顺序或中间态，不满足结合律，并发归约结果不确定。
解法：确保归约函数可结合、可交换，或用 AggregateFunction 显式定义累加器。
```
