## 概述

流处理作业 7x24 小时运行，机器故障、网络抖动、代码升级都可能导致任务中断，容错能力因此成为 Flink 的核心竞争力。Flink 通过 Checkpoint 定期对状态做一致性快照，故障后从最近一次快照恢复，配合 Exactly-Once 语义保证"数据不丢、结果不错"。Savepoint 则是手动触发的、面向运维的快照，用于升级、迁移与回滚。理解 Barrier 对齐、非对齐检查点与状态后端的差异，是生产环境稳定运行 Flink 作业的关键。

```text
要点：
- Checkpoint：周期性自动快照，用于故障自动恢复
- Savepoint：手动触发的快照，用于升级、迁移、回滚等运维操作
- Barrier：注入流中的标记，驱动状态快照与对齐
- Unaligned Checkpoint：跳过对齐，降低反压下的 checkpoint 延迟
- State Backend：决定状态存在哪，HashMapStateBackend 与 RocksDB 两种
```

## Checkpoint

Checkpoint（检查点）是 Flink 自动触发的分布式一致性快照，由 JobManager 周期性地向所有 Source 注入 barrier，各算子把当前状态快照到 State Backend 并上报，全部完成后即生成一个可恢复的完整快照。作业故障时，Flink 从最近一次成功的 checkpoint 恢复所有算子状态并继续处理，配合数据源的可重放能力（如 Kafka offset）实现 Exactly-Once。检查点间隔、超时、并发数等参数直接影响作业稳定性与恢复速度。

```text
要点：
- 触发方：JobManager 按 checkpointInterval 周期性自动触发
- 内容：所有算子状态 + 各数据源的 offset/位置信息
- 语义：配合可重放数据源（Kafka）实现 Exactly-Once 或 At-Least-Once
- 关键参数：interval（间隔）、timeout（超时）、minPauseBetweenCheckpoints、容忍失败次数
- 恢复：从最近一次成功 checkpoint 恢复到一致性状态继续消费
```

启用并配置 Checkpoint 的标准代码：

```java
StreamExecutionEnvironment env =
        StreamExecutionEnvironment.getExecutionEnvironment();

// 启用 checkpoint，每 10 秒一次
env.enableCheckpointing(10_000);

CheckpointConfig config = env.getCheckpointConfig();
config.setCheckpointTimeout(60_000);              // 单次 checkpoint 超时 60 秒
config.setMinPauseBetweenCheckpoints(5_000);      // 两次 checkpoint 最小间隔 5 秒
config.setMaxConcurrentCheckpoints(1);            // 最多并发 1 个（默认）
config.setTolerableCheckpointFailureNumber(3);    // 容忍 3 次失败
config.setCheckpointStorage("hdfs://namenode:8020/flink/checkpoints");

// 语义选择：Exactly-Once（默认）或 At-Least-Once
config.setCheckpointingMode(CheckpointingMode.EXACTLY_ONCE);

// 外部化 checkpoint：作业取消后保留 checkpoint 供恢复
config.setExternalizedCheckpointCleanup(
        CheckpointConfig.ExternalizedCheckpointCleanup.RETAIN_ON_CANCELLATION);
```

## Savepoint

Savepoint（保存点）是用户手动触发的一致性快照，其底层格式与 Checkpoint 兼容，但定位不同：Checkpoint 面向故障自动恢复，Savepoint 面向人工运维。它可以在升级 Flink 版本、修改作业逻辑、调整并行度、迁移集群时，作为"安全回退点"保存当前状态，之后从 Savepoint 恢复作业。Savepoint 默认不自动清理、可指定路径、支持修改并行度与算子 uid，是版本管理与灰度发布的基石。

```text
要点：
- 触发方：用户通过 CLI 或 API 手动触发，非自动
- 用途：版本升级、逻辑变更、扩缩容、集群迁移、回滚
- 特性：可指定存储路径、长期保留、可改并行度、可改算子逻辑
- 依赖算子 uid：变更拓扑时靠 uid 匹配新旧算子状态
- 命令：flink savepoint <jobId> <path> 与 flink run -s <savepointPath>
```

使用 Savepoint 进行作业升级的完整流程：

```bash
# 1) 触发 savepoint 并停止旧作业（保留状态到指定路径）
flink stop --savepointPath hdfs://namenode:8020/flink/savepoints <jobId>

# 2) 从 savepoint 恢复并启动新版本作业
flink run -s hdfs://namenode:8020/flink/savepoints/savepoint-xxxx \
    -d /path/to/new-job.jar

# 3) 查看 savepoint 信息（可选）
flink savepoint -d hdfs://namenode:8020/flink/savepoints/savepoint-xxxx

# 4) 丢弃不再需要的 savepoint
flink savepoint -d hdfs://namenode:8020/flink/savepoints/savepoint-xxxx
```

为保证升级时状态能正确匹配，作业内每个有状态算子都应设置稳定的 uid：

```java
env.addSource(new FlinkKafkaConsumer<>("orders", new OrderEventDeserializer(), props))
        .uid("source-kafka-orders")          // 固定 uid，升级时状态可匹配
        .keyBy(OrderEvent::getUserId)
        .process(new OrderCountFunction())
        .uid("process-order-count")
        .addSink(new HBaseSink("order_count"))
        .uid("sink-hbase-order-count");
```

## Barrier

Barrier（屏障）是 Flink 在数据流中注入的特殊标记记录，是实现分布式快照的核心机制（基于 Chandy-Lamport 算法）。JobManager 触发 checkpoint 时，Source 向自己的每条输出流注入 barrier，下游算子在收到来自所有上游分区的同一编号 barrier 后，先快照自己的状态，再把 barrier 继续向下游广播。这个过程叫"对齐"：在对齐完成前，慢分区的数据会缓冲，保证快照的一致性。

```text
要点：
- 本质：随数据流流动的标记记录，携带 checkpoint 编号
- 注入：由 Source 在触发时向各输出流注入，源自 Chandy-Lamport 快照算法
- 对齐：算子等齐所有上游同编号 barrier 才快照并继续传播
- 代价：对齐期间慢分区数据被缓冲，可能加剧反压
- 优化：Unaligned Checkpoint 跳过对齐，用"屏障优先"降低延迟
```

Barrier 对齐过程的关键行为，可用配置控制对齐方式与超时：

```java
CheckpointConfig config = env.getCheckpointConfig();

// 对齐超时：超过该时间仍未对齐则转为非对齐 checkpoint
config.setAlignedCheckpointTimeout(Duration.ofSeconds(30));

// 完全启用非对齐 checkpoint
config.enableUnalignedCheckpoints();

// 关闭非对齐（默认对齐）
config.disableUnalignedCheckpoints();
```

```text
Barrier 对齐流程：
1. Source 向所有输出流注入编号为 N 的 barrier
2. 下游算子收到某上游分区的 barrier N，标记该分区"已到"
3. 等待所有上游分区都收到 barrier N，期间缓冲已到分区的后续数据
4. 全部到齐后，快照算子状态，把 barrier N 广播到下游
5. 重复直至 sink 完成，所有算子快照齐备即 checkpoint N 成功
```

## Unaligned Checkpoint

Unaligned Checkpoint（非对齐检查点）是对齐机制的优化：当某个分区数据量远超其他分区、对齐迟迟无法完成时，标准对齐会让 checkpoint 长时间卡住并加剧反压。非对齐检查点允许算子"先快照再等"——barrier 到达即立即快照，把"已越过 barrier 的数据"一并作为状态的一部分持久化，从而消除对齐等待，显著降低反压场景下的 checkpoint 延迟。代价是 checkpoint 体积更大，且需要状态后端支持。

```text
要点：
- 动机：解决对齐在数据倾斜/反压下的长时间阻塞
- 做法：barrier 到达即快照，不等待其他分区，越过 barrier 的数据一并入快照
- 优点：反压下 checkpoint 延迟大幅降低，恢复更快
- 代价：快照体积增大，需要 RocksDB 等支持的状态后端
- 适用：高反压、数据倾斜严重、对齐超时频繁的作业
```

启用非对齐检查点并配合超时降级：

```java
StreamExecutionEnvironment env =
        StreamExecutionEnvironment.getExecutionEnvironment();

env.enableCheckpointing(10_000);

CheckpointConfig config = env.getCheckpointConfig();
// 方案 A：直接全量启用非对齐
config.enableUnalignedCheckpoints();

// 方案 B：先对齐，超时 30 秒仍无法对齐则本次转为非对齐
config.setAlignedCheckpointTimeout(Duration.ofSeconds(30));
```

```text
非对齐 checkpoint 与对齐 checkpoint 对比：
- 对齐：等所有分区 barrier 到齐才快照，快照小但等待久
- 非对齐：barrier 到达即快照，无等待但快照大
- 反压场景：非对齐明显优于对齐
- 低反压场景：对齐快照更小，恢复开销更低
- 选择：默认对齐，配置 alignedCheckpointTimeout 做自适应降级最稳妥
```

## State Backend

State Backend（状态后端）决定运行时的状态数据存在哪里、checkpoint 快照如何持久化。Flink 提供两大类：HashMapStateBackend 把状态保存在 TaskManager 堆内存中，访问快、延迟低，但受内存限制；EmbeddedRocksDBStateBackend 把状态下沉到 RocksDB 磁盘，可支撑 TB 级状态与增量 checkpoint，但访问有序列化开销。选择状态后端是作业容量规划与性能调优的第一道决策。

```text
要点：
- 职责：决定状态在运行时存哪、checkpoint 如何持久化
- HashMapStateBackend：状态在堆内存，快、低延迟，适合小状态
- EmbeddedRocksDBStateBackend：状态在 RocksDB 磁盘，支撑大状态、增量 checkpoint
- 旧名对照：MemoryStateBackend / FsStateBackend 已合并为 HashMapStateBackend
- 选型：按状态大小、延迟要求、是否需要增量 checkpoint 决定
```

配置状态后端与 checkpoint 存储：

```java
StreamExecutionEnvironment env =
        StreamExecutionEnvironment.getExecutionEnvironment();

// 状态后端：内存（默认，适合小状态）
env.setStateBackend(new HashMapStateBackend());

// 或：RocksDB（大状态、增量 checkpoint）
env.setStateBackend(new EmbeddedRocksDBStateBackend(true));  // true = 启用增量 checkpoint

// checkpoint 存储位置：文件系统或对象存储
env.getCheckpointConfig().setCheckpointStorage(
        new FileSystemCheckpointStorage("hdfs://namenode:8020/flink/checkpoints"));
```

```text
两种状态后端对比：
HashMapStateBackend：
- 状态位置：TaskManager JVM 堆内存
- 延迟：极低，无磁盘 I/O 与序列化开销
- 容量：受堆内存限制，状态过大会 GC 压力与 OOM
- 适用：小状态、高吞吐低延迟的实时作业

EmbeddedRocksDBStateBackend：
- 状态位置：RocksDB 本地磁盘（内存做缓存）
- 延迟：有序列化/反序列化开销，略高
- 容量：可达 TB 级，超出内存上限
- 适用：大状态、需要增量 checkpoint、长窗口的作业
```

## RocksDB

RocksDB 是 Flink 默认推荐的大状态存储引擎，一个基于 LSM-Tree 的嵌入式 KV 数据库，作为 EmbeddedRocksDBStateBackend 的底层把状态写到本地磁盘。它最大的价值是支持增量 checkpoint：每次只把上次快照以来的增量数据（SST 文件）上传到远端，大幅降低大状态作业的 checkpoint 时间与存储开销。同时 RocksDB 还支持状态本地恢复、TTL 压缩、布隆过滤器等优化，是生产环境大状态作业的事实标准。

```text
要点：
- 本质：LSM-Tree 结构的嵌入式 KV 数据库，作为状态后端底层
- 核心价值：增量 checkpoint，只上传变化的 SST 文件
- 支持：本地恢复（local recovery）、TTL 压缩、布隆过滤器
- 调优：block cache、write buffer、compaction 策略等
- 适用：GB~TB 级大状态、长窗口、需要高可用恢复的场景
```

RocksDB 状态后端的关键调优配置：

```java
EmbeddedRocksDBStateBackend backend = new EmbeddedRocksDBStateBackend(true);
env.setStateBackend(backend);

// 通过配置项调优 RocksDB
Configuration rocksConfig = new Configuration();
rocksConfig.set(RocksDBOptions.LOCAL_DIRECTORIES, "/data/rocksdb");
rocksConfig.set(RocksDBOptions.TIMER_SERVICE_FACTORY,
        RocksDBOptions.TimerServiceFactoryType.ROCKSDB);
backend.setRocksDBOptions(rocksConfig);
```

```text
RocksDB 调优要点：
- 增量 checkpoint：new EmbeddedRocksDBStateBackend(true) 开启
- 本地目录：SSD 上配置多个 LOCAL_DIRECTORIES 分散 I/O
- block cache：加大提升读性能，但占用堆外内存需控好
- 写放大：合理设置 write buffer 与 level compaction 减少写放大
- 定时器：TimerServiceFactory 用 RocksDB 存储定时器，避免堆内存占用
```

## 应用场景实战

### 场景一：Kafka 到 HBase 的 Exactly-Once 实时落库

实时订单数据从 Kafka 消费，经过聚合后写入 HBase，要求故障恢复后"既不丢也不重"。通过 enableCheckpointing + Exactly-Once 语义 + 可重放的 Kafka Source offset，配合 HBase 幂等写入实现端到端精确一次。

```java
public class ExactlyOnceJob {
    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env =
                StreamExecutionEnvironment.getExecutionEnvironment();

        // 精确一次语义 + 周期 checkpoint
        env.enableCheckpointing(30_000);
        env.getCheckpointConfig().setCheckpointingMode(CheckpointingMode.EXACTLY_ONCE);
        env.getCheckpointConfig().setMinPauseBetweenCheckpoints(10_000);
        env.getCheckpointConfig().setCheckpointStorage(
                "hdfs://namenode:8020/flink/checkpoints/exactly-once");
        // 大状态用 RocksDB 增量 checkpoint
        env.setStateBackend(new EmbeddedRocksDBStateBackend(true));

        Properties props = new Properties();
        props.setProperty("bootstrap.servers", "broker:9092");
        props.setProperty("group.id", "exactly-once-group");

        DataStream<OrderEvent> orders = env
                .addSource(new FlinkKafkaConsumer<>("orders",
                        new OrderEventDeserializer(), props))
                .uid("kafka-source-orders");

        orders.keyBy(OrderEvent::getShopId)
                .process(new ShopGmvFunction())
                .uid("shop-gmv-process")
                .addSink(new IdempotentHBaseSink())
                .uid("hbase-sink");

        env.execute("exactly-once-job");
    }
}
```

```java
// 幂等 Sink：用 orderId 做幂等键，checkpoint 完成后才提交
public class IdempotentHBaseSink extends RichSinkFunction<GmvResult>
        implements CheckpointedFunction {

    private transient ListState<GmvResult> pendingState;

    @Override
    public void open(Configuration parameters) {
        // 初始化 HBase 连接
    }

    @Override
    public void invoke(GmvResult value, Context context) throws Exception {
        pendingState.add(value);   // 先缓存，不直接写
    }

    @Override
    public void snapshotState(FunctionSnapshotContext context) throws Exception {
        // checkpoint 前把 pending 数据刷到 HBase（幂等写入）
        for (GmvResult r : pendingState.get()) {
            writeIdempotent(r);
        }
        pendingState.clear();
    }

    @Override
    public void initializeState(FunctionInitializationContext context) throws Exception {
        pendingState = context.getOperatorStateStore().getListState(
                new ListStateDescriptor<>("pending", GmvResult.class));
    }

    private void writeIdempotent(GmvResult r) {
        // 以 orderId 为 rowkey 幂等 upsert，重复写结果一致
    }
}
```

### 场景二：无停机作业升级与回滚（Savepoint）

线上作业需要升级逻辑，且要求升级失败时能快速回滚，不能丢状态。用 savepoint 保存当前状态，从 savepoint 启动新版本，出问题再从同一 savepoint 恢复旧版本，实现灰度与回滚。

```bash
# 1) 对运行中的作业触发 savepoint（不停止作业，先做快照）
flink savepoint <jobId> hdfs://namenode:8020/flink/savepoints/pre-upgrade

# 2) 停掉旧作业并保留 savepoint
flink cancel <jobId>

# 3) 从 savepoint 启动新版本作业（携带新 jar）
flink run -s hdfs://namenode:8020/flink/savepoints/pre-upgrade/savepoint-xxxx \
    -d /opt/jobs/order-count-v2.jar

# 4) 若新版本异常，从同一 savepoint 快速回滚到旧版本
flink run -s hdfs://namenode:8020/flink/savepoints/pre-upgrade/savepoint-xxxx \
    -d /opt/jobs/order-count-v1.jar
```

```text
升级回滚最佳流程：
1. 升级前先打 savepoint，确认快照成功且可读
2. 用 flink stop --savepointPath 优雅停止（先停源再快照，避免丢尾数据）
3. 从 savepoint 启动新版本，观察指标与结果正确性
4. 新版本异常时，从同一 savepoint 重启旧版本实现秒级回滚
5. 稳定运行一段时间后，清理不再需要的旧 savepoint
```

## 最佳实践与踩坑记录

### 最佳实践

1. checkpoint 间隔按"状态大小 + 可接受恢复窗口"权衡：小状态 1~5 分钟，大状态 10~15 分钟。
2. 大状态作业用 RocksDB 后端并开启增量 checkpoint，显著缩短 checkpoint 时间与存储。
3. 每个有状态算子都设稳定 uid，否则升级/改并行度后 savepoint 无法匹配状态。
4. 生产环境务必配置外部化 checkpoint（RETAIN_ON_CANCELLATION），作业取消后仍可恢复。
5. 升级前一律打 savepoint，用 flink stop --savepointPath 优雅停止，避免丢失尾部数据。
6. 高反压作业启用非对齐 checkpoint 或设置 alignedCheckpointTimeout 自适应降级。
7. 定期演练故障恢复，验证 checkpoint 目录可读、恢复耗时与结果正确性，而非等故障才发现。

### 踩坑记录

```text
坑 1：checkpoint 一直超时失败
结论：checkpoint 频繁超时，作业反复重启。
原因：状态过大、checkpoint 时间超过 timeout，或存储（HDFS/S3）带宽不足。
解法：增大 timeout、降低间隔、改用 RocksDB 增量 checkpoint、提升存储带宽。

坑 2：升级后作业无法从 savepoint 恢复
结论：flink run -s 报错，状态匹配失败。
原因：算子未设置 uid，或新代码改了算子链导致 uid 漂移，状态无法对齐。
解法：为所有有状态算子固定 uid，升级时保持 uid 与状态类型一致。

坑 3：作业取消后 checkpoint 被删除，无法恢复
结论：想恢复历史数据却发现 checkpoint 目录已空。
原因：未配置外部化 checkpoint，默认取消作业即清理 checkpoint。
解法：设置 ExternalizedCheckpointCleanup.RETAIN_ON_CANCELLATION。

坑 4：高反压作业 checkpoint 卡住导致雪崩
结论：反压严重时 checkpoint 迟迟无法完成，进一步拖垮作业。
原因：对齐机制等待慢分区，反压与 checkpoint 互相阻塞形成恶性循环。
解法：启用非对齐 checkpoint 或设置 alignedCheckpointTimeout 降级。

坑 5：内存后端状态过大导致 OOM
结论：状态增长到一定程度后 TaskManager 频繁 GC 甚至崩溃。
原因：HashMapStateBackend 状态全在堆内存，无上限增长。
解法：迁移到 RocksDB 后端，状态落盘，并配 TTL 清理过期状态。

坑 6：savepoint 从旧 Flink 版本无法恢复
结论：跨大版本升级时 savepoint 不兼容。
原因：Flink 大版本之间状态序列化格式可能不兼容。
解法：按官方升级路径逐版本升级，避免跨多个大版本直接跳升。
```
