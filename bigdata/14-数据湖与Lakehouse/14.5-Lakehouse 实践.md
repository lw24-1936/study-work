## 概述

Lakehouse 建起来只是开始，长期稳定运行靠的是运维与治理。本主题聚焦 Lakehouse 落地的四个日常工程问题：小文件治理（流式写入产生的海量小文件）、Compaction（合并与数据重排）、分区策略（分区字段与粒度的选择）、数据质量（Schema 校验与质量规则）、成本治理（冷热分层与资源优化）。这些是区分「能跑」和「能长期跑」的关键。

```text
Lakehouse 运维的四大工程问题：
1. 小文件 —— 流式微批写出的碎片文件，拖慢查询、膨胀元数据
2. 布局 —— 数据文件是否按查询习惯聚类，决定裁剪效率
3. 质量 —— 入口校验 + 定期质检，防止脏数据污染
4. 成本 —— 冷热分层 + 快照清理，控制存储成本
```

## 小文件治理

小文件是数据湖的头号性能杀手：每个文件有独立的元数据开销（对象存储 list、表格式 manifest 条目、NameNode 内存），海量小文件会让查询「元数据读取」的时间超过「数据扫描」。小文件主要来自流式微批写入（每批写几十 KB 的小文件）和过度分区。治理手段：控制写入批次大小、定期 Compaction 合并、合理的文件目标大小（512MB~1GB）。

```text
小文件危害与治理：
1. 危害 —— 元数据膨胀、list 变慢、查询裁剪失效
2. 来源 —— 流式微批、过度分区、频繁小批量写入
3. 治理 —— 增大写入批次 + Compaction 合并 + 目标文件大小
4. 目标 —— 单文件 512MB~1GB，分区内文件数控制在上千以内
```

```text
判断小文件问题：
- 表目录下文件数 >> 记录数/目标文件大小
- 查询时间主要花在「planning/listing」而非「scan」
- 表格式的 manifest 条目数爆炸
```

## Compaction 合并

Compaction 是把小文件合并成大文件、并按指定列重排数据的维护操作，是治理小文件的核心手段。三种表格式都有对应能力：Iceberg 用 rewrite_data_files，Hudi 用 Clustering/Compaction，Delta 用 OPTIMIZE。Compaction 通常由调度器定时触发（每天/每周），合并时可按主键或高频过滤列排序（Z-Order/Clustering），同时提升查询裁剪。

```text
Compaction 要点：
1. 合并小文件 —— 降低文件数、减少元数据开销
2. 重排数据 —— 按主键/过滤列排序，提升数据跳过
3. 触发 —— 定时任务（Airflow/DolphinScheduler），非实时
4. 写放大 —— 合并会重写数据，别高频跑
```

```sql
-- Iceberg：合并 + 按主键排序
CALL db.system.rewrite_data_files(
    table => 'db.orders',
    strategy => 'sort', sort_order => 'order_id ASC'
);

-- Delta：合并 + Z-Order 聚类
OPTIMIZE delta.`s3://warehouse/orders` ZORDER BY (user_id);
```

## 分区策略

分区是数据湖查询裁剪的第一道关口，分区字段和粒度直接决定查询性能。原则：分区字段选低基数、高频过滤的列（日期、状态、地域）；粒度选得让单分区大小适中（几 GB 到几十 GB）；高基数列（user_id）别做分区（会分区爆炸），改用 bucket 分桶或 Z-Order。分区过细（如按小时）会产生大量小分区和小文件，过粗则裁剪效率低。

```text
分区策略要点：
1. 分区字段 —— 低基数 + 高频过滤（日期/状态/地域）
2. 分区粒度 —— 单分区几 GB~几十 GB，太大裁剪差、太小文件碎
3. 高基数列 —— 别分区（爆炸），用 bucket(16, col) 或 Z-Order
4. 演进 —— Iceberg 支持改分区不重写数据（分区演进）
```

```text
分区粒度权衡：
按天分区 —— 适合日增几百 MB~几 GB 的表
按月分区 —— 适合日增很小、跨月查询多的表
按小时 —— 仅超高吞吐实时表，否则小文件泛滥
```

## 数据质量

Lakehouse 的数据质量靠「入口校验 + 定期质检」两层保障：入口靠表格式的 Schema Enforcement（Iceberg/Delta 写时校验类型和约束）拒绝脏数据；定期质检靠质量平台（Great Expectations、dbt test、自研规则引擎）跑规则（非空、唯一、范围、分布漂移），发现异常告警。质量规则要落到数据契约（Data Contract）里，生产者和消费者对齐口径。

```text
数据质量两层保障：
1. 入口校验 —— 表格式 Schema Enforcement（类型/非空/约束）
2. 定期质检 —— 质量规则平台（GE/dbt test）跑规则 + 告警
3. 数据契约 —— 生产者承诺的 schema + 质量 SLA，消费者据此消费
```

```python
# Great Expectations 示例：校验订单表
import great_expectations as ge

df = ge.read_parquet("s3://lake/gold/orders/")
result = df.expect_column_values_to_not_be_null("order_id") and \
         df.expect_column_values_to_be_unique("order_id") and \
         df.expect_column_values_to_be_between("amount", 0, 1000000)
assert result.success, "订单表质量校验失败"
```

## 成本治理

Lakehouse 的存储成本主要来自三处：全量快照/历史版本累积、冷热不分、小文件浪费的元数据开销。治理手段：配置快照保留期并定期 expire（Iceberg expire_snapshots、Delta VACUUM）；对象存储生命周期规则做冷热分层（热数据标准存储、冷数据归档）；压缩和去重减少冗余。计算成本则靠合理的表布局（分区/排序）减少扫描量。

```text
成本治理要点：
1. 快照清理 —— 定期 expire_snapshots / VACUUM，释放历史版本文件
2. 冷热分层 —— 生命周期规则自动降冷/归档
3. 压缩去重 —— Compaction 合并 + 去重减少冗余存储
4. 布局优化 —— 分区/排序好，查询少扫描，算力成本也降
```

```text
存储成本 = 数据量 × 副本 × 单价 × 留存时间
优化方向：压缩格式（Parquet+snappy）降数据量、生命周期降单价、expire 降留存
```

## 应用场景实战

### 场景一：定时小文件合并任务

```python
# Airflow DAG：每天凌晨跑 Iceberg 表的 Compaction
from airflow import DAG
from airflow.providers.apache.spark.operators.spark_submit import SparkSubmitOperator
from datetime import datetime, timedelta

default_args = {"owner": "data", "retries": 1, "retry_delay": timedelta(minutes=5)}

with DAG("iceberg_compaction", default_args=default_args,
         start_date=datetime(2024, 1, 1), schedule_interval="0 3 * * *") as dag:

    compact = SparkSubmitOperator(
        task_id="compact_orders",
        application="s3://jobs/compact.py",
        application_args=["--table", "db.orders", "--sort", "order_id"],
        conf={"spark.executor.memory": "8g"}
    )
```

### 场景二：质量告警 + 快照清理

```sql
-- 定期清理：释放 7 天前的旧快照（Iceberg）
CALL db.system.expire_snapshots('db.orders', TIMESTAMP '2024-08-07 00:00:00');
CALL db.system.remove_orphan_files(table => 'db.orders');

-- Delta 版本：清理 7 天前的软删除文件
VACUUM delta.`s3://warehouse/orders` RETAIN 168 HOURS;
```

## 最佳实践与踩坑记录

### 最佳实践

1. 流式写入必配 Compaction 定时任务，否则小文件爆炸
2. 分区选低基数列（日期/状态），高基数列用 bucket 或 Z-Order
3. 快照保留期按业务定（默认 7 天），定期 expire 释放空间
4. 数据质量「入口校验 + 定期质检」两手抓，别只靠入口
5. 对象存储开生命周期规则，冷数据自动降本
6. 文件目标大小 512MB~1GB，兼顾裁剪粒度和元数据开销

### 踩坑记录

```text
坑 1：流式写入从不 Compaction
结论：查询越来越慢，元数据读取成为瓶颈。
原因：微批写出的海量小文件无人合并。
解法：调度器定时跑 Compaction（rewrite_data_files/OPTIMIZE/Clustering）。

坑 2：分区字段选错（用高基数列分区）
结论：分区数量爆炸，每个分区只有几条数据。
原因：把 user_id 这类高基数列当分区字段。
解法：高基数列用 bucket 分桶或 Z-Order，分区只用低基数列。

坑 3：快照从不清理
结论：存储成本持续上涨，历史版本文件堆积。
原因：表格式每次写都产生新快照，旧文件软删除但没物理清理。
解法：定期 expire_snapshots / VACUUM，配合 remove_orphan_files。

坑 4：只做入口校验不做定期质检
结论：schema 合法但业务上错的脏数据（如金额为负）长期混在表里。
原因：Schema Enforcement 只查类型不查业务规则。
解法：质量平台跑业务规则（范围/唯一/分布），异常告警。

坑 5：Compaction 跑太频繁
结论：写放大严重，成本不降反升。
原因：Compaction 每次重写数据，高频跑等于反复搬数据。
解法：按数据增长节奏定频率（日增大的表每天，小的每周），别小时级跑。
```
