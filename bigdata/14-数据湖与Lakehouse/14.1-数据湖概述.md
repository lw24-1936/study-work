## 概述

数据湖（Data Lake）是把企业所有原始数据（结构化、半结构化、非结构化）以原生格式集中存储在一个低成本、可扩展存储池（对象存储/HDFS）上的架构。它区别于数据仓库「先定义结构再入数」的方式，采用「先存原始数据、读取时再定义结构」（Schema-on-Read），因此能以低成本保留全部历史数据，等需要时再加工。数据湖是 Lakehouse 的底座，也是 Medallion（青铜/白银/黄金）分层落地的载体。

```text
数据湖的核心特征：
1. 存全量原始数据 —— 结构化+半结构化+非结构化，原生格式落地
2. 低成本 —— 对象存储（S3/OSS）比数仓存储便宜一个数量级
3. Schema-on-Read —— 读时定义结构，写入无需预先建模
4. 多引擎 —— Spark/Flink/Trino/Hive 都能读写同一份数据
5. 开放格式 —— Parquet/ORC/Iceberg/Hudi，不锁定厂商
```

## Data Lake 数据湖

数据湖的核心思想是「先收数据、再谈结构」：把来自业务库、日志、埋点、传感器、音视频等各种数据源的数据，以接近原始的形式灌进一个统一的大池子。相比数仓，它省去了繁琐的入库建模，缩短了「数据产生到可用」的时间，也避免了「只存了加工后的数据、原始数据丢了」的风险。代价是数据质量、治理、查询性能需要额外建设（这正是 Lakehouse 补齐的部分）。

```text
数据湖 vs 数据仓库：
1. 数据 —— 湖存全量原始（含未清洗），仓存已加工、结构化的
2. 结构 —— 湖读时定义（Schema-on-Read），仓写时定义（Schema-on-Write）
3. 成本 —— 湖便宜（对象存储），仓贵（专用存储+算力）
4. 质量 —— 湖需自建治理，仓自带治理
5. 使用 —— 湖面向数据科学/探索，仓面向 BI/报表
```

## Object Storage 对象存储

对象存储（S3、OSS、GCS、MinIO）是数据湖的默认存储底座：它用扁平的「桶 + 对象键」模型替代文件系统的目录树，通过 HTTP API 访问，具备近乎无限的扩展能力、极高的持久性（11 个 9）和低成本。对象存储牺牲了低延迟随机读写和目录遍历性能，换来海量吞吐和弹性，恰好匹配数据湖「大量顺序读写、极少随机更新」的访问模式。

```text
对象存储 vs HDFS：
1. 扩展性 —— 对象存储近乎无限，HDFS 受 NameNode 内存限制
2. 成本 —— 对象存储便宜（冷热分层），HDFS 需自建集群
3. 一致性 —— 对象存储（多数）强一致，HDFS 强一致
4. 性能 —— 对象存储单对象吞吐高但 list 慢，HDFS 随机读更好
5. 运维 —— 对象存储托管免运维，HDFS 需自己维护
```

```text
对象存储关键特性（以 S3 为例）：
- 桶（Bucket）：顶级命名空间，全局唯一
- 对象键（Key）：桶内唯一，形如 warehouse/db/table/part-xxx.parquet
- 一致性：现代对象存储对 PUT/LIST 提供强一致
- 分层：Standard/Infrequent-Access/Glacier，冷数据降本
```

## Schema-on-Read 读时模式

Schema-on-Read 指数据写入时不强制套用表结构，而是在读取（分析）时才定义/解析结构。它让数据能以原始格式快速落地（采集即存储），结构定义推迟到使用环节，从而保留最大的灵活性——同一个原始数据可以被不同分析以不同结构解读。代价是读时要做解析（慢）、且数据质量问题（脏数据、类型错）在读取时才暴露。

```text
Schema-on-Read vs Schema-on-Write：
1. 写入 —— on-Read 无需建模直接落地，on-Write 必须先定义表结构
2. 速度 —— on-Read 采集快，on-Write 入库慢（要清洗校验）
3. 灵活 —— on-Read 结构可变，on-Write 结构固定
4. 质量 —— on-Read 质量后置（读到才发现），on-Write 入口把关
5. 趋势 —— Lakehouse 用表格式（Iceberg/Hudi/Delta）给 on-Read 补上 on-Write 的质量保障
```

## Bronze-Silver-Gold 分层

Medallion（奖牌）架构把数据湖分成三层：Bronze（青铜）存原始贴源数据（原样落地，只加来源和采集时间），Silver（白银）存清洗、去重、规范化后的数据（口径统一，可被多个下游复用），Gold（黄金）存面向业务的分析就绪数据（聚合宽表、报表结果）。这三层对应数仓的 ODS/DWD/DWS-ADS，是数据湖里组织数据质量的通用范式。

```text
Medallion 三层：
1. Bronze（青铜）—— 原始数据，贴源落地，只做采集不加工
2. Silver（白银）—— 清洗去重、类型规范、口径统一，企业级可复用
3. Gold（黄金）—— 业务就绪，聚合宽表/报表结果，直接消费
```

```text
Bronze → Silver → Gold 数据流：
原始日志/CDC → Bronze（原样）→ Silver（清洗规范）→ Gold（聚合就绪）
   （增量追加）      （可重复加工）       （供 BI/产品）
```

## 数据湖与数仓、Lakehouse 的关系

数据湖解决了「存得便宜、存得全」，数据仓库解决了「查得快、口径统一」，Lakehouse 是两者的融合——在数据湖（对象存储 + 开放格式）之上，用表格式（Iceberg/Hudi/Delta）加事务、Schema 演进、时间旅行，让同一份数据既能做数据湖的探索分析，也能做数仓的 BI 报表，避免「湖仓之间导来导去」。这是当前大数据架构的主流演进方向。

```text
三者关系：
数据湖（存全量原始 + 低成本）
   + 表格式（ACID/Schema 演进/时间旅行）
   = Lakehouse（湖仓一体，一份数据多用途）
数据仓库（专用存储 + 强治理 + 高性能）→ 与 Lakehouse 并存，各司其职
```

## 应用场景实战

### 场景一：日志数据入湖的 Medallion 分层

```python
# 原始日志 → Bronze → Silver → Gold
from pyspark.sql import SparkSession

spark = SparkSession.builder.getOrCreate()

# Bronze：原始日志贴源落地（只加采集时间）
raw = spark.read.json("s3://raw/logs/2024/08/14/")
raw.withColumn("ingest_time", spark.sql("current_timestamp()")) \
   .write.mode("append").format("parquet").save("s3://lake/bronze/logs/")

# Silver：清洗去重、类型规范、字段统一
bronze = spark.read.parquet("s3://lake/bronze/logs/")
silver = bronze.dropDuplicates(["event_id"]) \
    .withColumnRenamed("uid", "user_id") \
    .na.fill({"event_type": "unknown"})
silver.write.mode("append").format("delta").save("s3://lake/silver/logs/")

# Gold：按天聚合的指标宽表
gold = silver.groupBy("user_id", "event_type").count()
gold.write.mode("overwrite").format("delta").save("s3://lake/gold/log_metrics/")
```

### 场景二：用对象存储做冷热分层降本

```text
冷热分层策略：
热数据（近 7 天）  → S3 Standard，供高频查询
温数据（7~90 天）  → S3 Infrequent-Access，低频访问
冷数据（90 天以上）→ S3 Glacier，归档，极低成本
实现：对象存储生命周期规则自动迁移，或 Iceberg 表按分区搬迁
```

## 最佳实践与踩坑记录

### 最佳实践

1. 原始数据永远进 Bronze 层留底，别只存加工后的结果
2. 用开放格式（Parquet/ORC + Iceberg/Hudi/Delta），避免厂商锁定
3. 数据落地即分区（按时间），后续查询裁剪
4. Bronze 贴源不加业务逻辑，Silver 做清洗规范化，Gold 做业务聚合
5. 对象存储开生命周期规则做冷热分层降本
6. 治理靠元数据目录（Catalog）+ 血缘，别让数据湖变成「数据沼泽」

### 踩坑记录

```text
坑 1：数据湖变数据沼泽
结论：数据堆了一堆，谁也找不到、不知道能不能用。
原因：只存不治理，没有元数据目录、没有分层、没有质量校验。
解法：建 Medallion 分层 + 元数据目录 + 数据质量规则 + 血缘。

坑 2：把数据湖当数据库做随机读写
结论：频繁的小文件随机更新，性能极差、成本爆炸。
原因：对象存储为顺序大文件优化，不支持高效随机改写。
解法：随机更新用表格式（Hudi/Iceberg 的 Upsert）或转到适合的存储。

坑 3：list 对象存储目录做查询
结论：查询前 list 百万对象，比查询本身还慢。
原因：对象存储 list 是 O(对象数) 的慢操作。
解法：用表格式的 manifest/元数据定位文件，别直接 list。

坑 4：Schema-on-Read 变成「读到才发现全是脏数据」
结论：分析时才暴露大量类型错、空值、重复。
原因：写入无校验，质量后置。
解法：Silver 层做清洗校验，或用表格式的 Schema Enforcement。

坑 5：冷热不分，全放标准存储
结论：海量冷数据占用昂贵的热存储，成本失控。
原因：没做冷热分层。
解法：对象存储生命周期规则自动降冷，归档冷数据。
```
