## 概述

Delta Lake 是 Databricks 开源的存储层（表格式），在 Parquet 文件之上加了一层事务日志，给数据湖带来 ACID 事务、版本管理、时间旅行、模式强制与演进、批流一体（同一张表既能批读也能流读）等能力。它深度集成 Spark，是 Spark 生态里最顺手的 Lakehouse 方案，也是 Databricks 平台默认的存储格式。Delta 的架构核心是「Parquet 数据文件 + JSON 事务日志」。

```text
Delta Lake 核心能力：
1. ACID —— 事务日志保证并发写和读的一致性
2. Time Travel —— 按版本/时间戳查历史数据
3. Schema Enforcement —— 写入数据必须符合表结构，防止脏数据
4. Schema Evolution —— 在线增列演进
5. 批流一体 —— 同一张 Delta 表既是批读源也是流读源
```

```text
Delta 表目录结构：
/table/
├── _delta_log/          # 事务日志（核心元数据）
│   ├── 000000.json      # 每个版本一个 JSON（commit 记录）
│   └── 000001.checkpoint.parquet  # 检查点（定期合并历史日志）
└── part-00000-xxx.parquet  # 数据文件（Parquet）
```

## Transaction Log 事务日志

事务日志是 Delta Lake 的元数据中枢，记录对表的所有变更（增删数据文件、改 schema、改属性）。每次提交追加一个 JSON 文件（按版本号命名 000000.json、000001.json...），里面记录这次操作改动了哪些 Parquet 文件。读表时先重放事务日志，得到当前表的文件清单。为避免日志文件太多导致重放变慢，Delta 定期把日志合并成 checkpoint（Parquet 格式的快照），读时只需读最近的 checkpoint + 少量后续 JSON。

```text
事务日志要点：
1. 追加式 —— 每次 commit 一个 JSON，永不修改历史
2. 内容 —— 记录 add/remove 的 Parquet 文件 + 统计 + schema 变更
3. checkpoint —— 定期合并日志为 Parquet 快照，加速元数据读取
4. 单写者 —— 默认靠乐观并发，写冲突靠 _last_checkpoint 和版本号 CAS
```

```json
// _delta_log/000001.json —— 一次 commit 的日志内容（示意）
{
  "commitInfo": { "timestamp": 1723600000000, "operation": "WRITE" },
  "add": {
    "path": "part-00000-abc.parquet",
    "partitionValues": {"dt": "2024-08-14"},
    "size": 1048576,
    "stats": "{\"numRecords\":1000,\"minValues\":{\"order_id\":1},\"maxValues\":{\"order_id\":1000}}"
  }
}
```

## ACID 事务保证

Delta Lake 通过事务日志实现 ACID：原子性靠「日志 commit 一次性生效」，一致性靠写入时校验约束，隔离性靠乐观并发控制（写前记录起始版本、提交时对比版本号，冲突则重试或失败），持久性靠日志落盘。并发写同一张表时，只有一个写者能成功提交，其他冲突写入会重试（默认）或报错。这解决了数据湖「并发写、读到半成品」的老问题。

```text
ACID 实现要点：
1. 原子性 —— commit 要么整个生效要么不生效，读到的是完整版本
2. 一致性 —— 写入可配 NOT NULL/CHECK 约束，非法数据拒绝
3. 隔离性 —— 乐观并发（版本号 CAS），冲突写重试
4. 持久性 —— 事务日志落盘后 commit 才可见
```

```python
# Delta 表并发写由乐观锁保证
from delta.tables import DeltaTable

dt = DeltaTable.forPath(spark, "s3://warehouse/orders")

# 带条件的原子更新（Upsert）
dt.alias("t").merge(
    updates.alias("s"),
    "t.order_id = s.order_id"
).whenMatchedUpdateAll().whenNotMatchedInsertAll().execute()
```

## Version 版本与 Time Travel

每次 commit 给表一个递增的版本号，Time Travel 就是按版本号（或时间戳）查询历史状态。它用于审计（看数据怎么变的）、误删恢复（读删除前版本）、实验复现（固定版本出数）。Delta 里用 VERSION AS OF 或 TIMESTAMP AS OF 指定历史版本，底层是把事务日志重放到对应版本。

```text
版本与时间旅行要点：
1. 版本号 —— 从 0 递增，每次 commit +1
2. 时间旅行 —— VERSION AS OF <n> / TIMESTAMP AS OF <ts>
3. 历史保留 —— 由日志保留策略决定，默认保留 30 天
4. 恢复 —— RESTORE 把表回滚到历史版本（会生成新版本）
```

```sql
-- 查历史版本
SELECT * FROM delta.`s3://warehouse/orders` VERSION AS OF 10;

SELECT * FROM delta.`s3://warehouse/orders` TIMESTAMP AS OF '2024-08-14 00:00:00';

-- 回滚（生成新版本）
RESTORE TABLE delta.`s3://warehouse/orders` TO VERSION AS OF 8;
```

## Schema Enforcement 模式强制

Schema Enforcement 指写入的数据必须符合表的 schema——列类型不匹配、缺少非空列、出现未知列（默认）都会拒绝写入，防止脏数据污染表。它靠事务日志里记录的 schema 在写入时校验实现。这是 Delta 相比「纯文件湖」的进步：数据湖时代写错了类型也没人发现，Delta 在入口就把关。

```text
模式强制要点：
1. 类型匹配 —— int 写进 long 列报错（反之也拒绝，除非自动提升）
2. 非空约束 —— NOT NULL 列写入 null 拒绝
3. 未知列 —— 默认拒绝，可开 mergeSchema 允许
4. 写时校验 —— 违规数据整批拒绝，保证表内数据干净
```

```python
# 写未知列默认报错
df_with_extra_col.write.mode("append") \
    .option("mergeSchema", "false") \
    .save("s3://warehouse/orders")   # 若 df 含表里没有的列 → 报错
```

## Schema Evolution 模式演进

Schema Evolution 允许在线修改表结构（加列、改类型、重命名），不需要重写旧数据。最常用的是「加列」（append 新列，旧数据该列为 null），以及类型的安全提升（int → long）。演进靠事务日志记录 schema 变更实现。开 mergeSchema 后，写入数据带新列时自动加列，是流式场景里字段不断扩展的标配。

```text
模式演进要点：
1. 加列 —— ALTER TABLE ADD COLUMN，旧数据补 null
2. 自动演进 —— 写时 mergeSchema=true，新列自动加入
3. 类型提升 —— int→long、float→double 等安全提升自动发生
4. 不支持的 —— 删列/改列名/降级类型，需要重写表
```

```sql
-- 手动加列
ALTER TABLE delta.`s3://warehouse/orders` ADD COLUMN discount DECIMAL(10,2);

-- 流式写入自动演进 schema
df.writeStream.format("delta") \
    .option("mergeSchema", "true") \
    .option("checkpointLocation", "s3://checkpoint/orders") \
    .start("s3://warehouse/orders")
```

## Optimize 与 Z-Order

Optimize 是 Delta 的压缩/优化命令：把小文件合并成大文件，减少文件数量、提升查询效率。Z-Order（ZORDER BY）是 Optimize 的可选聚类方式，把数据按指定列做多维聚类重排，让同一列值相近的行落在相近的文件里，大幅提升该列过滤查询的裁剪效率（类似数据库的多维索引）。

```text
Optimize 与 Z-Order 要点：
1. Optimize —— 合并小文件（bin-packing），提升扫描效率
2. Z-Order —— 按列多维聚类，提升过滤查询的数据跳过
3. 适用 —— 高基数列（如 user_id、order_id）做 ZORDER BY，低基数列（如日期）用分区
4. 频率 —— 定时跑（写放大场景每天/每周），别高频跑
```

```sql
-- 合并小文件
OPTIMIZE delta.`s3://warehouse/orders`;

-- 按 user_id 做 Z-Order 聚类
OPTIMIZE delta.`s3://warehouse/orders` ZORDER BY (user_id);
```

## Vacuum 清理

Vacuum 清理被事务日志标记为删除、且超过保留期（默认 7 天）的旧数据文件，释放存储空间。删除和更新操作只是在新版本里「移除」旧文件引用，旧文件物理上还在（为了 Time Travel），Vacuum 才是真正删文件。保留期默认 7 天，即 7 天内的历史版本可 Time Travel，7 天后文件被清、历史不可查。

```text
Vacuum 要点：
1. 删除文件是软删除 —— 事务日志 remove，物理文件还在
2. Vacuum —— 清理超过保留期的软删除文件，真正释放空间
3. 保留期 —— 默认 7 天（delta.deletedFileRetentionDuration），可调
4. 风险 —— 清理后历史版本不可 Time Travel，别设太短
```

```sql
-- 清理 7 天前的旧文件
VACUUM delta.`s3://warehouse/orders` RETAIN 168 HOURS;

-- 表属性配置保留期
ALTER TABLE delta.`s3://warehouse/orders`
SET TBLPROPERTIES ('delta.deletedFileRetentionDuration' = 'interval 7 days');
```

## 应用场景实战

### 场景一：批流一体的订单表

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

spark = SparkSession.builder \
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension") \
    .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog") \
    .getOrCreate()

# 建 Delta 表
spark.sql("""
    CREATE TABLE delta_orders (
        order_id BIGINT, user_id BIGINT, amount DECIMAL(10,2), dt DATE
    ) USING delta PARTITIONED BY (dt)
""")

# 批写入
spark.sql("""
    INSERT INTO delta_orders VALUES
    (1, 100, 99.9, '2024-08-14'),
    (2, 101, 199.0, '2024-08-14')
""")

# 流读同一张表（批流一体）
stream = spark.readStream.format("delta").load("spark-warehouse/delta_orders")
stream.writeStream.format("console").start()
```

### 场景二：Upsert 合并与历史回滚

```python
from delta.tables import DeltaTable

dt = DeltaTable.forPath(spark, "spark-warehouse/delta_orders")

# Merge（Upsert）
dt.alias("t").merge(
    spark.createDataFrame([(1, 100, 150.0)], ["order_id", "user_id", "amount"]).alias("s"),
    "t.order_id = s.order_id"
).whenMatchedUpdate(set={"amount": "s.amount"}) \
 .whenNotMatchedInsertAll().execute()

# 查看版本历史
dt.history().select("version", "timestamp", "operation").show(truncate=False)

# 回滚到上一个版本
dt.restoreToVersion(dt.history().select("version").collect()[-2][0])
```

## 最佳实践与踩坑记录

### 最佳实践

1. 高基数列（user_id/order_id）用 Z-Order，低基数列（日期/状态）用分区
2. 写多场景定期跑 OPTIMIZE 合并小文件，但别太频繁（有写放大）
3. VACUUM 保留期别设太短，留足 Time Travel 时间（默认 7 天合适）
4. 流式写入开 mergeSchema=true，应对字段扩展
5. 关键表开 Delta 的 OPTIMIZE + ZORDER，查询性能提升明显
6. 用 MERGE 做幂等 Upsert，天然去重
7. checkpoint 定期生成（日志多了读元数据会慢）

### 踩坑记录

```text
坑 1：VACUUM 太激进导致历史不可查
结论：想回滚到 3 天前，发现文件已被清理。
原因：VACUUM 清掉了超过保留期的软删除文件，历史版本失效。
解法：保留期 ≥ 业务需要的最长回滚时间，默认 7 天别乱改短。

坑 2：不跑 OPTIMIZE，小文件爆炸
结论：流式写入长期累积，查询扫描成千上万小文件变慢。
原因：流式微批每次写小文件，无合并。
解法：定期 OPTIMIZE + ZORDER，控制文件大小和数量。

坑 3：mergeSchema 误开导致 schema 失控
结论：表结构被写入数据不断「污染」，出现大量杂散列。
原因：mergeSchema=true 让任意新列自动加入表。
解法：只在明确的字段扩展场景开，平时关闭或严格管控。

坑 4：并发写同一表冲突
结论：写入失败报 ConcurrentAppendException。
原因：乐观并发下两个写者同时 commit，版本冲突。
解法：依赖 Delta 自动重试，或业务上避免同表并发写（串行化）。

坑 5：把 Delta 表当普通 Parquet 目录读
结论：读到半成品或看不到最新数据。
原因：绕过了事务日志，直接读 Parquet 目录看不到未 checkpoint 的变更。
解法：始终用 Delta 接口读（delta.`path` 或 DeltaTable）。
```
