## 概述

Apache Hudi（Hadoop Upserts Deletes and Incrementals）是面向「增量更新」的数据湖表格式，核心价值是让 HDFS/对象存储上的数据湖支持记录级的 UPSERT 和 DELETE，同时提供增量查询能力。它通过 COW/MOR 两种存储模式在「读性能」和「写延迟」间权衡，配合 Timeline 实现幂等写入、回滚和增量拉取。Hudi 是 CDC 数据入湖、流式更新宽表的常用选择。

```text
Hudi 的核心能力：
1. 记录级 Upsert —— 按主键更新/插入，数据湖上也能像数据库一样改数据
2. 增量查询 —— 拉取两次提交之间的变更（changelog），做增量 ETL
3. 两种模式 —— COW（读优化）与 MOR（写优化）
4. Timeline —— 记录每次提交的元数据，支持回滚、恢复、并发控制
5. 自动小文件治理 —— 写入时合并小文件，内嵌 Clustering
```

```text
Hudi 与 Iceberg/Delta 的定位差异：
Hudi —— 强在增量更新（upsert/增量拉取），CDC 入湖首选
Iceberg —— 强在元数据演进（分区演进/时间旅行/多引擎）
Delta —— 强在 Spark 生态整合 + 流批一体
```

## COW 与 MOR 两种表类型

COW（Copy-on-Write）和 MOR（Merge-on-Read）是 Hudi 的两种存储模式。COW 写入时重写整个受影响的数据文件（把更新合并进新文件），读时直接读列式文件，读性能最好、写放大严重，适合读多写少。MOR 写入时只追加增量日志（Log/Delta 文件），读时实时合并 Base 文件和 Log 文件，写延迟低、读要合并，适合写多读少或需要低延迟写入的场景。

```text
COW vs MOR 对比：
1. 写入 —— COW 重写数据文件（慢、放大），MOR 追加日志（快）
2. 读取 —— COW 直接读（快），MOR 需合并 base+log（慢）
3. 存储 —— COW 列式文件，MOR 列式 base + 行式 log
4. 适用 —— COW 读多写少/批更新，MOR 写多读少/低延迟流式更新
```

```sql
-- 建 COW 表
CREATE TABLE hudi_orders (
    order_id BIGINT, user_id BIGINT, amount DECIMAL(10,2), ts TIMESTAMP,
    PRIMARY KEY(order_id) NOT ENFORCED
) PARTITIONED BY (date_format(ts, 'yyyyMMdd'))
USING hudi
TBLPROPERTIES (type='cow');

-- 建 MOR 表
CREATE TABLE hudi_orders_mor (
    order_id BIGINT, user_id BIGINT, amount DECIMAL(10,2), ts TIMESTAMP,
    PRIMARY KEY(order_id) NOT ENFORCED
) USING hudi
TBLPROPERTIES (type='mor');
```

## Timeline 时间轴

Timeline 是 Hudi 的核心元数据概念：记录表上所有动作（提交、压缩、清理、回滚）的时间线，是 Hudi 保证事务性和可恢复性的基础。Timeline 由一组按时间排序的 Instant 组成，存储在表目录的 .hoodie 元数据目录下。读写操作都要先查 Timeline 判断表的当前状态（哪些 commit 已完成、哪些进行中），据此决定可见数据。

```text
Timeline 要点：
1. 位置 —— 表目录下 .hoodie/ 目录
2. 组成 —— 按时间排序的 Instant（每个动作一个）
3. 状态 —— requested / inflight / completed 三态
4. 作用 —— 事务性（幂等）、并发控制、故障恢复、增量拉取
```

```text
.hoodie/ 目录结构：
.hoodie/
├── hoodie.properties          # 表配置（表类型、键等）
├── 20240814100000.commit      # 完成的 commit
├── 20240814110000.deltacommit # MOR 的增量提交
├── 20240814120000.compaction  # 压缩动作
└── 20240814130000.clean       # 清理动作
```

## Instant 与 Action

Instant 是 Timeline 上的一个时间点，代表一次操作；Action 是操作类型。Instant 有三态：requested（请求已提出）、inflight（正在执行）、completed（已完成）。Hudi 用这三态实现故障恢复：写失败留下的 inflight 状态会被下一次写入识别并回滚（或重试），保证不产生「半提交」的脏数据。常见 Action 类型有 commit（COW 提交）、deltacommit（MOR 增量提交）、compaction（压缩）、clean（清理）、rollback（回滚）。

```text
Instant 三态与 Action 类型：
1. 三态 —— requested → inflight → completed，写文件用 .requested/.inflight/.commit 后缀标记
2. commit —— COW 表的数据提交
3. deltacommit —— MOR 表追加日志的提交
4. compaction —— MOR 把 log 合并进 base
5. clean —— 清理旧版本文件
6. rollback —— 回滚失败的提交（恢复 inflight 残留）
```

## Upsert 更新机制

Upsert 是 Hudi 的标志能力：按主键判断记录是「更新」还是「插入」，更新的记录用新值覆盖旧值，插入的记录追加新文件。实现上依赖 Index 定位「旧记录在哪个文件」，然后 COW 模式重写该文件（合并新值），MOR 模式把更新追加到 log 文件。它让流式 CDC 数据可以幂等地反复写入同一张表，天然去重。

```text
Upsert 机制要点：
1. 主键 —— 表定义的主键，用于定位记录
2. 定位 —— 通过 Index 找旧记录所在文件
3. COW —— 重写受影响文件（读新值直接可见）
4. MOR —— 更新写 log，读时合并
5. 幂等 —— 同主键重复写自动覆盖，天然去重
```

```python
# PySpark 写入 Hudi（Upsert 模式）
from pyspark.sql import SparkSession

spark = SparkSession.builder.getOrCreate()

df = spark.read.format("json").load("s3://raw/orders_update.json")

df.write.format("hudi") \
    .option("hoodie.datasource.write.recordkey.field", "order_id") \
    .option("hoodie.datasource.write.precombine.field", "ts") \
    .option("hoodie.datasource.write.operation", "upsert") \
    .option("hoodie.table.name", "hudi_orders") \
    .mode("append") \
    .save("s3://warehouse/hudi_orders")
```

## Index 索引

Index 是 Hudi 定位「一条记录在哪个文件」的机制，是 Upsert 性能的关键。它把主键映射到 file-group，写入时据此判断是更新还是插入。索引类型有 Bloom Filter Index（默认，用文件级布隆过滤器判断记录是否在某文件）、Simple Index（join 现有键）、HBase Index（外置 HBase 存键映射）、Bucket Index（按主键哈希分桶，固定映射）。

```text
Index 类型与选择：
1. Bloom Filter Index —— 默认，写文件时生成 bloom，Upsert 时快速判断，开销小
2. Simple Index —— 全量 join 现有键，小表/全键场景
3. HBase Index —— 键映射存 HBase，大规模键、跨表更新场景
4. Bucket Index —— 主键哈希到固定桶，写入无需全局索引，最新推荐
```

## Clustering 聚类

Clustering 是 Hudi 的文件重组机制：把分散的小文件按指定列（如主键、分区列）重新排列合并成大文件，改善数据布局、提升查询裁剪效率。它类似数据库的「重整/聚类索引」，和 Compaction 不同——Compaction 是 MOR 的 log 合并进 base，Clustering 是对数据文件做重排。Hudi 支持异步 Clustering（写时并发执行），不影响写入延迟。

```text
Clustering 要点：
1. 目的 —— 小文件合并 + 数据按列重排，提升查询裁剪
2. 与 Compaction 区别 —— Compaction 合并 log，Clustering 重排数据文件
3. 异步 —— 可配置 inline（写入内嵌）或异步（后台任务）
4. 配置 —— hoodie.clustering.plan.strategy（按分区/文件数触发）
```

```text
# 关键配置（写时自动触发 Clustering）
hoodie.clustering.inline=true
hoodie.clustering.inline.max.commits=4          # 每 4 次提交触发一次
hoodie.clustering.plan.strategy.sort.columns=order_id  # 按 order_id 排序
```

## 应用场景实战

### 场景一：CDC 数据实时入湖（Upsert）

```python
# MySQL binlog → Kafka → Spark Streaming → Hudi（按主键 Upsert）
from pyspark.sql import SparkSession
from pyspark.sql.functions import from_json, col

spark = SparkSession.builder \
    .config("spark.sql.extensions", "org.apache.spark.sql.hudi.HoodieSparkSessionExtension") \
    .getOrCreate()

# 从 Kafka 读 CDC 变更流
stream = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "kafka:9092") \
    .option("subscribe", "orders_cdc") \
    .load()

parsed = stream.select(from_json(col("value").cast("string"), schema).alias("data")) \
    .select("data.*")

def upsert_to_hudi(df, epoch_id):
    df.write.format("hudi") \
        .option("hoodie.datasource.write.recordkey.field", "order_id") \
        .option("hoodie.datasource.write.precombine.field", "ts") \
        .option("hoodie.datasource.write.operation", "upsert") \
        .option("hoodie.table.name", "hudi_orders") \
        .mode("append") \
        .save("s3://warehouse/hudi_orders")

parsed.writeStream \
    .foreachBatch(upsert_to_hudi) \
    .option("checkpointLocation", "s3://checkpoint/hudi_orders") \
    .start().awaitTermination()
```

### 场景二：增量拉取做下游 ETL

```python
# 增量读 Hudi 表：拉取某个 commit 之后的所有变更
incremental_df = spark.read.format("hudi") \
    .option("hoodie.datasource.query.type", "incremental") \
    .option("hoodie.datasource.read.begin.instanttime", "20240814100000") \
    .load("s3://warehouse/hudi_orders")

# 把增量变更同步到下游数仓
incremental_df.write.mode("append").saveAsTable("dwd_order_delta")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 主键必须唯一且稳定，precombine 字段用单调递增的时间戳（保证同主键取最新）
2. 读多写少用 COW，写多读少或低延迟用 MOR
3. MOR 表定期做 Compaction，否则 log 文件堆积导致读变慢
4. CDC 入湖用 Upsert 操作 + 主键，天然幂等去重
5. 配置 Clustering 按主键重排，提升下游查询裁剪
6. 小文件治理靠 Clustering + 写入时 file size 上限
7. 用 Bucket Index 或 Bloom Index，别默认用全局 Simple Index（大数据量会慢）

### 踩坑记录

```text
坑 1：MOR 表不 Compaction，读性能越来越差
结论：查询要合并越来越多的 log 文件，延迟飙升。
原因：MOR 写入只追加 log，不合并进 base，log 堆积。
解法：定期跑 Compaction（内嵌或调度任务），把 log 合并进 base。

坑 2：precombine 字段没设好导致更新顺序错乱
结论：同主键多条更新，旧值覆盖新值。
原因：precombine 字段非单调，Upsert 时选了错误的最大值。
解法：precombine 用事件时间/时间戳等单调字段，保证取最新值。

坑 3：频繁小批量写入导致大量小文件
结论：查询变慢，元数据膨胀。
原因：流式微批每次写一小批，文件都很小。
解法：配 Clustering + hoodie.parquet.small.file.limit 合并，控制文件大小。

坑 4：写失败留下 inflight 残留
结论：下次读写报错或数据不一致。
原因：任务中断，Instant 停在 inflight 态。
解法：Hudi 会自动回滚 inflight 残留；手动用 hoodie-cli 的 rollback 命令清理。

坑 5：误用 COW 做高频小批量更新
结论：写放大严重，每次更新重写整个文件。
原因：COW 每次 Upsert 都重写受影响数据文件。
解法：高频更新场景改用 MOR，或降低更新频率、增大批大小。
```
