## 概述

Apache Iceberg 是面向海量分析场景的开放表格式（Table Format），解决的是「Hive 表在对象存储/分布式文件系统上不好用」的问题：它把表定义成三层元数据（metadata → manifest → data files），给数据湖带来事务 ACID、Schema 演进、分区演进、时间旅行、行级更新等能力，同时保持底层文件对任意引擎（Spark、Flink、Trino）开放可读。Iceberg 是 Lakehouse 架构的默认存储底座之一。

```text
Iceberg 解决的核心问题（对比 Hive 表）：
1. 分区不再写死目录 —— 隐藏分区，分区字段与物理目录解耦，改分区不重写数据
2. 表有版本 —— 每次提交生成快照，可回滚、可时间旅行
3. 元数据是文件 —— 不依赖 Hive Metastore，元数据自包含、可被多引擎并发读
4. 列级统计 —— manifest 里记录每列的 min/max/null 计数，查询时做文件级裁剪
5. 行级更新 —— v2 支持 Copy-on-Write 与 Merge-on-Read，支持 UPDATE/DELETE/MERGE
```

```text
Iceberg 三层元数据：
metadata.json（表版本）→ manifest list（快照清单）→ manifest（文件清单）→ data files（Parquet/ORC）
```

## Metadata 元数据层

Iceberg 的表状态由 metadata.json 描述，它是表的最顶层元数据文件，记录表结构（Schema）、分区规格（Partition Spec）、排序规则（Sort Order）、当前快照（Current Snapshot）和快照历史（Snapshot Log）。每次提交都会生成一个新的 metadata.json（版本号递增），旧版本保留用于回滚。客户端通过 Catalog 定位到当前 metadata.json，再逐层向下读 manifest 和 data files。

```text
metadata.json 关键字段：
1. schema —— 表结构，带 schema-id，支持多版本共存
2. partition-spec —— 分区字段与分区变换，带 spec-id
3. current-snapshot-id —— 当前生效的快照
4. snapshots —— 快照历史列表（按时间排序，可回滚）
5. properties —— 表属性（format-version、文件格式等）
```

```json
{
  "format-version": 2,
  "table-uuid": "d1e2f3a4-...",
  "location": "s3://bucket/warehouse/db/orders",
  "last-sequence-number": 5,
  "schema": { "type": "struct", "schema-id": 0,
    "fields": [
      {"id": 1, "name": "order_id", "required": true, "type": "long"},
      {"id": 2, "name": "amount", "required": false, "type": "decimal(10,2)"}
    ]
  },
  "partition-spec": [
    {"name": "dt", "transform": "day", "source-id": 3, "field-id": 1000}
  ],
  "current-snapshot-id": 1234567890123456789,
  "snapshots": [ { "snapshot-id": 1234567890123456789, "timestamp-ms": 1723600000000 } ]
}
```

## Snapshot 快照

快照（Snapshot）是 Iceberg 表在某一时刻的不可变视图，由一组 manifest list 指向当时的数据文件。每次写操作（INSERT/UPDATE/MERGE/COMPACTION）都会提交一个新快照，新快照只记录「变化」的 manifest 和文件，未变的文件复用——因此快照创建是 O(变化量) 而非 O(全表)。快照历史可配置保留数量（过期清理），过期前的快照可任意回滚。

```text
快照要点：
1. 不可变 —— 快照提交后不可改，只能新建快照
2. 增量 —— 新快照只引用新增/变更的 manifest 与文件，节省存储
3. 回滚 —— rollback 把 current-snapshot 指回历史快照，秒级完成
4. 过期 —— expire_snapshots 清理旧快照，释放被删除文件占用的空间
```

```sql
-- 查看快照历史
SELECT * FROM db.orders.snapshots;

-- 回滚到某个快照
CALL db.system.rollback_to_snapshot('db.orders', 1234567890123456789);

-- 按时间回滚
CALL db.system.rollback_to_timestamp('db.orders', TIMESTAMP '2024-08-14 00:00:00');

-- 清理 3 天前的旧快照
CALL db.system.expire_snapshots('db.orders', TIMESTAMP '2024-08-11 00:00:00');
```

## Manifest 与数据文件

Manifest 是介于快照和数据文件之间的清单文件，记录一批数据文件的位置及其统计信息（每列 min/max/value_counts/null_counts、记录数、文件大小）。查询时 Iceberg 先读 manifest 的列统计，跳过不满足谓词的文件（文件级裁剪），再只读命中的 data files。Manifest list 则记录快照里包含哪些 manifest 文件及其分区的统计，实现更快的一级裁剪。

```text
Manifest 与裁剪机制：
1. manifest —— 记录数据文件路径 + 列级 min/max/null 统计
2. manifest list —— 记录 manifest 的分区范围统计，用于一级裁剪
3. 文件级裁剪 —— 谓词下推对比 manifest 里的 min/max，跳过不命中的文件
4. 数据文件 —— 底层 Parquet/ORC/Avro，格式可配置（write.format.default）
```

```text
查询裁剪流程：
SQL 谓词 (dt = '2024-08-14')
  → 读 metadata.json 找到当前 snapshot
  → 读 manifest list，按分区统计跳过不相关 manifest
  → 读相关 manifest，按列 min/max 跳过不相关 data files
  → 只读命中的 data files（Parquet 内部再做 row group 裁剪）
```

## Catalog 目录

Catalog 是 Iceberg 表元数据的「登记处」，负责把「表名」映射到「当前 metadata.json 的位置」，并在提交时做并发控制（乐观锁 CAS 更新 current-snapshot）。支持的 Catalog 实现有 Hive Metastore、AWS Glue、REST Catalog、JDBC Catalog、Nessie 等。多引擎（Spark/Flink/Trino）通过同一个 Catalog 读写同一张表，是 Iceberg 多引擎互操作的基础。

```text
Catalog 要点：
1. 作用 —— 表名 → 当前 metadata.json 位置的映射 + 提交 CAS 锁
2. 实现 —— Hive Metastore / Glue / REST / JDBC / Nessie（git 式版本）
3. 多引擎 —— Spark/Flink/Trino 都配同一个 Catalog，读写同一张表
4. 提交并发 —— 乐观并发，提交时对比 current-snapshot-id，冲突则重试
```

```sql
-- Spark SQL 配置 REST Catalog
CREATE CATALOG iceberg_catalog USING org.apache.iceberg.spark.SparkCatalog
LOCATION 'http://catalog-service:8181/';

USE iceberg_catalog.db;

-- 建表（指定分区与格式）
CREATE TABLE orders (
    order_id BIGINT, user_id BIGINT, amount DECIMAL(10,2),
    status STRING, dt DATE
) USING iceberg
PARTITIONED BY (dt)
TBLPROPERTIES ('format-version'='2');
```

## Schema 与分区演进

Iceberg 的 Schema 演进指表结构（增删列、改列类型、重命名）可以在线进行，不需要重写整表数据——新数据按新 Schema 写，旧数据按旧 Schema 读，读取时按 schema-id 对齐。分区演进（Partition Evolution）更进一步：可以改变分区字段（如从按天分区改成按月分区），旧数据保持旧分区、新数据用新分区，查询时 Iceberg 自动识别两套分区规格。

```text
Schema 演进支持的操作：
1. 加列 —— ADD COLUMN，默认值/null，O(1) 元数据操作
2. 删列 —— DROP COLUMN，逻辑删除，读取时屏蔽
3. 改类型 —— 支持安全提升（int → long），不支持不安全转换
4. 重命名 —— RENAME COLUMN，记录映射
```

```sql
-- Schema 演进
ALTER TABLE orders ADD COLUMN discount DECIMAL(10,2) COMMENT '折扣';
ALTER TABLE orders DROP COLUMN old_col;
ALTER TABLE orders ALTER COLUMN amount TYPE BIGINT;

-- 分区演进：从按天改成按月
ALTER TABLE orders REPLACE PARTITION FIELD dt WITH month(dt);
```

## Hidden Partition 隐藏分区

隐藏分区是 Iceberg 区别于 Hive 的关键设计：分区由「分区变换函数」定义（如 day(ts)、bucket(16, user_id)、truncate(10, name)），物理目录名由变换结果决定，用户写查询时只需写原始字段的谓词（WHERE ts = '...'），Iceberg 自动把它转成对分区目录的裁剪——用户无需知道分区字段的物理路径。这解决了 Hive 的「分区是目录路径」导致的需手动指定分区、改分区要重写数据两大痛点。

```text
隐藏分区要点：
1. 分区变换 —— identity（原值）、day/month/year（时间截断）、bucket（哈希分桶）、truncate（截断）
2. 自动裁剪 —— 查询写原始列谓词，Iceberg 自动映射到分区
3. 分区不落盘语义 —— 目录名是变换结果，与业务字段解耦
4. 演进无损 —— 改分区变换不重写数据，旧分区继续有效
```

```sql
-- 用 bucket 分区避免热点（按 user_id 分 16 桶）
CREATE TABLE orders (
    order_id BIGINT, user_id BIGINT, amount DECIMAL(10,2), ts TIMESTAMP
) USING iceberg
PARTITIONED BY (bucket(16, user_id), month(ts));

-- 查询无需知道分区，直接写原始谓词
SELECT * FROM orders WHERE user_id = 12345 AND ts >= '2024-08-01';
```

## Time Travel 时间旅行

时间旅行指查询表在历史某个时刻（或某个快照）的状态，是 Iceberg 快照机制的直接应用。它用于数据审计（对比改动前后）、误操作恢复（读删除前的数据）、可复现分析（用固定历史版本出数）。实现上是把 current-snapshot-id 临时指向历史快照，读取那套 manifest/data files。

```text
时间旅行用法：
1. 按快照 ID —— SELECT ... VERSION AS OF <snapshot-id>
2. 按时间戳 —— SELECT ... TIMESTAMP AS OF '2024-08-14 00:00:00'
3. 用途 —— 审计、误删恢复、可复现
```

```sql
-- 查询历史时间点的数据
SELECT * FROM orders VERSION AS OF 1234567890123456789;

SELECT * FROM orders TIMESTAMP AS OF '2024-08-14 00:00:00';

-- 误删恢复：把误删的数据读出来重新插入
CREATE TABLE orders_recovered AS
SELECT * FROM orders TIMESTAMP AS OF '2024-08-14 00:00:00';
```

## Branch 与 Tag

Branch（分支）和 Tag（标签）是 Iceberg 表级别的引用管理（类似 git）：Branch 是可读写的独立数据谱系，用于隔离实验写入（如 ETL 先写分支、验证后再合并回主分支）；Tag 是不可变的快照别名，用于标记里程碑版本（如「2024 Q3 财报用数据」）。两者都通过 metadata.json 的 refs 字段管理。

```text
Branch 与 Tag 要点：
1. Branch —— 可写，用于实验/隔离写入，用 fast_forward 合并回 main
2. Tag —— 只读，标记里程碑版本，不可变
3. 语法 —— 表名后加 .branch_<名> 或 .tag_<名>（各引擎略有差异）
4. 场景 —— 数据回填验证、合规留档、多人协作隔离
```

```sql
-- 建分支、写分支、合并回主分支
ALTER TABLE orders CREATE BRANCH etl_test;
INSERT INTO orders.branch_etl_test SELECT ... ;
CALL db.system.fast_forward('db.orders', 'main', 'etl_test');

-- 打 tag 留档
ALTER TABLE orders CREATE TAG q3_final RETAIN 365 DAYS;
```

## Compaction 与维护

流式写入会产生大量小文件，Iceberg 提供一批维护操作保证表健康：Compaction（合并小文件为大文件，减少 manifest 元数据开销）、Expire Snapshots（清理过期快照）、Remove Orphan Files（删除无引用的孤儿文件）、Rewrite Manifests（合并 manifest 文件）。这些是数据湖运维的日常动作，通常由调度任务定期执行。

```text
维护操作清单：
1. rewrite_data_files —— 合并小文件（按 target-file-size-bytes 合并）
2. rewrite_manifests —— 合并 manifest 文件
3. expire_snapshots —— 清理过期快照与可回收文件
4. remove_orphan_files —— 删除未被任何快照引用的文件
5. 触发 —— 用调度器（Airflow/DolphinScheduler）定时跑这些 CALL 语句
```

```sql
-- 合并小文件
CALL db.system.rewrite_data_files(
    table => 'db.orders',
    strategy => 'sort', sort_order => 'order_id ASC'
);

-- 合并 manifest
CALL db.system.rewrite_manifests('db.orders');

-- 清理孤儿文件（快照过期之后）
CALL db.system.remove_orphan_files(table => 'db.orders');
```

## 应用场景实战

### 场景一：用 Spark 建表、写数据、时间旅行

```python
# PySpark 读写入 Iceberg 表
from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .config("spark.sql.catalog.iceberg", "org.apache.iceberg.spark.SparkCatalog") \
    .config("spark.sql.catalog.iceberg.type", "hadoop") \
    .config("spark.sql.catalog.iceberg.warehouse", "hdfs:///warehouse") \
    .getOrCreate()

# 建表
spark.sql("""
    CREATE TABLE iceberg.db.orders (
        order_id BIGINT, user_id BIGINT, amount DECIMAL(10,2), ts TIMESTAMP
    ) USING iceberg PARTITIONED BY (month(ts))
""")

# 写入
spark.sql("""
    INSERT INTO iceberg.db.orders VALUES
    (1, 100, 99.90, TIMESTAMP '2024-08-14 10:00:00'),
    (2, 101, 199.00, TIMESTAMP '2024-08-14 11:00:00')
""")

# 时间旅行：读 1 分钟前的版本
spark.sql("SELECT * FROM iceberg.db.orders TIMESTAMP AS OF (current_timestamp() - interval 1 minute)").show()
```

### 场景二：CDC 到 Iceberg 的 MERGE 幂等写入

```sql
-- Flink/Spark 流式写入时，按主键 UPSERT（v2 格式支持）
MERGE INTO iceberg.db.orders t
USING (SELECT 1 AS order_id, 100 AS user_id, 120.00 AS amount) s
ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET t.amount = s.amount
WHEN NOT MATCHED THEN INSERT (order_id, user_id, amount) VALUES (s.order_id, s.user_id, s.amount);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产用 format-version=2（支持行级更新/删除，v1 只支持追加）
2. 时间戳字段分区用 month/day 变换，避免用裸 timestamp 当分区字段
3. 高基数字段（user_id）分区用 bucket 变换，避免分区热点和分区爆炸
4. 流式写入后定期跑 rewrite_data_files 合并小文件
5. 快照保留策略要配（如保留 7 天），否则 metadata 无限膨胀
6. 多引擎共享同一个 Catalog，保证元数据一致
7. 写文件格式默认 Parquet，列裁剪和压缩都优秀

### 踩坑记录

```text
坑 1：用 Hive 的目录式思维去理解分区
结论：以为改了分区字段就要迁移目录，或者查询漏写分区条件导致全表扫。
原因：Iceberg 是隐藏分区，分区与目录解耦，思维还停在 Hive。
解法：查询直接写原始字段谓词，改分区用 REPLACE PARTITION FIELD，无需重写数据。

坑 2：format-version=1 的表执行 DELETE 报错
结论：报 Row-level operations not supported。
原因：v1 是纯追加格式，不支持行级删除。
解法：建表时指定 format-version=2，或升级已有表。

坑 3：快照不清理导致 metadata 目录膨胀
结论：metadata 文件越来越多，Catalog 读当前版本变慢。
原因：每次提交都生成新 metadata.json，快照历史无限保留。
解法：定期 expire_snapshots + remove_orphan_files，保留期按业务定（如 7 天）。

坑 4：流式写入产生海量小文件
结论：查询变慢，manifest 元数据爆炸。
原因：Flink/Spark 微批每次写一批小文件，长期累积。
解法：定期 rewrite_data_files 合并，target-file-size 设 512MB~1GB。

坑 5：多引擎同时写同一张表冲突
结论：提交失败或数据不一致。
原因：不同引擎的 Catalog 提交并发控制不一致，或用了不同的 Catalog 实例。
解法：所有引擎配同一个 Catalog 服务（如 REST Catalog），依赖它的 CAS 乐观锁。
```
