## 概述

数据测试与工程规范解决「如何保证数据管线的正确性、可维护性与可复现性」的问题。它分两大块：测试（单元/集成/数据/回归/Schema 测试，用 Great Expectations、dbt test 等把数据质量断言自动化）和工程规范（Git/DVC/LakeFS 版本管理、命名/SQL/分区规范、生命周期管理、小文件与倾斜治理、数据契约）。数据工程正从「写脚本」走向「软件工程化」。

```text
数据测试与工程规范两大支柱：
1. 测试 —— 用自动化断言守住数据正确性
2. 工程规范 —— 版本化、契约化、规范化，让管线可维护可复现
```

```text
数据工程成熟度阶梯：
写脚本（无测试）-> 加数据测试 -> 版本化（Git/DVC）
-> 数据契约 -> 工程规范 -> CI/CD 自动化
```

## Unit Test

Unit Test（单元测试）对最小可测单元（一个函数、一个转换逻辑）做隔离测试，验证输入输出正确性，不依赖外部数据库或集群。数据工程中的单元测试针对清洗函数、指标计算、特征变换函数，跑得快、定位准，是数据逻辑正确性的第一道防线，常用 pytest 编写。

```text
Unit Test 要点：
1. 对象 —— 单个函数 / 转换逻辑，隔离测试
2. 隔离 —— 不依赖外部 DB/集群，用 mock 或内存数据
3. 快速 —— 秒级完成，适合进 CI 每次提交都跑
```

```python
def clean_status(raw: str) -> str:
    m = {'paid': 'paid', 'shipped': 'paid',
         'refunded': 'refunded', 'cancelled': 'cancelled'}
    return m.get(raw, 'unknown')

def test_clean_status():
    assert clean_status('paid') == 'paid'
    assert clean_status('shipped') == 'paid'   # 归一化
    assert clean_status('xxx') == 'unknown'    # 兜底
    print("单元测试通过")

test_clean_status()
```

## Integration Test

Integration Test（集成测试）验证多个模块协同工作是否正确，如「清洗 + 写入 + 下游读取」整条链路。它比单元测试范围更大，可能需要测试库/测试集群，重点抓「联调才暴露的问题」——类型不匹配、接口约定不一致、环境配置差异。

```text
Integration Test 要点：
1. 对象 —— 多个模块协同的链路片段
2. 环境 —— 需要测试库 / 集群（隔离于生产）
3. 重点 —— 接口匹配、数据流转、环境一致性
```

```python
class FakeTable:
    def __init__(self):
        self.data = []
    def write(self, rows):
        self.data.extend(rows)

def clean(rows):
    return [{'id': r['id'], 'amount': float(r['amount'])} for r in rows]

def pipeline(raw, table):        # 清洗 -> 写入 -> 读取
    table.write(clean(raw))
    return table.data

t = FakeTable()
result = pipeline([{'id': 1, 'amount': '10.5'}], t)
assert result[0]['amount'] == 10.5
print("集成测试通过：", result)
```

## Data Test

Data Test（数据测试）对数据本身的正确性做断言，而非对代码：非空、唯一、取值范围、引用完整性、统计特征。它回答「产出的数据对不对」，是数据工程特有的测试类型，通常用 SQL 断言或 Great Expectations、dbt test 实现，在数据产出后运行，是数据质量的直接守门人。

```text
Data Test 要点：
1. 对象 —— 数据本身，而非代码逻辑
2. 断言 —— 非空、唯一、范围、引用完整、行数
3. 时机 —— 数据产出后立即运行，拦截坏数据
```

```sql
-- 用 SQL 做数据测试（返回非空即失败）
-- 主键唯一性
SELECT order_id, COUNT(*) FROM dwd_order_detail
WHERE dt = '2026-08-14' GROUP BY order_id HAVING COUNT(*) > 1;

-- 非空校验
SELECT COUNT(*) FROM dwd_order_detail
WHERE dt = '2026-08-14' AND amount IS NULL;

-- 取值范围校验
SELECT COUNT(*) FROM dwd_order_detail
WHERE dt = '2026-08-14' AND (amount < 0 OR amount > 1000000);
```

## Regression Test

Regression Test（回归测试）在代码或逻辑变更后重新运行既有测试，确保新改动没有破坏原有功能。数据工程中常用于 SQL 改写后对比新旧结果、指标口径调整后核对历史值。核心手段是「快照对比」——把已知正确结果存为基准（baseline），变更后与基准比对。

```text
Regression Test 要点：
1. 目的 —— 变更后确认旧功能没被破坏
2. 手段 —— 基准快照对比、重跑历史用例
3. 时机 —— SQL 改写、口径调整、依赖升级后
```

```python
def old_metric(orders):
    return sum(o['amount'] for o in orders)

def new_metric(orders):
    return sum(o['amount'] for o in orders if o['status'] == 'paid')

orders = [{'amount': 10, 'status': 'paid'},
          {'amount': 5, 'status': 'refunded'}]
print("旧口径：", old_metric(orders))
print("新口径：", new_metric(orders))   # 只算已支付
assert new_metric(orders) == 10
```

## Schema Test

Schema Test（模式测试）校验数据结构是否符合预期——列名、类型、是否为空、分区字段是否齐全，防止上游 schema 变更（加列、改类型、删列）静默破坏下游。通常在数据落地时做结构快照对比，或通过数据契约声明期望 schema 后自动校验。

```text
Schema Test 要点：
1. 对象 —— 表结构：列名、类型、空值约束、分区字段
2. 风险 —— 上游加列 / 改类型 / 删列导致下游异常
3. 手段 —— schema 快照对比、契约声明校验
```

```yaml
# Schema 契约声明（期望结构）
table: dwd_order_detail
columns:
  - {name: order_id, type: bigint, nullable: false}
  - {name: amount, type: decimal(10,2), nullable: true}
  - {name: status, type: string, nullable: false}
partitions: [{name: dt, type: string}]
```

```python
def validate_schema(actual, expected_cols):
    errors = []
    exp = {c['name']: c for c in expected_cols}
    for name, col in actual.items():
        if name not in exp:
            errors.append(f"多余列：{name}")
        elif exp[name]['type'] != col['type']:
            errors.append(f"类型不符：{name}")
    for name in exp:
        if name not in actual:
            errors.append(f"缺失列：{name}")
    return errors

actual = {'order_id': {'type': 'bigint'}, 'amount': {'type': 'string'}}
expected = [{'name': 'order_id', 'type': 'bigint'},
            {'name': 'amount', 'type': 'decimal(10,2)'}]
print("Schema 校验：", validate_schema(actual, expected))
```

## Data Contract

Data Contract（数据契约）是数据生产者与消费者之间关于数据结构与语义的正式约定——声明表有哪些字段、什么类型、什么语义、什么约束、由谁负责。它把「隐式约定」变成「显式可校验的契约」，生产方改动必须遵守契约，消费方按契约消费，违约自动告警，是数据网格与数据工程化的核心实践。

```text
数据契约（Data Contract）要点：
1. 定义 —— 生产与消费双方对数据结构的显式约定
2. 内容 —— 字段、类型、语义、约束、负责人、SLA
3. 校验 —— 契约声明可被工具自动校验，违约即告警
4. 治理 —— 变更需评审，向后兼容，版本化演进
```

```yaml
# 数据契约声明（示意）
contract:
  name: dwd_order_detail
  version: "1.0.0"
  owner: data-team
  schema:
    - {name: order_id, type: bigint, description: 订单ID, nullable: false}
    - {name: status, type: string, enum: [paid, refunded, cancelled]}
  constraints:
    - {field: order_id, rule: unique}
    - {field: amount, rule: "range: [0, 1000000]"}
  sla:
    freshness: "T+1 08:00"
```

## Great Expectations

Great Expectations（GE）是 Python 数据质量测试框架，用「期望（Expectation）」声明数据应满足的条件（如非空、唯一、范围），自动生成数据文档与校验报告。它把数据测试从手写 SQL 升级为声明式、可复用、可观测的资产，支持 Pandas、Spark、SQL 多种后端。

```text
Great Expectations 要点：
1. 期望 —— 声明式断言（非空、唯一、范围、集合成员）
2. 文档 —— 自动生成 Data Docs 展示校验结果
3. 数据源 —— Pandas / Spark / SQL 多后端
```

```python
import pandas as pd
import great_expectations as gx

df = pd.DataFrame({
    'order_id': [1, 2, 3, 4],
    'amount': [10.5, 20.0, -5.0, 100.0],
    'status': ['paid', 'paid', 'refunded', 'paid'],
})

context = gx.get_context()
validator = context.sources.pandas_default.read_dataframe(df)
validator.expect_column_values_to_not_be_null('order_id')
validator.expect_column_values_to_be_unique('order_id')
validator.expect_column_values_to_be_between('amount', 0, 1000000)
result = validator.validate()
print("校验通过：", result.success)
```

## dbt Test

dbt Test 是 dbt 内置的数据测试能力，在模型目录的 schema.yml 中为列声明测试（unique、not_null、accepted_values、relationships），dbt test 命令统一运行并报告失败。它把测试与建模融为一体——模型定义在哪测试就写在哪，随模型版本化、进 CI，是现代数据栈（ELT）质量保障的标准做法。

```text
dbt Test 要点：
1. 内置 —— unique、not_null、accepted_values、relationships
2. 位置 —— 在模型 schema.yml 声明，随模型版本化
3. 运行 —— dbt test 统一执行，失败即报错
```

```yaml
# dbt models/schema.yml
version: 2
models:
  - name: dwd_order_detail
    columns:
      - name: order_id
        tests: [unique, not_null]
      - name: amount
        tests:
          - not_null
          - dbt_utils.accepted_range: {min_value: 0, max_value: 1000000}
      - name: status
        tests:
          - accepted_values:
              values: ['paid', 'refunded', 'cancelled']
      - name: user_id
        tests:
          - relationships: {to: ref('dim_user'), field: user_id}
```

```bash
dbt test                    # 运行所有测试
dbt test --select dwd_order_detail   # 只测指定模型
```

## Git

Git 是分布式版本控制系统，用于管理代码（SQL、脚本、配置、DAG 定义）的版本历史，支持分支开发、合并、回溯、代码评审。数据工程中，SQL 脚本、dbt 模型、Airflow DAG、配置都应纳入 Git，配合分支策略与 CI/CD 实现「代码即配置、变更可追溯、可回滚」，是数据工程化的地基。

```text
Git 要点：
1. 对象 —— SQL、脚本、配置、DAG、模型代码
2. 流程 —— feature branch + PR review + CI
3. 价值 —— 变更可追溯、可回滚、多人协作
```

```bash
git init
git add dags/ models/ sql/
git commit -m "feat: 新增订单日汇总模型"

git checkout -b feature/order-dws     # 分支开发
git commit -am "add dws_order_1d"
git push origin feature/order-dws
# PR 评审通过后合并
git checkout main && git merge feature/order-dws

git log --oneline     # 查看历史
git revert HEAD       # 回滚
```

## DVC

DVC（Data Version Control）是面向数据和机器学习管线的版本控制工具，用 Git 管理数据文件的元数据指针（轻量），把数据本体存对象存储（S3/GCS/HDFS），实现数据版本化与可复现管线。它解决 Git 不适合存大文件的问题——Git 存 .dvc 指针，DVC 负责数据的拉取、推送与版本切换。

```text
DVC 要点：
1. 问题 —— Git 存不了大文件，数据版本化缺失
2. 方案 —— Git 存 .dvc 指针，数据存对象存储
3. 能力 —— 数据版本切换、管线可复现（dvc repro）
```

```bash
dvc init
dvc remote add -d myremote s3://my-bucket/dvc-store

dvc add data/raw_orders.parquet      # 生成 .dvc 指针文件
git add data/raw_orders.parquet.dvc .dvc/config
git commit -m "add raw orders v1"

dvc push                 # 推送数据到远端
dvc checkout             # 切换版本
dvc repro                # 按依赖重跑管线，可复现
```

## LakeFS 与版本快照

LakeFS 把数据湖（S3 等对象存储）变成 Git 一样的版本化系统：对数据做分支、提交、合并、回滚，每个操作都是元数据层的指针切换，不复制数据本体，成本极低。它提供「版本与快照」能力——任意时点数据湖状态可快照、回溯、隔离实验，是数据湖工程化的关键基础设施。

```text
LakeFS 与版本快照要点：
1. 原理 —— 元数据层指针实现分支/提交/合并，不复制数据
2. 分支 —— 隔离环境（dev/staging/prod），实验不污染生产
3. 快照 —— 任意 commit 即数据湖某时点完整快照
4. 回滚 —— 出错一键回滚到历史 commit
```

```bash
lakectl branch create lakefs://repo/dev-branch -s main

lakectl fs upload lakefs://repo/dev-branch/data/orders.parquet \
    -s ./orders.parquet
lakectl commit lakefs://repo/dev-branch -m "experiment"

lakectl diff lakefs://repo/main lakefs://repo/dev-branch
lakectl merge lakefs://repo/dev-branch lakefs://repo/main
lakectl revert lakefs://repo/main --commit <previous_commit>
```

## 可复现

可复现（Reproducibility）指同样的代码 + 同样的数据 + 同样的环境能产出同样的结果。管线不可复现是排查问题、回溯历史、协作开发的噩梦。实现可复现需要：代码版本化（Git）、数据版本化（DVC/LakeFS）、环境固定（依赖锁定、容器镜像）、参数显式化（不用隐式随机/当前时间）。

```text
可复现要点：
1. 定义 —— 同代码 + 同数据 + 同环境 => 同结果
2. 代码 —— Git 版本化，可回溯任意版本
3. 数据 —— DVC/LakeFS 版本化，数据随代码对齐
4. 参数 —— 显式传参，避免隐式随机种子 / 系统时间
```

```python
import random

def reproducible(seed=42):
    rng = random.Random(seed)      # 显式种子
    data = [1, 2, 3, 4, 5]
    rng.shuffle(data)
    return data

print("第一次：", reproducible(42))
print("第二次：", reproducible(42))
print("结果一致：", reproducible(42) == reproducible(42))
```

## 命名规范

命名规范约定表、字段、任务、模型的命名规则，让数据资产可读、可检索、口径一致。常见约定：分层前缀（ods_/dwd_/dws_/ads_/dim_）、小写下划线、字段名语义化（gmv、order_cnt 而非 a、b）、日期分区统一（dt）。命名规范是数据资产治理与协作的基础，需工具强制检查落地。

```text
命名规范要点：
1. 分层前缀 —— ods_/dwd_/dws_/ads_/dim_/tmp_
2. 大小写 —— 全小写 + 下划线分隔
3. 语义化 —— 字段名表达含义，杜绝 a/b/temp
4. 统一 —— 指标缩写全仓一致（gmv、uv、pv、dau）
```

```sql
-- 坏：无分层、字段无意义、大小写混乱
CREATE TABLE OrderData (a BIGINT, b STRING, c DECIMAL);

-- 好：分层前缀 + 语义化 + 小写下划线
CREATE TABLE dwd_order_detail (
    order_id  BIGINT        COMMENT '订单ID',
    order_cnt INT           COMMENT '下单数量',
    gmv       DECIMAL(10,2) COMMENT '成交金额',
    dt        STRING        COMMENT '日期分区'
);
```

## SQL 规范

SQL 规范约定 SQL 写法标准，提升可读性、可维护性、可复用性，降低 review 成本与出错率。常见约定：关键字大写、缩进对齐、每列一行、显式写字段名（禁 SELECT *）、显式 JOIN 条件、复杂逻辑拆 CTE。通常用 SQLFluff 等工具自动检查，纳入 CI 强制执行。

```text
SQL 规范要点：
1. 关键字大写、缩进对齐、每列一行
2. 禁 SELECT *，显式列出字段
3. JOIN 显式 ON 条件，避免隐式笛卡尔积
4. 复杂逻辑拆 CTE（WITH）
```

```sql
-- 坏：SELECT *、无缩进、隐式逻辑
select * from a,b where a.id=b.id and b.amount>100;

-- 好：显式字段、缩进、CTE、注释
WITH paid_orders AS (
    SELECT o.order_id, o.user_id, o.amount, o.dt
    FROM dwd_order_detail AS o
    WHERE o.dt = '2026-08-14' AND o.status = 'paid'
)
SELECT user_id, COUNT(*) AS order_cnt, SUM(amount) AS gmv
FROM paid_orders
GROUP BY user_id;
```

## 分区规范

分区规范约定分区字段、粒度、格式与管理方式，是数仓表设计的核心规范。通常按日期分区（dt），格式统一为 yyyy-MM-dd，分区字段放末尾，写入必须显式指定分区（静态分区）或规范动态分区，避免全表扫描和脏数据落错分区。分区规范直接决定查询性能与生命周期管理的可行性。

```text
分区规范要点：
1. 分区字段 —— 统一用 dt，格式 yyyy-MM-dd
2. 位置 —— 分区字段放表末尾，查询优先带分区
3. 写入 —— 显式静态分区，或规范动态分区
4. 粒度 —— 按天为主，超大表可按小时（dh）
```

```sql
-- 分区表：分区字段放末尾
CREATE TABLE dws_user_order_1d (
    user_id BIGINT, order_cnt INT, gmv DECIMAL(10,2)
) PARTITIONED BY (dt STRING);

-- 静态分区写入（显式指定分区，避免落错）
INSERT OVERWRITE TABLE dws_user_order_1d PARTITION (dt = '2026-08-14')
SELECT user_id, COUNT(*), SUM(amount)
FROM dwd_order_detail WHERE dt = '2026-08-14'
GROUP BY user_id;

-- 查询必须带分区条件，避免全表扫描
SELECT * FROM dws_user_order_1d WHERE dt = '2026-08-14';
```

## 生命周期

生命周期（Data Lifecycle）管理数据从产生到销毁的全过程——定义每张表/每个分区保留多久、何时降冷、何时归档、何时删除。合理设置生命周期能控制存储成本、满足合规删除要求（如 PII 到期删除）、避免无限膨胀。落地手段：分区过期清理、冷热分层、TTL 策略。

```text
生命周期要点：
1. 定义 —— 产生 -> 保留 -> 降冷 -> 归档 -> 删除
2. 分级 —— 热数据（频繁访问）、温数据、冷数据（归档）
3. 手段 —— 分区过期清理、冷热分层、TTL 策略
```

## 小文件与倾斜

小文件与数据倾斜是分布式数据处理的两大性能杀手。小文件（大量几 KB 碎文件）导致元数据压力大、调度开销大、读取效率低；数据倾斜（部分 key 数据量远超其他）导致少数 task 拖慢整个作业。治理手段：小文件用合并/重分区收敛，倾斜用加盐/两阶段聚合/广播解决。

```text
小文件与倾斜要点：
1. 小文件 —— 大量碎文件拖慢 HDFS/对象存储与调度
2. 成因 —— 频繁小批量写入、过度分区、reduce 数过多
3. 倾斜 —— 少数 key 数据量过大，长尾 task 拖慢作业
4. 治理 —— 加盐打散、两阶段聚合、map join 广播
```

```sql
-- 小文件治理：写入时控制输出文件数
INSERT OVERWRITE TABLE dwd_order_detail PARTITION (dt = '2026-08-14')
SELECT /*+ COALESCE(32) */ order_id, user_id, amount, status
FROM ods_order WHERE dt = '2026-08-14';

-- 倾斜治理：加盐两阶段聚合
-- 阶段 1：加随机盐聚合，打散热点 key
SELECT CONCAT(user_id, '_', FLOOR(RAND() * 10)) AS sk, COUNT(*) AS c
FROM dwd_order_detail WHERE dt = '2026-08-14'
GROUP BY CONCAT(user_id, '_', FLOOR(RAND() * 10));
-- 阶段 2：去盐再次聚合
SELECT SUBSTRING_INDEX(sk, '_', 1) AS user_id, SUM(c) AS order_cnt
FROM (阶段1结果) tmp GROUP BY SUBSTRING_INDEX(sk, '_', 1);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 数据逻辑先写单元测试再进管线，测试与代码同仓库同版本
2. 数据测试接入 CI，每次变更自动跑 dbt test / GE 断言
3. 用数据契约显式声明 schema 与约束，违约自动告警
4. 代码进 Git、数据进 DVC/LakeFS，实现整体可复现
5. 统一命名/SQL/分区规范，用 SQLFluff 等工具强制检查
6. 表统一按 dt 分区并配置生命周期，控制存储与合规

### 踩坑记录

```text
坑 1：SELECT * 导致上游加列后下游列错位
结论：上游加一列，下游按位置取值，结果全错。
原因：用 SELECT * 和位置索引，schema 漂移无感知。
解法：显式列名 + schema 契约校验，加列走兼容评审。

坑 2：测试只在本地跑不进 CI
结论：本地通过但生产挂了，测试形同虚设。
原因：未纳入 CI/CD，靠人肉执行，久了被跳过。
解法：数据测试接入 CI，失败阻断合并。

坑 3：数据未版本化，出错无法回溯
结论：跑出坏数据后无法回到正确版本，只能全量重算。
原因：数据本体无版本，只靠代码版本无法还原数据状态。
解法：用 DVC/LakeFS 版本化数据，快照可回溯可回滚。

坑 4：不设生命周期导致存储无限膨胀
结论：历史分区堆积，存储成本失控，查询变慢。
原因：无保留策略，数据只进不出。
解法：按表配置 retention，调度定期 drop 过期分区。

坑 5：忽略数据倾斜直接上线大作业
结论：个别 task 跑数小时，整作业被长尾拖垮。
原因：热点 key 未识别未治理，reduce 负载不均。
解法：上线前分析 key 分布，加盐/两阶段聚合治理。
```
