## 概述

数据调度与工作流解决「何时、按什么顺序、以何种可靠性运行数据任务」的问题。它把分散的 ETL、计算、同步任务组织成有依赖关系的流水线（Pipeline），用 DAG 表达任务先后顺序，由调度器按计划触发、管理重试、支持回填，并用 SLA/SLO 保障时效。Airflow、DolphinScheduler、Dagster、Prefect、Argo Workflows 是主流调度/编排引擎。

```text
数据调度解决的核心问题：
1. 何时跑 —— 定时调度（cron）、事件触发、依赖触发
2. 顺序 —— 用 DAG 表达任务依赖，先父后子
3. 容错 —— 自动重试、告警、人工干预
4. 补数 —— 回填（backfill）批量重跑历史周期
5. 时效 —— SLA/SLO 定义并监控任务时效
```

```text
主流调度 / 编排引擎对比：
Airflow         —— Python 定义 DAG，生态最广，重量级成熟
DolphinScheduler —— 可视化拖拽，分布式去中心化，适合中文团队
Dagster         —— 面向数据资产，强调可测试与类型安全
Prefect         —— 轻量、动态工作流、云原生、易上手
Argo Workflows  —— Kubernetes 原生，容器编排
```

## Pipeline

Pipeline（流水线）是一系列按顺序或并行组织的数据处理任务的集合，从采集、清洗、加工到产出报表形成端到端链路。它强调「数据从源头到终点」的完整视角，每个任务输出作为下游输入。好的流水线应可观测、可重跑、幂等，任意节点失败都能从失败点恢复而非从头再来。

```text
Pipeline 要点：
1. 定义 —— 一组有序 / 并行的任务，端到端产出数据
2. 形态 —— 线性（A→B→C）、分支、汇聚（A/B→C）
3. 特性 —— 幂等、可重跑、可观测、可回填
4. 粒度 —— 大流水线可拆子流水线（sub-pipeline）复用
```

```text
典型离线数仓 Pipeline：
采集 -> ODS 贴源 -> DWD 清洗 -> DWS 汇总 -> ADS 报表
```

```python
# 最简流水线：上游 -> 中游 -> 下游（示意）
def extract():
    return "raw_orders"          # 采集

def clean(raw):
    return "clean_" + raw        # 清洗

def aggregate(clean_data):
    return "report_" + clean_data  # 汇总

def pipeline():
    result = aggregate(clean(extract()))
    print("流水线产出：", result)

pipeline()
```

## DAG

DAG（Directed Acyclic Graph，有向无环图）是工作流编排的核心抽象：节点代表任务，有向边代表依赖方向（上游 → 下游），不允许成环。DAG 保证任务能按拓扑顺序执行、无依赖的任务可并行调度，失败时只重跑受影响的下游分支。环会导致死循环依赖，因此被禁止。

```text
DAG 要点：
1. 节点 —— 任务，有向边 —— 依赖关系
2. 无环 —— 禁止循环依赖，保证拓扑排序可行
3. 并行 —— 无依赖关系的任务可并行执行
4. 调度 —— 按拓扑顺序，父任务成功才触发子任务
```

```text
DAG 拓扑示意（数仓分层）：
ods_order  ods_user
     \       /
      dwd_order
     /        \
dws_user_1d  dws_product_1d
     \        /
     ads_report
```

```python
import networkx as nx

G = nx.DiGraph()
G.add_edges_from([
    ('ods_order', 'dwd_order'), ('ods_user', 'dwd_order'),
    ('dwd_order', 'dws_user_1d'), ('dwd_order', 'dws_product_1d'),
    ('dws_user_1d', 'ads_report'), ('dws_product_1d', 'ads_report'),
])
print("无环：", nx.is_directed_acyclic_graph(G))
print("拓扑顺序：", list(nx.topological_sort(G)))
```

## Task

Task（任务）是流水线中最小的执行单元，代表一个不可再分的操作（一条 SQL、一个 Spark 作业、一个脚本）。每个任务有明确的输入输出、执行命令、资源需求和运行配置，是重试、监控、SLA 管理的基本单位。任务粒度应适中——太细调度开销大，太粗失败影响面大。

```text
Task 要点：
1. 定义 —— 最小执行单元：一条 SQL / 一个脚本 / 一个作业
2. 属性 —— 输入输出、执行命令、资源、超时、重试策略
3. 幂等 —— 同参数多次运行结果一致，支持安全重跑
4. 可观测 —— 有日志、状态、耗时，便于定位问题
```

```text
Task 关键属性：
task_id  —— 任务唯一标识
command  —— 执行命令（SQL / bash / python）
upstream —— 上游任务列表
retries  —— 失败重试次数
sla      —— 时效目标（须在何时前完成）
```

## Dependency

Dependency（依赖）定义任务间的先后关系：下游必须等上游成功后才能执行。依赖分任务级（A 完成后 B 才跑）、时间级（等某时间点/分区就绪）和数据级（等某张表出现数据）。调度器根据依赖构建 DAG 决定触发时机，依赖设计是工作流正确性的关键。

```text
依赖要点：
1. 任务级 —— 上游成功才触发下游
2. 时间级 —— 等某个时间窗 / 分区数据就绪
3. 数据级 —— 等某表 / 某分区数据落地（就绪检查）
4. 触发规则 —— all_success / one_success / all_done
```

```python
# 依赖调度（示意）：反复寻找依赖已满足的任务
tasks = {
    "A": [], "B": ["A"], "C": ["A"], "D": ["B", "C"],
}
done = []
while len(done) < len(tasks):
    for name, ups in tasks.items():
        if name not in done and all(u in done for u in ups):
            print("执行", name)
            done.append(name)
print("完成顺序：", done)
```

## Retry

Retry（重试）在任务失败后自动重新执行，应对临时性故障（网络抖动、资源竞争、外部服务短暂不可用）。重试策略包括最大次数和间隔（固定或指数退避）。重试必须配合任务幂等性——任务可重复执行而不产生副作用，否则重试会导致数据重复污染。

```text
Retry 要点：
1. 触发 —— 任务失败自动重试
2. 次数 —— 最大重试次数，超过则失败告警
3. 间隔 —— 固定间隔或指数退避（1s、2s、4s...）
4. 前提 —— 任务必须幂等，否则重试产生脏数据
```

```python
import time

def retry(max_retries=3, base_delay=1):
    def decorator(fn):
        def wrapper(*a, **kw):
            for attempt in range(max_retries + 1):
                try:
                    return fn(*a, **kw)
                except Exception as e:
                    if attempt == max_retries:
                        raise
                    time.sleep(base_delay * (2 ** attempt))
                    print(f"第 {attempt+1} 次失败：{e}，重试")
        return wrapper
    return decorator

@retry(max_retries=2, base_delay=0)
def flaky():
    raise ConnectionError("网络抖动")

try:
    flaky()
except ConnectionError:
    print("重试耗尽，转人工处理")
```

## Backfill

Backfill（回填）对历史周期批量补跑任务，用于修复历史数据、上线新指标回溯、补全缺失分区。回填时调度器为指定时间范围内每个时间点生成一次运行。回填要谨慎：可能覆盖已有数据、触发下游级联重算，需明确范围、是否覆盖、是否连带下游，并控制并发避免冲击生产。

```text
Backfill 要点：
1. 定义 —— 对历史时间段批量补跑任务
2. 用途 —— 修复历史数据、新指标回溯、补缺失分区
3. 范围 —— 明确起止时间与是否覆盖已有结果
4. 风险 —— 大量补跑冲击生产，需限流并发
```

```bash
# Airflow 回填（示意）：回填指定日期区间
airflow dags backfill -s 2026-08-01 -e 2026-08-14 daily_etl_dag

# DolphinScheduler 补数（示意）
dolphinscheduler backfill --process daily_etl \
    --start 2026-08-01 --end 2026-08-14
```

## SLA/SLO

SLA（服务等级协议）与 SLO（服务等级目标）定义并监控数据任务的时效与质量承诺。SLO 是内部目标（如「日报 8 点前产出」），SLA 是面向业务方的正式承诺（违约有代价）。在调度中，SLA 常指「任务须在某时间点前完成，否则告警」，是数据时效治理的核心手段。

```text
SLA/SLO 要点：
1. SLO —— 内部目标：报表 8 点前产出、延迟 < 5 分钟
2. SLA —— 对外承诺，违约有惩罚，通常更严格
3. 指标 —— 及时率、准确率、可用率、延迟
4. 治理 —— 用 SLA 倒推链路优化，定位瓶颈任务
```

```text
数仓 SLA 分层（典型）：
T+0 实时 —— 秒级 / 分钟级，实时数仓指标
T+1 离线 —— 次日 8 点前，核心日报指标
T+1 非核心 —— 次日 10 点前，辅助分析
```

```yaml
# 任务 SLA 配置（示意）
tasks:
  - name: dws_user_order_1d
    sla:
      deadline: "08:00"        # 次日 8 点前必须完成
      alert_after: "07:30"     # 7:30 未完成预警
    owners: [data-team]
```

## Airflow

Airflow 是 Apache 基金会最流行的开源工作流编排平台，用 Python 代码定义 DAG。核心组件有 Scheduler（调度）、Executor（执行）、WebServer（UI）、Metastore（元数据）。它把 DAG 作为代码管理（可版本化、可测试），支持丰富的 Operator（Bash/Python/SQL/Sensor）和多种 Executor（Local/Celery/K8s），适合复杂大规模工作流。

```text
Airflow 要点：
1. 定义 —— 用 Python 写 DAG，代码即配置（as code）
2. 组件 —— Scheduler、Executor、WebServer、Metastore
3. Operator —— Bash / Python / SQL / Sensor
4. Executor —— Local / Celery / Kubernetes
```

```python
from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

default_args = {'owner': 'data-team', 'retries': 2,
                'retry_delay': timedelta(minutes=5)}

with DAG(dag_id='daily_etl', default_args=default_args,
         schedule_interval='0 2 * * *',
         start_date=datetime(2026, 8, 1), catchup=True) as dag:

    extract = BashOperator(
        task_id='extract_orders',
        bash_command='python extract.py --date {{ ds }}')

    def clean(**context):
        print(f"清洗 {context['ds']} 的数据")

    clean_task = PythonOperator(task_id='clean', python_callable=clean)

    load = BashOperator(task_id='load_dwd',
                        bash_command='hive -f load_dwd.sql')

    extract >> clean_task >> load      # 定义依赖
```

## DolphinScheduler

Apache DolphinScheduler 是分布式、去中心化的可视化工作流调度平台，通过 Web 界面拖拽式编排 DAG，无需写代码即可创建任务。它支持多租户、任务优先级、失败告警、补数，采用 Master/Worker 去中心化架构避免单点瓶颈，适合低代码、可视化运维的中文团队。

```text
DolphinScheduler 要点：
1. 编排 —— Web 拖拽式可视化 DAG，低代码
2. 架构 —— Master/Worker 去中心化，无单点
3. 任务类型 —— Shell、SQL、Spark、Flink、DataX、子流程
4. 能力 —— 多租户、优先级、告警、补数
```

```yaml
# DolphinScheduler 流程定义（示意）
process:
  name: daily_etl
  schedule: "0 0 2 * * ?"
  tasks:
    - name: extract_orders
      type: SHELL
      command: "python extract.py"
    - name: clean_orders
      type: SQL
      datasource: hive_warehouse
      sql: "insert overwrite table dwd_order select * from ods_order"
      pre_tasks: [extract_orders]
    - name: load_report
      type: SPARK
      main_class: com.example.ReportJob
      pre_tasks: [clean_orders]
```

## Dagster

Dagster 是面向数据资产的开源编排框架，把「软件定义资产（Software-Defined Assets）」作为一等公民——每个任务明确声明它产出哪些数据资产（表、文件），框架自动推断资产间依赖并构建 DAG。它强调可测试性、类型检查、资产级血缘，适合重视工程质量与数据契约的团队。

```text
Dagster 要点：
1. 资产 —— 软件定义资产，任务声明产出，依赖自动推断
2. 测试 —— 任务可独立单元测试，类型可校验
3. 观测 —— 资产级血缘、分区、回溯
4. 触发 —— 定时调度、传感器（Sensor）触发
```

```python
from dagster import asset, AssetSelection, Definitions, define_asset_job

@asset
def ods_order():
    return ["order1", "order2"]

@asset
def dwd_order(ods_order):          # 依赖 ods_order，自动推断
    return [o.upper() for o in ods_order]

@asset
def dws_user_1d(dwd_order):        # 依赖 dwd_order
    return {"order_cnt": len(dwd_order)}

daily_job = define_asset_job(
    name="daily_etl",
    selection=AssetSelection.assets(dws_user_1d))

defs = Definitions(
    assets=[ods_order, dwd_order, dws_user_1d],
    jobs=[daily_job])
print("Dagster 作业：", daily_job.name)
```

## Prefect

Prefect 是轻量、云原生的现代工作流编排引擎，用 Python 装饰器定义任务与流水线，强调动态工作流（运行时动态生成任务）、本地优先开发体验、弹性基础设施。它把编排层与执行层分离，任务可在本地、Docker、K8s 上运行，比 Airflow 更轻量、上手快。

```text
Prefect 要点：
1. 定义 —— Python 装饰器 @task / @flow，简洁
2. 动态 —— 支持运行时动态构建工作流
3. 分离 —— 编排层与执行层解耦
4. 运行 —— 本地 / Docker / Kubernetes
```

```python
from prefect import task, flow

@task(retries=2, retry_delay_seconds=30)
def extract():
    return 100

@task
def clean(raw):
    return raw

@task
def load(clean_cnt):
    return "done"

@flow(name="daily_etl")
def daily_etl_flow():
    load(clean(extract()))
    return "flow complete"

if __name__ == "__main__":
    daily_etl_flow()
```

## Argo Workflows

Argo Workflows 是 Kubernetes 原生的工作流引擎，用 YAML 定义工作流，每个任务是一个容器（Pod），由 K8s 负责调度和资源管理。它天然契合云原生生态，适合计算密集型、需容器隔离和弹性伸缩的场景，配合 CronWorkflow、Argo Events 实现定时与事件触发。

```text
Argo Workflows 要点：
1. 定义 —— YAML 声明式，任务是容器（Pod）
2. 原生 —— 运行在 Kubernetes，复用 K8s 调度
3. 模板 —— steps / DAG 模板表达依赖与并行
4. 触发 —— CronWorkflow 定时、Argo Events 事件
```

```yaml
# Argo Workflows 定义（示意）
apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata:
  generateName: daily-etl-
spec:
  entrypoint: etl-dag
  templates:
    - name: etl-dag
      dag:
        tasks:
          - name: extract
            template: run
            arguments: {parameters: [{name: cmd, value: "python extract.py"}]}
          - name: clean
            template: run
            dependencies: [extract]
            arguments: {parameters: [{name: cmd, value: "python clean.py"}]}
          - name: load
            template: run
            dependencies: [clean]
            arguments: {parameters: [{name: cmd, value: "hive -f load.sql"}]}
    - name: run
      inputs:
        parameters: [{name: cmd}]
      container:
        image: my-etl-image:latest
        command: [sh, -c]
        args: ["{{inputs.parameters.cmd}}"]
```

## 应用场景实战

### 场景一：用 Airflow 编排电商离线数仓每日 ETL

```python
from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.dummy import DummyOperator
from datetime import datetime, timedelta

default_args = {'owner': 'data-team', 'retries': 2,
                'retry_delay': timedelta(minutes=5),
                'email_on_failure': True}

with DAG(dag_id='ecommerce_daily_etl', default_args=default_args,
         schedule_interval='0 2 * * *', start_date=datetime(2026, 8, 1),
         catchup=False, max_active_runs=1) as dag:

    start = DummyOperator(task_id='start')

    sync_order = BashOperator(
        task_id='sync_ods_order',
        bash_command='sqoop import ... --target-dir /ods/order/dt={{ ds }}')
    sync_user = BashOperator(
        task_id='sync_ods_user',
        bash_command='sqoop import ... --target-dir /ods/user/dt={{ ds }}')

    clean_dwd = BashOperator(
        task_id='clean_dwd_order',
        bash_command='hive -f dwd_order.sql --hivevar ds={{ ds }}')
    agg_dws = BashOperator(
        task_id='agg_dws_user_1d',
        bash_command='hive -f dws_user_1d.sql --hivevar ds={{ ds }}')
    report_ads = BashOperator(
        task_id='report_ads',
        bash_command='hive -f ads_report.sql --hivevar ds={{ ds }}')

    start >> [sync_order, sync_user] >> clean_dwd >> agg_dws >> report_ads
```

```text
调度链路说明：
1. 每天凌晨 2 点触发，ODS 订单与用户同步并行执行
2. 两者都成功后才执行 DWD 清洗（汇聚依赖）
3. 逐层向下：DWS 汇总 -> ADS 报表
4. 失败自动重试 2 次，仍失败发邮件告警
```

### 场景二：跨 DAG 依赖与 SLA 告警

```python
from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.sensors.external_task import ExternalTaskSensor
from datetime import datetime, timedelta

with DAG(dag_id='report_dag', schedule_interval='0 4 * * *',
         start_date=datetime(2026, 8, 1), catchup=False) as dag:

    wait_upstream = ExternalTaskSensor(
        task_id='wait_agg_dws',
        external_dag_id='ecommerce_daily_etl',
        external_task_id='agg_dws_user_1d',
        timeout=3 * 3600, poke_interval=300, mode='reschedule')

    report = BashOperator(
        task_id='generate_report',
        bash_command='python generate_report.py --date={{ ds }}',
        sla=timedelta(hours=8))      # SLA：8 点前完成

    wait_upstream >> report
```

```text
跨 DAG 与 SLA 要点：
1. ExternalTaskSensor 实现跨 DAG 依赖，需对齐执行日期
2. SLA 超时触发 sla_miss 回调，接告警 / 升级
3. 依赖等待设超时，避免上游失败导致无限等待
4. mode=reschedule 释放 worker 槽位，适合长等待
```

## 最佳实践与踩坑记录

### 最佳实践

1. 任务保持幂等，重试与回填才能安全执行
2. 用 DAG 显式声明依赖，不依赖任务名排序或隐式顺序
3. 关键任务设重试与 SLA，失败及时告警而非静默堆积
4. 回填前明确范围与是否覆盖，控制并发避免冲击生产
5. 时间用逻辑日期（ds）而非系统当前时间，保证回填正确
6. 一条 DAG 只做一件事，复杂链路拆子 DAG 复用

### 踩坑记录

```text
坑 1：任务不幂等导致重试/回填脏数据
结论：重试后同一数据被重复插入，指标翻倍。
原因：用 INSERT 而非幂等的 INSERT OVERWRITE/去重。
解法：任务写成幂等（按分区覆盖写），重试无副作用。

坑 2：回填未控制并发冲击生产
结论：回填 90 天任务同时起 90 个实例，把集群打挂。
原因：未限流，回填与生产任务争抢资源。
解法：限制回填并发，错峰执行。

坑 3：用系统当前时间而非逻辑日期
结论：回填历史数据时读到「今天」而非目标日期。
原因：代码用 now() 取日期，未用调度传入的 ds。
解法：统一用调度器传入的 ds 作为数据日期。

坑 4：Sensor 不设超时无限等待
结论：上游数据未就绪，Sensor 一直占用资源空等。
原因：未设 timeout，长等待还占用 worker 槽位。
解法：Sensor 设 timeout 并用 reschedule 模式释放槽位。
```
