## 概述

企业级数据平台是一套覆盖「采集、接入、存储、计算、查询、治理」全链路的数据基础设施，目标是把企业内分散的异构数据统一汇聚成可信、可管、可用的数据资产。平台以 CDC + Kafka 接入实时增量，Flink 做实时计算、Spark 做离线批处理，数据统一落地 Iceberg Lakehouse，Trino + OLAP 提供查询服务，并在其上建设数据目录、数据质量、血缘、权限、安全与成本治理六大治理能力。相比单点工具，企业级平台的核心是「治理 + 开放 + 规模化」。

```text
项目目标与业务价值：
1. 统一接入 —— 采集 + CDC 覆盖异构数据源，增量实时入湖
2. 批流一体 —— Flink 实时 + Spark 离线共享同一份数据
3. 开放查询 —— Trino 联邦查询 + OLAP 多维分析统一出口
4. 全链路治理 —— 目录/质量/血缘/权限/安全/成本六位一体
5. 资产化 —— 数据从「成本」变为「可信可复用的资产」
```

## 技术选型

企业级平台选型遵循「开源 + 成熟 + 分层解耦」：采集层用 CDC（Debezium/Flink CDC）捕获数据库增量，Kafka 做统一消息总线；计算层 Flink 负责实时、Spark 负责离线批处理；存储层用 Iceberg 做 Lakehouse 统一表格式；查询层 Trino 做联邦查询、OLAP（ClickHouse/Doris）做多维分析；治理层用数据目录（DataHub/Atlas）管元数据，Ranger 管权限。这套组合覆盖全链路，且各组件可独立替换、水平扩展。

```text
技术选型与理由：
1. 采集 —— CDC（Debezium/Flink CDC）：数据库增量实时捕获
2. 总线 —— Kafka：统一消息通道，解耦采集与计算
3. 实时 —— Flink：流式计算 + 实时入湖
4. 离线 —— Spark：批处理 ETL、Compaction、重算
5. 存储 —— Iceberg：Lakehouse 统一表格式，批流共享
6. 查询 —— Trino（联邦）+ OLAP（多维分析）
7. 治理 —— 数据目录 + Ranger（权限）+ 血缘 + 质量
```

## 架构设计

架构分五层：数据源层（业务库、日志、埋点、文件）→ 接入层（CDC + Kafka 采集与缓冲）→ 存储计算层（Iceberg Lakehouse + Flink/Spark）→ 查询服务层（Trino + OLAP）→ 治理层（目录/质量/血缘/权限/安全/成本横切所有层）。数据流：业务库 binlog 经 CDC 进 Kafka，Flink 实时写 Iceberg、Spark 离线批处理，Trino/OLAP 对外提供查询，治理组件全程记录元数据、校验质量、管控权限。

```text
架构分层（数据流）：
业务库/日志/埋点/文件
  ↓ CDC + 采集
Kafka 消息总线
  ↓ Flink（实时）/ Spark（离线）
Iceberg Lakehouse（对象存储）
  ↓ Trino / OLAP
查询服务 → BI / 数据应用 / 数据科学
  ↓ 横切
治理层：目录 + 质量 + 血缘 + 权限 + 安全 + 成本
```

```text
技术架构：
┌────────────┬────────────┬───────────────┬────────────┬──────────┐
│  数据源层   │   接入层    │   存储计算层    │  查询服务层  │  治理层   │
│  业务库     │  CDC       │  Iceberg      │  Trino     │  数据目录  │
│  日志/埋点  │  Kafka     │  Flink/Spark  │  OLAP      │  质量/血缘 │
│  文件       │  采集器     │  对象存储      │  联邦查询   │  权限/安全 │
└────────────┴────────────┴───────────────┴────────────┴──────────┘
```

## 采集与 CDC 接入

采集覆盖三类数据源：数据库（用 CDC 捕获 binlog 增量，保证实时、低侵入）、日志与埋点（Filebeat/Agent 采集）、文件（批量导入）。CDC 是核心——相比定时全量抽取，它基于 binlog 做到「实时 + 增量 + 可回溯」，不侵入业务系统。项目用 Flink CDC 或 Debezium 将数据库变更实时同步到 Kafka，统一后续计算入口。

```text
采集与 CDC 要点：
1. CDC —— 基于 binlog 实时捕获增量，低侵入、可回溯
2. 全量 + 增量 —— 首次全量快照 + 后续增量变更
3. 统一入口 —— 所有变更进 Kafka，计算层只对接 Kafka
4. 断点续传 —— 记录 binlog offset，故障恢复不丢不重
```

```yaml
# Flink CDC 同步 MySQL 到 Kafka（示例配置）
source:
  connector: mysql-cdc
  hostname: mysql
  port: 3306
  username: user
  password: pwd
  database: shop
  table: orders
  startup-mode: initial
sink:
  connector: kafka
  topic: cdc_shop_orders
  format: json
```

## 消息总线与流批计算

Kafka 是统一消息总线，采集的数据先进 Kafka，Flink 和 Spark 各自订阅消费。Flink 负责实时链路：实时 ETL、实时指标、实时入湖（写 Iceberg）；Spark 负责离线链路：批处理 ETL、数据重算、Compaction、模型训练特征加工。二者共享 Iceberg 表，实现「实时 + 离线」批流一体，避免数据双份与口径分裂。

```text
流批分工：
1. Flink —— 实时 ETL、实时指标、实时入湖（毫秒~秒级）
2. Spark —— 离线批处理、重算、Compaction（分钟~小时级）
3. 共享 —— 统一写 Iceberg，Trino 查询最新结果
```

```java
// Flink 实时消费 Kafka 写 Iceberg
DataStream<String> stream = env
    .fromSource(kafkaSource, WatermarkStrategy.noWatermarks(), "cdc")
    .map(new JsonToRowMap());

FlinkSink.forRowData(stream.map(new RowToRowDataMap()))
    .table(table).append();
```

```scala
// Spark 离线批处理读取 Iceberg 重算汇总
val df = spark.read.format("iceberg").load("lakehouse.db.orders")
val agg = df.groupBy("user_id").agg(sum("amount").as("total"))
agg.writeTo("lakehouse.db.user_total").overwritePartitions()
```

## 存储层与查询层

存储层用 Iceberg 建 Lakehouse，数据统一落对象存储，按主题分库分表，支持模式演进、时间旅行、ACID。查询层双出口：Trino 做联邦查询（跨 Iceberg、Hive、关系库的秒级查询，服务 BI 与自助分析），OLAP 做多维分析（ClickHouse/Doris 存预聚合指标，服务高并发看板与即席下钻）。存储计算分离，查询层按需弹性扩展。

```text
存储与查询分工：
1. Iceberg —— 明细数据统一存储，批流共享
2. Trino —— 联邦查询，跨源秒级分析
3. OLAP —— 预聚合指标，高并发多维下钻
```

```sql
-- Trino 联邦查询：Iceberg 明细 join 关系库维表
SELECT o.user_id, d.region, SUM(o.amount) AS gmv
FROM lakehouse.db.orders o
JOIN mysql.dim.region d ON o.region_id = d.id
WHERE o.dt >= '2026-08-01'
GROUP BY o.user_id, d.region;
```

## 数据目录

数据目录是企业数据的「黄页」，统一管理元数据——表、字段、分区、owner、业务含义、标签、SLA，让数据「可发现、可理解、可信赖」。项目用 DataHub（或 Atlas）采集各引擎的元数据，提供搜索、浏览、血缘、热度排行，并支持业务术语表对齐，解决「数据在哪里、什么意思、能不能用」三大问题。

```text
数据目录核心能力：
1. 元数据采集 —— 自动扫描各引擎的表/字段/分区
2. 搜索发现 —— 按名/标签/业务术语搜索数据资产
3. 业务语义 —— 术语表对齐，技术字段对应业务含义
4. owner 与 SLA —— 每张表有负责人与时效承诺
```

```text
数据目录解决的问题：
1. 数据在哪 —— 全局搜索定位数据资产
2. 数据是什么 —— 字段含义、业务口径、血缘
3. 能不能用 —— owner、质量状态、权限、SLA
```

## 数据质量

数据质量贯穿「采集 → 计算 → 存储 → 查询」全链路，用规则引擎定义校验（非空、唯一、范围、分布、及时性、一致性），在关键节点（入湖后、加工后、出数前）执行校验，不通过则告警并阻断下游。质量度量（完整性、准确性、一致性、及时性、唯一性）量化打分，形成质量报告与看板，推动数据从「能用」到「可信」。

```text
质量六维度：
1. 完整性 —— 非空、记录数完整
2. 准确性 —— 取值合法、范围正确
3. 一致性 —— 跨表口径一致
4. 及时性 —— 数据按时产出（SLA）
5. 唯一性 —— 主键不重复
6. 有效性 —— 格式、枚举合法
```

```text
质量校验落地：
1. 入湖后 —— 校验 schema 与脏数据
2. 加工后 —— 校验结果正确性与完整性
3. 出数前 —— 校验口径与及时性
4. 不通过 → 告警 + 阻断下游
```

## 血缘

血缘记录数据「从哪来、经过什么加工、到哪去」的全链路依赖——表级血缘（源表 → 目标表）、列级血缘（源字段 → 目标字段）、任务级血缘（任务 → 表）。血缘自动采集（解析 SQL + 引擎 hook），用于影响分析（改一张表知道影响哪些下游）、根因定位（数据出错追溯到源头）、合规审计（数据流向透明）。

```text
血缘三级：
1. 表级 —— 源表 → 目标表的依赖
2. 列级 —— 字段粒度的血缘追踪
3. 任务级 —— 加工任务与表的关联
```

```text
血缘的用途：
1. 影响分析 —— 变更上游，评估下游影响范围
2. 根因定位 —— 数据出错，向上追溯到源头
3. 合规审计 —— 数据流向透明可追溯
```

## 权限

权限采用「RBAC + 细粒度鉴权」：基于角色的访问控制（角色 → 权限 → 资源），配合库/表/列级鉴权，实现「最小权限原则」。用 Ranger 做统一权限中心，各引擎（Spark/Flink/Trino/Hive）对接 Ranger 插件统一鉴权，支持行级过滤与列级脱敏。权限申请走审批流，权限定期审计，防止越权访问。

```text
权限体系要点：
1. RBAC —— 角色分配权限，用户挂角色
2. 细粒度 —— 库/表/列级 + 行级过滤 + 列级脱敏
3. 统一鉴权 —— Ranger 中心，各引擎插件对接
4. 审批审计 —— 申请审批流 + 定期权限审计
```

```text
最小权限原则落地：
1. 默认拒绝 —— 未授权默认不可访问
2. 按需申请 —— 申请具体表/字段的权限
3. 定期回收 —— 长期不用的权限自动回收
```

## 安全

安全覆盖数据全生命周期的防护：传输加密（TLS）、存储加密（对象存储服务端加密 + 密钥管理 KMS）、敏感数据识别与脱敏（自动发现手机号/身份证等并脱敏）、访问审计（记录谁在何时访问了什么数据）。对 PII（个人身份信息）执行分级分类管理，高敏感数据严格脱敏 + 最小化授权，满足合规要求。

```text
安全防护维度：
1. 传输加密 —— TLS 加密数据流转
2. 存储加密 —— 服务端加密 + KMS 密钥管理
3. 敏感识别 —— 自动发现 PII 并脱敏
4. 访问审计 —— 记录访问行为，可追溯
```

```text
数据分级分类：
1. 公开 —— 可自由访问
2. 内部 —— 企业内部可见
3. 敏感 —— 需授权，字段脱敏
4. 机密 —— 严格授权 + 全程加密 + 审计
```

## 成本治理

成本治理解决「数据平台越用越贵」的问题：存储成本靠冷热分层（热数据标准存储、冷数据归档）+ 生命周期（快照过期、历史数据归档）+ 小文件治理（Compaction）；计算成本靠弹性伸缩（闲时缩容）+ 资源配额（按团队限额）+ 任务优化（减少重复计算）；并建立成本看板，按团队/项目分摊成本，倒逼优化。

```text
成本治理四板斧：
1. 冷热分层 —— 热数据标准存储、冷数据归档存储
2. 生命周期 —— 快照过期、历史数据归档清理
3. 弹性伸缩 —— 计算资源按需伸缩，闲时缩容
4. 成本看板 —— 按团队/项目分摊，倒逼优化
```

```text
成本优化清单：
1. 小文件合并，降低存储与查询成本
2. 压缩格式（Parquet + 压缩算法）降低存储
3. 分区裁剪 + 索引，减少扫描降低计算成本
4. 重复任务去重，避免重复计算浪费
```

## 应用场景实战

### 场景一：新业务接入数据的全流程

```text
1. 数据源注册 —— 在数据目录登记新业务库
2. 配置 CDC —— Flink CDC 订阅业务库，变更进 Kafka
3. Flink 实时入湖 —— 写 Iceberg 明细表
4. 数据质量 —— 入湖后校验 schema 与脏数据
5. 血缘自动采集 —— 记录源库到 Iceberg 表的血缘
6. 权限申请 —— 下游用户按需申请表权限
7. 查询开放 —— Trino/OLAP 提供查询服务
```

### 场景二：数据事故的根因定位与影响分析

```text
1. 下游报表发现 GMV 异常下跌
2. 查血缘 —— 从报表表向上追溯到上游表与任务
3. 查质量 —— 定位到某 ETL 任务质量校验失败
4. 查审计 —— 确认是上游 schema 变更导致
5. 影响分析 —— 评估受影响的全部下游
6. 修复 + 补数 —— 重跑任务，通知受影响方
```

## 最佳实践与踩坑记录

### 最佳实践

1. 全链路统一走 Kafka，计算层只对接消息总线，避免点对点耦合
2. 治理能力（目录/质量/血缘/权限）从第一天就建设，别等数据乱了补
3. 权限遵循最小权限原则，默认拒绝 + 按需申请
4. 敏感数据分级分类，PII 自动识别脱敏，满足合规
5. 成本看板按团队分摊，让成本透明倒逼优化
6. 血缘和质量联动，数据出错能快速定位根因

### 踩坑记录

```text
坑 1：各团队各建一套平台，数据烟囱林立
结论：同一指标多个口径，数据互不相通，重复建设浪费。
原因：缺乏统一平台规划，各团队自建小工具。
解法：统一平台 + 统一数据目录，口径与元数据集中管理。

坑 2：CDC 只做增量没做全量快照，历史数据缺失
结论：接入前的存量数据没同步，下游口径不全。
原因：只关注增量变更，忽略了首次全量快照。
解法：CDC 用 initial 模式，先全量快照再增量，保证数据完整。

坑 3：权限一把梭，人人都是管理员
结论：越权访问频发，敏感数据泄露风险高。
原因：图省事全员高权限，未做最小权限与审计。
解法：RBAC + 细粒度鉴权 + 审批流 + 定期审计。

坑 4：不建血缘，数据出错只能人肉排查
结论：报表出错，排查半天找不到源头，影响面未知。
原因：血缘缺失，依赖关系不可见。
解法：血缘自动采集，支撑影响分析与根因定位。

坑 5：成本失控，存储和计算费用飞涨
结论：数据无限堆积、资源常开，账单每月飙升。
原因：无生命周期管理、无冷热分层、无资源配额。
解法：冷热分层 + 快照过期 + 弹性伸缩 + 成本看板分摊。
```
