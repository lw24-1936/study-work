## 概述

实时风控数据平台的目标是在毫秒到秒级内识别并拦截欺诈、薅羊毛、盗号、刷单等风险行为。平台以 Kafka 为事件总线接入全链路行为数据，用 Flink CEP 做复杂事件模式匹配，结合黑白名单、设备指纹、实时特征与风险规则进行多维度判定，结果写入 Redis 供业务实时查询拦截，同时落地 OLAP 供离线分析与策略复盘。核心指标是「低延迟 + 高召回 + 低误杀」。

```text
项目目标与业务价值：
1. 实时拦截 —— 毫秒级完成风险判定并回传业务侧拦截
2. 多维判定 —— 名单 + 设备 + 特征 + 规则 + 行为模式组合判定
3. 策略可迭代 —— 规则配置化，策略离线分析后快速上线
4. 可追溯 —— 决策过程留痕，支持复核与审计
```

## 技术选型

选型围绕「低延迟流处理 + 规则判定」：Kafka 做事件总线（高吞吐、可重放、解耦上下游）；Flink CEP 做复杂事件模式匹配（状态化流处理、毫秒级延迟、支持跨事件的时序模式）；Redis 做在线名单与特征存储（内存读写、微秒级查询、支撑实时决策）；OLAP（ClickHouse/Doris）做离线分析与策略效果评估。选择这套组合是因为「Kafka + Flink + Redis」是实时风控的事实标准，成熟且生态完善。

```text
技术选型与理由：
1. 事件总线 —— Kafka：高吞吐、持久化、可重放、解耦
2. 规则引擎 —— Flink CEP：复杂事件模式匹配、低延迟、有状态
3. 在线存储 —— Redis：名单/特征/频控的微秒级读写
4. 离线分析 —— OLAP：策略效果评估、案件复盘、特征挖掘
5. 配置中心 —— 规则配置热更新，不改代码上线策略
```

## 架构设计

架构分四层：接入层（业务埋点、网关日志、交易流水 → Kafka）→ 计算层（Flink CEP 消费事件，加载名单与特征，执行规则判定）→ 存储层（Redis 存名单/特征/频控计数，OLAP 存决策明细）→ 应用层（业务实时查询拦截、风控后台、告警）。数据流：事件进 Kafka → Flink 做预处理、特征计算、CEP 模式匹配、规则判定 → 决策写 Redis + OLAP → 命中风险触发告警与拦截。

```text
架构分层（数据流）：
业务埋点/交易/登录事件
  ↓ 写入
Kafka 事件总线
  ↓ 消费（Flink CEP）
预处理 → 设备指纹 → 实时特征 → CEP 模式匹配 → 规则判定
  ↓ 决策输出
Redis（名单/特征/频控） + OLAP（决策明细）
  ↓ 查询
业务拦截 / 风控后台 / 告警
```

```text
技术架构：
┌──────────────┬───────────────┬────────────────┬──────────────┐
│   接入层      │    计算层       │    存储层        │   应用层      │
│  业务埋点     │  Flink CEP     │  Redis 在线     │  业务拦截    │
│  网关日志     │  特征计算       │  OLAP 离线      │  风控后台    │
│  交易流水     │  规则判定       │  名单/频控      │  告警通知    │
└──────────────┴───────────────┴────────────────┴──────────────┘
```

## 事件接入与 Kafka 缓冲

所有风险事件统一进 Kafka，按事件类型分 topic（登录、下单、支付、领券等），按用户/设备做分区保证同一实体的事件有序。Kafka 承担「削峰填谷 + 解耦 + 可重放」三重作用：流量洪峰时缓冲、下游故障时重放、策略迭代时回溯历史事件重算。事件 schema 用统一的 envelope 结构（事件类型、用户、设备、时间、扩展字段）。

```text
事件接入要点：
1. 分 topic —— 按事件类型隔离，独立消费与扩缩容
2. 分区键 —— 按用户/设备哈希，保证同实体有序
3. 可重放 —— 保留历史事件，支持策略回溯重算
4. 统一 schema —— envelope 结构，字段标准化
```

```json
{
  "event_type": "payment",
  "event_id": "evt_20260814_0001",
  "user_id": "u_10086",
  "device_id": "dev_abc123",
  "ip": "203.0.113.7",
  "amount": 999.0,
  "ts": 1766250000000,
  "ext": {"channel": "app", "merchant": "m_001"}
}
```

## Flink CEP 规则引擎

Flink CEP 是核心规则引擎，用于识别「跨事件的时序模式」——单个事件看不出风险，但连续事件组合起来就是攻击特征。CEP 用 Pattern API 描述模式（如「同一设备 5 分钟内登录失败 5 次后触发成功登录」），Flink 基于 NFA 状态机在事件流上增量匹配，发现命中模式即输出告警事件。相比简单规则，CEP 能表达「先后 + 时间窗口 + 次数」的复杂行为序列。

```text
CEP 适用场景：
1. 暴力破解 —— 短时间内多次登录失败后成功
2. 盗刷 —— 注册后秒级内高频下单
3. 薅羊毛 —— 同一设备批量注册领券
4. 刷单 —— 短时高频交易 + 金额规律
```

```java
// Flink CEP 匹配「5 分钟内登录失败 >= 5 次」模式
Pattern<LoginEvent, LoginEvent> pattern = Pattern.<LoginEvent>begin("fail")
    .where(e -> "FAIL".equals(e.getResult()))
    .timesOrMore(5)
    .within(Time.minutes(5));

PatternStream<LoginEvent> patternStream = CEP.pattern(
    loginStream.keyBy(LoginEvent::getDeviceId), pattern);

patternStream.select(map -> {
    List<LoginEvent> fails = map.get("fail");
    return new Alert("暴力破解", fails.get(0).getDeviceId(), fails.size());
}).addSink(alertSink);
```

## 黑白名单过滤

黑白名单是第一道也是最廉价的防线：命中黑名单直接拒绝，命中白名单直接放行，跳过后续重计算。黑名单存风险实体（设备、IP、账号、卡号），来源包括历史欺诈案件、外部情报、规则命中自动加黑；白名单存可信实体（VIP、内部测试账号、合作方）。名单存 Redis，Flink 用 broadcast state 或定时刷新到内存，保证判定在微秒级完成，名单变更秒级生效。

```text
名单管理要点：
1. 黑名单 —— 命中即拒，来源：案件、情报、规则自动加黑
2. 白名单 —— 命中即放，避免误杀 VIP/测试账号
3. 自动加黑 —— 规则命中达阈值自动进黑名单
4. 过期机制 —— 名单带 TTL，防止永久误杀
```

```text
名单判定流程：
事件进入 → 查黑名单（命中→拒绝并告警）
        → 查白名单（命中→放行，跳过后续）
        → 均未命中 → 进入特征计算与规则判定
```

## 设备指纹识别

设备指纹用于识别「同一台设备背后的多个账号」，是反薅羊毛和反批量注册的核心。通过采集设备的硬件参数（型号、屏幕、系统版本）、浏览器指纹（UA、字体、Canvas 指纹）与行为特征，生成稳定且唯一的 device_id。即使攻击者更换账号、IP、手机号，只要设备指纹一致，就能关联起同一实体的风险行为。

```text
设备指纹要点：
1. 采集维度 —— 硬件参数 + 浏览器指纹 + 行为特征
2. 稳定性 —— 同一设备生成一致指纹，抗清缓存/换 IP
3. 关联 —— 多账号共用指纹 = 团伙/批量风险信号
4. 对抗 —— 指纹伪造/篡改的检测与降权
```

```text
设备指纹在风控中的用法：
1. 一台设备绑定账号数过多 → 批量注册风险
2. 新设备 + 新账号 + 大额交易 → 盗刷风险
3. 设备指纹突变 → 模拟器/改机风险
```

## 实时特征计算

实时特征是把原始事件加工成「可判定风险的数值化信号」，如近 1 小时登录失败次数、近 24 小时交易金额、近 5 分钟下单频次等。Flink 用滑动/滚动窗口或增量状态计算特征，结果写入 Redis 供规则引擎查询。特征要「可解释、可复用、可回溯」——同一个特征既服务在线判定，也落 OLAP 供离线分析与建模。

```text
实时特征示例：
1. 频次类 —— 近 5 分钟下单数、近 1 小时登录失败数
2. 金额类 —— 近 24 小时交易总额、单笔金额偏差
3. 关联类 —— 同设备账号数、同 IP 设备数
4. 时长类 —— 注册到首笔交易的间隔
```

```sql
-- Flink SQL 实时计算「近 5 分钟下单频次」特征
SELECT user_id, COUNT(*) AS order_cnt_5m, SUM(amount) AS amount_5m
FROM payment_stream
GROUP BY user_id, TUMBLE(ts, INTERVAL '5' MINUTE);
```

## 风险规则与决策

风险规则把「特征 + 名单 + 设备」组合成可配置的判定逻辑，采用「条件 + 阈值 + 动作 + 分值」的规则模型。规则配置化存储在配置中心（或 DB），Flink 通过 broadcast 流热更新规则，不改代码即可上线/下线策略。决策引擎对每条事件执行规则集，输出「通过/拒绝/挑战（二次验证）」，并附风险分与命中规则，支持策略评估与调优。

```text
规则模型四要素：
1. 条件 —— 特征/名单/设备的组合判定
2. 阈值 —— 触发风险的临界值
3. 动作 —— 通过 / 拒绝 / 挑战（短信/人脸二次验证）
4. 分值 —— 风险分加权，支持多规则叠加评分
```

```text
规则示例：
1. 黑名单命中 → 直接拒绝
2. 近 5 分钟下单 > 20 次 → 拒绝（刷单）
3. 同设备账号数 > 10 → 挑战（批量注册）
4. 风险分 > 80 → 拒绝，60~80 → 挑战
```

## Redis 缓存与 OLAP 分析

Redis 是风控的在线存储：名单、实时特征、频控计数都在 Redis，读写微秒级，支撑高 QPS 实时判定。OLAP（ClickHouse/Doris）是离线存储：决策明细、特征快照、告警记录全部落地，用于策略效果评估、案件复盘、特征挖掘与模型训练。二者分工明确——Redis 要快，OLAP 要全，实时决策与离线分析分离。

```text
Redis 与 OLAP 分工：
1. Redis —— 名单/特征/频控，微秒级读写，高 QPS
2. OLAP —— 决策明细/特征快照/告警，海量存储，多维分析
3. 写放大 —— 决策结果同时写 Redis（在线）+ OLAP（离线）
```

```text
频控计数（Redis 原子操作）：
1. INCR user:u_10086:order_cnt_5m  → 自增计数
2. EXPIRE 键 → 设置 5 分钟过期，窗口滑动
3. GET 计数 → 规则判定是否超阈值
```

## 告警与处置

命中高风险规则时触发告警与处置：告警分实时通知（短信/电话/IM 通知风控值班）与系统处置（写黑名单、拦截交易、冻结账号、二次验证）。告警要分级（高危立即电话、中危短信、低危汇总报表），带上下文（事件详情、命中规则、特征快照、设备指纹），并记录处置动作，形成「判定 → 告警 → 处置 → 复核」闭环。

```text
告警与处置闭环：
1. 判定 —— 风险规则命中，输出告警事件
2. 告警 —— 分级通知（高危电话/中危短信/低危汇总）
3. 处置 —— 加黑名单 / 拦截 / 冻结 / 二次验证
4. 复核 —— 案件复盘，评估误杀，优化规则
```

```text
告警分级：
1. P0 高危 —— 盗刷/大额欺诈，电话 + 短信立即通知
2. P1 中危 —— 批量注册/薅羊毛，短信通知
3. P2 低危 —— 疑似异常，汇总报表，定期复盘
```

## 应用场景实战

### 场景一：登录暴力破解实时拦截

```text
1. 登录事件进 Kafka login topic
2. Flink CEP 按 device_id 匹配「5 分钟失败 >= 5 次」
3. 命中模式 → 查询黑名单/白名单
4. 非白名单 → 输出拒绝决策 + 触发 P1 告警
5. 决策写 Redis（频控锁定）+ 自动加黑设备
6. 业务侧拦截该设备的后续登录
```

### 场景二：营销活动薅羊毛识别

```text
1. 领券/注册事件进 Kafka
2. 设备指纹识别出同设备多账号
3. 实时特征计算「同设备注册账号数、领券频次」
4. 规则判定：同设备账号 > 10 或领券频次超阈值 → 挑战/拒绝
5. 命中后写黑名单，阻断后续领券
6. 决策明细落 OLAP，活动结束后复盘效果
```

## 最佳实践与踩坑记录

### 最佳实践

1. 黑白名单放最前面，命中直接短路，省掉后续重计算
2. 规则配置化，broadcast 热更新，策略上线不重启作业
3. 设备指纹与名单、特征结合，单维度判定易被绕过
4. 决策结果双写 Redis（在线）+ OLAP（离线），支持复盘
5. 告警分级，避免高危告警淹没在低危噪声里
6. 名单带 TTL，防止误加黑导致永久误杀

### 踩坑记录

```text
坑 1：CEP 没按 keyBy 分组，模式跨实体串扰
结论：A 用户的失败登录和 B 用户的成功登录被误拼成同一模式。
原因：CEP 前没按 device_id/user_id keyBy，事件全局无序混流。
解法：CEP 前必须 keyBy 到同一实体维度，保证模式在同一分区内匹配。

坑 2：名单没做 TTL，误加黑永久误杀
结论：被自动加黑的正常用户永久无法登录，客诉激增。
原因：自动加黑无过期机制，名单只进不出。
解法：名单带 TTL 自动过期，配合白名单兜底与人工复核。

坑 3：规则硬编码在 Flink 作业里，改策略要发版
结论：风控策略迭代慢，应对新攻击手段滞后数天。
原因：规则写死在代码中，改一条阈值要改代码 + 重启作业。
解法：规则配置化 + broadcast 流热更新，秒级上线新策略。

坑 4：Redis 频控计数用错了原子操作
结论：并发下计数不准，频控阈值形同虚设。
原因：用 GET 后 SET 的非原子操作，存在竞态。
解法：用 INCR + EXPIRE 原子操作，或 Lua 脚本保证原子性。

坑 5：决策明细只写 Redis 没落 OLAP
结论：事后无法复盘策略效果，误杀和漏杀无从分析。
原因：只关注在线拦截，忽略了离线分析的数据沉淀。
解法：决策结果双写 OLAP，保留完整上下文供复盘与建模。
```
