## 概述

CDC（Change Data Capture，变更数据捕获）数据同步平台，把 MySQL 等业务库的增量变更实时同步到数据湖（Iceberg），实现「业务库 → 数据湖」的低延迟、可追溯数据同步。链路是「MySQL → Debezium → Kafka → Flink → Iceberg」，Debezium 解析 binlog 捕获变更，Kafka 缓冲解耦，Flink 做清洗、幂等去重、schema 对齐，Iceberg 落地支持 ACID 和 upsert。平台解决「实时同步、断点续传、schema 变更」三大难题。

```text
项目目标与业务价值：
1. 实时同步 —— binlog 变更秒级同步到数据湖，替代 T+1 批量
2. 断点续传 —— 故障恢复从断点继续，不丢不重
3. Schema Evolution —— 表结构变更自动同步，不阻塞写入
4. 幂等去重 —— 重放、重复消费不产生重复数据
5. 多下游复用 —— Kafka 缓冲，一份变更多下游消费
```

## 技术选型

选型围绕「binlog 捕获 + 消息缓冲 + 流处理 + 湖落地」：Debezium 是 MySQL binlog 捕获的事实标准（无需业务侵入、格式统一），Kafka 做高吞吐缓冲和多下游分发，Flink 做流处理（清洗、幂等去重、schema 对齐、写 Iceberg），Iceberg 做数据湖存储（ACID、upsert、schema evolution、时间旅行）。选择理由：这套组合开源成熟、格式统一（Debezium 统一变更格式）、端到端可精确一次。

```text
技术选型与理由：
1. 采集 —— Debezium（解析 binlog，统一变更格式，无业务侵入）
2. 消息 —— Kafka（高吞吐缓冲、多下游分发、可重放）
3. 计算 —— Flink（流处理、幂等去重、写 Iceberg）
4. 湖 —— Iceberg（ACID、upsert、schema evolution、时间旅行）
5. 替代 —— 也可用 Flink CDC 直接读 binlog，省去 Kafka 中转
```

## 架构设计

架构分四层：数据源（MySQL，开启 binlog）→ 采集层（Debezium 订阅 binlog，变更写 Kafka）→ 计算层（Flink 消费 Kafka，清洗、幂等去重、写 Iceberg）→ 存储层（Iceberg 数据湖）。数据流：MySQL 变更经 binlog 被 Debezium 捕获，转成统一变更事件（before/after/op）写 Kafka，Flink 消费后按主键 upsert 写 Iceberg，保证数据湖与业务库最终一致。

```text
数据流（同步链路）：
MySQL 业务库（binlog）
  ↓ Debezium 订阅 binlog
Kafka（变更事件 topic：before/after/op）
  ↓ Flink 消费、清洗、幂等去重
Flink（按主键 upsert）
  ↓ 写 Iceberg
Iceberg 数据湖（ACID + 时间旅行）
```

```text
技术架构：
┌────────────┬────────────┬──────────────┬────────────┐
│  数据源     │  采集层     │  计算层       │  存储层     │
│  MySQL     │  Debezium  │  Flink       │  Iceberg   │
│  binlog    │  订阅解析   │  清洗去重     │  ACID      │
│  业务表     │  → Kafka   │  upsert 写入 │  时间旅行   │
└────────────┴────────────┴──────────────┴────────────┘
```

## Binlog 原理与解析

Binlog（Binary Log）是 MySQL 的二进制日志，记录所有对数据的变更操作（增删改），是主从复制和 CDC 的基础。三种格式：Statement（记录 SQL 语句，非确定性函数不准）、Row（记录每行变更前后值，精确但体积大）、Mixed（混合，默认）。CDC 场景必须用 Row 格式，因为需要精确的行级 before/after 值。Debezium 通过伪装成 MySQL 从库订阅 binlog，实时解析变更事件。

```text
Binlog 要点：
1. 作用 —— 记录数据变更，主从复制 + 数据恢复 + CDC 的基础
2. Statement 格式 —— 记录 SQL 语句，非确定性函数不准，体积小
3. Row 格式 —— 记录每行变更前后值，精确，体积大，CDC 首选
4. Mixed 格式 —— 混合，默认格式
5. 配置 —— CDC 需开启 binlog_format=ROW、binlog_row_image=FULL
```

```sql
-- 开启 binlog（my.cnf 配置）
-- [mysqld]
-- server-id = 1
-- log-bin = mysql-bin
-- binlog_format = ROW
-- binlog_row_image = FULL

-- 查看 binlog 状态
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'binlog_format';

-- 变更示例：更新订单状态，Row 格式记录 before/after 完整行
UPDATE orders SET status = 'paid' WHERE order_id = 1001;
-- binlog 记录：before = (1001, 'unpaid'), after = (1001, 'paid')
```

## Debezium 数据采集

Debezium 伪装成 MySQL 从库订阅 binlog，把每行变更转成统一的事件结构（op 操作类型 + before 变更前 + after 变更后），写 Kafka。事件结构统一，下游无需关心源库差异。关键配置：连接器（MySQL connector）、binlog 位置（首次全量快照 + 后续增量）、事件 topic 命名（按库.表）。Debezium 支持全量快照 + 增量续传，保证不丢数据。

```text
Debezium 事件结构要点：
1. op —— 操作类型 c（insert）/ u（update）/ d（delete）/ r（read 快照）
2. before —— 变更前值（insert 为 null，delete 有值）
3. after —— 变更后值（delete 为 null，insert 有值）
4. 全量快照 —— 首次启动全量读取，标 op=r
5. 增量 —— 快照完成后订阅 binlog，从快照位置续传
```

```json
{
  "before": {"order_id": 1001, "status": "unpaid"},
  "after": {"order_id": 1001, "status": "paid"},
  "source": {"table": "orders", "db": "shop", "ts_ms": 1723600000000},
  "op": "u",
  "ts_ms": 1723600000000
}
```

```text
Debezium 连接器配置要点：
1. database.hostname/port/user/password —— 源库连接
2. database.server.id —— 伪装从库的 server id，唯一
3. table.include.list —— 需要同步的表白名单
4. snapshot.mode —— 全量快照模式（initial）
5. 事件 topic —— 每表一个 topic，命名 {server}.{db}.{table}
```

## Schema Evolution

Schema Evolution 解决「业务表结构变更」问题：上游加列、删列、改类型时，数据湖 schema 要同步演进，否则写入失败。Iceberg 原生支持 schema evolution（加列、删列、重命名、改类型都支持），Flink 写 Iceberg 时按事件 schema 自动对齐。Debezium 会把源表 schema 变化也发到 Kafka（schema change 事件），Flink 消费后可据此更新 Iceberg 表结构。

```text
Schema Evolution 要点：
1. 加列 —— 源表加列，Iceberg 自动加列，旧数据该列为 null
2. 删列 —— 源表删列，Iceberg 保留列但不再写入（或标记删除）
3. 改类型 —— 需兼容（如 int → bigint），不兼容需处理
4. 重命名 —— Iceberg 支持列重命名，避免数据迁移
5. 同步 —— Debezium 发 schema change 事件，Flink 消费更新 Iceberg
```

```sql
-- Iceberg schema evolution：加列
ALTER TABLE lake.orders ADD COLUMN coupon_id BIGINT;

-- Iceberg schema evolution：改列类型（兼容演进）
ALTER TABLE lake.orders ALTER COLUMN total_amount TYPE DECIMAL(20,2);

-- Iceberg schema evolution：重命名列
ALTER TABLE lake.orders RENAME COLUMN status TO order_status;

-- 查看表历史 schema（时间旅行）
SELECT * FROM lake.orders FOR SYSTEM_VERSION AS OF '2026-08-14 00:00:00';
```

## 幂等与去重

幂等（idempotency）保证「同一操作重复执行结果不变」，去重（dedup）保证「同一变更事件只处理一次」。CDC 同步会面临重复：Flink 从 Checkpoint 恢复重放、Kafka 重复消费、Debezium 重发事件都会导致重复数据。方案：按主键 upsert（同一主键重复写结果一致）+ 事件去重（按 binlog 位置 + 主键去重，同一事件只处理一次），保证数据湖不重复。

```text
幂等与去重要点：
1. 幂等 —— 按主键 upsert，同一主键重复写结果一致
2. 去重 —— 按 binlog 位置/主键去重，同一事件只处理一次
3. 原因 —— Checkpoint 恢复重放、Kafka 重复消费、Debezium 重发
4. 实现 —— 主键 upsert + 事件级去重（GTID/binlog 位置）
5. 保证 —— 端到端 exactly-once，数据湖不重复
```

```java
// Flink 消费 Debezium 事件，按主键 upsert 写 Iceberg（幂等）
DataStream<Row> rows = env.addSource(flinkKafkaConsumer)   // 消费变更事件
    .map(event -> {
        // 只取 after（insert/update），delete 走删除流
        return event.op.equals("d") ? null : toRow(event.after);
    })
    .filter(Objects::nonNull);

// 写 Iceberg，按主键 upsert（幂等：同一主键重复写结果一致）
FlinkSink.forRow(rows, schema)
    .tableName("lake.orders")
    .upsert(true)          // 按主键 upsert，幂等
    .append();
```

```text
去重策略（事件级去重）：
1. GTID 去重 —— MySQL GTID 唯一标识每个事务，重复事件 GTID 相同
2. binlog 位置去重 —— 按 binlog 文件名 + 偏移量标识唯一事件
3. 主键 + 时间戳去重 —— 同一主键同一时间戳只处理一次
4. 实现 —— State 保存已处理事件标识，重复直接跳过
```

## 断点续传与容错

断点续传保证「故障后从断点继续同步，不丢不重」。三层保障：Debezium 记录 binlog 位置（offset），重启从上次位置续传；Kafka 保存消息，Flink 消费位置（offset）可回退重放；Flink Checkpoint 保存作业状态和消费位置，故障从 Checkpoint 恢复。三者配合，任意环节故障都能从断点恢复，保证数据最终一致。

```text
断点续传三层保障：
1. Debezium offset —— 记录 binlog 位置，重启从上次位置续传
2. Kafka offset —— Flink 消费位置可回退，重放未处理消息
3. Flink Checkpoint —— 保存作业状态 + 消费位置，故障恢复
4. 全量 + 增量 —— 首次全量快照，之后增量续传，衔接不断
5. 验证 —— 故障注入测试，确认恢复后数据不丢不重
```

```java
// Flink Checkpoint 保证断点续传
StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.enableCheckpointing(60_000);                        // 60 秒 checkpoint
env.getCheckpointConfig().setCheckpointingMode(CheckpointingMode.EXACTLY_ONCE);

// Kafka 消费位置随 Checkpoint 保存，恢复时从断点续传
Properties props = new Properties();
props.setProperty("group.id", "cdc-sync");
props.setProperty("enable.auto.commit", "false");       // 关闭自动提交，由 Checkpoint 管理
DataStream<String> events = env.addSource(
    new FlinkKafkaConsumer<>("shop.shop.orders", new SimpleStringSchema(), props));
```

```text
容错验证要点：
1. 注入故障 —— 模拟 Flink 作业崩溃、Kafka 重发、MySQL 重启
2. 恢复验证 —— 重启后从断点续传，核对数据量不丢不重
3. 对账 —— 数据湖行数 vs 业务库行数，确认最终一致
4. 断点位置 —— Debezium offset、Kafka offset、Checkpoint 三者对齐
```

## 应用场景实战

### 场景一：订单表实时同步到数据湖

```text
1. MySQL 开启 binlog（ROW 格式），订单表开启变更记录
2. Debezium 首次全量快照订单表，写 Kafka（op=r）
3. 快照完成后订阅 binlog，增量变更写 Kafka（op=c/u/d）
4. Flink 消费 Kafka，按主键 upsert 写 Iceberg
5. 数据湖订单表与业务库秒级同步，供下游实时分析
```

### 场景二：业务表加列后的自动演进

```text
1. 业务在订单表加列 coupon_id（优惠券号）
2. Debezium 捕获 schema change 事件，发到 Kafka
3. Flink 消费 schema change 事件，触发 Iceberg 加列
4. 后续订单变更事件携带 coupon_id 字段，正常写入
5. 旧数据该列为 null，无阻塞、无需人工介入
```

## 最佳实践与踩坑记录

### 最佳实践

1. 开启 binlog 用 ROW 格式 + FULL 行镜像，保证 before/after 完整
2. 变更事件统一走 Kafka 缓冲，一份变更多下游复用
3. 写 Iceberg 按主键 upsert，幂等保证重放不重复
4. Debezium offset、Kafka offset、Checkpoint 三者对齐，保证断点续传
5. Schema 变更走 schema change 事件自动演进，避免人工改表
6. 定期对账数据湖 vs 业务库行数，发现同步漂移及时修复

### 踩坑记录

```text
坑 1：binlog 用 Statement 格式，CDC 解析不出精确行值
结论：Debezium 无法解析非确定性函数，变更数据不准。
原因：binlog_format=STATEMENT，只记录 SQL 不记录行值。
解法：binlog_format=ROW + binlog_row_image=FULL，保证行级 before/after。

坑 2：不加主键 upsert，Checkpoint 恢复后重复数据
结论：故障恢复重放，数据湖出现重复行，对账不一致。
原因：写 Iceberg 用 append 而非 upsert，重放重复插入。
解法：按主键 upsert 写入，同一主键重复写结果一致，保证幂等。

坑 3：Debezium 重启丢失 binlog 位置，从头全量同步
结论：Debezium 重启后从头快照，全量重导耗时且影响下游。
原因：offset 存储未持久化（未配 Kafka 存储 offset），重启丢失位置。
解法：Debezium offset 存 Kafka（offset.storage），重启从断点续传。

坑 4：业务表加列后同步报错，数据湖 schema 未演进
结论：上游加列，Flink 写 Iceberg 报 schema 不匹配，同步中断。
原因：未处理 schema change 事件，数据湖 schema 未同步演进。
解法：消费 schema change 事件自动演进 Iceberg schema，旧数据补 null。

坑 5：全量快照与增量衔接出现数据重复/丢失
结论：快照切换增量瞬间，变更数据重复或丢失。
原因：全量快照与 binlog 增量切换位置未对齐。
解法：Debezium 快照记录一致性位置，增量从该位置续传，保证衔接不丢不重。
```
