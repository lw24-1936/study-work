## 概述

电商离线数仓是电商公司的数据底座，目标是把订单、用户、商品、支付、物流等业务数据，按标准分层（ODS/DWD/DWS/ADS）加工成可供报表、BI、运营分析消费的主题数据。本项目围绕「用户域、商品域、订单域」三大主题域，落地维度建模、缓慢变化维、拉链表、快照表、增量同步等核心数仓技术，产出 GMV、留存、复购等关键经营指标。

```text
项目目标与业务价值：
1. 统一口径 —— GMV、留存、复购等指标口径唯一，全公司一致
2. 主题域划分 —— 用户/商品/订单三大主题域，各自独立可扩展
3. 历史可追溯 —— 拉链表保存维度变化历史，快照表保存每日状态
4. 分层解耦 —— ODS 贴源、DWD 明细、DWS 汇总、ADS 出数，单向依赖
5. 增量高效 —— 增量同步只处理变化数据，降低全量扫描成本
```

## 技术选型

电商离线数仓选型围绕「Hive 数仓 + Spark 计算 + DataX 同步 + DolphinScheduler 调度」的经典组合：Hive 负责元数据和 SQL 层，Spark 负责 ETL 加工（比 MapReduce 快），DataX/Canal 负责数据库同步（全量 + 增量），DolphinScheduler 负责 DAG 调度。选择理由：这套组合生态成熟、社区活跃、招聘需求大，是电商离线数仓的事实标准。

```text
技术选型与理由：
1. 存储 —— HDFS（兼容 Hive）+ Parquet/ORC（列式压缩）
2. 数仓 —— Hive（Metastore 元数据 + SQL 层）
3. 计算 —— Spark（内存计算，ETL 主力引擎）
4. 同步 —— DataX（全量）+ Canal（binlog 增量）
5. 调度 —— DolphinScheduler（DAG + 重试 + 依赖 + 补数）
6. 指标 —— 离线 T+1，凌晨调度产出前一天数据
```

## 架构设计

架构分五层：业务库（MySQL 订单/用户/商品表）→ 同步层（DataX 全量 + Canal 增量）→ 数仓分层（ODS/DWD/DWS/ADS）→ 调度层（DolphinScheduler）→ 应用层（BI 报表）。数据流：业务库每日凌晨经增量同步写入 ODS 贴源层，Spark 任务按「清洗 → 关联 → 汇总」依次加工出 DWD 明细、DWS 汇总、ADS 指标，最后供 BI 消费。

```text
数据流（分层链路）：
MySQL 业务库（订单/用户/商品/支付）
  ↓ DataX 全量 + Canal 增量同步
ODS 贴源层（原始数据，按 dt 分区）
  ↓ Spark 清洗、去重、口径统一
DWD 明细层（事实表 + 维度表）
  ↓ Spark 汇总、关联
DWS 汇总层（主题宽表，日粒度）
  ↓ Hive 出指标
ADS 应用层（GMV/留存/复购结果表）→ BI 报表
```

```text
技术架构：
┌────────────┬────────────┬──────────────┬────────────┐
│  业务库     │  同步层     │  数仓分层     │  应用层     │
│  MySQL     │  DataX     │  ODS/DWD     │  BI 报表   │
│  订单/用户  │  Canal     │  DWS/ADS     │  运营分析   │
│  商品/支付  │  binlog    │  Hive+Spark  │  数据看板   │
└────────────┴────────────┴──────────────┴────────────┘
```

## 数仓分层设计

数仓分层是口径统一和依赖管理的基础。ODS（贴源层）保留原始数据、按日期分区；DWD（明细层）做清洗、去重、口径统一，按主题域建事实表和维度表；DWS（汇总层）按天、按维度做轻度聚合；ADS（应用层）产出可直接被报表消费的指标结果表。分层原则：单向依赖、禁止跳层、禁止反向引用。

```text
分层职责与规范：
1. ODS —— 贴源存储，结构与业务库一致，按 dt 分区，保留原始粒度
2. DWD —— 清洗去重 + 口径统一，事实表 + 维度表，关联外键规范化
3. DWS —— 按主题域轻度汇总，日粒度，宽表化便于查询
4. ADS —— 面向指标的结果表，直接供 BI 报表读取
5. 命名 —— 层.主题_粒度（如 dwd.fact_order_detail、dws.user_gmv_1d）
```

```sql
-- ODS 层：贴源订单表
CREATE TABLE ods.ods_order_info (
    order_id BIGINT COMMENT '订单号',
    user_id BIGINT COMMENT '用户号',
    total_amount DECIMAL(16,2) COMMENT '订单金额',
    order_status STRING COMMENT '订单状态',
    create_time STRING COMMENT '创建时间',
    dt STRING COMMENT '分区日期'
) PARTITIONED BY (dt) STORED AS PARQUET;

-- DWD 层：订单事实表（清洗 + 类型规范）
CREATE TABLE dwd.dwd_fact_order_detail (
    order_id BIGINT COMMENT '订单号',
    user_id BIGINT COMMENT '用户号',
    total_amount DECIMAL(16,2) COMMENT '订单金额',
    order_status STRING COMMENT '订单状态(paid/unpaid/refunded)',
    create_time TIMESTAMP COMMENT '创建时间',
    dt STRING COMMENT '分区日期'
) PARTITIONED BY (dt) STORED AS PARQUET;
```

## 维度建模与缓慢变化维

维度建模是电商数仓的核心建模方法：围绕业务过程建事实表，围绕分析维度建维度表，形成星型/雪花模型。维度属性会随时间缓慢变化（如用户等级升级、商品价格调整），需要缓慢变化维（SCD）策略处理：SCD1 覆盖（不保留历史）、SCD2 新增行（保留历史，配合拉链表）、SCD3 加列（保留上一次值）。电商场景用户/商品维度普遍采用 SCD2 拉链表保留完整变更历史。

```text
缓慢变化维（SCD）三种策略：
1. SCD1 覆盖 —— 直接更新旧值，不保留历史，简单但丢失变更
2. SCD2 新增行 —— 变化时新增一行，用生效/失效时间标记，保留历史
3. SCD3 加列 —— 新增一列保存上一次值，只保留最近一次
4. 选型 —— 用户/商品维度用 SCD2（拉链表），配置类维度用 SCD1
```

```sql
-- 维度表（星型模型）
-- 商品维度表 dim_sku：sku_id, sku_name, category_id, brand, price
-- 用户维度表 dim_user：user_id, user_name, level, city, register_time
-- 事实表关联维度外键
CREATE TABLE dwd.dwd_fact_order_detail (
    order_id BIGINT,
    user_id BIGINT COMMENT '关联 dim_user.user_id',
    sku_id BIGINT COMMENT '关联 dim_sku.sku_id',
    order_amount DECIMAL(16,2),
    order_status STRING,
    dt STRING
) PARTITIONED BY (dt) STORED AS PARQUET;

-- SCD1 覆盖：用户等级直接更新
UPDATE dwd.dim_user SET level = 'vip' WHERE user_id = 1001;

-- SCD2 新增行：用户等级变更时新增一行
INSERT INTO dwd.dim_user (user_id, user_name, level, start_date, end_date)
VALUES (1001, '张三', 'vip', '2026-08-14', '9999-12-31');
UPDATE dwd.dim_user SET end_date = '2026-08-14' WHERE user_id = 1001 AND end_date = '9999-12-31';
```

## 拉链表与快照表设计

拉链表（zipper table）是 SCD2 的落地实现，用「生效日期 start_date + 失效日期 end_date」记录维度每一段状态的有效期，查询时按日期定位历史状态；快照表（snapshot table）每日全量保存一份完整状态（如每日用户资产快照），便于直接取某天全貌但存储成本高。两者配合：拉链表省空间、保存变更历史，快照表省计算、保存每日全量。

```text
拉链表 vs 快照表：
1. 拉链表 —— 只存变化，start_date/end_date 标记有效期，省空间、可追溯
2. 快照表 —— 每日一份全量，查询直接取某天，占空间、但无需还原
3. 拉链表查询历史 —— WHERE start_date <= '日期' AND end_date > '日期'
4. 选型 —— 变化慢、要历史的维度用拉链表；每日全貌用快照表
```

```sql
-- 拉链表结构：记录状态有效期
CREATE TABLE dwd.dim_user_zip (
    user_id BIGINT COMMENT '用户号',
    user_name STRING COMMENT '用户名',
    level STRING COMMENT '用户等级',
    start_date STRING COMMENT '生效日期',
    end_date STRING COMMENT '失效日期(9999-12-31 表示当前有效)'
) STORED AS PARQUET;

-- 拉链表查询某天历史状态
SELECT user_id, level
FROM dwd.dim_user_zip
WHERE start_date <= '2026-08-14' AND end_date > '2026-08-14';

-- 快照表：每日全量保存
CREATE TABLE dws.user_snapshot_daily (
    user_id BIGINT,
    total_order_amount DECIMAL(16,2) COMMENT '累计消费',
    order_cnt BIGINT COMMENT '累计订单数',
    level STRING COMMENT '等级',
    dt STRING COMMENT '快照日期'
) PARTITIONED BY (dt) STORED AS PARQUET;
```

## 数据同步与增量策略

数据同步分「全量 + 增量」两阶段：首次用 DataX 全量同步历史数据，之后用 Canal 订阅 MySQL binlog 做增量同步，只处理新增/变更数据。增量同步的关键是「增量字段」——用 create_time/update_time 或 binlog 偏移量标识变化，每天只抽取 dt 分区内变化的数据，避免全表扫描。DWD 层按增量字段做 upsert 合并，保证数据不丢不重。

```text
增量同步策略要点：
1. 全量 —— DataX 首次同步历史数据，一次性落 ODS
2. 增量 —— Canal 订阅 binlog，实时/准实时同步变化数据
3. 增量字段 —— update_time/create_time 标识，按 dt 抽取变化数据
4. 合并 —— DWD 层按主键 upsert，处理新增 + 变更
5. 幂等 —— 同步可重放，重跑不产生重复数据
```

```sql
-- 增量同步：只抽取当日变化数据
INSERT INTO TABLE ods.ods_order_info PARTITION (dt = '2026-08-14')
SELECT * FROM ods.ods_order_info_tmp
WHERE update_time >= '2026-08-14 00:00:00'
  AND update_time < '2026-08-15 00:00:00';

-- DWD 层按主键 upsert 合并增量
INSERT OVERWRITE TABLE dwd.dwd_fact_order_detail PARTITION (dt = '2026-08-14')
SELECT o.order_id, o.user_id, o.total_amount,
       CASE WHEN o.order_status IN ('paid','shipped','finished') THEN 'paid'
            WHEN o.order_status = 'refunded' THEN 'refunded'
            ELSE 'unpaid' END AS order_status,
       o.create_time, o.dt
FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY update_time DESC) AS rn
    FROM ods.ods_order_info WHERE dt = '2026-08-14'
) o WHERE o.rn = 1;
```

## 用户域与留存复购指标

用户域关注「人」的维度：用户注册、活跃、消费行为。核心指标是留存（retention）和复购（repurchase）。留存率 = 新增用户中第 N 天仍活跃的比例，衡量产品粘性；复购率 = 有二次及以上购买行为的用户占比，衡量用户忠诚度。计算留存需按「新增日 + 活跃日」双维度分组，复购需按用户聚合订单次数判断。

```text
留存与复购指标定义：
1. 次日留存 —— 新增用户中第 2 天仍活跃的用户占比
2. N 日留存 —— 新增用户中第 N 天仍活跃的用户占比
3. 复购率 —— 购买次数 >= 2 的用户数 / 总购买用户数
4. 复购周期 —— 用户两次购买之间的平均间隔
5. 留存口径 —— 活跃以「登录」或「下单」为准，需统一
```

```sql
-- 留存率：新增用户次日留存
WITH new_users AS (
    SELECT user_id, MIN(dt) AS first_dt
    FROM dws.user_active_daily GROUP BY user_id
),
retained AS (
    SELECT n.first_dt,
           COUNT(DISTINCT n.user_id) AS new_cnt,
           COUNT(DISTINCT a.user_id) AS retained_cnt
    FROM new_users n
    LEFT JOIN dws.user_active_daily a
        ON n.user_id = a.user_id
       AND a.dt = DATE_ADD(n.first_dt, 1)
    GROUP BY n.first_dt
)
SELECT first_dt, retained_cnt / new_cnt AS next_day_retention
FROM retained;

-- 复购率：购买次数 >= 2 的用户占比
SELECT SUM(CASE WHEN order_cnt >= 2 THEN 1 ELSE 0 END) / COUNT(*) AS repurchase_rate
FROM (
    SELECT user_id, COUNT(DISTINCT order_id) AS order_cnt
    FROM dwd.dwd_fact_order_detail
    WHERE order_status = 'paid'
    GROUP BY user_id
) t;
```

## 商品域主题

商品域关注「货」的维度：商品（SKU）、类目（category）、品牌（brand）、价格（price）。商品维度属性（类目、品牌、价格）会随时间变化，采用 SCD2 拉链表保存历史；商品销售事实记录每个 SKU 的销量、销售额、库存。商品域支撑「畅销榜、类目销售占比、价格带分布、新品动销」等分析。

```text
商品域要点：
1. 维度 —— SKU/类目/品牌/价格，SKU 是最小粒度
2. 类目层级 —— 一级/二级/三级类目，层级关联
3. 价格变化 —— 商品调价用 SCD2 拉链表记录历史价格
4. 销售事实 —— 每个 SKU 的销量、销售额、库存快照
5. 分析场景 —— 畅销榜、类目占比、价格带、新品动销
```

```sql
-- 商品维度表（SCD2 拉链表）
CREATE TABLE dwd.dim_sku (
    sku_id BIGINT,
    sku_name STRING,
    category_l1 STRING COMMENT '一级类目',
    category_l2 STRING COMMENT '二级类目',
    brand STRING,
    price DECIMAL(16,2),
    start_date STRING,
    end_date STRING
) STORED AS PARQUET;

-- 类目销售占比
SELECT d.category_l1,
       SUM(f.order_amount) AS category_gmv,
       SUM(f.order_amount) / SUM(SUM(f.order_amount)) OVER () AS ratio
FROM dwd.dwd_fact_order_detail f
JOIN dwd.dim_sku d ON f.sku_id = d.sku_id
WHERE f.order_status = 'paid' AND f.dt = '2026-08-14'
  AND d.start_date <= '2026-08-14' AND d.end_date > '2026-08-14'
GROUP BY d.category_l1;
```

## 订单域与 GMV 指标

订单域是电商数仓最核心的主题域，关注「交易」的完整生命周期：下单 → 支付 → 发货 → 完成 → 退款的订单状态流转。核心指标 GMV（Gross Merchandise Volume，成交总额）是电商经营的第一指标。GMV 计算要明确口径：含不含退款、含不含未支付订单，通常「支付口径 GMV = 已支付订单金额之和」。订单域还衍生出订单量、客单价、转化率、退款率等指标。

```text
GMV 与订单域指标：
1. GMV —— 成交总额，支付口径 = 已支付订单金额之和
2. 订单量 —— 下单/支付/完成各状态订单数
3. 客单价 —— GMV / 支付订单数
4. 转化率 —— 支付订单数 / 下单订单数
5. 退款率 —— 退款订单数 / 支付订单数
6. 口径 —— 必须明确「含不含未支付/退款」，全公司统一
```

```sql
-- GMV：支付口径成交总额
SELECT dt, SUM(total_amount) AS gmv, COUNT(DISTINCT order_id) AS paid_order_cnt
FROM dwd.dwd_fact_order_detail
WHERE order_status = 'paid' AND dt = '2026-08-14'
GROUP BY dt;

-- 客单价与退款率
SELECT SUM(total_amount) / COUNT(DISTINCT order_id) AS avg_order_value,
       SUM(CASE WHEN order_status = 'refunded' THEN 1 ELSE 0 END)
           / COUNT(DISTINCT order_id) AS refund_rate
FROM dwd.dwd_fact_order_detail
WHERE dt = '2026-08-14';

-- ADS 层：GMV 结果表
CREATE TABLE ads.ads_gmv_daily (
    dt STRING COMMENT '日期',
    gmv DECIMAL(20,2) COMMENT '成交总额',
    paid_order_cnt BIGINT COMMENT '支付订单数',
    avg_order_value DECIMAL(16,2) COMMENT '客单价'
) PARTITIONED BY (dt) STORED AS PARQUET;
```

## 应用场景实战

### 场景一：日报 GMV 与留存复购产出

```text
1. 凌晨 0 点：DolphinScheduler 触发日调度 DAG
2. DataX 全量 + Canal 增量同步 MySQL 到 ODS（按 dt 分区）
3. Spark 清洗写 DWD：订单事实表 + 用户/商品维度表（SCD2 拉链表更新）
4. Spark 汇总写 DWS：用户日活跃、订单日汇总、用户快照表
5. Hive 出 ADS：GMV 日报、留存率、复购率结果表
6. 质量校验通过后 BI 报表读取 ADS 出数
```

### 场景二：商品调价后历史价格追溯

```text
1. 运营在后台修改商品价格（price 从 99 改为 129）
2. Canal 捕获商品表 update 事件，同步到 ODS
3. 拉链表加工：旧价格行 end_date 置为当日，新增价格行 start_date 为当日
4. 查询历史：指定日期取 start_date/end_date 覆盖该日期的价格行
5. 支撑「历史价格趋势、调价对销量影响」分析
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先定指标口径（GMV 含不含退款、留存活跃口径），全公司统一，避免口径打架
2. 严格分层单向依赖（ODS/DWD/DWS/ADS），禁止跳层和反向引用
3. 维度表用 SCD2 拉链表保留历史，配合快照表查每日全貌
4. 增量同步用 update_time 标识变化，DWD 层按主键 upsert 保证幂等
5. 大表按 dt 分区，分区裁剪是查询性能的基础
6. 维度表和事实表用外键关联，避免大表 join 大表

### 踩坑记录

```text
坑 1：GMV 口径不统一，财务和运营各算各的
结论：同一 GMV 出现多个数值，汇报时打架。
原因：没明确「含不含未支付/退款订单」，各团队口径不一。
解法：指标口径文档化，支付口径统一，ADS 层只出一份结果。

坑 2：维度变化直接覆盖，历史订单关联错误维度
结论：用户等级升级后，历史订单全算到新等级，分析失真。
原因：维度表用 SCD1 覆盖，丢失了历史状态。
解法：维度用 SCD2 拉链表，历史订单按订单日期关联对应历史维度。

坑 3：全量同步每天都全表扫描，任务越跑越慢
结论：数据量增长后全量同步耗时数小时，影响出数 SLA。
原因：没做增量同步，每天全表重导。
解法：全量 + 增量结合，增量只处理 update_time 变化的数据。

坑 4：增量同步不幂等，重跑产生重复数据
结论：任务失败重跑后，DWD 出现重复订单行，GMV 翻倍。
原因：增量合并没按主键去重，重跑重复插入。
解法：DWD 层按主键 upsert（ROW_NUMBER 取最新），保证幂等可重放。

坑 5：拉链表 end_date 处理不当，出现重叠有效期
结论：同一维度多行 end_date 都未闭合，查询历史返回多行。
原因：更新拉链表时只新增未关闭旧行的 end_date。
解法：变更时先关闭旧行（end_date = 变更日），再新增新行，保证有效期不重叠。
```
