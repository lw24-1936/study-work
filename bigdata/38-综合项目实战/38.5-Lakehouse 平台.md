## 概述

Lakehouse 平台的目标是把「数据湖的廉价灵活」与「数据仓库的 ACID 与管理能力」合二为一：数据统一落在对象存储上，用开放表格式 Iceberg 提供事务、版本、模式演进与时间旅行，Spark / Flink / Trino 三类引擎共享同一份数据，实现「一份数据、多引擎读写、批流一体」。本项目围绕「Object Storage + Iceberg + Spark + Flink + Trino」搭建，并补齐 Catalog、Schema Evolution、Time Travel、Compaction 与治理五大能力。

```text
项目目标与业务价值：
1. 一份数据 —— 对象存储上只存一份，批/流/交互三种引擎共享
2. 开放格式 —— Iceberg 开放表格式，不绑定厂商，避免 vendor lock-in
3. ACID 能力 —— 事务写入、版本快照、模式演进、时间旅行
4. 成本可控 —— 对象存储成本远低于数仓专属存储，冷热分层
5. 治理闭环 —— Catalog 元数据 + Compaction 文件治理 + 权限血缘
```

## 技术选型

Lakehouse 的选型核心是「存储计算分离 + 开放表格式」。存储选对象存储（S3/OSS/MinIO），因为廉价、无限扩展、天然支持计算分离；表格式选 Apache Iceberg，因为它是开放标准，生态支持最广（Spark/Flink/Trino 都有原生集成），且支持隐藏分区、模式演进、行级删除等仓库级能力；Catalog 选 REST Catalog 或 Hive Metastore，统一元数据入口；计算引擎按场景分工——Spark 批处理、Flink 流式写入、Trino 交互式联邦查询。

```text
技术选型与理由：
1. 存储 —— 对象存储（S3/OSS/MinIO）：廉价、无限扩展、计算分离
2. 表格式 —— Iceberg：开放标准、ACID、多引擎生态最全
3. Catalog —— REST/Hive Metastore：元数据统一入口，避免多引擎各自为政
4. 批处理 —— Spark：成熟批计算，读写 Iceberg 原生支持
5. 流写入 —— Flink：低延迟实时写入 Iceberg，批流一体
6. 交互查询 —— Trino：秒级联邦查询，BI 与自助分析入口
```

## 架构设计

架构分四层：存储层（对象存储上的数据文件 + 元数据文件）→ 表格式层（Iceberg 提供表抽象与快照）→ 计算层（Spark/Flink/Trino 共享读写）→ 应用层（BI 报表、数据科学、实时应用）。数据流：Flink 实时写入 Iceberg 表生成增量数据文件，Spark 定期 Compaction 合并小文件，Trino 直接查询最新快照；所有引擎通过同一 Catalog 解析表元数据。

```text
架构分层（数据流）：
数据源（业务库/日志/流）
  ↓ 实时写入（Flink）
Iceberg 表（对象存储：data + metadata + snapshot）
  ↓ 批处理/合并（Spark）
Compaction 后的数据文件
  ↓ 交互查询（Trino）/ 批分析（Spark）
应用层：BI 报表 / 数据科学 / 实时看板
```

```text
技术架构：
┌──────────────┬───────────────┬────────────────┬──────────────┐
│   存储层      │   表格式层      │    计算层        │   应用层      │
│  对象存储 S3  │  Iceberg 表   │  Spark 批处理   │  BI 报表     │
│  data 文件    │  metadata 文件 │  Flink 流写入   │  数据科学    │
│  snapshot     │  manifest 清单 │  Trino 交互查询 │  实时看板    │
└──────────────┴───────────────┴────────────────┴──────────────┘
```

## 对象存储与 Iceberg 表格式

对象存储只提供「按 key 读写对象」的扁平语义，没有目录树和事务，因此需要 Iceberg 在对象存储之上构建「表」的抽象。Iceberg 用三层文件组织表：数据文件（Parquet/ORC）存实际数据，Manifest 清单文件记录数据文件的列统计信息，Manifest List 与 Metadata 文件记录快照。元数据与数据分离，使快照隔离、时间旅行、增量读取都基于元数据层的原子切换实现，不重写数据文件。

```text
Iceberg 表的三层文件结构：
1. 数据文件 —— Parquet/ORC，存真实数据
2. Manifest 清单 —— 记录数据文件路径 + 列级统计（min/max/null count）
3. Metadata/snapshot —— 表级别元数据 + 快照链，指向 manifest list
```

```sql
-- 在对象存储上建 Iceberg 表（以 Spark SQL 为例）
CREATE TABLE lakehouse.db.orders (
    order_id BIGINT,
    user_id BIGINT,
    amount DECIMAL(10,2),
    status STRING,
    created_at TIMESTAMP
) USING iceberg
PARTITIONED BY (months(created_at))
LOCATION 's3://lakehouse/db/orders';
```

## Catalog 与元数据管理

Catalog 是「表名 → 表元数据位置」的映射，所有引擎读写前都先经 Catalog 解析表。多引擎共享同一份数据的关键就是共享同一个 Catalog，否则 Spark 建的表 Flink/Trino 认不出来。项目用 REST Catalog 作为统一入口，它把元数据管理服务化，支持跨引擎一致、原子切换元数据指针、权限校验等能力。

```text
Catalog 的作用：
1. 名称解析 —— 表名 → metadata 文件位置
2. 多引擎一致 —— Spark/Flink/Trino 共享同一 Catalog
3. 原子提交 —— 元数据指针切换保证事务可见性
4. 权限入口 —— 统一鉴权，防止绕过引擎直接读写
```

```sql
-- Flink 通过 SQL Client 配置 Iceberg Catalog
CREATE CATALOG lakehouse_catalog WITH (
    'type' = 'iceberg',
    'catalog-type' = 'rest',
    'uri' = 'http://rest-catalog:8181',
    'warehouse' = 's3://lakehouse'
);
USE CATALOG lakehouse_catalog;
```

## 计算引擎统一接入

三类引擎共享 Iceberg 表，各司其职：Spark 做批处理（ETL、重算、Compaction），Flink 做实时写入（低延迟 upsert 到 Iceberg，实现批流一体），Trino 做交互式联邦查询（BI 自助分析、秒级返回）。因为都走同一 Catalog + 同一表格式，数据只存一份，消除了「仓库里一份、湖里一份」的双份存储与口径不一致问题。

```scala
// Spark 批处理写入 Iceberg（ETL 结果落地）
val df = spark.read.parquet("s3://raw/orders")
df.writeTo("lakehouse.db.orders")
  .append()
```

```sql
-- Flink 实时写入 Iceberg（CDC 流 upsert）
INSERT INTO lakehouse.db.orders
SELECT order_id, user_id, amount, status, created_at
FROM cdc_source_stream;
```

```sql
-- Trino 交互式查询 Iceberg 表
SELECT status, COUNT(*) AS cnt, SUM(amount) AS gmv
FROM lakehouse.db.orders
WHERE created_at >= DATE '2026-08-01'
GROUP BY status;
```

## Schema Evolution 模式演进

Schema Evolution 指表结构随业务变化而演进——加列、删列、改类型、重命名——而不需要重建表或停机。Iceberg 通过「元数据层记录每列的 field id」实现：列的身份由 field id 决定而非名字，因此重命名列、调整列顺序都不改变数据文件，加列是元数据操作，几乎零成本。这是相比 Hive 表的关键优势——Hive 加列往往要重写数据或位置错位。

```sql
-- 加列：元数据操作，不重写数据
ALTER TABLE lakehouse.db.orders
ADD COLUMN channel STRING;

-- 重命名列：field id 不变，数据文件无需改动
ALTER TABLE lakehouse.db.orders
RENAME COLUMN amount TO order_amount;

-- 改列类型：宽化（int -> long）安全，窄化需校验
ALTER TABLE lakehouse.db.orders
ALTER COLUMN order_amount TYPE DECIMAL(12,2);
```

## Time Travel 时间旅行

Time Travel 让查询能回到任意历史快照读取数据，实现「数据版本回溯」——可用于数据误删恢复、审计、重现历史报表。Iceberg 每次写入生成一个新 snapshot，snapshot id 或时间戳都可作为查询入口，历史快照保留到过期策略触发为止。相比 Hive「覆盖即丢」，Time Travel 是数据安全的重大提升。

```sql
-- 按时间戳回看历史数据（Trino/Spark 支持）
SELECT * FROM lakehouse.db.orders
FOR TIMESTAMP AS OF TIMESTAMP '2026-08-13 23:59:59';

-- 按 snapshot id 精确回溯
SELECT * FROM lakehouse.db.orders
FOR VERSION AS OF 87654321;
```

```text
Time Travel 的典型用途：
1. 误删恢复 —— 回滚到删除前快照，找回数据
2. 报表重现 —— 重现某历史时点口径
3. 数据对比 —— 对比两个版本的差异
4. 审计溯源 —— 追溯某时间点的数据状态
```

## Compaction 与文件治理

流式写入（尤其 Flink 高频 upsert）会产生大量小文件，导致查询性能下降、元数据膨胀。Compaction 通过合并小文件为大文件、清理过期快照与孤儿文件，维持表的健康状态。项目用 Spark 定期（如每小时）跑 Compaction 任务，合并数据文件、按分区重写，并配合 expire_snapshots 与 remove_orphan_files 清理历史版本。

```sql
-- 触发 Compaction（Spark 的 rewrite_data_files）
CALL lakehouse.system.rewrite_data_files(
    table => 'db.orders',
    strategy => 'binpack',
    options => map('target-file-size-bytes', '134217728')
);
```

```sql
-- 清理过期快照（保留最近 7 天）
CALL lakehouse.system.expire_snapshots(
    table => 'db.orders',
    older_than => TIMESTAMP '2026-08-07 00:00:00',
    retain_last => 7
);
```

```text
文件治理三大任务：
1. Compaction —— 合并小文件，控制文件大小与数量
2. 快照过期 —— expire_snapshots 清理历史快照
3. 孤儿文件 —— remove_orphan_files 清理无引用数据文件
```

## 数据治理

治理贯穿 Lakehouse 全生命周期：元数据治理靠 Catalog 统一管理表与分区；权限治理靠 Ranger 结合 Iceberg 做库/表/列级鉴权；数据质量靠写入前校验 + 表级约束；血缘靠 Catalog 记录表依赖；生命周期靠冷热分层（热数据标准存储、冷数据归档存储）+ 快照过期策略控制成本。治理的落点是「数据可发现、可管控、可追溯、成本可控」。

```text
治理维度与落地：
1. 元数据 —— Catalog 统一管理，表/分区/字段可发现
2. 权限 —— Ranger 做库表列级鉴权，多引擎统一
3. 质量 —— 写入校验 + 表约束，脏数据不入湖
4. 血缘 —— 表依赖追踪，支撑影响分析
5. 成本 —— 冷热分层 + 快照过期 + 小文件治理
```

## 应用场景实战

### 场景一：CDC 数据实时入湖（批流一体）

```text
1. Debezium 采集 MySQL binlog，进入 Kafka
2. Flink 消费 CDC 流，按主键 upsert 写入 Iceberg 表
3. 数据实时可见，Trino 秒级查询最新状态
4. Spark 每小时跑 Compaction 合并小文件
5. 深夜跑 expire_snapshots 清理历史快照
6. BI 通过 Trino 直接消费 Iceberg 表
```

### 场景二：误删数据的 Time Travel 恢复

```text
1. 运维误操作覆盖了 orders 表
2. 通过 snapshot 历史找到覆盖前的 snapshot id
3. 用 FOR VERSION AS OF 查回历史数据
4. 将历史数据写回新表或回滚当前表
5. 确认无误后保留恢复证据，供审计
```

## 最佳实践与踩坑记录

### 最佳实践

1. 三个引擎必须共享同一个 Catalog，否则表互不可见
2. 分区用 Iceberg 隐藏分区（months/days），查询无需写分区字段
3. Schema 变更走 field id 语义，重命名前评估下游影响
4. Compaction 定时跑，防止小文件堆积拖垮查询
5. 快照过期策略要配置，避免元数据无限膨胀
6. 冷热分层存储，历史数据降冷控成本

### 踩坑记录

```text
坑 1：各引擎各建一套 Catalog，表互不可见
结论：Spark 建的表 Flink 读不到，重复建表、口径分裂。
原因：Catalog 不统一，元数据各存一份。
解法：统一 REST Catalog 作为唯一入口，禁止直连绕过。

坑 2：实时写入不 Compaction，小文件爆炸
结论：查询变慢、元数据膨胀、对象存储 LIST 成本飙升。
原因：Flink 高频 upsert 产生海量小文件，无人合并。
解法：Spark 定时 rewrite_data_files，按 target-file-size 合并。

坑 3：快照不清理，元数据无限增长
结论：metadata 文件越积越多，表加载和查询规划变慢。
原因：只写不删，历史快照永久保留。
解法：配置 expire_snapshots 保留策略，定期清理孤儿文件。

坑 4：改列类型时选了不安全的窄化转换
结论：decimal(12,2) 改 decimal(6,2) 导致数据截断或写入失败。
原因：不了解 Iceberg 类型演进的「宽化安全、窄化需校验」规则。
解法：优先宽化，窄化前先校验数据范围，必要时重写表。

坑 5：Time Travel 依赖快照但快照被过早清理
结论：想回看历史数据时快照已过期，无法恢复。
原因：快照保留期太短，没按业务审计需求设置。
解法：按审计合规要求设置 retain_last 与保留时长，重要表单独延长。
```
