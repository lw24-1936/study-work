## 概述

离线数据分析平台是企业数据基础设施的「地基」：把分散在各业务系统的数据采集到统一存储，经过清洗、加工、分层，形成可供 BI 报表和数据分析消费的数据资产。本项目的目标是搭建一个「文件/Kafka → 对象存储/HDFS → Hive/Spark → 数仓 → BI」的完整离线数据链路，覆盖采集、契约、质量、血缘、监控、告警，并用 Docker/Kubernetes 部署。

```text
项目目标与业务价值：
1. 统一采集 —— 业务库、日志、文件多源接入，统一落地
2. 分层数仓 —— ODS/DWD/DWS/ADS 分层，口径统一
3. 质量保障 —— 数据契约 + 质量校验 + 血缘追踪
4. 稳定运维 —— 监控告警 + 故障演练 + 性能测试
```

## 技术选型

技术选型围绕「离线批处理」的成熟组合：采集用 Kafka（实时缓冲）+ Flume/DataX（批量迁移），存储用对象存储（S3/OSS）或 HDFS，数仓用 Hive（元数据 + SQL 层），计算用 Spark（内存计算替代 MapReduce），调度用 DolphinScheduler（国产、可视化 DAG），质量用 Great Expectations，血缘用 Atlas。选择理由：这套组合是「开源 + 成熟 + 生态完善」的标准答案。

```text
技术选型与理由：
1. 采集 —— Kafka（缓冲解耦）+ DataX（异构源迁移）+ Flume（日志）
2. 存储 —— 对象存储（低成本、无限扩展）+ HDFS（兼容 Hive）
3. 数仓 —— Hive（SQL 层 + Metastore 元数据）
4. 计算 —— Spark（内存计算，比 MR 快几个数量级）
5. 调度 —— DolphinScheduler（DAG 编排 + 重试 + 依赖）
6. 质量 —— Great Expectations（规则校验）
7. 血缘 —— Atlas（表/列血缘追踪）
```

## 架构设计

架构分四层：数据源层（业务库、日志、文件）→ 采集层（Kafka/DataX/Flume）→ 存储计算层（对象存储 + Hive + Spark + DolphinScheduler）→ 应用层（BI 报表、数据服务）。数据流：业务数据经 CDC/批量采集进入 Kafka 或直接落地，再由调度任务按 DAG 依次执行「采集 → 清洗 → 分层加工 → 出数」，最后供 BI 消费。

```text
架构分层（数据流）：
业务库/日志/文件
  ↓ 采集（DataX/Kafka/Flume）
ODS 层（对象存储/HDFS，贴源）
  ↓ 清洗（Spark，DWD）
DWD 明细层（口径统一）
  ↓ 汇总（Spark，DWS）
DWS 汇总层（主题宽表）
  ↓ 出数（Hive，ADS）
ADS 应用层 → BI 报表 / 数据服务
```

```text
技术架构：
┌─────────────┬──────────────┬───────────────┬─────────────┐
│  数据源层    │   采集层      │  存储计算层     │   应用层     │
│  MySQL/Oracle│  Kafka       │  对象存储/HDFS │  BI 报表    │
│  日志文件     │  DataX       │  Hive + Spark │  数据服务    │
│  埋点流       │  Flume       │  DolphinSched │  自助分析    │
└─────────────┴──────────────┴───────────────┴─────────────┘
```

## 数据采集模块

采集模块负责「把分散的数据搬到统一存储」。分三类：数据库同步（DataX 全量 + Canal/Debezium 增量）、日志采集（Flume/Filebeat 落盘）、埋点/消息（Kafka 消费落地）。核心是「数据契约」——定义每个数据源的 schema、格式、分区、SLA，生产者和消费者对齐。采集要保证「不丢、不重、可重放」。

```text
采集模块要点：
1. 数据库 —— DataX 全量 + Canal 增量（binlog）
2. 日志 —— Flume/Filebeat 采集落盘
3. 消息 —— Kafka 消费落地对象存储
4. 契约 —— schema/格式/分区/SLA 定义，生产消费对齐
```

```shell
# DataX 全量同步 MySQL 到 HDFS
```

## 存储与数仓模块

存储用对象存储（按 bucket/前缀组织）或 HDFS，数仓用 Hive 建 ODS/DWD/DWS/ADS 四层。ODS 贴源（按日期分区、保留原始粒度），DWD 清洗（去重、类型规范、口径统一），DWS 汇总（按主题轻度聚合），ADS 出数（供 BI 直接消费）。分区统一按 dt（日期），大表必须分区。

```sql
-- ODS 层：贴源存储
CREATE TABLE ods.orders (
    order_id BIGINT, user_id BIGINT, amount DECIMAL(10,2),
    status STRING, created_at TIMESTAMP, dt STRING
) PARTITIONED BY (dt) STORED AS PARQUET;

-- DWD 层：清洗 + 口径统一
CREATE TABLE dwd.order_detail AS
SELECT order_id, user_id, amount,
       CASE WHEN status IN ('paid','shipped') THEN 'paid'
            WHEN status = 'refunded' THEN 'refunded' END AS status,
       created_at, dt
FROM ods.orders WHERE dt = '${bizdate}' AND order_id IS NOT NULL;

-- DWS 层：按天汇总
CREATE TABLE dws.user_order_1d AS
SELECT user_id, dt, COUNT(*) AS order_cnt, SUM(amount) AS gmv
FROM dwd.order_detail WHERE dt = '${bizdate}'
GROUP BY user_id, dt;
```

## 计算与加工模块

计算用 Spark（内存计算），加工任务是 DolphinScheduler 编排的 DAG：每个节点是一个 Spark SQL / Spark 批处理任务，节点间有依赖关系（先 ODS 后 DWD 后 DWS）。调度器负责「定时触发、依赖检查、失败重试、补数（backfill）」。任务失败告警、超时告警，支持断点续跑。

```python
# Spark 批处理任务（DWD 层加工）
from pyspark.sql import SparkSession

spark = SparkSession.builder.enableHiveSupport().getOrCreate()

# 从 ODS 读，清洗写 DWD
df = spark.sql("SELECT * FROM ods.orders WHERE dt = '${bizdate}'")
cleaned = df.dropDuplicates(["order_id"]) \
    .na.drop(subset=["order_id"]) \
    .withColumn("status", df.status)   # 口径统一
cleaned.write.mode("overwrite") \
    .partitionBy("dt") \
    .saveAsTable("dwd.order_detail")
```

## 数据质量与血缘

数据质量用 Great Expectations 定义规则（非空、唯一、范围、分布），在每个加工任务后跑校验，不通过则告警并阻断下游。血缘用 Atlas 自动采集（Hive hook + Spark 任务），追踪「表 → 列 → 任务」的依赖关系，支撑影响分析和数据溯源。

```text
质量与血缘要点：
1. 质量规则 —— 非空/唯一/范围/分布，任务后校验
2. 阻断 —— 质量不通过，阻断下游任务
3. 血缘 —— Atlas 采集表/列/任务依赖
4. 影响分析 —— 改一个表，知道影响哪些下游
```

```python
# Great Expectations 校验示例
import great_expectations as ge

df = ge.read_parquet("s3://warehouse/dwd/orders/")
result = df.expect_column_values_to_not_be_null("order_id") and \
         df.expect_column_values_to_be_unique("order_id") and \
         df.expect_column_values_to_be_between("amount", 0, 1000000)
if not result.success:
    raise RuntimeError("质量校验失败，阻断下游")
```

## 监控与告警

监控覆盖「调度监控 + 数据监控 + 资源监控」：调度监控看任务成功率、耗时、积压；数据监控看数据量波动（分区行数 vs 历史均值）、数据延迟（产出时间 vs SLA）；资源监控看集群 CPU/内存/存储。告警走 Prometheus + Alertmanager（或 DolphinScheduler 自带告警），分级告警（P0 电话、P1 短信、P2 邮件）。

```text
监控告警要点：
1. 调度监控 —— 任务成功率/耗时/失败重试
2. 数据监控 —— 数据量波动、数据延迟（SLA）
3. 资源监控 —— CPU/内存/存储利用率
4. 分级告警 —— P0/P1/P2 分级，不同通知渠道
```

## 应用场景实战

### 场景一：电商日增数据的完整离线链路

```text
1. 凌晨 0 点：DolphinScheduler 触发日调度
2. DataX 全量 + Canal 增量同步 MySQL 到 ODS（贴源）
3. Spark 任务清洗写 DWD（口径统一、去重）
4. Spark 任务汇总写 DWS（按天、按用户聚合）
5. Hive 出 ADS（报表口径结果表）
6. Great Expectations 校验 + Atlas 血缘记录
7. BI 报表读取 ADS 出数
```

### 场景二：任务失败自动重试 + 告警

```text
1. DWD 任务失败（如数据源连接超时）
2. DolphinScheduler 自动重试（配置重试 3 次、间隔 5 分钟）
3. 重试仍失败 → 触发 P1 告警（短信通知 oncall）
4. oncall 排查（看日志 + 血缘定位影响下游）
5. 修复后手动补数（backfill），或从断点续跑
```

## 最佳实践与踩坑记录

### 最佳实践

1. 采集先定数据契约（schema/格式/SLA），生产消费对齐，别各写各的
2. 数仓严格分层（ODS/DWD/DWS/ADS），单向依赖，禁止跳层
3. 大表按日期分区，分区裁剪是查询性能的基础
4. 每个加工任务后跑质量校验，不通过阻断下游
5. 血缘从第一天就采集，别等数据乱了才补
6. 监控告警分级，避免告警疲劳

### 踩坑记录

```text
坑 1：数据契约没约定，生产消费各写各的
结论：上游改字段下游报错，联调反复。
原因：没有数据契约，schema/格式/SLA 没对齐。
解法：采集前先定契约文档，字段变更走评审和版本。

坑 2：数仓不分层，ADS 直接读 ODS
结论：口径混乱，同一指标多处实现，改一处漏一处。
原因：图省事跨层取数，破坏分层依赖。
解法：严格分层单向依赖，用血缘校验禁止跳层。

坑 3：没做数据质量校验
结论：脏数据（null、重复、超范围）混进报表，业务决策出错。
原因：采集和加工都没有质量校验。
解法：加工后跑质量规则，不通过阻断下游 + 告警。

坑 4：任务失败没有重试和告警
结论：凌晨任务失败，第二天才发现报表没出。
原因：调度没配重试、没配告警，失败静默。
解法：调度配重试 + 超时告警 + 分级通知。

坑 5：小文件问题没治理
结论：Spark 写 Hive 产生大量小文件，查询变慢。
原因：Spark 默认每个分区写一个小文件，分区多小文件就多。
解法：写时 coalesce 控制分区数，定期合并小文件。
```
