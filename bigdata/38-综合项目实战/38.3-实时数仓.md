## 概述

实时数仓解决「数据延迟」问题：把原来 T+1 才出的离线指标，压缩到秒级/分钟级产出。链路是「业务库/埋点 → Kafka → Flink → StarRocks/Doris/Iceberg/Redis」，用 Flink 做实时计算，Event Time + Watermark + Window + State + Checkpoint 保证乱序处理和精确一次，产出实时指标、实时维表关联和实时画像，支撑大促实时监控、实时风控等场景。

```text
项目目标与业务价值：
1. 秒级延迟 —— 数据从产生到可查秒级，告别 T+1
2. 实时指标 —— 实时 GMV、订单量、UV 等秒级刷新
3. 精确一次 —— Checkpoint + 幂等写入保证不丢不重
4. 实时画像 —— 用户行为实时更新画像标签
5. 实时维表 —— 维度变化实时同步，join 结果实时准确
```

## 技术选型

实时数仓选型围绕「Kafka 消息缓冲 + Flink 流计算 + 多目标存储」：Kafka 做高吞吐消息缓冲和解耦，Flink 做有状态流计算（Event Time/Watermark/Window/State/Checkpoint 能力最强），存储按用途分——StarRocks/Doris 做实时 OLAP 查询（秒级响应），Iceberg 做实时数据湖落地（支持 ACID 和 upsert），Redis 做实时结果缓存（低延迟读）。选择理由：Flink 是流计算事实标准，OLAP + 湖 + 缓存的组合覆盖「查询/落地/低延迟」三种需求。

```text
技术选型与理由：
1. 消息 —— Kafka（高吞吐、分区有序、多消费者）
2. 计算 —— Flink（Event Time/Watermark/State/Checkpoint 最成熟）
3. OLAP —— StarRocks/Doris（MPP 列式，秒级聚合查询）
4. 湖 —— Iceberg（ACID、upsert、schema evolution）
5. 缓存 —— Redis（实时结果低延迟读、画像标签存储）
6. 维表 —— Flink 侧输出流 + 广播流，维度变化实时更新
```

## 架构设计

架构分四层：数据源（业务库 binlog + 埋点日志）→ 消息层（Kafka 多 topic）→ 计算层（Flink 多作业，分层 ODS/DWD/DWS）→ 存储层（StarRocks/Doris 查询、Iceberg 落地、Redis 缓存）。数据流：数据进 Kafka 后，Flink 作业按「清洗 → 关联维表 → 开窗聚合 → 写出」处理，实时指标写 StarRocks，明细落地 Iceberg，标签写 Redis。

```text
数据流（实时链路）：
业务库 binlog / 埋点日志
  ↓ 采集（Canal/Flink CDC）
Kafka（ODS topic）
  ↓ Flink 清洗 + 关联维表
Kafka（DWD topic）
  ↓ Flink 开窗聚合
DWS（实时指标）
  ↓ 写出
StarRocks（OLAP 查询）+ Iceberg（落地）+ Redis（缓存）
```

```text
技术架构：
┌────────────┬────────────┬──────────────┬────────────┐
│  数据源     │  消息层     │  计算层       │  存储层     │
│  MySQL binlog│ Kafka     │  Flink 作业   │  StarRocks │
│  埋点日志    │  多 topic  │  ODS/DWD/DWS │  Doris     │
│  业务系统    │  分区有序  │  有状态计算   │  Iceberg   │
│             │            │              │  Redis     │
└────────────┴────────────┴──────────────┴────────────┘
```

## 数据接入与链路

实时数仓的接入链路是「Kafka → Flink → 下游存储」。Kafka 按业务分 topic（订单、支付、埋点），分区保证同 key 有序；Flink 消费 Kafka 做实时 ETL，分层流转：ODS 层贴源 topic → DWD 层清洗宽表 topic → DWS 层聚合指标；下游按用途写不同存储——查询写 StarRocks/Doris，明细落地 Iceberg，低延迟结果写 Redis。链路要保证「顺序性、精确一次、可重放」。

```text
链路分层与职责：
1. ODS topic —— 贴源数据，原始格式，保留全量字段
2. DWD topic —— 清洗 + 关联维表后的明细宽表
3. DWS —— 开窗聚合后的指标，写 OLAP/缓存
4. 有序性 —— 同一订单事件进同一 Kafka 分区，保证顺序
5. 精确一次 —— Checkpoint + 幂等 sink，端到端 exactly-once
```

```java
// Flink 消费 Kafka 做实时 ETL
DataStream<String> ods = env.addSource(
    new FlinkKafkaConsumer<>("ods_order", new SimpleStringSchema(), props));

DataStream<OrderEvent> dwd = ods
    .map(json -> parseOrder(json))          // 解析
    .filter(e -> e.orderId != null)          // 过滤脏数据
    .keyBy(OrderEvent::getOrderId)           // 按订单分组
    .process(new OrderStatusProcess());      // 状态流转处理

dwd.addSink(new FlinkKafkaProducer<>("dwd_order", new OrderSchema(), props));
```

## 时间语义与水印

实时计算的关键是 Event Time（事件发生时间）而非处理时间（Processing Time），因为数据会乱序、会延迟。Flink 用 Watermark（水位线）表示「该时间点之前的数据都到了」，Watermark 触发窗口计算。水位线 = 已到达最大事件时间 - 允许延迟时间，用于容忍乱序；水位线推进过慢会导致窗口迟迟不触发，过快则丢弃迟到数据。

```text
时间语义与水印要点：
1. Event Time —— 事件真实发生时间，取自数据字段（如订单时间）
2. Processing Time —— 机器处理时间，乱序时不准确
3. Watermark —— 声明 event time 进度，触发窗口计算
4. 乱序容忍 —— Watermark = maxEventTime - allowedLateness
5. 迟到数据 —— 超过 watermark 的数据走侧输出流（side output）
```

```java
// 指定 Event Time 和水印
DataStream<OrderEvent> withTime = orderStream
    .assignTimestampsAndWatermarks(
        WatermarkStrategy.<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(5))
            .withTimestampAssigner((e, ts) -> e.getEventTime())
    );

// 乱序容忍 5 秒，窗口触发后迟到的数据进侧输出流
OutputTag<OrderEvent> lateTag = new OutputTag<OrderEvent>("late"){};
SingleOutputStreamOperator<OrderEvent> main = withTime
    .keyBy(OrderEvent::getUserId)
    .window(TumblingEventTimeWindows.of(Time.minutes(1)))
    .sideOutputLateData(lateTag)
    .process(new GmvAggregate());
```

## 窗口计算

窗口把无限流切分成有界数据集，是实时聚合的基础。Flink 支持四类窗口：滚动窗口（Tumbling，固定大小不重叠）、滑动窗口（Sliding，固定大小有滑动步长）、会话窗口（Session，按活动间隔动态划分）、全局窗口（Global，全量数据需自定义触发器）。窗口由 Watermark 触发，窗口聚合结果要明确「触发时机、迟到数据处理、结果更新方式」。

```text
窗口类型与选型：
1. 滚动窗口 —— 固定大小不重叠，适合每分钟 GMV
2. 滑动窗口 —— 固定大小有步长，适合近 10 分钟每 1 分钟滑动的实时趋势
3. 会话窗口 —— 按活动间隔动态划分，适合用户访问会话
4. 全局窗口 —— 全量数据，需自定义触发器，适合累计指标
5. 触发 —— 窗口结束 + watermark 越过窗口边界时触发
```

```java
// 滚动窗口：每分钟 GMV
DataStream<GmvResult> gmv = withTime
    .keyBy(OrderEvent::getUserId)
    .window(TumblingEventTimeWindows.of(Time.minutes(1)))
    .aggregate(new AggregateFunction<OrderEvent, Long, Long>() {
        @Override public Long createAccumulator() { return 0L; }
        @Override public Long add(OrderEvent e, Long acc) { return acc + e.getAmount(); }
        @Override public Long getResult(Long acc) { return acc; }
        @Override public Long merge(Long a, Long b) { return a + b; }
    });

// 滑动窗口：近 10 分钟、每 1 分钟滑动的实时趋势
DataStream<Long> trend = withTime
    .keyBy(OrderEvent::getUserId)
    .window(SlidingEventTimeWindows.of(Time.minutes(10), Time.minutes(1)))
    .sum("amount");
```

## 状态管理

State 是 Flink 有状态计算的核心，用于保存跨事件/跨窗口的中间结果（累计 GMV、去重集合、会话信息）。State 分 Keyed State（按 key 隔离）和 Operator State（算子级）；Keyed State 有 ValueState（单值）、ListState（列表）、MapState（键值）、ReducingState/AggregatingState（聚合）四种。State 由 Flink 管理、随 Checkpoint 持久化，故障恢复时从状态重建。

```text
State 类型与用途：
1. ValueState —— 保存单值（累计金额、上次状态）
2. ListState —— 保存列表（待处理的订单、会话事件）
3. MapState —— 保存键值（用户标签 map、去重集合）
4. ReducingState/AggregatingState —— 增量聚合状态
5. Keyed State —— 按 key 隔离，每个 key 独立状态
```

```java
// 用 ValueState 累计用户累计 GMV
public class UserGmvProcess extends KeyedProcessFunction<Long, OrderEvent, Long> {
    private ValueState<Long> totalState;

    @Override public void open(Configuration conf) {
        ValueStateDescriptor<Long> desc =
            new ValueStateDescriptor<>("total", Long.class);
        totalState = getRuntimeContext().getState(desc);
    }

    @Override public void processElement(OrderEvent e, Context ctx, Collector<Long> out)
            throws Exception {
        Long total = totalState.value();
        total = (total == null ? 0 : total) + e.getAmount();
        totalState.update(total);
        out.collect(total);
    }
}
```

## Checkpoint 与容错

Checkpoint 是 Flink 的容错机制：周期性对作业状态做一致性快照（基于 Chandy-Lamport 分布式快照算法），故障时从最近一次成功的 Checkpoint 恢复，保证精确一次（exactly-once）。关键是「Checkpoint 间隔、状态后端、端到端精确一次」——Checkpoint 间隔越短恢复越快但开销越大；状态后端用 RocksDB 支持超大状态；端到端精确一次需 source 可重放（Kafka 偏移量）+ sink 幂等或事务。

```text
Checkpoint 要点：
1. 一致性快照 —— 周期性保存全作业状态，基于 Chandy-Lamport 算法
2. 恢复 —— 故障从最近成功 Checkpoint 恢复，重新消费 Kafka
3. 精确一次 —— source 存偏移量 + sink 幂等/两阶段提交
4. 状态后端 —— RocksDB 支持超大状态，可溢出到磁盘
5. 间隔调优 —— 间隔短恢复快开销大，间隔长恢复慢开销小
```

```java
// 配置 Checkpoint 和状态后端
StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.enableCheckpointing(60_000);                      // 每 60 秒 checkpoint
env.getCheckpointConfig().setCheckpointingMode(
    CheckpointingMode.EXACTLY_ONCE);                  // 精确一次
env.getCheckpointConfig().setMinPauseBetweenCheckpoints(30_000);
env.getCheckpointConfig().setCheckpointTimeout(120_000);
env.setStateBackend(new EmbeddedRocksDBStateBackend()); // RocksDB 状态后端
env.getCheckpointConfig().enableExternalizedCheckpoints(
    CheckpointConfig.ExternalizedCheckpointCleanup.RETAIN_ON_CANCELLATION);
```

## 实时指标计算

实时指标是实时数仓的产出：实时 GMV、实时订单量、实时 UV/PV。计算用「Event Time + 滚动/滑动窗口 + State 聚合」产出分钟级指标，写 StarRocks/Doris 供 OLAP 秒级查询，写 Redis 供大屏低延迟读。关键点：指标口径与离线对齐（同一 GMV 口径）、聚合粒度合理（避免状态无限膨胀）、结果幂等写入（避免重复累加）。

```text
实时指标要点：
1. 实时 GMV —— 滚动窗口聚合已支付订单金额，分钟级刷新
2. 实时订单量 —— 按状态统计下单/支付订单数
3. 实时 UV/PV —— 去重统计（UV 用去重，PV 直接计数）
4. 口径对齐 —— 与离线 GMV/留存口径一致，可对账
5. 幂等写入 —— 结果按「指标 + 时间」主键 upsert，避免重复
```

```java
// 实时 GMV：滚动窗口聚合写 StarRocks
DataStream<GmvResult> gmv = withTime
    .filter(e -> "paid".equals(e.getStatus()))
    .keyBy(e -> e.getDt())
    .window(TumblingEventTimeWindows.of(Time.minutes(1)))
    .aggregate(new GmvAggregate())
    .map(r -> new GmvResult(r.getDt(), r.getGmv()));

gmv.addSink(new StarRocksSink("gmv_minute", "dt,gmv"));  // upsert 写入
```

## 实时维表关联

实时维表关联解决「事实流关联维度」的问题：订单流要关联用户等级、商品类目等维度才能算出带维度的指标。维度数据实时变化（用户升级、商品调价），传统全量维表加载会过期。方案：维度变更通过 CDC 进 Kafka，Flink 用广播流（Broadcast State）把维表广播到所有任务，事实流 connect 广播流做实时关联，维度更新即时生效。

```text
维表关联方案：
1. 全量维表加载 —— 启动时全量加载，维度更新需重启，会过期
2. 实时维表（广播流）—— 维度变更进 Kafka，广播到所有任务，实时生效
3. 外部存储维表 —— 每事件查 Redis/HBase，延迟高但有最新值
4. Broadcast State —— 维表存广播状态，事实流 connect 关联
5. 选型 —— 变化快的维度用广播流，超大维表用外部存储查询
```

```java
// 广播维表 + 事实流实时关联
// 维表流：用户等级变更，广播到所有任务
MapStateDescriptor<String, String> dimDesc =
    new MapStateDescriptor<>("dim_user", String.class, String.class);
BroadcastStream<String> dimBroadcast = dimStream.broadcast(dimDesc);

DataStream<EnrichedOrder> enriched = orderStream
    .keyBy(OrderEvent::getUserId)
    .connect(dimBroadcast)
    .process(new BroadcastProcessFunction<OrderEvent, String, EnrichedOrder>() {
        @Override public void processElement(OrderEvent e, ReadOnlyContext ctx,
                Collector<EnrichedOrder> out) {
            String level = ctx.getBroadcastState(dimDesc).get(e.getUserId());
            out.collect(new EnrichedOrder(e, level));   // 关联维度
        }
        @Override public void processBroadcastElement(String dim, Context ctx,
                Collector<EnrichedOrder> out) {
            ctx.getBroadcastState(dimDesc).put(dim, parseLevel(dim));  // 更新维表
        }
    });
```

## 实时画像

实时画像基于用户实时行为（浏览、点击、下单、支付）秒级更新用户标签（兴趣偏好、消费能力、活跃度、风险等级），写 Redis 供推荐、风控、营销实时读取。实现：Flink 消费埋点流，用 State 维护用户近期行为特征，实时计算标签（如「近 10 分钟高频下单」「高价值用户」），标签变更即写 Redis，供下游实时调用。

```text
实时画像要点：
1. 标签维度 —— 兴趣偏好、消费能力、活跃度、风险等级
2. 实时特征 —— 用 State 维护近 N 分钟行为（滑动窗口/去重）
3. 标签计算 —— 行为触发标签更新，实时写 Redis
4. 应用 —— 实时推荐、实时风控、实时营销触达
5. 存储 —— Redis 存标签，低延迟读
```

```java
// 实时画像：近 10 分钟高频下单用户打「活跃」标签
DataStream<String> profile = behaviorStream
    .keyBy(BehaviorEvent::getUserId)
    .window(SlidingEventTimeWindows.of(Time.minutes(10), Time.minutes(1)))
    .aggregate(new CountAggregate())                     // 近 10 分钟行为数
    .map(cnt -> cnt.getCnt() >= 5 ? "high_active" : "normal");

profile.addSink(new RedisSink("user_profile"));          // 标签写 Redis
```

## 应用场景实战

### 场景一：大促实时 GMV 大屏

```text
1. 大促开始，订单事件实时进 Kafka（ods_order topic）
2. Flink 作业清洗 + 关联维表，写 DWD topic
3. Flink 开滚动窗口（1 分钟）聚合 GMV，写 StarRocks
4. 大屏每 5 秒查询 StarRocks 展示实时 GMV、订单量
5. Checkpoint 保证故障后从断点恢复，不丢不重
```

### 场景二：实时风控拦截

```text
1. 支付事件实时进 Kafka
2. Flink 用 State 维护用户近 10 分钟支付次数、金额
3. 滑动窗口统计触发「高频支付」风险标签
4. 标签实时写 Redis，风控系统读取判断是否拦截
5. 命中风险 → 拦截支付并告警，秒级响应
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 Event Time 而非 Processing Time，乱序数据才能算准
2. Watermark 乱序容忍度按业务最大延迟设置，配合侧输出流兜底迟到数据
3. 指标口径与离线对齐，实时离线可对账，避免口径打架
4. Checkpoint 间隔和状态后端按状态大小调优，超大状态用 RocksDB
5. 维表关联用广播流实时更新，避免维度过期导致关联错误
6. 结果幂等写入（按指标 + 时间主键 upsert），重放不重复累加

### 踩坑记录

```text
坑 1：用 Processing Time 算指标，乱序数据算错
结论：延迟到达的订单被算到错误窗口，实时 GMV 与离线对不上。
原因：用处理时间而非事件时间，数据乱序/延迟导致错位。
解法：用 Event Time + Watermark，按事件时间归属窗口。

坑 2：Watermark 乱序容忍设太小，迟到数据被丢弃
结论：网络抖动导致延迟数据被丢，指标偏小。
原因：forBoundedOutOfOrderness 设太小，迟到数据直接丢弃。
解法：按业务最大延迟设置容忍度，迟到数据走侧输出流补偿。

坑 3：维表全量加载后过期，关联错误维度
结论：用户等级升级后，订单仍关联旧等级，实时画像不准。
原因：维表启动时全量加载，运行中不更新。
解法：维表走 CDC 进 Kafka，广播流实时更新，关联即时生效。

坑 4：State 无限增长，作业内存溢出
结论：去重集合、累计状态不断增长，最终 OOM。
原因：无界 key 的 State 未清理，状态无限膨胀。
解法：用 TTL 设置状态过期时间，定期清理过期状态。

坑 5：sink 不幂等，Checkpoint 恢复后重复累加
结论：故障恢复重放，结果被重复累加，指标翻倍。
原因：sink 无幂等，重放时重复写入。
解法：sink 按主键 upsert（幂等），或两阶段提交保证精确一次。
```
