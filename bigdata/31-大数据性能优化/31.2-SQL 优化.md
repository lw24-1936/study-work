## 概述

SQL 优化是数据工程师最常打交道的调优场景，核心是「让优化器生成更优的执行计划」。优化器依赖统计信息做代价估算，靠规则（谓词下推、分区裁剪、列裁剪）和代价模型（CBO）来选择 Join 顺序与 Join 策略。工程师要做的是写出「优化器友好」的 SQL，并在必要时通过 Hint 干预。

```text
SQL 优化总纲：
1. 读懂执行计划 —— 先 explain 看引擎打算怎么执行，别凭空猜
2. 尽早过滤 —— 谓词下推 + 分区裁剪，把数据量在源头压下去
3. Join 是重点 —— 大表 JOIN 小表走广播/MapJoin，大表 JOIN 大表选对策略
4. 统计信息是地基 —— 统计信息缺失或过旧，优化器只能瞎选
5. CBO 进阶 —— 开 CBO 让代价模型决定 Join 顺序与广播
```

```sql
-- 任何优化动作的第一步：查看执行计划
EXPLAIN SELECT o.order_id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.dt = '2024-08-14';
-- Hive 用 EXPLAIN EXTENDED 看更细；Spark 用 df.explain("cost")
```

## 执行计划

执行计划是优化器把 SQL 翻译成的「物理执行步骤序列」，描述了数据从哪读、经过哪些算子（扫描、过滤、聚合、Join）、以何种顺序和策略执行。读懂执行计划是 SQL 优化的第一能力：能看出是否走了分区裁剪、Join 用了什么策略、是否存在全表扫描或笛卡尔积。不同引擎计划形态不同，但核心元素一致。

```text
执行计划要点：
1. 逻辑计划 vs 物理计划 —— 逻辑计划描述「做什么」，物理计划描述「怎么做」
2. 关键节点 —— Scan（扫描）、Filter（过滤）、Join、Aggregate、Exchange/Shuffle
3. 看三件事 —— 扫了多少数据、Join 策略是什么、有没有多余 Shuffle
4. EXPLAIN 扩展 —— Hive 的 EXTENDED、Spark 的 cost 模式能看到统计与代价
5. 计划不稳定 —— 统计信息变化会改变计划，线上计划漂移要能对比
```

```sql
-- Hive：查看扩展执行计划
EXPLAIN EXTENDED
SELECT /*+ MAPJOIN(u) */ o.order_id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.dt = '2024-08-14';

-- Spark SQL：查看物理计划与代价（在 spark-sql 或代码 explain 中使用）
-- df.explain("cost")  打印包含统计信息的优化后计划
```

## Join 优化

Join 是 SQL 中最昂贵也最需要优化的算子。核心策略分三类：广播 Join（小表整表发到每个节点，无 Shuffle）、Shuffle Join（两边按连接键重分布后归并或哈希连接）、分桶 Join（写入时预分桶，Join 时免 Shuffle）。优化原则是「能广播就广播、能分桶就分桶、避免笛卡尔积、把大表放前小表放后」。

```text
Join 优化要点：
1. 广播 Join —— 小表塞进内存，大表不做 Shuffle，是最快的 Join 方式
2. MapJoin Hint —— Hive 用 /*+ MAPJOIN(t) */，Spark 用 broadcast(t) 强制广播
3. 分桶 Join —— bucket 表按连接键分桶排序，Join 时可直接归并免 Shuffle
4. 笛卡尔积 —— 无条件 Join 或条件失效会产生巨大中间结果，务必避免
5. 倾斜 Join —— 连接键分布不均时热点分区拖垮作业，需加盐或单独处理
```

```sql
-- 方案一：MapJoin 广播小表（Hive）
SELECT /*+ MAPJOIN(u) */ o.order_id, u.name
FROM orders o JOIN users u ON o.user_id = u.id;

-- 方案二：分桶表 Join（写入时预分桶，Join 免 Shuffle）
CREATE TABLE orders_bucket (order_id BIGINT, user_id BIGINT, amount DOUBLE)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 256 BUCKETS;
CREATE TABLE users_bucket (id BIGINT, name STRING)
CLUSTERED BY (id) SORTED BY (id) INTO 256 BUCKETS;
-- 两表桶数一致、按同一键分桶，Join 时可走 Bucket Map Join
SELECT o.order_id, u.name
FROM orders_bucket o JOIN users_bucket u ON o.user_id = u.id;

-- 方案三：避免笛卡尔积（错误示范 -> 正确写法）
-- 错误：条件写错导致笛卡尔积
-- SELECT * FROM orders o JOIN users u ON o.user_id = o.user_id;
-- 正确：连接键两侧各取所需
SELECT * FROM orders o JOIN users u ON o.user_id = u.id;
```

## 分区裁剪

分区裁剪指优化器根据 WHERE 条件中的分区列，只扫描满足条件的分区，跳过无关分区，从而大幅减少扫描数据量。这是数仓查询提速最立竿见影的手段，前提是表按时间等维度做了分区、且过滤条件直接作用在分区列上。一旦分区列被函数包裹或参与运算，裁剪就会失效退化为全表扫描。

```text
分区裁剪要点：
1. 前提 —— 表按 dt/hour 等字段分区，过滤条件直接引用分区列
2. 失效场景 —— 分区列套函数（date(dt)=...）、被运算（dt+1=...）会导致裁剪失败
3. 动态分区 —— 写入时按数据值自动生成分区，但过多分区会拖慢元数据操作
4. 分区粒度 —— 太粗裁剪不彻底，太细产生小文件与元数据压力，需折中
5. 验证 —— explain 里看扫描的分区数量，确认裁剪生效
```

```sql
-- 分区裁剪生效：直接引用分区列
SELECT count(*) FROM orders WHERE dt = '2024-08-14';          -- 只扫 1 个分区

-- 分区裁剪失效：分区列套了函数，退化为全表扫描
SELECT count(*) FROM orders WHERE date(dt) = '2024-08-14';    -- 扫全部分区
-- 改写：把函数移到常量侧
SELECT count(*) FROM orders WHERE dt = date('2024-08-14');

-- 多级分区裁剪：同时裁剪年/月/日
SELECT count(*) FROM orders WHERE year = 2024 AND month = 8 AND day = 14;

-- 动态分区写入（Hive）：按 dt 自动建分区
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;
INSERT OVERWRITE TABLE orders_part PARTITION (dt)
SELECT order_id, user_id, amount, dt FROM orders_stage;
```

## 谓词下推

谓词下推是把过滤条件尽量下沉到数据源（或最靠近扫描的算子）执行，让上层只处理过滤后的少量数据。它减少的不只是计算量，更重要的是减少了 Join 前和 Shuffle 前的数据量。优化器通常会自动下推，但 Join 场景下有讲究：内侧表（inner 表）的谓词可在 Join 前下推，外侧表（outer 表）的谓词在 Join 后过滤才语义正确。

```text
谓词下推要点：
1. 下推收益 —— 在扫描或 Join 前过滤，减少后续算子处理与 Shuffle 的数据量
2. outer join 语义 —— left join 中右表谓词可下推，左表谓词下推会改变结果
3. 常量折叠 —— 表达式能算成常量的先算，如 dt = date('2024-08-14')
4. 存储下推 —— 列式存储可把过滤推到存储层，只读命中的行与列
5. 验证 —— explain 里 Filter 出现在 Scan 之后、Join 之前即为下推成功
```

```sql
-- 谓词下推生效：过滤在 Join 前完成
SELECT o.order_id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.dt = '2024-08-14' AND o.amount > 100;

-- left join 中右表谓词可下推，左表谓词不可下推
-- 正确：右表过滤写在 ON 里可下推
SELECT o.order_id, u.name
FROM orders o LEFT JOIN users u ON o.user_id = u.id AND u.status = 'active';
-- 错误：左表过滤写在 ON 里（写在 ON 会被当作 Join 条件，保留左表所有行）
-- 左表过滤应放 WHERE，保证语义正确
SELECT o.order_id, u.name
FROM orders o LEFT JOIN users u ON o.user_id = u.id
WHERE o.dt = '2024-08-14';
```

## 统计信息

统计信息是优化器做代价估算的「燃料」，包括表的行数、文件大小、每列的最大/最小值、不同值数量（NDV）、空值数、直方图等。统计信息准确，优化器才能正确判断「哪张表该广播、Join 顺序怎么排、分区合并多少」；统计信息缺失或过旧，优化器只能按默认假设拍脑袋，常选出糟糕计划。

```text
统计信息要点：
1. 关键指标 —— 行数、文件大小、列 NDV、max/min、空值率、直方图
2. 缺失后果 —— 行数未知会低估/高估，导致错误广播或错误 Join 顺序
3. 时效性 —— 数据大量变更后统计信息会失真，需定期重新收集
4. 收集方式 —— Hive 用 ANALYZE TABLE，Spark 用 ANALYZE TABLE COMPUTE STATISTICS
5. 列级统计 —— 只收集表级行数不够，Join/过滤依赖列级统计才准确
```

```sql
-- Hive：收集表级与列级统计信息
ANALYZE TABLE orders COMPUTE STATISTICS;                          -- 表级：行数、大小
ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS user_id, dt;  -- 列级：NDV 等

-- Spark：收集统计信息
ANALYZE TABLE orders COMPUTE STATISTICS;
ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS user_id, amount;

-- 查看已收集的统计信息（Hive）
DESC FORMATTED orders;      -- 查看 numRows、totalSize
-- 查看列统计
DESC FORMATTED orders user_id;
```

## CBO

CBO（Cost-Based Optimizer，基于代价的优化器）根据统计信息计算每条候选计划的代价（IO、CPU、网络），从中选出代价最低的执行计划，尤其擅长决策 Join 顺序和是否广播。与之相对的是 RBO（基于规则的优化器），只按固定规则改写。CBO 是 SQL 优化的高级能力，其上限取决于统计信息的准确性。

```text
CBO 要点：
1. 代价模型 —— 用行数、字节数、NDV 等估算各算子代价，选总代价最低的计划
2. Join 重排 —— 多表 Join 时选择更优的连接顺序，而非按 SQL 书写顺序
3. 广播决策 —— 依据统计信息判断哪侧表适合广播，而非硬编码阈值
4. 依赖统计 —— CBO 强依赖统计信息，统计不准则 CBO 反而选错
5. 开关 —— Hive 用 hive.cbo.enable，Spark 用 spark.sql.cbo.enabled
```

```sql
-- Hive：开启 CBO
SET hive.cbo.enable = true;
SET hive.compute.query.using.stats = true;
SET hive.stats.fetch.column.stats = true;    -- 拉取列级统计供 CBO 使用
SET hive.stats.fetch.partition.stats = true;

-- Spark：开启 CBO
-- spark.sql.cbo.enabled=true
-- spark.sql.cbo.joinReorder.enabled=true     -- 允许 Join 顺序重排
-- spark.sql.cbo.joinReorder.dp.star.filter=true

-- 多表 Join：CBO 会重排顺序，选代价最小的执行路径
SELECT o.order_id, u.name, p.product_name
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id
WHERE o.dt = '2024-08-14';
```

## 应用场景实战

### 场景一：一张大表 Join 维表的完整优化

```sql
-- 目标：orders(百亿级，按 dt 分区) JOIN users(千万级维表) 出日报
-- 1. 先看执行计划，确认问题
EXPLAIN SELECT o.user_id, u.name, sum(o.amount)
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.dt = '2024-08-14'
GROUP BY o.user_id, u.name;

-- 2. 收集统计信息，让优化器算准代价
ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS user_id, amount;
ANALYZE TABLE users COMPUTE STATISTICS FOR COLUMNS id, name;

-- 3. 小维表强制 MapJoin（广播），避免大表 Shuffle
SELECT /*+ MAPJOIN(u) */ o.user_id, u.name, sum(o.amount) AS total
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.dt = '2024-08-14'
GROUP BY o.user_id, u.name;

-- 4. 分区裁剪 + 谓词下推同时生效，扫描量降到最低
SELECT /*+ MAPJOIN(u) */ o.user_id, u.name, sum(o.amount) AS total
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.dt = '2024-08-14' AND o.amount > 0
GROUP BY o.user_id, u.name;
```

### 场景二：避免分区裁剪失效的典型改写

```sql
-- 业务需求：查最近 7 天数据，新手常写出导致全表扫描的 SQL
-- 反例：分区列套函数，裁剪失效
SELECT count(*) FROM orders WHERE date(dt) >= date_sub('2024-08-14', 6);

-- 正例：把函数移到常量侧，让 dt 直接参与比较
SELECT count(*) FROM orders WHERE dt >= date_sub('2024-08-14', 6);

-- 反例：分区列参与运算，裁剪失效
SELECT count(*) FROM orders WHERE dt * 1 = 20240814;

-- 正例：等价改写，保留分区裁剪
SELECT count(*) FROM orders WHERE dt = 20240814;

-- 验证裁剪生效：EXPLAIN 中 TableScan 的 partition 数应显著减少
EXPLAIN SELECT count(*) FROM orders WHERE dt >= date_sub('2024-08-14', 6);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优化前先 EXPLAIN，看清扫描量、Join 策略与 Shuffle 数量，再动手改写
2. 大表 JOIN 小表一律走广播/MapJoin，显式加 Hint，不依赖优化器猜测
3. 分区列永远直接参与比较，禁止套函数或运算，保住分区裁剪
4. 定期 ANALYZE TABLE 更新统计信息，数据大变更后立刻重收集
5. 大表多级分区 + 列裁剪，只 SELECT 真正需要的列
6. 开启 CBO 并保证列级统计完整，让优化器做好 Join 重排与广播决策
7. 对连接键分布不均的表做倾斜治理（加盐、热点单独处理、分桶）

```text
SQL 优化口诀：
先看计划再动手，广播小表免 Shuffle。
分区裁剪别套函数，谓词下推写 WHERE。
统计信息是地基，CBO 依赖要收集。
```

### 踩坑记录

```text
坑 1：分区列套函数导致全表扫描
结论：查询时间从秒级涨到分钟级，扫描了全部历史分区。
原因：WHERE 里 date(dt)=... 使优化器无法做分区裁剪。
解法：把函数移到常量侧，保持分区列原样比较：dt = date('2024-08-14')。

坑 2：left join 把左表过滤写在 ON 里
结论：结果集莫名多出大量行，指标对不上。
原因：left join 中 ON 条件只影响匹配不决定左表保留，左表过滤未生效。
解法：左表过滤条件一律写 WHERE，右表过滤可写 ON 以触发下推。

坑 3：统计信息过旧导致错误广播
结论：小表已长成大表，优化器仍广播，Executor 内存被打爆 OOM。
原因：数据量变更后未重新收集统计信息，行数严重失真。
解法：数据大变更后重跑 ANALYZE TABLE，或调小自动广播阈值兜底。

坑 4：笛卡尔积写进 Join 条件没发现
结论：作业产生天文数字的中间结果，运行几小时不结束。
原因：Join 条件写错（如两边都写同一表列），退化为笛卡尔积。
解法：explain 检查 Join 条件，代码评审重点核查 ON 子句两侧列。

坑 5：盲目开 CBO 但统计信息不全，计划反而更差
结论：开启 CBO 后 Join 顺序被改乱，性能不升反降。
原因：列级统计缺失，CBO 用错误代价做决策。
解法：先补齐列级统计信息，再开 CBO，并对比开启前后计划。
```
