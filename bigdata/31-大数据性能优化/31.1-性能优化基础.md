## 概述

大数据性能优化是分层级的系统工程：底层是硬件资源（CPU、内存、IO、网络），上层是运行时行为（GC、序列化）。调优的本质是「先定位瓶颈在哪一层，再对症下药」，而不是盲目加配置。本主题覆盖六个核心维度，是所有上层组件（Spark/Flink/Hive/Kafka）调优的公共底座。

```text
性能优化六维总纲：
1. CPU —— 算力瓶颈：压缩、序列化、哈希、排序等 CPU 密集阶段
2. 内存 —— 容量瓶颈：能否把热数据常驻内存，避免溢写与 OOM
3. IO —— 吞吐瓶颈：数据密集型作业最常见，顺序 IO 与随机 IO 天差地别
4. 网络 —— 搬移瓶颈：Shuffle、跨节点 Join 与数据同步的耗时来源
5. GC —— 停顿瓶颈：JVM 引擎的 Full GC 会 STW 拖垮所有任务线程
6. 序列化 —— 体积瓶颈：决定网络传输量、溢写量与内存占用
```

```shell
# 定位瓶颈的第一步：用系统工具看整体画像
top -b -n 1 | head -20        # CPU 与内存整体占用
uptime                          # load average 判断是否过载
free -h                         # 内存与 swap 使用情况
```

## CPU

CPU 是计算密集型任务的核心瓶颈，衡量指标有 CPU 使用率、load average（平均负载）、上下文切换次数、CPU 亲和性与 NUMA 拓扑。大数据框架的 CPU 密集阶段包括压缩/解压、序列化/反序列化、哈希计算、排序归并、加解密等。CPU 打满不代表「在干活」——可能是频繁上下文切换、锁竞争或空转。

```text
CPU 要点：
1. 使用率 vs 负载 —— 使用率 100% 但 load 高，说明任务排队等待 CPU
2. 上下文切换 —— cs 过高说明线程过多、锁竞争，调度开销吃掉算力
3. 核数与并行度 —— 并行度超过核数只会增加调度开销而非吞吐
4. 压缩是 CPU/IO 的权衡 —— 高压缩比省 IO 但费 CPU（如 gzip vs snappy）
5. NUMA —— 跨 socket 访问内存会变慢，进程尽量绑定本 socket
```

```shell
# 观察 CPU 使用率、负载与上下文切换
uptime                                    # 1/5/15 分钟平均负载，大于核数即过载
mpstat -P ALL 1 3                         # 每核使用率，看是否单核打满
vmstat 1 5                                # cs 列（上下文切换）与 us/sy/wa 分布
nproc                                     # 查看可用核数，用于确定并行度
lscpu | grep -E "Socket|Core|Thread"      # 查看 NUMA 拓扑
```

## 内存

内存决定数据能否常驻内存而避免磁盘溢写，衡量指标有可用内存、页换入换出（swap in/out）、缺页中断、内存带宽。大数据引擎普遍使用堆内 + 堆外混合内存：堆内受 JVM GC 管理，堆外（Direct Memory）用于网络缓冲与页缓存。内存不足的典型表现是频繁溢写磁盘（spill）、缓存被淘汰导致重算、最终 OOM 崩溃。

```text
内存要点：
1. swap 抖动 —— 物理内存不足时频繁换页，性能断崖式下跌，务必关 swap 或调大内存
2. 堆内 vs 堆外 —— 堆外内存不受 GC 管理但需手工释放，网络与直接缓冲走堆外
3. 内存带宽 —— 多核同时访问大内存时带宽会成为隐藏瓶颈
4. 页缓存 —— 操作系统用空闲内存缓存文件，重复读数据可命中页缓存
5. 大数据内存模型 —— 执行内存与存储内存隔离，避免互相挤占
```

```shell
# 观察内存与换页情况
free -h                                   # 可用内存、buff/cache、swap
vmstat 1 5                                # si/so 列：swap 换入换出，非 0 说明内存不足
sar -B 1 5                                # pgpgin/pgpgout 缺页与换页统计
cat /proc/meminfo | grep -E "MemAvailable|SwapTotal"  # 内核视角内存
```

## IO

IO 是数据密集型作业最常见的瓶颈，分磁盘 IO 与文件系统两个层面。衡量指标有 IOPS、吞吐量、await（单次 IO 等待时间）、util（磁盘繁忙度）、顺序读写与随机读写的差异。大数据框架大量依赖顺序读写（列式扫描、日志写入），但 Shuffle 溢写、随机查找会引入随机 IO，成为性能杀手。

```text
IO 要点：
1. 顺序 vs 随机 —— 机械盘顺序读可到百 MB/s，随机读只有几 MB/s，差两个数量级
2. util 与 await —— util 100% 且 await 高，说明磁盘队列拥堵，是真实瓶颈
3. 列式存储 —— 只读需要的列，减少 IO 总量；配合分区裁剪进一步缩小范围
4. 溢写 spill —— 内存不足时算子把数据落盘，产生额外写 IO + 读 IO
5. 小文件 —— 大量小文件会让 namenode 与扫描开销剧增，应合并
```

```shell
# 观察磁盘 IO 与顺序/随机性能差异
iostat -x 1 5                             # %util、await、r/s、w/s 定位磁盘是否打满
df -h                                     # 磁盘空间，满了会直接报错
# 顺序写吞吐测试（会真实写 1GB 文件，谨慎执行）
dd if=/dev/zero of=/tmp/seq_test bs=1M count=1024 oflag=direct 2>&1 | tail -1
rm -f /tmp/seq_test
```

## 网络

网络决定 Shuffle 与数据搬移的耗时，衡量指标有带宽、延迟、丢包率、重传次数、连接数。大数据框架中 Shuffle 阶段是网络密集期：Map 端把中间结果按 key 分区发往各 Reduce 端，跨节点 Join、聚合、数据同步都依赖网络。网络瓶颈常见于网卡打满、跨机架流量过大、TCP 重传导致吞吐骤降。

```text
网络要点：
1. 带宽 vs 延迟 —— 大数据关心吞吐（带宽），流计算关心延迟，两者瓶颈不同
2. 数据本地性 —— 尽量在数据所在节点计算，减少跨节点搬移
3. Shuffle 流量 —— 压缩 shuffle 数据可显著减少网络传输量
4. 重传 —— TCP 重传率高于 1% 说明链路质量差，吞吐会大幅下降
5. 机架感知 —— 跨机架流量比机架内慢且贵，副本与调度要考虑机架拓扑
```

```shell
# 观察网络吞吐、丢包与重传
sar -n DEV 1 5                            # rxkB/s、txkB/s 网卡吞吐
ethtool eth0 | grep -E "Speed|Duplex"     # 网卡协商速率
netstat -s | grep -iE "retransmit|segments"  # TCP 重传统计
# 两点间带宽测试（iperf3 需两侧安装，服务端 iperf3 -s）
iperf3 -c 192.168.1.10 -t 5               # 客户端打 5 秒测带宽
```

## GC

GC 是 JVM 类大数据引擎（Spark、Flink、Hadoop、Hive）最常见的卡顿源，Full GC 会 Stop-The-World 暂停所有应用线程，导致任务卡顿、超时甚至被 YARN 判定失联而杀死。衡量指标有 GC 频率、停顿时间、堆占用、各分代使用率。调优围绕堆大小、分代比例、选择合适收集器（现代 JVM 默认 G1）展开。

```text
GC 要点：
1. STW 停顿 —— Full GC 期间所有线程暂停，是性能抖动与超时的元凶
2. 堆大小 —— 堆过小频繁 GC，堆过大单次停顿时间长，需折中
3. 分代 —— 年轻代放短命对象，老年代放长命对象，比例失衡会加速 Full GC
4. G1 收集器 —— 现代默认选择，可设停顿目标 -XX:MaxGCPauseMillis
5. 观察指标 —— GC 时间占比超过 10% 需要警惕，超过 20% 必须调优
```

```shell
# 观察 JVM 堆与 GC 情况（PID 为运行中的 Java 进程号）
jps                                       # 列出 Java 进程
jstat -gcutil 12345 1000 10               # 各分代使用率、YGC/FGC 次数与耗时
jmap -heap 12345 | head -20               # 堆配置概览

# JVM 常用 GC 参数（写入启动脚本）
# -Xms4g -Xmx4g                           堆初始/最大值，两者相等避免动态扩容
# -XX:+UseG1GC -XX:MaxGCPauseMillis=200   G1 收集器 + 200ms 停顿目标
# -Xlog:gc*:file=/tmp/gc.log:time,uptime  打印 GC 日志用于离线分析
```

## 序列化

序列化决定网络传输量、磁盘溢写量与内存占用，是把内存对象变成可传输字节流的过程。衡量指标有序列化后体积、序列化/反序列化耗时。常见格式：Java 原生（体积大、慢）、Kryo（快但需注册）、Protobuf（跨语言、紧凑、需定义 schema）、Avro（带 schema、适合存储）、JSON（可读但最臃肿）。大数据框架在 Shuffle 与持久化阶段大量依赖序列化。

```text
序列化要点：
1. 体积 vs 速度 —— Java 序列化最慢最臃肿，Kryo 比其快数倍、体积小一半以上
2. Schema 进化 —— Protobuf/Avro 支持前后兼容，适合跨系统长期存储
3. 注册类 —— Kryo 不注册类会退化到慢速路径，务必 register 自定义类型
4. 闭包序列化 —— 别在算子里捕获大集合，改为广播变量只序列化一份
5. 序列化是 CPU/网络/IO 的交汇点，格式选择直接影响 Shuffle 成本
```

```java
import java.io.*;
import java.util.ArrayList;
import java.util.List;

// 对比 Java 原生序列化与更紧凑的定长二进制写入
public class SerializationDemo {
    static class Order implements Serializable {
        long id; double amount;
        Order(long id, double amount) { this.id = id; this.amount = amount; }
    }

    public static void main(String[] args) throws Exception {
        List<Order> orders = new ArrayList<>();
        for (long i = 0; i < 100000; i++) orders.add(new Order(i, i * 1.5));

        // Java 原生序列化：体积大，含类描述等元数据
        ByteArrayOutputStream bos = new ByteArrayOutputStream();
        ObjectOutputStream oos = new ObjectOutputStream(bos);
        oos.writeObject(orders); oos.close();
        System.out.println("Java 序列化体积: " + bos.size() + " 字节");

        // 定长二进制写入：每条记录固定 16 字节，无额外元数据
        ByteArrayOutputStream bin = new ByteArrayOutputStream();
        DataOutputStream dos = new DataOutputStream(bin);
        for (Order o : orders) { dos.writeLong(o.id); dos.writeDouble(o.amount); }
        dos.close();
        System.out.println("二进制序列化体积: " + bin.size() + " 字节");
    }
}
```

## 应用场景实战

### 场景一：诊断一台慢 Worker 的性能瓶颈

```shell
#!/bin/bash
# 综合诊断脚本：一次性输出 CPU / 内存 / IO / 网络 / GC 关键指标
echo "=== 1. CPU 负载 ==="
uptime
echo "=== 2. 内存与 swap ==="
free -h
echo "=== 3. 磁盘 IO（1 次采样）==="
iostat -x 1 1 | tail -5
echo "=== 4. 网络吞吐（2 秒采样）==="
sar -n DEV 1 2 | tail -3
echo "=== 5. Java 进程 GC ==="
JVM_PID=$(jps | grep -E "Executor|TaskManager|Driver" | head -1 | awk '{print $1}')
if [ -n "$JVM_PID" ]; then
  jstat -gcutil "$JVM_PID" 1000 1
else
  echo "未找到 Java 计算进程"
fi
echo "=== 诊断结论指引 ==="
echo "load 高 + CPU 打满 -> CPU 瓶颈；si/so 非 0 -> 内存不足；%util 100 -> IO 瓶颈；GC 占比高 -> 调 GC"
```

### 场景二：为日志数据选择序列化格式

```java
// 选型决策：跨系统长期存储用 Protobuf/Avro，Shuffle 内部用 Kryo
// 这里演示 Kryo 风格的「注册 + 快速序列化」思路（以手写紧凑编码近似）
import java.io.*;

public class FormatChoice {
    // 模拟：同一份数据用不同格式估算体积，指导选型
    public static void main(String[] args) {
        long records = 10_000_000L;         // 一千万条
        long jsonPerRec = 180;              // JSON 一条约 180 字节（含字段名与引号）
        long protobufPerRec = 40;           // Protobuf 一条约 40 字节（定长编码）
        System.out.printf("JSON 总量: %.1f GB%n", records * jsonPerRec / 1024.0 / 1024 / 1024);
        System.out.printf("Protobuf 总量: %.1f GB%n", records * protobufPerRec / 1024.0 / 1024 / 1024);
        System.out.println("结论：高频传输/落盘用二进制格式，可减少 4 倍以上网络与存储开销");
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 调优前先定位瓶颈层（CPU/内存/IO/网络/GC），用 `top`+`iostat`+`vmstat` 三件套建立基线，别凭感觉加参数
2. 生产 JVM 引擎统一开启 GC 日志，长期留存用于离线分析停顿原因
3. Shuffle 与持久化阶段优先用紧凑序列化（Kryo/二进制），别用 Java 原生序列化
4. 关闭 swap 或调小 swappiness，避免大数据进程被换页拖垮
5. 压缩选型做权衡：吞吐优先用 snappy/lz4（快、CPU 省），存储优先用 zstd/gzip（压缩比高）
6. 数据本地性优先调度，把计算推到数据所在节点，减少网络搬移
7. 定期检查小文件、磁盘 util 与网络重传，把隐患消灭在爆发之前

```text
性能优化口诀：
先观测、后动手；找瓶颈、再下药。
CPU 满看切换，内存紧看 swap，IO 慢看 util，网络堵看重传，GC 卡看日志。
```

### 踩坑记录

```text
坑 1：load average 高就断定 CPU 瓶颈
结论：误判瓶颈层，加了 CPU 资源依然慢。
原因：load 高可能是 IO 等待（wa）或不可中断睡眠导致的，不一定是算力不足。
解法：结合 vmstat 看 wa（IO 等待）与 cs（上下文切换），再决定加 CPU 还是优化 IO。

坑 2：没关 swap，内存一紧作业集体变慢
结论：内存吃紧时进程被换页，吞吐断崖式下降且难以复现。
原因：Linux 默认 swappiness 较高，会主动把内存页换出到磁盘。
解法：大数据节点关闭 swap 或设置 vm.swappiness=1，保证热数据常驻内存。

坑 3：gzip 压缩换取更小体积却拖慢全链路
结论：压缩比高了，但 CPU 打满、Shuffle 变慢，整体反而更差。
原因：gzip 压缩 CPU 开销大且不支持切分，压缩/解压成为新瓶颈。
解法：吞吐敏感场景改用 snappy/lz4，存储归档场景才考虑 zstd/gzip。

坑 4：忽略 GC 日志，Full GC 抖动查无可查
结论：作业周期性卡顿，无日志可分析，只能盲猜。
原因：未开启 GC 日志，停顿发生时的堆状态与触发原因无法还原。
解法：上线即开启 GC 日志并保留，用 GCViewer 等工具离线分析停顿曲线。

坑 5：闭包里捕获大集合，序列化体积爆炸
结论：每个 Task 都序列化一份完整大集合，网络与内存开销成倍放大。
原因：闭包捕获的对象会随任务序列化分发到每个 Executor。
解法：把大只读集合改为广播变量，集群内只传输一份。
```
