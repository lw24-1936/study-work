## 概述

Spark 优化围绕「减少数据搬运、减少磁盘与网络 IO、减少内存浪费」展开。慢作业几乎都源于三类问题：分区不合理导致并行度失衡、Shuffle 过多或过重、数据倾斜让个别 Task 拖垮全局。现代 Spark（3.x）还提供了 AQE 自适应查询执行，能根据运行时统计动态优化分区与 Join。本主题覆盖分区、Shuffle、Join 策略、Cache、AQE、Skew 与 GC 七大抓手。

```text
Spark 优化总纲：
1. 分区 —— 分区数匹配核数（1~3 倍），避免空转与碎片
2. Shuffle —— 减少 Shuffle 次数、压缩 shuffle 数据、治理倾斜
3. Join —— 能广播就广播，能分桶就分桶，大表走 SortMerge
4. Cache —— 复用中间结果，用序列化缓存减少内存与 GC 压力
5. AQE —— 打开自适应执行，动态合并分区、拆分倾斜、优化 Join
6. GC —— 统一内存管理，调高执行内存占比，降低 Full GC
```

```scala
import org.apache.spark.sql.SparkSession

val spark = SparkSession.builder()
  .appName("SparkOpt")
  .config("spark.sql.adaptive.enabled", "true")       // AQE 总开关
  .config("spark.sql.shuffle.partitions", "400")      // 按核数调整
  .getOrCreate()

// 观察作业执行细节的两个入口：物理计划 + Shuffle 统计
df.explain("cost")            // 看物理计划与统计
// Spark UI -> SQL/Stage 页看 Shuffle 读写量、Task 倾斜、GC 时间
```

## 分区

分区是 Spark 并行与调度的基本单位，一个分区对应一个 Task。分区数太少，集群核数闲置、单任务数据量过大易 OOM；分区数太多，任务调度开销大、产生大量小文件。经验值是「分区数约为总核数的 1~3 倍」。分区数的来源：读文件时由块数决定，Shuffle 后由 `spark.sql.shuffle.partitions`（默认 200）决定，也决定了输出文件数。

```text
分区要点：
1. RDD 分区 —— 读文件按块切分，可 repartition/coalesce 调整
2. DataFrame 分区 —— 无 Shuffle 沿用上游，Shuffle 后由 shuffle.partitions 决定
3. 默认 200 —— 对大数据量太小、对中小数据量偏大，务必按集群规模调整
4. 分区与倾斜 —— 分区越细，单 key 倾斜越易暴露，需配合倾斜治理
5. 分区决定文件数 —— 写盘前用 repartition/coalesce 控制小文件
```

```scala
// 查看与调整分区数
val df = spark.range(0, 1000000L)
println("当前分区数: " + df.rdd.getNumPartitions)

// 增大并行度：触发一次全量 Shuffle
val expanded = df.repartition(400)

// 减少分区、尽量不 Shuffle：相邻分区原地合并（写盘前收敛小文件常用）
val shrunk = df.coalesce(100)

// 按列重分区：打散倾斜 key，把同一 key 数据放到同一分区
val byUser = df.repartition(df("id"))
```

## Shuffle

Shuffle 是 Spark 中最昂贵的操作，它把数据按 key 跨节点重新分区，涉及 Map 端溢写排序、网络传输、Reduce 端合并，产生大量磁盘与网络 IO。凡是宽依赖（groupBy、reduceByKey、join、distinct、repartition）都会触发 Shuffle。优化的核心是「减少 Shuffle 次数、缩小 Shuffle 数据量、压缩 Shuffle 数据」。

```text
Shuffle 要点：
1. 触发条件 —— groupBy/reduceByKey/join/distinct/repartition 等宽依赖
2. 成本构成 —— Map 端排序溢写 + 网络传输 + Reduce 端合并，是磁盘与网络双重 IO
3. 减少次数 —— 用 reduceByKey 代替 groupByKey（先局部聚合）、合并多个聚合
4. 压缩 —— spark.shuffle.compress=true 压缩 Map 输出，减少网络与磁盘
5. 溢写调优 —— spark.shuffle.spill.compress 压缩溢写文件，减少磁盘 IO
```

```scala
// 减少 Shuffle：reduceByKey 先 map 端局部聚合，优于 groupByKey
val rdd = spark.sparkContext.parallelize(Seq(("a", 1), ("b", 2), ("a", 3)))
val byReduce = rdd.reduceByKey(_ + _)      // map 端先聚合，Shuffle 数据小
val byGroup  = rdd.groupByKey()            // 全量 Shuffle，不推荐

// Shuffle 相关配置
spark.conf.set("spark.shuffle.compress", "true")          // 压缩 Map 输出
spark.conf.set("spark.shuffle.spill.compress", "true")    // 压缩溢写文件
spark.conf.set("spark.shuffle.file.buffer", "64k")        // 写盘缓冲

// 用 AQE 让 Shuffle 后的分区数动态收敛，避免固定 200 浪费
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
```

## Join 策略

Spark 的 Join 策略决定两张表如何关联，直接影响性能。主要有三种：Broadcast Hash Join（小表广播到每个 Executor，无 Shuffle）、SortMerge Join（两边排序后按 key 归并，大表默认）、Shuffled Hash Join（按 key Shuffle 后建哈希表，省排序）。选择逻辑：能广播就广播，不能广播走 SortMerge，分桶表可免 Shuffle。

```text
Join 策略要点：
1. BroadcastHashJoin —— 小表整表进内存，大表 map 端哈希查找，最快
2. SortMergeJoin —— 大表默认，Shuffle + 双端排序 + 归并，代价高
3. ShuffledHashJoin —— 省去排序但哈希表需全驻内存，默认关闭
4. 广播阈值 —— spark.sql.autoBroadcastJoinThreshold 默认 10MB，可上调
5. 分桶 Join —— bucketBy 预分桶，Join 时免 Shuffle 直接归并
```

```scala
import org.apache.spark.sql.functions.broadcast

val fact = spark.read.parquet("/warehouse/fact_orders")   // 大表
val dim  = spark.read.parquet("/warehouse/dim_users")     // 小维表

// 自动广播：小表 < 阈值时优化器自动选 BroadcastHashJoin
val auto = fact.join(dim, "user_id")

// 显式强制广播：即使稍大于阈值也走广播
val forced = fact.join(broadcast(dim), "user_id")

// 确认物理计划
forced.explain()
// 输出应含 BroadcastHashJoin [user_id]，而非 SortMergeJoin

// 分桶表 Join 免 Shuffle
fact.write.bucketBy(200, "user_id").sortBy("user_id").saveAsTable("fact_bucket")
// 两表同键同桶数 Join 时可直接归并，跳过 Shuffle
```

## Cache 缓存

Cache（缓存）把中间结果或频繁复用的数据集物化到内存或磁盘，避免重复计算。当一个 DataFrame 被多个下游算子引用，或迭代算法需要反复访问同一数据时，缓存能避免重算。缓存级别从 MEMORY_ONLY 到 MEMORY_AND_DISK_SER，序列化缓存（SER）能显著减少内存占用与 GC 压力。用后要 unpersist 释放。

```text
Cache 要点：
1. 使用时机 —— 同一数据集被多次引用、迭代计算、或昂贵转换的结果
2. 缓存级别 —— MEMORY_ONLY 快但占内存，MEMORY_AND_DISK_SER 省内存抗 GC
3. 序列化缓存 —— 对象转二进制存储，内存占用降数倍，GC 压力大减
4. 惰性求值 —— cache 本身不触发，需后续 action（count）才真正物化
5. 及时释放 —— 用完 unpersist，避免占着 Executor 内存挤占执行内存
```

```scala
import org.apache.spark.storage.StorageLevel

val cleaned = spark.read.parquet("/warehouse/events")
  .filter("amount > 0")

// 复用中间结果：序列化缓存，减少对象数量与 GC 压力
cleaned.persist(StorageLevel.MEMORY_AND_DISK_SER)
cleaned.count()                     // 触发缓存物化

// 被多个分支复用，不会重复计算
val byEvent = cleaned.groupBy("event").count()
val byUser  = cleaned.groupBy("user_id").count()

// 用完释放内存
cleaned.unpersist()

// 缓存级别选择
val df2 = spark.range(0, 1000000L)
df2.cache()                                  // 等价 MEMORY_AND_DISK
df2.persist(StorageLevel.MEMORY_ONLY)        // 只内存，放不下就重算
df2.persist(StorageLevel.DISK_ONLY)          // 只磁盘
```

## AQE 自适应查询执行

AQE（Adaptive Query Execution）是 Spark 3.x 的核心优化，它在 Shuffle 完成后根据实际统计信息动态调整执行计划，解决「静态计划无法预知运行时数据分布」的难题。三大能力：动态合并 Shuffle 分区（解决分区过多/过少）、动态切换 Join 策略（运行时发现可广播则转广播）、动态拆分倾斜分区（自动治理数据倾斜）。

```text
AQE 要点：
1. 动态合并分区 —— 把过多的小分区合并，减少 Task 数与调度开销
2. 动态切换 Join —— 运行时统计发现一侧变小，自动从 SortMerge 转广播
3. 动态倾斜拆分 —— 检测到倾斜分区自动拆成多份，是倾斜治理的兜底
4. 总开关 —— spark.sql.adaptive.enabled 默认 true（Spark 3.2+）
5. 前提 —— 统计信息实时采集，Shuffle 后自动重优化，无需人工干预
```

```scala
// AQE 相关配置
spark.conf.set("spark.sql.adaptive.enabled", "true")                       // 总开关
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")    // 动态合并分区
spark.conf.set("spark.sql.adaptive.coalescePartitions.minPartitionNum", "1")
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "64MB")  // 目标分区大小

// 动态切换 Join 策略
spark.conf.set("spark.sql.adaptive.localShuffleReader.enabled", "true")
spark.conf.set("spark.sql.adaptive.autoBroadcastJoinThreshold", "20MB")

// 动态倾斜拆分
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256MB")

// AQE 生效后，物理计划会显示 AdaptiveSparkPlan 节点
df.explain()
```

## Skew 数据倾斜

数据倾斜指某个或某几个 key/分区的数据量远超其他分区，导致这些分区的 Task 成为瓶颈，其余 Task 早早完成空等，整条作业耗时被拖到最长任务。倾斜是 Spark 作业变慢的头号原因。治理手段有：加盐打散（key 加随机前缀二次聚合）、广播小表消除 Shuffle、AQE 自动拆分、热点 key 单独处理等。

```text
Skew 治理要点：
1. 定位 —— Spark UI 看 Stage 内各 Task 数据量与耗时是否严重不均
2. 加盐打散 —— 倾斜 key 加 0~N 随机前缀，聚合/Join 后去盐二次聚合
3. 广播消除 —— 小表倾斜改 broadcast join，从根上消除 Shuffle 倾斜
4. AQE 兜底 —— 开启 skewJoin 自动拆分倾斜分区
5. 热点分离 —— 把热点 key 单独拎出处理，非热点走常规路径
```

```scala
import org.apache.spark.sql.functions._

// 方案一：加盐打散解决聚合倾斜
val N = 64
val salted = df.withColumn("salt", (rand() * N).cast("int"))
  .groupBy("salt", "user_id").agg(sum("amount").as("partial"))
  .groupBy("user_id").agg(sum("partial").as("total"))

// 方案二：AQE 自动倾斜 Join 拆分（Spark 3.x 兜底方案）
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")

// 方案三：热点 key 单独处理 + 非热点广播 join
import spark.implicits._
val hotKeys = List(10001, 10002)
val hot = df.filter($"user_id".isin(hotKeys: _*))
val normal = df.filter(!$"user_id".isin(hotKeys: _*))
// 非热点正常广播 join，热点单独加盐处理
val normalJoined = normal.join(broadcast(dimDF), "user_id")
val hotJoined = hot.withColumn("salt", (rand() * N).cast("int"))
  .join(broadcast(dimDF), "user_id")   // 热点加盐后打散
```

## GC 垃圾回收

GC 是 Spark 内存调优的隐形杀手：Executor 频繁 Full GC 会暂停所有任务线程，导致作业卡顿、超时甚至 OOM。调优分两块：内存层面用统一内存管理（`spark.memory.fraction` 划分统一内存占堆比例，`spark.memory.storageFraction` 划分存储与执行比例）；序列化层面用序列化缓存减少对象数量。目标是提高执行内存占比、降低对象数。

```text
GC 调优要点：
1. 执行内存不足 -> 频繁溢写磁盘 -> 慢；存储内存不足 -> 缓存淘汰 -> 重算
2. spark.memory.fraction 默认 0.6，留 40% 堆给对象与框架开销
3. spark.memory.storageFraction 默认 0.5，存储与执行各半，可调小给执行更多
4. 序列化缓存 MEMORY_AND_DISK_SER 大幅减少对象数与 GC 压力
5. Spark UI Executor 页看 GC Time 占比，>10% 要警惕
```

```scala
import org.apache.spark.storage.StorageLevel

// 内存调优配置
spark.conf.set("spark.memory.fraction", "0.7")          // 统一内存占堆比例
spark.conf.set("spark.memory.storageFraction", "0.4")   // 存储占比调小，给执行更多

// 用序列化缓存减少对象数量，降低 GC 压力
val cached = df.persist(StorageLevel.MEMORY_AND_DISK_SER)
cached.count()

// 大数据量中间结果落盘并序列化
val processed = df.mapPartitions { it => it }.persist(StorageLevel.MEMORY_AND_DISK_SER)

// JVM 层面 GC 参数（写入 spark.executor.extraJavaOptions）
// -XX:+UseG1GC -XX:MaxGCPauseMillis=200
spark.conf.set("spark.executor.extraJavaOptions",
  "-XX:+UseG1GC -XX:MaxGCPauseMillis=200")
```

## 应用场景实战

### 场景一：大表 Join 维表 + 倾斜治理全流程

```scala
import org.apache.spark.sql.SparkSession
import org.apache.spark.sql.functions._

val spark = SparkSession.builder()
  .appName("JoinWithSkew")
  .config("spark.sql.adaptive.enabled", "true")
  .config("spark.sql.adaptive.coalescePartitions.enabled", "true")
  .config("spark.sql.adaptive.skewJoin.enabled", "true")
  .config("spark.sql.autoBroadcastJoinThreshold", "104857600") // 100MB 内广播
  .getOrCreate()

// 事实表（大）与维表（小，80MB）：直接广播，消除 Shuffle
val fact = spark.read.parquet("/warehouse/fact_orders")
val dim  = spark.read.parquet("/warehouse/dim_users")
val enriched = fact.join(broadcast(dim), Seq("user_id"), "left")

// 聚合时有热点用户：加盐打散 + 二次聚合
val N = 64
val agg = enriched
  .withColumn("salt", (rand() * N).cast("int"))
  .groupBy("salt", "user_id").agg(sum("amount").as("partial_sum"))
  .groupBy("user_id").agg(sum("partial_sum").as("total_amount"))

// 写盘前收敛分区，控制小文件
agg.coalesce(50).write.mode("overwrite").parquet("/warehouse/user_totals")
```

### 场景二：AQE + Cache 优化多分支 ETL

```scala
import org.apache.spark.sql.functions._
import org.apache.spark.storage.StorageLevel

// 一条典型 ETL：读取 -> 过滤 -> 缓存复用 -> 多分支聚合 -> 写入
val raw = spark.read.option("header", "true").csv("/data/raw/events")
  .filter($"dt".between("2024-08-01", "2024-08-14"))   // 尽早过滤（谓词下推）
  .select("user_id", "event", "amount", "dt")           // 列裁剪

// 中间结果被多分支复用，用序列化缓存
val cleaned = raw.filter($"amount".isNotNull && $"amount" > 0)
  .persist(StorageLevel.MEMORY_AND_DISK_SER)
cleaned.count()

// 分支一：按事件聚合
val byEvent = cleaned.groupBy("event").agg(sum("amount").as("total"))
// 分支二：按用户聚合（复用 cleaned，不重算）
val byUser = cleaned.groupBy("user_id", "dt").agg(count("*").as("cnt"))

// AQE 会在 Shuffle 后动态合并分区，写盘前无需手动 coalesce
byUser.write.mode("overwrite").partitionBy("dt").parquet("/warehouse/events_agg")

cleaned.unpersist()   // 释放缓存
```

## 最佳实践与踩坑记录

### 最佳实践

1. 打开 AQE（`spark.sql.adaptive.enabled=true`），让动态分区合并与倾斜拆分自动生效
2. 大表 JOIN 小表一律广播，阈值按集群内存上调到 100MB 级
3. `spark.sql.shuffle.partitions` 按「总核数 1~3 倍」设置，别用默认 200 硬扛
4. 尽早 filter 与 select 列裁剪，把数据量在源头压下去
5. 复用的中间结果用 MEMORY_AND_DISK_SER 序列化缓存，用完 unpersist
6. 用 reduceByKey 代替 groupByKey，map 端先局部聚合减少 Shuffle
7. 数据倾斜优先广播消除，其次加盐打散，最后 AQE 倾斜拆分兜底

```text
Spark 优化口诀：
分区匹配核数，Shuffle 能省则省。
小表广播免搬移，中间结果序列化缓存。
AQE 开启做兜底，倾斜加盐二次聚合。
```

### 踩坑记录

```text
坑 1：默认 shuffle.partitions=200 导致并行度不足
结论：大集群核数上百，作业只用 200 个 Task，大量核闲置、单 Task 数据过大。
原因：默认分区数远小于实际核数，未按集群规模调整。
解法：按总核数 1~3 倍设置 spark.sql.shuffle.partitions。

坑 2：groupByKey 全量 Shuffle 拖慢作业
结论：聚合作业 Shuffle 数据量巨大，网络与磁盘 IO 打满。
原因：groupByKey 不做 map 端预聚合，所有数据原样 Shuffle。
解法：改用 reduceByKey/combineByKey 先局部聚合，减少 Shuffle 数据量。

坑 3：缓存级别选 MEMORY_ONLY，内存不足频繁重算
结论：缓存被淘汰后反复重算，作业越跑越慢。
原因：MEMORY_ONLY 放不下就丢弃缓存，下游每次触发重算。
解法：改用 MEMORY_AND_DISK_SER，放不下的部分溢写磁盘，避免重算。

坑 4：忽略 GC 导致作业周期性卡顿
结论：Executor 频繁 Full GC，任务长时间无进展甚至超时被杀。
原因：执行内存不足 + 对象过多，堆被打满触发 Full GC。
解法：调大 spark.memory.fraction，用序列化缓存，设 G1 停顿目标。

坑 5：加盐打散后忘记二次聚合，结果翻倍
结论：聚合结果重复计数，指标错误。
原因：加盐把同一 key 拆成多组，只聚到盐粒度未去盐再聚合。
解法：加盐 -> 局部聚合 -> 去盐二次聚合，两步缺一不可。
```
