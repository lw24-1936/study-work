## 概述

Kafka 的高吞吐能力不是靠单条消息的极致低延迟，而是靠「顺序写盘 + 页缓存 + 批量 + 零拷贝」这一整套组合拳。优化 Kafka 必须同时从 Producer、Broker、Consumer 三端入手，任何一端成为瓶颈都会拖垮整体。本章围绕批量、压缩、分区、Broker IO、页缓存五个核心维度，给出可落地的参数与代码。

```text
Kafka 优化核心公式
吞吐 ↑ = 批量(batch) ↑ × 压缩(compression) ↑ × 分区(partition) ↑
延迟 ↓ = 批量↓、压缩强度↓、分区等待↓
关键：吞吐与延迟是跷跷板，需按业务 SLA 取舍
```

## Batch 批量

批量的本质是用「攒一小会儿」换取「每次网络往返和磁盘刷写摊薄到更多条消息」。Producer 端通过 `batch.size` 与 `linger.ms` 控制攒批，Consumer 端通过 `fetch.min.bytes` 与 `fetch.max.wait.ms` 控制一次拉取的量。批量越大，单条消息的固定开销越低，但端到端延迟越高。

```text
Producer 攒批触发条件（满足其一即发送）
1. 当前批次大小达到 batch.size
2. 自批次创建起等待达到 linger.ms
3. 达到 max.request.size 或手动 flush
Consumer 攒批
fetch.min.bytes: 攒够多少字节才返回
fetch.max.wait.ms: 最多等多久必须返回
```

```java
import org.apache.kafka.clients.producer.*;
import java.util.Properties;

public class BatchProducer {
    public static void main(String[] args) throws Exception {
        Properties p = new Properties();
        p.put("bootstrap.servers", "kafka1:9092,kafka2:9092");
        p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        // 关键批量参数
        p.put("batch.size", 65536);        // 64KB，单批次上限
        p.put("linger.ms", 5);             // 最多等 5ms 攒批
        p.put("buffer.memory", 67108864);  // 发送缓冲 64MB
        p.put("compression.type", "lz4");  // 配合压缩降低体积

        Producer<String, String> producer = new KafkaProducer<>(p);
        for (int i = 0; i < 100000; i++) {
            producer.send(new ProducerRecord<>("orders", "key-" + i, "value-" + i),
                    (meta, e) -> { if (e != null) e.printStackTrace(); });
        }
        producer.flush();
        producer.close();
    }
}
```

```text
参数选择经验
linger.ms：日志/埋点类可 10~50ms，交易类 0~1ms
batch.size：默认 16KB，高吞吐场景可 64KB~256KB
buffer.memory：需 > batch.size × 并发 partition 数，否则阻塞
```

## Compression 压缩

压缩用 CPU 换网络与磁盘。Kafka 支持 gzip、snappy、lz4、zstd 四种算法：lz4 是吞吐与 CPU 的均衡之选，zstd 压缩比最高但 CPU 略贵，gzip 压缩比高但 CPU 最贵，snappy 速度快但压缩比一般。推荐 `compression.type=producer` 实现「端到端压缩」：消息在 Producer 端压一次，Broker 原样落盘、Consumer 端解压，避免 Broker 反复解压再压缩的浪费。

```text
四种压缩算法对比（相对值）
算法    压缩比    CPU 开销   吞吐    适用
gzip    高       高         中      磁盘/带宽紧张
snappy  低       低         高      CPU 敏感
lz4     中       低         最高    默认推荐
zstd    最高     中         高      长期存储/跨机房
```

```java
Properties p = new Properties();
p.put("bootstrap.servers", "kafka1:9092");
p.put("compression.type", "producer"); // 端到端压缩，保留 Producer 的压缩
// 或显式指定：p.put("compression.type", "zstd");
```

```bash
# 修改 Broker 端默认压缩策略（新主题默认值）
kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type brokers --entity-default \
  --alter --add-config compression.type=producer

# 查看某主题压缩相关配置
kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name orders --describe
```

```text
端到端压缩（compression.type=producer）的价值
1. 只在 Producer 压一次、Consumer 解一次，无中间反复
2. Broker 落盘体积 = 网络传输体积，节省磁盘与复制带宽
3. 前提：不同 Producer 可混用不同算法，Broker 原样透传
```

## Partition 分区

分区是 Kafka 并行度与扩展性的基本单位：一个分区同一时刻只能被一个 Consumer 实例消费，写入吞吐也随分区数线性扩展。分区设计决定了两件事——数据是否均衡（Key 路由）与消费者能否充分并行。分区的代价是：分区越多，Broker 上打开的文件句柄越多、Leader 选举与副本同步开销越大、端到端延迟越高。

```text
分区设计三原则
1. 并行度：分区数 >= 消费者并发实例数
2. 均衡度：Key 设计要让哈希均匀，避免热点分区
3. 有序性：只保证「单分区内有序」，跨分区无序
扩容注意：分区只增不减，扩分区会破坏按 Key 的局部有序
```

```java
import org.apache.kafka.clients.producer.Partitioner;
import org.apache.kafka.common.Cluster;

// 自定义分区器：订单按 user_id 哈希，保证同一用户进同一分区
public class UserIdPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        int partitions = cluster.partitionCountForTopic(topic);
        if (key == null) return 0;
        return Math.abs(key.toString().hashCode()) % partitions;
    }
    @Override public void close() {}
    @Override public void configure(java.util.Map<String, ?> configs) {}
}
```

```bash
# 扩容分区（Kafka 3.x 可用 --alter）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic orders --partitions 12

# 查看分区分布与副本（识别热点分区）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic orders
```

```text
分区数规划经验值
单分区吞吐约 1~5 MB/s（视硬件），先测再定
目标分区数 = 峰值吞吐 / 单分区吞吐，并预留 20% 余量
分区数过万的代价：文件句柄、选举风暴、元数据膨胀
```

## Broker IO

Broker 的 IO 优化围绕「顺序写日志 + 减少刷盘 + 隔离 IO 线程 + 分离磁盘」。Kafka 日志是 append-only 顺序写，天然适配机械盘与 SSD 的顺序带宽；`log.flush.interval.messages` 与 `log.flush.interval.ms` 控制刷盘策略，但更推荐依赖操作系统页缓存与副本机制而非频繁 fsync。网络线程与 IO 线程分离，避免慢磁盘拖慢网络。

```text
Broker IO 关键参数
num.network.threads  处理网络请求（含副本复制）
num.io.threads       处理磁盘 IO（读写日志）
log.segment.bytes    单段日志大小，过大导致清理慢
log.retention.hours  保留时长，影响磁盘水位
log.dirs             多目录可挂多块盘分摊 IO
```

```text
# server.properties 关键片段
num.network.threads=8
num.io.threads=16
log.segment.bytes=1073741824        # 1GB 一个段
log.retention.hours=168             # 保留 7 天
log.flush.interval.messages=10000   # 每 1 万条刷盘一次
log.flush.interval.ms=1000          # 或每 1 秒刷盘一次
log.dirs=/data1/kafka,/data2/kafka  # 多盘分摊 IO
num.replica.fetchers=4              # 副本拉取线程，影响复制带宽
```

```bash
# 通过 iostat 观察 Broker 磁盘压力
iostat -x 1 5
# 关注 %util 与 await：util 长期 100% 说明磁盘是瓶颈

# 查看 Kafka 副本落后情况（衡量复制 IO 压力）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --under-replicated-partitions
```

```text
IO 优化要点
1. 写路径顺序写，读路径靠页缓存，随机读命中缓存
2. 副本同步与业务读写的 IO 线程是共享的，落后副本要尽快修
3. SSD 上关闭不必要的预读，机械盘上保证 log.dirs 分盘
```

## Page Cache

页缓存是 Kafka 高性能的基石：Linux 会把磁盘文件缓存到内存，Kafka 写消息本质是「写页缓存」，读消息若命中页缓存则完全不走磁盘。Kafka 读路径用 `sendfile` 零拷贝，数据从页缓存直接经网卡发出，不经过用户态缓冲区的二次拷贝。因此 Broker 要预留足够内存给页缓存，且不应手动 `echo 3 > drop_caches` 清空缓存。

```text
Kafka 读写路径与页缓存
写：Producer -> 网络 -> 页缓存(脏页) -> 后台刷盘
读：Consumer -> 网络 -> 页缓存命中(零拷贝 sendfile) -> 直接发送
关键：读命中缓存 = 纯内存操作；未命中 = 磁盘随机读
```

```bash
# 观察系统页缓存水位
free -h
# buff/cache 越大，说明缓存越多；available 才是真正可分配内存

# 查看 Kafka 进程实际占用的缓存（常被误判为内存泄漏）
cat /proc/$(pgrep -f kafka.Kafka | head -1)/status | grep -E 'VmRSS|RssFile'
```

```text
页缓存优化原则
1. 为 Broker 留足内存，堆外部分主要给页缓存用
2. 堆内存(heap) 6~8GB 即可，其余交给操作系统页缓存
3. 冷启动后首次读会「穿透」到磁盘，可预热或接受首读慢
4. 不要设 swappiness 过高，避免页缓存被换出到 swap
```

```text
Kafka 核心链路总览
Producer 批量攒批 -> 压缩 -> 分区路由 -> Broker 顺序写页缓存
-> 副本异步复制 -> Consumer 批量拉取 -> 页缓存零拷贝返回
每一环的参数都影响最终的吞吐与延迟
```

## 应用场景实战

### 场景一：日志采集高吞吐管道

某业务每天产生 50 亿条日志，峰值 20 万条/秒，要求端到端延迟 < 5 秒、数据不丢。采用「加大批量 + lz4 压缩 + 合理分区 + at-least-once」的组合方案。

```java
Properties p = new Properties();
p.put("bootstrap.servers", "kafka1:9092,kafka2:9092,kafka3:9092");
p.put("acks", "1");                       // 日志类容忍少量丢失，acks=1 提速
p.put("retries", 3);
p.put("batch.size", 131072);              // 128KB 大批量
p.put("linger.ms", 20);                   // 20ms 攒批
p.put("compression.type", "lz4");
p.put("buffer.memory", 134217728);        // 128MB 缓冲
p.put("max.in.flight.requests.per.connection", 5);
KafkaProducer<String, String> producer = new KafkaProducer<>(p);
```

```text
# 主题配置：60 分区，复制因子 2，保留 3 天
kafka-topics.sh --bootstrap-server localhost:9092 --create \
  --topic app-log --partitions 60 --replication-factor 2 \
  --config retention.ms=259200000
```

```bash
# 验证吞吐与延迟：kafka-producer-perf-test 压测
kafka-producer-perf-test.sh --topic app-log --num-records 1000000 \
  --record-size 512 --throughput -1 \
  --producer-props bootstrap.servers=localhost:9092 \
  batch.size=131072 linger.ms=20 compression.type=lz4
```

### 场景二：交易消息低延迟 + 有序保障

支付交易要求端到端延迟 < 100ms，且同一订单的状态流转必须严格有序。方案：`linger.ms=0` 关闭攒批、`acks=all` 强一致、按订单号 Key 路由保证单分区有序，同时用 `idempotence` 保证不重复。

```java
Properties p = new Properties();
p.put("bootstrap.servers", "kafka1:9092,kafka2:9092,kafka3:9092");
p.put("acks", "all");                       // 强一致：所有 ISR 副本确认
p.put("enable.idempotence", true);          // 幂等，防重复
p.put("max.in.flight.requests.per.connection", 5);
p.put("linger.ms", 0);                      // 立即发送，不攒批
p.put("batch.size", 16384);
p.put("compression.type", "snappy");        // 低 CPU 快速压缩
p.put("partitioner.class", "com.example.UserIdPartitioner");
KafkaProducer<String, String> producer = new KafkaProducer<>(p);
```

```text
低延迟场景取舍
acks=all + linger.ms=0：牺牲吞吐换毫秒级延迟与强一致
Key 路由 + 单分区有序：同一订单永远进同一分区
幂等 + 事务：消费端配合 read_committed 实现精确一次
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产端统一 `compression.type=producer`，让压缩只发生一次，Broker 不做二次压缩。
2. 分区数按「峰值吞吐 / 单分区吞吐 × 1.2」规划，并保证分区数是消费者并发数的整数倍。
3. 为 Broker 预留足够内存给页缓存，堆内存控制在 6~8GB，其余交给操作系统。
4. 日志/埋点类用 `acks=1 + 大批量 + lz4`；交易类用 `acks=all + 幂等`，按 SLA 分档配置。
5. 监控指标优先看「端到端延迟、副本落后数、请求队列深度、页缓存命中率」，而非只看吞吐。
6. 用 `kafka-producer-perf-test` 与 `kafka-consumer-perf-test` 上线前压测，校准分区数与批量参数。
7. `log.dirs` 用多块盘分摊 IO，SSD 场景下把日志与副本分布到不同故障域。

### 踩坑记录

```text
坑 1：linger.ms 设得过大导致端到端延迟爆表
结论：攒批是「延迟换吞吐」，默认 0，设 20ms 就引入至少 20ms 固定延迟
原因：linger.ms 是「最多等这么久」，有数据就一直等到点才发
解法：交易类设 0，日志类 10~20ms，先测延迟再定

坑 2：分区数远小于消费者实例数，消费者空转
结论：一个分区只能被一个实例消费，实例多于分区时多余的实例拿不到数据
原因：Consumer Group 的分配以分区为最小单位
解法：分区数 >= 实例数，扩容前先评估；用 range/roundrobin 分配策略均衡

坑 3：Broker 内存被误判为泄漏，频繁 drop_caches
结论：Kafka 依赖页缓存，RSS 高是正常的，手动清缓存会击穿性能
原因：写读都走页缓存，缓存越多越好；Linux 会在内存紧张时自动回收
解法：不要 drop_caches；监控用 available 而非 free；给 Broker 专属内存

坑 4：compression.type 设成 gzip 但 CPU 打满
结论：gzip 压缩比高但 CPU 最贵，高吞吐下会成为瓶颈
原因：压缩/解压在 Producer 与 Consumer 端都要消耗 CPU
解法：默认 lz4 或 zstd，CPU 敏感用 snappy，带宽敏感才用 gzip

坑 5：扩分区后按 Key 的局部有序被破坏
结论：分区数变化会改变 hash 取模结果，同一 Key 会落到不同分区
原因：默认哈希是 key.hashCode() % partitions，分区数一变取模结果就变
解法：分区只增不减且尽量一次规划到位；如需严格有序用单分区或外部排序
```
