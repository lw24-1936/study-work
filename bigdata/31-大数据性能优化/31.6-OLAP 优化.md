## 概述

OLAP 引擎（ClickHouse、Doris、StarRocks、Kylin）的核心思路是「用空间换时间、用排序换查询、用合并换写入」。优化 OLAP 不外乎五件事：选对排序键让查询走范围扫描、用主键索引快速定位、用物化视图和预聚合把高成本计算前移、以及用合并策略控制后台开销。本章以 ClickHouse 为主、Doris/StarRocks 为辅展开。

```text
OLAP 优化核心公式
查询加速 = 排序键(Scan 缩小) + 主键(定位快) + 物化视图/预聚合(算前移)
存储/后台 = Compaction(合并策略) 平衡写入放大与查询效率
关键：一切围绕「让查询扫描更少的数据、做更少的计算」
```

## Sort Key 排序键

排序键（`ORDER BY`）决定数据在磁盘上的物理顺序，是 OLAP 加速的第一杠杆。查询条件命中排序键前缀时，引擎能直接跳到对应区间做范围扫描，跳过海量无关数据。排序键设计原则是「把高频过滤、低基数的列放前面」，因为前缀索引只对排在前面的列生效。

```text
排序键设计原则
1. 高频等值/范围过滤列放最前（如时间、分区列）
2. 低基数列靠前，高基数列靠后（前缀压缩更有效）
3. 避免把高基数列（如 uuid）放前面，索引几乎失效
4. 排序键过长会拖慢写入，需在查询与写入间平衡
```

```sql
-- ClickHouse：按 时间 + 用户 排序，查询按时间范围扫描
CREATE TABLE events (
    event_time DateTime,
    user_id    UInt64,
    event_type LowCardinality(String),
    amount     Decimal(18, 2)
) ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY (event_time, user_id);   -- 排序键 = 主键前缀

-- 命中排序键前缀的查询：只扫描对应时间区间
SELECT count(), sum(amount)
FROM events
WHERE event_time >= '2026-08-01' AND event_time < '2026-08-14';
```

```sql
-- Doris：Duplicate 模型 + 排序键，前缀过滤生效
CREATE TABLE events (
    event_time DATETIME,
    user_id    BIGINT,
    event_type VARCHAR(32),
    amount     DECIMAL(18, 2)
) DUPLICATE KEY(event_time, user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 16
PROPERTIES ("replication_num" = "1");
```

```text
排序键与查询的关系
命中前缀列 -> 范围扫描，读数据量指数级下降
未命中前缀 -> 退化为全表扫描，排序键白设计
典型错误：把 uuid 放第一列，等于没有排序键
```

## Primary Key 主键

OLAP 中的主键与传统数据库主键含义不同：它首先是「稀疏索引」的键，用来在排序键基础上进一步跳过数据块（granule/mark），而不强制唯一性。ClickHouse 主键必须是排序键的前缀，主键越长、基数越高，索引粒度越粗，跳数效果越差。

```text
主键 vs 排序键（ClickHouse）
排序键 ORDER BY：决定物理顺序，是数据布局
主键 PRIMARY KEY：默认等于排序键，用于构建稀疏索引
稀疏索引：每 N 行（默认 8192）记录一个 mark，定位数据块
主键必须是排序键前缀；主键越短，索引越紧凑、跳数越快
```

```sql
-- 显式指定主键为排序键前缀，主键更短更紧凑
CREATE TABLE orders (
    order_id   UInt64,
    order_time DateTime,
    user_id    UInt64,
    status     LowCardinality(String)
) ENGINE = MergeTree
PARTITION BY toYYYYMM(order_time)
ORDER BY (order_time, user_id, order_id)
PRIMARY KEY (order_time, user_id);   -- 只对前两列建稀疏索引

-- 查看是否命中主键索引（扫描了多少 mark）
SELECT count() FROM orders WHERE order_time >= '2026-08-01';
-- 用 EXPLAIN 查看过滤后扫描的数据块数
EXPLAIN indexes = 1
SELECT count() FROM orders WHERE order_time >= '2026-08-01';
```

```text
主键优化要点
1. 高基数列（uuid、订单号）不适合做主键前缀，稀疏索引退化
2. 主键越短越好，可只取排序键前 2~3 列
3. index_granularity 默认 8192，超大宽表可调大，窄表可调小
4. 主键不保证唯一，去重需另用 ReplacingMergeTree 或去重表
```

## Materialized View 物化视图

物化视图把「查询时现算」变成「写入时预算」。OLAP 的物化视图通常有两种形态：一是引擎内部的增量物化视图（如 ClickHouse 的 `MATERIALIZED VIEW` + `TO` 表），随写入自动触发；二是查询改写型的物化视图（如 Doris/StarRocks 的同步物化视图），优化器自动路由。它能把聚合、Join、表达式计算前移，代价是额外存储与写入开销。

```text
两种物化视图形态
1. 增量物化视图（ClickHouse）：写入源表时触发器计算并落目标表
   查询需显式查目标表，适合「固定口径的预聚合」
2. 查询改写物化视图（Doris/StarRocks）：透明加速
   优化器自动改写查询到物化视图，对用户无感知
```

```sql
-- ClickHouse 增量物化视图：按天预聚合金额
CREATE TABLE events_daily (
    day        Date,
    user_id    UInt64,
    cnt        UInt64,
    total_amt  Decimal(38, 2)
) ENGINE = SummingMergeTree
ORDER BY (day, user_id);

CREATE MATERIALIZED VIEW mv_events_daily TO events_daily AS
SELECT toDate(event_time) AS day,
       user_id,
       count() AS cnt,
       sum(amount) AS total_amt
FROM events
GROUP BY day, user_id;

-- 查询直接命中预聚合表，秒级返回
SELECT day, sum(total_amt) FROM events_daily
WHERE day >= '2026-08-01' GROUP BY day;
```

```sql
-- StarRocks：同步物化视图，优化器自动改写
CREATE MATERIALIZED VIEW mv_orders_amount AS
SELECT user_id, sum(amount) AS total_amount
FROM orders
GROUP BY user_id;

-- 用户照常查明细表，优化器自动命中物化视图
SELECT user_id, sum(amount) FROM orders GROUP BY user_id;
```

```text
物化视图注意事项
1. 每个物化视图都是一份额外存储，会放大写入成本
2. 明细更新模型下，物化视图可能滞后，需评估一致性需求
3. 只对「高频、低变化、聚合口径固定」的查询建物化视图
```

## Compaction 合并

OLAP 引擎普遍采用 LSM-Tree 或类似结构：数据先写内存，再刷成一个个不可变的段（part/segment/rowset），后台线程不断把小段合并成大段。合并的价值在于减少查询要扫描的段数、删除过期/重复数据、触发排序与索引重建；代价是后台 IO 与 CPU 开销，即「写入放大」。

```text
Compaction 关键概念
小段合并 -> 大段：减少查询扫描的段数
合并时触发：去重(Replacing)、聚合(Summing)、过期删除(TTL)
写入放大：数据被反复读写多次，合并越激进放大越严重
分层策略：L0 小段多，逐层合并到 Ln 大段
```

```sql
-- ClickHouse 合并参数（表级或全局）
CREATE TABLE events (
    event_time DateTime,
    user_id    UInt64,
    amount     Decimal(18, 2)
) ENGINE = MergeTree
ORDER BY event_time
SETTINGS
    merge_with_ttl_timeout = 86400;   -- TTL 合并间隔

-- 手动触发合并（可选）
OPTIMIZE TABLE events FINAL;

-- 查看当前段与合并状态
SELECT table, part_name, rows
FROM system.parts WHERE table = 'events' AND active;
```

```text
# Doris 后台合并相关配置（be.conf）
# 合并线程数
max_compaction_threads = 8
# 单次合并最大并发
max_base_compaction_concurrency = 4
# 每轮合并选择段数上限
cumulative_compaction_max_deltas = 1000
```

```text
合并策略取舍
查询多、写入少：可以激进合并（较少段、扫描快）
写入多、查询少：降低合并频率，避免与写入争抢 IO
大宽表 + 高写入：用分层合并，控制单次合并规模
```

## Pre-Aggregation 预聚合

预聚合是把「查询时聚合」提前到「数据写入时或定期任务中」，常见三种落点：引擎内置聚合模型（Summing/AggregatingMergeTree、Doris 聚合模型）、异步物化视图、以及 Kylin 式的 Cube 预计算。预聚合的核心收益是「明细几十亿行，聚合后可能只有几万行」，查询从扫明细变成读结果。

```text
三种预聚合落点对比
1. 引擎聚合模型：写入时即合并（SummingMergeTree 等），强实时但仅支持固定聚合
2. 异步物化视图：后台周期刷新，支持 Join/复杂口径，略滞后
3. Cube 预计算(Kylin)：离线预建多维立方体，查询最快，构建成本最高
```

```sql
-- ClickHouse SummingMergeTree：写入时按主键自动 sum 数值列
CREATE TABLE events_sum (
    day       Date,
    user_id   UInt64,
    cnt       UInt64,
    amount    Decimal(38, 2)
) ENGINE = SummingMergeTree
ORDER BY (day, user_id);

-- AggregatingMergeTree：配合聚合函数状态，支持任意聚合
CREATE TABLE events_agg (
    day     Date,
    user_id UInt64,
    amt     AggregateFunction(sum, Decimal(38, 2)),
    cnt     AggregateFunction(count, UInt64)
) ENGINE = AggregatingMergeTree
ORDER BY (day, user_id);

-- 写入聚合状态
INSERT INTO events_agg
SELECT toDate(event_time), user_id,
       sumState(amount), countState()
FROM events GROUP BY toDate(event_time), user_id;

-- 查询合并状态
SELECT day, sumMerge(amt), countMerge(cnt)
FROM events_agg GROUP BY day;
```

```sql
-- Doris 聚合模型：写入时按 Key 自动聚合
CREATE TABLE user_stats (
    user_id   BIGINT,
    pv        BIGINT SUM DEFAULT "0",
    amount    DECIMAL(18,2) SUM DEFAULT "0"
) AGGREGATE KEY(user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 10;
```

```text
预聚合适用边界
适用：明细超大、口径固定、只需统计结果（PV/UV/金额汇总）
不适用：需要下钻明细、口径频繁变化、需要精确去重明细
取舍：预聚合 = 存储/构建成本 换 查询性能，先算收益再上
```

## 应用场景实战

### 场景一：实时订单看板秒级聚合

某电商大促期间订单量暴增，明细表每天几十亿行，要求「按小时/按天的 GMV、订单数」秒级返回。方案：明细表用 `toYYYYMMDD` 分区 + 时间排序，另建 SummingMergeTree 预聚合表 + 物化视图自动写入。

```sql
-- 明细表：时间分区 + 时间排序，写入走批量
CREATE TABLE order_detail (
    order_id   UInt64,
    order_time DateTime,
    user_id    UInt64,
    amount     Decimal(18, 2)
) ENGINE = MergeTree
PARTITION BY toYYYYMMDD(order_time)
ORDER BY (order_time, order_id);

-- 预聚合表：按小时+用户，SummingMergeTree 自动求和
CREATE TABLE order_hour_sum (
    hour     DateTime,
    user_id  UInt64,
    cnt      UInt64,
    amount   Decimal(38, 2)
) ENGINE = SummingMergeTree
ORDER BY (hour, user_id);

-- 物化视图：写入明细时自动预聚合
CREATE MATERIALIZED VIEW mv_order_hour TO order_hour_sum AS
SELECT toStartOfHour(order_time) AS hour,
       user_id, count() AS cnt, sum(amount) AS amount
FROM order_detail GROUP BY hour, user_id;
```

```sql
-- 看板查询：命中预聚合表，秒级返回
SELECT toStartOfHour(hour) AS h, sum(cnt) AS orders, sum(amount) AS gmv
FROM order_hour_sum
WHERE hour >= now() - INTERVAL 24 HOUR
GROUP BY h ORDER BY h;
```

### 场景二：多维分析 Cube 预计算

需要支持任意维度的组合下钻分析（地区 × 品类 × 渠道 × 时间），且查询要亚秒级。方案：用 Kylin/Doris 预构建 Cube，把维度组合预先物化，查询直接命中 Cube。

```text
# 预计算 Cube 的构建与收益
维度：地区、品类、渠道、时间（4 维 -> 16 种组合）
Cube：离线任务预计算所有维度组合的聚合结果
查询：任意组合下钻 -> 直接读对应 Cuboid，亚秒级返回
代价：组合爆炸，需做维度裁剪与聚合组（Aggregation Group）
```

```sql
-- Doris：异步物化视图做复杂口径预聚合（周期刷新）
CREATE MATERIALIZED VIEW mv_channel_cate AS
SELECT channel, category, toDate(order_time) AS day,
       count(*) AS orders, sum(amount) AS gmv
FROM order_detail
GROUP BY channel, category, day;

-- 刷新任务（调度系统定时触发）
REFRESH MATERIALIZED VIEW mv_channel_cate;
```

```text
Cube 设计要点
1. 维度不超过 20 个，否则组合爆炸，存储失控
2. 用 Aggregation Group 裁剪不必要的维度组合
3. 高基维度（如 user_id）不要进 Cube，改回明细查询
```

## 最佳实践与踩坑记录

### 最佳实践

1. 排序键永远把「分区列/时间列 + 高频过滤列」放最前，高基数列放最后或干脆不进排序键。
2. 主键只取排序键前 2~3 列，保持稀疏索引紧凑，避免把 uuid 放进主键前缀。
3. 高频固定口径的聚合用「预聚合表 + 物化视图」，明细保留一份用于下钻，双写而非单一路径。
4. 写入高峰降低合并频率，查询高峰前手动 `OPTIMIZE` 合并小段，错峰执行后台任务。
5. 用 `system.parts` / `EXPLAIN indexes` 观察扫描段数与 mark 数，量化每项优化的收益。
6. 聚合口径会变、需要精确明细的查询不要强行预聚合，先评估「收益/存储成本」再决策。
7. 预聚合与物化视图要纳入数据质量校验，避免明细更新后聚合结果滞后或口径漂移。

### 踩坑记录

```text
坑 1：把 uuid 放进排序键/主键第一列
结论：查询走不了范围扫描，主键稀疏索引几乎失效，退化全表扫描
原因：高基数列让每个 mark 区间都唯一，跳数能力为零
解法：uuid 放最后或作为数据列不参与排序键

坑 2：排序键太长拖慢写入
结论：排序键列越多、越长，每次刷盘排序与索引构建越贵，写入吞吐下降
原因：MergeTree 每个段写入都要按排序键排序并建稀疏索引
解法：排序键控制在 2~4 列，高基数列不进排序键

坑 3：物化视图建太多导致写入放大
结论：每个物化视图都是一份额外写入与存储，写入 QPS 会被拖垮
原因：写入明细表时要同步触发所有物化视图的计算与落盘
解法：只对真正高频的查询建物化视图，定期清理无用视图

坑 4：合并与写入高峰撞车导致延迟毛刺
结论：Compaction 与实时写入争抢 IO/CPU，查询与写入出现毛刺
原因：后台合并线程与写入刷盘共用磁盘带宽
解法：错峰合并、限制合并线程数、把合并调低优先级

坑 5：SummingMergeTree 当作精确结果源
结论：SummingMergeTree 只在合并时求和，查询前没合并会读到「未合并的重复行」
原因：数据可能散在多个段中，同一 Key 的多次写入未及时合并
解法：查询统一用 sum()/sumMerge() 聚合函数，或查询前 OPTIMIZE FINAL
```
