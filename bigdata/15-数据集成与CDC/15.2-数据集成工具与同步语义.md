## 概述

数据集成是把数据从源端（数据库、文件、日志、消息队列）搬到目标端（数仓、数据湖、缓存、搜索）的过程，是数据平台的「水渠」。它涉及两类形态——批量 ETL（按批次离线搬运）和流式 ETL（实时持续搬运），以及两大工程难题——全量/增量如何衔接、数据如何保证不丢不重不错。正确理解投递语义（Exactly-once / At-least-once / At-most-once）与幂等、去重、重试等保障手段，是做好数据集成的关键。

```text
数据集成两大维度：
1. 形态 —— 批量 ETL（T+1 离线）/ 流式 ETL（秒级实时）
2. 保障 —— 全量/增量衔接、投递语义、幂等去重、重试与死信
常见链路：MySQL → DataX/SeaTunnel → Hive（批量离线）
          MySQL binlog → Canal/Debezium → Kafka → Flink → 数仓（实时）
```

## 批量与流式 ETL

批量 ETL 按固定的时间窗口（如每天凌晨）批量搬运数据，典型工具是 DataX、Sqoop、SeaTunnel 批模式；优点是实现简单、稳定、吞吐高，缺点是延迟大（T+1）。流式 ETL 持续处理增量数据，典型是 Kafka Connect、Flink、SeaTunnel 流模式；优点是延迟低（秒级），缺点是复杂度高、需要处理乱序与容错。两者常组合使用：先用批量做历史全量，再用流式做增量续跑。

```text
批量 vs 流式 ETL：
1. 批量 —— 周期调度、T+1 延迟、吞吐高、实现简单
2. 流式 —— 持续运行、秒级延迟、复杂度高、需容错
3. 组合 —— 批做全量回补 + 流做增量续跑，是主流方案
```

```shell
# 批量：SeaTunnel 批模式同步 MySQL 到 Hive
./bin/start-seatunnel-flink.sh --config config/mysql_to_hive.conf
# 流式：Flink CDC 实时同步 MySQL 到 Kafka
./bin/flink run -c com.example.MysqlCdcJob -d cdc-job.jar
```

## 全量与增量同步

全量同步一次性搬运源端所有数据，增量同步只搬运自上次同步以来的变更。首次接入数据源时先做全量（快照），之后靠增量（binlog/时间戳/CDC）持续跟进，这是数据集成的基本套路。关键难点是「全量与增量的衔接位点」——处理不好会丢数据或重复，需要记录全量完成时的位点，增量从该位点续跑。

```text
全量 vs 增量：
1. 全量 —— 首次快照，搬全部数据，用于初始化
2. 增量 —— 只搬变更，靠 binlog/时间戳/CDC 实现
3. 衔接 —— 记录全量完成位点，增量从该位点续跑
4. 难点 —— 全量期间数据仍在变，需一致性快照
```

```shell
# DataX 全量同步 MySQL 表到 HDFS
python bin/datax.py job/mysql_to_hdfs.json
# 增量：按更新时间拉取（SQL 带时间条件）
# SELECT * FROM orders WHERE update_time > '${last_run_time}'
```

## 同步一致性

同步一致性指数据搬到目标端后，内容是否正确、完整、且与源端一致。它涵盖三个层面：数据一致性（条数、字段值正确）、时序一致性（按正确顺序落地）、最终一致性（允许短暂不一致但最终收敛）。跨系统同步很难做到强一致，通常追求「最终一致 + 可校验」：通过全量对账、增量幂等、位点管理来保证不丢不重。

```text
同步一致性的三个层面：
1. 数据一致性 —— 条数、字段值搬运后与源端一致
2. 时序一致性 —— 变更按正确顺序落地（尤其同主键的更新）
3. 最终一致性 —— 允许短暂不一致，最终收敛到一致
```

```shell
# 对账：比较源端和目标端条数
mysql -e "SELECT COUNT(*) FROM shop.orders"
hive -e "SELECT COUNT(*) FROM ods.orders"   # 两者应相等，不等则补数
```

## Kafka Connect

Kafka Connect 是 Kafka 生态的数据集成框架，用「连接器（Connector）」把外部系统与 Kafka 对接：Source Connector 把外部数据灌进 Kafka，Sink Connector 把 Kafka 数据写到外部。它分布式、可横向扩展、内置 offset 管理，是流式数据集成的标准组件。Debezium（CDC 源）、JDBC Sink、Elasticsearch Sink 等都是它的连接器，适合「一切经过 Kafka」的流式集成架构。

```text
Kafka Connect 要点：
1. 架构 —— 分布式 worker 集群，连接器可并行扩展
2. Source —— 外部系统 → Kafka；Sink —— Kafka → 外部系统
3. offset —— 记录消费位点，故障后断点续传
4. 生态 —— Debezium、JDBC、ES、HDFS 等连接器丰富
```

```json
// 注册 Kafka Connect Sink 连接器（写 MySQL）
{
  "name": "mysql-sink",
  "config": {
    "connector.class": "io.confluent.connect.jdbc.JdbcSinkConnector",
    "topics": "orders",
    "connection.url": "jdbc:mysql://localhost:3306/shop",
    "connection.user": "root",
    "connection.password": "password",
    "insert.mode": "upsert"
  }
}
```

## NiFi

Apache NiFi 是面向「数据流可视化编排」的集成工具，通过拖拽处理器（Processor）在 Web UI 上编排数据流转，每个处理器负责一个动作（拉取、转换、路由、落库）。它的特色是「FlowFile」抽象——数据以带属性的流文件在处理器间流动，支持背压、优先级、数据溯源（provenance）。适合需要灵活编排、可视化、跨异构系统的集成场景，但吞吐量不如 DataX/SeaTunnel。

```text
NiFi 要点：
1. 抽象 —— FlowFile 带属性流转，处理器对 FlowFile 加工
2. 编排 —— 可视化拖拽，无需写代码
3. 溯源 —— provenance 记录每个 FlowFile 的完整流转历史
4. 适用 —— 灵活编排、异构系统、需要可视化管理的场景
```

```text
NiFi 典型数据流：
GetFile（拉取文件）→ RouteOnAttribute（按属性路由）
→ ConvertRecord（格式转换）→ PutDatabaseRecord（写库）
```

## DataX

DataX 是阿里巴巴开源的离线数据同步工具，采用「Reader + Writer」插件化架构，通过一个 Job 把数据从 Reader 端读出来、经内存通道传给 Writer 端写入。它单机多线程、吞吐高，支持 MySQL、Oracle、HDFS、Hive、ODPS 等大量数据源，是离线批量同步（尤其数据库到 Hive/HDFS）的事实标准。缺点是不支持实时、需手工配置 JSON。

```text
DataX 要点：
1. 架构 —— Reader（读）+ Channel（通道）+ Writer（写）
2. 定位 —— 离线批量同步，单机多线程，吞吐高
3. 生态 —— 支持主流 RDBMS、HDFS、Hive、ODPS 等
4. 限制 —— 只做批量，不做实时，配置为 JSON
```

```json
// DataX Job：MySQL 读 → HDFS 写
{
  "job": {
    "content": [{
      "reader": {
        "name": "mysqlreader",
        "parameter": {
          "username": "root", "password": "password",
          "column": ["order_id", "user_id", "amount"],
          "connection": [{"jdbcUrl": ["jdbc:mysql://localhost:3306/shop"],
            "table": ["orders"]}]
        }
      },
      "writer": {
        "name": "hdfswriter",
        "parameter": {
          "defaultFS": "hdfs://namenode:8020", "fileType": "orc",
          "path": "/warehouse/orders", "writeMode": "append"
        }
      }
    }]
  }
}
```

## SeaTunnel

SeaTunnel（原 Waterdrop）是新一代开源数据集成工具，同样基于 Source + Transform + Sink 的插件化架构，但比 DataX 多了两大能力：一是支持流批一体（同一套配置既能跑批也能跑流），二是支持数据转换（Transform）。它可运行在 Flink、Spark、Zeta 等多个引擎上，配置文件用 HOCON 格式，比 DataX 的 JSON 更简洁，定位是 DataX 的现代替代品。

```text
SeaTunnel 要点：
1. 架构 —— Source + Transform + Sink 三段式，插件化
2. 流批一体 —— 一套配置支持批和流两种模式
3. 引擎 —— 可运行在 Flink / Spark / Zeta 引擎上
4. 优势 —— 配置简洁、支持转换、现代替代 DataX
```

```shell
# SeaTunnel 同步 MySQL 到 Hive（HOCON 配置）
cat > config/mysql_to_hive.conf <<'EOF'
env { job.mode = "BATCH" }
source {
  Jdbc {
    url = "jdbc:mysql://localhost:3306/shop"
    user = "root"; password = "password"
    query = "SELECT * FROM orders"
  }
}
sink { Hive { table_name = "ods.orders" } }
EOF
./bin/start-seatunnel-flink.sh --config config/mysql_to_hive.conf
```

## Flume 与 Filebeat

Flume 和 Filebeat 都是「日志/文件采集」工具，负责把分布在各个机器上的日志文件实时采集到 Kafka 或存储。Flume 是 Hadoop 生态的采集组件，用 Source + Channel + Sink 三段式架构，适合 HDFS/HBase 落盘；Filebeat 是 Elastic 生态的轻量采集器，只做「读文件 + 发 Kafka/Logstash」，极轻、低资源占用。二者都解决「多机日志如何集中」的问题。

```text
Flume 与 Filebeat 对比：
1. Flume —— Hadoop 生态，Source+Channel+Sink，可落 HDFS
2. Filebeat —— Elastic 生态，极轻量，读文件发 Kafka/ES
3. 共同点 —— 都做日志/文件采集，都支持 tail 增量读
4. 选型 —— 进 ES 用 Filebeat，进 HDFS/HBase 用 Flume
```

```shell
# Filebeat 采集日志到 Kafka
cat > filebeat.yml <<'EOF'
filebeat.inputs:
  - type: log
    paths: ["/var/log/app/*.log"]
output.kafka:
  hosts: ["localhost:9092"]
  topic: "app-logs"
EOF
filebeat -e -c filebeat.yml
```

## Exactly-once 语义

Exactly-once（恰好一次）是最强的投递语义：每条数据在目标端恰好处理/写入一次，既不丢也不重。它的实现依赖「幂等写入」和「端到端事务」。Flink 靠 Checkpoint + 两阶段提交（2PC）实现 Kafka 到 Kafka 的端到端恰好一次；下游存储若支持事务（如支持 upsert 的数据库）也能达到。注意 Exactly-once 通常指「处理恰好一次」，「端到端恰好一次」需要上下游都配合。

```text
Exactly-once 要点：
1. 含义 —— 每条数据恰好被处理/写入一次，不丢不重
2. 基础 —— 幂等写入 + 事务（2PC）+ 状态快照
3. 实现 —— Flink Checkpoint + TwoPhaseCommitSinkFunction
4. 链路 —— Kafka Source → Flink → Kafka Sink（2PC 提交）
```

## At-least-once 语义

At-least-once（至少一次）保证每条数据至少被处理一次，允许重复但不允许丢失。这是最常见的默认语义：故障恢复时，未确认（ack）的数据会被重新处理，因此可能重复。Kafka 消费者默认就是至少一次（先消费后提交 offset，提交前崩溃则重读）。它的实现成本低、吞吐高，配合下游幂等（按主键 upsert）就能把重复的影响消除。

```text
At-least-once 要点：
1. 含义 —— 每条数据至少处理一次，可能重复，不会丢失
2. 原理 —— 先处理、后提交 offset，提交前崩溃则重放
3. 代价 —— 成本低、吞吐高，但要下游幂等兜底
4. 消除重复 —— 下游按主键 upsert / 去重
```

```shell
# Kafka 消费者 at-least-once：先处理再提交
# enable.auto.commit=false，处理成功后手动 commitSync
```

## At-most-once 语义

At-most-once（至多一次）保证每条数据最多被处理一次，允许丢失但不允许重复。它的实现是「先提交 offset、再处理数据」：处理前就提交，若处理中途崩溃，这条数据就丢了。这种语义吞吐最高、实现最简单，但会丢数据，只适合「丢失可接受」的场景（如非关键日志、监控采样、点击统计可容忍少量丢失）。

```text
At-most-once 要点：
1. 含义 —— 每条数据最多处理一次，可能丢失，不会重复
2. 原理 —— 先提交 offset、再处理，处理中崩溃则丢数据
3. 适用 —— 丢失可接受的场景：监控采样、非关键日志
4. 对比 —— At-least-once 不丢可能重，Exactly-once 不丢不重
```

## 幂等

幂等（Idempotence）指同一个操作执行多次与执行一次的效果相同。在数据集成里，幂等是「把重复数据变成正确数据」的关键手段：下游写入采用 upsert（按主键更新而非插入）、覆盖写（overwrite），那么即使上游重发了数据，最终结果仍是正确的。幂等是 At-least-once 语义的完美搭档——上游允许重复，下游幂等兜底。

```text
幂等要点：
1. 含义 —— 同一操作执行多次 = 执行一次，结果不变
2. 手段 —— 按主键 upsert、覆盖写、唯一键约束
3. 作用 —— 抵消 at-least-once 的重复，达到等效恰好一次
4. 前提 —— 数据有稳定的主键或唯一键
```

```sql
-- 幂等写入：按主键 upsert（重复执行结果相同）
INSERT INTO ods.orders (order_id, user_id, amount)
VALUES (1, 100, 99.9)
ON DUPLICATE KEY UPDATE user_id = VALUES(user_id), amount = VALUES(amount);
```

## 去重

去重（Deduplication）是在数据落地前或落地后，把重复的记录识别并消除的过程。它与幂等的区别是：幂等靠「写入时覆盖」天然去重，去重则是在「处理链路中」显式地识别并丢弃重复。去重可以在多个环节做——源端（唯一键）、传输（消息去重）、目标端（主键约束）。精确去重依赖全局唯一标识（主键/事件 ID），近似去重可用布隆过滤器。

```text
去重要点：
1. 含义 —— 识别并消除重复记录
2. 与幂等区别 —— 幂等靠覆盖写，去重靠显式识别丢弃
3. 依赖 —— 主键/事件 ID 做精确去重，布隆过滤器做近似去重
4. 位置 —— 源端、传输中、目标端都可做
```

```shell
# 用 sort + uniq 对文本去重（按主键排序后去重）
sort -u orders.txt > orders_dedup.txt
```

## 有序

有序（Ordering）指数据按正确的顺序到达和落地，对同一主键的多次更新，顺序错了最终值就错了。Kafka 靠「同一 key 写入同一分区」保证分区内有序，因此数据集成里常按主键作为分区键，保证同一主键的变更顺序不乱。跨分区的全局有序很难且代价高，实践中只保证「同一主键内有序」即可满足大多数场景。

```text
有序要点：
1. 含义 —— 数据按正确顺序处理，同主键的更新顺序不乱
2. 手段 —— 按主键做分区键，同一 key 进同一分区
3. Kafka —— 分区内有序，跨分区无序
4. 实践 —— 只保证主键内有序即可，全局有序代价高
```

```shell
# Kafka 生产者按主键分区，保证同一主键有序
# key 传 order_id，Kafka 按 key 哈希到固定分区
```

## 重试

重试（Retry）是数据集成应对「瞬时故障」的手段：写入失败、网络抖动时，自动重试若干次，多数瞬时错误能靠重试恢复。重试要配「最大次数 + 退避策略（backoff）」避免无限重试或雪崩；重试的语义必须是幂等的，否则重试本身会造成重复。超过重试上限仍失败的记录，应转入死信队列（DLQ）人工处理。

```text
重试要点：
1. 作用 —— 应对瞬时故障（网络抖动、短暂不可用）
2. 配置 —— 最大重试次数 + 退避策略（指数退避）
3. 前提 —— 重试操作必须幂等，否则重试造成重复
4. 兜底 —— 重试耗尽转入 DLQ，人工处理
```

```shell
# 带重试的同步脚本：失败后指数退避重试 3 次
attempt=0
while [ $attempt -lt 3 ]; do
  ./bin/start-seatunnel-flink.sh --config job.conf && break
  attempt=$((attempt+1)); sleep $((2 ** attempt))
done
```

## DLQ 死信队列

DLQ（Dead Letter Queue，死信队列）是存放「重试耗尽仍然失败」的脏数据的队列，避免坏数据阻塞主链路。数据集成里，格式错误、缺主键、约束冲突的记录会被重定向到 DLQ，主流程继续跑，坏数据由人工或脚本定期修复、补回。DLQ 是「失败隔离」的关键设计，保证个别坏数据不拖垮整个同步任务。

```text
DLQ 要点：
1. 作用 —— 隔离处理失败的脏数据，不阻塞主流程
2. 触发 —— 重试耗尽、格式错误、约束冲突
3. 处理 —— 人工/脚本修复后补回，或直接丢弃
4. 意义 —— 失败隔离，保证主链路可用性
```

```yaml
# SeaTunnel 配置 sink 的容错（重试 + DLQ 示意）
sink {
  Jdbc {
    url = "jdbc:mysql://localhost:3306/shop"
    table = "orders"
    max_retries = 3
    # 失败记录写入死信：dead_letter = { type = "kafka", topic = "dlq-orders" }
  }
}
```

## Replay 回放

Replay（回放）是数据集成出错后「重新消费一段历史数据」的能力。Kafka 天然支持回放——通过重置 offset 到某个历史位点，重新消费该位点之后的数据，从而修复错误结果。回放的前提是数据源保留足够长的历史（Kafka 的 retention 足够长），以及下游写入是幂等的（回放覆盖旧值而非产生重复）。回放是「数据可修复性」的核心保障。

```text
Replay 要点：
1. 含义 —— 重置位点，重新消费历史数据修复错误
2. 前提 —— Kafka retention 够长 + 下游幂等
3. 手段 —— 重置 consumer group offset 到历史位点
4. 意义 —— 出错可修复，是数据可回溯的保障
```

```shell
# 回放：把 consumer group offset 重置到最早，重新消费
kafka-consumer-groups --bootstrap-server localhost:9092 \
    --group sync-group --topic orders \
    --reset-offsets --to-earliest --execute
```

## 最佳实践与踩坑记录

### 最佳实践

1. 首次接入用「全量快照 + 增量续跑」组合，位点要记录清楚
2. 下游写入一律按主键 upsert，用幂等抵消 at-least-once 的重复
3. Kafka 同步链路用主键做分区键，保证同一主键内有序
4. 重试必须幂等 + 指数退避，重试耗尽进 DLQ 隔离脏数据
5. Kafka retention 配置足够长，保证出错后能回放修复
6. 定期对账（源端 vs 目标端条数/校验和），发现不一致及时补数
7. 批量用 DataX/SeaTunnel，流式用 Kafka Connect/Flink CDC，按延迟选型

### 踩坑记录

```text
坑 1：全量同步期间源端继续写入导致衔接处丢数据
结论：全量和增量的衔接位点漏掉一段数据。
原因：全量快照和增量位点不是原子衔接，中间变更被漏掉。
解法：用一致性快照（记录快照完成位点），或全量后按时间回补。

坑 2：下游不幂等 + 上游 at-least-once 导致重复数据
结论：目标端出现大量重复记录，指标虚高。
原因：故障重放产生重复，下游直接 insert 不做 upsert。
解法：下游按主键 upsert，或加唯一键约束。

坑 3：Kafka 不按主键分区导致同主键乱序
结论：同一主键的多次更新落地顺序错乱，最终值错误。
原因：不同分区消费进度不一，乱序落地。
解法：生产者用主键做 key，保证同主键进同分区。

坑 4：重试不幂等导致雪上加霜
结论：失败重试反而写入多份数据，数据更乱。
原因：重试操作本身非幂等，每次重试都再写一次。
解法：重试语义幂等化（upsert/覆盖写），或重试前先查重。

坑 5：Kafka retention 太短导致无法回放修复
结论：出错后历史数据已被清理，无法重放补数。
原因：retention 配置过短（如几小时），历史数据被删除。
解法：同步链路 topic 的 retention 配置数天以上，保留回放能力。

坑 6：坏数据阻塞主链路导致同步中断
结论：一条格式错误的数据卡住整个任务，反复失败。
原因：没有失败隔离，坏数据不断重试失败拖垮任务。
解法：重试耗尽转 DLQ，主流程继续，坏数据单独修复。
```
