## 概述

CDC（Change Data Capture，变更数据捕获）是识别并捕获数据库变更（增删改）的技术，核心目标是把业务库的变更实时、低延迟、低侵入地同步到下游（数据湖、数仓、缓存、索引）。相比全量快照同步，CDC 只传增量变更，延迟从小时级降到秒级，且不影响业务库性能。它是实时数仓、数据集成、缓存一致性、异构数据库同步的基础设施。

```text
CDC 的四种实现方式：
1. 基于日志 —— 解析数据库的 binlog/WAL（Debezium/Canal/Maxwell），低侵入、全量增量
2. 基于触发器 —— 业务表加触发器写变更表，侵入大、影响业务性能
3. 基于时间戳 —— 按更新时间拉增量，简单但漏删、漏多次更新
4. 基于快照对比 —— 定期全量对比差异，延迟高、开销大
```

```text
CDC 典型链路：
MySQL（binlog）→ Debezium/Canal → Kafka → Flink/Spark → 数据湖/数仓/缓存
```

## Binlog 二进制日志

Binlog 是 MySQL 的二进制日志，记录所有修改数据的 SQL 事件（增删改），是 MySQL 主从复制和 CDC 的数据来源。它有三种格式：STATEMENT（记 SQL 语句）、ROW（记每行变更前后值，CDC 需要这个）、MIXED（混合）。CDC 工具解析 ROW 格式的 binlog，还原出每一行的增删改事件。使用 binlog 需要开启（log_bin）、设置 ROW 格式，并给 CDC 工具足够的复制权限。

```text
Binlog 要点：
1. 内容 —— 记录数据变更事件（ROW 格式记每行变更前后值）
2. 格式 —— STATEMENT/ROW/MIXED，CDC 必须用 ROW
3. 复制协议 —— 工具伪装成 MySQL 从库（slave），订阅 binlog 流
4. 配置 —— log_bin=ON、binlog_format=ROW、server_id 唯一
```

```sql
-- MySQL 开启 binlog（my.cnf）
-- [mysqld]
-- server-id = 1
-- log_bin = /var/lib/mysql/mysql-bin
-- binlog_format = ROW
-- binlog_row_image = FULL

-- 授权 CDC 用户
GRANT SELECT, RELOAD, SHOW DATABASES, REPLICATION SLAVE, REPLICATION CLIENT
ON *.* TO 'cdc_user'@'%' IDENTIFIED BY 'password';
```

## WAL 预写日志

WAL（Write-Ahead Log）是数据库「先写日志再写数据」的机制，保证崩溃恢复和事务持久性。PostgreSQL 的 WAL（也叫 xlog）记录所有数据变更，是 PostgreSQL CDC 的数据来源。逻辑复制（Logical Replication）基于 WAL 把变更解码成逻辑事件（INSERT/UPDATE/DELETE），供 CDC 工具订阅。WAL 与 MySQL 的 binlog 本质相同——都是数据库变更的「事实日志」。

```text
WAL 要点：
1. 机制 —— 先写日志后写数据，崩溃后可重放恢复
2. CDC 来源 —— PostgreSQL 逻辑复制解码 WAL 得到变更事件
3. 逻辑解码 —— 用 pgoutput/test_decoding 插件解码 WAL
4. 配置 —— wal_level=logical、max_replication_slots 足够
```

```sql
-- PostgreSQL 开启逻辑复制
-- postgresql.conf:
-- wal_level = logical
-- max_replication_slots = 4
-- max_wal_senders = 4

-- 创建复制槽（Debezium 会自动创建）
SELECT * FROM pg_create_logical_replication_slot('debezium', 'pgoutput');
```

## Logical Replication 逻辑复制

逻辑复制（Logical Replication）是 PostgreSQL 提供的一种复制机制，它不像物理复制那样复制整个数据库的字节，而是把 WAL 解码成逻辑的 INSERT/UPDATE/DELETE 事件，发送给订阅者。这是 CDC 的理想来源——订阅者拿到的是「语义化的行级变更」，而非底层的物理页。Debezium 等工具就是作为逻辑复制的订阅者接收这些变更。

```text
逻辑复制 vs 物理复制：
1. 物理复制 —— 复制 WAL 字节流，主备字节级一致，用于高可用
2. 逻辑复制 —— 解码成行级变更事件，用于 CDC/数据分发/异构同步
3. 逻辑复制优势 —— 跨版本、跨库、可过滤表/列、可转换
```

## Debezium

Debezium 是 Red Hat 开源的 CDC 平台，作为 Kafka Connect 的源连接器运行，把数据库变更流式写入 Kafka。它支持 MySQL、PostgreSQL、MongoDB、SQL Server、Oracle 等，通过「首次快照 + 增量 binlog/WAL 订阅」实现全量+增量同步。Debezium 的优势是标准化（统一变更事件格式）、分布式（Kafka Connect 集群）、低延迟（秒级）、故障恢复（offset 记录在 Kafka）。

```text
Debezium 要点：
1. 架构 —— 运行在 Kafka Connect 集群上，作为 Source Connector
2. 流程 —— 首次一致性快照 + 订阅 binlog/WAL 增量
3. 事件格式 —— 统一的 create/update/delete 事件，含 before/after 值
4. 恢复 —— 变更 offset 存在 Kafka，故障后从断点续传
```

```json
// Debezium 变更事件（发给 Kafka）
{
  "before": null,
  "after": {"order_id": 1, "user_id": 100, "amount": 99.9},
  "source": {"table": "orders", "db": "shop", "ts_ms": 1723600000000},
  "op": "c",
  "ts_ms": 1723600000123
}
```

```shell
# 注册 Debezium MySQL 连接器
curl -X POST http://connect:8083/connectors -H 'Content-Type: application/json' -d '{
  "name": "mysql-orders-connector",
  "config": {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "database.hostname": "mysql",
    "database.port": "3306",
    "database.user": "cdc_user",
    "database.password": "password",
    "database.server.id": "184054",
    "database.include.list": "shop",
    "table.include.list": "shop.orders",
    "database.history.kafka.bootstrap.servers": "kafka:9092",
    "database.history.kafka.topic": "schema-changes.shop"
  }
}'
```

## Canal

Canal 是阿里巴巴开源的 MySQL binlog 解析工具，把自己伪装成 MySQL 从库，接收并解析 binlog，输出结构化的变更事件。它的优势是纯 Java、轻量、国内生态成熟（配合 canal-admin 管理、canal-adapter 落地到 ES/HBase/Kafka）。Canal 支持增量订阅和消费，客户端模式可自定义处理逻辑，是国产 CDC 事实标准之一。

```text
Canal 要点：
1. 原理 —— 伪装 MySQL slave，订阅 binlog，解析成事件
2. 组件 —— canal-server（解析）+ canal-client（消费）+ canal-admin（管理）
3. 输出 —— 可发 Kafka/RocketMQ，或自定义客户端消费
4. 特点 —— 纯 Java、轻量、国内生态成熟
```

```yaml
# canal.properties 关键配置
canal.instance.master.address = mysql:3306
canal.instance.dbUsername = canal
canal.instance.dbPassword = canal
canal.instance.filter.regex = shop\\.orders  # 只同步 orders 表
canal.serverMode = kafka                      # 输出到 Kafka
canal.mq.topic = canal_orders
```

## Maxwell

Maxwell 是 Zendesk 开源的 MySQL CDC 工具，同样基于 binlog 解析，特色是「一行数据一个 JSON」——把每条变更输出成一个 JSON 对象（含数据库、表、变更类型、数据），直接发 Kafka。它的优势是极简（单进程、无需集群）、JSON 友好、支持行级过滤和幂等消费。适合中小规模的 MySQL → Kafka 同步场景。

```text
Maxwell 要点：
1. 原理 —— 读 binlog，解析成行级变更
2. 输出 —— 一行变更一个 JSON，直接发 Kafka
3. 特点 —— 单进程极简、JSON 友好、易用
4. 定位 —— 轻量场景，对比 Debezium 更简单、对比 Canal 更轻
```

```shell
# 运行 Maxwell，同步到 Kafka
bin/maxwell --user=cdc_user --password=password \
    --host=mysql --producer=kafka \
    --kafka.bootstrap.servers=kafka:9092 \
    --filter='exclude: *.*, include: shop.orders'
```

```json
// Maxwell 输出的变更事件
{"database":"shop","table":"orders","type":"insert",
 "ts":1723600000,"xid":100,
 "data":{"order_id":1,"user_id":100,"amount":99.9}}
```

## 应用场景实战

### 场景一：MySQL 订单表实时同步到数据湖

```text
架构：MySQL → Debezium → Kafka → Flink → Iceberg/Hudi

1. MySQL 开 binlog（ROW 格式），建 cdc_user
2. Debezium 订阅 orders 表，变更发 Kafka topic shop.shop.orders
3. Flink 消费 Kafka，按主键 Upsert 写入 Hudi/Iceberg
4. 下游数仓/BI 实时读到最新订单数据
```

```python
# Flink SQL：Kafka CDC 到 Iceberg（按主键 Upsert）
# 使用 Flink CDC connector 直接读 MySQL binlog
sql = """
CREATE TABLE mysql_orders (
    order_id BIGINT, user_id BIGINT, amount DECIMAL(10,2),
    PRIMARY KEY (order_id) NOT ENFORCED
) WITH (
    'connector' = 'mysql-cdc',
    'hostname' = 'mysql',
    'port' = '3306',
    'username' = 'cdc_user',
    'password' = 'password',
    'database-name' = 'shop',
    'table-name' = 'orders'
);

CREATE TABLE iceberg_orders (
    order_id BIGINT, user_id BIGINT, amount DECIMAL(10,2),
    PRIMARY KEY (order_id) NOT ENFORCED
) WITH (
    'connector' = 'iceberg',
    'catalog-name' = 'iceberg_catalog',
    'catalog-type' = 'hadoop',
    'warehouse' = 's3://warehouse'
);

INSERT INTO iceberg_orders SELECT * FROM mysql_orders;
"""
```

## 最佳实践与踩坑记录

### 最佳实践

1. binlog 格式必须 ROW，row_image=FULL（否则拿不到完整变更前后值）
2. CDC 工具独立账号，只授 SELECT + REPLICATION 权限，最小权限
3. 变更事件带主键，下游按主键 Upsert 实现幂等
4. CDC 到下游的写入用「先快照后增量」，保证不丢数据
5. offset 存 Kafka/本地，故障后断点续传
6. 监控 binlog 延迟和积压，防止上游大事务卡住解析

### 踩坑记录

```text
坑 1：binlog 格式不是 ROW 导致拿不到行级变更
结论：Debezium/Canal 解析失败或拿到不完整的变更。
原因：STATEMENT 格式只记 SQL 语句，无法还原每行变更。
解法：binlog_format=ROW、binlog_row_image=FULL 后重启。

坑 2：没有主键的表做 CDC
结论：下游无法按主键 Upsert，重复消费产生脏数据。
原因：CDC 幂等依赖主键，无主键表每行无法唯一定位。
解法：给表加主键，或用唯一键替代；实在无键的用业务去重逻辑。

坑 3：大事务拖垮 binlog 解析
结论：一个批量 update 几百万行，CDC 延迟飙升甚至 OOM。
原因：ROW 格式把大事务拆成海量行事件，工具内存处理不过来。
解法：拆分大事务、调大工具内存、监控 binlog 积压。

坑 4：首次快照期间业务继续写导致数据不一致
结论：快照和增量衔接处丢数据或重复。
原因：全量快照和 binlog 增量不是原子衔接。
解法：用 Debezium 的一致性快照（snapshot + 记录 binlog 位点），或快照后按时间回补。

坑 5：重复消费导致数据重复
结论：下游出现重复记录。
原因：CDC 至少一次语义，故障恢复可能重放。
解法：下游按主键 Upsert 幂等消费，配合去重。
```
