## 概述

数据架构演进的主线是「如何组织、存储、加工、服务企业数据」。从关系型数仓（Data Warehouse）到数据湖（Data Lake），再到湖仓一体（Lakehouse），是「数据形态」的演进；从集中式到 Data Mesh/Data Fabric，是「数据组织方式」的演进；而 Lambda/Kappa/Medallion 则是「数据处理流水线」的架构范式。理解这条演进脉络，才能在选型时知道「当下该用哪种」。

```text
数据架构演进的两条线索：
线索一（数据形态）：Data Warehouse -> Data Lake -> Lakehouse
    —— 从「只存结构化」到「存一切」再到「统一格式下的事务与高性能」
线索二（组织方式）：集中式 -> Data Mesh -> Data Fabric
    —— 从「一个团队管所有数据」到「按域自治」再到「元数据驱动的智能编排」
第三条（处理范式，与上两条正交）：Lambda / Kappa / Medallion
    —— 批流怎么结合、数据怎么分层加工
```

```text
各类架构一句话定位：
1. Data Warehouse —— 结构化、高性能、口径统一的分析库
2. Data Lake —— 廉价存一切原始数据的池子，但治理难
3. Lakehouse —— 在数据湖上加事务与表格式，兼具湖的灵活与仓的性能
4. Data Mesh —— 按业务域去中心化治理数据，数据即产品
5. Data Fabric —— 用元数据织网，自动化连接分散数据
6. Lambda —— 批流两套链路并存，实时 + 准确兼顾
7. Kappa —— 只用流一条链路，实时为准、重放补历史
8. Medallion —— 湖内的分层规范（青铜/白银/黄金）
```

## Data Warehouse

数据仓库（数仓）是面向分析的结构化数据存储：数据从业务系统 ETL 进来，经清洗、建模（星型/雪花）后按主题组织，供 BI 报表和决策分析。它的特点是「先定义 schema 再写入」（Schema-on-Write）、数据质量高、口径统一、查询性能好。局限是只能存结构化数据，扩展成本高（专用硬件），对半结构化/非结构化数据无能为力。

```text
数据仓库要点：
1. Schema-on-Write —— 写前先定义结构，数据规整、质量高
2. 主题化 —— 面向分析主题（订单/用户/商品）建模
3. 分层 —— 经典 ODS/DWD/DWS/ADS 分层加工
4. 性能 —— 列式存储 + 预聚合，BI 查询快
5. 局限 —— 只存结构化、扩容贵、非结构化数据进不来
```

```text
典型数据仓库形态：
业务系统（OLTP）-> ETL -> 数仓（ODS -> DWD -> DWS -> ADS）-> BI 报表
技术栈：Teradata / Oracle / Greenplum / ClickHouse / 自建 Hive 数仓
适用：口径要求高、报表固定的企业分析场景
```

## Data Lake

数据湖是「把企业所有原始数据（结构化/半结构化/非结构化）原样存进廉价对象存储」的池子，写入时不做转换（Schema-on-Read，读时再定义结构）。它解决了数仓「只存结构化、存储贵」的问题——低成本存下一切，数据不丢失、可回溯。代价是数据质量靠下游自己保证，缺乏事务和治理，容易退化成「数据沼泽」。

```text
数据湖要点：
1. Schema-on-Read —— 写入原样，读取时再套结构，灵活但易脏
2. 存一切 —— 结构化/半结构化/非结构化、日志、图片都能进
3. 廉价 —— 对象存储（S3/OSS）+ 开放格式（Parquet/ORC）
4. 无事务 —— 原始数据湖缺 ACID，并发写、一致性难保证
5. 风险 —— 缺乏治理会退化成数据沼泽（data swamp）
```

```text
数据湖 vs 数仓对比：
数据湖：Schema-on-Read、存一切、对象存储、灵活、治理难、分析性能一般
数仓：Schema-on-Write、只存结构化、专用存储、规范、口径统一、查询快
```

## Lakehouse

湖仓一体（Lakehouse）是「在数据湖上叠加事务和治理能力」的架构——数据仍存对象存储（Parquet/ORC 文件），但用开放表格式（Iceberg/Hudi/Delta Lake）加上 ACID 事务、schema 演进、时间旅行等能力，把湖的「低成本 + 灵活性」和仓的「事务 + 高性能 + 治理」结合起来。它让同一份数据既能跑批处理、也能跑 BI 和机器学习，是当前主流方向。

```text
Lakehouse 要点：
1. 开放表格式 —— Iceberg/Hudi/Delta Lake 提供 ACID 与元数据管理
2. 存算分离 —— 数据在对象存储，多引擎共享同一份
3. 多负载 —— 批处理、交互式查询、机器学习用同一份数据
4. 事务能力 —— ACID、upsert、时间旅行、schema 演进
5. 治理 —— 统一元数据（Metastore），口径可统一
```

```text
湖仓一体架构：
对象存储（Parquet 文件）
    + Iceberg 表格式（ACID/快照/分区演进）
    + 统一元数据服务（Hive Metastore）
    => 多引擎共享：Spark（批）/ Trino（查询）/ Flink（流写入）
```

## Data Mesh

Data Mesh（数据网格）是把数据治理「去中心化」的组织架构理念：不再是中央数据团队统一管所有数据，而是每个业务域自己负责自己的数据产品（data as a product），用自助式数据平台 + 联邦治理来协调。它解决的是「中央数据团队成为瓶颈」的组织问题——当企业大到一定程度，集中式数仓的交付速度和领域知识都会成为瓶颈。

```text
Data Mesh 要点：
1. 数据即产品 —— 每个域把自己的数据当作产品，对质量/SLA 负责
2. 域自治 —— 领域团队最懂自己的数据，自己建模、自己服务
3. 自助平台 —— 提供统一底座，但治理权下放到域
4. 联邦治理 —— 全局标准（口径、安全）由中央定义，域内自治
5. 适用 —— 大型组织、数据域众多、中央团队成为瓶颈时
```

```text
Data Mesh 四原则：
1. 面向域的所有权（Domain Ownership）
2. 数据即产品（Data as a Product）
3. 自助式数据平台（Self-serve Platform）
4. 联邦计算治理（Federated Computational Governance）
```

## Data Fabric

Data Fabric（数据编织）是「用元数据把分散的数据源智能连接起来」的技术架构——它不是又一个存储，而是在现有各种数据源（湖、仓、库、API）之上，构建统一的元数据知识图谱，自动发现、理解、治理数据，并自动化完成数据集成与交付。核心是「元数据驱动的智能编排」，减少人工集成工作，让数据「自动找得到、用得上」。

```text
Data Fabric 要点：
1. 元数据驱动 —— 构建全企业元数据知识图谱，自动发现数据
2. 连接分散 —— 不搬数据，统一访问分散在多处（多云/混合）的数据
3. 自动化 —— 自动做数据发现、血缘、质量、访问控制
4. 增强集成 —— 用 ML 辅助（主动元数据），减少人工 ETL
5. 与 Mesh —— Fabric 是技术实现，Mesh 是组织理念，二者常结合
```

```text
Data Fabric vs Data Mesh：
Data Fabric —— 技术架构，靠元数据图谱 + 自动化集成连接数据
Data Mesh —— 组织架构，靠域自治 + 数据产品去中心化治理
实践中常结合：Mesh 定组织边界，Fabric 提供技术底座
```

## Lambda

Lambda 架构是「批处理 + 流处理两条链路并行」的实时大数据架构：批处理层（Batch Layer）对全量历史数据做精确计算产出批视图；速度层（Speed Layer）对增量实时数据做近似计算产出实时视图；服务层（Serving Layer）合并两者对外提供查询。它兼顾「实时性」和「准确性」，代价是两套代码、两套逻辑要维护一致。

```text
Lambda 架构要点：
1. 三层 —— Batch Layer（批，精确）/ Speed Layer（流，实时）/ Serving Layer（合并）
2. 批层 —— 全量重算，结果准确，延迟高（T+1）
3. 速度层 —— 增量实时计算，低延迟，结果可能不精确
4. 合并 —— 查询时融合批视图 + 实时视图
5. 痛点 —— 同一套逻辑写两遍（批 + 流），维护成本高、易不一致
```

```text
Lambda 架构数据流：
数据源 -> 分两路
  ├-> Batch Layer（全量重算，产出批视图）
  └-> Speed Layer（增量实时，产出实时视图）
两路视图 -> Serving Layer 合并 -> 查询
典型组合：Hadoop/Spark 批处理 + Storm/Flink 实时处理
```

## Kappa

Kappa 架构是「只用流处理一条链路」的架构：所有数据（历史 + 实时）都进消息队列（Kafka），用流处理引擎（Flink）统一处理；要重算历史时，就把消息队列里的历史数据「重放」（replay）再算一遍，不需要单独的批处理层。它解决了 Lambda「两套代码」的问题——一套流逻辑，实时和历史复用，代价是要求消息队列保留足够久的历史数据。

```text
Kappa 架构要点：
1. 单链路 —— 只用流处理，没有独立批处理层
2. 重放 —— 历史数据存在消息队列里，重算时重新消费（replay）
3. 一套逻辑 —— 实时与历史用同一套流代码，维护成本低
4. 前提 —— 消息队列要有足够长的保留期（retention）存历史
5. 局限 —— 全量重算慢，某些批式优化（大规模 join）不如批处理
```

```text
Kappa 架构数据流：
数据源 -> 消息队列（Kafka，长保留期）
         -> 流处理（Flink，一套代码）
         -> 结果视图（实时 + 重放历史都可算）
对比 Lambda：砍掉 Batch Layer，逻辑只写一份，靠 replay 补历史
```

## Medallion

Medallion（奖牌架构，又称多层湖架构）是数据湖/湖仓内部的「分层规范」，用青铜（Bronze）/白银（Silver）/黄金（Gold）三层组织数据加工：青铜层存原始落地数据（未加工），白银层做清洗、校验、去重（可复用），黄金层产出面向业务的聚合结果。它是 Databricks 推广的 Lakehouse 分层最佳实践，让湖里的数据也像数仓一样有清晰的加工链路。

```text
Medallion 架构要点：
1. Bronze —— 原始层，数据原样落地（追加式），保留最细粒度
2. Silver —— 清洗层，去重/校验/标准化，形成可复用的干净数据
3. Gold —— 业务层，按主题聚合、面向分析/报表的结果表
4. 对应数仓 —— Bronze≈ODS、Silver≈DWD、Gold≈DWS/ADS
5. 价值 —— 给「灵活但易乱」的数据湖加上分层纪律，兼顾灵活与治理
```

```text
Medallion 三层映射：
Bronze（青铜）-> 原始落地，追加不可变，可随时重放
Silver（白银）-> 清洗去重、schema 统一、可复用的明细
Gold（黄金）  -> 主题聚合、指标宽表，直接供 BI/应用
与数仓分层对照：Bronze≈ODS，Silver≈DWD，Gold≈DWS/ADS
```

## 应用场景实战

### 场景一：选型决策——小型团队 vs 大型企业的数据平台

```text
场景：判断该用哪种数据架构
1. 中小团队、报表为主 -> 传统数仓（口径统一、查询快、够用）
2. 数据多样、要存原始、成本敏感 -> 数据湖（对象存储存一切）
3. 既要湖的灵活又要仓的性能 -> Lakehouse（Iceberg + 多引擎）
4. 大型组织、中央团队瓶颈 -> Data Mesh（域自治 + 数据产品）
5. 多源异构、跨云 -> Data Fabric（元数据驱动统一访问）
```

```text
实时架构选型决策树：
要实时结果吗？
  ├─ 否 -> 纯批处理（T+1 离线数仓）
  └─ 是 -> 实时结果要求精确吗？
        ├─ 是 -> Lambda（批 + 流双链路，各自优化）
        └─ 否（可容忍近似）-> Kappa（只流处理，一套代码）
```

### 场景二：从数仓到湖仓一体的迁移路径

```text
迁移路径（传统 Hive 数仓 -> Lakehouse）：
1. 现状：Hive 数仓跑在 HDFS 上，按 ODS/DWD/DWS/ADS 分层
2. 第一步：数据迁移到对象存储（S3/OSS），格式保持 Parquet
3. 第二步：用 Iceberg 建表，把 HDFS 上的 Hive 表迁移为 Iceberg 表
4. 第三步：查询引擎从 Hive 换成 Trino/Spark SQL，性能提升
5. 第四步：引入 Medallion 分层，用 Bronze/Silver/Gold 规范湖内加工
收益：存算分离降成本、多引擎共享、支持事务与时间旅行
```

```text
迁移后 Lakehouse 架构：
对象存储（S3）
  + Iceberg 表格式（ACID/快照/时间旅行）
  + Hive Metastore（统一元数据）
  + Medallion 分层（Bronze -> Silver -> Gold）
  + 多引擎（Spark 批 / Flink 流 / Trino 查询）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 选型先看规模与诉求——小团队别上 Data Mesh，大组织别死守集中式数仓
2. 数据湖一定要配治理，否则会退化成数据沼泽
3. Lakehouse 是当前主流，Iceberg + 多引擎 + Medallion 分层是成熟组合
4. 实时链路首选 Kappa，除非有强一致性的批式重算需求才上 Lambda
5. 湖内加工用 Medallion 分层，让灵活的数据湖也有清晰链路
6. Data Mesh 是组织变革，先解决组织与所有权，再谈技术平台
7. 架构演进要渐进，别推倒重来，先迁存储、再迁计算、后改组织

### 踩坑记录

```text
坑 1：建了数据湖但没治理，退化成数据沼泽
结论：数据湖堆满各种格式的原始文件，没人说得清有哪些数据、能不能用。
原因：只追求「存下一切」的灵活性，没配套元数据、质量、权限治理。
解法：引入表格式 + 元数据目录 + 质量规则，用 Medallion 分层规范加工。

坑 2：Lambda 架构两套逻辑维护不一致
结论：批处理和实时处理算出的同一指标对不上，口径混乱。
原因：同一业务逻辑在批、流里各写一遍，改了批忘了改流。
解法：优先改用 Kappa（一套流逻辑），或用统一语义层保证口径一致。

坑 3：盲目上 Data Mesh 但组织没跟上
结论：把数据平台拆成各域自治后，各域重复造轮子、口径更乱。
原因：Data Mesh 本质是组织变革，技术拆了但所有权、治理没理顺。
解法：先明确域边界和数据产品 owner，再逐步下放，中央保留联邦治理。

坑 4：从数仓迁湖仓时直接推倒重来
结论：迁移周期长、业务中断，最终半途而废又退回老数仓。
原因：想一步到位重写全部链路，风险太高。
解法：渐进迁移——先迁存储与表格式，查询引擎逐步切换，老链路保留并行。

坑 5：Kappa 架构消息队列保留期太短
结论：要重算历史数据时，发现消息队列里数据已经被清掉，无法 replay。
原因：Kafka 默认保留期短（7 天），没按重算需求调长。
解法：按「最长重算窗口」设置 retention，或用分层存储（tiered storage）保留历史。
```
