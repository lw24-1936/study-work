## 概述

AI 数据架构是面向机器学习与大模型应用的数据基础设施，核心任务是让「原始数据 → 特征 → 模型 → 在线服务」这条链路高效、可复用地运转。它在大数据平台之上叠加了特征存储、向量检索、Embedding 生成、模型服务与效果评估等能力，既支撑传统机器学习，也支撑 RAG 检索增强生成等大模型应用。

```text
AI 数据架构分层：
┌──────────────────────────────────────────────────────┐
│  应用层     智能问答 / 推荐 / 风控 / 搜索 / Agent        │
├──────────────────────────────────────────────────────┤
│  服务层     Serving(模型服务) / RAG 编排 / 特征在线服务   │
├──────────────────────────────────────────────────────┤
│  特征层     Feature Store(离线+在线特征) / Vector DB      │
├──────────────────────────────────────────────────────┤
│  计算层     Embedding 生成 / 特征计算(Spark/Flink)       │
├──────────────────────────────────────────────────────┤
│  数据层     Data Lake(湖仓) / 结构化+非结构化统一存储      │
└──────────────────────────────────────────────────────┘
```

## Data Lake

Data Lake（数据湖）是 AI 数据架构的数据底座，负责以原生格式集中存储海量的结构化、半结构化与非结构化数据。它强调「先存储、后建模」，用开放表格式（Iceberg/Hudi/Delta）管理大规模数据，同时容纳文本、图像、日志等模型训练所需的多样化语料。数据湖为特征工程与模型训练提供统一、可追溯的数据来源。

```text
Data Lake 要点：
- 统一存储：结构化表 + 非结构化文件（文本/图像/日志）集中管理
- 开放表格式：Iceberg/Hudi 提供 ACID、upsert、time travel
- 训练语料来源：模型训练与微调数据的唯一可信来源
- 数据版本：配合 time travel 实现训练数据的版本化与可复现
```

可运行示例：在数据湖中创建训练数据集并做版本化快照。

```sql
-- 创建训练样本表（Iceberg）
CREATE TABLE ml.training_samples (
  sample_id   BIGINT,
  feature_vec ARRAY<DOUBLE>,
  label       INT,
  dt          STRING
) USING iceberg
PARTITIONED BY (dt);

-- 写入一批训练样本
INSERT INTO ml.training_samples VALUES
  (1, array(0.1, 0.2, 0.3), 1, '2026-08-13'),
  (2, array(0.4, 0.5, 0.6), 0, '2026-08-13');

-- 记录训练数据快照版本
SELECT snapshot_id, committed_at FROM ml.training_samples.snapshots;
```

## Feature Store

Feature Store（特征存储）是特征工程的「统一管理中枢」，负责特征的离线计算、在线读取与一致性保障。它解决了训练与推理特征不一致（Training-Serving Skew）的核心痛点：离线用 Spark 计算特征并注册，在线通过特征服务低延迟地提供同一套特征。特征按「特征组」组织，带版本与血缘，可被多个模型复用。

```text
Feature Store 要点：
- 离线特征：批/流计算产生，存入特征表，供训练使用
- 在线特征：同步到低延迟存储（Redis），供推理实时读取
- 一致性：训练与在线共用同一套特征定义，消除 skew
- 复用与血缘：特征组可复用，带版本与血缘追溯
```

可运行示例：注册特征并在线读取（Feast 风格）。

```python
from feast import FeatureStore

store = FeatureStore(repo_path=".")

# 获取历史特征用于训练
training_df = store.get_historical_features(
    entity_df="select user_id, event_ts from user_events where dt='2026-08-13'",
    features=["user_features:age", "user_features:total_gmv"],
).to_df()

# 在线读取特征用于推理
online_features = store.get_online_features(
    entity_rows=[{"user_id": 200}],
    features=["user_features:age", "user_features:total_gmv"],
).to_dict()
print(online_features)
```

## Vector DB

Vector DB（向量数据库）是面向 Embedding 向量检索的专用存储，支撑语义相似度搜索。它通过索引（HNSW、IVF、PQ）加速高维向量的近似最近邻（ANN）查询，是 RAG、相似推荐、以图搜图等应用的核心组件。主流实现有 Milvus、Qdrant、Weaviate、Pinecone 等，通常支持标量过滤 + 向量检索的混合查询。

```text
Vector DB 要点：
- 向量索引：HNSW/IVF/PQ 加速 ANN 检索
- 相似度度量：余弦相似度、内积、欧氏距离
- 混合查询：标量条件过滤 + 向量相似度联合检索
- 应用场景：RAG 检索、语义搜索、推荐召回、去重
```

可运行示例：用 Milvus 写入向量并做相似度检索。

```python
from pymilvus import Collection, connections, DataType, CollectionSchema, FieldSchema

connections.connect(host="milvus-host", port="19530")

fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True),
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=128),
    FieldSchema(name="doc_id", dtype=DataType.VARCHAR, max_length=64),
]
schema = CollectionSchema(fields, "document_vectors")
col = Collection("doc_vectors", schema)

# 写入向量
col.insert([[1], [[0.1] * 128], ["doc_001"]])

# 建索引并检索 Top-K
col.create_index("embedding", {"index_type": "HNSW", "metric_type": "COSINE"})
col.load()
results = col.search([[0.1] * 128], "embedding", {"metric_type": "COSINE"}, limit=3)
print(results)
```

## Embedding

Embedding（向量嵌入）是把文本、图像等非结构化数据映射为稠密向量的过程，是 AI 数据架构中连接「原始数据」与「向量检索/模型」的关键一环。它通过预训练模型（如 BERT、BGE、text-embedding 系列）将语义编码进向量空间，使语义相近的内容在向量空间中距离更近。Embedding 质量直接决定 RAG 检索与相似度计算的效果。

```text
Embedding 要点：
- 语义映射：文本/图像 → 稠密向量，语义相近则向量相近
- 模型选择：BGE、text-embedding-3、M3E 等，按语言与场景选型
- 离线批量：对海量文档离线生成向量，写入 Vector DB
- 在线实时：对查询语句实时生成向量，用于检索匹配
```

可运行示例：用 Python 生成文本 Embedding。

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-small-zh-v1.5")

texts = ["如何申请退款", "订单物流查询", "Python 数据清洗教程"]
embeddings = model.encode(texts, normalize_embeddings=True)

print(embeddings.shape)  # (3, 512)
```

## RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是大模型应用的主流范式，通过「先检索、再生成」让大模型基于外部知识回答问题，缓解幻觉与知识时效问题。其流程为：文档切分（chunking）→ Embedding 向量化 → 写入向量库 → 查询时检索 Top-K 相关片段 → 拼接进 Prompt 交给大模型生成。RAG 是 AI 数据架构与向量检索技术最典型的落地点。

```text
RAG 要点：
- 文档切分：按语义/长度切 chunk，控制上下文相关性
- 向量检索：Top-K 召回相关片段，可加 rerank 精排
- Prompt 组装：检索片段 + 用户问题拼接为上下文
- 生成：大模型基于上下文生成答案，降低幻觉
```

可运行示例：简化的 RAG 检索与生成流程。

```python
import numpy as np
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-small-zh-v1.5")

# 知识库文档与向量化
docs = ["退款需在订单完成后 7 天内申请", "物流可在订单页查看轨迹", "满 99 元包邮"]
doc_vecs = model.encode(docs, normalize_embeddings=True)

def retrieve(query, top_k=2):
    q_vec = model.encode([query], normalize_embeddings=True)
    scores = np.dot(doc_vecs, q_vec.T).flatten()
    top_idx = np.argsort(scores)[-top_k:][::-1]
    return [(docs[i], scores[i]) for i in top_idx]

# 检索出最相关片段，拼接给大模型
context = retrieve("怎么申请退款？")
print(context)
```

## Serving

Serving（模型服务）负责把训练好的模型或封装好的 RAG 应用以在线服务的形式对外提供推理能力。它关注低延迟、高并发、弹性扩缩容与灰度发布，支持在线特征读取、模型推理与结果返回的完整链路。常见方案有 Triton、TorchServe、vLLM、Seldon 等，配合模型版本管理与流量控制实现稳定上线。

```text
Serving 要点：
- 在线推理：模型以 HTTP/gRPC 服务对外提供低延迟推理
- 特征在线读取：从 Feature Store/Redis 实时取特征
- 弹性扩缩容：按流量自动伸缩，保障高并发
- 版本与灰度：多版本共存，支持灰度发布与回滚
```

可运行示例：用 FastAPI 封装一个简单的在线推理服务。

```python
from fastapi import FastAPI
from pydantic import BaseModel
import numpy as np

app = FastAPI()

class Sample(BaseModel):
    features: list[float]

# 假设已加载的模型权重
weights = np.array([0.5, -0.2, 0.8])
bias = 0.1

@app.post("/predict")
def predict(sample: Sample):
    x = np.array(sample.features)
    score = float(np.dot(weights, x) + bias)
    pred = 1 if score > 0.5 else 0
    return {"score": score, "prediction": pred}
```

## Evaluation

Evaluation（效果评估）是 AI 数据架构的「质量闭环」，通过离线与在线指标持续度量模型与 RAG 应用的效果。离线评估用测试集计算准确率、召回率、AUC 等；RAG 场景额外关注检索命中率与答案相关性；在线评估通过 A/B 实验观察业务指标。评估结果反哺特征与模型迭代，形成数据飞轮。

```text
Evaluation 要点：
- 离线指标：准确率、召回率、F1、AUC，衡量模型质量
- RAG 评估：检索命中率、答案相关性、忠实度
- 在线评估：A/B 实验对比业务指标（点击率、转化率）
- 可复现：固定数据版本与评估脚本，保证结果可对比
```

可运行示例：计算二分类模型的离线评估指标。

```python
from sklearn.metrics import accuracy_score, precision_score, recall_score, roc_auc_score

y_true = [1, 0, 1, 1, 0, 1, 0, 0]
y_pred = [1, 0, 0, 1, 0, 1, 1, 0]
y_score = [0.9, 0.1, 0.4, 0.8, 0.2, 0.7, 0.6, 0.3]

print("准确率:", accuracy_score(y_true, y_pred))
print("精确率:", precision_score(y_true, y_pred))
print("召回率:", recall_score(y_true, y_pred))
print("AUC:", roc_auc_score(y_true, y_score))
```

## 应用场景实战

### 场景一：企业知识库 RAG 问答系统

某企业要构建内部知识库问答，让员工用自然语言查询制度与文档。完整链路为：文档从 Data Lake 读取 → 切分后 Embedding 向量化 → 写入 Vector DB → 用户提问时检索 Top-K 片段 → 拼接 Prompt 调用大模型生成 → 对答案做评估反馈。

```python
import numpy as np
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-small-zh-v1.5")

# 1. 文档切分（简化示例）
document = "员工年假每年 10 天；病假需提供医院证明；婚假 3 天。"
chunks = [c.strip() for c in document.replace("。", "。\n").split("\n") if c.strip()]

# 2. 向量化并建索引（简化用内存存储）
chunk_vecs = model.encode(chunks, normalize_embeddings=True)

def rag_answer(question):
    q_vec = model.encode([question], normalize_embeddings=True)
    scores = np.dot(chunk_vecs, q_vec.T).flatten()
    top_idx = int(np.argmax(scores))
    context = chunks[top_idx]
    # 3. 拼接 Prompt（实际调用大模型 API 生成答案）
    prompt = f"请根据以下资料回答问题。\n资料：{context}\n问题：{question}"
    return prompt, context

prompt, context = rag_answer("年假有几天？")
print("上下文片段:", context)
print("组装 Prompt:", prompt)
```

### 场景二：推荐系统特征在线化服务

某推荐系统需要把离线算好的用户特征实时提供给在线推理服务，避免训练与推理特征不一致。链路为：Spark 离线计算用户特征并写入 Feature Store → 同步到 Redis 在线存储 → 在线 Serving 实时读取特征并推理打分。

```python
import redis
import numpy as np

# 假设在线特征已同步到 Redis
r = redis.Redis(host="redis-host", port=6379, decode_responses=True)
r.hset("user:200", mapping={"age": "28", "total_gmv": "3560.5"})

# 在线服务读取特征并打分
def recommend(user_id):
    feat = r.hgetall(f"user:{user_id}")
    age = float(feat["age"])
    gmv = float(feat["total_gmv"])
    # 简化打分：gmv 越高、年龄越年轻分越高
    score = np.log1p(gmv) * 0.6 + (1.0 / (1.0 + age * 0.01)) * 0.4
    return round(float(score), 4)

print("用户 200 推荐分:", recommend(200))
```

## 最佳实践与踩坑记录

### 最佳实践

1. 训练推理特征统一：特征必须走 Feature Store 统一注册，在线离线共用一份定义，彻底消除 Training-Serving Skew。
2. 语料治理先行：RAG 的检索质量上限取决于语料质量，先做文档去重、清洗、结构化，再谈切分与向量化。
3. 分块策略贴合场景：chunk 大小需结合模型上下文长度与文档结构，避免切分过细丢失语义、过粗稀释相关性。
4. 混合检索优于纯向量：结合关键词检索（BM25）与向量检索，再叠加 rerank 精排，显著提升 RAG 召回质量。
5. 向量索引按需选型：数据量大用 HNSW/IVF，追求精度可配高召回参数，内存紧张用 PQ 量化，需按场景权衡。
6. 评估闭环不可省：建立离线评估集与在线 A/B 实验，用指标驱动特征与模型迭代，避免「凭感觉」上线。
7. 服务可观测：推理延迟、特征新鲜度、检索命中率都要埋点监控，及时发现问题。

### 踩坑记录

```text
坑 1：训练与在线特征不一致导致线上效果骤降
  结论：模型离线 AUC 很好，上线后效果大幅衰减。
  原因：训练用离线特征，在线用另一套实时计算逻辑，产生 skew。
  解法：特征统一走 Feature Store，训练与在线共用同一特征定义与计算逻辑。

坑 2：Embedding 模型与检索场景不匹配
  结论：RAG 检索出的片段与问题相关性差，答案质量低下。
  原因：用了通用英文模型处理中文文档，或未做领域适配。
  解法：按语言与领域选择 Embedding 模型，必要时用领域语料微调。

坑 3：向量库未建索引导致检索极慢
  结论：向量检索延迟高达秒级，无法支撑在线服务。
  原因：写入向量后忘记建索引或未加载 collection。
  解法：写入后调用 create_index 并 load，再执行检索。

坑 4：chunk 过大导致检索片段稀释关键信息
  结论：检索命中的片段包含大量无关内容，答案偏离问题。
  原因：文档切分粒度太粗，单 chunk 塞入过多主题。
  解法：按语义与结构切分，控制 chunk 在数百 token，必要时加标题上下文。

坑 5：缺少评估体系导致迭代无方向
  结论：反复调参却无法判断效果好坏，迭代陷入停滞。
  原因：未建立离线评估集与在线指标，改版全凭主观感受。
  解法：建设评测集与 A/B 实验框架，用指标量化每次变更的收益。
```
