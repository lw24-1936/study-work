## 概述

企业数据平台是一套覆盖数据「采集、存储、计算、服务、治理」全生命周期的统一基础设施，目标是让数据在企业内部被可信、高效、安全地使用。它不是一个单一组件，而是由多个子系统协同构成的一体化平台：底层以湖仓存储为底座，中层以批流计算引擎为核心，上层以数据服务与治理能力对外输出价值。

```text
企业数据平台分层架构：
┌──────────────────────────────────────────────────────┐
│  数据服务层   统一查询网关 / API 服务 / 指标平台 / BI     │
├──────────────────────────────────────────────────────┤
│  数据治理层   元数据 / 数据质量 / 数据血缘 / 权限审计      │
├──────────────────────────────────────────────────────┤
│  数据开发层   离线调度 / 实时开发 / SQL IDE / 任务编排     │
├──────────────────────────────────────────────────────┤
│  计算引擎层   Spark / Flink / Trino / MapReduce        │
├──────────────────────────────────────────────────────┤
│  存储底座层   HDFS / 对象存储 / Hive / Iceberg / Kafka   │
├──────────────────────────────────────────────────────┤
│  数据采集层   DataX / Flume / Canal / Kafka Connect    │
└──────────────────────────────────────────────────────┘
```

## 数据采集

数据采集负责把散落在业务库、日志、埋点、文件等异构数据源中的原始数据，源源不断地接入平台。离线场景通常采用批量抽取工具做全量或增量同步，实时场景则通过数据库变更捕获（CDC）或消息队列做秒级同步。采集的核心诉求是「不丢、不重、可回溯」，需要在源头就带上采集时间与数据来源标识。

```text
数据采集要点：
- 批量采集：DataX、Sqoop，按调度周期全量/增量抽取关系型数据库
- 实时采集：Canal 解析 MySQL binlog、Flume 采集日志、Kafka Connect 对接异构源
- 采集规范：统一记录采集时间 ts、来源库表 source、采集批次 batch_id
- 断点续传：记录水位线（主键/时间戳/binlog offset），失败可重跑
```

可运行示例：使用 DataX 将 MySQL 订单表全量同步到 HDFS。

```json
{
  "job": {
    "setting": {
      "speed": { "channel": 3 }
    },
    "content": [
      {
        "reader": {
          "name": "mysqlreader",
          "parameter": {
            "username": "root",
            "password": "******",
            "column": ["id", "user_id", "amount", "status", "created_at"],
            "connection": [
              { "jdbcUrl": ["jdbc:mysql://db-host:3306/mall"], "table": ["orders"] }
            ]

            "fileType": "orc",
            "path": "/ods/orders/dt=${dt}",
            "fileName": "orders",
            "writeMode": "append"
          }
        }
      }
    ]
  }
}
```

## 数据存储

数据存储层是整个平台的物理底座，需要同时满足「海量、廉价、多类型、高吞吐」的要求。典型的做法是以 HDFS 或云对象存储作为统一存储，之上用 Hive 提供表抽象，用列式格式（ORC/Parquet）压缩存储，用 Iceberg/Hudi 等开放表格式提供 ACID 与实时更新能力，用 Kafka 承担实时消息的中间缓冲。

```text
数据存储要点：
- 分布式文件系统：HDFS 或 S3/OSS 等对象存储，三副本保证可靠性
- 表格式演进：Hive 托管表 → Iceberg/Hudi/Delta 开放表格式（支持 upsert、time travel）
- 列式存储：ORC、Parquet 按列压缩，大幅降低分析型查询的 IO
- 消息缓冲：Kafka 按分区持久化实时数据，解耦生产与消费
- 分层分域：按 ODS/DWD/DWS/ADS 与业务域划分目录，控制权限粒度
```

可运行示例：创建 Iceberg 表并演示 time travel 回退。

```sql
-- 创建 Iceberg 分区表
CREATE TABLE mall.orders_iceberg (
  id            BIGINT,
  user_id       BIGINT,
  amount        DECIMAL(10,2),
  status        STRING,
  created_at    TIMESTAMP
) USING iceberg
PARTITIONED BY (days(created_at))
TBLPROPERTIES ('format-version' = '2');

-- 写入一批数据并记录快照
INSERT INTO mall.orders_iceberg VALUES
  (1, 100, 99.90, 'paid',   TIMESTAMP '2026-08-13 10:00:00'),
  (2, 101, 19.90, 'unpaid', TIMESTAMP '2026-08-13 11:00:00');

SELECT snapshot_id, committed_at FROM mall.orders_iceberg.snapshots;

-- 误删数据后，利用快照回退
ROLLBACK mall.orders_iceberg TO SYSTEM_VERSION AS OF 1234567890123456;
```

## 数据处理

数据处理层将原始数据加工成业务可用的结果，分为离线批处理与实时流处理两条链路。离线链路以 Spark/Hive 为主，适合海量数据的大规模 ETL 与复杂统计；实时链路以 Flink 为主，满足秒级延迟的指标计算与告警。二者常通过 Lambda 或流批一体架构统一，避免维护两套口径。

```text
数据处理要点：
- 批处理：Spark SQL、Hive on Tez/Spark，适合 T+1 的大批量计算
- 流处理：Flink DataStream/SQL，毫秒~秒级延迟，支持事件时间与窗口
- 流批一体：同一套 SQL 口径在流批两种模式下结果一致，降低双链路维护成本
- 任务编排：DolphinScheduler / Airflow 管理依赖与调度周期
```

可运行示例：使用 Spark SQL 做离线 ETL 清洗订单明细。

```scala
import org.apache.spark.sql.SparkSession
import org.apache.spark.sql.functions._

val spark = SparkSession.builder()
  .appName("OrdersETL")
  .enableHiveSupport()
  .getOrCreate()

// 从 ODS 读原始订单，清洗后写入 DWD
spark.sql("""
  INSERT OVERWRITE TABLE dwd.dwd_orders PARTITION (dt = '2026-08-13')
  SELECT
    id,
    user_id,
    amount,
    CASE WHEN status IN ('paid','refunded') THEN 1 ELSE 0 END AS is_valid,
    created_at
  FROM ods.ods_orders
  WHERE dt = '2026-08-13'
    AND amount > 0
    AND user_id IS NOT NULL
""")

spark.stop()
```

## 数仓

数仓是数据平台对数据的「建模与沉淀」环节，通过分层建模把杂乱数据组织成统一、规范、可复用的结构。经典分层为 ODS（贴源层）→ DWD（明细层）→ DWS（汇总层）→ ADS（应用层），配合维度建模（星型/雪花模型）与缓慢变化维处理，形成企业级的一致性数据视图。

```text
数仓要点：
- 分层：ODS 贴源、DWD 明细清洗、DWS 轻度汇总、ADS 面向应用
- 建模方法：维度建模（星型/雪花）、事实表 + 维度表
- 缓慢变化维：SCD1 覆盖、SCD2 拉链保留历史、SCD3 加列
- 主题域划分：交易、用户、商品、营销等，按域建库授权
```

可运行示例：构建一个缓慢变化维（SCD2）的用户维度拉链表。

```sql
-- 用户维度拉链表，记录生效/失效时间
CREATE TABLE dim.dim_user (
  user_id       BIGINT,
  user_name     STRING,
  user_level    STRING,
  start_date    STRING,   -- 生效日期
  end_date      STRING    -- 失效日期，9999-12-31 表示当前有效
);

-- 每日增量更新：新数据生效，旧数据闭链
INSERT OVERWRITE TABLE dim.dim_user
SELECT user_id, user_name, user_level, start_date, end_date
FROM (
  -- 新版本数据（当天拉取，end_date 置为 9999-12-31）
  SELECT user_id, user_name, user_level,
         '2026-08-13' AS start_date, '9999-12-31' AS end_date
  FROM ods.ods_user WHERE dt = '2026-08-13'
  UNION ALL
  -- 历史数据：若当天有变化则闭链，否则保持原样
  SELECT a.user_id, a.user_name, a.user_level,
         a.start_date,
         CASE WHEN b.user_id IS NOT NULL THEN '2026-08-12' ELSE a.end_date END
  FROM dim.dim_user a
  LEFT JOIN ods.ods_user b
    ON a.user_id = b.user_id AND b.dt = '2026-08-13'
  WHERE a.end_date = '9999-12-31'
) t;
```

## 数据服务

数据服务层把加工好的数据以标准化的方式开放给业务方，屏蔽底层存储细节。常见的服务形态包括统一 SQL 查询网关（如 Trino、StarRocks）、数据 API 服务（把 SQL 包装成 REST 接口）、指标平台（统一口径的指标查询）与 BI 报表。服务层强调高并发、低延迟与口径唯一，避免各业务方各取各数导致数据不一致。

```text
数据服务要点：
- 统一查询网关：Trino 联邦查询、StarRocks MPP 分析，提供统一 SQL 入口
- 数据 API：将指标/模型结果封装成 RESTful 接口，供应用系统调用
- 指标平台：原子/派生指标统一定义，口径唯一，供 BI 与分析复用
- 服务治理：限流、鉴权、配额、缓存，保障高并发下的稳定性
```

可运行示例：通过 Trino 联邦查询跨库关联订单与用户数据。

```sql
-- Trino 联邦查询：同时访问 Hive 订单与 MySQL 用户维表
SELECT
  o.order_id,
  o.amount,
  u.user_name,
  u.user_level
FROM hive.mall.dwd_orders o
JOIN mysql.crm.dim_user u
  ON o.user_id = u.user_id
WHERE o.dt = '2026-08-13'
  AND o.amount > 100
LIMIT 100;
```

## 数据治理

数据治理是对数据资产的「质量管理与规则运营」，目标是让数据可信、可懂、可用。治理围绕元数据管理、数据质量、数据血缘、生命周期与成本展开：通过元数据统一登记数据资产，通过质量规则发现脏数据，通过血缘追踪数据从源头到报表的流转链路，通过生命周期管理淘汰冷数据、控制存储成本。

```text
数据治理要点：
- 元数据管理：统一采集表、字段、分区、负责人等元信息
- 数据质量：完整性、唯一性、准确性、及时性等规则，异常自动告警
- 数据血缘：字段级血缘，支持影响分析与根因回溯
- 生命周期：冷热分层、TTL 清理、小文件合并，控制成本
```

可运行示例：定义数据质量校验规则（以 Spark SQL 校验空值与重复）。

```sql
-- 质量规则 1：订单金额不为空且大于 0
SELECT COUNT(*) AS invalid_count
FROM dwd.dwd_orders
WHERE dt = '2026-08-13'
  AND (amount IS NULL OR amount <= 0);

-- 质量规则 2：订单 ID 唯一性校验
SELECT order_id, COUNT(*) AS cnt
FROM dwd.dwd_orders
WHERE dt = '2026-08-13'
GROUP BY order_id
HAVING COUNT(*) > 1;
```

## 数据安全

数据安全贯穿平台的每个环节，覆盖「身份认证、访问授权、数据脱敏、数据加密、审计留痕」五大能力。基于 RBAC 或 ABAC 模型做细粒度权限控制，对敏感字段（身份证、手机号）做脱敏或加密，对所有访问行为记录审计日志，满足合规要求并防范数据泄露。

```text
数据安全要点：
- 身份认证：对接 LDAP/Kerberos，统一账号体系
- 访问授权：库/表/字段/行级权限，Ranger、Sentry 集中管控
- 数据脱敏：动态脱敏（查询时遮蔽）与静态脱敏（落库前处理）
- 数据加密：传输层 TLS、存储层透明加密
- 审计留痕：记录谁在何时访问了哪些数据，支撑合规审查
```

可运行示例：字段级脱敏与权限授予。

```sql
-- 授予只读权限
GRANT SELECT ON TABLE dwd.dwd_orders TO ROLE data_analyst;

-- 对敏感字段创建脱敏视图
CREATE VIEW dwd.v_orders_masked AS
SELECT
  order_id,
  user_id,
  amount,
  -- 手机号中间四位脱敏
  CONCAT(SUBSTR(phone, 1, 3), '****', SUBSTR(phone, 8, 4)) AS phone_masked
FROM dwd.dwd_orders;
```

## 数据目录

数据目录是数据资产的「统一检索与发现入口」，把分散在各系统中的元数据汇聚成一个可搜索、可浏览、可理解的知识图谱。用户通过目录可以快速找到所需数据，了解其含义、口径、质量与负责人，实现「找得到、看得懂、敢使用」。主流实现有 Apache Atlas、DataHub、Amundsen 等。

```text
数据目录要点：
- 资产发现：全文检索、标签、业务术语，帮助用户快速定位数据
- 业务语义：字段注释、指标口径、数据字典，让数据「可理解」
- 血缘图谱：表级与字段级血缘，直观展示数据流转
- 自助服务：数据申请、审批、开放流程线上化
```

可运行示例：用 DataHub CLI 登记并检索数据资产。

```shell
# 登记一个数据集
datahub put dataset \
  --urn "urn:li:dataset:(urn:li:dataPlatform:hive,mall.dwd_orders,PROD)" \
  --name "订单明细表" \
  --description "DWD 层订单明细，含金额与状态"

# 检索关键词为「订单」的资产
datahub search "订单" --page-size 10
```

## 应用场景实战

### 场景一：构建订单主题的离线数据链路

某电商企业需要把 MySQL 订单数据接入平台，加工成可供运营分析的日活订单报表。完整链路为：DataX 增量采集订单表到 ODS → Spark ETL 清洗到 DWD → 汇总到 DWS → 写入 ADS 供 BI 查询。

```sql
-- 1. DWD 层：清洗订单明细
INSERT OVERWRITE TABLE dwd.dwd_orders PARTITION (dt = '${dt}')
SELECT id AS order_id, user_id, amount, status, created_at
FROM ods.ods_orders
WHERE dt = '${dt}' AND amount > 0;

-- 2. DWS 层：按日汇总订单指标
INSERT OVERWRITE TABLE dws.dws_orders_daily PARTITION (dt = '${dt}')
SELECT
  dt,
  COUNT(DISTINCT user_id) AS pay_users,
  SUM(amount)            AS gmv,
  COUNT(1)               AS order_cnt
FROM dwd.dwd_orders
WHERE dt = '${dt}' AND status = 'paid'
GROUP BY dt;

-- 3. ADS 层：面向报表的应用结果
CREATE TABLE ads.ads_orders_report AS
SELECT dt, pay_users, gmv, order_cnt, gmv / pay_users AS arpu
FROM dws.dws_orders_daily;
```

### 场景二：搭建数据 API 服务对外开放指标

将上一步计算好的订单指标封装成 HTTP 接口，供业务系统实时调用。以 Python 服务为例，从 StarRocks 查询指标并返回 JSON。

```python
from flask import Flask, jsonify, request
import pymysql

app = Flask(__name__)

def query_metric(dt):
    conn = pymysql.connect(host='starrocks-host', port=9030,
                           user='reader', password='******', database='ads')
    with conn.cursor() as cur:
        cur.execute(
            "SELECT pay_users, gmv, order_cnt, arpu "
            "FROM ads_orders_report WHERE dt = %s", (dt,))
        row = cur.fetchone()
    conn.close()
    return row

@app.route('/api/orders/daily')
def daily_report():
    dt = request.args.get('dt', '2026-08-13')
    pay_users, gmv, order_cnt, arpu = query_metric(dt)
    return jsonify({
        "dt": dt,
        "pay_users": pay_users,
        "gmv": float(gmv),
        "order_cnt": order_cnt,
        "arpu": float(arpu)
    })

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=8080)
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分层分级规划目录：ODS/DWD/DWS/ADS 按业务域分库，权限从源头按层收敛，避免「一张大宽表打天下」。
2. 口径唯一化：指标定义收敛到指标平台或统一 SQL，禁止各团队私下重复计算同一指标。
3. 开放表格式优先：新表尽量使用 Iceberg/Hudi，天然支持 upsert、time travel 与流批一体，减少后续迁移成本。
4. 权限最小化：默认拒绝、按需申请，敏感字段统一走脱敏视图，杜绝直接暴露明文。
5. 可观测性：为每个任务埋点记录运行时长、数据量、延迟，形成数据平台的健康度看板。

### 踩坑记录

```text
坑 1：增量采集未做断点续传导致数据重复或丢失
  结论：数据同步任务失败重跑后出现重复数据。
  原因：增量抽取依赖时间戳或自增主键，但未持久化水位线，重跑从头开始。
  解法：用 Canal/DataX 记录 binlog offset 或主键水位，重跑时从断点续传，配合幂等写入。

坑 2：小文件过多拖垮 HDFS 与查询性能
  结论：流式写入产生海量小文件，NameNode 内存暴涨，查询极慢。
  原因：实时任务按批次频繁提交小文件，未做合并。
  解法：定期执行小文件合并，Iceberg 表开启 compaction，写入端控制文件大小。

坑 3：指标口径不一致导致「数据打架」
  结论：运营与财务报出的同一指标数值不同，互不认可。
  原因：各团队各自写 SQL，过滤条件、时间口径、去重逻辑不一致。
  解法：指标统一定义到指标平台，落地为唯一 SQL 口径，其他系统只做引用。

坑 4：宽表权限失控泄露敏感数据
  结论：业务方申请整表权限后拿到了未脱敏的手机号、身份证。
  原因：权限只做到表级，未做字段级与行级控制。
  解法：敏感字段单独建脱敏视图，仅授予视图权限；Ranger 配置字段级策略。

坑 5：血缘缺失导致变更影响无法评估
  结论：上游表结构变更后，下游大量任务报错，无法快速定位影响面。
  原因：未建设血缘，数据依赖靠人肉梳理。
  解法：通过 Atlas/DataHub 自动采集 SQL 解析血缘，变更前做影响分析。
```
