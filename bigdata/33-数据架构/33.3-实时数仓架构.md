## 概述

实时数仓是在传统离线数仓基础上，把数据处理时效从「T+1 小时/天」提升到「秒级」的架构形态，让业务能基于最新数据实时决策。其核心思想是把离线数仓的 ODS/DWD/DWS/ADS 分层搬到流式计算引擎上，以 Kafka 作为实时消息总线，以 Flink 作为流计算引擎，以 Iceberg 等开放表格式落地明细数据，以 StarRocks/ES/Redis 分别承担分析、检索与加速查询。

```text
实时数仓典型架构：
业务库 ──Canal/Debezium──▶ Kafka(ODS) ──Flink ETL──▶ Kafka(DWD)
                                                     │
                                     ┌───────────────┴───────────────┐
                                     ▼                               ▼
                              Iceberg(明细归档)              Kafka(DWS 汇总流)
                                                                     │
                                              ┌──────────────────────┤
                                              ▼                      ▼
                                        StarRocks(ADS 分析)    Redis/ES(指标加速/检索)
```

## Kafka

Kafka 在实时数仓中扮演「实时数据总线与分层存储」的角色，承接所有实时数据的缓冲与分层传输。它通过主题（Topic）与分区（Partition）实现高吞吐、可回放的消息存储，消费者可按 offset 精确控制读取位置，天然支持多个下游同时消费与故障回放。ODS、DWD、DWS 各层之间的数据流动都以 Kafka 主题为纽带，形成解耦的流式管道。

```text
Kafka 在实时数仓中的作用：
- 实时总线：所有 CDC 与埋点数据先进入 Kafka，削峰填谷
- 分层主题：ods_* / dwd_* / dws_* 对应数仓各层
- 可回放：按 offset 重放，支持下游故障恢复与口径重算
- 高吞吐：分区并行，支撑每秒百万级消息
```

可运行示例：创建实时数仓分层主题并写入测试数据。

```shell
# 创建 ODS 与 DWD 主题
kafka-topics.sh --bootstrap-server kafka:9092 \
  --create --topic ods_orders --partitions 6 --replication-factor 2
kafka-topics.sh --bootstrap-server kafka:9092 \
  --create --topic dwd_orders --partitions 6 --replication-factor 2

# 生产者写入一条订单消息
echo '{"order_id":1001,"user_id":200,"amount":99.9,"ts":1723500000000}' \
  | kafka-console-producer.sh --bootstrap-server kafka:9092 --topic ods_orders

# 消费者从头消费
kafka-console-consumer.sh --bootstrap-server kafka:9092 \
  --topic ods_orders --from-beginning
```

## Flink

Flink 是实时数仓的计算引擎，负责把 Kafka 中的原始流经过清洗、关联、聚合，加工成分层数据。它支持事件时间、水位线（Watermark）与各类窗口，能够在数据乱序、迟到的情况下仍保证计算结果的正确性；Checkpoint 机制提供了精确一次（Exactly-Once）的状态保障，确保故障后不丢不重。Flink SQL 让实时数仓可以用声明式 SQL 建模，极大降低开发门槛。

```text
Flink 在实时数仓中的作用：
- 流式 ETL：清洗、过滤、关联维表，产出 DWD 明细流
- 实时聚合：按窗口/维度聚合，产出 DWS 汇总流
- 精确一次：Checkpoint + 两阶段提交，保证端到端 Exactly-Once
- 维表关联：实时 join Redis/HBase 维表，补充维度信息
```

可运行示例：用 Flink SQL 做实时清洗并写入 DWD 主题。

```sql
-- 定义 ODS 源表（Kafka）
CREATE TABLE ods_orders (
  order_id BIGINT,
  user_id  BIGINT,
  amount   DECIMAL(10,2),
  ts       BIGINT,
  proctime AS PROCTIME()
) WITH (
  'connector' = 'kafka',
  'topic' = 'ods_orders',
  'properties.bootstrap.servers' = 'kafka:9092',
  'format' = 'json',
  'scan.startup.mode' = 'latest-offset'
);

-- 定义 DWD 目标表（Kafka）
CREATE TABLE dwd_orders (
  order_id BIGINT,
  user_id  BIGINT,
  amount   DECIMAL(10,2),
  dt       STRING,
  PRIMARY KEY (order_id) NOT ENFORCED
) WITH (
  'connector' = 'kafka',
  'topic' = 'dwd_orders',
  'properties.bootstrap.servers' = 'kafka:9092',
  'format' = 'json'
);

-- 清洗：过滤非法数据，补充日期字段
INSERT INTO dwd_orders
SELECT order_id, user_id, amount,
       DATE_FORMAT(proctime, 'yyyy-MM-dd') AS dt
FROM ods_orders
WHERE amount > 0 AND user_id IS NOT NULL;
```

## Iceberg

Iceberg 在实时数仓中承担「明细数据的持久化与归档」职责，解决纯 Kafka 无法长期存储、无法做复杂分析的问题。它提供 ACID 事务、行级 upsert、time travel 与流批一体能力，Flink 实时写入的同时，Spark/Trino 可基于同一份数据做离线分析。Iceberg 让实时数仓的明细层既能被实时消费，又能被离线回溯，实现了流批的真正统一。

```text
Iceberg 在实时数仓中的作用：
- 明细归档：实时明细流落地为可长期保存的列式表
- 流批一体：Flink 流写、Spark 批算共用同一份数据
- 行级更新：主键 upsert，支持订单状态等频繁变更的数据
- 时间旅行：按快照回溯任意历史版本，支持数据回滚
```

可运行示例：Flink 实时写入 Iceberg 明细表。

```sql
-- 创建 Iceberg 明细表（flink 写入）
CREATE TABLE dwd_orders_iceberg (
  order_id BIGINT,
  user_id  BIGINT,
  amount   DECIMAL(10,2),
  status   STRING,
  PRIMARY KEY (order_id) NOT ENFORCED
) WITH (
  'connector' = 'iceberg',
  'catalog-name' = 'realtime_catalog',
  'catalog-type' = 'hive',
  'warehouse' = 'hdfs://namenode:8020/warehouse',
  'format-version' = '2'
);

-- 实时 upsert 写入
INSERT INTO dwd_orders_iceberg
SELECT order_id, user_id, amount, status FROM dwd_orders;
```

## StarRocks

StarRocks 是实时数仓的「在线分析查询引擎」，承担 ADS 应用层的秒级查询。它采用 MPP（大规模并行处理）架构与向量化执行，支持高并发、低延迟的 OLAP 查询，并且支持从 Kafka 直接导入实时数据、与 Iceberg 做外表联邦查询。实时数仓的最终指标表通常落地到 StarRocks，直接对 BI 与数据应用提供服务。

```text
StarRocks 在实时数仓中的作用：
- 在线分析：MPP + 向量化，秒级返回聚合结果
- 高并发：面向 BI 报表与自助分析的高并发查询
- 实时导入：Routine Load 从 Kafka 持续导入
- 物化视图：预聚合加速常用指标查询
```

可运行示例：建 ADS 指标表并用 Routine Load 从 Kafka 导入。

```sql
-- 创建 ADS 指标表
CREATE TABLE ads_order_stats (
  dt          DATE,
  pay_users   BIGINT SUM,
  gmv         DECIMAL(20,2) SUM,
  order_cnt   BIGINT SUM
) AGGREGATE KEY (dt)
DISTRIBUTED BY HASH(dt) BUCKETS 4;

-- 从 Kafka 持续导入 DWS 汇总流
CREATE ROUTINE LOAD ads_order_stats_load ON ads_order_stats
PROPERTIES (
  'desired_concurrent_number' = '2',
  'format' = 'json'
)
FROM KAFKA (
  'kafka_broker_list' = 'kafka:9092',
  'kafka_topic' = 'dws_order_stats',
  'kafka_partitions' = '0,1,2',
  'property.group.id' = 'starrocks_load'
);
```

## ES

ES（Elasticsearch）在实时数仓中承担「明细检索与多维分析」的职责，补充 StarRocks 在文本检索、模糊匹配上的不足。它基于倒排索引提供近实时的全文搜索能力，常用于订单/日志/用户行为的明细检索、关键词聚合分析以及实时大屏的即席钻取。实时明细流经 Flink 处理后写入 ES，供业务做秒级检索与下钻。

```text
ES 在实时数仓中的作用：
- 全文检索：订单号、关键词、日志明细的模糊查询
- 近实时：数据写入后约 1 秒即可被检索到
- 多维聚合：按任意字段做聚合统计，支撑即席分析
- 大屏下钻：实时明细检索 + 维度聚合，支撑实时监控大屏
```

可运行示例：写入订单明细到 ES 并检索。

```shell
# 写入一条明细
curl -X POST "http://es:9200/orders/_doc/1001" -H 'Content-Type: application/json' -d '
{
  "order_id": 1001,
  "user_id": 200,
  "amount": 99.9,
  "status": "paid",
  "created_at": "2026-08-13T10:00:00Z"
}'

# 检索金额大于 50 的订单
curl -X GET "http://es:9200/orders/_search" -H 'Content-Type: application/json' -d '
{
  "query": {
    "range": { "amount": { "gt": 50 } }
  }
}'
```

## Redis

Redis 在实时数仓中承担「热数据加速与实时指标存储」的职责，为高并发、极低延迟的场景提供内存级读写。它常用于实时指标的即时查询（如大屏秒级刷新）、Flink 维表关联、去重与限量计数（如 UV、去重用户数）以及缓存热门查询结果。Redis 让实时数仓能支撑秒级甚至毫秒级的指标响应。

```text
Redis 在实时数仓中的作用：
- 指标加速：大屏实时指标内存存储，秒级读取
- 维表关联：Flink 关联 Redis 维表，补充维度字段
- 去重计数：HyperLogLog 近似 UV、Set 精确去重
- 结果缓存：缓存高频查询结果，降低后端压力
```

可运行示例：Flink 实时统计 GMV 并写入 Redis。

```sql
-- Flink SQL 实时聚合并写入 Redis
CREATE TABLE dws_gmv (
  dt    STRING,
  gmv   DECIMAL(20,2),
  PRIMARY KEY (dt) NOT ENFORCED
) WITH (
  'connector' = 'redis',
  'host' = 'redis-host',
  'port' = '6379',
  'format' = 'json'
);

INSERT INTO dws_gmv
SELECT DATE_FORMAT(proctime, 'yyyy-MM-dd') AS dt, SUM(amount) AS gmv
FROM ods_orders
GROUP BY DATE_FORMAT(proctime, 'yyyy-MM-dd');
```

## 应用场景实战

### 场景一：实时订单大屏

某电商需要在大促期间实时展示 GMV、支付用户数、订单量等核心指标，要求秒级刷新。链路为：Canal 采集订单变更到 Kafka ODS → Flink 实时清洗与聚合到 DWS → 指标写入 Redis/StarRocks → 大屏前端定时拉取。

```sql
-- Flink SQL：按分钟聚合订单指标，写入 Redis 供大屏读取
CREATE TABLE dws_order_minute (
  minute_key STRING,
  gmv        DECIMAL(20,2),
  order_cnt  BIGINT,
  pay_users  BIGINT,
  PRIMARY KEY (minute_key) NOT ENFORCED
) WITH (
  'connector' = 'redis',
  'host' = 'redis-host',
  'port' = '6379',
  'format' = 'json'
);

INSERT INTO dws_order_minute
SELECT
  DATE_FORMAT(proctime, 'yyyy-MM-dd HH:mm') AS minute_key,
  SUM(amount)                               AS gmv,
  COUNT(1)                                  AS order_cnt,
  COUNT(DISTINCT user_id)                   AS pay_users
FROM ods_orders
GROUP BY DATE_FORMAT(proctime, 'yyyy-MM-dd HH:mm');
```

### 场景二：订单明细实时检索与下钻

运营人员需要在大屏上点击某个指标后，能实时检索到对应的订单明细，并做多维聚合分析。链路为：Flink 清洗明细后双写 Iceberg（归档）与 ES（检索），前端通过 ES 完成明细检索与聚合下钻。

```shell
# 在 ES 中按状态聚合订单金额（多维分析下钻）
curl -X GET "http://es:9200/orders/_search" -H 'Content-Type: application/json' -d '
{
  "size": 0,
  "aggs": {
    "by_status": {
      "terms": { "field": "status" },
      "aggs": {
        "total_amount": { "sum": { "field": "amount" } }
      }
    }
  }
}'
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分层复用 Kafka：ODS/DWD/DWS 用不同主题分层，各层职责清晰，下游可独立消费，避免重复计算。
2. 明细落地 Iceberg：实时明细必须落地 Iceberg 持久化，Kafka 只做缓冲，防止因保留期到期导致明细永久丢失。
3. 精确一次保障：开启 Flink Checkpoint 与两阶段提交，配合幂等 sink，保证端到端 Exactly-Once。
4. 维表用 Redis 缓存：高频维表 join 优先用 Redis，配合 TTL 与定时刷新，避免每次请求都查关系库。
5. 水位线统一：多流 join 时统一水位线推进策略，避免因乱序导致窗口迟迟不关闭、内存暴涨。
6. 指标分层落地：实时指标最终统一落地到 StarRocks/Redis，避免业务方直连 Kafka 各算各的口径。

### 踩坑记录

```text
坑 1：只靠 Kafka 存明细导致数据永久丢失
  结论：Kafka 保留期到期后，历史明细无法回溯，数据审计失败。
  原因：误以为 Kafka 可长期保存数据，未落地持久化存储。
  解法：明细流在 Flink 中双写 Iceberg 归档，Kafka 仅作短期缓冲。

坑 2：窗口不关闭导致 Flink 内存持续上涨
  结论：实时任务运行数小时后内存告警，最终 OOM 崩溃。
  原因：多流 join 时水位线推进被慢流阻塞，窗口状态无法清理。
  解法：设置 idle 超时或允许迟到上限，确保水位线持续推进并触发窗口关闭。

坑 3：Redis 存大对象拖垮读写性能
  结论：把整张明细写入 Redis，key 膨胀，读写延迟急剧升高。
  原因：Redis 仅适合热指标与维表，不应承载大明细数据。
  解法：明细检索走 ES，指标与维表才用 Redis，并对 value 大小设限。

坑 4：Routine Load 消费延迟导致指标滞后
  结论：StarRocks 实时指标延迟达分钟级，大屏数据明显滞后。
  原因：Routine Load 并发不足，或数据倾斜导致单分区积压。
  解法：增大 desired_concurrent_number，合理设置 Kafka 分区数，消除热点分区。

坑 5：实时与离线口径不一致引发对账差异
  结论：同一指标实时值与离线 T+1 值对不上，业务质疑数据可信度。
  原因：实时链路与离线链路使用不同的口径与去重逻辑。
  解法：实时与离线共用同一套 SQL 口径定义，并通过流批一体引擎统一实现。
```
