## 概述

Hive SQL（HiveQL）是 Hive 的查询语言，在标准 SQL 之上扩展了分区、分桶、复杂类型（ARRAY/MAP/STRUCT）、Lateral View 等大数据特性。查询优化则是把「能跑」的 SQL 变成「跑得快」的 SQL，手段分三类：逻辑优化（谓词下推、列裁剪、Join 重排）、物理执行（Tez 引擎、向量化、Map Join）和成本优化（CBO 基于统计信息选计划）。

```text
Hive 查询优化全景：
1. 语法层 —— HiveQL 扩展：分区、复杂类型、Lateral View、SORT BY/CLUSTER BY
2. 逻辑优化 —— 谓词下推、列裁剪、常量折叠、Join 重排，减少读写量
3. 执行引擎 —— Tez 有向无环图 + 向量化 + LLAP，替代慢速 MapReduce
4. 物理优化 —— Map Join 小表广播、Skew Join 倾斜拆分、分桶 Map Join
5. 成本优化 —— CBO 依赖统计信息选择最优 Join 顺序与计划
```

## Hive SQL

HiveQL 基本兼容标准 SQL 的 SELECT/JOIN/GROUP BY/窗口函数，并有自己的扩展：分区列读写、复杂类型（ARRAY/MAP/STRUCT）、Lateral View + explode 打平数组、SORT BY（单 reducer 内排序）/DISTRIBUTE BY（按 key 分 reducer）/CLUSTER BY（前两者合并）、以及 INSERT OVERWRITE/INTO 写入语义。理解这些方言差异是写好 Hive SQL 的前提。

```text
HiveQL 与标准 SQL 的差异：
1. 复杂类型 —— ARRAY/MAP/STRUCT + Lateral View explode 打平嵌套数据
2. DISTRIBUTE BY/SORT BY —— 控制数据分发到哪个 reducer 与 reducer 内排序
3. 写入语义 —— INSERT OVERWRITE（覆盖分区）与 INSERT INTO（追加）
4. 不支持行级更新 —— 表是 append-only，更新靠重建分区（或用 ACID 事务表）
```

```sql
-- 复杂类型：解析 JSON/嵌套字段
CREATE TABLE events (
    event_id   BIGINT,
    payload    MAP<STRING,STRING>,
    tags       ARRAY<STRING>
) STORED AS PARQUET;

-- Lateral View + explode 打平数组
SELECT event_id, tag
FROM events LATERAL VIEW explode(tags) t AS tag;

-- 控制分发与排序：按 user_id 分发，reducer 内按金额降序
SELECT user_id, amount
FROM ods_orders
DISTRIBUTE BY user_id SORT BY amount DESC;

-- 覆盖写分区
INSERT OVERWRITE TABLE dwd_orders PARTITION (dt='2024-08-14')
SELECT * FROM ods_orders WHERE dt='2024-08-14';
```

## UDF/UDAF/UDTF

UDF 是 Hive 的函数扩展机制：UDF（一进一出，如大小写转换）、UDAF（多进一出，聚合）、UDTF（一进多出，如 explode 打平）。内置函数不够用时（业务专属加解密、复杂解析、自定义聚合），用 Java/Scala 写自定义函数，打成 jar 后 ADD JAR 注册。这是 Hive 可扩展性的核心。

```text
三类函数：
1. UDF —— 一行进一行出，如 parse_user_agent、脱敏、解码
2. UDAF —— 多行进一行出，自定义聚合（如中位数、分位数）
3. UDTF —— 一行进多行出，如 explode、自定义字符串切分
4. 注册方式 —— 临时函数（CREATE TEMPORARY FUNCTION，会话级）/ 永久函数（库级）
```

```java
// 自定义 UDF：字符串脱敏（保留首尾，中间打星）
import org.apache.hadoop.hive.ql.exec.UDF;

public class MaskUDF extends UDF {
    public String evaluate(String s) {
        if (s == null || s.length() <= 2) return s;
        StringBuilder sb = new StringBuilder();
        sb.append(s.charAt(0));
        for (int i = 1; i < s.length() - 1; i++) sb.append('*');
        sb.append(s.charAt(s.length() - 1));
        return sb.toString();
    }
}
```

```sql
-- 打包成 hive-mask.jar 后注册使用
ADD JAR /opt/lib/hive-mask.jar;
CREATE TEMPORARY FUNCTION mask AS 'com.example.MaskUDF';

SELECT user_id, mask(user_name) AS masked_name FROM users;
```

## 窗口函数

窗口函数在「不折叠行」的前提下做跨行计算，是 Hive 分析最常用的能力：ROW_NUMBER/RANK/DENSE_RANK 排名、SUM/AVG 运行累计、LAG/LEAD 取前后行、FIRST_VALUE/LAST_VALUE 取窗口边界。语法 OVER (PARTITION BY ... ORDER BY ... [ROWS BETWEEN ...])，其中 ROWS BETWEEN 定义物理窗口帧（如 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW）。

```text
窗口函数要点：
1. 排名三兄弟 —— ROW_NUMBER 唯一连续、RANK 并列跳号、DENSE_RANK 并列不跳号
2. 运行累计 —— SUM(...) OVER (ORDER BY ...) 默认帧是「首行到当前行」
3. LAG/LEAD —— 取前/后第 N 行，环比、留存、相邻时间差常用
4. 窗口帧 —— ROWS BETWEEN n PRECEDING AND n FOLLOWING 精确控制范围
```

```sql
-- 每个用户按金额排名，取每个用户 Top 3 订单
SELECT user_id, order_id, amount FROM (
    SELECT user_id, order_id, amount,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY amount DESC) AS rn
    FROM ods_orders
) t WHERE rn <= 3;

-- 运行累计：用户累计消费
SELECT user_id, order_id, amount,
       SUM(amount) OVER (PARTITION BY user_id ORDER BY created_at
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_amount
FROM ods_orders;

-- LAG 算相邻订单间隔
SELECT order_id, created_at,
       LAG(created_at, 1) OVER (PARTITION BY user_id ORDER BY created_at) AS prev_time
FROM ods_orders;
```

## Tez

Tez 是 Hive 的默认执行引擎（Hive 2.x 起），用有向无环图（DAG）描述作业，把 MapReduce 的多阶段（多个 job）合并成一个 DAG，中间结果尽量在内存/本地传递而不落盘，显著减少启动开销与磁盘 IO。相比 MapReduce，Tez 通常能带来 2~5 倍的性能提升，还能配合 LLAP 做常驻内存的交互式查询。

```text
Tez 要点：
1. DAG 执行 —— 一个 Tez 作业对应一个 DAG，顶点间数据边传输，避免多 job 串行
2. 少落盘 —— 中间数据用内存 + 本地磁盘缓存，减少 shuffle 写读
3. Container 复用 —— 任务在容器里复用，省去反复申请释放的开销
4. 配合 LLAP —— 常驻内存执行，秒级交互查询
```

```xml
<!-- 开启 Tez 执行引擎 -->
<configuration>
  <property>
    <name>hive.execution.engine</name>
    <value>tez</value>
  </property>
  <property>
    <name>hive.tez.container.size</name>
    <value>4096</value>
  </property>
</configuration>
```

```shell
# 会话级切换引擎
SET hive.execution.engine = tez;

# 查看查询实际用的执行引擎与进度
SET hive.tez.exec.inplace.progress = true;
```

## 向量化

向量化执行（Vectorized Execution）把「一行一行处理」改成「一批一批处理」（默认 1024 行一批），利用 CPU 的 SIMD 指令和列式存储，大幅减少函数调用与分支开销。向量化只对 ORC/Parquet 等列式格式生效，是 Hive 提速的「免费午餐」——开启即可享受，无需改 SQL。

```text
向量化要点：
1. 批量处理 —— 一次处理一批（1024 行）而非一行，减少虚函数调用
2. 依赖列式存储 —— 只对 ORC/Parquet 生效，TextFile 不支持
3. SIMD 加速 —— 利用 CPU 单指令多数据并行算多行
4. 开启方式 —— hive.vectorized.execution.enabled=true（Hive 2.x 默认已开）
```

```sql
-- 会话级开启向量化
SET hive.vectorized.execution.enabled = true;
SET hive.vectorized.execution.reduce.enabled = true;

-- 只在 ORC 表上生效；查看计划确认 vectorized
EXPLAIN SELECT COUNT(*), SUM(amount) FROM dwd_orders WHERE dt='2024-08-14';
```

## CBO

CBO（Cost-Based Optimizer，基于成本的优化器）用表的统计信息（行数、列基数、数据分布）估算各执行计划的代价，选出代价最小的计划，核心收益是自动决定最优的 Join 顺序与 Join 策略。要让 CBO 生效，必须先用 ANALYZE TABLE 收集统计信息，否则退化为基于规则的 RBO。

```text
CBO 要点：
1. 成本模型 —— 根据行数、基数、IO/CPU 代价估算每个计划的成本
2. Join 顺序 —— 自动把小结果集放前面，减少中间数据量
3. 依赖统计信息 —— 需 ANALYZE TABLE ... COMPUTE STATISTICS 采集
4. 用 Calcite —— Hive CBO 基于 Apache Calcite 实现
```

```sql
-- 收集表统计信息（行数）
ANALYZE TABLE dwd_orders COMPUTE STATISTICS;

-- 收集列统计信息（基数、分布）
ANALYZE TABLE dwd_orders COMPUTE STATISTICS FOR COLUMNS user_id, status;

-- 开启 CBO（默认已开）
SET hive.cbo.enable = true;

-- 查看 CBO 选择的执行计划
EXPLAIN SELECT o.*, p.user_name
FROM dwd_orders o JOIN dim_user p ON o.user_id = p.user_id;
```

## 谓词下推

谓词下推（Predicate Pushdown）把 WHERE 过滤条件尽量提前执行、下推到存储层，在读取数据时就过滤掉不需要的行，减少 IO 与后续处理量。配合列式存储（ORC/Parquet），还能同时做「列裁剪 + 谓词下推」，只读相关列相关行。Hive 的 ORC/Parquet 存储层原生支持把条件推给文件格式层过滤。

```text
谓词下推要点：
1. 尽早过滤 —— 条件在 Map 端 / 存储层就执行，不把脏数据传到 Reduce
2. 存储层下推 —— ORC/Parquet 用 stripe/row group 的 min-max 统计跳过整块数据
3. Join 下推 —— ON 条件能下推到子查询，减少参与 Join 的行
4. 失效场景 —— 函数包裹列、UDF、OR 条件可能阻断下推
```

```sql
-- 可下推：dt 与 status 都能在存储层过滤
SELECT order_id, amount FROM dwd_orders
WHERE dt = '2024-08-14' AND status = 'paid';

-- Join 谓词下推：先在子查询过滤再 Join，减少 shuffle 数据量
SELECT o.order_id, p.user_name
FROM (SELECT * FROM dwd_orders WHERE dt = '2024-08-14') o
JOIN dim_user p ON o.user_id = p.user_id;
```

## Map Join

Map Join（也叫 Broadcast Join）把一张小表完整加载到每个 Map 端的内存哈希表，大表在 Map 端直接查表关联，完全避免 shuffle 和 reduce 阶段。这是 Hive 最重要的 Join 优化——当一张表足够小（默认 25MB 以内）时，Hive 自动把小表广播，把昂贵的 shuffle Join 变成廉价的本地 Join。

```text
Map Join 要点：
1. 原理 —— 小表广播到所有 Mapper 内存，大表流式关联，无 shuffle
2. 阈值 —— hive.auto.convert.join.noconditionaltask.size 默认约 25MB
3. 手动指定 —— /*+ MAPJOIN(small_table) */ hint 强制小表广播
4. 适用 —— 事实表 JOIN 维表（维表通常很小），数仓最经典场景
```

```sql
-- 自动 Map Join：维表 < 25MB 时自动广播
SET hive.auto.convert.join = true;
SET hive.auto.convert.join.noconditionaltask.size = 25600000;

SELECT o.order_id, p.user_name, o.amount
FROM dwd_orders o JOIN dim_user p ON o.user_id = p.user_id;

-- 手动 hint 强制 Map Join
SELECT /*+ MAPJOIN(p) */ o.order_id, p.user_name
FROM dwd_orders o JOIN dim_user p ON o.user_id = p.user_id;
```

## Skew Join

Skew Join 解决数据倾斜：当 Join key 分布严重不均（如某几个热门 key 占了大部分数据），部分 reduce 任务被压垮。Hive 把倾斜的 key 单独抽出来做 Map Join，其余 key 正常 shuffle Join，从而均衡负载。开启后 Hive 自动检测超过阈值的倾斜 key 并拆分处理。

```text
Skew Join 要点：
1. 倾斜识别 —— 统计 key 分布，超过 hive.skewjoin.key 阈值（如 10 万行）判为倾斜
2. 拆分处理 —— 倾斜 key 单独 Map Join，非倾斜 key 走普通 Join
3. 场景 —— 热门商品、大 V、默认值（NULL/空串/0）集中导致的倾斜
4. 治本 —— 提前把 NULL/空值打散，或给 key 加随机前缀
```

```sql
-- 开启 Skew Join
SET hive.optimize.skewjoin = true;
SET hive.skewjoin.key = 100000;

SELECT o.order_id, p.user_name
FROM dwd_orders o JOIN dim_user p ON o.user_id = p.user_id;

-- 治本：NULL 键加随机后缀打散
SELECT o.order_id, p.user_name
FROM dwd_orders o JOIN dim_user p
ON (CASE WHEN o.user_id IS NULL
         THEN CONCAT('null_', CAST(RAND() * 100 AS INT))
         ELSE o.user_id END) = p.user_id;
```

## 小文件治理

小文件是 Hive 最大的性能杀手之一：大量小文件（远小于块大小）导致 NameNode 元数据膨胀、Map 任务数爆炸、每个 Mapper 启动开销大于处理开销。治理手段分事前（合并写入、控制 reducer 数、用 Concatenate）与事后（定期合并小文件），以及用 ORC/Parquet 的合并工具与 Hive 的 concatenate 命令。

```text
小文件治理要点：
1. 危害 —— 元数据膨胀 + Mapper 数爆炸 + 启动开销 > 计算开销
2. 事前 —— 控制 reducer 数、关闭动态分区过细、用桶表
3. Concatenate —— ALTER TABLE ... CONCATENATE 合并 ORC 同分区小文件
4. 事后 —— 定期用 Spark/Hive 重写分区，或 HDFS 层面合并
```

```sql
-- 合并 ORC 表某分区的小文件
ALTER TABLE dwd_orders PARTITION (dt='2024-08-14') CONCATENATE;

-- 控制写入产生的文件数
SET hive.merge.mapfiles = true;
SET hive.merge.mapredfiles = true;
SET hive.merge.smallfiles.avgsize = 16000000;
SET hive.merge.size.per.task = 256000000;

-- 重写分区合并小文件
INSERT OVERWRITE TABLE dwd_orders PARTITION (dt='2024-08-14')
SELECT * FROM dwd_orders WHERE dt='2024-08-14';
```

## 应用场景实战

### 场景一：大表 Join 维表 + 倾斜 key 优化

```sql
-- 事实表（百亿级）关联维表，经典 Map Join + 倾斜处理
SET hive.auto.convert.join = true;
SET hive.optimize.skewjoin = true;

-- 维表不算小（>25MB），手动裁剪列缩小后广播
WITH small_dim AS (
    SELECT user_id, user_name, city
    FROM dim_user WHERE city IN ('北京','上海','深圳')
)
SELECT /*+ MAPJOIN(small_dim) */ o.order_id, small_dim.user_name, o.amount
FROM dwd_orders o JOIN small_dim ON o.user_id = small_dim.user_id
WHERE o.dt = '2024-08-14';
```

### 场景二：用窗口函数构建用户 RFM 画像

```sql
-- RFM：最近消费时间（R）、消费频次（F）、消费金额（M）
WITH rfm AS (
    SELECT user_id,
           DATEDIFF('2024-08-14', MAX(created_at)) AS recency,
           COUNT(DISTINCT order_id) AS frequency,
           SUM(amount) AS monetary
    FROM dwd_orders
    WHERE dt BETWEEN '2024-05-01' AND '2024-08-14'
    GROUP BY user_id
)
SELECT user_id,
       CASE WHEN recency <= 30 THEN '高' ELSE '低' END AS r_level,
       NTILE(4) OVER (ORDER BY frequency DESC) AS f_quartile,
       NTILE(4) OVER (ORDER BY monetary DESC) AS m_quartile
FROM rfm;
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优先用 Tez 引擎 + 向量化 + ORC，三件套是 Hive 提速的基本盘
2. Join 前先过滤，谓词下推 + 列裁剪减少读写量
3. 维表 Join 事实表走 Map Join，维表超阈值时手动 hint 或裁剪列
4. 定期 ANALYZE TABLE 收集统计信息，让 CBO 有据可依
5. 窗口函数替代自关联，避免重复扫表
6. 动态分区写入控制 reducer 数，配合 merge 参数减少小文件
7. 大表按 dt 分区 + 分桶，配合分区裁剪与桶 Map Join

### 踩坑记录

```text
坑 1：小表其实不小导致 Map Join 失效
结论：以为维表小，实际超阈值，Hive 回退成 shuffle Join，跑得很慢。
原因：hive.auto.convert.join.noconditionaltask.size 默认约 25MB，超了就退化成普通 Join。
解法：确认维表实际大小，超阈值时裁剪列或调大阈值 + 给广播端加内存。

坑 2：数据倾斜导致长尾任务
结论：个别 reduce 跑几小时，其他任务几秒完成，作业被拖垮。
原因：热门 key 集中到同一 reduce，负载严重不均。
解法：开启 Skew Join；或对 NULL/空值 key 加随机前缀打散；或两阶段聚合。

坑 3：忘记收集统计信息导致 CBO 选错计划
结论：开了 CBO 但没统计信息，Join 顺序反而更差。
原因：CBO 依赖 ANALYZE TABLE 的行数与基数，没有就退化为估算。
解法：建表/导入后定期 ANALYZE TABLE ... COMPUTE STATISTICS。

坑 4：函数包裹列导致谓词下推失效
结论：WHERE year(created_at)=2024 全表扫描，比 dt 分区裁剪慢几个量级。
原因：函数破坏了列与分区/统计的映射，优化器无法下推。
解法：用裸列范围比较 WHERE dt BETWEEN '2024-01-01' AND '2024-12-31'。

坑 5：小文件爆炸拖慢整个集群
结论：ETL 后产生几十万小文件，NameNode 告警，查询 Mapper 数上万。
原因：动态分区过细 + reducer 过多，每个分区每 reducer 一个文件。
解法：合并小文件（CONCATENATE/重写），控制分区粒度与 reducer 数。
```
