## 概述

Hive 是构建在 Hadoop 之上的数据仓库工具，把结构化数据映射成表，用类 SQL 的 HiveQL 查询，底层翻译成 MapReduce/Tez/Spark 作业执行。它让不懂 Java 的分析师也能用 SQL 处理海量数据，是离线数仓的事实标准入口。表管理是 Hive 的核心——理解内部表/外部表、分区、分桶直接决定数仓的数据组织方式与查询性能。

```text
Hive 架构与表管理核心：
1. 元数据分离 —— 表结构/分区信息存 Metastore，数据存 HDFS，两者解耦
2. SQL 转作业 —— HiveQL 经解析/优化后翻译成 Tez/MR/Spark 计算作业
3. 内部表 vs 外部表 —— 管理权在 Hive 还是外部系统，决定 DROP 时数据去留
4. 分区 —— 按列值分目录存数据，是查询裁剪的第一道防线
5. 分桶 —— 按列哈希分文件，为 Map Join 与抽样提供更细粒度
```

## 核心概念

Hive 的表管理围绕 8 个核心概念展开：整体架构（Hive Architecture）、元数据中心（Metastore）、官方客户端（Beeline）、两类表（Managed/External Table）、两级数据组织（Partition 与 Bucket）、两种写入方式（静态/动态分区）、以及查询提速的关键（分区裁剪）。

### Hive Architecture

Hive 采用客户端-服务端架构：客户端（Beeline/JDBC/ODBC/Hue）提交 HiveQL，Driver 负责解析、编译、优化，生成执行计划后提交到计算引擎（Tez/MapReduce/Spark）执行。执行引擎通过 Metastore 获取表元数据，从 HDFS 读取数据，结果返回客户端。Hive 本身不存数据、不算数据，它是「翻译官 + 调度员」。

```text
Hive 架构分层：
1. 客户端层 —— Beeline/JDBC/ODBC/Hue，统一入口
2. 服务层 —— HiveServer2 提供多客户端并发访问，Driver 做编译优化
3. 元数据层 —— Metastore（Derby/MySQL/PostgreSQL）存库表分区元数据
4. 执行层 —— Tez（默认）/MapReduce/Spark 真正跑计算，LLAP 做内存加速
5. 存储层 —— HDFS/对象存储 + ORC/Parquet/TextFile 文件格式
```

```xml
<!-- hive-site.xml 关键配置：指定元数据库与执行引擎 -->
<configuration>
  <!-- Metastore 数据库连接 -->
  <property>
    <name>javax.jdo.option.ConnectionURL</name>
    <value>jdbc:mysql://metastore-host:3306/hive_meta?createDatabaseIfNotExist=true</value>
  </property>
  <property>
    <name>javax.jdo.option.ConnectionDriverName</name>
    <value>com.mysql.cj.jdbc.Driver</value>
  </property>
  <!-- 执行引擎：mr / tez / spark -->
  <property>
    <name>hive.execution.engine</name>
    <value>tez</value>
  </property>
</configuration>
```

### Metastore

Metastore 是 Hive 的元数据中心，存数据库、表、列、类型、分区、分桶、存储位置等所有「关于数据的数据」，底层用关系数据库（MySQL/PostgreSQL/Derby）持久化。计算引擎执行查询前先查 Metastore 拿到表结构和数据位置。Metastore 有三种部署模式：内嵌（Derby，单进程，仅测试）、本地（同一 JVM，共享数据库）、远程（独立 MetastoreServer，生产标配）。

```text
Metastore 要点：
1. 元数据内容 —— 库表结构、字段类型、分区键、存储格式、HDFS 路径、统计信息
2. 三种模式 —— 内嵌/本地/远程，生产必须远程独立部署供多客户端共享
3. 独立数据库 —— 生产用 MySQL/PG 主备，Derby 只能单会话、不能并发
4. 元数据 = 数据入口 —— Metastore 挂了，所有查询都无法定位数据
```

```shell
# 启动独立远程 Metastore 服务
hive --service metastore -p 9083 &

# 初始化/升级元数据库 Schema
schematool -dbType mysql -initSchema

# 连接 Metastore 查看表元数据（Beeline）
beeline -u "jdbc:hive2://localhost:10000" -e "DESCRIBE FORMATTED orders;"
```

### Beeline

Beeline 是 Hive 的官方命令行客户端，通过 JDBC 连接 HiveServer2，取代了老旧的 Hive CLI。它支持多用户并发、用户认证（Kerberos/LDAP）、嵌入模式（本地跑）与远程模式。Beeline 可执行单条 SQL（-e）、脚本文件（-f）、交互式会话，是大数据运维与调试的常用入口。

```text
Beeline 要点：
1. 取代 Hive CLI —— 老 CLI 直连 Metastore 有并发与安全问题，已废弃
2. JDBC 连接 —— 走 HiveServer2，支持认证、并发、长连接
3. 常用参数 —— -u 连接串、-e 单条、-f 脚本、--hiveconf 传配置
4. 输出格式 —— 可设 header、分隔符、静默模式，方便导出 TSV/CSV
```

```shell
# 远程连接并执行单条 SQL
beeline -u "jdbc:hive2://hive-server:10000/default" -e "SHOW TABLES;"

# 执行脚本文件（-f），并输出到文件
beeline -u "jdbc:hive2://hive-server:10000/default" -f query.sql > result.tsv

# 交互式进入，可连续执行，并传配置
beeline -u "jdbc:hive2://hive-server:10000/default" \
  --hiveconf mapreduce.job.queuename=etl
```

### Managed/External Table

内部表（Managed Table，也叫托管表）由 Hive 全权管理，数据存放在 Hive 指定的仓库目录（hive.metastore.warehouse.dir），DROP 表时元数据和数据一起删除；外部表（External Table）用 LOCATION 指定已有数据目录，Hive 只管理元数据，DROP 时只删元数据、不动数据。数仓生产基本都用外部表，避免误删数据、也方便多引擎共享同一份数据。

```text
内部表 vs 外部表：
1. 内部表 —— 数据归 Hive 管，DROP 删数据，适合临时/中间表
2. 外部表 —— LOCATION 指定路径，DROP 只删元数据，数据保留，生产首选
3. 转换 —— ALTER TABLE ... SET TBLPROPERTIES('EXTERNAL'='TRUE') 互转
4. 判断 —— DESCRIBE FORMATTED 看 Table Type：MANAGED_TABLE / EXTERNAL_TABLE
```

```sql
-- 内部表：数据由 Hive 管理
CREATE TABLE orders_managed (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2)
) STORED AS ORC;

-- 外部表：指向已有 HDFS 数据目录
CREATE EXTERNAL TABLE orders_ext (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2)
)
PARTITIONED BY (dt STRING)
STORED AS PARQUET
LOCATION '/warehouse/ods/orders';

-- 内部表转外部表
ALTER TABLE orders_managed SET TBLPROPERTIES('EXTERNAL'='TRUE');
```

### Partition

分区（Partition）按一个或多个列的值把表数据物理分散到不同子目录（如 /warehouse/orders/dt=2024-08-14/），查询时只扫描命中的分区目录，大幅减少 IO。分区列不存进数据文件，而是在目录名里体现。分区是数仓按日期（dt）、地区、业务线组织数据的标准手段，是查询提速的第一道防线。

```text
Partition 要点：
1. 物理目录 —— 每分区一个子目录，目录名形如 dt=2024-08-14
2. 分区列不落数据 —— 值只体现在目录名，查询结果由 Hive 从路径补回
3. 多级分区 —— dt + region 形成两级目录，层级别过深（小文件、元数据膨胀）
4. 分区价值 —— 配合分区裁剪，把全表扫描变成只扫几天/几目录
```

```sql
-- 建分区表，按日期 dt 分区
CREATE TABLE ods_orders (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2)
)
PARTITIONED BY (dt STRING)
STORED AS PARQUET;

-- 查看表的所有分区
SHOW PARTITIONS ods_orders;

-- 只查询某几个分区的数据
SELECT COUNT(*) FROM ods_orders WHERE dt IN ('2024-08-13','2024-08-14');
```

### Bucket

分桶（Bucket）按某列值的哈希把数据分到固定数量的文件里（如 CLUSTERED BY (user_id) INTO 16 BUCKETS），保证同 key 的数据落在同一个文件。分桶常用于：让 Join key 相同的数据在同一桶，配合 Bucket Map Join 提速；以及 TABLESAMPLE 按桶抽样。分桶是比分区更细的粒度，解决的是数据倾斜与 Join 优化问题。

```text
Bucket 要点：
1. 哈希分文件 —— 桶数固定，key 哈希对桶数取模决定落在哪个文件
2. 建桶需开启 —— 写数据前要 set hive.enforce.bucketing=true 或控制 reducer 数
3. 与分区正交 —— 分区按值分目录，分桶按哈希分文件，可叠加
4. 桶数选择 —— 通常取 2 的幂（16/32/64），避免数据倾斜
```

```sql
-- 建分桶表：按 user_id 分 16 个桶
CREATE TABLE user_orders_bucket (
    user_id    BIGINT,
    order_id   BIGINT,
    amount     DECIMAL(10,2)
)
CLUSTERED BY (user_id) INTO 16 BUCKETS
STORED AS ORC;

-- 写分桶表时强制分桶
SET hive.enforce.bucketing = true;
INSERT OVERWRITE TABLE user_orders_bucket
SELECT user_id, order_id, amount FROM ods_orders;

-- 按桶抽样：抽取约 1/16 的数据
SELECT * FROM user_orders_bucket TABLESAMPLE(BUCKET 3 OUT OF 16 ON user_id);
```

### 静态/动态分区

静态分区在 INSERT 时显式指定分区值（PARTITION (dt='2024-08-14')），适合单分区或少量固定分区；动态分区由 Hive 根据查询结果最后一列的值自动创建分区，适合一次写入多天/多地区的数据。生产 ETL 常用动态分区把明细数据按日期自动落盘，但必须配合严格模式限制，防止误建海量分区。

```text
静态 vs 动态分区：
1. 静态分区 —— 显式写死分区值，可控但繁琐，适合固定少量分区
2. 动态分区 —— 按结果集列值自动建分区，ETL 批量落盘的标配
3. 严格模式 —— hive.exec.dynamic.partition.mode=strict 要求必须有一个静态分区
4. 保护参数 —— max.dynamic.partitions 限制单次分区总数，防爆库
```

```sql
-- 静态分区写入
INSERT OVERWRITE TABLE ods_orders PARTITION (dt='2024-08-14')
SELECT order_id, user_id, amount FROM staging;

-- 动态分区：开启后按 dt 列自动落分区
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;

INSERT OVERWRITE TABLE ods_orders PARTITION (dt)
SELECT order_id, user_id, amount, dt FROM staging;
```

### 分区裁剪

分区裁剪（Partition Pruning）是查询优化器把 WHERE 里的分区列条件翻译成「只读哪几个目录」的过程，避免全表扫描。它是数仓查询提速的第一手段——只查需要的分区，几十 TB 的表也能秒级返回。前提是查询里对分区列做了过滤（=、IN、范围），且条件能下推到存储层。

```text
分区裁剪要点：
1. 原理 —— WHERE dt='2024-08-14' 只扫对应目录，不读其他分区
2. 条件形式 —— 等值/IN/范围都能裁剪，函数包裹分区列则失效（如 WHERE year(dt)=2024）
3. 与文件格式联动 —— ORC/Parquet 列式 + 分区裁剪 = 只读相关列与相关目录
4. 验证 —— EXPLAIN 看执行计划里 TableScan 是否只命中部分分区
```

```sql
-- 等值裁剪：只读一个分区目录
SELECT COUNT(*) FROM ods_orders WHERE dt = '2024-08-14';

-- 范围裁剪：只读区间内的分区
SELECT COUNT(*) FROM ods_orders
WHERE dt BETWEEN '2024-08-01' AND '2024-08-14';

-- 反例：函数包裹分区列，裁剪失效，全表扫描
SELECT COUNT(*) FROM ods_orders WHERE substr(dt,1,7) = '2024-08';

-- 查看是否裁剪
EXPLAIN SELECT COUNT(*) FROM ods_orders WHERE dt = '2024-08-14';
```

## 工作原理

Hive 的一条 SQL 从提交到返回结果，走的是「解析 -> 语义分析 -> 优化 -> 物理计划 -> 执行」的完整流水线：

```text
Hive SQL 执行流水线：
SQL 文本
  -> Parser（Antlr 解析成 AST 抽象语法树）
  -> Semantic Analyzer（查 Metastore 校验表/列，生成逻辑计划，补类型/分区信息）
  -> Optimizer（逻辑优化：分区裁剪、列裁剪、谓词下推、Join 重排）
  -> Physical Plan（翻译成 Tez/MR/Spark 的 DAG 任务）
  -> YARN 调度执行（读 HDFS 数据，算完落盘）
  -> 结果返回客户端
```

表管理的底层机制：CREATE TABLE 时 Hive 只往 Metastore 写一行元数据（表名、列、分区键、存储格式、LOCATION），HDFS 上不产生任何文件；真正写入数据（INSERT/LOAD）时才在目标目录下生成文件。所以「表」本质是「Metastore 里的元数据 + HDFS 上的文件」的映射关系，两者解耦是理解内部表/外部表的关键。

```text
表管理三件事的落点：
1. CREATE TABLE —— 只写 Metastore 元数据，HDFS 不产生文件（外部表 LOCATION 可先于表存在）
2. INSERT/LOAD —— 按存储格式在分区目录下写数据文件（内部表写 warehouse 目录，外部表写 LOCATION）
3. DROP —— 内部表删元数据 + 删 HDFS 数据；外部表只删元数据，数据保留
4. 分区落点 —— 每分区一个子目录（dt=2024-08-14）；分桶落点 —— 每桶一个文件（000000_0 ... 000015_0）
```

## 常用命令与配置

```shell
# 建表/看表/改表（Beeline 里执行）
beeline -u "jdbc:hive2://hive-server:10000/default" -e "SHOW TABLES;"
beeline -u "jdbc:hive2://hive-server:10000/default" -e "DESCRIBE FORMATTED ods_orders;"

# Metastore 运维
hive --service metastore -p 9083 &          # 独立远程 Metastore 服务
schematool -dbType mysql -initSchema        # 初始化元数据库
schematool -dbType mysql -upgradeSchema     # 升级元数据库

# HiveServer2 服务（Beeline 的连接对象）
hive --service hiveserver2 &                # 启动 HiveServer2

# 看表在 HDFS 的物理目录
hadoop fs -ls /warehouse/ods/orders
```

```text
常用配置速查（SET 会话级 / hive-site.xml 集群级）：
1. hive.execution.engine=tez —— 执行引擎（mr/tez/spark）
2. hive.metastore.uris —— 远程 Metastore 地址（thrift://host:9083）
3. hive.metastore.warehouse.dir —— 内部表仓库目录（默认 /user/hive/warehouse）
4. hive.exec.dynamic.partition=true —— 开动态分区
5. hive.exec.dynamic.partition.mode=nonstrict —— 动态分区非严格模式
6. hive.enforce.bucketing=true —— 写入时强制分桶
7. hive.optimize.bucketmapjoin=true —— 开启桶表 Map Join
```

## 配置文件解析

Hive 配置分层加载，优先级从低到高：hive-default.xml.template（内置默认）-> hive-site.xml（集群）-> SET 命令（会话）-> 命令行 --hiveconf（单次）。生产上改 hive-site.xml 统一生效，调试用 SET 临时覆盖。

```xml
<!-- hive-site.xml 核心配置 -->
<configuration>
  <!-- Metastore 元数据库连接（生产用 MySQL/PG，禁用内嵌 Derby） -->
  <property>
    <name>javax.jdo.option.ConnectionURL</name>
    <value>jdbc:mysql://meta-host:3306/hive_meta?createDatabaseIfNotExist=true</value>
  </property>
  <property>
    <name>javax.jdo.option.ConnectionDriverName</name>
    <value>com.mysql.cj.jdbc.Driver</value>
  </property>
  <property>
    <name>javax.jdo.option.ConnectionUserName</name>
    <value>hive</value>
  </property>
  <property>
    <name>javax.jdo.option.ConnectionPassword</name>
    <value>hive_pass</value>
  </property>

  <!-- 远程 Metastore 地址（独立服务模式） -->
  <property>
    <name>hive.metastore.uris</name>
    <value>thrift://meta-host:9083</value>
  </property>

  <!-- 内部表仓库目录 -->
  <property>
    <name>hive.metastore.warehouse.dir</name>
    <value>/user/hive/warehouse</value>
  </property>

  <!-- 执行引擎 -->
  <property>
    <name>hive.execution.engine</name>
    <value>tez</value>
  </property>

  <!-- HiveServer2 端口 -->
  <property>
    <name>hive.server2.thrift.port</name>
    <value>10000</value>
  </property>
</configuration>
```

```text
配置项含义：
1. 优先级 —— hive-default.xml.template < hive-site.xml < SET 会话 < --hiveconf 命令行
2. 连接类 —— javax.jdo.* 是 Metastore 连关系库的 JDBC 配置，hive.metastore.uris 是客户端连 Metastore 服务的地址
3. 仓库目录 —— warehouse.dir 只对内部表生效，外部表用建表时的 LOCATION 显式指定
4. 执行引擎 —— tez 是 DAG 计算（默认推荐），spark 需额外部署 Spark on YARN
```

## 应用场景实战

### 场景一：建 ODS 订单外部表并按日期动态分区入仓

```sql
-- 1. 建外部表，按 dt 分区，存 Parquet
CREATE EXTERNAL TABLE ods_orders (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2),
    status     STRING,
    created_at STRING
)
PARTITIONED BY (dt STRING)
STORED AS PARQUET
LOCATION '/warehouse/ods/orders';

-- 2. 从落地文件动态分区入仓
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;
SET hive.exec.max.dynamic.partitions = 1000;

INSERT OVERWRITE TABLE ods_orders PARTITION (dt)
SELECT order_id, user_id, amount, status, created_at, dt
FROM landing_orders;

-- 3. 校验分区是否生成
SHOW PARTITIONS ods_orders;
```

### 场景二：分桶表做用户订单 Join 提速

```sql
-- 1. 两张都按 user_id 分 16 桶
CREATE TABLE user_profile_bucket (
    user_id    BIGINT,
    user_name  STRING,
    city       STRING
) CLUSTERED BY (user_id) INTO 16 BUCKETS STORED AS ORC;

CREATE TABLE user_orders_bucket (
    user_id    BIGINT,
    order_id   BIGINT,
    amount     DECIMAL(10,2)
) CLUSTERED BY (user_id) INTO 16 BUCKETS STORED AS ORC;

-- 2. 写入时强制分桶，保证同 user_id 落同一桶
SET hive.enforce.bucketing = true;
INSERT OVERWRITE TABLE user_profile_bucket SELECT * FROM user_profile;
INSERT OVERWRITE TABLE user_orders_bucket SELECT * FROM ods_orders;

-- 3. 桶表 Map Join：同 key 在同一桶，无需 shuffle
SET hive.optimize.bucketmapjoin = true;
SELECT p.user_name, SUM(o.amount) AS total
FROM user_orders_bucket o
JOIN user_profile_bucket p ON o.user_id = p.user_id
GROUP BY p.user_name;
```

### 场景三：外部表挂载已有 HDFS 数据并修复分区

```sql
-- 场景：历史数据已按 dt=yyyy-mm-dd 目录躺在 HDFS，建外部表直接挂载，不搬数据
-- 已有数据目录结构：
--   /warehouse/ods/orders/dt=2024-08-13/...
--   /warehouse/ods/orders/dt=2024-08-14/...

-- 1. 建外部表，LOCATION 指向已有根目录，分区键 dt
CREATE EXTERNAL TABLE ods_orders_hist (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2)
)
PARTITIONED BY (dt STRING)
STORED AS PARQUET
LOCATION '/warehouse/ods/orders';

-- 2. 让 Metastore 识别已有分区目录（扫描目录批量补分区元数据）
MSCK REPAIR TABLE ods_orders_hist;

-- 2' 目录命名不规范（非 dt=xxx）时，手动逐分区添加
ALTER TABLE ods_orders_hist ADD PARTITION (dt='2024-08-13')
    LOCATION '/warehouse/ods/orders/dt=2024-08-13';

-- 3. 验证：分区已登记，可直接按 dt 裁剪查询
SHOW PARTITIONS ods_orders_hist;
SELECT COUNT(*) FROM ods_orders_hist WHERE dt = '2024-08-14';
```

## 性能与调优

```text
表管理层面的调优（先表设计、再查询优化）：
1. 分区裁剪 —— WHERE 命中分区才扫，数仓提速第一手段；分区列别套函数
2. 列式存储 —— ORC/Parquet 只读相关列 + 谓词下推，比 TextFile 快一个量级
3. 分桶 Map Join —— 两张桶表同 key Join 免 shuffle，set hive.optimize.bucketmapjoin=true
4. 动态分区参数 —— max.dynamic.partitions 限制单次分区数，防元数据/小文件爆炸
5. 分区粒度 —— 天级合适，小时/分钟级分区产生海量小文件拖垮 NameNode
6. 统计信息 —— ANALYZE TABLE 收集统计信息，CBO 靠它选 Join 顺序
7. 执行引擎 —— tez/spark 替代默认 MapReduce，避免每个阶段落盘
```

```sql
-- 收集表/分区统计信息，供 CBO 优化器使用
ANALYZE TABLE ods_orders PARTITION (dt='2024-08-14') COMPUTE STATISTICS;
ANALYZE TABLE ods_orders COMPUTE STATISTICS FOR COLUMNS user_id, amount;

-- 小文件合并（动态分区入仓后的常见后处理）
SET hive.merge.mapfiles = true;
SET hive.merge.mapredfiles = true;
SET hive.merge.size.per.task = 256000000;
SET hive.merge.smallfiles.avgsize = 128000000;
```

## 安全与权限

```text
Hive 安全三层（认证 -> 授权 -> 审计）：
1. 认证 —— Kerberos/LDAP 确认「你是谁」，Beeline 连 HiveServer2 时做身份认证
2. 授权 —— 控制「你能访问什么库/表/列」，SQL 标准授权或 Ranger/Sentry 集中管理
3. 审计 —— 记录访问行为，满足合规与追溯

授权实现对比：
- SQL Standard Authorization —— 基于角色（ROLE）的 GRANT/REVOKE，库/表/列粒度，配置简单
- Ranger —— 集中策略管理，支持行级过滤 + 列级脱敏（masking），策略实时下发
- Storage Based Authorization —— 依赖 HDFS 文件权限，粗粒度，不够细

Metastore 安全：
- 远程 Metastore 开启 Kerberos/SASL，不裸暴露 9083 端口
- 元数据库账号最小权限：普通用户只读、管理员可写
```

```sql
-- SQL 标准授权示例（角色 + 授权）
CREATE ROLE analyst;
GRANT SELECT ON DATABASE dw TO ROLE analyst;
GRANT ROLE analyst TO USER alice;
SHOW GRANT USER alice ON TABLE dw.dwd_orders;
```

## 故障排查

```text
排查思路：连接 -> 元数据 -> 数据目录 -> 执行计划，自外向内定位。

常见故障与定位：
1. Beeline 连不上 HiveServer2 —— 检查 HiveServer2 进程、10000 端口、认证配置（Kerberos ticket）
2. 报 Metastore 连接失败 —— 看 hive.metastore.uris、9083 端口、元数据库是否存活
3. 查询很慢/全表扫 —— EXPLAIN 看执行计划是否裁剪分区、谓词是否下推
4. 动态分区报错/全落默认分区 —— 查 strict 模式、结果集最后一列是否是分区列且非 NULL
5. 外部表查不到数据 —— 确认 LOCATION 路径、分区是否 ADD / MSCK REPAIR
6. DROP 内部表后数据没了 —— 内部表 DROP 删数据，确认是否为外部表
```

```shell
# 常用排查命令
jps                                     # 看 HiveServer2 / RunJar(metastore) 进程在不在
beeline -u "jdbc:hive2://hive:10000" -e "SHOW DATABASES;"   # 验证连接
hadoop fs -ls /user/hive/warehouse      # 看内部表仓库目录
hadoop fs -ls /warehouse/ods/orders     # 看外部表数据目录
```

## 常见问题

```text
Q1: 内部表和外部表到底怎么选？
A: 生产统一用外部表（EXTERNAL + LOCATION），DROP 只删元数据不删数据，数据可被多引擎共享、也不怕误删。内部表只用于临时/中间表。

Q2: Metastore 为什么不能用默认的 Derby？
A: Derby 是内嵌单会话数据库，不支持多客户端并发，多实例访问会报锁冲突。生产必须换 MySQL/PostgreSQL 并独立部署远程 Metastore。

Q3: 分区表的分区列为什么不能建在普通列里（不能重复定义）？
A: 分区列不落数据文件，值只体现在目录名（dt=xxx），Hive 查询时从路径补回。若再定义成普通列会语义冲突，报错「Column repeated in partitioning columns」。

Q4: 动态分区和静态分区怎么选？
A: 一次写一个/少量固定分区用静态；一次写多天/多地区用动态（ETL 批量落盘标配）。动态分区必须限制 max.dynamic.partitions，防误建海量分区。

Q5: 分区裁剪为什么对 substr(dt,1,7) 失效？
A: 裁剪靠「分区列的值 == 目录名」这个直接映射，函数包裹后列和目录名对不上，优化器无法下推，只能全表扫。改成 dt BETWEEN / dt LIKE 裸用分区列。

Q6: 分桶表为什么写入时还要强制分桶？
A: 分桶靠「key 哈希对桶数取模」决定落哪个文件，只有写入时按桶数 reducer 分文件，数据才真正按桶分布；不强制分桶则数据是散的，Bucket Map Join 和抽样都失效。

Q7: MSCK REPAIR TABLE 是什么？什么时候用？
A: 外部表指向的目录里新增了分区目录，但 Metastore 不知道，用它扫描目录批量补分区元数据。目录命名不规范（非 dt=xxx）时改用 ALTER TABLE ADD PARTITION 手动加。
```

## 面试题

```text
1. Hive 的架构包含哪几部分？各自职责？
   答：客户端（Beeline/JDBC/ODBC）、HiveServer2（多客户端并发入口）、Driver（解析/编译/优化）、Metastore（元数据，独立关系库）、执行引擎（Tez/MR/Spark）跑在 YARN 上、存储（HDFS + ORC/Parquet）。

2. 内部表和外部表的本质区别？
   答：内部表数据归 Hive 管（存 warehouse 目录），DROP 时元数据和数据一起删；外部表用 LOCATION 指向已有目录，Hive 只管元数据，DROP 只删元数据不动数据。生产用外部表。

3. 分区和分桶的区别与联系？
   答：分区按列值分目录（如 dt=2024-08-14），是查询裁剪手段；分桶按列哈希分文件（固定桶数），同 key 落同桶，为 Bucket Map Join 和抽样服务。两者正交可叠加，分区管「读哪几块」，分桶管「块内怎么排」。

4. 动态分区的执行原理？为什么要限制分区数？
   答：INSERT 时 Hive 把结果集最后一列当分区值，自动在目标表下建对应分区目录。若分区列基数大（如按 user_id 动态分区），会瞬间建几百万分区，元数据膨胀 + 海量小文件，所以要用 max.dynamic.partitions 和严格模式限制。

5. 什么是分区裁剪？什么写法会破坏它？
   答：优化器把 WHERE 里的分区列条件翻译成「只读哪几个分区目录」，避免全表扫描。分区列被函数包裹（substr(dt,...)）、隐式类型转换、或 join 后才过滤都会破坏裁剪。

6. Bucket Map Join 为什么能避免 shuffle？
   答：两张表按同一列分相同数量的桶，同 key 的数据落在相同编号的桶文件里，Join 时对应桶两两配对在 Map 端完成，无需 shuffle。前提是桶数一致、写入时强制分桶。

7. Metastore 挂了会影响什么？怎么保障？
   答：Metastore 是元数据入口，挂了所有查询都无法定位表和数据（数据本身还在 HDFS，但「看不见」）。保障：远程独立部署、MySQL/PG 主备、定期备份元数据库。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产表一律用外部表（EXTERNAL + LOCATION），DROP 不丢数据
2. 按日期 dt 做一级分区，分区粒度别过细（小时级分区慎用，防小文件与元数据膨胀）
3. Metastore 用独立 MySQL/PG 并做主备，禁用内嵌 Derby
4. 建表显式指定 STORED AS ORC/PARQUET，别用默认 TextFile
5. 动态分区开启严格模式或限制 max.dynamic.partitions，防止误建海量分区
6. 分区列查询别套函数，保持分区裁剪生效
7. 分桶表桶数选 2 的幂，且写入时强制分桶
8. 定期 ANALYZE TABLE 收集统计信息，供 CBO 选好执行计划

### 踩坑记录

```text
坑 1：DROP 内部表把数据也删了
结论：内部表 DROP 后 HDFS 数据被级联删除，数据不可恢复。
原因：内部表数据归 Hive 管理，DROP 语义是「表和数据一起删」。
解法：生产表建外部表；已建的内部表先 ALTER SET TBLPROPERTIES('EXTERNAL'='TRUE') 再操作。

坑 2：动态分区全落同一个默认分区
结论：ETL 后所有数据都进了 dt=__HIVE_DEFAULT_PARTITION__ 或直接报错。
原因：结果集里没有对应分区列，或分区列顺序/名称不对。
解法：确认 SELECT 最后一列就是分区列，且值非 NULL。

坑 3：函数包裹分区列导致全表扫描
结论：WHERE substr(dt,1,7)='2024-08' 走了全表，几十 TB 的表跑几小时。
原因：分区裁剪只在分区列「裸用」时才生效，函数破坏了列与目录的映射。
解法：改成 dt BETWEEN '2024-08-01' AND '2024-08-31' 或 dt LIKE '2024-08-%'。

坑 4：内嵌 Derby 报「另一个 Metastore 实例已锁库」
结论：多客户端并发访问时报 metastore lock 错误，无法共享。
原因：Derby 是嵌入式单会话数据库，不支持并发多连接。
解法：迁移到 MySQL/PostgreSQL 远程 Metastore。

坑 5：分区过细产生海量小文件
结论：小时级/分钟级分区导致目录与文件爆炸，NameNode 压力大、查询慢。
原因：每个分区至少一个文件，分区太细 = 文件太多。
解法：分区粒度控制在天级，小文件定期合并（见 08.2 小文件治理）。

坑 6：外部表建好却查不到数据
结论：外部表 LOCATION 指向的目录里有数据，但查询结果为空或分区报错。
原因：Metastore 没登记这些分区，Hive 不知道目录下有数据。
解法：执行 MSCK REPAIR TABLE 批量补分区，或 ALTER TABLE ADD PARTITION 手动登记。

坑 7：分桶表写入没强制分桶，桶数不对
结论：分桶表数据没按桶分布，Bucket Map Join 失效、抽样结果偏差。
原因：没开 hive.enforce.bucketing=true，写入时 reducer 数不等于桶数，数据散落。
解法：写入前 SET hive.enforce.bucketing=true，或控制 reducer 数等于桶数。
```
