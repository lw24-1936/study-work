## 概述

Hive 是构建在 Hadoop 之上的数据仓库工具，把结构化数据映射成表，用类 SQL 的 HiveQL 查询，底层翻译成 MapReduce/Tez/Spark 作业执行。它让不懂 Java 的分析师也能用 SQL 处理海量数据，是离线数仓的事实标准入口。表管理是 Hive 的核心——理解内部表/外部表、分区、分桶直接决定数仓的数据组织方式与查询性能。

```text
Hive 架构与表管理核心：
1. 元数据分离 —— 表结构/分区信息存 Metastore，数据存 HDFS，两者解耦
2. SQL 转作业 —— HiveQL 经解析/优化后翻译成 Tez/MR/Spark 计算作业
3. 内部表 vs 外部表 —— 管理权在 Hive 还是外部系统，决定 DROP 时数据去留
4. 分区 —— 按列值分目录存数据，是查询裁剪的第一道防线
5. 分桶 —— 按列哈希分文件，为 Map Join 与抽样提供更细粒度
```

## Hive Architecture

Hive 采用客户端-服务端架构：客户端（Beeline/JDBC/ODBC/Hue）提交 HiveQL，Driver 负责解析、编译、优化，生成执行计划后提交到计算引擎（Tez/MapReduce/Spark）执行。执行引擎通过 Metastore 获取表元数据，从 HDFS 读取数据，结果返回客户端。Hive 本身不存数据、不算数据，它是「翻译官 + 调度员」。

```text
Hive 架构分层：
1. 客户端层 —— Beeline/JDBC/ODBC/Hue，统一入口
2. 服务层 —— HiveServer2 提供多客户端并发访问，Driver 做编译优化
3. 元数据层 —— Metastore（Derby/MySQL/PostgreSQL）存库表分区元数据
4. 执行层 —— Tez（默认）/MapReduce/Spark 真正跑计算，LLAP 做内存加速
5. 存储层 —— HDFS/对象存储 + ORC/Parquet/TextFile 文件格式
```

```xml
<!-- hive-site.xml 关键配置：指定元数据库与执行引擎 -->
<configuration>
  <!-- Metastore 数据库连接 -->
  <property>
    <name>javax.jdo.option.ConnectionURL</name>
    <value>jdbc:mysql://metastore-host:3306/hive_meta?createDatabaseIfNotExist=true</value>
  </property>
  <property>
    <name>javax.jdo.option.ConnectionDriverName</name>
    <value>com.mysql.cj.jdbc.Driver</value>
  </property>
  <!-- 执行引擎：mr / tez / spark -->
  <property>
    <name>hive.execution.engine</name>
    <value>tez</value>
  </property>
</configuration>
```

## Metastore

Metastore 是 Hive 的元数据中心，存数据库、表、列、类型、分区、分桶、存储位置等所有「关于数据的数据」，底层用关系数据库（MySQL/PostgreSQL/Derby）持久化。计算引擎执行查询前先查 Metastore 拿到表结构和数据位置。Metastore 有三种部署模式：内嵌（Derby，单进程，仅测试）、本地（同一 JVM，共享数据库）、远程（独立 MetastoreServer，生产标配）。

```text
Metastore 要点：
1. 元数据内容 —— 库表结构、字段类型、分区键、存储格式、HDFS 路径、统计信息
2. 三种模式 —— 内嵌/本地/远程，生产必须远程独立部署供多客户端共享
3. 独立数据库 —— 生产用 MySQL/PG 主备，Derby 只能单会话、不能并发
4. 元数据 = 数据入口 —— Metastore 挂了，所有查询都无法定位数据
```

```shell
# 启动独立远程 Metastore 服务
hive --service metastore -p 9083 &

# 初始化/升级元数据库 Schema
schematool -dbType mysql -initSchema

# 连接 Metastore 查看表元数据（Beeline）
beeline -u "jdbc:hive2://localhost:10000" -e "DESCRIBE FORMATTED orders;"
```

## Beeline

Beeline 是 Hive 的官方命令行客户端，通过 JDBC 连接 HiveServer2，取代了老旧的 Hive CLI。它支持多用户并发、用户认证（Kerberos/LDAP）、嵌入模式（本地跑）与远程模式。Beeline 可执行单条 SQL（-e）、脚本文件（-f）、交互式会话，是大数据运维与调试的常用入口。

```text
Beeline 要点：
1. 取代 Hive CLI —— 老 CLI 直连 Metastore 有并发与安全问题，已废弃
2. JDBC 连接 —— 走 HiveServer2，支持认证、并发、长连接
3. 常用参数 —— -u 连接串、-e 单条、-f 脚本、--hiveconf 传配置
4. 输出格式 —— 可设 header、分隔符、静默模式，方便导出 TSV/CSV
```

```shell
# 远程连接并执行单条 SQL
beeline -u "jdbc:hive2://hive-server:10000/default" -e "SHOW TABLES;"

# 执行脚本文件（-f），并输出到文件
beeline -u "jdbc:hive2://hive-server:10000/default" -f query.sql > result.tsv

# 交互式进入，可连续执行，并传配置
beeline -u "jdbc:hive2://hive-server:10000/default" \
  --hiveconf mapreduce.job.queuename=etl
```

## Managed/External Table

内部表（Managed Table，也叫托管表）由 Hive 全权管理，数据存放在 Hive 指定的仓库目录（hive.metastore.warehouse.dir），DROP 表时元数据和数据一起删除；外部表（External Table）用 LOCATION 指定已有数据目录，Hive 只管理元数据，DROP 时只删元数据、不动数据。数仓生产基本都用外部表，避免误删数据、也方便多引擎共享同一份数据。

```text
内部表 vs 外部表：
1. 内部表 —— 数据归 Hive 管，DROP 删数据，适合临时/中间表
2. 外部表 —— LOCATION 指定路径，DROP 只删元数据，数据保留，生产首选
3. 转换 —— ALTER TABLE ... SET TBLPROPERTIES('EXTERNAL'='TRUE') 互转
4. 判断 —— DESCRIBE FORMATTED 看 Table Type：MANAGED_TABLE / EXTERNAL_TABLE
```

```sql
-- 内部表：数据由 Hive 管理
CREATE TABLE orders_managed (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2)
) STORED AS ORC;

-- 外部表：指向已有 HDFS 数据目录
CREATE EXTERNAL TABLE orders_ext (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2)
)
PARTITIONED BY (dt STRING)
STORED AS PARQUET
LOCATION '/warehouse/ods/orders';

-- 内部表转外部表
ALTER TABLE orders_managed SET TBLPROPERTIES('EXTERNAL'='TRUE');
```

## Partition

分区（Partition）按一个或多个列的值把表数据物理分散到不同子目录（如 /warehouse/orders/dt=2024-08-14/），查询时只扫描命中的分区目录，大幅减少 IO。分区列不存进数据文件，而是在目录名里体现。分区是数仓按日期（dt）、地区、业务线组织数据的标准手段，是查询提速的第一道防线。

```text
Partition 要点：
1. 物理目录 —— 每分区一个子目录，目录名形如 dt=2024-08-14
2. 分区列不落数据 —— 值只体现在目录名，查询结果由 Hive 从路径补回
3. 多级分区 —— dt + region 形成两级目录，层级别过深（小文件、元数据膨胀）
4. 分区价值 —— 配合分区裁剪，把全表扫描变成只扫几天/几目录
```

```sql
-- 建分区表，按日期 dt 分区
CREATE TABLE ods_orders (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2)
)
PARTITIONED BY (dt STRING)
STORED AS PARQUET;

-- 查看表的所有分区
SHOW PARTITIONS ods_orders;

-- 只查询某几个分区的数据
SELECT COUNT(*) FROM ods_orders WHERE dt IN ('2024-08-13','2024-08-14');
```

## Bucket

分桶（Bucket）按某列值的哈希把数据分到固定数量的文件里（如 CLUSTERED BY (user_id) INTO 16 BUCKETS），保证同 key 的数据落在同一个文件。分桶常用于：让 Join key 相同的数据在同一桶，配合 Bucket Map Join 提速；以及 TABLESAMPLE 按桶抽样。分桶是比分区更细的粒度，解决的是数据倾斜与 Join 优化问题。

```text
Bucket 要点：
1. 哈希分文件 —— 桶数固定，key 哈希对桶数取模决定落在哪个文件
2. 建桶需开启 —— 写数据前要 set hive.enforce.bucketing=true 或控制 reducer 数
3. 与分区正交 —— 分区按值分目录，分桶按哈希分文件，可叠加
4. 桶数选择 —— 通常取 2 的幂（16/32/64），避免数据倾斜
```

```sql
-- 建分桶表：按 user_id 分 16 个桶
CREATE TABLE user_orders_bucket (
    user_id    BIGINT,
    order_id   BIGINT,
    amount     DECIMAL(10,2)
)
CLUSTERED BY (user_id) INTO 16 BUCKETS
STORED AS ORC;

-- 写分桶表时强制分桶
SET hive.enforce.bucketing = true;
INSERT OVERWRITE TABLE user_orders_bucket
SELECT user_id, order_id, amount FROM ods_orders;

-- 按桶抽样：抽取约 1/16 的数据
SELECT * FROM user_orders_bucket TABLESAMPLE(BUCKET 3 OUT OF 16 ON user_id);
```

## 静态/动态分区

静态分区在 INSERT 时显式指定分区值（PARTITION (dt='2024-08-14')），适合单分区或少量固定分区；动态分区由 Hive 根据查询结果最后一列的值自动创建分区，适合一次写入多天/多地区的数据。生产 ETL 常用动态分区把明细数据按日期自动落盘，但必须配合严格模式限制，防止误建海量分区。

```text
静态 vs 动态分区：
1. 静态分区 —— 显式写死分区值，可控但繁琐，适合固定少量分区
2. 动态分区 —— 按结果集列值自动建分区，ETL 批量落盘的标配
3. 严格模式 —— hive.exec.dynamic.partition.mode=strict 要求必须有一个静态分区
4. 保护参数 —— max.dynamic.partitions 限制单次分区总数，防爆库
```

```sql
-- 静态分区写入
INSERT OVERWRITE TABLE ods_orders PARTITION (dt='2024-08-14')
SELECT order_id, user_id, amount FROM staging;

-- 动态分区：开启后按 dt 列自动落分区
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;

INSERT OVERWRITE TABLE ods_orders PARTITION (dt)
SELECT order_id, user_id, amount, dt FROM staging;
```

## 分区裁剪

分区裁剪（Partition Pruning）是查询优化器把 WHERE 里的分区列条件翻译成「只读哪几个目录」的过程，避免全表扫描。它是数仓查询提速的第一手段——只查需要的分区，几十 TB 的表也能秒级返回。前提是查询里对分区列做了过滤（=、IN、范围），且条件能下推到存储层。

```text
分区裁剪要点：
1. 原理 —— WHERE dt='2024-08-14' 只扫对应目录，不读其他分区
2. 条件形式 —— 等值/IN/范围都能裁剪，函数包裹分区列则失效（如 WHERE year(dt)=2024）
3. 与文件格式联动 —— ORC/Parquet 列式 + 分区裁剪 = 只读相关列与相关目录
4. 验证 —— EXPLAIN 看执行计划里 TableScan 是否只命中部分分区
```

```sql
-- 等值裁剪：只读一个分区目录
SELECT COUNT(*) FROM ods_orders WHERE dt = '2024-08-14';

-- 范围裁剪：只读区间内的分区
SELECT COUNT(*) FROM ods_orders
WHERE dt BETWEEN '2024-08-01' AND '2024-08-14';

-- 反例：函数包裹分区列，裁剪失效，全表扫描
SELECT COUNT(*) FROM ods_orders WHERE substr(dt,1,7) = '2024-08';

-- 查看是否裁剪
EXPLAIN SELECT COUNT(*) FROM ods_orders WHERE dt = '2024-08-14';
```

## 应用场景实战

### 场景一：建 ODS 订单外部表并按日期动态分区入仓

```sql
-- 1. 建外部表，按 dt 分区，存 Parquet
CREATE EXTERNAL TABLE ods_orders (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2),
    status     STRING,
    created_at STRING
)
PARTITIONED BY (dt STRING)
STORED AS PARQUET
LOCATION '/warehouse/ods/orders';

-- 2. 从落地文件动态分区入仓
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;
SET hive.exec.max.dynamic.partitions = 1000;

INSERT OVERWRITE TABLE ods_orders PARTITION (dt)
SELECT order_id, user_id, amount, status, created_at, dt
FROM landing_orders;

-- 3. 校验分区是否生成
SHOW PARTITIONS ods_orders;
```

### 场景二：分桶表做用户订单 Join 提速

```sql
-- 1. 两张都按 user_id 分 16 桶
CREATE TABLE user_profile_bucket (
    user_id    BIGINT,
    user_name  STRING,
    city       STRING
) CLUSTERED BY (user_id) INTO 16 BUCKETS STORED AS ORC;

CREATE TABLE user_orders_bucket (
    user_id    BIGINT,
    order_id   BIGINT,
    amount     DECIMAL(10,2)
) CLUSTERED BY (user_id) INTO 16 BUCKETS STORED AS ORC;

-- 2. 写入时强制分桶，保证同 user_id 落同一桶
SET hive.enforce.bucketing = true;
INSERT OVERWRITE TABLE user_profile_bucket SELECT * FROM user_profile;
INSERT OVERWRITE TABLE user_orders_bucket SELECT * FROM ods_orders;

-- 3. 桶表 Map Join：同 key 在同一桶，无需 shuffle
SET hive.optimize.bucketmapjoin = true;
SELECT p.user_name, SUM(o.amount) AS total
FROM user_orders_bucket o
JOIN user_profile_bucket p ON o.user_id = p.user_id
GROUP BY p.user_name;
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产表一律用外部表（EXTERNAL + LOCATION），DROP 不丢数据
2. 按日期 dt 做一级分区，分区粒度别过细（小时级分区慎用，防小文件与元数据膨胀）
3. Metastore 用独立 MySQL/PG 并做主备，禁用内嵌 Derby
4. 建表显式指定 STORED AS ORC/PARQUET，别用默认 TextFile
5. 动态分区开启严格模式或限制 max.dynamic.partitions，防止误建海量分区
6. 分区列查询别套函数，保持分区裁剪生效
7. 分桶表桶数选 2 的幂，且写入时强制分桶

### 踩坑记录

```text
坑 1：DROP 内部表把数据也删了
结论：内部表 DROP 后 HDFS 数据被级联删除，数据不可恢复。
原因：内部表数据归 Hive 管理，DROP 语义是「表和数据一起删」。
解法：生产表建外部表；已建的内部表先 ALTER SET TBLPROPERTIES('EXTERNAL'='TRUE') 再操作。

坑 2：动态分区全落同一个默认分区
结论：ETL 后所有数据都进了 dt=__HIVE_DEFAULT_PARTITION__ 或直接报错。
原因：结果集里没有对应分区列，或分区列顺序/名称不对。
解法：确认 SELECT 最后一列就是分区列，且值非 NULL。

坑 3：函数包裹分区列导致全表扫描
结论：WHERE substr(dt,1,7)='2024-08' 走了全表，几十 TB 的表跑几小时。
原因：分区裁剪只在分区列「裸用」时才生效，函数破坏了列与目录的映射。
解法：改成 dt BETWEEN '2024-08-01' AND '2024-08-31' 或 dt LIKE '2024-08-%'。

坑 4：内嵌 Derby 报「另一个 Metastore 实例已锁库」
结论：多客户端并发访问时报 metastore lock 错误，无法共享。
原因：Derby 是嵌入式单会话数据库，不支持并发多连接。
解法：迁移到 MySQL/PostgreSQL 远程 Metastore。

坑 5：分区过细产生海量小文件
结论：小时级/分钟级分区导致目录与文件爆炸，NameNode 压力大、查询慢。
原因：每个分区至少一个文件，分区太细 = 文件太多。
解法：分区粒度控制在天级，小文件定期合并（见 08.2 小文件治理）。
```
