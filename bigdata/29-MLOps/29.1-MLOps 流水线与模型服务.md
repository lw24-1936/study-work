## 概述

MLOps 把 DevOps 的自动化理念引入机器学习：用流水线把「数据 → 特征 → 训练 → 评估 → 部署 → 服务」串成可复现、可追踪、可回滚的工程链路。它解决的核心痛点：模型是「代码 + 数据 + 配置」的组合产物，只靠人工脚本无法保证可复现和可持续交付。

```text
MLOps 核心目标：
1. 可复现 —— 同样的代码 + 数据 + 参数，产出同样的模型
2. 可追踪 —— 每个模型都能回溯到训练数据、代码、配置的血缘
3. 可交付 —— 训练、评估、部署全自动，减少人工干预
4. 可回滚 —— 模型版本化，线上出问题一键回退
```

## Data Pipeline

数据流水线负责把原始数据采集、清洗、转换、落盘为可供训练与推理使用的数据集。它强调「数据即版本」——训练用的数据必须带版本快照，否则模型血缘断裂。数据流水线通常由调度器（Airflow/Dagster）驱动，产出带 schema 校验的数据集。

```text
1. 采集 —— 从数据库、消息队列、对象存储、日志抽取
2. 清洗 —— 去重、补缺、格式统一、异常值处理
3. 版本 —— 数据集打版本号，训练引用具体版本而非「最新」
```

```python
import hashlib, pandas as pd
def clean(df: pd.DataFrame) -> pd.DataFrame:
    return df.drop_duplicates(["user_id", "event_time"]).query("amount >= 0")
def register(df: pd.DataFrame, name: str) -> str:
    digest = hashlib.sha256(pd.util.hash_pandas_object(df).values).hexdigest()[:16]
    df.to_parquet(f"s3://datasets/{name}/{digest}/data.parquet")
    return f"{name}:{digest}"
print("已登记:", register(clean(pd.read_parquet("s3://raw/orders/2024-08-14.parquet")), "orders_train"))
```

## Feature Pipeline

特征流水线把原始数据加工成模型可直接消费的特征向量，是 MLOps 中最易出错的一环。核心难题是「训练-推理一致性」：离线训练用的特征计算逻辑必须与在线服务完全一致，否则出现训练/服务偏差（train/serving skew）。成熟方案是把特征计算写成共享代码，通过特征存储（Feast）统一管理。

```text
1. 特征定义 —— 特征的语义、计算逻辑、类型统一声明
2. 离线计算 —— 批式生成训练特征，落特征存储
3. 在线计算 —— 服务时实时计算/查特征存储，逻辑与离线一致
```

```python
from datetime import datetime
import pandas as pd
def compute_features(uid: int, orders: pd.DataFrame, now: datetime) -> dict:
    recent = orders[(orders["user_id"] == uid) & (orders["event_time"] <= now)]
    week = recent[recent["event_time"] >= now - pd.Timedelta(days=7)]
    return {"order_cnt_7d": len(week), "gmv_30d": float(recent["amount"].sum())}
rows = [compute_features(u, orders, datetime.now()) for u in orders["user_id"].unique()]
pd.DataFrame(rows).to_parquet("s3://features/user_features.parquet")
print("离线特征已物化")
```

## Training Pipeline

训练流水线把「加载数据 → 加载特征 → 训练 → 保存 checkpoint」自动化。它需处理超参管理、分布式训练、断点续训和产物统一保存。训练必须记录输入（数据集版本、代码 commit、超参）和输出（模型权重、指标、日志），这些元数据是后续模型管理的基础。

```text
1. 超参管理 —— 超参配置化，支持网格/贝叶斯搜索
2. 分布式训练 —— 数据并行/模型并行，多机多卡
3. 断点续训 —— checkpoint 定期保存，失败可续跑
```

```python
import torch
import torch.nn as nn
def train(data_version: str, hp: dict, commit: str) -> dict:
    model = nn.Sequential(nn.Linear(10, 64), nn.ReLU(), nn.Linear(64, 1))
    opt = torch.optim.Adam(model.parameters(), lr=hp["lr"])
    x, y, loss_fn = torch.randn(1024, 10), torch.randn(1024, 1), nn.MSELoss()
    for _ in range(hp["epochs"]):
        loss = loss_fn(model(x), y); opt.zero_grad(); loss.backward(); opt.step()
    torch.save(model.state_dict(), "s3://models/latest/model.pt")
    return {"data_version": data_version, "commit": commit, "final_loss": float(loss)}
print(train("orders_train:abc123", {"lr": 0.001, "epochs": 5}, "main@a1b2c3"))
```

## Evaluation Pipeline

评估流水线在模型上线前用「门禁」拦截不合格模型：在留出集/时间外样本上计算指标（AUC、F1、RMSE），与基线模型或业务阈值比较，达标才允许注册与部署。评估必须「防穿越」——用时间切分而非随机切分，模拟真实上线后分布。

```text
1. 评估集 —— 时间外切分（out-of-time），避免随机切分乐观估计
2. 指标 —— 分类用 AUC/F1，回归用 RMSE/MAE
3. 门禁 —— 指标阈值 + 相对基线提升率，不达标阻断发布
```

```python
from sklearn.metrics import roc_auc_score
def evaluate(y_true, y_score, baseline_auc, min_auc):
    auc = roc_auc_score(y_true, y_score)
    return {"auc": auc, "passed": auc >= min_auc and auc >= baseline_auc - 0.01}
r = evaluate([0, 1, 0, 1], [0.1, 0.9, 0.2, 0.8], baseline_auc=0.85, min_auc=0.80)
assert r["passed"], f"评估门禁未通过: {r}"
print("评估通过，允许进入注册与部署:", r)
```

## Deployment Pipeline

部署流水线把「通过评估的模型」安全发布到生产。它采用 CI/CD 思路：代码/模型变更触发构建，经测试环境验证后灰度发布，配合金丝雀（canary）和蓝绿（blue-green）策略逐步放量，出问题自动回滚。部署对象不只是一份权重，还包括依赖、运行时、服务配置的完整镜像。

```text
1. 构建 —— 模型 + 依赖 + 运行时打包成不可变镜像
2. 测试 —— 冒烟测试、推理结果对比、延迟压测
3. 灰度 —— 金丝雀放量（先 5% 流量再逐步扩大）
```

```yaml
# K8s 金丝雀发布：新版本只承接 10% 流量
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: ctr-model
spec:
  predictor:
    canaryTrafficPercent: 10
    model:
      modelFormat:
        name: pytorch
      storageUri: s3://models/ctr/v2/
```

## Model Registry

模型注册表是 ML 模型版的「制品仓库 + 目录」，集中存储模型版本、阶段（staging/production/archived）及关联元数据。它让团队能回答「线上跑的是哪个模型、哪个数据训练的、谁发布的」这类审计问题。MLflow Model Registry 是典型实现，模型进入注册表是「上线」的前置动作。

```text
1. 集中管理 —— 一个注册表统一管理全团队模型
2. 阶段标记 —— Staging（测试）/ Production（生产）/ Archived（归档）
3. 版本 —— 同一模型名下有多个版本，可对比
```

```python
import mlflow
def promote(name: str, version: str, stage: str):
    mlflow.tracking.MlflowClient().transition_model_version_stage(
        name=name, version=version, stage=stage)
version = mlflow.register_model("s3://models/ctr/v2", "ctr_model").version
promote("ctr_model", version, "Staging")     # 先到测试
promote("ctr_model", version, "Production")  # 再晋升生产
print(f"模型 ctr_model v{version} 已晋升 Production")
```

## Model Version

模型版本是模型不可变快照的标识，用于回答「哪一版模型在什么数据上训练、表现如何」。版本号应自动递增并与代码 commit、数据集版本、超参绑定。版本化让「回滚」「对比」「灰度」成为可能——没有版本就谈不上模型治理。

```text
1. 不可变 —— 版本一经发布不可覆盖，修改即产生新版本
2. 关联 —— 版本绑定代码 commit + 数据集版本 + 超参
3. 语义 —— 可用语义化版本（v1.2.0）或注册表自增序号
```

```text
模型版本三元组（可复现的关键）：
模型版本 v42 = 代码 commit a1b2c3 + 数据集版本 orders_train:abc123
             + 超参 {lr=0.001, epochs=5}
三者任一变化，都必须产生新的模型版本，否则无法复现。
```

## Artifact

Artifact（制品）是流水线各阶段产出的、需被存储和版本化的文件或包，包括模型权重、特征定义、评估报告、数据统计、依赖快照等。制品统一存放在对象存储或制品仓库，用唯一 URI 引用。把「代码之外的一切产物」都当制品管理，是 MLOps 可追溯的物理基础。

```text
1. 种类 —— 模型权重、tokenizer、特征配置、评估报告、数据 schema
2. 存储 —— 对象存储（S3/OSS）+ 制品仓库，统一 URI
3. 不可变 —— 制品发布后只读，避免被意外篡改
```

```yaml
# 一次训练运行的完整制品清单
artifacts:
  - uri: s3://models/ctr/v42/model.pt
    type: model_weights
    checksum: sha256:9f8e7d...
  - uri: s3://models/ctr/v42/eval_report.json
    type: evaluation
  - uri: s3://models/ctr/v42/requirements.lock
    type: dependency_snapshot
```

## Metadata

Metadata（元数据）是描述模型「从哪来、怎么训练、表现如何」的结构化信息，包括超参、指标、数据集版本、代码 commit、训练时长、作者、环境等。元数据通常存储在实验跟踪系统（MLflow Tracking）里，是模型血缘和审计的核心载体。

```text
1. 输入元数据 —— 数据集版本、代码 commit、超参、环境
2. 输出元数据 —— 指标、训练曲线、checkpoint 路径、耗时
3. 血缘 —— 元数据串联起「数据 -> 特征 -> 模型 -> 服务」
```

```python
import mlflow
mlflow.set_experiment("ctr_ranking")
with mlflow.start_run(run_name="ctr_v42") as run:
    mlflow.log_params({"lr": 0.001, "epochs": 5, "batch_size": 256})
    mlflow.log_metric("auc", 0.912)
    mlflow.log_param("data_version", "orders_train:abc123")
```

## Promotion

Promotion（晋升）是模型在生命周期各阶段之间流转的动作：从开发（Development）到测试（Staging）再到生产（Production），最后归档（Archived）。晋升不是简单改标签，而应绑定审批与门禁——只有通过评估、灰度验证的模型才允许晋升生产。

```text
1. 阶段流转 —— Development -> Staging -> Production -> Archived
2. 门禁绑定 —— 评估达标、灰度无异常才允许晋升
3. 审批 —— 生产晋升需人工审批或自动门禁放行
```

```python
import mlflow
def promote_with_gate(name, version, auc):
    client = mlflow.tracking.MlflowClient()
    if auc < 0.80:
        raise ValueError("AUC 未达标，禁止晋升生产")
    client.transition_model_version_stage(name=name, version=version, stage="Staging")
    client.transition_model_version_stage(name=name, version=version, stage="Production")
    print(f"{name} v{version} 已晋升生产")
promote_with_gate("ctr_model", "42", 0.912)
```

## Batch Inference

批量推理（离线推理）是对大规模历史数据一次性跑模型产出预测，结果落盘供下游使用（如全量用户打分、生成推荐候选）。它关注吞吐而非延迟，常用 Spark/分布式框架并行处理海量数据。批量推理适合离线报表、离线打分等非实时场景。

```text
1. 场景 —— 离线打分、全量用户预测、批式内容生成
2. 指标 —— 关注吞吐（每秒样本数），不苛求单条延迟
3. 框架 —— Spark / Ray / 分布式批处理
```

```python
from pyspark.sql import SparkSession
spark = SparkSession.builder.appName("batch_inference").getOrCreate()
model_path = "s3://models/ctr/v42/model.pt"
def predict(partition):
    import torch
    model = torch.jit.load(model_path)
    for row in partition:
        yield (row.user_id, float(model(torch.tensor([row.features]))[0]))
(spark.read.parquet("s3://features/user_features.parquet")
 .rdd.mapPartitions(predict).toDF(["user_id", "score"])
 .write.parquet("s3://predictions/ctr_scores/2024-08-14/"))
```

## Online Inference

在线推理（实时推理）对外提供低延迟、高可用的模型预测服务，是推荐、风控、搜索等系统的核心。它把模型常驻内存，通过 REST/gRPC 接口接收单个或小批量请求，毫秒级返回。在线推理强调延迟（P99）、吞吐、可用性（多副本、自动扩缩容）。

```text
1. 延迟 —— P99 通常要求几十毫秒以内
2. 可用 —— 多副本部署，滚动更新不中断服务
3. 弹性 —— 按流量自动扩缩容
```

```python
from fastapi import FastAPI
from pydantic import BaseModel
import torch
app = FastAPI()
model = torch.jit.load("s3://models/ctr/v42/model.pt"); model.eval()
class PredictRequest(BaseModel):
    features: list[float]
@app.post("/predict")
def predict(req: PredictRequest):
    with torch.no_grad():
        return {"score": float(model(torch.tensor([req.features]))[0])}
```

## Streaming Inference

流式推理对持续到达的数据流做实时预测，介于批量和在线之间：它要求低延迟但不一定是单请求响应，而是逐条/微批消费流数据、实时产出预测并写回下游（如实时风控、IoT 异常检测）。流式推理常与 Flink/Spark Streaming 集成，把模型封装成 UDF 调用。

```text
1. 场景 —— 实时风控、实时推荐、IoT 实时异常检测
2. 模式 —— 逐条或微批处理，延迟秒级以内
3. 集成 —— 模型作为 UDF 嵌入 Flink/Spark Streaming 作业
```

```python
from confluent_kafka import Consumer, Producer
import json, torch
model = torch.jit.load("s3://models/fraud/v7/model.pt")
c = Consumer({"bootstrap.servers": "kafka:9092", "group.id": "infer"}); c.subscribe(["txn_events"])
p = Producer({"bootstrap.servers": "kafka:9092"})
while True:
    if (msg := c.poll(1.0)) is None:
        continue
    e = json.loads(msg.value())
    risk = float(model(torch.tensor([e["features"]]))[0])
    p.produce("fraud_scores", json.dumps({"txn_id": e["txn_id"], "risk": risk}))
```

## REST/gRPC Serving

模型服务通常以 REST 或 gRPC 协议对外提供。REST 基于 HTTP/JSON，简单通用、易调试、跨语言友好，适合低并发和工具集成；gRPC 基于 HTTP/2 + Protobuf，二进制序列化、支持流式、性能更高，适合高吞吐低延迟的内部服务间调用。生产上常用 KServe/BentoML 封装，配合网关、鉴权、限流对外暴露。

```text
1. REST —— HTTP/JSON，易读易调试，跨语言，适合对外与低频
2. gRPC —— HTTP/2 + Protobuf，二进制高性能，支持流式
3. 封装 —— 用 KServe/BentoML 统一协议、指标、健康检查
```

```text
// gRPC 服务定义（Protobuf）
syntax = "proto3";
service InferenceService {
  rpc Predict(PredictRequest) returns (PredictResponse);
}
message PredictRequest { repeated float features = 1; }
message PredictResponse { float score = 1; string model_version = 2; }
```

## 应用场景实战

### 场景一：用 MLflow 搭建「训练 → 注册 → 服务」完整流水线

```python
import mlflow, mlflow.sklearn
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.metrics import roc_auc_score
from sklearn.model_selection import train_test_split
from sklearn.datasets import make_classification
X, y = make_classification(n_samples=2000, n_features=10, random_state=42)
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.2)
mlflow.set_experiment("ctr_demo")
with mlflow.start_run(run_name="gbdt_v1"):
    model = GradientBoostingClassifier().fit(X_train, y_train)
    auc = roc_auc_score(y_test, model.predict_proba(X_test)[:, 1])
    mlflow.log_metric("auc", auc)
    mlflow.sklearn.log_model(model, "model", registered_model_name="ctr_gbdt")
    c = mlflow.tracking.MlflowClient()
    v = c.get_latest_versions("ctr_gbdt")[0].version
    c.transition_model_version_stage("ctr_gbdt", v, "Production")
    print(f"模型 v{v} 已上线，AUC={auc:.3f}")
```

### 场景二：特征存储 + 批量/在线双模式推理

```text
统一特征流水线，服务两种推理模式：
Feature Pipeline（共享特征计算逻辑）
    |-- 离线物化（批式）--> s3://features/ --> 批量推理（Spark）
    |-- 在线查询（实时）--> Feast Online Store --> 在线推理（REST）
```

```python
from feast import FeatureStore
store = FeatureStore(repo_path="./feature_repo")
def online_predict(user_id: int, model) -> float:
    f = store.get_online_features(
        features=["user_stats:order_cnt_7d", "user_stats:gmv_30d"],
        entity_rows=[{"user_id": user_id}]).to_dict()
    return float(model([f["order_cnt_7d"][0], f["gmv_30d"][0]]))
store.materialize(start_date="2024-08-01", end_date="2024-08-14")
print("离线特征已物化，训练/服务特征逻辑一致")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一切皆版本：数据、特征、代码、模型四者都版本化，模型版本绑定前三者
2. 特征逻辑只写一份，离线在线复用，杜绝训练/服务偏差
3. 评估用时间外切分，防穿越，模拟真实上线分布
4. 模型晋升绑定门禁与审批，不达标禁止上线
5. 服务层统一封装（REST/gRPC），纳入网关、鉴权、限流治理
6. 制品与元数据全部落对象存储 + 注册表，保证可追溯
7. 灰度发布 + 自动回滚，线上变更永远可逆

### 踩坑记录

```text
坑 1：训练与服务特征逻辑不一致
结论：离线评估 AUC 很高，上线后效果暴跌，CTR 明显下降。
原因：离线用 pandas 算特征、在线用 SQL 另写一套，逻辑有细微差异。
解法：特征计算逻辑抽成共享代码/特征存储，离线在线复用同一份定义。
坑 2：随机切分导致评估虚高
结论：评估 AUC 0.95，上线后只有 0.7，模型被误判为优秀而发布。
原因：随机切分让未来数据泄漏进训练集，时间外切分才贴近真实。
解法：按时间切分训练/评估集，评估集必须是未来时间段。
坑 3：模型直接覆盖，无法回滚
结论：新模型出问题，发现旧权重已被覆盖，无法快速回退。
原因：模型以「latest」命名反复覆盖，没有版本化。
解法：每个模型写唯一版本 URI，注册表管理版本，回滚切版本即可。
坑 4：批量与在线延迟指标混淆
结论：用批量推理的吞吐标准衡量在线服务，上线后 P99 超时告警。
原因：没区分两类推理的优化目标（吞吐 vs 延迟）。
解法：在线服务单独做延迟压测（P99/P999），按延迟目标定副本与批大小。
```
