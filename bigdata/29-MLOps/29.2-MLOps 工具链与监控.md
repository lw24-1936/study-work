## 概述

MLOps 工具链把「模型从训练到生产」的流程工程化：MLflow 管实验追踪和模型注册，Kubeflow 管训练流水线，KServe/BentoML 管模型服务，Ray 管分布式训练，Feast 管特征存储。模型上线后的监控（延迟、吞吐、错误率、数据漂移、概念漂移、模型性能）是「模型活着」的保障——模型性能会随数据分布变化而退化，不监控就会「静默地变差」。

```text
MLOps 工具链全景：
训练 —— MLflow（实验追踪）/ Kubeflow（流水线）/ Ray（分布式训练）
特征 —— Feast（特征存储）
服务 —— KServe / BentoML（模型服务）
监控 —— 延迟/吞吐/错误率/漂移/性能
```

## Latency 延迟

延迟（Latency）是模型服务的核心指标：从请求进入到返回结果的耗时，通常看 P50/P95/P99。延迟影响用户体验，也影响系统容量。优化手段：模型推理加速（量化、TensorRT、批处理）、缓存热点结果、异步化非关键路径。监控延迟用分位数（别只看均值，慢请求会被平均淹没）。

```text
延迟监控要点：
1. 指标 —— P50/P95/P99 延迟（分位数，非均值）
2. 优化 —— 推理加速（量化/批处理）、缓存、异步
3. 告警 —— P99 超阈值告警，识别慢请求
```

```python
import time

def measure_latency(func, *args, n=100):
    latencies = []
    for _ in range(n):
        t0 = time.time()
        func(*args)
        latencies.append((time.time() - t0) * 1000)
    latencies.sort()
    return {
        "p50": latencies[n // 2],
        "p95": latencies[int(n * 0.95)],
        "p99": latencies[int(n * 0.99)],
    }

# 示例：测量某个推理函数的延迟分位
def dummy_predict():
    time.sleep(0.01)   # 模拟 10ms 推理
    return 1

print(measure_latency(dummy_predict))
```

## Throughput 吞吐

吞吐（Throughput）是「单位时间处理的请求数」（QPS/RPS）。吞吐和延迟是跷跷板——批处理能提升吞吐（一次推理多个样本），但增加单请求延迟；增加并发提升吞吐，但可能拉高延迟。优化吞吐：批处理（dynamic batching）、模型并行、多副本水平扩展。

```text
吞吐监控要点：
1. 指标 —— QPS/RPS（每秒请求数）
2. 与延迟权衡 —— 批处理提吞吐增延迟，扩副本提吞吐
3. 优化 —— 动态批处理、多副本、推理加速
```

## Error Rate 错误率

错误率（Error Rate）是「请求失败的比例」：模型服务返回错误、超时、异常。它反映服务健康度，是最基础的告警指标。错误来源：输入非法（缺字段、类型错）、模型异常（推理报错）、依赖故障（特征服务挂了）、资源耗尽（OOM）。监控错误率并区分「客户端错误（4xx）」和「服务端错误（5xx）」。

```text
错误率监控要点：
1. 指标 —— 5xx 比例（服务端错误）、4xx 比例（客户端错误）
2. 来源 —— 输入非法、模型异常、依赖故障、资源耗尽
3. 告警 —— 错误率超阈值（如 1%）告警
```

## Data Drift 数据漂移

数据漂移（Data Drift）指「模型输入特征的分布发生变化」——线上数据的分布偏离了训练数据的分布（如用户年龄结构变化、消费习惯改变）。它不一定导致性能下降，但常常是「模型退化」的前兆。检测方法：用统计检验（PSI 种群稳定指数、KS 检验）对比「训练数据」和「线上数据」的特征分布。

```text
数据漂移要点：
1. 定义 —— 输入特征分布偏离训练分布
2. 检测 —— PSI（种群稳定指数）、KS 检验、分布对比
3. 应对 —— 定期重训、特征监控告警
```

```python
import numpy as np

def psi(expected, actual, bins=10):
    """PSI 种群稳定指数，衡量两个分布差异，>0.2 说明漂移"""
    e_hist, _ = np.histogram(expected, bins=bins)
    a_hist, _ = np.histogram(actual, bins=bins)
    e_ratio = e_hist / e_hist.sum()
    a_ratio = a_hist / a_hist.sum()
    # 避免除零
    e_ratio = np.clip(e_ratio, 1e-6, 1)
    a_ratio = np.clip(a_ratio, 1e-6, 1)
    return float(np.sum((a_ratio - e_ratio) * np.log(a_ratio / e_ratio)))

train = np.random.normal(0, 1, 10000)
online = np.random.normal(0.5, 1, 10000)   # 分布偏移
print(f"PSI = {psi(train, online):.4f}（>0.2 说明漂移）")
```

## Concept Drift 概念漂移

概念漂移（Concept Drift）指「输入到输出的映射关系发生变化」——同一个输入，真实结果变了（如用户对某商品的偏好改变、欺诈模式变化）。它比数据漂移更严重（直接导致性能下降），检测更难（需要真实标签，通常有延迟）。应对：在线学习、定期重训、A/B 对比新旧模型。

```text
概念漂移要点：
1. 定义 —— X → Y 的映射关系变化（数据漂移是 X 分布变）
2. 检测 —— 监控模型性能（准确率/F1），需要真实标签
3. 应对 —— 定期重训、在线学习、滚动更新
```

```text
数据漂移 vs 概念漂移：
- 数据漂移：P(X) 变了（输入分布变化），模型可能还准
- 概念漂移：P(Y|X) 变了（映射变化），模型一定退化
```

## Model Performance 模型性能

模型性能监控是「持续追踪线上模型的业务指标」：准确率、F1、AUC、回归的 MAE/RMSE。难点是「线上缺真实标签」（预测结果要过一段时间才有真实反馈），所以常用「代理指标」（点击率、转化率、投诉率）间接衡量。性能退化是「重训」的触发信号。

```text
模型性能监控要点：
1. 指标 —— 准确率/F1/AUC（分类）、MAE/RMSE（回归）
2. 难点 —— 线上缺实时标签，用代理指标
3. 触发 —— 性能退化超阈值 → 触发重训
```

## MLflow

MLflow 是开源的 ML 生命周期管理平台，核心四组件：Tracking（记录实验参数、指标、模型）、Projects（打包可复现的代码）、Models（模型格式 + 部署）、Registry（模型注册、版本、阶段管理）。它是「实验追踪 + 模型注册」的事实标准，轻量、与框架无关，是 MLOps 的入门工具。

```text
MLflow 四组件：
1. Tracking —— 记录参数/指标/模型（实验追踪）
2. Projects —— 打包代码，可复现
3. Models —— 统一模型格式，多框架支持
4. Registry —— 模型注册、版本、阶段（staging/production）
```

```python
import mlflow

# 实验追踪
mlflow.set_experiment("churn_prediction")
with mlflow.start_run():
    mlflow.log_param("learning_rate", 0.01)
    mlflow.log_param("max_depth", 6)
    mlflow.log_metric("auc", 0.85)
    mlflow.sklearn.log_model(model, "model")   # 记录模型
# 模型注册
mlflow.register_model("runs:/<run_id>/model", "churn_model")
```

## Kubeflow

Kubeflow 是「Kubernetes 上的 MLOps 平台」，把 ML 工作流（数据准备、训练、调参、部署）用 K8s 的 CRD 编排。核心组件：Kubeflow Pipelines（DAG 编排训练流水线）、Katib（超参调优）、KF Serving（模型服务）、Notebooks（交互开发）。它适合「已经用 K8s」的团队，把 ML 流水线容器化、可编排。

```text
Kubeflow 核心组件：
1. Pipelines —— DAG 编排训练流水线（数据→训练→评估→部署）
2. Katib —— 超参调优（自动搜索）
3. KF Serving —— 模型服务（多框架）
4. Notebooks —— Jupyter 交互开发
```

## KServe

KServe 是「Kubernetes 上的标准化模型服务」，用 InferenceService CRD 定义模型服务，支持「预测 + 解释 + 转换」的组件化，内置「灰度发布（金丝雀）、自动扩缩、服务网格」。它是 KF Serving 的继任者，是 K8s 上模型服务的标准，支持多种推理框架（TensorFlow、PyTorch、ONNX、Triton）。

```text
KServe 要点：
1. InferenceService CRD —— 声明式定义模型服务
2. 组件化 —— 预测 + 解释 + 转换（可插拔）
3. 能力 —— 金丝雀、自动扩缩、服务网格
4. 框架 —— 支持 TF/PyTorch/ONNX/Triton
```

```yaml
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: churn-model
spec:
  predictor:
    model:
      storageUri: s3://models/churn
      framework: pytorch
  canaryTrafficPercent: 10   # 金丝雀 10% 流量
```

## Ray

Ray 是「分布式计算框架」，核心是「分布式任务 + Actor 模型」，用于分布式训练（Ray Train）、超参调优（Ray Tune）、强化学习（RLlib）、模型服务（Ray Serve）。它让「单机 Python 代码」几乎不改就能跑在集群上，是大模型分布式训练和 RL 的主流框架。

```text
Ray 核心组件：
1. Ray Core —— 分布式任务 + Actor（远程函数/对象）
2. Ray Train —— 分布式训练（PyTorch/TF 集成）
3. Ray Tune —— 超参调优
4. RLlib —— 强化学习
5. Ray Serve —— 模型服务
```

```python
import ray

ray.init()
@ray.remote
def train_one(seed):
    return seed * 2   # 模拟一次训练

# 并行跑多个训练任务
futures = [train_one.remote(i) for i in range(8)]
results = ray.get(futures)
print(results)
```

## Feast

Feast 是「特征存储（Feature Store）」：统一管理特征的「离线存储（历史特征，供训练）+ 在线存储（实时特征，供推理）」，保证「训练和线上用同一套特征定义」（避免训练/线上特征不一致的经典问题）。核心概念：Feature View（特征定义）、Entity（实体，如 user）、数据源（离线/在线）。

```text
Feast 要点：
1. 特征统一 —— 训练和线上用同一套特征定义（point-in-time correct）
2. 离线存储 —— 历史特征（训练用）
3. 在线存储 —— 实时特征（推理用，低延迟）
4. 解决 —— 训练/线上特征不一致的「训练-服务偏差」
```

## BentoML

BentoML 是「模型打包与服务」的轻量框架：把训练好的模型「打包成标准服务」（bento），一键部署成 REST API，支持多种框架和部署目标（Docker、K8s、Serverless）。它比 KServe 轻量（不强制 K8s），适合「快速把模型变成 API」的场景，与 MLflow 互补（MLflow 管实验、BentoML 管服务）。

```text
BentoML 要点：
1. 打包 —— 模型 + 依赖 + 代码打包成 bento
2. 服务 —— 一键生成 REST API
3. 部署 —— Docker / K8s / Serverless
4. 定位 —— 轻量模型服务（对比 KServe 的重）
```

```python
import bentoml

# 保存模型并创建服务
saved = bentoml.sklearn.save_model("churn_model", model)
runner = bentoml.sklearn.get("churn_model:latest").to_runner()
svc = bentoml.Service("churn_service", runners=[runner])

@svc.api(input=bentoml.io.JSON(), output=bentoml.io.JSON())
def predict(input_data):
    return runner.predict.run(input_data["features"])
```

## 最佳实践与踩坑记录

### 最佳实践

1. 实验追踪用 MLflow，从第一天就记录参数/指标，别等模型多了才补
2. 特征统一用 Feast，避免「训练-服务」特征不一致
3. K8s 环境用 KServe，轻量快速用 BentoML
4. 监控延迟用分位数（P99），别只看均值
5. 数据漂移用 PSI 定期检测，性能退化是重训触发信号

### 踩坑记录

```text
坑 1：训练和线上特征不一致
结论：模型上线后效果远差于离线评估。
原因：训练用了离线特征，线上用实时特征，两者口径/取值不同。
解法：用特征存储（Feast）统一特征定义，训练/线上同一套。

坑 2：只监控延迟不监控漂移
结论：模型静默退化，业务受损才发现。
原因：数据分布变化导致性能下降，但没有漂移监控。
解法：PSI 检测数据漂移 + 监控模型性能（代理指标）。

坑 3：模型注册没有版本和阶段管理
结论：不知道线上跑的是哪个版本，回滚无从下手。
原因：模型散落各处，没有 Registry 统一管理。
解法：MLflow Registry 管理版本 + 阶段（staging/production）。

坑 4：批处理提升吞吐却忘了延迟
结论：吞吐上去了，单请求延迟暴涨，用户体验差。
原因：动态批处理要等凑批，增加等待延迟。
解法：批处理大小和等待时间权衡，延迟敏感场景减小批。

坑 5：错误率告警没区分 4xx 和 5xx
结论：客户端输入错误触发大量告警，掩盖真实服务故障。
原因：把「用户输入非法（4xx）」当「服务故障（5xx）」告警。
解法：分开监控 4xx（客户端）和 5xx（服务端），只对 5xx 告警。
```
