## 概述

Docker 用「容器」替代「虚拟机」来解决环境一致性问题：它把应用及其依赖打包成不可变镜像，通过 Linux 的 Namespace 与 Cgroup 实现进程隔离与资源限制，共享宿主机内核，启动秒级、资源开销极小。容器化是大数据组件上云、CI/CD、开发测试环境标准化的基石，理解镜像、容器、卷、网络、仓库、编排六大核心即可覆盖绝大多数场景。

```text
Docker 六大核心对象
镜像(Image)：只读的构建模板，分层存储
容器(Container)：镜像的运行实例，可写层 + 生命周期
卷(Volume)：持久化数据，独立于容器生命周期
网络(Network)：容器间、容器与宿主机的通信
仓库(Registry)：镜像的存储与分发中心
编排(Compose)：多容器应用的一键定义与启动
```

## Docker 基础

Docker 采用客户端-服务端架构：`docker` CLI 通过 Unix Socket 与 `dockerd` 守护进程通信，守护进程负责拉取镜像、创建容器、管理网络等。与传统虚拟机的核心区别在于「共享内核 + 进程级隔离」，因此启动快、密度高，但隔离性弱于虚拟机。大数据场景下，Docker 常用于快速拉起 HDFS、Kafka、Spark、Flink 的本地开发集群。

```text
容器 vs 虚拟机
容器：共享宿主内核，Namespace 隔离进程，Cgroup 限制资源，秒级启动
虚拟机：每个有独立 Guest OS 内核，隔离强，分钟级启动，开销大
```

```bash
# 安装后验证 Docker 是否就绪
docker version

# 最常用命令速览
docker run -d --name nginx -p 8080:80 nginx   # 后台启动并映射端口
docker ps                                      # 查看运行中容器
docker ps -a                                   # 查看所有容器（含停止）
docker exec -it nginx bash                     # 进入容器
docker logs -f nginx                           # 跟踪日志
docker stop nginx && docker rm nginx           # 停止并删除
```

## 镜像

镜像是分层存储的只读模板，每一条 Dockerfile 指令生成一层，层与层之间共享、缓存。镜像由「仓库名:标签」唯一定位（如 `openjdk:17`），底层通过 OverlayFS 等联合文件系统叠加。构建时要把「变化频繁的层放后面」以命中缓存，并尽量精简层数减小体积。

```dockerfile
# Dockerfile 示例：Java 大数据基础镜像
FROM eclipse-temurin:17-jre
LABEL maintainer="bigdata-team"
ENV TZ=Asia/Shanghai
WORKDIR /app
# 先拷贝依赖（变化少，命中缓存）
COPY pom.xml /app/
# 再拷贝代码（变化多，放后面）
COPY target/app.jar /app/app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

```bash
# 构建并打标签
docker build -t myapp:1.0 .
# 查看镜像分层结构
docker history myapp:1.0
# 查看镜像占用空间
docker images
# 清理悬空镜像（无标签的中间层）
docker image prune
```

```text
镜像优化要点
1. 选择 Alpine/Distroless 等精简基础镜像，减小体积与攻击面
2. 用多阶段构建(multi-stage)把编译与运行分离，最终只带运行时
3. .dockerignore 排除 target/.git 等大目录，避免打进镜像
4. 层缓存：不常变的依赖先 COPY，常变的代码最后 COPY
```

```dockerfile
# 多阶段构建：Maven 构建 + 精简运行时
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

FROM eclipse-temurin:17-jre
COPY --from=build /src/target/app.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

## 容器

容器是镜像的运行实例，拥有独立的 PID、网络、挂载、UTS 等命名空间，通过 Cgroup 限制 CPU/内存。容器在镜像的只读层之上加了一层「可写层」，容器删除后该层数据即丢失，这正是要用 Volume 做持久化的原因。容器的核心操作是 `run` 的参数设计：端口映射、资源限制、环境变量、重启策略。

```bash
# 完整 run 示例：带资源限制与重启策略
docker run -d \
  --name kafka-broker \
  --restart=unless-stopped \
  --cpus=2 \
  --memory=4g \
  -p 9092:9092 \
  -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092 \
  -v /data/kafka:/var/lib/kafka/data \
  apache/kafka:3.7.0
```

```text
容器核心参数
-p 宿主:容器       端口映射，对外暴露服务
-e KEY=VALUE       环境变量，注入配置
--cpus/--memory    CPU 与内存上限（Cgroup）
--restart          重启策略：no/always/on-failure/unless-stopped
-v 宿主:容器       卷挂载，做持久化
```

```bash
# 资源监控与限制检查
docker stats kafka-broker            # 实时 CPU/内存
docker inspect kafka-broker          # 查看完整配置
```

## Volume 数据卷

Volume 把数据存在宿主机文件系统（默认 `/var/lib/docker/volumes`），独立于容器生命周期，容器删除后数据仍在。它解决了两件事：持久化（数据库/日志数据不随容器消失）与共享（多个容器读写同一份数据）。相比 `bind mount` 直接挂宿主机路径，命名卷由 Docker 管理，可移植性更好。

```bash
# 创建命名卷并挂载
docker volume create kafka-data
docker run -d --name kafka \
  -v kafka-data:/var/lib/kafka/data \
  apache/kafka:3.7.0

# bind mount：直接挂宿主机路径（开发调试常用）
docker run -d -v /opt/data:/data nginx

# 查看卷信息
docker volume ls
docker volume inspect kafka-data
```

```yaml
# 卷在 Compose 中的声明方式
services:
  kafka:
    image: apache/kafka:3.7.0
    volumes:
      - kafka-data:/var/lib/kafka/data   # 命名卷
      - ./config:/opt/kafka/config       # bind mount 配置
volumes:
  kafka-data:                             # 顶层声明命名卷
```

```text
三种数据挂载方式对比
命名卷(volume)：Docker 管理，路径不透明，生产推荐
bind mount：挂宿主绝对路径，调试方便但依赖宿主目录结构
tmpfs：内存盘，数据随容器消失，适合临时缓存
```

## Network 网络

Docker 网络让容器之间、容器与宿主机之间通信。默认 bridge 网络下容器通过 IP 互通，但更推荐「自定义 bridge 网络」——它自带 DNS，容器之间可以直接用容器名互相访问。host 网络则让容器直接共享宿主网络栈，性能最好但端口易冲突；overlay 网络用于跨主机（Swarm）通信。

```bash
# 创建自定义网络（自带 DNS，容器名即域名）
docker network create bigdata-net

# 两个容器接入同一网络，用容器名互访
docker run -d --name mysql --network bigdata-net mysql:8
docker run -d --name app --network bigdata-net myapp:1.0
# app 内可直接 ping mysql，无需知道 IP
docker exec app ping mysql
```

```text
Docker 网络模式
bridge：默认，NAT 隔离，容器间通过网关互通
host：共享宿主网络栈，性能最好，端口直接暴露
none：无网络，纯计算/离线任务
overlay：跨主机容器互通（Swarm/K8s 场景）
macvlan：给容器分配「物理网卡同网段」的独立 MAC/IP
```

```yaml
# Compose 中网络声明与引用
services:
  zookeeper:
    image: zookeeper:3.8
    networks: [bigdata-net]
  kafka:
    image: apache/kafka:3.7.0
    networks: [bigdata-net]
    environment:
      KAFKA_ZOOKEEPER_CONNECT: zookeeper:2181   # 直接用容器名
networks:
  bigdata-net:
    driver: bridge
```

```text
网络排查要点
docker network inspect bigdata-net：查看网段与已接入容器
容器互通失败先检查：是否在同一网络、是否用了容器名而非 IP
```

## Registry 镜像仓库

Registry 是镜像的存储与分发中心。Docker Hub 是默认公共仓库，企业内网通常自建 Harbor 做私有仓库，支持镜像安全扫描、签名、RBAC 权限。镜像以「仓库/镜像:标签」定位，推送前需 `docker tag` 打上仓库地址前缀，再 `docker push` 上传。

```bash
# 登录私有仓库
docker login harbor.example.com -u admin -p 'password'

# 打标签（前缀必须是仓库地址）
docker tag myapp:1.0 harbor.example.com/bigdata/myapp:1.0

# 推送与拉取
docker push harbor.example.com/bigdata/myapp:1.0
docker pull harbor.example.com/bigdata/myapp:1.0
```

```text
镜像命名与标签规范
完整名：registry/namespace/repository:tag
示例：harbor.example.com/bigdata/spark:3.5.0
tag 规范：用版本号而非 latest，latest 不可追溯、易踩坑
多平台：--platform linux/amd64,linux/arm64 构建多架构镜像
```

```bash
# 查看远程仓库中的镜像标签（需要 registry 支持）
docker manifest inspect harbor.example.com/bigdata/myapp:1.0

# 导出/导入镜像（离线环境分发）
docker save myapp:1.0 -o myapp-1.0.tar
docker load -i myapp-1.0.tar
```

```text
私有仓库选型
Harbor：CNCF 项目，支持镜像扫描、签名、RBAC、复制，企业首选
Nexus/Artifactory：同时管理 Maven 依赖与镜像的通用制品库
Docker Registry：官方最简实现，功能少但轻量
```

## Compose 编排

Compose 用一份 YAML 文件定义并启动多容器应用，解决「多个容器 + 依赖关系 + 网络 + 卷」的一键编排问题。它适合单机/开发环境的服务编排，生产级多机编排则交给 Kubernetes。Compose 文件核心是 `services`（服务）、`networks`、`volumes` 三大顶层键，用 `depends_on` 声明启动顺序。

```yaml
# docker-compose.yml：一键拉起 Zookeeper + Kafka
services:
  zookeeper:
    image: zookeeper:3.8
    container_name: zookeeper
    ports:
      - "2181:2181"
    networks: [bigdata-net]

  kafka:
    image: apache/kafka:3.7.0
    container_name: kafka
    depends_on:
      - zookeeper
    ports:
      - "9092:9092"
    environment:
      KAFKA_ZOOKEEPER_CONNECT: zookeeper:2181
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
    volumes:
      - kafka-data:/var/lib/kafka/data
    networks: [bigdata-net]

networks:
  bigdata-net:
    driver: bridge

volumes:
  kafka-data:
```

```bash
# Compose 常用命令
docker compose up -d            # 后台启动全部服务
docker compose ps               # 查看服务状态
docker compose logs -f kafka    # 跟踪某服务日志
docker compose down             # 停止并删除容器/网络
docker compose down -v          # 连卷一起删除（慎用）
docker compose up -d --build    # 重新构建并启动
```

```text
Compose 编排要点
depends_on 只保证启动顺序，不保证服务「就绪」，健康检查用 healthcheck
环境变量用 .env 文件或 environment 段注入，避免硬编码
生产多机部署不要用 Compose，升级到 Kubernetes
```

## 应用场景实战

### 场景一：本地一键拉起大数据开发集群

开发 Kafka/Spark 联调时，手动装一堆组件又慢又脏。用 Compose 定义一套 Zookeeper + Kafka + MySQL 的本地环境，一条命令起停，环境完全一致、可随时销毁重建。

```yaml
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: warehouse
    ports: ["3306:3306"]
    volumes: [mysql-data:/var/lib/mysql]
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      retries: 10

  zookeeper:
    image: zookeeper:3.8
    ports: ["2181:2181"]

  kafka:
    image: apache/kafka:3.7.0
    depends_on: [zookeeper]
    ports: ["9092:9092"]
    environment:
      KAFKA_ZOOKEEPER_CONNECT: zookeeper:2181
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: "1"

volumes:
  mysql-data:
```

```bash
# 启动、验证、销毁一条龙
docker compose up -d
docker compose ps
# 验证 Kafka 可用
docker exec kafka kafka-topics.sh --bootstrap-server localhost:9092 --list
# 用完整销毁（清理数据）
docker compose down -v
```

### 场景二：构建并部署一个 Spark 应用镜像

把 Spark 作业打成镜像，本地构建后推送到私有 Harbor，供 Kubernetes 或 Docker 环境统一部署，保证「本地跑通 = 线上一致」。

```dockerfile
# 构建 Spark 应用镜像
FROM apache/spark:3.5.0
USER root
# 拷贝依赖 jar 与作业 jar
COPY --chown=spark:spark app/target/spark-job.jar /opt/spark/jars/
COPY --chown=spark:spark app/target/lib/*.jar /opt/spark/jars/
USER spark
ENTRYPOINT ["/opt/spark/bin/spark-submit"]
```

```bash
# 构建并推送
docker build -t spark-job:1.0 .
docker tag spark-job:1.0 harbor.example.com/bigdata/spark-job:1.0
docker push harbor.example.com/bigdata/spark-job:1.0

# 本地用 Docker 直接跑 Spark 作业验证
docker run --rm --network bigdata-net \
  harbor.example.com/bigdata/spark-job:1.0 \
  --master local[4] \
  --class com.example.WarehouseJob \
  /opt/spark/jars/spark-job.jar
```

## 最佳实践与踩坑记录

### 最佳实践

1. 镜像标签永远用语义化版本（如 `1.2.0`）而非 `latest`，保证可追溯、可回滚。
2. 用多阶段构建 + 精简基础镜像，把编译与运行分离，缩小镜像体积与攻击面。
3. 所有有状态数据（数据库、日志、配置）挂 Volume，绝不留在容器可写层。
4. 容器加 `--cpus/--memory` 资源上限与 `--restart` 策略，避免失控拖垮宿主机。
5. 优先用自定义 bridge 网络 + 容器名互访，不要依赖写死的容器 IP。
6. 用 `.dockerignore` 排除 `target/.git/node_modules` 等大目录，加快构建、减小体积。
7. 大数据组件镜像要显式设置时区、编码（`TZ`、`LANG`）与 JVM 参数，避免时区/乱码问题。

### 踩坑记录

```text
坑 1：用 latest 标签导致线上版本不可控
结论：latest 指向会变，回滚时无法确定上次跑的是哪个版本
原因：latest 只是「最近一次 push」，不固定
解法：CI/CD 中用 git 提交号或语义化版本打标签

坑 2：容器内时区不对，日志时间错乱
结论：容器默认 UTC，中国区日志少 8 小时，写入数仓时间错位
原因：基础镜像未设 TZ 环境变量
解法：Dockerfile 里 ENV TZ=Asia/Shanghai 或挂 /etc/localtime

坑 3：数据写在容器可写层，删除容器数据全丢
结论：不挂 Volume 的数据库/日志，容器删除即永久丢失
原因：可写层随容器生命周期销毁
解法：所有有状态目录挂命名卷或 bind mount，定期备份卷

坑 4：容器重启后 IP 变化，配置里写死 IP 导致连不上
结论：默认 bridge 网络下容器 IP 每次重建都可能变化
原因：IP 由 Docker 动态分配，不保证稳定
解法：用自定义网络 + 容器名做 DNS 互访，不要写死 IP

坑 5：内存未设上限，大数据组件 OOM 拖垮宿主机
结论：JVM 类组件（Kafka/Spark/Flink）默认按宿主内存算堆，容易 OOM 或挤爆宿主机
原因：容器内 JVM 感知不到 Cgroup 内存限制，按宿主物理内存设置堆
解法：设 --memory 并显式 -Xmx，或用支持容器感知的 JVM 版本
```
