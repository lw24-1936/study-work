## 概述

Kubernetes（K8s）是容器编排的事实标准：它把一组容器抽象成 Pod，用控制器声明「期望状态」，控制循环持续把「实际状态」收敛到「期望状态」，实现自愈、弹性伸缩、滚动发布与服务发现。大数据领域正把 Spark、Flink、Kafka 迁到 K8s，获得统一资源调度与运维。

```text
K8s 核心抽象分层
工作负载：Pod -> Deployment / StatefulSet / DaemonSet / Job / CronJob
网络服务：Service(集群内) -> Ingress(集群外)
配置存储：ConfigMap / Secret + PVC(持久化存储)
```

```bash
kubectl get pods -n bigdata        # 查看 Pod
kubectl logs -f <pod>              # 跟踪日志
kubectl apply -f deploy.yaml       # 声明式应用配置
```

## Pod

Pod 是 K8s 调度的最小单位，一个 Pod 内可包含多个共享网络与存储命名空间的容器，通常「一主容器 + 若干 sidecar」。Pod 易逝、随时可能被重建，IP 与文件系统都不应作为持久化依据。

```text
Pod 关键概念
共享网络/存储：同 Pod 容器共享 IP 与卷，用 localhost 互通
resources：requests 是调度依据，limits 是硬上限
探针：liveness 失败重启容器；readiness 失败从 Service 摘除
```

```yaml
# pod.yaml：主容器 + 日志采集 sidecar
apiVersion: v1
kind: Pod
metadata: {name: spark-driver}
spec:
  containers:
    - name: spark
      image: apache/spark:3.5.0
      volumeMounts: [{name: log, mountPath: /var/log/spark}]
    - name: log-agent
      image: fluentd:latest
      volumeMounts: [{name: log, mountPath: /var/log/spark}]
  volumes:
    - {name: log, emptyDir: {}}
```

## Deployment

Deployment 是最常用的无状态工作负载控制器，管理一组可替换的 Pod 副本，提供滚动更新、版本回滚与水平伸缩。它通过 ReplicaSet 维护副本数量，声明 `replicas` 即可弹性扩缩。

```text
Deployment 关键点
无状态用 Deployment，有状态用 StatefulSet
滚动更新靠 readinessProbe 兜底，没探针等于「盲更新」
扩缩 kubectl scale；回滚 kubectl rollout undo
```

```yaml
# deployment.yaml：无状态应用 + 滚动更新
apiVersion: apps/v1
kind: Deployment
metadata: {name: api-server}
spec:
  replicas: 3
  selector: {matchLabels: {app: api}}
  strategy: {type: RollingUpdate}
  template:
    metadata: {labels: {app: api}}
    spec:
      containers:
        - name: api
          image: harbor.example.com/bigdata/api:1.2.0
          ports: [{containerPort: 8080}]
          readinessProbe:
            httpGet: {path: /health, port: 8080}
```

## Service

Service 为 Pod 提供稳定访问入口：Pod 的 IP 会变，但 Service 通过标签选择器把流量转发到匹配的 Pod，并提供稳定的 ClusterIP 与 DNS 名，解决服务发现与负载均衡。类型有 ClusterIP、NodePort、LoadBalancer、ExternalName 四种。

```text
Service 四种类型
ClusterIP：集群内虚拟 IP，只能内部访问（默认）
NodePort：在每台节点开端口，可外部访问
LoadBalancer：云厂商分配外部 LB，生产常用
```

```yaml
# service.yaml：ClusterIP + NodePort
apiVersion: v1
kind: Service
metadata: {name: api-server}
spec:
  type: ClusterIP
  selector: {app: api}
  ports: [{name: http, port: 8080, targetPort: 8080}]
---
apiVersion: v1
kind: Service
metadata: {name: api-nodeport}
spec:
  type: NodePort
  selector: {app: api}
  ports: [{port: 8080, targetPort: 8080, nodePort: 30080}]
```

## ConfigMap

ConfigMap 存储非敏感配置（键值对或文件），与镜像解耦，实现「同一镜像、不同环境不同配置」。应用可通过环境变量、命令行参数或挂载文件三种方式消费，挂载卷方式可热更新。

```text
ConfigMap 消费三方式
环境变量：env.valueFrom.configMapKeyRef，改配置需重启
挂载文件：volume.configMap，可热更新（kubelet 周期同步）
注意：ConfigMap 有 1MB 上限，大数据配置过大需拆分
```

```yaml
# configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata: {name: spark-conf}
data:
  spark-defaults.conf: |
    spark.executor.instances=4
    spark.executor.memory=4g
---
apiVersion: v1
kind: Pod
metadata: {name: spark-job}
spec:
  containers:
    - name: spark
      image: apache/spark:3.5.0
      envFrom:
        - configMapRef: {name: spark-conf}
      volumeMounts: [{name: conf, mountPath: /opt/spark/conf}]
  volumes:
    - {name: conf, configMap: {name: spark-conf}}
```

## Secret

Secret 与 ConfigMap 类似，但专用于敏感信息（密码、Token、证书），以 base64 编码存储（base64 只是编码不是加密）。生产环境应配合 KMS 或静态加密保护，密钥托管建议用 Vault，避免明文进 Git。

```text
Secret 安全要点
base64 只是编码非加密，需配 RBAC 限制读取
生产开启 EncryptionConfiguration 做静态加密
类型：Opaque(通用) / dockerconfigjson(拉取凭证) / tls(证书)
```

```yaml
# secret.yaml：Opaque + 镜像拉取凭证
apiVersion: v1
kind: Secret
metadata: {name: mysql-secret}
type: Opaque
data: {username: cm9vdA==, password: cGFzc3dvcmQ=}
---
apiVersion: v1
kind: Secret
metadata: {name: harbor-pull}
type: kubernetes.io/dockerconfigjson
data: {.dockerconfigjson: eyJhdXRocyI6e319}
```

## StatefulSet

StatefulSet 管理有状态应用：每个 Pod 有稳定唯一身份（`name-0`、`name-1`）与稳定存储，支持有序部署、有序扩缩容。它是部署 Kafka、Zookeeper、HDFS DataNode、数据库的核心控制器，常配合 Headless Service 提供稳定 DNS 名。

```text
StatefulSet 核心特性
稳定身份：Pod 名固定 name-0/1/2，重建后不变
稳定存储：volumeClaimTemplates 为每个 Pod 建独立 PVC
稳定网络：配合 Headless Service，每个 Pod 有固定 DNS 名
```

```yaml
# statefulset.yaml：Zookeeper 风格的有状态应用
apiVersion: v1
kind: Service
metadata: {name: zk-headless}
spec:
  clusterIP: None
  selector: {app: zk}
  ports: [{port: 2181}]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: {name: zk}
spec:
  serviceName: zk-headless
  replicas: 3
  selector: {matchLabels: {app: zk}}
  template:
    metadata: {labels: {app: zk}}
    spec:
      containers:
        - name: zk
          image: zookeeper:3.8
          volumeMounts: [{name: data, mountPath: /data}]
  volumeClaimTemplates:
    - metadata: {name: data}
      spec:
        accessModes: ["ReadWriteOnce"]
        resources: {requests: {storage: 10Gi}}
```

## DaemonSet

DaemonSet 保证「每个（或指定）节点运行一个 Pod」，节点加入自动创建、节点下线自动回收。典型用途是节点级基础设施：日志采集、监控代理、网络插件、存储插件等。

```text
DaemonSet 典型用途
日志采集：每节点一个 agent 收集容器/宿主机日志
监控代理：node-exporter 采集节点指标
特点：副本数由节点数决定，不手动指定 replicas
```

```yaml
# daemonset.yaml：每节点一个日志采集代理
apiVersion: apps/v1
kind: DaemonSet
metadata: {name: fluentd}
spec:
  selector: {matchLabels: {app: fluentd}}
  template:
    metadata: {labels: {app: fluentd}}
    spec:
      containers:
        - name: fluentd
          image: fluentd:latest
          volumeMounts: [{name: varlog, mountPath: /var/log}]
      volumes:
        - {name: varlog, hostPath: {path: /var/log}}
```

## Job

Job 运行「一次性、跑完即退」的任务，保证指定数量的 Pod 成功完成，适合离线计算、数据迁移、批处理等有明确结束的负载，支持并行度控制与失败重试。

```text
Job 关键参数
completions：要成功完成的总次数；parallelism：并行 Pod 数
backoffLimit：失败重试上限，超过则 Job 标记失败
restartPolicy：Job 内只能是 Never 或 OnFailure
```

```yaml
# job.yaml：一次性数据迁移任务
apiVersion: batch/v1
kind: Job
metadata: {name: data-migrate}
spec:
  backoffLimit: 3
  completions: 1
  parallelism: 1
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: migrate
          image: harbor.example.com/bigdata/migrate:1.0
          args: ["--from", "mysql", "--to", "hive"]
```

## CronJob

CronJob 在 Job 之上叠加定时调度，用标准 Cron 表达式（分 时 日 月 周）周期性创建 Job，典型用途是定时 ETL、每日报表、定期清理。需用 startingDeadlineSeconds 与 concurrencyPolicy 控制「错过」与「重叠」。

```text
Cron 表达式（分 时 日 月 周）
"0 2 * * *"     每天 02:00
"*/15 * * * *"  每 15 分钟
concurrencyPolicy：Forbid 防重叠，Replace 用新任务替换旧任务
```

```yaml
# cronjob.yaml：每天凌晨 2 点跑离线 ETL
apiVersion: batch/v1
kind: CronJob
metadata: {name: daily-etl}
spec:
  schedule: "0 2 * * *"
  startingDeadlineSeconds: 300
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: etl
              image: harbor.example.com/bigdata/etl:2.0
```

## PVC

PVC（PersistentVolumeClaim）是「存储申请单」，用户声明容量与访问模式，由 PV（PersistentVolume）绑定。PVC 与 Pod 生命周期解耦，配合 StorageClass 可实现按需动态创建云盘/NFS，是大数据组件落盘的关键。

```text
PVC/PV/StorageClass 关系
PV：集群级存储资源（云盘、NFS、本地盘）
PVC：用户申请，绑定合适的 PV；StorageClass 动态供给
访问模式：RWO 单节点 / ROX 多节点只读 / RWX 多节点读写
```

```yaml
# pvc.yaml：申请 20Gi 并挂载到 Pod
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: kafka-data}
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: fast-ssd
  resources: {requests: {storage: 20Gi}}
---
apiVersion: v1
kind: Pod
metadata: {name: kafka}
spec:
  containers:
    - name: kafka
      image: apache/kafka:3.7.0
      volumeMounts: [{name: data, mountPath: /var/lib/kafka/data}]
  volumes:
    - {name: data, persistentVolumeClaim: {claimName: kafka-data}}
```

## Ingress

Ingress 是集群的七层入口，把集群外 HTTP/HTTPS 流量按域名与路径路由到集群内 Service，统一管理 TLS 证书与路由规则。它需要一个 Ingress Controller（Nginx Ingress、Traefik）来实际执行规则。

```text
Ingress 关键点
Ingress 只是规则，真正干活的是 Ingress Controller
域名 -> 规则路由，路径 -> 后端 Service
TLS 终止、限流、灰度由 Controller 的 annotation 控制
```

```yaml
# ingress.yaml：按路径路由到不同服务
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations: {nginx.ingress.kubernetes.io/rewrite-target: /}
spec:
  ingressClassName: nginx
  tls: [{hosts: [api.example.com], secretName: tls-secret}]
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend: {service: {name: api-server, port: {number: 8080}}}
```

## 应用场景实战

### 场景一：把 Flink 作业部署到 K8s

将 Flink 实时作业以 Application 模式跑在 K8s 上，用 ConfigMap 管配置、Secret 管凭证、PVC 存 Checkpoint，实现作业容器化统一调度。

```yaml
# flink-job.yaml：Flink 作业部署清单（简化）
apiVersion: batch/v1
kind: Job
metadata: {name: flink-realtime-job}
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: flink
          image: harbor.example.com/bigdata/flink:1.18
          args: ["run-application", "-t", "kubernetes-application", "/opt/flink/job.jar"]
          env:
            - name: KAFKA_PASSWORD
              valueFrom: {secretKeyRef: {name: kafka-secret, key: password}}
          volumeMounts:
            - {name: conf, mountPath: /opt/flink/conf}
            - {name: checkpoint, mountPath: /opt/flink/checkpoint}
      volumes:
        - {name: conf, configMap: {name: flink-conf}}
        - {name: checkpoint, persistentVolumeClaim: {claimName: flink-checkpoint}}
```

```bash
kubectl apply -f flink-job.yaml
kubectl logs -f job/flink-realtime-job
```

### 场景二：部署高可用 Kafka 集群

用 StatefulSet + Headless Service + PVC 部署 3 节点 Kafka，保证稳定身份与数据持久化（生产建议直接使用 Strimzi Operator）。

```yaml
apiVersion: v1
kind: Service
metadata: {name: kafka-headless}
spec:
  clusterIP: None
  selector: {app: kafka}
  ports: [{port: 9092}]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: {name: kafka}
spec:
  serviceName: kafka-headless
  replicas: 3
  selector: {matchLabels: {app: kafka}}
  template:
    metadata: {labels: {app: kafka}}
    spec:
      containers:
        - name: kafka
          image: apache/kafka:3.7.0
          env: [{name: KAFKA_ADVERTISED_LISTENERS, value: "PLAINTEXT://kafka-0.kafka-headless:9092"}]
          volumeMounts: [{name: data, mountPath: /var/lib/kafka/data}]
  volumeClaimTemplates:
    - metadata: {name: data}
      spec:
        accessModes: ["ReadWriteOnce"]
        resources: {requests: {storage: 50Gi}}
```

```text
Kafka 上 K8s 的核心难点
1. 广播地址要用稳定 DNS 名（kafka-0.kafka-headless）
2. 副本同步与磁盘扩容依赖 Operator（Strimzi）才完善
```

## 最佳实践与踩坑记录

### 最佳实践

1. 所有工作负载都设 `resources.requests/limits`，requests 是调度依据，limits 防失控。
2. 无状态用 Deployment，有状态用 StatefulSet，一次性任务用 Job，定时任务用 CronJob。
3. 每个容器都配 `readinessProbe` 与 `livenessProbe`，滚动更新与自愈都依赖探针。
4. 配置与镜像解耦：非敏感用 ConfigMap，敏感用 Secret，禁止把密钥写进镜像或 Git。
5. Service 用 ClusterIP 做内部访问，对外统一走 Ingress，避免滥用 NodePort。
6. 有状态数据一律走 PVC + StorageClass 动态供给，绝不用 emptyDir 存持久数据。
7. 用命名空间 + RBAC 做资源与权限隔离，大数据集群与业务应用分开。

### 踩坑记录

```text
坑 1：没配探针导致滚动更新「假成功」
结论：Pod 起来但服务未就绪，流量已切入，请求失败
原因：Deployment 只看容器进程状态，不看应用是否 ready
解法：加 readinessProbe，未就绪的 Pod 不会加入 Service endpoints

坑 2：把持久数据写进 emptyDir 或容器层
结论：Pod 重建后数据全丢，导致 Kafka 数据、Checkpoint 丢失
原因：emptyDir 与容器可写层都随 Pod/容器销毁
解法：持久数据挂 PVC，且用 StatefulSet 保证稳定存储

坑 3：Secret 用 base64 就以为安全了
结论：base64 只是编码，任何人可解码，等于明文
原因：误解 base64 为加密，且默认静态存储未加密
解法：配 RBAC 限制读取 + 开启静态加密 + 用 Vault 托管

坑 4：CronJob 任务重叠导致数据重复计算
结论：上一个任务没跑完，新任务又启动，重复写数仓
原因：默认 concurrencyPolicy=Allow，允许并发
解法：设 concurrencyPolicy: Forbid 或 Replace，保证不重叠

坑 5：StatefulSet 删除 Pod 时误以为永久下线
结论：StatefulSet 删除 Pod 会按模板自动重建，不是真正删除
原因：控制器持续调谐，Pod 少了就会补
解法：要下线需 scale 副本数或删除整个 StatefulSet
```
