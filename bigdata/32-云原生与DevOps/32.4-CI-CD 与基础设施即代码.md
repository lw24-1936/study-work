## 概述

CI/CD 解决「代码改动如何安全、自动地到达生产」的问题：CI（持续集成）在每次提交后自动构建、测试、打包；CD（持续交付/部署）把通过验证的产物自动部署到环境。基础设施即代码（IaC）则把服务器、网络、集群等基础设施用代码描述、版本化、可复现地创建。两者合起来，让大数据平台从「手工运维」走向「代码化、自动化、可审计」的工程实践。

```text
CI/CD 与 IaC 的核心价值：
1. 自动化 —— 提交即触发构建测试部署，减少人工介入
2. 可复现 —— 环境由代码描述，任意时刻可重建一致的集群
3. 可审计 —— 每次变更可追溯（谁改了什么、为什么改）
4. 快速交付 —— 变更小步快跑，降低单次发布风险
5. 一致性 —— 测试、预发、生产环境同构，避免「我本地没问题」
```

```text
三者分工（CI/CD + IaC 全景）：
代码仓库（Git） --push--> CI 流水线（GitHub Actions/GitLab CI/Jenkins）
    |-- 构建镜像 --> 镜像仓库
    |-- 跑测试 --> 质量门禁
    |-- 打包 Helm Chart / 触发 Terraform --> CD 部署
基础设施（K8s 集群/云资源） <-- Terraform 声明云资源 / Helm 部署应用 / Ansible 配置机器
```

## GitHub Actions

GitHub Actions 是 GitHub 内置的 CI/CD 服务，用 YAML 文件（放在 `.github/workflows/` 下）声明工作流。工作流由「事件（push/PR/定时）」触发，由「job → step」组成，每个 step 可以是 shell 命令或复用 action（如 checkout、docker/login、setup-java）。它托管运行、无需自建服务器，是开源项目和中小团队的首选。

```text
GitHub Actions 要点：
1. 触发 —— push、pull_request、schedule（定时）、workflow_dispatch（手动）
2. 结构 —— workflow（YAML 文件）-> job（可并行）-> step（顺序执行）
3. action —— 复用社区动作，如 actions/checkout、actions/setup-java
4. Runner —— GitHub 托管或自托管（self-hosted），自托管可连内网
5. 缓存 —— actions/cache 缓存依赖，加速构建
```

```yaml
# .github/workflows/ci.yml —— 提交即构建 Spark 作业并跑测试
name: Spark Job CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 安装 JDK 与 Maven
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "11"
          cache: maven

      - name: 编译打包
        run: mvn -q clean package -DskipTests

      - name: 单元测试
        run: mvn -q test

      - name: 构建镜像并推送
        run: |
          docker build -t registry.example.com/spark-job:${{ github.sha }} .
          echo "${{ secrets.REGISTRY_PASSWORD }}" | docker login registry.example.com -u robot --password-stdin
          docker push registry.example.com/spark-job:${{ github.sha }}
```

## GitLab CI

GitLab CI 是 GitLab 内置的 CI/CD，配置写在仓库根目录的 `.gitlab-ci.yml`。它由 GitLab Runner 执行（可装在任意机器/容器上），用 `stages` 组织流水线阶段，`jobs` 定义具体任务，`variables`/`cache`/`artifacts` 管理变量、缓存与产物传递。相比 GitHub Actions，它私有化部署更成熟，企业内网常用。

```text
GitLab CI 要点：
1. 配置 —— 仓库根 .gitlab-ci.yml，stages 定义阶段顺序
2. Runner —— 需自行注册 GitLab Runner，支持 Docker/Shell/K8s executor
3. artifacts —— 阶段间产物传递（如构建出的 jar 传给部署阶段）
4. cache —— 依赖缓存，加速后续构建
5. 环境 —— environments 关联部署目标，配合审批与回滚
```

```yaml
# .gitlab-ci.yml —— 构建、测试、部署三段流水线
stages:
  - build
  - test
  - deploy

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"

cache:
  paths:
    - .m2/repository

build:
  stage: build
  image: maven:3.8-openjdk-11
  script:
    - mvn clean package -DskipTests
  artifacts:
    paths:
      - target/*.jar
    expire_in: 1 day

test:
  stage: test
  image: maven:3.8-openjdk-11
  script:
    - mvn test
  artifacts:
    reports:
      junit: target/surefire-reports/*.xml

deploy:
  stage: deploy
  image: docker:24
  services:
    - docker:24-dind
  script:
    - docker build -t registry.example.com/spark-job:$CI_COMMIT_SHA .
    - docker push registry.example.com/spark-job:$CI_COMMIT_SHA
  only:
    - main
```

## Jenkins

Jenkins 是历史最久的开源 CI/CD 服务器，需要自建和运维。它的核心是「流水线（Pipeline）」——用 Jenkinsfile（声明式/脚本式 DSL）把构建过程写成代码，存储在仓库里。插件生态极其丰富（数千个插件），适合需要深度定制、对接各种遗留系统的场景。缺点是运维成本高、UI 老旧，新项目往往转向 GitHub Actions/GitLab CI。

```text
Jenkins 要点：
1. 自建 —— 需自备 Jenkins master + agent（支持静态/动态 agent）
2. Pipeline —— Jenkinsfile 声明式 DSL，pipeline 即代码
3. 插件 —— 生态最丰富，几乎能对接任何工具
4. 触发 —— SCM 轮询、webhook、定时、手动
5. 选型 —— 深度定制/遗留系统用 Jenkins，新项目优先托管型 CI
```

```text
Jenkinsfile 声明式流水线结构（语言为 Groovy DSL）：
pipeline {
    agent any
    stages {
        stage('Checkout') { steps { git 'https://git.example.com/spark-job.git' } }
        stage('Build')    { steps { sh 'mvn clean package -DskipTests' } }
        stage('Test')     { steps { sh 'mvn test' } }
        stage('Deploy')   { steps { sh 'docker build -t spark-job . && docker push spark-job' } }
    }
    post {
        failure { mail to: 'team@example.com', subject: '构建失败' }
    }
}
```

## Terraform

Terraform 是 HashiCorp 的 IaC 工具，用声明式 HCL 语言描述云资源（虚拟机、VPC、对象存储、K8s 集群），执行 `terraform apply` 把现实环境对齐到代码描述的状态。它维护 state 文件记录资源与代码的映射，支持 plan（预览变更）和依赖图自动编排。核心优势是跨云（AWS/Azure/GCP/阿里云一个语法）和不可变基础设施。

```text
Terraform 要点：
1. 声明式 —— HCL 描述目标状态，Terraform 计算差异并收敛
2. state —— 记录资源与代码映射，是 plan/apply 的基础，需安全存放
3. plan/apply —— plan 预览变更，apply 落地，destroy 销毁
4. provider —— 每个云/平台一个 provider 插件，跨云统一语法
5. 模块 —— 把资源组织成可复用 module，团队共享
```

```text
# main.tf —— 声明对象存储桶 + K8s 集群（示意）
provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "data_lake" {
  bucket = "bigdata-lake"
}

resource "aws_eks_cluster" "bigdata" {
  name     = "bigdata-cluster"
  role_arn = aws_iam_role.eks.arn
  vpc_config {
    subnet_ids = [aws_subnet.private_a.id, aws_subnet.private_b.id]
  }
}
```

```bash
# Terraform 核心工作流
terraform init            # 初始化 provider 与后端
terraform plan            # 预览即将产生的变更
terraform apply -auto-approve   # 应用变更
terraform destroy         # 销毁全部资源
```

## Helm

Helm 是 Kubernetes 的包管理器，把一组 K8s 资源（Deployment/Service/ConfigMap 等）打包成 Chart，用 `values.yaml` 参数化。它解决「同一套应用在不同环境（dev/staging/prod）如何复用部署」的问题——Chart 是模板，values 是差异，一套 Chart 多套 values 即可部署多个环境。大数据组件（Spark/Flink/Kafka/Trino/Airflow）几乎都有官方 Helm Chart。

```text
Helm 要点：
1. Chart —— 打包一组 K8s 资源 + 模板 + 默认值
2. 模板 —— 用 Go template 语法，values 注入生成最终 YAML
3. 版本 —— helm upgrade 滚动升级，helm rollback 回滚
4. 仓库 —— Helm repo 发布/拉取 Chart，共享复用
5. 分层 —— 大团队可用 umbrella chart 组织多组件
```

```yaml
# values.yaml —— 同一 Chart 的差异化配置
replicaCount: 3
image:
  repository: apache/trino
  tag: "455"
service:
  type: ClusterIP
  port: 8080
resources:
  limits:
    cpu: "2"
    memory: "4Gi"
```

```bash
# 部署、升级、回滚一条龙
helm repo add trino https://trinodb.github.io/charts
helm install trino trino/trino --namespace bigdata -f values.yaml
helm upgrade trino trino/trino -f values.yaml --namespace bigdata
helm rollback trino 1 --namespace bigdata   # 回滚到第 1 个版本
helm uninstall trino --namespace bigdata
```

## Ansible

Ansible 是无 agent 的配置管理与编排工具，用 YAML 编写 playbook，通过 SSH 在目标机器上执行任务。它声明「机器应该处于什么状态」（装什么包、起什么服务、改什么配置），幂等地把机器收敛到该状态。适合配置裸机/虚拟机、初始化组件依赖，与 Terraform 互补——Terraform 管资源创建，Ansible 管资源上机的软件配置。

```text
Ansible 要点：
1. 无 agent —— 通过 SSH 执行，目标机无需装客户端
2. playbook —— YAML 描述任务（tasks）与目标主机（hosts）
3. 幂等 —— 模块设计幂等，重复执行结果一致
4. inventory —— 主机清单，定义分组与变量
5. 分工 —— Terraform 建资源，Ansible 配软件，常组合使用
```

```yaml
# playbook.yaml —— 初始化一批 Kafka 机器
- hosts: kafka_servers
  become: true
  vars:
    kafka_version: "3.7.0"
  tasks:
    - name: 安装 JDK
      apt:
        name: openjdk-11-jdk
        state: present
    - name: 创建 kafka 用户
      user:
        name: kafka
        create_home: false
    - name: 下载并解压 Kafka
      unarchive:
        src: "https://downloads.apache.org/kafka/{{ kafka_version }}/kafka_2.13-{{ kafka_version }}.tgz"
        dest: /opt
        remote_src: true
        creates: "/opt/kafka_2.13-{{ kafka_version }}"
    - name: 配置 server.properties
      template:
        src: server.properties.j2
        dest: /opt/kafka_2.13-{{ kafka_version }}/config/server.properties
    - name: 启动 Kafka
      systemd:
        name: kafka
        state: started
        enabled: true
```

```bash
# 执行 playbook
ansible-playbook -i inventory.ini playbook.yaml

# 检查某台机器状态（ad-hoc 模式）
ansible kafka_servers -i inventory.ini -m ping
```

## 应用场景实战

### 场景一：从代码提交到 Spark 作业上 K8s 的完整 CI/CD

```text
开发者 push 代码
  -> GitHub Actions 触发：编译 + 测试 + 构建镜像 + 推送镜像仓库
  -> 触发 CD：更新 Helm values 里的镜像 tag
  -> Helm upgrade 滚动更新 K8s 上的 Spark/Flink 作业
  -> 失败自动 rollback，并通知告警
```

```yaml
# 完整 CD 工作流：构建镜像 -> 部署到 K8s
name: Deploy to K8s

on:
  push:
    tags: ["v*"]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 构建并推送镜像
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: registry.example.com/spark-job:${{ github.ref_name }}

      - name: 部署到 K8s
        uses: azure/k8s-set-context@v3
        with:
          method: kubeconfig
          kubeconfig: ${{ secrets.KUBECONFIG }}

      - name: Helm 升级
        run: |
          helm upgrade spark-job ./helm/spark-job \
            --set image.tag=${{ github.ref_name }} \
            --namespace bigdata
```

### 场景二：用 Terraform + Ansible 拉起一套自建 Kafka 集群

```text
Terraform（建资源）          Ansible（配软件）
   |-- 创建 3 台虚拟机          |-- 装 JDK
   |-- 创建安全组/网络          |-- 装 Kafka
   |-- 创建对象存储桶           |-- 写 server.properties
   |-- 输出 inventory.ini       |-- 启动 Kafka 服务
```

```bash
# 一条命令串起 IaC 全流程
terraform apply -auto-approve          # 建好 3 台机器，生成 inventory.ini
ansible-playbook -i inventory.ini playbook.yaml   # 配置并启动 Kafka
# 验证
ansible kafka_servers -i inventory.ini -m shell -a "systemctl is-active kafka"
```

## 最佳实践与踩坑记录

### 最佳实践

1. 流水线即代码——Jenkinsfile/.gitlab-ci.yml/工作流 YAML 都进仓库，随代码一起评审
2. 镜像 tag 用 commit SHA 或语义化版本，禁止用 latest 部署生产
3. 密钥（密码/token/kubeconfig）只进 Secrets 管理，绝不写进代码或日志
4. 构建产物（jar/镜像）只构建一次，在各环境间传递，避免重复构建引入差异
5. Terraform state 存远程后端（S3/OSS + 锁），团队共享，避免本地 state 漂移
6. Helm 一套 Chart 多套 values，用环境差异化，不用环境差异化 Chart
7. 部署加灰度/回滚机制，任何 CD 都应该是可逆的

### 踩坑记录

```text
坑 1：Terraform state 放本地被多人覆盖
结论：A 和 B 同时 apply，资源状态互相覆盖，集群被改乱。
原因：state 文件存在本地，无锁无共享，两人各持一份。
解法：state 迁移到远程后端（S3 + DynamoDB 锁 / OSS + 表格存储锁），团队共享同一份 state。

坑 2：镜像用 latest 导致部署不可回滚
结论：线上出问题想回滚，发现 latest 已被新镜像覆盖，无法回退。
原因：latest 是可变标签，历史版本被覆盖。
解法：镜像 tag 用 git SHA 或版本号，回滚时改回旧 tag 即可。

坑 3：Helm 升级没加 --atomic 导致半成品状态
结论：升级中途失败，Pod 一半新一半旧，服务不可用。
原因：helm upgrade 失败后不自动回滚，留下中间态。
解法：升级加 --atomic --timeout，失败自动回滚到上一版本。

坑 4：CI 里跑测试用了生产配置
结论：CI 测试把数据写进了生产库，造成脏数据。
原因：测试代码读取的环境变量/配置指向了生产环境。
解法：CI 环境强制注入测试配置，生产凭证只在生产环境可见，测试用 mock/测试库。

坑 5：Ansible 任务不幂等导致重复执行报错
结论：playbook 第二次跑报「端口已占用」「目录已存在」。
原因：用 shell 命令直接起服务/建目录，没判断已存在状态。
解法：优先用幂等模块（systemd/user/unarchive），shell 加 creates 参数，保证重复执行一致。
```
