## 概述

可观测性（Observability）回答三个问题：系统现在状态如何（Metrics）、发生了什么事件（Logs）、一次请求走了哪条链路耗时多少（Traces）。它是「运维从被动救火到主动发现」的基础——没有这三类信号，出问题只能靠猜。运维则是在可观测数据之上做容量规划、故障恢复、备份容灾和成本管理，让大数据平台既稳定又经济。
```text
可观测性三支柱 + 运维四件套：
三大信号：
1. Metrics —— 数值型指标（CPU、QPS、延迟），看趋势与告警
2. Logs —— 离散事件文本（报错、审计），定位「发生了什么」
3. Traces —— 请求调用链（span 树），定位「慢在哪一跳」
运维四件套：
4. 容量规划 —— 提前算好资源，避免峰值打爆
5. 故障恢复 —— 出问题快速止血与恢复
6. 备份容灾 —— 数据可恢复、机房级故障可切换
7. 成本管理 —— 资源利用率与账单管控
```
## Metrics

Metrics 是可聚合的数值型指标，典型如 CPU 使用率、内存占用、请求 QPS、P99 延迟、Kafka 消费 lag。它以时间序列形式存储，支持聚合（sum/avg/quantile）和告警阈值判断。Metrics 回答「趋势性问题」——某个指标是否在恶化，是告警系统的主要数据来源。
```text
Metrics 要点：
1. 类型 —— Counter（只增，如请求数）/ Gauge（可升降，如内存）/ Histogram（分布）/ Summary（分位数）
2. 标签 —— label 区分维度（如 method=GET、status=200），多维聚合
3. 聚合 —— PromQL 支持 sum/rate/quantile 等聚合运算
4. 告警 —— 阈值 + 持续时间判断，避免瞬时抖动误报
5. 采样 —— 数据量可控，长期低成本存储
```
```yaml
# 应用暴露 Prometheus 指标（Java 应用用 micrometer，这里以配置文件示意）
management:
  endpoints:
    web:
      exposure:
        include: prometheus,health,metrics
  metrics:
    tags:
      application: spark-job
# 常见大数据组件的关键指标：
# 1. Spark —— 作业运行时长、task 失败数、shuffle 数据量、executor 内存
# 2. Flink —— numRecordsIn/Out、checkpoint 时长、barrier 对齐时间、背压
# 3. Kafka —— 分区消息速率、consumer lag、broker 磁盘使用率
# 4. Trino —— 查询并发、排队时间、worker CPU、内存溢出次数
```
## Logs

Logs 是服务产生的离散事件文本，记录「什么时候发生了什么」。它是排障的第一入口——报错堆栈、异常信息、关键路径打印都在日志里。与 Metrics 不同，日志是离散的、海量的、不便聚合的，需要集中采集（如 Loki/ELK）后按关键词、时间范围检索。日志要结构化（JSON），才能被高效解析和检索。
```text
Logs 要点：
1. 结构化 —— 输出 JSON 日志，字段（level/timestamp/logger）可解析
2. 采集 —— Filebeat/Fluentd/Promtail 采集到集中存储（ELK/Loki）
3. 检索 —— 按时间 + 关键词 + 字段过滤快速定位
4. 关联 —— 日志带 trace_id，与 Traces 打通，从告警跳到日志
5. 保留 —— 日志量大，按保留期分层（热/冷），控制成本
```
```yaml
# 用 Fluent Bit 采集 K8s 容器日志到 Loki（daemonset 配置）
pipeline:
  inputs:
    - name: tail
      path: /var/log/containers/*.log
      parser: docker
  outputs:
    - name: loki
      match: "*"
      host: loki
      port: 3100
      labels: "{job=\"k8s\"}"
```
```bash
# 从 Loki 检索日志（LogQL）
# 查某作业最近 5 分钟的 ERROR 日志
curl -G "http://loki:3100/loki/api/v1/query_range" \
  --data-urlencode 'query={app="spark-job"} |= "ERROR"' \
  --data-urlencode 'start=5m'
```
## Traces

Traces 记录一次请求跨越多服务的完整调用链——由一串 span（每个服务的一段处理）组成树状结构，标注了每段耗时、依赖关系。分布式追踪解决「微服务/分布式作业里，一次慢到底慢在哪一跳」的问题。大数据场景里，Flink 作业、Spark 任务、在线服务的调用链都可用 Trace 观测。
```text
Traces 要点：
1. span —— 一次调用的基本单元，含起止时间、耗时、父 span
2. trace_id —— 贯穿整条链路的唯一 ID，把分散的 span 串起来
3. 传播 —— 跨服务传递 trace_id/span_id（W3C Trace Context）
4. 价值 —— 定位慢调用、依赖关系、瓶颈所在
5. 采样 —— 全量开销大，按比例采样（如 1%）
```
```text
一次请求的 Trace 结构（span 树）：
trace_id: abc123（一次用户查询）
  ├─ span: 网关转发        (2ms)
  ├─ span: Trino 查询      (1200ms)
  │    ├─ span: 读 Iceberg 元数据 (50ms)
  │    └─ span: 扫对象存储数据    (1100ms)  <- 瓶颈在这里
  └─ span: 返回结果        (3ms)
```
## OpenTelemetry

OpenTelemetry（OTel）是统一的可观测数据标准与采集框架，目标是「一次埋点，多处使用」。它定义了一套 API/SDK 和采集协议（OTLP），让 Metrics/Logs/Traces 统一采集、统一格式，再导出到任意后端（Prometheus、Jaeger、Loki 等）。它避免了「换个后端就要换埋点」的厂商锁定，是当前可观测的事实标准。
```text
OpenTelemetry 要点：
1. 统一标准 —— 一套 API 覆盖三信号，厂商无关
2. OTLP —— 标准采集协议，数据可导出到任意兼容后端
3. Collector —— 统一采集/处理/导出的 agent（可部署为 daemonset）
4. 自动埋点 —— 对主流框架自动注入，减少改代码
5. 收益 —— 后端可替换，避免被单一厂商绑定
```
```yaml
# OpenTelemetry Collector 配置：接收 OTLP 并导出到多个后端
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
exporters:
  prometheus:
    endpoint: 0.0.0.0:8889
  jaeger:
    endpoint: jaeger:14250
    tls:
      insecure: true
  loki:
    endpoint: http://loki:3100/loki/api/v1/push
service:
  pipelines:
    traces:
      receivers: [otlp]
      exporters: [jaeger]
    metrics:
      receivers: [otlp]
      exporters: [prometheus]
    logs:
      receivers: [otlp]
      exporters: [loki]
```
## Prometheus

Prometheus 是云原生事实标准的指标监控系统，采用「拉取（pull）」模型——它定期从应用暴露的 /metrics 端点抓取指标，存成本地时序库，用 PromQL 查询和告警。配合服务发现自动感知新实例，配合 Alertmanager 发告警。它是 Metrics 这一支柱的默认实现，几乎所有大数据组件（通过 exporter）都暴露 Prometheus 指标。
```text
Prometheus 要点：
1. 拉模型 —— 主动 scrape 目标的 /metrics 端点，目标由服务发现管理
2. TSDB —— 本地时序存储，按标签索引，高效压缩
3. PromQL —— 强大的查询语言，支持 rate/quantile/聚合
4. 告警规则 —— 定义阈值，触发后交 Alertmanager 通知
5. 局限 —— 单机存储有上限，长期存储需接 Thanos/VictoriaMetrics
```
```yaml
# prometheus.yml：抓取目标与告警规则
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: flink
    static_configs:
      - targets: ["flink-jobmanager:9249", "flink-taskmanager:9249"]
  - job_name: kafka
    static_configs:
      - targets: ["kafka-exporter:9308"]
rule_files:
  - /etc/prometheus/alerts.yml
# alerts.yml：Kafka lag 告警规则
groups:
  - name: kafka
    rules:
      - alert: KafkaLagTooHigh
        expr: sum(kafka_consumergroup_lag) by (group) > 100000
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "消费组 {{ $labels.group }} 延迟过高"
```
## Grafana

Grafana 是通用的可视化与仪表盘平台，对接 Prometheus、Loki、Jaeger 等几十种数据源，把指标、日志、链路统一展示。它是可观测性的「门面」——运维通过它看大盘、做排查，也通过它配置告警通知。数据团队用它做业务指标大屏（GMV、实时 DAU 等），把技术指标和业务指标放在同一平台。
```text
Grafana 要点：
1. 多数据源 —— 一个面板可混合 Prometheus 指标 + Loki 日志
2. Dashboard —— 面板（panel）组成大盘，支持变量（variable）模板化
3. 告警 —— Grafana Alerting 统一管理告警规则与通知渠道
4. 探索 —— Explore 模式交互式查日志/指标，排障利器
5. 供给 —— Dashboard 用 JSON 或 Terraform 代码化管理
```
```json
{
  "dashboard": {
    "title": "Flink 作业监控",
    "panels": [
      {
        "type": "timeseries",
        "title": "每秒处理记录数",
        "targets": [
          {
            "expr": "rate(flink_taskmanager_job_task_numRecordsIn[1m])",
            "legendFormat": "{{task_name}}"
          }
        ]
      },
      {
        "type": "stat",
        "title": "当前消费 Lag",
        "targets": [
          {
            "expr": "sum(kafka_consumergroup_lag)"
          }
        ]
      }
    ]
  }
}
```
## Alertmanager

Alertmanager 是 Prometheus 生态的告警通知组件，负责「接收告警 → 去重 → 分组 → 抑制 → 静默 → 路由到通知渠道」。它解决「告警风暴」问题——同类告警合并成一条、按严重级别分组、按时间窗口抑制重复、值班时静默非关键告警。通知渠道支持邮件、企业微信、钉钉、Slack、Webhook 等。
```text
Alertmanager 要点：
1. 去重分组 —— 相同 label 的告警合并，避免一条故障刷屏
2. 抑制 —— 高优先级告警抑制低优先级（如整机宕机抑制其上所有服务告警）
3. 静默 —— 维护窗口手动静默，避免误报打扰
4. 路由 —— 按 label 匹配路由到不同接收人（如数据库告警只发 DBA）
5. 升级 —— 持续未恢复的告警自动升级通知更高层
```
```yaml
# alertmanager.yml：路由与接收配置
route:
  receiver: default
  group_by: ["alertname", "cluster"]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - match:
        severity: critical
      receiver: oncall
receivers:
  - name: default
    webhook_configs:
      - url: http://dingtalk-webhook/send
        send_resolved: true
  - name: oncall
    webhook_configs:
      - url: http://oncall-alert/send
```
## 容量规划

容量规划是「提前估算业务增长对应的资源需求，避免峰值时打爆、也避免长期超配浪费」的工作。大数据场景的核心变量是数据量增长速率、计算作业的并行度与资源需求、以及存储的容量与 IO。做法是建立「指标 → 资源」的换算模型，结合监控趋势做预测，再定期复盘调优。
```text
容量规划要点：
1. 数据增长 —— 按日增量 × 保留期估算存储容量，预留 20%~30% 余量
2. 计算峰值 —— 按高峰期并发作业数 × 单作业资源估算计算资源
3. 趋势预测 —— 用历史 Metrics 拟合增长曲线，提前扩容而非事后补救
4. 分层 —— 热数据 SSD、冷数据对象存储，分层控制成本
5. 弹性 —— 能弹性伸缩的（无状态计算）按需扩，有状态的提前规划
存储容量估算示例：
日新增数据 10TB × 保留 30 天 = 300TB 原始数据
Iceberg 列式压缩（约 3:1）=> 100TB 实际占用
加 20% 余量 => 需要 120TB 可用容量
对象存储按月计费，提前申请配额即可弹性扩展
```
## 故障恢复

故障恢复关注「故障发生后如何快速定位、止血、恢复服务」。核心不是「不出故障」（不可能），而是「故障影响可控、恢复时间短（MTTR）」。手段包括：健康检查与自动重启、失败作业自动重试、降级开关、回滚机制、以及事后复盘（postmortem）沉淀预案。SRE 用 SLO/SLI 量化「多快恢复」的目标。
```text
故障恢复要点：
1. 健康检查 —— liveness/readiness 探针，Pod 异常自动重启
2. 自动重试 —— Flink/Spark 作业失败按策略自动重启（restart 策略）
3. 降级 —— 非核心链路故障时降级，保住核心服务
4. 回滚 —— 配置/镜像/版本可一键回退
5. 复盘 —— 事后写 postmortem，沉淀 runbook，同类故障下次更快
```
```bash
# 常见故障快速排查命令
kubectl describe pod spark-driver -n bigdata          # 看 Pod 事件与退出原因
kubectl logs spark-driver -n bigdata --tail=100       # 看日志
kubectl get events -n bigdata --sort-by=.lastTimestamp # 集群事件
# Flink 作业失败自动重启策略（Flink 配置）
# restart-strategy: fixed-delay, 失败后固定间隔重启
```
## 备份

备份是「对数据做副本，供误删/损坏/故障后恢复」。大数据场景备份分两类：元数据备份（Hive Metastore 的库、表结构、权限）和数据备份（对象存储里的实际数据）。对象存储本身有多副本，但防不了「逻辑错误」（误删、被程序写坏），所以还要有版本化、快照、跨区域复制等逻辑备份手段。
```text
备份要点：
1. 元数据备份 —— Metastore 数据库定期 dump，损坏后可重建
2. 数据备份 —— 对象存储版本控制 + 生命周期，防误删可恢复
3. 快照 —— Iceberg 时间旅行天然支持回滚到历史快照
4. 跨区域 —— 数据跨区域/跨账号复制，防区域级故障
5. 演练 —— 定期做恢复演练，验证备份真的能恢复
```
```bash
# 备份 Hive Metastore（PostgreSQL dump）
pg_dump -h metastore-db -U hive hive_metastore | gzip > metastore-$(date +%F).sql.gz
# 开启对象存储版本控制（以 S3 为例）
aws s3api put-bucket-versioning --bucket bigdata-lake \
  --versioning-configuration Status=Enabled
# Iceberg 时间旅行恢复（回到误删前的快照）
spark-sql -e "SELECT * FROM warehouse.orders FOR SYSTEM_VERSION AS OF '2024-08-14 09:00:00'"
```
## 容灾

容灾（DR）是在更高层面保证「机房级、区域级故障时业务还能继续」——区别于备份（数据可恢复），容灾强调「服务可切换」。常见分级：冷备（数据定期复制、故障后手动恢复，RTO 长）、温备（数据近实时复制、可快速拉起）、热备/双活（两地同时服务，RTO 近零）。大数据平台通常采用「数据跨区域异步复制 + 计算资源两地预置」的温备方案。
```text
容灾要点：
1. RTO/RPO —— RTO（恢复时间目标）、RPO（数据丢失容忍度）是容灾核心指标
2. 分级 —— 冷备（成本低恢复慢）到双活（成本高恢复快），按业务重要性选
3. 数据复制 —— 对象存储跨区域复制、Kafka MirrorMaker 跨集群同步
4. 计算预置 —— 灾备地预置最小计算集群，故障时扩容接管
5. 切换演练 —— 定期做切流演练，验证真能切过去
容灾等级对比：
冷备：数据定期复制，故障后人工恢复，RPO 小时级、RTO 天级，成本最低
温备：数据近实时复制，灾备地有备用集群，RPO 分钟级、RTO 小时级
双活：两地同时服务分担流量，故障自动切换，RPO≈0、RTO 分钟级，成本最高
```
## 成本管理

成本管理是「让大数据平台的每一分钱花得明白」。上云后资源从「一次买断」变成「按量付费」，成本可控但更容易失控（忘了关的集群、超配的资源、小文件导致的 List 开销）。手段包括：资源标签化（按团队/项目分摊）、闲置资源识别与回收、存算分离降低存储单价、spot 实例跑批处理、以及定期成本复盘。
```text
成本管理要点：
1. 标签化 —— 资源打标签，按团队/项目/环境分摊账单
2. 闲置回收 —— 定时巡检无流量的集群/作业，自动缩容或关停
3. 存算分离 —— 计算按需弹性、存储走对象存储，降存储单价
4. Spot 实例 —— 离线批处理用可抢占实例，成本降 60%~70%
5. 利用率 —— 提升资源利用率（合并小集群、合理设置资源上限）
```
```bash
# 成本优化示例：给资源打标签 + 用 spot 节点池跑 Spark
kubectl label ns bigdata team=data-platform env=prod
# 为离线批处理创建 spot 节点池（示意）
eksctl create nodegroup --cluster bigdata --name spot-pool \
  --spot --instance-types=m5.xlarge --nodes-min=0 --nodes-max=20
```
## 应用场景实战

### 场景一：Flink 作业的可观测性全链路
```text
Flink 作业 -> 暴露 Metrics（/metrics 端点）
    |-> Prometheus 抓取指标 -> Alertmanager 告警 -> 通知
    |-> 日志采集（Fluent Bit -> Loki）
    |-> OpenTelemetry 采集 Trace -> Jaeger
Grafana 统一展示（指标大盘 + 日志检索 + 链路追踪）
```
```yaml
# Flink 作业开启指标上报（flink-conf 配置）
metrics.reporter.prom.class: org.apache.flink.metrics.prometheus.PrometheusReporter
metrics.reporter.prom.port: 9249
metrics.reporter.prom.factory.class: org.apache.flink.metrics.prometheus.PrometheusReporterFactory
```
```yaml
# Prometheus 抓取 Flink 指标 + 告警规则
scrape_configs:
  - job_name: flink
    static_configs:
      - targets: ["flink-jobmanager:9249"]
rule_files: ["/etc/prometheus/alerts.yml"]
```
### 场景二：Kafka 消费延迟监控 + 自动扩容
```text
监控链路：
kafka-exporter 暴露消费组 lag
  -> Prometheus 采集并聚合
  -> lag > 阈值触发 Alertmanager 告警
  -> 通知到值班 + 触发 HPA 扩容消费者
  -> Grafana 大盘实时展示 lag 曲线
```

```yaml
# 消费组 lag 告警规则
groups:
  - name: kafka-lag
    rules:
      - alert: ConsumerLagHigh
        expr: sum(kafka_consumergroup_lag) by (consumergroup) > 500000
        for: 3m
        labels: { severity: critical }
        annotations:
          summary: "消费组 {{ $labels.consumergroup }} lag 超过 50 万"
```
## 最佳实践与踩坑记录

### 最佳实践

1. 三信号都上——Metrics 看趋势、Logs 定位事件、Traces 找瓶颈，缺一不可
2. 日志结构化输出 JSON 并带 trace_id，与 Trace 打通，从告警能直接跳到日志
3. 告警规则用「阈值 + 持续时间」双重判断，避免瞬时抖动刷屏
4. 用 OpenTelemetry 统一埋点，后端可替换，避免厂商锁定
5. 容量规划看趋势而非拍脑袋，预留弹性余量但别长期超配
6. 备份要定期做恢复演练，验证「真能恢复」而不只是「有备份」
7. 资源打标签 + 定期成本复盘，让账单可分摊、可优化

### 踩坑记录
```text
坑 1：告警只设阈值不设持续时间
结论：指标瞬时抖动导致告警风暴，值班被刷屏后开始忽略告警。
原因：单点超过阈值立刻触发，没过滤瞬时毛刺。
解法：规则加 for: 5m 之类的持续时间，连续超阈值才告警。
坑 2：日志没带 trace_id 导致排障断链
结论：看到报错日志却不知道是哪次请求、上游是哪，排查费时。
原因：日志与调用链没打通，各系统日志孤立。
解法：结构化日志带 trace_id，Grafana 里从 Trace 一键跳到对应日志。
坑 3：备份只做不演练，真出事故发现恢复不了
结论：数据误删后执行恢复，发现备份损坏或流程不通，RTO 远超预期。
原因：备份文件从没验证过能否恢复，脚本也长期没跑。
解法：定期做恢复演练，把恢复流程写成 runbook 并实际跑通。
坑 4：存算分离后对象存储小文件爆增，成本反升
结论：迁移对象存储后 List/GET 请求费飙升，存储成本没降反升。
原因：高频小写入产生海量小文件，对象存储按请求计费。
解法：写侧控制批次大小，定期合并小文件（rewriteDataFiles），生命周期转冷存储。
坑 5：无标签资源导致账单无法分摊
结论：月底账单出来了，没人说得清每笔钱是谁花的。
原因：资源创建时没打标签，成本无法按团队/项目归集。
解法：IaC 里强制资源打标签，配成本报表按标签维度归集。
```
