## 概述

「大数据组件上云」解决的是：把原本跑在物理机/自建集群上的 Hadoop 生态组件，迁移到 Kubernetes 与对象存储上，实现资源池化、弹性伸缩和统一调度。核心思路是「计算上 K8s、存储上对象存储」——计算引擎（Spark/Flink/Trino）容器化跑在 K8s 上，数据落到 S3/OSS 这类对象存储（配合 Iceberg 等表格式），元数据交给 Hive Metastore。这样做的收益是运维统一、按需扩缩、资源利用率高。
```text
大数据组件上云的核心模式：
1. 计算容器化 —— Spark/Flink/Trino/Airflow 以容器运行在 K8s，按作业弹性伸缩
2. 存储对象化 —— 数据落对象存储（S3/OSS），用表格式（Iceberg/Hudi）组织成表
3. 存算分离 —— 计算节点无状态，存储与计算独立扩缩，降低成本
4. 元数据统一 —— Hive Metastore / 统一元数据服务，多引擎共享一张表
5. 调度统一 —— 作业调度（Airflow）与资源调度（K8s）解耦协作
```
## Spark on K8s

Spark 从 2.3 开始支持原生 K8s 调度（取代 YARN 的一种选择）。提交作业时 Spark 会创建一个 driver Pod，driver 再向 K8s API 申请 executor Pod，作业结束 Pod 自动回收。相比 YARN，K8s 模式下 Spark 与其它服务共享同一个集群，资源粒度更细（按 Pod 的 CPU/内存），也更容易做多租户隔离和镜像版本管理。
```text
Spark on K8s 要点：
1. 运行模式 —— driver 与 executor 都是 Pod，由 spark-submit 动态创建
2. 资源申请 —— 按 Pod 申请 CPU/内存，支持弹性 executor 数量（动态分配）
3. 镜像 —— 把依赖打进镜像，避免每次作业启动时现拉 jar 包
4. 存储 —— 读写对象存储（s3a://）或 HDFS，配合 Iceberg 存算分离
5. 对比 YARN —— 共享 K8s 集群、隔离更细，但缺少 YARN 的公平调度队列
```
```bash
# 向 K8s 集群提交 Spark 作业（driver/executor 以 Pod 运行）
spark-submit \
  --master k8s://https://k8s-master:6443 \
  --deploy-mode cluster \
  --name spark-on-k8s-demo \
  --conf spark.kubernetes.container.image=apache/spark:3.5.0 \
  --conf spark.kubernetes.namespace=bigdata \
  --conf spark.kubernetes.authenticate.driver.serviceAccountName=spark \
  --conf spark.executor.instances=4 \
  --conf spark.executor.memory=4g \
  --conf spark.hadoop.fs.s3a.endpoint=http://minio:9000 \
  --conf spark.hadoop.fs.s3a.access.key=admin \
  --conf spark.hadoop.fs.s3a.secret.key=password \
  --conf spark.hadoop.fs.s3a.path.style.access=true \
  local:///opt/spark/examples/jars/spark-examples.jar 1000
```
```yaml
# 为 Spark 作业准备的 RBAC：允许 driver 创建/管理 executor Pod
apiVersion: v1
kind: ServiceAccount
metadata:
  name: spark
  namespace: bigdata
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: spark-role
  namespace: bigdata
rules:
  - apiGroups: [""]
    resources: ["pods", "services", "configmaps"]
    verbs: ["get", "list", "create", "delete", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: spark-role-binding
  namespace: bigdata
subjects:
  - kind: ServiceAccount
    name: spark
    namespace: bigdata
roleRef:
  kind: Role
  name: spark-role
  apiGroup: rbac.authorization.k8s.io
```
## Flink Operator

Flink 原生的 standalone/会话集群在 K8s 上管理繁琐，Flink Kubernetes Operator 把 Flink 集群变成 K8s 自定义资源（CRD），用声明式方式管理整个生命周期：提交、扩缩容、升级、Savepoint 触发、自动恢复。它监听 FlinkDeployment/FlinkSessionJob 资源，调和出对应的 JobManager/TaskManager Pod，并内置了升级策略（Stateful/Stateless）与自动重启。
```text
Flink Operator 要点：
1. CRD —— FlinkDeployment（应用模式）/ FlinkSessionJob（会话模式）声明作业
2. 声明式 —— 修改 spec 即触发升级，Operator 负责调和到目标状态
3. Savepoint —— 升级前自动打 Savepoint，保证状态不丢
4. 升级策略 —— Stateless（直接重启）与 Stateful（保留状态滚动升级）
5. 自动恢复 —— 作业崩溃后按 restartPolicy 自动拉起
```
```yaml
# FlinkDeployment：声明一个跑在 K8s 上的 Flink 作业
apiVersion: flink.apache.org/v1beta1
kind: FlinkDeployment
metadata:
  name: word-count
  namespace: bigdata
spec:
  image: flink:1.18
  flinkVersion: v1_18
  flinkConfiguration:
    taskmanager.numberOfTaskSlots: "2"
    state.savepoints.dir: s3://flink/savepoints
    s3.endpoint: http://minio:9000
    s3.access-key: admin
    s3.secret-key: password
  serviceAccount: flink
  jobManager:
    resource:
      memory: "2048m"
      cpu: 1
  taskManager:
    resource:
      memory: "2048m"
      cpu: 2
  job:
    jarURI: local:///opt/flink/examples/streaming/StateMachineExample.jar
    parallelism: 2
    state: running
    upgradeMode: savepoint
  restartNonce: 1
```
```bash
# 安装 Flink Kubernetes Operator（Helm 方式）
helm repo add flink-operator https://downloads.apache.org/flink/flink-kubernetes-operator-1.9.0/
helm install flink-kubernetes-operator flink-operator/flink-kubernetes-operator \
  --set webhook.enabled=false \
  --namespace flink --create-namespace
# 提交 FlinkDeployment 作业
kubectl apply -f flink-deployment.yaml -n bigdata
# 触发一次 Savepoint 并停机
kubectl patch flinkdeployment word-count -n bigdata \
  --type merge -p '{"spec":{"job":{"state":"suspended"}}}'
```
## Kafka on K8s

Kafka 是有状态服务，上 K8s 不能像无状态应用那样随便重启——每个 broker 都带着自己的分区数据。社区方案 Strimzi 用 Operator 管理 Kafka 集群的 CRD，把 broker 的存储绑定到 PVC，并内置了滚动升级、副本重平衡、Topic 管理与指标暴露。核心难点是「网络身份」：broker 需要稳定的 DNS 名和可路由的端口，Strimzi 用 per-broker Service 解决。
```text
Kafka on K8s 要点：
1. 有状态 —— broker 数据绑定 PVC，Pod 重建后数据不丢
2. 网络身份 —— 每个 broker 独立 Service + headless Service，保证稳定 DNS
3. Strimzi —— Operator 管理 CRD（Kafka/KafkaTopic/KafkaUser），滚动升级
4. 存储 —— 用本地盘或云盘 PVC，吞吐敏感，别用网络文件系统
5. 权衡 —— 运维简单但调优受限，超高吞吐场景仍需评估裸机部署
```
```yaml
# Strimzi：声明一个 3 节点 Kafka 集群
apiVersion: kafka.strimzi.io/v1beta2
kind: Kafka
metadata:
  name: my-cluster
  namespace: bigdata
spec:
  kafka:
    version: 3.7.0
    replicas: 3
    listeners:
      - name: plain
        port: 9092
        type: internal
        tls: false
      - name: external
        port: 9094
        type: nodeport
        tls: false
    storage:
      type: persistent-claim
      size: 100Gi
      class: fast-ssd
    config:
      offsets.topic.replication.factor: 3
      transaction.state.log.replication.factor: 3
      min.insync.replicas: 2
  entityOperator:
    topicOperator: {}
    userOperator: {}
  zookeeper:
    replicas: 3
    storage:
      type: persistent-claim
      size: 20Gi
```
```yaml
# 用 KafkaTopic CRD 声明一个 Topic（替代命令行 kafka-topics.sh）
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaTopic
metadata:
  name: orders
  namespace: bigdata
  labels:
    strimzi.io/cluster: my-cluster
spec:
  partitions: 12
  replicas: 3
  config:
    retention.ms: 604800000
    cleanup.policy: delete
```
## Airflow on K8s

Airflow 是数据工程的主流调度器，官方 Helm Chart 支持把它跑在 K8s 上。关键能力是 KubernetesExecutor——每个 task 实例启动一个独立 Pod 运行，任务之间完全隔离、资源独立申请，天然适合「任务多、依赖各异、资源需求差异大」的大数据场景。CeleryExecutor 则用 worker 常驻模式，适合任务轻、启动频繁的场景。
```text
Airflow on K8s 要点：
1. Executor 选型 —— KubernetesExecutor（任务级 Pod 隔离）vs CeleryExecutor（worker 常驻）
2. 组件 —— webserver/scheduler/worker（可选）各自独立 Pod
3. 元数据库 —— 依赖 PostgreSQL（外置），存 DAG 与任务状态
4. DAG 同步 —— git-sync 把 Git 仓库里的 DAG 同步进容器
5. 日志 —— 任务日志落到对象存储/PVC，Pod 销毁后仍可查
```
```yaml
# values.yaml（Airflow 官方 Helm Chart 关键配置）
executor: KubernetesExecutor
postgresql:
  enabled: false
data:
  metadataConnection:
    user: airflow
    pass: airflow-pass
    host: pg.example.com
    port: 5432
    db: airflow
dags:
  gitSync:
    enabled: true
    repo: https://git.example.com/team/airflow-dags.git
    branch: main
    subPath: dags
workers:
  replicas: 2
  resources:
    requests: { cpu: "500m", memory: "1Gi" }
logs:
  persistence:
    enabled: true
    storageClassName: standard
```
```bash
# 安装 Airflow 到 K8s
helm repo add apache-airflow https://airflow.apache.org
helm upgrade --install airflow apache-airflow/airflow \
  --namespace airflow --create-namespace \
  -f values.yaml
# 查看 DAG 是否同步
kubectl exec -n airflow deploy/airflow-scheduler -- airflow dags list
```
## Trino on K8s

Trino（原 PrestoSQL）是联邦查询引擎，本身无状态，是「上 K8s」最自然的一类组件。社区提供 Helm Chart，把 coordinator 和 worker 分别部署为 Deployment，worker 用 HPA 按负载自动扩缩容。Trino 集群通过多个 catalog 连接对象存储、Hive Metastore、关系库，跑在 K8s 上可以按查询负载弹性伸缩 worker 数量，显著降低空闲成本。
```text
Trino on K8s 要点：
1. 无状态 —— coordinator + worker 都是无状态 Pod，天然适配 K8s
2. 弹性 —— worker 用 HPA 按 CPU/查询并发自动扩缩
3. Catalog —— 配置 Hive/Iceberg/MySQL 等 catalog 连接各类数据源
4. 存算分离 —— 数据在对象存储，worker 只管计算，扩缩不迁移数据
5. 协调 —— coordinator 单一，worker 可横向扩展
```
```yaml
# Trino Helm Chart 关键配置（catalog 通过 configmap 注入）
server:
  workers: 2
  coordinator:
    resources:
      requests: { cpu: "1", memory: "2Gi" }
  worker:
    resources:
      requests: { cpu: "2", memory: "4Gi" }
  autoscaling:
    enabled: true
    maxReplicas: 10
    targetCPUUtilizationPercentage: 70
catalogs:
  iceberg: |-
    connector.name=iceberg
    hive.metastore.uri=thrift://hive-metastore:9083
    fs.hadoop.enabled=true
    s3.endpoint=http://minio:9000
    s3.aws-access-key=admin
    s3.aws-secret-key=password
  mysql: |-
    connector.name=mysql
    connection-url=jdbc:mysql://mysql:3306
    connection-user=root
    connection-password=secret
```
```bash
# 安装 Trino 集群
helm repo add trino https://trinodb.github.io/charts
helm install trino trino/trino --namespace bigdata -f values.yaml
# 查询 Iceberg 表（验证 catalog 生效）
kubectl exec -n bigdata deploy/trino-coordinator -- trino \
  --execute "SELECT count(*) FROM iceberg.warehouse.orders"
```
## Iceberg on Object Storage

Iceberg 是「开放表格式」，它不存储数据，而是定义「一批对象存储文件如何组织成一张带 schema、分区、快照的表」。把 Iceberg 落在 S3/OSS 上，配合 Hive Metastore 存元数据，就能实现「存算分离」的湖仓：任何引擎（Spark/Flink/Trino）读同一份数据，ACID 事务、时间旅行、schema 演进都由表格式保证。这是大数据上云后存储层的事实标准。
```text
Iceberg on Object Storage 要点：
1. 表格式 —— Iceberg 是元数据层，数据文件仍在对象存储（Parquet/ORC）
2. 元数据 —— 表定义、分区、快照存 Hive Metastore / 对象存储目录
3. 能力 —— ACID 事务、时间旅行、隐式分区、schema 演进、行级更新
4. 多引擎 —— Spark/Flink/Trino 共享同一张表，口径一致
5. 性价比 —— 对象存储比 HDFS 便宜，且存算分离、按需付费
```
```bash
# 用 Spark SQL 在对象存储上建 Iceberg 表并写入
spark-sql \
  --conf spark.sql.catalog.iceberg=org.apache.iceberg.spark.SparkCatalog \
  --conf spark.sql.catalog.iceberg.type=hive \
  --conf spark.sql.catalog.iceberg.uri=thrift://hive-metastore:9083 \
  --conf spark.sql.catalog.iceberg.warehouse=s3://warehouse \
  -e "
  CREATE TABLE iceberg.warehouse.orders (
      order_id BIGINT, user_id BIGINT, amount DECIMAL(10,2), dt STRING
  ) USING iceberg PARTITIONED BY (dt);
  INSERT INTO iceberg.warehouse.orders VALUES
      (1, 1001, 99.90, '2024-08-14'),
      (2, 1002, 199.00, '2024-08-14');
  "
```
```sql
-- 时间旅行：读某个快照版本的数据
SELECT * FROM iceberg.warehouse.orders
FOR SYSTEM_VERSION AS OF '2024-08-14 10:00:00';
```
## 应用场景实战

### 场景一：Spark + Iceberg + 对象存储的存算分离离线链路
```text
数据流：
Kafka（源） -> Flink（K8s 上实时入湖） -> Iceberg 表（S3 对象存储）
         -> Spark on K8s（离线批处理） -> 结果写回 Iceberg
         -> Trino on K8s（联邦查询）-> BI 报表
```
```bash
# Flink 实时写 Iceberg（K8s 上运行的 FlinkDeployment 作业）
kubectl apply -n bigdata -f - <<'EOF'
apiVersion: flink.apache.org/v1beta1
kind: FlinkDeployment
metadata:
  name: kafka-to-iceberg
spec:
  image: flink:1.18
  flinkVersion: v1_18
  serviceAccount: flink
  jobManager: { resource: { memory: "2048m", cpu: 1 } }
  taskManager: { resource: { memory: "2048m", cpu: 2 } }
  flinkConfiguration:
    state.savepoints.dir: s3://flink/savepoints
    s3.endpoint: http://minio:9000
    s3.access-key: admin
    s3.secret-key: password
  job:
    jarURI: local:///opt/flink/usrlib/kafka-iceberg-1.0.jar
    parallelism: 4
    state: running
    upgradeMode: savepoint
EOF
# Spark 按小时聚合并回写 Iceberg
spark-submit --master k8s://https://k8s-master:6443 --deploy-mode cluster \
  --conf spark.kubernetes.container.image=apache/spark:3.5.0 \
  --class com.example.HourlyAggJob local:///opt/spark/jobs/agg.jar
```
### 场景二：Trino 联邦查询统一取数入口
```text
BI / 数据产品
     |
     v
Trino on K8s（coordinator + 弹性 worker）
     |-- iceberg catalog -> Iceberg 表（S3）
     |-- mysql catalog   -> 业务库（只读副本）
     |-- hive catalog    -> 历史 Hive 表
```
```sql
-- 跨数据源联邦查询：Iceberg 订单表 JOIN MySQL 用户维表
SELECT u.city, SUM(o.amount) AS gmv
FROM iceberg.warehouse.orders o
JOIN mysql.biz.dim_user u ON o.user_id = u.user_id
WHERE o.dt = '2024-08-14'
GROUP BY u.city
ORDER BY gmv DESC;
```
## 最佳实践与踩坑记录

### 最佳实践

1. 存储优先对象化，计算容器化——先迁移存储到对象存储 + 表格式，再迁计算，顺序别反
2. 计算引擎镜像里预装依赖和 jar 包，避免每次作业启动现拉依赖拖慢启动
3. 有状态组件（Kafka/Flink）用 Operator 管理生命周期，别手动编排 Pod
4. executor/worker 打开动态分配或 HPA，让资源按负载弹性伸缩
5. 统一 ServiceAccount 与 RBAC，最小权限授予 driver 创建 executor 的能力
6. 对象存储访问用 IAM 角色/短期凭证，别把 AK/SK 明文写进 Pod 环境变量
7. 元数据统一到 Hive Metastore，多引擎共享一张表，避免各自为政

### 踩坑记录
```text
坑 1：Spark executor 起不来报权限错误
结论：driver 能起、executor 一直 Pending 后报 forbidden。
原因：spark 用的 ServiceAccount 缺少 pods 的 create/watch 权限。
解法：给 spark ServiceAccount 绑定最小 RBAC（见上文 Role），权限只授 pods/services/configmaps。
坑 2：Kafka broker Pod 重建后连不上
结论：broker 重启后客户端连接报 unknown host，集群不稳。
原因：broker 用了随机 DNS 名，重建后地址变化，副本无法互认。
解法：用 Strimzi 这类 Operator 的 per-broker Service 保证稳定网络身份，别裸 Deployment 跑 Kafka。
坑 3：Flink 升级直接丢状态
结论：升级 FlinkDeployment 后作业从头消费，丢数据。
原因：upgradeMode 设为 stateless，没先打 Savepoint 就重启。
解法：job.upgradeMode 设 savepoint，升级前自动触发 Savepoint，恢复时从 Savepoint 续跑。
坑 4：Trino worker 扩缩后查询失败
结论：HPA 缩容时正在跑的查询被中断。
原因：缩容直接杀 Pod，没考虑在途查询的优雅退出。
解法：给 worker 配 graceful shutdown 时间，缩容时等待在途查询结束再终止。
坑 5：对象存储小文件过多导致查询变慢
结论：入湖后 List 操作极慢，查询延迟飙升。
原因：高频小批量写入产生海量小文件，对象存储 List 开销大。
解法：用 Iceberg 的 rewriteDataFiles 定期合并小文件，写侧用合适批次大小。
```
