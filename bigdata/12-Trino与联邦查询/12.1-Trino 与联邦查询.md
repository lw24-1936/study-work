## 概述

Trino（原名 PrestoSQL）是一个分布式 SQL 查询引擎，专为交互式分析（秒级到分钟级）设计。它最大的特点是「联邦查询」——通过 Connector 把 Hive、Iceberg、Kafka、Elasticsearch、MySQL、MongoDB 等异构数据源统一抽象成 Catalog/Schema/Table，用一条 SQL 就能跨库跨源 JOIN。Trino 不存数据、只做计算（内存 MPP 架构），因此必须配合底层存储和元数据服务使用。

```text
Trino 的核心定位：
1. 纯计算引擎 —— 不存储数据，数据留在 HDFS/对象存储/数据库里
2. 内存 MPP —— 全内存流水线执行，中间结果不落盘（可溢写），秒级返回
3. 联邦查询 —— 一个 SQL 跨多个数据源 JOIN，这是它区别于 Spark 的最大价值
4. 交互式 —— 面向即席查询和 BI，不是批处理引擎
5. 无容错 —— 单查询失败需重跑，不做长任务的 shuffle 容错
```

```text
Trino 与 Presto 的渊源：
1. 2012 Facebook 开源 Presto，面向 Hive 之上的交互式 SQL
2. 2019 核心团队出走成立 Presto Software Foundation，Presto 更名为 PrestoSQL
3. 2020 更名为 Trino（因 Presto 商标归属问题），社区合并
4. 现存两个分支 —— Trino（社区主流）与 PrestoDB（Linux 基金会托管）
5. 本文以 Trino 为准，语法与 Presto 基本兼容
```

## Trino/Presto 架构

Trino 是典型的主从（Coordinator/Worker）MPP 架构。客户端提交 SQL 给 Coordinator，Coordinator 负责解析、优化、生成执行计划，并把计划拆成 Stage 和 Task 分发到多个 Worker 上并行执行。Worker 之间通过 Exchange 交换中间数据，最终结果汇总回 Coordinator 返回客户端。整个执行是流水线式的——上游 Task 产出一点数据，下游 Task 就立刻消费，不需要等整个 Stage 结束。

```text
Trino 架构核心组件：
1. Coordinator —— 接收 SQL、解析优化、调度 Task、汇总结果（单点，可配 HA）
2. Worker —— 执行 Task，从 Connector 读数据、做算子计算、互相 Exchange 数据
3. Discovery —— 服务发现，Worker 注册到 Coordinator（基于内嵌 Discovery Service）
4. Connector —— 数据源适配插件，实现读写某类数据源（Hive/Iceberg/MySQL...）
5. Catalog —— 一个 Connector 的具体实例配置，映射为一个 catalog 名
```

```text
一条 SQL 的执行流程：
Client --SQL--> Coordinator
                  1. Parser 解析成 AST
                  2. Analyzer 语义分析 + 绑定元数据
                  3. Planner 生成逻辑计划（Logical Plan）
                  4. Optimizer 规则优化（谓词下推、列裁剪、Join 重排）
                  5. Scheduler 拆 Stage/Task 分发到 Worker
Worker: 读 Split -> 算子流水线 -> Exchange 交换 -> 结果汇总
Coordinator <-- 汇总结果 -- Client
```

```yaml
# Trino 节点角色配置（config.properties）
# Coordinator 节点
coordinator: true
node-scheduler.include-coordinator: false   # Coordinator 不参与计算
http-server.http.port: 8080
discovery.uri: http://coordinator:8080

# Worker 节点
coordinator: false
http-server.http.port: 8080
discovery.uri: http://coordinator:8080
```

## Coordinator/Worker

Coordinator 是 Trino 的「大脑」，负责查询的完整生命周期：接收 SQL、解析、规划、优化、调度，并监控各 Task 的执行进度。Worker 是「肌肉」，只负责执行 Coordinator 下发的 Task——从 Connector 读取 Split、执行过滤/聚合/Join 算子、把结果通过 Exchange 传给下游。Coordinator 默认不参与计算（避免调度负载影响查询性能），生产环境通常单独部署一个 Coordinator 加多个 Worker。

```text
Coordinator 职责：
1. 查询解析与优化 —— Parser/Analyzer/Planner/Optimizer 全在 Coordinator 上跑
2. 计划调度 —— 把逻辑计划切成 Stage，再切成 Task 分发到 Worker
3. 资源管理 —— 跟踪集群内存/CPU，决定任务放置和并发度
4. 结果汇总 —— 收集各 Worker 的最终输出返回客户端
5. 查询监控 —— 记录查询状态、耗时、失败原因（Query 页面可查）
```

```text
Worker 职责：
1. 执行 Task —— 接收 Coordinator 下发的算子片段（一或多个算子）
2. 数据读取 —— 通过 Connector 读取分配给它的 Split
3. 算子计算 —— Filter/Project/Aggregate/Join 等内存算子
4. 数据交换 —— 通过 Exchange 与其它 Worker 交换中间结果
5. 心跳汇报 —— 定期向 Coordinator 汇报状态和资源使用
```

```yaml
# jvm.config —— Worker 内存配置（影响并发与稳定性）
-Xmx16G
-XX:+UseG1GC
-XX:G1HeapRegionSize=32M
-XX:+ExplicitGCInvokesConcurrent
-XX:+ExitOnOutOfMemoryError
-Djdk.attach.allowAttachSelf=true
```

## Connector/Catalog/Schema

Connector 是 Trino 对接某类数据源的插件（如 Hive Connector、MySQL Connector），定义了如何读元数据、如何读数据、如何下推谓词。Catalog 是 Connector 的一个「实例」——在 catalog 目录下放一个 properties 文件，就创建了一个指向具体数据源的 catalog（如 hive 指向 Hive Metastore，mysql 指向某台 MySQL）。Schema 等价于数据库/库，Table 等价于表。查询时用三段式 `catalog.schema.table` 定位。

```text
三者层次关系：
1. Connector —— 插件代码，实现 SPI（读元数据/读数据/下推），一个 Connector 可有多个 Catalog
2. Catalog —— 配置文件目录下的实例，绑定具体连接（一个 hive catalog 连一个 Metastore）
3. Schema —— catalog 下的库（database），Table 是库下的表
4. 三段式命名 —— catalog.schema.table，跨 catalog JOIN 即联邦查询
5. 示例 —— hive.ods.orders 与 mysql.biz.users 可直接 JOIN
```

```properties
# etc/catalog/hive.properties —— 一个指向 Hive Metastore 的 catalog
connector.name=hive-hadoop2
hive.metastore.uri=thrift://metastore:9083
hive.s3.aws-access-key=AKIA...
hive.s3.aws-secret-key=xxx
hive.allow-drop-table=true
```

```properties
# etc/catalog/mysql.properties —— 一个指向业务 MySQL 的 catalog
connector.name=mysql
connection-url=jdbc:mysql://mysql.example.com:3306
connection-user=etl_ro
connection-password=secret
```

```sql
-- 查看所有 catalog / schema / table
SHOW CATALOGS;
SHOW SCHEMAS FROM hive;
SHOW TABLES FROM hive.ods;

-- 三段式跨 catalog 联邦查询
SELECT o.order_id, u.name
FROM hive.ods.orders o
JOIN mysql.biz.users u ON o.user_id = u.id
WHERE o.dt = '2024-08-14';
```

## Split

Split 是 Trino 读取数据的最小并行单元，由 Connector 生成。Coordinator 规划时向 Connector 要表的 Split 列表，每个 Split 描述「读哪块数据」（如 Hive 的一个文件、MySQL 的一个分片、Kafka 的一个分区），然后按 Split 分发给 Worker。Split 的数量决定了查询的并行度和 Task 数，是性能调优的关键——Split 太多调度开销大，太少并行度不足。

```text
Split 要点：
1. 定义 —— 数据读取的原子单位，一个 Split 交给一个 Task 读
2. 来源 —— Connector 的 getSplits 接口生成（Hive 按文件/块，MySQL 按主键分片）
3. 并行度 —— Split 数直接决定初始并行度，影响 CPU 利用率和调度开销
4. 调度 —— Scheduler 把 Split 分给有空闲的 Worker，支持动态负载均衡
5. 调优 —— 通过 max-split-size 等参数控制 Split 大小，避免小文件碎片
```

```text
不同 Connector 的 Split 划分：
1. Hive/Iceberg —— 按文件或文件的块（受 max-split-size 限制）
2. MySQL/JDBC —— 按主键范围分片（如 id % N 或 BETWEEN 区间）
3. Kafka —— 按 topic 的分区（partition）划分
4. Elasticsearch —— 按索引分片（shard）划分
5. 大表查询 —— Split 越多并行越充分，但调度/元数据开销越大
```

```sql
-- 查看一个查询的 Split 数量与调度情况
EXPLAIN ANALYZE SELECT COUNT(*) FROM hive.ods.orders WHERE dt = '2024-08-14';
-- 输出中 Split 行显示 Split 数量，Task 行显示实际并行度
```

## Exchange

Exchange 是 Worker 之间传递中间数据的机制，也是 MPP 引擎「重分区」的实现。当数据需要按 Join 键或分组键重新分布到不同 Worker 时（Shuffle），就通过 Exchange 把数据从上游 Task 发送到下游 Task。Trino 的 Exchange 默认走内存缓冲（可溢写到磁盘），支持多种分发策略：单播、哈希、广播、复制。

```text
Exchange 类型与分发策略：
1. 哈希分发（Hash） —— 按 key 的 hash 分桶，用于 Join/GroupBy 的重分区
2. 广播（Broadcast） —— 把小表全量发给每个下游 Task，用于 Broadcast Join
3. 单播（Single） —— 数据全部发给一个下游，用于全局聚合
4. 复制（Replicate） —— 同一份数据复制给多个下游
5. 流水线 —— Exchange 是流式的，上游产出即发送，不等整批完成
```

```text
Exchange 相关的执行阶段：
1. 每个 Exchange 边界切出一个 Stage（Stage = 一组无 shuffle 的算子）
2. 上游 Stage 的 Task 通过 Exchange Client 发送数据
3. 下游 Stage 的 Task 通过 Exchange Operator 接收并缓存
4. exchange-buffer 内存不够时溢写磁盘（exchange.spill-enabled）
5. 数据倾斜时可在 Exchange 侧观察各 Task 的输入数据量定位热点
```

```properties
# 控制 Exchange 溢写（防止大 shuffle 打爆内存）
exchange.spill-enabled=true
spiller-spill-path=/data/trino/spill
max-spill-per-node=100GB
query-max-memory-per-node=10GB
```

## Parser/Analyzer/Planner/Optimizer

这四者是 Trino 查询处理的流水线。Parser 把 SQL 文本解析成抽象语法树（AST）；Analyzer 做语义分析，把表名/列名绑定到元数据、做类型检查；Planner 把 AST 转成逻辑执行计划（一棵算子树）；Optimizer 用大量规则（Rule）对逻辑计划做等价变换——谓词下推、列裁剪、常量折叠、Join 重排、去相关子查询等，是 Trino 查询快的核心所在。

```text
查询处理四阶段：
1. Parser —— 词法/语法分析，SQL -> AST（ANTLR 实现）
2. Analyzer —— 语义绑定：表/列/函数解析，类型推断与校验
3. Planner —— AST -> 逻辑计划（PlanNode 树），含 Join/Scan/Filter/Aggregate 节点
4. Optimizer —— 规则驱动的等价变换，IterativeOptimizer 多轮应用规则
```

```text
关键优化规则（Optimizer）：
1. 谓词下推（PushPredicateThroughJoin） —— filter 下推到 Scan 层，减少读量
2. 列裁剪（PruneUnreferencedOutputs） —— 只读用到的列，配合列式存储大幅提速
3. Join 重排（ReorderJoins） —— 基于统计信息重排 Join 顺序
4. 分区裁剪 —— 谓词含分区列时直接跳过无关分区（Hive/Iceberg 受益最大）
5. 常量折叠 / 去相关子查询 —— 简化表达式、改写子查询为 Join
```

```sql
-- 观察优化后的逻辑计划，理解规则效果
EXPLAIN (TYPE LOGICAL) SELECT u.city, SUM(o.amount)
FROM hive.ods.orders o JOIN mysql.biz.users u ON o.user_id = u.id
WHERE o.dt = '2024-08-14'
GROUP BY u.city;
-- 输出可见：分区裁剪、谓词下推、列裁剪后的 ScanNode 与 JoinNode
```

## Broadcast Join

Broadcast Join（广播连接）是把其中一张小表完整复制到每个 Worker 的内存里，然后大表在本地直接和这份「广播表」做哈希 Join，从而完全避免大表数据的 shuffle。它适用于「大表 JOIN 小表」的场景，是 Trino 处理维表关联的默认高效手段。Trino 基于统计信息自动判断是否用 Broadcast Join（默认阈值 512MB，可调）。

```text
Broadcast Join 要点：
1. 适用 —— 小表能放进每个 Worker 内存（默认 < join-distribution-type 阈值）
2. 机制 —— 小表通过 Replicate Exchange 复制到所有 Worker，大表本地 Join
3. 优势 —— 避免大表 shuffle，网络传输和内存压力小
4. 代价 —— 小表数据在每个 Worker 各存一份，小表太大时反而吃亏
5. 自动 —— 有统计信息时自动选择，无统计信息时可能误判
```

```text
控制 Broadcast Join 的参数：
1. join-distribution-type=AUTOMATIC —— 自动选择（默认）
2. join-max-broadcast-table-size —— 广播表大小阈值（默认约 100MB/512MB 视版本）
3. 手动强制 —— 用 /*+ */ 或让小表在 Join 右侧（取决于版本与规则）
4. 禁用 —— 设 join-distribution-type=PARTITIONED 可强制走 Partitioned Join
5. 注意 —— 无统计信息时 Trino 可能选错，需 ANALYZE 收集统计
```

```sql
-- Broadcast Join 典型场景：事实表 JOIN 小维表
SELECT o.order_id, u.name, o.amount
FROM hive.ods.orders o
JOIN mysql.biz.users u ON o.user_id = u.id;   -- users 是百万级小表，自动广播

-- 查看是否走了 Broadcast Join
EXPLAIN (TYPE DISTRIBUTED) SELECT ... ;
-- 输出中的 RemoteSource/Join 节点标注了 DistributionType=REPLICATED 即广播
```

## Partitioned Join

Partitioned Join（分区连接，即 Shuffle Join）是两张表都按 Join 键哈希重分布，相同 key 的数据落到同一个 Worker 再本地 Join。它适用于「大表 JOIN 大表」——无法广播小表时，只能把两边都 shuffle。代价是两张表的数据都要跨节点传输，网络和内存压力大，且对数据倾斜敏感（少数热点 key 会让个别 Worker 成为瓶颈）。

```text
Partitioned Join 要点：
1. 适用 —— 两张表都大，无法广播
2. 机制 —— 两边按 Join 键 hash 到相同 Worker，本地做哈希 Join
3. 代价 —— 两张表都要 shuffle，网络开销是 Broadcast Join 的数倍
4. 倾斜风险 —— key 分布不均时部分 Worker 过载，拖慢整体
5. 优化 —— 数据倾斜时可改 Broadcast 或做 key 加盐、提前过滤热点 key
```

```text
Join 分发策略选择逻辑：
1. 判断小表大小 —— 有统计信息且小于阈值 -> Broadcast Join
2. 无法广播 —— 两边 hash shuffle -> Partitioned Join
3. 统计信息缺失 —— Trino 可能误判，需 ANALYZE 补统计
4. 空表/极小表 —— 直接广播，成本几乎为零
5. 手动干预 —— 通过 session 参数或 hint 强制某种分发
```

```sql
-- Partitioned Join 场景：两张十亿级大表
SELECT a.order_id, b.item_name
FROM hive.ods.order_items a
JOIN hive.dwd.products b ON a.product_id = b.product_id;

-- 查看分发类型
EXPLAIN (TYPE DISTRIBUTED) SELECT ... ;
-- JoinNode 标注 DistributionType=PARTITIONED 即分区连接

-- 收集统计信息，帮助优化器正确选型
ANALYZE hive.dwd.products;
```

## Hive/Iceberg/Kafka/Elasticsearch/MongoDB/JDBC 联邦查询

联邦查询是 Trino 的杀手级特性：一个 SQL 里同时 JOIN 多个不同数据源。它把 Hive/Iceberg（数仓湖仓）、Kafka（实时消息）、Elasticsearch（检索/日志）、MongoDB（文档库）、MySQL/PG/Oracle（关系库）都抽象成统一的 catalog.schema.table，用户无感地在异构数据之间做关联分析。典型场景：实时订单（Kafka）关联用户画像（MySQL）和商品维度（Hive），一次查询出结果。

```text
常见 Connector 与用途：
1. Hive Connector —— 读 Hive 表 + HDFS/对象存储文件，兼容 Hive Metastore
2. Iceberg Connector —— 原生读写 Iceberg 表，支持 Time Travel、分区演进
3. Kafka Connector —— 把 Kafka topic 当表读（流式消费，不消费 offset）
4. Elasticsearch Connector —— 读 ES 索引，支持谓词下推和聚合下推
5. MongoDB Connector —— 读 MongoDB collection，支持字段下推
6. JDBC Connector —— 通吃 MySQL/PG/Oracle/SQLServer 等关系库
```

```properties
# 多个 catalog 并存（etc/catalog/ 目录）
# kafka.properties
connector.name=kafka
kafka.table-names=order_events,click_events
kafka.nodes=kafka1:9092,kafka2:9092

# elasticsearch.properties
connector.name=elasticsearch
elasticsearch.host=es-cluster
elasticsearch.port=9200
elasticsearch.default-schema-name=default

# mongodb.properties
connector.name=mongodb
mongodb.connection-url=mongodb://mongo1:27017
```

```sql
-- 联邦查询实战：Kafka 实时事件 JOIN MySQL 画像 JOIN Hive 商品维
SELECT e.user_id, u.tier, p.category, COUNT(*) AS cnt
FROM kafka.default.order_events e
JOIN mysql.biz.user_profile u ON e.user_id = u.user_id
JOIN hive.dwd.dim_product p ON e.product_id = p.product_id
WHERE e.event_time > TIMESTAMP '2024-08-14 00:00:00'
GROUP BY e.user_id, u.tier, p.category;
```

## 应用场景实战

### 场景一：跨数据湖与关系库的统一分析

```text
业务诉求：分析师要同时看「订单事实（Hive/Iceberg 数据湖）」和「用户等级（MySQL 业务库）」，
传统做法是把 MySQL 用户表定时同步进数仓，链路长且滞后。
Trino 联邦查询直接跨源 JOIN，实时取数。
```

```sql
-- 数据湖订单事实 关联 业务库用户等级，实时出报表
SELECT u.tier,
       COUNT(DISTINCT o.order_id) AS order_cnt,
       SUM(o.amount)             AS gmv
FROM iceberg.warehouse.fact_orders o
JOIN mysql.biz.user_profile u ON o.user_id = u.user_id
WHERE o.order_date >= DATE '2024-08-01'
GROUP BY u.tier
ORDER BY gmv DESC;

-- 结果直接输出到 BI，无需预先同步
```

```text
落地要点：
1. 业务库用只读账号 + 从库连接，避免压垮生产库
2. 大表加分区过滤条件，配合谓词下推减少扫描
3. 对高频查询结果物化成视图或缓存到数仓，避免反复查业务库
```

### 场景二：实时日志关联维度做秒级分析

```sql
-- Kafka 实时点击流 关联 ES 中的用户标签，做实时漏斗
SELECT e.user_id, t.tag, COUNT(*) AS clicks
FROM kafka.default.click_events e
JOIN elasticsearch.default.user_tags t ON e.user_id = t.user_id
WHERE e._timestamp > CURRENT_TIMESTAMP - INTERVAL '10' MINUTE
GROUP BY e.user_id, t.tag;

-- 或用 JDBC 联邦关联 Oracle 主数据
SELECT c.customer_id, c.name, o.amount
FROM jdbc_oracle.mdm.customers c
JOIN hive.dws.customer_orders o ON c.customer_id = o.customer_id
WHERE o.dt = '2024-08-14'
  AND c.region = '华东';
```

## 最佳实践与踩坑记录

### 最佳实践

1. 大表 JOIN 小表优先用 Broadcast Join，保证小表有统计信息（定期 ANALYZE）
2. 查询一律带分区过滤条件，让谓词下推和分区裁剪生效
3. 用列式存储（Parquet/ORC）+ 只读所需列，配合列裁剪提速
4. 生产部署 Coordinator 与 Worker 分离，Coordinator 不参与计算
5. 控制并发（max-concurrent-queries）和单查询内存，避免互相挤占
6. 联邦查业务库用只读从库账号，避免影响在线事务
7. 用 EXPLAIN ANALYZE 观察实际计划，定位数据倾斜和低效 Join

### 踩坑记录

```text
坑 1：无统计信息导致 Join 选错策略
结论：小表没走广播，反而触发大表 shuffle，查询慢数倍。
原因：优化器缺少表的行数/大小统计，误判了广播阈值。
解法：对关联表定期 ANALYZE 收集统计，或在会话里手动调整 join 参数。

坑 2：联邦查询拖垮业务库
结论：直接连生产 MySQL 主库做大查询，业务库 CPU 飙高、事务变慢。
原因：跨源 JOIN 会把大量谓词/扫描压力下推到业务库，无隔离。
解法：连只读从库、加连接池限制、大结果集先落数仓再查。

坑 3：Kafka Connector 当普通表反复全量扫
结论：把 Kafka topic 当事实表反复查询，每次消费全量历史，性能极差。
原因：Kafka Connector 每查询都从头消费分区，不维护 offset。
解法：Kafka 只用于短窗口实时分析，历史数据落 Iceberg/Hive 再查。

坑 4：忽略 Exchange 溢写导致 OOM
结论：大 shuffle 查询把 Worker 内存打爆，节点被 kill。
原因：未配置 exchange spill，中间结果全堆内存。
解法：开启 exchange.spill-enabled 并配置溢写路径，限制单节点内存。

坑 5：小文件导致 Split 爆炸
结论：表里百万小文件，查询生成百万 Split，调度开销压垮 Coordinator。
原因：数据写入时未合并，文件粒度太细。
解法：源端控制小文件（合并写入/compaction），调大 max-split-size 减少 Split 数。
```
