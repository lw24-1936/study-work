## 概述

Spark SQL 是 Spark 处理结构化数据的模块，提供 DataFrame/Dataset 编程 API 与 SQL 查询能力。它通过 Catalyst 优化器做逻辑/物理计划优化，通过 Tungsten 做内存与 CPU 优化，通过 AQE 做运行时自适应优化，通过 Codegen 做整段代码生成，最终将查询翻译成高效的 Java 字节码在集群上执行。

```text
要点
- 统一入口 SparkSession，支持 SQL 与 DataFrame/Dataset API
- Catalyst 负责查询优化：解析、逻辑优化、物理计划、代码生成
- Tungsten 负责内存管理、二进制编码与缓存友好布局
- AQE 在运行时根据真实数据统计动态调整执行计划
- Codegen 将多个算子融合成一段 Java 代码，减少虚函数调用
```

## 核心概念

Spark SQL 的核心概念围绕「API 抽象」与「引擎优化」两条线展开：DataFrame/Dataset 是面向用户的编程抽象，Catalyst/Tungsten/AQE/Codegen 是底层引擎的四项关键技术。掌握这六个概念，就掌握了 Spark SQL 的全貌。

### DataFrame

DataFrame 是带 Schema 的分布式数据集合，可以理解为"结构化表"，由 Row 对象组成，每一列都有名称和类型。相比 RDD 的无类型 Row 集合，DataFrame 保留了 Schema 元数据，使 Catalyst 能在编译期做列裁剪、谓词下推等优化。DataFrame 是类型宽松（untyped）的 API，在运行时才校验列与类型。

```text
要点
- 带 Schema 的分布式 Row 集合，类似关系表
- 通过 SparkSession.read 或 SQL 创建
- 无类型 API：列名/类型在运行期解析
- 支持列裁剪、谓词下推等优化
- 是 Spark ML 与流处理的标准数据结构
```

```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("DataFrameDemo").getOrCreate()

# 创建带 Schema 的 DataFrame
df = spark.createDataFrame([
    ("Alice", 28, "北京"),
    ("Bob", 35, "上海"),
    ("Cathy", 31, "北京"),
], ["name", "age", "city"])

df.printSchema()   # 打印 Schema：name/age/city 三列

# DataFrame 变换：过滤 + 聚合
result = (df.filter(F.col("age") > 30)
            .groupBy("city")
            .agg(F.avg("age").alias("avg_age")))

result.show()
```

### Dataset

Dataset 是强类型（typed）的分布式数据集合，结合了 RDD 的类型安全与 Catalyst 的优化能力。在 Scala/Java 中通过 case class 定义类型，编译器在编译期即可发现类型错误；在 Python 中 DataFrame 与 Dataset 合二为一（没有单独的强类型 Dataset）。Dataset 在需要复杂业务对象与类型安全的场景下更合适。

```text
要点
- 强类型 API：编译期类型检查（Scala/Java）
- 通过 case class 或 Encoder 定义元素类型
- 兼具 RDD 的类型安全与 Catalyst 优化
- Python 中只有 DataFrame，无独立 Dataset
- 通过 .as[CaseClass] 把 DataFrame 转为 Dataset
```

```scala
import org.apache.spark.sql.{SparkSession, Dataset}

case class Person(name: String, age: Int, city: String)

val spark = SparkSession.builder().appName("DatasetDemo").master("local[2]").getOrCreate()
import spark.implicits._

// 构造强类型 Dataset
val ds: Dataset[Person] = spark.read
  .option("header", "true")
  .csv("/data/people.csv")
  .as[Person]   // 转为强类型 Dataset

// 编译期类型安全：可直接访问字段且类型错误在编译期暴露
val adults = ds.filter(_.age >= 18)          // 类型安全的 lambda
val names: Dataset[String] = adults.map(_.name)

names.show()
```

### Catalyst

Catalyst 是 Spark SQL 的查询优化器，采用基于规则的优化（RBO）与基于代价的优化（CBO）。它将 SQL/DataFrame 先解析成未解析的逻辑计划，经过分析、逻辑优化（谓词下推、列裁剪、常量折叠）、物理计划生成（选择 Join 策略）等多个阶段，最终生成可执行的物理计划。Catalyst 用 Scala 的 Tree 结构表示计划，用规则对树做递归变换。

```text
要点
- 流程：解析 → 分析 → 逻辑优化 → 物理计划 → 代码生成
- 逻辑优化：谓词下推、列裁剪、常量折叠、投影合并
- 物理计划：选择 BroadcastHashJoin、SortMergeJoin 等策略
- 基于规则（RBO）+ 基于代价（CBO）双管齐下
- 用 explain() 可查看各阶段计划
```

```python
df = spark.read.parquet("/data/orders")

# 查询：观察 Catalyst 如何优化
query = (df.filter("amount > 100")
           .select("uid", "amount")
           .groupBy("uid")
           .agg({"amount": "sum"}))

# 查看逻辑计划与物理计划
query.explain("extended")
```

### Tungsten

Tungsten 是 Spark SQL 的底层执行引擎，通过内存管理与 CPU 优化提升执行效率。它使用堆外内存（off-heap）与二进制格式存储数据，避免 JVM 对象头与 GC 开销；使用缓存友好的列式内存布局；并通过整段代码生成减少虚函数调用与对象分配。Tungsten 让 Spark SQL 接近手写代码的性能。

```text
要点
- 二进制编码存储，避免 Java 对象序列化开销
- 支持堆外内存，减少 JVM GC 压力
- 列式内存布局，提升 CPU 缓存命中率
- 通过 Unsafe API 直接操作内存
- 与 Codegen 配合，消除虚函数调用
```

```scala
val spark = SparkSession.builder()
  .appName("TungstenDemo")
  .config("spark.sql.tungsten.enabled", "true")          // 启用 Tungsten
  .config("spark.memory.offHeap.enabled", "true")        // 启用堆外内存
  .config("spark.memory.offHeap.size", "2g")
  .master("local[2]")
  .getOrCreate()

// Tungsten 优化的算子：聚合、排序、Join 等
val df = spark.range(1, 1000000L)
val agg = df.groupBy((df("id") % 100).alias("bucket")).count()

agg.show()
```

### AQE

AQE（Adaptive Query Execution，自适应查询执行）是 Spark 3.0 引入的运行时优化机制。它在 Shuffle 边界收集真实的数据统计，动态调整执行计划：合并小分区（Coalesce）、优化数据倾斜 Join（Skew Join）、动态切换 Join 策略（如 SortMergeJoin 转 BroadcastHashJoin）。AQE 解决了静态优化器无法预知数据分布的问题。

```text
要点
- Spark 3.0 引入，默认关闭，3.2+ 默认开启
- 合并小分区：减少 Task 数量与调度开销
- 倾斜 Join 优化：对倾斜分区拆分处理
- 动态切换 Join 策略：根据实际大小改广播 Join
- 在 Shuffle 边界基于真实统计做决策
```

```scala
val spark = SparkSession.builder()
  .appName("AQEDemo")
  .config("spark.sql.adaptive.enabled", "true")                    // 开启 AQE
  .config("spark.sql.adaptive.coalescePartitions.enabled", "true") // 合并小分区
  .config("spark.sql.adaptive.skewJoin.enabled", "true")           // 倾斜 Join 优化
  .config("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256MB")
  .master("local[2]")
  .getOrCreate()

val big = spark.range(0, 100000000L)
val small = spark.range(0, 1000L)

// AQE 会在运行时判断 small 是否可广播，并处理倾斜
val joined = big.join(small, "id")
joined.explain("adaptive")   // 查看自适应执行计划
```

### Codegen

Codegen（代码生成）是 Spark SQL 的核心加速技术，把一组算子的执行逻辑编译成一段优化的 Java 字节码，避免逐行虚函数调用与中间对象分配。它分为整段代码生成（WholeStageCodegen，把多个算子融合进一个函数）与表达式代码生成（Expression Codegen）。开启 Codegen 后，典型查询可获得数倍性能提升。

```text
要点
- WholeStageCodegen：把多个算子融合成一段 Java 代码
- 减少虚函数调用与中间对象的创建
- 表达式代码生成：把表达式树编译成高效字节码
- 可通过 spark.sql.codegen.wholeStage 配置开关
- 用 explain("codegen") 查看生成的代码片段
```

```scala
val spark = SparkSession.builder()
  .appName("CodegenDemo")
  .config("spark.sql.codegen.wholeStage", "true")   // 开启整段代码生成
  .master("local[2]")
  .getOrCreate()

val df = spark.range(0, 10000000L)
val result = df.filter("id % 2 = 0").selectExpr("id * 2 as double_id", "id + 1 as next_id")

// 查看代码生成计划，带 * 的节点表示启用了 WholeStageCodegen
result.explain("codegen")
result.count()
```

## 工作原理

一条 Spark SQL 查询从提交到出结果，走完「解析 → 分析 → 逻辑优化 → 物理计划 → 代码生成 → 执行」六步。Catalyst 负责前四步的计划生成与优化，Tungsten 与 Codegen 负责执行层的加速，AQE 在执行中途插入运行时调整。

```text
完整链路（以 SELECT 为例）：
SQL/API -> Parser 解析成 Unresolved LogicalPlan
        -> Analyzer 绑定 Catalog 元数据（表/列校验、类型推断）
        -> Optimizer 逻辑优化（谓词下推、列裁剪、常量折叠）
        -> QueryPlanner 生成 PhysicalPlan（选 Join 策略、Exchange 布局）
        -> Codegen 把算子融合成 Java 字节码
        -> Tungsten 二进制内存布局上执行 -> 返回结果
```

```text
各阶段产出物：
1. Unresolved LogicalPlan —— 语法树，列名/表名未绑定
2. LogicalPlan —— 绑定 Catalog 后的逻辑计划，含列类型
3. Optimized LogicalPlan —— 规则优化后的逻辑计划
4. PhysicalPlan —— 含 Exchange/Shuffle/具体算子，可执行
5. SparkPlan 执行 —— Tungsten 内存 + Codegen 代码执行
```

AQE 在这条链路中的位置：物理计划生成后、真正执行前，Spark 3.0+ 会先跑一个查询准备阶段，在 Shuffle 边界插入统计收集点；每轮 Shuffle 结束后拿真实分区大小重新做决策：合并小分区、切换 Join 策略、拆分倾斜分区。这等于把「优化器不知道的真实数据分布」在执行期补进计划。

```text
AQE 三个运行时优化：
1. Coalesce Partitions —— 按真实输出大小合并小分区
2. Optimize Skew Join —— 倾斜分区按比例拆分，配合复制小表侧
3. Switch Join Strategy —— 一侧数据量小于广播阈值时，SortMergeJoin 降级 BroadcastHashJoin
```

## 常用命令与配置

```shell
# spark-sql CLI：交互式执行 SQL（连接 Spark Thrift Server 或本地会话）
spark-sql --master yarn --executor-memory 4g
spark-sql -e "SELECT count(*) FROM ods.orders WHERE dt='2026-08-18'"
spark-sql -f etl.sql                       # 执行 SQL 文件

# spark-shell：交互式写 DataFrame/Dataset/SQL
spark-shell --master yarn --num-executors 10 --executor-cores 4

# 提交 Spark SQL 应用
spark-submit --class com.example.SqlJob --master yarn --deploy-mode cluster app.jar
spark-submit --py-files etl.py --master yarn etl_main.py
```

```text
常用运行时配置（--conf 或代码内 spark.conf.set）：
spark.sql.shuffle.partitions             Shuffle 分区数，默认 200，小数据调小大数据调大
spark.sql.adaptive.enabled               AQE 开关，3.2+ 默认 true
spark.sql.autoBroadcastJoinThreshold     广播阈值，默认 10MB
spark.sql.files.maxPartitionBytes        读文件时单个分区的最大字节数，默认 128MB
spark.sql.session.timeZone               会话时区，影响时间函数与分区裁剪
```

## 应用场景实战

### 场景一：基于 DataFrame 的订单聚合分析

使用 DataFrame API 完成订单数据的过滤、多表 Join、聚合与排序，展示 Catalyst 优化与常见算子组合。

```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("OrderAnalysis").getOrCreate()

orders = spark.read.parquet("/data/orders")        # 订单表
users = spark.read.parquet("/data/users")          # 用户表

# 过滤 + Join + 聚合 + 排序，全程由 Catalyst 优化
result = (orders.filter(F.col("status") == "paid")
                .join(users, "uid", "left")
                .groupBy("city")
                .agg(F.sum("amount").alias("total_amount"),
                     F.countDistinct("uid").alias("buyer_cnt"))
                .orderBy(F.desc("total_amount")))

result.show(20)
```

### 场景二：AQE 解决数据倾斜的 Join

构造一个带倾斜 key 的数据集，通过开启 AQE 的 skewJoin 优化，观察倾斜 Join 的拆分与加速效果。

```scala
import org.apache.spark.sql.functions._

val spark = SparkSession.builder()
  .appName("SkewJoinDemo")
  .config("spark.sql.adaptive.enabled", "true")
  .config("spark.sql.adaptive.skewJoin.enabled", "true")
  .getOrCreate()

import spark.implicits._

// 构造一个极度倾斜的 key 分布：key=1 占绝大多数
val big = spark.range(0, 10000000L).map { id =>
  val key = if (id < 9000000L) 1L else (id % 100)
  (key, id)
}.toDF("key", "value")

val dim = spark.range(1, 100L).toDF("key")   // 维度表

// 倾斜 Join：AQE 会把 key=1 的超大分区拆分成多个子任务
val joined = big.join(dim, "key")
joined.explain("adaptive")
println(s"结果行数 = ${joined.count()}")
```

### 场景三：SQL 方式做离线数仓 ETL

用纯 SQL 语法从 Hive 原始表读取数据、清洗聚合、动态分区写回结果表，这是离线数仓最常见的每日任务形态，直接由 Spark SQL 引擎执行。

```sql
-- 建结果表（按日期分区）
CREATE TABLE IF NOT EXISTS dws.daily_sales (
    city       STRING,
    gmv        DECIMAL(20,2),
    order_cnt  BIGINT
) USING PARQUET PARTITIONED BY (dt STRING);

-- 清洗 + 聚合 + 动态分区写入
INSERT OVERWRITE TABLE dws.daily_sales PARTITION (dt)
SELECT city, SUM(amount) AS gmv, COUNT(*) AS order_cnt, dt
FROM ods.orders
WHERE dt = '2026-08-18'
  AND status = 'paid'
  AND amount > 0
GROUP BY city, dt;
```

```text
要点：
- INSERT OVERWRITE + 动态分区，一条 SQL 完成写入，避免先查后写两步
- WHERE 过滤下推到文件扫描层（谓词下推），减少读取量
- 列裁剪只取 amount/status/dt/city 四列
```

## 性能与调优

```text
Spark SQL 调优主线：数据量 -> 分区/并行度 -> 内存 -> Join/倾斜 -> 文件格式
1. 并行度：spark.sql.shuffle.partitions 与数据量匹配（每个分区约 64~128MB）
2. 广播：小表小于 autoBroadcastJoinThreshold 自动广播；更大用 broadcast hint 或调阈值
3. 数据倾斜：开启 AQE skewJoin；聚合倾斜用两阶段聚合（加盐打散）
4. 文件格式：Parquet/ORC + Snappy/ZSTD，列式存储配合列裁剪
5. 分区/分桶：按过滤频率最高的列分区；Join 列分桶可消除 Shuffle
6. 谓词下推与列裁剪：过滤条件写清楚，别在分区列上套函数
7. 资源配比：executor 内存与 core 匹配数据量，避免 OOM 与频繁 GC
```

```text
常见性能问题速查：
现象                          排查方向
单个 Task 处理大量数据          增加分区数/并行度
聚合或 Join 慢且有倾斜          AQE skewJoin 或两阶段聚合
小文件多、NameNode 压力大       合并分区并控制输出文件数（coalesce/repartition）
GC 频繁、Full GC             检查堆内存与 off-heap 配比、广播表大小
```

## 安全与权限

```text
Spark SQL 安全体系（与 Hadoop 生态一致）：
1. 元数据权限 —— 通过 Hive Metastore 集成，库/表/列权限由 Ranger 统一下发
2. SQL 访问控制 —— Spark Thrift Server 场景可接 Ranger 做 SQL 级授权
3. 认证 —— 集群开启 Kerberos 时，提交任务需带 principal/keytab
4. 数据脱敏 —— 敏感列做掩码：Ranger 列级 masking 或视图封装
5. 网络与端口 —— Spark UI/History Server 不暴露公网，走内网或网关
6. 静态加密 —— 落盘数据用 HDFS 透明加密或列级加密
```

```shell
# Kerberos 环境下提交 Spark SQL 任务
kinit -kt /etc/security/keytabs/spark.keytab spark@EXAMPLE.COM
spark-submit --principal spark@EXAMPLE.COM \
  --keytab /etc/security/keytabs/spark.keytab \
  --class com.example.SqlJob --master yarn app.jar
```

## 故障排查

```text
排查顺序：看日志 -> 看执行计划 -> 看资源配置 -> 看数据特征
1. 任务失败/Stage 重试 —— 先看 executor stderr 日志，多数是 OOM 或数据倾斜
2. 查询慢 —— explain() 看是否全表扫描、Join 策略错误、谓词未下推
3. OOM —— 区分 driver OOM（collect 大结果）与 executor OOM（分区过大/广播过大）
4. 结果错误 —— 检查 NULL 处理、会话时区、动态分区覆盖范围
5. 找不到表/列 —— Catalog 元数据问题，确认 catalogImplementation 与 Metastore 连接
```

```shell
# 常用排查命令
spark-sql -e "SET -v"                        # 查看全部生效配置
yarn logs -applicationId application_xxx     # 拉取应用日志
hdfs dfs -ls /tmp/spark-events               # 历史任务事件文件
spark-submit --conf spark.ui.port=4040 ...   # 本地调试实时看 SQL 页面
```

## 常见问题

```text
Q1: DataFrame 和 Dataset 有什么区别？
A: DataFrame 是 Dataset[Row] 的类型别名，弱类型、列在运行期校验；Dataset 强类型、编译期校验（Scala/Java）。Python 里只有 DataFrame，没有独立 Dataset。

Q2: Catalyst 的 RBO 和 CBO 有什么区别？
A: RBO（基于规则）按固定规则优化，如谓词下推、列裁剪；CBO（基于代价）用统计信息估算各计划代价选最优，如 Join 顺序与策略。RBO 先行，CBO 需要 ANALYZE TABLE 收集统计信息。

Q3: AQE 在什么版本默认开启？
A: Spark 3.0 引入（默认关闭），3.2 起默认开启。开启后自动合并小分区、优化倾斜 Join、动态切换 Join 策略。

Q4: 为什么 DataFrame 比 RDD 快？
A: RDD 无法利用 Schema，只能按 Java 对象序列化；DataFrame 带 Schema，Catalyst 可优化、Tungsten 二进制存储、Codegen 消除虚函数调用。

Q5: broadcast hint 和自动广播阈值的关系？
A: 小于 spark.sql.autoBroadcastJoinThreshold（默认 10MB）的表自动广播；超过阈值但确知是小表时，用 broadcast(df) hint 强制广播。

Q6: 为什么我的查询没有走分区裁剪？
A: 常见原因：过滤条件不是分区列；对分区列套了函数（如 date_format(dt, 'yyyy-MM-dd') = '2026-08-18'）；分区列类型与比较值不匹配触发隐式转换。

Q7: INSERT OVERWRITE 分区表会覆盖哪些数据？
A: 静态分区只覆盖指定分区；动态分区（PARTITION (dt)）只覆盖本次写入涉及的分区，不会清空整表。
```

## 面试题

```text
1. 一条 Spark SQL 从提交到执行经历了哪些阶段？
   答：Parser 解析成 Unresolved LogicalPlan -> Analyzer 绑定 Catalog 生成 LogicalPlan -> Optimizer 规则优化 -> Planner 生成 PhysicalPlan -> 代码生成 + Tungsten 执行。AQE 在 Shuffle 边界做运行时调整。

2. Catalyst 优化器做了哪些典型优化？
   答：谓词下推（过滤提前到扫描/Join 前）、列裁剪（只读需要的列）、常量折叠、投影合并、Join 重排与策略选择（广播/排序归并）。逻辑优化基于规则树变换，物理层选 Join 策略与数据布局。

3. 什么是数据倾斜？Spark SQL 怎么处理？
   答：某个 key 数据量远大于其它 key，导致单个 Task 处理大部分数据。处理：AQE skewJoin 自动拆分倾斜分区；聚合倾斜用加盐两阶段聚合；Join 倾斜可广播小表或拆分大表侧。

4. WholeStageCodegen 的原理？
   答：把相邻多个算子（如 Scan -> Filter -> Project -> Agg）的表达式合并成一个 Java 方法生成字节码，行数据在局部变量间传递，消除逐算子虚函数调用与中间对象分配。

5. Tungsten 为什么快？
   答：二进制行格式避免 Java 对象头与序列化开销；列式缓存友好布局提升 CPU 缓存命中率；Unsafe API 直接操作内存、支持堆外；配合 Codegen 消除虚调用。

6. 大表 join 大表如何优化？
   答：按 Join 列分桶（bucket join 消除 Shuffle）；过滤后广播缩小的一侧；开启 AQE 让运行时切换策略；对倾斜 key 单独处理（拆分/过滤/加盐）。

7. Spark SQL 和 Hive SQL 的区别？
   答：Spark SQL 用 Spark 引擎（Catalyst + Tungsten + Codegen），Hive 用 MapReduce/Tez/Spark 引擎；Spark SQL 在交互式与迭代场景更快。两者可共用 Hive Metastore，常配合使用。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优先用 DataFrame/Dataset API，而非 RDD，以充分享受 Catalyst + Tungsten + AQE 的自动优化。
2. 尽量用 Spark SQL 内建函数（`functions._`）而非自定义 UDF，内建函数可被优化与代码生成。
3. 大表 join 小表时，把小表 broadcast，避免 SortMergeJoin 的全量 Shuffle。
4. 开启 AQE 并合理配置，让运行时自适应合并小分区、优化倾斜 Join。
5. 用 explain() 定期检查执行计划，确认谓词下推、列裁剪、Join 策略符合预期。
6. 写 Parquet/ORC 等列式格式，配合列裁剪与谓词下推提升读写性能。
7. 避免在循环中反复创建临时视图，改用 DataFrame 变量复用计划。
8. 生产环境固定 spark.sql.session.timeZone 与字段类型，避免隐式转换导致结果漂移。
9. 定期 ANALYZE TABLE 更新统计信息，让 CBO 与 AQE 的决策更准确。

### 踩坑记录

```text
坑 1：隐式类型转换导致 UDF 性能极差
结论：查询极慢，CPU 占用高
原因：Python/Scala UDF 无法参与 Catalyst 优化与 Codegen，逐行序列化调用
解法：用内建函数替代 UDF；必须用 UDF 时改用 Pandas UDF（向量化）减少开销

坑 2：AQE 未生效
结论：配置了 AQE 参数但执行计划无自适应优化
原因：Spark 版本低于 3.0 不支持 AQE，或 spark.sql.adaptive.enabled 被覆盖为 false
解法：升级到 Spark 3.2+（默认开启），并确认配置优先级正确

坑 3：explain 看到全表扫描
结论：查询走了全表扫描而非分区裁剪
原因：过滤条件不是分区列，或使用了导致无法下推的函数（如对分区列做运算）
解法：把过滤条件放到分区列上，避免在分区列上套函数，保持谓词可直接下推

坑 4：Join 策略选了 SortMerge 导致慢
结论：小表 Join 却走了 Shuffle，性能差
原因：小表超过了广播阈值，或未用 broadcast hint
解法：对确知的小表用 broadcast(df) hint，或调大 spark.sql.autoBroadcastJoinThreshold

坑 5：DataFrame 与 Dataset 混用报错
结论：编译期或运行期类型不匹配
原因：DataFrame 是 Row 类型，Dataset 是强类型，用 .as[T] 转换时 Schema 与 case class 不一致
解法：确保 case class 字段名与 DataFrame 列名完全一致，或用 Encoders 显式映射

坑 6：动态分区过多导致 executor OOM
结论：写入时报 ExecutorLostFailure 或 OOM
原因：一条 SQL 写出成千上万个动态分区，单个 Executor 打开过多输出流
解法：控制分区列粒度（如按天而非按小时），或调大 spark.sql.shuffle.partitions 分散输出

坑 7：会话时区不一致导致日期分区对不上
结论：任务在凌晨跑出的分区日期与预期差一天
原因：Driver/Executor 时区不一致，date_format 等函数结果漂移
解法：统一设置 spark.sql.session.timeZone 与 JVM 时区（Asia/Shanghai）
```
