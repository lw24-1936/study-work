## 概述

Spark 是一个基于内存计算的分布式计算引擎，采用 Master/Worker 架构。核心思想是把应用拆分成 Driver 进程 + 若干 Executor 进程，由 Cluster Manager 统一调度资源，把用户编写的程序翻译成 Job → Stage → Task 三级执行粒度，分发到集群各节点并行执行。

```text
要点
- Driver：运行 main 方法、生成执行计划、调度任务的"大脑"
- Executor：真正干活的工作进程，负责执行 Task 并缓存数据
- Cluster Manager：管理集群资源、分配 Executor 的调度器
- Application：用户提交的一个 Spark 应用（一份代码 + 资源）
- Job：一次 Action 触发的一整条计算链
- Stage：按 Shuffle 边界切分出的可并行执行单元
- Task：Stage 内发送到单个分区的具体计算任务
```

## Driver

Driver 是运行在客户端或集群节点上的一个进程，负责解析用户代码、把 RDD/DataFrame 的逻辑计划转换成物理执行计划，并通过 DAGScheduler 把执行计划切分成 Stage 和 Task。Driver 还负责与 Cluster Manager 通信申请 Executor，调度 Task 到 Executor，并收集最终结果。Driver 是单点，一旦崩溃整个 Application 就会失败。

```text
要点
- 持有 SparkContext / SparkSession 入口
- 负责 Job 的 DAG 构建与 Stage/Task 划分
- 通过 RPC 向 Executor 下发 Task 并回收结果
- 维护元数据（RDD 血缘、累加器、广播变量）
- 单点故障：Driver 崩溃则整个应用失败
```

```scala
import org.apache.spark.sql.SparkSession

// Driver 进程中的入口代码：创建 SparkSession
val spark = SparkSession.builder()
  .appName("DriverDemo")
  .master("spark://master:7077") // 交给 Cluster Manager 管理
  .config("spark.driver.memory", "2g")
  .getOrCreate()

// 这里的逻辑都在 Driver 端执行：惰性构建执行计划
val df = spark.read.parquet("/data/events")
  .filter("date = '2026-08-14'")
  .groupBy("uid")
  .count()

// Action 触发时，Driver 生成 Job 并调度 Task
df.show()

spark.stop()
```

## Executor

Executor 是运行在 Worker 节点上的工作进程，负责真正执行 Task、把结果写回 Driver 或持久化到存储系统。每个 Executor 独占一定数量的 CPU Core 和内存，同一个 Application 的所有 Task 在它的多个 Executor 上并行运行。Executor 内部使用线程池，一个 Core 同时只能跑一个 Task。

```text
要点
- 生命周期由 Cluster Manager 分配、随 Application 结束而回收
- 内部按 Core 数量并行执行 Task（一核一 Task）
- 负责 RDD/DataFrame 的分区数据缓存（MemoryStore）
- 执行 Shuffle 时的数据读写与网络传输
- 与 Driver 通过心跳 + RPC 通信，异常会被重新调度
```

```shell
# 提交应用时通过配置指定 Executor 的规格
spark-submit \
  --class com.example.MyJob \
  --master yarn \
  --deploy-mode cluster \
  --num-executors 20 \
  --executor-cores 4 \
  --executor-memory 8g \
  --driver-memory 4g \
  my-job.jar
```

## Cluster Manager

Cluster Manager 是负责集群资源管理与调度的组件，负责接收 Driver 的资源申请，在 Worker 节点上启动 Executor，并在 Executor 故障时回收/重新分配资源。Spark 支持多种 Cluster Manager：Standalone（自带）、YARN、Kubernetes 和 Mesos（已退役）。

```text
要点
- Standalone：Spark 自带，简单易用，适合小规模集群
- YARN：Hadoop 生态默认，支持资源队列与多租户
- Kubernetes：云原生，动态扩缩容，适合容器化环境
- 只负责"给资源"，不参与具体任务计算
- 通过 spark.master 配置选择，如 yarn / k8s://... / spark://...
```

```yaml
# 使用 Kubernetes 作为 Cluster Manager 时的提交示例
spark-submit \
  --master k8s://https://k8s.example.com:6443 \
  --deploy-mode cluster \
  --conf spark.kubernetes.container.image=spark:3.5.0 \
  --conf spark.kubernetes.namespace=bigdata \
  --conf spark.executor.instances=10 \
  --conf spark.kubernetes.authenticate.driver.serviceAccountName=spark \
  local:///opt/spark/examples/jars/my-job.jar
```

## Application

Application 是用户提交的一个完整 Spark 程序，由 Driver 进程 + 它申请到的若干 Executor 构成。一个 Application 对应一个 SparkContext/SparkSession，拥有独立的资源与命名空间，各 Application 之间默认不共享内存和缓存。在 YARN/K8s 上，一个 Application 通常对应一个独立的运行实例。

```text
要点
- 一份可执行代码 + 运行所需资源的总和
- 内部包含一个 Driver 和一组 Executor
- 不同 Application 之间隔离，不共享 SparkContext
- 通过 spark-submit 或编程方式提交
- 资源由 Cluster Manager 按 Application 维度分配
```

```bash
# 通过 spark-submit 提交一个 Application
spark-submit \
  --name "daily-agg-job" \
  --master yarn \
  --deploy-mode cluster \
  --conf spark.yarn.queue=etl \
  --conf spark.sql.shuffle.partitions=200 \
  daily_agg.py
```

## Job

Job 是 Spark 执行的顶层单元，每调用一次 Action（如 collect、count、save）就会触发一个 Job。一个 Application 中可以包含多个 Job，它们由 Driver 的 DAGScheduler 依次或并发调度。每个 Job 对应一段完整的 DAG，从数据源读入到最终写出结果。

```text
要点
- 一次 Action 触发一个 Job
- Job 由 DAGScheduler 切分为多个 Stage
- 一个 Application 可包含多个 Job
- Job 的执行结果是 Action 的返回值或写入的副作用
- 惰性求值下，多个 Transformation 只会组成一个 Job
```

```scala
val rdd = sc.textFile("/data/logs")          // 惰性，不触发 Job
  .flatMap(_.split(" "))                     // 惰性
  .map((_, 1))                               // 惰性

val result = rdd.reduceByKey(_ + _)          // 惰性

result.collect()          // Action → 触发第一个 Job
result.saveAsTextFile("/out/wordcount")      // Action → 触发第二个 Job
```

## Stage

Stage 是 Job 内部按 Shuffle 边界切分的执行阶段。DAGScheduler 从最后一个 RDD 反向遍历血缘，遇到窄依赖就合并到同一 Stage，遇到宽依赖（Shuffle）就切分新 Stage。同一 Stage 内的分区可以完全并行、无需等待其他分区；Stage 之间必须等上游 Shuffle 数据落盘后才能继续。

```text
要点
- 切分依据是 Shuffle（宽依赖）边界
- Stage 内是窄依赖，可并行计算
- Stage 间存在数据依赖，需等待上游完成
- ShuffleMapStage 写 Shuffle 数据，ResultStage 产出最终结果
- Stage 数量 = Shuffle 次数 + 1（大致）
```

```python
from pyspark import SparkContext

sc = SparkContext(appName="StageDemo")
rdd = sc.parallelize(range(100), 4)

# map 是窄依赖，和上一个操作合并进同一 Stage
mapped = rdd.map(lambda x: x * 2)

# groupByKey 是宽依赖，触发 Shuffle，切分出新的 Stage
grouped = mapped.groupBy(lambda x: x % 3)

# 最终 count 是 Action，生成 ResultStage
print(grouped.mapValues(len).collect())
```

## Task

Task 是 Spark 最小的执行单元，一个 Task 处理一个分区的数据。Stage 内有多少个分区，就有多少个 Task，它们会被 Driver 调度到不同 Executor 的 Core 上并行执行。Task 执行失败会被自动重试（默认最多 4 次），只有所有 Task 成功，整个 Stage 才算完成。

```text
要点
- 一个 Task 只处理一个分区的数据
- Task 数量 = 该 Stage 的分区数
- 由 Driver 通过 TaskScheduler 分配到 Executor
- 失败自动重试，重试次数受 spark.task.maxFailures 控制
- 可通过 Spark UI 查看每个 Task 的耗时、Shuffle 读写量
```

```scala
// 通过分区数控制 Task 数量
val rdd = sc.textFile("/data/events")   // 默认按 HDFS block 决定分区
println(s"分区数 = ${rdd.getNumPartitions}")   // 分区数即 Task 数

// repartition 增加分区，会触发 Shuffle，Task 数随之变化
val repartitioned = rdd.repartition(20)
println(s"重分区后分区数 = ${repartitioned.getNumPartitions}")
```

## 应用场景实战

### 场景一：多 Job 的 ETL 批处理流水线

在一个 Application 中串联多个 Job，完成"清洗 → 聚合 → 落地"的完整链路，观察 Job 与 Stage 的对应关系。

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .appName("ETLPipeline") \
    .master("local[4]") \
    .getOrCreate()

# 读取日志数据
logs = spark.read.text("/data/access.log")

# Job 1：清洗并落盘中间结果（第一次 save 触发第一个 Job）
cleaned = logs.filter("value is not null and value != ''")
cleaned.write.mode("overwrite").parquet("/tmp/cleaned")

# Job 2：聚合统计（第二次 save 触发第二个 Job）
cleaned_df = spark.read.parquet("/tmp/cleaned")
agg = cleaned_df.groupBy("value").count().orderBy("count", ascending=False)
agg.write.mode("overwrite").csv("/tmp/agg_result")

print("ETL 完成，共触发 2 个 Job")
spark.stop()
```

### 场景二：观察 Stage 与 Shuffle 的关系

通过一个包含 groupByKey 的任务，在 Spark UI 或日志中观察 Shuffle 导致的 Stage 切分，理解 Task 数量与分区的关系。

```scala
import org.apache.spark.{SparkConf, SparkContext}

val conf = new SparkConf()
  .setAppName("StageObservation")
  .setMaster("local[4]")
  .set("spark.ui.port", "4040")

val sc = new SparkContext(conf)
sc.setLogLevel("WARN")

// 8 个分区 = 第一个 Stage 的 8 个 Task
val rdd = sc.parallelize(1 to 1000, 8)

val result = rdd
  .map(x => (x % 10, x))       // 窄依赖，Stage 0 内
  .groupByKey()                 // 宽依赖 → Shuffle，切分 Stage 1
  .mapValues(_.sum)             // 窄依赖，Stage 1 内

println(s"结果分区数 = ${result.getNumPartitions}")
result.collect().foreach(println)

// 打开浏览器访问 http://localhost:4040 查看 Job/Stage/Task 明细
sc.stop()
```

## 最佳实践与踩坑记录

### 最佳实践

1. 合理设置 Executor 规格：单个 Executor 内存不宜过大（推荐 4~16g），Core 数控制在 4~8，避免 Executor 过大导致 GC 压力与资源碎片。
2. 使用动态资源分配：开启 `spark.dynamicAllocation.enabled=true`，让集群按负载自动增减 Executor，避免资源浪费。
3. 优先使用窄依赖算子：尽量用 reduceByKey/aggregateByKey 代替 groupByKey，减少 Shuffle 数据量与网络传输。
4. 控制 Shuffle 分区数：根据数据量设置 `spark.sql.shuffle.partitions` 与 `spark.default.parallelism`，避免 Task 过少导致单分区过大或过多导致调度开销。
5. 监控 Spark UI：提交后关注 Stage 的 Shuffle Read/Write、Task 倾斜、GC 时间，及时定位性能瓶颈。
6. Driver 只做轻量工作：避免在 Driver 端 collect 大量数据或执行大循环，防止 Driver OOM。
7. 生产环境用 cluster 模式：`--deploy-mode cluster` 让 Driver 与 Executor 同集群运行，避免客户端网络抖动导致任务失败。

### 踩坑记录

```text
坑 1：Driver OOM
结论：Driver 进程内存不足导致应用失败
原因：在 Driver 端 collect 了过大的结果集，或维护了超大广播变量/累加器
解法：改用 write 落盘而非 collect；调大 spark.driver.memory；广播变量用 SparkContext.broadcast

坑 2：Executor 数量计算错误
结论：提交的 Executor 数量与预期不符，任务并行度不足
原因：混淆了 --num-executors（实例数）与 --executor-cores（每实例核数），实际并行度是两者乘积
解法：并行 Task 数 = executor 数 × 每 executor 核数，按此反推资源配置

坑 3：Shuffle 分区数过多导致调度开销
结论：小数据量任务却跑出上千个 Task，总耗时反而更长
原因：spark.sql.shuffle.partitions 默认 200，未按数据量调小，大量空 Task 徒增调度成本
解法：小数据场景调小 shuffle 分区数，或开启 AQE 自动合并小分区

坑 4：groupByKey 导致 OOM
结论：Executor 内存溢出，Shuffle 阶段失败
原因：groupByKey 把同 key 的所有 value 集中到单分区，数据倾斜时单 Task 内存爆炸
解法：改用 reduceByKey 预聚合，或对倾斜 key 加随机前缀打散

坑 5：Standalone 模式下资源竞争
结论：多个 Application 争抢资源导致整体变慢
原因：Standalone 模式缺少像 YARN 那样的队列隔离与抢占机制
解法：迁移到 YARN 或 Kubernetes，按队列/命名空间做资源隔离
```
