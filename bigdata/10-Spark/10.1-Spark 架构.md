## 概述

Spark 是一个基于内存计算的分布式计算引擎，采用 Master/Worker 架构。核心思想是把应用拆分成 Driver 进程 + 若干 Executor 进程，由 Cluster Manager 统一调度资源，把用户编写的程序翻译成 Job → Stage → Task 三级执行粒度，分发到集群各节点并行执行。
```text
要点
- Driver：运行 main 方法、生成执行计划、调度任务的"大脑"
- Executor：真正干活的工作进程，负责执行 Task 并缓存数据
- Cluster Manager：管理集群资源、分配 Executor 的调度器
- Application：用户提交的一个 Spark 应用（一份代码 + 资源）
- Job：一次 Action 触发的一整条计算链
- Stage：按 Shuffle 边界切分出的可并行执行单元
- Task：Stage 内发送到单个分区的具体计算任务
```
## 核心概念

Spark 架构围绕 7 个核心概念展开：Driver、Executor、Cluster Manager、Application、Job、Stage、Task。它们共同构成一次分布式计算从「提交代码」到「产出结果」的完整链路，理解每个角色的职责与协作关系，就理解了 Spark 的整个运行框架。

### Driver

Driver 是运行在客户端或集群节点上的一个进程，负责解析用户代码、把 RDD/DataFrame 的逻辑计划转换成物理执行计划，并通过 DAGScheduler 把执行计划切分成 Stage 和 Task。Driver 还负责与 Cluster Manager 通信申请 Executor，调度 Task 到 Executor，并收集最终结果。Driver 是单点，一旦崩溃整个 Application 就会失败。
```text
要点
- 持有 SparkContext / SparkSession 入口
- 负责 Job 的 DAG 构建与 Stage/Task 划分
- 通过 RPC 向 Executor 下发 Task 并回收结果
- 维护元数据（RDD 血缘、累加器、广播变量）
- 单点故障：Driver 崩溃则整个应用失败
```

```scala
import org.apache.spark.sql.SparkSession
// Driver 进程中的入口代码：创建 SparkSession
val spark = SparkSession.builder()
  .appName("DriverDemo")
  .master("spark://master:7077") // 交给 Cluster Manager 管理
  .config("spark.driver.memory", "2g")
  .getOrCreate()
// 这里的逻辑都在 Driver 端执行：惰性构建执行计划
val df = spark.read.parquet("/data/events")
  .filter("date = '2026-08-14'")
  .groupBy("uid")
  .count()
// Action 触发时，Driver 生成 Job 并调度 Task
df.show()
spark.stop()
```
### Executor

Executor 是运行在 Worker 节点上的工作进程，负责真正执行 Task、把结果写回 Driver 或持久化到存储系统。每个 Executor 独占一定数量的 CPU Core 和内存，同一个 Application 的所有 Task 在它的多个 Executor 上并行运行。Executor 内部使用线程池，一个 Core 同时只能跑一个 Task。
```text
要点
- 生命周期由 Cluster Manager 分配、随 Application 结束而回收
- 内部按 Core 数量并行执行 Task（一核一 Task）
- 负责 RDD/DataFrame 的分区数据缓存（MemoryStore）
- 执行 Shuffle 时的数据读写与网络传输
- 与 Driver 通过心跳 + RPC 通信，异常会被重新调度
```

```shell
# 提交应用时通过配置指定 Executor 的规格
spark-submit \
  --class com.example.MyJob \
  --master yarn \
  --deploy-mode cluster \
  --num-executors 20 \
  --executor-cores 4 \
  --executor-memory 8g \
  --driver-memory 4g \
  my-job.jar
```
### Cluster Manager

Cluster Manager 是负责集群资源管理与调度的组件，负责接收 Driver 的资源申请，在 Worker 节点上启动 Executor，并在 Executor 故障时回收/重新分配资源。Spark 支持多种 Cluster Manager：Standalone（自带）、YARN、Kubernetes 和 Mesos（已退役）。
```text
要点
- Standalone：Spark 自带，简单易用，适合小规模集群
- YARN：Hadoop 生态默认，支持资源队列与多租户
- Kubernetes：云原生，动态扩缩容，适合容器化环境
- 只负责"给资源"，不参与具体任务计算
- 通过 spark.master 配置选择，如 yarn / k8s://... / spark://...
```

```yaml
# 使用 Kubernetes 作为 Cluster Manager 时的提交示例
spark-submit \
  --master k8s://https://k8s.example.com:6443 \
  --deploy-mode cluster \
  --conf spark.kubernetes.container.image=spark:3.5.0 \
  --conf spark.kubernetes.namespace=bigdata \
  --conf spark.executor.instances=10 \
  --conf spark.kubernetes.authenticate.driver.serviceAccountName=spark \
  local:///opt/spark/examples/jars/my-job.jar
```
### Application

Application 是用户提交的一个完整 Spark 程序，由 Driver 进程 + 它申请到的若干 Executor 构成。一个 Application 对应一个 SparkContext/SparkSession，拥有独立的资源与命名空间，各 Application 之间默认不共享内存和缓存。在 YARN/K8s 上，一个 Application 通常对应一个独立的运行实例。
```text
要点
- 一份可执行代码 + 运行所需资源的总和
- 内部包含一个 Driver 和一组 Executor
- 不同 Application 之间隔离，不共享 SparkContext
- 通过 spark-submit 或编程方式提交
- 资源由 Cluster Manager 按 Application 维度分配
```

```bash
# 通过 spark-submit 提交一个 Application
spark-submit \
  --name "daily-agg-job" \
  --master yarn \
  --deploy-mode cluster \
  --conf spark.yarn.queue=etl \
  --conf spark.sql.shuffle.partitions=200 \
  daily_agg.py
```
### Job

Job 是 Spark 执行的顶层单元，每调用一次 Action（如 collect、count、save）就会触发一个 Job。一个 Application 中可以包含多个 Job，它们由 Driver 的 DAGScheduler 依次或并发调度。每个 Job 对应一段完整的 DAG，从数据源读入到最终写出结果。
```text
要点
- 一次 Action 触发一个 Job
- Job 由 DAGScheduler 切分为多个 Stage
- 一个 Application 可包含多个 Job
- Job 的执行结果是 Action 的返回值或写入的副作用
- 惰性求值下，多个 Transformation 只会组成一个 Job
```

```scala
val rdd = sc.textFile("/data/logs")          // 惰性，不触发 Job
  .flatMap(_.split(" "))                     // 惰性
  .map((_, 1))                               // 惰性
val result = rdd.reduceByKey(_ + _)          // 惰性
result.collect()          // Action → 触发第一个 Job
result.saveAsTextFile("/out/wordcount")      // Action → 触发第二个 Job
```
### Stage

Stage 是 Job 内部按 Shuffle 边界切分的执行阶段。DAGScheduler 从最后一个 RDD 反向遍历血缘，遇到窄依赖就合并到同一 Stage，遇到宽依赖（Shuffle）就切分新 Stage。同一 Stage 内的分区可以完全并行、无需等待其他分区；Stage 之间必须等上游 Shuffle 数据落盘后才能继续。
```text
要点
- 切分依据是 Shuffle（宽依赖）边界
- Stage 内是窄依赖，可并行计算
- Stage 间存在数据依赖，需等待上游完成
- ShuffleMapStage 写 Shuffle 数据，ResultStage 产出最终结果
- Stage 数量 = Shuffle 次数 + 1（大致）
```

```python
from pyspark import SparkContext
sc = SparkContext(appName="StageDemo")
rdd = sc.parallelize(range(100), 4)
# map 是窄依赖，和上一个操作合并进同一 Stage
mapped = rdd.map(lambda x: x * 2)
# groupByKey 是宽依赖，触发 Shuffle，切分出新的 Stage
grouped = mapped.groupBy(lambda x: x % 3)
# 最终 count 是 Action，生成 ResultStage
print(grouped.mapValues(len).collect())
```
### Task

Task 是 Spark 最小的执行单元，一个 Task 处理一个分区的数据。Stage 内有多少个分区，就有多少个 Task，它们会被 Driver 调度到不同 Executor 的 Core 上并行执行。Task 执行失败会被自动重试（默认最多 4 次），只有所有 Task 成功，整个 Stage 才算完成。
```text
要点
- 一个 Task 只处理一个分区的数据
- Task 数量 = 该 Stage 的分区数
- 由 Driver 通过 TaskScheduler 分配到 Executor
- 失败自动重试，重试次数受 spark.task.maxFailures 控制
- 可通过 Spark UI 查看每个 Task 的耗时、Shuffle 读写量
```

```scala
// 通过分区数控制 Task 数量
val rdd = sc.textFile("/data/events")   // 默认按 HDFS block 决定分区
println(s"分区数 = ${rdd.getNumPartitions}")   // 分区数即 Task 数
// repartition 增加分区，会触发 Shuffle，Task 数随之变化
val repartitioned = rdd.repartition(20)
println(s"重分区后分区数 = ${repartitioned.getNumPartitions}")
```
## 工作原理

Spark 的一次任务执行可以拆成「提交 → 资源申请 → 计划构建 → 任务分发 → 执行回收」五个阶段：

1. **提交**：spark-submit 启动 Driver。client 模式下 Driver 跑在提交端（如开发机），cluster 模式下 Driver 由 Cluster Manager 在集群内启动。
2. **资源申请**：Driver 内的 SparkContext 向 Cluster Manager 注册 Application 并申请 Executor 资源；Cluster Manager 在 Worker 节点（或 YARN NodeManager / K8s Pod）上启动 Executor 进程。
3. **计划构建**：Driver 执行用户代码，构建 RDD/DataFrame 的血缘 DAG。Action 触发 Job 时，DAGScheduler 从后往前遍历血缘，按宽依赖切分 Stage，形成 ShuffleMapStage + ResultStage 的链条。
4. **任务分发**：TaskScheduler 把 Stage 内每个分区对应的 Task 分配到有空闲 Core 的 Executor。Executor 启动后先向 Driver 反向注册，Driver 才能给它派活；Task 尽量调度到数据所在节点（数据本地性）。
5. **执行回收**：Executor 执行 Task，结果写外部存储或回传 Driver；Executor 通过心跳持续汇报状态与资源使用。最后一个 Stage 完成、结果返回后，Application 结束，Cluster Manager 回收全部 Executor 资源。
```text
提交链路：
spark-submit -> Driver(SparkContext) -> Cluster Manager -> 启动 Executor
Action 触发 Job -> DAGScheduler 切 Stage -> TaskScheduler 分发 Task
-> Executor 执行 -> 结果回收/落盘 -> 心跳维持 -> 资源释放
关键点：
- client 模式：Driver 跑在提交端，适合交互调试，提交端断网任务失败
- cluster 模式：Driver 跑在集群内，适合生产，提交端可随时关闭
- Executor 反向注册到 Driver 后才会被派活
- Shuffle 数据由上游 Stage 落盘，下游 Stage 拉取，Stage 间天然串行
```

## 配置文件解析

Spark 的配置集中在 `$SPARK_HOME/conf/` 下，提交任务时也可用 `--conf key=value` 覆盖。spark-defaults.conf 放全局默认值，spark-env.sh 放环境级参数。
```text
# conf/spark-defaults.conf 关键配置
spark.master                          yarn
spark.driver.memory                   4g                  # Driver 堆内存
spark.executor.memory                 8g                  # 每个 Executor 堆内存
spark.executor.cores                  4                   # 每个 Executor 核数
spark.executor.instances              20                  # Executor 实例数
spark.sql.shuffle.partitions          200                 # Shuffle 后分区数（默认 200）
spark.default.parallelism             100                 # 无 shuffle 时的默认并行度
spark.dynamicAllocation.enabled       true                # 开启动态资源分配
spark.serializer                      org.apache.spark.serializer.KryoSerializer
spark.eventLog.enabled                true                # 开启事件日志（供 History Server）
spark.eventLog.dir                    hdfs://namenode:8020/spark-history
spark.ui.port                         4040                # Spark UI 端口
```

```shell
# conf/spark-env.sh 关键配置（Standalone 集群）
SPARK_MASTER_HOST=master              # Master 节点地址
SPARK_WORKER_CORES=8                  # 每个 Worker 可用核数
SPARK_WORKER_MEMORY=32g               # 每个 Worker 可用内存
SPARK_WORKER_INSTANCES=2              # 每台机器启动的 Worker 数
JAVA_HOME=/usr/lib/jvm/java-8-openjdk
HADOOP_CONF_DIR=/etc/hadoop/conf      # 集成 YARN/HDFS 时的配置目录
```
```text
字段含义速记：
spark.driver.memory / spark.executor.memory   进程堆内存，超出会 OOM
spark.executor.cores × spark.executor.instances   = 可并行 Task 上限
spark.sql.shuffle.partitions    所有 shuffle 结果的默认分区数，数据量大要调大
spark.dynamicAllocation.*       按负载自动伸缩 Executor，需配 shuffle service
spark.eventLog.*                打开才能用 History Server 看历史任务
```
## 应用场景实战

### 场景一：多 Job 的 ETL 批处理流水线

在一个 Application 中串联多个 Job，完成"清洗 → 聚合 → 落地"的完整链路，观察 Job 与 Stage 的对应关系。

```python
from pyspark.sql import SparkSession
spark = SparkSession.builder \
    .appName("ETLPipeline") \
    .master("local[4]") \
    .getOrCreate()
# 读取日志数据
logs = spark.read.text("/data/access.log")
# Job 1：清洗并落盘中间结果（第一次 save 触发第一个 Job）
cleaned = logs.filter("value is not null and value != ''")
cleaned.write.mode("overwrite").parquet("/tmp/cleaned")
# Job 2：聚合统计（第二次 save 触发第二个 Job）
cleaned_df = spark.read.parquet("/tmp/cleaned")
agg = cleaned_df.groupBy("value").count().orderBy("count", ascending=False)
agg.write.mode("overwrite").csv("/tmp/agg_result")
print("ETL 完成，共触发 2 个 Job")
spark.stop()
```
### 场景二：观察 Stage 与 Shuffle 的关系

通过一个包含 groupByKey 的任务，在 Spark UI 或日志中观察 Shuffle 导致的 Stage 切分，理解 Task 数量与分区的关系。

```scala
import org.apache.spark.{SparkConf, SparkContext}
val conf = new SparkConf()
  .setAppName("StageObservation")
  .setMaster("local[4]")
  .set("spark.ui.port", "4040")
val sc = new SparkContext(conf)
sc.setLogLevel("WARN")
// 8 个分区 = 第一个 Stage 的 8 个 Task
val rdd = sc.parallelize(1 to 1000, 8)
val result = rdd
  .map(x => (x % 10, x))       // 窄依赖，Stage 0 内
  .groupByKey()                 // 宽依赖 → Shuffle，切分 Stage 1
  .mapValues(_.sum)             // 窄依赖，Stage 1 内
println(s"结果分区数 = ${result.getNumPartitions}")
result.collect().foreach(println)
// 打开浏览器访问 http://localhost:4040 查看 Job/Stage/Task 明细
sc.stop()
```
### 场景三：生产环境 cluster 模式 + 动态资源分配

业务高峰期数据量波动大时，固定 Executor 数量要么浪费、要么不够。开启动态资源分配，让集群按负载自动增减 Executor。

```python
from pyspark.sql import SparkSession
spark = SparkSession.builder \
    .appName("DailyReport") \
    .config("spark.dynamicAllocation.enabled", "true") \
    .config("spark.dynamicAllocation.initialExecutors", "5") \
    .config("spark.dynamicAllocation.minExecutors", "2") \
    .config("spark.dynamicAllocation.maxExecutors", "50") \
    .config("spark.shuffle.service.enabled", "true") \
    .config("spark.sql.shuffle.partitions", "400") \
    .getOrCreate()
df = spark.read.parquet("/data/orders")
report = df.groupBy("province", "dt").sum("amount")
report.coalesce(20).write.mode("overwrite").parquet("/data/report/daily")
print("日报生成完成")
spark.stop()
```

```shell
# 生产提交：cluster 模式，Driver 跑在集群内，提交端可关闭
spark-submit \
  --master yarn \
  --deploy-mode cluster \
  --conf spark.yarn.queue=report \
  daily_report.py
# 提交后查看运行状态
yarn application -list
yarn logs -applicationId application_1699999999999_0002 | grep -i error
```
```text
注意点：
- 动态资源分配 + shuffle service：Executor 缩容时 shuffle 中间数据由
  ExternalShuffleService 保留，避免下游拉不到数据
- cluster 模式下日志看 yarn logs，不打印在提交端
- 高峰期 maxExecutors 给足，低峰期自动缩到 minExecutors
```
## 性能与调优
```text
1. Executor 规格设计：
   单 Executor 内存 4~16g、核数 4~8 为宜；核数太多则单 Task 内存变小，
   内存太多则 GC 停顿变长、资源碎片化。
   并行度 = executor 数 × 每 executor 核数，要大于等于目标 Task 数。
2. 并行度设置：
   - 无 Shuffle 阶段用 spark.default.parallelism
   - Shuffle 后分区用 spark.sql.shuffle.partitions（或 rdd 的 repartition）
   - 经验值：每个分区数据量控制在几十 MB 到一两百 MB
3. 动态资源分配：
   spark.dynamicAllocation.enabled=true，低峰省资源、高峰自动扩容，
   必须配套 spark.shuffle.service.enabled=true（YARN 模式）。
4. 内存配比：
   spark.memory.fraction 默认 0.6（执行 + 存储共享堆的 60%），
   存储与执行内存通过 spark.memory.storageFraction 划分，溢出互借。
5. 序列化：
   开启 Kryo（spark.serializer=KryoSerializer），比 Java 序列化小 3~5 倍，
   Shuffle 与缓存的 IO 压力显著下降。
6. 数据本地性：
   默认等 3 秒（spark.locality.wait）争取本地执行；本地性降级说明
   分区与 Executor 分布不合理，可配合 repartition 或调整调度。
7. 广播变量：
   小维度表用 SparkContext.broadcast 广播，避免每个 Task 都拉一份。
8. 监控先行：
   Spark UI 看各 Stage 的 Shuffle Read/Write 量、Task 倾斜、GC 时间，
   先定位瓶颈再调，别盲目堆资源。
```
## 安全与权限
```text
1. 网络边界：
   - Spark UI（4040）、History Server（18080）、Master（7077/8080）只绑内网，
     禁止暴露公网；外网访问走 VPN 或反向代理加认证。
2. 认证与加密：
   - spark.authenticate=true 开启 RPC 认证（共享密钥）
   - spark.network.crypto.enabled=true 加密 Executor 间网络传输
   - spark.ui.authenticate 可对接反向代理的认证层
3. YARN 集成：
   - Kerberos 集群提交需 keytab 认证（spark-submit --keytab --principal）
   - 队列 ACL：yarn.scheduler.capacity.root.<queue>.acl_submit_applications
     控制谁能往队列提交任务
4. Kubernetes 集成：
   - 用 ServiceAccount 做身份（spark.kubernetes.authenticate.driver.serviceAccountName）
   - Namespace 隔离 + RBAC 限制资源操作权限
5. UI 访问控制：
   - spark.ui.acls.enable=true 后，spark.admin.acls 指定管理员、
     spark.ui.view.acls 指定可查看任务的用户，防止敏感信息泄露
6. 日志与事件：
   - 事件日志（spark.eventLog.dir）目录按用户分权限，避免任务信息泄露
   - 代码与日志中避免硬编码密钥（建议用环境变量/密钥管理服务注入）
```
## 故障排查

```shell
# 1. 看进程与资源
jps                                    # 确认 Master/Worker/Driver/Executor 进程在不在
yarn application -list -appStates ALL  # YARN 上所有应用及状态
# 2. 看日志
yarn logs -applicationId <app_id>      # YARN 应用日志（含 Driver 日志）
journalctl -u spark-master -f          # Standalone Master 日志
$SPARK_HOME/logs/                      # Standalone 模式本机日志目录
# 3. 看执行详情
# 打开 History Server / Spark UI：Jobs/Stages/Tasks 三个标签逐级看
# Stages 里看每个 Stage 的 Shuffle Read/Write、失败 Task 的报错栈
```
```text
常见故障定位：
1. 提交后立刻失败 —— 看 Driver 日志：ClassNotFound（jar 没带全）、
   代码语法错、spark.master 配错。
2. Executor 频繁丢失 —— 节点内存不足被 YARN 杀（看 NodeManager 日志）、
   心跳超时（spark.network.timeout 过小）、Executor OOM。
3. Task 大量失败重试 —— 单分区数据倾斜、序列化错误、
   spark.task.maxFailures 内重试耗尽则整个 Stage 失败。
4. Stage 卡住不动 —— 上游 Shuffle 数据未就绪、资源不足排队
   （看「运行中的 Task / 申请的资源」）、数据倾斜单 Task 长尾。
5. 结果不对 —— 先怀疑重试导致的副作用（累加器在失败重试时被重复累加），
   累加器只在 Action 内使用才可靠。
6. 集群模式看不到日志 —— 日志在集群侧，用 yarn logs 拉取，
   提交端控制台只有提交状态。
```
## 常见问题
```text
Q1: spark-submit 的 client 和 cluster 模式有什么区别？
A: client 模式 Driver 跑在提交端（本地/网关机），交互调试方便，但提交端断网或关机任务就失败；cluster 模式 Driver 由集群启动、跑在集群内，提交端提交完即可关闭，生产环境用 cluster。
Q2: 一个 Application 里能产生多个 Job 吗？怎么产生？
A: 能。每调用一次 Action（collect/count/save/write/show 等）就触发一个 Job。一次 ETL 里多次落盘就对应多个 Job，它们共享同一个 SparkContext 和 Executor 资源。
Q3: Executor 数量、核数、内存怎么定？
A: 并行度 = executor 数 × 每 executor 核数，要能覆盖目标并行 Task 数；单 Executor 内存 4~16g、核数 4~8 是常见区间。总资源受集群容量约束，还要给 Driver 和系统预留内存。
Q4: Driver 是单点，挂了怎么办？
A: Driver 崩溃整个 Application 失败。缓解手段：YARN 模式配 spark.yarn.maxAppAttempts 让 AM 重试；Standalone 配 spark.deploy.recoveryMode=ZOOKEEPER 做 Master 高可用；关键任务用 cluster 模式减少外部因素导致的 Driver 死亡。
Q5: Spark 和 MapReduce 的架构区别？
A: MapReduce 每个 Job 重新启动进程、中间结果必落盘；Spark 的 Application 常驻 Executor 进程、中间结果优先内存，DAG 在一个 Job 内流水线执行，迭代和交互式场景快得多。
Q6: Standalone / YARN / Kubernetes 怎么选？
A: 小集群或学习用 Standalone；已有 Hadoop 生态、要多租户队列和 Kerberos 用 YARN；云原生环境、要容器化与自动扩缩容用 Kubernetes。Mesos 已退役，别选。
Q7: Stage 数量怎么预估？
A: 大致等于「Shuffle 次数 + 1」。每个宽依赖算子（groupByKey/reduceByKey/join 等）都会在 DAG 里切出一个新的 Stage 边界。
Q8: Task 数量和什么有关？
A: 只和分区数有关：一个分区一个 Task。分区数由数据源（HDFS 块数）、repartition/coalesce、shuffle 分区数决定。
```
## 面试题
```text
1. 简述 Spark 的运行架构，各组件职责是什么？
   答：Application 由 Driver + 一组 Executor 组成。Driver 跑 main 方法、构建 DAG、切分 Stage/Task、调度任务；Executor 执行 Task、缓存数据、做 Shuffle；Cluster Manager（Standalone/YARN/K8s）负责分配与回收 Executor 资源。
2. Job、Stage、Task 是怎么划分的？
   答：Action 触发一个 Job；DAGScheduler 从后往前遍历血缘，遇宽依赖（Shuffle）切 Stage；Stage 内每个分区对应一个 Task，Task 是调度与执行的最小单元。
3. 为什么 Stage 一定要按 Shuffle 边界切？
   答：窄依赖分区之间无数据交换，可流水线并行；宽依赖需要把同 key 数据汇聚，必须先等上游所有分区算完、Shuffle 数据落盘，下游才能拉取，所以必须切成独立阶段并串行执行。
4. 讲一下 spark-submit 到 Task 执行的完整流程？
   答：提交 → 启动 Driver（client/cluster 两种位置）→ SparkContext 向 Cluster Manager 注册并申请 Executor → 启动 Executor 反向注册 → 执行用户代码构建 DAG → Action 触发 Job → DAGScheduler 切 Stage → TaskScheduler 分发 Task → Executor 执行并回报 → 结果回收 → 应用结束释放资源。
5. Executor 的内存是怎么划分的？
   答：堆内存按 spark.memory.fraction（默认 0.6）分出执行内存（Shuffle 排序/聚合）与存储内存（缓存），两者可互借；其余为 User 代码与保留区。Spark 2.0+ 统一内存管理，执行内存不足时优先驱逐存储内存。
6. 集群资源充足但任务还是很慢，从架构上看先查什么？
   答：先看 Spark UI 的 Stage 页：Task 是否倾斜（长尾）、是否有 Task 因数据本地性降级（等待 3 秒后换节点）、Shuffle Read 是否巨大、GC 时间占比是否过高，再针对定位到的瓶颈调整并行度/分区/内存。
7. Spark 为什么比 MapReduce 快？
   答：一是有向无环图（DAG）在一个 Job 内流水线执行、中间结果优先放内存不落盘；二是 Executor 进程常驻、避免每次任务都重新启动进程；三是内存计算与缓存让迭代/交互式场景优势明显。
```
## 最佳实践与踩坑记录

### 最佳实践

1. 合理设置 Executor 规格：单个 Executor 内存不宜过大（推荐 4~16g），Core 数控制在 4~8，避免 Executor 过大导致 GC 压力与资源碎片。
2. 使用动态资源分配：开启 `spark.dynamicAllocation.enabled=true`，让集群按负载自动增减 Executor，避免资源浪费。
3. 优先使用窄依赖算子：尽量用 reduceByKey/aggregateByKey 代替 groupByKey，减少 Shuffle 数据量与网络传输。
4. 控制 Shuffle 分区数：根据数据量设置 `spark.sql.shuffle.partitions` 与 `spark.default.parallelism`，避免 Task 过少导致单分区过大或过多导致调度开销。
5. 监控 Spark UI：提交后关注 Stage 的 Shuffle Read/Write、Task 倾斜、GC 时间，及时定位性能瓶颈。
6. Driver 只做轻量工作：避免在 Driver 端 collect 大量数据或执行大循环，防止 Driver OOM。
7. 生产环境用 cluster 模式：`--deploy-mode cluster` 让 Driver 与 Executor 同集群运行，避免客户端网络抖动导致任务失败。
8. 为任务打上清晰的 `--name` 并按队列/命名空间隔离，方便在 YARN/K8s 上定位与治理。
9. 部署 History Server 并开启 spark.eventLog，出问题后能回看任意历史任务的 UI。

### 踩坑记录
```text
坑 1：Driver OOM
结论：Driver 进程内存不足导致应用失败
原因：在 Driver 端 collect 了过大的结果集，或维护了超大广播变量/累加器
解法：改用 write 落盘而非 collect；调大 spark.driver.memory；广播变量用 SparkContext.broadcast
坑 2：Executor 数量计算错误
结论：提交的 Executor 数量与预期不符，任务并行度不足
原因：混淆了 --num-executors（实例数）与 --executor-cores（每实例核数），实际并行度是两者乘积
解法：并行 Task 数 = executor 数 × 每 executor 核数，按此反推资源配置
坑 3：Shuffle 分区数过多导致调度开销
结论：小数据量任务却跑出上千个 Task，总耗时反而更长
原因：spark.sql.shuffle.partitions 默认 200，未按数据量调小，大量空 Task 徒增调度成本
解法：小数据场景调小 shuffle 分区数，或开启 AQE 自动合并小分区
坑 4：groupByKey 导致 OOM
结论：Executor 内存溢出，Shuffle 阶段失败
原因：groupByKey 把同 key 的所有 value 集中到单分区，数据倾斜时单 Task 内存爆炸
解法：改用 reduceByKey 预聚合，或对倾斜 key 加随机前缀打散
坑 5：Standalone 模式下资源竞争
结论：多个 Application 争抢资源导致整体变慢
原因：Standalone 模式缺少像 YARN 那样的队列隔离与抢占机制
解法：迁移到 YARN 或 Kubernetes，按队列/命名空间做资源隔离
坑 6：client 模式提交后任务跟着终端死掉
结论：关掉终端或网络断开后，运行中的任务失败
原因：client 模式 Driver 在提交端，提交端退出 = Driver 死亡
解法：生产改 cluster 模式，提交后无需保持连接
坑 7：开启动态资源分配后 Shuffle 阶段报「Executor 已释放」
结论：缩容后下游 Stage 拉不到 Shuffle 数据，任务失败
原因：Executor 被回收时 Shuffle 中间文件随之删除，未开 shuffle service 兜底
解法：YARN 模式开启 spark.shuffle.service.enabled=true，让外部服务持有 Shuffle 文件
```
