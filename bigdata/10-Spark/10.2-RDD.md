## 概述

RDD（Resilient Distributed Dataset，弹性分布式数据集）是 Spark 最核心的抽象，表示一个不可变、可分区、可并行计算的数据集合。它通过血缘（Lineage）记录计算过程，实现容错；通过 Partition 实现并行；通过懒加载与缓存实现性能优化。RDD 是 DataFrame/Dataset 的底层基础。
```text
要点
- 不可变：一旦创建不可修改，只能生成新的 RDD
- 可分区：数据按 Partition 切分，分布到集群各节点
- 可并行：每个 Partition 对应一个 Task 并行计算
- 可容错：通过血缘 Lineage 重算丢失的分区，无需复制数据
- 可缓存：可将中间结果持久化到内存/磁盘加速复用
```
## 核心概念

RDD 的编程模型围绕 8 个核心概念展开：Partition、Transformation、Action、Lazy、Dependency、Shuffle、Cache、Checkpoint。它们分别回答「数据怎么切、怎么算、何时算、怎么容错、怎么加速」这几个问题，共同构成 RDD 的执行模型。

### Partition

Partition 是 RDD 数据的物理切分单元，一个 RDD 被切分成多个 Partition，分布到不同 Executor 上。Partition 的数量直接决定了任务的并行度，一个 Partition 对应一个 Task。合理的 Partition 数量应使每个 Partition 的数据量适中（通常几十 MB 到几百 MB），避免过少导致负载不均、过多导致调度开销。
```text
要点
- RDD 的逻辑数据被切分为多个 Partition
- 一个 Partition 对应一个 Task，是并行度的单位
- 分区数由数据源、默认并行度或用户指定决定
- 通过 getNumPartitions 查看分区数
- 分区过多/过少都会影响性能
```

```scala
import org.apache.spark.rdd.RDD
val rdd: RDD[Int] = sc.parallelize(1 to 100, 4)   // 4 个分区
println(s"分区数 = ${rdd.getNumPartitions}")          // 4
// 查看每个分区的数据分布
val perPartition = rdd.mapPartitionsWithIndex { (idx, iter) =>
  Iterator(s"分区 $idx 包含: ${iter.mkString(",")}")
}
perPartition.collect().foreach(println)
```
### Transformation

Transformation 是从一个 RDD 生成另一个 RDD 的操作，如 map、filter、flatMap、reduceByKey 等。它不立即执行，只记录下运算逻辑，形成新的 RDD 与血缘关系。Transformation 分为窄依赖（无需 Shuffle）和宽依赖（需要 Shuffle）两类，宽依赖 Transformation 是 Stage 划分与性能瓶颈的关键。
```text
要点
- 输入一个或多个 RDD，输出新 RDD
- 惰性执行，只在 Action 触发时才真正计算
- 窄依赖：map/filter/flatMap/mapPartitions 等
- 宽依赖：groupByKey/reduceByKey/join/sortByKey 等
- 构成 RDD 血缘 Lineage，是容错的基础
```

```python
from pyspark import SparkContext
sc = SparkContext(appName="TransformationDemo")
rdd = sc.parallelize(["hello world", "hello spark", "spark rdd"])
# 多个 Transformation 串联，均为惰性，不触发计算
words = rdd.flatMap(lambda line: line.split(" "))   # 窄依赖
pairs = words.map(lambda w: (w, 1))                  # 窄依赖
counts = pairs.reduceByKey(lambda a, b: a + b)       # 宽依赖（Shuffle）
# 尚未执行，只有调用 Action 才真正计算
print("到这里为止没有任何计算发生")
```
### Action

Action 是触发 RDD 真正计算的算子，它会启动一个 Job，把计算结果返回给 Driver 或写入外部存储。常见的 Action 有 collect、count、reduce、take、saveAsTextFile、foreach 等。每调用一次 Action 就会触发一个 Job，是 Spark 惰性求值机制的执行入口。
```text
要点
- 触发 Job 的执行入口，产生实际计算结果
- 返回 Driver 端：collect/count/first/take/reduce
- 写入外部存储：saveAsTextFile/saveAsSequenceFile
- 每调用一次 Action 触发一个 Job
- 慎用 collect：数据量大时会导致 Driver OOM
```

```scala
val rdd = sc.parallelize(1 to 1000000)
val count = rdd.count()            // Action：返回元素个数
val sum = rdd.reduce(_ + _)        // Action：求和
val firstFew = rdd.take(5)         // Action：取前 5 个
println(s"count=$count, sum=$sum, firstFew=${firstFew.mkString(",")}")
// 写入磁盘也是 Action
rdd.saveAsTextFile("/tmp/numbers")
```
### Lazy

Lazy（惰性求值）是 Spark 的核心设计：所有 Transformation 不会立即执行，只记录计算逻辑，直到遇到 Action 才一次性构建执行计划并运行。惰性求值让 Spark 能够整体优化执行计划（如合并连续的窄依赖算子、重排算子顺序），减少不必要的中间结果落盘与网络传输。
```text
要点
- Transformation 只构建 DAG，不产生数据
- Action 触发时才真正执行
- 允许 Spark 全局优化：算子融合、列裁剪、谓词下推
- 避免中间结果反复物化，节省 IO 与内存
- 副作用操作（如累加器更新）也受惰性影响
```

```scala
import org.apache.spark.util.LongAccumulator
val rdd = sc.parallelize(1 to 1000)
val acc: LongAccumulator = sc.longAccumulator("filtered")
// 下面这行是惰性 Transformation，累加器此时不会更新
val filtered = rdd.filter { x =>
  if (x % 2 == 0) acc.add(1)   // 惰性阶段不会执行
  x > 500
}
println(s"Action 之前累加器值 = ${acc.value}")   // 0，证明尚未执行
val result = filtered.collect()                    // 触发真正计算
println(s"Action 之后累加器值 = ${acc.value}")     // 才被更新
```
### Dependency

Dependency（依赖）描述 RDD 之间如何生成，是血缘关系的具体表现形式。分为窄依赖（NarrowDependency，父 RDD 的每个分区最多被一个子分区使用）与宽依赖（ShuffleDependency，父 RDD 的分区被多个子分区使用）。窄依赖支持在单个节点上流水线式计算，宽依赖则必须经过 Shuffle，是 Stage 切分的边界。
```text
要点
- 窄依赖：子分区只依赖单个父分区，如 map/filter/union
- 宽依赖：子分区依赖多个父分区，如 groupByKey/join
- 窄依赖可合并到同一 Stage 内流水线执行
- 宽依赖触发 Shuffle，划分新 Stage
- 可通过 rdd.dependencies 查看依赖类型
```

```scala
val rdd = sc.parallelize(1 to 100)
val mapped = rdd.map(_ * 2)                 // 窄依赖
val grouped = mapped.groupBy(_ % 10)        // 宽依赖
// 查看 RDD 的依赖类型
println(s"mapped 的依赖: ${mapped.dependencies.head.getClass.getSimpleName}")
println(s"grouped 的依赖: ${grouped.dependencies.head.getClass.getSimpleName}")
// 查看完整血缘
println(grouped.toDebugString)
```
### Shuffle

Shuffle 是宽依赖 Transformation 触发的数据重分布过程：把上游每个分区的数据按 key 重新划分，将相同 key 的数据汇聚到下游同一分区。Shuffle 涉及磁盘读写与网络传输，是 Spark 中开销最大的环节。其核心组件是 ShuffleManager，负责 Shuffle 写（Shuffle Write）与读（Shuffle Read）两阶段。
```text
要点
- 触发条件：宽依赖算子（groupByKey/reduceByKey/join 等）
- 写阶段：Map 端把数据按 key 分区落盘（Shuffle Write）
- 读阶段：Reduce 端拉取对应分区的数据（Shuffle Read）
- 是网络 IO、磁盘 IO、数据倾斜的主要来源
- 可通过减少 Shuffle 次数、预聚合等方式优化
```

```python
from pyspark import SparkContext
sc = SparkContext(appName="ShuffleDemo")
# 构造一个会发生 Shuffle 的操作
rdd = sc.parallelize([("a", 1), ("b", 2), ("a", 3), ("c", 4), ("b", 5)], 2)
# reduceByKey 触发 Shuffle：相同 key 汇聚到同一分区
reduced = rdd.reduceByKey(lambda x, y: x + y)
print(reduced.collect())
# 对比：mapValues 不触发 Shuffle（窄依赖）
mapped = rdd.mapValues(lambda v: v * 10)
print(mapped.collect())
```
### Cache

Cache（缓存）将 RDD 的中间结果持久化到内存或磁盘，供后续 Action 复用，避免重复计算。默认用 cache() 把数据缓存到内存（StorageLevel.MEMORY_ONLY），也可用 persist() 指定存储级别（如 MEMORY_AND_DISK、DISK_ONLY）。缓存是惰性的，需在 Action 触发后才真正物化，适合被多次复用的中间结果。
```text
要点
- cache() 等价于 persist(MEMORY_ONLY)
- persist() 可指定多种存储级别
- 缓存是惰性的，Action 触发后才真正缓存
- 适合被多个 Action 复用的 RDD，避免重复计算
- 内存不足时按 LRU 淘汰，可配合磁盘级别容错
```

```scala
import org.apache.spark.storage.StorageLevel
val rdd = sc.textFile("/data/large_logs").flatMap(_.split(" ")).map((_, 1))
rdd.persist(StorageLevel.MEMORY_AND_DISK)   // 缓存到内存 + 磁盘
// 第一次 Action 触发计算并缓存
val total = rdd.count()
// 后续 Action 直接读缓存，不再重算
val distinct = rdd.keys.distinct().count()
println(s"total=$total, distinct=$distinct")
rdd.unpersist()   // 手动释放缓存
```
### Checkpoint

Checkpoint 是把 RDD 的数据物化到可靠的分布式存储（如 HDFS），并切断其血缘，用于长血缘链路的容错与迭代计算的稳定。与缓存不同，Checkpoint 的数据在 Application 结束后仍存在，且重算成本高时能避免长链路重放。使用前需设置 checkpoint 目录，且 Checkpoint 会额外触发一次 Job 计算。
```text
要点
- 将 RDD 数据写入 HDFS 等可靠存储，切断血缘
- 用于超长血缘、迭代算法、关键中间结果容错
- 需先 sc.setCheckpointDir() 指定目录
- 会额外触发一次 Job 完成物化
- 数据持久存在，不随 Application 结束而消失
```

```scala
sc.setCheckpointDir("hdfs://namenode:8020/spark/checkpoint")
// 构造一个长血缘的迭代计算
var rdd = sc.parallelize(1 to 1000)
for (i <- 1 to 50) {
  rdd = rdd.map(_ + 1)   // 50 次 map，血缘越来越长
}
rdd.checkpoint()          // 标记 checkpoint，触发后物化并切断血缘
println(rdd.count())      // 触发 checkpoint 物化
// 查看血缘：checkpoint 后血缘被截断
println(rdd.toDebugString)
```
## 工作原理

RDD 是一个「描述如何计算的抽象」，本身不存数据。它的实现由五个要素组成，Spark 的执行引擎按这五要素驱动计算：
```text
RDD 五要素：
1. partitions          分区列表（数据怎么切）
2. compute             计算函数（分区怎么算，给定父分区数据产出本分区）
3. dependencies        依赖列表（数据从哪来，构成血缘）
4. partitioner         分区器（可选，key-value RDD 如何定 key 到分区）
5. preferredLocations  优先位置（分区数据倾向落在哪些节点，优化本地性）
```

执行流程分三步：

1. **构建血缘**：用户代码里的每个 Transformation 都生成一个新 RDD 并记录父依赖，形成一张只增不减的 DAG。这个阶段不碰数据。
2. **触发计算**：Action 调用时，Driver 以该 RDD 为终点反向遍历血缘，DAGScheduler 按宽依赖切 Stage，TaskScheduler 把分区作为 Task 分发到 Executor。
3. **容错重算**：某个分区的计算结果丢失（Executor 崩溃、缓存被淘汰）时，Spark 沿血缘重算该分区。窄依赖只需重算丢失分区对应的少数父分区；宽依赖因为一个子分区依赖多个父分区，通常要重算整个父 Stage 的 Shuffle。
```text
容错对比：
缓存（cache）     保留计算结果，不切血缘，Executor 挂掉后仍要按血缘重算
Checkpoint       物化到 HDFS 并切断血缘，重算时直接从 HDFS 读，不回溯祖先
窄依赖故障恢复    只重算受影响分区的父分区，代价小
宽依赖故障恢复    要重算父 Stage 全部 Shuffle，代价大
```
## 常用命令与配置

RDD 没有独立 CLI，日常通过 spark-shell（Scala）/ pyspark（Python）交互式操作，或写作业用 spark-submit 提交。

```shell
# 交互式环境（本地 4 核）
spark-shell --master local[4]
pyspark --master local[4]
# 交互环境里常用的 RDD 操作
sc.parallelize(1 to 100, 4)          # 本地集合转 RDD，指定 4 个分区
sc.textFile("/data/access.log")      # 读 HDFS/本地文件为 RDD（按块分区）
rdd.getNumPartitions                 # 查看分区数
rdd.toDebugString                    # 打印血缘链
rdd.collect()                        # 拉回 Driver 端查看（小数据量）
rdd.take(5)                          # 取前 5 条预览
rdd.saveAsTextFile("/out/result")    # 结果写盘
# 提交 RDD 作业（Python 依赖用 --py-files 带上）
spark-submit --master yarn --deploy-mode cluster \
  --py-files my_utils.py wordcount_job.py
```
```text
常见算子速查：
窄依赖（无 Shuffle）：map / flatMap / filter / mapPartitions / union
宽依赖（有 Shuffle）：groupByKey / reduceByKey / aggregateByKey / join / sortByKey / distinct
分区操作：repartition(增分区，有 Shuffle) / coalesce(减分区，可无 Shuffle) / partitionBy(自定义分区器)
Action：collect / count / take / first / reduce / foreach / saveAsTextFile
```
## 配置文件解析

RDD 相关的调优配置集中在 spark-defaults.conf，多数作用于并行度、Shuffle、存储与序列化。
```text
# conf/spark-defaults.conf 中与 RDD 强相关的配置
spark.default.parallelism           100       # RDD 无 Shuffle 时的默认并行度
spark.sql.shuffle.partitions        200       # Shuffle 结果的默认分区数
spark.serializer                    org.apache.spark.serializer.KryoSerializer
spark.rdd.compress                  true      # 缓存/Shuffle 数据压缩（节省内存）
spark.memory.fraction               0.6       # 执行+存储共享堆比例
spark.memory.storageFraction        0.5       # 存储内存占共享区比例
spark.shuffle.file.buffer           32k       # Shuffle 写缓冲（调大减磁盘 IO 次数）
spark.reducer.maxSizeInFlight       48m       # 单个 Reduce 同时拉取的 Shuffle 数据量
spark.shuffle.compress              true      # Shuffle 中间数据压缩
spark.shuffle.io.maxRetries         3         # Shuffle 拉取失败重试次数
spark.kryo.registrator              com.example.MyKryoRegistrator  # 自定义 Kryo 注册
```
```text
关键理解：
- spark.default.parallelism 决定 sc.parallelize / textFile 的默认分区数
  （textFile 实际还受 HDFS 块数影响，两者取大）
- spark.rdd.compress 只压缩序列化后的缓存数据，CPU 换内存，内存紧张时开
- spark.memory.storageFraction 越大，缓存能用的内存越多，
  但执行内存不足时会反噬 Shuffle 性能
- Kryo 需注册类（spark.kryo.registrator）才能拿到最优压缩率，
  不注册也能用，只是回退到反射序列化
```
## 应用场景实战

### 场景一：日志词频统计（WordCount）

RDD 最经典的入门实战，完整串联 map/flatMap/reduceByKey 等 Transformation 与 saveAsTextFile Action，理解 Lazy 与 Shuffle 机制。

```python
from pyspark import SparkContext
sc = SparkContext(appName="WordCount")
lines = sc.textFile("/data/access.log")
word_counts = (lines
               .flatMap(lambda line: line.split(" "))        # 切词
               .map(lambda word: (word, 1))                   # 映射为键值对
               .filter(lambda t: len(t[0]) > 0)               # 过滤空词
               .reduceByKey(lambda a, b: a + b))              # 聚合（Shuffle）
word_counts.saveAsTextFile("/out/wordcount")   # Action 触发执行
print("词频统计完成")
```
### 场景二：缓存加速的迭代 PageRank

利用 RDD 的缓存与宽依赖 join，实现 PageRank 迭代算法，展示 Cache 在多次复用场景下的加速价值。

```scala
import org.apache.spark.rdd.RDD
// 构造图：每个节点指向一个邻居列表
val links: RDD[(Int, Array[Int])] = sc.parallelize(Seq(
  (1, Array(2, 3)), (2, Array(3)), (3, Array(1, 2))
))
var ranks: RDD[(Int, Double)] = links.mapValues(_ => 1.0)
// 迭代 10 轮
for (i <- 1 to 10) {
  // 宽依赖 join，产生 Shuffle
  val contributions = links.join(ranks).flatMap {
    case (_, (neighbors, rank)) =>
      neighbors.map(n => (n, rank / neighbors.length))
  }
  ranks = contributions.reduceByKey(_ + _).mapValues(0.15 + 0.85 * _)
  ranks.cache()   // 缓存，供下一轮复用，避免重复计算
}
ranks.collect().foreach { case (node, rank) =>
  println(s"节点 $node 的 PageRank = $rank")
}
```
### 场景三：TopN 热搜词榜

从搜索日志里统计每个词的出现次数并取 Top 10，演示 takeOrdered 这类只在 Driver 端取少量结果的 Action（避免 collect 全量）。

```python
from pyspark import SparkContext
sc = SparkContext(appName="HotWordsTopN")
# 模拟一天的热搜日志：每行一个搜索词
log = sc.textFile("/data/search_log.txt")
# 统计每个词的出现次数
counts = (log
          .filter(lambda w: len(w.strip()) > 0)   # 去掉空行
          .map(lambda w: (w, 1))                  # 映射为 (词, 1)
          .reduceByKey(lambda a, b: a + b))       # Shuffle 聚合
# takeOrdered 只取前 10，不把全量结果拉回 Driver
top10 = counts.takeOrdered(10, key=lambda kv: -kv[1])
for word, cnt in top10:
    print(f"{word}: {cnt}")
# 全量结果落盘（大数据量写盘用 save，不 collect）
counts.sortByKey().saveAsTextFile("/out/hot_words")
sc.stop()
```
## 性能与调优
```text
1. 分区数：
   目标每个分区几十 MB 到一两百 MB。分区过少 -> 并行度不足、单分区过大；
   分区过多 -> 调度开销与空 Task。
   - 增大：repartition（有 Shuffle）或提高 spark.default.parallelism
   - 减小：coalesce（无 Shuffle 优先）
2. 减少 Shuffle：
   - 能用 reduceByKey/aggregateByKey 就不用 groupByKey（map 端预聚合）
   - 合并连续宽依赖算子，避免每步都全量 Shuffle
   - 小表用广播变量（SparkContext.broadcast）替代 join 的 Shuffle
3. Shuffle 参数：
   - spark.shuffle.file.buffer 调大（如 128k），减少写磁盘次数
   - spark.reducer.maxSizeInFlight 调大，加快 Reduce 拉取
   - spark.shuffle.compress / spark.rdd.compress 开压缩，网络与内存换 CPU
4. 缓存策略：
   - 多次复用的中间 RDD 用 persist 选合适级别：
     MEMORY_ONLY 最快但吃内存；MEMORY_AND_DISK 防 OOM；DISK_ONLY 兜底
   - 用完立即 unpersist，避免占着存储内存挤掉执行内存
5. 序列化：
   开启 KryoSerializer，Shuffle 与缓存数据体积可缩小数倍；
   自定义类注册到 spark.kryo.registrator 效果最佳。
6. 数据倾斜（RDD 层面）：
   - 倾斜 key 加随机前缀打散，两阶段聚合（先局部聚合再全局聚合）
   - 大 key 单独拆出来处理，避免拖垮整个 Task
7. 长血缘：
   迭代算法或超长转换链定期 checkpoint，切断血缘，
   避免故障时从源头重放整条链路。
```
## 安全与权限
```text
1. 序列化安全：
   - Kryo/Java 序列化对反序列化输入敏感，只处理可信数据源
   - 不要反序列化来自不可信来源的对象（RCE 风险）
2. 闭包与数据泄露：
   - Transformation 的闭包会序列化到 Executor，注意别把敏感凭据
     写进闭包捕获的变量里
   - 日志中避免打印全量业务数据（尤其 PII 字段）
3. Spark UI 暴露面：
   - UI 能看到执行的 DAG 与数据量级，默认只绑内网，
     生产通过 spark.ui.acls.enable + view.acls 控制查看权限
4. Checkpoint 与缓存目录权限：
   - sc.setCheckpointDir 指向的 HDFS 目录按团队/用户隔离，
     HDFS ACL 控制读写，避免越权读取或覆盖中间结果
   - 临时缓存目录（spark.local.dir）落在受控磁盘，勿用共享 /tmp
5. 事件日志：
   - spark.eventLog.dir 中记录任务细节，目录权限收紧，
     配合审计日志记录谁在何时提交了什么任务
```
## 故障排查
```text
1. NotSerializableException（任务无法执行）
   现象：Task 序列化失败，报某个对象不可序列化。
   原因：闭包捕获了不可序列化的对象（连接、Stream、自定义类没实现 Serializable）。
   解法：把不可序列化对象从闭包里挪出去；用 mapPartitions 在分区内创建连接；
   自定义类实现 Serializable 或注册 Kryo。
2. StackOverflowError（Driver 栈溢出）
   现象：长迭代循环后 Driver 崩溃。
   原因：血缘链条过长，toDebugString 或 DAG 构建递归过深。
   解法：定期 checkpoint 切断血缘；改用 DataFrame 高阶算子。
3. 缓存了还是慢 / 反复重算
   现象：同一 RDD 被多个 Action 使用时每次都重算。
   原因：cache() 未触发过 Action（惰性未物化），或内存不足被 LRU 淘汰。
   解法：复用前先触发一次 Action 物化；改 MEMORY_AND_DISK 防淘汰；
   检查 Storage 标签页确认数据确实驻留。
4. Shuffle 文件丢失（FetchFailedException / Block not found）
   现象：Reduce 阶段拉取上游数据失败。
   原因：Executor 频繁被杀或重启，Shuffle 中间文件随进程消失。
   解法：开 shuffle service（spark.shuffle.service.enabled）让文件
   独立于 Executor 存活；调大 spark.shuffle.io.maxRetries。
5. Checkpoint 目录报错
   现象：checkpoint() 后任务失败。
   原因：未 setCheckpointDir，或目录不存在/无写权限。
   解法：先 sc.setCheckpointDir 指向 HDFS 可靠目录，再 checkpoint。
6. 单个 Task 极慢（数据倾斜）
   现象：其他 Task 秒完，个别 Task 跑很久甚至 OOM。
   原因：少数 key 数据量巨大，集中在单个分区。
   解法：倾斜 key 加盐两阶段聚合；提高分区数；定位后单独处理大 key。
7. collect 后 Driver OOM
   现象：作业在最后一步崩溃。
   原因：collect 把全量结果拉回 Driver，超出 Driver 堆内存。
   解法：take/takeOrdered 取样；改 saveAsTextFile 落盘；调大 driver.memory。
```
## 常见问题
```text
Q1: RDD 和 DataFrame 有什么区别？
A: RDD 是元素级 API，类型安全但优化靠人；DataFrame 带 Schema，Catalyst 能做列裁剪、谓词下推、Codegen 等自动优化，性能更好且开发效率高。新代码优先 DataFrame，RDD 用于底层或非结构化数据处理。
Q2: cache 和 checkpoint 有什么区别？
A: cache 缓存计算结果但不切血缘，Executor 挂掉后仍需按血缘重算，数据随 Application 结束消失；checkpoint 物化到 HDFS 并切断血缘，重算时直接读存储，数据跨 Application 保留。缓存用于加速，checkpoint 用于容错与断链。
Q3: reduceByKey 和 groupByKey 的区别？
A: groupByKey 把所有 value 全量 Shuffle 到下游再聚合；reduceByKey 在 map 端先做局部聚合（combiner），Shuffle 的数据量小得多。能用 reduceByKey/aggregateByKey 就别用 groupByKey。
Q4: 窄依赖和宽依赖的区别？为什么窄依赖恢复快？
A: 窄依赖子分区只依赖单个父分区（map/filter/union），可在节点内流水线执行，故障时只需重算丢失分区对应的少数父分区；宽依赖子分区依赖多个父分区（groupByKey/join），必须全量 Shuffle，故障时通常要重算整个父 Stage。
Q5: 为什么 RDD 设计成不可变？
A: 不可变让血缘 DAG 只增不减、天然可重放，容错只需记录依赖而非维护副本；也避免并发修改带来的一致性问题。要改数据就生成新 RDD。
Q6: Partition 和 Task 是什么关系？
A: 一个 Partition 对应一个 Task，Task 是执行单元、Partition 是数据切分单元。Stage 的 Task 数 = 该 Stage 的分区数。调整分区数就能调整并行度。
Q7: RDD 为什么要惰性求值？
A: 惰性让 Spark 在 Action 触发前拿到整条 DAG，可以全局优化（算子融合、裁剪、重排），避免中间结果反复物化；代价是副作用（如累加器）的执行时机不可控，只能在 Action 里用。
Q8: 怎么选择缓存存储级别？
A: 数据量小、内存充足用 MEMORY_ONLY；数据量大于内存、可接受部分落盘用 MEMORY_AND_DISK；仅需防重算、不在乎速度用 DISK_ONLY；带 _SER 的级别序列化后存，更省内存但多 CPU 开销。
```
## 面试题
```text
1. RDD 是什么？五大特性是什么？
   答：RDD 是弹性分布式数据集，一个不可变、可分区、可并行计算的抽象。五大特性：分区列表、计算函数 compute、依赖列表（血缘）、分区器（可选）、优先位置。
2. 血缘（Lineage）是怎么实现容错的？
   答：每个 RDD 记录父依赖，分区数据丢失时沿血缘重算。窄依赖只需重算受影响分区的父分区，宽依赖要重算父 Stage 的 Shuffle。相比复制副本，血缘容错省存储、恢复粒度更细。
3. cache 和 checkpoint 的区别？什么时候用哪个？
   答：cache 不切血缘、随应用结束失效，用于加速复用；checkpoint 写 HDFS 并切血缘、跨应用保留，用于长血缘容错与迭代稳定。两者常配合：先 cache 再 checkpoint，避免 checkpoint 时重复计算。
4. reduceByKey 和 groupByKey 谁更优？为什么？
   答：reduceByKey。它在 map 端做预聚合（combiner），只把局部聚合结果 Shuffle 出去，数据量小、网络与磁盘开销低；groupByKey 全量 Shuffle 后再聚合。数据倾斜与内存压力下差距更明显。
5. RDD 数据倾斜怎么解决？
   答：倾斜 key 加随机前缀打散后两阶段聚合（先局部聚合再去前缀全局聚合）；提高分区数分散热点；定位倾斜 key 单独处理。RDD 层面没有 AQE，这些要靠代码显式做。
6. 描述一次 Shuffle 的完整过程？
   答：写阶段，Map 端任务把数据按 key 用分区器分到各下游分区，写本地文件（合并文件）并登记索引；读阶段，Reduce 端任务根据索引从各上游节点拉取自己分区对应的数据块，边拉边聚合/排序。Shuffle 的成败与性能决定任务整体表现。
7. RDD 的惰性求值带来了什么好处和坑？
   答：好处是整体优化（算子融合、裁剪、避免中间物化）。坑是副作用不可控：累加器、foreach 里的外部写操作执行时机取决于 Action 与重试，失败重试可能导致副作用重复执行，副作用逻辑要设计成幂等。
```
## 最佳实践与踩坑记录

### 最佳实践

1. 优先用窄依赖算子，减少 Shuffle 次数；能用 reduceByKey 就不要用 groupByKey + map。
2. 合理设置分区数，使每个 Partition 数据量适中，避免单分区过大导致倾斜或过小导致调度开销。
3. 对会被多次复用的 RDD 主动 cache/persist，用 `rdd.unpersist()` 及时释放不再使用的缓存。
4. 长血缘或迭代算法及时 checkpoint，切断血缘防止重算爆炸。
5. 用 take/first 代替 collect 预览数据，避免 Driver 端拉取全量导致 OOM。
6. 大数据量写盘优先 saveAsTextFile/parquet 等 Action，而非 collect 回 Driver。
7. 使用 Kryo 序列化（`spark.serializer=org.apache.spark.serializer.KryoSerializer`）降低 Shuffle 与缓存的数据体积。
8. 闭包里不捕获不可序列化对象（连接、Stream），连接在 mapPartitions 内按分区创建。
9. 迭代循环里缓存中间结果并定期 checkpoint，PageRank 这类算法每轮复用上一轮结果时尤其关键。

### 踩坑记录
```text
坑 1：collect 拉取全量导致 Driver OOM
结论：Driver 内存溢出，应用崩溃
原因：用 collect 把千万级数据拉回 Driver 端，超出 Driver 内存
解法：改用 write/saveAsTextFile 落盘，或用 take 取少量样本预览
坑 2：缓存了却未生效
结论：重复执行 Action 仍然重算，缓存无加速
原因：cache() 是惰性的，第一次 Action 后才物化；或内存不足数据被淘汰
解法：确保在复用前先触发一次 Action 物化；内存紧张时用 MEMORY_AND_DISK
坑 3：频繁 Shuffle 导致任务极慢
结论：宽依赖算子过多，网络与磁盘 IO 成为瓶颈
原因：连续使用 groupByKey、join 等宽依赖算子，每步都全量 Shuffle
解法：合并算子、用 map-side 预聚合（reduceByKey/aggregateByKey）减少 Shuffle 数据量
坑 4：checkpoint 目录未设置报错
结论：调用 checkpoint() 抛异常
原因：未调用 sc.setCheckpointDir() 指定 checkpoint 目录
解法：先 setCheckpointDir 指向 HDFS 等可靠存储，再调用 checkpoint
坑 5：长血缘导致 StackOverflow
结论：迭代上百次后 Driver 抛出栈溢出
原因：RDD 血缘链条过长，toDebugString 或 DAG 构建递归过深
解法：定期 checkpoint 切断血缘；或改用 DataFrame 的高阶算子
坑 6：闭包捕获连接对象导致序列化失败
结论：任务提交即报 NotSerializableException
原因：在 map 里直接 new 了数据库连接/文件句柄，闭包序列化时连不上
解法：连接移到 mapPartitions 内按分区创建/复用，闭包里只放可序列化数据
坑 7：Shuffle 中间文件丢失导致 FetchFailed
结论：Reduce 阶段反复拉取失败，Stage 重试后仍失败
原因：Executor 被频繁回收，Shuffle 文件随 Executor 进程一起消失
解法：YARN 模式开启 spark.shuffle.service.enabled，并适当调大 spark.shuffle.io.maxRetries
```
