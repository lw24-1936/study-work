## 概述

Spark 性能优化是数据工程师的核心能力，本质是「减少数据搬运、减少磁盘/网络 IO、减少内存浪费」。绝大部分慢作业都源于三类问题：分区不合理导致并行度不足或碎片过多、Shuffle 导致大量网络与磁盘 IO、数据倾斜导致个别任务拖垮整条作业。本主题覆盖 Spark 性能优化的核心抓手：分区控制、连接策略、倾斜治理、序列化与 GC 调优。

```text
Spark 性能优化总纲：
1. 数据量层面 —— 尽早过滤、列裁剪、只扫必要分区（谓词下推）
2. 并行度层面 —— 分区数匹配核数，避免空转与碎片
3. Shuffle 层面 —— 减少 Shuffle 次数、选择合适的 Join 策略、治理倾斜
4. 内存层面 —— 统一内存管理、序列化存储、避免频繁 GC
5. 序列化层面 —— 用 Kryo 序列化 RDD 与闭包，减少网络与存储开销
```

```scala
// 观察作业执行细节的两个入口
// 1. Spark UI 上的 SQL 页 / Stage 页看 Shuffle 读写量、倾斜、GC 时间
// 2. 代码里读执行计划
df.explain("cost")   // 查看物理计划与统计信息
```

## Partition 分区

Partition 是 Spark 并行与调度的基本单位，一个分区对应一个 Task。分区数太少，集群核数闲置、单任务处理数据过大易 OOM；分区数太多，任务调度开销大、产生大量小文件。合理分区是「分区数 ≈ 总核数的 1~3 倍」。默认分区数由数据源（HDFS 块数）或 `spark.sql.shuffle.partitions`（默认 200）决定。

```text
Partition 要点：
1. RDD 分区 —— 读文件时按块切分，可用 repartition/coalesce 调整
2. DataFrame 分区 —— 无 Shuffle 时沿用上游，Shuffle 后由 shuffle.partitions 决定
3. 默认 200 对大数据量太小、对中小数据量又偏大，要按集群规模调整
4. 分区数与数据倾斜强相关：分区越细，单 key 倾斜越易暴露
5. 分区数最终决定输出文件数，影响下游小文件问题
```

```scala
import org.apache.spark.sql.SparkSession

val spark = SparkSession.builder()
  .appName("PartitionDemo")
  .config("spark.sql.shuffle.partitions", "400")  // 按核数调整，如 200 核设 400
  .getOrCreate()

val df = spark.range(0, 1000000L)
println("当前分区数: " + df.rdd.getNumPartitions)  // 默认继承上游

// 查看每个分区的数据分布（用于发现倾斜）
df.rdd.mapPartitionsWithIndex { (idx, it) => Iterator(s"$idx:${it.size}") }
  .collect().foreach(println)
```

## Repartition 重分区

`repartition(n)` 会触发一次全量 Shuffle，把数据重新均匀地分到 n 个分区。它可以增大或减小分区数，代价是网络与磁盘 IO。典型用途：分区数太少时增大并行度、按列重新分布以缓解倾斜（`repartition(col)` 用哈希分区）、写入前控制输出文件数。由于它总是做 Shuffle，能换来均匀分布，但也可能引入新的倾斜。

```text
Repartition 要点：
1. repartition(n) 一定触发 Shuffle，可增可减分区数
2. repartition(cols) 按列哈希分布，常用于打散倾斜 key
3. 分区结果近似均匀，但代价是一次完整 Shuffle，别滥用
4. 写入前 repartition(n) 可精确控制输出文件数 = 分区数
5. 与 coalesce 的区别：repartition 可增大分区，coalesce 只能减小
```

```scala
// 增大并行度：从小分区扩到 200
val expanded = df.repartition(200)

// 按列重分区：把同一 user_id 的数据放到同一分区，缓解 join 倾斜
val byUser = df.repartition(df("user_id"))

// 写入前控制文件数：按日期分区，每个日期 10 个文件
df.write.partitionBy("dt").mode("overwrite")
  .repartition(10).parquet("/warehouse/orders")

// 显式列重分区 + 指定并行度
val redist = df.repartition(200, df("user_id"))
```

## Coalesce 合并分区

`coalesce(n)` 用于减少分区数且尽量避免 Shuffle：它把相邻分区原地合并，只在「目标分区数 > 当前分区数」时才退化为 Shuffle。因为不搬数据，coalesce 性能远好于 repartition，但合并后的分区可能大小不均（尤其上游本身倾斜时）。它常用于「处理完大量分区后，在写盘前收敛分区数，减少小文件」。

```text
Coalesce 要点：
1. coalesce(n) 默认 shuffle=false，相邻分区原地合并，无网络 IO
2. 只能减少分区数，n > 当前分区数时无效（需配合 shuffle=true 或改用 repartition）
3. 合并后分区可能不均：上游倾斜的分区会原样保留倾斜
4. 典型用法：Shuffle 后分区数很大，写盘前 coalesce 到目标文件数
5. 追求均匀用 repartition，追求快且能接受不均用 coalesce
```

```scala
// 从 1000 个分区收敛到 100 个，尽量不 Shuffle
val shrunk = df.coalesce(100)

// 强制 Shuffle 合并（目标大于当前分区数时必须 shuffle=true）
val forced = df.coalesce(500, shuffle = true)

// 实战：Shuffle 后 400 分区，写盘前合并到每日期 20 文件
df.filter($"dt" === "2024-08-14")
  .coalesce(20)
  .write.mode("overwrite").parquet("/warehouse/orders/dt=2024-08-14")
```

## Broadcast 广播

Broadcast（广播连接）把较小的表完整地发送到每个 Executor 的内存，避免 Shuffle：大表每个分区直接和内存中的小表做哈希查找。适用条件是「小表能塞进内存」，默认阈值 `spark.sql.autoBroadcastJoinThreshold` 为 10MB。广播连接的性能远优于 Shuffle 连接，是「大表 JOIN 小表」的标准做法，也是消除 Shuffle 的首选手段。

```text
Broadcast 要点：
1. 小表广播到所有 Executor，大表不做 Shuffle，连接在 map 端完成
2. 阈值 spark.sql.autoBroadcastJoinThreshold 默认 10MB，可上调到 100MB 级
3. 广播表过大反而更慢：传输、序列化、内存压力都增加
4. 显式强制广播用 broadcast hint，优先级高于自动阈值
5. 广播后的小表以只读哈希表常驻内存，适合维表、字典表
```

```scala
import org.apache.spark.sql.functions.broadcast

// 自动广播：小表 < 10MB 时优化器自动选 BroadcastHashJoin
val joined = bigFactDF.join(smallDimDF, "dim_id")

// 显式 hint：强制走广播（即使稍大于阈值）
val joined2 = bigFactDF.join(broadcast(smallDimDF), "dim_id")

// 调大自动广播阈值
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "104857600") // 100MB

// 查看物理计划确认是 BroadcastHashJoin 而非 SortMergeJoin
joined2.explain()
```

## SortMerge Join

SortMerge Join（排序归并连接）是 Spark 默认的大表 JOIN 策略：两边表先按连接键在各自分区内排序，再做 Shuffle 按哈希分到同一分区，最后双指针归并。它适合「两张大表、都能接受 Shuffle + 排序」的场景，对有序数据归并阶段是线性复杂度。缺点是必须经历 Shuffle 和全量排序，键分布不均时倾斜严重。

```text
SortMerge Join 要点：
1. 流程：两侧各自 map 端局部排序 -> Shuffle 按连接键分区 -> 归并连接
2. 适用：两张大表 JOIN，是 Spark 默认的非广播连接策略
3. 成本：Shuffle 网络 IO + 两侧排序 CPU + 落盘，是重操作
4. 可加 bucket（分桶）消除 Shuffle：按连接键预分桶后可直接归并
5. 倾斜时个别分区数据爆炸，需配合倾斜治理
```

```scala
// 两张大表默认走 SortMergeJoin
val result = factDF.join(dimDF, Seq("dim_id"), "inner")

// 确认物理计划
result.explain()
// 输出含: SortMergeJoin [dim_id], ...

// 用分桶消除 Shuffle（写入时按连接键分桶）
factDF.write.bucketBy(200, "dim_id").sortBy("dim_id")
  .saveAsTable("fact_bucketed")
// 读取分桶表 JOIN 时可跳过 Shuffle（Spark 3.x 支持 bucket join）
```

## ShuffleHash Join

ShuffleHash Join 是把连接键作为哈希键做 Shuffle，把相同键分到同一分区后，在分区内用哈希表做连接，不需要全量排序。相比 SortMerge Join 省掉了排序，适合「一侧表经过 Shuffle 后能整体放进内存」的场景。历史上它是 SortMergeJoin 之前的默认策略，如今默认关闭（因为内存不可控），可在特定场景显式开启。

```text
ShuffleHash Join 要点：
1. 流程：按连接键哈希 Shuffle -> 一侧建哈希表 -> 另一侧探测连接
2. 优点：省去排序，比 SortMerge Join 快
3. 缺点：哈希表需完整驻内存，大表易 OOM，故默认关闭
4. 开启：spark.sql.join.preferSortMergeJoin=false 时优先选 SHJ
5. 判定依赖统计信息：一侧数据量小于某阈值且可广播才考虑
```

```scala
// 默认 Spark 偏向 SortMergeJoin；关闭偏好后可触发 ShuffleHashJoin
spark.conf.set("spark.sql.join.preferSortMergeJoin", "false")

// 需要一侧表在 Shuffle 后能放内存；通常配合 AQE 动态选择
val r = df1.join(df2, Seq("key"), "inner")
r.explain()
// 当一侧较小且关闭 preferSortMerge 时，输出: ShuffledHashJoin [key]
```

## Skew 数据倾斜

数据倾斜指某个或某几个连接键/分区数据量远超其他分区，导致这些分区的 Task 成为瓶颈，其余 Task 早早完成空等，整条作业耗时被拖到最长任务。倾斜是 Spark 作业变慢的头号原因。治理手段有：加盐打散（给 key 加随机后缀再二次聚合）、两阶段聚合、广播小表、AQE 自动拆分倾斜分区、调整分区键等。

```text
Skew 治理要点：
1. 定位：Spark UI 看 Stage 内各 Task 数据量与耗时是否严重不均
2. 加盐打散 —— 倾斜 key 加 0~N 随机前缀，join/聚合后去盐二次聚合
3. 广播 —— 小表倾斜改 broadcast join，从根上消除 Shuffle 倾斜
4. AQE —— 开启 spark.sql.adaptive.skewJoin.enabled 自动拆分倾斜分区
5. 预处理 —— 把热点 key 单独拎出来处理，非热点走常规路径
```

```scala
import org.apache.spark.sql.functions._

// 方案一：加盐打散解决聚合倾斜
val N = 100  // 盐的份数
val salted = df.withColumn("salt", (rand() * N).cast("int"))
  .groupBy("salt", "user_id").agg(sum("amount").as("partial"))
  .groupBy("user_id").agg(sum("partial").as("total"))

// 方案二：AQE 自动倾斜 Join（Spark 3.x）
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256MB")

// 方案三：热点 key 单独处理 + 非热点广播 join
val hotUsers = List(10001, 10002)  // 已知热点 key
import spark.implicits._
val hot = df.filter($"user_id".isin(hotUsers: _*))
val normal = df.filter(!$"user_id".isin(hotUsers: _*))
val normalJoined = normal.join(broadcast(dimDF), "user_id")
val hotJoined = hot.join(dimDF.hint("skew"), "user_id")  // 或对 hot 单独加盐
```

## Serialization 序列化

序列化影响 Shuffle 传输量、缓存占用和闭包广播大小。Spark 默认对 RDD 用 Java 序列化（体积大、慢），对 DataFrame 用 Tungsten 二进制格式（紧凑高效）。调优方向：RDD 场景开启 Kryo 序列化并注册自定义类，DataFrame 尽量用 Encoder（二进制列式）而非 Java 对象；避免在闭包里捕获大对象导致序列化膨胀。

```text
Serialization 要点：
1. DataFrame/Dataset 用 Tungsten 二进制格式，远优于 Java 序列化，优先使用
2. RDD 自定义类型可开 Kryo：spark.serializer=org.apache.spark.serializer.KryoSerializer
3. Kryo 需注册自定义类（registerKryoClasses），否则退化为慢速路径
4. 闭包序列化 —— 别在 map/flatMap 里捕获大集合，改为广播变量
5. 序列化体积直接决定 Shuffle 网络耗时与内存占用
```

```scala
import org.apache.spark.serializer.KryoSerializer

// 开启 Kryo 序列化
spark.conf.set("spark.serializer", classOf[KryoSerializer].getName)
spark.conf.set("spark.kryo.registrationRequired", "true")

// 注册自定义类
class User(val id: Long, val name: String) extends Serializable
spark.conf.set("spark.kryo.classesToRegister",
  "com.example.User")

// 用广播变量代替闭包捕获大集合（避免每个 Task 序列化一份）
val bigDict = Map(1L -> "a", 2L -> "b")
val bcDict = spark.sparkContext.broadcast(bigDict)
val rdd = spark.sparkContext.parallelize(Seq(1L, 2L))
rdd.map(id => bcDict.value.getOrElse(id, "unknown")).collect()
```

## GC 垃圾回收

GC 是 Spark 内存调优的隐形杀手：Executor 频繁 Full GC 会暂停所有任务线程，导致作业卡顿、超时甚至 OOM。调优方向分两块：内存层面用统一内存管理（`spark.memory.fraction` 划分执行/存储内存，`spark.memory.storageFraction` 划分存储占比）；序列化层面用序列化存储减少对象数量。GC 目标是把「执行内存」占比调高、把对象数降下来。

```text
GC 调优要点：
1. 执行内存不足 -> 频繁溢出到磁盘 -> 慢；存储内存不足 -> 缓存被淘汰 -> 重算
2. spark.memory.fraction 默认 0.6（留给 JVM 40% 堆做对象与框架开销）
3. spark.memory.storageFraction 默认 0.5（存储与执行各半）
4. 序列化缓存（StorageLevel.MEMORY_AND_DISK_SER）大幅减少对象数与 GC 压力
5. 观察 GC：Spark UI Executor 页看 GC Time 占比，>10% 要警惕
```

```scala
import org.apache.spark.storage.StorageLevel

// 内存调优配置
spark.conf.set("spark.memory.fraction", "0.7")        // 统一内存占堆比例
spark.conf.set("spark.memory.storageFraction", "0.4") // 存储内存占比（给执行留更多）

// 用序列化缓存减少对象数量，降低 GC 压力
df.persist(StorageLevel.MEMORY_AND_DISK_SER)

// 大数据量计算时，中间结果落盘并序列化，避免内存爆炸
val processed = df.mapPartitions { it =>
  // 重计算逻辑
  it
}.persist(StorageLevel.MEMORY_AND_DISK_SER)
processed.count()  // 触发缓存

// 显式释放，及时回收内存
processed.unpersist()
```

## 应用场景实战

### 场景一：大表 JOIN 维表 + 倾斜治理

```scala
import org.apache.spark.sql.SparkSession
import org.apache.spark.sql.functions._

val spark = SparkSession.builder()
  .appName("JoinOptimization")
  .config("spark.sql.adaptive.enabled", "true")
  .config("spark.sql.adaptive.coalescePartitions.enabled", "true")
  .config("spark.sql.adaptive.skewJoin.enabled", "true")
  .config("spark.sql.autoBroadcastJoinThreshold", "104857600") // 100MB 内广播
  .getOrCreate()

// 事实表（大）与维表（小）关联：维表 80MB，直接广播
val fact = spark.read.parquet("/warehouse/fact_orders")
val dim  = spark.read.parquet("/warehouse/dim_users")
val enriched = fact.join(broadcast(dim), Seq("user_id"), "left")

// 聚合时有热点用户，加盐打散
val N = 64
val agg = enriched
  .withColumn("salt", (rand() * N).cast("int"))
  .groupBy("salt", "user_id").agg(sum("amount").as("partial_sum"))
  .groupBy("user_id").agg(sum("partial_sum").as("total_amount"))

// 写盘前收敛分区，控制小文件
agg.coalesce(50).write.mode("overwrite").parquet("/warehouse/user_totals")
```

### 场景二：ETL 全链路分区与缓存调优

```scala
// 一条典型 ETL：读取 -> 过滤 -> 多步转换 -> 写入
val raw = spark.read.option("header", "true").csv("/data/raw/events")
  .filter($"dt".between("2024-08-01", "2024-08-14"))   // 尽早过滤
  .select("user_id", "event", "amount", "dt")           // 列裁剪

// 中间结果会被复用，用序列化缓存
val cleaned = raw.filter($"amount".isNotNull && $"amount" > 0)
  .persist(StorageLevel.MEMORY_AND_DISK_SER)

// 分支一：按事件聚合
val byEvent = cleaned.groupBy("event").agg(sum("amount").as("total"))
// 分支二：按用户聚合（复用 cleaned，不重算）
val byUser = cleaned.groupBy("user_id", "dt").agg(count("*").as("cnt"))

// 重分区到合理并行度后写盘
byUser.repartition(200, $"dt").write.partitionBy("dt").mode("overwrite")
  .parquet("/warehouse/events_agg")

cleaned.unpersist()  // 释放缓存
```

## 最佳实践与踩坑记录

### 最佳实践

1. 打开 AQE（`spark.sql.adaptive.enabled=true`），让动态分区合并与倾斜拆分自动生效
2. 大表 JOIN 小表一律走广播，阈值按集群内存上调到 100MB 级
3. `spark.sql.shuffle.partitions` 按「总核数 1~3 倍」设置，别用默认 200 硬扛
4. 尽早 filter 与 select 列裁剪，把数据量在源头压下去
5. 写盘前用 repartition/coalesce 控制文件数，避免小文件
6. 复用的中间结果用 MEMORY_AND_DISK_SER 序列化缓存
7. 数据倾斜优先广播消除，其次加盐打散，最后才考虑 AQE 倾斜拆分兜底

### 踩坑记录

```text
坑 1：默认 shuffle.partitions=200 导致并行度不足
结论：大集群核数上百，作业只用 200 个 Task，大量核闲置、单 Task 数据过大。
原因：默认分区数远小于实际核数，未按集群规模调整。
解法：按总核数 1~3 倍设置 spark.sql.shuffle.partitions。

坑 2：coalesce 后分区严重不均
结论：合并后个别分区极大，仍出现长尾 Task。
原因：coalesce 原地合并、无 Shuffle，上游倾斜分区原样保留。
解法：追求均匀分布改用 repartition；仅减少文件数且可接受不均时才用 coalesce。

坑 3：广播表过大反而更慢甚至 OOM
结论：强制广播 500MB 维表，Executor 内存被打爆。
原因：广播表需完整序列化进每个 Executor 内存，过大时得不偿失。
解法：只广播能稳定放进内存的表；大维表走 SortMergeJoin 或分桶 join。

坑 4：忽略 GC 导致作业周期性卡顿
结论：Executor 频繁 Full GC，任务长时间无进展，甚至超时被杀。
原因：执行内存不足 + 对象过多，堆被打满触发 Full GC。
解法：调大 spark.memory.fraction，用序列化缓存，减少闭包大对象。

坑 5：加盐打散后忘记二次聚合，结果翻倍
结论：聚合结果重复计数，指标错误。
原因：加盐把同一 key 拆成多组，只聚合到盐粒度未去盐再聚合。
解法：加盐 -> 局部聚合 -> 去盐二次聚合，两步缺一不可。
```
