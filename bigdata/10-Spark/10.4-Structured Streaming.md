## 概述

Structured Streaming 是 Spark 基于 Spark SQL 引擎构建的可扩展、容错的流式处理框架。它把流数据建模成"持续追加的无界表"，用与批处理完全一致的 DataFrame/Dataset API 编写查询，底层按微批（Micro-batch）或连续（Continuous）模式增量执行。它原生支持 exactly-once 语义、事件时间、水印与有状态聚合。

```text
要点
- 流数据 = 持续增长的无界表（Unbounded Table）
- 复用 Spark SQL 的 DataFrame/Dataset API 与 Catalyst 优化
- 微批模式：默认，按 Trigger 间隔触发增量查询
- 连续模式：低延迟毫秒级，但算子支持有限
- 通过 Checkpoint + 可重放的 Source 实现 exactly-once
```

## 核心概念

Structured Streaming 的六个核心概念组成一个完整闭环：Source 进数据、Sink 出结果、Trigger 定节奏、Checkpoint 保容错、Watermark 管延迟数据、State 存跨批状态。下面逐个拆解。

### Source

Source 是流式数据的输入来源，负责持续读取数据并转化为 DataFrame。Structured Streaming 支持多种内置 Source：文件源（File Source，读目录下新文件）、Kafka、Socket、Rate（测试用）。每个 Source 都要求可重放（replayable）或配合 Checkpoint 记录读取偏移，以保证故障恢复后不丢不重。

```text
要点
- File Source：监控目录新文件，支持 Parquet/JSON/CSV/Text
- Kafka Source：消费 Topic，记录分区偏移
- Socket Source：仅测试用，无法保证 exactly-once
- Rate Source：按固定速率生成测试数据
- 自定义 Source 需实现 Source 接口
```

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .appName("KafkaSourceDemo") \
    .getOrCreate()

# Kafka Source：从 topic 读取流数据
kafka_df = (spark.readStream
            .format("kafka")
            .option("kafka.bootstrap.servers", "broker1:9092,broker2:9092")
            .option("subscribe", "user_events")
            .option("startingOffsets", "latest")   # 从最新偏移开始
            .load())

# value 是二进制，需解析为字符串
parsed = kafka_df.selectExpr("CAST(value AS STRING) as json_str")
parsed.writeStream.outputMode("append").format("console").start()
```

### Sink

Sink 是流式结果的输出目标，负责把每一批处理后的结果写入外部系统。内置 Sink 包括：Console（调试）、File（写文件）、Kafka、Foreach/ForeachBatch（自定义写入）。不同 Sink 支持的输出模式不同：Append、Complete、Update 需按查询类型选择。Kafka Sink 常用于把结果回写到消息队列。

```text
要点
- Console Sink：打印到控制台，仅调试用
- File Sink：以文件形式落盘，支持 JSON/Parquet/ORC
- Kafka Sink：把结果写回 Kafka Topic
- ForeachBatch：自定义每批数据的写入逻辑，最灵活
- 输出模式：Append（仅新增）、Complete（全量）、Update（更新）
```

```scala
val spark = SparkSession.builder()
  .appName("SinkDemo")
  .getOrCreate()

import spark.implicits._

val stream = spark.readStream
  .format("rate")
  .option("rowsPerSecond", 10)
  .load()
  .withColumn("bucket", $"value" % 5)

// Kafka Sink：把聚合结果写回 Kafka
val query = stream
  .groupBy("bucket")
  .count()
  .selectExpr("CAST(bucket AS STRING) as key", "CAST(count AS STRING) as value")
  .writeStream
  .outputMode("complete")
  .format("kafka")
  .option("kafka.bootstrap.servers", "broker1:9092")
  .option("topic", "agg_result")
  .option("checkpointLocation", "/tmp/checkpoint/sink")
  .start()

query.awaitTermination()
```

### Trigger

Trigger 决定流式查询何时以及如何触发新的一批数据处理。默认是微批模式，按固定间隔触发；也支持 ProcessingTime（指定间隔）、Once（只处理当前可用数据后停止，常用于一次性回填）与 Continuous（连续模式，毫秒级延迟）。合理设置 Trigger 可以在延迟与吞吐之间做权衡。

```text
要点
- 默认微批：上一批完成即触发下一批，最快
- ProcessingTime：按固定时间间隔触发，如 10 秒一批
- Once：处理当前可用数据后停止，适合一次性批式回填
- Continuous：连续模式，1ms 级延迟但算子支持有限
- 间隔越小延迟越低，但小批次吞吐与开销也越差
```

```python
# ProcessingTime Trigger：每 30 秒触发一批
query = (parsed.writeStream
         .outputMode("append")
         .format("console")
         .trigger(processingTime="30 seconds")   # 固定间隔触发
         .start())

# Once Trigger：处理当前可用数据后立即停止
query2 = (parsed.writeStream
          .outputMode("append")
          .format("parquet")
          .option("path", "/out/backfill")
          .trigger(once=True)                     # 一次性回填
          .start())
```

### Checkpoint

Checkpoint 是 Structured Streaming 实现容错与 exactly-once 的关键机制，它把查询的元数据（Source 偏移、聚合状态、Watermark、Schema）持久化到可靠存储（如 HDFS）。故障恢复时，引擎从 Checkpoint 恢复偏移与状态，配合可重放的 Source 重新处理，保证数据不丢不重。每个流式查询必须有唯一的 checkpointLocation。

```text
要点
- 持久化偏移、状态、Watermark、Schema 等元数据
- 故障恢复时从 Checkpoint 恢复，实现 exactly-once
- 每个流查询必须配置唯一 checkpointLocation
- 变更查询逻辑后，Checkpoint 不兼容需删除重建
- 推荐存放到 HDFS/S3 等可靠分布式存储
```

```scala
val query = spark.readStream
  .format("kafka")
  .option("kafka.bootstrap.servers", "broker1:9092")
  .option("subscribe", "events")
  .load()
  .selectExpr("CAST(value AS STRING)")
  .writeStream
  .format("parquet")
  .option("path", "/out/events")
  .option("checkpointLocation", "hdfs://namenode:8020/checkpoints/events")  // 唯一目录
  .outputMode("append")
  .start()

// 重启后从 checkpoint 恢复，不丢不重
query.awaitTermination()
```

### Watermark

Watermark（水印）是处理乱序与延迟数据、控制状态无限增长的机制。它基于事件时间，声明"允许的最晚到达延迟"（如 10 分钟），引擎据此判定某时间窗口的数据已齐，可以输出结果并清理过期状态。只有带事件时间（event-time）的聚合才支持 Watermark，且需配合时间窗口使用。

```text
要点
- 处理乱序/延迟到达的数据，界定窗口结果何时输出
- 用 withWatermark("ts", "10 minutes") 声明延迟阈值
- 输出晚于 Watermark 的迟到数据，但不再更新窗口
- 超期状态被自动清理，防止状态无限膨胀
- 仅在事件时间聚合（窗口 + 水印）下生效
```

```python
from pyspark.sql import functions as F

events = (spark.readStream
          .format("kafka")
          .option("kafka.bootstrap.servers", "broker1:9092")
          .option("subscribe", "click_events")
          .load()
          .selectExpr("CAST(value AS STRING) as json")
          .select(F.from_json("json", "uid STRING, ts TIMESTAMP").alias("data"))
          .select("data.uid", "data.ts"))

# 10 分钟窗口 + 5 分钟水印：容忍 5 分钟延迟
windowed = (events
            .withWatermark("ts", "5 minutes")
            .groupBy(F.window("ts", "10 minutes"), "uid")
            .count())

windowed.writeStream \
    .outputMode("append") \
    .format("console") \
    .option("truncate", "false") \
    .start()
```

### State

State 是流式聚合在跨批次间维护的中间状态，用于累计计数、求和、会话等需要跨微批记忆的计算。Structured Streaming 用状态存储（State Store，默认基于 HDFS 的 RocksDB）持久化状态，配合 Checkpoint 实现容错。无界聚合（如全局 count）会让状态无限增长，需用水印或定期清理来控制。

```text
要点
- 流式聚合在批次间保存的中间结果
- 由 State Store（HDFS/RocksDB）持久化，随 Checkpoint 容错
- 有状态算子：groupBy 聚合、mapGroupsWithState、flatMapGroupsWithState
- 无界状态需用水印或自定义清理防止膨胀
- 可用 mapGroupsWithState 实现任意自定义有状态逻辑
```

```scala
import org.apache.spark.sql.streaming.GroupState

// 用 flatMapGroupsWithState 实现会话超时检测
def trackSession(uid: String,
                 events: Iterator[Long],
                 state: GroupState[Long]): Iterator[(String, String)] = {
  val lastTs = state.getOption.getOrElse(0L)
  val latest = events.max
  if (state.hasTimedOut) {
    state.remove()
    Iterator((uid, s"session_expired"))
  } else {
    state.update(latest)
    state.setTimeoutDuration("30 seconds")
    Iterator((uid, s"session_active"))
  }
}

val sessions = events
  .groupByKey(_.uid)
  .flatMapGroupsWithState(
    outputMode = org.apache.spark.sql.streaming.OutputMode.Update(),
    timeoutConf = GroupStateTimeout.ProcessingTimeTimeout())(trackSession)
```

## 工作原理

Structured Streaming 的执行模型是「无界表 + 增量查询」：流数据每批到达后作为新行追加到无界表，用户查询被增量应用到新数据上，结果按输出模式写出。整条链路由 Trigger 驱动、Checkpoint 保障容错、State Store 维护跨批状态、Watermark 控制事件时间。

```text
微批执行循环（每批）：
1. Trigger 触发 -> 引擎向 Source 询问「从上个已提交偏移到当前」的新数据
2. 新数据作为本批 DataFrame 输入
3. 对「本批新数据 + 上一批状态」执行增量查询（Catalyst 优化 + 代码生成）
4. 按 OutputMode 把结果写入 Sink
5. 原子提交：偏移 + 状态 + 输出提交信息写入 Checkpoint
6. 故障恢复：从 Checkpoint 最后一个已提交批次重新执行
```

```text
容错链路：
Source（可重放，记录偏移）
  -> Checkpoint（偏移 + 状态 + 已提交批次，存 HDFS/S3）
  -> Sink（幂等写入）
三层配合，实现端到端 exactly-once
```

连续模式（Continuous）是另一条执行路径：Source 以流式接口持续读取，算子不再按批划分，提交延迟降到毫秒级，但只支持有限的无状态算子（select/filter/map 等），且 Sink 的容错语义弱于微批，生产环境默认用微批。


## 应用场景实战

### 场景一：实时点击流窗口聚合

从 Kafka 读取点击事件，按 10 分钟窗口 + 水印做 PV/UV 统计，输出到 Console 与 Kafka，完整串联 Source、Watermark、聚合与 Sink。

```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("ClickStreamAgg").getOrCreate()

clicks = (spark.readStream
          .format("kafka")
          .option("kafka.bootstrap.servers", "broker1:9092")
          .option("subscribe", "clicks")
          .option("startingOffsets", "latest")
          .load()
          .selectExpr("CAST(value AS STRING) as json")
          .select(F.from_json("json", "uid STRING, ts TIMESTAMP").alias("d"))
          .select("d.uid", "d.ts"))

# 5 分钟水印容忍迟到，10 分钟滚动窗口聚合 PV
pv = (clicks
      .withWatermark("ts", "5 minutes")
      .groupBy(F.window("ts", "10 minutes"))
      .count()
      .alias("pv"))

pv.writeStream \
  .outputMode("append") \
  .format("console") \
  .option("truncate", "false") \
  .trigger(processingTime="30 seconds") \
  .option("checkpointLocation", "/tmp/ckpt/clicks") \
  .start()
```

### 场景二：基于 ForeachBatch 的微批写外部存储

使用 ForeachBatch Sink，把每个微批的数据写入 MySQL 或自定义存储，实现灵活的按批落库，适用于结果表写入关系型数据库的实时场景。

```scala
import org.apache.spark.sql.{DataFrame, SparkSession}

val spark = SparkSession.builder().appName("ForeachBatchDemo").getOrCreate()

val stream = spark.readStream
  .format("rate")
  .option("rowsPerSecond", 5)
  .load()

// 自定义每批写入逻辑：可写 JDBC、写文件、调用外部 API 等
val query = stream.writeStream
  .outputMode("append")
  .foreachBatch { (batchDF: DataFrame, batchId: Long) =>
    // 每个微批执行一次，batchDF 是普通 DataFrame
    val agg = batchDF.groupBy("value").count()
    agg.write
      .mode("append")
      .format("jdbc")
      .option("url", "jdbc:mysql://db:3306/warehouse")
      .option("dbtable", "stream_agg")
      .option("user", "root")
      .option("password", "secret")
      .save()
  }
  .option("checkpointLocation", "/tmp/ckpt/foreach")
  .start()

query.awaitTermination()
```

### 场景三：实时 ETL 明细落盘 + 窗口聚合双路输出

同一份 Kafka 订单流，一路 Append 模式写 Parquet 明细，一路带 Watermark 做窗口 GMV 聚合，展示一个流式查询的两种输出形态（多路 writeStream 从同一 Source 派生）。

```scala
import org.apache.spark.sql.SparkSession
import org.apache.spark.sql.functions._

val spark = SparkSession.builder()
  .appName("StreamingETL")
  .getOrCreate()

import spark.implicits._

val raw = spark.readStream
  .format("kafka")
  .option("kafka.bootstrap.servers", "broker1:9092")
  .option("subscribe", "order_events")
  .load()
  .selectExpr("CAST(value AS STRING) as json")
  .select(from_json($"json",
    "order_id STRING, uid STRING, amount DOUBLE, ts TIMESTAMP").alias("d"))
  .select("d.*")

// 路一：明细实时落盘（Append + Parquet）
val detail = raw.writeStream
  .outputMode("append")
  .format("parquet")
  .option("path", "/data/stream/order_detail")
  .option("checkpointLocation", "hdfs://ns1/checkpoints/order_detail")
  .start()

// 路二：5 分钟窗口 + 10 分钟水印，按用户聚合 GMV（Update 模式）
val agg = raw
  .withWatermark("ts", "10 minutes")
  .groupBy(window($"ts", "5 minutes"), $"uid")
  .agg(sum($"amount").alias("gmv"))
  .writeStream
  .outputMode("update")
  .format("console")
  .option("truncate", "false")
  .option("checkpointLocation", "hdfs://ns1/checkpoints/order_agg")
  .start()

detail.awaitTermination()
agg.awaitTermination()
```

## 性能与调优

```text
Structured Streaming 调优主线：并行度 -> 状态 -> Trigger -> Sink 瓶颈
1. 并行度：Kafka topic 分区数 = 消费并行度上限，分区不够先扩分区
2. 状态大小：大状态换 RocksDB State Store，避免默认实现 OOM 与 GC 抖动
3. Trigger 间隔：延迟敏感用短间隔（5s 内），吞吐优先用长间隔 + 大批
4. 背压：消费速度跟不上时，用 maxOffsetsPerTrigger 限速或扩分区
5. 水印与窗口：窗口粒度越大状态越多，别开过大的窗口
6. 输出批大小：ForeachBatch 里批量写库，避免每批大量小事务
7. 监控指标：盯 inputRowsPerSecond / processedRowsPerSecond / stateRows
```

```text
指标速查：
inputRowsPerSecond      每秒输入行数，低于预期查 Source 与分区数
processedRowsPerSecond  每秒处理行数，持续低于输入则积压
stateRows / stateSize   状态行数与大小，异常增长查 Watermark/清理逻辑
batchDuration           单批耗时，连续多批超时说明处理能力不足
```

## 安全与权限

```text
1. Kafka 安全 —— SASL/SSL 认证 + ACL，流任务用专用服务账号消费与写入
2. 敏感数据 —— 消费后立即脱敏/过滤（身份证、手机号），再进下游
3. Checkpoint 权限 —— checkpoint 目录限制写权限，防止被其它任务覆盖
4. 输出权限 —— Sink 目标（HDFS 目录/Kafka topic/库表）按最小权限授权
5. 审计 —— 流任务谁在跑、读哪个 topic、写哪个目标，要可追溯
```

## 故障排查

```text
常见故障与定位：
1. 重启报 checkpoint 不兼容 —— 查询逻辑（Schema/状态结构）变了，需删 checkpoint 重建
2. OffsetOutOfRangeException —— Kafka 保留期短于消费进度，调保留期或重建 checkpoint
3. 状态无限增长 OOM —— 无界聚合没 Watermark/超时清理，加 Watermark 或 timeout
4. 处理延迟持续上升 —— 消费速度大于处理速度，扩分区/调 Trigger/查倾斜
5. 空批频繁 —— 无新数据仍触发，用 noDataStreamEventThreshold 控制
6. 输出重复 —— Sink 非幂等 + 任务重试导致，写库加主键去重或做幂等写入
```

```scala
// 程序内查看流查询状态与进度
val active = spark.streams.active      // 所有活动查询
active.foreach { q =>
  println(s"query=${q.name} status=${q.status} progress=${q.lastProgress}")
}

// 注册监听器：查询失败时及时告警
spark.streams.addListener(new StreamingQueryListener {
  override def onQueryStarted(e: StreamingQueryListener.QueryStartedEvent): Unit = {}
  override def onQueryProgress(e: StreamingQueryListener.QueryProgressEvent): Unit = {}
  override def onQueryTerminated(e: StreamingQueryListener.QueryTerminatedEvent): Unit = {
    println(s"terminated: ${e.id} error=${e.exception}")
  }
})
```

## 常见问题

```text
Q1: 微批和连续模式的区别？
A: 微批是默认模式，按 Trigger 间隔把新数据打包成批执行，吞吐高、算子支持全；连续模式毫秒级延迟，但只支持有限算子（select/filter/map 等），生产很少用。

Q2: Append、Update、Complete 输出模式的区别？
A: Append 只输出新增行（适合明细落盘）；Update 输出本批有更新的行（适合聚合结果更新）；Complete 每次输出全量聚合结果（适合小基数聚合）。

Q3: Watermark 一定保证不丢数据吗？
A: 不。Watermark 只声明「允许的迟到上限」，晚于水印的迟到数据会被丢弃（聚合）或不处理。想少丢就把水印调大，代价是状态留存更久。

Q4: 为什么必须用唯一的 checkpointLocation？
A: checkpoint 记录了源偏移、状态、已提交批次等元数据。两个查询共用会互相覆盖导致丢数据或重复；重启时引擎还会严格校验 Schema 一致性。

Q5: 端到端 exactly-once 怎么保证？
A: 三层：Source 可重放（Kafka 按偏移重读）+ Checkpoint 记录已提交偏移 + Sink 幂等（Kafka 写、带主键的库表、幂等的 ForeachBatch 逻辑）。三层缺一不可。

Q6: State 存不下怎么办？
A: 换 RocksDB State Store（本地磁盘 + 增量 checkpoint）；缩小窗口/水印；对无界状态加清理（timeout、会话过期）；仍不够则按 key 分流到多个任务。

Q7: 流任务重启后从哪里继续消费？
A: 从 checkpoint 记录的「最后已提交批次」继续，不重不丢。若 checkpoint 被删，则按 startingOffsets 从头（earliest）或最新（latest）开始。
```

## 面试题

```text
1. Structured Streaming 的「无界表」模型是什么？
   答：把持续到达的数据流看作一张无限增长的表，新数据每批追加为行。用户查询定义在这张表上的增量计算，微批执行 = 每批对新增行执行一次查询。

2. 如何实现端到端 exactly-once？
   答：可重放 Source（Kafka 记录偏移）+ Checkpoint（原子记录已处理偏移与状态）+ 幂等 Sink。失败时从上次 commit 重放，Sink 幂等保证不重复写入。

3. Watermark 是怎么工作的？
   答：用户声明最大延迟阈值，引擎跟踪「已见最大事件时间 - 阈值」作为水印；窗口结束时间早于水印即判定数据已齐，输出结果并清理状态；晚于水印到达的迟到数据被丢弃。

4. 有状态聚合和无状态操作的区别？
   答：无状态操作（filter/map/select）每行独立、不跨批记忆；有状态聚合（groupBy、mapGroupsWithState）在 State Store 保存跨批中间结果，用于计数、累计、会话等。

5. 为什么要用 mapGroupsWithState / flatMapGroupsWithState？
   答：内置聚合算子覆盖不了自定义逻辑（会话超时、状态机、去重窗口）。这两个算子按 key 维护任意自定义状态，并支持超时机制自动清理过期状态。

6. 数据延迟越来越大怎么排查？
   答：看 processedRowsPerSecond 是否长期低于 inputRowsPerSecond；检查 Kafka 分区数是否等于并行度；看 state 是否膨胀（GC/磁盘慢）；看 Sink 是否成为瓶颈（写库慢、事务大）。

7. Structured Streaming 与 Flink 的取舍？
   答：Structured Streaming 与 Spark 生态统一（批流一体、复用 Catalyst），微批吞吐高，但状态管理和超低延迟不如 Flink。低延迟、复杂状态场景 Flink 更合适。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每个流式查询配置唯一的 checkpointLocation，并存放到 HDFS/S3 等可靠存储，避免本地目录丢失。
2. 涉及事件时间聚合时必须设置 Watermark，防止状态无限增长、及时输出迟到窗口。
3. 选择合适 Trigger：批式回填用 Once，实时大吞吐用微批，超低延迟才考虑 Continuous。
4. 用 ForeachBatch 写外部系统时，确保写入逻辑幂等，配合 checkpoint 实现端到端 exactly-once。
5. 生产环境监控查询指标（输入速率、处理延迟、状态大小），及时扩容或调优。
6. 尽量用内建聚合函数，避免在无界流上做需要保存全部历史的状态操作。
7. 修改查询逻辑后，若 Schema 或状态结构变化，需清理旧 checkpoint 目录重启，避免兼容性报错。
8. Kafka 消费偏移交给 checkpoint 管理，别手动 seek，避免偏移与 checkpoint 不一致。
9. 大状态任务显式配置 RocksDB State Store，并在独立磁盘上运行，避免默认状态存储 OOM。

### 踩坑记录

```text
坑 1：checkpoint 目录复用导致启动失败
结论：查询启动报 checkpoint 不兼容错误
原因：多个查询共用了同一个 checkpointLocation，或修改查询逻辑后未重建
解法：每个查询用唯一 checkpoint 目录；变更逻辑后删除旧 checkpoint 再启动

坑 2：未设 Watermark 导致状态无限增长
结论：有状态聚合状态越积越大，Executor 内存/磁盘耗尽
原因：事件时间聚合未声明 Watermark，历史窗口状态永不清理
解法：添加 withWatermark 声明延迟阈值，让引擎自动清理过期状态

坑 3：Socket Source 丢失数据
结论：测试时数据丢失，无法保证 exactly-once
原因：Socket Source 不可重放，故障恢复后无法从偏移重读
解法：生产环境用 Kafka/File 等可重放 Source，Socket 仅用于本地测试

坑 4：Kafka 消费报 offset 越界
结论：启动时抛出 OffsetOutOfRangeException
原因：startingOffsets 指定 earliest/latest 但 checkpoint 里的偏移已被清理（Kafka 保留期过了）
解法：设置 Kafka 保留期足够长，或重建 checkpoint 并重新指定起始偏移

坑 5：append 模式却用了 complete 聚合
结论：运行时报 output mode 不支持的异常
原因：在无窗口/无水印的聚合上使用了 append 输出，append 无法增量输出聚合结果
解法：改用 complete 模式，或给聚合加窗口与水印后使用 append

坑 6：File Source 重复读被覆盖/追加的文件
结论：同一文件的数据被处理多次，下游重复
原因：File Source 按「文件路径 + 修改时间」判断新文件，源文件被覆盖或追加写会触发重读
解法：源文件写完原子改名（rename）后再进入监控目录，保证文件内容不变

坑 7：append 模式 + 窗口聚合看起来"丢结果"
结论：窗口结果迟迟不输出，以为丢了
原因：append 只输出不可变结果，窗口聚合必须等窗口结束（越过水印）才输出一次
解法：需要实时看到窗口中间结果用 update 模式，append 只用于最终结果
```
