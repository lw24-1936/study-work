## 概述

Spark 源码解析围绕「一个作业从提交到执行完成」的主线展开：SparkContext 是驱动程序的入口，DAG Scheduler 把 RDD 血缘切分成 Stage 和 Task，Task Scheduler 把 Task 分发到 Executor，BlockManager 负责数据块存取，MemoryManager 管理执行/存储内存，Shuffle 负责跨分区数据交换。理解这些组件，才能看懂 Spark UI 的调度信息、定位 OOM 与慢作业。
```text
作业执行主线（源码视角）：
1. action 触发 -> DAGScheduler 从最后一个 RDD 反向回溯血缘
2. 遇到 Shuffle 依赖切分 Stage，形成 DAG
3. DAGScheduler 提交 TaskSet 给 TaskScheduler
4. TaskScheduler 按数据本地性把 Task 派发到 Executor
5. Executor 用 BlockManager 读写数据、MemoryManager 分配内存
6. Shuffle 读写贯穿 Stage 之间，是性能与容错的关键
```

```scala
// 从一条最简单的作业看完整链路
import org.apache.spark.sql.SparkSession
val spark = SparkSession.builder().master("local[2]").appName("src").getOrCreate()
val rdd = spark.sparkContext.parallelize(1 to 100)
val result = rdd.map(_ * 2).filter(_ % 3 == 0).reduce(_ + _) // reduce 触发 action
println(result)
// 内部依次经过: SparkContext -> DAGScheduler -> TaskScheduler -> Executor
```
## 核心概念

Spark 源码的主线组件共六个：SparkContext 是入口与总管家，DAG Scheduler 负责切 Stage，Task Scheduler 负责派发 Task，BlockManager 管数据块，MemoryManager 管内存，Shuffle 管 Stage 间数据交换。下面逐个拆解。

### SparkContext

SparkContext（Spark 2.x 起被封装在 SparkSession 内部）是驱动程序的入口与作业的总管家。它持有集群配置（SparkConf）、集群资源管理器接口（SchedulerBackend）、调度器（DAGScheduler/TaskScheduler）、块管理器、以及各类组件的初始化。所有 RDD 的创建、广播变量、累加器的注册都通过它完成，一个 JVM 通常只允许存在一个活跃的 SparkContext。
```text
SparkContext 要点：
1. 职责 —— 组件装配：创建 SparkEnv（含 BlockManager/MemoryManager/序列化器）
2. 持有 —— DAGScheduler、TaskScheduler、SchedulerBackend、SparkUI
3. 生命周期 —— 通过 createSparkContext 初始化，stop() 释放所有资源
4. 入口方法 —— parallelize/textFile 创建 RDD，runJob 触发作业
5. SparkSession 是它的门面，底层最终调用 SparkContext
```

```scala
import org.apache.spark.{SparkConf, SparkContext}
// 传统方式直接构建 SparkContext（SparkSession 内部也做同样的事）
val conf = new SparkConf()
  .setAppName("SparkContextDemo")
  .setMaster("local[2]")
val sc = new SparkContext(conf)
// 作业提交的入口：runJob 触发 action
val rdd = sc.parallelize(Seq(1, 2, 3, 4))
val sum = rdd.reduce(_ + _)   // 内部调用 sc.runJob
// 自定义累加器（SparkContext 负责注册与汇总）
val acc = sc.longAccumulator("even_count")
rdd.foreach(x => if (x % 2 == 0) acc.add(1))
println(s"偶数个数: ${acc.value}")
sc.stop()
```
### DAG Scheduler

DAG Scheduler 是高层调度器，把用户提交的 RDD 血缘（DAG）转换为按 Stage 组织的 Task 集合。它从触发 action 的最后一个 RDD 反向遍历依赖：遇到窄依赖（NarrowDependency）继续回溯，遇到宽依赖（ShuffleDependency）就切分出一个新 Stage。切分完成后，按 Stage 的前后依赖顺序，把每个 Stage 打包成 TaskSet 交给 TaskScheduler。
```text
DAG Scheduler 要点：
1. 核心方法 —— handleJobSubmitted：反向切分 Stage，生成 ResultStage 与 ShuffleMapStage
2. 窄依赖 —— 子分区只依赖单个父分区，同 Stage 内流水线执行
3. 宽依赖 —— 子分区依赖多个父分区，触发 Stage 边界与 Shuffle
4. 容错 —— Stage 失败重算，窄依赖只需重算丢失分区，宽依赖可能重算整个上游
5. 输出 —— TaskSet（每个 Task 处理一个分区），附带数据本地性偏好
```

```scala
// 观察 Stage 切分的边界（宽依赖处会切出新 Stage）
val sc = spark.sparkContext
val rdd = sc.parallelize(1 to 1000, 4)
val pairs = rdd.map(x => (x % 10, x))          // 窄依赖，同 Stage
val grouped = pairs.groupByKey()               // 宽依赖，切出新 Stage
val counts = grouped.mapValues(_.sum)          // 窄依赖，同 Stage
counts.collect()
// 用 toDebugString 看血缘与依赖类型
println(counts.toDebugString)
// 输出中的 ShuffledRDD 即宽依赖边界
```
### Task Scheduler

Task Scheduler 是底层调度器，负责把 DAG Scheduler 生成的 TaskSet 实际派发到 Executor 上执行。它按数据本地性（PROCESS_LOCAL -> NODE_LOCAL -> RACK_LOCAL -> ANY）选择最优节点，处理任务失败重试、慢任务推测执行（speculation）、以及多作业间的资源竞争（通过 SchedulerBackend 与集群管理器交互）。不同部署模式对应不同实现（如 YARN 下是 YarnScheduler）。
```text
Task Scheduler 要点：
1. 数据本地性 —— 优先把 Task 派到数据所在节点，逐级降级
2. 推测执行 —— 检测明显落后的 Task，在另一节点启动副本，先完成的胜出
3. 失败重试 —— spark.task.maxFailures 控制，超过则整个作业失败
4. 调度模式 —— FIFO 默认，可切 FAIR 支持多作业并发共享资源
5. 依赖 SchedulerBackend —— 负责与 YARN/K8s/Standalone 通信申请 Executor
```

```scala
// 推测执行与本地性相关配置
spark.conf.set("spark.speculation", "true")                 // 开启推测执行
spark.conf.set("spark.speculation.multiplier", "1.5")       // 慢于中位数 1.5 倍触发
spark.conf.set("spark.locality.wait", "3s")                 // 等待更高本地性的时间
spark.conf.set("spark.task.maxFailures", "4")               // 任务最大重试次数
// FAIR 调度：多作业共享资源
spark.conf.set("spark.scheduler.mode", "FAIR")
// 提交一个含长尾任务的小作业观察调度
val data = sc.parallelize(1 to 1000, 8)
data.mapPartitions { it => Thread.sleep(10); it }.sum()
```
### BlockManager

BlockManager 是每个 Executor（以及 Driver）上的块存储管理器，负责 RDD 缓存块、Shuffle 中间数据、广播变量的本地存取与跨节点传输。它内部维护内存（MemoryStore）与磁盘（DiskStore）两级存储，通过 BlockManagerMaster 与 Driver 通信登记块位置。读数据时先查本地，再根据副本位置远程拉取。
```text
BlockManager 要点：
1. 结构 —— MemoryStore（内存块）+ DiskStore（磁盘块）+ 传输服务（Netty）
2. 存储级别 —— MEMORY_ONLY / MEMORY_AND_DISK / DISK_ONLY / *_SER 等
3. 块寻址 —— BlockManagerId（executorId + host + port）定位块所在节点
4. 与 Shuffle 协作 —— Shuffle 写出/读入都经 BlockManager 落地
5. 淘汰 —— 内存不足时按 LRU 淘汰，可溢出到磁盘
```

```scala
import org.apache.spark.storage.StorageLevel
val rdd = sc.parallelize(1 to 100000, 4).map(x => (x % 100, x))
// 缓存即写入 BlockManager 的内存/磁盘
rdd.persist(StorageLevel.MEMORY_AND_DISK)
// 触发缓存落盘
rdd.count()
// 查看块信息（Spark UI 的 Storage 页对应此数据）
val env = spark.sparkContext.env
val blockManager = env.blockManager
println(s"内存已用: ${blockManager.memoryStore.memoryUsed}")
// 释放块
rdd.unpersist()
```
### MemoryManager

MemoryManager 负责在 Executor 内划分 JVM 堆内存给「执行内存」（用于 Shuffle、聚合、连接）与「存储内存」（用于缓存 RDD）。Spark 1.6 起用统一内存管理（UnifiedMemoryManager）：执行与存储共享一块内存，可互相借用，由 `spark.memory.fraction` 控制共享区占堆比例、`spark.memory.storageFraction` 控制存储区初始占比。执行内存可抢占存储内存（淘汰缓存），反之存储不能抢占执行。
```text
MemoryManager 要点：
1. UnifiedMemoryManager —— 执行/存储共享内存，动态借用
2. spark.memory.fraction —— 共享区占 JVM 堆比例，默认 0.6
3. spark.memory.storageFraction —— 存储初始占比，默认 0.5
4. 执行内存可驱逐存储缓存，存储不能驱逐执行（保证计算不失败）
5. 堆外内存 —— spark.memory.offHeap.enabled 开启后走堆外，避免 GC
```

```scala
// 统一内存模型相关配置
spark.conf.set("spark.memory.fraction", "0.6")
spark.conf.set("spark.memory.storageFraction", "0.5")
spark.conf.set("spark.memory.offHeap.enabled", "true")
spark.conf.set("spark.memory.offHeap.size", "2g")
// 演示执行内存压力：大 groupBy 会占用执行内存，可能驱逐缓存
val big = sc.parallelize(1 to 5000000, 8).map(x => (x % 1000, x.toLong))
val cached = big.persist(StorageLevel.MEMORY_ONLY)  // 占用存储内存
cached.count()
big.groupByKey().mapValues(_.sum).count()           // 占用执行内存
```
### Shuffle

Shuffle 是 Spark 在 Stage 边界重分区数据的机制：上游 Stage 的每个 Task 把结果按分区号写出到本地（Shuffle Write），下游 Stage 的每个 Task 按需拉取自己分区对应的数据（Shuffle Read）。实现有 Hash Shuffle（老版本，文件爆炸）与 Sort Shuffle（当前默认，BypassMergeSortShuffleWriter 等按条件选择）。Shuffle 是 Spark 最昂贵的操作，也是性能优化的主战场。
```text
Shuffle 要点：
1. Shuffle Write —— map 端把数据按 partitionId 分区，溢写排序后落盘成数据文件 + 索引文件
2. Shuffle Read —— reduce 端从各 map 端拉取属于自己的数据块，聚合排序
3. SortShuffleManager —— 默认实现，Bypass 模式在分区少时免排序
4. Shuffle 依赖是 Stage 切分依据，也是容错重算的边界
5. 优化方向 —— 减少 Shuffle 次数、减少写出体积（序列化/压缩）
```

```scala
// 触发 Shuffle 的操作：groupByKey / reduceByKey / join / repartition
val pairs = sc.parallelize(1 to 1000000, 8).map(x => (x % 100, x))
// reduceByKey 在 map 端先合并，Shuffle 数据量小
val reduced = pairs.reduceByKey(_ + _)
reduced.count()
// 对比 groupByKey：map 端不合并，Shuffle 全量传输（更慢）
val grouped = pairs.groupByKey()
grouped.mapValues(_.sum).count()
// 观察 Shuffle 读写量
// Spark UI -> Stage 页 -> Shuffle Read/Write 列
spark.conf.set("spark.sql.shuffle.partitions", "400")
```
## 工作原理

一个作业从提交到结果返回，在源码层面走的是固定链路：SparkContext 初始化时装配 SparkEnv（BlockManager、MemoryManager、序列化器、ShuffleManager），action 触发后 DAGScheduler 把 RDD 血缘反向切分成 Stage，TaskScheduler 按数据本地性把 Task 派发到 Executor，Executor 的 TaskRunner 执行计算，Shuffle 数据经 BlockManager 读写，最后 Driver 聚合结果返回。
```text
作业执行链路（源码视角）：
1. SparkContext 初始化：创建 SparkEnv + DAGScheduler + TaskScheduler + SchedulerBackend（申请 Executor）
2. action 触发：RDD.runJob -> SparkContext.runJob -> DAGScheduler.handleJobSubmitted
3. DAGScheduler：从最后一个 RDD 反向遍历血缘，宽依赖处切 Stage，生成 ResultStage + ShuffleMapStage
4. submitStage：先提交父 Stage，父 Stage 完成后提交子 Stage，TaskSet 交给 TaskScheduler
5. TaskScheduler：TaskSetManager 按 PROCESS_LOCAL -> NODE_LOCAL -> RACK_LOCAL -> ANY 派发 Task
6. Executor 执行：TaskRunner 反序列化闭包 -> 计算 -> 结果经 BlockManager 写回
7. Shuffle：map 端写出数据文件 + 索引文件，reduce 端 ShuffleBlockFetcherIterator 拉取
8. 结果回收：Driver 聚合 Task 结果 -> action 返回
```

```scala
// 注册 SparkListener 观察 Stage 级调度事件（源码调试常用手段）
import org.apache.spark.scheduler.{SparkListener, SparkListenerStageCompleted}
spark.sparkContext.addSparkListener(new SparkListener {
  override def onStageCompleted(s: SparkListenerStageCompleted): Unit = {
    val info = s.stageInfo
    val wall = info.completionTime.get - info.submissionTime.get
    println(s"Stage ${info.stageId} ${info.name}: 墙钟 $wall ms, 任务数 ${info.numTasks}")
  }
})
// 跑一个多 Stage 作业，观察每个 Stage 的调度与计算耗时
val pairs = spark.sparkContext.parallelize(1 to 1000000, 8).map(x => (x % 100, x))
val result = pairs.reduceByKey(_ + _).sortByKey()
println(result.collect().take(5).mkString(","))
```

## 配置文件解析

spark-defaults.conf 中与源码组件一一对应的关键配置：
```text
# spark-defaults.conf（源码组件相关段）
# --- Scheduler（对应 DAGScheduler / TaskSchedulerImpl）---
spark.scheduler.mode                 FIFO
spark.task.maxFailures               4
spark.locality.wait                  3s
spark.speculation                    false
spark.scheduler.minRegisteredResourcesRatio 0.0   # 等待 Executor 注册比例
# --- BlockManager / 存储 ---
spark.storage.memoryMapThreshold     2m
spark.shuffle.service.enabled        true          # external shuffle service
spark.shuffle.blockTransferService   netty         # 块传输协议
# --- MemoryManager（对应 UnifiedMemoryManager）---
spark.memory.fraction                0.6           # 统一内存占堆比例
spark.memory.storageFraction         0.5           # 存储内存初始占比
spark.memory.offHeap.enabled         false
spark.memory.offHeap.size            2g
# --- Shuffle（对应 SortShuffleManager）---
spark.shuffle.compress               true          # Shuffle 数据压缩
spark.shuffle.spill.compress         true          # 溢写文件压缩
spark.shuffle.file.buffer            32k           # map 端写出缓冲
spark.shuffle.io.maxRetries          3             # 拉取重试次数
spark.shuffle.io.retryWait           5s
spark.shuffle.sort.bypassMergeThreshold 200        # Bypass 模式分区数阈值
```
```text
配置与源码对应关系：
spark.scheduler.mode        -> TaskSchedulerImpl.schedulingMode
spark.locality.wait         -> TaskSchedulerImpl 本地性降级计时器
spark.memory.fraction       -> UnifiedMemoryManager 构造参数
spark.memory.storageFraction -> UnifiedMemoryManager 的 storageRegion 初始值
spark.shuffle.sort.bypassMergeThreshold -> SortShuffleManager 选择 BypassMergeSortShuffleWriter 的条件
spark.shuffle.service.enabled -> 决定 Shuffle 读是否走 ExternalShuffleService
```
## 应用场景实战

### 场景一：通过 toDebugString 定位宽依赖边界

```scala
// 目标：理解一条复杂 RDD 链在哪里发生 Shuffle，以便优化
val sc = spark.sparkContext
val rdd = sc.textFile("/data/logs/access.log")        // 窄依赖：读文件
  .flatMap(_.split(" "))                              // 窄依赖
  .map(w => (w, 1))                                   // 窄依赖
  .reduceByKey(_ + _)                                 // 宽依赖：Shuffle，切 Stage
  .map { case (w, c) => (c, w) }                      // 窄依赖
  .sortByKey(ascending = false)                       // 宽依赖：Shuffle，切 Stage
println(rdd.toDebugString)
// 观察输出：每个 ShuffledRDD 都是一次 Stage 边界，据此判断 Shuffle 次数
```
### 场景二：诊断缓存未命中导致的重复计算

```scala
import org.apache.spark.storage.StorageLevel
val raw = spark.read.parquet("/warehouse/fact")
  .select("user_id", "amount", "dt")
// 错误示范：不缓存，同一数据被两个 action 重复计算（每次都要重新读 + Shuffle）
val agg = raw.groupBy("user_id").sum("amount")
agg.write.mode("overwrite").parquet("/out/total")   // 第 1 次计算
agg.write.mode("overwrite").parquet("/out/total2")  // 第 2 次重新计算！
// 正确示范：缓存中间结果，两次 action 复用
val cachedAgg = raw.groupBy("user_id").sum("amount").persist(StorageLevel.MEMORY_AND_DISK)
cachedAgg.write.mode("overwrite").parquet("/out/total")   // 第 1 次：计算并缓存
cachedAgg.write.mode("overwrite").parquet("/out/total2")  // 第 2 次：直接读缓存
cachedAgg.unpersist()
// 在 Spark UI Storage 页确认缓存命中，在 SQL 页确认 Stage 是否重复
```
### 场景三：用 SparkListener 采集作业指标

```scala
// 场景：对比「墙钟耗时」与「任务计算耗时」，判断慢在调度还是慢在计算
import org.apache.spark.scheduler._
val spark = SparkSession.builder().master("local[4]").appName("ListenerDemo").getOrCreate()
spark.sparkContext.addSparkListener(new SparkListener {
  override def onStageCompleted(s: SparkListenerStageCompleted): Unit = {
    val info = s.stageInfo
    val wall = info.completionTime.get - info.submissionTime.get
    println(s"Stage ${info.stageId} ${info.name}: 墙钟 $wall ms, 任务数 ${info.numTasks}")
  }
})
// 跑一个多 Stage 作业（reduceByKey 一次 Shuffle + sortByKey 一次 Shuffle）
val pairs = spark.sparkContext.parallelize(1 to 1000000, 8).map(x => (x % 100, x))
val result = pairs.reduceByKey(_ + _).sortByKey()
println(result.collect().take(5).mkString(","))
// 墙钟明显大于任务总时长 = 调度/排队开销大（资源不足、本地性等待）
// 墙钟接近任务总时长 = 计算本身是瓶颈，去优化 Shuffle/内存/代码
```
## 性能与调优

源码视角的调优，每个配置都对应一个组件实现，知道「调的是谁」才能调对：
```text
组件级调优杠杆：
1. DAGScheduler 层 —— 减少 Stage 数量与 Shuffle 次数：reduceByKey 替代 groupByKey、尽早过滤
2. TaskScheduler 层 —— 调度开销：任务数上万时调度成为瓶颈，合并小分区；本地性差调大 locality.wait
3. BlockManager 层 —— 存储级别选择、块传输缓冲、spark.shuffle.blockTransferService=netty
4. MemoryManager 层 —— fraction/storageFraction 配比决定 spill 与缓存淘汰频率
5. Shuffle 层 —— 写出器选择（Bypass vs Sort）、压缩、缓冲大小、reduce 端拉取并发
```

```scala
// Shuffle 相关源码级调优参数
spark.conf.set("spark.shuffle.compress", "true")
spark.conf.set("spark.shuffle.io.maxRetries", "3")
spark.conf.set("spark.shuffle.io.retryWait", "5s")
```

## 故障排查
```text
源码视角的故障定位：
1. 作业卡在 WAITING —— TaskScheduler 等待 Executor 注册（minRegisteredResourcesRatio），查资源是否充足
2. FetchFailed —— Shuffle 数据拉取失败：Executor 崩溃后数据需重算，看 maxRetries/retryWait 与动态分配
3. Block 丢失（MissingBlockException）—— 缓存被驱逐或 Executor 挂掉，RDD 从血缘重算，看是否反复触发
4. 内存溢出 —— MemoryManager 分配失败：执行内存不足（spill 无效则 OOM）与存储内存不足（缓存被逐）要分开看
5. 推测执行误伤 —— 慢任务副本重复执行导致外部写入重复，写外部系统需幂等或关 speculation
6. Driver 侧 Full GC —— collect 返回数据过大，repartition 控制返回量，聚合尽量推到 Executor 完成
```

## 常见问题
```text
Q1: SparkContext 初始化时发生了什么？
A: 创建 SparkEnv（BlockManager、MemoryManager、序列化器、ShuffleManager 等）、注册 BlockManagerMaster、创建 DAGScheduler/TaskScheduler、启动 SchedulerBackend 向集群申请 Executor、启动 SparkUI。
Q2: Stage 是怎么切出来的？
A: DAGScheduler 从触发 action 的 RDD 反向遍历依赖：窄依赖（NarrowDependency）留在当前 Stage，遇到宽依赖（ShuffleDependency）就切出一个新 Stage。最后一个 Stage 是 ResultStage，前面的都是 ShuffleMapStage。
Q3: 宽依赖和窄依赖的本质区别？
A: 窄依赖子分区只依赖父 RDD 的固定分区，可同 Stage 流水线执行、容错时只重算丢失分区；宽依赖子分区依赖父 RDD 全部分区，必须 Shuffle、失败时可能重算整个上游。
Q4: Task 是怎么被派发到 Executor 的？
A: DAGScheduler 把 Stage 打包成 TaskSet 交给 TaskScheduler，TaskScheduler 按数据本地性（PROCESS_LOCAL -> NODE_LOCAL -> RACK_LOCAL -> ANY）排队，通过 SchedulerBackend 的 reviveOffers 把 Task 放到 Executor 的 TaskRunner 里执行。
Q5: BlockManager 和 Shuffle 是什么关系？
A: Shuffle 数据读写都经 BlockManager：map 端写出的 ShuffleBlock 由 BlockManager 登记位置（上报 BlockManagerMaster），reduce 端通过 BlockManager 的 BlockTransferService 按 BlockManagerId 拉取。
Q6: 统一内存管理中执行内存为什么能抢占存储内存？
A: 执行内存（Shuffle/聚合）需要保证计算完成，失败代价是重算；存储内存（缓存）被逐只损失缓存命中。所以 UnifiedMemoryManager 允许执行内存驱逐存储缓存，反向不允许。
Q7: 为什么 sortByKey 比 map+collect 慢那么多？
A: sortByKey 是宽依赖，触发 Shuffle + 全局排序：map 端排序溢写、reduce 端归并，数据全量落盘传输。全局排序的成本是分布式重操作。
Q8: Executor 挂了对作业有什么影响？
A: 该 Executor 上的缓存块丢失、Shuffle 数据丢失：丢失的 Shuffle 数据由对应上游 Stage 重算（DAGScheduler 重提 ShuffleMapStage），缓存块从血缘重算。Executor 不足时作业可能一直重试失败。
Q9: 为什么 Spark 2.x 之后 SparkContext 通常由 SparkSession 创建？
A: SparkSession 是 SQL/Streaming/ML 的统一入口，内部持有一个 SparkContext；避免用户直接管理多个 context 导致资源混乱，SparkContext 仍是底层执行核心。
```
## 面试题
```text
1. 讲一下 Spark 作业提交到执行的完整流程。
   答：SparkContext 初始化（SparkEnv + 调度器 + SchedulerBackend 申请 Executor）-> action 触发 -> DAGScheduler 反向切 Stage -> TaskSet 交给 TaskScheduler -> 按本地性派发到 Executor 的 TaskRunner -> 执行并写结果 -> Driver 聚合返回。Shuffle 在 Stage 边界发生。
2. DAGScheduler 如何划分 Stage？
   答：从 ResultStage 反向遍历血缘，窄依赖在同一 Stage，宽依赖（ShuffleDependency）处切分，得到 ShuffleMapStage + ResultStage。提交时先提交父 Stage，父 Stage 全部完成才提交子 Stage。
3. TaskScheduler 的数据本地性是怎么实现的？
   答：每个 Task 带位置偏好（preferredLocations），TaskSetManager 按 PROCESS_LOCAL -> NODE_LOCAL -> RACK_LOCAL -> ANY 逐级匹配可用 Executor，每级等待 spark.locality.wait 时间后降级。
4. 推测执行（speculation）的原理与风险？
   答：TaskScheduler 监控 Task 进度，超过中位数一定倍数（spark.speculation.multiplier，默认 1.5）的慢任务在另一节点启动副本，先完成的胜出。风险：写外部系统的任务可能重复执行，需幂等或关闭 speculation。
5. BlockManager 是怎么做到跨节点读数据的？
   答：写块时向 Driver 的 BlockManagerMaster 登记（executorId, host, port），读时先查本地，未命中按 BlockManagerId 用 BlockTransferService（Netty）远程拉取；带副本的块（如广播变量）可按副本位置就近取。
6. 统一内存管理解决了什么问题？
   答：Spark 1.6 前执行/存储内存固定划分，缓存占满时执行内存不足、执行占满时缓存全被淘汰。UnifiedMemoryManager 让两者共享 spark.memory.fraction 区域、可互相借用，执行内存优先级更高，spark.memory.storageFraction 只控制初始比例。
7. Sort Shuffle 的三种写出器分别在什么时候用？
   答：BypassMergeSortShuffleWriter（分区数 <= byPassMergeThreshold 200 且无 map 端聚合，免排序快）；UnsafeShuffleWriter（Tungsten 优化，序列化对象 + 排序）；SortShuffleWriter（通用路径，map 端聚合后排序）。按分区数与是否需要聚合自动选择。
8. 为什么 groupByKey 不如 reduceByKey？从 Shuffle 机制解释。
   答：reduceByKey 的 map 端（ShuffleMapTask）先做局部聚合再写出，Shuffle 数据量小；groupByKey map 端不聚合，所有键值对原样落盘传输。Shuffle 写出的字节数决定网络与磁盘开销，所以 reduceByKey 快一个数量级。
```
## 最佳实践与踩坑记录

### 最佳实践

1. 读源码按「action -> DAGScheduler 切 Stage -> TaskScheduler 派发 -> Executor 执行」主线走，别零散跳读
2. 判断 Shuffle 次数先看 toDebugString 或 Spark UI 的 Stage 依赖图，宽依赖即边界
3. 能用 reduceByKey/aggregateByKey 就别用 groupByKey，前者 map 端先合并减少 Shuffle 数据
4. 被多个 action 复用的中间结果一定要 persist，避免重复计算
5. 内存紧张时用 MEMORY_AND_DISK_SER，序列化降低内存占用与 GC 压力
6. 慢作业先看 Shuffle 读写量与 GC 时间，再决定是调分区还是调内存
7. 理解统一内存模型（fraction/storageFraction），执行内存不足会直接溢出到磁盘

### 踩坑记录
```text
坑 1：groupByKey 导致 Shuffle 数据量爆炸
结论：大表 groupByKey 后 Shuffle 全量传输，作业极慢甚至 OOM。
原因：groupByKey 在 map 端不做任何合并，所有键值对原样落盘传输。
解法：改用 reduceByKey/aggregateByKey，在 map 端先局部合并。
坑 2：多个 action 未缓存导致重复计算
结论：同一 DataFrame 被多次写盘，作业耗时成倍增加。
原因：DataFrame 是惰性求值，每个 action 都从源头重新计算。
解法：复用中间结果先 persist，写完再 unpersist。
坑 3：执行内存不足频繁溢写磁盘
结论：Shuffle/聚合时任务不断 spill，耗时飙升。
原因：spark.memory.fraction 设置过小或数据量超过执行内存。
解法：调大执行内存占比，或增加分区降低单 Task 数据量。
坑 4：忽略数据本地性导致网络开销
结论：Task 被派到远程节点，读数据全走网络，慢。
原因：locality.wait 太短，调度器没等到本地节点就降级派发。
解法：适当调大 spark.locality.wait，或确保数据与计算同机架。
坑 5：小分区过多导致任务调度开销大
结论：数万个小 Task，调度与启动开销远超计算本身。
原因：上游分区过多（如大量小文件）未合并。
解法：读后 coalesce/repartition 收敛分区，避免海量小 Task。
坑 6：开启推测执行导致外部写入重复
结论：HBase/MySQL 等外部系统出现重复数据。
原因：慢任务被推测执行，两个副本都跑完写入逻辑。
解法：写外部系统的作业关闭 spark.speculation，或写入逻辑做幂等。
坑 7：动态分配开启但没配 shuffle service，Executor 退出后数据拉取失败
结论：作业报 FetchFailed，Stage 反复重算。
原因：Executor 动态回收后其 Shuffle 数据无人承接，reduce 端拉不到。
解法：开启 spark.shuffle.service.enabled，或关闭动态分配固定 Executor。
```
