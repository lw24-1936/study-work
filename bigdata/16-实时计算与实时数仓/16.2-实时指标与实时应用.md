## 概述

实时指标是基于流式计算框架（以 Flink 为主）对业务事件流做秒级/亚秒级聚合，产出供大屏、告警、风控、推荐实时消费的指标。与离线指标相比，实时指标强调「低延迟 + 可近似 + 可回溯」，常配合 Kafka、OLAP（ClickHouse/Doris）与状态存储（RocksDB）。实时应用是在指标之上的业务闭环，如实时风控、实时画像、实时运营触达。

```text
实时指标体系分层：
1. 原子指标 —— 直接聚合的量：PV、UV、GMV、点击次数
2. 派生指标 —— 原子指标加工：CTR、CVR、留存率、转化率
3. 复合指标 —— 多维组合：分渠道 GMV、分人群转化漏斗

实时计算技术要点：
4. 事件时间 —— 用事件发生时间而非处理时间，保证口径一致
5. 窗口聚合 —— 滑动/滚动/会话窗口承载大部分指标计算
6. 状态后端 —— RocksDB 支持超大状态与精确去重
7. 近似算法 —— HLL 估 UV，省内存，误差约 1~2%
8. 结果落库 —— 实时写 OLAP/Redis，供下游秒级查询
```

## UVPV

UV（独立访客）与 PV（页面浏览量）是最基础的流量指标。PV 是事件条数，UV 是去重后的访客数，两者比值反映人均访问深度。UV 精确计算需保存所有去重 ID，内存压力大，通常用 HLL 近似去重；PV 直接 COUNT 即可。

```text
U V / P V 要点：
1. PV —— COUNT(事件)，有访客行为即累加
2. UV —— 按访客 ID 去重计数，需状态或近似算法
3. 人均 PV —— PV / UV，衡量用户活跃深度
```

```sql
CREATE TABLE page_view (
  user_id STRING, page_id STRING, ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH ('connector'='kafka','topic'='page_view','format'='json');

SELECT TUMBLE_START(ts, INTERVAL '1' MINUTE) AS win_start,
       COUNT(*) AS pv, COUNT(DISTINCT user_id) AS uv
FROM page_view GROUP BY TUMBLE(ts, INTERVAL '1' MINUTE);
```

## DAUMAU

DAU（日活跃用户）与 MAU（月活跃用户）衡量产品活跃规模，DAU/MAU 即「用户粘性」。实时 DAU 是当日截至目前的活跃去重用户数，常用去重状态累加；MAU 通常离线批算，实时侧用近 30 天 HLL 合并近似。实时 DAU 常输出到 Redis 或大屏供观测。

```text
D A U / M A U 要点：
1. DAU —— 当日去重活跃用户数，实时用状态累加当天集合
2. MAU —— 近 30 天去重活跃，一般离线批算或 HLL 近似
3. 粘性 —— DAU / MAU 越高，留存与活跃越健康
```

```sql
CREATE TABLE login_event (
  user_id STRING, login_time TIMESTAMP(3),
  WATERMARK FOR login_time AS login_time - INTERVAL '5' SECOND
) WITH ('connector'='kafka','topic'='login_event','format'='json');

SELECT DATE_FORMAT(login_time, 'yyyy-MM-dd') AS dt,
       COUNT(DISTINCT user_id) AS dau
FROM login_event
GROUP BY DATE_FORMAT(login_time, 'yyyy-MM-dd');
```

## GMV

GMV（成交总额）是电商核心交易指标，等于有效订单成交金额之和，用于大促看板、秒级成交监控。由于订单状态会变化（下单、支付、取消），实时 GMV 口径必须明确统计「已支付订单」，并处理支付事件迟到与撤单扣减，用可更新状态保证准确。

```text
G M V 要点：
1. 定义 —— 有效（已支付）订单金额求和
2. 口径 —— 含不含运费/优惠/退款，须统一
3. 状态变更 —— 支付/取消事件到达后需增删累计值
```

```sql
CREATE TABLE pay_event (
  order_id STRING, amount DECIMAL(10, 2), pay_time TIMESTAMP(3),
  WATERMARK FOR pay_time AS pay_time - INTERVAL '10' SECOND
) WITH ('connector'='kafka','topic'='pay_event','format'='json');

SELECT TUMBLE_START(pay_time, INTERVAL '1' MINUTE) AS win_start,
       SUM(amount) AS gmv
FROM pay_event GROUP BY TUMBLE(pay_time, INTERVAL '1' MINUTE);
```

## CTRCVR

CTR（点击率）是点击量/曝光量，衡量内容的吸引力；CVR（转化率）是转化量/点击量，衡量点击到成交的转化效率。两者都是比率指标，实时计算时须先分别聚合分子分母再相除，绝不能对每条比率求平均。

```text
C T R / C V R 要点：
1. CTR = 点击数 / 曝光数，反映内容吸引力
2. CVR = 转化数 / 点击数，反映承接转化能力
3. 比率聚合 —— 分子分母分别 SUM 再相除，不做比率平均
```

```sql
CREATE TABLE ad_event (
  ad_id STRING, event_type STRING, ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH ('connector'='kafka','topic'='ad_event','format'='json');

SELECT ad_id,
  SUM(CASE WHEN event_type='impression' THEN 1 ELSE 0 END) AS imp_cnt,
  SUM(CASE WHEN event_type='click'      THEN 1 ELSE 0 END) AS clk_cnt,
  SUM(CASE WHEN event_type='convert'    THEN 1 ELSE 0 END) AS cvt_cnt
FROM ad_event GROUP BY ad_id;
-- 上层：ctr = clk_cnt/imp_cnt，cvr = cvt_cnt/clk_cnt
```

## 留存

留存衡量新增或活跃用户在后续某天仍活跃的比例，常见次日、7 日留存。实时留存需把「当天活跃用户」与「未来第 N 天仍活跃的用户」做关联，用状态保存首次活跃集合，后续活跃命中则计入留存分子。实时侧多为近似估计，精确留存以离线为准。

```text
留存要点：
1. 次日留存 = 当天新增用户中第 2 天仍活跃的占比
2. 本质 —— 首日用户集合 ∩ 第 N 日活跃用户集合
3. 留存率 = 交集人数 / 首日集合人数
```

```sql
CREATE TABLE active_event (
  user_id STRING, reg_date STRING, active_day STRING, ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH ('connector'='kafka','topic'='active_event','format'='json');

SELECT reg_date,
  COUNT(DISTINCT CASE WHEN active_day =
    DATE_FORMAT(DATE_ADD(TO_DATE(reg_date), 1), 'yyyy-MM-dd')
    THEN user_id END) AS day1_retained,
  COUNT(DISTINCT user_id) AS base_users
FROM active_event GROUP BY reg_date;
-- 留存率 = day1_retained / base_users
```

## Funnel

漏斗分析追踪用户沿一系列步骤的转化（浏览→加购→下单→支付），统计各步骤到达人数并计算步骤间转化率，定位流失环节。实时漏斗关键是「事件按用户 + 时间顺序匹配」，通常按窗口内有序事件匹配，可用 Flink 状态机或 CEP 实现。

```text
Funnel 要点：
1. 定义 —— 有序事件序列，统计逐步骤到达用户数
2. 转化率 —— 相邻步骤人数之比，定位流失环节
3. 口径 —— 严格有序 vs 宽松有序（可跳跃）
```

```sql
CREATE TABLE behavior (
  user_id STRING, step STRING, ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH ('connector'='kafka','topic'='behavior','format'='json');

SELECT step, COUNT(DISTINCT user_id) AS reach_users
FROM behavior GROUP BY step;
-- 各步骤人数对比得到漏斗：view > cart > order > pay
```

## CEP

CEP（复杂事件处理）在事件流上识别满足特定「模式」的事件序列，如「同一设备 1 分钟内登录失败超 5 次」。Flink CEP 提供 Pattern API 定义模式（连续、组合、循环、时间约束），比窗口聚合更适合表达跨事件的时序关系，是风控、异常检测、告警规则的核心能力。

```text
C E P 要点：
1. 模式 —— 定义事件序列结构：next / followedBy / 循环
2. 时间约束 —— within 限制模式在时间窗口内匹配
3. 应用 —— 刷单检测、连续登录失败、异常交易序列
```

```sql
SELECT *
FROM login_event
MATCH_RECOGNIZE (
  PARTITION BY user_id ORDER BY ts
  MEASURES FIRST(A.ts) AS first_fail_time, COUNT(*) AS fail_cnt
  ONE ROW PER MATCH
  AFTER MATCH SKIP PAST LAST ROW
  PATTERN (A{3,})
  DEFINE A AS A.result = 'fail'
);
```

## 实时风控

实时风控在事件发生的毫秒级窗口内对交易、登录、注册等行为做风险评估并即时拦截/放行。它把规则引擎、模型打分、黑白名单、设备指纹结合，形成「识别→评分→决策→处置」闭环。实时风控对延迟要求极高（通常 100ms 内出决策），常采用 Flink + Redis 在线特征。

```text
实时风控要点：
1. 目标 —— 毫秒级识别欺诈，损失发生前拦截
2. 链路 —— 事件 → 特征 → 规则/模型 → 风险分 → 决策
3. 关键指标 —— 拦截率、误杀率、响应延迟
```

```sql
CREATE TABLE txn_event (
  user_id STRING, txn_id STRING, amount DECIMAL(10, 2), ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH ('connector'='kafka','topic'='txn_event','format'='json');

SELECT user_id, COUNT(*) AS txn_cnt, SUM(amount) AS txn_amt
FROM txn_event
GROUP BY user_id, TUMBLE(ts, INTERVAL '5' MINUTE)
HAVING COUNT(*) > 10;   -- 5 分钟超 10 笔告警
```

## 黑白名单

黑白名单是风控最直接的名单策略：黑名单直接拦截，白名单直接放行，用于快速处置已知欺诈主体或保护可信用户。名单数据常存 Redis 或维表，实时流通过 Lookup Join 关联判断。名单需支持动态增删（人工运营 + 策略自动拉黑），并注意时效性与命中日志留痕。

```text
黑白名单要点：
1. 黑名单 —— 已知欺诈主体（用户/设备/IP/卡号）直接拦截
2. 白名单 —— 可信主体直接放行，降低误杀
3. 实时关联 —— 流事件 Lookup Join 名单维表即时判断
```

```sql
CREATE TABLE blacklist (
  user_id STRING PRIMARY KEY NOT ENFORCED, reason STRING
) WITH ('connector'='redis','table-name'='blacklist');

CREATE TABLE login_event (
  user_id STRING, ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH ('connector'='kafka','topic'='login_event','format'='json');

SELECT e.user_id, e.ts,
  CASE WHEN b.user_id IS NOT NULL THEN 'BLOCK' ELSE 'PASS' END AS decision
FROM login_event AS e
LEFT JOIN blacklist FOR SYSTEM_TIME AS OF e.ts AS b
  ON e.user_id = b.user_id;
```

## 设备指纹

设备指纹通过采集设备软硬件特征（屏幕、系统、字体、时区、浏览器等）生成唯一标识，用于识别同一台物理设备，对抗刷量、多账号欺诈。实时场景下设备指纹作为去重和风控关键维度，把「多账号」还原到「同设备」从而发现异常聚集。指纹需兼顾稳定性与区分度。

```text
设备指纹要点：
1. 原理 —— 多维软硬件特征组合哈希生成唯一 ID
2. 稳定性 —— 同一设备多次采集指纹应一致
3. 用途 —— 多账号识别、刷量检测、设备黑名单
```

```sql
CREATE TABLE register_event (
  user_id STRING, device_fp STRING, ip STRING, ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH ('connector'='kafka','topic'='register_event','format'='json');

SELECT device_fp,
  COUNT(DISTINCT user_id) AS account_cnt, COUNT(DISTINCT ip) AS ip_cnt
FROM register_event
GROUP BY device_fp, TUMBLE(ts, INTERVAL '1' HOUR)
HAVING COUNT(DISTINCT user_id) > 5;   -- 单设备 1 小时注册超 5 账号
```

## 实时画像

实时画像在用户行为发生的秒级内更新其标签与特征（偏好、活跃度、消费力、风险标签），供推荐、营销、风控实时消费。与离线画像（T+1）相比，实时画像强调「行为即标签」，用 Flink 流式聚合短期行为特征，再与离线长期特征合并，输出到 Redis/KV 供在线毫秒级读取。

```text
实时画像要点：
1. 目标 —— 行为发生秒级内更新用户标签
2. 特征 —— 短期实时特征 + 长期离线特征合并
3. 存储 —— Redis/HBase 等 KV，供在线低延迟查询
```

```sql
CREATE TABLE behavior_event (
  user_id STRING, action STRING, item_id STRING, ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH ('connector'='kafka','topic'='behavior_event','format'='json');

SELECT user_id,
  SUM(CASE WHEN action='click'    THEN 1 ELSE 0 END) AS click_1h,
  SUM(CASE WHEN action='add_cart' THEN 1 ELSE 0 END) AS cart_1h,
  SUM(CASE WHEN action='pay'      THEN 1 ELSE 0 END) AS pay_1h
FROM behavior_event GROUP BY user_id, TUMBLE(ts, INTERVAL '1' HOUR);
```

## 风险评分

风险评分把多维风险特征（名单命中、设备异常、行为频率、金额异常等）综合成 0~100 的分数，按分数区间决策（放行/验证/拦截）。评分可基于规则加权，也可基于机器学习模型（逻辑回归、GBDT）实时打分。实时评分链路强调「特征实时化 + 模型在线推理 + 分数落库/回传」。

```text
风险评分要点：
1. 定义 —— 综合多维特征输出 0~100 风险分
2. 方法 —— 规则加权 or 模型打分（LR/GBDT）
3. 决策 —— 低分放行 / 中分验证 / 高分拦截
```

```sql
SELECT user_id,
  (CASE WHEN hit_blacklist=1 THEN 40 ELSE 0 END)        -- 名单命中 +40
  + (CASE WHEN device_fp_abnormal=1 THEN 30 ELSE 0 END) -- 设备异常 +30
  + LEAST(txn_cnt_5m * 2, 20)                           -- 频率 + 上限 20
  + (CASE WHEN amount > 10000 THEN 10 ELSE 0 END)       -- 大额 +10
    AS risk_score
FROM risk_feature_view;
-- 决策：risk_score>=60 拦截，30~60 二次验证，<30 放行
```

## 应用场景实战

### 场景一：大促实时 GMV 与流量大屏

```sql
-- Kafka 事件 -> Flink 聚合 -> ClickHouse 大屏
CREATE TABLE pay_event (
  order_id STRING, amount DECIMAL(10, 2), pay_time TIMESTAMP(3),
  WATERMARK FOR pay_time AS pay_time - INTERVAL '10' SECOND
) WITH ('connector'='kafka','topic'='pay_event','format'='json');

CREATE TABLE gmv_sink (
  win_start TIMESTAMP(3), gmv DECIMAL(18, 2),
  PRIMARY KEY (win_start) NOT ENFORCED
) WITH ('connector'='jdbc','url'='jdbc:clickhouse://localhost:8123/default',
        'table-name'='realtime_gmv');

INSERT INTO gmv_sink
SELECT TUMBLE_START(pay_time, INTERVAL '1' MINUTE) AS win_start,
       SUM(amount) AS gmv
FROM pay_event GROUP BY TUMBLE(pay_time, INTERVAL '1' MINUTE);
```

```text
大屏口径设计：
1. 实时 GMV —— 分钟窗口 SUM(amount)，含当日累计
2. 实时 PV/UV —— 分钟窗口 COUNT / COUNT(DISTINCT user_id)
3. 大屏刷新 —— 每 5 秒查询 ClickHouse 最新窗口
4. 峰值保障 —— 双 11 需预扩 Flink 并行度与 Kafka 分区
```

### 场景二：实时风控——异常交易拦截

```shell
# Flink 风控作业启动
flink run -d -c com.example.RiskControlJob -p 16 risk-control.jar \
  --kafka-bootstrap localhost:9092 --redis-host localhost \
  --model-path /models/gbdt_risk.onnx
```

```text
风控链路设计：
1. 接入 —— 交易事件进 Kafka，Flink 消费
2. 名单关联 —— Lookup Join 黑名单/白名单维表
3. 特征计算 —— 近 5 分钟频率、金额、设备指纹聚集
4. 模型打分 —— 规则加权 + GBDT 模型，输出风险分
5. 决策回传 —— 风险分超阈值写回拦截结果，低延迟响应
6. 日志留痕 —— 命中详情写 HBase/ES 供追溯与申诉
```

## 最佳实践与踩坑记录

### 最佳实践

1. 明确口径 —— 每个指标先定义分子/分母、去重维度、事件类型，再写 SQL
2. 比率指标先聚合后相除，绝不做比率平均
3. UV/留存等去重指标按规模选精确去重或 HLL 近似，控制内存
4. 统一事件时间与水印策略，保证跨流 join 口径一致
5. 风控决策结果必落日志（输入 + 分数 + 原因），供追溯与误杀申诉
6. 名单、规则、模型阈值做成可动态配置，避免每次改策略都发版
7. 实时指标双写：明细落 OLAP 供分析，聚合值落 Redis 供在线查询

### 踩坑记录

```text
坑 1：COUNT(DISTINCT) 状态无限膨胀
结论：UV 类指标状态随去重键线性增长，长时间窗口 OOM。
原因：精确去重需保存所有去重 ID 到状态，窗口越长内存越大。
解法：改用 HLL 近似去重，或用支持精确去重的存储下沉去重。

坑 2：比率指标直接平均导致结果错误
结论：把每条记录算出的 CTR 求平均，与真实 CTR 不一致。
原因：每条记录的曝光基数不同，简单平均权重失真。
解法：分子分母分别 SUM 后再相除。

坑 3：忽略订单状态变更导致 GMV 虚高
结论：取消/退款的订单仍计入 GMV，金额偏大。
原因：只统计下单事件，未处理取消、退款事件对金额的扣减。
解法：以支付事件为准，并订阅取消/退款事件做状态扣减。

坑 4：水印设置过小导致迟到数据丢失
结论：网络抖动下部分支付事件被丢弃，指标偏小。
原因：水印提前过多，晚到事件超出 allowed lateness 被丢弃。
解法：结合业务容忍度设置水印与 allowed lateness，大促适当放宽。

坑 5：黑名单 Lookup Join 维表更新不及时
结论：新拉黑用户仍被放行，风控失效。
原因：维表缓存未及时刷新，Lookup 命中旧数据。
解法：开启维表定时刷新或 CDC 同步，缩短缓存 TTL。
```
