## 概述

实时数仓是对离线数仓的实时化升级，目标是把数据从「T+1 天级可见」提升到「秒级可见」，支撑实时大屏、实时监控、实时运营决策。它建立在流处理引擎（Flink）之上，核心是理解流、事件时间、窗口、状态、水位线、检查点这套流计算概念，再按 ODS/DWD/DWS/ADS 分层组织数据，最终通过 Kafka → Flink → OLAP 的链路对外提供实时查询。

```text
实时数仓的两大支柱：
1. 流计算概念 —— 事件时间/窗口/状态/水位线/检查点
2. 分层架构 —— ODS/DWD/DWS/ADS 四层，逐层加工
3. 数据链路 —— Kafka（传输）→ Flink（计算）→ OLAP（查询）
标准链路：业务库 → CDC → Kafka → Flink（分层加工）→ OLAP → 大屏/报表
```

## 流与事件

流（Stream）是无界、持续产生的事件序列，事件（Event）是流中的最小单元，代表「某时刻发生的一件事」（一次下单、一次点击、一条日志）。实时数仓处理的对象就是事件流，与批处理处理「静态数据集」不同，流处理要面对数据持续到达、可能乱序、无法一次性看全的特点。理解「事件携带事件时间」是流计算与批计算的分水岭。

```text
流与事件要点：
1. 流 —— 无界、持续产生的事件序列
2. 事件 —— 流的最小单元，代表某时刻发生的一件事
3. 特点 —— 持续到达、可能乱序、无法一次看全
4. 关键 —— 事件自带事件时间，是流计算正确性的基础
```

```sql
-- 一条下单事件（自带事件时间），定义为 Kafka 动态表
CREATE TABLE orders (
    order_id   BIGINT,
    amount     DECIMAL(10, 2),
    event_time TIMESTAMP(3)
) WITH (
    'connector' = 'kafka',
    'topic' = 'orders',
    'properties.bootstrap.servers' = 'localhost:9092',
    'format' = 'json'
);
```

## 事件时间

事件时间（Event Time）是事件「真实发生」的时间，记录在事件自身的字段里（如订单创建时间）。它是流计算正确性的基石：无论数据何时到达、如何乱序，按事件时间计算的窗口和聚合都能还原「业务真实发生的时序」。相比处理时间，事件时间不受网络延迟、系统抖动影响，是实时数仓统计口径的标准时间。

```text
事件时间要点：
1. 定义 —— 事件真实发生的时间，记录在事件字段里
2. 意义 —— 还原业务真实时序，不受传输延迟影响
3. 挑战 —— 事件可能乱序到达，需要水位线配合
4. 使用 —— 声明 WATERMARK 后，窗口按事件时间划分
```

```sql
-- 用事件时间字段声明水位线，后续窗口按事件时间计算
CREATE TABLE orders (
    order_id   BIGINT,
    amount     DECIMAL(10, 2),
    event_time TIMESTAMP(3),
    WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND
) WITH (
    'connector' = 'kafka',
    'topic' = 'orders',
    'properties.bootstrap.servers' = 'localhost:9092',
    'format' = 'json'
);
```

## 处理时间

处理时间（Processing Time）是事件「被系统处理」的时刻，即事件进入算子的墙上时钟时间。它实现简单、延迟最低，但受系统负载、网络延迟影响，无法还原业务真实时序。处理时间适合对时序要求不高的场景（如粗略的实时计数、系统监控），而涉及业务口径的统计（如「今天卖了多少」）必须用事件时间。

```text
处理时间要点：
1. 定义 —— 事件被系统处理的墙上时钟时刻
2. 优点 —— 实现简单、延迟最低、无需水位线
3. 缺点 —— 受负载/网络影响，无法还原业务时序
4. 适用 —— 对时序要求不高的粗略统计、监控告警
```

```sql
-- 用处理时间（PROCTIME()）做实时计数，无需水位线
CREATE TABLE clicks (
    user_id BIGINT,
    proctime AS PROCTIME()
) WITH (
    'connector' = 'kafka',
    'topic' = 'clicks',
    'properties.bootstrap.servers' = 'localhost:9092',
    'format' = 'json'
);

SELECT COUNT(*) FROM clicks GROUP BY TUMBLE(proctime, INTERVAL '10' SECOND);
```

## 窗口

窗口（Window）把无界的流切成有界的片段，让聚合「在每一段上」计算，是流式聚合的基本手段。Flink 提供滚动窗口（Tumbling，固定长度不重叠）、滑动窗口（Sliding，固定长度有重叠）、会话窗口（Session，按事件间隔动态切分）、以及全局窗口（Global，配合触发器）。窗口配合事件时间或处理时间，把「无限流」变成「一段段有限数据」来统计。

```text
窗口要点：
1. 作用 —— 把无界流切成有界片段，逐段聚合
2. 滚动窗口 —— 固定长度、不重叠（每分钟）
3. 滑动窗口 —— 固定长度、有重叠（每 30 秒看过去 1 分钟）
4. 会话窗口 —— 按事件间隔动态切分（用户会话）
```

```sql
-- 滚动窗口：每分钟统计订单金额
SELECT TUMBLE_START(event_time, INTERVAL '1' MINUTE) AS win_start,
       SUM(amount) AS total_amount
FROM orders
GROUP BY TUMBLE(event_time, INTERVAL '1' MINUTE);

-- 滑动窗口：每 30 秒看过去 1 分钟的订单数
SELECT COUNT(*) AS cnt
FROM orders
GROUP BY HOP(event_time, INTERVAL '30' SECOND, INTERVAL '1' MINUTE);
```

## 状态

状态（State）是流处理算子「记住的历史信息」，流计算的很多结果都依赖状态（如累计和、去重集合、窗口内数据、双流 join 的另一侧）。Flink 把状态托管（Managed State），支持在内存、RocksDB 中存储，并通过检查点持久化。状态是流处理区别于无状态批处理的核心，也是「有状态算子」正确性与容错的基础。

```text
状态要点：
1. 定义 —— 算子记住的历史信息，支撑聚合/去重/join
2. 类型 —— Keyed State（按 key 分）/ Operator State（算子级）
3. 存储 —— 堆内存或 RocksDB（可溢写磁盘）
4. 容错 —— 通过检查点持久化，故障后恢复
```

```java
// 有状态算子：KeyedState 累计每个用户的订单金额
orders.keyBy(Order::getUserId)
      .process(new KeyedProcessFunction<Long, Order, Long>() {
          private ValueState<Long> total;
          @Override
          public void open(Configuration c) {
              total = getRuntimeContext().getState(
                  new ValueStateDescriptor<>("total", Long.class));
          }
          @Override
          public void processElement(Order o, Context ctx, Collector<Long> out)
                  throws Exception {
              Long cur = total.value() == null ? 0 : total.value();
              total.update(cur + o.getAmount());
              out.collect(total.value());
          }
      });
```

## 水位线

水位线（Watermark）是事件时间的进度标记：它声明「事件时间早于水位线的数据都已到齐」，水位线之后不会再有更早的事件。水位线驱动事件时间窗口的触发——当水位线越过窗口结束时间，窗口才关闭并输出结果。它解决的是「乱序数据要等多久才触发窗口」的问题，水位线延迟（允许的乱序量）是正确性与延迟之间的权衡。

```text
水位线要点：
1. 定义 —— 事件时间进度标记，声明更早的数据已到齐
2. 作用 —— 驱动事件时间窗口触发，处理乱序
3. 延迟 —— 水位线 = 最大事件时间 - 允许乱序量
4. 权衡 —— 延迟大则正确性高但输出慢，延迟小则反之
```

```sql
-- 水位线延迟 5 秒，窗口在事件时间 + 5 秒后才关闭
CREATE TABLE orders (
    order_id   BIGINT,
    amount     DECIMAL(10, 2),
    event_time TIMESTAMP(3),
    WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND
) WITH (
    'connector' = 'kafka',
    'topic' = 'orders',
    'properties.bootstrap.servers' = 'localhost:9092',
    'format' = 'json'
);
```

## 检查点

检查点（Checkpoint）是 Flink 的容错机制：周期性把算子状态和消费位点做一致性快照存到外部存储，故障后从最近一次检查点恢复，实现「不丢数据」的精确一次语义。检查点基于 Chandy-Lamport 分布式快照算法，靠 barrier（屏障）在流中传播，对齐后做快照。检查点间隔、模式（精确一次/至少一次）、超时等参数直接影响作业的稳定性与性能。

```text
检查点要点：
1. 作用 —— 一致性快照，故障后恢复，保证不丢数据
2. 算法 —— Chandy-Lamport 快照，barrier 对齐
3. 存储 —— 外部存储（HDFS/S3），可增量
4. 语义 —— 精确一次（默认）/ 至少一次（更快）
```

```yaml
# flink-conf.yaml 检查点相关配置
execution.checkpointing.interval: 60s
execution.checkpointing.mode: EXACTLY_ONCE
execution.checkpointing.timeout: 10min
execution.checkpointing.max-concurrent-checkpoints: 1
```

## Kafka-Flink-OLAP 链路

实时数仓的标准数据链路是 Kafka → Flink → OLAP：Kafka 作为消息总线承接 CDC 的变更流（传输层），Flink 作为计算引擎做分层加工（计算层），OLAP 引擎（ClickHouse、Doris、StarRocks 等）作为查询层对外提供亚秒级即席查询。这条链路分工明确——Kafka 负责缓冲与解耦，Flink 负责流式计算，OLAP 负责高性能查询，三者组合构成实时数仓的骨架。

```text
Kafka → Flink → OLAP 分工：
1. Kafka —— 消息总线，缓冲、解耦、可回放
2. Flink —— 流式计算，分层加工、窗口聚合、join
3. OLAP —— 亚秒级即席查询，对外服务大屏/报表
4. 优势 —— 各司其职，水平扩展，链路可回放可修复
```

```sql
-- Flink 消费 Kafka 加工后写入 OLAP（StarRocks）
CREATE TABLE dws_orders (
    user_id BIGINT,
    total   DECIMAL(10, 2),
    PRIMARY KEY (user_id) NOT ENFORCED
) WITH (
    'connector' = 'starrocks',
    'jdbc-url' = 'jdbc:mysql://fe:9030',
    'load-url' = 'fe:8030',
    'database-name' = 'dws',
    'table-name' = 'orders'
);

INSERT INTO dws_orders
SELECT user_id, SUM(amount) FROM orders GROUP BY user_id;
```

## 实时 ODS DWD DWS ADS 分层

实时数仓沿用离线数仓的分层思想，但每一层都是「实时流转」的流/动态表：ODS 层是原始明细（贴近源系统，保留最细粒度）；DWD 层做清洗、标准化、维表关联，形成明细宽表；DWS 层做轻度汇总（按主题聚合的公共汇总层）；ADS 层面向应用（大屏、报表的最终指标）。分层让加工解耦、口径统一、可复用，是实时数仓的工程规范。

```text
实时数仓四层：
1. ODS —— 原始数据，贴近源系统，保留最细粒度
2. DWD —— 清洗、标准化、维表关联，形成明细宽表
3. DWS —— 主题汇总，公共指标层，供多应用复用
4. ADS —— 面向应用，大屏/报表的最终指标
```

```sql
-- DWD：订单明细关联用户维表，形成宽表
INSERT INTO dwd_orders
SELECT o.order_id, o.user_id, o.amount, u.city
FROM ods_orders o
LEFT JOIN dim_users FOR SYSTEM_TIME AS OF o.event_time AS u
    ON o.user_id = u.user_id;

-- DWS：按城市汇总订单金额（公共汇总层）
INSERT INTO dws_orders_city
SELECT u.city, SUM(o.amount)
FROM dwd_orders o
GROUP BY TUMBLE(o.event_time, INTERVAL '1' MINUTE), u.city;
```

## 实时维表

维表（Dimension Table）是描述业务实体属性的表（用户、商品、地区等），实时数仓里维表通常是「持续变更」的流（如 CDC 出来的用户表）。实时维表有几种使用方式：广播维表（小维表广播到所有节点）、Temporal Join 维表（版本化维表按事件时间关联）、外存查询维表（Lookup Join 查外部 DB）。维表管理是实时数仓 DWD 层关联的关键，直接影响数据准确性。

```text
实时维表要点：
1. 定义 —— 描述业务实体属性，持续变更（CDC 流）
2. 使用方式 —— 广播 / Temporal Join / Lookup Join
3. 关键 —— 维表更新的时效性影响关联准确性
4. 挑战 —— 维表大、更新频繁时的性能与一致性
```

```sql
-- CDC 维表：用户维表（版本化，带主键和时间）
CREATE TABLE dim_users (
    user_id    BIGINT,
    user_name  STRING,
    city       STRING,
    update_ts  TIMESTAMP(3),
    PRIMARY KEY (user_id) NOT ENFORCED,
    WATERMARK FOR update_ts AS update_ts - INTERVAL '5' SECOND
) WITH (
    'connector' = 'mysql-cdc',
    'hostname' = 'mysql',
    'username' = 'cdc_user',
    'password' = 'password',
    'database-name' = 'shop',
    'table-name' = 'users'
);
```

## 广播维表

广播维表（Broadcast Dimension）是把「小维表」广播到作业的所有并行实例，每个实例本地存一份完整维表，join 时无需跨节点传输。它适合维表小（几十万行以内）、更新不频繁的场景，如地区表、渠道表、配置表。Flink 用 Broadcast State 实现：把维表作为广播流，与主数据流通过 connect 关联。优点是零网络开销、低延迟，缺点是维表太大时内存放不下。

```text
广播维表要点：
1. 适用 —— 维表小、更新不频繁（地区/渠道/配置表）
2. 原理 —— Broadcast State，维表广播到所有实例
3. 优点 —— 零网络开销、低延迟、本地 join
4. 限制 —— 维表太大内存放不下，需评估
```

```java
// 广播维表 join：小维表广播，主数据流本地关联
MapStateDescriptor<String, String> desc =
    new MapStateDescriptor<>("dim", String.class, String.class);
BroadcastStream<String> dimBroadcast = dimStream.broadcast(desc);

orderStream.connect(dimBroadcast)
    .process(new BroadcastProcessFunction<Order, String, String>() {
        @Override
        public void processElement(Order o, ReadOnlyContext ctx,
                                   Collector<String> out) throws Exception {
            String city = ctx.getBroadcastState(desc).get(o.getRegion());
            out.collect(o.getOrderId() + " -> " + city);
        }
        @Override
        public void processBroadcastElement(String dim, Context ctx,
                                            Collector<String> out) throws Exception {
            ctx.getBroadcastState(desc).put(dim.split(",")[0], dim.split(",")[1]);
        }
    });
```

## Temporal Join

Temporal Join（时态连接）在实时数仓里用于「把明细流与版本化维表按事件时间关联」，取事件发生时刻的维表历史版本。它是实时数仓 DWD 层维表关联的标准手段——订单流按订单发生时间关联「当时的」商品信息，而不是现在的商品信息，保证历史正确。维表必须是版本表（CDC 流天然具备主键 + 时间属性），语法用 `FOR SYSTEM_TIME AS OF`。

```text
Temporal Join 要点：
1. 作用 —— 明细流按事件时间关联维表历史版本
2. 维表要求 —— 版本表（主键 + 时间属性，CDC 流天然满足）
3. 价值 —— 还原历史时点的维表状态，保证历史正确
4. 语法 —— FOR SYSTEM_TIME AS OF event_time
```

```sql
-- 订单流 Temporal Join 用户维表，取下单时的用户属性
SELECT
    o.order_id,
    o.event_time,
    u.user_name,
    u.city
FROM ods_orders o
LEFT JOIN dim_users FOR SYSTEM_TIME AS OF o.event_time AS u
    ON o.user_id = u.user_id;
```

## 应用场景实战

### 场景一：实时订单大屏

```text
目标：大屏实时展示每分钟的订单量、销售额，秒级刷新
链路：订单 CDC → Kafka → Flink（窗口聚合）→ Doris → 大屏
```

```sql
-- Flink SQL：每分钟订单量与销售额，写入 Doris
CREATE TABLE dws_order_stats (
    window_start TIMESTAMP(3),
    order_cnt    BIGINT,
    sales_amount DECIMAL(12, 2),
    PRIMARY KEY (window_start) NOT ENFORCED
) WITH (
    'connector' = 'doris',
    'fenodes' = 'fe:8030',
    'table.identifier' = 'dws.order_stats',
    'sink.properties.format' = 'json'
);

INSERT INTO dws_order_stats
SELECT
    TUMBLE_START(event_time, INTERVAL '1' MINUTE) AS window_start,
    COUNT(*) AS order_cnt,
    SUM(amount) AS sales_amount
FROM ods_orders
GROUP BY TUMBLE(event_time, INTERVAL '1' MINUTE);
```

### 场景二：实时用户画像宽表

```text
目标：实时构建用户维表关联的订单宽表，供实时运营查询
链路：订单流 + 用户 CDC 维表 → Temporal Join → DWD 宽表
```

```sql
-- DWD 宽表：订单关联用户维表（Temporal Join 历史正确）
CREATE TABLE dwd_order_user (

    'properties.bootstrap.servers' = 'localhost:9092',
    'format' = 'json'

SELECT
    o.order_id, o.user_id, o.amount, u.user_name, u.city, o.event_time

    ON o.user_id = u.user_id;
```

## 最佳实践与踩坑记录

### 最佳实践

1. 业务口径统计一律用事件时间，处理时间只用于监控等非业务场景
2. 水位线延迟按业务可接受乱序设置（通常 5~60 秒），不要过大过小
3. 检查点间隔在「恢复速度」和「性能开销」之间权衡，通常 1~5 分钟
4. 维表关联优先用 Temporal Join 还原历史，小维表用广播维表省网络
5. ODS 层保留最细粒度原始数据，为下游回放和重算留余地
6. DWS 层做公共汇总、多应用复用，避免每个应用重复聚合
7. 链路 Kafka 保留足够 retention，出错后能回放重算

### 踩坑记录

```text
坑 1：窗口用水位线但没有设置乱序延迟
结论：迟到的数据被丢弃，窗口统计偏小。
原因：水位线延迟为 0，晚到的事件落在窗口关闭之后。
解法：设置合理的乱序延迟，并配置 side output 兜底迟到数据。

坑 2：状态无限增长导致 OOM
结论：作业运行一段时间后内存耗尽崩溃。
原因：join/聚合状态没有清理，或用无界窗口累积状态。
解法：用有界窗口、设状态 TTL、及时清理过期状态。

坑 3：维表用 Lookup Join 查外部库导致维表被打爆
结论：外部维表 QPS 飙升，拖垮数据库。
原因：每条流记录都实时查询外部维表。
解法：小维表广播，大维表用 Temporal Join 或加缓存。

坑 4：检查点间隔过长导致恢复慢、丢失多
结论：故障后恢复时间长，回退数据多。
原因：检查点间隔过大，快照之间状态变化多。
解法：调小检查点间隔，并配置增量检查点。

坑 5：分层不清晰导致重复计算、口径混乱
结论：每个应用各自聚合，指标口径不一致。
原因：没有按 ODS/DWD/DWS/ADS 分层，公共指标没沉淀。
解法：严格分层，DWS 沉淀公共汇总，ADS 面向应用。

坑 6：事件时间与处理时间混用导致统计错误
结论：同一指标不同作业算出来结果不一致。
原因：有的用事件时间、有的用处理时间，口径不统一。
解法：业务指标统一事件时间，规范时间语义。
```
