## 概述

分布式理论是理解所有大数据系统（HBase、Kafka、Redis Cluster、TiDB、CockroachDB）的基石。核心问题：多台机器组成一个系统时，如何在「一致性（数据一致）」「可用性（始终能响应）」「分区容错（网络分区时仍工作）」三者间取舍。CAP 定理、PACELC 扩展、一致性模型（强一致/最终一致/因果一致）是回答这个问题的理论框架，复制和分片是落地的手段。

```text
分布式系统的根本矛盾：
数据分布在多台机器上，网络可能分区、机器可能故障
→ 无法同时保证「强一致 + 高可用 + 分区容错」
→ 必须按业务场景做取舍
```

## CAP 定理

CAP 定理（Brewer 2000，Gilbert/Lynch 2002 证明）指出：分布式系统无法同时满足「一致性（Consistency）、可用性（Availability）、分区容错（Partition Tolerance）」三者，最多只能同时满足两个。由于网络分区（P）在实践中不可避免，系统必须在 C 和 A 之间取舍：选 CP（分区时牺牲可用性保一致，如 HBase/ZooKeeper）或选 AP（分区时牺牲一致性保可用，如 Cassandra/Dynamo）。

```text
CAP 三要素：
1. C 一致性 —— 所有节点同一时刻读到相同数据
2. A 可用性 —— 每个请求都能得到响应（不保证数据最新）
3. P 分区容错 —— 网络分区（节点失联）时系统仍工作
```

```text
CAP 取舍（P 必选，C/A 二选一）：
- CP 系统 —— 分区时拒写保一致：ZooKeeper、HBase、etcd、TiDB
- AP 系统 —— 分区时继续读写、牺牲一致：Cassandra、Dynamo、Eureka
- CA 系统 —— 无分区时才有意义：单机数据库（分布式里不现实）
```

## PACELC

PACELC 是 CAP 的扩展（Abadi 2012）：CAP 只考虑「分区（P）发生时」的取舍，PACELC 补充了「无分区（E，Else）时」也要在「延迟（Latency）vs 一致性（Consistency）」间取舍。即：有分区时选 A 还是 C，无分区时选「低延迟」还是「强一致」。它更贴近工程现实——即使没有网络分区，强一致（同步复制）也有延迟代价。

```text
PACELC 含义：
P（分区时）：A（可用）还是 C（一致）
E（无分区时）：L（低延迟）还是 C（一致）
```

```text
PACELC 分类：
- PC/EC —— 分区时一致、无分区时一致：强一致系统（Spanner、etcd）
- PA/EL —— 分区时可用、无分区时低延迟：最终一致（Cassandra、Dynamo）
- PA/EC —— 分区时可用、无分区时一致：折中（部分 NoSQL）
```

## 一致性模型

一致性模型描述「并发读写下，系统保证什么顺序/可见性」。从强到弱：线性一致（最强，所有操作全局有序）→ 顺序一致 → 因果一致 → 最终一致（最弱，最终收敛但不保证顺序）。越强的一致越难实现、延迟越高，越弱的一致越易扩展。理解一致性模型是「选数据库」和「设计缓存一致性」的前提。

```text
一致性模型（从强到弱）：
1. 线性一致（Linearizability）—— 全局有序，读到自己最近写的值
2. 顺序一致（Sequential）—— 所有操作按某个全局顺序，但不实时
3. 因果一致（Causal）—— 有因果关系的操作有序，无关的可乱序
4. 最终一致（Eventual）—— 最终收敛到一致，中间可能读旧值
```

## 可用性与分区容错

可用性指「系统始终能响应请求」（可能返回旧数据），分区容错指「网络分区（节点失联、脑裂）时系统仍工作」。这两个概念在 CAP 里与一致性冲突：要强一致（C）就得在分区时拒写（牺牲 A）；要可用（A）就得在分区时继续读写（牺牲 C）。工程上「可用性」常用「几个 9」度量（99.99% = 年停机 52 分钟）。

```text
可用性与分区容错要点：
1. 可用性 —— 请求始终有响应（SLA 用几个 9 度量）
2. 分区容错 —— 网络分区时系统仍工作（分布式不可避免）
3. 与一致性冲突 —— 分区时 C 和 A 不可兼得
4. 度量 —— 99.9%（年停机 8.8 小时）、99.99%（52 分钟）、99.999%（5 分钟）
```

## 复制

复制（Replication）是把数据复制到多台机器，是「高可用 + 容错」的基础。复制方式有同步复制（所有副本确认才提交，强一致但慢）和异步复制（主副本确认即返回，快但可能丢）。复制模式有主从（Master-Slave）、多主（Multi-Master）、无主（Leaderless，如 Dynamo 的 Quorum）。复制带来「复制延迟」问题——副本间数据有滞后。

```text
复制要点：
1. 同步复制 —— 所有副本确认才成功，强一致、延迟高
2. 异步复制 —— 主副本确认即成功，快、可能丢数据
3. 模式 —— 主从（MySQL）、多主、无主（Quorum，Cassandra）
4. 问题 —— 复制延迟（副本滞后）、脑裂（双主）
```

## 分片

分片（Sharding/Partition）是把数据按某种规则拆到多台机器，是「水平扩展」的基础。分片方式有哈希分片（按 key 哈希）、范围分片（按 key 范围）、一致性哈希（节点增减只影响相邻节点）。分片解决「单机存不下、写不下」，但引入「跨分片查询/事务」的复杂度。分片与复制正交——每个分片内部再做复制。

```text
分片要点：
1. 哈希分片 —— 按 key 哈希取模，均匀但范围查询难
2. 范围分片 —— 按 key 范围，范围查询友好但易热点
3. 一致性哈希 —— 节点增减只影响相邻，Dynamo/Cassandra 用
4. 挑战 —— 跨分片事务、数据倾斜、再平衡
```

```text
分片 + 复制（正交组合）：
数据先按 key 分片（水平扩展），每个分片再复制多副本（高可用）
如：Redis Cluster 16384 槽分片 + 主从复制
```

## Strong Consistency 强一致

强一致（严格说「线性一致」）指「所有读写操作表现得像在单机顺序执行」：写操作完成后，所有后续读（任意节点）都能读到新值。它让分布式系统「看起来像单机」，但代价是同步复制（写要等所有副本）、分区时不可用。实现手段有 Raft/Paxos 共识、同步复制、分布式事务（2PC）。

```text
强一致要点：
1. 语义 —— 像单机一样，写后读一定读到新值
2. 代价 —— 同步复制、分区时牺牲可用性
3. 实现 —— Raft/Paxos、同步复制、2PC
4. 适用 —— 账户余额、库存、元数据（ZooKeeper/etcd）
```

## Eventual Consistency 最终一致

最终一致指「系统最终会收敛到一致状态，但中间可能读到旧值」——写入后，副本异步同步，经过一段时间所有副本一致。它换来了高可用和高性能（异步复制、分区时可读写），代价是「读可能读到旧数据」。实现手段有异步复制、Quorum 读写（R+W>N）、反熵（Gossip 传播）。

```text
最终一致要点：
1. 语义 —— 最终收敛一致，中间可能读旧值
2. 代价 —— 读可能不一致（要处理冲突）
3. 实现 —— 异步复制、Quorum、Gossip
4. 适用 —— 点赞数、浏览量、社交 Feed（容忍短暂不一致）
```

```text
Quorum 读写（Dynamo）：
N = 副本数，W = 写确认数，R = 读确认数
R + W > N 保证读能读到最新写（大多数场景）
如 N=3, W=2, R=2：写 2 副本成功、读 2 副本，必读到新值
```

## Causal Consistency 因果一致

因果一致是「介于强一致和最终一致之间」的一致性：有因果关系的操作（如「回复」依赖「帖子」）保持顺序，无因果关系的操作可以乱序。它比最终一致更强（保证因果顺序）、比强一致更弱（不保证全局顺序），是「既要一定的一致性、又要性能」的折中。实现用向量时钟、Lamport 时钟等逻辑时钟。

```text
因果一致要点：
1. 语义 —— 有因果关系的操作有序，无关的可乱序
2. 代价 —— 比强一致便宜，比最终一致更一致
3. 实现 —— 向量时钟、Lamport 时钟
4. 适用 —— 社交评论、协作编辑、聊天（因果相关的操作）
```

## 应用场景实战

### 场景一：选型——账户系统 vs 点赞系统

```text
账户余额（要强一致）：
- 选 CP（如 TiDB、MySQL 主从同步），保证余额不错
- 同步复制 + 事务，分区时拒写保一致

点赞数（可最终一致）：
- 选 AP（如 Redis + 异步落库、Cassandra），容忍短暂不准
- 异步复制，分区时继续服务，最终收敛
```

### 场景二：缓存一致性设计

```text
数据库 + 缓存的一致性（经典难题）：
- 强一致：更新 DB 后失效缓存，读时回源（Cache Aside）
- 最终一致：异步更新缓存，容忍短暂不一致
- 避免：先删缓存再更新 DB（并发下会读到旧值写回缓存）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先判断业务「能不能容忍短暂不一致」，再选一致性模型
2. 账户/库存/元数据要强一致（CP），点赞/浏览/Feed 可最终一致（AP）
3. 用 PACELC 思维：分区时选 A/C，无分区时也要权衡延迟/一致
4. 复制用「同步复制保一致、异步复制保性能」，按业务选
5. 分片避免热点（哈希分片 + 热点 key 单独处理）

### 踩坑记录

```text
坑 1：把 CAP 理解成「三选二」而非「P 必选 C/A 二选一」
结论：以为能同时要 C 和 A（不要 P）。
原因：网络分区不可避免，P 必须选，只能在 C 和 A 间取舍。
解法：默认 P 必选，聚焦「分区时选 C 还是 A」。

坑 2：强一致系统里忽略了同步复制的延迟
结论：写性能差，超时频繁。
原因：同步复制要等所有副本，跨机房延迟高。
解法：权衡「同步写核心副本 + 异步写其他」，或用半同步。

坑 3：最终一致系统里没处理冲突
结论：并发写冲突导致数据错乱。
原因：最终一致允许并发写，不处理冲突会覆盖。
解法：用版本号/向量时钟检测冲突，业务上做合并或 last-write-wins。

坑 4：分片键选错导致热点
结论：某分片数据量/请求量远超其他，单点瓶颈。
原因：分片键分布不均（如用时间戳分片，最新数据都进一个分片）。
解法：选高基数、分布均匀的分片键，热点 key 加盐或单独处理。

坑 5：混淆「复制」和「分片」
结论：把两者当一回事，扩展和容错策略混乱。
原因：复制是「多副本（容错）」，分片是「拆数据（扩展）」，正交。
解法：明确「先分片扩容量，再复制保高可用」，两者独立设计。
```
