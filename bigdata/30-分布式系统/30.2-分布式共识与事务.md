## 概述

分布式共识解决「多台机器就某个值达成一致」的问题，分布式事务解决「跨多个节点/服务的操作要么全成功要么全失败」的问题。共识算法（Raft/Paxos）是「复制状态机」的基础，支撑 ZooKeeper/etcd 这类协调服务；分布式事务（2PC/3PC/TCC/Saga）是「跨服务数据一致性」的手段。这两者是构建可靠分布式系统（微服务、分布式数据库）的核心。

```text
两类核心问题：
1. 共识（Consensus）—— 多个节点就「谁是 leader」「某个值是什么」达成一致
2. 事务（Transaction）—— 跨多个节点/服务的操作，原子提交或回滚
```

## Leader Election 选举

Leader Election（领导者选举）是「从一组节点中选出一个 leader」的问题，是共识的简化形式。Leader 负责协调（写请求路由到 leader、元数据变更由 leader 决定），避免「多主冲突」。实现有基于 ZooKeeper 的临时节点 + 顺序节点、Raft 的投票选举、etcd 的租约 + 选举。选举的难点是「脑裂」（网络分区时选出了两个 leader），需要 fencing 机制防护。

```text
Leader 选举要点：
1. 目的 —— 选出一个协调者，避免多主冲突
2. 实现 —— ZooKeeper 临时顺序节点、Raft 投票、etcd 租约
3. 难点 —— 脑裂（分区时双 leader），需 fencing 防护
4. 应用 —— Kafka Controller、HDFS NameNode、etcd leader
```

## Consensus 共识

共识（Consensus）是「一组节点就某个值达成一致」的分布式基础问题：即使有节点故障、网络分区，所有正常节点最终都同意同一个值。它是「复制状态机」的核心——通过共识复制日志，让多个副本保持一致状态。经典算法有 Paxos（理论基石）和 Raft（工程友好）。共识保证「安全性（不产生冲突的值）+ 活性（最终能达成一致）」。

```text
共识要点：
1. 问题 —— 多节点就某个值达成一致，容忍故障
2. 用途 —— 复制状态机（日志复制）、Leader 选举
3. 算法 —— Paxos（理论）、Raft（工程）
4. 保证 —— 安全性（不冲突）+ 活性（最终达成）
```

## Raft

Raft 是「工程友好」的共识算法，把共识拆成三个子问题：Leader 选举、日志复制、安全性。它用「强 leader」简化——所有写经 leader，leader 把日志复制到多数派（过半节点）确认后提交。Raft 的可理解性来自「分解问题 + 明确的任期（term）和日志索引」，是 etcd、TiKV、CockroachDB 等系统的共识实现。

```text
Raft 核心机制：
1. Leader 选举 —— 任期（term）+ 随机超时投票，多数派当选
2. 日志复制 —— leader 收到写请求，复制日志到 follower，多数派确认后提交
3. 安全性 —— 日志匹配性质（选举时选日志最新的节点当 leader）
```

```text
Raft 三态：
Follower（跟随者）→ 超时没收到心跳 → Candidate（候选，发起投票）
→ 获得多数票 → Leader（领导，处理写 + 发心跳）
```

```text
Raft 日志复制流程：
1. Client 写请求发给 leader
2. leader 追加日志到本地，并行复制给 follower
3. 多数派（> N/2）确认后，leader 提交，通知 follower 提交
4. 提交后对客户端可见，返回成功
```

## Paxos

Paxos 是共识算法的理论基石（Lamport 1990），用「两阶段」达成一致：Prepare/Promise 阶段（提议者发提案号，接受者承诺不接受更小号），Accept/Accepted 阶段（提议者发值，接受者接受）。它保证「只要多数派存活，最终达成一致」，但难理解、难实现，工程上多被 Raft 替代。Multi-Paxos（一次选举 leader 后多轮共识）是 Paxos 的实用化。

```text
Paxos 要点：
1. 两阶段 —— Prepare（提案号）+ Accept（值）
2. 多数派 —— 过半节点确认即可达成一致
3. 保证 —— 安全性（不冲突）+ 活性（最终一致）
4. 演进 —— Multi-Paxos（选 leader 后多轮）、Raft（工程简化）
```

```text
Paxos 两阶段（单值共识）：
Phase 1: Proposer 发 Prepare(n)，Acceptor 承诺不接受 < n 的提案
Phase 2: Proposer 发 Accept(n, v)，Acceptor 接受（多数派即达成）
```

## ZooKeeper

ZooKeeper 是经典的分布式协调服务，提供「文件系统式的树形命名空间 + 临时节点 + 顺序节点 + Watch 通知」。它用 ZAB 协议（类 Paxos）保证「顺序一致 + 原子广播」，是 Kafka（Controller/元数据）、HBase（Region 协调）、Hadoop（HA）的协调底座。ZK 提供的是「协调原语」（锁、选举、配置、命名），而不是存储。

```text
ZooKeeper 要点：
1. 数据模型 —— 树形命名空间（znode），类似文件系统
2. 一致性 —— ZAB 协议（顺序一致 + 原子广播）
3. 原语 —— 临时节点（会话）、顺序节点（编号）、Watch（通知）
4. 应用 —— 分布式锁、Leader 选举、配置中心、命名服务
```

```text
ZooKeeper 常用原语：
- 分布式锁：创建临时顺序节点，序号最小的持锁
- Leader 选举：创建临时顺序节点，序号最小的当 leader
- 配置管理：Watch 监听配置节点变化
- 服务发现：服务注册为临时节点，挂了自动消失
```

## etcd

etcd 是「用 Raft 实现」的分布式键值存储，是 Kubernetes 的元数据后端（存 Pod、Service、ConfigMap 等）。它提供「强一致的 KV + 租约（lease）+ Watch + 事务（Txn）」，比 ZooKeeper 更现代（Raft 更易理解、gRPC 接口、MVCC 版本）。etcd 的核心价值是「强一致的分布式键值」，支撑服务发现、配置、分布式锁。

```text
etcd 要点：
1. 一致性 —— Raft 共识，强一致 KV
2. 数据模型 —— KV + MVCC 版本 + 租约
3. 能力 —— Watch、事务（Txn）、租约、选举
4. 应用 —— K8s 元数据、服务发现、分布式锁、配置
```

```text
etcd 分布式锁（租约 + 事务）：
1. 客户端创建租约，用「key + 租约」原子抢占锁
2. 抢到锁的客户端续租（keepalive）
3. 锁释放或租约过期（客户端挂了）→ 锁自动释放
```

## 2PC 两阶段提交

2PC（Two-Phase Commit）是「跨节点原子提交」的经典协议：协调者（Coordinator）发起，阶段一（Prepare）询问所有参与者「能否提交」，阶段二（Commit/Rollback）根据投票结果决定「全部提交或全部回滚」。它保证「原子性」，但「同步阻塞」（参与者锁定资源等协调者）和「协调者单点」是两大痛点，是 XA 事务的实现基础。

```text
2PC 流程：
阶段一（准备）：协调者发 prepare，参与者锁资源、写 undo/redo 日志、投票
阶段二（提交）：全 yes → 发 commit；有 no → 发 rollback
```

```text
2PC 痛点：
1. 同步阻塞 —— 参与者 prepare 后锁资源等协调者，协调者挂则阻塞
2. 单点故障 —— 协调者挂，参与者不知该提交还是回滚
3. 数据不一致 —— 阶段二部分节点收到 commit、部分没收到
```

## 3PC 三阶段提交

3PC（Three-Phase Commit）是 2PC 的改进，增加「预提交（PreCommit）」阶段：Prepare → PreCommit → DoCommit。它用「参与者超时后自动提交」（而非无限等待）减少阻塞，但仍有「网络分区时数据不一致」的风险（参与者超时提交、但实际应回滚）。3PC 理论上比 2PC 减少阻塞，但引入新的一致性问题，工程上较少使用。

```text
3PC 三阶段：
1. CanCommit —— 协调者问能否提交
2. PreCommit —— 协调者发预提交，参与者准备就绪
3. DoCommit —— 协调者发正式提交，参与者超时可自动提交
```

```text
3PC vs 2PC：
- 2PC：两阶段，参与者阻塞等协调者，协调者挂则卡死
- 3PC：三阶段，参与者超时自动提交，减少阻塞
- 但 3PC 有「网络分区时误提交」风险，工程少用
```

## TCC 补偿事务

TCC（Try-Confirm-Cancel）是「补偿型」分布式事务：Try 阶段预留资源（如冻结库存），Confirm 阶段确认提交（真正扣减），Cancel 阶段补偿回滚（释放冻结）。它不用锁资源（Try 只预留），相比 2PC 减少阻塞，是「柔性事务」的代表，适合「跨服务、可补偿」的业务（如下单扣库存）。代价是「业务侵入」（要写 Try/Confirm/Cancel 三个逻辑）。

```text
TCC 三阶段：
1. Try —— 预留资源（冻结库存、预占额度）
2. Confirm —— 确认提交（真正扣减、完成业务）
3. Cancel —— 补偿回滚（释放预留、撤销业务）
```

```text
TCC 特点：
- 不锁资源（Try 只预留），减少阻塞
- 业务侵入（要写三套逻辑）
- 适用：下单扣库存、转账、跨服务资金操作
```

## Saga 事务

Saga 是「长事务」的补偿方案：把一个长事务拆成多个本地事务（T1, T2, ..., Tn），每个本地事务有对应的补偿操作（C1, C2, ..., Cn），某步失败则逆序执行补偿。它适合「长时间、跨多个服务」的事务（如订单-支付-发货-确认收货），是微服务架构下的主流事务方案。实现分「编排式」（中央协调）和「协同式」（事件驱动）。

```text
Saga 要点：
1. 拆解 —— 长事务拆成多个本地事务（各自提交）
2. 补偿 —— 每步有补偿操作，失败逆序补偿
3. 实现 —— 编排式（中央协调器）、协同式（事件链）
4. 适用 —— 订单、支付、物流等长链路业务
```

```text
Saga 补偿流程（订单为例）：
T1 创建订单 → T2 扣库存 → T3 扣款 → T4 发货
若 T3 扣款失败 → 补偿 C2（加回库存）→ 补偿 C1（取消订单）
```

## Outbox 与事务消息

Outbox（事务发件箱）解决「本地事务 + 发消息」的原子性：在本地事务里「同时写业务表 + 写 outbox 表（待发消息）」，事务提交后，后台进程异步把 outbox 里的消息发给 MQ。它保证「业务和消息要么都成功、要么都失败」，是「可靠消息最终一致」的实现，配合消费者幂等实现跨服务数据一致。

```text
Outbox 要点：
1. 原子性 —— 本地事务里同时写业务 + outbox
2. 异步发送 —— 事务提交后，后台把 outbox 消息发 MQ
3. 幂等消费 —— 消费者按消息 ID 幂等，防重复
4. 保证 —— 业务和消息最终一致（非强一致）
```

```text
Outbox 流程：
本地事务：INSERT 订单 + INSERT outbox（订单消息）
→ 提交事务
→ 后台进程读 outbox → 发 MQ → 标记已发送
→ 消费者幂等处理
```

## 分布式锁与 Fencing Token

分布式锁是「多个进程互斥访问共享资源」的机制，基于 ZooKeeper（临时顺序节点）或 Redis（SETNX + 过期）或 etcd（租约）。Fencing Token（栅栏令牌）是防「锁过期后旧持有者继续写」的机制：锁服务发一个递增的 token，持有者写共享资源时带上 token，资源方拒绝「比当前 token 旧」的写——防止「GC 停顿导致锁过期、旧进程继续写」的脑裂问题。

```text
分布式锁要点：
1. Redis 锁 —— SETNX + 过期时间 + 唯一 value（防误删）
2. ZooKeeper 锁 —— 临时顺序节点 + Watch
3. 问题 —— 锁过期后旧持有者继续写（GC 停顿）
4. Fencing Token —— 递增令牌，资源方拒绝旧 token 的写
```

```python
# Redis 分布式锁（带唯一 token 防误删）
import redis, uuid, time

def acquire_lock(r, key, ttl=10):
    token = uuid.uuid4().hex
    if r.set(key, token, nx=True, ex=ttl):
        return token
    return None

def release_lock(r, key, token):
    # Lua 脚本保证「比较 value + 删除」原子性，防误删别人的锁
    lua = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end"
    return r.eval(lua, 1, key, token)
```

## 应用场景实战

### 场景一：跨服务下单（TCC/Saga 选型）

```text
下单流程（订单-库存-账户三服务）：
- 强一致要求、链路短 → TCC（冻结库存/账户，确认或补偿）
- 长链路、可异步 → Saga（各步本地事务 + 逆序补偿）
- 消息可靠性 → Outbox（本地事务 + 事务消息 + 幂等消费）
```

### 场景二：用 etcd 做服务注册与 Leader 选举

```text
etcd 做服务发现 + 选举：
- 服务启动：写 key（/services/order/instance1）带租约，续租保活
- 服务发现：Watch /services/ 前缀，感知上下线
- Leader 选举：抢 key（带租约），抢到者续租当 leader
```

## 最佳实践与踩坑记录

### 最佳实践

1. 共识选 Raft（易理解、工程成熟），别手写 Paxos
2. 分布式协调用 etcd（现代）或 ZooKeeper（生态成熟），别自研
3. 短事务强一致用 2PC/XA，长事务用 Saga/TCC（柔性）
4. 跨服务消息用 Outbox + 幂等消费，保证最终一致
5. 分布式锁一定配 Fencing Token，防锁过期脑裂

### 踩坑记录

```text
坑 1：Redis 锁释放误删了别人的锁
结论：锁过期后，新持有者的锁被旧持有者删掉。
原因：释放时只按 key 删，没校验 value，旧进程过期后删了新进程的锁。
解法：释放时用 Lua 脚本「比较 value + 删除」原子操作。

坑 2：2PC 协调者挂导致参与者阻塞
结论：参与者 prepare 后锁资源等协调者，协调者挂了就卡死。
原因：2PC 同步阻塞，协调者单点。
解法：协调者做高可用 + 超时自动决策，或改用 TCC/Saga 柔性事务。

坑 3：Saga 补偿操作没实现幂等
结论：补偿重试导致重复补偿，数据错乱。
原因：补偿操作本身不幂等，重试时重复执行。
解法：补偿操作设计成幂等（按业务 ID 去重）。

坑 4：Outbox 消息发了但没幂等消费
结论：消息重复消费，数据重复。
原因：后台发送 + 消费者重试导致重复投递，消费者没去重。
解法：消费者按消息 ID 幂等，配合去重表。

坑 5：分布式锁没配 Fencing Token
结论：GC 停顿导致锁过期，旧持有者继续写共享资源，脑裂。
原因：锁过期后旧进程不知情继续写。
解法：锁服务发递增 token，资源方拒绝旧 token 的写。
```
