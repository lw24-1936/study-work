## 概述

数据血缘（Data Lineage）记录数据从源头到消费终点的完整流动路径，回答「这个数据从哪里来、经过了哪些加工、最终流向了哪里」。它按粒度分为表级、列级、任务级与管道级，是数据治理中影响分析、根因定位、合规审计与口径追溯的核心基础设施。没有血缘，数仓中的表就会变成一座座彼此孤立的「黑箱」，一旦上游出错，下游往往只能靠人工猜测排查。

```text
数据血缘核心：
- 粒度：表级（表→表）、列级（字段→字段）、任务级（Job 依赖）、管道级（端到端链路）
- 价值：影响分析、根因定位、口径追溯、合规审计、冷数据识别
- 采集：SQL 解析、调度依赖、运行日志、手工登记
- 代表工具：Apache Atlas、DataHub、OpenLineage、Spline
血缘 = 数据流动的「地图」，治理的「导航」
```

## 表级血缘

表级血缘描述表与表之间的产出依赖关系，例如「订单明细表由订单表 JOIN 用户表生成」，是血缘体系中最基础、最易采集的粒度。它通常通过解析 ETL 任务中的 SQL（INSERT INTO ... SELECT FROM ...）自动提取源表与目标表，或在调度系统中读取任务间的输入输出表声明得到。表级血缘足以支撑「改了这张表会影响哪些表」的粗粒度影响分析。

```text
表级血缘要点：
- 表达：源表（上游）→ 目标表（下游）的有向边
- 采集：SQL 解析（源/目标表）、任务输入输出声明、手工登记
- 存储：图结构，表为节点、加工关系为边
- 用途：粗粒度影响分析、资产盘点、热度与冷数据识别
```

```sql
-- 表级血缘存储：以边表记录上下游关系
CREATE TABLE IF NOT EXISTS lineage_table_edge (
    source_table VARCHAR(200),
    target_table VARCHAR(200),
    task_name    VARCHAR(200),
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (source_table, target_table, task_name)
);

-- 插入一条加工关系：dwd_order_detail 由 ods_order 与 ods_user 生成
INSERT INTO lineage_table_edge (source_table, target_table, task_name) VALUES
('ods_order',  'dwd_order_detail', 'etl_dwd_order'),
('ods_user',   'dwd_order_detail', 'etl_dwd_order'),
('dwd_order_detail', 'ads_gmv_daily', 'etl_ads_gmv');
```

## 列级血缘

列级血缘深入到字段粒度，描述目标字段由哪些源字段计算而来，例如「订单表.实付金额 = 源表.单价 × 源表.数量 - 源表.优惠」。它是精确影响分析与口径追溯的基础：当某个源字段定义变更或质量异常时，可以精确定位到下游受影响的字段，避免表级血缘「一刀切」带来的过度告警。列级血缘采集难度高于表级，需要解析 SQL 表达式中的字段映射，甚至跨越多层函数与聚合。

```text
列级血缘要点：
- 表达：源字段（表.列）→ 目标字段（表.列）的映射
- 采集：SQL AST 解析字段级映射、手工维护复杂口径
- 挑战：表达式、聚合、CASE WHEN、跨表 JOIN 的字段追踪
- 用途：精确影响分析、指标口径追溯、敏感字段流向审计
```

```sql
-- 列级血缘存储与查询示例
CREATE TABLE IF NOT EXISTS lineage_column_edge (
    source_table  VARCHAR(200), source_column VARCHAR(200),
    target_table  VARCHAR(200), target_column VARCHAR(200),
    task_name     VARCHAR(200),
    PRIMARY KEY (source_table, source_column, target_table, target_column)
);

-- 查询：目标字段 amount 依赖哪些源字段（口径追溯）
SELECT source_table, source_column
FROM lineage_column_edge
WHERE target_table = 'dwd_order_detail' AND target_column = 'amount';
```

## 任务血缘

任务血缘描述调度系统中任务（Job）之间的依赖关系，例如「日报任务依赖小时任务全部完成、指标任务依赖明细任务成功」。它回答的是「这个任务依赖哪些上游任务、又被哪些下游任务依赖」，是调度编排、故障影响范围判断与重跑顺序决策的依据。任务血缘通常由调度系统（Airflow、DolphinScheduler、Azkaban）的任务依赖配置直接导出。

```text
任务血缘要点：
- 表达：上游任务 → 下游任务的有向无环图（DAG）
- 采集：调度系统的依赖配置、任务运行日志
- 用途：调度编排、故障定位、重跑范围判断、关键路径分析
- 与表级血缘关系：任务读取/产出表，任务血缘可关联到表级血缘
```

```yaml
# 调度系统 DAG 依赖定义（示意），直接构成任务血缘
tasks:
  - id: sync_ods_order
    name: 同步订单源数据
    upstream: []
  - id: etl_dwd_order
    name: 清洗订单明细
    upstream: [sync_ods_order]
  - id: etl_ads_gmv
    name: 计算 GMV 指标
    upstream: [etl_dwd_order]
  - id: report_daily
    name: 生成日报
    upstream: [etl_ads_gmv]
```

## 管道血缘

管道血缘是面向「数据产品/业务指标」的端到端全链路血缘，把从业务系统源表、数仓各层加工、到最终报表/指标/API 的整条管道串联起来。它跨越表级与任务级，回答「某个业务报表最终由哪些源系统数据经过哪些环节生成」。管道血缘是数据可信度与合规审计的关键：监管要求能完整解释某个数字「从何而来、如何算出」。

```text
管道血缘要点：
- 端到端：源系统 → ODS → DWD → DWS/ADS → 报表/指标
- 跨越粒度：融合表级 + 任务级 + 指标口径
- 用途：指标可信度证明、监管审计、全链路影响评估
- 落地：OpenLineage 等开放标准统一采集，拼接全链路
```

```python
# 用 networkx 构建并遍历管道血缘（端到端链路）
import networkx as nx

G = nx.DiGraph()
# 节点：源系统、数仓各层、报表
G.add_edges_from([
    ("CRM订单源", "ods_order"),
    ("ERP库存源", "ods_inventory"),
    ("ods_order", "dwd_order_detail"),
    ("ods_inventory", "dwd_order_detail"),
    ("dwd_order_detail", "ads_gmv_daily"),
    ("ads_gmv_daily", "GMV日报报表"),
])

# 端到端追溯：GMV 日报的完整上游链路
for src in ["CRM订单源", "ERP库存源"]:
    paths = list(nx.all_simple_paths(G, src, "GMV日报报表"))
    for p in paths:
        print(" -> ".join(p))
```

## 影响分析

影响分析（Impact Analysis）是血缘最重要的消费场景，回答「如果某张表/某个字段/某个任务发生变化或出错，会影响哪些下游」。正向（向前）影响分析沿血缘方向找下游受影响对象，用于变更评估与故障通知；反向（向后）根因分析沿血缘逆方向找上游来源，用于定位数据异常的根本原因。两者是数据治理中「变更可控、故障可溯」的核心能力。

```text
影响分析要点：
- 正向影响分析：节点 → 所有下游（变更评估、告警范围）
- 反向根因分析：节点 ← 所有上游（定位异常来源）
- 实现：图上 BFS/DFS 遍历可达性，或图数据库查询
- 价值：变更风险评估、故障影响面通知、口径追溯
```

```python
import networkx as nx

G = nx.DiGraph()
G.add_edges_from([
    ("ods_order", "dwd_order_detail"),
    ("ods_user",  "dwd_order_detail"),
    ("dwd_order_detail", "ads_gmv_daily"),
    ("dwd_order_detail", "ads_uv_daily"),
    ("ads_gmv_daily", "gmv_report"),
    ("ads_uv_daily",  "uv_report"),
])

def downstream(G, node):
    """正向影响分析：找出 node 的所有下游"""
    return list(nx.descendants(G, node))

def upstream(G, node):
    """反向根因分析：找出 node 的所有上游"""
    return list(nx.ancestors(G, node))

print("ods_order 影响的下游:", downstream(G, "ods_order"))
print("gmv_report 的上游来源:", upstream(G, "gmv_report"))
```

## 应用场景实战

### 场景一：上游字段变更的影响评估

数据团队计划修改订单源表的字段类型，需要评估会影响多少下游表与报表。用图遍历实现正向影响分析，输出受影响的全部下游节点，作为变更评审与通知的依据。

```python
import networkx as nx

G = nx.DiGraph()
G.add_edges_from([
    ("ods_order.order_id", "dwd_order_detail.order_id"),
    ("ods_order.order_id", "ads_gmv_daily.order_id"),
    ("dwd_order_detail.amount", "ads_gmv_daily.gmv"),
    ("ads_gmv_daily.gmv", "gmv_report.gmv"),
])

changed = "ods_order.order_id"
affected = nx.descendants(G, changed)
print(f"变更节点: {changed}")
print("受影响下游:", sorted(affected))

# 输出变更评审结论
for node in sorted(affected):
    print(f"  -> 需评估: {node}")
```

### 场景二：数据异常的反向根因定位

某日报的 GMV 指标异常，需要沿血缘向上追溯可能的上游来源，快速缩小排查范围。用图遍历做反向根因分析，再结合质量检查定位真正的脏数据源头。

```python
import networkx as nx

G = nx.DiGraph()
G.add_edges_from([
    ("订单源", "ods_order"),
    ("ods_order", "dwd_order_detail"),
    ("支付源", "ods_payment"),
    ("ods_payment", "dwd_order_detail"),
    ("dwd_order_detail", "ads_gmv_daily"),
    ("ads_gmv_daily", "gmv_report"),
])

# 反向根因：GMV 报表异常，向上追溯所有可能来源
suspicious = nx.ancestors(G, "gmv_report")
print("异常节点: gmv_report")
print("候选上游来源:", sorted(suspicious))

# 结合质量规则逐一排查（示意）
for node in sorted(suspicious):
    print(f"检查 {node} 的质量规则与数据量是否正常...")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 采集自动化优先：通过 SQL 解析与调度依赖自动采集血缘，手工登记只作为兜底，避免血缘「有图但过时」。
2. 分层建设粒度：先做表级血缘（易采集、价值立现），再逐步补充列级血缘与管道血缘，不要一步到位求全。
3. 血缘与质量、目录联动：血缘图上的节点关联质量评分与 owner，异常时能一键定位责任人与影响面。
4. 统一图存储：用图数据库或统一血缘模型存储，支持 BFS/DFS 遍历与递归查询，支撑影响分析秒级返回。
5. 变更前必跑影响分析：把「影响分析」纳入表结构变更、任务下线的审批流程，成为硬性门槛。
6. 血缘纳入发布 CI：新增/修改 ETL 任务时自动解析并更新血缘，保证血缘与代码同步演进。
7. 保留历史版本：血缘随时间变化，保留快照才能回答「过去某天数据是怎么算出来的」这类审计问题。

### 踩坑记录

```text
坑 1
结论：血缘图显示有依赖，但实际数据没有流动
原因：血缘来自静态 SQL 解析，而任务运行时有分支/过滤/未执行
解法：结合任务运行日志与「最近产出时间」校验边的活跃性，剔除僵尸依赖

坑 2
结论：列级血缘在跨多层聚合后断裂，追不到源字段
原因：SQL 解析只处理单层 INSERT-SELECT，未穿透嵌套子查询与函数
解法：选用支持 AST 级递归解析的工具，或对关键指标手工维护口径映射

坑 3
结论：影响分析结果「虚大」，一个字段改动告警了所有下游
原因：只做了表级血缘，字段改动本不该影响整张表的全部下游
解法：建设列级血缘，把影响范围精确到字段级，减少过度告警

坑 4
结论：调度系统改版后任务血缘消失或错乱
原因：血缘依赖从旧调度配置导出，迁移时未同步映射
解法：血缘采集与调度系统解耦，用统一任务标识与标准接口（OpenLineage）上报

坑 5
结论：临时表/中间表污染血缘图，导致链路臃肿难以阅读
原因：把不具业务含义的中间表也作为节点纳入展示
解法：对中间表做折叠/隐藏，只保留业务层节点，按需展开查看细节

坑 6
结论：反向根因分析追到源表，但仍找不到具体哪条数据有问题
原因：血缘只回答「哪张表」，未结合质量规则与坏数据明细
解法：血缘定位到表/字段后，联动质量检查结果与分区粒度，缩小到具体行
```
