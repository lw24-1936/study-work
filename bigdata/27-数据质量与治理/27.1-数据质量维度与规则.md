## 概述

数据质量（Data Quality）衡量数据在多大程度上满足其使用目的，通常用一组可度量的「维度」来描述，再通过可执行的「规则」在数据管道每个环节落地检查。维度是抽象定性标准（如准确、完整），规则是把维度转译为可自动校验的断言（如「金额不能为负」）。高质量数据带来可信指标与稳定模型，低质量数据则直接导致「garbage in, garbage out」的分析错误与业务损失。
```text
数据质量体系核心：
- 维度（定性）：Accuracy / Completeness / Consistency / Timeliness / Uniqueness / Validity / Freshness
- 规则（定量可执行）：Null / Range / Uniqueness / Referential / Distribution / Volume / Schema
- 落地方式：规则引擎（Great Expectations、dbt tests、自研）、SLA 门禁、血缘追踪
- 度量输出：规则通过率、坏数据行数、问题根因分类
维度是「要求什么」，规则是「怎么检查」，二者一一映射、可量化
```

## Accuracy 准确性

准确性（Accuracy）指数据值与其所描述的真实世界对象之间的一致程度，即数据「对不对」。它是数据质量最核心也最难的维度，因为真实值常难以自动获取，需依赖权威参考源、对账或人工抽检。准确性规则通常借助主数据、第三方权威数据或业务规则交叉验证，例如身份证号与出生日期是否匹配。
```text
Accuracy 要点：
- 定义：数据值 = 真实值（误差在业务容忍范围内）
- 校验：与权威源对账、业务规则推断、人工抽样审计
- 度量：错误行数 / 总行数，或与基准数据的差异率
```

```sql
-- 准确性：身份证号推导的出生日期与登记日期是否一致
SELECT COUNT(*) AS total,
       SUM(CASE WHEN SUBSTR(id_card, 7, 8) <> birth_date THEN 1 ELSE 0 END) AS mismatch
FROM dim_customer
WHERE id_card IS NOT NULL AND LENGTH(id_card) = 18;
```

## Completeness 完整性

完整性（Completeness）衡量必需字段是否都有值，即数据「全不全」。它既包括字段级空值，也包括记录级信息缺失（例如某天根本没有产生订单）。完整性是最易自动化度量的维度，常通过空值率、缺失记录数来量化，是多数数据质量平台的第一个检查项。
```text
Completeness 要点：
- 定义：非空字段占比 + 应存在记录是否齐全
- 字段级：NULL 计数 / 空字符串 / 默认占位符（0、'N/A'）
- 记录级：按时间粒度比对是否缺天、缺分区
- 度量：完整性 = 非空行数 / 总行数
```

```sql
-- 字段级完整性：关键字段空值率
SELECT COUNT(*) AS total,
       SUM(CASE WHEN customer_id IS NULL THEN 1 ELSE 0 END) AS null_customer,
       SUM(CASE WHEN order_amount IS NULL THEN 1 ELSE 0 END) AS null_amount
FROM fact_order;
```

## Consistency 一致性

一致性（Consistency）指同一数据在系统内部及跨系统之间是否保持一致、不矛盾，即数据「矛不矛盾」。它既包含单表内部的逻辑约束（如订单金额 = 单价 × 数量），也包含跨表、跨系统的一致性（如订单表与用户表口径统一）。不一致常源于多套系统各自维护、ETL 口径漂移或并发更新未同步。
```text
Consistency 要点：
- 单表：字段间逻辑约束（金额=单价×数量、时间先后）
- 跨表：同一实体在多个表取值应一致
- 跨系统：CRM、交易、数仓之间的主数据一致
- 度量：违反约束的行占比、跨系统对账差异
```

```sql
-- 单表一致性：订单金额是否等于单价 × 数量
SELECT COUNT(*) AS total,
       SUM(CASE WHEN ABS(amount - unit_price * quantity) > 0.01
                THEN 1 ELSE 0 END) AS inconsistent_rows
FROM fact_order_detail;
```

## Timeliness 及时性

及时性（Timeliness）指数据在需要的时刻是否可用，即数据「到得及不及时」。它衡量数据从产生到可被使用之间的延迟是否满足业务 SLA，例如实时风控要求秒级、日报要求次日早晨可用。及时性与 Freshness 常被混用：前者侧重「满足使用时间要求」，后者侧重「数据有多新」。
```text
Timeliness 要点：
- 定义：数据可用时刻 ≤ 业务要求时刻
- 关注：任务调度延迟、上游依赖阻塞、传输耗时
- 与 SLA 绑定：实时/准实时/离线有不同时效要求
- 度量：任务完成时刻 vs 约定时刻的延迟分钟数
```

```sql
-- 及时性：任务完成时间是否晚于约定 SLA
SELECT task_name,
       TIMESTAMPDIFF(MINUTE, scheduled_time, actual_finish_time) AS delay_min
FROM task_schedule_log
WHERE TIMESTAMPDIFF(MINUTE, scheduled_time, actual_finish_time) > 0
ORDER BY delay_min DESC;
```

## Uniqueness 唯一性

唯一性（Uniqueness）指同一实体、事件或记录在数据集中不应重复出现，即数据「重不重复」。它要求主键或业务唯一键没有重复值，防止同一笔交易被多次计入、同一用户被重复建档导致指标虚高。唯一性检查通常在主键、业务唯一键（如订单号、用户 ID + 渠道）上执行。
```text
Uniqueness 要点：
- 定义：唯一键列不存在重复值
- 关键：区分主键唯一性与业务唯一键（联合唯一）
- 典型问题：重复下单、幂等失败、多源合并产生重复
- 度量：重复记录数 / 总记录数，重复分组数量
```

```sql
-- 唯一性：检查订单号是否存在重复
SELECT order_id, COUNT(*) AS cnt
FROM fact_order
GROUP BY order_id
HAVING COUNT(*) > 1
ORDER BY cnt DESC
LIMIT 100;
```

## Validity 有效性

有效性（Validity）指数据值是否符合既定的格式、类型与取值范围约束，即数据「合不合规」。它关注数据的结构合法性，例如邮箱是否符合格式、枚举字段是否落在合法值集合、日期是否合法。有效性是最容易用规则自动化执行的维度，多数「规则」本质上都是有效性校验。
```text
Validity 要点：
- 格式：正则匹配（邮箱、手机号、身份证、IP）
- 类型：字段数据类型正确（数字列不含字符串）
- 枚举：取值必须属于合法集合（状态码、币种）
- 范围：数值、日期落在业务允许区间内
```

```sql
-- 有效性：状态字段取值是否合法、邮箱格式是否合规
SELECT COUNT(*) AS total,
       SUM(CASE WHEN status NOT IN ('NEW','PAID','SHIPPED','CLOSED')
                THEN 1 ELSE 0 END) AS invalid_status
FROM dim_customer;
```

## Freshness 新鲜度

新鲜度（Freshness）指数据反映当前现实的程度，即数据「有多新」，通常用数据产生时刻与最近一次更新时刻之间的时间差来衡量。它强调数据的「年龄」而非「是否迟到」，例如一张用户表最后一次更新是一年前，即便历史准确，新鲜度也很差。新鲜度监控常通过对比目标表的最大时间戳与当前时间实现。
```text
Freshness 要点：
- 定义：max(数据时间戳) 与 now() 的差距
- 关注：数据是否「过时」，而非是否「迟到」
- 常见指标：数据年龄（data age）、最后更新时间
- 与 Timeliness 区别：Freshness 看新旧，Timeliness 看是否满足使用时点
```

```sql
-- 新鲜度：表最近更新数据的时间戳距今多久
SELECT 'fact_order' AS table_name,
       MAX(update_time) AS max_update_time,
       TIMESTAMPDIFF(HOUR, MAX(update_time), NOW()) AS age_hours
FROM fact_order;
```

## Null 规则

Null 规则是数据质量中最基础的规则类型，用于约束字段是否允许为空、空值占比是否超阈值。它既包含「必填字段不允许空」的硬性约束，也包含「允许为空但空值率不能超过 X%」的软性监控。在 SQL 中需注意 NULL 的三值逻辑，比较时必须显式使用 IS NULL / IS NOT NULL。
```text
Null 规则要点：
- 必填校验：关键字段（主键、外键、金额）非空
- 空值率阈值：允许为空字段设置占比上限
- 陷阱：NULL 参与 = 比较结果为 UNKNOWN，需用 IS NULL
- 区分：NULL（未知）与空字符串 ''、占位符（0、-1）含义不同
```

```sql
-- Null 规则：关键字段空值检查并断言结果
SELECT 'customer_id' AS column_name,
       SUM(CASE WHEN customer_id IS NULL THEN 1 ELSE 0 END) AS null_cnt,
       CASE WHEN SUM(CASE WHEN customer_id IS NULL THEN 1 ELSE 0 END) > 0
            THEN 'FAIL' ELSE 'PASS' END AS check_result
FROM fact_order;
```

## Range 规则

Range 规则约束数值或日期字段必须落在业务允许的取值区间内，例如「订单金额在 0 到 100 万之间」「用户年龄在 0 到 150 之间」。它属于有效性校验的子集，因使用频率极高而单独成类。Range 规则能快速发现异常值、单位错误与数据污染，是最常用的异常检测手段之一。
```text
Range 规则要点：
- 数值范围：min ≤ value ≤ max（金额、数量、评分）
- 日期范围：不早于业务起始日、不晚于当前日期
- 阈值来源：业务规则、历史分布（如 ±3σ）、法规约束
- 边界：明确开闭区间，避免边界值误报
```

```sql
-- Range 规则：金额与年龄是否越界
SELECT COUNT(*) AS total,
       SUM(CASE WHEN order_amount < 0 OR order_amount > 1000000
                THEN 1 ELSE 0 END) AS amount_out_of_range
FROM fact_order o
JOIN dim_customer c ON o.customer_id = c.customer_id;
```

## Uniqueness 规则

Uniqueness 规则是唯一性维度的可执行落地，明确指定在哪些列（单列或联合列）上不允许出现重复值，并输出重复明细供排查。它与 Null 规则常组合使用：主键既不能为空也不能重复。实现上通常用 GROUP BY + HAVING COUNT(*) > 1 找出重复，再决定去重策略（保留最新、保留最全、合并）。
```text
Uniqueness 规则要点：
- 单列唯一：主键、订单号、手机号等
- 联合唯一：如 (用户, 渠道, 日期) 粒度上唯一
- 输出：重复键值 + 重复次数 + 明细行，便于定位
- 处置：删除重复、幂等去重（ROW_NUMBER 保留一条）
```

```python
import pandas as pd

df = pd.DataFrame({
    "order_id": ["A1", "A2", "A1", "A3", "A2"],
    "amount":   [100, 200, 101, 300, 200],
})
dup = df[df.duplicated(subset=["order_id"], keep=False)]
print("重复记录数:", dup.shape[0])
print(df.drop_duplicates(subset=["order_id"], keep="first"))
```

## Referential 规则

Referential 规则即引用完整性（外键完整性），约束事实表的外键必须能在对应维度表中找到匹配记录，即「引用的对象必须存在」。例如订单表中的 customer_id 必须存在于用户维度表，否则会出现无法关联的孤儿记录（orphan）。它是星型建模与数仓分层中最重要的规则之一，常用 LEFT JOIN 反查 NULL 实现。
```text
Referential 规则要点：
- 事实表外键 → 维度表主键必须命中
- 孤儿记录：LEFT JOIN 后右表键为 NULL 的行
- 常见原因：维度表延迟更新、ETL 顺序错误、脏数据进入
- 处置：补维度、丢弃孤儿、或降级为未知成员（-1 代理键）
```

```sql
-- Referential 规则：订单表外键在用户维度表是否都能命中
SELECT COUNT(*) AS orphan_rows
FROM fact_order o
LEFT JOIN dim_customer c ON o.customer_id = c.customer_id
WHERE c.customer_id IS NULL;
```

## Distribution 规则

Distribution 规则监控字段取值的分布形态，检测分布是否发生异常漂移，例如某品类占比突然从 10% 飙升到 90%、数值分布严重偏离历史基线。它常用于捕获数据倾斜、特征漂移与上游口径变更，是比单点 Range 规则更强的「整体形状」检测手段，可借助直方图、分位数、卡方检验或 JS 散度实现。
```text
Distribution 规则要点：
- 基线对比：当前分布 vs 历史基线/昨日分布
- 检测手段：分位数、直方图差异、PSI / JS 散度、卡方检验
- 典型场景：类别占比漂移、数值均值方差突变
- 价值：发现 Range/Null 无法覆盖的「系统性」变化
```

```python
import numpy as np

def psi(e, a, buckets=10):
    e, a = np.array(e), np.array(a)
    b = np.linspace(min(e.min(), a.min()), max(e.max(), a.max()), buckets + 1)
    ep = np.histogram(e, b)[0] + 1e-4; ap = np.histogram(a, b)[0] + 1e-4
    ep, ap = ep / ep.sum(), ap / ap.sum()
    return float(np.sum((ap - ep) * np.log(ap / ep)))

print("PSI =", round(psi(np.random.normal(100, 10, 1e4), np.random.normal(130, 15, 1e4)), 4))
# PSI > 0.25 通常判为显著漂移
```

## Volume 规则

Volume 规则监控数据量是否落在预期范围，即数据「够不够量」。它既检测数据量暴增（重复、异常写入），也检测数据量骤减（丢数据、上游故障、漏分区）。常见实现是比对当前周期行数与历史同期行数或阈值区间，例如「今日订单量不应低于过去 7 日均值的 50%」，是及时发现管道断流的哨兵。
```text
Volume 规则要点：
- 行数阈值：当前行数 vs 固定上下限
- 同比环比：与昨日、上周同期、移动均值对比
- 检测目标：数据丢失（骤减）、重复/膨胀（暴增）
- 常与分区检查结合：确认关键分区存在且有数据
```

```sql
-- Volume 规则：今日订单量是否低于近 7 日均值的 50%
SELECT dt, cnt,
       AVG(cnt) OVER (ORDER BY dt ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING) AS prev_avg
FROM (SELECT dt, COUNT(*) AS cnt FROM fact_order
      WHERE dt >= CURRENT_DATE - INTERVAL '7' DAY GROUP BY dt) t
ORDER BY dt DESC
LIMIT 1;
```

## Schema 规则

Schema 规则校验表结构与预期元数据是否一致，包括表是否存在、字段是否齐全、字段类型是否正确、是否新增/缺失列、分区结构是否合规。它是数据管道最前置的防线，因为结构一旦漂移（上游改表、加列删列），下游所有消费逻辑都可能静默失败，故常在任务运行前用 Schema 校验先行拦截。
```text
Schema 规则要点：
- 表/字段存在性：预期表与列是否齐全
- 类型校验：字段数据类型与约定一致
- 结构漂移：上游加列、删列、改类型的检测
- 分区合规：分区字段、分区格式是否符合规范
```

```python
import pandas as pd

expected = {"order_id": "object", "amount": "float64", "dt": "datetime64[ns]"}

def validate_schema(df, spec):
    ok = True
    for col, dtype in spec.items():
        if col not in df.columns:
            print(f"缺失列: {col}"); ok = False
        elif str(df[col].dtype) != dtype:
            print(f"类型不符: {col} 期望 {dtype}, 实际 {df[col].dtype}"); ok = False
    return ok

print("Schema 校验通过:", validate_schema(
    pd.DataFrame({"order_id": ["A1"], "amount": [1.5]}), expected))
```

## 应用场景实战

### 场景一：订单表入库质量门禁

数据仓库每日凌晨从业务库同步订单数据，需要在数据落地后、指标计算前执行一组质量规则，全部通过才放行下游任务。用 SQL 将多条规则打包为一次检查，返回每条规则的通过与失败行数。

```sql
WITH checks AS (
  SELECT 'null_customer_id' AS rule,
         SUM(CASE WHEN customer_id IS NULL THEN 1 ELSE 0 END) AS fail_cnt
  FROM fact_order
  UNION ALL
  SELECT 'amount_out_of_range',
         SUM(CASE WHEN amount < 0 OR amount > 1000000 THEN 1 ELSE 0 END)
  FROM fact_order
  UNION ALL
  SELECT 'orphan_customer',
         (SELECT COUNT(*) FROM fact_order o
          LEFT JOIN dim_customer c ON o.customer_id = c.customer_id
          WHERE c.customer_id IS NULL)
)
SELECT rule, fail_cnt,
       CASE WHEN fail_cnt > 0 THEN 'FAIL' ELSE 'PASS' END AS result
FROM checks;
```

### 场景二：用 Python 构建可复用的质量校验框架

当规则数量增多且需跨表复用时，适合用 Python 编写轻量校验框架，将规则声明为断言函数，批量执行并汇总报告，可作为独立的质量审计脚本或集成进 Airflow 任务。

```python
import pandas as pd

def not_null(df, col):
    return df[col].notna().all(), f"{col} 空 {int(df[col].isna().sum())} 行"

def in_range(df, col, lo, hi):
    return df[col].between(lo, hi).all(), f"{col} 越界 {int((~df[col].between(lo, hi)).sum())} 行"

def unique(df, col):
    return df[col].is_unique, f"{col} 重复 {int(df.duplicated(col).sum())} 组"

df = pd.DataFrame({"order_id": ["A1", "A2", "A1"],
                   "amount": [100, -5, 200],
                   "customer_id": ["C1", None, "C3"]})
rules = [("订单号唯一", lambda d: unique(d, "order_id")),
         ("金额非负", lambda d: in_range(d, "amount", 0, 1e6)),
         ("客户ID非空", lambda d: not_null(d, "customer_id"))]
for name, fn in rules:
    ok, msg = fn(df)
    print(f"[{'PASS' if ok else 'FAIL'}] {name}: {msg}")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 维度与规则分层：先定义统一的质量维度框架，再把每条规则挂到维度下，避免规则零散、口径混乱。
2. 质量左移：在数据进入数仓的第一道入口（ODS 层）就做校验，越早发现问题修复成本越低。
3. 规则即代码：把质量规则用 SQL / dbt test / Great Expectations 写成版本化代码，纳入 CI，避免散落在口头约定。
4. 门禁化：将关键规则设为 SLA 门禁（gate），失败即阻断下游任务并告警，而非只出报告无人看。
5. 阈值要分层：核心字段硬性阻断，次要字段设软性监控（空值率、漂移阈值），避免误报疲劳。
6. 记录基线与趋势：分布类、容量类规则需保存历史基线，用同比环比而非拍脑袋的固定阈值。
7. 问题闭环：每条告警关联到责任表与 owner，跟踪修复状态，形成「发现→定位→修复→复检」闭环。

### 踩坑记录
```text
坑 1
结论：用 = NULL 判断空值永远查不到结果
原因：SQL 三值逻辑中 NULL 与任何值比较结果都是 UNKNOWN
解法：一律使用 IS NULL / IS NOT NULL 显式判断空值

坑 2
结论：空值率规则把空字符串和占位符漏掉了
原因：只检查 IS NULL，未覆盖 '' 、'N/A'、0、-1 等「伪空」
解法：规则需显式枚举业务上的「无效取值」集合，统一清洗后再判空

坑 3
结论：Uniqueness 规则在主键上通过，但业务上仍出现重复实体
原因：主键唯一不等于业务唯一键唯一，多主键/联合键未覆盖
解法：在真正的业务唯一键（订单号、手机号、用户+渠道）上独立建唯一规则

坑 4
结论：Volume 规则固定阈值频繁误报
原因：业务量有周期性波动（周末、大促），固定上下限不适用
解法：改用同比环比与移动均值，阈值设为相对比例（如低于 7 日均值 50%）

坑 5
结论：Referential 规则白天通过、凌晨偶发失败
原因：事实表先于维度表更新，外键暂时无匹配（时序问题）
解法：调整 ETL 依赖顺序让维度先跑，或对刚入库窗口内的孤儿记录做容忍/延迟复检

坑 6
结论：Schema 规则校验类型时 float 与 double 被误判为不符
原因：不同引擎对数值类型表示不同（FLOAT/DOUBLE/DECIMAL）
解法：按「类型族」而非精确类型名校验，或约定统一的类型映射规范
```
