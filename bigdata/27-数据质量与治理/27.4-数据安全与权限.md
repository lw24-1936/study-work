## 概述

数据安全与权限解决「谁能访问什么数据、访问后能做什么、留下的痕迹如何追溯」三个问题。它由三层组成：认证（确认身份）→ 授权（确认权限）→ 防护与审计（加密、脱敏、令牌化保护数据本身，审计记录所有访问行为）。在大数据平台中，数据集中存储、多方共享，权限与防护尤其关键——既要让分析师高效取数，又要守住敏感数据不外泄的底线。

```text
数据安全与权限三层模型：
1. 身份层 —— 认证（Authentication）：确认「你是谁」
2. 权限层 —— 授权（Authorization）：确认「你能做什么」
3. 防护层 —— 加密 / 脱敏 / 令牌化 + 审计：保护数据本身并留痕
```

```text
数据安全核心原则：
1. 最小权限 —— 只授予完成任务所需的最小权限
2. 纵深防御 —— 认证、授权、加密、审计多道防线叠加
3. 默认拒绝 —— 未显式授权即拒绝访问
4. 职责分离 —— 授权者、使用者、审计者分离
5. 全程留痕 —— 所有敏感访问可审计、可追溯
```

## Authentication

Authentication（认证）回答「你是谁」——通过凭证（密码、密钥、证书、生物特征）验证用户身份的真实性。常见机制有：用户名密码、LDAP/AD 目录认证、Kerberos（大数据生态标配，如 Hadoop/Hive 的 GSSAPI）、OAuth2/OIDC（第三方登录）、JWT 令牌。认证是安全的第一道门，认证失败应拒绝一切后续操作。

```text
常见认证机制：
1. 密码 —— 最简单，需配合哈希存储与复杂度策略
2. LDAP/AD —— 企业目录统一认证，员工账号集中管理
3. Kerberos —— 大数据生态标配（Hadoop/Hive/HBase），票据 + KDC
4. OAuth2/OIDC —— 第三方授权登录（Google/GitHub）
5. JWT —— 无状态令牌，适合微服务与 API 鉴权
```

```python
import hashlib
import secrets

# 密码哈希存储与校验（切勿明文存密码）
def hash_password(password: str, salt: str) -> str:
    # 加盐后迭代哈希，防彩虹表
    return hashlib.pbkdf2_hmac(
        'sha256', password.encode(), salt.encode(), 100_000
    ).hex()

def verify_password(password: str, salt: str, expected: str) -> bool:
    return secrets.compare_digest(
        hash_password(password, salt), expected
    )

salt = secrets.token_hex(16)
stored = hash_password("S3cret!@#", salt)
print("认证结果：", verify_password("S3cret!@#", salt, stored))   # True
print("错误密码：", verify_password("wrong", salt, stored))       # False
```

## Authorization

Authorization（授权）回答「你能做什么」——在认证之后，决定已通过身份验证的用户对哪些资源拥有哪些操作权限（读、写、执行、删除）。授权与认证必须分离：认证只负责确认身份，授权负责权限判定。授权模型主要有 RBAC、ABAC 两大类，以及更细的 ACL（访问控制列表）。

```text
授权要点：
1. 位置 —— 认证之后，每次资源访问前做权限判定
2. 粒度 —— 库级 / 表级 / 列级 / 行级，越细越安全也越复杂
3. 模型 —— RBAC（按角色）、ABAC（按属性）、ACL（按对象列用户）
4. 默认 —— 默认拒绝（deny by default），未授权即拒
5. 落地 —— 数据库 GRANT、Apache Ranger、AWS IAM 等
```

```sql
-- 授权：基于角色的授权在数据库中的落地
-- 创建只读角色并授予 SELECT 权限
CREATE ROLE analyst;
GRANT SELECT ON warehouse.dwd_order_detail TO analyst;

-- 授予写权限给工程师角色（只对特定库）
CREATE ROLE data_engineer;
GRANT SELECT, INSERT, UPDATE, DELETE
    ON warehouse.dwd_order_detail TO data_engineer;

-- 把角色授予用户
GRANT analyst TO 'alice';
GRANT data_engineer TO 'bob';

-- 撤销权限（最小权限原则：离职 / 转岗时收回）
REVOKE SELECT ON warehouse.dwd_order_detail FROM analyst;
```

## RBAC

RBAC（Role-Based Access Control，基于角色的访问控制）通过「用户 → 角色 → 权限」三层间接授权：不直接给用户授权限，而是把权限打包成角色（如「分析师」「工程师」「管理员」），再把角色授予用户。它大幅简化权限管理——用户多、角色少，权限变更只需改角色即可，是大数据平台（Ranger、Hive、云 IAM）最主流的授权模型。

```text
RBAC 要点：
1. 三层 —— 用户关联角色，角色关联权限，用户不直接挂权限
2. 角色 —— 按岗位 / 职责抽象（分析师、工程师、审计员、管理员）
3. 优势 —— 权限管理从 O(用户×权限) 降为 O(角色)
4. 继承 —— 角色可继承（高级角色含低级角色权限）
5. 落地 —— Ranger 策略、Hive/PostgreSQL 的 ROLE、云 IAM Role
```

```text
RBAC 模型：
用户(User) --N:M--> 角色(Role) --N:M--> 权限(Permission)
权限 = (资源, 操作)，如 (dwd_order_detail, SELECT)
```

```yaml
# Ranger 风格的 RBAC 策略定义（示意）
policies:
  - name: analyst_read_dwd
    roles: [analyst]
    resources:
      database: warehouse
      table: dwd_order_detail
      column: "*"
    permissions: [select]
  - name: engineer_write_dwd
    roles: [data_engineer]
    resources:
      database: warehouse
      table: dwd_order_detail
      column: "*"
    permissions: [select, insert, update, delete]
```

## ABAC

ABAC（Attribute-Based Access Control，基于属性的访问控制）不依赖角色，而是用「属性」动态判定权限：主体属性（部门、职级、安全级别）、资源属性（密级、所属业务）、环境属性（时间、地点、设备）共同参与策略计算。它比 RBAC 更灵活、更细粒度，适合属性复杂、规则动态变化的场景，但策略编写和调试成本更高。

```text
ABAC 要点：
1. 属性 —— 主体 / 资源 / 环境 / 动作四类属性参与判定
2. 策略 —— 用属性表达式定义规则（如「仅工作日 + 本人部门」）
3. 优势 —— 细粒度、动态、可表达复杂约束（含环境条件）
4. 代价 —— 策略复杂，需要策略引擎（OPA、XACML）
5. 对比 —— RBAC 简单易管，ABAC 灵活精细，常混合使用
```

```text
ABAC 策略示例（自然语言表达）：
允许访问，当且仅当：
  主体.部门 == 资源.所属部门  AND
  资源.密级 <= 主体.安全级别  AND
  环境.时间 in [工作日 9:00-18:00]
```

```python
# 简化的 ABAC 策略评估
def evaluate_abac(subject, resource, action, environment, policy):
    # policy 是一组属性条件表达式
    for cond in policy["conditions"]:
        attr_path, op, value = cond
        obj_name, attr = attr_path.split(".")
        obj = {"subject": subject, "resource": resource,
               "environment": environment}[obj_name]
        actual = obj[attr]
        if op == "==" and actual != value:
            return False
        if op == "<=" and not (actual <= value):
            return False
    return True

subject = {"department": "growth", "clearance": 3}
resource = {"department": "growth", "classification": 2}
environment = {"time": "workday"}

policy = {"conditions": [
    ("subject.department", "==", "growth"),
    ("resource.classification", "<=", 2),
]}
print("ABAC 判定：", evaluate_abac(subject, resource, "read", environment, policy))
```

## Encryption

Encryption（加密）把明文转成密文，只有持有密钥者能解密还原，是数据安全的最后防线——即使数据泄露，密文也无法被直接利用。分静态加密（数据落盘时加密，如字段级 AES、存储级透明加密）和传输加密（网络传输中的 TLS/SSL）。密钥管理（KMS）是加密安全的关键，密钥一旦泄露加密即失效。

```text
加密要点：
1. 静态加密 —— 数据落盘加密：字段级、表级、存储卷级
2. 传输加密 —— 网络传输加密：TLS/SSL、HTTPS
3. 对称加密 —— AES，加解密同密钥，快，适合大数据量
4. 非对称加密 —— RSA/ECC，公私钥，慢，适合密钥交换 / 签名
5. 密钥管理 —— KMS 集中托管，密钥轮换、权限隔离
```

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

# AES-GCM 对称加密（认证加密，防篡改）
key = AESGCM.generate_key(bit_length=256)
aesgcm = AESGCM(key)

plaintext = b"13800138000"          # 敏感字段：手机号
nonce = os.urandom(12)              # 每次加密用新 nonce
ciphertext = aesgcm.encrypt(nonce, plaintext, None)

# 解密还原
decrypted = aesgcm.decrypt(nonce, ciphertext, None)
print("明文：", plaintext.decode())
print("密文：", ciphertext.hex()[:32], "...")
print("还原：", decrypted.decode())
```

## Masking

Masking（脱敏）对敏感数据做变形处理，使其在保留格式/统计特性的同时隐藏真实值，常用于测试环境、报表展示、非授权访问。分静态脱敏（把源数据脱敏后落地一份副本，用于测试/开发）和动态脱敏（查询时按权限实时脱敏返回，源数据不变）。常见手段：遮盖（138****8000）、替换、截断、伪造。

```text
脱敏要点：
1. 静态脱敏 —— 落盘一份脱敏副本，供测试 / 开发 / 外部分析
2. 动态脱敏 —— 查询时按权限实时脱敏，源数据保持原样
3. 手段 —— 遮盖、截断、替换、伪造、加噪
4. 原则 —— 不可逆 + 保持格式 + 保留分析价值
5. 对象 —— 手机号、身份证、银行卡、邮箱、姓名、地址
```

```sql
-- 动态脱敏：创建脱敏视图，按角色返回不同结果
CREATE VIEW v_user_masked AS
SELECT
    user_id,
    CONCAT(SUBSTRING(phone, 1, 3), '****', SUBSTRING(phone, 8, 4)) AS phone,
    CONCAT(SUBSTRING(id_card, 1, 6), '********', SUBSTRING(id_card, 15, 4)) AS id_card,
    CONCAT(LEFT(email, 2), '***@', SUBSTRING_INDEX(email, '@', -1)) AS email
FROM dwd_user;

-- 仅授权给「受限分析师」查看脱敏视图，而非原始表
GRANT SELECT ON v_user_masked TO limited_analyst;
```

## Tokenization

Tokenization（令牌化）用无业务含义的令牌（token）替换敏感数据，真实值与令牌的映射关系存放在独立的令牌库（vault）中。与加密不同，令牌化不可逆（无法用数学方法还原，只能查映射表），令牌格式可与原值一致（如保留 16 位卡号格式）。常用于支付卡号（PCI DSS 合规）、身份证号等，让业务系统无需接触真实敏感值即可处理数据。

```text
令牌化要点：
1. 原理 —— 用随机令牌替换敏感值，映射存令牌库
2. 不可逆 —— 无密钥可算回，只能查映射表（区别于加密）
3. 格式保持 —— 令牌可保持原格式（长度、类型）
4. 应用 —— 支付卡号（PCI）、身份证、手机号
5. 价值 —— 业务系统只接触令牌，降低合规范围
```

```python
import secrets
import string

# 简单令牌化：生成随机令牌并建立映射（生产中映射存安全 vault）
class TokenVault:
    def __init__(self):
        self._map = {}   # token -> 真实值（实际存加密库）

    def tokenize(self, real_value: str) -> str:
        token = ''.join(secrets.choice(string.digits) for _ in range(len(real_value)))
        self._map[token] = real_value
        return token

    def detokenize(self, token: str) -> str:
        return self._map.get(token)

vault = TokenVault()
card = "6222021234567890"
token = vault.tokenize(card)
print("真实卡号：", card)
print("令牌：", token)                 # 格式一致，无业务含义
print("还原：", vault.detokenize(token))
```

## PII

PII（Personally Identifiable Information，个人身份信息）指能直接或间接识别到特定自然人的信息，是数据安全治理的首要保护对象。直接标识符（身份证号、手机号、姓名）可直接定位个人；间接标识符（生日、邮编、性别组合）可联合定位个人。合规要求（GDPR、个保法）对 PII 的收集、存储、处理、删除有严格约束，需分类分级管理。

```text
PII 要点：
1. 定义 —— 能识别特定自然人的信息
2. 直接标识 —— 身份证、手机号、姓名、人脸、指纹
3. 间接标识 —— 生日 + 邮编 + 性别等组合可再识别
4. 分类分级 —— 按敏感程度分级（公开 / 内部 / 秘密 / 机密），分级施策
5. 合规 —— GDPR、个保法：最小必要、目的限制、可删除
```

```python
import re

# 识别文本中的 PII（手机号、身份证号、邮箱）
def detect_pii(text: str):
    patterns = {
        "手机号": r"\b1[3-9]\d{9}\b",
        "身份证": r"\b\d{17}[\dXx]\b",
        "邮箱": r"\b[\w.+-]+@[\w-]+\.[\w.]+\b",
    }
    found = {}
    for name, pat in patterns.items():
        matches = re.findall(pat, text)
        if matches:
            found[name] = matches
    return found

sample = "用户张三 手机号13800138000 邮箱zhang@example.com 证件110101199001011234"
print("识别到的 PII：", detect_pii(sample))
```

## Audit

Audit（审计）记录「谁在什么时间、从哪来、对什么数据、做了什么操作、结果如何」，是安全事件追溯、合规举证、异常检测的依据。审计日志应不可篡改、完整保留、与业务日志隔离。大数据平台常通过 Ranger Audit、数据库审计日志、访问网关统一采集。审计不仅用于事后追责，也用于事前威慑与异常行为检测。

```text
审计要点：
1. 内容 —— 谁、何时、何地、何资源、何操作、何结果
2. 要求 —— 不可篡改、完整、长期保留、与业务日志隔离
3. 用途 —— 事件追溯、合规举证、异常检测、威慑
4. 落地 —— Ranger Audit、数据库审计、网关统一采集
5. 自动化 —— 审计日志接入 SIEM/告警，异常访问实时告警
```

```sql
-- 审计表结构与访问记录写入
CREATE TABLE audit_log (
    log_id      BIGINT PRIMARY KEY,
    user_name   STRING,          -- 谁
    ts          TIMESTAMP,       -- 何时
    source_ip   STRING,          -- 何地
    database    STRING,          -- 何资源
    table_name  STRING,
    operation   STRING,          -- 何操作（SELECT/INSERT/DELETE）
    result      STRING,          -- 何结果（success/denied）
    detail      STRING
);

INSERT INTO audit_log VALUES
(1, 'alice', NOW(), '10.0.0.12', 'warehouse',
 'dwd_order_detail', 'SELECT', 'success', 'query 100 rows'),
(2, 'mallory', NOW(), '10.0.9.7', 'warehouse',
 'dwd_user', 'SELECT', 'denied', 'no permission on PII columns');
```

## 应用场景实战

### 场景一：数仓 RBAC 授权 + 动态脱敏落地

```sql
-- 1. 建角色
CREATE ROLE analyst;          -- 分析师：只读，且看脱敏数据
CREATE ROLE engineer;         -- 工程师：可读写明细表
CREATE ROLE admin;            -- 管理员：全部权限

-- 2. 授权
GRANT SELECT ON warehouse.dws_* TO analyst;
GRANT SELECT, INSERT, UPDATE ON warehouse.dwd_* TO engineer;
GRANT ALL ON warehouse.* TO admin;

-- 3. 敏感表建脱敏视图，仅给受限角色
CREATE VIEW v_user_safe AS
SELECT user_id,
       CONCAT(SUBSTRING(phone,1,3),'****',SUBSTRING(phone,8,4)) AS phone,
       name, city
FROM dwd_user;

-- 4. 分析师只能看脱敏视图，看不到原始 dwd_user
GRANT SELECT ON v_user_safe TO analyst;
REVOKE SELECT ON dwd_user FROM analyst;

-- 5. 把角色授予具体用户
GRANT analyst TO 'zhang'; GRANT engineer TO 'li'; GRANT admin TO 'wang';
```

```text
权限落地效果：
1. zhang（分析师）—— 只能查脱敏视图，看不到真实手机号
2. li（工程师）—— 可写明细表，不可改权限
3. wang（管理员）—— 全部权限，且其操作被审计
4. 未授权用户 —— 默认拒绝，访问被记录为 denied
```

### 场景二：用 ABAC 策略保护敏感列并做审计

```python
# 结合 ABAC 判定 + 审计记录，保护 PII 列访问
def check_access(user, table, column, env, audit):
    pii_columns = {"phone", "id_card", "email", "name"}
    allowed = True
    reason = "ok"
    if column in pii_columns:
        if user["department"] != table["owner_department"]:
            allowed, reason = False, "跨部门访问 PII 列"
        elif user["clearance"] < 3:
            allowed, reason = False, "密级不足"
    audit.append({
        "user": user["name"], "table": table["name"], "column": column,
        "allowed": allowed, "reason": reason,
    })
    return allowed

audit = []
users = [
    {"name": "alice", "department": "growth", "clearance": 4},
    {"name": "bob", "department": "finance", "clearance": 2},
]
table = {"name": "dwd_user", "owner_department": "growth"}

for u in users:
    check_access(u, table, "phone", {}, audit)
print("审计记录：", audit)
```

## 最佳实践与踩坑记录

### 最佳实践

1. 认证与授权分离，授权采用最小权限与默认拒绝原则
2. 优先用 RBAC 管理角色，复杂约束场景再引入 ABAC 混合
3. 敏感列（PII）统一清单化管理，脱敏/加密/令牌化按场景选择
4. 密钥统一托管到 KMS，定期轮换，杜绝硬编码密钥
5. 动态脱敏优于静态脱敏——源数据只存一份，按权限实时变形
6. 审计日志独立存储、不可篡改，接入告警做异常检测
7. 权限变更走审批流程，定期做权限盘点回收僵尸权限

### 踩坑记录

```text
坑 1：直接用明文存密码
结论：数据库泄露后密码全部暴露，撞库风险极高。
原因：未做哈希/加盐，密码以可还原形式存储。
解法：用 PBKDF2/bcrypt/argon2 加盐迭代哈希，绝不存明文。

坑 2：把权限直接挂在用户上
结论：员工转岗/离职时权限收不干净，越权风险累积。
原因：绕过角色层，用户与权限直接多对多，难管理。
解法：走 RBAC 三层模型，权限挂角色，用户挂角色。

坑 3：授权过度（一把梭给 ALL）
结论：测试账号拥有全库权限，误删或泄露后果严重。
原因：图省事直接 GRANT ALL，违背最小权限原则。
解法：按岗位最小授权，用角色细分，定期权限盘点。

坑 4：静态脱敏规则太简单可被还原
结论：脱敏后的副本可被关联反推，脱敏形同虚设。
原因：脱敏规则固定替换，攻击者可利用已知值反推。
解法：用随机化/令牌化脱敏，脱敏副本与映射分库存储。

坑 5：审计日志与业务日志混存且可改
结论：安全事件发生后无法追溯，审计失去法律效力。
原因：审计日志未隔离、未做防篡改。
解法：审计日志独立存储、只追加、哈希链防篡改、定时归档。
```
