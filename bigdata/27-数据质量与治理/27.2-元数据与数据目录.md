## 概述

元数据（Metadata）是「关于数据的数据」，描述数据的结构、语义、来源、质量、归属与血缘；数据目录（Catalog）则是集中管理、检索这些元数据的产品化系统，让组织内的数据「找得到、看得懂、信得过、用得好」。在企业数据治理中，元数据与数据目录是其他治理活动（质量、安全、血缘、生命周期）的基础设施——没有元数据，就无法回答「这个字段什么意思、归谁管、能不能用」。

```text
元数据与数据目录核心：
- 元数据分类：技术元数据（schema/分区/存储）、业务元数据（定义/口径/owner）、操作元数据（任务/运行日志）
- 数据目录价值：数据资产化、检索发现、影响分析、权限与合规
- 代表工具：开源 Amundsen / DataHub / OpenMetadata、云原生 AWS Glue / GCP Data Catalog
- 治理闭环：采集 → 统一模型 → 检索 → 消费 → 反馈修正
元数据是「原材料」，目录是「货架与索引」，治理是「运营规则」
```

## Metadata 元数据

元数据是对数据各方面属性的形式化描述，通常分为三类：技术元数据（表结构、字段类型、分区、存储位置、行数）、业务元数据（业务含义、指标口径、数据字典、标签）与操作元数据（ETL 任务、运行时间、读写频率）。元数据管理的核心是从各类引擎、调度系统、代码仓库中自动采集这些信息，形成统一、可查询的元数据图谱，避免依赖人工口头维护。

```text
Metadata 要点：
- 技术元数据：库表结构、字段类型、分区、存储格式、统计信息
- 业务元数据：字段业务含义、指标口径、术语、标签、owner
- 操作元数据：任务血缘、运行时长、访问频率、最近读写时间
- 采集方式：连接器自动同步（Hive/Spark/DB）、SQL 解析、API 上报
```

```sql
-- 从 Hive Metastore 查询技术元数据（表、库、字段、类型）
SELECT d.NAME                    AS db_name,
       t.TBL_NAME                AS table_name,
       c.COLUMN_NAME             AS column_name,
       c.TYPE_NAME               AS column_type,
       c.COMMENT                 AS column_comment
FROM COLUMNS_V2 c
JOIN SDS s        ON c.CD_ID = s.CD_ID
JOIN TBLS t       ON s.SD_ID = t.SD_ID
JOIN DBS  d       ON t.DB_ID = d.DB_ID
WHERE d.NAME = 'ods'
ORDER BY t.TBL_NAME, c.INTEGER_IDX;
```

## Catalog 数据目录

数据目录是面向数据消费者（分析师、科学家、工程师）的元数据产品，核心能力是「数据资产的统一检索与发现」。用户可以在目录中搜索表与字段、浏览字段含义、查看血缘与质量状态、了解数据归属并申请权限。现代数据目录强调自动采集（而非手工登记）、搜索优先（而非目录树点选）、以及与数据血缘、质量、权限系统的深度集成。

```text
Catalog 要点：
- 检索发现：按关键词、标签、owner、分类搜索数据资产
- 资产画像：字段含义、样例数据、质量评分、更新频率
- 联动能力：血缘图、质量告警、权限申请、术语关联
- 代表产品：DataHub、OpenMetadata、Amundsen、AWS Glue Catalog
- 关键指标：资产覆盖率、搜索命中率、元数据新鲜度
```

## Ownership 数据归属

Ownership（数据归属/责任人）指明每张表、每个数据资产「由谁负责」，是数据治理中「有人管」的机制保障。清晰的责任人划分能确保：数据出问题时找得到人、字段口径有人确认、权限申请有人审批。归属通常包含「业务 owner（懂业务口径）」与「技术 owner（懂实现）」，并可细分为负责人、贡献者、审批人等角色。

```text
Ownership 要点：
- 业务 owner：负责字段口径、业务含义的准确性
- 技术 owner：负责表结构、ETL、数据生产的稳定性
- 作用：问题定位、权限审批、口径仲裁、责任追溯
- 落地：在目录中为每张表标注 owner，与组织架构/值班表联动
```

```sql
-- 在自建元数据库维护表的归属信息
CREATE TABLE IF NOT EXISTS meta_table_owner (
    table_name    VARCHAR(200) PRIMARY KEY,
    business_owner VARCHAR(100),
    tech_owner    VARCHAR(100),
    team          VARCHAR(100),
    updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 查询无人认领（owner 缺失）的表，是治理的重点对象
SELECT table_name FROM meta_table_owner
WHERE business_owner IS NULL OR tech_owner IS NULL;
```

## Classification 数据分类分级

Classification（分类分级）按照数据的重要程度与敏感程度对数据资产打标签并划分等级（如公开、内部、机密、绝密），是数据安全与合规的基础。它要求先建立分类分级标准，再对字段或表做打标，最终驱动差异化的安全策略：高等级数据的访问需审批、脱敏、审计。常见法规依据包括《数据安全法》《个人信息保护法》以及行业分级指南。

```text
Classification 要点：
- 分类：按业务属性划分（客户、交易、财务、人力）
- 分级：按敏感与重要程度（L1 公开 ~ L4 绝密）
- 打标维度：字段级 / 表级 / 标签（PII、手机号、身份证）
- 驱动策略：高等级 → 加密、脱敏、最小权限、审计留痕
```

```yaml
# 字段级分类分级标注示例
classification:
  - column: customer.id_card
    category: 个人信息
    level: L3-机密
    tags: [PII, 身份证]
    policy: 默认脱敏显示
  - column: customer.phone
    category: 个人信息
    level: L3-机密
    tags: [PII, 手机号]
    policy: 掩码显示 138****0000
  - column: product.price
    category: 商品信息
    level: L1-公开
    tags: []
    policy: 正常显示
```

## Dictionary 数据字典

数据字典（Dictionary）是字段级业务含义的权威解释集合，回答「这个字段到底是什么意思、有哪些取值、口径如何」。它是数据目录中最贴近业务、也最需要人工维护的部分。一份好的数据字典会为每个字段记录：中文名、业务定义、取值枚举、单位、计算口径、示例值，让不同团队对同一字段的理解一致，是消除「同名异义、异名同义」的关键。

```text
Dictionary 要点：
- 字段条目：中文名、定义、类型、单位、枚举、示例、口径
- 解决痛点：同名异义、异名同义、口径不一致
- 维护方式：目录中在线编辑 + 评审流程 + 版本留痕
- 与指标口径、数据标准的联动：字典是标准的载体之一
```

```sql
-- 数据字典表结构与查询示例
CREATE TABLE IF NOT EXISTS meta_data_dictionary (
    table_name   VARCHAR(200),
    column_name  VARCHAR(200),
    cn_name      VARCHAR(200),
    definition   TEXT,
    value_enum   TEXT,          -- 取值枚举，如 "0=否,1=是"
    unit         VARCHAR(50),
    biz_rule     TEXT,          -- 计算口径 / 业务规则
    example      VARCHAR(200),
    PRIMARY KEY (table_name, column_name)
);

-- 检索某字段的业务定义
SELECT cn_name, definition, value_enum, biz_rule
FROM meta_data_dictionary
WHERE table_name = 'fact_order' AND column_name = 'order_status';
```

## Standard 数据标准

数据标准（Standard）是对数据命名、类型、格式、取值、编码的统一规范，是数据字典与分类分级的上位约束。它解决跨系统、跨团队数据口径不统一的问题，典型包括：命名规范（表/字段/指标命名规则）、编码标准（性别、币种、地区代码统一编码）、格式标准（日期格式、金额精度）与指标标准（同一指标唯一定义）。标准落地后，新建数据资产必须符合标准，存量资产逐步治理对齐。

```text
Standard 要点：
- 命名标准：表/字段/指标命名规则（如 f_ 事实表、d_ 维度表）
- 编码标准：统一枚举编码（性别、币种、地区、状态码）
- 格式标准：日期、金额精度、字符串长度约定
- 指标标准：一个指标唯一定义（口径、单位、维度）
- 落地：标准发布 → 建表校验 → 目录标注符合性
```

```yaml
# 数据标准定义示例（指标与编码标准）
standards:
  naming:
    fact_table: "f_{业务域}_{粒度}_{主题}"
    dim_table:  "d_{主题}"
    metric:     "{业务动作}_{度量}_[{口径修饰}]"
  enums:
    gender:    {0: 未知, 1: 男, 2: 女, 9: 未说明}
    currency:  {CNY: 人民币, USD: 美元, EUR: 欧元}
  format:
    date:     "yyyy-MM-dd"
    amount:   "decimal(18,2)"
  metrics:
    gmv: {name: 成交总额, formula: "sum(实付金额)", unit: 元, owner: 交易域}
```

## Lifecycle 数据生命周期

数据生命周期（Lifecycle）管理数据从创建、使用、归档到销毁的全过程，核心诉求是「冷热分层、到期归档、合规删除」，在满足业务查询与合规留存要求的同时控制存储成本与安全风险。数据目录中通过记录数据的最后访问时间、热度与保留策略，自动识别冷数据，驱动分层存储与过期清理，避免「只进不出」的数据无限膨胀。

```text
Lifecycle 要点：
- 阶段：创建 → 活跃使用 → 低频访问 → 归档 → 销毁
- 冷热分层：热数据 SSD/高频、温数据 HDD、冷数据对象存储/压缩
- 保留策略：按法规与业务定义保留期限，到期自动清理或归档
- 识别依据：最后访问时间、访问频次、业务重要等级
```

```python
import pandas as pd
from datetime import datetime, timedelta

# 模拟元数据：识别冷数据并给出生命周期处置建议
now = datetime(2026, 8, 14)
assets = pd.DataFrame({
    "table": ["f_order", "f_click_log", "d_customer", "f_archive_2020"],
    "last_access_days_ago": [1, 5, 90, 400],
    "level": ["L1", "L1", "L2", "L3"],
})

def lifecycle_action(row):
    if row["last_access_days_ago"] > 365:
        return "归档到冷存储"
    if row["last_access_days_ago"] > 180:
        return "迁移到温层并压缩"
    if row["last_access_days_ago"] > 30:
        return "标记低频，观察"
    return "保持热层"

assets["action"] = assets.apply(lifecycle_action, axis=1)
print(assets[["table", "last_access_days_ago", "action"]])
```

## 应用场景实战

### 场景一：构建数据资产检索服务

数据团队需要一个统一入口，让分析师能按关键词、owner、分类检索到表与字段，并查看其含义与责任人。用 SQL 在自建元数据库中实现资产检索，覆盖「搜表」「搜字段」「查归属」三类查询。

```sql
-- 1) 按关键词检索表（名称或注释命中）
SELECT t.table_name, t.comment, o.business_owner, o.team
FROM meta_table t
LEFT JOIN meta_table_owner o ON t.table_name = o.table_name
WHERE t.table_name LIKE '%order%' OR t.comment LIKE '%订单%';

-- 2) 检索字段：找到所有含义涉及「金额」的字段
SELECT table_name, column_name, cn_name, definition
FROM meta_data_dictionary
WHERE cn_name LIKE '%金额%' OR definition LIKE '%金额%';

-- 3) 按分类查资产：找出所有 L3 及以上敏感表
SELECT table_name, category, level
FROM meta_classification
WHERE level IN ('L3-机密', 'L4-绝密');
```

### 场景二：元数据采集与目录同步脚本

数据平台需要定时从 Hive Metastore 采集元数据，同步到统一目录库，并自动补充「无 owner 表」清单。用 Python 模拟采集与治理同步流程，展示元数据管道的典型实现。

```python
import json

# 模拟从 Hive Metastore 采集到的技术元数据
hive_metadata = [
    {"db": "ods", "table": "ods_order", "cols": [
        {"name": "order_id", "type": "string"},
        {"name": "amount", "type": "double"}]},
    {"db": "dwd", "table": "dwd_order_detail", "cols": [
        {"name": "order_id", "type": "string"},
        {"name": "status", "type": "string"}]},
]

owner_map = {"ods_order": "张三"}  # 已登记的 owner

catalog = []
unclaimed = []
for t in hive_metadata:
    full_name = f"{t['db']}.{t['table']}"
    entry = {
        "table": full_name,
        "column_count": len(t["cols"]),
        "columns": [c["name"] for c in t["cols"]],
        "owner": owner_map.get(t["table"]),
    }
    catalog.append(entry)
    if not entry["owner"]:
        unclaimed.append(full_name)

print(json.dumps(catalog, ensure_ascii=False, indent=2))
print("无人认领的表:", unclaimed)
```

## 最佳实践与踩坑记录

### 最佳实践

1. 元数据采集自动化优先：优先通过连接器自动同步各引擎元数据，人工只维护业务含义与 owner，避免「登记一次、再也不会更新」。
2. 三类元数据统一建模：技术、业务、操作元数据落到统一图谱，才能支撑检索、血缘、质量联动，而非各自为政。
3. owner 全覆盖并纳入考核：对无主表定期巡检通报，把「数据有人管」变成硬性要求而非倡议。
4. 分类分级先行、策略跟进：先定分类分级标准，再逐字段打标，最后用标签驱动脱敏、加密、审计策略落地。
5. 数据标准与建表流程绑定：新建表必须通过命名、类型、字典的合规校验，从源头保证标准落地。
6. 目录要「可搜索」而非「可浏览」：投入资源做搜索、标签、样例数据，而不是堆一个没人点的大目录树。
7. 生命周期靠数据说话：以最后访问时间、热度为依据做冷热分层与归档，避免拍脑袋保留与一刀切删除。

### 踩坑记录

```text
坑 1
结论：目录里表很多，但字段级业务含义大面积空白
原因：只采集了技术元数据，业务元数据依赖人工且无人负责
解法：把字段注释补全设为 owner 职责与发布门槛，用字典模板批量补齐

坑 2
结论：元数据「过期」，表已删除但目录仍能搜到
原因：采集只做增量新增，未处理表删除（软删除/下线）
解法：开启 markDeletedTables 等软删除标记，定期比对源端做对账清理

坑 3
结论：同名异义导致指标口径打架（两个团队都叫 GMV 含义不同）
原因：缺少统一的数据标准与指标字典，各自定义
解法：建立指标标准唯一登记，同名指标强制引用同一口径并仲裁冲突

坑 4
结论：分类分级打标后安全策略没生效，敏感字段仍明文可见
原因：只打了标签，未把标签同步给权限/脱敏引擎执行策略
解法：标签 → 策略引擎联动，高等级字段自动触发脱敏与访问审批

坑 5
结论：冷热分层策略误伤活跃数据，归档后业务查不到
原因：仅按「最后访问时间」单点判断，忽略了周期性访问模式
解法：结合访问频次、访问窗口与业务等级综合判定，归档前留观察期

坑 6
结论：目录搜索结果一堆，但用户找不到「真正该用的那张表」
原因：缺少资产热度、质量评分、样例数据等辅助排序信息
解法：为资产增加使用频率、质量分、样例预览，按可信度排序推荐
```
