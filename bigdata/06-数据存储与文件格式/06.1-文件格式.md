## 概述

文件格式是数据在存储/传输中的组织方式，直接决定数据的读写性能、压缩比、schema 演进能力和跨语言兼容性。大数据场景下，格式分「行式文本」（CSV/JSON/XML，人可读但笨重）、「二进制序列化」（Avro/Protobuf，紧凑、跨语言、带 schema）和「列式分析」（Parquet/ORC，面向扫描聚合，压缩比高）三类，外加内存列式格式 Arrow 和 Hadoop 原生 SequenceFile。选对格式是数据湖、数仓、流处理性能的第一道关。

```text
文件格式选型原则：
1. 分析扫描 —— Parquet/ORC 列式，只读需要的列，压缩比高
2. 流式/消息序列化 —— Avro/Protobuf，紧凑、schema 演进、跨语言
3. 人可读/交换 —— CSV/JSON 简单通用，但解析慢、无类型
4. 内存计算 —— Arrow 列式内存格式，跨系统零拷贝
5. 兼容性 —— 看是否要 schema 演进、是否要跨语言、是否要列裁剪
```

```text
三类格式速览：
行式文本 —— CSV / JSON / XML：可读性好，但无压缩、解析慢、无列裁剪
行式二进制 —— Avro / Protobuf / SequenceFile：紧凑、有 schema、可演进
列式分析 —— Parquet / ORC / Arrow：按列存储、编码压缩、支持谓词下推
```

## CSV

CSV（Comma-Separated Values）是最简单的行式文本格式，每行一条记录、逗号分隔字段。它通用、人可读、任何工具都能处理，但问题也多：无类型、无 schema、无压缩、字段含逗号/换行需转义、解析慢、无法列裁剪。适合小批量数据交换和人工检查，不适合作为大数据主存储格式。

```text
CSV 要点：
1. 优点 —— 通用、简单、人可读、任何语言/工具都支持
2. 缺点 —— 无类型、无 schema、解析慢、无压缩、转义易错
3. 转义 —— 字段含逗号/引号/换行时用双引号包裹，引号内引号双写
4. 定位 —— 数据交换、人工校验、小批量导入，非大数据主格式
```

```text
id,name,city,amount
1001,alice,beijing,120.50
1002,"bob, jr","new york",99.90
1003,"carol","san ""fran""",200.00
```

```python
import csv

with open('users.csv') as f:
    reader = csv.reader(f)
    for row in reader:
        print(row)
# ['id', 'name', 'city', 'amount']
# ['1001', 'alice', 'beijing', '120.50']
```

## JSON

JSON（JavaScript Object Notation）是半结构化、自描述的数据格式，支持嵌套对象和数组，schema 灵活，是 API 和日志的事实标准。它比 CSV 表达能力强的多（可嵌套、可缺失字段），但仍是文本、冗余大（重复的 key）、解析慢、无列裁剪，不适合海量数据分析。大数据里 JSON 常作为原始日志格式，之后 ETL 转成 Parquet。

```text
JSON 要点：
1. 优点 —— 自描述、可嵌套、schema 灵活、生态最广
2. 缺点 —— 文本冗余（key 重复）、解析慢、无压缩、无列裁剪
3. 定位 —— API 交换、日志、配置、半结构化原始数据
4. 进阶 —— 每行一个 JSON 的 JSON Lines（JSONL）更适合流式追加
```

```json
{"id": 1001, "name": "alice", "city": "beijing", "tags": ["vip", "frequent"]}
{"id": 1002, "name": "bob", "city": "new york", "profile": {"age": 28}}
```

```sql
-- 用 JSON 函数解析（PostgreSQL / MySQL / Hive 通用思路）
SELECT data->>'name' AS name,
       data->>'city' AS city
FROM events_json;
```

## XML

XML 是带标签的树形标记格式，曾是数据交换的主流（Web Service、配置文件），现在逐步被 JSON 取代，但仍广泛存在于金融、政务、企业集成和配置领域。XML 支持 schema 校验（XSD）和命名空间，但冗长、解析慢、结构复杂。大数据里 XML 常出现在历史遗留系统和行业标准接口中。

```text
XML 要点：
1. 优点 —— 结构严谨、可 schema 校验（XSD）、支持命名空间
2. 缺点 —— 极其冗长、解析慢、学习/处理成本高
3. 定位 —— 金融/政务/企业遗留系统、配置文件、SOAP 接口
4. 处理 —— 用 XPath/XQuery 提取字段，或 Spark 的 XML 数据源
```

```xml
<users>
  <user id="1001">
    <name>alice</name>
    <city>beijing</city>
  </user>
  <user id="1002">
    <name>bob</name>
    <city>new york</city>
  </user>
</users>
```

## Avro

Apache Avro 是行式二进制序列化格式，特点是「schema 与数据分离」——schema 以 JSON 定义，数据按 schema 紧凑编码，读时用 writer schema + reader schema 做 schema 演进。它支持丰富类型、跨语言（Java/Python/Scala）、且天然适合 Kafka 消息（Confluent Schema Registry 的标准格式）。适合流式传输和「写多读少」的场景。

```text
Avro 要点：
1. Schema 分离 —— schema 单独存（JSON），数据紧凑二进制
2. Schema 演进 —— writer schema 与 reader schema 独立，可增删字段（默认值）
3. 跨语言 —— Java/Python/Scala/C++ 都有实现，RPC 与消息常用
4. 定位 —— Kafka 消息、流处理序列化、Hadoop 行式存储
```

```json
{
  "type": "record",
  "name": "User",
  "namespace": "com.example",
  "fields": [
    { "name": "id", "type": "long" },
    { "name": "name", "type": "string" },
    { "name": "city", "type": ["null", "string"], "default": null }
  ]
}
```

```python
import fastavro

schema = {
    "type": "record", "name": "User", "namespace": "com.example",
    "fields": [
        {"name": "id", "type": "long"},
        {"name": "name", "type": "string"},
        {"name": "city", "type": ["null", "string"], "default": None}
    ]
}
record = {"id": 1001, "name": "alice", "city": "beijing"}

# 序列化
with open('user.avro', 'wb') as f:
    fastavro.writer(f, schema, [record])

# 反序列化
with open('user.avro', 'rb') as f:
    for r in fastavro.reader(f):
        print(r)
```

## Protobuf

Protocol Buffers（Protobuf）是 Google 的行式二进制序列化格式，与 Avro 类似但更侧重「极致紧凑 + 高性能 RPC」。它用 .proto 文件定义 schema，编译生成各语言代码，用字段编号做向后兼容（新增字段用新编号）。相比 Avro，Protobuf 序列化更快、体积更小，是 gRPC 和内部高性能传输的默认格式。

```text
Protobuf 要点：
1. 紧凑高效 —— 变长编码，体积小、序列化快，性能优于 JSON/XML
2. 字段编号 —— 靠 field number 做兼容，新字段用新编号、旧字段保留
3. 代码生成 —— .proto 编译出各语言强类型代码（gRPC 标准）
4. 定位 —— gRPC、高性能内部传输、微服务通信
```

```text
// user.proto
syntax = "proto3";
message User {
  int64  id   = 1;
  string name = 2;
  string city = 3;
}
```

```python
# 编译 user.proto 生成 user_pb2 后使用（示意）
import user_pb2

u = user_pb2.User(id=1001, name="alice", city="beijing")
data = u.SerializeToString()          # 序列化
u2 = user_pb2.User()
u2.ParseFromString(data)              # 反序列化
print(u2.name)
```

## Parquet

Apache Parquet 是列式存储格式的事实标准，数据按列组织、分块（Row Group）存储，每列的 Page 独立编码压缩（字典编码、RLE、位打包、Snappy/Zstd）。列式 + 编码带来两大优势：查询只读需要的列（列裁剪）、压缩比高（同列数据相似）。Parquet 还内嵌每列的统计信息（min/max），支持谓词下推跳过不匹配的 Row Group。它是数据湖、Spark、Iceberg/Hudi/Delta 的默认格式。

```text
Parquet 要点：
1. 列式存储 —— 按列组织，查询只读相关列（列裁剪）
2. Row Group —— 文件按行分组（默认约 1 万到数万行），组内按列存
3. 谓词下推 —— 每列 Page 存 min/max 统计，过滤时跳过整块
4. 嵌套支持 —— 用 Dremel 编码（definition/repetition level）表达嵌套结构
```

```python
import pyarrow.parquet as pq
import pyarrow as pa

# 写 Parquet
table = pa.table({
    'id': [1001, 1002, 1003],
    'name': ['alice', 'bob', 'carol'],
    'city': ['beijing', 'new york', 'shanghai']
})
pq.write_table(table, 'users.parquet', compression='snappy')

# 读 Parquet（列裁剪 + 谓词下推）
t = pq.read_table('users.parquet', columns=['id', 'city'])
print(t.to_pandas())
```

## ORC

ORC（Optimized Row Columnar）是 Hortonworks 为 Hive 优化的列式格式，与 Parquet 同源（都源自 Dremel），但更偏 Hive 生态。ORC 有更细的 stripe 结构、轻量索引（每 10000 行的 min/max）、内置 Bloom Filter，压缩比和查询性能在 Hive 场景常优于 Parquet。Parquet 胜在生态通用（Spark/Iceberg/云），ORC 胜在 Hive 深度优化。

```text
ORC 要点：
1. Stripe —— 默认 64MB 的 stripe，含行索引与数据，粒度细
2. 轻量索引 —— 每 stripe 记录各列 min/max，快速跳过
3. Bloom Filter —— 可选，加速等值过滤
4. 定位 —— Hive 生态首选，压缩比与查询性能优秀
```

```sql
-- Hive 建 ORC 表
CREATE TABLE users_orc (
    id    BIGINT,
    name  STRING,
    city  STRING
) STORED AS ORC;

-- 写入 ORC 并开启 Bloom Filter（Hive 表属性）
CREATE TABLE users_orc (
    id BIGINT, name STRING, city STRING
) STORED AS ORC
TBLPROPERTIES ('orc.bloom.filter.columns' = 'id');
```

## Arrow

Apache Arrow 是「内存中的列式数据格式」标准，定义了一套跨语言的列式内存布局，让不同系统（Spark、pandas、DuckDB、Parquet）之间零拷贝共享数据，避免序列化/反序列化开销。它是「内存计算」的格式，与 Parquet（磁盘格式）互补——Arrow 常作为内存表示，Parquet 作为落盘格式。

```text
Arrow 要点：
1. 内存列式 —— 定义内存布局标准，跨语言零拷贝共享
2. 零拷贝 —— 不同系统间传数据不序列化，直接指针共享
3. 与 Parquet 互补 —— 内存用 Arrow，落盘用 Parquet
4. 生态 —— PyArrow、pandas 2.0、DuckDB、Spark 都基于或兼容 Arrow
```

```python
import pyarrow as pa

# Arrow 内存表
arrays = [
    pa.array([1001, 1002, 1003]),
    pa.array(['alice', 'bob', 'carol'])
]
table = pa.Table.from_arrays(arrays, names=['id', 'name'])

# 零拷贝转 pandas（底层共享内存）
df = table.to_pandas()
print(df)
```

## SequenceFile

SequenceFile 是 Hadoop 原生的键值对二进制格式，把若干「key-value」记录序列化成一个文件，支持压缩（record/block 两级）。它是 MapReduce 中间结果和 HDFS 小文件合并的经典格式，后来逐步被 Parquet/ORC/Avro 取代，但在 MapReduce 生态和「小文件打包」场景仍有应用。

```text
SequenceFile 要点：
1. 键值对 —— 每条记录是 key-value，适合 MapReduce 输入输出
2. 可切分 —— 文件可切分并行处理，适合做 MR 输入
3. 压缩 —— 支持 record/block 两种压缩级别
4. 小文件合并 —— 常把海量小文件打成 SequenceFile 减少 NameNode 压力
```

```java
// 写 SequenceFile
Configuration conf = new Configuration();
Path path = new Path("/data/seqfile");
try (SequenceFile.Writer writer = SequenceFile.createWriter(
        conf, SequenceFile.Writer.file(path),
        SequenceFile.Writer.keyClass(LongWritable.class),
        SequenceFile.Writer.valueClass(Text.class))) {
    writer.append(new LongWritable(1001), new Text("alice"));
    writer.append(new LongWritable(1002), new Text("bob"));
}
```

## 应用场景实战

### 场景一：埋点日志 JSON -> Parquet 的 ETL 优化

```python
import pyarrow as pa
import pyarrow.parquet as pq
import json

# 原始 JSON 日志（一行一条）
raw_lines = [
    '{"id": 1001, "name": "alice", "city": "beijing", "amount": 120.5}',
    '{"id": 1002, "name": "bob", "city": "new york", "amount": 99.9}',
]

# 解析 JSON 转 Arrow 表，落 Parquet
rows = [json.loads(line) for line in raw_lines]
table = pa.Table.from_pylist(rows)
pq.write_table(table, 'events.parquet', compression='zstd')

# 下游分析只读需要的列，压缩后体积大幅减小
t = pq.read_table('events.parquet', columns=['id', 'amount'])
print(t.to_pandas())
```

### 场景二：Kafka 消息用 Avro + Schema Registry 序列化

```text
架构：
Producer -> Avro 序列化（schema 注册到 Schema Registry）-> Kafka
Consumer <- Avro 反序列化（从 Registry 取 schema）<- Kafka

价值：
1. 消息紧凑（二进制），吞吐高、占用小
2. schema 演进安全（增删字段有默认值），新旧版本兼容
3. 跨语言：Java Producer 写，Python Consumer 读
```

```python
# Confluent Schema Registry + Avro 示意（Schema Registry 客户端）
from confluent_kafka import Producer

# schema 由 Schema Registry 统一管理，producer 只需传 value + schema id
conf = {'bootstrap.servers': 'localhost:9092'}
producer = Producer(conf)
producer.produce('users', key='1001', value=b'\x00\x01...avro bytes...')
producer.flush()
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分析型数据（数仓/数据湖）默认用 Parquet（或 Hive 生态用 ORC），享受列裁剪和压缩
2. Kafka/流式消息用 Avro + Schema Registry，紧凑且 schema 演进安全
3. 微服务 RPC 用 Protobuf（gRPC），性能极致
4. 原始日志先存 JSON/CSV，ETL 后转 Parquet，别拿 JSON 直接做分析
5. Parquet 写文件时合理设置 row group 大小，兼顾下推粒度和元数据开销
6. 内存计算、跨系统传数据用 Arrow，避免序列化开销
7. 小文件用 SequenceFile/Parquet 合并，减少元数据压力

### 踩坑记录

```text
坑 1：拿 JSON 直接做海量分析
结论：查询慢、存储大、成本高。
原因：JSON 无列裁剪，每次全量解析，key 冗余、无压缩。
解法：ETL 转 Parquet/ORC 再分析，JSON 仅作原始暂存。

坑 2：CSV 字段含逗号/换行导致解析错位
结论：字段错位，数据串行，下游全错。
原因：CSV 未正确转义含分隔符的字段。
解法：用标准 CSV 库（带转义），或直接换 JSON/Parquet 避免歧义。

坑 3：Avro/Protobuf 乱改 schema 破坏兼容
结论：老消费者读新消息报错，消费中断。
原因：删除/改类型字段没考虑向后兼容，reader schema 不匹配。
解法：字段只增不删，删字段保留默认值，遵守 schema 演进规则。

坑 4：Parquet 小文件过多
结论：任务多、元数据大、查询慢。
原因：频繁写入产生大量小 Parquet 文件，未做合并。
解法：定期 compaction 合并小文件，控制写入批次大小。

坑 5：忽略列式格式的谓词下推
结论：全表扫描，列式格式的性能优势没发挥。
原因：查询没利用 min/max 统计，或过滤条件写法阻断了谓词下推。
解法：过滤条件直接写列比较（col > x），避免对列套函数。
```
