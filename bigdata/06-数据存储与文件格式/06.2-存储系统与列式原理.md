## 概述

存储系统是数据的物理底座，决定数据怎么放、怎么读、怎么保证不丢。列式存储原理（行存 vs 列存、字典编码、RLE、位打包、压缩）解释了为什么 Parquet/ORC 能又小又快；存储系统的分层（块存储、对象存储、分布式文件系统）和可靠性机制（副本、纠删码、容错）则支撑了数据湖和海量存储的落地。理解这些，才能为不同负载选对存储、调对参数。

```text
存储系统的两个层面：
1. 编码压缩层 —— 列式存储 + 字典编码/RLE/位打包 + 通用压缩
   => 解决「存得小、读得快」
2. 分布式存储层 —— 块/对象/文件存储 + 副本/纠删码 + 容错
   => 解决「存得下、不丢失、可扩展」
```

```text
关键取舍：
列式 vs 行式 —— 分析扫描 vs 事务点查
副本 vs 纠删码 —— 简单可靠 vs 省空间但计算重
块存储 vs 对象存储 —— 低延迟随机访问 vs 海量低成本可扩展
```

## 行存与列存

行式存储（Row-oriented）把一行数据连续存放，适合按行读写（OLTP 的点查、整行更新）；列式存储（Column-oriented）把同一列的数据连续存放，适合按列扫描聚合（OLAP）。列存的优势：只读需要的列（列裁剪）、同列数据相似度高便于压缩、更适合向量化执行。这是 OLAP 引擎和 Parquet/ORC 快于行存的根本原因。

```text
行存 vs 列存：
1. 行存 —— 一行连续，点查/更新快，整行读取高效（MySQL InnoDB、HBase）
2. 列存 —— 一列连续，扫描/聚合快，压缩比高（ClickHouse、Parquet、ORC）
3. 列裁剪 —— 列存查询只读涉及列，行存必须读整行
4. 写入 —— 行存单行写入快；列存单行写慢（需拆列），批量写快
```

```text
同一份数据（id, name, city）的存储布局：
行存：[1001, alice, beijing] [1002, bob, ny] [1003, carol, sh]
列存：id:   [1001, 1002, 1003]
      name: [alice, bob, carol]
      city: [beijing, ny, sh]

查询 SELECT city FROM ... 时：
行存要读每一整行；列存只读 city 这一列
```

## 字典编码

字典编码（Dictionary Encoding）把列中重复出现的值映射成一个小整数 ID，存储「字典（值->ID 映射）+ 编码后的 ID 数组」。低基数列（如状态、城市、性别）重复值多，用字典编码后体积骤减，查询时还能直接对 ID 做等值比较。它是列式存储最常用、收益最大的编码之一。

```text
字典编码要点：
1. 映射 —— 每个 distinct 值分配一个整数 ID，数据存 ID 而非原值
2. 低基数收益大 —— 重复值越多，ID 越短，压缩比越高
3. 等值过滤加速 —— 比较整数 ID 比比较字符串快
4. 高基数失效 —— 每值都不同时字典本身很大，收益低
```

```text
原始列：beijing, ny, beijing, sh, beijing, ny
字典：  beijing=0, ny=1, sh=2
编码后：[0, 1, 0, 2, 0, 1]

存储 = 字典表（3 个值）+ 6 个小整数
原值存储 = 6 个字符串
```

## RLE

RLE（Run-Length Encoding，游程编码）把连续重复的值压缩成「值 + 重复次数」。经过排序或字典编码后，列里会形成大量连续相同的值（或 ID），RLE 压缩效果极佳。它常与字典编码组合：先字典编码，再对 ID 序列做 RLE，是 Parquet/ORC 的标准流程。

```text
RLE 要点：
1. 原理 —— 连续相同值记作 (值, 次数)，如 0 0 0 0 -> (0, 4)
2. 依赖排序 —— 排序后相同值聚集，RLE 收益最大化
3. 与字典组合 —— 字典编码后的 ID 序列天然适合 RLE
4. 失效场景 —— 值完全随机无连续重复时，RLE 可能反而膨胀
```

```text
原始：[0, 0, 0, 0, 1, 1, 2, 2, 2, 2, 2]
RLE： (0,4), (1,2), (2,5)   —— 11 个值压成 3 组
```

## Bit Packing

位打包（Bit Packing）用「刚好够用的位数」存整数，而不是固定 32/64 位。例如列里所有值都在 0~7 之间（字典编码后的 ID），只需 3 bit 就能存一个值，空间直接降到原来的 1/10。它常与 RLE 组合成「RLE + Bit Packing」混合编码（Parquet 的 RLE_DICTIONARY 就是这种组合）。

```text
Bit Packing 要点：
1. 原理 —— 按当前值的最大范围定 bit 数，多个值打包进一个机器字
2. 收益 —— 值域小时（如字典 ID 0~255）用 8bit 存，省 75% 空间
3. 组合 —— 常与 RLE 组合：先 RLE 再对 run 长度/值做位打包
4. 编码计算 —— 需知道值的最大值（或按页动态确定 bit 宽度）
```

```text
值范围 0~7（3 bit 可表示）的 8 个值：
原始（32bit/个）：8 * 32 = 256 bit
位打包（3bit/个）：8 * 3 = 24 bit  —— 省 90%
```

## 压缩

压缩算法进一步减小存储体积，分通用压缩（Snappy/Zstd/Gzip/LZ4）和针对列式数据的专用编码组合。通用压缩里 Snappy/LZ4 快但压缩比一般，Zstd 平衡，Gzip 压缩比高但慢。列式存储通常「列内编码（字典/RLE/位打包）+ 通用压缩」两层叠加，才能达到 5~20 倍的压缩比。

```text
压缩算法权衡：
1. Snappy —— 速度快、CPU 低，压缩比一般（Spark 默认）
2. LZ4 —— 极快，解压最快，适合热数据
3. Zstd —— 压缩比与速度平衡好，逐渐成为主流默认
4. Gzip —— 压缩比高但慢，适合冷数据归档
```

```text
列式压缩的整体收益来源：
1. 列裁剪 —— 只存/读需要的列
2. 同列相似 —— 类型一致、值域集中，编码效率高
3. 字典 + RLE + 位打包 —— 针对数据特征的专用编码
4. 通用压缩 —— 在编码结果上再压一层
```

## 对象存储

对象存储（Object Storage）把数据作为「对象」存，用唯一 key 寻址，通过 HTTP API（GET/PUT/DELETE）访问，无目录树、无文件系统语义。它以「海量、低成本、高可用、强扩展」著称，是云上数据湖的默认底座（AWS S3、阿里 OSS、MinIO、GCS）。代价是延迟高、不支持原地修改（只能整体重写）、无 POSIX 语义。

```text
对象存储要点：
1. 对象寻址 —— key -> value，扁平命名空间，无目录层级（用前缀模拟）
2. 强扩展 —— 无限容量，自动分布到多台存储节点
3. 高可用 —— 内部多副本/纠删码，S3 保证 11 个 9 的持久性
4. 限制 —— 延迟较高（毫秒级），对象不可原地改，最终一致（部分场景）
```

```shell
# S3 风格对象存储操作（aws cli / mc）
aws s3 cp data.parquet s3://my-bucket/raw/data.parquet
aws s3 ls s3://my-bucket/raw/
aws s3 rm s3://my-bucket/raw/old.parquet
```

## 块存储

块存储（Block Storage）把存储以「固定大小块」暴露，通过 iSCSI/FC 协议挂载成块设备（如云硬盘 EBS），支持随机读写、低延迟，是数据库/虚拟机的底层存储。它类似「裸硬盘」，无文件语义，由上层文件系统管理。块存储性能好（低延迟随机 IO）但扩展性差（单卷容量有限、需 RAID/快照管理）。

```text
块存储要点：
1. 块设备 —— 以 block 为单位，随机读写、低延迟
2. 挂载使用 —— 格式化成文件系统后使用（ext4/xfs）
3. 适用 —— 数据库数据盘、虚拟机系统盘、需要低延迟随机 IO 的场景
4. 局限 —— 容量有限、跨节点共享难、扩展需上层配合
```

```text
块存储 vs 对象存储：
块存储 —— 低延迟、随机读写、容量有限、强一致（数据库盘）
对象存储 —— 高延迟、整对象读写、无限扩展、最终一致（数据湖）
```

## 分布式文件系统

分布式文件系统（DFS）把文件分布存储到多台机器，对外提供统一的文件系统接口（POSIX 或类 POSIX）。HDFS 是代表：大文件切块分布、元数据集中管理（NameNode）、副本容错。它介于块存储（提供文件语义）和对象存储（海量扩展）之间，是大数据「先落地」的经典存储层，如今逐步让位于对象存储 + 表格式。

```text
分布式文件系统要点：
1. 文件切块 —— 大文件切块分布到多节点，支持大文件顺序读写
2. 元数据分离 —— 元数据（目录/块映射）集中，数据分散
3. 副本容错 —— 每块多副本，坏节点自动恢复
4. 代表 —— HDFS、CephFS、GlusterFS
```

```text
HDFS 架构回顾（详见 07.2-HDFS）：
NameNode（元数据）+ DataNode（数据块）+ 客户端
文件 -> 块（128MB）-> 分布到 DataNode -> 3 副本
```

## 副本

副本（Replication）把同一份数据存多份，分布到不同节点，用冗余换容错和读性能：一个副本坏了，其他副本顶上，系统自动补副本。副本是最简单直观的容错手段，代价是存储放大（3 副本 = 3 倍空间）。它是 HDFS、Kafka、多数分布式系统的默认容错机制。

```text
副本要点：
1. 冗余容错 —— N 副本可容忍 N-1 个副本同时故障
2. 存储放大 —— 副本数 x 空间，成本高
3. 读扩展 —— 多副本可分散读压力
4. 自动恢复 —— 副本损坏/节点宕机时系统自动补副本
```

```text
副本 vs 纠删码：
副本 —— 简单、读写快、容错直观，但 3 倍空间
纠删码 —— 1.4~1.5 倍空间，省存储，但计算开销大、恢复慢
选择 —— 热数据/小文件用副本，冷数据/大文件用纠删码
```

## 纠删码

纠删码（Erasure Coding，EC）把数据分成 k 个数据块，计算出 m 个校验块，共 k+m 块分布存储，任意丢失 m 块都能恢复原数据。典型 RS(6,3) 用 6 个数据块 + 3 个校验块，存储开销 1.5 倍（vs 3 副本的 3 倍），却能容忍 3 块丢失。代价是恢复时要读多块重算，CPU 和网络开销大。适合冷数据、大文件的低成本容错。

```text
纠删码要点：
1. 原理 —— k 数据块 + m 校验块，丢失 <= m 块可恢复
2. 存储效率 —— 开销 = (k+m)/k，如 RS(6,3) = 1.5x，远优于 3 副本
3. 恢复代价 —— 恢复需读多块参与计算，CPU/网络开销大
4. 适用 —— 冷数据、归档、大文件（HDFS 3.x、对象存储默认）
```

```text
RS(6,3) 示例：
6 个数据块 + 3 个校验块 = 9 块，分布到 9 个节点
任意 3 块损坏都能恢复，存储开销仅 1.5 倍
```

```shell
# HDFS 纠删码策略
hdfs ec -listPolicies
hdfs ec -enablePolicy -policy RS-6-3-1024k
hdfs ec -setPolicy -path /data/cold -policy RS-6-3-1024k
```

## 数据局部性

数据局部性（Data Locality）指「让计算靠近数据」——把任务调度到数据所在的节点执行，避免跨网络拉数据。数据量大时网络是瓶颈，移动计算比移动数据便宜得多。它是 MapReduce/HDFS 时代调度器的核心原则，也是现代缓存、数据分区设计的基本考量。

```text
数据局部性要点：
1. 移动计算 —— 计算任务调度到数据所在节点，减少网络传输
2. 层级 —— 同节点 > 同机架 > 跨机架，越近越快
3. 缓存友好 —— 热点数据就近缓存，减少重复拉取
4. 与分片结合 —— 数据按访问模式分区，让相关数据同处一地
```

```text
数据局部性的层次（延迟递增）：
进程内内存 -> 本机内存 -> 本机磁盘 -> 同机架磁盘 -> 跨机架网络 -> 跨数据中心
```

## 容错

容错（Fault Tolerance）是分布式系统在节点故障、网络故障、磁盘损坏时仍能正常工作的能力。手段分数据层（副本、纠删码、快照）和计算层（任务重试、检查点、幂等写）。核心假设是「故障是常态而非异常」，系统必须把故障当成设计输入，而非事后补救。

```text
容错要点：
1. 副本/纠删码 —— 数据层容错，坏盘/宕机不丢数据
2. 任务重试 —— 计算层容错，失败任务自动重跑（幂等性前提）
3. 检查点 —— 长任务定期保存状态，失败从检查点恢复
4. 心跳检测 —— 及时探测故障节点，触发恢复
```

```text
容错的分层：
存储层 —— 副本/纠删码/快照（防数据丢失）
计算层 —— 重试/检查点/幂等（防任务失败）
调度层 —— 心跳/故障转移（防节点不可用）
```

## 应用场景实战

### 场景一：为数据湖选择存储与容错策略

```text
需求：数据湖存 PB 级数据，冷热分层，控成本

方案：
1. 存储底座 —— 对象存储（S3/OSS），无限扩展、低成本
2. 表格式 —— Iceberg + Parquet，列式 + 压缩（Zstd）
3. 冷数据 —— 对象存储开启纠删码（省空间）
4. 热数据 —— 高副本 + 本地缓存（提升读性能）
5. 容错 —— 对象存储内部多副本/EC，Iceberg 保证元数据一致性
```

### 场景二：列式编码压缩的收益估算

```text
原始 CSV 日志：100 GB（纯文本，无压缩）
转 Parquet + 列式编码后：
1. 列裁剪 —— 只存分析需要的 20 列（原 100 列）
2. 字典编码 —— 低基数列（城市/状态）压成 ID
3. RLE + 位打包 —— ID 序列压缩
4. Zstd 压缩 —— 在编码结果上再压一层
最终：约 8~12 GB，压缩比 10:1 左右，查询只读相关列
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分析型数据用列式（Parquet/ORC）+ Zstd 压缩，兼顾压缩比和速度
2. 冷数据/大文件用纠删码省存储，热数据用小副本数保性能
3. 数据湖底座用对象存储，别用块存储存海量文件
4. 数据库数据盘用块存储（SSD），保证低延迟随机 IO
5. 任务调度优先数据局部性，把计算挪到数据所在节点
6. 容错设计默认「故障必然发生」，副本/重试/检查点都要配齐
7. 低基数列优先字典编码，高基数或随机值列谨慎（收益低）

### 踩坑记录

```text
坑 1：冷热数据不分，全部 3 副本
结论：存储成本暴涨，冷数据白白占 3 倍空间。
原因：一刀切 3 副本，没对冷数据用纠删码。
解法：冷数据切纠删码（RS-6-3），热数据才用多副本。

坑 2：高基数列强行字典编码
结论：字典表巨大，编码后体积反而更大，得不偿失。
原因：高基数列每个值都不同，字典编码无压缩收益还有字典开销。
解法：高基数列直接通用压缩，低基数列才用字典编码。

坑 3：对象存储当块存储用（频繁随机小更新）
结论：延迟高、成本高（每次改对象要整体重写）。
原因：对象存储不支持原地修改，语义不匹配随机更新负载。
解法：随机更新负载用块存储/数据库，对象存储只做整对象读写。

坑 4：忽略数据局部性导致网络打满
结论：任务跨节点大量拉数据，网络成为瓶颈，计算变慢。
原因：调度没考虑数据位置，计算和数据分离。
解法：调度器开启数据局部性优先，或数据分区贴合访问模式。

坑 5：纠删码用于频繁读写的热数据
结论：读取/恢复开销大，延迟升高。
原因：纠删码读要跨多块、恢复要重算，不适合低延迟热数据。
解法：热数据用副本，纠删码只用于冷数据/归档。
```
