## 概述

在线协作编辑器（如 Google Docs、Figma、飞书文档）让多人实时编辑同一份内容。技术上由三块拼成：渲染层（Canvas 或 DOM）、同步层（WebSocket）、一致性层（CRDT/OT 解决并发冲突），再加离线编辑与状态同步，实现「各自本地改、全局一致」。

```text
协作编辑器的三大支柱：
1. 渲染层 —— Canvas/DOM 呈现文档与选区
2. 同步层 —— WebSocket 实时广播操作
3. 一致性层 —— CRDT/OT 保证多端编辑最终一致
```

```text
编辑数据流：
本地编辑 → 生成操作 → 广播 → 对端应用 → 冲突合并 → 全局一致
```

## Canvas

Canvas 是协作编辑器（尤其是白板/图形类）的渲染基础，用 2D 上下文绘制图形、文字、路径。相比 DOM，Canvas 在大规模图形场景性能更好，但需要自己实现命中检测与重绘。

```js
// Canvas 绘制基础图形
const canvas = document.getElementById('board');
const ctx = canvas.getContext('2d');

function drawShape(shape) {
  ctx.beginPath();
  if (shape.type === 'rect') {
    ctx.rect(shape.x, shape.y, shape.w, shape.h);
  } else if (shape.type === 'circle') {
    ctx.arc(shape.x, shape.y, shape.r, 0, Math.PI * 2);
  }
  ctx.fillStyle = shape.color;
  ctx.fill();
}

// 图形列表驱动重绘
function redraw(shapes) {
  ctx.clearRect(0, 0, canvas.width, canvas.height);
  shapes.forEach(drawShape);
}
```

```text
Canvas 要点：
1. 无状态 —— 每次重绘都是全量清空再画
2. 命中检测 —— 用坐标判断点到哪个图形
3. 高频重绘用 requestAnimationFrame 或脏区域优化
4. 高 DPI 屏要处理 devicePixelRatio 缩放
```

## WebSocket

WebSocket 承载协作操作的双向广播。与聊天不同，协作编辑器传输的是「操作」（operation）而非整份文档，通过操作增量同步，避免整篇文档反复传输。

```js
// 操作广播与接收
class CollabSocket {
  sendOp(op) {
    this.ws.send(JSON.stringify({ type: 'op', op }));
  }
  onMessage(data) {
    if (data.type === 'op') {
      applyRemoteOp(data.op);   // 对端操作本地应用
    }
  }
}
```

```text
协作 WebSocket 要点：
1. 传输操作增量，而非整份文档
2. 操作按序或带版本号，处理乱序
3. 低延迟优先，协作对延迟比聊天更敏感
4. 服务端做操作广播与持久化
```

## CRDT/OT

CRDT 与 OT 是解决「多人同时编辑冲突」的两大算法。OT（操作变换）按操作顺序做变换合并；CRDT（无冲突复制数据类型）用数学性质（交换律、结合律）让任意顺序的操作收敛到同一结果，天然支持离线与去中心化。

```js
// 简化版 CRDT：字符序列（RGA 思想）
// 每个字符带唯一 id + 前驱引用，插入位置由 id 定位而非下标
const doc = [
  { id: 'a1', char: 'H', prev: null },
  { id: 'b2', char: 'i', prev: 'a1' },
];

// 插入时只需引用前驱 id，两处并发插入互不影响
function insert(doc, char, prevId, newId) {
  const idx = doc.findIndex(c => c.id === prevId);
  doc.splice(idx + 1, 0, { id: newId, char, prev: prevId });
}
```

```text
CRDT vs OT：
1. OT 需要中心服务器做变换，顺序敏感
2. CRDT 天然可交换，适合离线与 P2P
3. 文本用 RGA/序列 CRDT，图/表格用 Map/Register CRDT
4. 现代协作工具（Figma、飞书）多采用 CRDT
```

## Cursor

Cursor 是协作者的远程光标（或选区），让用户看到别人正在编辑的位置。每个协作者把自己的光标位置（含名字、颜色）广播出去，其他端渲染成带颜色的标记。

```js
// 远程光标渲染（以文本编辑器为例）
const remoteCursors = [
  { userId: 'u2', name: '李四', color: '#f00', position: 42 },
];

function renderCursors(editor) {
  remoteCursors.forEach(c => {
    const coords = editor.indexToCoords(c.position);
    drawCursor(coords, c.color, c.name);
  });
}
```

```text
Cursor 要点：
1. 光标用 userId 标识，位置随编辑实时广播
2. 每个用户分配唯一颜色，便于区分
3. 光标位置用字符偏移（index）而非像素
4. 断线/离开时清除对应光标
```

## Presence

Presence 在协作场景表示「谁在编辑这个文档」，常与会话列表、头像组、在线状态结合展示。用户进入/离开文档时广播，客户端维护参与人集合。

```js
// 参与人列表维护
function handlePresence(participants) {
  setParticipants(participants);
  // 右上角头像组展示
  renderAvatarStack(participants.map(p => ({
    name: p.name, color: p.color, online: p.online,
  })));
}
```

```text
Presence 要点：
1. 文档级参与人集合，实时增删
2. 展示为头像组 + 在线状态点
3. 编辑活跃度可辅助「谁在改哪段」
4. 与 Cursor 结合，光标带用户名
```

## Conflict Resolution

冲突解决是协作编辑的核心命题：两人同时改同一处时如何合并。CRDT 用算法保证自动收敛，OT 用变换合并；业务层还需处理「删改冲突」「权限冲突」等边界。

```js
// 简化 OT 变换：两个并发操作交换顺序后结果一致
function transform(op1, op2) {
  // 若两者位置冲突，调整偏移
  if (op1.type === 'insert' && op2.type === 'insert' && op1.pos < op2.pos) {
    return { ...op2, pos: op2.pos + op1.text.length };
  }
  return op2;
}
```

```text
冲突解决策略：
1. CRDT 自动收敛，无需中心协调
2. OT 靠变换函数保证各端一致
3. 版本冲突用「以服务端为准 + 冲突提示」
4. 权限冲突（只读 vs 编辑）按权限优先
```

## Offline

离线编辑让用户在无网络时继续编辑，恢复网络后再同步。CRDT 天然支持离线（本地先改，联网后合并）；OT 则需离线队列暂存操作。

```js
// 离线操作队列
const offlineQueue = [];

function localEdit(op) {
  applyOp(op);                    // 本地立即生效
  if (!isOnline) {
    offlineQueue.push(op);        // 离线暂存
    localStorage.setItem('offline-ops', JSON.stringify(offlineQueue));
  } else {
    sendOp(op);
  }
}

// 恢复网络后重放队列
async function flushQueue() {
  while (offlineQueue.length) {
    sendOp(offlineQueue.shift());
  }
  localStorage.removeItem('offline-ops');
}
```

```text
离线要点：
1. 本地编辑立即生效，操作持久化到本地
2. 恢复网络后按序重放操作
3. 重放可能触发冲突，交给一致性层合并
4. 本地缓存文档快照，离线也能打开
```

## Sync

Sync 是文档状态在本地与服务端之间的同步机制，分「实时同步」（在线时操作即时广播）与「增量同步」（离线后补差）。核心是版本号/游标定位差异，只同步变更部分。

```js
// 版本号驱动的增量同步
async function syncDocument() {
  const local = { doc: currentDoc, version: localVersion };
  const res = await fetch('/api/doc/sync', {
    method: 'POST',
    body: JSON.stringify({ version: localVersion }),
  });
  const { ops, latestVersion } = await res.json();
  ops.forEach(applyRemoteOp);      // 应用服务端的新操作
  localVersion = latestVersion;
}
```

```text
Sync 要点：
1. 版本号/游标定位差异，只传增量
2. 实时同步 + 定时增量同步兜底
3. 同步冲突交给一致性层，不覆盖对端
4. 同步状态可视化（已同步/同步中/离线）
```

## 应用场景实战

### 场景一：多人白板图形同步

```js
// 图形白板：本地画 + 广播操作 + 对端重放
function addShape(shape) {
  const op = { type: 'add', shape };
  applyOp(op);            // 本地立即画
  collab.sendOp(op);      // 广播
}

function applyRemoteOp(op) {
  if (op.type === 'add') {
    shapes.push(op.shape);
    redraw(shapes);       // 重放对端操作
  }
}
```

### 场景二：远程光标实时追踪

```js
// 本地光标移动时广播位置，对端渲染
editor.on('selectionChange', throttle(() => {
  const pos = editor.getCursorPosition();
  collab.send({ type: 'cursor', userId: me.id, pos });
}, 50));

collab.on('cursor', ({ userId, pos }) => {
  const color = userColor(userId);
  drawRemoteCursor(pos, color);   // 渲染带颜色的远程光标
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一致性层优先选 CRDT，天然支持离线与去中心化
2. 操作带唯一 id 与版本号，处理乱序与重复
3. 光标位置用字符偏移，渲染时再转坐标
4. 离线操作入队持久化，联网后按序重放
5. 高频操作（光标/选区）节流广播，降低带宽
6. 重绘用脏区域或 rAF 优化，避免全量重绘卡顿

### 踩坑记录

```text
坑 1：用「整篇文档」同步而非操作增量
结论：多人编辑时反复传全量文档，卡顿且易覆盖。
原因：没有操作粒度的增量同步。
解法：传输操作（op），对端增量应用。

坑 2：光标用像素坐标而非字符偏移
结论：对方缩放/换行后光标位置错位。
原因：像素坐标依赖渲染布局，不稳定。
解法：用字符偏移（index）表示位置，渲染时转换。

坑 3：离线重放覆盖他人修改
结论：恢复网络后旧操作覆盖了别人的新编辑。
原因：直接全量覆盖，没有走一致性合并。
解法：重放操作交给 CRDT/OT 合并，而非整体覆盖。

坑 4：未处理并发插入导致字符乱序
结论：两人同时插入，文本顺序错乱。
原因：用数组下标定位插入位置，下标并发下失效。
解法：用 CRDT 的 id 引用定位，或用 OT 变换调整偏移。

坑 5：高频同步未节流
结论：光标移动等高频事件把带宽打满。
原因：每次位置变化都立即广播。
解法：光标/选区节流（如 50ms），内容操作才即时广播。
```
