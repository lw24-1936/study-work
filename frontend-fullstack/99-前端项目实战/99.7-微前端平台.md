## 概述

微前端把大型前端应用拆成多个可独立开发、独立部署的子应用，由一个主应用（Host）统一编排。它解决了巨石应用「团队协作难、发布互相阻塞、技术栈难升级」的问题，代价是引入运行时协调与隔离的复杂度。

```text
微前端的核心概念：
1. Host —— 主应用（基座），负责编排与挂载子应用
2. Remote —— 子应用（微应用），独立开发部署
3. Module Federation —— Webpack 模块联邦，运行时共享模块
4. Routing —— 路由分发到对应子应用
5. 隔离 —— 依赖共享 + CSS 隔离 + 状态隔离
```

```text
微前端架构：
Host（基座）── 路由分发 ──> Remote A / Remote B / Remote C
                共享依赖 / 统一认证 / 统一监控
```

## Host

Host 是微前端的基座应用，负责整体布局（导航、壳）、子应用加载与卸载、全局资源与公共能力（认证、监控、主题）。子应用通过注册接口接入基座。

```js
// 基座注册并挂载子应用
import { registerApplication, start } from 'single-spa';

registerApplication({
  name: '@shop/order',
  app: () => import('@shop/order'),       // 子应用入口
  activeWhen: ['/order'],                  // 匹配路由时激活
});

registerApplication({
  name: '@shop/user',
  app: () => import('@shop/user'),
  activeWhen: ['/user'],
});

start();
```

```text
Host 职责：
1. 子应用生命周期管理（加载/挂载/卸载）
2. 全局布局与导航壳
3. 公共能力下沉：认证、监控、主题、埋点
4. 版本与灰度：控制加载哪个版本的子应用
```

## Remote

Remote 是独立开发的子应用，拥有自己的仓库、构建、发布节奏与团队。它通过暴露约定的生命周期（bootstrap/mount/unmount）或模块入口接入基座。

```js
// 子应用暴露生命周期（single-spa 风格）
export async function bootstrap() { /* 初始化 */ }
export async function mount(props) {
  render(props.container);                 // 挂载到基座提供的容器
}
export async function unmount() {
  destroy();                               // 清理 DOM 与监听
}
```

```text
Remote 要点：
1. 独立仓库、独立 CI/CD、独立版本
2. 暴露统一生命周期接口
3. 不依赖具体基座实现，可移植
4. 技术栈可独立（但建议统一以降低维护成本）
```

## Module Federation

Module Federation（模块联邦）是 Webpack 5 的运行时模块共享方案，让应用在运行时从远程加载模块，同时共享依赖（React、Vue 等）避免重复打包。它是实现微前端的现代主流方案。

```js
// 基座（Host）的 webpack 配置
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      remotes: {
        order: 'order@http://localhost:3001/remoteEntry.js',
        user: 'user@http://localhost:3002/remoteEntry.js',
      },
      shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
    }),
  ],
};

// 子应用（Remote）配置
// new ModuleFederationPlugin({
//   name: 'order',
//   filename: 'remoteEntry.js',
//   exposes: { './OrderApp': './src/OrderApp' },
//   shared: { react: { singleton: true } },
// });
```

```text
Module Federation 要点：
1. 运行时按需加载远程模块，无需整体部署
2. shared + singleton 保证依赖只加载一份
3. 支持版本协商，处理依赖版本不一致
4. 相比 iframe/qiankun 更轻，但隔离需自己处理
```

## Routing

微前端路由负责把 URL 路径分发到对应子应用。基座持有「路由表」，匹配到某子应用的路径时激活并挂载它；子应用内部管理自己的子路由。

```js
// 基座路由分发
const routes = [
  { path: '/order/*', app: 'order' },
  { path: '/user/*', app: 'user' },
];

function matchRoute(pathname) {
  return routes.find(r => pathname.startsWith(r.path.split('*')[0]));
}

// 子应用内部路由（相对路径，独立管理）
// <BrowserRouter basename="/order">
//   <Route path="/list" element={<OrderList />} />
//   <Route path="/:id" element={<OrderDetail />} />
// </BrowserRouter>
```

```text
微前端路由要点：
1. 基座负责顶层分发，子应用管理内部子路由
2. 用 basename/前缀避免路由冲突
3. 路由切换时正确挂载/卸载子应用
4. 状态保持：切走再切回是否恢复现场
```

## Shared Dependencies

共享依赖让多个子应用复用同一份 React/Vue/组件库，避免重复加载、减少体积、保证实例一致（Hooks 上下文不能跨实例）。核心是 singleton + 版本协商。

```js
// shared 配置：singleton 保证全局唯一实例
shared: {
  react: { singleton: true, requiredVersion: '^18.0.0' },
  'react-dom': { singleton: true, requiredVersion: '^18.0.0' },
  '@company/ui': { singleton: true },
}
```

```text
共享依赖要点：
1. singleton 依赖全局唯一，避免多实例
2. requiredVersion 声明版本范围，不匹配时降级或告警
3. 共享依赖升级需各子应用协同
4. 共享库尽量薄，减少版本耦合
```

## CSS Isolation

CSS 隔离防止子应用样式互相污染：A 应用的全局样式不能影响 B 应用。方案有 CSS Modules、Shadow DOM、命名空间前缀、样式运行时隔离（如 qiankun 的实验性隔离）。

```js
// 方案一：CSS Modules（构建期隔离，最常用）
// Button.module.css 生成唯一类名
import styles from './Button.module.css';
// <button className={styles.btn}>...</button>

// 方案二：Shadow DOM（运行时隔离）
const host = document.createElement('div');
const shadow = host.attachShadow({ mode: 'open' });
shadow.innerHTML = `<style>${appStyles}</style>${appTemplate}`;
container.appendChild(host);
```

```text
CSS 隔离要点：
1. CSS Modules 最省心，构建期自动加作用域
2. Shadow DOM 彻底隔离，但组件穿透与全局样式麻烦
3. 命名空间前缀适合存量项目
4. 全局设计令牌（Token）走基座统一下发
```

## Authentication

微前端的认证需要统一：用户登录一次，所有子应用共享登录态。方案是基座持有 Token（Cookie/内存），子应用通过共享状态或统一 SDK 获取，避免各自维护登录。

```js
// 基座统一认证，子应用通过共享上下文读取
const AuthContext = createContext(null);

function Host() {
  const auth = useAuth();          // 基座统一登录
  return (
    <AuthContext.Provider value={auth}>
      <RemoteApp />
    </AuthContext.Provider>
  );
}

// 子应用读取
function OrderPage() {
  const { user, token } = useContext(AuthContext);
  return <div>欢迎，{user.name}</div>;
}
```

```text
认证要点：
1. 登录态基座统一管理，子应用只读
2. Token 存 HttpOnly Cookie 或基座内存，避免各子应用重复存储
3. 子应用接口请求统一带认证头
4. 退出登录基座统一处理，通知所有子应用
```

## Monitoring

微前端监控需要覆盖「基座 + 各子应用」的错误、性能与用户行为，且能定位到具体子应用。方案是基座注入统一监控 SDK，子应用上报时带上应用标识。

```js
// 统一监控：错误上报带应用标识
function reportError(error, appName) {
  monitor.send({
    type: 'error',
    app: appName,              // 标识来自哪个子应用
    message: error.message,
    stack: error.stack,
    url: location.href,
  });
}

// 各子应用接入
window.addEventListener('error', e => reportError(e.error, 'order'));
window.addEventListener('unhandledrejection', e => reportError(e.reason, 'order'));
```

```text
监控要点：
1. 错误、性能、埋点都带上 app 标识
2. 基座统一接入监控 SDK，子应用复用
3. 跨子应用链路（如跳转）可追踪
4. 监控数据按子应用维度聚合分析
```

## 应用场景实战

### 场景一：qiankun 主从应用注册

```js
// qiankun 基座注册微应用
import { registerMicroApps, start } from 'qiankun';

registerMicroApps([
  {
    name: 'order',
    entry: '//localhost:3001',
    container: '#subapp-container',
    activeRule: '/order',
  },
  {
    name: 'user',
    entry: '//localhost:3002',
    container: '#subapp-container',
    activeRule: '/user',
  },
]);

start();
```

### 场景二：子应用间通信（全局事件总线）

```js
// 基座提供全局事件总线，子应用间解耦通信
class EventBus {
  constructor() { this.map = new Map(); }
  on(type, fn) {
    (this.map.get(type) || this.map.set(type, []).get(type)).push(fn);
  }
  emit(type, payload) {
    (this.map.get(type) || []).forEach(fn => fn(payload));
  }
}

window.__appBus = new EventBus();

// 子应用 A 发布
window.__appBus.emit('cart:updated', { count: 3 });
// 子应用 B 订阅
window.__appBus.on('cart:updated', ({ count }) => updateBadge(count));
```

## 最佳实践与踩坑记录

### 最佳实践

1. 只有「独立团队 + 独立部署」需求时才上微前端，避免过度设计
2. 共享依赖配 singleton，避免多实例导致的 Hook 失效
3. CSS 用 CSS Modules 做构建期隔离，省心可靠
4. 认证、监控、埋点等公共能力下沉基座统一提供
5. 子应用暴露统一生命周期接口，与基座解耦
6. 路由按前缀划分，子应用内部用 basename 管理

### 踩坑记录

```text
坑 1：共享依赖未设 singleton
结论：React 多实例，Hooks 上下文失效、状态丢失。
原因：每个子应用打包了一份 React，实例不共享。
解法：shared 里配 singleton: true 强制单例。

坑 2：子应用全局样式互相污染
结论：A 应用的全局 CSS 覆盖了 B 应用的样式。
原因：未做 CSS 隔离。
解法：CSS Modules / 命名空间 / Shadow DOM 隔离。

坑 3：路由切换后子应用状态丢失
结论：切走再切回，表单填写内容全没了。
原因：子应用被卸载销毁，状态没有保持。
解法：用 keep-alive 或状态持久化，恢复现场。

坑 4：微前端滥用导致复杂度爆炸
结论：团队被运行时协调、版本、调试问题拖垮。
原因：规模不大却强行微前端，收益低于成本。
解法：先评估团队与发布诉求，小团队单体优先。

坑 5：错误定位不到具体子应用
结论：线上报错只看到基座堆栈，不知哪个子应用出的问题。
原因：监控上报没带应用标识。
解法：统一监控 SDK，错误/性能/埋点都带 app 标识。
```
