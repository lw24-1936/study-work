## 概述

实时聊天系统（IM）的核心是「低延迟双向通信 + 消息可靠投递」。WebSocket 承载实时通道，配合消息模型、在线状态（Presence）、已读回执、离线消息、断线重连等机制，才能构建出体验完整的聊天应用。

```text
聊天系统的关键机制：
1. 实时通道 —— WebSocket 双向长连接
2. 消息模型 —— 会话、消息、已读、回执
3. 可靠性 —— 离线消息补发、断线重连、消息去重
4. 体验增强 —— 在线状态、通知、文件、Emoji 表情
```

```text
消息流转：
发送方 → WebSocket → 服务端 → 推送给接收方 → 已读回执回流
```

## WebSocket

WebSocket 是浏览器与服务器之间的全双工长连接，握手基于 HTTP 升级，之后以帧为单位双向传输数据，延迟远低于 HTTP 轮询。它承载聊天消息的实时收发。

```js
// WebSocket 客户端封装
class ChatSocket {
  constructor(url) {
    this.ws = new WebSocket(url);
    this.ws.onopen = () => console.log('已连接');
    this.ws.onmessage = (e) => this.handleMessage(JSON.parse(e.data));
    this.ws.onclose = () => this.scheduleReconnect();
    this.ws.onerror = (e) => console.error('连接错误', e);
  }

  send(type, payload) {
    if (this.ws.readyState === WebSocket.OPEN) {
      this.ws.send(JSON.stringify({ type, payload }));
    }
  }

  handleMessage(msg) {
    switch (msg.type) {
      case 'message': this.onMessage?.(msg.payload); break;
      case 'presence': this.onPresence?.(msg.payload); break;
      case 'receipt': this.onReceipt?.(msg.payload); break;
    }
  }
}
```

```text
WebSocket 要点：
1. 连接状态 readyState：CONNECTING/OPEN/CLOSING/CLOSED
2. 消息用 JSON 序列化，type 字段区分消息类型
3. 长连接需要心跳保活，避免被中间设备断开
4. 消息有序但可能重复，客户端要按 id 去重
```

## Presence

Presence 是在线状态管理，展示用户「在线 / 离线 / 离开」等状态。它靠心跳 + 服务端状态维护实现，用户上下线时广播给相关方。

```js
// 在线状态渲染
const PRESENCE_COLOR = {
  online: '#22c55e',
  away: '#f59e0b',
  offline: '#9ca3af',
};

function PresenceDot({ status }) {
  return <span className="dot" style={{ background: PRESENCE_COLOR[status] }} />;
}

// 客户端定时发心跳，服务端据此判断在线
setInterval(() => socket.send('heartbeat', { ts: Date.now() }), 30000);
```

```text
Presence 要点：
1. 心跳超时未收到即判定离线
2. 状态变更广播给「关心该用户」的客户端
3. 支持「在线 / 离开 / 离线」多级状态
4. 用户量大时心跳频率与后端压力要权衡
```

## Message

消息是聊天的基本单元，包含唯一 id、会话 id、发送方、内容类型（文本/图片/文件）、时间戳、状态。消息模型要支持单聊、群聊与多设备同步。

```js
// 消息数据结构
const message = {
  id: 'msg_1001',           // 全局唯一，用于去重与排序
  conversationId: 'conv_1', // 所属会话
  senderId: 'u_1',
  type: 'text',             // text / image / file / system
  content: '你好',
  timestamp: Date.now(),
  status: 'sent',           // sending / sent / delivered / read / failed
};

// 消息列表按时间排序
messages.sort((a, b) => a.timestamp - b.timestamp);
```

```text
消息模型要点：
1. 全局唯一 id，用于去重（断线重连可能收到重复消息）
2. status 跟踪发送生命周期
3. 会话（conversation）聚合消息，列表页展示最近会话
4. 本地缓存 + 服务端同步，支持多端一致
```

## Offline Message

离线消息解决「接收方不在线时消息不丢」的问题：服务端把消息暂存，接收方上线后拉取补发。客户端用「最后同步游标」记录已收到的位置。

```js
// 上线后拉取离线消息
async function syncOfflineMessages() {
  const lastSeq = localStorage.getItem('last_seq') || 0;
  const res = await fetch(`/api/messages?since=${lastSeq}`);
  const { messages, latestSeq } = await res.json();
  appendMessages(messages);
  localStorage.setItem('last_seq', String(latestSeq));  // 更新游标
}
```

```text
离线消息要点：
1. 用序号/游标做增量拉取，避免全量重拉
2. 消息去重：以消息 id 为准，重复则丢弃
3. 离线期间的消息按原时间顺序插入会话
4. 服务端保留一定窗口的离线消息，超期归档
```

## Notification

通知是聊天的触达手段，分站内通知（未读角标）与系统通知（Web Notifications API）。用户不在聊天页时，用系统通知提醒新消息。

```js
// 系统通知（需用户授权）
async function notify(message) {
  if (!('Notification' in window)) return;
  const permission = await Notification.requestPermission();
  if (permission === 'granted') {
    new Notification(message.senderName, {
      body: message.content,
      icon: message.senderAvatar,
    });
  }
}
```

```text
通知要点：
1. 请求授权时机要恰当，别一进来就弹授权
2. 未读角标实时更新，读后清零
3. 页面在前台时用站内提醒，后台才用系统通知
4. 通知点击后跳转到对应会话
```

## File Upload

聊天中的文件（图片/文档/视频）先上传到对象存储，再发送文件元信息（URL、类型、大小）作为消息内容。大文件需支持分片上传与进度展示。

```js
// 图片消息：先上传再发消息
async function sendImage(file, conversationId) {
  const form = new FormData();
  form.append('file', file);
  const res = await fetch('/api/upload', { method: 'POST', body: form });
  const { url } = await res.json();

  socket.send('message', {
    conversationId,
    type: 'image',
    content: url,           // 消息内容只存 URL
    meta: { name: file.name, size: file.size },
  });
}
```

```text
文件上传要点：
1. 大文件分片上传，支持断点续传
2. 上传进度实时反馈
3. 图片生成缩略图，消息里先展示缩略图
4. 文件类型与大小做白名单校验，防恶意上传
```

## Emoji

Emoji 表情是聊天消息的常见组成部分，通过表情选择器快速插入 Unicode Emoji 字符或自定义表情（图片/短代码）。渲染时需处理不同平台的显示一致性。

```js
// 表情选择器：插入表情到输入框
const emojiList = [
  { name: 'smile', code: 'U+1F600' },
  { name: 'heart', code: 'U+2764' },
];

function insertEmoji(code, inputRef) {
  const emoji = String.fromCodePoint(parseInt(code.replace('U+', ''), 16));
  const input = inputRef.current;
  const start = input.selectionStart;
  input.value = input.value.slice(0, start) + emoji + input.value.slice(input.selectionEnd);
  input.focus();
}
```

```text
Emoji 表情要点：
1. 用 Unicode 码点转义展示，正文中不直接书写真实表情字符
2. 自定义表情用短代码（如 :smile:）映射到图片
3. 输入时做联想补全，如输入冒号触发表情搜索
4. 消息渲染时解析并替换表情占位符
```

## Read Receipt

已读回执（Read Receipt）让发送方知道消息被对方看到，是聊天的关键体验。单聊常见「已读/未读」，群聊常展示「已读人数」。实现靠接收方在查看消息时回发已读事件。

```js
// 收到消息并进入会话时回发已读
function markRead(conversationId, lastMessageId) {
  socket.send('receipt', { conversationId, lastMessageId });
  // 本地同步已读状态
  updateMessages(conversationId, msg =>
    msg.id <= lastMessageId ? { ...msg, status: 'read' } : msg
  );
}
```

```text
已读回执要点：
1. 回执只标记「到某个消息 id 为止已读」
2. 群聊已读用「已读人数」而非回执风暴
3. 已读状态用乐观更新，失败再回滚
4. 回执频率可节流，避免消息量大时刷屏
```

## Reconnect

断线重连是 IM 的可靠性基石。网络抖动、切换网络、后台唤醒都可能导致连接断开，客户端要用「指数退避 + 心跳超时」策略自动重连，并在重连后同步状态。

```js
// 指数退避重连
class ReconnectManager {
  constructor() { this.attempt = 0; }

  schedule(onReconnect) {
    const delay = Math.min(1000 * 2 ** this.attempt, 30000); // 1s 起，封顶 30s
    this.attempt += 1;
    setTimeout(() => {
      onReconnect();
    }, delay);
  }

  reset() { this.attempt = 0; }   // 连上后重置
}
```

```text
重连要点：
1. 指数退避，避免断线风暴
2. 心跳超时判定断开，主动触发重连
3. 重连成功后重新拉取离线消息、同步 Presence
4. 页面可见性变化（切回前台）时检查并重连
```

## 应用场景实战

### 场景一：会话列表 + 未读角标

```js
// 收到消息更新会话列表与未读计数
function handleNewMessage(msg) {
  setConversations(prev => prev.map(c => {
    if (c.id !== msg.conversationId) return c;
    const unread = isActive(c.id) ? 0 : c.unread + 1;  // 当前会话不累计
    return { ...c, lastMessage: msg, unread };
  }));
}
```

### 场景二：消息发送生命周期（乐观更新）

```js
// 乐观更新：先本地展示，再按服务端回执更新状态
async function sendMessage(conversationId, content) {
  const tempId = `local_${Date.now()}`;
  const msg = { id: tempId, conversationId, content, status: 'sending' };
  appendMessage(msg);                       // 立即上屏

  socket.send('message', { tempId, conversationId, content });
  // 收到服务端 ack 后：把 tempId 换成真实 id，status → sent
  // 收到对方已读回执后：status → read
  // 发送失败：status → failed，展示重试按钮
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 消息全局唯一 id，客户端按 id 去重
2. 断线重连用指数退避，封顶延迟
3. 离线消息按游标增量拉取，避免全量
4. 发送用乐观更新，失败展示重试而非丢消息
5. 文件先上传取 URL，消息里只传元信息
6. 心跳保活，及时探测断线

### 踩坑记录

```text
坑 1：断线重连后消息重复
结论：重连补发导致同一消息显示两次。
原因：离线消息补发与实时推送重叠，没有去重。
解法：消息以全局唯一 id 去重，存在即跳过。

坑 2：未读计数在活跃会话里误涨
结论：正在看的会话还在累计未读，角标不消失。
原因：只判「收到消息就 +1」，没判当前会话是否活跃。
解法：当前活跃会话不累计未读，直接标记已读。

坑 3：WebSocket 长时间无消息被断开
结论：连接被中间网络设备静默断开，收不到消息。
原因：没有心跳，空闲连接被 NAT/代理回收。
解法：定期发心跳包，超时未回则主动重连。

坑 4：重连风暴
结论：服务端故障时大量客户端同时重连，把服务压垮。
原因：所有客户端固定间隔重试，时间集中。
解法：指数退避 + 随机抖动，分散重连时间。

坑 5：消息发送未做失败处理
结论：网络失败时消息凭空消失，用户以为发了。
原因：只做乐观上屏，没处理失败回滚。
解法：失败标记 status=failed，提供重试按钮。
```
