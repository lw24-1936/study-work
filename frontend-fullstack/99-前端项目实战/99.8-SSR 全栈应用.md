## 概述

SSR 全栈应用让前端框架（Next.js/Nuxt）同时承担服务端渲染与 API 服务，把「渲染 + 数据 + 接口」整合到一个框架里。它兼顾 SEO 与首屏性能，并提供 SSR/SSG/ISR 多种渲染模式，是内容型、电商型应用的主流选择。

```text
SSR 全栈应用的能力：
1. 渲染模式 —— SSR 实时渲染 / SSG 构建时渲染 / ISR 增量再生成
2. 服务端能力 —— API 路由、数据库访问、缓存
3. 交付优化 —— CDN、SEO、边缘部署
```

```text
渲染模式选择：
动态数据、强实时 → SSR
静态内容、少更新 → SSG
内容较多、定期更新 → ISR
```

## Next.js/Nuxt

Next.js（React）与 Nuxt（Vue）是两大 SSR 全栈框架，提供文件路由、渲染模式、数据获取、API 路由等开箱能力。它们都支持「文件即路由」，约定式开发，降低配置成本。

```text
Next.js 项目结构：
app/
  page.tsx          # 首页
  blog/[slug]/page.tsx  # 动态路由
  api/users/route.ts  # API 路由
```

```js
// Nuxt 项目结构
// pages/index.vue —— 首页
// pages/blog/[slug].vue —— 动态路由
// server/api/users.ts —— API 路由
export default defineEventHandler((event) => {
  return { users: [] };
});
```

```text
框架选择：
1. React 团队用 Next.js，Vue 团队用 Nuxt
2. 文件路由 + 约定式开发
3. 内置渲染模式与数据获取
4. 支持边缘/Serverless 部署
```

## SSR

SSR（Server-Side Rendering）在请求到达时于服务端渲染出完整 HTML 返回，首屏直接可见，搜索引擎可直接抓取。适合数据实时变化的页面（商品详情、个性化首页）。

```jsx
// Next.js SSR：每次请求服务端取数渲染
export default async function ProductPage({ params }) {
  const product = await fetchProduct(params.id);   // 服务端直连数据
  return (
    <div>
      <h1>{product.title}</h1>
      <p>{product.price}</p>
    </div>
  );
}

// Pages Router 写法
// export async function getServerSideProps() {
//   const product = await fetchProduct(params.id);
//   return { props: { product } };
// }
```

```text
SSR 要点：
1. 每次请求都实时渲染，数据最新
2. 首屏 HTML 完整，SEO 与首屏性能好
3. 服务端压力大，需缓存与扩容
4. 用户相关/强实时页面用 SSR
```

## SSG

SSG（Static Site Generation）在构建时预渲染成静态 HTML，部署到 CDN 上秒开。适合内容几乎不变的页面（博客、文档、落地页），性能与成本最优。

```jsx
// Next.js SSG：构建时生成静态页
export async function generateStaticParams() {
  const posts = await fetchPosts();               // 构建时取数
  return posts.map(p => ({ slug: p.slug }));      // 预生成所有路径
}

export default function BlogPost({ params }) {
  const post = getPost(params.slug);              // 静态数据
  return <article>{post.content}</article>;
}
```

```text
SSG 要点：
1. 构建时渲染，产出纯静态 HTML
2. 部署到 CDN，性能与成本最优
3. 内容更新需重新构建
4. 内容型、营销型页面首选 SSG
```

## ISR

ISR（Incremental Static Regeneration）是 SSG 与 SSR 的折中：页面静态生成，但可设置「重新生成间隔」，到期后后台增量更新，无需全量重新构建。适合内容较多、定期更新的场景。

```jsx
// Next.js ISR：设置重新生成间隔
export const revalidate = 60;   // 60 秒后下次请求触发后台再生成

export default async function NewsList() {
  const news = await fetchNews();                 // 构建时取数 + 定时刷新
  return (
    <ul>{news.map(n => <li key={n.id}>{n.title}</li>)}</ul>
  );
}
```

```text
ISR 要点：
1. 首访返回静态页，到期后台再生成
2. 无需重新构建整个站点
3. revalidate 控制更新频率
4. 支持按需再生成（on-demand ISR）
```

## RSC

RSC（React Server Components）让组件默认在服务端渲染，可直接访问数据库，且不产生客户端 JS。客户端组件（需交互）用 'use client' 标记，形成服务端/客户端混合组件树，减少发送到浏览器的 JS 体积。

```jsx
// Server Component（默认，服务端执行，可直连数据库）
async function ProductList() {
  const products = await db.query('SELECT * FROM products');
  return <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}

// Client Component（需交互，加 'use client'）
'use client';
import { useState } from 'react';
function AddToCart() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>加入购物车 {count}</button>;
}
```

```text
RSC 要点：
1. 服务端组件默认，可访问数据库与文件系统
2. 客户端组件加 'use client'，处理交互
3. 服务端组件不打包进客户端 bundle，减小体积
4. 混合树：服务端组件嵌套客户端组件
```

## API

SSR 全栈框架内置 API 路由，让前后端共用一套代码部署，前端直接调用同源接口，省去跨域与额外的后端服务。适合中小型应用的服务端逻辑。

```js
// Next.js API 路由
// app/api/users/route.ts
import { NextResponse } from 'next/server';

export async function GET() {
  const users = await db.user.findMany();
  return NextResponse.json({ users });
}

export async function POST(request: Request) {
  const body = await request.json();
  const user = await db.user.create({ data: body });
  return NextResponse.json({ user }, { status: 201 });
}
```

```text
API 要点：
1. 文件路由映射接口，约定式组织
2. 同源部署，省去 CORS 配置
3. 适合轻量服务端逻辑，复杂逻辑可拆独立服务
4. 支持中间件（鉴权、限流、日志）
```

## Database

SSR 全栈应用可直接在服务端组件或 API 路由里访问数据库，用 ORM（Prisma、Drizzle）或数据库客户端。数据库访问只在服务端发生，不暴露连接信息给客户端。

```js
// Prisma ORM 访问数据库
import { PrismaClient } from '@prisma/client';
const prisma = new PrismaClient();

// 在 Server Component 或 API 里查询
export async function getUsers() {
  return prisma.user.findMany({
    where: { active: true },
    orderBy: { createdAt: 'desc' },
  });
}
```

```text
数据库访问要点：
1. 只在服务端访问，连接串不进客户端
2. ORM 类型安全，查询结果有完整类型
3. 查询注意 N+1 问题，用 include/join 优化
4. 连接池管理，避免连接泄漏
```

## Cache

缓存是 SSR 全栈应用的性能关键，分多层：数据缓存（服务端缓存查询结果）、页面缓存（整页缓存）、组件缓存（React cache 去重）。合理缓存能显著降低数据库压力与响应时间。

```js
// React cache：同一次请求内去重
import { cache } from 'react';

export const getUser = cache(async (id: string) => {
  return db.user.findUnique({ where: { id } });
});

// Next.js 数据缓存（fetch 默认缓存）
const res = await fetch('https://api.example.com/data', {
  next: { revalidate: 3600 },   // 1 小时缓存
});
```

```text
缓存分层：
1. 组件缓存 —— React cache 去重重复请求
2. 数据缓存 —— 查询结果按时间/失效缓存
3. 页面缓存 —— 整页缓存到 CDN 或边缘
4. 客户端缓存 —— 浏览器缓存静态资源
```

## CDN

CDN 把内容分发到离用户最近的边缘节点，加速静态资源与可缓存的页面。SSG/ISR 产出的静态页天然适合放 CDN，SSR 页面也可配合边缘缓存。

```text
CDN 加速的内容：
1. 静态资源 —— JS/CSS/图片，长缓存
2. SSG/ISR 页面 —— 缓存到边缘，秒开
3. 可缓存的 SSR 响应 —— 按 Cache-Control 缓存
```

```js
// 设置缓存头，让 CDN 缓存可缓存的响应
export async function GET() {
  const data = await fetchData();
  return NextResponse.json(data, {
    headers: { 'Cache-Control': 'public, s-maxage=3600' },  // CDN 缓存 1 小时
  });
}
```

```text
CDN 要点：
1. 静态资源长缓存 + 指纹命名
2. 静态页部署到 CDN 边缘
3. 缓存头（Cache-Control）控制 CDN 行为
4. 按需失效（purge）更新内容
```

## SEO

SEO 是 SSR 全栈应用的核心价值之一。通过服务端输出完整 HTML、动态 meta、结构化数据、sitemap，让搜索引擎能抓取并理解页面内容。

```jsx
// Next.js Metadata API 动态 SEO
import type { Metadata } from 'next';

export async function generateMetadata({ params }): Promise<Metadata> {
  const product = await fetchProduct(params.id);
  return {
    title: product.title,
    description: product.summary,
    openGraph: {
      title: product.title,
      images: [product.image],
    },
  };
}
```

```text
SEO 要点：
1. 完整 HTML 进搜索结果，别全靠 JS
2. 动态 title/description/meta 按页面定制
3. Open Graph 优化社交分享
4. sitemap.xml + canonical 规范收录
```

### 场景一：博客站点（SSG + 动态路由）

```jsx
// 构建时预生成所有博客页
export async function generateStaticParams() {
  const posts = await getPosts();

    <article>
      <h1>{post.title}</h1>
      <div>{post.content}</div>
    </article>
  );
}
```

### 场景二：带缓存的商品列表 API

```js
// API 路由 + 缓存头
export async function GET() {
  const products = await db.product.findMany({ take: 50 });
  return NextResponse.json(
    { products },
    { headers: { 'Cache-Control': 'public, s-maxage=300, stale-while-revalidate=600' } }
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 按数据更新频率选渲染模式：SSR/SSG/ISR 各就各位
2. 数据库只服务端访问，连接串绝不进客户端
3. 分层缓存（组件/数据/页面/CDN），逐级降低压力
4. 静态页放 CDN，缓存头控制边缘缓存
5. 动态 meta 与结构化数据做 SEO
6. 服务端组件访问数据，客户端组件只处理交互

### 踩坑记录

```text
坑 1：服务端组件里用了浏览器 API
结论：报 window/localStorage is not defined。
原因：服务端组件没有浏览器环境。
解法：浏览器 API 放客户端组件（'use client'）或 useEffect 里。

坑 2：数据库连接串打进客户端 bundle
结论：数据库凭证泄露，可被直接访问。
原因：在客户端组件里引用了数据库连接。
解法：数据库访问只在服务端组件/API 里，用 'server-only' 保护。

坑 3：SSR 页面未缓存导致服务端过载
结论：高流量下服务端被打爆。
原因：每次请求都实时渲染，无缓存。
解法：数据缓存 + CDN 缓存 + 合理用 ISR/SSG。

坑 4：全站 SSG 导致内容更新滞后
结论：发布新内容要等重新构建才可见。
原因：内容型页面全用 SSG，更新成本高。
解法：频繁更新页面用 ISR，配合 on-demand 再生成。

坑 5：忽视缓存失效导致脏数据
结论：改了数据但页面还是旧的。
原因：缓存没有正确失效。
解法：明确缓存失效策略，更新时 purge/重新验证。
```
