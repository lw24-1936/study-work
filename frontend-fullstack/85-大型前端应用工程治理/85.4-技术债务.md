## 概述

技术债务是过去为了赶进度而做的「权宜之计」长期积累下来的代价：重复代码、坏味道、过时依赖、纠缠的旧系统。债务不会自动消失，只会在复利下越滚越大——每次改动都要在旧代码上绕路。治理债务的核心是「持续识别、有计划偿还、别借新债」。

```text
技术债务的形态：
1. Refactoring —— 还债手段：持续重构，改善结构不改行为
2. Legacy —— 债务本体：难改、难测、难懂的旧代码
3. Migration —— 还债路径：把旧系统迁移到新方案
4. Deprecation —— 还债信号：标记过时，引导淘汰
5. Compatibility —— 还债约束：迁移期间保持兼容，不中断业务
```

```text
债务闭环：
识别债务 → 评估代价 → 排期偿还 → 重构/迁移 → 验证 → 防止新债
```

## Refactoring

Refactoring（重构）在不改变外部行为的前提下，改善代码的内部结构：提炼函数、消除重复、简化条件、拆分大模块。重构是偿还债务最日常的手段，靠小步、有测试保护的改动持续进行。

```ts
// 重构前：长函数 + 重复逻辑
function processOrder(order) {
  let total = 0;
  for (const item of order.items) {
    total += item.quantity * item.price;
  }
  if (order.vip) {
    total = total * 0.9;
  }
  if (total > 1000) {
    total = total - 50;
  }
  return total;
}
```

```ts
// 重构后：提炼小函数，语义清晰、可单测
function calcSubtotal(items: OrderItem[]): number {
  return items.reduce((sum, item) => sum + item.quantity * item.price, 0);
}

function applyVipDiscount(total: number, isVip: boolean): number {
  return isVip ? total * 0.9 : total;
}

function applyThresholdCoupon(total: number): number {
  return total > 1000 ? total - 50 : total;
}

function processOrder(order: Order) {
  const subtotal = calcSubtotal(order.items);
  const discounted = applyVipDiscount(subtotal, order.vip);
  return applyThresholdCoupon(discounted);
}
```

```text
重构的纪律：
1. 有测试保护 —— 先写测试，重构后测试全绿才算成功
2. 小步快跑 —— 一次只改一件事，可随时回退
3. 行为不变 —— 重构不改变外部行为，只改内部结构
```

## Legacy

Legacy（遗留代码）是没有测试、文档缺失、结构混乱、维护者已离开的旧代码。遗留代码的可怕之处不在「旧」，而在「不可知」——没人敢改，因为不知道改了会炸哪里。治理遗留代码的第一步是「补上安全网」。

```text
# 遗留代码的特征
1. 无测试 —— 改了不知道会不会坏
2. 无文档 —— 不知道当初为什么这么写
3. 高耦合 —— 改一处牵动全身
4. 技术栈过时 —— 依赖老旧、无人维护
```

```ts
// 治理遗留代码：先加「特征化测试」锁定现有行为
// 在重构前，为遗留函数补上测试，把当前行为固化成基准
describe('legacy processOrder', () => {
  it('keeps current behavior for vip order', () => {
    const order = { vip: true, items: [{ quantity: 2, price: 100 }] };
    expect(processOrder(order)).toBe(180); // 锁定现状，再重构
  });
});
```

```text
治理遗留代码的策略：
1. 先补测试 —— 特征化测试锁定现有行为，建立安全网
2. 再小改 —— 每次只动一小块，测试保护下渐进重构
3. 缓兵之计 —— 用适配层隔离，先止血再慢慢替换
```

## Migration

Migration（迁移）是把旧系统/旧技术栈搬到新方案的工程化过程：从旧框架迁到新框架、从 JS 迁到 TS、从老打包器迁到新打包器。迁移的关键是「分步、可回退、可并行」，用 Strangler 模式逐步替换，而非一次性推倒重来。

```text
# Strangler Fig 模式：新旧并存，逐步替换
1. 搭好新系统的骨架，与旧系统并行运行
2. 新需求只在新系统实现
3. 旧功能按优先级逐个搬移
4. 旧系统使用量归零后下线
```

```text
# 迁移路线图（以 JS → TS 为例）
阶段 1：允许 .js 与 .ts 共存，配好 tsconfig allowJs
阶段 2：新代码全部用 TS，旧 JS 逐步改造
阶段 3：核心模块优先迁移，边迁边跑类型检查
阶段 4：全量 TS 化后，开启 strict 并关闭 allowJs
```

```json
// tsconfig：渐进式迁移的配置
{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": false,
    "strict": false,
    "noImplicitAny": false
  },
  "include": ["src"]
}
```

## Deprecation

Deprecation（废弃标记）为过时的 API、模块、依赖打上「即将移除」的标签，给使用者缓冲时间。废弃是迁移的前奏——先声明意图，再给替代方案，最后才真正移除。

```ts
/**
 * @deprecated 自 2.0.0 起废弃，请使用 `fetchUserV2`。
 * 计划于 3.0.0 移除。
 */
export function fetchUserV1(id: string) {
  console.warn('[deprecated] fetchUserV1 已废弃，请使用 fetchUserV2。');
  return fetchUserV2(id);
}

export function fetchUserV2(id: string) {
  // 新实现
}
```

```js
// 用 ESLint 规则禁止使用已废弃 API
module.exports = {
  rules: {
    'deprecation/deprecation': 'warn', // 引用 @deprecated 即告警
  },
};
```

```text
废弃的配套动作：
1. 标记 —— JSDoc @deprecated + 运行时告警 + 文档
2. 替代 —— 明确给出替代方案与对照
3. 节奏 —— 公布移除版本，留足迁移窗口
4. 统计 —— 监控使用量，归零后删除
```

## Compatibility

Compatibility（兼容性）在迁移和演进过程中保持新旧共存、不中断业务。它要求新方案在一段时间内兼容旧接口、旧数据、旧调用方，让迁移可以分步进行，而不是「一夜切换」。

```ts
// 兼容层：新函数兼容旧调用方的两种签名
type UserArgs = { id: string } | string;

export function getUser(args: UserArgs) {
  const id = typeof args === 'string' ? args : args.id;
  // 统一处理，旧传 string、新传对象都能用
  return fetchUser(id);
}
```

```ts
// 版本化 API：保留旧字段，平滑过渡
interface UserResponse {
  id: string;
  name: string;         // 新字段
  username?: string;    // 旧字段，保留兼容期，之后移除
}
```

```text
兼容性策略：
1. 双签名 —— 新旧调用方式并存，过渡期后收敛
2. 版本化 —— 接口带版本，旧版本保留到使用量归零
3. 数据兼容 —— 新代码能读旧数据，必要时做迁移脚本
4. 灰度切换 —— 新方案按比例放量，验证稳定后全量
```

## 应用场景实战

### 场景一：为遗留模块补测试后安全重构

```ts
// 1. 遗留代码：无测试的旧函数
export function legacyPrice(items) {
  var sum = 0;
  for (var i = 0; i < items.length; i++) {
    sum = sum + items[i].q * items[i].p;
  }
  return sum;
}
```

```ts
// 2. 先写特征化测试，锁定现有行为
import { legacyPrice } from './legacy';

test('legacyPrice keeps behavior', () => {
  expect(legacyPrice([{ q: 2, p: 10 }, { q: 1, p: 5 }])).toBe(25);
});

// 3. 测试保护下重构为现代写法
export function legacyPrice(items: Array<{ q: number; p: number }>) {
  return items.reduce((sum, item) => sum + item.q * item.p, 0);
}
// 测试仍然通过，说明行为未变
```

### 场景二：Strangler 模式渐进迁移旧模块

```js
// 新路由优先匹配，未迁移的路径回落到旧系统
const newRouter = new Router();
newRouter.get('/users', newUserHandler);      // 已迁移
newRouter.get('/orders', newOrderHandler);    // 已迁移

// 兜底：剩余路径仍走旧系统
newRouter.use((req, res) => {
  legacyApp.handle(req, res); // 旧系统继续服务未迁移的模块
});

// 迁移进度：每搬一个模块，就在 newRouter 里加一条路由
```

## 最佳实践与踩坑记录

### 最佳实践

1. 偿还债务前先补测试，特征化测试锁定现有行为
2. 重构小步进行，一次只改一件事，测试全绿再继续
3. 迁移用 Strangler 模式，新旧并存、逐步替换、可回退
4. 废弃走完整流程：标记 → 指引 → 时间表 → 监控 → 删除
5. 迁移期保留兼容层，业务不中断，使用量归零后再收尾
6. 建立债务看板，量化债务、排期偿还，防止无限滚雪球

### 踩坑记录

```text
坑 1：没测试就重构，改完不知道坏没坏
结论：重构后线上出现隐藏 bug，还说不清是不是重构引入的。
原因：遗留代码没有测试保护，重构失去安全网。
解法：重构前先写特征化测试，把当前行为固化成基准，再动代码。

坑 2：一次性推倒重来，迁移成了无底洞
结论：整个系统同时重写，迁移进行了一年还没上线，业务停滞。
原因：想一步到位，忽略了渐进迁移的可控性。
解法：Strangler 模式逐步替换，新需求走新系统，旧模块按优先级迁移。

坑 3：废弃 API 直接删除，调用方大面积报错
结论：旧 API 一夜消失，依赖方集体编译失败，被迫回滚。
原因：没给废弃过渡期，也没监控调用量。
解法：先 @deprecated 标记 + 告警 + 文档，监控使用量归零后再移除。

坑 4：迁移期没做兼容层，新旧数据对不上
结论：新系统读不了旧数据，切换后出现数据缺失或格式错误。
原因：忽略了新旧数据格式差异，没有数据迁移与兼容方案。
解法：新代码兼容旧数据格式，必要时写迁移脚本，切换前验证数据完整。

坑 5：只口头提「以后重构」，债务从没排期
结论：技术债务越积越多，重构永远排在「以后」，最终压垮开发效率。
原因：债务没有量化、没有进排期，成了空头承诺。
解法：建债务看板，按影响面评估优先级，每迭代固定分配还债额度。
```
