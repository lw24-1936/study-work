## 概述

组件治理管理的是「组件库从诞生到退役」的全生命周期：如何统一设计、如何登记与检索、如何约束 API、如何废弃旧组件、如何迁移使用者。组件是前端复用最基本的单元，组件治理做好了，新页面用现成组件拼装即可；做不好，就会沉淀出一堆重复、不一致、没人维护的「野组件」。

```text
组件治理五个环节：
1. Design System —— 统一设计语言，组件有共同底座
2. Component Registry —— 组件登记造册，可检索、可发现
3. API Standard —— 组件接口统一规范，可预测、可组合
4. Deprecation —— 旧组件有序废弃，不默默消失
5. Migration —— 使用者平滑迁移，升级不痛苦
```

```text
组件生命周期：
设计 → 开发 → 登记 → 使用 → 维护 → 废弃 → 迁移/下线
```

## Design System

Design System（设计系统）是组件治理的底座，用统一的 token、规范和组件库保证所有组件「长在同一个体系里」。它是「单一事实来源」：颜色、间距、字号、圆角都有统一定义，组件只是这些定义的组合。

```json
// 设计 token：组件共用的原子变量
{
  "color": {
    "primary": "#4f46e5",
    "primaryHover": "#4338ca",
    "text": "#18181b",
    "border": "#e4e4e7"
  },
  "radius": { "sm": "4px", "md": "8px", "lg": "12px" },
  "space": { "xs": "4px", "sm": "8px", "md": "16px", "lg": "24px" }
}
```

```tsx
// 组件基于 token 构建，保证一致性
import { tokens } from '@app/design-system';

export function Input({ size = 'md', disabled = false }) {
  return (
    <input
      style={{
        padding: tokens.space[size],
        borderRadius: tokens.radius.md,
        border: `1px solid ${tokens.color.border}`,
      }}
      disabled={disabled}
    />
  );
}
```

```text
设计系统对治理的价值：
1. 一致性 —— 所有组件共享同一套 token 与规范
2. 可维护 —— 改一个 token，全局组件样式同步更新
3. 可扩展 —— 新组件复用现有 token，不必重新定义
```

## Component Registry

Component Registry（组件注册表）给每个组件建立档案：它叫什么、做什么、怎么用、谁维护、状态如何。注册表让组件可被发现、可检索，避免「不知道有现成的，又写了一个」。

```text
# 组件注册表字段（以 Storybook/文档站承载）
1. 组件名与分类 —— 如 Button / Form / DataDisplay
2. 用途说明 —— 一句话说清它解决什么问题
3. Props API —— 完整的 props 说明与默认值
4. 示例 —— 至少一个可交互示例
5. 维护者 —— 谁负责这个组件
6. 状态 —— stable / beta / deprecated
```

```json
// 组件元数据登记（供文档站与工具消费）
{
  "name": "Button",
  "category": "Actions",
  "description": "触发操作的基础按钮",
  "status": "stable",
  "owner": "@ui-team",
  "since": "2.0.0",
  "props": {
    "variant": { "type": "'primary' | 'secondary' | 'ghost'", "default": "primary" },
    "size": { "type": "'sm' | 'md' | 'lg'", "default": "md" }
  }
}
```

```text
注册表治理要点：
1. 单一入口 —— 文档站/Storybook 是组件的唯一发现渠道
2. 状态可见 —— stable/beta/deprecated 一目了然
3. 有归属 —— 每个组件有明确的维护者，不沦落为孤儿组件
```

## API Standard

API Standard（接口规范）统一组件的对外接口设计：props 命名、事件约定、受控/非受控、ref 转发等。统一的 API 让组件可预测、可组合，使用者学一个就全会，降低心智负担。

```text
# 组件 API 统一规范示例
1. 命名 —— props 用 camelCase，布尔 props 用 is/has/can 前缀
2. 事件 —— onChange 而非 onInput/onTextChange，事件回调名统一
3. 受控 —— 有 value 就必须有 onChange，支持受控与非受控
4. 样式 —— 统一用 className/style，不散落自定义前缀
```

```tsx
// 遵循统一 API 规范的组件
interface SelectProps {
  value?: string;
  defaultValue?: string;
  options: Array<{ label: string; value: string }>;
  disabled?: boolean;
  placeholder?: string;
  onChange?: (value: string) => void;
}

export function Select({ value, defaultValue, options, onChange }: SelectProps) {
  const [inner, setInner] = useState(defaultValue ?? '');
  const current = value ?? inner;
  const isControlled = value !== undefined;

  function handleChange(next: string) {
    if (!isControlled) setInner(next);
    onChange?.(next);
  }

  return (
    <select value={current} onChange={(e) => handleChange(e.target.value)}>
      {options.map((o) => (
        <option key={o.value} value={o.value}>
          {o.label}
        </option>
      ))}
    </select>
  );
}
```

```text
API 规范的价值：
1. 可预测 —— 看到 value/onChange 就知道是受控组件
2. 可组合 —— 统一的约定让组件能任意嵌套组合
3. 低心智 —— 团队只需学一套约定，而非每个组件一个套路
```

## Deprecation

Deprecation（废弃）是旧组件的「有序退场」：标记为 deprecated、给出替代方案、设定下线时间表。废弃不等于立刻删除——要给使用者充分的迁移时间和明确的指引。

```ts
// 废弃标记：运行时告警 + JSDoc 说明 + 文档标注
/**
 * @deprecated 自 3.0.0 起废弃，请使用 `Button` 的 `variant="primary"` 替代。
 * 计划于 4.0.0 移除。
 */
export function PrimaryButton(props: ButtonProps) {
  if (process.env.NODE_ENV !== 'production') {
    console.warn(
      '[deprecated] PrimaryButton 已废弃，请改用 <Button variant="primary">。',
    );
  }
  return <Button variant="primary" {...props} />;
}
```

```text
废弃流程：
1. 标记 —— JSDoc @deprecated + 运行时告警 + 文档置灰
2. 指引 —— 明确给出替代组件与迁移路径
3. 时间表 —— 公布下线版本，倒计时提醒
4. 观察 —— 监控废弃组件使用量，降到零再删除
```

## Migration

Migration（迁移）帮助使用者从旧组件平滑切换到新组件：提供迁移文档、自动化 codemod、兼容层，让升级「可执行、可验证、可回退」。

```js
// codemod：用 jscodeshift 批量改写旧组件用法
// PrimaryButton → Button variant="primary"
export default function transformer(file, api) {
  const j = api.jscodeshift;
  const root = j(file.source);

  root.findJSXElements('PrimaryButton').forEach((path) => {
    // 改标签名
    path.node.name.name = 'Button';
    // 加 variant 属性
    const attr = j.jsxAttribute(
      j.jsxIdentifier('variant'),
      j.stringLiteral('primary'),
    );
    path.node.attributes.push(attr);
  });

  return root.toSource();
}
```

```bash
# 批量执行 codemod
npx jscodeshift -t migrate-primary-button.js src/
# 迁移后跑全量测试验证
npm test
```

```text
迁移策略：
1. 文档先行 —— 写清「旧 → 新」对照表与步骤
2. codemod 提速 —— 机械化改动交给脚本批量处理
3. 兼容过渡 —— 新旧并存一段时间，旧组件内部转调新组件
4. 验证闭环 —— 迁移后跑测试、看监控，确认无回归
```

## 应用场景实战

### 场景一：建立带状态标记的组件注册表

```tsx
// 组件注册表：集中登记，配合文档站展示状态
export const componentRegistry = {
  Button: {
    status: 'stable',
    owner: '@ui-team',
    description: '触发操作的基础按钮',
  },
  PrimaryButton: {
    status: 'deprecated',
    owner: '@ui-team',
    description: '已废弃，使用 Button variant="primary"',
    replacement: 'Button',
  },
  LegacyTable: {
    status: 'beta',
    owner: '@data-team',
    description: '新一代表格，替代旧 Table',
  },
};

// 文档站按 status 渲染徽标，使用者一眼识别可用性
for (const [name, meta] of Object.entries(componentRegistry)) {
  console.log(`${name} [${meta.status}] — ${meta.description}`);
}
```

### 场景二：旧组件废弃 → 迁移 → 下线的完整流程

```bash
# 1. 标记废弃：JSDoc + 运行时告警（见上文 Deprecation 代码）

# 2. 批量迁移：codemod 自动改写
npx jscodeshift -t migrate-primary-button.js src/

# 3. 验证迁移结果：全量测试 + 类型检查
npm test && npx tsc --noEmit

# 4. 监控废弃组件使用量归零后，在下一个大版本删除
grep -r "PrimaryButton" src/   # 输出为空即安全删除
```

## 最佳实践与踩坑记录

### 最佳实践

1. 组件统一基于 Design Token 构建，改 token 全局生效
2. 组件登记造册，文档站是唯一发现渠道，状态一目了然
3. 统一组件 API 规范，value/onChange、事件命名全校一致
4. 废弃要走流程：标记 → 指引 → 时间表 → 监控 → 删除
5. 提供 codemod 自动化迁移，机械改动交给脚本
6. 新旧组件兼容过渡一段时间，旧组件内部转调新组件

### 踩坑记录

```text
坑 1：旧组件一删了之，使用者大面积报错
结论：组件被直接删除，几十个页面 import 报错，被迫紧急回滚。
原因：没有废弃过渡期，删除前没通知、没监控使用量。
解法：先标记 deprecated，监控使用量归零后再删除，删除前发公告。

坑 2：每个团队各写一个 Button，组件库形同虚设
结论：设计系统里有一个 Button，业务里又出现十几个自定义 Button。
原因：组件不可发现，或文档不到位，开发者不知道有现成的。
解法：建立组件注册表 + 文档站，Code Review 强制优先使用库内组件。

坑 3：组件 API 不统一，一个组件一个套路
结论：有的组件 onChange 传值，有的传事件对象，使用者苦不堪言。
原因：没有统一的 API 规范，各组件各写各的。
解法：制定 API 标准并工具化检查，新组件不合规不通过评审。

坑 4：废弃只写了个注释，没人知道有替代品
结论：@deprecated 注释藏在代码里，使用者看不到，继续用旧组件。
原因：废弃信息没有触达使用者，文档也没更新。
解法：废弃信息同步到文档站、运行时告警、CHANGELOG，三处到位。

坑 5：迁移靠手工一个个改，又慢又容易错
结论：几百处旧组件用法手工替换，改错、漏改频繁。
原因：没有用 codemod 自动化，把机械劳动交给了人工。
解法：写 jscodeshift codemod 批量改写，配合测试验证，一键迁移。
```
