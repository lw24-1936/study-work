## 概述

依赖治理管理的是前端工程「引进来的一切」：直接依赖、传递依赖、版本、安全漏洞、许可证、以及它们最终对产物体积的影响。一个前端项目的 node_modules 动辄几百上千个包，治理的核心是「看得见、控得住、能追溯」——知道依赖了谁、版本是否合规、有没有漏洞、会不会把包打爆。

```text
依赖治理五件事：
1. Dependency Graph —— 看清依赖关系，找出重复与循环
2. Version Policy —— 锁定版本，控制升级节奏
3. Security Audit —— 扫描已知漏洞，阻断高危依赖
4. License Audit —— 检查许可证合规，避免法律风险
5. Bundle Budget —— 监控产物体积，防止包无限膨胀
```

```text
依赖生命周期：
引入 → 锁版本 → 审计（安全/许可证）→ 升级 → 淘汰
      ↑ 每一环都需要治理手段
```

## Dependency Graph

Dependency Graph（依赖图谱）描述一个包依赖了哪些包、哪些包又传递依赖了谁。可视化依赖图能发现重复依赖（同一个包多个版本）、异常大的依赖树、以及不该引入的重型依赖。

```bash
# 查看依赖树
npm ls --depth=2

# 找出同一个包的多版本（重复依赖）
npm ls lodash

# 用工具可视化依赖图
npx depcheck          # 找出未使用和缺失的依赖
npx madge --image graph.png src/   # 生成项目内部依赖图
```

```text
# npm ls 输出示例（发现 lodash 多版本）
app@1.0.0
├── lodash@4.17.21
└─┬ some-lib@2.0.0
  └── lodash@3.10.1   # 重复依赖，需要 dedupe
```

```text
依赖图谱治理要点：
1. 去重 —— 用 overrides/resolutions 统一重复包版本
2. 精简 —— depcheck 找出未使用依赖，及时清理
3. 可视化 —— 依赖图让「引了不该引的」无处遁形
```

## Version Policy

Version Policy（版本策略）规定依赖如何声明版本、如何升级。核心原则是「锁文件定版本、锁文件进仓库」：package.json 声明范围，lockfile 锁定确切版本，保证所有环境和 CI 安装完全一致。

```json
// package.json：版本范围声明
{
  "dependencies": {
    "react": "18.3.1",          // 精确版本
    "lodash": "^4.17.21",       // 兼容版本（4.x 内升级）
    "eslint": "~9.2.0"          // 补丁版本（9.2.x 内升级）
  },
  "engines": {
    "node": ">=20"
  }
}
```

```bash
# 版本策略落地
npm ci              # 按 lockfile 精确安装，CI 必用
npm outdated        # 查看可升级的依赖
npm update          # 按范围升级到兼容的最新版本
```

```text
版本策略的纪律：
1. lockfile 必须进版本库，CI 一律 npm ci/pnpm install --frozen-lockfile
2. 主版本升级单独评估 —— breaking change 要回归测试
3. 依赖升级走 PR —— 通过 CI 全量测试后再合并，而非随手 npm update
```

## Security Audit

Security Audit（安全审计）扫描依赖树中的已知安全漏洞（CVE），对高危漏洞阻断合并。npm 内置 audit，也可用 Snyk、Dependabot 等工具做持续监控与自动修复。

```bash
# npm 内置安全审计
npm audit                    # 列出漏洞
npm audit --audit-level=high # 高危漏洞返回非零，可作 CI 门槛
npm audit fix                # 自动修复可修复的漏洞
```

```yaml
# Dependabot 自动提 PR 升级有漏洞的依赖
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: 'npm'
    directory: '/'
    schedule:
      interval: 'weekly'
    open-pull-requests-limit: 10
```

```text
安全审计的要点：
1. 高危即阻断 —— audit-level=high 接入 CI，高危漏洞不合并
2. 自动修复 + 人工确认 —— audit fix 后要跑全量测试
3. 关注传递依赖 —— 漏洞往往藏在深层传递依赖里
```

## License Audit

License Audit（许可证审计）检查依赖的 License 是否与公司合规要求冲突。GPL 等「传染性」许可证可能要求开源衍生代码，商业项目要特别警惕；同时要识别未经许可的商用依赖。

```bash
# 用 license-checker 检查依赖许可证
npx license-checker --summary

# 只列出有问题的许可证（如 GPL）
npx license-checker --onlyAllow "MIT;ISC;Apache-2.0;BSD-3-Clause"
```

```text
# license-checker --summary 输出示例
MIT: 412
Apache-2.0: 38
ISC: 55
GPL-3.0: 2   # 需要法务评估的传染性许可证
```

```text
许可证审计要点：
1. 白名单机制 —— 明确允许的 License 清单，之外的告警
2. 关注传染性 —— GPL/AGPL 等可能要求开源衍生代码
3. 定期审计 —— 新依赖引入时自动检查，接入 CI
```

## Bundle Budget

Bundle Budget（产物预算）给打包产物体积设定上限，超出即告警或阻断，防止依赖越引越多、包越打越大。它把「性能红线」固化成 CI 门槛，让体积失控在合并前被发现。

```js
// webpack 的 performance 预算配置
module.exports = {
  performance: {
    maxEntrypointSize: 400_000, // 入口产物 400KB 上限
    maxAssetSize: 300_000,      // 单个资源 300KB 上限
    hints: 'error',             // 超出即报错
  },
};
```

```js
// 或用 size-limit 在 CI 里做预算断言
// package.json
{
  "size-limit": [
    {
      "path": "dist/*.js",
      "limit": "400 kB"
    }
  ]
}
```

```bash
# CI 里执行预算检查
npx size-limit
# 超出预算 → 构建失败，阻断合并
```

```text
Bundle Budget 的价值：
1. 防膨胀 —— 每次引入重依赖都会触发告警，倒逼评估
2. 可追溯 —— 体积增长有记录，能定位是哪个依赖导致
3. 与性能挂钩 —— 体积直接关系到首屏加载速度
```

## 应用场景实战

### 场景一：CI 里的依赖治理全流程

```yaml
# .github/workflows/deps.yml —— 依赖治理一体化流水线
name: Dependency Governance
on:
  pull_request:
  schedule:
    - cron: '0 2 * * 1' # 每周一凌晨定期审计

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm audit --audit-level=high          # 安全审计
      - run: npx license-checker --onlyAllow "MIT;ISC;Apache-2.0;BSD-3-Clause"  # 许可证审计
      - run: npx depcheck                          # 未使用依赖检查
      - run: npm run build
      - run: npx size-limit                        # 产物预算
```

### 场景二：用 overrides 统一重复依赖版本

```json
// package.json：强制全树使用同一个 lodash 版本
{
  "dependencies": {
    "lodash": "4.17.21"
  },
  "overrides": {
    "lodash": "4.17.21"
  }
}
```

```bash
# 统一后验证：全树只有一个 lodash 版本
npm ls lodash
# app@1.0.0
# └── lodash@4.17.21  (deduped)
```

## 最佳实践与踩坑记录

### 最佳实践

1. lockfile 进版本库，CI 一律按锁文件确定性安装
2. 安全审计设高危阻断，Dependabot 自动提升级 PR
3. 许可证白名单进 CI，传染性许可证单独评估
4. 产物预算设 error 级别，超出即阻断合并
5. 用 overrides/resolutions 统一重复依赖，缩小 node_modules
6. 依赖升级走 PR + 全量测试，禁止随手 npm update

### 踩坑记录

```text
坑 1：CI 用 npm install 导致依赖漂移
结论：CI 装的依赖和本地、生产不一致，出现「本地好好的 CI 挂了」。
原因：npm install 按范围重新解析，可能装到 lockfile 之外的新版本。
解法：CI 一律 npm ci（或 pnpm install --frozen-lockfile），按锁文件确定性安装。

坑 2：忽略了传递依赖里的高危漏洞
结论：直接依赖看着干净，漏洞藏在第三四层传递依赖里。
原因：只关注了直接依赖，没有看完整的依赖树。
解法：npm audit / Snyk 扫描整个依赖树，高危漏洞一视同仁阻断。

坑 3：引了 GPL 依赖，公司有法律风险
结论：商业闭源产品里引了 GPL 库，可能被迫开源衍生代码。
原因：引入依赖时没做许可证检查。
解法：许可证白名单进 CI，GPL/AGPL 等传染性许可证先过法务评估。

坑 4：体积预算只设了 warning，超了也没人管
结论：bundle 一年翻了三倍，预算形同虚设。
原因：performance.hints 设成 warning，不阻断合并。
解法：预算设 error 级别，超出即失败，倒逼每次引入重依赖都三思。

坑 5：depcheck 报告的一堆「未使用依赖」不敢删
结论：仓库里躺着一堆没人用的依赖，徒增体积和审计面。
原因：担心删除后某处动态引用报错，索性留着。
解法：depcheck 结果逐项确认，动态 require 的加 ignore 白名单，其余果断删除并全量回归。
```
