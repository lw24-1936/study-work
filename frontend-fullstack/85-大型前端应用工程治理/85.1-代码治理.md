## 概述

代码治理是大型前端工程里保证代码「长期可维护」的一整套制度与工具：用编码规范统一风格，用 Lint 和类型检查机器把关，用 Code Review 和架构评审人把关。治理的目标不是限制自由，而是让几百人写的代码看起来像「一个人写的」，且每一处变更都有人负责、有据可查。

```text
代码治理的分层：
1. Coding Standard —— 规范约定，统一风格与结构
2. Lint / Type Check —— 机器自动把关，把问题挡在提交前
3. Review —— 人把关，审查正确性与设计
4. Architecture Review —— 架构把关，守住长期演进方向
```

```text
治理闭环：
写代码 → 本地 Lint/类型检查 → 提交 → CI 校验 → Code Review → 合并
                                              ↑ 每一环都是闸门
```

## Coding Standard

Coding Standard（编码规范）是团队约定的一套代码风格与结构规则，覆盖命名、目录结构、导入顺序、注释、错误处理等。它让代码可预测、可阅读，是后续所有自动化检查的基础。

```text
# 前端编码规范示例（约定俗成）
1. 命名 —— 变量/函数用 camelCase，组件/类型用 PascalCase，常量用 UPPER_SNAKE
2. 目录 —— feature/domain/shared 分层，文件名与导出名一致
3. 导入顺序 —— 第三方 → 内部共享 → 相对路径，同类之间留空行
4. 错误处理 —— 不吞异常，catch 必须处理或重新抛出
```

```js
// 规范落地：用 ESLint + Prettier 把规范变成可执行规则
// .prettierrc.json
{
  "semi": true,
  "singleQuote": true,
  "printWidth": 100,
  "trailingComma": "all"
}
```

```text
规范的制定原则：
1. 少而精 —— 只规范真正影响质量的点，不搞形式主义
2. 可自动化 —— 能写成规则的都要工具化，不留「靠自觉」
3. 有依据 —— 每条规范都能解释「为什么」，而非「我觉得」
```

## Lint

Lint 用静态分析工具在代码运行前发现风格问题、潜在 bug、坏味道。前端常用 ESLint（JS/TS）、Stylelint（CSS）、Prettier（格式化）。Lint 的最大价值是「把问题挡在提交前」，配合 Git Hooks 和 CI 形成强制闸门。

```json
// package.json：统一 lint 脚本
{
  "scripts": {
    "lint": "eslint src --ext .ts,.tsx --max-warnings 0",
    "lint:style": "stylelint 'src/**/*.css'",
    "format": "prettier --write src",
    "format:check": "prettier --check src"
  }
}
```

```js
// .eslintrc 关键规则示例
module.exports = {
  extends: ['eslint:recommended', 'plugin:@typescript-eslint/recommended'],
  rules: {
    'no-unused-vars': 'error', // 未使用变量
    'no-console': 'warn',      // 生产代码禁 console
    'eqeqeq': ['error', 'always'], // 强制 ===
    '@typescript-eslint/no-explicit-any': 'error', // 禁止 any
  },
};
```

```text
Lint 治理要点：
1. --max-warnings 0 —— 警告也算失败，防止警告累积
2. 统一规则集 —— 团队共享一份 eslint-config，禁止各写各的
3. 增量检查 —— 大仓库全量 lint 慢，配合 lint-staged 只查改动
```

## Type Check

Type Check（类型检查）用 TypeScript 的静态类型系统在编译期发现类型错误，比 Lint 更深入——它验证的是「数据的形状是否正确」。类型检查能消除大量运行时才能暴露的 undefined、空值、类型不匹配问题。

```ts
// 类型检查能发现的错误示例
interface Order {
  id: string;
  items: OrderItem[];
  status: 'pending' | 'paid';
}

function shipOrder(order: Order): void {
  // order.total 不存在 → 编译期报错，而非运行时 undefined
  console.log(order.total);
}

function pay(order: Order) {
  // 传错类型 → 编译期报错
  return order.status === 'shipped';
}
```

```bash
# 类型检查命令：只做检查不产出文件
npx tsc --noEmit

# tsconfig 关键配置
# "strict": true      —— 开启所有严格检查
# "noUncheckedIndexedAccess": true —— 数组/索引访问结果可能为 undefined
```

```text
类型治理策略：
1. strict: true 起步 —— 严格模式是默认门槛
2. 禁止 any —— any 会让类型检查形同虚设，逐处消除
3. 类型进 CI —— tsc --noEmit 作为独立 CI 步骤，不过不合并
```

## Review

Code Review（代码评审）由同事在合并前审查代码的正确性、可读性、设计合理性。机器检查管「对不对」，人工评审管「好不好」——是否可读、是否过度设计、是否有隐藏的坑、是否符合团队约定。

```text
Code Review 关注点：
1. 正确性 —— 逻辑对不对，边界情况是否处理
2. 可读性 —— 命名、结构是否清晰，注释是否必要
3. 设计 —— 是否引入不必要的复杂度，是否有更简单方案
4. 规范 —— 是否符合编码规范与分层约定
5. 安全 —— 是否有注入、泄漏、越权等隐患
```

```text
# 评审的粒度与纪律
1. 小步提交 —— 单次 PR 控制在几百行内，便于评审
2. 明确描述 —— PR 说明「为什么改、改了什么、怎么验证」
3. 及时响应 —— 评审意见及时处理，缩短合并周期
4. 对事不对人 —— 评审针对代码，不针对作者
```

## Architecture Review

Architecture Review（架构评审）在更大的尺度上把关：新模块的引入、技术选型、跨模块改动、重大重构，都要经过架构层面的评审。它防止「局部最优、全局失控」——每个改动看起来都对，合起来却把架构带偏。

```text
# 架构评审的触发场景
1. 引入新框架/新依赖 —— 技术选型是否必要、是否有替代
2. 跨领域改动 —— 是否破坏了分层与边界
3. 重大重构 —— 目标架构是否清晰、迁移路径是否可行
4. 性能/安全敏感改动 —— 是否引入不可控风险
```

```text
# 架构评审的产物
1. 评审结论 —— 通过 / 有条件通过 / 驳回
2. 待办清单 —— 需要补齐的设计、测试、文档
3. ADR —— 重要决策沉淀成 Architecture Decision Record
```

## 应用场景实战

### 场景一：用 Husky + lint-staged 把检查挡在提交前

```bash
# 安装 Git Hooks 与增量检查工具
npm i -D husky lint-staged
npx husky init
```

```json
// package.json：lint-staged 只对暂存文件做检查
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.css": ["stylelint --fix"]
  }
}
```

```bash
# .husky/pre-commit：提交前自动执行增量检查
npx lint-staged
```

### 场景二：CI 里把类型检查设为合并门槛

```yaml
# .github/workflows/ci.yml
name: CI
on: pull_request

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm run lint           # Lint 不过不合并
      - run: npx tsc --noEmit       # 类型不过不合并
      - run: npm run format:check   # 格式不过不合并
```

## 最佳实践与踩坑记录

### 最佳实践

1. 规范、Lint、类型检查全部工具化，写入 CI 和 Git Hooks
2. 团队共享一份 eslint-config 和 tsconfig，杜绝各写各的
3. strict 模式起步，any 逐处消灭，类型检查作为合并硬门槛
4. PR 小步提交，单次改动控制在可评审的粒度
5. 重大改动、新技术引入必须走架构评审，沉淀 ADR
6. 评审关注设计而非格式——格式交给机器，人专注架构与正确性

### 踩坑记录

```text
坑 1：只配了 Lint 没接 Git Hooks 和 CI
结论：规则形同虚设，开发者本地不跑，问题照样进仓库。
原因：检查工具只停留在配置，没有强制执行的闸门。
解法：Husky + lint-staged 本地拦截，CI 二次校验，双保险。

坑 2：lint 警告不阻断，警告越积越多
结论：仓库里几千条 warning，没人敢开 --max-warnings 0。
原因：早期没设零容忍，警告累积成技术债。
解法：lint 加 --max-warnings 0，一次性清理存量警告，之后零新增。

坑 3：类型检查开了 any 豁免，漏洞百出
结论：代码里到处 any，TS 退化成了 JS，类型保护失效。
原因：图省事用 any 绕过类型，没有收敛。
解法：no-explicit-any 设 error，存量 any 分批消除，新增 any 必须说明理由。

坑 4：Code Review 只挑格式问题，设计问题没人看
结论：评审流于形式，合进去一堆坏设计。
原因：格式已被机器处理，评审还盯着格式，忽略设计。
解法：评审聚焦正确性、可读性、设计合理性，格式交给 Prettier。

坑 5：架构评审只在出事后补，成了「事后诸葛亮」
结论：系统已经跑偏，评审变成救火，收效甚微。
原因：没有事前评审机制，重大改动随意合并。
解法：设定架构评审触发条件，新技术、跨模块改动、重大重构必须事前评审。
```
