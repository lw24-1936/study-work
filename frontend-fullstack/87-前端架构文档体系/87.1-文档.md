## 概述

架构文档体系是团队协作的「共识底座」：它把系统的设计决策、接口契约、组件规范和运维流程沉淀成可检索的文字，让新成员能快速理解系统、老成员在变更时有据可依。前端架构文档不是为了写而写，而是为了让「为什么这样设计」和「应该怎么用」不再只存在于少数人的脑子里。

```text
架构文档体系的核心价值：
1. 可发现 —— 新成员按文档就能理解系统全貌和决策历史
2. 可追溯 —— 每个重大决策都有 ADR 记录「为什么这么选」
3. 契约化 —— API Spec 和 Component Spec 是跨团队协作的契约
4. 可执行 —— Runbook 让运维操作可复现、可交接
5. 防退化 —— 文档随代码一起评审、一起演进
```

## README

README 是仓库的门面，回答「这是什么、怎么跑起来、怎么参与贡献」。它是任何进入仓库的人读到的第一份文档，好坏直接影响上手成本。

````markdown
# shop-web（电商前端）

一站式电商 Web 应用，基于 React + TypeScript + Vite。

## 快速开始

```bash
npm install
npm run dev      # 开发环境 http://localhost:5173
npm run build    # 生产构建，产物在 dist/
npm test         # 运行单元测试
```

## 技术栈

- React 18 + TypeScript 5
- 状态管理：Zustand
- 构建：Vite 5
- 测试：Vitest + Testing Library

## 目录结构

```text
src/
  components/   # 通用组件
  features/     # 业务功能模块
  stores/       # 全局状态
  api/          # 接口封装
```

## 贡献指南

1. Fork 仓库并从 main 拉分支
2. 提交前运行 npm run lint 与 npm test
3. PR 描述关联对应 issue
````

```text
README 的必备要素：
1. 一句话简介 —— 这个项目是做什么的
2. 快速开始 —— 三条命令内能跑起来
3. 技术栈 —— 让读者知道要补什么知识
4. 目录结构 —— 代码在哪、怎么组织
5. 贡献方式 —— 分支规范、CI 门槛、PR 流程
```

## Architecture

Architecture 文档描述系统的整体设计：模块划分、数据流、关键权衡。它回答「系统长什么样、为什么这样划分」，是架构评审和新成员 onboarding 的核心输入。

````markdown
# 前端架构设计

## 1. 架构总览

前后端分离，SPA 通过 BFF 聚合后端微服务，按业务域拆分为若干 feature 模块。

## 2. 分层设计

```text
┌─────────────┐
│   View 层    │  React 组件，只负责渲染与交互
├─────────────┤
│   Store 层   │  Zustand 状态，管理客户端状态
├─────────────┤
│   API 层     │  axios 封装，统一错误处理与鉴权
├─────────────┤
│   BFF        │  Node 聚合层，裁剪/合并后端数据
└─────────────┘
```

## 3. 数据流

单向数据流：View 触发 action → Store 更新 → 组件重新渲染。

## 4. 关键权衡

- 选 Zustand 而非 Redux：体积小、样板少，团队规模下够用
- 选 BFF：屏蔽后端微服务差异，为前端定制聚合接口
````

```text
Architecture 文档的常见结构：
1. 架构总览 —— 一张图 + 一段话讲清整体
2. 模块/分层 —— 各层的职责与依赖方向
3. 数据流 —— 数据如何从后端流到界面
4. 关键决策与权衡 —— 为什么选 A 不选 B
5. 演进方向 —— 已知的技术债和未来规划
```

## ADR

ADR（Architecture Decision Record，架构决策记录）用固定的轻量模板记录「在某个时间点，我们面对什么问题、做了哪个选择、为什么」。它让决策可追溯，避免后人重复踩坑或无意推翻历史决策。

```markdown
# ADR-007：状态管理选型 Zustand

- 状态：已接受
- 日期：2026-08-13
- 决策者：前端架构组

## 背景

现有 Redux 样板代码多、接入成本高，团队希望更轻量的方案。

## 决策

采用 Zustand 作为全局状态管理库。

## 备选方案

1. Redux Toolkit —— 生态成熟，但样板仍多
2. Jotai —— 原子化思路好，但团队不熟悉

## 后果

- 正面：代码量减少约 40%，上手快
- 负面：缺少中间件生态，复杂异步需自行封装
```

```text
ADR 的关键字段：
1. 标题编号 —— ADR-007 之类，便于引用
2. 状态 —— 已提出 / 已接受 / 已废弃 / 被取代
3. 背景 —— 面临的问题和约束
4. 决策 —— 做了什么选择
5. 备选 —— 考虑过但没选的其他方案
6. 后果 —— 正面与负面影响都要写
```

## RFC

RFC（Request for Comments，征求意见稿）在动手实现前，先写一份提案征求团队反馈，把设计问题前移。它用于影响面较大的新特性或架构变更，让评审发生在代码之前。

```markdown
# RFC-012：支持多租户的权限模型

## 摘要

引入租户隔离 + 基于角色的权限，支持 SaaS 多租户场景。

## 动机

现有单租户模型无法支撑 B 端客户独立数据隔离的需求。

## 方案设计

- 数据模型：新增 tenant_id 字段，所有查询自动带上租户过滤
- 权限：RBAC，前端按权限点控制菜单与按钮
- 兼容：老数据默认归属默认租户

## 开放问题

- 租户间是否允许共享组件配置？
- 超管是否可跨租户查看？
```

```text
RFC 的常见章节：
1. 摘要 —— 一段话概括要做什么
2. 动机 —— 为什么需要，解决什么问题
3. 方案设计 —— 核心思路与关键实现
4. 备选方案 —— 其他可能的做法
5. 开放问题 —— 尚未定论、需要讨论的点
```

## API Spec

API Spec（接口规范）是前后端协作的契约，用机器可读的格式（OpenAPI/JSON Schema）定义接口的路径、参数、响应结构。有了它，前后端可以并行开发，还能自动生成类型和 Mock。

```yaml
# openapi.yaml —— OpenAPI 3.0 规范
openapi: 3.0.0
info:
  title: 商品接口
  version: 1.0.0
paths:
  /products/{id}:
    get:
      summary: 查询商品详情
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        '200':
          description: 成功
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Product'
components:
  schemas:
    Product:
      type: object
      required: [id, name, price]
      properties:
        id:
          type: string
        name:
          type: string
        price:
          type: number
```

```text
API Spec 的价值：
1. 单一事实来源 —— 前后端都对齐同一份契约
2. 自动生成 —— OpenAPI 可生成 TS 类型、客户端 SDK、Mock
3. 契约测试 —— 后端改动破坏契约时 CI 能提前发现
4. 文档同步 —— 接口文档不再手写、不再过期
```

## Component Spec

Component Spec（组件规范）定义每个组件的 props、事件、插槽和行为约定，是设计系统与组件库落地的基石。它让组件使用方不用翻源码就知道怎么用、边界在哪。

```typescript
// Button 组件的规范描述
interface ButtonSpec {
  name: 'Button'
  props: {
    variant: 'primary' | 'secondary' | 'ghost'   // 视觉变体
    size: 'sm' | 'md' | 'lg'                     // 尺寸
    disabled: boolean                            // 是否禁用
    loading: boolean                             // 加载态
  }
  events: {
    onClick: (e: MouseEvent) => void             // 点击事件
  }
  slots: {
    default: '按钮内容'
    icon: '前置图标'
  }
  notes: 'loading 为 true 时自动禁用并显示 spinner'
}
```

```text
Component Spec 要覆盖的维度：
1. props —— 类型、是否必填、默认值、取值范围
2. events —— 组件对外抛出的所有事件及其参数
3. slots —— 可插槽区域及各自用途
4. 行为约定 —— 交互边界（如 loading 时禁用）
5. 示例 —— 至少一个最小可用示例
```

## Runbook

Runbook（运行手册）是可操作的运维文档，记录「出了问题怎么办、例行操作怎么做」。它的目标是让一个不熟悉系统的值班同事也能按步骤执行，而不是靠经验。

```markdown
# 前端发布 Runbook

## 常规发布

1. 在 main 分支打 tag：git tag v1.2.3
2. 触发 CI，等待 build 与 test 通过
3. 审批通过后自动部署到灰度环境
4. 观察监控 15 分钟，无异常则全量发布
5. 若异常，执行回滚（见下节）

## 回滚步骤

1. 找到上一个稳定 tag：git tag -l | tail -2
2. 在发布平台选择「回滚到上一版本」
3. 确认回滚后页面恢复正常

## 常见故障排查

- 白屏：查看构建产物是否 404，确认静态资源路径
- 接口 502：检查 BFF 是否存活，看网关日志
- 资源加载慢：确认 CDN 缓存是否被击穿
```

```text
Runbook 的编写原则：
1. 面向新人 —— 假设执行者不熟悉系统
2. 步骤明确 —— 可复制粘贴执行的命令/操作
3. 含失败分支 —— 每一步都要有「失败了怎么办」
4. 滚动更新 —— 随系统变更同步修订，过期即删除
```

## 应用场景实战

### 场景一：为新仓库一次性生成文档骨架

```bash
# 用脚本快速生成 README + ADR + Runbook 骨架，保证结构统一
mkdir -p docs/adr docs/runbook

cat > README.md <<'EOF'
# <项目名>
一句话描述。快速开始见 docs/。
EOF

cat > docs/adr/0001-记录架构决策.md <<'EOF'
# ADR-0001

- 状态：已提出
- 日期：$(date +%F)
EOF

cat > docs/runbook/发布手册.md <<'EOF'
# 发布手册
1. 打 tag
2. 触发 CI
3. 观察监控
EOF
```

### 场景二：用 OpenAPI 自动生成前端类型

```bash
# 后端提供 openapi.yaml 后，自动生成 TS 类型，杜绝手写接口类型
npx openapi-typescript openapi.yaml -o src/api/schema.d.ts
# 生成后，前端所有接口响应类型都从这份契约派生，接口一变类型就报错
```

## 最佳实践与踩坑记录

### 最佳实践

1. 文档与代码同仓，随 PR 一起评审，杜绝文档代码两张皮
2. ADR 轻量、及时写，宁可三行也要记录，别等「有空再补」
3. API Spec 用机器可读格式（OpenAPI），类型和 Mock 全部自动生成
4. Runbook 每季度演练一次回滚，确保步骤真的可执行
5. README 保持「三条命令能跑起来」，复杂度一升就提醒重构
6. 文档也要有负责人和失效期限，过期文档及时归档或删除

### 踩坑记录

```text
坑 1：文档和代码分离导致过期
结论：文档说一套、代码做一套，新人照着文档跑不起来。
原因：文档单独放 wiki，没有随代码变更一起更新。
解法：文档与代码同仓，PR 评审时把「是否更新文档」作为 checklist 一项。

坑 2：ADR 写得太重没人愿意写
结论：决策全靠口头约定，半年后没人记得为什么这么设计。
原因：ADR 模板字段过多，写一篇要半小时。
解法：砍到 背景/决策/后果 三块，三分钟能写完，先有记录再谈完整。

坑 3：API 文档靠手写，接口一改就漂移
结论：前端类型和后端实际返回不一致，上线才发现字段对不上。
原因：接口文档手写维护，后端改字段没同步。
解法：用 OpenAPI 作为单一契约，前端类型自动生成，契约破坏 CI 即失败。

坑 4：README 堆满历史信息没人敢删
结论：README 越来越长，真正的「快速开始」被淹没。
原因：把变更日志、会议纪要都塞进 README。
解法：README 只留「是什么 + 怎么跑 + 怎么贡献」，其余拆分到 docs/。

坑 5：Runbook 只写正常路径
结论：真出故障时，值班同事卡在失败分支上不知所措。
原因：只写了「正常情况下怎么做」，没写「失败/异常怎么办」。
解法：Runbook 每一步都补失败分支，并定期演练回滚流程。
```
