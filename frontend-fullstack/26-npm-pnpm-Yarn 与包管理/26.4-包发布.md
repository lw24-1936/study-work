## 概述

包发布是把本地开发好的包上传到 registry，让其他项目能通过 npm install 使用。核心命令是 `npm publish`，涉及 registry 选择、作用域、版本管理，以及 provenance/signing 这类供应链安全机制。

```text
包发布的完整链路：
1. 准备 package.json（name/version/files/入口）
2. 登录 registry（npm login）
3. npm publish 上传
4. 下游 npm install 拉取使用
```

```bash
# 发布前检查会包含哪些文件
npm pack --dry-run

# 正式发布
npm publish
```

## npm publish

npm publish 把当前目录的包上传到 registry，成功后在 registry 上可见并可供安装。

```bash
# 基础发布
npm publish

# 指定 tag（默认 latest）
npm publish --tag beta

# 发布预发布版本
npm version 1.2.3-beta.1
npm publish --tag beta
```

```text
publish 的规则：
1. 每次发布版本号必须比上次更高（SemVer）
2. 默认发布到 latest tag
3. package.json 的 files 字段决定上传哪些文件
4. "private": true 的包无法发布
```

```bash
# 撤销发布（24 小时内且无人依赖）
npm unpublish my-lib@1.2.3

# 标记某个版本为弃用
npm deprecate my-lib@1.0.0 "请升级到 2.x"
```

```text
发布前清单：
1. 版本号已按 SemVer 正确升级
2. files 白名单正确，无多余文件
3. 入口字段（main/module/exports/types）齐全
4. README 已更新
```

## npm registry

npm registry 是包的托管仓库，npm 官方公共 registry 是 `https://registry.npmjs.org`，可配置切换到私有源。

```bash
# 查看当前 registry
npm config get registry

# 切换到官方源
npm config set registry https://registry.npmjs.org

# 国内镜像源
npm config set registry https://registry.npmmirror.com
```

```text
registry 的配置层级：
1. 命令行 --registry 临时指定
2. 项目 .npmrc 针对项目
3. 用户 ~/.npmrc 针对当前用户
4. 全局 npm config 全局默认
```

```ini
# .npmrc 项目级配置
registry=https://registry.npmjs.org
```

```text
registry 的作用：
1. 存储包的 tarball（压缩包）
2. 提供元数据（版本、依赖、dist-tags）
3. install 时从这里下载，publish 时上传到这里
```

## private registry

private registry 是组织内部自建的包仓库，用于托管私有包、缓存公共包，常见实现有 Verdaccio、Nexus、Artifactory。

```text
为什么要私有 registry：
1. 内部包不外传（代码保密）
2. 内网加速（缓存公共包，减少外网请求）
3. 权限控制（谁能发布、谁能安装）
```

```bash
# 搭建 Verdaccio（本地私有 registry）
npm install -g verdaccio
verdaccio
```

```ini
# 项目 .npmrc 指向私有 registry
registry=http://localhost:4873
```

```bash
# 登录私有 registry
npm login --registry http://localhost:4873

# 发布到私有 registry
npm publish --registry http://localhost:4873
```

```text
私有 registry 与公共源共存：
1. 私有包用 scope（@company/*）指向私有源
2. 公共包仍走公共源，避免内网私有源缓存不全
3. 通过 .npmrc 的 scope 级 registry 实现分流
```

```ini
# 按 scope 分流
@company:registry=http://localhost:4873
registry=https://registry.npmjs.org
```

## scoped package

scoped package（作用域包）名字带 `@scope/name` 前缀，用于把组织相关的包分组，默认是私有的。

```bash
# 初始化作用域包
npm init --scope=@mycompany
```

```json
{
  "name": "@mycompany/logger",
  "version": "1.0.0"
}
```

```text
scoped package 的规则：
1. 命名空间归组织所有，避免公共包名抢占
2. 默认私有，公共发布需加 --access public
3. 安装时用完整名字 @scope/name
```

```bash
# 发布作用域包（默认私有，公开需显式指定）
npm publish --access public
```

```bash
# 安装作用域包
npm install @mycompany/logger
```

```text
作用域与 registry 的配合：
1. 内部包用 @company scope，指向私有 registry
2. 公开作用域包走公共 registry
3. scope 级 registry 配置见 private registry 一节
```

## package provenance

package provenance（构建来源证明）用 Sigstore 记录「这个包确实由某次可信 CI 构建产出」，建立「源码 → 构建 → 发布」的可追溯链。

```text
provenance 解决的问题：
1. 攻击者伪造包内容，声称来自某仓库
2. 下游无法确认包的构建来源是否可信
3. provenance 把发布动作与 GitHub Actions 工作流绑定
```

```yaml
# GitHub Actions 发布并附带 provenance
permissions:
  id-token: write

steps:
  - run: npm ci
  - run: npm run build
  - run: npm publish --provenance --access public
```

```bash
# 查看包的 provenance 信息
npm view <pkg> --json | grep provenance
```

```text
provenance 的关键点：
1. 需要 OIDC（id-token: write）而非长期 token
2. 由 npm 与 Sigstore 配合签名
3. 下游可验证包确实来自声明的仓库和提交
```

## package signing

package signing（包签名）对发布内容做数字签名，让安装方能验证包完整性和发布者身份，npm 生态通过 Sigstore 实现签名。

```text
签名 vs 完整性哈希：
1. integrity 哈希 —— 验证内容未被篡改（防传输篡改）
2. 签名 —— 额外验证「发布者身份」（防冒充）
3. 两者配合：内容哈希 + 发布者签名
```

```bash
# 签名发布（通过 OIDC 无 token 签名）
npm publish --provenance

# 验证包的签名和来源
npm audit signatures
```

```text
签名的信任模型：
1. 发布者通过 OIDC 从 CI 获取短期身份
2. Sigstore 记录签名到透明日志（Rekor）
3. 下游用公钥验证签名有效性
```

```text
供应链安全的价值：
1. 防投毒 —— 包内容被替换时可察觉
2. 可追溯 —— 每个包能定位到具体构建和提交
3. 合规 —— 满足企业安全审计要求
```

## 应用场景实战

### 场景一：发布一个作用域公共包

```bash
# 1. 初始化作用域包
npm init --scope=@myorg

# 2. 配置 package.json（files + 入口）
# {
#   "name": "@myorg/utils",
#   "version": "1.0.0",
#   "files": ["dist"],
#   "main": "./dist/index.js",
#   "types": "./dist/index.d.ts"
# }

# 3. 构建并检查发布内容
npm run build
npm pack --dry-run

# 4. 登录并发布（作用域包公开需 --access public）
npm login
npm publish --access public
```

### 场景二：内网私有 registry 发布内部包

```bash
# 1. 启动 Verdaccio
npx verdaccio

# 2. 项目 .npmrc 配置
# @company:registry=http://localhost:4873

# 3. 登录私有源
npm login --registry http://localhost:4873

# 4. 发布内部包（默认私有，无需 --access）
npm publish
```

## 最佳实践与踩坑记录

### 最佳实践

1. 发布前 npm pack --dry-run 预览内容，确认无源码/测试文件泄露
2. 作用域包明确 --access public 或 private，别依赖默认值
3. 预发布版本用 --tag beta，不污染 latest
4. 公开包用 --provenance 建立构建来源可信链
5. 内部包走私有 registry，公共包走公共源，按 scope 分流

### 踩坑记录

```text
坑 1：版本号没升级导致发布失败
结论：publish 报 403 或「You cannot publish over the previously published versions」。
原因：同版本不能重复发布，SemVer 要求每次递增。
解法：发布前 npm version patch/minor/major 升级版本。

坑 2：private: true 无法发布
结论：publish 报私有包不能发布。
原因：package.json 里 private: true 是发布保护开关。
解法：应用项目保持 private，可发布库去掉该字段。

坑 3：作用域包默认私有导致 402 付费墙
结论：publish @scope/name 报需要付费私有包。
原因：作用域包默认 private，公共发布必须显式 --access public。
解法：加 --access public，或确认组织有私有包额度。

坑 4：registry 切换后登录态失效
结论：换 registry 后 publish 报未授权。
原因：npm 的登录 token 绑定特定 registry，切换源后 token 不通用。
解法：对新 registry 重新 npm login，或按 scope 分别配置登录。

坑 5：files 白名单漏了入口文件
结论：发布后安装报找不到入口。
原因：files 只列了 dist 但入口指向别处，或 dist 没构建。
解法：publish 前 npm run build 再 npm pack --dry-run 核对入口文件存在。
```
