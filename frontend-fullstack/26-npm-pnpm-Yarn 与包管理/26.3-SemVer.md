## 概述

SemVer（语义化版本，Semantic Versioning）规定版本号用 `major.minor.patch` 三段表达，每一段的变化都代表明确的兼容性承诺。它是 npm 生态依赖解析的基础，包管理器靠它判断「范围声明」能不能匹配「某个精确版本」。

```text
版本号结构：
1.2.3-beta.1+build.5
│ │ │   │        │
│ │ │   │        └─ build 元数据（不影响比较）
│ │ │   └────────── prerelease 预发布标识
│ │ └────────────── patch 补丁版本
│ └──────────────── minor 次版本
└────────────────── major 主版本
```

```text
SemVer 的兼容性承诺：
1. major 变化 —— 不兼容的 API 变更，升级可能破坏现有代码
2. minor 变化 —— 向后兼容的新功能
3. patch 变化 —— 向后兼容的 bug 修复
```

## major、minor 与 patch

三段版本号各有明确的语义：major 表示不兼容变更，minor 表示新增功能，patch 表示 bug 修复。

```text
语义对照：
1. major（主版本）—— 破坏性变更，移除/修改 API
2. minor（次版本）—— 向后兼容地新增功能
3. patch（补丁版本）—— 向后兼容地修复 bug
```

```bash
# 手动升级版本号
npm version major     # 1.2.3 -> 2.0.0
npm version minor     # 1.2.3 -> 1.3.0
npm version patch     # 1.2.3 -> 1.2.4

# 直接指定
npm version 2.0.0
```

```text
何时升哪个版本：
1. 修 bug、不新增 API       -> patch（1.2.3 -> 1.2.4）
2. 新增向后兼容的功能       -> minor（1.2.3 -> 1.3.0）
3. 破坏兼容性、删改 API     -> major（1.2.3 -> 2.0.0）
4. 0.x 阶段视为不稳定，minor 也可能破坏兼容
```

```text
0.y.z 特殊规则：
1. 0.x 是「初始开发期」，不承诺任何兼容性
2. 0.1.0 -> 0.2.0 可能包含破坏性变更
3. 稳定 API 应从 1.0.0 开始
```

## caret 与 tilde

caret（^）和 tilde（~）是 package.json 里最常见的「范围前缀」，决定依赖能升级到哪些版本。

```text
caret（^）：允许 minor 和 patch 升级，锁定 major
^1.2.3 -> >=1.2.3 <2.0.0
兼容 minor 和 patch 变更（默认推荐）

tilde（~）：只允许 patch 升级，锁定 major 和 minor
~1.2.3 -> >=1.2.3 <1.3.0
只兼容 patch 变更（更保守）
```

```json
{
  "dependencies": {
    "react": "^18.2.0",
    "lodash": "~4.17.21",
    "axios": "1.6.0",
    "chalk": "*"
  }
}
```

```text
范围写法对照：
1. ^18.2.0   -> >=18.2.0 <19.0.0
2. ~4.17.21  -> >=4.17.21 <4.18.0
3. 1.6.0     -> 精确锁定 1.6.0
4. *         -> 任意版本
5. >=1.0.0 <2.0.0 -> 显式范围
```

```bash
# 查看一个范围实际能匹配哪些版本
npx semver -r '^18.2.0' 18.2.0 18.3.5 19.0.0
```

```text
0.x 时 caret 的行为：
1. ^0.2.3 -> >=0.2.3 <0.3.0（只允许 patch）
2. 0.x 下 caret 变得更保守，因为 0.x 的 minor 也可能破坏兼容
```

## prerelease

prerelease（预发布版本）在 patch 后追加 `-` 和标识符，用于发布测试版、beta、RC，正常范围不会匹配到它们。

```text
prerelease 格式：
1.2.3-alpha.1
1.2.3-beta.2
2.0.0-rc.1
```

```text
prerelease 的规则：
1. 用 - 连接标识符，点分隔多级（alpha.1）
2. 标识符常见：alpha、beta、rc（release candidate）
3. 版本比较：1.2.3-alpha < 1.2.3-beta < 1.2.3（正式版更高）
4. 范围（^1.2.3）默认不匹配 prerelease，除非显式写
```

```bash
# 发布预发布版本
npm version 1.2.3-beta.1
npm publish --tag beta
```

```bash
# 安装预发布版本需显式指定
npm install my-lib@1.2.3-beta.1
npm install my-lib@beta       # 按 tag 装
```

```text
prerelease 的排序（从小到大）：
1.2.3-alpha.1 < 1.2.3-alpha.2 < 1.2.3-beta.1 < 1.2.3-rc.1 < 1.2.3
```

## peer dependency

peer dependency（对等依赖）是 SemVer 生态里的一种依赖关系：库声明自己「需要宿主提供某个版本范围的包」，本身不安装它。

```json
{
  "name": "react-router",
  "peerDependencies": {
    "react": ">=16.8.0"
  }
}
```

```text
peer dependency 的版本规则：
1. 用范围声明兼容的宿主版本，如 >=16.8.0 或 ^18.0.0
2. 宿主版本不匹配时，npm 7+ 安装会报 ERESOLVE
3. 库升级 peer 范围是破坏性变更，通常对应 major 升级
```

```text
peer dependency 与普通依赖的区别：
1. dependencies —— 自己装一份，独立使用
2. peerDependencies —— 要求宿主提供，避免多实例
3. 典型：React 生态插件都 peer 依赖 react，防止出现两份 react
```

```text
版本冲突的处理：
1. 宿主 react 18，库要求 ^17 -> 冲突，npm 报错
2. 解法：升级库到支持 18 的版本，或升级/降级宿主
3. 临时绕过：--legacy-peer-deps（不推荐长期用）
```

## 应用场景实战

### 场景一：根据变更类型正确升级版本

```bash
# 修一个 bug，不改 API
npm version patch          # 1.2.3 -> 1.2.4

# 新增一个向后兼容的功能
npm version minor          # 1.2.4 -> 1.3.0

# 移除/改了公开 API
npm version major          # 1.3.0 -> 2.0.0

# 发一个 beta 测试版
npm version 2.0.0-beta.1
npm publish --tag beta
```

### 场景二：检查依赖是否可安全升级（semver 工具）

```bash
# 检查当前项目依赖是否有更新
npm outdated

# 用 npx semver 验证范围
npx semver -r '^18.0.0' 18.0.0 18.3.0 19.0.0
# 输出 18.0.0 18.3.0（19.0.0 超出范围被排除）
```

```text
npm outdated 输出解读：
Package   Current  Wanted  Latest
lodash    4.17.20  4.17.21 5.0.0
^4.17.20  -> Wanted 是范围内最新，Latest 是全局最新（可能跨 major）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 默认用 caret（^），只在需要严格控制时用 tilde 或精确版本
2. 发布前按变更类型选对版本号，遵守 SemVer 承诺
3. 预发布版本用 --tag 发布，避免默认 latest tag 污染正式版
4. 库的 peer 范围放宽（>= 或 ^），减少宿主版本冲突
5. 用 npm outdated 定期检查依赖是否有安全更新

### 踩坑记录

```text
坑 1：破坏性变更却只升了 patch
结论：升级到 1.2.4 后代码报错，因为 API 被改了。
原因：发布方没遵守 SemVer，破坏性变更放在 patch 里。
解法：发布方按 SemVer 升 major，使用方靠锁文件 + 测试拦截。

坑 2：caret 在 0.x 版本下过于乐观
结论：^0.2.3 以为能升到 0.9.x，实际只匹配 <0.3.0。
原因：0.x 的 caret 只允许 patch 升级，防止 0.x minor 破坏兼容。
解法：0.x 库要么精确锁定，要么尽快升到 1.0.0。

坑 3：prerelease 被范围意外匹配
结论：^1.2.3 装到了 1.2.4-beta，导致生产引入预发布版。
原因：显式写了包含 prerelease 的范围，或用了 tag 安装。
解法：正常范围不匹配 prerelease，发布用 --tag beta 且安装不追 beta。

坑 4：peer 依赖范围过窄导致 ERESOLVE
结论：安装时 npm 报无法解析依赖树。
原因：库的 peer 范围写死 ^17.0.0，宿主是 react 18。
解法：升级库版本，或用 --legacy-peer-deps 临时绕过。

坑 5：npm version 在 git 脏状态时报错
结论：npm version patch 报 working directory not clean。
原因：npm version 会同时打 git tag 和 commit，要求工作区干净。
解法：先提交改动，或加 --no-git-tag-version 跳过 git 操作。
```
