## 概述

锁文件（Lockfile）把「依赖树的精确版本和来源」固化下来，保证不同机器、不同时间安装得到完全一致的依赖。package.json 里写的是「范围」（如 ^1.0.0），锁文件里写的是「精确版本」（如 1.2.3）以及每个包的完整性哈希。

```text
锁文件解决的问题：
1. 范围版本（^1.0.0）每次安装可能解析到不同的精确版本
2. 没有锁文件，团队/CI 环境的依赖树可能不一致
3. 锁文件记录精确版本 + integrity 哈希，实现可复现安装
```

```text
三种包管理器的锁文件：
1. npm     —— package-lock.json（JSON 格式）
2. pnpm    —— pnpm-lock.yaml（YAML 格式）
3. Yarn    —— yarn.lock（自定义格式）
```

## package-lock.json

npm 的锁文件，JSON 格式，记录每个包的精确版本、解析地址和 integrity 哈希。npm 5+ 自动生成。

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "lockfileVersion": 3,
  "packages": {
    "": {
      "name": "my-app",
      "dependencies": {
        "lodash": "^4.17.21"
      }
    },
    "node_modules/lodash": {
      "version": "4.17.21",
      "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
      "integrity": "sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvSg=="
    }
  }
}
```

```text
package-lock.json 的字段：
1. version —— 依赖的精确版本号
2. resolved —— 包的下载地址
3. integrity —— SRI 哈希，校验下载内容未被篡改
4. lockfileVersion —— 锁文件格式版本（v2/v3）
```

```bash
# 生成/更新锁文件
npm install

# 只看锁文件改动影响（不实际安装）
npm ci --dry-run
```

## pnpm-lock.yaml

pnpm 的锁文件，YAML 格式，比 JSON 更紧凑，同样记录精确版本和完整性信息，配合 pnpm 的内容寻址存储。

```yaml
lockfileVersion: '9.0'

importers:
  .:
    dependencies:
      lodash:
        specifier: ^4.17.21
        version: 4.17.21

packages:
  lodash@4.17.21:
    resolution: {integrity: sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvSg==}
```

```text
pnpm-lock.yaml 的特点：
1. importers 记录每个 workspace 包的依赖范围
2. packages 记录所有解析后的精确版本
3. 配合 pnpm 的硬链接存储，节省磁盘空间
```

```bash
# pnpm 生成锁文件
pnpm install

# 冻结锁文件安装（类似 npm ci）
pnpm install --frozen-lockfile
```

## yarn.lock

Yarn 的锁文件，自定义格式（非 JSON/YAML），键是「包名@版本范围」，值是解析后的精确版本和依赖。

```text
# yarn.lock 片段
lodash@^4.17.21:
  version "4.17.21"
  resolved "https://registry.yarnpkg.com/lodash/-/lodash-4.17.21.tgz"
  integrity sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvSg==
```

```text
yarn.lock 的特点：
1. 键是「包名@范围」，一个包可能有多个键对应不同范围
2. 值记录精确 version、resolved、integrity
3. 不区分顶层/嵌套，扁平记录所有解析结果
```

```bash
# yarn 生成锁文件
yarn install

# 冻结安装
yarn install --frozen-lockfile
```

## 依赖解析

依赖解析（Dependency Resolution）是把 package.json 里的「范围声明」逐层展开成「精确版本」的过程，锁文件就是这个过程的结果快照。

```text
依赖解析的流程：
1. 读 package.json 的直接依赖（含范围）
2. 对每个范围，从 registry 查询可用的精确版本
3. 按 SemVer 规则选出满足范围的最新版本
4. 递归解析该版本的依赖，处理冲突（npm 嵌套、pnpm 隔离）
5. 把最终精确版本写入锁文件
```

```bash
# 查看实际解析到的依赖树
npm ls --depth=2

# 查看某个包解析到哪个版本
npm ls lodash
```

```text
版本冲突的处理策略：
1. npm —— 冲突时嵌套安装（node_modules 里多层）
2. pnpm —— 硬链接 + 软链接，各依赖拿到自己的版本
3. Yarn —— 类似 npm，但做更激进的去重
```

## 完整性校验

完整性（Integrity）用 SRI（Subresource Integrity）哈希保证下载的包内容与锁文件记录一致，防篡改、防缓存损坏。

```text
integrity 字段：
1. 格式：sha512-<base64>
2. 安装时计算实际下载内容的哈希，与记录比对
3. 不一致则拒绝使用该包（防止中间人篡改或 registry 投毒）
```

```json
{
  "node_modules/lodash": {
    "version": "4.17.21",
    "integrity": "sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvSg=="
  }
}
```

```text
校验的两种场景：
1. 下载校验 —— registry 返回的内容哈希与 integrity 比对
2. 缓存校验 —— 本地缓存的包在使用前也做哈希验证
```

## 确定性安装

确定性安装（Deterministic Install）指「同样的锁文件 → 同样的依赖树」，通过 `npm ci` / `pnpm install --frozen-lockfile` / `yarn install --frozen-lockfile` 实现。

```text
确定性安装 vs 普通安装：
1. 普通 install —— 会更新锁文件、可能改变依赖版本
2. ci / frozen —— 严格按锁文件安装，锁文件与 package.json 不符则直接报错
3. CI 环境必须用 ci / frozen，保证可复现
```

```bash
# npm：删除 node_modules 后严格按锁文件装
npm ci

# pnpm：锁文件冻结，不符则失败
pnpm install --frozen-lockfile

# yarn：同 pnpm
yarn install --frozen-lockfile
```

```text
CI 使用确定性安装的原因：
1. 可复现 —— 每次构建用完全相同的依赖
2. 快速 —— npm ci 直接按锁文件下载，不做重新解析
3. 安全 —— 锁文件被篡改或过时立即暴露
```

## 应用场景实战

### 场景一：CI 里的确定性安装

```yaml
# GitHub Actions 片段
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-node@v4
    with:
      node-version: 20
      cache: npm
  - run: npm ci          # 严格按 package-lock.json 安装
  - run: npm run build
  - run: npm test
```

### 场景二：提交锁文件到 Git（团队一致性）

```bash
# 应用项目：锁文件必须提交
git add package.json package-lock.json
git commit -m "chore: 升级依赖并更新锁文件"

# 库项目：可不提交锁文件，让下游自己解析（可选策略）
# .gitignore 里忽略 package-lock.json
```

## 最佳实践与踩坑记录

### 最佳实践

1. 应用项目锁文件必须提交到 Git，保证团队一致
2. CI 用 npm ci / --frozen-lockfile，不用 npm install
3. 手改 package.json 后运行 install 让锁文件同步，不要手改锁文件
4. 依赖升级统一用 install 命令，避免 package.json 与锁文件脱节
5. 三种包管理器锁文件不通用，团队统一用一种

### 踩坑记录

```text
坑 1：手改 package.json 后锁文件没更新
结论：改了版本号但 node_modules 还是旧版本。
原因：只改 package.json 不运行 install，锁文件保持旧解析。
解法：改完 package.json 后运行 npm install / pnpm install 同步锁文件。

坑 2：CI 用 npm install 导致依赖漂移
结论：不同时间构建装到不同版本，出现「本地能跑 CI 挂」。
原因：install 会按范围重新解析，可能装上更新的版本。
解法：CI 改用 npm ci，严格按锁文件安装。

坑 3：锁文件冲突（merge conflict）
结论：多人同时升级依赖，锁文件合并冲突。
原因：锁文件记录全局依赖树，任何改动都大范围冲突。
解法：合并时冲突部分直接选一方，再重新 install 生成一致锁文件。

坑 4：混用包管理器导致锁文件互相覆盖
结论：npm 和 pnpm 交替使用，生成两套锁文件且依赖状态不一致。
原因：不同包管理器读各自的锁文件，无法共享。
解法：项目锁定一种包管理器，用 engines + packageManager 字段声明。

坑 5：integrity 校验失败
结论：安装时报 EINTEGRITY。
原因：下载的包内容与锁文件哈希不符，可能是缓存损坏或 registry 异常。
解法：npm cache clean --force 清缓存后重装，或删锁文件重新生成。
```
