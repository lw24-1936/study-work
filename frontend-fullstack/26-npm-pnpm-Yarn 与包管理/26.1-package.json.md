## 概述

package.json 是 Node.js 项目的「身份证」，记录包名、版本、脚本、依赖关系等元信息。npm/pnpm/Yarn 都依赖它来安装依赖、执行脚本、发布包。它是整个包管理体系的起点。

```text
package.json 的核心职责：
1. 标识 —— name + version 唯一定位一个包
2. 脚本 —— scripts 定义常用命令入口
3. 依赖 —— dependencies / devDependencies 等声明依赖关系
4. 发布 —— files / exports / bin 控制发布内容和入口
```

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "private": true
}
```

## name 与 version

name 是包名（npm 上全局唯一），version 遵循 SemVer 规范，两者共同组成包的唯一标识。

```json
{
  "name": "my-awesome-lib",
  "version": "1.2.3"
}
```

```text
name 规则：
1. 小写，可用连字符，不能用大写和空格
2. npm 公共仓库上全局唯一，重名会被拒绝
3. 作用域包用 @scope/name 形式
4. 不想发布时设 "private": true

version 规则：
1. 遵循 SemVer：major.minor.patch
2. 每次发布必须比上次版本号更大
3. 预发布版本可带后缀，如 1.2.3-beta.1
```

```bash
# 查看当前包名和版本
npm pkg get name version
```

## scripts

scripts 是「命令别名」，用 `npm run <script>` 执行，内置一些生命周期钩子（pre/post、install 等）。

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest run",
    "lint": "eslint .",
    "prebuild": "npm run lint",
    "postbuild": "node scripts/notify.js"
  }
}
```

```bash
# 执行脚本
npm run dev        # 自定义脚本需要 run
npm test           # test 等内置脚本可省略 run
```

```text
scripts 的约定：
1. 自定义脚本用 npm run，内置脚本（test/start/stop）可省略 run
2. pre<script> / post<script> 会在目标脚本前后自动执行
3. 脚本里能调用 node_modules/.bin 下的命令，无需加路径
4. 用 && 串联、& 并行，跨平台建议用脚本文件封装
```

```json
{
  "scripts": {
    "build": "npm run clean && vite build",
    "clean": "rimraf dist"
  }
}
```

## dependencies 与 devDependencies

dependencies 是「运行时依赖」（打包进产物、生产环境需要），devDependencies 是「开发时依赖」（构建、测试、lint 工具）。

```json
{
  "dependencies": {
    "react": "^18.2.0",
    "axios": "^1.6.0"
  },
  "devDependencies": {
    "typescript": "^5.4.0",
    "vite": "^5.0.0",
    "eslint": "^8.57.0"
  }
}
```

```text
区分原则：
1. dependencies —— 应用运行时 import 的库（框架、工具库）
2. devDependencies —— 只在开发/构建阶段用的（编译器、测试框架、lint）
3. 装到哪个字段取决于「产物运行」时是否需要
```

```bash
# 安装到对应字段
npm install react            # 默认写 dependencies
npm install -D typescript    # -D / --save-dev 写 devDependencies
npm install --save-prod vue  # 显式写 dependencies
```

## peerDependencies

peerDependencies 声明「宿主环境需要提供的依赖」，用于插件/库，避免重复安装同一依赖造成多个实例。

```json
{
  "name": "my-react-hook-lib",
  "peerDependencies": {
    "react": ">=17.0.0"
  }
}
```

```text
peerDependencies 的意义：
1. 库依赖宿主提供 react，自己不装一份
2. 避免应用里出现两份 react 导致 hooks 状态异常
3. npm 7+ 会自动安装 peer 依赖，版本不匹配会报错
```

```json
{
  "peerDependencies": {
    "react": "^18.0.0"
  },
  "peerDependenciesMeta": {
    "react": {
      "optional": true
    }
  }
}
```

## optionalDependencies

optionalDependencies 是「装不上也不影响整体安装」的依赖，安装失败时 npm 不报错、继续完成其他依赖的安装。

```json
{
  "optionalDependencies": {
    "fsevents": "^2.3.0"
  }
}
```

```text
optionalDependencies 的场景：
1. 平台专属的原生模块（如 fsevents 仅 macOS 需要）
2. 可选加速器，装不上回退到纯 JS 实现
3. 安装失败不阻塞 npm install
```

```ts
// 运行时对可选依赖做存在性判断
let watcher;
try {
  watcher = require('fsevents');
} catch {
  // 回退到跨平台实现
  watcher = require('chokidar');
}
```

## engines

engines 声明包要求的 Node 版本和包管理器版本，版本不符时给出警告（配合 engine-strict 可强制报错）。

```json
{
  "engines": {
    "node": ">=18.0.0",
    "npm": ">=9.0.0",
    "pnpm": ">=8.0.0"
  }
}
```

```text
engines 的作用：
1. 声明最低 Node 版本，避免在旧版本上运行出错
2. 配合 .npmrc 的 engine-strict=true 强制拦截
3. 提示团队成员使用一致的 Node 版本
```

```ini
# .npmrc
engine-strict=true
```

## exports 与 imports

exports 定义「包的对外入口映射」（控制外部能 import 哪些路径），imports 定义「包内部的路径别名」（用 # 前缀）。

```json
{
  "name": "my-lib",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./utils": "./dist/utils.mjs",
    "./package.json": "./package.json"
  }
}
```

```text
exports 的规则：
1. 声明 exports 后，未列出的路径外部无法导入（封装性）
2. 可按 import/require/types 分别指定产物
3. 子路径需以 ./ 开头
```

```json
{
  "imports": {
    "#utils/*": "./src/utils/*.js",
    "#config": "./src/config/index.js"
  }
}
```

```js
// 内部使用 # 别名导入，无需相对路径 ../../../utils
import { helper } from '#utils/helper.js';
import config from '#config';
```

## bin

bin 把包注册成可执行命令，安装后可直接在命令行调用，常用于 CLI 工具。

```json
{
  "name": "my-cli",
  "bin": {
    "mycli": "./bin/cli.js"
  }
}
```

```js
// bin/cli.js 顶部必须有 shebang
#!/usr/bin/env node

console.log('my-cli running');
```

```text
bin 的规则：
1. 值是指向可执行文件的路径
2. 入口文件第一行必须是 #!/usr/bin/env node
3. 安装后命令链接到 node_modules/.bin，npm run 和全局安装都能调用
4. 对象形式可定义多个命令名
```

```bash
# 全局安装后直接调用
npm install -g my-cli
mycli
```

## files

files 是「发布白名单」，声明 npm publish 时哪些文件会打进包里，未列出的默认被排除。

```json
{
  "files": [
    "dist",
    "README.md",
    "LICENSE"
  ]
}
```

```text
files 的规则：
1. 只发布列出的文件/目录
2. README、LICENSE、package.json 始终包含，无需列出
3. .npmignore 与 files 冲突时，files 优先（白名单优先）
4. 减小包体积、避免泄露源码和测试文件
```

```bash
# 预览发布内容
npm pack --dry-run
```

## 应用场景实战

### 场景一：一个可发布的工具库的完整 package.json

```json
{
  "name": "@myorg/string-utils",
  "version": "1.0.0",
  "description": "字符串工具库",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  },
  "files": ["dist"],
  "engines": {
    "node": ">=18"
  },
  "scripts": {
    "build": "tsup src/index.ts --format esm,cjs --dts",
    "test": "vitest run"
  },
  "peerDependencies": {
    "typescript": ">=5.0.0"
  }
}
```

### 场景二：前端应用的 package.json（不发布）

```json
{
  "name": "my-web-app",
  "version": "0.1.0",
  "private": true,
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "preview": "vite preview",
    "lint": "eslint ."
  },
  "dependencies": {
    "react": "^18.2.0",
    "react-dom": "^18.2.0"
  },
  "devDependencies": {
    "@vitejs/plugin-react": "^4.2.0",
    "typescript": "^5.4.0",
    "vite": "^5.0.0"
  }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 应用项目设 "private": true，防止误发布
2. 构建/测试工具放 devDependencies，运行时库放 dependencies
3. 插件库用 peerDependencies 声明宿主依赖，不自己装一份
4. 发布库用 files 白名单，减小体积、防源码泄露
5. exports 显式声明入口，未列路径自动隐藏

### 踩坑记录

```text
坑 1：误把构建工具放进 dependencies
结论：生产环境安装了大量不需要的 dev 依赖。
原因：eslint/vite 等只在构建期用，运行时不需要。
解法：统一放 devDependencies，生产安装用 npm install --omit=dev。

坑 2：name 大小写导致安装失败
结论：npm install My-Lib 找不到包。
原因：npm 包名要求小写，大小写不一致视为不同包。
解法：包名统一小写，引用时保持一致。

坑 3：声明 exports 后其他路径无法导入
结论：加 exports 后 deep import 报错「Package subpath not defined」。
原因：exports 是白名单，未列出的子路径全部被屏蔽。
解法：把需要的子路径显式加进 exports，或提供通配 ./utils/*。

坑 4：peerDependencies 版本冲突
结论：npm 7+ 安装时报 ERESOLVE 无法解析依赖树。
原因：宿主提供的版本与 peer 声明不匹配。
解法：放宽 peer 范围（用 >=），或用 --legacy-peer-deps 临时绕过。

坑 5：bin 入口忘加 shebang
结论：安装后命令无法执行，报 permission/语法错误。
原因：bin 指向的文件缺少 #!/usr/bin/env node，系统不知道怎么执行。
解法：入口文件首行加 shebang，并保证文件有可执行权限。
```
