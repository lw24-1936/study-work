## 概述

内存诊断是「找出内存去哪了、是谁占着、什么时候涨的」的过程。Chrome DevTools 的 Memory 面板提供四件核心工具：Heap Snapshot（堆快照）、Allocation Timeline（分配时间线）、Retainer（引用链）、Dominator Tree（支配树）。四者配合能定位绝大多数内存泄漏。

```text
四种内存诊断工具：
1. Heap Snapshot —— 某时刻堆的完整快照，看谁占内存、谁在泄漏
2. Allocation Timeline —— 按时间记录对象分配，看内存何时、因谁而涨
3. Retainer —— 从对象反向看「谁引用了我」，追引用链
4. Dominator Tree —— 按「支配者」聚合对象，看删除某对象能释放多少
```

```js
// 诊断前先建基线：记录堆大小，配合操作观察增长
function heapSizeMB() {
  return performance.memory
    ? (performance.memory.usedJSHeapSize / 1048576).toFixed(1)
    : 'N/A';
}
console.log('初始堆:', heapSizeMB(), 'MB');
```

## Heap Snapshot

Heap Snapshot 在某个时刻拍下整个 JS 堆的快照，列出所有对象、大小、引用关系。核心用法是「两次快照对比」：操作前后各拍一张，用 Comparison 视图看增量，新增且没释放的对象就是泄漏嫌疑。

```js
// 快照对比的思路：操作前后各记一次，找新增对象
// 在 DevTools 里手动操作：Take snapshot -> 执行可疑操作 -> Take snapshot
// 切到 Comparison 视图，按 "Alloc. Size" 或 "New" 过滤新增对象

// 代码侧辅助：给可疑对象打标记，方便在快照里搜索
window.__suspectObject = createSuspect();  // 泄漏嫌疑对象挂出来
// 快照里搜 "__suspectObject" 直接定位
```

```text
Heap Snapshot 的要点：
1. 拍快照时机 —— 操作前一张、操作后一张，对比增量
2. Comparison 视图 —— 看 New/Deleted/Delta，新增对象是重点
3. Shallow Size —— 对象本身大小
4. Retained Size —— 对象 + 它独占引用的对象总大小（更有意义）
5. 过滤 —— 按 "Detached" 找脱离 DOM 的节点
```

## Allocation Timeline

Allocation Timeline（分配时间线）持续记录一段时间内的对象分配，生成按时间轴分布的内存增长图。蓝色柱代表存活内存，能直观看到「哪个操作触发了内存上涨」，点击柱子能看到那段时间分配了哪些对象。

```js
// Allocation Timeline 的实操流程
// 1. 打开 Memory 面板，选 "Allocation instrumentation on timeline"
// 2. 点录制，执行可疑操作（滚动、点击、切路由）
// 3. 停止录制，观察蓝色柱：持续上涨 = 泄漏
// 4. 点击上涨的柱子，看那段时间 new 了哪些对象

// 代码侧：用数组验证「操作 N 次后对象数量是否线性增长」
const tracker = [];
function suspectAction() {
  tracker.push(new SomeObject());  // 如果 SomeObject 用完没释放，这里会累积
}
```

```text
Allocation Timeline 的要点：
1. 蓝色柱 —— 存活内存，持续上涨说明泄漏
2. 灰色柱 —— 已回收内存，正常波动
3. 定位到操作 —— 上涨的柱子对应的时间点就是触发操作
4. 结合快照 —— 时间线找到操作，快照定位具体对象
```

## Retainer

Retainer（引用链/保留路径）回答「这个对象为什么没被回收」：从对象出发，沿着引用关系一路向上，直到根对象（window 等）。这条链上的每一环都是一条「保留」这个对象的引用。

```js
// Retainer 展示的引用链示意（在 DevTools 里点对象查看）
// object -> 某闭包 -> 事件监听器 -> window
// 含义：window 持有监听器，监听器持有闭包，闭包持有 object

// 代码侧复现一条典型泄漏链
window.handler = function () {
  const data = new Array(1000000);  // 被闭包捕获的大对象
  return () => data.length;
};
// Retainer 链：data <- 返回的闭包 <- window.handler 相关引用
// 切断 window.handler = null 即可释放整条链
```

```text
Retainer 的要点：
1. 反向追踪 —— 从对象向上找引用者，直到根
2. 找第一环 —— 链上离根最近的可控环节，往往就是修复点
3. 常见根 —— window、document、模块作用域、DOM 节点
4. 修复 —— 切断链上任意一环，对象即可回收
```

## Dominator Tree

Dominator Tree（支配树）按「支配关系」组织对象：如果回收对象 A 会导致对象 B 也变不可达，那么 A 支配 B。支配树视图把对象按支配者聚合，能一眼看出「回收某个大对象能连带释放多少内存」。

```js
// 支配关系示意
// root 支配 a；a 支配 b、c（回收 a 时 b、c 也变垃圾）
// 在 Dominator Tree 里展开 a，能看到 b、c 挂在它下面

// 代码侧构造可观察的支配结构
const container = {
  children: [ { name: 'a' }, { name: 'b' } ],  // 被 container 支配
};
// Retained Size 视角：container 的 retained size = 自身 + children
// 删除 container 就能释放 children，这是支配树的聚合逻辑
```

```text
Dominator Tree 的要点：
1. 支配者 —— 回收它就回收子节点的对象
2. Retained Size —— 支配树下所有对象的总大小
3. 找大头 —— 按 retained size 排序，最大的就是值得优化的
4. 与 Retainer 互补 —— 支配树看「能释放多少」，Retainer 看「谁在引用」
```

## 应用场景实战

### 场景一：两次快照定位路由切换泄漏

```text
操作步骤：
1. 打开 Memory 面板，Take Snapshot（快照 1）
2. 反复进入/退出页面 10 次
3. 再 Take Snapshot（快照 2）
4. 切 Comparison 视图，按 Delta 降序排列
5. 关注 "New" 且 Delta 大的对象，展开看 Retainer 链
6. 修复：切断链上离根最近的引用（多为忘记解绑的监听器/定时器）
```

```js
// 代码侧：模拟一次路由切换，验证清理是否到位
function enterPage() {
  window.pageTimer = setInterval(() => { /* 轮询 */ }, 1000);
}
function leavePage() {
  clearInterval(window.pageTimer);  // 有这行则不会泄漏
}
// 反复 enterPage/leavePage 后看堆是否稳定
```

### 场景二：Allocation Timeline 定位滚动卡顿的分配源

```js
// 滚动时内存抖动，用时间线定位是哪个对象在疯狂分配
window.addEventListener('scroll', () => {
  // 差：每帧 new 大量临时对象，时间线蓝色柱随滚动上涨
  const arr = Array.from(document.querySelectorAll('.item'))
    .map(el => ({ rect: el.getBoundingClientRect() }));
  // 好：复用外部数组，避免滚动路径上的高频分配
});
// 录制时间线 -> 滚动 -> 停止，点上涨柱看是 getBoundingClientRect 结果对象
```

## 最佳实践与踩坑记录

### 最佳实践

1. 诊断顺序：先时间线看「何时涨」，再快照对比看「谁在涨」，最后 Retainer 看「谁引用」
2. 快照必拍两张对比，单张快照看不出泄漏
3. 关注 Retained Size 而非 Shallow Size，大 retained 才是真大头
4. 用 "Detached" 过滤找脱离 DOM 的泄漏节点
5. 代码里给嫌疑对象挂 window 属性，方便快照里搜索定位
6. 怀疑泄漏时优先查「忘记解绑」的监听器/定时器/订阅

### 踩坑记录

```text
坑 1：只看单张快照就下结论
结论：拍了快照看不出哪里在泄漏，误判为没有泄漏。
原因：单张快照只反映某一时刻，无法体现「增长」。
解法：操作前后各拍一张，用 Comparison 视图看增量。

坑 2：把 Shallow Size 当对象真实占用
结论：优化了半天小对象，内存没降多少。
原因：真正的占用是 Retained Size（含被独占引用的子对象）。
解法：按 Retained Size 排序，优先优化 retained 大的对象。

坑 3：时间线只看到蓝色柱上涨，不知道是谁
结论：确认内存涨了，但找不到具体对象。
原因：没点开上涨的柱子看那段时间的分配详情。
解法：点击上涨柱子，按构造器/大小查看分配的对象清单。

坑 4：Retainer 链太长不知从哪断
结论：引用链追到根，还是不知道改哪里。
原因：没找到链上「离根最近且可控」的环节。
解法：找链上第一处「业务代码可控」的引用（监听器/闭包/缓存），切断它。

坑 5：诊断内存却开着 console.log 大对象
结论：快照里出现大量本不该存在的对象。
原因：console.log 会保留对象引用，干扰快照结果。
解法：诊断前清掉 console.log，或理解这些是日志引用可忽略。
```
