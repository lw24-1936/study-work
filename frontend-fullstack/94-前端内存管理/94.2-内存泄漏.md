## 概述

内存泄漏是「本应回收的内存因为仍被引用而无法回收」的现象，JS 里最常见的原因是对象从根对象可达（见 GC 的 Reachability）。泄漏会让页面占用内存持续上涨，最终卡顿甚至崩溃。本文梳理七类典型泄漏来源与对应解法。

```text
七类内存泄漏来源：
1. Global Variable —— 意外挂到全局作用域
2. Event Listener —— 监听器没解绑
3. Timer —— 定时器没清除
4. Closure —— 闭包持有不再需要的大对象
5. Detached DOM —— 移除节点但仍被 JS 引用
6. Cache —— 缓存无限增长
7. Subscription —— 事件订阅/Observable 没退订
```

```js
// 泄漏的本质：从根可达。用一条引用链示意
// window -> leakedObj -> 大数组，window 是根，一直可达
window.leakedObj = { big: new Array(1000000) };
// 只要 window.leakedObj 还在，这个大数组就永远无法回收
```

## Global Variable

未声明的变量会隐式成为全局变量，挂在 window 上；显式的 window.xxx 同理。全局变量从根（window）可达，除非手动清除，否则永远不回收。

```js
// 三种产生全局变量的写法
function bad() {
  leaked = 'oops';              // 1. 未声明直接赋值 -> 隐式全局
  this.alsoLeaked = true;       // 2. 非严格模式下 this 指向 window
}
bad();

window.explicit = { big: true }; // 3. 显式挂 window

// 解法：严格模式 + 声明关键字
'use strict';
function good() {
  const local = 'safe';          // 局部变量，函数返回即可回收
  return local;
}
```

```text
Global Variable 的要点：
1. 隐式全局 —— 漏写 const/let/var，或 this 误指向 window
2. 严格模式 —— 'use strict' 能拦截隐式全局赋值
3. 显式全局 —— 该共享的状态挂全局无妨，但要记得清理
4. 排查 —— DevTools Console 里看 window 上多出的属性
```

## Event Listener

addEventListener 注册的监听器会持有对回调的引用，如果回调闭包里引用了大对象，而监听器一直没 remove，对象就一直可达。组件销毁后不解除绑定是最常见的泄漏。

```js
// 泄漏写法：绑定后从不解绑
function mount(el) {
  el.addEventListener('click', function handler() {
    console.log('clicked', el.textContent); // handler 闭包引用 el
  });
}

// 正确写法：销毁时解绑
function mountWithCleanup(el) {
  function handler() { console.log('clicked'); }
  el.addEventListener('click', handler);
  return function unmount() {
    el.removeEventListener('click', handler); // 解除引用
  };
}
const unmount = mountWithCleanup(btn);
// 组件销毁时调用 unmount()
```

```text
Event Listener 的要点：
1. 闭包引用 —— handler 里的闭包可能引用大对象，导致连锁泄漏
2. 成对管理 —— add 和 remove 成对出现，或用 once 选项
3. 框架封装 —— React/Vue 的 useEffect 清理函数就是干这个
4. AbortController —— 用 signal 一次性批量解绑
```

## Timer

setInterval/setTimeout 会持续持有回调，如果回调闭包引用大对象，且定时器没 clear，对象就一直可达。特别是 setInterval 长期运行，泄漏会持续累积。

```js
// 泄漏写法：setInterval 永不停止，闭包引用大对象
function start() {
  const big = new Array(1000000);
  setInterval(() => {
    console.log(big.length);   // 闭包引用 big，定时器不停就永远可达
  }, 1000);
}

// 正确写法：提供停止入口，组件销毁时 clear
function startWithStop() {
  const big = new Array(1000000);
  const id = setInterval(() => console.log(big.length), 1000);
  return function stop() {
    clearInterval(id);          // 清除定时器，释放 big
  };
}
const stop = startWithStop();
// 组件销毁时 stop()
```

```text
Timer 的要点：
1. 长期 interval —— 回调持续存在，闭包里的东西都活着
2. clear 时机 —— 组件卸载、页面隐藏时清除
3. 页面隐藏 —— 用 visibilitychange 暂停定时器，既省内存又省 CPU
4. 递归 setTimeout —— 需要外部变量保存 id 以便清除
```

## Closure

闭包本身不泄漏，泄漏的是「闭包捕获了不再需要的大对象，而闭包本身又被长期持有」。典型场景：大对象只需要用一次，却被某个长期存活的函数闭包引用。

```js
// 泄漏写法：闭包捕获了整个大对象，但只用其中一个小字段
function createHandler() {
  const bigData = new Array(1000000).fill('x');  // 大对象
  return function onClick() {
    console.log(bigData.length);  // 只用 length，却捕获了整个数组
  };
}
const handler = createHandler();  // handler 长期存活，bigData 无法回收

// 优化：只捕获需要的小值
function createHandlerFixed() {
  const bigData = new Array(1000000).fill('x');
  const len = bigData.length;     // 只提取需要的小值
  return function onClick() {
    console.log(len);             // 闭包只捕获 len，bigData 可回收
  };
}
```

```text
Closure 的要点：
1. 捕获最小化 —— 只捕获需要的小值，别把整个大对象塞进闭包
2. 释放引用 —— 用完把闭包引用置 null
3. 链式引用 —— 闭包 -> 大对象 -> 更多对象，一条链全卡住
4. 事件循环 —— 回调（如 Promise.then）长期挂起也会卡闭包
```

## Detached DOM

「脱离 DOM」节点是指已经从文档移除、但仍有 JS 变量引用它的节点。移除节点本身不回收，只要 JS 还持有引用，整个子树（包括子节点、事件）都会卡在内存里。

```js
// 泄漏写法：移除节点但变量仍引用
let detached = document.getElementById('widget');
detached.remove();          // 从文档移除，但 detached 变量还引用它
// 节点及其子树仍驻留内存，直到 detached 被置 null

// 排查：Chrome 里 Detached 节点有特殊标记
// 在 Heap Snapshot 中按 "Detached" 过滤，能直接找到脱离 DOM 的节点

// 解法：移除后置空引用
detached = null;
```

```text
Detached DOM 的要点：
1. 双引用 —— DOM 树引用 + JS 变量引用，两个都断掉才回收
2. 子树连坐 —— 父节点被引用，整棵子树都回收不了
3. 排查 —— Heap Snapshot 搜 "Detached"，红色节点即泄漏点
4. 框架场景 —— 组件卸载但 ref 仍指向 DOM 节点
```

## Cache

缓存本身合理，但无上限的缓存会无限增长，把「缓存优化」变成「内存泄漏」。典型是模块级 Map/数组缓存，key 不断增加，从不清除。

```js
// 泄漏写法：无上限缓存
const cache = new Map();
function getData(key) {
  if (!cache.has(key)) {
    cache.set(key, expensiveLoad(key));   // 只增不减
  }
  return cache.get(key);
}

// 正确写法：加容量上限 + 淘汰策略（LRU）
class LRUCache {
  constructor(limit = 100) {
    this.limit = limit;
    this.map = new Map();
  }
  get(key) {
    if (!this.map.has(key)) return undefined;
    const v = this.map.get(key);
    this.map.delete(key);
    this.map.set(key, v);       // 刷新为最近使用
    return v;
  }
  set(key, value) {
    if (this.map.has(key)) this.map.delete(key);
    this.map.set(key, value);
    if (this.map.size > this.limit) {
      this.map.delete(this.map.keys().next().value); // 淘汰最旧
    }
  }
}
```

```text
Cache 的要点：
1. 容量上限 —— 缓存必须设 max size
2. 淘汰策略 —— LRU/LFU/TTL，超过就踢
3. TTL —— 带过期时间的缓存，定时清理
4. WeakMap —— key 是对象时用 WeakMap，key 消失自动回收
```

## Subscription

事件总线、Observable（RxJS）、WebSocket、消息订阅等都要求「订阅后必须退订」。忘记退订会让回调一直持有闭包，且订阅中心还持有回调引用，形成双重泄漏。

```js
// 泄漏写法：订阅后从不退订
import { Subject } from 'rxjs';
const bus = new Subject();
bus.subscribe((msg) => {
  console.log(msg);   // 回调永久驻留
});

// 正确写法：保存 subscription，组件销毁时退订
const subscription = bus.subscribe((msg) => console.log(msg));
function destroy() {
  subscription.unsubscribe();  // 退订，释放回调
}
```

```text
Subscription 的要点：
1. 成对 —— subscribe 与 unsubscribe 必须成对
2. 集中管理 —— 多个订阅用数组收集，销毁时统一退订
3. takeUntil —— RxJS 用 takeUntil 自动完成退订
4. 一次性 —— 只订阅一次的场景用 first() 或 take(1)
```

## 进阶：容易被忽略的泄漏源

```text
Observer 三兄弟（忘 disconnect 是最隐蔽的泄漏）：
1. ResizeObserver / IntersectionObserver / MutationObserver 注册后，
   observer 持有回调、回调闭包持有元素，三者互相引用。
2. 组件销毁时若只移除 DOM 而不调用 observer.disconnect()，
   观察目标虽然没了，observer 与回调仍存活，持续泄漏。
3. 解法 —— 销毁入口里显式 disconnect()，或把 observer 挂在组件实例上一并销毁。
```

```text
Map / Set 强引用对象 key：
1. 普通 Map 以对象为 key 时是强引用，只要 Map 活着，key 对象就不会被回收。
2. 缓存「对象 → 数据」的场景若 key 已「逻辑删除」但从不 delete，就会累积。
3. 解法 —— key 允许消失时用 WeakMap；key 是基本类型时用 Map + 手动 delete / TTL。
```

```text
未 settle 的 Promise 与长连接：
1. 一直 pending 的 Promise（忘了 resolve / reject）会让 await 之后的闭包、
   以及 then 链上捕获的变量长期悬挂。
2. WebSocket / SSE / EventSource 长连接在组件销毁后不 close，连接与回调常驻。
3. 解法 —— 封装成「可取消」的异步，销毁时 close / abort 并解除引用。
```

```text
框架侧（Vue / React 的销毁时机）：
1. React —— useEffect 返回的清理函数就是解绑入口，漏写清理是高频泄漏源。
2. Vue —— watch / watchEffect 会返回停止函数；setup 作用域内同步创建的 watcher
   会自动清理，手动创建的（如异步回调里）要记得调用返回的停止函数。
3. keep-alive —— 被缓存的组件实例不会卸载，其内部监听器 / 定时器持续存活，
   长驻缓存页要额外注意清理。
```

## 应用场景实战

### 场景一：排查一个递增的列表组件泄漏

```js
// 组件反复挂载卸载，内存持续上涨
// 问题：每次挂载都注册监听，卸载没解绑
function ListItem(el) {
  function onResize() {
    el.classList.toggle('wide', el.clientWidth > 600);
  }
  window.addEventListener('resize', onResize);   // 泄漏：window 监听永不解绑
  return () => {
    window.removeEventListener('resize', onResize); // 修复：卸载解绑
  };
}
```

### 场景二：无上限缓存拖垮长跑页面

```js
// 长时间运行的仪表盘，缓存无限增长导致内存泄漏
// 用 WeakMap 当 key 是对象、且允许 key 消失时自动回收
const cache = new WeakMap();
function getExpensive(node) {
  if (!cache.has(node)) {
    cache.set(node, compute(node));
  }
  return cache.get(node);
}
// 当 node 不再被引用时，WeakMap 里的条目自动被 GC 回收
```

## 最佳实践与踩坑记录

### 最佳实践

1. 监听器、定时器、订阅一律「成对管理」，销毁入口与创建入口对称
2. 缓存设上限 + 淘汰策略，长跑页面尤其要注意
3. 闭包捕获最小化，只捕获需要的小值
4. 移除 DOM 节点后同步置空 JS 引用
5. 用 WeakMap/WeakSet 存对象 key，让 key 消失时自动回收
6. 定期在 Memory 面板看堆趋势，发现「台阶式」上涨立即排查

### 踩坑记录

```text
坑 1：以为移除 DOM 节点就释放内存
结论：remove 节点后内存没降，堆里还有 Detached 节点。
原因：JS 变量仍引用该节点，DOM 树引用断了但 JS 引用还在。
解法：移除节点后把引用置 null，或排查闭包里的 DOM 引用。

坑 2：setInterval 里的闭包引用大对象
结论：单页应用常驻页面内存只涨不降。
原因：定时器回调持续存活，闭包引用的大对象无法回收。
解法：组件销毁时 clearInterval，或改用 visibilitychange 暂停。

坑 3：全局缓存 Map 无限增长
结论：长跑页面运行几小时后内存逼近上限崩溃。
原因：缓存只增不减，key 持续累积。
解法：加容量上限 + LRU 淘汰，或用 WeakMap/TTL。

坑 4：事件总线订阅忘退订
结论：组件销毁后回调仍被触发，且闭包对象不释放。
原因：订阅中心持有回调引用，回调闭包又持有组件对象。
解法：销毁时统一 unsubscribe，或用 takeUntil 自动退订。

坑 5：误用 WeakMap 存基本类型 key
结论：WeakMap 报错 Invalid value used as weak map key。
原因：WeakMap 的 key 必须是对象，基本类型会抛错。
解法：基本类型 key 用普通 Map + 手动清理。

坑 6：ResizeObserver 忘 disconnect 导致列表页反复挂载内存上涨
结论：元素都 remove 了，堆里却残留大量 observer 与回调闭包。
原因：observer 与回调、元素互相强引用，移除 DOM 不解绑 observer。
解法：销毁入口统一 observer.disconnect()，或用组件生命周期保证成对清理。
```
