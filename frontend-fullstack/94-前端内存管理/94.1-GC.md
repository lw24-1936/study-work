## 概述

GC（Garbage Collection，垃圾回收）是 JS 引擎自动回收不再使用的内存的机制。它基于「可达性」判断对象是否存活，再经过 Mark（标记）、Sweep（清除）、Compact（整理）三个阶段回收垃圾，并通过分代策略减少全量扫描的开销。理解 GC 是理解内存泄漏和内存优化的前提。

```text
GC 的核心概念：
1. Reachability —— 从根对象出发可达的对象是活的，不可达的是垃圾
2. Mark —— 从根遍历，标记所有可达对象
3. Sweep —— 清除未标记（不可达）的对象，回收内存
4. Compact —— 整理存活对象，消除内存碎片
5. Generational GC —— 按对象年龄分代，年轻代高频小回收，老年代低频大回收
```

```js
// 可达性的直观例子
let user = { name: 'John' };   // user 指向对象，对象可达
user = null;                    // 没有引用指向它，对象不可达，等待回收

let a = { x: 1 };
let b = a;                      // b 也引用同一对象
a = null;                       // 对象仍被 b 引用，可达，不会被回收
b = null;                       // 现在没有引用了，对象变成垃圾
```

## Reachability

可达性是 GC 判断对象是否存活的唯一标准：从「根」（全局对象、调用栈上的局部变量、活跃的闭包等）出发，通过引用链能到达的对象就是活的。不可达对象无论引用关系多复杂，都会被回收。

```js
// 引用环不可达：虽然互相引用，但根无法到达，仍会被回收
function createCycle() {
  const a = {};
  const b = {};
  a.ref = b;
  b.ref = a;   // 形成环，但函数返回后两个对象都不可达
  return 'done';
}
createCycle(); // 环对象不可达，现代 GC 能回收（标记-清除不依赖引用计数）
```

```text
可达性的关键点：
1. 根 —— 全局作用域、调用栈局部变量、当前活跃的闭包
2. 引用链 —— 根 -> A -> B，只要链上可达就算活
3. 引用环 —— 互相引用但根不可达，仍是垃圾（标记清除能处理）
4. 引用计数法（老 IE）处理不了环，会导致泄漏
```

## Mark

Mark 阶段从根对象开始做深度优先遍历，把所有能到达的对象打上「存活」标记。这是标记-清除（Mark-and-Sweep）算法的前半段。

```js
// 标记算法的简化示意（不依赖引擎实现）
function mark(root) {
  const visited = new Set();
  function walk(obj) {
    if (!obj || visited.has(obj)) return;
    visited.add(obj);           // 标记为存活
    for (const key of Object.keys(obj)) {
      const val = obj[key];
      if (val && typeof val === 'object') walk(val);
    }
  }
  walk(root);
  return visited;               // 返回所有可达（存活）对象
}

const root = { a: { b: 1 }, c: { d: 2 } };
const alive = mark(root);
console.log(alive.size);        // 3 个对象被标记
```

```text
Mark 阶段的要点：
1. 从根出发 —— 不接触根的对象直接被忽略
2. 三色标记（引擎实现）—— 白（未访问）、灰（访问中）、黑（已访问完）
3. 增量标记 —— V8 把标记拆成小片，穿插在 JS 执行间隙，减少停顿
```

## Sweep

Sweep 阶段遍历堆上所有对象，回收那些没被标记的（不可达）对象，把内存归还给堆的空闲列表。标记-清除由此得名。

```js
// 清除算法的简化示意：扫描堆，回收未标记对象
function sweep(heap, aliveSet) {
  const freed = [];
  for (const obj of heap) {
    if (!aliveSet.has(obj)) {
      freed.push(obj);          // 未标记 = 垃圾，回收
      heap.delete(obj);
    }
  }
  return freed.length;
}

// 实际引擎中 sweep 回收的是内存块，归还给空闲列表供下次分配
```

```text
Sweep 阶段的要点：
1. 全堆扫描 —— 逐块检查标记位，未标记的回收
2. 空闲列表 —— 回收的内存进入空闲列表，下次分配复用
3. 碎片问题 —— 标记-清除不移动对象，会产生内存碎片（靠 Compact 解决）
```

## Compact

Compact（整理/压缩）阶段把存活对象向一端移动，让它们连续排列，消除 Sweep 留下的碎片。这样下次分配大对象时更容易找到连续空间。

```js
// 整理算法的简化示意：把存活对象搬到连续区间
function compact(memory, aliveSet) {
  let write = 0;
  for (let read = 0; read < memory.length; read++) {
    if (aliveSet.has(memory[read])) {
      memory[write] = memory[read];   // 存活对象前移
      write++;
    }
  }
  memory.length = write;              // 截断尾部碎片
  return memory;
}
```

```text
Compact 阶段的要点：
1. 消除碎片 —— 存活对象连续排列，空闲空间合并成整块
2. 代价更高 —— 要移动对象、更新引用，比只清除慢
3. 按需触发 —— 碎片严重时才整理，不是每轮都做
4. 配合分代 —— 老年代用标记-整理，年轻代用复制式回收
```

## Generational GC

分代 GC 基于「大多数对象朝生夕死」的经验假设：把堆分成新生代（Young）与老生代（Old）。新生代对象存活时间短、回收频繁且快；活得久的对象晋升到老生代，回收频率低但范围大。

```js
// 分代策略的简化示意：对象按存活次数晋升
class Heap {
  constructor() {
    this.young = new Set();  // 新生代，回收频繁
    this.old = new Set();    // 老生代，回收低频
  }
  promote(obj, survivedGC) {
    if (survivedGC >= 2) {   // 挺过两次新生代回收就晋升
      this.young.delete(obj);
      this.old.add(obj);
    }
  }
}
```

```text
分代 GC 的要点：
1. 新生代 —— Scavenge（复制式）回收，快但空间小，存活对象少
2. 老生代 —— Mark-Sweep + Compact，慢但频率低
3. 晋升 —— 年轻对象活过多次 GC 后搬进老生代
4. 收益 —— 高频小回收只扫新生代，避免全堆扫描
```

## 进阶：V8 GC 的具体算法

```text
新生代：Scavenger（半空间复制）
1. 新生代分成 From / To 两个等大空间，对象只分配在 From。
2. 回收时把 From 里的活对象复制到 To（Cheney 算法，广度优先），
   垃圾对象不复制、直接丢弃，然后 From / To 互换。
3. 只复制活对象 → 存活率低时极快，代价是要牺牲一半空间。
4. 晋升 —— 挺过一次 Scavenge 就半晋升（移到中间代），挺过两次或 To 空间满了，
   就整批搬到老生代。
```

```text
老生代：Mark-Sweep + Mark-Compact
1. 常规回收走增量标记 + 惰性清理（lazy sweeping），把标记拆成小片穿插在 JS 执行间隙。
2. 内存碎片严重时触发 Full GC，做 Mark-Compact 整理，这个会明显停顿（stop-the-world）。
3. 并发标记 —— 用独立线程在后台做标记，主线程继续执行 JS；
   靠「写屏障」记录「老对象指向新对象」的引用，避免漏标。
```

```text
Orinoco 项目与停顿优化：
1. V8 的 GC 代号 Orinoco，核心目标是把 stop-the-world 停顿降到最小。
2. 演进路径：串行 → 并行（多线程一起标）→ 增量（分片）→ 并发（后台线程）。
3. 大对象（超大 ArrayBuffer / 大数组）直接进大对象空间，不参与复制，
   因此频繁分配大对象会直接抬升老生代 / 大对象空间，触发更重的回收。
```

```text
选型与适用场景：
1. Scavenger —— 大量短命临时对象的场景最优，代价是双倍空间。
2. Mark-Sweep —— 老生代常规回收，停顿小但会留碎片。
3. Mark-Compact —— 碎片严重 / 需要整块空间时触发，停顿最大但内存最规整。
4. 结论 —— 前端优化内存的通用原则：让对象「朝生夕死」别晋升到老生代，
   大对象复用 buffer 而不是反复 new。
```

## 应用场景实战

### 场景一：用 FinalizationRegistry 观察对象回收

```js
// 观察对象何时被回收，验证可达性
const registry = new FinalizationRegistry((heldValue) => {
  console.log(`${heldValue} 被回收了`);
});

let obj = { data: 'big' };
registry.register(obj, 'obj');

obj = null;           // 断开引用
// 触发 GC 后（时机不定），会打印 "obj 被回收了"
// 注：GC 时机由引擎决定，不能强制，仅作观察用途
```

### 场景二：减少对象分配降低 GC 压力

```js
// 高频循环里避免每次创建新对象，减少新生代回收压力
// 差：每帧分配 1000 个新对象
function bad(items) {
  return items.map(item => ({ ...item, done: true }));
}

// 好：复用已有结构，或用基础类型
function good(items) {
  const result = new Array(items.length);
  for (let i = 0; i < items.length; i++) {
    result[i] = items[i];
  }
  return result;
}

// 动画循环里同理：临时对象会频繁触发新生代 GC
let cache = null;
function onFrame(data) {
  if (!cache || cache.length !== data.length) cache = new Float32Array(data.length);
  cache.set(data);   // 复用缓冲区，不每次 new
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 高频路径（动画、滚动、大循环）里避免频繁创建临时对象
2. 大对象、长生命周期的缓存对象别乱 new，考虑复用
3. 用 FinalizationRegistry 观察回收时机，但别依赖它做业务逻辑
4. 理解分代：短命对象别混进老生代，避免污染老年代
5. 怀疑内存问题时先看「可达性」：谁还在引用这个对象

### 踩坑记录

```text
坑 1：以为引用环一定泄漏
结论：a -> b、b -> a 的环对象无法被回收，是误解。
原因：现代 GC 用标记-清除，不依赖引用计数，环也能回收。
解法：只有「从根仍可达的环」才会泄漏，环本身不可达不是问题。

坑 2：依赖 GC 的精确时机
结论：FinalizationRegistry 回调迟迟不触发，以为是 bug。
原因：GC 时机由引擎决定，不保证立即回收，甚至可能永不触发。
解法：GC 观察只用于调试，业务清理逻辑用显式 dispose。

坑 3：在动画循环里不停 new 对象
结论：页面偶发卡顿，帧率不稳。
原因：每帧分配大量临时对象，触发频繁的新生代 GC。
解法：复用缓冲区、对象池，或改用基础类型数组。

坑 4：把短命对象误挂到全局
结论：本来该被回收的对象一直留在内存里。
原因：挂到 window/全局 Map 后从根可达，永远不会被回收。
解法：局部变量能解决的别提升作用域，用完手动置 null。

坑 5：频繁分配大对象导致老生代膨胀、Full GC 卡顿
结论：动画 / 大文件解析里反复 new 大数组，页面周期性长卡顿。
原因：大对象直接进老生代 / 大对象空间，不经过新生代快速回收，
     积多了就触发昂贵的 Mark-Compact Full GC。
解法：大 buffer 复用（ArrayBuffer / Float32Array 池），避免一次性 new 几十 MB 又丢弃。

坑 6：WeakRef.deref() 返回 undefined 就以为对象已回收
结论：缓存逻辑判断「数据没了」而重复加载，或漏掉了即将出现的对象。
原因：WeakRef 不保证回收时机，同一轮事件循环内对象可能「复活」；
     deref 返回 undefined 不代表对象已不可达，只代表当前不可见。
解法：WeakRef 只做「尽力而为」的缓存辅助，不能当可靠的存活判定或业务依据。
```
