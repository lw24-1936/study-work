## 概述

前端领域拆分是把一个大型前端应用按「业务领域」切割成相互独立、边界清晰模块的过程，让每个领域拥有自己的 UI、逻辑、数据与 API 访问。它解决的核心痛点是：应用变大后，组件、状态、请求互相纠缠，改一处功能要动十几个文件。领域拆分让团队能按业务边界分工、并行开发、独立演进。

```text
领域拆分的目标：
1. 高内聚 —— 一个领域相关的代码放在一起
2. 低耦合 —— 领域之间只通过明确接口交互
3. 边界清晰 —— 每个模块职责单一
4. 可并行 —— 不同团队独立开发不同领域
5. 可演进 —— 单个领域可独立重构甚至替换
```

```text
按领域拆分的典型目录：
src/
├── features/          # 业务领域（Feature）
├── domain/            # 领域模型（Domain）
├── shared/            # 跨领域共享（Shared）
├── ui/                # 通用 UI 组件（UI）
├── api/               # 数据访问层（API）
└── state/             # 状态管理（State）
```

## Feature

Feature（特性/功能）是领域拆分的核心单元：一个 Feature 对应一个完整的业务能力，内部包含实现该能力所需的一切——组件、hooks、状态、API 调用、类型。Feature 之间原则上不互相 import，共享能力下沉到 Shared 或 Domain。

```text
Feature 的组织原则：
1. 按业务能力划分 —— 一个 Feature 一件事
2. 自包含 —— 内部包含该能力的全部实现
3. 禁止横向依赖 —— Feature 之间不直接引用
4. 可整体移除 —— 删掉一个 Feature 不影响其他
```

```tsx
// features/orders/ 目录（一个完整的订单 Feature）
// index.ts 对外只暴露明确入口
export { OrderListPage } from './OrderListPage';
export { usePlaceOrder } from './hooks/usePlaceOrder';
export type { Order } from './types';

// hooks/usePlaceOrder.ts —— 内部逻辑
export function usePlaceOrder() {
  const { mutate } = useCreateOrder();
  return { placeOrder: (items: CartItem[]) => mutate(items) };
}
```

Feature 是「纵向切片」：从 UI 一路切到数据层，而非按「组件/容器/服务」这样的技术分层横向切。横向切会让「订单」的代码散落十几个目录，纵向切让订单相关代码聚在一个文件夹。

## Domain

Domain（领域层）存放与业务规则相关的、可脱离 UI 与框架的纯逻辑：领域模型、类型定义、业务计算、校验规则。它是领域拆分的「大脑」，不依赖 React/Vue 等框架，也不直接发请求，保证可复用和可测试。

```text
领域层的内容：
1. 领域类型 —— 实体、值对象、枚举
2. 业务规则 —— 状态机、校验、计算
3. 纯函数 —— 可独立测试的领域操作
4. 不依赖框架 —— 不 import React、不碰 DOM
```

```ts
// domain/orders.ts —— 纯领域逻辑，无框架依赖
export type OrderStatus = 'pending' | 'paid' | 'shipped' | 'completed';

export interface Order {
  id: string;
  status: OrderStatus;
  items: OrderItem[];
}

export function canCancel(order: Order): boolean {
  return order.status === 'pending' || order.status === 'paid';
}

export function orderTotal(order: Order): number {
  return order.items.reduce((sum, i) => sum + i.price * i.qty, 0);
}
```

领域层与 Feature 的关系：Feature 负责「组装」——把领域层的规则接到 UI 和数据上；领域层负责「决策」——所有 if/else 业务判断都在这里。领域层做成无框架依赖的纯 TypeScript，是它可测、可复用的关键。

## Shared

Shared（共享层）存放跨领域复用的、与具体业务无关的通用能力：工具函数、常量、通用类型、基础组件、hooks。它与 Domain 的区别在于：Shared 不含业务规则，是可被任何 Feature 使用的「公共设施」。

```text
共享层的内容：
1. 工具函数 —— 格式化、转换、通用算法
2. 通用类型 —— 泛型类型、Result
3. 基础组件 —— Button、Modal、Table
4. 通用 hooks —— useDebounce、useLocalStorage
```

```ts
// shared/format.ts —— 通用工具，不含业务
export function formatCurrency(amount: number, currency = 'CNY'): string {
  return new Intl.NumberFormat('zh-CN', {
    style: 'currency',
    currency,
  }).format(amount);
}

// shared/result.ts —— 通用错误处理类型
export type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };
```

Shared 层的纪律是「克制」：能不下沉就不下沉，避免 Shared 变成新「杂物间」。判断标准是「是否被至少两个 Feature 使用、且不含业务含义」。只被一个 Feature 用的代码，应留在那个 Feature 内部。

## UI

UI 层存放与具体业务无关的「展示型组件」：按钮、表单控件、布局、图标等纯视觉组件。它们是「哑组件」（dumb component），只通过 props 接收数据、通过回调上报事件，不含业务规则，也不知道数据从哪来。

```text
UI 层与 Feature 组件的区别：
1. UI 组件 —— 通用、可复用、无业务，放 ui/
2. Feature 组件 —— 绑定业务、拼装数据，放 features/xxx/
3. UI 组件不 import Feature —— 依赖方向朝下
4. UI 组件靠 props 通信 —— 不读 store、不发请求
```

```tsx
// ui/Button.tsx —— 通用按钮，无业务含义
interface ButtonProps {
  label: string;
  onClick: () => void;
  variant?: 'primary' | 'secondary';
  disabled?: boolean;
}

export function Button({ label, onClick, variant = 'primary', disabled }: ButtonProps) {
  return (
    <button className={`btn btn-${variant}`} onClick={onClick} disabled={disabled}>
      {label}
    </button>
  );
}
```

UI 层的价值在于复用和一致性：所有 Feature 共用一套 Button/Input/Table，视觉统一，改一处全站生效。若 UI 组件里出现「订单」「用户」等业务字段，说明业务泄漏，应当拆回 Feature。

## API

API 层是应用与后端交互的「统一出入口」：封装 HTTP 客户端、定义请求/响应类型、处理鉴权、错误与重试。所有 Feature 都通过 API 层访问数据，而非各自散落调用 fetch/axios，从而统一处理 token、超时、错误码。

```text
API 层的职责：
1. 封装请求 —— 统一 baseURL、headers、拦截器
2. 类型定义 —— 请求参数与响应结构
3. 错误处理 —— 统一错误码映射、重试
4. 与领域解耦 —— 返回 DTO，由 Feature 转成领域对象
```

```ts
// api/client.ts —— 统一 HTTP 客户端
export async function request<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`${BASE_URL}${path}`, {
    ...init,
    headers: {
      'content-type': 'application/json',
      authorization: `Bearer ${getToken()}`,
      ...init?.headers,
    },
  });
  if (!res.ok) throw new ApiError(res.status, await res.text());
  return res.json() as Promise<T>;
}

// api/orders.ts —— 订单域的数据访问
export const orderApi = {
  list: () => request<OrderDto[]>('/api/orders'),
  cancel: (id: string) => request<void>(`/api/orders/${id}/cancel`, { method: 'POST' }),
};
```

API 层是「防腐层」：后端返回的字段命名（snake_case、缩写）在这里统一转换成前端领域的类型，避免后端结构变化波及整个应用。

## State

State（状态层）负责管理应用的全局/共享状态：用户信息、购物车、主题、跨 Feature 的共享数据。它规定「哪些状态放全局、哪些放局部」，以及状态如何更新、持久化、跨 Feature 消费。

```text
状态分层策略：
1. 服务端状态 —— 接口数据，用 TanStack Query 缓存
2. 客户端状态 —— UI 状态、表单，就近管理
3. 全局状态 —— 跨 Feature 共享，放 store
4. 状态尽量下沉 —— 能局部的就不全局
```

```ts
// state/cart.ts —— 购物车状态（Zustand 风格）
import { create } from 'zustand';

interface CartState {
  items: CartItem[];
  add: (item: CartItem) => void;
  clear: () => void;
}

export const useCartStore = create<CartState>((set) => ({
  items: [],
  add: (item) => set((s) => ({ items: [...s.items, item] })),
  clear: () => set({ items: [] }),
}));
```

状态层的核心纪律：不要让状态成为新的「全局变量」。优先用服务端状态库管理接口数据，客户端状态尽量放组件内部，只有真正跨 Feature 共享的状态才进全局 store。

## 应用场景实战

### 场景一：电商应用的完整领域拆分

```text
src/
├── features/
│   ├── catalog/        # 商品浏览
│   ├── cart/           # 购物车
│   ├── checkout/       # 结账
│   └── account/        # 账户
├── domain/             # 领域模型
├── api/                # 数据访问
├── ui/                 # 通用组件
├── shared/             # 工具函数
└── state/              # 状态管理
```

```ts
// features/cart/ 只依赖 domain、api、shared，不依赖其他 Feature
import { useCartStore } from '../../state/cart';
import { productApi } from '../../api/products';

export function useAddToCart() {
  const add = useCartStore((s) => s.add);
  return async (productId: string) => {
    const product = await productApi.get(productId);
    add({ id: product.id, name: product.name, price: product.price, qty: 1 });
  };
}
```

### 场景二：跨领域协作通过公开接口解耦

```tsx
// 结账 Feature 读取购物车，通过 store 公开接口而非 import cart 内部
import { useCartStore } from '../../state/cart';
import { orderApi } from '../../api/orders';

export function CheckoutPage() {
  const items = useCartStore((s) => s.items);
  const clear = useCartStore((s) => s.clear);

  const submit = async () => {
    await orderApi.create(items);
    clear();
  };

  return (
    <div>
      <h2>确认订单</h2>
      <ul>{items.map((i) => <li key={i.id}>{i.name} x {i.qty}</li>)}</ul>
      <button onClick={submit}>提交订单</button>
    </div>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先按业务能力切 Feature，再在 Feature 内部按技术分层
2. 依赖方向单向：Feature → Domain/API/Shared，禁止反向
3. 领域层做成无框架的纯 TypeScript，保证可测试可复用
4. 服务端状态交给数据缓存库，全局 store 只放共享客户端状态
5. API 层统一做鉴权、错误、DTO 转换，不让组件裸调 fetch
6. Shared 层保持克制，只有多 Feature 复用且无业务含义的代码才下沉

### 踩坑记录

```text
坑 1：Shared 层演变成杂物间
结论：Shared 目录膨胀到几百个文件，业务逻辑混入。
原因：把所有「看起来能复用」的代码都塞进 Shared。
解法：只下沉多 Feature 复用且无业务含义的代码。

坑 2：Feature 之间互相 import
结论：A Feature import B Feature 内部组件，改动连锁反应。
原因：没有建立 Feature 间的依赖边界。
解法：Feature 间通过 Shared/State/API 或事件协作，禁止直接 import。

坑 3：领域层 import 了 React
结论：domain 里出现 useState，无法脱离组件复用。
原因：业务规则和 UI 副作用混写。
解法：领域层纯函数化，副作用交给 Feature 的 hooks。

坑 4：API 层返回裸后端结构
结论：组件里到处是 snake_case 字段和 res.data.xxx 转换。
原因：没有做 DTO 到领域对象的映射。
解法：在 API 层完成字段转换，对外只暴露前端领域类型。

坑 5：全局 store 塞满服务端数据
结论：接口数据全进 store，缓存、失效、去重一团糟。
原因：用客户端状态库硬管服务端状态。
解法：服务端状态用 TanStack Query 等缓存库，客户端状态才进 store。
```
