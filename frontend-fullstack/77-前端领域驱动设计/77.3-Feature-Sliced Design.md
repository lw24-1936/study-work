## 概述

Feature-Sliced Design（FSD，特性切片设计）是一套面向大型前端应用的架构方法论，用七层结构把项目按「业务领域 + 复用程度」组织起来，并规定了严格的单向依赖规则。它的核心理念是「项目结构反映业务结构」，让新人能「从文件夹读懂产品」，让改动的影响范围可预测。

```text
FSD 的七层（从上到下，依赖只能向下）：
1. app/      应用初始化、路由、全局样式
2. pages/    页面：把 widget / feature 组装成路由页面
3. widgets/  大型组合块：页面的一段完整区域
4. features/ 用户交互单元：一个完整的业务动作
5. entities/ 业务实体：领域数据的展示与基础操作
6. shared/   通用基础代码：UI kit、工具函数、API 客户端
```

```text
FSD 的依赖规则：
1. 单向依赖 —— 上层可依赖下层，下层禁止依赖上层
2. 同层隔离 —— 同一层之间尽量不互相依赖
3. 切片（slice）—— 每层按业务领域分成切片
4. 段（segment）—— 切片内按技术类型分段（ui/api/model/lib）
```

## App

App 层是应用的「外壳」：它负责初始化整个应用、装配全局 Provider、配置路由、引入全局样式和主题。App 是唯一可以「把一切拼起来」的层，它依赖所有下层，但不被任何层依赖，也不包含业务逻辑。

```text
App 层的内容：
1. 入口文件 —— main.tsx / App.tsx
2. 路由装配 —— 把 pages 映射到 URL
3. 全局 Provider —— store、i18n、主题、错误边界
4. 全局样式 —— reset、主题变量、字体
```

```tsx
// app/main.tsx —— 应用入口，装配全局能力
import { createRoot } from 'react-dom/client';
import { BrowserRouter } from 'react-router-dom';
import { Provider } from 'react-redux';
import { store } from './store';
import { App } from './App';
import './styles/global.css';

createRoot(document.getElementById('root')!).render(
  <Provider store={store}>
    <BrowserRouter>
      <App />
    </BrowserRouter>
  </Provider>,
);
```

```tsx
// app/App.tsx —— 路由装配
import { Routes, Route } from 'react-router-dom';
import { HomePage } from '@/pages/home';
import { CartPage } from '@/pages/cart';

export function App() {
  return (
    <Routes>
      <Route path="/" element={<HomePage />} />
      <Route path="/cart" element={<CartPage />} />
    </Routes>
  );
}
```

App 层要保持「薄」：它只做装配和初始化，不写业务逻辑。一旦 App 里出现业务判断，说明分层失守了。全局 Provider 的配置（theme、locale、store）是 App 层最典型的职责。

## Pages

Pages 层是「完整页面」的组装层：一个 Page 对应一个路由，负责把 widgets 和 features 拼成一个可访问的页面，处理路由参数、页面级数据获取和布局。Page 自身尽量不含交互细节，细节下沉到 widget / feature。

```text
Pages 层的职责：
1. 对应路由 —— 一个 Page 一个 URL
2. 组装 —— 把 widget / feature 排布成页面
3. 页面级数据 —— 处理路由参数、页面初始化请求
4. 不写交互细节 —— 复杂交互交给下层
```

```tsx
// pages/product/ProductPage.tsx —— 商品详情页
import { useParams } from 'react-router-dom';
import { ProductInfo } from '@/widgets/product-info';
import { AddToCartButton } from '@/features/add-to-cart';
import { useProduct } from './lib/use-product';

export function ProductPage() {
  const { id } = useParams();
  const { product } = useProduct(id!);

  return (
    <div className="product-page">
      <ProductInfo product={product} />
      <AddToCartButton productId={id!} />
    </div>
  );
}
```

Pages 层与 Widgets 层的边界在于「可复用性」：Page 是路由专属的、不可复用的；Widget 是可以被多个 Page 复用的页面区块。Page 变复杂时，应把重复出现的区块下沉成 Widget。

## Widgets

Widgets 层是「大型组合块」：它把多个 features 和 entities 组合成页面里的一个完整独立区域，如页头、商品卡片区、购物车侧栏。Widget 是可复用的「页面局部」，比 Feature 更大、更贴近页面布局。

```text
Widgets 层的特征：
1. 组合块 —— 由 feature / entity 拼成的区域
2. 可复用 —— 多个 Page 共用同一 Widget
3. 独立区域 —— 页头、侧栏、卡片列表等
4. 不含跨区域状态 —— 状态就近放 feature/entity
```

```tsx
// widgets/product-list/ProductList.tsx —— 商品列表区
import { ProductCard } from '@/entities/product';
import { AddToCartButton } from '@/features/add-to-cart';

export function ProductList({ products }: { products: Product[] }) {
  return (
    <div className="product-list">
      {products.map((p) => (
        <ProductCard key={p.id} product={p}>
          <AddToCartButton productId={p.id} />
        </ProductCard>
      ))}
    </div>
  );
}
```

Widget 与 Feature 的区别是粒度：Feature 是「一个动作」的交互单元（点赞、加购、搜索），Widget 是「一块区域」的布局单元（把多个动作拼成区域）。Widget 层不是必须的——小项目可以从 Feature 直接跳到 Page。

## Features

Features 层是「用户交互单元」：一个 Feature 承载一个完整的业务动作，如「添加购物车」「提交评论」「搜索商品」。它是 FSD 里最活跃的层，包含该动作所需的 UI、状态、副作用，通过 entities 的模型和 shared 的工具来实现。

```text
Features 层的特征：
1. 一个动作 —— 一个 Feature 一个用户意图
2. 业务交互 —— 包含按钮、表单、弹窗等交互
3. 依赖 entities —— 复用业务实体的数据与操作
4. 不互相依赖 —— Feature 之间不 import 彼此
```

```tsx
// features/add-to-cart/AddToCartButton.tsx —— 加购 Feature
import { useCart } from '@/entities/cart';
import { Button } from '@/shared/ui/button';

export function AddToCartButton({ productId }: { productId: string }) {
  const { add, isAdding } = useCart();

  return (
    <Button
      label="加入购物车"
      loading={isAdding}
      onClick={() => add(productId)}
    />
  );
}
```

```tsx
// features/search/SearchBar.tsx —— 搜索 Feature
export function SearchBar() {
  const { query, setQuery, results } = useSearch();
  return (
    <div>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ul>{results.map((r) => <li key={r.id}>{r.name}</li>)}</ul>
    </div>
  );
}
```

Feature 之间如何协作？通过实体层的共享状态（如两个 Feature 都读写 cart entity 的 store）或通过页面层编排，而不是直接 import。这保持了 Feature 的独立性和可组合性。

## Entities

Entities 层是「业务实体」的展示与基础操作：它围绕领域对象（商品、订单、用户）组织 UI 卡片、类型定义、store 切片和 API 调用。Entity 是「最小业务单元」，被 features 和 widgets 复用，本身不含复杂的跨实体交互。

```text
Entities 层的内容（以 product 为例）：
1. ui/ —— ProductCard、ProductImage 展示组件
2. model/ —— 类型、store、常量的领域模型
3. api/ —— 该实体的数据访问
4. lib/ —— 该实体的工具函数
```

```tsx
// entities/product/model/store.ts —— 商品实体的状态
import { create } from 'zustand';

interface ProductState {
  products: Record<string, Product>;
  load: (id: string) => Promise<void>;
}

export const useProductStore = create<ProductState>((set) => ({
  products: {},
  load: async (id) => {
    const product = await productApi.get(id);
    set((s) => ({ products: { ...s.products, [id]: product } }));
  },
}));
```

```tsx
// entities/product/ui/ProductCard.tsx —— 商品实体的展示
export function ProductCard({ product, children }: { product: Product; children?: ReactNode }) {
  return (
    <div className="product-card">
      <img src={product.image} alt={product.name} />
      <h3>{product.name}</h3>
      <span>{product.price}</span>
      {children}
    </div>
  );
}
```

Entity 与 Feature 的分工：Entity 提供「商品的展示和基础数据」，Feature 提供「对商品做某件事的动作」。把「加购」放进 product entity 会让实体过重，放进 feature 则职责清晰。

## Shared

Shared 层是「通用基础」：不含任何业务含义、可被任意层复用的代码——UI kit（按钮、输入框）、工具函数、类型工具、API 客户端、配置常量。它是依赖图的「最底层」，被所有层依赖，但从不依赖任何业务层。

```text
Shared 层的内容：
1. ui/ —— 基础 UI kit（Button、Input、Modal）
2. lib/ —— 工具函数、hooks
3. api/ —— HTTP 客户端、请求封装
4. config/ —— 环境配置、常量
```

```tsx
// shared/ui/Button.tsx —— 通用按钮，无业务
interface ButtonProps {
  label: string;
  onClick?: () => void;
  variant?: 'primary' | 'ghost';
  loading?: boolean;
}

export function Button({ label, onClick, variant = 'primary', loading }: ButtonProps) {
  return (
    <button className={`btn btn-${variant}`} onClick={onClick} disabled={loading}>
      {loading ? '...' : label}
    </button>
  );
}
```

```ts
// shared/lib/format.ts —— 通用工具
export function formatPrice(price: number): string {
  return new Intl.NumberFormat('zh-CN', {
    style: 'currency',
    currency: 'CNY',
  }).format(price);
}
```

Shared 层的最大风险是「业务泄漏」：Button、Input 是合理的；一旦 shared 里出现 ProductCard、OrderStatus 这类业务概念，就违反了分层，应下沉到 entities。

## 应用场景实战

### 场景一：从零搭建 FSD 目录

```text
src/
├── app/
│   ├── main.tsx
│   └── App.tsx
├── pages/
│   └── product/ProductPage.tsx
├── widgets/
│   └── product-list/ProductList.tsx
├── features/
│   ├── add-to-cart/AddToCartButton.tsx
│   └── search/SearchBar.tsx
├── entities/
│   ├── product/ui/ProductCard.tsx
│   ├── product/model/store.ts
│   └── cart/model/store.ts
└── shared/
    ├── ui/Button.tsx
    └── lib/format.ts
```

```tsx
// 组装示例：Page 把 Widget 和 Feature 拼起来
export function ProductPage() {
  const { products } = useProducts();
  return (
    <div>
      <SearchBar />
      <ProductList products={products} />
    </div>
```

### 场景二：新增一个业务功能

```tsx
// 需求：给商品列表增加「收藏」功能 —— 只需新增一个 Feature
// features/favorite/FavoriteButton.tsx
import { useFavoriteStore } from './model/store';
import { Button } from '@/shared/ui/button';

export function FavoriteButton({ productId }: { productId: string }) {
  const { isFav, toggle } = useFavoriteStore(productId);
  return (
    <Button
      label={isFav ? '已收藏' : '收藏'}
      variant={isFav ? 'primary' : 'ghost'}
      onClick={toggle}
    />
  );
}
```

```tsx
// 在 entity 卡片里挂载新 Feature，不修改其他层
// entities/product/ui/ProductCard.tsx
import { FavoriteButton } from '@/features/favorite';

export function ProductCard({ product }: { product: Product }) {
  return (
    <div className="product-card">
      <h3>{product.name}</h3>
      <FavoriteButton productId={product.id} />
    </div>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 从 shared 和 entities 起步，业务长出来后再引入 feature/widget 层
2. 严格单向依赖，用 ESLint 插件（eslint-plugin-boundaries）自动检查
3. 用别名（@/app、@/entities）替代相对路径，避免 ../../../../ 地狱
4. 切片按业务命名而非技术命名，保持「从文件夹读产品」的可读性
5. Feature 保持单一动作，做太多事的 Feature 应拆成多个
6. 小项目不必七层俱全，从 Pages + Features + Shared 三层开始

### 踩坑记录

```text
坑 1：循环依赖
结论：A 依赖 B，B 又依赖 A，打包或运行时报错、架构腐化。
原因：没有守住单向依赖，同层之间互相引用。
解法：用 eslint-plugin-boundaries 强制依赖规则，把共享代码下沉到更底层。

坑 2：相对路径地狱
结论：import 出现 ../../../../../shared/ui/button，移动文件就崩。
原因：没有配置路径别名，深目录只能用相对路径。
解法：在 vite/tsconfig 配 @/app、@/shared 等别名，统一绝对路径。

坑 3：把业务塞进 shared
结论：shared/ui 里出现 ProductCard，shared 层与业务耦合。
原因：贪图方便，把「看起来通用」的业务组件下沉。
解法：凡含业务字段的组件放 entities/features，shared 只留无业务基础件。

坑 4：Feature 之间直接互相 import
结论：收藏 Feature import 加购 Feature 的内部函数，改动互相牵连。
原因：把 Feature 当普通目录，没有隔离交互单元。
解法：Feature 间通过 entity 的共享状态或页面编排协作，禁止直接 import。

坑 5：七层俱全却空有其表
结论：每个层只有一个文件，结构复杂但收益为零。
原因：机械套用 FSD，小项目也强上七层。
解法：按需取舍层，小项目用 Pages + Features + Shared 三层即可，随规模增长再补层。
```
