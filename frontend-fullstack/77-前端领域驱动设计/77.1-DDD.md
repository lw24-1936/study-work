## 概述

DDD（Domain-Driven Design，领域驱动设计）是一套以「业务领域」为核心的软件设计方法论：它把复杂业务拆成清晰的领域模型，让代码结构与业务语言对齐。对前端而言，DDD 的价值不在「照搬后端分层」，而在「把散落在组件里的业务规则收拢到领域模型」，使表单、列表、状态机等 UI 逻辑可复用、可测试。

```text
DDD 的核心思想：
1. 以领域为中心 —— 先理解业务，再谈技术实现
2. 通用语言 —— 团队用同一套词汇描述业务
3. 模型驱动 —— 领域模型是代码结构的蓝图
4. 分层隔离 —— 领域逻辑与 UI、网络、存储解耦
```

```ts
// 前端引入 DDD 的效果：把「订单能否取消」从组件里抽出
function OrderCard({ order }) {
  return <button disabled={order.status !== 'pending'}>取消</button>;
}

// 改为领域模型表达：
class Order {
  canCancel(): boolean {
    return this.status === 'pending' && this.items.length > 0;
  }
}
```

## Domain

Domain（领域）是软件要解决的业务问题本身：电商的领域是商品、订单、库存；金融的领域是账户、交易、风控。DDD 的一切建模都围绕领域展开，技术只是承载领域的工具。

```text
领域建模的步骤：
1. 识别领域 —— 确定业务范围和核心价值
2. 划分限界上下文 —— 把大领域切成相对独立的子领域
3. 建立通用语言 —— 统一术语，代码命名与术语一致
4. 提炼模型 —— 抽象出实体、值对象、聚合等元素
```

```ts
// 领域 = 一组相关的概念和规则，前端用模块承载
export interface OrderDomain {
  place(order: Order): Promise<OrderId>;
  cancel(orderId: OrderId): Promise<void>;
  query(orderId: OrderId): Promise<Order | null>;
}
```

领域与「限界上下文（Bounded Context）」强相关：同一个词在不同上下文里含义不同。例如「用户」在「账户上下文」是登录主体，在「营销上下文」是触达对象，两者应建模成不同的模型，而非硬塞进一个巨型 User 对象。

## Entity

Entity（实体）是有唯一标识、且状态随生命周期变化的领域对象：它靠「身份」被区分，两个实体即使属性完全相同，只要 ID 不同就是两个对象。实体的相等性比较的是标识，而非属性值。

```text
实体的特征：
1. 有唯一标识 —— 通过 ID 区分个体
2. 可变 —— 属性随业务操作变化
3. 有生命周期 —— 从创建到归档
4. 相等性基于标识 —— 同 ID 即同一实体
```

```ts
class User {
  constructor(
    public readonly id: string,
    public name: string,
    private _status: 'active' | 'disabled' = 'active',
  ) {}

  disable() {
    this._status = 'disabled';
  }

  get status() {
    return this._status;
  }
}

const a = new User('u1', 'Alice');
const b = new User('u1', 'Bob');
a.id === b.id; // true —— 同一实体（身份相同）
```

在前端，Entity 常对应「后端返回的一条带 id 的记录」，如列表里的一行订单。把它的业务规则（权限判断、状态流转）封装进 Entity 类，比散在组件里更容易维护和测试。

## Value Object

Value Object（值对象）是没有唯一标识、靠「值」定义的不可变对象：两个值对象只要属性全等就是同一个。值对象描述「是什么」而非「是谁」，通常表达金额、坐标、颜色、日期范围等概念。

```text
值对象的特征：
1. 无标识 —— 身份就是值本身
2. 不可变 —— 修改产生新对象
3. 相等性基于值 —— 属性全等即相等
4. 自校验 —— 构造时保证合法性
```

```ts
class Money {
  private constructor(
    public readonly amount: number,
    public readonly currency: string,
  ) {
    if (amount < 0) throw new Error('金额不能为负');
  }

  static cny(amount: number) {
    return new Money(amount, 'CNY');
  }

  add(other: Money): Money {
    if (this.currency !== other.currency) throw new Error('币种不一致');
    return new Money(this.amount + other.amount, this.currency);
  }

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }
}

Money.cny(10).equals(Money.cny(10)); // true
```

实体和值对象的取舍是 DDD 的经典判断：有独立身份、需追踪生命周期的用实体；只描述性质的用值对象。把「地址」建模成值对象是常见正解——地址变了就是换个新值对象。

## Aggregate

Aggregate（聚合）是一组必须保持业务一致性的实体和值对象的集合，聚合根（Aggregate Root）是对外的唯一入口。外部只能通过聚合根访问和修改内部对象，从而保证「不变量」不被破坏。

```text
聚合的规则：
1. 一个聚合一个根 —— 外部只持有根引用
2. 通过根修改 —— 内部对象只能由根操作
3. 一致性边界 —— 一次事务只改一个聚合
4. 小聚合优先 —— 越小越容易保证一致
```

```ts
class Order {
  private items: OrderItem[] = [];
  private status: OrderStatus = 'pending';

  addItem(item: OrderItem) {
    if (this.status !== 'pending') throw new Error('订单已提交');
    this.items.push(item);
  }

  submit() {
    if (this.items.length === 0) throw new Error('空订单不能提交');
    this.status = 'submitted';
  }
}
```

前端引入聚合的价值：把「库存扣减 + 订单状态 + 明细」这类必须一起变化的逻辑封在同一个对象里，避免多个组件各自改一处状态导致不一致。聚合根天然适合做表单/编辑器的单一数据源。

## Repository

Repository（仓储）是领域对象的「存取抽象」：它把「对象如何持久化/从哪加载」的技术细节隐藏起来，让领域代码只面对一个像内存集合一样的接口。领域层只依赖仓储接口，不关心背后是 HTTP、IndexedDB 还是本地缓存。

```text
仓储的职责：
1. 集合式接口 —— save / find / remove
2. 隐藏存储细节 —— 领域不感知 HTTP / DB
3. 边界防腐 —— 领域对象与存储结构解耦
4. 可替换 —— 切换后端不影响领域逻辑
```

```ts
// 仓储接口（领域层定义，不依赖具体存储）
interface OrderRepository {
  findById(id: OrderId): Promise<Order | null>;
  save(order: Order): Promise<void>;
  remove(id: OrderId): Promise<void>;
}

// 实现（基础设施层，用 HTTP 访问后端）
class HttpOrderRepository implements OrderRepository {
  async findById(id: OrderId): Promise<Order | null> {
    const res = await fetch(`/api/orders/${id}`);
    if (res.status === 404) return null;
    return toOrder(await res.json());
  }

  async save(order: Order): Promise<void> {
    await fetch(`/api/orders/${order.id}`, {
      method: 'PUT',
      body: JSON.stringify(order),
    });
  }

  async remove(id: OrderId): Promise<void> {
    await fetch(`/api/orders/${id}`, { method: 'DELETE' });
  }
}
```

## Domain Service

Domain Service（领域服务）承载「不属于任何单一实体或值对象」的领域逻辑：当一个业务操作需要协调多个聚合、或规则不属于某个对象时，就交给领域服务。它是无状态的，只编排领域对象，不碰 I/O。

```text
领域服务的判定：
1. 逻辑不属于单个实体 —— 涉及多个聚合协作
2. 无状态 —— 不持有业务状态
3. 纯领域 —— 不直接访问数据库 / 网络
4. 表达业务动作 —— 命名体现领域动词
```

```ts
// 领域服务：转账涉及两个账户，不属于任一账户
class TransferService {
  transfer(from: Account, to: Account, money: Money): void {
    if (from.balance < money.amount) throw new Error('余额不足');
    from.withdraw(money);
    to.deposit(money);
  }
}
```

判断逻辑放哪里的口诀：属于单个对象的放实体/值对象，属于多个对象协作的放领域服务。把「优惠券抵扣 + 满减 + 积分」这类跨对象计算塞进一个实体，会变成臃肿的上帝对象。

## Application Service

Application Service（应用服务）是「用例」的编排层：它接收外部输入（UI 事件、API 请求），协调领域对象和仓储完成一个完整业务动作，并处理事务、权限、日志等横切关注点。应用服务不包含业务规则，业务规则在领域层。

```text
应用服务的职责：
1. 编排用例 —— 串联仓储、领域对象完成操作
2. 事务边界 —— 决定何时提交、回滚
3. 输入输出 —— DTO 与领域对象互转
4. 不写业务规则 —— 规则下沉到领域层
```

```ts
// 应用服务：下单用例的编排
class PlaceOrderService {
  constructor(
    private orders: OrderRepository,
    private inventory: InventoryRepository,
  ) {}

  async placeOrder(cmd: PlaceOrderCommand): Promise<OrderId> {
    const order = Order.create(cmd.customerId);
    for (const line of cmd.lines) {
      order.addItem(new OrderItem(line.productId, line.qty));
    }
    order.submit();
    await this.orders.save(order);
    await this.inventory.reserve(order.items);
    return order.id;
  }
}
```

前端的分层对应：组件（Controller）→ 应用服务（用例编排）→ 领域服务/实体（业务规则）→ 仓储（存储）。应用服务是「薄编排层」，一旦塞满 if/else 业务判断，说明规则泄漏，应当下沉。

## 应用场景实战

### 场景一：购物车结账

```ts
// 把结账逻辑收拢到领域模型 + 应用服务
class Cart {
  private items: CartItem[] = [];

  add(item: CartItem) {
    this.items.push(item);
  }

  total(): Money {
    return this.items
      .map((i) => i.price.multiply(i.qty))
      .reduce((sum, m) => sum.add(m), Money.cny(0));
  }

  isEmpty(): boolean {
    return this.items.length === 0;
  }
}

class CheckoutService {
  constructor(private orders: OrderRepository) {}

  async checkout(cart: Cart, customerId: string): Promise<OrderId> {
    if (cart.isEmpty()) throw new Error('购物车为空');
    const order = Order.fromCart(cart, customerId);
    order.submit();
    await this.orders.save(order);
    return order.id;
  }
}
```

### 场景二：表单校验与提交

```ts
// 用值对象承载表单字段的自校验
class Email {
  private constructor(public readonly value: string) {}

  static parse(raw: string): Email {
    if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(raw)) {
      throw new Error('邮箱格式非法');
    }
    return new Email(raw.trim().toLowerCase());
  }
}

// 组件捕获领域抛出的校验错误，映射到表单
try {
  const email = Email.parse(input);
  await register('Alice', email.value);
} catch (e) {
  setError(String(e));
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 从「识别聚合根」开始建模，聚合越小越好保证一致性
2. 值对象优先于实体：能无标识表达的概念就不要强加 ID
3. 仓储接口定义在领域层，实现在基础设施层，依赖方向朝领域
4. 应用服务保持薄编排，业务规则一律下沉到实体和领域服务
5. 通用语言落地到代码：类名、方法名用业务词汇
6. 一个事务只改一个聚合，跨聚合用领域服务 + 最终一致

### 踩坑记录

```text
坑 1：把贫血模型当 DDD
结论：实体只有 getter/setter，业务逻辑全写在组件里。
原因：只抄了 DDD 的类名，没有把规则放进对象。
解法：把状态流转、校验、计算封装进实体/值对象，组件只调用。

坑 2：无限膨胀的上帝对象
结论：一个 User 类塞进几百个字段，牵一发动全身。
原因：没有划分限界上下文，把所有概念堆进单个实体。
解法：按上下文拆分实体，不同场景用不同的领域模型。

坑 3：值对象建模成实体导致误判
结论：把「地址」「金额」加上 id 当实体，相等性判断混乱。
原因：混淆了「身份」与「值」的区别。
解法：无生命周期、靠值定义的概念建模成值对象。

坑 4：仓储直接暴露存储结构
结论：领域层直接 import API 响应类型，换后端就崩。
原因：仓储接口没有隔离基础设施。
解法：仓储接口用领域对象签名，DTO 转换放实现层。

坑 5：领域服务里写 I/O
结论：领域服务里直接 fetch 和读写 store，无法单测。
原因：把应用服务的编排职责混进领域服务。
解法：领域服务只做纯计算，I/O 交给应用服务 + 仓储。
```
