## 概述

工程规范是用工具链把「代码风格、提交信息、检查时机」统一起来，让团队写出的代码风格一致、提交历史可读、问题在提交前就被拦截。核心是「代码规范靠工具强制，不靠人肉 review 风格」。

```text
工程规范的工具分工：
1. ESLint —— 语法/最佳实践检查，能自动修复
2. Prettier —— 纯格式化（缩进、引号、换行）
3. Stylelint —— CSS 规范检查
4. EditorConfig —— 编辑器基础配置（缩进、换行符）
5. Husky + lint-staged —— 在 git 提交时自动执行检查
6. Commitlint + Commitizen —— 规范提交信息
```

## ESLint

ESLint 是 JS/TS 的静态检查工具，按规则检查代码，很多规则支持 `--fix` 自动修复。它管「逻辑正确性」和「编码风格」，但不做格式化（交给 Prettier）。

```bash
# 安装
npm install -D eslint

# 初始化配置
npx eslint --init
```

```js
// eslint.config.js（flat config）
import js from '@eslint/js';

export default [
  js.configs.recommended,
  {
    rules: {
      'no-unused-vars': 'error',
      'no-console': 'warn',
      'eqeqeq': ['error', 'always'],
    },
  },
];
```

```bash
# 检查
npx eslint src/

# 自动修复
npx eslint src/ --fix
```

```text
ESLint 常见配置：
1. extends —— 继承预设（eslint:recommended、airbnb）
2. rules —— 覆盖具体规则（off/warn/error）
3. plugins —— 加载额外规则集（typescript、react）
4. 配合 Prettier 用 eslint-config-prettier 关闭冲突的格式规则
```

## Prettier

Prettier 是「零配置」的代码格式化工具，只关心格式不关心逻辑，风格选项极少，避免团队在格式上争论。

```bash
npm install -D prettier
```

```json
// .prettierrc.json
{
  "semi": true,
  "singleQuote": true,
  "tabWidth": 2,
  "printWidth": 100,
  "trailingComma": "es5"
}
```

```bash
# 格式化
npx prettier --write src/

# 检查但不修改
npx prettier --check src/
```

```text
ESLint 与 Prettier 的分工：
1. ESLint —— 代码质量（未使用变量、类型错误）
2. Prettier —— 代码格式（引号、缩进、换行）
3. 用 eslint-config-prettier 关闭 ESLint 里与格式冲突的规则
```

```bash
# 关闭 ESLint 与 Prettier 冲突的格式规则
npm install -D eslint-config-prettier
```

```js
// eslint.config.js 里最后引入 prettier 配置，覆盖冲突规则
import prettier from 'eslint-config-prettier';

export default [
  js.configs.recommended,
  prettier,  // 必须放最后
];
```

## Stylelint

Stylelint 是 CSS 的检查工具，检查样式表里的错误和风格问题，支持 SCSS/Less/CSS-in-JS。

```bash
npm install -D stylelint stylelint-config-standard
```

```json
// .stylelintrc.json
{
  "extends": ["stylelint-config-standard"],
  "rules": {
    "color-no-invalid-hex": true,
    "declaration-block-no-duplicate-properties": true,
    "unit-allowed-list": ["px", "rem", "%", "em", "vh", "vw"]
  }
}
```

```bash
# 检查
npx stylelint "src/**/*.css"

# 自动修复
npx stylelint "src/**/*.css" --fix
```

```text
Stylelint 的定位：
1. 检查 CSS 语法错误（无效颜色、重复属性）
2. 强制 CSS 风格约定（单位、命名）
3. 对 CSS 做 ESLint 之于 JS 的事
```

## EditorConfig

EditorConfig 用 `.editorconfig` 文件统一不同编辑器的基础行为（缩进、换行符、字符集），是所有编辑器都支持的最低共识层。

```ini
# .editorconfig
root = true

[*]
charset = utf-8
indent_style = space
indent_size = 2
end_of_line = lf
insert_final_newline = true
trim_trailing_whitespace = true

[*.md]
trim_trailing_whitespace = false
```

```text
EditorConfig 的作用：
1. 跨编辑器统一缩进和换行符
2. 解决 Windows（CRLF）与 Linux/Mac（LF）换行符不一致
3. 是其他工具（Prettier 等）的基础，优先级最低
```

## Husky 与 lint-staged

Husky 管理 git hooks（提交前执行脚本），lint-staged 只对「暂存的文件」跑检查，避免全量扫描。

```bash
npm install -D husky lint-staged
npx husky init
```

```bash
# 添加 pre-commit 钩子
echo "npx lint-staged" > .husky/pre-commit
```

```json
// package.json 里的 lint-staged 配置
{
  "lint-staged": {
    "*.{js,ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{css,scss}": ["stylelint --fix", "prettier --write"]
  }
}
```

```text
Husky + lint-staged 的工作流：
1. git commit 触发 pre-commit 钩子
2. Husky 执行 lint-staged
3. lint-staged 只处理暂存文件，跑检查并修复
4. 检查不通过则提交被阻止
```

```text
只检查暂存文件的好处：
1. 快 —— 不用全量扫描
2. 渐进 —— 老代码不动，新提交的必须合规
```

## Commitlint 与 Commitizen

Commitlint 校验提交信息格式，Commitizen 提供交互式界面帮开发者生成符合规范的提交信息。

```bash
npm install -D @commitlint/cli @commitlint/config-conventional
```

```js
// commitlint.config.js
export default {
  extends: ['@commitlint/config-conventional'],
};
```

```bash
# 添加 commit-msg 钩子
echo "npx --no -- commitlint --edit \$1" > .husky/commit-msg
```

```bash
# 安装 Commitizen
npm install -D commitizen cz-conventional-changelog
```

```json
{
  "config": {
    "commitizen": {
      "path": "cz-conventional-changelog"
    }
  },
  "scripts": {
    "commit": "cz"
  }
}
```

```text
Commitlint vs Commitizen：
1. Commitlint —— 校验（被动，格式不对就拒绝）
2. Commitizen —— 引导（主动，交互式生成合规信息）
3. 两者配合：cz 生成 -> commitlint 校验
```

## Conventional Commits

Conventional Commits（约定式提交）规定提交信息格式为 `type(scope): subject`，让提交历史结构化、可自动生成 changelog 和版本号。

```text
提交信息格式：
<type>(<scope>): <subject>

类型（type）常见取值：
feat     —— 新功能
fix      —— bug 修复
docs     —— 文档变更
style    —— 格式（不影响逻辑）
refactor —— 重构（不改功能）
perf     —— 性能优化
test     —— 测试相关
build    —— 构建/依赖变更
ci       —— CI 配置
chore    —— 杂项
```

```text
提交信息示例：
feat(user): 新增用户登录功能
fix(auth): 修复 token 过期未刷新的问题
docs(readme): 补充安装说明
refactor(utils): 提取日期格式化公共函数
```

```text
约定式提交的价值：
1. 提交历史可读 —— 扫一眼 type 就知道改动性质
2. 自动 changelog —— 从提交信息生成发布说明
3. 自动版本号 —— 根据 type 决定 minor/patch 升级
```

## 应用场景实战

### 场景一：从零搭建规范工具链

```bash
# 1. 安装全部依赖
npm install -D eslint prettier stylelint husky lint-staged \
  @commitlint/cli @commitlint/config-conventional \
  eslint-config-prettier

# 2. 初始化 husky
npx husky init

# 3. 配置 pre-commit 钩子
echo "npx lint-staged" > .husky/pre-commit

# 4. 配置 commit-msg 钩子
echo "npx --no -- commitlint --edit \$1" > .husky/commit-msg

# 5. package.json 加 lint-staged 和 scripts
```

```json
{
  "scripts": {
    "lint": "eslint src/",
    "format": "prettier --write src/",
    "lint:css": "stylelint \"src/**/*.css\"",
    "prepare": "husky"
  },
  "lint-staged": {
    "*.{js,ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.css": ["stylelint --fix", "prettier --write"]
  }
}
```

### 场景二：交互式提交（Commitizen）

```bash
npm run commit
# 交互提示：
# ? 选择提交类型: feat
# ? 影响范围: user
# ? 简短描述: 新增用户列表页
# ? 详细描述: (回车跳过)
# ? 是否有破坏性变更: no
# 生成: feat(user): 新增用户列表页
```

## 最佳实践与踩坑记录

### 最佳实践

1. ESLint 管质量、Prettier 管格式，用 eslint-config-prettier 关闭冲突
2. 提交时用 lint-staged 只查暂存文件，不阻塞全量历史代码
3. EditorConfig 作为最底层共识，其他工具配置保持一致
4. 约定式提交 + Commitlint 强制，配合 Commitizen 降低门槛
5. 把 lint 命令也加进 CI，双保险（本地钩子可被 --no-verify 绕过）

### 踩坑记录

```text
坑 1：ESLint 与 Prettier 规则冲突
结论：eslint --fix 和 prettier 反复打架，格式来回变。
原因：ESLint 的格式规则与 Prettier 规则不一致。
解法：引入 eslint-config-prettier 并放配置最后，关闭冲突规则。

坑 2：Husky 钩子不触发
结论：提交时 pre-commit 没执行。
原因：.husky 目录没提交、或 core.hooksPath 未指向 .husky。
解法：确认 .husky/pre-commit 有可执行权限且已提交，重新 npx husky init。

坑 3：lint-staged 匹配不到文件
结论：改了文件但 lint-staged 没跑。
原因：glob 模式与文件扩展名不匹配，或文件在暂存区外。
解法：检查 lint-staged 的 glob 是否覆盖实际文件后缀。

坑 4：--no-verify 绕过钩子导致 CI 挂
结论：本地 git commit --no-verify 跳过检查，提交到 CI 才报错。
原因：钩子可被 --no-verify 跳过，本地偷懒绕过。
解法：CI 里加 npm run lint，作为不可绕过的最终防线。

坑 5：commitlint 校验不到（commit-msg 路径错误）
结论：提交信息不合法却没被拦截。
原因：commit-msg 钩子里 $1 未转义或路径写错。
解法：钩子写 npx --no -- commitlint --edit \$1（注意 $ 要转义）。
```
