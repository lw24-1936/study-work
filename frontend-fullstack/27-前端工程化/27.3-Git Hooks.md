## 概述

Git Hooks 是 Git 在特定事件（提交、推送等）时自动执行的脚本，用于在「本地」拦截问题，让有问题的代码进不了仓库。配合 Husky 管理，配合 CI 做服务端兜底，形成双层防线。

```text
常见 hook 及触发时机：
1. pre-commit —— 提交前（git commit 但还没生成 commit）
2. commit-msg  —— 提交信息写好后（校验 message 格式）
3. pre-push    —— 推送前（git push 但还没到远程）
4. 服务端兜底 —— CI Validation（不可被本地绕过）
```

```text
hook 脚本的位置：
1. .git/hooks/ —— Git 原生 hook 目录（不入库）
2. .husky/ —— Husky 管理，可提交到仓库共享
```

## pre-commit

pre-commit 在「提交前」触发，常用于跑 lint、格式化、测试，检查通过才允许生成 commit。

```bash
# .husky/pre-commit 内容
npx lint-staged
```

```json
// package.json
{
  "lint-staged": {
    "*.{js,ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.css": ["stylelint --fix"]
  }
}
```

```bash
# 提交时自动执行，不通过则中断提交
git add .
git commit -m "feat: xxx"
# 触发 pre-commit -> lint-staged -> 检查并修复暂存文件
```

```text
pre-commit 的典型任务：
1. 代码检查 —— eslint、stylelint
2. 格式化 —— prettier
3. 秘密扫描 —— 防止把 key/token 提交进去
4. 单元测试（轻量，太重会拖慢提交）
```

```bash
# 也可以直接跑测试
# .husky/pre-commit
npm test
```

```text
pre-commit 的权衡：
1. 太快 —— 只能查格式，查不了逻辑
2. 太慢 —— 每次提交都等，开发者烦躁
3. 建议：lint-staged 只查暂存文件，重量级测试放 pre-push 或 CI
```

## commit-msg

commit-msg 在「提交信息写好之后」触发，用于校验 message 是否符合规范（如 Conventional Commits）。

```bash
# .husky/commit-msg 内容
npx --no -- commitlint --edit $1
```

```js
// commitlint.config.js
export default {
  extends: ['@commitlint/config-conventional'],
};
```

```bash
# 不合规的提交信息会被拦截
git commit -m "改了点东西"   # 拦截：不符合 type(scope): subject
git commit -m "feat(user): 新增登录"  # 通过
```

```text
commit-msg 的参数：
1. $1 —— 指向存有提交信息的临时文件
2. commitlint --edit $1 读取该文件做校验
3. 校验失败返回非 0 退出码，提交被取消
```

```text
commit-msg 校验的价值：
1. 强制约定式提交，提交历史结构化
2. 为自动 changelog 和版本号提供依据
```

## pre-push

pre-push 在「推送前」触发，适合跑重量级检查（全量测试、构建），避免把坏代码推到远程。

```bash
# .husky/pre-push 内容
npm run test
npm run build
```

```text
pre-push 与 pre-commit 的分工：
1. pre-commit —— 快（lint、格式），每次提交都跑
2. pre-push —— 慢（测试、构建），推送前跑一次
3. 这样提交频繁但推送时才做完整验证
```

```text
pre-push 的典型任务：
1. 全量单元测试
2. 构建验证（确保能编译）
3. 集成测试
```

```bash
# 也可以只推当前分支时跑
# .husky/pre-push 脚本
branch=$(git symbolic-ref --short HEAD)
if [ "$branch" = "main" ]; then
  npm run test
fi
```

## CI Validation

CI Validation 是「服务端兜底」，在 push 之后由 CI 系统（GitHub Actions、GitLab CI）跑完整检查。本地 hook 可被 `--no-verify` 绕过，CI 绕不过。

```yaml
# GitHub Actions
name: CI
on: [push, pull_request]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npx tsc --noEmit
      - run: npx eslint src/
      - run: npx prettier --check src/
      - run: npm test
      - run: npm run build
```

```text
CI Validation 与本地 hook 的分层：
1. 本地 pre-commit —— 第一道，快速反馈（可被绕过）
2. 本地 pre-push —— 第二道，较重验证（可被绕过）
3. CI —— 最终防线，不可绕过，合并/部署前必须通过
```

```text
CI 是权威的原因：
1. --no-verify 能跳过本地 hook
2. 开发者机器环境差异导致本地「能过 CI 挂」
3. CI 环境干净可复现，结果可信
```

```text
CI 的扩展能力：
1. 跑测试矩阵（多 Node 版本、多浏览器）
2. 生成覆盖率报告
3. 自动部署、发 changelog
4. PR 时强制检查通过才能合并（branch protection）
```

## 应用场景实战

### 场景一：完整 Hook 链路配置

```bash
# 初始化 husky
npm install -D husky lint-staged @commitlint/cli @commitlint/config-conventional
npx husky init

# pre-commit：lint + 格式化暂存文件
echo "npx lint-staged" > .husky/pre-commit

# commit-msg：校验提交信息
echo "npx --no -- commitlint --edit \$1" > .husky/commit-msg

# pre-push：跑测试和构建
printf 'npm test\nnpm run build\n' > .husky/pre-push
```

```json
{
  "scripts": {
    "prepare": "husky",
    "test": "vitest run",
    "build": "vite build"
  },
  "lint-staged": {
    "*.{js,ts,tsx}": ["eslint --fix", "prettier --write"]
  }
}
```

### 场景二：分支保护 + CI 强制

```text
GitHub 分支保护设置：
1. main 分支开启 branch protection
2. 勾选「Require status checks to pass before merging」
3. 选择 CI 的 validate job
4. 未通过 CI 的 PR 无法合并，即使本地 hook 被绕过
```

```yaml
# 只对 main 分支的 PR 跑完整检查
on:
  pull_request:
    branches: [main]
```

## 最佳实践与踩坑记录

### 最佳实践

1. 本地 hook 做快速反馈（lint/格式），重量级检查放 CI
2. pre-commit 只查暂存文件（lint-staged），不拖慢提交
3. 提交信息用 commit-msg 强制约定式提交
4. 分支保护 + CI 状态检查是权威防线，别只依赖本地 hook
5. hook 脚本要提交到仓库（.husky/），团队共享

### 踩坑记录

```text
坑 1：.husky 目录没提交，同事机器 hook 不生效
结论：自己的 hook 生效，同事 clone 后不生效。
原因：.husky 在 .gitignore 里或被忽略，没进仓库。
解法：确认 .husky/ 已 git add 提交，package.json 有 prepare: husky。

坑 2：hook 脚本无执行权限
结论：hook 触发时报 permission denied。
原因：Windows 或复制过程丢失了可执行权限。
解法：chmod +x .husky/pre-commit 等脚本，或重新 npx husky init。

坑 3：--no-verify 绕过本地检查
结论：git commit --no-verify 跳过了 pre-commit，问题代码进了仓库。
原因：本地 hook 本来就是可绕过的。
解法：靠 CI 状态检查兜底，合并前必须通过。

坑 4：pre-push 跑全量测试导致推送很慢
结论：每次 push 都等几分钟。
原因：pre-push 里放了太重的任务。
解法：轻量检查放 pre-commit，重测试放 CI，pre-push 只做必要验证。

坑 5：commit-msg 里 $1 未转义
结论：hook 报错或校验不生效。
原因：脚本里写 --edit $1，$1 在生成脚本时被展开成空。
解法：写 --edit \$1，保留 $1 给运行时的 git 传入。
```
