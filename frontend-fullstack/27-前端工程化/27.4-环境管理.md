## 概述

环境管理是「让同一份代码在不同环境用不同配置运行」：开发环境连本地服务，生产环境连线上服务。核心手段是环境变量和 feature flags，让配置从代码里剥离出来，代码不随环境改。

```text
四个标准环境：
1. development —— 开发环境，本地调试
2. test —— 测试环境，跑自动化测试
3. staging —— 预发布环境，上线前验收
4. production —— 生产环境，面向真实用户
```

```text
环境管理解决的核心问题：
1. 配置差异 —— API 地址、密钥、日志级别各环境不同
2. 代码一致 —— 同一份代码，靠配置区分环境
3. 灰度发布 —— feature flags 控制功能开关
```

## development

development（开发环境）是开发者本地的运行环境，特点是热更新、详细日志、宽松校验。

```text
development 的特点：
1. 热更新（HMR）—— 改代码即时生效
2. 详细日志 —— 便于调试
3. 连本地/测试服务 —— 不碰生产数据
4. source map 完整 —— 方便定位源码
```

```bash
# Vite 开发服务器
npm run dev
```

```ts
// 根据环境切换行为
if (import.meta.env.DEV) {
  console.log('开发环境，打印调试信息');
}
```

```text
开发环境的配置来源：
1. .env.development 环境变量文件
2. 默认走 localhost 的 API 地址
3. mock 数据或本地代理
```

## test

test（测试环境）是自动化测试运行的隔离环境，特点是确定性、可重复、隔离外部依赖。

```text
test 环境的特点：
1. 确定性 —— 同样的输入同样的结果
2. 隔离 —— mock 外部依赖（网络、数据库）
3. 快速 —— 用内存数据库、mock，不真连服务
```

```bash
# 测试环境运行
NODE_ENV=test vitest run
```

```js
// vitest.config.js 设置测试环境
export default {
  test: {
    environment: 'jsdom',
    setupFiles: ['./test/setup.ts'],
  },
};
```

```ts
// 测试环境常见：mock 网络请求
vi.mock('./api');
import { fetchUser } from './api';

test('fetchUser 返回 mock 数据', async () => {
  fetchUser.mockResolvedValue({ id: 1, name: 'Alice' });
  const user = await fetchUser(1);
  expect(user.name).toBe('Alice');
});
```

## staging

staging（预发布环境）是与生产尽量一致的「演练场」，在正式上线前做最后验收，验证部署流程和功能。

```text
staging 的特点：
1. 与生产同构 —— 配置、数据、基础设施尽量一致
2. 验收用途 —— 产品/测试在上线前确认
3. 灰度前哨 —— 先上 staging，再上生产
```

```text
staging 与 production 的区别：
1. 数据 —— staging 用脱敏/模拟数据，不用真实用户数据
2. 域名 —— staging.example.com vs www.example.com
3. 风险 —— staging 挂了不影响真实用户
```

```text
staging 环境的价值：
1. 验证部署脚本和配置
2. 集成测试（前端 + 后端联调）
3. 回归测试上线前的最后一道关
```

## production

production（生产环境）面向真实用户，特点是稳定优先、性能优化、监控告警。

```text
production 的特点：
1. 代码压缩 —— 去掉注释、tree-shaking、混淆
2. 关闭调试 —— 不输出 console、不暴露 source map
3. 监控告警 —— 错误上报、性能监控
4. 缓存优化 —— 静态资源 CDN + 长缓存
```

```bash
# 生产构建
npm run build
```

```ts
// 生产环境关闭调试日志
if (!import.meta.env.PROD) {
  console.log('仅非生产环境打印');
}
```

```text
生产环境的红线：
1. 密钥不进前端代码（前端密钥等同于公开）
2. source map 默认不公开
3. 任何改动走 CI/CD，不手动改线上
```

## 环境变量

环境变量（environment variables）是「随环境变化的配置项」，通过 `.env` 文件或 CI 注入，在构建时/运行时读取。

```bash
# .env.development
VITE_API_BASE=http://localhost:3000
VITE_ENABLE_MOCK=true

# .env.production
VITE_API_BASE=https://api.example.com
VITE_ENABLE_MOCK=false
```

```ts
// 读取环境变量（Vite 用 import.meta.env）
const apiBase = import.meta.env.VITE_API_BASE;
const enableMock = import.meta.env.VITE_ENABLE_MOCK === 'true';
```

```text
环境变量的读取方式：
1. Vite —— import.meta.env.VITE_XXX（需 VITE_ 前缀）
2. Webpack —— process.env.XXX
3. Node —— process.env.XXX
```

```text
.env 文件的优先级：
1. .env —— 所有环境通用
2. .env.local —— 本地覆盖（不提交）
3. .env.development / .env.production —— 按模式加载
4. 后加载的覆盖先加载的
```

```text
环境变量的使用规范：
1. 密钥（API key）不进前端代码，前端拿不到真正的秘密
2. .env.local 放本地敏感配置，进 .gitignore
3. 变量名加前缀（VITE_）避免误暴露
```

## feature flags

feature flags（功能开关）是「运行时控制功能是否开启」的开关，让部署和发布解耦：代码先上线，功能按需打开，支持灰度。

```ts
// 简单 feature flag
const flags = {
  newCheckout: import.meta.env.VITE_FLAG_NEW_CHECKOUT === 'true',
  darkMode: import.meta.env.VITE_FLAG_DARK_MODE === 'true',
};

if (flags.newCheckout) {
  renderNewCheckout();
} else {
  renderOldCheckout();
}
```

```text
feature flags 的价值：
1. 部署与发布分离 —— 代码上线 ≠ 功能上线
2. 灰度发布 —— 先给 5% 用户开，再逐步放量
3. 快速回滚 —— 关掉 flag 即回滚，不用重新部署
4. A/B 测试 —— 按用户分组开不同功能
```

```ts
// 按用户/比例灰度
function isEnabled(flag: string, userId: string): boolean {
  const rollout = getRolloutPercent(flag);  // 如 5%
  const hash = hashCode(userId);
  return hash % 100 < rollout;
}
```

```text
feature flags 的实现方案：
1. 环境变量 —— 简单，但改配置要重新构建
2. 远程配置 —— 运行时拉取，可动态开关（LaunchDarkly 等）
3. 自建服务 —— 后台管理 flag，前端轮询或订阅
```

```text
feature flags 的注意事项：
1. flag 要有时效性，功能稳定后清理旧 flag
2. 避免 flag 堆积成「配置地狱」
3. 关键路径的 flag 要有默认值，防止配置服务挂了影响主流程
```

## 应用场景实战

### 场景一：Vite 多环境配置

```bash
# .env（通用）
VITE_APP_TITLE=我的应用

# .env.development
VITE_API_BASE=http://localhost:3000

# .env.production
VITE_API_BASE=https://api.example.com
```

```ts
// src/api/request.ts
const API_BASE = import.meta.env.VITE_API_BASE;

export function request(path: string) {
  return fetch(`${API_BASE}${path}`);
}
```

```json
// package.json 用不同 mode 构建
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "build:staging": "vite build --mode staging"
  }
}
```

### 场景二：feature flag 灰度新功能

```ts
// src/flags.ts
export const flags = {
  newHomePage: import.meta.env.VITE_FLAG_NEW_HOME === 'true',
};

// src/App.tsx
import { flags } from './flags';

function App() {
  return flags.newHomePage ? <NewHome /> : <OldHome />;
}
```

```bash
# 灰度开启（只对部分环境）
VITE_FLAG_NEW_HOME=true npm run build
```

## 最佳实践与踩坑记录

### 最佳实践

1. 配置从代码剥离，用环境变量，别在代码里写死 if (host === 'localhost')
2. 密钥绝不放前端，前端环境变量都是公开的
3. .env.local 进 .gitignore，敏感配置不入库
4. feature flags 用于灰度/回滚，但要及时清理过期 flag
5. staging 与 production 尽量同构，缩小「预发正常生产翻车」的概率

### 踩坑记录

```text
坑 1：把 API 地址写死在代码里
结论：换环境要改代码，容易漏改导致连错服务。
原因：配置硬编码在源码里，没走环境变量。
解法：用环境变量注入 API_BASE，各环境用 .env 区分。

坑 2：Vite 环境变量没加 VITE_ 前缀
结论：import.meta.env.MY_VAR 拿到 undefined。
原因：Vite 只暴露 VITE_ 前缀的变量给前端。
解法：变量名加 VITE_ 前缀，或用 define 显式注入。

坑 3：密钥写进 .env 并提交到仓库
结论：API key 泄露到公开仓库。
原因：把敏感配置放进 .env 且没加 .gitignore。
解法：密钥放服务端或 CI 的 secret，.env.local 进 .gitignore。

坑 4：feature flag 堆积不清理
结论：代码里一堆 if (flag) 分支，逻辑难维护。
原因：功能上线后 flag 一直留着，没清理。
解法：功能稳定后删除 flag 和旧分支，保持代码干净。

坑 5：staging 与 production 配置差异大
结论：staging 测试正常，production 上线翻车。
原因：两个环境数据库、配置、依赖版本不一致。
解法：staging 与 production 同构，只隔离数据和域名。
```
