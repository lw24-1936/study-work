## 概述

代码质量是「代码可维护性、可读性、正确性」的综合度量，靠工具（静态分析、类型检查、lint）和流程（代码评审）共同保障。目标是让代码在长期维护中不腐化，bug 在早期被发现。

```text
代码质量的三个层次：
1. 自动检查 —— 静态分析、类型检查、lint、格式化（机器做）
2. 人工评审 —— Code Review（人做，查设计/逻辑）
3. 长期度量 —— 复杂度、重复代码、技术债（趋势监控）
```

```text
各手段的分工：
1. 静态分析 —— 不运行代码，分析 AST/数据流找潜在问题
2. 类型检查 —— 编译期校验类型正确性
3. Lint —— 规则检查（风格 + 潜在 bug 模式）
4. 格式化 —— 统一代码排版
```

## 静态分析

静态分析（Static Analysis）在不执行代码的前提下分析源代码，发现潜在 bug、安全漏洞、代码坏味道。工具会构建 AST 并做数据流/控制流分析。

```bash
# ESLint 本质是静态分析：解析 AST 跑规则
npx eslint src/

# SonarQube / SonarLint 做更深的静态分析
# 能发现空指针、资源泄漏、安全漏洞等
```

```text
静态分析能发现的问题：
1. 未使用变量、未到达的代码
2. 可能为 null/undefined 的访问
3. 安全漏洞（注入、不安全的正则）
4. 逻辑错误（恒真/恒假条件）
```

```js
// 静态分析能发现的坏味道
function process(data) {
  let result = 0;
  if (data.length > 0) {
    result = data[0];
  }
  const unused = 'never used';  // no-unused-vars 报错
  return result;
}
```

## 类型检查

类型检查（Type Checking）由 TypeScript 编译器在编译期校验类型，把「运行时才暴露的类型错误」提前到「写代码时」。

```ts
// 类型错误在编译期暴露
function add(a: number, b: number): number {
  return a + b;
}

// add('1', 2);  // 编译报错：string 不能赋给 number
```

```bash
# 只做类型检查，不产出 JS
npx tsc --noEmit

# tsconfig 严格模式
```

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitAny": true
  }
}
```

```text
类型检查的价值：
1. 提前暴露错误 —— 写代码时即时报错，而非运行时
2. 文档化 —— 函数签名即文档
3. 重构安全 —— 改类型后所有引用处编译报错
```

## Lint

Lint 是按规则集检查代码，规则覆盖「潜在 bug 模式」和「风格约定」，多数支持自动修复。

```js
// eslint.config.js
export default [
  {
    rules: {
      'no-unused-vars': 'error',
      'no-var': 'error',
      'prefer-const': 'error',
      'no-debugger': 'error',
    },
  },
];
```

```bash
# 检查
npx eslint src/

# 自动修复
npx eslint src/ --fix
```

```text
Lint 规则分类：
1. 潜在错误 —— no-unused-vars、no-undef、no-constant-condition
2. 最佳实践 —— eqeqeq、prefer-const、no-var
3. 风格 —— 引号、分号、缩进（现代交给 Prettier）
```

## 格式化

格式化（Formatting）统一代码排版（缩进、引号、换行、空格），让代码风格一致，减少 review 时对格式的争论。

```bash
# Prettier 格式化
npx prettier --write src/

# 检查格式是否合规
npx prettier --check src/
```

```json
{
  "semi": true,
  "singleQuote": true,
  "printWidth": 100
}
```

```text
格式化的意义：
1. 消除个人风格差异，全团队统一
2. 减少 diff 噪音（不再有「这里多一个空格」）
3. 让 review 聚焦逻辑而非排版
```

## 代码评审

代码评审（Code Review）是人工检查代码的过程，机器工具查不到的「设计合理性、业务逻辑、可维护性」靠人来判断。

```text
Code Review 关注点：
1. 逻辑正确性 —— 业务逻辑是否对、边界是否处理
2. 设计合理性 —— 结构是否清晰、是否过度设计
3. 可维护性 —— 命名是否达意、是否可测试
4. 安全与性能 —— 是否有注入风险、性能隐患
```

```text
评审流程（GitHub PR 为例）：
1. 开发者提交 PR
2. 分配 reviewer
3. reviewer 逐行看 diff，留评论
4. 问题修复后通过，合并
```

```text
评审的边界：
1. 机器能查的（格式、lint）不靠人评
2. 人重点评「机器查不出」的设计和逻辑
3. 小步提交，PR 尽量小，评审效率高
```

## 复杂度

复杂度（Complexity）衡量代码的理解难度，常用「圈复杂度」（Cyclomatic Complexity）：一个函数里独立路径的数量，if/循环越多复杂度越高。

```text
圈复杂度的计算：
1. 每个分支（if/else/case）、每个循环（for/while）加 1
2. 圈复杂度 > 10 通常建议拆分
3. 高复杂度 = 难测试、难理解、易出 bug
```

```js
// 圈复杂度示例（if 越多复杂度越高）
function classify(score) {
  if (score >= 90) return 'A';
  if (score >= 80) return 'B';
  if (score >= 70) return 'C';
  if (score >= 60) return 'D';
  return 'F';
}
```

```bash
# 用 eslint-plugin-complexity 检测
npm install -D eslint-plugin-complexity
```

```js
// eslint 配置
{
  rules: {
    complexity: ['warn', 10],
  },
}
```

```text
降低复杂度的手段：
1. 拆函数 —— 大函数拆成多个小函数
2. 查表法 —— 用映射替代 if/else 链
3. 早返回 —— 提前 return 减少嵌套
```

## 重复代码

重复代码（Duplication）是「相同或相似的代码出现在多处」，维护时要改多份，容易漏改导致 bug。

```text
重复代码的危害：
1. 改一处漏一处，产生不一致
2. 增加维护成本
3. 通常是「该抽象没抽象」的信号
```

```bash
# jscpd 检测重复代码
npx jscpd src/
```

```js
// 重复代码示例（应提取公共函数）
function formatDateCn(d) {
  return `${d.getFullYear()}年${d.getMonth() + 1}月${d.getDate()}日`;
}
function formatDateEn(d) {
  return `${d.getFullYear()}-${d.getMonth() + 1}-${d.getDate()}`;
}
```

```js
// 提取后
function formatDate(d, sep = '-') {
  const mm = d.getMonth() + 1;
  const dd = d.getDate();
  return [d.getFullYear(), mm, dd].join(sep);
}
```

```text
处理重复代码：
1. 提取函数/组件/模块
2. 注意「伪重复」——看起来像但语义不同，别强行合并
3. 用 jscpd/Sonar 检测定位重复
```

## 技术债

技术债（Technical Debt）是「为了赶进度做的妥协」累积的维护成本，如硬编码、缺少测试、复制粘贴、过时依赖。它需要被记录和有计划地偿还。

```text
技术债的来源：
1. 赶工期 —— 跳过测试、硬编码、临时方案
2. 缺少重构 —— 功能堆叠，结构腐化
3. 依赖过时 —— 老版本 API 残留
```

```text
管理技术债的做法：
1. 记录 —— 建 issue 或 TODO 注释标记债务
2. 度量 —— 用复杂度/重复代码/覆盖率监控趋势
3. 偿还 —— 每个迭代留固定时间重构
```

```bash
# 搜索 TODO/FIXME 标记
grep -rn "TODO\|FIXME\|HACK" src/
```

```text
技术债的权衡：
1. 不是所有债务都要立刻还，要评估影响面
2. 高影响（核心路径、安全相关）优先
3. 用「童子军规则」：每次改动让代码比来时更干净一点
```

## 应用场景实战

### 场景一：配置一套质量门禁（CI 里跑）

```yaml
# GitHub Actions 质量检查
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npx tsc --noEmit        # 类型检查
      - run: npx eslint src/         # lint
      - run: npx prettier --check src/  # 格式
      - run: npm test                # 测试
```

### 场景二：重构高复杂度函数

```js
// 重构前：圈复杂度高，难测
function getPrice(user, items) {
  let total = 0;
  for (const item of items) {
    if (item.type === 'book') {
      total += item.price * 0.9;
    } else if (item.type === 'electronics') {
      total += item.price;
    } else {
      total += item.price;
    }
  }
  if (user.vip) {
    total *= 0.8;
  } else if (user.coupon) {
    total -= user.coupon;
  }
  return total;
}
```

```js
// 重构后：拆函数 + 查表，复杂度降低
const DISCOUNT = { book: 0.9, electronics: 1, other: 1 };

function itemPrice(item) {
  return item.price * (DISCOUNT[item.type] ?? 1);
}

function applyUserDiscount(total, user) {
  if (user.vip) return total * 0.8;
  if (user.coupon) return total - user.coupon;
  return total;
}

function getPrice(user, items) {
  const total = items.reduce((sum, item) => sum + itemPrice(item), 0);
  return applyUserDiscount(total, user);
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 质量门禁放 CI（tsc + eslint + prettier + test），本地钩子只是第一道
2. 严格模式全开，类型检查是最高性价比的质量手段
3. PR 尽量小，review 聚焦逻辑而非格式
4. 复杂度/重复代码用工具度量趋势，别只看绝对数
5. 技术债要显式记录并排期偿还，别默默累积

### 踩坑记录

```text
坑 1：只加 lint 不跑类型检查
结论：代码风格统一了，但类型错误到运行时才暴露。
原因：lint 规则查不到类型问题，需要 tsc 单独跑。
解法：CI 里 tsc --noEmit 和 eslint 都跑。

坑 2：格式规则和 lint 规则冲突
结论：eslint --fix 与 prettier 结果互相覆盖。
原因：两边都配了格式规则且不一致。
解法：格式统一交给 Prettier，ESLint 关掉格式规则。

坑 3：圈复杂度阈值一刀切
结论：设了 complexity: 5，大量合法函数被标红。
原因：阈值过低，简单函数也超限。
解法：阈值设为 10 左右，重点盯超过的部分，别追求零警告。

坑 4：把「伪重复」强行合并
结论：合并后代码更绕，耦合更紧。
原因：两段看起来像的代码语义不同，强行抽象适得其反。
解法：先判断语义是否真一致，再决定提取。

坑 5：技术债只记不还
结论：TODO 注释越积越多，代码持续腐化。
原因：债务没有被排进迭代计划，永远「下次再说」。
解法：把技术债转成 issue，每迭代固定分配偿还时间。
```
