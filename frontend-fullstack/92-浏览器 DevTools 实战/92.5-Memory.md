## 概述

Memory（内存）面板用于分析页面的内存占用与泄漏：拍快照看当前堆里有什么对象、用时间线看内存如何随时间增长、定位哪些 DOM 节点该回收却还活着。内存泄漏会导致页面越来越卡，最终崩溃，是前端必须掌握的排查技能。

```text
Memory 面板的三种分析方式：
1. Heap Snapshot —— 某个时刻的内存快照，看「现在堆里有什么」
2. Allocation Timeline —— 一段时间内的分配记录，看「内存怎么涨的」
3. Allocation Sampling —— 按函数采样分配，定位「谁在分配内存」
```

```js
// 一个典型的内存泄漏：全局变量持有引用
let leaked = [];
function leak() {
  leaked.push(new Array(10000).fill('x')); // 数组只增不减
}
setInterval(leak, 1000); // 每秒钟堆内存都会上涨
```

## Heap Snapshot

Heap Snapshot（堆快照）是某个时刻堆内存的完整清单：所有存活对象及其大小、数量、引用关系。拍两张快照对比，就能算出「这期间多了多少对象、哪些对象该被回收却没回收」。

```text
堆快照的分析方法：
1. 拍一张快照，做一次操作，再拍一张
2. 切换到 Comparison 视图，看两次快照的差异
3. 按 Shallow Size / Retained Size 排序找膨胀大户
4. 展开对象看 Retainers，追溯它为什么没被回收
```

```text
两个关键尺寸：
1. Shallow Size —— 对象自身占的内存（不含引用的对象）
2. Retained Size —— 对象自身 + 其独占引用的所有对象的内存
3. 排查泄漏主要看 Retained Size，它代表「回收这个对象能释放多少」
```

## Allocation Timeline

Allocation Timeline（分配时间线）连续记录一段时间内新分配的对象，用时间轴展示内存的增长过程。它能捕捉「短时间内的内存暴涨」，并精确到是哪个函数、哪个操作在分配。

```js
// 触发内存暴涨的操作
function burst() {
  const big = [];
  for (let i = 0; i < 1e5; i++) big.push({ i, data: 'x'.repeat(100) });
  return big;
}
burst(); // Allocation Timeline 里会看到一段陡峭的内存增长
```

```text
Allocation Timeline 的读法：
1. 蓝色柱 —— 每次分配的内存大小
2. 走势 —— 曲线持续上升说明内存持续增长（疑似泄漏）
3. 锯齿 —— 上升后回落说明有 GC 在回收（正常）
4. 定位 —— 点某个柱，能看到是哪个调用栈分配的
```

## Detached DOM

Detached DOM（游离 DOM）是「已从页面树移除、但被 JS 变量引用而无法回收」的 DOM 节点。这是前端内存泄漏最常见的形态：节点视觉上消失了，内存里却还占着。

```js
// 制造游离 DOM：移除节点但引用还留着
let cached = [];
function addRow() {
  const row = document.createElement('div');
  document.body.appendChild(row);
  cached.push(row); // 缓存了引用
}
function clearRows() {
  document.body.innerHTML = ''; // 只清空 DOM，cached 里的引用还在
  // row 们变成 detached，内存没释放
}
```

```text
Detached DOM 的排查：
1. 快照里筛选 Detached 前缀的节点（如 Detached HTMLDivElement）
2. 看它的 Retainers，找到持有了它的 JS 变量/闭包
3. 解除引用（cached = null）后节点才能被 GC 回收
4. 注意 Detached 节点若被 Detached 节点引用，可能整棵子树都泄漏
```

## Retainers

Retainers（持有者）是「让某个对象不被回收的引用链」：从 GC Root 出发，谁一路引用到了这个对象。Memory 面板里选中对象，能展开完整的 Retainers 链，直接定位到「是哪一行代码、哪个变量把它拽住了」。

```text
Retainers 链的读法：
1. 从下往上读 —— 底部是 GC Root，顶部是目标对象
2. 中间每一环 —— 都是一个「持有者」（变量、闭包、Map、事件监听器等）
3. 关键环 —— 找出「本可以断开却没断开」的那一环
4. 常见持有者 —— 全局变量、定时器、事件监听、闭包、缓存 Map
```

```text
常见泄漏源（Retainers 视角）：
1. 全局变量 —— 挂在 window 上的引用永远不会被回收
2. 定时器 —— setInterval 未清理，回调闭包持有外部变量
3. 事件监听 —— 未 removeEventListener，元素与其闭包互相引用
4. 闭包 —— 返回的函数持有大对象引用
5. 缓存 —— 无上限的 Map/数组，只进不出
```

## 应用场景实战

### 场景一：定位一个内存泄漏

```text
步骤：
1. 打开 Memory 面板，先拍一张 Heap Snapshot
2. 反复执行可疑操作（切换页面、增删列表）若干次
3. 再拍一张快照，用 Comparison 视图看两次差异
4. 找 Retained Size 增长最多的对象（通常是 Detached DOM）
5. 展开该对象的 Retainers，追溯到持有了它的代码
6. 修复：移除引用 / 清理定时器 / 解绑事件
```

### 场景二：检查定时器是否泄漏

```js
// 泄漏写法：定时器从不清理，闭包持有大对象
function start() {
  const data = new Array(100000).fill(0);
  setInterval(() => { use(data); }, 1000); // 定时器永不清理
}

// 正确写法：保存 id，组件销毁时清理
let timerId = null;
function start() {
  const data = new Array(100000).fill(0);
  timerId = setInterval(() => { use(data); }, 1000);
}
function stop() {
  clearInterval(timerId); // 清理后闭包释放，data 可被 GC
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 排查泄漏用「两张快照对比」，别只看单张快照的绝对值
2. 关注 Retained Size 而非 Shallow Size，它才代表可释放内存
3. 组件销毁时清理定时器、事件监听、订阅，一个都别漏
4. 缓存要有上限（LRU 或容量限制），别无限增长
5. 用 Allocation Timeline 捕捉「操作导致的内存暴涨」，比快照更精准

### 踩坑记录

```text
坑 1：只清空 DOM 不清引用，产生游离节点
结论：列表清空了，内存却一直涨。
原因：JS 数组/变量还持有已移除节点的引用，节点变 Detached。
解法：清空 DOM 的同时清空对应引用（list = []）。

坑 2：定时器没清理，闭包持有大对象
结论：页面停留越久越卡，内存持续上涨。
原因：setInterval 未 clear，其回调闭包持有外部大对象。
解法：组件卸载/停止时 clearInterval，并置空引用。

坑 3：把 Shallow Size 当成泄漏依据
结论：优化了半天「大对象」，内存却没降下来。
原因：Shallow Size 只算自身，真正的泄漏在 Retained Size。
解法：看 Retained Size，它能代表回收该对象能释放多少内存。

坑 4：事件监听未解绑
结论：元素已移除，但监听器与闭包仍互相引用。
原因：addEventListener 未配对 removeEventListener。
解法：在组件销毁生命周期里统一解绑，或用 AbortController 批量清理。

坑 5：误把 GC 延迟当成泄漏
结论：快照里对象还在，以为泄漏，其实只是 GC 没跑。
原因：GC 是延迟执行的，短时间内的对象可能还没被回收。
解法：多次操作后对比趋势，或用强制 GC（Performance 里垃圾桶按钮）再判断。
```
