## 概述

Network（网络）面板记录页面加载过程中发出的所有网络请求，包括文档、脚本、样式、图片、XHR/fetch、WebSocket 等，是排查「资源为什么慢、请求为什么失败、接口返回了什么」的核心工具。

```text
Network 面板记录什么：
1. 请求清单 —— 每个请求的方法、状态码、类型、大小、耗时
2. 请求详情 —— 请求头、请求体、响应头、响应体
3. 时序 —— 单个请求的排队/连接/等待/下载各阶段耗时
4. 依赖关系 —— 是谁（哪个脚本/样式）发起了这个请求
```

```js
// 触发几类请求，在 Network 里观察
fetch('/api/data', { method: 'POST', body: JSON.stringify({ a: 1 }) });
const img = new Image(); img.src = '/images/logo.png';
```

## Request

Request 是一次网络请求的「发出方」信息：请求方法、URL、请求头、请求体。在面板里选中请求，切到 Headers/Payload 标签即可看到完整的请求内容，常用于核对「前端到底发对了没有」。

```js
// 前端发起请求的代码
fetch('/api/user?id=1', {
  method: 'GET',
  headers: { 'Content-Type': 'application/json' },
});
```

```text
Request 的排查要点：
1. 方法 —— GET/POST/PUT/DELETE 是否正确
2. URL —— 路径、query 参数、端口、协议是否拼对
3. 请求体 —— Payload 标签看 POST 的 body 内容与格式
4. 是否发出 —— 请求没出现在列表，说明根本没发（代码没执行/被拦截）
```

## Response

Response 是服务端返回的信息：状态码、响应头、响应体。状态码是排查的第一线索（200 成功、4xx 客户端错、5xx 服务端错），响应体则是「服务端到底返回了什么数据」。

```text
常见状态码速查：
1. 200 —— 成功
2. 204 —— 成功但无内容
3. 301/302 —— 永久/临时重定向
4. 304 —— 命中缓存，未修改
5. 400 —— 请求参数错误
6. 401 —— 未认证
7. 403 —— 无权限
8. 404 —— 资源不存在
9. 429 —— 请求过于频繁
10. 500/502/503 —— 服务端错误
```

```js
// 前端检查响应
const res = await fetch('/api/user');
if (!res.ok) {
  console.error('状态码', res.status); // 非 2xx 时排查
}
const data = await res.json();
```

## Headers

Headers 是请求/响应的元信息，承载认证、缓存、跨域、内容类型等控制。Network 面板把请求头与响应头分开展示，是排查 CORS、缓存、鉴权问题的关键。

```text
关键请求头：
1. Authorization / Cookie —— 认证凭证
2. Content-Type —— 请求体格式
3. Accept —— 期望的响应格式
4. Cache-Control —— 缓存策略
5. Origin / Referer —— 来源（CORS 校验用）

关键响应头：
1. Access-Control-Allow-Origin —— 跨域白名单
2. Set-Cookie —— 服务端写 Cookie
3. Cache-Control / ETag —— 缓存控制与校验
4. Content-Encoding —— gzip/br 压缩
```

```text
Headers 的排查要点：
1. CORS —— 看响应头有没有 Access-Control-Allow-Origin 且匹配当前源
2. 鉴权 —— 看 Authorization/Cookie 有没有带上去
3. 缓存 —— 看 Cache-Control 决定是否命中强缓存/协商缓存
4. 压缩 —— Content-Encoding 确认响应有没有被 gzip/br 压缩
```

## Timing

Timing 是单个请求的耗时分解，把「从发起请求到收到响应」拆成若干阶段。它精确回答了「慢在哪里」——是排队等、还是 DNS 慢、还是等服务器响应（TTFB）、还是下载大文件慢。

```text
Timing 的阶段分解：
1. Queuing —— 排队等待（受并发连接数限制）
2. Stalled —— 停滞（等可用连接）
3. DNS Lookup —— 域名解析耗时
4. Initial connection —— TCP 握手 + TLS 握手耗时
5. Request sent —— 发送请求体
6. Waiting (TTFB) —— 等待服务器首字节响应
7. Content Download —— 下载响应体
```

```text
Timing 的排查要点：
1. TTFB 长 —— 服务端处理慢，优化后端逻辑或缓存
2. Content Download 长 —— 响应体大，做压缩、分片、CDN
3. Queuing/Stalled 长 —— 并发太多，合并请求或 HTTP/2
4. DNS/TLS 长 —— 用 CDN、连接复用、预连接（preconnect）
```

## Waterfall

Waterfall（瀑布图）把所有请求的时序并排画在一条时间轴上，一眼看出「哪个请求最早、哪个最慢、哪些是并行哪些是串行」。它把单请求的 Timing 放大到全局视角，是分析页面加载性能的起点。

```text
Waterfall 的读法：
1. 横轴 —— 时间，最长的条就是最慢的请求
2. 颜色 —— 不同阶段用不同颜色（排队/等待/下载）
3. 并行 —— 多条同时开始，说明并发加载
4. 串行 —— 一条结束下一条才开始，可能存在依赖阻塞
```

```text
Waterfall 的优化信号：
1. 前面有长条 —— 关键资源慢，优先优化
2. 瀑布阶梯状 —— 资源串行加载，考虑预加载或 HTTP/2
3. 大量并行 —— 并发数打满，考虑合并或精简
4. 空白段 —— 期间无网络活动，可能是 JS 执行阻塞
```

## Blocking

Blocking 指「阻塞了页面渲染的请求」：浏览器解析 HTML 时，遇到同步脚本、未 defer 的脚本、以及渲染必需的 CSS，会停下渲染等待资源。Network 面板可标出这些阻塞渲染的资源，帮助识别「首屏为什么白屏」。

```html
<!-- 会阻塞渲染的脚本 -->
<script src="/app.js"></script>

<!-- 不阻塞渲染的写法 -->
<script src="/app.js" defer></script>
<!-- 或 async，或放在 body 底部 -->
```

```text
Blocking 的排查要点：
1. 阻塞资源 —— 同步 script 与关键 CSS 会阻塞渲染
2. defer/async —— 让脚本不阻塞解析
3. 内联关键 CSS —— 首屏样式内联，减少一次阻塞请求
4. 目标是 —— 让首屏渲染尽快发生，非关键资源延后加载
```

## Initiator

Initiator 是「发起者」，告诉你每个请求是谁发起的：是 HTML 解析、某个 CSS 里的 url()、还是某段 JS 代码。选中请求切到 Initiator 标签，能看到发起源的调用堆栈，直接定位到源码。

```text
Initiator 的类型：
1. Parser —— HTML 解析过程中发起的（script/link/img 标签）
2. Script —— 由 JS 代码发起（fetch/XHR/动态插入）
3. Redirect —— 重定向产生的后续请求
4. CSS —— 样式里引用的字体、背景图等
```

```text
Initiator 的排查要点：
1. 定位来源 —— 点击堆栈帧直接跳到发起请求的源码行
2. 意外请求 —— 页面加载了没预料到的资源，追溯是哪里引入的
3. 重复请求 —— 同一资源被多处发起，考虑复用与缓存
```

## 应用场景实战

### 场景一：排查「接口报 404」

```text
步骤：
1. Network 里找到红色 404 的请求，看 URL 拼对没有
2. 对比正确的接口路径，检查 query 参数、路径前缀、环境变量
3. 看 Headers 里的 Origin 与 Cookie，确认鉴权信息带上了
4. 用 Copy as fetch 复制请求，到 Console 里手动重放验证
5. 定位到 Initiator，找到发起请求的源码位置修正
```

### 场景二：分析首屏加载慢

```js
// 操作：
// 1. Network 勾选 Disable cache，刷新页面
// 2. 看 Waterfall，找出最长的请求
// 3. 看 Blocking，找出阻塞渲染的同步脚本
// 4. 看 Timing，判断慢在 TTFB 还是 Download
// 5. 针对性优化：脚本 defer、资源压缩、CDN、预加载

// 优化后验证：对比前后 waterfall 的加载完成时间
```

## 最佳实践与踩坑记录

### 最佳实践

1. 排查问题先勾选 Disable cache，排除缓存干扰
2. 用 Copy as fetch 把请求复制到 Console 重放，快速复现
3. 用 Preserve log 保留跳转前后的请求，追踪重定向链路
4. 按资源类型过滤（XHR/Fetch、JS、Img），别在混杂列表里大海捞针
5. 慢请求先看 Timing 的 TTFB，判断是网络、后端还是下载问题

### 踩坑记录

```text
坑 1：缓存干扰排查，改了代码「看起来没生效」
结论：刷新后 Network 里 304，拿到的还是旧资源。
原因：强缓存命中，浏览器没真正发请求到服务端。
解法：排查时勾选 Disable cache，或 Ctrl+Shift+R 硬刷新。

坑 2：把 CORS 报错当成服务端 500
结论：看到请求变红，误以为服务端挂了。
原因：CORS 被拦截的请求状态码显示为 failed 或 0，并非服务端错。
解法：看 Console 的 CORS 提示，检查响应头 Access-Control-Allow-Origin。

坑 3：以为请求「没发出」，其实是没勾 Preserve log
结论：页面跳转后之前的请求列表被清空，看不到关键请求。
原因：默认跳转会清空列表。
解法：勾选 Preserve log 保留跨页面请求记录。

坑 4：忽略 Timing 里的 Queuing 阶段
结论：只优化了下载，却忽视了请求排队导致的延迟。
原因：HTTP/1.1 并发连接数有限，请求排队等待。
解法：升级 HTTP/2 或合并请求，减少排队。

坑 5：把 Initiator 当成「响应来源」
结论：想找响应内容却去看 Initiator，结果找不到。
原因：Initiator 是「谁发起的」，响应内容在 Response/Preview 标签。
解法：看内容去 Response，看谁发起的去 Initiator，别混淆。
```
