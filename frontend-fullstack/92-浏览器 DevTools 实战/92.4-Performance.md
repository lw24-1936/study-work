## 概述

Performance（性能）面板录制页面运行过程中的主线程活动，把「谁在执行、执行了多久、触发了什么渲染阶段」用火焰图和时间轴呈现出来。它是定位卡顿、长任务、渲染瓶颈的权威工具。

```text
Performance 面板回答的问题：
1. 主线程在忙什么 —— 哪个函数占用了最多时间
2. 渲染瓶颈在哪 —— Layout/Paint/Composite 哪个阶段最耗时
3. 卡顿源头 —— 哪些 Long Task 阻塞了交互
4. 帧率如何 —— FPS 是否稳定在 60
```

```js
// 录制一段耗时操作，观察火焰图
function heavyWork() {
  let sum = 0;
  for (let i = 0; i < 1e7; i++) sum += i; // 主线程阻塞
  return sum;
}
heavyWork(); // 录制 Performance 会看到一段长任务
```

## Flame Chart

Flame Chart（火焰图）是 Performance 面板里按调用栈堆叠的时间条：横轴是时间，纵轴是调用深度，每条横条是一个函数调用。最宽、最深的条就是耗时大户，点击可跳到对应源码。

```text
火焰图的读法：
1. 横向 —— 条越宽，函数执行时间越长
2. 纵向 —— 越靠下，调用层级越深
3. 自顶向下 —— 顶层是入口，向下展开是被调用的函数
4. 颜色 —— 不同活动（脚本/渲染/空闲）有不同底色
```

```js
function outer() {
  innerA(); // 火焰图里 innerA 是 outer 下面的一条
  innerB();
}
function innerA() { /* 耗时 50ms */ }
function innerB() { /* 耗时 10ms */ }
outer();
```

## Main Thread

Main Thread（主线程）是浏览器执行 JS、计算样式、布局、绘制的唯一线程。它一旦被长任务占用，页面就无法响应点击、滚动、输入。Performance 面板的「Main」轨道展示了主线程从脚本到渲染的完整时间线。

```text
主线程的活动类型：
1. Scripting —— 执行 JS
2. Rendering —— 样式计算、布局、绘制
3. Painting —— 栅格化、合成
4. Idle —— 空闲（应尽量多）
5. GC —— 垃圾回收
```

```text
主线程的优化方向：
1. 减少脚本执行 —— 拆分长任务、懒加载、缓存计算
2. 减少渲染工作 —— 降低布局/绘制频率
3. 让出主线程 —— 重活交给 Web Worker
4. 目标 —— 单个任务不超过 50ms，保持流畅响应
```

## Long Task

Long Task 是「执行超过 50ms 的任务」，它会让页面明显卡顿（错过帧、输入延迟）。Performance 面板用红色三角标出长任务，展开能看到它内部具体是哪个函数耗时。

```js
// 制造一个长任务
function longTask() {
  const start = performance.now();
  while (performance.now() - start < 200) {} // 阻塞 200ms
}
longTask();

// 拆分长任务：把大循环切成小段
function chunkedWork(items) {
  const step = 100;
  for (let i = 0; i < items.length; i += step) {
    const slice = items.slice(i, i + step);
    requestIdleCallback(() => process(slice)); // 空闲时处理
  }
}
```

```text
Long Task 的应对：
1. 拆分 —— 大任务切成多个小于 50ms 的小任务
2. 让步 —— 用 requestIdleCallback / setTimeout 让出主线程
3. 迁移 —— 计算密集逻辑移到 Web Worker
4. 观察 —— 用 PerformanceObserver 监听 longtask 事件做监控
```

## Layout

Layout（布局）是浏览器计算元素几何位置（大小、位置）的阶段，也叫 Reflow。它由 DOM 结构或样式变化触发，代价高，且会级联影响子元素，是「改样式导致卡顿」的常见源头。

```js
// 触发多次布局：每次读 offsetWidth 都强制同步布局
function badLayout() {
  for (let i = 0; i < 100; i++) {
    el.style.width = i + 'px';
    el.offsetWidth; // 读几何属性，强制 layout（layout thrashing）
  }
}
```

```text
Layout 的优化要点：
1. 批量写 —— 一次性改完样式，中间别读几何属性
2. 读写分离 —— 先读后写，或读写之间用 requestAnimationFrame 隔开
3. 避免频繁改 —— 用 transform 替代 width/top/left 这类几何属性
4. 观察 —— Performance 里 Layout 阶段越长，说明重排越多
```

## Paint

Paint（绘制）是浏览器把布局结果画出来的阶段：填充颜色、绘制边框、渲染文本、绘制阴影等。重绘（Repaint）由不影响布局的样式变化触发（如颜色、背景），代价小于布局但仍应控制。

```js
// 触发重绘（不影响布局，只重画）
el.style.backgroundColor = 'red';
el.style.boxShadow = '0 0 10px #000';

// 提升为合成层，避免重绘（用 transform 做动画）
el.style.transform = 'translateX(100px)';
```

```text
Paint 的优化要点：
1. 减少重绘范围 —— 用 will-change 提示浏览器单独成层
2. 动画用 transform/opacity —— 只走合成，不触发重绘
3. 避免昂贵样式 —— 大阴影、模糊、多背景图都加重绘制
4. 观察 —— Paint 阶段面积大说明重绘区域大
```

## Composite

Composite（合成）是渲染的最后阶段：把分层后的各个图层合并成最终画面，交给 GPU 完成。transform 和 opacity 的变化只触发合成，不触发布局与绘制，是「最便宜」的动画方式。

```css
/* 触发合成的动画（推荐） */
.box {
  transform: translateX(0);
  transition: transform 0.3s;
}
.box:hover { transform: translateX(100px); }
```

```text
Composite 的要点：
1. 分层 —— 浏览器把某些元素提升为独立图层（如 will-change、transform）
2. GPU 加速 —— 合成由 GPU 完成，速度快、不阻塞主线程
3. 最省动画 —— transform/opacity 只触发 composite，跳过 layout/paint
4. 别滥用 —— 图层太多会占显存，反而拖慢合成
```

## FPS

FPS（帧率）衡量画面每秒渲染多少帧。流畅标准是 60fps（每帧约 16.6ms），低于 30fps 会明显卡顿。Performance 面板顶部的 FPS 轨道用绿色条显示帧率，红条表示掉帧。

```js
// 用 rAF 监测帧率
let frames = 0, last = performance.now();
function loop() {
  frames++;
  const now = performance.now();
  if (now - last >= 1000) {
    console.log('FPS =', frames); // 每秒打印一次帧率
    frames = 0; last = now;
  }
  requestAnimationFrame(loop);
}
requestAnimationFrame(loop);
```

```text
FPS 的要点：
1. 60fps —— 每帧预算 16.6ms，超了就掉帧
2. 掉帧原因 —— 长任务、频繁布局/绘制、大重绘区域
3. 观察 —— FPS 轨道红条越多，卡顿越严重
4. 优化目标 —— 把每帧工作压到 16.6ms 以内
```

## 进阶技巧与选型

### 录制流程与设置

```text
录制前的关键设置（录制按钮旁的齿轮/下拉）：
1. CPU throttling —— 4x/6x 减速，模拟低端设备，暴露真机卡顿
2. Network throttling —— 配合网络节流，还原弱网下的加载时序
3. Disable JavaScript samples —— 关闭 JS 调用栈采样，降低录制开销，只看宏观时间
4. 录制方式 —— Reload 测加载阶段，Record 手动触发测交互
5. 建议 —— 无痕窗口、关扩展、多录几次取稳定结果
```

```text
火焰图的快捷键与读法：
1. WASD —— 在时间轴上平移与缩放
2. 点击函数条 —— 跳转到 Sources 对应源码
3. Bottom-up / Call tree / Event log —— 三种视图切换，找耗时大户
4. Summary 标签 —— 看各阶段（Scripting/Rendering/Painting）总耗时占比
```

### 强制同步布局检测

```text
如何用 Performance 抓 layout thrashing：
1. 录制时观察 Main 轨道 —— 反复出现的紫色 Layout 小块就是强制同步布局
2. 展开 Layout 任务 —— 可定位到触发它的 JS 调用
3. 红色三角警告 —— 浏览器会把「强制 reflow」标为性能警告
4. 代码信号 —— 循环里「写样式后立刻读几何属性」是典型 thrashing 写法
```

### 选型：Performance vs 其他面板

```text
选型速查：
1. 找「哪个函数最慢」 → Performance 火焰图
2. 找「哪个请求慢」 → Network Timing/Waterfall
3. 找「哪个对象占内存」 → Memory 堆快照
4. 找「渲染的哪个阶段慢」 → Performance 的 Summary（Layout/Paint/Composite）
5. 线上监控 → PerformanceObserver + 自定义上报，别只靠面板
```

### 性能与兼容性注意

```text
Performance 面板注意点：
1. 录制本身有开销 —— CPU 节流 + JS 采样会让页面更慢，结果偏悲观，对照基线看
2. 浏览器差异 —— 火焰图细节在 Chrome/Firefox/Safari 间不一致，结论以 Chrome 做基线
3. 扩展干扰 —— 广告/翻译扩展会注入脚本污染时间线，务必无痕
4. 短任务易漏 —— 低于采样阈值的极短函数可能被折叠，别据此断定「没执行」
```

## 应用场景实战

### 场景一：定位页面滚动卡顿

```text
步骤：
1. 打开 Performance，点击录制，滚动页面触发卡顿
2. 停止录制，看 FPS 轨道的红条集中在哪个时间段
3. 在 Main 轨道找到对应时间的 Long Task
4. 展开长任务，看是脚本执行还是 Layout 重排
5. 若是 Layout，找到触发的代码，改用 transform 或批量改样式
```

### 场景二：优化一个动画的流畅度

```js
// 卡顿写法：动画改 left，每帧触发 layout + paint
function badAnimate() {
  let x = 0;
  function step() {
    box.style.left = x + 'px'; // 触发布局与绘制
    x++;
    requestAnimationFrame(step);
  }
  requestAnimationFrame(step);
}

// 流畅写法：用 transform，只触发 composite
function goodAnimate() {
  let x = 0;
  function step() {
    box.style.transform = `translateX(${x}px)`;
    x++;
    requestAnimationFrame(step);
  }
  requestAnimationFrame(step);
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 动画只用 transform 和 opacity，避开会触发布局/绘制的属性
2. 长任务拆分成小于 50ms 的小段，别让主线程连续阻塞
3. 布局读写分离，避免 layout thrashing（反复读写几何属性）
4. 用 PerformanceObserver 监听 longtask 做线上监控
5. 录性能时用「无痕窗口」排除扩展干扰，多录几次取稳定值

### 踩坑记录

```text
坑 1：动画改 width/left 导致掉帧
结论：动画卡顿，FPS 掉到 30 以下。
原因：改几何属性每帧都触发 layout + paint，主线程忙不过来。
解法：改用 transform 做位移/缩放，只走合成层。

坑 2：循环里读写 offsetWidth 造成 layout thrashing
结论：几十次布局堆积，页面一顿一顿。
原因：每次读几何属性都强制同步布局，写读交替反复重排。
解法：先批量读、再批量写，或读写之间用 rAF 分隔。

坑 3：只看脚本时间，忽视 Layout 阶段
结论：脚本不慢但页面还是卡，找不到原因。
原因：瓶颈在 Layout 重排，不在脚本执行。
解法：看 Main 轨道里 Layout 的耗时，定位触发重排的代码。

坑 4：will-change 滥用导致图层爆炸
结论：给大量元素加 will-change，显存暴涨反而更卡。
原因：每个 will-change 都提升为独立图层，图层太多合成变慢。
解法：只在真正会动的元素上短时使用，动画结束移除。

坑 5：测量性能时没排除缓存与扩展
结论：两次测量结果差异大，优化「有效」是假象。
原因：缓存命中、浏览器扩展干扰了真实数据。
解法：无痕窗口 + 禁用扩展 + 硬刷新，多次测量取平均。

坑 6：开着 CPU 节流对比优化前后，误判「越优化越慢」
结论：加了节流后所有数值都变差，优化效果被掩盖。
原因：4x/6x 减速会放大所有耗时，不同录制设置之间数值不可直接比。
解法：对比必须用相同的节流/网络设置，或关节流测相对变化。
```
