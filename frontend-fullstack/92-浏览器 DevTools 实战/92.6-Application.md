## 概述

Application（应用）面板是浏览器「数据存储」的总控台：本地存储、Cookie、IndexedDB、缓存、Service Worker 都在这里查看与管理。它回答「数据存在哪、存了什么、有多大、怎么清」，是排查存储、鉴权、离线问题的核心工具。

```text
Application 面板管理的存储：
1. Local/Session Storage —— 键值对，简单但同步、容量小
2. Cookies —— 会话与鉴权，随请求自动携带
3. IndexedDB —— 结构化大容量数据库，异步
4. Cache Storage —— Service Worker 的缓存
5. Service Workers —— 离线与后台能力的管理
```

```js
// 各种存储的写入
localStorage.setItem('theme', 'dark');
document.cookie = 'token=abc; path=/';
// IndexedDB 与 Cache Storage 则是异步 API
```

## Storage

Storage 指 Local Storage 与 Session Storage：都是同步的键值存储，只能存字符串。区别在于作用域——Local Storage 永久保存（除非手动清除），Session Storage 在标签页关闭后失效。Application 面板可直接查看、编辑、删除其中的数据。

```js
// Local Storage：持久，跨会话
localStorage.setItem('user', JSON.stringify({ id: 1, name: 'vue' }));
localStorage.getItem('user');        // 字符串，需 JSON.parse
localStorage.removeItem('user');

// Session Storage：仅当前标签页，关页即清
sessionStorage.setItem('draft', 'hello');
```

```text
Storage 的要点：
1. 同步 API —— 读写阻塞主线程，别存大文件
2. 只存字符串 —— 对象要先 JSON.stringify
3. 容量 —— 约 5MB，超了抛 QuotaExceededError
4. 用途 —— 主题、偏好、草稿等轻量数据，结构化数据用 IndexedDB
```

## Cookies

Cookies 是随每个 HTTP 请求自动携带的小段文本，主要用于会话保持与鉴权。它由服务端通过 Set-Cookie 下发，也可由 JS 写入。Application 面板可查看每个 Cookie 的名称、值、域、路径、过期时间与安全属性。

```text
Cookie 的关键属性：
1. Name/Value —— 键值对，Value 是核心内容
2. Domain/Path —— 作用范围，决定哪些请求会带上它
3. Expires/Max-Age —— 过期时间，决定是会话还是持久
4. HttpOnly —— 仅服务端可读，JS 读不到（防 XSS 窃取）
5. Secure —— 仅 HTTPS 传输
6. SameSite —— 防 CSRF：Strict/Lax/None
```

```text
Cookies 的排查要点：
1. 没带上 —— 检查 Domain/Path 是否匹配当前请求
2. 读不到 —— 是不是 HttpOnly，JS 本来就拿不到
3. 跨站丢失 —— SameSite 太严格或 Secure 未满足
4. 容量 —— 每个 Cookie 约 4KB，总数量也有限制
```

## IndexedDB

IndexedDB 是浏览器内置的结构化数据库：异步、支持索引与事务、容量远大于 Storage，适合存大量结构化数据（缓存列表、离线数据、文件）。Application 面板能浏览其数据库、对象仓库（store）与索引。

```js
// IndexedDB 的基本使用
const openReq = indexedDB.open('mydb', 1);
openReq.onupgradeneeded = (e) => {
  const db = e.target.result;
  db.createObjectStore('users', { keyPath: 'id' });
};
openReq.onsuccess = (e) => {
  const db = e.target.result;
  const tx = db.transaction('users', 'readwrite');
  tx.objectStore('users').put({ id: 1, name: 'vue' });
};
```

```text
IndexedDB 的要点：
1. 异步 —— 基于事件回调或 Promise 封装，不阻塞主线程
2. 事务 —— 读写都要包在 transaction 里
3. 索引 —— 建索引后可按字段快速查询
4. 容量 —— 通常 GB 级，远超 localStorage
```

## Cache

Cache（Cache Storage）是 Service Worker 专属的缓存 API，存储 Request/Response 对，用于离线缓存与性能优化。Application 面板的 Cache Storage 栏可查看缓存的条目、大小与内容，也能手动清空。

```js
// Service Worker 里缓存资源
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      return cached || fetch(event.request).then((res) => {
        return caches.open('v1').then((cache) => {
          cache.put(event.request, res.clone());
          return res;
        });
      });
    }),
  );
});
```

```text
Cache 的要点：
1. 按 Request 匹配 —— 以完整请求为键，含 URL、方法、头
2. 版本化 —— cache.open('v1') 用版本名隔离，更新时清旧版本
3. 与 HTTP 缓存不同 —— 完全由 SW 控制，不遵守 Cache-Control
4. 排查 —— 离线失败先看 Cache Storage 里有没有对应资源
```

## Service Worker

Service Worker（SW）是运行在后台、独立于页面的脚本，可拦截网络请求、做离线缓存、推送通知，是 PWA 的核心。Application 面板的 Service Workers 栏可查看 SW 状态、更新、注销，以及控制哪些页面。

```js
// 注册 Service Worker
navigator.serviceWorker.register('/sw.js').then((reg) => {
  console.log('SW registered', reg);
});

// sw.js：拦截请求做缓存
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('v1').then(c => c.addAll(['/', '/index.html', '/app.js'])),
  );
});
```

```text
Service Worker 的排查要点：
1. 状态 —— activated/installing/waiting，卡在 installing 多是 install 里报错
2. 更新 —— 内容改了没生效，看是不是旧 SW 还在控制页面
3. 注销 —— Unregister 后刷新才能彻底移除
4. 作用域 —— SW 只能控制其注册路径下的页面
```

## 应用场景实战

### 场景一：排查「登录态丢失」

```text
步骤：
1. 打开 Application 面板，看 Cookies 里有没有会话 Cookie
2. 若没有，检查登录接口的 Set-Cookie 响应头是否下发
3. 若 Cookie 存在但仍未登录，检查 Domain/Path 是否匹配
4. 检查 Expires，是否已经过期导致浏览器丢弃
5. 检查 SameSite/Secure，跨站场景下是否被浏览器拦截
```

### 场景二：给页面加离线缓存

```js
// 完整的最小离线缓存方案
// 1. 页面注册 SW
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js');
}

// 2. sw.js 缓存关键资源
const CACHE_NAME = 'app-v1';
self.addEventListener('install', (e) => {
  e.waitUntil(
    caches.open(CACHE_NAME).then(c => c.addAll(['/', '/app.js', '/style.css'])),
  );
});
self.addEventListener('fetch', (e) => {
  e.respondWith(
    caches.match(e.request).then(r => r || fetch(e.request)),
  );
});

// 3. 在 Application → Cache Storage 验证缓存已写入
// 4. 断网刷新，页面仍能打开即说明离线缓存生效
```

## 最佳实践与踩坑记录

### 最佳实践

1. 结构化、大数据用 IndexedDB，别塞进 localStorage
2. 敏感数据（token）优先 HttpOnly Cookie，别存 localStorage 防 XSS 窃取
3. Cache Storage 要版本化并清理旧版本，否则缓存无限膨胀
4. Service Worker 更新要处理 skipWaiting 与 clients.claim，避免新旧混用
5. 排查存储问题先看 Application 面板的「存储总览」，快速定位是哪种存储

### 踩坑记录

```text
坑 1：把大对象塞进 localStorage
结论：写入抛 QuotaExceededError，页面报错。
原因：localStorage 约 5MB 且同步，存大文件/大数组超限。
解法：结构化大数据用 IndexedDB，大文件用 Cache 或 File API。

坑 2：Cookie 没带 HttpOnly 被 XSS 窃取
结论：token 存 JS 可读的 Cookie/localStorage，被脚本盗走。
原因：可读存储能被注入脚本读取，HttpOnly 才能挡住 JS 访问。
解法：敏感凭证用 HttpOnly Cookie，本地只存非敏感数据。

坑 3：Service Worker 更新后页面还是旧版
结论：发布了新版本，用户看到的还是旧的。
原因：旧 SW 仍控制页面，新 SW 停在 waiting 没接管。
解法：install 后 skipWaiting + 页面里 clients.claim，或提示用户刷新。

坑 4：Cache Storage 版本不清理导致膨胀
结论：缓存越积越多，占满存储配额。
原因：每次更新都 open 新版本名，旧缓存从不删除。
解法：activate 里遍历删除不属于当前版本的缓存。

坑 5：误以为 Session Storage 能跨标签页共享
结论：新标签页读不到上一个标签页存的 Session Storage。
原因：Session Storage 按标签页隔离，关页即清。
解法：跨标签页共享用 localStorage 或 IndexedDB。
```
