## 概述

SSR（Server Side Rendering，服务端渲染）指「在服务器上把组件渲染成 HTML 字符串，随响应返回给浏览器」。它解决了纯 CSR（客户端渲染）的首屏白屏与 SEO 问题，是内容型、营销型网站的首选方案。

```text
SSR 的完整流程：
1. 浏览器请求页面 URL
2. 服务器运行组件，读取数据，渲染成完整 HTML
3. 服务器返回 HTML（此时用户已能看到内容）
4. 浏览器下载 JS，执行 Hydration 绑定事件
5. 之后交互由客户端接管（变成 SPA）

SSR vs CSR：
CSR —— 服务器只返回空 HTML，JS 下载执行后才渲染内容
SSR —— 服务器直接返回带内容的 HTML，首屏快、可被爬虫抓取
```

## Server Side Rendering

Server Side Rendering 是 SSR 的核心概念：服务端执行组件渲染逻辑，产出 HTML。以 React 的 `renderToString` 为例。

```js
// React 服务端渲染基础 API
import { renderToString } from 'react-dom/server';
import App from './App';

// 服务端：渲染组件为 HTML 字符串
const html = renderToString(<App />);
const fullPage = `<!DOCTYPE html>
<html>
  <body>
    <div id="root">${html}</div>
    <script src="/bundle.js"></script>
  </body>
</html>`;
```

```js
// Next.js 中，默认页面即 SSR（页面组件在服务端渲染）
// app/page.js
export default async function Page() {
  const data = await fetchData(); // 服务端读取数据
  return <div>{data.title}</div>; // 渲染成 HTML 返回
}
```

## Request Time Rendering

Request Time Rendering（请求时渲染）指「每次请求到达时才实时渲染」，数据是「最新」的。它强调渲染发生的时间点是「请求时」而非「构建时」。

```text
Request Time Rendering 的含义：
1. 每个请求都重新执行渲染，拿到最新数据
2. 适合个性化、实时性要求高的页面（用户信息、实时行情）
3. 代价是每次请求都要付出渲染成本（需缓存优化）

对比：
构建时渲染（SSG）—— 数据是构建时刻的快照
请求时渲染（SSR）—— 数据是请求时刻的最新值
```

```js
// Next.js 中，动态渲染即请求时渲染
export const dynamic = 'force-dynamic'; // 强制每次请求都渲染

export default async function Dashboard() {
  const user = await fetchCurrentUser(); // 每个请求拿最新用户数据
  return <div>欢迎，{user.name}</div>;
}
```

## Hydration

Hydration（水合）是 SSR 的「下半场」：浏览器收到服务端渲染的 HTML 后，下载 JS 并在已有 DOM 上「绑定事件、恢复状态」，让静态 HTML 变成可交互的应用。

```text
Hydration 的过程：
1. 服务端返回带内容的 HTML（静态，不可交互）
2. 浏览器渲染 HTML，用户立即看到内容
3. JS 加载执行，React 遍历 DOM 树
4. 为每个节点绑定事件监听、挂载组件状态
5. 完成后页面「活」起来，可交互

关键点：
1. Hydration 要求客户端渲染结果与服务端 HTML 一致
2. 不一致会触发 Hydration Mismatch（见 56.4）
3. Hydration 完成前，页面「能看不能点」
```

```js
// 客户端入口：hydrate 而非 render
import { hydrateRoot } from 'react-dom/client';
import App from './App';

// 在服务端渲染出的 DOM 上水合
hydrateRoot(document.getElementById('root'), <App />);
```

## Streaming SSR

Streaming SSR（流式渲染）把 HTML 分成多个「块」，渲染好一块就立即发送一块，而不是等整个页面渲染完再一次性返回。它让首屏内容更快到达，慢数据不阻塞快内容。

```text
Streaming SSR 的价值：
1. 首屏更快 —— 头部/骨架先到达，用户先看到内容
2. 慢数据不阻塞 —— 慢接口用 Suspense 包裹，先流式返回其他部分
3. 降低 TTFB 感知 —— 浏览器边收边解析边渲染

实现依赖：
1. HTTP 分块传输（Transfer-Encoding: chunked）
2. React 的 Suspense + renderToPipeableStream
```

```js
// React 流式渲染：renderToPipeableStream
import { renderToPipeableStream } from 'react-dom/server';

app.get('/', (req, res) => {
  const stream = renderToPipeableStream(<App />, {
    onShellReady() {
      res.setHeader('Content-Type', 'text/html');
      stream.pipe(res); // 外壳就绪立即开始流式输出
    },
  });
});
```

```jsx
// 配合 Suspense：慢组件延迟到达，其余部分先流式返回
import { Suspense } from 'react';

export default function Page() {
  return (
    <div>
      <Header />                        {/* 立即返回 */}
      <Suspense fallback={<Skeleton />}>
        <SlowComments />                {/* 数据就绪后流式补入 */}
      </Suspense>
    </div>
  );
}
```

## 应用场景实战

### 场景一：Node.js 手写 SSR 服务

```js
// 极简 SSR 服务：Express + React
import express from 'express';
import { renderToString } from 'react-dom/server';

const app = express();
const data = { title: 'SSR 示例', items: ['A', 'B', 'C'] };

function App({ data }) {
  return (
    <main>
      <h1>{data.title}</h1>
      <ul>{data.items.map((i) => <li key={i}>{i}</li>)}</ul>
    </main>
  );
}

app.get('/', (req, res) => {
  const html = renderToString(<App data={data} />);
  res.send(`<!DOCTYPE html><html><body><div id="root">${html}</div>
    <script>window.__DATA__=${JSON.stringify(data)}</script>
    <script src="/bundle.js"></script></body></html>`);
});

app.listen(3000);
```

### 场景二：首屏数据注水避免二次请求

```js
// 服务端把数据序列化到 HTML，客户端 hydrate 时直接复用，不发重复请求
// 服务端
const html = renderToString(<App data={data} />);
res.send(`...<script>window.__INITIAL_STATE__=${JSON.stringify(data)}</script>...`);

// 客户端
const initialData = window.__INITIAL_STATE__;
hydrateRoot(root, <App data={initialData} />);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 首屏内容型页面用 SSR，后台/复杂交互页面可保持 CSR
2. 服务端渲染避免使用浏览器专属 API（window/localStorage），需做环境判断
3. 用 Streaming SSR + Suspense 让首屏更快，慢数据不阻塞
4. 首屏数据「注水」到 HTML，客户端 hydrate 时不重复请求
5. 服务端渲染结果与客户端保持一致，避免 Hydration Mismatch
6. 渲染结果用缓存（页面缓存/组件缓存）降低服务端压力
7. 大流量场景配合 CDN 边缘渲染或降级为 SSG
8. 监控服务端渲染耗时，慢数据接口单独告警

### 踩坑记录

```text
坑 1：服务端代码访问 window 报错
结论：服务端渲染时 window is not defined。
原因：Node 环境没有浏览器 API。
解法：用 useEffect（仅客户端执行）包裹，或 typeof window 判断。

坑 2：渲染结果不一致导致 Mismatch
结论：控制台报 Hydration Mismatch，DOM 重挂载。
原因：服务端/客户端用了不同数据（如 Date.now()、随机数）。
解法：把不确定性数据放到 useEffect 中，渲染阶段保持纯函数。

坑 3：SSR 首屏仍慢（TTFB 高）
结论：加 SSR 后反而更慢。
原因：服务端数据接口慢，渲染被阻塞。
解法：数据接口缓存、流式渲染、或对慢模块用 Suspense 延迟。

坑 4：内存/CPU 压力大
结论：高并发下服务端崩溃。
原因：每次请求都实时渲染，开销大且无缓存。
解法：页面级缓存、CDN、或对可静态的部分用 SSG/ISR。

坑 5：事件不生效（能看不能点）
结论：页面渲染正常但点击无响应。
原因：Hydration 未完成或 hydrateRoot 未正确绑定。
解法：检查客户端入口用 hydrateRoot，确认 JS 正常加载执行。
```
