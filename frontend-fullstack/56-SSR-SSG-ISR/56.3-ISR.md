## 概述

ISR（Incremental Static Regeneration，增量静态再生成）是 SSG 的「动态化补丁」：页面仍然以静态 HTML 提供服务，但在后台按需更新部分页面，无需重建整个站点。它兼具 SSG 的性能与 SSR 的时效性。

```text
ISR 解决的核心矛盾：
SSG —— 快，但内容陈旧（改数据要全量重建）
SSR —— 新鲜，但每次请求要渲染（慢、贵）
ISR —— 静态提供 + 后台定时/按需刷新单个页面（又快又新鲜）

ISR 的工作方式：
1. 页面首次按静态 HTML 返回（快）
2. 过了 revalidate 时间后，下次请求触发后台再生成
3. 再生成期间，用户仍拿到旧页面（stale-while-revalidate）
4. 再生成完成，后续请求拿到新页面
```

## Incremental Static Regeneration

Incremental Static Regeneration 指「增量」地重新生成静态页面，只更新变化的页面，而不是重建整个站点。

```text
增量的含义：
1. 空间上的增量 —— 只重建变化的页面，其余保持不变
2. 时间上的增量 —— 后台异步重建，不阻塞请求
3. 成本上的增量 —— 相比全量重建，构建成本大幅降低

典型场景：
1. 商品详情页 —— 价格/库存变化频繁，但页面多、访问不均衡
2. 新闻详情页 —— 内容发布后更新，但旧内容仍需可访问
3. 博客文章 —— 文章发布后补充修改
```

```js
// Next.js 中，用 revalidate 启用 ISR
export const revalidate = 60; // 60 秒后允许后台再生成

export default async function Product({ params }) {
  const product = await fetch(`https://api.example.com/products/${params.id}`).then((r) => r.json());
  return <div>{product.name}：{product.price}</div>;
}
```

## Revalidate

Revalidate（重新验证/再生成）是 ISR 的时间阈值：过了这个时间后，页面才允许在后台重新生成。它控制着「内容最多陈旧多久」。

```text
Revalidate 的工作机制：
1. 设置 revalidate = N 秒
2. 页面生成后，N 秒内所有请求直接返回缓存的静态 HTML
3. N 秒后，第一个到达的请求触发后台再生成
4. 再生成期间，后续请求仍拿旧 HTML（不会卡住用户）
5. 再生成完成，缓存被替换为新 HTML

这本质是「stale-while-revalidate」策略：
先返回旧内容（快），后台刷新（新鲜）。
```

```js
// 三种设置 revalidate 的方式
// 方式一：页面级配置
export const revalidate = 60;

// 方式二：fetch 级配置（针对单个请求）
export default async function Page() {
  const data = await fetch('https://api.example.com/data', {
    next: { revalidate: 60 },
  });
  return <div>{data}</div>;
}

// 方式三：全站兜底配置 next.config.js
module.exports = {
  experimental: {},
};
// 或在路由段配置 export const revalidate
```

```text
Revalidate 取值建议：
1. 静态内容 —— 不设置（永久静态）
2. 较稳定内容 —— 3600 秒（1 小时）
3. 较频繁内容 —— 60~300 秒
4. 实时内容 —— 用 SSR 或 On-demand Revalidation
```

## On-demand Revalidation

On-demand Revalidation（按需再验证）不依赖固定时间阈值，而是在「数据实际变化时」主动触发页面再生成，内容更新更及时、更省资源。

```text
按需再验证 vs 定时再验证：
定时 —— 固定时间间隔刷新，可能「过度刷新」或「更新不及时」
按需 —— 数据一变就刷新，精准、及时、省资源

按需的触发来源：
1. 内容管理系统（CMS）发布/更新内容时回调
2. 数据库变更事件
3. 后台管理操作
4. Webhook
```

```js
// Next.js 按需再验证：调用 revalidatePath / revalidateTag
// app/api/revalidate/route.js
import { revalidatePath, revalidateTag } from 'next/cache';

export async function POST(request) {
  const { secret, path } = await request.json();
  // 校验密钥，防止被恶意调用
  if (secret !== process.env.REVALIDATE_SECRET) {
    return Response.json({ error: 'invalid secret' }, { status: 401 });
  }
  revalidatePath(path); // 按路径再验证
  return Response.json({ revalidated: true });
}
```

```js
// 用 tag 批量再验证：给 fetch 打标签
export default async function Post({ params }) {
  const post = await fetch(`/api/posts/${params.id}`, {
    next: { tags: ['posts'] },
  });
  return <article>{post}</article>;
}

// 触发：revalidateTag('posts') 一次刷新所有带 posts 标签的页面
```

## 应用场景实战

### 场景一：商品详情页 ISR

```js
// 商品详情：价格库存变化频繁，用 ISR + 按需更新
export const revalidate = 60;

export async function generateStaticParams() {
  const products = await fetch(`${API}/products`).then((r) => r.json());
  return products.map((p) => ({ id: p.id }));
}

export default async function ProductDetail({ params }) {
  const product = await fetch(`${API}/products/${params.id}`, {
    next: { tags: [`product-${params.id}`] },
  }).then((r) => r.json());
  return (
    <div>
      <h1>{product.name}</h1>
      <p>价格：{product.price}</p>
      <p>库存：{product.stock}</p>
    </div>
  );
}
```

### 场景二：CMS 发布触发按需更新

```js
// 后台发布内容后，调用 revalidate 接口刷新对应页面
async function publishArticle(articleId) {
  await updateDB(articleId);
  // 通知 Next.js 重新生成该文章页
  await fetch('/api/revalidate', {
    method: 'POST',
    body: JSON.stringify({
      secret: process.env.REVALIDATE_SECRET,
      path: `/posts/${articleId}`,
    }),
  });
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 revalidate 时间阈值兜底，用 On-demand 做精准更新
2. 给 fetch 打 tag，按需批量再验证相关页面
3. Revalidate 接口必须校验密钥，防止被刷
4. 再生成是「后台异步」的，注意用户可能短暂看到旧内容
5. 商品/文章等「读多写少」的内容最适合 ISR
6. 大规模站点用 ISR 延迟生成，避免构建爆炸
7. 监控再生成失败率，接口不稳定会拖垮缓存刷新
8. 结合 CDN，再生成后 CDN 缓存也要同步失效

### 踩坑记录

```text
坑 1：改了数据页面迟迟不更新
结论：内容更新延迟很久。
原因：revalidate 设太大，或没触发按需再验证。
解法：调小 revalidate，或数据变更后调 revalidatePath/Tag。

坑 2：再生成期间用户看到旧数据
结论：更新「慢半拍」。
原因：ISR 是 stale-while-revalidate，先返回旧内容。
解法：对强实时性内容改用 SSR，或接受短暂延迟。

坑 3：revalidate 接口被恶意调用
结论：缓存被频繁刷新，服务被打爆。
原因：再验证接口没鉴权，任何人都能触发。
解法：加 secret 密钥校验 + 限流。

坑 4：再生成失败导致内容永久陈旧
结论：页面一直停留在旧版本。
原因：后台再生成抛错，未重试且无监控。
解法：再生成加重试、失败告警，接口做好降级。

坑 5：误以为 ISR 等于实时
结论：把强实时场景用 ISR，用户看到过期数据。
原因：ISR 本质仍是静态 + 延迟刷新，不是实时渲染。
解法：实时性要求高的页面用 SSR/CSR，ISR 用于「可容忍延迟」内容。
```
