## 概述

SSG（Static Site Generation，静态站点生成）指「在构建阶段就把页面渲染成静态 HTML 文件」。上线后直接由 CDN/静态服务器提供这些文件，无需服务端运行时。它是性能最好、成本最低、可扩展性最强的渲染方式。

```text
SSG 的核心思想：
1. 构建时（Build Time）—— 执行一次渲染，生成静态 HTML
2. 运行时（Run Time）—— 直接返回预生成的 HTML，无服务端计算
3. 每个页面都是独立文件，可被 CDN 缓存到全球边缘

SSG vs SSR：
SSG —— 构建时渲染一次，所有用户看到同一份（快照）
SSR —— 请求时实时渲染，每个请求拿最新数据

SSG 适合：博客、文档、营销页、商品详情（数据变化不频繁）
SSG 不适合：个性化内容、实时数据、用户相关页面
```

## Static Site Generation

Static Site Generation 是 SSG 的完整过程：构建时遍历页面，取数据、渲染、落盘为 HTML。

```text
静态生成的步骤：
1. 定义需要预渲染的页面/路径
2. 构建时为每个页面取数据
3. 渲染组件成 HTML
4. 连同静态资源输出到 dist 目录
5. 部署到 CDN/静态托管

特点：
1. 构建后内容固定，改动需重新构建
2. 无服务端，访问就是「下载 HTML」
3. 性能极致，几乎无 TTFB 瓶颈（CDN 边缘）
```

```js
// Next.js：默认静态化的页面（无动态数据依赖）
// app/page.js —— 不读请求、不用动态数据，自动静态生成
export default function Home() {
  return <h1>欢迎来到我的博客</h1>;
}
```

## Build Time Rendering

Build Time Rendering（构建时渲染）强调「渲染发生在构建阶段」。数据在构建时读取并「烧进」HTML，运行时不再请求数据。

```js
// Next.js 构建时渲染：generateStaticParams + 构建时取数据
export async function generateStaticParams() {
  // 构建时获取所有博客 id
  const posts = await fetch('https://api.example.com/posts').then((r) => r.json());
  return posts.map((p) => ({ id: p.id }));
}

export default async function Post({ params }) {
  // 构建时取数据并渲染成静态 HTML
  const post = await fetch(`https://api.example.com/posts/${params.id}`).then((r) => r.json());
  return <article>{post.content}</article>;
}
```

```text
构建时渲染的关键点：
1. 数据在构建时刻读取，成为「快照」
2. 构建完成后，页面内容不再变化（除非重新构建）
3. 构建产物包含完整 HTML，无需数据库运行时访问
4. 页面数量在构建时确定（通过 generateStaticParams）
```

```js
// Pages Router 时代的等价写法（getStaticProps）
export async function getStaticProps({ params }) {
  const post = await fetchPost(params.id); // 构建时取数据
  return { props: { post } };
}

export async function getStaticPaths() {
  const posts = await fetchPosts();
  return {
    paths: posts.map((p) => ({ params: { id: p.id } })), // 预渲染路径
    fallback: 'blocking',
  };
}
```

```text
构建快照 vs 运行时数据的取舍：
快照 —— 构建时固化，性能好但会「过期」
运行时 —— 每次请求实时，新鲜但成本高
折中 —— ISR 定时/按需刷新快照（见 56.3）
```

## Static HTML

Static HTML 是 SSG 的产物形态：完全静态的 HTML 文件，包含服务端渲染好的完整内容，可直接被 CDN 分发。

```text
Static HTML 的特征：
1. 完整内容 —— 打开即有内容，无白屏
2. 无服务端 —— 任何静态服务器/CDN 都能托管
3. 极致性能 —— 边缘分发，全球就近访问
4. 天然 SEO —— 爬虫直接读到完整内容
5. 可离线 —— 配合 Service Worker 缓存

典型产物结构：
dist/
  index.html
  about.html
  posts/
    post-1.html
    post-2.html
  _next/static/...
```

```bash
# 静态托管：任何静态服务器均可
npx serve dist
# 或部署到 CDN / GitHub Pages / Vercel / Netlify
```

```text
Static HTML 的缓存策略：
1. 内容哈希命名 —— 内容变则文件名变，可长期强缓存
2. HTML 用协商缓存 —— 更新后能及时拿到新版本
3. 静态资源用强缓存 + 指纹 —— 一年有效期
4. CDN 边缘缓存 —— 全球就近访问，命中率高

这样静态站点的性能可逼近「理论极限」：几乎零服务端计算。
```

## 应用场景实战

### 场景一：博客站点静态化

```js
// Next.js 博客：构建时生成所有文章页
export async function generateStaticParams() {
  const posts = await fetch(`${API}/posts`).then((r) => r.json());
  return posts.map((post) => ({ slug: post.slug }));
}

export default async function BlogPost({ params }) {
  const post = await fetch(`${API}/posts/${params.slug}`).then((r) => r.json());
  return (
    <article>
      <h1>{post.title}</h1>
      <div dangerouslySetInnerHTML={{ __html: post.content }} />
    </article>
  );
}
```

### 场景二：文档站多语言静态化

```js
// 按语言 + 文档路径生成静态页
export async function generateStaticParams() {
  const locales = ['zh', 'en'];
  const docs = await fetch(`${API}/docs`).then((r) => r.json());
  const paths = [];
  for (const locale of locales) {
    for (const doc of docs) {
      paths.push({ locale, slug: doc.slug });
    }
  }
  return paths;
}

export default async function Doc({ params }) {
  const { locale, slug } = params;
  const doc = await fetch(`${API}/${locale}/docs/${slug}`).then((r) => r.json());
  return <article>{doc.body}</article>;
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 内容不频繁变化的页面一律优先 SSG
2. 用 `generateStaticParams` 明确预渲染哪些路径
3. 构建时数据做缓存，避免构建耗时过长
4. 大型站点按需构建（只构建变更页面），配合 ISR
5. 静态 HTML 交给 CDN，配合长缓存头
6. 构建产物做内容哈希，实现原子发布
7. 数据源变化时用 Webhook 触发重新构建或 ISR
8. 监控构建时长与产物体积，防止构建爆炸

### 踩坑记录

```text
坑 1：内容更新但页面不变
结论：改了数据，线上页面还是旧的。
原因：SSG 是构建快照，未重新构建或未触发 ISR。
解法：数据变更后触发重新构建，或用 ISR 定时/按需更新。

坑 2：动态路径未生成导致 404
结论：访问未预渲染的路径返回 404。
原因：generateStaticParams 没覆盖所有路径，或 dynamicParams 默认行为。
解法：补充路径列表，或设置 dynamicParams = true 允许运行时兜底。

坑 3：构建时间爆炸
结论：构建动辄几十分钟。
原因：页面数量巨大（几万页），逐个构建取数据太慢。
解法：数据接口并行取数、增量构建、或改 ISR 延迟生成。

坑 4：构建时接口挂了导致构建失败
结论：构建流水线失败，无法发布。
原因：构建强依赖外部接口，接口抖动直接导致失败。
解法：接口重试 + 失败兜底数据，或数据前置到构建环境。

坑 5：误把个性化内容 SSG
结论：不同用户看到同一个人的数据。
原因：把依赖用户/请求的页面静态化了。
解法：个性化页面用 SSR/CSR，SSG 只用于公共内容。
```
