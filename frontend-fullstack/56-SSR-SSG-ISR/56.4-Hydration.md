## 概述

Hydration（水合）是 SSR/SSG 的关键第二步：服务端已经把组件渲染成 HTML，浏览器加载 JS 后，React 需要「认领」这些已有 DOM，绑定事件、恢复状态，让静态页面变成可交互应用。

```text
为什么叫「水合」（Hydration）：
就像干海参泡水恢复活性 —— 静态 HTML（干的）注入 JS 后
「活」过来，变得可交互。

Hydration 的三个阶段：
1. 服务端渲染 —— 生成完整 HTML（静态，无交互）
2. 浏览器解析 —— 渲染 HTML，用户立即看到内容
3. JS 水合 —— React 遍历 DOM，绑定事件与状态（页面可交互）

核心问题：
1. 一致性 —— 客户端渲染结果必须与服务端 HTML 一致
2. 成本 —— 水合需要下载并执行 JS，期间页面「能看不能点」
```

## Hydration

Hydration 是基础过程：客户端 React 在服务端渲染出的 DOM 上「接管」，而不是从零重新渲染。

```js
// 客户端入口：hydrateRoot 接管服务端 DOM
import { hydrateRoot } from 'react-dom/client';
import App from './App';

const container = document.getElementById('root');
hydrateRoot(container, <App />); // 在已有 DOM 上水合
```

```text
Hydration 做了什么：
1. 遍历服务端生成的 DOM 树
2. 建立 React 内部 Fiber 结构，与 DOM 对应
3. 为节点绑定事件监听器
4. 恢复组件状态（从注水数据）
5. 之后进入正常的客户端更新流程

与 render 的区别：
render —— 从头创建 DOM（会清空已有内容）
hydrateRoot —— 复用已有 DOM，只做「绑定」不重建
```

## Partial Hydration

Partial Hydration（部分水合）指「只水合需要交互的部分」，静态部分保持纯 HTML 不注入 JS，减少水合成本和下载体积。

```text
部分水合的思想：
1. 页面大部分是静态内容（文字、图片），无需 JS
2. 只有少量组件（按钮、表单、轮播）需要交互
3. 只对这些「交互岛」做水合，其余保持静态

收益：
1. 减少需要下载/执行的 JS
2. 降低水合开销
3. 更快达到可交互（TTI）

实现框架：Astro 的 Islands 架构、Qwik 的 Resumability 是典型代表
```

```js
// Astro Islands：默认静态，只有标记了 client:* 的组件才水合
// ---
// import Interactive from '../components/Interactive.jsx';
// ---
// <html><body>
//   <StaticContent />                        <!-- 纯静态，零 JS -->
//   <Interactive client:load />              <!-- 页面加载即水合 -->
//   <Interactive client:visible />           <!-- 滚动到可见才水合 -->
//   <Interactive client:idle />              <!-- 空闲时才水合 -->
// </body></html>
```

## Selective Hydration

Selective Hydration（选择性水合）是 React 18 的能力：通过 `Suspense` 边界，让「水合」可以按组件粒度分批、延迟进行，不阻塞高优先级交互。

```text
选择性水合解决的问题：
传统水合 —— 整个应用一次性水合，大应用水合慢，期间阻塞
选择性水合 —— 按 Suspense 边界分批水合，优先级高的先水合

特性：
1. 分批 —— 不同 Suspense 边界的水合可以错开
2. 可中断 —— 水合过程中用户点击高优先级区域，可优先水合该区域
3. 延迟 —— 不在首屏的组件可以推迟水合
```

```jsx
// React 18：用 Suspense 边界实现选择性水合
import { Suspense } from 'react';

export default function Page() {
  return (
    <div>
      <Header />                          {/* 优先水合 */}
      <Suspense fallback={<Loader />}>
        <Comments />                      {/* 数据就绪后再水合 */}
      </Suspense>
      <Suspense fallback={<Loader />}>
        <Sidebar />                       {/* 独立边界，互不阻塞 */}
      </Suspense>
    </div>
  );
}
```

```text
选择性水合的关键：
1. Suspense 边界是水合的「分片单位」
2. 用户交互会提高对应区域的优先级
3. 流式 SSR + 选择性水合配合，实现「渐进增强」的交互
```

## Hydration Mismatch

Hydration Mismatch（水合不一致）指客户端渲染结果与服务端 HTML 不一致，React 无法复用已有 DOM，导致报错、重新渲染甚至布局跳动。

```text
Mismatch 的常见原因：
1. 服务端/客户端环境差异（window、Date、Math.random）
2. 渲染时用了随机数、时间戳
3. 数据不一致（服务端数据与客户端注水数据不同）
4. 依赖用户代理/时区/语言等环境信息
5. 浏览器扩展篡改了 DOM

后果：
1. 控制台警告 Hydration failed
2. React 丢弃服务端 DOM，重新渲染（性能浪费）
3. 可能出现视觉闪烁、布局跳动
```

```jsx
// 错误示例：渲染时用随机值/时间戳
function BadComponent() {
  const now = Date.now(); // 服务端和客户端值不同
  return <div>当前时间：{now}</div>; // 必然 Mismatch
}

// 正确示例：把不确定性移到 useEffect
import { useEffect, useState } from 'react';
function GoodComponent() {
  const [now, setNow] = useState(null);
  useEffect(() => {
    setNow(Date.now()); // 仅客户端执行，避免 Mismatch
  }, []);
  return <div>当前时间：{now}</div>;
}
```

```jsx
// 抑制特定元素的水合告警（确知差异且无害时）
<div suppressHydrationWarning>
  {new Date().toLocaleString()}
</div>
```

## Hydration Cost

Hydration Cost（水合成本）指水合带来的额外开销：下载 JS、执行水合遍历、阻塞交互的时间。它是 SSR「首屏快但可交互慢」的根源。

```text
水合成本构成：
1. 下载成本 —— 客户端 JS 体积（SSR 仍需下载完整 bundle）
2. 执行成本 —— 解析、编译、执行 JS
3. 遍历成本 —— React 遍历整棵 DOM 树建立 Fiber
4. 绑定成本 —— 为节点绑定事件

水合成本导致的问题：
1. TTI（可交互时间）延迟 —— 首屏「能看不能点」
2. 低端设备更明显 —— CPU 弱，水合更慢
3. JS 越大，成本越高
```

```text
降低水合成本的策略：
1. 减少客户端 JS —— 更多组件留在服务端（RSC）
2. 部分水合 —— 只水合交互岛（Astro Islands）
3. 代码分割 —— 按路由/组件拆 bundle
4. 选择性水合 —— Suspense 边界分批水合
5. 边缘流式 —— 更快开始水合
6. Resumability —— Qwik 直接「恢复」而非「重放水合」
```

## 应用场景实战

### 场景一：修复水合不一致

```jsx
// 典型 Mismatch：依赖 localStorage 的主题初始化
import { useEffect, useState } from 'react';

function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light'); // 服务端固定 light
  useEffect(() => {
    const saved = localStorage.getItem('theme'); // 客户端才读真实值
    if (saved) setTheme(saved);
  }, []);
  return <div data-theme={theme}>{children}</div>;
}
```

### 场景二：选择性水合优化长页面

```jsx
// 评论区在首屏之外，用 Suspense 延迟水合
import { Suspense, lazy } from 'react';

const Comments = lazy(() => import('./Comments')); // 独立 chunk

export default function Article() {
  return (
    <article>
      <h1>标题</h1>
      <p>正文内容（服务端渲染，立即可见）</p>
      <Suspense fallback={<div>评论加载中...</div>}>
        <Comments /> {/* 滚动到时才加载与水合 */}
      </Suspense>
    </article>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 渲染函数保持「纯函数」，不确定性数据放 useEffect
2. 服务端与客户端数据用「注水」保持一致
3. 用 Suspense 边界切分水合粒度，实现选择性水合
4. 首屏外的重组件延迟加载，降低首屏水合成本
5. 尽量把组件留在服务端（RSC），减少客户端 JS
6. Mismatch 告警逐个排查，不要用 suppressHydrationWarning 掩盖问题
7. 监控 TTI 而非只看 FCP，水合成本体现在 TTI
8. 低端设备实测水合性能，避免「高端机流畅、低端机卡死」

### 踩坑记录

```text
坑 1：Mismatch 报错但不影响显示
结论：页面正常但控制台刷屏 Hydration failed。
原因：渲染时用了 Date.now()/Math.random() 等不确定值。
解法：不确定性数据移到 useEffect，渲染阶段保持确定。

坑 2：首屏能看不能点
结论：内容秒出，但点击按钮无反应数秒。
原因：水合未完成，大 bundle 阻塞了水合。
解法：代码分割 + 选择性水合，减小首屏水合范围。

坑 3：SSR 后事件全部失效
结论：页面完全静态，任何交互都没反应。
原因：客户端用了 render 而非 hydrateRoot，或 JS 加载失败。
解法：确认入口用 hydrateRoot，检查 bundle 加载与报错。

坑 4：localStorage 读取导致 Mismatch
结论：主题/语言初始化不一致，页面闪烁。
原因：服务端无 localStorage，客户端有，初始值不同。
解法：服务端用默认值，客户端 useEffect 中再读取真实值。

坑 5：以为 SSR 就没有 JS 成本
结论：加了 SSR，TTI 依然很差。
原因：SSR 只解决首屏 HTML，水合仍需下载执行完整 JS。
解法：结合 RSC/部分水合/代码分割，降低水合成本。
```
