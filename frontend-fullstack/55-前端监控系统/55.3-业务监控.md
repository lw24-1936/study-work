## 概述

业务监控关注的是「产品做得好不好」，而非「代码有没有 bug」。它通过埋点采集用户行为，计算 PV、UV、转化率、留存率等指标，回答「多少用户在用、用了哪些功能、转化是否健康」。

```text
业务监控与错误/性能监控的区别：
1. 错误监控 —— 代码是否出错（技术视角）
2. 性能监控 —— 页面是否流畅（技术视角）
3. 业务监控 —— 用户是否达成目标（产品视角）

业务监控的核心指标：
1. 流量指标 —— PV、UV、会话数
2. 转化指标 —— Conversion、Funnel
3. 留存指标 —— Retention（次日/7 日/30 日）
4. 功能指标 —— Feature Usage（功能使用率、活跃度）
```

## PV

PV（Page View，页面浏览量）是页面被访问的次数，每次加载/刷新都计一次，是流量规模的基础指标。

```js
// 页面 PV 埋点：在路由切换或页面加载时上报
function trackPV(pageName) {
  report({
    event: 'page_view',
    page: pageName || location.pathname,
    referrer: document.referrer,
    time: Date.now(),
  });
}

// SPA 场景：监听路由变化上报
router.afterEach((to) => {
  trackPV(to.path);
});
```

```text
PV 的关键点：
1. PV 统计「次数」，同一用户刷新 10 次计 10 次
2. SPA 中路由切换也算 PV，需在路由钩子埋点
3. PV 常与 UV 组合：PV/UV = 人均浏览页数
```

## UV

UV（Unique Visitor，独立访客）是去重后的访客数，按用户身份（设备/账号）去重，反映真实用户规模。

```js
// UV 需要稳定的用户标识
function getUserId() {
  // 已登录用账号 ID，未登录用持久化匿名 ID
  let id = localStorage.getItem('uid');
  if (!id) {
    id = crypto.randomUUID();
    localStorage.setItem('uid', id);
  }
  return id;
}

// 上报时携带 userId，后端按 userId 去重得到 UV
function trackUV(eventName, params = {}) {
  report({ event: eventName, userId: getUserId(), ...params });
}
```

```text
UV 与 PV 的关系：
1. UV 去重统计「人」，PV 统计「次」
2. 人均 PV = PV / UV，反映用户粘性与页面深度
3. UV 依赖稳定标识：登录用户用账号，匿名用户用持久化 Cookie/localStorage
```

## Conversion

Conversion（转化率）是完成目标行为的用户占进入流程用户的比例，是衡量产品价值的核心指标。

```js
// 转化埋点：在关键动作（注册成功、下单支付）打点
function trackConversion(goalName, params = {}) {
  report({
    event: 'conversion',
    goal: goalName,           // 例如 'signup' / 'purchase'
    userId: getUserId(),
    value: params.value || 0, // 金额等价值
    ...params,
  });
}

// 使用
trackConversion('signup', { channel: 'organic' });
trackConversion('purchase', { value: 199, orderId: 'o123' });
```

```text
转化率计算：
转化率 = 完成目标用户数 / 进入流程用户数 × 100%

常见转化目标：注册、下单、支付、订阅、激活。
转化率是漏斗的终点，常与渠道（channel）关联分析。
```

## Funnel

Funnel（漏斗）把用户路径拆成多个步骤，统计每步的转化率，定位「流失最严重」的环节。

```js
// 漏斗埋点：给每个步骤打点，后端按 userId 串联成漏斗
function trackFunnel(step, stepName) {
  report({
    event: 'funnel',
    step,                 // 步骤序号 1/2/3
    stepName,             // 例如 'view_product' / 'add_cart' / 'checkout' / 'pay'
    userId: getUserId(),
  });
}

// 电商漏斗示例
trackFunnel(1, 'view_product');  // 浏览商品
trackFunnel(2, 'add_cart');      // 加入购物车
trackFunnel(3, 'checkout');      // 提交订单
trackFunnel(4, 'pay');           // 支付成功
```

```text
漏斗分析的关键：
1. 步骤之间是「有序且递减」的关系
2. 每步转化率 = 本步人数 / 上一步人数
3. 定位流失最大的步骤，针对性优化
4. 需按用户维度串联，保证同一用户贯穿全程
```

## Retention

Retention（留存率）衡量用户「来了之后是否还回来」，按首次激活后第 N 天仍活跃的比例计算。

```js
// 留存埋点：每次活跃（启动/访问）都上报，后端计算留存
function trackActive() {
  report({
    event: 'active',
    userId: getUserId(),
    firstSeen: localStorage.getItem('first_seen'), // 首次访问时间
  });
}

// 首次访问记录
if (!localStorage.getItem('first_seen')) {
  localStorage.setItem('first_seen', String(Date.now()));
}
```

```text
留存率计算：
1. 次日留存 = 第 1 天新增用户中，第 2 天仍活跃的比例
2. 7 日留存 = 第 7 天仍活跃的比例
3. 30 日留存 = 第 30 天仍活跃的比例

留存率是「产品是否真正有价值」的最强信号，
高留存通常比高 PV 更重要。
```

## Feature Usage

Feature Usage（功能使用）统计各功能的使用频次与用户数，回答「哪些功能被用了、哪些是摆设」。

```js
// 功能使用埋点：统一封装，所有功能点击都打点
function trackFeature(feature, action = 'click') {
  report({
    event: 'feature',
    feature,       // 例如 'dark_mode' / 'export' / 'share'
    action,        // click / toggle / open
    userId: getUserId(),
  });
}

// 使用
document.querySelector('#darkModeBtn').addEventListener('click', () => {
  trackFeature('dark_mode', 'toggle');
});
```

```js
// 功能使用率：使用过某功能的用户 / 活跃用户
// 后端聚合：按 feature 分组，distinct userId 计数
// 产出「功能使用排行榜」，指导功能取舍
```

## 应用场景实战

### 场景一：电商下单漏斗监控

```js
// 完整电商转化链路埋点
const tracker = {
  viewProduct(id) { trackFunnel(1, 'view_product', { id }); },
  addCart(id) { trackFunnel(2, 'add_cart', { id }); },
  checkout(ids) { trackFunnel(3, 'checkout', { ids }); },
  paySuccess(orderId, value) {
    trackFunnel(4, 'pay', { orderId });
    trackConversion('purchase', { orderId, value });
  },
};

// 页面流程调用
tracker.viewProduct('p1001');
tracker.addCart('p1001');
tracker.checkout(['p1001']);
tracker.paySuccess('o20260813', 199);
```

### 场景二：新功能灰度与使用评估

```js
// 灰度上线新功能，监控使用率与转化贡献
function trackFeatureExperiment(feature, variant) {
  report({
    event: 'feature',
    feature,
    variant, // 'A' 对照组 / 'B' 实验组（A/B 测试）
    userId: getUserId(),
  });
}

// 对照组与实验组各打点，对比使用率与转化
trackFeatureExperiment('new_search', 'A');
trackFeatureExperiment('new_search', 'B');
```

## 最佳实践与踩坑记录

### 最佳实践

1. 埋点统一封装（track 函数），规范 event 命名
2. 关键路径打漏斗，而非零散打点
3. 转化目标明确且可量化，绑定 userId 去重
4. 数据上报带 userId、渠道、版本、时间，支持多维度分析
5. 留存按「首次激活日」分组（cohort 分析），而非简单平均
6. 功能使用率 = 使用用户 / 活跃用户，而非点击次数
7. 埋点做采样与去重，控制上报量
8. 埋点字段预留扩展位，避免后续频繁改动数据结构

### 踩坑记录

```text
坑 1：PV 用错统计口径
结论：数据虚高或偏低。
原因：SPA 路由切换没埋点，或后端把接口请求误当 PV。
解法：前端路由钩子统一埋点，前后端口径对齐。

坑 2：UV 去重失效
结论：同一用户被计成多个 UV。
原因：匿名用户每次清 localStorage 都换新 ID。
解法：登录态优先用账号 ID，匿名 ID 持久化到 Cookie（而非 localStorage 可被清）。

坑 3：漏斗数据对不齐
结论：漏斗后一步人数比前一步还多。
原因：没按 userId 串联，各步骤独立统计了「次数」。
解法：漏斗用 distinct userId，按用户维度串联全程。

坑 4：留存定义混淆
结论：留存率看起来异常高或低。
原因：把「第 7 天活跃」与「7 天内任意一天活跃」混为一谈。
解法：明确口径，统一用「第 N 天当天活跃」。

坑 5：功能埋点遗漏导致误判
结论：以为功能没人用，其实是埋点没覆盖。
原因：只埋了入口，没埋内部交互分支。
解法：功能上线前梳理全部交互点，逐一埋点。
```
