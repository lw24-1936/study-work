## 概述

性能监控负责采集页面「加载快不快、交互顺不顺、渲染稳不稳」的量化数据。它依赖浏览器提供的多种 Performance API，把「用户主观感受」变成「可分析、可告警、可优化的客观指标」。

```text
性能监控的指标层次：
1. 加载性能 —— 页面从发起请求到渲染完成有多快（Navigation Timing、LCP）
2. 资源性能 —— 每个静态资源的耗时与体积（Resource Timing）
3. 渲染性能 —— 首屏绘制、内容绘制节点（Paint Timing）
4. 交互性能 —— 长任务、输入响应（Long Task、INP）
5. 自定义性能 —— 业务自定义埋点（User Timing）

核心 Performance API：
1. Performance Timeline —— 所有性能条目的统一入口
2. Navigation Timing —— 页面导航各阶段时间
3. Resource Timing —— 资源加载耗时
4. Paint Timing —— FP/FCP 绘制节点
5. Long Tasks —— 超过 50ms 的长任务
6. User Timing —— mark/measure 自定义测量
```

## Web Vitals

Web Vitals 是 Google 定义的核心体验指标，其中 LCP、INP、CLS 构成「核心 Web 指标」（Core Web Vitals），是 SEO 排名的参考因素。

```text
核心 Web 指标（Core Web Vitals）：
1. LCP（Largest Contentful Paint）—— 最大内容绘制，< 2.5s 为优
2. INP（Interaction to Next Paint）—— 交互响应，< 200ms 为优
3. CLS（Cumulative Layout Shift）—— 布局偏移，< 0.1 为优

辅助指标：
FCP（首次内容绘制）、TTFB（首字节时间）、FID（首次输入延迟，已被 INP 取代）
```

```js
// 官方 web-vitals 库：自动采集并上报
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals';

function send(metric) {
  report({ name: metric.name, value: metric.value, rating: metric.rating });
}

onLCP(send);
onINP(send);
onCLS(send);
onFCP(send);
onTTFB(send);
```

## Navigation Timing

Navigation Timing 记录页面导航全过程的精确时间点，是分析「首屏慢在哪一段」的基础。

```js
// Navigation Timing API（Level 2，基于 PerformanceObserver）
const [nav] = performance.getEntriesByType('navigation');
if (nav) {
  const metrics = {
    dns: nav.domainLookupEnd - nav.domainLookupStart,       // DNS 解析
    tcp: nav.connectEnd - nav.connectStart,                 // TCP 建连
    ttfb: nav.responseStart - nav.requestStart,             // 首字节时间
    download: nav.responseEnd - nav.responseStart,          // 响应下载
    domParse: nav.domContentLoadedEventEnd - nav.domInteractive, // DOM 解析
    load: nav.loadEventEnd - nav.startTime,                 // 完整加载
  };
  console.log(metrics);
}
```

```text
Navigation Timing 关键阶段：
startTime → redirect → DNS → TCP → request → response → domInteractive
→ domContentLoaded → loadEventEnd

TTFB（responseStart - requestStart）是首屏优化的第一指标，
它由「服务端响应 + 网络往返」共同决定。
```

## Resource Timing

Resource Timing 提供每个静态资源（JS/CSS/图片/接口）的加载耗时与体积，用于找出「最慢的资源」。

```js
// 通过 PerformanceObserver 监听资源加载
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    const { name, initiatorType, duration, transferSize, encodedBodySize } = entry;
    report({
      type: 'resource',
      url: name,
      kind: initiatorType,            // script/css/img/fetch 等
      duration: Math.round(duration), // 总耗时 ms
      transferSize,                   // 传输大小（含头）
      encodedBodySize,                // 压缩后体积
    });
  }
});
observer.observe({ type: 'resource', buffered: true });
```

```js
// 一次性读取所有资源，找出耗时 Top 5
const resources = performance.getEntriesByType('resource')
  .filter((e) => e.duration > 0)
  .sort((a, b) => b.duration - a.duration)
  .slice(0, 5)
  .map((e) => ({ url: e.name, duration: Math.round(e.duration) }));
console.log('最慢资源：', resources);
```

## Paint Timing

Paint Timing 提供首次绘制（FP）与首次内容绘制（FCP）的时间点，反映用户「看到内容」的速度。

```js
// Paint Timing API
const paintObserver = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.name === 'first-paint') report({ name: 'FP', value: entry.startTime });
    if (entry.name === 'first-contentful-paint') report({ name: 'FCP', value: entry.startTime });
  }
});
paintObserver.observe({ type: 'paint', buffered: true });
```

```text
FP（First Paint）—— 浏览器首次在屏幕上绘制任何像素
FCP（First Contentful Paint）—— 首次绘制文本/图片等实质内容

FCP 比 FP 更有意义：用户感知「页面有内容了」而非「白屏结束」。
LCP 则是 FCP 的延伸：主要内容（大图/大标题）真正呈现的时间。
```

## Long Task

Long Task 指占用主线程超过 50ms 的任务，它会导致页面卡顿、输入无响应。通过监听 longtask 定位「卡顿元凶」。

```js
// Long Tasks API：监听超过 50ms 的长任务
const longTaskObserver = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    report({
      type: 'longtask',
      duration: Math.round(entry.duration), // 阻塞主线程时长
      startTime: entry.startTime,
      attribution: entry.attribution?.[0]?.name, // 来源脚本
    });
  }
});
longTaskObserver.observe({ type: 'longtask', buffered: true });
```

```js
// 手动模拟：一个阻塞主线程 200ms 的长任务
function heavyBlock() {
  const start = Date.now();
  while (Date.now() - start < 200) {} // 同步死循环阻塞 200ms
}
heavyBlock(); // 会被 longtask 捕获
```

## User Timing

User Timing 通过 `performance.mark` 打点、`performance.measure` 测量区间，用于测量业务自定义阶段耗时（如「点击提交到接口返回」）。

```js
// 打点 + 测量
performance.mark('submit-start');
await doSubmit();            // 业务操作
performance.mark('submit-end');
performance.measure('submit-duration', 'submit-start', 'submit-end');

const m = performance.getEntriesByName('submit-duration')[0];
console.log(`提交耗时：${m.duration}ms`);
```

```js
// 清理标记，避免内存堆积
performance.clearMarks('submit-start');
performance.clearMarks('submit-end');
performance.clearMeasures('submit-duration');
```

## 应用场景实战

### 场景一：首屏性能自动埋点 SDK

```js
// 页面加载完成后一次性采集全部加载指标
function collectPagePerformance() {
  window.addEventListener('load', () => {
    setTimeout(() => {
      const nav = performance.getEntriesByType('navigation')[0];
      const paint = performance.getEntriesByType('paint');
      const fcp = paint.find((p) => p.name === 'first-contentful-paint');
      report({
        ttfb: nav?.responseStart - nav?.requestStart,
        domReady: nav?.domContentLoadedEventEnd - nav?.startTime,
        loadTime: nav?.loadEventEnd - nav?.startTime,
        fcp: fcp?.startTime,
        resourceCount: performance.getEntriesByType('resource').length,
      });
    }, 0);
  });
}
```

### 场景二：慢资源分析看板

```js
// 统计各资源类型的平均耗时，辅助优化决策
function summarizeResources() {
  const byType = {};
  for (const e of performance.getEntriesByType('resource')) {
    const t = e.initiatorType || 'other';
    byType[t] = byType[t] || { count: 0, total: 0 };
    byType[t].count++;
    byType[t].total += e.duration;
  }
  return Object.entries(byType).map(([type, v]) => ({
    type,
    avg: Math.round(v.total / v.count),
  }));
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优先采集 Core Web Vitals（LCP/INP/CLS），这是 SEO 与体验的核心
2. 用 PerformanceObserver 而非轮询 getEntries，实时且不遗漏
3. 关注 P75/P95 分位数而非平均值，长尾才是真实体感
4. 性能数据区分「实验室数据」与「真实用户数据（RUM）」
5. 首屏指标在 load 后延迟采集，避免干扰页面加载
6. 慢资源分析按 initiatorType 分类统计，定位是图片还是接口
7. 采集数据带设备、网络、版本维度，方便归因
8. 打点用 User Timing 统一规范命名，避免标记名冲突

### 踩坑记录

```text
坑 1：用平均值评估性能
结论：平均值好看但用户实际卡顿。
原因：少数慢请求被大量快请求拉平。
解法：上报分位数（P75/P95），重点关注长尾。

坑 2：LCP 采样时机不对
结论：LCP 值偏小甚至缺失。
原因：LCP 元素可能在图片懒加载后才出现，早期采样会漏。
解法：用 web-vitals 库持续监听直到 hidden/pagehide。

坑 3：PerformanceObserver 遗漏历史条目
结论：监听前已发生的条目采集不到。
原因：默认 observe 不返回已存在的条目。
解法：observe 加 buffered: true。

坑 4：Long Task 监听在生产被忽略
结论：卡顿无法定位。
原因：没监听 longtask，只看了 load 时间。
解法：上线 longtask 采集 + 脚本 attribution 归因。

坑 5：measure 报错 "mark not found"
结论：performance.measure 抛异常。
原因：end mark 在 start mark 之前，或 mark 名拼写错误。
解法：确保打点顺序，measure 前检查 mark 存在。
```
