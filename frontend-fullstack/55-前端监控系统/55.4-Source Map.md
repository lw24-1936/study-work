## 概述

Source Map 是把「压缩混淆后的产物代码」映射回「原始源码」的映射文件。监控平台拿到线上报错的压缩堆栈后，必须借助 Source Map 才能还原出可读的源码位置，否则只能看到 `a.js:1:23456` 这样的天书。

```text
Source Map 在错误监控中的作用：
1. 构建时生成 —— devtool 配置生成 .map 文件
2. 构建后上传 —— 把 .map 上传到监控平台（Upload）
3. 关联版本 —— 用 Release/Commit 标识哪个版本（Release）
4. 报错时还原 —— 用 map 把压缩堆栈映射回源码（Stack Trace Mapping）

Source Map 文件内容（.map 是 JSON）：
1. version —— Source Map 规范版本
2. sources —— 原始源码文件列表
3. names —— 原始变量/函数名
4. mappings —— VLQ 编码的位置映射
5. sourcesContent —— 内嵌的源码内容（可选）
```

## Source Map Upload

Source Map 需要在上线时上传到监控平台，平台才能在收到报错后解析堆栈。上传方式有手动 CLI、Webpack 插件、CI 集成三种。

```js
// webpack 配置：生成带 sourcemap 的产物
module.exports = {
  mode: 'production',
  devtool: 'hidden-source-map', // 生成 map 但不加 sourceMappingURL 注释
};
```

```bash
# 方式一：Sentry CLI 手动上传
sentry-cli sourcemaps upload \
  --release 1.0.0 \
  --org my-org \
  --project my-app \
  ./dist

# 方式二：Sentry Webpack 插件（构建时自动上传）
npm install @sentry/webpack-plugin
```

```js
// 方式二实现：Webpack 插件自动上传
const { sentryWebpackPlugin } = require('@sentry/webpack-plugin');
module.exports = {
  devtool: 'hidden-source-map',
  plugins: [
    sentryWebpackPlugin({
      org: 'my-org',
      project: 'my-app',
      release: process.env.VERSION,
      authToken: process.env.SENTRY_AUTH_TOKEN,
      include: './dist',
      ignore: ['node_modules'],
    }),
  ],
};
```

## Release

Release 是「版本标识」，用于把某个报错关联到「哪一次发布的代码」。只有报错上报时携带的 release 与上传 Source Map 时的 release 一致，堆栈才能被还原。

```text
Release 的规则：
1. 每个上线版本有唯一 release 标识（如 1.0.0 或 git 提交哈希）
2. 上传 Source Map 时指定 release
3. 报错上报时也要带同一个 release
4. release 不匹配 → 平台找不到对应 map → 还原失败
```

```js
// 前端上报时注入 release
import * as Sentry from '@sentry/browser';
Sentry.init({
  dsn: 'https://xxx@yyy.ingest.sentry.io/1',
  release: process.env.REACT_APP_VERSION || '1.0.0',
});

// 构建时注入版本号（webpack DefinePlugin）
new webpack.DefinePlugin({
  'process.env.REACT_APP_VERSION': JSON.stringify(process.env.VERSION),
});
```

```bash
# 上传时指定相同 release
sentry-cli sourcemaps upload --release 1.0.0 ./dist
```

## Commit

Commit 把「代码提交」与「版本」关联，让监控平台能定位到「哪个 commit 引入了这个 bug」，甚至关联到具体作者，实现报错 → commit → 代码改动的完整链路。

```text
Commit 关联的价值：
1. 定位引入 bug 的提交
2. 关联提交作者，自动指派处理人
3. 结合 PR/issue，形成闭环

实现：集成代码托管平台（GitHub/GitLab），
监控平台根据 commit 哈希拉取提交信息与改动 diff。
```

```bash
# Sentry CLI 关联 commit（从当前 git 历史读取）
sentry-cli releases set-commits 1.0.0 --auto

# 或手动指定
sentry-cli releases set-commits 1.0.0 \
  --commit "my-org/my-repo@abc1234"
```

```js
// 前端上报时携带 commit 上下文（可选）
Sentry.init({
  dsn: '...',
  release: '1.0.0',
  integrations: [],
  beforeSend(event) {
    event.release = '1.0.0';
    return event;
  },
});
```

## Stack Trace Mapping

Stack Trace Mapping 是「压缩堆栈 → 源码堆栈」的还原过程。监控平台收到报错堆栈后，根据文件名、行列号在 Source Map 中查找对应的源码位置。

```text
堆栈还原流程：
1. 收到压缩堆栈，如 at a (bundle.js:1:23456)
2. 解析出产物文件 bundle.js、行 1、列 23456
3. 在 bundle.js.map 的 mappings 中查找 VLQ 编码的映射
4. 找到对应 sources 中的源码文件、行号、列号、原函数名
5. 替换堆栈帧，得到可读源码位置

关键前提：
1. 上报的 release 与上传 map 的 release 一致
2. 产物文件 URL 前缀（如 CDN 域名）能匹配上传时的路径
3. map 文件在平台侧完整保留（sourcesContent 内嵌）
```

```js
// 手动解析 Source Map（示例：用 source-map 库还原单帧）
const { SourceMapConsumer } = require('source-map');

async function mapFrame(rawFrame) {
  // rawFrame: { file: 'bundle.js', line: 1, column: 23456 }
  const rawMap = require('./bundle.js.map');
  const consumer = await new SourceMapConsumer(rawMap);
  const original = consumer.originalPositionFor({
    line: rawFrame.line,
    column: rawFrame.column,
  });
  consumer.destroy();
  return original; // { source: 'src/App.js', line: 12, column: 5, name: 'init' }
}
```

## 应用场景实战

### 场景一：CI 中自动上传 Source Map

```yaml
# .github/workflows/deploy.yml 片段
- name: Build
  run: npm run build
  env:
    VERSION: ${{ github.sha }}

- name: Upload Source Maps
  run: |
    npx sentry-cli sourcemaps upload \
      --release $GITHUB_SHA \
      --org my-org \
      --project my-app \
      ./dist
  env:
    SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
```

### 场景二：本地调试还原线上报错

```js
// 从监控平台拿到线上报错的压缩堆栈，本地用 source-map 还原
const { SourceMapConsumer } = require('source-map');
const rawMap = require('./dist/bundle.js.map');

async function restoreStack(rawStack) {
  const consumer = await new SourceMapConsumer(rawMap);
  const restored = rawStack.map((frame) => {
    const pos = consumer.originalPositionFor({
      line: frame.line,
      column: frame.column,
    });
    return `${pos.source}:${pos.line}:${pos.column} ${pos.name || ''}`;
  });
  consumer.destroy();
  return restored;
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产用 `hidden-source-map`，生成 map 但不在产物里暴露路径
2. 用 release 严格标识版本，上报与上传必须同版本
3. 在 CI 构建完成后自动上传，避免手动遗漏
4. map 上传时内嵌 sourcesContent，平台离线可还原
5. 关联 commit，实现报错到代码改动的闭环
6. map 文件不上传到 CDN/公开服务器，防止源码泄露
7. 定期清理历史 map，控制平台存储成本
8. 测试环境也用真实 map，验证还原链路是否打通

### 踩坑记录

```text
坑 1：release 不匹配导致还原失败
结论：监控平台显示「Source Map 未找到」。
原因：上报时 release 与上传 map 时的 release 不一致。
解法：构建注入版本号，上报和上传都用同一个环境变量。

坑 2：CDN 前缀不匹配
结论：平台找不到对应 map。
原因：产物部署在 CDN（https://cdn.x.com/...），上传时路径前缀不同。
解法：上传时配置 urlPrefix，或上传完整目录保持路径一致。

坑 3：Source Map 泄露源码
结论：线上 .map 文件可被公开下载。
原因：devtool 用了 source-map，map 被部署到 CDN 且未限制访问。
解法：用 hidden-source-map，map 只上传监控平台，不随产物部署。

坑 4：mappings 还原位置偏差
结论：还原出的行号与真实源码不符。
原因：构建时 sourceRoot 配置、多 loader 叠加导致映射错位。
解法：检查 devtool 与 loader 顺序，必要时用较慢但精确的 source-map 模式。

坑 5：map 过大影响上传
结论：上传超时或存储爆满。
原因：大型项目 map 体积巨大，sourcesContent 内嵌翻倍。
解法：按 chunk 拆分上传，或平台侧裁剪 sourcesContent。
```
