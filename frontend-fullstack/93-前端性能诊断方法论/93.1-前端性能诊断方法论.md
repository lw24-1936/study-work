## 概述

前端性能诊断不是「打开 DevTools 随便点两下」，而是一条有闭环的方法论：从发现性能问题，到建立基线、定位瓶颈、提出并验证假设，最后优化、回归、监控并持续治理。它解决的核心问题是「性能问题该按什么顺序查、每步怎么验证、优化后怎么保证不回退」。

```text
前端性能诊断的九步闭环：
发现问题 → 建立基线 → 定位瓶颈 → 提出假设 → 实验验证 → 优化 → 回归测试 → 建立监控 → 持续治理
```

```js
// 诊断的起点：先把性能问题量化成数字
// 用 PerformanceObserver 监听核心 Web Vitals
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.name, entry.value);
  }
});
observer.observe({ type: 'largest-contentful-paint', buffered: true });
observer.observe({ type: 'layout-shift', buffered: true });
observer.observe({ type: 'longtask', buffered: true });
```

## 发现问题

性能问题的来源通常是三类：用户反馈「页面卡」、监控告警（LCP/INP 超阈值）、或者上线前压测。这一步的关键是把「感觉慢」转成「哪慢、慢多少」的量化描述。

```js
// 用 web-vitals 在页面里采集核心指标，发现超过预算的项
import { onLCP, onINP, onCLS } from 'web-vitals';

onLCP((metric) => {
  if (metric.value > 2500) report('lcp-over-budget', metric.value);
});
onINP((metric) => {
  if (metric.value > 200) report('inp-over-budget', metric.value);
});
onCLS((metric) => {
  if (metric.value > 0.1) report('cls-over-budget', metric.value);
});
```

```text
发现问题的三个信号源：
1. 用户反馈 —— 定性：卡、白屏、发热，需转成可复现路径
2. 监控告警 —— 定量：LCP > 2.5s、INP > 200ms、CLS > 0.1
3. 主动巡检 —— 上线前 Lighthouse 跑分、性能预算 CI 拦截
```

## 建立基线

优化前必须先记录「当前到底多慢」，否则优化完无从判断有没有效果。基线要包含指标值、采样环境、时间戳，最好能复现。

```js
// 采集一组关键指标作为基线快照
function snapshotBaseline() {
  const nav = performance.getEntriesByType('navigation')[0];
  const paint = performance.getEntriesByType('paint');
  return {
    time: Date.now(),
    fcp: paint.find(p => p.name === 'first-contentful-paint')?.startTime,
    lcp: paint.find(p => p.name === 'largest-contentful-paint')?.startTime,
    domContentLoaded: nav.domContentLoadedEventEnd,
    load: nav.loadEventEnd,
    transferSize: performance.getEntriesByType('resource')
      .reduce((sum, r) => sum + (r.transferSize || 0), 0),
  };
}
console.log(snapshotBaseline());
```

```text
基线的三个要素：
1. 指标值 —— FCP/LCP/INP/CLS 或自定义耗时
2. 环境 —— 设备、网络（CPU/网络节流）、浏览器版本
3. 复现 —— 用 Lighthouse CLI 或固定脚本，保证可重复测量
```

## 定位瓶颈

瓶颈定位围绕三大面板：Performance（主线程/渲染）、Network（资源加载）、Memory（内存增长）。先把范围收敛到「加载慢 / 交互慢 / 内存涨」中的哪一类。

### Performance 面板

```js
// 长任务切分：定位主线程被什么长任务占满
const observer = new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    console.log(`长任务 ${entry.startTime.toFixed(0)}ms，持续 ${entry.duration}ms`);
    // 入口属性 attribution 可看是哪段脚本引起
    console.log(entry.attribution?.[0]?.containerType);
  });
});
observer.observe({ type: 'longtask', buffered: true });
```

### Network 面板

```js
// 资源时序：找出最慢、最大、阻塞渲染的资源
performance.getEntriesByType('resource')
  .filter(r => r.initiatorType !== 'fetch')
  .sort((a, b) => b.duration - a.duration)
  .slice(0, 10)
  .forEach(r => console.log(r.name, `${r.duration.toFixed(0)}ms`, r.transferSize));
```

### Memory 面板

```js
// Chrome 专有：观察 JS 堆随时间的变化趋势
// 配合 DevTools Memory 面板的堆快照定位具体对象
setInterval(() => {
  if (performance.memory) {
    console.log('usedJSHeapSize', (performance.memory.usedJSHeapSize / 1048576).toFixed(1), 'MB');
  }
}, 1000);
```

## 提出假设

定位到可疑区域后，先写一条「可证伪」的假设，再设计实验去验证。假设要具体到「改了 X，Y 指标会从 A 变成 B」。

```text
假设的写法（可证伪）：
假设 1：首屏 LCP 高是因为 hero 图片是 2MB 的 PNG，改成 WebP + 懒加载后 LCP 应从 4.2s 降到 2.5s 内。
假设 2：列表滚动卡顿是因为每帧都在重建 1000 个 DOM 节点，改成虚拟滚动后 INP 应从 320ms 降到 150ms 内。
假设 3：页面内存持续上涨是因为定时器里累积了闭包引用，清掉后堆内存应稳定在 60MB 以下。
```

```js
// 用 performance.mark/measure 给可疑代码段打点，量化假设里的 A/B
performance.mark('suspect-start');
doSuspectWork();
performance.mark('suspect-end');
performance.measure('suspect-cost', 'suspect-start', 'suspect-end');
console.log(performance.getEntriesByName('suspect-cost')[0].duration, 'ms');
```

## 实验验证

假设必须经过控制变量实验验证，而不是「改了感觉快一点」。验证手段：本地复现、Lighthouse 对比、A/B 分桶，关键是每次只改一个变量。

```js
// 控制变量：对比优化前后同一段逻辑的耗时
function measure(label, fn) {
  const t0 = performance.now();
  const result = fn();
  const t1 = performance.now();
  console.log(label, (t1 - t0).toFixed(2), 'ms');
  return result;
}

measure('优化前', () => {
  for (let i = 0; i < 100000; i++) document.createElement('div');
});
measure('优化后', () => {
  const frag = document.createDocumentFragment();
  for (let i = 0; i < 100000; i++) frag.appendChild(document.createElement('div'));
});
```

```text
实验验证的三条纪律：
1. 一次只改一个变量 —— 同时改十处，快了也不知道是谁的功劳
2. 多次测量取中位数 —— 单次抖动会误导结论
3. 同环境下对比 —— 设备、网络、浏览器一致，否则不可比
```

## 优化

优化是假设被验证后的落地执行，按收益从高到低排序。常见方向：减少传输（压缩/懒加载）、减少主线程工作（虚拟滚动/离屏）、减少重排重绘。

```js
// 三个高频优化手段
// 1. 图片懒加载（减少首屏传输）
<img loading="lazy" src="hero.webp" alt="hero" />;

// 2. 重计算缓存（减少主线程工作）
const memo = new Map();
function expensive(n) {
  if (memo.has(n)) return memo.get(n);
  const r = n * n * Math.random();
  memo.set(n, r);
  return r;
}

// 3. 批量 DOM 写入（减少重排）
const list = document.querySelector('#list');
const frag = document.createDocumentFragment();
items.forEach(item => {
  const li = document.createElement('li');
  li.textContent = item;
  frag.appendChild(li);
});
list.appendChild(frag);
```

## 回归测试

优化完必须防「回退」：把关键指标固化成性能预算，跑 CI 拦截。否则三个月后同一批优化被后人无意改回，性能又退化。

```js
// 自定义性能预算断言：CI 里失败即拦截
function assertBudget(budgets) {
  const nav = performance.getEntriesByType('navigation')[0];
  const paint = performance.getEntriesByType('paint');
  const lcp = paint.find(p => p.name === 'largest-contentful-paint');
  const checks = {
    lcp: { value: lcp?.startTime ?? Infinity, max: budgets.lcp },
    load: { value: nav.loadEventEnd, max: budgets.load },
  };
  for (const [name, { value, max }] of Object.entries(checks)) {
    if (value > max) throw new Error(`${name} ${value}ms 超预算 ${max}ms`);
  }
}
assertBudget({ lcp: 2500, load: 3000 });
```

```text
回归测试的载体：
1. Lighthouse CI —— 每次 PR 跑 LHCI，分数下降即报错
2. 自定义预算脚本 —— 上面 assertBudget，接在 E2E 之后
3. 监控告警 —— 线上指标超阈值自动报警
```

## 建立监控

本地测一次不够，真实用户分布在不同设备与网络，需要在线上持续采集，这就是 RUM（Real User Monitoring）。

```js
// 采集真实用户指标并上报
const observer = new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    navigator.sendBeacon('/api/rum', JSON.stringify({
      name: entry.name,
      value: entry.value,
      startTime: entry.startTime,
    }));
  });
});
observer.observe({ type: 'largest-contentful-paint', buffered: true });
observer.observe({ type: 'layout-shift', buffered: true });
```

```text
监控与本地诊断的分工：
1. 本地诊断 —— 定位「为什么慢」，用 DevTools 深挖
2. 线上监控 —— 回答「谁慢、多慢、何时开始慢」，用 RUM
3. 两者联动 —— 监控告警触发本地复现，形成闭环
```

## 持续治理

性能治理是长期动作，不是一次性运动：预算进 CI、指标上大盘、定期复盘趋势，把性能纳入日常开发流程。

```text
持续治理的四个抓手：
1. 预算进 CI —— 每次合入都跑性能预算，超了不让合并
2. 指标上大盘 —— LCP/INP/CLS 分位数趋势图，盯趋势不看单点
3. 分级告警 —— 告警分级，P0 立即处理，P2 列入迭代
4. 定期复盘 —— 每迭代看一次趋势，把性能项排进需求
```

## 应用场景实战

### 场景一：定位一次首屏白屏慢

```js
// 用户反馈首屏白屏 5 秒，按流程走一遍
// 1. 建立基线
const nav = performance.getEntriesByType('navigation')[0];
console.log('DNS+TCP+请求:', nav.responseStart, 'ms');
console.log('DOM 可交互:', nav.domInteractive, 'ms');

// 2. 定位瓶颈：看关键资源时间线
performance.getEntriesByType('resource')
  .sort((a, b) => a.startTime - b.startTime)
  .forEach(r => console.log(`${r.startTime.toFixed(0)}ms`, r.name, r.initiatorType));

// 3. 提出假设：主 bundle 阻塞 + 首屏图片未压缩
// 4. 实验验证：拆分 vendor、压缩图片后重新测量
// 5. 回归：把 LCP 预算写进 CI
```

### 场景二：监控长任务定位卡顿源头

```js
// 用户反馈点击按钮后页面卡 1 秒
// 用 longtask + 入口归属定位是哪个脚本/框架引起
const observer = new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    const a = entry.attribution?.[0] || {};

  performance.mark('click-handler-end');

  console.log('点击处理耗时:', m.duration, 'ms');
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先量化再优化，没基线别动手，否则不知道有没有效果
2. 定位瓶颈从「加载/交互/内存」三分类入手，先收敛范围再深挖
3. 每次只改一个变量，改完立即测，别攒一堆一起上
4. 把结论固化成性能预算和监控告警，防回退
5. 优先优化收益大的方向：传输大小 > 主线程长任务 > 重排重绘
6. 线上监控与本地诊断联动，监控发现问题，本地定位原因

### 踩坑记录

```text
坑 1：只看 Lighthouse 分数就下结论
结论：Lighthouse 分数高了但用户还是感觉卡。
原因：Lighthouse 用模拟网络/CPU，与真实用户设备差异大。
解法：结合 RUM 真实用户指标（LCP/INP 分位数）一起判断。

坑 2：一次改十处导致无法归因
结论：性能变快了但不知道是哪项优化生效。
原因：控制变量失败，多个改动互相干扰。
解法：一次只改一处，测完再改下一处。

坑 3：用单次测量值当基线
结论：基线值不稳定，优化后对比失真。
原因：网络抖动、CPU 调度导致单次测量误差大。
解法：多次测量取中位数，或固定节流环境测。

坑 4：优化后不做回归测试
结论：三个月后性能回退到优化前。
原因：后续合入的代码无意间破坏了优化。
解法：性能预算写进 CI，超预算直接拦截合并。

坑 5：内存泄漏当渲染问题排查
结论：在 Performance 面板查了半天找不到卡顿原因。
原因：页面卡是内存持续上涨导致 GC 频繁，根因在内存。
解法：先看 Memory 面板堆趋势，区分「渲染慢」和「内存涨」。
```
