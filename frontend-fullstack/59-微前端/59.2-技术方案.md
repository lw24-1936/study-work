## 概述

实现微前端有多种技术方案，从最朴素的 iframe 到运行时编排（single-spa/qiankun）、构建期共享（Module Federation）以及浏览器原生能力（Web Components）。不同方案在隔离性、性能、改造成本上各有取舍。

```text
主流方案概览：
1. iframe —— 浏览器原生隔离，最简单，但体验与通信受限
2. Module Federation —— 构建期共享模块，运行时组合，无隔离
3. single-spa —— 运行时路由编排框架，需自行处理隔离
4. qiankun —— 基于 single-spa，补全了隔离与加载（国内主流）
5. Web Components —— 浏览器原生组件标准，天然封装
6. Runtime Integration —— 运行时动态加载与组合的通用模式
```

```text
方案选型要点：
隔离性：iframe > qiankun > single-spa > Module Federation
体验流畅：Module Federation/single-spa/qiankun > iframe
改造成本：iframe 最低，Module Federation 需改造构建
生态成熟：qiankun 国内最成熟，Module Federation 国际流行
```

## iframe

iframe 是浏览器原生的隔离容器，每个子应用放在独立的 iframe 中，拥有独立的 window、文档和 JS 执行环境，隔离性最强。

```html
<!-- 主应用中嵌入子应用 -->
<iframe src="https://sub.example.com/app" width="100%" height="600"></iframe>
```

```text
iframe 方案的优势：
1. 隔离彻底 —— JS、CSS、DOM 天然隔离，互不污染
2. 实现简单 —— 无需任何框架，原生标签即可
3. 技术栈无关 —— 子应用可以是任意技术
4. 独立加载 —— 子应用独立渲染，互不阻塞

iframe 方案的劣势：
1. 通信繁琐 —— 需要 postMessage，跨域受限
2. 性能开销 —— 每个 iframe 是独立文档，资源重复加载
3. 体验割裂 —— 弹窗、路由、滚动、样式难以统一
4. SEO 差 —— 内容不被主页面直接索引
```

```js
// iframe 通信：postMessage
// 主应用 → 子应用
iframe.contentWindow.postMessage({ type: 'init', data: {} }, 'https://sub.example.com');

// 子应用 → 主应用
window.parent.postMessage({ type: 'ready' }, '*');

// 监听
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://sub.example.com') return;  // 校验来源
  console.log(e.data);
});
```

## Module Federation

Module Federation（模块联邦，MF）是 Webpack 5 提供的构建期能力：让多个独立构建的应用在运行时共享模块，应用 A 可以使用应用 B 暴露的组件，实现「构建期解耦、运行时组合」。

```js
// webpack.config.js —— 远程应用（Remote）暴露组件
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'app_remote',
      filename: 'remoteEntry.js',
      exposes: {
        './Button': './src/Button.vue'
      },
      shared: ['vue']
    })
  ]
};
```

```js
// webpack.config.js —— 主应用（Host）消费远程组件
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'app_host',
      remotes: {
        remote: 'app_remote@http://localhost:3002/remoteEntry.js'
      },
      shared: ['vue']
    })
  ]
};
```

```js
// 主应用运行时加载远程组件
import('remote/Button').then(({ default: Button }) => {
  // 使用远程暴露的 Button 组件
});
```

```text
Module Federation 的特点：
1. 构建期解耦 —— 各应用独立构建，无需同时发布
2. 运行时组合 —— 按需加载远程模块，共享依赖去重
3. 无隔离 —— 共享同一个 JS 运行时，需自行处理样式/全局变量冲突
4. 同技术栈更友好 —— 共享依赖（如 Vue/React）时收益最大
```

## single-spa

single-spa 是一个运行时微前端框架，核心是「路由驱动加载」：根据当前 URL 决定激活哪个子应用，负责子应用的生命周期管理，但不提供样式隔离和 JS 沙箱。

```js
// single-spa 注册子应用
import { registerApplication, start } from 'single-spa';

registerApplication({
  name: 'app-a',
  app: () => System.import('app-a'),     // 动态加载子应用
  activeWhen: (location) => location.pathname.startsWith('/app-a')
});

registerApplication({
  name: 'app-b',
  app: () => System.import('app-b'),
  activeWhen: ['/app-b']
});

start();
```

```text
single-spa 的生命周期：
子应用需要导出三个生命周期函数：
bootstrap —— 初始化（只调用一次）
mount     —— 挂载（激活时调用）
unmount   —— 卸载（离开时调用）

子应用（以 Vue 为例）：
export async function bootstrap() { /* 初始化 */ }
export async function mount(props) { /* 挂载实例 */ }
export async function unmount() { /* 卸载实例 */ }
```

```text
single-spa 的定位：
1. 只做路由编排 + 生命周期管理
2. 不提供样式隔离、JS 沙箱、通信机制
3. 需要配合 systemjs 等模块加载器，或用 import-maps

因此通常在其上再封装一层（如 qiankun）来补全能力。
```

## qiankun

qiankun 是基于 single-spa 的微前端框架，补全了 JS 沙箱、样式隔离、资源预加载、应用通信等能力，是国内使用最广泛的微前端方案。

```js
// 主应用：注册子应用
import { registerMicroApps, start } from 'qiankun';

registerMicroApps([
  {
    name: 'app-a',
    entry: '//localhost:8081',             // 子应用地址
    container: '#subapp-container',        // 挂载容器
    activeRule: '/app-a',                  // 激活路由
    props: { user: { name: 'Alice' } }     // 传递数据
  },
  {
    name: 'app-b',
    entry: '//localhost:8082',
    container: '#subapp-container',
    activeRule: '/app-b'
  }
]);

start();
```

```js
// 子应用：导出生命周期（以 Vue 为例）
let instance = null;

export async function bootstrap() {}
export async function mount(props) {
  instance = new Vue({ render: (h) => h(App) }).$mount('#app');
}
export async function unmount() {
  instance.$destroy();
}
```

```text
qiankun 的核心能力：
1. JS 沙箱 —— Proxy 沙箱隔离各子应用全局变量
2. 样式隔离 —— shadow DOM 或 scoped 前缀方案
3. 资源预加载 —— 提前加载子应用静态资源
4. 应用通信 —— initGlobalState 全局状态通信
5. 加载策略 —— 支持 HTML Entry，直接加载子应用 HTML
```

```js
// qiankun 全局状态通信
import { initGlobalState } from 'qiankun';

const actions = initGlobalState({ user: null });
actions.setGlobalState({ user: { name: 'Alice' } });   // 主应用设置
actions.onGlobalStateChange((state) => {               // 监听变化
  console.log(state);
});
```

## Web Components

Web Components 是浏览器原生组件标准（Custom Elements + Shadow DOM + Templates），提供原生的组件封装与样式隔离，可作为微前端的实现载体。

```js
// 定义自定义元素（子应用以组件形式暴露）
class UserCard extends HTMLElement {
  constructor() {
    super();
    const shadow = this.attachShadow({ mode: 'open' });   // Shadow DOM 隔离
    shadow.innerHTML = `
      <style>p { color: red; }</style>
      <p>用户：<slot name="name"></slot></p>
    `;
  }
}
customElements.define('user-card', UserCard);
```

```html
<!-- 主应用中使用 -->
<user-card><span slot="name">Alice</span></user-card>
```

```text
Web Components 做微前端的优劣：
优势：
1. 浏览器原生，无需框架依赖
2. Shadow DOM 天然隔离样式与 DOM
3. 技术栈完全无关，任意框架可产出
4. 生命周期清晰（connectedCallback 等）

劣势：
1. 缺少路由编排、应用间通信等上层能力
2. SSR 支持弱，SEO 需要额外方案
3. 大型应用的工程化（构建、拆包）需自行设计
```

## Runtime Integration

Runtime Integration（运行时集成）是微前端最通用的模式：主应用在运行时动态加载子应用的资源（JS/CSS），子应用向主应用暴露挂载/卸载接口，主应用负责编排生命周期。

```text
运行时集成的一般流程：
1. 主应用启动，加载子应用资源清单（manifest）
2. 路由变化 → 主应用动态加载对应子应用的 JS/CSS
3. 调用子应用暴露的 mount(container, props)
4. 路由离开 → 调用 unmount()，清理 DOM 与副作用
```

```js
// 主应用：通用的运行时加载器
async function loadMicroApp(url) {
  await loadScript(url);                 // 动态加载子应用 JS
  return window.__MICRO_APP__;           // 子应用挂载到全局的接口
}

// 子应用暴露统一的挂载接口
window.__MICRO_APP__ = {
  mount: (container, props) => { /* 渲染 */ },
  unmount: () => { /* 清理 */ }
};
```

```text
运行时集成 vs 构建期集成：
运行时集成：子应用独立构建成 bundle，运行时动态加载
  → 优势：真正独立部署，主应用无需重新构建
  → 劣势：需要约定接口规范，处理资源冲突

构建期集成（如 Module Federation）：
  → 优势：共享依赖去重，同栈体验好
  → 劣势：耦合构建产物，需协调版本
```

## 应用场景实战

### 场景一：Vue 生态的中后台微前端

```text
需求：多个 Vue 后台系统整合，需要样式隔离与状态通信。
方案：qiankun（生态成熟，开箱即用）。

主应用：注册各子应用，统一菜单导航与登录态
子应用：按 qiankun 规范导出 bootstrap/mount/unmount
通信：initGlobalState 共享登录用户信息
隔离：JS 沙箱 + 样式隔离，避免全局污染
```

### 场景二：跨技术栈的组件共享

```text
需求：React 团队与 Vue 团队需要共享一批业务组件。
方案：Module Federation。

各团队独立构建，通过 shared 共享 react/vue 依赖，
通过 exposes 暴露组件，主应用 remotes 消费。

收益：无需发布到 npm，运行时直接共享最新组件。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 同技术栈且需深度共享组件 → Module Federation
2. Vue 中后台、需要完整隔离与生态 → qiankun
3. 简单隔离、快速整合、容忍体验割裂 → iframe
4. 仅需组件封装复用 → Web Components
5. 无论哪种方案，先约定清晰的接口契约

### 踩坑记录

```text
坑 1：qiankun 子应用资源加载 404
结论：子应用加载后资源路径错误。
原因：子应用静态资源使用了绝对路径 /，与主应用域名不符。
解法：子应用配置 publicPath 为相对路径或完整 CDN 地址。

坑 2：Module Federation 共享依赖版本冲突
结论：加载共享模块时报版本不兼容错误。
原因：shared 依赖版本不一致，或 singleton 配置不当。
解法：shared 中设置 singleton: true，并统一依赖版本。

坑 3：iframe 跨域通信失败
结论：postMessage 收不到消息或数据异常。
原因：未校验 origin，或目标地址跨域不匹配。
解法：postMessage 指定精确 targetOrigin，监听时校验 event.origin。

坑 4：single-spa 未处理样式隔离导致污染
结论：子应用样式影响主应用或其他子应用。
原因：single-spa 本身不提供样式隔离。
解法：子应用使用 scoped CSS/CSS Modules，或换用 qiankun。

坑 5：Web Components 组件 SSR 渲染空白
结论：服务端渲染时自定义元素不显示。
原因：Web Components 依赖客户端 JS 定义，SSR 阶段未注册。
解法：用 Declarative Shadow DOM 或客户端挂载，或放弃 SSR。
```
