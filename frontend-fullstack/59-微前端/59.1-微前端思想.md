## 概述

微前端（Micro Frontend）把「微服务」的思想搬到前端：将一个大型前端应用拆分为多个可独立开发、独立部署、独立运行的小应用，再在运行时或构建时组合成一个整体。

```text
微前端要解决的问题：
1. 巨石应用 —— 单体前端代码量膨胀，构建慢、协作难
2. 技术栈锁定 —— 所有团队被迫使用同一技术栈与版本
3. 发布耦合 —— 改一行代码要全量回归、全量发布
4. 团队协作 —— 多团队在同一仓库互相影响

微前端的价值：
1. 独立开发 —— 各团队互不阻塞
2. 独立部署 —— 各自发布，互不影响
3. 技术栈自由 —— 各子应用可选用不同框架
4. 渐进式演进 —— 老系统逐步替换
```

```text
微前端 vs 微服务的类比：
微服务：把后端按业务拆成独立服务，独立部署、独立扩缩容。
微前端：把前端按业务拆成独立应用，独立开发、独立部署。

两者都强调：领域边界清晰 + 团队自治 + 独立交付。
```

## Micro Frontend

Micro Frontend（微前端）是一种架构风格：由多个独立交付的前端应用组成一个整体产品。它借鉴微服务的设计原则，把「拆分」延伸到 UI 层。

```text
微前端的核心概念：
1. 主应用（Host/Shell）—— 负责加载、编排子应用，提供外壳
2. 子应用（Micro App/Remote）—— 独立的业务应用
3. 组合方式 —— 运行时组合 或 构建期组合
4. 边界 —— 每个子应用有清晰的业务与路由边界
```

```text
微前端的典型形态：
┌─────────────────────────────┐
│  主应用（Shell：导航、鉴权、布局）  │
├──────┬──────┬──────┬────────┤
│ 子应用A │ 子应用B │ 子应用C │ 子应用D  │
│ 商品    │ 购物车  │ 订单   │ 用户中心 │
└──────┴──────┴──────┴────────┘
```

```text
关键原则：
1. 每个子应用是「自治」的，拥有自己的代码、构建、发布流程
2. 子应用之间通过约定的接口（props、事件、全局状态）通信
3. 主应用保持「薄」，只做编排，不承载业务
4. 共享基础设施（鉴权、日志、监控）而非共享业务代码
```

## Independent Deployment

Independent Deployment（独立部署）是微前端最核心的价值：每个子应用可以独立构建、独立测试、独立发布，不依赖其他应用的发布节奏。

```text
独立部署带来的收益：
1. 发布解耦 —— A 团队发版不影响 B 团队
2. 快速迭代 —— 小改动小发布，无需全量回归
3. 降低风险 —— 故障影响范围被限制在单个子应用
4. 独立回滚 —— 某个子应用出问题可单独回滚
```

```text
实现独立部署的要点：
1. 每个子应用有独立的仓库、独立的 CI/CD 流水线
2. 子应用产物发布到独立的地址（CDN 路径 / 独立域名）
3. 主应用按需加载子应用的最新资源
4. 版本管理 —— 子应用可独立版本号，主应用引用对应版本

流程示例：
子应用构建 → 产物上传 CDN → 更新资源清单（manifest）
主应用启动 → 读取清单 → 按需加载对应子应用版本
```

```text
独立部署的挑战：
1. 版本一致性 —— 多子应用并存时如何保证兼容
2. 依赖共享 —— 如何避免重复加载相同依赖
3. 灰度发布 —— 如何按用户/流量逐步放量
```

## Team Autonomy

Team Autonomy（团队自治）指每个业务团队对自己的子应用拥有完全自主权：技术选型、代码规范、发布节奏都由团队自己决定。

```text
团队自治的体现：
1. 技术栈自由 —— A 团队用 Vue，B 团队用 React
2. 版本自由 —— 各自选择框架版本与依赖版本
3. 规范自治 —— 在团队内制定自己的代码规范
4. 节奏自治 —— 按自己的节奏迭代与发布
```

```text
自治与统一的平衡：
完全自治的代价：
1. 技术栈碎片化，招聘与维护成本高
2. 用户体验不一致（样式、交互不统一）
3. 重复造轮子，公共能力重复建设

平衡之道：
1. 约定最小公共契约（通信协议、路由规则、鉴权方式）
2. 提供共享基础设施（组件库、工具链、脚手架）
3. 业务代码自治，基础设施统一
```

```text
团队自治的前提：
1. 清晰的领域边界 —— 职责不重叠，减少跨团队协调
2. 稳定的接口契约 —— 子应用间通信接口向后兼容
3. 成熟的工程能力 —— 团队能独立承担完整交付
```

## Domain Decomposition

Domain Decomposition（领域分解）是微前端拆分的依据：按照业务领域（而非技术层）划分子应用边界，遵循 DDD（领域驱动设计）思想。

```text
正确拆分 vs 错误拆分：
错误（按技术层拆）：
前端 A = 所有列表页，前端 B = 所有表单页
→ 一个业务改动要跨多个子应用，反而增加协调成本

正确（按业务域拆）：
商品域、订单域、用户域、营销域
→ 一个业务域内的改动只需改一个子应用
```

```text
领域分解的原则：
1. 高内聚 —— 一个领域内的功能放在一起
2. 低耦合 —— 领域之间依赖最小化
3. 边界清晰 —— 每个领域有明确的职责范围
4. 对齐组织 —— 拆分边界与团队组织结构对齐（康威定律）

康威定律：
系统设计会复制组织的沟通结构。
所以先想清楚团队怎么分，再决定前端怎么拆。
```

```text
电商领域的分解示例：
商品域 —— 商品列表、详情、搜索
交易域 —— 购物车、下单、支付
用户域 —— 登录、注册、个人中心、会员
营销域 —— 优惠券、活动页、推荐
售后域 —— 订单售后、评价
```

```text
分解的边界信号（什么时候该拆/该合）：
1. 两个功能频繁一起改动 → 可能该合并
2. 一个子应用内多个团队频繁冲突 → 可能该拆分
3. 跨子应用改动需要大量协调 → 边界划分不合理
```

## 应用场景实战

### 场景一：大型电商平台改造

```text
背景：单体 React 应用，多团队协作，发布互相阻塞。
方案：按业务域拆分为商品、交易、用户等子应用。

落地要点：
1. 主应用负责导航、鉴权、全局布局
2. 各子应用独立仓库、独立发布
3. 商品团队、交易团队各自自治
4. 统一鉴权与通信协议

收益：各团队独立发布，故障隔离，迭代提速。
```

### 场景二：多后台系统整合

```text
背景：公司内部多个独立后台系统，希望统一入口、统一体验。
方案：微前端聚合，主应用做统一壳。

落地要点：
1. 各后台作为子应用接入主应用导航
2. 统一登录态（SSO），子应用共享鉴权
3. 统一菜单、主题、权限模型
4. 各后台仍独立维护、独立部署
```

## 最佳实践与踩坑记录

### 最佳实践

1. 按业务领域拆分，而非按技术层拆分
2. 主应用保持轻薄，只做编排不做业务
3. 明确子应用间的通信契约与路由边界
4. 共享基础设施，避免重复建设公共能力
5. 拆分前先评估是否真的需要微前端（小团队慎用）

### 踩坑记录

```text
坑 1：为了微前端而微前端
结论：小团队引入微前端后复杂度不降反升。
原因：微前端有额外的编排、通信、隔离成本。
解法：团队小、耦合可控时优先单体；确有独立部署需求再拆分。

坑 2：按技术层拆分导致频繁跨应用改动
结论：一个业务功能要改多个子应用。
原因：拆分边界没有对齐业务领域。
解法：以领域为边界拆分，保证高内聚低耦合。

坑 3：完全技术栈自由导致体验割裂
结论：不同子应用样式、交互差异巨大。
原因：自治过度，缺少统一设计规范与公共组件。
解法：统一设计系统与基础组件库，业务层保持自治。

坑 4：子应用边界重叠、职责不清
结论：同一功能两个团队都在做，互相推诿。
原因：领域边界划分模糊，缺少明确的所有权。
解法：建立应用职责清单，明确每个子应用的 owner。

坑 5：忽视兼容性导致频繁故障
结论：主应用升级后子应用集体异常。
原因：子应用间接口契约不稳定，缺少向后兼容。
解法：通信接口版本化、向后兼容，主应用升级前做兼容性回归。
```
