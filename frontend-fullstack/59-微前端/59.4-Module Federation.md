## 概述

Module Federation（模块联邦，MF）是 Webpack 5 引入的架构能力：让多个相互独立构建的应用，在运行时像使用本地模块一样共享彼此的模块。它把「代码共享」从构建期 npm 依赖提升到「运行时动态消费」，是微前端的重要实现方案。

```text
Module Federation 的核心概念：
1. Host —— 消费远程模块的应用（宿主）
2. Remote —— 暴露模块供他人使用的应用（远程）
3. Exposes —— Remote 声明「对外暴露哪些模块」
4. Remotes —— Host 声明「消费哪些远程模块」
5. Shared —— 声明共享的依赖，运行时去重
6. Runtime Loading —— 运行时动态加载远程模块
```

```text
Module Federation 解决的问题：
传统共享组件 → 发布 npm 包 → 各应用安装 → 版本升级要全部重装重发
模块联邦 → Remote 构建时暴露 → Host 运行时直接加载最新代码

价值：
1. 免 npm 发布的即时共享
2. 各应用独立构建、独立部署
3. 共享依赖去重，避免重复打包
```

## Host

Host（宿主应用）是消费远程模块的一方，在 `remotes` 中声明要加载的远程应用，并负责在运行时发起对远程模块的请求。

```js
// webpack.config.js —— Host 配置
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host_app',
      filename: 'remoteEntry.js',        // Host 自身也可被他人消费时提供
      remotes: {
        // 别名：远程名@远程入口地址
        remoteA: 'remote_a@http://localhost:3001/remoteEntry.js'
      },
      shared: {
        react: { singleton: true },
        'react-dom': { singleton: true }
      }
    })
  ]
};
```

```js
// Host 运行时消费远程模块
import React, { Suspense, lazy } from 'react';

// 动态加载远程暴露的组件
const RemoteButton = lazy(() => import('remoteA/Button'));

function App() {
  return (
    <Suspense fallback={<div>加载中...</div>}>
      <RemoteButton text="来自远程" />
    </Suspense>
  );
}
```

```text
Host 的职责：
1. 声明 remotes 列表及其入口地址
2. 在运行时按需加载远程模块
3. 声明 shared 依赖，与远程应用共享
4. 处理加载失败、降级等容错
```

## Remote

Remote（远程应用）是暴露模块的一方，在 `exposes` 中声明对外开放的模块，并生成 `remoteEntry.js` 作为远程入口文件供 Host 加载。

```js
// webpack.config.js —— Remote 配置
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  devServer: { port: 3001 },
  plugins: [
    new ModuleFederationPlugin({
      name: 'remote_a',                     // 唯一名称，Host 引用它
      filename: 'remoteEntry.js',           // 远程入口文件
      exposes: {
        './Button': './src/components/Button'
      },
      shared: {
        react: { singleton: true },
        'react-dom': { singleton: true }
      }
    })
  ]
};
```

```text
Remote 的职责：
1. 声明 exposes，决定暴露哪些模块
2. 生成 remoteEntry.js（远程模块清单 + 引导代码）
3. 声明 shared，与 Host 共享依赖
4. 独立构建、独立部署到自己的地址

Remote 本身也可以是 Host（双向消费），
一个应用可以同时 exposes 和 remotes。
```

## Exposes

Exposes 是 Remote 对外的「模块清单」，声明哪些本地模块可以被其他应用加载。它相当于「导出的 API 面」。

```js
// Remote 的 exposes 配置
new ModuleFederationPlugin({
  name: 'remote_a',
  exposes: {
    './Button': './src/components/Button',
    './Header': './src/components/Header',
    './utils': './src/utils/index'
  }
});
```

```text
exposes 的要点：
1. 键是「对外模块名」（Host 用 remote_a/Button 引用）
2. 值是「本地文件路径」
3. 暴露的可以是组件、函数、工具、整个页面
4. 建议只暴露稳定的公共接口，内部实现不要暴露
```

```js
// 暴露一个带多个导出的模块
// src/components/index.js
export { default as Button } from './Button';
export { default as Card } from './Card';

// exposes
exposes: {
  './components': './src/components/index'
}

// Host 消费
import { Button, Card } from 'remote_a/components';
```

```text
设计 exposed API 的原则：
1. 只暴露「对外契约」，避免暴露内部细节
2. 暴露的模块要保持向后兼容
3. 暴露面越小，维护成本越低
4. 用文档明确每个暴露模块的用法与版本
```

## Remotes

Remotes 是 Host 对外的「依赖声明」，声明要消费哪些远程应用以及它们的入口地址。

```js
// Host 的 remotes 配置
new ModuleFederationPlugin({
  name: 'host_app',
  remotes: {
    remoteA: 'remote_a@http://localhost:3001/remoteEntry.js',
    remoteB: 'remote_b@http://localhost:3002/remoteEntry.js',
    // 支持动态配置地址（运行时决定）
    remoteC: 'remote_c@[remoteCUrl]/remoteEntry.js'
  }
});
```

```text
remotes 的格式：
别名: '远程名@入口地址'

别名 —— Host 内 import 时使用的名字（import 'remoteA/Button'）
远程名 —— 对应 Remote 的 name 配置
入口地址 —— remoteEntry.js 的完整 URL
```

```js
// 运行时动态指定远程地址
// 通过 external 方式或 __webpack_init_sharing__ 动态注入
function loadRemote(url, scope, module) {
  return new Promise((resolve, reject) => {
    const script = document.createElement('script');
    script.src = url;
    script.onload = () => {
      const container = window[scope];
      container.init(__webpack_share_scopes__.default);
      container.get(module).then((factory) => {
        resolve(factory());
      });
    };
    script.onerror = reject;
    document.head.appendChild(script);
  });
}

// 使用
loadRemote('http://localhost:3001/remoteEntry.js', 'remote_a', './Button')
  .then((m) => console.log(m.default));
```

```text
动态 remotes 的价值：
1. 地址不必硬编码在构建配置里
2. 可配合 manifest 实现「不重新构建就切换远程版本」
3. 支持灰度、A/B 测试、环境切换
```

## Shared

Shared 声明多个应用之间「共享」的依赖库。运行时，这些依赖只会加载一份（在满足版本要求的前提下），避免重复打包与多实例冲突。

```js
// shared 配置
new ModuleFederationPlugin({
  shared: {
    react: { singleton: true, requiredVersion: '^18.0.0' },
    'react-dom': { singleton: true, requiredVersion: '^18.0.0' },
    lodash: { singleton: false }        // 允许加载多份
  }
});
```

```text
shared 的关键参数：
singleton: true      —— 全局只允许一个实例（框架类库必须设置）
requiredVersion      —— 版本要求，不满足则各自加载
eager: true          —— 立即加载共享模块，而非按需
strictVersion        —— 严格版本匹配
version              —— 明确声明的版本
```

```text
为什么要 singleton？
Vue/React 这类框架若加载两份实例：
1. 体积翻倍，浪费带宽
2. 跨应用的 Context/事件系统不互通
3. Hooks/插件注册错乱，运行时报错

所以框架类依赖必须 singleton: true，
普通工具库（lodash 等）可不强制单例。
```

## Runtime Loading

Runtime Loading（运行时加载）是模块联邦区别于传统 npm 共享的核心：模块不是构建时打包进产物，而是在浏览器运行时按需从远程地址加载。

```text
运行时加载的流程：
1. Host 启动，初始化 shared scope（共享依赖注册表）
2. 代码执行到 import('remoteA/Button')
3. 浏览器动态加载 remoteA 的 remoteEntry.js
4. remoteEntry 初始化远程容器，注册 shared
5. 远程容器按需加载 ./Button 的实际 chunk
6. 返回模块，Host 使用
```

```text
运行时加载的特征：
1. 按需 —— 只有用到时才加载对应 chunk
2. 独立 —— 远程模块独立部署，Host 无需重新构建
3. 共享 —— 依赖在 shared scope 中协商复用
4. 异步 —— import() 返回 Promise，天然支持懒加载
```

```js
// 运行时加载配合 React.lazy / Suspense
const RemotePage = lazy(() => import('remoteA/Page'));

<Suspense fallback={<Loading />}>
  <RemotePage />
</Suspense>;
```

```text
运行时加载的注意点：
1. 远程入口地址要可访问（CORS 正确配置）
2. 网络失败要有降级方案
3. shared 版本协商发生在运行时，需提前约定
4. 远程模块变更后，Host 需刷新缓存才能获取新版本
```

## Version Conflict

Version Conflict（版本冲突）是模块联邦最棘手的问题：当 Host 与 Remote 声明的共享依赖版本不一致时，如何决定加载哪一份。

```text
冲突场景：
Host 用 react 18，Remote 用 react 17，都声明 singleton。
此时只能加载一份，需要协商：
1. 版本满足 requiredVersion 范围 → 复用现有实例
2. 版本不满足 → 回退为各自加载（破坏 singleton）
3. 强制指定 → 按配置的版本加载，可能不兼容
```

```js
// 处理版本冲突的配置
shared: {
  react: {
    singleton: true,
    requiredVersion: '^18.0.0',     // 声明要求
    strictVersion: false            // 非严格：18.x 内都接受
  }
}
```

```text
版本冲突的解决策略：
1. 统一版本 —— 团队协商，锁定公共依赖主版本（最稳妥）
2. 宽松范围 —— requiredVersion 用兼容范围而非精确版本
3. 隔离运行 —— 冲突模块不共享，各自打包（牺牲去重）
4. 版本策略 —— 依赖统一升级节奏，避免长期分叉

实用建议：
框架类（react/vue）保持主版本一致；
工具库用宽松范围 + singleton: false。
```

```text
版本管理的长期之道：
1. 建立公共依赖清单，团队共同维护版本
2. 依赖升级时所有应用协同（但可分批发布）
3. 用 requiredVersion 声明边界，冲突时构建期/运行时可见
4. 监控 shared scope 的实际版本，及时发现问题
```

## 应用场景实战

### 场景一：跨团队共享业务组件

```text
需求：商品组件由商品团队维护，多个团队（首页、搜索、详情）都要使用。
方案：商品团队构建为 Remote，其他应用为 Host。

商品团队（Remote）：
exposes: { './ProductCard': './src/ProductCard' }

首页团队（Host）：
remotes: { product: 'product@https://cdn/product/remoteEntry.js' }
import('product/ProductCard').then(...)

收益：商品团队改组件即时生效，其他团队无需重新发布。
```

### 场景二：统一框架依赖 + 动态远程

```text
需求：多应用都依赖 React，要避免多实例；且远程地址需动态配置。
方案：singleton 共享 + 动态 remotes。

1. shared 中 react/react-dom 设 singleton: true
2. remote 地址不写死在构建配置，运行时从 manifest 读取
3. 用 loadRemote 动态加载远程模块
4. 灰度时切换 manifest 中的远程地址即可
```

## 最佳实践与踩坑记录

### 最佳实践

1. 框架类依赖（react/vue）必须 singleton: true
2. 只暴露稳定的公共契约，不暴露内部实现
3. 远程地址用动态配置（manifest），便于独立部署与回滚
4. 远程模块加载失败要有降级与错误提示
5. 建立公共依赖清单，尽量统一主版本

### 踩坑记录

```text
坑 1：多实例 Vue/React 导致运行时报错
结论：共享组件不生效，hooks 报错或 Context 丢失。
原因：shared 未设 singleton，加载了多个框架实例。
解法：框架依赖设 singleton: true，并统一版本。

坑 2：远程模块 404 或 CORS 错误
结论：加载远程模块时报跨域或找不到文件。
原因：远程地址错误，或服务端未配置 CORS。
解法：校验 remoteEntry.js 地址，服务端加 Access-Control-Allow-Origin。

坑 3：版本不满足导致依赖重复加载
结论：shared 未去重，产物体积异常大。
原因：requiredVersion 范围不匹配，回退为各自加载。
解法：统一公共依赖版本，或放宽 requiredVersion 范围。

坑 4：修改远程模块后 Host 未更新
结论：远程组件改了，Host 仍显示旧代码。
原因：浏览器或 CDN 缓存了旧的 remoteEntry.js / chunk。
解法：远程入口加版本号/哈希，配置合理的缓存策略。

坑 5：shared 初始化顺序错误
结论：动态加载远程时报 __webpack_share_scopes__ undefined。
原因：容器未正确 init 共享作用域。
解法：动态加载时先调用 container.init(shareScope)，或使用框架封装。
```
