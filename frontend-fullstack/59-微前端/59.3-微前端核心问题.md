## 概述

微前端在带来独立部署、团队自治的同时，也引入了一系列必须解决的核心问题：应用如何加载、路由如何协调、依赖如何共享、样式与 JS 如何隔离、应用间如何通信、鉴权如何统一、部署如何管理、如何监控运行状态。

```text
微前端九大核心问题：
1. Application Loading —— 子应用如何被加载与卸载
2. Routing —— 主应用与子应用的路由如何协调
3. Shared Dependencies —— 公共依赖如何共享去重
4. CSS Isolation —— 子应用样式如何互不污染
5. JS Isolation —— 全局变量/运行时如何隔离
6. Communication —— 子应用之间如何通信
7. Authentication —— 登录态如何统一管理
8. Deployment —— 多应用如何独立部署与版本管理
9. Monitoring —— 如何监控各子应用的运行状态
```

## Application Loading

Application Loading（应用加载）指主应用如何获取、启动、挂载和卸载子应用。这是微前端的入口问题。

```text
加载方式：
1. JS Entry —— 加载子应用的 JS bundle，调用其暴露的挂载接口
   （需要子应用配合导出 mount/unmount，如 single-spa/qiankun）
2. HTML Entry —— 加载子应用的完整 HTML，解析其中的 JS/CSS
   （qiankun 默认方式，子应用无需额外改造构建）
3. 模块联邦 —— 加载 remoteEntry.js，消费其 exposes 的模块
```

```js
// JS Entry：主应用动态加载并调用挂载接口
async function loadApp(url, container) {
  await loadScript(url);                          // 加载子应用 JS
  const app = window.__APP__;                     // 子应用导出的接口
  app.mount(container, { user: currentUser });    // 挂载
  return app;
}

function unloadApp(app) {
  app.unmount();                                  // 卸载并清理
}
```

```text
加载过程中的关键点：
1. 资源加载 —— 动态注入 script/link，注意路径与缓存
2. 预加载 —— 空闲时预取子应用资源，切换更流畅
3. 容错 —— 加载失败时降级提示或重试
4. 卸载清理 —— 移除 DOM、解绑事件、清理定时器，防止内存泄漏
```

## Routing

Routing（路由）是微前端的协调中枢：主应用拥有全局路由表，根据 URL 决定激活哪个子应用；子应用内部再有自己的路由。

```text
路由分层：
主应用路由 —— 决定「哪个子应用」激活（一级路由）
子应用路由 —— 子应用内部页面（二级及以下路由）

例如：
/app-a/*   → 子应用 A（内部再分 /app-a/list、/app-a/detail）
/app-b/*   → 子应用 B
```

```js
// 主应用：按前缀匹配激活子应用（qiankun 的 activeRule）
registerMicroApps([
  { name: 'app-a', activeRule: '/app-a', entry: '//localhost:8081' },
  { name: 'app-b', activeRule: '/app-b', entry: '//localhost:8082' }
]);
```

```text
路由协调的注意事项：
1. 子应用路由 base 要与其挂载前缀一致（如 history base 设为 /app-a）
2. 主应用与子应用都使用 history 模式时，需注意 URL 不冲突
3. 子应用跳转跨应用路由时，需通过主应用的路由器跳转
4. 刷新页面时，服务端需正确回退到主应用入口
```

```js
// 子应用（Vue Router）设置 base 前缀
const router = createRouter({
  history: createWebHistory('/app-a'),   // 与主应用 activeRule 一致
  routes: [
    { path: '/list', component: List },
    { path: '/detail/:id', component: Detail }
  ]
});
```

## Shared Dependencies

Shared Dependencies（共享依赖）指多个子应用都使用的公共库（如 Vue、React、lodash）。不共享会导致重复加载；共享不当则引发版本冲突。

```text
共享依赖的策略：
1. 不共享 —— 每个子应用打包自己的依赖（体积大，但隔离彻底）
2. externals —— 公共库从 CDN 全局加载，子应用不打包
   （如 Vue/React 走 window.Vue，需版本统一）
3. 模块联邦 shared —— 构建时声明共享，运行时复用同一实例
4. 主应用注入 —— 主应用加载公共库，通过 props 传给子应用
```

```js
// webpack externals：依赖从全局获取
module.exports = {
  externals: {
    vue: 'Vue',
    'vue-router': 'VueRouter'
  }
};
```

```js
// Module Federation shared：共享并去重
new ModuleFederationPlugin({
  shared: {
    vue: { singleton: true, requiredVersion: '^3.0.0' },
    'vue-router': { singleton: true }
  }
});
```

```text
版本冲突的处理：
1. singleton —— 强制只保留一份实例，避免多个 Vue 实例冲突
2. requiredVersion —— 声明版本要求，不满足则加载多份
3. 版本统一 —— 团队协商锁定公共依赖的主版本
```

## CSS Isolation

CSS Isolation（样式隔离）确保子应用的样式不会污染主应用或其他子应用，也不会被外部样式影响。

```text
样式隔离方案：
1. Shadow DOM —— 浏览器原生隔离（qiankun 可选，Web Components 默认）
2. Scoped CSS —— Vue scoped / CSS Modules，样式带唯一哈希前缀
3. 前缀命名 —— 约定 BEM 等命名规范，人为隔离
4. 运行时改写 —— qiankun 在加载时给样式选择器加前缀
```

```vue
<!-- Vue scoped：编译后选择器带 data-v-xxx 属性，天然隔离 -->
<style scoped>
.title { color: red; }
</style>
```

```css
/* CSS Modules：类名被哈希化，避免冲突 */
/* style.module.css */
.card { padding: 16px; }
```

```text
隔离方案的权衡：
Shadow DOM：隔离最彻底，但影响全局样式、弹窗、UI 库兼容
Scoped/CSS Modules：构建期隔离，兼容性好，是主流选择
前缀命名：最简单，但依赖团队纪律，容易漏
运行时改写：无需改造子应用，但性能有开销、可能误伤
```

## JS Isolation

JS Isolation（JS 隔离）确保子应用的全局变量、事件监听、定时器等不会污染主应用或其他子应用。

```text
JS 隔离方案：
1. iframe —— 独立 window，隔离最彻底
2. Proxy 沙箱 —— qiankun 用 Proxy 拦截 window 读写，各子应用
   有独立的全局变量快照，卸载时还原
3. 快照沙箱 —— 记录全局变量，卸载后恢复原状
4. 约定 —— 子应用不污染全局，卸载时自行清理（single-spa 需手动）
```

```js
// qiankun Proxy 沙箱的示意原理
class ProxySandbox {
  constructor() {
    this.modifiedProps = new Map();
    const fakeWindow = new Proxy(window, {
      set: (target, key, value) => {
        this.modifiedProps.set(key, value);   // 记录修改
        return true;
      },
      get: (target, key) => {
        if (this.modifiedProps.has(key)) return this.modifiedProps.get(key);
        return target[key];
      }
    });
    this.proxy = fakeWindow;
  }
}
```

```text
JS 隔离要清理的副作用：
1. 全局变量污染（window.xxx）
2. 事件监听（addEventListener 未移除）
3. 定时器（setInterval/setTimeout 未清理）
4. 全局 CSS（动态插入的 style 标签）
卸载子应用时必须清理这些，否则内存泄漏或行为错乱。
```

## Communication

Communication（通信）指主应用与子应用之间、子应用与子应用之间的数据传递。

```text
通信方式：
1. Props —— 主应用 mount 时传参给子应用（单向）
2. 全局状态 —— qiankun 的 initGlobalState
3. 自定义事件 —— CustomEvent / 事件总线
4. URL/query —— 通过路由参数传递
5. localStorage/Storage —— 简单共享数据
6. postMessage —— 跨 iframe/跨窗口通信
```

```js
// 自定义事件总线
const bus = new EventTarget();
// 应用 A 发送
bus.dispatchEvent(new CustomEvent('cart-updated', { detail: { count: 3 } }));
// 应用 B 监听
bus.addEventListener('cart-updated', (e) => console.log(e.detail.count));
```

```js
// qiankun 全局状态
const actions = initGlobalState({ cartCount: 0 });
actions.setGlobalState({ cartCount: 1 });         // 主应用/子应用均可设置
actions.onGlobalStateChange((state) => {           // 任意应用监听
  console.log('购物车数量', state.cartCount);
});
```

```text
通信设计原则：
1. 优先用 props 单向传数据，减少耦合
2. 全局状态只放「跨应用共享」的数据，避免滥用
3. 事件通信要定义清晰的事件名与数据结构
4. 避免子应用间直接强耦合，尽量通过主应用中转
```

## Authentication

Authentication（鉴权）在微前端中需要统一：用户登录一次，所有子应用共享登录态。

```text
鉴权统一方案：
1. 主应用负责登录 —— 登录页放主应用，登录后共享 token
2. 共享 token —— token 存 localStorage/Cookie，子应用读取
3. 通过 props 传递 —— 主应用 mount 子应用时传入用户信息
4. SSO —— 统一登录中心，各应用跳转登录中心认证
```

```js
// 主应用登录后，通过 props 传给子应用
registerMicroApps([
  {
    name: 'app-a',
    activeRule: '/app-a',
    entry: '//localhost:8081',
    props: { token: getToken(), user: getUser() }
  }
]);
```

```text
鉴权注意事项：
1. token 统一存储位置（localStorage 或 HttpOnly Cookie）
2. 子应用接口请求统一携带 token（拦截器配置）
3. token 过期后的统一处理（跳登录页/静默刷新）
4. 权限（菜单、按钮级）由主应用统一下发
```

## Deployment

Deployment（部署）是微前端的核心诉求：每个子应用独立构建、独立发布，互不阻塞。

```text
部署策略：
1. 独立域名/路径 —— 每个子应用部署到独立地址
2. 独立 CDN —— 子应用产物上传各自 CDN 路径
3. 资源清单 —— 主应用通过 manifest 获取子应用最新地址
4. 灰度发布 —— 按用户/流量逐步切换子应用版本
```

```text
部署流程示例：
1. 子应用提交代码 → CI 构建 → 产物上传 CDN（带版本哈希）
2. 更新资源清单（manifest.json），记录最新子应用地址
3. 主应用启动时读取 manifest，加载对应版本
4. 回滚 = 把 manifest 指回上一个版本

优势：
主应用无需重新构建即可感知子应用更新；
子应用可独立灰度、独立回滚。
```

```js
// 主应用通过 manifest 加载子应用（而非硬编码地址）
async function loadApps() {
  const manifest = await fetch('/manifest.json').then(r => r.json());
  // manifest: { "app-a": "https://cdn.example.com/app-a/1.2.0/index.js" }
  registerMicroApps(Object.entries(manifest).map(([name, entry]) => ({
    name, entry, activeRule: `/${name}`
  })));
}
```

## Monitoring

Monitoring（监控）在微前端中需要区分「哪个子应用」出了问题，并具备统一的错误采集、性能监控与告警能力。

```text
监控维度：
1. 错误监控 —— 子应用 JS 错误、资源加载失败、接口异常
2. 性能监控 —— 各子应用加载耗时、渲染耗时
3. 可用性 —— 子应用加载成功率、接口成功率
4. 版本追踪 —— 当前运行的子应用版本，便于定位
```

```js
// 全局错误监听（主应用统一采集，标注子应用信息）
window.addEventListener('error', (e) => {
  reportError({
    type: 'js-error',
    subApp: currentAppName,          // 当前激活的子应用
    message: e.message,
    filename: e.filename
  });
});

window.addEventListener('unhandledrejection', (e) => {
  reportError({ type: 'promise-error', subApp: currentAppName, reason: e.reason });
});
```

```text
监控的关键点：
1. 错误信息要带上子应用标识，避免定位困难
2. 主应用统一采集，子应用接入统一 SDK 上报
3. 记录子应用加载失败、超时等异常
4. 监控数据打上版本号，关联发布记录
```

## 应用场景实战

### 场景一：统一登录态 + 共享购物车

```text
需求：电商平台，多个子应用需共享登录态与购物车数量。
方案：主应用统一鉴权，全局状态共享购物车。

1. 主应用负责登录，token 存 localStorage
2. mount 子应用时通过 props 传入 token 和 user
3. 购物车数量用全局状态（initGlobalState）共享
4. 任一子应用修改购物车，其他子应用实时更新角标
```

### 场景二：多子应用独立发布 + 监控

```text
需求：三个团队独立迭代，需要独立发布和统一监控。
方案：manifest 加载 + 统一监控。

1. 各子应用独立构建，上传 CDN，更新 manifest
2. 主应用读 manifest 动态加载，无需重新构建
3. 统一监控 SDK 采集错误/性能，带上子应用标识
4. 发布后按版本号关联监控，异常可快速回滚
```

## 最佳实践与踩坑记录

### 最佳实践

1. 路由前缀明确划分，主应用与子应用 base 一致
2. 公共依赖统一版本，用 singleton 或 externals 去重
3. 样式用 Scoped/CSS Modules，JS 副作用卸载时清理
4. 通信优先 props 与全局状态，事件名约定清晰
5. 鉴权主应用统一，token 与用户信息通过 props 下发

### 踩坑记录

```text
坑 1：子应用刷新后 404
结论：直接访问 /app-a/list 返回 404。
原因：服务端未配置 history 回退，或回退到错误入口。
解法：服务端/网关把未知路径回退到主应用 index.html。

坑 2：多个 Vue 实例导致组件失效
结论：共享组件不生效，事件穿透异常。
原因：共享依赖未去重，运行了多份 Vue 实例。
解法：shared 设 singleton: true，或 externals 统一全局加载。

坑 3：样式互相污染
结论：子应用 A 的样式影响子应用 B。
原因：全局选择器未隔离。
解法：用 scoped/CSS Modules/Shadow DOM，避免裸全局选择器。

坑 4：卸载后事件泄漏
结论：切换子应用后出现重复请求或内存增长。
原因：卸载时未清理事件监听、定时器、全局变量。
解法：卸载函数中统一清理副作用，沙箱自动还原全局变量。

坑 5：token 不同步导致接口 401
结论：登录后子应用接口仍报未授权。
原因：子应用未拿到或未携带最新 token。
解法：统一 token 存储与拦截器，登录态变更时通知各子应用刷新。
```
