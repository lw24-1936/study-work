## 概述

JavaScript 模块化经历了从无到有、从社区方案到官方标准的演进。理解各模块系统的历史与差异，才能看懂遗留代码、正确选型。

```text
模块化的演进脉络：
无模块（全局作用域）
  → CommonJS（服务端，同步）
  → AMD（浏览器，异步）
  → UMD（兼容多端）
  → ESM（官方标准，静态）
  → SystemJS（动态加载 ESM）
```

```text
为什么需要模块化：
1. 作用域隔离 —— 避免全局变量污染
2. 依赖管理 —— 明确模块间的依赖关系
3. 代码复用 —— 抽离公共代码
4. 按需加载 —— 拆分代码，控制体积
```

## AMD 异步模块定义

AMD（Asynchronous Module Definition）面向浏览器，异步加载模块，代表实现是 RequireJS。

```js
// 定义模块：define(依赖, 工厂函数)
define(['jquery', 'utils'], function($, utils) {
  return {
    init() {
      utils.log($);
    },
  };
});
```

```js
// 使用模块：require(依赖, 回调)
require(['app', 'utils'], function(app, utils) {
  app.start();
});
```

```text
AMD 特点：
1. 异步加载 —— 浏览器环境友好，不阻塞页面
2. 依赖前置 —— 先声明依赖，再执行工厂函数
3. 代表实现 —— RequireJS（已逐渐淡出）

历史地位：解决浏览器无模块化的痛点，后被 ESM + 打包工具取代。
```

## CommonJS

CommonJS 是 Node.js 的模块规范，同步加载，服务端场景。（详见 [[13.1-CommonJS]]）

```js
// 导出
module.exports = { add };

// 引入
const { add } = require('./math.js');
```

```text
CommonJS 特点：
1. 同步加载 —— 适合服务端本地文件
2. 运行时解析 —— 模块结构运行期确定
3. 值拷贝 —— 导出的是值的拷贝
4. Node 默认 —— 服务端事实标准
```

## UMD 通用模块定义

UMD（Universal Module Definition）是「兼容多端」的包装模式，同时支持 AMD、CommonJS 和全局变量。

```js
(function(root, factory) {
  if (typeof define === 'function' && define.amd) {
    // AMD 环境
    define(['jquery'], factory);
  } else if (typeof module === 'object' && module.exports) {
    // CommonJS 环境
    module.exports = factory(require('jquery'));
  } else {
    // 浏览器全局变量
    root.MyLib = factory(root.jQuery);
  }
}(this, function($) {
  // 模块实现
  return { /* ... */ };
}));
```

```text
UMD 的价值：
1. 一次构建，多处使用 —— 同时兼容 AMD/CJS/全局
2. 用于发布「通用」库 —— 打包工具常输出 UMD 格式

现状：ESM 成为标准后，UMD 主要用于需要兼容旧环境的库。
```

## ESM 官方模块

ESM 是 ECMAScript 官方标准，静态结构、引用绑定，是现在的主流。（详见 [[13.2-ES Modules]]）

```js
// 导出
export const add = (a, b) => a + b;
export default function greet() {}

// 引入
import greet, { add } from './math.js';
```

```text
ESM 特点：
1. 静态结构 —— 编译期确定，可 tree shaking
2. 引用绑定 —— 实时引用，非值拷贝
3. 异步加载 —— 浏览器并行加载
4. 官方标准 —— 现代项目事实标准
```

## SystemJS

SystemJS 是动态模块加载器，支持在浏览器中加载 ESM、CommonJS、AMD 等多种格式，是 import maps 的早期实践。

```js
// SystemJS 动态加载
System.import('./module.js').then(module => {
  module.default();
});
```

```html
<!-- 配合 import map 使用 -->
<script type="systemjs-importmap">
{
  "imports": {
    "lodash": "https://cdn.example.com/lodash.js"
  }
}
</script>
```

```text
SystemJS 的定位：
1. 动态加载 —— 运行时加载模块（配合 import map）
2. 多格式兼容 —— 加载 ESM/CJS/AMD
3. 场景 —— 微前端、动态插件系统

现状：原生 import map + ESM 逐渐替代 SystemJS，但仍见于微前端方案。
```

## 选型对比

```text
对比维度        AMD        CommonJS    UMD        ESM
加载时机       异步       同步        兼容多端   异步
环境           浏览器     服务端      通用       通用
结构           运行时     运行时      运行时     静态
值语义         拷贝       拷贝        拷贝       引用
tree shaking   不支持     不支持      不支持     支持
现代推荐       否         服务端可    否         是（首选）
```

```text
选型建议：
1. 新项目一律 ESM
2. Node 服务端可用 CommonJS 或 ESM（新代码倾向 ESM）
3. 发布库可输出 ESM + CJS 双格式（exports 条件导出）
4. UMD/AMD 仅用于维护遗留代码
```

## 应用场景实战

### 场景一：库的双格式发布

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",   // ESM 消费者
      "require": "./dist/index.cjs"   // CJS 消费者
    }
  }
}
```

### 场景二：识别遗留模块格式

```js
// AMD：看到 define(...)
define(['dep'], function(dep) {});

// CJS：看到 require / module.exports
const dep = require('dep');

// UMD：看到 if/else 环境检测
(function(root, factory) { ... }(this, ...));

// ESM：看到 import / export
import dep from 'dep';
```

## 最佳实践与踩坑记录

### 最佳实践

1. 新代码统一 ESM
2. 发布库用 exports 条件导出双格式
3. 理解各格式特征，快速识别遗留代码
4. 打包工具（webpack/Vite）能处理多格式，开发时统一 ESM 即可
5. 避免手写 UMD，交给打包工具生成

### 踩坑记录

```text
坑 1：混用模块系统
结论：import 与 require 混用，语义不一致甚至报错。
原因：ESM 与 CJS 的加载时机、值语义都不同。
解法：项目内统一模块系统，跨格式用 exports 条件隔离。

坑 2：误以为 UMD 是「标准」
结论：把 UMD 当成官方规范。
原因：UMD 只是社区约定的兼容包装模式。
解法：理解 UMD 是「兼容层」，官方标准是 ESM。

坑 3：tree shaking 不生效
结论：打包后体积没减小，未用代码没被摇掉。
原因：用了 CommonJS 格式，静态分析失效。
解法：改用 ESM，保证 import/export 静态可分析。

坑 4：值拷贝 vs 引用绑定混淆
结论：CJS 导入后改「值」没反应，ESM 能拿到最新值。
原因：两套系统的导出语义不同。
解法：理解 CJS 拷贝、ESM 引用，按需选择。

坑 5：浏览器直接加载 CommonJS 失败
结论：浏览器里 require 未定义。
原因：CommonJS 是服务端规范，浏览器不内置。
解法：浏览器用 ESM，或打包工具转译。
```
