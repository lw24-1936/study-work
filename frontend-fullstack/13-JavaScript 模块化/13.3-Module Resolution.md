## 概述

模块解析（Module Resolution）决定「import/require 一个包名时，实际加载哪个文件」。它是包发布、多环境兼容、TypeScript 类型支持的关键机制。

```text
模块解析要回答的问题：
1. 包的入口文件是哪个（main / exports）
2. 不同环境加载不同文件（ESM / CJS / 浏览器 / 类型）
3. 包内部如何引用（imports 别名）
4. 子路径如何暴露（exports 控制）
```

## package.json 入口字段

package.json 中的字段决定了包的解析行为。

```json
{
  "name": "my-lib",
  "version": "1.0.0",
  "main": "dist/index.js",       // 传统入口（CommonJS）
  "module": "dist/index.esm.js", // ESM 入口（打包工具用）
  "exports": "./dist/index.js",  // 现代入口（精确控制）
  "types": "dist/index.d.ts",    // TypeScript 类型入口
  "browser": "dist/index.browser.js"  // 浏览器专用入口
}
```

```text
入口字段的优先级（现代工具）：
exports > main（exports 定义后，main 被忽略）

各字段作用：
main —— 默认入口（Node 传统、CommonJS）
module —— ESM 入口（webpack/rollup 等打包工具识别）
exports —— 现代精确入口，支持条件导出（推荐）
types —— TypeScript 类型声明入口
browser —— 浏览器环境替代入口
```

## exports 条件导出

exports 是现代推荐的入口定义，支持**条件导出**和**子路径导出**，能精确控制包的暴露面。

```json
{
  "name": "my-lib",
  "exports": {
    ".": {
      "import": "./dist/index.mjs",     // ESM 环境
      "require": "./dist/index.cjs",    // CommonJS 环境
      "types": "./dist/index.d.ts"      // TypeScript
    },
    "./utils": "./dist/utils.js",       // 子路径导出
    "./package.json": "./package.json"
  }
}
```

```js
// 使用
import lib from 'my-lib';              // 命中 "." 的 import 条件
import utils from 'my-lib/utils';      // 命中子路径
```

```text
exports 的价值：
1. 精确控制 —— 未声明的子路径无法被 import（封装）
2. 条件导出 —— 不同环境/条件加载不同文件
3. 替代 main —— 更强大、更明确的入口定义
```

## imports 内部映射

imports 字段定义包**内部**的路径别名，用于简化深路径引用（# 前缀）。

```json
{
  "imports": {
    "#utils": "./src/utils/index.js",
    "#config/*": "./src/config/*.js"
  }
}
```

```js
// 包内部引用（用 # 别名，代替冗长的相对路径）
import { helper } from '#utils';
import db from '#config/db.js';
```

```text
imports vs exports：
imports —— 包内部别名（# 前缀，仅供包自身使用）
exports —— 对外暴露的入口（供使用方 import）

imports 的价值：内部引用不用写 ../../ 长相对路径。
```

## main / module / browser / types

这些字段共同服务于「多环境兼容」。

```text
main —— CommonJS 入口，Node require 时使用
module —— ESM 入口，打包工具 tree-shaking 时使用
browser —— 浏览器专用入口（替换 Node 专属实现）
types —— TypeScript 类型声明（.d.ts）
```

```json
{
  "main": "dist/index.js",
  "module": "dist/index.mjs",
  "browser": "dist/index.browser.js",
  "types": "dist/index.d.ts"
}
```

```text
双入口（dual package）的坑：
同时提供 CJS 和 ESM 时，可能产生「双实例」问题（同一包被加载两次）。
解决：尽量单一入口，或用 exports 条件 + 明确文件扩展名。
```

## Conditional Exports 条件导出详解

条件导出根据「条件键」匹配，按数组顺序，第一个匹配的生效。

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",      // 条件 1：类型
      "import": "./dist/index.mjs",      // 条件 2：ESM
      "require": "./dist/index.cjs",     // 条件 3：CJS
      "browser": "./dist/index.browser.mjs", // 条件 4：浏览器
      "default": "./dist/index.js"       // 兜底
    }
  }
}
```

```text
条件键类型：
1. 模块系统 —— import、require、node
2. 环境 —— browser、deno、worker
3. 开发 —— development、production
4. 类型 —— types（TypeScript 专用，通常放最前）
5. 兜底 —— default（最后）

规则：条件按对象顺序匹配，第一个满足的生效；default 兜底。
```

```json
// 嵌套条件：先环境后模块系统
{
  "exports": {
    ".": {
      "browser": {
        "import": "./browser.mjs",
        "require": "./browser.cjs"
      },
      "node": {
        "import": "./node.mjs",
        "require": "./node.cjs"
      }
    }
  }
}
```

## 应用场景实战

### 场景一：库的现代 exports 配置

```json
{
  "name": "@scope/my-lib",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./styles.css": "./dist/styles.css"
  }
}
```

### 场景二：内部路径别名

```json
{
  "imports": {
    "#lib/*": "./src/lib/*.js"
  }
}
```

```js
import { format } from '#lib/format.js';   // 代替 ../../../src/lib/format.js
```

## 最佳实践与踩坑记录

### 最佳实践

1. 新库用 exports 定义入口，明确 import/require/types 条件
2. types 条件放最前，default 放最后兜底
3. 内部引用用 imports（# 别名），避免长相对路径
4. 子路径用 exports 精确暴露，隐藏内部实现
5. 双入口库注意「双实例」问题，尽量单一格式

### 踩坑记录

```text
坑 1：exports 定义后 main 失效
结论：配了 exports，但 main 入口不生效。
原因：exports 优先级高于 main。
解法：统一用 exports，删掉冗余的 main。

坑 2：忘配 types 导致类型丢失
结论：TS 项目找不到类型，报 any 或错误。
原因：exports 未声明 types 条件。
解法：exports 每个入口配 types 条件（放最前）。

坑 3：条件顺序错误
结论：default 放在前面，后面的 import/require 不生效。
原因：条件按顺序匹配，default 永远命中。
解法：default 放最后，types 放最前。

坑 4：子路径未在 exports 声明
结论：import 'pkg/internal/x' 报 ERR_PACKAGE_PATH_NOT_EXPORTED。
原因：exports 未声明该子路径，被封装保护。
解法：需要暴露的子路径加入 exports，或用 ./* 通配。

坑 5：双入口导致双实例
结论：同一包 CJS 和 ESM 各加载一次，状态不一致。
原因：同时提供两种入口，且被不同方式引入。
解法：单一入口，或确保 ESM 包装 CJS（共用实例）。
```
