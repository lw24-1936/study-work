## 概述

回调函数（Callback）是 JavaScript 异步编程最原始的方案：把「稍后要执行的函数」作为参数传给异步操作，操作完成时调用它。它是 Promise、async/await 等一切现代异步方案的起点。

```text
回调的本质：
1. 函数是「一等公民」—— 可以当参数传递
2. 异步操作不阻塞主线程，完成后再「回头调用」传入的函数
3. 通过回调参数，把异步结果传回调用方
```

## Callback 回调函数

```js
// 同步回调：数组方法
[1, 2, 3].forEach(n => console.log(n));

// 异步回调：定时器
setTimeout(() => {
  console.log('1 秒后执行');
}, 1000);
```

```js
// 异步回调传递结果
function fetchData(callback) {
  setTimeout(() => {
    const data = { id: 1, name: 'Alice' };
    callback(data);          // 完成时调用回调，传入结果
  }, 500);
}

fetchData(data => {
  console.log(data.name);    // 'Alice'
});
```

```text
回调的两类场景：
同步回调 —— 立即执行（forEach、map、sort）
异步回调 —— 稍后执行（setTimeout、事件、网络请求）

关键区别：同步回调在当前调用栈内执行，异步回调在之后的事件循环中执行。
```

## Error First Callback 错误优先回调

Node.js 社区约定：回调的第一个参数是错误对象（null 表示无错），后续参数是结果。这一约定被称为 Error-First Callback。

```js
function readFile(path, callback) {
  // 模拟异步读取
  setTimeout(() => {
    if (!path) {
      callback(new Error('路径不能为空'));   // 第一个参数传错误
      return;
    }
    callback(null, '文件内容');              // null 表示无错
  }, 100);
}

readFile('/a.txt', (err, data) => {
  if (err) {
    console.error('读取失败:', err.message);
    return;
  }
  console.log(data);          // '文件内容'
});
```

```text
Error-First 约定的价值：
1. 统一错误处理 —— 所有回调用同一模式判断错误
2. 避免静默失败 —— 错误必须被显式处理
3. Node 生态标准 —— fs、http 等核心模块都遵循
```

## Callback Hell 回调地狱

多个异步操作需要顺序执行时，回调层层嵌套，形成「回调地狱」（Callback Hell / Pyramid of Doom）。

```js
// 回调地狱：三层嵌套，向右缩进越来越深
getUser(1, (err, user) => {
  if (err) return handleError(err);
  getOrders(user.id, (err, orders) => {
    if (err) return handleError(err);
    getOrderDetail(orders[0].id, (err, detail) => {
      if (err) return handleError(err);
      getProduct(detail.productId, (err, product) => {
        if (err) return handleError(err);
        console.log(product);
      });
    });
  });
});
```

```text
回调地狱的问题：
1. 可读性差 —— 嵌套层层向右，难以理解
2. 错误处理重复 —— 每一层都要写 if (err)
3. 维护困难 —— 增删步骤要重新调整嵌套
4. 变量作用域混乱 —— 外层变量在内层共享

解决方案：Promise（链式）、async/await（扁平化）。
```

## 回调的缺陷与替代

```text
回调方案的根本缺陷：
1. 控制反转 —— 把执行权交给异步函数，无法确定它何时/是否调用
2. 信任问题 —— 回调可能不调用、调用多次、调用时机错误
3. 顺序依赖难表达 —— 顺序执行靠嵌套，并发执行难协调

现代替代：
Promise —— 链式调用，扁平化顺序依赖，统一错误处理
async/await —— 同步写法写异步，彻底告别嵌套
```

```js
// 回调 → Promise → async/await 的演进
// 回调
getUser(1, (err, user) => getOrders(user.id, (err2, orders) => {...}));

// Promise
getUser(1)
  .then(user => getOrders(user.id))
  .then(orders => getOrderDetail(orders[0].id));

// async/await
const user = await getUser(1);
const orders = await getOrders(user.id);
```

## 应用场景实战

### 场景一：包装回调为 Promise（promisify）

```js
// 把 Error-First 回调包装成 Promise
function promisify(fn) {
  return (...args) => new Promise((resolve, reject) => {
    fn(...args, (err, result) => {
      err ? reject(err) : resolve(result);
    });
  });
}

const readFileAsync = promisify(readFile);
const data = await readFileAsync('/a.txt');
```

### 场景二：避免回调地狱的早期手法（命名函数）

```js
// 用命名函数拆平嵌套（治标不治本）
function handleProduct(product) { console.log(product); }
function handleDetail(detail) { getProduct(detail.productId, handleProduct); }
function handleOrders(orders) { getOrderDetail(orders[0].id, handleDetail); }
function handleUser(user) { getOrders(user.id, handleOrders); }
getUser(1, handleUser);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 新代码用 Promise 或 async/await，回调仅用于事件、定时器等场景
2. Node 风格回调遵循 Error-First 约定
3. 回调函数保持短小，复杂逻辑拆成命名函数
4. 需要顺序执行的异步操作，用 Promise 链式而非回调嵌套
5. 理解控制反转，注意回调的调用时机与次数

### 踩坑记录

```text
坑 1：回调地狱
结论：多层异步嵌套，代码向右缩进成金字塔。
原因：顺序依赖用回调表达，只能嵌套。
解法：用 Promise 链式或 async/await 扁平化。

坑 2：忘处理回调中的错误
结论：异步操作失败被静默忽略。
原因：回调里只写了成功分支，没检查 err。
解法：遵循 Error-First，先判断 err。

坑 3：回调被多次调用
结论：同一个回调被执行两次，状态错乱。
原因：异步函数内部逻辑分支未 return，或重复触发。
解法：回调前 return，或用 once 语义（Promise 天然只 resolve 一次）。

坑 4：回调里的 this 丢失
结论：回调里 this 不是预期对象。
原因：回调作为普通函数调用，this 默认绑定。
解法：用箭头函数继承外层 this，或 bind 绑定。

坑 5：同步与异步回调混淆
结论：回调有时同步执行、有时异步，行为不一致。
原因：函数内部分支有的走同步 return，有的走异步。
解法：Promise 统一异步语义，避免「Zalgo」问题。
```
