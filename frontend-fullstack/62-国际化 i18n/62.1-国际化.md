## 概述

国际化（i18n）让一个应用能适配不同语言、地区、时区的用户。它不只是「把文字翻译成英文」，还涉及数字/日期/货币格式、阅读方向、时区处理。做好国际化，产品才能进入全球市场而不必为每个地区重写一套代码。

```text
国际化要处理的四类差异：
1. 语言 —— 文案翻译（英文、日文、阿拉伯文）
2. 格式 —— 数字、日期、货币、时间的本地格式
3. 方向 —— LTR（从左到右）与 RTL（从右到左）布局
4. 时区 —— 时间的显示与转换
```

```text
国际化相关的核心术语：
i18n —— internationalization，国际化（架构上支持多语言）
l10n —— localization，本地化（为特定地区准备翻译与格式）
Locale —— 语言 + 地区组合标识（zh-CN、en-US）
Timezone —— 时区（Asia/Shanghai、America/New_York）
```

## i18n 与 l10n

i18n（国际化）和 l10n（本地化）是一对易混淆的概念：i18n 是「开发阶段让应用具备多语言能力」的过程，l10n 是「为某个具体地区准备翻译和格式」的过程。先做 i18n 的架构，才有 l10n 的内容。

```text
i18n（国际化）vs l10n（本地化）：
            i18n                      l10n
阶段        开发期                    发布期
做什么       抽离文案、接 i18n 框架    翻译文案、调整格式
产出        可国际化的代码架构        某语言的翻译资源
负责人       开发者                   翻译/本地化团队
数量        一次                      每个语言一次
```

```text
i18n 的四个层次（越深越完整）：
1. 文案抽离 —— 硬编码字符串改为 key 引用
2. 格式化 —— 数字/日期/货币走 Intl 或 i18n 库
3. 方向适配 —— 支持 RTL 布局
4. 时区处理 —— 时间按用户时区显示
```

```js
// i18n 之前的硬编码（坏）
const msg = '你有 ' + count + ' 条未读消息';

// i18n 之后的 key 引用（好）
// 各语言资源里定义 msg.unread，运行时按 locale 取
const msg = t('msg.unread', { count });
```

## Locale

Locale 是「语言 + 地区」的标识，用 BCP 47 语言标签表示，如 `zh-CN`（简体中文-中国）、`en-US`（英语-美国）、`zh-TW`（繁体中文-台湾）。它决定了用哪套翻译、哪种格式。

```text
Locale 的结构（BCP 47 标签）：
language-REGION
  zh    -  CN   （简体中文，中国大陆）
  zh    -  TW   （繁体中文，台湾）
  en    -  US   （英语，美国）
  en    -  GB   （英语，英国）
  pt    -  BR   （葡萄牙语，巴西）

语言相同、地区不同 → 翻译和格式都可能不同。
```

```js
// JavaScript 里获取和设置 locale
const locale = navigator.language;   // 浏览器语言，如 'zh-CN'

// Intl 按 locale 格式化
new Intl.NumberFormat('zh-CN').format(1234567);  // '1,234,567'
new Intl.NumberFormat('en-US').format(1234567);  // '1,234,567'
new Intl.NumberFormat('de-DE').format(1234567);  // '1.234.567'
```

```text
Locale 解析的注意点：
1. navigator.language 是浏览器语言，未必是用户真实偏好
2. 应允许用户手动切换 locale，并持久化
3. locale 匹配有回退链：zh-CN → zh → 默认语言
```

## Language

Language（语言）是 Locale 的语言部分，决定「用哪套文案」。语言是国际化的核心维度，同一个应用需要为每种支持的语言准备一份翻译资源。

```text
语言相关的问题：
1. 文案长度差异 —— 英文普遍比中文长，德文更长，布局要能伸缩
2. 语法差异 —— 复数、性别、词序（如「N 条消息」vs「N messages」）
3. 文化差异 —— 同一概念不同语言表达方式不同
```

```text
支持的语言清单示例：
zh-CN / zh-TW / en-US / ja-JP / ko-KR / ar-SA / es-ES ...

选语言时注意：
1. 按目标市场选择，不是越多越好（每多一种都增加维护成本）
2. 区分 zh-CN 与 zh-TW（简繁不同，不能合并）
```

```js
// 语言资源 —— 每种语言一份
// zh-CN.json
{ "greeting": "你好" }
// en-US.json
{ "greeting": "Hello" }
// ja-JP.json
{ "greeting": "こんにちは" }
```

## Region

Region（地区）是 Locale 的地区部分，决定「格式规范」——同一语言在不同地区，数字、日期、货币格式可能不同。地区影响的是「怎么显示」，语言影响的是「说什么」。

```text
地区影响格式的例子（同为英语）：
            en-US            en-GB
日期        12/31/2024       31/12/2024
数字        1,234.56         1,234.56
货币        $1,234.56        £1,234.56
纸张         Letter          A4

语言相同（en），地区不同（US/GB），格式不同。
```

```js
// 同一语言不同地区的格式差异
new Intl.DateTimeFormat('en-US').format(new Date('2024-12-31'));
// '12/31/2024'

new Intl.DateTimeFormat('en-GB').format(new Date('2024-12-31'));
// '31/12/2024'
```

```text
Region 的常见误区：
把语言和地区混为一谈。zh-CN 和 zh-TW 是两种 locale，
文案（简繁）和格式（日期）都要分别处理，不能只翻译不调格式。
```

## Timezone

Timezone（时区）决定「时间如何显示」。全球同一时刻在不同时区显示不同本地时间。国际化应用必须把「存储的绝对时间」转换成「用户时区的显示时间」。

```text
时区处理的两个核心原则：
1. 存储用 UTC（或带时区的时间戳）—— 绝对时间
2. 显示用用户时区 —— 本地时间

同一事件：2024-12-31T20:00:00Z（UTC）
北京显示：2025-01-01 04:00
纽约显示：2024-12-31 15:00
```

```js
// 获取用户时区
const tz = Intl.DateTimeFormat().resolvedOptions().timeZone;
// 'Asia/Shanghai'

// 按指定时区格式化
new Intl.DateTimeFormat('zh-CN', {
  timeZone: 'America/New_York',
  dateStyle: 'full',
  timeStyle: 'long',
}).format(new Date('2024-12-31T20:00:00Z'));
// '2024年12月31日 15:00:00 北美东部标准时间'
```

```text
时区的常见坑：
1. 用 new Date('2024-01-01') 解析 —— 被当作本地时间或 UTC，结果不一
2. 用 getHours() 取本地小时 —— 服务器和浏览器时区不同会错
3. 倒计时用本地时间戳 —— 跨时区用户看到不同剩余时间
```

## Currency

Currency（货币）格式化涉及「币种符号、位置、小数位、千分位」。不同地区对同一金额的显示差异巨大，必须用 `Intl.NumberFormat` 而非手工拼接。

```text
货币格式的差异维度：
1. 符号 —— $、€、¥、£
2. 位置 —— 符号在前（$100）还是后（100 €）
3. 小数位 —— 美元 2 位、日元 0 位
4. 千分位 —— 逗号（1,000）还是点（1.000）
```

```js
const amount = 1234.5;

// 不同币种
new Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' }).format(amount);
// '$1,234.50'

new Intl.NumberFormat('de-DE', { style: 'currency', currency: 'EUR' }).format(amount);
// '1.234,50 €'

new Intl.NumberFormat('ja-JP', { style: 'currency', currency: 'JPY' }).format(amount);
// '￥1,235'（日元无小数）

new Intl.NumberFormat('zh-CN', { style: 'currency', currency: 'CNY' }).format(amount);
// '¥1,234.50'
```

```text
货币格式化的注意点：
1. 金额计算用整数（分）而非浮点，避免精度误差
2. 显示时才格式化，存储始终存最小货币单位
3. 币种与 locale 解耦 —— 美元金额给德国用户看，是 $ 还是 €？
   取决于「币种」而非「locale」，明确用 currency 参数
```

## 应用场景实战

### 场景一：用 Intl 实现一套本地化格式化工具

```js
// format.js —— 统一格式化入口
export function formatNumber(value, locale) {
  return new Intl.NumberFormat(locale).format(value);
}

export function formatDate(value, locale, options = {}) {
  return new Intl.DateTimeFormat(locale, options).format(value);
}

export function formatCurrency(value, locale, currency) {
  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency,
  }).format(value);
}

export function formatDateTime(value, locale, timeZone) {
  return new Intl.DateTimeFormat(locale, {
    dateStyle: 'medium',
    timeStyle: 'short',
    timeZone,
  }).format(value);
}
```

```js
// 使用
const locale = 'zh-CN';
formatNumber(1234567, locale);                    // '1,234,567'
formatDate(new Date('2024-12-31'), locale);        // '2024/12/31'
formatCurrency(99.9, locale, 'USD');               // 'US$99.90'
formatDateTime(new Date(), locale, 'Asia/Shanghai');
```

### 场景二：读取用户 locale 并优雅回退

```js
// 确定生效 locale —— 用户选择 > 浏览器 > 默认
const SUPPORTED = ['zh-CN', 'zh-TW', 'en-US', 'ja-JP'];

function resolveLocale(userChoice, browserLang) {
  const candidates = [userChoice, browserLang, 'zh-CN'];
  for (const c of candidates) {
    if (!c) continue;
    // 精确匹配
    if (SUPPORTED.includes(c)) return c;
    // 语言匹配回退（zh-TW → 无 zh → 用 zh-CN）
    const lang = c.split('-')[0];
    const fallback = SUPPORTED.find((s) => s.startsWith(lang));
    if (fallback) return fallback;
  }
  return 'zh-CN';   // 最终默认
}

resolveLocale(null, navigator.language);   // 例如浏览器是 'zh-HK' → 'zh-CN'
```

## 最佳实践与踩坑记录

### 最佳实践

1. 存储用 UTC 绝对时间，显示时才转用户时区
2. 金额存储用最小货币单位（分），显示时才格式化
3. locale 解析做回退链：精确匹配 → 语言匹配 → 默认
4. 日期/数字/货币统一走 Intl，禁止手工拼接
5. 区分「语言」和「地区」—— 简繁、日期格式分别处理
6. 允许用户手动切换 locale 并持久化，别只依赖浏览器语言

### 踩坑记录

```text
坑 1：用 new Date('2024-01-01') 解析日期字符串
结论：不同浏览器/时区解析结果不一致。
原因：无时区的日期字符串解析规则不统一。
解法：传完整 ISO 时间戳（带 Z 或时区），或用库显式解析。

坑 2：货币符号跟着 locale 走而非币种走
结论：人民币金额给美国用户显示成 $。
原因：用 en-US locale 格式化却没指定 currency。
解法：Intl.NumberFormat 显式传 currency: 'CNY'，符号由币种决定。

坑 3：倒计时用本地时间计算
结论：跨时区用户看到的剩余时间不一致。
原因：用 new Date() 本地时间相减，受时区影响。
解法：用绝对时间戳（Date.now() / 服务器返回的 UTC）相减。

坑 4：getHours() 在服务器上取本地小时
结论：服务器 UTC 时区，返回的小时和用户看到的不符。
原因：getHours 取的是运行环境的本地时区。
解法：用 Intl.DateTimeFormat 指定 timeZone 取用户时区时间。

坑 5：把 zh-TW 和 zh-CN 合并成一种语言
结论：台湾用户看到简体中文。
原因：只做了 zh 一种资源，没区分繁简。
解法：zh-CN 与 zh-TW 分别准备文案，简繁不能混用。
```
