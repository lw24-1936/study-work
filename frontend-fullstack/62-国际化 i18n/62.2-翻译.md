## 概述

翻译是国际化的内容层——把应用的文案组织成「消息目录」（Message Catalog），用 key 引用、按 locale 取对应语言文本。难点不在「单词翻译」，而在「带变量的动态文案」：复数、性别、词序，不同语言的规则完全不同。

```text
翻译要解决的三个层次：
1. 静态文案 —— key → 对应语言的固定文本
2. 带变量文案 —— key + 参数，运行时插值（{name}、{count}）
3. 复杂语法文案 —— 复数/性别/选择，不同语言规则不同
```

```text
翻译的核心概念：
Translation —— 一条文案从源语言到目标语言的对应
Message Catalog —— 某语言的全部文案集合（一个 JSON 文件）
Plural —— 复数规则，不同语言不同
Gender —— 性别规则，影响形容词/动词词形
ICU Message Format —— 国际化消息的标准语法
Dynamic Translation —— 运行时动态取词（如接口返回的文案）
```

## Translation

Translation（翻译）是把源语言的文案映射到目标语言的过程。工程上通过「key 引用」实现：代码里写 `t('button.submit')`，运行时根据 locale 从对应语言的资源里取「提交」或「Submit」。

```js
// 代码里用 key 引用，不写死文案
const label = t('button.submit');

// zh-CN.json
{ "button.submit": "提交" }

// en-US.json
{ "button.submit": "Submit" }
```

```text
key 设计原则：
1. 语义化 —— button.submit 优于 msg_001
2. 层级化 —— 用点分层（nav.home、form.submit），便于组织
3. 稳定 —— key 一旦发布就不改名，改了要同步所有语言资源
4. 带默认值 —— t('key', '默认文案') 避免漏翻时显示空白
```

```js
// 带默认值的 key —— 未翻译时显示默认文案而非空白
t('feature.newLabel', '新建');   // 若 en-US 没翻，显示「新建」兜底
```

## Message Catalog

Message Catalog（消息目录）是「某一种语言的全部文案」的集合，通常是一个 JSON 文件（或 YAML/PO 文件）。每种语言一份，结构完全一致（同一组 key），只有 value 不同。

```text
消息目录结构示例：
locales/
├── zh-CN.json     # 源语言（通常以它为基准）
├── en-US.json
├── ja-JP.json
└── ar-SA.json
```

```json
// zh-CN.json —— 源语言目录
{
  "app.title": "我的应用",
  "app.greeting": "你好，{name}",
  "button.submit": "提交",
  "message.count": "你有 {count} 条消息"
}
```

```json
// en-US.json —— 翻译后的目录（结构一致）
{
  "app.title": "My App",
  "app.greeting": "Hello, {name}",
  "button.submit": "Submit",
  "message.count": "You have {count} messages"
}
```

```text
消息目录的格式：
1. JSON —— 前端最常用，i18next/react-intl 默认
2. YAML —— 可读性好，支持注释
3. PO/POT —— gettext 生态（C/Python 传统）
4. XLIFF —— 翻译行业标准，TMS（翻译管理系统）交换格式
```

## Plural

Plural（复数）规则是翻译里最易踩的坑：不同语言的复数规则数量不同，不能简单地「count > 1 就加 s」。英语有 2 种复数形式，阿拉伯语有 6 种，中文则不区分单复数。

```text
各语言的复数规则（CLDR 分类）：
中文/日语/韩语 —— 1 种形式（不区分单复数）
英语 —— 2 种（1 和其他）
法语 —— 2 种（0/1 和其他）
俄语 —— 3 种（1、2-4、其他）
阿拉伯语 —— 6 种（0、1、2、3-10、11-99、其他）
```

```text
错误做法（中文思维硬套）：
'你有 ' + count + ' 条消息' + (count > 1 ? 's' : '')
// 对英语勉强，对俄语/阿拉伯语完全错

正确做法：用复数 key，让 i18n 库按语言的复数规则选择
t('message.count', { count })  // key 定义多种复数形式
```

```json
// i18next 的复数形式 —— key 后缀区分
{
  "message.count_one": "You have {{count}} message",
  "message.count_other": "You have {{count}} messages"
}
```

```js
// 使用 —— 库自动按 count 选 one/other
i18n.t('message.count', { count: 1 });   // "You have 1 message"
i18n.t('message.count', { count: 5 });   // "You have 5 messages"
```

## Gender

Gender（性别）规则影响某些语言的词形变化。英语几乎无性别语法，但法语、俄语、阿拉伯语中，形容词、动词词形会随主语性别变化。翻译带「用户性别」的文案时必须考虑。

```text
性别影响的例子：
英语：Welcome back!（性别无关）
法语：Bienvenue!（欢迎女性） / Bienvenu!（欢迎男性）
阿拉伯语：动词、形容词随主语性别全面变化
```

```text
带性别的文案处理：
1. 传入性别参数 —— t('welcome', { gender })
2. 定义按性别区分的消息 —— key_male / key_female
3. 尽量避免带性别的文案 —— 改写为中性表达
```

```json
// i18next 按性别选择
{
  "welcome_male": "Bienvenu, {{name}}",
  "welcome_female": "Bienvenue, {{name}}",
  "welcome_other": "Bienvenue, {{name}}"
}
```

```js
i18n.t('welcome', { name: 'Alice', gender: 'female' });   // 欢迎女性
i18n.t('welcome', { name: 'Bob', gender: 'male' });       // 欢迎男性
```

```text
Gender 参数的来源：
1. 用户资料里的性别字段
2. 语法性别（如某些语言的「桌子」是阴性名词）

注意：性别字段缺失或为「不愿透露」时，用 other/中性兜底。
```

## ICU Message Format

ICU Message Format 是国际化消息的行业标准语法，用一个表达式同时处理插值、复数、性别、选择。react-intl、FormatJS 等库原生支持，是复杂文案的规范写法。

```text
ICU Message Format 的语法元素：
{name}                    —— 插值变量
{count, plural, ...}      —— 复数
{gender, select, ...}     —— 选择（性别/枚举）
{value, number, ...}      —— 数字格式化
{date, date, ...}         —— 日期格式化
```

```text
复数 —— plural 语法：
{count, plural,
  =0 {无消息}
  one {1 条消息}
  other {# 条消息}   # 会被替换成 count 的值
}
```

```text
选择 —— select 语法：
{gender, select,
  male {先生}
  female {女士}
  other {用户}
}
```

```js
// react-intl 里用 ICU 消息
import { FormattedMessage } from 'react-intl';

<FormattedMessage
  id="message.count"
  defaultMessage="{count, plural, =0 {No messages} one {# message} other {# messages}}"
  values={{ count: 5 }}
/>
// 渲染 "5 messages"
```

```text
ICU 消息的完整例子（复数 + 性别 + 插值组合）：
{gender, select,
  male {{count, plural, one {He has # item} other {He has # items}}}
  female {{count, plural, one {She has # item} other {She has # items}}}
  other {{count, plural, one {They have # item} other {They have # items}}}
}
```

## Dynamic Translation

Dynamic Translation（动态翻译）指「运行时才确定的文案」——如后端接口返回的内容、用户输入、第三方数据。这类内容不能预置到消息目录，需要特殊处理。

```text
动态翻译的两类：
1. 后端返回的文案 —— 接口直接返回本地化好的文本（后端 i18n）
2. 用户生成内容 —— 不翻译（用户名、评论），或机器翻译
```

```text
后端返回文案的场景：
1. 错误信息 —— 后端根据请求的 locale 返回对应语言
2. 商品描述 —— 数据库存多语言版本
3. 通知模板 —— 服务端按 locale 渲染

前端动态翻译的做法：
1. 后端返回前已本地化（推荐，后端统一管理）
2. 前端拿 code 后查本地目录映射（如错误码 → 文案）
```

```js
// 错误码映射 —— 前端按 code 取本地文案
const errorMessages = {
  'en-US': { 1001: 'Invalid email', 1002: 'Password too short' },
  'zh-CN': { 1001: '邮箱格式错误', 1002: '密码过短' }
};

function translateError(code, locale) {
  return errorMessages[locale]?.[code] ?? `Error ${code}`;
}
```

```text
动态翻译的边界：
1. 用户生成内容（评论、昵称）—— 不翻译，这是用户原话
2. 错误码 —— 前端映射本地文案，别让后端传整句
3. 大段内容 —— 用翻译服务或 TMS 管理，不硬编码在前端
```

## 应用场景实战

### 场景一：用 i18next 搭建带复数/插值的翻译

```bash
npm install i18next
```

```js
// i18n.js —— 初始化 i18next
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';

i18n.use(initReactI18next).init({
  resources: {
    'zh-CN': {
      translation: {
        'greeting': '你好，{{name}}',
        'cart': '购物车里有 {{count}} 件商品',
        'cart_plural': '购物车里有 {{count}} 件商品'
      }
    },
    'en-US': {
      translation: {
        'greeting': 'Hello, {{name}}',
        'cart_one': '{{count}} item in cart',
        'cart_other': '{{count}} items in cart'
      }
    }
  },
  lng: 'zh-CN',
  fallbackLng: 'zh-CN'
});

export default i18n;
```

```js
// 使用
i18n.t('greeting', { name: 'Alice' });   // "你好，Alice"
i18n.t('cart', { count: 1 });             // en: "1 item in cart"
i18n.t('cart', { count: 5 });             // en: "5 items in cart"
```

### 场景二：react-intl 的 ICU 消息实现复数 + 性别

```jsx
import { IntlProvider, FormattedMessage } from 'react-intl';

const messages = {
  'zh-CN': {
    'welcome': '{gender, select, male {先生您好} female {女士您好} other {您好}}，{name}'
  },
  'en-US': {
    'welcome': '{gender, select, male {Welcome Mr.} female {Welcome Ms.} other {Welcome}} {name}'
  }
};

function App() {
  return (
    <IntlProvider locale="en-US" messages={messages['en-US']}>
      <FormattedMessage
        id="welcome"
        values={{ gender: 'female', name: 'Alice' }}
      />
    </IntlProvider>
  );
}
// 渲染 "Welcome Ms. Alice"
```

## 最佳实践与踩坑记录

### 最佳实践

1. 复数用复数 key（one/other），别用 `count > 1 ? 's' : ''` 硬拼
2. 带性别/枚举的文案用 select 或分 key，别用 if/else 拼句子
3. 复杂文案用 ICU Message Format，一个表达式处理插值+复数+性别
4. key 带默认值兜底，漏翻时显示默认文案而非空白
5. 源语言目录（通常 zh-CN）作为基准，其他语言对齐同一组 key
6. 错误码、状态码前端映射文案，别让后端传整句

### 踩坑记录

```text
坑 1：中文思维写复数，英语以外全错
结论：俄语/阿拉伯语用户看到语法错误的复数形式。
原因：用 count > 1 加 s 的硬编码，只适配英语。
解法：用 i18n 库的复数 key（one/other/few/many），
     或 ICU 的 plural 语法，按语言规则自动选择。

坑 2：翻译改了 key 结构，其他语言没同步
结论：某语言缺 key，运行时报错或显示 key 原文。
原因：加了新 key 或改了 key 名，只更新了源语言目录。
解法：用抽取工具比对各语言目录的 key 集合，缺 key 报警。

坑 3：插值变量名拼错导致不替换
结论：显示成「你好，{{name}}」原文。
原因：模板写 {{naem}}，传参 name，变量名不匹配。
解法：变量名统一，配合 ESLint 插件检查模板变量。

坑 4：ICU 消息里 # 号被误解
结论：复数消息里 # 没被替换成数字。
原因：# 只有在 plural 块内才是 count 占位符，块外是字面量。
解法：确认 # 写在 {count, plural, ...} 块内部。

坑 5：动态文案硬编码进组件
结论：后端改了错误文案，前端还显示旧的。
原因：错误信息写死在前端，没走后端或映射。
解法：错误码前端映射本地文案，或后端按 locale 返回已本地化文本。
```
