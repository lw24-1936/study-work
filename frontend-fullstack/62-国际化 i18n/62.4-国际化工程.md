## 概述

国际化工程化解决「翻译资源的规模与维护」问题——语言一多、文案一多，全部打包进首屏会拖慢加载，手工维护 key 会漏会乱。于是有了懒加载、自动抽取、集中管理、回退、漏翻检测这一整套工程机制。

```text
国际化工程的五个环节：
1. Lazy Translation —— 按需加载语言包，不全部打进首屏
2. Translation Extraction —— 从代码自动抽取 key，不手工维护
3. Translation Management —— 翻译资源集中管理与协作
4. Fallback —— 缺失时的回退策略
5. Missing Translation —— 漏翻的检测与提示
```

```text
国际化工程要回答的问题：
1. 语言包太大怎么办？→ 懒加载，按语言按需取
2. key 谁来维护？→ 抽取工具自动收集
3. 翻译谁来做、怎么协作？→ TMS / 平台管理
4. 某语言没翻全怎么办？→ 回退到默认语言
5. 怎么知道有没有漏翻？→ 检测工具 + CI 门禁
```

## Lazy Translation

Lazy Translation（懒加载）指「不把全部语言的翻译打进首屏包，而是按用户当前语言按需加载」。支持几十种语言时，全量打包会让首屏 JS 膨胀几百 KB，懒加载只加载当前语言一份。

```js
// i18next 的懒加载 —— 按需加载语言资源
import i18n from 'i18next';
import Backend from 'i18next-http-backend';
import LanguageDetector from 'i18next-browser-languagedetector';

i18n
  .use(Backend)          // 从后端按需拉取语言包
  .use(LanguageDetector)
  .init({
    fallbackLng: 'zh-CN',
    load: 'currentOnly',   // 只加载当前语言，不预加载全部
    backend: {
      loadPath: '/locales/{{lng}}/{{ns}}.json'  // 按语言+命名空间取
    }
  });
```

```text
懒加载的两个维度：
1. 按语言 —— 只加载当前 locale 的资源（en-US.json）
2. 按命名空间 —— 只加载当前页面用到的模块（home.json、checkout.json）

命名空间切分：
locales/en-US/
├── common.json      # 通用文案
├── home.json        # 首页
├── checkout.json    # 结算页
└── admin.json       # 后台（用户可能永远不进）
```

```js
// 按命名空间懒加载 —— 进到某页才加载对应文案
import { useTranslation } from 'react-i18next';

function CheckoutPage() {
  const { t } = useTranslation('checkout');  // 只加载 checkout 命名空间
  return <div>{t('checkout.total')}</div>;
}
```

```text
懒加载的实现方式：
1. 运行时拉取 —— i18next-http-backend，按需 fetch JSON
2. 构建时分割 —— Webpack/Vite 代码分割，语言包单独 chunk
3. 命名空间 —— 拆模块，进模块才加载对应文案

运行时拉取有网络延迟，构建分割则更可控（无额外请求）。
```

## Translation Extraction

Translation Extraction（翻译抽取）指「从源码里自动收集所有文案 key，生成源语言目录」。手动维护 key 必然漏掉或重复，抽取工具（Babel 插件、CLI）扫描代码里的 `t('...')` 调用，自动生成完整的消息目录。

```text
抽取的两种思路：
1. 运行时抽取 —— i18next-parser 扫描 t('key') 调用生成 JSON
2. 编译期抽取 —— Babel 插件（如 babel-plugin-react-intl）在编译时收集
```

```bash
# i18next-parser —— 扫描源码，自动生成/更新语言目录
npx i18next-parser

# 配置：i18next-parser.config.js
# 输出 locales/zh-CN/translation.json（源语言基准）
# 扫描所有 t('...') 调用，新 key 自动追加
```

```js
// i18next-parser.config.js
module.exports = {
  input: ['src/**/*.{js,jsx,ts,tsx}'],
  output: 'locales/$LOCALE/$NAMESPACE.json',
  locales: ['zh-CN', 'en-US'],
  namespaceSeparator: '.',
  keySeparator: '.',
  defaultValue: '__STRING_NOT_TRANSLATED__'
};
```

```js
// 源码 —— 抽取工具从这里收集 key
const a = t('button.submit');
const b = t('message.count', { count: 5 });
// 抽取结果自动写入 zh-CN/translation.json：
// { "button.submit": "", "message.count": "" }
```

```text
抽取的注意事项：
1. 动态 key（t(variable)）抽取不到 —— 避免用变量作 key
2. 抽取只生成源语言，其他语言需要翻译流程补齐
3. defaultValue 标记未翻译的 key，便于后续识别
4. 抽取结果要纳入版本管理，diff 可看出新增/删除了哪些文案
```

## Translation Management

Translation Management（翻译管理）指「翻译资源的集中存储、翻译协作、审核发布」流程。个人项目手工维护 JSON 即可，团队项目则需要 TMS（翻译管理系统）或平台来管理多语言协作。

```text
翻译管理的三个层次：
1. 手工 JSON —— 个人项目，直接改文件
2. 平台托管 —— 上传到 TMS（Lokalise、Crowdin），翻译团队在线协作
3. CI 集成 —— 抽取 → 上传 → 翻译 → 拉回 → 打包 全自动化
```

```text
主流翻译管理方案：
1. Lokalise —— 在线翻译平台，支持机器翻译 + 人工审核
2. Crowdin —— 开源友好的翻译协作平台
3. Transifex —— 老牌翻译管理
4. 自建 —— git 仓库 + PR 流程管理（团队小够用）

选型因素：团队是否有专职翻译、语言数量、预算。
```

```yaml
# CI 集成的翻译流程（示例）
# 1. 抽取源语言 key
# 2. 上传到 TMS
# 3. 翻译完成
# 4. 拉回翻译好的资源
# 5. 打包发布
- run: npx i18next-parser
- run: lokalise2 upload locales/zh-CN/translation.json
- run: lokalise2 download --format json --dest locales/
```

```text
翻译管理的核心价值：
1. 翻译与代码解耦 —— 翻译团队不改代码
2. 状态追踪 —— 每个 key 的翻译进度、审核状态
3. 记忆库 —— 相同句段自动复用，保持术语一致
4. 机器翻译预填 —— MT 先翻，人工只审核
```

## Fallback

Fallback（回退）指「当前语言缺某条文案时，回退到备用语言」。最典型的是「英语作为兜底语言」——所有未翻译的 key 显示英文，而不是空白或 key 本身。

```js
// i18next 的回退链配置
i18n.init({
  lng: 'pt-BR',
  fallbackLng: ['en-US', 'zh-CN'],  // 缺则回退英文，再缺回退中文
  // fallbackLng: 'en' —— 单一回退语言
});
```

```text
回退链的层级：
用户语言 pt-BR（巴西葡语）
  ↓ 缺 key
en-US（英语，兜底语言）
  ↓ 仍缺 key
key 本身（或 defaultValue）

回退策略的选择：
1. 单一兜底 —— fallbackLng: 'en'，最简
2. 链式回退 —— ['en-US', 'zh-CN']，多级兜底
3. 语言族回退 —— pt-BR → pt → en（先回退到同语言变体）
```

```json
// 回退的匹配顺序（pt-BR 缺 key 时）：
// 1. pt-BR/translation.json 精确匹配
// 2. pt/translation.json    语言匹配（去掉地区）
// 3. en/translation.json    兜底语言
// 4. key 本身或 defaultValue
```

```text
回退要注意：
1. 兜底语言必须「完整」—— 兜底语言自己缺 key，就彻底没内容了
2. 回退静默发生 —— 用户看到英文，但不知道是漏翻，需配合检测
3. 区分「回退」和「漏翻」—— 回退是策略，漏翻是要修的问题
```

## Missing Translation

Missing Translation（漏翻）指「某语言的目录里缺了某条 key」。它和回退配合——漏翻触发回退，但漏翻本身要在开发期暴露，不能悄悄流到线上。

```text
漏翻的检测手段：
1. 开发期 —— i18next 的 missingKey 回调，控制台提示
2. 构建期 —— 比对各语言目录的 key 集合，缺 key 报错
3. 页面期 —— 显示特殊标记（如 [en] 前缀），肉眼可见
```

```js
// 开发期检测 —— missingKey 回调打印
i18n.init({
  fallbackLng: 'en-US',
  saveMissing: true,        // 开发环境：漏翻的 key 收集起来
  missingKeyHandler: (lng, ns, key) => {
    console.warn(`[i18n] 漏翻: ${lng} 缺少 "${key}"`);
  }
});
```

```js
// 构建期比对 —— 检查各语言目录 key 是否一致
import zhCN from './locales/zh-CN/translation.json';
import enUS from './locales/en-US/translation.json';

function findMissingKeys(source, target) {
  const sourceKeys = Object.keys(source);
  const targetKeys = new Set(Object.keys(target));
  return sourceKeys.filter((k) => !targetKeys.has(k));
}

const missing = findMissingKeys(zhCN, enUS);
if (missing.length > 0) {
  console.error('en-US 漏翻的 key:', missing);
  // CI 里可 process.exit(1) 阻断发布
}
```

```text
漏翻的显示策略（线上）：
1. 显示兜底语言 —— 用户看到英文（最平滑，但掩盖了漏翻）
2. 显示 key —— 如 "button.submit"（暴露问题，但体验差）
3. 特殊标记 —— [en]Submit（既能看懂，又提示未本地化）

多数产品选「回退英文」，配合「漏翻监控」在后台告警，
而非在界面上暴露 key。
```

## 应用场景实战

### 场景一：完整国际化工程流程（抽取 + 懒加载 + 回退）

```bash
# 安装依赖
npm install i18next i18next-http-backend i18next-browser-languagedetector
npm install -D i18next-parser
```

```js
// i18n.js —— 懒加载 + 回退 + 漏翻提示
import i18n from 'i18next';
import Backend from 'i18next-http-backend';
import LanguageDetector from 'i18next-browser-languagedetector';
import { initReactI18next } from 'react-i18next';

i18n
  .use(Backend)
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    fallbackLng: 'en-US',
    load: 'currentOnly',
    backend: {
      loadPath: '/locales/{{lng}}/{{ns}}.json'
    },
    missingKeyHandler: (lng, _ns, key) => {
      console.warn(`[i18n] ${lng} 缺少 "${key}"`);
    }
  });

export default i18n;
```

```js
// 抽取配置 —— 从源码自动生成源语言目录
// i18next-parser.config.js
module.exports = {
  input: ['src/**/*.{js,jsx,ts,tsx}'],
  output: 'public/locales/$LOCALE/$NAMESPACE.json',
  locales: ['zh-CN', 'en-US'],
  defaultValue: ''
};
```

```bash
npx i18next-parser   # 扫描源码，生成 zh-CN/en-US 目录
```

### 场景二：CI 门禁 —— 漏翻阻断发布

```yaml
# .github/workflows/i18n-check.yml
name: i18n check
on: [pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npx i18next-parser            # 重新抽取，diff 看新增 key
      - run: node scripts/check-missing.mjs # 比对漏翻，缺则退出 1
```

```js
// scripts/check-missing.mjs —— 漏翻检查脚本
import zhCN from '../public/locales/zh-CN/translation.json' assert { type: 'json' };
import enUS from '../public/locales/en-US/translation.json' assert { type: 'json' };

const missing = Object.keys(zhCN).filter((k) => !(k in enUS));
if (missing.length) {
  console.error('en-US 漏翻:', missing);
  process.exit(1);
}
console.log('翻译完整，检查通过');
```

## 最佳实践与踩坑记录

### 最佳实践

1. 语言包懒加载，按语言 + 命名空间拆包，别全量打进首屏
2. 用抽取工具自动收集 key，杜绝手工维护漏 key
3. 兜底语言必须保持 100% 完整，它是最后的保障
4. 漏翻检测接 CI，构建期比对 key 集合，缺则阻断
5. 翻译资源纳入版本管理，diff 追踪文案增删
6. 避免动态 key（t(variable)），抽取工具和类型检查都抓不到

### 踩坑记录

```text
坑 1：全部语言打包进首屏，首屏 JS 爆炸
结论：支持 30 种语言，首屏包多出几 MB。
原因：所有语言资源都 import 进来了。
解法：load: 'currentOnly' + 后端按需加载，或构建时分割 chunk。

坑 2：兜底语言自己也缺 key
结论：用户看到 key 原文或空白。
原因：fallbackLng 指向的语言目录没翻全。
解法：兜底语言保持完整，CI 里兜底语言缺 key 直接报错。

坑 3：动态 key 抽取不到
结论：t(dynamicKey) 这类调用，抽取工具漏掉了。
原因：key 是运行时变量，静态分析无法确定。
解法：用静态 key，动态内容走插值变量而非 key 本身。

坑 4：命名空间配错导致加载失败
结论：页面文案全部空白，请求 404。
原因：loadPath 模板或命名空间名与实际文件不匹配。
解法：核对 loadPath 路径与目录结构，命名空间名严格一致。

坑 5：漏翻静默回退，产品上线才发现
结论：某语言部分文案显示英文，没人察觉。
原因：fallback 静默发生，没接漏翻监控。
解法：开发期 missingKey 告警 + 构建期 key 比对门禁。
```
