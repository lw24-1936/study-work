## 概述

Docker 把应用及其运行环境打包成可移植的镜像，再以容器的形式在任何支持 Docker 的机器上运行，解决「我本地能跑，线上跑不起来」的环境差异问题。对前端而言，Docker 的价值在于把「构建产物 + Web 服务器 + 配置」封装成标准交付单元，交给 Kubernetes 或任意平台部署。

```text
Docker 的核心概念：
1. Image —— 只读的构建模板，包含应用和运行环境
2. Container —— 镜像的运行实例，有独立的进程和文件系统
3. Layer —— 镜像的分层结构，每一条 Dockerfile 指令一层
4. Dockerfile —— 描述如何构建镜像的脚本
5. Registry —— 镜像仓库，存储和分发镜像
6. Volume / Network —— 持久化数据 / 容器间通信
```

```bash
# 一条命令体验 Docker 的全流程
docker run -d -p 8080:80 --name web nginx:alpine
# 拉取镜像 -> 启动容器 -> 映射端口 -> 后台运行
curl http://localhost:8080
```

## Image

Image（镜像）是容器的只读模板，包含运行应用所需的文件系统、依赖、配置和启动命令。镜像由多个层叠加而成，可以基于已有镜像（如 nginx、node）继续构建，也可以完全从零开始。

```bash
# 列出本地镜像
docker images

# 拉取镜像
docker pull node:20-alpine

# 给镜像打标签（重命名）
docker tag node:20-alpine my-node:latest

# 删除镜像
docker rmi my-node:latest
```

```text
镜像命名规范：
1. registry/namespace/name:tag —— 完整形式
2. tag 默认 latest，但生产环境应使用明确版本
3. 镜像以分层方式存储，相同层在多个镜像间共享
```

## Container

Container（容器）是镜像的运行实例，拥有独立的进程空间、网络和文件系统，但与宿主机共享内核。容器是「一次性」的：可以随时启动、停止、删除，状态不持久，持久化数据要挂载 Volume。

```bash
# 启动容器（前台）
docker run nginx:alpine

# 后台运行 + 端口映射 + 命名
docker run -d --name my-web -p 8080:80 nginx:alpine

# 查看运行中的容器
docker ps

# 进入容器内部
docker exec -it my-web sh

# 停止 / 启动 / 删除
docker stop my-web
docker start my-web
docker rm my-web
```

```text
容器的生命周期：
1. create —— 从镜像创建容器，但不启动
2. start / stop —— 启动 / 停止
3. restart —— 重启（配合 --restart=always 自愈）
4. rm —— 删除容器（用 -f 强制删除运行中的）
5. exec —— 在运行中的容器里执行命令
```

## Layer

Layer（层）是镜像的构建单元。Dockerfile 里每一条指令（RUN、COPY、ADD）都会生成一个新层，层之间是只读叠加的。分层带来两个好处：构建缓存（没变的层直接复用）和镜像共享（多个镜像复用相同的底层）。

```text
镜像分层示意：
1. 基础层 —— FROM nginx:alpine（操作系统 + nginx）
2. 依赖层 —— COPY package.json + RUN npm ci
3. 源码层 —— COPY src/
4. 构建层 —— RUN npm run build
5. 配置层 —— COPY nginx.conf
```

```bash
# 查看镜像的分层历史
docker history my-app:latest
# 输出每一层的指令、大小、创建时间
```

```text
Layer 与缓存的关系：
1. 层按顺序构建，某层变化则其后所有层缓存失效
2. 把不易变的指令放前面（如依赖安装），易变的放后面（如源码复制）
3. 缓存命中时构建几乎瞬时完成，大幅加速 CI/CD
```

## Dockerfile

Dockerfile 是构建镜像的脚本，用声明式的指令描述「从哪开始、装什么、放什么、怎么启动」。前端最常用的指令组合是 FROM（基础镜像）、COPY（复制文件）、RUN（执行命令）、EXPOSE（声明端口）、CMD（启动命令）。

```dockerfile
# 一个最小的 Node 应用镜像
FROM node:20-alpine

WORKDIR /app

# 先复制依赖清单，利用层缓存
COPY package*.json ./
RUN npm ci --only=production

# 再复制源码
COPY . .

EXPOSE 3000
CMD ["node", "server.js"]
```

```text
常用 Dockerfile 指令：
1. FROM —— 指定基础镜像，必须放在最前面
2. WORKDIR —— 设置工作目录，后续指令都在此执行
3. COPY —— 复制文件到镜像（推荐，比 ADD 更可预期）
4. RUN —— 构建时执行命令（装依赖、编译）
5. ENV —— 设置环境变量
6. EXPOSE —— 声明容器监听端口（文档作用）
7. CMD —— 容器启动时执行的默认命令
```

## Registry

Registry（镜像仓库）用于存储和分发镜像，分为公开的 Docker Hub 和私有的自建仓库（如 Harbor、云厂商的容器镜像服务）。镜像通过 push 上传、pull 下载，仓库是 CD 流水线里镜像流转的中转站。

```bash
# 登录仓库
docker login registry.example.com

# 打标签（指向私有仓库）
docker tag my-app:v1.2.3 registry.example.com/my-app:v1.2.3

# 推送 / 拉取
docker push registry.example.com/my-app:v1.2.3
docker pull registry.example.com/my-app:v1.2.3
```

```text
Registry 的要点：
1. 认证 —— 私有仓库需要登录，凭证注意保密
2. 命名空间 —— 按团队/项目组织，避免命名冲突
3. 版本管理 —— 用明确的 tag 而非 latest 追踪版本
4. 清理策略 —— 定期清理旧镜像，控制存储成本
```

## Volume

Volume（数据卷）用于持久化容器数据。容器本身是临时的，删除即丢数据；Volume 把数据挂载到宿主机或外部存储，让数据独立于容器生命周期存在，也用于容器间共享数据。

```bash
# 命名卷：数据由 Docker 管理
docker run -d -v my-data:/var/lib/data my-app

# 绑定挂载：直接映射宿主机目录（常用于开发热更新）
docker run -d -v $(pwd)/dist:/usr/share/nginx/html nginx:alpine

# 查看卷
docker volume ls
```

```text
Volume 的适用场景：
1. 数据库持久化 —— 容器重启数据不丢
2. 开发热更新 —— 宿主机源码直接映射进容器
3. 日志收集 —— 挂载日志目录供外部采集
4. 配置注入 —— 挂载配置文件覆盖镜像默认值
```

## Network

Network（网络）管理容器之间以及容器与外部的通信。默认情况下容器运行在 bridge 网络里，可以通过容器名互相访问；要访问宿主机外部服务，或让外部访问容器，则需要端口映射或自定义网络。

```bash
# 端口映射：宿主机的 8080 转发到容器的 80
docker run -d -p 8080:80 nginx:alpine

# 创建自定义网络，容器间用名字互访
docker network create my-net
docker run -d --name api --network my-net my-api
docker run -d --name web --network my-net my-web
# web 容器内可以直接 curl http://api
```

```text
Docker 网络的类型：
1. bridge —— 默认桥接网络，容器间可互通，外部需端口映射
2. host —— 直接使用宿主机网络，性能好但端口易冲突
3. none —— 无网络，完全隔离
4. overlay —— 跨主机的集群网络（Swarm/K8s 场景）
```

## 应用场景实战

### 场景一：本地起一个完整的前后端环境

```yaml
# docker-compose.yml —— 一键拉起前端 + API + 数据库
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - db-data:/var/lib/postgresql/data

  api:
    build: ./api
    environment:
      DATABASE_URL: postgres://postgres:secret@db:5432/app
    depends_on:
      - db

  web:
    build: ./web
    ports:
      - "8080:80"
    depends_on:
      - api

volumes:
  db-data:
```

```bash
# 启动整个环境
docker compose up -d
# 查看状态
docker compose ps
# 停止并清理
docker compose down
```

### 场景二：构建并推送前端镜像到仓库

```bash
# 构建镜像（用 commit hash 做 tag）
docker build -t registry.example.com/web:$(git rev-parse --short HEAD) .

# 推送到私有仓库
docker push registry.example.com/web:$(git rev-parse --short HEAD)

# 本地验证
docker run -d -p 8080:80 registry.example.com/web:$(git rev-parse --short HEAD)
curl http://localhost:8080
```

## 最佳实践与踩坑记录

### 最佳实践

1. 镜像尽量小：选 alpine 基础镜像，清理构建缓存和临时文件
2. 利用层缓存：先复制依赖清单再装依赖，最后复制源码
3. 用 .dockerignore 排除 node_modules、dist、.git，避免复制垃圾进镜像
4. 镜像 tag 用明确版本或 commit hash，禁止生产用 latest
5. 一个容器一个进程，复杂应用用 docker compose 编排
6. 敏感信息（密钥、密码）通过环境变量或 Secret 注入，不写进镜像

### 踩坑记录

```text
坑 1：把 node_modules 复制进镜像导致镜像巨大
结论：镜像动辄 1GB 以上，构建和拉取都极慢。
原因：没有 .dockerignore，node_modules 被 COPY 进镜像。
解法：写 .dockerignore 排除 node_modules、dist、.git 等，镜像体积骤降。

坑 2：源码改动导致依赖层缓存失效
结论：每次改一行源码都要重新 npm ci，构建慢到离谱。
原因：COPY . . 放在 RUN npm ci 之前，源码一变依赖层全部失效。
解法：先 COPY package.json 再 RUN npm ci，最后才 COPY 源码，缓存命中率高。

坑 3：容器里数据没挂 Volume 就删容器
结论：容器一删，数据库或用户数据全没了。
原因：把有状态数据写进了容器可写层，容器删除即丢失。
解法：有状态数据一律挂 Volume，让数据独立于容器生命周期。

坑 4：容器内 localhost 访问不到另一个容器
结论：前端容器里调 http://localhost:3000 访问 API 失败。
原因：每个容器有独立的网络命名空间，localhost 指向容器自己。
解法：用容器名（docker compose 服务名）互访，或加入同一自定义网络。

坑 5：用 latest 标签导致无法回滚
结论：不知道线上跑的是哪个版本，出了事回不去。
原因：latest 每次都覆盖，历史版本不可追溯。
解法：tag 用 commit hash 或语义化版本，保留多个历史镜像便于回滚。
```
