## 概述

前端项目的 Docker 化有一个核心矛盾：构建需要 Node.js 全家桶，运行只需要一个静态文件服务器。多阶段构建（Multi-stage Build）完美解决这个问题——在带 Node 的镜像里完成构建，再把产物拷贝到轻量的 Nginx 镜像里运行，最终镜像只有几十 MB。

```text
前端 Docker 化的关键点：
1. Node Build —— 在 Node 镜像里安装依赖并构建产物
2. Multi-stage Build —— 构建和运行分离，最终镜像最小化
3. Nginx —— 运行阶段用 Nginx 托管静态文件
4. Static Asset —— 静态资源的缓存策略与体积优化
5. Runtime Configuration —— 运行时注入环境相关配置
```

```dockerfile
# 前端镜像的标准骨架：两阶段构建
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
```

## Node Build

Node Build 指在 Node 镜像里完成前端构建：安装依赖、类型检查、打包出 dist。这一阶段是「重量级」的，镜像里包含 Node 运行时、node_modules 和构建工具链，但它只是过渡阶段，最终不会出现在运行镜像里。

```dockerfile
FROM node:20-alpine AS build
WORKDIR /app

# 安装依赖（npm ci 按锁文件确定性安装）
COPY package*.json ./
RUN npm ci

# 复制源码并构建
COPY . .
RUN npm run build
# 产物输出到 /app/dist
```

```text
Node Build 阶段的要点：
1. 锁文件 —— 用 npm ci / pnpm install --frozen-lockfile 保证可复现
2. 环境变量 —— 构建期变量（如 API 地址）用 ARG/ENV 传入
3. 缓存 —— 依赖层单独复制，命中层缓存加速构建
4. 隔离 —— 构建产生的临时文件和依赖不会带进最终镜像
```

## Multi-stage Build

Multi-stage Build（多阶段构建）让一个 Dockerfile 里可以有多个 FROM，每个 FROM 开启一个新阶段，阶段之间用 COPY --from 传递文件。前端典型用法：build 阶段用 Node 构建，runtime 阶段用 Nginx 运行，最终镜像只包含第二阶段的内容。

```dockerfile
# 三阶段：依赖 -> 构建 -> 运行
FROM node:20-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

FROM node:20-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM nginx:1.27-alpine AS runtime
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
```

```text
多阶段构建的好处：
1. 镜像极小 —— 只保留运行阶段的内容，Node 工具链被丢弃
2. 构建清晰 —— 每个阶段职责单一，便于复用和调试
3. 缓存友好 —— 依赖阶段独立，源码变动不影响依赖缓存
4. 安全 —— 构建工具、依赖源码不进入最终镜像，减少攻击面
```

## Nginx

Nginx 是前端运行阶段最常用的静态服务器：轻量、高性能、配置简单，能处理静态文件、反向代理、缓存和压缩。前端镜像的 runtime 阶段通常就是 Nginx 镜像 + dist 产物 + 一份 Nginx 配置。

```dockerfile
FROM nginx:1.27-alpine
# 删除默认欢迎页
RUN rm -rf /usr/share/nginx/html/*
COPY dist/ /usr/share/nginx/html/
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
```

```nginx
# nginx.conf —— 前端静态服务 + SPA 回退
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

```text
为什么前端运行选 Nginx：
1. 轻量 —— 镜像小、内存占用低、启动快
2. 高性能 —— 静态文件吞吐极强，适合纯前端托管
3. 功能全 —— 缓存、gzip、反向代理、TLS 一站式搞定
4. 生态成熟 —— 配置资料多，运维熟悉度高
```

## Static Asset

Static Asset（静态资源）指构建产物里的 JS/CSS/图片/字体等文件。前端镜像本质上就是在托管这些静态资源，因此资源组织、缓存策略和压缩策略直接决定线上性能。带 hash 的资源应该长缓存，入口 index.html 应该短缓存。

```nginx
# 静态资源的缓存策略
server {
    root /usr/share/nginx/html;

    # 带 hash 的资源长缓存
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 入口文件短缓存
    location = /index.html {
        add_header Cache-Control "no-cache";
    }
}
```

```text
静态资源的优化要点：
1. 文件命名 —— 构建产物带 content hash，内容变文件名变
2. 缓存策略 —— hash 资源 immutable 长缓存，入口短缓存
3. 压缩 —— 开启 gzip/brotli，文本资源体积可降 70%+
4. 预压缩 —— 构建时产出 .gz/.br 文件，Nginx 直接返回，省 CPU
```

## Runtime Configuration

Runtime Configuration（运行时配置）解决「同一个镜像部署到不同环境」的问题：镜像应该与环境无关，环境相关的配置（API 地址、特性开关、埋点 key）在运行时注入，而不是构建时写死。常见做法是在容器启动时用环境变量渲染一份 config.js，页面运行时读取。

```bash
# 运行时注入：用环境变量替换占位符生成配置
#!/bin/sh
# docker-entrypoint.sh
envsubst < /usr/share/nginx/html/config.template.js > /usr/share/nginx/html/config.js
exec nginx -g "daemon off;"
```

```js
// config.template.js —— 占位符在启动时被替换
window.__APP_CONFIG__ = {
  apiBaseUrl: "${API_BASE_URL}",
  featureFlags: "${FEATURE_FLAGS}",
  sentryDsn: "${SENTRY_DSN}",
};
```

```text
运行时配置的两种思路：
1. 环境变量渲染 —— 启动时替换占位符，生成最终配置文件
2. 远程配置中心 —— 页面启动时拉取配置，无需重新构建部署
```

```text
运行时配置 vs 构建时配置：
1. 构建时 —— 简单但一个环境一份产物，环境多了维护成本高
2. 运行时 —— 一个镜像到处跑，环境差异靠变量注入
3. 权衡 —— 前端大部分配置可运行时化，真正构建期的只有编译相关项
```

## 应用场景实战

### 场景一：完整的前端多阶段构建镜像

```dockerfile
# Dockerfile —— 可复用的前端镜像构建模板
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine AS runtime
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

```bash
# 构建并运行
docker build -t my-frontend:v1.0.0 .
docker run -d -p 8080:80 my-frontend:v1.0.0
curl http://localhost:8080
```

### 场景二：支持运行时配置注入的前端镜像

```dockerfile
# Dockerfile —— 支持 envsubst 运行时配置注入
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine AS runtime
COPY --from=build /app/dist /usr/share/nginx/html
COPY docker-entrypoint.sh /docker-entrypoint.sh
RUN chmod +x /docker-entrypoint.sh
ENTRYPOINT ["/docker-entrypoint.sh"]
```

```bash
# 运行时传入 API 地址
docker run -d -p 8080:80 \
  -e API_BASE_URL=https://api.example.com \
  -e SENTRY_DSN=https://xxx@sentry.io/1 \
  my-frontend:v1.0.0
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用多阶段构建，构建用 Node、运行用 Nginx，镜像从 GB 级降到几十 MB
2. 依赖清单先复制、后复制源码，最大化命中层缓存
3. 写 .dockerignore 排除 node_modules、dist、.git、测试文件
4. 环境相关配置运行时注入，一个镜像跑所有环境
5. 静态资源带 hash 长缓存，入口文件短缓存
6. 开启 gzip/brotli 并预压缩静态资源，降低传输体积

### 踩坑记录

```text
坑 1：单阶段构建把整个 Node 环境打进镜像
结论：镜像 1GB 起步，还带着 node_modules 和源码，臃肿且不安全。
原因：直接在 node 镜像里跑，没有分离构建和运行阶段。
解法：多阶段构建，运行阶段只留 Nginx + dist，镜像几十 MB。

坑 2：COPY . . 放在 npm ci 前面导致缓存失效
结论：改一行源码就重装全部依赖，构建又慢又费。
原因：源码复制触发了其后的依赖安装层缓存失效。
解法：先 COPY package*.json 再 RUN npm ci，最后 COPY . .。

坑 3：构建期把 API 地址写死进产物
结论：换一个环境就要重新构建一次镜像，部署繁琐易错。
原因：环境配置在构建时固化，无法复用镜像。
解法：配置运行时注入，用环境变量 + envsubst 或远程配置中心。

坑 4：Nginx 容器以默认方式启动导致退出
结论：容器起来就退出，报 "daemon off" 相关错误。
原因：Nginx 默认前台守护进程化，容器主进程退出容器即结束。
解法：CMD 用 nginx -g "daemon off;" 保持前台运行。

坑 5：dist 没排除导致 COPY 把旧产物带进镜像
结论：镜像里混入了上次构建的旧产物，线上出现诡异文件。
原因：.dockerignore 没排除 dist，本地旧 dist 被复制进镜像覆盖了新构建。
解法：.dockerignore 明确排除 dist，构建产物只在 build 阶段生成。
```
