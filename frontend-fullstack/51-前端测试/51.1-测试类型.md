## 概述

前端测试按"覆盖范围和目的"分成多种类型，从最小的函数单元到完整的用户流程。理解各类型的定位和工具选型，是搭建测试体系的第一步。

```text
测试金字塔（从下到上，数量递减）：
E2E —— 少量，验证完整用户流程
Integration / Component —— 中等，验证模块协作
Unit —— 大量，验证最小单元

金字塔原则：
底层快而多，顶层慢而少。单元测试为主，E2E 兜底关键流程。
```

```text
// 各类型对比
类型            | 覆盖范围       | 速度   | 稳定性 | 工具
Unit           | 函数/模块       | 极快   | 高     | Jest、Vitest
Integration    | 模块间协作      | 快     | 高     | Jest、Vitest
Component      | 单个组件        | 快     | 高     | Testing Library
E2E            | 完整用户流程    | 慢     | 中     | Playwright、Cypress
Visual         | 视觉回归        | 慢     | 中     | Percy、Playwright
Performance    | 性能指标        | 慢     | 低     | Lighthouse、WebPageTest
Accessibility  | 可访问性        | 快     | 高     | axe、jest-axe
Security       | 安全漏洞        | 慢     | 中     | 依赖扫描、DAST
```

测试类型的选择没有绝对标准，关键是在成本、速度和信心之间找平衡：核心逻辑多写单测，关键流程配 E2E，其余按风险补充。

## Unit Test

单元测试验证最小可测单元（通常是函数），是测试金字塔的基石。它快、稳定、定位问题精准。

```js
// 被测函数
export function formatPrice(cents, currency = 'CNY') {
  const symbol = { CNY: '¥', USD: '$' }[currency];
  return `${symbol}${(cents / 100).toFixed(2)}`;
}
```

```js
// 单元测试
import { describe, it, expect } from 'vitest';
import { formatPrice } from './formatPrice';

describe('formatPrice', () => {
  it('把分转成元并带货币符号', () => {
    expect(formatPrice(12345)).toBe('¥123.45');
  });

  it('支持美元', () => {
    expect(formatPrice(999, 'USD')).toBe('$9.99');
  });
});
```

```text
单元测试的特征：
1. 无外部依赖（网络、DOM、文件系统都 mock 掉）
2. 每个用例只测一件事
3. 命名清晰，失败时能一眼看出哪里坏了

适合测：纯函数、工具方法、数据转换、校验逻辑、状态机
```

单元测试的价值不在"跑通"，而在"重构安全网"——改动代码后跑一遍单测，快速确认没有破坏既有行为。

## Integration Test 与 Component Test

集成测试验证多个单元协作是否正常；组件测试是前端特色的集成测试，验证组件在给定 props/交互下的渲染输出和行为。

```text
Integration Test —— 模块间协作：
1. 测多个模块/函数组合起来的完整功能
2. 可以带真实的外部依赖（如真实数据库、真实 API），也可以部分 mock
3. 前端里常见的"表单提交 → 调 API → 更新状态"链路就是集成测试

Component Test —— 单个组件：
1. 渲染组件，模拟用户交互，断言 DOM 输出
2. 用 Testing Library 按"用户视角"测试（找元素、点按钮、看结果）
3. 不测实现细节，测可观察行为
```

```jsx
// 组件测试示例（React Testing Library）
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import LoginForm from './LoginForm';

test('提交空表单显示校验错误', async () => {
  render(<LoginForm />);
  await userEvent.click(screen.getByRole('button', { name: /登录/ }));
  expect(await screen.findByText('请输入用户名')).toBeInTheDocument();
});
```

```text
组件测试的原则：
1. 从用户视角断言（看到什么、点了什么、结果如何）
2. 用 role/label 找元素，而不是 CSS 类名（贴近可访问性）
3. 交互用 userEvent 模拟真实用户行为
```

## E2E Test

端到端测试模拟真实用户在真实浏览器里走完整流程，覆盖前端、后端、数据库的全链路，是信心最高、成本也最高的测试。

```js
// Playwright E2E 示例
import { test, expect } from '@playwright/test';

test('用户登录并创建订单', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('用户名').fill('alice');
  await page.getByLabel('密码').fill('secret123');
  await page.getByRole('button', { name: '登录' }).click();

  await expect(page).toHaveURL('/dashboard');

  await page.getByRole('button', { name: '新建订单' }).click();
  await page.getByLabel('商品').fill('MacBook Pro');
  await page.getByRole('button', { name: '提交' }).click();

  await expect(page.getByText('订单创建成功')).toBeVisible();
});
```

```text
E2E 的特征：
1. 启动真实应用 + 真实浏览器，走完整用户路径
2. 慢（秒级/用例）、环境依赖重（数据库、后端都要就绪）
3. 数量克制 —— 只测最关键的几条黄金路径

适合测：登录注册、下单支付、核心业务闭环
```

## Visual Test

视觉回归测试通过截图对比，发现 UI 的意外变化（样式错乱、布局偏移、元素丢失），补上"功能没坏但样子坏了"的盲区。

```text
视觉测试原理：
1. 对页面/组件截图，存为基线（baseline）
2. 后续每次跑测试截图，与基线逐像素或结构对比
3. 有差异则报告，人工确认是"有意改动"还是"回归"
```

```js
// Playwright 截图对比
import { test, expect } from '@playwright/test';

test('首页视觉快照', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveScreenshot('home.png');
});
```

```text
视觉测试工具：
1. Playwright/Cypress 内置截图对比
2. Percy、Chromatic —— 云平台，管理基线和审阅
3. BackstopJS —— 专注视觉回归

适合场景：
设计系统、组件库、营销页等"样式敏感"的页面，
靠功能测试发现不了样式回归。
```

## Performance Test

性能测试衡量页面加载速度、交互响应和运行时性能，用指标而非"主观感觉"来约束性能，防止性能劣化。

```text
核心性能指标（Web Vitals）：
LCP —— Largest Contentful Paint，最大内容绘制（<2.5s）
CLS —— Cumulative Layout Shift，布局偏移（<0.1）
INP —— Interaction to Next Paint，交互响应（<200ms）
FCP —— First Contentful Paint，首次内容绘制（<1.8s）
```

```js
// 用 Lighthouse CI 在 CI 里跑性能测试
// lighthouse.config.js
module.exports = {
  ci: {
    collect: { url: ['https://app.example.com/'], numberOfRuns: 3 },
    assert: {
      assertions: {
        'largest-contentful-paint': ['error', { maxNumericValue: 2500 }],
        'cumulative-layout-shift': ['error', { maxNumericValue: 0.1 }],
      },
    },
  },
};
```

```text
性能测试的工具：
1. Lighthouse —— 综合评分 + Web Vitals
2. WebPageTest —— 多地域、多设备真实环境测试
3. Chrome DevTools Performance —— 运行时性能剖析

落地方式：把性能断言接入 CI，指标超标即失败，防止劣化。
```

## Accessibility Test

可访问性测试验证页面是否对残障用户可用（屏幕阅读器、键盘导航、颜色对比），既是合规要求也是质量要求。

```js
// jest-axe 在组件测试里做可访问性断言
import { render } from '@testing-library/react';
import { axe, toHaveNoViolations } from 'jest-axe';
import Modal from './Modal';

expect.extend(toHaveNoViolations);

test('Modal 无严重可访问性问题', async () => {
  const { container } = render(<Modal open title="确认删除" />);
  const results = await axe(container);
  expect(results).toHaveNoViolations();
});
```

```text
可访问性检查的常见项：
1. 图片有无 alt 文本
2. 表单控件有无 label 关联
3. 颜色对比度是否达标
4. 键盘能否完整操作
5. 语义标签是否正确（button/heading/landmark）

工具：axe-core、jest-axe、Lighthouse 的 a11y 分类
```

## Security Test

安全测试发现依赖漏洞、注入攻击面和配置问题。前端安全测试主要靠自动化扫描，无法替代人工审计，但能拦住大量低级问题。

```text
前端安全测试的类型：
1. 依赖漏洞扫描 —— npm audit、Snyk，检查依赖的已知 CVE
2. 静态安全扫描 —— ESLint 安全插件、Semgrep，发现危险 API 误用
3. 头/配置检查 —— 安全 Header 是否齐全（SecurityHeaders）
4. DAST —— 动态扫描（ZAP、Burp），模拟攻击
```

```bash
# 依赖漏洞扫描
npm audit
npm audit --audit-level=high   # 有高危即失败，接入 CI
```

```text
// 危险 API 误用（静态扫描能发现的典型问题）
element.innerHTML = userInput;   // DOM XSS 风险
eval(userCode);                  // 代码注入
document.write(html);            // 注入
```

```text
前端安全测试的定位：
自动化扫描是底线（依赖漏洞、危险 API、安全头），
针对业务逻辑的安全（越权、数据校验）需要人工审计 + 后端安全测试配合。
```

## 应用场景实战

### 场景一：为项目搭建分层测试体系

```text
测试分层落地：
1. 纯函数/工具 —— Unit Test（Vitest）
2. 组件交互 —— Component Test（Testing Library）
3. 模块协作 —— Integration Test（Vitest + 部分 mock）
4. 关键流程 —— E2E Test（Playwright）
5. 设计系统 —— Visual Test（Playwright 截图）
6. 每次 CI —— Performance + Accessibility + Security 扫描
```

```js
// vitest 配置：区分单元测试与组件测试
// vitest.config.js
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'node',        // 单测默认 node 环境
    include: ['src/**/*.test.js'],
  },
});
```

### 场景二：CI 里的质量门禁

```yaml
# GitHub Actions 示例：一条流水线跑多类测试
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run test:unit          # 单元 + 组件测试
      - run: npm run test:e2e           # E2E 测试
      - run: npm run test:visual        # 视觉回归
      - run: npm run lighthouse:ci      # 性能断言
      - run: npm run test:a11y          # 可访问性
      - run: npm audit --audit-level=high   # 依赖安全
```

## 最佳实践与踩坑记录

### 最佳实践

1. 遵循测试金字塔：单元测试为主，E2E 只覆盖关键流程
2. 组件测试从用户视角断言，不测实现细节
3. 视觉回归用于设计系统和样式敏感页面，配合基线审阅流程
4. 性能、可访问性、安全测试接入 CI，作为质量门禁自动执行
5. E2E 测试隔离环境（独立数据库），避免用例间相互污染
6. 测试命名描述行为而非实现，重构时不改测试名

### 踩坑记录

```text
坑 1：测试金字塔倒置
结论：大量 E2E 测试，跑一次半小时，维护成本极高。
原因：把所有逻辑都塞进 E2E 里测。
解法：下沉到单元/组件测试，E2E 只留黄金路径。

坑 2：组件测试测实现细节
结论：改个内部变量名，测试全红。
原因：断言了 state、props 传递等内部实现。
解法：只断言用户可观察的输出（渲染内容、交互结果）。

坑 3：视觉回归基线管理混乱
结论：每次 UI 改动都报一堆差异，团队麻木后直接"全接受"。
原因：没有基线审阅流程，差异未分级处理。
解法：规范基线更新流程，区分有意改动和意外回归。

坑 4：E2E 用例间共享状态
结论：用例顺序一换就挂，或数据互相污染。
原因：用例依赖前一个用例留下的状态/数据。
解法：每个用例独立造数据、独立清理，不依赖执行顺序。

坑 5：性能测试只看平均值
结论：平均值达标，但 P95/P99 体验极差。
原因：只看 mean 指标，忽略了长尾。
解法：关注分位数（P75/P95），结合 CLS/INP 等多指标综合判断。
```
