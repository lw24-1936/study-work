## 概述

实时状态是「实时通信之上、用户能感知到的那些动态信息」：谁在线、光标在哪、有没有新通知、聊天消息、协作中的他人动作。它建立在 WebSocket/SSE 等通道之上，本质是「把远端的变化实时同步到本地 UI」。核心难点不是传输，而是状态的组织和一致性。

```text
实时状态的六类内容：
1. Presence —— 谁在场：在线成员列表
2. Online Status —— 在线/离线状态标记
3. Cursor —— 协作者的光标位置
4. Notification —— 实时通知推送
5. Chat —— 即时消息
6. Collaboration —— 协作中的编辑、操作同步
```

```js
// 实时状态的通用模型：远端事件 → 更新本地状态
function createRealtimeState() {
  const state = {
    presence: new Set(),   // 在线成员
    cursors: new Map(),    // userId -> {x, y}
    notifications: [],     // 通知列表
  };
  return {
    state,
    apply(event) { /* 根据事件类型更新对应状态 */ },
  };
}
```

## Presence

Presence（在场）描述「谁当前在这个空间里」：文档的在线协作者、直播间的观众、群聊里的成员。它是有生命周期的状态——用户进入时加入、离开时移除，需要心跳和超时来维护，否则「幽灵在线」会一直挂着。

```text
Presence 的关键点：
1. 动态成员列表 —— 进入加入、离开移除
2. 心跳保活 —— 定期发心跳维持在场状态
3. 超时判定 —— 心跳超时判定离线
4. 订阅广播 —— 成员变化广播给所有在场者
```

```js
// 维护在线成员列表（前端视角）
const presence = new Map(); // userId -> lastSeen

function onPresenceEvent(e) {
  if (e.type === 'join') presence.set(e.userId, Date.now());
  if (e.type === 'leave') presence.delete(e.userId);
  if (e.type === 'heartbeat') presence.set(e.userId, Date.now());
}

// 定时清理超时成员
setInterval(() => {
  const now = Date.now();
  for (const [id, lastSeen] of presence) {
    if (now - lastSeen > 60_000) presence.delete(id); // 60 秒没心跳判离线
  }
}, 10_000);
```

Presence 的正确性依赖心跳机制：没有心跳，就无法区分「真的离线」和「网络暂时断开」。

## Online Status

Online Status（在线状态）是 Presence 的个人化投影：标记某个用户当前在线还是离线。它通常用「绿点」呈现，但要面对「假在线」问题——用户关了标签页但连接没正常关闭，状态还显示在线。

```text
Online Status 的关键点：
1. 个人在线标记 —— 在线/离线/离开/忙碌
2. 状态来源 —— 连接状态 + 心跳 + 显式上下线
3. 假在线问题 —— 异常断开需要超时兜底
4. 多端聚合 —— 一个用户多个设备，任一在线即在线
```

```js
// 在线状态判定：连接 + 心跳双因子
class OnlineTracker {
  constructor() { this.lastHeartbeat = new Map(); }
  markHeartbeat(userId) { this.lastHeartbeat.set(userId, Date.now()); }
  isOnline(userId) {
    const last = this.lastHeartbeat.get(userId);
    return last != null && Date.now() - last < 45_000; // 45 秒内有心跳算在线
  }
  onDisconnect(userId) { this.lastHeartbeat.delete(userId); }
}
```

在线状态别只靠连接事件：连接断开的异常路径（掉线、崩溃、强杀）不会触发正常的 leave，必须靠心跳超时兜底。

## Cursor

Cursor（光标）是协作者在共享文档里「鼠标/光标位置」的实时同步。多人协作编辑器里，你能看到别人光标在哪、选中了哪段文字。它是高频低价值状态——每动一下鼠标就一条消息，必须做节流和增量更新。

```text
Cursor 的关键点：
1. 高频更新 —— 鼠标移动产生大量事件
2. 节流 —— 必须限频，不能每次移动都广播
3. 增量同步 —— 只传位置变化
4. 短暂有效 —— 光标停太久没动应自动消失
```

```js
// 光标同步：节流 + 过期清理
let cursorTimer = null;
const cursors = new Map(); // userId -> {x, y, ts}

function onLocalCursorMove(x, y) {
  if (cursorTimer) return; // 节流：间隔内只发一次
  cursorTimer = setTimeout(() => {
    socket.emit('cursor', { x, y });
    cursorTimer = null;
  }, 50);
}

function onRemoteCursor(e) {
  cursors.set(e.userId, { x: e.x, y: e.y, ts: Date.now() });
}

setInterval(() => {
  const now = Date.now();
  for (const [id, c] of cursors) {
    if (now - c.ts > 5000) cursors.delete(id); // 5 秒没动光标消失
  }
}, 1000);
```

光标同步要控制消息频率，否则一个用户的鼠标移动就能淹没整个协作通道。

## Notification

Notification（通知）是「有事件发生时即时推给用户」的实时状态：新消息提醒、系统告警、@ 提及。它由服务端事件驱动推送，客户端收到后更新未读数、弹 toast，还可以调系统通知。

```text
Notification 的关键点：
1. 事件驱动 —— 服务端有事件就推
2. 未读计数 —— 未读数实时累加
3. 用户可见反馈 —— toast / 系统通知
4. 去重 —— 多端收到要避免重复提醒
```

```js
// 实时通知：推送到达更新未读数 + 弹提示
const unread = { count: 0 };

socket.on('notification', (n) => {
  unread.count += 1;
  renderBadge(unread.count);
  if (Notification.permission === 'granted') {
    new Notification(n.title, { body: n.body });
  }
});
```

通知系统要处理「消息已读」的同步：用户在 A 端读了，B 端的未读数也要清零，否则未读标记不一致。

## Chat

Chat（即时消息）是实时状态最典型的应用：消息发送、接收、已读、输入中提示。它的难点在消息的顺序、去重和「已读」状态的同步——断线重连后消息不能丢也不能重复。

```text
Chat 的关键点：
1. 消息收发 —— 发送、广播、接收
2. 顺序保证 —— 消息按序号排序
3. 去重 —— 客户端消息 id 去重
4. 已读回执 —— 已读状态同步
```

```js
// 聊天：本地消息 id 去重 + 按序号排序
const messages = new Map(); // msgId -> message

function send(text) {
  const msg = { id: crypto.randomUUID(), text, seq: -1 };
  messages.set(msg.id, msg);
  socket.emit('chat', msg);
}

socket.on('chat', (msg) => {
  if (messages.has(msg.id)) return; // 去重：自己发的会回传
  messages.set(msg.id, msg);
  renderSorted([...messages.values()].sort((a, b) => a.seq - b.seq));
});
```

聊天的「已读」和「在线」常和 Presence 联动：显示「对方正在输入」就是实时状态的组合。

## Collaboration

Collaboration（协作）是实时状态的最高形态：多人同时编辑同一份文档、看板、白板，每个人的操作实时同步给其他人。它把前面所有状态——Presence、Cursor、消息——组合在一起，核心是「操作如何无损同步」。

```text
Collaboration 的关键点：
1. 多人同时操作 —— 编辑、移动、删除并发发生
2. 操作同步 —— 每次操作广播给其他人
3. 冲突处理 —— OT / CRDT 保证收敛
4. 一致性 —— 各端看到的最终结果一致
```

```js
// 协作编辑：本地操作广播，远端操作应用
function applyLocalEdit(op) {
  apply(op);                 // 本地立即应用（乐观）
  socket.emit('edit', op);   // 广播给其他人
}

socket.on('edit', (op) => {
  apply(op);                 // 应用远端操作
});
```

协作的难点不在「把操作传过去」，而在「并发操作如何合并」——这属于 OT/CRDT 的范畴，见实时协作专题。

## 应用场景实战

### 场景一：协作文档的 Presence + Cursor

```js
// 在线成员 + 光标位置实时同步
class CollaborativeDoc {
  constructor(socket) {
    this.socket = socket;
    this.presence = new Map();
    this.cursors = new Map();
    socket.on('presence', (e) => this.onPresence(e));
    socket.on('cursor', (e) => this.onCursor(e));
  }
  onPresence(e) {
    if (e.type === 'join') this.presence.set(e.userId, Date.now());
    if (e.type === 'leave') this.presence.delete(e.userId);
    renderAvatars([...this.presence.keys()]);
  }
  onCursor(e) {
    this.cursors.set(e.userId, { x: e.x, y: e.y });
    renderCursors(this.cursors);
  }
  sendCursor(x, y) {
    this.socket.emit('cursor', { x, y });
  }
}
```

### 场景二：实时通知中心

```js
// 通知订阅 + 未读计数 + 系统通知
class NotificationCenter {
  constructor(socket) {
    this.unread = 0;
    socket.on('notification', (n) => this.onNotify(n));
  }
  onNotify(n) {
    this.unread += 1;
    this.updateBadge();
    if (Notification.permission === 'granted') {
      new Notification(n.title, { body: n.body });
    }
  }
  markAllRead() {
    this.unread = 0;
    this.updateBadge();
  }
  updateBadge() {
    document.querySelector('#badge').textContent = this.unread || '';
  }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. Presence 和在线状态必须有心跳 + 超时兜底，别只信连接事件
2. 光标、鼠标这类高频状态要节流，控制消息频率
3. 消息和操作带唯一 id，客户端去重，断线重连不重复不丢失
4. 已读状态要同步到所有端，避免 A 端读了 B 端还显示未读
5. 断线重连后先拉全量快照，再订阅增量事件
6. 协作操作同步用 OT/CRDT 保证收敛，别直接覆盖

### 踩坑记录

```text
坑 1：幽灵在线
结论：用户关闭页面后，在线列表还一直显示他在线。
原因：异常断开没触发 leave 事件，心跳也没做超时判定。
解法：心跳 + 超时判离线，定时清理超过阈值无心跳的成员。

坑 2：光标同步刷爆带宽
结论：几个人动鼠标，消息量大到通道卡死。
原因：每次 mousemove 都广播，没有节流。
解法：光标事件节流（50ms），停止移动后光标自动过期消失。

坑 3：断线重连消息重复
结论：网络抖动重连后，同一条消息出现两次。
原因：重连后重新拉取，没有按消息 id 去重。
解法：消息带唯一 id，客户端 Map 去重，重连按序号补拉。

坑 4：未读计数多端不一致
结论：手机上读了通知，电脑上未读红点还在。
原因：已读状态没有广播同步到其他端。
解法：已读操作广播，或拉取时以服务端已读游标为准。

坑 5：协作操作直接覆盖
结论：两人同时编辑，后保存的把先保存的内容盖掉。
原因：协作同步没做合并，用了整份覆盖。
解法：操作级同步 + OT/CRDT 收敛，或基于版本号做冲突检测。
```
