## 概述

实时协作让多个用户同时编辑同一份内容（文档、白板、看板），每个人的操作实时同步给其他人，最终各端收敛到一致状态。核心难题不是传输，而是「并发操作如何合并不冲突」——OT 和 CRDT 是两大主流解法。Awareness 负责「感知他人」，Sync Protocol 负责「怎么同步」。

```text
实时协作的五个关键环节：
1. OT —— 操作变换，服务端集中式合并并发操作
2. CRDT —— 无冲突数据结构，副本独立修改自动收敛
3. Conflict Resolution —— 并发冲突的解决策略
4. Awareness —— 感知协作现场：在线、光标、选中
5. Sync Protocol —— 同步协议：操作如何广播、如何落盘
```

```js
// 协作编辑的最小闭环：本地操作 → 广播 → 应用远端操作
function collaborativeEdit(socket, doc) {
  function localOp(op) {
    doc.apply(op);          // 本地立即应用
    socket.emit('op', op);  // 广播给服务端/其他人
  }
  socket.on('op', (op) => doc.apply(op)); // 应用远端操作
  return { localOp };
}
```

## OT

OT（Operational Transformation，操作变换）是实时协作的经典方案：把编辑拆成插入、删除等原子操作，服务端收到并发操作时，对操作做「变换」使它们能按统一顺序应用，保证各端结果一致。它通常需要中心服务器协调，按服务端的顺序为准。

```text
OT 的关键点：
1. 操作原子化 —— 插入、删除等基础操作
2. 变换 —— 并发操作相互变换以兼容
3. 中心协调 —— 服务端统一操作顺序
4. 成熟应用 —— Google Docs 曾用，ShareDB 等库实现
```

```js
// OT 的核心：并发操作变换
// 两个用户在相同位置插入，需要变换其中一个的位置
function transform(opA, opB) {
  // 若 A 的插入位置在 B 之前或相等，B 的位置要后移
  if (opA.position < opB.position) {
    return { ...opB, position: opB.position + opA.text.length };
  }
  return opB;
}

// 用户 A 在位置 0 插入 "a"，用户 B 在位置 0 插入 "b"
const opA = { type: 'insert', position: 0, text: 'a' };
const opB = { type: 'insert', position: 0, text: 'b' };
// 服务端先应用 A，则 B 变换为在位置 1 插入
const opB2 = transform(opA, opB); // { position: 1, text: 'b' }
```

OT 的变换逻辑复杂，处理不好就有 edge case 和并发 bug。生产环境一般用成熟的 OT 库（如 ShareDB、ot.js），别手写变换。

## CRDT

CRDT（Conflict-free Replicated Data Type）从数据结构层面消除冲突：副本各自独立修改，合并操作满足交换律和结合律，乱序合并也收敛一致。它不需要中心服务器协调，天然适合离线编辑和去中心化协作。

```text
CRDT 的关键点：
1. 无冲突设计 —— 合并必然收敛
2. 副本独立 —— 可离线编辑，之后合并
3. 无需中心 —— 不依赖服务端协调顺序
4. 适合文本 —— 序列 CRDT（如 RGA、YATA）做文本编辑
```

```js
// 序列 CRDT 的字符身份（简化示意）
// 每个字符带唯一 id，插入时引用前一个字符定位
const doc = [
  { id: 'a1', char: 'h', after: null },
  { id: 'a2', char: 'i', after: 'a1' },
];

// 在 'h' 后插入 '!'，只需引用 'a1'，与其他并发插入不冲突
function insertAfter(charId, newChar) {
  const id = crypto.randomUUID();
  doc.push({ id, char: newChar, after: charId });
  return id;
}
insertAfter('a1', '!'); // 与并发插入同一位置的另一个字符不冲突
```

CRDT 在离线场景和去中心化协作里优势明显，代价是元数据（字符 id）的存储和传输开销比 OT 高。

## Conflict Resolution

Conflict Resolution（冲突解决）决定并发修改撞车时听谁的。OT 和 CRDT 各自内置了收敛机制，但业务层仍有需要仲裁的语义——比如两个用户改了同一个标题，到底留哪个。策略从自动收敛到人工仲裁不等。

```text
冲突解决策略：
1. 自动收敛 —— CRDT 合并天然无冲突
2. 操作变换 —— OT 变换后按统一顺序应用
3. 后写覆盖 —— LWW 语义，时间戳新者赢
4. 人工仲裁 —— 冲突时提示用户选择
```

```js
// 字段级冲突：并发改同一字段，用版本号仲裁
async function updateTitle(docId, newTitle) {
  const current = await fetch(`/api/docs/${docId}`).then(r => r.json());
  const res = await fetch(`/api/docs/${docId}`, {
    method: 'PUT',
    body: JSON.stringify({ title: newTitle, version: current.version }),
  });
  if (res.status === 409) {
    // 并发冲突：提示用户，展示两份内容选择
    const remote = await res.json();
    promptResolve(remote.title, newTitle);
  }
}
```

选择哪种策略看业务：文本编辑用 CRDT/OT 自动收敛，单值字段用版本号或 LWW，重要决策让人工仲裁。

## Awareness

Awareness（感知）是协作的「现场感」：看到谁在线、谁的光标在哪、谁选中了什么、谁正在打字。它不参与内容合并，是独立于文档内容的「元状态」通道，让协作不像是盲操作。

```text
Awareness 的关键点：
1. 现场信息 —— 在线成员、光标、选中、输入中
2. 独立通道 —— 与文档内容分离
3. 高频低价值 —— 需要节流和过期清理
4. 短暂性 —— 光标停久了自动消失
```

```js
// Awareness：同步在线成员和光标（与内容同步解耦）
class Awareness {
  constructor(socket) {
    this.states = new Map(); // userId -> {cursor, name, online}
    socket.on('awareness', (e) => this.apply(e));
  }
  setLocal(state) {
    socket.emit('awareness', { userId: 'me', ...state });
  }
  apply(e) {
    if (e.online === false) this.states.delete(e.userId);
    else this.states.set(e.userId, { cursor: e.cursor, name: e.name, ts: Date.now() });
  }
}
```

Awareness 走独立通道，高频更新（光标）不能和低频的文档操作混在一个同步流里，否则互相拖累。

## Sync Protocol

Sync Protocol（同步协议）定义协作数据「如何传输、如何落盘、如何恢复」：操作以什么格式广播、如何保证顺序、如何持久化、断线后如何补拉快照。它是协作系统的骨架，决定了系统的可靠性和扩展性。

```text
Sync Protocol 的关键点：
1. 操作格式 —— 操作序列化格式（insert/delete/update）
2. 顺序保证 —— 序列号/版本号保证操作有序
3. 持久化 —— 操作日志落盘，可恢复
4. 快照 + 增量 —— 重连先拉快照，再订阅增量
```

```js
// 同步协议：断线重连后快照 + 增量恢复
class SyncClient {
  constructor(socket) {
    this.lastSeq = 0;
    this.pending = [];
  }
  connect() {
    socket.emit('sync', { since: this.lastSeq }); // 请求增量
    socket.on('snapshot', (snap) => this.applySnapshot(snap));
    socket.on('ops', (ops) => this.applyOps(ops));
  }
  applyOps(ops) {
    for (const op of ops) {
      if (op.seq > this.lastSeq) {
        doc.apply(op);
        this.lastSeq = op.seq;
      }
    }
  }
}
```

设计同步协议时先想清楚「快照 + 增量」的边界：快照多久打一次、增量日志保留多久、重连时从哪个序号补，都是可靠性关键。

## 应用场景实战

### 场景一：基于 CRDT 的离线协作编辑器

```js
// 本地 CRDT 文档 + 同步，离线也能编辑，恢复后合并
class CRDTEditor {
  constructor(doc) {
    this.doc = doc;          // 序列 CRDT
    this.unsynced = [];      // 本地未同步的操作
  }
  insert(char, afterId) {
    const op = this.doc.insert(char, afterId); // 本地应用
    this.unsynced.push(op);
    if (navigator.onLine) this.flush();
  }
  async flush() {
    for (const op of this.unsynced) {
      await fetch('/api/sync', { method: 'POST', body: JSON.stringify(op) });
    }
    this.unsynced = [];
  }
}
window.addEventListener('online', () => editor.flush());
```

### 场景二：协作白板的 Awareness 同步

```js
// 同步协作者光标与选中（Awareness），与画布内容分开
class Whiteboard {
  constructor(socket) {
    this.cursors = new Map();
    socket.on('awareness', (e) => this.onAwareness(e));
  }
  onAwareness(e) {
    if (e.type === 'cursor') this.cursors.set(e.userId, e.pos);
    if (e.type === 'leave') this.cursors.delete(e.userId);
    this.render();
  }
  reportCursor(pos) {
    socket.emit('awareness', { type: 'cursor', pos });
  }
  render() {
    for (const [userId, pos] of this.cursors) {
      drawCursor(userId, pos);
    }
  }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 文本协作优先用成熟库（ShareDB、Yjs、Automerge），别手写 OT/CRDT
2. 内容同步与 Awareness 走独立通道，高频光标别拖累文档操作
3. 断线重连先拉快照再订阅增量，用序号保证不重不漏
4. 操作日志落盘，快照 + 增量结合，支持任意时点恢复
5. 离线场景优先 CRDT，中心化低延迟场景可考虑 OT
6. 字段级冲突用版本号仲裁，重要决策留人工处理

### 踩坑记录

```text
坑 1：手写 OT 变换埋 bug
结论：某些并发操作序列下，两端文档内容不一致。
原因：OT 变换要考虑大量 edge case，手写极易漏。
解法：用 ShareDB / ot.js 等成熟实现，别自己造轮子。

坑 2：Awareness 与内容同步混流
结论：光标高频更新把文档操作同步拖慢，操作排队。
原因：高频低价值状态和低频高价值操作走同一通道。
解法：Awareness 独立通道 + 节流，内容同步单独走。

坑 3：断线重连不补拉快照
结论：断线期间的操作丢失，重连后文档缺一段。
原因：重连后只订阅了后续增量，没补断线期间的快照。
解法：重连按最后序号拉快照或增量，再继续订阅。

坑 4：CRDT 元数据膨胀
结论：文档编辑越久，同步负载越大，性能下降。
原因：CRDT 的字符 id、删除墓碑从不清理。
解法：定期压缩/GC，合并历史元数据。

坑 5：并发改单值字段无仲裁
结论：两人同时改标题，谁后提交谁覆盖，先提交的丢失。
原因：单值字段没用版本号或 LWW，直接整份覆盖。
解法：字段更新带版本号，冲突返回 409 走仲裁或提示。
```
