## 概述

实时通信让前端在不刷新、不轮询的情况下即时拿到最新数据。四种主流技术各有定位：WebSocket 是双向全双工长连接，SSE 是单向服务端推送，WebRTC 是点对点的音视频和低延迟数据通道，Long Polling 是「长连接模拟实时」的降级方案。选型的关键是「双向还是单向、要不要低延迟、穿透 NAT 吗」。

```text
四种实时通信技术对比：
1. WebSocket —— 双向、全双工、需要服务端维护连接
2. SSE —— 单向、服务端推、基于 HTTP、自动重连
3. WebRTC —— 点对点、低延迟、可传音视频、要信令
4. Long Polling —— 请求挂起等响应、兼容最好、效率低
```

```js
// 按场景选通信方式
function pickChannel(need) {
  if (need.p2p && need.lowLatency) return 'WebRTC';
  if (need.bidirectional) return 'WebSocket';
  if (need.serverPush && !need.clientSend) return 'SSE';
  return 'Long Polling'; // 兼容兜底
}
```

## WebSocket

WebSocket 在单个 TCP 连接上建立全双工通道，客户端和服务端可以随时互发消息，没有 HTTP 请求-响应的强绑定。它通过 HTTP Upgrade 握手从 101 切换到 WebSocket 协议，之后就是帧的双向流动。

```text
WebSocket 的关键点：
1. 全双工 —— 双向随时发，适合聊天、协作
2. 握手升级 —— HTTP 101 切换协议
3. 帧 —— 文本和二进制帧
4. 心跳 —— 应用层 ping/pong 保活
```

```js
// 客户端建立 WebSocket
const ws = new WebSocket('wss://example.com/ws');

ws.onopen = () => ws.send(JSON.stringify({ type: 'subscribe', channel: 'orders' }));
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  handle(msg);
};
ws.onerror = () => console.log('连接错误');
ws.onclose = (e) => scheduleReconnect(); // 断线重连
```

WebSocket 的复杂度在服务端和运维：要维护海量连接状态、处理心跳和重连、配置负载均衡支持 Upgrade。断线重连和消息补偿要应用层自己处理。

## SSE

SSE（Server-Sent Events）让服务端通过普通 HTTP 连接持续向客户端推送事件流。它只用单向（服务端→客户端），但换来简单：标准 HTTP、浏览器原生自动重连、带事件类型和消息 id。

```text
SSE 的关键点：
1. 单向 —— 只能服务端推给客户端
2. 自动重连 —— 断线后浏览器自动重连
3. 事件类型 —— event 字段区分不同流
4. 基于 HTTP —— 兼容代理、负载均衡
```

```js
// 客户端订阅 SSE 事件流
const es = new EventSource('/api/stream');

es.onopen = () => console.log('已连接');
es.addEventListener('message', (e) => console.log('默认事件', e.data));
es.addEventListener('price', (e) => console.log('价格', e.data));
es.onerror = () => console.log('连接异常，浏览器会自动重连');
```

SSE 适合股票行情、进度通知、日志流这类「只要服务端推、客户端基本不回」的场景。需要客户端频繁回传就用 WebSocket。

## WebRTC

WebRTC（Web Real-Time Communication）让浏览器之间点对点传输音视频和任意数据，不需要经过服务器中转。它天然低延迟（点对点直达），但建立连接需要信令服务器交换 SDP 和 ICE 候选，还要处理 NAT 穿透。

```text
WebRTC 的关键点：
1. 点对点 —— 数据不经过服务器，延迟低
2. 音视频 + 数据 —— 媒体流和 DataChannel 双通道
3. 信令 —— 需要外部服务器交换连接信息（SDP/ICE）
4. NAT 穿透 —— STUN/TURN 处理网络地址转换
```

```js
// 建立 DataChannel 传输数据（简化，省略信令交换）
const pc = new RTCPeerConnection(config);
const dc = pc.createDataChannel('chat');

dc.onopen = () => dc.send('hello peer');
dc.onmessage = (e) => console.log('收到:', e.data);

// 信令服务器转发 offer/answer 和 ICE candidate（略）
// pc.setLocalDescription(offer) → 信令 → peer.setRemoteDescription(offer)
```

WebRTC 最复杂的地方在连接建立（信令、ICE、NAT 穿透），一旦建立起来，点对点的低延迟是 WebSocket 中转比不了的。

## Long Polling

Long Polling（长轮询）是实时通信的「兼容兜底」：客户端发起请求，服务端不立即返回，而是挂起直到有新数据或超时才响应；客户端收到响应后立刻再发下一个请求。它用普通 HTTP 模拟实时，兼容性最好，但每次「实时推送」都要一次请求-响应，效率低。

```text
Long Polling 的关键点：
1. 请求挂起 —— 服务端有数据或超时才返回
2. 兼容性最好 —— 普通 HTTP，无特殊要求
3. 模拟实时 —— 服务端有变化立刻响应
4. 效率低 —— 每次推送一次请求，连接反复建立
```

```js
// 长轮询客户端：收到响应立刻发起下一次
async function longPoll() {
  while (true) {
    const res = await fetch('/api/long-poll');
    const data = await res.json();
    handle(data);
    // 立即发起下一次长轮询
  }
}
longPoll();
```

```text
# 服务端长轮询（Node 伪代码）：
app.get('/api/long-poll', async (req, res) => {
  const data = await waitForNewData(30_000); // 最多等 30 秒
  res.json(data); // 有新数据立即返回，超时返回空
});
```

Long Polling 是 WebSocket 和 SSE 出现前的方案，现在主要作为极端兼容环境的降级，或某些特殊网络环境下的兜底。

## 应用场景实战

### 场景一：实时聊天（WebSocket + 断线重连）

```js
// 带心跳和重连的聊天客户端
function createChat(url, handlers) {
  let ws;
  let heartbeat;

  function connect() {
    ws = new WebSocket(url);
    ws.onopen = () => {
      // 心跳保活
      heartbeat = setInterval(() => ws.send(JSON.stringify({ type: 'ping' })), 30_000);
    };
    ws.onmessage = (e) => handlers.onMessage(JSON.parse(e.data));
    ws.onclose = () => {
      clearInterval(heartbeat);
      setTimeout(connect, 1000); // 1 秒后重连
    };
  }
  connect();
  return {
    send: (msg) => ws.readyState === 1 && ws.send(JSON.stringify(msg)),
  };
}
```

### 场景二：实时行情推送（SSE）

```js
// 订阅股票价格，自动重连由浏览器处理
function subscribePrice(symbol, onPrice) {
  const es = new EventSource(`/api/quotes/${symbol}`);
  es.addEventListener('price', (e) => onPrice(JSON.parse(e.data)));
  es.onerror = () => console.log('连接断开，浏览器将自动重连');
  return () => es.close();
}

const unsub = subscribePrice('AAPL', (quote) => {
  console.log(`AAPL 最新价: ${quote.price}`);
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 双向实时用 WebSocket，单向推送用 SSE，别用长轮询硬撑实时
2. WebSocket 客户端必须处理心跳保活和断线重连，别假设连接永远在线
3. 断线重连后按最后消息序号补拉，别丢断线期间的消息
4. WebRTC 用于点对点音视频和低延迟数据，配合 STUN/TURN 处理穿透
5. 长轮询只作兼容降级，实时主力不要依赖它
6. SSE 响应要关缓冲（no-cache），否则代理会攒批延迟推送

### 踩坑记录

```text
坑 1：WebSocket 不处理断线重连
结论：网络一抖连接就断，之后再也收不到消息。
原因：只依赖 onopen 一次连接，断线后没有重连逻辑。
解法：onclose 里定时重连，配合心跳探测，恢复后补拉消息。

坑 2：SSE 被代理缓冲
结论：事件攒一批才一次性到达，实时性丧失。
原因：中间代理/网关缓冲了流式响应。
解法：响应头加 Cache-Control: no-cache、X-Accel-Buffering: no。

坑 3：长轮询连接堆积
结论：并发用户多时，服务端挂起大量长连接，资源耗尽。
原因：每个长轮询都占用一个连接，且要等超时才释放。
解法：长轮询只作兜底，主力换成 WebSocket/SSE，或限制挂起时长。

坑 4：WebRTC 忽略信令和穿透
结论：两端浏览器无法建立连接，一直卡在 connecting。
原因：没有信令服务器交换 SDP/ICE，也没有 STUN/TURN 穿透 NAT。
解法：部署信令服务器 + STUN，对称 NAT 场景加 TURN 中继。

坑 5：心跳缺失导致连接假死
结论：网络中断但没触发 onclose，连接其实已死，消息发不出去。
原因：TCP 半开连接，没有心跳探测发现异常。
解法：定时发 ping，超时无 pong 就主动断开重连。
```
