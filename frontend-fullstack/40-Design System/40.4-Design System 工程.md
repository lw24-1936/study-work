## 概述

Design System 工程化是把设计系统当作一个**可发布、可测试、可持续演进**的软件产品来维护：设计侧以 Figma 为源，工程侧以 Storybook 为组件文档与测试平台，Chromatic 做视觉回归，Token Sync 打通设计变量与代码变量的同步。

```text
Design System 工程的完整链路：
Figma（设计源） → Token Sync（变量同步） → 组件库（代码实现）
                                           ↓
                              Storybook（文档 + 开发环境）
                                           ↓
                              Chromatic（视觉回归 + 部署）
```

```text
工程化要解决的问题：
1. 设计与代码脱节 —— 用 Token Sync 统一变量
2. 组件文档缺失 —— 用 Storybook 自动生成文档
3. 视觉回归靠人眼 —— 用 Chromatic 自动截图比对
4. 组件发布与版本 —— 用 npm 包 + changesets 管理
```

## Figma

Figma 是设计系统的设计源：组件、样式、变量都定义在 Figma 里。设计系统工程师关心的关键是**命名一致**（Figma 变量名与代码 Token 名对齐）和**结构化组织**。

```text
Figma 设计系统的组织：
1. Variables —— 颜色/间距/字号等设计变量（对应代码 Design Token）
2. Styles —— 文本样式、效果样式（对应代码的类型/阴影 Token）
3. Components —— 可复用组件及 variant（对应代码组件）
4. Libraries —— 跨文件共享的组件库
```

```text
Figma Variables 的命名约定（与代码 Token 对齐）：
color/bg/primary        ↔  --color-bg-primary
color/text/secondary    ↔  --color-text-secondary
spacing/4               ↔  --space-4
radius/md               ↔  --radius-md
```

## Storybook

Storybook 是组件开发与文档平台：每个组件写多个 Story 展示不同形态，同时作为隔离开发环境和交互测试工具。

```js
// Button.stories.jsx
import { Button } from './Button';

export default {
  title: 'Components/Button',
  component: Button,
  argTypes: {
    variant: { control: 'select', options: ['primary', 'secondary', 'danger'] },
    size: { control: 'select', options: ['sm', 'md', 'lg'] },
  },
};

export const Primary = { args: { variant: 'primary', children: '提交' } };
export const Secondary = { args: { variant: 'secondary', children: '取消' } };
export const Disabled = { args: { variant: 'primary', disabled: true, children: '禁用' } };
```

```js
// 交互测试（play 函数，基于 Testing Library）
export const Clickable = {
  args: { children: '点击我' },
  play: async ({ canvasElement }) => {
    const canvas = within(canvasElement);
    await userEvent.click(canvas.getByRole('button'));
  },
};
```

## Chromatic

Chromatic 是 Storybook 官方的视觉回归与托管服务：把每个 Story 渲染截图，与基线比对，发现视觉差异；同时提供团队评审界面。

```text
Chromatic 的工作方式：
1. 每次提交 CI 自动把全部 Story 渲染成截图
2. 与已接受的基线截图逐像素比对
3. 有差异的 Story 标记出来，供人审阅（接受/拒绝）
4. 接受后更新基线，作为后续比对的参照
```

```yaml
# GitHub Actions 里跑 Chromatic
- name: Publish to Chromatic
  uses: chromaui/action@v1
  with:
    projectToken: ${{ secrets.CHROMATIC_PROJECT_TOKEN }}
    buildScriptName: build-storybook
```

## Component Documentation

组件文档要覆盖：用途、API 表格、示例、可访问性说明。Storybook 的 autodocs 能从 Props 类型自动生成 API 表格。

```jsx
// 用 JSDoc/TS 类型生成文档
export interface ButtonProps {
  /** 按钮视觉变体 */
  variant?: 'primary' | 'secondary' | 'danger';
  /** 按钮尺寸 */
  size?: 'sm' | 'md' | 'lg';
  /** 是否禁用 */
  disabled?: boolean;
}
```

```md
# Button 使用说明

用于触发操作。primary 用于主操作，secondary 用于次操作。

- 主操作每屏只出现一个 primary
- disabled 状态要说明原因
- 图标按钮必须提供 aria-label
```

## Visual Regression

视觉回归是防止组件改动破坏视觉的自动检查：对比渲染截图找出像素差异。核心策略是**用基线快照**，配合局部截图减少误报。

```text
视觉回归策略：
1. 全量截图 —— 每个 Story 一张图，比对慢但覆盖全
2. 局部截图 —— 只截组件区域，减少布局抖动误报
3. 忽略区域 —— 时间戳、动画帧等动态区域标记忽略
4. 阈值设定 —— 容忍 0.5% 以内的像素差，过滤抗锯齿噪声
```

```js
// 无 Chromatic 时用 Playwright 自建视觉回归
import { test, expect } from '@playwright/test';

test('button 视觉回归', async ({ page }) => {
  await page.goto('/iframe.html?id=button--primary');
  await expect(page.locator('.btn')).toHaveScreenshot('button-primary.png');
});
```

## Token Sync

Token Sync 打通 Figma 设计变量与代码 Token 的同步，避免设计改了颜色而代码没跟上。常见方案有 Style Dictionary、Tokens Studio、Figma Tokens。

```json
// tokens.json —— 单一 Token 源文件
{
  "color": {
    "primary": { "value": "#2563eb" },
    "text": { "value": "#1f2937" }
  },
  "space": {
    "4": { "value": "16px" }
  }
}
```

```js
// style-dictionary 把 JSON 编译成多平台产物
module.exports = {
  source: ['tokens/**/*.json'],
  platforms: {
    css: {
      transformGroup: 'css',
      buildPath: 'build/css/',
      files: [{ destination: 'variables.css', format: 'css/variables' }],
    },
    js: {
      transformGroup: 'js',
      buildPath: 'build/js/',
      files: [{ destination: 'tokens.js', format: 'javascript/es6' }],
    },
  },
};
```

## 应用场景实战

### 场景一：搭建最小 Design System 工程

```text
目录结构：
design-system/
├── tokens/            # Token 源文件（JSON）
├── src/components/    # 组件实现
├── src/stories/       # Storybook stories
├── build/             # style-dictionary 产物
└── .storybook/        # Storybook 配置
```

```bash
# 1. 初始化
npm init -y
npm i -D react react-dom @storybook/react style-dictionary

# 2. 编译 Token 到 CSS 变量
npx style-dictionary build

# 3. 启动 Storybook 开发
npx storybook dev -p 6006
```

## 最佳实践与踩坑记录

### 最佳实践

1. Figma 变量名与代码 Token 名严格对齐，用工具自动同步而非手工搬
2. Storybook Story 用 CSF3 格式，配合 argTypes 提供可视化控制
3. 视觉回归用基线快照，动态区域（时间、动画）标记忽略
4. 组件 API 类型用 TS 定义，文档从类型自动生成
5. Token 单一源文件（JSON），style-dictionary 编译成多平台产物

### 踩坑记录

```text
坑 1：Figma 变量与代码 Token 命名不一致
结论：设计改了主色，代码同步脚本对不上，变量漂移。
原因：Figma 里叫 blue-500，代码里叫 --color-primary，无映射关系。
解法：统一命名约定，用 Tokens Studio 插件按同一份 JSON 双向同步。

坑 2：视觉回归误报频繁
结论：每次提交都一堆"差异"，团队对差异麻木，真 bug 被淹没。
原因：截图包含时间戳、随机数据、抗锯齿差异等不稳定像素。
解法：局部截图 + 忽略动态区域 + 设定像素阈值，过滤噪声。

坑 3：Story 只写了默认形态
结论：组件改了 size 分支出 bug，Storybook 里看不到。
原因：每个 variant/size/state 没写对应 Story。
解法：用模板批量生成 Story 覆盖所有变体组合。

坑 4：组件文档靠手写，与实现脱节
结论：文档里的 Props 和实际组件对不上。
原因：文档手工维护，组件加了属性没同步文档。
解法：autodocs 从 TS 类型自动生成 API 表格。

坑 5：Token 编译产物提交进 Git 造成冲突
结论：多人合并时 build 产物反复冲突。
原因：style-dictionary 的生成文件也提交进仓库。
解法：build 产物加 .gitignore，只在发布时构建。
```
