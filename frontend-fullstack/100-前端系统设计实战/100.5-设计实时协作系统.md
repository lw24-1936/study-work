## 概述

实时协作系统（如在线文档、白板、多人表格）的核心挑战是「多个人同时改同一份数据，还要最终一致」。它依赖一条实时通道（WebSocket）传递变更，用 CRDT 或 OT 算法保证无锁合并，用 Presence 感知彼此在场，用离线队列兜底弱网。

```text
实时协作系统的六大支柱：
1. WebSocket —— 双向实时通道，低延迟推送变更
2. CRDT —— 无冲突数据结构，本地合并无需中心仲裁
3. Presence —— 在场感知，谁在看、谁在编辑
4. Sync —— 变更同步策略，增量推送与重连补发
5. Conflict Resolution —— 冲突解决，CRDT/OT 保证收敛
6. Offline —— 离线编辑与重连合并
```

```js
// 实时协作系统的分层架构
// 客户端：本地模型（CRDT） + 编辑操作 → 通过 WebSocket 广播
// 服务端：中心节点，转发变更 + 持久化 + 权威版本
//
// 两种经典方案：
// 1. OT（Operational Transformation）—— 基于操作变换，需要中心服务器
// 2. CRDT（Conflict-free Replicated Data Type）—— 无冲突复制，可纯 P2P
```

## WebSocket

WebSocket 提供全双工的持久连接，是实时协作的传输底座。相比 HTTP 轮询，它省去每次建连开销、服务端可主动推送。协作系统在 WebSocket 之上定义消息协议：变更（update）、在场（presence）、确认（ack）。

```js
// WebSocket 客户端封装：重连 + 心跳 + 消息分发
class RealtimeClient {
  constructor(url) {
    this.url = url;
    this.ws = null;
    this.handlers = new Map();
    this.connect();
  }

  connect() {
    this.ws = new WebSocket(this.url);
    this.ws.onopen = () => this.startHeartbeat();
    this.ws.onmessage = (e) => this.dispatch(JSON.parse(e.data));
    this.ws.onclose = () => this.reconnect();
  }

  startHeartbeat() {
    this.timer = setInterval(() => {
      if (this.ws.readyState === WebSocket.OPEN) {
        this.ws.send(JSON.stringify({ type: 'ping' }));
      }
    }, 30000);
  }

  reconnect() {
    clearInterval(this.timer);
    setTimeout(() => this.connect(), 1000 * Math.random() + 500); // 随机退避
  }

  on(type, handler) { this.handlers.set(type, handler); }
  send(type, payload) {
    this.ws.send(JSON.stringify({ type, payload }));
  }
  dispatch(msg) {
    this.handlers.get(msg.type)?.forEach((fn) => fn(msg.payload));
  }
}
```

```text
WebSocket 消息协议设计：
1. 消息分类 —— update（变更）/ presence（在场）/ ack（确认）
2. 心跳保活 —— ping/pong 检测连接存活，及时重连
3. 断线重连 —— 指数退避重连，重连后补发增量
4. 按文档分频道 —— 同一文档的协作者进同一频道
```

## CRDT

CRDT（Conflict-free Replicated Data Type）是一类「天然可合并」的数据结构：任意两个副本的修改都能自动合并，无需中心服务器仲裁冲突。文本协作常用 RGA（Replicated Growable Array）或 Yjs 的 YATA，每个字符带唯一 ID，按 ID 排序合并。

```js
// 用 Yjs 实现 CRDT 文本协作
import * as Y from 'yjs';

// 两个副本（模拟两个协作者）
const docA = new Y.Doc();
const docB = new Y.Doc();
const textA = docA.getText('content');
const textB = docB.getText('content');

// A 插入 "Hello"
textA.insert(0, 'Hello');
// B 同时插入 "World"（本地独立操作）
textB.insert(0, 'World');

// 同步：双向合并，无需中心仲裁
Y.applyUpdate(docB, Y.encodeStateAsUpdate(docA));
Y.applyUpdate(docA, Y.encodeStateAsUpdate(docB));

console.log(textA.toString());  // 两个副本都收敛到一致结果
```

```text
CRDT 的核心特性：
1. 无冲突合并 —— 任何顺序合并都收敛到同一结果
2. 无需中心服务器 —— 可 P2P，离线编辑天然支持
3. 字符带 ID —— 每个插入的字符有全局唯一 ID，按 ID 排序
4. 代表实现 —— Yjs（YATA）、Automerge、Loro
```

## Presence

Presence（在场感知）让协作者看到「谁在线、谁在看、谁的光标在哪」。它通常是一段轻量的临时状态（用户 ID、名字、颜色、光标位置、选中范围），随用户操作实时广播，不持久化。

```js
// Presence 状态与广播
// 每个协作者维护一份 presence 信息
const presenceState = {
  clientId: 'user-123',
  name: '张三',
  color: '#3b82f6',       // 分配给用户的光标颜色
  cursor: { index: 42 },   // 光标在文档中的位置
};

// 光标移动时广播（节流）
function onCursorMove(index) {
  presenceState.cursor.index = index;
  throttle(() => {
    client.send('presence', presenceState);
  }, 50)();
}

// 收到的 presence 集合 = 当前所有在线协作者
// 渲染：在编辑器里给每个协作者画不同颜色的光标和名字标签
```

```text
Presence 的设计要点：
1. 轻量临时 —— 不持久化，断开即失效
2. 高频节流 —— 光标移动要节流，避免消息风暴
3. 颜色区分 —— 每个用户分配唯一颜色，视觉可辨识
4. 超时清理 —— 心跳超时的 presence 标记为离线
```

## Sync

同步策略解决「变更如何可靠地到达所有副本」。核心是增量同步 + 版本号/序列号 + 重连补发：每个变更带递增版本号，重连后客户端上报最后已知版本，服务端补发缺失的变更。

```js
// 基于版本号的增量同步
// 服务端为每个文档维护变更日志
const changeLog = [];     // [{ version, update }]
let currentVersion = 0;

// 客户端连接时上报已同步到的版本
client.on('hello', (lastSeenVersion) => {
  // 补发 lastSeenVersion 之后的所有变更
  const missed = changeLog.filter((c) => c.version > lastSeenVersion);
  missed.forEach((c) => client.send('update', c.update));
});

// 收到新变更：追加日志 + 广播给其他客户端
function onUpdate(update) {
  const version = ++currentVersion;
  changeLog.push({ version, update });
  broadcast('update', { version, update });
}
```

```text
同步策略要点：
1. 增量同步 —— 只传变更，不传全量文档
2. 版本号 —— 变更带单调递增版本，用于检测缺失
3. 重连补发 —— 客户端上报 lastSeenVersion，服务端补发
4. 快照压缩 —— 日志过长时做快照，减少补发量
```

## Conflict Resolution

冲突解决是协作系统的灵魂。CRDT 用「数学上可交换」的操作保证收敛，OT 用「操作变换」把并发操作变成等价顺序执行。理解两者差异，才能选对方案。

```text
OT 的冲突解决（操作变换）：
1. 两个用户同时编辑同一位置
2. 服务端接收操作，变换后应用到权威版本
3. 变换保证：无论操作以何顺序到达，结果一致
```

```js
// OT 操作变换的简单示意（字符插入）
// 用户 A 在位置 5 插入 'x'，用户 B 在位置 3 插入 'y'
// 并发时：
const opA = { type: 'insert', pos: 5, char: 'x' };
const opB = { type: 'insert', pos: 3, char: 'y' };

// 变换规则：B 的操作在 A 之前应用，则 A 的位置要 +1（因为 B 插了 1 个字符）
function transform(op1, op2) {
  if (op1.type === 'insert' && op2.type === 'insert' && op1.pos >= op2.pos) {
    return { ...op1, pos: op1.pos + 1 };   // 位置后移
  }
  return op1;
}

// CRDT 则无需变换：每个字符有唯一 ID，直接按 ID 排序合并
```

```text
CRDT vs OT 的选型：
1. CRDT —— 无需中心服务器、天然离线、P2P 友好，适合去中心化
2. OT —— 需要中心服务器做权威变换，实现简单直观，历史方案成熟
3. 选型 —— 新项目优先 CRDT（Yjs），存量 OT 项目（Google Docs）保持
```

## Offline

离线支持让用户在断网时仍能编辑，重连后自动合并。CRDT 天然支持离线（本地副本随时可编辑），OT 则较复杂。离线还要处理：本地持久化草稿、重连冲突合并、离线期间的 Presence 标记。

```js
// 离线优先：本地持久化 + 重连合并（Yjs + IndexedDB）
import * as Y from 'yjs';
import { IndexeddbPersistence } from 'y-indexeddb';
import { WebsocketProvider } from 'y-websocket';

const doc = new Y.Doc();

// 本地持久化：编辑自动存 IndexedDB，断网也能继续编辑
const localPersistence = new IndexeddbPersistence('my-doc', doc);

// 网络同步：有网时通过 WebSocket 同步
const provider = new WebsocketProvider('wss://sync.acme.com', 'my-doc', doc);

// 断网：本地 IndexedDB 继续编辑，不阻塞
// 重连：provider 自动重连，Yjs 自动合并本地与远端变更
provider.on('status', (event) => {
  if (event.status === 'connected') {
    console.log('重连成功，本地离线编辑已自动合并');
  }
});
```

```text
离线支持的要点：
1. 本地可编辑 —— 变更写本地副本，不依赖网络
2. 本地持久化 —— IndexedDB 落盘，刷新不丢
3. 重连合并 —— 自动 merge 本地与远端变更
4. 冲突兜底 —— 极小概率的语义冲突提示用户处理
```

## 应用场景实战

### 场景一：搭建一个实时共享文本编辑器

```js
// 完整的最小实时协作编辑器（Yjs + y-websocket）
import * as Y from 'yjs';
import { WebsocketProvider } from 'y-websocket';
import { MonacoBinding } from 'y-monaco';
import * as monaco from 'monaco-editor';

const doc = new Y.Doc();
const ytext = doc.getText('code');

// 连接同步服务器
const provider = new WebsocketProvider('wss://sync.acme.com', 'room-1', doc);

// 绑定到 Monaco 编辑器
const editor = monaco.editor.create(document.getElementById('editor'), {
  value: '',
  language: 'javascript',
});
const binding = new MonacoBinding(ytext, editor.getModel(), new Set([editor]), provider.awareness);

// 光标在场感知：awareness 自动同步光标位置
provider.awareness.setLocalStateField('user', {
  name: '张三',
  color: '#' + Math.floor(Math.random() * 16777215).toString(16),
});
```

### 场景二：带 Presence 光标的协作文档

```js
// 渲染多个协作者的光标（基于 awareness 状态）
provider.awareness.on('change', () => {
  const states = provider.awareness.getStates();   // 所有在线协作者
  renderCursors(states);
});

function renderCursors(states) {
  clearCursors();
  states.forEach((state, clientId) => {
    if (clientId === doc.clientID) return;   // 跳过自己
    const { cursor, user } = state;
    // 在光标位置画一个带名字和颜色的标签
    drawCursor({ index: cursor.index, color: user.color, name: user.name });
  });
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 变更走增量同步 + 版本号，重连只补发缺失部分
2. 文本协作优先用 CRDT（Yjs），避免自己实现 OT 变换
3. Presence 用节流广播，光标移动 50ms 一次即可
4. 心跳 + 指数退避重连，重连后自动补发
5. 本地副本持久化到 IndexedDB，断网也能继续编辑
6. 变更日志定期做快照压缩，控制补发体积
7. 服务端做变更校验与权限控制，别盲目信任客户端

### 踩坑记录

```text
坑 1：自己手写 OT 变换算法
结论：并发编辑时文档乱序、丢字符，难以修复。
原因：OT 变换的边界情况极多，手写极易出错。
解法：用成熟的 CRDT 库（Yjs/Automerge），别造轮子。

坑 2：Presence 高频广播导致消息风暴
结论：几十人协作时光标移动消息刷屏，服务器和带宽被打爆。
原因：光标每次移动都全量广播，没有节流。
解法：光标移动节流 50ms，且只广播变化的字段。

坑 3：断线重连后全量拉取文档
结论：弱网下重连一次要拉全量文档，卡顿严重。
原因：没有增量同步，重连就全量覆盖。
解法：版本号增量补发，只传缺失的变更。

坑 4：变更日志无限增长
结论：同步服务端内存和磁盘持续膨胀。
原因：变更日志只追加不清理。
解法：定期做快照，老日志压缩，只保留快照后的增量。

坑 5：离线编辑的数据重连后直接覆盖
结论：离线编辑的内容或他人编辑被覆盖丢失。
原因：重连用了「以本地为准」的粗暴合并。
解法：用 CRDT 自动 merge，或检测冲突后提示用户选择。
```
