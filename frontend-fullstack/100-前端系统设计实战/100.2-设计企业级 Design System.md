## 概述

企业级 Design System 是一套可复用、可版本化、可测试的设计资产体系：用 Design Token 统一设计决策，用组件库落地交互，用文档与版本管理保证多团队协作的一致性。它的目标不是「做一个按钮」，而是让全公司几百个页面在视觉、交互、可访问性上保持同一套标准。

```text
Design System 的七大支柱：
1. Token —— 颜色/间距/字体的单一事实来源
2. Component —— 组件 API 稳定、组合能力强
3. Documentation —— 文档即产品，示例即契约
4. Versioning —— 语义化版本，破坏性变更可追踪
5. Accessibility —— 可访问性内建，不是事后补
6. Testing —— 视觉回归 + 单元 + 可访问性测试
7. Publishing —— 私有 registry 发布，订阅方平滑升级
```

```js
// Design System 的典型目录结构
design-system/
  tokens/           // Design Token：单一事实来源
    color.json
    spacing.json
  packages/
    core/           // 基础组件：Button、Input、Icon
    patterns/       // 复合模式：Form、Dialog、Table
    themes/         // 主题：light/dark/brand
  docs/             // 文档站点（Storybook 等）
```

## Token

Design Token 是设计系统的基石，把颜色、间距、字体、圆角等设计决策抽成命名变量，实现「改一处、全系统生效」。Token 分层（原始值 → 语义值 → 组件值）让主题切换变得简单。

```json
{
  "color": {
    "brand": {
      "500": { "value": "#3b82f6", "type": "color" },
      "600": { "value": "#2563eb", "type": "color" }
    },
    "text": {
      "primary": { "value": "{color.neutral.900}", "type": "color" },
      "secondary": { "value": "{color.neutral.600}", "type": "color" }
    }
  },
  "spacing": {
    "sm": { "value": "8px", "type": "dimension" },
    "md": { "value": "16px", "type": "dimension" },
    "lg": { "value": "24px", "type": "dimension" }
  },
  "radius": {
    "md": { "value": "8px", "type": "borderRadius" }
  }
}
```

```css
/* Token 编译产物：CSS 变量（或各平台产物） */
:root {
  --color-brand-500: #3b82f6;
  --color-text-primary: #1a1a1a;
  --spacing-md: 16px;
  --radius-md: 8px;
}

/* 暗色主题覆盖 */
[data-theme='dark'] {
  --color-text-primary: #f5f5f5;
}
```

```text
Token 三层结构：
1. 原始值（primitive）—— 具体色值/像素，如 #3b82f6
2. 语义值（semantic）—— 表达用途，如 color.text.primary
3. 组件值（component）—— 绑定到组件，如 button.bg
```

## Component

组件是 Design System 的「产品」。组件 API 要稳定、可组合、可扩展，避免每个业务团队各写一个「长得像但行为不同」的按钮。好的组件 API 强调组合（composition）而非配置（props 地狱）。

```jsx
// 组件 API 设计：组合优于配置
// 反例：props 地狱，几十个开关
// <Button type="primary" size="lg" icon="left" iconName="plus" rounded loading disabled />

// 正例：组合式 API，职责单一、可扩展
import { Button } from '@acme/design-system';

function SubmitButton() {
  return (
    <Button variant="primary" size="md" onClick={submit}>
      <Button.Icon name="send" />
      提交
    </Button>
  );
}

// 组件 Props 用 TypeScript 严格约束
type ButtonProps = {
  variant: 'primary' | 'secondary' | 'ghost';
  size: 'sm' | 'md' | 'lg';
  disabled?: boolean;
  loading?: boolean;
  children: React.ReactNode;
};
```

```text
组件设计四原则：
1. API 稳定 —— 对外接口语义化版本管理，破坏性变更走 major
2. 组合优先 —— 用子组件组合，而不是几十个 boolean props
3. 可扩展 —— 支持 ref、className、as 等透传
4. 无样式冲突 —— 样式封装在组件内，不泄漏到外部
```

## Documentation

文档是 Design System 的「门面」，决定组件能否被正确使用。文档要包含：实时可交互示例（Playground）、Props 说明、使用禁忌、可访问性说明。文档即契约，示例即测试。

```jsx
// Storybook 文档示例：Button 的 stories
import type { Meta, StoryObj } from '@storybook/react';
import { Button } from './Button';

const meta: Meta<typeof Button> = {
  title: 'Core/Button',
  component: Button,
  argTypes: {
    variant: { control: 'select', options: ['primary', 'secondary', 'ghost'] },
    size: { control: 'select', options: ['sm', 'md', 'lg'] },
  },
};
export default meta;

export const Primary: StoryObj<typeof Button> = {
  args: { variant: 'primary', children: '主按钮' },
};

export const Disabled: StoryObj<typeof Button> = {
  args: { variant: 'primary', children: '禁用', disabled: true },
};
```

```text
文档必备四要素：
1. 可交互示例 —— 用户能实时改 Props 看效果
2. Props 表格 —— 每个属性的类型、默认值、说明
3. 使用禁忌 —— 什么场景不该用这个组件
4. 可访问性 —— 键盘操作、ARIA、对比度说明
```

## Versioning

语义化版本（SemVer）是 Design System 协作的命脉。major 表示破坏性变更，minor 表示新增功能，patch 表示修复。配合 changelog 与迁移指南，让订阅方知道「升级会踩什么坑」。

```text
SemVer 规则与 Design System 的映射：
1. major（x.0.0）—— 移除/重命名组件或 Props，行为不兼容
2. minor（x.y.0）—— 新增组件或新增可选 Props
3. patch（x.y.z）—— 样式微调、bug 修复，无 API 变化
```

```yaml
# 版本发布流程：changeset 自动化
# .changeset/config.json
access: restricted
baseBranch: main
updateInternalDependencies: patch

# 一条 changeset 记录一次变更意图
# .changeset/smooth-pandas.md
---
'@acme/design-system': major
---
移除 Button 的 type 属性，改用 variant
```

## Accessibility

可访问性（a11y）必须内建到每个组件里，而不是上线后打补丁。组件要支持键盘导航、正确的 ARIA 属性、足够的颜色对比度，符合 WCAG 2.1 AA 标准。

```jsx
// 可访问性内建的组件：Dialog 的焦点管理 + ARIA
import { useEffect, useRef } from 'react';

function Dialog({ open, onClose, title, children }) {
  const panelRef = useRef(null);

  useEffect(() => {
    if (open) {
      panelRef.current?.focus();            // 焦点移入弹窗
      const onKey = (e) => e.key === 'Escape' && onClose();  // Esc 关闭
      document.addEventListener('keydown', onKey);
      return () => document.removeEventListener('keydown', onKey);
    }
  }, [open, onClose]);

  if (!open) return null;
  return (
    <div role="dialog" aria-modal="true" aria-labelledby="dlg-title">
      <div ref={panelRef} tabIndex={-1}>
        <h2 id="dlg-title">{title}</h2>
        {children}
        <button onClick={onClose}>关闭</button>
      </div>
    </div>
  );
}
```

```text
可访问性检查清单：
1. 键盘可达 —— 所有交互可 Tab 到达，可 Enter/Space 触发
2. ARIA 正确 —— role、aria-label、aria-expanded 语义准确
3. 对比度 —— 文字与背景对比度 ≥ 4.5:1（AA）
4. 焦点管理 —— 弹窗/抽屉打开时焦点正确移入移出
```

## Testing

Design System 的测试是「三层防线」：单元测试保证逻辑正确，可访问性测试保证 a11y 达标，视觉回归测试保证样式改动不回归。视觉回归用 Playwright + 截图对比。

```js
// 三层测试：单元 + a11y + 视觉回归
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { axe, toHaveNoViolations } from 'jest-axe';
import { Button } from './Button';

expect.extend(toHaveNoViolations);

test('Button 可点击并触发事件', async () => {
  const onClick = vi.fn();
  render(<Button onClick={onClick}>提交</Button>);
  await userEvent.click(screen.getByRole('button'));
  expect(onClick).toHaveBeenCalled();
});

test('Button 无严重可访问性违规', async () => {
  const { container } = render(<Button>提交</Button>);
  const results = await axe(container);
  expect(results).toHaveNoViolations();
});
```

```js
// 视觉回归测试：Playwright 截图对比
import { test, expect } from '@playwright/test';

test('Button 视觉回归', async ({ page }) => {
  await page.goto('http://localhost:6006/iframe.html?id=core-button--primary');
  const btn = page.locator('button');
  await expect(btn).toHaveScreenshot('button-primary.png');
});
```

## Publishing

发布是 Design System 落地的「最后一公里」：构建产物（ESM/CJS + 类型声明）发布到私有 npm registry，消费方按语义化版本平滑升级。多包结构用 changesets 统一管理版本。

```json
{
  "name": "@acme/design-system",
  "version": "2.3.0",
  "main": "dist/cjs/index.js",
  "module": "dist/esm/index.js",
  "types": "dist/types/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/types/index.d.ts",
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.js"
    }
  },
  "sideEffects": ["**/*.css"],
  "publishConfig": {
    "registry": "https://npm.acme.com/"
  }
}
```

```text
发布要点：
1. 双格式产物 —— ESM + CJS + .d.ts 类型声明
2. 私有 registry —— 企业内网发布，控制访问
3. 版本自动化 —— changesets 从变更集生成版本与 changelog
4. 平滑升级 —— 破坏性变更附迁移指南，废弃 API 先 deprecate
```

## 应用场景实战

### 场景一：用 Token 实现一键主题切换

```jsx
// 基于 CSS 变量的主题切换
// 1. 定义两套主题 Token
const themes = {
  light: { '--color-bg': '#ffffff', '--color-text': '#1a1a1a' },
  dark: { '--color-bg': '#111111', '--color-text': '#f5f5f5' },
};

// 2. 切换主题：给根元素设置 data-theme，CSS 变量随之切换
function toggleTheme(mode) {
  const vars = themes[mode];
  Object.entries(vars).forEach(([k, v]) => {
    document.documentElement.style.setProperty(k, v);
  });
}

// 组件只消费变量，不关心主题
// .card { background: var(--color-bg); color: var(--color-text); }
```

### 场景二：发布一个支持暗色模式的 Button 组件

```jsx
// Button 组件：消费 Token 变量，天然支持主题
import './button.css';

export function Button({ variant = 'primary', size = 'md', children, ...rest }) {
  return (
    <button className={`btn btn-${variant} btn-${size}`} {...rest}>
      {children}
    </button>
  );
}

// button.css 只消费 CSS 变量
/*
.btn {
  padding: var(--spacing-sm) var(--spacing-md);
  border-radius: var(--radius-md);
  font-size: var(--font-md);
}
.btn-primary {
  background: var(--color-brand-500);
  color: #fff;
}
.btn-ghost {
  background: transparent;
  color: var(--color-text-primary);
}
*/
```

## 最佳实践与踩坑记录

### 最佳实践

1. 所有设计决策先落 Token，组件只消费 Token 变量，杜绝硬编码色值
2. Token 分三层（原始/语义/组件），主题切换只改语义层映射
3. 组件 API 用组合式设计，避免几十个 boolean props
4. 每个组件配套 Storybook 文档，示例即契约
5. 可访问性内建，CI 里跑 axe 检查，违规即阻断
6. 用 changesets 自动化版本管理，破坏性变更必写迁移指南
7. 视觉回归测试兜底，防止「改了 A 组件 B 组件坏了」

### 踩坑记录

```text
坑 1：组件里硬编码色值
结论：改主题要逐个组件改色值，漏一处就花屏。
原因：设计决策散落在组件代码里，没有收敛到 Token。
解法：色值/间距/字体全部走 Token，组件只引用变量。

坑 2：一次发布十几个破坏性变更
结论：订阅方升级一次要改几百处，升级意愿极低。
原因：没按语义化版本拆分，破坏性变更混在 minor 里。
解法：破坏性变更集中到 major，废弃 API 先标记 deprecate。

坑 3：文档和代码不同步
结论：文档写的 Props 实际已不存在，照着文档用直接报错。
原因：文档靠手写，没有从类型/Props 自动生成。
解法：Storybook/TSDocs 从组件类型自动生成 Props 表格。

坑 4：可访问性事后补
结论：键盘用户无法操作核心组件，合规审计不过。
原因：开发时没考虑 a11y，上线后返工成本高。
解法：组件开发阶段就跑 axe，把 a11y 纳入 DoD（完成定义）。

坑 5：发布产物缺类型声明
结论：消费方 TS 项目报错，或回退到 any 失去类型安全。
原因：构建只出了 JS，没生成 .d.ts。
解法：构建产物必须包含 ESM/CJS + .d.ts，exports 正确映射。
```
