## 概述

微前端把「一个巨型 SPA」拆成「多个可独立开发、独立部署的子应用」，由宿主（Host）统一编排。它解决的是大型组织的工程问题：多个团队各自的技术栈、发布节奏、代码仓库如何在一个页面里和平共处。

```text
微前端平台的八大支柱：
1. Host —— 宿主应用，负责加载与编排子应用
2. Remote —— 远程子应用，独立开发独立部署
3. Shared —— 共享依赖，避免重复打包
4. Routing —— 路由分发，决定加载哪个子应用
5. Auth —— 统一鉴权，登录态跨子应用共享
6. Communication —— 子应用间与主应用间通信
7. Isolation —— JS/CSS/全局变量隔离
8. Deployment —— 各子应用独立发布，主应用按版本组合
```

```js
// 微前端架构总览
// Host（主应用）：负责路由、鉴权、布局，动态加载 Remote
// Remote（子应用）：各自独立的 SPA，可异构技术栈
//
// 方案选型：
// 1. Module Federation（Webpack 5）—— 构建期共享、运行时加载
// 2. single-spa —— 路由驱动，框架无关
// 3. qiankun —— 基于 single-spa，内置沙箱与样式隔离
// 4. iframe —— 最强隔离，但通信与体验成本高
```

## Host

Host（主应用/基座）是微前端的「门面」，负责：注册子应用、按路由加载、提供全局布局（导航/侧边栏）、注入全局能力（鉴权、埋点、主题）。Host 本身保持轻量，业务逻辑尽量下沉到子应用。

```js
// Host：注册并启动子应用（qiankun 风格）
import { registerMicroApps, start } from 'qiankun';

registerMicroApps([
  {
    name: 'app-user',          // 子应用名，全局唯一
    entry: '//cdn.acme.com/app-user/',   // 子应用入口
    container: '#subapp-viewport',       // 挂载容器
    activeRule: '/user',                 // 匹配到 /user 路由时激活
    props: { token: getToken(), theme: 'light' },  // 传给子应用
  },
  {
    name: 'app-order',
    entry: '//cdn.acme.com/app-order/',
    container: '#subapp-viewport',
    activeRule: '/order',
  },
]);

start();
```

```text
Host 的职责边界：
1. 路由分发 —— 把 URL 匹配到对应子应用
2. 生命周期 —— 子应用的 bootstrap/mount/unmount
3. 全局能力注入 —— 鉴权 token、埋点 SDK、主题
4. 布局编排 —— 导航、侧边栏等全局 UI
```

## Remote

Remote（子应用/微应用）是独立开发、独立部署的业务单元。每个子应用是一个完整的应用，可以有自己的技术栈、自己的依赖、自己的发布节奏，但要遵守宿主约定的生命周期接口。

```js
// 子应用：暴露生命周期钩子供宿主调用（qiankun）
// main.js
import { createApp } from 'vue';
import App from './App.vue';
import router from './router';

let instance = null;

function render(props = {}) {
  const { container, token } = props;
  instance = createApp(App);
  instance.provide('globalToken', token);   // 接收主应用注入
  instance.use(router);
  instance.mount(container ? container.querySelector('#root') : '#root');
}

// 独立运行（开发态直接访问子应用）
if (!window.__POWERED_BY_QIANKUN__) {
  render();
}

// 被宿主加载时的生命周期
export async function bootstrap() {}
export async function mount(props) { render(props); }
export async function unmount() { instance?.unmount(); instance = null; }
```

```text
子应用约束：
1. 生命周期 —— 实现 bootstrap/mount/unmount 三个钩子
2. 挂载点 —— 渲染到宿主分配的 container，不抢全局
3. 资源路径 —— 静态资源用相对路径或 publicPath 动态修正
4. 独立可运行 —— 脱离宿主也能单独开发调试
```

## Shared

共享依赖是微前端的性能关键：如果每个子应用都打包一份 React/Vue/lodash，页面会重复下载几十 MB 代码。通过 Module Federation 的 shared 配置，运行时共享同一份依赖。

```js
// Module Federation 的 shared 配置
// 主应用 webpack.config.js
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      remotes: {
        app_user: 'app_user@//cdn.acme.com/app-user/remoteEntry.js',
      },
      shared: {
        react: { singleton: true, eager: true, requiredVersion: '^18.0.0' },
        'react-dom': { singleton: true, eager: true, requiredVersion: '^18.0.0' },
        lodash: { singleton: true, requiredVersion: '^4.17.0' },
      },
    }),
  ],
};
```

```text
共享依赖三原则：
1. singleton —— 关键库（React）必须单例，否则 hooks 报错
2. 版本协商 —— requiredVersion 约束，运行时择优加载
3. 按需共享 —— 大而稳定的库共享，小而边缘的各自打包
```

## Routing

微前端路由的核心问题是「URL 如何分发给不同的子应用」。常见两种模式：主应用拥有路由（集中式）和子应用各自拥有路由（分布式）。qiankun 用 activeRule 匹配，激活对应子应用。

```js
// 路由分发：主应用路由 + activeRule 激活子应用
// 主应用路由表
const routes = [
  { path: '/user', app: 'app-user' },
  { path: '/order', app: 'app-order' },
  { path: '/user/:id', app: 'app-user' },  // 带参数的路径也归 user
];

// 子应用内部用自己的路由，主应用只负责「到 /user 就激活 user」
// 子应用 router（Vue Router）
const routes = [
  { path: '/', component: UserList },
  { path: ':id', component: UserDetail },
];
```

```text
路由分发的注意点：
1. 前缀隔离 —— 子应用路由前缀互不冲突
2. 激活规则 —— activeRule 支持函数，复杂匹配可自定义
3. 路由同步 —— 子应用内部路由变化同步到浏览器 URL
4. 刷新保持 —— 直接访问子应用深链接要能正确激活
```

## Auth

鉴权是跨子应用的头等大事。登录态（token、用户信息）由主应用统一管理，通过 props 或全局事件注入子应用，避免每个子应用各自维护登录流程、各自弹登录框。

```js
// 主应用统一鉴权，注入 token 给子应用
import { registerMicroApps } from 'qiankun';

const token = localStorage.getItem('token');
const user = JSON.parse(localStorage.getItem('user') || 'null');

registerMicroApps([
  {
    name: 'app-order',
    entry: '//cdn.acme.com/app-order/',
    container: '#subapp-viewport',
    activeRule: '/order',
    props: { token, user, onLogout: handleLogout },
  },
]);

// 子应用接收并消费
export async function mount(props) {
  const { token, user } = props;
  axios.defaults.headers.Authorization = `Bearer ${token}`;
  render({ token, user });
}
```

```text
鉴权统一策略：
1. 登录入口唯一 —— 登录/登出只在主应用，子应用不重复实现
2. token 注入 —— 通过 props 传给子应用，子应用只消费
3. 失效统一处理 —— 401 由主应用统一跳登录页
4. 权限下发 —— 菜单/权限由主应用下发，子应用按权限渲染
```

## Communication

子应用之间、主应用与子应用之间需要通信：全局事件总线、自定义事件、props 下发、共享 store 都是可选方案。原则是「能 props 下发的不用全局事件，能事件解耦的不共享 store」。

```js
// 方案一：全局事件总线（自定义事件）
// 主应用广播
window.dispatchEvent(new CustomEvent('user:logout'));

// 子应用订阅
window.addEventListener('user:logout', () => {
  clearLocalState();
  redirectToLogin();
});

// 方案二：主应用提供的通信 API（通过 props 注入）
// 主应用
const actions = {
  onGlobalStateChange: (cb) => store.subscribe(cb),
  setGlobalState: (state) => store.setState(state),
};
// 传给子应用：props.actions.setGlobalState({ theme: 'dark' })

// 方案三：共享 store（zookeeper 式，慎用，耦合强）
```

```text
通信选型原则：
1. 主 → 子：props 下发（token、主题、配置）
2. 子 → 主：回调或事件上抛（标题、埋点）
3. 子 ↔ 子：事件总线解耦，避免直接互相依赖
4. 共享 store：仅限强一致的全局状态，能不用就不用
```

## Isolation

隔离是微前端最容易踩坑的地方：子应用的全局变量、CSS 样式、事件监听会互相污染。JS 隔离用沙箱（Proxy 代理 window），CSS 隔离用 Shadow DOM 或样式前缀，事件要能正确卸载。

```js
// JS 沙箱：Proxy 代理 window，隔离全局变量（qiankun 核心思路）
function createSandbox() {
  const fakeWindow = new Proxy(window, {
    get(target, key) {
      return sandboxProps[key] ?? target[key];
    },
    set(target, key, value) {
      sandboxProps[key] = value;   // 写入沙箱，不污染真实 window
      return true;
    },
  });
  const sandboxProps = {};
  return { fakeWindow, sandboxProps };
}

// 子应用 unmount 时清理：全局事件、定时器、MutationObserver
export async function unmount() {
  instance?.unmount();
  window.removeEventListener('resize', onResize);   // 清理事件
  clearInterval(timer);                              // 清理定时器
}
```

```text
隔离三件套：
1. JS 隔离 —— Proxy 沙箱，子应用全局变量互不干扰
2. CSS 隔离 —— Shadow DOM 或 scoped 样式，防止样式串扰
3. 副作用清理 —— unmount 时清事件、定时器、Observer
```

## Deployment

微前端的部署优势在于「独立发布」：每个子应用独立构建、独立上 CDN、独立回滚，互不阻塞。主应用通过入口地址（remoteEntry 或 entry）加载子应用，更新子应用无需重新发布主应用。

```yaml
# 子应用独立部署流水线
stages:
  - build
  - deploy

build:
  script:
    - npm ci
    - npm run build            # 产出子应用静态资源 + remoteEntry.js
  artifacts:
    paths: [dist/]

deploy:
  script:
    - npm run upload-cdn       # 上传到独立目录 /app-user/<version>/
  environment: production
```

```text
部署要点：
1. 独立发布 —— 子应用各自 CI/CD，互不阻塞
2. 版本化路径 —— 子应用资源放 /app-name/<version>/，支持回滚
3. 入口稳定 —— remoteEntry 地址稳定，主应用无需改动
4. 灰度发布 —— 按版本组合子应用，灰度放量
```

## 应用场景实战

### 场景一：搭建一个最小可运行的 qiankun 主应用

```js
// 主应用：加载两个子应用，按路由激活
import { registerMicroApps, start } from 'qiankun';

const apps = [
  {
    name: 'app-user',
    entry: '//localhost:7101',       // 子应用 dev server
    container: '#subapp-viewport',
    activeRule: '/user',
  },
  {
    name: 'app-order',
    entry: '//localhost:7102',
    container: '#subapp-viewport',
    activeRule: '/order',
  },
];

registerMicroApps(apps, {
  beforeLoad: [async (app) => console.log('加载前', app.name)],
  afterMount: [async (app) => console.log('挂载后', app.name)],
});

start({ prefetch: true });   // 预加载子应用资源
```

### 场景二：Module Federation 的 remote 消费

```jsx
// 主应用动态加载远程组件（Module Federation）
import { lazy, Suspense } from 'react';

// webpack 配置里声明 remote 后，可直接 import
const RemoteHeader = lazy(() => import('app_header/Header'));

function HomePage() {
  return (
    <div>
      <Suspense fallback={<div>加载远程组件...</div>}>
        <RemoteHeader title="首页" />
      </Suspense>
      <main>主应用内容</main>
    </div>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 子应用必须暴露 bootstrap/mount/unmount 生命周期，卸载时清理副作用
2. 关键依赖（React/Vue）用 singleton 共享，避免多实例导致的报错
3. 登录态由主应用统一管理，token 通过 props 注入子应用
4. 子应用路由加独立前缀，避免互相冲突
5. CSS 用隔离方案，防止全局样式互相污染
6. 通信优先 props + 事件总线，共享 store 只在必要时用
7. 子应用独立部署、独立回滚，主应用通过稳定入口加载

### 踩坑记录

```text
坑 1：React 多实例导致 hooks 报错
结论：子应用报 Invalid hook call 或状态不同步。
原因：主应用和子应用各打了一份 React，违反单例原则。
解法：shared 里 react/react-dom 设 singleton: true，运行时共享。

坑 2：子应用卸载后全局事件还在
结论：切换子应用后，旧子应用的监听器仍在触发，内存泄漏。
原因：unmount 钩子没清理 addEventListener/定时器/Observer。
解法：unmount 里显式清理所有全局副作用。

坑 3：CSS 全局污染
结论：A 子应用的样式影响了 B 子应用的同名 class。
原因：两个子应用的全局 CSS 作用到同一个 document。
解法：启用 CSS 隔离（Shadow DOM/scoped），或规范 BEM 前缀。

坑 4：子应用资源 404（publicPath 问题）
结论：子应用被主应用加载后，chunk 和图片加载失败。
原因：子应用按绝对路径 / 引用资源，挂到主应用后路径错位。
解法：设置正确的 publicPath，或用运行时动态修正资源路径。

坑 5：子应用路由与主应用路由冲突
结论：两个子应用都匹配 / 根路径，激活错乱。
原因：没有给子应用分配独立的路由前缀。
解法：每个子应用分配唯一前缀，主应用按前缀激活。
```
