## 概述

前端监控平台把「用户浏览器里发生了什么」从黑盒变成白盒：采集 JS 错误、性能指标、接口耗时、用户行为，配合 Source Map 还原线上报错位置，再通过告警把问题第一时间推到开发者面前。它的核心是「可观测性」——不仅能发现问题，还能定位根因。

```text
前端监控平台的七大支柱：
1. Error —— 捕获 JS 错误、Promise 拒绝、资源加载失败
2. Performance —— 采集页面加载与交互性能指标
3. RUM —— 真实用户监控，还原真实用户体验
4. Metrics —— 指标定义、聚合与多维下钻
5. Trace —— 全链路追踪，关联前后端调用
6. Source Map —— 还原压缩后的报错堆栈到源码位置
7. Alert —— 阈值告警，及时通知责任人
```

```js
// 监控平台数据流总览
// 采集 SDK（浏览器） → 上报（批量/采样） → 接入层（去重/清洗）
// → 存储（时序/日志） → 分析（聚合/下钻） → 展示（大盘/告警）
```

## Error

错误监控是监控平台的基石：捕获三类错误——运行时错误（window.onerror）、Promise 拒绝（unhandledrejection）、资源加载失败（error 事件捕获），并采集堆栈、上下文、用户信息一起上报。

```js
// 前端错误采集 SDK（核心部分）
function initErrorMonitor() {
  // 1. 运行时错误：window.onerror 捕获同步错误 + 堆栈
  window.addEventListener('error', (event) => {
    const { message, filename, lineno, colno, error } = event;
    report({
      type: 'error',
      message,
      stack: error?.stack,
      source: `${filename}:${lineno}:${colno}`,
      url: location.href,
      userAgent: navigator.userAgent,
      timestamp: Date.now(),
    });
  }, true);   // 捕获阶段，能拿到资源加载错误

  // 2. Promise 拒绝：unhandledrejection 捕获异步错误
  window.addEventListener('unhandledrejection', (event) => {
    report({
      type: 'unhandledrejection',
      message: event.reason?.message || String(event.reason),
      stack: event.reason?.stack,
      url: location.href,
      timestamp: Date.now(),
    });
  });

  // 3. 接口错误：包装 fetch/axios 捕获请求失败
  const originFetch = window.fetch;
  window.fetch = async (...args) => {
    const start = Date.now();
    try {
      const res = await originFetch(...args);
      if (res.status >= 400) {
        report({ type: 'api-error', url: args[0], status: res.status, duration: Date.now() - start });
      }
      return res;
    } catch (err) {
      report({ type: 'api-error', url: args[0], message: err.message });
      throw err;
    }
  };
}
```

```text
错误采集三要素：
1. 错误本身 —— 消息、堆栈、错误类型
2. 发生环境 —— URL、UserAgent、浏览器版本、设备
3. 用户上下文 —— 用户 ID、操作轨迹（面包屑）、版本号
```

## Performance

性能监控采集页面从开始加载到可交互的完整时间线：导航计时（Navigation Timing）、资源计时（Resource Timing）、Web Vitals（LCP/FID/CLS/INP）。这些数据回答「页面到底快不快、慢在哪」。

```js
// 性能数据采集
function initPerformanceMonitor() {
  // 1. 导航计时：页面加载各阶段耗时
  window.addEventListener('load', () => {
    const nav = performance.getEntriesByType('navigation')[0];
    report({
      type: 'navigation',
      dns: nav.domainLookupEnd - nav.domainLookupStart,
      tcp: nav.connectEnd - nav.connectStart,
      ttfb: nav.responseStart - nav.requestStart,
      domReady: nav.domContentLoadedEventEnd - nav.fetchStart,
      load: nav.loadEventEnd - nav.fetchStart,
    });
  });

  // 2. Web Vitals：LCP / CLS / INP
  new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      report({ type: 'vital', name: entry.name, value: entry.value });
    }
  }).observe({ entryTypes: ['largest-contentful-paint', 'layout-shift'] });

  // 3. 资源计时：慢资源的加载耗时
  new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      if (entry.duration > 1000) {   // 超过 1s 的资源上报
        report({ type: 'resource', name: entry.name, duration: entry.duration });
      }
    }
  }).observe({ entryTypes: ['resource'] });
}
```

```text
性能监控的核心指标：
1. LCP —— 最大内容绘制，衡量首屏可见速度
2. INP —— 交互到下一次绘制，衡量交互响应
3. CLS —— 累积布局偏移，衡量视觉稳定性
4. TTFB —— 首字节时间，衡量服务端响应
```

## RUM

RUM（Real User Monitoring，真实用户监控）采集真实用户的真实体验数据，与实验室数据（Lighthouse/Synthetic）互补。它按用户维度（设备、网络、地区）聚合，回答「真实用户到底体验如何、哪些用户最慢」。

```js
// RUM：按用户维度采集与聚合
function initRUM() {
  // 采集每个真实用户的会话数据
  const session = {
    sessionId: generateId(),
    device: getDeviceType(),        // mobile/desktop/tablet
    network: navigator.connection?.effectiveType,   // 4g/3g/2g
    region: undefined,              // 由接入层按 IP 解析
    userAgent: navigator.userAgent,
    startTime: Date.now(),
    vitals: {},                     // 会话内的 Web Vitals
    errors: 0,                      // 会话内错误数
  };

  // 会话结束/页面卸载时上报
  window.addEventListener('pagehide', () => {
    report({ type: 'rum-session', ...session, duration: Date.now() - session.startTime });
  });
}
```

```text
RUM 的价值：
1. 真实分布 —— LCP 的 P75/P95，而非平均值
2. 维度下钻 —— 按设备/网络/地区定位最慢人群
3. 关联体验 —— 性能与转化率、跳出率关联分析
4. 对比基线 —— 发版前后的体验变化对比
```

## Metrics

指标（Metrics）是监控平台的「度量单位」，需要统一命名、类型（计数器/直方图/仪表）与聚合方式。好的指标设计让告警和看板都能复用，支持多维标签（label）下钻。

```text
前端监控常用指标类型：
1. Counter（计数器）—— 只增不减：错误数、请求数
2. Histogram（直方图）—— 分布统计：LCP 分布、接口耗时分布
3. Gauge（仪表）—— 瞬时值：当前在线用户数、当前错误率
```

```js
// 指标定义与上报（Prometheus 风格 label）
const metrics = {
  // 错误总数（Counter），带错误类型标签
  js_error_total: { type: 'counter', labels: ['errorType'] },
  // LCP 直方图（Histogram），分桶统计
  lcp_seconds: { type: 'histogram', buckets: [0.5, 1, 1.5, 2.5, 4] },
  // 当前在线用户（Gauge）
  online_users: { type: 'gauge' },
};

function record(name, value, labels = {}) {
  report({ type: 'metric', name, value, labels, timestamp: Date.now() });
}

record('js_error_total', 1, { errorType: 'TypeError' });
record('lcp_seconds', 2.3);
```

```text
指标设计原则：
1. 命名规范 —— 带单位（_seconds/_total），语义清晰
2. 多维标签 —— 错误类型、页面、版本号做 label
3. 聚合方式 —— 看分布用直方图，看总量用计数器
4. 基数控制 —— label 取值不要过高，避免存储爆炸
```

## Trace

全链路追踪（Trace）把一次用户请求从前端到后端串起来：前端请求带 Trace ID，后端日志记录同一 ID，出问题时能沿着调用链定位是前端问题还是后端问题。前端监控与后端 APM 通过 Trace ID 打通。

```js
// 前端生成并传播 Trace ID
const traceId = generateTraceId();   // 唯一标识一次用户操作链路

// 1. 注入到 HTTP 请求头，后端据此关联日志
function tracedFetch(url, options = {}) {
  const headers = { ...options.headers, 'X-Trace-Id': traceId };
  return fetch(url, { ...options, headers });
}

// 2. 前端上报日志也带 Trace ID
function report(payload) {
  payload.traceId = traceId;
  payload.spanId = generateSpanId();
  navigator.sendBeacon('/collect', JSON.stringify(payload));
}

// 3. 页面跳转时透传 Trace ID（SPA 内保持同一链路）
router.afterEach((to) => {
  to.query.traceId = traceId;
});
```

```text
Trace 的串联方式：
1. Trace ID —— 一次用户操作生成一个，贯穿整个链路
2. Span —— 链路上的每个环节（前端请求、后端处理）
3. 请求头透传 —— X-Trace-Id 传给后端，后端日志记录
4. 关联查询 —— 前端监控和 APM 用同一 Trace ID 关联
```

## Source Map

Source Map 把压缩混淆后的线上代码映射回源码，让报错堆栈从「一行压缩代码」变成「源码文件 + 行号 + 列号」。监控平台在收到错误堆栈后，用 Source Map 自动还原，开发者直接看到可读的报错位置。

```js
// 构建时生成 Source Map，上传到监控平台
// vite.config.js
export default defineConfig({
  build: {
    sourcemap: 'hidden',   // 生成 .map 但不引用（不暴露给普通用户）
  },
});

// 发布流程：把 .map 文件上传到监控平台（不上传到 CDN 公开目录）
// scripts/upload-sourcemap.js
async function uploadSourceMap() {
  const mapFiles = await glob('dist/assets/**/*.map');
  for (const file of mapFiles) {
    await monitorSDK.uploadSourceMap(file, { version: getReleaseVersion() });
  }
}
```

```text
Source Map 的正确姿势：
1. sourcemap: hidden —— 生成 .map 但不公开引用
2. .map 不进 CDN —— 只上传到监控平台，避免源码泄露
3. 版本关联 —— .map 与发布版本对应，还原时按版本匹配
4. 定期清理 —— 老版本 .map 超过保留期清理
```

## Alert

告警把「指标异常」变成「即时通知」。合理的告警要：设对阈值（避免误报）、分级（P0/P1/P2）、收敛（同类告警聚合）、可行动（通知到能处理的人）。告警太少漏问题，太多则狼来了。

```yaml
# 告警规则示例（Prometheus Alertmanager 风格）
groups:
  - name: frontend
    rules:
      # 错误率告警：5 分钟内错误率 > 1% 触发
      - alert: HighErrorRate
        expr: sum(rate(js_error_total[5m])) / sum(rate(page_view_total[5m])) > 0.01
        for: 5m
        labels:
          severity: P1
        annotations:
          summary: "JS 错误率超过 1%"

      # LCP 告警：P75 超过 4 秒
      - alert: SlowLCP
        expr: histogram_quantile(0.75, rate(lcp_seconds_bucket[10m])) > 4
        for: 10m
        labels:
          severity: P2
        annotations:
          summary: "LCP P75 超过 4 秒"
```

```text
告警设计四原则：
1. 阈值合理 —— 基于历史基线，避免频繁误报
2. 分级处理 —— P0 立即电话，P1 工单，P2 观察
3. 收敛去重 —— 同类告警聚合，防止告警风暴
4. 关联上下文 —— 告警附带 Trace ID、版本号、影响面
```

## 应用场景实战

### 场景一：一个完整的前端错误采集 SDK

```js
// 最小可用的错误采集 SDK
class Monitor {
  constructor(config) {
    this.config = config;
    this.init();
  }

  init() {
    this.captureError();
    this.captureRejection();
  }

  captureError() {
    window.addEventListener('error', (e) => {
      this.report({
        type: 'error',
        message: e.message,
        stack: e.error?.stack,
        source: `${e.filename}:${e.lineno}:${e.colno}`,
      });
    }, true);
  }

  captureRejection() {
    window.addEventListener('unhandledrejection', (e) => {
      this.report({
        type: 'unhandledrejection',
        message: String(e.reason),
        stack: e.reason?.stack,
      });
    });
  }

  report(data) {
    const payload = {
      ...data,
      appId: this.config.appId,
      version: this.config.version,
      url: location.href,
      timestamp: Date.now(),
    };
    // 用 sendBeacon 保证页面卸载时也能上报
    if (navigator.sendBeacon) {
      navigator.sendBeacon(this.config.endpoint, JSON.stringify(payload));
    } else {
      fetch(this.config.endpoint, { method: 'POST', body: JSON.stringify(payload) });
    }
  }
}

// 使用
new Monitor({ appId: 'shop-web', version: 'v2.1.0', endpoint: '/collect' });
```

### 场景二：用 Source Map 还原线上报错堆栈

```js
// 服务端/监控平台：收到报错堆栈后用 Source Map 还原
const sourceMap = require('source-map');

async function restoreStack(minifiedStack, sourceMapContent) {
  const consumer = await new sourceMap.SourceMapConsumer(sourceMapContent);

  // 报错堆栈是压缩后的行列号，逐行映射回源码
  const frames = minifiedStack.map((frame) => {
    const original = consumer.originalPositionFor({
      line: frame.line,
      column: frame.column,
    });
    return {
      source: original.source,           // 源码文件
      line: original.line,               // 源码行号
      column: original.column,           // 源码列号
      name: original.name,               // 原始函数名
    };
  });

  consumer.destroy();
  return frames;
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 错误采集带用户 ID 和操作面包屑，方便复现定位
2. 上报用 sendBeacon，页面卸载/崩溃时也能送达
3. 性能指标看分布（P75/P95），别只看平均值
4. Source Map 用 hidden 模式，只上传监控平台不进 CDN
5. 前端请求带 Trace ID，打通前后端全链路
6. 上报做采样与批量，避免海量数据压垮服务
7. 告警设合理阈值 + 分级 + 收敛，避免告警疲劳

### 踩坑记录

```text
坑 1：Source Map 上传到 CDN 公开目录
结论：线上源码被公开，业务逻辑泄露。
原因：构建产物连同 .map 一起发布到 CDN。
解法：sourcemap: hidden，.map 只上传监控平台。

坑 2：上报用普通 fetch 导致卸载时丢失
结论：页面关闭瞬间的错误/埋点经常丢，数据不全。
原因：fetch 在页面卸载时可能被中断。
解法：用 navigator.sendBeacon，浏览器保证送达。

坑 3：错误堆栈是压缩代码，定位困难
结论：报错显示 bundle.js:1:5234，看不懂是哪行源码。
原因：线上代码经过压缩混淆，没有还原 Source Map。
解法：构建生成 hidden Source Map，监控平台自动还原。

坑 4：告警阈值拍脑袋，误报频繁
结论：每天收到大量告警，团队对告警麻木。
原因：阈值没基于历史基线，且没做分级收敛。
解法：基于基线设阈值，分级处理，同类告警聚合。

坑 5：埋点 label 基数爆炸
结论：存储成本飙升，查询变慢。
原因：用 userId 这种高基数字段做 label。
解法：label 用低基数字段（页面/版本/设备），高基数放日志。
```
