## 概述

HTTP（HyperText Transfer Protocol）是 Web 的基石协议，浏览器和服务器之间的一切交互——页面、接口、资源——都通过它完成。它是前端工程师最该吃透的协议：请求和响应的结构、方法语义、状态码含义，直接影响接口设计、调试和性能优化。这篇笔记覆盖 HTTP 的版本演进、报文结构、方法语义和状态码，Header 的细节在 02.6 展开，HTTPS 在 02.7 展开。

```text
HTTP 的核心特征：
1. 无状态 —— 每个请求独立，服务器不记得上次（靠 Cookie/Token 补状态）
2. 基于请求-响应 —— 客户端发请求，服务器回响应
3. 可扩展 —— 通过 Header 和 Method 自由扩展语义
4. 文本可读 —— HTTP/1.x 报文是明文文本，可直接阅读调试
```

## HTTP 版本演进

HTTP 从 0.9 到 3，核心演进主线是「提升性能」：

```text
HTTP/0.9（1991）：
只有 GET，只返回 HTML，没有 Header、没有状态码。
请求就是一行：GET /index.html

HTTP/1.0（1996）：
引入 Header、状态码、POST/HEAD 等方法，支持多资源类型。
每个请求一个独立的 TCP 连接（短连接），用完即关。

HTTP/1.1（1997，至今最普及）：
1. 持久连接（Keep-Alive）—— 默认复用 TCP 连接，避免频繁握手
2. 管线化（Pipelining）—— 一个连接上排队发多个请求（因队头阻塞基本没用起来）
3. 分块传输（Chunked）—— 支持流式响应
4. Host 头 —— 一个 IP 上虚拟主机多个域名
5. 缓存增强 —— Cache-Control、ETag 等

HTTP/2（2015）：
1. 二进制分帧 —— 报文改成二进制帧，不再纯文本
2. 多路复用 —— 一个连接并发多个请求，无队头阻塞（应用层）
3. 头部压缩（HPACK）—— 请求头压缩，减少重复传输
4. 服务器推送（Server Push）—— 服务器主动推资源（实际少用）
5. 流优先级 —— 关键资源优先传输

HTTP/3（2022）：
底层从 TCP 换成 QUIC（UDP），解决 TCP 层的队头阻塞，
连接建立更快、连接迁移不断线（详见 02.3-UDP）。
```

```text
版本协商：
HTTP/1.1 靠 Upgrade/协商；HTTPS 下 HTTP/2 靠 ALPN（TLS 握手时协商）；
HTTP/3 靠 Alt-Svc 响应头告知，浏览器自动升级。
```

```text
HTTP/1.1 vs HTTP/2 的关键差异（前端视角）：
1.1 每个域名限 6 个并发连接，多请求排队 → 要域名分片、雪碧图、合并
2.0 一个连接多路复用 → 上述优化手段反而可能有害（见踩坑）
```

```text
前端何时真正受益于 HTTP/2：
1. 多小文件（大量 JS/CSS/图片）—— 多路复用收益最大
2. 需要加密（HTTPS）—— HTTP/2 主流实现都要求 TLS
3. 高延迟链路 —— 单连接减少握手次数
```

## Request 与 Response

HTTP 报文分请求（Request）和响应（Response），都由「起始行 + Header + Body」组成。

### Request 请求报文

```http
POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...

{"name": "张三", "email": "zhang@example.com"}
```

```text
请求报文结构：
1. 请求行 —— 方法 + 路径 + 协议版本（POST /api/users HTTP/1.1）
2. 请求头（Header）—— 元信息，键值对
3. 空行 —— 分隔 Header 和 Body
4. 请求体（Body）—— 数据（GET 通常没有，POST/PUT/PATCH 有）
```

### Response 响应报文

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-cache
Content-Length: 87

{"id": 1, "name": "张三", "email": "zhang@example.com"}
```

```text
响应报文结构：
1. 状态行 —— 协议版本 + 状态码 + 原因短语（HTTP/1.1 200 OK）
2. 响应头（Header）—— 元信息
3. 空行
4. 响应体（Body）—— 数据（HTML/JSON/二进制等）
```

### Header 与 Body

```text
Header（头）—— 描述请求/响应的元信息，键值对，大小写不敏感。
                 常见头见 02.6-HTTP Header。

Body（体）—— 实际传输的数据，格式由 Content-Type 声明。
             格式：JSON、表单、XML、HTML、二进制（文件/图片）等。
```

```text
Header 与 Body 的分隔：
一个空行（CRLF CRLF）分隔。调试时看报文，空行之后就是 Body。
```

## Method 与语义

HTTP 方法定义了对资源的操作语义。RESTful 设计的关键就是用对方法。

```text
常用方法：
GET     —— 获取资源（幂等、安全、可缓存）
POST    —— 创建资源 / 提交数据（非幂等）
PUT     —— 整体替换资源（幂等）
PATCH   —— 部分更新资源（非幂等，语义上比 PUT 轻）
DELETE  —— 删除资源（幂等）
OPTIONS —— 预检请求，查询服务器支持的方法（CORS 预检）
HEAD    —— 同 GET 但只返回 Header，不返回 Body（探测资源）
```

```text
幂等性（Idempotent）：
多次执行结果相同。GET/PUT/DELETE 幂等，POST/PATCH 通常非幂等。
幂等是重试安全的基础——网络失败自动重试幂等请求不会产生副作用。
```

```text
GET vs POST（最常被问的对比）：
| 维度     | GET              | POST            |
|----------|------------------|-----------------|
| 语义     | 获取资源         | 创建/提交       |
| 数据位置 | URL 查询串       | 请求体          |
| 缓存     | 可缓存           | 默认不缓存      |
| 幂等     | 是               | 否              |
| 安全性   | 数据暴露在 URL   | 数据在 Body     |
| 长度限制 | URL 长度受限     | Body 基本不限   |
```

```text
方法的安全性与实践：
1. GET 只用于读取，不产生副作用（不要用 GET 做删除/修改）
2. 删除/修改操作用对应方法，不要全用 POST
3. 敏感数据（密码、token）不放 URL（GET 会进日志和浏览器历史）
4. PATCH 表达部分更新，PUT 表达整体替换，语义要区分
```

```text
OPTIONS 与 CORS 预检：
跨域请求时，浏览器先发 OPTIONS 预检（Preflight），询问服务器是否允许
该请求（方法、Header）。服务器通过 Access-Control-* 头应答。
非简单请求（自定义 Header、PUT/DELETE、JSON 等）都会触发预检。
```

## Status Code 状态码

状态码是响应的第一行，三部分：2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误。

```text
2xx 成功：
200 OK           —— 请求成功（GET/POST 通用）
201 Created      —— 资源创建成功（POST 创建后返回）
204 No Content   —— 成功但无返回体（DELETE 常见）
206 Partial Content —— 部分内容（断点续传、Range 请求）

3xx 重定向：
301 Moved Permanently —— 永久重定向（资源永久搬家，浏览器缓存）
302 Found         —— 临时重定向（历史遗留，语义模糊）
303 See Other     —— 见其他资源（POST 后重定向到 GET）
304 Not Modified  —— 缓存有效，用本地缓存（配合 ETag/Last-Modified）
307 Temporary Redirect —— 临时重定向（保持方法不变）
308 Permanent Redirect —— 永久重定向（保持方法不变）

4xx 客户端错误：
400 Bad Request  —— 请求格式错误（参数校验失败）
401 Unauthorized —— 未认证（没登录/凭证无效）
403 Forbidden    —— 已认证但无权限（权限不足）
404 Not Found    —— 资源不存在
405 Method Not Allowed —— 方法不允许
408 Request Timeout —— 请求超时
409 Conflict     —— 冲突（如并发修改）
429 Too Many Requests —— 请求过多（限流）

5xx 服务端错误：
500 Internal Server Error —— 服务器内部错误（通用）
501 Not Implemented —— 未实现
502 Bad Gateway   —— 网关错误（上游服务异常）
503 Service Unavailable —— 服务不可用（过载/维护）
504 Gateway Timeout —— 网关超时（上游响应慢）
```

```text
301 vs 302 vs 307 vs 308（易混淆）：
301/308 —— 永久重定向（浏览器会缓存，SEO 用 301）
302/307 —— 临时重定向
302 —— 部分浏览器会把 POST 改成 GET，语义模糊
307/308 —— 严格保持方法不变（POST 还是 POST）
```

```text
401 vs 403（易混淆）：
401 —— 没登录/凭证无效，需要认证
403 —— 已登录但没权限，认证了也不让你访问
```

```text
前端如何处理状态码：
1. 401 —— 引导重新登录、刷新 token
2. 403 —— 提示无权限
3. 404 —— 提示资源不存在（接口或路由）
4. 429 —— 按 Retry-After 头限流重试
5. 5xx —— 提示服务异常，做重试或降级
```

## 应用场景实战

### 场景一：设计一个符合 HTTP 语义的 RESTful 接口

```text
用户资源 /api/users：

GET    /api/users          → 200，用户列表
GET    /api/users/1        → 200，单个用户；不存在 → 404
POST   /api/users          → 201，创建成功，返回新资源（Location 头）
PUT    /api/users/1        → 200，整体替换
PATCH  /api/users/1        → 200，部分更新
DELETE /api/users/1        → 204，删除成功（无返回体）

错误响应规范：
400 —— 参数校验失败（附具体错误信息）
401 —— 未登录
403 —— 无权限
404 —— 资源不存在
409 —— 冲突（如邮箱已注册）
```

```js
// 前端按状态码分支处理
async function request(url, options) {
  const res = await fetch(url, options);
  if (res.status === 204) return null;
  const data = await res.json().catch(() => null);

  if (res.ok) return data;
  if (res.status === 401) { /* 跳登录 */ }
  if (res.status === 403) { throw new Error('无权限'); }
  if (res.status === 429) {
    const retryAfter = res.headers.get('Retry-After');
    throw new Error(`限流，${retryAfter}秒后重试`);
  }
  throw new Error(data?.message || `请求失败(${res.status})`);
}
```

### 场景二：用 curl 手写 HTTP 报文调试接口

```bash
# GET 请求，只看响应头（HEAD 语义）
curl -I https://example.com/api/users

# 完整查看请求和响应头
curl -v https://example.com/api/users

# POST JSON
curl -X POST https://example.com/api/users \
  -H "Content-Type: application/json" \
  -d '{"name":"张三","email":"zhang@example.com"}'

# 查看状态码和耗时（排查性能）
curl -o /dev/null -s -w "%{http_code} %{time_total}s\n" https://example.com
```

## 最佳实践与踩坑记录

### 最佳实践

1. 按 HTTP 语义用方法：GET 读、POST 建、PUT 替换、PATCH 更新、DELETE 删，不用 GET 做写操作
2. 错误响应带明确状态码和结构化错误信息，前端按状态码分支处理而非全当失败
3. 敏感数据只放 Body，不放 URL（URL 会进日志、历史记录、Referer）
4. 幂等接口（GET/PUT/DELETE）可安全重试；非幂等接口重试要加幂等键
5. 生产环境走 HTTP/2+，压测验证多路复用收益；不再需要域名分片/雪碧图等 1.1 时代的优化

### 踩坑记录

```text
坑 1：用 GET 做删除/修改操作
结论：接口被爬虫、预加载、浏览器历史重放误触发，数据被误删/误改。
原因：GET 语义是只读，但实现成了写操作，且 GET 会被缓存和预取。
解法：写操作用 POST/DELETE 等方法，GET 严格只读。

坑 2：302 重定向把 POST 变 GET
结论：POST 请求被 302 重定向后方法变成 GET，请求体丢失。
原因：302 历史语义不严格，部分客户端会把重定向后的请求改成 GET。
解法：需要保持方法的场景用 307/308，POST 后跳转用 303（语义明确转 GET）。

坑 3：状态码 200 但业务失败
结论：接口一直返回 200，错误信息塞在响应体里，前端无法用 res.ok 判断。
原因：后端把所有响应都返回 200，用自定义 code 字段表达错误。
解法：错误用真实状态码（400/401/404/500 等），前端按状态码统一处理。

坑 4：升级 HTTP/2 后反而变慢
结论：改成 HTTP/2 后页面加载没变快甚至更慢。
原因：HTTP/2 多路复用下，还沿用 HTTP/1.1 的域名分片、雪碧图、资源合并，
反而破坏缓存和并行度。
解法：HTTP/2 下取消域名分片和合并，让资源独立缓存、并行传输。

坑 5：HTTP 缓存头配错导致「改了不生效」
结论：改完前端资源，用户还是看到旧版本。
原因：强缓存（Cache-Control: max-age 过大）导致浏览器不重新请求。
解法：HTML 用协商缓存或 no-cache，带 hash 的静态资源用长强缓存（见 02.6 缓存相关头）。
```
