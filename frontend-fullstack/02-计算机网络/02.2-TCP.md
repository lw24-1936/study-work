## 概述

TCP（Transmission Control Protocol）是面向连接、可靠的字节流传输协议，HTTP/1.1、HTTP/2、WebSocket、数据库连接都跑在它上面。它是前端性能的底层决定因素——页面加载的很多时间都花在「建立 TCP 连接」和「TCP 传输」上。这篇笔记讲清 TCP 的三大机制：连接管理（握手/挥手）、可靠性（重传）、流量与拥塞控制，以及前端最常遇到的「粘包拆包」问题。

```text
TCP 的核心特性：
1. 面向连接 —— 通信前先握手建立连接
2. 可靠传输 —— 有序、不丢、不重，靠确认和重传保证
3. 字节流 —— 数据是连续的字节流，没有消息边界
4. 全双工 —— 双向可同时收发
```

## TCP 报文结构与标志位

TCP 报文头（20 字节固定）里，前端需要理解的关键字段：

```text
源端口/目标端口（Source/Dest Port）—— 各 16 位，标识应用
序号（Sequence Number）—— 本报文段数据的第一个字节序号
确认号（ACK Number）—— 期望收到对方的下一个字节序号
标志位（Flags）—— SYN/ACK/FIN/RST 等控制位
窗口大小（Window）—— 接收方还能接收多少数据（流量控制）
```

### 标志位

```text
SYN —— 建立连接（三次握手的发起）
ACK —— 确认（绝大多数报文都带）
FIN —— 关闭连接（四次挥手的发起）
RST —— 强制重置连接（异常中断）
PSH —— 催促尽快交付数据
URG —— 紧急数据
```

### Sequence 与 ACK Number

这两个字段是 TCP 可靠性和有序性的基础：

```text
Sequence（序号）：
每个字节都有序号。发送方给本段第一个字节编号，接收方按序号重排。

ACK Number（确认号）：
确认号 = 已收到的字节序号 + 1，表示「这个序号之前的字节我都收到了，
期望下一个是这个序号」。

例子：A 发了 100 字节（序号 1~100），B 回 ACK Number=101，
表示「1~100 都收到了，接下来请发 101」。
```

### Window

窗口大小字段是接收方「还能收多少」的广告，是流量控制的直接手段。

## 三次握手

TCP 建立连接需要三次握手，目的是双方确认彼此的收发能力，并同步初始序号。

```text
三次握手过程：
1. 客户端 → 服务端：SYN（seq=x）
   「我要建立连接，我的初始序号是 x」
2. 服务端 → 客户端：SYN + ACK（seq=y, ack=x+1）
   「收到，我的初始序号是 y，我确认你的 x」
3. 客户端 → 服务端：ACK（ack=y+1）
   「收到，连接建立完成」
```

```text
为什么是三次而不是两次：
两次握手无法防止「历史失效连接请求」被错误建立。
第三次握手的 ACK 让双方都确认了对方的接收能力。

类比：电话沟通
1. A：「喂，听得到吗？」（SYN）
2. B：「听得到，你能听到我吗？」（SYN+ACK）
3. A：「能听到，开始说吧」（ACK）
```

```text
三次握手对前端性能的影响：
每次新 TCP 连接都要一个 RTT（往返时间）才能开始发数据。
HTTPS 还要叠加 TLS 握手。这就是为什么「减少连接数、复用连接」能显著提速。
```

## 四次挥手

TCP 是全双工的，关闭连接需要双方各自关闭自己的发送方向，所以是四次挥手。

```text
四次挥手过程：
1. 主动方 → 被动方：FIN（「我数据发完了，要关闭」）
2. 被动方 → 主动方：ACK（「收到你的 FIN」）
3. 被动方 → 主动方：FIN（「我这边也发完了，要关闭」）
4. 主动方 → 被动方：ACK（「收到，确认关闭」）
```

```text
为什么是四次不是三次：
ACK 和 FIN 分开发，是因为被动方收到 FIN 时可能还有数据没发完，
先 ACK 表示「知道了」，等数据发完再发 FIN。
（如果被动方没数据要发，2、3 步可合并，实际变三次）
```

```text
TIME_WAIT 状态：
主动关闭方挥手后进入 TIME_WAIT，等待 2MSL（约 60 秒）才真正释放。
作用：确保最后的 ACK 送达，让旧连接的延迟报文在网络中消失。
大量 TIME_WAIT 是服务器高并发下的常见问题。
```

```text
挥手后的状态流转：
主动方：FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
被动方：CLOSE_WAIT → LAST_ACK → CLOSED

CLOSE_WAIT 堆积 = 被动方收到 FIN 后没主动 close 连接（应用层 bug）。
```

## 流量控制

流量控制（Flow Control）防止「发送太快，接收方处理不过来」，由**接收方**主导，通过窗口大小实现。

```text
滑动窗口机制：
接收方在 ACK 里带上窗口大小（Window），告诉发送方「我还能收多少」。
发送方根据窗口大小控制发送速率，窗口为 0 时暂停发送。

窗口大小动态调整 —— 接收方应用处理越快，窗口越大，发送越快。
```

```text
流量控制 vs 拥塞控制：
流量控制 —— 点对点，防止「接收方」被淹没（端到端）
拥塞控制 —— 全局，防止「网络」被淹没（全网拥塞）

一个是接收方能力，一个是网络承受力。
```

## 拥塞控制

拥塞控制（Congestion Control）防止「发送太快导致网络拥塞」，由**发送方**主导，通过维护拥塞窗口（cwnd）实现。

```text
拥塞窗口 cwnd：
发送方实际发送量 = min(cwnd, 接收方窗口)。
cwnd 根据网络状况动态调整。
```

四个核心算法：

```text
1. 慢启动（Slow Start）
   连接刚建立时 cwnd 很小，每收到一个 ACK 指数级增长（1→2→4→8...），
   快速探测网络带宽，直到达到阈值（ssthresh）。

2. 拥塞避免（Congestion Avoidance）
   cwnd 超过阈值后改为线性增长（每次 +1），缓慢逼近极限。

3. 快重传（Fast Retransmit）
   收到 3 个重复 ACK，不等超时立即重传丢失的段。

4. 快恢复（Fast Recovery）
   快重传后不回到慢启动，而是把 cwnd 减半进入拥塞避免，
   避免网络抖动时吞吐量断崖下跌。
```

```text
拥塞控制对前端的意义：
1. 慢启动解释了「小文件加载慢、大文件下载先慢后快」——带宽是逐步「爬」上去的
2. 丢包会触发拥塞控制降速，弱网环境（移动端）体验骤降
3. 复用已有连接（HTTP/1.1 keep-alive、HTTP/2 多路复用）可跳过慢启动，
   这就是连接复用提速的底层原因
```

## 重传机制

TCP 通过重传保证可靠性。触发重传的两种方式：

```text
1. 超时重传（RTO）
   发送后启动计时器，超时未收到 ACK 就重传。
   RTO 动态计算（RTT 的加权平均），超时时间逐步翻倍。

2. 快重传（收到 3 个重复 ACK）
   不依赖超时，收到 3 个重复 ACK 说明中间有段丢了，立即重传。
   比超时重传快得多，是现代 TCP 的主要重传手段。
```

```text
SACK（Selective ACK）：
选择性确认，告诉发送方「哪些段收到了，哪些丢了」，
只重传真正丢失的段，避免不必要的全量重传。
```

## Keep Alive 与 TCP 半连接

### Keep Alive

TCP Keep Alive 是连接空闲时的探活机制，防止「死连接」长期占用资源。

```text
TCP Keep Alive：
连接空闲一段时间后，发送探测包确认对方是否还活着。
默认间隔很长（2 小时），应用层一般自己实现更短的心跳。
```

```text
TCP Keep Alive vs HTTP Keep-Alive（易混淆）：
TCP Keep Alive    —— 传输层探活，检测死连接
HTTP Keep-Alive   —— 复用同一个 TCP 连接发多个 HTTP 请求
两者只是名字像，完全是两回事。
```

### TCP 半连接

半连接（半开连接）指连接一方已关闭或异常，另一方不知情。

```text
两种半连接场景：
1. SYN 洪泛导致的「半连接队列」—— 服务端收到 SYN 回了 SYN+ACK，
   但客户端不完成第三次握手，服务端把这些未完成的连接放半连接队列。
   SYN 攻击就是刷爆这个队列（DDoS 常见手段）。

2. 应用层半开 —— 一方进程崩溃/断电，没发 FIN，另一方仍以为连接正常，
   直到超时才发现。
```

```text
SYN Flood 防护：
SYN Cookie —— 不分配资源，把连接信息编码进 SYN+ACK 的序号里，
收到 ACK 才真正建连接。缓解 SYN 洪泛。
```

## TCP 粘包与拆包

TCP 是字节流协议，没有消息边界。应用层「一次 write 的数据」和「一次 read 到的数据」没有对应关系，就产生粘包和拆包。

```text
粘包 —— 多个消息的数据连在一起，接收方一次读到（黏住了）
拆包 —— 一个消息的数据被拆成多段，分多次才读完

原因：
1. 发送方：Nagle 算法把多个小数据合并成一个包发（粘包）
2. 接收方：读取不及时，多个包积压在缓冲区（粘包）
3. 数据包超过 MTU 被分片，或网络分段（拆包）
```

```text
解决方案 —— 应用层定界：
1. 固定长度 —— 每条消息固定字节数
2. 分隔符 —— 消息间用特殊字符分隔（如 \n）
3. 长度前缀 —— 每条消息前加长度字段（最常见，如 4 字节长度 + 数据）
```

```text
前端场景：
WebSocket 底层是 TCP，但 WebSocket 协议自带帧（frame）定义，
帧头含长度和 opcode，浏览器自动处理粘包拆包，开发者感知不到。

只有自己基于 TCP 写自定义协议（Node.js 的 net 模块、Socket 通信）时，
才需要手动处理粘包拆包。
```

```js
// Node.js net 模块处理粘包拆包（长度前缀方案）
const net = require('net');

const server = net.createServer((socket) => {
  let buffer = Buffer.alloc(0);
  socket.on('data', (chunk) => {
    buffer = Buffer.concat([buffer, chunk]);
    // 4 字节长度前缀 + 数据
    while (buffer.length >= 4) {
      const len = buffer.readUInt32BE(0);
      if (buffer.length < 4 + len) break; // 数据还没收全（拆包）
      const message = buffer.slice(4, 4 + len);
      console.log('收到消息:', message.toString());
      buffer = buffer.slice(4 + len);
    }
  });
});
server.listen(3000);
```

## 应用场景实战

### 场景一：分析一次完整的页面请求

```text
浏览器访问 https://example.com 的网络时序：
1. DNS 解析 example.com → IP（UDP，详见 02.4）
2. TCP 三次握手（1 RTT）
3. TLS 握手（HTTPS，1-2 RTT）
4. 发送 HTTP 请求，慢启动阶段逐步提速
5. 服务端响应，TCP 有序传输 + 确认
6. 空闲后连接 keep-alive 保持，供后续请求复用
7. 页面加载完，连接保留一段时间后四次挥手关闭

性能优化方向：
- 减少握手次数（连接复用、HTTP/2 多路复用）
- 减少传输数据（压缩、缓存）
- 提升网络质量（CDN 就近接入，降低 RTT）
```

### 场景二：排查接口偶发超时

```bash
# 用 tcpdump 抓包分析 TCP 层发生了什么
sudo tcpdump -i eth0 host 93.184.216.34 and port 443 -w capture.pcap

# 关注点：
# 1. 是否有大量重传（网络丢包）
# 2. 握手是否正常完成（SYN 是否被丢弃）
# 3. 是否频繁断开重连（keep-alive 失效）
# 4. RTT 是否过高（延迟大）
```

```text
判断依据：
- 重传多 + RTT 高 → 网络质量差（丢包/拥塞）
- 握手慢 → 服务器或链路问题
- 频繁挥手重连 → keep-alive 没生效，连接被提前关闭
```

## 最佳实践与踩坑记录

### 最佳实践

1. 前端复用连接：HTTP/1.1 开 keep-alive，HTTP/2 天然多路复用，跳过慢启动和握手开销
2. 关键资源（HTML/CSS/JS）走 HTTP/2 或就近 CDN，降低 RTT 和握手次数
3. 移动端弱网场景优先考虑减少请求数和传输体积，TCP 在丢包下吞吐会骤降
4. 自定义 TCP 协议（Node net/Socket）必须处理粘包拆包，用长度前缀方案
5. 服务端关注 TIME_WAIT/CLOSE_WAIT 堆积，这是连接泄漏的常见信号

### 踩坑记录

```text
坑 1：TCP Keep Alive 和 HTTP Keep-Alive 混淆
结论：以为开了 TCP Keep Alive 就能复用连接，实际连接还是每次新建。
原因：两者是不同层的东西，复用连接靠的是 HTTP 层的 Keep-Alive 或 HTTP/2。
解法：前端复用连接看 HTTP 层的 keep-alive/多路复用，TCP Keep Alive 只用于探活。

坑 2：长连接（WebSocket）在 NAT 设备下被静默断开
结论：WebSocket 连接空闲一段时间后「假死」，消息发不出去。
原因：NAT 有连接空闲超时（几十秒到几分钟），超时后映射被清除，双方都不知情。
解法：应用层心跳（WebSocket ping/pong 或业务心跳），间隔小于 NAT 超时时间。

坑 3：移动弱网下接口超时但服务端日志正常
结论：客户端超时了，服务端却处理成功了。
原因：丢包触发 TCP 重传 + 拥塞控制降速，数据没及时送达，客户端先超时。
解法：弱网场景加大超时时间、做幂等重试（防止重复提交），或换更可靠的信道。

坑 4：CLOSE_WAIT 堆积导致连接耗尽
结论：服务端连接数持续上涨，最终无法建立新连接。
原因：服务端收到 FIN 后没调用 close，连接卡在 CLOSE_WAIT（应用层 bug）。
解法：排查服务端代码，确保收到对端关闭后及时关闭 socket。

坑 5：自建 TCP 服务出现消息「串台」
结论：收到的消息内容错乱、粘连。
原因：没处理粘包拆包，把字节流当消息边界用。
解法：用长度前缀或分隔符定界，按协议解析完整消息。
```
