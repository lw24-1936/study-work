## 概述

HTTP Header 是报文的元信息，承载了缓存策略、身份凭证、内容协商、安全策略等核心能力。前端调试接口、排查缓存问题、处理跨域和 Cookie，都是在和 Header 打交道。这篇笔记按用途把常用 Header 分组讲清楚：它们是什么、怎么用、有哪些坑。

```text
Header 的分类（按用途）：
1. 请求头 —— 请求方告知服务器的信息（Host、User-Agent、Accept、Authorization）
2. 响应头 —— 服务器告知客户端的元信息（Set-Cookie、ETag、CSP）
3. 实体头 —— 描述 Body 本身的头（Content-Type、Content-Length）
```

## 请求头：Host、User-Agent、Accept、Authorization

### Host

Host 指定请求的目标主机（域名和端口），是 HTTP/1.1 唯一必需的请求头，支撑「一个 IP 上跑多个域名」的虚拟主机。

```http
Host: www.example.com
```

```text
Host 的作用：
1. 虚拟主机 —— 同一台服务器根据 Host 区分不同站点（Nginx server_name 匹配）
2. 反向代理 —— 网关根据 Host 路由到不同后端服务
3. HTTP/2 用 :authority 伪头替代，但语义相同
```

### User-Agent

User-Agent（UA）标识客户端（浏览器、设备、爬虫）的信息。

```http
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ...
```

```text
User-Agent 的用途和坑：
1. 用途 —— 服务端据此做设备适配、统计、爬虫识别
2. 坑 —— UA 可伪造（爬虫伪装成浏览器），不可作为安全依据
3. 历史包袱 —— UA 字符串里一堆 Mozilla/WebKit 是历史兼容的产物
```

### Accept

Accept 系列头用于内容协商（Content Negotiation），客户端声明自己能接受什么。

```http
Accept: text/html, application/json;q=0.9, */*;q=0.8
Accept-Encoding: gzip, deflate, br
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
```

```text
Accept 系列：
Accept           —— 能接受的响应内容类型（MIME）
Accept-Encoding  —— 能接受的压缩算法（gzip/br）
Accept-Language  —— 能接受的语言

q 值（0~1）表示优先级，q 越高越优先，默认 q=1。
```

```text
前端相关：
Accept-Encoding 决定服务器是否返回压缩内容（gzip/br 压缩是重要优化）。
```

### Authorization

Authorization 携带身份凭证，用于认证。

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
Authorization: Basic dXNlcjpwYXNz   # base64 编码的 user:pass
```

```text
认证方式：
Bearer Token —— JWT 等 token（现代主流）
Basic        —— base64 编码用户名密码（明文等价，必须配 HTTPS）
```

```text
Authorization vs Cookie（认证的两种载体）：
Authorization —— 显式带凭证，前后端分离 / 移动端常用
Cookie        —— 浏览器自动携带，传统 Web 会话常用
详见 50-前端认证与权限。
```

## 实体头：Content-Type、Content-Length

### Content-Type

Content-Type 声明 Body 的媒体类型（MIME）和编码，告诉接收方怎么解析 Body。

```http
Content-Type: application/json
Content-Type: application/json; charset=utf-8
Content-Type: text/html; charset=utf-8
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary
```

```text
常见 Content-Type：
application/json       —— JSON 数据（API 主流）
application/x-www-form-urlencoded —— 表单（键值对 URL 编码）
multipart/form-data   —— 文件上传
text/html / text/plain —— 文本
application/octet-stream —— 二进制流（下载文件）
```

```text
前端相关坑：
1. 请求 JSON 必须带 Content-Type: application/json，否则后端可能解析不到
2. 文件上传用 FormData，浏览器自动设 multipart/form-data（别手动设）
3. charset 编码不一致会导致中文乱码（见 02.1 的编码坑）
```

### Content-Length

Content-Length 声明 Body 的字节长度，让接收方知道 Body 何时结束。

```text
Content-Length 的意义：
1. 定长 Body 用 Content-Length 标明边界
2. 动态内容（不知道长度）用 Transfer-Encoding: chunked 分块传输
3. 两者互斥，不能同时出现
```

```text
Content-Length 的坑：
长度算错会导致 Body 截断或粘包（和 TCP 粘包类似的边界问题）。
压缩后长度变化、编码字节数（中文 UTF-8 占 3 字节）都要算对。
```

## Cookie 相关：Cookie、Set-Cookie

Cookie 是 HTTP 的状态保持机制，弥补 HTTP 无状态的问题。

```text
Set-Cookie（响应头，服务器下发给浏览器）：
Set-Cookie: sessionId=abc123; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600

Cookie（请求头，浏览器回传）：
Cookie: sessionId=abc123; theme=dark
```

```text
Set-Cookie 的关键属性：
Name=Value  —— 键值对
Domain      —— 生效域名（默认当前域）
Path        —— 生效路径（默认当前路径）
Max-Age     —— 存活秒数（相对）
Expires     —— 过期时间（绝对，和 Max-Age 二选一）
HttpOnly    —— 禁止 JS 读取（document.cookie 读不到），防 XSS 窃取
Secure      —— 只在 HTTPS 下传输
SameSite    —— 跨站限制（Strict/Lax/None），防 CSRF
```

```text
SameSite 三值：
Strict —— 跨站请求完全不带 Cookie（最严）
Lax    —— 顶层导航（点链接）带，跨站子请求不带（默认，防 CSRF 推荐）
None   —— 跨站都带（必须同时配 Secure，用于第三方场景）
```

```text
Cookie 的工作流程：
1. 服务器 Set-Cookie 下发
2. 浏览器存储（按 Domain/Path 归集）
3. 后续请求自动在 Cookie 头回传（满足 Domain/Path/SameSite 规则时）
```

```text
Cookie 的局限（催生 Web Storage 的原因）：
1. 每次请求都自动携带（同域），增加请求体积
2. 大小限制（约 4KB）
3. 只有字符串，无结构化存储
详见 20-浏览器存储。
```

## 缓存相关头

HTTP 缓存由请求头和响应头配合完成，是前端性能优化的核心。

```text
强缓存（不发请求，直接用本地缓存）：
Cache-Control: max-age=31536000    —— 缓存一年（配合 immutable）
Cache-Control: no-store            —— 完全不缓存
Cache-Control: no-cache            —— 可缓存但每次要协商验证

协商缓存（发请求，304 则用本地缓存）：
ETag / If-None-Match           —— 资源版本标识，精确校验
Last-Modified / If-Modified-Since —— 资源修改时间，秒级校验
```

```text
Cache-Control 的指令：
max-age=N     —— 缓存 N 秒（相对，优先级高于 Expires）
no-store      —— 禁止缓存（敏感数据）
no-cache      —— 可缓存，但使用前必须验证（协商缓存）
must-revalidate —— 过期后必须重新验证
public/private —— 可被中间缓存（CDN）存 / 只能浏览器存
immutable     —— 资源永不变，过期前不验证（配合 hash 文件名）
```

```text
强缓存 vs 协商缓存的流程：
请求资源：
1. 有强缓存且未过期 → 直接用本地（200 from cache，不发请求）
2. 强缓存过期/需验证 → 带 If-None-Match 发请求
   - 服务器返回 304 → 用本地缓存（省 Body 传输）
   - 服务器返回 200 → 下载新内容
```

```text
ETag 与 Last-Modified 对比：
ETag          —— 内容哈希，精确到内容变化（推荐）
Last-Modified —— 修改时间，秒级精度，内容不变但时间变了也会失效

两者都有时 ETag 优先。
```

```text
前端缓存最佳实践：
1. HTML 用 no-cache（每次协商），保证入口最新
2. 带 hash 的静态资源（app.abc123.js）用 max-age 长期缓存 + immutable
3. 不带 hash 的资源设短缓存或 no-cache
4. 接口数据按场景：实时数据 no-store，可复用数据短 max-age
```

## 安全与跨域：Origin、Referer、CSP、CORS

### Origin 与 Referer

两个头都和「请求来源」相关，但粒度不同。

```text
Referer —— 完整来源 URL（含路径和参数），拼写错误是历史遗留（正确是 Referrer）
Origin  —— 只有协议 + 域名 + 端口（不含路径），更「干净」

对比：
Referer: https://example.com/page/detail?id=1
Origin:  https://example.com
```

```text
用途与风险：
1. 防盗链 —— 服务端校验 Referer，拒绝非本站来源（但可伪造）
2. 统计 —— 分析流量来源
3. 隐私风险 —— Referer 可能泄露 URL 里的敏感参数（token、id）

缓解：
Referrer-Policy 响应头控制 Referer 的发送粒度
（no-referrer / strict-origin / no-referrer-when-downgrade 等）。
```

### CSP

CSP（Content-Security-Policy）是响应头，声明允许加载哪些资源、执行哪些脚本，是防 XSS 的核心防线。

```http
Content-Security-Policy: default-src 'self'; script-src 'self' cdn.example.com; img-src *;
```

```text
CSP 的核心指令：
default-src —— 默认来源
script-src  —— 脚本来源（'self' 只允许同源，'unsafe-inline' 允许内联）
style-src   —— 样式来源
img-src     —— 图片来源
connect-src —— fetch/XHR/WebSocket 来源
frame-src   —— iframe 来源
```

```text
CSP 防 XSS 的原理：
即使攻击者注入了 <script>，只要不在 script-src 白名单里，浏览器也拒绝执行。
用 'nonce-xxx' 或 hash 允许可信内联脚本。
详见 49-Web 安全高级。
```

### CORS

CORS（Cross-Origin Resource Sharing）是跨域资源共享机制，通过一组 Header 控制跨域访问。

```text
CORS 响应头（服务器返回）：
Access-Control-Allow-Origin    —— 允许的来源（* 或具体域名）
Access-Control-Allow-Methods   —— 允许的方法（GET,POST,PUT,DELETE）
Access-Control-Allow-Headers   —— 允许的请求头
Access-Control-Allow-Credentials —— 是否允许携带 Cookie（true 时 Origin 不能是 *）
Access-Control-Max-Age         —— 预检结果缓存时间

CORS 请求头（浏览器自动加）：
Origin             —— 标识来源
Access-Control-Request-Method  —— 预检时询问方法
Access-Control-Request-Headers —— 预检时询问头
```

```text
简单请求 vs 预检请求：
简单请求 —— GET/HEAD/POST + 标准头，直接发，浏览器校验响应头
预检请求 —— 其他方法或自定义头，先发 OPTIONS 预检，通过后才发真实请求

触发预检：PUT/DELETE、JSON 的 Content-Type、自定义 Header（如 token）
```

```text
CORS 的本质：
跨域限制是浏览器的安全策略（同源策略），不是服务器的限制。
服务器用 Access-Control-Allow-Origin 声明「我允许谁跨域访问我」。
请求本身能发出去，响应被浏览器拦截（若没 CORS 头）。
```

## Range 与 Connection

### Range

Range 请求头用于断点续传和分块下载，配合 206 Partial Content。

```http
Range: bytes=0-1023        # 前 1024 字节
Range: bytes=1024-         # 从 1024 到结尾
Range: bytes=-500          # 最后 500 字节
```

```text
Range 的用途：
1. 断点续传 —— 大文件下载中断后从断点继续
2. 视频拖动 —— 视频播放器按需请求片段
3. 分片下载 —— 多线程并发下载同一文件的不同片段
```

### Connection

Connection 头控制连接的保持和关闭。

```http
Connection: keep-alive   # 保持连接（HTTP/1.1 默认）
Connection: close        # 本次请求后关闭连接
```

```text
Connection 相关：
1. keep-alive —— HTTP/1.1 复用连接（HTTP/2 已废弃此头，改由协议层管理）
2. Upgrade —— 协议升级（如 HTTP → WebSocket）
   Connection: Upgrade + Upgrade: websocket
```

## 应用场景实战

### 场景一：前端资源缓存策略配置

```text
静态资源部署的缓存策略（Nginx 示例）：
1. HTML 入口 —— 协商缓存（每次验证，保证最新）
   add_header Cache-Control "no-cache";

2. 带 hash 的资源 —— 长期强缓存（内容变了 hash 变，URL 变）
   location ~* \.(js|css)$ {
     add_header Cache-Control "max-age=31536000, immutable";
   }

3. 图片/字体 —— 长期缓存
   location ~* \.(png|jpg|woff2)$ {
     add_header Cache-Control "max-age=31536000";
   }
```

```text
原理：
文件名带内容 hash，内容不变 URL 不变（强缓存命中），
内容变化 URL 变化（自动请求新文件），HTML 用协商缓存保证引用到最新的资源 URL。
```

### 场景二：用 curl 查看和调试 Header

```bash
# 查看响应头
curl -I https://example.com

# 查看完整请求/响应头
curl -v https://example.com/api/users

# 测试缓存：带 If-None-Match 发条件请求
curl -i -H "If-None-Match: \"abc123\"" https://example.com/app.js
# 返回 304 说明缓存有效

# 测试 CORS：带 Origin 看响应头
curl -i -H "Origin: https://other.com" https://example.com/api
# 看 Access-Control-Allow-Origin 是否包含 other.com

# 测试 Range：断点续传
curl -i -H "Range: bytes=0-99" https://example.com/file.zip
# 返回 206 和指定片段
```

## 最佳实践与踩坑记录

### 最佳实践

1. 带 hash 静态资源用 immutable 长期缓存，HTML 用 no-cache 协商缓存
2. Cookie 一律加 HttpOnly + Secure，写操作场景加 SameSite=Lax 防 CSRF
3. 请求 JSON 显式带 Content-Type: application/json，文件上传用 FormData 别手动设 Content-Type
4. CSP 用 'nonce'/'hash' 而非 'unsafe-inline'，缩小脚本执行面
5. CORS 用具体域名而非 *（尤其涉及 Cookie 时必须配 Allow-Credentials + 具体 Origin）
6. Referrer-Policy 设 strict-origin-when-cross-origin，避免泄露 URL 参数

### 踩坑记录

```text
坑 1：Cache-Control 配错导致资源更新不生效
结论：发版后用户仍加载旧 JS/CSS。
原因：强缓存 max-age 过大，浏览器不重新请求。
解法：HTML no-cache + 静态资源 hash 文件名 + immutable 的组合策略。

坑 2：Cookie 没设 HttpOnly 被 XSS 窃取
结论：sessionId 被注入脚本通过 document.cookie 偷走。
原因：Cookie 未加 HttpOnly，JS 可读取。
解法：认证 Cookie 一律 HttpOnly + Secure，配合 CSP 降低 XSS 风险。

坑 3：CORS 配了 * 又想带 Cookie 失败
结论：Allow-Origin: * 时请求带不上 Cookie。
原因：CORS 规范要求 Allow-Credentials 时不能用 *，必须用具体域名。
解法：带凭证的跨域请求配具体 Origin + Access-Control-Allow-Credentials: true。

坑 4：文件上传手动设了错误的 Content-Type
结论：后端解析 multipart 失败。
原因：手动设 multipart/form-data 但没带 boundary，后端无法解析。
解法：用 FormData 让浏览器自动生成完整 Content-Type（含 boundary），不要手动设置。

坑 5：Content-Length 与 Body 字节数不符导致解析错乱
结论：接口返回被截断或粘连。
原因：Content-Length 算错（没算压缩后长度，或中文按 1 字节算）。
解法：让框架自动计算 Content-Length，手动构造报文时用字节长度（Buffer.byteLength）。

坑 6：Referer 泄露了 URL 里的 token
结论：登录 token 出现在第三方网站的访问日志里。
原因：URL 带 token（如 ?token=xxx），跨域跳转时 Referer 把完整 URL 传给第三方。
解法：敏感数据不放 URL；配 Referrer-Policy 收紧 Referer 发送。
```
