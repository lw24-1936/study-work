## 概述

HTTPS 是「HTTP + TLS 加密」，解决 HTTP 明文传输的三大问题：窃听、篡改、冒充。它是现代 Web 的默认形态——没有 HTTPS，浏览器会标记「不安全」，很多 API（地理位置、摄像头、Service Worker、HTTP/2）直接拒绝工作。这篇笔记讲 HTTPS 的底层 TLS 协议、密码学原理、证书体系和握手流程。

```text
HTTPS 解决的三个问题：
1. 机密性 —— 内容加密，第三方看不到（防窃听）
2. 完整性 —— 内容不可篡改（防中间人改包）
3. 身份认证 —— 确认「你真的是 example.com」（防冒充）
```

## HTTPS 与 TLS/SSL

```text
SSL（Secure Sockets Layer）：
Netscape 提出的加密协议，有 1.0/2.0/3.0 版本。SSL 3.0 及之前全都有严重漏洞，
已废弃禁用。

TLS（Transport Layer Security）：
SSL 的继任者，由 IETF 标准化。TLS 1.0/1.1 也已废弃，当前主流是 TLS 1.2/1.3。
日常说的「SSL 证书」实际是「TLS 证书」，是历史叫法。
```

```text
TLS 版本现状：
TLS 1.0/1.1 —— 已废弃（2020 年主流浏览器禁用）
TLS 1.2      —— 当前广泛使用（2008 年发布，成熟稳定）
TLS 1.3      —— 最新（2018 年发布），更快更安全，逐步成为默认
```

```text
TLS 1.3 相比 1.2 的改进：
1. 握手更快 —— 1-RTT 完成（1.2 要 2-RTT）
2. 加密套件精简 —— 去掉不安全算法（只留 AEAD 模式）
3. 0-RTT 恢复 —— 重连可 0 往返直接发数据
4. 前向保密 —— 强制使用带前向保密的密钥交换（ECDHE）
```

```text
HTTPS 的位置：
HTTPS = HTTP over TLS，TLS 在 TCP 之上、HTTP 之下。
协议栈：HTTP → TLS → TCP → IP
```

## 密码学基础：对称与非对称加密

TLS 的核心设计是「用非对称加密交换密钥，用对称加密传输数据」，兼顾安全和性能。

### 对称加密（Symmetric Encryption）

加密和解密用同一个密钥，速度快，适合加密大量数据。

```text
对称加密算法：
AES —— 最主流的对称加密（AES-128/AES-256），TLS 用 AEAD 模式（AES-GCM）
ChaCha20 —— 移动设备友好（无硬件 AES 加速时更快）

特点：快、密钥要安全分发（难点）
```

### 非对称加密（Asymmetric Encryption）

公钥加密、私钥解密（或反过来签名），速度慢，适合交换密钥和签名。

```text
非对称加密算法：
RSA —— 最经典，基于大整数分解难题，密钥长（2048/4096 位）
ECC —— 椭圆曲线，基于椭圆曲线离散对数，同等安全性下密钥更短、更快

特点：慢，但解决「密钥怎么安全分发」的问题——公钥可以公开。
```

### 哈希与 HMAC

```text
SHA（Secure Hash Algorithm）：
单向哈希，把任意长度数据映射成固定长度摘要，不可逆。
SHA-256（32 字节）是主流，SHA-1 已不安全（可碰撞）。

用途：
1. 完整性校验 —— 内容变了哈希就变
2. 证书指纹 —— 证书的摘要
3. 数字签名 —— 对哈希签名而非对原文签名

HMAC（Hash-based Message Authentication Code）：
带密钥的哈希，验证消息完整性和真实性。
TLS 里用 HMAC 或 AEAD 保证数据完整性（防篡改）。
```

```text
TLS 的混合加密流程（简化）：
1. 用非对称加密（RSA/ECDHE）安全地协商出一个「会话密钥」
2. 之后的数据全部用这个会话密钥对称加密（AES）传输
3. 哈希/HMAC 保证每段数据的完整性

原因：非对称安全但慢，对称快但密钥难分发，各取所长。
```

## 证书与 CA

HTTPS 的「身份认证」靠证书体系和 CA（Certificate Authority，证书颁发机构）。

```text
数字证书（Certificate）包含：
1. 域名（Subject）—— 证书是发给谁的
2. 公钥（Public Key）—— 用于加密/验签
3. 颁发者（Issuer）—— 哪个 CA 签发的
4. 有效期 —— 起止时间
5. 签名 —— CA 用自己的私钥对证书做的签名
```

```text
公钥与私钥（Public Key / Private Key）：
公钥 —— 公开，用于加密数据或验证签名
私钥 —— 保密，用于解密数据或生成签名
一对密钥，公钥加密的内容只有私钥能解，私钥签名只有公钥能验。
```

```text
证书信任链（Chain of Trust）：
网站证书 → 中间 CA → 根 CA
浏览器/系统内置了「根 CA」的公钥，逐级验签，最终信任网站证书。
任何一环有问题，整个链就断（「证书不受信任」警告）。
```

```text
CA 的作用：
CA 是「受信任的第三方」，验证域名归属后签发证书。
浏览器信任根 CA，所以信任 CA 签发的所有证书。

证书类型：
DV（域名验证）—— 只验证域名控制权，免费（Let's Encrypt），最快
OV（组织验证）—— 额外验证组织身份
EV（扩展验证）—— 最严格，浏览器地址栏显示公司名（现已弱化）
```

```text
私钥泄露的后果：
私钥是身份的核心。私钥泄露 = 任何人都能冒充你的站点。
所以私钥绝不外传、不上传到代码仓库、不放前端代码。
```

## TLS 握手

TLS 握手是客户端和服务器协商加密参数、验证身份、交换密钥的过程。

### TLS 1.2 握手（2-RTT）

```text
1. Client Hello    → 客户端发：支持的 TLS 版本、加密套件、随机数、SNI
2. Server Hello    ← 服务器回：选定的版本、加密套件、随机数、证书
3. 证书验证        客户端验证证书（信任链 + 域名匹配）
4. 密钥交换        客户端生成预主密钥，用服务器公钥加密后发送
5. 双方各自生成会话密钥
6. Finished        ←→ 双方确认握手完成，开始加密通信
```

```text
TLS 1.2 的性能问题：
握手要 2 个 RTT 才能开始传数据。
（TCP 握手 1 RTT + TLS 握手 2 RTT = 3 RTT）
```

### TLS 1.3 握手（1-RTT）

```text
TLS 1.3 的优化：
1. 把密钥交换提前到 Client Hello（ECDHE），省掉一轮
2. 握手只需 1 RTT
3. 重连可 0-RTT（用之前缓存的密钥直接发数据）

结果：TCP + TLS 1.3 = 2 RTT（比 1.2 的 3 RTT 少一轮）
```

```text
握手对前端性能的影响：
HTTPS 比 HTTP 多出的握手时间就是「TLS 握手开销」。
优化方向：
1. 用 TLS 1.3（省一轮）
2. 复用连接（HTTP/2 多路复用，避免重复握手）
3. 会话恢复（Session Resumption，重连免完整握手）
4. CDN 就近接入，降低 RTT
```

## SNI 与 ALPN

### SNI（Server Name Indication）

解决「一个 IP 上多个 HTTPS 站点，服务器该给哪个证书」的问题。

```text
SNI 的作用：
TLS 握手时，客户端在 Client Hello 里带上要访问的域名（SNI 字段）。
服务器据此返回对应域名的证书。

没有 SNI 的困境：
握手发生在 HTTP 之前，服务器不知道你要访问哪个域名，
一个 IP 只能配一张证书（一个 HTTPS 站点）。
```

```text
SNI 的实践意义：
1. 虚拟主机 —— 一个 IP 上跑多个 HTTPS 域名
2. CDN —— 边缘节点根据 SNI 选证书和回源
```

### ALPN（Application-Layer Protocol Negotiation）

TLS 握手时协商「握手之后用什么应用协议」，主要用于 HTTP/1.1 和 HTTP/2 的选择。

```text
ALPN 的作用：
客户端在 Client Hello 里声明支持的协议（h2, http/1.1），
服务器在握手时选定一个。
这样 HTTP/2 的协商在 TLS 握手内完成，不额外增加往返。

对比旧方案 NPN（Next Protocol Negotiation）：
ALPN 是标准方案，由服务器优先；NPN 已废弃。
```

```text
ALPN 的实践：
支持 HTTP/2 的站点，TLS 握手后直接走 HTTP/2，无需额外协商。
用 openssl 可查看协商结果：
openssl s_client -connect example.com:443 -alpn h2,http/1.1
```

## HSTS 与 Certificate Pinning

### HSTS

HSTS（HTTP Strict Transport Security）强制浏览器只能通过 HTTPS 访问站点，防降级攻击。

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

```text
HSTS 解决的问题：
1. 用户手动输入 http:// 或点 http 链接 → 浏览器自动转 https（不先发明文请求）
2. 防止 SSL 剥离攻击（中间人把 https 降级成 http）

HSTS 的坑：
首次访问（还没收到 HSTS 头）仍可能被降级。
解决：加入 HSTS preload 列表（浏览器内置强制 https 的名单）。
```

### Certificate Pinning（证书锁定）

客户端只信任「特定证书」而非「任何有效证书」，防中间人用伪造证书。

```text
证书锁定的思路：
把目标站点的证书（或公钥）指纹硬编码在客户端，
握手时校验服务器证书指纹是否匹配，不匹配则拒绝连接。

作用：
即使攻击者拿到一个「有效但伪造」的证书（CA 被攻破/恶意签发），
也因为指纹不匹配而被拒绝。
```

```text
证书锁定的风险（实践中的争议）：
1. 证书轮换困难 —— 证书过期/更换时，硬编码的指纹要跟着发版
2. 锁错会导致站点完全无法访问
3. 现代推荐：移动 App 用公钥锁定（HPKP 已被浏览器废弃），
   浏览器场景更依赖证书透明度（CT）和 CA 监管
```

## 应用场景实战

### 场景一：用 openssl 检查 HTTPS 站点

```bash
# 查看证书详情（域名、有效期、颁发者、SAN）
openssl s_client -connect example.com:443 -servername example.com \
  | openssl x509 -noout -subject -issuer -dates

# 查看证书指纹
openssl s_client -connect example.com:443 -servername example.com \
  | openssl x509 -noout -fingerprint -sha256

# 测试 TLS 版本和加密套件
openssl s_client -connect example.com:443 -tls1_3

# 测试 SNI（不同域名返回不同证书）
openssl s_client -connect example.com:443 -servername www.example.com
```

### 场景二：排查「证书不安全」警告

```text
浏览器提示「您的连接不是私密连接」的常见原因：
1. 证书过期 —— 检查有效期，及时续期
2. 域名不匹配 —— 证书的 SAN 列表里没有当前域名
3. 证书链不完整 —— 没配中间证书，信任链断
4. 自签名证书 —— 测试环境常见，需手动信任
5. 系统时间错误 —— 本地时间超出证书有效期
6. 用了被吊销的证书

排查命令：
openssl s_client -connect domain:443 -servername domain
看返回的证书 subject/SAN/有效期，逐项核对。
```

### 场景三：本地开发环境启用 HTTPS

```bash
# 方法 1：mkcert 生成受信任的本地证书（推荐）
mkcert -install                 # 安装本地 CA
mkcert localhost 127.0.0.1      # 生成证书
# 把生成的 cert.pem/key.pem 配到 dev server

# Vite 配置 HTTPS
# vite.config.js
import { defineConfig } from 'vite';
export default defineConfig({
  server: {
    https: {
      key: './key.pem',
      cert: './cert.pem'
    }
  }
});

# 方法 2：用 ngrok/cloudflared 隧道（获得公网 HTTPS）
cloudflared tunnel --url http://localhost:3000
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产环境强制 HTTPS + HSTS（考虑加入 preload 列表）
2. 用 TLS 1.2/1.3，禁用 SSL 和 TLS 1.0/1.1
3. 证书用自动化续期（Let's Encrypt + certbot/ACME），避免过期
4. 私钥绝不进代码仓库和前端代码，权限 600，密钥与证书分开管理
5. 证书要覆盖所有域名（含 www 和裸域名，用 SAN 或通配符证书）
6. 静态资源、API 全站 HTTPS，避免混合内容（mixed content）问题

### 踩坑记录

```text
坑 1：混合内容（mixed content）导致资源被拦截
结论：HTTPS 页面里的 http 图片/脚本/接口被浏览器拦截。
原因：HTTPS 页面加载 HTTP 资源违反安全策略，浏览器默认阻断。
解法：全站资源改 HTTPS，或配 CSP upgrade-insecure-requests 自动升级。

坑 2：证书过期导致线上全面瘫痪
结论：某天起所有用户访问报「连接不安全」，服务实际正常。
原因：证书到期未续期。
解法：用 ACME 自动化续期 + 到期监控告警，证书轮换纳入运维流程。

坑 3：私钥提交到 Git 仓库
结论：私钥泄露，站点可被冒充。
原因：把 key.pem 或环境变量里的私钥误提交。
解法：私钥进 .gitignore；已泄露立即吊销证书、重新签发，历史里彻底清除。

坑 4：证书链不完整导致部分设备/浏览器报错
结论：PC 浏览器正常，部分手机/旧系统报「证书不受信任」。
原因：只配了叶子证书，没配中间证书，部分客户端无法补全信任链。
解法：配置完整证书链（叶子 + 中间），用 SSL Labs 检测链完整性。

坑 5：本地自签名证书 dev server 报不安全
结论：本地 HTTPS 开发时浏览器一直报警告，影响调试（如 Service Worker、摄像头 API）。
原因：自签名证书不被系统信任。
解法：用 mkcert 生成本地受信任证书，一次配置长期有效。

坑 6：升级 TLS 1.3 后老客户端连不上
结论：部分旧设备/旧 App 无法访问。
原因：TLS 1.3 移除了旧算法，极老的客户端不支持。
解法：服务器保留 TLS 1.2 兼容，按客户端能力协商，不强制只开 1.3。
```
