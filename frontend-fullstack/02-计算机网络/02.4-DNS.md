## 概述

DNS（Domain Name System）把人类好记的域名（example.com）翻译成机器用的 IP 地址（93.184.216.34）。它是所有网络请求的第一步，也是前端性能的第一道关卡——DNS 解析慢，页面加载就慢。这篇笔记讲域名结构、解析流程、记录类型、缓存机制和现代加密 DNS。

```text
DNS 的两个核心问题：
1. 正向解析 —— 域名 → IP（最常见）
2. 反向解析 —— IP → 域名（PTR 记录，排查用）
```

## 域名结构：Domain、Root、TLD

域名是分层的树状结构，从右到左逐级细化：

```text
www.example.com.
│   │       │   │
│   │       │   └── 根（Root，最后的点，通常省略）
│   │       └────── 顶级域（TLD，Top-Level Domain）
│   └────────────── 二级域（SLD，注册的域名主体）
└────────────────── 主机名（Host）

完整域名末尾其实有一个「.」（根域），日常书写省略。
```

```text
TLD 分类：
通用顶级域 gTLD —— .com、.org、.net、.info
国别顶级域 ccTLD —— .cn、.jp、.uk
新通用顶级域 new gTLD —— .app、.dev、.io、.ai
```

```text
根（Root）：
全球 13 组根服务器（a.root-servers.net ~ m.root-servers.net），
是 DNS 解析的起点，存着所有 TLD 服务器的地址。
```

```text
Domain 相关的几个概念：
域名（Domain）—— example.com，注册主体
子域名（Subdomain）—— www.example.com、api.example.com
FQDN（完全限定域名）—— 含主机名的完整域名，如 www.example.com
```

## 解析流程：Resolver 与 Authoritative DNS

一次 DNS 解析涉及多个角色，用「递归 + 迭代」配合完成：

```text
DNS 角色：
Resolver（递归解析器）—— 客户端（或本地 DNS 服务器），负责「帮你查到最终答案」
Root Server             —— 根服务器，告诉你 TLD 服务器在哪
TLD Server              —— 顶级域服务器，告诉你权威服务器在哪
Authoritative DNS       —— 权威服务器，真正持有该域名的记录，给出最终答案
```

```text
一次完整解析（浏览器访问 www.example.com）：
1. 浏览器先查缓存（浏览器缓存 → 系统缓存 → hosts 文件）
2. 未命中，向配置的 DNS 服务器（Resolver）发查询
3. Resolver 查自己的缓存，未命中则从根服务器开始递归：
   → 问根：「www.example.com 在哪？」根答：「去 .com 的 TLD 服务器」
   → 问 .com TLD：「example.com 在哪？」TLD 答：「去 example.com 的权威服务器」
   → 问权威服务器：「www.example.com 的 IP？」权威答：「93.184.216.34」
4. Resolver 把结果返回给浏览器，并缓存
```

```text
递归 vs 迭代：
递归 —— Resolver 替客户端跑完全程，返回最终结果
迭代 —— 每一步服务器只告诉你「下一步问谁」，客户端/Resolver 自己接力
实际中：客户端 → Resolver 是递归，Resolver → 各层服务器是迭代。
```

```text
dig 命令可以完整看到解析过程：
dig +trace www.example.com   # 从根开始逐步追踪
dig www.example.com          # 常规查询
nslookup www.example.com     # Windows/简单查询
```

## DNS 记录类型

DNS 记录（Resource Record）类型决定「域名映射到什么」：

```text
A     —— 域名 → IPv4 地址（example.com → 93.184.216.34）
AAAA  —— 域名 → IPv6 地址（example.com → 2606:2800:...）
CNAME —— 别名 → 规范名（www → example.com，指向另一个域名）
MX    —— 邮件服务器（example.com → mail.example.com，带优先级）
TXT   —— 任意文本（SPF 反垃圾、DKIM 验证、域名所有权验证）
NS    —— 该域的权威 DNS 服务器（example.com → ns1.example.com）
```

```text
A vs CNAME（关键区别）：
A    —— 直接指向 IP，一个域名多个 A 记录实现负载均衡
CNAME —— 指向另一个域名，最终要解析到 A 才能得到 IP

坑：CNAME 不能和 MX 等其他记录同用（RFC 规定），根域（裸域名）用 CNAME
会冲突。裸域名通常配 A 记录或 ALIAS/ANAME（部分 DNS 商支持）。
```

```text
TXT 记录的前端应用：
1. 域名所有权验证 —— Google Search Console、Cloudflare、微信等要求加 TXT 记录
2. SPF —— 声明哪些服务器可以代发邮件（防伪造）
3. DKIM —— 邮件签名验证
```

```text
dig 查询各记录类型：
dig example.com A
dig example.com AAAA
dig example.com MX
dig example.com TXT
```

## DNS Cache 与 TTL

DNS 缓存遍布各层，是「改了解析不生效」问题的根源，而 TTL 控制缓存时长。

```text
DNS 缓存的层级：
1. 浏览器缓存（Chrome 独立缓存）
2. 操作系统缓存（/etc/hosts 优先级最高）
3. 本地路由器缓存
4. 运营商 DNS 服务器缓存
5. Resolver 缓存

每一层都可能缓存，这就是解析变更要等 TTL 过期才全网生效的原因。
```

```text
TTL（Time To Live，生存时间）：
记录在缓存里的存活秒数。TTL 到期后，缓存失效，重新向上游查询。
TTL 越短，变更生效越快，但查询压力越大（缓存命中率低）。
```

```text
TTL 的实践建议：
正常记录 —— 300~3600 秒
变更前 —— 提前把 TTL 调到 60 秒，等旧 TTL 过期后再改记录，
          改完恢复，这样变更能快速生效且可控
```

```text
前端排查「改了 DNS 不生效」：
1. 查本地缓存是否过期（浏览器/系统/hosts）
2. 查运营商 DNS 是否缓存旧记录
3. 用公共 DNS（8.8.8.8 / 1.1.1.1）对比验证
4. 查权威服务器上的记录是否真的改了
```

## 加密 DNS：DoH 与 DoT

传统 DNS 是明文 UDP 查询，存在被窃听和篡改的风险（DNS 劫持/污染）。加密 DNS 解决这个问题。

```text
DoH（DNS over HTTPS）：
DNS 查询走 HTTPS（端口 443），伪装成普通 HTTPS 流量，难以被区分和封锁。

DoT（DNS over TLS）：
DNS 查询走 TLS（专用端口 853），加密但端口可识别。

DoH vs DoT：
DoH —— 走 443，和普通 Web 流量混在一起，抗封锁强，浏览器原生支持
DoT —— 走 853，端口固定，网络设备可识别和管控
```

```text
DoH 的前端配置：
Chrome/Edge 设置里开启「安全 DNS」，选 Cloudflare（1.1.1.1）
或 Google（8.8.8.8）的 DoH 服务。
系统层面用 AdGuard、dnscrypt-proxy 等工具统一走加密 DNS。
```

```text
加密 DNS 的意义：
1. 防窃听 —— 别人看不到你访问了什么域名
2. 防篡改 —— 防止 DNS 污染/劫持（某些网络环境篡改解析结果）
3. 隐私 —— 运营商拿不到你的浏览记录（域名层面）
```

## 应用场景实战

### 场景一：排查「域名解析到错误 IP」

```bash
# 1. 本地解析结果
nslookup example.com
# 对比本地 DNS 返回的 IP 是否正确

# 2. 用公共 DNS 交叉验证
nslookup example.com 8.8.8.8
nslookup example.com 1.1.1.1

# 3. 直接查权威服务器（绕过缓存）
dig example.com @ns1.example.com

# 4. 检查 hosts 文件是否被篡改
cat /etc/hosts     # Linux/macOS
type C:\Windows\System32\drivers\etc\hosts  # Windows
```

```text
判断逻辑：
本地解析错、公共 DNS 对 → 本地缓存/hosts/运营商 DNS 问题，清缓存或换 DNS
公共 DNS 也错 → 权威服务器记录本身有误
权威对、但访问还是错 → 可能是 CDN 调度、防火墙或 IP 被封
```

### 场景二：前端部署切换服务器（平滑切流）

```text
需求：把 api.example.com 从旧服务器切到新服务器，尽量不中断服务。

步骤：
1. 提前把 A 记录 TTL 调低到 60 秒，等旧 TTL（如 3600 秒）过期
2. 新服务器部署好、验证通过
3. 修改 A 记录指向新 IP
4. 由于 TTL 已是 60 秒，全网最多 1 分钟完成切换
5. 验证流量已到新服务器后，把 TTL 恢复为正常值
```

## 最佳实践与踩坑记录

### 最佳实践

1. 变更 DNS 前先降 TTL，变更后再恢复，实现平滑快速切换
2. 关键域名配置多个 A 记录（不同 IP）做简单负载均衡和容灾
3. 裸域名用 A/ALIAS 记录，避免 CNAME 与 MX 等记录冲突
4. 内网服务用内网 DNS 或 hosts 分流，避免公网 DNS 泄露内网域名
5. 隐私敏感环境开启 DoH/DoT，防止 DNS 劫持和窃听

### 踩坑记录

```text
坑 1：改了 DNS 记录迟迟不生效
结论：解析还是旧 IP，等了很久没变化。
原因：多层缓存（浏览器/系统/运营商）都按旧 TTL 缓存，要等各自 TTL 过期。
解法：变更前先降 TTL；排查时逐层清缓存，用公共 DNS 交叉验证。

坑 2：裸域名用 CNAME 导致解析异常
结论：example.com 配了 CNAME，部分服务解析失败。
原因：CNAME 与 MX/NS 等记录冲突（RFC 限制），裸域名不该用 CNAME。
解法：裸域名用 A 记录或 ALIAS/ANAME（支持裸域名 CNAME 的扩展类型）。

坑 3：DNS 污染/劫持导致访问到钓鱼站
结论：域名解析到陌生 IP，网站被劫持。
原因：明文 DNS 被中间人篡改，或运营商污染。
解法：开启 DoH/DoT 加密 DNS，换可信 DNS（1.1.1.1/8.8.8.8），用 HTTPS + 证书校验防钓鱼。

坑 4：本地 hosts 文件残留导致调试困惑
结论：浏览器访问到的 IP 和线上不一致，排查半天没找到原因。
原因：hosts 文件里残留旧映射，优先级高于 DNS 查询。
解法：检查 /etc/hosts 或 Windows hosts 文件，清理临时映射。

坑 5：DNS 故障导致「网络连着但网站全打不开」
结论：ping IP 通，但任何域名都解析不了。
原因：配置的 DNS 服务器故障或不可达。
解法：换公共 DNS（8.8.8.8 / 114.114.114.114 / 1.1.1.1），或配置备用 DNS。
```
