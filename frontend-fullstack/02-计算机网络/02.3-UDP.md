## 概述

UDP（User Datagram Protocol）是无连接、不可靠的数据报传输协议。它的价值恰恰在「不可靠」——省去了握手、确认、重传的开销，换来更低的延迟和更高的吞吐。对前端，UDP 的直接意义是 QUIC 和 HTTP/3（浏览器正在大规模启用）、WebRTC 的媒体传输、DNS 查询。这篇笔记讲 UDP 的特性和它催生出的新一代传输方案。

```text
UDP 的核心特性：
1. 无连接 —— 不握手，直接发
2. 不可靠 —— 不保证送达、不保证顺序、可能重复
3. 数据报 —— 有消息边界，每次发送是一个完整数据报
4. 轻量 —— 头部仅 8 字节，开销极小
```

## Datagram 与无连接

UDP 传输的基本单位是 Datagram（数据报），每个数据报是独立、完整的消息。

```text
UDP 报文头（仅 8 字节）：
源端口（16 位）、目标端口（16 位）
长度（16 位）、校验和（16 位）

对比 TCP 头 20 字节 + 选项，UDP 头固定 8 字节，开销最小。
```

```text
无连接的含义：
1. 发送前不握手，直接发包
2. 不维护连接状态，服务端不需要为每个「连接」分配资源
3. 同一 socket 可以向任意目标发数据
```

```text
Datagram 的「消息边界」：
UDP 一次 send 对应一次 receive，接收方一次拿到完整数据报，
不存在 TCP 的粘包拆包问题。但单报文长度受 MTU 限制（约 64KB 上限，
实际受限于链路 MTU，过大要应用层自己分片）。
```

## 丢包与顺序：UDP 的不可靠性

UDP 不保证送达，也不保证顺序，这是它的「特性」而非「缺陷」——把可靠性交给应用层，让应用按需定制。

```text
UDP 的不可靠体现在：
1. 丢包 —— 发了可能丢，不重传
2. 乱序 —— 后发的可能先到
3. 重复 —— 同一个包可能收到多次
```

```text
为什么「不可靠」反而是优势：
1. 延迟低 —— 没有握手和重传等待，实时场景（音视频、游戏）宁可丢一帧也不愿等
2. 无队头阻塞 —— 一个包丢了不影响后续包，TCP 里丢一个包后续都要排队等重传
3. 服务端压力小 —— 无连接状态，单机可支撑海量连接（如 DNS 服务器）
```

```text
需要可靠时怎么办：
在 UDP 之上自己实现可靠性（如 QUIC），或者干脆用 TCP。
选择依据是「延迟敏感」还是「可靠性敏感」。
```

## QUIC

QUIC（Quick UDP Internet Connections）是 Google 提出的基于 UDP 的传输协议，把 TCP 的可靠性、TLS 的加密、HTTP/2 的多路复用整合进一个协议，是 HTTP/3 的底层。

```text
QUIC 解决 TCP 的痛点：
1. 握手慢 —— TCP + TLS 要 2-3 RTT，QUIC 集成加密，1 RTT 甚至 0 RTT（重连）
2. 队头阻塞 —— TCP 一个包丢了整条流都等；QUIC 在 UDP 上实现多路复用，
   不同流互不阻塞
3. 连接迁移 —— TCP 用「四元组」标识连接，切 Wi-Fi/4G 就要重连；
   QUIC 用 Connection ID，网络切换连接不断
4. 协议僵化 —— TCP 被中间设备（NAT/防火墙）深度介入，演进困难；
   QUIC 跑在 UDP 上，中间设备无法解析，可自由升级
```

```text
QUIC 的关键设计：
1. 基于 UDP —— 避开中间设备对 TCP 的干预，用户态实现，升级快
2. 内置 TLS 1.3 —— 加密是必选项，没有明文 QUIC
3. 独立流 —— 多路复用但每条流独立，无队头阻塞
4. 连接迁移 —— Connection ID 标识连接，网络切换不中断
```

```text
QUIC 为什么快（以首次连接为例）：
TCP + TLS 1.3：TCP 握手(1 RTT) + TLS 握手(1 RTT) = 2 RTT 才能发数据
QUIC：        TLS 握手内嵌，1 RTT 发数据
QUIC 重连：   缓存了密钥，0 RTT 直接发
```

## HTTP/3

HTTP/3 是 HTTP 的第三个大版本，底层从 TCP 换成 QUIC。

```text
HTTP 版本演进与传输层：
HTTP/1.0、1.1 —— TCP（每个/每批请求一个 TCP 连接）
HTTP/2         —— TCP（单连接多路复用，但仍有 TCP 队头阻塞）
HTTP/3         —— QUIC over UDP（彻底解决队头阻塞）
```

```text
HTTP/3 的核心改进：
1. 连接建立更快（1 RTT / 0 RTT）
2. 无队头阻塞（丢包只影响单条流）
3. 连接迁移（移动网络切换不断连）
4. 强制加密（TLS 1.3 内置）
```

```text
HTTP/3 的现状与前端：
1. 主流浏览器（Chrome/Firefox/Safari）已支持，默认对部分站点启用
2. 大型 CDN（Cloudflare、Fastly）和云厂商已支持
3. 服务端支持：Nginx 1.25+、Caddy、以及各云厂商 LB
4. 前端无需改代码，协议协商在浏览器和服务器之间自动完成（Alt-Svc 头）
```

```text
HTTP/3 的代价：
1. QUIC 在用户态实现，CPU 开销略高于内核态的 TCP
2. UDP 可能被某些企业网络/防火墙封锁（443/udp 端口要放行）
3. 兼容性兜底：不支持 HTTP/3 时自动回退 HTTP/2
```

## TCP 与 UDP 对比

```text
| 维度       | TCP                  | UDP                  |
|------------|----------------------|----------------------|
| 连接       | 面向连接（握手）     | 无连接               |
| 可靠性     | 可靠（重传、确认）   | 不可靠               |
| 顺序       | 有序                 | 无序                 |
| 头部开销   | 20 字节起            | 8 字节               |
| 传输方式   | 字节流（无边界）     | 数据报（有边界）     |
| 适用场景   | 文件、网页、API      | 音视频、游戏、DNS    |
| 队头阻塞   | 有                   | 无（但需自行处理）   |
```

```text
选择原则：
要可靠、要顺序 → TCP（网页、API、文件传输）
要低延迟、能容忍丢包 → UDP（实时音视频、游戏、DNS）
两者都要 → QUIC（HTTP/3）
```

## 应用场景实战

### 场景一：WebRTC 实时音视频

WebRTC 的媒体流（音频、视频）走 UDP 而非 TCP：

```text
为什么音视频用 UDP：
1. 实时性优先 —— 丢一帧画面比等重传一帧更可接受
2. 无队头阻塞 —— 一个包丢了，后续包继续播，画面不卡死
3. 延迟低 —— 没有握手和重传的等待

补充：WebRTC 的媒体走 UDP（SRTP），但信令/数据通道可走 TCP（SCTP/WebSocket），
并且 NAT 穿透需要 STUN/TURN 辅助（见 64-音视频、65-WebRTC 工程）。
```

### 场景二：DNS 查询为什么用 UDP

```text
DNS 查询默认走 UDP（端口 53）：
1. 查询小 —— 一个域名查询报文很小，不需要 TCP 的流式传输
2. 无状态 —— DNS 服务器要扛海量查询，UDP 无需维护连接，吞吐高
3. 快 —— 一个往返搞定，TCP 握手的三次往返太奢侈

例外：响应超过 512 字节（UDP 限制）、或区域传送（AXFR）时改用 TCP。
现代 DNS 还支持 DNS over HTTPS / DNS over TLS（见 02.4-DNS）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 音视频、游戏、实时通信优先 UDP（或 QUIC），容忍丢包换低延迟
2. 网页、API、文件传输用 TCP/HTTP，可靠性优先
3. 新项目拥抱 HTTP/3（QUIC），同时保留 HTTP/2 兜底
4. 自定义 UDP 协议要自行处理丢包/乱序/重复，按需实现重传
5. UDP 报文尽量小（< MTU），避免 IP 分片带来的丢包放大

### 踩坑记录

```text
坑 1：企业网络封锁 UDP 导致 HTTP/3 连不上
结论：浏览器 HTTP/3 协商失败，回退 HTTP/2（功能正常但失去 HTTP/3 收益）。
原因：部分企业防火墙只放行 443/tcp，不放行 443/udp。
解法：确认网络放行 443/udp；无法放行时依赖 HTTP/2 兜底，影响有限。

坑 2：UDP 应用在高丢包下体验崩坏却无感知
结论：实时应用画面/声音卡顿，但没有重传机制兜底。
原因：UDP 不重传，应用层没实现丢包恢复（FEC 前向纠错、重传请求）。
解法：实时音视频用 FEC、PLC（丢包隐藏）等抗丢包手段，而非裸 UDP。

坑 3：大 UDP 报文被分片导致丢包率飙升
结论：单个 UDP 报文超过 MTU，整体丢包率显著上升。
原因：IP 分片后任一片丢失，整个报文都要重发，丢包被放大。
解法：应用层把报文控制在 MTU 以内（通常 < 1400 字节），避免分片。

坑 4：误以为 UDP 一定比 TCP 快
结论：在可靠传输场景硬用 UDP，性能反而不如 TCP。
原因：UDP 省了握手，但应用层补可靠性（重传、排序）的实现往往不如内核 TCP 高效。
解法：可靠场景直接用 TCP 或成熟方案（QUIC），不要自己造轮子。
```
