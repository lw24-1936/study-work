## 概述

CDN（Content Delivery Network，内容分发网络）把内容缓存到离用户最近的边缘节点，让用户就近获取资源，解决「源站离得远、访问慢、扛不住大流量」的问题。它是前端性能优化的核心基础设施——静态资源、图片、视频、甚至动态请求都可以走 CDN 加速。这篇笔记讲 CDN 的原理、缓存机制、刷新预热和调度。

```text
CDN 解决的核心问题：
1. 延迟 —— 物理距离远导致 RTT 高，CDN 就近接入降低延迟
2. 带宽 —— 源站带宽有限，CDN 分摊流量
3. 可用性 —— 源站挂了，CDN 缓存还能撑一段时间（降级容灾）
```

## CDN 原理与架构

CDN 的核心是「把内容提前放到离用户近的地方」，由边缘节点、调度系统、源站组成。

```text
核心概念：
Edge Node（边缘节点）—— 分布在全球/全国各地的缓存服务器，离用户最近
Origin（源站）—— 内容的原始服务器（你的业务服务器/对象存储）
调度系统 —— 把用户请求导到最优的边缘节点（DNS 或 HTTP 调度）
```

```text
CDN 工作流程（用户访问 cdn.example.com/app.js）：
1. 用户请求域名，DNS 调度解析到最近的边缘节点 IP
2. 边缘节点检查本地缓存：
   - 命中（Cache Hit）→ 直接返回给用户
   - 未命中（Cache Miss）→ 向源站回源获取，缓存后返回给用户
3. 后续请求直接命中缓存，不再回源
```

```text
边缘节点的层级：
部分 CDN 有多级缓存：
用户 → 边缘节点（Edge）→ 区域节点（Parent）→ 源站
层级缓存能减少回源次数，但层级越多复杂度越高。
```

## 缓存机制：Cache Hit、Cache Miss 与回源

CDN 的性能取决于缓存命中率，命中率越高，回源越少，越快越省。

```text
Cache Hit（缓存命中）：
用户请求的内容边缘节点有缓存，直接返回，不访问源站。
命中率是 CDN 的核心指标。

Cache Miss（缓存未命中）：
边缘节点没有该内容，需要向上游/源站获取。

回源（Origin Fetch）：
边缘节点向上游源站请求内容的过程。
回源频繁 = 命中率低 = 源站压力大、用户等待久。
```

```text
影响命中率的因素：
1. 缓存 TTL —— 缓存时间越长命中率越高（但内容更新慢）
2. 内容热度 —— 热门内容命中率高，冷门内容易 miss
3. 缓存键 —— 缓存键设计不合理会导致同内容多次缓存
4. 流量分布 —— 用户集中在少数边缘节点时命中率高
```

```text
CDN 缓存的缓存键（Cache Key）：
默认用完整 URL 作为缓存键。
问题：URL 带随机参数（?v=123、?t=时间戳）会导致同内容多次缓存、命中率暴跌。
解决：配置忽略特定参数，或统一资源 URL 规范。
```

## CDN 刷新与预热

刷新（Purge/Refresh）和预热（Prefetch/Warm-up）是 CDN 运维的两个基本操作。

### CDN 刷新

主动清除边缘节点上的缓存，让用户立即获取新内容。

```text
刷新（Purge/Refresh）：
把指定 URL（或目录）的缓存标记失效/删除。
下次请求该资源时，边缘节点回源获取最新内容。

使用场景：
1. 发版后资源更新，需要立即生效
2. 内容错误需要紧急替换
```

```text
刷新的代价：
刷新后缓存被清空，短期内大量请求回源（源站压力骤增）。
所以「刷新整个目录」要谨慎，最好只刷新真正变化的资源。
```

### CDN 预热

主动把内容提前推送到边缘节点，避免首次访问的回源延迟。

```text
预热（Prefetch/Warm-up）：
在用户访问前，CDN 主动把指定资源提前加载到边缘节点缓存。
这样用户第一次访问就是 Cache Hit。

使用场景：
1. 大促/发布会前，预热即将爆量的资源（首页、大图、视频）
2. 新版本上线前，预热新资源
```

```text
刷新 vs 预热：
刷新 —— 删缓存，让内容更新（解决「改了不生效」）
预热 —— 填缓存，让内容提前就位（解决「首次访问慢」）
```

## 静态资源 CDN 与图片 CDN

### 静态资源 CDN

静态资源（JS、CSS、字体、图片）是 CDN 最主要的应用场景。

```text
静态资源走 CDN 的收益：
1. 就近加载 —— 降低 RTT，加载更快
2. 分担流量 —— 静态资源占了页面大部分体积，卸载后源站轻松
3. 长期缓存 —— 带 hash 的资源配长 TTL，命中率极高
```

```text
静态资源 CDN 的缓存策略：
1. 带 hash 的资源（app.abc123.js）—— 长缓存（max-age 一年 + immutable）
2. 不带 hash 的资源 —— 短缓存（如 max-age 300）
3. HTML 入口 —— 不缓存或协商缓存（保证引用到最新资源）
```

```text
为什么静态资源用独立域名（cdn.example.com）：
1. 避免无谓的 Cookie 传输 —— 主域名带 Cookie，独立 CDN 域名不带，省流量
2. 浏览器对同域名并发连接有限，独立域名增加并行度（HTTP/1.1 时代，HTTP/2 下意义减弱）
3. CDN 域名和业务域名隔离，缓存策略独立管理
```

### 图片 CDN

图片 CDN 在静态 CDN 基础上增加图片处理能力，是前端图片优化的重要工具。

```text
图片 CDN 的能力：
1. 格式转换 —— 按需返回 WebP/AVIF（浏览器支持时自动转）
2. 尺寸裁剪/缩放 —— URL 参数控制宽高，按需出图
3. 质量压缩 —— 按需降低质量（q=80）
4. 响应式 —— 不同 DPR/视口返回不同尺寸

示例（常见图片 CDN URL 参数）：
https://img.example.com/photo.jpg?w=800&q=80&format=webp
```

```text
图片 CDN 的价值：
1. 减少传输体积 —— WebP/AVIF 比 JPEG/PNG 小 30%~50%
2. 按需出图 —— 列表用小图、详情用大图，不浪费带宽
3. 节省存储 —— 存一份原图，派生尺寸按需生成
```

## 动态加速

动态加速（Dynamic Site Acceleration）针对「不可缓存」的动态请求（API、个性化内容）做网络层优化。

```text
动态内容不能缓存，CDN 如何加速：
1. 智能路由 —— 选择最优网络路径（避开拥塞链路）
2. 连接复用 —— CDN 与源站间保持长连接，减少握手开销
3. 协议优化 —— 用 HTTP/2、TLS 1.3、QUIC 加速传输
4. 边缘计算 —— 部分逻辑在边缘节点执行，减少回源
```

```text
动态加速的典型场景：
1. API 接口 —— 跨地域访问源站，网络路径优化
2. 电商下单、支付 —— 稳定低延迟的链路
3. 实时数据 —— 边缘缓存 + 短 TTL 的「准动态」加速
```

```text
动态 vs 静态加速：
静态 —— 靠缓存命中率提速（内容离用户近）
动态 —— 靠网络路径和连接优化提速（内容仍要回源，但路径更优）
```

## DNS 调度

CDN 的调度核心是「把用户导到最优边缘节点」，DNS 调度是最常用的方式。

```text
DNS 调度的原理：
1. 用户请求 cdn.example.com 的 IP
2. CDN 的 DNS 服务器根据用户来源（本地 DNS 的 IP）判断用户位置
3. 返回「离用户最近/负载最低」的边缘节点 IP
```

```text
调度的依据：
1. 地理位置 —— 用户在哪，就近分配节点
2. 网络质量 —— 节点负载、链路质量动态调整
3. 运营商 —— 电信/联通/移动走各自最优线路
```

```text
DNS 调度的局限（催生 HTTP 调度）：
1. DNS 解析有缓存（TTL），调度结果可能滞后
2. 本地 DNS 的 IP 不一定代表用户真实位置（DNS 污染/公共 DNS）
3. 调度粒度粗，难以精确到单用户

改进：HTTP 302 调度 —— 源站返回 302，把用户重定向到精确的边缘节点，
或 Anycast（同一个 IP 路由到最近节点，BGP 层调度）。
```

## 应用场景实战

### 场景一：前端静态资源接入 CDN

```text
1. 建一个 CDN 加速域名 cdn.example.com（CNAME 到 CDN 提供的域名）
2. 构建产物上传到对象存储（或直接回源到源站）
3. 资源引用用绝对 CDN 域名：
   <script src="https://cdn.example.com/app.abc123.js"></script>

4. 配置缓存规则：
   - *.js / *.css 带 hash → 长缓存 + immutable
   - *.html → 不缓存
5. 发版时：
   - 上传新资源（新 hash 文件名）
   - 更新 HTML 引用
   - 刷新 HTML 缓存（可选），静态资源不用刷（URL 变了自然 miss）
```

### 场景二：排查 CDN 缓存问题

```bash
# 1. 查看请求走的哪个节点、是否命中缓存
curl -I https://cdn.example.com/app.js
# 关注响应头：
# X-Cache: HIT（命中）/ MISS（未命中）
# Age: 缓存存活时间
# Via / X-Cache-Lookup 等 CDN 标识头

# 2. 对比边缘节点和源站内容
# 边缘节点：
curl -s https://cdn.example.com/app.js | head -c 200
# 源站（绕过 CDN，直接请求源站 IP）：
curl -s --resolve cdn.example.com:443:源站IP https://cdn.example.com/app.js | head -c 200

# 3. 强制回源验证（带 cache-busting 参数）
curl -I "https://cdn.example.com/app.js?v=$(date +%s)"
```

```text
排查思路：
1. X-Cache: MISS → 缓存没命中，检查 TTL 和缓存键
2. 边缘和源站内容不一致 → 缓存没刷新，执行刷新操作
3. 刷新后仍旧内容 → 检查是否刷错了 URL（带参数的 URL 要精确匹配）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 静态资源用独立 CDN 域名，避免携带业务 Cookie，减少流量
2. 带 hash 资源配长缓存 + immutable，配合 hash 文件名实现「更新即生效」
3. 资源 URL 规范化（去掉随机参数），避免缓存键分裂导致命中率下降
4. 发版只刷新 HTML，静态资源靠 hash 文件名自然更新，不刷全目录
5. 大促/上线前预热核心资源，避免首次访问集中回源打垮源站
6. 图片走图片 CDN，按需转 WebP/AVIF 和裁剪尺寸

### 踩坑记录

```text
坑 1：CDN 缓存了不该缓存的动态内容
结论：用户看到别人的数据（个人信息串台）。
原因：动态接口/个性化内容被 CDN 缓存，不同用户命中同一份缓存。
解法：动态内容配 no-store/no-cache 或跳过 CDN，只有公共内容才走 CDN 缓存。

坑 2：刷新缓存后仍看到旧内容
结论：执行了刷新，用户还是旧资源。
原因：刷新 URL 没匹配上（带了没刷到的参数），或浏览器本地缓存未过期。
解法：刷新精确 URL；排查浏览器本地缓存；资源用 hash 文件名避免这类问题。

坑 3：URL 带随机参数导致命中率极低
结论：CDN 命中率长期很低，回源频繁。
原因：URL 带时间戳/随机数（?v=timestamp），每次请求 URL 都不同，缓存键分裂。
解法：统一资源 URL，去掉随机参数，用 hash 文件名表达版本。

坑 4：刷新全目录导致源站被打崩
结论：大促期间刷新整个目录，海量请求同时回源，源站宕机。
原因：刷新清空缓存后，所有请求都回源，源站瞬间承压。
解法：只刷新变化资源；分批次刷新；配合预热提前回填缓存。

坑 5：CDN 域名没配证书导致 HTTPS 访问失败
结论：https://cdn.example.com 报证书错误。
原因：CDN 域名单独接入，忘了配置 HTTPS 证书。
解法：CDN 域名也配证书（CDN 商通常支持一键托管或上传），全站 HTTPS。
```
