## 概述

大型前端应用指代码量大、模块多、团队并行开发的前端工程，治理的核心不是「写得快」，而是「改得动、拆得开、并得稳」。通过分层把代码按职责切成稳定的 Domain / Feature / Shared 层次，通过依赖管理让模块之间的耦合单向可控。

```text
大型应用治理的三大命题：
1. 分层 —— 把代码按职责切成 Domain / Feature / Shared 等稳定层次
2. 边界 —— 模块之间只通过显式接口通信，禁止随意跨层引用
3. 依赖 —— 依赖方向单向流动，避免循环依赖
```

```text
# 分层目录结构示意
src/
  domain/        # 业务领域层（领域模型、核心规则）
  feature/       # 特性层（面向某个产品能力的完整实现）
  shared/        # 共享层（跨领域复用的通用代码）
```

## Modularization

模块化是把大系统拆成多个内聚、松耦合的单元，每个模块有明确职责和边界，通过显式接口交互。前端模块化从文件级（ESM）到包级（Monorepo 子包）再到应用级（微前端），粒度逐级放大。

```ts
// 文件级模块化：只导出公共 API，隐藏内部实现
// src/shared/user/user.service.ts
export interface User {
  id: string;
  name: string;
  status: 'active' | 'disabled';
}

export async function fetchUser(id: string): Promise<User> {
  // 内部实现（请求、缓存、格式化）对外不可见
  const raw = await api.get(`/users/${id}`);
  return normalize(raw);
}

export function isActive(user: User): boolean {
  return user.status === 'active';
}
```

```text
模块化的三个层次：
1. 文件级 —— ESM import/export，单文件单职责
2. 包级 —— Monorepo 子包，独立版本、独立发布
3. 应用级 —— 微前端，独立部署、可独立技术栈
```

## Componentization

组件化关注 UI 层的复用：把界面拆成可组合、可复用的组件，通过 props 输入、通过事件输出，内部状态自管理。组件是前端复用最基本、最成熟的单元，配合类型系统可大幅降低界面维护成本。

```tsx
// 组件化：props 进、事件出，内部状态自管
// src/shared/ui/TagList.tsx
interface TagListProps {
  tags: string[];
  max?: number;
  onRemove?: (tag: string) => void;
}

export function TagList({ tags, max = 5, onRemove }: TagListProps) {
  const visible = tags.slice(0, max);
  return (
    <div className="tag-list">
      {visible.map((tag) => (
        <span key={tag} className="tag">
          {tag}
          {onRemove && (
            <button onClick={() => onRemove(tag)} aria-label={`删除 ${tag}`}>
              ×
            </button>
          )}
        </span>
      ))}
    </div>
  );
}
```

```text
组件化的关键点：
1. 单一职责 —— 一个组件只做一件事
2. 明确契约 —— props/events 类型化，边界清晰
3. 可组合 —— 大组件由小组件拼装，不重写
```

## Domain

Domain（领域层）承载业务的核心概念和规则，与 UI、框架、网络解耦。它是大型应用里最稳定、最不该被频繁改动的部分，通常按业务子域（如订单、用户、库存）划分，采用 DDD 的思想组织模型与用例。

```ts
// 领域层：纯业务逻辑，不依赖 UI 和框架
// src/domain/order/order.ts
export interface Order {
  id: string;
  items: OrderItem[];
  status: OrderStatus;
}

export interface OrderItem {
  sku: string;
  quantity: number;
  price: number;
}

export type OrderStatus = 'pending' | 'paid' | 'shipped' | 'closed';

export function calculateTotal(order: Order): number {
  return order.items.reduce((sum, item) => sum + item.quantity * item.price, 0);
}

export function canShip(order: Order): boolean {
  return order.status === 'paid' && order.items.length > 0;
}
```

```text
Domain 层的设计原则：
1. 无框架依赖 —— 不 import React/Vue，可独立单测
2. 显式模型 —— 用类型/接口描述领域对象
3. 单一归属 —— 每个业务概念只在一个领域模块内定义
```

## Feature

Feature（特性层）面向某个具体的产品能力，把该能力相关的页面、组件、状态、请求聚合在一起。特性之间彼此隔离，删除一个特性只需删掉对应目录，不影响其他特性。

```text
# 一个 Feature 目录 = 一个完整的产品能力
src/feature/checkout/
  pages/          # 页面入口
  components/     # 该特性私有组件
  hooks/          # 该特性私有逻辑
  api/            # 该特性的接口调用
  state/          # 该特性的状态
  index.ts        # 对外的路由/入口导出
```

```tsx
// Feature 只暴露入口，内部实现封装
// src/feature/checkout/index.tsx
import { lazy } from 'react';

export const CheckoutPage = lazy(() => import('./pages/CheckoutPage'));

export const checkoutRoutes = [
  { path: '/checkout', component: CheckoutPage },
];
```

```text
Feature 与 Domain 的分工：
1. Feature —— 面向产品能力，关心「怎么做给用户」
2. Domain —— 面向业务规则，关心「业务本质是什么」
3. Feature 依赖 Domain，Domain 不依赖 Feature
```

## Shared

Shared（共享层）存放跨领域、跨特性复用的通用代码：UI 基础组件、工具函数、常量、类型。共享层必须保持「无业务语义」，一旦某段代码开始携带业务逻辑，就应下沉到对应领域或特性。

```ts
// 共享层：纯通用工具，不含任何业务语义
// src/shared/utils/format.ts
export function formatMoney(amount: number, currency = 'CNY'): string {
  return new Intl.NumberFormat('zh-CN', {
    style: 'currency',
    currency,
  }).format(amount);
}

export function debounce<T extends (...args: unknown[]) => void>(
  fn: T,
  delay = 300,
): T {
  let timer: ReturnType<typeof setTimeout>;
  return ((...args: unknown[]) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  }) as T;
}
```

```text
Shared 层的红线：
1. 禁止业务语义 —— 不出现「订单」「用户」等业务词
2. 禁止依赖 Feature/Domain —— 只能被上层依赖
3. 变更需谨慎 —— 共享层改动影响面最大，要有测试兜底
```

## Dependency Management

依赖管理控制模块之间的引用关系，保证依赖方向单向、无循环，让系统可预测、可增量构建。工具上靠 ESLint 的 import 规则做边界约束，靠依赖分析工具（如 madge、Nx 依赖图）做可视化与 CI 校验。

```js
// ESLint 用 import/no-restricted-paths 强制依赖方向
// .eslintrc.js
module.exports = {
  rules: {
    'import/no-restricted-paths': [
      'error',
      {
        zones: [
          // domain 不能引用 feature/shared 之外的上层
          { target: './src/domain', from: './src/feature' },
          { target: './src/domain', from: './src/pages' },
          // shared 不能引用任何上层
          { target: './src/shared', from: './src/domain' },
          { target: './src/shared', from: './src/feature' },
        ],
      },
    ],
  },
};
```

```text
依赖管理三件事：
1. 约束方向 —— 上层依赖下层，禁止反向
2. 检测环 —— 循环依赖会破坏 tree-shaking 和增量构建
3. 可视化 —— 依赖图让架构决策有据可依
```

## 应用场景实战

### 场景一：为大型应用搭建分层目录并配置依赖边界

```bash
# 生成分层目录结构
mkdir -p src/{domain,feature,shared}
mkdir -p src/domain/{user,order}
mkdir -p src/shared/{ui,utils,types}
mkdir -p src/feature/{cart,checkout}
```

```js
// 用 ESLint 规则锁定依赖方向，CI 里跑 lint 即校验架构
// eslint.config.js（flat config 写法）
import noRestrictedPaths from 'eslint-plugin-import';

export default [
  {
    plugins: { import: noRestrictedPaths },
    rules: {
      'import/no-cycle': 'error',
      'import/no-restricted-paths': [
        'error',
        {
          zones: [
            { target: './src/domain', from: './src/feature' },
            { target: './src/shared', from: './src/domain' },
          ],
        },
      ],
    },
  },
];
```

### 场景二：用依赖分析工具检测循环依赖

```bash
# 安装 madge 并扫描循环依赖
npm i -D madge

# 生成依赖图并检测循环引用
npx madge --circular --extensions ts,tsx src/

# 输出示例（存在循环时）：
# ✗ Found 1 circular dependency:
#   src/feature/cart/hooks/useCart.ts > src/shared/utils/format.ts > src/feature/cart/hooks/useCart.ts
```

```text
修复循环依赖的常见手段：
1. 提取公共部分下沉到 shared
2. 用接口/回调倒置依赖方向（依赖倒置）
3. 拆出第三模块承接双方共用的逻辑
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先分层再写代码，用目录结构固化架构约定
2. 依赖方向单向：feature → domain → shared，禁止反向与跨层
3. 用 ESLint 的 import 规则把架构边界写进 CI，靠工具而非自觉
4. 共享层保持「零业务语义」，出现业务词立即下沉
5. 每个 Feature 有独立入口文件，删除特性 = 删除一个目录
6. 定期跑依赖图分析，循环依赖清零

### 踩坑记录

```text
坑 1：shared 层越写越大，最后变成垃圾场
结论：共享层塞满业务逻辑，任何改动都要全局回归，没人敢动。
原因：图省事把带业务语义的代码都扔进 shared，边界形同虚设。
解法：共享层只放无业务语义的通用代码，业务代码一律下沉到 domain/feature。

坑 2：domain 反向依赖了 feature
结论：领域层引用了页面组件，领域逻辑无法独立测试和复用。
原因：没有依赖约束，开发者随手 import 了上层的 UI 组件。
解法：用 import/no-restricted-paths 锁定方向，CI 阻断反向引用。

坑 3：循环依赖导致构建产物异常或运行时报 undefined
结论：A 依赖 B、B 又依赖 A，模块初始化顺序错乱，出现奇怪的 undefined。
原因：跨模块互相引用，没有及时察觉。
解法：用 madge --circular 定期扫描，把循环依赖纳入 CI 门槛，发现即修。

坑 4：每个团队各建一套 shared，重复造轮子
结论：同一个格式化函数在三个包里各写一遍，改一处漏三处。
原因：共享层没有统一入口，团队各自为政。
解法：建立统一的 shared 包（或 Monorepo 子包），统一维护、统一发布。

坑 5：分层只落在文档里，代码里还是乱引
结论：文档写了分层规范，实际代码到处跨层引用。
原因：规范没有工具化，靠 code review 口头提醒。
解法：把架构规则固化成 ESLint 规则和 CI 检查，机器把关。
```
