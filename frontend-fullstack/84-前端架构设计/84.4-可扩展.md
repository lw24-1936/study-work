## 概述

可扩展前端指系统在不改动核心代码的前提下，能持续「长」出新功能、新模块、新团队。扩展性靠两条腿走路：代码层面用插件机制和设计系统让功能可插拔、可复用，组织层面用微前端和 Monorepo 让团队和模块可以并行、独立演进。

```text
可扩展的三个维度：
1. 功能可插拔 —— 插件机制，新功能即插即用
2. 模块可独立 —— 微前端/Module Federation，模块独立开发部署
3. 复用有体系 —— Design System + Monorepo，公共能力沉淀复用
```

```text
扩展性 vs 复杂性：
新增功能不碰核心 = 高扩展性
新增功能要改多处 = 扩展性差，复杂度失控
```

## Plugin

插件（Plugin）机制让第三方或后续团队在不改主程序的情况下扩展能力：核心系统定义插件接口与生命周期，插件按约定注册自己的实现。前端典型的插件化包括 Webpack/Vite 插件、编辑器插件、业务系统的功能插件。

```ts
// 定义插件接口：插件只需实现约定的钩子
export interface Plugin {
  name: string;
  setup(ctx: PluginContext): void;
}

export interface PluginContext {
  registerCommand(cmd: string, handler: () => void): void;
  on(event: string, handler: (payload: unknown) => void): void;
}

// 插件管理器：加载、注册、触发
export class PluginManager {
  private plugins: Plugin[] = [];

  use(plugin: Plugin) {
    this.plugins.push(plugin);
  }

  setup() {
    const ctx: PluginContext = {
      registerCommand: (cmd, handler) => {
        this.commands.set(cmd, handler);
      },
      on: (event, handler) => {
        this.listeners.push({ event, handler });
      },
    };
    for (const p of this.plugins) p.setup(ctx);
  }

  run(command: string) {
    this.commands.get(command)?.();
  }
}
```

```ts
// 业务插件：实现约定的 setup 钩子，注册自己的命令
const exportPlugin: Plugin = {
  name: 'export',
  setup(ctx) {
    ctx.registerCommand('export:pdf', () => {
      /* 导出 PDF 逻辑 */
    });
  },
};

const manager = new PluginManager();
manager.use(exportPlugin);
manager.setup();
manager.run('export:pdf');
```

```text
插件机制的要点：
1. 稳定接口 —— 核心只依赖插件接口，不依赖具体实现
2. 生命周期钩子 —— 约定 setup/mount/unmount 等阶段
3. 隔离 —— 插件之间不直接通信，通过核心转发
```

## Micro Frontend

微前端（Micro Frontend）把一个大应用拆成多个可独立开发、独立部署、独立上线的子应用，再由一个主应用（壳）把它们组合起来。它把「大型单体的部署耦合」变成「子应用各自演进」，适合多团队协作的超大前端。

```text
微前端的三种组合方式：
1. 构建时集成 —— 子应用打包成库，主应用统一构建（耦合最紧）
2. 运行时集成 —— 主应用运行时加载子应用的 JS，挂载到容器（常用）
3. 服务端集成 —— 服务端按路由拼接不同子应用的 HTML（如 SSR 拼接）
```

```js
// 运行时集成：主应用按路由挂载子应用（single-spa 风格）
import { registerApplication, start } from 'single-spa';

registerApplication({
  name: 'cart',
  app: () => import('cart-app/cart'), // 子应用独立包
  activeWhen: (location) => location.pathname.startsWith('/cart'),
});

registerApplication({
  name: 'checkout',
  app: () => import('checkout-app/checkout'),
  activeWhen: (location) => location.pathname.startsWith('/checkout'),
});

start();
```

```text
微前端的权衡：
1. 收益 —— 独立部署、独立技术栈、团队自治
2. 成本 —— 运行时有沙箱/样式/通信/状态共享等额外复杂度
3. 适用 —— 数十人以上、多团队、超大应用；小团队慎用
```

## Module Federation

Module Federation（模块联邦）是 Webpack/Rspack 提供的运行时共享机制：多个独立构建的应用可以在运行时互相暴露、消费对方的模块，共享依赖。相比传统微前端，模块联邦更细粒度——共享的不是「整个应用」而是「具体模块」。

```js
// 远程应用（提供方）：暴露模块
// webpack.config.js
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'designSystem',
      filename: 'remoteEntry.js',
      exposes: {
        './Button': './src/components/Button',
        './Theme': './src/theme',
      },
      shared: { react: { singleton: true } }, // 共享依赖，避免双 React
    }),
  ],
};
```

```js
// 宿主应用（消费方）：远程引用模块
// webpack.config.js
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      remotes: {
        designSystem: 'designSystem@https://cdn.example.com/remoteEntry.js',
      },
      shared: { react: { singleton: true } },
    }),
  ],
};
```

```tsx
// 宿主代码里像本地模块一样 import 远程组件
import Button from 'designSystem/Button';

export function Page() {
  return <Button variant="primary">提交</Button>;
}
```

```text
Module Federation 的关键点：
1. exposes —— 明确暴露哪些模块，形成对外契约
2. remotes —— 声明远程地址，运行时加载 remoteEntry
3. shared —— 声明共享依赖（singleton 防双实例）
4. 版本 —— 远程模块升级，宿主可独立消费新版本
```

## Monorepo

Monorepo 把多个相关包/应用放在一个仓库里统一管理，配合工具（pnpm workspace、Nx、Turborepo）实现共享代码、原子提交、统一构建。它是「代码层面」的扩展底座——新增一个包、一个应用，不新增一套工程基础设施。

```json
// pnpm-workspace.yaml：声明 workspace 下的所有包
{
  "packages": [
    "apps/*",
    "packages/*"
  ]
}
```

```text
# Monorepo 目录结构
apps/
  web/          # 主站应用
  admin/        # 管理后台
packages/
  ui/           # 共享 UI 组件库
  utils/        # 共享工具
  config/       # 共享配置（eslint/tsconfig）
```

```bash
# 用 pnpm --filter 针对单个包操作
pnpm --filter @app/ui build      # 只构建 ui 包
pnpm --filter @app/web dev       # 只启动 web 应用
pnpm --filter "@app/*" test      # 跑所有 app 的测试

# Nx 按依赖图只构建受影响的包
npx nx affected:build --base=main
```

```text
Monorepo 对扩展的价值：
1. 新增包零成本 —— 复用同一套 lint/test/build 配置
2. 依赖共享 —— 公共代码直接引用，改一处全生效
3. 原子提交 —— 跨包改动一次提交，不会版本错位
```

## Design System

Design System（设计系统）把设计语言沉淀成可复用的设计 token、组件和规范，让「新增界面」不必从零开始，而是用现成组件拼装。它是 UI 层面的扩展底座：功能越多，复用红利越大，视觉与交互越一致。

```json
// 设计 token：颜色、间距、字号统一管理
{
  "color": {
    "primary": "#2563eb",
    "danger": "#dc2626",
    "text": "#111827"
  },
  "space": {
    "sm": "8px",
    "md": "16px",
    "lg": "24px"
  },
  "font": {
    "size": { "sm": "12px", "base": "14px", "lg": "18px" }
  }
}
```

```tsx
// 基于 token 的组件，保证一致性与可扩展
import { tokens } from '@app/design-system';

export function Button({ variant = 'primary', size = 'md', children }) {
  const bg = tokens.color[variant];
  const padding = tokens.space[size];
  return (
    <button style={{ background: bg, padding }} className="btn">
      {children}
    </button>
  );
}
```

```text
Design System 的构成：
1. Design Token —— 颜色/间距/字号等原子变量
2. 组件库 —— Button/Input/Table 等可复用组件
3. 规范 —— 使用文档、最佳实践、无障碍要求
```

## 应用场景实战

### 场景一：给主应用接入插件化命令面板

```ts
// 1. 定义插件接口（核心只认接口）
interface Plugin {
  name: string;
  commands: Array<{ id: string; title: string; run: () => void }>;
}

// 2. 插件管理器
class CommandPalette {
  private plugins: Plugin[] = [];
  register(p: Plugin) {
    this.plugins.push(p);
  }
  execute(id: string) {
    for (const p of this.plugins) {
      const cmd = p.commands.find((c) => c.id === id);
      if (cmd) return cmd.run();
    }
    console.warn(`command ${id} not found`);
  }
}

// 3. 新团队写插件，无需改核心
const searchPlugin: Plugin = {
  name: 'search',
  commands: [
    { id: 'search:global', title: '全局搜索', run: () => openSearch() },
  ],
};
palette.register(searchPlugin);
palette.execute('search:global');
```

### 场景二：Module Federation 实现设计系统远程共享

```js
// 设计系统应用（提供方）暴露组件
new ModuleFederationPlugin({
  name: 'ds',
  filename: 'remoteEntry.js',
  exposes: {
    './Button': './src/Button',
    './Input': './src/Input',
  },
  shared: { react: { singleton: true } },
});
```

```js
// 多个业务应用（消费方）远程引用同一套设计系统
new ModuleFederationPlugin({
  name: 'shop',
  remotes: { ds: 'ds@https://cdn.example.com/ds/remoteEntry.js' },
  shared: { react: { singleton: true } },
});
```

```tsx
// 业务应用里直接用远程组件，设计系统升级所有应用同步受益
import { Button, Input } from 'ds';

export function SearchBar() {
  return (
    <form>
      <Input placeholder="搜索商品" />
      <Button variant="primary">搜索</Button>
    </form>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 插件接口设计优先：核心只依赖稳定接口，不依赖具体插件
2. 插件之间不直接通信，统一通过核心转发，避免网状耦合
3. 微前端按业务边界拆分，而不是按技术层级拆分
4. Module Federation 用 shared + singleton 共享 React/Vue，防止双实例
5. Monorepo 统一工程配置，新增包自动继承 lint/test/build 规范
6. Design System 先行，新界面优先用现成组件而非从零写

### 踩坑记录

```text
坑 1：微前端没做依赖共享，页面里跑了两份 React
结论：页面加载两个 React 实例，Hook 状态错乱、体积翻倍。
原因：各子应用各自打包 React，运行时存在双实例。
解法：Module Federation 用 shared 声明 singleton，或用 externals 共享同一实例。

坑 2：插件接口频繁变动，插件作者苦不堪言
结论：核心每发一版，所有插件都要跟着改，扩展性名存实亡。
原因：插件接口设计不稳固，把内部实现细节暴露给了插件。
解法：接口面向「能力」而非「实现」，保持向后兼容，废弃走 deprecation 流程。

坑 3：Monorepo 里包之间互相乱引，依赖图变成一团乱麻
结论：A 包引 B 包、B 包又引 A 包，构建和测试都失控。
原因：workspace 没有依赖边界约束，谁都能引谁。
解法：用 ESLint 的 no-restricted-paths 或 Nx 的 tag 规则锁定依赖方向。

坑 4：Design System 沦为「示例代码库」，没人真正复用
结论：设计系统做了一堆组件，业务还是各写各的，无法统一。
原因：只建了组件库，没有配套的接入流程、文档和强制约束。
解法：设计系统要配套使用规范、代码评审强制引用、组件覆盖率看板。

坑 5：微前端拆得太碎，运行时代价大于收益
结论：每个页面一个子应用，加载慢、样式冲突、通信复杂。
原因：盲目追求拆分，忽略了运行时集成的额外成本。
解法：小团队/中小应用优先模块化 + Monorepo，确有多团队独立部署需求再上微前端。
```
