## 概述

高可用前端指在依赖故障、网络抖动、服务过载时，页面仍能「用」——至少核心功能不中断、不白屏。高可用的本质是「假设故障必然发生」，用故障转移、重试、超时、熔断、降级、兜底这一整套手段把故障的影响控制在局部。

```text
高可用六件套：
1. Failover —— 主备切换，一条链路挂了换另一条
2. Retry —— 偶发失败自动重试
3. Timeout —— 及时止损，不无限等待
4. Circuit Breaker —— 熔断，故障源先隔离再恢复
5. Graceful Degradation —— 优雅降级，能力从完整到精简
6. Fallback —— 兜底，总有一个可用结果返回
```

```text
故障处理链路：
请求 → 超时控制 → 重试 → 熔断判断 → 降级/兜底 → 返回结果
           ↑ 每一步都是保护，避免故障扩散
```

## Failover

Failover（故障转移）在某个依赖不可用时自动切换到备用实例或备用链路，让用户无感知地继续使用。前端常见的 failover 包括多域名容灾、主备接口切换、多 CDN 节点切换。

```js
// 多数据源 failover：主源失败自动切备用源
const primaryApi = 'https://api.example.com';
const backupApi = 'https://api-backup.example.com';

async function fetchWithFailover(path) {
  const sources = [primaryApi, backupApi];
  for (const base of sources) {
    try {
      const resp = await fetch(`${base}${path}`, { signal: timeoutSignal(3000) });
      if (resp.ok) return await resp.json();
    } catch (err) {
      console.warn(`failover source ${base} failed:`, err);
    }
  }
  throw new Error('all sources failed');
}
```

```text
Failover 的要点：
1. 备用源要真正独立 —— 不同机房/不同域名，否则一起挂
2. 切换要快 —— 配合超时，主源失败立即换备用
3. 记录切换事件 —— 便于发现主源故障与回归
```

## Retry

Retry（重试）对偶发性的失败（网络抖动、瞬时超时）自动再试，提高请求成功率。重试要「有限度、有退避」：限制次数，指数退避延迟，避免重试本身加重故障。

```js
// 指数退避重试：次数有限、延迟递增、只重试可重试的错误
async function fetchWithRetry(url, { retries = 3, baseDelay = 200 } = {}) {
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      const resp = await fetch(url);
      if (resp.ok) return await resp.json();
      if (resp.status >= 500 && attempt < retries) throw new Error('5xx');
      return await resp.json(); // 4xx 是客户端错误，不重试
    } catch (err) {
      if (attempt === retries) throw err;
      const delay = baseDelay * 2 ** attempt; // 200/400/800ms
      await new Promise((r) => setTimeout(r, delay));
    }
  }
}
```

```text
重试的纪律：
1. 只重试幂等请求 —— GET/查询可重试，POST 提交要谨慎
2. 只重试瞬时错误 —— 5xx、网络抖动可重试，4xx 不重试
3. 指数退避 + 抖动 —— 避免重试风暴同时打到后端
4. 设上限 —— 次数与总时长都要封顶
```

## Timeout

Timeout（超时）给每个依赖调用设置时间上限，超时即中断，避免一个慢依赖拖垮整个页面。前端通过 AbortController 或请求库的 timeout 配置实现，配合超时后的重试或降级。

```js
// AbortController 实现请求超时
function timeoutSignal(ms) {
  const controller = new AbortController();
  setTimeout(() => controller.abort(), ms);
  return controller.signal;
}

async function fetchWithTimeout(url, ms = 5000) {
  try {
    const resp = await fetch(url, { signal: timeoutSignal(ms) });
    return await resp.json();
  } catch (err) {
    if (err.name === 'AbortError') {
      throw new Error(`request timeout after ${ms}ms`);
    }
    throw err;
  }
}
```

```text
超时设置的考量：
1. 分级设置 —— 核心接口短超时，慢查询适当放宽
2. 总预算 —— 页面总加载时间 = 各依赖超时之和的上限
3. 超时 ≠ 失败 —— 超时后走重试或降级，而非直接报错
```

## Circuit Breaker

Circuit Breaker（熔断器）在依赖连续失败达到阈值时「打开」熔断，短期内不再请求该依赖，给故障源恢复时间；一段时间后半开试探，成功则闭合恢复。熔断避免了「明明挂了还反复打」造成的资源浪费与雪崩。

```js
// 简单熔断器：闭合 → 打开 → 半开 三态切换
class CircuitBreaker {
  constructor(fn, { threshold = 3, cooldown = 10_000 } = {}) {
    this.fn = fn;
    this.threshold = threshold;
    this.cooldown = cooldown;
    this.failures = 0;
    this.state = 'closed'; // closed | open | half-open
    this.openedAt = 0;
  }

  async call(...args) {
    if (this.state === 'open') {
      if (Date.now() - this.openedAt < this.cooldown) {
        throw new Error('circuit open'); // 熔断中，直接拒绝
      }
      this.state = 'half-open'; // 冷却结束，进入半开试探
    }
    try {
      const result = await this.fn(...args);
      this.failures = 0;
      this.state = 'closed'; // 成功，恢复闭合
      return result;
    } catch (err) {
      this.failures += 1;
      if (this.failures >= this.threshold) {
        this.state = 'open';
        this.openedAt = Date.now(); // 达到阈值，打开熔断
      }
      throw err;
    }
  }
}
```

```text
熔断器三态：
1. closed —— 正常放行，累计失败次数
2. open —— 失败达阈值，短期拒绝所有请求
3. half-open —— 冷却后放少量试探请求，成功则闭合
```

## Graceful Degradation

Graceful Degradation（优雅降级）在资源不足或依赖异常时，主动关掉非核心功能，保证核心链路可用。降级是「有意识的能力收缩」：先保主流程，再保体验，最后才是全功能。

```js
// 优雅降级：主依赖失败时，关闭非核心模块，保住主流程
async function loadDashboard() {
  // 核心数据：必须成功
  const core = await fetchCoreData(); // 失败则整页不可用，走兜底

  // 非核心数据：失败不影响主流程
  const optional = await Promise.allSettled([
    fetchRecommendations(), // 推荐位，失败可隐藏
    fetchLiveStats(),       // 实时统计，失败可省略
  ]);

  const [recommend, live] = optional;
  return {
    core,
    recommend: recommend.status === 'fulfilled' ? recommend.value : null,
    live: live.status === 'fulfilled' ? live.value : null,
  };
  // 推荐/实时挂了，主面板照常用，只是少了这些区块
}
```

```text
降级的分级思路：
1. 先保主流程 —— 核心数据、核心交互不降
2. 再保体验 —— 图片降清晰度、列表降分页
3. 最后全功能 —— 非核心模块可整体关闭
```

## Fallback

Fallback（兜底）在一切尝试都失败后，仍给用户一个可用的结果：默认值、缓存数据、错误占位。兜底是最后一道防线，保证「页面永远有东西可显示」，而不是白屏或崩溃。

```js
// 兜底策略：内存 → 缓存 → 网络 → 默认值
async function getUserProfile(id) {
  const fallback = { id, name: '游客', avatar: '/default-avatar.png' };

  try {
    const data = await fetchWithRetry(`/api/users/${id}`, { retries: 2 });
    return data;
  } catch (err) {
    // 尝试读本地缓存
    const cached = localStorage.getItem(`user:${id}`);
    if (cached) return JSON.parse(cached);
    // 最终兜底：返回默认对象，页面不白屏
    return fallback;
  }
}
```

```tsx
// 渲染层兜底：数据缺失时用占位，而不是渲染报错
export function UserCard({ user }: { user?: User }) {
  const u = user ?? { name: '—', avatar: '/placeholder.png' };
  return (
    <div className="user-card">
      <img src={u.avatar} alt={u.name} />
      <span>{u.name}</span>
    </div>
  );
}
```

```text
兜底的价值排序：
1. 缓存数据 —— 最近的可用真实数据
2. 默认值/占位 —— 保证结构完整、可渲染
3. 明确错误态 —— 实在不行也要给用户可操作的错误提示
```

## 应用场景实战

### 场景一：给核心接口加超时 + 重试 + 熔断的组合保护

```js
// 三层保护组合：超时兜底 → 指数退避重试 → 熔断隔离
const breaker = new CircuitBreaker(fetchWithRetry, {
  threshold: 3,
  cooldown: 15_000,
});

async function loadProducts(category) {
  try {
    return await breaker.call(`/api/products?category=${category}`);
  } catch (err) {
    if (err.message === 'circuit open') {
      return readProductsFromCache(category); // 熔断期间读缓存兜底
    }
    return []; // 最终兜底：空列表，页面不白屏
  }
}
```

### 场景二：页面级降级 —— 非核心模块失败不影响主流程

```js
// 首页各模块独立容错，核心与可选分离
async function renderHome() {
  const results = await Promise.allSettled([
    fetchCoreFeeds(),          // 核心信息流，失败走重试+兜底
    fetchBanners(),            // Banner，失败隐藏
    fetchHotTopics(),          // 热榜，失败隐藏
    fetchPersonalizedFeed(),   // 个性化推荐，失败用默认推荐
  ]);

  return {
    feeds: settle(results[0], () => []),
    banners: settle(results[1], () => []),
    hotTopics: settle(results[2], () => []),
    personalized: settle(results[3], () => fetchDefaultFeed()),
  };
}

function settle(result, fallbackFn) {
  return result.status === 'fulfilled' ? result.value : fallbackFn();
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每个外部依赖都设超时，配合 AbortController 及时中断
2. 重试只针对幂等请求和瞬时错误，做指数退避 + 抖动
3. 熔断器按依赖粒度隔离，避免一个故障源拖垮全局
4. 核心链路与可选链路分离，降级先砍可选功能
5. 兜底永远返回可渲染的结果，杜绝白屏
6. 故障切换、熔断打开等事件要打点上报，便于复盘

### 踩坑记录

```text
坑 1：重试了非幂等请求导致重复下单
结论：用户点了一次提交，网络超时自动重试，结果生成了两笔订单。
原因：对 POST 提交类请求也套了盲目重试。
解法：只对幂等请求（GET/查询）重试；写操作用幂等键或改用确认机制。

坑 2：超时设得太长，慢依赖拖垮整个页面
结论：一个接口要 20 秒才超时，页面卡死，其他模块全被阻塞。
原因：统一用了过长超时，没有按依赖分级。
解法：按依赖重要性分级设超时，核心短、次要长，并设置总时间预算。

坑 3：熔断后从不恢复，依赖恢复了一直报错
结论：后端早就恢复了，前端熔断器一直开着，接口持续报错。
原因：熔断器没有半开探测机制，打开后永不重试。
解法：实现 closed/open/half-open 三态，冷却后放试探请求自动恢复。

坑 4：兜底返回了空对象，渲染层解构报错白屏
结论：兜底数据字段缺失，组件访问 undefined 的属性直接崩溃。
原因：兜底对象结构不完整，与真实数据契约不一致。
解法：兜底值必须满足与真实数据相同的类型契约，渲染层做空值保护。

坑 5：把所有模块放一个 Promise.all，一个失败全失败
结论：Banner 接口挂了，整个首页连同信息流一起报错。
原因：核心与可选模块没有隔离，互相牵连。
解法：用 Promise.allSettled 隔离各模块，核心模块单独容错。
```
