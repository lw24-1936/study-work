## 概述

高并发前端指在大量用户同时访问时，仍能保证页面快速、稳定地返回。前端应对高并发的核心思路是「把压力挡在离用户最近的地方」：能缓存的缓存、能静态化的静态化、能在边缘算的就不回源。

```text
高并发前端的五层防线：
1. CDN —— 静态资源就近分发，源站几乎不承压
2. Cache —— 浏览器/边缘/服务端多级缓存
3. 静态化 —— 能预渲染的页面直接出 HTML
4. SSR —— 首屏在服务端出结果，减轻客户端负担
5. Edge —— 计算下沉到边缘节点，减少回源
```

```text
请求链路与各层职责：
用户 → CDN 边缘 → API Gateway → 源站/后端
      ↑ 缓存/静态   ↑ 限流/聚合   ↑ 业务计算
```

## CDN

CDN（内容分发网络）把静态资源分发到全球各地的边缘节点，用户就近拉取，源站压力骤降、访问延迟大幅缩短。前端几乎所有静态资源（JS/CSS/图片/字体）都应走 CDN。

```html
<!-- 静态资源走 CDN，配合 hash 文件名做长缓存 -->
<!doctype html>
<html>
  <head>
    <link rel="stylesheet" href="https://cdn.example.com/app.8f2c1a.css" />
  </head>
  <body>
    <div id="root"></div>
    <script src="https://cdn.example.com/app.9d3b7e.js"></script>
  </body>
</html>
```

```text
CDN 使用要点：
1. 文件名带内容 hash —— 内容变了文件名变，可放心长缓存
2. 合理缓存头 —— 静态资源 Cache-Control 设长 max-age + immutable
3. 多地域调度 —— 用 CNAME/智能 DNS 把用户调度到最近节点
4. 回源收敛 —— 缓存命中率越高，源站越轻松
```

## Cache

缓存是应对高并发最有效的手段：把「算一次、用多次」的结果存下来，后续请求直接命中。前端相关的缓存贯穿浏览器（HTTP 缓存、Service Worker）、边缘节点（CDN 缓存）、服务端（页面/数据缓存）三个层面。

```text
# 三层缓存
1. 浏览器缓存 —— Cache-Control/ETag 控制，命中则不发请求
2. Service Worker —— 拦截请求，可做离线与细粒度缓存
3. 边缘/CDN 缓存 —— s-maxage 控制共享缓存，命中不回源
```

```js
// Service Worker 缓存静态资源，二次访问几乎零请求
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('static-v1').then((cache) =>
      cache.addAll(['/app.js', '/app.css', '/logo.png']),
    ),
  );
});

self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((hit) => hit || fetch(event.request)),
  );
});
```

```text
缓存策略口诀：
1. 静态资源 —— 长缓存 + hash 文件名（immutable）
2. HTML 入口 —— 短缓存或不缓存，保证拿到最新引用
3. 数据接口 —— 按业务定 TTL，写操作不缓存
```

## Static Rendering

静态渲染（Static Rendering / SSG）在构建期就把页面预渲染成 HTML 文件，运行时直接返回现成的 HTML。纯静态页面可以完全放在 CDN 上，源站几乎零压力，是高并发场景下性价比最高的方案。

```js
// Next.js 静态生成：构建时生成 HTML
// pages/products/[id].js
export async function getStaticProps({ params }) {
  const product = await fetchProduct(params.id);
  return { props: { product }, revalidate: 60 }; // ISR：60 秒增量再生成
}

export async function getStaticPaths() {
  const products = await fetchAllProducts();
  return {
    paths: products.map((p) => ({ params: { id: p.id } })),
    fallback: 'blocking',
  };
}

export default function ProductPage({ product }) {
  return <article>{product.name}: {product.price}</article>;
}
```

```text
静态渲染的适用与边界：
1. 适合 —— 内容变化不频繁的页面（商品详情、文章、落地页）
2. 不适合 —— 强个性化、依赖实时数据的页面
3. 折中 —— ISR 增量再生，兼顾静态化与新鲜度
```

## SSR

SSR（服务端渲染）在服务端执行渲染逻辑，返回完整 HTML，首屏可立即呈现、利于 SEO。高并发下 SSR 的关键是「渲染结果可缓存」——对公共页面做结果缓存，命中后不再重复渲染，把 CPU 压力转化为缓存读取。

```js
// Node 服务端渲染 + 结果缓存，公共页面只渲染一次
import { renderToString } from 'react-dom/server';
import { App } from './App';

const cache = new Map(); // 页面缓存：url → html

export async function handle(req, res) {
  const key = req.url;
  if (cache.has(key)) {
    return res.send(cache.get(key)); // 命中缓存，跳过渲染
  }
  const data = await fetchData(req.url);
  const html = renderToString(<App data={data} />);
  cache.set(key, html);
  res.send(html);
}
```

```text
SSR 高并发优化点：
1. 结果缓存 —— 公共页面缓存渲染结果
2. 流式返回 —— renderToPipeableStream 边渲染边输出
3. 降级 —— 渲染压力大时降级到 CSR 或静态页
```

## Edge

Edge（边缘计算）把计算下沉到离用户最近的边缘节点，在 CDN 节点上直接运行代码，返回动态结果。相比回源，边缘计算延迟更低、并发能力更强，常用于个性化改写、鉴权、A/B 分流、地理位置相关逻辑。

```js
// 边缘函数（如 Cloudflare Workers / Vercel Edge）
export default {
  async fetch(request) {
    const url = new URL(request.url);
    const country = request.headers.get('cf-ipcountry'); // 边缘直接拿到地域

    // 边缘做 A/B 分流
    const bucket = country === 'CN' ? 'a' : 'b';

    // 从边缘缓存读取，命中则直接返回
    const cacheKey = `${bucket}:${url.pathname}`;
    const cached = await caches.default.match(cacheKey);
    if (cached) return cached;

    const resp = await fetch(`https://origin.example.com${url.pathname}`);
    await caches.default.put(cacheKey, resp.clone());
    return resp;
  },
};
```

```text
Edge 的典型职责：
1. 边缘缓存与改写 —— 命中即返，不回源
2. 个性化/鉴权 —— 在地域、Cookie 维度就近计算
3. 分流与灰度 —— A/B、灰度在边缘完成，源站无感
```

## API Gateway

API Gateway（网关）作为客户端请求的统一入口，负责路由、聚合、鉴权、限流、协议转换。对前端而言，网关可以把多个微服务接口聚合成一个面向页面的接口，减少客户端请求次数，也把限流、鉴权等横切逻辑收口到一处。

```yaml
# 网关路由配置示意（聚合多个后端服务）
routes:
  - path: /api/products/:id
    target: http://product-service
    methods: [GET]
  - path: /api/orders
    target: http://order-service
    methods: [GET, POST]
    rate_limit: 1000/min
  - path: /api/page/home
    # 页面级聚合：一次请求返回首页所需全部数据
    aggregate:
      - service: product-service
        path: /hot-products
      - service: banner-service
        path: /banners
```

```text
网关对高并发的价值：
1. 收口横切 —— 鉴权、限流、日志在网关统一处理
2. 接口聚合 —— 减少客户端请求数与网络往返
3. 路由与灰度 —— 流量切换在网关完成，客户端无感
```

## Rate Limit

限流（Rate Limit）在请求量超过阈值时拒绝或排队，保护后端不被突发流量打垮。前端相关的限流既发生在网关/服务端（按 IP、用户、接口维度），也发生在客户端（防抖、节流控制请求频率）。

```js
// 服务端：令牌桶限流（按用户维度）
class TokenBucket {
  constructor(capacity, refillPerSecond) {
    this.capacity = capacity;
    this.tokens = capacity;
    this.refill = refillPerSecond;
    this.last = Date.now();
  }

  take() {
    const now = Date.now();
    this.tokens = Math.min(
      this.capacity,
      this.tokens + ((now - this.last) / 1000) * this.refill,
    );
    this.last = now;
    if (this.tokens >= 1) {
      this.tokens -= 1;
      return true;
    }
    return false; // 拒绝或排队
  }
}
```

```js
// 客户端：节流控制高频事件触发的请求
function throttle(fn, wait) {
  let last = 0;
  return (...args) => {
    const now = Date.now();
    if (now - last >= wait) {
      last = now;
      fn(...args);
    }
  };
}
```

```text
限流策略：
1. 服务端兜底 —— 令牌桶/漏桶，防突发打垮后端
2. 客户端减负 —— 防抖节流，减少无效请求
3. 优雅降级 —— 超限返回 429，前端给出友好提示与重试
```

## 应用场景实战

### 场景一：静态化 + CDN 承载大促活动页

```bash
# 1. 构建期静态生成活动页 HTML
npm run build
# 产物输出 dist/，包含预渲染的 HTML/JS/CSS

# 2. 上传 CDN，入口 HTML 短缓存、静态资源长缓存
aws s3 sync dist/ s3://my-cdn-bucket/ --cache-control 'max-age=31536000, immutable'

# 3. 边缘节点分发，用户就近命中，源站零压力
```

```text
# 关键缓存头策略
/index.html        → Cache-Control: no-cache        # 入口要拿最新
/app.9d3b7e.js     → Cache-Control: max-age=31536000, immutable
/app.8f2c1a.css    → Cache-Control: max-age=31536000, immutable
```

### 场景二：网关聚合 + 结果缓存扛住热点接口

```js
// 网关对热点接口做结果缓存 + 限流，保护后端
const cache = new Map();

export async function handleProductDetail(req, res) {
  const { id } = req.params;

  if (!rateLimiter.take(req.ip)) {
    return res.status(429).json({ error: 'too many requests' });
  }

  const key = `product:${id}`;
  if (cache.has(key)) {
    return res.json(cache.get(key)); // 命中缓存，直接返回
  }

  const data = await fetchProduct(id);
  cache.set(key, data);
  setTimeout(() => cache.delete(key), 60_000); // 60 秒过期
  res.json(data);
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 静态资源一律走 CDN，文件名带内容 hash 做长缓存
2. HTML 入口短缓存或不缓存，静态资源长缓存 + immutable
3. 能静态化的页面优先静态化（SSG/ISR），源站压力最小
4. SSR 页面做结果缓存，公共页面避免重复渲染
5. 计算下沉到边缘，个性化与分流就近完成
6. 网关统一做限流、鉴权、聚合，后端只做业务

### 踩坑记录

```text
坑 1：入口 HTML 也设了长缓存
结论：发版后用户拿到的还是旧 HTML，引用不到新 JS，页面白屏或报错。
原因：index.html 被设成 max-age=31536000，浏览器一直用旧的。
解法：入口 HTML 用 no-cache（或很短 max-age），静态资源才用长缓存 + hash。

坑 2：静态资源不带 hash 导致缓存错乱
结论：改了 JS 内容但文件名没变，CDN 返回旧内容，发版不生效。
原因：文件名不带内容 hash，缓存无法感知内容变化。
解法：构建产物文件名强制带 contenthash，内容变则文件名变。

坑 3：SSR 页面不做缓存，CPU 被打满
结论：大促时每个请求都全量渲染，服务端 CPU 飙升、响应变慢。
原因：SSR 渲染是重 CPU 操作，没有结果缓存。
解法：公共页面做渲染结果缓存，命中后直接返回 HTML。

坑 4：限流只做了 IP 维度，误伤共享出口
结论：公司/校园共用出口 IP，一个人刷导致整片用户被限流。
原因：限流维度太粗，只按 IP。
解法：按用户 + 接口 + IP 多维度限流，合理配置阈值。

坑 5：静态化页面塞了实时数据
结论：活动页显示的是构建时的旧数据，用户看到过期信息。
原因：把实时数据也静态化进 HTML，没有刷新机制。
解法：实时数据用客户端请求或 ISR 增量再生，静态只承载骨架与不变内容。
```
