## 概述

Web Crypto API 是浏览器内置的密码学接口，通过 `window.crypto.subtle` 暴露，提供哈希、对称/非对称加解密、签名验签等能力。它只暴露在「安全上下文」（HTTPS 或 localhost）中，是前端在不引入第三方库的情况下做加密与安全编程的基础。

```text
Web Crypto API 的核心能力：
1. 安全上下文 —— 仅 HTTPS/localhost 可用，防止明文密钥在 HTTP 上泄露
2. 异步接口 —— subtle 的所有方法都返回 Promise，不阻塞主线程
3. 密钥抽象 —— 密钥是 CryptoKey 对象，默认不可导出原始字节
4. 算法白名单 —— 只暴露标准算法，避免自造轮子引入漏洞
```

```js
// 判断环境是否支持 Web Crypto
const isSecureContext = window.isSecureContext;         // 是否为安全上下文
const hasSubtle = !!window.crypto?.subtle;              // 是否有 subtle 接口
console.log({ isSecureContext, hasSubtle });
```

## crypto.subtle

`crypto.subtle` 是 SubtleCrypto 接口的实例，是所有密码学操作的入口。它提供的方法按用途可分为四类：哈希（digest）、密钥管理（generateKey/importKey/exportKey/deriveKey）、加解密（encrypt/decrypt）、签名验签（sign/verify）。

```js
// crypto.subtle 的方法总览
// 哈希
crypto.subtle.digest(algorithm, data)                       // 返回 ArrayBuffer
// 密钥管理
crypto.subtle.generateKey(algorithm, extractable, usages)   // 返回 CryptoKey 或 CryptoKeyPair
crypto.subtle.importKey(format, keyData, algorithm, extractable, usages)
crypto.subtle.exportKey(format, key)
// 加解密
crypto.subtle.encrypt(algorithm, key, data)
crypto.subtle.decrypt(algorithm, key, data)
// 签名验签
crypto.subtle.sign(algorithm, key, data)
crypto.subtle.verify(algorithm, key, signature, data)
```

```text
subtle 的「usages」约束：
1. encrypt / decrypt —— 对称加密用
2. sign / verify —— 签名验签用
3. deriveKey / deriveBits —— 密钥派生用
4. wrapKey / unwrapKey —— 密钥包裹用
5. 生成密钥时声明的 usages 决定了该 key 之后能做什么
```

## Digest（哈希摘要）

`digest` 用于计算数据的哈希值，支持 SHA-1、SHA-256、SHA-384、SHA-512 等算法。它是单向不可逆的，常用于校验文件完整性、生成内容指纹。

```js
// 计算 SHA-256 摘要
async function sha256(message) {
  const encoder = new TextEncoder();
  const data = encoder.encode(message);          // 字符串 → Uint8Array
  const hashBuffer = await crypto.subtle.digest('SHA-256', data);
  return toHex(hashBuffer);
}

// ArrayBuffer → 十六进制字符串
function toHex(buffer) {
  return [...new Uint8Array(buffer)]
    .map(b => b.toString(16).padStart(2, '0'))
    .join('');
}

sha256('hello world').then(hex => console.log(hex));
```

```text
Digest 的使用要点：
1. 输入是 BufferSource（ArrayBuffer/TypedArray），字符串需先 TextEncoder 编码
2. 输出是 ArrayBuffer，展示前通常转 hex 或 base64
3. 哈希不可逆，不能用于需要还原的场景（此时用加解密）
4. SHA-1 已不安全，新项目一律用 SHA-256 及以上
```

## GenerateKey（生成密钥）

`generateKey` 在浏览器内安全地生成密钥，密钥永远不会以明文形式出现在 JS 变量之外。对称算法（如 AES-GCM）返回单个 CryptoKey，非对称算法（如 ECDSA）返回 CryptoKeyPair。

```js
// 生成 AES-GCM 对称密钥
const aesKey = await crypto.subtle.generateKey(
  { name: 'AES-GCM', length: 256 },  // 算法与长度
  true,                               // extractable：是否可导出
  ['encrypt', 'decrypt']              // usages：允许的用途
);

// 生成 ECDSA 非对称密钥对
const ecdsaKeyPair = await crypto.subtle.generateKey(
  { name: 'ECDSA', namedCurve: 'P-256' },
  true,
  ['sign', 'verify']
);
console.log(ecdsaKeyPair.publicKey, ecdsaKeyPair.privateKey);
```

```text
GenerateKey 的参数三元组：
1. algorithm —— 算法对象，如 { name: 'AES-GCM', length: 256 }
2. extractable —— 布尔值，true 才允许 exportKey 导出
3. usages —— 用途数组，未声明的用途后续调用会报错
```

## ImportKey（导入密钥）

`importKey` 把外部得到的密钥材料（raw 字节、PEM、JWK）导入成 CryptoKey 对象，供后续加解密或验签使用。前端常见场景是从后端拿到 base64 的公钥后导入验签。

```js
// 导入 raw 格式的 AES 密钥（如后端下发的 32 字节密钥）
async function importAesKey(rawBytes) {
  return crypto.subtle.importKey(
    'raw',                              // 格式：raw / pkcs8 / spki / jwk
    rawBytes,                           // 密钥数据（BufferSource）
    { name: 'AES-GCM' },                // 算法
    false,                              // extractable
    ['encrypt', 'decrypt']              // usages
  );
}

// 导入 spki 格式的 RSA 公钥（base64 → bytes）
async function importRsaPublicKey(pemBase64) {
  const bytes = Uint8Array.from(atob(pemBase64), c => c.charCodeAt(0));
  return crypto.subtle.importKey(
    'spki',
    bytes,
    { name: 'RSA-OAEP', hash: 'SHA-256' },
    true,
    ['encrypt']
  );
}
```

```text
ImportKey 的格式（format）：
1. raw —— 原始字节，用于 AES/HMAC 对称密钥
2. pkcs8 —— 私钥标准格式（PKCS#8）
3. spki —— 公钥标准格式（SubjectPublicKeyInfo）
4. jwk —— JSON Web Key，键值对描述的密钥，便于传输
```

## ExportKey（导出密钥）

`exportKey` 把 CryptoKey 导出为可传输的格式。只有在生成/导入时声明了 `extractable: true` 的密钥才能导出，这是防止密钥被随意拿走的安全设计。

```js
// 导出为 JWK（最便于 JSON 传输）
async function exportAsJwk(key) {
  const jwk = await crypto.subtle.exportKey('jwk', key);
  return JSON.stringify(jwk);
}

// 导出 raw 字节并转 base64
async function exportAesKeyBase64(key) {
  const raw = await crypto.subtle.exportKey('raw', key);
  return btoa(String.fromCharCode(...new Uint8Array(raw)));
}
```

```text
ExportKey 的注意事项：
1. extractable: false 的密钥导出会抛 InvalidAccessError
2. 非对称密钥只能导出公钥部分（spki），私钥用 pkcs8
3. 导出的密钥落到明文，传输必须走 HTTPS
4. 生产环境尽量保持密钥不可导出，降低泄露面
```

## Encrypt（加密）

`encrypt` 用对称密钥（如 AES-GCM）或非对称公钥（如 RSA-OAEP）加密数据。AES-GCM 是 AEAD 算法，自带完整性校验，能同时保证机密性与完整性。

```js
// AES-GCM 加密
async function aesEncrypt(plainText, key) {
  const iv = crypto.getRandomValues(new Uint8Array(12)); // 12 字节随机 IV
  const encoded = new TextEncoder().encode(plainText);
  const cipherBuffer = await crypto.subtle.encrypt(
    { name: 'AES-GCM', iv },      // iv 每次加密都要新生成
    key,
    encoded
  );
  return {
    iv: toHex(iv),                                    // IV 需随密文一起保存
    cipherText: toHex(cipherBuffer)                   // 密文含 GCM 认证标签
  };
}

// RSA-OAEP 加密（用公钥，适合加密小数据）
async function rsaEncrypt(plainText, publicKey) {
  const encoded = new TextEncoder().encode(plainText);
  return crypto.subtle.encrypt(
    { name: 'RSA-OAEP' },
    publicKey,
    encoded
  );
}
```

```text
Encrypt 的要点：
1. AES-GCM 的 IV 每次加密必须随机且不重复，否则密钥会被破解
2. GCM 输出的密文自带认证标签，能检测数据是否被篡改
3. RSA-OAEP 只能加密小于密钥模长的数据，长数据用它加密 AES 密钥（密钥包裹）
4. 加密数据量较大时优先对称加密，性能远高于非对称
```

## Decrypt（解密）

`decrypt` 是 `encrypt` 的逆操作，用同一个对称密钥（或对应私钥）还原明文。AES-GCM 解密时若认证标签校验失败会抛错，说明密文被篡改。

```js
// AES-GCM 解密
async function aesDecrypt(ivHex, cipherHex, key) {
  const iv = hexToBytes(ivHex);
  const cipher = hexToBytes(cipherHex);
  const plainBuffer = await crypto.subtle.decrypt(
    { name: 'AES-GCM', iv },        // iv 必须与加密时一致
    key,
    cipher
  );
  return new TextDecoder().decode(plainBuffer);
}

// hex 字符串 → Uint8Array
function hexToBytes(hex) {
  const bytes = new Uint8Array(hex.length / 2);
  for (let i = 0; i < bytes.length; i++) {
    bytes[i] = parseInt(hex.slice(i * 2, i * 2 + 2), 16);
  }
  return bytes;
}
```

```text
Decrypt 的要点：
1. IV 必须和加密时完全相同，所以 IV 要随密文一起存/传
2. GCM 认证失败会抛 OperationError，应捕获并提示「数据被篡改」
3. 解密失败不要向用户暴露内部细节，避免信息泄露
```

## Sign（签名）

`sign` 用私钥对数据生成数字签名，用于证明「数据确实来自持有私钥的一方」。ECDSA 和 RSA-PSS 是前端最常用的签名算法。签名保证完整性与不可否认性，但不加密内容本身。

```js
// ECDSA 签名
async function signMessage(message, privateKey) {
  const encoded = new TextEncoder().encode(message);
  const signature = await crypto.subtle.sign(
    { name: 'ECDSA', hash: 'SHA-256' },   // hash 是签名内部使用的摘要算法
    privateKey,
    encoded
  );
  return toHex(signature);
}

// HMAC 签名（对称的完整性校验，双方共享同一密钥）
async function hmacSign(message, key) {
  const encoded = new TextEncoder().encode(message);
  const sig = await crypto.subtle.sign('HMAC', key, encoded);
  return toHex(sig);
}
```

```text
Sign 的要点：
1. 签名用私钥，验签用公钥，方向不能反
2. ECDSA 签名是随机化的，同一数据两次签名结果不同（正常现象）
3. HMAC 是「对称签名」，适合服务端与客户端共享密钥做请求校验
4. 签名不隐藏内容，需要保密要配合 encrypt
```

## Verify（验签）

`verify` 用公钥（或共享密钥）校验签名是否有效，返回布尔值。它是防止数据被篡改、确认来源可信的最后一道防线。

```js
// ECDSA 验签
async function verifyMessage(message, signatureHex, publicKey) {
  const encoded = new TextEncoder().encode(message);
  const signature = hexToBytes(signatureHex);
  return crypto.subtle.verify(
    { name: 'ECDSA', hash: 'SHA-256' },
    publicKey,
    signature,
    encoded
  );
}

// 使用示例：校验服务端返回的签名
const isValid = await verifyMessage(payload, sigHex, publicKey);
console.log('签名有效:', isValid);
```

```text
Verify 的要点：
1. 验签返回 boolean，不会抛「签名错误」异常，只有参数错误才抛错
2. 验签前必须确认公钥来源可信，否则可能被中间人替换公钥
3. 验签失败应视为数据不可信，直接拒绝处理
```

## 应用场景实战

### 场景一：文件完整性校验（SHA-256）

```js
// 计算上传文件的哈希，用于秒传/去重/校验
async function fileHash(file) {
  const buffer = await file.arrayBuffer();
  const hash = await crypto.subtle.digest('SHA-256', buffer);
  return [...new Uint8Array(hash)]
    .map(b => b.toString(16).padStart(2, '0'))
    .join('');
}

document.querySelector('#file').addEventListener('change', async (e) => {
  const file = e.target.files[0];
  const hash = await fileHash(file);
  console.log(`${file.name} 的 SHA-256: ${hash}`);
  // 可将 hash 上传给后端做秒传判断
});
```

### 场景二：端到端数据加解密（AES-GCM）

```js
// 用口令派生密钥，加密本地数据再存 localStorage
async function deriveKeyFromPassword(password, salt) {
  const keyMaterial = await crypto.subtle.importKey(
    'raw',
    new TextEncoder().encode(password),
    'PBKDF2',
    false,
    ['deriveKey']
  );
  return crypto.subtle.deriveKey(
    { name: 'PBKDF2', salt, iterations: 100000, hash: 'SHA-256' },
    keyMaterial,
    { name: 'AES-GCM', length: 256 },
    false,
    ['encrypt', 'decrypt']
  );
}

async function saveSecret(password, secret) {
  const salt = crypto.getRandomValues(new Uint8Array(16));
  const key = await deriveKeyFromPassword(password, salt);
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const cipher = await crypto.subtle.encrypt(
    { name: 'AES-GCM', iv },
    key,
    new TextEncoder().encode(secret)
  );
  localStorage.setItem('vault', JSON.stringify({
    salt: btoa(String.fromCharCode(...salt)),
    iv: btoa(String.fromCharCode(...iv)),
    cipher: btoa(String.fromCharCode(...new Uint8Array(cipher)))
  }));
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 密钥一律通过 generateKey 在安全上下文内生成，不要把密钥硬编码进源码
2. AES-GCM 的 IV 每次加密都重新随机生成，并随密文一起保存
3. 非对称算法（RSA/ECDSA）只处理小数据或密钥，大数据用对称加密
4. 哈希用 SHA-256 及以上，SHA-1 和 MD5 一律禁用
5. 敏感数据加密后再落 localStorage，密钥用 PBKDF2 从用户口令派生
6. 签名验签场景明确区分「私钥签名、公钥验签」的方向

### 踩坑记录

```text
坑 1：在 HTTP 页面上访问 crypto.subtle
结论：window.crypto.subtle 为 undefined，调用直接报错。
原因：Web Crypto 只暴露在安全上下文（HTTPS/localhost）。
解法：生产环境启用 HTTPS，本地开发用 localhost。

坑 2：AES-GCM 复用同一个 IV
结论：多次加密用相同 IV，攻击者可破解明文甚至伪造数据。
原因：GCM 是流式加密，IV 重复会泄露密钥流。
解法：每次加密用 crypto.getRandomValues 生成全新 IV。

坑 3：extractable 设为 false 后又去 exportKey
结论：导出密钥时抛出 InvalidAccessError。
原因：密钥生成时声明不可导出，系统强制拦截。
解法：确需导出就在生成时把 extractable 设为 true。

坑 4：把签名当加密用
结论：签名的数据仍以明文可见，敏感信息直接泄露。
原因：签名只保证完整性，不提供机密性。
解法：需要保密用 encrypt，需要证明来源用 sign，两者配合使用。

坑 5：TextEncoder 编码与 TextDecoder 解码不配对
结论：解密出乱码，或加密时字符丢失。
原因：编码与解码字符集不一致（如 UTF-8 加密、其他方式解码）。
解法：统一用 TextEncoder/TextDecoder 的 UTF-8 编解码。
```
