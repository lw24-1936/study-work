## 概述

前端安全不是「给代码加锁」，而是一套贯穿数据输入、存储、传输、输出的原则。核心认知是：浏览器端的一切都可以被用户查看和篡改，所以真正的秘密不能放前端，安全防线要架在服务端，前端只负责做好自己的那一环。

```text
前端安全七原则：
1. 不在前端保存 Secret —— 密钥/令牌的机密性只能靠服务端
2. HTTPS —— 传输加密，防窃听防篡改
3. Least Privilege —— 最小权限，能不给的权限绝不给
4. Input Validation —— 输入校验，所有输入都不可信
5. Output Encoding —— 输出编码，按上下文转义防注入
6. CSP —— 内容安全策略，限制可加载资源来源
7. Secure Cookie —— 敏感凭证用安全 Cookie 属性
```

```js
// 原则落地速查：判断当前上下文是否安全
const secure = {
  isHttps: location.protocol === 'https:',
  isSecureContext: window.isSecureContext,
  hasCrypto: !!window.crypto?.subtle,
};
console.log(secure);
```

## 不在前端保存 Secret

任何写进前端代码、打进 bundle、存进 localStorage 的「秘密」都不再是秘密。API Key、数据库密码、私钥、签名密钥等一律不能出现在前端，机密操作必须由服务端完成。

```js
// 反例：把密钥写死在前端（任何人都能从源码里拿到）
// const API_KEY = 'sk-live-xxxxxxxxxxxx';  // 绝对禁止

// 正例：前端只拿短期、可撤销的临时凭证，密钥在服务端
async function fetchData() {
  // 凭证由服务端在登录后签发，且设置过期时间
  const res = await fetch('/api/data', {
    headers: { Authorization: `Bearer ${await getAccessToken()}` },
    credentials: 'include',
  });
  return res.json();
}
```

```text
Secret 的边界：
1. 前端只放「可撤销、短期、最小权限」的临时凭证
2. 长期密钥、私钥、支付密钥只能存在服务端密钥管理系统
3. 加混淆、加环境变量都不算真安全，只是增加破解成本
4. 需要客户端加密时，用「用户口令派生密钥」而非硬编码密钥
```

## HTTPS

HTTPS 通过 TLS 加密传输内容，防止中间人窃听和篡改。它是所有其他安全机制的前提——没有 HTTPS，Cookie、Token、加密数据都会在传输途中裸奔。

```js
// 强制跳转 HTTPS（服务端 301 是首选，前端兜底）
if (location.protocol === 'http:' && location.hostname !== 'localhost') {
  location.replace(`https://${location.host}${location.pathname}`);
}
```

```text
HTTPS 的要点：
1. TLS 提供机密性（防窃听）+ 完整性（防篡改）+ 身份认证（防冒充）
2. 全站 HTTPS，禁止混合内容（HTTPS 页面加载 HTTP 资源）
3. 配置 HSTS 头，强制浏览器后续都用 HTTPS
4. 本地开发用 localhost 即可满足安全上下文要求
```

## Least Privilege

最小权限原则：任何主体（用户、Token、接口、密钥）只拥有完成任务所需的最小权限。前端表现为权限最小化——不该看到的菜单、按钮、接口、数据都不给。

```js
// 最小权限：按用户角色渲染能力，且后端强制校验
const permissions = {
  viewer: ['read'],
  editor: ['read', 'write'],
  admin: ['read', 'write', 'delete'],
};

function can(user, action) {
  return (permissions[user.role] || []).includes(action);
}

// 前端隐藏只是体验优化，真正的拦截在服务端
if (can(currentUser, 'delete')) {
  showDeleteButton();       // 无权限则不渲染
}
```

```text
Least Privilege 的落地：
1. Token 只包含所需 scope，别发一把万能钥匙
2. 前端隐藏按钮不等于安全，服务端必须二次校验
3. 第三方 SDK/脚本只授予其声明需要的最小能力
4. 定期回收不再需要的权限
```

## Input Validation

输入校验是「所有输入都不可信」原则的落地。来自用户、URL 参数、第三方接口、甚至 localStorage 的数据都可能是攻击向量，必须在边界处校验类型、长度、格式。

```js
// 前端校验（体验层）+ 服务端校验（安全层，必须）
function validateEmail(input) {
  const value = String(input).trim();
  if (!value) return '邮箱不能为空';
  if (value.length > 254) return '邮箱过长';
  // 格式校验
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(value)) return '邮箱格式错误';
  return null;
}

const error = validateEmail(userInput);
if (error) {
  showError(error);
} else {
  submit();   // 服务端仍要再校验一次
}
```

```text
Input Validation 的边界：
1. 前端校验是用户体验，服务端校验才是安全防线
2. 校验类型、长度、范围、格式、白名单枚举值
3. 优先白名单（只允许合法的），而非黑名单（只禁止已知非法的）
4. URL 参数、查询串、文件上传都视为不可信输入
```

## Output Encoding

输出编码是按输出上下文对数据进行转义，防止用户输入被当作代码执行（XSS 的核心防御）。关键原则：数据放进 HTML、属性、JS、CSS、URL 时，要用对应的转义规则。

```js
// 不同上下文的转义函数
function escapeHtml(str) {
  return String(str)
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;');
}

// 反例：直接拼接用户输入到 innerHTML
// element.innerHTML = userInput;                 // 危险，可能执行脚本

// 正例：用 textContent 或转义后再插入
element.textContent = userInput;                  // 安全，浏览器当纯文本
element.innerHTML = escapeHtml(userInput);        // 转义后安全
```

```text
Output Encoding 的上下文规则：
1. HTML 正文 → 转义 & < > " '
2. HTML 属性 → 同 HTML 转义，属性值必须加引号
3. JavaScript 上下文 → 用 JSON.stringify 而非手动拼接
4. URL 参数 → 用 encodeURIComponent
5. 现代框架默认转义，避免用 v-html / dangerouslySetInnerHTML
```

## CSP

CSP（Content Security Policy）通过响应头告诉浏览器「允许加载哪些来源的资源」，是防御 XSS 的纵深防线。即使攻击者成功注入了脚本，CSP 也能阻止它执行。

```text
CSP 响应头示例：
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com; img-src 'self' data:; style-src 'self' 'unsafe-inline'
```

```js
// 前端可用 meta 标签声明 CSP（推荐服务端响应头设置）
// <meta http-equiv="Content-Security-Policy"
//   content="default-src 'self'; script-src 'self'">
```

```text
CSP 的核心指令：
1. default-src —— 兜底来源，未单独指定的资源都遵循它
2. script-src —— 脚本来源，是防 XSS 的关键
3. style-src / img-src / font-src —— 样式、图片、字体来源
4. connect-src —— fetch/XHR/WebSocket 可连接的来源
5. 尽量避免 'unsafe-inline' 与 'unsafe-eval'
```

## Secure Cookie

Secure Cookie 是通过 Cookie 属性加固凭证安全的机制：`Secure` 只在 HTTPS 传输、`HttpOnly` 禁止 JS 读取（防 XSS 偷 Cookie）、`SameSite` 限制跨站携带（防 CSRF）。

```text
安全的 Set-Cookie 响应头示例：
Set-Cookie: sessionId=abc123; Secure; HttpOnly; SameSite=Strict; Path=/
```

```js
// 前端只能读取非 HttpOnly 的 Cookie，安全 Cookie 对 JS 不可见
document.cookie = 'theme=dark; Secure; SameSite=Lax; Path=/';
// 注意：HttpOnly 只能由服务端设置，JS 无法写入
```

```text
Secure Cookie 三属性：
1. Secure —— 只在 HTTPS 连接中发送，防明文传输泄露
2. HttpOnly —— JS 无法读取，XSS 也偷不走会话 Cookie
3. SameSite —— Strict/Lax/None，控制跨站请求是否携带 Cookie
4. 会话 Token 优先用 HttpOnly Cookie，而非 localStorage
```

## 应用场景实战

### 场景一：防 XSS 的用户评论渲染

```js
// 用户评论是典型的不信输入，渲染时按上下文编码
function renderComment(comment) {
  // 1. 输入校验：长度、允许的字符集
  const text = String(comment.text || '').slice(0, 500);

  // 2. 输出编码：用 textContent 而非 innerHTML
  const li = document.createElement('li');
  const author = document.createElement('strong');
  author.textContent = comment.author;      // 纯文本，安全
  const body = document.createElement('p');
  body.textContent = text;                   // 纯文本，安全
  li.append(author, body);
  return li;
}
```

### 场景二：带安全属性的登录态设置

```js
// 登录后服务端返回 Set-Cookie，前端无需存 token 到 localStorage
async function login(username, password) {
  const res = await fetch('/api/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    credentials: 'include',                  // 跨域也携带 Cookie
    body: JSON.stringify({ username, password }),
  });
  if (res.ok) {
    // 会话存在 HttpOnly Cookie 里，JS 拿不到，XSS 也偷不走
    location.replace('/dashboard');
  }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 密钥、私钥、长期 Token 一律不落前端，机密操作交给服务端
2. 全站 HTTPS + HSTS，禁用一切明文传输
3. 权限做前端体验 + 服务端强制的双重校验
4. 所有输入在边界校验，优先白名单策略
5. 渲染用户数据用 textContent 或框架默认转义，远离 innerHTML
6. 会话凭证用 HttpOnly + Secure + SameSite Cookie

### 踩坑记录

```text
坑 1：把 JWT 存进 localStorage
结论：XSS 一打，token 直接被人拿走。
原因：localStorage 可被任何脚本读取，没有 HttpOnly 隔离。
解法：会话 token 放 HttpOnly Cookie，或用短期 + 刷新机制。

坑 2：前端校验了就当安全
结论：绕过前端直接调接口，攻击者长驱直入。
原因：前端代码可被篡改，校验只是体验层。
解法：服务端必须对所有输入做完整校验。

坑 3：用 innerHTML 渲染用户输入
结论：用户输入被当成 HTML 执行，触发 XSS。
原因：innerHTML 会解析并执行脚本。
解法：用 textContent，或先做上下文转义。

坑 4：CSP 里到处写 'unsafe-inline'
结论：CSP 形同虚设，内联脚本照常执行。
原因：'unsafe-inline' 放开了内联脚本的封锁。
解法：用 nonce/hash 精确放行，避免全局 unsafe-inline。

坑 5：Cookie 没加 SameSite
结论：跨站请求自动带上凭证，遭 CSRF 攻击。
原因：默认策略下浏览器可能携带 Cookie 跨站发送。
解法：SameSite=Strict 或 Lax，配合 CSRF Token。
```
