## 概述

Git 是分布式版本控制系统，前端开发的日常操作几乎绕不开它：管理代码版本、多人协作、代码回溯、发布上线。

```text
Git 要解决的核心问题：
1. 记录每一次改动，随时回退到任意历史版本
2. 多人并行开发不互相覆盖，改动可合并
3. 分支隔离：新功能、修复、实验互不影响
```

```text
集中式（SVN）vs 分布式（Git）：
SVN —— 只有服务器一份完整历史，离线不能提交
Git —— 每个开发者本地都有完整仓库和全部历史，离线也能提交、看历史、开分支
```

前端工程师至少要能熟练做四件事：提交代码、开分支合并、解决冲突、回退改坏了的提交。本文按"基础概念 → 常用命令 → 协作工作流"展开。

## Git 基础与 Repository

Repository（仓库，简称 repo）是 Git 管理的项目目录，里面有个 `.git` 目录存着所有版本数据：

```bash
git init                 # 把当前目录变成仓库
git clone <url>          # 克隆远程仓库到本地
git status               # 看工作区状态（改了哪些文件）
git log --oneline        # 看提交历史
git remote -v            # 看远程仓库地址
```

```text
Git 三个区域：
1. 工作区（Working Directory）—— 你实际编辑的文件
2. 暂存区（Staging Area / Index）—— git add 之后、commit 之前的"待提交"区
3. 本地仓库（Repository）—— git commit 之后，版本历史存这里

文件流转：编辑（工作区）→ git add（暂存区）→ git commit（仓库）→ git push（远程）
```

```bash
git add .                # 把当前目录所有改动加入暂存区
git add src/index.js     # 只加指定文件
git commit -m "feat: 新增登录页"   # 提交暂存区
git push origin main     # 推送到远程 main 分支
git pull                 # 拉取远程更新并合并
```

```text
.gitignore 文件列出不纳入版本控制的文件/目录（node_modules、dist、.env 等）：
```

```gitignore
node_modules/
dist/
.env
*.log
```

## Commit

Commit（提交）是 Git 的最小版本单位，记录一次快照（不是差异，是整个文件树的快照）：

```text
每个 commit 包含：
1. 一个 SHA-1 哈希值（唯一标识，如 a1b2c3d）
2. 作者、提交时间、提交信息
3. 指向父 commit 的指针（形成链式历史）
4. 完整的文件快照（通过 tree/blob 对象引用）
```

```bash
git commit -m "fix: 修复导航栏样式"
git commit --amend              # 修改上一次提交（信息或内容）
git commit --amend -m "新信息"  # 只改提交信息
```

```text
关键概念：
HEAD —— 指向当前所在位置的指针（通常是当前分支的最新 commit）
哈希 —— 每次 commit 由内容计算出的唯一 ID，内容变哈希就变，保证不可篡改
```

```text
commit 要"小步、单一职责"：一个提交只做一件事（一个功能、一个修复），
信息写清楚做了什么和为什么。这决定以后 git log / bisect / revert 好不好用。
```

## Branch 与 Tag

### Branch：分支

Branch（分支）本质是一个指向某个 commit 的指针。开分支极轻量，所以 Git 鼓励频繁开分支：

```bash
git branch                    # 列出本地分支
git branch feature-login      # 创建分支（不切换）
git checkout feature-login    # 切换到分支
git checkout -b feature-login # 创建并切换（常用）
git switch feature-login      # 新命令，同 checkout 切换
git branch -d feature-login   # 删除分支
git merge feature-login       # 把分支合并到当前分支
```

```text
checkout 和 switch 的区别：checkout 既切分支又恢复文件，职责过重容易误用；
Git 2.23 后新增 switch（切分支）和 restore（恢复文件）拆分职责，新项目建议用它们。
```

### Tag：标签

Tag（标签）给某个 commit 打上固定名称，标记发布版本：

```bash
git tag v1.0.0                    # 轻量标签
git tag -a v1.0.0 -m "发布 1.0"    # 附注标签（含作者、时间、说明，推荐）
git tag                           # 列出标签
git push origin v1.0.0            # 推送标签
git push origin --tags            # 推送所有标签
git checkout v1.0.0               # 切换到标签对应的版本
```

```text
tag 和 branch 的区别：branch 会随提交移动，tag 是固定在某一个 commit 上的永久标记。
发布流程里 tag 标"这个版本就是 v1.0.0"，用于回滚和追溯。
```

## Merge、Rebase 与 Cherry-pick

### Merge：合并

Merge 把另一条分支的改动并入当前分支：

```bash
git checkout main
git merge feature-login
```

```text
两种合并方式：
1. Fast-forward（快进）—— 当前分支没有新提交，直接把指针移过去，历史是一条直线
2. 三方合并（3-way merge）—— 两条分支都有新提交，生成一个 merge commit 把两边合起来
```

```text
冲突（Conflict）：两个分支改了同一个文件的同一处，Git 无法自动决定，需要手动解决：
```

```bash
git merge feature-login
# 冲突时文件里会出现标记：
<<<<<<< HEAD
const name = "main 分支的版本";
=======
const name = "feature 分支的版本";
>>>>>>> feature-login

# 手动改成想要的最终版本，删除标记，然后：
git add .
git commit -m "merge: 合并 feature-login"
```

### Rebase：变基

Rebase 把当前分支的提交"搬"到目标分支最新提交之上，重写提交历史成一条直线：

```bash
git checkout feature-login
git rebase main
```

```text
merge vs rebase：
merge —— 保留两条分支的完整历史，产生 merge commit（历史是网状的）
rebase —— 把 feature 提交搬到 main 最新处，历史变成一条直线（更清爽）
```

```text
交互式 rebase 可以整理本地提交（合并、改信息、删除、调顺序）：
```

```bash
git rebase -i HEAD~3     # 整理最近 3 个提交
# 打开编辑器，可对每个提交选 pick（保留）/ squash（合并到上一个）/ reword（改信息）/ drop（删除）
```

```text
Rebase 黄金法则：不要 rebase 已经推送到共享仓库的分支。
rebase 会重写提交哈希，别人已经基于旧哈希开发，强制推送会把历史搞乱。
本地未推送的提交随便 rebase，公开的提交用 merge。
```

### Cherry-pick：挑拣提交

Cherry-pick 把指定的单个提交复制到当前分支：

```bash
git cherry-pick a1b2c3d          # 把提交 a1b2c3d 应用到当前分支
git cherry-pick a1b2c3d e4f5a6b  # 挑多个
```

```text
典型场景：hotfix 修复了 main 上的一个 bug，release 分支也需要这个修复，
但不想要 main 上其他改动，直接 cherry-pick 那一个修复提交过去。
```

## Reset、Revert、Stash、Reflog

### Reset：移动指针

Reset 把 HEAD 和分支指针移到指定提交，可选地处理暂存区和工作区：

```bash
git reset --soft HEAD~1    # 撤销提交，改动留在暂存区（可重新 commit）
git reset --mixed HEAD~1   # 撤销提交，改动回到工作区（默认，回到未 add 状态）
git reset --hard HEAD~1    # 撤销提交并丢弃所有改动（危险！）
git reset --hard origin/main  # 让本地完全对齐远程
```

```text
三档区别：
--soft —— 只动 HEAD（撤销 commit，改动还在暂存区）
--mixed —— 动 HEAD 和暂存区（撤销 commit + unstage，改动在工作区）
--hard  —— 全动（撤销 commit 并删掉改动，找不回来，除非有 reflog）
```

### Revert：反向提交

Revert 生成一个新的提交，内容是"撤销某次提交的改动"，不改写历史：

```bash
git revert a1b2c3d          # 撤销提交 a1b2c3d，生成新提交
```

```text
reset vs revert：
reset —— 回到过去，抹掉之后的提交（适合本地未推送的提交）
revert —— 新增一个"反向"提交撤销改动（适合已推送的提交，不改历史，安全）
```

### Stash：暂存改动

Stash 把未提交的改动临时收起来，让工作区变干净：

```bash
git stash                 # 暂存当前改动
git stash list            # 看暂存列表
git stash pop             # 取出最近一次并删除记录
git stash apply           # 取出但不删除记录
git stash drop            # 删除记录
git stash push -m "描述"  # 带说明暂存
```

```text
场景：功能写到一半，突然要切分支改个紧急 bug，又不想提交半成品，
git stash 收起来，切走修 bug，回来 git stash pop 恢复继续写。
```

### Reflog：后悔药

Reflog 记录 HEAD 的所有移动历史，是找回"丢失"提交的终极手段：

```bash
git reflog                 # 看 HEAD 移动历史（含被 reset 掉的提交）
git reset --hard HEAD@{2}  # 回到 reflog 里第 2 条记录指向的状态
```

```text
reset --hard 误删了提交？git reflog 能找回。reflog 是本地记录（默认保留 90 天），
只要提交过，reflog 里就有痕迹，所以 reset --hard 之后别慌，先看 reflog。
```

## Diff、Blame、Bisect

### Diff：看差异

```bash
git diff                    # 工作区 vs 暂存区的差异（未 add 的改动）
git diff --staged           # 暂存区 vs 上次提交的差异（已 add 的改动）
git diff main feature-login # 两个分支的差异
git diff a1b2c3d e4f5a6b    # 两个提交的差异
git diff --stat             # 只看改动了哪些文件、多少行
```

### Blame：追责

Blame 显示每一行代码是谁、哪个提交改的：

```bash
git blame src/index.js              # 每行显示作者和提交哈希
git blame -L 10,20 src/index.js     # 只看第 10-20 行
git blame -L 10,20 a1b2c3d src/index.js  # 看某个历史版本
```

```text
场景：发现一段有问题的代码，想知道当初是谁、为什么这么写，blame 定位提交，
再结合 git log 看提交信息，或者直接找当事人确认。
```

### Bisect：二分定位

Bisect 用二分法在历史提交里找出引入 bug 的那一次：

```bash
git bisect start              # 开始二分
git bisect bad                # 标记当前版本有问题
git bisect good v1.0.0        # 标记某个好版本
# Git 自动 checkout 中间版本，你测试后标记 good/bad：
git bisect good               # 或 git bisect bad
# 重复直到找到引入 bug 的提交
git bisect reset              # 结束二分，回到原分支
```

```text
场景：线上突然出 bug，但最近提交了几十个，不知道哪个引入的。
bisect 每次砍一半，几十个提交最多测试五六次就能定位。
```

## Submodule 与 Worktree

### Submodule：嵌套仓库

Submodule 让一个仓库引用另一个独立仓库（项目依赖的共享库、主题、文档）：

```bash
git submodule add <url> libs/shared    # 添加子模块
git submodule update --init --recursive  # 拉取子模块内容（克隆后必做）
git submodule update --remote          # 更新子模块到远程最新
```

```text
submodule 记录的是"指向哪个 commit 的指针"，不是代码本身。
clone 一个带 submodule 的仓库后，子模块目录是空的，必须 update --init 拉取。
```

### Worktree：多工作目录

Worktree 让同一个仓库同时 checkout 多个分支到不同目录，不用来回切：

```bash
git worktree add ../project-hotfix hotfix   # 在新目录 checkout hotfix 分支
git worktree list                            # 看所有 worktree
git worktree remove ../project-hotfix        # 删除 worktree
```

```text
场景：当前目录在跑 dev 开发，突然要改 main 的紧急 bug，
不想 stash 也不想切分支，worktree 在另一个目录并行操作，互不干扰。
前端多版本并行构建、并行审查 MR 时很有用。
```

## Git Hooks

Hooks 是 Git 在特定事件（提交、推送）触发时自动执行的脚本：

```text
常用 hooks：
pre-commit      —— commit 前执行（代码检查、格式化、lint）
commit-msg      —— 校验提交信息格式
pre-push        —— push 前执行（跑测试）
post-merge      —— 合并后执行（重新装依赖）
```

```bash
# hooks 存在 .git/hooks/ 目录，去掉 .sample 后缀即启用
ls .git/hooks/
```

```text
前端项目里 hooks 通常不手写，而是用工具管理（因为 .git/hooks 不随仓库提交）：
1. Husky —— 把 hooks 脚本纳入版本控制，团队共享（npm 生态主流）
2. lint-staged —— 只对暂存的文件跑 lint/format，快
```

```json
// package.json（Husky + lint-staged 典型配置）
{
  "lint-staged": {
    "*.{js,ts,tsx}": ["eslint --fix", "prettier --write"]
  }
}
```

```bash
# Husky 配置 pre-commit 钩子
npx husky add .husky/pre-commit "npx lint-staged"
```

```text
Hooks 的价值：把代码质量检查前置到提交前，坏代码进不了仓库。
前提是钩子要快（只查改动文件），不然开发体验很差，反而有人绕过 --no-verify。
```

## Conventional Commits

Conventional Commits（约定式提交）是一套提交信息规范，让提交信息结构化、可自动化：

```text
格式：<type>(<scope>): <subject>
type（类型）：
feat     —— 新功能
fix      —— 修复 bug
docs     —— 文档改动
style    —— 格式（不影响代码逻辑，如空格、分号）
refactor —— 重构（既不是新功能也不是修 bug）
test     —— 增加/修改测试
chore    —— 构建、依赖、工具等杂项
perf     —— 性能优化
build    —— 构建系统或外部依赖
ci       —— CI 配置

scope（可选）—— 改动范围，如 feat(auth): 新增登录
```

```bash
git commit -m "feat: 新增用户登录功能"
git commit -m "fix(button): 修复按钮点击无效"
git commit -m "feat!: 重构 API 接口"     # ! 表示破坏性变更（BREAKING CHANGE）
git commit -m "refactor: 抽取公共请求函数"
```

```text
规范的价值：
1. 一眼看出提交是干嘛的，git log 清晰
2. 可自动生成 changelog 和版本号（semantic-release 按 feat/fix 自动发版）
3. 团队协作统一，review 时好定位
```

```text
与语义化版本（SemVer）的联动：
feat → 次版本号 +1（1.0.0 → 1.1.0）
fix  → 修订号 +1（1.0.0 → 1.0.1）
feat! → 主版本号 +1（1.0.0 → 2.0.0）
```

## 分支模型：Git Flow 与 Trunk Based Development

### Git Flow

Git Flow 是多分支协作的经典模型，适合有明确版本发布周期的项目：

```text
分支结构：
main       —— 稳定生产分支，只存已发布版本
develop    —— 开发主分支，所有 feature 合并到这里
feature/*  —— 功能分支，从 develop 分出，完成后合回 develop
release/*  —— 发布分支，从 develop 分出，准备发布，修 bug 后合并到 main 和 develop
hotfix/*   —— 紧急修复，从 main 分出，修复后合并到 main 和 develop
```

```text
流程：
1. 新功能：develop 拉 feature/login → 开发 → 合回 develop
2. 发布：develop 拉 release/1.0 → 测试修 bug → 合回 main（打 tag）和 develop
3. 紧急修复：main 拉 hotfix/x → 修 → 合回 main（打 tag）和 develop
```

```text
优点：结构清晰，各分支职责明确，适合大团队和长周期版本
缺点：分支多、合并链路长，发布慢，小团队会觉得繁琐
```

### Trunk Based Development

Trunk Based Development（主干开发，TBD）是所有人都往主干（trunk/main）提交，用短生命周期分支 + 功能开关控制发布：

```text
核心原则：
1. 只有一个长期分支 main，所有人直接在上面开发
2. 分支生命周期极短（几小时到一两天），改完立即合并回主干
3. 未完成的功能用 feature flag（功能开关）隐藏，而不是靠长分支隔离
4. 频繁小步提交，靠 CI 持续集成保证主干始终可用
```

```text
对比：

| 维度 | Git Flow | Trunk Based |
|---|---|---|
| 长期分支 | main + develop | 只有 main |
| 功能分支生命周期 | 几天到几周 | 几小时到一两天 |
| 发布方式 | 版本周期，打 tag | 持续部署，feature flag 控制 |
| 合并频率 | 低（周期性） | 高（每天多次） |
| 适合团队 | 大团队、长周期版本 | 追求快速交付、持续部署 |
```

```text
前端/互联网公司现在大多倾向 TBD 或其变体（GitHub Flow）：
GitHub Flow = 只有 main + 短期 feature 分支 + PR 合并，比 Git Flow 简单，比 TBD 多了 PR 审查环节。
```

## Monorepo

Monorepo（单仓库）是把多个项目/包放在同一个 Git 仓库里管理：

```text
├── apps/
│   ├── web/          # 前端应用
│   └── admin/        # 管理后台
├── packages/
│   ├── ui/           # 共享 UI 组件库
│   └── utils/        # 共享工具库
├── package.json
└── pnpm-workspace.yaml
```

```text
monorepo vs 多仓库（polyrepo）：

| 维度 | Monorepo | 多仓库 |
|---|---|---|
| 代码复用 | 直接引用，原子提交 | 发布 npm 包，跨仓库协作 |
| 改动范围 | 一次提交跨多个包 | 各仓库独立提交 |
| 依赖管理 | 统一版本，锁文件一致 | 各仓库独立，版本易漂移 |
| 仓库规模 | 大，clone 慢 | 小，各自快 |
| 权限控制 | 粗（整仓库） | 细（按仓库） |
```

```text
前端 Monorepo 工具：
1. pnpm workspace —— pnpm 自带，轻量，npm/yarn 也有 workspace
2. Turborepo —— 缓存构建产物，增量构建，大幅提速
3. Nx —— 功能更全（依赖图、缓存、生成器），大团队用
4. Lerna —— 老牌工具，现在多被上面替代
```

## Pull Request 与 Code Review

### Pull Request

Pull Request（PR，GitLab 里叫 Merge Request）是请求把某分支的改动合并到目标分支的机制：

```text
完整流程：
1. 从 main 拉 feature 分支，开发提交
2. 推送到远程：git push origin feature-login
3. 在平台（GitHub/GitLab/Gitee）创建 PR，填描述、指定 reviewer
4. reviewer 审查，提意见，作者修改后继续 push（PR 自动更新）
5. 通过后合并（merge / squash merge / rebase merge）
6. 删除 feature 分支
```

```bash
# 典型的 PR 工作流命令
git checkout -b feature-login        # 1. 开分支
git add . && git commit -m "feat: 登录功能"  # 2. 提交
git push origin feature-login        # 3. 推送
# ... 平台上创建 PR，review，修改 ...
git push origin feature-login        # 修改后再次推送，PR 自动更新
```

```text
三种合并方式：
merge commit —— 保留完整历史，产生 merge commit（最保真）
squash merge —— 把 PR 的所有提交压成一个提交（历史最干净，常用）
rebase merge —— 把 PR 提交变基到目标分支，历史成直线
```

### Code Review

Code Review（代码审查）是合并前由他人检查代码的流程，核心目的是发现 bug、保证质量、共享知识：

```text
Review 重点：
1. 逻辑正确性：边界条件、错误处理、潜在 bug
2. 可维护性：命名、结构、重复代码、可读性
3. 安全性：输入校验、注入、敏感信息
4. 性能：不必要的循环、大对象、内存泄漏
5. 是否遵循项目规范（代码风格、目录结构）
```

```text
提交 PR 的注意事项：
1. PR 要小（几百行以内），大 PR 没人愿意认真看
2. 写清楚背景、改动内容、测试方式
3. 一个 PR 只做一件事
4. 主动自查一遍再请求 review（别浪费 reviewer 时间挑低级错误）

Review 的注意事项：
1. 对事不对人，评论具体代码不攻击人
2. 区分"必须改"和"建议改"
3. 及时 review，别让 PR 晾太久
```

## 应用场景实战

### 场景 1：功能开发完整流程

从拉取最新代码到提交 PR 的标准操作：

```bash
# 1. 拉取最新代码
git checkout main
git pull

# 2. 开功能分支
git checkout -b feature/user-list

# 3. 开发 + 频繁小步提交
git add src/pages/UserList.jsx
git commit -m "feat: 新增用户列表页面"
git add src/api/user.js
git commit -m "feat: 新增用户列表接口"

# 4. 推送并创建 PR
git push origin feature/user-list

# 5. review 后按意见修改，追加提交
git add src/pages/UserList.jsx
git commit -m "fix: 修复列表分页问题"
git push origin feature/user-list

# 6. 合并后切回 main 同步，删本地分支
git checkout main
git pull
git branch -d feature/user-list
```

### 场景 2：线上出 bug 紧急修复

```bash
# 1. 从 main 拉 hotfix 分支
git checkout main
git pull
git checkout -b hotfix/login-crash

# 2. 修复并提交
git add src/Login.jsx
git commit -m "fix: 修复登录页崩溃"
git push origin hotfix/login-crash

# 3. 合并后打 tag 发布
git checkout main
git merge hotfix/login-crash
git tag -a v1.0.1 -m "修复登录崩溃"
git push origin main --tags
```

### 场景 3：改坏了的代码要回退

```bash
# 情况 A：刚提交还没推送，直接撤销这次提交（改动保留）
git reset --soft HEAD~1

# 情况 B：已推送，用 revert 安全撤销（不改历史）
git revert a1b2c3d
git push origin main

# 情况 C：reset --hard 误删了提交，用 reflog 找回
git reflog
git reset --hard HEAD@{3}
```

## 最佳实践与踩坑记录

### 最佳实践

1. commit 小步、单一职责，信息遵循 Conventional Commits 规范
2. 本地未推送的提交用 reset/rebase 整理，已推送的提交用 revert 撤销
3. 开功能分支开发，通过 PR + Code Review 合并，不直接往 main 推
4. PR 保持小规模，写清楚改动内容和测试方式
5. 用 Husky + lint-staged 把 lint/format 前置到提交前
6. node_modules、dist、.env 进 .gitignore，敏感信息不进仓库
7. 定期 git fetch + rebase 同步主干，减少合并冲突

### 踩坑记录

```text
坑 1：rebase 了已经推送的分支，强制推送搞乱团队
结论：git push --force 之后同事的本地分支全乱了。
原因：rebase 重写了提交哈希，别人的历史基于旧哈希。
解法：公开分支用 merge 不用 rebase；确需强推用 git push --force-with-lease（推送前检查远程是否有新提交）。

坑 2：冲突标记没删干净就提交
结论：提交后代码里留着 <<<<<<< ======= >>>>>>>，直接报语法错误。
原因：解决冲突时只改了一处，漏删了标记。
解法：解决完冲突 grep -rn "<<<<<<<" . 全局搜一遍确认无残留再 add commit。

坑 3：reset --hard 把没提交的代码删了
结论：工作区辛辛苦苦写的代码没了。
原因：--hard 会直接丢弃工作区改动，没有经过暂存区就找不回。
解法：reset 前先 git stash 或 commit 保底；误删后立即 git reflog 找，找不回就认了。

坑 4：把 .env 或密钥提交进了仓库
结论：敏感信息进了版本历史，删文件也没用，历史里还有。
原因：.gitignore 没配好，或加了文件后才想起来加 ignore（ignore 对已跟踪文件无效）。
解法：立即轮换密钥，用 git filter-repo 从历史中清除；.gitignore 要在 add 之前配好。

坑 5：直接 git pull 拉出混乱的合并历史
结论：本地和远程各有提交时，git pull 默认 merge 产生一堆 merge commit。
原因：git pull = fetch + merge，默认策略是 merge 而非 rebase。
解法：git pull --rebase 让本地提交变基到远程之上，历史干净；或配置 pull.rebase true。

坑 6：切分支忘了提交，改动被带过去
结论：改动跟着 checkout 跑到别的分支，污染了目标分支。
原因：未提交的改动在工作区，属于所有分支共享，切分支会带着走。
解法：切分支前 git status 确认工作区干净，或用 git stash 暂存。
```
