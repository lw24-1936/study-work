## 概述

Git 是分布式版本控制系统，核心是记录文件的**快照**而非差异。前端工程师每天都要用它：分支、合并、回滚、协作。这篇笔记不讲安装和 `git init` 这种入门操作，而是讲清楚版本控制的核心机制和工程实践——哪些命令会改写历史、哪些操作有风险、团队协作用什么分支模型。

Git 的三个核心概念：

```text
工作区（Working Directory） —— 你当前看到的文件
暂存区（Staging Area / Index） —— git add 后、git commit 前的状态
版本库（Repository / Object Store） —— git commit 后保存的快照
```

Git 的数据模型可以理解为一张有向无环图（DAG），每个 commit 是一个节点，指向它的父节点（parent）。分支只是一个指向某个 commit 的**可变指针**。

## Git 基础与 Repository

Repository（仓库）分两种：

```text
本地仓库 —— 在你机器上的 .git 目录，包含完整历史
远程仓库 —— 托管在 GitHub/GitLab/Gitee 的副本，用于协作
```

`.git` 目录是仓库的本体，删掉它仓库就没了（历史全丢）。里面几个关键部分：

```text
.git/objects/    —— 所有对象的存储（commit、tree、blob、tag）
.git/refs/       —— 分支和标签的指针
.git/HEAD        —— 当前检出的分支引用
.git/config      —— 仓库级配置
.git/hooks/      —— Git Hooks 脚本
```

常用基础命令与对象模型：

```bash
git init                 # 初始化仓库
git clone <url>          # 克隆远程仓库
git add <file>           # 加入暂存区
git status               # 查看工作区/暂存区状态
git log --oneline --graph # 查看提交历史（图形化）
git config --global user.name / user.email  # 配置提交身份
```

对象模型里四种对象：

```text
blob   —— 文件内容（不含文件名）
tree   —— 目录结构（文件名 + blob/tree 引用）
commit —— 一次提交（tree + parent + author + message）
tag    —— 附注标签（指向 commit，含签名信息）
```

理解 blob 和 tree 就能理解 Git 的「内容寻址」：相同内容的文件只存一份，文件名变更是零成本的（tree 里改个指针即可）。这也是 `git mv` 重命名能被 Git 自动追踪的原因。

## Commit 与提交历史

Commit 是 Git 的基本单位，包含：作者、提交者、时间戳、提交信息、指向 tree 的指针、指向父 commit 的指针。

```bash
git commit -m "message"      # 提交暂存区
git commit -am "message"     # 跳过 add，直接提交已追踪文件的修改（新文件不包含）
git commit --amend           # 修改最近一次提交（补充漏掉的文件或改信息）
```

Commit 的不可变性：commit 一旦生成，其内容由 SHA-1（新版 SHA-256）哈希唯一标识，改任何字段都会得到全新哈希。这是「改写历史」所有操作（amend、rebase）的本质——不是修改旧 commit，而是生成新 commit 替换它。

```text
commit 哈希为什么这么长：
SHA-1 是 40 位十六进制。前 7 位通常足够唯一定位一个 commit，
git log --oneline 默认显示前 7 位。日常用前 7 位即可。
```

写好 commit message 值得投入，它直接决定半年后你能否看懂这段历史。规范见下文「Conventional Commits」。

## Branch 与 Tag

Branch 是一个指向 commit 的轻量指针，创建和切换几乎零成本。

```bash
git branch                    # 列出本地分支
git branch <name>             # 创建分支（不切换）
git checkout <name>           # 切换分支（旧语法）
git switch <name>             # 切换分支（新语法，语义更清晰）
git checkout -b <name>        # 创建并切换
git switch -c <name>          # 创建并切换（新语法）
git branch -d <name>          # 删除已合并分支
git branch -D <name>          # 强制删除分支（丢失未合并提交）
```

分支的两种类型：

```text
本地分支 —— 只存在于本地仓库
远程跟踪分支（如 origin/main） —— 本地缓存的远程分支状态
```

Tag 是固定的「里程碑」指针，常用于标记发版：

```bash
git tag                      # 列出标签
git tag v1.0.0               # 轻量标签（只是一个指针）
git tag -a v1.0.0 -m "..."   # 附注标签（含作者、时间、信息）
git push origin v1.0.0       # 推送标签
git push origin --tags       # 推送所有标签
```

轻量标签 vs 附注标签：附注标签是独立对象（含签名信息），轻量标签只是 refs/tags 下的一个指针。发版一律用附注标签。

## Merge、Rebase 与 Cherry-pick

这是 Git 最核心、最容易混淆的三个整合操作。

### Merge（合并）

把两个分支的历史合并，生成一个 merge commit。

```bash
git checkout main
git merge feature   # 把 feature 合并进 main
```

```text
merge 的三种情况：
1. Fast-forward（快进）—— main 没有新提交，直接移动指针，不产生 merge commit
2. 三方合并 —— 两个分支都有新提交，生成 merge commit
3. 冲突 —— 同一文件同一区域被不同修改，需要手动解决
```

解决冲突的流程：

```bash
git merge feature          # 提示冲突
# 手动编辑冲突文件，删掉 <<<<<<< ======= >>>>>>> 标记
git add <冲突文件>
git commit                 # 完成 merge commit
```

### Rebase（变基）

把当前分支的提交「移动」到目标分支最新提交之后，重写提交历史，使历史线性。

```bash
git checkout feature
git rebase main            # 把 feature 的提交重放到 main 之上
```

```text
merge vs rebase：
merge —— 保留真实历史，有分叉有合并，历史完整但杂乱
rebase —— 历史线性干净，但改写历史（提交哈希全变）

规则：公共分支（main）永远不 rebase，只在自己的 feature 分支上 rebase。
```

### Cherry-pick（拣选）

把某个提交「复制」到当前分支，不改写原提交。

```bash
git cherry-pick <commit-hash>        # 拣选单个提交
git cherry-pick A..B                 # 拣选 A 到 B 的提交范围
git cherry-pick --continue           # 解决冲突后继续
```

典型场景：hotfix 分支修了一个 bug，需要同时合到 main 和 release 分支——在 main 上 cherry-pick 那个修复提交即可，不必合并整个 hotfix 分支。

## Reset、Revert 与回滚

回滚操作分「撤销」和「回滚」两种，关键是区分它们对历史的影响。

```bash
git reset --soft HEAD~1    # 撤销提交，改动保留在暂存区
git reset --mixed HEAD~1   # 撤销提交和暂存，改动保留在工作区（默认）
git reset --hard HEAD~1    # 撤销提交、暂存和工作区改动（危险，改动全丢）
git revert <commit>        # 生成一个新提交，反向撤销某提交的改动
```

```text
reset 三种模式的对比：
--soft  —— 只移动 HEAD 指针，暂存区和工作区不变
--mixed —— 移动 HEAD + 重置暂存区，工作区不变
--hard  —— 移动 HEAD + 重置暂存区 + 丢弃工作区改动

reset vs revert：
reset —— 改写历史（历史里看不到被撤销的提交），适合本地未推送的提交
revert —— 新增反向提交（保留完整历史），适合已推送到远程的提交
```

关键原则：**已推送的提交永远用 revert 而不是 reset**，否则其他协作者的历史会和你分叉。

```bash
# 恢复工作区某个文件到最近提交状态（丢弃本地改动）
git checkout -- <file>
git restore <file>

# 取消暂存（unstage）
git reset HEAD <file>
git restore --staged <file>
```

## Stash、Reflog 与 Diff

### Stash（暂存现场）

临时保存未提交的改动，切分支处理紧急任务。

```bash
git stash                 # 保存工作区+暂存区改动
git stash save "message"  # 带说明保存
git stash list            # 查看 stash 列表
git stash pop             # 恢复最近一次 stash 并删除记录
git stash apply           # 恢复但不删除记录
git stash drop            # 删除某条 stash
```

### Reflog（后悔药）

记录 HEAD 和分支的所有移动历史，是「误操作」的最后防线。

```bash
git reflog                # 查看 HEAD 移动历史
git reflog <branch>       # 查看某分支的移动历史
git reset --hard HEAD@{2} # 恢复到 reflog 里记录的某个状态
```

```text
reflog 为什么是后悔药：
即使 git reset --hard 把 commit 从分支里删掉了，
reflog 仍保留那个 commit 的哈希（默认 90 天），
所以能「找回」被误删的提交。
```

### Diff（差异对比）

```bash
git diff                  # 工作区 vs 暂存区
git diff --cached         # 暂存区 vs 最近提交
git diff HEAD             # 工作区 vs 最近提交
git diff main..feature    # 两个分支的差异
git diff <commitA> <commitB>  # 两个提交的差异
```

## Blame 与 Bisect

### Blame（溯源）

查某行代码是谁、哪个 commit 改的。

```bash
git blame <file>          # 逐行显示作者和提交
git blame -L 10,20 <file> # 只看第 10-20 行
```

用途：定位一个 bug 是哪次提交引入的，或理解一段历史代码的来龙去脉。

### Bisect（二分定位）

在大量提交中二分查找「坏提交」——哪个提交引入了问题。

```bash
git bisect start          # 开始二分
git bisect bad            # 标记当前提交是坏的（有问题）
git bisect good <hash>    # 标记一个已知好的提交
# Git 自动切换到中间提交，你测试后标记：
git bisect good           # 或 git bisect bad
# 重复直到定位到引入问题的提交
git bisect reset          # 结束二分，回到原分支
```

## Submodule 与 Worktree

### Submodule（子模块）

在一个仓库里引用另一个独立仓库，适合共享库或跨项目复用。

```bash
git submodule add <url> <path>   # 添加子模块
git clone --recurse-submodules <url>  # 克隆含子模块的仓库
git submodule update --init --recursive  # 初始化并更新子模块
```

```text
submodule 的本质：
主仓库只记录子模块的「指针」（指向子模块某 commit 的哈希），
不包含子模块的实际内容。所以克隆后必须单独 update 才能拿到代码。
```

坑：submodule 更新后，主仓库要提交子模块指针的变更，否则别人拉到的还是旧版本。

### Worktree（多工作目录）

同一仓库检出多个分支到不同目录，同时工作。

```bash
git worktree add ../project-hotfix hotfix-branch  # 检出分支到独立目录
git worktree list                # 列出所有 worktree
git worktree remove ../project-hotfix  # 移除
```

典型场景：正在开发功能，突然要修 hotfix——不用 stash，直接 worktree 开个新目录修 hotfix 分支。

## Git Hooks

Git 在特定事件（commit、push、merge）触发时执行的脚本，位于 `.git/hooks/`。用于自动化检查。

```text
常用 hook：
pre-commit     —— commit 前触发，做 lint/格式化（husky 的核心）
commit-msg     —— 校验 commit message 格式（commitlint）
pre-push       —— push 前触发，跑测试
post-merge     —— merge 后触发，如自动安装新依赖
```

前端工程里 hooks 配合 husky + lint-staged 使用：

```bash
# package.json 里 husky + lint-staged 配置
{
  "lint-staged": {
    "*.{js,ts,jsx,tsx}": ["eslint --fix", "prettier --write"]
  }
}
```

```text
hook 的本质限制：
.git/hooks/ 是本地目录，不会随 push 同步到远程。
所以团队统一 hook 需要 husky 这类工具，在 install 时写入 hook。
```

## 提交规范：Conventional Commits

Conventional Commits 约定提交信息的格式，让历史可读、可自动化（生成 changelog、决定版本号）。

```text
<type>(<scope>): <subject>

type     —— 提交类型
scope    —— 影响范围（可选）
subject  —— 简短描述（祈使句，不超过 50 字符）
```

```text
常用 type：
feat     —— 新功能
fix      —— 修复 bug
docs     —— 文档变更
style    —— 代码格式（不影响逻辑）
refactor —— 重构（不是新功能也不是修 bug）
perf     —— 性能优化
test     —— 测试相关
build    —— 构建系统或依赖变更
ci       —— CI 配置变更
chore    —— 其他杂项
```

示例：

```bash
git commit -m "feat(login): 新增手机号登录"
git commit -m "fix(cart): 修复购物车数量计算错误"
git commit -m "refactor(router): 抽取路由守卫公共逻辑"
```

配套工具 commitlint 校验信息格式：

```js
// commitlint.config.js
module.exports = { extends: ['@commitlint/config-conventional'] };
```

## 分支模型：Git Flow 与 Trunk Based Development

### Git Flow

经典分支模型，分支类型多、流程重，适合有明确发版节奏的项目。

```text
分支类型：
main       —— 生产分支，只存已发布代码
develop    —— 开发主分支，集成所有 feature
feature/*  —— 功能分支，从 develop 分出，完成合回 develop
release/*  —— 发布分支，从 develop 分出，准备发版，修复后合并到 main 和 develop
hotfix/*   —— 紧急修复，从 main 分出，修复后合并回 main 和 develop
```

```text
适用场景：版本化交付的软件（App、桌面端），发版周期长。
缺点：分支多、合并路径复杂，团队小或持续部署时显得笨重。
```

### Trunk Based Development（主干开发）

所有人都直接提交到 main（trunk），通过短生命周期分支 + 频繁合入保持主干始终可发布。

```text
核心原则：
1. 分支存活不超过 1-2 天
2. 小步提交，频繁合入主干
3. 用 Feature Flag 控制未完成功能的可见性
4. 主干永远可部署
```

```text
适用场景：持续交付/部署的 Web 项目，这是现代前端团队的主流。
关键配套：Feature Flag（功能开关）——功能没做完但代码已合入主干时，
用开关隐藏，而不是用长分支隔离。
```

## Monorepo 与 Git

Monorepo 是把多个项目/包放在一个 Git 仓库里管理，配套工具 pnpm workspace、Turborepo、Nx。

```text
monorepo 与 Git 的关系：
1. 单一仓库 —— 所有包的提交历史集中，跨包改动一次提交完成
2. 原子提交 —— 改 A 包 API 同时改 B 包调用方，一个 commit 保证一致
3. 统一 tag —— 发版时统一打 tag，版本一致性可追溯
```

```bash
# monorepo 里常见的原子提交
git commit -m "feat(shared): 提取通用类型到 @repo/types"
git commit -m "refactor: 全仓升级 React 19"
```

Monorepo 的取舍：仓库会变大（大厂仓库动辄几十 GB），需要 sparse-checkout 或部分克隆缓解。

## Pull Request 与 Code Review

Pull Request（PR，GitLab 里叫 Merge Request）是代码合入主干的「评审关卡」。

```text
PR 的生命周期：
1. 从 main 拉 feature 分支
2. 提交代码，推送远程
3. 创建 PR，描述改动和背景
4. 自动化检查（CI：lint、test、build）
5. 人工 Code Review
6. 合并到 main，删除 feature 分支
```

```bash
# 一个完整的 PR 工作流
git switch -c feat/login
# ... 开发、提交 ...
git push -u origin feat/login
# 在 GitHub/GitLab 上创建 PR，等待 review 和 CI
# 合并后：
git switch main && git pull
git branch -d feat/login
```

Code Review 的关注点：

```text
1. 正确性 —— 逻辑对不对，边界情况是否处理
2. 可维护性 —— 命名、结构、是否重复造轮子
3. 性能 —— 是否有明显性能问题
4. 安全 —— 注入、越权、敏感信息
5. 测试 —— 是否有对应测试覆盖
```

PR 的编写要点：小而聚焦（一个 PR 只做一件事）、描述清楚「为什么」而不只是「做了什么」。

## 应用场景实战

### 场景一：误提交了不该提交的文件，且已 push 到远程

```bash
# 1. 先从历史移除文件（保留在工作区）
git rm --cached .env
git commit -m "chore: 从版本库移除 .env"
git push

# 2. 立即在 .gitignore 加上 .env，防止再次提交
echo ".env" >> .gitignore

# 3. 如果 .env 含密钥已经泄露，必须轮换密钥（不能只删历史，
#    因为历史里仍能看到，且可能已被第三方抓取）
```

### 场景二：开发到一半需要紧急修线上 bug

```bash
# 方法 A：stash 保存现场
git stash save "feature 进行中"
git switch main
git switch -c hotfix/crash
# 修复、提交、合并、部署 ...
git switch feature-branch
git stash pop

# 方法 B：worktree 并行工作（不打断当前开发）
git worktree add ../repo-hotfix main
cd ../repo-hotfix && git switch -c hotfix/crash
# 在独立目录修 hotfix，原目录继续开发
```

### 场景三：本地 commit 太乱，push 前整理成干净历史

```bash
# 交互式 rebase，合并/改写最近 5 个提交
git rebase -i HEAD~5

# 编辑器里把要合并的提交标记为 squash 或 fixup：
# pick a1b2c3d feat: 登录页
# fixup b2c3d4e wip
# fixup c3d4e5f 小修
# pick d4e5f6g feat: 注册页

# 结果：两个 feature 提交，wip 和小修被并入
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每个 commit 只做一件事，可独立回滚
2. 已推送的提交用 revert，未推送的用 reset --soft/--mixed
3. 只在自己的 feature 分支上 rebase，公共分支永不 rebase
4. commit message 遵循 Conventional Commits，配 commitlint 校验
5. 敏感文件（.env、密钥）进 .gitignore，泄露后必须轮换密钥
6. 合并前先 rebase main，保持历史线性、减少冲突
7. feature 分支生命周期短（主干开发），做完即合、即删

### 踩坑记录

```text
坑 1：git reset --hard 丢失未提交改动
结论：工作区没提交的改动被彻底清除，无法找回。
原因：--hard 直接丢弃工作区和暂存区内容。
解法：慎用 --hard；误操作后用 reflog 找 commit，未提交的改动靠编辑器本地历史抢救。

坑 2：公共分支 rebase 导致协作崩溃
结论：其他协作者 push 时遇到 non-fast-forward，历史分叉。
原因：rebase 改写已推送的提交哈希，别人本地还是旧哈希。
解法：已推送分支用 merge；误 rebase 后用 git push --force-with-lease 前先和团队确认。

坑 3：git commit -am 漏掉新文件
结论：新建文件没被提交，功能不完整。
原因：-a 只提交已追踪文件的修改，新文件（untracked）不包含。
解法：新文件先 git add，或用 git add -A 后 commit。

坑 4：merge 冲突解决后漏 add 直接 commit 导致「空提交」
结论：冲突标记还在文件里就被提交，或提交了一个没实际内容的 merge commit。
原因：解决冲突后忘记 git add 就 commit。
解法：冲突文件改完先 git add，再 commit；用 git diff --cached 确认暂存内容。

坑 5：submodule 更新后忘记提交指针
结论：别人 clone 或 pull 后子模块还是旧版本，代码对不上。
原因：主仓库记录的是子模块指针，指针变更也是主仓库的一次提交。
解法：子模块更新后，在主仓库 git add <子模块路径> && git commit。

坑 6：在 Windows 和 macOS 之间换行符导致大量无意义 diff
结论：CRLF vs LF 让整个文件显示为被修改。
原因：不同系统换行符不一致，未配置 core.autocrlf。
解法：配置 git config --global core.autocrlf input（macOS/Linux）或 true（Windows），配合 .gitattributes 统一。
```
