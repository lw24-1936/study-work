## 概述

操作系统（Operating System）是管理硬件资源、为应用程序提供统一抽象服务的软件层。它向下管理 CPU、内存、磁盘、网络，向上给进程提供进程/线程、虚拟内存、文件系统、Socket 这些抽象。

前端工程师学操作系统，不是为了写内核，而是因为**前端代码运行的环境本身就是操作系统之上的产物**：

- 浏览器本身就是一个"操作系统"：多进程架构、任务调度、内存管理、安全沙箱，处处是 OS 思想的翻版
- Node.js 直接跑在 OS 上，`fs`、`net`、`worker_threads` 底层都是系统调用
- 性能问题的根源常在 OS 层：频繁上下文切换、缺页中断、swap、文件描述符耗尽

本文逐个讲清 OS 的核心概念，每个都落到前端能感知的场景。

## 用户态与内核态

CPU 有特权级别，区分两种运行状态：

```text
内核态（Kernel Mode / Ring 0）：
- 可执行特权指令：直接访问硬件、管理内存、开关中断
- 操作系统内核代码运行在此

用户态（User Mode / Ring 3）：
- 不能直接访问硬件，不能执行特权指令
- 所有应用程序（浏览器、Node.js、你的 JS）运行在此
```

用户态程序要访问硬件（读文件、发网络包），必须**陷入内核**，由内核代劳，这就是系统调用的由来。

```text
为什么要分两种态：
1. 保护系统安全 —— 用户程序不能随意改内存映射、关中断、直接操作磁盘
2. 隔离错误 —— 一个进程崩溃不能拖垮内核
```

```text
前端关联：
浏览器的安全沙箱是同一思想：网页 JS 不能直接读本地文件、不能跨域读数据，
必须通过浏览器提供的 API（fetch、File API）间接访问，浏览器内部再去跟内核交互。
```

## 系统调用

系统调用（System Call）是用户态请求内核服务的唯一入口。用户程序通过软中断或专用指令（x86 的 `syscall`）陷入内核，内核执行完再返回用户态。

```text
常见系统调用：
1. 进程：fork、exec、wait、exit
2. 文件：open、read、write、close、lseek
3. 网络：socket、bind、listen、accept、connect
4. 内存：brk、mmap、munmap
```

```javascript
// Node.js 里 fs.readFile 底层链路：
// fs.readFile（JS）
//   -> libuv 线程池（C）
//   -> open / read / close 系统调用（内核态）
//   -> 磁盘
const fs = require('fs');
fs.readFile('/etc/hosts', 'utf8', (err, data) => {
    console.log(data);
});
```

```text
前端关联：
Node.js 的 fs、net、http 模块本质上是对系统调用的封装，libuv 负责把阻塞的
系统调用转成异步回调，这是 Node 单线程却能高并发的底层原因。
```

## 进程

进程（Process）是操作系统进行**资源分配**的基本单位。每个进程有独立的地址空间（代码段、数据段、堆、栈），进程之间互不干扰。

```text
进程的组成：
1. 代码段 —— 程序的机器指令
2. 数据段 —— 全局变量、静态变量
3. 堆 —— 动态分配的内存（malloc/new）
4. 栈 —— 函数调用栈、局部变量
5. PCB（进程控制块）—— 内核维护的进程元数据（PID、状态、寄存器、优先级、打开的文件表）
```

```text
进程状态：
就绪（Ready）→ 运行（Running）→ 阻塞（Blocked）→ 就绪，循环往复
```

```text
进程 vs 线程：
```

| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 资源 | 独立地址空间，资源分配单位 | 共享进程地址空间，调度单位 |
| 隔离 | 进程间天然隔离 | 线程间共享堆和全局变量 |
| 通信 | IPC（管道、Socket、共享内存） | 直接读写共享内存 |
| 切换代价 | 高（切换地址空间、刷 TLB） | 低（共享地址空间） |
| 崩溃影响 | 一个进程崩溃不影响其他 | 一个线程崩溃可能拖垮整个进程 |

```text
前端关联：Chrome 多进程架构
1. 浏览器主进程 —— 管理界面、协调其他进程
2. 渲染进程 —— 每个站点一个（站点隔离），跑 HTML/CSS/JS
3. GPU 进程 —— 合成渲染
4. 网络进程 —— 网络请求
5. 插件进程 —— 隔离插件

好处：一个标签页崩溃不会拖垮整个浏览器，这是进程隔离思想的直接应用。
```

## 线程

线程（Thread）是 CPU 进行**调度**的基本单位。同一进程内的多个线程共享代码段、数据段、堆，但各自拥有独立的栈和寄存器。

```javascript
// Node.js 的 worker_threads：CPU 密集任务用多线程
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

if (isMainThread) {
    // 主线程
    const worker = new Worker(__filename, { workerData: { n: 40 } });
    worker.on('message', (result) => console.log('fib(40) =', result));
    worker.on('error', (err) => console.error(err));
} else {
    // worker 线程
    function fib(n) {
        return n <= 1 ? n : fib(n - 1) + fib(n - 2);
    }
    parentPort.postMessage(fib(workerData.n));
}
```

```text
前端关联：
1. 浏览器渲染进程内部多线程：主线程（JS/DOM）、合成线程、光栅化线程、IO 线程
2. Web Worker 在独立线程跑 JS，不阻塞主线程
3. JS 主线程是单线程，但浏览器的网络、定时器、渲染由其他线程负责
```

## 协程

协程（Coroutine）是用户态的轻量级"线程"，由程序自己调度（协作式），不经过内核。切换只保存/恢复少量上下文，代价远低于线程切换。

```text
协程 vs 线程：
```

| 维度 | 线程 | 协程 |
| --- | --- | --- |
| 调度者 | 内核（抢占式） | 程序自己（协作式） |
| 切换代价 | 微秒级，要进内核 | 纳秒级，纯用户态 |
| 并发规模 | 上千个已吃力 | 百万级 |
| 是否并行 | 多核可并行 | 单线程内并发，不并行 |

```javascript
// JS 的 generator 是协程思想的直接体现：手动让出执行权
function* counter() {
    yield 1;   // 让出，保存现场
    yield 2;
    yield 3;
}
const it = counter();
console.log(it.next().value);   // 1
console.log(it.next().value);   // 2

// async/await 是协程 + 事件循环的语法糖
async function fetchUser(id) {
    const res = await fetch(`/api/user/${id}`);  // await 处让出，等结果再继续
    return res.json();
}
```

```text
前端关联：
1. async/await 本质是协程：await 处让出执行权，Promise 完成后恢复
2. React 的并发特性（时间切片、Suspense）是协程式调度思想的体现
3. 相比线程，协程更适合 IO 密集的异步场景（前端正是这种场景）
```

## 上下文切换

上下文切换（Context Switch）指 CPU 从一个任务切到另一个任务时，保存当前任务的现场（寄存器、程序计数器、栈指针），再恢复新任务现场的过程。

```text
切换代价：
1. 保存/恢复寄存器、栈
2. 进程切换额外要：切换页表、刷新 TLB（缓存失效）
3. 频繁切换会吃掉大量 CPU 时间，属于纯开销
```

```text
切换类型与代价排序：
协程切换（纳秒级，用户态）< 线程切换（微秒级）< 进程切换（微秒级 + TLB 刷新）
```

```text
前端关联：
1. JS 单线程避免了线程间的上下文切换开销，这是它做高并发 IO 的优势
2. React 时间切片：把长任务切成小片，让浏览器有机会处理输入和渲染，
   避免一次长任务阻塞主线程（本质是主动让出执行权）
3. 大量微小的异步任务会造成调度开销，批处理（batch）是常见优化手段
```

## 调度

调度（Scheduling）是内核决定"下一个该运行哪个任务"的机制。

```text
经典调度算法：
1. FCFS（先来先服务）—— 简单，但长任务会让后面的短任务等很久
2. SJF（短作业优先）—— 平均等待时间最短，但长任务可能饿死
3. RR（时间片轮转）—— 每个任务轮流跑固定时间片，交互系统常用
4. 优先级调度 —— 高优先级先跑，可能饿死低优先级
5. 多级反馈队列 —— 结合以上：短任务高优先级快跑，长任务降优先级，
   是现代操作系统的实际做法
```

```text
前端关联：
1. 浏览器事件循环：宏任务队列（setTimeout、IO）按序执行，微任务（Promise）
   在每轮宏任务后清空 —— 这就是一套调度规则
2. React Scheduler：根据优先级（用户输入 > 动画 > 数据更新）调度渲染任务，
   低优先级任务可被打断
3. 理解"调度"才能理解为什么 setTimeout(fn, 0) 不会立即执行
```

## 内存管理

内存管理（Memory Management）解决"给每个进程分多少内存、如何回收、如何保护"三个问题。

```text
内存分配方式：
1. 连续分配 —— 早期做法，会产生外部碎片
2. 分段 —— 按逻辑（代码段/数据段/栈）划分，大小不固定
3. 分页 —— 内存切成固定大小页（4KB），按页分配，现代主流
```

```text
内存保护：
1. 每个进程只能访问自己的地址空间
2. 越界访问触发段错误（Segmentation Fault）
3. 这是"进程隔离"的硬件基础
```

```javascript
// JS 视角：栈内存 vs 堆内存
function add(a, b) {
    const sum = a + b;      // sum 是局部变量，存栈（函数返回即释放）
    return sum;
}

const obj = { list: [] };   // obj 引用的对象存堆，由 GC 管理
for (let i = 0; i < 1000; i++) {
    obj.list.push(i);       // 堆内存增长，超出引用后被 GC 回收
}
```

```text
前端关联：
1. V8 的内存分代管理：新生代（存活短、频繁回收）+ 老生代（存活久、偶尔回收）
2. 栈存基本类型和引用，堆存对象，这就是"深拷贝/浅拷贝"差异的根源
3. 内存泄漏本质是堆上的对象仍被引用，GC 无法回收
```

## 虚拟内存

虚拟内存（Virtual Memory）给每个进程一个独立的、连续的虚拟地址空间，让进程以为自己独占全部内存，实际由内核映射到物理内存。

```text
虚拟内存解决三个问题：
1. 隔离 —— 进程 A 无法读写进程 B 的内存
2. 空间放大 —— 运行比物理内存更大的程序（部分换到磁盘）
3. 简化编程 —— 程序用连续地址，不用关心物理碎片
```

```text
地址翻译流程：
虚拟地址 → 查页表（MMU 硬件完成）→ 物理地址
```

```text
前端关联：
1. V8 堆有上限：64 位系统约 4GB，超出抛 OOM（这是虚拟地址空间的约束）
2. ArrayBuffer/TypedArray 对应连续内存块，可被 WASM 高效读写
3. 内存不足时 OS 把内存页换到磁盘（swap），应用会突然变卡
```

## 页表

页表（Page Table）是虚拟页到物理页帧的映射表。每个进程有自己的页表。

```text
页表结构：
1. 单级页表 —— 虚拟页号 → 物理帧号，大地址空间下页表本身占内存巨大
2. 多级页表 —— 只分配实际用到的层级，节省内存（现代主流）
```

```text
TLB（Translation Lookaside Buffer，快表）：
地址翻译要查页表（在内存里），太慢。TLB 是 CPU 内部的页表缓存，
缓存最近用过的虚拟页→物理帧映射。TLB 命中则翻译快，未命中要查内存页表。
```

```text
前端关联：
1. TLB 未命中是进程切换的隐性成本之一（切换地址空间要刷新 TLB）
2. 理解"缓存加速翻译"有助于理解为什么连续内存访问快（局部性）
```

## Page Fault

缺页中断（Page Fault）指程序访问的虚拟页不在物理内存中，触发 CPU 中断，由内核从磁盘把页换入。

```text
两类缺页：
1. 硬缺页（Major Fault）—— 页不在内存，要从磁盘读入，代价高（毫秒级）
2. 软缺页（Minor Fault）—— 页已在内存（如共享库被别的进程加载），只更新页表，代价低
```

```text
缺页处理流程：
访问虚拟页 → 页表项无效 → 触发缺页中断 → 内核从磁盘换入页 → 更新页表 → 重新执行指令
```

```text
前端关联：
1. 应用突然卡顿、掉帧，常见原因是内存不足触发大量缺页 + swap
2. Node 进程内存超限会频繁缺页甚至 OOM，需要关注 V8 堆和 RSS
3. 冷启动慢：程序刚加载时大量硬缺页，从磁盘读代码和数据
```

## 文件系统

文件系统（File System）负责把磁盘上的数据组织成文件和目录，提供持久化存储的抽象。

```text
文件系统做的事：
1. 组织：目录树、文件、inode（存文件元数据：大小、权限、数据块位置）
2. 分配：为文件分配磁盘块，管理空闲空间
3. 访问控制：文件权限
```

```text
常见文件系统：
ext4（Linux 主流）、APFS（macOS）、NTFS（Windows）
```

```text
前端关联：
1. 前端构建（Vite/Webpack）大量小文件读写，文件系统性能直接影响构建速度
2. npm install 动辄上万个小文件，机械硬盘上极慢，SSD 明显快
3. 打包产物、静态资源最终都落在文件系统上
```

## 文件描述符

文件描述符（File Descriptor）是进程打开文件后拿到的整数索引，后续读写都通过它引用文件，而非每次传路径。

```text
约定：
0 = 标准输入 stdin
1 = 标准输出 stdout
2 = 标准错误 stderr
之后打开的文件从 3 开始递增
```

```javascript
// Node.js 中 fs 打开的 fd
const fs = require('fs');

fs.open('/tmp/test.txt', 'w', (err, fd) => {
    if (err) throw err;
    console.log('fd =', fd);   // 通常为 3（0/1/2 被标准流占用）
    fs.write(fd, 'hello', () => {
        fs.close(fd, () => console.log('closed'));
    });
});
```

```text
前端关联：
1. 文件描述符有上限（ulimit -n，默认常为 1024），超限报 EMFILE（too many open files）
2. Node 服务高并发时忘 close 文件描述符会耗尽，导致服务挂掉
3. 监听 Socket 也是文件描述符，连接数受 fd 上限约束
```

## Socket

Socket 是网络通信的端点，由 IP 地址 + 端口号唯一标识。进程通过 Socket 收发数据。

```text
Socket 分类：
1. TCP Socket —— 面向连接、可靠、有序（流式）
2. UDP Socket —— 无连接、不可靠、快（数据报）
3. Unix Domain Socket —— 本机进程间通信，不走网络栈
```

```javascript
// Node.js 用 Socket 建立 TCP 服务
const net = require('net');

const server = net.createServer((socket) => {
    console.log('client connected');
    socket.on('data', (data) => {
        console.log('received:', data.toString());
        socket.write('pong');
    });
});
server.listen(3000, () => console.log('tcp server on 3000'));
```

```text
前端关联：
1. WebSocket 是浏览器里基于 TCP 的 Socket 抽象，长连接实时通信
2. Node.js 的 http 服务底层是 Socket（TCP 连接）
3. 浏览器同一域名的并发连接数限制（HTTP/1.1 约 6 个），本质是 Socket 连接复用问题
```

## IPC

IPC（Inter-Process Communication，进程间通信）是进程之间交换数据的机制。

```text
常见 IPC 方式：
1. 管道（Pipe）—— 单向字节流，父子进程常用
2. 消息队列 —— 有边界的消息，可异步
3. 共享内存 —— 最快，但需要同步（信号量）
4. Socket —— 可跨机器，最通用
5. 信号 —— 只传一个"通知"，不传数据
```

```text
前端关联：
1. Chrome 各进程之间用 Mojo（基于共享内存 + 消息）通信
2. Node.js cluster 模块：主进程 fork 多个子进程，靠 IPC 通道通信
3. Web Worker 与主线程靠 postMessage 通信（结构化克隆，本质是消息传递）
```

```javascript
// Node.js cluster：主进程与子进程 IPC
const cluster = require('cluster');
const http = require('http');

if (cluster.isMaster) {
    for (let i = 0; i < 2; i++) {
        const w = cluster.fork();
        w.on('message', (msg) => console.log('master got:', msg));
    }
} else {
    http.createServer((req, res) => {
        process.send('handled');   // 子进程通过 IPC 通知主进程
        res.end('ok');
    }).listen(8000);
}
```

## 信号

信号（Signal）是操作系统发给进程的异步通知，用于告知进程发生了某事件。

```text
常见信号：
SIGINT  —— Ctrl+C 中断，优雅退出
SIGTERM —— 请求终止（kill 默认），可被捕获
SIGKILL —— 强制杀死，不可捕获不可忽略
SIGSEGV —— 段错误（访问非法内存）
SIGCHLD —— 子进程结束
```

```javascript
// Node.js 捕获信号做优雅退出
process.on('SIGINT', () => {
    console.log('received SIGINT, closing...');
    server.close(() => process.exit(0));
});

process.on('SIGTERM', () => {
    console.log('received SIGTERM, graceful shutdown');
    process.exit(0);
});
```

```text
前端关联：
1. 部署时 kill 命令默认发 SIGTERM，应用要捕获它做优雅退出（关闭连接、落盘日志）
2. 容器（K8s/Docker）停止容器也是发 SIGTERM，超时未退出才 SIGKILL
3. SIGKILL 不可捕获，被它杀掉的应用没有机会做清理
```

## 权限

权限（Permission）控制谁（用户/组）能对文件做什么（读/写/执行）。

```text
Linux 文件权限：
r（读，4）w（写，2）x（执行，1），分三组：属主 / 属组 / 其他人
```

```bash
ls -l app.js
# -rw-r--r-- 1 user group 1024 Aug 13 10:00 app.js
# 属主 rw-，属组 r--，其他 r--（即 644）

chmod 755 app.js   # 属主 rwx，属组 r-x，其他 r-x
chmod 600 key.pem  # 仅属主可读写（私钥文件）
```

```text
前端关联：
1. 部署静态资源：目录 755、文件 644 是常见约定
2. 私钥、证书等敏感文件设为 600，只允许属主读写
3. Nginx 以非 root 用户运行，文件权限不对会 403
```

## 应用场景实战

### 场景 1：用 worker_threads 做 CPU 密集计算，避免阻塞主线程

```javascript
// heavy.js —— 计算斐波那契，模拟 CPU 密集任务
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

function fib(n) {
    return n <= 1 ? n : fib(n - 1) + fib(n - 2);
}

if (isMainThread) {
    // 主线程：起多个 worker 并行计算
    const jobs = [40, 41, 42, 43];
    const results = [];

    jobs.forEach((n, i) => {
        const worker = new Worker(__filename, { workerData: { n } });
        worker.on('message', (v) => {
            results[i] = v;
            if (results.filter(Boolean).length === jobs.length) {
                console.log('all done:', results);
            }
        });
    });
    console.log('main thread is free');   // 主线程不被阻塞
} else {
    parentPort.postMessage(fib(workerData.n));
}
```

运行方式：`node heavy.js`。主线程起 worker 后立即打印 "main thread is free"，计算在 worker 线程完成，主线程可以继续处理其他事件。

### 场景 2：文件描述符耗尽模拟与排查

```javascript
// leak-fd.js —— 模拟忘记关闭文件导致的 fd 泄漏
const fs = require('fs');

const files = [];
let count = 0;
const timer = setInterval(() => {
    // 打开文件但不关闭，fd 持续增长
    const fd = fs.openSync('/tmp/test.txt', 'r');
    files.push(fd);
    count++;
    if (count % 100 === 0) {
        console.log('open fds:', count);
    }
}, 10);

process.on('SIGINT', () => {
    clearInterval(timer);
    console.log('leaked', count, 'fds');
    process.exit(0);
});
```

```bash
# 验证：fd 耗尽后 fs.openSync 会抛 EMFILE: too many open files
```

### 场景 3：协程思想——用 generator 实现异步流程控制

```javascript
// 用 generator 手动管理异步流程（async/await 的雏形）
function* fetchFlow() {
    const user = yield fetch('/api/user').then(r => r.json());
    console.log('user:', user);
    const posts = yield fetch(`/api/user/${user.id}/posts`).then(r => r.json());
    console.log('posts:', posts.length);
}

// 简易执行器：每次让出 Promise，完成后用结果恢复
function run(gen) {
    const it = gen();
    function step(result) {
        const { value, done } = it.next(result);
        if (done) return;
        value.then(step);
    }
    step();
}

run(fetchFlow());
```

## 最佳实践与踩坑记录

### 最佳实践

1. CPU 密集任务交给 worker_threads 或 Web Worker，别堵主线程
2. 打开的文件、Socket 用后及时 close，避免 fd 泄漏
3. Node 服务捕获 SIGINT/SIGTERM 做优雅退出（关连接、落日志）
4. 敏感文件（私钥、证书）权限设 600，静态资源目录 755 / 文件 644
5. 处理大量异步任务时批处理，减少调度与上下文切换开销
6. 理解 V8 堆上限，大块数据用 ArrayBuffer/TypedArray 而非普通对象数组

### 踩坑记录

```text
坑 1：Node 服务高并发时突然报 EMFILE: too many open files
结论：文件描述符耗尽，服务无法再接受新连接或打开文件。
原因：打开的文件/Socket 未 close，或 fd 上限（ulimit -n）设置过低。
解法：及时 close；必要时调高 ulimit -n 并排查泄漏点（ls /proc/<pid>/fd）。

坑 2：进程被 SIGKILL 杀死，日志里没有优雅退出记录
结论：SIGKILL 不可捕获，应用没有机会做清理。
原因：部署平台超时后直接 SIGKILL，应用来不及处理 SIGTERM。
解法：捕获 SIGTERM 做优雅退出，且把退出流程控制在平台超时窗口内。

坑 3：JS 主线程跑大循环导致页面卡死
结论：长同步任务阻塞主线程，渲染和事件全部冻结。
原因：JS 单线程，一个长任务独占 CPU，无法响应输入。
解法：拆分成时间片（requestIdleCallback / 时间切片）或移到 Worker。

坑 4：内存不足时应用周期性卡顿
结论：物理内存不够，OS 频繁把内存页换到磁盘（swap），出现大量缺页。
原因：进程占用超过物理内存，触发 swap 和硬缺页。
解法：减少内存占用、排查内存泄漏、增加物理内存或限制 swap 使用。

坑 5：容器里 kill 进程不退出
结论：发 SIGTERM 后进程仍存活，最终被 SIGKILL 强杀。
原因：应用未捕获 SIGTERM，或主进程不是 PID 1 时信号没有传递到应用。
解法：应用捕获 SIGTERM；容器内用 exec 形式启动应用让它成为 PID 1。
```
