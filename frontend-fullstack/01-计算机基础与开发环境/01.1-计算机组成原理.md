## 概述

计算机组成原理讲的是"计算机硬件如何工作"：CPU 怎么执行指令、数据怎么存储、IO 怎么完成。前端工程师学它不是要造芯片，而是因为**前端代码最终运行在 CPU 和内存上**——理解了硬件，才能解释那些"玄学"性能问题：

- 为什么遍历二维数组按行比按列快（缓存行）
- 为什么 JS 里 `0.1 + 0.2 !== 0.3`（浮点表示）
- 为什么 `ArrayBuffer`/`TypedArray` 能大幅提升二进制处理性能（连续内存 + 字节序）
- 为什么字符串乱码（字符编码）

本文从硬件视角讲清这些底层机制，每个知识点都落到前端场景。

## CPU 与指令执行

CPU（Central Processing Unit，中央处理器）是计算机的"大脑"，负责执行指令。一条指令从读取到执行完毕，走的是经典的**取指-译码-执行-写回**流水线：

```text
取指（Fetch）   —— 从内存读取下一条指令
译码（Decode）  —— 解析指令要做什么
执行（Execute） —— 运算（ALU 计算、内存访问）
写回（Write Back）—— 把结果写回寄存器
```

现代 CPU 的关键特性：

```text
1. 流水线 —— 多条指令同时处于不同阶段（第 1 条在执行时第 2 条在译码）
2. 乱序执行 —— 不依赖的指令可提前执行，充分利用执行单元
3. 分支预测 —— 遇到 if 提前猜走哪条分支，猜错要回滚（分支预测失败的代价）
4. 超线程 —— 一个物理核模拟两个逻辑核，减少流水线空闲
```

对前端的意义：CPU 的指令执行极快（纳秒级），性能瓶颈几乎不在 CPU 本身，而在**等待数据**（内存/IO 访问）。所以前端优化的核心是"减少等待、提高缓存命中"，而不是"减少算术运算"。

```text
为什么 CPU 快但程序慢：
CPU 执行一条指令约 0.3ns，但读一次内存约 100ns（差 300 倍）。
CPU 大部分时间在"等数据"，不是"算数据"。
```

## GPU

GPU（Graphics Processing Unit）是专门做大规模并行计算的处理器。

```text
CPU vs GPU：
CPU —— 几个强核心，擅长复杂逻辑、分支、串行任务
GPU —— 成百上千个弱核心，擅长同质化、可并行的数值计算
```

```text
对前端的意义：
1. CSS 动画/变换（transform、opacity）由 GPU 合成层处理，不阻塞主线程
2. WebGL / WebGPU 直接在浏览器里用 GPU 做并行计算
3. CSS will-change、transform: translateZ(0) 触发 GPU 加速
```

前端说"用 GPU 加速动画"，本质是把渲染交给 GPU 的合成器，而不是 JS 在主线程里一帧帧改样式。

## ALU

ALU（Arithmetic Logic Unit，算术逻辑单元）是 CPU 内部做运算的部件：

```text
ALU 能做的：加、减、乘、除、与、或、非、异或、移位、比较
ALU 不能做的：直接算浮点（早期要靠浮点单元 FPU，现代 CPU 集成）
```

```javascript
// JS 里的位运算，底层就是 ALU 的按位操作
const a = 0b1010;        // 10
a & 0b1100;              // 1000 = 8（与）
a | 0b0011;              // 1011 = 11（或）
a ^ 0b1111;              // 0101 = 5（异或）
a << 1;                  // 10100 = 20（左移，乘 2）
a >> 1;                  // 101 = 5（右移，除 2）
```

```text
前端位运算的常见应用：
1. 状态标志位（权限：READ=1, WRITE=2, EXEC=4，用 | 组合，& 判断）
2. 取整：x | 0、~~x（比 Math.floor 快，但只对 32 位整数有效）
3. 颜色值操作：RGB 打包成 0xRRGGBB
4. 加密/哈希、哈希取模（n & (2^k - 1) 等价 n % 2^k）
```

## 寄存器

寄存器是 CPU 内部最快的存储单元，直接参与指令执行：

```text
寄存器特点：
1. 位于 CPU 内部，访问最快（0 时钟周期）
2. 容量极小（几十个，每个 8 字节）
3. 指令操作的对象只能是寄存器（内存数据要先加载到寄存器）
```

```text
关键寄存器：
1. 程序计数器 PC —— 存下一条指令地址
2. 通用寄存器 —— 存运算的中间结果
3. 状态寄存器 —— 存标志位（进位、溢出、零）
```

对前端的意义：JS 引擎（V8）JIT 编译后，频繁访问的局部变量会被映射到寄存器，这是"热代码"快的原因之一。局部变量比对象属性快，部分原因就是寄存器 vs 内存访问的差异。

## 指令集

指令集是 CPU 能识别的机器指令的集合，定义了硬件和软件的接口。

```text
两大体系：
1. CISC（复杂指令集，x86）—— 指令多而复杂，单条指令功能强（Intel/AMD）
2. RISC（精简指令集，ARM）—— 指令少而简单，每条执行快（手机、苹果 M 系列）
```

```text
与前端的关系：
1. WebAssembly 的指令集接近 RISC，这也是它比 JS 快的原因之一（更接近机器码）
2. 判断用户设备架构（x86 vs ARM）对性能分析有意义
3. SIMD（单指令多数据）：一条指令同时算多个数据，WebAssembly 的 SIMD 指令
   能并行处理 TypedArray 数据
```

## 存储层次与 Cache

计算机存储是一个金字塔，越往上越快、越贵、越小：

```text
寄存器（0ns，KB 级）
  ↓
L1 Cache（~1ns，32-64KB）      ← 每个核心私有
  ↓
L2 Cache（~4ns，256KB-1MB）    ← 每个核心私有
  ↓
L3 Cache（~12ns，4-32MB）      ← 多核心共享
  ↓
内存 RAM（~100ns，GB 级）
  ↓
SSD（~50-150us，TB 级）
  ↓
HDD（~5-10ms，TB 级）
```

Cache（高速缓存）的原理是**局部性**：

```text
1. 时间局部性 —— 刚访问过的数据，很快会再访问（循环变量）
2. 空间局部性 —— 访问一个数据，相邻的数据也很快会被访问（数组遍历）
```

```text
缓存行（Cache Line）：
Cache 按固定大小（64 字节）读写数据，叫缓存行。
CPU 读一个字节，会一次性把周围 64 字节都读进 Cache。
```

```javascript
// 缓存友好 vs 不友好：二维数组遍历
const n = 1024;
const arr = new Array(n).fill(0).map(() => new Array(n).fill(0));

// 按行遍历（缓存友好：连续内存，命中缓存行）
for (let i = 0; i < n; i++) {
    for (let j = 0; j < n; j++) {
        arr[i][j] += 1;
    }
}

// 按列遍历（缓存不友好：跳跃访问，缓存行浪费）
for (let j = 0; j < n; j++) {
    for (let i = 0; i < n; i++) {
        arr[i][j] += 1;
    }
}
```

```text
按行遍历比按列遍历快：按行访问 arr[i][0..n] 是连续内存，一次缓存行加载能命中
后续元素；按列访问 arr[0..n][j] 是跳跃的，每次都可能缓存未命中。
```

对前端的意义：JS 数组底层是连续内存，顺序遍历快、随机跳跃慢。TypedArray 因为内存连续，遍历性能优于普通对象数组。

## 内存与虚拟内存

内存（RAM）是 CPU 和磁盘之间的高速存储，断电即失。

```text
内存特点：
1. 随机访问，读写速度一致（区别于磁盘的顺序访问）
2. 断电数据丢失（易失性）
3. 容量有限（8-64GB 常见）
```

虚拟内存是操作系统给每个进程的"假象"——每个进程以为自己独占全部内存：

```text
虚拟内存机制：
1. 每个进程有独立的虚拟地址空间（32 位系统 4GB，64 位系统巨大）
2. 内存管理单元（MMU）把虚拟地址映射到物理地址
3. 分页：内存按 4KB 页管理，按需加载
4. 缺页中断：访问不在内存的页，从磁盘换入（慢！）
5. 页面置换：内存满时把不常用的页换出到磁盘（swap）
```

```text
对前端的意义：
1. JS 的 V8 堆有上限（64 位系统约 4GB），超了会 OOM
2. ArrayBuffer/TypedArray 对应连续内存块，可被 WASM 高效读写
3. 页面 swap 会导致应用突然卡顿（内存不足时）
```

## 持久化存储 SSD 与 HDD

SSD 和 HDD 是持久化存储，断电不丢数据：

```text
HDD（机械硬盘）：
1. 磁盘旋转 + 磁头寻道，随机读写慢（寻道时间 5-10ms）
2. 顺序读写较快
3. 价格低，容量大

SSD（固态硬盘）：
1. 基于闪存，无机械部件，随机读写快（微秒级）
2. 有写入寿命（擦写次数有限）
3. 价格较高
```

```text
对前端的意义：
1. 浏览器 IndexedDB/localStorage 数据最终落磁盘，SSD 用户读写明显更快
2. 构建工具（Webpack/Vite）的磁盘 IO 是瓶颈之一，SSD 显著加速构建
3. 理解"随机 IO vs 顺序 IO"有助于理解数据库和文件系统的性能差异
```

## IO、DMA 与中断

IO 是 CPU 与外部设备（磁盘、网卡、键盘）的数据交换。

```text
三种 IO 方式：
1. 程序控制 IO —— CPU 亲自一个个字节读，全程占用 CPU（慢，浪费）
2. 中断驱动 IO —— 设备准备好后发中断通知 CPU，CPU 只在需要时介入
3. DMA（直接内存访问）—— 数据在设备和内存间直接传输，不经 CPU（现代主流）
```

```text
DMA 的价值：磁盘读写大量数据时，DMA 控制器直接搬运数据，CPU 可以去做别的事。
这正是"异步 IO"的硬件基础。
```

```text
中断（Interrupt）：
1. 硬件设备（键盘、网卡、定时器）通过中断信号通知 CPU
2. CPU 暂停当前任务，跳到中断处理程序，处理完恢复
3. 中断让 CPU 能"响应"外部事件，而不是傻等
```

```text
对前端的意义：
JS 的事件循环（Event Loop）本质是中断思想在软件层的体现——
浏览器底层 IO（网络、文件）完成后通过回调通知 JS 引擎，
JS 主线程不用阻塞等待，这就是"异步非阻塞"的来源。
```

## 总线

总线是计算机内部各部件（CPU、内存、IO 设备）之间传输数据的通道。

```text
三类总线：
1. 数据总线 —— 传输数据
2. 地址总线 —— 传输内存地址（决定可寻址空间，32 位地址总线 = 4GB 空间）
3. 控制总线 —— 传输控制信号
```

```text
前端关联：
1. "64 位系统"里的 64 位，指的是地址总线/数据总线宽度
2. 总线的带宽是性能上限之一，前端不必深究，但理解"数据传输有带宽限制"
   有助于理解为什么大文件下载、大图片渲染是瓶颈
```

## 数据表示：二进制与十六进制

计算机内部一切数据都是二进制（0 和 1）。

```text
二进制：0b1010 = 10
十六进制：0xA = 10，0xFF = 255（每 4 位二进制对应 1 位十六进制）
```

```javascript
// JS 中的进制表示
0b1010;       // 二进制，10
0o17;         // 八进制，15
0xff;         // 十六进制，255

// 进制转换
(255).toString(2);   // "11111111"
(255).toString(16);  // "ff"
parseInt("ff", 16);  // 255
```

```text
十六进制在前端的应用：
1. 颜色值：#FF0000 = 红 255、绿 0、蓝 0
2. 二进制数据查看（文件十六进制 dump）
3. 加密哈希、随机 ID
```

## 字节序

字节序（Byte Order）指多字节数据在内存中的存储顺序：

```text
1. 大端序（Big Endian）—— 高位字节存低地址（网络字节序）
2. 小端序（Little Endian）—— 低位字节存低地址（x86/ARM 默认）
```

```javascript
// 用 TypedArray 观察字节序
const buf = new ArrayBuffer(4);
const view = new DataView(buf);
view.setUint32(0, 0x12345678);

// 逐字节查看
const bytes = new Uint8Array(buf);
console.log(bytes[0].toString(16));  // 小端序输出 78，大端序输出 12
```

```javascript
// 显式指定字节序读写
const buf = new ArrayBuffer(4);
const view = new DataView(buf);
view.setUint32(0, 0x12345678, false);   // false = 大端序
view.getUint32(0, false);               // 0x12345678
```

```text
前端字节序的应用：
1. 处理二进制协议（WebSocket 二进制帧、文件格式）必须知道字节序
2. DataView 可以显式指定大端/小端，Uint32Array 等 TypedArray 用系统字节序
3. 网络传输通常用大端序（网络字节序），本地内存通常小端序
```

## 字符编码与 Unicode

字符编码解决"字符如何用字节表示"的问题。

```text
演进历史：
ASCII —— 7 位，128 个字符（英文字母、数字、符号）
  ↓ 各国扩展
GBK / Latin-1 —— 用扩展字节表示本地语言（互不兼容，乱码根源）
  ↓ 统一
Unicode —— 给全世界每个字符分配唯一码点（code point）
UTF-8 —— Unicode 的一种变长编码，兼容 ASCII，互联网标准
```

```text
Unicode 码点：
每个字符有唯一编号，如 'A' = U+0041，'中' = U+4E2D，'😀' = U+1F600
```

```text
UTF-8 变长编码：
1. ASCII 字符（U+0000~U+007F）—— 1 字节
2. 大部分中文（U+0800~U+FFFF）—— 3 字节
3. emoji 等（U+10000 以上）—— 4 字节
```

```javascript
// JS 中的字符编码
const s = "A中😀";
s.length;                    // 4（不是 3！emoji 占 2 个 UTF-16 码元）
[...s].length;               // 3（用展开运算符按码点计数）
s.codePointAt(0);            // 65（'A' 的码点）
s.codePointAt(1);            // 20013（'中' 的码点）

// UTF-8 编码
const encoder = new TextEncoder();
const bytes = encoder.encode("中");   // Uint8Array [228, 184, 173]（3 字节）

const decoder = new TextDecoder();
decoder.decode(bytes);                // "中"
```

```text
前端字符编码的坑：
1. JS 字符串内部是 UTF-16，emoji 占 2 个码元（surrogate pair）
2. 字符串长度用 [...str].length 或 Array.from 才准确
3. 后端接口编码不一致导致中文乱码（UTF-8 vs GBK）
4. fetch 的 Response.text() 默认按 UTF-8 解码，错误编码会乱码
```

## 应用场景实战

### 场景 1：权限位运算

用 ALU 的位运算做权限管理，一个整数存所有权限：

```javascript
const READ = 1;    // 0b001
const WRITE = 2;   // 0b010
const EXEC = 4;    // 0b100

let perm = READ | WRITE;          // 0b011 = 3（拥有读和写）
perm & READ;                       // 1（有读权限）
perm & EXEC;                       // 0（无执行权限）
perm = perm | EXEC;                // 0b111 = 7（授予执行权限）
perm = perm & ~WRITE;              // 0b101 = 5（撤销写权限）
```

### 场景 2：TypedArray 处理二进制

利用连续内存和字节序处理二进制数据：

```javascript
// 从二进制流解析一个 4 字节整数 + 2 字节短整数
const buf = new ArrayBuffer(6);
const dv = new DataView(buf);
dv.setUint32(0, 123456, false);   // 大端序写 4 字节
dv.setUint16(4, 65535, false);    // 大端序写 2 字节

// 读取
const intValue = dv.getUint32(0, false);
const shortValue = dv.getUint16(4, false);
```

### 场景 3：缓存友好的数据遍历

大数组处理时，保持内存访问的连续性：

```javascript
// 连续内存（TypedArray）顺序遍历，缓存命中率高
const data = new Float64Array(1000000);
for (let i = 0; i < data.length; i++) {
    data[i] = data[i] * 2;
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 遍历大数组保持顺序访问，避免跳跃访问（利用缓存行）
2. 二进制数据处理用 TypedArray/DataView，而非普通数组
3. 权限、状态标志用位运算，一个整数存多状态
4. 处理字符串长度和截断时考虑 Unicode（emoji 占 2 码元）
5. 接口和文件编码统一 UTF-8，避免乱码

### 踩坑记录

```text
坑 1：二维数组按列遍历比按行慢
结论：按列遍历（跳跃访问）缓存未命中率高，大数组性能差几倍。
原因：缓存行 64 字节，按列访问浪费已加载的相邻数据。
解法：调整循环顺序，按内存连续方向遍历。

坑 2：JS 字符串长度计算 emoji 出错
结论：'😀'.length === 2，用它做截断会拆散 emoji。
原因：JS 内部 UTF-16，emoji 是代理对（2 个码元）。
解法：用 [...str]、Array.from(str) 或 for...of 按码点处理。

坑 3：二进制解析字节序搞反
结论：直接读多字节整数，值完全错误。
原因：本地小端序 vs 网络大端序不一致。
解法：用 DataView 显式指定字节序，确认协议的大端/小端约定。

坑 4：前端文件乱码
结论：后端返回 GBK 编码，前端按 UTF-8 解码，中文变乱码。
原因：编码不一致。
解法：统一 UTF-8；无法改后端时用 TextDecoder 指定编码解码。

坑 5：位运算误用导致精度丢失
结论：x | 0 取整只对 32 位整数有效，超出范围结果错误。
原因：JS 位运算先把操作数转 32 位整数。
解法：大数取整用 Math.floor/trunc，位运算只用于 32 位范围内。
```
