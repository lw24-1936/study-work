## 概述

开发环境决定开发效率和团队协作一致性。前端开发环境由四部分组成：编辑器、浏览器调试工具、Node.js 运行时和包管理器。这篇笔记覆盖每类工具的核心能力、选择依据和常见坑，目标是让新环境能在十分钟内搭好并和团队保持一致。

```text
开发环境四件套：
1. 编辑器/IDE —— 写代码
2. 浏览器 + DevTools —— 运行和调试
3. Node.js —— 跑构建工具、脚手架、本地服务
4. 包管理器 —— 管理依赖
```

## VS Code

VS Code 是前端事实标准编辑器，基于 Electron，插件生态最丰富。核心是「编辑器 + 插件」模型：本体轻量，能力靠插件扩展。

```text
前端必装插件（按类型）：
语言支持   —— ESLint、Prettier、Vue - Official / Vue Volar、ES7+ React/Redux snippets
智能提示   —— GitHub Copilot、TypeScript 内置、Tailwind CSS IntelliSense
调试       —— Debugger for Chrome、REST Client
工程       —— GitLens（Git 增强）、Remote - SSH、Dev Containers、Path Intellisense
```

几个提高效率的内置能力：

```text
多光标（Alt/Cmd + Click）—— 同时编辑多处
命令面板（Cmd/Ctrl + Shift + P）—— 所有操作的入口
Emmet —— HTML/CSS 快速补全（! 展开 HTML 骨架，ul>li*5 展开列表）
Settings Sync —— 通过 GitHub 账号同步配置
```

VS Code 的配置分三层：

```text
用户级 settings.json —— 全局，对所有人有效
工作区 .vscode/settings.json —— 项目级，随仓库共享（团队统一规范用这个）
文件夹级 —— 最细粒度
```

工作区配置是团队统一的关键，通常提交到仓库：

```jsonc
// .vscode/settings.json —— 团队共享的编辑器配置
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": true
  },
  "files.eol": "\n",
  "editor.tabSize": 2
}
```

VS Code 的短板：大型 TypeScript 项目或 Java/多语言场景下，索引和重构能力不如 JetBrains。

## JetBrains IDE

JetBrains 是重 IDE，IntelliJ IDEA 为旗舰，WebStorm 是前端专用版，还有 GoLand、PyCharm、DataGrip 等。特点是开箱即用的深层次代码分析、重构和跨文件导航。

```text
JetBrains vs VS Code：
JetBrains —— 重、智能、开箱即用，重构和类型分析强，适合大项目
VS Code    —— 轻、可定制、插件驱动，启动快，前端生态最全

选择：纯前端用 VS Code（或 WebStorm），全栈/多语言用 JetBrains。
```

WebStorm 的前端特性：内置对 TypeScript、React、Vue 的深度支持，代码补全和重构比 VS Code 插件的实现更可靠，还有内置的数据库工具、HTTP 客户端。

JetBrains 全家桶的记忆点：快捷键体系统一、支持 `Settings Sync`、按语言买不同 IDE（或买 All Products Pack）。

## Chrome DevTools 与 Firefox DevTools

DevTools 是前端调试的核心工具，Chrome DevTools 是事实标准。核心面板：

```text
Elements   —— 查看/修改 DOM 和 CSS，调试布局
Console    —— 执行 JS、查看日志和报错
Sources    —— 断点调试、查看源码、Snippet 片段
Network    —— 查看网络请求、时序、瀑布图
Performance —— 录制性能分析、火焰图
Memory     —— 堆快照、内存泄漏排查
Application —— Cookie、Storage、Service Worker、缓存
```

```text
高频操作：
F12 / Cmd+Option+I —— 打开 DevTools
Cmd+Shift+C —— 检查元素
断点调试 —— Sources 面板设断点，或代码里写 debugger 语句
Network 过滤 —— 按类型（XHR/JS/CSS/Img）筛选请求
```

Chrome DevTools 与 Firefox DevTools 的差异：Firefox 的 CSS Grid/Flexbox 调试器、响应式设计模式（设备模拟）做得更细，部分 CSS 兼容性提示更准。但团队一般统一用 Chrome DevTools，Firefox 作为跨浏览器兼容性排查的补充。

```text
前端调试的三种手段：
1. Console 日志 —— 快速排查（console.log/table/time）
2. 断点调试 —— Sources 面板逐步执行、查看变量
3. Performance 录制 —— 性能分析
```

## Node.js

Node.js 是服务端的 JavaScript 运行时，前端开发里它跑的是构建工具（Webpack/Vite）、脚手架（CLI）、本地开发服务器，而不是业务后端。

```text
Node.js 的两个角色：
1. 运行时 —— 执行 JS 的工具（V8 引擎 + 系统 API）
2. 生态平台 —— 承载 npm 包管理器和几百万个 npm 包
```

版本策略：

```text
LTS（Long Term Support）—— 长期支持版，偶数版本号（18/20/22），生产和日常开发用这个
Current —— 最新特性版，奇数版本号，尝鲜用

前端项目一律锁定 LTS 版本。
```

```bash
node -v      # 查看版本
node app.js  # 运行脚本
npm -v       # 查看 npm 版本
```

Node.js 的模块系统（CommonJS vs ESM）和事件循环会在后续篇章展开，这里只关注「版本和安装」。

## 包管理器：npm、pnpm、Yarn

包管理器解决依赖的安装、版本锁定和脚本执行。三个主流工具：

```text
npm   —— Node 自带，最通用
pnpm  —— 省磁盘、严格依赖隔离，现代项目主流选择
Yarn  —— Facebook 出品，Yarn 1 已被 pnpm/npm 超越，Yarn Berry（v2+）用 PnP 模式另辟蹊径
```

核心区别在「依赖存储方式」：

```text
npm/yarn —— 扁平化 node_modules，可能有幽灵依赖（能 import 未声明的包）
pnpm     —— 硬链接 + 符号链接，node_modules 里只暴露声明过的依赖，
           省磁盘（同版本只存一份）、依赖隔离更严格
```

常用命令对照：

```text
安装依赖     —— npm install / pnpm install / yarn
安装指定包   —— npm i <pkg> / pnpm add <pkg> / yarn add <pkg>
安装开发依赖 —— npm i -D <pkg> / pnpm add -D <pkg> / yarn add -D <pkg>
全局安装     —— npm i -g <pkg> / pnpm add -g <pkg> / yarn global add <pkg>
运行脚本     —— npm run dev / pnpm dev / yarn dev
```

锁文件确保团队依赖一致：

```text
package-lock.json —— npm
pnpm-lock.yaml    —— pnpm
yarn.lock         —— Yarn
锁文件必须提交到仓库，团队依赖才能可复现。
```

pnpm 的两个关键概念：

```text
workspace —— 管理 monorepo 的 workspace 包（pnpm-workspace.yaml）
store     —— 全局内容寻址存储，所有项目共享同一份依赖文件
```

## Corepack

Corepack 是 Node.js 自带的包管理器「分流器」，按项目声明的包管理器版本自动切换，解决团队里「有人用 npm 有人用 pnpm」的不一致问题。

```jsonc
// package.json —— 声明项目用什么包管理器和版本
{
  "packageManager": "pnpm@9.1.0"
}
```

```bash
corepack enable        # 启用 corepack（Node 16.9+ 自带）
corepack prepare pnpm@9.1.0 --activate  # 预下载指定版本
pnpm install           # 之后直接跑 pnpm，corepack 自动用声明的版本
```

```text
Corepack 的作用：
package.json 里声明 packageManager 后，任何人 clone 项目跑 pnpm，
都会用声明的那个版本，而不是机器上装的随便哪个版本。
```

## Node 版本管理：nvm、fnm、Volta

不同项目可能要求不同 Node 版本，版本管理器让你在它们之间切换。

```text
nvm   —— Node Version Manager，最老牌，bash 脚本实现
fnm   —— Fast Node Manager，Rust 实现，速度比 nvm 快很多，支持 .nvmrc
Volta —— 按项目自动锁定版本，无需手动切换
```

```bash
# nvm
nvm install 20          # 安装 Node 20
nvm use 20              # 切换
nvm alias default 20    # 设默认版本

# fnm（快）
fnm install 20
fnm use 20
fnm default 20

# 项目级 .nvmrc 文件（配合 nvm/fnm）
# .nvmrc 内容：20
nvm use                 # 读 .nvmrc 自动切换
```

Volta 的理念是「声明式」——在 package.json 里声明 Node 版本，进目录自动切换：

```jsonc
// package.json
{
  "volta": {
    "node": "20.11.0",
    "pnpm": "9.1.0"
  }
}
```

```text
选型：
nvm —— 稳定、资料多，但每次开新终端要手动 use（或配 shell 集成）
fnm —— nvm 的加速替代，支持 .nvmrc 自动切换
Volta —— 最省心，声明式自动锁定，现代项目推荐
```

## Docker 与 Dev Container

### Docker

Docker 把应用和依赖打包成镜像，解决「我本地能跑你本地跑不了」的环境差异问题。前端用它跑 Node 环境、数据库、中间件，避免在宿主机装一堆服务。

```dockerfile
# Dockerfile —— 前端项目的 Node 环境
FROM node:20-alpine
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile
COPY . .
EXPOSE 5173
CMD ["pnpm", "dev"]
```

```bash
docker build -t my-app .
docker run -p 5173:5173 my-app
```

前端常见用法：本地跑 MySQL/Redis 等依赖服务，而不是把整个前端开发流程都塞进 Docker。

### Dev Container

VS Code 的 Dev Containers 插件，把整个开发环境（含编辑器配置、插件、依赖）定义成容器配置，实现「一键拉起完全一致的开发环境」。

```jsonc
// .devcontainer/devcontainer.json
{
  "name": "frontend",
  "image": "mcr.microsoft.com/devcontainers/javascript-node:20",
  "features": {
    "ghcr.io/devcontainers/features/node:1": {}
  },
  "customizations": {
    "vscode": {
      "extensions": ["dbaeumer.vscode-eslint", "esbenp.prettier-vscode"]
    }
  }
}
```

```text
Dev Container 的价值：
新人入职不用配环境，clone 后「Reopen in Container」即可，
编辑器插件、Node 版本、系统依赖全部一致。
```

## WSL

WSL（Windows Subsystem for Linux）让 Windows 用户跑完整 Linux 环境，是 Windows 前端开发的标配（Node 生态在 Linux 下更快更省事）。

```bash
# WSL 常用命令（在 PowerShell 里）
wsl --install                    # 安装 WSL2 + 默认发行版
wsl --list --verbose             # 查看已安装发行版
wsl --set-default Ubuntu         # 设默认发行版
```

```text
WSL 开发的优势：
1. Node/npm 等工具链在 Linux 下比 Windows 原生快（文件 IO 和 npm install 尤其明显）
2. 与服务器/CI 环境一致，减少「本地 Windows 能跑、Linux CI 报错」
3. 配合 VS Code Remote - WSL 插件，编辑器跑在 Windows、代码跑在 WSL
```

```text
关键配置：项目文件放 WSL 文件系统（~/ 下），不要放 Windows 的 /mnt/c 下
再通过 VS Code 访问。放 /mnt/c 会走跨文件系统访问，npm install 慢一个数量级。
```

## 应用场景实战

### 场景一：新机器十分钟搭好前端环境

```bash
# 1. 安装 Node 版本管理器（以 fnm 为例）
curl -fsSL https://fnm.vercel.app/install | bash
fnm install 20 && fnm default 20

# 2. 启用 corepack 并装 pnpm
corepack enable
corepack prepare pnpm@9.1.0 --activate

# 3. 配置 npm 镜像（国内网络加速）
pnpm config set registry https://registry.npmmirror.com

# 4. 安装 VS Code 插件（或直接同步）
#    ESLint / Prettier / Vue-Official / GitLens / Dev Containers

# 5. 验证
node -v && pnpm -v
```

### 场景二：统一团队开发环境（Dev Container）

```jsonc
// .devcontainer/devcontainer.json —— 提交到仓库
{
  "name": "web",
  "image": "mcr.microsoft.com/devcontainers/javascript-node:20",
  "features": {
    "ghcr.io/devcontainers-contrib/features/pnpm:1": { "version": "9" }
  },
  "customizations": {
    "vscode": {
      "extensions": [
        "dbaeumer.vscode-eslint",
        "esbenp.prettier-vscode",
        "Vue.volar"
      ]
    }
  },
  "postCreateCommand": "pnpm install"
}
```

任何团队成员 clone 后「Reopen in Container」，环境、Node 版本、插件、依赖全部一致，消除「我本地跑不起来」这类问题。

## 最佳实践与踩坑记录

### 最佳实践

1. 团队用 corepack + packageManager 字段锁定包管理器版本，杜绝 npm/pnpm 混用
2. 锁文件（lockfile）提交仓库，CI 里用 `--frozen-lockfile` 禁止意外改动
3. 项目 Node 版本用 .nvmrc 或 Volta 声明，新成员一条命令对齐版本
4. `.vscode/settings.json` 提交仓库，统一格式化、换行符、tab 宽度
5. 全局依赖尽量少装（eslint/prettier 之类装成项目 devDependency），避免版本漂移
6. 用 Docker 跑数据库/中间件，用 Dev Container 跑开发环境，宿主机保持干净

### 踩坑记录

```text
坑 1：npm 镜像源配置到全局导致私有包拉不到
结论：全局 registry 改成镜像后，公司私有 scope 包安装失败。
原因：镜像源不包含私有包。
解法：只给公开源走镜像，私有 scope 单独配 registry，或只改项目级 .npmrc。

坑 2：混用 npm 和 pnpm 导致依赖树损坏
结论：同一项目先用 npm 后用 pnpm，node_modules 结构混乱、依赖丢失。
原因：两者 node_modules 结构不同，互相覆盖产生半损坏状态。
解法：换包管理器先删 node_modules 和锁文件，只用一种；用 corepack 强制统一。

坑 3：WSL 里项目放 /mnt/c 导致 npm install 极慢
结论：install 动辄几分钟，热更新也卡。
原因：跨文件系统（Windows NTFS 经 9p 协议）访问，IO 开销巨大。
解法：项目放 WSL 家目录 ~/，用 VS Code Remote-WSL 打开。

坑 4：Dev Container 里 node_modules 挂载导致性能/兼容问题
结论：容器内依赖和宿主机冲突，或 volume 挂载后权限报错。
原因：宿主机 node_modules（尤其含原生模块）与容器平台二进制不兼容。
解法：node_modules 用 named volume 而非 bind mount，原生模块在容器内重装。

坑 5：新版 Node 的 ESM 特性让老构建工具报错
结论：升 Node 后 Webpack 4 或旧脚手架直接崩。
原因：Node 新版本默认行为或 API 变化，老工具不兼容。
解法：升 Node 前查项目工具链支持范围，先升级构建工具再升 Node。

坑 6：全局装了 eslint 项目里却报版本不一致
结论：CLI 和插件版本对不上，lint 结果和 CI 不一致。
原因：全局 eslint 版本和项目 devDependency 不同。
解法：eslint/prettier 一律装项目依赖，用 npx eslint 调用，不依赖全局版本。
```
