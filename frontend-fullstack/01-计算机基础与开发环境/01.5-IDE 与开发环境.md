## 概述

开发环境决定了前端工程师的日常效率。这一篇把前端开发用到的工具链串起来：编辑器、浏览器调试工具、Node.js 运行时、包管理器、版本管理、容器化环境。

```text
一条典型的前端开发链路：
编辑器写代码（VS Code）→ 浏览器调试（Chrome DevTools）→ Node.js 跑构建/服务 →
包管理器装依赖（pnpm）→ 版本管理（nvm/Volta）→ 容器化部署（Docker）
```

选工具的原则：不求多，求顺——同一类工具选一个用熟，团队统一，别各自为战导致环境不一致。

## 编辑器：VS Code

VS Code 是前端事实标准编辑器。轻量、插件生态庞大、内置 Git 和终端，开箱就能干活：

```text
核心特性：
1. 多光标编辑 —— Alt+Click 加光标，批量改
2. 命令面板 —— Ctrl/Cmd+Shift+P，所有操作都能搜到
3. 集成终端 —— 编辑器里直接跑命令，不用切窗口
4. Git 集成 —— 内置 diff、暂存、提交，可视化解冲突
5. Remote 开发 —— 远程 SSH、容器、WSL 里开发，本地只留个瘦客户端
```

```text
前端必备插件（按用途分类）：

| 类别 | 插件 | 作用 |
|---|---|---|
| 语言服务 | ESLint / Prettier | 代码检查 + 格式化 |
| 框架 | Vue - Official / ESLint(React) 等 | 框架语法高亮、补全、模板支持 |
| 效率 | Auto Rename Tag / Path Intellisense | 自动改标签、路径补全 |
| 工具 | GitLens / Live Share | Git 增强 / 结对编程 |
```

```json
// .vscode/settings.json —— 团队共享编辑器配置（提交进仓库）
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.tabSize": 2,
  "files.eol": "\n",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  }
}
```

```text
.vscode/ 目录（settings.json、extensions.json、launch.json）提交进仓库，
团队成员的编辑器行为自动统一，减少"你那边怎么和我这边格式不一样"的问题。
extensions.json 的 recommendations 字段能推荐插件，新同事克隆项目后一键装齐。
```

## JetBrains IDE

JetBrains 家的 IDE 以 WebStorm（前端）和 IntelliJ IDEA（Java 全栈）为代表，特点是"开箱即用的重型 IDE"：

```text
WebStorm 相对 VS Code 的优势：
1. 代码智能更强：重构（rename、extract）、类型推断、跳转定义更准
2. 内置调试器更完善：断点、变量、调用栈、性能分析一体
3. 数据库工具：内置 DataGrip 功能，直接连库看表
4. 集成更全：VCS、终端、TODO、测试运行器都内置
```

```text
怎么选：
VS Code —— 轻量、免费、插件生态大，前端主流，公司标配
WebStorm —— 付费（有免费社区版限制），大项目重构体验好，重度 TS/框架用户觉得值
```

```text
两者不冲突：很多人 VS Code 日常开发 + WebStorm 做大型重构。选择跟团队走，别单干。
```

## 浏览器调试：Chrome DevTools

Chrome DevTools 是前端最重要的调试工具，F12 打开。日常定位问题全靠它：

```text
八大面板及用途：
1. Elements —— 看/改 DOM 和 CSS，实时预览样式
2. Console —— 执行 JS、看日志、报错
3. Sources —— 断点调试 JS、看源码、snippets
4. Network —— 看所有请求（状态、耗时、参数、响应）
5. Performance —— 录制性能分析，找长任务和瓶颈
6. Memory —— 堆快照，查内存泄漏
7. Application —— 看 localStorage、Cookie、IndexedDB、Service Worker
8. Lighthouse —— 一键出性能/可访问性/SEO 报告
```

```javascript
// Sources 面板断点调试
function calculate(a, b) {
  const result = a + b;   // 在这行打断点，看 a、b、result 的值
  return result;
}
calculate(1, 2);
// 快捷键：F10 单步跳过，F11 单步进入，Shift+F11 跳出，F8 继续
```

```text
Network 面板排障要点（前端联调必看）：
1. 先看状态码：200 正常，404 路径错，500 后端错，304 走缓存
2. 看耗时瀑布图：排队、DNS、连接、TTFB、下载各段哪段慢
3. 看请求头/响应头：跨域（CORS）、缓存策略（Cache-Control）、Cookie
```

```text
实用小技巧：
1. $0 —— Console 里引用 Elements 当前选中的元素
2. console.table() —— 数组/对象以表格形式输出
3. Network 里右键请求 → Copy as fetch/cURL —— 复现请求给后端
4. Performance 里找 Long Task —— 定位主线程卡顿
```

## Firefox DevTools

Firefox DevTools 是 Firefox 自带的调试工具，功能与 Chrome DevTools 类似，但有几处独有优势：

```text
Firefox DevTools 的特色：
1. CSS Grid 可视化 —— 显示网格线，调 grid 布局比 Chrome 直观
2. Flexbox 检查器 —— 可视化 flex 容器和项目
3. 字体面板 —— 看页面用了哪些字体、加载耗时
4. 无障碍面板 —— 检查 ARIA、对比度等可访问性问题
5. 响应式设计模式 —— 模拟设备、触屏、慢网速
```

```text
前端要两个浏览器都测：不是所有用户都用 Chrome。Firefox、Safari 的渲染和 API 支持有差异，
开发时至少用 Chrome 主调试，Firefox/Safari 做兼容性回归。
```

## Node.js

Node.js 是跑在服务器端的 JavaScript 运行时。前端即使不写后端，也离不开它——所有构建工具（Vite、Webpack）、包管理器、脚手架都运行在 Node 上：

```text
前端用 Node 做什么：
1. 跑开发服务器（vite dev、webpack-dev-server）
2. 跑构建（vite build、打包、压缩、Tree Shaking）
3. 跑脚本（npm scripts、自动化、代码生成）
4. 本地 mock 接口、SSR（服务端渲染）
```

```bash
node -v              # 查看版本
node index.js        # 运行脚本
node --inspect index.js   # 开启调试，可用 DevTools 断点调试 Node
```

```javascript
// 一个 Node 脚本示例：批量重命名文件
const fs = require("node:fs");
const path = require("node:path");
const dir = process.argv[2];
fs.readdirSync(dir).forEach((f) => {
  const newName = f.replace(/\.jpeg$/, ".jpg");
  fs.renameSync(path.join(dir, f), path.join(dir, newName));
});
```

```text
Node 的 LTS（长期支持）版本是生产环境的稳妥选择。Node 每年 4 月发偶数版本（LTS），
10 月发奇数版本（非 LTS）。团队项目统一用某个 LTS，配合 nvm/Volta 锁定。
```

## 包管理器：npm、pnpm、Yarn

包管理器负责安装、更新、卸载依赖，解决版本冲突。npm 是 Node 自带的，pnpm 和 Yarn 是它的优化替代：

```text
三者对比：

| 维度 | npm | pnpm | Yarn |
|---|---|---|---|
| 安装速度 | 慢 | 快（硬链接） | 快 |
| 磁盘占用 | 大（每项目一份） | 小（全局 store 共享） | 中 |
| 依赖结构 | 扁平 node_modules | 符号链接（严格） | 扁平/Plug'n'Play |
| workspace | 支持 | 原生且强 | 支持 |
| 幽灵依赖 | 有 | 无 | 基本无 |
| 现状 | 默认标配 | 前端主流 | 使用率下降 |
```

```bash
# npm 常用命令
npm init -y                 # 初始化 package.json
npm install                 # 安装全部依赖
npm install lodash          # 安装到 dependencies
npm install -D eslint       # 安装到 devDependencies（-D）
npm install -g pnpm         # 全局安装
npm uninstall lodash        # 卸载
npm run dev                 # 跑 package.json 里的 scripts
npx vite                    # 不安装直接运行包（npx）
```

```text
dependencies vs devDependencies：
dependencies —— 运行时需要的（axios、vue、react）
devDependencies —— 只在开发/构建时需要的（vite、eslint、typescript）
生产部署用 npm install --production 或 CI 里区分，能少装一大半依赖。
```

```text
pnpm 的核心优势：
1. 内容寻址存储（content-addressable store）—— 所有项目共享一个全局仓库，
   相同版本的包只存一份，用硬链接引用，省磁盘、装得快
2. 严格依赖树 —— 只有 package.json 声明的依赖能 import，
   杜绝"幽灵依赖"（npm 扁平化导致能 require 没声明的包）
3. workspace 原生支持 monorepo
```

```bash
# pnpm 常用命令
pnpm add lodash             # 安装
pnpm add -D eslint          # 开发依赖
pnpm remove lodash          # 卸载
pnpm run dev                # 跑脚本
pnpm dlx vite               # 同 npx
```

```text
Yarn 分两个时代：
Yarn 1（Classic）—— 早期 npm 的加速替代，现在使用率下降
Yarn 2+（Berry）—— 引入 PnP（Plug'n'Play，不用 node_modules，依赖存 .yarn/cache），
理念先进但生态兼容有摩擦，迁移成本高，前端用得不多
```

## Corepack

Corepack 是 Node.js 自带的"包管理器版本管理"工具，用来统一 pnpm/Yarn 的版本：

```bash
corepack enable                 # 启用（会接管 pnpm/yarn 命令）
corepack prepare pnpm@9.0.0 --activate   # 准备指定版本的 pnpm
corepack prepare yarn@4.0.0 --activate
```

```text
package.json 里的 packageManager 字段声明项目用哪个包管理器、哪个版本：
```

```json
{
  "packageManager": "pnpm@9.0.0"
}
```

```text
Corepack 的价值：团队项目锁定 pnpm 版本，新同事克隆后 corepack enable，
自动用锁定的版本，不会"我装的 pnpm 8 你装的 pnpm 9"导致 lockfile 冲突。
注意：Corepack 管理的是 pnpm/yarn 本身，nvm/Volta 管理的是 node 本身，层次不同。
```

## Node 版本管理：nvm、fnm、Volta

不同项目依赖不同 Node 版本（老项目跑在 14，新项目用 20），版本管理器让你随时切换：

### nvm

nvm（Node Version Manager）是最老牌的方案，纯 shell 脚本实现：

```bash
nvm install 20            # 安装 Node 20
nvm install 18.20.4       # 安装指定小版本
nvm use 20                # 切换到 20（当前 shell）
nvm alias default 20      # 设默认版本（新终端生效）
nvm ls                    # 列出已装版本
nvm ls-remote             # 列出可装版本
```

```text
nvm 的缺点：切换版本要手动 nvm use，且 shell 启动时要加载 nvm 脚本（拖慢终端）。
可以在项目目录放 .nvmrc 文件写版本号，进目录后 nvm use 自动读。
```

### fnm

fnm（Fast Node Manager）用 Rust 写的，切换速度快，体验比 nvm 好：

```bash
fnm install 20            # 安装
fnm use 20                # 切换
fnm default 20            # 设默认
fnm list                  # 列出
```

```text
fnm 支持自动切换：配置 shell 钩子后，进到有 .nvmrc 或 .node-version 的目录自动切版本，
不用手动 use。macOS/Linux 推荐 fnm 替代 nvm。
```

### Volta

Volta 是"工具链管理器"，不仅能管 Node，还能锁 npm/pnpm/yarn 版本，按项目固定：

```bash
volta install node@20        # 全局装 Node 20
volta install pnpm@9         # 全局装 pnpm 9
volta pin node@20            # 项目里固定 node 版本（写入 package.json）
volta pin pnpm@9             # 固定 pnpm 版本
```

```text
Volta 的 pin 会把版本写进 package.json 的 volta 字段，任何人进这个项目自动用锁定的版本，
团队环境最省心。对比：nvm/fnm 偏"手动切换"，Volta 偏"项目自动锁定"。
```

## Docker

Docker 把应用和它的运行环境打包成容器（container），实现"构建一次，处处运行"：

```text
核心概念：
1. 镜像（Image）—— 打包好的只读模板，含应用 + 依赖 + 系统环境
2. 容器（Container）—— 镜像的运行实例，轻量隔离
3. Dockerfile —— 构建镜像的脚本
4. Docker Compose —— 编排多个容器的工具（一个 yml 定义整个应用栈）
```

```dockerfile
# Dockerfile —— 前端静态站点构建 + 部署（多阶段构建）
FROM node:20-alpine AS build
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install
COPY . .
RUN pnpm build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
```

```bash
docker build -t my-app .        # 构建镜像
docker run -p 8080:80 my-app    # 运行容器，映射端口
docker ps                       # 看运行中的容器
docker exec -it <id> sh         # 进入容器
docker logs <id>                # 看容器日志
docker compose up -d            # 按 compose 文件启动整个栈
```

```text
前端用 Docker 的场景：
1. 本地跑依赖服务（MySQL、Redis、Nginx），不用在宿主机装一堆环境
2. 统一构建环境，避免"我本地能跑 CI 不行"
3. 部署打包，把构建产物 + Web 服务器打成镜像发布
```

## Dev Container

Dev Container 是 VS Code 的功能，把开发环境也装进容器，实现"环境即代码"：

```text
解决的问题：新同事入职要装一堆东西（Node 版本、数据库、工具），
环境不一致导致"我本地跑不起来"。Dev Container 把整套环境定义成配置文件，一键复现。
```

```json
// .devcontainer/devcontainer.json
{
  "name": "Frontend Dev",
  "image": "mcr.microsoft.com/devcontainers/javascript-node:20",
  "features": {
    "ghcr.io/devcontainers/features/docker-in-docker:2": {}
  },
  "customizations": {
    "vscode": {
      "extensions": ["dbaeumer.vscode-eslint", "esbenp.prettier-vscode"]
    }
  },
  "forwardPorts": [5173],
  "postCreateCommand": "pnpm install"
}
```

```text
团队把 .devcontainer/ 提交进仓库，任何有 Docker + VS Code 的人打开项目，
自动拉起配置好的容器环境（正确的 Node 版本、依赖、插件），真正做到环境零配置。
```

## WSL

WSL（Windows Subsystem for Linux）让 Windows 直接跑完整的 Linux 环境，是 Windows 前端开发的标配：

```bash
wsl --install                  # 安装 WSL2（默认装 Ubuntu）
wsl -l -v                      # 看已装的发行版和版本（v2）
wsl --set-version Ubuntu 2     # 升级到 WSL2
wsl                            # 进入 Linux
```

```text
为什么 Windows 前端开发要用 WSL：
1. 前端工具链（Node、pnpm、构建脚本）原生跑在 Linux 上，和线上环境一致
2. 文件系统性能好：WSL2 里项目放 Linux 文件系统（~/），别放 /mnt/c（慢一个数量级）
3. 命令行体验：bash/zsh、管道、工具生态完胜 PowerShell
```

```text
WSL2 是完整 Linux 内核虚拟机，不是模拟层，兼容性和性能都远好于 WSL1。
配合 VS Code 的 WSL Remote 插件，编辑器跑在 Windows，代码和终端跑在 WSL 里。
```

## 应用场景实战

### 场景 1：新项目环境从零搭起

一个新前端项目，从装 Node 到跑起来：

```bash
# 1. 用 fnm 装并固定 Node 版本
fnm install 20
fnm default 20
fnm use 20

# 2. 用 Corepack 启用 pnpm
corepack enable

# 3. 用 Vite 创建项目
pnpm create vite my-app --template vue
cd my-app

# 4. 固定项目工具链版本
volta pin node@20
volta pin pnpm@9

# 5. 装依赖并跑起来
pnpm install
pnpm dev        # 打开浏览器访问 http://localhost:5173
```

### 场景 2：用 Docker 一键起本地依赖

本地开发需要 Redis 和 MySQL，用 Docker Compose 一次拉起：

```yaml
# docker-compose.yml
services:
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
  mysql:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: app
    ports:
      - "3306:3306"
    volumes:
      - mysql-data:/var/lib/mysql

volumes:
  mysql-data:
```

```bash
docker compose up -d      # 后台拉起 redis + mysql
docker compose down       # 停掉
```

### 场景 3：给团队统一开发环境

把编辑器配置、Node 版本、容器环境都提交进仓库，新同事克隆即用：

```text
项目里提交这些文件：
.nvmrc                     # 或 .node-version，声明 Node 版本
package.json               # packageManager 字段锁定包管理器
.vscode/settings.json      # 编辑器行为统一
.vscode/extensions.json    # 推荐插件
.devcontainer/devcontainer.json  # 完整容器环境（可选）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 团队统一 Node LTS 版本，用 .nvmrc 或 Volta pin 锁定，别各用各的
2. 用 pnpm 替代 npm 作为项目包管理器，省磁盘、装得快、依赖更严格
3. .vscode/ 和 .devcontainer/ 提交进仓库，环境配置代码化、团队共享
4. 依赖分类清楚：运行时依赖进 dependencies，构建工具进 devDependencies
5. 本地依赖服务（数据库、缓存）用 Docker Compose 起，不污染宿主机
6. 生产部署用多阶段 Dockerfile，构建产物和运行环境分离，镜像更小

### 踩坑记录

```text
坑 1：换 Node 版本后 pnpm 命令没了
结论：升级 Node 后全局装的 pnpm 失效，报 command not found。
原因：npm 全局包跟随 node 版本目录，nvm 切版本后旧全局包不在新版本的 PATH 里。
解法：用 Corepack 管理 pnpm/yarn（跟随 node 自带），或每次切版本后重装全局包。

坑 2：锁文件冲突导致 CI 构建失败
结论：本地 pnpm 8 生成 lockfile，CI 用 pnpm 9 解析不一致，装依赖报错。
原因：包管理器版本不一致，lockfile 格式不兼容。
解法：package.json 里 packageManager 字段锁定版本 + CI 里 corepack enable 自动对齐。

坑 3：幽灵依赖本地能跑、线上报错
结论：本地 require 了没在 package.json 声明的包，构建能过，上线后模块找不到。
原因：npm 扁平化把传递依赖提升到顶层 node_modules，能意外 import 到没声明的包。
解法：用 pnpm（严格依赖树），或装 eslint-plugin-import 等规则禁止 import 未声明依赖。

坑 4：Docker 里 node_modules 没生效
结论：容器里 COPY . . 把本地 node_modules 覆盖进去了，依赖装错平台。
原因：本地（如 macOS）的 node_modules 含平台二进制，直接拷进 Linux 容器跑不起来。
解法：Dockerfile 用 .dockerignore 排除 node_modules，容器内重新 install。

坑 5：WSL 里项目放 /mnt/c 慢到怀疑人生
结论：WSL2 里访问 Windows 文件系统（/mnt/c）构建、装依赖极慢。
原因：WSL2 跨文件系统走 9p 协议，IO 性能差一个数量级。
解法：项目放 Linux 文件系统（~/projects），Windows 通过 \\wsl$ 访问。

坑 6：DevTools 看的是缓存不是最新代码
结论：改了代码刷新页面不生效，以为没保存。
原因：浏览器缓存了旧资源，或 Service Worker 拦截了请求。
解法：DevTools Network 勾选 Disable cache，或 Ctrl+Shift+R 强制刷新；清掉 Service Worker。
```
