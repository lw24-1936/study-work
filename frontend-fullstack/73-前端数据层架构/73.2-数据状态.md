## 概述

前端状态不该被笼统地塞进一个 store，而应该按「数据从哪来、活多久、谁在消费」分成几类。区分 UI State 和 Server State 是第一步：UI 状态属于组件交互、转瞬即逝，服务端状态属于远程数据的本地快照、有缓存和过期问题，两者管理方式完全不同。

```text
前端数据状态的五类划分：
1. UI State —— 交互界面状态：弹窗开关、选中项、输入框内容
2. Server State —— 服务端数据的本地副本：用户列表、订单详情
3. Cache —— 为加速和离线而复用的数据副本：接口缓存、静态资源
4. Persistent State —— 需要跨会话持久化的状态：主题、登录态
5. Derived State —— 由其他状态计算得出的状态：筛选结果、总数
```

```js
// 五类状态的一个直观对照
const state = {
  ui: { modalOpen: false, selectedTab: 'list' },          // UI State
  server: { users: [], order: null },                     // Server State
  cache: { 'users:page1': { data: [], ttl: 1700000000 } },// Cache
  persistent: { theme: 'dark', token: null },             // Persistent State
  // derived: activeUsers = users.filter(u => u.active)   // Derived State（计算得出）
};
```

## UI State

UI State 是描述「界面此刻长什么样」的临时状态，生命周期跟着组件走：弹窗是否打开、哪个 tab 被选中、表单输入了什么。它只对当前交互有意义，一般不需要持久化，也不需要跨页面共享。

```text
UI State 的关键点：
1. 局部性 —— 多数只属于单个组件，不必全局
2. 短暂 —— 组件卸载即丢弃，不值得持久化
3. 高频更新 —— 输入框每个字符都可能触发更新
4. 不共享 —— 能不下沉到全局 store 就不下沉
```

```js
// React 里的局部 UI State
function Dropdown() {
  const [open, setOpen] = useState(false);      // UI State
  const [keyword, setKeyword] = useState('');    // UI State
  return (
    <div>
      <button onClick={() => setOpen(!open)}>菜单</button>
      {open && <input value={keyword} onChange={e => setKeyword(e.target.value)} />}
    </div>
  );
}
```

UI State 放错地方（塞进全局 store）是状态管理混乱的根源：一个下拉框的开关不需要全应用可见。

## Server State

Server State 是「服务端数据的本地快照」：前端请求回来的数据，真实源头在服务端。它的特点是异步获取、会过期、可能被多端修改，因此自带缓存、失效、重取、去重这些问题，需要专门的管理方式。

```text
Server State 的关键点：
1. 源头在服务端 —— 前端只是副本，真实数据可能已变化
2. 会过期 —— 需要失效策略和重新拉取
3. 异步 —— 有 loading / error / data 三态
4. 多端共享 —— 别的用户可能改过同一份数据
```

```js
// 用 TanStack Query 管理 Server State
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

function UserList() {
  const { data, isLoading, error } = useQuery({
    queryKey: ['users'],
    queryFn: () => fetch('/api/users').then(r => r.json()),
  });
  if (isLoading) return <div>加载中</div>;
  if (error) return <div>加载失败</div>;
  return <ul>{data.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}
```

把 Server State 交给专门的库（TanStack Query、SWR）管理缓存、重取和去重，比手写 useEffect + useState 可靠得多。

## Cache

Cache 是「为了下次更快而保留的数据副本」。在前端，缓存横跨多个层面：HTTP 缓存、接口数据缓存、静态资源缓存。缓存的核心矛盾是新鲜度和命中率的平衡——缓存越久命中越高，但越可能返回过期数据。

```text
Cache 的关键点：
1. 以空间换时间 —— 保留副本换下次访问速度
2. 有失效策略 —— TTL、LRU、版本号、主动失效
3. 分层 —— 内存缓存、浏览器存储、HTTP 缓存各司其职
4. 一致性风险 —— 缓存越久，数据越可能过期
```

```js
// 一个带 TTL 的简单内存缓存
const cache = new Map();

async function cachedFetch(key, fn, ttl = 60_000) {
  const hit = cache.get(key);
  if (hit && Date.now() - hit.ts < ttl) return hit.data;
  const data = await fn();
  cache.set(key, { data, ts: Date.now() });
  return data;
}

// 60 秒内重复调用只请求一次
const users = await cachedFetch('users', () => fetch('/api/users').then(r => r.json()));
```

缓存失效是编程界两大难题之一。设计缓存时先想清楚「什么时候必须刷新」，而不是「先缓存起来再说」。

## Persistent State

Persistent State 是需要跨会话、跨刷新保留的状态，通常写入 Local Storage、IndexedDB 或 Cookie。主题偏好、登录 token、草稿都属于这一类。它与 Server State 的区别是「源头就在本地」，服务端不负责保存。

```text
Persistent State 的关键点：
1. 跨会话 —— 刷新、关闭浏览器后仍在
2. 存本地 —— Local Storage / IndexedDB / Cookie
3. 需序列化 —— 对象存字符串，读回要反序列化
4. 有安全边界 —— 敏感数据不能随便落本地
```

```js
// 主题偏好持久化 + 恢复
function useTheme() {
  const [theme, setTheme] = useState(() => localStorage.getItem('theme') || 'light');

  useEffect(() => {
    localStorage.setItem('theme', theme);
    document.documentElement.dataset.theme = theme;
  }, [theme]);

  return [theme, setTheme];
}
```

Persistent State 适合存「用户自己的偏好」，不适合存「业务数据」——业务数据放服务端才是真相来源，本地存业务数据会引入同步问题。

## Derived State

Derived State 不是独立存储的状态，而是由其他状态「计算」出来的结果：列表的筛选结果、购物车总价、未读消息数。它的原则是「不重复存储，只派生计算」，避免同一份数据有两处真相。

```text
Derived State 的关键点：
1. 可计算 —— 由现有状态推导，不需要新存储
2. 单一真相 —— 源状态只有一份，派生值跟着变
3. 用选择器缓存 —— 避免每次渲染重复计算
4. 别手动同步 —— 源变了派生值自动重算
```

```js
// 用 useMemo 缓存派生值
function TodoList({ todos }) {
  const activeCount = useMemo(
    () => todos.filter(t => !t.done).length, // Derived State
    [todos]
  );
  return <span>剩余 {activeCount} 项</span>;
}
```

```js
// 状态库里用 selector 派生（Zustand）
const useStore = create((set) => ({
  items: [],
  add: (item) => set(s => ({ items: [...s.items, item] })),
}));
const total = useStore(s => s.items.reduce((sum, i) => sum + i.price, 0)); // Derived
```

手动维护派生状态（比如 add 时同步更新 total）是 bug 温床，正确的做法是只改源状态，派生值让计算逻辑自动更新。

## 应用场景实战

### 场景一：搜索列表（UI + Server + Derived 协同）

```js
// 输入关键字是 UI State，结果是 Server State，筛选是 Derived State
function SearchPage() {
  const [keyword, setKeyword] = useState('');                    // UI State
  const { data } = useQuery({
    queryKey: ['search', keyword],
    queryFn: () => fetch(`/api/search?q=${keyword}`).then(r => r.json()),
    enabled: keyword.length > 1,                                 // Server State
  });
  const topResults = useMemo(
    () => (data || []).filter(item => item.score > 0.8),         // Derived State
    [data]
  );
  return (
    <div>
      <input value={keyword} onChange={e => setKeyword(e.target.value)} />
      {topResults.map(item => <div key={item.id}>{item.title}</div>)}
    </div>
  );
}
```

### 场景二：购物车（Server 同步 + 本地持久化草稿）

```js
// 购物车条目来自服务端，本地存草稿避免刷新丢失
async function addToCart(product) {
  const draft = JSON.parse(localStorage.getItem('cart-draft') || '[]');
  draft.push(product);
  localStorage.setItem('cart-draft', JSON.stringify(draft));

  try {
    await fetch('/api/cart', {
      method: 'POST',
      body: JSON.stringify({ productId: product.id }),
    });
    localStorage.removeItem('cart-draft'); // 同步成功清草稿
  } catch (e) {
    console.log('同步失败，草稿已保留');
  }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先分清状态类型，再选管理工具：UI State 局部化，Server State 用缓存库
2. 派生状态只计算不存储，别手动维护第二份真相
3. Server State 交给 TanStack Query / SWR，别手写 useEffect 请求
4. 缓存都要有失效策略（TTL / 版本号 / 主动失效），没有失效的缓存是定时炸弹
5. 持久化只存用户偏好和小配置，业务数据以服务端为准
6. 敏感数据不落 Local Storage，偏好类数据才用 Persistent State

### 踩坑记录

```text
坑 1：把 Server State 复制进全局 store
结论：同一份用户列表在 store 和组件里各存一份，手动同步后经常不一致。
原因：Server State 源头在服务端，手动复制必然产生双真相。
解法：用 TanStack Query/SWR 管理 Server State，组件读缓存，不复制进 store。

坑 2：派生状态手动同步
结论：加购物车时忘了更新 total，结算金额和列表对不上。
原因：把本应计算的派生值当独立状态存储，源变了派生值没跟着变。
解法：total 用 selector 或 useMemo 从 items 实时计算，删掉手动更新。

坑 3：缓存没有失效策略
结论：用户改完资料，列表页还显示旧头像。
原因：缓存设了永久有效，从不清除也不刷新。
解法：给缓存加 TTL，写操作后主动 invalidate 相关 key。

坑 4：Local Storage 存业务数据引发多端不一致
结论：换台设备或换浏览器，数据「消失」了。
原因：业务数据源头在服务端，本地存储只是孤本，没有同步机制。
解法：业务数据走服务端接口，本地只存偏好和临时草稿。

坑 5：派生状态在渲染里重复重算
结论：大列表每次渲染都跑一遍 filter，页面卡顿。
原因：派生计算没做缓存，每次渲染重新执行。
解法：用 useMemo / selector 缓存派生值，依赖不变就不重算。
```
