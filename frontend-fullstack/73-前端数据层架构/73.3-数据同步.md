## 概述

数据同步解决「本地展示的数据如何与服务端保持一致」。前端拿到数据后，服务端可能随时变化，用户也可能在本地发起修改——同步策略决定了数据多久刷新一次、修改时如何保证体验、冲突时听谁的。核心取舍是「实时性、一致性、体验」三者之间的平衡。

```text
前端数据同步的六种策略：
1. Polling —— 定时轮询，简单但浪费
2. Revalidation —— 失焦/重连时重新校验数据
3. Optimistic Update —— 先改本地再同步，失败回滚
4. Conflict Resolution —— 多端修改冲突时的取舍规则
5. Offline First —— 离线也能用，恢复后同步
6. Event Driven —— 事件驱动的增量同步
```

```js
// 同步策略的选择逻辑
function pickSyncStrategy(need) {
  if (need.immediate && need.feedback) return 'Optimistic Update';
  if (need.freshness && !need.realtime) return 'Revalidation';
  if (need.simple && !need.realtime) return 'Polling';
  if (need.offline) return 'Offline First';
  return 'Polling';
}
```

## Polling

Polling（轮询）是定时器周期性地重新请求数据，用最简单的「过一会再问一次」来逼近实时。实现零门槛，但大部分请求是空转，实时性和浪费成正比。

```text
Polling 的关键点：
1. 固定间隔 —— 每隔 N 秒请求一次
2. 实现简单 —— setInterval 包一层 fetch
3. 浪费带宽 —— 数据没变也在请求
4. 实时性受限 —— 新数据最多延迟一个间隔
```

```js
// 轮询：每 5 秒拉一次最新价格
function pollPrice() {
  const timer = setInterval(async () => {
    const price = await fetch('/api/price').then(r => r.json());
    render(price);
  }, 5000);
  return () => clearInterval(timer);
}

const stop = pollPrice();
// 页面卸载时 stop() 清理定时器
```

轮询适合对实时性要求不高、数据量小的场景。需要即时推送时，WebSocket 和 SSE 都比轮询更合适。

## Revalidation

Revalidation（重新校验）不在固定间隔请求，而是在「用户重新关注数据」的时刻刷新：窗口重新聚焦、网络从离线恢复、路由重新进入。它把刷新动作绑定到用户行为，比盲目轮询更省。

```text
Revalidation 的关键点：
1. 事件触发 —— 聚焦、重连、重访时刷新
2. 常配 SWR —— stale-while-revalidate 先显示旧数据再后台刷新
3. 比轮询省 —— 没用户关注就不请求
4. 体验好 —— 旧数据兜底，不闪空白
```

```js
// SWR 的 stale-while-revalidate 语义
import useSWR from 'swr';

function Profile() {
  const { data } = useSWR('/api/profile', fetcher, {
    revalidateOnFocus: true,   // 窗口聚焦时重新校验
    revalidateOnReconnect: true, // 网络恢复时重新校验
  });
  return <div>{data?.name}</div>;
}

// 窗口聚焦触发刷新
window.addEventListener('focus', () => revalidate());
```

Revalidation 是「按需刷新」的代表，配合 SWR 的缓存先返回旧数据、后台静默更新，用户几乎感知不到刷新过程。

## Optimistic Update

Optimistic Update（乐观更新）在用户操作后立即更新本地 UI，不等服务端确认，同时后台发请求；失败再回滚。它把「等待网络」的延迟从体验里抹掉，适合点赞、拖拽排序、已读标记这类高频轻量操作。

```text
Optimistic Update 的关键点：
1. 先改 UI —— 操作即反馈，不等网络
2. 后台同步 —— 同时发请求写服务端
3. 失败回滚 —— 请求失败恢复原状
4. 需要 rollback 逻辑 —— 复杂度集中在回滚
```

```js
// 乐观更新：点赞立即 +1，失败回滚
function like(postId) {
  // 1. 乐观更新：先改本地缓存
  queryClient.setQueryData(['post', postId], old => ({
    ...old,
    liked: true,
    likes: old.likes + 1,
  }));

  // 2. 后台同步
  fetch(`/api/posts/${postId}/like`, { method: 'POST' }).catch(() => {
    // 3. 失败回滚
    queryClient.setQueryData(['post', postId], old => ({
      ...old,
      liked: false,
      likes: old.likes - 1,
    }));
  });
}
```

乐观更新让界面「秒回」，但代价是要写清楚回滚逻辑，且要接受「本地短暂地与服务端不一致」这个事实。

## Conflict Resolution

Conflict Resolution（冲突解决）处理「同一份数据被多处同时修改」时的取舍。多端同步、离线编辑、协作场景都逃不开冲突。策略从简单到复杂：后写覆盖、版本比较、字段级合并、人工仲裁。

```text
冲突解决策略：
1. Last Write Wins —— 后写覆盖先写，简单但丢更新
2. 版本比较 —— 基于版本号判断，旧版本不允许覆盖
3. 字段级合并 —— 只冲突的字段才需要处理
4. 人工仲裁 —— 冲突时把选择权交给用户
```

```js
// 基于版本号的乐观并发控制
async function updatePost(id, patch) {
  const current = await fetch(`/api/posts/${id}`).then(r => r.json());
  const res = await fetch(`/api/posts/${id}`, {
    method: 'PUT',
    body: JSON.stringify({ ...patch, version: current.version }),
  });
  if (res.status === 409) {
    // 版本冲突：提示用户合并或刷新
    console.log('数据已被他人修改，请刷新后重试');
  }
}
```

选哪种策略取决于业务对「丢更新」的容忍度：点赞用后写覆盖无所谓，文档编辑就必须上版本比较或 CRDT。

## Offline First

Offline First 把「离线可用」当默认前提而不是异常：本地先有完整数据，操作先写本地，网络可用时再同步到服务端。它让应用在网络差、甚至断网时依然能用。

```text
Offline First 的关键点：
1. 本地为先 —— 读写都先落到本地存储
2. 后台同步 —— 网络恢复后自动同步
3. 数据持久 —— IndexedDB 存业务数据
4. 冲突处理 —— 离线期间可能产生冲突
```

```js
// 离线优先：写操作先落本地，网络恢复后同步
async function saveTodo(todo) {
  await db.put('todos', { ...todo, sync: 'pending' }); // 先写本地
  if (navigator.onLine) {
    syncPending(); // 在线则立即同步
  }
}

async function syncPending() {
  const pending = await db.getAll('todos', 'pending');
  for (const t of pending) {
    await fetch('/api/todos', { method: 'POST', body: JSON.stringify(t) });
    await db.put('todos', { ...t, sync: 'synced' });
  }
}

window.addEventListener('online', syncPending);
```

Offline First 的完整实现涉及缓存策略、同步队列和冲突解决，落地常借助 PWA + Service Worker + IndexedDB。

## Event Driven

Event Driven（事件驱动）让数据同步不再靠「主动去问」，而是「订阅变化」：数据变化以事件的形式广播，感兴趣的订阅者收到事件后更新本地。它把同步从拉模式变成推模式，减少无效请求、实现即时更新。

```text
Event Driven 的关键点：
1. 事件广播 —— 数据变化发布事件
2. 订阅更新 —— 订阅者收到后更新本地
3. 解耦 —— 生产者和消费者互不直接依赖
4. 即时 —— 变化发生即通知，无轮询延迟
```

```js
// 事件驱动的数据同步：服务端变化推送，本地订阅更新
const bus = new EventTarget();

// 订阅价格变化事件
bus.addEventListener('price-change', (e) => {
  const { id, price } = e.detail;
  updateLocalPrice(id, price);
});

// 收到服务端推送时广播事件（WebSocket 或 SSE 触发）
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === 'price-change') {
    bus.dispatchEvent(new CustomEvent('price-change', { detail: msg }));
  }
};
```

事件驱动和 Server State 缓存库（Query、SWR）可以配合：写操作后主动失效缓存，触发订阅组件重新拉取，本质就是事件驱动同步。

## 应用场景实战

### 场景一：实时协作看板（事件驱动 + 乐观更新）

```js
// 拖拽卡片后立即更新本地（乐观），并广播给其他端（事件驱动）
function moveCard(cardId, toColumn) {
  // 乐观更新本地
  queryClient.setQueryData(['board'], old => moveInBoard(old, cardId, toColumn));

  // 同步服务端，并触发事件广播
  fetch(`/api/cards/${cardId}`, {
    method: 'PATCH',
    body: JSON.stringify({ column: toColumn }),
  });
}

// 其他端收到广播事件后失效缓存，触发重取
socket.on('board-changed', ({ cardId }) => {
  queryClient.invalidateQueries(['board']);
});
```

### 场景二：表单草稿离线保存

```js
// 输入即存草稿（离线优先），网络恢复后上传
const input = document.querySelector('#note');

input.addEventListener('input', () => {
  const draft = { text: input.value, updatedAt: Date.now() };
  db.put('drafts', { id: 'note', ...draft }); // 本地持久化
});

async function uploadDraft() {
  const draft = await db.get('drafts', 'note');
  if (!draft) return;
  await fetch('/api/notes', { method: 'POST', body: JSON.stringify(draft) });
  await db.delete('drafts', 'note');
}

window.addEventListener('online', uploadDraft);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 数据不常变、实时性要求低用轮询；需要即时性用 WebSocket/SSE 或事件驱动
2. 高频轻量操作（点赞、排序、已读）用乐观更新，交互即反馈
3. 乐观更新必须配套回滚逻辑，失败时恢复原状
4. 涉及多人编辑的数据用版本号或 CRDT 做冲突解决，别裸用后写覆盖
5. 离线场景把读写都落到本地，网络恢复走同步队列
6. 事件驱动同步配合缓存失效（invalidateQueries），别手动改 store

### 踩坑记录

```text
坑 1：轮询叠加导致请求雪崩
结论：组件反复挂载，定时器没清理，请求数成倍增长。
原因：setInterval 在组件卸载后没 clearInterval，新挂载又开新定时器。
解法：返回清理函数，组件卸载时 clearInterval；轮询统一放一处管理。

坑 2：乐观更新失败不回滚
结论：点赞显示成功，刷新后点赞数又回去了。
原因：后台请求失败但没有回滚逻辑，本地和服务端不一致。
解法：catch 里恢复修改前的状态，必要时提示「操作失败」。

坑 3：后写覆盖丢更新
结论：两人同时编辑同一份文档，后保存的把先保存的覆盖了。
原因：冲突解决用了最简单的 Last Write Wins，没有版本比较。
解法：用版本号/时间戳做乐观并发控制，冲突时提示合并。

坑 4：离线期间本地数据与草稿混淆
结论：离线编辑的内容在恢复网络后没同步，刷新页面就丢了。
原因：离线写操作只改了内存，没落到 IndexedDB 持久层。
解法：离线操作先写本地持久存储，标记 pending，恢复后批量同步。

坑 5：事件驱动同步漏事件
结论：订阅组件偶尔收不到某次更新，数据停在了旧状态。
原因：事件在订阅建立前发出，或断线期间的事件没有重放。
解法：订阅建立后先拉一次全量数据，事件带上序号便于断线补拉。
```
