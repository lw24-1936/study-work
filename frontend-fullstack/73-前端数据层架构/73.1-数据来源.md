## 概述

前端的数据来源可以分成两类：一类是从服务端「拉取」或「推送」的远程数据，另一类是存在浏览器本地的持久数据。选择哪种来源取决于数据的实时性、体量和读写频率——读多写少的配置用请求即可，需要服务端主动推送的用长连接，需要离线可用的存本地。

```text
前端数据来源全景：
1. REST —— 基于 HTTP 的请求-响应接口，最通用
2. GraphQL —— 声明式查询，按需取字段，单请求聚合多资源
3. WebSocket —— 全双工长连接，服务端主动推送
4. SSE —— 单向服务端推送，基于 HTTP，自动重连
5. IndexedDB —— 浏览器内结构化大容量存储，异步 API
6. Local Storage —— 同步的小容量键值存储，适合简单配置
```

```js
// 数据来源选择的一个简单决策示例
function pickSource(need) {
  if (need.realtime && need.bidirectional) return 'WebSocket';
  if (need.realtime && need.serverPushOnly) return 'SSE';
  if (need.flexibleQuery) return 'GraphQL';
  if (need.offline && need.largeData) return 'IndexedDB';
  if (need.offline && need.smallConfig) return 'Local Storage';
  return 'REST';
}
```

## REST

REST（Representational State Transfer）把服务端资源映射成 URL，用 HTTP 方法表达操作语义：GET 读取、POST 创建、PUT/PATCH 更新、DELETE 删除。它无状态、可缓存、约定简单，是前端最常打交道的接口形式。

```text
REST 的关键点：
1. 资源用名词 URL 表达 —— /users/1 表示 id 为 1 的用户
2. 方法表达动作 —— GET/POST/PUT/PATCH/DELETE
3. 状态码表达结果 —— 200 成功、201 已创建、404 不存在、422 校验失败
4. 无状态 —— 每次请求自包含，服务端不依赖会话内存
```

```js
// REST 接口调用
const list = await fetch('/api/users?page=1&size=20').then(r => r.json());

// 创建资源
const created = await fetch('/api/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Alice', age: 25 }),
}).then(r => r.json());
```

REST 的短板是「过取」和「欠取」：一个列表接口返回的字段可能远超页面所需，而一个详情页又可能需要拼多次请求才能凑齐数据。

## GraphQL

GraphQL 用一套类型系统（Schema）描述可查询的数据，客户端用查询语言按需声明要哪些字段，服务端一次返回精确结果。它解决了 REST 的过取/欠取问题，也把「多个请求聚合」压成一次往返。

```text
GraphQL 的关键点：
1. 声明式查询 —— 客户端写 query 指定字段，不多不少
2. 单一端点 —— 所有操作走 /graphql 一个入口
3. 类型系统 —— Schema 定义 Query/Mutation/Subscription 三类操作
4. Subscription —— 基于长连接的实时订阅能力
```

```graphql
# 一次请求同时拿用户信息和其订单，字段精确到列
query {
  user(id: 1) {
    name
    orders { id total status }
  }
}
```

```js
// 前端调用 GraphQL
const res = await fetch('/graphql', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    query: `query { user(id: 1) { name orders { total } } }`,
  }),
});
const { data } = await res.json();
```

GraphQL 的代价是服务端要实现解析器、复杂度控制和缓存策略，N+1 查询和「大查询打挂服务」需要单独防护。

## WebSocket

WebSocket 在单个 TCP 连接上提供全双工通信，客户端和服务端可以随时互发消息，没有 HTTP 的请求-响应强绑定。它适合聊天、协作、行情推送这类双向实时场景。

```text
WebSocket 的关键点：
1. 全双工 —— 双向随时发消息，不需要轮询
2. 握手升级 —— 用 HTTP Upgrade 从 101 切换协议
3. 帧 —— 数据以帧传输，支持文本和二进制
4. 心跳 —— 应用层需要 ping/pong 探测存活
```

```js
// 客户端建立 WebSocket 连接
const ws = new WebSocket('wss://example.com/chat');

ws.onopen = () => ws.send(JSON.stringify({ type: 'join', room: 'frontend' }));
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  console.log('收到消息:', msg);
};
ws.onclose = () => console.log('连接已关闭，准备重连');
```

WebSocket 需要服务端维护连接状态，代理和负载均衡也要支持升级；断线重连、心跳保活、消息重放都要在应用层处理。

## SSE

SSE（Server-Sent Events）让服务端通过普通 HTTP 连接持续向客户端单向推送文本事件。它比 WebSocket 轻：走标准 HTTP、自动重连、带事件类型和消息 id，但只能服务端→客户端单向。

```text
SSE 的关键点：
1. 单向 —— 只能服务端推给客户端
2. 自动重连 —— 浏览器原生支持断线重连
3. 事件类型 —— 用 event 字段区分不同事件流
4. 基于 HTTP —— 兼容性好，可通过代理和缓存
```

```js
// 客户端订阅 SSE
const source = new EventSource('/api/events');

source.addEventListener('message', (e) => {
  console.log('默认事件:', e.data);
});
source.addEventListener('price', (e) => {
  console.log('价格事件:', e.data);
});
```

```text
# 服务端响应格式（Content-Type: text/event-stream）
data: {"price": 3.14}

event: price
data: {"price": 3.20}
id: 42

```

SSE 适合股票行情、进度通知、日志流这类只需服务端推、客户端不回的实时场景。

## IndexedDB

IndexedDB 是浏览器内置的 NoSQL 数据库，支持结构化数据、索引和事务，容量可达几百 MB，所有操作都是异步的。它适合离线存储大块数据（文档、图片、业务数据缓存）。

```text
IndexedDB 的关键点：
1. 异步 API —— 所有操作返回 request，通过回调或 Promise 取结果
2. 事务 —— 读写必须在事务内完成
3. 索引 —— 可建索引加速查询
4. 对象仓库 —— 类似表，存放结构化对象
```

```js
// 打开数据库并写入一条记录
const openReq = indexedDB.open('my-db', 1);
openReq.onupgradeneeded = (e) => {
  const db = e.target.result;
  if (!db.objectStoreNames.contains('notes')) {
    db.createObjectStore('notes', { keyPath: 'id' });
  }
};

openReq.onsuccess = (e) => {
  const db = e.target.result;
  const tx = db.transaction('notes', 'readwrite');
  tx.objectStore('notes').put({ id: 1, title: '购物清单', body: '牛奶、鸡蛋' });
  tx.oncomplete = () => console.log('写入完成');
};
```

IndexedDB 的原生 API 比较啰嗦，通常用封装库（如 idb、Dexie）简化调用。

## Local Storage

Local Storage 是同步的键值存储，只能存字符串，容量约 5MB，读写立即生效。它适合保存用户偏好、主题、token 这类小量、无需事务的数据。

```text
Local Storage 的关键点：
1. 同步 —— 读写阻塞主线程，不适合大数据量
2. 只存字符串 —— 对象需 JSON 序列化
3. 同源共享 —— 同源下所有标签页共享
4. 无过期 —— 数据永久保留，除非手动清除
```

```js
// 读写 Local Storage
localStorage.setItem('theme', 'dark');
localStorage.setItem('prefs', JSON.stringify({ fontSize: 14, lang: 'zh' }));

const theme = localStorage.getItem('theme');
const prefs = JSON.parse(localStorage.getItem('prefs') || '{}');
localStorage.removeItem('theme');
```

Local Storage 不适合存敏感信息（XSS 可直接读取），也不适合高频写入（同步阻塞）。会话级临时数据用 Session Storage，结构化大容量数据用 IndexedDB。

## 应用场景实战

### 场景一：带缓存的用户列表页

```js
// 优先读本地缓存，再请求 REST 更新
const CACHE_KEY = 'users-cache';

async function loadUsers({ force = false } = {}) {
  if (!force) {
    const cached = localStorage.getItem(CACHE_KEY);
    if (cached) return JSON.parse(cached);
  }
  const users = await fetch('/api/users').then(r => r.json());
  localStorage.setItem(CACHE_KEY, JSON.stringify(users));
  return users;
}

const users = await loadUsers();
console.log('用户数:', users.length);
```

### 场景二：离线笔记（IndexedDB + 同步标记）

```js
// 无网络时写入本地库，标记待同步，恢复网络后批量上传
async function saveNote(note) {
  const db = await openDB('notes-db');
  await db.put('notes', { ...note, sync: navigator.onLine ? 'synced' : 'pending' });
  if (navigator.onLine) await upload(note);
}

async function flushPending() {
  const db = await openDB('notes-db');
  const pending = await db.getAll('notes', 'pending');
  for (const note of pending) {
    await upload(note);
    await db.put('notes', { ...note, sync: 'synced' });
  }
}

window.addEventListener('online', flushPending);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 读多写少、字段固定的接口用 REST，字段灵活多变的用 GraphQL
2. 双向实时用 WebSocket，单向推送用 SSE，别用轮询硬凑实时
3. 大容量、需要查询的结构化数据放 IndexedDB，小配置放 Local Storage
4. Local Storage 里的对象统一 JSON 序列化，读的时候做容错
5. 敏感数据（token、个人信息）不要放进 Local Storage，XSS 能直接读
6. WebSocket 和 SSE 都要处理断线重连与心跳，别假设连接永远在线

### 踩坑记录

```text
坑 1：Local Storage 存 token 被 XSS 窃取
结论：登录态被第三方脚本直接读取并外传。
原因：Local Storage 可被同源任意 JS 读取，XSS 攻击下毫无防护。
解法：token 优先存 HttpOnly Cookie，必须存前端时配合严格的 CSP 与输入过滤。

坑 2：IndexedDB 写入丢失
结论：写入后立刻刷新页面，数据没存进去。
原因：读写操作必须包在事务里，且要在事务 oncomplete 后才算真正落库。
解法：等待事务完成回调再继续，别在 request.onsuccess 就以为数据已持久化。

坑 3：SSE 连接被代理缓冲
结论：事件迟迟收不到，攒成一批才一次性到达。
原因：中间代理或网关缓冲了流式响应，破坏了实时性。
解法：响应头设 Cache-Control: no-cache、X-Accel-Buffering: no，关闭缓冲。

坑 4：WebSocket 断线后消息丢失
结论：网络抖动后，断线期间的消息收不到。
原因：WebSocket 断开后不缓存消息，客户端没有重连和补拉机制。
解法：断线重连后按最后收到的消息 id 补拉缺失消息，或用消息队列兜底。

坑 5：GraphQL 大查询拖垮服务
结论：某个深度嵌套查询让服务端 CPU 和内存飙升。
原因：客户端可自由组合字段，缺少深度和复杂度限制。
解法：服务端限制查询深度、节点数和复杂度，超限直接拒绝。
```
