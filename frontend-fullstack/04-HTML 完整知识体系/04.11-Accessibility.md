## 概述

Accessibility（可访问性，a11y）让网站对所有人可用——包括依赖屏幕阅读器的视障用户、无法用鼠标的行动障碍用户、以及对动画敏感的用户。可访问性不是「额外功能」，而是「基本要求」，也是很多地区（欧美）的法律合规要求。这篇笔记覆盖可访问性的完整技术：WCAG 标准、ARIA、键盘导航、焦点管理。

```text
可访问性关注的三类能力：
1. 视觉 —— 屏幕阅读器、对比度、缩放
2. 操作 —— 键盘导航、焦点管理
3. 感知 —— 字幕、动画控制
```

## WCAG 标准

WCAG（Web Content Accessibility Guidelines）是可访问性的国际标准，由 W3C 制定。

```text
WCAG 的四个原则（POUR）：
Perceivable（可感知）—— 信息能被用户感知（文字、图片 alt、字幕）
Operable（可操作）—— 界面能被操作（键盘可达、时间充足）
Understandable（可理解）—— 内容可理解（清晰、一致）
Robust（健壮）—— 兼容辅助技术（语义化、规范）
```

```text
WCAG 的合规等级：
A  —— 最低要求（必须满足）
AA —— 中等要求（大多数组织的目标，法律常要求）
AAA —— 最高要求（难以全部满足）

实践目标：达到 AA 级。
```

```text
WCAG 2.1 的关键要求（前端高频）：
1. 图片有文字替代（1.1.1）
2. 颜色对比度 4.5:1（1.4.3，AA 级）
3. 键盘可操作（2.1.1）
4. 焦点可见（2.4.7）
5. 动画可暂停（2.2.2）
```

## ARIA 与 role

ARIA（Accessible Rich Internet Applications）是一组补充语义的属性，当原生 HTML 无法表达语义时使用。

```text
ARIA 的核心规则：
「能用原生 HTML 就不用 ARIA」—— 原生标签自带语义和键盘行为，
ARIA 是「补丁」，只在不满足时使用。
```

### role

role 声明元素的角色（语义）：

```html
<!-- 自定义标签页（div 没有语义，用 role 补充） -->
<div role="tablist">
  <button role="tab" aria-selected="true">标签 1</button>
  <button role="tab" aria-selected="false">标签 2</button>
</div>
<div role="tabpanel">内容 1</div>
```

```text
常见 role：
tablist / tab / tabpanel —— 标签页
dialog —— 对话框
alert —— 警告（立即播报）
navigation / banner / main —— 地标角色（对应 nav/header/main）
button / link —— 交互角色
```

```text
role 的使用原则：
1. 原生元素有默认 role（button 的 role 就是 button），不用重复写
2. 只有 div 等无语义元素模拟交互组件时，才需要 role
3. 错误的 role 比不写 role 更糟（误导辅助技术）
```

## aria 属性详解

ARIA 属性补充「状态」和「关系」信息。

### aria-label（标签）

给元素一个「可读的名称」，覆盖元素本身的文本：

```html
<!-- 图标按钮：图标无法被读，用 aria-label 补充 -->
<button aria-label="关闭对话框">
  <svg><!-- X 图标 --></svg>
</button>
```

### aria-labelledby（关联标签）

引用其他元素的文本作为本元素的标签（比 aria-label 优先）：

```html
<h2 id="dialog-title">确认删除</h2>
<div role="dialog" aria-labelledby="dialog-title">
  <p>确定要删除这条记录吗？</p>
</div>
```

### aria-describedby（关联描述）

引用描述性文本（补充说明，非标签）：

```html
<label for="password">密码</label>
<input type="password" id="password" aria-describedby="password-help">
<p id="password-help">密码至少 8 位，含字母和数字。</p>
```

### aria-hidden（隐藏）

对辅助技术隐藏元素（视觉上还在）：

```html
<!-- 装饰性图标对屏幕阅读器隐藏 -->
<span aria-hidden="true">🎨</span>
```

```text
aria-hidden 的要点：
1. aria-hidden="true" —— 辅助技术「忽略」这个元素
2. 用于装饰性内容（视觉有用，读出来是噪音）
3. 不要在可聚焦的元素上加 aria-hidden（会导致焦点进入「消失」的元素）
```

### aria-expanded（展开状态）

声明「可展开元素」的展开/收起状态：

```html
<button aria-expanded="false" aria-controls="menu-1">菜单</button>
<div id="menu-1" hidden>菜单内容</div>
```

### aria-selected（选中状态）

声明「可选项」的选中状态（标签页、列表选中项）：

```html
<div role="tablist">
  <button role="tab" aria-selected="true">已选中</button>
</div>
```

### aria-live（动态播报）

声明「动态更新区域」，内容变化时屏幕阅读器自动播报：

```html
<!-- 通知区域：内容变化时播报 -->
<div aria-live="polite">加载完成，共 10 条结果</div>
```

```text
aria-live 的取值：
polite —— 温和播报（等当前朗读结束）
assertive —— 立即播报（打断当前朗读）

用于：表单提交结果、加载状态、动态通知。
```

## keyboard navigation 键盘导航

键盘导航是可访问性的核心——不能只依赖鼠标。

```text
键盘导航的基础：
Tab / Shift+Tab —— 在可聚焦元素间移动
Enter / Space —— 激活按钮
方向键 —— 在列表/菜单/标签页间移动
Esc —— 关闭对话框/菜单
```

```text
可聚焦元素：
默认可聚焦：a[href]、button、input、select、textarea
div/span 默认不可聚焦，要模拟交互需加 tabindex="0"
```

```text
tabindex 的取值：
tabindex="0"  —— 可聚焦，按 DOM 顺序进入 Tab 序列
tabindex="-1" —— 可编程聚焦，但不进入 Tab 序列（对话框焦点管理用）
tabindex=">0" —— 手动指定顺序（反模式，避免使用）
```

```text
键盘导航的关键要求：
1. 所有交互元素都能用键盘操作
2. 焦点可见（focus 样式，不能去掉）
3. 焦点顺序符合逻辑（视觉顺序 = DOM 顺序）
```

## focus management 焦点管理

焦点管理是「复杂交互组件」（对话框、路由切换）的可访问性关键。

```text
焦点管理的典型场景：
1. 打开对话框 —— 焦点移到对话框内，关闭后移回触发按钮
2. 路由切换 —— 焦点移到新页面顶部
3. 删除列表项 —— 焦点移到下一项
```

```js
// 对话框的焦点管理
function openDialog() {
  dialog.showModal();
  dialog.querySelector('input').focus();  // 焦点进入对话框
}

function closeDialog() {
  dialog.close();
  triggerButton.focus();  // 焦点回到触发按钮
}
```

```text
焦点陷阱（focus trap）：
对话框打开时，Tab 键应在对话框内循环，不跑到背景页面。
原生 <dialog> 的 showModal() 自动处理焦点陷阱，
自定义对话框需要手动实现。
```

## screen reader 与 semantic HTML

屏幕阅读器是视障用户「读」网页的工具，它的信息来源是「语义」而非「视觉」。

```text
屏幕阅读器如何工作：
1. 读取 DOM 的语义结构（不是视觉样式）
2. 用 accessibility tree（可访问性树）导航
3. 语义化 HTML 直接映射成正确的可访问性树
```

```text
semantic HTML 对屏幕阅读器的意义：
语义化标签 → 正确的可访问性树 → 屏幕阅读器正确朗读。

例：
<button>提交</button> → 读作「按钮，提交」
<div onclick="submit()">提交</div> → 读作「提交」（不是按钮，无法键盘操作）
```

```text
屏幕阅读器的地标导航：
<header>/<nav>/<main>/<footer> 等地标标签，
让屏幕阅读器能「跳到导航」「跳到主内容」快速定位。
```

## color contrast 与 reduced motion

### color contrast 颜色对比度

文字与背景的对比度要足够，弱视用户才能看清。

```text
WCAG AA 级的对比度要求：
普通文字 —— 4.5:1
大文字（18px+ 或 14px 加粗）—— 3:1
```

```text
对比度检查：
用工具（如 WebAIM Contrast Checker）检测，
确保正文、按钮文字、链接都达标。
```

### reduced motion 减少动画

部分用户对动画敏感（前庭障碍），需要提供「减少动画」选项。

```css
/* 尊重系统的「减少动态效果」设置 */
@media (prefers-reduced-motion: reduce) {
  * {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

```text
prefers-reduced-motion：
用户在系统设置里开启「减少动态效果」后，
prefers-reduced-motion: reduce 生效，网站应减少/关闭动画。
```

## 应用场景实战

### 场景一：可访问的模态对话框

```html
<button id="open-dialog">打开对话框</button>

<dialog id="my-dialog" aria-labelledby="dialog-title">
  <h2 id="dialog-title">确认操作</h2>
  <p>确定要执行这个操作吗？</p>
  <button id="confirm">确定</button>
  <button id="cancel">取消</button>
</dialog>

<script>
  const dialog = document.getElementById('my-dialog');
  const openBtn = document.getElementById('open-dialog');

  openBtn.addEventListener('click', () => dialog.showModal());
  // 原生 showModal() 自动处理焦点陷阱和焦点恢复

  document.getElementById('cancel').addEventListener('click', () => dialog.close());
</script>
```

### 场景二：可访问的标签页组件

```html
<div role="tablist" aria-label="内容标签">
  <button role="tab" id="tab-1" aria-selected="true" aria-controls="panel-1">介绍</button>
  <button role="tab" id="tab-2" aria-selected="false" aria-controls="panel-2">详情</button>
</div>
<div role="tabpanel" id="panel-1" aria-labelledby="tab-1">介绍内容</div>
<div role="tabpanel" id="panel-2" aria-labelledby="tab-2" hidden>详情内容</div>
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优先语义化 HTML，能用原生标签不用 ARIA
2. 图标按钮加 aria-label，动态区域加 aria-live
3. 所有交互支持键盘操作（Tab 可达、Enter/Space 激活）
4. 对话框用原生 dialog + showModal（自动焦点管理）
5. 文字对比度达 WCAG AA（4.5:1）
6. 尊重 prefers-reduced-motion，提供减少动画选项

### 踩坑记录

```text
坑 1：滥用 ARIA（div 加 role="button"）
结论：role="button" 的 div 没有键盘行为，Tab 聚焦不到、Enter 无效。
原因：role 只补语义，不补行为。
解法：直接用原生 button，实在要用 div 就补 tabindex + 键盘事件。

坑 2：aria-hidden 加在可聚焦元素上
结论：焦点进入「隐藏」元素，屏幕阅读器读不到，焦点迷失。
原因：aria-hidden 和 focusable 冲突。
解法：aria-hidden 的元素不能包含可聚焦子元素。

坑 3：去掉焦点样式（outline: none）
结论：键盘用户看不到当前焦点在哪。
原因：为了美观去掉 outline，破坏了焦点可见性。
解法：保留 focus 样式，或用 :focus-visible 定制可见的焦点样式。

坑 4：动态内容不配 aria-live
结论：提交结果、加载状态更新了，屏幕阅读器用户不知道。
原因：动态更新没有播报。
解法：动态通知区域加 aria-live="polite"。

坑 5：颜色作为唯一的区分手段
结论：用红色表示错误，色盲用户无法区分。
原因：只靠颜色传递信息，没其他提示。
解法：颜色 + 图标/文字/下划线等多重提示。
```
