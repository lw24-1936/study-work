## 概述

Nginx 的缓存优化分两个层面：一是「告诉浏览器怎么缓存」（Cache-Control、expires），让用户少发请求；二是「Nginx 自己缓存后端响应」（proxy_cache），减少对后端的压力。再加上 gzip、brotli 压缩，把传输体积降下来，三者叠加能显著提升前端加载速度。

```text
Nginx 缓存与压缩的四个维度：
1. Cache-Control —— 精细控制浏览器缓存行为（强缓存/协商缓存）
2. expires —— 简化版的缓存过期时间设置
3. proxy_cache —— Nginx 作为代理时缓存后端响应
4. gzip / brotli —— 压缩文本资源，减小传输体积
```

```text
前端缓存策略的总原则：
1. 带 hash 的静态资源 —— 长缓存（immutable）
2. 入口 index.html —— 短缓存或 no-cache
3. 动态接口 —— 一般不缓存或谨慎缓存
```

## Cache-Control

Cache-Control 是 HTTP 响应头，精确控制浏览器和中间节点的缓存行为。它比 expires 更强大：能声明是否可缓存、缓存多久、是否允许共享缓存、以及强缓存/协商缓存的策略。前端静态资源最常用的组合是长缓存 immutable 和 no-cache。

```nginx
server {
    root /var/www/html;

    # 带 hash 的资源：一年强缓存 + immutable
    location ~* \.(css|js|png|jpg|svg|woff2)$ {
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    # 入口文件：不缓存，每次重新验证
    location = /index.html {
        add_header Cache-Control "no-cache";
    }
}
```

```text
Cache-Control 常用指令：
1. public —— 允许浏览器和 CDN 等共享缓存
2. private —— 只允许浏览器缓存
3. max-age=N —— 缓存 N 秒，强缓存
4. no-cache —— 可缓存但每次需重新验证（协商缓存）
5. no-store —— 完全不缓存
6. immutable —— 资源不会变，缓存期间不重新验证
```

```text
强缓存 vs 协商缓存：
1. 强缓存 —— max-age 内直接用缓存，不发请求
2. 协商缓存 —— no-cache 配合 ETag/Last-Modified，发请求但 304 免传输
3. 组合 —— 静态资源用强缓存，HTML 用协商缓存
```

## expires

expires 是简化版的缓存过期控制，直接设置一个过期时间或时长，Nginx 会生成对应的 Expires 和 Cache-Control: max-age 响应头。它语法简单，适合快速给静态资源设置缓存时长，但表达力不如 Cache-Control 精细。

```nginx
server {
    root /var/www/html;

    # 静态资源缓存 30 天
    location ~* \.(css|js|png|jpg)$ {
        expires 30d;
    }

    # 永不缓存
    location = /index.html {
        expires -1;
        add_header Cache-Control "no-cache";
    }
}
```

```text
expires 的时间单位：
1. s / m / h / d —— 秒 / 分 / 时 / 天
2. expires max —— 设为 10 年，近似永久
3. expires -1 —— 立即过期，不缓存
4. expires epoch —— 设为 1970 年，强制过期
```

```text
expires 与 Cache-Control 的关系：
1. expires 是旧标准，Cache-Control 是新标准
2. 同时存在时 Cache-Control 优先级更高
3. Nginx 设置 expires 会自动生成对应的 max-age
```

## proxy_cache

proxy_cache 让 Nginx 作为反向代理时缓存后端的响应，下次相同请求直接返回缓存，不再访问后端。它对「响应慢但内容相对稳定」的接口收益最大，能大幅降低后端压力和响应时间。

```nginx
# 定义缓存路径和参数
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m max_size=1g inactive=60m;

server {
    location /api/ {
        proxy_pass http://backend:3000;
        proxy_cache my_cache;
        proxy_cache_valid 200 10m;    # 200 响应缓存 10 分钟
        proxy_cache_valid 404 1m;     # 404 缓存 1 分钟
        proxy_cache_key "$scheme$request_method$host$request_uri";
        add_header X-Cache-Status $upstream_cache_status;
    }
}
```

```text
proxy_cache 的关键配置：
1. proxy_cache_path —— 缓存存储路径、内存区、大小上限
2. proxy_cache_valid —— 按状态码设置缓存时长
3. proxy_cache_key —— 缓存的键，默认包含 URI 和参数
4. $upstream_cache_status —— 命中/未命中状态，用于调试
```

```text
proxy_cache 的适用场景：
1. 内容相对稳定的 GET 接口
2. 响应耗时长的查询接口
3. 读多写少的数据
4. 不适用 —— 用户相关的个性化数据、需要实时性的接口
```

## gzip

gzip 是 Nginx 内置的文本压缩功能，把 HTML/CSS/JS/JSON 等文本资源压缩后传输，体积通常能减小 60%-80%，显著加快加载速度。它针对文本类资源，对已经压缩过的图片、视频无效。

```nginx
server {
    # 开启 gzip
    gzip on;
    # 只压缩大于 1KB 的响应
    gzip_min_length 1k;
    # 压缩级别 1-9，5 是性能和体积的平衡点
    gzip_comp_level 5;
    # 需要压缩的内容类型
    gzip_types text/plain text/css application/json application/javascript image/svg+xml;
    # 响应头加 Vary，兼容代理缓存
    gzip_vary on;
}
```

```text
gzip 的配置要点：
1. gzip on —— 总开关
2. gzip_types —— 指定压缩的 MIME 类型，必须配否则只压 text/html
3. gzip_comp_level —— 压缩级别，越高越慢但体积越小
4. gzip_min_length —— 小于该长度不压缩，小文件压缩反而浪费
5. gzip_vary —— 加 Vary: Accept-Encoding，避免缓存错乱
```

## brotli

brotli 是比 gzip 更新、压缩率更高的算法，同样体积下通常能比 gzip 再小 15%-25%，特别适合压缩 JS 和 CSS。Nginx 官方版本默认不带 brotli 模块，需要用 ngx_brotli 模块编译的版本（或官方新版 Nginx 已内置）。

```nginx
server {
    # 开启 brotli
    brotli on;
    brotli_comp_level 6;
    brotli_min_length 1k;
    brotli_types text/plain text/css application/json application/javascript image/svg+xml;
}
```

```text
brotli 与 gzip 的对比：
1. 压缩率 —— brotli 更高，尤其对 JS/CSS 优势明显
2. 性能 —— brotli 压缩更耗 CPU，但解压速度相当
3. 兼容性 —— brotli 需 HTTPS（规避代理干扰），gzip 无此限制
4. 部署 —— brotli 需要额外模块或新版 Nginx
```

```text
brotli 的使用建议：
1. 动态压缩耗 CPU，静态资源可预压缩成 .br 文件
2. 配合 gzip 双开，按 Accept-Encoding 自动协商
3. 高压缩级别（9-11）适合静态预压缩，在线压缩用中低级别
```

## 应用场景实战

### 场景一：前端静态资源的完整缓存 + 压缩配置

```nginx
# 一个生产级的前端缓存配置
server {
    listen 80;
    server_name app.example.com;
    root /var/www/html;

    # 压缩
    gzip on;
    gzip_min_length 1k;
    gzip_comp_level 5;
    gzip_types text/plain text/css application/json application/javascript image/svg+xml;
    gzip_vary on;

    # 带 hash 的资源长缓存
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 入口文件短缓存
    location = /index.html {
        expires -1;
        add_header Cache-Control "no-cache";
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

### 场景二：反向代理接口缓存

```nginx
# 缓存慢接口的响应，减轻后端压力
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=api_cache:10m max_size=1g inactive=60m;

server {
    listen 80;

    location /api/catalog/ {
        proxy_pass http://backend:3000;
        proxy_cache api_cache;
        proxy_cache_valid 200 10m;
        proxy_cache_key "$scheme$request_method$host$request_uri";
        add_header X-Cache-Status $upstream_cache_status;
    }

    # 用户相关接口不缓存
    location /api/user/ {
        proxy_pass http://backend:3000;
        proxy_no_cache 1;
    }
}
```

## 三层缓存与进阶

### 缓存分层：浏览器 → CDN → Nginx → 后端

```text
三层缓存的分工：
1. 浏览器缓存 —— Cache-Control/ETag，命中不发请求，离用户最近
2. CDN 缓存 —— 边缘节点缓存，命中不回源，扛住大流量
3. Nginx proxy_cache —— 源站前缓存后端响应，降后端压力
4. 职责边界 —— 浏览器缓存管「用户不再请求」，CDN/Nginx 管「后端不再被打」
```

```text
选型要点：
1. 带 hash 静态资源 —— 三者全开：浏览器 immutable + CDN 长缓存 + 回源 ETag
2. index.html —— 浏览器 no-cache，CDN 也不缓存（或秒级缓存），保证发布即时
3. 动态接口 —— 只缓存稳定只读数据，带用户身份的一律不缓存
4. Nginx proxy_cache vs CDN —— 单机用 proxy_cache，多地域用 CDN，二者可叠加
```

### ETag 与协商缓存

```text
Nginx 默认对静态文件生成 ETag（基于 mtime + 文件大小）和 Last-Modified：
1. 强缓存命中 —— 不发请求，最快
2. 协商缓存 —— no-cache 时带 If-None-Match/If-Modified-Since，命中返回 304 免传输
3. 坑 —— ETag 基于 mtime，多节点部署且 mtime 不一致会导致缓存反复失效
4. 建议 —— 构建产物统一时间戳，或关闭 etag 只靠 hash + 长缓存
```

### 预压缩静态文件

```nginx
# 构建时预生成 .br/.gz，运行时直接返回，省去在线压缩 CPU
server {
    # 存在 .gz 文件时直接返回预压缩结果
    gzip_static on;
    # 存在 .br 文件时优先返回 brotli
    brotli_static on;
}
```

```text
预压缩 vs 在线压缩：
1. 在线压缩 —— gzip on 每次请求都压，CPU 开销大，适合小流量
2. 预压缩 —— 构建时压好，运行时零开销，适合大流量静态资源
3. 前提 —— 需要 gzip_static / brotli_static 模块（brotli 需额外编译）
4. 配合 —— 预压缩文件 + Cache-Control 长缓存，命中率最高
```

### proxy_cache 的绕过

```nginx
location /api/catalog/ {
    proxy_pass http://backend:3000;
    proxy_cache api_cache;
    proxy_cache_valid 200 10m;
    # 带 nocache 参数时绕过缓存直连后端
    proxy_cache_bypass $http_cache_control_no_cache;
    proxy_no_cache $http_cache_control_no_cache;
}
```

```text
缓存绕过要点：
1. proxy_cache_bypass —— 绕过读取，仍会写缓存
2. proxy_no_cache —— 不写缓存，用于排除个性化响应
3. 主动清除 —— 需第三方模块 ngx_cache_purge，或删缓存目录文件
4. 版本化 —— 更简单的做法：接口 URL 带版本号，天然绕开旧缓存
```

## 最佳实践与踩坑记录

### 最佳实践

1. 带 hash 的静态资源用 immutable 长缓存，入口 HTML 用 no-cache
2. gzip 和 brotli 都开启，按浏览器 Accept-Encoding 自动协商
3. gzip_types 必须显式列出要压缩的 MIME 类型，否则只压 HTML
4. proxy_cache 只缓存稳定的 GET 接口，用户相关数据一律不缓存
5. 静态资源构建时预压缩出 .br/.gz 文件，避免运行时压缩耗 CPU
6. 加 X-Cache-Status 响应头，方便调试缓存命中情况

### 踩坑记录

```text
坑 1：index.html 被长缓存导致发布后用户看不到新版本
结论：发布了新版本但用户浏览器一直加载旧页面。
原因：index.html 也被设了长缓存，浏览器不重新请求。
解法：入口 HTML 设 no-cache 或短 max-age，hash 资源才用长缓存。

坑 2：gzip 开了但 JS/CSS 没被压缩
结论：响应体积没变小，压缩形同虚设。
原因：没有配置 gzip_types，默认只压缩 text/html。
解法：显式列出 text/css、application/javascript 等类型。

坑 3：图片和视频被 gzip 处理反而更慢
结论：对已压缩的二进制资源做 gzip，CPU 白耗且体积几乎不变。
原因：gzip_types 匹配了图片/视频的 MIME 类型。
解法：gzip_types 只列文本类资源，图片视频走 CDN 和缓存。

坑 4：proxy_cache 缓存了用户个性化接口
结论：A 用户的数据被缓存后返回给了 B 用户，严重数据泄漏。
原因：没有区分接口性质，把带用户身份的响应也缓存了。
解法：用户相关接口用 proxy_no_cache 1 或 Cache-Control: private 排除缓存。

坑 5：brotli 依赖模块缺失导致配置不生效
结论：配了 brotli 但启动报错 unknown directive "brotli"。
原因：官方标准 Nginx 默认不带 brotli 模块。
解法：用带 ngx_brotli 模块的版本或新版官方镜像，确认模块已加载。

坑 6：ETag 基于 mtime 多节点缓存抖动
结论：同一资源在不同节点反复 200/304 抖动，缓存命中率低。
原因：多台机器文件 mtime 不一致，ETag 各不相同。
解法：构建产物统一时间戳，或对 hash 资源关闭 etag 只依赖长缓存。

坑 7：proxy_cache_key 不含变化头导致串味
结论：不同 Accept-Language/UA 的响应互相串，A 用户看到 B 的版本。
原因：默认 cache key 不含这些请求头，响应被当成同一份缓存。
解法：把影响响应的头拼进 proxy_cache_key，或对变化响应 proxy_no_cache 1。
```
