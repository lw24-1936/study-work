## 概述

反向代理（Reverse Proxy）指 Nginx 站在服务器一侧，接收客户端请求后转发给后端的应用服务器，再把响应返回给客户端。前端项目里它最常见的用途是「解决跨域」：把 /api 请求代理到后端服务，浏览器只跟 Nginx 同源通信，跨域问题在服务端消解。

```text
反向代理的核心价值：
1. 跨域解决 —— 前端同源访问，后端由 Nginx 转发
2. 负载均衡 —— 把流量分摊到多个后端实例
3. 安全隔离 —— 隐藏后端真实地址，统一入口
4. 统一入口 —— 静态资源和 API 共用同一域名
```

```nginx
# 最小反向代理：把 /api 转发到后端
server {
    listen 80;
    location /api/ {
        proxy_pass http://backend:3000;
    }
}
```

## proxy_pass

proxy_pass 是反向代理的核心指令，指定把请求转发到哪个后端地址。它会重写请求的 URI 规则，是否携带 location 前缀取决于 proxy_pass 末尾是否带路径。理解这个拼接规则是配置反向代理最容易出错的地方。

```nginx
server {
    # 不带路径：完整保留原始 URI
    location /api/ {
        proxy_pass http://backend:3000;
        # 请求 /api/users -> 转发到 http://backend:3000/api/users
    }

    # 带路径：替换匹配到的前缀
    location /api/ {
        proxy_pass http://backend:3000/;
        # 请求 /api/users -> 转发到 http://backend:3000/users
    }
}
```

```text
proxy_pass 的 URI 拼接规则：
1. 不带路径 —— proxy_pass http://host:port，原始 URI 原样转发
2. 带 / 结尾 —— proxy_pass http://host:port/，替换 location 前缀
3. 带具体路径 —— proxy_pass http://host:port/v1，location 前缀替换为 /v1
4. 关键 —— 是否带路径（末尾斜杠也算）决定是否改写 URI
```

## proxy_set_header

proxy_set_header 用于设置转发给后端的请求头。后端通常需要知道真实的客户端 IP（X-Forwarded-For）、原始协议（X-Forwarded-Proto）和主机名（Host），否则拿到的都是 Nginx 自己的地址，影响日志、鉴权和重定向。

```nginx
server {
    location /api/ {
        proxy_pass http://backend:3000;

        # 传递真实客户端 IP
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # 传递原始协议
        proxy_set_header X-Forwarded-Proto $scheme;
        # 传递原始 Host
        proxy_set_header Host $host;
    }
}
```

```text
常用 proxy_set_header 头：
1. Host —— 原始请求的域名，后端据此生成正确链接
2. X-Real-IP —— 客户端真实 IP
3. X-Forwarded-For —— 代理链上的完整 IP 列表
4. X-Forwarded-Proto —— 原始协议（http/https），后端判断是否 HTTPS
5. X-Forwarded-Host —— 原始主机名
```

## upstream

upstream 定义一组后端服务器，给它起一个名字，proxy_pass 直接指向这个名字。它是负载均衡的基础：多个后端实例组成一个池子，Nginx 按策略分发请求，某台挂了还能自动剔除。

```nginx
# 定义后端服务器组
upstream backend {
    server backend1:3000;
    server backend2:3000;
    server backend3:3000;
}

server {
    location /api/ {
        proxy_pass http://backend;
        proxy_set_header Host $host;
    }
}
```

```text
upstream 的要点：
1. 命名 —— 给后端组起名，proxy_pass 指向该名字
2. 多实例 —— 声明多个 server，形成后端池
3. 权重 —— server 后可加 weight= 控制分配比例
4. 健康检查 —— 配合 max_fails 和 fail_timeout 剔除故障实例
```

## load balancing

Load Balancing（负载均衡）是把请求分发到 upstream 里的多个后端实例，避免单点过载、提升可用性。Nginx 支持多种分配算法：轮询（默认）、权重、IP 哈希、最少连接等，配合故障转移实现高可用。

```nginx
upstream backend {
    # 加权轮询：backend1 权重更高，分到更多请求
    server backend1:3000 weight=3;
    server backend2:3000 weight=1;
    server backend3:3000 weight=1;

    # 故障剔除：1 次失败暂停 10 秒
    # max_fails=3 fail_timeout=30s;
}

upstream sticky_backend {
    # IP 哈希：同一客户端固定打到同一后端
    ip_hash;
    server backend1:3000;
    server backend2:3000;
}

upstream least_backend {
    # 最少连接：优先分给连接数最少的后端
    least_conn;
    server backend1:3000;
    server backend2:3000;
}
```

```text
负载均衡算法：
1. 轮询 —— 默认，逐个轮流分配
2. weight —— 加权轮询，按权重比例分配
3. ip_hash —— 按客户端 IP 哈希，会话粘滞
4. least_conn —— 最少连接，适合长连接场景
```

```text
负载均衡的附加能力：
1. 故障转移 —— max_fails + fail_timeout 自动剔除坏实例
2. 健康检查 —— 定时探测后端，剔除不健康的
3. 会话保持 —— ip_hash 或 cookie 粘滞，保持会话连续性
```

## 应用场景实战

### 场景一：前端 + 后端同域反代（解决跨域）

```nginx
# 静态资源和 API 同一域名，/api 反代到后端
server {
    listen 80;
    server_name app.example.com;
    root /var/www/app;

    # 前端页面
    location / {
        try_files $uri $uri/ /index.html;
    }

    # API 反向代理
    location /api/ {
        proxy_pass http://backend:3000/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### 场景二：多后端负载均衡 + 故障转移

```nginx
# 一个 upstream 池 + 加权 + 故障转移
upstream api_backend {
    server api-1:3000 weight=3 max_fails=3 fail_timeout=30s;
    server api-2:3000 weight=2 max_fails=3 fail_timeout=30s;
    server api-3:3000 weight=1 max_fails=3 fail_timeout=30s;
    keepalive 32;
}

server {
    listen 80;
    location /api/ {
        proxy_pass http://api_backend/;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 前端 API 走同域反代，从架构上规避跨域，而不是靠后端加 CORS 头
2. 反代时传递 Host、X-Forwarded-For、X-Forwarded-Proto，后端才能拿到真实信息
3. 用 upstream 管理后端池，配合 weight 和故障转移实现高可用
4. proxy_pass 末尾是否带斜杠要深思熟虑，避免 URI 被意外改写
5. 长连接场景开启 keepalive 复用后端连接，降低握手开销

### 踩坑记录

```text
坑 1：proxy_pass 末尾斜杠写错导致 URI 被改写
结论：后端收到的路径少了 /api 前缀，路由匹配不到返回 404。
原因：proxy_pass http://backend:3000/ 会把 location 前缀替换掉。
解法：明确拼接规则，需要保留前缀就不带路径，需要去掉就带 / 或具体路径。

坑 2：没传 X-Forwarded-For 导致后端日志全是 Nginx IP
结论：后端日志、风控、限流看到的都是代理 IP，无法定位真实用户。
原因：默认转发时客户端 IP 被替换成 Nginx 的地址。
解法：加 proxy_set_header X-Real-IP 和 X-Forwarded-For。

坑 3：没传 Host 导致后端重定向错误
结论：后端生成的链接或重定向用的是错误域名。
原因：Host 头被改成后端地址，后端拿不到原始域名。
解法：加 proxy_set_header Host $host 保留原始 Host。

坑 4：upstream 实例挂了还在转发
结论：请求打到故障实例，出现超时或 502。
原因：没有配置 max_fails 和 fail_timeout，故障实例未被剔除。
解法：配置 max_fails=3 fail_timeout=30s，让 Nginx 自动剔除坏实例。

坑 5：ip_hash 与动态扩容不兼容
结论：后端扩缩容后会话粘滞被打破，部分用户掉线。
原因：ip_hash 按 IP 取模，后端数量变化会重新分配。
解法：会话粘滞优先用 cookie 方式（sticky），或后端无状态化。
```
