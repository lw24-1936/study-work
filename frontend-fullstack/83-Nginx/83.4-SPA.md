## 概述

SPA（Single Page Application，单页应用）只有一个 index.html 入口，页面切换靠前端路由（history 模式）改写 URL，不发生真正的服务器请求。因此部署 SPA 时最大的坑是「刷新子路由 404」——服务器按文件路径去找 /about，但磁盘上根本没有这个文件。Nginx 通过 try_files 的 history fallback 机制，把未知路径统一回退到 index.html 解决这个问题。

```text
SPA 部署的三个核心问题：
1. history fallback —— 未知路径回退到 index.html，交给前端路由
2. try_files —— 实现回退的关键指令
3. 404 —— 真正的资源缺失与路由回退如何区分
```

```nginx
# SPA 部署的标准配置
server {
    listen 80;
    server_name app.example.com;
    root /var/www/app;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

## history fallback

history fallback（历史路由回退）是 SPA 部署的核心机制：当前端用 history 模式路由时，URL 形如 /about、/user/123，刷新页面或直接访问这些 URL，服务器找不到对应文件。回退机制就是「找不到文件时，返回 index.html」，让前端 JS 重新接管路由，渲染正确的页面。

```text
history 路由 vs hash 路由：
1. history —— URL 干净（/about），刷新需服务器回退支持
2. hash —— URL 带 #（/#/about），# 后不发送到服务器，天然不 404
3. 结论 —— history 模式体验好，但必须配置服务器回退
```

```nginx
# history fallback 的实现：所有未命中路径回退到 index.html
location / {
    try_files $uri $uri/ /index.html;
}
```

```text
history fallback 的工作流程：
1. 请求 /about —— 前端路由的路径
2. Nginx 查找 /about 文件 —— 不存在
3. 回退返回 index.html —— 兜底
4. 前端 JS 加载 —— 读取 URL 渲染对应路由组件
```

```bash
# 部署后验证回退是否生效
curl -I http://app.example.com/about
# 应返回 200，且 Content-Type 是 text/html（回退到了 index.html）

curl -I http://app.example.com/assets/app.js
# 应返回 200 且是真实的 JS 文件（真实资源优先命中）
```

```text
history fallback 的适用范围：
1. Vue Router / React Router 的 history 模式
2. 直接访问或刷新子路由的场景
3. 分享链接、收藏链接直达深层页面
4. 搜索引擎抓取子路径时返回正确内容
```

## try_files

try_files 是 SPA 回退的具体实现指令：按顺序尝试多个候选路径，全部不存在时执行最后的回退动作。对 SPA，标准写法是 `try_files $uri $uri/ /index.html;`——先找真实文件，再找目录，最后回退到 index.html。

```nginx
server {
    root /var/www/app;

    location / {
        # 顺序尝试：文件 -> 目录 -> 回退 index.html
        try_files $uri $uri/ /index.html;
    }

    # 静态资源走真实文件，不参与回退
    location /assets/ {
        try_files $uri =404;
    }
}
```

```text
try_files 在 SPA 里的分层：
1. $uri —— 命中真实文件（如 /assets/app.js）直接返回
2. $uri/ —— 命中真实目录则触发 index
3. /index.html —— 兜底回退，SPA 路由接管
```

```nginx
# 用命名 location 做回退：回退逻辑可复用、更清晰
server {
    root /var/www/app;

    location / {
        try_files $uri $uri/ @fallback;
    }

    location @fallback {
        # 回退到 index.html，交给前端路由
        root /var/www/app;
        try_files /index.html =404;
    }
}
```

```text
try_files 的边界：
1. 真实资源优先 —— 静态文件永远先于回退被返回
2. 回退兜底 —— 只有真的找不到才回退到 index.html
3. 静态资源区 —— assets 等目录用 =404，避免误回退
```

## 404

SPA 部署里的 404 处理是个矛盾点：路由路径「找不到文件」是正常的（应该回退 index.html），但「资源真的缺失」又应该返回 404。关键在于区分「前端路由路径」和「真实静态资源路径」——前者回退，后者严格 404。

```nginx
server {
    root /var/www/app;

    # 已知静态资源目录：严格 404，不参与回退
    location /assets/ {
        try_files $uri =404;
    }

    # 前端路由路径：回退到 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

```text
404 的几种处理策略：
1. 回退 index.html —— 前端路由路径，交给 SPA 处理
2. 严格 404 —— 真实资源缺失，如实返回 404
3. 自定义 404 页 —— error_page 404 /404.html，提升体验
```

```text
SPA 内自定义 404：
1. 前端路由兜底 —— 路由表里匹配不到，渲染 NotFound 组件
2. 服务器 404 —— 资源文件缺失时由 Nginx 返回
3. 分工 —— 路由 404 归前端，资源 404 归服务器
```

## 应用场景实战

### 场景一：标准 SPA 部署（Vue/React history 路由）

```nginx
# 完整的 SPA 部署配置
server {
    listen 80;
    server_name app.example.com;
    root /var/www/app;
    index index.html;

    # 静态资源长缓存
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }

    # history fallback
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

### 场景二：带自定义 404 页的 SPA 部署

```nginx
# SPA + 自定义 404 页面
server {
    listen 80;
    server_name app.example.com;
    root /var/www/app;
    index index.html;

    # 自定义 404 页面
    error_page 404 /404.html;
    location = /404.html {
        internal;
    }

    # 静态资源严格 404
    location /assets/ {
        try_files $uri =404;
    }

    # 前端路由回退
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 前端路由用 history 模式，服务器统一配 try_files 回退到 index.html
2. 静态资源目录（assets）用 try_files $uri =404，避免误回退到 HTML
3. 带 hash 的静态资源长缓存，index.html 短缓存，保证发布即时生效
4. 后端 API 用 /api 前缀反代，与前端路由路径区分开
5. 前端路由兜底渲染 NotFound 组件，服务器 404 与路由 404 分工明确
6. 部署后验证「刷新子路由」和「访问不存在的资源」两种场景

### 踩坑记录

```text
坑 1：刷新子路由直接 404
结论：用户刷新 /about 页面白屏或 404，从首页导航则正常。
原因：没有 try_files 回退，Nginx 按文件查找找不到 /about。
解法：location / 加 try_files $uri $uri/ /index.html;。

坑 2：静态资源 404 被回退成 index.html
结论：缺失的 JS 文件返回了 HTML 内容，浏览器报语法错误且难以排查。
原因：assets 目录没有单独配 try_files =404，未知资源被回退。
解法：静态资源目录用 try_files $uri =404，只有路由路径才回退。

坑 3：hash 路由模式却配了 history fallback
结论：配置了回退但 # 后的路径根本不发到服务器，回退形同虚设。
原因：hash 路由的 URL 不包含真实路径，服务器只收到根路径请求。
解法：升级到 history 路由模式，配合服务器回退，获得干净的 URL。

坑 4：index.html 长缓存导致发布后白屏
结论：发布后用户加载的还是旧 index.html，引用的新资源可能已不存在。
原因：index.html 被设了长缓存，浏览器不重新获取入口。
解法：index.html 设 no-cache 或短缓存，静态资源用 hash 长缓存。

坑 5：API 路径被 history fallback 吞掉
结论：/api/xxx 请求返回了 HTML 而不是 JSON，接口报错。
原因：location 顺序或配置错误，/api 请求被 SPA 回退逻辑处理。
解法：/api 用独立的 location 反代到后端，优先级高于 SPA 回退。
```
