## 概述

DOM Clobbering（DOM 污染/覆盖）是一种利用 HTML 命名元素自动挂载到 window/document 上的特性，覆盖全局变量，干扰脚本逻辑的攻击手段。

```text
DOM Clobbering 的本质：
1. HTML 元素的 id/name 会自动成为 window 上的全局属性
2. 攻击者注入带特定 id/name 的元素，覆盖脚本依赖的全局变量
3. 脚本读到的变量变成攻击者控制的元素，而非预期值
```

```text
危害：
1. 覆盖配置变量 —— 让脚本误判环境，走危险分支
2. 覆盖函数 —— 让脚本调用被劫持
3. 配合其他漏洞 —— 放大 XSS 或逻辑漏洞的影响
```

```html
<!-- 攻击载荷：注入一个 id=config 的元素 -->
<form id="config">
  <input name="isAdmin" value="true">
</form>
```

```js
// 受害脚本本来的意图
if (window.config && window.config.isAdmin) {
  // 危险操作
}
// 被污染后 window.config 变成了上面的 form 元素
// config.isAdmin 变成 input 元素，判定逻辑被操纵
```

## DOM Clobbering 攻击原理

理解 DOM Clobbering 的关键是浏览器的一个特性：HTML 元素的 id 和 name 会自动注册为全局对象的属性。

```text
浏览器特性（污染根源）：
1. 元素的 id 属性 → window.<id> 可直接访问
2. 元素的 name 属性（表单内）→ 也挂到 window 和 form 上
3. 多个同名元素 → 变成 HTMLCollection 数组
```

```html
<!-- 这三行就能污染全局 -->
<img id="foo">
<a name="bar"></a>

<script>
  console.log(window.foo);  // <img> 元素（而非 undefined）
  console.log(window.bar);  // <a> 元素
</script>
```

```js
// 正常情况下这些变量应该是 undefined 或脚本自己定义的
// 但被 DOM Clobbering 污染后，它们变成了攻击者控制的元素
console.log(typeof window.foo); // 'object'（元素对象）
```

```text
会被污染的目标：
1. window 上的全局变量（window.config、window.defaultStatus）
2. document 上的属性（document.title 等部分只读）
3. 表单元素的属性（form.action、form.length 等）
4. 脚本里未声明就直接用的全局标识符
```

## 命名元素的污染

命名元素污染是 DOM Clobbering 的机制：id 和 name 让元素以全局变量形式暴露。

```html
<!-- id 污染 -->
<div id="config">attacker controlled</div>

<!-- name 污染（需在表单内） -->
<form name="target">
  <input name="id" value="attacker">
</form>
```

```js
// 污染后的效果
console.log(window.config);     // <div id="config">
console.log(document.target);   // <form name="target">
```

```text
污染细节：
1. id 直接成为 window 属性
2. 多个同名 id → window.<id> 是 HTMLCollection（类数组）
3. 表单的 name 成为 document 属性（部分浏览器）
4. 表单内控件的 name 成为该 form 的属性
```

```html
<!-- 多元素同名，形成集合 -->
<img id="x"><img id="x"><img id="x">
<script>
  console.log(window.x.length); // 3，HTMLCollection
</script>
```

```text
防护思路：
1. 脚本里避免依赖裸的全局标识符（用 const/let 显式声明）
2. 关键变量用 var/let 声明，声明优先于元素属性
3. 不信任外部可控的 id/name
4. 用严格模式（strict mode）减少隐式全局
```

## DOM Clobbering 的利用

攻击者利用污染变量，干扰脚本的判断逻辑或劫持函数调用。

```html
<!-- 利用一：污染函数引用 -->
<button id="submitForm">被污染的按钮</button>
<script>
  // 脚本本意是调用一个全局函数
  // 但 window.submitForm 被上面的 button 覆盖了
  typeof window.submitForm; // 'object'，不是 'function'
  // 如果脚本执行 submitForm()，会报 TypeError
</script>
```

```html
<!-- 利用二：污染判断逻辑 -->
<form id="isLoggedIn">
  <input name="value" value="true">
</form>
<script>
  // 危险模式：直接读全局标识符判断登录态
  if (isLoggedIn) {
    // 攻击者注入 form 后，isLoggedIn 变成 truthy 的 form 元素
    // 未登录用户被误判为已登录
    grantAccess();
  }
</script>
```

```text
利用场景：
1. 覆盖 config/flag —— 让 if 判断永远走攻击者想要的分支
2. 覆盖函数 —— 让脚本调用失效或抛错（DoS）
3. 结合 innerHTML 注入 —— 先注入污染元素，再触发受害逻辑
```

```js
// 正确防护：显式声明变量，声明优先级高于元素属性
let config = null;   // 声明后 window.config 的污染被屏蔽
// 或使用 const 定义常量，元素无法覆盖
```

## Trusted Types

Trusted Types 是浏览器的安全 API，从根源上防止基于 DOM 的注入攻击，是 DOM Clobbering 和 DOM XSS 的现代防线。

```text
Trusted Types 解决什么问题：
1. innerHTML 等危险 API 默认拒绝接受普通字符串
2. 只有经过「信任策略」处理的 TrustedHTML 才能写入
3. 攻击者注入的字符串无法直接到达 DOM
```

```js
// 启用 Trusted Types（通过 CSP）
// Content-Security-Policy: require-trusted-types-for 'script'
```

```js
// 创建信任策略
if (window.trustedTypes && trustedTypes.createPolicy) {
  trustedTypes.createPolicy('default', {
    createHTML: (input) => {
      // 在这里消毒，返回的才是可信 HTML
      return DOMPurify.sanitize(input);
    },
    createScriptURL: (input) => {
      // 校验 URL 白名单
      return input.startsWith('https://trusted.com') ? input : '';
    },
  });
}
```

```js
// 启用后，直接赋值会被拦截
el.innerHTML = '<img src=x onerror=alert(1)>';  // TypeError
// 必须用可信类型
el.innerHTML = trustedTypes.defaultPolicy.createHTML(cleanHtml);
```

```text
Trusted Types 要点：
1. 三个可信类型 —— TrustedHTML、TrustedScript、TrustedScriptURL
2. 危险 API 只接受可信类型 —— innerHTML、script.src、eval 等
3. 策略负责消毒 —— 把「可信」和「不可信」在类型层面隔离
4. 需 CSP require-trusted-types-for 'script' 启用
5. 对 DOM Clobbering 是间接防线 —— 阻止注入，污染无从谈起
```

## 应用场景实战

### 场景一：防止配置变量被污染

```html
<!-- 页面里有个全局配置对象，容易被 id 污染 -->
<script>
  // 错误做法：裸全局变量
  // window.appConfig 可能被 <div id="appConfig"> 污染

  // 正确做法：用闭包/模块作用域隔离
  const appConfig = (() => {
    const config = { isAdmin: false };
    // 从可信来源（如后端注入的 JSON）读取，而非依赖 window
    return config;
  })();

  // 或显式用 let 声明，声明优先于元素 id 属性
</script>
```

### 场景二：启用 Trusted Types 防护注入

```js
// 完整启用 Trusted Types 的示例
// 1. 服务端 CSP 头：require-trusted-types-for 'script'
// 2. 前端注册策略
const policy = trustedTypes.createPolicy('secure', {
  createHTML: (s) => DOMPurify.sanitize(s, { RETURN_TRUSTED_TYPE: true }),
  createScript: (s) => { throw new Error('禁止动态脚本'); },
  createScriptURL: (s) => {
    const url = new URL(s, location.origin);
    if (url.origin === location.origin) return s;
    throw new Error('禁止外部脚本');
  },
});

// 3. 所有 innerHTML 写入都走策略
el.innerHTML = policy.createHTML(userContent);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 脚本里避免依赖裸全局标识符，一律 const/let 显式声明
2. 关键配置从可信来源读取，别直接读 window 上的属性
3. 使用严格模式 + 模块作用域，减少全局污染面
4. 引入 Trusted Types，从类型层面隔离不可信字符串
5. 输出 HTML 一律消毒，阻断注入污染元素的机会

### 踩坑记录

```text
坑 1：if 判断直接用裸全局变量
结论：登录态/配置判断被污染元素劫持。
原因：id/name 元素自动挂到 window，覆盖了预期变量。
解法：用 const/let 显式声明，或从模块/闭包读取。

坑 2：以为 innerHTML 消毒了就没问题
结论：消毒只防 XSS，防不了 DOM Clobbering。
原因：消毒可能保留无害的 form/input，这些仍会污染全局。
解法：配合 Trusted Types 和 CSP 做纵深防护。

坑 3：Trusted Types 开启后页面全报错
结论：开启 require-trusted-types 后大量脚本失效。
原因：原有 innerHTML 直接赋字符串的代码都不被允许。
解法：先建默认策略，逐步迁移，用 report-only 模式过渡。

坑 4：Trusted Types 默认策略放水
结论：策略里 createHTML 直接返回输入，等于没防护。
原因：策略没有真正消毒，可信类型形同虚设。
解法：策略里必须做白名单过滤/消毒。

坑 5：忽略了 name 属性污染
结论：只防了 id，没防 name 属性污染。
原因：表单控件的 name 也会挂到 window/form 上。
解法：id 和 name 都要警惕，外部可控的命名元素一律消毒。
```
