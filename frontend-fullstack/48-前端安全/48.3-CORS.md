## 概述

CORS（Cross-Origin Resource Sharing，跨域资源共享）是浏览器的一种机制，让一个源（origin）的页面能安全地访问另一个源的资源。它是同源策略的「受控例外」。

```text
为什么需要 CORS：
1. 同源策略默认禁止跨域请求，保护用户数据
2. 但前后端分离、调用第三方 API 都需要跨域
3. CORS 通过响应头声明「允许哪些源访问我」
```

```text
核心概念：源（Origin）= 协议 + 域名 + 端口
https://api.example.com:443
http://localhost:3000 与 http://localhost:8080 是不同源（端口不同）
```

```js
// 跨域请求示例：前端页面在 localhost:3000，请求 api 在 localhost:8080
const res = await fetch('http://localhost:8080/api/data');
// 浏览器会先检查响应头是否允许当前源
```

## Same Origin Policy

同源策略（SOP）是浏览器的安全基石：一个源的脚本不能随意读写另一个源的资源，防止恶意页面窃取数据。

```text
同源策略限制什么：
1. 读跨域响应 —— fetch/XHR 读不到跨域接口的数据
2. 跨域 DOM 访问 —— iframe 里的跨域页面读不到内容
3. 跨域存储 —— 读不到其他源的 localStorage/Cookie

不限制什么（可跨域但读不到响应）：
1. 发送请求 —— 请求能发出去，但响应被拦截
2. 嵌入资源 —— <img>、<script>、<link> 可跨域加载
```

```js
// 跨域读取失败示例
try {
  const res = await fetch('https://other-site.com/api/data');
  const data = await res.json(); // 这里会抛错，响应被同源策略拦截
} catch (e) {
  console.error('被同源策略拦截', e);
}
```

```text
同源策略的本质：
1. 防止恶意站点读取你在其他站点的数据
2. 请求可以发（POST 也能发出去），但响应读不到
3. CORS 就是服务端「授权」特定源读取响应的机制
```

## Simple Request

简单请求（Simple Request）不触发预检，浏览器直接发请求，检查响应头决定是否放行。

```text
简单请求需同时满足：
1. 方法 —— GET / HEAD / POST 之一
2. 头部 —— 仅限简单头（Accept、Accept-Language、Content-Language、Content-Type）
3. Content-Type —— 仅限 text/plain、multipart/form-data、application/x-www-form-urlencoded
4. 无自定义头、无 ReadableStream 请求体
```

```js
// 简单请求：GET + 无自定义头
const res = await fetch('https://api.example.com/data');
// 浏览器直接发 GET，检查响应头 Access-Control-Allow-Origin
```

```text
简单请求流程：
1. 浏览器直接发请求（带 Origin 头）
2. 服务端返回响应，可带 Access-Control-Allow-Origin
3. 浏览器检查该头是否包含当前源
4. 包含 → 放行；不包含 → 拦截
```

## Preflight 与 OPTIONS

非简单请求（带自定义头、PUT/DELETE、JSON 请求体等）会先发一个 OPTIONS 预检请求，确认服务端允许后再发正式请求。

```text
预检请求（Preflight）的触发条件：
1. 方法不是 GET/HEAD/POST
2. 带了自定义请求头（如 Authorization、X-CSRF-Token）
3. Content-Type 是 application/json 等非简单类型
```

```js
// 这个请求会触发预检：PUT + JSON + 自定义头
const res = await fetch('https://api.example.com/user/1', {
  method: 'PUT',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': 'Bearer token',   // 自定义头触发预检
  },
  body: JSON.stringify({ name: 'Alice' }),
});
```

```text
预检请求的实际报文：
OPTIONS /user/1 HTTP/1.1
Origin: https://myapp.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization, content-type
```

```text
服务端预检响应：
Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: PUT, GET, POST, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 86400   ← 预检结果缓存时间（秒）
```

```text
预检要点：
1. OPTIONS 请求不带请求体，只做权限询问
2. 预检通过后才发正式请求
3. Access-Control-Max-Age 缓存预检结果，减少 OPTIONS 次数
4. 预检失败，正式请求根本不会发出
```

## Access-Control-Allow-Origin

Access-Control-Allow-Origin（ACAO）是 CORS 最核心的响应头，声明允许哪些源访问。

```text
两种取值：
1. 具体源 —— Access-Control-Allow-Origin: https://myapp.com（只允许该源）
2. 通配符 —— Access-Control-Allow-Origin: *（允许任意源）
```

```js
// 服务端设置（Node/Express）
app.use((req, res, next) => {
  res.setHeader('Access-Control-Allow-Origin', 'https://myapp.com');
  next();
});
```

```text
ACAO 要点：
1. 浏览器校验 ACAO 是否匹配当前页面源
2. 不匹配 → 拦截响应，JS 读不到数据
3. 通配符 * 与凭证（Cookie）不兼容，见 Credentials
4. 服务端可根据请求 Origin 动态返回，也可用中间件（cors 包）
```

```js
// 使用 cors 中间件（Node）
import cors from 'cors';
app.use(cors({
  origin: ['https://myapp.com', 'https://admin.myapp.com'],
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
}));
```

## Credentials

默认情况下，跨域请求不携带 Cookie 等凭证。需要携带时前端要显式开启，服务端也要配合配置。

```js
// 前端：开启携带凭证
const res = await fetch('https://api.example.com/me', {
  credentials: 'include',   // 跨域也带上 Cookie
});
```

```text
credentials 取值：
1. omit —— 不携带凭证（默认）
2. same-origin —— 同源携带，跨域不携带
3. include —— 始终携带（跨域也带）
```

```js
// 服务端：携带凭证时的正确配置
res.setHeader('Access-Control-Allow-Origin', 'https://myapp.com'); // 不能用 *
res.setHeader('Access-Control-Allow-Credentials', 'true');
```

```text
Credentials 要点：
1. 携带凭证时 ACAO 不能用 *，必须指定具体源
2. 服务端还要加 Access-Control-Allow-Credentials: true
3. Cookie 的 SameSite=None 才允许跨站携带
4. 两者缺一，浏览器都拒绝
```

```text
常见报错：
「The value of the 'Access-Control-Allow-Origin' header must not
 be the wildcard '*' when the request's credentials mode is 'include'」
→ 携带凭证却用了通配符 *
```

## 应用场景实战

### 场景一：前后端分离开发配置 CORS

```js
// 后端（Express）开发环境允许前端 dev server
import cors from 'cors';

const allowedOrigins = ['http://localhost:3000', 'http://localhost:5173'];
app.use(cors({
  origin: (origin, callback) => {
    // 无 origin 的请求（如 curl、同源）也放行
    if (!origin || allowedOrigins.includes(origin)) callback(null, true);
    else callback(new Error('Not allowed by CORS'));
  },
  credentials: true,
}));
```

### 场景二：调用第三方 API（不携带凭证）

```js
// 调用公开 API，不需要 Cookie，用简单配置
const res = await fetch('https://api.github.com/repos/nodejs/node', {
  headers: { Accept: 'application/vnd.github+json' },
});
const repo = await res.json();
console.log(repo.stargazers_count);
```

```text
第三方 API 通常配置 ACAO: * 允许任意源，
因为不涉及用户凭证，开放访问是安全的。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产环境 ACAO 用具体源白名单，别用通配符 *
2. 携带凭证时 ACAO 不能用 *，必须具体源 + Allow-Credentials
3. 用 cors 中间件，别手写响应头逻辑
4. 预检结果用 Access-Control-Max-Age 缓存，减少 OPTIONS 请求
5. 错误信息不要暴露敏感细节，生产环境统一处理

### 踩坑记录

```text
坑 1：携带 Cookie 却配了 ACAO: *
结论：请求被拦截，报通配符错误。
原因：携带凭证时不允许 ACAO 为 *。
解法：指定具体源 + Access-Control-Allow-Credentials: true。

坑 2：前端忘了 credentials: include
结论：跨域请求不带 Cookie，登录态丢失。
原因：fetch 默认 credentials 是 same-origin。
解法：需要带 Cookie 时显式 credentials: 'include'。

坑 3：预检请求 404
结论：OPTIONS 请求返回 404，正式请求发不出去。
原因：后端没处理 OPTIONS 预检路由。
解法：cors 中间件自动处理，或手动响应 OPTIONS。

坑 4：自定义头未加入 Allow-Headers
结论：预检失败，报头不被允许。
原因：Authorization 等自定义头未在 Access-Control-Allow-Headers 声明。
解法：把用到的自定义头都加进 allowedHeaders。

坑 5：CORS 配好了还是被拦
结论：响应头配置正确但仍报跨域错误。
原因：服务端逻辑抛错，错误响应没有 CORS 头。
解法：错误处理中间件也要设置 CORS 头。
```
