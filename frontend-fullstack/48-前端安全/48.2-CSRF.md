## 概述

CSRF（Cross-Site Request Forgery，跨站请求伪造）是攻击者诱导已登录用户，在不知情的情况下向目标站点发出恶意请求。因为浏览器会自动带上 Cookie，服务端误以为是用户本人操作。

```text
CSRF 的特点：
1. 借刀杀人 —— 利用用户已登录的 Cookie，而非窃取 Cookie
2. 浏览器自动带 Cookie —— 这是漏洞根源
3. 攻击者拿不到响应 —— 但破坏性请求（转账/改密码）已经发出
```

```text
典型危害：
1. 转账 —— 诱导点击后账户钱被转走
2. 修改密码/邮箱 —— 账号被接管
3. 发帖/关注 —— 伪造用户行为
4. 管理员操作 —— 诱导管理员执行危险命令
```

```js
// 攻击者页面里的隐藏表单：受害者打开即提交
// <form action="https://bank.com/transfer" method="POST">
//   <input type="hidden" name="to" value="attacker">
//   <input type="hidden" name="amount" value="10000">
// </form>
// 自动提交后，浏览器带着受害者的 Cookie 发出转账请求
```

## CSRF 攻击原理

CSRF 能成功，是因为「浏览器自动带 Cookie」和「服务端只凭 Cookie 判断身份」这两个前提同时成立。

```text
攻击链路：
1. 用户登录 bank.com，浏览器持有会话 Cookie
2. 用户访问攻击者的恶意页面（或点击链接）
3. 恶意页面里的表单/请求指向 bank.com
4. 浏览器发请求时自动带上 bank.com 的 Cookie
5. 服务端看到有效 Cookie，执行了请求
```

```js
// 攻击手段一：自动提交的表单
document.forms[0].submit();

// 攻击手段二：GET 请求也能触发（改密码这类操作绝不能用 GET）
// <img src="https://bank.com/transfer?to=attacker&amount=10000">
```

```text
防护思路（对应两个前提逐个击破）：
1. 让跨站请求带不上 Cookie → SameSite
2. 让请求必须带额外凭证 → CSRF Token
3. 服务端校验请求来源 → Origin / Referer Check
```

## SameSite

SameSite 是 Cookie 属性，控制跨站请求是否携带该 Cookie，是从根源阻断 CSRF 最简洁的手段。

```text
SameSite 三值：
Strict —— 任何跨站请求都不带 Cookie（最严格）
Lax    —— 仅顶级导航（点链接跳转）带 Cookie，跨站子请求不带
None   —— 跨站请求也带 Cookie（必须配 Secure）
```

```js
// 服务端设置（以 Node 为例）
res.setHeader('Set-Cookie', 'sessionId=abc; SameSite=Strict; Secure; HttpOnly');
```

```text
SameSite 防 CSRF 原理：
CSRF 依赖「跨站请求自动带 Cookie」。
SameSite=Strict/Lax 让跨站请求不带 Cookie，
服务端收不到会话标识，自然拒绝请求。
```

```text
三值取舍：
1. Strict —— 最安全，但用户从外部链接跳进来时是未登录态，体验差
2. Lax —— 平衡之选，允许点链接跳转带 Cookie，阻止表单/图片等子请求
3. None —— 完全不防 CSRF，仅用于第三方嵌入场景，必须另配 Token
```

## CSRF Token

CSRF Token 是服务端生成的一次性随机串，页面加载时注入，提交请求时带上，服务端校验。攻击者无法提前拿到这个串。

```text
工作流程：
1. 服务端生成随机 token，存 session，注入页面
2. 前端每次提交请求时带上 token（header 或表单字段）
3. 服务端校验 token 与 session 一致才放行
4. 攻击者跨站请求带不上 token → 被拒
```

```js
// 前端：从 meta 标签读取 token，请求时放 header
const token = document.querySelector('meta[name=csrf-token]').content;

fetch('/api/transfer', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': token,       // 带上 token
  },
  body: JSON.stringify({ to: 'bob', amount: 100 }),
});
```

```js
// 服务端校验（Node/Express 伪代码）
app.post('/api/transfer', (req, res) => {
  const token = req.headers['x-csrf-token'];
  if (token !== req.session.csrfToken) {
    return res.status(403).send('CSRF token 无效');
  }
  // ... 执行转账
});
```

```text
CSRF Token 要点：
1. token 要足够随机、不可预测
2. 每次会话或每次请求生成，防止重放
3. 攻击者跨站无法读到 token（受同源策略限制）
4. 前端框架（如 axios）可统一拦截器注入 token
```

## Origin Check

校验请求的 Origin 请求头，只允许来自自己站点的请求。

```js
// 服务端校验 Origin
app.use((req, res, next) => {
  const origin = req.headers.origin;
  const allowed = ['https://myapp.com', 'https://www.myapp.com'];
  if (origin && !allowed.includes(origin)) {
    return res.status(403).send('非法来源');
  }
  next();
});
```

```text
Origin Check 要点：
1. Origin 由浏览器自动设置，攻击者无法伪造
2. 跨站请求的 Origin 是攻击者域名，与白名单不符 → 拒绝
3. 同源请求通常不带 Origin（可用 Referer 兜底）
4. 浏览器兼容性：老浏览器可能不发 Origin
```

## Referer Check

Referer（拼写确实是单 r）记录请求来源页面 URL，可用来判断请求是否来自本站。

```js
// 服务端校验 Referer
app.use((req, res, next) => {
  const referer = req.headers.referer;
  if (referer && !referer.startsWith('https://myapp.com')) {
    return res.status(403).send('非法来源');
  }
  next();
});
```

```text
Referer Check 的局限：
1. Referer 可能被浏览器策略或用户设置禁用
2. 部分场景（跳转、HTTPS→HTTP）不发送 Referer
3. 相对 Origin 更不可靠，作为辅助手段
```

```text
Origin vs Referer 对比：
1. Origin —— 只含协议+域名+端口，浏览器强制发送，更可靠
2. Referer —— 含完整路径，可能被禁用，隐私泄露风险
3. 实践 —— 优先 Origin，Referer 做兜底
```

## 应用场景实战

### 场景一：转账接口的多重防护

```js
// 前端：axios 拦截器统一注入 CSRF token
import axios from 'axios';

axios.interceptors.request.use((config) => {
  const token = document.querySelector('meta[name=csrf-token]').content;
  if (token) config.headers['X-CSRF-Token'] = token;
  return config;
});

await axios.post('/api/transfer', { to: 'bob', amount: 100 });
```

```text
服务端三道防线：
1. SameSite=Lax 的会话 Cookie（跨站请求带不上）
2. CSRF Token 校验（请求必须带 token）
3. Origin 白名单校验（只认自己站点）
```

### 场景二：登录态与 SameSite 配置

```js
// 服务端设置安全的会话 Cookie
res.setHeader('Set-Cookie', [
  'sessionId=' + sessionId + '; Path=/; HttpOnly; Secure; SameSite=Lax',
  'csrfToken=' + csrfToken + '; Path=/; Secure; SameSite=Lax',
].join(', '));
```

```text
配置要点：
1. 会话 Cookie 用 HttpOnly（防 XSS 窃取）+ SameSite（防 CSRF）
2. csrfToken 不能 HttpOnly，前端 JS 要能读
3. 两者都要 Secure，HTTPS 才生效
```

## 最佳实践与踩坑记录

### 最佳实践

1. 会话 Cookie 用 SameSite=Lax，从根源阻断跨站携带
2. 状态变更接口（POST/PUT/DELETE）必须加 CSRF Token
3. 服务端校验 Origin 白名单，Referer 做兜底
4. 敏感操作永远用 POST，别用 GET（GET 可被 img 标签触发）
5. 双重验证：重要操作加二次确认（短信/密码）

### 踩坑记录

```text
坑 1：SameSite=None 忘配 Secure
结论：浏览器拒绝该 Cookie。
原因：SameSite=None 必须配合 Secure 才生效。
解法：None + Secure 一起设置，且站点必须 HTTPS。

坑 2：用 GET 做状态变更
结论：改密码/转账接口被 GET 触发。
原因：GET 可被 <img>、<a> 等标签发起，且带 Cookie。
解法：状态变更一律 POST/PUT/DELETE。

坑 3：CSRF Token 放进 HttpOnly Cookie
结论：前端 JS 读不到 token，请求发不出去。
原因：HttpOnly 禁止 JS 访问。
解法：csrfToken 用普通 Cookie 或直接渲染进 meta 标签。

坑 4：只做前端校验不做服务端校验
结论：绕过前端直接调接口成功。
原因：前端校验可被开发者工具绕过。
解法：CSRF 防护必须落在服务端。

坑 5：依赖 Referer 但浏览器不发
结论：Referer 为空的请求被误伤或漏防。
原因：部分浏览器/隐私模式/HTTPS→HTTP 不发 Referer。
解法：以 Origin 为主，Referer 仅做辅助。
```
