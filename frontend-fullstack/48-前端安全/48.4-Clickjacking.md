## 概述

Clickjacking（点击劫持，又称 UI 覆盖攻击）是攻击者把受害站点用透明 iframe 覆盖在诱饵页面上，让用户以为在点击诱饵，实际点击的是被隐藏的真实按钮。

```text
Clickjacking 的危害：
1. 诱导点击 —— 用户点「领取奖品」实际点了「转账确认」
2. 诱导授权 —— 用户点「播放视频」实际点了「授权相机/麦克风」
3. 诱导点赞/关注 —— 隐藏社交按钮被误点
4. 诱导改设置 —— 隐藏安全设置开关被关闭
```

```text
攻击本质：
1. 用户看到的是攻击者的页面
2. 用户点到的却是被透明 iframe 覆盖的受害站点
3. 受害者全程不知情，浏览器认为是用户主动点击
```

```js
// 攻击者页面的核心结构
// <div style="position:relative;width:500px;height:400px">
//   <div>点我领红包</div>
//   <iframe src="https://bank.com/confirm" style="
//     position:absolute; top:0; left:0;
//     opacity:0;             ← 透明
//     width:100%; height:100%;
//     z-index:9999;">        ← 盖在最上层
//   </iframe>
// </div>
// 用户点「领红包」，实际点到的是透明 iframe 里的「确认转账」
```

## Clickjacking 攻击原理

点击劫持靠的是 iframe 嵌入 + 视觉欺骗，浏览器会认为 iframe 里的点击是用户的真实操作。

```text
攻击步骤：
1. 攻击者建一个诱饵页面（领奖、播放、抽奖）
2. 用 iframe 嵌入受害站点，设置 opacity: 0 透明
3. 把透明 iframe 精确定位到诱饵按钮的正上方
4. 用户点击诱饵，实际命中 iframe 里的目标按钮
5. 因为点击发生在真实站点 iframe 内，Cookie 会正常携带
```

```text
进阶变种：
1. 光标劫持 —— 用假光标让用户看不清真实点击位置
2. 键盘劫持 —— iframe 捕获键盘输入（如密码框）
3. 双重 iframe —— 嵌套多层绕过简单检测
4. 拖放劫持 —— 诱导用户拖拽，触发隐蔽操作
```

```js
// 基础防护：检测自己是否被嵌入 iframe，是则跳出
if (window.top !== window.self) {
  window.top.location = window.location;  // 尝试跳回顶层
}
```

## iframe 与透明覆盖

iframe 是点击劫持的载体。理解它的嵌入行为，才能理解防护手段。

```html
<!-- 正常的 iframe 嵌入 -->
<iframe src="https://example.com/page" width="600" height="400"></iframe>
```

```text
iframe 嵌入的相关属性：
1. src —— 被嵌入的页面地址
2. sandbox —— 限制 iframe 能力（脚本、表单、弹窗等）
3. allow —— 授权 iframe 使用相机/麦克风等
4. style opacity/position —— 点击劫持正是用它做透明覆盖
```

```text
防护层面：
1. 服务端 —— 声明「我不允许被 iframe 嵌入」（本文重点）
2. 页面脚本 —— 检测被嵌入后跳出（frame-busting，不可靠）
3. iframe 使用者 —— 用 sandbox 限制第三方内容
```

```html
<!-- 作为 iframe 使用方，用 sandbox 限制不可信内容 -->
<iframe src="https://untrusted.com/widget"
        sandbox="allow-scripts allow-same-origin"></iframe>
```

## X-Frame-Options

X-Frame-Options 是经典的服务端响应头，直接告诉浏览器「这个页面能否被 iframe 嵌入」。

```text
X-Frame-Options 三值：
DENY        —— 任何情况都不允许被嵌入
SAMEORIGIN  —— 只允许同源页面嵌入
ALLOW-FROM uri —— 只允许指定来源嵌入（已废弃，兼容性差）
```

```js
// 服务端设置（Node/Express）
app.use((req, res, next) => {
  res.setHeader('X-Frame-Options', 'DENY');
  next();
});
```

```text
响应头实际效果：
X-Frame-Options: DENY
→ 浏览器拒绝在任何 iframe 中渲染该页面

X-Frame-Options: SAMEORIGIN
→ 同源的 iframe 可以嵌入，跨源嵌入被拒
```

```text
X-Frame-Options 局限：
1. ALLOW-FROM 已废弃，多浏览器支持不一致
2. 不支持「允许多个特定来源」的列表
3. 逐步被 CSP frame-ancestors 取代
4. 两者可同时设置，现代浏览器优先用 CSP
```

## CSP frame-ancestors

CSP 的 frame-ancestors 指令是 X-Frame-Options 的现代替代，功能更强，可指定多个来源。

```text
CSP frame-ancestors 语法：
Content-Security-Policy: frame-ancestors 'none'
Content-Security-Policy: frame-ancestors 'self'
Content-Security-Policy: frame-ancestors https://trusted.com https://*.example.com
```

```js
// 服务端设置
res.setHeader(
  'Content-Security-Policy',
  "frame-ancestors 'self' https://trusted.com"
);
```

```text
frame-ancestors 取值：
1. 'none' —— 不允许任何来源嵌入（等价 X-Frame-Options: DENY）
2. 'self' —— 只允许同源嵌入（等价 SAMEORIGIN）
3. 具体域名 —— 允许列出的来源，支持多个、支持通配符
```

```text
frame-ancestors vs X-Frame-Options：
1. frame-ancestors 支持多来源、通配符，更灵活
2. frame-ancestors 是 CSP 标准，持续演进
3. 两者都设置，浏览器优先遵循 frame-ancestors
4. 兼容旧浏览器可同时保留 X-Frame-Options
```

```html
<!-- 也可通过 meta 标签设置（注意：frame-ancestors 在 meta 中无效）
     必须通过响应头设置 -->
```

```text
注意：
frame-ancestors 指令无法通过 <meta> 标签生效，
必须通过 HTTP 响应头 Content-Security-Policy 设置。
```

## 应用场景实战

### 场景一：银行/支付页面防点击劫持

```js
// 敏感页面统一加最严格的防护头
app.use('/account', (req, res, next) => {
  res.setHeader('X-Frame-Options', 'DENY');
  res.setHeader('Content-Security-Policy', "frame-ancestors 'none'");
  next();
});
```

```text
为什么用 'none'/DENY：
1. 支付、转账、改密页面绝无被嵌入的正当需求
2. 最严格策略，杜绝任何形式的点击劫持
```

### 场景二：允许自家站点嵌入的页面

```js
// 需要被同源后台或受信域嵌入的页面
res.setHeader('Content-Security-Policy', "frame-ancestors 'self' https://admin.example.com");
```

```text
适用场景：
1. 自家管理后台嵌入业务页面
2. 受信合作伙伴的嵌入
3. 只列白名单来源，其余一律拒绝
```

## 最佳实践与踩坑记录

### 最佳实践

1. 全局默认设置 X-Frame-Options: DENY，按需放宽
2. 现代浏览器用 CSP frame-ancestors，替代 X-Frame-Options
3. 敏感页面（支付/改密）用 'none' 最严格策略
4. 需要嵌入时用白名单，别用通配符
5. 别依赖 frame-busting 脚本，它可被 sandbox 绕过

### 踩坑记录

```text
坑 1：用 frame-busting 脚本代替响应头
结论：页面仍能被嵌入劫持。
原因：攻击者给 iframe 加 sandbox 就能禁用脚本跳出。
解法：用服务端响应头（X-Frame-Options / CSP），别靠 JS。

坑 2：frame-ancestors 写进 meta 标签
结论：meta 里的 frame-ancestors 不生效。
原因：frame-ancestors 指令不支持 meta 标签，只能响应头。
解法：通过 HTTP 响应头设置。

坑 3：只用 X-Frame-Options 不用 CSP
结论：需要多来源嵌入时做不到精细控制。
原因：X-Frame-Options 只有 DENY/SAMEORIGIN，ALLOW-FROM 已废弃。
解法：用 CSP frame-ancestors 指定多来源白名单。

坑 4：误把第三方内容直接嵌入
结论：嵌入的第三方内容存在风险。
原因：不可信内容可能反向劫持或窃取信息。
解法：第三方 iframe 加 sandbox 属性限制能力。

坑 5：CSP 配置覆盖了 frame-ancestors
结论：多处设置 CSP，frame-ancestors 被覆盖失效。
原因：多个 CSP 头会取交集，配置冲突可能导致失效。
解法：统一 CSP 策略，frame-ancestors 单独测验证。
```
