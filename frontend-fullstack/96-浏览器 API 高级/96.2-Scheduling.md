## 概述

Scheduling（任务调度）是浏览器提供的一组「何时执行某段代码」的 API，核心是 requestAnimationFrame（下一帧渲染前执行）、requestIdleCallback（空闲时执行）、scheduler API（按优先级调度）。它们解决同一个问题：把工作安排在合适的时机，避免卡顿主线程、掉帧。

```text
三种调度 API 的定位：
1. requestAnimationFrame —— 动画/渲染，每帧渲染前执行，保证 60fps
2. requestIdleCallback —— 低优先级后台工作，浏览器空闲时执行
3. scheduler API —— 按优先级调度任务，可中止、可传递信号
```

```js
// 三种 API 对比：时机不同
requestAnimationFrame(() => console.log('下一帧渲染前'));
requestIdleCallback(() => console.log('浏览器空闲时'));
scheduler.postTask(() => console.log('按优先级调度'), { priority: 'user-visible' });
```

## requestAnimationFrame

requestAnimationFrame（rAF）在浏览器「下一帧渲染前」执行回调，回调里做的 DOM 修改会合并在同一帧渲染，避免一帧内多次重排。它是做动画、批量 DOM 更新的标准手段，由显示器刷新率驱动（通常 60Hz）。

```js
// 用 rAF 做动画：每帧更新位置，流畅不掉帧
let x = 0;
function animate(timestamp) {
  x += 2;
  box.style.transform = `translateX(${x}px)`;
  if (x < 500) {
    requestAnimationFrame(animate);  // 递归调度下一帧
  }
}
requestAnimationFrame(animate);

// rAF 回调参数 timestamp 是帧开始时间，可算帧间隔
let last = 0;
requestAnimationFrame(function loop(ts) {
  console.log('帧间隔', ts - last, 'ms');
  last = ts;
  requestAnimationFrame(loop);
});
```

```text
requestAnimationFrame 的要点：
1. 渲染前执行 —— 回调在绘制前，DOM 修改合并到本帧
2. 显示器同步 —— 由刷新率驱动，通常 60fps
3. 后台暂停 —— 标签页隐藏时自动暂停，省资源
4. 批量 DOM 更新 —— 多次修改合并成一次渲染
```

## requestIdleCallback

requestIdleCallback（rIC）在浏览器「空闲时段」执行低优先级任务，回调收到 deadline 参数，可判断剩余空闲时间（timeRemaining）决定干多少活。适合预加载、数据上报、后台计算等不紧急的工作。

```js
// 在空闲时段分批处理大任务，避免卡顿
const tasks = [...Array(10000).keys()];  // 一万个待处理项

function processQueue(deadline) {
  // 空闲时间够就继续干，不够就把控制权交还浏览器
  while (tasks.length > 0 && deadline.timeRemaining() > 1) {
    const task = tasks.shift();
    doWork(task);
  }
  if (tasks.length > 0) {
    requestIdleCallback(processQueue);  // 下个空闲时段继续
  }
}
requestIdleCallback(processQueue, { timeout: 2000 });
// timeout：最多等 2s 也必须执行，防任务饿死
```

```text
requestIdleCallback 的要点：
1. 空闲执行 —— 不保证立即跑，浏览器忙时延后
2. timeRemaining —— 判断还剩多少空闲时间，分批干
3. timeout —— 兜底，超过等待时限强制执行
4. 不适合 —— 不要放影响交互的紧急任务
```

## scheduler API

scheduler API（scheduler.postTask）是新的优先级调度接口，可给任务指定优先级（user-blocking / user-visible / background），返回 Promise，支持 AbortSignal 中止任务。它是更精细、可组合的任务调度方案，目前支持度还在逐步铺开。

```js
// 按优先级调度任务
scheduler.postTask(() => {
  console.log('高优先级：用户输入响应');
}, { priority: 'user-blocking' });

scheduler.postTask(() => {
  console.log('普通优先级：内容渲染');
}, { priority: 'user-visible' });

scheduler.postTask(() => {
  console.log('低优先级：日志上报');
}, { priority: 'background' });

// 支持中止
const controller = new AbortController();
scheduler.postTask(() => doWork(), {
  priority: 'background',
  signal: controller.signal,
});
controller.abort();  // 任务被中止
```

```text
scheduler API 的要点：
1. 优先级 —— user-blocking / user-visible / background 三档
2. 返回 Promise —— 可 await 任务完成
3. 可中止 —— signal 传 AbortSignal
4. 演进中 —— 是 rAF/rIC 的现代统一方案，注意兼容性
```

## 应用场景实战

### 场景一：长列表分批渲染不卡首屏

```js
// 一万条数据一次性渲染会卡死主线程
// 用 rIC 分批插入，保持交互流畅
const data = Array.from({ length: 10000 }, (_, i) => `item-${i}`);
const list = document.querySelector('#list');
let index = 0;

function renderBatch(deadline) {
  while (index < data.length && deadline.timeRemaining() > 1) {
    const li = document.createElement('li');
    li.textContent = data[index++];
    list.appendChild(li);
  }
  if (index < data.length) {
    requestIdleCallback(renderBatch);
  } else {
    console.log('渲染完成');
  }
}
requestIdleCallback(renderBatch);
```

### 场景二：滚动时批量更新 DOM

```js
// 滚动事件高频触发，直接在 scroll 里改 DOM 会掉帧
// 用 rAF 把多次滚动合并到下一帧处理
let ticking = false;
window.addEventListener('scroll', () => {
  if (ticking) return;          // 已有待处理帧，跳过
  ticking = true;
  requestAnimationFrame(() => {
    updateHeader(scrollY);      // 本帧只更新一次
    ticking = false;
  });
});

function updateHeader(y) {
  header.classList.toggle('stuck', y > 100);
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 动画和视觉更新用 rAF，别用 setTimeout（间隔与渲染不同步）
2. 低优先级后台工作用 rIC，分批处理，别一次干完
3. 滚动/resize 高频事件里用 rAF 节流，合并到下一帧
4. rIC 任务设 timeout 兜底，防低优先级任务饿死
5. scheduler.postTask 优先级按任务性质选，交互响应用 user-blocking

### 踩坑记录

```text
坑 1：动画用 setTimeout
结论：动画卡顿、掉帧，不同步刷新率。
原因：setTimeout 间隔与显示器刷新不同步，可能一帧内跑两次或漏帧。
解法：动画改用 requestAnimationFrame，由刷新率驱动。

坑 2：rIC 里做影响交互的任务
结论：页面交互响应延迟。
原因：rIC 只在空闲执行，紧急任务放里面会被拖到空闲才跑。
解法：紧急任务放同步/微任务，rIC 只放真正不紧急的后台工作。

坑 3：忘记取消 rAF
结论：组件销毁后动画仍在跑，浪费 CPU 还报错。
原因：没保存 rAF 返回的 id 并 cancelAnimationFrame。
解法：保存 id，销毁时 cancelAnimationFrame(id)。

坑 4：rIC 没有 timeout 导致任务饿死
结论：低优先级任务迟迟不执行。
原因：页面持续繁忙，rIC 一直等不到空闲时段。
解法：传 timeout 参数，超过时限强制执行。

坑 5：以为 rAF 是精确的 16.7ms
结论：帧间隔测量出来不是固定 16.7ms。
原因：高刷新率屏（120Hz）是 8.3ms，且有系统抖动。
解法：用回调的 timestamp 参数算真实帧间隔，别硬编码 16.7。
```
