## 概述

Performance API 是浏览器提供的性能测量接口，核心是 performance 对象，它能记录导航时序、资源加载、绘制时机、自定义打点等各类性能条目（PerformanceEntry）。配合 PerformanceObserver 可以监听这些条目的产生，是前端性能监控的数据基础。

```text
Performance API 的核心组成：
1. Performance API —— performance 对象，性能数据的统一入口
2. PerformanceMark —— 打标记，记录某个时间点
3. PerformanceMeasure —— 量测两个标记之间的耗时
4. PerformanceObserver —— 监听性能条目，新数据流入口
5. Navigation Timing —— 页面导航各阶段耗时
6. Resource Timing —— 每个资源加载的耗时
7. Paint Timing —— 首次绘制/首次内容绘制时间
8. Long Tasks —— 超过 50ms 的长任务
```

```js
// 一次拿到所有性能条目的基础用法
const entries = performance.getEntries();
console.log(entries);  // 导航、资源、绘制等所有条目
// 按类型取
console.log(performance.getEntriesByType('navigation'));
console.log(performance.getEntriesByType('resource'));
console.log(performance.getEntriesByType('paint'));
```

## Performance API

performance 对象是性能 API 的入口，挂在 window 上，提供时间基准（timeOrigin）、打点方法（mark/measure）、条目查询（getEntries*）、以及计时（now）。now() 是高精度时间，单位毫秒，适合测量代码耗时。

```js
// performance 的核心方法与属性
const now = performance.now();       // 页面加载到现在的毫秒数，高精度
const origin = performance.timeOrigin; // 时间基准点

// 时间精度：now() 比 Date.now() 精度高
console.log('now:', now);
console.log('timeOrigin:', origin);

// 测量一段代码耗时
const t0 = performance.now();
doExpensiveWork();
const t1 = performance.now();
console.log('耗时', (t1 - t0).toFixed(2), 'ms');
```

```text
Performance API 的要点：
1. now() —— 高精度时间戳，测耗时首选
2. timeOrigin —— 时间基准，各条目时间戳的统一参照
3. getEntries —— 查询所有/按类型/按名称的性能条目
4. 精度 —— 受浏览器安全策略限制，可能被四舍五入
```

## PerformanceMark

PerformanceMark 是在性能时间线上打一个命名标记，记录「某个时刻」。它常与 measure 配合：先 mark 起点、再 mark 终点，然后用 measure 算耗时。

```js
// 打标记：记录关键时间点
performance.mark('start-task');
doTask();
performance.mark('end-task');

// 读取标记
const marks = performance.getEntriesByType('mark');
marks.forEach(m => console.log(m.name, m.startTime));

// 清理标记
performance.clearMarks('start-task');
```

```text
PerformanceMark 的要点：
1. 命名标记 —— 记录关键时间点，如「首屏开始」「数据就绪」
2. 时间线 —— 标记落在 performance timeline 上
3. 与 measure 配合 —— 两个标记夹一段耗时
4. 清理 —— clearMarks 防标记堆积
```

## PerformanceMeasure

PerformanceMeasure 测量两个标记（或标记到当前时间）之间的耗时，生成一条 measure 条目。它让「某段逻辑花了多久」有了标准化的记录方式。

```js
// 测量两个标记之间的耗时
performance.mark('a');
// ... 中间的逻辑
performance.mark('b');
performance.measure('a-to-b', 'a', 'b');

// 读 measure 结果
const m = performance.getEntriesByName('a-to-b')[0];
console.log('a 到 b 耗时:', m.duration, 'ms');

// 不传终点则测到当前时间
performance.measure('a-to-now', 'a');
```

```text
PerformanceMeasure 的要点：
1. 夹耗时 —— 两个标记之间的 duration
2. 可命名 —— 生成一条具名 measure 条目
3. 可叠加 —— 多个 measure 组成分段的性能记录
4. 被 Observer 监听 —— measure 类型可被 PerformanceObserver 观察
```

## PerformanceObserver

PerformanceObserver 监听新产生的性能条目，是「事件驱动」的性能数据流入口，替代手动轮询 getEntries。它支持 buffered 获取历史条目，是采集 Web Vitals 的标准方式。

```js
// 监听绘制、长任务、自定义 measure
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.entryType, entry.name, entry.startTime);
  }
});

observer.observe({ type: 'paint', buffered: true });
observer.observe({ type: 'longtask', buffered: true });
observer.observe({ entryTypes: ['measure', 'mark'] });

// 不再需要时断开
// observer.disconnect();
```

```text
PerformanceObserver 的要点：
1. 事件驱动 —— 条目产生时回调，不用轮询
2. buffered —— 拿 observe 之前的历史条目
3. 多类型 —— type 或 entryTypes 指定监听范围
4. 用途 —— Web Vitals 采集、长任务监控、自定义打点上报
```

## Navigation Timing

Navigation Timing 记录页面导航从开始到加载完成的各阶段耗时：DNS、TCP、TLS、请求、响应、DOM 解析、load 事件等。通过 navigation 类型条目可拿到完整时间线，用于分析首屏加载瓶颈。

```js
// 读取导航时序
const nav = performance.getEntriesByType('navigation')[0];
// 关键阶段耗时（毫秒）
const timing = {
  dns: nav.domainLookupEnd - nav.domainLookupStart,          // DNS 解析
  tcp: nav.connectEnd - nav.connectStart,                    // TCP 连接
  tls: nav.secureConnectionStart ? nav.connectEnd - nav.secureConnectionStart : 0,
  request: nav.responseStart - nav.requestStart,             // 请求耗时
  response: nav.responseEnd - nav.responseStart,             // 响应耗时
  domContentLoaded: nav.domContentLoadedEventEnd,            // DOMContentLoaded
  load: nav.loadEventEnd,                                    // load 完成
};
console.table(timing);
```

```text
Navigation Timing 的要点：
1. 全阶段耗时 —— DNS/TCP/TLS/请求/响应/DOM/load
2. 定位瓶颈 —— 哪段长就优化哪段
3. 首屏分析 —— 结合 Paint Timing 判断首屏快慢
4. 单条目 —— navigation 类型只有一条
```

## Resource Timing

Resource Timing 记录页面加载的每个资源（脚本、样式、图片、XHR、fetch 等）的加载耗时与大小，用于定位「哪个资源拖慢了加载」。通过 resource 类型条目获取。

```js
// 找出最慢、最大的资源
const resources = performance.getEntriesByType('resource')
  .map(r => ({
    name: r.name,
    initiatorType: r.initiatorType,        // script/img/css/fetch...
    duration: r.duration,                  // 加载总耗时
    transferSize: r.transferSize,          // 传输大小
    startTime: r.startTime,
  }))
  .sort((a, b) => b.duration - a.duration);

console.table(resources.slice(0, 10));     // 最慢的 10 个
```

```text
Resource Timing 的要点：
1. 每个资源一条 —— 脚本/样式/图片/接口请求都有
2. initiatorType —— 资源类型（script/img/css/fetch）
3. transferSize —— 传输大小，判断体积问题
4. 定位慢资源 —— 按 duration 排序找拖后腿的
```

## Paint Timing

Paint Timing 记录浏览器首次绘制的时间点，最关键是 FP（First Paint，首次绘制）和 FCP（First Contentful Paint，首次内容绘制）。通过 paint 类型条目获取，是衡量「用户多久看到内容」的指标。

```js
// 读取绘制时机
const paint = performance.getEntriesByType('paint');
const fp = paint.find(p => p.name === 'first-paint');
const fcp = paint.find(p => p.name === 'first-contentful-paint');

console.log('FP:', fp?.startTime, 'ms');
console.log('FCP:', fcp?.startTime, 'ms');
// FCP 是 Web Vitals 相关的重要指标，代表首次内容可见
```

```text
Paint Timing 的要点：
1. FP —— 首次绘制，白屏结束
2. FCP —— 首次内容绘制，用户看到第一个内容
3. 首屏体验 —— FCP 越小，白屏越短
4. 采集 —— 用 PerformanceObserver + buffered 拿
```

## Long Tasks

Long Tasks 是执行时间超过 50ms 的任务，会阻塞主线程导致掉帧、交互卡顿。通过 longtask 类型条目监听，可定位是哪些长任务卡了主线程。

```js
// 监听长任务
const observer = new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    console.log('长任务:', entry.startTime, '持续', entry.duration, 'ms');
    // entry.attribution 可看归属（框架/脚本）
    const a = entry.attribution?.[0];
    if (a) console.log('来源:', a.containerType, a.containerName);
  });
});
observer.observe({ type: 'longtask', buffered: true });
```

```text
Long Tasks 的要点：
1. 阈值 50ms —— 超过即长任务，会阻塞主线程
2. 掉帧根源 —— 长任务导致渲染延迟，INP 恶化
3. 归属 —— attribution 定位是哪个脚本/框架引起
4. 优化 —— 拆分长任务，切成小于 50ms 的小块
```

## 应用场景实战

### 场景一：采集核心 Web Vitals 并上报

```js
// 用 PerformanceObserver 采集 LCP / CLS / FID，发到监控后端
function report(metric) {
  navigator.sendBeacon('/api/metrics', JSON.stringify(metric));
}

new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    // LCP：largest-contentful-paint
    report({ type: 'LCP', value: entry.startTime });
  });
}).observe({ type: 'largest-contentful-paint', buffered: true });

new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    // CLS：layout-shift，累加不带 recentInput 的偏移
    if (!entry.hadRecentInput) report({ type: 'CLS', value: entry.value });
  });
}).observe({ type: 'layout-shift', buffered: true });
```

### 场景二：定位首屏加载瓶颈

```js
// 分阶段测量，找出首屏慢在哪一段
const nav = performance.getEntriesByType('navigation')[0];
const fcp = performance.getEntriesByType('paint')
  .find(p => p.name === 'first-contentful-paint');

console.log('网络+响应:', nav.responseEnd, 'ms');
console.log('FCP:', fcp?.startTime, 'ms');
console.log('DOM 可交互:', nav.domInteractive, 'ms');

// 再看资源：谁在阻塞
performance.getEntriesByType('resource')
  .filter(r => r.initiatorType === 'script')
  .sort((a, b) => b.duration - a.duration)
  .forEach(r => console.log(r.name, r.duration.toFixed(0), 'ms'));
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 PerformanceObserver 而非轮询 getEntries，事件驱动不遗漏
2. 采 Web Vitals 时给 observe 加 buffered: true，拿历史条目
3. 自定义打点用 mark + measure，标准化记录耗时
4. 长任务监控是定位卡顿的第一手数据，尽早接入
5. 上报用 sendBeacon，页面卸载时也能发出
6. 注意精度限制，别依赖亚毫秒级时间

### 踩坑记录

```text
坑 1：PerformanceObserver 漏掉早期数据
结论：observer 建立前的 FCP/LCP 拿不到。
原因：默认只监听 observe 之后的条目。
解法：observe 传 buffered: true，获取历史缓冲条目。

坑 2：LCP 用 startTime 而非 entry 最终值
结论：LCP 值偏小或不准。
原因：LCP 可能多次更新，最后一条才是最终 LCP。
解法：监听 largest-contentful-paint 取最后一条的 startTime。

坑 3：上报用 fetch 而非 sendBeacon
结论：页面卸载/跳转时埋点数据丢失。
原因：fetch 在页面卸载时可能被中断，请求发不出去。
解法：性能上报用 navigator.sendBeacon，卸载时可靠发送。

坑 4：把 transferSize 当资源真实大小
结论：资源大小判断错误。
原因：transferSize 含响应头开销，且缓存命中时为 0。
解法：看 encodedBodySize（压缩后）和 decodedBodySize（解压后）。

坑 5：忽略 Long Tasks 阈值
结论：卡顿问题找不到根源。
原因：没监听 longtask，不知道主线程被谁占满。
解法：接入 longtask 监听，配合 attribution 定位卡顿脚本。
```
