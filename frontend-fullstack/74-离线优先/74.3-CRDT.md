## 概述

CRDT（Conflict-free Replicated Data Type，无冲突复制数据类型）是一类数据结构，多个副本可以各自独立修改、离线编辑，合并时不需要中心协调就自动收敛到一致状态。它的核心价值是「不用解决冲突，因为设计上就不产生冲突」——协作编辑、离线同步的底层都靠它。

```text
CRDT 家族核心成员：
1. CRDT —— 无冲突复制数据类型的总称，合并必然收敛
2. LWW —— Last Write Wins，后写覆盖，用时间戳定胜负
3. G-Counter —— 只增计数器，天然无冲突
4. PN-Counter —— 可增可减计数器
5. OR-Set —— 可观察移除集合，删除不丢
6. Vector Clock —— 向量时钟，描述事件的因果先后
7. Conflict Free Replication —— 无冲突复制，CRDT 的设计目标
```

```js
// CRDT 的核心契约：任意顺序合并，结果都收敛
// merge(merge(a, b), c) === merge(a, merge(b, c))
function merge(a, b) {
  return a.join(b); // 每个 CRDT 定义自己的 join 规则
}
```

## CRDT

CRDT 是一类「合并操作满足交换律、结合律、幂等律」的数据结构。因为合并顺序不影响最终结果，多个副本可以并行修改、离线编辑、乱序同步，最后 join 一下自然收敛。它把「冲突解决」从应用层下沉到数据结构本身。

```text
CRDT 的关键点：
1. 无冲突 —— 设计上保证合并不会冲突
2. 收敛性 —— 副本交换信息后最终一致
3. 可离线 —— 副本独立修改，之后合并
4. 两类实现 —— 基于状态（state-based）和基于操作（op-based）
```

```text
状态型 CRDT 的合并定义（join 需满足）：
1. 交换律 —— merge(a, b) === merge(b, a)
2. 结合律 —— merge(merge(a, b), c) === merge(a, merge(b, c))
3. 幂等律 —— merge(a, a) === a
```

```js
// 状态型 CRDT 的骨架：每个副本持有 state，合并用 join
class GCounter {
  constructor(id, size) {
    this.id = id;
    this.counts = new Array(size).fill(0); // 每个副本一个计数位
  }
  increment() { this.counts[this.id] += 1; }
  value() { return this.counts.reduce((a, b) => a + b, 0); }
  join(other) { // 逐位取最大值
    this.counts = this.counts.map((c, i) => Math.max(c, other.counts[i]));
  }
}
```

CRDT 是协作编辑（文本、计数器、集合）和离线同步的通用底座，代价是存储开销和实现复杂度比普通数据结构高。

## LWW

LWW（Last Write Wins，后写覆盖）是最简单的冲突解决：给每个值打上时间戳，合并时时间戳新的覆盖旧的。它实现简单、语义直观，适合「后写的本来就该生效」的场景，但依赖时钟，且会丢并发更新。

```text
LWW 的关键点：
1. 后写覆盖 —— 时间戳大的赢
2. 实现简单 —— 每个值带时间戳即可
3. 依赖时钟 —— 时钟偏差会误判先后
4. 丢并发更新 —— 同刻写两处，只留一个
```

```js
// LWW 寄存器：带时间戳的值，合并取时间戳新的
class LWWRegister {
  constructor(value = null, ts = 0) {
    this.value = value;
    this.timestamp = ts;
  }
  set(value, ts = Date.now()) {
    if (ts >= this.timestamp) {
      this.value = value;
      this.timestamp = ts;
    }
  }
  join(other) {
    if (other.timestamp > this.timestamp) {
      this.value = other.value;
      this.timestamp = other.timestamp;
    }
  }
}
```

LWW 适合「字段型」数据（用户昵称、状态标记），不适合需要保留所有并发修改的场景（如文档协同编辑）。

## G-Counter

G-Counter（Grow-only Counter，只增计数器）只能加不能减，每个副本维护自己的计数位，合并时逐位取最大值。因为「加」操作单调递增，合并永远无冲突，总计数就是所有副本计数之和。

```text
G-Counter 的关键点：
1. 只增不减 —— 没有减法就没有冲突
2. 每副本一位 —— 各副本只增自己的计数位
3. 合并取最大 —— join 逐位取 max
4. 读值求和 —— 总数是各位之和
```

```js
// G-Counter：两个副本并发 +1，合并后总数正确
class GCounter {
  constructor(replicaId, replicaCount) {
    this.id = replicaId;
    this.counts = new Array(replicaCount).fill(0);
  }
  inc() { this.counts[this.id] += 1; }
  value() { return this.counts.reduce((a, b) => a + b, 0); }
  join(other) {
    this.counts = this.counts.map((c, i) => Math.max(c, other.counts[i]));
  }
}

const a = new GCounter(0, 2);
const b = new GCounter(1, 2);
a.inc(); a.inc(); // a 加了两次
b.inc();          // b 加了一次
a.join(b); b.join(a);
console.log(a.value()); // 3
```

G-Counter 适合点赞数、访问量这类只增的计数，缺点是只能加不能减。

## PN-Counter

PN-Counter（Positive-Negative Counter）扩展 G-Counter，用两个 G-Counter 分别记录「加」和「减」，解决只增计数器的减操作问题。计数值 = 增量计数 - 减量计数，合并时两个分量各自取最大。

```text
PN-Counter 的关键点：
1. 可增可减 —— 两个 G-Counter 分别记加和减
2. 值 = 加 - 减 —— 增量减量各自收敛
3. 合并分量独立 —— 加分量、减分量分别 join
4. 仍无冲突 —— 两个分量都是单调的
```

```js
// PN-Counter：可增可减的无冲突计数器
class PNCounter {
  constructor(replicaId, replicaCount) {
    this.inc = new Array(replicaCount).fill(0); // 增量
    this.dec = new Array(replicaCount).fill(0); // 减量
    this.id = replicaId;
  }
  increment() { this.inc[this.id] += 1; }
  decrement() { this.dec[this.id] += 1; }
  value() {
    const plus = this.inc.reduce((a, b) => a + b, 0);
    const minus = this.dec.reduce((a, b) => a + b, 0);
    return plus - minus;
  }
  join(other) {
    this.inc = this.inc.map((c, i) => Math.max(c, other.inc[i]));
    this.dec = this.dec.map((c, i) => Math.max(c, other.dec[i]));
  }
}
```

PN-Counter 适合库存、在线人数这类可增可减的计数，是 G-Counter 的实用升级。

## OR-Set

OR-Set（Observed-Remove Set，可观察移除集合）解决普通集合的「删除丢失」问题：元素删除时打上删除标记而非物理移除，合并时只有「所有副本都删了」才真正删掉。它保证「一个副本加了元素、另一个删了，合并后不丢」。

```text
OR-Set 的关键点：
1. 删除不物理移除 —— 删除打标记，不是抹掉
2. 加删并发安全 —— 一边加一边删，合并后保留
3. 标记全局唯一 —— 每次添加带唯一 tag
4. 全删才删 —— 所有副本都删除才真正移除
```

```js
// OR-Set：添加带唯一 tag，删除只删对应 tag
class ORSet {
  constructor() { this.elements = new Map(); } // value -> Set(tags)
  add(value, tag = crypto.randomUUID()) {
    if (!this.elements.has(value)) this.elements.set(value, new Set());
    this.elements.get(value).add(tag);
  }
  remove(value) { this.elements.delete(value); }
  join(other) {
    for (const [value, tags] of other.elements) {
      if (!this.elements.has(value)) this.elements.set(value, new Set());
      const merged = new Set([...this.elements.get(value), ...tags]);
      this.elements.set(value, merged);
    }
  }
  has(value) { return this.elements.has(value) && this.elements.get(value).size > 0; }
}
```

OR-Set 适合「购物车、标签、协作成员」这类集合数据，避免并发删除把数据删没。

## Vector Clock

Vector Clock（向量时钟）用一个「每副本一个计数器」的向量描述事件的因果顺序：每个副本发生事件时自增自己的分量，同步时合并向量。它不直接给数据排序，而是回答「事件 A 和事件 B 谁先谁后，还是并发」。

```text
Vector Clock 的关键点：
1. 每副本一维 —— 向量长度等于副本数
2. 本地事件自增 —— 本副本分量 +1
3. 合并取最大 —— 逐维取 max
4. 判断因果 —— 可判断先后、并发、相等
```

```js
// 向量时钟：判断两个事件的因果顺序
class VectorClock {
  constructor(id, size) { this.id = id; this.clock = new Array(size).fill(0); }
  tick() { this.clock[this.id] += 1; }
  merge(other) {
    this.clock = this.clock.map((c, i) => Math.max(c, other.clock[i]));
  }
  // 判断 this 是否先于 other
  happensBefore(other) {
    let less = false;
    for (let i = 0; i < this.clock.length; i++) {
      if (this.clock[i] > other.clock[i]) return false;
      if (this.clock[i] < other.clock[i]) less = true;
    }
    return less;
  }
}
```

向量时钟是 CRDT 的「观察者」，常用来判断两个副本的状态是否有因果依赖，辅助冲突检测。

## Conflict Free Replication

Conflict Free Replication（无冲突复制）是 CRDT 要达到的目标：多个副本自由复制、独立修改，合并时不需要任何协调就收敛一致。它回答的是「怎么让分布式/离线场景下，数据既不冲突又最终一致」这个根本问题。

```text
无冲突复制的关键点：
1. 副本独立修改 —— 各端想改就改，不等别人
2. 合并自动收敛 —— join 后各副本状态一致
3. 无需协调 —— 不用中心服务器仲裁
4. 最终一致 —— 只要副本充分交换，最终一致
```

```js
// 无冲突复制：三个副本乱序合并，最终一致
const r1 = new PNCounter(0, 3);
const r2 = new PNCounter(1, 3);
const r3 = new PNCounter(2, 3);

r1.increment(); r2.increment(); r3.decrement();
// 任意顺序两两合并，最终值都等于 2 - 1 = 1
r1.join(r2); r1.join(r3);
r2.join(r3); r2.join(r1);
r3.join(r1); r3.join(r2);
console.log(r1.value(), r2.value(), r3.value()); // 1 1 1
```

无冲突复制的代价是：数据结构要专门设计（普通数据做不到），且存储开销通常比普通结构高。换来的是「离线自由编辑 + 自动收敛」的能力。

## 应用场景实战

### 场景一：协作点赞计数器

```js
// 多人协作点赞：PN-Counter 各端独立 +1/-1，合并自动收敛
class LikeCounter {
  constructor(userId, totalUsers) {
    this.userId = userId;
    this.inc = new Array(totalUsers).fill(0);
    this.dec = new Array(totalUsers).fill(0);
  }
  like() { this.inc[this.userId] += 1; }
  unlike() { this.dec[this.userId] += 1; }
  count() {
    const up = this.inc.reduce((a, b) => a + b, 0);
    const down = this.dec.reduce((a, b) => a + b, 0);
    return up - down;
  }
  merge(other) {
    this.inc = this.inc.map((c, i) => Math.max(c, other.inc[i]));
    this.dec = this.dec.map((c, i) => Math.max(c, other.dec[i]));
  }
}
```

### 场景二：协作标签集合（OR-Set 防删丢）

```js
// 多个协作者同时给任务打标签，删除不会误删别人的标签
class TagSet {
  constructor() { this.tags = new Map(); }
  add(tag) {
    if (!this.tags.has(tag)) this.tags.set(tag, new Set());
    this.tags.get(tag).add(crypto.randomUUID());
  }
  remove(tag) { this.tags.delete(tag); }
  merge(other) {
    for (const [tag, ids] of other.tags) {
      if (!this.tags.has(tag)) this.tags.set(tag, new Set());
      this.tags.set(tag, new Set([...this.tags.get(tag), ...ids]));
    }
  }
  list() { return [...this.tags.keys()]; }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 只增的计数用 G-Counter，可增可减用 PN-Counter，别用 LWW 硬凑计数
2. 集合类数据（标签、成员）用 OR-Set，删除打标记防并发丢失
3. 字段型简单数据用 LWW 即可，前提是「后写覆盖」语义可接受
4. 判断因果先后用向量时钟，别用单一时间戳
5. 协作编辑文本用序列 CRDT 或 OT，别自己造轮子
6. CRDT 的存储和传输开销高于普通结构，按数据量评估是否值得

### 踩坑记录

```text
坑 1：用 LWW 做计数器
结论：两个客户端并发点赞，合并后只算了一次。
原因：LWW 是覆盖语义，后写覆盖先写，并发 +1 丢了一个。
解法：计数用 G-Counter / PN-Counter，合并逐位取最大。

坑 2：普通集合删除丢数据
结论：A 端加了元素，B 端同时删，合并后元素没了。
原因：普通 Set 删除是物理移除，加删并发时删除覆盖了添加。
解法：用 OR-Set，删除打标记，加删并发合并后保留元素。

坑 3：时间戳判断并发冲突
结论：时钟偏差导致「后写」被判成「先写」被覆盖。
原因：单点时间戳无法表达并发关系，时钟还可能不准。
解法：用向量时钟或版本号判断因果，别依赖墙钟时间。

坑 4：CRDT 元数据无限增长
结论：长时间协作后，删除标记、向量时钟体积越来越大。
原因：OR-Set 的删除标记、操作的日志从不清理。
解法：定期做 GC/压缩，合并历史状态，丢弃已收敛的元数据。

坑 5：副本数固定导致向量时钟扩不了
结论：新加入协作者后，向量时钟维度不够用。
原因：向量时钟初始化时写死了副本数量。
解法：用动态向量时钟或点阵时钟（Dotted Version Vector）支持动态副本。
```
