## 概述

Offline First（离线优先）把「离线可用」从异常分支变成默认设计：应用在断网时依然能启动、能读数据、能提交操作，网络恢复后再自动同步。它不是「偶尔支持离线」，而是把本地当作第一数据层，服务端只是最终的同步目标。

```text
Offline First 的四大支柱：
1. Offline Cache —— 缓存应用壳和资源，离线能打开页面
2. Local Database —— 本地数据库存业务数据，离线能读写
3. Sync Queue —— 同步队列记录待同步的写操作
4. Conflict Resolution —— 离线产生的修改如何与服务端合并
```

```js
// 离线优先应用的最小骨架
async function bootstrap() {
  // 1. 注册 Service Worker 缓存应用壳
  await navigator.serviceWorker.register('/sw.js');
  // 2. 打开本地数据库
  const db = await openDB('app-db');
  // 3. 数据读写先走本地，再异步同步
  return { db, sync: syncQueue };
}
```

## Offline Cache

Offline Cache 负责「断网时页面还能打开」：用 Service Worker 拦截请求，把 HTML、JS、CSS、图片这些应用壳缓存起来，网络不可用时从缓存返回。它是离线体验的地基——没有它，应用连页面都渲染不出来。

```text
Offline Cache 的关键点：
1. Service Worker 拦截 —— 在请求层做缓存控制
2. 缓存策略 —— Cache First / Network First / Stale While Revalidate
3. 应用壳 —— 先缓存骨架，保证首屏可离线
4. 版本管理 —— 缓存要能更新、能清理
```

```js
// sw.js：应用壳缓存 + 运行时缓存
const SHELL = ['/', '/index.html', '/app.js', '/app.css'];

self.addEventListener('install', (e) => {
  e.waitUntil(
    caches.open('shell-v1').then(c => c.addAll(SHELL))
  );
});

self.addEventListener('fetch', (e) => {
  e.respondWith(
    caches.match(e.request).then(hit =>
      hit || fetch(e.request).then(res => {
        const copy = res.clone();
        caches.open('runtime-v1').then(c => c.put(e.request, copy));
        return res;
      })
    )
  );
});
```

缓存策略的选择很关键：应用壳用 Cache First，API 数据用 Network First 或 Stale While Revalidate，别一刀切。

## Local Database

Local Database 是「断网时数据还能读写」的载体：用 IndexedDB 存业务数据，让用户离线也能看列表、写笔记、改配置。它和 Offline Cache 的分工是：Cache 管资源加载，Database 管业务数据。

```text
Local Database 的关键点：
1. IndexedDB —— 浏览器内置，容量大、异步、支持索引
2. 结构化数据 —— 存对象而非字符串，能按索引查询
3. 事务 —— 读写一致性靠事务保证
4. 封装库 —— idb / Dexie 简化原生 API
```

```js
// 用 Dexie 定义本地数据库
import Dexie from 'dexie';

const db = new Dexie('offline-db');
db.version(1).stores({
  notes: 'id, title, updatedAt, sync', // 主键 + 索引
});

// 离线写入
async function addNote(note) {
  await db.notes.put({ ...note, sync: 'pending', updatedAt: Date.now() });
}

// 离线查询
const notes = await db.notes.where('sync').equals('pending').toArray();
```

本地数据库承担了「离线期间的所有读写」，也埋下了同步的伏笔：每个写操作都要记录状态，才能在恢复网络后对齐。

## Sync Queue

Sync Queue（同步队列）记录所有「本地已做、服务端还没确认」的操作。在线时队列为空、写完即同步；离线时写操作进队列，网络恢复后按顺序重放。它是 Offline First 的核心机制——把「离线期间的修改」变成可恢复的清单。

```text
Sync Queue 的关键点：
1. 记录待同步操作 —— 每次本地写都入队，带操作类型和负载
2. 顺序重放 —— 恢复网络后按入队顺序发送
3. 状态流转 —— pending → syncing → synced / failed
4. 失败重试 —— 同步失败保留在队列，稍后重试
```

```js
// 同步队列：离线入队，恢复后按序重放
const queue = [];

function enqueue(op) {
  queue.push({ id: crypto.randomUUID(), op, status: 'pending' });
  db.syncOps.put({ ...op, status: 'pending' }); // 持久化队列
  if (navigator.onLine) flush();
}

async function flush() {
  const ops = await db.syncOps.where('status').equals('pending').toArray();
  for (const op of ops) {
    try {
      await fetch(op.op.url, { method: op.op.method, body: op.op.body });
      await db.syncOps.update(op.id, { status: 'synced' });
    } catch (e) {
      await db.syncOps.update(op.id, { status: 'failed' });
    }
  }
}

window.addEventListener('online', flush);
```

队列要持久化（存 IndexedDB），否则刷新页面队列就丢了，离线期间的修改全部蒸发。

## Conflict Resolution

Conflict Resolution 处理「离线修改与线上修改撞车」：用户离线改了一篇文章，别人在线也改了同一篇，同步时两份修改冲突。离线场景下冲突不可避免，关键是选对策略，把「丢数据」的风险降到最低。

```text
冲突解决策略：
1. Last Write Wins —— 后写覆盖，简单但可能丢更新
2. 版本号比较 —— 基于版本拒绝覆盖旧数据
3. 字段级合并 —— 只冲突字段需要处理
4. CRDT —— 数学上保证多端收敛
```

```js
// 基于版本号的冲突检测
async function syncNote(note) {
  const res = await fetch(`/api/notes/${note.id}`, {
    method: 'PUT',
    body: JSON.stringify({ ...note, baseVersion: note.baseVersion }),
  });
  if (res.status === 409) {
    // 冲突：本地是基于旧版本改的，服务端已更新
    return { conflict: true, remote: await res.json() };
  }
  return { conflict: false };
}
```

离线优先的冲突解决通常和同步队列绑定：重放队列时逐条检测版本冲突，冲突的操作留待用户或规则仲裁，而不是静默覆盖。

## 应用场景实战

### 场景一：离线笔记应用

```js
// 完整离线笔记：本地写、本地读、恢复后同步
import Dexie from 'dexie';

const db = new Dexie('notes-app');
db.version(1).stores({ notes: 'id, updatedAt, sync' });

async function saveNote(id, content) {
  await db.notes.put({ id, content, updatedAt: Date.now(), sync: 'pending' });
  if (navigator.onLine) await syncNotes();
}

async function syncNotes() {
  const pending = await db.notes.where('sync').equals('pending').toArray();
  for (const note of pending) {
    try {
      await fetch(`/api/notes/${note.id}`, {
        method: 'PUT',
        body: JSON.stringify(note),
      });
      await db.notes.update(note.id, { sync: 'synced' });
    } catch (e) {
      break; // 网络又断了，下次再同步
    }
  }
}

window.addEventListener('online', syncNotes);
```

### 场景二：离线可用的列表页（应用壳 + 数据缓存）

```js
// 注册 Service Worker + 运行时缓存接口数据
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js');
}

// sw.js 里对 API 数据用 Network First：在线拿最新，离线读缓存
self.addEventListener('fetch', (e) => {
  if (e.request.url.includes('/api/')) {
    e.respondWith(
      fetch(e.request)
        .then(res => {
          const copy = res.clone();
          caches.open('api-v1').then(c => c.put(e.request, copy));
          return res;
        })
        .catch(() => caches.match(e.request)) // 离线回退缓存
    );
  }
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 应用壳用 Cache First，API 数据用 Network First 或 Stale While Revalidate，分开定策略
2. 本地数据库统一用 IndexedDB，配合 Dexie/idb 封装，别用 Local Storage 存业务数据
3. 同步队列必须持久化，写操作先落库再入队，刷新页面不丢
4. 每个写操作记录 sync 状态（pending/synced/failed），同步是幂等的
5. 离线场景用版本号或 CRDT 做冲突解决，别静默覆盖
6. 监听 online/offline 事件驱动同步，同步完成后给用户可见反馈

### 踩坑记录

```text
坑 1：缓存策略一刀切导致数据过期
结论：列表页离线能开，但显示的还是几天前的旧数据。
原因：API 数据也用了 Cache First，永远命中缓存不更新。
解法：API 用 Network First，在线拿最新；静态资源才用 Cache First。

坑 2：同步队列不持久化
结论：离线改了几条数据，刷新页面后全没了。
原因：队列只存在内存里，刷新即清空。
解法：队列存 IndexedDB，恢复时从持久层读取重放。

坑 3：同步操作非幂等导致重复数据
结论：网络抖动重试后，同一条数据被重复创建。
原因：POST 请求重放没有幂等键，服务端无法去重。
解法：写操作带上幂等键（uuid），服务端按幂等键去重。

坑 4：忽略冲突静默覆盖
结论：离线改的字段把别人在线改的字段整个覆盖了。
原因：同步用 Last Write Wins，没有检测版本冲突。
解法：同步时带 baseVersion，409 冲突时走合并或提示用户。

坑 5：Service Worker 缓存无法更新
结论：发了新版本，用户看到的还是旧页面。
原因：缓存 key 没变，浏览器一直命中旧缓存。
解法：缓存名带版本号（shell-v2），activate 里清理旧缓存。
```
