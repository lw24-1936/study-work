## 概述

离线数据同步关注「本地和服务端之间的数据如何高效、安全地对齐」。离线期间本地积累了大量修改，恢复网络后要把它同步上去，同时把服务端的新变化拉下来——这个过程要解决三个问题：只传变化的部分（Delta/Incremental）、失败能安全重试（Retry/Idempotency）、多端修改不冲突（Version/Timestamp）。

```text
离线同步要解决的六个问题：
1. Delta Sync —— 只同步变化的部分，不传全量
2. Incremental Sync —— 增量同步，按游标/游标推进
3. Retry —— 失败重试机制，网络恢复后继续
4. Idempotency —— 幂等，重试不产生重复副作用
5. Version —— 版本号，判断数据新旧和冲突
6. Timestamp —— 时间戳，记录修改时间和顺序
```

```js
// 一次可靠的离线同步调用
async function safeSync(op) {
  const res = await fetch(op.url, {
    method: op.method,
    headers: { 'Idempotency-Key': op.id }, // 幂等键
    body: JSON.stringify({ ...op.payload, version: op.version }),
  });
  if (res.status === 409) return { conflict: true };
  return { ok: true };
}
```

## Delta Sync

Delta Sync（增量同步，差量同步）只传输「发生变化的数据」，而不是每次都全量拉取。客户端带上自己已知的最后状态（游标或时间戳），服务端只返回此后的变化。它把同步的数据量从「全部」压到「增量」，是离线同步省流量的关键。

```text
Delta Sync 的关键点：
1. 只传变化 —— 客户端给游标，服务端回增量
2. 游标推进 —— 用时间戳或自增 id 标记进度
3. 首次全量 —— 第一次同步没有游标，拉全量
4. 省带宽 —— 后续同步只传少量变化
```

```js
// 增量拉取：带上游标，只拿新变化
async function fetchDelta(cursor) {
  const url = cursor
    ? `/api/changes?since=${cursor}`
    : '/api/changes'; // 首次无游标拉全量
  const { changes, nextCursor } = await fetch(url).then(r => r.json());
  applyChanges(changes);
  localStorage.setItem('sync-cursor', nextCursor);
}
```

Delta Sync 的前提是服务端能提供「按游标取变化」的接口，游标本身要可靠持久化，否则会重复或漏数据。

## Incremental Sync

Incremental Sync（增量同步）强调「状态持续推进，而不是每次从头开始」：用游标、页码或序列号记录已经同步到哪里，下次从这里继续。它和 Delta Sync 侧重点不同——Delta 强调「传差量」，Incremental 强调「进度可恢复、可续传」。

```text
Incremental Sync 的关键点：
1. 进度可恢复 —— 游标持久化，中断后从断点续传
2. 序列号推进 —— 用自增 id 或时间戳做游标
3. 分批拉取 —— 大增量分批，避免一次拉爆
4. 幂等应用 —— 应用变化要能重复执行不重复
```

```js
// 增量同步：分批拉取，游标持续推进
async function incrementalSync() {
  let cursor = Number(localStorage.getItem('cursor') || 0);
  while (true) {
    const { items, nextCursor, hasMore } = await fetch(
      `/api/records?after=${cursor}&limit=100`
    ).then(r => r.json());
    await applyRecords(items);
    cursor = nextCursor;
    localStorage.setItem('cursor', String(cursor));
    if (!hasMore) break;
  }
}
```

增量同步配合批量处理，能把一次大数据同步拆成多次可控的小步，避免内存和网络一次性打满。

## Retry

Retry（重试）是同步失败的兜底机制：网络抖动、服务端 5xx、超时都可能导致同步失败，重试机制决定「何时、以什么节奏、重试多少次」。好的重试要带退避策略，否则失败重试会放大请求压力。

```text
Retry 的关键点：
1. 退避策略 —— 指数退避、抖动，避免重试风暴
2. 次数上限 —— 无限重试会一直失败一直打
3. 可重试判断 —— 4xx 业务错误不该重试，5xx/网络错误才重试
4. 持久化 —— 重试队列要落盘，刷新不丢
```

```js
// 带指数退避的重试
async function retryFetch(url, options, { maxRetries = 5 } = {}) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    try {
      const res = await fetch(url, options);
      if (res.status >= 500) throw new Error('server error');
      return res; // 4xx 不重试，直接返回
    } catch (e) {
      const delay = Math.min(1000 * 2 ** attempt, 30_000) + Math.random() * 500;
      await new Promise(r => setTimeout(r, delay)); // 指数退避 + 抖动
    }
  }
  throw new Error('max retries exceeded');
}
```

Retry 和幂等必须成对出现：重试会重复发送请求，如果操作不幂等，重试就会产生重复数据。

## Idempotency

Idempotency（幂等）指同一个操作执行一次和执行多次，结果相同。离线同步里重试几乎不可避免，所以每个写操作都要设计成幂等——要么服务端天然幂等，要么靠幂等键去重，否则重试就会重复下单、重复扣款。

```text
Idempotency 的关键点：
1. 幂等键 —— 客户端为每次操作生成唯一 id，服务端按 id 去重
2. 天然幂等 —— PUT/DELETE 天然幂等，POST 需要幂等键
3. 去重存储 —— 服务端保存已处理的幂等键
4. 重试安全 —— 有了幂等键，重试就不会重复副作用
```

```js
// 幂等写操作：带上幂等键
async function createOrder(order) {
  const idempotencyKey = order.clientId; // 客户端生成的唯一 id
  return fetch('/api/orders', {
    method: 'POST',
    headers: { 'Idempotency-Key': idempotencyKey },
    body: JSON.stringify(order),
  });
}

// 重试同一订单，服务端按幂等键返回第一次的结果，不重复创建
```

```text
服务端幂等处理逻辑（伪代码）：
if (exists(idempotencyKey)) return storedResponse;
result = process(request);
store(idempotencyKey, result);
return result;
```

幂等键要客户端生成并持久化，和同步队列里的操作一一对应，这样重试多少次都不会重复。

## Version

Version（版本号）给数据打上「修改代次」标记，用来判断数据新旧、检测并发冲突。每次修改版本号递增，同步时比较版本号：本地基于旧版本修改，服务端已经到新版本，说明有人抢先改过，产生冲突。

```text
Version 的关键点：
1. 单调递增 —— 每次修改版本号 +1
2. 乐观并发控制 —— 带版本号提交，版本不符拒绝
3. 冲突检测 —— 版本号不一致说明并发修改
4. 覆盖保护 —— 旧版本不允许覆盖新版本
```

```js
// 基于版本号的乐观并发控制
async function updateWithVersion(id, patch) {
  const local = await db.get('records', id);
  const res = await fetch(`/api/records/${id}`, {
    method: 'PUT',
    body: JSON.stringify({ ...patch, version: local.version }),
  });
  if (res.status === 409) {
    const remote = await res.json();
    return merge(local, remote); // 冲突，走合并
  }
  await db.put('records', { ...patch, version: local.version + 1 });
}
```

版本号是乐观并发控制的基础：读时记版本，写时带版本，版本不符就说明有并发冲突。

## Timestamp

Timestamp（时间戳）记录数据的修改时间，用于排序、判断先后、做增量同步的游标。但时间戳有两个天然缺陷：多端时钟可能不同步，同一毫秒可能多次修改，所以时间戳更适合做「增量拉取的游标」，不适合单独做「冲突仲裁」。

```text
Timestamp 的关键点：
1. 记录修改时间 —— updatedAt 字段
2. 做游标 —— 增量同步用时间戳定位「之后的变化」
3. 时钟不可靠 —— 客户端时钟可能不准
4. 不够唯一 —— 同毫秒多次修改无法区分先后
```

```js
// 时间戳做增量同步游标
async function syncByTimestamp() {
  const lastSync = Number(localStorage.getItem('last-sync') || 0);
  const { changes } = await fetch(`/api/changes?since=${lastSync}`).then(r => r.json());
  for (const c of changes) {
    await db.put('records', { ...c, updatedAt: c.updatedAt });
  }
  const maxTs = Math.max(...changes.map(c => c.updatedAt), lastSync);
  localStorage.setItem('last-sync', String(maxTs));
}
```

```text
时间戳的取舍：
1. 做游标合适 —— 只用于「拉取某时间之后的数据」
2. 做仲裁不合适 —— 时钟偏差会导致先后判断错误
3. 配合版本号 —— 版本号仲裁冲突，时间戳定位增量
```

时间戳负责「从哪里开始拉」，版本号负责「谁新谁旧」，各司其职，别用时间戳去判断冲突胜负。

## 应用场景实战

### 场景一：可靠的待办同步（幂等 + 版本 + 重试）

```js
// 一次完整的可靠同步：幂等键 + 版本号 + 退避重试
async function syncTodo(todo) {
  const res = await retryFetch(`/api/todos/${todo.id}`, {
    method: 'PUT',
    headers: { 'Idempotency-Key': todo.syncId },
    body: JSON.stringify({ content: todo.content, version: todo.version }),
  });
  if (res.status === 409) {
    const remote = await res.json();
    console.log('冲突，远程版本更新，需合并', remote);
    return;
  }
  await db.todos.update(todo.id, { sync: 'synced', version: todo.version + 1 });
}
```

### 场景二：增量拉取远程数据

```js
// 用时间戳游标增量同步，中断可续传
async function pullIncremental() {
  let cursor = localStorage.getItem('sync-cursor'); // 上次同步位置
  while (true) {
    const { changes, nextCursor, hasMore } = await fetch(
      `/api/changes?since=${cursor || 0}&limit=200`
    ).then(r => r.json());
    for (const c of changes) await applyChange(c);
    cursor = nextCursor;
    localStorage.setItem('sync-cursor', cursor);
    if (!hasMore) break; // 增量拉完
  }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 写操作一律带幂等键，重试才能不产生重复副作用
2. 同步队列持久化到 IndexedDB，游标和幂等键一起落盘
3. 重试用指数退避 + 抖动，且只重试网络错误和 5xx，4xx 不重试
4. 版本号做乐观并发控制，冲突返回 409 走合并，别静默覆盖
5. 时间戳做增量游标，版本号做冲突仲裁，别混用
6. 增量同步分批拉取，游标推进持久化，中断后能续传

### 踩坑记录

```text
坑 1：重试重复下单
结论：网络抖动后重试，用户被扣了两次款。
原因：写操作没有幂等键，重试让服务端重复执行了创建。
解法：写操作带 Idempotency-Key，服务端按键去重。

坑 2：时间戳判断冲突先后
结论：两台设备时钟差 5 分钟，新修改被判成旧修改被覆盖。
原因：用客户端时间戳做冲突仲裁，时钟偏差导致判断错误。
解法：冲突仲裁用版本号或服务端时间，时间戳只做增量游标。

坑 3：游标不持久化导致漏数据
结论：增量同步中途刷新页面，游标丢了，从头拉又重复。
原因：游标只存内存，没落盘。
解法：游标每次推进后写 Local Storage / IndexedDB。

坑 4：重试风暴放大故障
结论：服务端抖动，大量客户端同时重试，把服务端打挂。
原因：重试没有退避和抖动，失败客户端齐刷刷重试。
解法：指数退避 + 随机抖动，错开重试时间点。

坑 5：版本号只在本地自增
结论：同步成功后版本号没更新，下次提交又被判冲突。
原因：服务端版本号推进了，本地没同步最新版本。
解法：同步成功后用服务端返回的新版本号更新本地记录。
```
