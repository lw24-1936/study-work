## 概述

类型工程（Type Engineering）把「类型」当成工程产物来管理：从 API 契约自动生成类型，用 schema 库做运行时校验并反推类型，避免手写类型与后端接口脱节。核心思想是「单一事实来源（Single Source of Truth）」，类型要么来自契约，要么来自 schema，不靠人肉维护两份。

```text
类型工程的两种来源：
1. 契约生成 —— OpenAPI / GraphQL Schema 生成 TS 类型（编译期）
2. Schema 定义 —— Zod / Valibot 定义 schema，同时得到运行时校验 + 类型推导
```

```ts
// 手写类型的痛点：后端改了字段，前端类型不会自动更新
interface User {
  id: number;
  name: string;
}
```

## API 类型生成

API 类型生成指从「接口契约」自动产出 TypeScript 类型定义，减少手写、保证前后端一致。

```text
常见生成链路：
1. 后端提供 OpenAPI/GraphQL 契约
2. 用生成器产出 .d.ts 或类型文件
3. 前端直接 import 使用，契约变更时重新生成
```

```ts
// 生成后的类型（示意）
export interface User {
  id: number;
  name: string;
  email: string;
}

export interface ApiResponse<T> {
  code: number;
  data: T;
}
```

```ts
// 前端直接使用生成的类型
import type { User } from './api-types';

async function fetchUser(id: number): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  return res.json();
}
```

## OpenAPI 类型生成

OpenAPI（原 Swagger）是 REST 接口的标准化描述，用 `openapi-typescript` 或 `swagger-typescript-api` 把 spec 转成 TS 类型。

```text
OpenAPI 类型生成工具：
1. openapi-typescript —— 轻量，只生成类型不生成请求代码
2. swagger-typescript-api —— 类型 + 请求函数一起生成
3. openapi-generator —— 多语言，重量级
```

```yaml
# OpenAPI spec 片段（openapi.yaml）
openapi: 3.0.0
info:
  title: User API
  version: 1.0.0
paths:
  /users/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: 成功
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/User'
components:
  schemas:
    User:
      type: object
      required: [id, name]
      properties:
        id:
          type: integer
        name:
          type: string
        email:
          type: string
```

```bash
# 生成类型文件
npx openapi-typescript openapi.yaml -o src/types/api.d.ts
```

```ts
// 生成的 api.d.ts 内容（示意）
export interface components {
  schemas: {
    User: {
      id: number;
      name: string;
      email?: string;
    };
  };
}
```

## GraphQL Codegen

GraphQL Codegen 是 GraphQL 生态的代码生成器，从 schema 和客户端操作（query/mutation）生成类型与 hooks。

```graphql
# 客户端操作定义（query.graphql）
query GetUser($id: ID!) {
  user(id: $id) {
    id
    name
    email
  }
}
```

```yaml
# codegen.ts 配置
schema: http://localhost:4000/graphql
documents: src/**/*.graphql
generates:
  src/generated/graphql.ts:
    plugins:
      - typescript
      - typescript-operations
      - typescript-react-apollo
```

```bash
# 运行生成
npx graphql-codegen
```

```ts
// 生成的类型（示意）
export interface GetUserQuery {
  user: { id: string; name: string; email: string } | null;
}
```

```text
GraphQL Codegen 的价值：
1. 类型精确到「客户端实际查询的字段」，不多不少
2. 同步生成 hooks（useGetUserQuery），减少样板
```

## Zod

Zod 是「schema 优先」的校验库：定义 schema 后既能做运行时校验，又能通过 `z.infer` 反推 TS 类型。

```ts
import { z } from 'zod';

// 定义 schema
const UserSchema = z.object({
  id: z.number(),
  name: z.string().min(1),
  email: z.string().email().optional(),
});

// 反推类型
type User = z.infer<typeof UserSchema>;

// 运行时校验
const result = UserSchema.safeParse({ id: 1, name: 'Alice' });
if (result.success) {
  const user: User = result.data;  // 校验通过，类型安全
} else {
  console.log(result.error.issues);
}
```

```ts
// 复杂 schema：联合、默认值、转换
const ConfigSchema = z.object({
  mode: z.enum(['dev', 'prod']),
  retries: z.number().int().default(3),
  tags: z.array(z.string()),
});

type Config = z.infer<typeof ConfigSchema>;
```

## Valibot

Valibot 是新兴的 schema 校验库，定位与 Zod 类似，卖点是「更小的包体积 + 更好的 tree-shaking」。

```ts
import * as v from 'valibot';

// 定义 schema
const UserSchema = v.object({
  id: v.number(),
  name: v.pipe(v.string(), v.minLength(1)),
  email: v.optional(v.pipe(v.string(), v.email())),
});

// 反推类型
type User = v.InferOutput<typeof UserSchema>;

// 运行时校验
const result = v.safeParse(UserSchema, { id: 1, name: 'Alice' });
if (result.success) {
  const user: User = result.output;
} else {
  console.log(v.flatten(result.issues));
}
```

```text
Zod vs Valibot：
1. Zod —— 生态成熟，API 丰富，体积较大
2. Valibot —— 体积小，按需导入，API 与 Zod 相似但略有差异
3. 两者都支持 z.infer / InferOutput 反推类型
```

## 运行时校验

运行时校验在「数据进入系统边界」时（API 响应、表单输入、URL 参数）用 schema 验证，把不可信的 any 变成可信的类型。

```ts
import { z } from 'zod';

// API 响应在边界处校验，而不是信任 as 断言
const ResponseSchema = z.object({
  code: z.number(),
  data: z.object({
    items: z.array(z.object({ id: z.number(), title: z.string() })),
  }),
});

async function loadItems(): Promise<z.infer<typeof ResponseSchema>> {
  const res = await fetch('/api/items');
  const json: unknown = await res.json();
  return ResponseSchema.parse(json);  // 失败时抛错，成功时类型安全
}
```

```ts
// 表单输入校验
const LoginSchema = z.object({
  username: z.string().min(3),
  password: z.string().min(8),
});

function submit(raw: unknown): void {
  const parsed = LoginSchema.safeParse(raw);
  if (!parsed.success) {
    // 返回字段级错误
    console.log(parsed.error.flatten().fieldErrors);
    return;
  }
  // 拿到可信数据
  const { username, password } = parsed.data;
}
```

## 静态类型检查

静态类型检查在编译期（不运行代码）发现类型错误，由 `tsc --noEmit` 或编辑器语言服务完成，是类型工程的最后一道防线。

```ts
// 编译期捕获错误
function add(a: number, b: number): number {
  return a + b;
}

// add('1', 2);  // 编译报错：类型 string 不能赋给 number
```

```bash
# 只做类型检查，不产出 JS
npx tsc --noEmit

# 配合 tsconfig 严格模式
# "strict": true  开启所有严格检查
```

```text
静态检查 vs 运行时校验：
1. 静态检查 —— 编译期，零运行时开销，只能检查类型
2. 运行时校验 —— 运行时，有开销，能验证「真实数据」是否合法
3. 两者互补：静态检查管代码内部，运行时校验管外部输入
```

## 应用场景实战

### 场景一：用 Zod 校验 API 响应并在边界处收窄

```ts
import { z } from 'zod';

const UserListSchema = z.object({
  data: z.array(z.object({
    id: z.number(),
    name: z.string(),
  })),
});

async function getUsers(): Promise<z.infer<typeof UserListSchema>['data']> {
  const res = await fetch('/api/users');
  const json: unknown = await res.json();
  const parsed = UserListSchema.safeParse(json);
  if (!parsed.success) {
    throw new Error('接口返回格式不符：' + parsed.error.message);
  }
  return parsed.data.data;  // 类型已收窄为 { id: number; name: string }[]
}
```

### 场景二：OpenAPI 类型 + 请求函数生成（swagger-typescript-api）

```bash
# 从 swagger 生成类型和请求客户端
npx swagger-typescript-api \
  -p https://api.example.com/swagger.json \
  -o src/generated \
  -n api.ts
```

```ts
// 生成的客户端使用（示意）
import { Api } from './generated/api';

const api = new Api({ baseUrl: 'https://api.example.com' });
const users = await api.users.getUsersList();  // 类型自动带出
```

## 最佳实践与踩坑记录

### 最佳实践

1. 类型来源单一化：有契约用生成器，有 schema 用 z.infer，别手写两份
2. API 响应在「边界处」校验（parse），而不是用 `as` 断言糊弄
3. 生成的文件放进 gitignore 或独立目录，避免手改被覆盖
4. 严格模式（strict: true）全开，必要时局部关闭并加注释说明
5. 用 safeParse 处理外部输入，parse 处理「应该合法」的内部数据

### 踩坑记录

```text
坑 1：手改生成文件被下次生成覆盖
结论：改了 generated 目录的文件，重新生成后改动丢失。
原因：生成器每次全量覆盖输出目录。
解法：生成文件放独立目录并 gitignore，自定义逻辑放别处。

坑 2：用 as 断言绕过校验
结论：res.json() as User 在字段不符时静默得到错误类型。
原因：as 断言不做任何运行时检查，纯编译期信任。
解法：用 Zod/Valibot 在边界处 parse，把 unknown 变成可信类型。

坑 3：Zod 校验失败抛错未捕获导致崩溃
结论：parse 在数据不合法时直接 throw，未处理则页面崩溃。
原因：parse 抛错是设计行为，用于「应该合法」的场景。
解法：外部输入用 safeParse 返回结果对象，自行处理失败分支。

坑 4：生成器版本与后端契约不同步
结论：后端改了接口，前端类型还是旧的。
原因：类型生成是一次性动作，契约变更后未重新生成。
解法：CI 里加生成步骤，契约变更自动重新生成并跑 tsc。

坑 5：GraphQL Codegen 生成类型不包含未查询字段
结论：生成的类型只有查询里写的字段，想用别的字段报错。
原因：typescript-operations 精确到查询字段，这是特性不是 bug。
解法：需要的字段在 query 里显式声明，或另外生成 schema 全量类型。
```
