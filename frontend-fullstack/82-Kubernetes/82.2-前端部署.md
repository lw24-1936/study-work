## 概述

前端在 Kubernetes 上的部署形态很清晰：前端是无状态的静态资源服务，构建产物打进 Nginx 镜像，用 Deployment 跑起来，通过 Service 和 Ingress 对外提供访问，再配合 CDN、TLS 和自动扩缩容保证性能与可用性。前端服务本身无状态，因此天然适合横向扩容。

```text
前端 K8s 部署的完整链路：
1. Static Server —— 前端本质是静态资源服务，无状态
2. Nginx —— 运行容器里的静态服务器，托管 dist
3. CDN —— 静态资源走边缘节点，减轻集群压力
4. Ingress —— 统一对外入口，域名路由 + TLS 终止
5. TLS —— HTTPS 证书配置，安全传输
6. Autoscaling —— 按流量自动扩缩容
```

```text
前端部署与后端部署的差异：
1. 无状态 —— 不需要持久化，Pod 随便重建无副作用
2. 资源静态 —— 核心是带宽和缓存，而非 CPU 密集计算
3. 可 CDN —— 大部分流量可以被边缘缓存吸收
4. 简单 —— 没有数据库、消息队列等复杂依赖
```

## Static Server

Static Server（静态服务器）是前端在 K8s 里的角色定位：它只负责把 dist 目录里的静态文件（HTML/JS/CSS/图片）原样返回给请求方，不做业务计算。因为无状态，前端服务的副本可以随意增减，非常适合容器化和自动扩缩容。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 3
  selector:
    matchLabels: { app: frontend }
  template:
    metadata:
      labels: { app: frontend }
    spec:
      containers:
        - name: frontend
          image: registry.example.com/my-app:v1.2.3
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 128Mi
```

```text
静态服务器的特点：
1. 无状态 —— 每个 Pod 都是等价可替换的
2. 轻量 —— CPU/内存需求低，资源可以压得很小
3. 易扩容 —— 流量来了直接加副本，没有数据一致性负担
4. 带宽敏感 —— 瓶颈通常在网络 I/O 而非计算
```

## Nginx

Nginx 是前端容器里的静态服务器，负责托管 dist 产物、处理 SPA 路由回退、做压缩和缓存。前端镜像的 runtime 阶段就是 Nginx + dist + 配置，运行在 K8s 的 Pod 里。

```dockerfile
# 前端镜像：Nginx 托管静态产物
FROM nginx:1.27-alpine
COPY dist/ /usr/share/nginx/html/
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
```

```nginx
# nginx.conf —— 静态服务 + SPA 回退 + 健康检查端点
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    # 健康检查端点
    location = /healthz {
        return 200 "ok";
        add_header Content-Type text/plain;
    }
}
```

```text
Nginx 在前端 K8s 部署中的职责：
1. 静态托管 —— 服务 dist 产物
2. SPA 回退 —— try_files 处理前端路由刷新
3. 健康检查 —— 提供 /healthz 供 readinessProbe 探测
4. 压缩缓存 —— gzip/brotli 和缓存头优化传输
```

## CDN

CDN 在 K8s 前端部署里是「集群的减压阀」：把 JS/CSS/图片等静态资源推到 CDN，让大部分请求命中边缘节点，不再回源到集群。这样前端服务本身只需兜底处理少量回源请求，副本数可以更少，成本更低。

```text
前端 + CDN 的分工：
1. CDN 承载 —— 带 hash 的静态资源（JS/CSS/图片/字体）
2. 集群承载 —— index.html 入口和动态接口
3. 回源 —— 仅当 CDN 缓存未命中时，才请求到集群
```

```bash
# 构建产物里的静态资源上传 CDN，index.html 保留在集群
# 或者全部托管 CDN，集群只跑动态 API
aws s3 sync dist/assets s3://cdn-bucket/assets --delete \
  --cache-control "public, max-age=31536000, immutable"
```

```text
CDN 集成的两种形态：
1. 旁路 —— 静态资源单独发布到 CDN，集群只服务动态请求
2. 前置 —— CDN 作为集群入口的前置缓存，回源到 Ingress
```

## Ingress

Ingress 是前端对外暴露的入口，把域名路由到前端的 Service，统一处理 80/443 端口、TLS 终止和路径转发。对前端而言，Ingress 通常是「域名 -> 前端 Service」的映射，再配合 rewrite 或路径规则把 /api 转发给后端。

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - app.example.com
      secretName: app-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port: { number: 80 }
```

```text
Ingress 在前端部署的要点：
1. 域名路由 —— 一个 Ingress 管理多个域名/路径
2. TLS 终止 —— 集中处理 HTTPS 证书
3. 统一入口 —— 配合 ingress-nginx 提供丰富的注解能力
4. 重写转发 —— 把 /api 路径转发到后端服务
```

## TLS

TLS（Transport Layer Security）为前端提供 HTTPS 加密传输。在 K8s 里，证书通过 Secret 存储，Ingress 负责 TLS 终止（解密请求再转发给后端），也可以配合 cert-manager 自动签发和续期 Let's Encrypt 证书。

```yaml
# TLS 证书存入 Secret，Ingress 引用
apiVersion: v1
kind: Secret
metadata:
  name: app-tls
type: kubernetes.io/tls
data:
  tls.crt: <base64 编码的证书>
  tls.key: <base64 编码的私钥>
```

```yaml
# 用 cert-manager 自动签发证书
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: app-cert
spec:
  secretName: app-tls
  dnsNames:
    - app.example.com
  issuerRef:
    name: letsencrypt
    kind: ClusterIssuer
```

```text
TLS 的要点：
1. 证书存储 —— 证书和私钥放 Secret，类型 kubernetes.io/tls
2. 终止位置 —— 通常在 Ingress 层终止，后端走明文 HTTP
3. 自动续期 —— cert-manager 自动签发和续期，避免证书过期
4. HSTS —— 配合安全头强制 HTTPS，防降级攻击
```

## Autoscaling

Autoscaling（自动扩缩容）让前端服务的副本数随负载自动调整：流量高峰自动扩容，低谷缩容，兼顾性能和成本。K8s 用 HPA（Horizontal Pod Autoscaler）根据 CPU、内存或自定义指标（如请求量）动态调整副本数。

```yaml
# HPA：按 CPU 使用率自动扩缩容
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: frontend
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: frontend
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```

```text
Autoscaling 的要点：
1. 指标选择 —— CPU/内存是基础，请求量/延迟是更贴近业务的指标
2. 扩缩边界 —— min/max 设好，防止雪崩或浪费
3. 冷启动 —— 扩容有延迟，突发流量需要预留余量
4. 就绪探测 —— 新 Pod 就绪前不打流量，配合 readinessProbe
```

## 应用场景实战

### 场景一：前端 + 后端的一体化 Ingress 路由

```yaml
# 一个 Ingress 同时路由前端页面和 API 请求
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - app.example.com
      secretName: app-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port: { number: 80 }
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port: { number: 3000 }
```

### 场景二：带 HPA 和健康检查的完整前端部署

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 2
  selector:
    matchLabels: { app: frontend }
  template:
    metadata:
      labels: { app: frontend }
    spec:
      containers:
        - name: frontend
          image: registry.example.com/my-app:v1.2.3
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /healthz
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10
          resources:
            requests: { cpu: 50m, memory: 64Mi }
            limits: { cpu: 200m, memory: 128Mi }
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: frontend
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: frontend
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```

## 最佳实践与踩坑记录

### 最佳实践

1. 静态资源上 CDN，集群只兜底回源，减少集群压力和成本
2. 配置 readinessProbe，让 Pod 就绪后再接入流量，避免冷启动 502
3. 设置合理的 resources.requests/limits，为 HPA 和调度提供依据
4. TLS 用 cert-manager 自动签发续期，证书放 Secret 由 Ingress 引用
5. HPA 设好 min/max 边界，按 CPU 或请求量指标扩缩容
6. 镜像 tag 用 commit hash，发布用 kubectl set image 滚动更新

### 踩坑记录

```text
坑 1：没有 resources 配置导致调度和扩缩容失准
结论：HPA 无法基于 CPU 百分比工作，Pod 也可能被驱逐或抢占。
原因：没有声明 requests/limits，K8s 无法计算资源使用率。
解法：为每个容器声明 requests 和 limits，HPA 才能正常计算指标。

坑 2：静态资源没上 CDN，集群被打爆
结论：大流量下前端 Pod 和带宽成本飙升，甚至集群雪崩。
原因：所有静态资源请求都回源到集群，没有边缘缓存分担。
解法：静态资源推 CDN 长缓存，集群只处理入口和动态请求。

坑 3：TLS 证书过期导致全站 HTTPS 报错
结论：用户访问时浏览器显示证书错误，业务中断。
原因：手工签发的证书过期，没有自动续期机制。
解法：用 cert-manager 自动签发和续期 Let's Encrypt 证书。

坑 4：HPA 扩容赶不上突发流量
结论：流量突增瞬间新 Pod 还在冷启动，服务超时。
原因：扩容有延迟，加上没有预留余量，突发流量直接打满。
解法：minReplicas 预留缓冲，配合 CDN 吸收峰值，必要时用预测性扩容。

坑 5：Ingress 路径 / 把 /api 也吞掉了
结论：API 请求被前端 SPA 回退逻辑处理，返回 HTML 而非 JSON。
原因：Ingress 路径顺序或匹配规则错误，/ 前缀把 /api 也匹配走了。
解法：Ingress 用更精确的路径匹配，/api 规则优先，或用前缀长度决定优先级。
```
