## 概述

Kubernetes（简称 K8s）是容器编排平台，用「声明式」的方式管理容器：你描述期望的状态（几个副本、哪个镜像、什么配置），K8s 自动把集群收敛到这个状态。它解决的核心问题是容器的调度、扩容、自愈和服务发现，是现代应用部署的事实标准。

```text
Kubernetes 的核心对象：
1. Pod —— 最小调度单元，一个或多个容器的集合
2. Deployment —— 管理 Pod 副本、滚动更新和回滚
3. Service —— 稳定的访问入口，负载均衡到 Pod
4. Ingress —— 对外暴露 HTTP 路由，域名 + 路径转发
5. ConfigMap / Secret —— 配置和敏感信息的管理
6. Namespace —— 资源隔离的逻辑分区
```

## Pod

Pod 是 K8s 最小的调度和部署单元，一个 Pod 可以包含一个或多个紧密耦合的容器，共享网络命名空间（同一个 IP）和存储卷。通常一个 Pod 跑一个主容器，但也可能带 sidecar 容器（如日志采集、服务网格代理）。

```yaml
# 一个运行前端容器的 Pod
apiVersion: v1
kind: Pod
metadata:
  name: frontend-pod
  labels:
    app: frontend
spec:
  containers:
    - name: frontend
      image: registry.example.com/my-app:v1.2.3
      ports:
        - containerPort: 80
```

```text
Pod 的特点：
1. 最小单元 —— 不能直接调度容器，只能调度 Pod
2. 共享网络 —— 同一 Pod 内容器共享 IP 和端口空间
3. 临时性 —— Pod 可能被重建，IP 和状态都会变
4. 多容器 —— 主容器 + sidecar 的组合模式很常见
```

```bash
# 查看 Pod 状态和日志
kubectl get pods -o wide
kubectl describe pod frontend-pod
kubectl logs frontend-pod
kubectl exec -it frontend-pod -- sh
```

## Deployment

Deployment 是管理 Pod 的高级控制器，声明期望的副本数和镜像版本，负责滚动更新、扩容缩容和回滚。生产环境几乎不会直接创建 Pod，而是通过 Deployment 管理，这样 Pod 挂了会自动重建、版本升级可以平滑滚动。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
        - name: frontend
          image: registry.example.com/my-app:v1.2.3
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /healthz
              port: 80
```

```bash
# 扩容 / 缩容
kubectl scale deployment frontend --replicas=5

# 滚动更新到新版本
kubectl set image deployment/frontend frontend=registry.example.com/my-app:v1.2.4

# 查看发布状态
kubectl rollout status deployment/frontend
```

```text
Deployment 的职责：
1. 副本管理 —— 保证期望数量的 Pod 始终存活
2. 滚动更新 —— 逐个替换旧 Pod，零停机升级
3. 回滚 —— rollout undo 一键退回历史版本
4. 自愈 —— Pod 崩溃或节点故障时自动重建
```

## Service

Service 为 Pod 提供稳定的访问入口。因为 Pod 的 IP 会随重建而变化，Service 通过 selector 把一组 Pod 聚合成一个稳定的虚拟 IP 和 DNS 名，内部组件通过 Service 名访问，而不用关心具体是哪个 Pod 在服务。

```yaml
apiVersion: v1
kind: Service
metadata:
  name: frontend
spec:
  selector:
    app: frontend
  ports:
    - port: 80          # Service 对外暴露的端口
      targetPort: 80    # 转发到 Pod 的端口
  type: ClusterIP       # 默认类型，仅集群内可访问
```

```text
Service 的类型与价值：
1. ClusterIP —— 默认，集群内部访问；虚拟 IP 和 DNS 名不随 Pod 重建变化
2. NodePort —— 在节点上开端口，外部可通过节点 IP 访问
3. LoadBalancer —— 云厂商负载均衡，直接对外提供公网入口
4. ExternalName —— 把外部服务映射到集群内的 DNS 名
5. 负载均衡 —— 自动把请求分发到后端多个 Pod
6. 服务发现 —— 通过名字访问，无需硬编码 IP
```

## Ingress

Ingress 是对外暴露 HTTP/HTTPS 服务的入口，负责把域名和路径路由到后端的 Service。相比 NodePort 每个服务占一个端口，Ingress 统一 80/443 入口，按 host 和 path 转发，还能做 TLS 终止、重写、限流等。

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 3000
```

```text
Ingress 的要点：
1. 路由 —— 按域名和路径转发到不同 Service
2. TLS —— 集中配置 HTTPS 证书，做 TLS 终止
3. 统一入口 —— 一个 Ingress Controller 管理所有流量入口
4. 需要 Controller —— 集群需部署 ingress-nginx / Traefik 等实现
```

## ConfigMap

ConfigMap 用于管理非敏感配置，把配置从镜像里解耦出来，以环境变量或挂载文件的形式注入 Pod。这样改配置只需更新 ConfigMap，无需重新构建镜像。

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: frontend-config
data:
  API_BASE_URL: "https://api.example.com"
  FEATURE_NEW_CHECKOUT: "true"
  nginx.conf: |
    server {
      listen 80;
      root /usr/share/nginx/html;
      location / { try_files $uri $uri/ /index.html; }
    }
```

```yaml
# 在 Deployment 里引用 ConfigMap
spec:
  containers:
    - name: frontend
      image: registry.example.com/my-app:v1.2.3
      envFrom:
        - configMapRef:
            name: frontend-config
```

```text
ConfigMap 的使用方式：
1. envFrom —— 把整个 ConfigMap 作为环境变量批量注入
2. valueFrom —— 取 ConfigMap 里的某个 key 作为单个环境变量
3. volumeMount —— 把 ConfigMap 挂载成文件（适合配置文件）
```

## Secret

Secret 与 ConfigMap 类似，但专门用于存放敏感信息（密码、token、证书），数据以 base64 编码存储，并配合 RBAC 控制访问。虽然 base64 不是加密，但 Secret 相比 ConfigMap 有更严格的访问控制和更小的暴露面。

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: frontend-secret
type: Opaque
data:
  API_KEY: dXNlcm5hbWU=        # base64 编码
  SENTRY_DSN: aHR0cHM6Ly9zZW50cnk=  # base64 编码
```

```bash
# 用命令行生成 base64 编码的值
echo -n 'my-api-key' | base64
# 或直接从字面量创建 Secret（kubectl 自动编码）
kubectl create secret generic frontend-secret \
  --from-literal=API_KEY=my-api-key
```

```text
Secret 的安全要点：
1. base64 只是编码不是加密，务必配合 RBAC 限制访问
2. 优先用云厂商的密钥管理（如 Vault、KMS）托管真正的密钥
3. Secret 不要提交到 Git，用密封工具（sealed-secrets）或外部存储
4. 最小授权 —— 只给需要读 Secret 的 Pod 授权
```

## Namespace

Namespace 是集群内资源的逻辑隔离分区，把不同团队、不同环境的资源隔开，避免命名冲突，也便于配额管理和权限控制。默认有 default、kube-system 等命名空间。

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: staging
```

```bash
# 在不同命名空间操作资源
kubectl create namespace staging
kubectl apply -f deployment.yaml -n staging
kubectl get pods -n staging
# 切换默认命名空间
kubectl config set-context --current --namespace=staging
```

```text
Namespace 的常见划分：
1. 按环境 —— dev / staging / production 隔离
2. 按团队 —— 每个团队一个命名空间
3. 按用途 —— 应用与基础设施（监控、日志）分离
4. 配额 —— 限制每个命名空间的 CPU/内存/对象数
```

## 应用场景实战

### 场景一：前端应用的完整部署清单

```yaml
# 一个前端服务的 Deployment + Service + Ingress
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels: { app: frontend }
  template:
    metadata:
      labels: { app: frontend }
    spec:
      containers:
        - name: frontend
          image: registry.example.com/my-app:v1.2.3
          ports:
            - containerPort: 80
          envFrom:
            - configMapRef:
                name: frontend-config
---
apiVersion: v1
kind: Service
metadata:
  name: frontend
  namespace: production
spec:
  selector: { app: frontend }
  ports:
    - port: 80
      targetPort: 80
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend
  namespace: production
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port: { number: 80 }
```

### 场景二：用 ConfigMap 管理 Nginx 配置并热更新

```yaml
# 把 nginx.conf 放进 ConfigMap，改配置无需重打镜像
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
data:
  default.conf: |
    server {
      listen 80;
      root /usr/share/nginx/html;
      location / {
        try_files $uri $uri/ /index.html;
      }
    }
```

```yaml
# 挂载到容器，覆盖默认配置
spec:
  containers:
    - name: frontend
      image: registry.example.com/my-app:v1.2.3
      volumeMounts:
        - name: nginx-config
          mountPath: /etc/nginx/conf.d
  volumes:
    - name: nginx-config
      configMap:
        name: nginx-config
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 Deployment 管理 Pod，不要直接创建裸 Pod，享受自愈和滚动更新
2. 配置和敏感信息分别放 ConfigMap 和 Secret，不要写死进镜像
3. 配置 readinessProbe 和 livenessProbe，保证流量只打到就绪的 Pod
4. 按环境用 Namespace 隔离，用标签规范组织资源
5. Service 用名字访问，Ingress 统一对外入口和 TLS
6. 资源清单提交 Git 管理，用 kubectl apply 声明式部署

### 踩坑记录

```text
坑 1：没有 readinessProbe，Pod 未就绪就接流量
结论：新 Pod 刚启动还没监听端口就被打入流量，用户看到 502。
原因：K8s 默认容器一启动就算就绪，但应用可能还在初始化。
解法：配置 readinessProbe 做健康检查，就绪后才由 Service 分发流量。

坑 2：直接删除 Pod 而不是用 Deployment 管理
结论：Pod 删了不会自动恢复，服务直接中断。
原因：裸 Pod 没有控制器，不具备自愈能力。
解法：用 Deployment 管理，控制器会自动重建故障 Pod。

坑 3：Secret 的 base64 当加密用
结论：base64 编码的密钥被泄露后直接可用，形同明文。
原因：误以为 base64 是加密，没有额外的访问控制。
解法：配合 RBAC 限制 Secret 访问，敏感密钥用云 KMS 或 Vault 托管。

坑 4：ConfigMap 改了但 Pod 没生效
结论：改了 ConfigMap 里的配置，运行中的容器看不到变化。
原因：环境变量方式注入的配置在 Pod 启动时固化，不会动态更新。
解法：环境变量配置需要滚动重启 Pod；挂载文件方式可自动同步（需应用支持热加载）。

坑 5：Service selector 匹配不到 Pod
结论：Service 一直没有后端，请求全部失败。
原因：Service 的 selector 与 Pod 的 labels 不一致，匹配不到任何 Pod。
解法：核对 selector 与 labels 完全一致，用 kubectl get endpoints 验证后端是否存在。
```
