## 概述

AI SDK 是连接前端应用与大语言模型（LLM）的中间层：它把「调用模型、流式输出、工具调用、结构化结果」这些繁琐细节封装成统一的 API，让前端开发者不必直接手写 HTTP 请求和 SSE 解析。目前最主流的通用方案是 Vercel AI SDK，此外各模型厂商（OpenAI、Anthropic）也提供各自的官方 SDK。

```text
AI SDK 解决的核心问题：
1. 统一接口 —— 一套 API 对接多家模型提供商
2. 流式输出 —— 封装 SSE/流式读取，token 级更新 UI
3. 工具调用 —— 让模型调用外部函数（联网、查库）
4. 结构化输出 —— 强制模型返回合法 JSON Schema
5. 前后端同构 —— 服务端生成、客户端消费的完整链路
```

```ts
// Vercel AI SDK 的核心用法
import { generateText } from 'ai';
import { openai } from '@ai-sdk/openai';

const { text } = await generateText({
  model: openai('gpt-4o'),
  prompt: '用一句话解释什么是边缘计算',
});
console.log(text);
```

## LLM API

LLM API 是各大模型服务商提供的 HTTP 接口：通过 REST 请求把 prompt（或 messages）发给模型，模型返回生成的文本。虽然各家的端点、鉴权、参数名略有差异，但核心概念高度一致——消息列表进、补全文本出。

```text
LLM API 的通用结构：
1. 请求 —— 携带 model、messages、temperature 等参数
2. 消息 —— system / user / assistant 三类角色
3. 响应 —— 返回 choices[].message.content 文本
4. 令牌 —— 按输入 + 输出 token 计费
5. 参数 —— temperature、max_tokens、top_p 控制生成行为
```

```js
// 直接调用 OpenAI 兼容的 Chat Completions API
const res = await fetch('https://api.openai.com/v1/chat/completions', {
  method: 'POST',
  headers: {
    'content-type': 'application/json',
    authorization: `Bearer ${process.env.OPENAI_API_KEY}`,
  },
  body: JSON.stringify({
    model: 'gpt-4o',
    messages: [
      { role: 'system', content: '你是简洁的中文助手' },
      { role: 'user', content: '什么是 CDN？' },
    ],
    temperature: 0.7,
  }),
});
const data = await res.json();
console.log(data.choices[0].message.content);
```

AI SDK 的价值正是把这套手写请求的样板代码封装掉，并处理重试、超时、错误、流式等边界情况。

## Streaming

Streaming（流式输出）是 LLM 应用体验的关键：模型生成是逐 token 的，如果等全部生成完再一次性返回，用户会盯着空白页面发呆。流式输出让每个 token 生成后立即推送到前端，实现「打字机」般的逐字显示，把首字延迟降到最低。

```text
流式输出的要点：
1. SSE / 流 —— 服务端用 ReadableStream 持续推送
2. token 粒度 —— 每生成一段就发一段
3. 首字延迟 —— 用户很快看到第一个字，感知更快
4. 增量渲染 —— 前端边收边渲染，不做整段替换
```

```ts
// AI SDK 流式生成：streamText 返回一个 ReadableStream
import { streamText } from 'ai';
import { openai } from '@ai-sdk/openai';

export async function POST(req: Request) {
  const { prompt } = await req.json();
  const result = streamText({
    model: openai('gpt-4o'),
    prompt,
  });
  // 返回流式响应给前端
  return result.toTextStreamResponse();
}
```

```ts
// 前端消费流：useChat 自动处理增量
import { useChat } from '@ai-sdk/react';

const { messages, input, handleSubmit } = useChat();
```

流式输出的本质是把「长任务」切成「可感知的进度」，让用户始终知道模型在干活。

## Chat

Chat 是 LLM 应用最主流的交互形态：把多轮对话建模成 messages 数组（system + user + assistant 交替），每次请求都把完整历史发给模型，模型基于上下文续写回复。Chat 的关键在于「上下文管理」——历史太长会超 token 上限，太短会丢失上下文。

```text
Chat 的关键点：
1. 消息数组 —— system / user / assistant 交替排列
2. 上下文窗口 —— 历史总长受模型 token 上限约束
3. 历史裁剪 —— 超长时截断或摘要旧消息
4. 多轮 —— 每轮追加 user 消息，模型补 assistant 回复
```

```ts
// 多轮对话：维护 messages 数组并逐轮追加
import { generateText } from 'ai';
import { openai } from '@ai-sdk/openai';

const messages = [
  { role: 'system', content: '你是客服助手' },
];

async function chat(userInput: string) {
  messages.push({ role: 'user', content: userInput });
  const { text } = await generateText({
    model: openai('gpt-4o'),
    messages,
  });
  messages.push({ role: 'assistant', content: text });
  return text;
}
```

Chat 模型的上下文是「一次性全部传入」的，没有跨请求的隐式记忆——所以历史必须显式维护并传回。

## Tool Calling

Tool Calling（工具调用 / Function Calling）让模型「动手做事」：开发者声明一批可调用的函数（工具），模型根据用户意图决定调用哪个工具、传什么参数，执行后把结果返回给模型继续生成。这让 LLM 从「只会说话」变成「能查数据、能操作系统」。

```text
Tool Calling 流程：
1. 声明工具 —— 提供名称、描述、参数 JSON Schema
2. 模型决策 —— 判断是否需要调用工具
3. 返回调用 —— 给出工具名和参数（不是最终答案）
4. 执行工具 —— 开发者实际调用函数得到结果
5. 回传结果 —— 把结果作为 tool 消息发给模型，生成最终回复
```

```ts
import { generateText, tool } from 'ai';
import { openai } from '@ai-sdk/openai';
import { z } from 'zod';

const { text } = await generateText({
  model: openai('gpt-4o'),
  messages: [{ role: 'user', content: '北京今天天气怎么样？' }],
  tools: {
    getWeather: tool({
      description: '查询指定城市的天气',
      parameters: z.object({ city: z.string() }),
      execute: async ({ city }) => {
        // 实际调用天气 API
        return { city, temp: 26, condition: '晴' };
      },
    }),
  },
});
```

Tool Calling 把模型的「推理能力」与程序的「执行能力」连接起来，是构建 Agent 的基础。

## Structured Output

Structured Output（结构化输出）强制模型返回符合指定格式的结果（通常是 JSON Schema），而不是自由文本。这对「把模型结果喂给程序」至关重要——自由文本需要脆弱的正则解析，结构化输出直接可反序列化，稳定可靠。

```text
结构化输出的价值：
1. 稳定格式 —— 严格符合 JSON Schema，无需正则解析
2. 直接可用 —— 反序列化后即可参与程序逻辑
3. 约束生成 —— 限制输出字段和类型，减少幻觉
4. 校验可靠 —— 与 zod 等 schema 库天然契合
```

```ts
import { generateObject } from 'ai';
import { openai } from '@ai-sdk/openai';
import { z } from 'zod';

const { object } = await generateObject({
  model: openai('gpt-4o'),
  schema: z.object({
    sentiment: z.enum(['positive', 'negative', 'neutral']),
    summary: z.string(),
    keywords: z.array(z.string()),
  }),
  prompt: '分析这段用户评价：产品很好用，就是发货太慢了。',
});

console.log(object); // { sentiment: 'neutral', summary: '...', keywords: [...] }
```

结构化输出让 LLM 从「对话工具」变成「可编程的确定性组件」，是 LLM 接入业务系统的关键一步。

## 应用场景实战

### 场景一：流式问答助手

```ts
// 服务端：流式输出 route handler
// app/api/chat/route.ts
import { streamText } from 'ai';
import { openai } from '@ai-sdk/openai';

export async function POST(req: Request) {
  const { messages } = await req.json();
  const result = streamText({
    model: openai('gpt-4o'),
    system: '你是知识库助手，回答要简洁。',
    messages,
  });
  return result.toTextStreamResponse();
}
```

```tsx
// 前端：useChat 消费流
import { useChat } from '@ai-sdk/react';

export default function ChatBox() {
  const { messages, input, handleInputChange, handleSubmit } = useChat();
  return (
    <div>
      {messages.map((m) => (
        <div key={m.id}>{m.role}: {m.content}</div>
      ))}
      <form onSubmit={handleSubmit}>
        <input value={input} onChange={handleInputChange} />
        <button type="submit">发送</button>
      </form>
    </div>
  );
}
```

### 场景二：工具调用实现「查订单」

```ts
import { generateText, tool } from 'ai';
import { openai } from '@ai-sdk/openai';
import { z } from 'zod';

const { text } = await generateText({
  model: openai('gpt-4o'),
  messages: [{ role: 'user', content: '帮我查一下订单 A1001 的状态' }],
  tools: {
    getOrder: tool({
      description: '根据订单号查询订单状态',
      parameters: z.object({ orderId: z.string() }),
      execute: async ({ orderId }) => {
        // 查询数据库
        return { orderId, status: '已发货' };
      },
    }),
  },
});
console.log(text);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 流式输出默认开启，首字延迟决定用户体感
2. 工具参数用 zod schema 声明，类型安全和校验一起解决
3. 结构化输出用 generateObject，别用正则解析自由文本
4. API Key 永远放服务端，前端只经过你自己的后端转发
5. 长对话做上下文裁剪或摘要，避免超出 token 上限

### 踩坑记录

```text
坑 1：API Key 直接暴露在前端
结论：密钥被盗刷，账单暴涨。
原因：把 SDK 调用写在前端，Key 打进 bundle 可被任意查看。
解法：模型调用一律走服务端，前端只请求自己的 API 路由。

坑 2：自由文本结果用正则解析
结论：模型输出格式稍有变化，解析就崩。
原因：自由文本格式不稳定，正则脆弱。
解法：用结构化输出（JSON Schema / generateObject）替代。

坑 3：流式请求忘了处理错误
结论：中途断流，前端卡在「生成中」无提示。
原因：只处理了成功路径，忽略了网络中断和服务端异常。
解法：加 onError 回调，中断时给用户明确提示并允许重试。

坑 4：多轮对话无限增长导致超限
结论：会话越来越长，最终报 token 超限错误。
原因：每轮都把完整历史发出去，历史无限累积。
解法：裁剪旧消息、做摘要、或用滑动窗口限制上下文长度。

坑 5：工具调用结果没回传给模型
结论：模型一直等工具结果，或直接编造答案。
原因：执行完工具后忘了把结果作为 tool 消息追加回对话。
解法：严格按「模型决策 → 执行 → 回传 → 继续生成」闭环实现。
```
