## 概述

浏览器 AI 指的是在浏览器本地运行机器学习模型，无需把数据发到服务器。它的价值在于隐私（数据不出设备）、低延迟（无网络往返）、离线可用（不依赖后端）。实现载体从 WASM 到 WebGPU 逐步演进，让浏览器逐渐具备接近原生的推理能力。

```text
浏览器 AI 的实现层次：
1. WASM —— CPU 推理，兼容性最好
2. WebGPU —— GPU 加速，性能最高
3. WebNN —— 浏览器原生神经网络 API，直接调硬件加速
4. ONNX Runtime Web —— 统一运行时，自动选择后端
5. Transformers.js —— 把 Hugging Face 模型搬进浏览器
```

```js
// 浏览器 AI 的典型入口：加载模型 → 推理 → 输出
import { pipeline } from '@xenova/transformers';

const classifier = await pipeline('sentiment-analysis', 'Xenova/distilbert-base-uncased');
const result = await classifier('I love this!');
console.log(result); // [{ label: 'POSITIVE', score: 0.99 }]
```

## WebGPU

WebGPU 是浏览器访问 GPU 的下一代 API，为通用计算（GPGPU）设计。对 AI 而言，GPU 的数千个核心天然适合矩阵运算，让浏览器里的模型推理速度比纯 CPU（WASM）快一个量级。它是浏览器 AI 性能的天花板，但兼容性仍在普及中。

```text
WebGPU 用于 AI 的要点：
1. 通用计算 —— Compute Shader 做矩阵运算
2. 高并行 —— 数千核心并行，推理提速明显
3. 显存访问 —— 权重加载到 GPU Buffer
4. 兼容性 —— Chrome/Edge 已支持，仍在演进
```

```js
// 检测 WebGPU 是否可用
if (!navigator.gpu) {
  console.log('当前浏览器不支持 WebGPU');
} else {
  const adapter = await navigator.gpu.requestAdapter();
  const device = await adapter.requestDevice();
  console.log('WebGPU 可用');
}
```

WebGPU 是底层 API，直接写矩阵乘法的 Compute Shader 很繁琐，实际开发中通常由 ONNX Runtime Web / Transformers.js 这样的上层库封装。

## WebNN

WebNN 是浏览器原生提供的神经网络推理 API：它把「加载模型、执行推理」抽象成标准接口，浏览器底层自动调度到 CPU、GPU 或专用 NPU 加速硬件。相比自己用 WebGPU 手写算子，WebNN 更接近「开箱即用」，能充分利用设备的专用 AI 芯片。

```text
WebNN 的特点：
1. 原生 API —— 浏览器内置，无需额外运行时
2. 硬件调度 —— 自动使用 CPU / GPU / NPU
3. 标准模型图 —— 以计算图形式表达神经网络
4. 早期阶段 —— 规范仍在演进，Chrome 已开始落地
```

```js
// WebNN 概念示意（API 仍在演进）
// 构建计算图 → 编译 → 输入数据 → 推理
const context = await navigator.ml.createContext();
const builder = new MLGraphBuilder(context);
const input = builder.input('input', { dataType: 'float32', dimensions: [1, 3, 224, 224] });
const output = builder.relu(input);
const graph = await builder.build({ output });
// 用 graph.compute(inputs, outputs) 执行推理
```

WebNN 的愿景是「浏览器直接把模型交给系统优化」，让推理性能不再受 JS/WASM 解释开销拖累。

## WASM

WASM（WebAssembly）是浏览器 AI 的「保底方案」：几乎所有支持 WASM 的浏览器都能跑，兼容性最好。它把 C/C++/Rust 编译成接近原生的字节码，比纯 JS 快数倍，但仍是 CPU 推理，速度不如 GPU。它是 ONNX Runtime Web 和 Transformers.js 的默认后端之一。

```text
WASM 用于 AI 的要点：
1. 兼容性最好 —— 所有现代浏览器都支持
2. CPU 推理 —— 比 JS 快，但不如 GPU
3. SIMD 加速 —— 128 位向量指令进一步提速
4. 体积可控 —— 模型量化后可达数十 MB
```

```js
// 用 WASM 后端加载 ONNX 模型
import * as ort from 'onnxruntime-web';

// 显式指定 WASM 后端
const session = await ort.InferenceSession.create('./model.onnx', {
  executionProviders: ['wasm'],
});
```

WASM 是浏览器 AI 的「稳定下限」——当 WebGPU 不可用时，它保证模型仍然能跑起来。

## ONNX Runtime Web

ONNX Runtime Web 是微软 ONNX Runtime 的浏览器版本：一个统一的推理运行时，加载 ONNX 格式模型，自动在 WASM 和 WebGPU 后端之间切换。开发者只关心「加载模型 + 喂数据 + 取结果」，后端选择交给运行时处理，是浏览器部署模型最省心的方式。

```text
ONNX Runtime Web 的特点：
1. 统一运行时 —— 一份代码，多后端切换
2. 自动选后端 —— WASM / WebGPU 按可用性选择
3. ONNX 格式 —— 生态通用，模型从 PyTorch 导出
4. 量化支持 —— int8 量化减小体积、提速
```

```js
import * as ort from 'onnxruntime-web';

async function runInference(input) {
  const session = await ort.InferenceSession.create('./model.onnx', {
    executionProviders: ['webgpu', 'wasm'], // 优先 WebGPU，回退 WASM
  });
  const feeds = { input: new ort.Tensor('float32', input, [1, 3, 224, 224]) };
  const results = await session.run(feeds);
  return results.output.data;
}
```

ONNX Runtime Web 的价值在于「后端无关」：今天用 WASM 兜底，明天浏览器支持 WebGPU 后自动提速，代码几乎不用改。

## Transformers.js

Transformers.js 是 Hugging Face Transformers 的浏览器移植版，目标是把海量预训练模型「原样搬进浏览器」。它封装了 tokenizer、模型加载、pipeline 全部流程，一行代码就能跑文本分类、翻译、embedding 等任务，底层基于 ONNX Runtime Web（WASM/WebGPU）。

```text
Transformers.js 的特点：
1. 模型丰富 —— 直接复用 Hugging Face 海量模型
2. 开箱即用 —— pipeline 封装任务全流程
3. 多后端 —— 底层 ONNX Runtime Web，WASM / WebGPU
4. 前端友好 —— ESM / npm，可直接在 Vite 项目用
```

```js
import { pipeline, env } from '@xenova/transformers';

// 可选：启用 WebGPU 加速
env.backends.onnx.wasm.proxy = false;

// 文本向量化（embedding），用于语义搜索
const extractor = await pipeline('feature-extraction', 'Xenova/all-MiniLM-L6-v2');
const embedding = await extractor('前端工程化', { pooling: 'mean', normalize: true });
console.log(embedding.data.length); // 384 维向量
```

Transformers.js 让前端开发者不必理解模型底层，就能把 NLP 能力直接嵌进网页。

## 应用场景实战

### 场景一：本地敏感词检测

```js
// 数据不出浏览器：本地做文本分类
import { pipeline } from '@xenova/transformers';

let classifier;
async function loadModel() {
  classifier = await pipeline('text-classification', 'Xenova/distilbert-base-uncased');
}

async function check(text) {
  if (!classifier) await loadModel();
  const results = await classifier(text);
  return results[0]; // 本地推理，文本不上传服务器
}
```

### 场景二：图片目标检测（WebGPU 加速）

```js
import { pipeline, env } from '@xenova/transformers';

// 优先使用 WebGPU
env.backends.onnx.providers = ['webgpu', 'wasm'];

const detector = await pipeline('object-detection', 'Xenova/detr-resnet-50');

const image = document.getElementById('img');
const results = await detector(image.src);
// results: [{ label, score, box: { xmin, ymin, xmax, ymax } }]
results.forEach(({ label, score, box }) => {
  console.log(`${label} ${score.toFixed(2)} @ ${JSON.stringify(box)}`);
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 大模型先量化（int8/uint8）再进浏览器，控制体积和内存
2. 模型加载放 Web Worker，避免阻塞主线程
3. 后端优先 WebGPU、回退 WASM，兼顾性能和兼容
4. 模型缓存到 Cache Storage，二次访问免下载
5. 冷启动时显示加载进度，模型下载通常需要几秒到几十秒

### 踩坑记录

```text
坑 1：模型文件太大导致首屏卡顿
结论：页面加载模型耗时数秒甚至更久，用户以为卡死。
原因：未量化的模型动辄数百 MB，下载和初始化都慢。
解法：用量化模型、加载放 Worker、显示进度条、缓存到 Cache Storage。

坑 2：WebGPU 后端报错或不可用
结论：部分浏览器/设备上推理直接失败。
原因：WebGPU 兼容性未全覆盖，或设备 GPU 受限。
解法：executionProviders 写成 ['webgpu', 'wasm']，自动回退。

坑 3：主线程推理卡死 UI
结论：推理时页面冻结，交互无响应。
原因：同步/重计算推理跑在主线程。
解法：把推理放进 Web Worker，主线程只收发消息。

坑 4：跨域加载模型失败
结论：从 CDN 加载模型被 CORS 拦截。
原因：模型文件托管在不允许跨域的源上。
解法：模型放同源或配置正确 CORS 头，或用代理。

坑 5：内存溢出（OOM）
结论：大模型推理时浏览器崩溃或标签页被杀死。
原因：模型权重 + 中间激活占满内存。
解法：减小 batch、用量化模型、及时释放 session、控制并发推理。
```
