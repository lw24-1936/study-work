## 概述

Electron 采用「多进程」架构：一个主进程管理应用，多个渲染进程负责界面，Preload 与 IPC 承担进程间通信，ContextBridge 保障安全边界。

```text
Electron 进程模型：
1. Main —— 主进程，唯一，管理窗口与系统能力
2. Renderer —— 渲染进程，每个窗口一个，负责 UI
3. Preload —— 预加载脚本，架起安全通信桥
4. IPC —— 进程间通信（ipcMain/ipcRenderer）
5. ContextBridge —— 隔离上下文，安全暴露接口
```

```text
架构分层：
Renderer（HTML/JS，界面层）
  |-- ContextBridge：Preload 暴露的安全接口
  |-- IPC：invoke/handle 请求-响应
Main（Node/系统能力层）
  |-- 文件系统、子进程、系统 API
  |-- 窗口生命周期管理
```

## Main

主进程是 Electron 的「大脑」，控制应用全局。

```text
主进程核心职责：
1. 应用生命周期 —— ready、activate、window-all-closed
2. 窗口管理 —— 创建/销毁 BrowserWindow
3. 系统集成 —— 菜单、托盘、快捷键、通知
4. Node 全能力 —— 文件、网络、子进程
```

```js
const { app, BrowserWindow } = require('electron');

const windows = new Set();

function createWindow() {
  const win = new BrowserWindow({
    width: 1024,
    height: 768,
    webPreferences: {
      preload: `${__dirname}/preload.js`,
      contextIsolation: true,
    },
  });
  windows.add(win);
  win.on('closed', () => windows.delete(win));
  win.loadFile('index.html');
}

app.whenReady().then(() => {
  createWindow();
  app.on('activate', () => {
    if (BrowserWindow.getAllWindows().length === 0) createWindow();
  });
});

app.on('window-all-closed', () => {
  if (process.platform !== 'darwin') app.quit();
});
```

## Renderer

渲染进程是用户看到的界面，运行在独立的 Chromium 渲染环境。

```text
渲染进程特点：
1. 独立进程 —— 每个 BrowserWindow 一个，隔离崩溃
2. 标准 Web —— HTML/CSS/JS，可用任意前端框架
3. 无 Node 环境 —— 默认 nodeIntegration: false
4. 与主进程隔离 —— 需通过 IPC 通信
```

```html
<!-- index.html -->
<!DOCTYPE html>
<html>
<head>
  <meta charset="UTF-8" />
  <title>Electron App</title>
</head>
<body>
  <div id="app"></div>
  <script src="./renderer.js"></script>
</body>
</html>
```

```js
// renderer.js
window.addEventListener('DOMContentLoaded', () => {
  document.getElementById('app').textContent = '渲染进程已就绪';
});
```

## Preload

Preload 在页面加载前运行，是唯一能同时访问 Electron 能力与页面的脚本。

```text
Preload 特性：
1. 执行时机 —— 页面脚本之前
2. 运行环境 —— 独立 context，能 require Electron
3. 职责 —— 通过 contextBridge 暴露白名单接口
4. 不应直接操作 DOM
```

```js
const { contextBridge, ipcRenderer } = require('electron');

// 暴露给页面的安全接口
contextBridge.exposeInMainWorld('app', {
  // 请求-响应式
  invoke: (channel, ...args) => ipcRenderer.invoke(channel, ...args),
  // 订阅主进程推送
  on: (channel, callback) => {
    const listener = (_event, data) => callback(data);
    ipcRenderer.on(channel, listener);
    return () => ipcRenderer.removeListener(channel, listener);
  },
});
```

## IPC

IPC 让主进程与渲染进程互相通信，是架构的数据通道。

```text
IPC 通道类型：
1. 同步 —— 不推荐，阻塞渲染进程
2. 异步 send/on —— 单向消息
3. invoke/handle —— 请求响应（推荐）
4. 主进程 → 渲染进程 —— webContents.send
```

```js
// 主进程：处理请求
const { ipcMain } = require('electron');

ipcMain.handle('data:fetch', async (event, url) => {
  const res = await fetch(url);
  return res.json();
});

// 主进程：主动推送
function notifyRenderer(win, data) {
  win.webContents.send('data:update', data);
}
```

```js
// 渲染进程：调用与订阅
const data = await window.app.invoke('data:fetch', 'https://api.example.com/x');
const off = window.app.on('data:update', (d) => console.log(d));
```

## ContextBridge

ContextBridge 是 Preload 与页面之间的安全桥，把受控接口暴露到隔离的页面上下文。

```text
ContextBridge 机制：
1. 双上下文 —— preload 的 isolated world 与页面的 main world
2. 显式暴露 —— 只有 exposeInMainWorld 的东西页面可见
3. 类型限制 —— 只能暴露可序列化的函数/值
4. 防篡改 —— 页面无法覆盖暴露的方法
```

```js
const { contextBridge, ipcRenderer } = require('electron');

contextBridge.exposeInMainWorld('secure', {
  getVersion: () => ipcRenderer.invoke('version'),
  // 不能直接暴露 ipcRenderer 本身（危险）
});
```

```text
为什么不直接暴露 ipcRenderer？
若页面能拿到 ipcRenderer，恶意脚本可调用任意 channel，
绕过白名单校验，等于重新打开安全漏洞。
```

## 应用场景实战

### 场景一：搭建完整通信链路

```js
// main.js —— 主进程
const { app, BrowserWindow, ipcMain } = require('electron');

ipcMain.handle('sum', (e, a, b) => a + b);

app.whenReady().then(() => {
  const win = new BrowserWindow({
    webPreferences: {
      preload: `${__dirname}/preload.js`,
      contextIsolation: true,
    },
  });
  win.loadFile('index.html');
});
```

```js
// preload.js
const { contextBridge, ipcRenderer } = require('electron');
contextBridge.exposeInMainWorld('api', {
  sum: (a, b) => ipcRenderer.invoke('sum', a, b),
});
```

```js
// renderer.js
const result = await window.api.sum(1, 2);   // 3
```

### 场景二：主进程推送进度

```js
// 主进程
let progress = 0;
const timer = setInterval(() => {
  progress += 10;
  win.webContents.send('task:progress', progress);
  if (progress >= 100) clearInterval(timer);
}, 1000);
```

```js
// 渲染进程
window.api.on('task:progress', (p) => {
  document.getElementById('bar').style.width = `${p}%`;
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 主进程处理系统与 I/O，渲染进程专注 UI
2. 通信统一走 invoke/handle，保持单向数据流
3. Preload 只做「暴露接口」，不做业务逻辑
4. 通过 contextBridge 暴露最小白名单，不暴露 ipcRenderer
5. 监听器用后即清，避免内存泄漏

### 踩坑记录

```text
坑 1：preload 中直接操作 DOM
结论：preload 里 document 访问异常。
原因：contextIsolation 开启时，preload 与页面 DOM 隔离。
解法：preload 只暴露接口，DOM 操作放渲染进程。

坑 2：channel 命名冲突
结论：两个模块用同一 channel 相互干扰。
原因：ipcMain.handle 同名后注册覆盖前者。
解法：统一 channel 命名规范，加命名空间前缀。

坑 3：监听器未清理
结论：页面多次触发回调，内存上涨。
原因：ipcRenderer.on 注册后未 removeListener。
解法：on 时返回解绑函数，组件卸载时调用。

坑 4：invoke 无响应
结论：调用后 Promise 永不 resolve。
原因：主进程未注册对应 handle，或抛错未捕获。
解法：检查 handle 注册，主进程 try/catch 并返回错误。

坑 5：同步 IPC 卡死
结论：用 sendSync 导致渲染进程冻结。
原因：同步 IPC 阻塞渲染进程事件循环。
解法：改用 invoke/handle 异步通信。
```
