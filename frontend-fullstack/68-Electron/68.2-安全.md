## 概述

Electron 应用若配置不当，渲染进程的 XSS 可直接演变为系统级攻击（读写文件、执行命令）。安全的核心是「最小权限」与「进程隔离」。

```text
Electron 安全威胁模型：
1. 渲染进程被攻破 → 若可访问 Node，等于拿到系统权限
2. 首要原则 —— 让渲染进程「不可信」
3. 手段 —— 隔离、沙箱、禁 Node、CSP、校验 IPC
```

```text
安全配置基线（webPreferences）：
contextIsolation: true
nodeIntegration: false
sandbox: true
webSecurity: true
allowRunningInsecureContent: false
```

## Context Isolation

Context Isolation 是隔离 Preload 与页面 JS 的核心机制，是第一道防线。

```text
Context Isolation 原理：
1. Preload 运行在 isolated world（有自己的全局对象）
2. 页面运行在 main world
3. 两者共享 DOM 但 JS 上下文隔离
4. 页面无法直接访问 preload 的 require/Node
```

```js
const path = require('path');
new BrowserWindow({
  webPreferences: {
    contextIsolation: true,   // 必须开启
    preload: path.join(__dirname, 'preload.js'),
  },
});
```

```text
若关闭 contextIsolation（危险）：
preload 里的变量会污染页面全局，
页面可直接调用 preload 引入的 Node 模块，
一次 XSS 即可执行任意系统命令。
```

## Sandbox

Sandbox 让渲染进程运行在受限的沙箱环境，限制其系统访问能力。

```text
Sandbox 特性：
1. 渲染进程运行在 OS 沙箱中
2. 无法直接访问文件系统、网络以外的系统资源
3. Preload 在沙箱中只能使用有限的 Electron/Node API
4. 与 contextIsolation 配合，双层防护
```

```js
new BrowserWindow({
  webPreferences: {
    sandbox: true,
    contextIsolation: true,
    nodeIntegration: false,
  },
});
```

```text
Sandbox 下的限制：
1. preload 中只能 require 有限的模块（ipcRenderer、contextBridge 等）
2. 不能 require fs、child_process 等
3. 需要系统能力时必须通过主进程 IPC 代理
```

## Node Integration

Node Integration 控制渲染进程是否能直接使用 Node.js。

```text
nodeIntegration：
1. true —— 渲染进程可直接 require Node 模块（危险）
2. false —— 渲染进程无 Node 环境（推荐）
3. 默认 false，但老项目常误开
```

```js
// 危险配置（禁止）
new BrowserWindow({
  webPreferences: {
    nodeIntegration: true,
    contextIsolation: false,
  },
});
```

```text
为什么危险？
nodeIntegration: true 时，页面 JS 可直接：
require('child_process').exec('rm -rf ...')
一旦 XSS 注入，攻击者获得完整系统权限。
```

```js
// 安全配置
new BrowserWindow({
  webPreferences: {
    nodeIntegration: false,
    contextIsolation: true,
    sandbox: true,
  },
});
```

## CSP

CSP（Content Security Policy）限制渲染进程可加载的资源，缓解 XSS 危害。

```html
<!-- 在 index.html 中设置 CSP -->
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'" />
```

```text
CSP 规则：
1. default-src 'self' —— 默认只允许同源资源
2. script-src 'self' —— 禁止内联脚本与外域脚本
3. connect-src —— 限制网络请求目标
4. 禁止 eval —— 减少代码注入执行面
```

```text
注意：
1. CSP 是缓解措施，不是根本防线
2. 根本防线仍是隔离 + 禁 Node + IPC 校验
3. 开发时 CSP 过严可能影响热更新，需按环境配置
```

## IPC Validation

IPC Validation 在主进程校验所有来自渲染进程的请求，防止越权调用。

```text
IPC 校验要点：
1. 不信任渲染进程 —— 所有参数都要验证
2. 校验 sender —— 确认请求来源合法
3. 校验参数 —— 类型、范围、路径合法性
4. 最小权限 —— 只开放必要的能力
```

```js
const { ipcMain } = require('electron');
const path = require('path');
const fs = require('fs').promises;

const ALLOWED_DIR = '/safe/dir';

ipcMain.handle('file:read', (event, filePath) => {
  // 1. 校验来源
  if (!event.senderFrame.url.startsWith('file://')) {
    throw new Error('非法来源');
  }
  // 2. 校验类型
  if (typeof filePath !== 'string') {
    throw new Error('参数类型错误');
  }
  // 3. 校验路径（防止路径穿越）
  const resolved = path.resolve(filePath);
  if (!resolved.startsWith(path.resolve(ALLOWED_DIR))) {
    throw new Error('越权访问');
  }
  return fs.readFile(resolved, 'utf-8');
});
```

```text
校验清单：
1. 来源校验 —— event.senderFrame 检查
2. 类型校验 —— 参数类型断言
3. 范围校验 —— 路径、数值边界
4. 权限校验 —— 操作是否在允许清单内
```

## 应用场景实战

### 场景一：加固一个老项目

```js
// 统一封装安全窗口创建
const path = require('path');

function createSecureWindow(entry) {
  return new BrowserWindow({
    webPreferences: {
      contextIsolation: true,
      nodeIntegration: false,
      sandbox: true,
      preload: path.join(__dirname, 'preload.js'),
    },
  });
}
```

### 场景二：安全的文件读写代理

```js
// preload —— 只暴露两个受控方法
const { contextBridge, ipcRenderer } = require('electron');
contextBridge.exposeInMainWorld('file', {
  read: (p) => ipcRenderer.invoke('file:read', p),
  write: (p, data) => ipcRenderer.invoke('file:write', p, data),
});
```

```js
// 主进程 —— 严格校验
ipcMain.handle('file:write', (event, p, data) => {
  const resolved = path.resolve(p);
  if (!resolved.startsWith(ALLOWED_DIR)) throw new Error('越权');
  if (typeof data !== 'string') throw new Error('参数错误');
  return fs.writeFile(resolved, data, 'utf-8');
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 永远保持 contextIsolation: true、nodeIntegration: false、sandbox: true
2. 渲染进程加载内容加 CSP，限制资源与内联脚本
3. 所有 IPC 在主进程做来源、类型、范围三重校验
4. 导航限制 —— 用 will-navigate 阻止跳转到外部站点
5. 需要 Node 能力时一律由主进程代理，不让渲染进程直连

### 踩坑记录

```text
坑 1：为图省事开 nodeIntegration
结论：XSS 后攻击者拿到系统 shell。
原因：渲染进程可直接 require child_process 等。
解法：关闭 nodeIntegration，能力走 IPC 代理。

坑 2：CSP 写太松等于没写
结论：仍可加载外域脚本，XSS 危害不减。
原因：script-src 含 unsafe-inline 或 * 通配。
解法：script-src 'self'，按需放开具体域。

坑 3：IPC 不校验参数
结论：路径穿越读取任意文件。
原因：直接拼接用户输入路径。
解法：resolve 后校验是否在允许目录内。

坑 4：忽略导航劫持
结论：页面被跳转到恶意站点。
原因：未拦截 will-navigate，外部链接可导航窗口。
解法：拦截导航，外部链接用系统浏览器打开。

坑 5：preload 暴露过宽
结论：暴露整个 ipcRenderer 或 require。
原因：图方便把 ipcRenderer 直接 expose。
解法：只暴露白名单函数，参数在两端校验。
```
