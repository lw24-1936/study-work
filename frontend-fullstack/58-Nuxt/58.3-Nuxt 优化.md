## 概述

Nuxt 优化关注如何减少传输体积、降低服务端压力、加快首屏与交互速度。核心手段包括：按需加载组件（Lazy Component）、按路由配置渲染与缓存策略（Route Rules）、精简服务端到客户端的数据传输（Payload）、以及多级缓存（Caching）。

```text
Nuxt 优化的四个方向：
1. Lazy Component —— 组件按需加载，减小初始 JS 体积
2. Route Rules —— 按路由控制渲染方式、缓存与响应头
3. Payload —— 控制 SSR 数据如何传输给客户端
4. Caching —— 服务端响应缓存与静态资源缓存
```

## Lazy Component

Lazy Component（懒加载组件）让组件只在真正需要时才加载代码。Nuxt 通过 `Lazy` 前缀自动拆分并延迟加载组件，减少首屏 JS 体积。

```vue
<!-- pages/index.vue -->
<template>
  <div>
    <button @click="show = !show">切换</button>
    <!-- Lazy 前缀：组件代码只在首次渲染时异步加载 -->
    <LazyHeavyChart v-if="show" :data="chartData" />
  </div>
</template>

<script setup>
const show = ref(false);
const chartData = ref([]);
</script>
```

```text
懒加载的触发时机：
1. v-if 条件首次为 true 时
2. 动态组件 <component :is> 渲染时
3. 使用 Lazy 前缀后，Nuxt 自动为组件生成独立 chunk

对比：
<AppModal />       —— 随页面一起打包，立即加载
<LazyAppModal />   —— 独立 chunk，按需加载
```

```vue
<!-- 动态组件懒加载 -->
<template>
  <component :is="activeComponent" />
</template>

<script setup>
const activeComponent = shallowRef(null);

function loadChart() {
  // resolveComponent 配合动态导入实现按需
  import('~/components/Chart.vue').then((m) => {
    activeComponent.value = m.default;
  });
}
</script>
```

```text
懒加载的价值与代价：
价值：初始 bundle 更小，首屏 JS 下载/解析更快。
代价：交互时才加载，可能有短暂延迟；不适用于首屏关键组件。
```

## Route Rules

Route Rules 在 `nuxt.config.ts` 中按路由粒度配置渲染模式与缓存策略，是混合渲染的核心，也是优化服务端性能的关键。

```ts
// nuxt.config.ts —— 按路由优化
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true },               // 首页静态生成
    '/blog/**': { swr: 3600 },              // 缓存 1 小时，过期后台重建
    '/news/**': { isr: 300 },               // 增量静态再生成
    '/dashboard/**': { ssr: false },        // 后台纯 SPA
    '/api/search/**': { swr: 60 },          // 搜索接口缓存 1 分钟
    '/assets/**': { headers: { 'cache-control': 'public, max-age=31536000, immutable' } }
  }
});
```

```text
swr 与 isr 的区别：
swr（Stale-While-Revalidate）：
1. 首次请求生成并缓存
2. 缓存期内直接返回旧内容
3. 过期后先返回旧内容，同时后台重建并更新缓存

isr（Incremental Static Regeneration）：
1. 构建时或首次请求生成静态页
2. 到期后下次请求触发重新生成
3. 生成完成后替换旧缓存
```

```ts
// 单个路由用 routeRules 的完整配置项
routeRules: {
  '/api/legacy/**': { proxy: 'https://legacy.example.com/**' },
  '/old': { redirect: '/new' },
  '/api/private/**': { cors: true, headers: { 'x-custom': 'value' } }
}
```

## Payload

Payload 是 SSR 数据从服务端传输到客户端的载体。服务端渲染时获取的数据被序列化到 payload，随 HTML 返回，客户端水合时直接复用，避免重复请求。

```text
Payload 的工作原理：
1. 服务端执行 useAsyncData/useFetch 获取数据
2. 数据被序列化，写入 <script type="application/json">（即 payload）
3. HTML 与 payload 一起返回浏览器
4. 客户端水合时从 payload 还原数据，不再发起请求
```

```vue
<!-- 数据随 payload 传输，客户端不再重复请求 -->
<script setup>
const { data } = await useFetch('/api/posts');
</script>
```

```text
Payload 大小的影响：
payload 越大，HTML 体积越大，首屏解析越慢。
优化方向：
1. 只返回页面真正需要的数据（后端裁剪字段）
2. 大列表分页，不要一次性塞进 payload
3. 不参与首屏的数据用 lazy: true 延迟获取
```

```ts
// 控制 payload 行为
const { data } = await useFetch('/api/posts', {
  lazy: true,          // 不阻塞渲染，数据后台获取（不进首屏 payload）
  pick: ['title'],     // 只保留 title 字段，减小 payload
  transform: (res) => res.posts.map(p => ({ id: p.id, title: p.title }))
});
```

```ts
// 手动向 payload 注入数据（页面级）
// 在 <script setup> 中使用 useNuxtApp 的 payload
const nuxtApp = useNuxtApp();
nuxtApp.payload.myKey = { shared: 'data' };
```

## Caching

Caching（缓存）贯穿多个层面：服务端响应缓存（swr/isr）、HTTP 缓存头、静态资源指纹缓存、以及 Nitro 的存储缓存。

```text
缓存层级：
1. CDN 缓存 —— 边缘缓存静态资源与 HTML
2. 响应缓存 —— swr/isr 缓存服务端渲染结果
3. HTTP 缓存 —— cache-control 头控制浏览器/代理缓存
4. 数据缓存 —— useStorage 缓存接口/查询结果
```

```ts
// 接口层：用 useStorage 缓存外部数据
// server/api/hot-posts.ts
export default defineEventHandler(async (event) => {
  const cache = useStorage('cache');
  const cached = await cache.getItem('hot-posts');
  if (cached) return cached;                       // 命中缓存

  const posts = await $fetch('https://api.example.com/hot');
  await cache.setItem('hot-posts', posts, { ttl: 60 });  // 缓存 60 秒
  return posts;
});
```

```ts
// 静态资源：长缓存 + 指纹
routeRules: {
  '/_nuxt/**': {
    headers: { 'cache-control': 'public, max-age=31536000, immutable' }
  }
}
// 带内容哈希的文件可放心长缓存，更新后哈希变化自动失效
```

```text
缓存策略选择：
1. 公共内容、变化不频繁 → 长缓存 + swr/isr
2. 个性化内容 → 不缓存或极短缓存（ssr 实时渲染）
3. 静态资源（JS/CSS/图片）→ immutable 长缓存
4. 接口数据 → 短 TTL 的响应缓存或存储缓存
```

## 应用场景实战

### 场景一：营销首页 + 内容站提速

```text
需求：营销页追求加载速度与 SEO，内容站更新不频繁。
方案：结合懒加载与静态生成。

routeRules: {
  '/': { prerender: true },               // 首页静态化
  '/blog/**': { swr: 86400 }              // 文章缓存 1 天
}

首页内的大图表、视频播放器用 Lazy 前缀懒加载，
首屏只加载关键内容，JS 体积显著下降。
```

### 场景二：高流量列表页

```text
需求：列表页访问量大，后端压力高。
方案：接口缓存 + 客户端数据复用。

server/api/posts/index.ts 中用 useStorage 缓存查询结果（TTL 60 秒），
相同请求命中缓存，后端压力骤降。

前端用 useFetch({ lazy: true, pick: [...] }) 只取列表必要字段，
减小 payload 体积，首屏更快。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 首屏非关键组件加 Lazy 前缀，减小初始 bundle
2. 用 routeRules 按路由差异化策略，而非全站一刀切
3. 数据用 pick/transform 精简 payload，只传页面需要的字段
4. 静态资源用 immutable 长缓存，动态 HTML 用 swr/isr
5. 接口层用 useStorage 缓存热数据，降低后端压力

### 踩坑记录

```text
坑 1：懒加载组件首屏闪烁
结论：切到懒加载组件时出现短暂空白。
原因：组件代码按需异步加载，存在网络延迟。
解法：关键首屏组件不懒加载；可配合 loading 占位或 Suspense。

坑 2：swr 缓存导致内容更新延迟
结论：文章修改后页面仍显示旧内容。
原因：swr 缓存期内直接返回旧响应。
解法：缩短 swr 时间，或提供缓存刷新/失效机制，或关键内容用 ssr。

坑 3：payload 过大拖慢首屏
结论：HTML 体积巨大，解析缓慢。
原因：SSR 把大量数据序列化进 payload。
解法：pick 裁剪字段、分页、大块数据 lazy 获取。

坑 4：immutable 缓存后资源更新失效
结论：修改代码后用户仍加载旧 JS。
原因：未使用内容哈希，资源名不变导致缓存不失效。
解法：确保文件名带哈希（Nuxt 默认），只对带哈希资源用 immutable。

坑 5：lazy 数据在客户端拿不到
结论：lazy: true 后模板里数据为 null。
原因：lazy 数据不在首屏 payload，渲染时尚未返回。
解法：用 pending 判断渲染 loading，或配合 refresh 手动获取。
```
