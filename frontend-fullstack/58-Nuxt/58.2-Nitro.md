## 概述

Nitro 是 Nuxt 的服务端引擎，也被独立作为 UnJS 生态的一部分使用。它把服务端代码（API 路由、中间件）编译成平台无关的产物，通过不同的 Preset 部署到 Node、Deno、Cloudflare Workers、Vercel、Netlify 等任意环境。

```text
Nitro 的核心特征：
1. 文件式路由 —— server/ 目录下的文件自动成为服务端路由
2. 平台无关 —— 通过 Preset 适配不同部署目标
3. 边缘友好 —— 可运行在 Edge Runtime（Workers、Deno Deploy 等）
4. 内置工具 —— $fetch、useStorage、useRuntimeConfig 等自动导入
5. 统一缓存 —— 内置响应缓存与 KV 存储抽象
```

```text
server/ 目录结构（由 Nitro 驱动）：
server/api/         —— API 路由（返回 JSON）
server/routes/      —— 服务端路由（可返回 HTML 等任意响应）
server/middleware/  —— 服务端中间件（全局或命名）
server/utils/       —— 服务端工具（自动导入）
server/plugins/     —— Nitro 插件（注册钩子、初始化存储）
```

## Server Routes

Server Routes（服务端路由）位于 `server/routes/` 目录，返回任意 HTTP 响应（HTML、文件等），常用于服务端渲染页面、SSR 兜底、动态资源等场景。

```ts
// server/routes/sitemap.xml.ts —— 返回 XML 内容
export default defineEventHandler((event) => {
  const urls = ['/', '/about', '/blog'].map(
    (u) => `<url><loc>https://example.com${u}</loc></url>`
  );
  return new Response(
    `<?xml version="1.0" encoding="UTF-8"?><urlset>${urls.join('')}</urlset>`,
    { headers: { 'Content-Type': 'application/xml' } }
  );
});
```

```ts
// server/routes/hello.ts —— 返回 HTML
export default defineEventHandler((event) => {
  return `<h1>Hello Nitro</h1>`;
});
```

```text
Handler 的返回值类型：
1. 对象/数组 —— 自动 JSON.stringify
2. 字符串 —— 原样返回（Content-Type: text/html）
3. Response —— 完全自定义
4. null/undefined —— 204 No Content
```

```ts
// 从事件对象读取请求信息
export default defineEventHandler((event) => {
  const method = event.method;              // GET/POST/...
  const query = getQuery(event);            // 查询参数
  const body = readBody(event);             // 请求体（POST）
  const headers = getHeaders(event);        // 请求头
  return { method, query };
});
```

## API Routes

API Routes（API 路由）位于 `server/api/` 目录，专用于提供 JSON 接口，URL 前缀为 `/api`。这是搭建后端接口、BFF 层最常用的方式。

```text
文件 → API 路由映射：
server/api/hello.ts          →  GET /api/hello
server/api/posts/index.ts    →  GET /api/posts
server/api/posts/[id].ts     →  GET /api/posts/:id
server/api/posts/index.post.ts → POST /api/posts（HTTP 方法后缀）
```

```ts
// server/api/posts/[id].ts —— 动态参数接口
export default defineEventHandler(async (event) => {
  const id = getRouterParam(event, 'id');    // 读取路径参数
  const post = await fetchPostById(id);       // 业务查询
  if (!post) {
    throw createError({ statusCode: 404, statusMessage: 'Post Not Found' });
  }
  return post;
});
```

```ts
// server/api/posts/index.post.ts —— 创建资源（方法后缀决定 HTTP 方法）
export default defineEventHandler(async (event) => {
  const body = await readBody(event);
  // 校验 + 写入数据库
  return { id: 'new-id', ...body };
});
```

```ts
// 使用 createError 统一错误响应
export default defineEventHandler((event) => {
  const { token } = getQuery(event);
  if (!token) {
    throw createError({ statusCode: 401, statusMessage: 'Unauthorized' });
  }
  return { ok: true };
});
```

```text
客户端调用（自动导入 $fetch）：
在页面/composable 中直接用 $fetch('/api/posts')，
或 useFetch（SSR 阶段服务端直连，免跨域）。
```

## Presets

Presets（预设）定义 Nitro 如何构建与运行产物。同一份代码，切换 Preset 即可适配不同部署平台，无需改动业务逻辑。

```text
常见 Preset：
node-server      —— 标准 Node.js HTTP 服务器（默认）
node-cluster     —— Node.js 集群模式
vercel           —— Vercel（Serverless Functions）
netlify          —— Netlify Functions
cloudflare       —— Cloudflare Workers（Edge）
deno-deploy      —— Deno Deploy（Edge）
aws-lambda       —— AWS Lambda
bun              —— Bun 运行时
```

```ts
// nuxt.config.ts —— 指定 Preset
export default defineNuxtConfig({
  nitro: {
    preset: 'node-server'
  }
});
```

```text
构建与产物：
npm run build 后生成 .output/ 目录：
.output/server/   —— 服务端代码（不同 preset 结构不同）
.output/public/   —— 静态资源
.output/nitro.json —— Nitro 元信息

部署 Node：node .output/server/index.mjs
```

```text
Preset 的选择依据：
1. 传统服务器/容器 → node-server
2. Serverless 平台 → 对应平台 preset（vercel/netlify/aws-lambda）
3. 边缘网络、全球低延迟 → cloudflare / deno-deploy
```

## Edge Runtime

Edge Runtime 指把服务端代码运行在 CDN 边缘节点（Cloudflare Workers、Deno Deploy、Vercel Edge 等），实现全球低延迟。Nitro 通过 `cloudflare`、`deno-deploy` 等 Preset 支持边缘部署。

```text
Edge Runtime 的特点：
1. 就近响应 —— 代码运行在离用户最近的节点
2. 冷启动极快 —— 无需启动完整 Node 进程
3. 无状态 —— 不能依赖本地文件系统、长连接
4. 标准 Web API —— 使用 Fetch/Request/Response 等 Web 标准 API
```

```ts
// 边缘环境使用标准 Web API，而非 Node 专属 API
export default defineEventHandler((event) => {
  const url = getRequestURL(event);
  const country = event.headers.get('cf-ipcountry');  // Cloudflare 提供
  return { url, country };
});
```

```text
Edge Runtime 的限制：
1. 不能使用 Node 内置模块（fs、child_process 等）
2. 无持久化本地磁盘（存储走 KV/对象存储）
3. 计算时间与内存有上限
4. 部分 npm 包依赖 Node API，需 polyfill 或替换

解决：使用 Web 标准 API 与边缘存储（Cloudflare KV、Deno KV）。
```

```ts
// 边缘场景下用 useStorage 对接 KV 存储
// nuxt.config.ts 中配置 storage 驱动
export default defineNuxtConfig({
  nitro: {
    storage: {
      cache: { driver: 'cloudflare-kv-binding', binding: 'KV' }
    }
  }
});

// 服务端读写
export default defineEventHandler(async (event) => {
  await useStorage('cache').setItem('key', { v: 1 });
  return await useStorage('cache').getItem('key');
});
```

## Server Middleware

Server Middleware（服务端中间件）在请求到达 Handler 之前执行，用于鉴权、日志、CORS、请求改写等横切逻辑。全局中间件放在 `server/middleware/` 目录，按文件名字母序执行。

```ts
// server/middleware/auth.ts —— 全局鉴权中间件
export default defineEventHandler((event) => {
  const url = getRequestURL(event);
  // 仅保护 /api/admin 路径
  if (url.pathname.startsWith('/api/admin')) {
    const token = getHeader(event, 'authorization');
    if (token !== 'Bearer secret') {
      throw createError({ statusCode: 401, statusMessage: 'Unauthorized' });
    }
  }
});
```

```ts
// server/middleware/log.ts —— 日志中间件
export default defineEventHandler((event) => {
  const start = Date.now();
  const url = getRequestURL(event);
  // 记录请求开始时间，供后续读取
  event.context.startTime = start;
  console.log(`[${event.method}] ${url.pathname}`);
});
```

```text
中间件要点：
1. 全局中间件对 /api、/routes、页面 SSR 请求都会执行
2. 执行顺序按文件名字母序（可用 01.auth.ts 命名控制）
3. 不 return 任何值表示放行；return 值会直接作为响应
4. 可在 event.context 上挂载数据，传递给下游 Handler
```

```ts
// 命名中间件（按需在 API 路由中引用，而非全局）
// server/middleware/rate-limit.ts 中定义：
export default defineEventHandler((event) => {
  // 限流逻辑
});
```

```text
按路由应用中间件的方式：
在 definePageMeta 中为页面路由声明（页面中间件，属前端层）；
服务端中间件则通过 event.context 或路由前缀自行判断作用范围。
```

## 应用场景实战

### 场景一：BFF 聚合层

```text
需求：前端需要聚合多个后端接口，且要隐藏内部服务细节。
方案：用 Nitro 的 API Routes 做 BFF。

server/api/user-profile.ts:
export default defineEventHandler(async (event) => {
  const id = getRouterParam(event, 'id');
  const [user, orders] = await Promise.all([
    $fetch(`https://internal/user/${id}`),
    $fetch(`https://internal/orders?userId=${id}`)
  ]);
  return { user, orders };
});
```

### 场景二：全球低延迟的轻量接口

```text
需求：一个轻量接口希望全球用户都能快速访问。
方案：部署到 Edge Runtime（Cloudflare Workers）。

nuxt.config.ts:
export default defineNuxtConfig({
  nitro: { preset: 'cloudflare' }
});

接口逻辑使用标准 Web API，读写 Cloudflare KV，
冷启动快、就近响应，无需维护 Node 服务器。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 接口统一放 server/api，页面 SSR 兜底放 server/routes
2. 鉴权、日志等横切逻辑放 middleware，避免每个接口重复
3. 跨平台部署时优先使用标准 Web API，减少 Node 专属依赖
4. 错误用 createError 抛出，统一错误响应格式
5. 数据存储用 useStorage 抽象，方便切换本地/Redis/KV

### 踩坑记录

```text
坑 1：Edge 环境使用 Node API 报错
结论：部署到 Cloudflare 后 fs、path 等模块报错。
原因：Edge Runtime 不提供 Node 内置模块。
解法：改用 Web 标准 API；确需 Node 的包则换 node-server preset。

坑 2：中间件顺序不符合预期
结论：鉴权中间件没有先执行。
原因：全局中间件按文件名字母序执行。
解法：用 01.auth.ts、02.log.ts 等前缀命名控制顺序。

坑 3：动态 API 路由读取不到参数
结论：getRouterParam 返回 undefined。
原因：文件名未用 [id] 形式，或用了错误的方法读取。
解法：文件命名为 [id].ts，用 getRouterParam(event, 'id') 读取。

坑 4：POST 请求读不到 body
结论：readBody 返回空。
原因：未匹配到正确的方法后缀文件（如 index.post.ts）。
解法：按 HTTP 方法后缀命名文件（get/post/put/delete）。

坑 5：本地构建产物部署后路径错乱
结论：部署后静态资源 404。
原因：baseURL 或 preset 与部署环境不匹配。
解法：配置正确的 nitro.preset 与 baseURL，部署后校验 .output 结构。
```
