## 概述

CSS 架构要解决的核心问题：当样式规模从几十行膨胀到几万行时，如何保证**可读、可维护、可扩展、不互相污染**。CSS 本身没有作用域、没有模块、没有命名空间，所以架构方案本质上是「约定 + 工具」的组合。

```text
CSS 架构要解决的四大痛点：
1. 命名冲突 —— 全局作用域下同名类互相覆盖
2. 选择器层级失控 —— .a .b .c .d 深嵌套难维护
3. 样式冗余 —— 相同的样式在多处重复定义
4. 不可预测 —— 改了 A 处却影响了 B 处

主流方案：
BEM / OOCSS / SMACSS / ITCSS —— 纯约定（命名与分层规范）
CSS Modules / Scoped CSS —— 工具生成的局部作用域
Atomic CSS / Utility First —— 原子类 + 功能优先
```

## BEM 命名规范

BEM（Block Element Modifier）是最流行的命名约定，通过类名结构表达组件层级与状态，避免嵌套选择器。

```text
BEM 三要素：
Block    —— 独立的块/组件（.button、.card）
Element  —— 块的组成部分（.card__title、.card__body）
Modifier —— 块或元素的状态/变体（.button--primary、.card__title--large）

连接符：
Block__Element  —— 双下划线连接元素
Block--Modifier —— 双连字符连接修饰符
```

```css
/* Block */
.card { padding: 16px; border: 1px solid #eee; }

/* Element */
.card__title { font-size: 18px; font-weight: 600; }
.card__body { color: #666; }

/* Modifier */
.card--highlight { border-color: #0066cc; }
.card__title--large { font-size: 24px; }
```

```text
BEM 的优势：
1. 见名知义 —— 类名即结构，无需看 HTML 就能理解关系
2. 扁平化 —— 不依赖后代选择器，特异性始终为单类
3. 可扩展 —— 新增变体只需加 Modifier，不改原有结构

BEM 的代价：
1. 类名较长 —— HTML 略显臃肿
2. 需要团队遵守 —— 约定靠自觉，需配合 lint
```

## OOCSS 面向对象的 CSS

OOCSS（Object Oriented CSS）由 Nicole Sullivan 提出，核心是两条原则：**结构与皮肤分离**、**容器与内容分离**，追求样式的复用。

```text
原则一：结构与皮肤分离
结构 —— 尺寸、布局（宽高、边距、定位）
皮肤 —— 外观（颜色、背景、边框、阴影）

原则二：容器与内容分离
元素样式不应依赖它所在的具体容器，才能到处复用。
```

```css
/* 反例：结构 + 皮肤耦合，无法复用 */
.btn-primary {
  width: 100px;
  height: 32px;
  background: #0066cc;
  color: #fff;
}

/* 正例：拆成可组合的「对象」 */
.btn { width: 100px; height: 32px; }
.btn-primary { background: #0066cc; color: #fff; }
.btn-danger { background: #cc3300; color: #fff; }
```

```text
OOCSS 的意义：
它启发了后来的 BEM、SMACSS、Atomic CSS。
「多类组合」的思路（btn + btn-primary）直接影响了 Utility First 流派。
```

## SMACSS 可扩展模块化架构

SMACSS（Scalable and Modular Architecture for CSS）把样式按**职责**分成五类，是「分层思想」的早期实践。

```text
SMACSS 五类：
Base    —— 基础（reset、元素默认样式，如 body、h1、a）
Layout  —— 布局（页面骨架，如 .l-header、.l-sidebar、.l-grid）
Module  —— 模块（可复用组件，如 .card、.modal）
State   —— 状态（is- 前缀，如 .is-active、.is-hidden）
Theme   —— 主题（主题皮肤，如 .theme-dark）
```

```css
/* Base */
body { font-family: sans-serif; }
a { color: #0066cc; }

/* Layout */
.l-header { display: flex; height: 60px; }

/* Module */
.card { border: 1px solid #eee; }

/* State */
.is-active { background: #0066cc; }

/* Theme */
.theme-dark .card { border-color: #333; }
```

## ITCSS 倒三角分层

ITCSS（Inverted Triangle CSS）把样式按**特异性从低到高、通用性从高到低**排列成倒三角，越往下越具体、越少被复用。

```text
ITCSS 分层（从上到下）：
Settings   —— 变量、配置（Sass 变量、CSS 变量）
Tools      —— 工具（mixin、function）
Generic    —— 通用（reset、normalize）
Elements   —— 元素（h1、a、ul 等无类名元素）
Objects    —— 对象（布局类，如 .o-container、.o-grid）
Components —— 组件（具体 UI，如 .c-card、.c-button）
Utilities  —— 工具类（!important 的原子类，如 .u-hidden）

关键：每一层只允许使用前面已定义层的内容，越靠上层越通用、特异性越低。
```

```scss
/* Settings */
$color-primary: #0066cc;

/* Tools */
@mixin flex-center { display: flex; align-items: center; justify-content: center; }

/* Generic */
* { margin: 0; padding: 0; box-sizing: border-box; }

/* Elements */
h1 { font-size: 2rem; }

/* Objects */
.o-container { max-width: 1200px; margin: 0 auto; }

/* Components */
.c-card { @include flex-center; border: 1px solid #eee; }

/* Utilities */
.u-hidden { display: none !important; }
```

```text
ITCSS 的价值：
1. 层级清晰 —— 新成员知道每一层该放什么
2. 特异性可控 —— 整体特异性单调递增，冲突可预期
3. 便于 Tree Shaking —— Utilities 层可整层移除
```

## Utility First 与 Atomic CSS

Utility First（功能优先）把样式拆成**单一职责的原子类**（每个类只做一件事），在 HTML 中组合使用，代表作是 Tailwind CSS。

```text
Atomic CSS 核心思想：
1. 一个类只负责一个样式属性（.p-4 = padding）
2. 样式定义在类里，HTML 里通过组合类完成布局
3. 类名与样式一一对应，所见即所得
```

```html
<!-- Utility First 组合 -->
<div class="flex items-center justify-between p-4 bg-white rounded-lg shadow">
  <span class="text-lg font-semibold text-gray-900">标题</span>
  <button class="px-4 py-2 bg-blue-600 text-white rounded">按钮</button>
</div>
```

```text
Utility First 的优劣：
优点 —— 无需命名、无需切换文件、样式与结构同屏、高度一致
缺点 —— HTML 类名冗长、学习成本、需要工具（构建期按需生成）

与 BEM 的对比：
BEM —— 语义化组件类，适合组件库、长期维护的大中型项目
Utility —— 原子类组合，适合快速开发、设计系统约束强的团队
```

## CSS Modules 局部作用域

CSS Modules 通过**构建工具**给类名加上哈希，把全局 CSS 变成**模块级局部作用域**，从根源上消灭命名冲突。

```text
CSS Modules 原理：
1. 每个 .module.css 文件是一个独立模块
2. 构建时类名被转换为带哈希的唯一名（如 .button → .button_3jk2f）
3. JS 中 import styles from './x.module.css' 后，styles.button 拿到哈希名
4. 默认局部作用域，需全局的用 :global() 包裹
```

```css
/* Button.module.css */
.button { background: #0066cc; }
.button:hover { background: #0055aa; }

:global(.reset) { margin: 0; }
```

```jsx
import styles from './Button.module.css';

function Button() {
  return <button className={styles.button}>点击</button>;
}
```

## Scoped CSS 组件隔离

Scoped CSS 是组件化框架（Vue 等）提供的隔离方案：给组件的每个元素加一个唯一属性，选择器自动追加该属性，实现「样式只作用于本组件」。

```vue
<template>
  <button class="btn">点击</button>
</template>

<style scoped>
.btn {
  background: #0066cc;
}
</style>
```

```text
Scoped CSS 原理（Vue）：
1. 编译时给组件元素加 data-v-xxxxxx 属性
2. 样式选择器改写为 .btn[data-v-xxxxxx]
3. 实现组件级作用域，不影响其他组件

与 CSS Modules 对比：
Scoped —— 仍写普通 CSS，作用域靠属性选择器，子组件根节点会受父组件影响
CSS Modules —— 类名哈希，完全隔离，JS 导入引用
```

## 应用场景实战

### 场景一：中小型项目 —— BEM + 分层

```css
/* 组件内 BEM，全局按 SMACSS 分层管理 */
.c-button { padding: 8px 16px; border-radius: 4px; }
.c-button--primary { background: #0066cc; }
.c-button--disabled { opacity: 0.5; pointer-events: none; }
```

### 场景二：组件库 —— CSS Modules

```css
/* 组件库内部用 CSS Modules 彻底隔离，对外暴露语义类 */
.prefix-button { /* 默认样式 */ }
.prefix-button__icon { margin-right: 8px; }
```

### 场景三：快速迭代 —— Utility First

```html
<div class="grid grid-cols-3 gap-4">
  <div class="p-4 bg-white shadow-sm">卡片</div>
</div>
```

## 最佳实践与踩坑记录

### 最佳实践

1. 团队统一一套方案（BEM 或 Utility），不混用多套命名
2. 分层思想通用：无论哪种方案都建议按「通用 → 具体」组织
3. 组件库或长期项目优先 CSS Modules / Scoped CSS 实现隔离
4. 用 Stylelint 约束命名与嵌套深度，避免选择器超过 3 层
5. 新项目优先考虑 ITCSS 分层 + BEM 命名的组合

### 踩坑记录

```text
坑 1：BEM 命名过度拆分
结论：类名越来越长，反而难读。
原因：把每个视觉差异都拆成 Element/Modifier，粒度失控。
解法：只对「会被复用或需要主题化」的部分拆分，其余保持简单。

坑 2：深嵌套选择器
结论：.a .b .c .d 特异性飙升，后续无法覆盖。
原因：早期图方便用后代选择器，越写越深。
解法：坚持 BEM/原子类扁平化，嵌套不超过 3 层。

坑 3：CSS Modules 与第三方库样式冲突
结论：用了 :global 覆盖第三方样式，哈希后失效。
原因：:global 的类名不受哈希保护，语义理解错。
解法：第三方样式覆盖统一放在全局样式文件，不用 :global 在模块内覆盖。

坑 4：Scoped CSS 子组件根节点被父组件污染
结论：父组件 scoped 样式意外作用到子组件根节点。
原因：scoped 对子组件根节点仍生效（Vue 机制）。
解法：子组件根节点用独立类名，或用 :deep() 明确穿透。

坑 5：Utility First 全项目铺开但没统一 Design Token
结论：颜色、间距各写各的，出现 10 种相近蓝。
原因：原子类自由组合，缺乏设计令牌约束。
解法：原子类必须基于 Design Token 生成，禁止任意值。
```
