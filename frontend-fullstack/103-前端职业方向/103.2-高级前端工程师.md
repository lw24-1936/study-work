## 概述

高级前端工程师与初级的分水岭，在于从「实现功能」转向「对系统的质量与稳定性负责」：不仅要写对代码，还要让代码可维护、可扩展、可观测。其能力围绕架构、性能、安全、测试、监控五根支柱展开。

```text
高级前端工程师的五根能力支柱：
1. Architecture —— 代码分层与模块边界，可维护可扩展
2. Performance —— 性能指标、渲染优化与加载优化
3. Security —— 前端攻击面与防护，XSS/CSRF/CORS
4. Testing —— 单元/组件/E2E 测试与质量卡点
5. Monitoring —— 错误、性能与业务可观测性
```

## Architecture

架构能力是高级工程师的核心，指如何组织代码、划分模块、管理状态与依赖，让系统在规模增长后仍可维护。它不追求「高大上」，而是追求「边界清晰、依赖合理」。

```text
架构设计的关键问题：
1. 分层 —— 视图层、状态层、数据层、工具层的分离
2. 模块边界 —— 高内聚低耦合，明确的依赖方向
3. 状态管理 —— 服务端状态 vs 客户端状态的分治
4. 可扩展 —— 新需求落地不破坏既有结构
```

### 能力要求

- 能对已有代码做架构评审，指出耦合点与改进方向
- 能设计目录结构与模块分层，制定依赖规则
- 能区分「过度设计」与「合理抽象」，拒绝为了设计而设计

### 成长路径

- 初级：单文件堆代码，能跑就行
- 高级：分层分模块，边界清晰，依赖单向
- 专家：领域驱动，架构演进有据可依

## Performance

性能是用户体验的直接组成部分，也是高级工程师的必修课。核心是「先测量、再优化」，用指标定位瓶颈，用手段针对性解决。

```text
性能优化的闭环：
1. 测量 —— LCP/INP/CLS 等 Core Web Vitals
2. 定位 —— Performance 面板、Lighthouse、火焰图
3. 优化 —— 资源体积、渲染路径、网络链路
4. 回归 —— 优化后再次测量，验证收益
```

### 技能清单

```text
1. 掌握 LCP/FID/INP/CLS/TTFB 等指标含义与阈值
2. 会用 Lighthouse、Performance 面板定位瓶颈
3. 能优化资源加载：压缩、懒加载、CDN、缓存
4. 能优化渲染：减少重排重绘、代码分割、虚拟列表
5. 理解 React/Vue 的渲染优化手段
```

### 能力要求

- 能针对一个慢页面给出量化诊断与优化方案
- 能用数据证明优化的收益，而非凭感觉
- 能把性能指标接入 CI，防止性能回退

## Security

前端安全关注浏览器侧的攻防面，核心是理解「输入即不可信」原则，识别 XSS、CSRF、点击劫持等攻击并正确防护。

```text
前端安全的主要攻击面：
1. XSS —— 反射型/存储型/DOM 型，注入恶意脚本
2. CSRF —— 跨站请求伪造，借用户身份发请求
3. CORS —— 跨域资源共享的配置与滥用
4. 供应链 —— 依赖投毒、第三方脚本风险
```

### 技能清单

```text
1. 理解 XSS 三种类型与对应的转义/过滤手段
2. 理解 CSRF 原理与 Token/SameSite 防护
3. 掌握 CORS 配置与跨域安全策略
4. 了解 CSP、Trusted Types 等纵深防御
5. 关注依赖安全与第三方脚本风险
```

### 能力要求

- 能审查代码中的安全漏洞并给出修复方案
- 能制定安全编码规范，把防护下沉到框架与工具
- 能评估第三方依赖与脚本的安全风险

## Testing

测试是质量保障的最后一道防线，高级工程师要能分层建立测试策略：单元测试保证逻辑正确，组件测试保证交互正确，E2E 测试保证流程正确。

```text
前端测试的金字塔：
1. 单元测试 —— 函数、工具、纯逻辑，快而多
2. 组件测试 —— 渲染与交互，Testing Library
3. 集成测试 —— 组件组合与状态流转
4. E2E 测试 —— 真实浏览器完整流程，Playwright/Cypress
```

### 技能清单

```text
1. 会用 Jest/Vitest 写单元测试与断言
2. 会用 Testing Library 测组件交互而非实现细节
3. 会用 Playwright/Cypress 写 E2E 测试
4. 掌握 Mock 与测试隔离技巧
5. 理解覆盖率指标的意义与局限
```

### 能力要求

- 能为关键路径设计测试策略，而非追求 100% 覆盖率
- 能写出稳定、不脆弱的测试，减少假失败
- 能把测试接入 CI，作为合入门禁

## Monitoring

监控是可观测性的落地，让问题「在用户之前被发现」。高级工程师要建立错误监控、性能监控与业务监控，形成从告警到定位的闭环。

```text
前端监控体系：
1. 错误监控 —— JS 运行时错误、资源错误、Promise 错误
2. 性能监控 —— 首屏、接口耗时、Web Vitals 上报
3. 业务监控 —— 关键转化、埋点与漏斗
4. 告警与定位 —— Source Map 还原、链路追踪
```

### 技能清单

```text
1. 理解错误捕获机制（window.onerror、unhandledrejection）
2. 会用 Sentry 等平台做错误监控与 Source Map 还原
3. 掌握性能指标采集与上报方案
4. 理解日志、指标、链路追踪三者关系
5. 能设计监控告警的阈值与分级
```

### 能力要求

- 能搭建或接入一套前端监控体系
- 能通过监控数据定位线上问题根因
- 能建立监控驱动的稳定性改进闭环

## 应用场景实战

### 场景一：线上出现白屏，如何定位

```text
白屏问题定位链路：
1. 看监控 —— 错误平台是否有 JS 报错与堆栈
2. 还原堆栈 —— Source Map 定位到具体源码行
3. 复现 —— 结合用户环境（浏览器/版本）复现
4. 定位根因 —— 是数据异常、依赖冲突还是兼容性
5. 修复与回归 —— 修复后补测试，防止复发
```

### 场景二：首屏加载从 5 秒优化到 2 秒

```text
性能优化实战步骤：
1. 测量 —— Lighthouse 定位 LCP 与资源体积瓶颈
2. 压缩 —— 开启 gzip/brotli，压缩图片与字体
3. 分包 —— 路由级代码分割，按需加载
4. 缓存 —— 合理设置强缓存与协商缓存
5. 预加载 —— 关键资源 preload，路由 prefetch
6. 验证 —— 重新测量，确认指标达标
```

## 最佳实践与踩坑记录

### 最佳实践

1. 性能优化先测量再动手，用数据说话
2. 安全默认假设「输入不可信」，转义与校验前置
3. 测试优先覆盖核心业务与关键路径，而非追求覆盖率
4. 监控要覆盖错误、性能、业务三个维度
5. 架构演进小步走，用边界约束而非一次性重写
6. 建立 CI 质量门禁，让规范与测试自动化执行

### 踩坑记录

```text
坑 1：性能优化拍脑袋，不测量就改
结论：改了一堆「看起来有用」的优化，指标没变化甚至更差。
原因：没有基线数据，不知道瓶颈在哪。
解法：先用 Lighthouse/Performance 建立基线，再针对瓶颈优化。

坑 2：XSS 只在后端做，前端直接插 HTML
结论：innerHTML 拼接用户输入，导致 DOM 型 XSS。
原因：前端信任了未转义的数据。
解法：用 textContent 或框架的插值，避免 innerHTML 拼接。

坑 3：测试写得太细，绑定实现细节
结论：重构一次代码，测试大面积失败。
原因：断言了内部实现而非用户可见行为。
解法：用 Testing Library 按用户视角断言，而非测内部函数调用。

坑 4：监控只在报错时才看
结论：问题在用户投诉后才发现，被动响应。
原因：没有建立告警与日常巡检机制。
解法：设置错误率/性能告警阈值，主动巡检线上数据。

坑 5：Source Map 直接暴露到生产
结论：线上代码可被反推出源码，泄露业务逻辑。
原因：构建时把 source map 一并部署且未做访问控制。
解法：Source Map 只上传到监控平台，不部署到公网或加权限。
```
