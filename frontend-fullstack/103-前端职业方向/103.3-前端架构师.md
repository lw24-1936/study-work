## 概述

前端架构师是从「写代码」走向「设计系统」的角色，负责为团队或组织定义技术架构、技术选型、基础设施与工程规范，让多个团队能在统一约束下高效协作。其价值体现在「让系统长期可演进、让团队协作有章法」。

```text
前端架构师的职责版图：
1. Architecture —— 整体架构设计与技术选型
2. Micro Frontend —— 大规模应用的分治与解耦
3. Design System —— 设计语言与组件体系的统一
4. Platform —— 研发平台与基础设施的建设
5. Engineering Governance —— 工程治理与规范落地
```

## Architecture

架构师的核心职责是架构设计：基于业务规模与团队形态，选择合适的技术栈、分层结构与演进路径，并在「简单够用」与「可扩展」之间权衡。

```text
架构设计要回答的问题：
1. 技术选型 —— 框架、构建、状态管理的取舍
2. 分层设计 —— 应用层/领域层/基础设施层
3. 演进路线 —— 单体到微前端、模块化到平台化
4. 权衡 —— 复杂度、交付速度、团队能力的平衡
```

### 能力要求

- 能基于业务与团队给出有依据的技术选型
- 能设计分层清晰、依赖合理的大型应用架构
- 能制定架构决策记录（ADR），让决策可追溯

### 成长路径

- 高级工程师：能实现单点最优
- 架构师：能设计全局最优，平衡多方约束
- 首席架构师：能主导组织级技术演进

## Micro Frontend

微前端是「把巨石前端拆成可独立开发、独立部署的子应用」的架构模式，适用于多团队并行交付大型应用。核心是解决「应用拆分后的集成、隔离与协作」问题。

```text
微前端要解决的核心问题：
1. 集成方式 —— 构建时集成 vs 运行时集成
2. 应用隔离 —— JS/CSS/状态的作用域隔离
3. 通信与共享 —— 主子应用间的数据与依赖共享
4. 部署独立 —— 各子应用独立发布、独立回滚
```

### 技能清单

```text
1. 理解微前端的适用场景与代价
2. 掌握常见方案：qiankun、Module Federation、single-spa
3. 理解运行时集成与构建时集成的权衡
4. 能设计应用隔离、通信与共享机制
5. 能设计微前端的部署与灰度策略
```

### 能力要求

- 能判断「是否需要微前端」，避免为拆分而拆分
- 能设计子应用边界，减少跨应用耦合
- 能解决样式污染、状态隔离、性能等工程难题

## Design System

Design System（设计系统）是把设计语言、设计 Token 与组件库统一起来的一套体系，让产品在多团队协作下保持一致的体验与高效的研发。

```text
Design System 的层次：
1. Design Token —— 颜色、间距、字号等原子变量
2. 基础组件 —— Button/Input 等无业务语义组件
3. 业务组件 —— 带业务语义的组合组件
4. 规范文档 —— 用法、示例与无障碍要求
```

### 技能清单

```text
1. 理解 Design Token 的分层（primitive/semantic/component）
2. 能设计组件 API，兼顾灵活与约束
3. 掌握主题机制与多主题支持
4. 能搭建组件文档与示例（Storybook）
5. 理解组件发布与版本管理
```

### 能力要求

- 能主导设计系统的架构设计与落地
- 能平衡组件的通用性与业务灵活性
- 能推动设计系统的采用率与治理

## Platform

平台能力是架构师把能力「产品化」的结果：把构建、部署、脚手架、监控等能力沉淀为研发平台，让业务团队开箱即用，降低重复建设。

```text
前端研发平台的能力域：
1. 脚手架与模板 —— 统一初始化与项目规范
2. 构建与发布 —— 统一构建、部署与灰度
3. 组件与物料 —— 组件市场与物料沉淀
4. 可观测 —— 监控、日志与告警的统一接入
```

### 技能清单

```text
1. 理解平台化的目标：降本、提效、统一标准
2. 能设计脚手架与工程模板
3. 能设计统一构建发布流水线
4. 能沉淀组件物料与最佳实践
5. 能设计平台的度量与反馈闭环
```

### 能力要求

- 能识别重复建设，推动能力平台化
- 能设计平台 API 与接入成本
- 能平衡平台强制性与团队自主性

## Engineering Governance

工程治理是架构师的「软实力」：通过规范、流程与度量，让架构决策真正落地到日常开发，防止架构腐化。

```text
工程治理的手段：
1. 规范 —— 编码规范、目录规范、提交规范
2. 工具链 —— Lint、格式化、CI 卡点
3. 度量 —— 代码质量、技术债务、架构健康度
4. 流程 —— 代码评审、变更管理、技术决策
```

### 技能清单

```text
1. 能制定并推行编码与架构规范
2. 能把规范固化到工具链与 CI 门禁
3. 能建立代码质量与技术债务的度量体系
4. 能设计代码评审与技术决策流程
5. 能推动规范的持续演进
```

### 能力要求

- 能把「规范」转化为「自动化约束」，而非口头要求
- 能建立架构健康度看板，持续治理技术债
- 能平衡治理成本与团队效率

## 应用场景实战

### 场景一：把巨石应用拆分为微前端

```text
拆分实施步骤：
1. 现状盘点 —— 梳理模块、依赖与团队边界
2. 边界划分 —— 按业务域划分子应用，最小耦合
3. 基建先行 —— 搭好基座、路由与通信机制
4. 渐进迁移 —— 一个模块一个模块地切分
5. 治理闭环 —— 建立边界规范与健康度看板
```

### 场景二：从零搭建企业级 Design System

```text
搭建 Design System 步骤：
1. 盘点现状 —— 收集现有组件与样式碎片
2. 定义 Token —— 统一颜色/间距/字号等原子变量
3. 建设组件 —— 先基础组件，再业务组件
4. 文档化 —— Storybook 示例与使用规范
5. 落地推广 —— 接入现有项目，持续迭代
```

## 最佳实践与踩坑记录

### 最佳实践

1. 架构选型以业务与团队为出发点，避免技术炫技
2. 微前端「能不拆就不拆」，拆分要有明确收益
3. Design System 从 Token 开始，先统一再组件化
4. 治理靠工具链自动化，而非依赖自觉
5. 架构决策写 ADR，让演进有据可查
6. 平台建设小步快跑，先解决最高频的痛点

### 踩坑记录

```text
坑 1：为了微前端而微前端
结论：单体拆成微前端后，复杂度反而暴涨，交付变慢。
原因：没有评估团队规模与业务是否需要，盲目跟风架构。
解法：先回答「拆了解决什么问题」，收益不明确就不拆。

坑 2：Design System 只做组件不做 Token
结论：组件库风格难统一，改主题要到处改样式。
原因：跳过 Token 层，颜色间距硬编码在组件里。
解法：先定义 Design Token，组件消费 Token 而非写死值。

坑 3：规范只写在文档里，没有工具卡点
结论：规范形同虚设，代码评审靠人工反复提醒。
原因：规范没有固化到 Lint、CI 等自动化工具。
解法：把规范转成 ESLint 规则与 CI 门禁，自动拦截。

坑 4：微前端子应用样式互相污染
结论：A 应用的全局样式影响了 B 应用的页面。
原因：子应用 CSS 没有隔离，全局选择器互相覆盖。
解法：用 CSS Modules、Shadow DOM 或沙箱机制做样式隔离。

坑 5：平台强行统一，扼杀团队灵活性
结论：平台过于强势，团队特殊需求无法满足，绕开平台。
原因：平台只考虑统一，没预留扩展与豁免机制。
解法：平台提供默认能力 + 可插拔扩展，允许有据的例外。

坑 6：架构决策只靠口头，不落文档
结论：几个月后没人记得当初为什么这样设计，反复争论。
原因：架构决策没有记录，知识随人员流动丢失。
解法：用 ADR 记录每次重要架构决策的背景与取舍。
```
