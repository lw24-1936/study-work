## 概述

全栈工程师横跨前端与后端，能独立完成从页面到服务、从数据到部署的完整链路。核心价值在于「端到端交付能力」——减少跨端沟通成本，快速把想法变成可运行的产品。

```text
全栈工程师的能力版图：
1. Frontend —— 页面与交互，用户体验的出口
2. Node.js —— 服务端运行时，用 JS 打通前后端
3. Database —— 数据建模与持久化
4. API —— 接口设计，前后端契约
5. Cloud —— 部署与运维，让应用跑起来
```

## Frontend

全栈工程师的前端能力侧重「能独立交付可用界面」，不必深入到框架源码，但要有完整的页面开发与联调能力。

```text
前端能力要求：
1. HTML/CSS/JS —— 三件套基础扎实
2. 框架 —— React 或 Vue 组件化开发
3. 状态与请求 —— 状态管理、数据获取
4. 联调 —— 与后端接口对接、错误处理
```

### 技能清单

```text
1. 能独立开发页面与交互组件
2. 熟练与后端 API 对接（fetch/axios）
3. 理解跨域、鉴权、错误处理等联调问题
4. 能做基础的性能优化与体验打磨
```

### 能力要求

- 能独立完成一个功能的前端闭环
- 能与后端约定清晰的数据契约
- 能处理联调中的跨域、鉴权、异常等常见问题

## Node.js

Node.js 让全栈工程师用同一门语言（JavaScript/TypeScript）打通前后端，是前端工程师走向全栈最自然的技术路径。

```text
Node.js 核心能力：
1. 运行时 —— 事件循环、模块系统、异步模型
2. Web 框架 —— Express/Koa/Fastify/NestJS
3. 中间件 —— 鉴权、日志、错误处理
4. 性能 —— Stream、并发与资源控制
```

### 技能清单

```text
1. 理解 Node 事件循环与异步非阻塞模型
2. 会用 Express/Koa/NestJS 搭建服务
3. 掌握中间件机制与错误处理
4. 会用 Stream 处理大文件与流式响应
5. 理解进程管理、日志与健康检查
```

### 能力要求

- 能独立搭建一个可运行的 Web 服务
- 能设计服务端的错误处理与日志体系
- 能处理并发、限流等基础性能问题

## Database

数据库是数据的持久化层，全栈工程师要掌握数据建模、查询与访问模式，理解关系型与非关系型数据库的取舍。

```text
数据库核心能力：
1. 建模 —— 表结构/文档结构设计，范式与反范式
2. 查询 —— SQL 与索引优化，NoSQL 查询
3. ORM —— Prisma/TypeORM 等对象关系映射
4. 事务与一致性 —— 事务、锁与并发控制
```

### 技能清单

```text
1. 掌握关系型数据库基础（MySQL/PostgreSQL）
2. 理解索引原理与查询优化
3. 会用 ORM（Prisma/TypeORM）做数据访问
4. 了解 NoSQL（Redis/MongoDB）的适用场景
5. 理解事务、ACID 与并发问题
```

### 能力要求

- 能设计合理的表结构与索引
- 能写出高效的查询并优化慢查询
- 能根据场景选择关系型/NoSQL/缓存

## API

API 是前后端的契约，全栈工程师既是 API 的消费者也是提供者，要设计清晰、稳定、可演进的接口。

```text
API 设计要点：
1. 风格 —— REST 资源化 vs RPC vs GraphQL
2. 契约 —— 请求/响应结构、错误码、分页
3. 版本与演进 —— 兼容与版本管理
4. 安全 —— 鉴权、限流、输入校验
```

### 技能清单

```text
1. 掌握 REST API 设计（资源、方法、状态码）
2. 理解 GraphQL 与 RPC 的适用场景
3. 能设计统一的响应结构与错误码
4. 掌握接口鉴权（JWT/Session）与限流
5. 会用 OpenAPI 做接口文档与契约管理
```

### 能力要求

- 能设计清晰、一致的 API 契约
- 能处理 API 的版本演进与向后兼容
- 能做接口的鉴权、校验与限流

## Cloud

云与部署让应用真正「上线」，全栈工程师要掌握容器化、CI/CD 与云平台，实现从代码到生产的自动化交付。

```text
云部署能力：
1. 容器化 —— Docker 镜像与编排
2. CI/CD —— 自动构建、测试、部署
3. 云平台 —— 云函数、Serverless、托管服务
4. 运维基础 —— 日志、监控、回滚
```

### 技能清单

```text
1. 会用 Docker 打包与运行应用
2. 了解 Kubernetes 基础编排概念
3. 能搭建 CI/CD 流水线自动部署
4. 了解 Serverless/云函数与托管服务
5. 掌握日志采集、监控与回滚策略
```

### 能力要求

- 能独立完成应用的部署上线
- 能设计部署策略（滚动、蓝绿、灰度）
- 能通过日志与监控快速定位线上问题

## 应用场景实战

### 场景一：从零做一个待办事项全栈应用

```text
端到端交付流程：
1. 数据建模 —— 设计 todo 表结构（id/内容/状态/时间）
2. API 设计 —— REST 资源 /todos，定义增删改查
3. 后端实现 —— Node.js + ORM 实现接口与鉴权
4. 前端实现 —— 页面 + 状态管理 + 请求封装
5. 部署上线 —— Docker 打包，CI/CD 部署到云
```

### 场景二：设计一个前后端分离的鉴权方案

```text
鉴权方案设计：
1. 登录 —— 前端提交凭证，后端校验
2. 凭证 —— 后端签发 JWT（或 Session + Cookie）
3. 携带 —— 前端在请求头携带 Token
4. 校验 —— 后端中间件统一校验与续期
5. 刷新 —— 短时 access token + 长时 refresh token
```

## 最佳实践与踩坑记录

### 最佳实践

1. 前后端约定明确的 API 契约，用类型或文档固化
2. 输入校验放后端，前端校验只是体验优化
3. 数据访问走 ORM，避免拼接 SQL 注入
4. 密码用哈希（bcrypt）存储，绝不存明文
5. 部署用容器化 + CI/CD，减少手工操作
6. 敏感配置用环境变量/密钥管理，不进代码库

### 踩坑记录

```text
坑 1：前端校验代替后端校验
结论：绕过前端校验即可直接提交非法数据。
原因：前端校验只是体验，服务端没做输入校验。
解法：后端对所有输入做校验与过滤，前端校验仅作提示。

坑 2：SQL 字符串拼接导致注入
结论：用户输入拼进 SQL，可被注入删库。
原因：没有用参数化查询或 ORM。
解法：用参数化查询/ORM，禁止字符串拼接 SQL。

坑 3：密码明文存储
结论：数据库泄露后用户密码直接暴露。
原因：没有做哈希加盐。
解法：用 bcrypt/argon2 哈希加盐存储。

坑 4：跨域配置直接开 *
结论：接口允许任意来源，带来 CSRF 与数据泄露风险。
原因：CORS 配置为 Access-Control-Allow-Origin: *。
解法：精确配置允许的来源，携带凭证时禁用通配符。

坑 5：Token 无过期与刷新机制
结论：Token 永久有效，泄露后长期可被利用。
原因：没有设置过期时间与刷新机制。
解法：access token 短时有效，配 refresh token 续期。
```
