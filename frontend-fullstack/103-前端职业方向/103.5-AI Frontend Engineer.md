## 概述

AI Frontend Engineer 是前端与 AI 交叉的新兴方向，负责把大模型能力「产品化」到浏览器端：设计流式交互的 AI UI、编排 LLM/RAG/Agent 调用，并用 WebGPU/WASM 把推理与计算搬到端上。核心是既懂前端体验，又懂 AI 的技术边界。

```text
AI Frontend Engineer 的能力版图：
1. AI UI —— 流式输出、对话式交互与生成式界面
2. LLM —— 大模型调用、Prompt 与流式响应处理
3. RAG —— 检索增强生成，让模型「知道」你的知识
4. Agent —— 工具调用、规划与多步任务编排
5. WebGPU —— 端侧高性能计算与本地推理
6. WASM —— 把高性能模型与库编译到浏览器
```

## AI UI

AI UI 是面向生成式交互的界面设计：与传统的确定性表单不同，AI 应用有流式输出、不确定结果、多轮对话等特性，需要新的交互范式。

```text
AI UI 的设计要点：
1. 流式渲染 —— 逐字/逐 token 输出，边生成边显示
2. 对话式交互 —— 消息列表、角色区分、历史管理
3. 生成态管理 —— loading、中断、重试、回退
4. 不确定结果 —— 结果的展示、校验与人工确认
```

### 技能清单

```text
1. 掌握 SSE/WebSocket 流式接收与渲染
2. 能设计对话界面与消息状态管理
3. 处理生成中断、重试、回退等状态机
4. 理解 token 级渲染与性能优化
5. 能设计生成结果的展示与编辑交互
```

### 能力要求

- 能独立搭建一个流式对话前端
- 能设计优雅的生成态与错误态交互
- 能平衡「实时感」与「渲染性能」

## LLM

LLM（大语言模型）是 AI 应用的大脑，AI 前端工程师要理解其调用方式、Prompt 设计与流式响应处理，把模型能力接进前端。

```text
LLM 前端开发要点：
1. 调用 —— API 调用、鉴权、参数（temperature 等）
2. Prompt —— 系统提示词、上下文组装、模板
3. 流式响应 —— SSE 解析、增量渲染
4. 成本与限流 —— token 计量、并发控制、降级
```

### 技能清单

```text
1. 掌握 LLM API 的调用与参数调优
2. 能设计 Prompt 模板与上下文组装
3. 处理 SSE 流式响应与增量渲染
4. 理解 token 计费与成本控制
5. 能做超时、限流与降级处理
```

### 能力要求

- 能把模型能力封装成可复用的前端服务
- 能设计多轮对话的上下文管理
- 能处理模型输出的解析、校验与容错

## RAG

RAG（检索增强生成）通过「先检索相关知识，再让模型基于知识生成」，解决模型知识过时与幻觉问题，是构建私有知识问答应用的主流范式。

```text
RAG 的流程：
1. 索引 —— 文档切分、向量化、入库
2. 检索 —— 用户问题向量化，召回相关片段
3. 增强 —— 把检索结果拼进 Prompt 上下文
4. 生成 —— 模型基于上下文回答问题
```

### 技能清单

```text
1. 理解文档切分、向量化与向量检索
2. 能设计检索的召回与排序策略
3. 掌握 Prompt 组装（把检索结果注入上下文）
4. 理解引用与溯源（答案引用原文）
5. 能做 RAG 效果的评估与调优
```

### 能力要求

- 能搭建一个可用的 RAG 问答应用
- 能优化检索质量，减少答非所问
- 能设计引用溯源，让答案可验证

## Agent

Agent（智能体）让模型不再只是「一问一答」，而是能调用工具、做规划、执行多步任务，前端要负责把 Agent 的思考与执行过程可视化。

```text
Agent 的核心机制：
1. 工具调用 —— Function Calling，模型决定调用哪个工具
2. 规划 —— 把复杂任务拆成多步执行
3. 循环 —— 思考-行动-观察的循环（ReAct）
4. 记忆 —— 短期上下文与长期记忆
```

### 技能清单

```text
1. 理解 Function Calling 与工具注册
2. 能处理模型输出工具调用并执行
3. 设计 Agent 执行过程的可视化
4. 理解 ReAct 循环与多步任务编排
5. 处理工具执行失败与重试
```

### 能力要求

- 能实现工具调用的完整链路
- 能把 Agent 的执行过程清晰呈现给用户
- 能处理多步任务的异常与中断恢复

## WebGPU

WebGPU 是新一代浏览器 GPU API，让前端直接利用 GPU 做高性能并行计算，是端侧 AI 推理与图形计算的基础设施。

```text
WebGPU 的核心概念：
1. 适配器与设备 —— GPU 的抽象入口
2. 渲染管线/计算管线 —— 渲染与并行计算
3. 着色器 —— WGSL 语言编写 GPU 程序
4. Buffer 与内存 —— 显存数据读写
```

### 技能清单

```text
1. 理解 WebGPU 与 WebGL 的差异
2. 会用 WGSL 编写计算着色器
3. 掌握 Buffer 与数据上传/读取
4. 了解用 WebGPU 做端侧推理（如 LLM）
5. 关注浏览器兼容性与降级
```

### 能力要求

- 能用 WebGPU 做基础的并行计算
- 能评估 WebGPU 在端侧推理中的价值
- 能处理兼容性与降级方案

## WASM

WebAssembly（WASM）是一种可在浏览器运行的二进制格式，能把 C/C++/Rust 等语言编译到浏览器，以接近原生的性能运行，常用于把高性能模型与算法搬到前端。

```text
WASM 的核心要点：
1. 编译目标 —— 把 Rust/C/C++ 编译成 .wasm
2. 与 JS 互操作 —— 数据交换与函数调用
3. 性能场景 —— 计算密集、图像处理、模型推理
4. 生态 —— WASI、Emscripten、wasm-bindgen
```

### 技能清单

```text
1. 理解 WASM 的定位与适用场景
2. 会用 Rust/wasm-bindgen 或 Emscripten 编译 WASM
3. 掌握 JS 与 WASM 的数据交换
4. 了解 WASM 在模型推理/音视频中的应用
5. 理解 WASM 的内存模型与性能边界
```

### 能力要求

- 能把计算密集模块编译为 WASM 提速
- 能评估 WASM vs 纯 JS 的性能收益
- 能处理 WASM 与 JS 的互操作细节

## 应用场景实战

### 场景一：搭建一个流式 AI 聊天前端

```text
流式聊天实现步骤：
1. 请求 —— 前端发起对话请求，开启 SSE 连接
2. 流式接收 —— 逐段解析 SSE 返回的 token
3. 增量渲染 —— 把 token 追加到消息尾部
4. 状态管理 —— 处理停止、重试、多轮上下文
5. 优化 —— 节流渲染，避免频繁 DOM 更新
```

### 场景二：把模型推理搬到浏览器端

```text
端侧推理方案：
1. 模型选择 —— 选择可量化的轻量模型
2. 运行时 —— 用 WASM 或 WebGPU 运行推理
3. 加载 —— 模型分片下载与缓存
4. 推理 —— 用户数据不出端，本地计算
5. 降级 —— 不支持时回退到服务端调用
```

## 最佳实践与踩坑记录

### 最佳实践

1. 流式输出做节流与增量渲染，避免频繁 DOM 抖动
2. Prompt 集中管理，便于版本迭代与 A/B 测试
3. RAG 检索质量优先，先优化召回再优化生成
4. Agent 工具调用要可观测、可中断、可回退
5. 端侧推理先评估收益，避免为炫技增加复杂度
6. 模型输出永远做校验与容错，不直接信任

### 踩坑记录

```text
坑 1：流式输出每次 token 都触发一次完整渲染
结论：逐 token 直接 setState，页面卡顿。
原因：没有做增量更新与节流，渲染频率过高。
解法：按时间片或 token 数批量更新，或用增量 DOM 更新。

坑 2：模型输出直接当 HTML 渲染
结论：模型返回内容含恶意脚本，导致 XSS。
原因：把模型输出当作可信内容渲染。
解法：统一转义或用 markdown 安全渲染库。

坑 3：RAG 检索不相关导致答非所问
结论：模型基于无关片段回答，产生幻觉。
原因：检索召回质量差，上下文被噪声污染。
解法：优化切分与向量化，加召回排序与相关性过滤。

坑 4：Agent 工具调用死循环
结论：模型反复调用同一工具，任务卡住烧 token。
原因：没有设置最大步数与终止条件。
解法：限制最大循环步数，设置失败终止与人工接管。

坑 5：WebGPU 兼容性没做降级
结论：不支持 WebGPU 的浏览器直接报错白屏。
原因：没有检测特性支持与降级方案。
解法：检测 WebGPU 可用性，不支持时回退 WebGL/WASM。
```
