## 概述

指标（Metrics）是把应用状态量化成可监控的数字，用于判断健康度、发现劣化、驱动告警。前端指标分两大类：性能指标（LCP/INP/CLS）和业务健康指标（错误率、成功率、延迟）。

```text
前端核心指标全景：
业务健康指标：
1. Error Rate —— 错误率（多少请求/操作失败了）
2. Success Rate —— 成功率（多少请求/操作成功了）
3. Latency —— 延迟（操作/接口耗时）

核心 Web 性能指标（Core Web Vitals）：
4. LCP —— 最大内容绘制（加载速度）
5. INP —— 交互响应（响应性）
6. CLS —— 布局偏移（视觉稳定性）

细分指标：
7. API Latency —— 接口延迟
8. JS Error Rate —— JS 错误率
```

```text
指标与日志的区别：
日志 —— 离散事件（一条条记录，回答"发生了什么"）
指标 —— 聚合数字（统计值，回答"整体怎么样"）

指标的价值：
1. 趋势 —— 错误率是上升还是下降
2. 告警 —— 超过阈值自动报警
3. 对比 —— 新旧版本、不同环境对比
```

```js
// 基础指标采集工具
const metrics = {
  total: 0,
  failed: 0,
  durations: [],

  record(success, duration) {
    this.total++;
    if (!success) this.failed++;
    this.durations.push(duration);
  },

  getErrorRate() {
    return this.total ? this.failed / this.total : 0;
  },

  getSuccessRate() {
    return this.total ? (this.total - this.failed) / this.total : 0;
  },

  getAvgLatency() {
    return this.durations.length
      ? this.durations.reduce((a, b) => a + b, 0) / this.durations.length
      : 0;
  },
};
```

## Error Rate

Error Rate（错误率）是失败请求或失败操作占总数的比例，是衡量系统健康度最直接的指标。

```js
// 统计接口错误率
const apiStats = {
  total: 0,
  failed: 0,

  record(status) {
    this.total++;
    if (status >= 400 || status === 0) {
      this.failed++;
    }
  },

  errorRate() {
    return this.total ? this.failed / this.total : 0;
  },
};

// 在请求封装里统计
async function request(url, options) {
  const start = Date.now();
  try {
    const res = await fetch(url, options);
    apiStats.record(res.status);
    return res;
  } catch (err) {
    apiStats.record(0);   // 网络错误记 0
    throw err;
  }
}
```

```text
Error Rate 的计算与解读：
公式：失败数 / 总数 × 100%

阈值参考：
1% 以内 —— 正常
1%~5% —— 需要关注
5% 以上 —— 严重，需立即排查

注意：
1. 区分错误类型 —— 4xx（客户端）和 5xx（服务端）分开统计
2. 看趋势 —— 突增比绝对值更重要
3. 按维度拆 —— 按接口、按地域、按版本分别看错误率
```

## Success Rate

Success Rate（成功率）是成功操作占总数的比例，与错误率互补（成功率 = 1 - 错误率），常用于业务关键流程的健康监控。

```js
// 统计支付成功率（业务维度）
const paymentStats = {
  total: 0,
  success: 0,

  record(success) {
    this.total++;
    if (success) this.success++;
  },

  successRate() {
    return this.total ? this.success / this.total : 0;
  },
};

async function pay(orderId) {
  try {
    const result = await request('/api/pay', { method: 'POST' });
    paymentStats.record(true);
    return result;
  } catch (err) {
    paymentStats.record(false);
    throw err;
  }
}
```

```text
Success Rate 的应用场景：
1. 关键流程 —— 支付成功率、登录成功率、下单成功率
2. 可用性 SLA —— 成功率作为服务可用性承诺指标
3. 用户体验 —— 成功率直接反映用户能否完成任务

与 Error Rate 的关系：
Success Rate + Error Rate = 1（同一件事的两面）。
成功率更贴近业务视角（"用户成功了吗"），
错误率更贴近技术视角（"哪里出错了"）。
```

## Latency

Latency（延迟）是操作或请求的耗时，反映系统响应速度。前端关注接口延迟和交互延迟，通常用平均值和分位数（P50/P95/P99）衡量。

```js
// 采集延迟数据
const latencyData = [];

function recordLatency(duration) {
  latencyData.push(duration);
}

// 计算分位数
function percentile(p) {
  if (!latencyData.length) return 0;
  const sorted = [...latencyData].sort((a, b) => a - b);
  const index = Math.ceil(sorted.length * p) - 1;
  return sorted[index];
}

const p50 = percentile(0.5);   // 中位数
const p95 = percentile(0.95);  // 95% 的请求在此耗时内
const p99 = percentile(0.99);  // 99% 的请求在此耗时内
```

```text
为什么用分位数而非平均值：
平均值会被极端值拉高，掩盖真实体验。
P95 = 500ms 意味着 95% 用户都在 500ms 内完成，
比"平均 800ms（被少数超慢请求拉高）"更能反映大多数体验。

延迟的参考阈值：
接口延迟 P95 < 300ms 良好，< 800ms 可接受
交互延迟（INP）< 200ms 良好
```

```js
// 长任务（Long Task）监控，长任务会阻塞主线程
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('长任务耗时：', entry.duration);   // > 50ms 的长任务
  }
});
observer.observe({ entryTypes: ['longtask'] });
```

## LCP

LCP（Largest Contentful Paint，最大内容绘制）衡量页面主要内容加载完成的时间，是 Core Web Vitals 中衡量加载性能的核心指标。

```js
// 用 PerformanceObserver 采集 LCP
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const lastEntry = entries[entries.length - 1];   // 取最后一条
  console.log('LCP:', lastEntry.startTime, 'ms');
  reportMetric('lcp', lastEntry.startTime);
}).observe({ type: 'largest-contentful-paint', buffered: true });
```

```text
LCP 是什么：
页面视口内最大的内容元素（图片、文本块、视频）渲染完成的时间。

阈值（Google 标准）：
良好 < 2.5s
需要改进 2.5s ~ 4s
差 > 4s

优化方向：
1. 优化 LCP 元素（首屏大图、标题）的加载
2. 减少首屏渲染阻塞（关键 CSS 内联、JS 延迟）
3. 图片预加载、CDN 加速
```

```js
// 用 web-vitals 库更准确地采集
import { onLCP } from 'web-vitals';

onLCP((metric) => {
  console.log('LCP:', metric.value, 'ms');
  reportMetric('lcp', metric.value);
});
```

## INP

INP（Interaction to Next Paint，交互到下一次绘制）衡量页面响应交互的速度，是 2024 年起取代 FID 的 Core Web Vitals 交互性指标。

```js
// 用 web-vitals 采集 INP
import { onINP } from 'web-vitals';

onINP((metric) => {
  console.log('INP:', metric.value, 'ms');
  reportMetric('inp', metric.value);
});
```

```text
INP 是什么：
用户交互（点击、输入）到浏览器完成下一次绘制的时间。
取整个页面会话中最慢的一次交互。

阈值（Google 标准）：
良好 < 200ms
需要改进 200ms ~ 500ms
差 > 500ms

与 FID 的区别：
FID 只看首次交互的延迟，INP 看全部交互的最差表现，
INP 更能反映真实使用中的响应性。

优化方向：
1. 拆分长任务，避免主线程长时间阻塞
2. 减少事件处理中的重计算
3. 用 Web Worker 移走耗时计算
```

## CLS

CLS（Cumulative Layout Shift，累积布局偏移）衡量页面视觉稳定性，数值越大说明页面元素跳动越严重，体验越差。

```js
// 用 web-vitals 采集 CLS
import { onCLS } from 'web-vitals';

onCLS((metric) => {
  console.log('CLS:', metric.value);
  reportMetric('cls', metric.value);
});
```

```text
CLS 是什么：
页面加载过程中，可见元素位置发生意外偏移的程度总和。
无单位数值，越低越好。

阈值（Google 标准）：
良好 < 0.1
需要改进 0.1 ~ 0.25
差 > 0.25

常见原因：
1. 图片/广告无尺寸占位，加载后撑开布局
2. 动态注入内容导致下方元素下移
3. 字体加载后文字重排

优化方向：
1. 图片、iframe 显式设置宽高（预留空间）
2. 动态内容用固定容器或动画过渡
3. 字体用 font-display 控制加载行为
```

## API Latency

API Latency 是接口请求的耗时，是前端最常监控的延迟指标，通过请求封装统一采集。

```js
// 统一的接口延迟采集
async function request(url, options = {}) {
  const start = performance.now();
  try {
    const res = await fetch(url, options);
    const duration = performance.now() - start;

    // 采集耗时和状态
    recordApiMetric({
      url,
      method: options.method || 'GET',
      status: res.status,
      duration,
    });

    return res;
  } catch (err) {
    const duration = performance.now() - start;
    recordApiMetric({
      url,
      method: options.method || 'GET',
      status: 0,
      duration,
      error: err.message,
    });
    throw err;
  }
}
```

```text
API Latency 的监控维度：
1. 按接口 —— 哪个接口慢（url + method）
2. 按状态 —— 慢接口是否伴随错误
3. 按分位 —— P95/P99，看长尾
4. 按环境 —— 生产/预发对比

实践要点：
1. 请求封装里统一埋点，避免散落各处
2. 记录 method、url、status、duration 四要素
3. 慢接口（> 阈值）单独标记，便于排查
```

## JS Error Rate

JS Error Rate 是页面发生 JS 错误的比例（错误会话数 / 总会话数），反映前端代码的稳定性。

```js
// 统计 JS 错误率
const errorStats = {
  errorSessions: new Set(),   // 发生错误的会话
  totalSessions: new Set(),   // 所有会话

  markSession() {
    this.totalSessions.add(getSessionId());
  },

  markError() {
    this.errorSessions.add(getSessionId());
  },

  errorRate() {
    return this.totalSessions.size
      ? this.errorSessions.size / this.totalSessions.size
      : 0;
  },
};

window.addEventListener('error', (e) => {
  if (e.target === window) {
    errorStats.markError();
  }
});

window.addEventListener('unhandledrejection', () => {
  errorStats.markError();
});
```

```text
JS Error Rate 的计算与解读：
公式：发生错误的会话数 / 总会话数 × 100%

解读：
按会话（而非请求）统计，因为一个错误可能导致多次上报。
错误率 < 1% 通常是健康水平。

监控要点：
1. 区分错误类型 —— 按 errorId 聚合去重
2. 看趋势 —— 新版本发布后错误率是否上升
3. 关联影响 —— 错误率高的页面/版本优先处理
```

## 应用场景实战

### 场景一：搭建核心指标采集面板

```js
// metrics.js —— 统一采集核心指标
import { onLCP, onINP, onCLS } from 'web-vitals';

function reportMetric(name, value) {
  navigator.sendBeacon('/api/metrics', JSON.stringify({
    name,
    value,
    page: location.pathname,
    time: Date.now(),
    release: window.__APP_VERSION__,
  }));
}

// 采集 Web Vitals
onLCP((m) => reportMetric('lcp', m.value));
onINP((m) => reportMetric('inp', m.value));
onCLS((m) => reportMetric('cls', m.value));

// 采集接口延迟（在 request 封装里）
function recordApiMetric({ url, method, status, duration }) {
  reportMetric('api_latency', duration);
  if (status >= 400 || status === 0) {
    reportMetric('api_error', 1);
  }
}
```

### 场景二：指标告警阈值配置

```js
// 前端本地做阈值判断，超阈值打标记
const thresholds = {
  lcp: 2500,        // ms
  inp: 200,         // ms
  cls: 0.1,
  apiLatency: 300,  // ms
  errorRate: 0.01,  // 1%
};

function checkThreshold(name, value) {
  if (value > thresholds[name]) {
    console.warn(`指标超标: ${name} = ${value}`);
    reportMetric(`${name}_over_threshold`, 1);   // 上报超标事件
  }
}

// 监控平台侧配置告警：超标事件率 > 阈值时触发报警
```

## 最佳实践与踩坑记录

### 最佳实践

1. 延迟看分位数（P50/P95/P99），不只盯平均值
2. 错误率、成功率按维度拆（接口、版本、地域）分析
3. Web Vitals 用 web-vitals 库采集，比手写更准确
4. 指标采集统一封装，避免各业务重复实现
5. 指标上报轻量化，用 sendBeacon 批量发送
6. 建立基线 + 阈值告警，指标劣化自动报警

### 踩坑记录

```text
坑 1：只看平均值忽略长尾
结论：平均延迟达标，但少数用户极慢。
原因：平均值被长尾拉平，掩盖了 P99 的糟糕体验。
解法：重点看 P95/P99 分位数。

坑 2：错误率只按请求统计，重复上报虚高
结论：一个错误触发多次上报，错误率失真。
原因：未按会话/errorId 去重。
解法：按会话聚合，或按 errorId 去重统计。

坑 3：LCP 采集取错元素
结论：LCP 值波动大，不准确。
原因：手动采集没取最后的 entry，或没处理 buffered。
解法：用 web-vitals 库，或取 PerformanceObserver 最后一条。

坑 4：CLS 与用户交互混淆
结论：把用户主动触发的布局变化算进 CLS。
原因：未区分意外偏移和用户交互导致的正常变化。
解法：用 web-vitals 库的 CLS 计算（已排除交互后 500ms 内变化）。

坑 5：指标采集影响性能
结论：埋点本身拖慢页面。
原因：高频同步上报，阻塞主线程。
解法：异步批量上报，用 sendBeacon，采样而非全量。
```
