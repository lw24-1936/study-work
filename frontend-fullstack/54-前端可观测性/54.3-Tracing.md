## 概述

Tracing（链路追踪）记录一次请求在分布式系统中经过的所有环节，把前端调用、网关、后端服务、数据库串成一条完整的链路。前端 Tracing 负责生成 Trace ID 并传递给后端，让整条链路可追踪、可关联。

```text
Tracing 的核心概念：
1. Trace —— 一次完整请求的链路（由多个 Span 组成）
2. Span —— 链路中的一个环节（一次操作/调用）
3. Trace ID —— 标识整条链路的 ID
4. Span ID —— 标识单个 Span 的 ID
5. Context Propagation —— 上下文传播（ID 在服务间传递）

前端在 Tracing 中的角色：
前端是链路的起点，负责生成 Trace ID，
通过请求头传给后端，让前后端链路串联起来。
```

```text
一次请求的链路示例：
Trace ID: abc123（贯穿整条链路）
├─ Span A：前端页面加载（span-1）
├─ Span B：前端调 /api/orders（span-2）
│    ├─ Span C：网关转发（span-3）
│    ├─ Span D：订单服务处理（span-4）
│    │    └─ Span E：查询数据库（span-5）
│    └─ Span F：订单服务返回（span-6）
└─ Span G：前端渲染结果（span-7）
```

## Trace

Trace 是一次完整操作（如一个请求、一次用户操作）从开始到结束的整个链路，由多个 Span 按父子关系组成树状结构。

```js
// 创建一个 Trace（前端发起）
import { trace } from '@opentelemetry/api';

const tracer = trace.getTracer('frontend-app');

// 开始一个 Trace（根 Span）
const rootSpan = tracer.startSpan('page_load');

// Trace 内的所有操作都挂在根 Span 下
const apiSpan = tracer.startSpan('fetch_orders', {
  attributes: { 'http.url': '/api/orders' },
});

try {
  const data = await fetchOrders();
  apiSpan.setStatus({ code: 0 });   // 成功
} catch (err) {
  apiSpan.recordException(err);     // 记录异常
  apiSpan.setStatus({ code: 2, message: err.message });
} finally {
  apiSpan.end();
}

rootSpan.end();
```

```text
Trace 的特征：
1. 树状结构 —— 一个根 Span，多个子 Span，反映调用层级
2. 跨服务 —— 从前端到后端、数据库，贯穿所有环节
3. 有始有终 —— 每个 Span 有开始和结束时间，可算耗时

Trace 的价值：
1. 定位慢请求 —— 看链路中哪个 Span 耗时最长
2. 定位故障点 —— 看错误发生在哪个环节
3. 理解依赖 —— 一次请求依赖了哪些服务
```

## Span

Span 是 Tracing 的基本单位，代表一次具体操作（一次函数调用、一次 HTTP 请求、一次数据库查询），记录了操作名、起止时间、状态和属性。

```js
import { trace, SpanStatusCode } from '@opentelemetry/api';

const tracer = trace.getTracer('frontend-app');

async function loadUserData(userId) {
  // 创建一个 Span 包裹操作
  return tracer.startActiveSpan('load_user_data', async (span) => {
    try {
      // 设置 Span 属性
      span.setAttribute('user.id', userId);
      span.setAttribute('component', 'UserProfile');

      const data = await fetch(`/api/users/${userId}`);

      span.setStatus({ code: SpanStatusCode.OK });
      return data;
    } catch (err) {
      span.recordException(err);
      span.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
      throw err;
    } finally {
      span.end();
    }
  });
}
```

```text
Span 的关键要素：
1. 名称 —— 描述这个操作（如 fetch_orders）
2. 起止时间 —— 计算耗时
3. 状态 —— 成功 / 失败
4. 属性 —— 键值对，记录上下文（url、userId 等）
5. 事件 —— 时间点事件（如缓存命中）
6. 父子关系 —— parent Span ID 串联层级

Span 的属性设计：
记录对排查有帮助的信息，但不记录敏感数据。
常见属性：http.url、http.method、http.status_code、user.id。
```

```js
// Span 事件（记录操作过程中的关键节点）
const span = tracer.startSpan('checkout');

span.addEvent('cart_validated', { itemCount: 3 });
span.addEvent('payment_started', { method: 'wechat' });
span.addEvent('payment_succeeded', { orderId: 'o_123' });

span.end();
```

## Trace ID

Trace ID 是标识整条链路的唯一 ID，贯穿请求的所有环节。前端生成 Trace ID 并通过请求头传给后端，是前后端链路串联的纽带。

```js
// 生成 Trace ID
function generateTraceId() {
  // 128 位随机 ID，转成 32 位十六进制
  const bytes = crypto.getRandomValues(new Uint8Array(16));
  return Array.from(bytes)
    .map((b) => b.toString(16).padStart(2, '0'))
    .join('');
}

const traceId = generateTraceId();
console.log(traceId);   // 例如 '4bf92f3577b34da6a3ce929d0e0e4736'
```

```js
// 前端把 Trace ID 传给后端
const traceId = getOrCreateTraceId();

async function request(url, options = {}) {
  const headers = {
    ...options.headers,
    // W3C Trace Context 标准头
    traceparent: buildTraceParent(traceId, spanId),
  };
  return fetch(url, { ...options, headers });
}
```

```text
Trace ID 的生成与传递：
1. 生成 —— 前端（或网关）生成，随机 128 位
2. 传递 —— 通过请求头传给后端（traceparent）
3. 关联 —— 所有服务复用同一个 Trace ID

W3C Trace Context 标准：
traceparent: 00-<trace-id>-<span-id>-<flags>
例如：00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

## Span ID

Span ID 标识链路中的单个 Span，通过父子关系（parentSpanId 指向父 Span）构成树状结构，配合 Trace ID 完整定位到具体环节。

```js
// 生成 Span ID（64 位，16 位十六进制）
function generateSpanId() {
  const bytes = crypto.getRandomValues(new Uint8Array(8));
  return Array.from(bytes)
    .map((b) => b.toString(16).padStart(2, '0'))
    .join('');
}

// 手动构建父子关系
const rootSpanId = generateSpanId();
const childSpanId = generateSpanId();

const traceContext = {
  traceId: generateTraceId(),
  spanId: rootSpanId,           // 当前 Span
  parentSpanId: null,           // 根 Span 无父
};

const childContext = {
  traceId: traceContext.traceId,
  spanId: childSpanId,          // 子 Span
  parentSpanId: rootSpanId,     // 指向父 Span
};
```

```text
Span ID 的要点：
1. 唯一性 —— 每个 Span 有独立 ID
2. 父子关系 —— parentSpanId 指向父 Span，构成树
3. 与 Trace ID 配合 —— Trace ID 定位链路，Span ID 定位环节

完整的 traceparent 结构：
trace-id（32 位 hex）+ span-id（16 位 hex）+ flags

通过 traceparent，任意服务都能知道：
自己属于哪条链路（trace-id）、父环节是谁（parent-span-id）。
```

## Context Propagation

Context Propagation（上下文传播）是把 Trace ID、Span ID 等上下文信息在服务间传递的机制，让分布式链路能串联起来。前端通过请求头把追踪上下文传给后端。

```js
// 构建 W3C traceparent 请求头并传播
const traceContext = {
  traceId: generateTraceId(),
  spanId: generateSpanId(),
};

function buildTraceParent(traceId, spanId, flags = '01') {
  return `00-${traceId}-${spanId}-${flags}`;
}

// 在请求头中传播
async function tracedRequest(url, options = {}) {
  const spanId = generateSpanId();   // 为这次请求生成新 Span
  const headers = {
    ...options.headers,
    traceparent: buildTraceParent(traceContext.traceId, spanId),
  };

  const res = await fetch(url, { ...options, headers });

  // 从响应头读取后端返回的追踪信息（可选）
  const tracestate = res.headers.get('tracestate');

  return res;
}
```

```text
上下文传播的机制：
1. 前端生成 traceparent 头
2. 请求经过网关、后端时，各服务读取并继续传播
3. 每个服务生成自己的 span，parent 指向上一环
4. 最终所有 span 用同一个 traceId 串成完整链路

传播方式：
1. HTTP 头 —— traceparent / tracestate（W3C 标准）
2. 消息队列 —— 消息头携带上下文
3. 进程内 —— 全局变量 / AsyncLocalStorage

前端实践：
1. 用 OpenTelemetry SDK 自动注入 traceparent
2. 或手动在请求封装里加 traceparent 头
3. 确保所有 fetch/axios 请求统一传播
```

```js
// 用 OpenTelemetry 自动传播（推荐）
import { WebTracerProvider } from '@opentelemetry/sdk-trace-web';
import { FetchInstrumentation } from '@opentelemetry/instrumentation-fetch';
import { registerInstrumentations } from '@opentelemetry/instrumentation';

const provider = new WebTracerProvider();
provider.register();

registerInstrumentations({
  instrumentations: [new FetchInstrumentation()],
});

// 之后所有 fetch 请求自动带上 traceparent 头，
// 并自动生成 span 记录请求耗时和状态
```

## 应用场景实战

### 场景一：手动为关键请求加追踪

```js
// tracing.js —— 简单的追踪工具
const activeTrace = {
  traceId: null,
};

function startTrace() {
  activeTrace.traceId = generateTraceId();
  return activeTrace.traceId;
}

function generateTraceId() {
  return Array.from(crypto.getRandomValues(new Uint8Array(16)))
    .map((b) => b.toString(16).padStart(2, '0'))
    .join('');
}

function generateSpanId() {
  return Array.from(crypto.getRandomValues(new Uint8Array(8)))
    .map((b) => b.toString(16).padStart(2, '0'))
    .join('');
}

function tracedFetch(url, options = {}) {
  const spanId = generateSpanId();
  const traceparent = `00-${activeTrace.traceId}-${spanId}-01`;

  const start = performance.now();
  return fetch(url, {
    ...options,
    headers: { ...options.headers, traceparent },
  }).finally(() => {
    const duration = performance.now() - start;
    console.log(`[trace] ${url} 耗时 ${duration}ms`);
  });
}

// 使用
startTrace();   // 页面加载时开启一条 trace
const data = await tracedFetch('/api/orders');
```

### 场景二：前端链路与后端关联排查

```js
// 用户反馈下单失败，通过 traceId 关联前后端日志
async function checkout(order) {
  // 每次关键操作生成 span，统一 traceId
  const span = startSpan('checkout');

  span.addEvent('create_order', { orderId: order.id });
  const orderRes = await tracedFetch('/api/orders', {
    method: 'POST',
    body: JSON.stringify(order),
  });

  span.addEvent('pay_order', { orderId: order.id });
  const payRes = await tracedFetch('/api/pay', {
    method: 'POST',
    body: JSON.stringify({ orderId: order.id }),
  });

  // 前端日志带 traceId，后端日志也带同一个 traceId，
  // 排查时用 traceId 把整条链路的日志串起来
  span.end();
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 OpenTelemetry SDK 自动采集和传播，减少手写成本
2. 前端作为链路起点生成 Trace ID，通过 traceparent 头传给后端
3. Span 记录关键属性（url、userId、状态），不记录敏感数据
4. 采样控制成本 —— 高频请求全量追踪代价大，按比例采样
5. 统一 Trace ID 贯穿前后端，让日志、指标、追踪可关联
6. 关键业务流程（下单、支付）显式创建 Span 标记节点

### 踩坑记录

```text
坑 1：前后端 Trace ID 不一致
结论：前端和后端日志无法关联。
原因：前端没传播 traceparent，后端各自生成新 traceId。
解法：前端生成 traceId，通过 traceparent 头统一传播。

坑 2：全量追踪导致成本爆炸
结论：追踪数据量巨大，存储和性能都扛不住。
原因：所有请求都全量追踪，没采样。
解法：按比例采样（如 1%~10%），或只追踪关键链路。

坑 3：Span 未正确关闭（end）
结论：Span 时长异常，链路断裂。
原因：异常分支忘调 span.end()。
解法：用 try/finally 保证 end 一定执行，或用 startActiveSpan 自动管理。

坑 4：Span 记录敏感信息
结论：token、密码进了追踪数据。
原因：Span 属性全量塞入请求参数。
解法：白名单属性，敏感字段脱敏或不记录。

坑 5：忽略异步传播导致链路断裂
结论：异步回调里的请求没有父 Span。
原因：上下文传播没覆盖异步场景。
解法：用 OpenTelemetry 的 Context API 或 AsyncLocalStorage 管理异步上下文。
```
