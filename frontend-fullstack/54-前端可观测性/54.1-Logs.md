## 概述

日志（Log）是可观测性的基础，记录应用运行过程中的事件和状态。前端日志不同于后端日志——它分散在每个用户的浏览器里，需要结构化、分级、并主动上报到中心平台才有价值。

```text
前端日志的四个层次：
1. Console —— 本地调试输出
2. Structured Log —— 结构化日志（带字段，可检索）
3. Error Log —— 错误日志（关联错误上下文）
4. User Action Log —— 用户行为日志（还原操作路径）

日志的完整生命周期：
产生（业务埋点）
  → 结构化（加字段、加级别）
    → 缓冲（批量、防抖）
      → 上报（sendBeacon/批量接口）
        → 存储检索（ELK/Sentry 等）
```

```js
// 日志级别
console.debug('调试信息');
console.info('一般信息');
console.warn('警告');
console.error('错误');
```

```text
日志分级的意义：
debug —— 开发调试，生产不记录
info —— 关键业务事件（下单成功、登录）
warn —— 非致命异常（降级、重试）
error —— 错误（必须关注和上报）

分级让日志有优先级，生产环境可按级别过滤，控制上报量和噪音。
```

## Console

Console 是前端最基础的日志输出方式，通过 console 对象的一组方法输出到浏览器控制台，主要用于本地调试。

```js
// 基础输出
console.log('值：', value);
console.info('信息');
console.warn('警告');
console.error('错误');

// 格式化输出
console.log('用户 %s 的年龄是 %d', name, age);
console.log('对象 %o', { a: 1 });      // 可展开对象
console.log('%c高亮样式', 'color: red; font-size: 20px');
```

```js
// 分组与计时
console.group('用户请求');
console.log('开始请求');
console.log('收到响应');
console.groupEnd();

console.time('loadData');
await loadData();
console.timeEnd('loadData');   // loadData: 123.45ms

// 表格展示
console.table([
  { id: 1, name: 'Alice', age: 30 },
  { id: 2, name: 'Bob', age: 25 },
]);
```

```js
// 断言与追踪
console.assert(x > 0, 'x 必须大于 0');   // 条件为假时输出
console.trace('调用栈');                  // 输出当前调用栈
console.count('调用次数');                // 计数
console.countReset('调用次数');
```

```text
Console 的使用要点：
1. 调试为主 —— 生产环境应移除或降级 console.log
2. 合适的级别 —— 错误用 error，警告用 warn，别全用 log
3. 性能开销 —— 大量 log 影响性能，尤其大对象序列化
4. 对象引用 —— console.log 的对象是引用，展开时可能是最新值

生产环境的 console 管理：
1. 构建时用插件移除 console.log
2. 保留 console.error 用于兜底
3. 重写 console 方法统一接入日志上报
```

## Structured Log

Structured Log 是带结构化字段（键值对）的日志，而非自由文本。结构化让日志可被检索、过滤、聚合，是可观测性的关键。

```js
// 非结构化日志（难检索）
console.log('用户 alice 在 12:30 登录了');

// 结构化日志（可检索、可聚合）
function logEvent(event, data = {}) {
  const entry = {
    timestamp: new Date().toISOString(),
    level: data.level || 'info',
    event,                    // 事件名
    ...data,                  // 结构化字段
  };
  console.log(JSON.stringify(entry));
  // 生产环境：上报到日志平台
  sendToLogPlatform(entry);
}

logEvent('user_login', { userId: 'u_123', method: 'password', duration: 230 });
logEvent('order_created', { orderId: 'o_456', amount: 99, userId: 'u_123' });
```

```js
// 统一的日志工具封装
const logger = {
  info(event, data) {
    this._write('info', event, data);
  },
  warn(event, data) {
    this._write('warn', event, data);
  },
  error(event, data) {
    this._write('error', event, data);
  },
  _write(level, event, data) {
    const entry = {
      time: Date.now(),
      level,
      event,
      page: location.pathname,
      user: window.__USER__?.id,
      release: window.__APP_VERSION__,
      ...data,
    };
    // 缓冲批量上报
    buffer.push(entry);
  },
};
```

```text
结构化日志的字段设计：
1. 时间戳 —— 何时发生
2. 级别 —— 重要程度
3. 事件名 —— 发生了什么（统一命名，如 user_login）
4. 上下文 —— userId、orderId、page 等业务字段
5. 环境 —— release、environment

好处：
1. 可检索 —— 按字段过滤（如 level=error AND userId=u_123）
2. 可聚合 —— 按事件名统计频次
3. 可关联 —— 通过 userId/orderId 串联相关日志
```

## Error Log

Error Log 专门记录错误信息，除了错误本身，还要带上足够的上下文（调用栈、用户、页面、面包屑）才能定位问题。

```js
// 错误日志采集
function logError(error, context = {}) {
  const entry = {
    time: Date.now(),
    level: 'error',
    type: error.name || 'Error',
    message: error.message || String(error),
    stack: error.stack || '',
    page: location.href,
    user: window.__USER__?.id,
    ...context,
  };
  console.error('[Error]', entry);
  sendToLogPlatform(entry);   // 上报错误日志
}

// 全局捕获
window.addEventListener('error', (e) => {
  logError(e.error || new Error(e.message), {
    filename: e.filename,
    lineno: e.lineno,
  });
});

window.addEventListener('unhandledrejection', (e) => {
  logError(e.reason, { type: 'unhandledrejection' });
});
```

```js
// 业务代码里主动记录错误
try {
  await processOrder(order);
} catch (err) {
  logError(err, { orderId: order.id, action: 'processOrder' });
  throw err;
}
```

```text
Error Log 的关键要素：
1. 完整调用栈 —— 定位出错代码
2. 业务上下文 —— orderId、userId 等，回答"处理什么数据时出错"
3. 环境信息 —— 页面、版本、浏览器
4. 关联面包屑 —— 出错前的操作轨迹

Error Log 与 Console 的区别：
Console.error 只在本地，Error Log 会上报到平台持久化，
两者都要结构化，便于后续检索分析。
```

## User Action Log

User Action Log 记录用户的关键操作（点击、提交、跳转），用于还原用户行为路径、分析产品使用情况、辅助复现问题。

```js
// 用户行为日志采集
function logAction(action, data = {}) {
  const entry = {
    time: Date.now(),
    type: 'action',
    action,               // 动作名，如 'click_submit_order'
    page: location.pathname,
    user: window.__USER__?.id,
    ...data,
  };
  sendToLogPlatform(entry);
}

// 关键业务操作埋点
function submitOrder(order) {
  logAction('submit_order', { orderId: order.id, amount: order.amount });
  // ... 提交逻辑
}

function payOrder(order) {
  logAction('pay_order', { orderId: order.id, method: order.method });
  // ... 支付逻辑
}
```

```js
// 全局点击监听（自动记录用户操作）
document.addEventListener('click', (e) => {
  const target = e.target.closest('button, a, [data-action]');
  if (!target) return;

  logAction('click', {
    tag: target.tagName,
    text: target.textContent?.trim().slice(0, 50),
    action: target.dataset.action,   // 显式埋点优先
  });
}, { capture: true });
```

```text
User Action Log 的价值：
1. 还原路径 —— 用户操作序列，复现问题
2. 产品分析 —— 哪个功能用得多、转化漏斗
3. 关联错误 —— 出错前的操作，定位触发条件

与面包屑（Breadcrumb）的关系：
面包屑是"出错时的上下文"（随错误上报），
User Action Log 是"持续记录的行为流"（独立上报），
两者互补，面包屑更聚焦，行为日志更全面。
```

## 应用场景实战

### 场景一：统一日志工具 + 批量上报

```js
// logger.js —— 统一日志模块
class Logger {
  constructor(endpoint) {
    this.endpoint = endpoint;
    this.buffer = [];
    this.flushTimer = null;
  }

  log(level, event, data) {
    this.buffer.push({
      time: Date.now(),
      level,
      event,
      user: window.__USER__?.id,
      page: location.pathname,
      release: window.__APP_VERSION__,
      ...data,
    });

    // 错误日志立即上报，普通日志批量
    if (level === 'error') {
      this.flush();
    } else {
      this.scheduleFlush();
    }
  }

  scheduleFlush() {
    if (this.flushTimer) return;
    this.flushTimer = setTimeout(() => this.flush(), 5000);
  }

  flush() {
    clearTimeout(this.flushTimer);
    this.flushTimer = null;
    if (this.buffer.length === 0) return;

    const logs = this.buffer.splice(0, this.buffer.length);
    navigator.sendBeacon(this.endpoint, JSON.stringify(logs));
  }
}

const logger = new Logger('/api/logs');
export default logger;
```

### 场景二：关键业务流程的日志埋点

```js
// 电商下单流程的关键日志
async function checkout(cart) {
  logger.log('info', 'checkout_start', { cartId: cart.id, itemCount: cart.items.length });

  try {
    const order = await createOrder(cart);
    logger.log('info', 'order_created', { orderId: order.id, amount: order.amount });

    const payment = await pay(order.id);
    logger.log('info', 'payment_done', { orderId: order.id, method: payment.method });

    return order;
  } catch (err) {
    logger.log('error', 'checkout_failed', {
      cartId: cart.id,
      message: err.message,
      stack: err.stack,
    });
    throw err;
  }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 日志结构化（键值对），而非自由文本，便于检索聚合
2. 分级使用，错误即时上报，普通日志批量防抖
3. 错误日志带完整栈和业务上下文，不只记一句 message
4. 用 sendBeacon 上报，避免页面卸载时日志丢失
5. 生产环境移除 console.log，统一走日志工具
6. 关键业务流程埋点，还原用户操作路径

### 踩坑记录

```text
坑 1：生产环境残留大量 console.log
结论：控制台刷屏，性能下降，还可能泄露敏感数据。
原因：开发期日志没移除，也没统一管控。
解法：构建期移除 console.log，统一走 logger 工具。

坑 2：日志是自由文本无法检索
结论：出问题只能肉眼翻日志。
原因：日志用字符串拼接，没有结构化字段。
解法：结构化键值对，事件名统一，字段标准化。

坑 3：页面卸载时日志丢失
结论：跳转、关闭前的关键日志没上报。
原因：用普通 fetch 异步上报，随卸载中断。
解法：sendBeacon 或 fetch keepalive: true。

坑 4：高频操作日志导致请求风暴
结论：滚动、输入等高频事件刷爆上报接口。
原因：每个事件都立即上报。
解法：防抖 + 批量缓冲，合并上报。

坑 5：日志泄露敏感信息
结论：token、密码出现在日志平台。
原因：全量对象 JSON 化上报，未脱敏。
解法：白名单字段，过滤敏感信息。
```
