## 概述

Serverless 平台是托管无服务器函数的云服务：开发者上传函数代码，平台负责运行、伸缩、计费。不同平台在运行时、部署模型、冷启动表现和生态上各有侧重，选型时需要在「延迟、成本、生态、锁定」之间权衡。

```text
主流 Serverless 平台对比要点：
1. Cloudflare Workers —— 边缘优先，V8 isolate，全球节点最多
2. Vercel Functions —— 前端框架友好，与 Next.js 深度集成
3. AWS Lambda —— 生态最全，与 AWS 全家桶打通
4. Deno Deploy —— Deno 原生，Web 标准 API，部署极简
5. Edge Middleware —— 请求入口的轻逻辑层，非独立函数形态
```

```js
// 各平台函数入口的最小形态（抽象示意）
// Cloudflare Workers：默认导出 fetch
export default { async fetch(req, env) { return new Response('ok'); } };

// Vercel / AWS Lambda：导出 handler
export async function handler(req) { return { statusCode: 200, body: 'ok' }; }
```

## Cloudflare Workers

Cloudflare Workers 是部署在 Cloudflare 全球边缘网络上的函数运行时，基于 workerd（V8 isolate）实现毫秒级启动。它的最大优势是「边缘优先」：函数自动跑在全球数百个节点，离用户最近，冷启动几乎可以忽略。缺点是运行时与 Node 不完全兼容。

```text
Cloudflare Workers 特点：
1. 边缘部署 —— 全球数百节点就近执行
2. 毫秒级启动 —— V8 isolate 隔离，无传统冷启动
3. 配套齐全 —— KV、Durable Objects、R2、Queues、Cron
4. 定价友好 —— 免费额度大，按请求计费
```

```js
// Cloudflare Workers + KV 计数
export default {
  async fetch(request, env) {
    const count = Number(await env.KV.get('visits') ?? '0') + 1;
    await env.KV.put('visits', String(count));
    return new Response(JSON.stringify({ visits: count }), {
      headers: { 'content-type': 'application/json' },
    });
  },
};
```

```toml
# wrangler.toml：声明 KV 绑定
name = "my-worker"
main = "src/index.js"

[[kv_namespaces]]
binding = "KV"
id = "xxxxxxxx"
```

## Vercel Functions

Vercel Functions 是 Vercel 平台上的 Serverless 函数，与前端部署深度集成：前端项目目录下 `api/` 文件夹里的文件自动变成函数路由。它对 Next.js 支持最好，App Router 的 Route Handler、Server Actions 天然跑在 Vercel Functions 上，几乎零配置。

```text
Vercel Functions 特点：
1. 零配置 —— api/ 目录即路由，文件即函数
2. Next.js 原生 —— 与 App Router、ISR、Middleware 打通
3. 自动伸缩 —— 按流量扩容，支持流式响应
4. 区域部署 —— 可指定函数部署区域
```

```js
// Vercel Function：api/hello.js
export default function handler(req, res) {
  const { name = 'world' } = req.query;
  res.status(200).json({ message: `hello ${name}` });
}
```

```js
// Next.js App Router 的 Route Handler（跑在 Vercel Functions）
// app/api/posts/route.ts
export async function GET(request: Request) {
  const posts = [{ id: 1, title: 'Hello' }];
  return Response.json(posts);
}
```

## AWS Lambda

AWS Lambda 是 Serverless 的鼻祖和事实标准，生态最庞大：与 API Gateway、DynamoDB、S3、SQS 等 AWS 服务无缝打通。运行时支持 Node、Python、Go、Java、自定义容器等，适合对 AWS 生态有依赖的企业级应用。缺点是配置相对繁琐，冷启动（尤其容器）较明显。

```text
AWS Lambda 特点：
1. 生态最全 —— 与 AWS 全家桶原生集成
2. 多运行时 —— Node / Python / Go / Java / 容器
3. 事件源丰富 —— API Gateway、S3、SQS、DynamoDB 流
4. 冷启动明显 —— 传统容器/微虚拟机模型，启动较慢
```

```js
// AWS Lambda handler
export const handler = async (event) => {
  const name = event.queryStringParameters?.name ?? 'world';
  return {
    statusCode: 200,
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ message: `hello ${name}` }),
  };
};
```

```yaml
# serverless.yml：用 Serverless Framework 部署 Lambda
service: my-api
provider:
  name: aws
  runtime: nodejs20.x
functions:
  hello:
    handler: handler.handler
    events:
      - http:
          path: hello
          method: get
```

## Deno Deploy

Deno Deploy 是 Deno 团队推出的边缘 Serverless 平台，运行时就是 Deno：原生支持 TypeScript、Web 标准 API、ES Modules，无需打包即可部署。它强调「现代 Web 标准」，代码写起来最干净，从本地 Deno 到线上 Deno Deploy 体验一致。

```text
Deno Deploy 特点：
1. 原生 TS —— 无需构建，直接运行 TypeScript
2. Web 标准 —— 全面拥抱 fetch / Request / Response / Streams
3. 部署极简 —— 从 GitHub 或 CLI 一键部署
4. 内置 KV / Cron / 队列 —— 配套能力开箱即用
```

```ts
// Deno Deploy 函数：原生 TS，无需转译
Deno.serve((req: Request) => {
  const url = new URL(req.url);
  if (url.pathname === '/hello') {
    return Response.json({ hello: 'deno' });
  }
  return new Response('Not Found', { status: 404 });
});
```

```js
// 部署到 Deno Deploy
// deployctl deploy --project=my-project main.ts
```

## Edge Middleware

Edge Middleware 是跑在边缘、位于「请求到达应用之前」的轻逻辑层：它拦截每个请求，在响应生成前执行鉴权、重写、重定向、A/B 测试等逻辑。与独立函数不同，Middleware 是请求链路上的一环，通常无状态、极轻量，必须在很短的时间内完成并放行。

```text
Edge Middleware 的定位：
1. 请求前置 —— 在应用逻辑之前拦截请求
2. 轻而快 —— 只做快速决策，不做重计算
3. 无状态 —— 不维护会话，读取头/查询/地理位置
4. 典型用途 —— 鉴权、重定向、改写、限流、A/B 测试
```

```js
// Next.js Middleware（跑在边缘）
// middleware.ts
import { NextResponse } from 'next/server';

export function middleware(request) {
  const token = request.cookies.get('token')?.value;
  if (!token) {
    // 未登录重定向到登录页
    return NextResponse.redirect(new URL('/login', request.url));
  }
  return NextResponse.next();
}

export const config = {
  matcher: '/dashboard/:path*',
};
```

Middleware 的关键约束是「快」：它挡在所有请求前面，任何耗时逻辑都会直接放大到整个站点的延迟。

## 应用场景实战

### 场景一：多平台统一鉴权层

```js
// 同一个鉴权逻辑，用 Edge Middleware 挡在所有路由前面
// middleware.ts（Next.js）
import { NextResponse } from 'next/server';
import { jwtVerify } from 'jose';

export async function middleware(request) {
  const token = request.cookies.get('session')?.value;
  if (!token) {
    return NextResponse.redirect(new URL('/login', request.url));
  }
  try {
    await jwtVerify(token, new TextEncoder().encode(process.env.SECRET));
    return NextResponse.next();
  } catch {
    return NextResponse.redirect(new URL('/login', request.url));
  }
}

export const config = { matcher: ['/api/:path*', '/dashboard/:path*'] };
```

### 场景二：跨平台选型决策表实现

```js
// 一个按请求头分流到不同平台的网关（Cloudflare Workers 作统一入口）
export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    // 静态资源走边缘缓存
    if (url.pathname.startsWith('/static/')) {
      const cache = await caches.open('static');
      const cached = await cache.match(request);
      if (cached) return cached;
      const res = await fetch(request);
      await cache.put(request, res.clone());
      return res;
    }
    // 动态 API 转发到上游 Serverless 平台
    return fetch(`https://api.example.com${url.pathname}`, request);
  },
};
```

## 最佳实践与踩坑记录

### 最佳实践

1. 前端项目优先考虑 Vercel / Netlify，函数与部署同平台最省事
2. 需要全球最低延迟时选 Cloudflare Workers 或 Deno Deploy
3. 深度绑定 AWS 生态时选 Lambda，但要接受配置复杂度
4. 鉴权、重写等入口逻辑统一放 Edge Middleware，不散落在业务代码
5. 关注平台锁定：尽量用 Web 标准 API，保持可迁移性

### 踩坑记录

```text
坑 1：把 Node 代码直接搬到边缘平台
结论：本地跑得好好的，部署后报错。
原因：Cloudflare Workers / Deno Deploy 不兼容 Node 原生模块。
解法：只依赖 Web API，或用平台兼容的 polyfill / 替代包。

坑 2：忽略平台间的函数签名差异
结论：同一份 handler 在不同平台无法直接复用。
原因：Workers 用 fetch(req, env)，Lambda 用 handler(event)，Vercel 用 (req, res)。
解法：封装统一入口适配层，隔离平台差异。

坑 3：Middleware 里做重计算
结论：整站延迟被拉高，页面明显变慢。
原因：Middleware 挡在所有请求前面，耗时线性放大。
解法：Middleware 只做快速判断，重逻辑放回业务函数或后台。

坑 4：Lambda 冷启动导致首屏超时
结论：偶发请求明显变慢，P99 抖动大。
原因：Lambda 容器模型冷启动较慢。
解法：减小包体积、用 Provisioned Concurrency、或换边缘型平台。

坑 5：过度依赖平台私有能力导致锁定
结论：迁移平台时大量代码要重写。
原因：KV、Durable Objects、队列等绑定都是平台私有。
解法：抽象存储/队列接口，业务逻辑与平台能力解耦。
```
