## 概述

Edge Computing（边缘计算）把计算从「中心机房」下沉到「离用户最近的网络边缘节点」：请求不再千里迢迢回到一个数据中心，而是在地理上靠近用户的 CDN 节点就地处理。对前端而言，边缘计算意味着更低的网络延迟、更快的响应，以及「离用户更近」的服务能力。

```text
边缘计算的核心要点：
1. 就近处理 —— 在靠近用户的边缘节点执行代码
2. 低延迟 —— 省去回源数据中心的长途往返
3. 无冷启动 —— 边缘运行时用 V8/Workerd 隔离，启动极快
4. 全球分布 —— 一次部署，跑在数百个边缘节点
5. 轻量约束 —— 有限运行时 API，无 Node 原生模块
```

```js
// 边缘上的函数（Cloudflare Workers 风格）
// 部署后自动跑在离用户最近的节点
export default {
  async fetch(request, env) {
    // request.cf 携带边缘节点的地理位置信息
    const country = request.cf?.country ?? 'unknown';
    return new Response(JSON.stringify({ region: country }), {
      headers: { 'content-type': 'application/json' },
    });
  },
};
```

## Edge Runtime

Edge Runtime 是运行在边缘节点的 JavaScript 运行时。它不是一个完整的 Node.js，而是一个基于 V8（或 Deno 的 V8 沙箱、Cloudflare 的 workerd）裁剪出的轻量运行时：支持标准 Web API（fetch、URL、Request/Response、Web Crypto、Streams），但不支持 Node 原生模块（fs、net、child_process）和部分 Node API。

```text
Edge Runtime 的边界：
1. 支持 —— Web 标准 API（fetch、Request/Response、Streams、Crypto）
2. 支持 —— ES Modules、async/await、WebAssembly
3. 不支持 —— Node 的 fs / net / child_process 等原生模块
4. 不支持 —— 部分依赖 Node 能力的 npm 包
5. 运行环境 —— V8 isolate / workerd，毫秒级启动
```

```js
// Edge Runtime 支持 Web 标准 API
export default async function handler(request) {
  const url = new URL(request.url);
  const params = url.searchParams;

  // fetch 可用，可以聚合上游 API
  const upstream = await fetch(`https://api.example.com/data?id=${params.get('id')}`);
  const data = await upstream.json();

  return new Response(JSON.stringify(data), {
    headers: { 'content-type': 'application/json' },
  });
}
```

判断一段代码能否跑在 Edge Runtime，关键看它是否只依赖 Web API。凡是要读写本地文件系统、起 TCP 服务、调用原生库的，都不行。

## Edge Function

Edge Function 是部署在边缘节点上的函数：与 Serverless Function 同源，但执行位置在边缘而非中心机房。它继承了 Serverless 的按需运行、自动伸缩特性，又在延迟上更进一步——因为离用户更近。

```text
Edge Function 的特点：
1. 就近执行 —— 在边缘节点直接处理请求
2. 快速启动 —— 无传统冷启动，毫秒级拉起
3. 前端友好 —— 天然适合鉴权、重写、A/B 测试等轻逻辑
4. 上游聚合 —— 在边缘拼装多个 API 响应
```

```js
// Edge Function：在边缘做 A/B 测试分流
export default async function handler(request) {
  const cookie = request.headers.get('cookie') ?? '';
  const bucket = cookie.includes('variant=b')
    ? 'b'
    : Math.random() > 0.5 ? 'b' : 'a';

  if (bucket === 'b') {
    // 返回实验版页面
    return new Response('实验版首页', {
      headers: { 'set-cookie': 'variant=b; Path=/' },
    });
  }
  return new Response('正式版首页');
}
```

Edge Function 适合「轻逻辑、重延迟」的场景：它不该承载重计算或长任务，而应专注于请求入口处的快速决策。

## CDN Compute

CDN Compute 指的是直接在 CDN 节点上运行计算：传统 CDN 只能缓存和转发静态内容，CDN Compute 让节点具备了「执行代码」的能力，可以在缓存层之上做动态逻辑（鉴权、改写、聚合），把「动态」和「静态」统一到同一条边缘链路上。

```text
CDN Compute 的演进：
1. 传统 CDN —— 只缓存静态资源，动态请求回源
2. Edge Compute —— 节点可运行代码，动态逻辑就地处理
3. 统一入口 —— 静态缓存 + 动态计算在同一节点完成
4. 缓存感知 —— 代码可以读写边缘缓存（KV、Cache API）
```

```js
// CDN Compute：在边缘缓存 API 响应
export default async function handler(request, env) {
  const url = new URL(request.url);
  const cacheKey = new Request(url.toString(), request);
  const cache = await caches.open('api-cache');

  // 命中缓存直接返回
  const cached = await cache.match(cacheKey);
  if (cached) return cached;

  const res = await fetch(`https://origin.example.com${url.pathname}`);
  const clone = new Response(res.body, res);

  // 回源后写入边缘缓存
  await cache.put(cacheKey, clone.clone());
  return clone;
}
```

CDN Compute 的价值在于：把原本「回源数据中心」的请求拦截在边缘，用缓存或轻计算直接应答，既降低延迟又减轻源站压力。

## Low Latency

Low Latency（低延迟）是边缘计算追求的核心目标：把响应时间压到尽可能低。延迟主要来自物理距离（光速上限）和网络跳数，边缘计算通过「就近部署」直接从物理层面缩短距离，是降低延迟最有效的手段之一。

```text
降低延迟的层次：
1. 地理就近 —— 在离用户最近的节点处理
2. 边缘缓存 —— 命中缓存无需回源
3. 快速运行时 —— 无冷启动，毫秒级执行
4. 协议优化 —— HTTP/3、TLS 复用、连接保持
```

```js
// 用 request.cf 感知用户与节点的距离
export default async function handler(request) {
  const cf = request.cf ?? {};
  // cf.colo 是处理该请求的边缘节点代码
  // cf.asOrganization 是用户的网络运营商
  return new Response(JSON.stringify({
    colo: cf.colo,
    country: cf.country,
    city: cf.city,
  }), { headers: { 'content-type': 'application/json' } });
}
```

低延迟不是单一技术，而是一系列决策叠加的结果：把计算和缓存放到边缘，选对运行时，再配合现代网络协议。

## 应用场景实战

### 场景一：边缘地理位置鉴权

```js
// 在边缘根据国家/地区做访问控制，不把请求放回源站
export default {
  async fetch(request, env) {
    const cf = request.cf ?? {};
    const allowed = ['CN', 'US', 'JP'];

    if (!allowed.includes(cf.country)) {
      return new Response('Forbidden', { status: 403 });
    }
    // 放行后继续回源
    return fetch(request);
  },
};
```

### 场景二：边缘 API 聚合与改写

```js
// 在边缘一次聚合两个上游服务，减少前端请求次数
export default async function handler(request) {
  const [user, orders] = await Promise.all([
    fetch('https://api.example.com/user/me').then(r => r.json()),
    fetch('https://api.example.com/orders').then(r => r.json()),
  ]);

  // 在边缘拼装成前端需要的数据结构
  return new Response(JSON.stringify({
    name: user.name,
    orderCount: orders.length,
    recent: orders.slice(0, 3),
  }), {
    headers: { 'content-type': 'application/json' },
  });
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 边缘只放轻逻辑，重计算交给 Worker 或回源服务
2. 优先使用 Web 标准 API，避免依赖 Node 原生模块
3. 合理利用边缘缓存，减少回源请求
4. 用 request.cf 做地理相关逻辑（鉴权、就近、本地化）
5. 把可缓存的静态资源尽量推到边缘缓存层

### 踩坑记录

```text
坑 1：在边缘运行时引入 Node 专属依赖
结论：构建通过但运行时报错，或干脆无法构建。
原因：Edge Runtime 不提供 fs、net 等 Node 原生模块。
解法：改用 Web API 实现，或把依赖替换成边缘兼容的版本。

坑 2：误以为边缘缓存全局一致
结论：不同用户可能命中不同边缘节点的缓存，数据不一致。
原因：边缘节点分布全球，缓存是按节点分布的。
解法：对强一致数据不要依赖边缘缓存，或设置合理的缓存策略。

坑 3：把重计算丢给边缘函数
结论：CPU 密集型任务拖慢边缘节点，甚至超时。
原因：边缘函数有 CPU 时长限制，不适合重计算。
解法：重任务回源处理或交给后台 Worker / 队列。

坑 4：忽视边缘函数的冷启动边界
结论：看似无冷启动，但个别平台仍有初始化开销。
原因：不同平台运行时差异，隔离环境首次加载仍有成本。
解法：保持函数体积小、依赖少，惰性加载非必要模块。

坑 5：request.cf 字段依赖平台
结论：同一份代码在不同平台拿到的 cf 字段不一样。
原因：cf 是平台私有扩展，并非统一标准。
解法：做平台兼容，读字段前先判空并给默认值。
```
