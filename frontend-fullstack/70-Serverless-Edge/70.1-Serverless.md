## 概述

Serverless（无服务器）不是真的没有服务器，而是把「服务器管理」从开发者身上剥离：开发者只写函数，托管平台负责扩容、缩容、计费。对前端而言，Serverless 是「后端能力下沉到边缘」的核心载体——写一小段函数就能提供 API、鉴权、渲染，不再需要维护一台常驻的 Node 服务。

```text
Serverless 的核心特性：
1. 按需运行 —— 有请求才拉起实例，无请求不占资源
2. 自动伸缩 —— 平台按流量自动扩容，峰值零干预
3. 按量计费 —— 只按调用次数和执行时长付费
4. 无状态 —— 实例可随时销毁，状态必须外置
5. 事件驱动 —— 由事件（HTTP 请求、定时器、队列）触发
```

```js
// 一个典型的 Serverless 函数（Cloudflare Workers 风格）
export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    if (url.pathname === '/api/hello') {
      return new Response(JSON.stringify({ hello: 'world' }), {
        headers: { 'content-type': 'application/json' },
      });
    }
    return new Response('Not Found', { status: 404 });
  },
};
```

## Function

Function 是 Serverless 的最小执行单元：一段接收事件、返回响应的代码，由平台托管运行。

```text
Function 的关键点：
1. 入口是单个函数 —— 不是完整的 HTTP 服务
2. 平台负责加载、执行、回收
3. 有执行时长上限（几秒到几分钟不等）
4. 有内存/CPU 配额（按规格计费）
```

```js
// Vercel Function：一个文件一个函数
// api/user.ts —— 默认导出即 handler
export default function handler(req, res) {
  res.status(200).json({ id: 1, name: 'Alice' });
}
```

```js
// AWS Lambda 风格：exports.handler 是固定入口
export const handler = async (event) => {
  return {
    statusCode: 200,
    body: JSON.stringify({ message: 'ok' }),
  };
};
```

Function 与普通服务的本质区别：普通服务是一个常驻进程，能维护内存状态、长连接、定时任务；Function 是「随叫随到、用完即弃」的短命执行体。

## Trigger

Trigger 是触发 Function 执行的事件源。没有 Trigger，Function 永远不会运行。

```text
常见 Trigger 类型：
1. HTTP 请求 —— 最常见，网关把请求路由到函数
2. 定时器 Cron —— 定时触发（清理、报表、预热）
3. 消息队列 —— 消费队列消息（削峰、异步）
4. 对象存储事件 —— 上传文件后触发（图片处理）
5. 数据库变更 —— 数据写入后触发（CDC）
```

```js
// Cloudflare Workers Cron Trigger（wrangler.toml）
// 定时器触发，处理定时清理任务
export default {
  async scheduled(event, env, ctx) {
    // 每天凌晨清理过期数据
    await env.KV.delete('expired-key');
  },
};
```

```toml
# wrangler.toml 声明 cron 触发
[triggers]
crons = ["0 0 * * *"]
```

Trigger 决定了 Function 的「何时跑」，Function 决定了「跑什么」。设计 Serverless 应用的第一步就是梳理事件源。

## Cold Start

Cold Start（冷启动）是 Serverless 的经典性能问题：平台收到请求时没有现成的运行实例，需要临时拉起一个（加载运行时、初始化代码、建立连接），这段时间请求处于等待状态。

```text
冷启动的耗时构成：
1. 实例调度 —— 找到/分配可运行实例
2. 运行时启动 —— 加载 Node.js/Deno/Worker 运行时
3. 代码加载 —— 解析、编译函数代码
4. 初始化 —— 函数顶部代码（建连接、读配置）
```

```js
// 冷启动的代价示例
// 这段代码在冷启动时执行一次，之后热启动复用
const client = new Database({ /* 建连耗时 200ms */ });

export async function handler(event) {
  // 若每次请求都建连，冷启动 + 建连 = 明显延迟
  return await client.query('SELECT ...');
}
```

```text
降低冷启动的手段：
1. 减小包体积 —— Tree Shaking、按需加载
2. 少用重量级依赖 —— 能用原生 API 就不引库
3. 惰性初始化 —— 请求真正需要时才建连
4. 平台预热 —— 配置最小常驻实例（付费换延迟）
```

## Warm Start

Warm Start（热启动）是冷启动的对应概念：平台把刚执行完的实例保留一段时间，后续请求命中同一实例，跳过启动开销，直接执行代码。

```text
热启动 vs 冷启动：
1. 热启动 —— 实例复用，毫秒级响应
2. 冷启动 —— 实例新建，百毫秒到秒级响应
3. 实例复用窗口 —— 平台保留实例的时长（通常几十秒到几分钟）
4. 并发超限 —— 同时请求数超过实例容量时，再拉起新实例（又是冷启动）
```

```js
// 热启动可复用的「全局状态」
let counter = 0; // 实例存活期间保留

export async function handler() {
  counter++;
  // 注意：counter 只在当前实例内有效，不能当持久存储
  return { count: counter };
}
```

热启动带来的优化思路：把昂贵的初始化（数据库连接、SDK 加载、配置读取）放在函数顶部，让它们在冷启动时做一次，热启动时直接复用。

## Stateless

Stateless（无状态）是 Serverless 的核心约束：实例随时可能被销毁或新建，任何依赖「内存状态」的逻辑都不可靠。

```text
Stateless 的推论：
1. 不依赖本地文件 —— 实例文件系统是临时的
2. 不依赖内存变量 —— 实例销毁即丢失
3. 状态必须外置 —— 数据库、KV、对象存储
4. 可水平扩展 —— 无状态才能任意复制实例
```

```js
// 错误：依赖内存状态（实例销毁后计数丢失）
let visitCount = 0;
export async function handler() {
  visitCount++;
  return { count: visitCount }; // 不可靠
}
```

```js
// 正确：状态外置到 KV / 数据库
export async function handler(env) {
  const count = await env.KV.get('visits');
  const next = (Number(count) || 0) + 1;
  await env.KV.put('visits', String(next));
  return { count: next };
}
```

无状态带来的架构收益：任意实例都能处理任意请求，负载均衡、故障恢复、水平扩容都变得简单。代价是「状态管理」的责任转移到外部存储。

## Event Driven

Event Driven（事件驱动）是 Serverless 的编排范式：Function 不直接调用其他 Function，而是通过事件（写入队列、发布消息、触发存储）解耦，形成异步链路。

```text
事件驱动的价值：
1. 解耦 —— 生产者不关心消费者是谁
2. 削峰 —— 队列缓冲突发流量
3. 弹性 —— 每个环节独立伸缩
4. 可观测 —— 事件流本身就是链路记录
```

```js
// 事件驱动链路示例：上传图片 → 自动生成缩略图
// 1. 前端上传图片到对象存储
// 2. 存储事件触发 processImage 函数
// 3. processImage 生成缩略图，写回存储
export async function onUpload(event) {
  const { bucket, key } = event;
  const image = await storage.get(bucket, key);
  const thumb = await resize(image, { width: 200 });
  await storage.put(bucket, `thumb/${key}`, thumb);
  // 4. 发布「缩略图已生成」事件，通知前端
  await queue.publish({ type: 'thumb-ready', key });
}
```

同步请求-响应是 Serverless 的一种形态，事件驱动是更复杂场景下的标准形态。两者结合：API 用同步、后台处理用事件。

## 应用场景实战

### 场景一：前端直连的 API 服务

```js
// 用 Serverless Function 提供前端需要的 JSON 接口
// api/products.ts（Vercel / Netlify 风格）
export default async function handler(req, res) {
  const products = [
    { id: 1, name: '键盘', price: 399 },
    { id: 2, name: '鼠标', price: 199 },
  ];
  res.setHeader('Cache-Control', 's-maxage=60, stale-while-revalidate=300');
  res.status(200).json(products);
}
```

```js
// 前端调用
const res = await fetch('/api/products');
const products = await res.json();
```

### 场景二：表单提交与后台处理

```js
// 提交表单 → 写入 KV → 发布事件 → 异步处理
export default {
  async fetch(request, env) {
    if (request.method === 'POST') {
      const data = await request.json();
      await env.KV.put(`form:${data.id}`, JSON.stringify(data));
      // 事件触发后续异步任务
      await env.QUEUE.send({ type: 'form-submitted', id: data.id });
      return new Response('ok', { status: 202 });
    }
    return new Response('Method Not Allowed', { status: 405 });
  },
};
```

## 最佳实践与踩坑记录

### 最佳实践

1. 函数保持小而单一，一个函数做一件事
2. 昂贵初始化（建连、加载 SDK）放在函数顶部，冷启动只做一次
3. 状态一律外置到 KV/数据库，绝不依赖内存
4. 设置合理的执行时长上限和内存规格，控制成本
5. 关键路径做预热或配置最小常驻实例，降低冷启动延迟
6. 给函数加超时和错误处理，避免雪崩

### 踩坑记录

```text
坑 1：函数顶部建连导致冷启动缓慢
结论：冷启动时每个函数都要重新建立数据库连接。
原因：连接建立发生在函数初始化阶段，冷启动每次都执行。
解法：用平台提供的连接复用能力，或把建连移到请求真正需要时（惰性初始化）。

坑 2：依赖内存变量做计数
结论：访问量统计不准确，实例销毁后归零。
原因：Serverless 实例无状态，多个实例各有各的内存。
解法：计数用 KV/数据库，配合原子递增操作。

坑 3：超长任务被平台强制中断
结论：视频转码、大批量导出等长任务执行到一半被终止。
原因：函数有执行时长上限，超过即被平台杀掉。
解法：长任务拆成多次调用，或用队列 + 事件驱动分片处理。

坑 4：冷启动导致 P99 延迟飙升
结论：平均响应快，但峰值请求明显变慢。
原因：并发超过热实例容量时，新实例冷启动。
解法：配置最小常驻实例、减小包体积、用预热请求维持热实例。

坑 5：忽略无状态约束导致文件丢失
结论：运行时写入本地文件，下次请求读不到。
原因：实例文件系统是临时的，实例回收即清空。
解法：持久数据写对象存储或数据库，本地只放临时中间结果。
```
