## 概述

Promise 的拒绝（rejection）是异步错误的主要形态。与同步错误不同，异步错误无法用 try/catch 直接捕获，必须通过 .catch、async/await 或全局 unhandledrejection 事件处理，否则会变成"未处理的拒绝"静默丢失。

```text
Promise 错误的两条主线：
1. 主动处理 —— .catch / try-await-catch 捕获 rejection
2. 兜底处理 —— unhandledrejection 事件捕获漏网的拒绝

rejection 与同步错误的差异：
同步错误 —— 顺着调用栈向上传播，可被 try/catch 拦截
rejection —— 沿 Promise 链传播，只能被 .catch / await 捕获
```

```js
// 三种处理 rejection 的方式

// 1. .catch 链
fetch('/api/user')
  .then((res) => res.json())
  .catch((err) => console.error(err));

// 2. async/await + try/catch
async function getUser() {
  try {
    const res = await fetch('/api/user');
    return await res.json();
  } catch (err) {
    console.error('获取用户失败', err);
  }
}

// 3. .then 的第二个参数（不推荐，容易漏）
fetch('/api/user').then(
  (res) => res.json(),
  (err) => console.error(err)   // 只捕获 fetch 的 reject，不捕获后续 .then 的错误
);
```

## rejection

rejection 是 Promise 进入失败状态（rejected）时携带的错误原因。理解它如何产生、如何传播、如何捕获，是掌握异步错误处理的关键。

```js
// rejection 的产生
Promise.reject(new Error('手动拒绝'));

new Promise((resolve, reject) => {
  reject(new Error('异步操作失败'));
});

// async 函数里 throw 等价于 reject
async function fail() {
  throw new Error('抛出即拒绝');
}
```

```js
// rejection 沿链传播，直到被最近的 catch 捕获
fetch('/api/a')
  .then((res) => res.json())
  .then((data) => process(data))     // 若这里抛错
  .catch((err) => {
    // 前面任何一环的 rejection 都会到达这里
    console.error(err);
  });
```

```text
rejection 的传播规则：
1. 沿 .then 链向下传播，直到遇到 .catch
2. .catch 返回的 Promise 恢复为 fulfilled（除非又抛错）
3. 链中间的 .then 无法处理 rejection（除非传了第二个参数）
4. 链尾没有 .catch 时，rejection 变成 unhandled
```

```js
// Promise.all —— 一个失败则整体失败
try {
  await Promise.all([fetchA(), fetchB(), fetchC()]);
} catch (err) {
  // 任一失败都会到这里
}

// Promise.allSettled —— 不因失败中断，返回所有结果
const results = await Promise.allSettled([fetchA(), fetchB()]);
results.forEach((r) => {
  if (r.status === 'fulfilled') {
    console.log('成功', r.value);
  } else {
    console.log('失败', r.reason.message);
  }
});

// Promise.any —— 任一成功即可，全部失败抛 AggregateError
try {
  await Promise.any([fetchPrimary(), fetchBackup()]);
} catch (err) {
  // err 是 AggregateError，err.errors 是所有失败原因
}
```

```js
// 错误在链中转换：捕获后抛出新错误
fetch('/api/user')
  .then((res) => {
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return res.json();
  })
  .catch((err) => {
    throw new ApiError(`获取用户失败: ${err.message}`);   // 转换为业务错误
  });
```

## unhandledrejection

unhandledrejection 事件在 Promise 被拒绝且没有 catch 处理时触发，是全局兜底捕获异步错误的手段，也是前端错误上报的重要数据源。

```js
// 全局监听未处理的拒绝
window.addEventListener('unhandledrejection', (event) => {
  console.error('未处理的 Promise 拒绝：', event.reason);

  // 阻止默认行为（默认会在控制台打印错误）
  event.preventDefault();

  // 上报到监控平台
  reportError({
    type: 'unhandledrejection',
    message: event.reason?.message || String(event.reason),
    stack: event.reason?.stack,
  });
});
```

```text
unhandledrejection 的触发时机：
1. Promise 被 reject，且到当前微任务队列结束时仍无 .catch
2. 事件对象有两个关键属性：
   reason —— 拒绝原因（通常是 Error 对象）
   promise —— 被拒绝的 Promise 本身

为什么要兜底：
即使代码规范要求每个 Promise 都 catch，也难免遗漏，
unhandledrejection 是最后的防线，配合错误上报避免问题静默丢失。
```

```js
// 触发 unhandledrejection 的典型场景
// 场景一：忘记 catch
fetch('/api/data');   // 若网络失败，rejection 无人处理

// 场景二：async 函数没 await 也没 catch
async function load() {
  throw new Error('加载失败');
}
load();   // 返回的 Promise 被拒绝但无人处理

// 场景三：then 链里新产生的 rejection 无人接
Promise.resolve()
  .then(() => { throw new Error('链中错误'); })
  // 后面没有 .catch
```

```js
// 与 window.onerror 的分工
window.addEventListener('error', (e) => {
  // 捕获同步错误 + 资源加载错误（需 capture 阶段）
  console.log('同步/资源错误', e.message);
});

window.addEventListener('unhandledrejection', (e) => {
  // 捕获异步 Promise 拒绝
  console.log('Promise 拒绝', e.reason);
});
```

## 应用场景实战

### 场景一：封装统一的请求错误处理

```js
class ApiError extends Error {
  constructor(message, status) {
    super(message);
    this.name = 'ApiError';
    this.status = status;
  }
}

async function request(url, options) {
  try {
    const res = await fetch(url, options);
    if (!res.ok) {
      throw new ApiError(`请求失败 ${res.status}`, res.status);
    }
    return await res.json();
  } catch (err) {
    if (err instanceof ApiError) {
      throw err;   // 业务错误直接抛
    }
    // 网络错误转成统一格式
    throw new ApiError('网络异常，请检查连接', 0);
  }
}

// 调用方统一处理
async function loadData() {
  try {
    return await request('/api/users');
  } catch (err) {
    toast(err.message);
    return [];
  }
}
```

### 场景二：并发请求的部分成功处理

```js
// 多个接口，允许部分失败
async function loadDashboard() {
  const [stats, orders, notices] = await Promise.allSettled([
    request('/api/stats'),
    request('/api/orders'),
    request('/api/notices'),
  ]);

  return {
    stats: stats.status === 'fulfilled' ? stats.value : null,
    orders: orders.status === 'fulfilled' ? orders.value : [],
    notices: notices.status === 'fulfilled' ? notices.value : [],
  };
}

// 全局兜底，捕获所有漏网的拒绝
window.addEventListener('unhandledrejection', (e) => {
  console.error('[unhandled]', e.reason);
  e.preventDefault();
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每个 Promise 都要有 .catch 或 await try/catch 处理
2. 用 async/await + try/catch，比 .then 链更直观、更少漏捕获
3. 全局注册 unhandledrejection 兜底，配合错误上报
4. 批量并发按需选 allSettled（部分成功）或 all（全成功）
5. 请求错误统一封装成业务错误类型，调用方统一处理
6. 链中转换错误时保留原始错误信息（cause）

### 踩坑记录

```text
坑 1：async 函数忘 await 导致 rejection 丢失
结论：load() 没 await 也没 catch，错误静默丢失。
原因：async 函数返回的 Promise 被忽略。
解法：调用处 await 或 .catch，别裸调用 async 函数。

坑 2：.then 的第二个参数漏捕获链中错误
结论：只有 fetch 的 reject 被捕获，后续 .then 的抛错没人管。
原因：onRejected 只处理前一个 Promise 的拒绝。
解法：统一用 .catch 在链尾处理所有环节的错误。

坑 3：Promise.all 一失败全失败
结论：一个接口挂掉，整个页面数据都加载不出来。
原因：用 all 做并发，但业务上允许部分失败。
解法：允许部分成功用 Promise.allSettled。

坑 4：unhandledrejection 里又抛错
结论：兜底处理本身报错，进入死循环或丢失。
原因：事件处理函数内部代码出错。
解法：处理函数里 try/catch 包裹，避免二次异常。

坑 5：reject 非 Error 对象
结论：err.message / err.stack 是 undefined，上报信息残缺。
原因：reject('字符串') 而非 reject(new Error(...))。
解法：始终 reject Error 实例，保证有 message 和 stack。
```
