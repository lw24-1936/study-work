## 概述

JavaScript 的错误处理围绕 try/catch 和 Error 对象展开。理解错误类型、抛出与捕获机制，是写出健壮代码和处理线上问题的前提。

```text
错误处理的两个层面：
1. 同步错误 —— try/catch 捕获，Error 对象承载信息
2. 异步错误 —— Promise 链 / async-await（见 53.2）

Error 对象的核心属性：
message —— 错误描述
name —— 错误类型名
stack —— 调用栈（非标准但各引擎都支持）
```

```js
// 基本捕获结构
try {
  const result = riskyOperation();
} catch (err) {
  console.log(err.name);      // 错误类型
  console.log(err.message);   // 错误信息
  console.log(err.stack);     // 调用栈
}
```

```text
JavaScript 内置错误类型（均继承自 Error）：
Error —— 通用错误基类
TypeError —— 类型错误（访问 undefined 的属性等）
ReferenceError —— 引用错误（访问未声明变量）
SyntaxError —— 语法错误（解析阶段）
RangeError —— 范围错误（数组长度越界、栈溢出）
AggregateError —— 聚合错误（多个错误打包）
URIError —— URI 编解码错误（较少见）
```

## try/catch

try/catch 捕获同步代码中的异常，让程序在出错时能优雅降级而非直接崩溃。可选地配合 finally 执行收尾逻辑。

```js
try {
  // 可能抛错的代码
  const data = JSON.parse(userInput);
  process(data);
} catch (err) {
  // 处理错误
  console.error('解析失败：', err.message);
} finally {
  // 无论成功失败都执行（清理、关闭资源）
  closeConnection();
}
```

```text
try/catch 的三个关键点：
1. 只捕获同步错误 —— 异步回调里的错误抓不到（需 Promise catch）
2. 可以重新抛出 —— catch 里 throw，让上层处理
3. finally 恒执行 —— 适合做资源清理

catch 的参数在 ES2019 后可省略：
try { ... } catch { ... }   // 不关心错误对象时
```

```js
// 选择性捕获 + 重新抛出
try {
  saveToDatabase(record);
} catch (err) {
  if (err instanceof ValidationError) {
    showValidationMessage(err.message);   // 已知错误，就地处理
  } else {
    throw err;   // 未知错误，抛给上层统一处理
  }
}
```

```js
// 条件捕获（ES 提案语法，部分环境支持）
try {
  risky();
} catch (err) {
  if (err.code === 'NOT_FOUND') {
    // 只处理特定错误
  }
}
```

## Error

Error 是内置错误基类，可以 new 创建并 throw 抛出，也可以继承它定义自定义错误类型。

```js
// 创建并抛出自定义错误
throw new Error('数据格式不正确');

// 自定义错误类型
class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = 'ValidationError';
    this.field = field;
  }
}

try {
  throw new ValidationError('用户名不能为空', 'username');
} catch (err) {
  if (err instanceof ValidationError) {
    console.log(`${err.field}: ${err.message}`);  // username: 用户名不能为空
  }
}
```

```text
Error 的常见用途：
1. throw new Error() —— 主动抛出业务错误
2. instanceof 判断 —— 区分错误类型分别处理
3. 自定义错误类 —— 携带领域信息（字段、错误码）

Error 的陷阱：
1. stack 属性是非标准但普遍支持，报错上报时很有用
2. 自定义错误要手动设 name，否则 instanceof 判断会混淆
```

```js
// 带错误码的业务错误
class ApiError extends Error {
  constructor(message, status) {
    super(message);
    this.name = 'ApiError';
    this.status = status;
  }
}

async function fetchUser(id) {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) {
    throw new ApiError(`请求失败 ${res.status}`, res.status);
  }
  return res.json();
}
```

## TypeError

TypeError 在值不是预期的类型时抛出，是前端最常见的运行时错误——最常见的就是对 null/undefined 访问属性。

```js
// 常见 TypeError 场景
const obj = null;
obj.name;                       // TypeError: Cannot read properties of null
undefined.foo;                  // TypeError: Cannot read properties of undefined

const num = 42;
num.toUpperCase();              // TypeError: num.toUpperCase is not a function

const arr = null;
arr.map((x) => x);              // TypeError: Cannot read properties of null
```

```js
// 防御：可选链 + 空值合并
const name = user?.profile?.name ?? '匿名';   // 安全访问

// 防御：判断类型再操作
if (typeof fn === 'function') {
  fn();
}
```

```text
TypeError 的根源与对策：
根源 —— 对 null/undefined 访问属性，或对非函数调用
对策：
1. 可选链 ?. —— 链式访问中途为 null 直接返回 undefined
2. 空值合并 ?? —— 提供默认值
3. 类型守卫 —— 先判断类型再操作
4. TypeScript —— 编译期就拦住大部分类型错误
```

## ReferenceError

ReferenceError 在访问不存在的变量（未声明、或暂时性死区 TDZ）时抛出，是典型的编码错误。

```js
// 访问未声明变量
console.log(notDefined);   // ReferenceError: notDefined is not defined

// 暂时性死区（TDZ）
console.log(x);            // ReferenceError: Cannot access 'x' before initialization
let x = 1;

// 拼写错误
const user = { name: 'Alice' };
console.log(user.naem);    // 不报错，返回 undefined（属性拼错不是 ReferenceError）
```

```js
// 与 undefined 的区别
typeof notDefined;    // 'undefined'（typeof 对未声明变量不报错）
typeof x;             // 'undefined'
```

```text
ReferenceError 的要点：
1. 访问未声明变量 —— 直接引用报 ReferenceError
2. TDZ —— let/const 声明前访问报错（var 则提升为 undefined）
3. typeof 例外 —— typeof 未声明变量返回 'undefined' 不报错
4. 属性拼错 —— 返回 undefined 而非 ReferenceError，更隐蔽
```

## SyntaxError

SyntaxError 是代码解析阶段的语法错误，整个脚本无法执行。它与运行时错误不同——SyntaxError 无法被同一脚本内的 try/catch 捕获。

```js
// 语法错误示例（整个脚本直接无法运行）
const a = ;           // SyntaxError: Unexpected token
function () {}        // SyntaxError: Function statements require a function name
if (true) {           // SyntaxError: Unexpected end of input（少了个括号）
```

```js
// 同一脚本内 try/catch 抓不到 SyntaxError
try {
  eval('const = ;');   // 动态代码的语法错误可以被捕获
} catch (err) {
  console.log(err instanceof SyntaxError);  // true
}
```

```text
SyntaxError 的要点：
1. 发生在解析阶段 —— 脚本整体不执行，比运行时错误更严重
2. 静态代码无法用 try/catch 捕获 —— 因为根本没执行到
3. eval / new Function 的语法错误可捕获 —— 因为它们在运行时解析
4. 实践中靠 ESLint 等工具在写代码阶段就拦截
```

## RangeError

RangeError 在数值超出允许范围时抛出，典型场景是数组长度非法、递归过深导致调用栈溢出、数值方法参数越界。

```js
// 数组长度非法
new Array(-1);              // RangeError: Invalid array length
new Array(2 ** 32);         // RangeError: Invalid array length

// 数值方法参数越界
(42).toFixed(200);          // RangeError: toFixed() digits argument must be between 0 and 100

// 无限递归导致栈溢出
function recurse() { return recurse(); }
recurse();                  // RangeError: Maximum call stack size exceeded
```

```text
RangeError 的要点：
1. 数组长度 —— new Array 或 length 赋值为负数/超上限
2. 栈溢出 —— 无限递归，调用栈超出引擎上限
3. 数值方法 —— toFixed/toPrecision 参数越界

栈溢出的应对：
递归要有终止条件，或改写为迭代；深层递归用尾递归优化（部分引擎支持）。
```

## AggregateError

AggregateError 把多个错误打包成一个错误对象，通过 `errors` 属性访问所有子错误。主要用于 Promise.any 全失败、以及批量操作汇总多个失败。

```js
// Promise.any 全部失败时抛出 AggregateError
const promises = [
  Promise.reject(new Error('请求超时')),
  Promise.reject(new Error('网络错误')),
  Promise.reject(new Error('服务器错误')),
];

try {
  await Promise.any(promises);
} catch (err) {
  console.log(err instanceof AggregateError);  // true
  console.log(err.errors.length);              // 3
  err.errors.forEach((e) => console.log(e.message));
}
```

```js
// 手动构造 AggregateError
const errors = [
  new Error('字段 A 校验失败'),
  new Error('字段 B 校验失败'),
];
throw new AggregateError(errors, '表单校验失败');
```

```text
AggregateError 的要点：
1. errors 属性 —— 包含所有子错误数组
2. message —— 聚合错误的总体描述
3. 典型来源 —— Promise.any 全部 reject、批量校验汇总
4. 处理方式 —— 遍历 err.errors 分别展示
```

## 应用场景实战

### 场景一：表单校验的分类型错误处理

```js
class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = 'ValidationError';
    this.field = field;
  }
}

function validate(form) {
  if (!form.username) {
    throw new ValidationError('用户名不能为空', 'username');
  }
  if (!form.email.includes('@')) {
    throw new ValidationError('邮箱格式不正确', 'email');
  }
}

try {
  validate({ username: '', email: 'abc' });
} catch (err) {
  if (err instanceof ValidationError) {
    highlightField(err.field, err.message);
  } else {
    reportUnexpected(err);
  }
}
```

### 场景二：封装安全解析函数避免崩溃

```js
// 把易错的 JSON.parse 包成安全函数
function safeParse(json, fallback = null) {
  try {
    return JSON.parse(json);
  } catch (err) {
    if (err instanceof SyntaxError) {
      console.warn('JSON 解析失败：', err.message);
      return fallback;
    }
    throw err;   // 其他错误继续抛出
  }
}

const data = safeParse(localStorage.getItem('cache') || '', {});
console.log(data);   // 解析失败时返回默认值，不崩溃
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用自定义错误类携带业务上下文（字段、错误码），便于分类处理
2. catch 里用 instanceof 区分错误类型，分别处理
3. 对 null/undefined 访问用可选链和空值合并做防御
4. 未知错误重新抛出，交给上层统一处理，别吞掉
5. 用 TypeScript 在编译期消除大部分 TypeError
6. JSON.parse、eval 等易错操作包一层安全函数

### 踩坑记录

```text
坑 1：try/catch 抓不到异步错误
结论：try 里 await 的 Promise reject 没被捕获。
原因：把 catch 写错了层级，或漏了 await。
解法：async 函数里用 await，或用 Promise.catch 链。

坑 2：属性拼错返回 undefined 而非报错
结论：user.naem 不报错，静默返回 undefined 埋下隐患。
原因：访问对象不存在的属性不抛 ReferenceError。
解法：用 TypeScript 或 lint 检查，关键对象加运行时校验。

坑 3：吞掉错误不处理
结论：catch 里什么都不做，问题被隐藏。
原因：catch 后只注释或空处理。
解法：至少记录日志，未知错误要重新抛出或上报。

坑 4：无限递归导致栈溢出
结论：RangeError: Maximum call stack size exceeded。
原因：递归缺终止条件，或终止条件永远不满足。
解法：检查递归基准条件，深层场景改迭代。

坑 5：SyntaxError 无法用 try/catch 捕获
结论：脚本整体报错，try/catch 形同虚设。
原因：语法错误在解析阶段就发生，代码未执行。
解法：靠 ESLint/编译器在开发期拦截语法错误。
```
