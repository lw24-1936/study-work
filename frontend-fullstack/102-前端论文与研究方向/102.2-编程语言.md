## 概述

编程语言研究方向关注「语言如何被设计、被编译、被分析、被优化」。对前端工程师而言，这条线最直接的落点是 TypeScript：它既是类型系统的实践样本，也是编译器与静态分析的研究对象。理解这四个子方向，能让你从「会写类型」升级到「理解类型检查器与编译器怎么工作」。

```text
编程语言研究的四大方向：
1. Type Systems —— 类型系统：静态类型、类型推断、子类型
2. Compilers —— 编译器：词法分析、语法分析、代码生成
3. Static Analysis —— 静态分析：不运行代码，靠 AST 分析缺陷与模式
4. Program Optimization —— 程序优化：死代码消除、常量折叠、tree shaking
```

```text
这些方向如何串联：
1. 编译器前端负责把源码变成 AST
2. 类型系统在 AST 上做类型检查
3. 静态分析复用 AST 与类型信息找问题
4. 程序优化复用 AST 与依赖信息产出更小更快的代码
```

## Type Systems

Type Systems 研究如何用类型约束程序、在编译期发现错误。核心概念包括静态/动态类型、强/弱类型、类型推断、子类型多态、结构化类型等。TypeScript 采用的是「结构化类型 + 渐进式类型」：类型按结构兼容，且允许 any 逐步迁移。

```text
Type Systems 研究重点：
1. 类型推断 —— 不写注解也能推导出类型（如 let x = 1 → number）
2. 子类型与协变/逆变 —— 函数参数、返回值的方向性兼容
3. 结构化类型 —— 按「形状」而非「名字」判断兼容（duck typing）
4. 联合类型与类型收窄 —— 用控制流收窄联合类型
```

```ts
// 结构化类型：只要形状一致就兼容
interface Point { x: number; y: number; }
interface NamedPoint { x: number; y: number; name: string; }

let p: Point = { x: 1, y: 2 };
let np: NamedPoint = { x: 1, y: 2, name: 'origin' };
p = np;  // 合法：NamedPoint 拥有 Point 的全部成员（结构化兼容）

// 类型收窄：根据运行时判断收窄联合类型
function format(value: string | number) {
  if (typeof value === 'string') {
    return value.toUpperCase();  // 这里 value 收窄为 string
  }
  return value.toFixed(2);       // 这里 value 收窄为 number
}
```

```text
研究方向的核心问题：
1. 如何设计类型推断算法（Hindley-Milner 的变体）
2. 如何处理 any 与类型逃逸，保持渐进迁移安全
3. 协变/逆变如何在函数类型中正确传播
4. 结构化 vs 名义化类型在大型工程中的取舍
```

## Compilers

Compilers 研究如何把一种语言翻译成另一种语言。经典流程分三个阶段：前端（词法分析、语法分析）、中端（语义分析、中间表示）、后端（优化、代码生成）。前端构建工具里的 Babel、SWC、esbuild 本质上都是「源码到源码」的编译器（transpiler）。

```text
Compilers 研究重点：
1. 词法分析（Lexer）—— 源码字符流 → Token 序列
2. 语法分析（Parser）—— Token 序列 → AST
3. 中间表示（IR）—— 与具体语言无关的表示，便于优化
4. 代码生成（Code Gen）—— AST/IR → 目标代码
```

```text
编译流程：
1. Source Code → 词法分析 → Tokens
2. Tokens → 语法分析 → AST
3. AST → 语义分析 / 类型检查 → 标注后的 AST
4. AST → 优化 → IR
5. IR → 代码生成 → 目标代码（JS / 机器码）
```

```text
研究方向的核心问题：
1. 错误恢复 —— 遇到语法错误如何继续解析并给出好报错
2. 增量编译 —— 只重编译变化的文件，提速构建
3. 保真转换 —— Babel 转译时如何保留注释与源码映射
4. 新语法支持 —— 如何用插件机制扩展语法（如 decorators）
```

## Static Analysis

Static Analysis 研究在不运行代码的情况下分析代码行为与缺陷。它基于 AST、类型信息与数据流分析，用于发现空指针、未使用变量、潜在 bug、安全漏洞等。ESLint、Prettier、SonarQube 都是静态分析工具。

```text
Static Analysis 研究重点：
1. 抽象语法树遍历 —— visitor 模式遍历 AST 节点
2. 数据流分析 —— 变量的赋值与使用路径（def-use chain）
3. 控制流分析 —— 分支、循环、异常的可达性
4. 调用图分析 —— 函数之间的调用关系，找死代码
```

```js
// 一个极简的 ESLint 规则：检测 console.log
// ESLint 的规则本质就是「遍历 AST + 报告问题」
const rule = {
  meta: { type: 'suggestion' },
  create(context) {
    return {
      CallExpression(node) {
        if (
          node.callee.type === 'MemberExpression' &&
          node.callee.object.name === 'console' &&
          node.callee.property.name === 'log'
        ) {
          context.report({ node, message: 'Unexpected console.log' });
        }
      },
    };
  },
};
```

```text
研究方向的核心问题：
1. 如何做跨文件分析（模块间的影响追踪）
2. 如何平衡误报（false positive）与漏报（false negative）
3. 如何做路径敏感分析（不同分支不同结论）
4. 如何把静态分析结果反馈到编辑器做实时提示（LSP）
```

## Program Optimization

Program Optimization 研究如何让程序更小、更快、更省内存。编译期优化包括死代码消除、常量折叠、内联、tree shaking、代码压缩等。前端的打包产物优化（tree shaking、minify）直接受益于这些理论。

```text
Program Optimization 研究重点：
1. 死代码消除（DCE）—— 移除永远不会执行的代码
2. 常量折叠 —— 编译期计算常量表达式
3. Tree Shaking —— 移除未引用的导出
4. 内联与代码压缩 —— 减少调用开销与体积
```

```text
常见优化手段：
1. 常量折叠：const x = 2 * 3 → 直接替换为 6
2. 死代码消除：if (false) { ... } → 整块删除
3. Tree Shaking：import { a } 但只用 b → a 被删除
4. 压缩：变量重命名为短名、删除空格注释
```

```text
研究方向的核心问题：
1. 如何保证优化不改变程序语义（正确性优先）
2. 如何做跨模块优化（scope hoisting 合并作用域）
3. 如何评估副作用（纯函数才能安全 tree shaking）
4. 优化与构建耗时的权衡（过度优化拖慢构建）
```

## 应用场景实战

### 场景一：用 TypeScript 的收窄避免类型断言

```ts
// 差：用类型断言强行绕过检查
function getLength(value: string | string[] | null) {
  return (value as string[]).length;  // value 为 null 时运行时报错
}

// 好：用类型收窄让编译器保证安全
function getLengthSafe(value: string | string[] | null) {
  if (value === null) return 0;               // 收窄掉 null
  return value.length;                        // string 和 string[] 都有 length
}
```

### 场景二：理解 tree shaking 为什么对某些库失效

```text
目标：排查一个第三方库无法被 tree shaking 的原因。
步骤：
1. 检查库的 package.json 是否声明 sideEffects: false
2. 检查是否从库的入口做具名导入（而非默认导入整包）
3. 检查库是否用 ESM 输出（CJS 无法静态分析）
4. 用 bundle 分析工具看哪些模块被打进来了
5. 确认未使用导出是否有副作用（顶层立即执行）
```

```js
// 为什么默认导入整包会破坏 tree shaking
// 差：默认导入会拉入整个库
import _ from 'lodash';
_.get(obj, 'a.b');

// 好：具名导入子路径，只打包用到的函数
import get from 'lodash/get';
get(obj, 'a.b');
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优先用类型收窄代替类型断言，让编译器帮你保证安全
2. 尽量用 ESM 输出的库，保证依赖能被 tree shaking
3. 编写 ESLint 规则时先明确「匹配哪个 AST 节点类型」
4. 在热路径避免创建新对象，减少 GC 与优化失效
5. 用 unknown 代替 any 作为「未知类型」的安全兜底
6. 读编译器源码前，先用手写 AST 熟悉节点结构

### 踩坑记录

```text
坑 1：滥用类型断言（as any）
结论：类型错误被强行压下去，运行期才暴露 bug。
原因：断言绕过了类型检查，等于关掉了安全网。
解法：优先用类型收窄或 unknown 逐步收窄，断言只作最后手段。

坑 2：给第三方库设 sideEffects: false 后样式丢失
结论：打包后组件库的 CSS 样式文件没被打进去。
原因：sideEffects: false 让打包器把「有副作用的 CSS import」也删了。
解法：把 CSS 文件列入 sideEffects 白名单，如 ["*.css"]。

坑 3：CJS 依赖导致 tree shaking 完全失效
结论：明明只用了库的一个函数，产物却包含整个库。
原因：CommonJS 的 require 是动态的，打包器无法静态分析导出。
解法：改用提供 ESM 输出的库，或从子路径（lodash/get）导入。

坑 4：以为 minify 只是删空格
结论：自己手写的「压缩逻辑」产出了错误代码。
原因：压缩还包含变量重命名、死代码消除等语义相关优化。
解法：交给成熟的 minifier（terser/esbuild），不要手写压缩。

坑 5：用 any 作为函数返回类型
结论：调用方拿到的类型都是 any，类型检查形同虚设。
原因：any 会「传染」，任何与 any 运算的结果都是 any。
解法：用 unknown 或精确类型标注返回类型，收窄后再使用。
```
