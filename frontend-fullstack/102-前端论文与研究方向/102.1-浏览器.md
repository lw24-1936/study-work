## 概述

浏览器研究方向的本质，是研究「一个网页如何被高效地解析、渲染、执行、调度」。这条线横跨渲染管线、JavaScript 引擎、即时编译、垃圾回收与任务调度五个子方向，是前端性能优化与浏览器底层原理的共同地基。读这一方向，能让你从「会用浏览器」升级到「理解浏览器为什么快或慢」。

```text
浏览器研究的五大方向：
1. Rendering —— 从 HTML/CSS 到像素的渲染管线
2. JavaScript Engine —— 引擎的解析、字节码与执行模型
3. JIT —— 即时编译，热点代码的机器码优化
4. Garbage Collection —— 自动内存管理
5. Scheduling —— 任务调度与主线程时间分配
```

```text
这些方向如何互相咬合：
1. Scheduling 决定主线程时间怎么分 → 影响渲染与 JS 执行
2. JavaScript Engine 的 JIT 决定 JS 跑多快 → 影响帧率
3. Garbage Collection 决定内存与停顿 → 影响长任务与卡顿
4. Rendering 是最终产出 → 前面几项都为它服务
```

## Rendering

Rendering 研究浏览器如何把 HTML、CSS 变成屏幕上的像素。核心是渲染管线（Rendering Pipeline）：解析、样式计算、布局、绘制、合成。现代浏览器把「合成」提到最关键位置，因为它是 GPU 加速与 60fps 的根基。

```text
Rendering 研究重点：
1. 渲染管线 —— HTML/DOM、CSSOM、RenderObject 树、Layout、Paint、Composite
2. 布局系统 —— 盒模型、流式布局、Flex/Grid 的布局算法
3. 绘制与合成 —— 分层、光栅化、合成器线程、GPU 上传
4. 增量更新 —— 局部失效、dirty 标记、只重绘/重排受影响区域
```

```text
渲染管线的关键阶段：
1. Parse —— HTML 生成 DOM 树，CSS 生成 CSSOM
2. Style —— 计算每个节点的最终样式
3. Layout —— 计算几何位置与尺寸
4. Paint —— 生成绘制指令
5. Composite —— 分层合成上屏
```

```text
研究方向的核心问题：
1. 如何避免布局抖动（layout thrashing）
2. 如何让动画只走合成器线程（transform/opacity）
3. 如何做 content-visibility 的按需渲染
4. 如何用 contain 隔离渲染范围
```

## JavaScript Engine

JavaScript Engine 研究引擎如何解析并执行 JS。现代引擎普遍采用「解释器 + 编译器」的混合架构：先用解释器快速执行，再对热点代码做优化编译。V8 的 Ignition（解释器）+ TurboFan（优化编译器）是最典型的样本。

```text
JavaScript Engine 研究重点：
1. 解析器 —— 源码到 AST，惰性解析与增量解析
2. 解释器 —— AST 到字节码，寄存器式字节码设计
3. 字节码优化 —— 内联缓存（Inline Cache）、隐藏类（Hidden Class）
4. 编译器 —— 优化编译器的中间表示与图优化
```

```text
V8 的执行架构：
1. Parser 解析源码 → AST
2. Ignition 解释器把 AST → 字节码并执行
3. 热点检测 → TurboFan 把字节码 → 优化机器码
4. 优化失败 → 反优化（deopt）回退到字节码
```

```text
研究方向的核心问题：
1. 如何让隐藏类（Map）保持稳定以提升属性访问速度
2. 如何让内联缓存命中率更高
3. 如何降低反优化的代价
4. 惰性解析如何平衡启动速度与执行速度
```

## JIT

JIT（Just-In-Time Compilation，即时编译）研究如何在运行时把热点代码编译成机器码。核心思想是「先快速执行，再按需优化」：解释器先跑，运行期收集类型信息（profiling），编译器用这些信息做激进优化。

```text
JIT 研究重点：
1. 热点检测 —— 函数调用次数、循环次数等阈值触发编译
2. 类型特化 —— 根据运行期收集的类型信息生成专用机器码
3. 内联 —— 把小函数内联进调用点，消除调用开销
4. 反优化 —— 类型假设失效时回退到解释器
```

```text
JIT 编译流程（以 V8 TurboFan 为例）：
1. 解释器执行，累计热点计数
2. 达到阈值 → 触发优化编译
3. 基于 profiled 类型生成假设（如「这里一定是 Smi」）
4. 假设成立 → 极速执行；假设失效 → 反优化
```

```text
研究方向的核心问题：
1. 如何减少「优化 → 反优化」的抖动
2. 如何让多态调用点也能高效执行
3. 编译线程与主线程如何协作，避免编译阻塞
4. 如何降低编译产物占用内存（code size）
```

## Garbage Collection

Garbage Collection（垃圾回收）研究引擎如何自动回收不再使用的内存。现代引擎采用分代回收（Generational GC）：新生代用复制/清道夫算法，老生代用标记-清除/标记-压缩。V8 的 Orinoco 是最值得研究的实现。

```text
GC 研究重点：
1. 分代假设 —— 大多数对象朝生夕死，新生代快速回收
2. 标记-清除 —— 从根对象出发标记存活对象，清除未标记对象
3. 增量与并发 —— 把 GC 拆成小步，减少主线程停顿
4. 内存布局 —— 压缩消除碎片，提升缓存局部性
```

```text
V8 的堆结构：
1. 新生代（Young Generation）—— Scavenger 复制算法，快
2. 老生代（Old Generation）—— Mark-Compact，大对象
3. 大对象空间 —— 超过阈值的对象单独存放
4. 代码空间 —— 编译产物的机器码
```

```text
研究方向的核心问题：
1. 如何缩短 Stop-The-World 停顿（并发标记、增量标记）
2. 如何减少 GC 触发的长任务（导致页面卡顿）
3. 如何让开发者写出更少垃圾的代码
4. WeakRef 与 FinalizationRegistry 如何影响回收
```

## Scheduling

Scheduling 研究浏览器如何分配主线程时间。核心矛盾是「主线程只有一个，任务却无穷多」：输入事件、JS 执行、样式计算、布局、绘制都要排队。浏览器用任务队列、渲染机会、长任务拆分来解决。

```text
Scheduling 研究重点：
1. 事件循环 —— 宏任务与微任务的调度顺序
2. 渲染时机 —— 每帧的渲染机会（rendering opportunity）
3. 长任务拆分 —— 时间片与 requestIdleCallback 让出主线程
4. 输入优先 —— 用户输入（点击、滚动）抢占渲染与 JS
```

```text
一帧的生命周期（理想 16.6ms）：
1. Input —— 处理输入事件
2. JS —— 执行脚本任务
3. Style / Layout —— 样式与布局计算
4. Paint / Composite —— 绘制与合成
5. Idle —— 空闲时间，可执行低优先级任务
```

```text
研究方向的核心问题：
1. 如何避免长任务（Long Task > 50ms）阻塞输入响应
2. 如何让 isInputPending 尽早响应输入
3. 如何用 scheduler.yield / scheduler.postTask 精细调度
4. 主线程与合成器线程如何并行工作
```

## 应用场景实战

### 场景一：分析一个页面的长任务卡顿

```text
目标：定位并优化一个长任务导致的卡顿。
步骤：
1. 打开 DevTools Performance 面板录制
2. 找到 > 50ms 的长任务，展开火焰图
3. 判断长任务是 JS 执行、GC、还是布局
4. 若是 JS → 拆分任务或移到 worker
5. 若是 GC → 减少对象分配或复用对象
6. 若是布局 → 合并读写，避免布局抖动
```

```js
// 常见的长任务来源：一次性处理大量数据
// 优化前：一个大循环阻塞主线程
function processItems(items) {
  for (const item of items) {
    heavyCompute(item);
  }
}

// 优化后：用时间片拆分，让出主线程
async function processItemsYield(items) {
  for (let i = 0; i < items.length; i++) {
    heavyCompute(items[i]);
    if (i % 100 === 0) {
      await new Promise(r => setTimeout(r, 0));  // 让出主线程
    }
  }
}
```

### 场景二：分析一次 GC 触发的卡顿

```text
目标：判断卡顿是否由 GC 引起。
步骤：
1. DevTools Performance 面板勾选 Memory 录制
2. 观察火焰图中灰色的 GC 块
3. 若 GC 频繁且停顿长 → 检查对象分配热点
4. 用 Allocation sampling 找到分配最多的函数
5. 对象池复用、减少闭包与临时对象
```

```js
// 减少垃圾产生的写法
// 差：循环里频繁创建临时对象
function sum1(list) {
  return list.map(x => x * 2).filter(x => x > 10).reduce((a, b) => a + b, 0);
}

// 好：单次遍历，少分配中间数组
function sum2(list) {
  let total = 0;
  for (const x of list) {
    const v = x * 2;
    if (v > 10) total += v;
  }
  return total;
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 动画只用 transform 与 opacity，让合成器线程独立完成，不触发布局
2. 读写 DOM 分离，先读后写或批量读，避免布局抖动
3. 长任务拆分成小片，用 setTimeout / requestIdleCallback 让出主线程
4. 保持对象形状稳定，避免动态增删属性破坏隐藏类
5. 热路径减少临时对象分配，降低 GC 压力
6. 读这一方向时，用 DevTools Performance 面板对照源码验证理解

### 踩坑记录

```text
坑 1：在循环里读 offsetWidth 再写样式
结论：每轮都触发强制同步布局，页面卡死。
原因：读布局属性迫使浏览器立即计算布局，读写交错导致布局抖动。
解法：先批量读，再批量写，或用 requestAnimationFrame 统一更新。

坑 2：用 left/top 做动画
结论：动画掉帧，主线程持续触发布局。
原因：left/top 改变会触发 Layout，占用主线程。
解法：改用 transform 位移，只走合成器线程。

坑 3：频繁动态添加对象属性
结论：属性访问变慢，甚至触发反优化。
原因：破坏隐藏类，内联缓存频繁失效。
解法：构造函数里一次性声明所有属性，保持对象形状一致。

坑 4：把所有重计算都塞进一个同步任务
结论：主线程被长时间阻塞，输入无响应。
原因：长任务超过 50ms，浏览器无法及时响应输入。
解法：拆分任务，用 isInputPending 或 scheduler.yield 让出主线程。

坑 5：误以为 GC 停顿可以完全避免
结论：过度追求零垃圾，写出难维护的复用代码。
原因：GC 是自动内存管理的固有成本，只能降低不能消除。
解法：只在热路径做对象复用，普通代码优先可读性。
```
