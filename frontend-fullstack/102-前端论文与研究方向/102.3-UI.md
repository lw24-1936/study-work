## 概述

UI 研究方向关注「人与界面如何交互、界面如何被设计、生成与系统化」。它横跨人机交互、可访问性、UI 生成与设计系统四个子方向，是把「工程能力」延伸到「体验与设计」的桥梁。对前端工程师而言，这一方向决定了你能否做出「好用、无障碍、可规模化」的界面，而不只是「能跑」的界面。

```text
UI 研究的四大方向：
1. Human Computer Interaction —— 人与机器的交互范式与认知模型
2. Accessibility —— 让所有用户都能访问的无障碍设计
3. UI Generation —— 用模型或规则自动生成界面
4. Design Systems —— 设计系统与组件库的工程化
```

```text
这些方向如何协同：
1. HCI 提供「交互是否好用」的理论依据
2. Accessibility 保证「所有人都能用」的底线
3. Design Systems 提供「一致、可复用」的工程载体
4. UI Generation 探索「自动产出界面」的新范式
```

## Human Computer Interaction

Human Computer Interaction（HCI，人机交互）研究人与计算机系统的交互方式，关注可用性、可学习性、认知负荷与交互范式。从命令行到 GUI、从鼠标到触屏、从点击到对话，交互范式的每一次演进都重塑了前端的工作方式。

```text
HCI 研究重点：
1. 交互范式 —— CLI、GUI、触屏、语音、手势、空间计算
2. 可用性 —— 尼尔森十大可用性原则、可学习性与效率
3. 认知模型 —— 心智模型、认知负荷、费茨定律
4. 反馈与响应 —— 即时反馈、加载状态、错误提示
```

```text
尼尔森可用性原则（Nielsen's 10 Usability Heuristics）速览：
1. 系统状态可见性 —— 始终让用户知道现在发生了什么
2. 系统与现实匹配 —— 用用户的语言，不用系统术语
3. 用户可控与自由 —— 支持撤销与重做
4. 一致性与标准 —— 遵循平台惯例
5. 防错 —— 优先预防错误而非报错
6. 识别而非回忆 —— 让信息可见，减少记忆负担
7. 灵活高效 —— 为新手与专家都提供路径
8. 极简设计 —— 去除无关信息
9. 帮助识别与修复错误 —— 清晰的错误提示
10. 帮助与文档 —— 必要时提供帮助
```

```text
研究方向的核心问题：
1. 如何度量交互的「好用程度」（任务完成率、时间、错误率）
2. 新交互范式（语音、AI 对话）如何与传统 GUI 融合
3. 如何降低用户的认知负荷
4. 反馈延迟（loading、skeleton）如何影响体验
```

## Accessibility

Accessibility（可访问性）研究如何让界面对残障用户可用，涵盖视觉、听觉、运动、认知四类障碍。Web 可访问性的标准是 WCAG，技术落点是语义化 HTML、ARIA、键盘操作与焦点管理。它不是「锦上添花」，而是「基本要求」。

```text
Accessibility 研究重点：
1. 语义化 —— 正确的 HTML 标签（button、nav、main）自带可访问性
2. ARIA —— 用 role、aria-* 属性补充语义
3. 键盘操作 —— 所有交互都能只用键盘完成
4. 焦点管理 —— 焦点可见、顺序合理、模态框焦点圈定
```

```html
<!-- 可访问的交互组件示例 -->
<!-- 语义化：原生 button 自带键盘与焦点支持 -->
<button type="button" aria-pressed="false" onclick="toggle()">
  订阅通知
</button>

<!-- ARIA：为非原生组件补充语义 -->
<div
  role="slider"
  tabindex="0"
  aria-valuemin="0"
  aria-valuemax="100"
  aria-valuenow="50"
>
  音量
</div>
```

```text
WCAG 的四大原则（POUR）：
1. Perceivable 可感知 —— 信息不依赖单一感官
2. Operable 可操作 —— 界面可被操作（键盘、时间充足）
3. Understandable 可理解 —— 内容与操作可理解
4. Robust 健壮 —— 兼容各类辅助技术
```

## UI Generation

UI Generation 研究如何自动生成界面，是近年来最活跃的方向之一。它分两类：规则驱动的传统方式（基于设计 token 与模板），与模型驱动的生成式方式（LLM 生成代码、文本到界面）。后者与 AI + Frontend 方向紧密交叉。

```text
UI Generation 研究重点：
1. 规则驱动 —— 设计 token + 组件模板拼装界面
2. 模型驱动 —— LLM 根据自然语言或设计稿生成代码
3. 设计稿转代码 —— Figma 设计稿到可运行 UI
4. 文本到界面 —— 描述需求直接产出组件
```

```text
UI 生成的典型路径：
1. 输入 —— 自然语言描述 / 设计稿 / 低代码配置
2. 解析 —— 提取结构、布局、组件与样式
3. 映射 —— 匹配到组件库的既有组件
4. 生成 —— 产出可运行的代码或 JSON schema
```

```text
研究方向的核心问题：
1. 生成结果如何保证可用性与一致性（对接 Design System）
2. 生成的代码如何维护、如何与人工代码共存
3. 设计稿到代码的像素级还原如何度量
4. 如何让生成结果可编辑、可迭代（而非一次性）
```

## Design Systems

Design Systems（设计系统）研究如何把设计决策沉淀为可复用的工程资产。核心是三层结构：设计 token（原子）→ 组件（分子）→ 模式（有机体）。它是「UI 一致性与可规模化」的工程答案，落地为组件库 + 文档 + 规范。

```text
Design Systems 研究重点：
1. Design Token —— 颜色、间距、字体等最小设计变量
2. 组件 API —— 组件的 props 设计与可组合性
3. 主题系统 —— 多主题、暗色模式、运行时切换
4. 工程化 —— 版本管理、文档、测试、发布
```

```json
{
  "color": {
    "primary": { "value": "#2563eb" },
    "primary-hover": { "value": "#1d4ed8" }
  },
  "spacing": {
    "sm": { "value": "8px" },
    "md": { "value": "16px" }
  }
}
```

```text
设计系统的分层：
1. 原则层 —— 设计价值观与指导原则
2. Token 层 —— 颜色、间距、字体、圆角等变量
3. 组件层 —— Button、Input、Modal 等可复用组件
4. 模式层 —— 表单、导航、列表页等组合模式
5. 内容层 —— 文案规范、图标、插画
```

## 应用场景实战

### 场景一：给一个自定义下拉组件补全可访问性

```html
<!-- 未补全：div 加点击，无键盘、无焦点、读屏不可用 -->
<div class="dropdown" onclick="toggle()">
  <div class="selected">请选择</div>
  <div class="options">...</div>
</div>

<!-- 补全后：用 combobox 模式 + 键盘 + ARIA -->
<div class="dropdown">
  <button
    role="combobox"
    aria-expanded="false"
    aria-haspopup="listbox"
    aria-controls="options-list"
    onclick="toggle()"
  >
    请选择
  </button>
  <ul id="options-list" role="listbox">
    <li role="option" tabindex="-1" onclick="select('a')">选项 A</li>
    <li role="option" tabindex="-1" onclick="select('b')">选项 B</li>
  </ul>
</div>
```

### 场景二：为一个团队建立最小可用的 Design Token

```text
目标：从零建立一套够用的设计 token。
步骤：
1. 盘点现有界面的颜色、间距、字体，找重复值
2. 抽象成 token：color.primary、spacing.md 等
3. 定义语义层 token：color.bg、color.text（而非直接 color.blue.500）
4. 用工具（Style Dictionary）生成各平台变量
5. 组件全部改用 token，禁止硬编码色值
```

```css
/* token 落地为 CSS 变量 */
:root {
  --color-bg: #ffffff;
  --color-text: #1a1a1a;
  --color-primary: #2563eb;
  --spacing-md: 16px;
  --radius-md: 8px;
}

.card {
  background: var(--color-bg);
  padding: var(--spacing-md);
  border-radius: var(--radius-md);
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 交互组件优先用原生语义标签，语义不够再用 ARIA 补充
2. 所有交互都要支持纯键盘操作，并保证焦点可见
3. 颜色对比度满足 WCAG AA（正文 4.5:1，大字 3:1）
4. 用语义层 token（color.bg、color.text）而非具体色值，支持主题切换
5. 模态框打开时锁定焦点，关闭时还原焦点
6. 新功能先问「键盘能用吗、读屏能读吗」，再做视觉

### 踩坑记录

```text
坑 1：用 div 加 onclick 实现按钮
结论：读屏软件不识别、键盘无法触发、焦点不可达。
原因：div 没有 button 的语义、键盘与焦点行为。
解法：用原生 button，需要自定义样式再覆盖外观。

坑 2：给元素乱加 aria 属性
结论：读屏软件读到错误或冲突的语义，反而更差。
原因：ARIA 是补充而非替代，错误使用会误导辅助技术。
解法：先正确使用语义标签，ARIA 只在必要时加且保证正确。

坑 3：颜色对比度不足
结论：弱视用户在浅色背景下看不清文字。
原因：只考虑美观，未校验前景与背景的对比度。
解法：用对比度工具校验，正文至少 4.5:1。

坑 4：token 直接用具体色值命名（blue.500）
结论：换主题或换品牌色时要全局改组件。
原因：具体色值命名让「语义」和「颜色」耦合。
解法：用语义层 token（color.primary、color.text）解耦。

坑 5：设计系统只有组件库没有文档
结论：组件用法不统一，团队各自为战。
原因：缺少用法说明与规范，组件库沦为「代码仓库」。
解法：配套 Storybook 文档、使用示例与贡献规范。
```
