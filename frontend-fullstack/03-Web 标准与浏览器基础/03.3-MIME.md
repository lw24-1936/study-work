## 概述

MIME（Multipurpose Internet Mail Extensions）类型标识「一段数据是什么格式」，在 Web 里通过 Content-Type 头声明。浏览器靠它决定「这段内容是当 HTML 渲染、当 JS 执行、还是当图片显示」。MIME 类型配错，轻则功能异常（JS 不执行、JSON 解析不出），重则安全风险（HTML 被当纯文本、或纯文本被当 HTML 执行）。

```text
MIME 类型在 Web 中的角色：
1. HTTP 响应 —— 服务器用 Content-Type 告诉浏览器 Body 是什么格式
2. HTTP 请求 —— 客户端告诉服务器上传的数据格式
3. 资源加载 —— <script>/<img> 等按 MIME 类型决定如何处理资源
```

## MIME 的作用与语法

MIME 类型的标准格式是「类型/子类型」，可选参数用分号分隔：

```text
语法：type/subtype; parameter=value

示例：
text/html                    —— HTML 文档
text/css                     —— 样式表
application/json; charset=utf-8 —— JSON，指定字符编码
multipart/form-data; boundary=xxx —— 表单上传
```

```text
顶层类型（type）：
text/        —— 文本（html、css、plain）
application/ —— 二进制/应用数据（json、javascript、octet-stream）
image/       —— 图片（png、jpeg、gif、svg、webp、avif）
font/        —— 字体（woff、woff2、ttf、otf）
video/       —— 视频（mp4、webm）
audio/       —— 音频（mp3、ogg、wav）
multipart/   —— 组合数据（form-data 上传）
```

```text
charset 参数：
MIME 可带 charset 参数声明字符编码，如 text/html; charset=utf-8。
现代浏览器默认按 UTF-8 处理，但服务器明确声明更可靠。
```

```text
浏览器如何使用 MIME（关键机制）：
浏览器收到响应后，按 Content-Type 决定「怎么处理」：
text/html        → 渲染成页面
text/css         → 应用样式
application/javascript → 执行脚本
image/png        → 显示图片

MIME 类型不对，处理方式就错（这是「MIME sniffing」和 X-Content-Type-Options 的由来）。
```

## 文本类型：text/html 与 text/css

### text/html

HTML 文档的标准 MIME 类型，是页面入口的标识。

```http
Content-Type: text/html; charset=utf-8
```

```text
text/html 的关键点：
1. 浏览器收到 text/html 才把内容当 HTML 渲染
2. charset 很重要 —— 声明错了中文就乱码（默认 UTF-8）
3. HTML 文件里的 <meta charset> 要和 HTTP 头的 charset 一致
```

### text/css

样式表的标准 MIME 类型。

```http
Content-Type: text/css; charset=utf-8
```

```text
text/css 的关键点：
1. 现代浏览器对 <link rel="stylesheet"> 要求 MIME 必须是 text/css，
   配错会拒绝加载（严格模式）
2. CSS 里 @import 的字体、图片按各自 MIME 处理
3. 老浏览器会「猜测」CSS，现代浏览器（尤其模块化 CSS）严格要求 text/css
```

```text
text 类型的其他常见成员：
text/plain —— 纯文本（不渲染 HTML，原样显示）
text/javascript —— 脚本（历史用法，已废弃，见下一节）
```

## application 类型：javascript 与 json

### application/javascript

JavaScript 脚本的标准 MIME 类型，但这个类型的演进历史值得了解。

```text
JavaScript 的 MIME 类型变迁：
text/javascript            —— 早期用法（Netscape 时代）
application/javascript     —— 现代标准（RFC 4329）
application/x-javascript   —— 历史过渡（x- 前缀是非标准）
text/ecmascript / application/ecmascript —— 历史提案，未普及

当前标准：application/javascript（或 text/javascript 兼容）
```

```text
JavaScript MIME 的实践要点：
1. <script src> 加载的 JS，现代浏览器对 MIME 有要求（尤其 type="module"）
2. ES Module 脚本（<script type="module">）对 MIME 更严格，
   MIME 不对会拒绝执行（CORS + MIME 双重校验）
3. 服务器配错 JS 的 MIME 会导致「脚本加载了但不执行」
```

### application/json

JSON 数据的标准 MIME 类型，API 交互的主流格式。

```http
Content-Type: application/json; charset=utf-8
```

```text
application/json 的关键点：
1. 请求 —— fetch 发 JSON 必须带 Content-Type: application/json，后端才知道怎么解析
2. 响应 —— 服务器返回 JSON 要带 application/json，前端 res.json() 才正常
3. 历史上曾有 text/json、application/x-json 等非标准用法，统一用 application/json
```

```text
JSON MIME 的坑：
1. 服务器返回 JSON 但 Content-Type 是 text/html —— 浏览器当 HTML 处理，
   fetch 的 res.json() 可能仍能解析，但语义错误、有安全风险
2. JSON 里中文用 charset=utf-8 声明，避免乱码
3. application/json 会触发 CORS 预检（非简单请求）
```

## 多媒体类型：image、font、video、audio

### image/*

图片类型按格式区分，前端优化关注「新格式更小」：

```text
image/png  —— 无损，支持透明，适合图标/截图（体积大）
image/jpeg —— 有损，照片压缩比高（无透明）
image/gif  —— 动图（256 色，体积大）
image/svg+xml —— 矢量图，无限缩放（注意子类型是 svg+xml）
image/webp —— Google 的现代格式，比 png/jpeg 小 30%+，支持透明和动图
image/avif —— 更新的格式，比 webp 更小，兼容性稍弱
```

```text
图片 MIME 的实践：
1. 服务器按图片扩展名返回对应 MIME，配错图片不显示
2. SVG 的 MIME 是 image/svg+xml（不是 image/svg）
3. WebP/AVIF 用 <picture> 或 Accept 头按浏览器能力降级
4. SVG 含脚本，image/svg+xml 有 XSS 风险（用户上传 SVG 要消毒）
```

### font/*

字体格式按类型区分：

```text
font/woff   —— WOFF 字体（Web Open Font Format）
font/woff2  —— WOFF 2.0，压缩率更高（现代主流）
font/ttf    —— TrueType（老格式）
font/otf    —— OpenType
```

```text
字体 MIME 的坑：
1. 字体 MIME 配错（如 text/plain），浏览器拒绝加载字体，图标/文字样式失效
2. woff2 是首选（体积最小），woff 兜底
3. 字体跨域加载需要 CORS（@font-face 跨域要 Access-Control-Allow-Origin）
```

### video/* 与 audio/*

```text
video/mp4   —— MP4 容器（H.264/H.265 编码），兼容性最好
video/webm  —— WebM 容器（VP8/VP9/AV1），开源格式
audio/mpeg  —— MP3
audio/ogg   —— Ogg Vorbis
audio/wav   —— 无损音频（体积大）
```

```text
音视频 MIME 的实践：
1. <video> 的 type 属性声明 MIME，浏览器按支持情况选择
2. 视频用 mp4（兼容）+ webm（体积）双格式提供
3. 音视频涉及流式加载，配合 Range 请求（206）实现拖动播放
```

```html
<!-- 多格式视频，浏览器按 MIME 选择支持的 -->
<video controls>
  <source src="video.webm" type="video/webm">
  <source src="video.mp4" type="video/mp4">
</video>
```

## 应用场景实战

### 场景一：排查「JS 文件加载了但不执行」

```bash
# 查看 JS 资源的 Content-Type
curl -I https://example.com/app.js
# 正确：Content-Type: application/javascript
# 错误：Content-Type: text/html 或 application/octet-stream
```

```text
判断与解决：
1. MIME 是 text/html —— 服务器把 JS 当 HTML 返回（路由 fallback 配错），
   浏览器可能拒绝执行
2. MIME 是 application/octet-stream —— 服务器没配置 JS 的 MIME 映射
3. 解决：服务器配置正确的 MIME 映射表（Nginx 的 mime.types）
```

### 场景二：配置服务器 MIME 类型

```nginx
# Nginx mime.types 的关键配置
types {
  text/html          html htm;
  text/css           css;
  application/javascript js mjs;
  application/json   json;
  image/png          png;
  image/svg+xml      svg;
  font/woff2         woff2;
  video/mp4          mp4;
}

# 新增自定义 MIME 映射
location ~ \.mjs$ {
  default_type application/javascript;
}
```

### 场景三：JSON 接口的 Content-Type 校验

```js
// 前端校验响应 MIME，确保是 JSON 才解析
const res = await fetch('/api/data');
const contentType = res.headers.get('Content-Type') || '';
if (!contentType.includes('application/json')) {
  throw new Error(`期望 JSON，实际 ${contentType}`);
}
const data = await res.json();
```

## 最佳实践与踩坑记录

### 最佳实践

1. 服务器配置完整的 MIME 映射表（Nginx mime.types），避免 octet-stream 兜底
2. JS 用 application/javascript，模块脚本（.mjs/type=module）尤其要配对
3. JSON 接口统一 application/json; charset=utf-8
4. 图片用 WebP/AVIF（配 <picture> 降级），字体用 woff2（woff 兜底）
5. 加 X-Content-Type-Options: nosniff 禁止浏览器猜测 MIME（防嗅探攻击）

### 踩坑记录

```text
坑 1：JS 的 MIME 配成 text/html 导致脚本不执行
结论：script 标签加载了但代码不运行，控制台报 MIME 错误。
原因：服务器路由 fallback 把 .js 请求也返回了 HTML，Content-Type 是 text/html。
解法：检查服务器 MIME 配置和路由规则，JS 资源返回 application/javascript。

坑 2：ES Module 因 MIME 错误被拒绝
结论：<script type="module"> 的模块加载失败，报 MIME type 错误。
原因：模块脚本对 MIME 更严格，必须是 JavaScript MIME（且需 CORS）。
解法：.mjs/.js 都配 application/javascript，跨域模块加 CORS 头。

坑 3：JSON 响应是 text/html 导致安全风险
结论：接口返回 JSON 但 Content-Type 是 text/html，可能触发 XSS。
原因：浏览器按 HTML 解析 JSON，含用户输入的 JSON 可能被当脚本执行。
解法：JSON 接口配 application/json + X-Content-Type-Options: nosniff。

坑 4：SVG 的 MIME 配错（写成 image/svg）
结论：SVG 图片不显示。
原因：正确的 MIME 是 image/svg+xml，不是 image/svg。
解法：服务器配 image/svg+xml，同时注意用户上传 SVG 的 XSS 消毒。

坑 5：字体 MIME 错误导致图标乱码
结论：网页字体加载失败，图标字体显示成方块/乱码。
原因：字体文件 MIME 配错，浏览器拒绝加载。
解法：woff2/woff 配 font/woff2、font/woff，跨域字体加 CORS 头。

坑 6：上传文件 MIME 由客户端声明导致误判
结论：服务器信任了客户端上传时声明的 MIME，实际内容不符。
原因：Content-Type 由客户端指定，可伪造。
解法：服务器校验文件内容（魔数/文件签名），不轻信客户端 MIME。
```
