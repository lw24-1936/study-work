## 概述

URL（Uniform Resource Locator）是 Web 资源的地址，前端每天都在解析、拼接、编码它。理解 URL 的结构、编码规则和同源策略，是处理路由、传参、跨域、防注入等问题的基本功。这篇笔记拆解 URL 的每个组成部分，讲清编码规则和同源判定。

```text
一个完整 URL 的解剖：
https://user:pass@example.com:443/path/to/page?query=1#section
└─┬─┘  └──┬───┘  └────┬────┘ └┬┘ └────┬────┘ └──┬───┘ └──┬──┘
Scheme  UserInfo   Host     Port   Path      Query   Fragment
```

## URL 结构：Scheme、Host、Port、Path、Query、Fragment

URL 由多个组件组成，每个组件有明确的职责：

```text
Scheme（协议）—— 访问资源的方式
Host（主机）—— 服务器域名或 IP
Port（端口）—— 服务端口（默认 80/443 可省略）
Path（路径）—— 资源在服务器上的位置
Query（查询串）—— 传给服务器的参数（键值对）
Fragment（片段）—— 页面内定位（#锚点），不发送给服务器
```

```text
完整示例：
https://www.example.com:443/products/list?category=book&page=2#reviews

Scheme   = https
Host     = www.example.com
Port     = 443（https 默认，通常省略）
Path     = /products/list
Query    = category=book&page=2
Fragment = reviews
```

```text
各组件详解：
Scheme —— http/https/ftp/mailto/file/data/blob 等，大小写不敏感（HTTPS 等价 https）
Host   —— 域名（DNS 解析成 IP）或直接 IP，也可以是 localhost
Port   —— http 默认 80、https 默认 443，非默认端口必须显式写出（:3000）
Path   —— 层级路径，用 / 分隔，区分大小写（取决于服务器）
Query  —— ? 之后，key=value 用 & 连接，需 URL 编码
Fragment —— # 之后，浏览器内定位，不参与 HTTP 请求
```

```text
Fragment 的特殊性：
1. 不发送给服务器（纯客户端行为）
2. 用于锚点定位（<a href="#section">）
3. SPA 路由早期用 hash 模式（#/page），因为改 hash 不刷新页面
4. 改变 Fragment 会在浏览器历史里加记录，可监听 hashchange 事件
```

```text
URL 相关易混淆点：
1. URL vs URI —— URI 是统一资源标识符（更宽泛），URL 是 URI 的一种（定位资源）
2. 绝对 URL vs 相对 URL —— 完整地址 vs 相对当前页面的路径（../、./、/）
3. 编码后的 URL —— 特殊字符需百分号编码（见下一节）
```

## URL Encoding 百分号编码

URL 只能安全传输 ASCII 字符，其他字符（中文、空格、特殊符号）需要编码成百分号形式。

```text
URL Encoding（百分号编码，Percent-Encoding）：
把非 ASCII 或保留字符转成 % + 两位十六进制。

规则：
1. 非 ASCII 字符（中文等）→ 先按 UTF-8 转字节，再每个字节 %XX
2. 保留字符（& = ? # / 等在 URL 里有特殊含义）→ 出现在数据里时需编码
3. 空格 → %20（或 +，表单场景）
```

```text
编码示例：
中文「中」→ %E4%B8%AD（UTF-8 三个字节）
空格     → %20
&        → %26
=        → %3D
/        → %2F
?        → %3F
#        → %23
```

```js
// JavaScript 里的 URL 编码
const s = '中 & / ?';

encodeURIComponent(s);   // %E4%B8%AD%20%26%20%2F%20%3F（编码所有特殊字符，用于参数值）
encodeURI(s);            // %E4%B8%AD%20&%20/%20?（保留 URL 结构字符，用于完整 URL）

decodeURIComponent('%E4%B8%AD');  // 解码
```

```text
encodeURIComponent vs encodeURI（关键区别）：
encodeURIComponent —— 编码除 A-Za-z0-9 -_.!~*'() 外的所有字符，
                      用于编码「参数值」（query 的 value）
encodeURI           —— 保留 & / ? : # 等 URL 结构字符，
                      用于编码「完整 URL」（但要小心）

实际最常用 encodeURIComponent 编码单个参数。
```

```text
查询串的编码坑：
Query 里的键值对，键和值都要编码，尤其是值里含 & = ? # 空格时。
不编码会导致参数被截断或语义错误。
```

## URL Parsing 与 URL API

现代浏览器提供 URL API，规范地解析和构造 URL，避免手写正则拼 URL 的坑。

```js
// URL 构造函数解析
const url = new URL('https://www.example.com:8080/products/list?category=book&page=2#reviews');

url.protocol;   // "https:"
url.host;       // "www.example.com:8080"
url.hostname;   // "www.example.com"
url.port;       // "8080"
url.pathname;   // "/products/list"
url.search;     // "?category=book&page=2"
url.hash;       // "#reviews"
url.origin;     // "https://www.example.com:8080"
```

```js
// 用 URLSearchParams 处理查询串（规范、自动编码）
const params = new URLSearchParams('category=book&page=2');

params.get('category');        // "book"
params.set('page', '3');       // 修改
params.append('tag', 'new');   // 追加
params.toString();             // "category=book&page=3&tag=new"

// 构造带参数 URL
const url = new URL('/search', 'https://example.com');
url.searchParams.set('q', '前端');
url.toString();  // "https://example.com/search?q=%E5%89%8D%E7%AB%AF"（自动编码中文）
```

```text
URL API 相比手写字符串拼接的优势：
1. 自动编码 —— 中文、特殊字符自动百分号编码
2. 规范解析 —— 处理相对路径、默认端口、路径规范化
3. 安全 —— 避免拼接错误导致的注入风险

坑：手写拼接 URL（如 `'?q=' + 用户输入`）是 XSS 和参数注入的常见来源。
```

```text
URL Parsing 的细节：
1. new URL(relative, base) —— 相对 URL 基于 base 解析成绝对 URL
2. URL 会自动规范化 —— 路径里的 . 和 .. 会被处理
3. 默认端口会隐藏 —— 443 端口的 https URL，url.port 返回空字符串
```

## Origin 与 Same Origin 同源策略

Origin（源）是 Web 安全的核心概念，同源策略（Same-Origin Policy）据此隔离不同源的资源。

```text
Origin 的定义：
协议 + 主机 + 端口，三者共同构成一个 Origin。

https://example.com:443
└─┬─┘  └────┬────┘ └┬┘
协议      主机     端口

只要三者有一个不同，就是不同源。
```

```text
同源判定示例（对比 https://example.com）：
https://example.com/app      —— 同源（路径不影响）
https://example.com:444/app  —— 不同源（端口不同）
http://example.com/app       —— 不同源（协议不同）
https://api.example.com/app  —— 不同源（主机不同）
https://sub.example.com/app  —— 不同源（主机不同，子域名也算不同）
```

```text
同源策略（Same-Origin Policy）限制什么：
1. DOM 访问 —— 不同源的页面不能互相读取 DOM
2. Cookie/localStorage —— 不同源不能访问
3. 网络请求响应 —— 跨域请求的响应被浏览器拦截（CORS 才能放行）

注意：同源策略限制的是「读取」，跨域请求本身能发出（CSRF 就是利用了这一点），
只是响应被浏览器拦截。
```

```text
同源策略不限制什么（可跨源加载）：
1. <script src>、<img src>、<link href>、<iframe src> —— 标签加载不受限
2. 表单提交、重定向
3. CORS 授权的跨域请求
```

```text
Origin 与 Same Origin 的实际应用：
1. 跨域 —— 前端调不同源的 API 要配 CORS
2. Cookie 作用域 —— SameSite 属性控制跨站携带
3. localStorage 隔离 —— 不同源（甚至不同端口）存储不共享
4. postMessage —— 跨源通信的安全手段，要校验 event.origin
```

## 应用场景实战

### 场景一：安全的拼接带参数的 URL

```js
// 错误：手写拼接（中文和特殊字符会出错）
const keyword = '前端 & 框架';
const bad = `/search?q=${keyword}`;  // 错误：& 会被当成参数分隔符，中文没编码

// 正确：用 URLSearchParams（自动编码）
const params = new URLSearchParams({ q: keyword });
const good = `/search?${params.toString()}`;
// "/search?q=%E5%89%8D%E7%AB%AF%20%26%20%E6%A1%86%E6%9E%B6"
```

### 场景二：解析当前页面的路由参数

```js
// 解析 URL 里的查询参数（SPA 常用）
function getQueryParams() {
  const params = new URLSearchParams(window.location.search);
  const result = {};
  for (const [key, value] of params) {
    result[key] = value;
  }
  return result;
}

// 或直接取单个参数
const page = new URLSearchParams(location.search).get('page');
```

### 场景三：跨源通信时的 Origin 校验

```js
// 父页面监听子 iframe 发来的消息，必须校验 origin
window.addEventListener('message', (event) => {
  // 关键：校验消息来源，防止恶意页面发消息
  if (event.origin !== 'https://trusted.example.com') {
    return;
  }
  // 处理 event.data
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 拼接 URL 用 URL/URLSearchParams API，不手写字符串拼接
2. 用户输入进 URL（查询参数、路径）一律 encodeURIComponent 编码
3. 解析参数用 URLSearchParams，不手写正则分割
4. 跨源通信（postMessage）必须校验 event.origin
5. SPA 路由优先 history 模式（干净 URL），hash 模式仅作兼容兜底
6. 敏感数据（token、密码）不放 Query（会进日志、Referer、历史记录）

### 踩坑记录

```text
坑 1：手写拼接 URL 导致参数被截断或注入
结论：含 & 或中文的参数解析错误，甚至被注入额外参数。
原因：没编码特殊字符，& 被当成分隔符，中文无法传输。
解法：用 URLSearchParams/encodeURIComponent，不要手写拼接。

坑 2：encodeURI 和 encodeURIComponent 用反
结论：用 encodeURI 编码参数值，& = ? 没编码，参数仍被截断。
原因：encodeURI 保留 URL 结构字符，不适合编码参数值。
解法：参数值用 encodeURIComponent，完整 URL 才用 encodeURI。

坑 3：history 路由刷新 404
结论：SPA 用 history 模式，直接访问 /page 或刷新报 404。
原因：history 路由靠前端拦截，服务器没有对应的真实文件，刷新时服务器找不到资源。
解法：服务器配 fallback 到 index.html（Nginx try_files、前端框架的 rewrite 规则）。

坑 4：跨域时误以为改端口不影响同源
结论：localhost:3000 调 localhost:8080 被 CORS 拦截。
原因：同源要求协议+主机+端口三者一致，端口不同就是跨域。
解法：配 CORS 或用代理（dev server proxy 转发同源请求）。

坑 5：Query 里放敏感数据被泄露
结论：token/password 出现在 URL 里，被日志、Referer、浏览器历史记录。
原因：Query 参数随 URL 到处传播（Referer 头、访问日志、历史）。
解法：敏感数据放 Body 或 Header，不放 Query。

坑 6：postMessage 不校验 origin 导致安全漏洞
结论：恶意页面发消息被父页面当成可信数据处理。
原因：没校验 event.origin，任何页面都能 postMessage 进来。
解法：始终校验 event.origin 是否为可信源，再处理 event.data。
```
