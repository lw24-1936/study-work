## 概述

Web 标准是「浏览器如何工作、网页如何编写」的规范集合。前端工程师写的每一行代码最终都由浏览器按标准解释执行，理解了「标准是谁定的、怎么演进的」，才能解释「为什么这个 API 在 Chrome 能用、在 Safari 不行」这类问题，也才能写出跨浏览器、可访问、可渐进增强的代码。

```text
Web 标准的三大支柱：
1. HTML —— 页面结构（WHATWG 维护）
2. CSS  —— 页面样式（W3C 维护）
3. JavaScript —— 页面行为（ECMA/TC39 维护）
```

## 标准组织：W3C、WHATWG、TC39

Web 标准不是一家定的，由多个组织分工协作：

```text
W3C（World Wide Web Consortium，万维网联盟）：
由 Tim Berners-Lee 创立的标准组织，制定 CSS、SVG、XML、WAI 可访问性等标准。
流程偏「委员会制」，文档叫 Recommendation（推荐标准）。

WHATWG（Web Hypertext Application Technology Working Group）：
浏览器厂商组成的组织（Apple/Google/Mozilla/Microsoft），维护 HTML、DOM、
URL、Fetch 等「活标准」（Living Standard）。
背景：W3C 曾想用 XHTML 取代 HTML，浏览器厂商反对，另立门户维护 HTML 的演进。

TC39（Technical Committee 39）：
Ecma International 下属的技术委员会，负责 ECMAScript（JavaScript 标准）的演进。
由各浏览器厂商和公司的工程师组成，提案经过固定流程进入标准。
```

```text
W3C 与 WHATWG 的分工（关键记忆点）：
WHATWG —— HTML、DOM、URL、Fetch（浏览器核心行为，活标准，持续更新）
W3C    —— CSS、SVG、Web 可访问性 WAI、WebAssembly 接口（委员会式推荐标准）

2019 年两组织达成合作：W3C 直接采用 WHATWG 的 HTML 活标准，
不再各自维护两套 HTML 规范。
```

```text
标准 vs 实现（为什么会有浏览器差异）：
标准是「应该怎样」，实现是「浏览器实际怎样」。
浏览器对标准支持有先后和差异，所以新 API 要用 caniuse.com 查兼容性，
用特性检测（feature detection）而非 UA 判断来写兼容代码。
```

## ECMAScript 与 JavaScript 的关系

```text
JavaScript vs ECMAScript：
ECMAScript —— 语言标准（语法、类型、内置对象），由 TC39 制定的规范文档
JavaScript —— 实现（V8、SpiderMonkey、JavaScriptCore 引擎按 ECMAScript 实现）

JavaScript = ECMAScript + 宿主环境 API（浏览器的 DOM/BOM、Node.js 的 fs/http）
```

```text
ECMAScript 版本演进（ES6 之后按年份命名）：
ES5（2009）—— 严格模式、JSON、Array 方法（map/filter/reduce）
ES6 / ES2015 —— let/const、箭头函数、类、模块、Promise、解构、模板字符串
ES2016~ES2023 —— async/await、可选链 ?.、空值合并 ??、BigInt、顶层 await
ESNext —— 提案阶段的新特性
```

```text
TC39 的提案流程（5 个阶段）：
Stage 0 —— 想法（Strawman）
Stage 1 —— 提案（Proposal）
Stage 2 —— 草案（Draft，开始有规范文本）
Stage 3 —— 候选（Candidate，浏览器开始实验性实现）
Stage 4 —— 完成（Finished，进入下一版 ECMAScript）

前端关注 Stage 3 的特性即可提前了解未来语法（如曾经的可选链、私有字段）。
```

## Web Platform：浏览器平台能力

Web Platform 指浏览器暴露给开发者的一整套 API 集合，是「浏览器能做什么」的总和。

```text
Web Platform 的能力范围：
1. DOM/BOM —— 操作页面结构和浏览器窗口
2. 网络 —— Fetch、WebSocket、SSE、WebRTC
3. 存储 —— Cookie、localStorage、IndexedDB、Cache Storage
4. 图形 —— Canvas、WebGL、WebGPU
5. 设备 —— 地理位置、摄像头、传感器
6. 性能 —— Performance API、Web Worker、Service Worker
7. 安全 —— CSP、Trusted Types、Web Crypto
```

```text
Web Platform 的演进特点：
1. 可扩展 —— 新 API 持续加入（每年都有新能力）
2. 兼容优先 —— 旧 API 基本不删除，保证老网页不坏
3. 渐进可用 —— 新 API 先在部分浏览器实现，逐步普及
```

```text
前端如何跟进 Web Platform：
1. caniuse.com / MDN 查兼容性
2. 用特性检测（'fetch' in window）而非 UA 字符串判断
3. 新能力配 polyfill 或降级方案
4. 关注 Chrome 的「intent to ship」和 TC39 提案
```

## 渐进增强与优雅降级

这是两个互补的「兼容性设计」思想，决定代码如何适配不同能力的浏览器。

```text
渐进增强（Progressive Enhancement）：
以「内容可用」为基础，能力越强的浏览器得到越好的体验。
先保证基本功能在任何环境可用，再叠加增强。

分层：
1. HTML —— 结构内容（任何浏览器都可用）
2. CSS  —— 样式增强
3. JavaScript —— 交互增强（JS 挂了页面仍有内容）
```

```text
优雅降级（Graceful Degradation）：
以「完整功能」为起点，能力弱的浏览器退而求其次，保证不崩溃。
先做完整功能，再为老浏览器做降级处理。
```

```text
渐进增强 vs 优雅降级：
渐进增强 —— 从「最小可用」往上加，底层稳（现代主流做法）
优雅降级 —— 从「完整功能」往下退，保底可用

实际是同一件事的两面：核心都是「基础内容在所有环境可用」。
现代实践倾向渐进增强——先让内容可访问，再用特性检测叠加能力。
```

```js
// 特性检测示例（渐进增强的核心手法）
// 支持 fetch 就用 fetch，不支持则降级到 XMLHttpRequest 或提示
if ('fetch' in window) {
  fetch('/api/data').then(r => r.json());
} else {
  // 降级：XMLHttpRequest
  const xhr = new XMLHttpRequest();
  xhr.open('GET', '/api/data');
  xhr.onload = () => console.log(xhr.responseText);
  xhr.send();
}
```

## Accessibility 可访问性

Accessibility（可访问性，简称 a11y）指让网站对所有人可用——包括视力、听力、行动、认知障碍用户，以及依赖辅助技术（屏幕阅读器）的用户。

```text
可访问性关注的人群：
1. 视障 —— 依赖屏幕阅读器、需要高对比度、可缩放
2. 听障 —— 视频需要字幕、音频需要文字替代
3. 行动障碍 —— 需要键盘导航（不能用鼠标）
4. 认知障碍 —— 需要清晰的内容结构
```

```text
可访问性的核心标准：WAI（Web Accessibility Initiative，W3C 下属）
WCAG（Web Content Accessibility Guidelines）—— 网页内容可访问性指南
四个原则 POUR：
Perceivable（可感知）—— 内容能被感知（图片有 alt、视频有字幕）
Operable（可操作）—— 界面可操作（键盘可导航、时间充足）
Understandable（可理解）—— 内容可理解（语言明确、导航一致）
Robust（健壮）—— 内容健壮（兼容辅助技术，语义化 HTML）
```

```text
前端可访问性的具体做法：
1. 语义化 HTML —— 用 <button>/<nav>/<main> 等正确标签，不用 div 堆
2. 图片加 alt —— 屏幕阅读器读 alt 文本
3. 键盘可达 —— 所有交互能用键盘完成（Tab 导航、focus 样式）
4. 颜色对比度 —— 文字与背景对比度达 WCAG 标准（正文 4.5:1）
5. ARIA —— 补充语义（role、aria-label、aria-expanded 等）
6. 表单标签 —— label 关联 input（for/id）
```

```html
<!-- 可访问性正确 vs 错误的写法 -->
<!-- 错误：div 当按钮，屏幕阅读器认不出 -->
<div onclick="submit()">提交</div>

<!-- 正确：语义化 button，可键盘操作 -->
<button type="submit">提交</button>

<!-- 图标按钮加 aria-label（图标本身没有文字） -->
<button aria-label="关闭">
  <svg><!-- 关闭图标 --></svg>
</button>
```

## 应用场景实战

### 场景一：判断一个 API 能否在当前浏览器使用

```js
// 特性检测 + 优雅降级的完整示例
function copyText(text) {
  // 优先用现代 Clipboard API
  if (navigator.clipboard && window.isSecureContext) {
    return navigator.clipboard.writeText(text);
  }
  // 降级：document.execCommand（老方案）
  const textarea = document.createElement('textarea');
  textarea.value = text;
  document.body.appendChild(textarea);
  textarea.select();
  document.execCommand('copy');
  document.body.removeChild(textarea);
  return Promise.resolve();
}
```

### 场景二：给组件做可访问性加固

```html
<!-- 一个可访问的折叠面板（accordion） -->
<button
  aria-expanded="false"
  aria-controls="panel-1"
  id="accordion-trigger-1">
  什么是 Web 标准？
</button>
<div id="panel-1" role="region" aria-labelledby="accordion-trigger-1" hidden>
  Web 标准是浏览器如何工作的规范集合...
</div>

<script>
  const btn = document.getElementById('accordion-trigger-1');
  const panel = document.getElementById('panel-1');
  btn.addEventListener('click', () => {
    const expanded = btn.getAttribute('aria-expanded') === 'true';
    btn.setAttribute('aria-expanded', String(!expanded));
    panel.hidden = expanded;  // hidden 属性让屏幕阅读器跳过
  });
</script>
```

## 最佳实践与踩坑记录

### 最佳实践

1. 新 API 用特性检测（feature detection）判断支持，不用 UA 字符串嗅探
2. 内容优先保证在「无 JS」环境可用（渐进增强），再用 JS 叠加交互
3. 用语义化 HTML 标签，不滥用 div/span 代替 button/nav/main
4. 图片加 alt、图标按钮加 aria-label、交互支持键盘操作
5. 关注 caniuse.com 和 MDN 的兼容性数据，新特性配 polyfill 或降级
6. 颜色对比度、字体缩放、焦点样式纳入设计规范，而非事后补

### 踩坑记录

```text
坑 1：用 UA 字符串判断浏览器能力
结论：Chrome 内核的国产浏览器、伪装 UA 的爬虫被误判，功能失效。
原因：UA 可伪造、同一内核 UA 千差万别，不能反映真实能力。
解法：用特性检测（'fetch' in window、'IntersectionObserver' in window）判断。

坑 2：无障碍按钮用 div 实现
结论：屏幕阅读器读不出、无法键盘 Tab 聚焦、Enter/Space 键无响应。
原因：div 没有语义，辅助技术识别不了，也不产生默认键盘行为。
解法：交互元素用原生 button/a，实在要用 div 就补 role + tabindex + 键盘事件。

坑 3：图标按钮没有文字说明
结论：屏幕阅读器读不出按钮作用（只读到「按钮」）。
原因：图标是 SVG/字体，没有可读文本。
解法：加 aria-label，或提供隐藏的可读文本（visually-hidden）。

坑 4：图片缺 alt 导致信息缺失
结论：视障用户完全不知道图片内容。
原因：没写 alt 属性。
解法：有意义图片写描述性 alt，纯装饰图片写空 alt=""（让阅读器跳过）。

坑 5：强依赖 JS 导致无 JS 环境白屏
结论：JS 加载失败/被禁用时页面空白。
原因：内容全靠 JS 渲染，HTML 是空壳。
解法：关键内容放 HTML（SSR 或静态渲染），JS 只做增强（渐进增强思想）。
```
