## 概述

字符编码解决「文字如何在计算机里存储和传输」的问题——计算机只认字节（0 和 1），而人类需要字符（字母、汉字、emoji）。前端几乎每天都会遇到编码问题：中文乱码、字符串长度计算错误、Base64 传输二进制、HTML 转义。这篇笔记讲清字符集、编码方案和几种编码应用。

```text
字符编码的两个层次（务必区分）：
1. 字符集（Character Set）—— 字符的集合和编号（如 Unicode 给每个字符一个码点）
2. 编码方案（Encoding）—— 码点如何转成字节序列（如 UTF-8、UTF-16）

同一个字符集（Unicode）可以有多种编码方案（UTF-8/UTF-16/UTF-32）。
```

## ASCII 与字符集基础

ASCII（American Standard Code for Information Interchange）是最早的字符集，用 7 位（0~127）表示 128 个字符。

```text
ASCII 的范围：
0~31    —— 控制字符（换行、制表符等）
32~126  —— 可打印字符
  48~57  —— 数字 0-9
  65~90  —— 大写字母 A-Z
  97~122 —— 小写字母 a-z
127     —— DEL（删除）
```

```text
ASCII 的局限：
只有 128 个字符，只能表示英文字母、数字、标点，无法表示中文、日文、emoji。

这就催生了各种扩展编码（问题所在）：
1. 各语言各自扩展 —— GB2312/GBK（中文）、Shift-JIS（日文）、Latin-1（西欧）
2. 互不兼容 —— 同一字节序列在不同编码下解读成不同字符（乱码的根源）
```

```text
乱码的本质：
字节序列是「用编码 A 写入」的，却「用编码 B 解读」，
解读结果和原意不符，就是乱码。
```

## Unicode 统一编码

Unicode 是「给全世界所有字符一个唯一编号」的统一字符集，解决各种扩展编码互不兼容的问题。

```text
Unicode 的核心概念 —— 码点（Code Point）：
每个字符分配一个唯一的编号，写作 U+XXXX。

'A'  = U+0041
'中' = U+4E2D
'😀' = U+1F600（超出 BMP，见下文）
```

```text
码点范围：
U+0000 ~ U+FFFF     —— BMP（基本多语言平面），常用字符都在这里
U+10000 ~ U+10FFFF  —— 增补平面，emoji、生僻字、古文字

Unicode 目前定义了 100 多万个码点，持续扩充。
```

```text
Unicode 相关概念：
1. 码点 —— 字符的唯一编号（字符集的层面）
2. 编码方案 —— 码点如何变成字节（UTF-8/16/32）
3. 字符 vs 字素簇（grapheme cluster）—— 一个「视觉字符」可能由多个码点组成
   （如 emoji 肤色修饰、组合字符），是前端处理字符串的难点
```

## 编码方案：UTF-8、UTF-16、UTF-32

UTF（Unicode Transformation Format）系列是 Unicode 的具体编码方案，区别在「变长还是定长」。

### UTF-8（变长，1~4 字节）

```text
UTF-8 的编码规则（变长）：
码点范围          字节数   格式
U+0000~U+007F     1 字节   0xxxxxxx
U+0080~U+07FF     2 字节   110xxxxx 10xxxxxx
U+0800~U+FFFF     3 字节   1110xxxx 10xxxxxx 10xxxxxx
U+10000~U+10FFFF  4 字节   11110xxx 10xxxxxx 10xxxxxx 10xxxxxx

特点：
1. 兼容 ASCII —— ASCII 字符在 UTF-8 里仍是 1 字节（0xxxxxxx），完全一致
2. 变长 —— 英文 1 字节，中文 3 字节，emoji 4 字节
3. 无字节序问题 —— 按字节流解析，天然无大小端
```

```text
UTF-8 是 Web 的事实标准：
1. 兼容 ASCII（老系统平滑过渡）
2. 节省空间（英文为主的内容小）
3. 无字节序问题
现代 Web 统一 UTF-8（HTML meta charset、HTTP 头、文件、数据库都用 UTF-8）。
```

```text
中文在 UTF-8 里占 3 字节：
'中' = U+4E2D → 1110xxxx 10xxxxxx 10xxxxxx → E4 B8 AD（3 字节）
```

### UTF-16（变长，2 或 4 字节）

```text
UTF-16 的编码规则：
BMP 字符（U+0000~U+FFFF）—— 2 字节（1 个码元）
增补字符（U+10000~U+10FFFF）—— 4 字节（2 个码元，代理对 surrogate pair）

代理对：用两个 16 位码元表示一个超出 BMP 的字符。
高代理（U+D800~U+DBFF）+ 低代理（U+DC00~U+DFFF）
```

```text
UTF-16 与 JavaScript：
JS 内部用 UTF-16 存储字符串，这是很多「字符串怪现象」的根源：
1. '中'.length === 1 —— BMP 内，1 个码元
2. '😀'.length === 2 —— 超出 BMP，代理对，2 个码元
3. 用 charAt/索引访问 emoji 会得到半个代理对（乱码）
```

```js
// JS 字符串长度与 Unicode 的坑
'中'.length;           // 1
'😀'.length;           // 2（代理对 = 2 个码元）
'👨‍👩‍👧‍👦'.length;      // 11（家庭 emoji 由多个码点 + 连接符组成）

// 正确处理（按码点或字素簇）
[...'😀'].length;              // 1（按码点）
[...'👨‍👩‍👧‍👦'].length;       // 7（按码点，仍不是 1 个视觉字符）
```

### UTF-32（定长 4 字节）

```text
UTF-32 的编码规则：
每个码点固定 4 字节（32 位），一一对应，最简单。

特点：
1. 定长 —— 按码点访问 O(1)，无需变长解析
2. 浪费空间 —— 英文也占 4 字节（是 UTF-8 的 4 倍）
3. 基本不用 —— 只在内存内部表示（如 Python 老版本内部）才见
```

```text
三种 UTF 方案对比：
| 方案    | 长度   | 英文 | 中文 | emoji | 特点                |
|---------|--------|------|------|-------|---------------------|
| UTF-8   | 变长   | 1    | 3    | 4     | 兼容 ASCII，Web 标准 |
| UTF-16  | 变长   | 2    | 2    | 4     | JS 内部，代理对      |
| UTF-32  | 定长 4 | 4    | 4    | 4     | 简单但浪费，少用     |
```

```text
字节序（Byte Order Mark / BOM）：
UTF-16/UTF-32 有字节序问题（大端/小端），用 BOM 标记。
UTF-8 无字节序问题，但有时文件开头会有 BOM（EF BB BF），
会导致 HTML/JS 解析异常（前端构建工具常要去 BOM）。
```

## Base64

Base64 是一种「把二进制数据编码成 ASCII 文本」的方案，让二进制数据能在只支持文本的渠道传输。

```text
Base64 的原理：
1. 把二进制按 6 位一组切分
2. 每组 6 位映射到一个可打印字符（64 个字符的表）
3. 字符表：A-Z a-z 0-9 + /（共 64 个），不足补 = 填充

3 字节 → 4 个 Base64 字符（体积增加约 1/3）
```

```text
Base64 的用途：
1. Data URL —— 把小图片/资源内嵌进 HTML/CSS（data:image/png;base64,...）
2. 传输二进制 —— 在 JSON/XML 里传图片、文件（如 API 传头像）
3. 邮件附件 —— MIME 里编码二进制附件
4. 简单混淆 —— 不是加密，只是编码（可轻易解码，勿当加密用）
```

```js
// 浏览器里的 Base64
btoa('hello');                          // "aGVsbG8="（字符串 → Base64）
atob('aGVsbG8=');                       // "hello"（Base64 → 字符串）

// 处理中文（btoa 不支持非 ASCII，需先转 UTF-8 字节）
const str = '中';
const bytes = new TextEncoder().encode(str);
let binary = '';
bytes.forEach(b => binary += String.fromCharCode(b));
btoa(binary);                            // 中文的 Base64
```

```text
Base64 的坑：
1. 不是加密 —— 只是编码，任何人可解码，不能保护敏感数据
2. 体积增大 —— 约 1/3，小文件才适合 base64 内嵌（大文件反而增加体积）
3. URL 安全的 Base64 —— 标准 Base64 的 + / = 在 URL 里有问题，
   有 base64url 变体（- _ 代替 + /，去掉 =）
```

## URL Encoding 与 HTML Entity

字符编码在 Web 里有两个具体应用：URL 编码和 HTML 实体。

### URL Encoding（百分号编码）

URL 只能传输 ASCII 字符，非 ASCII 和特殊字符需要百分号编码（详见 03.2-URL）。

```text
URL Encoding 规则：
非 ASCII 字符 → 按 UTF-8 转字节 → 每个字节 %XX

'中' → %E4%B8%AD（UTF-8 三个字节）
空格 → %20
&    → %26
```

```js
encodeURIComponent('中 &');  // "%E4%B8%AD%20%26"
```

### HTML Entity（HTML 实体）

HTML 里某些字符有特殊含义（< > & "），要显示它们本身就得用实体转义。

```text
常用 HTML 实体：
&lt;    → <（小于号）
&gt;    → >（大于号）
&amp;   → &（和号）
&quot;  → "（双引号）
&nbsp;  → 空格（不换行空格）

数字形式（用 Unicode 码点）：
&#60;   → <（十进制）
&#x3C;  → <（十六进制）
&#20013; → 中（Unicode 码点）
```

```text
HTML Entity 的用途：
1. 转义用户输入 —— 防 XSS（把 < 转成 &lt;，用户输入不会被当标签执行）
2. 显示特殊字符 —— 在 HTML 里显示 < > & 本身
3. 输入特殊符号 —— &copy;（©）、&rarr;（→）等
```

```js
// HTML 转义（防 XSS 的基础）
function escapeHtml(str) {
  return str
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;');
}
```

## 应用场景实战

### 场景一：处理文件/接口的 UTF-8 乱码

```text
场景：后端返回 GBK 编码的数据，前端按 UTF-8 解析出乱码。

解决（前端）：
1. 优先让后端统一 UTF-8（治本）
2. 无法改后端时，用 TextDecoder 按实际编码解码：

fetch('/api/data')
  .then(r => r.arrayBuffer())
  .then(buf => {
    // 假设实际是 GBK，用 TextDecoder 指定编码
    const text = new TextDecoder('gbk').decode(buf);
    console.log(text);
  });
```

### 场景二：上传文件用 Base64 传输

```js
// 文件转 Base64（配合 FileReader）
function fileToBase64(file) {
  return new Promise((resolve, reject) => {
    const reader = new FileReader();
    reader.onload = () => resolve(reader.result);  // data:...;base64,xxx
    reader.onerror = reject;
    reader.readAsDataURL(file);
  });
}

// 或转纯 Base64 字符串（不带 data: 前缀）
function fileToPureBase64(file) {
  return new Promise((resolve, reject) => {
    const reader = new FileReader();
    reader.onload = () => resolve(reader.result.split(',')[1]);
    reader.onerror = reject;
    reader.readAsDataURL(file);
  });
}
```

### 场景三：正确计算含 emoji 的字符串长度

```js
// 错误：直接 .length（UTF-16 码元数，emoji 算 2）
'hello😀'.length;  // 7（实际视觉是 6 个字符）

// 正确：按码点（Unicode 字符）计算
[...'hello😀'].length;  // 6

// 更精确：按字素簇（视觉字符），用 Intl.Segmenter
const seg = new Intl.Segmenter('zh', { granularity: 'grapheme' });
[...seg.segment('hello😀')].length;  // 6
```

## 最佳实践与踩坑记录

### 最佳实践

1. 全链路统一 UTF-8：文件、HTML meta、HTTP 头、数据库、接口
2. 字符串长度/截断用 [...str] 或 Intl.Segmenter 按码点/字素簇处理，不直接 .length
3. 用户输入进 HTML 前转义（HTML Entity），进 URL 前编码（encodeURIComponent）
4. Base64 只用于编码，不用来「加密」敏感数据
5. 二进制处理用 TextEncoder/TextDecoder 显式指定编码，避免隐式转换

### 踩坑记录

```text
坑 1：中文乱码
结论：页面/接口中文显示成 � 或奇怪字符。
原因：编码和解码不一致（GBK 数据按 UTF-8 解析，或反过来）。
解法：全链路统一 UTF-8；无法改后端时用 TextDecoder 指定实际编码。

坑 2：emoji 字符串长度计算错误
结论：'😀'.length === 2，用它做截断/字数统计会出错。
原因：JS 内部 UTF-16，emoji 是代理对（2 个码元）。
解法：用 [...str]、Array.from 或 Intl.Segmenter 按码点/字素簇处理。

坑 3：btoa 处理中文直接报错
结论：btoa('中文') 抛 InvalidCharacterError。
原因：btoa 只接受 Latin1（0~255）字符，中文超出范围。
解法：先 TextEncoder 转 UTF-8 字节，再转二进制字符串后 btoa。

坑 4：带 BOM 的文件导致解析异常
结论：JS/CSS 文件开头有 BOM，浏览器解析报错或样式失效。
原因：文件保存时带了 UTF-8 BOM（EF BB BF），浏览器把它当内容。
解法：用编辑器/构建工具去掉 BOM，保存为「无 BOM 的 UTF-8」。

坑 5：把 Base64 当加密用
结论：敏感数据用 Base64 编码后以为安全，实际可轻易解码。
原因：Base64 只是编码，不是加密，任何人可逆。
解法：敏感数据用真正的加密（AES 等），Base64 只用于二进制文本化传输。

坑 6：HTML 里显示用户输入没转义导致 XSS
结论：用户输入 <script> 被当成标签执行。
原因：没做 HTML Entity 转义，特殊字符直接进 DOM。
解法：用户输入进 HTML 前转义（escapeHtml），或用框架的安全渲染（React 默认转义）。
```
