## 概述

WebRTC 是浏览器端实时音视频通信的标准，实现点对点（P2P）的音频、视频、数据传输。它通过 ICE 框架解决 NAT 穿透，通过 SDP 协商媒体参数，通过 RTP/RTCP 传输与控制媒体流，通过 DataChannel 传输任意数据。

```text
WebRTC 通信全流程：
1. 信令交换 —— 双方交换 SDP（媒体能力描述）
2. ICE 收集 —— 通过 STUN/TURN 收集候选地址
3. 连接建立 —— PeerConnection 协商出可用通道
4. 媒体传输 —— RTP 传输媒体，RTCP 反馈质量
5. 数据通道 —— DataChannel 传输任意二进制数据
```

## WebRTC

WebRTC 是一套开放标准，核心 API 包括 RTCPeerConnection、getUserMedia、RTCDataChannel 三大模块。

```text
WebRTC 三大核心 API：
1. getUserMedia —— 采集本地摄像头/麦克风
2. RTCPeerConnection —— 建立 P2P 连接，传输音视频
3. RTCDataChannel —— 双向任意数据传输
```

```js
// 采集本地媒体
const localStream = await navigator.mediaDevices.getUserMedia({
  video: true,
  audio: true,
});

// 创建连接
const pc = new RTCPeerConnection({
  iceServers: [{ urls: 'stun:stun.l.google.com:19302' }],
});

// 把本地流加入连接
localStream.getTracks().forEach((track) => pc.addTrack(track, localStream));
```

## PeerConnection

RTCPeerConnection 是 WebRTC 的核心对象，负责建立、维护 P2P 连接，协商媒体格式，处理候选地址与媒体传输。

```text
PeerConnection 职责：
1. 生成/接收 SDP（offer/answer）
2. 收集与交换 ICE 候选
3. 收发音视频流与数据通道
4. 统计连接质量（getStats）
```

```js
const pc = new RTCPeerConnection(config);

pc.onicecandidate = (e) => {
  if (e.candidate) sendToPeer({ type: 'candidate', candidate: e.candidate });
};
pc.ontrack = (e) => {
  remoteVideo.srcObject = e.streams[0];   // 收到远端媒体流
};
pc.onconnectionstatechange = () => {
  console.log(pc.connectionState);        // new/connecting/connected/failed
};
```

```js
// 发起方：创建并发送 offer
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
sendToPeer({ type: 'offer', sdp: offer });

// 应答方：接收 offer 后创建 answer
await pc.setRemoteDescription(offer);
const answer = await pc.createAnswer();
await pc.setLocalDescription(answer);
sendToPeer({ type: 'answer', sdp: answer });

// 发起方：收到 answer 后设置远端描述
await pc.setRemoteDescription(answer);

// 双方：添加远端候选
await pc.addIceCandidate(remoteCandidate);
```

## ICE

ICE（Interactive Connectivity Establishment）是 WebRTC 建立连接的框架，负责发现双方之间所有可用的通信路径（候选地址）并选出最优路径。

```text
ICE 候选类型：
1. host —— 本机地址（局域网直连）
2. srflx —— 经 STUN 反射的公网地址
3. relay —— 经 TURN 中继的地址（最后手段）

流程：收集候选 → 交换 → 连通性检查 → 选出最优路径
```

```js
pc.onicecandidate = (e) => {
  if (e.candidate) {
    console.log('发现候选：', e.candidate.type);
    signaling.send({ candidate: e.candidate });
  }
};
```

## STUN

STUN（Session Traversal Utilities for NAT）服务器帮助客户端发现自己的公网 IP 与端口，实现 NAT 穿透，是 ICE 候选收集的关键一环。

```text
STUN 的作用：
1. 客户端向 STUN 服务器发请求
2. STUN 返回「你的公网地址是 X」
3. 客户端获得 srflx 候选
4. 双方据此尝试 P2P 直连

局限：对称型 NAT 无法穿透，需 TURN 兜底。
```

```js
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'stun:stun1.l.google.com:19302' },
  ],
});
```

## TURN

TURN（Traversal Using Relays around NAT）服务器在无法 P2P 直连时，作为中继转发媒体数据。它是 NAT 穿透失败后的兜底方案。

```text
TURN 的作用：
1. 双方都无法直连时，经 TURN 服务器中转
2. 产生 relay 候选（最可靠但最贵）
3. 消耗服务器带宽，成本高于直连

流程：STUN 直连失败 → 尝试 TURN 中继 → 建立连接
```

```js
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    {
      urls: 'turn:turn.example.com:3478',
      username: 'user',
      credential: 'password',
    },
  ],
});
```

## SDP

SDP（Session Description Protocol）描述媒体的会话信息——编码格式、码率、传输地址等。WebRTC 通过交换 SDP（offer/answer）协商双方都支持的媒体参数。

```text
SDP 包含信息：
1. 会话元数据（名称、时间）
2. 媒体描述（音频/视频，m= 行）
3. 编码格式（opus、vp8、h264 等）
4. 传输地址与端口
5. ICE 相关属性
```

```js
// offer/answer 就是 SDP 的交换
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
console.log(offer.sdp);   // 完整的 SDP 文本
```

## RTP 与 RTCP

RTP（Real-time Transport Protocol）负责传输媒体数据，RTCP（RTP Control Protocol）负责传输控制信息（质量反馈、同步）。

```text
RTP：
1. 传输音频/视频的实际数据包
2. 基于 UDP，低延迟
3. 包含时间戳、序列号（用于排序与抖动计算）

RTCP：
1. 反馈丢包率、延迟、抖动
2. 实现带宽自适应与拥塞控制
3. 发送方与接收方报告（SR/RR）
```

```js
// 通过 getStats 查看 RTP/RTCP 统计
const stats = await pc.getStats();
stats.forEach((report) => {
  if (report.type === 'inbound-rtp' && report.kind === 'video') {
    console.log('丢包数：', report.packetsLost);
    console.log('码率：', report.bitrate);
    console.log('抖动：', report.jitter);
  }
});
```

## DataChannel

RTCDataChannel 在 P2P 连接上建立双向、低延迟的任意数据传输通道，可用于文字聊天、文件传输、游戏状态同步等。

```text
DataChannel 特点：
1. 基于 SCTP，可靠或不可靠两种模式
2. 低延迟，适合实时数据
3. 复用同一 P2P 连接，无需额外服务器
4. 支持任意二进制数据
```

```js
// 创建数据通道
const dc = pc.createDataChannel('chat', { ordered: true });

dc.onopen = () => console.log('数据通道已打开');
dc.onmessage = (e) => console.log('收到消息：', e.data);
dc.send('你好，WebRTC！');
dc.send(new Uint8Array([1, 2, 3]));   // 二进制数据

// 接收方监听
pc.ondatachannel = (e) => {
  const receiveChannel = e.channel;
  receiveChannel.onmessage = (ev) => console.log(ev.data);
};
```

  const localStream = await navigator.mediaDevices.getUserMedia({ video: true, audio: true });
  localVideo.srcObject = localStream;

  const pc = new RTCPeerConnection({ iceServers: [{ urls: 'stun:stun.l.google.com:19302' }] });
  localStream.getTracks().forEach((t) => pc.addTrack(t, localStream));

  pc.ontrack = (e) => (remoteVideo.srcObject = e.streams[0]);

}

## 最佳实践与踩坑记录

### 最佳实践

1. 生产环境必须配置 TURN，保证 NAT 穿透兜底
2. 信令服务器只负责交换元数据，不传输媒体
3. 用 getStats 监控丢包/码率，及时自适应
4. ICE 候选用 trickle ICE 逐条发送，加速连接
5. DataChannel 大文件分片传输，带结束标记
6. 连接关闭后停止所有 track 并 close 连接

### 踩坑记录

```text
坑 1：忘记配置 TURN 导致部分用户连不上
结论：局域网可通，跨运营商/对称 NAT 用户失败。
原因：对称 NAT 无法通过 STUN 穿透。
解法：配置 TURN 服务器作为中继兜底。

坑 2：SDP 交换顺序错误
结论：setRemoteDescription 报 InvalidStateError。
原因：必须先 setLocalDescription 才能 setRemote。
解法：严格按 offer/answer 流程：local → 发送 → remote。

坑 3：iceServers 配置格式错误
结论：连接一直停留在 checking。
原因：iceServers 结构或 URL 格式不对。
解法：用 urls 数组字段，stun:/turn: 前缀正确。

坑 4：信令消息丢失导致状态不同步
结论：一方卡在 connecting。
原因：offer/answer/candidate 消息未可靠送达。
解法：信令服务器保证可靠传输，或用 WebSocket。

坑 5：忘记释放媒体资源
结论：多次通话后设备异常、内存上涨。
原因：getUserMedia 的 track 未 stop。
解法：通话结束 track.stop() + pc.close()。
```
