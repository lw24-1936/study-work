## 概述

WebRTC 工程关注把 WebRTC 的「点对点」能力扩展为「多对多」实时通信系统的完整链路：信令交换、网络穿透、多人拓扑、流控与录制直播。

```text
WebRTC 工程要解决的问题：
1. 信令 —— 建立连接前如何交换 SDP/ICE 信息
2. 穿透 —— 大多数设备在 NAT 后，如何互相连通
3. 多人 —— 2 人以上的会议需要怎样的拓扑（Mesh/SFU/MCU）
4. 质量 —— 弱网下的码率/分辨率自适应
5. 扩展 —— 录制、直播、大房间
```

## Signaling 信令

信令是建立 WebRTC 连接前的「媒人」，负责交换 SDP 和 ICE 候选，WebRTC 本身不定义信令协议。

```js
// 信令服务器（WebSocket 中转 SDP/ICE）
const ws = new WebSocket('wss://signal.example.com');

ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === 'offer') handleOffer(msg.sdp);
  if (msg.type === 'answer') handleAnswer(msg.sdp);
  if (msg.type === 'ice') pc.addIceCandidate(msg.candidate);
};
```

```text
信令协议的选择：
1. WebSocket —— 最常用，双向实时
2. SSE + POST —— 单向推送 + 请求
3. SIP —— 传统 VoIP 信令

信令内容：Offer/Answer（SDP）、ICE Candidate、加入/离开房间等。
```

## Offer / Answer / ICE Candidate

Offer/Answer 是 SDP 协商的两端，ICE Candidate 是候选网络地址。

```js
// 发起方创建 Offer
const pc = new RTCPeerConnection();
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
sendToPeer({ type: 'offer', sdp: offer });

// 接收方创建 Answer
const answer = await pc.createAnswer();
await pc.setLocalDescription(answer);
sendToPeer({ type: 'answer', sdp: answer });
```

```js
// ICE Candidate：网络地址候选
pc.onicecandidate = (event) => {
  if (event.candidate) {
    sendToPeer({ type: 'ice', candidate: event.candidate });
  }
};
```

```text
SDP 协商流程：
1. 发起方 createOffer → setLocalDescription → 发送
2. 接收方 setRemoteDescription → createAnswer → 发送
3. 双方交换 ICE Candidate 完成连接

ICE Candidate 是「我能通过哪些地址被访问」的列表。
```

## STUN / TURN / NAT Traversal

STUN/TURN 服务器解决 NAT 穿透问题。

```js
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.example.com:3478' },                 // STUN
    {                                                       // TURN
      urls: 'turn:turn.example.com:3478',
      username: 'user',
      credential: 'pass',
    },
  ],
});
```

```text
三种 NAT 穿透方案：
STUN —— 查询「我的公网地址」，帮助直连（免费、轻量）
TURN —— 中继转发（无法直连时兜底，收费、带宽压力大）
mDNS/ICE —— 浏览器本地候选与中继组合

流程：优先直连（host/STUN），失败则走 TURN 中继。
```

## SFU / MCU / Mesh 拓扑

多人会议有三种网络拓扑。

```text
Mesh（全网状）—— 每两人之间都建连接
优点：无需服务器中转，延迟低
缺点：N 人需要 N(N-1)/2 条连接，上传带宽随人数线性增长，4 人以上就吃力

SFU（Selective Forwarding Unit）—— 每人只上传一路到服务器，服务器转发
优点：上传带宽固定为一路，支持几十人
缺点：服务器转发有少量延迟与成本

MCU（Multipoint Control Unit）—— 服务器混流合成一路下发
优点：客户端只收一路，最省客户端带宽
缺点：服务器算力成本高，灵活性差（无法单独布局）

现代选择：中小房间用 SFU，大型直播/千人用 MCU 或级联 SFU。
```

## Simulcast 与 SVC

Simulcast（多路同源）和 SVC（分层编码）解决多人场景的带宽适配。

```text
Simulcast（多码流）：
1. 发送端同时编码多档（720p/360p/180p）
2. SFU 按接收方能力转发对应档位
3. 上传带宽略增，但能适配不同接收方

SVC（Scalable Video Coding，分层编码）：
1. 一个码流内分基础层 + 增强层
2. 丢增强层仍能看基础层
3. 更灵活，但编码复杂度高、兼容性略差
```

```js
// Simulcast：发送端声明多档编码
const sender = pc.getSenders()[0];
const params = sender.getParameters();
params.encodings = [
  { rid: 'h', maxBitrate: 1500_000, scaleResolutionDownBy: 1 },
  { rid: 'm', maxBitrate: 500_000, scaleResolutionDownBy: 2 },
  { rid: 'l', maxBitrate: 150_000, scaleResolutionDownBy: 4 },
];
await sender.setParameters(params);
```

## Recording 与 Live Streaming

录制和直播是 WebRTC 的常见扩展。

```js
// 录制：MediaRecorder 采集流
const stream = await navigator.mediaDevices.getUserMedia({ video: true, audio: true });
const recorder = new MediaRecorder(stream);
const chunks = [];

recorder.ondataavailable = (e) => chunks.push(e.data);
recorder.onstop = () => {
  const blob = new Blob(chunks, { type: 'video/webm' });
  const url = URL.createObjectURL(blob);
  // 下载或上传
};

recorder.start();
setTimeout(() => recorder.stop(), 10000);
```

```text
直播方案：
1. 浏览器推流 —— WebRTC → 服务器转 RTMP/HLS 分发
2. SFU 录制 —— 服务器侧录制各路流
3. 混合 —— 本地录制 + 服务端录制兜底

直播常用协议：WebRTC（低延迟）、RTMP（推流）、HLS/DASH（播放）。
```

## 应用场景实战

### 场景一：多人视频会议（SFU）

```js
// 加入 SFU 房间：上行一路，下行按需订阅
const pc = new RTCPeerConnection({ iceServers });

// 上行：推送本地音视频
const localStream = await navigator.mediaDevices.getUserMedia({ video: true, audio: true });
localStream.getTracks().forEach(t => pc.addTrack(t, localStream));

// 下行：接收远端流（SFU 转发后触发）
pc.ontrack = (event) => {
  remoteVideo.srcObject = event.streams[0];
};
```

### 场景二：屏幕共享

```js
const screenStream = await navigator.mediaDevices.getDisplayMedia({ video: true });
const screenTrack = screenStream.getVideoTracks()[0];

// 替换视频轨为屏幕流
const sender = pc.getSenders().find(s => s.track?.kind === 'video');
await sender.replaceTrack(screenTrack);

// 用户结束共享时恢复
screenTrack.onended = async () => {
  const camStream = await navigator.mediaDevices.getUserMedia({ video: true });
  await sender.replaceTrack(camStream.getVideoTracks()[0]);
};
```

## 最佳实践与踩坑记录

### 最佳实践

1. 4 人以上用 SFU，别用 Mesh
2. 弱网用 Simulcast/SVC 自适应，配合码率控制
3. 生产环境部署自己的 TURN 中继（免费 TURN 不可靠）
4. 信令与媒体分离：信令走 WebSocket，媒体走 WebRTC
5. 录制/直播在服务端做，别只依赖客户端

### 踩坑记录

```text
坑 1：Mesh 拓扑人数一多就崩
结论：5 人视频会议卡顿、断流。
原因：Mesh 每条连接都要上传一路，上传带宽耗尽。
解法：换 SFU，每人只上行一路。

坑 2：只配 STUN 不配 TURN
结论：部分用户（对称 NAT）始终无法连通。
原因：STUN 只能解决部分 NAT，对称 NAT 必须 TURN 中继。
解法：生产环境配 TURN，STUN 优先直连、TURN 兜底。

坑 3：信令丢失导致连接失败
结论：offer/answer/candidate 顺序错乱或丢失，连接建立失败。
原因：信令通道不可靠或时序处理不当。
解法：信令服务器按序转发，客户端缓存未处理的 ICE candidate。

坑 4：ice candidate 在 setRemoteDescription 前到达
结论：收到 candidate 但 peer connection 未就绪，addIceCandidate 报错。
原因：candidate 早于 offer/answer 到达。
解法：缓存 candidate，待 setRemoteDescription 后批量 add。

坑 5：录制只用客户端 MediaRecorder
结论：用户关页面后录制中断。
原因：客户端录制依赖页面存活。
解法：关键场景服务端录制（SFU 侧），客户端录制仅作辅助。
```
