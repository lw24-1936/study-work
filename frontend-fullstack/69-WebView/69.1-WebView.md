## 概述

WebView 是嵌入在原生 App 中的浏览器组件，让 Web 页面运行在 App 内。它是 Hybrid App（混合应用）的技术基础，通过 JS Bridge 实现 Web 与 Native 的双向通信。

```text
WebView 的核心能力：
1. 渲染网页 —— 在 App 内展示 H5 页面
2. JS Bridge —— Web 调用 Native 能力（相机、定位、支付）
3. 深链 —— URL 跳转到 App 内指定页面
4. 混合 —— Web 的快速迭代 + Native 的体验与能力
```

## Android WebView 与 iOS WKWebView

两大平台各有 WebView 实现，API 与行为有差异。

```text
Android WebView：
1. 基于 Chromium，内核随系统 WebView 组件更新
2. 通过 addJavascriptInterface 注入 JS 桥
3. 需处理版本碎片化（不同系统 WebView 内核版本不同）

iOS WKWebView：
1. 基于 WebKit，性能优于老 UIWebView（已废弃）
2. 通过 WKScriptMessageHandler 注入 JS 桥
3. JS 与 Native 分离进程，隔离更好
```

```js
// Web 端通用桥调用封装
function callNative(method, params) {
  if (window.webkit?.messageHandlers?.bridge) {
    // iOS
    window.webkit.messageHandlers.bridge.postMessage({ method, params });
  } else if (window.AndroidBridge) {
    // Android
    window.AndroidBridge[method](JSON.stringify(params));
  }
}
```

```text
平台差异要点：
1. iOS 的 messageHandler 是异步回调，Android 的 addJavascriptInterface 可同步返回
2. iOS WKWebView 默认不跨域共享 Cookie（需 WKWebsiteDataStore）
3. 版本兼容 —— Android 4.4 前后 WebView 内核差异大
```

## JS Bridge 双向通信

JS Bridge 是 Web 与 Native 通信的桥梁，实现双向调用。

```text
双向通信的两个方向：
1. Web → Native：Web 调用 Native 方法（相机、支付、分享）
2. Native → Web：Native 主动推送事件（登录状态、网络变化）
```

```js
// Web → Native：调用 + 回调
function callNative(method, params) {
  return new Promise((resolve, reject) => {
    const callbackId = `cb_${Date.now()}_${Math.random()}`;
    window._callbacks[callbackId] = { resolve, reject };

    const payload = { method, params, callbackId };
    if (window.webkit?.messageHandlers?.bridge) {
      window.webkit.messageHandlers.bridge.postMessage(payload);
    } else if (window.AndroidBridge?.invoke) {
      window.AndroidBridge.invoke(JSON.stringify(payload));
    }
  });
}

// Native 回调 Web
window._handleCallback = (callbackId, result) => {
  const cb = window._callbacks[callbackId];
  if (cb) {
    cb.resolve(result);
    delete window._callbacks[callbackId];
  }
};
```

## Native Bridge 与 Message Handler

Native 侧通过 Message Handler 接收 Web 消息，并回传结果。

```js
// Android：注入 JS 接口
webView.addJavascriptInterface(new Bridge(), "AndroidBridge");

class Bridge {
  @JavascriptInterface
  public String invoke(String json) {
    // 解析 payload，执行 method，返回结果
    return resultJson;
  }
}
```

```text
Native Bridge 的实现要点：
1. 方法注册 —— 白名单注册可调用的 Native 方法
2. 参数校验 —— 不信任 Web 传入的参数（安全）
3. 回调机制 —— callbackId 关联请求与响应
4. 线程 —— Native 方法可能在非 UI 线程，注意切线程
```

## Deep Link 深链

Deep Link 通过 URL 唤起 App 并跳转到指定页面。

```text
深链类型：
1. Universal Link（iOS）/ App Link（Android）—— 标准 HTTPS 链接，未装 App 时退网页
2. 自定义 Scheme —— myapp://page/detail?id=1，需注册 scheme
```

```text
// 自定义 scheme 示例
myapp://product/detail?id=123
myapp://user/profile

// Universal Link（iOS）
https://example.com/app/product/123
```

```js
// Web 端唤起 App
function openApp(url) {
  const iframe = document.createElement('iframe');
  iframe.style.display = 'none';
  iframe.src = url;          // 触发 scheme 唤起
  document.body.appendChild(iframe);
  setTimeout(() => iframe.remove(), 1000);
}
```

## Cookie 与 Cache

WebView 内的 Cookie 与缓存管理是 Hybrid 的常见痛点。

```text
Cookie 同步：
1. Android WebView 默认与系统 Cookie 共享
2. iOS WKWebView 首次加载需手动注入 Cookie（JS 或 WKHTTPCookieStore）
3. 登录态同步 —— App 登录后把 token 同步给 WebView
```

```js
// iOS：首次加载前注入 Cookie
const script = `document.cookie = 'token=xxx; path=/';`;
webView.evaluateJavaScript(script, nil);
```

```text
缓存管理：
1. WebView 有独立的磁盘/内存缓存
2. 版本更新后需清缓存（避免旧页面）
3. 离线缓存可配合 Service Worker 或本地资源拦截
```

## Offline 与 Hybrid App

Offline 能力和 Hybrid 架构是 WebView 的高级应用。

```text
Offline 方案：
1. 本地资源拦截 —— Native 拦截请求，返回本地打包的 HTML/JS
2. Service Worker —— Web 侧缓存（WKWebView 支持有限）
3. 预加载 —— 提前缓存核心页面

Hybrid 架构：
1. Web 负责页面与业务 UI（快速迭代）
2. Native 负责能力（相机、推送、支付）与容器（WebView）
3. 通过 JS Bridge 协作
```

## 最佳实践与踩坑记录

### 最佳实践

1. JS Bridge 统一封装，屏蔽 iOS/Android 差异
2. 桥方法白名单 + 参数校验，防注入攻击
3. 登录态用 Native 管理，Web 通过 Bridge 获取
4. 深链优先 Universal Link/App Link（可退网页）
5. 版本更新后清理 WebView 缓存

### 踩坑记录

```text
坑 1：iOS WKWebView 首屏 Cookie 丢失
结论：登录态在 WebView 内失效。
原因：WKWebView 首次加载不自动带 App 的 Cookie。
解法：首屏注入 Cookie，或 Native 侧用 WKHTTPCookieStore 同步。

坑 2：addJavascriptInterface 安全漏洞
结论：Web 页可反射调用任意 Native 方法。
原因：注入的接口暴露过多，未做白名单。
解法：方法白名单 + targetSdkVersion 17+ 加 @JavascriptInterface 注解。

坑 3：JS Bridge 回调丢失
结论：Native 异步回调后 Web 侧无响应。
原因：callbackId 关联失败或页面已刷新。
解法：统一 callbackId 管理，页面销毁时清理 pending 回调。

坑 4：深链唤起失败
结论：scheme 无法唤起 App 或跳转错误页面。
原因：scheme 未注册、被拦截、或通用链接配置错误。
解法：校验注册，测试 Universal Link 的 HTTPS 域名配置。

坑 5：WebView 缓存导致页面不更新
结论：发版后用户看到的还是旧页面。
原因：WebView 缓存了旧版本资源。
解法：版本号加缓存版本控制，必要时主动清缓存。
```
