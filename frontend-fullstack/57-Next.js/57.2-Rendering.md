## 概述

Next.js 支持从「完全静态」到「完全动态」的多种渲染模式，开发者可以按页面粒度选择。核心是把「在什么时候、在哪里渲染」决策交给开发者，用最合适的策略服务每一类内容。

```text
Next.js 渲染模式的谱系：
静态（构建时）  ←——————————————→  动态（请求时）
SSG             ISR             SSR / Streaming / RSC

选择原则：
1. 内容不变 → SSG（构建时渲染，最快最省）
2. 内容偶尔变 → ISR（静态 + 后台刷新）
3. 内容实时/个性化 → SSR（请求时渲染）
4. 大页面慢数据 → Streaming（流式，快内容先到）
5. 减少客户端 JS → RSC（服务端组件）

App Router 默认：页面静态化（无动态依赖时），
读到请求数据/动态 API 时自动降级为动态渲染。
```

## SSR

Next.js 中的 SSR（请求时渲染）指每次请求都在服务端实时渲染。在 App Router 中，组件默认异步执行，读到请求数据即触发动态渲染。

```js
// 动态渲染：读取请求上下文（cookies/headers）或强制 dynamic
import { cookies } from 'next/headers';

export const dynamic = 'force-dynamic'; // 强制每次请求都渲染

export default async function Page() {
  const token = (await cookies()).get('token')?.value;
  const user = await fetchUser(token); // 请求时拿最新数据
  return <div>欢迎，{user.name}</div>;
}
```

```text
触发动态渲染的条件（App Router）：
1. 使用 cookies() / headers() 等动态 API
2. 使用 searchParams
3. 显式设置 dynamic = 'force-dynamic'
4. fetch 未缓存（cache: 'no-store'）

反之，无动态依赖时，Next.js 会尽量静态化。
```

## SSG

Next.js 的 SSG（静态生成）在构建时渲染页面，产出静态 HTML。这是 App Router 的默认行为（页面无动态依赖时）。

```js
// 静态渲染：无动态依赖，构建时渲染
export default function About() {
  return <div>关于我们（构建时渲染，内容固定）</div>;
}
```

```js
// 配合 generateStaticParams 预渲染动态路径
export async function generateStaticParams() {
  const posts = await fetchPosts();
  return posts.map((p) => ({ slug: p.slug }));
}

export const dynamicParams = false; // 未预渲染的路径返回 404

export default async function Post({ params }) {
  const { slug } = await params;
  const post = await fetchPost(slug); // 构建时取数据
  return <article>{post.body}</article>;
}
```

## ISR

Next.js 的 ISR 通过 `revalidate` 让静态页面在后台定时刷新，兼顾静态性能与内容新鲜度。

```js
// 定时再验证：60 秒后后台重新生成
export const revalidate = 60;

export default async function Product({ params }) {
  const { id } = await params;
  const product = await fetch(`/api/products/${id}`, {
    next: { revalidate: 60 },
  }).then((r) => r.json());
  return <div>{product.name}：{product.price}</div>;
}
```

```js
// 按需再验证：数据变更时手动触发
import { revalidatePath, revalidateTag } from 'next/cache';

export async function POST(request) {
  const { secret, path } = await request.json();
  if (secret !== process.env.REVALIDATE_SECRET) {
    return Response.json({ error: 'invalid' }, { status: 401 });
  }
  revalidatePath(path);          // 按路径刷新
  revalidateTag('products');     // 按标签批量刷新
  return Response.json({ ok: true });
}
```

## Streaming

Next.js 的 Streaming（流式渲染）把页面拆成多个块，逐块发送，首屏内容先到达，慢数据用 Suspense 包裹延迟渲染。

```jsx
// 用 loading.js 实现路由级流式
// app/dashboard/loading.js
export default function Loading() {
  return <div>加载中...</div>;
}
// app/dashboard/page.js
export default async function Dashboard() {
  const data = await fetchSlowData(); // 慢数据，期间显示 loading
  return <div>{data}</div>;
}
```

```jsx
// 用 Suspense 实现组件级流式：慢组件不阻塞快组件
import { Suspense } from 'react';

export default function Page() {
  return (
    <div>
      <h1>立即渲染的标题</h1>
      <Suspense fallback={<p>评论加载中...</p>}>
        <Comments />   {/* 慢组件，数据就绪后流式补入 */}
      </Suspense>
    </div>
  );
}
```

## RSC

RSC（React Server Components，服务端组件）是 React 19/Next.js App Router 的核心：组件默认在服务端渲染并序列化发送，客户端 JS 大幅减少。

```text
RSC 的核心思想：
1. 组件默认在服务端执行，只发送「渲染结果」而非「组件代码」
2. 服务端组件可直接访问数据库、文件系统、环境变量
3. 零客户端 JS —— 服务端组件不打包进客户端 bundle
4. 客户端组件用 'use client' 显式声明

RSC 的收益：
1. 减小客户端 bundle（服务端组件代码不下发）
2. 数据就近获取（服务端直接查库，减少 API 往返）
3. 自动代码分割（客户端组件自动拆 chunk）
```

```jsx
// 服务端组件（默认）：可直接查数据库，不打包进客户端
async function getData() {
  const db = await connectDB();       // 服务端直接访问数据库
  return db.query('SELECT * FROM posts');
}

export default async function Posts() {
  const posts = await getData();
  return (
    <ul>
      {posts.map((p) => <li key={p.id}>{p.title}</li>)}
    </ul>
  );
}
```

```jsx
// 客户端组件：显式声明 'use client'
'use client';
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

```text
RSC 的边界规则：
1. 服务端组件不能使用 useState/useEffect/事件处理
2. 客户端组件不能直接导入服务端组件（可通过 children 传递）
3. 'use client' 是边界标记，其下所有导入都是客户端
4. 服务端组件可把客户端组件作为 children 传入
```

## 应用场景实战

### 场景一：新闻站分层渲染策略

```text
页面类型 → 渲染策略：
1. 首页（热点聚合）→ ISR revalidate 300，内容新鲜又静态
2. 文章详情（发布后不变）→ SSG 预渲染
3. 搜索页（实时查询）→ SSR + 请求参数
4. 评论区（慢数据）→ Streaming + Suspense
5. 用户中心（个性化）→ SSR + cookies
```

```jsx
// 文章详情（SSG）+ 评论区（Streaming）组合
export async function generateStaticParams() {
  return (await fetchPosts()).map((p) => ({ slug: p.slug }));
}

export default async function Article({ params }) {
  const { slug } = await params;
  const article = await fetchArticle(slug);
  return (
    <article>
      <h1>{article.title}</h1>
      <div>{article.body}</div>
      <Suspense fallback={<p>加载评论...</p>}>
        <Comments slug={slug} />  {/* 流式加载 */}
      </Suspense>
    </article>
  );
}
```

### 场景二：RSC 数据就近获取

```jsx
// 服务端组件直接查库，无需额外 API 层
import { db } from '@/lib/db';

export default async function UserList() {
  const users = await db.user.findMany(); // 服务端直连数据库
  return (
    <ul>
      {users.map((u) => (
        <li key={u.id}>{u.name} —— {u.email}</li>
      ))}
    </ul>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 按页面粒度选择渲染策略，不要一刀切
2. 默认让 Next.js 静态化，需要动态时再显式开启
3. 慢数据用 Suspense/loading.js 流式，别让整页等慢接口
4. 能放服务端的逻辑尽量放服务端（RSC），减小客户端 bundle
5. 客户端组件用 'use client' 显式标记，边界要清晰
6. ISR 配按需再验证，内容更新及时又省资源
7. 动态渲染页面注意缓存，避免每次请求都重复计算
8. 监控各渲染模式的占比与耗时，动态渲染单独关注 TTFB

### 踩坑记录

```text
坑 1：误以为页面静态了结果还是动态
结论：本应静态的页面每次请求都实时渲染。
原因：无意中用了 cookies()/headers() 等动态 API。
解法：排查动态依赖，去掉不必要的动态 API，或接受动态渲染。

坑 2：服务端组件用了 useState 报错
结论：报 "useState is not a function" 或边界错误。
原因：服务端组件不能使用 React Hooks。
解法：改用客户端组件（加 'use client'），或把交互部分拆出去。

坑 3：客户端组件误导入服务端组件
结论：构建报错或组件无法按预期工作。
原因：客户端组件不能直接导入服务端组件。
解法：通过 children 传递，或把该逻辑改成客户端组件。

坑 4：流式渲染导致布局跳动
结论：内容补入时页面高度突变，体验差。
原因：Suspense fallback 与真实内容高度差异大。
解法：fallback 用骨架屏占位，高度与真实内容接近。

坑 5：revalidate 不生效
结论：设了 revalidate 但内容不刷新。
原因：页面实际是动态渲染（无静态缓存），或 fetch 缓存策略冲突。
解法：确认页面是静态可缓存路径，检查 fetch 的 cache 配置。
```
