## 概述

Next.js 有四层缓存机制，层层叠加让页面「尽可能少地重复计算与重复请求」，是 Next.js 性能优势的重要来源。理解每层缓存的作用域、时机与失效方式，才能正确控制内容的新鲜度。

```text
Next.js 四层缓存：
1. Request Cache —— 请求级去重，同一次渲染内复用相同 fetch
2. Data Cache —— 跨请求缓存 fetch 结果（服务端持久化）
3. Full Route Cache —— 缓存渲染后的完整 HTML/RSC（服务端）
4. Router Cache —— 客户端内存缓存已访问路由的 RSC payload

缓存层级（从内到外）：
fetch → Request Cache → Data Cache → Full Route Cache → Router Cache → 浏览器

再验证（Revalidation）：
让过期缓存失效并重新生成，是「缓存」与「新鲜」的平衡点。
```

## Request Cache

Request Cache（请求缓存）是「单次请求内的 fetch 去重」：同一次渲染中，多个组件发起相同 URL 的 fetch，只真正请求一次。

```text
Request Cache 的特点：
1. 作用域 —— 单次请求（一次渲染过程）
2. 目的 —— 避免组件间重复请求同一接口
3. 自动 —— 无需配置，Next.js 内置（基于 React fetch 缓存）
4. 生命周期 —— 请求结束即失效

示例：
页面渲染时，Navbar 和 Sidebar 都 fetch('/api/user')，
实际只向后端发一次请求，结果共享。
```

```jsx
// 两个组件 fetch 相同 URL，请求自动去重
async function Navbar() {
  const user = await fetch('/api/user'); // 实际请求
  return <div>{user.name}</div>;
}
async function Sidebar() {
  const user = await fetch('/api/user'); // 命中请求缓存，不重复请求
  return <div>{user.avatar}</div>;
}
```

## Data Cache

Data Cache（数据缓存）跨请求、跨用户地缓存 `fetch` 的结果（服务端持久化），是「减少后端压力」的关键层。

```text
Data Cache 的特点：
1. 作用域 —— 跨请求、跨用户（服务端持久化）
2. 缓存内容 —— fetch 的响应结果
3. 生命周期 —— 默认永久，直到被 revalidate
4. 控制 —— 通过 fetch 的 cache/revalidate 选项

控制选项：
fetch(url, { cache: 'force-cache' })   —— 强制缓存（默认）
fetch(url, { cache: 'no-store' })      —— 不缓存（每次请求）
fetch(url, { next: { revalidate: 60 } }) —— 缓存 + 60 秒再验证
```

```js
// 默认缓存：结果永久缓存，除非 revalidate
const data = await fetch('https://api.example.com/data');

// 不缓存：每次请求都实时获取（动态数据）
const fresh = await fetch('https://api.example.com/live', {
  cache: 'no-store',
});

// 定时再验证：缓存 60 秒后后台刷新
const product = await fetch('https://api.example.com/product', {
  next: { revalidate: 60 },
});
```

## Full Route Cache

Full Route Cache（完整路由缓存）缓存「渲染后的完整输出」——HTML 和 RSC payload。静态渲染的页面会整页缓存，服务端直接返回缓存，不再执行组件。

```text
Full Route Cache 的特点：
1. 缓存内容 —— 渲染完成的 HTML / RSC payload
2. 作用域 —— 服务端（可持久化到磁盘/CDN）
3. 生效条件 —— 静态渲染的页面（无动态依赖）
4. 失效 —— 通过 revalidatePath/revalidateTag 或重新构建

与 Data Cache 的关系：
Data Cache 缓存「数据」，Full Route Cache 缓存「渲染结果」。
数据缓存失效后，路由缓存随之失效（重新渲染）。
```

```text
Full Route Cache 生效/失效：
生效 —— 页面是静态的（无 cookies/headers/searchParams 依赖）
失效 —— 1) 调用了 revalidatePath/revalidateTag
       2) Data Cache 失效
       3) 重新部署

动态渲染的页面不走 Full Route Cache（每次请求都渲染）。
```

## Router Cache

Router Cache（路由缓存）是「客户端内存缓存」：缓存已访问路由的 RSC payload，实现前进/后退、预取的即时响应。

```text
Router Cache 的特点：
1. 位置 —— 客户端内存（浏览器内存）
2. 缓存内容 —— 各路由段的 RSC payload
3. 生命周期 —— 会话级（刷新页面即清空）
4. 用途 —— 快速导航、后退/前进、<Link> 预取
5. 失效 —— 服务端 revalidate 后，客户端下次导航时刷新

预取（prefetch）：
<Link> 默认预取视口内的链接，提前缓存目标路由的 payload。
```

```jsx
// 客户端导航会命中 Router Cache，秒开
import Link from 'next/link';

export default function Nav() {
  return (
    <nav>
      <Link href="/about" prefetch>关于</Link>   {/* 预取 /about */}
      <Link href="/blog">博客</Link>
    </nav>
  );
}
```

## Revalidation

Revalidation（再验证）是让过期缓存失效并重新生成的过程，是控制「内容新鲜度」的核心机制。分「时间驱动」和「按需驱动」两类。

```js
// 时间驱动：revalidate 秒数到期后，下次请求触发后台再生成
export const revalidate = 60;

// fetch 级时间驱动
const data = await fetch('/api/data', { next: { revalidate: 60 } });
```

```js
// 按需驱动：数据变更时主动调用
import { revalidatePath, revalidateTag } from 'next/cache';

// 在 Server Action 或 Route Handler 中
export async function updatePost(formData) {
  await savePost(formData);
  revalidatePath('/posts/[id]');  // 刷新指定路径
  revalidateTag('posts');          // 刷新所有带 posts 标签的缓存
}
```

```text
Revalidation 的两种模式：
1. 时间驱动 —— revalidate = N 秒，到期后 stale-while-revalidate
2. 按需驱动 —— revalidatePath/Tag，数据一变就刷新

失效链条：
revalidateTag → Data Cache 失效 → Full Route Cache 失效
→ 客户端 Router Cache 下次导航时更新
```

## 应用场景实战

### 场景一：不同数据源的缓存策略组合

```js
// 页面级缓存策略：公共内容缓存，个性化内容不缓存
export const revalidate = 3600; // 页面默认 1 小时再验证

export default async function Home() {
  // 公共数据：默认缓存 + 定时再验证
  const banners = await fetch(`${API}/banners`);

  // 实时数据：不缓存
  const announcements = await fetch(`${API}/announcements`, {
    cache: 'no-store',
  });

  return (
    <div>
      <Banner data={banners} />
      <Announcement data={announcements} />
    </div>
  );
}
```

### 场景二：CMS 内容按需刷新

```js
// 发布文章后，精准刷新文章列表与详情
'use server';
import { revalidatePath, revalidateTag } from 'next/cache';

export async function publishArticle(article) {
  await db.article.create({ data: article });
  revalidateTag('articles');        // 刷新列表
  revalidatePath(`/posts/${article.slug}`); // 刷新详情页
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 公共静态数据默认走 Data Cache，减少后端压力
2. 个性化/实时数据用 cache: 'no-store'，避免缓存污染
3. 用 tag 组织缓存，按需批量 revalidate 相关页面
4. 动态渲染页面不依赖 Full Route Cache，注意 TTFB
5. Router Cache 是客户端内存，刷新页面即失效
6. revalidate 值按内容新鲜度需求设置，别一刀切
7. 数据变更后用 revalidateTag 而非全站刷新
8. 缓存策略要结合监控，避免「以为缓存了其实没有」

### 踩坑记录

```text
坑 1：改了数据页面不更新
结论：内容陈旧，迟迟不刷新。
原因：Data Cache 默认永久，未设 revalidate 也没按需刷新。
解法：设 revalidate 或数据变更后 revalidateTag/Path。

坑 2：以为缓存了其实每次都请求
结论：后端压力没降下来。
原因：页面用了 cookies()/headers() 等动态 API，变成动态渲染。
解法：去掉不必要的动态依赖，或接受动态渲染并单独优化。

坑 3：个性化数据被缓存串号
结论：A 用户看到 B 用户的数据。
原因：个性化数据用了默认 fetch 缓存，未设 no-store。
解法：用户相关数据必须 cache: 'no-store'。

坑 4：Router Cache 导致客户端看到旧内容
结论：服务端已更新，客户端导航仍是旧页面。
原因：客户端内存 Router Cache 未及时失效。
解法：调用 router.refresh() 强制刷新，或依赖 revalidate 自动失效。

坑 5：revalidatePath 参数不匹配
结论：刷新没生效，页面还是旧的。
原因：路径参数与实际路由不匹配（如 /posts/[id] vs /posts/123）。
解法：用实际动态段路径，或干脆用 revalidateTag 更稳。
```
