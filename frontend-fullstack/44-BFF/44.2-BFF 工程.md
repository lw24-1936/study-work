## 概述

BFF 工程关注「如何把 BFF 落地成可维护的服务」：语言/框架选型、对接下游的协议（REST/gRPC/GraphQL）、以及生产必需的稳定性手段（代理、限流、熔断）。前端团队用 Node.js 写 BFF，能复用 TS 类型和工程化经验。

```text
BFF 工程的技术栈组合：
1. 运行时 —— Node.js（前端团队技术栈统一）
2. 框架 —— NestJS（企业级）/ Fastify（高性能）/ Express（简单）
3. 协议 —— REST、GraphQL、gRPC 对接下游服务
4. 稳定性 —— Proxy 转发、Rate Limit 限流、Circuit Breaker 熔断
```

```text
BFF 工程的关键决策：
1. 框架选型 —— 团队规模大选 NestJS，追求性能选 Fastify
2. 协议选型 —— 下游已 REST 就 REST，内部新服务可 gRPC
3. 部署形态 —— 独立服务 or Serverless 函数
```

## Node.js

Node.js 是 BFF 的默认运行时：前端工程师无需切换语言即可编写服务端逻辑，且事件循环 + 非阻塞 I/O 非常适合 BFF 这种「I/O 密集、聚合转发」的工作负载。

```js
const http = require('http');

const server = http.createServer(async (req, res) => {
  if (req.url === '/bff/home') {
    const data = await aggregateHome();
    res.setHeader('Content-Type', 'application/json');
    res.end(JSON.stringify(data));
  } else {
    res.statusCode = 404;
    res.end('Not Found');
  }
});

server.listen(3000);
```

```text
Node.js 适合 BFF 的原因：
1. 语言统一 —— 前端团队直接上手，复用 TS 类型
2. I/O 密集 —— 聚合/转发是 BFF 主要负载，Node 天然擅长
3. 生态丰富 —— fetch、proxy 库、GraphQL、gRPC 客户端齐全
4. 启动快 —— 适合 Serverless 冷启动
```

```text
需要注意：
1. CPU 密集任务（大 JSON 解析）会阻塞事件循环
2. 单进程需用 cluster 或多实例扩展
3. 超大响应序列化可能成为瓶颈
```

## NestJS

NestJS 的分层架构非常适合大型 BFF：Module 划分领域、Provider 承载聚合逻辑、Guard/Interceptor 处理鉴权与响应包裹、Pipe 做入参校验，团队协作时结构清晰。

```ts
// bff.module.ts —— 领域模块划分
@Module({
  imports: [UserModule, OrderModule, PointModule],
  controllers: [HomeController],
})
export class BffModule {}
```

```ts
// home.service.ts —— 聚合逻辑
@Injectable()
export class HomeService {
  constructor(
    private userClient: UserClient,
    private orderClient: OrderClient,
  ) {}

  async getHome(userId: number) {
    const [user, orders, points] = await Promise.all([
      this.userClient.getUser(userId),
      this.orderClient.getOrders(userId),
      this.userClient.getPoints(userId),
    ]);
    return { name: user.name, orders, points };
  }
}
```

```ts
// home.controller.ts —— 路由 + 鉴权 + 包裹
@Controller('bff')
export class HomeController {
  constructor(private homeService: HomeService) {}

  @Get('home')
  @UseGuards(AuthGuard)
  @UseInterceptors(TransformInterceptor)
  async home(@CurrentUser() user: any) {
    return this.homeService.getHome(user.id);
  }
}
```

```text
NestJS 做 BFF 的优势：
1. DI 容器管理下游 client 的实例和配置
2. 请求生命周期（Guard → Pipe → Interceptor）天然对应 BFF 的横切关注点
3. 模块边界清晰，BFF 变复杂时仍可维护
```

## Fastify

Fastify 的高性能 + Schema 校验很适合「高吞吐、需要入参校验」的 BFF：用 response Schema 加速序列化，用 body/query Schema 自动校验，插件体系拆分下游 client。

```js
const fastify = require('fastify')({ logger: true });

fastify.get('/bff/home', {
  schema: {
    response: {
      200: {
        type: 'object',
        properties: {
          name: { type: 'string' },
          points: { type: 'integer' },
        },
      },
    },
  },
}, async (req) => {
  const user = await getUser(req.user.id);
  const points = await getPoints(req.user.id);
  return { name: user.name, points };
});

fastify.listen({ port: 3000 });
```

```text
Fastify 做 BFF 的优势：
1. 序列化加速 —— response Schema 预编译，聚合响应更快
2. 入参校验 —— body/query Schema 自动校验，非法请求直接 400
3. 插件封装 —— 下游 client 按插件注册，作用域隔离
4. 生态兼容 —— 可作 NestJS 底层引擎
```

## GraphQL

GraphQL 是 BFF 的天然搭档：前端按需声明所需字段，BFF 的 resolver 负责聚合多个数据源。它把「数据整形」从硬编码变成查询声明，适合字段需求差异大的多端场景。

```js
// GraphQL Schema 定义视图模型
const typeDefs = `
  type User {
    id: ID!
    name: String!
    orders: [Order!]!
  }
  type Order {
    id: ID!
    total: Float!
  }
  type Query {
    home: User!
  }
`;

const resolvers = {
  Query: {
    home: (_, __, ctx) => ({ id: ctx.user.id }),
  },
  User: {
    // 按需解析：前端不查 orders 就不会执行这里
    name: async (user) => (await getUser(user.id)).name,
    orders: async (user) => getOrders(user.id),
  },
};
```

```text
GraphQL 做 BFF 的优势与代价：
1. 优势 —— 字段按需加载、类型即文档、多端复用
2. 代价 —— 学习成本、N+1 问题需 DataLoader 解决、缓存复杂
3. 适用 —— 字段需求高度异构的多端场景
```

```js
// DataLoader 解决 N+1 问题
const DataLoader = require('dataloader');
const orderLoader = new DataLoader(async (userIds) => {
  const orders = await getOrdersForUsers(userIds);
  return userIds.map((id) => orders.filter((o) => o.userId === id));
});
```

## REST

REST 是 BFF 对接下游服务最常见的方式：下游提供资源化的 HTTP 接口，BFF 用 fetch/HTTP client 调用。它简单、通用、调试方便。

```js
// BFF 调用下游 REST 服务
class UserClient {
  constructor(baseUrl) {
    this.baseUrl = baseUrl;
  }
  async getUser(id) {
    const res = await fetch(`${this.baseUrl}/users/${id}`);
    if (!res.ok) throw new Error(`upstream ${res.status}`);
    return res.json();
  }
}
```

```text
REST 对接的要点：
1. 统一封装 client，集中处理超时、重试、错误
2. 下游分页接口要在 BFF 层处理翻页逻辑
3. 命名/字段以 BFF 自己的规范为准，不照搬下游
4. 用 OpenAPI 文档对齐下游契约
```

## gRPC

gRPC 是高性能的 RPC 协议，用 Protobuf 定义接口和消息，二进制传输、支持流式。当后端内部服务是 gRPC 时，BFF 通过生成的 client 直接调用，性能优于 HTTP+JSON。

```proto
// user.proto
syntax = "proto3";
package user;

service UserService {
  rpc GetUser (GetUserReq) returns (GetUserResp);
}

message GetUserReq {
  int64 id = 1;
}

message GetUserResp {
  int64 id = 1;
  string name = 2;
}
```

```js
// BFF 使用生成的 gRPC client
const grpc = require('@grpc/grpc-js');
const protoLoader = require('@grpc/proto-loader');

const def = protoLoader.loadSync('user.proto');
const proto = grpc.loadPackageDefinition(def).user;

const client = new proto.UserService('localhost:50051', grpc.credentials.createInsecure());

client.getUser({ id: 1 }, (err, resp) => {
  console.log(resp.name); // 二进制传输，比 JSON 快
});
```

```text
gRPC 的适用场景：
1. 内部服务间高频调用、追求低延迟
2. 强类型契约（Protobuf）适合跨团队协作
3. 支持双向流，适合消息推送类场景
```

## Proxy

Proxy（反向代理）是 BFF 的基础能力之一：把某些请求直接转发给下游，或转发到静态资源/CDN，BFF 自身不加工数据。常用于登录态代理、文件转发、灰度路由。

```js
// 用 http-proxy-middleware 转发
const { createProxyMiddleware } = require('http-proxy-middleware');

app.use(
  '/api/legacy',
  createProxyMiddleware({
    target: 'http://legacy-svc:8080',
    changeOrigin: true,
    onProxyReq: (proxyReq, req) => {
      proxyReq.setHeader('x-user-id', req.user.id); // 注入身份
    },
  }),
);
```

```text
Proxy 在 BFF 里的用途：
1. 遗留接口透传 —— 不重写，直接转发
2. 注入身份头 —— 转发时补充用户信息
3. 路径改写 —— 统一对外路径，映射到下游真实路径
4. 灰度/蓝绿 —— 按 header 或比例路由到不同版本
```

## Rate Limit

Rate Limit（限流）保护 BFF 和下游服务不被突发流量打垮。BFF 层限流常见策略有固定窗口、滑动窗口、令牌桶。

```js
// 简单令牌桶限流
class RateLimiter {
  constructor(limit, windowMs) {
    this.limit = limit;
    this.windowMs = windowMs;
    this.buckets = new Map();
  }
  allow(key) {
    const now = Date.now();
    const b = this.buckets.get(key) ?? { count: 0, reset: now + this.windowMs };
    if (now > b.reset) {
      b.count = 0;
      b.reset = now + this.windowMs;
    }
    b.count++;
    this.buckets.set(key, b);
    return b.count <= this.limit;
  }
}

const limiter = new RateLimiter(100, 60_000);
app.use((req, res, next) => {
  if (!limiter.allow(req.ip)) {
    return res.status(429).json({ message: 'too many requests' });
  }
  next();
});
```

```text
限流维度：
1. IP 维度 —— 防单点滥用
2. 用户维度 —— 防单账号刷接口
3. 接口维度 —— 高开销接口单独限流
4. 返回 429 + Retry-After 头，前端配合退避重试
```

## Circuit Breaker

Circuit Breaker（熔断器）在下游服务故障时快速失败，避免 BFF 被慢下游拖垮（线程/连接耗尽）。状态机：关闭 → 打开（熔断）→ 半开（试探恢复）。

```js
class CircuitBreaker {
  constructor(fn, { threshold = 5, timeout = 10_000 } = {}) {
    this.fn = fn;
    this.threshold = threshold;
    this.timeout = timeout;
    this.state = 'CLOSED';
    this.failures = 0;
    this.openedAt = 0;
  }
  async call(...args) {
    if (this.state === 'OPEN') {
      if (Date.now() - this.openedAt < this.timeout) {
        throw new Error('circuit open');
      }
      this.state = 'HALF_OPEN'; // 到时间试探恢复
    }
    try {
      const result = await this.fn(...args);
      this.reset();
      return result;
    } catch (err) {
      this.failures++;
      if (this.failures >= this.threshold) {
        this.state = 'OPEN';
        this.openedAt = Date.now();
      }
      throw err;
    }
  }
  reset() {
    this.state = 'CLOSED';
    this.failures = 0;
  }
}
```

```text
熔断三态：
1. CLOSED（关闭）—— 正常放行，累计失败
2. OPEN（打开）—— 失败超阈值，直接快速失败不调下游
3. HALF_OPEN（半开）—— 冷却后放一个请求试探，成功则关闭
```

```js
const breaker = new CircuitBreaker(getUser);

app.get('/bff/user/:id', async (req, res) => {
  try {
    const user = await breaker.call(req.params.id);
    res.json(user);
  } catch (err) {
    res.status(503).json({ message: 'service unavailable' });
  }
});
```

## 应用场景实战

### 场景一：带限流 + 熔断 + 聚合的 BFF 服务

```js
const express = require('express');
const app = express();

const limiter = new RateLimiter(100, 60_000);
const userBreaker = new CircuitBreaker(getUser, { threshold: 3, timeout: 5_000 });

app.use('/bff', auth, (req, res, next) => {
  if (!limiter.allow(req.ip)) return res.status(429).json({ message: 'too many requests' });
  next();
});

app.get('/bff/home', async (req, res) => {
  try {
    const [user, orders] = await Promise.all([
      userBreaker.call(req.user.id),
      getOrders(req.user.id),
    ]);
    res.json({ name: user.name, orders });
  } catch (err) {
    res.status(503).json({ message: 'service unavailable', fallback: true });
  }
});
```

### 场景二：NestJS + gRPC 下游 + GraphQL 出口

// 下游 gRPC client 封装成 Provider

export class UserGrpcClient {

## 最佳实践与踩坑记录

### 最佳实践

1. 下游 client 统一封装：超时、重试、错误码归一化
2. 无依赖的聚合用 Promise.all 并发，单点故障用 allSettled 降级
3. 所有下游调用都设超时，配合熔断器防止级联故障
4. 限流返回 429 + Retry-After，前端做指数退避
5. 敏感身份信息只从服务端会话取，转发时按需注入身份头
6. 观测三件套：结构化日志、指标、链路追踪（trace id 透传）

### 踩坑记录

```text
坑 1：下游调用没设超时导致请求堆积
结论：下游慢时 BFF 连接池耗尽，整体雪崩。
原因：fetch/axios 默认无超时或超时过长。
解法：每个下游调用设合理超时 + 熔断快速失败。

坑 2：熔断器状态没重置
结论：下游恢复后 BFF 仍拒绝请求。
原因：熔断打开后没有半开试探机制。
解法：冷却期后进入 HALF_OPEN，放行试探请求。

坑 3：gRPC client 没复用连接
结论：每个请求新建连接，性能反而差。
原因：gRPC 连接昂贵，应长连接复用。
解法：client 单例化，进程内复用。

坑 4：代理时丢失客户端真实 IP
结论：下游日志看到的全是 BFF 的 IP。
原因：转发时没设 X-Forwarded-For。
解法：proxy 设置 xfwd: true 透传真实 IP。

坑 5：限流键用全局单一 key
结论：一个用户刷接口把所有人限流了。
原因：限流 key 没区分用户/IP。
解法：按用户 ID 或 IP 维度做 key。
```
