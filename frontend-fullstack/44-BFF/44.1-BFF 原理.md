## 概述

BFF（Backend For Frontend，服务于前端的后端）是位于客户端与后端微服务之间的中间层。它为每个前端形态（Web、App、小程序）提供定制化的接口：聚合多个服务、裁剪字段、统一鉴权，避免前端直接面对细粒度微服务的复杂调用。

```text
BFF 要解决的问题：
1. 前端要调 N 个服务拼数据 —— 多往返、慢、难维护
2. 各端需求不同 —— Web 要全量、App 要精简，接口不通用
3. 鉴权逻辑分散 —— 每个前端都要处理 token、权限
4. 数据形状不匹配 —— 服务端字段名/结构不符合前端视图
```

```text
BFF 的定位：
1. 面向「视图」而非「资源」—— 一个页面一个接口
2. 属于前端团队 —— 由前端工程师维护
3. 不是通用 API 网关 —— 不做跨团队统一路由
4. 每个客户端形态可有一个专属 BFF
```

## Backend For Frontend

BFF 的核心思想是「为前端量身定制的后端」：每个前端客户端拥有自己的后端层，返回恰好满足其渲染需求的数据，而不是通用 REST 资源。

```text
BFF 与 API 网关的区别：
1. API 网关 —— 统一入口，做路由、限流、鉴权，面向服务
2. BFF —— 面向单个前端形态，做聚合、裁剪、编排，面向视图
3. 网关关注「流量」，BFF 关注「数据形状」
```

```text
BFF 带来的收益：
1. 减少前端发起的请求次数（聚合）
2. 隐藏后端微服务边界（前端不感知服务拆分）
3. 按端定制响应，减少传输量（移动端瘦身）
4. 鉴权/脱敏收敛到一处（安全）
```

```js
// 没有 BFF：前端要拼 3 个接口
const [user, orders, points] = await Promise.all([
  fetch('/users/1'),
  fetch('/orders?userId=1'),
  fetch('/points/1'),
]);
const viewModel = { name: user.name, orders, points: points.balance };
```

```js
// 有 BFF：一个接口拿到视图模型
const viewModel = await fetch('/bff/home').then((r) => r.json());
// { name: 'Alice', orders: [...], points: 100 }
```

## API Aggregation

API Aggregation（接口聚合）是 BFF 最核心的能力：把一个页面的多次后端调用合并成一次 BFF 调用，BFF 内部并发请求多个下游服务再合并返回。

```js
// BFF 侧聚合实现（Node.js）
async function homeHandler(req, res) {
  const userId = req.user.id;
  // 并发请求多个下游服务
  const [user, orders, points] = await Promise.all([
    fetch(`http://user-svc/users/${userId}`).then((r) => r.json()),
    fetch(`http://order-svc/orders?userId=${userId}`).then((r) => r.json()),
    fetch(`http://point-svc/points/${userId}`).then((r) => r.json()),
  ]);
  res.json({ name: user.name, orders, points: points.balance });
}
```

```text
聚合的实现要点：
1. 下游并发请求用 Promise.all，降低总耗时
2. 某个服务失败时可降级返回默认值，不全盘 500
3. 对慢服务设超时，避免拖垮整个聚合
4. 可加缓存，减少重复聚合计算
```

```js
// 容错聚合：单个服务失败不拖垮整体
const results = await Promise.allSettled([
  getUser(userId),
  getOrders(userId),
  getPoints(userId),
]);
const user = results[0].status === 'fulfilled' ? results[0].value : null;
const orders = results[1].status === 'fulfilled' ? results[1].value : [];
```

## Data Shaping

Data Shaping（数据裁剪/整形）指 BFF 根据前端需求对下游返回的数据做字段裁剪、重命名、类型转换、结构重组，输出恰好符合视图模型的数据。

```js
// 下游返回的「胖」数据
const rawUser = {
  id: 1,
  firstName: 'Alice',
  lastName: 'Smith',
  email: 'alice@example.com',
  passwordHash: 'xxx', // 绝不能发给前端
  address: { city: 'NY', zip: '10001', geo: { lat: 40, lng: -74 } },
  createdAt: '2024-01-01T00:00:00Z',
};

// BFF 整形后的视图模型
function shapeUser(raw) {
  return {
    id: raw.id,
    name: `${raw.firstName} ${raw.lastName}`,
    city: raw.address?.city,
  };
}
```

```text
Data Shaping 的几种操作：
1. 字段裁剪 —— 去掉前端用不到的字段，减小体积
2. 字段重命名 —— firstName/lastName → name
3. 类型转换 —— 时间戳、金额分转元、枚举转文案
4. 结构重组 —— 扁平化嵌套、合并/拆分对象
5. 脱敏 —— 剥离密码哈希、手机号打码等敏感字段
```

## Permission

BFF 是权限校验的收口点：在返回数据给前端之前，先校验当前用户是否有权访问该数据或执行该操作，避免把「不该看到的字段」下发。

```js
async function orderDetailHandler(req, res) {
  const order = await getOrder(req.params.id);
  // 越权校验：只能看自己的订单，或管理员
  if (order.userId !== req.user.id && req.user.role !== 'admin') {
    return res.status(403).json({ message: 'forbidden' });
  }
  res.json(order);
}
```

```text
BFF 层的权限职责：
1. 数据级权限 —— 该用户能否访问这条记录
2. 字段级权限 —— 敏感字段是否对当前角色可见
3. 操作级权限 —— 能否执行某个动作
```

```js
// 字段级权限：按角色裁剪字段
const adminFields = ['email', 'phone', 'status'];
const publicFields = ['id', 'name'];

function filterByRole(user, targetRole) {
  const fields = targetRole === 'admin' ? adminFields : publicFields;
  return Object.fromEntries(fields.map((k) => [k, user[k]]));
}
```

## Authentication

Authentication（认证）在 BFF 层统一处理：前端把凭据交给 BFF，BFF 完成登录、签发会话，并在后续请求中校验身份，下游服务只信任 BFF 转发的身份。

```js
// BFF 登录：校验凭据 → 签 token → 下发
async function loginHandler(req, res) {
  const { email, password } = req.body;
  const user = await verifyCredentials(email, password);
  if (!user) return res.status(401).json({ message: 'invalid credentials' });

  const token = jwt.sign({ id: user.id, role: user.role }, SECRET, { expiresIn: '7d' });
  res.json({ token, user: shapeUser(user) });
}
```

```text
BFF 层的认证模式：
1. 会话 Cookie —— BFF 签 HttpOnly Cookie，后续请求自动携带
2. JWT —— BFF 签发 token，前端存下并回传
3. 第三方 OAuth —— BFF 作为回调方，换取用户信息后自签会话
```

```js
// 认证中间件：校验 token 并挂到 req.user
function auth(req, res, next) {
  const token = req.get('Authorization')?.replace('Bearer ', '');
  try {
    req.user = jwt.verify(token, SECRET);
    next();
  } catch {
    res.status(401).json({ message: 'unauthorized' });
  }
}
```

## Caching

BFF 层做缓存能显著减少对下游服务的压力：把聚合/整形后的结果按 key 缓存，命中后直接返回，避免重复的聚合计算和下游调用。

```js
const cache = new Map(); // 简单内存缓存

async function homeHandler(req, res) {
  const key = `home:${req.user.id}`;
  const hit = cache.get(key);
  if (hit && Date.now() - hit.t < 60_000) {
    return res.json(hit.data); // 命中缓存
  }

  const data = await aggregateHome(req.user.id);
  cache.set(key, { data, t: Date.now() });
  res.json(data);
}
```

```text
BFF 缓存的策略：
1. 缓存键 —— 用户维度（userId）、参数维度（query）
2. TTL —— 设置合理过期时间，避免脏数据
3. 缓存位置 —— 内存、Redis（多实例共享）
4. 失效 —— 写操作后主动失效相关 key
5. 只缓存幂等读接口，不缓存写接口
```

```text
BFF 缓存 vs CDN/浏览器缓存：
1. CDN/浏览器 —— 缓存静态资源、公共内容
2. BFF —— 缓存个性化聚合结果（带用户维度）
```

## 应用场景实战

### 场景一：电商首页的 BFF 聚合

```js
// 首页需要：用户信息、推荐商品、购物车角标、优惠券
async function homeHandler(req, res) {
  const userId = req.user.id;
  const [user, recommend, cart, coupons] = await Promise.allSettled([
    getUser(userId),
    getRecommend(userId),
    getCartCount(userId),
    getCoupons(userId),
  ]);

  res.json({
    user: shapeUser(ok(user)),
    recommend: ok(recommend) ?? [],
    cartCount: ok(cart) ?? 0,
    coupons: ok(coupons) ?? [],
  });
}

function ok(result) {
  return result.status === 'fulfilled' ? result.value : null;
}
```

### 场景二：移动端与 Web 端差异化接口

```js
// Web BFF 返回全量字段
app.get('/web/orders', auth, async (req, res) => {
  const orders = await getOrders(req.user.id);
  res.json(orders.map((o) => ({ ...o, tracking: getTracking(o) })));
});

// App BFF 只返回列表需要的精简字段（省流量）
app.get('/app/orders', auth, async (req, res) => {
  const orders = await getOrders(req.user.id);
  res.json(orders.map((o) => ({ id: o.id, total: o.total, status: o.status })));
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一个页面一个 BFF 接口，让前端「一次请求」拿到视图模型
2. 下游调用用 Promise.allSettled 并发 + 容错，单个失败可降级
3. 敏感字段（密码哈希、隐私）在 BFF 层脱敏，绝不下发
4. 权限校验收敛在 BFF，不信任前端传来的 userId
5. 聚合结果做缓存，写操作后主动失效
6. BFF 保持「薄」，复杂业务逻辑仍下沉到下游服务

### 踩坑记录

```text
坑 1：BFF 变成「另一个单体」
结论：各团队都在一个 BFF 里堆代码，耦合严重。
原因：没按客户端形态/业务域拆分 BFF。
解法：按端拆分 BFF，或 BFF 内部按领域模块化。

坑 2：聚合接口串行调用导致更慢
结论：BFF 比前端直接调还慢。
原因：下游请求用 await 串行等待，没并发。
解法：无依赖的请求用 Promise.all 并发。

坑 3：把权限校验交给前端
结论：越权漏洞，用户可篡改 userId 查别人数据。
原因：BFF 直接信任前端传参。
解法：用户身份只从会话/token 取，不从前端参数取。

坑 4：缓存了不该缓存的写接口
结论：数据错乱、重复提交。
原因：把 POST 等写操作结果缓存了。
解法：只缓存幂等 GET，写操作后主动失效。

坑 5：BFF 层塞满业务逻辑
结论：BFF 越来越重，与下游服务职责重叠。
原因：把核心业务逻辑写进 BFF。
解法：BFF 只做编排/聚合/裁剪，业务下沉下游。
```
