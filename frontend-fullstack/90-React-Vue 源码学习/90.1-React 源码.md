## 概述

React 源码的核心是「从 JSX 到 DOM」的完整链路：JSX 先被编译成 createElement 调用，运行时生成 Fiber 树，Reconciler 在 Scheduler 的调度下增量地 diff 新旧 Fiber，最后把变更提交到 DOM。理解这条链路是读懂 React 源码的钥匙。

```text
React 源码的四大模块：
1. JSX Transform —— 编译期把 JSX 转成 React.createElement
2. Fiber —— 运行时的工作单元，可中断的虚拟节点
3. Reconciler —— 协调器，diff 新旧 Fiber 生成变更
4. Scheduler —— 调度器，按优先级分配时间片
```

```js
// JSX 编译前后对照
// 编译前
const el = <div className="box">hello</div>;

// 编译后（React 17+ 自动引入 jsx）
import { jsx as _jsx } from 'react/jsx-runtime';
const el = _jsx('div', { className: 'box', children: 'hello' });
```

## JSX Transform

JSX 不是浏览器能直接解析的语法，由 Babel/TS/SWC 编译成 React.createElement（或 react/jsx-runtime 的 jsx）调用。

```js
// @babel/preset-react 的两种模式
// classic：转成 React.createElement
React.createElement('div', { className: 'box' }, 'hello');

// automatic（React 17+ 默认）：转成 jsx-runtime 的 jsx
import { jsx as _jsx } from 'react/jsx-runtime';
_jsx('div', { className: 'box', children: 'hello' });
```

```text
JSX Transform 的要点：
1. 标签名 → 字符串或组件引用
2. 属性 → 第二个参数对象
3. 子元素 → 第三个参数起，或 props.children
4. automatic 模式无需手动 import React
```

## Fiber

Fiber 是 React 16 引入的架构核心：每个组件/元素对应一个 Fiber 节点，组成可中断的 Fiber 树。它把「不可中断的递归」改成「可中断的链表遍历」。

```js
// Fiber 节点核心字段（简化）
function createFiber(type, props, key) {
  return {
    type,          // 组件类型：字符串/函数/类
    key,           // 复用标识
    props,         // 属性
    stateNode,     // 对应 DOM 或组件实例
    // 树结构（三指针）
    return: null,  // 父 Fiber
    child: null,   // 第一个子 Fiber
    sibling: null, // 下一个兄弟 Fiber
    // 工作相关
    alternate: null,       // 双缓冲：current 与 workInProgress 互相指向
    flags: 0,              // 副作用标记（Placement/Update/Deletion）
    memoizedState: null,   // Hooks 链表 / 类组件 state
    updateQueue: null,     // 更新队列
  };
}
```

```text
Fiber 树 vs 普通树：
1. 链表结构 —— child/sibling/return 三指针，可中断遍历
2. 双缓冲 —— current 与 alternate 两棵树，diff 时新旧互相对应
3. 副作用标记 —— flags 记录 Placement/Update/Deletion，提交阶段统一处理
4. 优先级 —— lanes 标记调度优先级
```

## Reconciler

Reconciler（协调器）是 React 的 diff 引擎，在 Scheduler 的调度下遍历 Fiber 树，对比新旧节点生成变更列表。

```js
// 协调流程（简化示意）
function workLoop(deadline) {
  while (nextUnitOfWork && !shouldYield(deadline)) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  // 时间片用完，把控制权交回浏览器
  if (nextUnitOfWork) {
    requestIdleCallback(workLoop);
  } else {
    commitRoot();
  }
}

function performUnitOfWork(fiber) {
  beginWork(fiber);           // 向下：diff 当前 Fiber，生成子 Fiber
  if (fiber.child) return fiber.child;
  // 向上：完成当前 Fiber，找兄弟或父级
  let cur = fiber;
  while (cur) {
    completeWork(cur);        // 向上：创建 DOM，收集副作用
    if (cur.sibling) return cur.sibling;
    cur = cur.return;
  }
  return null;
}
```

```text
Reconciler 的 diff 三原则：
1. 同层级比较 —— 只 diff 同一层级，不跨层移动
2. type 不同则重建 —— 类型变了整个子树重建
3. key 复用 —— key 相同的节点优先复用（列表渲染）
```

## Scheduler

Scheduler 是 React 的调度模块，把「高优先级更新（用户输入）」插队到「低优先级更新（数据渲染）」之前，并用时间片（time slice）让出主线程。

```js
// 优先级与时间片（简化）
const priorities = {
  ImmediatePriority: 1,      // 同步，如用户输入
  UserBlockingPriority: 2,   // 用户交互
  NormalPriority: 3,         // 普通更新
  LowPriority: 4,            // 低优先级
  IdlePriority: 5,           // 空闲时
};

// 时间片：默认 5ms，超过就让出主线程
function shouldYield() {
  return performance.now() - startTime > 5;
}
```

```text
Scheduler 的机制：
1. 优先级队列 —— 高优先级任务先执行
2. 时间片 —— 每片 5ms，到点让出主线程
3. MessageChannel —— 用宏任务实现任务调度
4. 可中断 —— 时间片用完暂停，下个空闲周期继续
```

## Hooks

Hooks 的状态存在 Fiber 节点的 memoizedState 字段上，以链表串联。useState 等 Hook 按调用顺序挂到链表中。

```js
// Hook 数据结构（简化）
function createHook() {
  return {
    memoizedState: null,   // 当前状态值
    queue: null,           // 更新队列
    next: null,            // 下一个 Hook
  };
}

// useState 的简化实现
let currentFiber = null;
let hookIndex = 0;

function useState(initial) {
  const fiber = currentFiber;
  const hook = fiber.memoizedState || (fiber.memoizedState = createHook());
  // 首次渲染初始化
  if (hook.memoizedState === null) hook.memoizedState = initial;
  const setState = (action) => {
    hook.queue.push(action);
    scheduleUpdate(fiber);  // 触发重新渲染
  };
  return [hook.memoizedState, setState];
}
```

```text
Hooks 的规则来源：
1. 按顺序存储 —— Hook 是链表，按调用顺序匹配
2. 为什么不能条件调用 —— 顺序变了，Hook 就错位了
3. 为什么不能在循环里调用 —— 每次渲染的调用次数必须一致
```

## Context

Context 在 Fiber 树上的传播依赖「依赖收集」：Provider 修改 value 时，只更新真正消费了这个 Context 的组件，避免无关组件重渲染。

```js
// Context 传播原理（简化）
// Provider 的 value 变化 → 沿 Fiber 树向下查找消费该 Context 的节点
function propagateContextChange(fiber, context, changedBits) {
  let node = fiber;
  while (node) {
    if (node.dependencies && node.dependencies.includes(context)) {
      // 该节点消费了此 Context，标记更新
      scheduleUpdate(node);
      break;
    }
    node = node.child;
  }
}
```

```text
Context 的优化点：
1. 依赖收集 —— 只有 useContext 的组件才订阅变化
2. value 引用稳定 —— value 每次渲染新建对象会导致全量更新
3. 拆分 Context —— 高频变化与低频变化拆开，避免互相拖累
```

## Suspense

Suspense 用「抛出 Promise」实现：组件渲染时抛出一个 Promise，React 捕获后暂停渲染，Promise resolve 后重试。这是并发特性的基石。

```js
// Suspense 的底层原理：抛 Promise
function useSuspense(readFn) {
  const resource = readFn();
  if (resource.status === 'pending') {
    // 关键：抛出 Promise，让最近的 Suspense 边界捕获
    throw resource.promise;
  }
  if (resource.status === 'error') throw resource.error;
  return resource.value;
}

// 组件包一层 Suspense 边界
// <Suspense fallback={<Spinner />}><AsyncComponent /></Suspense>
```

```text
Suspense 的能力：
1. 代码分割 —— lazy 组件加载时显示 fallback
2. 数据获取 —— 配合 use 或 Relay 等，数据就绪前显示 fallback
3. 流式 SSR —— 服务端边渲染边输出，客户端渐进式 hydrate
4. 并发渲染 —— 配合 Transition 做可中断的切换
```

## Server Components

Server Components（RSC）让组件在服务端渲染，只把序列化后的「RSC Payload」发给客户端，客户端组件与 Server Component 混合渲染。

```text
RSC 的核心机制：
1. 服务端渲染 —— Server Component 只在服务端执行，不打包进客户端 bundle
2. RSC Payload —— 序列化的虚拟 DOM + 组件引用，客户端据此重建
3. 零客户端 JS —— Server Component 本身不产生客户端 JS
4. 混合树 —— 客户端组件（'use client'）与 Server Component 交错嵌套
```

```js
// Server Component（默认，服务端执行，可直连数据库）
async function ProductList() {
  const products = await db.query('SELECT * FROM products');
  return <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}

// Client Component（需交互，加 'use client'）
'use client';
import { useState } from 'react';
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
```

## 应用场景实战

### 场景一：读懂一次 setState 的更新流程

```text
setState 触发后的完整链路：
1. 创建 Update 对象，加入 fiber.updateQueue
2. 标记 fiber 的 lane，调度更新
3. Scheduler 按优先级调度 workLoop
4. Reconciler 从根开始 reconcile，diff 出变更
5. commit 阶段把变更应用到 DOM
6. 同步执行 useEffect / useLayoutEffect
```

### 场景二：手写一个迷你 Reconciler

```js
// 最小可运行：把 JSX 渲染成真实 DOM，并 diff 更新
function createElement(type, props, ...children) {
  return { type, props: { ...props, children } };
}

function render(vnode, container) {
  const dom = vnode.type === 'TEXT'
    ? document.createTextNode('')
    : document.createElement(vnode.type);
  Object.keys(vnode.props || {}).forEach(k => {
    if (k !== 'children') dom[k] = vnode.props[k];
  });
  (vnode.props.children || []).forEach(c => render(c, dom));
  container.appendChild(dom);
}

render(
  createElement('div', { id: 'app' }, createElement('span', null, 'hi')),
  document.getElementById('root')
);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 列表渲染始终给稳定的 key，别用 index 当 key
2. Context value 用 useMemo 包住，避免引用变化引发全量更新
3. 高频更新与低频更新拆成不同 Context/Store
4. 重计算用 useMemo、稳定引用用 useCallback，但别过度记忆化
5. 大列表用虚拟滚动，减少 Fiber 节点数量
6. 读源码先抓「数据流」再抠「细节」，别一头扎进位运算

### 踩坑记录

```text
坑 1：用 index 当 key 导致状态错乱
结论：列表增删/排序时，输入框内容串位。
原因：index 不稳定的 key 让 React 复用错了节点。
解法：用数据本身稳定的唯一 id 当 key。

坑 2：Context value 每次渲染都新建对象
结论：Provider 下所有消费组件每次都重渲染。
原因：value 引用变了，依赖收集判定为「变化」。
解法：value 用 useMemo 包裹，引用稳定后才跳过更新。

坑 3：滥用 useMemo 反而更慢
结论：简单计算加 useMemo，性能没有提升反而多了开销。
原因：useMemo 本身有比较成本，简单值不值得缓存。
解法：只在重计算、引用稳定性敏感处用 useMemo。

坑 4：Server Component 里用了浏览器 API
结论：RSC 构建报错或运行时报 window is not defined。
原因：Server Component 在服务端执行，没有浏览器环境。
解法：浏览器 API 放 Client Component（加 'use client'）。

坑 5：Suspense 没有设置 fallback
结论：异步组件加载时页面空白或报错。
原因：没有 Suspense 边界捕获 Promise，React 找不到暂停位置。
解法：异步组件外层包 Suspense，fallback 给加载态。
```
