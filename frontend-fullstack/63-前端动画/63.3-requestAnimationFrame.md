## 概述

requestAnimationFrame（rAF）是浏览器提供的「按帧执行动画」的 API。它告诉浏览器：你希望在下一次重绘之前执行某个回调。浏览器会在最合适的时机（通常与屏幕刷新率对齐）调用回调，从而保证动画与显示同步，避免掉帧。

```text
rAF 核心特性：
1. 与刷新率同步 —— 回调在每次重绘前执行
2. 自动节流 —— 页面不可见时暂停回调
3. 批量执行 —— 同一帧内的多个 rAF 一起执行
4. 高精度时间戳 —— 回调参数为 DOMHighResTimeStamp
```

```js
// 基本用法
function animate(timestamp) {
  // timestamp：回调触发时刻的高精度时间
  update(timestamp);
  requestAnimationFrame(animate);   // 注册下一帧
}
requestAnimationFrame(animate);     // 启动循环
```

```js
// 取消动画帧
const id = requestAnimationFrame(animate);
cancelAnimationFrame(id);           // 停止
```

## Frame

Frame（帧）是动画的基本单位。浏览器每秒渲染多帧静态画面，利用视觉暂留让人眼感知为连续运动。rAF 的每次回调就对应「准备渲染一帧」。

```text
一帧的渲染流程（渲染管线）：
1. Input —— 处理输入事件（点击、滚动）
2. JavaScript —— 执行 JS 回调（含 rAF）
3. Style —— 计算样式（Recalculate Style）
4. Layout —— 计算布局/回流
5. Paint —— 绘制/光栅化
6. Composite —— 合成图层输出到屏幕
```

```js
// rAF 回调在这一帧的「渲染之前」执行
requestAnimationFrame(() => {
  // 修改 DOM/样式，将影响本帧的渲染
  element.style.transform = `translateX(${x}px)`;
});
```

```text
为什么用 rAF 而非 setTimeout：
1. setTimeout 固定间隔，与屏幕刷新率不同步 → 可能一帧内执行多次或漏帧
2. rAF 由浏览器调度，精确对齐每帧，动画更平滑
3. 后台标签页 rAF 自动暂停，节省 CPU 与电量
```

## 60 FPS

60 FPS 表示每秒渲染 60 帧，是主流屏幕（60Hz）的刷新率。达到 60 FPS 意味着动画流畅、无肉眼可见卡顿。

```text
60 FPS 的含义：
1. 每帧约 1000ms / 60 ≈ 16.7ms
2. 所有渲染工作需在 16.7ms 内完成
3. 超过 16.7ms → 掉帧 → 出现卡顿

高刷新率屏幕（120Hz / 90Hz）：
rAF 会自动匹配更高频率，每帧预算更紧（约 8.3ms）。
```

```js
// 基于时间戳计算帧率（FPS）
let lastTime = performance.now();
let frames = 0;
let fps = 0;

function loop(now) {
  frames++;
  if (now - lastTime >= 1000) {
    fps = frames;                 // 过去一秒渲染的帧数
    frames = 0;
    lastTime = now;
    console.log(`当前 FPS：${fps}`);
  }
  requestAnimationFrame(loop);
}
requestAnimationFrame(loop);
```

## Frame Budget

Frame Budget（帧预算）指浏览器在一帧内可用于渲染的时间额度。60Hz 下约 16.7ms，其中 JS 执行、样式计算、布局、绘制都要挤在这个预算内。

```text
帧预算分配（60Hz，约 16.7ms）：
1. JavaScript 执行 —— 通常建议 < 5ms
2. Style / Layout / Paint —— 剩余时间
3. 浏览器内部开销

原则：任何单项任务都不应吞掉整个帧预算。
```

```js
// 长任务拆分：把大循环拆到多帧执行
const items = new Array(10000).fill(0);
function processChunk(start) {
  const end = Math.min(start + 100, items.length);   // 每帧处理 100 个
  for (let i = start; i < end; i++) {
    items[i] = i * 2;
  }
  if (end < items.length) {
    requestAnimationFrame(() => processChunk(end));  // 下一帧继续
  }
}
requestAnimationFrame(() => processChunk(0));
```

```text
帧预算超支的常见原因：
1. 同步长任务（大循环、复杂计算）
2. 强制同步布局（读写交错触发回流）
3. 大量 DOM 操作
4. 过大的图片解码、字体加载
```

## Jank

Jank（卡顿）指动画掉帧、画面不流畅的现象。当某帧耗时超过帧预算时，浏览器跳过该帧或延迟渲染，人眼就会察觉到跳动。

```text
Jank 的表现：
1. 动画顿挫、不连贯
2. 滚动卡顿
3. 页面响应迟滞

检测手段：
1. DevTools Performance 面板 —— 查看帧时间与长任务
2. rAF 采样 FPS —— 代码实时监测
3. PerformanceObserver —— 监听 longtask
```

```js
// 用 PerformanceObserver 监听长任务（Long Task API）
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // duration > 50ms 的任务即为长任务
    console.log(`长任务：${entry.duration.toFixed(1)}ms`);
  }
});
observer.observe({ entryTypes: ['longtask'] });
```

```text
减少 Jank 的策略：
1. 动画只用 transform/opacity（走合成，不触发回流）
2. 长任务拆分到多帧
3. 避免读写交错导致的强制回流
4. 大量节点用虚拟滚动/懒渲染
5. 复杂动画交给 CSS 或 Web Animations，别用 JS 逐帧改布局属性
```

```js
// 强制同步布局的反例：读写交错
// 坏写法：每轮循环都读 offsetWidth（触发回流）
for (let i = 0; i < 100; i++) {
  el.style.width = `${i}px`;
  const w = el.offsetWidth;    // 读取 → 强制回流
}

// 好写法：先全读，再全写
const width = el.offsetWidth;  // 先读一次
for (let i = 0; i < 100; i++) {
  el.style.width = `${width + i}px`;  // 只写
}
```

## 应用场景实战

### 场景一：平滑滚动到指定位置

```js
function smoothScrollTo(targetY, duration = 500) {
  const startY = window.scrollY;
  const diff = targetY - startY;
  const start = performance.now();

  function step(now) {
    const progress = Math.min((now - start) / duration, 1);
    const eased = progress < 0.5
      ? 2 * progress * progress
      : 1 - Math.pow(-2 * progress + 2, 2) / 2;   // easeInOutQuad
    window.scrollTo(0, startY + diff * eased);
    if (progress < 1) requestAnimationFrame(step);
  }
  requestAnimationFrame(step);
}
```

### 场景二：倒计时动画（按时间而非帧数驱动）

```js
function countdown(seconds, onTick) {
  const total = seconds * 1000;
  const start = performance.now();

  function tick(now) {
    const remain = Math.max(0, total - (now - start));
    onTick(Math.ceil(remain / 1000));
    if (remain > 0) requestAnimationFrame(tick);
  }
  requestAnimationFrame(tick);
}
// 用时间戳驱动，切后台也不漂移
```

## 最佳实践与踩坑记录

### 最佳实践

1. 动画进度用时间戳计算，别用「回调次数」（帧率不稳定会漂移）
2. 每帧只做必要工作，超预算就拆分到多帧
3. 组件卸载/页面隐藏时 cancelAnimationFrame
4. 纯 CSS 能做的动画优先用 CSS，rAF 用于 JS 驱动的动画
5. 用 rAF 节流 scroll/resize 等高频事件
6. 页面不可见时 rAF 自动暂停，长时间任务需考虑这个行为

### 踩坑记录

```text
坑 1：按回调次数计算进度导致速度不稳
结论：动画在掉帧时变慢、在 120Hz 屏上变快。
原因：帧率不恒定，回调次数不能代表时间。
解法：用时间戳差计算进度。

坑 2：忘记 cancelAnimationFrame
结论：页面切走后动画仍在后台消耗资源。
原因：rAF 在不可见时暂停，但回到前台会继续，且循环未终止。
解法：停止动画时 cancelAnimationFrame(id)。

坑 3：rAF 里做重活导致整帧卡死
结论：回调内大循环让本帧超过 16.7ms。
原因：rAF 回调阻塞了渲染管线。
解法：长任务拆分到多帧，或移入 Web Worker。

坑 4：在 rAF 中读写交错触发强制回流
结论：动画帧率骤降。
原因：读 offsetWidth 等强制同步布局，打断渲染。
解法：先读后写，或只操作 transform/opacity。

坑 5：多段动画各自创建独立 rAF 循环
结论：N 个动画 N 个循环，调度混乱、开销大。
原因：缺少统一调度。
解法：合并为单个 rAF 循环统一更新所有动画。
```
