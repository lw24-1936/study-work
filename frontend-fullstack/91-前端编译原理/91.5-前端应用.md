## 概述

前端工具链的「编译」无处不在：Babel/TypeScript 处理 JS，SWC/esbuild 用原生速度重写了同样的事，Vue/JSX 编译器把模板与语法糖转成渲染代码，CSS 也有自己的解析器。它们都遵循「Lexer → Parser → Transform → Codegen」的同一条流水线，只是输入输出不同。

```text
前端编译器的统一流水线：
1. Lexer   —— 源码 → Token
2. Parser  —— Token → AST
3. Transform —— AST → AST（降级、优化、转换）
4. Codegen —— AST → 目标代码

各工具差异只在「解析什么语言」和「生成什么代码」。
```

```js
// 同一段代码在不同工具下的使命
const a = <Comp x={1} />;   // JSX 语法糖
// Babel/SWC:  转成 React.createElement 或 jsx 调用
// TypeScript: 类型检查后擦除类型注解
// Vue:        template 编译成 h() 渲染函数
```

## Babel

Babel 是 JS 的「转译器」，用插件体系把新语法降级成旧语法，让旧浏览器也能运行。它的核心是 @babel/parser（解析）、@babel/traverse（遍历）、@babel/generator（生成），插件就是在这条链上挂 transform。

```js
// Babel 的工作方式
// 输入（新语法）：const fn = (x) => x?.y ?? 0;
// 输出（旧语法）：const fn = function (x) {
//   return x === null || x === void 0 ? void 0 : x.y !== null
//     && x.y !== void 0 ? x.y : 0;
// };

// 配置文件 babel.config.js
module.exports = {
  presets: [
    ['@babel/preset-env', { targets: '> 0.25%, not dead' }],
    ['@babel/preset-react', { runtime: 'automatic' }],
  ],
  plugins: ['@babel/plugin-transform-optional-chaining'],
};
```

```text
Babel 的要点：
1. 插件化 —— 每个语法特性是一个插件，preset 是插件的集合
2. preset-env —— 按 targets 自动决定需要哪些降级插件
3. 中间层 —— traverse 提供 path 抽象，插件据此增删改节点
4. 速度 —— 纯 JS 实现，大项目里是构建瓶颈之一
```

## TypeScript

TypeScript 编译器（tsc）在转译 JS 之外还做「类型检查」。它先解析源码并做完整的类型系统推导与检查，再把类型注解擦除，生成干净的 JS。类型检查是独立于转译的一步。

```ts
// TS 源码
function greet(name: string): string {
  return `Hello, ${name}`;
}
greet(42); // 类型错误：number 不能赋给 string

// 转译后（类型擦除，类型错误不影响生成代码）
function greet(name) {
  return `Hello, ${name}`;
}
```

```text
TypeScript 的要点：
1. 类型检查与转译分离 —— 报错也能产出 JS（除非 noEmitOnError）
2. 类型擦除 —— 类型注解在生成阶段被丢弃，不影响运行时
3. 类型空间 vs 值空间 —— interface/type 只存在于编译期
4. tsc 慢 —— 可交给 SWC/esbuild 只做转译，类型检查单独跑 tsc --noEmit
```

## SWC

SWC 是用 Rust 写的 JS/TS 编译器，API 与 Babel 高度兼容，但速度快一个数量级（原生 vs JS）。它既能做降级转译，也能做压缩（minify），是 Next.js 等框架的默认编译器。

```js
// SWC 配置（.swcrc）
{
  "jsc": {
    "parser": { "syntax": "typescript", "tsx": true },
    "target": "es2018",
    "transform": { "react": { "runtime": "automatic" } }
  },
  "minify": true
}
```

```text
SWC 的要点：
1. Rust 实现 —— 原生性能，比 Babel 快 20 倍量级
2. Babel 兼容 —— 大多数 Babel 插件有对应的 SWC 等价物
3. 一体化 —— parser + transform + codegen + minify 一个二进制搞定
4. 局限 —— 插件生态不如 Babel 成熟，复杂自定义 transform 仍靠 Babel
```

## esbuild

esbuild 是用 Go 写的极速打包器兼转译器，主打「毫秒级」构建。它的核心优势是并行 + 零依赖的原生实现，常被用作 dev 环境的热更新引擎，或作为 Vite 的底层依赖。

```js
// esbuild 的 API 调用
require('esbuild').build({
  entryPoints: ['src/index.tsx'],
  bundle: true,
  minify: true,
  target: ['es2018'],
  outfile: 'dist/bundle.js',
}).then(() => console.log('done'));
```

```text
esbuild 的要点：
1. Go 实现 —— 并行处理多个文件，速度极快
2. 职责 —— 转译 + 打包 + 压缩，一条龙
3. 不产 AST 中间层 —— 直接生成，故自定义 transform 能力弱
4. 生态位置 —— Vite 的 dev 构建、很多工具的底层引擎
```

## Vue Compiler

Vue Compiler 把模板（template）编译成渲染函数：先 parse 模板为 AST，transform 阶段做静态分析（静态提升、patchFlag、block tree），最后 codegen 生成返回 VNode 的 JS 代码。这是 Vue 3 相比 Vue 2「编译时优化」的核心。

```vue
<!-- 模板 -->
<template>
  <div class="box" @click="onClick">{{ msg }}</div>
</template>

<!-- 编译后的渲染函数（简化） -->
<script>
import { h } from 'vue';
export function render(ctx) {
  return h('div', {
    class: 'box',
    onClick: ctx.onClick,
  }, ctx.msg); // 静态 class 提升，动态部分打标
}
</script>
```

```text
Vue Compiler 的要点：
1. 静态提升 —— 不变的节点提到 render 外，避免每次重建
2. patchFlag —— 标记动态节点与动态属性，diff 时精准定位
3. block tree —— 把动态节点组织成扁平数组，跳过静态子树
4. 目标 —— 让运行时 diff 尽可能少做无用功
```

## JSX Compiler

JSX Compiler 把 JSX 语法转成 JS 函数调用。React 17+ 用 automatic runtime 转成 react/jsx-runtime 的 jsx，无需手动 import React；老版本则转成 React.createElement。

```jsx
// 编译前
const el = <div className="box">{items.map(i => <span key={i}>{i}</span>)}</div>;

// 编译后（automatic runtime）
import { jsx as _jsx } from 'react/jsx-runtime';
const el = _jsx('div', {
  className: 'box',
  children: items.map(i => _jsx('span', { key: i, children: i })),
});
```

```text
JSX Compiler 的要点：
1. 语法糖 —— JSX 不是标准 JS，必须编译后才能运行
2. 标签名分派 —— 小写是字符串，大写是组件引用
3. 属性映射 —— class → className、for → htmlFor 等
4. automatic runtime —— 产物更小，无需 import React
```

## CSS Parser

CSS Parser 把样式表解析成 AST（如 PostCSS 的 postcss AST），让工具能做属性排序、自动加前缀、变量替换、Tree Shaking 等操作。PostCSS 是这一领域事实上的标准，插件生态丰富。

```css
/* 输入 */
.box { color: red; display: flex; }

/* PostCSS 解析后的 AST（简化） */
{
  type: 'root',
  nodes: [{
    type: 'rule', selector: '.box',
    nodes: [
      { type: 'decl', prop: 'color', value: 'red' },
      { type: 'decl', prop: 'display', value: 'flex' },
    ],
  }],
}
```

```text
CSS Parser 的要点：
1. PostCSS —— 用 JS 解析 CSS，输出可遍历的 AST
2. 插件 —— autoprefixer（加前缀）、cssnano（压缩）、stylelint（检查）
3. Tailwind —— 同样基于 PostCSS，扫描类名生成对应样式
4. 局限 —— CSS 的解析边界（自定义属性、嵌套）需插件配合
```

## 进阶：SWC / esbuild 为什么快

```text
速度来源：
1. 原生语言 —— SWC 用 Rust、esbuild 用 Go，编译成机器码，
   没有 JS 引擎的解释 / JIT 预热开销，也没有 GC 停顿。
2. 并行 —— esbuild 把多个文件分配到多核并行处理；SWC 也利用 Rust 的零成本抽象与并行能力。
3. esbuild 不建完整 AST —— 转译时直接从语法树流式生成代码，省掉 AST 中间层的内存分配。
4. 内存分配策略 —— 用 arena 分配器一次性分配、批量释放，避免频繁 malloc / free。
5. 代价 —— esbuild 因此无法做复杂自定义 transform，插件能力弱；
   SWC 用 Rust 写插件（编译成 WASM 或 native），生态仍不如 Babel。
```

```text
选型：Babel / SWC / esbuild
1. 复杂自定义 transform、需要大量社区插件 —— Babel。
2. 需要快、且能接受写 Rust 插件 —— SWC。
3. 只想极速转译 / 打包、不做自定义 AST 变换 —— esbuild。
4. 常见组合 —— 开发与产物用 SWC / esbuild 转译，类型检查单独 tsc --noEmit。
```

```text
isolatedModules 的坑（TS 交给 SWC / esbuild 转译时）：
1. const enum —— 单文件转译时编译器看不到别的文件里的枚举值，
   会被直接擦成裸引用导致运行时报错，需换成普通对象或字符串字面量 union。
2. 类型重导出 —— re-export 一个 type 必须写成 export type { X }，
   否则转译器无法判断是类型还是值，产物里会多出运行时导入。
3. namespace / 全局声明 —— 依赖跨文件类型合并的写法在 isolatedModules 下失效。
4. 结论 —— 让 tsc --noEmit 检查，但编译目标若走 SWC / esbuild，
   代码要满足 isolatedModules 约束。
```

## 应用场景实战

### 场景一：搭一条完整的 TS 构建链

```js
// 用 esbuild 转译 + tsc 只做类型检查，兼顾速度与安全
// package.json scripts：
// "typecheck": "tsc --noEmit"
// "build": "esbuild src/index.tsx --bundle --minify --outfile=dist/bundle.js"

// 或者用 SWC 转译（Vite/Next 内部即此思路）
// swc src/index.ts -o dist/index.js
// 类型检查单独跑 tsc --noEmit，CI 里并行走
```

### 场景二：给 Vue 模板加一个自定义编译优化

```text
目标：统计模板里的动态节点数量，用于性能预算。

做法（走 Vue 编译器的 transform 钩子）：
1. 拿到模板编译的 AST（@vue/compiler-dom 的 parse 产物）
2. 遍历 AST，数出带插值/指令/v-model 的动态节点
3. 超过阈值（如 50 个）时构建报警，提示拆分组件
4. 该统计在构建期完成，不影响运行时性能
```

## 最佳实践与踩坑记录

### 最佳实践

1. 转译与类型检查分离：esbuild/SWC 转译 + tsc --noEmit 检查，各取所长
2. 用 preset-env + browserslist 精确控制降级目标，避免过度降级
3. 复杂自定义 transform 用 Babel 插件，简单场景交给 SWC/esbuild
4. 大模板拆小组件，配合 Vue/React 编译器的静态优化
5. CSS 处理统一走 PostCSS 插件链，别在构建里散落各种临时脚本

### 踩坑记录

```text
坑 1：TypeScript 报错但构建仍成功
结论：CI 里 tsc 报错，但 esbuild 转译照常产出，类型错误进了生产。
原因：esbuild/SWC 只做类型擦除，不做类型检查。
解法：构建流程里显式加 tsc --noEmit 作为一道门禁。

坑 2：Babel 转了但 preset-env 没配 targets
结论：按最激进方式降级，产物又大又慢。
原因：没配 targets，preset-env 用了默认的宽范围。
解法：配 browserslist 明确支持的浏览器范围。

坑 3：Vue 模板里写复杂表达式
结论：动态节点变多，编译期优化（静态提升/block tree）失效。
原因：表达式太复杂，编译器无法静态分析。
解法：把复杂逻辑抽成 computed 或方法，模板保持简单。

坑 4：JSX 里 class 写成 className 报错
结论：用 class 属性编译后成了非法 JS。
原因：JSX 的 class 要写成 className，for 写成 htmlFor。
解法：遵守 JSX 属性映射规则，或用 eslint 插件提示。

坑 5：CSS 插件顺序错乱
结论：autoprefixer 加了前缀，但 cssnano 又把它清掉了。
原因：插件执行顺序反了，压缩跑在了加前缀之前。
解法：PostCSS 插件按「处理 → 加前缀 → 压缩」顺序排列。

坑 6：const enum 在 esbuild / SWC 转译下运行时报错
结论：构建通过，但运行时报 xxx is not defined。
原因：isolatedModules 单文件转译看不到枚举值，const enum 被擦成裸引用。
解法：避免 const enum，改用普通对象或字符串字面量 union；类型重导出显式写 export type。
```
