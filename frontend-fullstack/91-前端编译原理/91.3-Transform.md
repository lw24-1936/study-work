## 概述

Transform 是编译流水线里承上启下的阶段：Parser 已经产出 AST，Transform 负责在这棵树上做「改写」与「优化」，为后续的 Codegen 准备一棵更合适的目标 AST。它不改源码语义，只改中间表示的结构与形态。

```text
Transform 在编译流程中的位置：
1. Parser → AST → Transform → 新的 AST → Codegen → 目标代码
2. Transform 的输入输出都是 AST，是「树到树」的转换
3. 典型用途：语法降级、静态分析、打标记、删除无用节点
```

```js
// Transform 的最小示例：把所有 const 改成 var
function transform(ast) {
  return {
    type: ast.type,
    ...(ast.type === 'VariableDeclaration'
      ? { kind: 'var' }          // const/let → var
      : {}),
    ...(ast.body ? { body: ast.body.map(transform) } : {}),
    ...(ast.left ? { left: transform(ast.left) } : {}),
    ...(ast.right ? { right: transform(ast.right) } : {}),
  };
}
```

## AST Transform

AST Transform 是「遍历 + 改写」的组合：用访问者模式（Visitor）遍历整棵树，在进入/离开某个节点时执行回调，返回新节点或原地修改，从而实现对 AST 的结构化改写。Babel 的 @babel/traverse 就是这个思想的完整实现。

```js
// 访问者模式（简化）
function traverse(node, visitors) {
  const visitor = visitors[node.type];
  visitor?.enter?.(node);              // 进入节点
  for (const key in node) {            // 遍历子节点
    const child = node[key];
    if (Array.isArray(child)) child.forEach(c => traverse(c, visitors));
    else if (child && typeof child.type === 'string') traverse(child, visitors);
  }
  visitor?.exit?.(node);               // 离开节点
}

// 使用：把所有标识符 name 从 a 改成 b
traverse(ast, {
  Identifier: {
    enter(node) { if (node.name === 'a') node.name = 'b'; },
  },
});
```

```text
AST Transform 的要点：
1. 访问者模式 —— 每个节点类型配一个 visitor，代码按类型组织
2. enter/exit —— 进入时与离开时各回调一次，满足「先改父还是先改子」的不同需求
3. path —— Babel 里用 path 包装节点，记录父子关系，支持替换/删除/插入
4. 不可变优先 —— 返回新节点比原地改更安全，Babel 推荐返回新节点
```

## Optimization

Optimization 是 Transform 的重要目标：在编译期做静态分析，把运行时才能做的判断提前到编译期，产出更小、更快的代码。常见手段包括常量折叠、死代码消除、静态提升、打动态标记等。

```js
// 常量折叠：把 1 + 2 * 3 直接算成 7
function foldConstants(node) {
  if (node.type === 'BinaryExpression') {
    node.left = foldConstants(node.left);
    node.right = foldConstants(node.right);
    if (node.left.type === 'Literal' && node.right.type === 'Literal') {
      const a = node.left.value, b = node.right.value;
      const value = { '+': a + b, '-': a - b, '*': a * b, '/': a / b }[node.operator];
      return { type: 'Literal', value }; // 编译期算好，运行时零开销
    }
  }
  return node;
}
```

```text
Optimization 的常见手段：
1. 常量折叠 —— 编译期算好常量表达式，消除运行时计算
2. 死代码消除 —— 删除永远走不到的分支、未使用的变量
3. 静态提升 —— 把不变的内容提到循环/组件外，避免重复计算
4. 内联 —— 把小函数展开，减少调用开销
5. 打标记 —— 标出「动态」节点，让后续阶段只处理会变的部分
```

## 进阶：Babel 插件写法与 Scope 管理

```js
// path API 速查：插件里最常用的几个操作
export default function ({ types: t }) {
  return {
    visitor: {
      VariableDeclaration(path) {
        const uid = path.scope.generateUidIdentifier('temp'); // 生成不冲突的名字
        path.insertBefore(t.variableDeclaration('const', [t.variableDeclarator(uid)]));
        path.skip();   // 跳过当前子树的后续遍历，提升性能
      },
    },
  };
}
```

```text
path 的核心 API：
1. replaceWith / replaceWithMultiple —— 替换为单节点 / 多节点
2. insertBefore / insertAfter —— 前后插入兄弟节点
3. remove —— 删除（内部延迟到 exit 后统一执行，避免遍历错乱）
4. skip / stop —— 跳过子树 / 终止整个遍历（性能优化）
```

```text
scope 与 binding（避免变量冲突的关键）：
1. 引入新变量永远用 path.scope.generateUidIdentifier(name)，
   它会基于当前作用域已存在的绑定生成一个绝不冲突的名字（如 _temp、_temp2）。
2. 判断引用关系用 scope.getBinding(name)，能拿到「定义在哪、被谁引用」。
3. 需要改名用 scope.rename(old, new)，它会同步更新所有引用点；
   手写字符串替换必然漏掉作用域遮蔽的场景。
4. 只处理本作用域的定义、跳过外部同名变量，先判断 binding.scope === path.scope。
```

```text
其他要点：
1. t.cloneNode(node, deep) —— 同一节点不能挂到两处（AST 是树不是 DAG），
   复用节点前必须 clone，否则后续遍历 / 生成会重复处理。
2. 不可变 vs 就地 —— Babel 对外推荐「返回新节点」，内部其实就地修改并用 path 记录变更，
   path 抽象把「就地」的复杂度藏起来了，插件作者不必关心。
3. 遍历顺序 —— 插件默认按「进入父 → 递归子 → 离开父」执行，
   enter 里改结构要谨慎，结构替换统一放 exit 更安全。
```

## 应用场景实战

### 场景一：写一个 Babel 插件

```js
// 一个 Babel 插件：把 console.log 在 production 下删除
module.exports = function ({ types: t }) {
  return {
    name: 'remove-console',
    visitor: {
      CallExpression(path) {
        if (
          t.isMemberExpression(path.node.callee) &&
          t.isIdentifier(path.node.callee.object, { name: 'console' })
        ) {
          path.remove(); // 删除整个 console.xxx() 调用
        }
      },
    },
  };
};

// 用法（babel.config.js）：
// { plugins: [['./remove-console']] }
```

### 场景二：用 transform 做模板静态分析

```js
// 遍历模板 AST，把纯静态的节点标记出来（供跳过 diff）
function markStatic(node) {
  if (!node.children) { node.static = true; return; }
  node.static = node.children.every(markStatic);
  return node.static;
}
// 结果：纯静态子树会被打上 static = true，
// 运行时渲染器看到这个标记可直接复用，跳过 diff。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用访问者模式组织代码，一个类型一个 visitor，避免巨型 if-else
2. 优先返回新节点而非原地修改，减少副作用、便于调试
3. 变换前先做静态分析，把能编译期算的别留到运行时
4. 给每个 transform 写「输入 AST → 输出 AST」的单元测试，用快照比对
5. 多个 transform 注意顺序与幂等性，重复运行不应产生不同结果

### 踩坑记录

```text
坑 1：原地修改导致遍历错乱
结论：边遍历边删除/插入节点，漏节点或重复处理。
原因：遍历器持有旧的子节点列表，结构变了索引就乱了。
解法：用 path.remove() 延迟删除，或收集待改项遍历后再统一处理。

坑 2：enter 里改了父节点导致子节点丢失
结论：把父节点替换后，原计划的子节点遍历全失效。
原因：enter 阶段就替换父节点，子节点引用已脱离原树。
解法：结构替换放在 exit 阶段，或替换时显式重接子节点。

坑 3：常量折叠忽略了除零
结论：1 / 0 被折叠成 Infinity，与原运行时报错行为不一致。
原因：折叠时没校验除数为零、浮点精度等边界。
解法：只折叠语义等价、无副作用的表达式，边界情况跳过。

坑 4：transform 不幂等
结论：重复运行插件，代码被改了两遍（如重复包 wrapper）。
原因：插件没做「是否已处理」的判断。
解法：加标记位或判断前置条件，保证幂等。

坑 5：删除了有副作用的节点
结论：把 console.log 删了，但里面还有有副作用的参数表达式被一起丢掉。
原因：只判断调用名，没考虑参数里的副作用。
解法：删除前检查参数是否纯函数，有副作用则只替换调用而非整体删除。

坑 6：插件引入的临时变量与用户代码冲突
结论：直接写 const _temp = ...，结果用户代码里也有 _temp，行为错乱或互相覆盖。
原因：没查作用域里已存在的绑定，硬编码了变量名。
解法：用 scope.generateUidIdentifier 生成唯一名，或 scope.rename 显式改名。
```
