## 概述

身份认证（Authentication）回答"你是谁"，是权限控制（Authorization，回答"你能干什么"）的前提。前端视角下，认证方案的差异直接决定 token 存哪、请求怎么带、刷新怎么处理。

```text
常见认证方案对比：
Session + Cookie —— 服务端存会话，浏览器自动带 Cookie，老牌方案
JWT —— 无状态令牌，前后端分离首选，自包含用户信息
OAuth 2.0 —— 授权协议，第三方登录的基础
OpenID Connect —— 基于 OAuth 2.0 的身份层，标准化用户信息
SAML —— 企业级 SSO 的 XML 协议
Passkey / WebAuthn —— 基于公钥的无密码认证
```

```text
方案选择逻辑：
1. 传统服务端渲染 → Session + Cookie
2. 前后端分离 SPA → JWT（Access Token + Refresh Token）
3. 需要第三方登录 → OAuth 2.0 / OIDC
4. 企业内部多系统 → SSO（SAML 或 OIDC）
5. 无密码、高安全 → Passkey / WebAuthn
```

## Session 与 Cookie

Session 是最经典的认证方式：用户登录后服务端生成会话记录（存内存/Redis/数据库），只把会话 ID 通过 Cookie 发给浏览器，之后每次请求浏览器自动带上 Cookie，服务端据此查会话。

```text
流程：
1. 用户提交账号密码
2. 服务端校验通过，创建 session（sessionId 关联用户信息）
3. 响应 Set-Cookie: sessionId=xxx; HttpOnly; Secure; SameSite=Lax
4. 浏览器后续请求自动携带 Cookie
5. 服务端根据 sessionId 查会话，确认身份
```

```js
// 前端几乎无感：Cookie 由浏览器自动携带
fetch('/api/profile', {
  credentials: 'include'   // 跨域时需显式声明携带 Cookie
}).then(r => r.json());
```

```text
Session 方案特点：
优点 —— 服务端可控，可随时吊销（删会话即踢下线）
缺点 —— 服务端要维护会话状态，分布式下需共享存储，扩展性差
安全要点 —— sessionId 必须 HttpOnly + Secure + SameSite，防 XSS 窃取和 CSRF
```

## JWT

JWT（JSON Web Token）是无状态令牌，把用户信息编码进 token 本身，服务端不存会话，靠签名验证真伪。

```text
JWT 结构（三段 base64url，点号分隔）：
header.payload.signature

header —— 声明签名算法，如 { "alg": "HS256", "typ": "JWT" }
payload —— 声明（claims），如用户 ID、过期时间 exp、签发者 iss
signature —— 用密钥对前两段签名，防篡改
```

```text
// 解码后的 payload 示例
{
  "sub": "10086",            // 用户标识
  "name": "Alice",
  "iat": 1755043200,         // 签发时间
  "exp": 1755129600          // 过期时间
}
```

```js
// 前端通常把 JWT 放在 Authorization 头
fetch('/api/profile', {
  headers: { Authorization: `Bearer ${accessToken}` }
});
```

```text
JWT 方案特点：
优点 —— 无状态，天然适合分布式和微服务
缺点 —— 签出后 token 在有效期内仍有效（吊销难），需配合短过期 + Refresh Token
安全要点 —— 不能存敏感信息（payload 只 base64 编码，可解码）；密钥不能泄露
```

JWT 不解决"存哪"的问题。存 localStorage 有 XSS 窃取风险，存 HttpOnly Cookie 又回到 CSRF 的防护需求，两种方案各有取舍，后面会结合 Refresh Token 展开。

## OAuth 2.0

OAuth 2.0 是授权协议，解决"让第三方应用在用户授权下访问其资源，而无需交出密码"。前端最常见的是"用 GitHub/微信登录"。

```text
OAuth 2.0 核心角色：
Resource Owner —— 用户（资源拥有者）
Client —— 第三方应用
Authorization Server —— 授权服务器（GitHub / 微信）
Resource Server —— 资源服务器（提供用户数据）

核心产物：
Access Token —— 访问令牌，短期，用于访问资源
Refresh Token —— 刷新令牌，长期，用于换取新 Access Token
```

```text
四种授权模式：
Authorization Code —— 最安全，适合有后端的应用（前端 OAuth 的标准选择）
Implicit —— 旧式纯前端方案，token 直接暴露在 URL，已不推荐
Client Credentials —— 机器对机器，无用户参与
Device Authorization —— 输入受限设备（电视、IoT），扫码授权
```

```text
Authorization Code 流程（前端 + 后端）：
1. 前端跳转授权页：/authorize?client_id=xxx&redirect_uri=xxx&response_type=code&state=yyy
2. 用户授权后，授权服务器回调 redirect_uri 并带上 code
3. 后端用 code + client_secret 换 token（code 换 token 必须走后端，secret 不能进前端）
4. 后端拿 token 后建立自己的会话，前端后续走自己的认证
```

OAuth 2.0 只解决"授权"，不解决"认证"——它不告诉应用"用户是谁"，只是发了个能访问资源的 token。要知道用户身份，需要 OpenID Connect。

## OpenID Connect

OpenID Connect（OIDC）是建立在 OAuth 2.0 之上的身份层，标准化了"用户信息"的获取方式，让 OAuth 真正能用于登录。

```text
OIDC 在 OAuth 2.0 基础上新增：
ID Token —— 用户身份的 JWT，包含 sub（用户唯一标识）等声明
UserInfo 端点 —— 用 Access Token 换取用户详细信息的标准接口
标准化的 scope —— openid、profile、email 等
```

```text
// ID Token payload 示例（JWT 格式）
{
  "iss": "https://accounts.google.com",   // 签发者
  "sub": "123456789",                     // 用户唯一标识
  "aud": "my-client-id",                  // 目标应用
  "exp": 1755129600,
  "email": "alice@example.com",
  "name": "Alice"
}
```

```text
OAuth 2.0 与 OIDC 的关系：
OAuth 2.0 —— 发 token，管授权
OIDC —— 加 ID Token，管身份
一句话：OIDC = OAuth 2.0 + 身份层，是"用第三方账号登录"的标准实现
```

```text
前端使用 OIDC 的要点：
1. 校验 ID Token 的签名、iss、aud、exp（防止伪造和重放）
2. 用 code 换 token 的流程放在后端，前端不接触 client_secret
3. 第三方登录后，用 sub 作为本地用户体系的关联键
```

## PKCE

PKCE（Proof Key for Code Exchange，发音 "pixy"）是 Authorization Code 模式的增强，为"没有 client_secret 的公共客户端"（纯前端 SPA、移动 App）防授权码拦截。

```text
PKCE 解决的问题：
纯前端应用无法安全保存 client_secret（代码公开在浏览器），
Authorization Code 模式下 code 一旦被拦截就可能被换成 token。
PKCE 用"一次性密钥"绑定授权请求和换 token 请求，拦截者拿到 code 也没用。

流程：
1. 前端生成随机字符串 code_verifier，并算 code_challenge（SHA256 后 base64）
2. 授权请求带上 code_challenge 和 code_challenge_method=S256
3. 换 token 时带上原始 code_verifier
4. 授权服务器校验 challenge 与 verifier 是否匹配，匹配才发 token
```

```js
// 生成 PKCE 参数（前端）
function generatePKCE() {
  const verifier = crypto.randomBytes(32).toString('base64url');
  const challenge = crypto.createHash('sha256')
    .update(verifier).digest('base64url');
  return { codeVerifier: verifier, codeChallenge: challenge };
}

// 授权请求
// /authorize?...&code_challenge=<challenge>&code_challenge_method=S256
// 换 token 请求
// /token  body: { code, code_verifier: verifier }
```

```text
PKCE 现状：
原本为公共客户端设计，现在推荐所有客户端（包括有 secret 的）都启用，
成本低、收益高，是 OAuth 2.1 草案的默认要求。
```

## SSO 与 SAML

SSO（Single Sign-On，单点登录）让用户登录一次就能访问多个相互信任的系统。SAML 是企业级 SSO 的老牌标准协议。

```text
SSO 的核心思想：
1. 独立的身份提供方（IdP）统一认证
2. 各业务系统（SP）信任 IdP 的认证结果
3. 用户一次登录，多系统免登录

常见实现：
1. 共享 Cookie 域（同域多系统，如 .example.com 下的 A/B 系统）
2. CAS —— 集中认证服务协议
3. SAML —— 企业级 XML 协议（Okta、ADFS）
4. OIDC —— 现代互联网应用的 SSO 事实标准
```

```text
SAML 流程（简化）：
1. 用户访问 SP（业务系统）
2. SP 重定向到 IdP（身份提供方）的 SSO 登录页
3. 用户在 IdP 认证，IdP 生成 SAML Assertion（XML 断言，含用户身份）
4. 断言经浏览器回传到 SP（POST Binding）
5. SP 验签断言，建立本地会话
```

```xml
<!-- SAML Assertion 结构示意 -->
<saml:Assertion>
  <saml:Subject>
    <saml:NameID>alice@example.com</saml:NameID>
  </saml:Subject>
  <saml:AttributeStatement>
    <saml:Attribute Name="email">alice@example.com</saml:Attribute>
    <saml:Attribute Name="role">admin</saml:Attribute>
  </saml:AttributeStatement>
</saml:Assertion>
```

```text
SAML vs OIDC：
SAML —— 企业级（ADFS、Okta）、XML、复杂、老牌
OIDC —— 互联网应用、JSON、简单、现代
新项目做 SSO 优先 OIDC，接入已有企业 IdP 时按对方支持的协议来
```

## Passkey 与 WebAuthn

Passkey 是基于 WebAuthn 标准的无密码认证：用设备上的生物识别/PIN 解锁私钥完成签名，公钥存在服务端，私钥永不出设备。

```text
WebAuthn 是浏览器 API，Passkey 是其上的产品形态：
1. 注册：前端调用 navigator.credentials.create() 生成密钥对
   公钥 + 凭据信息传服务端存储，私钥留在设备安全区
2. 登录：前端调用 navigator.credentials.get() 用私钥签名挑战
   服务端用存储的公钥验签，通过即认证成功
```

```js
// 注册（创建凭据）
async function register() {
  const options = await fetch('/api/webauthn/register-options').then(r => r.json());
  const cred = await navigator.credentials.create({ publicKey: options });
  await fetch('/api/webauthn/register', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(cred)
  });
}
```

```js
// 登录（断言）
async function login() {
  const options = await fetch('/api/webauthn/login-options').then(r => r.json());
  const assertion = await navigator.credentials.get({ publicKey: options });
  await fetch('/api/webauthn/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(assertion)
  });
}
```

```text
Passkey 的优势：
1. 无密码 —— 私钥不出设备，钓鱼和撞库攻击失效
2. 体验好 —— 指纹/面容一键登录，不用记密码
3. 防钓鱼 —— 凭据绑定 origin，伪站无法触发签名

落地要点：
1. 需 HTTPS（localhost 除外）和安全上下文
2. 作为登录方式的补充或升级，密码仍作降级方案
3. 支持设备漫游（云同步 Passkey）时注意账户恢复流程
```

## 应用场景实战

### 场景一：SPA 的 Access Token + Refresh Token 方案

```js
// 登录成功后拿到 accessToken（短期）+ refreshToken（长期）
// accessToken 存内存，refreshToken 存 HttpOnly Cookie（防 XSS）
async function request(url, options = {}) {
  let token = memoryStore.accessToken;
  if (token) options.headers = { ...options.headers, Authorization: `Bearer ${token}` };

  let res = await fetch(url, options);

  if (res.status === 401) {
    // access token 过期，用 refresh token 换新
    const refreshed = await fetch('/api/auth/refresh', { credentials: 'include' });
    if (refreshed.ok) {
      const { accessToken } = await refreshed.json();
      memoryStore.accessToken = accessToken;
      return request(url, options);  // 重试一次
    }
    // 刷新失败，跳登录
    location.href = '/login';
  }
  return res;
}
```

### 场景二：接入 Passkey 实现一键登录

```js
// 检测设备支持，优先走 Passkey
async function quickLogin() {
  if (!window.PublicKeyCredential) {
    return fallbackPasswordLogin();
  }
  try {
    const options = await fetch('/api/webauthn/login-options').then(r => r.json());
    const assertion = await navigator.credentials.get({ publicKey: options });
    const res = await fetch('/api/webauthn/login', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(assertion),
      credentials: 'include'
    });
    if (res.ok) location.href = '/dashboard';
  } catch (e) {
    // 用户取消或设备不支持，降级密码登录
    fallbackPasswordLogin();
  }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. access token 短过期（几分钟到几小时），refresh token 长过期，二者分离
2. token 存储优先 HttpOnly Cookie，比 localStorage 更能抵抗 XSS
3. 纯前端应用做 OAuth 必须用 PKCE，绝不把 client_secret 打进前端代码
4. JWT 用强签名算法（RS256/ES256），payload 不放敏感信息
5. 校验 ID Token 时必须核对 iss、aud、exp、签名，防伪造和重放
6. Passkey 作为主登录方式时保留密码/恢复码作为降级与找回通道

### 踩坑记录

```text
坑 1：refresh token 存在 localStorage
结论：XSS 攻击者能拿到 refresh token 长期冒用。
原因：localStorage 可被任意脚本读取，refresh token 长期有效放大风险。
解法：refresh token 存 HttpOnly Cookie，access token 存内存。

坑 2：JWT 无状态导致"退出登录"不彻底
结论：前端删了 token，但服务端不认，旧 token 仍可用。
原因：JWT 无状态，服务端不记录会话，无法主动失效。
解法：短过期 + 刷新，必要时用黑名单/版本号实现主动吊销。

坑 3：OAuth 用 Implicit 模式
结论：token 暴露在 URL fragment，容易被日志和第三方脚本截获。
原因：Implicit 模式无 code 交换环节，token 直接回前端。
解法：改用 Authorization Code + PKCE。

坑 4：SAML 断言回传被篡改
结论：SP 收到伪造的 SAML 断言，攻击者冒充他人登录。
原因：SP 未严格验签断言。
解法：校验断言签名、有效期、接收方 Audience 和 issuer。

坑 5：Passkey 在非 HTTPS 环境不可用
结论：本地开发或内网 HTTP 环境调用 credentials.create 失败。
原因：WebAuthn 要求安全上下文。
解法：本地用 localhost（浏览器豁免），生产必须 HTTPS。
```
