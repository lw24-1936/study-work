## 概述

CSP（Content Security Policy，内容安全策略）是一套声明式安全机制，通过响应头或 `<meta>` 标签告诉浏览器：哪些来源的资源允许加载、哪些脚本允许执行。它是防御 XSS 的兜底手段——即使攻击者注入了脚本，只要不在白名单里，浏览器就拒绝执行。

```text
CSP 的核心价值：
1. 资源白名单 —— 限定脚本、样式、图片等只能从指定源加载
2. 内联脚本限制 —— 默认禁用内联脚本和 eval，直接掐断注入点
3. 违规上报 —— 通过 report-uri/report-to 收集被拦截的违规事件
4. 兜底防御 —— 不依赖开发者"写对代码"，策略层面兜底
```

```text
// 通过响应头下发
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com

// 通过 meta 标签下发（部分指令如 frame-ancestors、report-uri 不支持 meta 形式）
<meta http-equiv="Content-Security-Policy" content="default-src 'self'">
```

CSP 的核心是"指令 + 源列表"，每个指令定义一类资源允许的来源。源列表支持关键字（`'self'`、`'none'`、`'unsafe-inline'`、`'unsafe-eval'`）、主机（`https://cdn.example.com`）、通配符（`*.example.com`）以及 nonce/hash。

## default-src

default-src 是所有"获取类"指令的兜底默认值。当某个具体指令（如 script-src、img-src）没写时，回退到 default-src。

```text
default-src 作用范围（作为默认值生效的指令）：
connect-src、font-src、frame-src、img-src、
manifest-src、media-src、object-src、script-src、
style-src、worker-src、prefetch-src

不受 default-src 影响的指令：
base-uri、form-action、frame-ancestors、
plugin-types、report-uri、sandbox、require-trusted-types-for
```

```text
// 典型用法：先收紧全局，再按需放开
Content-Security-Policy:
  default-src 'self';                    // 默认只允许同源
  img-src 'self' data: https://img.example.com;   // 图片额外允许 data 和 CDN
  script-src 'self' https://cdn.example.com       // 脚本允许同源 + CDN
```

```js
// 无 CSP 时的内联脚本，配置后会被拦截
// <script>alert(1)</script>   → 被 default-src 'self' 拦截（内联脚本默认禁止）
```

default-src 越松，整个 CSP 越容易失效。生产环境建议从 `default-src 'self'` 起步，逐项放宽具体指令，而不是把 default-src 设成 `*`。

## script-src

script-src 是 CSP 里最重要的指令，控制脚本的加载与执行来源，直接决定 XSS 的防御效果。

```text
script-src 约束的行为：
1. <script src> 加载外部脚本的来源
2. 内联 <script> 是否允许执行（默认禁止，需 'unsafe-inline' 或 nonce/hash）
3. eval / new Function / setTimeout(string) 是否允许（需 'unsafe-eval'）
```

```text
// 只允许同源脚本 + 明确白名单的 CDN
Content-Security-Policy: script-src 'self' https://cdn.example.com

// 允许内联脚本（削弱防御，谨慎使用）
Content-Security-Policy: script-src 'self' 'unsafe-inline'

// 允许 eval（动态执行，谨慎使用）
Content-Security-Policy: script-src 'self' 'unsafe-eval'
```

```html
<!-- 内联事件处理器同样受 script-src 约束 -->
<!-- <button onclick="doSomething()">点击</button>  被拦截 -->
```

script-src 是 XSS 防御的最后一环：即使攻击者通过漏洞把 `<script>` 注入页面，只要其来源或 nonce/hash 不在白名单里，浏览器就不会执行。

## style-src

style-src 控制样式资源的加载来源，包括外部 `<link rel="stylesheet">` 和内联 style。

```text
style-src 约束的行为：
1. <link rel="stylesheet"> 的 href 来源
2. 内联 <style> 块与 style 属性（默认禁止，需 'unsafe-inline'）
3. CSS 里的 @import、url() 引用的外部资源
```

```text
// 允许同源样式 + 内联样式
Content-Security-Policy: style-src 'self' 'unsafe-inline'

// 严格模式：只允许同源，内联样式也要 nonce
Content-Security-Policy: style-src 'self' 'nonce-abc123'
```

```html
<style nonce="abc123">
  .card { border-radius: 8px; }
</style>
```

样式注入也能造成危害（CSS 注入窃取数据、点击劫持配合、UI 重绘诱导点击），style-src 收紧后，这类攻击面被压缩。很多前端项目因为依赖 CSS-in-JS 动态注入 style，会保留 `'unsafe-inline'`，此时应评估是否可迁移到 nonce 方案。

## img-src、connect-src 与 frame-src

这三个指令覆盖"媒体加载、网络请求、内嵌框架"三类常见资源。

```text
img-src —— 图片来源
  控制 <img>、CSS 背景图、favicon 的加载来源
  常用放宽：data:（内联小图）、blob:（上传预览）

connect-src —— 网络请求来源
  控制 fetch / XHR / WebSocket / EventSource / sendBeacon 的目标
  前后端分离项目里，这是调用后端 API 的关键指令

frame-src —— 内嵌框架来源
  控制 <iframe> 的 src 来源
  旧项目也用 child-src，frame-src 优先级更高
```

```text
// 完整的资源类指令组合
Content-Security-Policy:
  default-src 'self';
  img-src 'self' data: blob: https://img.example.com;
  connect-src 'self' https://api.example.com wss://ws.example.com;
  frame-src 'self' https://www.youtube.com
```

```js
// 前端代码里对 connect-src 最直观的体会：fetch 到未白名单的源会被拦截
fetch('https://analytics.third-party.com/track')
  .catch(e => console.error('被 CSP connect-src 拦截', e));
```

connect-src 漏配是前后端分离项目最常见的 CSP 故障点——接口报错不一定是后端问题，先看浏览器控制台是否提示 `Refused to connect ... violates the following Content Security Policy directive`。

## nonce 与 hash

nonce 和 hash 是"白名单内联脚本"的两种方式，用来替代危险的 `'unsafe-inline'`。

```text
nonce（一次性随机数）：
1. 服务端每次响应生成一个随机 nonce，同时放入 CSP 头和 <script nonce>
2. 只有 nonce 匹配的内联脚本才执行
3. nonce 必须每次请求都不同，否则可被攻击者复用

hash（内容哈希）：
1. 对内联脚本内容做哈希（sha256/sha384/sha512）
2. CSP 头里写 'sha256-<base64哈希>'
3. 脚本内容不变哈希就不变，内容改了必须同步更新策略
```

```html
<!-- nonce 方式 -->
<!-- 响应头：Content-Security-Policy: script-src 'self' 'nonce-random123' -->
<script nonce="random123">
  console.log('这段内联脚本可以执行');
</script>
```

```text
<!-- hash 方式 -->
<!-- 内联脚本：<script>console.log('hello')</script> -->
<!-- 计算 console.log('hello') 的 sha256 后写入策略 -->
Content-Security-Policy: script-src 'self' 'sha256-xxxxxx'
```

nonce 适合服务端渲染、动态生成脚本的场景；hash 适合内容固定的内联脚本（如第三方埋点初始化片段）。两者都比 `'unsafe-inline'` 安全——`'unsafe-inline'` 会让所有内联脚本放行，等于给 XSS 开后门。

## strict-dynamic

strict-dynamic 是 CSP3 引入的关键字，配合 nonce/hash 使用，解决"白名单脚本动态创建脚本"的问题。

```text
strict-dynamic 的作用：
1. 当一个脚本被 nonce 或 hash 放行后，它动态创建的脚本自动获得信任
2. 不再需要把第三方脚本的所有域名都写进白名单
3. 出现在 script-src 中时，会忽略后面的 host 源列表（除 nonce/hash 和 'unsafe-inline'）

解决的问题：
第三方 SDK（如分析、广告脚本）会在运行时 document.createElement('script')
加载更多脚本，老式 CSP 需要把整条依赖链的域名全部列出来，维护成本极高。
```

```text
// 老式写法：需要枚举所有动态加载的域名
Content-Security-Policy: script-src 'nonce-abc' https://a.com https://b.com https://c.com

// strict-dynamic 写法：信任 nonce 放行的脚本，其子脚本自动放行
Content-Security-Policy: script-src 'nonce-abc' 'strict-dynamic'
```

```js
// 被 nonce 放行的脚本动态加载其他脚本，strict-dynamic 下自动放行
const s = document.createElement('script');
s.src = 'https://b.com/extra.js';
document.head.appendChild(s);
```

strict-dynamic 让 CSP 从"域名白名单"进化到"信任链"模型，是构建严格 CSP 的核心。但要注意：它不支持旧浏览器（IE 全系不支持），且必须配合 nonce/hash，单独写 `'strict-dynamic'` 无意义。

## report-uri 与 report-to

两个指令用于接收 CSP 违规上报，帮助发现策略误伤和真实攻击。

```text
report-uri（旧版，仍被广泛支持）：
1. 指定一个或多个 URI，浏览器 POST JSON 违规报告过去
2. 报告含 blocked-uri、violated-directive、document-uri 等字段

report-to（新标准，基于 Reporting API）：
1. 引用 Report-To 响应头里定义的端点组
2. 支持分组、采样、聚合，是 report-uri 的替代方案
3. 两者可同时写，现代浏览器优先 report-to
```

```text
// report-uri 用法
Content-Security-Policy: default-src 'self'; report-uri /csp-report

// 浏览器上报的违规报告示例
{
  "csp-report": {
    "document-uri": "https://example.com/page",
    "blocked-uri": "https://evil.com/x.js",
    "violated-directive": "script-src",
    "original-policy": "default-src 'self'",
    "disposition": "enforce"
  }
}
```

```text
// report-to 用法（配合 Report-To 头）
Report-To: { "group": "csp-endpoint", "max_age": 10886400, "endpoints": [{ "url": "https://example.com/csp-report" }] }
Content-Security-Policy: default-src 'self'; report-to csp-endpoint
```

排查 CSP 问题的最佳入口就是上报：先把策略上线为 `Content-Security-Policy-Report-Only`（只上报不拦截），观察一段时间没有误伤后再切到正式 enforce 模式。

## 应用场景实战

### 场景一：前后端分离项目的严格 CSP

```text
// 假设架构：页面在 www.example.com，静态资源在 CDN，API 在 api.example.com
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-<随机>' 'strict-dynamic' https://cdn.example.com;
  style-src 'self' 'nonce-<随机>';
  img-src 'self' data: blob: https://cdn.example.com;
  connect-src 'self' https://api.example.com;
  font-src 'self' https://cdn.example.com;
  frame-ancestors 'self';
  base-uri 'self';
  form-action 'self';
  report-to csp-endpoint
```

```html
<!-- 页面内脚本都带上服务端注入的 nonce -->
<script nonce="随机值">
  window.__CONFIG__ = { apiBase: 'https://api.example.com' };
</script>
```

### 场景二：嵌入第三方视频/广告的页面

```text
// 需要内嵌 YouTube 视频 + 第三方广告脚本
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://ad.example.com 'sha256-<广告初始化脚本哈希>';
  frame-src 'self' https://www.youtube.com https://player.vimeo.com;
  img-src 'self' data: https://ads.example.com;
  connect-src 'self' https://ad-metrics.example.com
```

```js
// 广告脚本初始化（内容固定，用 hash 白名单）
// <script>window.AdConfig = { publisherId: 'pub-123' };</script>
// 该脚本 hash 固定，写入 CSP 的 script-src 后无需 'unsafe-inline'
```

## 最佳实践与踩坑记录

### 最佳实践

1. 从 `default-src 'self'` 起步，逐项放开具体指令，不要上来就写 `*`
2. 内联脚本用 nonce 或 hash，禁止用 `'unsafe-inline'`
3. 动态加载第三方脚本用 `strict-dynamic`，配合 nonce 使用
4. 新策略先跑 `Content-Security-Policy-Report-Only` 观察误伤，再切 enforce
5. 配置 report-to 收集违规，长期监控策略有效性
6. 同时加 `frame-ancestors 'self'` 防点击劫持、`base-uri 'self'` 防 base 标签注入

### 踩坑记录

```text
坑 1：meta 标签形式不支持 report-uri
结论：用 meta 下发 CSP 时 report-uri 不生效。
原因：report-uri、frame-ancestors、sandbox 等指令只能在响应头里下发。
解法：CSP 优先用响应头下发，meta 只作为无服务端控制时的兜底。

坑 2：connect-src 漏配导致接口全部失败
结论：前端 fetch 报错，接口在 Postman 里却正常。
原因：CSP 收紧后 connect-src 没放行 API 域名。
解法：把 API 域名加入 connect-src，报错信息会明确提示被拦截的指令。

坑 3：'unsafe-inline' 与 nonce 混用
结论：写了 nonce 又写 'unsafe-inline'，nonce 被忽略。
原因：规范规定 'unsafe-inline' 存在时 nonce/hash 失效。
解法：二选一，不要同时出现。

坑 4：strict-dynamic 忽略 host 源列表
结论：script-src 里写了域名又写 strict-dynamic，域名被忽略。
原因：strict-dynamic 生效时忽略 host 源列表。
解法：用 nonce/hash 放行入口脚本，其余交给 strict-dynamic 信任链。

坑 5：hash 与脚本内容不匹配
结论：内联脚本被拦截，CSP 头里写的 hash 看似正确。
原因：脚本内容有任何字符变化（空格、换行）哈希就变。
解法：hash 必须精确匹配最终输出到浏览器的脚本内容。
```
