## 概述

安全 Header 是服务端下发的一组 HTTP 响应头，通过浏览器强制执行各类安全策略，不需要改动前端代码就能显著提升站点的安全基线。它们是纵深防御的一层——即使代码存在漏洞，浏览器层面的限制也能阻断部分攻击。

```text
安全 Header 覆盖的防御面：
1. Content-Security-Policy —— 资源加载白名单，防 XSS
2. Strict-Transport-Security —— 强制 HTTPS，防降级攻击
3. X-Content-Type-Options —— 禁止 MIME 嗅探，防脚本伪装
4. Referrer-Policy —— 控制 Referer 泄露
5. Permissions-Policy —— 禁用/限制浏览器能力（摄像头、定位等）
6. COOP/CORP/COEP —— 跨源隔离三件套
```

```text
// 常见的一组完整安全 Header（Nginx / CDN 上配置）
Content-Security-Policy: default-src 'self'
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

这些头对前端的影响直接体现在浏览器行为上：接口请求被拦截、iframe 被拒、摄像头调用失败等，排查"功能突然不可用"时优先检查是否被安全 Header 限制。

## Content-Security-Policy

CSP 已在独立文档详细展开，这里强调它在安全 Header 体系里的定位和几个易被忽略的指令。

```text
CSP 在安全 Header 中的定位：
1. 最重要的一条，直接对抗 XSS
2. 指令数量最多，配置复杂度最高，最容易误伤

几个常被忽略但很有价值的指令：
frame-ancestors —— 控制谁能用 iframe 嵌入本页（防点击劫持）
base-uri —— 限制 <base> 标签，防 base 注入改写相对路径
form-action —— 限制表单提交目标，防表单劫持
```

```text
// 补上常被忽略的三个指令
Content-Security-Policy:
  default-src 'self';
  frame-ancestors 'self';
  base-uri 'self';
  form-action 'self'
```

```text
frame-ancestors 与旧版 X-Frame-Options 的关系：
frame-ancestors 是 CSP 指令，功能更丰富（支持源列表），
现代浏览器优先用它，X-Frame-Options 作为老浏览器兜底保留。
```

## Strict-Transport-Security

HSTS（HTTP Strict Transport Security）强制浏览器在指定时间内只通过 HTTPS 访问站点，杜绝 HTTP 降级和中间人剥离攻击。

```text
HSTS 的核心行为：
1. 首次以 HTTPS 访问后，浏览器记住"以后只走 HTTPS"
2. 期限内访问 http:// 会自动 307 跳转到 https://
3. 证书错误时直接阻断，不允许用户点击"继续访问"
```

```text
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

max-age=31536000 —— 有效期限（秒），通常一年
includeSubDomains —— 子域名同样强制 HTTPS
preload —— 申请加入浏览器 HSTS Preload 名单
```

```text
注意点：
1. HSTS 只在 HTTPS 响应里下发才生效（HTTP 里下发被忽略）
2. 首次访问仍是 HTTPS 握手前的一次 HTTP 请求，preload 名单能补上这个空窗
3. 证书配置有问题时 HSTS 会导致站点完全不可访问，上生产前先确认证书有效
```

## X-Content-Type-Options

`X-Content-Type-Options: nosniff` 禁止浏览器做 MIME 类型嗅探，强制按响应头声明的 Content-Type 处理资源。

```text
MIME 嗅探的危害：
服务端误报 Content-Type（如把脚本当图片）时，
浏览器嗅探出"实际是脚本"就执行，攻击者可利用这一点上传伪装成图片的脚本。
nosniff 让浏览器严格按 Content-Type 处理，杜绝这类攻击。
```

```text
// 唯一合法取值就是 nosniff
X-Content-Type-Options: nosniff
```

```text
nosniff 对前端的影响：
1. 脚本文件必须正确返回 text/javascript 等脚本 MIME，否则不执行
2. 样式必须返回 text/css，否则不应用
3. 反过来看，它要求服务端 MIME 配置必须准确
```

## Referrer-Policy

Referrer-Policy 控制跨站请求时 Referer 请求头携带多少来源信息，防止 URL 里的敏感参数（token、路径）泄露给第三方。

```text
常用取值（从松到严）：
no-referrer —— 完全不发 Referer
strict-origin-when-cross-origin —— 跨源只发源，同源发完整 URL（现代浏览器默认，推荐）
same-origin —— 仅同源发完整 Referer，跨源不发
strict-origin —— 跨源只发源，降级到 HTTP 不发
no-referrer-when-downgrade —— HTTPS 到 HTTP 不发，其余发完整 URL（旧默认）
```

```text
// 推荐配置
Referrer-Policy: strict-origin-when-cross-origin

// 不希望泄露任何来源信息时
Referrer-Policy: no-referrer
```

```text
实际场景：
分享页 URL 带 ?token=xxx，用户点外部链接时，
若 Referrer-Policy 是 no-referrer-when-downgrade，token 会随 Referer 泄露给外站。
严格策略只发 origin，不携带路径和参数。
```

## Permissions-Policy

Permissions-Policy 允许站点声明"哪些浏览器能力可用、哪些禁用"，可限制摄像头、麦克风、定位、支付等敏感 API，也能限制 iframe 里的能力继承。

```text
Permissions-Policy 的作用：
1. 禁用本页不需要的敏感 API，缩小攻击面
2. 限制第三方 iframe 继承的能力（如禁止广告 iframe 调麦克风）
3. 取代旧版 Feature-Policy 头
```

```text
// 禁用摄像头、麦克风、定位；允许全屏和自动播放
Permissions-Policy: camera=(), microphone=(), geolocation=(self), fullscreen=(self)

// 语义：camera=() 表示任何源都禁用；geolocation=(self) 表示仅同源可用
```

```js
// 被禁用后，调用相关 API 会失败
navigator.mediaDevices.getUserMedia({ video: true })
  .catch(e => console.error('被 Permissions-Policy 禁用', e));
```

```text
语法要点：
1. 指令名对应能力（camera、microphone、geolocation、payment、fullscreen...）
2. 值是一组源：() 空表示全禁，(self) 同源，(* 或任意域名) 放行
3. 写 (self "https://example.com") 表示同源和指定域名可用
```

## Cross-Origin-Opener-Policy

COOP 控制"顶层窗口的跨源文档是否共享同一浏览上下文组"，用于隔离不同源的顶层页面，防止恶意页面通过 window.opener 或引用关系攻击目标页。

```text
COOP 取值：
unsafe-none —— 默认，不隔离，跨源页面可互相引用
same-origin —— 同源页面共享上下文，跨源页面隔离
same-origin-allow-popups —— 同源共享，弹窗类可放宽
```

```text
Cross-Origin-Opener-Policy: same-origin

防护的攻击场景：
1. window.opener 攻击 —— 恶意页通过 opener 操作被打开的目标页
2. 跨源引用导致的信息泄露（Spectre 类侧信道攻击的前置隔离）
```

```js
// 未隔离时，A 站打开的 B 站窗口可反向操作 A 站
// B 站页面里：window.opener.location = 'https://phishing.example.com'
// 设置 COOP: same-origin 后，跨源窗口的 opener 为 null
```

COOP 是跨源隔离（cross-origin isolation）的前置条件之一，配合 COEP 才能启用 SharedArrayBuffer、高精度计时等 API。

## Cross-Origin-Resource-Policy

CORP 控制"哪些源可以加载本源的资源"，与 CORS 互补——CORS 管跨源读数据，CORP 管资源本身允许被谁嵌入。

```text
CORP 取值：
same-origin —— 仅同源可加载
same-site —— 同站（同 eTLD+1）可加载
cross-origin —— 允许跨源加载（需配合 CORS 才能读内容）
```

```text
Cross-Origin-Resource-Policy: same-origin

防护目标：
防止其他站点把本方的图片、脚本、JSON 等资源直接嵌入其页面，
避免"资源被白嫖"和部分数据泄露。
```

```text
CORP 与 CORS 的区别：
CORS（Access-Control-Allow-Origin）—— 允许谁读我的数据（服务端主动开放）
CORP —— 声明资源可以被谁加载（默认收紧的自我保护）
两者常配合使用：CORP 收紧嵌入，CORS 控制读取。
```

## Cross-Origin-Embedder-Policy

COEP 控制"文档是否允许加载跨源资源"，是跨源隔离的另一半。设置 `require-corp` 后，页面只能加载明确声明了 CORP/CORS 的跨源资源。

```text
COEP 取值：
unsafe-none —— 默认，可自由加载跨源资源
require-corp —— 跨源资源必须带 CORP 或 CORS 头才允许加载
```

```text
Cross-Origin-Embedder-Policy: require-corp

启用跨源隔离的完整三件套：
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
（跨源资源需配合 CORP: cross-origin 或 CORS 头）

启用后可用的能力：
SharedArrayBuffer、performance.measureUserAgentSpecificMemory、
高精度定时器等（Spectre 缓解策略要求的隔离环境）
```

```js
// 未隔离时 SharedArrayBuffer 不可用
if (typeof SharedArrayBuffer === 'undefined') {
  // 需要配置 COOP + COEP 才能启用
}
```

```text
COEP: require-corp 的代价：
页面里所有跨源资源（图片、脚本、iframe）都必须带 CORP 或 CORS 头，
否则加载失败。接入前要梳理全部跨源依赖，逐个确认头配置。
```

## 应用场景实战

### 场景一：为静态站点配置完整安全头（Nginx）

```nginx
server {
    listen 443 ssl;
    server_name www.example.com;

    # CSP
    add_header Content-Security-Policy "default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; connect-src 'self' https://api.example.com";
    # HSTS
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload";
    # MIME 嗅探
    add_header X-Content-Type-Options "nosniff";
    # Referrer
    add_header Referrer-Policy "strict-origin-when-cross-origin";
    # 浏览器能力
    add_header Permissions-Policy "camera=(), microphone=(), geolocation=(self)";
    # 点击劫持兜底（配合 CSP frame-ancestors）
    add_header X-Frame-Options "SAMEORIGIN";
}
```

### 场景二：启用跨源隔离以使用 SharedArrayBuffer

```text
// 需求：页面要用 WASM 多线程 + SharedArrayBuffer 做高性能计算

// 服务端响应头
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp

// 引用的跨源 CDN 脚本/图片需返回
Cross-Origin-Resource-Policy: cross-origin
```

```js
// 验证隔离是否生效
if (crossOriginIsolated) {
  const sab = new SharedArrayBuffer(1024);
  const worker = new Worker('/worker.js');
  worker.postMessage(sab);
} else {
  console.warn('未启用跨源隔离，SharedArrayBuffer 不可用');
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 所有响应统一在网关/CDN 层下发安全头，避免散落在各服务
2. HSTS 上线前先确认证书链有效，max-age 从小值逐步加大
3. Referrer-Policy 用 strict-origin-when-cross-origin，兼顾安全与兼容
4. 用不到的敏感能力（摄像头、麦克风）在 Permissions-Policy 里直接禁用
5. 跨源隔离按需开启——不需要 SharedArrayBuffer 就别上 COEP，避免误伤跨源资源
6. 定期用安全扫描工具（SecurityHeaders、observatory.mozilla.org）检测评分

### 踩坑记录

```text
坑 1：HSTS 在 HTTP 响应里下发无效
结论：配置了 HSTS 但不生效，浏览器仍走 HTTP。
原因：HSTS 只在 HTTPS 响应里被浏览器接受。
解法：确保 HSTS 头出现在 HTTPS 响应，并考虑 preload 补首次访问空窗。

坑 2：CSP 里 'unsafe-inline' 与 HSTS 无关却常被一起改坏
结论：为过安全扫描把 style-src 收紧后，CSS-in-JS 样式全丢。
原因：CSS-in-JS 依赖内联 style 注入。
解法：style 内联需求用 nonce 方案，或保留 style-src 的 'unsafe-inline' 并评估风险。

坑 3：COEP: require-corp 导致第三方图片全挂
结论：开启跨源隔离后页面图片、脚本加载失败。
原因：跨源资源没带 CORP/CORS 头，被 require-corp 拒绝。
解法：让 CDN 返回 CORP: cross-origin，或暂缓开启 COEP。

坑 4：Permissions-Policy 禁用 geolocation 后定位功能失效
结论：地图/定位功能静默失败。
原因：Permissions-Policy 优先于运行时授权，直接禁用能力。
解法：按需在 allowlist 里放行 (self)，别一刀切全禁。

坑 5：nosniff 后脚本不执行
结论：加了 nosniff 后 JS 报 "MIME type mismatch"。
原因：服务端脚本 MIME 配错（如 text/plain），nosniff 下不再嗅探纠正。
解法：修正服务端 MIME 映射，脚本必须返回正确的 JavaScript MIME。
```
