## 概述

Trusted Types 是浏览器提供的 DOM XSS 防御机制，核心思路是：把会执行脚本的"危险 API 落点"（innerHTML、eval、script.src 等）从"接受任意字符串"改成"只接受可信类型对象"。攻击者注入的普通字符串无法通过类型检查，从根源上堵死 DOM XSS。

```text
Trusted Types 解决的问题：
1. innerHTML / insertAdjacentHTML 传用户输入 → DOM XSS
2. eval / new Function 执行不可信字符串 → 代码注入
3. script.src / iframe.src 被赋值恶意 URL → 脚本/框架注入

传统防护依赖开发者"记得转义"，Trusted Types 把"转义"变成"强制类型检查"，
漏一个点就会被浏览器拦截。
```

```text
// 通过响应头启用
Content-Security-Policy: require-trusted-types-for 'script'

// 禁用后：innerHTML 等 API 只接受 TrustedHTML，传字符串直接抛 TypeError
element.innerHTML = userInput;  // TypeError: This document requires 'TrustedHTML' assignment
```

Trusted Types 必须配合 CSP 的 `require-trusted-types-for 'script'` 指令启用，且默认（未配置 policy）会禁用所有危险落点——页面必须先注册 policy 才能正常用 innerHTML 等 API。

## Trusted Types 模型

Trusted Types 用三个类型（TrustedHTML、TrustedScript、TrustedScriptURL）给三类危险 API 上锁，通过 policy 对象完成"字符串 → 可信对象"的转换。

```text
模型结构：
1. 三个可信类型 —— 对应三类危险落点
2. Policy —— 注册到 Trusted Types 工厂，定义如何清洗/创建可信对象
3. 默认 policy —— 兜底策略，生产环境应避免（等于放弃类型检查）

启用后，浏览器还会给危险 API 打上"需要可信类型"的标记，
只有 trustedTypes.createPolicy 创建的对象才能通过检查。
```

```js
// 检查浏览器是否支持 Trusted Types
if (window.trustedTypes && trustedTypes.createPolicy) {
  // 支持
}
```

```text
危险落点与对应类型：
innerHTML、outerHTML、insertAdjacentHTML、document.write → TrustedHTML
eval、Function 构造器、setTimeout(string)、script.text → TrustedScript
script.src、iframe.src、import()、Worker 构造器 → TrustedScriptURL
```

Trusted Types 的防御价值在于"默认拒绝"：没有 policy 时一切危险操作都失败，开发者被迫显式声明"这段数据我确认过安全"，把安全决策从"别忘了转义"变成"必须主动声明"。

## TrustedHTML

TrustedHTML 是 innerHTML 等 HTML 落点要求的安全类型，创建时需要在 policy 里明确清洗逻辑。

```js
// 创建生成 TrustedHTML 的 policy
const sanitizePolicy = trustedTypes.createPolicy('sanitize-html', {
  createHTML: (input) => {
    // 这里放清洗逻辑，比如用 DOMPurify 去掉脚本
    return DOMPurify.sanitize(input);
  }
});

// 通过 policy 生成可信对象
const clean = sanitizePolicy.createHTML('<p>用户输入的内容</p>');
element.innerHTML = clean;  // 通过

// 直接传字符串会被拒
// element.innerHTML = '<p>不可信</p>';  // TypeError
```

```js
// 简单场景：纯文本展示，直接转义尖括号
const escapePolicy = trustedTypes.createPolicy('escape', {
  createHTML: (input) => {
    const div = document.createElement('div');
    div.textContent = input;   // textContent 不解析 HTML，天然安全
    return div.innerHTML;
  }
});
```

```text
TrustedHTML 的常见生产方案：
用 DOMPurify 等库做白名单清洗，再交给 createHTML 返回。
清洗逻辑应集中在少数 policy 里，散落各处等于没有类型约束。
```

## TrustedScript

TrustedScript 保护脚本执行落点：eval、Function 构造器、`setTimeout/setInterval` 传字符串等。

```js
const scriptPolicy = trustedTypes.createPolicy('scripts', {
  createScript: (input) => {
    // 只允许来自可信来源的脚本字符串，业务里通常直接用字符串字面量
    return input;
  }
});

// eval 传普通字符串会被拒
// eval('alert(1)');  // TypeError: requires 'TrustedScript'

// 通过 policy 包装后可执行
const trusted = scriptPolicy.createScript('console.log(1)');
eval(trusted);  // 通过
```

```js
// 实际项目中更安全的做法：禁用这些落点，不提供 createScript
const noEvalPolicy = trustedTypes.createPolicy('no-eval', {
  createScript: () => { throw new Error('禁止动态脚本'); }
});
// 这样所有 eval / new Function 尝试都会在 policy 层被拒绝
```

```text
createScript 是最危险的一个 policy 方法：
它等于把"字符串变成可执行代码"的入口集中暴露，
一旦攻击者能控制传入 createScript 的字符串，等于绕过整个机制。
生产环境应尽量避免提供 createScript，或对其输入做严格校验。
```

## TrustedScriptURL

TrustedScriptURL 保护 URL 落点：script.src、iframe.src、Worker 构造器、import() 动态导入。

```js
const urlPolicy = trustedTypes.createPolicy('script-url', {
  createScriptURL: (input) => {
    // 只允许同源或白名单域名的脚本 URL
    const url = new URL(input, location.origin);
    if (url.origin === location.origin) {
      return url.href;
    }
    throw new Error('不允许加载外部脚本');
  }
});

const script = document.createElement('script');
// script.src = 'https://evil.com/x.js';  // TypeError
script.src = urlPolicy.createScriptURL('/assets/app.js');  // 通过
```

```js
// Worker 与动态 import 同样受保护
const workerUrl = urlPolicy.createScriptURL('/workers/task.js');
const worker = new Worker(workerUrl);

const moduleUrl = urlPolicy.createScriptURL('/modules/lazy.js');
import(moduleUrl).then(m => m.init());
```

```text
TrustedScriptURL 的意义：
script.src 是 XSS 和供应链攻击的常见入口，
攻击者如果能控制 src 就能加载任意脚本。
强制走 createScriptURL 后，URL 必须先过白名单校验。
```

## Policy

Policy 是 Trusted Types 的注册中心，通过 `trustedTypes.createPolicy(name, rules)` 创建，`rules` 定义了 createHTML/createScript/createScriptURL 三个清洗函数。

```js
// 创建并命名 policy（同名重复创建会抛异常）
const policy = trustedTypes.createPolicy('default', {
  createHTML: (input) => DOMPurify.sanitize(input),
  createScript: (input) => { throw new Error('禁用'); },
  createScriptURL: (input) => {
    const u = new URL(input, location.origin);
    return u.origin === location.origin ? u.href : (() => { throw new Error('外部脚本被拒'); })();
  }
});
```

```js
// 获取已创建的 policy（重复调用返回同一个实例）
const same = trustedTypes.getPolicyNames();  // ['default']

// 通过 CSP 指定允许的 policy 名单，收紧命名空间
// Content-Security-Policy: trusted-types default other-policy
// 未在名单里的 policy 创建会失败
```

```text
policy 命名与管控：
1. createPolicy 同名会抛错，适合"启动时集中注册一次"
2. CSP 的 trusted-types 指令可限定允许的 policy 名
3. 生产环境不要用 'allow-duplicates'，也不要注册宽松的 default policy
```

```js
// 兜底 default policy（不推荐生产使用）
// 未显式 policy 时，危险落点会尝试走 default policy，等于保留了字符串直传的通道
trustedTypes.createPolicy('default', {
  createHTML: (input) => input   // 危险：不做任何清洗
});
```

Policy 是 Trusted Types 的治理核心：把"哪些地方允许写 HTML/脚本/URL"集中到一处声明，配合 CSP 的 `trusted-types` 白名单，可以做到"除了这几个经过审计的 policy，全站没有第二个地方能写 innerHTML"。

## 应用场景实战

### 场景一：富文本编辑器内容的 XSS 防护

```js
// 用户输入的富文本 HTML，需要渲染到页面
import DOMPurify from 'dompurify';

const richTextPolicy = trustedTypes.createPolicy('rich-text', {
  createHTML: (dirty) => DOMPurify.sanitize(dirty, {
    ALLOWED_TAGS: ['p', 'br', 'strong', 'em', 'ul', 'ol', 'li', 'a', 'img'],
    ALLOWED_ATTR: ['href', 'src', 'alt'],
  })
});

function renderComment(html) {
  const el = document.getElementById('comment');
  el.innerHTML = richTextPolicy.createHTML(html);  // 清洗后再赋值
}

// 攻击者输入 <img src=x onerror=alert(1)> 时，onerror 被 DOMPurify 剥掉
renderComment('<img src=x onerror=alert(1)>');
```

### 场景二：封装项目专用的安全 DOM 工具

```js
// 统一封装，业务代码不直接接触 innerHTML
const dom = (() => {
  const p = trustedTypes.createPolicy('app-dom', {
    createHTML: (s) => {
      const t = document.createElement('template');
      t.textContent = s;   // 先当纯文本
      return t.innerHTML;
    },
    createScriptURL: (s) => new URL(s, location.origin).href,
  });

  return {
    setText(el, text) {
      el.textContent = text;   // 纯文本场景走 textContent，不涉及可信类型
    },
    setHTML(el, html) {
      el.innerHTML = p.createHTML(html);  // HTML 场景统一走 policy
    },
    loadScript(src) {
      const s = document.createElement('script');
      s.src = p.createScriptURL(src);
      document.head.appendChild(s);
    },
  };
})();
```

```text
// 启用 CSP
Content-Security-Policy: require-trusted-types-for 'script'; trusted-types app-dom
// 只允许 app-dom 这一个 policy，任何绕过 dom 工具直接 innerHTML 的代码都会被拦截
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 `require-trusted-types-for 'script'` 启用，并在 CSP 的 `trusted-types` 里限制 policy 名单
2. 清洗逻辑集中在少数命名 policy 里，业务代码统一走封装好的工具函数
3. 纯文本渲染用 textContent，不要为了"统一"硬走 createHTML
4. createScript 能不给就不给，动态脚本走 createScriptURL 白名单
5. 用 DOMPurify 等成熟清洗库，不要手写正则清洗 HTML
6. 上线前用 Report-Only 模式观察，确认没有遗漏的 innerHTML 调用点再 enforce

### 踩坑记录

```text
坑 1：启用了 Trusted Types 但没注册 policy，页面直接白屏
结论：innerHTML 全部抛 TypeError，动态渲染的内容消失。
原因：默认拒绝模式下，任何危险落点没有 policy 就失败。
解法：启动阶段优先注册 policy，再渲染业务内容。

坑 2：DOMPurify 返回字符串，仍被 innerHTML 拒绝
结论：DOMPurify.sanitize() 返回的是普通字符串，不是 TrustedHTML。
原因：清洗函数只是"返回安全字符串"，类型转换靠 policy 的 createHTML 完成。
解法：把 DOMPurify.sanitize 的返回值作为 createHTML 的返回值。

坑 3：同名 policy 重复创建抛异常
结论：热更新或模块重复加载时报 duplicate policy 错误。
原因：createPolicy 同名默认不允许。
解法：用 getPolicyNames 判断，或把 policy 注册收敛到单一入口模块。

坑 4：default policy 被当成"兼容层"滥用
结论：全局注册宽松 default policy 后，Trusted Types 形同虚设。
原因：未显式处理的落点都会走 default policy，等于保留字符串直传通道。
解法：生产环境禁用 default policy，强制每个落点显式走对应 policy。

坑 5：老牌第三方库不兼容
结论：旧版富文本编辑器、广告 SDK 直接给 innerHTML 赋字符串，被拦截。
原因：这些库没有为 Trusted Types 适配。
解法：用 Report-Only 先评估，通过 DOMPurify 包装或升级库版本解决。
```
