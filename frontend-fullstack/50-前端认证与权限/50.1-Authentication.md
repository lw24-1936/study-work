## 概述

Authentication（认证）在前端工程里是一套完整的状态管理与请求处理机制：登录后如何保存凭证、如何把凭证带到每个请求、过期后如何静默续期、退出后如何清理。它不止是"调一个登录接口"，而是贯穿应用生命周期的横切关注点。

```text
前端认证要解决的四件事：
1. 登录 —— 收集凭证、调接口、拿到并存储令牌
2. 凭证携带 —— 每个请求自动带上令牌
3. 续期 —— 令牌过期后无感刷新，不打断用户操作
4. 退出 —— 清理本地凭证、通知服务端失效
```

```text
// 前端认证的典型状态
{
  isAuthenticated: false,
  user: null,
  accessToken: null,     // 短期，随请求发送
  refreshToken: null,    // 长期，用于换新 accessToken
  loading: true          // 启动时恢复会话中
}
```

认证方案的选型（Session vs Token）决定了存储位置和请求方式，但无论哪种，前端都要处理"登录态恢复""过期跳转""并发刷新"这些通用问题。

## Login 与 Logout

登录和退出是认证的入口和出口，前端要处理好表单、错误、重定向和状态清理。

```js
// 登录
async function login(username, password) {
  const res = await fetch('/api/auth/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ username, password }),
    credentials: 'include'
  });
  if (!res.ok) {
    const { message } = await res.json();
    throw new Error(message || '登录失败');
  }
  const { accessToken, user } = await res.json();
  store.setAccessToken(accessToken);
  store.setUser(user);
  redirectTo(returnUrl || '/dashboard');
}
```

```js
// 退出：清理本地 + 通知服务端失效
async function logout() {
  try {
    await fetch('/api/auth/logout', { method: 'POST', credentials: 'include' });
  } finally {
    store.clear();           // 清空 token 和用户信息
    redirectTo('/login');    // 无论服务端调用成功与否都跳登录
  }
}
```

```text
登录要处理好的细节：
1. 登录成功后回跳 returnUrl（用户在某个页面被踢到登录页，登录后应回到原页）
2. 密码错误 vs 网络错误的提示要区分
3. 防暴力破解：前端做基础限频，真正的防线在服务端

退出要处理好的细节：
1. 本地清理必须执行（服务端调用失败也不能卡住退出流程）
2. 用 finally 保证清理逻辑一定走
3. 多标签页场景要同步退出状态（storage 事件或 BroadcastChannel）
```

## Session 认证

Session 认证下，凭证是 HttpOnly Cookie，由浏览器自动携带，前端几乎不需要管理 token。

```js
// Session 方案前端代码极简：只管 credentials
async function getProfile() {
  const res = await fetch('/api/profile', { credentials: 'include' });
  return res.json();
}
```

```text
Session 认证前端要点：
1. Cookie 由服务端 Set-Cookie 下发，JS 读不到（HttpOnly）
2. 跨域请求必须 credentials: 'include'，服务端 CORS 也要 allowCredentials
3. 登录态判断依赖一个"whoami"接口，前端启动时调一次恢复会话
```

```js
// 启动时恢复登录态
async function bootstrap() {
  try {
    const res = await fetch('/api/auth/me', { credentials: 'include' });
    if (res.ok) {
      store.setUser(await res.json());
    } else {
      store.setUnauthenticated();
    }
  } finally {
    store.setLoading(false);
  }
}
```

Session 方案对前端最友好（不用碰 token），但要求前后端同域或处理好 CORS，且服务端要有会话存储，适合传统 SSR 或内部系统。

## Token 认证

Token 认证是前后端分离的主流方案，前端拿到 token 后自行存储、自行携带。

```js
// 请求拦截器统一携带 token
async function request(url, options = {}) {
  const token = store.getAccessToken();
  const headers = { ...options.headers };
  if (token) headers.Authorization = `Bearer ${token}`;
  const res = await fetch(url, { ...options, headers });
  return res;
}
```

```text
Token 存储位置对比：
内存（变量） —— 最安全，刷新页面即丢失，需配合 refresh token 恢复
localStorage —— 持久，但 XSS 可读，有窃取风险
HttpOnly Cookie —— XSS 读不到，但回到 CSRF 防护问题

折中方案：
access token 存内存，refresh token 存 HttpOnly Cookie，
兼顾安全性和"刷新不丢登录态"。
```

```text
Token 认证前端要点：
1. 统一封装请求层，禁止业务代码手动拼 Authorization
2. access token 不落 localStorage，避免被 XSS 一把梭
3. 请求前检查 token 是否临近过期，提前刷新避免竞态
```

## Access Token 与 Refresh Token

双 token 机制是 token 认证的核心工程实践：用短命的 access token 控制风险窗口，用长命的 refresh token 实现静默续期。

```text
两者分工：
Access Token —— 短期（如 15 分钟），随每个请求发送，用于鉴权
Refresh Token —— 长期（如 30 天），只在刷新接口使用，用于换新 access token

为什么不用一个长期 access token：
一旦泄露，攻击者可在整个有效期内冒用；
拆分后 access token 泄露影响窗口短，refresh token 使用频率低、更好保护。
```

```js
// 带自动续期的请求封装
let refreshPromise = null;  // 并发刷新合并

async function request(url, options = {}) {
  const res = await doFetch(url, options);
  if (res.status !== 401) return res;

  // access token 过期，触发刷新
  refreshPromise = refreshPromise || refreshTokens();
  const newToken = await refreshPromise;
  refreshPromise = null;

  if (newToken) return doFetch(url, options);  // 重试
  redirectTo('/login');                        // 刷新失败，跳登录
}

async function refreshTokens() {
  const res = await fetch('/api/auth/refresh', { credentials: 'include' });
  if (res.ok) {
    const { accessToken } = await res.json();
    store.setAccessToken(accessToken);
    return accessToken;
  }
  return null;
}
```

```text
并发刷新问题：
多个请求同时 401，会触发多次刷新。
用单例 refreshPromise 合并并发请求，只有第一个真正刷新，其余复用结果。
```

## JWT 实战

JWT 是 access token 最常用的格式，前端要理解它的结构、解码方式和过期处理。

```js
// 前端解码 JWT（不验签，仅读取 payload 展示信息）
function decodeJwt(token) {
  const payload = token.split('.')[1];            // 取中间段
  const base64 = payload.replace(/-/g, '+').replace(/_/g, '/');
  return JSON.parse(atob(base64));
}

// 判断是否临近过期（提前 60 秒刷新）
function isNearExpiry(token, bufferSeconds = 60) {
  const { exp } = decodeJwt(token);
  return exp * 1000 - Date.now() < bufferSeconds * 1000;
}
```

```js
// 定时器主动续期，避免请求时才被动刷新
function startTokenWatcher() {
  setInterval(() => {
    const token = store.getAccessToken();
    if (token && isNearExpiry(token)) {
      refreshTokens();
    }
  }, 30 * 1000);
}
```

```text
前端对 JWT 的正确认知：
1. payload 只是 base64 编码，任何人可解码，不能存敏感信息
2. 验签是服务端的事，前端解码只用于读取 exp 等非敏感声明
3. 不要把 JWT 当加密手段，它的价值是"签名防篡改"不是"保密"
```

## 应用场景实战

### 场景一：完整的认证模块（含启动恢复 + 路由守卫）

```js
// authStore.js —— 集中管理认证状态
const authStore = {
  user: null,
  accessToken: null,
  status: 'pending',   // pending / authenticated / unauthenticated

  async init() {
    try {
      const res = await fetch('/api/auth/me', { credentials: 'include' });
      if (res.ok) {
        this.user = await res.json();
        this.status = 'authenticated';
      } else {
        this.status = 'unauthenticated';
      }
    } catch {
      this.status = 'unauthenticated';
    }
  },

  async login(username, password) { /* 见 Login 节 */ },
  async logout() { /* 见 Logout 节 */ }
};
```

```js
// 路由守卫：未登录访问受保护页面重定向到登录
async function routeGuard(to) {
  if (to.meta.requiresAuth && authStore.status !== 'authenticated') {
    return { path: '/login', query: { returnUrl: to.fullPath } };
  }
}
```

### 场景二：多标签页登录态同步

```js
// 用 BroadcastChannel 同步退出状态，一个标签页退出，其他标签页跟着退出
const channel = new BroadcastChannel('auth');

channel.onmessage = (e) => {
  if (e.data.type === 'logout') {
    authStore.clear();
    redirectTo('/login');
  }
};

// 退出时广播
async function logout() {
  await fetch('/api/auth/logout', { method: 'POST', credentials: 'include' });
  authStore.clear();
  channel.postMessage({ type: 'logout' });
  redirectTo('/login');
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 登录态统一收敛到一个 auth store 和请求封装层，业务代码不碰 token
2. access token 存内存 + refresh token 存 HttpOnly Cookie，兼顾安全与持久
3. 并发 401 用单例 refreshPromise 合并刷新，避免重复请求
4. 退出用 finally 保证本地清理一定执行
5. 启动时调 /me 接口恢复会话，期间用 loading 态挡住路由跳转
6. 临近过期的 token 主动续期，不要每次都靠 401 触发

### 踩坑记录

```text
坑 1：把 access token 直接放 localStorage
结论：XSS 攻击者一次就能拿走长期有效的访问凭证。
原因：localStorage 可被任意脚本读取。
解法：access token 存内存，refresh token 存 HttpOnly Cookie。

坑 2：并发请求触发多次刷新
结论：token 过期瞬间多个请求同时刷新，产生多份 refresh 请求甚至冲突。
原因：每个 401 都独立触发刷新。
解法：用单例 refreshPromise 合并并发刷新。

坑 3：退出时服务端调用失败导致本地残留
结论：服务端异常时前端登录态没清，用户以为退出了其实还在。
原因：logout 的清理逻辑写在成功回调里。
解法：用 try/finally 保证本地清理无条件执行。

坑 4：忘记在跨域请求带 credentials
结论：Session 方案下登录成功但接口仍返回 401。
原因：跨域 fetch 默认不带 Cookie。
解法：credentials: 'include'，且服务端 CORS 配置 allowCredentials。

坑 5：登录后未回跳原页面
结论：用户在深层页面被踢到登录，登录后停在首页。
原因：没有记录 returnUrl。
解法：登录页读取 returnUrl 参数，成功后回跳。
```
