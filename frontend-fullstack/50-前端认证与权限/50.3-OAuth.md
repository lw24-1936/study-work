## 概述

OAuth 2.0 是授权框架，让第三方应用在用户授权下访问其资源，而无需拿到用户密码。前端场景里最常见的是"用 GitHub / Google / 微信登录"，本质是让应用拿到一个能代表用户授权的 token。

```text
OAuth 2.0 核心概念：
Resource Owner —— 用户
Client —— 应用（前端 + 后端）
Authorization Server —— 授权服务器（发 token）
Resource Server —— 资源服务器（校验 token 提供数据）

两种 token：
Access Token —— 短期，访问资源用
Refresh Token —— 长期，换新 access token 用
```

```text
四种授权模式与适用场景：
Authorization Code + PKCE —— 有用户参与的前端/移动应用（主流）
Client Credentials —— 服务间调用，无用户
Device Authorization —— 电视、IoT 等输入受限设备
Refresh Token —— 续期，配合其他模式使用
```

```text
// OAuth 各端点的统一形态
/authorize —— 授权端点（浏览器跳转，用户同意授权）
/token      —— 令牌端点（换 token，前端或后端调用）
/revoke     —— 吊销端点（退出登录、撤销授权）
```

选型核心问题只有一个："客户端能不能安全保存 client_secret"。能（后端服务）用 Confidential Client；不能（纯前端 SPA）就必须用 PKCE 补偿。

## Authorization Code

Authorization Code（授权码）模式是最安全的 OAuth 流程，核心是"先拿一次性 code，再换 token"，让 token 不直接暴露在浏览器。

```text
授权码模式流程：
1. 前端跳转授权页
   /authorize?response_type=code&client_id=xxx&redirect_uri=xxx&scope=openid&state=yyy
2. 用户在授权服务器登录并同意授权
3. 授权服务器重定向回 redirect_uri?code=zzz&state=yyy
4. 前端拿到 code，交给后端（code 是短命一次性凭证）
5. 后端用 code + client_secret 调 /token 换 access_token / refresh_token
6. 后端建立自己的会话，前端后续走自己的认证
```

```js
// 前端发起授权跳转
function startOAuth() {
  const params = new URLSearchParams({
    response_type: 'code',
    client_id: 'my-client-id',
    redirect_uri: 'https://app.example.com/callback',
    scope: 'openid profile email',
    state: crypto.randomUUID()   // 防 CSRF
  });
  location.href = `https://auth.example.com/authorize?${params}`;
}
```

```js
// 回调页：拿到 code 交给后端
async function handleCallback() {
  const params = new URLSearchParams(location.search);
  const code = params.get('code');
  const state = params.get('state');

  // 校验 state 防止 CSRF（与发起时保存的比对）
  if (state !== sessionStorage.getItem('oauth_state')) {
    throw new Error('state 不匹配');
  }

  // code 交给后端换 token，前端不接触 client_secret
  await fetch('/api/auth/oauth-callback', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ code })
  });
  location.href = '/dashboard';
}
```

```text
state 参数的作用（防 CSRF）：
攻击者诱导用户点一个"绑定攻击者账号"的授权链接，
用户授权后，攻击者的账号就和用户的第三方账号绑定了。
state 是前端生成的随机值，授权前保存、回调后校验，不匹配即拒绝，
确保授权流程是"本人发起"的。
```

## PKCE

PKCE（Proof Key for Code Exchange）为"没有 client_secret 的公共客户端"防授权码拦截，是纯前端 SPA 的标配。

```text
PKCE 原理：
前端生成随机 code_verifier，算哈希得 code_challenge。
授权请求带 challenge，换 token 带 verifier。
授权服务器验证两者匹配才发 token。
即使 code 被中间人截获，没有 verifier 也换不到 token。

流程：
1. 前端生成 code_verifier（随机）和 code_challenge（SHA256(verifier)）
2. 授权请求带 code_challenge + code_challenge_method=S256
3. 换 token 时带 code_verifier
4. 服务器校验 challenge 与 verifier 匹配
```

```js
// 浏览器端生成 PKCE（Web Crypto API）
async function generatePKCE() {
  const verifier = crypto.randomUUID() + crypto.randomUUID();
  const encoder = new TextEncoder();
  const hash = await crypto.subtle.digest('SHA-256', encoder.encode(verifier));
  const challenge = btoa(String.fromCharCode(...new Uint8Array(hash)))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
  return { codeVerifier: verifier, codeChallenge: challenge };
}
```

```js
// 授权时带上 challenge，换 token 时带上 verifier
async function startPKCEFlow() {
  const { codeVerifier, codeChallenge } = await generatePKCE();
  sessionStorage.setItem('code_verifier', codeVerifier);

  const params = new URLSearchParams({
    response_type: 'code',
    client_id: 'spa-client',
    redirect_uri: 'https://app.example.com/callback',
    code_challenge: codeChallenge,
    code_challenge_method: 'S256',
  });
  location.href = `https://auth.example.com/authorize?${params}`;
}
```

```text
PKCE 注意点：
1. code_verifier 要存起来（sessionStorage），换 token 时要用
2. 必须用 S256（哈希），plain 方式（直接传 verifier）已不推荐
3. 即使有 client_secret 的后端也建议启用 PKCE，防御 code 泄露
```

## Client Credentials

Client Credentials（客户端凭证）模式用于机器对机器认证，没有用户参与，客户端用自己的身份（client_id + client_secret）直接换 token。

```text
适用场景：
1. 后端服务之间调用（微服务、定时任务）
2. 前端不适用（secret 无法保密）
3. 代表"应用本身"而非"某个用户"访问资源
```

```text
// 流程：直接调 token 端点
POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=service-a
&client_secret=xxx
&scope=api:read
```

```js
// 后端示例（Node）：服务间调用拿 token
async function getServiceToken() {
  const res = await fetch('https://auth.example.com/token', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: new URLSearchParams({
      grant_type: 'client_credentials',
      client_id: process.env.CLIENT_ID,
      client_secret: process.env.CLIENT_SECRET,
      scope: 'api:read',
    }),
  });
  const { access_token, expires_in } = await res.json();
  return access_token;
}
```

```text
安全要点：
1. client_secret 只能在服务端环境出现，绝不能进前端代码
2. 返回的 token 通常没有 refresh token（服务端可随时重新申请）
3. 通过 scope 收敛权限，只申请最小必要范围
```

## Device Authorization

Device Authorization（设备授权）用于输入受限设备：电视、游戏机、IoT 设备、CLI 工具。设备自己不便输入账号密码，改用"在另一台设备上扫码/输码授权"。

```text
设备授权流程：
1. 设备调 /device_authorization，拿到 device_code、user_code、verification_uri
2. 设备展示 user_code 和 verification_uri（或二维码）
3. 用户在手机/电脑访问 verification_uri 并输入 user_code，登录授权
4. 设备轮询 /token（带 device_code），直到用户完成授权
5. 授权完成后 token 端点返回 access_token，设备停止轮询
```

```text
// 设备端请求示例
POST /device_authorization
client_id=smart-tv-app&scope=profile

// 响应
{
  "device_code": "abc...",
  "user_code": "WDJB-MJHT",          // 用户要输入的短码
  "verification_uri": "https://auth.example.com/device",
  "expires_in": 1800,
  "interval": 5                      // 建议轮询间隔（秒）
}
```

```js
// 设备端轮询逻辑
async function pollForToken(deviceCode, intervalMs) {
  while (true) {
    const res = await fetch('https://auth.example.com/token', {
      method: 'POST',
      headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
      body: new URLSearchParams({
        grant_type: 'urn:ietf:params:oauth:grant-type:device_code',
        device_code: deviceCode,
        client_id: 'smart-tv-app',
      }),
    });
    const data = await res.json();
    if (data.access_token) return data.access_token;
    if (data.error === 'authorization_pending') {
      await sleep(intervalMs);   // 用户还没授权，继续等
      continue;
    }
    if (data.error === 'slow_down') { intervalMs += 5000; continue; }
    throw new Error(data.error);  // expired_token / access_denied
  }
}
```

```text
错误码语义：
authorization_pending —— 用户尚未授权，继续轮询
slow_down —— 轮询太快，加大间隔
expired_token —— device_code 过期，重新发起
access_denied —— 用户拒绝授权
```

## Refresh Token

Refresh Token 是长期凭证，用于 access token 过期后换新的，避免用户反复登录。它是 token 生命周期管理的关键。

```text
Refresh Token 的使用：
1. access token 过期（或 401）时，用 refresh token 调 /token 换新
2. 换新时通常也会轮换 refresh token（rotation），旧的立即失效
3. refresh token 只发给授权服务器，不随业务请求发送
```

```text
// 用 refresh token 换新 access token
POST /token
grant_type=refresh_token
&refresh_token=xxx
&client_id=spa-client
```

```js
// 前端刷新逻辑（refresh token 存在 HttpOnly Cookie）
let refreshPromise = null;

async function refreshAccessToken() {
  refreshPromise = refreshPromise || fetch('/api/auth/refresh', {
    method: 'POST',
    credentials: 'include',
  }).then(r => r.ok ? r.json() : null)
    .finally(() => { refreshPromise = null; });

  return refreshPromise;
}
```

```text
Refresh Token 安全要点：
1. 只在与授权服务器交互时使用，不随普通 API 请求发送
2. 开启 rotation（轮换）—— 每次刷新换新 token，旧 token 立即失效
3. 检测到 refresh token 重放时，吊销整个授权（可能被盗）
4. 存储用 HttpOnly Cookie，避免 XSS 窃取
```

## 应用场景实战

### 场景一：SPA 接入第三方登录（Authorization Code + PKCE）

```js
// 1. 发起登录
async function loginWithGoogle() {
  const { codeVerifier, codeChallenge } = await generatePKCE();
  sessionStorage.setItem('oauth_code_verifier', codeVerifier);

  const params = new URLSearchParams({
    response_type: 'code',
    client_id: 'spa-client',
    redirect_uri: 'https://app.example.com/callback',
    scope: 'openid email profile',
    state: crypto.randomUUID(),
    code_challenge: codeChallenge,
    code_challenge_method: 'S256',
  });
  sessionStorage.setItem('oauth_state', params.get('state'));
  location.href = `https://accounts.example.com/authorize?${params}`;
}
```

```js
// 2. 回调处理（换 token 走 BFF，保护 client_secret）
async function handleOAuthCallback() {
  const url = new URL(location.href);
  const code = url.searchParams.get('code');
  const state = url.searchParams.get('state');

  if (state !== sessionStorage.getItem('oauth_state')) {
    return showError('授权状态校验失败');
  }

  const codeVerifier = sessionStorage.getItem('oauth_code_verifier');
  await fetch('/api/auth/oauth/code', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ code, codeVerifier }),
  });
  location.href = '/dashboard';
}
```

### 场景二：CLI 工具的设备授权登录

```js
// CLI 登录：展示验证码，轮询等待用户手机授权
async function deviceLogin() {
  const init = await fetch('https://auth.example.com/device_authorization', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: new URLSearchParams({ client_id: 'my-cli' }),
  }).then(r => r.json());

  console.log(`请访问 ${init.verification_uri} 并输入验证码：${init.user_code}`);
  const token = await pollForToken(init.device_code, init.interval * 1000);
  console.log('登录成功');
  return token;
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 纯前端一律用 Authorization Code + PKCE，绝不用 Implicit 模式
2. client_secret 只存在于后端，前端永远不接触
3. 授权请求必须带 state 并回调校验，防 CSRF
4. refresh token 开启 rotation，检测重放立即吊销
5. scope 最小化授权，只申请真正需要的权限
6. 设备授权按 interval 轮询，处理 slow_down 降频

### 踩坑记录

```text
坑 1：用 Implicit 模式给 SPA 发 token
结论：access token 直接暴露在 URL，易被日志和脚本截获。
原因：Implicit 模式 token 走前端回传，无 code 交换。
解法：改用 Authorization Code + PKCE。

坑 2：client_secret 写进前端代码
结论：攻击者从打包产物里提取 secret，冒用应用身份。
原因：前端代码公开，任何"保密"在浏览器里都是假的。
解法：secret 只在后端，前端走 PKCE 公共客户端流程。

坑 3：忘记校验 state
结论：用户被诱导绑定攻击者的账号。
原因：未校验 state，无法确认授权流程由本人发起。
解法：发起时生成随机 state，回调时严格比对。

坑 4：设备授权轮询不处理 slow_down
结论：轮询过快被限流，导致登录流程异常。
原因：忽略 slow_down 错误码继续高频轮询。
解法：收到 slow_down 时加大轮询间隔。

坑 5：refresh token 不轮换
结论：refresh token 泄露后攻击者可长期冒用。
原因：同一 refresh token 可反复换新 access token。
解法：每次刷新轮换 refresh token，旧 token 立即失效。
```
