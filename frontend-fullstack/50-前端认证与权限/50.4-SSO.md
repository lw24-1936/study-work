## 概述

SSO（Single Sign-On，单点登录）让用户在多个相互信任的系统间只需登录一次。登录后访问其他系统自动完成认证，退出时也能做到单点登出。对前端而言，SSO 的核心是"登录态如何在多个域名/系统间流转"。

```text
SSO 要解决的两个方向：
1. 单点登录 —— 一个系统登录，其他系统免登录
2. 单点登出 —— 一个系统退出，其他系统同步退出

实现 SSO 的常见协议/方案：
1. OIDC —— 基于 OAuth 2.0 的身份层，现代互联网标准
2. OAuth SSO —— 用 OAuth 授权结果直接当登录凭证
3. SAML —— 企业级 XML 协议（ADFS、Okta）
4. CAS —— 集中认证服务协议，高校/老系统常见
```

```text
SSO 的通用角色：
IdP（Identity Provider）—— 身份提供方，统一认证
SP（Service Provider）—— 业务系统，信任 IdP 的认证结果

用户 → 访问 SP → 未登录 → 跳 IdP 登录 → 拿凭证回 SP → SP 建会话 → 后续访问其他 SP 免登录
```

SSO 本质上把"认证"从各业务系统抽离到统一的 IdP，业务系统只负责"消费"认证结果，不再自己管密码。

## OAuth SSO

OAuth SSO 是"用 OAuth 授权结果当登录凭证"的做法：用户通过 OAuth 授权登录，应用拿到 token 后建立本地会话，多个应用共享同一套 OAuth 授权体系即实现 SSO。

```text
OAuth SSO 的思路：
1. 多个应用都接入同一个授权服务器
2. 用户在任一应用完成 OAuth 授权后，授权服务器记住登录态
3. 访问其他应用时，OAuth 流程自动跳过"输入密码"这一步（已有授权会话）
4. 各应用各自拿 token、各自建会话

本质：OAuth 本身是授权协议，但"授权"隐含了"认证"，
OAuth SSO 是把这个隐含能力拿来当登录用。
```

```js
// 前端发起 OAuth SSO 登录
function ssoLogin() {
  const params = new URLSearchParams({
    response_type: 'code',
    client_id: 'app-a',
    redirect_uri: 'https://a.example.com/callback',
    scope: 'openid',
    state: crypto.randomUUID(),
  });
  // 用户已在授权服务器登录过 → 直接回调，无密码输入
  location.href = `https://sso.example.com/authorize?${params}`;
}
```

```text
OAuth SSO 的局限：
OAuth 2.0 没有标准化的"用户是谁"的返回，
应用拿到 token 后还得自己调一个"用户信息"接口。
这正是 OIDC 要标准化解决的问题。
```

## OIDC

OIDC（OpenID Connect）是构建在 OAuth 2.0 上的身份层，是"用第三方账号登录"的现代标准，也是 SSO 的主流实现。

```text
OIDC 相对 OAuth 2.0 的增量：
1. ID Token —— 用户身份的 JWT，标准字段（sub/iss/aud/exp）
2. UserInfo 端点 —— 标准化的用户信息获取接口
3. 标准 scope —— openid、profile、email、address、phone
4. 发现文档 —— /.well-known/openid-configuration 自动发现配置
```

```text
// ID Token payload 示例
{
  "iss": "https://sso.example.com",     // 签发者（IdP）
  "sub": "user-10086",                  // 用户唯一标识
  "aud": "app-a",                       // 目标应用（必须校验）
  "exp": 1755129600,                    // 过期时间
  "iat": 1755043200,
  "email": "alice@example.com"
}
```

```js
// 前端用发现文档动态获取端点（避免硬编码）
async function discoverIssuer(issuer) {
  const res = await fetch(`${issuer}/.well-known/openid-configuration`);
  const cfg = await res.json();
  return {
    authorizeUrl: cfg.authorization_endpoint,
    tokenUrl: cfg.token_endpoint,
    userInfoUrl: cfg.userinfo_endpoint,
    jwksUrl: cfg.jwks_uri,
  };
}
```

```text
OIDC 的 SSO 优势：
1. 标准化 —— 各 IdP（Google、Okta、Auth0）实现一致，接入成本低
2. ID Token 自包含身份 —— 应用不必再查用户信息
3. 发现文档 —— 配置可自动发现，减少手工对接
```

前端接入 OIDC 通常用 SDK（如 oidc-client-ts）处理完整流程：授权跳转、code 交换、token 管理、静默续期、登出。

## SAML

SAML（Security Assertion Markup Language）是 XML 协议，企业级 SSO 的老牌标准，广泛应用于 ADFS、Okta、Shibboleth 等企业身份体系。

```text
SAML 的核心概念：
Assertion —— 断言，IdP 签发的"用户身份声明"（XML）
IdP —— 身份提供方（企业 AD、Okta）
SP —— 服务提供方（各业务系统）

SAML 2.0 的常见绑定（Binding）：
HTTP Redirect —— 传递认证请求（SP → IdP）
HTTP POST —— 回传断言（IdP → SP）
```

```text
SAML SSO 流程（SP-initiated）：
1. 用户访问 SP，SP 生成 SAMLRequest 重定向到 IdP
2. 用户在 IdP 登录（或已有会话直接放行）
3. IdP 生成 SAMLResponse（含签名的 Assertion），POST 回 SP
4. SP 验签、解析断言，提取用户身份，建立本地会话
```

```xml
<!-- SAML Assertion 结构示意 -->
<saml:Assertion Version="2.0" ID="abc123" IssueInstant="2026-08-13T10:00:00Z">
  <saml:Issuer>https://idp.example.com</saml:Issuer>
  <saml:Subject>
    <saml:NameID Format="urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress">
      alice@example.com
    </saml:NameID>
  </saml:Subject>
  <saml:Conditions NotBefore="..." NotOnOrAfter="...">
    <saml:AudienceRestriction>
      <saml:Audience>https://sp.example.com</saml:Audience>
    </saml:AudienceRestriction>
  </saml:Conditions>
  <saml:AttributeStatement>
    <saml:Attribute Name="role">
      <saml:AttributeValue>admin</saml:AttributeValue>
    </saml:Attribute>
  </saml:AttributeStatement>
  <!-- 数字签名 -->
  <ds:Signature>...</ds:Signature>
</saml:Assertion>
```

```text
SAML 安全要点：
1. 断言必须验签（防伪造）
2. 校验 Audience（断言是发给本 SP 的，防转发重放）
3. 校验有效期（NotBefore / NotOnOrAfter）
4. 校验 InResponseTo（防请求/响应不匹配）
```

SAML 复杂、XML 繁琐，但企业存量系统庞大，前端接入时通常已有成熟的 IdP 和中件（如 Passport-SAML），重点在正确配置而非手写协议。

## CAS

CAS（Central Authentication Service）是集中认证协议，通过"服务票据 + 一次性 ticket"实现 SSO，高校和部分老企业内部系统常见。

```text
CAS 的核心票据：
TGT（Ticket Granting Ticket）—— 存在 IdP 的 Cookie 里，代表"已登录"
ST（Service Ticket）—— 一次性服务票据，用于换取登录态

CAS 流程：
1. 用户访问 SP，未登录 → SP 重定向到 CAS 登录页（带 service 参数）
2. CAS 校验 TGT：无则要求登录，有则直接发 ST
3. CAS 重定向回 SP：service?ticket=ST-xxx
4. SP 拿 ST 调 CAS 的 /serviceValidate 验证，换取用户信息
5. SP 建立本地会话
```

```text
// CAS 端点
/login           —— 登录页，?service=回调地址
/serviceValidate —— SP 校验 ST 的接口，返回 XML 用户信息
/logout          —— 登出，?service=登出后回跳地址
```

```js
// 前端接入 CAS：登录跳转
function casLogin() {
  const service = encodeURIComponent('https://sp.example.com/cas-callback');
  location.href = `https://cas.example.com/login?service=${service}`;
}
```

```js
// SP 后端校验 ticket（前端拿到 ticket 后交给后端）
async function handleCasCallback() {
  const ticket = new URLSearchParams(location.search).get('ticket');
  if (!ticket) return location.href = '/login';

  await fetch('/api/auth/cas-validate', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ ticket, service: 'https://sp.example.com/cas-callback' }),
  });
  location.href = '/dashboard';
}
```

```text
CAS 与 OIDC/SAML 对比：
CAS —— 简单，专为 SSO 设计，但生态和标准化程度弱
OIDC —— 现代标准，互联网首选
SAML —— 企业级老牌，ADFS 体系首选
新项目优先 OIDC，对接存量系统时按对方协议来
```

## 应用场景实战

### 场景一：用 OIDC 实现多系统 SSO（前端侧）

```js
// 统一封装 OIDC 客户端（以 oidc-client-ts 思路示意）
import { UserManager } from 'oidc-client-ts';

const userManager = new UserManager({
  authority: 'https://sso.example.com',
  client_id: 'app-a',
  redirect_uri: 'https://a.example.com/callback',
  response_type: 'code',
  scope: 'openid profile email',
  post_logout_redirect_uri: 'https://a.example.com',
});

// 登录：跳转 IdP，完成后回跳并自动处理 code
export function login() {
  return userManager.signinRedirect();
}

// 回调页处理
export function completeLogin() {
  return userManager.signinRedirectCallback();
}

// 静默续期（iframe 方式，不打断用户）
export function renewSilently() {
  return userManager.signinSilent();
}

// 登出：跳 IdP 统一登出，实现单点登出
export function logout() {
  return userManager.signoutRedirect();
}
```

### 场景二：单点登出的实现

```js
// OIDC 的 end_session 端点实现单点登出
async function ssoLogout(idToken) {
  const cfg = await discoverIssuer('https://sso.example.com');
  const params = new URLSearchParams({
    id_token_hint: idToken,
    post_logout_redirect_uri: 'https://a.example.com',
  });
  // 跳 IdP 登出端点，IdP 会通知所有已登录的 SP 同步登出
  location.href = `${cfg.end_session_endpoint}?${params}`;
}
```

```text
单点登出的两种实现：
1. 前端跳 IdP 登出端点（end_session），IdP 通知各 SP 清会话
2. 各 SP 也提供自己的登出端点，接收 IdP 的回调清理本地会话
```

## 最佳实践与踩坑记录

### 最佳实践

1. 新项目做 SSO 优先 OIDC，标准化、生态好、SDK 成熟
2. 对接存量企业系统时按对方协议（SAML/CAS）来，用成熟中间件别手写协议
3. ID Token / SAML 断言必须校验签名、aud/audience、exp，一个都不能少
4. 统一登出要覆盖 IdP 和各 SP，避免"退出不彻底"
5. 用发现文档和元数据（SAML metadata）自动配置，减少手工对接错误
6. 登录跳转带 state，回调严格校验，防 SSO 流程的 CSRF

### 踩坑记录

```text
坑 1：SAML 断言不校验 Audience
结论：攻击者把 A 系统的断言转发到 B 系统，冒充身份。
原因：断言没绑定目标 SP，可被跨系统重放。
解法：校验 Audience 必须包含本 SP 的标识。

坑 2：OIDC 静默续期失败导致登录态丢失
结论：用户用着用着突然跳登录页。
原因：iframe 静默续期被第三方 Cookie 策略拦截。
解法：用 refresh token 走后台刷新，或降级为弹窗续期。

坑 3：CAS ticket 重复使用
结论：ticket 被重放，攻击者复用他人登录凭证。
原因：ST 是一次性的，但 SP 没有正确消费/校验。
解法：SP 校验后立即消费 ticket，且校验 service 与 ticket 匹配。

坑 4：单点登出只清本地，不清 IdP
结论：用户在一个系统退出，其他系统仍处于登录态。
原因：登出只清了本 SP 的会话，没走 IdP 的登出流程。
解法：登出跳 IdP 的 end_session/logout 端点，实现全局登出。

坑 5：回调地址配置不一致
结论：OIDC/OAuth 回调时报 redirect_uri 不匹配。
原因：前端跳转用的 redirect_uri 与 IdP 里注册的不完全一致（斜杠、端口、编码）。
解法：redirect_uri 必须与 IdP 注册值逐字符一致，注意 URL 编码。
```
