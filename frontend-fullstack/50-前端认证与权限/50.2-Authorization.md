## 概述

Authorization（授权）回答"通过认证的用户能做什么"。前端权限控制不是安全边界（真正的安全在服务端），而是体验层：把用户不该看的页面、按钮、数据提前隐藏，减少无效操作和越权请求。

```text
前端权限的四个层次：
1. 路由权限 —— 控制能否访问某个页面
2. 按钮/操作权限 —— 控制页面内某个操作是否显示、可点
3. 数据权限 —— 控制能看哪些数据（通常靠服务端，前端做展示配合）
4. 字段权限 —— 控制表单/表格的字段可见性
```

```text
权限模型对比：
RBAC —— 基于角色（Role-Based），最简单常用
ABAC —— 基于属性（Attribute-Based），更灵活复杂
ACL —— 访问控制列表，直接对资源挂权限主体
```

```text
// 前端权限数据的典型形态
{
  roles: ['admin', 'editor'],
  permissions: ['user:list', 'user:create', 'user:delete'],  // 权限点/码
  resources: { 'article': ['read', 'write'] }
}
```

前端权限的本质是"按权限数据做条件渲染"，无论模型多复杂，落到代码里都是"拿权限 → 判断 → 显示/隐藏"。

## RBAC

RBAC（Role-Based Access Control）把权限绑定到角色，用户通过拥有角色获得权限。它是前端权限实现的最常用模型。

```text
RBAC 三层关系：
用户（User）→ 角色（Role）→ 权限（Permission）

例：
用户 Alice 拥有角色 admin
角色 admin 拥有权限 user:create、user:delete
则 Alice 能创建、删除用户
```

```js
// 前端基于角色的判断
const user = { roles: ['admin', 'editor'] };

function hasRole(role) {
  return user.roles.includes(role);
}

if (hasRole('admin')) {
  // 显示管理后台入口
}
```

```text
RBAC 的优势与局限：
优势 —— 结构简单，符合直觉，管理成本低（调角色不调人）
局限 —— 角色会膨胀（每个组合一个角色），难以表达细粒度条件

应对局限：
1. 权限点（permission code）下沉一层：角色只是权限点的集合
2. 前端判断用权限码而非角色名，角色变化不影响代码
```

```js
// 更优实践：用权限码判断，而不是硬编码角色名
const user = { permissions: ['user:create', 'user:delete', 'report:view'] };

function hasPermission(code) {
  return user.permissions.includes(code);
}

// 角色名是后端管理概念，前端只认权限码
hasPermission('user:delete');   // true
```

## ABAC 与 ACL

ABAC（Attribute-Based Access Control）按属性（用户属性、资源属性、环境属性）动态计算权限；ACL（Access Control List）直接把权限主体挂到资源上。

```text
ABAC —— 基于属性：
规则形如"资源 owner 是本人，或部门相同，或时间在工作日"时放行
灵活性最高，适合复杂业务规则，但实现和调试成本高

ACL —— 访问控制列表：
每个资源维护一张"谁能访问"的列表
如文件系统里 file.txt → { alice: rw, bob: r }
前端通常由服务端按 ACL 算好结果下发
```

```js
// ABAC 前端示例：根据属性组合判断
function canEditDocument(doc, user, now = new Date()) {
  const isOwner = doc.ownerId === user.id;
  const isSameDept = doc.deptId === user.deptId;
  const isWorkday = now.getDay() >= 1 && now.getDay() <= 5;
  return isOwner || (isSameDept && isWorkday);
}
```

```text
前端落地建议：
1. RBAC 为主，覆盖 90% 场景
2. 复杂条件用 ABAC 思路在前端写纯函数判断，服务端做最终裁决
3. ACL 通常由服务端计算，前端拿到的是"该资源我可否操作"的结果
```

```js
// ACL 结果下发的典型形态：服务端已算好，前端直接消费
const doc = {
  id: 1,
  title: '方案文档',
  _acl: { canEdit: true, canDelete: false, canShare: true }
};
```

## Permission Tree

权限树是把权限按"模块 → 菜单 → 操作"组织成树形结构，常见于管理后台的权限配置界面，也是前端渲染权限选择器的基础数据。

```text
权限树结构：
系统管理
├── 用户管理
│   ├── 查看用户（user:list）
│   ├── 新建用户（user:create）
│   └── 删除用户（user:delete）
└── 角色管理
    ├── 查看角色（role:list）
    └── 分配权限（role:assign）
```

```js
// 权限树数据 + 前端勾选回显
const permissionTree = [
  {
    id: 'sys', name: '系统管理',
    children: [
      { id: 'user', name: '用户管理', children: [
        { id: 'user:list', name: '查看用户' },
        { id: 'user:create', name: '新建用户' },
        { id: 'user:delete', name: '删除用户' },
      ]},
    ],
  },
];

// 勾选状态与权限码互相转换
function collectCheckedCodes(tree, checkedIds) {
  const codes = [];
  const walk = (nodes) => nodes.forEach(n => {
    if (n.children) walk(n.children);
    else if (checkedIds.has(n.id)) codes.push(n.id);
  });
  walk(tree);
  return codes;
}
```

```text
权限树的两个用途：
1. 配置侧 —— 管理员在树上勾选，决定角色拥有哪些权限
2. 展示侧 —— 前端把后端返回的权限树渲染成选择器/展示组件

前端拿到的是树结构，判断权限时通常拍平成 code 集合。
```

## Resource Permission

资源权限指"对某个具体资源（对象）能做哪些操作"，把操作（增删改查）绑定到资源标识上，是权限码的一种组织方式。

```text
资源权限的编码规范：resource:action
article:read、article:create、article:update、article:delete
user:list、user:import、user:export
report:view、report:download
```

```js
// 前端集中定义资源操作，配合权限码判断
const permissions = {
  article: ['read', 'create', 'update', 'delete'],
  user: ['list', 'create', 'delete'],
  report: ['view', 'download'],
};

function has(resource, action) {
  const code = `${resource}:${action}`;
  return user.permissions.includes(code);
}

has('article', 'update');   // true/false
```

```text
资源权限的设计要点：
1. 命名统一（resource:action），避免 create/add/new 混用
2. 前后端共用同一套权限码，后端据码鉴权，前端据码渲染
3. 支持通配（article:*）时明确匹配规则
```

## Route Permission

路由权限控制"能否进入某个页面"，通过路由守卫 + 路由 meta 实现，是前端权限的第一道门。

```js
// 路由配置里声明所需权限
const routes = [
  {
    path: '/users',
    component: UserList,
    meta: { permission: 'user:list', title: '用户管理' }
  },
  {
    path: '/reports',
    component: ReportPage,
    meta: { roles: ['admin'], title: '报表中心' }   // 也支持按角色
  },
];
```

```js
// 全局路由守卫校验权限
router.beforeEach((to, from, next) => {
  const { permission, roles } = to.meta;
  if (!permission && !roles) return next();   // 公开页面

  const ok = permission
    ? hasPermission(permission)
    : roles.some(r => user.roles.includes(r));

  ok ? next() : next('/403');   // 无权限跳 403
});
```

```text
动态路由（更细的方案）：
登录后拉取用户可访问的菜单/路由列表，前端动态 addRoute 注册，
用户根本"看不到"无权路由，比静态 meta 拦截更彻底。
```

```js
// 动态路由：根据后端返回的菜单生成可访问路由
async function buildRoutes() {
  const menus = await fetch('/api/user/menus').then(r => r.json());
  const routes = menus.map(m => ({
    path: m.path,
    component: () => import(`@/views/${m.component}`),
    meta: { title: m.title }
  }));
  routes.forEach(r => router.addRoute(r));
}
```

## Button Permission

按钮权限是页面内的细粒度控制：同样的页面，不同用户看到的操作按钮不同。核心是"权限指令/组件"封装。

```js
// 自定义指令 v-permission：无权限则移除元素
import { createApp } from 'vue';

const app = createApp(App);
app.directive('permission', {
  mounted(el, binding) {
    const code = binding.value;
    if (!hasPermission(code)) {
      el.parentNode?.removeChild(el);   // 无权限直接移除
    }
  }
});
```

```html
<!-- 使用：仅拥有 user:delete 权限的用户才看到删除按钮 -->
<button v-permission="'user:delete'">删除</button>
<button v-permission="'user:create'">新建</button>
```

```js
// React 版：权限组件
function Permission({ code, children }) {
  return hasPermission(code) ? children : null;
}

<Permission code="user:delete">
  <button>删除</button>
</Permission>
```

```text
按钮权限的实现要点：
1. 用指令/组件封装，避免散落 if 判断
2. 无权限时优先"不渲染"，而不是"禁用"（禁用仍暴露功能存在）
3. 按钮隐藏只是体验优化，服务端仍必须校验操作权限
```

## Data Permission

数据权限控制"能看哪些数据"，比如普通用户只能看自己部门的数据，管理员能看全部。这层几乎由服务端裁决，前端做的是传递上下文和按返回结果展示。

```text
数据权限的常见维度：
1. 本人 —— 只能看自己创建的数据
2. 本部门 —— 看自己部门的数据
3. 本部门及以下 —— 看本部门和子部门的数据
4. 全部 —— 看所有数据
```

```js
// 前端请求时带上数据范围上下文（服务端据此过滤）
async function fetchOrders() {
  const res = await fetch('/api/orders', {
    headers: { Authorization: `Bearer ${token}` }
  });
  // 服务端根据当前用户的 dataScope 过滤后返回
  return res.json();
}
```

```text
数据权限的落地：
1. 过滤逻辑在服务端（SQL 层加 where），前端不能靠隐藏实现数据隔离
2. 前端展示上：数据范围决定列表/下拉选项的内容
3. 前端可能拿到的 dataScope 标记，用于展示"当前可见范围"提示
```

```js
// 前端拿到 dataScope 后做展示配合
const user = { dataScope: 'dept' };   // 本部门

const scopeLabel = {
  self: '仅本人数据',
  dept: '本部门数据',
  dept_and_child: '本部门及下级数据',
  all: '全部数据',
}[user.dataScope];

showBanner(`当前可见范围：${scopeLabel}`);
```

## 应用场景实战

### 场景一：管理后台完整权限链路

```js
// 登录后一次拉取用户信息 + 权限码集合
const auth = {
  async load() {
    const { user, permissions, menus } = await fetch('/api/auth/init').then(r => r.json());
    store.user = user;
    store.permissions = new Set(permissions);
    store.menus = menus;
  }
};

// 统一判断入口
export function hasPermission(code) {
  return store.permissions.has(code) || store.permissions.has('*');
}
```

```js
// 菜单/路由按权限动态生成
function buildMenu(menus) {
  return menus
    .filter(m => !m.permission || hasPermission(m.permission))
    .map(m => ({
      ...m,
      children: m.children ? buildMenu(m.children) : []
    }));
}
```

### 场景二：按钮 + 字段级权限的组合使用

```html
<!-- 表单：只读字段 vs 可编辑字段按权限渲染 -->
<form>
  <input v-model="form.name" :disabled="!can('user:update')" />
  <input v-model="form.salary" v-if="can('user:salary:view')" :disabled="!can('user:salary:edit')" />

  <button v-if="can('user:create')" type="submit">保存</button>
  <button v-if="can('user:delete')" type="button">删除</button>
</form>
```

```js
function can(code) {
  return hasPermission(code);
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 前端判断用权限码而非硬编码角色名，角色调整不牵动代码
2. 路由、按钮、字段三层权限用统一的 hasPermission 入口，判断逻辑集中
3. 无权限优先"不渲染"而非"禁用"，减少暴露面
4. 权限码前后端共用一套，后端鉴权、前端渲染一一对应
5. 动态路由按后端菜单生成，让用户看不见无权页面
6. 数据权限的过滤必须落在服务端，前端隐藏只是体验优化

### 踩坑记录

```text
坑 1：只在前端做权限控制
结论：攻击者直接调接口绕过前端，越权访问数据。
原因：前端权限只是 UI 隐藏，不是安全边界。
解法：服务端对所有接口做鉴权，前端权限仅用于体验。

坑 2：硬编码角色名判断
结论：角色改名或拆分后前端到处报错。
原因：if (role === 'admin') 散落在代码各处。
解法：改用权限码 hasPermission(code)，角色由后端映射成权限码。

坑 3：按钮禁用代替隐藏
结论：无权限用户能看到按钮，猜测功能存在并尝试绕过。
原因：用 disabled 而非移除元素。
解法：无权限直接不渲染按钮，配合服务端校验。

坑 4：动态路由与静态路由混用导致白屏
结论：刷新页面后动态路由丢失，直接 404 或白屏。
原因：动态 addRoute 只在登录后执行，刷新时路由表还没建好。
解法：启动时先恢复路由再挂载，或路由持久化后同步注册。

坑 5：权限码前后端不一致
结论：前端显示了按钮，后端却拒绝请求，或反之。
原因：前后端权限码命名不统一（create vs add）。
解法：制定统一命名规范 resource:action，用常量共享或文档对齐。
```
