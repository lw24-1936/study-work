## 概述

可访问性测试（Accessibility Testing）验证网页是否对所有用户可用，包括残障用户（视觉、听觉、运动、认知障碍）。它贯穿自动化检测与人工测试，目标是符合 WCAG 标准。

```text
可访问性测试的三个层次：
1. 自动化检测 —— axe、Lighthouse（能发现约 30-50% 的问题）
2. 人工测试 —— 键盘、屏幕阅读器、对比度（覆盖自动化盲区）
3. 合规审计 —— WCAG 标准逐条核对（A/AA/AAA 等级）
```

## axe 自动检测

axe（axe-core）是最流行的可访问性自动化检测引擎，能发现大量结构性、语义性问题。

```js
// 在浏览器中运行 axe
import axe from 'axe-core';

axe.run(document).then(results => {
  results.violations.forEach(v => {
    console.log(v.id, v.help);        // 违规项
    console.log(v.impact);            // 严重程度（critical/serious/moderate/minor）
    console.log(v.nodes);             // 涉及的 DOM 节点
  });
});
```

```js
// 配合测试框架（jest-axe）
import { axe } from 'jest-axe';

it('组件无可访问性违规', async () => {
  const { container } = render(<MyComponent />);
  const results = await axe(container);
  expect(results).toHaveNoViolations();
});
```

```text
axe 能检测的问题类型：
1. 图片缺 alt
2. 表单缺 label
3. 颜色对比度不足
4. 按钮缺可访问名称
5. ARIA 属性误用
6. 标题层级跳级

注意：自动化只能覆盖部分问题，仍需人工补充测试。
```

## Lighthouse Accessibility 审计

Lighthouse 的 Accessibility 审计内置了可访问性检查，给出 0-100 评分。

```js
// 用 Lighthouse 审计
import lighthouse from 'lighthouse';

const result = await lighthouse(url, { onlyCategories: ['accessibility'] });
const a11yScore = result.lhr.categories.accessibility.score;   // 0-1
const audits = result.lhr.audits;                              // 各审计项详情
```

```text
Lighthouse Accessibility 审计项：
1. 图片 alt 属性
2. 对比度
3. 表单 label
4. 链接可辨识名称
5. 标题顺序
6. ARIA 使用

评分 90+ 为良好，100 为满分。
```

## Keyboard Test 键盘测试

键盘测试验证页面完全可用键盘操作，这是可访问性最基础的测试。

```text
键盘测试要点：
1. Tab —— 焦点顺序是否符合逻辑（从左到右、从上到下）
2. Shift+Tab —— 反向移动
3. Enter / Space —— 激活按钮、链接
4. Esc —— 关闭弹窗、菜单
5. 方向键 —— 菜单、选项卡、下拉导航

核心问题：
1. 焦点陷阱 —— 焦点被卡住无法离开
2. 焦点丢失 —— 操作后焦点消失
3. 不可聚焦 —— 交互元素无法用键盘到达
```

```js
// 自动化键盘测试（Testing Library）
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

it('Tab 键可以聚焦到按钮', async () => {
  render(<Form />);
  const user = userEvent.setup();
  await user.tab();                    // Tab 到第一个元素
  expect(screen.getByRole('button')).toHaveFocus();
});
```

## Screen Reader 屏幕阅读器测试

屏幕阅读器测试验证内容能被正确朗读（NVDA、VoiceOver、JAWS）。

```text
主流屏幕阅读器：
NVDA（Windows，免费）、VoiceOver（macOS/iOS）、JAWS（Windows，商业）

测试要点：
1. 语义标签是否正确朗读（按钮、链接、标题）
2. 图片 alt 是否朗读
3. 动态内容更新是否被通知（aria-live）
4. 表单 label 是否关联
```

```html
<!-- 屏幕阅读器友好的语义 -->
<button aria-label="关闭对话框">×</button>

<img src="logo.png" alt="公司 Logo">

<div aria-live="polite">搜索到 10 条结果</div>
```

## Focus Test 焦点测试

焦点测试验证焦点可见性、焦点顺序、焦点管理。

```css
/* 焦点必须可见（focus visible） */
button:focus-visible {
  outline: 2px solid #0066cc;
  outline-offset: 2px;
}
```

```text
焦点测试要点：
1. 焦点可见 —— 所有交互元素有清晰的焦点指示
2. 焦点顺序 —— 符合视觉顺序
3. 焦点管理 —— 弹窗打开后焦点移入，关闭后焦点返回
4. 无焦点陷阱 —— 焦点能自由进出
```

```js
// 弹窗焦点管理
function openModal() {
  modal.showModal();
  modal.querySelector('button').focus();   // 焦点移入
}
function closeModal() {
  modal.close();
  triggerButton.focus();                   // 焦点返回触发按钮
}
```

## Contrast Test 对比度测试

对比度测试验证文字与背景的对比度是否达标（WCAG 要求）。

```text
WCAG 对比度要求：
正常文本 —— 对比度 ≥ 4.5:1（AA）、≥ 7:1（AAA）
大文本（18pt+/14pt 粗体）—— ≥ 3:1（AA）、≥ 4.5:1（AAA）
图形/图标 —— ≥ 3:1

工具：axe 自动检测、浏览器 DevTools 取色器、对比度计算器。
```

```js
// 计算对比度
function contrastRatio(rgb1, rgb2) {
  const lum = ([r, g, b]) => {
    const [rs, gs, bs] = [r, g, b].map(v => {
      v /= 255;
      return v <= 0.03928 ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4);
    });
    return 0.2126 * rs + 0.7152 * gs + 0.0722 * bs;
  };
  const l1 = lum(rgb1), l2 = lum(rgb2);
  const [light, dark] = l1 > l2 ? [l1, l2] : [l2, l1];
  return (light + 0.05) / (dark + 0.05);
}

contrastRatio([255, 255, 255], [0, 102, 204]);   // 对比度值
```

## ARIA Test ARIA 测试

ARIA 测试验证 ARIA 属性的正确使用（角色、状态、属性）。

```text
ARIA 测试要点：
1. 角色（role）是否正确
2. 状态（aria-expanded、aria-checked）是否同步
3. 属性（aria-label、aria-describedby）是否指向存在的元素
4. 不要用 ARIA 替代原生语义（能用原生就别用 ARIA）
```

```html
<!-- ARIA 使用示例 -->
<button aria-expanded="false" aria-controls="menu">菜单</button>
<div id="menu" role="menu">
  <button role="menuitem">选项 1</button>
</div>
```

```text
ARIA 的规则：
1. 首选原生 HTML 语义（button、nav、main）
2. ARIA 仅在原生无法表达时使用
3. 角色正确、状态同步、引用有效
```

## WCAG Audit 合规审计

WCAG（Web Content Accessibility Guidelines）是可访问性的国际标准，分 A、AA、AAA 三级。

```text
WCAG 四大原则（POUR）：
Perceivable（可感知）—— 内容能被感知（alt、对比度、字幕）
Operable（可操作）—— 可键盘操作、有足够时间
Understandable（可理解）—— 内容清晰、可预测
Robust（健壮）—— 兼容各种辅助技术

合规等级：
A —— 最低要求
AA —— 标准要求（多数组织目标）
AAA —— 最高要求（难以完全达到）
```

```text
WCAG 审计流程：
1. 确定目标等级（通常 AA）
2. 逐条核对标准（约 50 条成功标准）
3. 自动化 + 人工测试结合
4. 记录问题、修复、复测
5. 输出合规报告（VPAT/ACR）
```

## 应用场景实战

### 场景一：CI 中集成可访问性自动检测

```js
// jest-axe 接入测试套件，每次提交自动检测
import { render } from '@testing-library/react';
import { axe, toHaveNoViolations } from 'jest-axe';

expect.extend(toHaveNoViolations);

it('表单组件无可访问性违规', async () => {
  const { container } = render(<LoginForm />);
  const results = await axe(container);
  expect(results).toHaveNoViolations();
});
```

### 场景二：键盘可达性回归测试

```js
// 验证 Tab 顺序和 Enter 激活
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

it('Tab 聚焦到按钮并用 Enter 激活', async () => {
  const user = userEvent.setup();
  render(<Dialog />);

  await user.tab();                      // Tab 到关闭按钮
  expect(screen.getByRole('button', { name: '关闭' })).toHaveFocus();

  await user.keyboard('{Enter}');        // Enter 激活
  expect(screen.queryByRole('dialog')).not.toBeInTheDocument();
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 开发阶段就接入 axe，CI 中自动化检测
2. 自动化 + 人工（键盘、屏幕阅读器）结合，自动化只覆盖部分
3. 焦点可见性用 :focus-visible，别移除 outline
4. 对比度达标是底线，设计时就要考虑
5. 语义优先：能用原生 HTML 就别用 ARIA

### 踩坑记录

```text
坑 1：只做自动化测试
结论：自动化全绿，但实际仍有可访问性问题。
原因：axe 等只能检测约 30-50% 的问题，键盘/屏幕阅读器需人工。
解法：自动化 + 人工测试结合。

坑 2：移除 outline 导致焦点不可见
结论：为了美观 outline: none，键盘用户无法感知焦点。
原因：移除了焦点指示。
解法：用 :focus-visible 保留焦点样式。

坑 3：ARIA 滥用
结论：乱加 role/aria 反而破坏可访问性。
原因：ARIA 用错比不用更糟（如给 div 加 role=button 但不处理键盘）。
解法：首选原生语义，ARIA 仅补充。

坑 4：对比度只测一种状态
结论：hover/disabled 状态的对比度被忽略。
原因：只测了默认状态。
解法：所有状态（hover、focus、disabled、active）都测对比度。

坑 5：动态内容未通知屏幕阅读器
结论：新增的搜索结果、通知，屏幕阅读器用户不知道。
原因：动态更新未用 aria-live。
解法：动态区域加 aria-live="polite"。
```
