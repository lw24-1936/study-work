## 概述

CD（Continuous Deployment / Continuous Delivery，持续部署/持续交付）把 CI 产出的构建产物自动推送到目标环境，让「代码合并」到「用户可见」之间零人工干预。对前端而言，CD 的本质就是把静态产物或容器镜像，可靠、可回滚地交付到服务器、Kubernetes 或 CDN。

```text
CD 的核心价值：
1. 自动化 —— 合并即部署，不需要手动上传文件
2. 可回滚 —— 每次发布都有版本，一键回到上一个稳定版
3. 一致性 —— 用同一份产物部署到所有环境，杜绝「我本地能跑」
4. 可追踪 —— 每次发布都关联到具体的 commit 和构建记录
5. 降低风险 —— 小步快跑，配合灰度/金丝雀把影响面控到最小
```

```yaml
# CD 与 CI 的分工：CI 产出产物，CD 负责分发
# CI 阶段：npm ci -> lint -> test -> build -> upload artifact
# CD 阶段：download artifact -> 上传 CDN / 推镜像 / 滚动更新
name: CD
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: dist
          path: dist
      - run: aws s3 sync dist/ s3://my-bucket/ --delete
```

## Deployment

Deployment（部署）是把构建产物发布到运行环境的动作。对前端，它可以是「把 dist 目录上传到静态服务器」，也可以是「把新镜像推到集群滚动更新」。一次可靠的部署要回答三个问题：部署什么（产物）、部署到哪（环境）、怎么验证（健康检查）。

```bash
# 最朴素的前端部署：rsync 同步 dist 到远端服务器
rsync -avz --delete \
  -e "ssh -i ~/.ssh/deploy.pem" \
  ./dist/ user@server:/var/www/app/

# 或直接用 scp 上传
scp -r ./dist/* user@server:/var/www/app/
```

```text
一次典型部署的完整链路：
1. 取产物 —— 从 CI artifact / 镜像仓库拿到待发布版本
2. 传目标 —— 上传静态文件 / 推送镜像 / 触发平台部署
3. 切流量 —— 更新路由、滚动更新 Pod、切换 CDN 源
4. 验证 —— 健康检查、冒烟测试、监控告警确认
5. 记录 —— 记录版本号、commit、发布时间，方便回滚
```

## Artifact

Artifact（构建产物）是 CD 流通的「货币」。CI 构建完把产物作为不可变的一次性快照存起来，CD 再原样取用，保证「测试的就是发布的」。前端产物通常是 dist 目录压缩包，或封装成 Docker 镜像。

```yaml
# CI 上传产物，供 CD 复用
- uses: actions/upload-artifact@v4
  with:
    name: dist
    path: dist/
    retention-days: 7

# CD 下载同一份产物，保证发布的就是测试通过的
- uses: actions/download-artifact@v4
  with:
    name: dist
    path: dist
```

```text
Artifact 的要点：
1. 不可变 —— 构建一次，到处复用，不重复构建
2. 带版本 —— 用 commit hash / 构建号命名，可追溯可回滚
3. 短时留存 —— 产物临时保存，长期归档靠镜像仓库或对象存储
4. 可校验 —— 记录 checksum，防止传输过程中被篡改或损坏
```

## Docker

Docker 把应用和它的运行环境打包成镜像，让「环境差异」不再是部署问题。前端用 Docker 的场景通常是：把构建产物放进 Nginx 镜像，得到一个自包含、可移植的部署单元，交给 Kubernetes 或任意容器平台运行。

```dockerfile
# 前端应用镜像：Nginx 托管静态产物
FROM nginx:1.27-alpine
COPY dist/ /usr/share/nginx/html/
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
```

```bash
# 构建并推送镜像到仓库
docker build -t registry.example.com/my-app:v1.2.3 .
docker push registry.example.com/my-app:v1.2.3

# 本地跑起来验证
docker run -p 8080:80 registry.example.com/my-app:v1.2.3
```

```text
Docker 在 CD 中的角色：
1. 封装 —— 把产物 + Web 服务器 + 配置打包成一个镜像
2. 版本 —— 镜像 tag 就是发布版本，天然可回滚
3. 可移植 —— 本地、测试、生产跑同一个镜像
4. 隔离 —— 应用之间互不干扰，资源可控
```

## Kubernetes

Kubernetes 是容器编排平台，负责调度、扩容、自愈、滚动更新。对前端而言，Kubernetes 的价值在于「声明式」：你声明期望的副本数、镜像版本、资源配额，K8s 自动把集群收敛到期望状态，发布就是改镜像 tag。

```yaml
# 声明式部署：把镜像版本从 v1.2.2 升到 v1.2.3 即完成一次发布
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
        - name: frontend
          image: registry.example.com/my-app:v1.2.3
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /healthz
              port: 80
```

```text
Kubernetes 发布相关的核心能力：
1. Deployment —— 声明副本数和镜像版本，滚动更新
2. Service —— 稳定的集群内访问入口，负载均衡到 Pod
3. Ingress —— 对外暴露 HTTP 路由，域名 + 路径转发
4. 滚动更新 —— 逐个替换 Pod，不中断服务
5. 回滚 —— kubectl rollout undo 一键退回上一版本
```

## CDN

CDN（Content Delivery Network，内容分发网络）把静态资源缓存到离用户最近的边缘节点，解决「物理距离带来的延迟」。前端的 JS/CSS/图片几乎全部走 CDN，因此「上传到 CDN」往往是前端 CD 的最后一步。

```bash
# 上传产物到对象存储（CDN 源站），并失效缓存
aws s3 sync dist/ s3://my-bucket/ --delete --cache-control "max-age=31536000, immutable"
aws cloudfront create-invalidation --distribution-id E12345 --paths "/*"
```

```text
CDN 在 CD 中的要点：
1. 缓存分层 —— 带 hash 的资源长缓存，index.html 短缓存或不缓存
2. 缓存失效 —— 发布后主动失效旧缓存，避免用户拿到旧版本
3. 就近访问 —— 边缘节点缓存，回源仅首次请求
4. 原子切换 —— 源站更新 + 失效要在同一发布流程内完成
```

## Static Hosting

Static Hosting（静态托管）是纯前端项目最主流的部署形态：把构建产物托管在对象存储、静态站点平台或 Nginx 上，无需自建应用服务器。GitHub Pages、Vercel、Netlify、Cloudflare Pages 都是静态托管服务，它们把 CD 做到了「推送即发布」。

```bash
# Vercel / Netlify 风格：连接 Git 仓库，push 即自动构建部署
# vercel.json 声明路由和重写规则
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }],
  "headers": [
    {
      "source": "/assets/(.*)",
      "headers": [{ "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }]
    }
  ]
}
```

```text
静态托管的优势：
1. 零运维 —— 不需要管理服务器、装运行时、打补丁
2. 高可用 —— 平台自带 CDN 和冗余，天然扛流量
3. 成本低 —— 按流量计费甚至免费额度够用
4. 快 —— 静态文件 + CDN 缓存，首屏加载极快
```

## 应用场景实战

### 场景一：GitHub Actions 一键部署到对象存储 + CDN

```yaml
# .github/workflows/deploy.yml —— 合并 main 即自动发布到 S3 + CloudFront
name: Deploy
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm run build

      # 带 hash 的静态资源长缓存，index.html 短缓存
      - name: Sync to S3
        run: |
          aws s3 sync dist/assets s3://my-bucket/assets --delete \
            --cache-control "public, max-age=31536000, immutable"
          aws s3 sync dist s3://my-bucket --delete --exclude "assets/*" \
            --cache-control "public, max-age=0, must-revalidate"

      - name: Invalidate CDN
        run: aws cloudfront create-invalidation --distribution-id ${{ secrets.CF_ID }} --paths "/*"
```

### 场景二：镜像推送到 K8s 集群并滚动更新

```yaml
# .github/workflows/deploy-k8s.yml —— 构建镜像并滚动更新 Deployment
name: Deploy to K8s
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build

      - name: Build & push image
        run: |
          docker build -t registry.example.com/my-app:${{ github.sha }} .
          docker push registry.example.com/my-app:${{ github.sha }}

      - name: Rolling update
        run: |
          kubectl set image deployment/frontend \
            frontend=registry.example.com/my-app:${{ github.sha }}
          kubectl rollout status deployment/frontend
```

## 最佳实践与踩坑记录

### 最佳实践

1. 产物只构建一次，用 artifact 或镜像在 CI/CD 之间传递，绝不重复构建
2. 镜像 tag 用 commit hash 而非 latest，保证可追溯、可回滚
3. 带 hash 的静态资源设 immutable 长缓存，index.html 设短缓存或 no-cache
4. 发布流程内置健康检查和冒烟测试，验证通过才算成功
5. 每次发布记录版本号和 commit，回滚按钮必须始终可用
6. 用 --delete 同步静态文件，清理掉已经下线的旧资源

### 踩坑记录

```text
坑 1：镜像用 latest 标签发布
结论：无法确定线上跑的是哪个版本，回滚时无据可依。
原因：latest 是可变标签，每次都指向最新镜像，历史版本不可追溯。
解法：镜像 tag 一律用 commit hash 或语义化版本，禁止生产用 latest。

坑 2：静态资源没做缓存分层
结论：发布后用户迟迟拿不到新版本，或 index.html 被缓存导致白屏。
原因：所有文件统一长缓存，index.html 更新了但浏览器还在用旧缓存。
解法：hash 资源 immutable 长缓存，index.html 短缓存或 no-cache，发布后失效 CDN。

坑 3：CD 每次重复构建
结论：测试通过的产物和发布的产物不是同一份，可能出现「测过却挂了」。
原因：CD 阶段重新 npm run build，依赖或环境差异导致产物不同。
解法：CI 构建一次并上传 artifact，CD 只下载并分发，不重新构建。

坑 4：滚动更新没有 readinessProbe
结论：新 Pod 还没起来就被切流量，用户看到 502。
原因：K8s 默认认为容器启动即就绪，但应用可能还没监听端口。
解法：配置 readinessProbe 做健康检查，就绪后才接入 Service 流量。

坑 5：静态托管没有 history fallback
结论：用户刷新子路由（如 /about）直接 404。
原因：静态托管平台默认按文件路径查找，找不到 /about 对应的文件。
解法：配置 rewrite 把未知路径回退到 index.html，交给前端路由处理。
```
