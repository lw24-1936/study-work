## 概述

Deployment Strategy（部署策略）决定「新版本如何替换旧版本」，核心目标是在发布过程中控制风险、减少停机、快速回滚。不同的策略在「切换速度」「资源成本」「风险暴露面」之间做权衡：有的瞬时切换、有的渐进放量、有的先让流量双跑验证。

```text
部署策略的核心权衡：
1. 停机时间 —— 切换过程中服务是否可用
2. 风险暴露 —— 新版本出问题时影响多少用户
3. 资源成本 —— 是否需要双倍实例、额外环境
4. 回滚速度 —— 出问题后多久能退回旧版本
5. 验证能力 —— 切换前能否先验证新版本是否正确
```

```text
策略速览：
1. Rolling —— 逐个替换实例，零停机但过程较长
2. Blue Green —— 新旧两套环境瞬时切换，成本高回滚快
3. Canary —— 小比例流量先放新版本，逐步扩大
4. Shadow —— 复制真实流量到新版本但不返回结果，只验证
5. Feature Flag —— 代码里用开关控制，运行时按用户切特性
6. Rollback —— 所有策略的兜底，一键退回旧版本
```

## Rolling

Rolling（滚动更新）是 Kubernetes 默认的发布方式：逐个用新版本 Pod 替换旧版本 Pod，直到全部替换完成。整个过程零停机，但新旧版本会短暂共存，期间用户可能同时访问到两个版本。

```yaml
# Kubernetes Deployment 的滚动更新配置
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1   # 最多允许 1 个 Pod 不可用
      maxSurge: 1         # 最多多创建 1 个 Pod
  template:
    spec:
      containers:
        - name: frontend
          image: registry.example.com/my-app:v1.2.3
```

```text
Rolling 的特点：
1. 零停机 —— 始终保持足够副本对外服务
2. 渐进 —— 一个一个换，出问题影响有限
3. 共存 —— 切换期间新旧版本并存，需保证兼容
4. 耗时 —— 实例越多，完成发布的时间越长
```

## Blue Green

Blue Green（蓝绿部署）同时维护两套完整环境：Blue 是当前生产版本，Green 是全新部署的新版本。验证通过后，把流量入口（DNS、负载均衡、Service）一次性切到 Green。切换是瞬时的，回滚只需切回 Blue。

```yaml
# 蓝绿部署：两套 Deployment，通过 Service selector 瞬时切换流量
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-blue
spec:
  replicas: 3
  selector:
    matchLabels: { app: frontend, version: blue }
  template:
    metadata:
      labels: { app: frontend, version: blue }
    spec:
      containers:
        - name: frontend
          image: registry.example.com/my-app:v1.2.2
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-green
spec:
  replicas: 3
  selector:
    matchLabels: { app: frontend, version: green }
  template:
    metadata:
      labels: { app: frontend, version: green }
    spec:
      containers:
        - name: frontend
          image: registry.example.com/my-app:v1.2.3
```

```bash
# 流量切换：Service 的 selector 从 blue 改成 green
kubectl patch service frontend -p '{"spec":{"selector":{"app":"frontend","version":"green"}}}'
```

```text
Blue Green 的特点：
1. 瞬时切换 —— 流量一次切完，没有渐进过程
2. 回滚快 —— 切回 Blue 即可，秒级回滚
3. 成本高 —— 需要两倍资源，两套环境常驻
4. 适合 —— 大版本、数据库结构变更等需要整体切换的场景
```

## Canary

Canary（金丝雀发布）先让一小部分用户（如 5%）访问新版本，观察指标正常后逐步放大比例，直到 100%。它把「风险」限制在极小范围内，是灰度发布的一种典型实现。

```yaml
# 金丝雀：Ingress 按权重把流量分到新旧两个 Service
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "5"
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-canary
                port: { number: 80 }
```

```text
Canary 的放量节奏：
1. 5% —— 观察错误率、延迟、业务指标
2. 20% —— 指标正常继续放大
3. 50% —— 接近全量前再确认一轮
4. 100% —— 全部切新版本，回收旧版本
```

```text
Canary 的特点：
1. 风险可控 —— 出问题只影响小比例用户
2. 渐进验证 —— 用真实流量逐步验证新版本
3. 需要指标 —— 必须有可观测性支撑，否则无法判断好坏
4. 周期较长 —— 从 5% 到 100% 需要持续观察，发布变慢
```

## Shadow

Shadow（影子发布 / 流量镜像）把生产流量复制一份打到新版本，但只记录新版本的响应和指标，不返回给用户。用户始终只看到旧版本，新版本却在「真实流量」下接受验证，适合做性能和正确性的预演。

```yaml
# 流量镜像：把打到 stable 的请求复制一份发给 shadow 版本
apiVersion: v1
kind: Service
metadata:
  name: frontend-stable
spec:
  selector: { app: frontend, version: stable }
  ports:
    - port: 80
---
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: frontend
spec:
  hosts:
    - frontend
  http:
    - route:
        - destination:
            host: frontend-stable
      mirror:
        host: frontend-shadow
      mirrorPercentage:
        value: 100.0
```

```text
Shadow 的特点：
1. 零风险 —— 用户永远只看到旧版本结果
2. 真实负载 —— 用真实流量验证新版本性能和行为
3. 只读验证 —— 适合读接口和性能压测，写操作需谨慎
4. 资源翻倍 —— 新版本要完整处理一份流量，但不对外服务
```

## Feature Flag

Feature Flag（特性开关）把「部署」和「发布」解耦：代码先全部部署上去，但新功能默认关闭，通过开关按用户、按百分比逐步打开。它让发布变成「改一个配置」，而不是「发一次版本」，回滚就是关掉开关。

```js
// 前端用开关控制新功能是否对用户可见
const flags = await fetch('/api/flags').then(r => r.json());

if (flags['new-checkout']) {
  renderNewCheckout();
} else {
  renderOldCheckout();
}
```

```text
Feature Flag 的要点：
1. 部署 != 发布 —— 代码上线但功能未开启
2. 精准放量 —— 按用户 id、地域、百分比控制可见性
3. 秒级回滚 —— 关闭开关即回退，无需重新部署
4. 债务 —— 长期未清理的开关会累积成技术债，需定期下线
```

## Rollback

Rollback（回滚）是所有部署策略的兜底：当新版本出现问题时，快速把系统恢复到上一个已知稳定的版本。回滚的关键在于「保留旧版本」——无论镜像、产物还是环境，都要在发布时留好后路。

```bash
# Kubernetes 回滚到上一个版本
kubectl rollout undo deployment/frontend

# 回滚到指定历史版本
kubectl rollout undo deployment/frontend --to-revision=3

# 查看历史版本
kubectl rollout history deployment/frontend
```

```text
回滚的前提条件：
1. 版本留存 —— 旧镜像/旧产物必须仍然可用，没被删除
2. 数据库兼容 —— 回滚代码不能破坏新版本写入的数据
3. 配置同步 —— 回滚时相关配置、环境变量也要一起退回
4. 快 —— 回滚路径必须经过演练，几分钟内完成
```

## 应用场景实战

### 场景一：前端金丝雀发布 + 自动回滚

```yaml
# 用 ingress-nginx 金丝雀注解做按比例灰度
# 先给 canary Service 5% 流量，观察后调权重
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "5"
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-canary
                port: { number: 80 }
```

```bash
# 观察错误率，异常时一键回滚
kubectl rollout undo deployment/frontend-canary
```

### 场景二：蓝绿部署一个前端版本

```yaml
# 蓝绿：先部署 Green 验证，再瞬时切流量
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-green
spec:
  replicas: 3
  selector:
    matchLabels: { app: frontend, version: green }
  template:
    metadata:
      labels: { app: frontend, version: green }
    spec:
      containers:
        - name: frontend
          image: registry.example.com/my-app:v2.0.0
```

```bash
# Green 验证通过后，把 Service 指向 green
kubectl patch service frontend -p '{"spec":{"selector":{"app":"frontend","version":"green"}}}'
# 出问题随时切回 blue
kubectl patch service frontend -p '{"spec":{"selector":{"app":"frontend","version":"blue"}}}'
```

## 最佳实践与踩坑记录

### 最佳实践

1. 默认用滚动更新，风险较高的大版本再用蓝绿或金丝雀
2. 金丝雀必须配合可观测性，没有指标就无法判断该放量还是回滚
3. 每次发布保留至少上一个稳定版本，回滚路径要提前演练
4. 用 Feature Flag 把部署和发布解耦，让特性开启成为独立的轻量操作
5. 数据库变更采用「先加后删」的兼容策略，保证代码可安全回滚
6. 新旧版本共存期间保证接口和缓存兼容，避免切换期间出现脏数据

### 踩坑记录

```text
坑 1：金丝雀发布但没有任何监控指标
结论：放量变成拍脑袋，新版本的问题在 100% 时才爆发。
原因：没有错误率、延迟、转化率等指标，无法判断金丝雀是否健康。
解法：接入可观测性，设好告警阈值，指标异常立即停止放量并回滚。

坑 2：滚动更新期间新旧版本缓存不兼容
结论：切换期间部分用户看到新页面、部分看到旧页面，甚至报错。
原因：新旧版本对缓存 key、接口字段约定不一致，共存时互相污染。
解法：发布时保证向后兼容，缓存 key 带版本，共存窗口尽量缩短。

坑 3：回滚时数据库结构没退回
结论：代码退回旧版本，但数据表已经加了新字段，回滚后依然报错。
原因：只回滚了应用，没有考虑数据库 schema 的兼容性。
解法：数据库变更采用 expand-contract 模式，先加字段后删字段，保证双向兼容。

坑 4：蓝绿切换没做会话保持
结论：长连接或登录态用户在切换瞬间被断开，被迫重新登录。
原因：切换流量时没有考虑已有会话的连续性。
解法：切换前评估会话/连接影响，必要时结合滚动更新平滑过渡。

坑 5：Feature Flag 上线后从不清理
结论：代码里堆满永不关闭的死开关，逻辑分支爆炸难以维护。
原因：功能稳定后没有移除开关，开关成了永久技术债。
解法：开关设生命周期，功能稳定后定时清理，保持代码整洁。
```
