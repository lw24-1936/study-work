## 概述

CI（Continuous Integration，持续集成）让每次代码提交都自动触发构建、检查、测试，把「合并前才发现问题」变成「提交后立刻发现问题」。对前端而言，CI 是工程质量的第一道闸门：格式、类型、单测、构建、安全扫描全部在合并前自动跑一遍。

```text
CI 的核心价值：
1. 早发现 —— 提交即检查，问题不过夜
2. 自动化 —— 格式/类型/测试/构建全部流水线化
3. 一致性 —— 本地环境差异不影响构建结果
4. 可追溯 —— 每次提交都有对应的构建产物和日志
5. 门槛 —— 检查不过不允许合并
```

```yaml
# 一个最小 CI 流水线的骨架
name: CI
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build
```

## GitHub Actions

GitHub Actions 是 GitHub 内置的 CI/CD 服务，用 YAML 声明工作流，按事件触发，跑在托管 runner 上。

```yaml
# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 配置 Node 版本
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'

      # 安装依赖（npm ci 按锁文件确定性安装）
      - run: npm ci

      # 类型检查
      - run: npx tsc --noEmit

      # 单元测试
      - run: npm test -- --coverage

      # 构建
      - run: npm run build
```

```text
GitHub Actions 关键概念：
1. workflow —— .github/workflows/ 下的 YAML 文件
2. job —— 一个独立执行单元，可并行可串行
3. step —— job 内的执行步骤（run 或 uses）
4. runner —— 执行环境（ubuntu/windows/macos 或自托管）
5. action —— 复用单元（checkout/setup-node 等）
6. cache —— actions/cache 缓存 node_modules/构建产物
```

## GitLab CI

GitLab CI 是 GitLab 内置的 CI/CD，用 `.gitlab-ci.yml` 声明流水线，按 stage 组织 job。

```yaml
# .gitlab-ci.yml
image: node:20

stages:
  - install
  - test
  - build

cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/

install:
  stage: install
  script:
    - npm ci

lint:
  stage: test
  script:
    - npm run lint

test:
  stage: test
  script:
    - npm test

build:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - dist/
```

```text
GitLab CI 与 GitHub Actions 的差异：
1. 配置单文件 —— .gitlab-ci.yml 集中管理
2. stage 顺序 —— 显式声明 stages 执行顺序
3. cache 缓存 —— 按 key 缓存，跨 job 共享
4. artifacts 产物 —— 显式声明要保留的构建产物
```

## Jenkins

Jenkins 是自托管的 CI/CD 服务器，插件生态丰富，适合私有化部署和复杂流水线。

```groovy
// Jenkinsfile（声明式流水线）
pipeline {
  agent any

  environment {
    NODE_VERSION = '20'
  }

  stages {
    stage('Install') {
      steps {
        sh 'npm ci'
      }
    }
    stage('Lint') {
      steps {
        sh 'npm run lint'
      }
    }
    stage('Test') {
      steps {
        sh 'npm test'
      }
    }
    stage('Build') {
      steps {
        sh 'npm run build'
      }
    }
  }

  post {
    always {
      junit 'test-results.xml'
    }
  }
}
```

```text
Jenkins 的特点：
1. 自托管 —— 自己管理服务器和 runner
2. 插件多 —— 2000+ 插件覆盖各种集成
3. 灵活 —— 声明式 + 脚本式两种流水线
4. 成本 —— 需要维护服务器，适合有私有化需求的团队
```

## Build

Build 是 CI 的核心环节：把源码编译成可部署产物，验证代码能正常构建。

```yaml
- run: npm run build
# 生产构建，输出到 dist/，失败即阻断合并
```

```text
前端构建的关键检查点：
1. 构建成功 —— 语法、依赖、打包全部通过
2. 产物存在 —— dist/ 输出存在且非空
3. 产物大小 —— 记录 bundle 体积，防止失控
4. 类型通过 —— TS 项目 tsc --noEmit 通过
```

## Lint

Lint 在 CI 里做静态检查，统一代码风格、提前发现低级错误。

```yaml
- run: npm run lint
# ESLint + Prettier + Stylelint，失败即阻断
```

```json
// package.json 里的 lint 脚本
{
  "scripts": {
    "lint": "eslint src --ext .ts,.tsx --max-warnings 0",
    "lint:style": "stylelint 'src/**/*.css'",
    "format:check": "prettier --check src"
  }
}
```

```text
Lint 在 CI 里的要点：
1. --max-warnings 0 —— 警告也算失败，避免警告累积
2. 只检查改动文件 —— 大型仓库全量 lint 太慢
3. 与本地一致 —— CI 的 lint 规则必须和本地完全一致
```

## Test

Test 是 CI 的门槛：单元测试、集成测试在合并前必须全绿。

```yaml
- run: npm test -- --coverage
```

```js
// 配合覆盖率门槛
// jest.config.js
module.exports = {
  coverageThreshold: {
    global: {
      lines: 80,
      statements: 80,
    },
  },
};
```

```text
CI 测试策略：
1. 单元测试 —— 每次提交都跑，秒级
2. 覆盖率门槛 —— 低于阈值阻断合并
3. 分层 —— 单测快跑，E2E 慢跑（可单独 job）
4. 失败留痕 —— 上传测试报告和截图
```

## Security Scan

Security Scan 在 CI 里扫描依赖漏洞，防止供应链攻击。

```yaml
# 依赖安全审计
- run: npm audit --audit-level=high
# 高严重度漏洞阻断合并

# 或用 Snyk/Trivy 等专业工具
- run: npx snyk test
```

```text
前端安全扫描关注点：
1. 依赖漏洞 —— npm audit / Snyk / Dependabot
2. 许可证合规 —— 检查依赖 License 是否合规
3. 密钥泄漏 —— 扫描代码里误提交的密钥/token
4. SBOM —— 生成软件物料清单，追溯组件来源
```

## 应用场景实战

### 场景一：完整前端 CI 流水线

```yaml
# .github/workflows/ci.yml —— 一个完整可用的前端 CI
name: CI

on:
  push:
    branches: [main, develop]
  pull_request:

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npx tsc --noEmit
      - run: npm test -- --coverage
      - run: npm audit --audit-level=high

  build:
    runs-on: ubuntu-latest
    needs: quality
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
```

### 场景二：Monorepo 受影响包定向测试

```yaml
# 大型 Monorepo 只测受影响的包，加速 CI
- name: Build affected
  run: npx nx affected:test --base=origin/main
# Nx 计算依赖图，只跑被本次改动影响的包的测试
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 npm ci 而非 npm install，保证按锁文件确定性安装
2. 缓存 node_modules 和构建产物，加速流水线
3. lint/typecheck/unit test 全部设为零容忍门槛
4. 构建产物用 artifact 上传，供后续 CD 复用
5. 关键检查并行跑，缩短反馈时间
6. 依赖安全审计接入流水线，高危漏洞阻断合并

### 踩坑记录

```text
坑 1：CI 用 npm install 导致依赖漂移
结论：CI 构建结果和本地不一致，出现「本地好好的 CI 挂了」。
原因：npm install 会按 package.json 范围重新解析依赖，可能装到新版本。
解法：CI 一律用 npm ci（或 pnpm install --frozen-lockfile），按锁文件确定性安装。

坑 2：不缓存依赖导致流水线超慢
结论：每次 CI 都全量装依赖，耗时数分钟甚至超时。
原因：没有缓存 node_modules，重复下载。
解法：用 setup-node 的 cache 或 actions/cache 缓存 node_modules/构建产物。

坑 3：lint 警告被放过导致累积
结论：代码里警告越来越多，最终无法清理。
原因：lint 命令没有 --max-warnings 0，警告不阻断。
解法：lint 加 --max-warnings 0，警告即失败，从源头杜绝累积。

坑 4：类型检查没进 CI
结论：合并后才发现类型错误，生产构建失败。
原因：只跑了 lint 和 test，漏了 tsc --noEmit。
解法：TS 项目 CI 必加 tsc --noEmit，作为独立步骤。

坑 5：E2E 测试和单测混在一个 job
结论：流水线又慢又脆，一个 E2E 失败拖垮整个 CI。
原因：快慢测试混跑，互相阻塞。
解法：单测快 job、E2E 慢 job 分开，可并行可独立重跑。
```
