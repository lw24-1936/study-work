## 概述

设计模式是解决常见设计问题的可复用方案，在前端里它们大多不以「类继承」形式出现，而是藏在框架 API 和日常代码里：Vue 的响应式是 Observer，React Hook 是闭包化的 Factory，ES6 Proxy 是原生的 Proxy。掌握它们不是为了背名字，而是识别问题、找到对应解法。

```text
前端最常见的十二种设计模式：
1. Factory —— 工厂，封装对象创建
2. Singleton —— 单例，全局唯一实例
3. Adapter —— 适配器，接口转换
4. Decorator —— 装饰器，动态扩展能力
5. Proxy —— 代理，访问控制与拦截
6. Observer —— 观察者，变化通知
7. Strategy —— 策略，算法可替换
8. Command —— 命令，请求封装为对象
9. State —— 状态，状态驱动行为
10. Facade —— 外观，简化接口
11. Composite —— 组合，树形结构统一处理
12. Builder —— 建造者，分步构建复杂对象
```

```js
// 设计模式就是「把变化的点隔离起来」
// 创建变化用 Factory，行为变化用 Strategy，结构变化用 Adapter
const patterns = {
  creation: ['Factory', 'Singleton', 'Builder'],
  behavior: ['Observer', 'Strategy', 'Command', 'State'],
  structure: ['Adapter', 'Decorator', 'Proxy', 'Facade', 'Composite'],
};
```

## Factory

Factory（工厂模式）把对象创建集中到一个工厂函数里，调用方不需要知道具体类或创建细节。前端的 Factory 常以「工厂函数」形式出现——React 的自定义 Hook 就是工厂：每次调用返回一套独立的状态和方法。

```text
Factory 的关键点：
1. 封装创建 —— 隐藏具体类型和创建细节
2. 统一入口 —— 调用方通过工厂拿对象
3. 便于扩展 —— 新增类型只改工厂
4. 前端形态 —— 工厂函数、自定义 Hook
```

```js
// 工厂函数：根据类型创建不同的通知对象
function createNotification(type) {
  switch (type) {
    case 'email': return { send: (msg) => console.log('邮件:', msg) };
    case 'sms': return { send: (msg) => console.log('短信:', msg) };
    case 'push': return { send: (msg) => console.log('推送:', msg) };
    default: throw new Error('未知类型');
  }
}

const notifier = createNotification('email');
notifier.send('订单已发货');
```

React 的 `useState`、`useReducer` 本质都是工厂——每次调用生成一份独立的状态实例。

## Singleton

Singleton（单例模式）保证一个类全局只有一个实例，并提供全局访问点。前端里常用于全局状态、事件总线、日志器、SDK 实例——需要「全局唯一」的东西。实现上可以用闭包或模块导出单例。

```text
Singleton 的关键点：
1. 全局唯一 —— 整个应用一个实例
2. 全局访问 —— 统一入口获取
3. 共享状态 —— 单例常承载共享状态
4. 模块即单例 —— ES Module 天然单例
```

```js
// 闭包实现单例事件总线
const EventBus = (function () {
  let instance;
  function create() {
    return { listeners: new Map() };
  }
  return {
    getInstance() {
      if (!instance) instance = create();
      return instance;
    },
  };
})();

const bus1 = EventBus.getInstance();
const bus2 = EventBus.getInstance();
console.log(bus1 === bus2); // true
```

```js
// ES Module 天然单例：模块只加载一次
// logger.js
export const logger = { logs: [], info(msg) { this.logs.push(msg); } };
// 任何文件 import { logger } 拿到的都是同一实例
```

单例要警惕全局状态滥用：单例本身没问题，但把什么都塞进单例会制造隐式耦合。

## Adapter

Adapter（适配器模式）把不兼容的接口转换成调用方期望的接口，让原本不能一起工作的对象能协作。前端的典型场景是「统一多端 API 差异」——把不同第三方库、不同后端的接口适配成统一形状。

```text
Adapter 的关键点：
1. 接口转换 —— 把 A 接口转成 B 接口
2. 兼容差异 —— 抹平不同实现的差异
3. 不修改原对象 —— 包一层适配
4. 前端场景 —— 统一存储、统一请求、统一事件
```

```js
// 适配器：统一不同存储的 API
const localStorageAdapter = {
  get(key) { return localStorage.getItem(key); },
  set(key, val) { localStorage.setItem(key, val); },
};
const sessionStorageAdapter = {
  get(key) { return sessionStorage.getItem(key); },
  set(key, val) { sessionStorage.setItem(key, val); },
};

// 业务代码统一用 store 接口，不关心底层是哪种存储
const store = localStorageAdapter;
store.set('theme', 'dark');
store.get('theme');
```

适配器让业务代码依赖统一接口，底层实现（local/session/IndexedDB）可自由替换。

## Decorator

Decorator（装饰器模式）在不修改原对象的前提下，动态地给对象增加额外行为。前端的装饰器常见于高阶组件（HOC）、高阶函数、装饰器语法——给组件包一层日志、权限、埋点，原组件不变。

```text
Decorator 的关键点：
1. 动态扩展 —— 运行时给对象加行为
2. 不修改原对象 —— 包装而非改动
3. 可叠加 —— 多个装饰器层层包裹
4. 前端形态 —— HOC、装饰器、高阶函数
```

```js
// 装饰器：给函数加日志，不改原函数
function withLogging(fn) {
  return function (...args) {
    console.log('调用参数:', args);
    const result = fn.apply(this, args);
    console.log('返回结果:', result);
    return result;
  };
}

function add(a, b) { return a + b; }
const loggedAdd = withLogging(add);
loggedAdd(1, 2);
```

```js
// React 高阶组件（HOC）：给组件加权限装饰
function withAuth(Component) {
  return function AuthWrapper(props) {
    if (!props.isLogin) return <div>请先登录</div>;
    return <Component {...props} />;
  };
}
```

装饰器和代理的区别：装饰器增强「功能」，代理控制「访问」。

## Proxy

Proxy（代理模式）在访问目标对象时加一层拦截，控制访问、做校验、做缓存、做懒加载。ES6 原生支持 Proxy，Vue 3 的响应式就是基于 Proxy 实现的——拦截属性读写，实现依赖收集和触发更新。

```text
Proxy 的关键点：
1. 访问拦截 —— 拦截属性读写、函数调用
2. 控制访问 —— 校验、权限、缓存
3. 透明 —— 调用方无感知
4. 前端场景 —— 响应式、防抖代理、缓存代理
```

```js
// ES6 Proxy 实现属性访问校验
const user = { name: 'Alice', age: 25 };

const proxy = new Proxy(user, {
  get(target, key) {
    console.log(`读取 ${key}`);
    return target[key];
  },
  set(target, key, value) {
    if (key === 'age' && (value < 0 || value > 150)) {
      throw new Error('年龄不合法');
    }
    target[key] = value;
    return true;
  },
});

proxy.age = 30;  // 合法
proxy.age = -1;  // 抛错：年龄不合法
```

Vue 3 的 `reactive` 就是 Proxy 模式在响应式系统里的应用——拦截读写来追踪依赖。

## Observer

Observer（观察者模式）定义一对多的依赖关系：被观察对象状态变化时，自动通知所有观察者。它是前端使用最广的模式——DOM 事件、Vue 响应式、RxJS、Redux 订阅都是它的变体。

```text
Observer 的关键点：
1. 一对多 —— 一个被观察者，多个观察者
2. 自动通知 —— 状态变化主动推送
3. 解耦 —— 被观察者不关心观察者是谁
4. 前端场景 —— 事件、响应式、状态订阅
```

```js
// 观察者模式：主题 + 订阅/通知
class Subject {
  constructor() { this.observers = []; }
  subscribe(fn) { this.observers.push(fn); return () => {
    this.observers = this.observers.filter(o => o !== fn);
  }; }
  notify(data) { this.observers.forEach(fn => fn(data)); }
}

const store = new Subject();
const unsubscribe = store.subscribe((state) => console.log('状态更新:', state));
store.notify({ count: 1 });
unsubscribe();
```

观察者和发布订阅（Pub/Sub）的区别：观察者是被观察者直接通知，发布订阅中间多了个事件中心。

## Strategy

Strategy（策略模式）把一组可互换的算法各自封装成独立策略，运行时按需选择，避免大量 if-else 分支。前端典型场景：表单校验策略、支付方式选择、不同平台的登录策略。

```text
Strategy 的关键点：
1. 算法族 —— 一组可互换的策略
2. 独立封装 —— 每个策略各自独立
3. 运行时可换 —— 按条件选择策略
4. 消除分支 —— 用策略表替换 if-else
```

```js
// 策略模式：支付方式可替换
const payStrategies = {
  alipay(amount) { console.log(`支付宝支付 ${amount}`); },
  wechat(amount) { console.log(`微信支付 ${amount}`); },
  card(amount) { console.log(`银行卡支付 ${amount}`); },
};

function pay(method, amount) {
  const strategy = payStrategies[method];
  if (!strategy) throw new Error('不支持的支付方式');
  strategy(amount);
}

pay('alipay', 99);
```

策略模式把「选择逻辑」和「具体算法」分离，新增策略只需加一项，不用改判断逻辑。

## Command

Command（命令模式）把请求封装成独立对象，支持参数化、排队、撤销、重放。前端的典型场景：编辑器撤销/重做、按钮命令队列、宏命令。命令对象记录「要做什么」，让操作变得可管理。

```text
Command 的关键点：
1. 请求封装 —— 把操作封装成命令对象
2. 可撤销 —— 命令可反向执行
3. 可排队 —— 命令进队列延迟执行
4. 前端场景 —— 撤销/重做、命令队列
```

```js
// 命令模式：文本编辑器的撤销/重做
class TextEditor {
  constructor() { this.text = ''; this.history = []; this.redoStack = []; }
  execute(command) {
    this.text = command.execute(this.text);
    this.history.push(command);
    this.redoStack = [];
  }
  undo() {
    const cmd = this.history.pop();
    if (cmd) { this.text = cmd.undo(this.text); this.redoStack.push(cmd); }
  }
}

const insertCommand = (str) => ({
  execute: (text) => text + str,
  undo: (text) => text.slice(0, text.length - str.length),
});

const editor = new TextEditor();
editor.execute(insertCommand('你好'));
editor.execute(insertCommand('世界'));
editor.undo(); // 文本回到 "你好"
```

命令模式把「执行」和「撤销」成对封装，撤销/重做、宏命令、异步队列都靠它。

## State

State（状态模式）让对象在不同状态下表现出不同行为，状态变化时行为也随之变化，且状态切换逻辑内聚在状态对象里。前端典型场景：订单状态机、播放器状态、Promise 的三态。

```text
State 的关键点：
1. 状态驱动 —— 行为随状态变化
2. 切换内聚 —— 状态转换逻辑集中
3. 消除分支 —— 用状态对象替代 if-else
4. 前端场景 —— 状态机、播放器、请求三态
```

```js
// 状态模式：播放器状态机
const playerStates = {
  stopped: {
    play() { console.log('开始播放'); return 'playing'; },
    stop() { console.log('已经停止'); return 'stopped'; },
  },
  playing: {
    play() { console.log('已在播放'); return 'playing'; },
    stop() { console.log('暂停播放'); return 'stopped'; },
  },
};

class Player {
  constructor() { this.state = 'stopped'; }
  transition(action) {
    this.state = playerStates[this.state][action]();
  }
}

const player = new Player();
player.transition('play');  // 开始播放 → playing
player.transition('stop');  // 暂停播放 → stopped
```

状态模式把「每种状态下做什么、能切到哪」集中管理，复杂状态机（订单流转）尤其受益。

## Facade

Facade（外观模式）提供一个简化的统一接口，隐藏底层子系统的复杂性。前端典型场景：把复杂的浏览器 API 封装成简单函数，把多个库的调用收敛成一个入口。它降低使用门槛，也隔离了底层变化。

```text
Facade 的关键点：
1. 统一入口 —— 一个简单接口面对调用方
2. 隐藏复杂 —— 屏蔽底层细节
3. 降低耦合 —— 调用方不直接碰子系统
4. 前端场景 —— API 封装、工具函数收敛
```

```js
// 外观模式：封装复杂的存储操作
const storageFacade = {
  save(key, value) {
    const data = JSON.stringify(value);        // 序列化
    localStorage.setItem(key, data);           // 写入
    this.log(`saved ${key}`);                  // 日志
  },
  load(key) {
    const raw = localStorage.getItem(key);
    return raw ? JSON.parse(raw) : null;       // 反序列化 + 容错
  },
  log(msg) { console.log(msg); },
};

storageFacade.save('user', { name: 'Alice' }); // 调用方只面对简单接口
storageFacade.load('user');
```

Facade 和 Adapter 的区别：Facade 简化接口、屏蔽复杂，Adapter 转换接口、抹平差异。

## Composite

Composite（组合模式）把对象组织成树形结构，让「单个对象」和「对象组合」能被统一处理。前端最典型的应用是 DOM 树和 React 组件树——父组件和子组件、叶子组件用同一套接口递归渲染。

```text
Composite 的关键点：
1. 树形结构 —— 整体与部分层次
2. 统一接口 —— 叶子和组合一致处理
3. 递归 —— 组合里包含组合
4. 前端场景 —— DOM 树、组件树、菜单树
```

```js
// 组合模式：菜单树统一渲染
class MenuItem { // 叶子
  constructor(name) { this.name = name; }
  render() { return `<li>${this.name}</li>`; }
}

class MenuGroup { // 组合
  constructor(name) { this.name = name; this.children = []; }
  add(child) { this.children.push(child); return this; }
  render() {
    const items = this.children.map(c => c.render()).join('');
    return `<li>${this.name}<ul>${items}</ul></li>`;
  }
}

const file = new MenuItem('新建文件');
const edit = new MenuGroup('编辑').add(new MenuItem('复制')).add(new MenuItem('粘贴'));
const menu = new MenuGroup('菜单').add(file).add(edit);
// 叶子和组合都调用 render()，统一递归
```

React 组件树是 Composite 的最佳范本：组件可以包含组件，渲染递归统一。

## Builder

Builder（建造者模式）把复杂对象的构建过程分解成多个步骤，分步设置、最后产出对象。前端典型场景：复杂请求配置、图表配置、URL 构造——需要很多可选参数的对象。链式调用是它的常见形态。

```text
Builder 的关键点：
1. 分步构建 —— 一步步设置，最后产出
2. 链式调用 —— 可读性好
3. 处理可选参数 —— 不必一次传全部
4. 前端场景 —— 请求配置、URL、图表配置
```

```js
// 建造者模式：链式构造请求配置
class RequestBuilder {
  constructor() {
    this.options = { method: 'GET', headers: {}, timeout: 10000 };
  }
  method(m) { this.options.method = m; return this; }
  header(key, value) { this.options.headers[key] = value; return this; }
  body(data) { this.options.body = JSON.stringify(data); return this; }
  build() { return this.options; }
}

const config = new RequestBuilder()
  .method('POST')
  .header('Content-Type', 'application/json')
  .body({ name: 'Alice' })
  .build();

fetch('/api/users', config);
```

Builder 适合「可选参数多、构建步骤明确」的对象，比塞一堆参数的构造函数清晰得多。

## 应用场景实战

### 场景一：表单校验（策略 + 组合）

```js
// 校验规则用策略封装，规则可自由组合
const validators = {
  required: (v) => (v ? null : '必填'),
  email: (v) => (/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(v) ? null : '邮箱格式错误'),
  minLen: (n) => (v) => (v.length >= n ? null : `至少 ${n} 个字符`),
};

function validate(value, rules) {
  for (const rule of rules) {
    const error = rule(value);
    if (error) return error;
  }
  return null;
}

const error = validate('', [validators.required, validators.email]);
console.log(error); // 必填
```

### 场景二：可撤销的编辑操作（命令模式）

```js
// 命令模式实现撤销/重做，编辑操作可回退
class Editor {
  constructor() { this.value = ''; this.undoStack = []; this.redoStack = []; }
  apply(cmd) {
    this.value = cmd.do(this.value);
    this.undoStack.push(cmd);
    this.redoStack = [];
  }
  undo() {
    const cmd = this.undoStack.pop();
    if (cmd) { this.value = cmd.undo(this.value); this.redoStack.push(cmd); }
  }
  redo() {
    const cmd = this.redoStack.pop();
    if (cmd) { this.value = cmd.do(this.value); this.undoStack.push(cmd); }
  }
}

const append = (text) => ({
  do: (v) => v + text,
  undo: (v) => v.slice(0, v.length - text.length),
});

const ed = new Editor();
ed.apply(append('A'));
ed.apply(append('B'));
ed.undo(); // "A"
ed.redo(); // "AB"
```

## 最佳实践与踩坑记录

### 最佳实践

1. 消除大片 if-else 用策略模式，把判断换成策略表
2. 全局唯一资源（事件总线、SDK）用单例，但别把业务状态都塞进单例
3. 统一第三方库/多端接口差异用适配器，业务代码只依赖统一接口
4. 撤销/重做、命令队列用命令模式，把执行和回退成对封装
5. 复杂状态流转用状态模式建状态机，别用嵌套 if-else
6. 按「创建、行为、结构」三类识别问题，别为了用模式而用模式

### 踩坑记录

```text
坑 1：单例滥用导致隐式耦合
结论：全局单例被到处引用，改一处牵动全局。
原因：把业务状态塞进单例，单例变成全局可变状态。
解法：单例只放无状态服务（日志、总线），业务状态走状态管理。

坑 2：观察者忘记取消订阅
结论：组件卸载后订阅还在，触发时操作已销毁的 DOM，内存泄漏。
原因：subscribe 后没在清理时机取消订阅。
解法：订阅返回取消函数，组件卸载时调用（useEffect cleanup）。

坑 3：策略模式键名写错静默失败
结论：传了未定义的支付方式，静默不执行也不报错。
原因：策略表取不到对应函数，直接 undefined 调用。
解法：取不到策略时抛错或走默认策略，别静默吞掉。

坑 4：装饰器层层包裹难调试
结论：组件被十几个 HOC 包裹，排查问题要一层层扒。
原因：装饰器滥用，每个关注点都包一层。
解法：装饰器克制使用，优先用 Hook/组合替代，保留必要的分层。

坑 5：状态模式状态无限膨胀
结论：状态机状态越加越多，切换逻辑纠缠不清。
原因：没提前梳理状态和迁移表，随需求硬加状态。
解法：先画状态迁移图，明确状态和事件，再实现，避免临时加状态。
```
