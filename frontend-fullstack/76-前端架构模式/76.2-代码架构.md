## 概述

代码架构解决「代码怎么组织、职责怎么划分」的问题，让项目可维护、可测试、可扩展。经典 MV* 系列（MVC/MVVM/MVP）解决 UI 层的数据流，Clean Architecture 和 Hexagonal 解决业务与外部依赖的解耦，Feature Sliced 和 Layered 解决大规模代码的分层组织。核心目标都是「改动一处，不影响全局」。

```text
七种代码架构模式：
1. MVC —— 模型-视图-控制器
2. MVVM —— 模型-视图-视图模型
3. MVP —— 模型-视图-表现层
4. Clean Architecture —— 依赖指向核心的同心圆
5. Hexagonal Architecture —— 端口与适配器
6. Feature Sliced Design —— 按业务功能切片
7. Layered Architecture —— 分层架构
```

```js
// 架构的共同目标：分层解耦，依赖单向，核心不依赖细节
// 好的架构让「业务规则」不依赖「框架、UI、数据库」
function isGoodArch(dep) {
  return dep.direction === 'inward'; // 依赖指向核心
}
```

## MVC

MVC（Model-View-Controller）把应用分成三块：Model 管数据和业务逻辑，View 管展示，Controller 管输入和协调。它是 UI 架构的鼻祖，后端框架大量采用，前端早期（Backbone.js）也是它。缺点是 Controller 容易膨胀成「上帝对象」。

```text
MVC 的关键点：
1. Model —— 数据 + 业务逻辑
2. View —— 展示，观察 Model 变化
3. Controller —— 接收输入，更新 Model
4. 观察者模式 —— View 订阅 Model 更新
```

```js
// 前端 MVC（Backbone 风格）
const Model = {
  data: { count: 0 },
  listeners: [],
  increment() {
    this.data.count++;
    this.listeners.forEach(fn => fn(this.data)); // 通知 View
  },
};

const View = {
  render(model) {
    document.querySelector('#count').textContent = model.count;
  },
  bind(controller) {
    document.querySelector('#btn').onclick = () => controller.onIncrement();
  },
};

const Controller = {
  onIncrement() {
    Model.increment(); // Controller 更新 Model
  },
};

Model.listeners.push(data => View.render(data));
View.bind(Controller);
```

MVC 的问题在于 Controller 和 View 职责容易混，复杂交互下 Controller 越写越肥。

## MVVM

MVVM（Model-View-ViewModel）在 Model 和 View 之间加一个 ViewModel：它持有 View 需要的展示状态，并通过「双向绑定」让 View 和 ViewModel 自动同步。View 不直接碰 Model，ViewModel 也不碰 DOM。Vue、Angular 都是 MVVM 实现。

```text
MVVM 的关键点：
1. Model —— 数据 + 业务逻辑
2. ViewModel —— 展示状态 + 命令，暴露给 View
3. View —— 声明式绑定，不写同步逻辑
4. 双向绑定 —— View 和 ViewModel 自动同步
```

```js
// Vue 的 MVVM：ViewModel 用 data + methods，View 用模板绑定
const vm = new Vue({
  data() {
    return { count: 0 };          // ViewModel 状态
  },
  methods: {
    increment() { this.count++; }, // ViewModel 命令
  },
  template: `
    <button @click="increment">{{ count }}</button>
  `,
});
```

MVVM 用框架的响应式系统消掉了手动同步 DOM 的样板代码，是现代前端的主流范式。

## MVP

MVP（Model-View-Presenter）把 MVC 的 Controller 换成 Presenter：Presenter 完全掌控 View，View 只负责展示、不碰业务逻辑，所有交互都转发给 Presenter 处理。View 和 Presenter 通过接口解耦，便于单元测试。

```text
MVP 的关键点：
1. Presenter 主导 —— 所有逻辑在 Presenter
2. View 被动 —— 只渲染，转发用户输入
3. 接口解耦 —— View 通过接口与 Presenter 通信
4. 易测试 —— Presenter 可脱离 View 测试
```

```js
// MVP：View 只转发输入，Presenter 决策
class View {
  constructor(presenter) {
    this.presenter = presenter;
    document.querySelector('#btn').onclick = () => this.presenter.onIncrement();
  }
  render(count) {
    document.querySelector('#count').textContent = count;
  }
}

class Presenter {
  constructor(model, view) {
    this.model = model;
    this.view = view;
  }
  onIncrement() {
    this.model.count++;
    this.view.render(this.model.count); // Presenter 决定渲染什么
  }
}
```

MVP 的 Presenter 职责清晰、易测，代价是 Presenter 和 View 之间的接口代码比 MVVM 多。

## Clean Architecture

Clean Architecture（整洁架构）用同心圆表达依赖规则：核心是业务实体，向外依次是用例、接口适配器、框架和外部设备，依赖永远指向内层。它让业务逻辑不依赖框架、数据库、UI，可以独立测试和替换。

```text
Clean Architecture 的关键点：
1. 依赖向内 —— 外层依赖内层，内层不依赖外层
2. 核心是实体 —— 业务实体在最内层
3. 用例层 —— 应用业务规则
4. 适配器层 —— 把框架/DB/UI 隔离在外
```

```text
Clean Architecture 的同心圆（由内到外）：
1. Entities —— 业务实体
2. Use Cases —— 应用用例
3. Interface Adapters —— 控制器、网关、展示器
4. Frameworks & Drivers —— 框架、数据库、UI
依赖只能从外层指向内层，禁止反向。
```

```js
// Clean Architecture：业务用例不依赖具体存储
// 内层：用例，依赖抽象接口而非具体实现
class CreateOrder {
  constructor(orderRepository) { // 依赖抽象
    this.repo = orderRepository;
  }
  async execute(order) {
    if (!order.isValid()) throw new Error('订单无效');
    return this.repo.save(order); // 通过接口保存
  }
}
```

Clean Architecture 适合业务复杂、需要长期演进的项目，代价是抽象层多、初期代码量偏大。

## Hexagonal Architecture

Hexagonal Architecture（六边形架构，也叫端口与适配器）把应用核心放在六边形中心，通过「端口」定义对外接口，「适配器」实现端口对接外部世界（HTTP、数据库、消息队列）。它强调核心逻辑与外部 I/O 完全隔离，换掉数据库或框架不影响核心。

```text
Hexagonal Architecture 的关键点：
1. 端口 —— 核心定义的抽象接口
2. 适配器 —— 端口的具体实现
3. 驱动侧 —— 输入（HTTP、CLI、测试）
4. 被驱动侧 —— 输出（数据库、外部 API）
```

```js
// 六边形架构：核心通过端口与适配器交互
// 端口：核心定义的接口（不依赖具体实现）
class UserService {
  constructor(userPort) {  // 端口（抽象）
    this.userPort = userPort;
  }
  async register(email) {
    return this.userPort.create({ email }); // 通过端口写
  }
}

// 适配器：端口的实现，可替换
class PostgresUserAdapter {
  async create(user) { return db.insert('users', user); }
}
class MemoryUserAdapter {
  async create(user) { this.store.push(user); return user; }
}
```

Hexagonal 的核心思想「端口与适配器」和 Clean Architecture 一脉相承，都为了「核心不依赖外部」。

## Feature Sliced Design

Feature Sliced Design（FSD，功能切片设计）按「业务功能」而非「技术类型」组织代码：每个功能（feature）独立成切片，内部自己分层，跨功能通过公共 API 通信。它解决的是「按层组织的项目越大越乱」的问题，适合中大型前端。

```text
Feature Sliced Design 的关键点：
1. 按功能切片 —— 每个业务功能一个目录
2. 切片自治 —— 功能内部自己分层
3. 公共 API —— 切片间通过显式 API 通信
4. 依赖可追溯 —— 导入路径即依赖关系
```

```text
FSD 的目录结构：
src/
├── app/          # 应用初始化、路由、全局样式
├── pages/        # 页面组合层
├── features/     # 业务功能切片（如 auth、cart）
│   └── cart/
│       ├── ui/       # 组件
│       ├── model/    # 状态、业务逻辑
│       └── api/      # 数据请求
├── entities/     # 业务实体
└── shared/       # 共享工具、UI kit
```

```js
// 切片通过公共 API 导出，禁止跨切片直接引内部实现
// features/cart/index.js —— 显式导出公共接口
export { CartWidget } from './ui/CartWidget';
export { addToCart } from './model/cart';

// 其他切片只能从公共 API 引入
import { addToCart } from 'features/cart'; // 正确
// import { internalHelper } from 'features/cart/model/helpers'; // 禁止
```

FSD 把「依赖规则」用目录结构和导入约定固化下来，大型前端项目里能显著降低耦合。

## Layered Architecture

Layered Architecture（分层架构）把代码按技术职责分成若干层：表现层、业务层、数据访问层，层与层之间只允许相邻调用、依赖单向。它是最直观的组织方式，但大项目里层边界容易模糊，出现跨层调用。

```text
Layered Architecture 的关键点：
1. 分层 —— 表现 / 业务 / 数据访问
2. 相邻调用 —— 每层只调下一层
3. 依赖单向 —— 上层依赖下层，不反向
4. 边界模糊 —— 大项目易跨层调用
```

```text
分层架构的层次（前端视角）：
1. Presentation Layer —— 组件、UI
2. Application Layer —— 用例、编排
3. Domain Layer —— 业务规则、实体
4. Infrastructure Layer —— API 调用、存储
```

```js
// 分层：表现层不直接碰 API，经由业务层
// infrastructure（数据访问层）
const userApi = {
  async fetchUser(id) { return fetch(`/api/users/${id}`).then(r => r.json()); },
};

// application（业务层）
async function getUserProfile(id) {
  const user = await userApi.fetchUser(id);
  return { ...user, displayName: user.name || '匿名' }; // 业务加工
}

// presentation（表现层）
async function renderProfile(id) {
  const profile = await getUserProfile(id); // 只调业务层
  document.querySelector('#profile').textContent = profile.displayName;
}
```

Layered 适合中小项目快速起步，项目变大后通常演进为 FSD 或 Clean Architecture 来强化边界。

## 应用场景实战

### 场景一：Vue 项目的 MVVM 数据流

```js
// Model 是响应式状态，View 模板绑定，ViewModel 提供命令
import { ref, computed } from 'vue';

function useCart() {
  const items = ref([]);                 // Model
  const total = computed(() =>           // ViewModel 派生状态
    items.value.reduce((s, i) => s + i.price, 0)
  );
  function add(item) { items.value.push(item); } // ViewModel 命令
  return { items, total, add };
}

// View 模板：<button @click="add(item)">加入购物车</button>
//            <span>总计：{{ total }}</span>
```

## 最佳实践与踩坑记录

### 最佳实践

1. UI 数据流用 MVVM（Vue/Angular）或 MVC 变体（React + 单向数据流），别逆框架
2. 业务复杂、需长期演进的项目用 Clean/Hexagonal，核心不依赖框架和数据库
3. 中大型前端按 FSD 切片，用目录和导入约定固化依赖规则
4. 中小项目用分层架构起步，边界模糊了再演进，别过度设计
5. Presenter/ViewModel 里的逻辑保持可脱离 UI 测试
6. 依赖始终指向核心（向内），禁止业务层依赖框架细节

### 踩坑记录

```text
坑 1：Controller/Presenter 膨胀成上帝对象
结论：一个 Controller 里塞了几千行业务逻辑，难以维护。
原因：MVC/MVP 没有严格限制 Controller 职责，逻辑越堆越多。
解法：把业务逻辑下沉到 Model/用例层，Controller 只做编排转发。

坑 2：跨层调用破坏分层
结论：表现层直接调数据库，改了表结构 UI 全崩。
原因：分层架构没守住边界，出现跨层直接调用。
解法：强制相邻层调用，用依赖注入和接口隔离下层实现。

坑 3：FSD 切片间引用内部实现
结论：A 功能引了 B 功能的内部 helper，改 B 导致 A 崩。
原因：切片间没有走公共 API，直接引内部文件。
解法：每个切片只暴露 index 公共 API，用 ESLint 规则禁止跨切片内部引用。

坑 4：Clean Architecture 过度抽象
结论：小项目套 Clean Architecture，抽象层比业务代码还多。
原因：为解耦而解耦，业务简单时抽象是负担。
解法：按项目规模选架构，小项目分层即可，别提前套重架构。

坑 5：MVVM 双向绑定滥用
结论：复杂表单双向绑定互相影响，状态来源难以追踪。
原因：所有字段都双向绑定，数据流变成网状。
解法：表单用单向数据流 + 事件，状态变更显式化，别滥用 v-model 嵌套。
```
