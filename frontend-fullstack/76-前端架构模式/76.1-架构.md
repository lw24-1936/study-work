## 概述

前端架构模式回答「应用怎么被渲染和交付给用户」这个根本问题：是多页跳转还是单页应用，是服务端渲染还是静态生成，是整体还是微前端拆分。没有银弹，每种模式在首屏速度、交互体验、SEO、运维复杂度之间各有取舍，选型要看业务类型和团队能力。

```text
九种前端架构模式：
1. MPA —— 多页应用，传统跳转
2. SPA —— 单页应用，客户端渲染
3. SSR —— 服务端渲染，首屏快、SEO 好
4. SSG —— 静态生成，构建时出 HTML
5. ISR —— 增量静态再生成，静态+按需更新
6. Islands Architecture —— 岛屿架构，静态骨架+交互岛屿
7. Micro Frontend —— 微前端，拆分独立子应用
8. BFF —— 为前端定制的后端层
9. Edge Rendering —— 边缘渲染，就近出 HTML
```

```js
// 架构选型的粗判逻辑
function pickArch(need) {
  if (need.static && !need.dynamic) return 'SSG';
  if (need.seo && need.dynamic) return 'SSR';
  if (need.seo && need.dynamic && need.scale) return 'ISR';
  if (need.appLike && !need.seo) return 'SPA';
  if (need.teamScale) return 'Micro Frontend';
  return 'MPA';
}
```

## MPA

MPA（Multi-Page Application，多页应用）每个页面是独立的 HTML，跳转就是整页刷新。它是最传统的模式，结构简单、SEO 天然友好，但页面切换有白屏、体验割裂，交互重的前端应用逐渐被 SPA 取代。

```text
MPA 的关键点：
1. 每页独立 HTML —— 跳转整页刷新
2. SEO 友好 —— 每个 URL 都是完整页面
3. 简单 —— 无需复杂前端框架
4. 体验割裂 —— 切换有白屏，状态不保留
```

```html
<!-- MPA：两个独立页面，通过 a 标签跳转 -->
<!-- index.html -->
<a href="/about.html">关于我们</a>

<!-- about.html -->
<h1>关于我们</h1>
<a href="/index.html">返回首页</a>
```

MPA 适合内容型网站（门户、官网、文档站），对交互连续性和实时性要求高的应用则不适合。

## SPA

SPA（Single-Page Application，单页应用）只加载一个 HTML，后续所有交互和页面切换都在客户端完成，通过 JS 动态替换视图。它体验流畅、无整页刷新，但首屏要等 JS 下载执行，且对 SEO 不友好（内容靠 JS 渲染）。

```text
SPA 的关键点：
1. 单 HTML —— 一个壳，视图 JS 渲染
2. 客户端路由 —— history API 切换不刷新
3. 体验流畅 —— 无白屏，状态保留
4. 首屏慢 + SEO 差 —— 内容靠 JS 生成
```

```js
// SPA 客户端路由示意
const routes = {
  '/': () => '<h1>首页</h1>',
  '/about': () => '<h1>关于</h1>',
};

function render() {
  const path = location.pathname;
  document.querySelector('#app').innerHTML = routes[path]();
}

window.addEventListener('popstate', render);
// 切换时 history.pushState + render()，不整页刷新
```

SPA 适合后台系统、在线工具这类「应用型」产品，不依赖 SEO、追求交互体验。

## SSR

SSR（Server-Side Rendering，服务端渲染）在服务端把组件渲染成完整 HTML 再发给浏览器，浏览器「秒出内容」，之后再做水合（Hydration）接管交互。它解决了 SPA 首屏慢和 SEO 差的问题，代价是服务端压力和实现复杂度。

```text
SSR 的关键点：
1. 服务端出 HTML —— 首屏快、SEO 好
2. 水合 —— 客户端接管后激活交互
3. 服务端压力 —— 每次请求都要渲染
4. 实现复杂 —— 前后端同构、数据预取
```

```js
// Next.js 的 SSR 页面（服务端渲染 + 数据预取）
export async function getServerSideProps() {
  const data = await fetch('https://api.example.com/data').then(r => r.json());
  return { props: { data } }; // 服务端预取数据，随 HTML 一起下发
}

export default function Page({ data }) {
  return <main>{data.map(d => <div key={d.id}>{d.title}</div>)}</main>;
}
```

SSR 适合需要 SEO 的动态页面（电商详情、新闻内容），但每次请求都渲染，服务端成本高于 SSG。

## SSG

SSG（Static Site Generation，静态生成）在构建时就生成所有页面的 HTML，部署后直接返回静态文件。它首屏最快、SEO 最好、服务端成本最低（就一堆静态文件），但内容在构建时定格，数据更新需要重新构建。

```text
SSG 的关键点：
1. 构建时生成 —— 出静态 HTML 文件
2. 极快 + SEO 好 —— 直接返回静态文件
3. 成本低 —— 静态托管即可
4. 内容定格 —— 更新要重新构建
```

```js
// Next.js 的 SSG：构建时生成静态页
export async function getStaticProps() {
  const posts = await fetch('https://api.example.com/posts').then(r => r.json());
  return { props: { posts } }; // 构建时取一次，生成静态 HTML
}

export default function Blog({ posts }) {
  return <main>{posts.map(p => <article key={p.id}>{p.title}</article>)}</main>;
}
```

SSG 适合内容不常变的页面：博客、文档、营销页。数据频繁变化就不合适，需要 ISR 或 SSR。

## ISR

ISR（Incremental Static Regeneration，增量静态再生成）是 SSG 的升级：构建时生成静态页，但设置重新生成间隔，请求到达时若页面过期，就在后台重新生成并替换。它兼顾静态页的性能和内容的按需更新。

```text
ISR 的关键点：
1. 静态为主 —— 默认返回静态页
2. 按需再生 —— 过期页面后台重建
3. 更新无需全量构建 —— 单个页面独立再生
4. 延迟可见 —— 首次请求可能还是旧内容
```

```js
// Next.js 的 ISR：带 revalidate 的静态页
export async function getStaticProps() {
  const data = await fetch('https://api.example.com/stats').then(r => r.json());
  return { props: { data }, revalidate: 60 }; // 60 秒后过期再生
}

export default function Stats({ data }) {
  return <div>访问量：{data.views}</div>;
}
```

ISR 适合「内容基本静态、但希望定期更新」的页面（排行榜、文章详情），是 SSG 和 SSR 之间的折中。

## Islands Architecture

Islands Architecture（岛屿架构）把页面拆成「静态大海」和「交互岛屿」：绝大部分内容静态渲染，只有少数需要交互的组件（岛屿）才水合加载 JS。它大幅减少客户端 JS 体积，是 Astro 等框架的核心理念。

```text
Islands Architecture 的关键点：
1. 静态骨架 —— 大部分内容零 JS
2. 交互岛屿 —— 只有交互组件水合
3. JS 按需 —— 每个岛屿独立加载
4. 首屏 JS 极小 —— 性能显著提升
```

```astro
---
// Astro 组件：默认静态，交互组件用 client 指令激活
---
<html>
  <body>
    <h1>产品介绍</h1>          <!-- 静态，零 JS -->
    <p>这里是大段静态内容...</p>

    <!-- 只有这个购物车按钮是交互岛屿，独立水合 -->
    <AddToCart client:load />
  </body>
</html>
```

Islands Architecture 适合内容为主、交互零散的页面（营销站、博客、文档），追求极致首屏性能。

## Micro Frontend

Micro Frontend（微前端）把大型前端应用拆成多个可独立开发、独立部署的子应用，再在运行时组合成一个整体。它解决大型团队协作和单体前端的可维护性问题，但引入加载、通信、隔离等新复杂度。

```text
Micro Frontend 的关键点：
1. 独立子应用 —— 各自开发、构建、部署
2. 运行时组合 —— 宿主应用拼装子应用
3. 技术栈无关 —— 子应用可用不同框架
4. 隔离与通信 —— 样式隔离、跨应用通信
```

```js
// 微前端：宿主应用动态加载子应用（Module Federation 示意）
// 宿主配置：声明远程子应用
new ModuleFederationPlugin({
  name: 'host',
  remotes: {
    appCart: 'cart@https://cdn.example.com/cart/remoteEntry.js',
    appUser: 'user@https://cdn.example.com/user/remoteEntry.js',
  },
});

// 运行时加载子应用
const Cart = React.lazy(() => import('appCart/Cart'));
```

微前端适合大型组织、多团队并行开发同一产品，小团队用它反而增加复杂度。

## BFF

BFF（Backend for Frontend，为前端定制后端）在每个前端（Web、移动端、桌面）前面放一个专属的中间层，由它聚合、裁剪、转换后端数据，输出前端直接可用的接口。它让前端不用拼多个后端接口，也让后端通用服务保持纯粹。

```text
BFF 的关键点：
1. 前端专属层 —— 每种客户端一个 BFF
2. 聚合裁剪 —— 拼多个后端接口、裁字段
3. 前端友好 —— 接口形状按前端需求定制
4. 增加一层 —— 多一跳延迟和运维成本
```

```js
// BFF 聚合多个后端接口为一个前端接口
app.get('/api/product-page/:id', async (req, res) => {
  const [product, reviews, similar] = await Promise.all([
    fetch(`https://svc-products/api/${req.params.id}`).then(r => r.json()),
    fetch(`https://svc-reviews/api?product=${req.params.id}`).then(r => r.json()),
    fetch(`https://svc-recs/api/similar/${req.params.id}`).then(r => r.json()),
  ]);
  res.json({ product, reviews, similar }); // 前端一次请求拿全
});
```

BFF 适合多端共用一个后端、接口形状差异大的场景，常与 Serverless/Edge 结合部署。

## Edge Rendering

Edge Rendering（边缘渲染）把渲染放到离用户最近的边缘节点，而不是中心服务器，缩短网络往返、就近出 HTML。它结合 SSR 和 CDN 的优势，让动态页面也能享受到边缘低延迟。

```text
Edge Rendering 的关键点：
1. 边缘就近 —— 渲染节点离用户近
2. 低延迟 —— 减少网络往返
3. 动态 + 边缘 —— 动态页面也能边缘出 HTML
4. 平台依赖 —— 需要边缘平台支持
```

```js
// 边缘渲染（Cloudflare Workers / Vercel Edge 风格）
export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    // 在边缘节点渲染 HTML，就近返回
    const data = await env.KV.get(`page:${url.pathname}`, 'json');
    const html = renderPage(data);
    return new Response(html, {
      headers: { 'content-type': 'text/html' },
    });
  },
};
```

Edge Rendering 适合全球用户、对延迟敏感的动态页面，是 SSR 在 CDN 时代的演进。

## 应用场景实战

### 场景一：博客站（SSG + ISR 结合）

```js
// 静态文章用 SSG，热门榜单用 ISR 定时更新
export async function getStaticProps({ params }) {
  const post = await fetch(`https://api.example.com/posts/${params.slug}`).then(r => r.json());
  return { props: { post } }; // 文章静态生成
}

// 榜单页：带 revalidate，定期后台再生
export async function getStaticProps() {
  const trending = await fetch('https://api.example.com/trending').then(r => r.json());
  return { props: { trending }, revalidate: 300 }; // 5 分钟更新一次
}
```

### 场景二：内容站 + 交互岛屿

```astro
---
// Astro 页面：静态内容 + 局部交互岛屿

<Layout>

    <h1>架构模式详解</h1>
    <p>大段静态教程内容，零 JS 下发...</p>
  </article>

  <!-- 只有评论区是交互岛屿，独立水合加载 JS -->
  <CommentSection client:visible />
</Layout>
```

## 最佳实践与踩坑记录

### 最佳实践

1. 内容站用 SSG/ISR，应用型后台用 SPA，动态 SEO 页面用 SSR
2. 别一上来就微前端，只有多团队并行 + 独立部署需求时才用
3. 多端共享后端、接口形状差异大时引入 BFF，否则直接调后端
4. 内容为主、交互零散的页面用 Islands Architecture，JS 体积能降一个量级
5. 全球用户、延迟敏感的动态页面用 Edge Rendering，就近渲染
6. 选架构先看「SEO 需不需要、内容变不变、团队多大」三个维度

### 踩坑记录

```text
坑 1：SPA 做 SEO 页面
结论：搜索引擎抓不到内容，收录极差。
原因：内容靠 JS 渲染，爬虫拿到的是空壳 HTML。
解法：SEO 页面换 SSR/SSG，或用预渲染、动态渲染补齐。

坑 2：SSR 打满服务端
结论：流量高峰服务端渲染压力大，响应变慢。
原因：每个请求都实时渲染，没有缓存和静态化。
解法：能静态的用 SSG/ISR，SSR 结果加 CDN 缓存。

坑 3：微前端过度拆分
结论：小团队搞微前端，构建、通信、部署复杂度暴涨。
原因：微前端收益（独立部署、团队解耦）在小规模下用不上。
解法：先单体 + 模块化，规模够了再评估微前端。

坑 4：ISR 首次请求还是旧内容
结论：设置了 revalidate，但过期页面第一次访问仍返回旧版。
原因：ISR 是「后台再生」，首次触发时返回旧内容，下次才更新。
解法：可接受延迟就用 ISR；要强一致用 SSR 或 on-demand revalidation。

坑 5：Islands 水合遗漏交互
结论：静态骨架里的按钮点了没反应。
原因：交互组件没加 client 指令，没有被水合。
解法：检查岛屿组件的 client:load / client:visible 指令是否遗漏。
```
