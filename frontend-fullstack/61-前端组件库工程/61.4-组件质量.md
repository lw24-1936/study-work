## 概述

组件库的质量不只是「能跑」，而是「逻辑正确、渲染正确、样式正确、人人可用、体积可控」五个维度。对应五类质量保障手段，层层递进，共同构成组件库的质量门禁。

```text
组件质量的五个维度与手段：
1. Unit Test —— 纯逻辑正确性（工具函数、状态计算）
2. Component Test —— 渲染与交互正确性（挂载、点击、断言 DOM）
3. Visual Test —— 视觉正确性（截图对比防样式回归）
4. Accessibility —— 可访问性（键盘、读屏器、对比度）
5. Bundle Size —— 体积可控（按需引入、无冗余依赖）
```

```text
质量金字塔（越往下越基础、越多）：
        视觉测试（少，最贵）
       可访问性测试（适中）
     组件测试（多）
    单元测试（最多，最便宜）

底层廉价测试铺满，上层昂贵测试覆盖关键路径。
```

## Unit Test

Unit Test（单元测试）测试最小可独立验证的逻辑单元——纯函数、工具方法、状态计算。它不渲染 DOM，运行最快、最稳定，是质量金字塔的底座。

```ts
// formatNumber.ts —— 被测的纯函数
export function formatNumber(n: number, locale = 'zh-CN') {
  return new Intl.NumberFormat(locale).format(n);
}
```

```ts
// formatNumber.test.ts —— 单元测试
import { describe, it, expect } from 'vitest';
import { formatNumber } from './formatNumber';

describe('formatNumber', () => {
  it('中文环境加千分位', () => {
    expect(formatNumber(12345, 'zh-CN')).toBe('12,345');
  });

  it('德文环境用点作千分位', () => {
    expect(formatNumber(12345, 'de-DE')).toBe('12.345');
  });

  it('处理负数', () => {
    expect(formatNumber(-1000, 'zh-CN')).toBe('-1,000');
  });
});
```

```text
单元测试的适用对象：
1. 纯工具函数 —— 格式化、校验、转换
2. 状态机 / reducer —— 输入状态算输出状态
3. 组合逻辑 —— 组件里抽出的计算逻辑

不适用：依赖 DOM 的渲染（交给组件测试）、样式（交给视觉测试）。
```

## Component Test

Component Test（组件测试）在测试环境挂载组件，模拟交互并断言渲染结果。它验证「给定 props 渲染出正确的 DOM、交互后状态正确」。工具链通常是 Vitest/Jest + Testing Library。

```tsx
// Button.test.tsx —— 组件测试
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { Button } from './Button';

test('点击按钮触发 onClick', async () => {
  const onClick = vi.fn();
  render(<Button onClick={onClick}>提交</Button>);

  await userEvent.click(screen.getByRole('button', { name: '提交' }));

  expect(onClick).toHaveBeenCalledTimes(1);
});

test('disabled 状态不可点击', async () => {
  const onClick = vi.fn();
  render(<Button disabled onClick={onClick}>提交</Button>);

  await userEvent.click(screen.getByRole('button', { name: '提交' }));

  expect(onClick).not.toHaveBeenCalled();
});
```

```tsx
// 异步组件测试 —— 等待状态更新
import { render, screen, waitFor } from '@testing-library/react';
import { Select } from './Select';

test('选择后显示选中值', async () => {
  render(<Select options={[{ label: '苹果', value: 'apple' }]} />);

  await userEvent.click(screen.getByRole('combobox'));
  await userEvent.click(screen.getByText('苹果'));

  await waitFor(() => {
    expect(screen.getByText('apple')).toBeInTheDocument();
  });
});
```

```text
组件测试的原则（Testing Library 哲学）：
1. 按用户视角查询 —— getByRole/getByText，而非 getByTestId
2. 模拟真实交互 —— userEvent 而非 fireEvent
3. 断言用户可见的结果 —— 不测内部实现细节
```

## Visual Test

Visual Test（视觉测试）通过截图对比验证「组件长得对不对」。它抓的是「样式回归」——改 CSS 不小心改坏了间距、颜色、圆角，逻辑测试抓不到，截图 diff 能抓到。

```tsx
// 视觉测试 —— Playwright 截图断言
import { test, expect } from '@playwright/test';

test('按钮视觉快照', async ({ page }) => {
  await page.goto('/iframe.html?id=button--primary');
  await expect(page).toHaveScreenshot('button-primary.png');
});
```

```text
视觉测试的两类方案：
1. 全量截图（Chromatic / Percy）—— 每个 Story 自动截图对比
2. 单点截图（Playwright toHaveScreenshot）—— 手动为关键组件断言

视觉测试的稳定化要点：
1. 禁用动画与过渡（截图前等待稳定）
2. 固定字体与视口尺寸
3. 设置 diff 阈值，避免 1px 抖动误报
```

```bash
# Chromatic —— Storybook 官方视觉回归，接入 CI
npx chromatic --project-token=xxx --exit-zero-on-changes
```

## Accessibility

Accessibility（可访问性）质量保障通过自动化检查 + 手动验证结合：自动工具抓「可检测」的问题（缺 aria、对比度不足、无标签），手动验证覆盖「需要人判断」的问题（键盘流程、读屏体验）。

```tsx
// jest-axe —— 自动扫描可访问性问题
import { render } from '@testing-library/react';
import { axe } from 'jest-axe';
import { Button } from './Button';

test('Button 无可访问性违规', async () => {
  const { container } = render(<Button>提交</Button>);
  const results = await axe(container);
  expect(results).toHaveNoViolations();
});
```

```text
自动化可访问性检查（axe-core）能抓的问题：
1. 图片缺 alt、按钮缺 aria-label
2. 颜色对比度不足（< 4.5:1）
3. 表单控件缺 label
4. 标题层级错误（h1 → h3 跳级）

自动化抓不到、需手动验证的问题：
1. 键盘完整操作流程是否顺畅
2. 焦点顺序是否合理
3. 读屏器朗读是否通顺
```

```bash
# Storybook 的 a11y 插件 —— 在 Story 层面自动检查
npx storybook add @storybook/addon-a11y
```

## Bundle Size

Bundle Size（包体积）衡量组件库对使用方产物体积的影响。组件库要「按需引入 + 无冗余依赖」，否则引入一个 Button 就拖几百 KB 进使用方的 bundle。

```text
控制包体积的手段：
1. Tree Shaking —— ESM 产物 + sideEffects 声明
2. 按需引入 —— 支持子路径导入（@myorg/ui/button）
3. 依赖瘦身 —— 不把 react 等 peer 依赖打进产物
4. 体积监控 —— CI 里对比每次构建的产物体积
```

```json
// exports 子路径 —— 支持按需引入单个组件
{
  "exports": {
    ".": { "import": "./dist/index.mjs" },
    "./button": { "import": "./dist/button.mjs" },
    "./select": { "import": "./dist/select.mjs" }
  }
}
```

```js
// 使用方按需引入 —— 只打包 Button 相关代码
import { Button } from '@myorg/ui/button';
```

```bash
# 体积分析 —— 看产物里每个模块占多大
npx size-limit
npx webpack-bundle-analyzer stats.json
```

```json
// size-limit —— CI 里的体积门禁
[
  { "name": "全量", "path": "dist/index.mjs", "limit": "50 kB" },
  { "name": "按需 Button", "path": "dist/button.mjs", "limit": "10 kB" }
]
```

```text
peerDependencies 的意义：
组件库依赖 react、react-dom，但不应把它们打包进产物。
声明为 peerDependencies，让使用方自己装，避免重复打包
（否则 bundle 里会出现两份 React，体积翻倍、状态错乱）。
```

## 应用场景实战

### 场景一：给组件库搭完整测试栈（单元 + 组件 + 可访问性）

```bash
# 安装测试工具链
pnpm add -D vitest @testing-library/react @testing-library/user-event \
  jsdom @testing-library/jest-dom jest-axe
```

```ts
// vitest.config.ts —— 测试环境配置
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'jsdom',
    setupFiles: ['./test/setup.ts'],
    globals: true,
  },
});
```

```tsx
// 综合测试 —— 组件 + 可访问性一起断言
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { axe } from 'jest-axe';
import { Modal } from './Modal';

test('Modal 打开、关闭、可访问', async () => {
  const { container } = render(<Modal title="确认删除" />);

  // 组件交互
  expect(screen.getByRole('dialog')).toBeInTheDocument();
  await userEvent.click(screen.getByRole('button', { name: '关闭' }));

  // 可访问性
  const results = await axe(container);
  expect(results).toHaveNoViolations();
});
```

### 场景二：CI 里的包体积门禁

```yaml
# .github/workflows/size.yml —— 体积监控
name: Bundle Size
on: [pull_request]

jobs:
  size:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci

      - run: npx size-limit      # 超限即失败
```

## 最佳实践与踩坑记录

### 最佳实践

1. 纯逻辑抽成函数写单元测试，组件只测渲染与交互
2. 组件测试按用户视角（getByRole + userEvent），不测实现细节
3. 视觉测试接 CI，样式回归在 PR 里就暴露
4. 可访问性用 axe 自动扫描 + 键盘手动验证结合
5. 组件库依赖声明为 peerDependencies，避免重复打包 React
6. CI 里加 size-limit 门禁，体积超限直接阻断合并

### 踩坑记录

```text
坑 1：组件测试测了实现细节，重构全崩
结论：改了内部 state 名，测试全红。
原因：用 getByTestId 查内部元素、断言内部状态。
解法：只断言用户可见的 DOM 与行为，内部实现随便改。

坑 2：fireEvent 测不出真实交互
结论：fireEvent.click 通过了，真实点击却触发不了。
原因：fireEvent 绕过了事件的默认行为（如 focus、冒泡链）。
解法：用 userEvent，模拟真实用户操作序列。

坑 3：视觉测试因动画不稳定
结论：每次截图都有像素差异，测试持续失败。
原因：动画/过渡在截图瞬间状态不一致。
解法：截图前禁用动画、等待稳定，或设合理的 diff 阈值。

坑 4：把 React 打进了组件库产物
结论：使用方 bundle 里出现两份 React，hooks 报错。
原因：react 写成了 dependencies 而非 peerDependencies。
解法：react/react-dom 声明为 peerDependencies，且打包时 external。

坑 5：axe 扫描不到动态内容
结论：弹窗内容在扫描时还没渲染，漏检。
原因：axe 扫描时机早于异步渲染完成。
解法：等待内容出现后再扫描（waitFor + axe），或对每个状态
     单独 render 后扫描。
```
