## 概述

组件库开发完成后要「发布」给其他项目使用。发布不只是 `npm publish`，还涉及产物的模块格式（ESM/CJS/UMD）、类型声明、Tree Shaking 友好度、版本策略。一个组件的发布质量，直接决定使用者「装得上、引得对、打得小」。

```text
组件发布的五个关键决策：
1. 模块格式 —— ESM / CJS / UMD 分别服务谁
2. 类型声明 —— .d.ts 让 TS 使用者有完整提示
3. Tree Shaking —— 产物能被摇树优化，按需引入
4. 版本策略 —— SemVer 规范管理升级
5. 发布通道 —— npm registry 配置、权限、tag
```

```text
发布产物的目标：
1. ESM 消费者（Vite、Webpack5）→ 用 ESM 产物
2. CJS 消费者（Node、旧 Webpack）→ 用 CJS 产物
3. 浏览器 <script> 引入 → 用 UMD 产物
4. TS 消费者 → 需要 .d.ts 类型声明
```

## npm

npm 是 Node.js 的包管理器与包注册表（registry）。组件库通过 npm 发布到 registry，其他项目通过 npm/pnpm/yarn 安装。发布前要确认 `package.json` 的发布相关字段配置正确。

```json
// package.json —— 发布相关字段
{
  "name": "@myorg/ui",
  "version": "1.0.0",
  "files": ["dist"],              // 只发布 dist，排除源码
  "main": "dist/index.cjs",        // CJS 入口
  "module": "dist/index.mjs",      // ESM 入口（打包工具识别）
  "types": "dist/index.d.ts",      // 类型声明入口
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./styles.css": "./dist/styles.css"
  },
  "sideEffects": ["*.css"],        // 声明哪些文件有副作用
  "publishConfig": {
    "access": "public"             // scope 包默认私有，需显式公开
  }
}
```

```bash
# 发布流程
npm login
npm publish                 # 发布 1.0.0
npm publish --tag beta      # 发布到 beta tag
npm version patch           # 升补丁版本并打 git tag
```

```text
files 字段的重要性：
没配 files 时，npm 默认发布全部文件（源码、测试、配置全上去）。
配 files: ["dist"] 只发布产物，减小包体积、避免泄露源码。
```

## ESM

ESM（ECMAScript Modules）是标准的 JS 模块系统，用 `import` / `export` 语法。现代打包工具（Vite、Webpack 5、Rollup）和浏览器都原生支持，是前端组件库的主产物格式。

```js
// ESM 产物 —— index.mjs
export { Button } from './Button.mjs';
export { Select } from './Select.mjs';
```

```json
// 声明 ESM 入口
{
  "module": "dist/index.mjs",
  "exports": {
    ".": { "import": "./dist/index.mjs" }
  }
}
```

```text
ESM 的特点：
1. 静态结构 —— import/export 可静态分析，利于 Tree Shaking
2. 原生支持 —— 浏览器 <script type="module">、Node 直接跑
3. 严格模式 —— 默认启用
4. 顶层 await、import() 动态导入

对前端组件库：ESM 是「必须」产物，Tree Shaking 依赖它。
```

## CJS

CJS（CommonJS）是 Node.js 的传统模块系统，用 `require` / `module.exports`。Node 生态大量工具链（旧的 Webpack 配置、babel 配置、Node 脚本）仍以 CJS 为主，组件库通常同时提供 CJS 产物以兼容。

```js
// CJS 产物 —— index.cjs
const Button = require('./Button.cjs').Button;
module.exports = { Button };
```

```json
// 声明 CJS 入口
{
  "main": "dist/index.cjs",
  "exports": {
    ".": { "require": "./dist/index.cjs" }
  }
}
```

```text
ESM 与 CJS 的关键差异：
            ESM                     CJS
语法         import/export          require/module.exports
加载时机     静态（编译期）          动态（运行时）
Tree Shaking 支持                   不支持
顶层 this    undefined              module.exports
互操作       ESM 可 require CJS      CJS 不能 import ESM（需动态）
```

```text
双格式产物（dual package）：
同时发布 ESM + CJS，通过 exports 字段的条件导出让使用者
自动匹配。注意避免「双包实例」问题（同一包被 ESM 和 CJS
各加载一份，导致 instanceof 判断失败）。
```

## UMD

UMD（Universal Module Definition）是兼容多种加载方式的「通用」格式，既能在浏览器 `<script>` 全局引入，也能被 CJS/AMD 加载。现在主要用于 CDN 直引场景，不再是主流产物。

```js
// UMD 产物 —— 立即执行函数包裹
(function (global, factory) {
  typeof exports === 'object' && typeof module !== 'undefined'
    ? factory(exports)
    : typeof define === 'function' && define.amd
      ? define(['exports'], factory)
      : ((global = global || self), factory((global.MyLib = {})));
})(this, function (exports) {
  exports.Button = Button;
});
```

```html
<!-- UMD 产物通过 <script> 直接引入，挂到全局变量 -->
<script src="https://unpkg.com/my-lib/dist/index.umd.js"></script>
<script>
  MyLib.Button;   // 全局访问组件
</script>
```

```text
三种格式的选择：
1. 前端组件库 —— 优先 ESM + CJS（双格式）
2. 需要 CDN <script> 直引 —— 补 UMD
3. 纯 Node 工具库 —— CJS 即可

UMD 体积大、不能 Tree Shaking，仅作为补充而非主力。
```

## Type Definitions

Type Definitions（类型声明，.d.ts）为 TS 使用者提供类型提示。组件库发布时必须带上 `.d.ts`，否则 TS 项目里所有 props 都是 any，失去类型安全。

```json
// 声明类型入口
{
  "types": "dist/index.d.ts",
  "exports": {
    ".": { "types": "./dist/index.d.ts" }
  }
}
```

```ts
// 生成的 index.d.ts —— 声明组件类型
export interface ButtonProps {
  variant?: 'primary' | 'default';
  disabled?: boolean;
  children?: React.ReactNode;
  onClick?: () => void;
}
export declare function Button(props: ButtonProps): JSX.Element;
```

```text
生成 .d.ts 的方式：
1. tsc --declaration —— 手写 TS 时用 tsc 生成
2. rollup-plugin-dts —— 打包时合并类型声明
3. unbuild / tsup —— 一体化工具自动生成

注意：exports 里 types 条件要放在 import/require 之前，
否则 TS 解析不到类型。
```

## Tree Shaking

Tree Shaking（摇树优化）是打包时「移除未使用代码」的优化。它依赖 ESM 的静态 import/export 结构：打包器能确定哪些导出没被引用，从而在产物里剔除。组件库要让使用者能「按需引入」，必须保证产物可摇树。

```text
Tree Shaking 的前提条件：
1. ESM 产物 —— import/export 可静态分析
2. 无副作用声明 —— package.json 的 sideEffects 字段
3. 纯函数/纯导出 —— 模块顶层无副作用执行
```

```json
// sideEffects —— 告诉打包器「哪些文件有副作用，不能摇掉」
{
  "sideEffects": ["*.css", "*.scss"]
}
```

```js
// 好的导出结构 —— 每个组件独立导出，可单独摇树
export { Button } from './Button';
export { Select } from './Select';
export { Table } from './Table';

// 使用方：只引入 Button，Select/Table 会被摇掉
import { Button } from '@myorg/ui';
```

```text
破坏 Tree Shaking 的常见写法：
1. export * from './index' 再 re-export 循环引用
2. 顶层有副作用（如立即执行的初始化代码）
3. 产物是 CJS 或 UMD（无法静态分析）
4. sideEffects 字段标 false 却实际有 CSS 副作用
```

## Semantic Versioning

Semantic Versioning（语义化版本，SemVer）用 `major.minor.patch` 表达版本变化，让使用者能安全升级。组件库发布必须遵守，否则使用者升级就崩。

```text
SemVer 规则（MAJOR.MINOR.PATCH）：
MAJOR —— 不兼容的破坏性变更（删 API、改行为、改 props 必填）
MINOR —— 向后兼容的新增功能（加新组件、加新 props）
PATCH —— 向后兼容的 bug 修复

0.x.y —— 初期版本，API 不稳定，可任意破坏
1.0.0 —— 首个稳定版本，此后严格遵守 SemVer
```

```text
版本号与 npm tag：
latest   → 稳定版（默认安装）
beta     → 预发布（npm publish --tag beta）
next     → 下一主版本预览
canary   → 每次提交自动发布（CI）

使用者装 beta：npm install @myorg/ui@beta
```

```bash
# 标准发布流程
npm version patch     # 1.0.0 → 1.0.1（修 bug）
npm version minor     # 1.0.1 → 1.1.0（新功能）
npm version major     # 1.1.0 → 2.0.0（破坏性变更）
npm publish
```

```text
破坏性变更的界定（务必谨慎）：
1. 删除某个组件或 prop
2. 把可选 prop 改成必填
3. 改变 prop 的默认值或行为
4. 缩小某个 prop 的类型范围

这些都必须升 MAJOR，否则就是「破坏性变更伪装成 PATCH」，
使用方升级就踩坑。
```

## 应用场景实战

### 场景一：用 tsup 一键打包发布双格式组件库

```bash
# 安装 tsup（基于 esbuild，自动生成 ESM + CJS + .d.ts）
pnpm add -D tsup
```

```json
// package.json —— 完整发布配置
{
  "name": "@myorg/ui",
  "version": "1.0.0",
  "files": ["dist"],
  "main": "dist/index.cjs",
  "module": "dist/index.mjs",
  "types": "dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  },
  "sideEffects": ["*.css"],
  "scripts": {
    "build": "tsup src/index.ts --format esm,cjs --dts --clean",
    "release": "npm run build && npm publish"
  },
  "publishConfig": { "access": "public" }
}
```

```bash
# 发布
pnpm build
npm login
pnpm release
```

### 场景二：破坏性变更走 beta 通道灰度验证

```bash
# 主版本重构，先发 beta 让使用方验证
npm version 2.0.0-beta.1
npm publish --tag beta

# 使用方安装 beta 测试
npm install @myorg/ui@beta

# 验证通过后，把 beta 提升为 latest
npm version 2.0.0
npm publish
```

## 最佳实践与踩坑记录

### 最佳实践

1. 产物同时提供 ESM + CJS（exports 条件导出），ESM 保证 Tree Shaking
2. `files: ["dist"]` 限定发布内容，别把源码和测试发上去
3. `sideEffects` 字段如实声明，CSS 要标出来避免被摇掉
4. `.d.ts` 是必选项，TS 项目没有它就是没有类型
5. 严格遵守 SemVer，破坏性变更走 beta 通道或升 major
6. scope 包记得 `publishConfig.access: public`，否则发布被拒

### 踩坑记录

```text
坑 1：发布了源码和测试文件
结论：包体积巨大，还暴露了内部实现。
原因：没配 files 字段，npm 默认发布全部。
解法：package.json 配 files: ["dist"]。

坑 2：Tree Shaking 无效，引一个组件打进全部
结论：import { Button } 打包后还是全库体积。
原因：产物是 CJS，或 sideEffects 标 false 但实际有副作用。
解法：确保 ESM 产物 + 正确的 sideEffects 声明。

坑 3：双包实例问题
结论：typeof instance === Component 判断失败。
原因：ESM 和 CJS 各加载了一份组件，两份不同引用。
解法：核心共享模块只导出一次，避免 ESM/CJS 重复实例化。

坑 4：TS 使用方报「没有类型声明」
结论：import 后所有 props 都是 any。
原因：没发布 .d.ts，或 exports 里 types 条件位置不对。
解法：生成 .d.ts，且 exports 里 types 放 import 之前。

坑 5：PATCH 版本引入了破坏性变更
结论：使用方 npm install 升级后崩了。
原因：改了 props 默认值却只升了 patch。
解法：任何不兼容变更升 major，拿不准就发 beta 验证。
```
