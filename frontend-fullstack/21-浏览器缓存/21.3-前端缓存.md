## 概述

前端缓存在浏览器内部有多个层级，从快到慢、从易失到持久依次是 Memory Cache、Disk Cache、Service Worker Cache，再往上还有 CDN Cache。理解每一层的命中条件，才能解释「资源到底从哪加载」。

```text
浏览器缓存层级（命中优先级从高到低）：
1. Service Worker Cache —— 由 JS 完全控制，可拦截请求
2. Memory Cache —— 内存缓存，最快，关闭标签页即失效
3. Disk Cache —— 磁盘缓存，持久，重启浏览器仍保留
4. CDN Cache —— 边缘节点缓存，减少回源
```

```text
一次资源加载可能经过的路径：
请求 → Service Worker（可自定义策略）
  → Memory Cache（强缓存命中）
  → Disk Cache（强缓存命中）
  → 网络 → CDN Cache → 源站
```

## Memory Cache

Memory Cache（内存缓存）是浏览器把资源放在内存中，读取速度最快，但容量小、易失，关闭标签页或进程后就清空。

```text
特点：
1. 最快 —— 内存读取，无磁盘 IO
2. 易失 —— 关闭标签页/浏览器后失效
3. 容量小 —— 只缓存近期使用的小资源
4. 不持久 —— 无法跨会话复用
```

```text
通常命中的资源：
1. 当前页面频繁复用的小图片、内联资源
2. 预加载（preload/prefetch）的脚本
3. 刷新时命中的强缓存资源（短时间内的二次访问）
```

```text
DevTools 观察：
Network 面板 Size 列显示 "(memory cache)" 即来自内存缓存。
显示 "(disk cache)" 则来自磁盘缓存。
```

```text
无法直接控制：
Memory Cache 由浏览器自动管理，开发者无法通过 API 干预，
只能通过合理的缓存头与加载策略间接影响。
```

## Disk Cache

Disk Cache（磁盘缓存）把资源写入磁盘，容量大、持久，关闭浏览器后依然存在，是强缓存（Cache-Control/Expires）落地的默认位置。

```text
特点：
1. 持久 —— 重启浏览器仍保留
2. 容量大 —— 可缓存大量静态资源
3. 稍慢于内存 —— 但远快于网络
4. 受 HTTP 缓存头控制 —— max-age 等决定是否可用
```

```text
Disk Cache 与 Memory Cache 的切换：
1. 首次加载 → 写入磁盘
2. 短时间二次访问 → 常命中内存
3. 内存不足或时间久 → 回落到磁盘
4. 浏览器自动决定，细节不透明
```

```text
命中条件：
必须满足强缓存策略（Cache-Control: max-age 未过期，或 immutable）。
过期后则发起协商缓存验证（304 或 200）。
```

```text
磁盘缓存目录（Chrome）：
Windows: %LocalAppData%\Google\Chrome\User Data\Default\Cache
macOS:   ~/Library/Caches/Google/Chrome
Linux:   ~/.cache/google-chrome
```

## Service Worker Cache

Service Worker Cache 由 JavaScript 完全控制的缓存，可拦截所有同源请求，实现离线缓存和自定义缓存策略，是 PWA 的核心。

```text
特点：
1. 完全可控 —— 缓存什么、何时缓存、如何命中，全由代码决定
2. 可离线 —— 网络断开时返回缓存内容
3. 优先级最高 —— 在 Memory/Disk Cache 之前拦截
4. 基于 Cache Storage API —— 键值存储 Request → Response
```

```js
// 安装时预缓存静态资源
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('v1').then((cache) => {
      return cache.addAll(['/', '/app.js', '/style.css']);
    })
  );
});

// 请求拦截：缓存优先
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      return cached || fetch(event.request);
    })
  );
});
```

```text
与 HTTP 缓存的区别：
HTTP 缓存 → 浏览器自动，按响应头决定
SW 缓存 → 开发者用 JS 显式控制，粒度更细、策略更灵活
```

## CDN Cache

CDN Cache 是内容分发网络的边缘节点缓存，把资源缓存在离用户更近的服务器上，减少回源延迟和源站压力。

```text
特点：
1. 就近访问 —— 命中边缘节点，延迟低
2. 分担源站 —— 大量请求被边缘节点吸收
3. 受 Cache-Control 控制 —— public/s-maxage 决定缓存时长
4. 需主动刷新 —— 资源更新时需 purge 或依赖 hash 文件名
```

```text
CDN 缓存决策链：
1. 检查响应头 Cache-Control
   - public + s-maxage → 按 s-maxage 缓存
   - private / no-store → 不缓存
2. 命中 → 直接返回；未命中 → 回源拉取并缓存
3. 过期 → 回源验证（ETag/Last-Modified），304 则刷新
```

```text
# 适合 CDN 缓存的响应头
Cache-Control: public, max-age=300, s-maxage=86400

# 更新策略：文件名带 hash，更新即换 URL，无需手动 purge
app.5d8c9f3a.js
```

```text
刷新（purge）场景：
1. 内容改了但 URL 没变（如 index.html）
2. 需要立即让所有用户看到新内容
3. 操作：CDN 控制台 purge 或调 API 失效缓存
```

## Application Cache

Application Cache（AppCache）是早期 HTML 的离线缓存机制，通过 manifest 文件声明要缓存的资源。现已废弃（Deprecated），被 Service Worker 取代。

```text
<html manifest="cache.appcache">
```

```text
appcache 文件内容：
CACHE MANIFEST
# 要缓存的资源
/app.js
/style.css
/img/logo.png

NETWORK:
# 必须走网络的资源
/api/

FALLBACK:
# 兜底：请求失败时回退到指定资源
/ /offline.html
```

```text
为什么被废弃：
1. 缓存更新机制混乱，容易出现「永远旧版本」问题
2. 无法精细控制，策略单一
3. 坑多难调试，各浏览器行为不一致
4. 被 Service Worker + Cache Storage 取代
```

```text
结论：
新项目一律使用 Service Worker 实现离线能力，
不要在新代码中使用 Application Cache。
```

## 应用场景实战

### 场景一：判断资源来自哪层缓存

```text
打开 DevTools → Network 面板，看 Size 列：
"(memory cache)"       → 内存缓存命中，最快
"(disk cache)"         → 磁盘缓存命中（强缓存）
"(ServiceWorker)"      → 被 Service Worker 拦截处理
"304 Not Modified"     → 协商缓存命中（走了网络验证）
具体字节数（如 2.1 KB）→ 从网络/CDN 下载
```

### 场景二：离线优先的 PWA 缓存设计

```js
// 用 Service Worker 实现分层：先内存/SW 缓存，再网络
self.addEventListener('fetch', (event) => {
  const req = event.request;
  // 静态资源走 Cache First，接口走 Network First
  if (req.destination === 'script' || req.destination === 'style') {
    event.respondWith(
      caches.match(req).then((c) => c || fetch(req))
    );
  } else {
    event.respondWith(
      fetch(req).catch(() => caches.match(req))
    );
  }
});
```

```text
协同效果：
1. SW Cache 兜底离线 → 任何情况下都有内容
2. Memory/Disk Cache 加速重复访问 → 减少网络
3. CDN Cache 加速首次访问 → 减少回源
三层配合实现「快 + 稳 + 省」。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 静态资源用 hash 文件名 + 强缓存（Disk Cache 持久命中）
2. 离线能力用 Service Worker，不要用 AppCache
3. 动态接口数据走 CDN 时用 s-maxage 控制共享缓存
4. 敏感数据用 no-store，确保不进任何缓存层
5. 用 DevTools Size 列定位资源命中层级，排查缓存问题

### 踩坑记录

```text
坑 1：内存缓存导致测试结果「假新鲜」
结论：改代码后刷新仍是旧逻辑。
原因：资源命中了 Memory Cache，没重新请求。
解法：测试时禁用缓存（Network 面板勾选 Disable cache）。

坑 2：AppCache 缓存永远不更新
结论：老项目离线页一直显示旧版本。
原因：AppCache 更新机制复杂，manifest 不变就不刷新。
解法：迁移到 Service Worker，彻底摆脱 AppCache。

坑 3：CDN 缓存不生效，每次都回源
结论：CDN 命中率极低。
原因：响应头是 private 或缺 public/s-maxage。
解法：静态资源加 Cache-Control: public, s-maxage。

坑 4：SW 缓存占用过大
结论：浏览器存储空间告警，缓存写入失败。
原因：Service Worker 缓存了过多或过大资源未清理。
解法：版本化管理 cache，激活时删除旧版本缓存。

坑 5：Disk Cache 命中但内容已过期
结论：强缓存期内改了服务器资源用户看不到。
原因：max-age 未到期，浏览器不发起验证。
解法：改资源必须换 URL（hash 文件名），或调短 max-age。
```
