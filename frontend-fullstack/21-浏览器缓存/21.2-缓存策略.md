## 概述

缓存策略描述资源在「新鲜（Fresh）」「过期（Stale）」「重新验证（Revalidate）」之间的状态流转。理解这些状态和 Cache-Control 指令，才能为不同资源设计正确的缓存行为。

```text
核心概念：
1. Fresh —— 缓存未过期，直接使用
2. Stale —— 缓存已过期，需验证或按策略降级使用
3. Revalidate —— 向服务端确认资源是否变化
4. 指令组合 —— no-store / no-cache / max-age / s-maxage 等控制上述行为
```

```text
状态流转：
新鲜期内 → Fresh → 直接命中
过期后   → Stale → 触发 Revalidate（若允许）
  ├─ 服务端 304 → 回到 Fresh
  └─ 服务端 200 → 替换为新资源
```

## Fresh

Fresh（新鲜）表示缓存在有效期内，可以直接使用而无需联系服务端。新鲜时长由 max-age 等指令决定。

```text
新鲜期来源：
1. max-age=N —— 响应生成后 N 秒内新鲜
2. s-maxage=N —— 共享缓存的新鲜期
3. 计算方式：freshness_lifetime = max-age（或 Expires 换算）
```

```text
响应头示例：
Cache-Control: max-age=3600
说明：该资源在 3600 秒内是新鲜的，期间请求直接命中缓存
```

```text
Fresh 的判断：
age（缓存已存在时长）< freshness_lifetime → Fresh
age 由 Age 响应头或本地计时估算
```

## Stale

Stale（过期）表示缓存已超过新鲜期。过期缓存不能直接使用，需要重新验证；但某些策略下可临时降级使用（如 stale-while-revalidate、must-revalidate 缺省时）。

```text
Stale 的状态含义：
1. 缓存内容可能已过期，不代表一定变了
2. 默认行为 → 发起 Revalidate
3. 离线/降级场景 → 可能允许继续使用过期缓存
```

```text
# 允许使用过期缓存（服务端暂时不可用时的降级）
Cache-Control: max-age=3600, stale-if-error=600
# 表示：正常新鲜 1 小时；若重新验证时出错，最多再用 10 分钟的过期缓存
```

```text
Stale 的典型来源：
1. max-age 已耗尽
2. 手动刷新（普通刷新也会触发验证）
3. 过期后 must-revalidate 要求必须验证
```

## Revalidate

Revalidate（重新验证）是缓存过期后向服务端确认资源是否变化的过程，对应协商缓存。验证通过返回 304，否则返回 200 + 新资源。

```text
验证过程：
1. 浏览器带 If-None-Match / If-Modified-Since 发条件请求
2. 服务端比对 ETag / Last-Modified
3. 未变 → 304，缓存重新变 Fresh
4. 已变 → 200，用新资源替换缓存
```

```text
# no-cache 强制每次都重新验证
Cache-Control: no-cache

# must-revalidate 要求过期后必须验证，不可直接用过期缓存
Cache-Control: max-age=3600, must-revalidate
```

```js
// 前端强制验证的触发方式
// 1. 普通刷新（F5）→ 对缓存资源发条件请求
// 2. 强制刷新（Ctrl+Shift+R）→ 跳过缓存，直接重新请求
// 3. fetch 设置 cache 选项
fetch('/api/data', { cache: 'no-cache' });  // 重新验证后使用
```

## Immutable

Immutable 声明资源内容永不改变，在新鲜期内浏览器不发送任何条件请求。适用于带内容 hash 的静态资源，可完全跳过 Revalidate 阶段。

```text
Cache-Control: max-age=31536000, immutable

效果：
1. 新鲜期内，即使刷新页面也不发条件请求（直接命中）
2. 避免「刷新时 304 验证」的额外往返
3. 只有内容变 → 文件名变 → 新 URL 才会重新下载
```

```text
使用前提（关键）：
必须配合内容寻址文件名（如 app.5d8c9f3a.js）。
因为 immutable 声明了「此 URL 内容永不变」，
若文件内容改了但文件名没变，用户将永远拿到旧资源。
```

```text
对比：
无 immutable → 强缓存命中，但刷新时仍可能发 304 验证
有 immutable → 刷新也直接命中，零请求
```

## no-store

no-store 表示完全不缓存：响应不被写入任何缓存，也不读取缓存。适用于敏感数据（用户信息、交易数据、接口返回）。

```text
Cache-Control: no-store

含义：
1. 浏览器不存此响应
2. 中间层（CDN/代理）也不缓存
3. 每次请求都从服务器获取完整响应
```

```text
适用场景：
1. 银行卡余额、个人信息等敏感数据
2. 一次性 token、验证码
3. 需要保证绝对实时的数据
```

```js
// 前端请求敏感数据时也建议禁用缓存
fetch('/api/account', { cache: 'no-store' });

// axios 示例
axios.get('/api/account', { headers: { 'Cache-Control': 'no-store' } });
```

## no-cache

no-cache 不是「不缓存」，而是「缓存但每次使用前必须重新验证」。它允许存储响应，但强制走协商缓存，保证内容新鲜又节省带宽。

```text
Cache-Control: no-cache

正确理解：
1. 可缓存 —— 响应会被存储
2. 用前验证 —— 每次使用都发条件请求（If-None-Match 等）
3. 未变 → 304 继续用缓存；变了 → 200 拿新内容
```

```text
与 no-store 的区别：
no-store → 完全不存，每次都完整下载
no-cache → 存下来，但每次都问「变了没」
```

```text
适用场景：
1. HTML 入口文件（保证及时更新，又省带宽）
2. 频繁更新但变化不大的资源
```

## max-age

max-age 指定缓存新鲜时长（秒），是相对时间，从响应生成时刻起算。这是最常用的强缓存指令。

```text
Cache-Control: max-age=86400   # 缓存 1 天
Cache-Control: max-age=0       # 立即过期，等同每次验证

特性：
1. 相对时间，不受客户端时钟影响
2. 优先于 Expires
3. 对私有缓存和共享缓存都生效（可用 s-maxage 覆盖共享缓存）
```

```text
时间换算参考：
60        = 1 分钟
3600      = 1 小时
86400     = 1 天
604800    = 1 周
31536000  = 1 年
```

```text
# 常见配置
Cache-Control: max-age=31536000, immutable   # 带 hash 静态资源
Cache-Control: max-age=300                   # 短期缓存的数据
```

## s-maxage

s-maxage 专门针对「共享缓存」（Shared Cache，如 CDN、反向代理）设置新鲜期，优先级高于 max-age，且只在共享缓存中生效，不影响浏览器私有缓存。

```text
Cache-Control: public, max-age=60, s-maxage=600

含义：
1. 浏览器（私有缓存）→ 用 max-age，60 秒后过期
2. CDN（共享缓存）→ 用 s-maxage，600 秒后过期
```

```text
设计意图：
CDN 面向大量用户，缓存可以更激进；
浏览器面向单用户，可更频繁更新。
用 s-maxage 让 CDN 缓存更久，浏览器更短，实现分层缓存。
```

```text
注意：
1. s-maxage 只有在响应可被共享缓存时才有意义（需 public）
2. s-maxage 会覆盖共享缓存上的 max-age
3. 配合 stale-while-revalidate 可进一步提升 CDN 命中率
```

## stale-while-revalidate

stale-while-revalidate 允许在缓存过期后，先返回过期的缓存（Stale），同时后台异步去重新验证并更新缓存（Revalidate）。用户永远拿「即时」响应，后台刷新内容。

```text
Cache-Control: max-age=3600, stale-while-revalidate=86400

含义：
1. 0~3600 秒 → Fresh，直接命中
2. 3600 秒后 → 先返回过期缓存（快），同时后台更新
3. 后台更新成功后，下次请求拿到新内容
```

```text
优势：
1. 消除「过期后首次请求」的延迟（不必等验证往返）
2. 服务端抖动时依然有内容可用
3. 对 CDN 特别有效，命中率极高
```

```text
典型应用：
新闻列表、商品详情这类「允许短暂旧数据」的页面。
用户看到的是缓存秒开，后台静默更新，下次进入就是新内容。
```

## 应用场景实战

### 场景一：不同资源的缓存指令组合

```text
# 入口 HTML —— 每次验证，保证及时更新
Cache-Control: no-cache

# 带 hash 的 JS/CSS —— 永久缓存，永不验证
Cache-Control: max-age=31536000, immutable

# 商品列表接口 —— 短新鲜期 + 后台刷新
Cache-Control: max-age=60, stale-while-revalidate=600

# 用户资产接口 —— 完全不缓存
Cache-Control: no-store
```

### 场景二：CDN 分层缓存

```text
# 静态资源在 CDN 上缓存更久，浏览器相对更短
Cache-Control: public, max-age=300, s-maxage=86400, stale-while-revalidate=3600

# 效果：
# 浏览器 5 分钟过期，期间直接命中
# CDN 缓存 1 天，1 天内大量用户共享命中
# CDN 过期后先用旧内容兜底，后台回源更新
```

## 最佳实践与踩坑记录

### 最佳实践

1. 带 hash 资源用 `max-age=31536000, immutable`
2. HTML 入口用 `no-cache`，及时感知更新
3. CDN 资源用 `s-maxage` 延长共享缓存
4. 允许旧数据的页面用 `stale-while-revalidate` 提升体验
5. 敏感数据一律 `no-store`

### 踩坑记录

```text
坑 1：把 no-cache 当成不缓存
结论：以为 no-cache 不缓存，结果数据仍被存储。
原因：no-cache 是「缓存但每次验证」，真正不缓存是 no-store。
解法：需要完全不存就用 no-store。

坑 2：immutable 配了可变文件名
结论：改了文件内容，用户永远拿旧版本。
原因：immutable 声明 URL 内容不变，但文件名没变。
解法：immutable 必须搭配内容 hash 文件名。

坑 3：s-maxage 不生效
结论：CDN 没有按 s-maxage 缓存。
原因：响应头缺 public，或 CDN 配置覆盖了响应头。
解法：确保 Cache-Control 含 public，并检查 CDN 的缓存规则。

坑 4：stale-while-revalidate 用户看到旧数据被投诉
结论：用户短时间看到过期内容。
原因：过期后先返回了 stale 缓存。
解法：对时效性强的数据别用该指令，改用 no-cache 或短 max-age。

坑 5：max-age=0 与 no-cache 混用导致困惑
结论：缓存行为与预期不符。
原因：两者都会触发每次验证，但语义有差异，混用难排查。
解法：统一用 no-cache 表达「每次验证」，保持配置清晰。
```
