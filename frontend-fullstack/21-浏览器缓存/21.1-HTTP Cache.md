## 概述

HTTP 缓存通过响应头让浏览器复用已下载的资源，减少重复请求与带宽消耗。它分「强缓存」和「协商缓存」两级：强缓存命中后直接读本地不发请求，协商缓存则发送条件请求，由服务端判断资源是否变化。

```text
HTTP 缓存的两级机制：
1. 强缓存 —— Cache-Control / Expires，命中后不发请求，状态码 200（from memory/disk cache）
2. 协商缓存 —— ETag / Last-Modified 配合 If-None-Match / If-Modified-Since，命中返回 304
3. 优先级 —— Cache-Control 优先于 Expires；ETag 优先于 Last-Modified
4. 强缓存失效后才会进入协商缓存阶段
```

```text
完整流程：
请求资源 → 查强缓存（Cache-Control/Expires）
  ├─ 未过期 → 直接用缓存（200，from cache）
  └─ 已过期/无强缓存 → 带条件请求头
       ├─ 带 If-None-Match / If-Modified-Since
       ├─ 服务端判断资源未变 → 返回 304，浏览器更新缓存元数据继续用旧资源
       └─ 资源已变 → 返回 200 + 新资源 + 新缓存头
```

## Cache-Control

Cache-Control 是 HTTP/1.1 的强缓存控制头，比 Expires 更灵活，是现代缓存策略的核心。

```text
常用指令：
max-age=秒        —— 缓存新鲜时长（相对时间，从响应生成起算）
no-cache          —— 可缓存，但每次使用前必须重新验证（走协商缓存）
no-store          —— 完全不缓存
public            —— 可被 CDN 等中间层缓存
private           —— 只能被浏览器缓存，不可被中间层缓存
s-maxage=秒       —— 仅对共享缓存（CDN）生效，覆盖 max-age
must-revalidate   —— 过期后必须重新验证，不能用过期缓存
immutable         —— 资源永不变化，强缓存期内不发条件请求
```

```text
# 服务端响应头示例
Cache-Control: max-age=31536000, immutable   # 静态资源一年不过期
Cache-Control: no-cache                       # 每次都验证
Cache-Control: no-store                       # 敏感数据不缓存
Cache-Control: public, max-age=86400, s-maxage=600
```

```js
// 前端无法直接设置响应头，通常在服务端或代理配置
// Nginx 配置示例：
// location ~* \.(js|css|png|jpg|woff2)$ {
//   expires 30d;
//   add_header Cache-Control "public, immutable";
// }
```

## Expires

Expires 是 HTTP/1.0 时代的强缓存头，用绝对时间（GMT 格式）表示资源过期时刻。优先级低于 Cache-Control 的 max-age。

```text
Expires: Wed, 21 Oct 2026 07:28:00 GMT

特点：
1. 绝对时间 —— 依赖客户端与服务端时钟一致
2. 时钟偏差会导致缓存失效时间不准
3. 若同时存在 Cache-Control: max-age，浏览器忽略 Expires
```

```text
# 服务端设置 Expires
Expires: Thu, 01 Jan 2027 00:00:00 GMT

# 等价的 Cache-Control（推荐）
Cache-Control: max-age=2592000
```

```text
为什么被淘汰：
客户端本地时间被用户改错时，Expires 会提前或滞后失效。
max-age 是相对时长，不受时钟影响，因此现代实践统一用 Cache-Control。
```

## ETag

ETag（Entity Tag）是资源内容的唯一标识，通常是内容哈希或版本号。它是协商缓存的首选验证器，精度最高。

```text
ETag 工作方式：
1. 服务端生成资源的 ETag（如文件内容 hash）
2. 响应头返回 ETag: "abc123"
3. 浏览器下次请求带上 If-None-Match: "abc123"
4. 服务端比对：相同 → 304；不同 → 200 + 新 ETag
```

```text
# 响应
HTTP/1.1 200 OK
ETag: "5d8c9f3a2b1"
Cache-Control: no-cache
```

```text
强 ETag 与弱 ETag：
强 ETag —— "5d8c9f3a2b1"，逐字节相同才相等
弱 ETag —— W/"5d8c9f3a2b1"，语义等价即可（如允许空白差异）
```

```js
// 服务端生成 ETag 的常见做法（Node.js 示例）
import crypto from 'node:crypto';

const content = readFile('asset.js');
const etag = crypto.createHash('sha1').update(content).digest('hex').slice(0, 16);

// 比对
if (req.headers['if-none-match'] === `"${etag}"`) {
  res.writeHead(304);          // 未变化
  res.end();
} else {
  res.setHeader('ETag', `"${etag}"`);
  res.setHeader('Cache-Control', 'no-cache');
  res.end(content);            // 200 + 新内容
}
```

## Last-Modified

Last-Modified 记录资源的最后修改时间，作为协商缓存的次级验证器（精度到秒）。

```text
Last-Modified: Tue, 15 Sep 2026 08:00:00 GMT

特点：
1. 时间戳，精度只有 1 秒
2. 1 秒内的多次修改无法区分
3. 文件内容不变但 mtime 变（如 touch）会误判
4. 优先级低于 ETag
```

```text
# 响应
Last-Modified: Tue, 15 Sep 2026 08:00:00 GMT

# 浏览器下次请求
If-Modified-Since: Tue, 15 Sep 2026 08:00:00 GMT
```

```text
局限性场景：
1. 同一秒内资源被改两次，Last-Modified 无法察觉
2. 有些服务器拿不到准确的 mtime（如动态生成内容）
3. 结论：优先用 ETag，Last-Modified 作为兜底
```

## If-None-Match

If-None-Match 是请求头，携带上次响应里的 ETag，用于协商缓存验证。服务端据此判断资源是否变化。

```text
If-None-Match: "5d8c9f3a2b1"

规则：
1. ETag 匹配 → 返回 304 Not Modified
2. ETag 不匹配 → 返回 200 + 新资源 + 新 ETag
3. 可携带多个 ETag，用逗号分隔
```

```js
// 浏览器行为模拟
// 首次请求 → 拿到 ETag: "v1"
// 二次请求 → 自动带上 If-None-Match: "v1"
// 服务端比对一致 → 304，浏览器继续用本地缓存
```

```text
If-None-Match 与 If-Modified-Since 同时存在时，
服务端优先处理 If-None-Match（ETag 更精确）。
```

## If-Modified-Since

If-Modified-Since 是请求头，携带上次响应的 Last-Modified 时间，是协商缓存的另一种验证方式。

```text
If-Modified-Since: Tue, 15 Sep 2026 08:00:00 GMT

规则：
1. 资源在该时间后未被修改 → 返回 304
2. 资源已修改 → 返回 200 + 新资源 + 新 Last-Modified
3. 只能精确到秒
```

```js
// 服务端比对逻辑（伪代码）
const since = new Date(req.headers['if-modified-since']);
const mtime = stat('asset.js').mtime;

if (mtime <= since) {
  res.writeHead(304);
  res.end();
} else {
  res.setHeader('Last-Modified', mtime.toUTCString());
  res.end(content);
}
```

## 304

304 Not Modified 是协商缓存命中的响应状态码，表示「资源没变，用你本地的缓存」。它没有响应体，只有响应头。

```text
304 的含义：
1. 不是错误，是缓存命中信号
2. 无响应体，只返回必要的头
3. 浏览器收到 304 后，更新本地缓存元数据（如新的 max-age），继续用旧资源
```

```text
一个完整的协商缓存交互：
请求：GET /app.js
        If-None-Match: "v2"
响应：HTTP/1.1 304 Not Modified
        ETag: "v2"
        Cache-Control: max-age=86400
说明：资源未变，浏览器继续用本地缓存，并刷新新鲜度
```

```text
注意：304 响应也会带 Cache-Control，
服务端可借此延长缓存有效期，避免每次都来验证。
```

## 应用场景实战

### 场景一：静态资源长缓存 + 文件名 hash

```text
# 构建产物带内容 hash，配合 immutable 强缓存
app.5d8c9f3a.js
vendor.a1b2c3d4.js

# 响应头
Cache-Control: max-age=31536000, immutable
```

```js
// Vite/Webpack 默认对带 hash 的资源文件名做内容寻址
// 内容变 → 文件名变 → 新 URL 自然绕过旧缓存，无需协商缓存
// 内容不变 → 同一 URL → 命中强缓存，一年不再请求
```

### 场景二：HTML 用协商缓存，保证及时更新

```text
# index.html 需要及时更新，用 no-cache 走协商缓存
Cache-Control: no-cache
ETag: "html-3f2a"

# 流程：每次都带 If-None-Match 验证，变了就 200 拿新 HTML，
# 新 HTML 里引用新的 hash 资源，实现整体无缝更新
```

```text
# 典型前端部署缓存策略：
HTML          → no-cache（每次验证，保证入口最新）
JS/CSS 带 hash → max-age=1年, immutable（永久缓存）
图片/字体带 hash → max-age=1年, immutable
接口数据       → no-store 或短 max-age
```

## 最佳实践与踩坑记录

### 最佳实践

1. 带 hash 的静态资源用 `max-age=31536000, immutable`，永久缓存
2. HTML 入口用 `no-cache`，保证能及时拿到新版本
3. 优先使用 ETag，Last-Modified 作为兜底
4. 敏感数据用 `no-store`，禁止任何缓存
5. 统一用 Cache-Control，弃用 Expires（避免时钟问题）

### 踩坑记录

```text
坑 1：改了文件但线上没更新
结论：刷新后仍是旧资源。
原因：强缓存未过期，浏览器根本不发请求。
解法：给文件名加内容 hash，改内容即换 URL；或对 HTML 用 no-cache。

坑 2：Expires 时间不生效
结论：设置的过期时间与预期不符。
原因：Cache-Control 的 max-age 优先级高于 Expires。
解法：统一用 max-age，删除 Expires。

坑 3：协商缓存误判资源未变
结论：改动了文件但服务端仍返回 304。
原因：用 Last-Modified 时，同一秒内多次修改检测不到。
解法：改用 ETag（内容哈希）作为验证器。

坑 4：304 响应带了过期缓存头
结论：资源一直走验证，性能差。
原因：304 响应没带新的 Cache-Control，缓存新鲜度没刷新。
解法：304 响应也返回 Cache-Control，延长下次验证间隔。

坑 5：CDN 缓存了不该缓存的页面
结论：用户拿到别人/旧的数据。
原因：响应头用了 public，中间层也缓存了。
解法：用户私有数据用 private 或 no-store，避免 CDN 缓存。
```
