## 概述

API Contract（接口契约）是「前后端之间关于接口的正式约定」：用机器可读的规范（OpenAPI、JSON Schema）描述接口的路径、参数、请求体、响应结构，让双方围绕同一份契约开发。它解决了「前端猜后端、后端改字段前端就崩」的经典协作问题，把口头约定变成可校验、可生成代码的契约。

```text
API Contract 的价值：
1. 单一事实来源 —— 契约是前后端共同对齐的基准
2. 契约先行 —— 先定接口，再并行开发
3. 类型生成 —— 契约生成前端类型，杜绝手写错
4. 自动校验 —— 契约测试保证实现符合约定
5. 变更可控 —— 破坏性变更在契约层面显式暴露
```

```text
契约驱动的开发流程：
1. 写契约 —— 用 OpenAPI 定义接口
2. 生成代码 —— 生成前端类型/客户端、后端骨架
3. 并行开发 —— 前后端各自对着契约实现
4. 契约测试 —— CI 里校验实现与契约一致
5. 变更评审 —— 改契约走评审，破坏性变更加版本
```

## OpenAPI

OpenAPI（原 Swagger）是描述 REST API 的规范标准：用一份 YAML/JSON 文件声明接口的路径、HTTP 方法、参数、请求体、响应和错误码。它是 API 文档与代码生成的「母本」，也是前后端契约的核心载体。

```text
OpenAPI 文档的组成：
1. info —— 接口的元信息（标题、版本、描述）
2. paths —— 路径与方法定义
3. components —— 可复用的 schema、参数、响应
4. servers —— 服务器地址
```

```yaml
# openapi.yaml —— 一个用户接口的契约
openapi: 3.1.0
info:
  title: User API
  version: 1.0.0
paths:
  /users/{id}:
    get:
      operationId: getUser
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        '200':
          description: 用户详情
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/User'
        '404':
          description: 用户不存在
components:
  schemas:
    User:
      type: object
      required: [id, name]
      properties:
        id:
          type: string
        name:
          type: string
        email:
          type: string
          format: email
```

OpenAPI 的 `operationId` 是代码生成的关键——它被用来生成函数名。`$ref` 引用 components 里的 schema 复用类型定义。OpenAPI 既能生成交互式文档（Swagger UI），也能生成前端类型和 mock 服务器。

## JSON Schema

JSON Schema 是描述 JSON 数据结构的标准：定义字段的类型、必填性、格式、取值范围、嵌套结构。它是 OpenAPI 的 schema 部分，也可独立用于校验请求/响应、配置文件和前端表单数据。

```text
JSON Schema 的能力：
1. 类型约束 —— type: string/number/object/array
2. 必填约束 —— required 数组
3. 格式校验 —— format: email/date-time/uri
4. 取值约束 —— enum、minimum、maximum、pattern
5. 组合约束 —— oneOf、anyOf、allOf、not
```

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["id", "name", "price"],
  "properties": {
    "id": { "type": "string" },
    "name": { "type": "string", "minLength": 1 },
    "price": { "type": "number", "minimum": 0 },
    "category": {
      "type": "string",
      "enum": ["phone", "laptop", "accessory"]
    }
  }
}
```

```ts
// 前端用 JSON Schema 校验数据（Ajv）
import Ajv from 'ajv';

const schema = {
  type: 'object',
  required: ['email'],
  properties: {
    email: { type: 'string', format: 'email' },
  },
};

const ajv = new Ajv();
const validate = ajv.compile(schema);

validate({ email: 'alice@example.com' }); // true
validate({ email: 'not-an-email' }); // false
```

JSON Schema 在契约体系里承担「数据结构定义」的角色：OpenAPI 用它定义请求/响应结构，前端用它做运行时校验。一份 Schema 既能生成 TypeScript 类型，又能在运行时校验数据合法性。

## Type Generation

Type Generation（类型生成）是「从契约自动生成前端类型与客户端代码」的流程：以 OpenAPI/GraphQL Schema 为输入，用工具生成 TypeScript 类型、请求函数、甚至完整的 hooks。它消除手写接口类型，保证前端类型永远与后端契约一致。

```text
类型生成工具：
1. openapi-typescript —— OpenAPI → TypeScript 类型
2. openapi-generator —— OpenAPI → 多语言客户端
3. orval —— OpenAPI → TS 类型 + fetch/axios 客户端 + hooks
4. graphql-codegen —— GraphQL Schema → TS 类型 + hooks
```

```yaml
# orval.config.ts —— 用 orval 从 OpenAPI 生成代码
# orval 会读取 openapi.yaml，生成类型和请求函数
export default {
  api: {
    input: './openapi.yaml',
    output: {
      target: './src/api/generated.ts',
      client: 'axios',
    },
  },
};
```

```ts
// 生成后的代码（示意）：类型 + 请求函数自动生成
// src/api/generated.ts
export interface User {
  id: string;
  name: string;
  email?: string;
}

export const getUser = (id: string) =>
  client.get<User>(`/users/${id}`).then((r) => r.data);
```

类型生成的收益是「契约即类型」：后端改字段，前端重新生成，编译期立即暴露所有不匹配的地方，而不是运行时才报错。生成的代码应纳入版本控制或 CI 校验，防止手工修改导致漂移。

## Contract Testing

Contract Testing（契约测试）是「验证实现是否符合契约」的测试手段：分别对「提供方」（后端）和「消费方」（前端）做测试，确保后端真的按契约返回、前端真的按契约消费。它比端到端测试更快、更精准地定位契约违背点。

```text
契约测试的两种视角：
1. 提供方测试 —— 后端实际响应是否符合 OpenAPI 定义
2. 消费方测试 —— 前端 mock 数据是否符合契约、消费逻辑是否正确
3. 双向对齐 —— 两边都通过，契约才真正成立
```

```ts
// 提供方契约测试：用 jest + OpenAPI 校验实际响应
import { validate } from './openapi-validator';

test('GET /users/:id 返回符合契约', async () => {
  const res = await request(app).get('/users/u1');
  const violations = validate('/users/{id}', 'get', 200, res.body);
  expect(violations).toEqual([]); // 响应结构与契约一致
});
```

```ts
// 消费方契约测试：前端按契约 mock，验证消费逻辑
import { rest } from 'msw';
import { server } from './mocks/server';

test('用户详情组件正确消费契约字段', async () => {
  server.use(
    rest.get('/api/users/:id', (req, res, ctx) =>
      res(ctx.json({ id: 'u1', name: 'Alice', email: 'a@x.com' })),
    ),
  );
  render(<UserDetail id="u1" />);
  expect(await screen.findByText('Alice')).toBeInTheDocument();
});
```

契约测试的关键是「用契约文件作为断言依据」：提供方测试拿契约校验响应，消费方测试按契约构造 mock。当契约变更时，测试会先失败，倒逼双方同步调整，形成闭环。

## 应用场景实战

### 场景一：从 OpenAPI 一键生成前端类型

```yaml
# 后端提供 openapi.yaml，前端用 orval 生成代码
openapi: 3.1.0
info:
  title: Shop API
  version: 1.0.0
paths:
  /products:
    get:
      operationId: listProducts
      responses:
        '200':
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/Product'
components:
  schemas:
    Product:
      type: object
      required: [id, name, price]
      properties:
        id: { type: string }
        name: { type: string }
        price: { type: number }
```

```ts
// 生成并使用的流程
// 1. npx orval   （生成 src/api/generated.ts）
// 2. 业务代码直接使用生成的类型和函数
import { listProducts, type Product } from './api/generated';

async function loadProducts(): Promise<Product[]> {
  return listProducts(); // 类型与契约完全一致
}
```

### 场景二：契约测试守住前后端一致

```ts
// 提供方契约测试：后端实现符合契约
import { validateResponse } from './contract/validator';
import { app } from './server';

test('listProducts 响应符合 OpenAPI 契约', async () => {
  const res = await request(app).get('/products');
  expect(res.status).toBe(200);
  expect(validateResponse('listProducts', res.status, res.body)).toEqual([]);
});
```

```ts
// 消费方契约测试：前端按契约 mock 消费
import { rest } from 'msw';
import { server } from './mocks/server';
import { ProductList } from './ProductList';

test('商品列表按契约字段渲染', async () => {
  server.use(
    rest.get('/products', (req, res, ctx) =>
      res(ctx.json([{ id: 'p1', name: '键盘', price: 399 }])),
    ),
  );
  render(<ProductList />);
  expect(await screen.findByText('键盘')).toBeInTheDocument();
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 契约先行：先定 OpenAPI/Schema，再前后端并行开发
2. 契约文件纳入版本控制，变更走评审流程
3. 用类型生成工具产出前端类型，禁止手写接口类型
4. 生成代码纳入 CI 校验，防止手工修改导致漂移
5. 契约测试双视角：提供方验实现、消费方验消费
6. 破坏性变更加版本号，旧契约给足废弃宽限期

### 踩坑记录

```text
坑 1：契约与实现脱节
结论：文档说返回 name，实际返回 username，前端运行时才崩。
原因：契约写完就丢一边，实现没有用契约校验。
解法：契约测试进 CI，提供方响应必须通过契约校验。

坑 2：手写接口类型
结论：手写的 User 类型和后端字段不一致，改字段时漏改。
原因：没有用类型生成，靠人肉同步接口类型。
解法：用 orval / openapi-typescript 从契约生成类型，禁止手写。

坑 3：生成的代码被手工修改
结论：重新生成代码时，手工改动被覆盖或冲突。
原因：把生成文件当普通源码随意编辑。
解法：生成文件标记只读、纳入 CI 校验，定制需求用扩展点而非改生成物。

坑 4：破坏性变更没加版本
结论：后端直接删字段，老版本前端全部报错。
原因：契约变更没有版本控制，直接覆盖。
解法：破坏性变更走新版本契约，旧版本保留宽限期。

坑 5：只在联调时才发现不一致
结论：前后端各自开发，联调阶段才暴露字段对不上，返工成本高。
原因：没有契约先行，缺少契约测试的早期反馈。
解法：契约先定 + mock 服务器 + 契约测试，开发期就对齐。
```
