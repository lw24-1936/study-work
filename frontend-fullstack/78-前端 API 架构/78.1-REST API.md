## 概述

REST（Representational State Transfer）是一种以「资源」为核心的 Web API 设计风格：每个资源用 URL 唯一标识，通过 HTTP 方法表达操作，用状态码表达结果。对前端而言，REST 是最常见、最易上手的接口范式，理解它的约定能让请求、缓存、错误处理都变得可预测。

```text
REST 的核心约束：
1. 资源导向 —— URL 表示资源，不表示动作
2. 无状态 —— 每个请求自包含全部信息
3. 统一接口 —— 用 HTTP 方法 + 状态码表达语义
4. 可缓存 —— 通过响应头声明缓存策略
5. 分层 —— 客户端不关心背后是代理还是网关
```

```text
REST 的常见 HTTP 方法语义：
GET     —— 读取资源（幂等、安全）
POST    —— 创建资源（非幂等）
PUT     —— 整体替换资源（幂等）
PATCH   —— 局部更新资源
DELETE  —— 删除资源（幂等）
```

## Resource

Resource（资源）是 REST 的核心抽象：任何可被命名、寻址的事物都可以是资源，比如一个用户、一篇文章、一个订单。资源用名词复数的 URL 表达，通过 HTTP 方法区分操作，避免把动词塞进 URL。

```text
资源命名规则：
1. 名词复数 —— /users 而不是 /getUsers
2. 层级表达 —— /users/123/orders 表达归属关系
3. 不用动词 —— 操作交给 HTTP 方法
4. 小写 + 连字符 —— /blog-posts 而非 /blogPosts
```

```text
# 反例：动词 + 复数混用
POST /api/getUserList
POST /api/createOrder

# 正例：资源 + HTTP 方法
GET    /api/users
POST   /api/users
GET    /api/users/123
PATCH  /api/users/123
DELETE /api/users/123
GET    /api/users/123/orders
```

```ts
// 前端封装的资源式 API 客户端
const api = {
  listUsers: () => request<User[]>('/api/users', { method: 'GET' }),
  createUser: (data: UserInput) => request<User>('/api/users', { method: 'POST', body: data }),
  updateUser: (id: string, data: Partial<UserInput>) =>
    request<User>(`/api/users/${id}`, { method: 'PATCH', body: data }),
  deleteUser: (id: string) => request<void>(`/api/users/${id}`, { method: 'DELETE' }),
};
```

资源的嵌套层级不宜过深：超过两层的嵌套（/a/1/b/2/c/3）往往意味着需要拆分资源或改用查询参数。资源设计的目标是让 URL 一眼能看懂「访问的是什么」。

## Version

Version（版本化）是对 API 进行不兼容变更时的管理策略：当接口的响应结构或语义发生破坏性变化，需要通过版本号让新旧客户端共存。版本号可以放在 URL 路径、查询参数或请求头里。

```text
版本化策略对比：
1. URL 路径 —— /api/v1/users，最直观、易调试
2. 查询参数 —— /api/users?version=1，较隐晦
3. 请求头 —— Accept: application/vnd.api+json;version=1，最「纯 REST」
4. 尽量不破坏 —— 优先做向后兼容的增量演进
```

```ts
// 前端统一管理 API 版本
const API_VERSION = 'v1';
const BASE_URL = `/api/${API_VERSION}`;

// 路径版本化：调用时自动带版本前缀
export const userApi = {
  list: () => request<User[]>(`${BASE_URL}/users`),
};

// 请求头版本化：显式声明期望的版本
export async function requestV2<T>(path: string): Promise<T> {
  const res = await fetch(path, {
    headers: { Accept: 'application/vnd.api+json;version=2' },
  });
  return res.json();
}
```

```text
版本演进的最佳实践：
1. 新增字段 —— 不破坏，无需新版本
2. 删除/改名字段 —— 破坏性，需要新版本
3. 变更语义 —— 破坏性，需要新版本
4. 旧版本 —— 给足废弃宽限期，发布弃用公告
```

版本化的代价是维护多套接口，因此应尽量减少破坏性变更。能用「新增可选字段 + 默认值」解决的，就不动版本号。

## Pagination

Pagination（分页）是处理大量数据返回的标准手段：接口一次性返回全部数据既慢又费内存，通过分页参数让客户端按页拉取。常见的分页方式有「页码分页」和「游标分页」两种。

```text
分页的两种模式：
1. 页码分页 —— /users?page=2&size=20，靠 page + size
2. 游标分页 —— /users?cursor=xxx&limit=20，靠游标定位
```

```text
# 页码分页的请求与响应
GET /api/users?page=2&pageSize=20

{
  "items": [ { "id": "21", "name": "..." } ],
  "page": 2,
  "pageSize": 20,
  "total": 128,
  "totalPages": 7
}
```

```ts
// 前端页码分页的封装
interface Page<T> {
  items: T[];
  page: number;
  pageSize: number;
  total: number;
  totalPages: number;
}

export async function fetchPage<T>(path: string, page: number, pageSize = 20): Promise<Page<T>> {
  const url = `${path}?page=${page}&pageSize=${pageSize}`;
  const res = await fetch(url);
  return res.json();
}

const result = await fetchPage<User>('/api/users', 2);
console.log(result.items, result.totalPages);
```

页码分页适合「数据量不大、需要跳页、展示总页数」的场景；但数据频繁增删时，页码会「漂移」（翻页过程中新插入一条，下一页可能重复或漏项）。这是游标分页要解决的问题。

## Cursor Pagination

Cursor Pagination（游标分页）用「游标」代替页码：接口返回当前批次最后一条记录的位置标记，客户端下次请求带上这个游标，服务器从该位置之后继续返回。它避免了页码分页在数据变动时的漂移问题，适合无限滚动和实时数据流。

```text
游标分页的特征：
1. 游标定位 —— 用 cursor 标记「下一页起点」
2. 无漂移 —— 不受插入/删除影响
3. 不支持跳页 —— 只能顺序向前翻
4. 适合无限流 —— 信息流、评论、订单列表
```

```text
# 游标分页的请求与响应
GET /api/orders?cursor=eyJvZmZzZXQiOjUwfQ&limit=20

{
  "items": [ { "id": "51", ... }, ... ],
  "nextCursor": "eyJvZmZzZXQiOjcwfQ",
  "hasMore": true
}
```

```ts
// 前端无限滚动的游标分页实现
interface CursorPage<T> {
  items: T[];
  nextCursor: string | null;
  hasMore: boolean;
}

export async function fetchOrders(cursor?: string): Promise<CursorPage<Order>> {
  const url = cursor ? `/api/orders?cursor=${cursor}&limit=20` : '/api/orders?limit=20';
  const res = await fetch(url);
  return res.json();
}

// 无限滚动加载
let cursor: string | undefined;
let all: Order[] = [];
do {
  const page = await fetchOrders(cursor);
  all = all.concat(page.items);
  cursor = page.nextCursor ?? undefined;
} while (page.hasMore);
```

游标通常用「排序字段 + 唯一 ID」编码而成（例如按创建时间倒序 + id），服务器据此定位。前端把游标当「不透明字符串」处理即可，不要解析其内部结构。

## Error

Error（错误处理）是 REST API 设计里容易被忽视却至关重要的部分：用正确的 HTTP 状态码表达错误类型，用统一的结构体返回错误详情，前端才能据此做统一的提示、重试和降级。

```text
常见状态码语义：
400 —— 请求参数非法
401 —— 未认证
403 —— 无权限
404 —— 资源不存在
409 —— 冲突（重复创建等）
422 —— 参数格式正确但语义不合法
429 —— 请求过于频繁
500 —— 服务器内部错误
503 —— 服务不可用
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "邮箱格式不合法",
    "details": [
      { "field": "email", "reason": "invalid_format" }
    ]
  }
}
```

```ts
// 前端统一错误处理：状态码 + 错误码双维度
export class ApiError extends Error {
  constructor(
    public status: number,
    public code: string,
    message: string,
    public details?: { field: string; reason: string }[],
  ) {
    super(message);
  }
}

export async function request<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(path, init);
  if (!res.ok) {
    const body = await res.json().catch(() => null);
    throw new ApiError(res.status, body?.error?.code ?? 'UNKNOWN', body?.error?.message ?? res.statusText);
  }
  return res.json();
}
```

错误结构要「机器可读」：稳定的 `code` 字段供前端分支处理，`message` 供人阅读，`details` 承载字段级错误。前端不应靠解析 `message` 文本判断错误类型——那会脆如玻璃。

## Idempotency

Idempotency（幂等性）指同一操作执行多次与执行一次结果相同。在网络不可靠的场景（超时重试、用户重复点击）下，幂等设计能防止「重复下单」「重复扣款」。GET/PUT/DELETE 天然幂等，POST 需要额外机制保证。

```text
幂等性要点：
1. 天然幂等 —— GET、PUT、DELETE
2. 非幂等 —— POST（创建类）
3. 靠幂等键 —— 客户端生成唯一键，服务器去重
4. 重试安全 —— 幂等才能放心重试
```

```text
# 客户端生成幂等键，随请求发送
POST /api/orders
Idempotency-Key: 8f3a9c2e-1b4d-4a5e-9c7f-6d2b8e0a1f3c
```

```ts
// 前端：为「下单」生成幂等键，重试复用同一键
import { v4 as uuid } from 'uuid';

export async function placeOrder(payload: OrderInput): Promise<Order> {
  const idempotencyKey = uuid();
  try {
    return await request<Order>('/api/orders', {
      method: 'POST',
      headers: { 'Idempotency-Key': idempotencyKey },
      body: payload,
    });
  } catch (e) {
    // 网络错误时用同一键重试，服务器保证不重复创建
    return request<Order>('/api/orders', {
      method: 'POST',
      headers: { 'Idempotency-Key': idempotencyKey },
      body: payload,
    });
  }
}
```

幂等键的实现要点：客户端为「一次业务意图」生成一个键，重试时复用；服务器用该键做去重，把重复请求映射到首次结果。这样即使请求超时但服务器已处理，重试也不会产生副作用。

## 应用场景实战

### 场景一：前端通用分页列表组件

```tsx
// 一个支持游标分页 + 错误处理的列表组件
import { useState } from 'react';
import { fetchOrders } from './api/orders';

export function OrderList() {
  const [orders, setOrders] = useState<Order[]>([]);
  const [cursor, setCursor] = useState<string | undefined>();
  const [hasMore, setHasMore] = useState(true);
  const [error, setError] = useState<string | null>(null);

  const loadMore = async () => {
    try {
      const page = await fetchOrders(cursor);
      setOrders((prev) => [...prev, ...page.items]);
      setCursor(page.nextCursor ?? undefined);
      setHasMore(page.hasMore);
    } catch (e) {
      setError(e instanceof ApiError ? e.message : '加载失败');
    }
  };

  return (
    <div>
      <ul>{orders.map((o) => <li key={o.id}>{o.id}</li>)}</ul>
      {error && <p className="error">{error}</p>}
      {hasMore && <button onClick={loadMore}>加载更多</button>}
    </div>
  );
}
```

### 场景二：带幂等键的表单提交

```tsx
// 防重复提交：禁用按钮 + 幂等键 + 错误码分支
export function CheckoutForm() {
  const [submitting, setSubmitting] = useState(false);

  const submit = async (payload: OrderInput) => {
    setSubmitting(true);
    try {
      const order = await placeOrder(payload); // 内部带幂等键
      redirectTo(`/orders/${order.id}`);
    } catch (e) {
      if (e instanceof ApiError && e.code === 'DUPLICATE_ORDER') {
        toast('订单已存在，请勿重复提交');
      } else if (e instanceof ApiError && e.code === 'INSUFFICIENT_STOCK') {
        toast('库存不足');
      } else {
        toast('提交失败，请重试');
      }
    } finally {
      setSubmitting(false);
    }
  };

  return (
    <form onSubmit={(e) => { e.preventDefault(); submit(collect(e)); }}>
      <button disabled={submitting}>{submitting ? '提交中...' : '提交订单'}</button>
    </form>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 资源用名词复数，动作交给 HTTP 方法，URL 不用动词
2. 状态码用对，错误结构统一且带稳定的机器可读 code
3. 列表接口默认分页，数据可能很大时用游标分页
4. 写操作（POST/PUT/DELETE）考虑幂等，关键创建接口加幂等键
5. 版本化只在破坏性变更时引入，优先向后兼容演进
6. 前端封装统一请求层，集中处理鉴权、错误、重试

### 踩坑记录

```text
坑 1：URL 里塞动词
结论：/api/getUsers、/api/deleteOrder 这类接口难以维护、缓存策略混乱。
原因：没有区分资源与操作，把动作写进 URL。
解法：URL 只表达资源，操作用 HTTP 方法（GET/POST/DELETE）。

坑 2：页码分页数据漂移
结论：翻页过程中新数据插入，下一页出现重复或漏掉记录。
原因：页码分页按偏移量定位，数据变化导致偏移错位。
解法：数据频繁变动的场景改用游标分页，或接受页码分页的近似语义。

坑 3：靠解析错误 message 文本判断类型
结论：前端 if (msg.includes('库存')) 判断错误，后端改文案就崩。
原因：错误结构里没有稳定的 code 字段，前端只能猜文本。
解法：后端返回稳定的错误码，前端按 code 分支处理。

坑 4：重复点击导致重复下单
结论：用户狂点提交，创建了多条重复订单。
原因：POST 非幂等，客户端没有做防重和幂等键。
解法：提交时禁用按钮 + 服务端幂等键去重，双保险。

坑 5：一次性返回全量数据
结论：列表接口返回几万条，前端卡顿、内存飙升。
原因：没有分页设计，默认全量返回。
解法：默认分页，超大数据用游标分页 + 按需加载。
```
