## 概述

GraphQL 是 Facebook 开源的一套 API 查询语言与运行时：客户端声明「要什么字段」，服务器就精确返回这些字段，一次请求即可取到跨多个资源的数据。它解决了 REST 的两大痛点——「过度获取」（返回不需要的字段）和「获取不足」（要跑多个接口拼数据），让前端完全掌控响应的形状。

```text
GraphQL 的核心特点：
1. 单一端点 —— 所有请求走同一个 /graphql
2. 按需取数 —— 客户端声明字段，响应与之同构
3. 强类型 Schema —— 类型系统是接口契约
4. 一次请求多资源 —— 一个 query 关联多个对象
5. 三种操作 —— Query（读）、Mutation（写）、Subscription（订阅）
```

```graphql
# 客户端按需声明字段，响应结构完全一致
query {
  user(id: "1") {
    name
    email
    orders {
      id
      total
    }
  }
}
```

```json
{
  "data": {
    "user": {
      "name": "Alice",
      "email": "alice@example.com",
      "orders": [ { "id": "o1", "total": 399 } ]
    }
  }
}
```

## Schema

Schema（模式）是 GraphQL 的类型定义，也是客户端与服务端之间的「契约」：它定义了有哪些类型、每个类型有哪些字段、字段接受什么参数、支持哪些查询和变更。Schema 用 SDL（Schema Definition Language）书写，是 GraphQL 强类型的根基。

```text
Schema 的组成：
1. 对象类型 —— type User { ... }
2. 标量类型 —— String、Int、Float、Boolean、ID
3. 枚举 —— enum OrderStatus { ... }
4. 输入类型 —— input UserInput { ... }
5. 根类型 —— Query / Mutation / Subscription
```

```graphql
# schema.graphql —— 一个电商的 Schema 定义
type Query {
  user(id: ID!): User
  products(category: String): [Product!]!
}

type Mutation {
  createOrder(input: OrderInput!): Order!
}

type User {
  id: ID!
  name: String!
  email: String!
  orders: [Order!]!
}

type Product {
  id: ID!
  name: String!
  price: Float!
  category: String
}

type Order {
  id: ID!
  total: Float!
  status: OrderStatus!
}

enum OrderStatus {
  PENDING
  PAID
  SHIPPED
}

input OrderInput {
  userId: ID!
  items: [OrderItemInput!]!
}

input OrderItemInput {
  productId: ID!
  quantity: Int!
}
```

Schema 是「单一事实来源」：前端可以据此做代码生成（生成 TypeScript 类型和 hooks），后端据此校验请求。`!` 表示非空，`[Type!]!` 表示「非空的数组且元素非空」——类型系统能精确表达字段的可空性。

## Resolver

Resolver（解析器）是「字段值的实际计算函数」：Schema 只声明了「有什么」，Resolver 定义「怎么算」。每个字段都对应一个 resolver，根类型的 resolver 处理入口查询，对象类型的 resolver 处理嵌套字段的取值。

```text
Resolver 的职责：
1. 根字段 —— 处理 Query/Mutation 的入口逻辑
2. 嵌套字段 —— 计算对象类型字段的值
3. 参数解析 —— 接收并校验字段参数
4. 数据获取 —— 从数据库/服务取数并返回
```

```ts
// 用 Apollo Server 定义 resolver
const resolvers = {
  Query: {
    user: async (_parent, { id }, { db }) => {
      return db.users.findById(id); // 根字段：查用户
    },
  },
  User: {
    orders: async (parent, _args, { db }) => {
      return db.orders.findByUserId(parent.id); // 嵌套字段：用父对象取订单
    },
  },
  Mutation: {
    createOrder: async (_parent, { input }, { db }) => {
      return db.orders.create(input);
    },
  },
};
```

Resolver 的四个参数值得记住：`parent`（父字段返回值，根字段为 undefined）、`args`（字段参数）、`context`（共享上下文，如鉴权用户、数据源）、`info`（AST 元信息）。嵌套 resolver 收到 `parent` 就能「从父对象推导子字段」，这是关联数据的关键机制。

## Query

Query（查询）是 GraphQL 的读操作：客户端通过 `query` 声明要读取的字段，服务器按 Schema 校验并返回。Query 与 REST 的 GET 对应，但更灵活——一次 query 可以同时取多个资源、可以指定字段参数、可以嵌套关联。

```text
Query 的特性：
1. 只读 —— 不产生副作用
2. 按需字段 —— 只取声明的字段
3. 支持参数 —— 字段可带参数（分页、过滤）
4. 可嵌套 —— 关联对象一层层取
```

```graphql
query GetUserOrders($userId: ID!, $limit: Int!) {
  user(id: $userId) {
    name
    orders(limit: $limit) {
      id
      total
      items {
        product { name }
        quantity
      }
    }
  }
}
```

```ts
// 前端用 Apollo Client 执行带变量的查询
import { gql, useQuery } from '@apollo/client';

const GET_USER_ORDERS = gql`
  query GetUserOrders($userId: ID!, $limit: Int!) {
    user(id: $userId) {
      name
      orders(limit: $limit) {
        id
        total
      }
    }
  }
`;

function UserOrders({ userId }: { userId: string }) {
  const { data, loading, error } = useQuery(GET_USER_ORDERS, {
    variables: { userId, limit: 10 },
  });
  if (loading) return <p>加载中...</p>;
  if (error) return <p>出错了</p>;
  return <ul>{data.user.orders.map((o) => <li key={o.id}>{o.total}</li>)}</ul>;
}
```

Query 的威力在「字段级按需」：移动端只需 `name`，桌面端需要完整字段，两者用同一 Schema 却返回不同形状，无需为不同端维护不同接口。

## Mutation

Mutation（变更）是 GraphQL 的写操作：创建、更新、删除数据。Mutation 的字段「串行执行」而非并行（Query 是并行的），因为写操作有副作用，顺序必须保证。Mutation 通常返回被修改的对象，方便客户端同步缓存。

```text
Mutation 的特性：
1. 有副作用 —— 创建/更新/删除
2. 串行执行 —— 字段按顺序依次执行
3. 输入对象 —— 用 input 类型承载复杂参数
4. 返回结果 —— 返回新对象供客户端更新缓存
```

```graphql
mutation CreateOrder($input: OrderInput!) {
  createOrder(input: $input) {
    id
    total
    status
  }
}
```

```ts
// 前端执行 Mutation，并更新本地缓存
import { gql, useMutation } from '@apollo/client';

const CREATE_ORDER = gql`
  mutation CreateOrder($input: OrderInput!) {
    createOrder(input: $input) {
      id
      total
      status
    }
  }
`;

function CheckoutButton({ input }: { input: OrderInput }) {
  const [createOrder, { loading }] = useMutation(CREATE_ORDER, {
    onCompleted: (data) => {
      router.push(`/orders/${data.createOrder.id}`);
    },
  });

  return (
    <button disabled={loading} onClick={() => createOrder({ variables: { input } })}>
      {loading ? '提交中...' : '提交订单'}
    </button>
  );
}
```

Mutation 与 Query 的严格区分是 GraphQL 的设计纪律：查询走 Query（可缓存、可并行），写操作走 Mutation（有副作用、串行）。把写操作放进 Query 会导致缓存与副作用混乱。

## Subscription

Subscription（订阅）是 GraphQL 的实时推送机制：客户端订阅某个事件，服务器通过持久连接（通常是 WebSocket）把更新实时推给客户端。它适合聊天消息、实时价格、通知等「数据会自己变化」的场景。

```text
Subscription 的特性：
1. 实时推送 —— 服务器主动推，客户端被动收
2. 持久连接 —— 通常基于 WebSocket
3. 事件驱动 —— 订阅特定事件流
4. 三阶段 —— 建立订阅、持续推送、取消订阅
```

```graphql
subscription OnOrderStatusChanged($orderId: ID!) {
  orderStatusChanged(orderId: $orderId) {
    id
    status
    updatedAt
  }
}
```

```ts
// 前端订阅订单状态变化
import { gql, useSubscription } from '@apollo/client';

const ON_ORDER_STATUS = gql`
  subscription OnOrderStatusChanged($orderId: ID!) {
    orderStatusChanged(orderId: $orderId) {
      id
      status
    }
  }
`;

function OrderStatus({ orderId }: { orderId: string }) {
  const { data } = useSubscription(ON_ORDER_STATUS, {
    variables: { orderId },
  });

  const status = data?.orderStatusChanged.status ?? 'unknown';
  return <span>订单状态：{status}</span>;
}
```

Subscription 不是银弹：如果只是「定时轮询」就能满足的更新，用轮询更简单；只有真正需要低延迟推送时才用订阅。订阅连接的管理（断线重连、心跳、背压）也要纳入考虑。

## DataLoader

DataLoader 是 GraphQL 解决 N+1 查询问题的批处理与缓存工具：当嵌套 resolver 逐个查询时，会产生大量重复请求（N 个订单各自查一次商品，就是 N+1）。DataLoader 把同一事件循环内的多个独立加载请求「合并」成一次批量查询，并做请求级缓存。

```text
N+1 问题：
1. 查用户 —— 1 次查询
2. 每个用户的订单 —— N 次查询
3. 每个订单的商品 —— N x M 次查询
4. 总请求数爆炸 —— 数据库被打满
```

```ts
// 不用 DataLoader：每个订单都单独查一次商品（N+1）
const resolvers = {
  OrderItem: {
    product: async (parent, _args, { db }) => {
      return db.products.findById(parent.productId); // N 次独立查询
    },
  },
};
```

```ts
// 用 DataLoader：同一批次的 productId 合并成一次 IN 查询
import DataLoader from 'dataloader';

const productLoader = new DataLoader(async (ids: readonly string[]) => {
  const products = await db.products.findByIds(ids); // 一次批量查询
  const map = new Map(products.map((p) => [p.id, p]));
  return ids.map((id) => map.get(id) ?? null); // 保持顺序
});

const resolvers = {
  OrderItem: {
    product: (parent, _args, { loaders }) => {
      return loaders.product.load(parent.productId); // 自动合并 + 缓存
    },
  },
};
```

DataLoader 的两个关键机制：批处理（batching）把同一 tick 的加载合并成一次查询，缓存（caching）保证同一请求内相同 key 只查一次。它是「性能优化」而非「业务逻辑」，应放在 context 里统一注入。

## 应用场景实战

### 场景一：页面一次取齐多资源

```graphql
# 首页一次请求取用户、商品、购物车三块数据（REST 要三个接口）
query HomePageData($userId: ID!) {
  me: user(id: $userId) {
    name
    avatar
  }
  featuredProducts: products(featured: true) {
    id
    name
    price
  }
  cart {
    itemCount
    total
  }
}
```

```ts
// 前端一次查询拿到整页数据
const { data } = useQuery(HOME_PAGE_DATA, { variables: { userId } });
// data.me、data.featuredProducts、data.cart 一次到位
```

### 场景二：结合 DataLoader 的订单详情

```ts
// 服务端：订单详情聚合了订单 + 商品 + 用户，DataLoader 避免 N+1
const orderResolvers = {
  Query: {
    orders: (_p, { limit }, { db }) => db.orders.list(limit),
  },
  Order: {
    user: (parent, _a, { loaders }) => loaders.user.load(parent.userId),
  },
  OrderItem: {
    product: (parent, _a, { loaders }) => loaders.product.load(parent.productId),
  },
};
```

## 最佳实践与踩坑记录

### 最佳实践

1. Schema 优先设计：先定类型契约，再实现 resolver
2. 用 input 类型承载 Mutation 参数，避免散落的标量参数
3. 嵌套关联用 DataLoader 批处理，杜绝 N+1 查询
4. 客户端按需取字段，不要无脑 `__typename` 全量拉取
5. 错误用 GraphQL 的 errors 字段 + 扩展 code 表达，别只返回 null
6. 写操作严格走 Mutation，读操作走 Query，不混用

### 踩坑记录

```text
坑 1：N+1 查询打爆数据库
结论：列表查询触发海量嵌套查询，接口秒级变慢、数据库 CPU 飙升。
原因：嵌套 resolver 逐条查询，没有批处理。
解法：用 DataLoader 合并批次查询，或让根 resolver 一次性 join 出关联数据。

坑 2：Schema 不校验导致返回 null
结论：字段声明了非空 !，resolver 却返回 null，直接报错。
原因：resolver 数据源可能查不到，但类型声明为非空。
解法：可能缺失的字段声明为可空，或让 resolver 保证非空（查不到就抛错）。

坑 3：Mutation 与 Query 混用
结论：把写操作放进 Query，导致缓存失效、副作用不可控。
原因：图省事把创建接口写成 query。
解法：有副作用的操作一律用 Mutation，读操作才用 Query。

坑 4：客户端过度获取字段
结论：GraphQL 反而比 REST 更慢，响应体积巨大。
原因：客户端无脑声明全量字段，放弃了按需取数的优势。
解法：按页面实际需求裁剪字段，配合 persisted query 和 fragment 复用。

坑 5：错误只返回 null
结论：接口出错时前端只拿到 null，无法判断是没数据还是出错。
原因：resolver 吞掉异常返回 null，错误信息丢失。
解法：抛出 GraphQLError 并带扩展 code，前端在 errors 数组里读错误详情。
```
