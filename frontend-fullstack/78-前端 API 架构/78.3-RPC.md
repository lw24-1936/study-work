## 概述

RPC（Remote Procedure Call，远程过程调用）让「调用远程服务」像「调用本地函数」一样自然：客户端直接调用 `getUser(id)`，框架负责把请求序列化、传输、反序列化并返回结果。它与 REST 的核心区别在于「面向过程/方法」而非「面向资源」，更强调类型安全和跨语言的服务间通信。

```text
RPC 的核心思想：
1. 像本地函数 —— 调用远程方法如同调用本地函数
2. 接口先行 —— 用 IDL 定义服务契约，再生成代码
3. 强类型 —— 参数与返回值都有明确类型
4. 跨语言 —— 同一契约生成多语言客户端/服务端
5. 高效序列化 —— 通常用二进制格式
```

```text
RPC vs REST 的取舍：
RPC  —— 面向方法、强类型、二进制、适合服务间高频通信
REST —— 面向资源、松耦合、文本 JSON、适合浏览器直接访问
```

## gRPC

gRPC 是 Google 开源的高性能 RPC 框架，以 HTTP/2 为传输协议、Protobuf 为序列化格式，支持四种调用模式（一元、服务端流、客户端流、双向流）。它默认走二进制协议，浏览器无法直接访问，通常通过 gRPC-Web 或网关桥接。

```text
gRPC 的特性：
1. HTTP/2 —— 多路复用、头部压缩、双向流
2. Protobuf —— 高效二进制序列化
3. 四种调用 —— 一元 / 服务端流 / 客户端流 / 双向流
4. 强类型契约 —— .proto 生成代码
```

```proto
// order.proto —— 用 Protobuf 定义服务和消息
syntax = "proto3";

package ecommerce;

service OrderService {
  rpc CreateOrder(CreateOrderRequest) returns (Order);
  rpc ListOrders(ListOrdersRequest) returns (stream Order); // 服务端流
}

message CreateOrderRequest {
  string user_id = 1;
  repeated OrderItem items = 2;
}

message OrderItem {
  string product_id = 1;
  int32 quantity = 2;
}

message Order {
  string id = 1;
  double total = 2;
  string status = 3;
}
```

```ts
// 前端通过 gRPC-Web 调用（代码由 proto 生成）
import { OrderServiceClient } from './generated/order_grpc_web_pb';

const client = new OrderServiceClient('https://api.example.com');

const req = new CreateOrderRequest();
req.setUserId('u1');
const order = await client.createOrder(req, {});
console.log(order.getId());
```

gRPC 的四种调用模式里，最常用的是「一元调用」（一问一答）；流式调用适合大文件传输、实时推送等场景。对前端来说，gRPC-Web 是浏览器接入 gRPC 的标准方式，但功能受限（不支持客户端流、双向流需额外代理）。

## Connect

Connect 是 Buf 推出的 RPC 协议族：它在 gRPC 的基础上，让同一套服务定义同时支持 gRPC、gRPC-Web 和 Connect 三种协议，并且能生成「浏览器友好的 TypeScript 客户端」。Connect 的核心价值是「前端直接、类型安全地调用后端 RPC，无需手写 HTTP 胶水」。

```text
Connect 的价值：
1. 三协议合一 —— gRPC / gRPC-Web / Connect 一个服务全支持
2. 浏览器友好 —— 生成的 TS 客户端可直接在浏览器跑
3. 类型安全 —— 端到端的类型，前端后端共享契约
4. 可与 REST 共存 —— 支持普通 JSON 的 unary 调用
```

```proto
// 同一个 .proto 生成 Connect 客户端
service GreetService {
  rpc Greet(GreetRequest) returns (GreetResponse);
}
```

```ts
// 前端用 Connect 生成的客户端，像调用本地函数
import { createClient } from '@connectrpc/connect';
import { createConnectTransport } from '@connectrpc/connect-web';
import { GreetService } from './gen/greet_connect';

const transport = createConnectTransport({
  baseUrl: 'https://api.example.com',
});

const client = createClient(GreetService, transport);

const res = await client.greet({ name: 'Alice' });
console.log(res.greeting); // 完全类型安全，无手写 fetch
```

Connect 对前端最有吸引力的点是「类型端到端」：后端改 proto 字段，前端编译期就报错，不用靠文档对齐。它用标准 HTTP/1.1 + POST 也能跑，比纯 gRPC 更贴近浏览器环境。

## Protobuf

Protobuf（Protocol Buffers）是 Google 的二进制序列化格式与 IDL：用 `.proto` 文件定义消息结构，用字段编号（field number）代替字段名存储，生成多语言的数据类型代码。它比 JSON 更小、更快，且字段编号带来向后兼容性。

```text
Protobuf 的特性：
1. 二进制编码 —— 体积小、解析快
2. 字段编号 —— 用数字标识字段，改名不影响兼容
3. 强类型 —— 每个字段有明确类型
4. 代码生成 —— 生成各语言的 get/set 类
```

```proto
// 字段编号是兼容性的关键
message User {
  string id = 1;        // 编号 1
  string name = 2;      // 编号 2
  string email = 3;     // 编号 3
  int32 age = 4;        // 编号 4
}

// 新增字段用新编号，旧数据仍能解析
message User {
  string id = 1;
  string name = 2;
  string email = 3;
  int32 age = 4;
  string avatar = 5;    // 新增，向后兼容
}
```

```text
Protobuf 与 JSON 对比：
Protobuf —— 二进制、紧凑、有 Schema、跨语言、向后兼容强
JSON     —— 文本、可读、无 Schema 强制、浏览器原生支持
```

Protobuf 的向后兼容规则：字段编号一旦使用就「永久占用」，删除字段要标记 `reserved` 防止编号复用。新增字段必须用新编号，这样旧客户端能忽略新字段、新客户端能容错旧数据。

## Serialization

Serialization（序列化）是把内存中的数据结构转成可传输/可存储格式（字节流、文本）的过程，反序列化则是逆向还原。RPC 的每一次调用都依赖序列化：请求对象序列化后传输，服务器反序列化再处理，结果再序列化返回。

```text
序列化格式对比：
1. JSON —— 文本、可读、体积大、无 Schema
2. Protobuf —— 二进制、紧凑、有 Schema
3. MessagePack —— 二进制、紧凑、无 Schema
4. 选型考量 —— 可读性、体积、速度、Schema 需求
```

```ts
// JSON 序列化/反序列化
const obj = { id: 'u1', name: 'Alice', age: 30 };
const json = JSON.stringify(obj);        // 序列化
const back = JSON.parse(json);           // 反序列化

// MessagePack 二进制序列化
import { encode, decode } from '@msgpack/msgpack';
const bytes = encode(obj);               // 二进制序列化
const back2 = decode(bytes) as typeof obj; // 反序列化
```

```ts
// Protobuf 序列化（以 protobuf-ts 为例）
import { User } from './gen/user_pb';

const user = User.create({ id: 'u1', name: 'Alice', age: 30 });
const bytes = User.toBinary(user);       // 二进制序列化
const restored = User.fromBinary(bytes); // 反序列化
```

序列化的关键考量：二进制格式（Protobuf/MessagePack）适合高频、大流量的服务间通信，能显著减小带宽和延迟；文本格式（JSON）适合浏览器直连和调试。RPC 框架通常封装了序列化，开发者只需定义消息结构。

## 应用场景实战

### 场景一：前端通过 Connect 调用类型安全的 RPC

```proto
// product.proto —— 商品服务定义
syntax = "proto3";

package shop;

service ProductService {
  rpc GetProduct(GetProductRequest) returns (Product);
  rpc SearchProducts(SearchRequest) returns (stream Product);
}

message GetProductRequest { string id = 1; }
message SearchRequest { string query = 1; int32 limit = 2; }
message Product {
  string id = 1;
  string name = 2;
  double price = 3;
}
```

```ts
// 前端：生成的客户端 + React hooks 封装
import { createClient } from '@connectrpc/connect';
import { createConnectTransport } from '@connectrpc/connect-web';
import { ProductService } from './gen/product_connect';
import { GetProductRequest } from './gen/product_pb';

const client = createClient(ProductService, createConnectTransport({
  baseUrl: 'https://api.example.com',
}));

export async function fetchProduct(id: string) {
  const res = await client.getProduct({ id }); // 类型自动推导
  return res; // { id, name, price }
}
```

### 场景二：gRPC-Web 服务端流（实时推送）

```ts
// 服务端流：订阅价格变化，服务器持续推送
import { ProductServiceClient } from './gen/product_grpc_web_pb';
import { SearchRequest } from './gen/product_pb';

const client = new ProductServiceClient('https://api.example.com');

const req = new SearchRequest();
req.setQuery('phone');
req.setLimit(10);

// 服务端流：onData 持续收到推送
const stream = client.searchProducts(req, {});
stream.on('data', (product) => {
  console.log('收到商品', product.getName(), product.getPrice());
});
stream.on('end', () => console.log('流结束'));
```

## 最佳实践与踩坑记录

### 最佳实践

1. 接口先行：先写 proto / IDL 定契约，再实现服务端与客户端
2. 字段编号永久保留，删除字段用 reserved，绝不复用旧编号
3. 浏览器接入 gRPC 优先考虑 Connect / gRPC-Web，而非裸 gRPC
4. 序列化格式按场景选：服务间用 Protobuf，浏览器直连用 JSON
5. 生成代码纳入版本控制，CI 里校验 proto 与生成代码一致
6. 把 RPC 调用封装成领域友好的函数，别让 proto 类型穿透到组件深处

### 踩坑记录

```text
坑 1：字段编号复用导致数据错乱
结论：删除旧字段后用它的编号定义新字段，旧数据被错误解析。
原因：不了解 Protobuf 的编号兼容规则，随意复用编号。
解法：删除字段标 reserved，新字段用从未使用过的编号。

坑 2：浏览器直连 gRPC 失败
结论：gRPC 依赖 HTTP/2 trailer 等特性，浏览器原生 fetch 无法直连。
原因：把服务端 gRPC 端口直接暴露给前端。
解法：用 gRPC-Web 或 Connect 协议桥接，或加 Envoy 网关。

坑 3：proto 类型穿透到组件深处
结论：组件里到处都是 proto 生成的 getXxx/setXxx，业务逻辑与传输耦合。
原因：生成类型直接作为领域模型使用，没有做转换。
解法：在数据层做 proto 到领域对象的映射，组件只依赖领域类型。

坑 4：序列化格式选错
结论：内部服务用 JSON 导致体积大、延迟高，或对浏览器用 Protobuf 导致难调试。
原因：没有按场景权衡序列化格式。
解法：高频服务间通信用 Protobuf，浏览器直连与调试用 JSON。

坑 5：忽略生成的代码与 proto 同步
结论：proto 改了但生成代码没重新生成，前后端类型不一致，运行时才暴露。
原因：生成代码手改或未纳入自动化流程。
解法：生成代码入版本库，CI 用 buf/代码生成工具校验一致性。
```
