## 概述

工程质量是大厂用「可度量的指标」管理软件品质的实践：测试用金字塔分层保障正确性，SLO 和 Error Budget 量化可用性目标，Performance Budget 约束性能红线，Security Review 守住安全底线。核心思想是「质量不是感觉，是数字」——先定义目标，再用指标驱动，让质量可衡量、可追踪、可问责。

```text
工程质量的五个支柱：
1. Test Pyramid —— 分层测试策略，用最少的成本守住正确性
2. SLO —— 服务级别目标，量化「可用性」的承诺
3. Error Budget —— 错误预算，把「可用性目标」转化为可消耗的额度
4. Performance Budget —— 性能预算，给加载速度设红线
5. Security Review —— 安全评审，把安全风险挡在发布前
```

```text
质量从定义开始：
先定义「好」的量化标准 → 再建立度量 → 最后用门槛守护
```

## Test Pyramid

Test Pyramid（测试金字塔）是分层的测试策略：底层是大量快速廉价的单元测试，中间是适量的集成测试，顶层是少量慢而贵的端到端测试。金字塔强调「测试越靠近底层，数量越多、成本越低」，用最少的成本获得最大的信心。

```text
# 测试金字塔
        /\
       /E2E\        少量：端到端测试（慢、贵、覆盖关键链路）
      /------\
     / 集成  \      适量：集成测试（模块协作、接口契约）
    /----------\
   /   单元测试  \   大量：单元测试（快、便宜、覆盖核心逻辑）
  /--------------\
```

```ts
// 底层：单元测试（多而快）
import { calcSubtotal } from './order';

describe('calcSubtotal', () => {
  it('sums quantity * price', () => {
    expect(calcSubtotal([{ quantity: 2, price: 10 }])).toBe(20);
  });
});
```

```ts
// 中层：集成测试（验证模块协作）
import { orderService } from './orderService';
import { db } from './db';

test('creates and retrieves an order', async () => {
  const id = await orderService.create({ items: [{ sku: 'a', quantity: 1 }] });
  const order = await orderService.get(id);
  expect(order.items).toHaveLength(1);
});
```

```text
测试金字塔的配比原则：
1. 单元测试 70% —— 逻辑正确性，毫秒级
2. 集成测试 20% —— 模块协作、接口契约
3. E2E 测试 10% —— 关键用户旅程，秒级
4. 反模式：倒金字塔（E2E 过多）又慢又脆
```

## SLO

SLO（Service Level Objective，服务级别目标）是服务可用性的量化承诺，例如「99.9% 的请求在 300ms 内成功返回」。它用明确的指标 + 目标值定义「什么叫可用」，是可用性管理的锚点。

```text
# 前端常见的 SLO 指标
1. 可用性 —— 成功请求占比 ≥ 99.9%
2. 延迟 —— p95 首屏时间 ≤ 3s
3. 错误率 —— 5xx 错误占比 ≤ 0.1%
4. 页面可用 —— 关键页面加载成功率 ≥ 99.5%
```

```yaml
# SLO 定义示例（前端关键指标）
slo:
  availability:
    metric: "successful_requests / total_requests"
    target: "99.9%"          # 目标值
    window: "30d"            # 统计窗口
  latency:
    metric: "p95_first_contentful_paint"
    target: "3000ms"
  error_rate:
    metric: "js_errors / page_views"
    target: "0.1%"
```

```text
SLO 与 SLA 的区别：
1. SLO —— 内部目标，团队自己定的可用性承诺
2. SLA —— 对外合同，违反要赔偿，通常比 SLO 更宽松
3. SLO 应严于 SLA，给自己留缓冲
```

## Error Budget

Error Budget（错误预算）是「可用性目标允许消耗的故障额度」：SLO 是 99.9%，就意味着一个月有 0.1% 的「预算」可以犯错。错误预算把可用性从「模糊的追求」变成「可消耗、可决策的资源」——预算充足时可以大胆发布，预算耗尽则冻结发布、优先稳定。

```text
# 错误预算的计算
SLO = 99.9% → 允许不可用 = 0.1%
一个月 30 天 = 43200 分钟
错误预算 = 43200 × 0.1% ≈ 43 分钟/月
```

```js
// 错误预算监控：实时计算剩余预算
function calcErrorBudget({ target = 0.999, window = 30 * 24 * 60, downtimeMin }) {
  const budget = window * (1 - target); // 允许的总不可用分钟
  const remaining = budget - downtimeMin;
  const ratio = remaining / budget;
  return { remainingMin: remaining, ratio };
}

// 预算耗尽 80% 时告警，100% 时冻结发布
const { ratio } = calcErrorBudget({ downtimeMin: 35 });
if (ratio < 0.2) console.warn('错误预算告急，冻结发布');
```

```text
错误预算驱动的决策：
1. 预算充足（>50%）—— 可以正常发布、做实验
2. 预算告急（<20%）—— 收紧发布，优先稳定性
3. 预算耗尽 —— 冻结新功能发布，全力恢复
```

## Performance Budget

Performance Budget（性能预算）给关键性能指标设上限，例如「首屏 ≤ 3s」「JS 体积 ≤ 300KB」。它把性能从「事后优化」变成「事前约束」，在开发和 CI 阶段就守住性能红线。

```json
// Lighthouse 性能预算：CI 里断言关键指标
{
  "ci": {
    "assert": {
      "assertions": {
        "first-contentful-paint": ["error", { "maxNumericValue": 1800 }],
        "largest-contentful-paint": ["error", { "maxNumericValue": 2500 }],
        "total-blocking-time": ["error", { "maxNumericValue": 300 }],
        "cumulative-layout-shift": ["error", { "maxNumericValue": 0.1 }]
      }
    }
  }
}
```

```js
// webpack 产物体积预算
module.exports = {
  performance: {
    maxEntrypointSize: 350_000, // 350KB
    maxAssetSize: 250_000,      // 250KB
    hints: 'error',
  },
};
```

```text
性能预算的分层：
1. 指标预算 —— LCP/TBT/CLS 等核心指标设上限
2. 体积预算 —— JS/CSS/图片体积设红线
3. 数量预算 —— 请求数、依赖数设上限
```

## Security Review

Security Review（安全评审）在发布前系统性地检查安全风险：注入、越权、数据泄漏、依赖漏洞、密钥管理等。它把安全作为「发布门槛」而非「事后补救」，高风险产品上线前必须通过安全评审。

```text
# 前端安全评审检查清单
1. XSS —— 是否做了输出转义、是否用 dangerouslySetInnerHTML
2. CSRF —— 写操作是否有防护
3. 依赖漏洞 —— npm audit 是否通过
4. 密钥泄漏 —— 是否有硬编码的 token/密钥
5. 越权 —— 前端鉴权是否只是「藏起来」，后端是否真的校验
6. 敏感数据 —— 是否在日志/埋点里泄漏隐私
```

```js
// 安全评审关注的危险写法示例
// 1. 危险：直接插入 HTML（XSS 风险）
function renderComment(html) {
  return <div dangerouslySetInnerHTML={{ __html: html }} />; // 需评审
}

// 2. 危险：硬编码密钥
const API_KEY = 'sk-xxxx-secret-key'; // 禁止，应走环境变量
```

```text
安全评审的流程：
1. 自查清单 —— 开发者按清单自评
2. 安全评审 —— 安全负责人逐项复核
3. 自动化扫描 —— SAST/依赖扫描接入 CI
4. 高风险专项 —— 涉及资金、隐私的功能专项评审
```

## 应用场景实战

### 场景一：CI 里落地测试金字塔 + 性能预算 + 依赖安全

```yaml
# .github/workflows/quality.yml —— 工程质量一体化门槛
name: Quality Gate
on: pull_request

jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test -- --coverage   # 单元测试（塔底，最多）

  integration:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run test:integration  # 集成测试（适量）

  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run test:e2e          # E2E（少量关键链路）

  perf-security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build
      - run: npx size-limit            # 性能预算
      - run: npm audit --audit-level=high  # 依赖安全
```

### 场景二：错误预算驱动的发布决策

```js
// 监控错误预算，决定是否允许发布
const SLO = 0.999;
const WINDOW_MIN = 30 * 24 * 60;
const downtimeMin = queryDowntimeLast30Days(); // 从监控系统查询

function budgetStatus(downtimeMin) {
  const budget = WINDOW_MIN * (1 - SLO);
  const ratio = 1 - downtimeMin / budget;

  if (ratio <= 0) return '耗尽：冻结发布，全力恢复可用性';
  if (ratio < 0.2) return '告急：收紧发布，只允许修复类变更';
  if (ratio < 0.5) return '偏低：谨慎发布，控制变更规模';
  return '充足：正常发布，可做灰度与实验';
}

console.log(budgetStatus(downtimeMin));
// 输出示例：偏低：谨慎发布，控制变更规模
```

## 最佳实践与踩坑记录

### 最佳实践

1. 测试按金字塔分层，单元测试为主体，E2E 只覆盖关键链路
2. SLO 要量化、可测、有窗口，而非「尽量好」的模糊承诺
3. 错误预算与发布决策挂钩，预算耗尽即冻结发布
4. 性能预算写进 CI，超出即失败，倒逼优化而非事后补救
5. 安全评审作为发布门槛，高风险功能专项评审
6. 所有质量指标接入监控与看板，让质量持续可见

### 踩坑记录

```text
坑 1：测试倒金字塔，E2E 多而脆、单测几乎为零
结论：CI 又慢又脆，一个环境抖动就红一片，关键逻辑却没测到。
原因：迷信 E2E，忽略了便宜快速的单元测试。
解法：按金字塔重构——核心逻辑下沉单元测试，E2E 只留关键旅程。

坑 2：SLO 定成 100%，一点余量都没有
结论：99.99% 的目标几乎不可达成，团队要么造假要么躺平。
原因：可用性目标拍脑袋，没有基于现实和历史数据。
解法：基于历史数据定 SLO（如 p99 现有水平），留出可操作空间。

坑 3：有错误预算却从不影响发布决策
结论：预算早就耗尽了，功能照常发布，预算形同虚设。
原因：错误预算只做了监控，没有和发布流程联动。
解法：把预算写入发布策略——耗尽自动冻结，用流程强制落地。

坑 4：性能预算只在「优化季」看，平时没人管
结论：性能只在专项优化时关注，平时持续劣化。
原因：预算没进 CI，性能退化在合并前发现不了。
解法：性能预算设为 CI 硬门槛，超限即阻断，退化无处藏身。

坑 5：安全评审只在「被通报」后才做
结论：线上出了安全事故才开始查安全，成了亡羊补牢。
原因：安全没有前置到评审环节，缺乏常态化的检查。
解法：安全评审纳入发布门槛，自查清单 + 自动化扫描 + 高风险专项。
```
