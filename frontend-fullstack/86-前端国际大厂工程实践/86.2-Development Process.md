## 概述

Development Process（研发流程）是团队组织协作、交付软件的方式，从敏捷框架（Scrum、Kanban）到代码分支策略（Trunk Based Development）再到交付节奏（Continuous Delivery）。好的研发流程让交付「短、频、稳」——小步快跑、高频发布、随时可上线。

```text
研发流程的四个支柱：
1. Scrum —— 迭代式交付，固定节奏冲刺
2. Kanban —— 流式交付，限制在制品、持续流动
3. Trunk Based Development —— 主干开发，短命分支
4. Continuous Delivery —— 持续交付，任何提交都可安全发布
```

```text
价值流动：
需求 → 排期 → 开发 → 代码合并 → 自动化验证 → 发布
                  ↑ 流程的核心是缩短「开发到上线」的周期
```

## Scrum

Scrum 是迭代式敏捷框架，把工作切分成固定长度的 Sprint（通常 1-4 周），每个 Sprint 交付一个可用的增量。它有明确的角色（Product Owner、Scrum Master、开发团队）和仪式（计划会、站会、评审会、回顾会）。

```text
# Scrum 的核心要素
1. Sprint —— 固定时长（1-4 周）的迭代周期
2. Backlog —— 待办事项清单，按优先级排序
3. 每日站会 —— 每天 15 分钟同步进展与阻塞
4. Sprint 评审 —— 迭代结束演示成果、收集反馈
5. Sprint 回顾 —— 反思过程、持续改进
```

```text
# Sprint 计划示例
Sprint 目标：完成结算页的支付流程重构
用户故事：
- [ ] 作为用户，我可以用余额支付订单（P0）
- [ ] 作为用户，我可以查看支付失败原因（P1）
- [ ] 作为用户，我可以切换支付方式（P2）
```

```text
Scrum 的适用场景：
1. 需求变化快、需要快速验证的产品
2. 团队 5-9 人、可自组织的跨职能团队
3. 能接受固定节奏、定期评审与调整
```

## Kanban

Kanban 是流式交付方法，核心是「可视化工作流、限制在制品（WIP）、持续流动」。它不设固定迭代，任务按优先级流经看板的各个阶段，WIP 上限防止「同时开工太多、一件事都做不完」。

```text
# 看板列（工作流阶段）
待办 → 分析 → 开发中 → 测试中 → 待发布 → 已完成
       ↑ WIP=2   ↑ WIP=3   ↑ WIP=2
```

```yaml
# 看板配置示例（数字化看板）
columns:
  - name: 待办
    wip_limit: null
  - name: 开发中
    wip_limit: 3        # 最多 3 个任务同时开发
  - name: 测试中
    wip_limit: 2
  - name: 已完成
    wip_limit: null
```

```text
Kanban 的三个原则：
1. 可视化 —— 所有工作都在看板上，状态一目了然
2. 限 WIP —— 限制在制品，聚焦完成而非开工
3. 持续改进 —— 通过瓶颈分析不断优化流动效率
```

## Trunk Based Development

Trunk Based Development（主干开发，TBD）是一种分支策略：所有开发者频繁地把小改动直接合并到主干（trunk/main），分支的生命周期极短（不超过 1-2 天）。它配合特性开关（Feature Flag）和持续集成，避免长分支带来的合并地狱。

```text
# TBD 的核心实践
1. 短命分支 —— 分支存活不超过 1-2 天，快速合并回主干
2. 小步提交 —— 每笔改动小而完整，可独立验证
3. 特性开关 —— 未完成功能用 Flag 隐藏，不影响主干发布
4. 主干始终可发布 —— 任何时刻主干都能安全部署
```

```bash
# TBD 的日常操作：短分支快速合并
git checkout -b feat/payment-flow      # 创建短命分支
# ... 小步提交 ...
git push origin feat/payment-flow
# 立即提 PR → CI 通过 → 合并回 main → 删除分支
gh pr create --base main --title "feat: payment flow"
gh pr merge --squash --delete-branch
```

```ts
// 特性开关：未完成功能隐藏，主干照常发布
const features = {
  newPaymentFlow: false, // 上线前关闭
};

export function PaymentPage() {
  return features.newPaymentFlow ? <NewPaymentFlow /> : <LegacyPayment />;
}
```

```text
TBD 相比 GitFlow 的优势：
1. 避免合并地狱 —— 分支越短，冲突越少
2. 集成频率高 —— 持续发现集成问题
3. 主干永远可发布 —— 发布不再依赖「冻结分支」
```

## Continuous Delivery

Continuous Delivery（持续交付）让软件「任何时候都可以安全、快速地发布到生产」。它要求构建、测试、部署全流程自动化，每次提交都经过完整流水线验证，发布成为「按一下按钮」的例行操作而非高风险事件。

```yaml
# 持续交付流水线：提交 → 验证 → 自动部署到预发 → 一键发布生产
# .github/workflows/cd.yml
name: Continuous Delivery
on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npx tsc --noEmit
      - run: npm test

  deploy-staging:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: npm ci
      - run: npm run build
      - run: deploy staging   # 自动部署预发环境

  deploy-prod:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production   # 生产环境需要人工批准
    steps:
      - run: deploy prod
```

```text
持续交付的关键实践：
1. 一切自动化 —— 构建、测试、部署全流水线
2. 环境一致性 —— 预发与生产一致，减少「环境差异」事故
3. 一键回滚 —— 发布可快速回退，降低发布风险
4. 频繁小发布 —— 小批量发布，问题定位容易
```

## 应用场景实战

### 场景一：配置一个支持特性开关的 TBD 工作流

```ts
// 1. 特性开关集中管理，支持按环境/比例放量
// src/features.ts
export const featureFlags = {
  newSearch: {
    enabled: process.env.ENABLE_NEW_SEARCH === 'true',
    rollout: 0.1, // 灰度比例 10%
  },
};

export function isEnabled(name: keyof typeof featureFlags, userId: string) {
  const flag = featureFlags[name];
  if (!flag.enabled) return false;
  // 按用户 hash 做灰度分流
  const hash = [...userId].reduce((a, c) => a + c.charCodeAt(0), 0);
  return (hash % 100) / 100 < flag.rollout;
}
```

```tsx
// 2. 未完成功能用 Flag 隐藏，主干照常发布
import { isEnabled } from './features';

export function SearchBar({ userId }: { userId: string }) {
  return isEnabled('newSearch', userId) ? <NewSearch /> : <Search />;
}
```

### 场景二：Kanban 看板限制 WIP，聚焦流动

```text
# 团队看板（限制在制品，防止多任务并行）
待办(∞) → 开发中(WIP=3) → 测试中(WIP=2) → 发布(1) → 完成

规则：
1. 开发中满 3 个，禁止再拉新任务，先完成手头的
2. 测试中卡住，优先疏通瓶颈而非继续开发
3. 每天站会看「谁被阻塞」，而非「谁在忙什么」
```

```bash
# 用脚本统计看板各列任务数，暴露瓶颈
echo "开发中: 3/3 (已满，停止拉新)"
echo "测试中: 2/2 (已满，瓶颈在此，开发需协助测试)"
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分支越短越好，TBD 配合特性开关，主干始终可发布
2. 未完成功能用 Feature Flag 隐藏，而非靠长分支隔离
3. Kanban 严格限制 WIP，聚焦「完成」而非「开工」
4. 发布流水线全自动化，生产发布做到一键 + 一键回滚
5. 小批量高频发布，问题定位与回滚都更容易
6. 回顾会真找问题真改进，而非走形式

### 踩坑记录

```text
坑 1：长分支一开就是几周，合并时冲突成灾
结论：feature 分支活了 3 周，合并回主干时冲突上百处，耗时数天。
原因：没有采用 TBD，分支生命周期过长，集成严重滞后。
解法：改用短命分支 + 特性开关，小步频繁合并回主干。

坑 2：特性开关上线后忘了清理，开关堆积成债
结论：几十个 Feature Flag 散落代码里，条件判断层层嵌套，没人敢删。
原因：开关只有「加」没有「删」，缺乏清理机制。
解法：每个开关设过期时间，全量放行后安排清理任务，纳入回顾。

坑 3：Kanban 不限 WIP，团队陷入多任务并行
结论：每人同时做 4 件事，没一件能交付，整体效率反而下降。
原因：没有 WIP 上限，任务越多显得越忙，但完成率极低。
解法：按团队规模设 WIP 上限，满了就聚焦现有任务，禁止拉新。

坑 4：预发和生产环境不一致，发布上线才炸
结论：预发测试全通过，生产上线就报错，排查发现环境差异。
原因：预发和生产的环境、配置、数据不一致。
解法：环境配置化、镜像化，保证预发与生产一致性。

坑 5：发布没有回滚方案，出了问题只能硬扛
结论：生产发布出故障，没有回滚手段，紧急修复耗时数小时。
原因：只想着往前发，没准备往后退。
解法：每次发布都准备一键回滚，发布即带回滚预案。
```
