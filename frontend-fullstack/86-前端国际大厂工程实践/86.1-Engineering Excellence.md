## 概述

Engineering Excellence（工程卓越）是国际大厂把「个人手艺」沉淀为「组织能力」的一整套实践：代码有 Code Review、方案有 Design Review、重要决策有 RFC 和 ADR。它的核心思想是「决策显式化、知识书面化、质量流程化」——让每行代码、每个决策都可追溯、可复现、可持续改进。

```text
Engineering Excellence 的五件武器：
1. Code Review —— 代码合并前的同行评审
2. Design Review —— 方案实施前的设计评审
3. RFC —— 重大变更的公开征询（Request for Comments）
4. ADR —— 架构决策的书面记录（Architecture Decision Record）
5. Technical Proposal —— 技术方案的正式提案
```

```text
决策的时间线：
RFC 征询 → Technical Proposal 提案 → Design Review 评审 → 实施 → Code Review → 合并 → ADR 沉淀
```

## Code Review

Code Review 是合并前由同事审查代码变更的过程，大厂普遍要求「每笔变更至少一人 approve 才能合并」。它关注正确性、可读性、设计合理性，是工程质量的第一道人工闸门。

```text
# 大厂 Code Review 的要点
1. 小 PR —— 单次变更控制在几百行内，便于深入评审
2. 明确意图 —— PR 描述讲清「为什么改、改了什么、怎么验证」
3. 及时响应 —— 评审意见尽快处理，缩短合并周期
4. 一票通过制 —— 至少一名有权限的评审者 approve
```

```yaml
# GitHub 分支保护：强制 Code Review
# 通过仓库 Settings → Branches 配置，或用 gh CLI
# 至少 1 人 approve 才能合并，禁止直接 push main
```

```bash
# gh 配置分支保护规则
gh api repos/:owner/:repo/branches/main/protection \
  --method PUT \
  --field required_pull_request_reviews=null \
  -f required_pull_request_reviews.required_approving_review_count=1
```

```text
Code Review 关注什么：
1. 正确性 —— 逻辑对不对，边界是否覆盖
2. 可读性 —— 命名、结构是否清晰
3. 设计 —— 是否过度设计，有没有更简单方案
4. 一致性 —— 是否符合团队规范与既有模式
```

## Design Review

Design Review 在编码之前评审技术方案：数据流怎么设计、模块怎么划分、接口怎么定、有什么风险。它把问题发现的时间点从「代码里」提前到「设计里」，避免写完才发现方向错了。

```text
# Design Review 关注的问题
1. 方案正确性 —— 能否满足需求，边界是否清晰
2. 架构合理性 —— 模块划分、依赖方向是否合理
3. 风险 —— 性能、安全、可扩展性有哪些隐患
4. 备选方案 —— 是否考虑过其他方案，为何选这个
```

```text
# Design Review 的典型流程
1. 提案人写设计文档（Technical Proposal）
2. 评审会前发给相关方预读
3. 会上逐项讨论，记录分歧与结论
4. 会后修订文档，达成共识再开工
```

## RFC

RFC（Request for Comments，请求评议）是重大变更、新规范、新架构的公开征询机制：提案人写一份 RFC 文档，向团队甚至整个组织公开征求意见，收集反馈后修订定稿。它让「影响面大的决策」不再由少数人拍板，而是充分讨论、达成共识。

```text
# 一份 RFC 文档的结构
1. 标题与作者 —— 谁在提议
2. 背景与动机 —— 为什么要做这件事
3. 目标与非目标 —— 明确边界，避免范围蔓延
4. 方案设计 —— 核心设计、关键取舍
5. 备选方案 —— 考虑过哪些、为何否决
6. 影响面 —— 对现有系统、团队、用户的影响
7. 开放问题 —— 待讨论解决的点
```

```text
RFC 的适用场景：
1. 引入新的架构或范式（如微前端、Module Federation）
2. 跨团队协作的接口变更
3. 可能影响大量使用者的破坏性改动
4. 需要多方对齐的技术决策
```

## ADR

ADR（Architecture Decision Record，架构决策记录）是记录「重要架构决策及其背景」的轻量文档。每做一个影响深远的决策，就写一条 ADR：上下文、决策、后果，让后来者知道「当时为什么这么选」，避免反复争论已经决定过的事。

```markdown
# ADR-001：采用 Module Federation 实现微前端

## 状态
已接受

## 背景
前端应用持续膨胀，多个团队需要独立开发、独立部署。
需要一种运行时共享机制，避免重复打包公共依赖。

## 决策
采用 Webpack Module Federation，宿主应用远程加载子应用模块，
共享依赖用 singleton 保证 React 单实例。

## 后果
- 正面：团队可独立部署，公共依赖不重复打包
- 负面：运行时复杂度上升，需要处理版本对齐与降级
- 需要：建立 remoteEntry 版本管理规范
```

```text
ADR 的价值：
1. 决策可追溯 —— 知道「为什么」而非只知道「是什么」
2. 避免重复争论 —— 已决策的事不再反复讨论
3. 新人友好 —— 新成员通过 ADR 快速理解历史决策
```

## Technical Proposal

Technical Proposal（技术方案提案）是针对某个具体问题/需求的正式技术方案文档，通常在编码前编写并经过 Design Review。它把「想清楚再动手」固化为流程，是 Design Review 和 RFC 的输入物。

```text
# 技术方案提案的模板
1. 问题陈述 —— 要解决什么问题
2. 目标 —— 成功标准是什么
3. 方案对比 —— 列出 2-3 个候选方案及优劣
4. 推荐方案 —— 选哪个、为什么
5. 详细设计 —— 架构、数据流、接口、时序
6. 风险与缓解 —— 有哪些风险、怎么应对
7. 实施计划 —— 分几步、里程碑、回滚方案
```

```markdown
## 方案对比表示例

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 自建微前端框架 | 完全可控 | 维护成本高 | 否决 |
| single-spa | 生态成熟 | 运行时集成复杂 | 备选 |
| Module Federation | 细粒度共享 | 需管理版本 | 推荐 |
```

```text
提案的质量标准：
1. 有对比 —— 不只有推荐方案，还有否决方案及理由
2. 有取舍 —— 明确写出权衡，而非一味说好
3. 有风险 —— 主动暴露风险与缓解措施
```

## 应用场景实战

### 场景一：用 RFC 推动一次跨团队 API 变更

```text
# RFC-042：统一用户接口的返回结构
背景：各团队的 /api/user 返回结构不一致，前端要做多套适配。
动机：统一返回结构，减少前端适配成本。

设计：
所有用户相关接口统一返回：
{ "data": {...}, "code": 0, "message": "ok" }

备选方案：
1. 只在文档约定，不强制 → 否决，靠自觉不可靠
2. 网关层统一转换 → 备选，实现复杂
3. 制定契约 + 契约测试 → 推荐

开放问题：
- 老接口的兼容期多长？（建议 2 个版本周期）
```

```text
# 附：RFC 评审后达成的共识
1. 统一返回结构，网关层做兼容转换
2. 新接口直接遵守新契约，老接口 2 个版本内下线
3. 用 Pact 做契约测试，纳入 CI
```

### 场景二：写 ADR 沉淀架构决策

```bash
# 用 adr-tools 生成一条 ADR
adr new "采用 pnpm workspace 管理 Monorepo"
```

```markdown
# ADR-002：采用 pnpm workspace 管理 Monorepo

## 状态
已接受

## 背景
应用拆分为多个包，需要统一管理依赖、共享代码、
原子提交。对比了 npm/yarn/pnpm 三种方案。

## 决策
采用 pnpm workspace，配合 Turborepo 做任务编排。

## 后果
- 正面：依赖安装快、磁盘占用小、严格依赖隔离
- 负面：需要团队适应 pnpm 的严格依赖解析
- 需要：统一迁移 lockfile，CI 改造
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每笔代码变更都走 Code Review，至少一人 approve 才能合并
2. 编码前先做 Design Review，把问题挡在设计阶段
3. 影响面大的决策用 RFC 公开征询，充分讨论再定稿
4. 重要架构决策写 ADR，记录背景与取舍，避免重复争论
5. 技术方案要有候选对比与风险分析，而非单方案自嗨
6. 所有评审以文档为介质，结论书面化、可追溯

### 踩坑记录

```text
坑 1：Code Review 变成走过场，approve 不看代码
结论：评审沦为「点个按钮」，质量门形同虚设。
原因：PR 太大没人细看，或评审者没有责任感。
解法：限制 PR 粒度，明确评审关注点，评审质量纳入团队绩效。

坑 2：技术方案没评审就开工，写到一半推倒重来
结论：编码进行到一半发现方向有问题，大量返工。
原因：跳过了 Design Review，边写边改方案。
解法：编码前强制 Design Review，方案定稿再动手。

坑 3：RFC 收集了意见但没回音，参与者心寒
结论：大家认真提了意见，提案人既不采纳也不解释，后续没人再参与。
原因：RFC 只有征询没有闭环，反馈未得到回应。
解法：每份 RFC 都要对反馈逐条回应，采纳与否给出理由。

坑 4：决策只在会上口头定了，换个人就推翻
结论：上季度定好的架构决策，新来的负责人不知情，重新争论甚至推翻。
原因：决策没有写成 ADR，只存在于会议纪要或记忆里。
解法：重要架构决策一律落 ADR，决策上下文可追溯。

坑 5：技术提案只有「推荐方案」，没有对比和风险
结论：方案评审时说不出为什么选它，也看不到风险，拍脑袋定。
原因：提案质量低，缺少候选方案对比与风险分析。
解法：提案模板强制要求方案对比、取舍说明、风险与缓解。
```
