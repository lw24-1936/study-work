## 概述

Bundle Analysis（产物分析）是「分析打包产物的体积构成、依赖关系与优化空间」的实践：前端构建后的 bundle 往往包含大量隐藏的冗余——重复的库、被误打包的依赖、过大的 polyfill。通过分析工具可视化产物，找到「谁吃掉了体积」，再针对性地做 tree shaking、拆包、按需加载。

```text
产物分析要回答的问题：
1. 哪个包最大 —— 谁占据了主要体积
2. 哪些依赖重复 —— 同一库被多次打包
3. 哪里该按需 —— 大库应该懒加载
4. 是否误打包 —— 不该进产物的代码混了进来
```

```text
产物分析的常见结论：
1. moment.js 太大 → 换成 day.js
2. 重复的 lodash → 统一按需引入
3. 某个库全量引入 → 改为按需 + tree shaking
4. source map 未剔除 → 生产包体积虚高
```

## Bundle Analyzer

Bundle Analyzer（打包分析器）是「可视化 bundle 内部组成」的工具，最常用的是 webpack-bundle-analyzer：它把每个模块及其体积画成方块图，一眼看出哪些模块占据了多少空间，是定位「体积元凶」的第一步。

```text
Bundle Analyzer 展示的信息：
1. 模块体积 —— 每个依赖的实际大小（解析后/压缩后）
2. 嵌套关系 —— 谁引入了谁，父子依赖结构
3. stat / parsed / gzip —— 三种口径的体积
4. 重复检测 —— 同一模块的不同版本
```

```js
// webpack.config.js —— 接入 bundle-analyzer
const { BundleAnalyzerPlugin } = require('webpack-bundle-analyzer');

module.exports = {
  plugins: [
    new BundleAnalyzerPlugin({
      analyzerMode: 'static',   // 生成静态 HTML 报告
      openAnalyzer: false,
      reportFilename: 'bundle-report.html',
    }),
  ],
};
```

```bash
# 构建后生成报告，浏览器打开查看方块图
pnpm build
# 生成 dist/bundle-report.html，可视化各模块体积
```

```text
三个体积口径的含义：
stat    —— 源码的原始大小（未压缩）
parsed  —— 经过压缩后实际打包的大小
gzip    —— 服务器传输时 gzip 后的大小（最接近真实带宽）
```

Bundle Analyzer 的使用心法：先看最大的方块（通常是某个 UI 库或图表库），再看重复出现的模块（同一依赖多个版本），最后看「不该出现的」（测试代码、开发依赖混入）。定位之后，才能对症下药。

## Source Map Explorer

Source Map Explorer（源映射探索器）是「通过 source map 还原产物到源码」的分析工具：它读取 bundle 的 source map，把压缩混淆后的代码映射回原始模块和文件，精确显示「哪个源文件贡献了多少体积」。比 Bundle Analyzer 更贴近「源码视角」。

```text
Source Map Explorer 的能力：
1. 映射到源码 —— 显示源文件而非打包后的模块
2. 精确体积 —— 每个源文件的贡献大小
3. 跨工具 —— 支持 webpack、rollup、vite 的 source map
4. 定位具体文件 —— 精确到某个组件/工具函数
```

```bash
# 用 source-map-explorer 分析带 source map 的产物
npm install -g source-map-explorer
source-map-explorer dist/assets/*.js
```

```js
// 确保构建时生成 source map，才能用 source-map-explorer
// vite.config.js
export default defineConfig({
  build: {
    sourcemap: true, // 生成 source map 供分析
  },
});
```

```text
# source-map-explorer 输出示例
dist/assets/index.js
  ├── node_modules/react-dom/cjs/react-dom.production.js   130 KB
  ├── node_modules/lodash/lodash.js                         72 KB
  ├── src/components/DataTable.tsx                          38 KB
  └── src/utils/format.ts                                   12 KB
```

Source Map Explorer 的独特价值：Bundle Analyzer 显示的是「打包后的 chunk」，Source Map Explorer 显示的是「原始的源文件」。当你需要知道「是哪个业务文件拖大了包」时，它比 Bundle Analyzer 更直接。

## Bundle Size

Bundle Size（包体积）是「产物体积的度量与控制」：前端性能很大程度上取决于「用户要下载多少代码」。Bundle Size 关注三个口径（stat/parsed/gzip）和「首屏体积 vs 懒加载体积」的划分，并通过预算（budget）和 CI 门禁持续控制。

```text
Bundle Size 的关注点：
1. 总量 —— 所有 chunk 的总体积
2. 首屏体积 —— 入口 chunk 的大小（影响首次加载）
3. gzip 体积 —— 真实传输的大小
4. 体积预算 —— 设定上限，超出即告警/失败
```

```js
// webpack 配置体积预算：超出即构建失败
module.exports = {
  performance: {
    maxEntrypointSize: 250 * 1024,  // 入口最大 250KB
    maxAssetSize: 100 * 1024,       // 单个资源最大 100KB
    hints: 'error',                 // 超出报错
  },
};
```

```json
// 用 size-limit 做体积门禁，接入 CI
{
  "scripts": {
    "size": "size-limit"
  },
  "size-limit": [
    { "path": "dist/assets/*.js", "limit": "250 kB gzip" },
    { "path": "dist/assets/*.css", "limit": "50 kB gzip" }
  ]
}
```

```text
# size-limit 输出示例
✔ dist/assets/index.js  — 182.4 kB (gzip 58.1 kB)
✔ dist/assets/vendor.js — 96.2 kB (gzip 31.4 kB)
  Total: 89.5 kB gzip (limit 300 kB)
```

Bundle Size 管理的要点是「用 gzip 口径 + 设定预算 + 进 CI」：体积优化不是一次性运动，而是持续的门禁——每个 PR 都要过 size-limit，超出预算就阻断合并，才能防止体积缓慢膨胀回原点。

## Dependency Graph

Dependency Graph（依赖图）是「模块之间的依赖关系网络」：构建工具根据 import 关系构建模块依赖图，分析它能看到「哪些模块被谁依赖」「某个库被哪些入口引入」「是否存在不该有的依赖链」。依赖图是 tree shaking、拆包、按需加载的基础。

```text
依赖图能揭示的问题：
1. 死代码 —— 被引入但从未使用的模块
2. 重复依赖 —— 同一库的多个版本被不同模块引入
3. 意外依赖 —— 测试文件、开发工具混入产物
4. 长依赖链 —— 浅层 import 拖入整个库
```

```text
# 依赖图示意（谁引入了谁）
entry.js
├── react            ← 入口直接依赖
├── react-dom
└── pages/home.js
    ├── lodash       ← 深层依赖
    └── components/Chart.js
        └── echarts  ← 重型依赖（应懒加载）
```

```bash
# 用 madge 生成模块依赖图，发现循环依赖和结构问题
npx madge --circular src/index.ts      # 检查循环依赖
npx madge --image graph.svg src/index.ts  # 生成依赖图
```

```text
# madge 循环依赖检查输出
✖ Found 2 circular dependencies:
1) src/utils/a.ts > src/utils/b.ts > src/utils/a.ts
2) src/store/index.ts > src/api/client.ts > src/store/index.ts
```

依赖图分析的实战价值：定位「为什么 echarts 被打进首屏」（因为首页直接 import 了它，应该改懒加载）、发现「循环依赖」（会导致初始化顺序 bug）、找到「lodash 全量引入」（应该改 `import { map } from 'lodash-es'`）。

## 应用场景实战

### 场景一：用 Bundle Analyzer 定位体积元凶

```bash
# 1. 安装并配置 webpack-bundle-analyzer
pnpm add -D webpack-bundle-analyzer

# 2. 构建生成分析报告
pnpm build
# dist/bundle-report.html 生成
```

```text
# 3. 分析报告的发现与对策
发现 1：moment.js 占 232KB → 换 day.js（仅 7KB）
发现 2：lodash 全量打包 72KB → 改 import { debounce } from 'lodash-es'
发现 3：echarts 打进首屏 380KB → 路由懒加载 + 独立 chunk
发现 4：两个版本的 react 重复 → 统一依赖版本
```

### 场景二：体积预算接入 CI 门禁

```json
// package.json —— size-limit 预算
{
  "size-limit": [
    { "path": "dist/assets/index-*.js", "limit": "200 kB gzip" },
    { "path": "dist/assets/vendor-*.js", "limit": "150 kB gzip" }
  ]
}
```

```yaml
# CI 里跑 size-limit，超预算阻断合并
- run: pnpm build
- run: pnpm size-limit
  # 体积超预算 → 退出码非 0 → CI 失败
```

```ts
// 路由懒加载：把重型库拆出首屏 chunk
import { lazy, Suspense } from 'react';

const ChartPage = lazy(() => import('./pages/ChartPage')); // echarts 独立 chunk

export function App() {
  return (
    <Suspense fallback={<div>加载中...</div>}>
      <ChartPage />
    </Suspense>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 gzip 口径衡量体积，它最接近真实的网络传输
2. 定期跑 Bundle Analyzer，关注「最大方块」和「重复模块」
3. 用 Source Map Explorer 精确到源文件，定位业务代码的贡献
4. 设定体积预算（size-limit），并接入 CI 门禁持续守护
5. 重型库（图表、编辑器、地图）路由级懒加载，拆出首屏
6. 用 lodash-es 等 ESM 版本 + tree shaking，避免全量打包

### 踩坑记录

```text
坑 1：只看原始体积不看 gzip
结论：明明 gzip 后很小，却误判为体积过大，做了无谓优化。
原因：混淆 stat 与 gzip 口径，忽略传输层压缩。
解法：以 gzip 口径为准衡量，stat 只作参考。

坑 2：分析报告误导优化方向
结论：对着 Bundle Analyzer 的 stat 体积优化半天，实际收益为零。
原因：只看未压缩的原始大小，忽略了实际传输和解析成本。
解法：同时看 parsed/gzip，结合真实性能指标（LCP、加载时长）判断。

坑 3：生产包忘了关 source map
结论：生产 bundle 里带了完整 source map，体积虚高且源码泄露。
原因：构建配置里 sourcemap: true 没有区分环境。
解法：生产构建关闭 source map 或用 hidden-source-map，分析时临时开启。

坑 4：体积优化后又膨胀
结论：优化到 200KB，几个月后又涨回 400KB。
原因：没有体积预算和 CI 门禁，体积增长无感知。
解法：size-limit 进 CI，超出预算阻断合并，持续守护。

坑 5：重型库打进首屏
结论：echarts、monaco 等大库全量打进入口，首屏加载 3 秒以上。
原因：入口文件直接 import 重型库，没有懒加载。
解法：路由级/组件级懒加载，大库拆成独立 chunk 按需加载。
```
