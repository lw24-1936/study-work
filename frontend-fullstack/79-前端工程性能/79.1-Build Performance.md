## 概述

Build Performance（构建性能）指前端构建（打包、编译、产物生成）的速度与资源消耗。随着项目规模增长，构建时间从秒级涨到分钟级，直接影响开发体验和 CI 成本。提升构建性能的核心思路是「少做重复工作」——用缓存、增量、并行等手段，让每次构建只处理真正变化的部分。

```text
构建性能的关键指标：
1. 冷构建时间 —— 无缓存时的全量构建耗时
2. 热构建时间 —— 有缓存时的增量构建耗时
3. 开发时 HMR 速度 —— 改一行代码的反馈时间
4. 构建内存占用 —— 峰值内存决定能否并行
```

```text
构建性能优化的方向：
1. 缓存 —— 依赖缓存、持久缓存、远程缓存
2. 增量 —— 只重建变化的部分
3. 并行 —— 多核同时编译
4. 提速工具 —— 用 esbuild / SWC 替代慢速编译器
5. 减量 —— 缩小构建范围、按需编译
```

## Dependency Cache

Dependency Cache（依赖缓存）是「缓存 node_modules / 依赖下载结果」的优化：前端项目动辄几百上千个依赖，每次全新安装要下载、解压、链接大量包。通过锁文件 + 缓存目录，让依赖只在 lockfile 变化时才重新安装。

```text
依赖缓存的要点：
1. 锁文件 —— package-lock.json / pnpm-lock.yaml 决定依赖版本
2. 缓存键 —— 以 lockfile 哈希作为缓存键
3. 命中判断 —— lockfile 不变则复用缓存
4. 包管理器差异 —— npm / pnpm / yarn 各有缓存目录
```

```yaml
# CI 里用 lockfile 哈希做依赖缓存（GitHub Actions 风格）
- uses: actions/setup-node@v4
  with:
    node-version: '20'
    cache: 'pnpm'          # 按 pnpm-lock.yaml 哈希缓存
    cache-dependency-path: 'pnpm-lock.yaml'

- run: pnpm install --frozen-lockfile   # lockfile 命中时秒级完成
```

```text
依赖缓存失效的触发：
1. lockfile 变化 —— 增删依赖、升级版本
2. 缓存键变化 —— node 版本、包管理器版本
3. 缓存被清理 —— 缓存目录过期或被手动删除
```

依赖缓存的收益显著：命中缓存时，安装从几分钟降到几秒。关键是用「lockfile 哈希」做缓存键——只有依赖真正变化才重新安装，而不是每次 CI 都全量装一遍。

## Incremental Build

Incremental Build（增量构建）是「只重建变化的部分，复用未变化的结果」：开发时改一个文件，只重新编译该文件及其依赖链，而不是整个项目。它让开发反馈（HMR、热更新）从秒级降到毫秒级。

```text
增量构建的原理：
1. 变更检测 —— 监听文件变化，确定影响范围
2. 依赖图 —— 分析模块依赖，定位受影响模块
3. 局部重建 —— 只编译变化模块及其下游
4. 结果复用 —— 未变化模块直接用缓存结果
```

```text
各构建工具的增量能力：
Vite  —— 按需编译 + HMR，天然增量
Webpack —— 缓存 + 持久缓存实现增量
Turbopack —— 原生增量引擎
Rspack  —— Rust 实现，增量高效
```

```ts
// Vite 的开发服务器：只编译浏览器请求到的模块
// 修改 src/App.tsx 时，只重新编译 App 及其依赖，其余模块复用
export default defineConfig({
  server: {
    hmr: true,            // 模块热替换
  },
  build: {
    rollupOptions: {
      // 生产构建也能受益于增量缓存
    },
  },
});
```

增量构建的关键是「精确的依赖图」：工具需要知道「谁依赖了谁」，才能在变化发生时只重建受影响的部分。依赖图越精确，增量越高效；误判会导致「改了 A 却重建了整棵树」。

## Parallel Build

Parallel Build（并行构建）是「利用多核 CPU 同时编译多个模块」：现代机器普遍 8 核、16 核，但单线程编译器只用一核。并行构建把编译任务拆分到多个 worker，同时执行，显著缩短编译时间。

```text
并行构建的方式：
1. 多进程 —— 用 worker 进程池并行编译模块
2. 多线程 —— 共享内存的线程并行
3. 任务拆分 —— 把无依赖的模块分给不同 worker
4. 工具支持 —— terser-webpack-plugin、thread-loader 等
```

```js
// Webpack 并行压缩：用多个 worker 并行执行 terser
const TerserPlugin = require('terser-webpack-plugin');

module.exports = {
  optimization: {
    minimizer: [
      new TerserPlugin({
        parallel: true, // 默认按 CPU 核数 - 1 并行
      }),
    ],
  },
};
```

```text
并行构建的收益与边界：
1. 收益 —— 编译/压缩这类 CPU 密集任务几乎线性加速
2. 边界 —— I/O 密集或小项目收益有限
3. 开销 —— worker 进程创建与通信有固定成本
4. 内存 —— 并行度越高内存占用越大
```

并行构建的收益取决于任务类型：压缩、转译这类纯 CPU 任务，并行几乎线性加速；而大量小文件的 I/O 读取，收益会被磁盘瓶颈抵消。并行度一般设为「CPU 核数 - 1」，留一个核给主进程。

## Persistent Cache

Persistent Cache（持久缓存）是「把构建中间结果存到磁盘，跨构建复用」：Webpack 的 filesystem cache 会把模块编译结果序列化存盘，下次构建时直接读取，跳过重复的解析和编译。它让「冷启动后第一次增量构建」也很快。

```text
持久缓存的机制：
1. 序列化中间结果 —— 模块、chunk 的编译产物存盘
2. 缓存键 —— 模块内容 + 配置 + 依赖的哈希
3. 失效检测 —— 内容变化导致哈希变化，自动失效
4. 跨进程复用 —— 新进程启动也能读缓存
```

```js
// Webpack 持久缓存：把编译结果缓存到 node_modules/.cache
module.exports = {
  cache: {
    type: 'filesystem', // 持久缓存到磁盘
    buildDependencies: {
      config: [__filename], // 配置变化时缓存失效
    },
  },
};
```

```text
# 持久缓存目录示例
node_modules/.cache/webpack/
├── default-production/   # 生产构建缓存
│   └── index.pack        # 序列化的模块编译结果
└── default-development/  # 开发构建缓存
```

持久缓存与增量构建互补：增量构建管「本次构建内」的复用，持久缓存管「跨构建」的复用。配置持久缓存后，开发者重启编辑器、切换分支再构建，都能跳过大量重复编译。

## Remote Cache

Remote Cache（远程缓存）是「把构建产物/中间结果共享到远程，让团队和 CI 复用」：本地或 CI 构建出的结果上传到远程存储，其他机器构建时先查远程缓存，命中就直接下载复用，避免重复构建。这是 Monorepo 和大型团队提速的利器。

```text
远程缓存的原理：
1. 本地构建 —— 生成产物 + 计算缓存键
2. 上传 —— 把产物上传到远程存储（S3、Nx Cloud 等）
3. 复用 —— 其他机器构建前先查远程，命中则下载
4. 缓存键 —— 源码 + 依赖 + 配置的哈希决定是否命中
```

```text
支持远程缓存的工具：
Turborepo —— Remote Cache，多任务 + 远程缓存
Nx        —— Nx Cloud，分布式缓存 + 分布式执行
Bazel     —— 远程缓存 + 远程执行
```

```json
// Turborepo 配置远程缓存
{
  "pipeline": {
    "build": {
      "outputs": ["dist/**"],
      "cache": true
    }
  }
}
```

```bash
# 构建时命中远程缓存（其他机器已构建过相同内容）
npx turbo run build --filter=web
# Remote cache hit: 直接下载产物，跳过本地构建
```

远程缓存的价值在团队协作：A 开发者的构建结果，B 开发者和 CI 都能复用。它配合「内容寻址的缓存键」工作——只要源码、依赖、配置完全一致，缓存就能命中，无论在哪台机器上构建。

## 应用场景实战

### 场景一：为大型项目配置完整的构建缓存

```js
// webpack.config.js —— 综合缓存 + 并行 + 增量
const TerserPlugin = require('terser-webpack-plugin');

module.exports = {
  mode: 'production',
  cache: {
    type: 'filesystem', // 持久缓存
  },
  optimization: {
    minimizer: [
      new TerserPlugin({
        parallel: true, // 并行压缩
      }),
    ],
    splitChunks: {
      chunks: 'all', // 拆包，减少重复构建
    },
  },
  module: {
    rules: [
      {
        test: /\.tsx?$/,
        use: {
          loader: 'swc-loader', // SWC 替代 babel，更快
        },
        exclude: /node_modules/,
      },
    ],
  },
};
```

### 场景二：Monorepo 用 Turborepo 远程缓存

```json
// turbo.json —— 定义任务与缓存
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"],
      "cache": true
    },
    "test": {
      "dependsOn": ["build"],
      "cache": true
    }
  }
}
```

```bash
# 团队协作：别人构建过的结果，本地直接命中远程缓存
npx turbo run build
# ✓ web#build  — Remote cache hit (downloaded 4.2 MB in 1.1s)
# ✓ docs#build — Full turbo (built 38 modules in 12.4s)
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用锁文件哈希做依赖缓存键，命中时安装秒级完成
2. 开发环境优先用 Vite/Turbopack 这类天然增量、按需编译的工具
3. 压缩、转译等 CPU 密集任务开启并行，并行度设为核数减一
4. Webpack 开启 filesystem 持久缓存，让冷启动后首次构建也快
5. Monorepo 用 Turborepo/Nx 的远程缓存，让团队和 CI 共享构建结果
6. 用 esbuild/SWC 替代 Babel，转译速度可提升一个数量级

### 踩坑记录

```text
坑 1：依赖缓存键不含 lockfile
结论：依赖升级后 CI 仍用旧缓存，装出不一致的依赖版本。
原因：缓存键只按「是否启用」而非 lockfile 哈希，无法感知依赖变化。
解法：用 package-lock/pnpm-lock 的哈希做缓存键，lockfile 变了就重装。

坑 2：持久缓存导致陈旧结果
结论：改了代码构建结果却不变，出现诡异 bug。
原因：缓存键不完整（漏了配置/环境变量），变化未被检测到。
解法：把配置、环境、编译器版本都纳入 buildDependencies，保证失效准确。

坑 3：并行度过高反而变慢
结论：并行 worker 开到 32 个，构建反而比 8 个慢。
原因：worker 创建和通信开销超过并行收益，内存也吃满。
解法：并行度设为 CPU 核数减一，压测找到最优值。

坑 4：远程缓存命中却产物异常
结论：不同机器间缓存命中但结果不一致，出现环境相关 bug。
原因：缓存键没有覆盖全部输入（如环境变量、本地路径）。
解法：缓存键覆盖源码、依赖、配置、环境，保证内容寻址准确。

坑 5：忽略 node_modules 缓存导致 CI 巨慢
结论：每次 CI 都全量 pnpm install，安装耗时占据大半流水线。
原因：没有配置依赖缓存，白白重复下载安装。
解法：启用依赖缓存，按 lockfile 哈希复用 node_modules。
```
