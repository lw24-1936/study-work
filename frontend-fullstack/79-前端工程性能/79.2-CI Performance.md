## 概述

CI Performance（CI 性能）指持续集成流水线的执行速度与资源效率。前端 CI 流水线通常包含安装依赖、构建、测试、打包镜像等阶段，任何一个阶段的低效都会拖慢整个团队的回环时间。优化 CI 的核心是「缓存一切可缓存的、并行一切可并行的」，让流水线从「每次全量重跑」变成「只跑变化的」。

```text
前端 CI 流水线的典型阶段：
1. 检出代码 —— 拉取仓库
2. 安装依赖 —— 下载、安装 node_modules
3. 代码检查 —— lint、type-check、format
4. 构建 —— 打包生成产物
5. 测试 —— 单元测试、E2E 测试
6. 打包镜像 —— Docker build
```

```text
CI 优化的核心策略：
1. 缓存依赖 —— 复用 node_modules、镜像层
2. 缓存构建 —— 复用编译中间结果
3. 并行测试 —— 拆分测试任务多 worker 跑
4. 缓存产物 —— 复用跨流水线的构建产物
5. 精简流水线 —— 只跑变化的、必要的步骤
```

## Dependency Cache

Dependency Cache（依赖缓存）在 CI 里指「缓存 node_modules，避免每次流水线全量安装」：通过按 lockfile 哈希缓存依赖目录，让依赖只在 lockfile 变化时重新安装。这是 CI 提速最直接、收益最大的一步。

```yaml
# GitHub Actions 的依赖缓存
name: CI
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'pnpm'
          cache-dependency-path: 'pnpm-lock.yaml'
      - run: pnpm install --frozen-lockfile
      - run: pnpm build
```

```text
依赖缓存命中的判断：
1. lockfile 哈希相同 → 命中缓存，直接复用 node_modules
2. lockfile 变化 → 缓存失效，重新安装
3. 缓存键设计 → 包含 lockfile + 包管理器 + node 版本
```

```yaml
# 手动控制缓存键：lockfile 哈希作为缓存键
- name: Cache pnpm store
  uses: actions/cache@v4
  with:
    path: ~/.local/share/pnpm/store
    key: ${{ runner.os }}-pnpm-${{ hashFiles('pnpm-lock.yaml') }}
    restore-keys: |
      ${{ runner.os }}-pnpm-
```

依赖缓存的关键在于「用 lockfile 哈希做缓存键」。命中时，`pnpm install` 只需几秒（只做链接），未命中时才真正下载。跨流水线复用缓存，能把安装阶段从 3-5 分钟压缩到 10 秒以内。

## Docker Cache

Docker Cache（Docker 缓存）指「复用 Docker 镜像的构建层」：Docker 按 Dockerfile 指令逐层构建并缓存，未变化的层直接复用。合理编排 Dockerfile（把变化最少的放前面、变化最多的放后面）能大幅提升镜像构建速度。

```text
Docker 层缓存的原理：
1. 按层缓存 —— 每条指令生成一层，层未变则复用
2. 顺序敏感 —— 前面的层变了，后面全部失效
3. 稳定层在前 —— 把不易变的操作放前面
4. 变化层在后 —— 把易变操作（复制源码）放最后
```

```dockerfile
# 反例：COPY . . 太早，任何文件变化都让后续层失效
FROM node:20
WORKDIR /app
COPY . .                    # 源码一变，下面全重跑
RUN pnpm install
RUN pnpm build
```

```dockerfile
# 正例：先装依赖（利用层缓存），再复制源码
FROM node:20 AS build
WORKDIR /app

# 先复制锁文件，只装依赖 —— 依赖不变时这层永远命中
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile

# 最后复制源码并构建 —— 只有源码变化才重跑这层
COPY . .
RUN pnpm build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
```

Docker 层缓存的关键是「把高变化率的内容放最后」：依赖清单变化频率远低于源码，所以先 `COPY package.json + install`，再 `COPY . .`。这样日常改源码，只会让最后的构建层失效，安装层持续命中。

## Build Cache

Build Cache（构建缓存）在 CI 里指「复用构建的中间结果，跳过重复编译」：本地和 CI 环境不一致，构建缓存通常依赖远程缓存（Turborepo Remote Cache、Nx Cloud）或 CI 平台的缓存目录，让「源码没变的包」直接复用上次的构建产物。

```text
CI 构建缓存的实现：
1. 远程缓存 —— Turborepo/Nx 把产物存远程，多机器复用
2. 平台缓存目录 —— 用 actions/cache 缓存 .turbo、node_modules/.cache
3. 内容寻址 —— 源码哈希相同则产物一致，可安全复用
4. 跨流水线 —— 上次 CI 的构建结果，这次 CI 直接下载
```

```yaml
# Turborepo 远程缓存 + GitHub Actions
- name: Setup Turborepo cache
  uses: actions/cache@v4
  with:
    path: .turbo
    key: turbo-${{ github.sha }}
    restore-keys: |
      turbo-

- run: npx turbo run build
  env:
    TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
    TURBO_TEAM: ${{ vars.TURBO_TEAM }}
```

```bash
# 命中远程缓存的输出：跳过本地构建
npx turbo run build
# web#build  — Remote cache hit (downloaded 4.1 MB)
# docs#build — Full turbo (built in 15.2s)
```

构建缓存让 CI 的「构建阶段」从每次全量编译，变成「只在源码变化时编译」。配合 Monorepo 的按需构建（只构建变化的包），构建时间可以稳定在秒级，而不是随项目线性增长。

## Test Parallelization

Test Parallelization（测试并行化）是「把测试套件拆分成多份，在多个 worker 上同时执行」：前端项目动辄几千个测试用例，串行跑可能十几分钟。按文件、按分片（shard）拆分测试，并行执行，能线性缩短测试时间。

```text
测试并行化的方式：
1. 多进程 —— Vitest 默认多线程，Jest 用 worker 池
2. 分片 —— 把测试文件分成 N 片，分到 N 个 runner
3. 按文件拆分 —— 每个 worker 跑一部分测试文件
4. 平台并行 —— CI 平台用多个 job / matrix 并行
```

```js
// Vitest 默认并行：多 worker 同时跑测试文件
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    pool: 'threads',       // 多线程并行
    maxWorkers: 4,         // 并行 worker 数
    maxConcurrency: 4,
  },
});
```

```yaml
# CI 平台层面分片：把测试拆到多个 job 并行
strategy:
  matrix:
    shard: [1, 2, 3, 4]
steps:
  - run: pnpm test -- --shard=${{ matrix.shard }}/4
```

测试并行化的两个层次：框架层（Vitest/Jest 的 worker 池）和平台层（CI 的 matrix 分片）。前者开箱即用，后者能跨机器扩展。需要注意：测试间若有共享状态或顺序依赖，并行会暴露问题——这本身也是并行化带来的「测试质量红利」。

## Artifact Cache

Artifact Cache（产物缓存）指「缓存构建产物和中间产物，供后续阶段或后续流水线复用」：构建出的 dist、测试报告、node_modules 等，上传到 CI 平台的 artifact 存储，下游 job 或下一次流水线直接下载，避免重复生成。

```text
产物缓存的场景：
1. 构建产物复用 —— 构建一次，部署多个环境复用
2. 跨 job 传递 —— build job 产物传给 deploy job
3. 测试报告 —— 测试产物传给报告汇总 job
4. 依赖目录复用 —— 跨流水线复用 node_modules
```

```yaml
# 用 artifact 在 job 间传递构建产物
jobs:
  build:
    steps:
      - run: pnpm build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
          retention-days: 7

  deploy:
    needs: build
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: dist
          path: dist/
      - run: ./deploy.sh
```

```yaml
# 用缓存跨流水线复用产物（比 artifact 更快，适合中间产物）
- uses: actions/cache@v4
  with:
    path: |
      dist
      node_modules/.cache
    key: build-${{ hashFiles('src/**', 'package.json') }}
```

Artifact Cache 与 Dependency/Build Cache 的差异：artifact 是「正式的、需要版本留存的产物」（部署包、报告），缓存是「可再生的、按内容寻址的中间结果」。产物缓存的关键是「构建一次、多处复用」，避免同一产物在不同阶段重复构建。

## 应用场景实战

### 场景一：前端 CI 流水线的完整优化

```yaml
name: CI
on: [push, pull_request]

jobs:
  build-test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4]           # 测试并行分片
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'pnpm'                # 依赖缓存
          cache-dependency-path: 'pnpm-lock.yaml'

      - name: Restore turbo cache
        uses: actions/cache@v4
        with:
          path: .turbo                 # 构建缓存
          key: turbo-${{ github.sha }}
          restore-keys: turbo-

      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm build

      - name: Test (sharded)
        run: pnpm test -- --shard=${{ matrix.shard }}/4

      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
```

### 场景二：多阶段 Docker 构建利用层缓存

```dockerfile
# 多阶段构建 + 层缓存：依赖层稳定，源码层变化才重跑
FROM node:20-alpine AS deps
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile   # 依赖层，很少变化

FROM node:20-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN pnpm build                        # 构建层，源码变化才重跑

FROM nginx:alpine AS runner
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 lockfile 哈希做依赖缓存键，安装阶段从分钟级降到秒级
2. Dockerfile 把依赖安装放前、源码复制放后，充分利用层缓存
3. Monorepo 用 Turborepo/Nx 远程缓存，CI 复用本地和历史的构建结果
4. 测试按 shard 并行，测试时间随 worker 数线性下降
5. 构建产物用 artifact 传递，构建一次、部署复用
6. 只跑必要的检查：PR 只跑影响范围的测试，full suite 留到主干

### 踩坑记录

```text
坑 1：依赖缓存键不含 lockfile
结论：升级依赖后 CI 仍用旧缓存，跑出不一致的结果。
原因：缓存键固定不变，无法感知依赖版本变化。
解法：用 lockfile 哈希做缓存键，依赖一变缓存自动失效。

坑 2：Dockerfile 层顺序错误
结论：源码一改，依赖安装层也全部重跑，镜像构建巨慢。
原因：COPY . . 放在安装依赖之前，源码变化使后续层失效。
解法：先 COPY 锁文件 + install，再 COPY 源码，稳定层在前。

坑 3：测试并行但共享状态冲突
结论：并行后测试随机失败，串行能过。
原因：测试间共享文件、端口或全局变量，并行暴露了隐藏依赖。
解法：隔离测试（独立 mock、独立临时目录），并行化本身是质量检测。

坑 4：所有 job 都全量构建
结论：lint、test、deploy 各自重新 build，浪费数倍时间。
原因：没有用 artifact 传递产物，每个 job 独立构建。
解法：build job 构建一次，上传 artifact，下游 job 下载复用。

坑 5：缓存键过宽导致命中错误产物
结论：缓存键只含分支名，不同提交复用同一缓存，跑出旧代码。
原因：缓存键粒度太粗，无法区分不同源码版本。
解法：缓存键包含源码哈希或 commit sha，内容寻址保证准确。
```
