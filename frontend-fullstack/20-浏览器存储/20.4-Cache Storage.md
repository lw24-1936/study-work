## 概述

Cache Storage 是浏览器提供的**请求/响应**缓存机制，配合 Service Worker 实现离线访问。它缓存的是完整的 Request/Response 对象，不同于 localStorage（键值对）和 IndexedDB（结构化数据）。

```text
Cache Storage 的核心概念：
1. CacheStorage —— 缓存仓库，管理多个 Cache
2. Cache —— 单个缓存，存 Request/Response 对
3. 面向请求 —— 以「请求」为键，缓存「响应」

用途：Service Worker 离线缓存、资源预缓存。
```

## Cache 缓存对象

Cache 对象存「请求 → 响应」的映射，提供增删查方法。

```js
// 打开一个 Cache
const cache = await caches.open('my-cache-v1');

// 添加单个请求（自动 fetch 并缓存）
await cache.add('/api/data');

// 批量添加
await cache.addAll(['/', '/index.js', '/style.css']);

// 手动 put（自定义请求/响应）
await cache.put('/custom', new Response('自定义响应'));
```

```js
// 查询缓存
const response = await cache.match('/api/data');   // 精确匹配
const allResponses = await cache.matchAll('/api/'); // 匹配前缀

// 删除
await cache.delete('/api/data');
```

```text
Cache 的方法：
add / addAll —— 自动 fetch 并缓存
put —— 手动存入 Request/Response
match / matchAll —— 查询缓存
delete —— 删除条目
keys —— 列出缓存的请求
```

## CacheStorage 缓存存储

CacheStorage 是 Cache 的仓库，管理多个命名缓存。

```js
// CacheStorage 通过 caches 访问
caches;                    // CacheStorage 实例

// 打开/创建缓存
const cache = await caches.open('v1');

// 判断缓存是否存在
const has = await caches.has('v1');

// 删除整个缓存
await caches.delete('v1');

// 列出所有缓存名
const names = await caches.keys();   // ['v1', 'v2', ...]

// 全局匹配（跨所有缓存）
const res = await caches.match('/index.html');
```

```text
CacheStorage 的价值：
1. 多版本缓存 —— 用缓存名区分版本（v1、v2）
2. 批量管理 —— 一次性删除旧版本
3. 全局查找 —— match 跨所有缓存搜索
```

## Service Worker Cache 离线缓存

Cache Storage 最核心的用途是配合 Service Worker 实现离线访问。

```js
// Service Worker：预缓存
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('v1').then(cache =>
      cache.addAll(['/', '/app.js', '/style.css']),
    ),
  );
});
```

```js
// Service Worker：拦截请求，优先用缓存
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then(cached => {
      return cached || fetch(event.request);   // 缓存命中返回缓存，否则网络
    }),
  );
});
```

```js
// 版本更新：清理旧缓存
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then(names =>
      Promise.all(
        names.filter(name => name !== 'v2').map(name => caches.delete(name)),
      ),
    ),
  );
});
```

```text
离线缓存的完整流程：
1. install 阶段 —— 预缓存核心资源
2. fetch 阶段 —— 拦截请求，缓存优先/网络优先
3. activate 阶段 —— 清理旧版本缓存
```

## 应用场景实战

### 场景一：预缓存静态资源

```js
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('app-shell-v1').then(cache =>
      cache.addAll([
        '/',
        '/index.html',
        '/static/js/app.js',
        '/static/css/style.css',
      ]),
    ),
  );
});
```

### 场景二：运行时缓存（缓存新请求）

```js
self.addEventListener('fetch', (event) => {
  event.respondWith(
    fetch(event.request)
      .then(response => {
        // 成功响应写入缓存
        const clone = response.clone();
        caches.open('runtime-v1').then(cache => cache.put(event.request, clone));
        return response;
      })
      .catch(() => caches.match(event.request)),   // 网络失败回退缓存
  );
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 缓存名带版本号（v1、v2），便于更新清理
2. activate 阶段清理旧版本缓存
3. 响应对象只能读一次，缓存前 clone
4. 预缓存核心资源（App Shell），运行时缓存动态数据
5. 配合缓存策略（Cache First / Network First 等）

### 踩坑记录

```text
坑 1：响应对象重复消费
结论：缓存 put 后再返回，报错或数据为空。
原因：Response 是流，只能读一次。
解法：put 前 response.clone()。

坑 2：缓存版本未清理
结论：旧版本缓存堆积，占用存储。
原因：未在 activate 清理旧缓存。
解法：activate 里删除非当前版本的缓存。

坑 3：caches.match 跨缓存匹配顺序
结论：匹配到旧版本缓存。
原因：match 跨所有缓存，顺序不保证。
解法：用指定 cache 的 match，或缓存名前缀控制。

坑 4：addAll 一个失败全部失败
结论：一个资源 404，整个预缓存失败。
原因：addAll 是原子操作，任一失败全部 reject。
解法：核心资源单独 add + catch，或用 put 逐个处理。

坑 5：忽略存储配额
结论：缓存过多触发 QuotaExceededError。
原因：Cache Storage 有配额限制。
解法：控制缓存大小，定期清理过期条目。
```
