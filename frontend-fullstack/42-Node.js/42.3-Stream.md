## 概述

Stream 是 Node 处理数据的核心抽象：把数据切分成一块块（chunk）在内存中流动，边读边写，内存占用恒定。流分四类：可读、可写、双工、转换。几乎所有 I/O（文件、网络、进程）都基于流。

```text
Stream 的四种类型：
1. Readable —— 可读流（数据来源），如 fs.createReadStream
2. Writable —— 可写流（数据去向），如 fs.createWriteStream
3. Duplex —— 双工流（既可读又可写），如 net.Socket
4. Transform —— 转换流（读写中转换数据），如 zlib.createGzip
```

```text
为什么用流：
1. 内存恒定 —— 只持有当前 chunk，不整体加载
2. 响应更快 —— 第一块数据到达即可处理
3. 可组合 —— pipe 串联成处理管道
```

## Readable

可读流是数据源，通过 data 事件逐块消费，或用 readable 事件主动拉取。流默认处于 paused（暂停）模式，监听 data 或调 resume 切换到 flowing（流动）模式。

```js
const fs = require('node:fs');

const rs = fs.createReadStream('big.txt', { highWaterMark: 64 * 1024 });

// flowing 模式：data 事件自动推送
rs.on('data', (chunk) => console.log('chunk', chunk.length));
rs.on('end', () => console.log('读完'));
rs.on('error', (err) => console.error(err));
```

```js
// paused 模式：用 read() 主动拉取
rs.on('readable', () => {
  let chunk;
  while ((chunk = rs.read()) !== null) {
    console.log('主动读取', chunk.length);
  }
});
```

```js
// 自定义可读流
const { Readable } = require('node:stream');
const readable = Readable.from(['a', 'b', 'c']);   // 从数组生成
readable.on('data', (chunk) => console.log(chunk.toString()));
```

## Writable

可写流是数据去向，通过 write 写入数据，end 结束写入。write 返回布尔值表示内部缓冲区是否还能继续接收（背压信号）。

```js
const fs = require('node:fs');

const ws = fs.createWriteStream('out.txt');
ws.write('第一行\n');
ws.write('第二行\n');
ws.end('最后一行');         // end 可带最后一块数据
ws.on('finish', () => console.log('写入完成'));
```

```js
// 自定义可写流
const { Writable } = require('node:stream');

const ws = new Writable({
  write(chunk, encoding, callback) {
    console.log('写入', chunk.toString());
    callback();                     // 处理完调用 callback，触发下一块
  },
});
ws.write('hello');
ws.end();
```

## Duplex 与 Transform

双工流同时可读可写（如 socket，读写是两条独立通道）；转换流在读写之间做数据变换（如压缩、加密），读写是同一通道的变形。

```js
const { Duplex, Transform } = require('node:stream');
const zlib = require('node:zlib');

// Transform：转大写
const upper = new Transform({
  transform(chunk, encoding, callback) {
    callback(null, chunk.toString().toUpperCase());
  },
});

// 压缩流（zlib 就是 Transform）
const gzip = zlib.createGzip();

process.stdin.pipe(upper).pipe(process.stdout);
```

```js
// Duplex：内部独立维护读缓冲和写缓冲
const { Duplex } = require('node:stream');

const duplex = new Duplex({
  read() { this.push('可读数据'); this.push(null); },
  write(chunk, enc, cb) { console.log('写入', chunk.toString()); cb(); },
});
duplex.on('data', (d) => console.log('读到', d.toString()));
duplex.write('发送');
```

## backpressure

背压是流生产快于消费时的反压机制：可写流缓冲区满了，write 返回 false，通知上游暂停，防止内存被数据淹没。

```text
背压的产生与处理：
1. 可写流内部有缓冲（highWaterMark 阈值）
2. 写入超过阈值时 write 返回 false
3. 上游应暂停，等可写流 drain 事件再继续
4. 不处理背压会导致内存无限增长
```

```js
// 手动处理背压：write 返回 false 时暂停，drain 后恢复
const fs = require('node:fs');

const rs = fs.createReadStream('big.txt');
const ws = fs.createWriteStream('out.txt');

rs.on('data', (chunk) => {
  const canContinue = ws.write(chunk);
  if (!canContinue) {
    rs.pause();                     // 背压：暂停上游
    ws.once('drain', () => rs.resume());
  }
});
```

```text
highWaterMark：
默认值 —— 可读流 64KB，可写流 16KB
意义 —— 缓冲区水位线，超过即触发背压
```

## pipe 与 pipeline

pipe 串联读写流并自动处理背压；pipeline 是 pipe 的加强版，自动处理错误传播和清理，推荐生产使用。

```js
const fs = require('node:fs');
const zlib = require('node:zlib');

// pipe 串联：读 → 压缩 → 写
fs.createReadStream('big.txt')
  .pipe(zlib.createGzip())
  .pipe(fs.createWriteStream('big.txt.gz'));
```

```js
// pipeline：自动处理错误和清理，返回 Promise
const { pipeline } = require('node:stream/promises');

async function compress() {
  await pipeline(
    fs.createReadStream('big.txt'),
    zlib.createGzip(),
    fs.createWriteStream('big.txt.gz'),
  );
  console.log('压缩完成');
}
```

```text
pipe vs pipeline：
pipe    —— 简单串联，错误需逐段监听，不会自动销毁中间流
pipeline —— 任一段出错即销毁所有流并抛出，错误处理完备
```

## 应用场景实战

### 场景一：文件压缩（读 → 压缩 → 写）

```js
const fs = require('node:fs');
const zlib = require('node:zlib');
const { pipeline } = require('node:stream/promises');

async function gzipFile(src, dest) {
  await pipeline(
    fs.createReadStream(src),
    zlib.createGzip(),
    fs.createWriteStream(dest),
  );
  console.log(`${src} 已压缩为 ${dest}`);
}

gzipFile('data.txt', 'data.txt.gz').catch(console.error);
```

### 场景二：日志转换流（大写 + 前缀）

```js
const { Transform } = require('node:stream');

const logger = new Transform({
  transform(chunk, encoding, callback) {
    const line = `[${new Date().toISOString()}] ${chunk.toString().toUpperCase()}`;
    callback(null, line);
  },
});

process.stdin.pipe(logger).pipe(process.stdout);
// 输入 hello 回车 → 输出 [时间戳] HELLO
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产环境用 pipeline 而非 pipe，错误处理才完备
2. 正确处理背压：write 返回 false 时暂停上游，drain 后恢复
3. 监听 error 事件，流错误不处理会抛未捕获异常
4. 大文件、网络传输一律走流，不用 readFile 整体加载
5. 自定义流实现 _read/_write 方法，不要覆写 push/write 公共接口

### 踩坑记录

```text
坑 1：不处理背压导致内存飙升
结论：读写速度不匹配时内存持续增长直至 OOM。
原因：忽略了 write 返回的 false，上游继续狂推数据。
解法：write 返回 false 时暂停上游，drain 事件后恢复；或直接 pipe/pipeline。

坑 2：流错误未监听导致进程崩溃
结论：读文件出错时进程直接崩掉。
原因：流只监听了 data/end，没监听 error 事件。
解法：每个流都监听 error，或 pipeline 统一捕获。

坑 3：pipe 中途出错不清理后续流
结论：压缩到一半失败，写文件流还开着，留下损坏文件。
原因：pipe 不会自动销毁下游流。
解法：用 pipeline，任一段出错自动销毁所有流。

坑 4：end 之后继续 write 报错
结论：写入完成后又 write 抛 "write after end" 错误。
原因：end() 调用后流已关闭，又调了 write。
解法：写数据前判断 writableEnded，或确保逻辑上 end 是最后一次调用。

坑 5：objectMode 未开启却写对象
结论：向流写对象报类型错误。
原因：默认流只接受 Buffer/string，写入对象失败。
解法：需要对象流时在构造时设 objectMode: true。
```
