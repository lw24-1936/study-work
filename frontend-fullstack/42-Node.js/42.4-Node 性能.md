## 概述

Node 性能优化围绕两个维度展开：**CPU**（事件循环是否被阻塞、热点函数在哪）和**内存**（堆是否持续增长、是否泄漏）。工具上靠 V8 自带的 profiler 和 heap snapshot，手段上用 worker_threads 分摊 CPU 密集任务。

```text
Node 性能问题的两个信号：
1. 事件循环滞后（lag）—— 请求变慢、响应抖动，CPU 被阻塞
2. 内存持续增长 —— 堆快照对比发现对象不被回收，即内存泄漏
```

```text
诊断工具链：
1. 事件循环滞后 —— 自测 loop 延迟 + clinic 等工具
2. CPU 热点 —— --prof + prof-process，或 --cpu-prof
3. 堆内存 —— --heap-prof 生成快照，Chrome DevTools 分析
```

## Event Loop Lag

事件循环滞后是「主线程被占用、来不及处理 I/O」的直接指标：设定时器，测量实际触发比预期晚多少。滞后越大说明主线程越忙。

```js
// 测量事件循环滞后：setInterval 应 500ms 触发，测实际偏差
let last = Date.now();
setInterval(() => {
  const now = Date.now();
  const lag = now - last - 500;
  if (lag > 100) console.log('事件循环滞后', lag, 'ms');
  last = now;
}, 500);
```

```text
事件循环滞后的常见原因：
1. 同步 CPU 密集任务（大循环、正则、JSON 序列化）
2. 大量同步 I/O（readFileSync）
3. 过多的 process.nextTick 递归
```

```js
// 拆分大任务：每处理一部分让出事件循环
async function processLarge(items) {
  for (let i = 0; i < items.length; i++) {
    doWork(items[i]);
    if (i % 1000 === 0) {
      await new Promise((r) => setImmediate(r));   // 让出主线程
    }
  }
}
```

## CPU Profiling

CPU Profiling 找出最耗时的函数。用 `--cpu-prof` 启动，或 `--prof` 配合 `--prof-process` 解析，产出的文件用 Chrome DevTools 打开看火焰图。

```bash
# 方式一：--cpu-prof 生成 .cpuprofile，DevTools 直接打开
node --cpu-prof app.js

# 方式二：--prof 生成 v8.log，再解析成可读文本
node --prof app.js
node --prof-process isolate-*.log > profile.txt
```

```js
// 代码内手动起停 profiler（V8 inspector 协议）
const inspector = require('node:inspector');
const session = new inspector.Session();
session.connect();
session.post('Profiler.enable', () => {
  session.post('Profiler.start', () => {
    heavyWork();
    session.post('Profiler.stop', (err, { profile }) => {
      require('node:fs').writeFileSync('profile.cpuprofile', JSON.stringify(profile));
    });
  });
});
```

```text
火焰图读法：
1. 横轴 —— 时间占比，越宽越耗时
2. 纵轴 —— 调用栈深度，自下而上
3. 找最宽的"平顶"（self time 高），就是优化目标
```

## Heap Snapshot

堆快照记录某一时刻堆上所有对象的引用关系。取两个快照对比，看哪些对象数量/大小持续增长，定位泄漏。

```bash
# 启动时带 --heap-prof，在关键点生成快照
node --heap-prof app.js
```

```js
// 代码内手动写快照
const inspector = require('node:inspector');
const fs = require('node:fs');

const session = new inspector.Session();
session.connect();
session.post('HeapProfiler.enable', () => {
  session.post('HeapProfiler.takeHeapSnapshot', null, (err, { data }) => {
    fs.writeFileSync('snapshot.heapsnapshot', data);
  });
});
```

```text
快照分析三看：
1. Constructor —— 按构造函数归类，找数量异常的对象
2. Shallow Size —— 对象自身大小
3. Retained Size —— 对象及其引用链释放后能回收的总大小
```

## GC 与 Memory Leak

V8 用分代垃圾回收（新生代 Scavenge + 老生代 Mark-Sweep/Compact）。内存泄漏是「不再使用的对象仍被引用，无法回收」导致的堆持续增长。

```js
// 观察 GC 与内存：启动带 --trace-gc 看回收日志
// node --trace-gc --expose-gc app.js
if (global.gc) {
  global.gc();                      // 手动触发 GC（需 --expose-gc）
  console.log(process.memoryUsage());
}
```

```text
V8 分代 GC：
新生代 —— 存活时间短的对象，Scavenge 复制算法，回收快
老生代 —— 长期存活对象，Mark-Sweep 标记清除 + Mark-Compact 整理
```

```text
常见内存泄漏场景：
1. 全局变量/缓存无限增长（Map 只进不出）
2. 闭包持有大对象引用
3. 定时器/监听器未清理（setInterval 不清除）
4. 流未关闭，缓冲区持续累积
```

```js
// 典型泄漏：缓存无限增长
const cache = new Map();
function onRequest(data) {
  cache.set(data.id, data);        // 只增不减，长期运行必爆
}
// 修复：加容量上限 + LRU 淘汰
if (cache.size > 1000) {
  const firstKey = cache.keys().next().value;
  cache.delete(firstKey);
}
```

## Worker Threads

Worker Threads 把 CPU 密集任务丢到工作线程，避免阻塞主线程事件循环。适合加密、压缩、图像处理、大计算等场景。

```js
// worker.js
const { parentPort } = require('node:worker_threads');

parentPort.on('message', (n) => {
  let sum = 0;
  for (let i = 0; i < n; i++) sum += i;
  parentPort.postMessage(sum);
});
```

```js
// main.js
const { Worker } = require('node:worker_threads');

function runWorker(n) {
  return new Promise((resolve, reject) => {
    const w = new Worker('./worker.js');
    w.on('message', resolve);
    w.on('error', reject);
    w.postMessage(n);
  });
}

// 并发跑 4 个 CPU 密集任务
Promise.all([runWorker(1e8), runWorker(1e8), runWorker(1e8), runWorker(1e8)])
  .then((results) => console.log(results));
```

```js
// SharedArrayBuffer 共享内存：多线程读写同一块内存
const { Worker } = require('node:worker_threads');

const shared = new SharedArrayBuffer(4);
const view = new Int32Array(shared);
const w = new Worker(`
  const { parentPort, workerData } = require('node:worker_threads');
  const v = new Int32Array(workerData.buf);
  Atomics.add(v, 0, 1);
  parentPort.postMessage('done');
`, { eval: true, workerData: { buf: shared } });

w.on('message', () => console.log('结果', view[0]));   // 1
```

## 应用场景实战

### 场景一：定位内存泄漏（快照对比）

```js
// 模拟泄漏：全局数组只增不减
const leaks = [];
function addLeak() {
  leaks.push({ data: new Array(1000).fill('x') });
}
setInterval(addLeak, 100);

// 诊断流程：
// 1. node --heap-prof app.js
// 2. 运行一段时间后手动取快照 snapshot1.heapsnapshot
// 3. 再运行一段时间取 snapshot2.heapsnapshot
// 4. DevTools 打开两份快照，Comparison 视图看 delta
// 5. 发现 Array 数量持续增长 → 定位到 leaks 数组
```

### 场景二：worker_threads 分摊 CPU 密集计算

```js
// 加密任务丢给线程池，主线程保持响应
const { Worker } = require('node:worker_threads');
const os = require('node:os');

const pool = Array.from({ length: os.cpus().length }, () => new Worker(`
  const { parentPort } = require('node:worker_threads');
  parentPort.on('message', (data) => {
    const crypto = require('node:crypto');
    const hash = crypto.createHash('sha256').update(data).digest('hex');
    parentPort.postMessage(hash);
  });
`, { eval: true }));

let next = 0;
function hashAsync(data) {
  return new Promise((resolve) => {
    const w = pool[next++ % pool.length];
    w.once('message', resolve);
    w.postMessage(data);
  });
}

hashAsync('hello').then((h) => console.log(h));
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先测后优化：用 CPU profile / heap snapshot 定位，不靠猜
2. 缓存必须带容量上限和淘汰策略，禁止无限 Map
3. CPU 密集任务丢 worker_threads，别阻塞主线程事件循环
4. 大循环里定期 setImmediate 让出事件循环，保持响应
5. 定时器、监听器、流用毕即清理，避免隐性引用堆积

### 踩坑记录

```text
坑 1：把 CPU 密集任务放主线程
结论：一个计算任务拖慢整个服务，所有请求超时。
原因：Node 单线程，同步计算占满事件循环。
解法：拆块让出，或丢给 worker_threads。

坑 2：只看 process.memoryUsage 的 rss 判断泄漏
结论：rss 高不等于泄漏，误判了正常的内存增长。
原因：rss 含 V8 预留但未使用的内存，GC 后不一定归还 OS。
解法：看 heapUsed 趋势 + 快照对比，而非单点 rss。

坑 3：--prof 生成的日志没解析
结论：拿到 isolate-*.log 不知怎么看，白跑一遍。
原因：--prof 输出的是 V8 内部日志格式。
解法：node --prof-process isolate-*.log 转成可读的文本报告。

坑 4：worker_threads 传大数据性能差
结论：往 worker 传大对象很慢，反而更卡。
原因：postMessage 默认结构化克隆，大对象序列化开销大。
解法：共享数据用 SharedArrayBuffer，或传 Buffer 走转移（transfer）。

坑 5：GC 参数乱调
结论：改了 --max-old-space-size 等参数后性能反而下降。
原因：不理解分代回收就调 GC 参数。
解法：默认 GC 策略已够用，先优化代码，最后才考虑调 GC 参数。
```
