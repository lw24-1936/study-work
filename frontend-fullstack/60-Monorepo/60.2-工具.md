## 概述

Monorepo 工具解决的是「多个包的安装、依赖管理、构建调度、缓存」问题。它们分两层：pnpm/Yarn 负责 Workspace 与依赖安装（底层），Nx/Turborepo/Rush/Lerna 负责任务编排与构建加速（上层）。选型时先确定包管理器，再选编排工具。

```text
Monorepo 工具全景：
1. pnpm —— 包管理器，Workspace + 硬链接去重（最省磁盘）
2. Turborepo —— 构建编排，任务图 + 本地/远程缓存（轻量，Vercel）
3. Nx —— 构建编排 + 插件体系 + 代码生成（功能最全）
4. Rush —— 微软出品，大团队 + 严格发布流程
5. Lerna —— 老牌工具，现已并入 Nx，负责版本管理与发布
```

```text
选型速查：
            pnpm      Turborepo   Nx         Rush       Lerna
定位        包管理    构建加速    构建+插件   发布治理   版本发布
缓存        依赖缓存  本地+远程   本地+远程   本地+远程   无
学习成本    低        低          中          高         低
适用规模    任意      中小团队    中大型      超大团队   存量项目
```

## pnpm workspace

pnpm 是高效的包管理器，Workspace 是其 Monorepo 基础能力。核心机制是硬链接 + 内容寻址存储：所有包依赖存储在全局 store，各项目用硬链接引用，同一依赖全盘只存一份。

```yaml
# pnpm-workspace.yaml —— workspace 声明
packages:
  - "packages/*"
  - "apps/*"
```

```bash
# 常用命令
pnpm install                       # 安装全部 workspace 依赖
pnpm add lodash --filter @app/web  # 只给指定包加依赖
pnpm -r run build                  # 递归在所有包执行 build
pnpm --parallel -r run test        # 并行递归执行
pnpm exec tsc                     # 在 workspace 内执行命令
```

```text
pnpm 相对 npm 的优势：
1. 硬链接 —— 依赖不重复复制，安装快、省磁盘
2. 非扁平 node_modules —— 无幽灵依赖，依赖关系清晰
3. 严格 —— 只能 import 已声明的依赖，暴露隐藏依赖
4. workspace 协议 —— "workspace:^1.0.0" 本地包引用
```

```json
// 依赖本地 workspace 包用 workspace: 协议
{
  "dependencies": {
    "@myorg/ui": "workspace:^1.0.0"
  }
}
```

## Nx

Nx 是全功能 Monorepo 构建系统，核心是「任务图 + 计算缓存 + 代码生成 + 插件」。它知道项目之间的依赖关系，能精确算出「改了哪些代码需要重跑哪些任务」。

```bash
# 初始化（可选 React/Angular/Node 等插件）
npx create-nx-workspace@latest myorg

# 查看任务依赖图
npx nx graph

# 构建某项目及其依赖
npx nx build myapp

# 只构建受影响的项目
npx nx affected --target=build
```

```json
// nx.json —— Nx 核心配置
{
  "$schema": "./node_modules/nx/schemas/nx-schema.json",
  "targetDefaults": {
    "build": {
      "dependsOn": ["^build"],
      "cache": true
    }
  },
  "namedInputs": {
    "default": ["{projectRoot}/**/*", "sharedGlobals"]
  }
}
```

```text
Nx 的核心概念：
1. project.json —— 每个项目声明 targets（build/test/lint）
2. targetDefaults —— 统一 target 的缓存与依赖配置
3. 计算缓存 —— 按输入 hash 复用上次结果，命中则跳过执行
4. 插件 —— 识别框架约定，自动推断 targets 与依赖
5. 代码生成 —— nx generate 生成项目/组件模板
```

## Turborepo

Turborepo 是 Vercel 出品的轻量构建编排工具，理念是「内容寻址缓存 + 任务图调度」。相比 Nx 更简单：不需要为每个项目写配置，约定大于配置，几乎零配置接入已有 Monorepo。

```json
// turbo.json —— Turborepo 核心配置
{
  "$schema": "https://turbo.build/schema.json",
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "lint": {
      "dependsOn": ["^build"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}
```

```bash
# 安装与运行
npm install turbo
npx turbo run build        # 按任务图并行构建
npx turbo run build --filter=@app/web
npx turbo run build --force   # 忽略缓存强制重跑
npx turbo prune --scope=@app/web --docker  # 生成 Docker 裁剪产物
```

```text
Turborepo 的缓存原理：
1. 对每个任务的输入文件（源码 + 依赖源码）算 hash
2. hash 相同且上次有产物 → 直接复用输出（本地 .turbo 目录）
3. 配置 remote cache → 团队共享，CI 也能命中本地构建结果
4. 依赖有变化 → hash 变化 → 下游任务自动失效重跑
```

## Rush

Rush 是微软出品、面向大型团队（微软内部数百个项目）的 Monorepo 治理工具，强项是「统一依赖版本 + 严格变更日志 + 批量发布」。它不追求极致构建速度，而是追求「可预测、可审计、可回滚」的工程纪律。

```text
Rush 的核心机制：
1. rush.json —— 注册所有 project（每个项目必须显式声明）
2. 统一 lockfile —— 单一 shrinkwrap，全仓库依赖一致
3. rush change —— 提交前强制写变更说明，生成 CHANGELOG
4. rush version —— 依据 change 文件统一升版本
5. rush publish —— 按依赖顺序批量发布，带审核
```

```bash
# 初始化
npm install -g @microsoft/rush
rush init

# 关键流程
rush update              # 安装并校验依赖（等价 install）
rush build               # 并行构建所有项目
rush change              # 记录本次变更（写 change 文件）
rush version --bump      # 根据 change 文件升版本
rush publish             # 批量发布 + git tag
```

```text
Rush 适合谁：
1. 超大团队（百人级），需要严格的发布审计
2. 依赖版本必须全仓库统一（避免版本漂移）
3. 需要 change log / 回滚 / 审批等治理能力

不适合：小团队（太重）、追求构建速度（Rush 不是最快的）
```

## Lerna

Lerna 是最早的 JS Monorepo 工具，主打「多包版本管理与发布」。它自己不解决构建缓存（那是后来 Turborepo/Nx 的活），早期被广泛使用，2022 年被 Nx 团队接管后重心转向兼容与迁移。

```bash
# 初始化（经典模式）
npx lerna init

# 多包同时执行命令
npx lerna run build

# 版本管理与发布
npx lerna version          # 交互式升版本 + 打 tag + 生成 CHANGELOG
npx lerna publish          # 发布所有变更包
```

```json
// lerna.json
{
  "version": "independent",
  "npmClient": "pnpm",
  "command": {
    "publish": {
      "conventionalCommits": true
    }
  }
}
```

```text
Lerna 的两种版本模式：
1. fixed —— 所有包统一版本号（一次发布全部升版）
2. independent —— 各包独立版本号（只升发生变化的包）

现状：Lerna 已并入 Nx 维护，新项目建议直接选 Nx 或 Turborepo，
存量 Lerna 项目可用 nx 的命令保持兼容。
```

## 应用场景实战

### 场景一：零配置给现有 pnpm Monorepo 加 Turborepo 构建缓存

```bash
# 已有 pnpm workspace，直接加 turbo
pnpm add -D turbo -w
```

```json
// 根目录 turbo.json
{
  "$schema": "https://turbo.build/schema.json",
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**"]
    },
    "type-check": {},
    "test": {
      "dependsOn": ["build"]
    }
  }
}
```

```bash
# 根 package.json 加脚本，跑一次后二次运行即命中缓存
npx turbo run build
# 第二次：大部分 task 显示 "FULL TURBO"，秒级完成
```

### 场景二：用 Nx 的项目图排查依赖环路

```bash
# 生成可视化依赖图，浏览器打开查看
npx nx graph

# 只看某个项目的上下游
npx nx graph --focus=@myorg/ui

# affected 配合 CI，只测受影响的包
npx nx affected --target=test --base=main --head=HEAD
```

## 最佳实践与踩坑记录

### 最佳实践

1. 包管理器选 pnpm（硬链接省空间 + 严格依赖），构建编排按需选 Turborepo（轻）或 Nx（全）
2. 缓存输出目录要声明准确（outputs），漏声明会导致产物不缓存
3. dev 类长驻进程设 `cache: false` + `persistent: true`，避免误缓存
4. CI 里用 `affected` 而非全量构建，显著缩短流水线
5. 团队协作开启 Remote Cache，让 CI 复用本地构建结果
6. 发布类需求（批量升版 + CHANGELOG）用 Rush 或 Lerna 的 version 能力

### 踩坑记录

```text
坑 1：Turborepo 缓存命中但产物是旧的
结论：改了依赖包的源码，下游却没重新构建。
原因：依赖关系没写对，dependsOn 缺了 "^build"。
解法：被依赖包的 target 要写 "dependsOn": ["^build"]，
     确保依赖先构建、下游感知依赖变更。

坑 2：pnpm 下 Nx 找不到依赖
结论：nx build 报 module not found。
原因：pnpm 非扁平 node_modules，Nx 未识别 pnpm 布局。
解法：Nx 新版自动支持 pnpm，若异常在 nx.json 无特殊配置时
     检查是否用了 --hoist 或手动提升。

坑 3：Remote Cache 泄漏敏感产物
结论：构建产物含密钥/环境变量被缓存共享。
原因：未区分「可缓存」与「不可缓存」的 target。
解法：含密钥的 target 设 cache:false，或在 outputs 里排除。

坑 4：Lerna 升级到 v7+ 行为变化
结论：lerna bootstrap 等旧命令被移除。
原因：Lerna 并入 Nx，旧命令迁移到 nx 生态。
解法：用 pnpm install 替代 bootstrap，用 nx run 替代 run。
```
