## 概述

Monorepo 工程化解决的核心问题是「规模」——包一多，全量构建、全量测试就慢到不可接受。于是有了任务图、缓存、增量构建、受影响构建、依赖约束这一整套机制，让「改了 1 个包只跑该跑的任务、没改的复用上次结果」。

```text
Monorepo 工程化的五个核心机制：
1. Task Graph —— 任务依赖建模，决定「什么先跑、什么能并行」
2. Cache —— 本地缓存，输入不变则复用输出
3. Remote Cache —— 团队共享缓存，CI 复用本地结果
4. Incremental Build —— 只编译变化的部分，跳过未变的
5. Affected Build —— 结合依赖图算「受影响范围」，只构建下游
```

```text
这些机制的本质：
把「构建」从「状态」视角看 —— 只要输入（源码 + 依赖）没变，
输出（产物）就没变，直接复用即可。缓存命中率是工程效率的
核心指标。
```

## Task Graph

Task Graph（任务图）把每个包的每个任务（build/test/lint）建模成图节点，依赖关系建模成边。构建系统按拓扑序调度，互不依赖的任务并行执行。

```text
任务图示例：
@myorg/utils:build → @myorg/ui:build → @app/web:build
                                     ↘ @app/admin:build

调度顺序：
第 1 批（并行）：@myorg/utils:build
第 2 批（并行）：@myorg/ui:build
第 3 批（并行）：@app/web:build、@app/admin:build
```

```json
// turbo.json —— 声明任务间依赖
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"]   // ^ 表示「依赖包的 build 先跑」
    },
    "test": {
      "dependsOn": ["build"]     // 无 ^ 表示「本包 build 先跑」
    }
  }
}
```

```text
dependsOn 语法：
"^build"    —— 所有被依赖包的 build 先完成
"build"     —— 本包自己的 build 先完成
"^build" 与 "build" 可同时声明，形成完整依赖链
```

## Cache

Cache（缓存）是构建加速的第一手段：以任务输入（源码、配置、依赖版本）计算 hash，hash 命中则直接复用上次输出，整个任务跳过执行。

```text
缓存的工作原理：
1. 收集输入 —— 源码文件、依赖的 lockfile、环境变量、task 配置
2. 计算 hash —— 对输入做内容寻址（不是时间戳）
3. 查缓存 —— hash 已存在 → 恢复输出产物，标记 cache hit
4. 未命中 —— 执行任务，把输出存入缓存供下次复用
```

```json
// turbo.json —— 配置缓存输出
{
  "pipeline": {
    "build": {
      "outputs": ["dist/**", ".next/**", "!.next/cache/**"],
      "cache": true
    },
    "dev": {
      "cache": false        // dev 长驻进程不缓存
    }
  }
}
```

```text
缓存输入的影响因素：
1. 源码内容（含依赖包源码）
2. lockfile 变化
3. 相关环境变量（如 NODE_ENV）
4. 全局配置（tsconfig、eslint 配置）

任何一个变化都会导致 hash 变化 → 缓存失效 → 重新执行。
```

## Remote Cache

Remote Cache（远程缓存）把本地缓存上传到云端共享，让团队成员的构建、CI 流水线都能复用彼此的结果。新成员 clone 代码后第一次构建即可命中缓存，不必从头编译。

```bash
# Turborepo 远程缓存 —— Vercel 托管
npx turbo login
npx turbo link

# 本地构建后自动上传缓存
npx turbo run build

# CI 里设置同样的 token，复用远程缓存
export TURBO_TOKEN=xxx
export TURBO_TEAM=my-team
```

```text
Remote Cache 的价值：
1. CI 复用本地结果 —— 开发者在本地构建后，CI 直接命中
2. 跨机器复用 —— 换电脑、新同事、多台 CI runner 共享
3. 分支间复用 —— 相同输入不同分支也命中

实现方式：
1. 托管服务（Vercel Remote Cache、Nx Cloud）
2. 自建 —— 存到 S3 / MinIO / GCS（用官方 adapter 或自写）
```

```text
安全注意：
Remote Cache 存的是构建产物，若产物含密钥/环境变量，
等同于把敏感信息上传到云端。含密 target 务必 cache:false。
```

## Incremental Build

Incremental Build（增量构建）指「只编译发生变化的部分，而不是每次都从头编译」。在单包内部，它靠编译器（如 tsc 的 `incremental`、esbuild/Webpack 的缓存）实现；在 Monorepo 层面，它靠任务图 + 缓存实现。

```text
两层增量构建：
1. 单包内部 —— 编译器缓存已解析的 AST/模块图，只重编译变更文件
2. Monorepo 层面 —— 只有输入 hash 变化的任务才重新执行

tsc 增量示例（tsconfig.json）：
{
  "compilerOptions": {
    "incremental": true,
    "tsBuildInfoFile": "./.tsbuildinfo"
  }
}
```

```json
// turbo.json —— 声明全局依赖，精确控制增量失效
{
  "globalDependencies": [
    "tsconfig.base.json",
    ".env"
  ]
}
```

```text
增量构建的边界：
「哪些输入算进 hash」决定了增量精度。声明太宽 → 命中率低；
声明太窄 → 漏算依赖、产物错误。globalDependencies 用于
声明「全仓库共享」的输入（如根 tsconfig、环境变量）。
```

## Affected Build

Affected Build（受影响构建）结合 Git 变更与依赖图，算出「本次提交影响了哪些包」，只对这些包执行任务。是 CI 提速的关键——PR 改了 1 个包，就只测这个包及其下游，而不是全仓库跑一遍。

```bash
# Nx —— 相对 main 分支，只构建受影响的项目
npx nx affected --target=build --base=main --head=HEAD

# Turborepo —— --filter=... 语法表达「依赖图上游受影响」
npx turbo run build --filter=...[origin/main]

# 只测受影响的下游（不含上游本身）
npx turbo run test --filter=...@myorg/utils --filter=...[origin/main]
```

```text
Affected 的判定逻辑：
1. 用 git diff 拿到本次变更的文件
2. 定位这些文件属于哪些包（记为 changed 集合）
3. 在依赖图上沿「被依赖」方向扩展 —— 依赖 changed 的包也受影响
4. 最终集合 = changed + 所有直接/间接依赖它的包
```

```text
filter 语法（Turborepo）：
--filter=@app/web        单包
--filter=@app/web...     该包及其所有依赖（上游）
--filter=...@app/web     依赖该包的所有包（下游）
--filter=@app/web...[main]  结合 git 分支变化
```

## Dependency Constraints

Dependency Constraints（依赖约束）是一套「谁能依赖谁」的规则，防止架构腐化。例如：`utils` 不允许依赖 `ui`，`ui` 不允许依赖 `apps`，`apps` 不允许互相依赖。约束在 CI 里强制校验。

```text
分层约束示例（依赖只能自上而下）：
apps（应用层）
  ↓ 可依赖
ui / feature（业务组件层）
  ↓ 可依赖
utils / config（基础层）

违反约束的依赖（应被 CI 拒绝）：
utils → ui          （基础层不能依赖上层）
ui → apps           （组件不能依赖应用）
apps/web → apps/admin（应用间不能互相依赖）
```

```text
实现方式：
1. ESLint —— eslint-plugin-boundaries / import/no-restricted-paths
2. Nx —— project tag + enforce-module-boundaries rule
3. Turborepo —— 无内置，靠 ESLint 规则配合
```

```json
// Nx 项目标签 + 边界规则（.eslintrc.json）
{
  "rules": {
    "@nx/enforce-module-boundaries": [
      "error",
      {
        "depConstraints": [
          {
            "sourceTag": "scope:utils",
            "onlyDependOnLibsWithTags": []
          },
          {
            "sourceTag": "scope:ui",
            "onlyDependOnLibsWithTags": ["scope:utils"]
          },
          {
            "sourceTag": "scope:app",
            "onlyDependOnLibsWithTags": ["scope:ui", "scope:utils"]
          }
        ]
      }
    ]
  }
}
```

## 应用场景实战

### 场景一：搭建带缓存的 CI 流水线

```yaml
# .github/workflows/ci.yml —— 用 affected + 远程缓存
name: CI
on: [pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    env:
      TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
      TURBO_TEAM: my-team
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0      # 必须有完整历史才能算 affected
      - uses: pnpm/action-setup@v2
      - uses: actions/setup-node@v4
        with:
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm turbo run build test lint --filter=...[origin/main]
```

### 场景二：强制依赖方向，守住架构边界

```bash
# 用 eslint-plugin-boundaries 定义分层
pnpm add -D eslint-plugin-boundaries -w
```

```js
// eslint.config.js —— 依赖约束规则
module.exports = [
  {
    plugins: { boundaries: require('eslint-plugin-boundaries') },
    settings: {
      'boundaries/elements': [
        { type: 'app', pattern: 'apps/*', mode: 'folder' },
        { type: 'ui', pattern: 'packages/ui/*' },
        { type: 'utils', pattern: 'packages/utils/*' }
      ],
      'boundaries/include': ['**/*']
    },
    rules: {
      'boundaries/element-types': ['error', {
        default: 'disallow',
        rules: [
          { from: 'app', allow: ['ui', 'utils'] },
          { from: 'ui', allow: ['utils'] },
          { from: 'utils', allow: [] }
        ]
      }]
    }
  }
];
```

## 最佳实践与踩坑记录

### 最佳实践

1. CI 里 `fetch-depth: 0`，否则拿不到基线分支、affected 算不准
2. `outputs` 声明准确，缓存才有意义；漏了产物目录等于白缓存
3. 长驻进程（dev、watch）和含密任务设 `cache: false`
4. 全局共享输入（根 tsconfig、env）用 `globalDependencies` 声明
5. 依赖约束写进 CI，靠人自觉守不住架构边界
6. 远程缓存开起来，团队规模越大收益越明显

### 踩坑记录

```text
坑 1：affected 构建了「无关」的包
结论：改了一个包，全仓库任务都跑了。
原因：CI 没传 --filter/--affected，或 fetch-depth 不够导致
      git diff 算不出基线，退化成全量。
解法：用 --filter=...[origin/main]，并保证 checkout fetch-depth:0。

坑 2：缓存命中但产物是旧的
结论：改了依赖包，下游没重新构建。
原因：dependsOn 没写 "^build"，下游不感知上游变化。
解法：pipeline 里 build 声明 "dependsOn": ["^build"]。

坑 3：远程缓存导致环境泄漏
结论：测试环境变量/密钥被上传到远程缓存。
原因：含环境变量的构建 target 设了 cache:true。
解法：把含密 target 设 cache:false，或在 CI 里注入而非写进产物。

坑 4：tsc 增量缓存错乱
结论：删了文件重新构建报错。
原因：.tsbuildinfo 记录了旧文件列表，增量复用出错。
解法：clean 时同时删 .tsbuildinfo，或 CI 里先跑 clean。

坑 5：依赖约束误伤类型导入
结论：只有类型 import（import type）也被边界规则拦截。
原因：规则未区分 value import 和 type import。
解法：边界规则里允许 type-only import（enforce-module-boundaries
      的 allowTypeImports 选项）。
```
