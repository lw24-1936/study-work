## 概述

Monorepo（单一仓库）是把多个相关项目（Package）放在同一个 Git 仓库里统一管理的开发模式，与之相对的是 Polyrepo（每个项目独立仓库）。它解决的是「多项目共享代码、统一版本、原子提交」的问题，前端领域因共享组件、工具链复用需求强，Monorepo 几乎成了大型前端项目的默认选择。

```text
Monorepo 的核心价值：
1. 原子提交 —— 一次 commit 同时改多个包，保证一致性
2. 代码共享 —— 共享包直接 import，无需发版再安装
3. 统一工具链 —— 一份 ESLint/TS 配置、一次依赖安装
4. 跨包重构 —— 改共享包时能立即看到所有下游受影响
5. 统一版本 —— 版本联动、依赖对齐，避免版本漂移
```

```text
Monorepo vs Polyrepo：
            Monorepo          Polyrepo
仓库数量     1 个              每项目 1 个
代码共享     直接引用          发版 + 安装
版本管理     统一/联动         各自独立
构建缓存     易共享            难共享
仓库体积     大               小
权限控制     粗（按目录）      细（按仓库）
```

## Workspace

Workspace（工作区）是包管理器提供的「一个仓库管理多个包」的机制。在根目录声明各包的路径后，包管理器把子包符号链接到根 `node_modules`，使包之间可以直接 `import`，且依赖只安装一份。

```json
// 根目录 package.json —— pnpm 的 workspace 声明
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": [
    "packages/*",
    "apps/*"
  ]
}
```

```text
Workspace 的三种声明方式：
1. npm/yarn —— package.json 的 workspaces 字段
2. pnpm —— pnpm-workspace.yaml 单独文件（推荐，更清晰）
3. Lerna —— 早期靠 lerna.json 的 packages 字段

pnpm 推荐用 pnpm-workspace.yaml：
packages:
  - "packages/*"
  - "apps/*"
```

```bash
# 根目录统一安装，子包依赖提升（hoist）到根 node_modules
pnpm install

# 所有包可互相引用，例如 apps/web 里：
pnpm add @repo/ui --workspace
```

## Package

Package 是 Monorepo 里的最小单元，每个包有独立的 `package.json`、独立版本号、独立发布。包名通常带命名空间前缀（scope），如 `@myorg/ui`，避免与 npm 上其他包冲突。

```text
典型 Monorepo 目录结构：
my-monorepo/
├── package.json          # 根包（private，不发布）
├── pnpm-workspace.yaml
├── packages/
│   ├── ui/               # 组件库
│   ├── utils/            # 工具函数
│   └── config/           # 共享配置（eslint、tsconfig）
└── apps/
    ├── web/              # 主应用
    └── admin/            # 管理后台
```

```json
// packages/utils/package.json —— 一个独立的包
{
  "name": "@myorg/utils",
  "version": "1.2.0",
  "main": "dist/index.js",
  "types": "dist/index.d.ts",
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

## Shared Package

Shared Package（共享包）是「多个项目共同使用」的包，是 Monorepo 存在的核心理由。设计良好的共享包对外暴露稳定 API，内部实现可独立演进。

```text
Shared Package 设计原则：
1. 单一职责 —— 一个包只做一件事（UI、utils、config 分开）
2. 稳定 API —— 对外接口变化用版本号表达，避免破坏下游
3. 内部可私 —— 内部实现细节不暴露，只 export 公共接口
4. 幂等无副作用 —— 被多个项目 import 不应有全局副作用
```

```ts
// packages/utils/src/index.ts —— 共享包只导出公共 API
export { formatDate } from './formatDate';
export { debounce } from './debounce';
export { type Result, ok, err } from './result';

// 内部 helper 不导出，避免下游依赖实现细节
// import { padZero } from './formatDate' —— 不允许
```

## Internal Package

Internal Package（内部包）是「只在仓库内部使用、不发布到 npm」的包，通常根 `package.json` 标 `private: true`。内部包能享受 Workspace 的便利，同时避免被外部误依赖。

```text
Internal Package 与可发布包的区别：
            Internal Package     Publishable Package
private     必须 true            false
version     可固定 0.0.0         遵循 SemVer
发布        不发布               发布到 registry
用途        内部工具/配置/实验    对外交付的库/组件
```

```json
// packages/config/package.json —— 内部共享配置包
{
  "name": "@myorg/config",
  "version": "0.0.0",
  "private": true,
  "main": "eslint.config.js"
}
```

```text
常见 Internal Package 场景：
1. 共享 ESLint/TS/Prettier 配置 —— 所有包 extends 一份
2. 构建脚本、CLI 工具 —— 只在 CI 和本地使用
3. 实验性代码 —— 未稳定，暂不对外发布
```

## Dependency Graph

Dependency Graph（依赖图）描述各包之间的依赖关系，是 Monorepo 构建、缓存、变更分析的基础。用图表达后，可以回答「改了包 A 会影响哪些包」「构建某包前要先构建哪些包」。

```text
依赖图的三种依赖：
1. 包内依赖 —— 同一 workspace 内的包互相引用（@myorg/ui → @myorg/utils）
2. 外部依赖 —— 从 registry 安装的第三方包（react、lodash）
3. 开发依赖 —— 仅构建/测试用（typescript、vite）

依赖图必须是无环有向图（DAG），环会导致构建死锁。
```

```bash
# pnpm 查看依赖关系
pnpm list --depth 1

# Turborepo 可视化依赖图
npx turbo run build --graph
```

```text
依赖图的价值：
1. 拓扑排序 —— 决定构建顺序（先构建被依赖的包）
2. 变更影响分析 —— 改了 A 算出所有「依赖 A」的下游
3. 并行调度 —— 互不依赖的包可并行构建
4. 循环检测 —— 提前暴露「A 依赖 B、B 又依赖 A」的错误
```

## 应用场景实战

### 场景一：搭建一个前端 + 组件库 + 工具的 Monorepo

```bash
# 初始化
mkdir my-monorepo && cd my-monorepo
pnpm init

# pnpm-workspace.yaml
cat > pnpm-workspace.yaml <<'EOF'
packages:
  - "packages/*"
  - "apps/*"
EOF

# 创建共享工具包
mkdir -p packages/utils/src apps/web/src
```

```json
// packages/utils/package.json
{
  "name": "@myorg/utils",
  "version": "1.0.0",
  "main": "dist/index.js",
  "types": "dist/index.d.ts",
  "scripts": {
    "build": "tsc"
  }
}
```

```bash
# apps/web 引用共享包
cd apps/web
pnpm add @myorg/utils --workspace

# 根目录统一安装 + 构建
cd ../..
pnpm install
pnpm --filter @myorg/utils build
```

### 场景二：用依赖图做变更影响分析

```text
假设依赖关系：
apps/web → @myorg/ui → @myorg/utils
apps/admin → @myorg/ui

改了 @myorg/utils：
受影响 = @myorg/ui（直接依赖）→ apps/web、apps/admin（间接依赖）
需要重新构建/测试的包 = @myorg/utils、@myorg/ui、apps/web、apps/admin
```

```bash
# Turborepo 的 affected 命令自动完成上述分析
npx turbo run build --filter=...[@myorg/utils]

# 只构建受影响的下游
npx turbo run build --affected --filter=...@myorg/utils
```

## 最佳实践与踩坑记录

### 最佳实践

1. 根 `package.json` 设 `private: true`，避免误发整个仓库
2. 包名统一加 scope（`@myorg/*`），避免与第三方包冲突
3. 共享包遵守 SemVer，内部包可固定版本
4. 用 `pnpm --filter` 精确指定构建目标，不要全量构建
5. 依赖版本统一管理（锁文件 + 顶层声明），避免同库多版本漂移
6. 共享配置（eslint/tsconfig）做成 internal package，各包 extends 一份

### 踩坑记录

```text
坑 1：workspace 包互相引用时版本号不一致
结论：pnpm add @myorg/ui --workspace 安装的是 workspace:^ 协议。
原因：不声明 workspace 协议，会尝试从 registry 拉取而非本地链接。
解法：用 --workspace 或手动写 "workspace:^1.0.0"，别写纯 ^1.0.0。

坑 2：pnpm 幽灵依赖问题
结论：子包 import 了未在 package.json 声明的依赖却能用。
原因：依赖被提升到根 node_modules，产生「幽灵依赖」。
解法：pnpm 默认半严格，可在 .npmrc 设 shamefully-hoist=false，
     缺失依赖及时补到对应 package.json。

坑 3：依赖图出现环导致构建死锁
结论：A 依赖 B、B 依赖 A，拓扑排序失败。
原因：共享包设计不当，互相引用。
解法：抽出公共部分到第三个包（依赖倒置），或合并 A/B。

坑 4：pnpm install 后 import 报模块找不到
结论：workspace 目录没被识别，符号链接未建立。
原因：pnpm-workspace.yaml 的 packages 通配符没匹配到目标目录。
解法：检查通配符路径，确认子包目录下有 package.json。
```
