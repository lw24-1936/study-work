## 概述

性能指标是把「页面快不快、卡不卡」量化成可测量、可对比的数字。核心是 Google 的 Core Web Vitals（LCP、INP、CLS），它们直接影响搜索排名和用户体验。指标分「加载类」（TTFB/FCP/LCP）和「交互类」（INP/FID/TBT）与「视觉稳定类」（CLS）。

```text
性能指标的分类：
1. 加载类 —— 内容多久出现（TTFB、FCP、LCP、Speed Index）
2. 交互类 —— 响应是否及时（FID、INP、TBT、TTI）
3. 稳定性 —— 布局是否抖动（CLS）
```

```text
Core Web Vitals（核心指标）：
1. LCP —— 最大内容绘制，衡量加载速度（目标 ≤ 2.5s）
2. INP —— 交互到下次绘制，衡量响应速度（目标 ≤ 200ms）
3. CLS —— 累积布局偏移，衡量视觉稳定（目标 ≤ 0.1）
```

```js
// 用 web-vitals 库采集核心指标
import { onLCP, onINP, onCLS } from 'web-vitals';

onLCP((metric) => send('lcp', metric.value));
onINP((metric) => send('inp', metric.value));
onCLS((metric) => send('cls', metric.value));
```

## TTFB

TTFB（Time to First Byte，首字节时间）指从发起请求到收到响应第一个字节的时间，衡量服务端响应速度，包含 DNS、TCP、TLS 和服务器处理时间。

```text
TTFB 的组成：
1. 重定向时间 —— 若有 301/302
2. DNS 查询 —— 域名解析
3. TCP 连接 —— 三次握手
4. TLS 握手 —— HTTPS 协商
5. 服务器处理 —— 生成响应的耗时
```

```js
// 用 Navigation Timing API 计算 TTFB
const [nav] = performance.getEntriesByType('navigation');
const ttfb = nav.responseStart - nav.requestStart;
console.log('TTFB:', ttfb, 'ms');
```

```text
TTFB 优化方向：
1. 服务端缓存、CDN 边缘缓存（减少服务器处理时间）
2. 减少重定向链
3. 就近部署 / CDN（减少网络往返）
4. 预连接（DNS/TCP/TLS 提前建立）
```

## FCP

FCP（First Contentful Paint，首次内容绘制）指浏览器首次渲染出任何 DOM 内容（文本、图片、背景）的时间，是「页面开始有东西」的信号。

```js
// PerformanceObserver 监听 paint 事件
new PerformanceObserver((list) => {
  for (const entry of list.getEntriesByName('first-contentful-paint')) {
    console.log('FCP:', entry.startTime, 'ms');
  }
}).observe({ type: 'paint', buffered: true });
```

```text
FCP 的优化方向：
1. 内联关键 CSS，减少阻塞渲染的样式
2. 移除/延迟阻塞渲染的 JS
3. 压缩资源、加快传输
4. 服务端渲染 / 预渲染，让首屏有内容
```

## LCP

LCP（Largest Contentful Paint，最大内容绘制）指视口内最大可见元素（大图、大文本块）完成渲染的时间，是衡量「主要内容加载完成」的核心指标，目标 ≤ 2.5s。

```js
import { onLCP } from 'web-vitals';

onLCP((metric) => {
  console.log('LCP:', metric.value, '元素:', metric.entries[0]?.element);
});
```

```text
LCP 的四个阶段（需逐段优化）：
1. TTFB —— 服务器响应快
2. 资源加载延迟 —— 尽早发现并加载 LCP 资源
3. 资源下载时间 —— 压缩、CDN、缓存
4. 渲染延迟 —— 减少阻塞、避免长任务
```

```text
LCP 常见元素：
1. 首屏大图（hero image）
2. 大段文本 / 标题
3. 视频封面帧
```

```html
<!-- 让 LCP 图片尽快加载：preload + fetchpriority -->
<link rel="preload" as="image" href="hero.jpg" fetchpriority="high" />
<img src="hero.jpg" alt="hero" fetchpriority="high" />
```

## CLS

CLS（Cumulative Layout Shift，累积布局偏移）衡量页面加载过程中元素位置的意外移动，目标 ≤ 0.1。它反映「用户点错/看错」的风险。

```text
CLS 的计算：
CLS = 影响比例（影响视口面积） × 移动距离（相对视口）
整个加载期所有偏移累计求和（取最大会话窗口）
```

```js
import { onCLS } from 'web-vitals';

onCLS((metric) => {
  console.log('CLS:', metric.value);
});
```

```text
CLS 的常见来源与解法：
1. 图片/视频无尺寸 —— 显式设 width/height 或 aspect-ratio
2. 动态注入内容 —— 预留空间（skeleton）
3. 字体加载 —— font-display: swap + 字体度量匹配
4. 广告/iframe —— 预留固定容器尺寸
```

```css
/* 给图片预留空间，防止加载后撑开布局 */
img {
  width: 100%;
  height: auto;
  aspect-ratio: 16 / 9;
}

/* 字体加载期间用系统字体兜底，减少偏移 */
@font-face {
  font-family: 'MyFont';
  src: url('myfont.woff2') format('woff2');
  font-display: swap;
}
```

## INP

INP（Interaction to Next Paint，交互到下次绘制）是 2024 年取代 FID 的新核心指标，衡量用户交互（点击、按键）到界面视觉反馈的时间，目标 ≤ 200ms。它取页面整个生命周期中最差交互（高百分位）。

```text
INP 的三段：
1. Input delay —— 主线程忙，事件无法及时处理
2. Processing time —— 事件处理器本身的耗时
3. Presentation delay —— 浏览器绘制反馈的耗时
```

```js
import { onINP } from 'web-vitals';

onINP((metric) => {
  console.log('INP:', metric.value, '最差交互');
});
```

```text
INP 优化方向：
1. 减少长任务，让主线程尽快响应事件
2. 事件处理逻辑轻量化、拆分
3. 避免同步阻塞（大循环、布局抖动）
```

## TTI

TTI（Time to Interactive，可交互时间）指页面达到「可稳定响应交互」的时间，要求主线程在 5 秒内无长任务（>50ms）且网络安静。它是衡量「何时能真正使用页面」的指标。

```text
TTI 的判定条件：
1. 页面已有内容（FCP 之后）
2. 无超过 50ms 的长任务
3. 无超过 2 个并发网络请求
```

```js
// 用 Lighthouse 或 Performance 面板测量 TTI
// 无法直接用简单 API 获取，需 Lighthouse / 自定义长任务监测
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 50) console.log('长任务:', entry.duration, 'ms');
  }
}).observe({ type: 'longtask', buffered: true });
```

```text
TTI 优化方向：
1. 减少/拆分长任务（代码分割、懒加载）
2. 延迟非关键脚本
3. 降低主线程工作总量
```

## TBT

TBT（Total Blocking Time，总阻塞时间）衡量 FCP 到 TTI 之间主线程被长任务阻塞的总时长，即所有长任务超过 50ms 的部分之和。它直接反映主线程拥堵程度，是 INP 的实验室（Lighthouse）对应指标。

```text
TBT 的计算：
TBT = Σ (每个长任务时长 - 50ms)
例：一个 250ms 长任务，贡献 200ms TBT
```

```js
// 观察长任务，累计 TBT
let tbt = 0;
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    tbt += Math.max(0, entry.duration - 50);
  }
}).observe({ type: 'longtask', buffered: true });
```

```text
TBT 优化方向：
1. 代码分割 + 懒加载，减少首屏 JS 量
2. 用 Web Worker 移出主线程计算
3. 避免大量同步 DOM 操作
```

## FID

FID（First Input Delay，首次输入延迟）衡量用户首次交互（点击/按键）到浏览器能响应事件的时间，目标 ≤ 100ms。它已被 INP 取代，但仍常见于历史报告。

```text
FID 与 INP 的区别：
1. FID —— 只看「首次」交互，只测输入延迟
2. INP —— 看「所有」交互，测完整响应（输入+处理+绘制）
3. INP 更全面，已取代 FID 成为核心指标
```

```js
// 监听首次输入
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('FID:', entry.processingStart - entry.startTime, 'ms');
  }
}).observe({ type: 'first-input', buffered: true });
```

## Speed Index

Speed Index（速度指数）衡量页面内容「视觉上」多快被填充完成，计算的是可见区域内容随时间变化的累计面积，值越小越好。它由 Lighthouse/WebPageTest 计算。

```text
Speed Index 的含义：
1. 越小越好 —— 内容越快填满视口
2. 与 LCP 互补 —— LCP 看「最大元素」，SI 看「整体填充进度」
3. 依赖视频录制/帧对比，非浏览器原生 API
```

```text
Speed Index 优化方向：
1. 首屏内容优先渲染，减少空白
2. 图片懒加载（但首屏图要优先）
3. 骨架屏/占位，视觉上先有内容
4. 关键 CSS 内联，首屏尽快成型
```

## 应用场景实战

### 场景一：构建性能监控上报

```js
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals';

function report(name, value) {
  navigator.sendBeacon('/api/metrics', JSON.stringify({ name, value, url: location.href }));
}

onTTFB((m) => report('ttfb', m.value));
onFCP((m) => report('fcp', m.value));
onLCP((m) => report('lcp', m.value));
onINP((m) => report('inp', m.value));
onCLS((m) => report('cls', m.value));
```

### 场景二：诊断 LCP 慢的原因

```js
// 找出 LCP 元素并分析其加载链
import { onLCP } from 'web-vitals';

onLCP((metric) => {
  const el = metric.entries[0]?.element;
  if (el?.tagName === 'IMG') {
    const img = el;
    // 图片 LCP 慢的常见原因：发现晚、下载慢
    console.log({
      src: img.src,
      loading: img.loading,
      fetchpriority: img.fetchPriority,
      size: img.getBoundingClientRect(),
    });
  }
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优先盯 Core Web Vitals（LCP、INP、CLS），再关注 TTFB/FCP 等辅助指标
2. 指标要分「实验室数据」（Lighthouse）和「真实用户数据」（RUM），两者结合
3. 上报用 navigator.sendBeacon，不阻塞页面卸载
4. 指标看分位数（P75/P95），不看平均值（会被极端值稀释）
5. 设置性能预算，CI 里对关键指标卡阈值
6. 分析指标时结合瀑布图和长任务，定位瓶颈阶段

### 踩坑记录

```text
坑 1：只看平均值
结论：指标看着达标，实际部分用户很慢。
原因：平均值被快用户稀释，掩盖慢用户。
解法：看 P75/P95 分位数，关注长尾。

坑 2：CLS 用 window.onload 后采样不完整
结论：漏掉懒加载、动态内容引起的偏移。
原因：CLS 要持续观察整个生命周期。
解法：用 web-vitals 库持续监听，直到页面隐藏。

坑 3：混淆 LCP 和 FCP
结论：优化错了对象，首屏依旧慢。
原因：FCP 只是「有内容」，LCP 才是「主要内容」。
解法：先优化 LCP 元素（通常是首屏大图/大标题）。

坑 4：忽略 INP 只看 FID
结论：交互响应差但 FID 达标。
原因：FID 只看首次输入，覆盖不了后续卡顿。
解法：改用 INP，关注所有交互的最差表现。

坑 5：实验室数据好但真实用户差
结论：Lighthouse 满分，线上却卡。
原因：实验室环境 CPU/网络好，不代表真实设备。
解法：接入 RUM 采集真实用户指标，结合设备/网络维度分析。
```
