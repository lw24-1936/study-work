## 概述

网络性能优化围绕「减少请求、减少体积、减少往返」展开。一次请求要经过 DNS 解析、TCP 连接、TLS 握手、数据传输多个阶段，每个阶段都有可优化的空间。传输层（HTTP/2、HTTP/3）、分发层（CDN）、压缩层（Gzip/Brotli）三管齐下，能显著缩短加载时间。

```text
网络请求的完整链路：
DNS 解析 → TCP 连接（三次握手）→ TLS 握手 → HTTP 请求 → 响应传输
每一段都是可优化点
```

```text
网络优化的三个方向：
1. 减少往返 —— DNS 预解析、连接复用、协议升级
2. 减少体积 —— Gzip/Brotli 压缩、精简资源
3. 拉近距离 —— CDN 边缘节点就近响应
```

## DNS 优化

DNS 把域名解析成 IP，是请求的第一跳。解析慢会直接拖慢 TTFB。优化手段包括减少查询次数、提前解析、使用快 DNS。

```text
DNS 查询的耗时来源：
1. 多级递归查询（根域 → 顶级域 → 权威域）
2. 域名层级深、CNAME 链长
3. 用户 DNS 服务器慢
```

```html
<!-- DNS Prefetch：提前解析即将用到的域名 -->
<link rel="dns-prefetch" href="//api.example.com" />
<link rel="dns-prefetch" href="//cdn.example.com" />
```

```text
DNS 优化手段：
1. dns-prefetch 提前解析第三方域名
2. 减少域名数量，减少解析次数
3. 使用权威 DNS 服务商（低延迟）
4. 服务端设置合理的 TTL，让缓存更久
```

## TCP 优化

TCP 建立连接需要三次握手，每个新连接都有固定往返开销。优化核心是「复用连接、减少握手、加大吞吐」。

```text
TCP 的开销：
1. 三次握手 —— 1.5 个 RTT 才能发数据
2. 慢启动 —— 初始拥塞窗口小，传输逐步提速
3. 连接数限制 —— 浏览器对同域并发连接有限制（HTTP/1.1 约 6 个）
```

```text
TCP 优化手段：
1. 连接复用 —— keep-alive 保持连接，避免重复握手
2. 减少域名数量 —— 复用同一连接
3. HTTP/2 多路复用 —— 一个连接承载所有请求
4. 升级拥塞控制算法（如 BBR），提升吞吐
```

```js
// 服务端设置 keep-alive（Node.js）
const server = require('http').createServer(handler);
server.keepAliveTimeout = 65_000; // 保持连接 65s
server.headersTimeout = 66_000;
```

## TLS 优化

HTTPS 的 TLS 握手在 TCP 之上还要额外 1-2 个 RTT（TLS 1.2 两次、TLS 1.3 一次），是 HTTPS 比 HTTP 慢的主要原因。优化方向是减少往返和复用会话。

```text
TLS 握手的 RTT：
1. TLS 1.2 —— 需 2 个 RTT
2. TLS 1.3 —— 需 1 个 RTT（合并握手）
3. Session Resumption —— 复用会话，0 额外 RTT（0-RTT）
```

```text
TLS 优化手段：
1. 升级 TLS 1.3，减少握手往返
2. 启用会话复用（Session ID / Session Ticket）
3. 启用 OCSP Stapling，减少证书校验往返
4. 配合 HTTP/2/3（协议与 TLS 绑定升级）
```

## HTTP/2

HTTP/2 解决 HTTP/1.1 的队头阻塞和连接数限制，用「二进制分帧 + 多路复用 + 头部压缩 + 服务器推送」大幅提升传输效率。

```text
HTTP/2 的核心特性：
1. 多路复用 —— 一个 TCP 连接并发传输多个请求/响应
2. 头部压缩 —— HPACK 算法压缩重复请求头
3. 二进制分帧 —— 请求/响应拆成帧，可乱序传输
4. 服务器推送 —— 服务端主动推送资源（已逐渐弃用）
```

```text
HTTP/2 的收益：
1. 消除「6 连接限制」，请求不再排队
2. 去掉域名分片（domain sharding）的必要
3. 头部压缩减少重复传输
```

```text
HTTP/2 注意事项：
1. 需要 HTTPS（浏览器强制要求）
2. 多域名反而破坏多路复用，应减少域名
3. 资源合并（雪碧图、拼接）不再必要
```

## HTTP/3

HTTP/3 基于 QUIC（UDP 之上），彻底解决 TCP 层的队头阻塞问题，并支持 0-RTT 连接建立、连接迁移，在弱网/移动场景优势明显。

```text
HTTP/3 相对 HTTP/2 的改进：
1. 基于 QUIC —— 单个流丢包不影响其他流（解决队头阻塞）
2. 0-RTT —— 已连接过的客户端可立即发数据
3. 连接迁移 —— 切换网络（WiFi → 4G）连接不断
4. TLS 1.3 内置 —— 握手更快
```

```text
HTTP/3 的现状：
1. 主流浏览器/CDN 已支持，部署门槛降低
2. 需服务端支持 QUIC（Nginx 1.25+ / Caddy）
3. 适合弱网、移动端、视频等场景
```

## CDN

CDN（内容分发网络）把资源缓存到离用户最近的边缘节点，用户从就近节点取数据，减少传输距离和源站压力。静态资源（JS/CSS/图片/字体）都该走 CDN。

```text
CDN 的价值：
1. 就近响应 —— 降低 RTT，加快 TTFB 和资源下载
2. 缓存卸载 —— 静态资源命中边缘缓存，减轻源站压力
3. 高可用 —— 源站故障时边缘仍可服务缓存内容
```

```html
<!-- 静态资源使用 CDN 域名 -->
<script src="https://cdn.example.com/js/app.js"></script>
<link rel="stylesheet" href="https://cdn.example.com/css/app.css" />
```

```text
CDN 使用要点：
1. 静态资源设长缓存 + 内容指纹（hash）文件名
2. 开启 HTTP/2/3、Brotli、TLS 1.3
3. 正确配置缓存 TTL 与刷新/预热策略
4. 回源要稳定，配置好源站
```

## Compression

压缩是「减少传输体积」最直接的手段：服务端对文本类资源（HTML/CSS/JS/JSON/SVG）压缩后再传输，浏览器解压使用。可减少 60%-80% 的体积。

```text
压缩的适用对象：
1. 文本类 —— HTML、CSS、JS、JSON、SVG、字体（部分）
2. 不适合 —— 已压缩的图片/视频/zip（再压无收益还费 CPU）
```

```text
启用压缩的步骤：
1. 服务端配置压缩算法与阈值
2. 浏览器请求带 Accept-Encoding 头声明支持
3. 服务端按协商选算法压缩，响应带 Content-Encoding
```

```js
// Node.js 用 compression 中间件
const compression = require('compression');
const express = require('express');
const app = express();

app.use(compression({ threshold: 1024 })); // 超过 1KB 才压缩
app.use(express.static('public'));
app.listen(3000);
```

## Brotli

Brotli 是 Google 开发的压缩算法，比 Gzip 压缩率更高（同体积下通常小 15%-20%），现代浏览器全部支持，已成为静态资源压缩的首选。

```text
Brotli vs Gzip：
1. Brotli —— 压缩率更高，但压缩耗时略长
2. Gzip —— 速度快，兼容性最广
3. 最佳实践 —— 静态资源预压缩 Brotli，动态内容按需
```

```text
Brotli 的适用场景：
1. 静态资源（JS/CSS/HTML）预压缩，一次压缩多次用
2. 高压缩等级（9-11）适合可预压缩的静态文件
3. 动态响应用低等级（4-5）平衡 CPU 与体积
```

```js
// 用 zlib 预压缩 Brotli（Node.js）
const { brotliCompressSync } = require('zlib');
const fs = require('fs');

const js = fs.readFileSync('app.js');
fs.writeFileSync('app.js.br', brotliCompressSync(js, { params: { [require('zlib').constants.BROTLI_PARAM_QUALITY]: 11 } }));
```

```text
响应头示例：
Content-Encoding: br
```

## Gzip

Gzip 是历史最久、兼容性最好的压缩算法，几乎所有服务器和客户端都支持。压缩速度快，适合动态内容和兼容性要求高的场景。

```text
Gzip 的特点：
1. 兼容性最好 —— 所有浏览器/服务器支持
2. 压缩速度快 —— 适合实时压缩动态内容
3. 压缩率略低于 Brotli
```

```js
// 用 zlib 实时 Gzip 压缩响应
const zlib = require('zlib');
const http = require('http');

http.createServer((req, res) => {
  if (req.headers['accept-encoding']?.includes('gzip')) {
    res.setHeader('Content-Encoding', 'gzip');
    res.setHeader('Content-Type', 'text/plain');
    const gzip = zlib.createGzip();
    gzip.pipe(res);
    gzip.end('hello '.repeat(1000));
  } else {
    res.end('hello '.repeat(1000));
  }
}).listen(3000);
```

```text
Gzip 与 Brotli 的取舍：
1. 双算法都开 —— 按 Accept-Encoding 协商（br 优先）
2. 静态资源预压 br + 动态内容 gzip
3. 小文件（<1KB）别压，省 CPU 收益小
```

## Resource Hint

Resource Hint（资源提示）是给浏览器的「预告」，让它提前做 DNS 解析、建连接、预加载资源，缩短关键路径。包含 dns-prefetch、preconnect、preload、prefetch。

```html
<!-- dns-prefetch：只提前解析 DNS -->
<link rel="dns-prefetch" href="//api.example.com" />

<!-- preconnect：提前 DNS + TCP + TLS 完整连接 -->
<link rel="preconnect" href="//api.example.com" crossorigin />

<!-- preload：提前下载当前页面确定要用的资源 -->
<link rel="preload" as="script" href="/js/critical.js" />

<!-- prefetch：提前下载「下一个页面」可能用到的资源 -->
<link rel="prefetch" as="document" href="/next-page.html" />
```

```text
Resource Hint 的选择：
1. dns-prefetch —— 一定会用但只用一次的第三方域
2. preconnect —— 确定会发起请求的域（API、CDN）
3. preload —— 当前页面关键资源（LCP 图片、关键 CSS）
4. prefetch —— 预判用户下一步会访问的资源
```

```text
Resource Hint 的坑：
1. 过度 preconnect 浪费连接，只对关键域用
2. preload 不匹配的资源会被浏览器警告
3. preload 优先级高于 async，别滥用抢占带宽
```

## 应用场景实战

### 场景一：首屏关键路径优化

```html
<!DOCTYPE html>
<html>
<head>
  <!-- 1. 提前连接 API 和 CDN -->
  <link rel="preconnect" href="https://api.example.com" crossorigin />
  <link rel="preconnect" href="https://cdn.example.com" />

  <!-- 2. 预加载 LCP 图片和关键 CSS -->
  <link rel="preload" as="image" href="https://cdn.example.com/hero.jpg" fetchpriority="high" />
  <link rel="preload" as="style" href="https://cdn.example.com/css/critical.css" />

  <!-- 3. 内联关键 CSS 消除渲染阻塞 -->
  <style>/* 首屏关键样式 */</style>
</head>
<body>
  <img src="https://cdn.example.com/hero.jpg" alt="hero" fetchpriority="high" />
  <script src="https://cdn.example.com/js/app.js" defer></script>
</body>
</html>
```

### 场景二：配置服务端压缩与协议

```js
const express = require('express');
const compression = require('compression');
const app = express();

// Brotli + Gzip 双压缩，按 Accept-Encoding 协商
app.use(compression({
  threshold: 1024,
  level: 6,
}));

// 静态资源长缓存 + 内容指纹
app.use('/static', express.static('public', {
  maxAge: '365d',
  immutable: true,
  setHeaders: (res) => res.setHeader('Cache-Control', 'public, max-age=31536000, immutable'),
}));

app.listen(3000);
```

```text
部署层（Nginx）也要同步配置：
1. 开启 HTTP/2 或 HTTP/3
2. 启用 Brotli + Gzip
3. 配置 TLS 1.3 + 会话复用
```

## 最佳实践与踩坑记录

### 最佳实践

1. 静态资源上 CDN + 内容指纹 + 长缓存
2. 文本资源启用 Brotli（优先）+ Gzip（兜底）
3. 升级 HTTPS 到 TLS 1.3 + HTTP/2（或 HTTP/3）
4. 减少域名数量，让多路复用发挥最大价值
5. 关键第三方域用 preconnect，LCP 资源用 preload
6. 图片/视频等二进制资源不要再压缩，直接靠 CDN + 缓存

### 踩坑记录

```text
坑 1：对已压缩资源再做 Gzip
结论：图片/视频再压缩体积不降反增，浪费 CPU。
原因：JPEG/PNG/MP4 本身已是压缩格式。
解法：只压缩文本类资源（HTML/CSS/JS/JSON/SVG）。

坑 2：多域名反而更慢
结论：切了 HTTP/2 后保留域名分片，性能下降。
原因：HTTP/2 多路复用，一个连接更优，多域名破坏复用。
解法：减少域名，让同域请求走同一连接。

坑 3：preload 滥用抢占关键带宽
结论：preload 一堆非关键资源，阻塞真正关键资源。
原因：preload 优先级高，会抢占带宽。
解法：只 preload 首屏关键资源，其余用 prefetch。

坑 4：preconnect 到每个第三方域
结论：建立大量空闲连接，浪费资源。
原因：preconnect 有成本（DNS+TCP+TLS）。
解法：只对确定会发起请求的关键域 preconnect。

坑 5：压缩级别过高拖慢服务器
结论：动态响应压缩 CPU 占用飙升，响应反而慢。
原因：Brotli 高等级压缩耗 CPU。
解法：动态内容用低等级，静态内容预压缩高等级。
```
