## 概述

大文件（几百 MB 到几 GB）不能像小文件一样一次性上传，需要分片处理：把文件切成小块（Chunk Upload），逐片上传，失败可从断点续传（Resume Upload），还可多片并发（Parallel Upload）。整个方案依赖文件 Hash（MD5/SHA）做唯一标识，实现秒传与完整性校验。

```text
大文件上传的关键机制：
1. Chunk Upload —— 把大文件切成固定大小的片，逐片上传
2. Resume Upload —— 记录已传分片，失败后从断点继续
3. Parallel Upload —— 多片并发上传，提高吞吐
4. Hash —— 计算文件指纹，标识文件身份
5. MD5 / SHA —— 两种哈希算法，用于秒传和校验
6. Multipart Upload —— 服务端分片上传协议（对象存储）
```

```js
// 分片的核心：用 Blob.slice 切文件
function chunkFile(file, chunkSize = 5 * 1024 * 1024) { // 5MB 一片
  const chunks = [];
  let offset = 0;
  while (offset < file.size) {
    chunks.push(file.slice(offset, offset + chunkSize));
    offset += chunkSize;
  }
  return chunks;
}
```

## Chunk Upload

Chunk Upload（分片上传）把大文件按固定大小（通常 5MB）切成多个 Blob 片，逐片（或并发）上传。好处：单片小、失败只重传失败片、可显示精细进度、可断点续传。

```js
// 逐片上传，每片带序号，服务端按序合并
async function uploadChunks(file, chunkSize = 5 * 1024 * 1024) {
  const total = Math.ceil(file.size / chunkSize);
  for (let i = 0; i < total; i++) {
    const chunk = file.slice(i * chunkSize, (i + 1) * chunkSize);
    const fd = new FormData();
    fd.append('chunk', chunk);
    fd.append('index', i);
    fd.append('total', total);
    fd.append('filename', file.name);
    await fetch('/api/upload-chunk', { method: 'POST', body: fd });
    onProgress((i + 1) / total);
  }
  // 全部传完，通知服务端合并
  await fetch('/api/merge', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ filename: file.name, total }),
  });
}
```

```text
Chunk Upload 的要点：
1. 切片 —— 固定大小（5MB 常见），用 slice
2. 序号 —— 每片带 index/total，服务端按序合并
3. 进度 —— 按片数算百分比，比单文件精细
4. 重传粒度 —— 失败只重传某片，不用整个重来
```

## Resume Upload

Resume Upload（断点续传）在分片基础上增加「已传进度记录」：上传前先问服务端「哪些片已经传了」，只传缺失的片。网络中断、刷新页面后都能接着传，不用从头开始。

```js
// 断点续传：先查已传分片，只补传缺失的
async function resumeUpload(file) {
  const total = Math.ceil(file.size / CHUNK_SIZE);
  // 1. 查询服务端已收到的分片序号
  const uploaded = await fetch(`/api/uploaded?filename=${file.name}`)
    .then(r => r.json());  // [0, 1, 2, ...]

  // 2. 只传缺失的片
  for (let i = 0; i < total; i++) {
    if (uploaded.includes(i)) continue;  // 已传则跳过
    const chunk = file.slice(i * CHUNK_SIZE, (i + 1) * CHUNK_SIZE);
    const fd = new FormData();
    fd.append('chunk', chunk);
    fd.append('index', i);
    fd.append('filename', file.name);
    await fetch('/api/upload-chunk', { method: 'POST', body: fd });
  }
  // 3. 合并
  await fetch(`/api/merge?filename=${file.name}`, { method: 'POST' });
}
```

```text
Resume Upload 的要点：
1. 进度查询 —— 先问服务端已收哪些片
2. 只补缺失 —— 跳过已传分片，节省流量
3. 标识文件 —— 用 filename + hash 定位同一文件的上传进度
4. 断点触发 —— 网络恢复、页面刷新后自动续传
```

## Parallel Upload

Parallel Upload（并发分片上传）同时上传多个分片，用 Promise 池控制并发数（如同时 3-5 片）。相比逐片串行，能充分利用带宽，大幅缩短上传时间，但要控制并发避免打满连接。

```js
// 并发池：最多同时 3 片
async function parallelUpload(file, concurrency = 3) {
  const chunks = chunkFile(file);
  const pool = new Set();
  let i = 0;

  async function uploadOne(chunk, index) {
    const fd = new FormData();
    fd.append('chunk', chunk);
    fd.append('index', index);
    await fetch('/api/upload-chunk', { method: 'POST', body: fd });
  }

  while (i < chunks.length) {
    while (pool.size < concurrency && i < chunks.length) {
      const index = i++;
      const p = uploadOne(chunks[index], index)
        .finally(() => pool.delete(p));
      pool.add(p);
    }
    await Promise.race(pool);   // 等任一完成，腾出位置
  }
  await Promise.all(pool);      // 等剩余的完成
  await fetch('/api/merge', { method: 'POST' });
}
```

```text
Parallel Upload 的要点：
1. 并发池 —— 控制同时上传的片数
2. 吞吐提升 —— 充分利用带宽，缩短总时长
3. 别打满 —— 并发过高会触发服务端限流或浏览器连接上限
4. 失败重试 —— 单片失败可重试，不影响其他片
```

## Hash

Hash（哈希）在文件上传里有两个用途：一是「秒传」（服务端已有相同哈希的文件就跳过上传），二是「完整性校验」（上传后比对哈希确认没传错）。大文件哈希计算耗时，需异步化或用 Web Worker。

```js
// 用 Web Crypto 计算文件哈希（SHA-256）
async function fileHash(file) {
  const buffer = await file.arrayBuffer();
  const hashBuffer = await crypto.subtle.digest('SHA-256', buffer);
  const hashArray = Array.from(new Uint8Array(hashBuffer));
  return hashArray.map(b => b.toString(16).padStart(2, '0')).join('');
}

// 大文件应分块读，避免一次性 arrayBuffer 撑爆内存
async function fileHashChunked(file) {
  const chunkSize = 10 * 1024 * 1024;
  const hashArray = [];
  for (let offset = 0; offset < file.size; offset += chunkSize) {
    const chunk = await file.slice(offset, offset + chunkSize).arrayBuffer();
    hashArray.push(await crypto.subtle.digest('SHA-256', chunk));
  }
  // 简化示意：实际应增量合并，或用第三方库
  return hashArray.length;
}
```

```text
Hash 的要点：
1. 秒传 —— 服务端存过同哈希文件，直接返回成功
2. 校验 —— 上传后比对，确保完整无损
3. 大文件分块 —— 别一次性读入整个文件
4. 异步化 —— 哈希计算放 Web Worker，不阻塞主线程
```

## MD5

MD5 是常见的哈希算法，输出 128 位（32 个十六进制字符），曾广泛用于文件指纹。它已被证明有碰撞漏洞，不适合安全场景，但用于文件秒传/去重（非安全用途）仍常见。

```js
// MD5 计算常用第三方库（spark-md5），支持分块增量
// import SparkMD5 from 'spark-md5';
function md5Chunked(file) {
  return new Promise((resolve) => {
    const spark = new SparkMD5.ArrayBuffer();
    const chunkSize = 10 * 1024 * 1024;
    let offset = 0;
    const reader = new FileReader();

    reader.onload = (e) => {
      spark.append(e.target.result);        // 增量追加
      offset += chunkSize;
      if (offset < file.size) {
        readNext();
      } else {
        resolve(spark.end());               // 得到 32 位 hex
      }
    };
    function readNext() {
      reader.readAsArrayBuffer(file.slice(offset, offset + chunkSize));
    }
    readNext();
  });
}
```

```text
MD5 的要点：
1. 128 位 —— 32 个 hex 字符
2. 碰撞漏洞 —— 不安全，别用于密码/签名
3. 秒传可用 —— 文件去重、秒传场景够用
4. 增量计算 —— spark-md5 支持分块 append
```

## SHA

SHA（Secure Hash Algorithm）是一族更安全的哈希算法，SHA-256 输出 256 位（64 个 hex 字符），是当前主流。Web Crypto API 原生支持 SHA-256/384/512，无需第三方库，用于完整性校验和秒传更可靠。

```js
// Web Crypto 原生计算 SHA-256（分块示例）
async function sha256Chunked(file) {
  const chunkSize = 10 * 1024 * 1024;
  // Web Crypto 的 digest 不支持增量，分块需拼接（示意）
  // 实际生产用流式库（如 hash-wasm）或 Web Worker 全量算
  const buffer = await file.arrayBuffer();  // 小文件可直接全量
  const hash = await crypto.subtle.digest('SHA-256', buffer);
  return Array.from(new Uint8Array(hash))
    .map(b => b.toString(16).padStart(2, '0')).join('');
}
```

```text
SHA 的要点：
1. SHA-256 —— 64 个 hex 字符，主流安全哈希
2. Web Crypto 原生 —— 无需第三方库
3. 更安全 —— 相比 MD5 碰撞风险极低
4. 场景 —— 完整性校验、秒传、签名
```

## Multipart Upload

Multipart Upload 是对象存储（AWS S3、阿里云 OSS 等）提供的分片上传协议：先发起初始化拿到 uploadId，再分片上传（每片返回 ETag），最后完成合并。前端按协议分片、并发上传，服务端/存储端负责组装。

```js
// 对象存储 Multipart Upload 的三步协议
// 1. 初始化，拿到 uploadId
const init = await fetch('/api/multipart/init', {
  method: 'POST',
  body: JSON.stringify({ filename: file.name }),
}).then(r => r.json());  // { uploadId }

// 2. 分片上传，每片返回 ETag
const parts = [];
const chunks = chunkFile(file);
for (let i = 0; i < chunks.length; i++) {
  const res = await fetch(`/api/multipart/part?uploadId=${init.uploadId}&partNumber=${i + 1}`, {
    method: 'PUT',
    body: chunks[i],
  });
  parts.push({ PartNumber: i + 1, ETag: res.headers.get('ETag') });
}

// 3. 完成合并，提交所有 part
await fetch('/api/multipart/complete', {
  method: 'POST',
  body: JSON.stringify({ uploadId: init.uploadId, parts }),
});
```

```text
Multipart Upload 的要点：
1. 三步协议 —— init / upload part / complete
2. uploadId —— 一次上传会话的标识
3. ETag —— 每片的校验值，合并时提交
4. 并发友好 —— 各片独立上传，天然支持并发
```

## 应用场景实战

### 场景一：带秒传 + 断点续传的完整上传

```js
// 完整流程：算哈希 -> 秒传判断 -> 分片续传 -> 合并
async function uploadLargeFile(file) {
  // 1. 算哈希（可放 Web Worker）
  const hash = await md5Chunked(file);

  // 2. 秒传：服务端已有此文件，直接成功
  const exists = await fetch(`/api/check?hash=${hash}`).then(r => r.json());
  if (exists.uploaded) return { fastUpload: true };

  // 3. 断点续传：查已传分片，补传缺失
  const uploaded = await fetch(`/api/uploaded?hash=${hash}`).then(r => r.json());
  const chunks = chunkFile(file);
  for (let i = 0; i < chunks.length; i++) {
    if (uploaded.includes(i)) continue;
    const fd = new FormData();
    fd.append('chunk', chunks[i]);
    fd.append('index', i);
    fd.append('hash', hash);
    await fetch('/api/upload-chunk', { method: 'POST', body: fd });
  }

  // 4. 合并
  return fetch('/api/merge', {
    method: 'POST',
    body: JSON.stringify({ hash, filename: file.name, total: chunks.length }),
  });
}
```

### 场景二：Web Worker 计算哈希不卡主线程

```js
// worker.js
self.onmessage = async (e) => {
  const file = e.data;
  const buffer = await file.arrayBuffer();
  const hash = await crypto.subtle.digest('SHA-256', buffer);
  const hex = Array.from(new Uint8Array(hash))
    .map(b => b.toString(16).padStart(2, '0')).join('');
  self.postMessage(hex);
};

// 主线程
const worker = new Worker('worker.js');
worker.onmessage = (e) => console.log('文件哈希:', e.data);
worker.postMessage(file);   // 大文件哈希计算不阻塞 UI
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分片大小选 5MB 左右，太小请求多、太大重传代价高
2. 秒传先算哈希查服务端，命中直接跳过上传
3. 哈希计算放 Web Worker，别在主线程算大文件
4. 并发分片控制 3-5 路，别打满连接触发限流
5. 每片上传带 hash + index，服务端按 hash 分组、按 index 合并
6. 完整性校验：合并后比对服务端与客户端哈希

### 踩坑记录

```text
坑 1：一次性 arrayBuffer 读整个大文件
结论：上传 2GB 文件直接内存溢出、页面崩溃。
原因：把整个文件读进内存再哈希/上传。
解法：分片读（slice + FileReader），哈希也分块增量算。

坑 2：主线程算 MD5 导致卡顿
结论：选大文件后页面卡住几秒到几十秒。
原因：MD5 计算是 CPU 密集操作，放主线程阻塞 UI。
解法：哈希计算放 Web Worker。

坑 3：并发分片太多触发限流
结论：上传中途大量 429/失败，反而更慢。
原因：并发过高打满服务端连接或触发限流。
解法：用并发池控制 3-5 路，失败重试带退避。

坑 4：断点续传没按 hash 定位文件
结论：同名不同内容的文件续传错乱。
原因：只用 filename 标识进度，重名文件互相串。
解法：用 filename + hash 共同定位上传会话。

坑 5：合并时没校验完整性
结论：上传完成但文件损坏，秒传/续传引入错误。
原因：分片传输可能有丢片/错序，直接合并未校验。
解法：合并后比对服务端哈希与客户端哈希，不一致重传。
```
