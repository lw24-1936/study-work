## 概述

缓存策略是 Service Worker 在 fetch 事件中「如何取舍缓存与网络」的决策逻辑。不同资源适合不同策略，选对策略才能兼顾性能、新鲜度和离线能力。

```text
五种核心策略：
1. Cache First —— 先查缓存，未命中再走网络
2. Network First —— 先请求网络，失败回退缓存
3. Stale While Revalidate —— 先返回缓存，后台更新
4. Network Only —— 只用网络，不查缓存
5. Cache Only —— 只用缓存，不走网络
```

```text
选型原则：
静态不变资源 → Cache First
需新鲜但可容错 → Network First
可接受短暂旧数据 → Stale While Revalidate
必须实时 → Network Only
离线兜底 → Cache Only
```

## Cache First

Cache First（缓存优先）先查缓存，命中直接返回，未命中再请求网络并写入缓存。适合内容稳定、不易变化的资源。

```js
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      if (cached) return cached;
      return fetch(event.request).then((response) => {
        const clone = response.clone();
        caches.open('v1').then((cache) => cache.put(event.request, clone));
        return response;
      });
    })
  );
});
```

```text
适用场景：
1. 带内容 hash 的 JS/CSS/字体（内容不变）
2. 应用壳（app shell）
3. 图标、logo 等静态图片

优点：最快，离线友好
缺点：内容更新不及时，需配合缓存版本管理
```

```text
关键细节：
response 只能消费一次，写入缓存前要 response.clone()，
否则返回给页面的响应体已被读取，导致报错。
```

## Network First

Network First（网络优先）先请求网络，成功就用网络结果（并更新缓存），失败则回退到缓存。适合需要新鲜、但允许离线兜底的资源。

```js
self.addEventListener('fetch', (event) => {
  event.respondWith(
    fetch(event.request)
      .then((response) => {
        const clone = response.clone();
        caches.open('v1').then((cache) => cache.put(event.request, clone));
        return response;
      })
      .catch(() => caches.match(event.request))
  );
});
```

```text
适用场景：
1. 需要及时更新的内容（新闻、动态数据）
2. 接口数据（可接受离线时返回旧缓存）
3. 页面导航（网络失败回退到离线页）

优点：内容最新，失败可降级
缺点：网络慢时等待久，且网络失败才用缓存
```

```js
// 页面导航的网络优先 + 离线兜底
self.addEventListener('fetch', (event) => {
  if (event.request.mode === 'navigate') {
    event.respondWith(
      fetch(event.request).catch(() => caches.match('/offline.html'))
    );
  }
});
```

## Stale While Revalidate

Stale While Revalidate（先缓存后更新）立即返回缓存内容（无论是否过期），同时后台发起网络请求更新缓存。下次访问就能拿到新内容。

```js
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      const networkFetch = fetch(event.request).then((response) => {
        caches.open('v1').then((cache) => cache.put(event.request, response.clone()));
        return response;
      });
      return cached || networkFetch;   // 有缓存立即返回，同时后台更新
    })
  );
});
```

```text
适用场景：
1. 头像、封面图等「可接受旧图」的资源
2. 商品列表等更新不频繁的数据
3. 追求秒开体验的页面

优点：响应最快，又能保持内容更新
缺点：用户可能短暂看到旧内容
```

```text
与 Cache First 的区别：
Cache First → 命中缓存就绝不请求网络（更新要等版本变更）
SWR → 每次都会后台请求更新，缓存只是「先给用户看」的兜底
```

## Network Only

Network Only（仅网络）始终请求网络，不使用也不写入缓存。适合必须实时、敏感或不可缓存的请求。

```js
self.addEventListener('fetch', (event) => {
  if (event.request.url.includes('/api/secure')) {
    event.respondWith(fetch(event.request));   // 直接透传，不缓存
  }
});
```

```text
适用场景：
1. 实时数据（股票、聊天消息）
2. 敏感信息（账户余额、支付）
3. 需要最新结果的搜索
4. POST/PUT/DELETE 等非 GET 请求
```

```text
注意：
Network Only 不提供离线能力，断网时直接失败。
对应 HTTP 的 no-store 语义，保证数据绝不残留本地。
```

## Cache Only

Cache Only（仅缓存）只从缓存读取，绝不请求网络。适合已经预缓存、且明确要离线工作的资源。

```js
self.addEventListener('fetch', (event) => {
  if (event.request.url.includes('/shell/')) {
    event.respondWith(caches.match(event.request));
  }
});
```

```text
适用场景：
1. 已预缓存的应用壳（app shell）
2. 明确离线优先的静态资源
3. 缓存里一定有、且不想产生任何网络请求的资源

风险：缓存未命中会失败，需确保安装时已预缓存
```

```js
// 安装时预缓存，确保 Cache Only 能命中
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('shell-v1').then((cache) =>
      cache.addAll(['/shell/header.html', '/shell/footer.html'])
    )
  );
});
```

## 应用场景实战

### 场景一：电商首页的混合策略

```js
self.addEventListener('fetch', (event) => {
  const { request } = event;
  const url = new URL(request.url);

  // 静态资源：缓存优先
  if (request.destination === 'script' || request.destination === 'style' || request.destination === 'font') {
    event.respondWith(cacheFirst(request));
  }
  // 商品图：先缓存后更新
  else if (request.destination === 'image') {
    event.respondWith(staleWhileRevalidate(request));
  }
  // 商品接口：网络优先
  else if (url.pathname.startsWith('/api/')) {
    event.respondWith(networkFirst(request));
  }
});

async function cacheFirst(request) {
  const cached = await caches.match(request);
  return cached || fetch(request);
}
async function networkFirst(request) {
  try {
    return await fetch(request);
  } catch {
    return caches.match(request);
  }
}
async function staleWhileRevalidate(request) {
  const cached = await caches.match(request);
  const network = fetch(request).then((res) => {
    caches.open('v1').then((c) => c.put(request, res.clone()));
    return res;
  });
  return cached || network;
}
```

### 场景二：离线优先的阅读应用

```js
// 文章内容：Cache First（已读文章离线可看）
// 文章列表：Network First（列表要新，失败用缓存兜底）
self.addEventListener('fetch', (event) => {
  const url = new URL(event.request.url);
  if (url.pathname.startsWith('/article/')) {
    event.respondWith(cacheFirst(event.request));
  } else if (url.pathname.startsWith('/api/list')) {
    event.respondWith(networkFirst(event.request));
  }
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 按资源类型拆分策略，不要全站一刀切
2. 写缓存前先 response.clone()，避免响应体被消费
3. 缓存名带版本，更新时切换版本并清理旧缓存
4. 非 GET 请求默认 Network Only，别缓存 POST 结果
5. 网络失败兜底要返回明确结果（如离线页），避免 undefined

### 踩坑记录

```text
坑 1：Cache First 导致内容永远不更新
结论：改了资源用户仍看到旧版。
原因：缓存一直命中，从未请求网络。
解法：缓存名带版本，或改资源 URL（hash），或改用 SWR。

坑 2：写入缓存时报错 body already used
结论：响应体被读取两次报错。
原因：把 response 既返回给页面又 put 进缓存，没 clone。
解法：缓存前 const clone = response.clone()，返回原 response。

坑 3：Network First 断网时返回 undefined
结论：网络失败且缓存未命中，respondWith 收到 undefined。
原因：catch 分支没有兜底，caches.match 也可能 miss。
解法：兜底返回离线页或明确响应，保证 respondWith 有值。

坑 4：缓存了 POST 请求导致错误复用
结论：接口 POST 结果被缓存，重复提交。
原因：未区分请求方法，POST 也被 Cache First 命中。
解法：仅对 GET 做缓存，POST 等走 Network Only。

坑 5：SWR 后台请求失败覆盖了缓存
结论：缓存被更新成错误响应。
原因：后台 fetch 失败仍把异常结果 put 进缓存。
解法：put 前检查 response.ok，非 2xx 不写入缓存。
```
