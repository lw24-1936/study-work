## 概述

React Compiler（原名 React Forget）是 React 官方推出的编译期优化工具，它自动为组件插入 `useMemo`、`useCallback` 等记忆化逻辑，让开发者不再手动写性能优化代码。

```text
React Compiler 解决的痛点：
1. 手动 useMemo/useCallback 繁琐且易漏
2. 忘记记忆化导致子组件无效重渲染
3. 过度记忆化导致代码难读、反而更慢
目标：编译器理解你的代码，自动做「恰到好处」的优化。
```

```jsx
// 优化前：每次渲染都重建对象/函数，破坏 memo 子组件的优化
function TodoList({ todos, filter }) {
  const visible = todos.filter(t => t.type === filter);  // 每次新数组
  const handleClick = (id) => toggle(id);                 // 每次新函数
  return <List items={visible} onClick={handleClick} />;
}

// React Compiler 自动等价于：
function TodoList({ todos, filter }) {
  const visible = useMemo(() => todos.filter(t => t.type === filter), [todos, filter]);
  const handleClick = useCallback((id) => toggle(id), []);
  return <List items={visible} onClick={handleClick} />;
}
```

## Automatic Memoization

Automatic Memoization（自动记忆化）是编译器的核心能力：静态分析组件代码，自动缓存那些「依赖不变就结果不变」的值与函数。

```text
自动记忆化的原理：
1. 分析每个值的依赖（引用了哪些变量）
2. 依赖不变时，复用上次的计算结果/引用
3. 等价于自动插入 useMemo/useCallback，但更精准
```

```jsx
// 编译器会缓存这个派生值
function Cart({ items }) {
  const total = items.reduce((sum, i) => sum + i.price, 0);  // 自动记忆化
  return <div>合计：{total}</div>;
}

// 也会缓存这个回调
function Cart({ items, onCheckout }) {
  const handleCheckout = () => onCheckout(items);  // 自动记忆化
  return <button onClick={handleCheckout}>结算</button>;
}
```

```text
与传统手写 memo 的区别：
1. 编译器分析更细，能发现依赖关系的细微变化
2. 避免「漏 memo」与「过度 memo」两个极端
3. 开发者代码保持原样，可读性不下降
```

## Compiler

Compiler 是 Babel 插件，在构建期分析并改写组件代码。它需要理解 React 的「数据流」，通过分析变量依赖生成等价的记忆化代码。

```text
编译器的工作流程：
1. 构建期（Babel/SWC 插件）遍历源码
2. 分析组件内的变量与依赖关系
3. 识别「纯计算」与「稳定回调」
4. 插入记忆化指令（生成 useMemo/useCallback 等价代码）
```

```js
// babel 插件接入（示例）
// .babelrc
{
  "plugins": [
    ["babel-plugin-react-compiler", { "target": "18" }]
  ]
}
```

```js
// Next.js 15 起内置支持（next.config.js）
const nextConfig = {
  experimental: {
    reactCompiler: true,
  },
};
module.exports = nextConfig;
```

```text
编译器遵循的边界：
1. 只优化「符合 React 规则」的组件
2. 依赖分析基于源码，无法理解运行时的外部可变状态
3. 对「违反规则」的组件会跳过优化并提示
```

## Optimization

编译器带来的优化集中在「减少无效重渲染」：缓存派生值、稳定回调引用、避免对象/数组在每次渲染中重建。

```text
优化的三个层次：
1. 稳定引用 —— 函数、对象、数组不再每次渲染重建
2. 跳过重渲染 —— 配合 memo，子组件无需无效更新
3. 减少计算 —— 昂贵派生值只在依赖变化时重算
```

```jsx
// 优化前：每次渲染都创建新对象，传给 memo 子组件导致其重渲染
function Parent({ config }) {
  const merged = { ...config, extra: true };  // 每次新对象
  return <Child config={merged} />;
}

// 编译器自动记忆化后，config 不变则 merged 引用不变
// 配合 React.memo 的 Child 就能跳过重渲染
const Child = memo(function Child({ config }) {
  return <div>{config.name}</div>;
});
```

```text
编译器的优化上限：
1. 只处理「编译期可分析」的依赖
2. 无法优化「违反规则」的代码
3. 运行时行为（如闭包捕获可变外部变量）需开发者配合
```

## Rules of React

Rules of React 是编译器正确工作的前提：组件与 Hook 必须遵循「纯函数、Hook 调用稳定」等规则，编译器才能安全地做记忆化。

```text
Rules of React 核心：
1. 组件与 Hook 必须是纯函数 —— 同输入同输出，无副作用
2. 只在组件/Hook 顶层调用 Hook —— 调用顺序稳定
3. 不可变更新 —— 通过 setState 返回新引用，而非原地修改
```

```jsx
// 遵守规则：组件是纯函数
function Price({ amount, tax }) {
  const total = amount * (1 + tax);  // 纯计算，无副作用
  return <span>{total}</span>;
}
```

```jsx
// 违反规则一：组件内修改外部变量（非纯函数）
let counter = 0;
function Bad({ id }) {
  counter++;          // 副作用：编译器无法安全优化
  return <div>{id}</div>;
}
```

```jsx
// 违反规则二：在条件/循环中调用 Hook
function Bad({ flag }) {
  if (flag) {
    const [x] = useState(0);  // 错误：Hook 不在顶层
  }
  return <div />;
}
```

```text
为什么规则如此重要：
记忆化依赖「依赖不变 → 结果不变」这一假设。
若组件有副作用或 Hook 顺序不稳定，
编译器插入的记忆化会缓存错误结果，反而产生 bug。
```

## 应用场景实战

### 场景一：编译器优化后的列表渲染

```jsx
import { memo } from 'react';

const Row = memo(function Row({ item, onSelect }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

// 无需手写 useMemo/useCallback，编译器自动处理
function List({ items, onSelect }) {
  const sorted = items.toSorted((a, b) => a.name.localeCompare(b.name));
  const handleSelect = (id) => onSelect(id);

  return (
    <ul>
      {sorted.map(item => (
        <Row key={item.id} item={item} onSelect={handleSelect} />
      ))}
    </ul>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 遵守 Rules of React，组件保持纯函数、Hook 顶层调用
2. 优先让编译器自动优化，删除手写的 useMemo/useCallback（编译器覆盖后）
3. 用 React DevTools 验证 memo 是否生效
4. 保持不可变更新，便于编译器分析依赖
5. 渐进启用：先小范围开启，观察行为无误再铺开

### 踩坑记录

```text
坑 1：组件非纯导致编译后结果错误
结论：开启编译器后出现难以理解的 bug。
原因：组件有副作用，记忆化缓存了副作用结果。
解法：把组件改成纯函数，副作用移入 Effect。

坑 2：违反 Hook 规则被编译器跳过
结论：部分组件没被优化，且可能报 ESLint 警告。
原因：条件/循环中调用 Hook，编译器无法分析。
解法：Hook 提到顶层，遵守调用顺序规则。

坑 3：原地修改 state 导致记忆化失效
结论：数据变了但界面不更新，或缓存返回旧值。
原因：原地 mutate 不改引用，依赖比较判定「没变」。
解法：始终用不可变方式更新（展开、map/filter）。

坑 4：过度依赖编译器而写难分析的代码
结论：间接依赖外部可变变量的组件优化失效。
原因：编译器只能分析静态依赖，运行时可变值无法追踪。
解法：把依赖显式传入组件，减少对全局可变状态的依赖。

坑 5：编译后依赖检测误判
结论：某些引用捕获了「会变的外部值」却被缓存。
原因：编译器对闭包捕获的非 props 变量判断有限。
解法：遵循「组件只依赖 props/state」的约定。
```
