## 概述

浏览器兼容性是指同一份前端代码在不同浏览器上表现一致的能力。主流浏览器内核不同、版本迭代节奏不同，对 HTML/CSS/JS 新特性的支持存在时间差，这是前端必须处理兼容性的根本原因。理解各浏览器的内核与差异是做好兼容的第一步。

```text
主流浏览器的内核与引擎：
1. Chrome —— Blink 渲染引擎 + V8 JS 引擎，更新最快
2. Firefox —— Gecko 渲染引擎 + SpiderMonkey，标准跟进稳
3. Safari —— WebKit 渲染引擎 + JavaScriptCore，更新慢且滞后
4. Edge —— 新版改用 Chromium（Blink + V8），与 Chrome 同源
5. iOS Safari —— WebKit，受 iOS 系统版本绑定，无法单独升级
6. Android Browser —— 碎片化严重，国产机型多套 WebView 内核
```

```js
// 兼容性判断的第一手段：User-Agent 与特性检测
const ua = navigator.userAgent;
console.log('浏览器:', ua);

// 更推荐特性检测而非 UA 判断（见 95.2 Compatibility）
const supportsLazy = 'loading' in HTMLImageElement.prototype;
console.log('支持原生懒加载:', supportsLazy);
```

## Chrome

Chrome 使用 Blink 渲染引擎 + V8 引擎，是 Web 新特性的先锋，更新周期约 4 周，市场份额最高。多数新 API（如 WebGPU、View Transitions）先在 Chrome 落地，因此 Chrome 是「现代特性」的基准参照。

```js
// Chrome 独有/先行的能力示例
// 1. 支持最新的 ES 语法与 CSS 特性
const big = 123456789012345678901234567890n;  // BigInt
console.log(big);

// 2. 支持 WebGPU（需在支持版本上）
if ('gpu' in navigator) {
  console.log('支持 WebGPU');
}

// 3. DevTools 完善，是性能/内存诊断的首选工具
```

```text
Chrome 的要点：
1. Blink + V8 —— 渲染与 JS 执行都很快
2. 更新最快 —— 新特性最先支持，适合作为开发基准
3. DevTools 最全 —— 诊断调试首选
4. 市场份额最大 —— 兼容性的「最大公约数」参考
```

## Firefox

Firefox 使用 Gecko 渲染引擎 + SpiderMonkey 引擎，由 Mozilla 维护，标准跟进稳健但节奏略慢于 Chrome。它对隐私、开放标准的坚持使其在开发者群体中仍有稳定用户。

```js
// Firefox 的差异点示例
// 1. 某些 API 的参数/返回值与 Chrome 略有差异
// 2. 对 -moz- 前缀的早期特性支持（现代已少用）
// 3. CSS 上部分特性实现细节不同，需实测

// 检测是否为 Firefox
const isFirefox = navigator.userAgent.includes('Firefox');
console.log('isFirefox:', isFirefox);
```

```text
Firefox 的要点：
1. Gecko + SpiderMonkey —— 独立内核，非 Chromium 系
2. 标准跟进稳 —— 特性支持时间点常晚于 Chrome 数月
3. 隐私取向 —— 部分 API 受限（如部分硬件 API）
4. 测试必测 —— 不能只测 Chrome，Firefox 的差异要单独验证
```

## Safari

Safari 使用 WebKit 渲染引擎 + JavaScriptCore（Nitro）引擎，由 Apple 维护，是 iOS/macOS 的默认浏览器。它是「慢一拍」的代表：新特性支持滞后明显，且很多 Web API 支持不全或行为不同。

```js
// Safari 常见差异点示例
// 1. 部分 API 缺失，需 polyfill 或降级
if (!('IntersectionObserver' in window)) {
  console.log('Safari 旧版不支持 IO，需 polyfill');
}

// 2. 日期解析更严格
const d1 = new Date('2026-08-13');       // Safari 对非 ISO 格式易报 Invalid Date
const d2 = new Date('2026-08-13T00:00:00Z'); // ISO 8601 才可靠
console.log(d1, d2);

// 3. 不支持 WebM 视频格式，需提供 MP4
```

```text
Safari 的要点：
1. WebKit + JavaScriptCore —— 非 Chromium 系，差异大
2. 特性滞后 —— 新 API 支持晚，需查 caniuse
3. 日期/正则等细节差异 —— 容易踩坑
4. 桌面 + iOS 双端 —— 但 iOS Safari 与桌面 Safari 版本策略不同
```

## Edge

Edge 分两代：旧版 EdgeHTML 已淘汰，新版 Edge（2020 起）改用 Chromium 内核（Blink + V8），与 Chrome 高度一致。当前主要考虑新版，兼容问题与 Chrome 基本同步。

```js
// 新版 Edge 与 Chrome 同源，差异极小
const isChromium = !!window.chrome;
const isEdge = navigator.userAgent.includes('Edg');
console.log('Chromium 内核:', isChromium, '是 Edge:', isEdge);

// 旧版 EdgeHTML（Edge 18 及以前）才需单独适配，现可基本忽略
// 若仍需兼容，注意 fetch/模板字符串等特性在旧 Edge 的缺失
```

```text
Edge 的要点：
1. 新版 Chromium —— 与 Chrome 同内核，兼容性几乎一致
2. 旧版已淘汰 —— EdgeHTML 内核可基本不再适配
3. 企业场景 —— Windows 环境默认浏览器，仍有存量用户
4. 测试策略 —— 通常测了 Chrome 即可覆盖新版 Edge
```

## iOS Safari

iOS Safari 是 iPhone/iPad 上的浏览器，内核为 WebKit，但版本与 iOS 系统绑定——用户不升级系统就升不了浏览器，导致大量「老版本」长期存在。这是移动端兼容的难点。

```js
// iOS Safari 的差异点示例
// 1. 100vh 在 iOS 上含地址栏高度，需用 dvh 或 JS 修正
const vh = window.innerHeight * 0.01;
document.documentElement.style.setProperty('--vh', `${vh}px`);
// 2. 不支持 WebM，视频要 MP4
// 3. 无法自动播放带声音的视频
const video = document.querySelector('video');
video.play().catch(() => console.log('iOS 需用户手势才能播放'));
```

```text
iOS Safari 的要点：
1. 版本绑定系统 —— 老 iOS 必然对应老 Safari，无法单独升级
2. 100vh 坑 —— 地址栏导致视口高度计算差异
3. 自动播放受限 —— 需用户手势触发
4. 弹性滚动/橡皮筋 —— 滚动行为与桌面不同，需处理
```

## Android Browser

Android 浏览器碎片化严重：除 Chrome 外，还有大量国产 App 内置 WebView（基于不同 Chromium 版本）、三星浏览器等，内核版本参差不齐。老内核 WebView 常缺新特性，是兼容性「长尾」。

```js
// Android 浏览器/WebView 的差异点示例
// 1. WebView 内核版本难预测，需按低版本 Chromium 兜底
// 2. 老内核不支持可选链/空值合并等新语法（需 transpile）
const name = window.__legacyData?.user?.name;  // 老 WebView 需转译

// 3. 屏幕尺寸、DPR 差异大，适配要弹性
const dpr = window.devicePixelRatio || 1;
console.log('设备像素比:', dpr);
```

```text
Android Browser 的要点：
1. 碎片化 —— 内核版本跨度大，从老 WebView 到新 Chromium
2. WebView 兜底 —— 按最低目标版本做语法转译与 polyfill
3. 国产内核 —— 部分 App 用 X5/XWeb 等，行为略有差异
4. 测试矩阵 —— 用真机 + 云真机覆盖主流机型
```

## 应用场景实战

### 场景一：一份代码兼容 Chrome / Firefox / Safari

```js
// 用特性检测 + 降级策略，让同一份代码跑通三大内核
// 1. 懒加载：优先原生，不支持则 polyfill
const imgs = document.querySelectorAll('img[data-src]');
if ('loading' in HTMLImageElement.prototype) {
  imgs.forEach(img => { img.loading = 'lazy'; img.src = img.dataset.src; });
} else {
  // 降级：用 IntersectionObserver 或 scroll 监听手动懒加载
  const io = new IntersectionObserver((entries) => {
    entries.forEach(e => {
      if (e.isIntersecting) {
        e.target.src = e.target.dataset.src;
        io.unobserve(e.target);
      }
    });
  });
  imgs.forEach(img => io.observe(img));
}

// 2. 视频格式：提供 MP4 兜底（Safari/iOS 不支持 WebM）
// <video><source src="x.webm" type="video/webm"><source src="x.mp4" type="video/mp4"></video>
```

### 场景二：处理 iOS Safari 的 100vh 与安全区

```js
// iOS 地址栏折叠导致 100vh 实际比可视区高
// 用 JS 动态计算真实视口高度
function setViewportHeight() {
  const vh = window.innerHeight * 0.01;
  document.documentElement.style.setProperty('--vh', `${vh}px`);
}
window.addEventListener('resize', setViewportHeight);
setViewportHeight();

// 刘海屏安全区适配（env 常量）
// .safe-padding { padding-bottom: env(safe-area-inset-bottom); }
// 完整写法带 fallback：
// padding-bottom: constant(safe-area-inset-bottom); /* iOS < 11.2 */
// padding-bottom: env(safe-area-inset-bottom);       /* iOS >= 11.2 */
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 caniuse 查特性支持矩阵，再决定 polyfill / 降级 / 转译
2. 优先特性检测（'x' in obj）而非 UA 判断，UA 易伪造且脆弱
3. 测试矩阵至少覆盖 Chrome + Firefox + Safari + 一款 iOS 真机
4. 新特性先查 Safari 支持情况，它往往是最慢的那个
5. 视频/音频提供双格式（WebM + MP4），覆盖 Safari
6. 老 WebView 按最低目标版本做语法转译 + polyfill

### 踩坑记录

```text
坑 1：只测 Chrome 就上线
结论：Firefox/Safari 上样式错乱或功能不可用。
原因：三内核差异大，Chrome 正常不代表其他浏览器正常。
解法：测试矩阵至少覆盖 Chrome/Firefox/Safari + 移动端真机。

坑 2：用 UA 判断特性支持
结论：UA 被伪造或误判，导致功能走错分支。
原因：UA 字符串不可靠，且需维护一堆正则。
解法：用特性检测（'fetch' in window 等）判断能力。

坑 3：iOS 上 100vh 超出可视区
结论：页面底部被地址栏遮挡，出现滚动条。
原因：iOS 的 100vh 含地址栏高度，折叠时计算不准。
解法：用 --vh 变量 + innerHeight 动态计算，或用 100dvh。

坑 4：Safari 日期解析报 Invalid Date
结论：new Date('2026-08-13 10:00') 在 Safari 返回 Invalid Date。
原因：Safari 对非 ISO 8601 格式解析更严格。
解法：统一用 ISO 8601（含 T 和时区）格式，或手动解析。

坑 5：iOS 视频自动播放被拦截
结论：带声音的视频在 iOS 上无法自动播放。
原因：iOS Safari 要求用户手势才能播放带音视频。
解法：静音（muted）可自动播放，或等用户点击后再 play。
```
