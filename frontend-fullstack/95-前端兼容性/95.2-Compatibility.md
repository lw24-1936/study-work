## 概述

兼容性处理是「让同一份代码在不同浏览器上都能跑」的一套工程手段，核心有五件工具：Feature Detection（特性检测）、Polyfill（垫片）、Transpile（转译）、Browserslist（目标浏览器清单）、Autoprefixer（自动加前缀）。它们从运行时判断、能力补齐、语法降级、目标声明、CSS 前缀五个层面协同工作。

```text
五件兼容性工具的定位：
1. Feature Detection —— 运行时判断浏览器是否支持某特性，按能力分支
2. Polyfill —— 补齐缺失的 API（如 Promise、fetch）
3. Transpile —— 把新语法降级成老浏览器能懂的旧语法
4. Browserslist —— 声明要支持的浏览器范围，供工具链读取
5. Autoprefixer —— 按目标浏览器自动补 CSS 前缀
```

```js
// 兼容性处理的标准姿势：检测 -> 降级/补齐
if ('fetch' in window) {
  fetch('/api/data').then(r => r.json());
} else {
  // 不支持则走降级（或已被 polyfill 补齐）
  xhrFallback('/api/data');
}
```

## Feature Detection

特性检测是「运行时探测浏览器是否支持某个能力」，据此决定走原生实现还是降级。它比 UA 判断可靠，因为直接探测能力本身而非猜浏览器身份。

```js
// 特性检测的通用写法：探测对象/原型上是否存在
const supports = {
  fetch: 'fetch' in window,
  promise: 'Promise' in window,
  intersection: 'IntersectionObserver' in window,
  lazy: 'loading' in HTMLImageElement.prototype,
  esModules: 'noModule' in document.createElement('script'),
};

// 按能力分支
function loadImage(img) {
  if (supports.lazy) {
    img.loading = 'lazy';
    img.src = img.dataset.src;
  } else if (supports.intersection) {
    const io = new IntersectionObserver((es) => {
      es.forEach(e => { if (e.isIntersecting) { e.target.src = e.target.dataset.src; io.unobserve(e.target); } });
    });
    io.observe(img);
  } else {
    img.src = img.dataset.src; // 最终降级：直接加载
  }
}
```

```text
Feature Detection 的要点：
1. 探测能力 —— 不猜浏览器，直接看能力在不在
2. 检测语法 —— 语法错误无法运行时捕获，需靠转译解决
3. 分支降级 —— 支持走原生，不支持走降级/polyfill
4. 常见库 —— Modernizr 提供成套检测，但现在多手写几行即可
```

## Polyfill

Polyfill（垫片）是在运行时补齐缺失 API 的代码：检测到 `Promise` 不存在时，注入一个实现，让老浏览器也能用。它补的是「API 缺失」，不解决「新语法」（那是 Transpile 的事）。

```js
// Polyfill 的原理：能力缺失时注入实现
if (!window.Promise) {
  // 注入简化版 Promise（实际用 core-js 等成熟实现）
  window.Promise = class Promise {
    constructor(executor) {
      this.callbacks = [];
      executor(this.resolve.bind(this), this.reject.bind(this));
    }
    resolve(value) { this.value = value; this.callbacks.forEach(cb => cb(value)); }
    reject(error) { this.error = error; }
    then(onFulfilled) { this.callbacks.push(onFulfilled); return this; }
  };
}
// 业务代码可以无感使用 Promise
new Promise(resolve => setTimeout(() => resolve('done'), 100)).then(console.log);
```

```text
Polyfill 的要点：
1. 补 API —— 让老浏览器「假装」支持新 API
2. 按需注入 —— 只 polyfill 缺失的，别全量注入拖慢加载
3. 成熟实现 —— 用 core-js，别手写生产级 polyfill
4. 与转译区分 —— polyfill 补 API，transpile 降语法
```

## Transpile

Transpile（转译）在构建期把新语法降级成老浏览器能解析的旧语法，例如把箭头函数、可选链、async/await 转成 ES5。工具是 Babel / SWC / TypeScript 编译器。

```js
// 转译前的现代语法
const getUser = async (id) => {
  const res = await fetch(`/api/user/${id}`);
  return res?.data?.name ?? 'unknown';
};

// Babel 转译后（示意，降级到 ES5）
// var getUser = function getUser(id) {
//   return fetch('/api/user/' + id).then(function (res) {
//     return res && res.data && res.data.name ? res.data.name : 'unknown';
//   });
// };
```

```text
Transpile 的要点：
1. 语法降级 —— 箭头函数、可选链、class、async 等转旧语法
2. 构建期 —— 在打包时完成，产物即兼容代码
3. 按目标转 —— 目标浏览器清单（Browserslist）决定降到多旧
4. 配合 polyfill —— 语法转译 + API polyfill 双管齐下
```

## Browserslist

Browserslist 是一份「目标浏览器清单」的声明，写在前端工具链都能读的位置（package.json 的 browserslist 字段或 .browsersrc）。Babel、Autoprefixer、PostCSS 等工具据此决定转译深度与加前缀范围。

```json
{
  "browserslist": [
    "> 0.5%",
    "last 2 versions",
    "not dead",
    "not IE 11"
  ]
}
```

```text
Browserslist 的要点：
1. 单一事实来源 —— 一处声明，全工具链共用
2. 查询语法 —— 按份额、版本、地区、是否维护筛选
3. 决定转译深度 —— 目标越老，转译与 polyfill 越多
4. 决定前缀 —— Autoprefixer 据此判断要不要加前缀
```

## Autoprefixer

Autoprefixer 是 PostCSS 插件，按 Browserslist 目标自动给 CSS 属性补厂商前缀（-webkit-、-moz- 等）。开发者只写标准写法，前缀交给工具生成，避免手写前缀遗漏或多余。

```css
/* 开发者只写标准写法 */
.example {
  display: flex;
  user-select: none;
  backdrop-filter: blur(10px);
}
```

```css
/* Autoprefixer 按目标浏览器自动补前缀后的输出 */
.example {
  display: -webkit-box;
  display: -webkit-flex;
  display: flex;
  -webkit-user-select: none;
  user-select: none;
  -webkit-backdrop-filter: blur(10px);
  backdrop-filter: blur(10px);
}
```

```text
Autoprefixer 的要点：
1. 自动加前缀 —— 按 caniuse 数据 + Browserslist 判断
2. 只写标准 —— 开发者不手写前缀，交给工具
3. 避免多余 —— 目标浏览器不需要前缀时不会加
4. PostCSS 生态 —— 配合其他 CSS 插件一起用
```

## 应用场景实战

### 场景一：从零配置一份 Babel 兼容链

```js
// babel.config.js：按目标浏览器转译 + 按需 polyfill
module.exports = {
  presets: [
    ['@babel/preset-env', {
      targets: '> 0.5%, last 2 versions, not dead',
      useBuiltIns: 'usage',   // 按代码实际用到的 API 按需注入 polyfill
      corejs: 3,              // 指定 core-js 版本
    }],
  ],
};
// 源码里的 async/await、可选链、Promise、fetch 都会被自动处理
```

### 场景二：运行时检测 + 动态降级

```js
// 一个自包含的兼容性处理示例：图片懒加载三档降级
function lazyLoad(imgs) {
  // 第一档：原生 loading 属性
  if ('loading' in HTMLImageElement.prototype) {
    imgs.forEach(img => { img.loading = 'lazy'; img.src = img.dataset.src; });
    return;
  }
  // 第二档：IntersectionObserver
  if ('IntersectionObserver' in window) {
    const io = new IntersectionObserver((entries) => {
      entries.forEach(e => {
        if (e.isIntersecting) { e.target.src = e.target.dataset.src; io.unobserve(e.target); }
      });
    });
    imgs.forEach(img => io.observe(img));
    return;
  }
  // 第三档：直接加载（兜底）
  imgs.forEach(img => { img.src = img.dataset.src; });
}
lazyLoad([...document.querySelectorAll('img[data-src]')]);
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先声明 Browserslist，让 Babel/Autoprefixer 都读同一份目标
2. 特性检测优先于 UA 判断，能力探测比身份猜测可靠
3. polyfill 用 useBuiltIns: 'usage' 按需注入，别全量打包
4. 新语法交给转译，缺失 API 交给 polyfill，两者别混用
5. CSS 只写标准写法，前缀交给 Autoprefixer
6. 上线前用 caniuse 核对目标浏览器对关键特性的支持

### 踩坑记录

```text
坑 1：只转译语法不补 polyfill
结论：老浏览器报 Promise is not defined / fetch is not defined。
原因：转译只降语法，不补 API，两者职责不同。
解法：配合 core-js 按需 polyfill，或 useBuiltIns 配置。

坑 2：polyfill 全量打包
结论：bundle 体积暴涨，首屏变慢。
原因：@babel/polyfill 一次性注入全部 polyfill，不管用没用。
解法：useBuiltIns: 'usage' + corejs: 3，按代码实际用法注入。

坑 3：手写 CSS 前缀
结论：前缀遗漏导致样式失效，或写了多余前缀。
原因：手动维护前缀容易漏，且不知道目标浏览器到底要不要。
解法：交给 Autoprefixer，按 Browserslist 自动处理。

坑 4：Browserslist 范围过宽
结论：为了兼容 0.01% 的老浏览器，bundle 巨大且慢。
原因：目标浏览器定得太老，转译和 polyfill 全按最差情况来。
解法：按真实用户数据定目标，老浏览器用降级而非硬兼容。

坑 5：特性检测误判
结论：检测通过但实际功能仍异常。
原因：检测了属性存在，但该属性有 bug 或行为不符（如老 IE 的 addEventListener）。
解法：对已知有 bug 的特性，检测到也走降级路径。
```
