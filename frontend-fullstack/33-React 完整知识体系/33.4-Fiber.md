## 概述

Fiber 是 React 16 重写的协调引擎，把「一次完整、不可中断的递归渲染」拆成「可中断、可分片的单元」。它的目标是让 React 能优先响应高优任务（如输入、动画），把低优任务拆碎插空执行。

```text
Fiber 解决了什么问题：
1. 旧的栈递归渲染不可中断 → 长任务阻塞主线程
2. 无法区分任务优先级 → 紧急交互被大批量更新卡住
3. 无法让出主线程 → 动画/输入掉帧
Fiber 用「链表 + 优先级 + 可中断循环」解决上述问题。
```

```text
Fiber 的关键设计：
1. 每个组件/元素对应一个 Fiber Node（工作单元）
2. Fiber 组成一棵可遍历的树（Fiber Tree）
3. 双缓冲：current 树（当前屏上）与 workInProgress 树（正在构建）
4. 渲染可中断、可恢复、可丢弃重来
```

## Fiber Node

Fiber Node 是 Fiber 架构的基本工作单元，是一个描述组件实例信息、指向 DOM 与相邻节点的 JS 对象。

```js
// Fiber Node 的核心字段（简化示意）
{
  type: 'div',            // 组件类型（函数/类/HTML 标签）
  key: null,              // 列表 key
  props: { children: [] },// 传入的 props
  stateNode: domNode,     // 对应的真实 DOM 或组件实例

  return: parentFiber,    // 父 Fiber（向上）
  child: firstChildFiber, // 第一个子 Fiber（向下）
  sibling: nextSibling,   // 下一个兄弟 Fiber（向右）

  tag: FunctionComponent, // Fiber 种类
  flags: Update,          // 副作用标记（增删改）
  lanes: 0b0001,          // 该节点的优先级 Lane
  alternate: oldFiber,    // 双缓冲：指向另一棵树的对应节点
}
```

```text
Fiber Node 通过 return / child / sibling 三个指针构成链表，
替代了原递归调用栈，因此遍历可以「暂停并记住位置」。
```

## Fiber Tree

Fiber Tree 由 Fiber Node 通过链表指针连接而成，是「组件树 + 副作用」的完整表达。React 维护两棵：current 与 workInProgress（双缓冲）。

```text
两棵 Fiber Tree：
current Tree —— 已提交到屏幕上的树（可读、稳定）
workInProgress Tree —— 渲染阶段正在构建的新树
提交完成后两者互换（alternate 指针相互指向）。
```

```text
树的遍历（深度优先，可中断）：
1. beginWork —— 自上而下，为每个节点生成子节点
2. completeWork —— 自下而上，收集副作用、创建 DOM
通过 child/sibling/return 指针完成，替代递归调用栈。
```

```jsx
// 组件树
function App() {
  return (
    <div>
      <Header />
      <List />
    </div>
  );
}
// 对应 Fiber：App → div(child) → Header(child)、List(Header 的 sibling)
```

## Reconciliation

Reconciliation（协调）是「计算新旧 Fiber 树差异」的过程：遍历新元素、对比旧 Fiber，产出需要增删改的变更清单。

```text
Reconciliation 的流程：
1. 遍历新元素，逐个与旧 Fiber 对比
2. 判断节点是「复用、更新、新增、删除」
3. 打上 flags（Placement/Update/Deletion）
4. 产出 Effect List，交给提交阶段执行
```

```jsx
// 复用与否取决于 type 与 key
// type 相同 → 复用 Fiber，仅更新 props
// type 不同 → 销毁旧子树，重建新子树
function render() {
  return flag ? <div>文本</div> : <span>文本</span>;
  // div → span：type 变化，整个子树重建
}
```

## Diff

Diff 是 Reconciliation 的核心算法，针对「同层比较」做了三次优化，使复杂度从 O(n³) 降到近似 O(n)。

```text
Diff 三条规则：
1. 只做同层比较 —— 不跨层移动节点
2. type 不同 → 直接删除重建（子树整体替换）
3. 用 key 标识列表项，识别移动与复用
```

```jsx
// key 让 React 识别「同一个」列表项
const list = items.map(item => <li key={item.id}>{item.name}</li>);

// 没有 key（或 key 不稳定）时，插入/删除会导致后续项全部重建
const bad = items.map((item, i) => <li key={i}>{item.name}</li>);
```

```text
列表 Diff 的匹配策略：
1. 头对头、尾对尾匹配
2. 剩余部分用 key 建立映射表
3. 命中 key 的节点复用并移动，未命中的新增，多余的删除
```

## Scheduler

Scheduler 是独立的调度器，负责任务的优先级排序与时间分片：通过 `requestIdleCallback` 的替代实现（MessageChannel）把长任务切成 5ms 左右的小片。

```text
Scheduler 的职责：
1. 维护任务队列（按优先级排序）
2. 时间分片 —— 每个时间片（约 5ms）处理一批任务
3. 到期让出主线程，让浏览器处理输入/绘制
4. 高优先级任务可插队，低优先级可被中断
```

```js
// Scheduler 的核心 API（概念示意）
import { unstable_scheduleCallback, PriorityLevel } from 'scheduler';

unstable_scheduleCallback(PriorityLevel.LowPriority, () => {
  // 低优先级任务，可被中断
});
```

## Priority

优先级决定任务的执行顺序。React 把更新分成若干等级，高优先级（用户输入、动画）优先于低优先级（数据预取、离屏渲染）。

```text
优先级（由高到低）：
1. 离散事件 —— 点击、按键（同步、不可延迟）
2. 连续事件 —— 拖动、滚动、输入（需立即响应）
3. 默认优先级 —— 普通 setState
4. 过渡优先级 —— useTransition 标记的非紧急更新
5. 空闲优先级 —— 离屏、预渲染（可无限延迟）
```

```jsx
import { useTransition } from 'react';

// 输入是连续事件（高优），搜索结果渲染是过渡（低优）
function Search() {
  const [isPending, startTransition] = useTransition();
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);

  const onChange = (e) => {
    setQuery(e.target.value);       // 高优：输入框立即更新
    startTransition(() => {          // 低优：结果可被中断
      setResults(search(e.target.value));
    });
  };
  return <div>{isPending ? '加载中' : results.length}</div>;
}
```

## Lane

Lane 是优先级的二进制表达，用位掩码表示「这个更新属于哪些优先级」。每个 Fiber 上记录 lanes，调度器据此判断任务的紧急程度。

```text
Lane 模型：
1. 每种优先级对应一个 bit（如 SyncLane = 0b1, TransitionLane = 0b1000）
2. 一个更新可能对应多个 lane（位或运算合并）
3. 通过位运算快速判断、合并、批量处理优先级
4. 取代早期单一的 expirationTime，支持更细粒度的并发控制
```

```js
// Lane 位运算示意
const SyncLane = 0b0001;       // 同步
const InputLane = 0b0010;      // 输入
const TransitionLane = 0b0100; // 过渡

// 合并优先级
const lanes = SyncLane | TransitionLane;  // 0b0101

// 判断是否包含某优先级
const isTransition = (lanes & TransitionLane) !== 0;
```

## Render

Render（渲染阶段）在 Fiber 架构下变成「可中断的遍历」：从根节点开始 beginWork/completeWork，计算新的 workInProgress 树并标记副作用。

```text
Render 阶段（可中断）：
1. 从根 Fiber 开始深度优先遍历
2. beginWork：对比新旧节点，标记 flags
3. completeWork：创建/更新 DOM，收集 Effect List
4. 遇到更高优先级任务或时间片用尽 → 暂停并让出主线程
5. 恢复时从暂停处继续（得益于链表结构）
```

```jsx
// 渲染阶段的产物是「变更描述」，而非直接改 DOM
function List({ items }) {
  return (
    <ul>
      {items.map(i => <li key={i.id}>{i.name}</li>)}
    </ul>
  );
}
// Render 阶段只算出：哪些 li 新增、哪些复用、哪些删除
```

## Commit

Commit（提交阶段）把 Render 阶段产出的 Effect List 一次性应用到真实 DOM，此过程同步且不可中断。

```text
Commit 阶段（不可中断）：
1. Before Mutation —— 读取旧 DOM（如 getSnapshotBeforeUpdate）
2. Mutation —— 增删改真实 DOM，解绑/绑定 ref
3. Layout —— 执行 useLayoutEffect，DOM 已更新未绘制
之后浏览器绘制，最后异步执行 useEffect（Passive Effects）。
```

```jsx
import { useLayoutEffect, useEffect } from 'react';

function Example() {
  useLayoutEffect(() => {
    // Commit 的 Layout 子阶段，绘制前执行
  });
  useEffect(() => {
    // 提交完成后异步执行
  });
  return <div />;
}
```

## 应用场景实战

### 场景一：用 useTransition 保持输入流畅

```jsx
import { useState, useTransition, useMemo } from 'react';

function ProductSearch({ products }) {
  const [keyword, setKeyword] = useState('');
  const [isPending, startTransition] = useTransition();

  const filtered = useMemo(
    () => products.filter(p => p.name.includes(keyword)),
    [products, keyword]
  );

  const onChange = (e) => {
    const value = e.target.value;
    setKeyword(value);
    // 过滤放过渡中（低优），输入框保持高优流畅
    startTransition(() => { /* 触发过滤相关状态更新 */ });
  };

  return (
    <div>
      <input value={keyword} onChange={onChange} />
      {isPending && <span>过滤中…</span>}
      <ul>{filtered.map(p => <li key={p.id}>{p.name}</li>)}</ul>
    </div>
  );
}
```

### 场景二：稳定 key 减少列表重建

```jsx
function TodoList({ todos, onToggle }) {
  return (
    <ul>
      {todos.map(todo => (
        <li key={todo.id}>  {/* 稳定 id：切换状态只更新对应项 */}
          <input
            type="checkbox"
            checked={todo.done}
            onChange={() => onToggle(todo.id)}
          />
          {todo.text}
        </li>
      ))}
    </ul>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 列表渲染用稳定唯一 key，让 Diff 能复用节点而非重建
2. 大列表过滤/搜索用 useTransition，避免阻塞输入
3. 组件体保持纯函数，副作用交给 Effect，保证可中断渲染安全
4. 避免深层不必要的大范围状态提升，减少 Diff 遍历范围
5. 拆分大组件，让更新只影响局部子树

### 踩坑记录

```text
坑 1：用 index 作 key 导致复用错乱
结论：列表增删时出现输入框错位、动画异常。
原因：index 不稳定，Diff 误判为同一节点复用。
解法：使用数据的稳定唯一 id。

坑 2：render 阶段做副作用导致多次执行
结论：请求/日志被触发多次，出现重复副作用。
原因：并发模式下 render 可能被中断重跑，函数体非纯。
解法：副作用移入 useEffect/事件处理。

坑 3：组件体里创建大量对象/函数
结论：每次渲染产生新引用，破坏 memo 优化。
原因：render 阶段每次执行都重新创建。
解法：用 useMemo/useCallback 缓存，或提升到模块级。

坑 4：误以为所有 setState 都同步
结论：并发模式下低优更新被延迟或丢弃。
原因：更新有优先级，过渡更新可被打断。
解法：紧急交互不用 startTransition 包裹，理解优先级语义。

坑 5：一个巨型组件导致整树重渲染
结论：局部更新却整页卡顿。
原因：组件过大，Diff 与渲染范围过大。
解法：拆分组件、memo、合理上提状态。
```
