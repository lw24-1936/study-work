## 概述

并发渲染（Concurrent Rendering）是 React 18 的核心能力：渲染过程不再是一口气跑完，而是可被打断、恢复、放弃。它让 React 能优先响应用户交互，把耗时的更新放到空闲时处理，从而保持界面流畅。

```text
并发渲染带来的能力：
1. 可中断渲染 —— 高优任务随时插队
2. 过渡更新 —— 标记非紧急更新（useTransition）
3. 自动批处理 —— 多处 setState 合并为一次渲染
4. Suspense 数据获取 —— 用声明式等待异步数据
5. 流式 SSR —— 服务端边渲染边发送
```

```jsx
import { startTransition, useTransition } from 'react';

// startTransition 标记「非紧急」更新
startTransition(() => {
  setSearchResults(expensiveSearch(keyword));
});
```

## Concurrent Mode

Concurrent Mode 是一组并发特性的统称，React 18 起默认启用（通过 `createRoot`）。它改变了渲染模型：从「同步一次性」变为「可中断的调度」。

```text
开启方式（React 18）：
React 17: ReactDOM.render(<App/>, root)  // 旧同步渲染
React 18: createRoot(root).render(<App/>) // 并发渲染（默认开启）
```

```jsx
import { createRoot } from 'react-dom/client';

const root = createRoot(document.getElementById('root'));
root.render(<App />);
// 此后组件内的更新走并发调度，而非同步递归
```

```text
并发模式的本质：
渲染可被「暂停—让出—恢复—丢弃」，由调度器决定何时做、按什么优先级做。
开发者通过 API（startTransition、Suspense）标记任务的紧急程度。
```

## Scheduler

Scheduler 是并发渲染的调度核心：维护按优先级排序的任务队列，并用时间分片让出主线程。

```text
Scheduler 的工作方式：
1. 任务按优先级入队
2. 每 5ms 一个时间片，处理到期任务
3. 时间片用完 → 让出主线程（MessageChannel 宏任务）
4. 浏览器处理输入/绘制后再回来继续
```

```js
// 调度器选择宏任务而非微任务的示意
// 微任务会插队导致饥饿，宏任务（MessageChannel）更公平
const channel = new MessageChannel();
channel.port1.onmessage = () => flushTasks();  // 下个宏任务再处理
channel.port2.postMessage(null);
```

```text
为什么不用 requestIdleCallback：
1. 兼容性差（Safari 不支持）
2. 触发时机不稳定（约 50ms 才回调）
Scheduler 用 MessageChannel 自研实现，保证 5ms 级的分片精度。
```

## Transition

Transition 是「非紧急更新」的标记：用 `useTransition` 或 `startTransition` 包裹的更新，可被更紧急的更新打断，避免卡顿。

```jsx
import { useState, useTransition } from 'react';

function SearchBox({ onSearch }) {
  const [input, setInput] = useState('');
  const [result, setResult] = useState(null);
  const [isPending, startTransition] = useTransition();

  const handleChange = (e) => {
    setInput(e.target.value);            // 紧急：输入框立即响应
    startTransition(() => {               // 非紧急：结果可被打断
      setResult(onSearch(e.target.value));
    });
  };

  return (
    <div>
      <input value={input} onChange={handleChange} />
      {isPending ? <p>搜索中…</p> : <Result data={result} />}
    </div>
  );
}
```

```text
Transition 的价值：
1. 紧急更新（输入）永远优先于非紧急更新（结果）
2. 非紧急更新进行中可被丢弃，用最新一次代替
3. isPending 让 UI 展示「过渡中」状态
```

## Suspense

Suspense 让组件「声明式地等待」异步资源（数据、代码），在等待期间渲染 fallback，资源就绪后自动恢复。

```jsx
import { Suspense } from 'react';

function App() {
  return (
    <Suspense fallback={<Spinner />}>
      <Profile />
    </Suspense>
  );
}

// Profile 内部使用支持 Suspense 的数据源（如 React Query、use）
function Profile() {
  const user = useUser();  // 未就绪时抛 Promise，Suspense 捕获
  return <div>{user.name}</div>;
}
```

```jsx
// 嵌套 Suspense：不同区域独立等待
<Suspense fallback={<Skeleton />}>
  <Header />
  <Suspense fallback={<ListSkeleton />}>
    <CommentList />
  </Suspense>
</Suspense>;
```

## Streaming

Streaming（流式渲染）是服务端渲染的并发能力：服务端边渲染边把 HTML 分块发送，浏览器渐进式显示，无需等整页渲染完成。

```text
流式 SSR 的流程：
1. 服务端渲染出「外壳」HTML 立即发送
2. 用 Suspense 包裹的慢组件先发 fallback
3. 慢组件就绪后，把对应的 HTML + 数据以流的形式追加
4. 浏览器收到片段即渲染（配合 hydrate）
```

```jsx
// 服务端：慢数据组件用 Suspense 包裹，不阻塞首屏
import { Suspense } from 'react';

function Page() {
  return (
    <html>
      <body>
        <Header />                    {/* 立即流式输出 */}
        <Suspense fallback={<div>加载评论…</div>}>
          <Comments />                {/* 就绪后追加输出 */}
        </Suspense>
      </body>
    </html>
  );
}
```

```text
Streaming 的优势：
1. 首屏 TTFB 更快，用户先看到外壳
2. 慢查询不阻塞整页，逐块补齐
3. 配合 Suspense 实现细粒度的流式控制
```

## Interruptible Rendering

可中断渲染是并发渲染的底层机制：一次渲染可以被更高优先级的更新打断，让出主线程，稍后恢复或丢弃。

```text
可中断渲染的机制：
1. 渲染拆成 Fiber 单元（每个组件一个工作单元）
2. 每个单元执行前检查是否应让出（时间片/更高优先级）
3. 让出后记住位置，主线程空闲时继续
4. 若期间有更高优先级更新，则丢弃当前 workInProgress 重新开始
```

```jsx
import { useState, useDeferredValue } from 'react';

// useDeferredValue：让派生渲染「可被打断/延迟」
function List({ query }) {
  const deferredQuery = useDeferredValue(query);
  // query 更新立即生效，deferredQuery 滞后且可被中断
  const items = expensiveFilter(deferredQuery);
  return <ul>{items.map(i => <li key={i.id}>{i.name}</li>)}</ul>;
}
```

```text
可中断的边界：
1. Render 阶段可中断（纯计算，无副作用）
2. Commit 阶段不可中断（DOM 变更必须原子完成）
3. 因此组件体必须保持纯函数
```

## 应用场景实战

### 场景一：大列表搜索不卡输入

```jsx
import { useState, useTransition, useDeferredValue } from 'react';

function SearchableTable({ rows }) {
  const [keyword, setKeyword] = useState('');
  const [isPending, startTransition] = useTransition();
  const deferredKeyword = useDeferredValue(keyword);

  const filtered = rows.filter(r => r.name.includes(deferredKeyword));

  return (
    <div>
      <input
        value={keyword}
        onChange={e => {
          setKeyword(e.target.value);
          startTransition(() => { /* 触发表格状态更新 */ });
        }}
      />
      {isPending && <span>筛选进行中…</span>}
      <table>
        <tbody>
          {filtered.map(r => (
            <tr key={r.id}><td>{r.name}</td><td>{r.value}</td></tr>
          ))}
        </tbody>
      </table>
    </div>
  );
}
```

### 场景二：分区懒加载 + Suspense

```jsx
import { Suspense, lazy } from 'react';

const HeavyChart = lazy(() => import('./HeavyChart'));
const HeavyTable = lazy(() => import('./HeavyTable'));

function Dashboard() {
  return (
    <div>
      <Suspense fallback={<ChartSkeleton />}>
        <HeavyChart />
      </Suspense>
      <Suspense fallback={<TableSkeleton />}>
        <HeavyTable />
      </Suspense>
    </div>
  );
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 输入、点击等交互更新保持紧急，不用 transition 包裹
2. 昂贵计算/大数据渲染用 useTransition/useDeferredValue 降级
3. 慢组件用 Suspense + fallback 隔离，避免拖慢首屏
4. 组件体保持纯函数，确保可中断渲染的安全
5. 服务端渲染用 Suspense 分块，实现流式输出

### 踩坑记录

```text
坑 1：把紧急更新包进 startTransition
结论：点击、输入出现明显延迟。
原因：紧急交互被降级为过渡，可被打断延迟。
解法：只有非紧急、可延迟的更新才用 transition。

坑 2：组件体非纯导致并发渲染出错
结论：可中断渲染下副作用被执行多次。
原因：render 可能被丢弃重来，函数体非纯会产生重复副作用。
解法：副作用移入 Effect/事件，函数体保持纯计算。

坑 3：Suspense 资源未就绪时错误处理缺失
结论：fallback 卡住或渲染异常。
原因：数据源抛错时没有 ErrorBoundary 兜底。
解法：Suspense 外层配 ErrorBoundary，分别处理等待与错误。

坑 4：滥用 useDeferredValue 导致界面「滞后感」
结论：数据展示明显延迟，体验变差。
原因：所有派生都延迟，简单的也变慢。
解法：只在确实昂贵的场景用，简单渲染直接同步。

坑 5：忘记升级 createRoot
结论：用了并发 API 却不生效。
原因：仍用 ReactDOM.render 旧入口，未启用并发。
解法：React 18 起改用 createRoot 挂载。
```
