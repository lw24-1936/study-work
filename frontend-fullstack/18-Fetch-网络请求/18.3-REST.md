## 概述

REST（Representational State Transfer）是一种 API 设计风格，把服务端数据抽象为「资源」（Resource），用 HTTP 方法表达操作，用 URL 定位资源。

```text
REST 的核心原则：
1. 资源导向 —— 一切皆资源，URL 是资源标识
2. HTTP 方法 —— GET/POST/PUT/DELETE 表达操作
3. 无状态 —— 每个请求独立，不依赖服务端会话
4. 统一接口 —— 一致的 URL 和响应格式
```

## Resource 资源与 CRUD

资源是 REST 的核心，CRUD 对应四种 HTTP 方法。

```text
CRUD 与 HTTP 方法映射：
Create  —— POST   /users（创建）
Read    —— GET    /users、/users/1（读取）
Update  —— PUT    /users/1（整体更新）、PATCH（部分更新）
Delete  —— DELETE /users/1（删除）
```

```js
// 用户资源的 CRUD
// 创建
await fetch('/api/users', { method: 'POST', body: JSON.stringify(user) });
// 读取列表
await fetch('/api/users');
// 读取单个
await fetch('/api/users/1');
// 更新
await fetch('/api/users/1', { method: 'PUT', body: JSON.stringify(user) });
// 删除
await fetch('/api/users/1', { method: 'DELETE' });
```

```text
URL 设计规范：
1. 资源用复数名词（/users 而非 /user）
2. 层级关系（/users/1/orders）
3. 动作用 HTTP 方法，而非 URL 动词（不用 /getUser）
4. 过滤/分页用查询参数（/users?page=2）
```

## Idempotency 幂等性

幂等性指「多次执行同一操作，结果相同」。

```text
各方法的幂等性：
GET / DELETE —— 幂等（多次结果相同）
PUT —— 幂等（整体替换，重复结果一致）
POST —— 非幂等（每次创建新资源）

幂等的意义：网络重试安全，重复提交不会产生副作用。
```

```js
// POST 非幂等：重复提交会创建多条
await fetch('/api/users', { method: 'POST', body: JSON.stringify(user) });

// 幂等性保证：客户端生成唯一 ID 用 PUT
const id = crypto.randomUUID();
await fetch(`/api/users/${id}`, { method: 'PUT', body: JSON.stringify(user) });
```

```text
幂等性实践：
1. 重复提交防护 —— 表单防抖、按钮禁用
2. 关键操作（支付）用幂等键
3. 重试安全 —— 幂等接口可安全重试
```

## Pagination 分页

分页控制大数据量的返回，常见有偏移分页和游标分页。

```text
两种分页：
偏移分页（Offset）—— page / limit，简单但深页性能差
游标分页（Cursor）—— 基于游标，适合大数据/实时数据
```

```js
// 偏移分页
const page = 2;
const limit = 20;
await fetch(`/api/users?page=${page}&limit=${limit}`);
// 响应：{ data: [...], total: 100, page: 2, limit: 20 }
```

```js
// 游标分页
await fetch('/api/users?cursor=eyJpZCI6MTAwfQ&limit=20');
// 响应：{ data: [...], nextCursor: '...' }
```

```text
分页响应约定：
偏移分页 —— 返回 total、page、limit、data
游标分页 —— 返回 nextCursor、data

前端：滚动加载用游标，翻页用偏移。
```

## Filtering 与 Sorting

过滤和排序通过查询参数实现，保持 URL 语义清晰。

```js
// 过滤
await fetch('/api/users?status=active&role=admin');

// 排序（正序/倒序）
await fetch('/api/users?sort=createdAt');        // 升序
await fetch('/api/users?sort=-createdAt');       // 降序

// 组合
await fetch('/api/users?status=active&sort=-createdAt&page=1');
```

```text
过滤排序规范：
过滤 —— ?key=value（多条件用 & 连接）
排序 —— ?sort=field（-field 表示降序）
组合 —— 过滤 + 排序 + 分页自由组合
```

## Versioning 版本管理

API 版本管理让接口演进不影响旧客户端，常见有 URL 版本和 Header 版本。

```js
// URL 版本（最常见）
await fetch('/api/v1/users');
await fetch('/api/v2/users');

// Header 版本
await fetch('/api/users', {
  headers: { 'API-Version': '2026-01-01' },
});
```

```text
版本策略：
URL 版本 —— /v1/、/v2/（直观，最常用）
Header 版本 —— 自定义头（URL 干净，但不易调试）

重大变更升版本，兼容变更不升。
```

## Error Code 错误码

统一错误码让前端能可靠处理错误。

```text
HTTP 状态码约定：
200 —— 成功
201 —— 创建成功
400 —— 请求参数错误
401 —— 未认证
403 —— 无权限
404 —— 资源不存在
409 —— 冲突（重复创建）
422 —— 参数校验失败
429 —— 限流
500 —— 服务端错误
```

```js
// 统一错误响应格式
// { code: 'INVALID_PARAM', message: '参数错误', details: {...} }

try {
  await fetch('/api/users', { method: 'POST', body: JSON.stringify(user) });
} catch (error) {
  // 根据 error.code 分类处理
}
```

```text
错误处理的约定：
1. 用标准 HTTP 状态码
2. 响应体提供业务错误码（code）+ 提示（message）
3. 前端按状态码 + 业务码分类处理
```

## 应用场景实战

### 场景一：带分页过滤的列表

```js
async function fetchUsers({ page = 1, status, sort }) {
  const params = new URLSearchParams({ page, limit: 20 });
  if (status) params.set('status', status);
  if (sort) params.set('sort', sort);
  return fetch(`/api/users?${params}`).then(r => r.json());
}
```

### 场景二：幂等的更新操作

```js
// PUT 整体更新（幂等，可安全重试）
await fetch(`/api/users/${id}`, {
  method: 'PUT',
  body: JSON.stringify(user),
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 资源用复数名词，动作用 HTTP 方法
2. 更新用 PUT（整体）/ PATCH（部分）
3. 分页、过滤、排序用查询参数
4. 幂等操作（PUT/DELETE）可安全重试
5. 错误用标准状态码 + 业务错误码

### 踩坑记录

```text
坑 1：URL 用动词
结论：/api/getUser 这种设计不符合 REST。
原因：把操作放 URL，而非 HTTP 方法。
解法：/api/users + GET。

坑 2：POST 非幂等重复提交
结论：重复提交创建多条记录。
原因：POST 每次创建新资源。
解法：防抖/禁用按钮，或用幂等键。

坑 3：状态码误用
结论：业务错误也返回 200，前端难判断。
原因：所有响应都 200 + 业务码。
解法：遵循 HTTP 状态码语义（4xx 客户端错，5xx 服务端错）。

坑 4：深页性能问题
结论：offset 分页到第 100 页很慢。
原因：OFFSET 需要扫描并跳过前面的数据。
解法：大数据用游标分页。

坑 5：版本管理缺失
结论：接口变更导致旧客户端崩溃。
原因：没有版本隔离。
解法：URL 版本（/v1、/v2）或 Header 版本。
```
