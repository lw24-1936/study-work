## 概述

SSE（Server-Sent Events）是服务端向客户端**单向推送**的技术，基于 HTTP，用 EventSource 接收。相比 WebSocket 更轻量，适合「服务端主动推送、客户端只读」的场景。

```text
SSE 的特点：
1. 单向 —— 服务端推，客户端收（客户端用普通 HTTP 发请求）
2. 基于 HTTP —— 复用 HTTP 协议，穿透性好
3. 自动重连 —— 断线自动重连（内置）
4. 纯文本 —— 只支持文本数据（不支持二进制）

对比 WebSocket：SSE 简单、单向、文本；WebSocket 双向、二进制。
```

## EventSource 基础

EventSource 是 SSE 的客户端接口，连接服务端事件流。

```js
const source = new EventSource('/api/events');

// 连接建立
source.onopen = () => {
  console.log('连接建立');
};

// 接收默认消息
source.onmessage = (event) => {
  console.log('收到数据:', event.data);
};

// 错误处理
source.onerror = () => {
  console.log('连接错误或断开');
};

// 关闭连接
source.close();
```

```text
EventSource 的特点：
1. 自动重连 —— 断开后自动重连（无需手动）
2. 只支持 GET —— 不能自定义请求头
3. 文本格式 —— 数据是字符串
4. 同源/跨域 —— 跨域需服务端配 CORS
```

## Server-Sent Events 格式

SSE 的数据是特定格式的纯文本，服务端用 `text/event-stream` 响应。

```text
服务端响应格式：
Content-Type: text/event-stream

每条消息的字段：
data: 数据内容（可多行）
event: 事件名（可选，默认 message）
id: 事件 ID（可选，用于断点续传）
retry: 重连间隔（毫秒）

消息之间用空行分隔。
```

```
// 服务端推送示例
data: 第一条消息

data: 第二条消息
id: 100

event: customEvent
data: 自定义事件数据
```

## Event Stream 事件流

服务端持续发送事件流，客户端实时接收。

```js
// 服务端（Node.js 示例）
app.get('/api/events', (req, res) => {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
  });

  // 定时推送
  const timer = setInterval(() => {
    res.write(`data: ${JSON.stringify({ time: Date.now() })}\n\n`);
  }, 1000);

  req.on('close', () => clearInterval(timer));
});
```

```js
// 客户端接收
const source = new EventSource('/api/events');
source.onmessage = (e) => {
  const data = JSON.parse(e.data);
  console.log(data.time);
};
```

```text
事件流的处理：
1. 服务端保持连接，持续 write 数据
2. 客户端 onmessage 实时接收
3. 连接关闭时服务端清理定时器
```

## Reconnect 自动重连

EventSource 内置自动重连，断线后按 retry 间隔重连。

```text
自动重连机制：
1. 连接断开，浏览器自动重连
2. 重连间隔由 retry 字段指定（默认约 3 秒）
3. onerror 触发时可能正在重连

服务端可通过 retry 字段控制重连间隔。
```

```
retry: 5000
data: 这条消息后，重连间隔变为 5 秒
```

```js
// 客户端：监听重连状态
const source = new EventSource('/api/events');

source.onopen = () => console.log('已连接');
source.onerror = () => console.log('断开（会自动重连）');
```

## Last-Event-ID 断点续传

EventSource 重连时会带上 `Last-Event-ID` 头，服务端据此续传未收到的数据。

```text
断点续传机制：
1. 服务端给每条消息设置 id
2. 客户端记录最后收到的 id
3. 重连时自动带 Last-Event-ID 头
4. 服务端从该 id 之后继续推送
```

```js
// 服务端：根据 Last-Event-ID 续传
app.get('/api/events', (req, res) => {
  const lastId = req.headers['last-event-id'];
  // 从 lastId 之后的数据开始推送
  const events = getEventsAfter(lastId);
  events.forEach(e => {
    res.write(`id: ${e.id}\ndata: ${e.data}\n\n`);
  });
});
```

```text
断点续传的价值：
1. 断线期间的数据不丢失
2. 重连后从断点继续

注意：需要服务端配合实现（存储事件 + 处理 Last-Event-ID）。
```

## 应用场景实战

### 场景一：实时通知推送

```js
const source = new EventSource('/api/notifications');

source.addEventListener('notification', (e) => {
  const notification = JSON.parse(e.data);
  showToast(notification.message);
});
```

### 场景二：实时日志/进度

```js
const source = new EventSource('/api/task-progress');

source.onmessage = (e) => {
  const progress = JSON.parse(e.data);
  updateProgressBar(progress.percent);
  if (progress.done) source.close();
};
```

## 最佳实践与踩坑记录

### 最佳实践

1. 单向推送（通知、进度、日志）用 SSE，双向用 WebSocket
2. 服务端设置正确响应头（text/event-stream、no-cache）
3. 用 id 实现断点续传
4. 连接不再需要时主动 close
5. 跨域场景配 CORS

### 踩坑记录

```text
坑 1：EventSource 不能自定义请求头
结论：想加 Authorization 头发送，做不到。
原因：EventSource 只支持 GET，无自定义头。
解法：用 fetch 读流实现，或 token 放 URL 参数，或换 WebSocket。

坑 2：服务端未设 text/event-stream
结论：客户端收不到事件。
原因：Content-Type 不是 text/event-stream，浏览器不解析。
解法：设置正确响应头。

坑 3：代理/缓冲导致延迟
结论：数据被中间代理缓冲，不实时。
原因：未设置 no-cache 和禁用缓冲。
解法：Cache-Control: no-cache + X-Accel-Buffering: no。

坑 4：连接数限制
结论：打开太多 EventSource 连接，浏览器限制。
原因：浏览器对同域名 HTTP 连接数有限制（约 6 个）。
解法：合理复用连接，或 HTTP/2 提升并发。

坑 5：忽略断点续传导致数据丢失
结论：断线期间的数据永久丢失。
原因：未用 id + Last-Event-ID 续传。
解法：服务端设置消息 id，处理 Last-Event-ID。
```
