## 概述

WebSocket 提供**全双工、持久**的通信通道：建立连接后，客户端和服务端可随时互相发送消息，无需重复建立连接。适用于实时通信场景。

```text
WebSocket 的特点：
1. 全双工 —— 双向同时通信
2. 持久连接 —— 一次握手，长期复用
3. 低延迟 —— 相比 HTTP 轮询，实时性高
4. 二进制/文本 —— 支持两种消息格式

对比：HTTP 是「请求-响应」单向，WebSocket 是「双向实时」。
```

## Handshake 握手

WebSocket 通过 HTTP 升级协议建立连接（Upgrade 头），成功后切换为 WebSocket 协议。

```js
// 建立连接
const ws = new WebSocket('ws://example.com/chat');
// 或 wss://（加密，类似 https）

ws.onopen = () => {
  console.log('连接建立（握手成功）');
};
```

```text
握手过程：
1. 客户端发 HTTP 请求，带 Upgrade: websocket 头
2. 服务端返回 101 Switching Protocols
3. 协议切换为 WebSocket（ws:// 或 wss://）

ws:// —— 明文（类似 http）
wss:// —— 加密（类似 https，生产环境必须用）
```

## Frame 与 Text / Binary

WebSocket 以「帧」（Frame）传输数据，消息分为文本和二进制两类。

```js
const ws = new WebSocket('ws://example.com');

// 发送文本
ws.send('hello');

// 发送二进制（Blob / ArrayBuffer）
const buffer = new ArrayBuffer(16);
ws.send(buffer);
ws.binaryType = 'arraybuffer';   // 指定接收二进制类型
```

```js
// 接收消息
ws.onmessage = (event) => {
  console.log('收到文本:', event.data);   // 文本为字符串
  // 二进制则取决于 binaryType
};
```

```text
消息类型：
Text —— 字符串（默认）
Binary —— Blob / ArrayBuffer

binaryType 选项：'blob'（默认）或 'arraybuffer'。
```

## Ping / Pong 心跳

Ping/Pong 是协议层的心跳机制，用于检测连接是否存活。

```text
Ping/Pong 机制：
1. 一方发 Ping 帧
2. 另一方收到自动回 Pong 帧
3. 用于探测连接存活、保活

注意：浏览器 WebSocket API 不直接暴露 ping/pong，
应用层需要自己实现心跳（发自定义消息）。
```

```js
// 应用层心跳（浏览器不暴露 ping/pong，需自定义）
const ws = new WebSocket('ws://example.com');
let heartbeatTimer;

ws.onopen = () => {
  // 每 30 秒发一次心跳
  heartbeatTimer = setInterval(() => {
    if (ws.readyState === WebSocket.OPEN) {
      ws.send(JSON.stringify({ type: 'ping' }));
    }
  }, 30000);
};

ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === 'pong') {
    console.log('心跳正常');
  }
};
```

## Close 关闭

close 关闭连接，通过 close 事件和状态码处理关闭。

```js
const ws = new WebSocket('ws://example.com');

// 主动关闭
ws.close(1000, '正常关闭');   // 状态码 + 原因

// 监听关闭
ws.onclose = (event) => {
  console.log('连接关闭:', event.code, event.reason);
};
```

```text
常见关闭状态码：
1000 —— 正常关闭
1001 —— 端点离开（页面关闭）
1006 —— 异常断开（无关闭帧）
1011 —— 服务端错误

通过 code 判断关闭原因，决定是否重连。
```

## Reconnect 重连

网络波动会导致连接断开，健壮的 WebSocket 客户端需要自动重连。

```js
function createWebSocket(url) {
  const ws = new WebSocket(url);

  ws.onclose = () => {
    console.log('连接断开，3 秒后重连');
    setTimeout(() => createWebSocket(url), 3000);   // 重连
  };

  return ws;
}
```

```js
// 带退避的重连
function createWS(url) {
  const ws = new WebSocket(url);
  let retries = 0;

  ws.onclose = () => {
    const delay = Math.min(1000 * 2 ** retries, 30000);  // 指数退避
    retries++;
    setTimeout(() => createWS(url), delay);
  };
  ws.onopen = () => { retries = 0; };   // 连接成功重置
}
```

```text
重连策略：
1. 指数退避 —— 延迟逐步增加（1s、2s、4s...上限 30s）
2. 最大重试 —— 限制重连次数，避免无限循环
3. 页面可见性 —— 页面不可见时暂停重连
```

## Heartbeat 与 Backpressure

心跳保活检测连接；背压处理发送过快导致缓冲区积压。

```js
// 心跳：检测连接是否真的存活
// 服务端定期 ping，客户端超时未收到 pong 则断开重连

// 背压：检查发送缓冲区
const ws = new WebSocket('ws://example.com');

function sendLargeData(data) {
  if (ws.bufferedAmount === 0) {
    ws.send(data);
  } else {
    console.log('缓冲区积压，等待...');
    // 等 bufferedAmount 降低再发
  }
}
```

```text
bufferedAmount（背压）：
1. 表示未发送的数据量（字节）
2. 发送过快时缓冲区积压
3. 检查 bufferedAmount 控制发送速率
```

## 应用场景实战

### 场景一：实时聊天

```js
const ws = new WebSocket('wss://chat.example.com');

ws.onopen = () => ws.send(JSON.stringify({ type: 'join', room: 'general' }));

ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === 'message') {
    renderMessage(msg);
  }
};

function sendMessage(text) {
  ws.send(JSON.stringify({ type: 'message', text }));
}
```

### 场景二：实时行情推送

```js
const ws = new WebSocket('wss://market.example.com');

ws.onmessage = (e) => {
  const quote = JSON.parse(e.data);
  updatePrice(quote.symbol, quote.price);
};
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产环境用 wss://（加密）
2. 必须实现重连（指数退避）
3. 应用层心跳检测连接存活
4. 发送大数据检查 bufferedAmount（背压）
5. 页面卸载时主动 close，释放连接

### 踩坑记录

```text
坑 1：用 ws:// 而非 wss://
结论：生产环境明文传输，不安全、被拦截。
原因：忘用加密连接。
解法：生产环境用 wss://。

坑 2：无重连机制
结论：网络抖动后连接永久断开。
原因：只建一次连接，不重连。
解法：onclose 里自动重连（退避）。

坑 3：忽略心跳
结论：连接假死（实际已断，但无 close 事件）。
原因：中间设备/网络静默断开，客户端无感知。
解法：应用层心跳 + 超时检测。

坑 4：onclose 里无限重连
结论：服务端拒绝时反复重连，资源浪费。
原因：无最大重试限制。
解法：限制重试次数 + 指数退避 + 页面可见性判断。

坑 5：发送数据未检查 bufferedAmount
结论：高频发送导致内存暴涨、消息积压。
原因：忽略背压，发送速度超过网络。
解法：检查 bufferedAmount，控制发送速率。
```
