## 概述

JavaScript 是解释执行 + JIT 即时编译的混合模式。现代引擎（V8 等）先解析成字节码快速执行，再对热点代码做优化编译，实现高性能。

```text
JS 执行的完整流程：
源码 → Parser（解析）→ AST（语法树）→ Bytecode（字节码）
→ 解释执行 → 热点检测 → JIT 优化编译 → 机器码

核心思想：先快后优，热点代码才花时间优化。
```

## Parser 解析

Parser 把源码解析成 AST，是执行的第一步。

```text
解析的两阶段：
词法分析（Lexer）—— 源码 → Token（词法单元）
语法分析（Parser）—— Token → AST

解析是「同步阻塞」的，解析耗时影响首屏。
```

```js
// 解析慢的原因：代码量大、复杂语法
// 优化：代码分割、按需加载（懒解析）
```

```text
懒解析（Lazy Parsing）：
V8 对「暂时不执行的函数」先做浅解析，
真正调用时才完整解析，提升启动速度。
```

## AST 抽象语法树

AST 是源码的结构化表示，是编译/转换的基础。

```js
// 源码
const sum = a + b;

// AST（简化）
{
  type: 'VariableDeclaration',
  declarations: [{
    type: 'VariableDeclarator',
    id: { type: 'Identifier', name: 'sum' },
    init: {
      type: 'BinaryExpression',
      operator: '+',
      left: { type: 'Identifier', name: 'a' },
      right: { type: 'Identifier', name: 'b' },
    },
  }],
}
```

```text
AST 的用途：
1. 引擎执行 —— 转字节码
2. 工具链 —— Babel 转换、ESLint 检查、代码压缩
3. 分析 —— 依赖分析、tree shaking
```

## Bytecode 字节码

AST 编译为字节码，由解释器（Ignition）执行。

```text
字节码的特点：
1. 比 AST 更接近机器，但仍是中间表示
2. 由解释器逐条执行
3. 生成快，启动快
4. 牺牲峰值性能换启动速度
```

```text
为什么用字节码（而非直接机器码）：
1. 生成快 —— 快速开始执行
2. 跨平台 —— 字节码与硬件无关
3. 内存小 —— 比机器码占用少
```

## JIT 即时编译

JIT（Just-In-Time）在运行时把「热点代码」编译成机器码，提升执行速度。

```text
JIT 的核心策略：
1. 先解释执行（快启动）
2. 监控热点（频繁执行的代码）
3. 热点代码编译成机器码（快执行）
4. 非热点代码继续解释执行
```

```text
JIT 的价值：
1. 平衡启动速度与执行性能
2. 只优化真正需要的代码
3. 避免解释执行的重复开销
```

## Baseline Compiler 基线编译器

基线编译器（Baseline）快速把字节码编译为「未优化」的机器码，是热点代码的第一级优化。

```text
基线编译器的特点：
1. 编译快 —— 快速生成机器码
2. 未深度优化 —— 代码质量一般
3. 收集反馈 —— 记录类型信息供后续优化
```

## Optimizing Compiler 优化编译器与 Deoptimization

优化编译器（TurboFan 等）基于类型反馈做深度优化；假设失效时**反优化**（Deoptimization）回退。

```text
优化编译器的策略：
1. 内联缓存（Inline Cache）—— 缓存类型假设
2. 隐藏类（Hidden Class）—— 优化属性访问
3. 深度优化 —— 基于类型反馈生成高效机器码

Deoptimization（反优化）：
当类型假设被破坏（如对象结构变化），
回退到基线/解释执行，保证正确性。
```

```js
// 类型稳定的代码，JIT 能优化
function add(a, b) {
  return a + b;
}
add(1, 2);       // 总是数字，JIT 优化为整数加法
add('a', 'b');   // 传入字符串，类型变化 → 反优化

// 类型多变会破坏优化
function sum(arr) {
  let result = 0;
  for (const item of arr) {
    result += item;   // 若 item 类型多变，难以优化
  }
  return result;
}
```

```text
反优化的代价：
1. 放弃已生成的优化代码
2. 回退到基线/解释执行
3. 重新收集类型反馈

启示：保持类型稳定，让 JIT 持续优化。
```

## 应用场景实战

### 场景一：保持类型稳定

```js
// 反例：同一函数参数类型多变
function process(value) {
  return value + 1;   // 数字 → 字符串，类型不稳定
}
process(1);
process('a');

// 正例：类型一致
function processNumber(value) {
  return value + 1;   // 始终数字
}
```

### 场景二：避免隐藏类破坏

```js
// 反例：动态添加属性，破坏隐藏类
const obj = {};
obj.a = 1;
obj.b = 2;   // 隐藏类变化

// 正例：构造时初始化全部属性
const obj2 = { a: 1, b: 2 };
```

## 最佳实践与踩坑记录

### 最佳实践

1. 保持函数参数类型稳定，利于 JIT 优化
2. 对象属性在构造函数中一次性初始化（隐藏类）
3. 避免频繁改变对象结构（动态增删属性）
4. 代码分割减少解析成本
5. 热点代码避免类型多态

### 踩坑记录

```text
坑 1：类型多态破坏 JIT
结论：同一函数传入多种类型，性能下降。
原因：类型假设频繁失效，反复反优化。
解法：保持类型稳定，或按类型拆分函数。

坑 2：动态增删属性破坏隐藏类
结论：频繁 add/delete 属性，属性访问变慢。
原因：隐藏类结构变化，内联缓存失效。
解法：构造时初始化属性，少动态增删。

坑 3：大脚本解析慢
结论：首屏等待解析耗时。
原因：脚本量大，同步解析阻塞。
解法：代码分割、懒加载、减少依赖。

坑 4：误以为 JS 纯解释执行
结论：以为 JS 没有编译，性能都靠解释。
原因：不了解 JIT。
解法：理解 JIT，写出利于优化的代码。

坑 5：delete 属性导致反优化
结论：delete obj.x 使隐藏类退化。
原因：删除属性改变对象结构。
解法：用赋值 undefined 替代 delete（或重构）。
```
