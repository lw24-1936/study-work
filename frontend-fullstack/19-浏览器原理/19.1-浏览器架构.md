## 概述

现代浏览器（Chrome 等）采用**多进程架构**：把界面、渲染、网络、GPU 等职责拆分到不同进程，实现稳定性与安全隔离。理解进程模型是理解浏览器性能和安全的基础。

```text
多进程架构的进程：
1. Browser Process —— 浏览器主进程（界面、协调）
2. Renderer Process —— 渲染进程（解析渲染页面）
3. GPU Process —— GPU 进程（图形加速）
4. Network Process —— 网络进程（网络请求）
5. Utility Process —— 工具进程（辅助功能）
```

## Browser Process 浏览器主进程

主进程是浏览器的「大脑」，负责界面、协调、管理其他进程。

```text
Browser Process 的职责：
1. 界面 —— 地址栏、书签、标签栏、前进后退
2. 协调 —— 创建/销毁其他进程
3. 文件存储 —— 磁盘缓存、Cookie、历史记录
4. 权限 —— 管理权限请求（通知、定位等）
```

```js
// 主进程不直接处理页面内容，而是管理渲染进程
// 一个主进程 + 多个渲染进程（每个标签页一个）
```

```text
主进程的意义：
1. 单一入口 —— 用户操作统一由主进程处理
2. 进程管理 —— 控制各子进程生命周期
3. 崩溃恢复 —— 渲染进程崩溃不影响主进程
```

## Renderer Process 渲染进程

渲染进程负责页面的解析和渲染，每个标签页通常一个独立的渲染进程。

```text
Renderer Process 的职责：
1. HTML/CSS 解析 —— 构建 DOM、CSSOM
2. JavaScript 执行 —— 运行页面脚本
3. 布局与绘制 —— Layout、Paint
4. 渲染输出 —— 生成最终像素

隔离：一个标签页崩溃不影响其他标签页。
```

```js
// 渲染进程内的关键线程：
// 主线程 —— JS 执行、样式计算、布局
// 合成线程 —— 图层合成
// 光栅线程 —— 位图光栅化
```

```text
渲染进程的多线程：
主线程 —— JS、样式、布局、绘制（最繁忙）
合成器线程 —— 图层合成
光栅化线程 —— 生成位图
```

## GPU Process 与 Network Process

GPU 进程负责图形加速，网络进程统一处理网络请求。

```text
GPU Process：
1. 图形加速 —— 合成、光栅化的硬件加速
2. 共享 —— 多个渲染进程共享一个 GPU 进程

Network Process：
1. 网络请求 —— 统一处理所有标签页的网络 I/O
2. 安全 —— 网络隔离，独立于渲染进程
```

```text
网络进程的意义：
1. 集中管理 —— 所有网络请求统一出口
2. 安全隔离 —— 渲染进程无法直接访问网络
3. 性能 —— 连接复用、缓存管理
```

## Utility Process 工具进程

Utility Process 处理各种辅助功能，是杂项进程的统称。

```text
Utility Process 的职责（示例）：
1. 音频播放
2. 网络服务（部分实现）
3. 数据解码（图片、视频）
4. 扩展程序

特点：按需创建，任务单一。
```

## Sandbox 沙箱

渲染进程运行在沙箱中，隔离系统资源，即使页面有恶意代码也无法访问系统。

```text
Sandbox 的隔离：
1. 渲染进程无直接文件/网络/系统访问权限
2. 需通过主进程「代理」访问（IPC 通信）
3. 恶意代码被限制在沙箱内

安全意义：即使漏洞被利用，也难逃出沙箱。
```

```text
沙箱的代价：
1. 通信开销 —— 跨进程 IPC 调用
2. 复杂度 —— 权限代理与校验
```

## Site Isolation 站点隔离

Site Isolation 让不同站点的内容运行在**不同的渲染进程**，防止跨站攻击（如 Spectre/Meltdown 类侧信道攻击）。

```text
站点隔离的价值：
1. 安全 —— 不同站点进程隔离，防止数据窃取
2. 稳定 —— 一个站点崩溃不影响其他
3. 代价 —— 更多进程，内存占用增加

iframe 跨站内容也会被隔离到独立进程。
```

```text
多进程 vs 单进程：
多进程 —— 稳定、安全，但内存开销大
单进程 —— 省内存，但一个页面崩溃全崩

现代浏览器都采用多进程 + 站点隔离。
```

## 应用场景实战

### 场景一：理解页面卡顿

```text
页面卡顿通常是渲染进程主线程被长任务占用。
排查：Performance 面板看主线程的 Long Task。
优化：拆分长任务、使用 Worker。
```

### 场景二：理解内存占用

```text
每个标签页一个渲染进程，标签页越多内存越大。
站点隔离进一步增加进程数。
排查：浏览器任务管理器（Shift+Esc）看各进程内存。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 理解「渲染进程主线程」是性能瓶颈所在
2. 长任务拆分或放 Worker，避免阻塞主线程
3. 减少跨 iframe 跨站内容，降低站点隔离开销
4. 排查崩溃看渲染进程是否独立崩溃
5. 内存问题用浏览器任务管理器定位进程

### 踩坑记录

```text
坑 1：误以为 JS 卡顿是浏览器卡死
结论：页面卡顿，以为是浏览器问题。
原因：渲染进程主线程被 JS 长任务占用。
解法：优化 JS，拆分长任务，或用 Worker。

坑 2：iframe 跨站导致内存暴涨
结论：嵌入多个跨站 iframe，内存激增。
原因：站点隔离为每个跨站 iframe 开独立进程。
解法：减少跨站 iframe，或评估隔离成本。

坑 3：忽略渲染进程崩溃的恢复
结论：标签页崩溃后整页丢失。
原因：渲染进程崩溃，页面状态未持久化。
解法：关键状态及时保存（如 localStorage）。

坑 4：误解多进程的内存开销
结论：疑惑浏览器内存占用高。
原因：多进程 + 站点隔离，每进程都有基础开销。
解法：理解架构，合理管理标签页数量。

坑 5：在渲染进程做重活
结论：大量计算放主线程，页面卡顿。
原因：渲染进程主线程承担 JS + 布局 + 绘制。
解法：重计算放 Web Worker。
```
