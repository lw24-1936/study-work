## 概述

浏览器渲染是从输入 URL 到显示页面的完整流程，分为网络阶段和渲染阶段。理解这条流水线，才能针对性优化页面性能。

```text
完整渲染流水线：
网络阶段：
URL 输入 → DNS → TCP → TLS → HTTP 响应

渲染阶段：
HTML Parsing → DOM
CSS Parsing → CSSOM
DOM + CSSOM → Render Tree
Layout（布局）→ Paint（绘制）→ Raster（光栅化）→ Composite（合成）
```

## 网络阶段 URL 输入到 HTTP

输入 URL 后，浏览器经过 DNS 解析、TCP/TLS 连接、HTTP 请求获取资源。

```text
网络流程：
1. URL 输入 → 解析协议、域名、路径
2. DNS 解析 → 域名转 IP（缓存优先）
3. TCP 连接 → 三次握手
4. TLS 握手 → HTTPS 加密连接
5. HTTP 请求 → 发送请求，接收响应
6. 响应返回 → HTML 文档
```

```text
各阶段优化点：
DNS —— 预解析（dns-prefetch）
TCP —— 连接复用、预连接（preconnect）
TLS —— HTTP/2、会话复用
HTTP —— 缓存、压缩
```

## HTML Parsing 与 DOM

浏览器解析 HTML 字节流，构建 DOM 树。

```text
HTML 解析过程：
字节 → 字符 → Token（词法分析）→ 节点 → DOM 树

关键特性：
1. 流式解析 —— 边下载边解析
2. 容错 —— 不合法 HTML 也尽力解析
3. 遇 script 阻塞 —— 脚本阻塞解析（除非 async/defer）
```

```html
<!-- script 阻塞解析 -->
<script src="app.js"></script>

<!-- async：下载完立即执行（不阻塞下载，但执行时阻塞） -->
<script async src="a.js"></script>

<!-- defer：解析完后按顺序执行 -->
<script defer src="b.js"></script>
```

```text
script 的三种加载方式：
普通 —— 阻塞解析，下载+执行都阻塞
async —— 异步下载，下载完立即执行（顺序不定）
defer —— 异步下载，DOM 解析完按顺序执行
```

## CSS Parsing 与 CSSOM

CSS 解析构建 CSSOM（CSS 对象模型），CSS 会阻塞渲染但不阻塞 DOM 构建。

```text
CSS 解析过程：
CSS 字节 → 字符 → Token → 规则 → CSSOM 树

关键特性：
1. CSS 阻塞渲染 —— 未加载完 CSS，页面不渲染（避免闪烁）
2. CSS 不阻塞 DOM 构建 —— HTML 继续解析
3. CSS 阻塞 JS 执行 —— JS 可能查询样式
```

```html
<!-- CSS 阻塞渲染，放 head 尽早加载 -->
<link rel="stylesheet" href="style.css">
```

```text
优化：
1. CSS 尽早加载（放 head）
2. 减少 CSS 体积（未用样式）
3. 关键 CSS 内联
```

## Render Tree 渲染树

DOM 和 CSSOM 结合生成渲染树，只包含**可见**元素。

```text
渲染树构建：
DOM + CSSOM → Render Tree

渲染树特点：
1. 只含可见元素（display:none 的不在树中）
2. 每个节点有计算后的样式
3. 不含 head、script 等非渲染元素
```

```text
注意：
display: none —— 不在渲染树（不占位）
visibility: hidden —— 在渲染树（占位，不可见）
```

## Layout 布局

Layout 计算每个节点的几何信息（位置、尺寸）。

```js
// 触发 Layout 的读写
element.offsetWidth;     // 读布局，可能触发重排
element.style.width = '100px';   // 写，标记需要重排
```

```text
Layout 阶段：
1. 计算每个可见节点的位置和尺寸
2. 产生布局树（Layout Tree）
3. 也叫 Reflow（回流）

触发 Layout 的操作：改尺寸、增删元素、改字体等。
```

## Paint / Raster / Composite

Paint 生成绘制指令，Raster 光栅化为位图，Composite 合成图层。

```text
三个阶段：
Paint（绘制）—— 生成绘制指令（画什么）
Raster（光栅化）—— 把绘制指令转为位图
Composite（合成）—— 把各图层合并为最终画面

性能关键：
Layout/Paint 在主线程，代价高
Composite 在合成线程，代价低
```

```js
// 不同属性触发不同阶段
element.style.width = '100px';      // 触发 Layout + Paint + Composite
element.style.background = 'red';   // 触发 Paint + Composite
element.style.transform = 'translateX(10px)';  // 只触发 Composite（最优）
```

```text
性能启示：
transform/opacity 只触发合成（GPU 加速，最优）
width/height 触发布局 + 绘制 + 合成（最贵）

动画优先用 transform/opacity。
```

## 应用场景实战

### 场景一：优化首屏渲染

```html
<!-- 关键 CSS 内联，非关键 CSS 延迟加载 -->
<style>/* 关键样式 */</style>
<link rel="preload" href="style.css" as="style" onload="this.rel='stylesheet'">
```

### 场景二：避免渲染阻塞

```html
<!-- defer：脚本不阻塞解析 -->
<script defer src="app.js"></script>
```

## 最佳实践与踩坑记录

### 最佳实践

1. CSS 放 head 尽早加载，JS 用 defer/async
2. 动画用 transform/opacity（只触发合成）
3. 减少 Layout 触发（批量读写、用 class 代替直接改 style）
4. 关键资源内联，非关键延迟加载
5. 理解各阶段代价，针对性优化

### 踩坑记录

```text
坑 1：JS 阻塞渲染
结论：script 放 head 且无 defer，页面白屏等待。
原因：脚本阻塞 HTML 解析。
解法：用 defer/async，或脚本放 body 末尾。

坑 2：display:none 与 visibility:hidden 混淆
结论：误以为 visibility:hidden 不在渲染树。
原因：visibility:hidden 仍占位，在渲染树中。
解法：display:none 不占位，visibility:hidden 占位。

坑 3：改 width 触发 Layout 性能差
结论：动画用 width 导致卡顿。
原因：width 触发 Layout + Paint，代价高。
解法：动画用 transform。

坑 4：CSS 阻塞渲染
结论：CSS 加载慢导致白屏。
原因：CSS 阻塞渲染，未加载完不显示。
解法：关键 CSS 内联，非关键异步加载。

坑 5：频繁读写布局
结论：循环里读写布局，性能差。
原因：每次读触发强制同步布局。
解法：批量读、批量写，或缓存布局值。
```
