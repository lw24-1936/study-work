## 概述

Electron 是 GitHub 推出的桌面应用框架，用 HTML/CSS/JS 构建桌面应用，底层封装 Chromium 与 Node.js。VS Code、Slack、Discord 等都基于它。

```text
Electron 的核心特性：
1. Web 技术栈 —— 用 HTML/CSS/JS 写桌面应用
2. 双进程模型 —— 主进程 + 渲染进程
3. 跨平台 —— Windows/macOS/Linux 一套代码
4. 完整 Node 能力 —— 可访问文件系统、系统 API
5. 生态成熟 —— 自动更新、打包、调试工具完善
```

```js
// 主进程 main.js
const { app, BrowserWindow } = require('electron');

app.whenReady().then(() => {
  const win = new BrowserWindow({
    width: 800,
    height: 600,
    webPreferences: {
      preload: `${__dirname}/preload.js`,
    },
  });
  win.loadFile('index.html');
});
```

## Main Process

主进程是应用的入口，负责窗口管理、生命周期、系统级操作。

```text
主进程职责：
1. 创建窗口 —— BrowserWindow
2. 应用生命周期 —— app 的 ready/window-all-closed 等
3. 系统能力 —— 菜单、托盘、剪贴板、原生对话框
4. 只有一个主进程
```

```js
const { app, BrowserWindow, dialog } = require('electron');

let mainWindow = null;

app.on('ready', () => {
  mainWindow = new BrowserWindow({ width: 800, height: 600 });
  mainWindow.loadURL('https://example.com');
});

app.on('window-all-closed', () => {
  if (process.platform !== 'darwin') app.quit();
});

// 原生对话框
dialog.showMessageBox(mainWindow, {
  type: 'info',
  message: '保存成功',
});
```

## Renderer Process

渲染进程负责页面 UI，每个窗口对应一个渲染进程。

```text
渲染进程职责：
1. 渲染页面 —— HTML/CSS/JS
2. 每个 BrowserWindow 一个渲染进程
3. 默认不能直接访问 Node，需通过 Preload/IPC
4. 崩溃不影响主进程（独立进程）
```

```js
// 渲染进程 index.html 中的脚本
// 通过 window.api（preload 暴露）调用主进程能力
document.getElementById('btn').addEventListener('click', async () => {
  const version = await window.api.getVersion();
  document.getElementById('ver').textContent = version;
});
```

## Preload

Preload 是在渲染进程加载页面之前执行的脚本，是渲染进程与主进程之间的安全桥梁。

```text
Preload 特点：
1. 先于页面加载执行
2. 可访问 Node 与 Electron 受限 API
3. 通过 contextBridge 向页面暴露安全接口
4. 是暴露主进程能力的唯一推荐通道
```

```js
// preload.js
const { contextBridge, ipcRenderer } = require('electron');

contextBridge.exposeInMainWorld('api', {
  getVersion: () => ipcRenderer.invoke('app:version'),
  openFile: (path) => ipcRenderer.invoke('file:open', path),
});
```

## IPC

IPC 是主进程与渲染进程之间通信的机制。

```text
IPC 通信方式：
1. invoke/handle —— 请求-响应（推荐，Promise）
2. send/on —— 单向消息（事件式）
3. 主进程 → 渲染进程 —— 通过 mainWindow.webContents.send
```

```js
// 主进程
const { ipcMain, app } = require('electron');

ipcMain.handle('app:version', () => {
  return app.getVersion();
});

ipcMain.handle('file:open', async (event, path) => {
  const fs = require('fs').promises;
  return await fs.readFile(path, 'utf-8');
});
```

```js
// 渲染进程（通过 preload 暴露的 api）
const version = await window.api.getVersion();
const content = await window.api.openFile('/tmp/note.txt');
```

```text
推荐做法：
用 invoke/handle（双向、有返回值）而非 send/on，
前者基于 Promise，代码更清晰，错误更好处理。
```

## Context Isolation

Context Isolation 隔离渲染进程的预加载脚本与页面 JS 的执行环境。

```text
Context Isolation 作用：
1. 隔离 —— preload 与页面 JS 的上下文（world）分离
2. 安全 —— 页面 JS 无法直接访问 preload 的 Node 对象
3. 数据暴露 —— 只能通过 contextBridge 显式暴露
4. 默认开启 —— 强烈建议保持开启
```

```js
// 开启 contextIsolation（默认 true）
const path = require('path');
new BrowserWindow({
  webPreferences: {
    contextIsolation: true,
    nodeIntegration: false,
    sandbox: true,
    preload: path.join(__dirname, 'preload.js'),
  },
});
```

```text
对比：
nodeIntegration: true + contextIsolation: false —— 页面直接能 require Node，危险
contextIsolation: true —— 页面只能拿 preload 显式暴露的接口，安全
```

## 应用场景实战

### 场景一：桌面笔记应用

```js
// 主进程：保存文件
const fs = require('fs').promises;
ipcMain.handle('note:save', async (event, { path, content }) => {
  await fs.writeFile(path, content, 'utf-8');
  return { ok: true };
});
```

```js
// preload 暴露
contextBridge.exposeInMainWorld('note', {
  save: (data) => ipcRenderer.invoke('note:save', data),
});
```

```js
// 渲染进程调用
await window.note.save({ path: '/tmp/a.md', content: 'hello' });
```

### 场景二：读取系统信息

```js
// 主进程
ipcMain.handle('sys:info', () => {
  return {
    platform: process.platform,
    arch: process.arch,
    version: process.versions.electron,
  };
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 保持 contextIsolation: true、nodeIntegration: false
2. 通信用 invoke/handle，不用 send/on
3. 能力通过 preload 的 contextBridge 白名单暴露
4. 主进程只管系统，渲染进程只管 UI
5. 渲染进程不要直接 require Node，走 IPC

### 踩坑记录

```text
坑 1：渲染进程 require 报 undefined
结论：页面里 require('fs') 报错。
原因：nodeIntegration 默认关闭，页面无 Node 环境。
解法：通过 preload + contextBridge 暴露，或走 IPC。

坑 2：contextBridge 暴露对象后仍拿不到
结论：window.api 是 undefined。
原因：preload 路径错误，或 contextIsolation 未正确配置。
解法：检查 preload 绝对路径，确认 contextBridge 调用。

坑 3：invoke 与 handle 不匹配
结论：invoke 后一直 pending 或无响应。
原因：主进程用 ipcMain.on 而非 ipcMain.handle 接收。
解法：invoke 配 handle，send 配 on，别混用。

坑 4：打包后路径错误
结论：开发正常，打包后 preload/资源找不到。
原因：相对路径在打包后变化。
解法：用 path.join(__dirname, ...) 或 app.getAppPath()。

坑 5：窗口销毁后内存泄漏
结论：反复开关窗口内存上涨。
原因：监听器未清理、窗口引用未释放。
解法：窗口 close 时解绑监听，置空引用。
```
