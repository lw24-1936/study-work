## 概述

订阅消息是微信小程序向用户主动下发通知的核心能力：用户在小程序内通过授权弹窗或订阅按钮明确同意订阅某个模板后，服务端便可在符合条件时向该用户推送一条服务通知，消息出现在微信「服务通知」中。与旧版模板消息不同，订阅消息强调「用户主动订阅、一次订阅一次下发」，从机制上把触达权交还给用户，杜绝了开发者的随意群发。

订阅消息的完整链路是「公众平台申请模板 -> 小程序端引导用户订阅 -> 服务端调用接口下发」，涉及模板、订阅授权、下发三个环节。本篇章讲解订阅消息的类型划分、额度机制、模板申请与选用规则以及数据形态与限制，为后续小程序端订阅（11.2）与服务端下发（11.3）打下基础。

```text
本章核心要点：
1. 三种类型 —— 一次性订阅消息 / 长期订阅消息 / 设备订阅消息
2. 额度规则 —— 一次性订阅每次用户同意，仅可下发 1 条消息
3. 模板体系 —— 订阅消息必须使用公众平台审核通过的模板，带模板 ID
4. 废弃更替 —— 旧模板消息接口已废弃，新小程序只能使用订阅消息
5. 内容约束 —— 下发内容、跳转页面、频率均受平台规则限制
6. 授权凭证 —— 用户订阅关系是下发的唯一凭证，无额度下发报 43101
```

## 订阅消息类型与模板消息的演进

微信的消息触达能力经历了从「模板消息」到「订阅消息」的演进。旧版模板消息（templateMessage）允许服务端在用户产生交互行为后 48 小时内主动下发模板消息，开发者可以在用户没有明确同意的情况下持续触达，容易造成骚扰。微信从 2020 年初开始分批下线模板消息：新注册的小程序无法使用，存量小程序逐步灰度下线，最终全部停用。订阅消息取代模板消息，成为小程序主动通知的唯一官方通道。

订阅消息的核心设计原则是「订阅即授权、授权即限额」：用户必须在小程序内通过 wx.requestSubscribeMessage 或订阅按钮明确同意订阅某个模板，服务端才获得下发权限；且每次同意最多只对应一次下发（一次性订阅）。这一设计把「通知权」从开发者手中交还给用户，从机制上遏制了垃圾消息。凡是在网上搜到「模板消息」「formId」「模板消息群发」等旧资料，都要按已废弃处理。

```text
模板消息 vs 订阅消息：
1. 授权方式 —— 模板消息：用户产生交互即可发（隐式授权）；订阅消息：必须显式订阅
2. 下发次数 —— 模板消息：一次交互 48 小时内可发 1 条；订阅消息：一次订阅发 1 条（一次性）
3. 有效期 —— 模板消息：交互后 48 小时；订阅消息：订阅即生效，无固定有效期，用掉即失效
4. 消息位置 —— 模板消息：服务通知/订阅号消息；订阅消息：统一进入微信「服务通知」
5. 平台态度 —— 模板消息：已废弃；订阅消息：官方唯一主动通知通道
6. 数据能力 —— 订阅消息支持跳转页面与 miniprogram_state（开发版/体验版/正式版），能力更完整
```

当前订阅消息按授权与使用方式分为三类：一次性订阅消息、长期订阅消息、设备订阅消息。三类消息共用同一套「模板 + 下发接口」，区别只在授权方式与下发频次上。绝大多数业务（订单、物流、预约、活动）使用的都是一次性订阅消息。

```text
订阅消息三种类型：
1. 一次性订阅消息 —— 用户每次同意订阅，服务端可下发 1 条；适用于订单状态、发货、活动等低频通知
2. 长期订阅消息 —— 用户同意一次，长期有效可多次下发；仅政务、医疗、交通、金融等特定类目可申请
3. 设备订阅消息 —— 面向智能硬件场景，用户授权后设备状态变化可多次下发；需接入微信硬件平台
```

三类消息的选择不需要纠结：业务是「用户主动参与的交易或服务流程」（订单、预约、报名），一律使用一次性订阅；业务是政务民生服务且资质齐全，再评估长期订阅；业务有智能硬件设备，走设备订阅。判断标准是下发的消息是否对应「用户明确期待的一次性反馈」，是则一次性订阅完全够用，不要把简单问题复杂化。

```text
场景 vs 类型速查：
1. 电商订单/物流 —— 一次性订阅（支付、发货、签收各 1 条，每次需重新订阅）
2. 预约服务提醒 —— 一次性订阅（确认 + 开始前提醒，各需 1 次订阅）
3. 政务办事进度 —— 长期订阅（多次进度推送，需资质）
4. 智能硬件状态 —— 设备订阅（绑定设备后的状态通知）
5. 会员到期提醒 —— 一次性订阅（每年到期前引导重新订阅）
6. 营销活动 —— 谨慎使用，仅交易场景附加，单独立模板控制频次
```

## 一次性订阅消息与额度机制

一次性订阅消息是绝大多数小程序使用的类型，规则一句话概括：用户每同意一次订阅，服务端就获得 1 条下发额度；下发成功后额度消耗，未下发则额度一直保留。用户在一次授权弹窗中可以同时勾选多个模板，每个模板各获得 1 条额度；也可以对同一模板连续同意最多 2 次，获得 2 条额度，之后该模板短期内不会再弹出授权框。

额度与「用户 openid + 模板」绑定：换一个小程序、换一个模板都不通用，服务端不能把 A 模板的授权拿去发 B 模板。下发失败（如用户拒收 43101）时额度不消耗，可以重试；下发成功（errcode 为 0）后该条额度即被消耗，需要再次下发时必须让用户重新订阅。额度本身没有有效期，订阅后一直不消费会长期保留。

```text
一次性订阅额度机制：
1. 授权粒度 —— 一个用户对一个模板的一次同意 = 1 条下发额度
2. 批量授权 —— 一次调用可传多个 tmplIds，每个模板各得 1 条额度
3. 连续授权 —— 同一模板最多连续同意 2 次（2 条额度），之后需间隔再弹
4. 额度保留 —— 订阅后未下发，额度长期保留，不会被自动清除
5. 额度消耗 —— 下发成功后立即消耗 1 条；失败（43101 拒收等）不消耗
6. 重新订阅 —— 额度用完后需再次引导用户订阅才能继续下发
```

下面是一个演示额度管理思路的 JS 代码：小程序端本地记录「每个模板还剩几次下发额度」，服务端下发成功后通知前端扣减，额度不足时引导重新订阅。真实额度由微信服务端维护，本地记录只是为了给前端展示与引导提供依据：

```javascript
// utils/subscribeQuota.js —— 本地模拟订阅额度管理
// 说明：真实额度由微信服务端维护，本地记录用于展示与引导重订阅

const QUOTA_KEY = 'subscribe_quota_map'; // { templateId: 剩余次数 }

function getQuotaMap() {
  return wx.getStorageSync(QUOTA_KEY) || {};
}

// 用户每次成功订阅后调用：对应模板额度 +1（模拟微信侧额度）
function recordSubscribe(templateId) {
  const map = getQuotaMap();
  map[templateId] = (map[templateId] || 0) + 1;
  wx.setStorageSync(QUOTA_KEY, map);
}

// 服务端每次下发成功后调用：额度 -1
function recordSent(templateId) {
  const map = getQuotaMap();
  if (map[templateId] > 0) {
    map[templateId] -= 1;
    wx.setStorageSync(QUOTA_KEY, map);
  }
}

// 下发前检查：额度不足返回 false，调用方据此引导用户重新订阅
function hasQuota(templateId) {
  return (getQuotaMap()[templateId] || 0) > 0;
}

module.exports = {
  recordSubscribe,
  recordSent,
  hasQuota
};
```

同一个订阅弹窗在短时间内的展示次数也需要控制：同一模板连续同意上限为 2 次，拒绝后 7 天内系统不再弹窗。业务侧配合做「本地冷却」记录，避免在用户刚拒绝后再次触发弹窗请求造成静默失败。下面的工具函数把订阅冷却时间记录在本地缓存：

```javascript
// utils/subscribeCooldown.js —— 订阅弹窗本地冷却
const COOLDOWN_KEY = 'subscribe_cooldown'; // { templateId: 上次弹窗时间戳 }
const COOLDOWN_MS = 7 * 24 * 60 * 60 * 1000; // 7 天冷却期

function canShow(templateId) {
  const map = wx.getStorageSync(COOLDOWN_KEY) || {};
  const last = map[templateId] || 0;
  return Date.now() - last >= COOLDOWN_MS;
}

function markShown(templateId) {
  const map = wx.getStorageSync(COOLDOWN_KEY) || {};
  map[templateId] = Date.now();
  wx.setStorageSync(COOLDOWN_KEY, map);
}

module.exports = { canShow, markShown };
```

弹窗前先调 canShow 判断，冷却期内直接跳过弹窗，等用户下次自然进入业务流程（如再次下单）时再尝试。注意本地冷却只是业务侧的辅助，微信服务端的 7 天限制是硬性的，本地记录的意义在于避免发起注定失败的调用、以及让「何时再次引导」变得可预期。

额度是订阅消息体系中最容易理解错的概念。常见的误解包括：以为订阅一次可以发多条、以为用户点过授权弹窗里的某个模板就永远能发、以为服务端可以查询到剩余额度。实际上小程序端没有任何 API 能直接查询微信侧的剩余额度，只能通过「本地记录 + 下发错误码（43101）」间接判断。设计业务时要把「额度可能不足」当作常态，提前准备重新订阅的入口。

## 长期订阅与设备订阅

长期订阅消息指用户同意一次后，服务端可以长期多次下发，不受「一次一条」限制。它的申请门槛极高：仅面向政务民生、医疗、交通、金融、教育等公共服务类目开放，普通电商、工具类小程序无法申请。申请长期订阅模板需要在公众平台提交类目资质与业务必要性说明（如就诊提醒、政务办事进度通知），由微信审核是否授予长期订阅权限。绝大多数商业小程序用不到长期订阅，规划时不要把它当默认方案。

设备订阅消息（Device Subscribe Message）面向物联网与智能硬件场景：用户通过小程序绑定硬件设备后，设备状态变化（如空气净化器滤芯到期、门锁报警、洗衣机完成）可以通过订阅消息通知用户。它需要先接入微信硬件平台、完成设备与用户账号的绑定，模板同样在公众平台申请。设备订阅消息的授权次数与下发策略与一次性订阅类似，但绑定设备后用户可以多次授权，适合高频设备通知场景。

```text
长期订阅 vs 设备订阅：
1. 长期订阅 —— 一次同意长期有效、可多次下发；限政务/医疗/交通/金融/教育等公共服务类目
2. 长期订阅门槛 —— 需在公众平台提交类目资质与业务说明，审核严格，个人主体基本无法申请
3. 设备订阅 —— 面向智能硬件，设备状态变化通知；需接入微信硬件平台并完成设备绑定
4. 设备订阅形态 —— 用户订阅时通常携带设备信息，通知内容与具体设备状态绑定
5. 共同点 —— 都要使用公众平台审核通过的模板，都要服务端 access_token 下发
6. 选型建议 —— 普通业务一律用一次性订阅；确属公共服务再评估长期订阅；硬件业务走设备订阅
```

长期订阅的申请材料一般包括：小程序主体资质（政务/医疗机构需对应证照）、业务说明文档（描述通知场景、发送频率与必要性）、模板草稿（标题与关键词）。平台审核通过后会在「订阅消息 - 长期订阅」列表展示可用模板。审核周期不定（数天到数周），业务规划要预留时间；审核被拒后可以补充材料重新提交，但不要重复提交一模一样的申请，平台会提示差异点。

两类特殊订阅共同的注意点：长期订阅虽然「一次授权长期可发」，但微信同样要求内容与用户利益相关，滥用会被收回权限；设备订阅的消息必须与设备状态真实对应，不能把设备订阅当成普通群发通道。两类模板都计入小程序的模板配置数量，申请前先确认类目资质是否具备。

## 模板申请与选用

订阅消息不能像短信那样自拟文案随意发送，必须使用微信公众平台审核通过的模板。申请入口在公众平台「功能 - 订阅消息 - 公共模板库」：按行业分类浏览公共模板（如电商-物流、医疗-挂号、教育-上课提醒），选择与业务匹配的模板点击「选用」即可；如果公共模板库没有合适模板，可以「申请自定义模板」，提交模板标题与关键词，由平台审核（一般 1-3 个工作日）。

模板由「标题 + 关键词」组成。一个模板必须选择 2-5 个关键词，每个关键词必须来自平台的标准词库（如「订单号」「商品名称」「发货状态」），不能自造关键词。选用模板后系统生成模板 ID（形如 qweR1tGXnQmL9y7j_3xWpA），模板 ID 是下发的核心参数：小程序端 wx.requestSubscribeMessage 用它引导订阅，服务端 subscribeMessage.send 用它指定下发内容格式。每个小程序可同时配置的一次性订阅消息模板数量有限（约 50 个），长期订阅模板单独计算。

```text
模板申请与选用要点：
1. 入口 —— 公众平台「功能 - 订阅消息」，分公共模板库与自定义模板申请
2. 选用流程 —— 按行业筛选公共模板 -> 核对标题与关键词 -> 点击选用 -> 获得模板 ID
3. 关键词规则 —— 每个模板选 2-5 个关键词，关键词必须来自平台标准词库
4. 模板 ID —— 模板的唯一标识，前后端都必须引用，建议存配置中心统一管理
5. 数量上限 —— 一个小程序可配置的订阅消息模板数量有限（一次性模板 50 个左右）
6. 审核要求 —— 自定义模板标题不能含营销词，内容需与实际下发内容一致
```

关键词的选择直接决定下发内容的可填字段。比如电商「发货通知」模板，如果选了「商品名称」「订单号」「发货状态」三个关键词，那么下发时 data 里只能填这三个字段，每个字段对应模板中的一个 {{xxx.DATA}} 占位符，键名是系统分配的顺序编号（thing1、number2、phrase3）：

```json
{
  "touser": "o6_bmjrPTlm6_2sgVt7hMZOPfL2M",
  "template_id": "qweR1tGXnQmL9y7j_3xWpA",
  "page": "pages/order/detail?id=20260820001",
  "data": {
    "thing1": { "value": "小程序的 T 恤" },
    "number2": { "value": 20260820001 },
    "phrase3": { "value": "已发货" }
  }
}
```

模板选用后先用 curl 快速验证接口与模板参数是否匹配（用体验版环境的真实 openid 与后台获取的 access_token）：

```bash
# 用 curl 模拟下发，验证模板参数
curl -s -X POST \
  "https://api.weixin.qq.com/cgi-bin/message/subscribe/send?access_token=ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "touser": "o6_bmjrPTlm6_2sgVt7hMZOPfL2M",
    "template_id": "qweR1tGXnQmL9y7j_3xWpA",
    "page": "pages/order/detail?id=20260820001",
    "miniprogram_state": "trial",
    "data": {
      "thing1": { "value": "小程序的 T 恤" },
      "number2": { "value": 20260820001 },
      "phrase3": { "value": "已发货" }
    }
  }'
# 期望返回：{"errcode":0,"errmsg":"ok"}
```

curl 调试可以快速发现键名写错、字段超长等参数问题，比在代码里反复试错效率高得多。测试时把 miniprogram_state 设为 trial，消息会投递到体验版环境，真机上即可看到真实卡片效果。

模板选用后的管理动作：把模板 ID 登记到后台配置（application.yml 或配置中心），命名如 template.order.shipped，避免前后端各写各的字符串；模板标题与关键词一旦选用，后续想改关键词需要重新选用或申请模板，因此申请前先在后台模拟一遍下发内容，确认字段满足业务需求。模板数量紧张时优先保留高频模板，把低频场景合并进一个模板。

## 订阅消息的数据形态与限制

订阅消息下发到用户微信「服务通知」后，展示为一条标准卡片消息：最上方是模板标题（如「订单发货通知」），中间是各关键词的「名称：值」行，下方是「进入小程序查看」入口，点击后按 page 参数跳转到小程序指定页面（可带 query 参数）。因此下发的数据形态包含两部分：data 字段决定卡片内容，page 字段决定点击去向。

data 字段的每个键对应模板中的一个关键词占位符（如 {{thing1.DATA}}、{{number2.DATA}}、{{phrase3.DATA}}、{{time4.DATE}}、{{amount5.DATA}}），键名是申请模板时系统分配的顺序编号。不同关键词类型对 value 有格式与长度限制：thing 类型（事物）限 20 个汉字以内，phrase 类型（短语）限 5 个汉字，number 类型必须是数字，time 类型为时间戳（秒级），amount 类型为金额（单位分，最多两位小数）。字段值超长或类型不符，接口直接返回 47003 参数错误。

```text
订阅消息数据形态：
1. 卡片结构 —— 标题 + 关键词行（名称：值）+ 进入小程序入口
2. data 键名 —— 模板关键词编号，如 thing1 / number2 / phrase3 / time4 / amount5
3. 占位符 —— 服务端下发时用 {{thing1.DATA}} 形式对应模板中的关键词
4. page 参数 —— 点击消息跳转的小程序页面路径，可携带 query（如 pages/order/detail?id=xx）
5. 字段限制 —— thing 20 字 / phrase 5 字 / number 数字 / time 时间戳 / amount 金额（分）
6. 违规后果 —— 超长、错类型、营销内容会导致 47003 或模板被封禁
```

订阅消息的限制包括频率限制、内容规范与类目限制。频率上，同一用户同一模板的下发频次受额度天然约束（一次订阅一条）；接口本身有调用频率限制（access_token 获取每日 2000 次，send 接口超出限额返回 45009）。内容上，下发文案必须与模板申请时的用途一致，禁止营销、广告、诱导分享等违规内容，违规会被封禁模板甚至整个订阅消息能力。类目上，模板申请受小程序服务类目约束，类目之外的模板无法选用。

```text
订阅消息限制清单：
1. 频率限制 —— 一次性订阅受额度限制；接口调用受平台频率限制（超限返回 45009 等）
2. 内容规范 —— 禁止广告营销、诱导分享、诈骗色情等内容，违规封模板
3. 类目限制 —— 模板必须与小程序服务类目匹配，跨类目模板无法选用
4. 时间限制 —— 无固定下发时段限制，但深夜下发体验差、容易被用户拒收
5. 数量限制 —— 可配置模板数量上限，长期订阅模板单独限额
6. 场景限制 —— 必须由用户主动触发订阅（操作后弹窗），禁止进入小程序就强制弹订阅
```

服务端组装 data 时建议统一走一个字段处理工具，把长度校验与截断集中在一处，避免每个业务方各自处理、各自踩坑：

```java
// SubscribeDataBuilder.java —— data 字段组装与校验
import java.util.Map;

public class SubscribeDataBuilder {

    /** thing 类型：限 20 个汉字，超长截断 */
    public static Map<String, Object> thing(int index, String value) {
        return Map.of("thing" + index, Map.of("value", truncate(value, 20)));
    }

    /** number 类型：必须为数字 */
    public static Map<String, Object> number(int index, long value) {
        return Map.of("number" + index, Map.of("value", value));
    }

    /** phrase 类型：限 5 个汉字，超长截断 */
    public static Map<String, Object> phrase(int index, String value) {
        return Map.of("phrase" + index, Map.of("value", truncate(value, 5)));
    }

    /** time 类型：秒级时间戳 */
    public static Map<String, Object> time(int index, long timestampSeconds) {
        return Map.of("time" + index, Map.of("value", timestampSeconds));
    }

    /** amount 类型：金额，单位分 */
    public static Map<String, Object> amount(int index, long amountFen) {
        return Map.of("amount" + index, Map.of("value", amountFen));
    }

    private static String truncate(String s, int max) {
        if (s == null) {
            return "";
        }
        return s.length() <= max ? s : s.substring(0, max);
    }
}
```

关键词编号与类型的对应关系以公众平台模板详情页为准，不同模板的编号顺序不同，不要复用其他模板的编号。工具类把「编号 + 类型 + 截断」封装在一起后，业务代码只需要一行 SubscribeDataBuilder.thing(1, goodsName)，参数错误率会显著下降。

数据形态设计上的一个常见诉求是「消息里放更多信息」。受 thing/phrase 长度限制，正文放不下的信息有两个处理方式：一是把完整信息放到 page 跳转的落地页里，消息正文只放摘要；二是把多个关键词合理分配到不同字段（如商品名称用 thing、规格用 phrase）。切勿通过截断字符串的方式硬塞，超长会被 47003 直接拒绝。

## 应用场景实战

### 场景一：在公众平台申请并选用一个订阅消息模板

以电商小程序申请「订单发货通知」模板为例，完整流程：

```text
步骤：
1. 登录 mp.weixin.qq.com，进入「功能 - 订阅消息」
2. 在公共模板库按行业筛选「电商 - 物流」，搜索「发货通知」
3. 对比候选模板的关键词组合，选择包含「商品名称、订单号、发货状态」的模板
4. 点击「选用」，记录模板 ID（形如 qweR1tGXnQmL9y7j_3xWpA）
5. 记录模板关键词的顺序编号（thing1 商品名称、number2 订单号、phrase3 发货状态）
6. 把模板 ID 登记到后台配置中心，并同步给小程序端配置文件
7. 用公众平台调试工具或直接调 subscribeMessage.send 模拟下发一次，核对卡片样式
8. 确认字段与文案无误后，把模板 ID 写入前后端代码并提交
```

对应的后台配置登记（application.yml 片段）：

```yaml
# application.yml —— 订阅消息模板配置
wechat:
  app-id: wx1234567890abcdef
  app-secret: ${WECHAT_APP_SECRET}
  subscribe-templates:
    order-paid: qweR1tGXnQmL9y7j_3xWpA   # 支付成功通知
    order-shipped: xYZp2uHnRoL8z8k_4yQbB  # 订单发货通知
    order-remind: mNq3vIjTpS7a9l_5zWcC    # 物流签收提醒
```

模板 ID 一旦写入代码，后续更换模板需要改配置并重新发版，因此把模板 ID 放到配置中心（Spring Cloud Config / Nacos）或环境变量里，生产环境可以热切换而不需要重新编译。

### 场景二：结合支付流程设计订阅消息选型

把「支付成功提醒 + 发货通知」设计为两个模板，并规划额度分配：

```text
选型步骤：
1. 支付成功提醒 —— 选用「支付成功通知」模板（thing 订单号 + amount 实付金额）
2. 发货通知 —— 选用「订单发货通知」模板（thing 商品名称 + number 订单号 + phrase 发货状态）
3. 订阅时机 —— 支付成功页弹一次订阅（可同时勾选两个模板，一次弹窗各得 1 条额度）
4. 下发时机 —— 支付成功提醒在支付回调后立即下发；发货通知在订单发货时下发
5. 额度核对 —— 用户若只勾选了一个模板，则另一个模板额度为 0，需要后续再次引导订阅
6. 兜底策略 —— 额度不足时在订单详情页展示「提醒我发货」按钮，用户点击再订阅
```

对应的小程序端订阅调用示意（11.2 会详解）：

```javascript
// pages/pay/result.js 片段 —— 支付成功页引导订阅两个模板
wx.requestSubscribeMessage({
  tmplIds: [
    'qweR1tGXnQmL9y7j_3xWpA', // 支付成功通知模板 ID
    'xYZp2uHnRoL8z8k_4yQbB'   // 订单发货通知模板 ID
  ],
  success(res) {
    const payAccepted = res['qweR1tGXnQmL9y7j_3xWpA'] === 'accept';
    const shipAccepted = res['xYZp2uHnRoL8z8k_4yQbB'] === 'accept';
    console.log('支付提醒订阅：', payAccepted, '发货提醒订阅：', shipAccepted);
    // 把订阅结果上报后台，后台据此记录用户订阅状态（11.4 合规要求会讲）
    wx.request({
      url: 'https://api.example.com/api/subscribe/record',
      method: 'POST',
      data: {
        payAccepted: payAccepted,
        shipAccepted: shipAccepted
      }
    });
  }
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 模板关键词在选择前先在公众平台调试工具里模拟一遍下发内容，确认 thing/phrase 长度限制满足业务文案，避免上线后才发现字段超长
2. 模板 ID 统一登记在后台配置中心并命名规范（如 template.order.shipped），前后端引用同一配置，禁止在代码里散落裸字符串
3. 业务规划时默认使用一次性订阅消息，长期订阅只在确属公共服务类目时再评估申请
4. 把「订阅动作」绑定到具体业务动作上（支付完成、预约提交后立即弹），比单独设置订阅页转化率高得多
5. 订阅弹窗一次最多勾选 2-3 个模板，模板过多会明显降低用户接受率，优先推送转化率最高的模板
6. 每次下发前先判断用户对当前模板是否还有额度（本地记录 + 下发错误码兜底），额度不足提前引导重订阅
7. 关注微信公众平台订阅消息政策变化（模板下线、类目调整），模板被下线前平台会提前通知，及时更换模板
8. 下发文案与模板申请用途必须一致，营销类文案宁可不用也不要硬塞，模板封禁会波及整个订阅消息能力

### 踩坑记录

```text
坑 1：还在用旧模板消息接口，小程序无法收到消息
结论：新注册小程序调用模板消息接口直接报错，用户收不到任何通知。
原因：旧模板消息能力已于 2020 年起分批下线，新小程序完全不支持，接口已废弃。
解法：迁移到订阅消息：公众平台选用订阅消息模板，前端 wx.requestSubscribeMessage 引导订阅，服务端改调 subscribeMessage.send。

坑 2：把长期订阅当成默认方案，申请被驳回
结论：申请长期订阅模板被平台驳回，提示类目不符或资质不足。
原因：长期订阅仅向政务、医疗、交通、金融、教育等公共服务类目开放，普通电商/工具类小程序没有申请资格。
解法：普通业务改用一次性订阅；确属公共服务类目的，先确认小程序类目与资质材料齐全再申请。

坑 3：自定义模板关键词选错，上线后无法下发想要的内容
结论：模板选用后发现缺少「发票抬头」等字段，下发内容无法满足业务。
原因：关键词必须在选模板时确定，模板一旦选用关键词组合不可修改，只能重新申请新模板。
解法：申请前把业务需要的所有字段列出来逐项对照模板关键词；选错就重新选用/申请模板并更新模板 ID 配置。

坑 4：模板申请含营销词被拒
结论：自定义模板申请被驳回，提示标题含营销推广内容。
原因：平台禁止营销类模板，标题含「限时」「促销」「点击领取」等词会被拒。
解法：标题用中性业务描述（如「订单发货通知」）；营销触达改用活动页跳转或评估其他合规触达方式。

坑 5：data 字段超长导致 47003 参数错误
结论：下发报 47003，提示 data 参数格式错误，消息发不出去。
原因：thing 类型限 20 个汉字、phrase 类型限 5 个汉字，商品名/活动名超长。
解法：下发前对字段做长度截断与校验；超长内容放落地页里，消息正文只放摘要。

坑 6：用户没有任何订阅记录，服务端硬发报 43101
结论：服务端下发报 43101「用户拒收」，但用户并没有主动拒收。
原因：用户从未订阅该模板（或额度已用完），服务端没有下发权限。
解法：把 43101 当作「无额度」处理，记录到用户订阅状态表，触发前端引导重新订阅；不要反复硬发。

坑 7：模板被平台下线，所有下发突然失败
结论：某天开始下发全部失败，查询发现模板已下线。
原因：平台会清理使用率低或违规的模板，模板下线后模板 ID 失效。
解法：关注公众平台模板下线通知，提前选用替代模板并切换模板 ID；服务端模板 ID 配置化，支持热切换。
```
