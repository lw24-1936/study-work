## 概述

订阅消息的工程实现只是第一步，真正决定业务价值的是运营层面的设计：什么时机发、发什么内容、用户拒绝了怎么办、如何衡量触达效果、如何满足合规要求。本章把前三篇（11.1 基础、11.2 小程序端订阅、11.3 服务端下发）的能力串成一套可落地的实践方案。

实践的四个支柱：发送时机设计（把消息绑定到业务关键节点）、触达率优化（内容相关度与频率克制）、退订处理与降级方案（用户拒绝后的替代触达通道）、数据统计与合规（用数据驱动优化、用记录自证合规）。本章以电商与预约两个典型业务为主线，给出完整的消息运营体系设计。

```text
本章核心要点：
1. 时机设计 —— 支付成功、发货、预约提醒等业务节点即发送时机
2. 触达优化 —— 内容个性化 + 频率克制，提升打开率而非发送量
3. 退订降级 —— 用户拒绝后用站内信/短信等通道承接关键通知
4. 数据统计 —— 订阅转化率、发送成功率、打开率三张表
5. 合规要求 —— 授权记录落库、隐私政策说明、提供关闭入口
6. 体系闭环 —— 订阅 -> 下发 -> 统计 -> 优化 -> 再订阅
```

## 发送时机设计

订阅消息的本质是「业务事件驱动的通知」，发送时机就是业务事件发生的时刻。设计原则是消息必须与用户最近的某个动作或状态强相关：用户刚付了钱，期待发货进度；用户刚预约了服务，期待开始提醒；用户刚提交了报名，期待审核结果。时机错位的消息（如用户付款后收到毫不相关的促销通知）会直接消耗信任，导致后续订阅被拒绝。

典型业务节点的时机设计：

```text
典型发送时机：
1. 订单支付成功 —— 支付回调后立即下发，通知支付结果与预计发货时间
2. 商品发货 —— 仓库发货动作触发，通知物流单号与承运商
3. 物流签收 —— 物流状态变更为已签收后下发，引导评价与复购
4. 预约开始前 —— 预约时间前 1-2 小时提醒，降低爽约率
5. 活动报名成功 —— 报名成功后立即下发，附活动开始时间
6. 审核结果通知 —— 审核完成时下发，用户等待周期内最期待的消息
```

发送时机设计还要考虑「延迟窗口」：支付成功通知在回调后立即发；发货通知在发货动作确认后发；预约提醒则要精确到开始前 1-2 小时（过早提醒用户会遗忘，过晚提醒失去准备时间）。批量业务（如每日活动开始提醒）用定时任务扫描到期记录统一触发，单点业务（支付、发货）用事件驱动即时触发。

```java
// RemindTimeCalculator.java —— 提醒时机计算
import java.time.DayOfWeek;
import java.time.LocalDateTime;

public class RemindTimeCalculator {

    /**
     * 计算预约提醒的下发时间：开始前 2 小时。
     * 若开始时间距离现在不足 2 小时，则立即下发。
     */
    public static LocalDateTime remindTime(LocalDateTime startTime, LocalDateTime now) {
        LocalDateTime planned = startTime.minusHours(2);
        return planned.isAfter(now) ? planned : now;
    }

    /**
     * 判断是否在合适的下发时段（早 8 点 - 晚 21 点）。
     * 深夜下发体验差，且容易触发用户拒收。
     */
    public static boolean inSendWindow(LocalDateTime time) {
        int hour = time.getHour();
        return hour >= 8 && hour < 21;
    }

    /**
     * 工作日/休息日策略：活动类提醒在休息日效果更好。
     */
    public static boolean isWeekend(LocalDateTime time) {
        DayOfWeek day = time.getDayOfWeek();
        return day == DayOfWeek.SATURDAY || day == DayOfWeek.SUNDAY;
    }
}
```

时机设计的另一个要点是「与业务状态一致」：订单已取消就不发发货通知、退款完成就不发支付成功通知、预约改期后重新计算提醒时间。消息与业务状态的错位（用户收到已取消订单的发货提醒）是用户拒收订阅、投诉举报的最常见原因，发送前必须校验业务状态。

## 触达率优化

触达率优化的目标不是「发得更多」，而是「每一条都被看到、被点击」。订阅消息的打开率与三个因素强相关：内容相关度（这条消息跟我有什么关系）、发送频率（是不是又在骚扰我）、文案质量（一眼能否看懂价值）。相关度是第一位的：把模板关键词填上用户的真实数据（订单号、商品名、具体时间），比通用文案的打开率高出一个量级。

发送频率的克制是长期运营的生存线。建议的节奏：交易类消息（支付、发货、签收）随业务事件自然发生，本身低频，不需要额外限制；营销/活动类消息单用户每周不超过 1 条；同一用户每天收到订阅消息不超过 2 条。超频的代价是用户勾选「不再询问」甚至举报，一旦 ban 掉，后续所有触达通道都关闭。

```text
触达率优化清单：
1. 内容个性化 —— 消息里带订单号、商品名、时间等真实数据，拒绝群发式文案
2. 频率克制 —— 营销类单用户每周 ≤ 1 条，全量每天 ≤ 2 条
3. 时段选择 —— 早 8 点 - 晚 21 点下发，避开深夜与午休
4. 文案精简 —— thing/phrase 字段有限，用最少的字讲清价值
5. 用户分层 —— 高活跃用户多发业务通知，沉默用户只发关键通知
6. 打开率驱动 —— 持续观察打开率，打开率低的模板改文案或换时机
```

用户分层是进阶做法：按最近活跃时间与历史行为把用户分为核心用户、普通用户、沉默用户，核心用户享受完整通知（含营销活动），沉默用户只发交易关键通知（支付、退款、重要状态变化），避免用营销消息把沉默用户彻底推走。分层规则配置化（后台可调阈值），运营调整不需要发版。

```java
// UserSegmentService.java —— 用户分层与触达策略
import org.springframework.stereotype.Service;

import java.time.LocalDateTime;
import java.util.Map;

@Service
public class UserSegmentService {

    private final UserActivityMapper activityMapper;

    public UserSegmentService(UserActivityMapper activityMapper) {
        this.activityMapper = activityMapper;
    }

    public enum Segment {
        CORE,      // 核心用户：30 天内有活跃，全部通知
        NORMAL,    // 普通用户：90 天内有活跃，业务通知 + 低频活动
        SILENT     // 沉默用户：90 天无活跃，仅交易关键通知
    }

    /**
     * 根据最近活跃时间划分用户层级。
     */
    public Segment segment(String openid) {
        LocalDateTime lastActive = activityMapper.findLastActive(openid);
        if (lastActive == null) {
            return Segment.SILENT;
        }
        LocalDateTime now = LocalDateTime.now();
        if (lastActive.isAfter(now.minusDays(30))) {
            return Segment.CORE;
        }
        if (lastActive.isAfter(now.minusDays(90))) {
            return Segment.NORMAL;
        }
        return Segment.SILENT;
    }

    /**
     * 判断某类消息是否对该用户下发：营销消息只发给核心用户。
     */
    public boolean allowSend(String openid, String messageType, Map<String, Object> rules) {
        Segment segment = segment(openid);
        if ("marketing".equals(messageType)) {
            return segment == Segment.CORE || segment == Segment.NORMAL;
        }
        // 交易关键消息（支付/退款/发货）所有用户都发
        return true;
    }
}
```

文案层面，订阅消息受 thing（20 字）/phrase（5 字）限制，必须练就「短文案」能力：商品名称截断到 20 字以内、发货状态用「已发货」这样的短语、金额直接给数字。正文放不下的信息全部放到 page 跳转的落地页，让点击行为本身成为打开率的统计口径。

## 退订处理与降级方案

用户对订阅消息的「拒绝」有两种形态：订阅弹窗时拒绝（不获得额度）、下发时拒收（43101）。无论哪种，都应在服务端标记该用户对该模板的退订状态，停止后续下发。退订不代表失去这个用户，而是提示我们需要换一条触达通道——关键通知不能因为用户拒绝订阅就彻底丢失。

降级通道按优先级排列：站内信（小程序内消息中心，零成本、无平台限制）承接所有通知的副本；短信（高价值通知如退款到账、预约改期，成本高要克制）承接最关键的几类；公众号模板消息（用户同时关注了公众号时可用）作为微信生态内的替代触达。设计原则是「关键通知必有兜底，普通通知不打扰」。

```text
退订与降级方案：
1. 退订标记 —— 43101 与弹窗拒绝均记录用户退订状态，停止该模板下发
2. 站内信 —— 小程序内消息中心，承接全部通知副本，零成本
3. 短信 —— 仅退款到账、预约改期等关键通知，控制成本与频次
4. 公众号模板 —— 用户已关注公众号时作为微信内替代触达
5. 重新订阅 —— 业务页面保留「开启提醒」入口，用户可随时补订
6. 退订不等于流失 —— 降级通道承接关键信息，避免用户因收不到通知投诉
```

```java
// NotifyRouter.java —— 发送前检查偏好并选择降级通道
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;

@Service
public class NotifyRouter {

    private static final Logger log = LoggerFactory.getLogger(NotifyRouter.class);

    private final NotifyPreferenceMapper preferenceMapper;
    private final InboxService inboxService;      // 站内信
    private final SmsService smsService;          // 短信
    private final SubscribeMessageService subscribeMessageService;

    public NotifyRouter(NotifyPreferenceMapper preferenceMapper,
                        InboxService inboxService,
                        SmsService smsService,
                        SubscribeMessageService subscribeMessageService) {
        this.preferenceMapper = preferenceMapper;
        this.inboxService = inboxService;
        this.smsService = smsService;
        this.subscribeMessageService = subscribeMessageService;
    }

    /**
     * 通知路由：优先订阅消息，用户退订则按优先级降级。
     *
     * @param openid     用户 openid
     * @param templateId 订阅消息模板 ID
     * @param bizType    业务类型（refund 退款 / reminder 预约提醒 / marketing 营销）
     * @param payload    消息内容
     */
    public void route(String openid, String templateId, String bizType, Object payload) {
        // 1. 用户对该模板未退订：走订阅消息
        if (preferenceMapper.isSubscribed(openid, templateId)) {
            try {
                subscribeMessageService.sendTemplate(openid, templateId, payload);
                return;
            } catch (WechatApiException e) {
                if (e.getErrcode() == 43101) {
                    // 下发时才发现拒收：标记退订，走降级
                    preferenceMapper.markRejected(openid, templateId, "send_reject");
                } else {
                    log.error("订阅消息下发失败，转降级处理: {}", e.getMessage());
                }
            }
        }
        // 2. 站内信兜底：所有通知都进消息中心
        inboxService.push(openid, bizType, payload);
        // 3. 关键通知额外走短信（退款、预约改期等）
        if ("refund".equals(bizType) || "reschedule".equals(bizType)) {
            smsService.send(openid, buildSmsText(payload));
        }
        // 4. 用户已关注公众号时可用公众号模板消息承接（可选扩展）
    }
}
```

降级方案需要运营侧权衡：站内信成本为零但打开依赖用户回访；短信到达率高但按条计费且需要用户手机号（涉及单独授权）；公众号模板消息需要用户同时关注公众号。落地时先保证「站内信 + 关键通知短信」的组合，再逐步扩展。

## 数据统计与监控

订阅消息的运营要建立在数据之上，核心指标分为三张表：订阅转化率（accept 数 / 弹窗展示数，衡量订阅引导设计）、发送成功率（errcode=0 的下发占比，衡量服务端链路健康）、打开率（用户点击消息进入小程序的占比，衡量内容质量）。三个指标分别对应前端订阅设计、服务端实现、内容运营三个环节，任一环节出问题都能从指标上定位。

打开率的统计口径：在 page 参数中携带来源标记（如 pages/order/detail?id=1&from=submsg），小程序端在页面 onLoad 里识别 from=submsg 即记为一次消息打开；服务端按模板、按日期聚合。微信公众平台「数据分析 - 消息触达」也提供消息触达相关数据，可与自有统计交叉验证。

```text
核心指标与含义：
1. 订阅转化率 —— accept / (accept + reject + ban)，衡量订阅引导设计，目标 30%+
2. 发送成功率 —— errcode=0 占比，衡量服务端链路健康，目标 95%+
3. 打开率 —— 点击消息进入小程序的占比，衡量内容与时机，目标 10%+
4. 退订率 —— 43101 占比，衡量骚扰程度，突增需排查文案与频率
5. 错误码分布 —— 43101/47003/40003 等占比，定位具体问题
6. 分模板对比 —— 不同模板的转化率/打开率对比，指导模板与文案优化
```

统计 SQL 与监控任务：

```sql
-- subscribe_stats.sql —— 订阅消息数据统计
-- 1. 每日发送量与成功率
SELECT DATE(create_time)          AS day,
       COUNT(*)                   AS total,
       SUM(errcode = 0)           AS success,
       ROUND(SUM(errcode = 0) / COUNT(*) * 100, 2) AS success_rate
FROM subscribe_send_log
GROUP BY DATE(create_time)
ORDER BY day DESC;

-- 2. 错误码分布（定位问题）
SELECT errcode, COUNT(*) AS cnt
FROM subscribe_send_log
WHERE create_time >= DATE_SUB(NOW(), INTERVAL 7 DAY)
GROUP BY errcode
ORDER BY cnt DESC;

-- 3. 分模板打开率（打开日志表记录 from=submsg 的访问）
SELECT t.template_id,
       COUNT(DISTINCT s.openid) AS sent_users,
       COUNT(DISTINCT o.openid) AS opened_users,
       ROUND(COUNT(DISTINCT o.openid) / COUNT(DISTINCT s.openid) * 100, 2) AS open_rate
FROM subscribe_send_log s
LEFT JOIN message_open_log o ON o.biz_key = s.biz_key AND o.template_id = s.template_id
WHERE s.create_time >= DATE_SUB(NOW(), INTERVAL 30 DAY)
GROUP BY t.template_id;
```

监控告警的两个阈值：发送成功率连续 10 分钟低于 90% 告警（大概率是 token 故障或接口限流）；43101 占比突增告警（可能是文案/时机出了问题导致用户集中拒收，或模板即将被下线）。告警接入已有的监控体系（22.4），与日志平台联动，出问题时先看错误码分布再下结论。

## 合规要求

订阅消息的合规要点集中在授权与内容两个方面。授权侧：用户的每次订阅动作（accept/reject/ban）、订阅时间、来源页面必须记录落库，这是「用户授权记录」的凭证；用户应能在小程序内查看与管理自己的订阅（设置页开关、消息中心）。内容侧：下发内容必须与模板申请时的用途一致，不得夹带营销、诱导、虚假信息；跳转页面必须真实存在且内容与消息描述一致。

隐私政策必须覆盖订阅消息场景：说明收集了哪些信息（openid、订阅的模板、消息下发记录）、用于什么目的（业务状态通知）、用户如何撤回（设置页关闭订阅、微信设置页管理）。小程序提交审核时，「用户隐私保护指引」中应声明订阅消息相关信息的收集与使用。授权记录按监管要求保存（通常不少于 6 个月），支持随时导出。

```text
合规检查清单：
1. 授权记录 —— 订阅动作（accept/reject/ban）+ 时间 + 来源页面落库
2. 隐私政策 —— 说明订阅消息收集的信息、用途与撤回方式
3. 撤回通道 —— 小程序内设置页可关闭订阅，微信设置页可管理
4. 内容一致 —— 下发内容与模板申请用途一致，跳转页面真实对应
5. 留存期限 —— 授权记录按法规保存（建议 6 个月以上），可导出
6. 审核申报 —— 小程序提审时隐私保护指引覆盖订阅消息场景
```

```java
// SubscribeRecordService.java —— 授权记录落库与查询
import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class SubscribeRecordService {

    private final SubscribeRecordMapper recordMapper;

    public SubscribeRecordService(SubscribeRecordMapper recordMapper) {
        this.recordMapper = recordMapper;
    }

    /**
     * 小程序端上报订阅结果后落库（11.2 前端在订阅回调中上报）。
     */
    public void record(String openid, String templateId, String templateName,
                       String action, String sourcePage) {
        SubscribeRecord record = new SubscribeRecord();
        record.setOpenid(openid);
        record.setTemplateId(templateId);
        record.setTemplateName(templateName);
        record.setAction(action);
        record.setSourcePage(sourcePage);
        recordMapper.insert(record);
    }

    /**
     * 合规审计：导出某用户在某时间段的全部授权记录。
     */
    public List<SubscribeRecord> export(String openid, String start, String end) {
        return recordMapper.selectByOpenidAndTime(openid, start, end);
    }
}
```

合规与体验并不冲突：设置页的订阅管理开关同时满足「用户可撤回」的合规要求与「重新订阅」的运营需求；授权记录的落库既是合规凭证，也是订阅转化率统计的数据源。把合规动作设计成产品功能的一部分，而不是额外负担。

## 应用场景实战

### 场景一：电商订单全链路订阅消息方案

从下单到签收的四个节点设计消息触达，控制频率并埋点统计：

```text
方案设计：
1. 支付成功通知 —— 支付回调后立即下发，模板关键词：thing 订单号 + amount 实付金额
2. 发货通知 —— 仓库发货后下发，关键词：thing 商品名称 + number 订单号 + phrase 发货状态
3. 签收提醒 —— 物流签收后下发，关键词：thing 商品名称 + phrase 物流状态 + thing 售后提示
4. 营销活动 —— 仅核心用户每周最多 1 条，关键词：thing 活动名称 + time 活动时间
5. 订阅入口 —— 支付成功页一次弹 2 个模板（支付回执 + 发货）；订单详情页提供签收提醒按钮
6. 统计指标 —— 订阅转化率、按节点成功率、分模板打开率、退订率
```

对应核心下发编排（SpringBoot）：

```java
// OrderNotifyService.java —— 订单消息编排
import org.springframework.stereotype.Service;

@Service
public class OrderNotifyService {

    private final NotifyRouter notifyRouter;
    private final OrderMapper orderMapper;

    public OrderNotifyService(NotifyRouter notifyRouter, OrderMapper orderMapper) {
        this.notifyRouter = notifyRouter;
        this.orderMapper = orderMapper;
    }

    /** 支付回调触发：下发支付成功通知 */
    public void onPaid(String orderNo) {
        Order order = orderMapper.findByOrderNo(orderNo);
        if (order == null || !"PAID".equals(order.getStatus())) {
            return; // 状态校验：已取消/非支付成功不发
        }
        notifyRouter.route(
            order.getOpenid(),
            TEMPLATE_ORDER_PAID,
            "paid",
            Map.of("orderNo", order.getOrderNo(), "amountFen", order.getPaidAmountFen())
        );
    }

    /** 发货动作触发：下发发货通知 */
    public void onShipped(String orderNo, String trackingNo, String company) {
        Order order = orderMapper.findByOrderNo(orderNo);
        if (order == null || !"SHIPPED".equals(order.getStatus())) {
            return;
        }
        notifyRouter.route(
            order.getOpenid(),
            TEMPLATE_ORDER_SHIPPED,
            "shipped",
            Map.of("goodsName", order.getGoodsName(), "orderNo", order.getOrderNo(),
                   "trackingNo", trackingNo, "company", company)
        );
    }
}
```

### 场景二：预约服务提醒方案（定时任务 + 降级）

预约类业务的痛点是爽约率高，订阅消息是降低爽约率最有效的触达手段：

```text
方案设计：
1. 预约确认通知 —— 用户提交预约后立即下发，含服务时间与地点
2. 开始前提醒 —— 预约开始前 2 小时下发，由定时任务扫描到期预约触发
3. 改期/取消提醒 —— 商家改期或取消时下发，附新的时间或联系客服指引
4. 降级通道 —— 用户拒收订阅时，开始前提醒走短信（关键通知）
5. 重订入口 —— 预约详情页提供「开启提醒」按钮，随时补订
6. 效果衡量 —— 对比开启提醒用户与未开启用户的爽约率，量化消息价值
```

定时扫描与提醒下发：

```java
// AppointmentRemindJob.java —— 预约开始前提醒
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;
import java.util.List;

@Component
public class AppointmentRemindJob {

    private static final Logger log = LoggerFactory.getLogger(AppointmentRemindJob.class);

    private final AppointmentMapper appointmentMapper;
    private final NotifyRouter notifyRouter;

    public AppointmentRemindJob(AppointmentMapper appointmentMapper, NotifyRouter notifyRouter) {
        this.appointmentMapper = appointmentMapper;
        this.notifyRouter = notifyRouter;
    }

    /**
     * 每分钟扫描一次：找到 2 小时后开始、且尚未提醒的预约，下发提醒。
     */
    @Scheduled(fixedDelay = 60_000)
    public void scanAndRemind() {
        LocalDateTime remindAt = LocalDateTime.now().plusHours(2);
        List<Appointment> list = appointmentMapper.findByStartTimeAndStatus(
            remindAt, "CONFIRMED", "NOT_REMINDED");
        for (Appointment appt : list) {
            try {
                notifyRouter.route(
                    appt.getOpenid(),
                    TEMPLATE_APPOINTMENT_REMIND,
                    "reminder",
                    Map.of("serviceName", appt.getServiceName(),
                           "startTime", appt.getStartTime(),
                           "address", appt.getAddress())
                );
                appointmentMapper.markReminded(appt.getId());
            } catch (Exception e) {
                // 单条失败不影响其他预约，记录后下个周期重试
                log.error("预约提醒下发失败, id={}", appt.getId(), e);
            }
        }
    }
}
```

预约提醒的价值可以直接量化：开启提醒用户的到场率通常比未开启用户高 10-20 个百分点。把「是否开启提醒」作为预约列表页的一个筛选维度，运营可以直观看到订阅消息对业务指标的贡献，这也是向团队证明消息体系价值的最佳方式。

## 最佳实践与踩坑记录

### 最佳实践

1. 建立「发送时机矩阵」：事件 -> 模板 -> 延迟窗口 -> 频控 -> 降级通道，一页文档说清全部消息规则，避免各业务线乱发
2. 交易关键消息（支付、发货、退款）永不降级为不通知，用户拒收订阅时至少走站内信，退款类走短信
3. 频率控制优先级：交易消息 > 预约提醒 > 营销活动；营销消息单用户每周最多 1 条
4. 三张表持续监控：订阅转化率、发送成功率、打开率，任一指标连续下滑立即排查对应环节
5. 用户分层触达：核心用户全量通知，沉默用户仅关键通知，防止营销把沉默用户彻底推走
6. 授权记录全量落库（accept/reject/ban + 时间 + 来源页），既是合规凭证也是转化率分析的数据源
7. 打开率统计用 page 来源参数（from=submsg）实现，成本极低，别依赖微信后台的间接数据
8. 每季度复盘一次模板使用情况，清理低打开率模板，结合新业务补充新模板

### 踩坑记录

```text
坑 1：营销消息群发轰炸，用户大面积退订
结论：某次活动群发后，退订率飙升，多个模板 43101 占比超过 50%。
原因：对全量用户（含 90 天未活跃的沉默用户）群发营销消息，触发用户反感与批量拒收。
解法：营销消息按用户分层只发核心用户；频率降到每周 1 条以内；活动前先小流量测试打开率。

坑 2：深夜下发提醒消息
结论：凌晨下发的预约提醒打开率极低，且部分用户投诉。
原因：定时任务按「开始前 2 小时」无差别触发，凌晨开始的预约在深夜下发提醒。
解法：下发前判断时段（早 8 点 - 晚 21 点），深夜开始的预约改为前一晚 21 点前提醒，或次日早上下发。

坑 3：用户拒收后仍在发，投诉被举报
结论：用户已拒收订阅，后台仍每天重试下发，用户投诉骚扰。
原因：43101 没有标记退订状态，定时任务反复扫描重发。
解法：43101 立即写入通知偏好表标记退订；发送前先查偏好；重试只针对可重试错误码。

坑 4：打开率统计缺失，无法评估消息效果
结论：消息发了不少，但说不清哪条消息有效、打开率多少。
原因：page 参数没有带来源标记，也没有打开日志表，打开行为无法归因到具体消息。
解法：page 统一带 from=submsg&template=xx；小程序端 onLoad 识别后上报打开日志；按模板聚合打开率。

坑 5：授权记录没落库，合规审查无法自证
结论：平台抽查或监管要求提供用户授权记录时，拿不出数据。
原因：订阅结果只在前端 console 打印，没有上报后台，后台无任何授权凭证。
解法：前端订阅回调里把 accept/reject/ban + 时间 + 来源页上报；后台建 subscribe_record 表落库，支持导出。

坑 6：业务状态与消息不一致
结论：用户收到已取消订单的发货通知，投诉虚假消息。
原因：消息触发时没有校验订单当前状态，异步任务执行时订单状态已变化。
解法：发送前校验业务状态（订单已取消/已退款则跳过）；状态机流转时把「待发送消息」一并取消或改写。

坑 7：只盯接口成功率，忽略用户侧拒收率
结论：后台显示发送成功率 99%，但用户感知是「经常收不到消息」。
原因：只统计 errcode=0 的接口成功率，43101 被当成成功前的正常错误忽略了拒收趋势。
解法：43101 单独统计为退订率；退订率突增时排查文案、频率、时机；把退订率纳入监控告警。

坑 8：批量任务失败重跑重复下发
结论：一次网络抖动导致任务重跑，用户收到两条相同通知。
原因：任务无幂等，失败重跑重新扫描全部待发送记录。
解法：Redis 幂等键（openid+模板+业务单号）或数据库唯一索引；已成功下发的记录标记后不再重发。
```
