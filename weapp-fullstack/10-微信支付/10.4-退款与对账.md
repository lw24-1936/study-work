## 概述

退款是支付体系的资金反向操作：商户把用户已支付的金额按原路退回其微信零钱或原支付渠道。退款与支付是同一资金池的两面，退款 API、退款回调、每日对账共同构成资金闭环。本篇章讲解微信支付 v3 退款接口（POST /v3/refund/domestic/refunds）的请求与约束、退款状态机与退款回调、对账单的下载与解析（GET /v3/bill/tradebill）、对账差异的分类处理，以及退款金额限制、退款次数与风控等资金安全要点。

```text
本章核心要点：
1. 退款接口 —— POST /v3/refund/domestic/refunds，按原路退回
2. 退款单号 —— out_refund_no 商户侧唯一，退款结果以异步回调为准
3. 退款状态 —— PROCESSING / SUCCESS / CLOSED / ABNORMAL，对应订单状态机流转
4. 对账单 —— GET /v3/bill/tradebill 下载 T+1 日账单，CSV 格式可 GZIP 压缩
5. 差异处理 —— 微信有本地无 / 本地有微信无 / 金额不一致三类差异闭环
6. 资金安全 —— 退款金额不超过实付、可多次部分退款、风控拦截异常退款
```

## 退款 API 与退款流程

退款由商户后台发起，接口为 POST https://api.mch.weixin.qq.com/v3/refund/domestic/refunds。请求体核心字段：out_trade_no 或 transaction_id（原支付订单，二选一）、out_refund_no（商户退款单号，必须唯一）、reason（退款原因，展示给用户）、notify_url（退款结果回调地址）、amount（refund 为本次退款金额、total 为原订单支付金额、currency 为 CNY）。微信校验通过后返回 refund_id（微信退款单号）与 status。退款是「原路退回」：钱回到用户微信零钱（零钱支付）或原银行卡（银行卡支付），到账时效以微信提示为准（零钱实时，银行卡 1-3 个工作日）。

退款流程编排：用户在退款页面提交申请 -> 后端校验退款资格（订单已支付、可退金额足够、退款次数未超限）-> 更新订单为退款中（REFUNDING）-> 调退款 API -> 记录退款单（out_refund_no 落库）-> 等退款回调更新退款单与订单状态。发起退款前必须校验「本次退款金额 <= 剩余可退金额」，剩余可退金额 = 实付金额 - 已累计退款金额。部分退款后订单保持已支付，剩余可退金额递减；累计退款等于实付金额后订单置为已退款。

```text
退款 API 要点：
1. 接口路径 —— POST /v3/refund/domestic/refunds（v3 版本）
2. 订单标识 —— out_trade_no（商户订单号）与 transaction_id（微信订单号）二选一
3. 退款单号 —— out_refund_no 商户生成且唯一，重复使用会被微信拒绝
4. 金额字段 —— amount.refund 本次退款金额，amount.total 原订单金额，单位均为分
5. 原路退回 —— 退回用户原支付渠道（零钱/银行卡），不支持转账到其他账户
6. 到账时效 —— 零钱实时到账，银行卡一般 1-3 个工作日（以银行为准）
```

```java
// RefundService.java —— 申请退款（部分退款/全额退款通用）
import com.wechat.pay.java.service.refund.RefundService;
import com.wechat.pay.java.service.refund.model.AmountReq;
import com.wechat.pay.java.service.refund.model.CreateRequest;
import com.wechat.pay.java.service.refund.model.CreateResponse;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class RefundService {

    private final RefundService refundService; // 微信官方 SDK 的 RefundService（与类名相同，注意包名区分）
    private final WechatPayProperties props;
    private final OrderMapper orderMapper;
    private final RefundOrderMapper refundOrderMapper;

    public RefundService(RefundService refundService, WechatPayProperties props,
                         OrderMapper orderMapper, RefundOrderMapper refundOrderMapper) {
        this.refundService = refundService;
        this.props = props;
        this.orderMapper = orderMapper;
        this.refundOrderMapper = refundOrderMapper;
    }

    /**
     * 发起退款。
     *
     * @param outTradeNo    原支付订单号
     * @param refundAmountFen 本次退款金额（分）
     * @param reason        退款原因
     * @return 微信退款单号 refund_id
     */
    @Transactional
    public String refund(String outTradeNo, long refundAmountFen, String reason) {
        Order order = orderMapper.selectByOutTradeNo(outTradeNo);

        // 1. 校验：订单必须已支付
        if (order == null || order.getStatus() != OrderStatus.PAID) {
            throw new BizException("订单状态不允许退款");
        }
        // 2. 校验：本次退款金额不超过剩余可退金额
        long remaining = order.getAmountFen() - order.getRefundedAmountFen();
        if (refundAmountFen <= 0 || refundAmountFen > remaining) {
            throw new BizException("退款金额超过可退金额");
        }

        // 3. 生成商户退款单号并落库（退款中状态）
        String outRefundNo = generateRefundNo();
        refundOrderMapper.insert(new RefundOrder(outTradeNo, outRefundNo,
                refundAmountFen, RefundStatus.PROCESSING));

        // 4. 调微信退款接口
        CreateRequest request = new CreateRequest();
        request.setOutTradeNo(outTradeNo);
        request.setOutRefundNo(outRefundNo);
        request.setReason(reason);
        request.setNotifyUrl(props.getRefundNotifyUrl());

        AmountReq amount = new AmountReq();
        amount.setRefund(refundAmountFen);
        amount.setTotal(order.getAmountFen());
        amount.setCurrency("CNY");
        request.setAmount(amount);

        CreateResponse response = refundService.create(request);
        return response.getRefundId(); // 微信退款单号
    }

    private String generateRefundNo() {
        // 规则：R + yyyyMMddHHmmss + 6 位随机数
        return "R" + LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMddHHmmss"))
                + String.format("%06d", ThreadLocalRandom.current().nextInt(1000000));
    }
}
```

退款接口返回的 status 有四种：PROCESSING（退款处理中，最终结果以回调为准）、SUCCESS（退款成功）、CLOSED（退款关闭，如超过可退金额或退款期限导致关闭）、ABNORMAL（退款异常，需人工介入）。退款是异步过程，即使接口同步返回成功也只是受理成功，最终状态必须等退款回调。对应订单状态：发起退款后订单置 REFUNDING，退款成功回调后全额退款的订单置 REFUNDED，部分退款的订单保持 PAID 并累计退款金额。

```text
退款与订单状态联动：
1. 发起退款 —— 订单 PAID -> REFUNDING（记录退款单，状态 PROCESSING）
2. 退款成功 —— 全额退款：订单 REFUNDING -> REFUNDED（终态）
3. 退款成功 —— 部分退款：订单保持 PAID，累计退款金额增加
4. 退款关闭 —— 退款单 CLOSED，订单回到 PAID（可再次发起退款）
5. 退款异常 —— 退款单 ABNORMAL，告警人工核查
6. 资金口径 —— 可退金额 = 实付金额 - 累计退款金额，退款单与订单字段保持一致
```

## 退款回调与退款状态

退款结果通过异步回调通知商户：event_type 为 REFUND.SUCCESS（退款成功）、REFUND.ABNORMAL（退款异常，需人工介入）、REFUND.CLOSED（退款关闭）。回调报文结构与支付回调相同（request 头四个验签字段 + resource 密文），验签解密方式完全一致（平台证书验签 + APIv3 密钥 AES-256-GCM 解密）。解密后的明文包含 out_trade_no、out_refund_no、refund_id、refund_status、success_time、amount（refund 退款金额、payer_total 用户实际支付金额等）。回调处理同样必须幂等：以退款单状态条件更新为准，重复回调直接应答 SUCCESS。

退款回调的业务处理：根据 out_refund_no 找到退款单，校验退款金额与退款单一致，然后把退款单状态更新为 SUCCESS/ABNORMAL/CLOSED，并联动订单：全额退款 -> 订单置 REFUNDED；部分退款 -> 累计退款金额增加，若累计等于实付金额则订单也置 REFUNDED。退款回调与支付回调共用同一套验签解密基础设施，但事件类型与业务处理不同，需要独立实现。

```java
// RefundNotifyController.java —— 退款结果回调
import com.wechat.pay.java.core.notification.NotificationConfig;
import com.wechat.pay.java.core.notification.NotificationParser;
import com.wechat.pay.java.core.notification.RequestParam;
import com.wechat.pay.java.service.refund.model.RefundNotification;
import org.springframework.web.bind.annotation.*;

import java.util.Map;

@RestController
@RequestMapping("/api/pay")
public class RefundNotifyController {

    private final NotificationParser parser;
    private final RefundOrderService refundOrderService;

    public RefundNotifyController(NotificationConfig config,
                                  RefundOrderService refundOrderService) {
        this.parser = new NotificationParser(config); // 与支付回调共用验签解密配置
        this.refundOrderService = refundOrderService;
    }

    /** 退款结果回调：REFUND.SUCCESS / REFUND.ABNORMAL / REFUND.CLOSED */
    @PostMapping("/refund-notify")
    public Map<String, Object> refundNotify(@RequestBody String body,
                                            @RequestHeader("Wechatpay-Timestamp") String timestamp,
                                            @RequestHeader("Wechatpay-Nonce") String nonce,
                                            @RequestHeader("Wechatpay-Signature") String signature,
                                            @RequestHeader("Wechatpay-Serial") String serial) {
        try {
            // 1. 验签 + 解密（与支付回调同一套机制）
            RefundNotification notification = parser.parse(
                    new RequestParam.Builder()
                            .serialNumber(serial)
                            .nonce(nonce)
                            .signature(signature)
                            .timestamp(timestamp)
                            .body(body)
                            .build(),
                    RefundNotification.class);

            // 2. 幂等处理退款结果并联动订单状态
            refundOrderService.handleRefundResult(
                    notification.getOutRefundNo(),
                    notification.getRefundStatus(), // SUCCESS / ABNORMAL / CLOSED
                    notification.getAmount().getRefund());

            return Map.of("code", "SUCCESS", "message", "成功");
        } catch (Exception e) {
            return Map.of("code", "FAIL", "message", "失败");
        }
    }
}
```

```java
// RefundOrderService.java —— 退款结果幂等处理（含退款单状态机）
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class RefundOrderService {

    private final RefundOrderMapper refundOrderMapper;
    private final OrderMapper orderMapper;

    public RefundOrderService(RefundOrderMapper refundOrderMapper, OrderMapper orderMapper) {
        this.refundOrderMapper = refundOrderMapper;
        this.orderMapper = orderMapper;
    }

    /** 退款状态机：PROCESSING -> SUCCESS / ABNORMAL / CLOSED（终态） */
    @Transactional
    public void handleRefundResult(String outRefundNo, String refundStatus, long refundFen) {
        RefundOrder refund = refundOrderMapper.selectByOutRefundNo(outRefundNo);
        if (refund == null) {
            log.error("退款单不存在: {}", outRefundNo);
            throw new BizException("退款单不存在");
        }

        // 金额校验：微信退款金额必须等于退款单金额
        if (refund.getAmountFen() != refundFen) {
            log.error("退款金额不一致: outRefundNo={}, expect={}, actual={}",
                    outRefundNo, refund.getAmountFen(), refundFen);
            throw new BizException("退款金额不一致");
        }

        // 幂等：只有 PROCESSING 状态允许流转到终态
        int updated = refundOrderMapper.updateStatus(outRefundNo, refundStatus);
        if (updated == 0) {
            log.info("退款单重复回调或状态不允许: {}", outRefundNo);
            return;
        }

        // 联动订单：累计退款金额并判断是否全额退完
        if ("SUCCESS".equals(refundStatus)) {
            orderMapper.accumulateRefunded(refund.getOutTradeNo(), refund.getAmountFen());
        }
        // CLOSED/ABNORMAL 时退款单置终态，订单保持 PAID，可重新发起退款
    }
}
```

## 对账文件与下载

对账是资金安全的最后一道防线。微信支付按日生成对账单，商户可通过 GET https://api.mch.weixin.qq.com/v3/bill/tradebill 获取：query 参数 bill_date（账单日期，格式 yyyyMMdd，只能查最近 30 天内）、bill_type（ALL 全部 / SUCCESS 成功 / REFUND 退款 / RECHARGE 充值）、tar_type（GZIP 表示返回压缩包下载地址，不传则返回原始文件地址）。接口返回 download_url（有效期 5 分钟）与 hash 值，随后请求 download_url 下载文件，用 hash 校验完整性。

对账单是 CSV 文本（UTF-8 编码），结构为四段：第一行是说明（总交易单数、总交易金额、总退款单数、总退款金额等汇总），第二行是字段名（交易时间、公众账号ID、商户号、特约商户号、设备号、微信订单号、商户订单号、用户标识、商品类型、交易类型、交易状态、付款银行、货币种类、应结金额、代金券金额、微信退款单号、商户退款单号、退款金额、充值券退款金额、退款类型、退款状态、商品名称、商户数据包、手续费、费率、订单金额、申请退款金额、费率备注），第三行起是逐笔交易明细（逗号分隔），最后一行是汇总行。字段用逗号分隔，字段值本身不含逗号（金额字段为数字）。

```text
对账单结构：
1. 第 1 行 —— 说明行：统计日期、总交易单数、总交易金额、总退款单数、总退款金额
2. 第 2 行 —— 字段名行：约 28 个字段，按固定顺序排列
3. 第 3 行起 —— 交易明细：每行一笔交易或退款记录
4. 最后一行 —— 汇总行：总交易单数/总退款单数/总交易金额/总退款金额
5. 压缩格式 —— tar_type=GZIP 时下载的是 .gz 压缩包，需解压后解析
6. 时间窗口 —— 只能查询最近 30 天内的账单，务必每日下载归档
```

```java
// TradeBillService.java —— 获取对账单下载地址
import com.wechat.pay.java.core.Config;
import com.wechat.pay.java.core.http.*;
import org.springframework.stereotype.Service;

import java.time.LocalDate;
import java.time.format.DateTimeFormatter;

@Service
public class TradeBillService {

    private final HttpClient httpClient;

    public TradeBillService(Config config) {
        // 带商户签名的 HTTP 客户端（SDK 自动处理请求签名）
        this.httpClient = new DefaultHttpClientBuilder().config(config).build();
    }

    /** 获取对账单下载地址：GET /v3/bill/tradebill?bill_date=...&bill_type=ALL&tar_type=GZIP */
    public String fetchBillUrl(LocalDate billDate) {
        String url = "https://api.mch.weixin.qq.com/v3/bill/tradebill"
                + "?bill_date=" + billDate.format(DateTimeFormatter.BASIC_ISO_DATE) // 20260819
                + "&bill_type=ALL&tar_type=GZIP";
        HttpResponse<BillDownloadResponse> response = httpClient.get(
                HttpMethod.GET, url, BillDownloadResponse.class);
        return response.getBody().getDownloadUrl(); // 5 分钟内有效
    }

    /** 下载对账单字节（按 hash 校验完整性） */
    public byte[] downloadBill(String downloadUrl) {
        HttpResponse<FileDownloadResponse> response = httpClient.get(
                HttpMethod.GET, downloadUrl, FileDownloadResponse.class);
        return response.getBody().getBody();
    }
}
```

```java
// BillParser.java —— 解析对账单（解压 GZIP + 按行切分）
import java.io.*;
import java.nio.charset.StandardCharsets;
import java.util.ArrayList;
import java.util.List;
import java.util.zip.GZIPInputStream;

public class BillParser {

    /** 解析后的账单模型 */
    public record Bill(List<String> summary, List<String[]> detailRows) {}

    /**
     * 解析对账单字节流。
     * 第 1 行说明、第 2 行表头、第 3 行起明细、最后一行汇总。
     */
    public static Bill parse(byte[] gzipData) throws IOException {
        List<String> summary = new ArrayList<>();
        List<String[]> detailRows = new ArrayList<>();

        try (GZIPInputStream gis = new GZIPInputStream(new ByteArrayInputStream(gzipData));
             BufferedReader reader = new BufferedReader(
                     new InputStreamReader(gis, StandardCharsets.UTF_8))) {

            String headerLine = reader.readLine(); // 第 1 行：说明/汇总信息
            if (headerLine != null) {
                summary.add(headerLine);
            }
            reader.readLine(); // 第 2 行：字段名（跳过，字段顺序已知）

            String line;
            while ((line = reader.readLine()) != null) {
                if (line.trim().isEmpty()) {
                    continue;
                }
                // 第 3 行起的明细；最后一行「总交易单数,...」为汇总行
                if (line.startsWith("总交易单数")) {
                    summary.add(line);
                    continue;
                }
                detailRows.add(line.split(","));
            }
        }
        return new Bill(summary, detailRows);
    }
}
```

## 差异处理与对账实践

对账的落地方式是「每日 T+1 比对」：凌晨下载昨日对账单，把账单明细与本地订单表、退款单表逐笔比对，按差异类型分流处理。比对维度：商户订单号（out_trade_no）能对上且金额一致 -> 正常；其余归入差异。差异分三类——微信有本地无（本地缺单，多为回调丢失，调查单接口补记或人工补单）、本地有微信无（本地有订单但微信无交易记录，通常是下单未支付或测试数据，核对后清理）、金额不一致（高危，冻结相关业务并人工核查）。

差异处理要形成闭环：每笔差异生成记录（差异单号、类型、涉及金额、状态）-> 自动处理能自动的（掉单自动查单补记）-> 不能自动的挂起并通知财务/开发人工复核 -> 复核完成后销账。对账结果还应输出月度资金平衡表：交易金额 - 退款金额 - 手续费 = 结算到账金额，与银行流水比对。对账发现的问题要反哺代码修复（如某类回调丢失是应答格式问题）。

```java
// ReconcileService.java —— 对账比对主流程（示意）
import org.springframework.stereotype.Service;

import java.time.LocalDate;
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

@Service
public class ReconcileService {

    private final TradeBillService billService;
    private final BillParser billParser;
    private final OrderMapper orderMapper;
    private final RefundOrderMapper refundOrderMapper;
    private final DiffRecordMapper diffRecordMapper;

    public ReconcileService(TradeBillService billService, BillParser billParser,
                            OrderMapper orderMapper, RefundOrderMapper refundOrderMapper,
                            DiffRecordMapper diffRecordMapper) {
        this.billService = billService;
        this.billParser = billParser;
        this.orderMapper = orderMapper;
        this.refundOrderMapper = refundOrderMapper;
        this.diffRecordMapper = diffRecordMapper;
    }

    /** 对账入口：T+1 每日执行，产出差异清单 */
    public List<String> reconcile(LocalDate billDate) throws Exception {
        List<String> report = new ArrayList<>();

        // 1. 下载并解析对账单
        String url = billService.fetchBillUrl(billDate);
        Bill bill = billParser.parse(billService.downloadBill(url));

        // 2. 本地订单与退款单按商户单号索引
        Map<String, Order> localOrders = orderMapper.selectAll().stream()
                .collect(Collectors.toMap(Order::getOutTradeNo, o -> o));
        Map<String, RefundOrder> localRefunds = refundOrderMapper.selectAll().stream()
                .collect(Collectors.toMap(RefundOrder::getOutRefundNo, r -> r));

        // 3. 逐笔比对账单明细（字段：商户订单号=index 7，订单金额=index 25）
        for (String[] row : bill.detailRows()) {
            String tradeType = row[8];       // 交易类型：JSAPI / REFUND 等
            String orderNo = row[7];         // 商户订单号
            String amount = row[25];         // 订单金额（分）

            if ("REFUND".equals(tradeType)) {
                String refundNo = row[16];   // 商户退款单号
                if (!localRefunds.containsKey(refundNo)) {
                    report.add("差异[退款单缺失]: 微信有退款单 " + refundNo
                            + " 金额 " + amount + "，本地无记录");
                }
            } else {
                Order local = localOrders.get(orderNo);
                if (local == null) {
                    report.add("差异[订单缺失]: 微信有交易 " + orderNo
                            + " 金额 " + amount + "，本地无订单");
                } else if (local.getAmountFen() != Long.parseLong(amount)) {
                    report.add("差异[金额不一致]: 订单 " + orderNo
                            + " 本地=" + local.getAmountFen() + " 微信=" + amount);
                }
            }
        }

        // 4. 反向检查：本地已支付订单是否都在账单中（回调丢失检测）
        for (Order order : localOrders.values()) {
            if (order.getStatus() == OrderStatus.PAID
                    && !billContains(bill, order.getOutTradeNo())) {
                report.add("差异[账单缺单]: 本地订单 " + order.getOutTradeNo()
                        + " 已支付但不在微信账单中，需人工核查");
            }
        }
        return report;
    }

    private boolean billContains(Bill bill, String orderNo) {
        return bill.detailRows().stream().anyMatch(row -> row[7].equals(orderNo));
    }
}
```

## 资金安全与风控

退款直接涉及资金流出，必须严格管控。退款金额约束：单笔退款金额不超过订单实付金额（amount.refund <= amount.total），累计退款金额不超过实付金额；同一订单可多次部分退款，但累计达到实付金额后不可再退；订单超过退款期限（通常为支付后 1 年，以微信规则为准）或已全额退款后，退款接口会拒绝并返回 CLOSED。退款原因必填，会展示给用户并用于风控审核。

微信侧风控与商户侧风控要双重把关。微信侧：高频异常退款、退款金额与订单金额不符、商户退款失败率过高等会触发平台风控，严重时限制退款甚至冻结结算。商户侧：退款接口必须鉴权（仅管理员/客服权限可操作）、退款前二次确认、退款金额上限配置（单笔/单日）、异常退款（金额大、频率高、新用户）进入人工审核队列。退款单与订单、对账单三处金额必须一致，任何不一致都视为高危告警。

```text
资金安全红线：
1. 退款上限 —— 单笔退款 <= 剩余可退金额，累计退款 <= 实付金额
2. 退款次数 —— 支持多次部分退款，全额退款后不可再退
3. 期限限制 —— 超过微信退款期限的订单不可退款（接口返回 CLOSED）
4. 权限控制 —— 退款接口必须登录态 + 权限校验，操作留痕（操作人、时间、原因）
5. 金额三方一致 —— 退款单、订单累计退款、对账单三处金额必须一致
6. 风控告警 —— 大额/高频/新用户退款走人工审核，不一致立即冻结并告警
```

```java
// RefundGuard.java —— 商户侧退款风控校验（发起退款前执行）
import org.springframework.stereotype.Service;

import java.time.LocalDateTime;

@Service
public class RefundGuard {

    private final RefundOrderMapper refundOrderMapper;

    public RefundGuard(RefundOrderMapper refundOrderMapper) {
        this.refundOrderMapper = refundOrderMapper;
    }

    /** 退款风控校验，不通过直接抛异常 */
    public void guard(Order order, long refundAmountFen, Long operatorUserId) {
        // 1. 单笔上限：不超过剩余可退金额
        long remaining = order.getAmountFen() - order.getRefundedAmountFen();
        if (refundAmountFen > remaining) {
            throw new BizException("退款金额超过可退金额");
        }
        // 2. 单日退款上限（示例：单商户日退款 10 万元封顶，可按业务调整）
        long dailyRefunded = refundOrderMapper.sumSuccessAmountSince(
                LocalDateTime.now().minusDays(1));
        if (dailyRefunded + refundAmountFen > 100_000_00L) {
            throw new BizException("当日退款金额已达上限，请人工审核");
        }
        // 3. 大额退款人工审核（示例：单笔超过 5000 元需审核）
        if (refundAmountFen >= 500_000L) {
            refundOrderMapper.insertAudit(order.getOutTradeNo(), refundAmountFen,
                    operatorUserId, "大额退款待审核");
            throw new BizException("大额退款已提交人工审核");
        }
        // 4. 操作留痕
        refundOrderMapper.logOperation(order.getOutTradeNo(), operatorUserId, refundAmountFen);
    }
}
```

### 场景一：用户申请全额退款（含风控与回调联动）

场景：用户对已支付订单发起全额退款。后端校验 -> 发起退款 -> 微信受理 -> 回调确认 -> 订单置已退款。

```java
// RefundController.java —— 用户退款申请入口
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/orders")
public class RefundController {

    private final RefundService refundService;
    private final RefundGuard refundGuard;

    public RefundController(RefundService refundService, RefundGuard refundGuard) {
        this.refundService = refundService;
        this.refundGuard = refundGuard;
    }

    /** 用户申请退款：POST /api/orders/{orderId}/refund */
    @PostMapping("/{orderId}/refund")
    public Result<String> applyRefund(@PathVariable Long orderId,
                                      @RequestAttribute Long userId,
                                      @RequestBody RefundRequest req) {
        Order order = orderService.getOwnOrder(orderId, userId);

        // 1. 风控校验（金额上限、单日上限、大额审核、留痕）
        refundGuard.guard(order, req.getAmountFen(), userId);

        // 2. 发起退款（内部：订单 REFUNDING + 退款单 PROCESSING + 调微信接口）
        String refundId = refundService.refund(order.getOutTradeNo(),
                req.getAmountFen(), req.getReason());

        // 3. 返回受理结果（最终状态等退款回调）
        return Result.ok("退款已受理，微信退款单号: " + refundId);
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 退款接口统一走「校验 -> 落退款单（PROCESSING）-> 调微信 -> 回调确认」流程，禁止直接改订单状态
2. out_refund_no 每次生成新单号，同一笔退款不要复用旧单号，避免微信幂等语义与本地语义混淆
3. 退款金额校验放在业务层最前面：金额大于 0、不超过剩余可退金额、单日上限、大额审核
4. 退款回调与支付回调共用验签解密基础设施，但事件类型与处理逻辑分开实现，幂等各自独立
5. 对账单每日下载并归档（对账单只能查最近 30 天），解析时跳过说明行与汇总行，只处理明细行
6. 对账差异全部登记入库并闭环处理，禁止只打印日志；差异率/差异金额进入月度资金平衡报表
7. 退款操作全部留痕（操作人、时间、金额、原因），权限上只允许客服/管理员发起
8. 退款、订单、对账单三处金额一致是铁律，任何不一致立即告警并冻结相关订单的人工操作

### 踩坑记录

坑 1：退款金额超过订单实付金额被微信拒绝
结论：退款接口返回参数错误，退款无法发起。
原因：amount.refund 大于 amount.total（原订单金额），或累计退款超过实付金额。
解法：发起前计算剩余可退金额 = 实付 - 已退，校验本次退款金额 <= 剩余可退金额。

坑 2：out_refund_no 重复导致退款失败
结论：第二次发起退款报「商户退款单号重复」。
原因：out_refund_no 在商户侧必须唯一，重试逻辑复用了旧退款单号。
解法：每次退款生成新 out_refund_no；要查询旧退款结果用微信 refund_id 或查单接口。

坑 3：退款回调未处理，用户钱退了订单还显示未退款
结论：用户收到退款，但商户后台订单仍是退款中或已支付。
原因：退款回调接口未实现、验签失败、或回调处理异常未返回 SUCCESS 导致微信停止重试。
解法：实现退款回调并保证幂等；回调失败返回 FAIL 让微信重试；定时任务扫描超时未终态的退款单，调退款查询接口兜底。

坑 4：对账单 GZIP 未解压直接解析
结论：解析出乱码或解析异常。
原因：tar_type=GZIP 下载的是压缩包字节，直接按文本解析必然失败。
解法：用 GZIPInputStream 解压后再解析；或者不传 tar_type 参数获取原始文件。

坑 5：把对账单说明行与汇总行当明细解析
结论：对账比对出错，出现大量假差异。
原因：对账单第 1 行是说明、最后一行是汇总，字段含义与明细行不同。
解法：跳过第 1、2 行；遇到以「总交易单数」开头的行归入汇总；只解析中间明细行。

坑 6：全额退款后再次申请退款报错
结论：全额退款成功后再发起退款，接口返回退款关闭（CLOSED）或参数错误。
原因：累计退款已达实付金额，无可退金额；微信侧同一订单退款关闭后不可再退。
解法：发起前判断剩余可退金额为 0 时直接提示用户；退款单 CLOSED 状态不再发起。

坑 7：对账发现差异不处理，月底资金对不平
结论：月末对账发现资金差异，追溯成本极高。
原因：每日对账差异只记录不闭环，累积到月底无法定位。
解法：每日对账差异入库并当日处理（自动查单补记 + 人工复核），输出每日差异报告。

坑 8：退款原因含敏感词或高频退款触发风控
结论：退款接口返回风控拦截或商户被限制退款。
原因：退款原因含广告/违规词，或短时间高频发起小额退款触发平台风控。
解法：退款原因做敏感词过滤；退款频率与金额做商户侧限流；被风控后按平台指引申诉。
