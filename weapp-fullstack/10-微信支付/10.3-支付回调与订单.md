## 概述

用户支付成功后，微信支付服务器会向商户后台的 notify_url 异步发送支付结果通知，商户后台必须完成「验签 -> 解密 -> 幂等更新订单」三步才能可靠地确认一笔交易。回调是订单状态流转的唯一起点（前端 success 不可信），因此回调处理的正确性直接决定资金与订单的一致性。本篇章覆盖回调报文结构、平台证书验签、APIv3 密钥解密（AES-256-GCM）、回调幂等与订单状态机、订单超时关闭、掉单补偿与金额校验等异常场景。

```text
本章核心要点：
1. 回调报文 —— 微信 POST 到 notify_url，头部带签名，body 的 resource 密文需解密
2. 验签 —— 用微信支付平台证书验证签名，防止伪造回调
3. 解密 —— resource 用 AES-256-GCM 算法 + APIv3 密钥解密
4. 幂等 —— 同一回调可能重试多次，处理必须幂等（以状态机为准）
5. 订单状态机 —— 待支付/已支付/退款中/已退款/已关闭，非法流转必须拦截
6. 异常处理 —— 掉单主动查单补偿、金额不一致拦截、超时关闭订单
```

## 支付回调报文与验签

支付结果回调是 HTTPS POST 请求，Content-Type 为 application/json，回调地址是下单时传入的 notify_url。请求头携带四个验签要素：Wechatpay-Timestamp（时间戳）、Wechatpay-Nonce（随机串）、Wechatpay-Signature（签名值）、Wechatpay-Serial（微信支付平台证书序列号）。验签的通用流程是：用 Wechatpay-Serial 对应微信支付平台证书的公钥，对「时间戳 \n 随机串 \n 报文体 \n」构成的待验签串做 SHA256withRSA 验签。同时校验时间戳在 5 分钟内，防止重放攻击。

使用官方 SDK 时，验签、解密被封装在 NotificationParser 中自动完成，但开发者必须理解其原理，才能排查「验签失败」「解密失败」类问题。官方还要求商户回调接口在收到通知时立即返回应答，未返回 SUCCESS 的应答微信会按策略重试（首次失败后间隔 15 秒，之后逐步拉长，最长持续 24 小时，共重试若干次）。

```text
回调报文结构：
1. 请求头 —— Wechatpay-Timestamp / Wechatpay-Nonce / Wechatpay-Signature / Wechatpay-Serial
2. body.id —— 通知唯一 ID（可用于去重）
3. body.event_type —— 事件类型，支付成功为 TRANSACTION.SUCCESS
4. body.resource.algorithm —— 加密算法，固定 AEAD_AES_256_GCM
5. body.resource.ciphertext —— 密文，需用 APIv3 密钥解密
6. body.resource.nonce / associated_data —— GCM 解密所需的 nonce 与 AAD
```

```java
// PayNotifyController.java —— 支付结果回调入口
import com.wechat.pay.java.core.notification.NotificationConfig;
import com.wechat.pay.java.core.notification.NotificationParser;
import com.wechat.pay.java.core.notification.RequestParam;
import com.wechat.pay.java.service.payments.model.Transaction;
import org.springframework.web.bind.annotation.*;

import java.util.Map;

@RestController
@RequestMapping("/api/pay")
public class PayNotifyController {

    private final NotificationParser parser;
    private final OrderService orderService;

    public PayNotifyController(NotificationConfig config, OrderService orderService) {
        // NotificationConfig 内部完成「平台证书验签 + APIv3 密钥解密」
        this.parser = new NotificationParser(config);
        this.orderService = orderService;
    }

    /**
     * 微信支付结果回调。
     * 应答格式：HTTP 200 + {"code":"SUCCESS","message":"成功"}，
     * 返回其他内容或非 200 状态码都会被微信视为失败并重试。
     */
    @PostMapping("/notify")
    public Map<String, Object> notify(@RequestBody String body,
                                      @RequestHeader("Wechatpay-Timestamp") String timestamp,
                                      @RequestHeader("Wechatpay-Nonce") String nonce,
                                      @RequestHeader("Wechatpay-Signature") String signature,
                                      @RequestHeader("Wechatpay-Serial") String serial) {
        try {
            // 1. SDK 验签 + 解密，得到交易对象 Transaction
            Transaction transaction = parser.parse(
                    new RequestParam.Builder()
                            .serialNumber(serial)
                            .nonce(nonce)
                            .signature(signature)
                            .timestamp(timestamp)
                            .body(body)
                            .build(),
                    Transaction.class);

            // 2. 业务处理：幂等更新订单为已支付
            orderService.handlePaid(
                    transaction.getOutTradeNo(),      // 商户订单号
                    transaction.getTransactionId(),   // 微信支付订单号
                    transaction.getAmount().getTotal(), // 实际支付金额（分）
                    transaction.getTradeState());     // 交易状态

            // 3. 返回成功应答，微信停止重试
            return Map.of("code", "SUCCESS", "message", "成功");
        } catch (Exception e) {
            // 验签失败/解密失败/业务异常：返回失败，微信按策略重试
            return Map.of("code", "FAIL", "message", "失败");
        }
    }
}
```

Transaction 解密后的关键字段：out_trade_no（商户订单号）、transaction_id（微信支付订单号）、trade_state（SUCCESS 表示支付成功）、amount.total（实际支付金额，分）、amount.payer_total（用户支付金额，分，含零钱与银行卡拆分）、payer.openid、success_time、attach（下单时携带的附加数据，可用于透传业务标记）。业务处理前必须判断 trade_state 为 SUCCESS，其他状态（如 REFUND 退款后的回调会单独发 REFUND.SUCCESS 事件）不应触发「标记已支付」逻辑。

```java
// 手动验签示意：理解 SDK 内部做了什么（生产环境直接用 NotificationParser）
import java.nio.charset.StandardCharsets;
import java.security.Signature;
import java.util.Base64;

public class ManualVerifyExample {

    /** 验签：timestamp \n nonce \n body \n 用微信支付平台证书公钥验签 */
    public static boolean verify(String timestamp, String nonce, String body,
                                 String signature, java.security.cert.X509Certificate platformCert)
            throws Exception {
        String message = timestamp + "\n" + nonce + "\n" + body + "\n";
        Signature verifier = Signature.getInstance("SHA256withRSA");
        verifier.initVerify(platformCert.getPublicKey());
        verifier.update(message.getBytes(StandardCharsets.UTF_8));
        return verifier.verify(Base64.getDecoder().decode(signature));
    }
}
```

## 回调解密与幂等处理

验签通过后需要解密 resource 字段。微信使用 AEAD_AES_256_GCM 对称加密：密钥为 APIv3 密钥（32 字节，UTF-8 编码），nonce 与 associated_data 直接取自 resource 字段，对 ciphertext（Base64）解密后得到明文 JSON。明文示例：{"appid":"wx...","mchid":"1900000109","out_trade_no":"...","transaction_id":"420000...","trade_state":"SUCCESS","success_time":"2026-08-20T10:00:00+08:00","payer":{"openid":"o...","...},"amount":{"total":100,"payer_total":100,"currency":"CNY","payer_currency":"CNY"}}。

幂等是回调处理的第一原则：微信的重试机制（最长 24 小时、多次重试）、网络抖动导致的重复投递、以及商户自身重复部署都可能让同一笔回调到达多次。幂等处理的标准做法是「状态机 + 条件更新」：只有订单处于待支付状态时才允许更新为已支付；已支付/已退款/已关闭的订单收到重复回调时直接返回 SUCCESS 应答，不重复执行业务（不加积分、不重复发货）。SQL 层面用「UPDATE ... WHERE status = 'PENDING'」保证并发安全，更新行数为 0 即说明是重复回调。

```text
回调处理三步曲：
1. 验签 —— 平台证书验签 + 时间戳 5 分钟窗口防重放，失败直接应答 FAIL
2. 解密 —— APIv3 密钥 AES-256-GCM 解密 resource，得到明文交易数据
3. 幂等 —— 条件更新订单状态（仅待支付可置为已支付），重复回调直接 SUCCESS
```

```java
// OrderService.java —— 幂等的支付成功处理
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {

    private final OrderMapper orderMapper;

    public OrderService(OrderMapper orderMapper) {
        this.orderMapper = orderMapper;
    }

    /**
     * 处理支付成功回调（幂等）。
     * 关键校验：金额一致性 + 状态条件更新。
     */
    @Transactional
    public void handlePaid(String outTradeNo, String transactionId,
                           long paidAmountFen, String tradeState) {
        if (!"SUCCESS".equals(tradeState)) {
            // 非成功状态（如用户支付后立即退款触发的通知）不更新为已支付
            return;
        }
        Order order = orderMapper.selectByOutTradeNo(outTradeNo);
        if (order == null) {
            // 订单不存在：记录告警并返回（可人工核查是否恶意回调）
            log.error("回调订单不存在: {}", outTradeNo);
            throw new BizException("订单不存在");
        }

        // 金额一致性校验：微信实际支付金额必须等于订单金额
        if (order.getAmountFen() != paidAmountFen) {
            log.error("金额不一致: outTradeNo={}, orderAmount={}, paidAmount={}",
                    outTradeNo, order.getAmountFen(), paidAmountFen);
            throw new BizException("金额不一致，需人工核查");
        }

        // 幂等更新：仅当订单仍为待支付时置为已支付
        int updated = orderMapper.markPaid(outTradeNo, transactionId, OrderStatus.PAID);
        if (updated == 0) {
            // 已处理过（重复回调）或状态不允许流转，直接忽略
            log.info("重复回调或状态不允许: {}", outTradeNo);
        }
    }
}
```

```sql
-- OrderMapper.xml —— 条件更新实现幂等（核心 SQL）
<update id="markPaid">
    UPDATE t_order
    SET status = #{targetStatus},
        transaction_id = #{transactionId},
        paid_time = NOW()
    WHERE out_trade_no = #{outTradeNo}
      AND status = 'PENDING'   -- 只有待支付才允许流转到已支付
</update>
```

## 订单状态机

订单状态机是支付类系统的核心数据模型。本知识库订单状态定义如下：PENDING（待支付，下单成功未支付）、PAID（已支付，收到支付成功回调）、REFUNDING（退款中，已发起退款未收到退款成功回调）、REFUNDED（已退款，退款成功回调到达，全额退款时为终态）、CLOSED（已关闭，超时未支付或主动取消）。所有状态流转必须经过校验，任何非法流转（如已关闭订单被标记已支付）都会造成资金与业务不一致。

状态流转规则：PENDING -> PAID（支付回调）、PENDING -> CLOSED（超时/取消）、PAID -> REFUNDING（发起退款）、PAID -> REFUNDED（全额退款且微信直接返回成功，不经过 REFUNDING 回调时）、REFUNDING -> REFUNDED（退款成功回调）。PENDING 的订单只允许被支付回调或关闭操作命中一次；CLOSED 与 REFUNDED 是终态，不允许再流转。部分退款场景下 PAID 状态保持，用「剩余可退金额」字段配合流转。

```java
// OrderStatus.java —— 订单状态枚举与流转校验
public enum OrderStatus {

    PENDING("待支付"),
    PAID("已支付"),
    REFUNDING("退款中"),
    REFUNDED("已退款"),
    CLOSED("已关闭");

    private final String desc;

    OrderStatus(String desc) {
        this.desc = desc;
    }

    /**
     * 校验并返回目标状态；非法流转直接抛异常。
     * 适用于支付回调、退款发起、退款回调、关闭订单等所有入口。
     */
    public OrderStatus transitionTo(OrderStatus target) {
        boolean ok = switch (this) {
            case PENDING -> target == PAID || target == CLOSED;
            case PAID -> target == REFUNDING || target == REFUNDED;
            case REFUNDING -> target == REFUNDED;
            case REFUNDED, CLOSED -> false; // 终态
        };
        if (!ok) {
            throw new IllegalStateException("非法状态流转: " + this + " -> " + target);
        }
        return target;
    }

    public String getDesc() {
        return desc;
    }
}
```

订单超时关闭是状态机的常见触发场景：用户下单后 30 分钟未支付，系统应关闭订单（本地状态置 CLOSED），同时调用微信关闭订单接口让微信侧同步关闭，避免用户超时后仍能拉起支付。微信关闭接口：POST /v3/pay/transactions/out-trade-no/{out_trade_no}/close（body 传 mchid）。注意：微信侧关闭订单后，该 out_trade_no 不能再次下单（同一 appid 下唯一约束），因此关闭后如用户还想购买，需生成新的 out_trade_no。

```java
// OrderCloseTask.java —— 定时关闭超时未支付订单
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;
import java.util.List;

@Component
public class OrderCloseTask {

    private final OrderMapper orderMapper;
    private final WxPayCloseService wxPayCloseService;

    public OrderCloseTask(OrderMapper orderMapper, WxPayCloseService wxPayCloseService) {
        this.orderMapper = orderMapper;
        this.wxPayCloseService = wxPayCloseService;
    }

    /** 每 5 分钟扫描一次，关闭超过 30 分钟未支付的订单 */
    @Scheduled(cron = "0 */5 * * * ?")
    public void closeTimeoutOrders() {
        LocalDateTime deadline = LocalDateTime.now().minusMinutes(30);
        List<Order> pendingOrders = orderMapper.selectPendingBefore(deadline);
        for (Order order : pendingOrders) {
            try {
                // 1. 本地状态流转（幂等：仅 PENDING -> CLOSED）
                int updated = orderMapper.markClosed(order.getOutTradeNo());
                if (updated == 0) {
                    continue; // 已被支付回调抢占
                }
                // 2. 通知微信侧关闭订单，防止用户超时后仍可支付
                wxPayCloseService.close(order.getOutTradeNo());
                log.info("订单已超时关闭: {}", order.getOutTradeNo());
            } catch (Exception e) {
                log.error("关闭订单失败: {}", order.getOutTradeNo(), e);
            }
        }
    }
}
```

## 支付对账

支付对账是订单状态机的最终校验手段：以微信支付官方对账单为准，逐笔核对本地订单表，发现并修复「回调丢失、金额不一致、多记漏记」等问题。对账频率通常是 T+1（每日凌晨下载昨日账单核对）。对账单按日生成，包含当日全部交易与退款明细，格式为 CSV（UTF-8），支持 GZIP 压缩下载。下载接口为 GET /v3/bill/tradebill?bill_date=20260819&bill_type=ALL&tar_type=GZIP，返回 download_url，再请求该 URL 得到文件字节。

对账比对逻辑：把对账单的「商户订单号 + 订单金额」与本地订单表「out_trade_no + amount_fen + status」做全量比对，归类为三类差异——微信有本地无（回调丢失，调查单接口补单）、本地有微信无（本地订单未真实成交，通常是下单未支付或测试数据）、金额不一致（高危，需人工核查）。对账脚本产出差异报告供财务与开发处理。详细的对账文件格式、解析代码与差异处理流程见 10.4。

```text
对账与回调的关系：
1. 回调保证时效 —— 支付成功后秒级通知，支撑用户侧实时体验
2. 对账保证正确 —— T+1 全量核对，兜底回调丢失与数据错误
3. 掉单补偿 —— 对账发现本地缺单时，调查单接口补更新（见下方异常处理）
4. 差异闭环 —— 每笔差异登记、处理、复核，形成月度资金平衡报表
5. 对账口径 —— 交易金额、退款金额、手续费、结算金额分列核对
6. 详情见 10.4 —— 对账文件格式、下载解析、差异处理完整实践
```

## 支付异常处理

支付链路常见的异常有四类：掉单（用户支付成功但回调未达）、重复支付（同一订单被支付两次，实际表现为重复回调或两个微信订单号）、金额不一致（回调金额与订单金额不符）、回调伪造（非微信服务器发来的请求）。处理原则：回调只认「验签通过 + 金额一致 + 状态机允许」，任何异常都进入告警与人工核查流程，绝不静默吞掉。

掉单补偿依赖微信查单接口：GET /v3/pay/transactions/out-trade-no/{out_trade_no}?mchid={mchid}，返回该订单在微信侧的最新交易状态（trade_state 为 SUCCESS/NOTPAY/CLOSED/REFUND 等）。补偿策略分两层：用户触发层（前端支付后查询，见 10.2 场景二）+ 定时任务层（扫描超过 10 分钟仍为 PENDING 的订单，调查单接口核对，微信侧已支付则补更新本地）。查询到已支付但本地仍是 PENDING 时，走与回调相同的幂等更新逻辑。

```java
// OrderSyncService.java —— 掉单补偿：主动查单并补更新
import com.wechat.pay.java.service.payments.jsapi.JsapiService;
import com.wechat.pay.java.service.payments.jsapi.model.QueryOrderByOutTradeNoRequest;
import com.wechat.pay.java.service.payments.model.Transaction;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Service;

import java.time.LocalDateTime;
import java.util.List;

@Service
public class OrderSyncService {

    private final JsapiService jsapiService;
    private final WechatPayProperties props;
    private final OrderMapper orderMapper;

    public OrderSyncService(JsapiService jsapiService, WechatPayProperties props,
                            OrderMapper orderMapper) {
        this.jsapiService = jsapiService;
        this.props = props;
        this.orderMapper = orderMapper;
    }

    /** 每 10 分钟扫描：待支付超过 10 分钟的订单主动查单，兜底回调丢失 */
    @Scheduled(cron = "0 */10 * * * ?")
    public void syncPendingOrders() {
        List<Order> pending = orderMapper.selectPendingBefore(LocalDateTime.now().minusMinutes(10));
        for (Order order : pending) {
            try {
                Transaction tx = queryFromWechat(order.getOutTradeNo());
                if ("SUCCESS".equals(tx.getTradeState())) {
                    // 微信侧已支付 -> 幂等补更新本地订单（金额校验同样执行）
                    orderMapper.markPaid(order.getOutTradeNo(), tx.getTransactionId(),
                            OrderStatus.PAID);
                    log.info("掉单补偿成功: {}", order.getOutTradeNo());
                } else if ("CLOSED".equals(tx.getTradeState())) {
                    orderMapper.markClosed(order.getOutTradeNo());
                }
            } catch (Exception e) {
                log.error("查单失败: {}", order.getOutTradeNo(), e);
            }
        }
    }

    /** 查单接口：GET /v3/pay/transactions/out-trade-no/{out_trade_no} */
    public Transaction queryFromWechat(String outTradeNo) {
        QueryOrderByOutTradeNoRequest request = new QueryOrderByOutTradeNoRequest();
        request.setMchid(props.getMerchantId());
        request.setOutTradeNo(outTradeNo);
        return jsapiService.queryOrderByOutTradeNo(request);
    }
}
```

金额不一致校验必须在回调与查单两个入口都执行：order.amountFen != paidAmountFen 时抛出异常、记录告警、通知人工核查，同时拒绝更新订单状态。重复支付则靠 out_trade_no 唯一约束天然规避：同一订单号只能对应一笔微信交易，若出现同一 out_trade_no 两个 transaction_id 的极端情况（几乎不可能），以金额校验 + 人工核查收口。

## 应用场景实战

### 场景一：支付回调的完整落地（验签解密 + 幂等 + 金额校验）

场景：用户支付成功后，微信回调商户后台。后端完成验签解密，校验金额并幂等更新订单，再返回应答。

```java
// PayNotifyController.java —— 完整回调处理（含日志与应答封装）
@RestController
@RequestMapping("/api/pay")
public class PayNotifyController {

    private final NotificationParser parser;
    private final OrderService orderService;
    private static final Logger log = LoggerFactory.getLogger(PayNotifyController.class);

    public PayNotifyController(NotificationConfig config, OrderService orderService) {
        this.parser = new NotificationParser(config);
        this.orderService = orderService;
    }

    @PostMapping("/notify")
    public ResponseEntity<Map<String, String>> notify(
            @RequestBody String body,
            @RequestHeader("Wechatpay-Timestamp") String timestamp,
            @RequestHeader("Wechatpay-Nonce") String nonce,
            @RequestHeader("Wechatpay-Signature") String signature,
            @RequestHeader("Wechatpay-Serial") String serial) {

        log.info("收到支付回调, serial={}, timestamp={}", serial, timestamp);

        try {
            // 1. 验签 + 解密（SDK 内部完成，验签失败抛异常）
            Transaction tx = parser.parse(
                    new RequestParam.Builder()
                            .serialNumber(serial)
                            .nonce(nonce)
                            .signature(signature)
                            .timestamp(timestamp)
                            .body(body)
                            .build(),
                    Transaction.class);

            // 2. 幂等更新订单（内部含金额一致性校验与状态机校验）
            orderService.handlePaid(tx.getOutTradeNo(), tx.getTransactionId(),
                    tx.getAmount().getTotal(), tx.getTradeState());

            // 3. 返回成功应答
            return ResponseEntity.ok(Map.of("code", "SUCCESS", "message", "成功"));
        } catch (Exception e) {
            log.error("支付回调处理失败", e);
            // 返回失败应答，微信会按重试策略再次推送（最长 24 小时）
            return ResponseEntity.ok(Map.of("code", "FAIL", "message", "失败"));
        }
    }
}
```

```text
应答规则：
1. 处理成功 —— HTTP 200 + {"code":"SUCCESS","message":"成功"}，微信停止重试
2. 处理失败 —— 任意非 SUCCESS 应答或非 200 状态码，微信按策略重试
3. 重试策略 —— 首次失败后 15 秒重试，间隔逐步拉长，最长持续 24 小时
4. 业务异常 —— 金额不一致、订单不存在等也必须返回 FAIL 并告警，避免静默丢单
5. 防重放 —— 校验 Wechatpay-Timestamp 与服务器时间差在 5 分钟内
```

## 最佳实践与踩坑记录

### 最佳实践

1. 回调接口用 SDK 的 NotificationParser 统一处理验签解密，禁止手写解密逻辑（密钥管理、AAD、算法细节易错）
2. 回调处理必须幂等：以「条件更新 + 状态机校验」实现，重复回调直接返回 SUCCESS 应答
3. 回调、查单两个入口都执行金额一致性校验，不一致立即告警并拒绝更新，交由人工核查
4. 订单状态流转收敛到枚举的 transitionTo 方法统一校验，禁止在业务代码里直接 setStatus
5. 掉单补偿双保险：用户触发查单 + 定时任务批量查单，补偿走与回调相同的幂等更新
6. 回调日志必须记录完整报文摘要（out_trade_no、transaction_id、金额、状态），排查问题靠日志
7. 回调接口与查单接口都做限流与鉴权（验签本身就是鉴权，查单接口需登录态校验）
8. 超时关闭订单先本地流转再调微信关闭，本地关闭成功但微信关闭失败的要记日志补偿重试

### 踩坑记录

坑 1：回调处理未完成就返回 SUCCESS
结论：业务更新失败但应答成功，微信不再重试，订单永远停在待支付。
原因：把「收到回调」当成了「处理成功」，异常被吞掉后直接返回 SUCCESS。
解法：只有验签、解密、业务更新全部成功才返回 SUCCESS；任何异常返回 FAIL 让微信重试。

坑 2：验签失败（平台证书过期或序列号不匹配）
结论：回调接口报验签失败，订单无法更新。
原因：微信支付平台证书过期，或商户缓存了旧的平台证书。
解法：使用 SDK 的 RSAAutoCertificateConfig 自动轮换平台证书；自定义缓存需实现证书到期自动刷新。

坑 3：解密失败（APIv3 密钥错误或 associated_data 缺失）
结论：回调报解密失败或抛 AES 解密异常。
原因：APIv3 密钥配置错误（如填成 APIv2 密钥），或手动解密时漏用 resource.associated_data。
解法：核对商户平台 APIv3 密钥；解密参数 nonce、associated_data、ciphertext 必须取自 resource 且类型正确。

坑 4：未做幂等，重复回调重复发券/加积分
结论：用户收到多份权益，或积分余额翻倍。
原因：微信回调会重试，处理逻辑没有幂等保护，每次回调都执行了一遍加权益。
解法：订单状态条件更新（仅 PENDING 可置 PAID）+ 业务动作（发券）以订单状态为前置校验，重复回调直接跳过。

坑 5：金额不一致未校验，被低金额回调污染订单
结论：恶意或异常回调把订单标记为已支付，金额与订单不符。
原因：只校验了订单号，没有校验支付金额与订单金额一致。
解法：回调与查单入口都校验 amount.total == order.amountFen，不一致抛异常、告警、拒绝更新。

坑 6：回调接口没做时间戳校验，被重放攻击
结论：攻击者重放历史回调报文，反复触发业务动作。
原因：未校验 Wechatpay-Timestamp 与当前时间的差值。
解法：验签通过后校验时间戳在 5 分钟窗口内；SDK 部分版本需自行实现，按文档补充。

坑 7：已关闭订单被迟到的回调改成已支付
结论：订单已关闭退款流程，又变回已支付，状态与资金矛盾。
原因：更新 SQL 没有 status 条件，或状态机校验缺失。
解法：所有状态更新走条件 SQL（WHERE status = 'PENDING'）与 transitionTo 校验，非法流转直接拒绝。

坑 8：掉单无补偿，用户付了钱订单一直待支付
结论：回调丢失（网络抖动、服务重启、应答超时）后订单卡在待支付，用户投诉。
原因：只依赖回调，没有查单兜底机制。
解法：定时任务扫描待支付订单调查单接口补更新；前端支付成功页也主动触发一次查单。
