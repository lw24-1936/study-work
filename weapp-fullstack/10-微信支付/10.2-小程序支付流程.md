## 概述

小程序支付的完整链路是「前端下单 -> 后端创建订单 -> 后端调用微信 JSAPI 下单接口获取 prepay_id -> 后端生成支付参数并签名 -> 小程序 wx.requestPayment 拉起收银台 -> 用户支付 -> 前后端双确认支付结果」。其中，统一下单与支付参数签名必须发生在服务端（涉及商户私钥，绝不能在客户端完成），小程序端只负责展示与拉起收银台。本篇章讲解链路中的每一步：JSAPI 下单 API、prepay_id 的用法、支付参数的五要素与 RSA 签名、wx.requestPayment 的调用与结果处理，最后给出完整时序。

```text
本章核心要点：
1. 下单接口 —— POST /v3/pay/transactions/jsapi，返回 prepay_id（有效期 2 小时）
2. 支付参数 —— appId / timeStamp / nonceStr / package / signType / paySign 六要素
3. 签名算法 —— 待签名串按固定顺序拼接，用商户私钥做 SHA256withRSA 签名
4. 拉起支付 —— wx.requestPayment 携带六要素，拉起微信收银台
5. 结果确认 —— 前端 success 不等于支付成功，以后端收到微信回调为准
6. 金额单位 —— 所有金额一律用「分」为单位，避免浮点精度问题
```

## 支付流程总览与统一下单

小程序支付（JSAPI 支付）的核心是「服务端统一下单」。用户点击支付后，小程序把订单号发给自己的后端，后端确认订单存在且金额正确后，调用微信支付 v3 的 JSAPI 下单接口，微信返回 prepay_id（预支付交易会话标识）。prepay_id 是后续生成支付参数的关键凭据，有效期 2 小时，过期后需要重新下单。

接口定义：POST https://api.mch.weixin.qq.com/v3/pay/transactions/jsapi，请求体包含 appid、mchid、description（商品描述）、out_trade_no（商户订单号，商户侧唯一）、notify_url（支付结果回调地址）、amount（total 为订单金额，单位分，currency 为 CNY）、payer（openid 为用户在小程序内的 openid）。响应体返回 prepay_id。注意：out_trade_no 由商户自己生成并保证唯一，微信侧以「appid + out_trade_no」唯一约束，重复使用会报错。

```text
JSAPI 下单关键点：
1. 接口路径 —— POST /v3/pay/transactions/jsapi（v3 版本，请求需商户私钥签名）
2. 请求体 —— appid/mchid/description/out_trade_no/notify_url/amount/payer
3. 金额单位 —— amount.total 单位为分，如 9.90 元传 990
4. 返回结果 —— 响应体含 prepay_id，2 小时内有效
5. 唯一约束 —— 同一 appid 下 out_trade_no 不可重复，重复调用返回错误
6. openid 来源 —— 用户登录时 code2session 接口返回的 openid（见 09.1）
```

Java 服务端使用官方 SDK 的 JsapiService 完成下单，代码简洁且自动处理签名：

```java
// WxPayService.java —— JSAPI 统一下单
import com.wechat.pay.java.service.payments.jsapi.JsapiService;
import com.wechat.pay.java.service.payments.jsapi.model.Amount;
import com.wechat.pay.java.service.payments.jsapi.model.Payer;
import com.wechat.pay.java.service.payments.jsapi.model.PrepayRequest;
import com.wechat.pay.java.service.payments.jsapi.model.PrepayResponse;
import org.springframework.stereotype.Service;

@Service
public class WxPayService {

    private final JsapiService jsapiService;
    private final WechatPayProperties props;

    public WxPayService(JsapiService jsapiService, WechatPayProperties props) {
        this.jsapiService = jsapiService;
        this.props = props;
    }

    /**
     * 统一下单，返回 prepay_id。
     *
     * @param openid      用户 openid（小程序内唯一）
     * @param outTradeNo  商户订单号（后端生成，唯一）
     * @param amountFen   订单金额，单位分
     * @param description 商品描述（显示在收银台，建议简短如「XX商城-订单20260820120001」）
     */
    public String createJsapiOrder(String openid, String outTradeNo,
                                   long amountFen, String description) {
        PrepayRequest request = new PrepayRequest();
        request.setAppid(props.getAppId());
        request.setMchid(props.getMerchantId());
        request.setDescription(description);
        request.setOutTradeNo(outTradeNo);
        request.setNotifyUrl(props.getNotifyUrl());

        Amount amount = new Amount();
        amount.setTotal(amountFen);
        amount.setCurrency("CNY");
        request.setAmount(amount);

        Payer payer = new Payer();
        payer.setOpenid(openid);
        request.setPayer(payer);

        PrepayResponse response = jsapiService.prepay(request);
        return response.getPrepayId();
    }
}
```

下单前建议在服务端把订单持久化到数据库（订单表包含 out_trade_no、金额、状态等字段），再调微信下单接口。顺序是：先落库（状态待支付）再调微信，这样即使微信下单成功但响应丢失（超时），也可以靠订单表 + 查单接口补偿。下面对应的订单创建与下单编排：

```java
// OrderController.java —— 创建订单并返回支付参数
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService orderService;
    private final WxPayService wxPayService;
    private final PaySignService paySignService;

    public OrderController(OrderService orderService, WxPayService wxPayService,
                           PaySignService paySignService) {
        this.orderService = orderService;
        this.wxPayService = wxPayService;
        this.paySignService = paySignService;
    }

    /**
     * 用户点击「立即支付」时调用：
     * 1. 校验订单归属与状态（只能支付自己的待支付订单）
     * 2. 调微信统一下单，拿 prepay_id
     * 3. 生成支付参数并返回给小程序
     */
    @PostMapping("/{orderId}/pay")
    public Result<Map<String, String>> pay(@PathVariable Long orderId,
                                           @RequestAttribute Long userId) throws Exception {
        // 1. 查订单并校验：属于当前用户、状态为待支付、未超时
        Order order = orderService.getOwnOrder(orderId, userId);
        orderService.assertPayable(order);

        // 2. 微信统一下单
        String prepayId = wxPayService.createJsapiOrder(
                order.getOpenid(), order.getOutTradeNo(),
                order.getAmountFen(), order.getDescription());

        // 3. 生成小程序端支付参数（含 paySign）
        Map<String, String> payParams = paySignService.buildPayParams(prepayId);
        return Result.ok(payParams);
    }
}
```

## 支付参数生成与签名

拿到 prepay_id 后，后端需要生成一组「支付参数」返回给小程序，wx.requestPayment 才能拉起收银台。支付参数包含六个字段：appId（小程序 AppID）、timeStamp（秒级时间戳，字符串）、nonceStr（32 位以内的随机字符串）、package（固定格式 "prepay_id=" + prepayId）、signType（固定 "RSA"）、paySign（签名值）。其中 paySign 是后端用商户私钥对「待签名串」做 SHA256withRSA 签名的结果，保证参数没有被篡改。

待签名串的拼接格式非常严格：五个字段（appId、timeStamp、nonceStr、package）各占一行，行与行之间用换行符 \n 连接，最后一行也要以 \n 结尾。顺序不能变，漏掉任何一行或行尾少一个换行都会导致签名不一致，微信端验签失败后收银台直接报「支付验证签名失败」。

```text
签名规则：
1. 待签名串 —— appId + "\n" + timeStamp + "\n" + nonceStr + "\n" + package + "\n"
2. 签名算法 —— SHA256withRSA，私钥为商户 API 私钥（apiclient_key.pem）
3. 输出格式 —— Base64 编码的签名值，即 paySign
4. signType —— 固定传 RSA（v3 签名方式）
5. package —— 固定格式 prepay_id=xxxx，前缀不能丢
6. timeStamp —— 秒级（10 位数字），传毫秒会导致签名不匹配
```

```java
// PaySignService.java —— 生成 wx.requestPayment 所需支付参数与签名
import com.wechat.pay.java.core.util.NonceUtil;
import org.springframework.stereotype.Service;

import java.nio.charset.StandardCharsets;
import java.security.PrivateKey;
import java.security.Signature;
import java.util.Base64;
import java.util.HashMap;
import java.util.Map;

@Service
public class PaySignService {

    private final PrivateKey merchantPrivateKey;
    private final WechatPayProperties props;

    public PaySignService(PrivateKey merchantPrivateKey, WechatPayProperties props) {
        this.merchantPrivateKey = merchantPrivateKey;
        this.props = props;
    }

    /** 生成小程序端支付参数（六要素） */
    public Map<String, String> buildPayParams(String prepayId) throws Exception {
        String timeStamp = String.valueOf(System.currentTimeMillis() / 1000); // 秒级
        String nonceStr = NonceUtil.createNonce(32);
        String packageValue = "prepay_id=" + prepayId;

        // 待签名串：五段内容各占一行，每行以 \n 结尾，顺序固定
        String message = props.getAppId() + "\n"
                + timeStamp + "\n"
                + nonceStr + "\n"
                + packageValue + "\n";

        // SHA256withRSA 签名并 Base64 编码
        Signature signer = Signature.getInstance("SHA256withRSA");
        signer.initSign(merchantPrivateKey);
        signer.update(message.getBytes(StandardCharsets.UTF_8));
        String paySign = Base64.getEncoder().encodeToString(signer.sign());

        Map<String, String> params = new HashMap<>();
        params.put("appId", props.getAppId());
        params.put("timeStamp", timeStamp);
        params.put("nonceStr", nonceStr);
        params.put("package", packageValue);
        params.put("signType", "RSA");
        params.put("paySign", paySign);
        return params;
    }
}
```

签名用的 PrivateKey 由商户私钥文件加载，可在配置类中统一构建：

```java
// PrivateKeyConfig.java —— 加载商户 API 私钥
import com.wechat.pay.java.core.util.PemUtil;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.nio.file.Files;
import java.nio.file.Paths;
import java.security.PrivateKey;

@Configuration
public class PrivateKeyConfig {

    /** 从 apiclient_key.pem 加载商户私钥，供支付参数签名使用 */
    @Bean
    public PrivateKey merchantPrivateKey(WechatPayProperties props) throws Exception {
        String pem = Files.readString(Paths.get(props.getPrivateKeyPath()));
        return PemUtil.loadPrivateKey(pem);
    }
}
```

## wx.requestPayment 与支付结果处理

小程序端拿到支付参数后调用 wx.requestPayment 拉起微信收银台。该 API 只在用户触发（点击按钮）时调用，参数全部来自后端返回，前端不做任何拼装与计算。success 回调代表用户完成了支付操作（收银台提示支付成功），fail 回调包含失败原因：用户取消时 errMsg 为 "requestPayment:fail cancel"，其它为系统错误或签名错误。无论 success 还是 fail，都不能作为订单状态的最终依据。

支付结果的最终依据是「服务端收到微信支付回调」（见 10.3）：微信在用户支付成功后异步通知商户后台，后台更新订单状态。因此前端在 success 后应当主动向后端查询订单状态确认，而不是直接跳转「支付成功页」——这是防止「前端伪造支付成功」的关键设计。查询接口返回订单真实状态（PAID/PENDING），以查询结果为准渲染页面。

```text
wx.requestPayment 参数详解：
1. timeStamp —— 时间戳，秒级字符串，后端生成
2. nonceStr —— 随机字符串，32 位以内，后端生成
3. package —— prepay_id=xxx，后端生成，前缀不能省略
4. signType —— 固定 "RSA"
5. paySign —— 后端 RSA 签名，防篡改
6. 返回码 —— success 仅代表支付操作完成；fail 中 errMsg 含 cancel 表示用户取消
```

```js
// pages/order/pay.js —— 拉起微信支付收银台
const app = getApp();

Page({
  data: {
    orderId: '',
    paying: false
  },

  // 用户点击「立即支付」
  onPayTap() {
    if (this.data.paying) return;
    this.setData({ paying: true });

    // 1. 请求后端：创建支付并返回支付参数
    wx.request({
      url: `${app.globalData.baseUrl}/api/orders/${this.data.orderId}/pay`,
      method: 'POST',
      header: { Authorization: `Bearer ${wx.getStorageSync('token')}` },
      success: (res) => {
        const payParams = res.data.data;
        // 2. 拉起微信收银台
        wx.requestPayment({
          timeStamp: payParams.timeStamp,
          nonceStr: payParams.nonceStr,
          package: payParams.package,
          signType: payParams.signType,
          paySign: payParams.paySign,
          success: () => {
            // 3a. 用户完成支付：以服务端订单状态为准确认
            this.confirmOrder();
          },
          fail: (err) => {
            // 3b. 失败或取消：err.errMsg 含 "cancel" 表示用户主动取消
            const canceled = (err.errMsg || '').indexOf('cancel') > -1;
            wx.showToast({
              title: canceled ? '已取消支付' : '支付未完成，请重试',
              icon: 'none'
            });
          }
        });
      },
      fail: () => wx.showToast({ title: '网络异常，请重试', icon: 'none' }),
      complete: () => this.setData({ paying: false })
    });
  },

  // 支付后主动查询订单状态，以后端为准
  confirmOrder() {
    wx.request({
      url: `${app.globalData.baseUrl}/api/orders/${this.data.orderId}`,
      method: 'GET',
      header: { Authorization: `Bearer ${wx.getStorageSync('token')}` },
      success: (res) => {
        if (res.data.data.status === 'PAID') {
          wx.redirectTo({ url: `/pages/order/detail?orderId=${this.data.orderId}` });
        } else {
          // 回调可能延迟，提示用户稍后查看
          wx.showToast({ title: '支付结果确认中，请稍后刷新', icon: 'none' });
        }
      },
      fail: () => wx.showToast({ title: '网络异常', icon: 'none' })
    });
  }
});
```

## 支付时序

把整条链路按时间展开，前端（小程序）、商户后端（SpringBoot）、微信支付三方的交互顺序如下。理解时序图能帮助定位「哪个环节断了」：用户侧断在拉单，服务端断在下单接口，微信侧断在收银台，结果断在回调。

```text
支付完整时序：
1. 用户在小程序点击「立即支付」，前端把订单号发给商户后端
2. 商户后端校验订单（归属、状态、金额）后，先落库订单（待支付）
3. 商户后端调用微信 JSAPI 下单接口，携带 appid/mchid/out_trade_no/amount/payer
4. 微信支付校验通过，返回 prepay_id（2 小时有效）
5. 商户后端生成六要素支付参数（含 SHA256withRSA 的 paySign）返回小程序
6. 小程序 wx.requestPayment 拉起微信收银台，用户输入密码/指纹完成支付
7. 微信收银台向用户展示支付成功，触发小程序 success 回调
8. 微信支付异步 POST 支付结果到商户 notify_url（可重复多次，见 10.3）
9. 商户后端验签解密回调，幂等更新订单为已支付（PAID），返回 SUCCESS
10. 小程序前端 success 后调订单查询接口，以服务端状态为准跳转结果页
```

```text
角色职责划分：
1. 小程序端 —— 只做：传订单号、调 wx.requestPayment、展示结果、查询订单状态
2. 商户后端 —— 做：下单、签名、收回调、更新订单、退款、对账（核心逻辑全在这）
3. 微信支付 —— 做：校验商户请求、收用户钱、发回调、结算到商户对公账户
4. 金额规则 —— 前端展示金额来自后端订单，收银台金额以 prepay 下单金额为准
5. 超时规则 —— 用户 30 分钟未支付，后端应主动关闭订单并同步微信（见 10.3）
6. 双确认 —— 前端 success + 后端回调都收到才最终确认，缺一不可
```

## 应用场景实战

### 场景一：商品订单完整支付链路（后端下单 + 前端拉起）

场景：用户在商品详情页下单后跳转订单页，点击「立即支付」完成付款。后端编排「创建订单 -> 统一下单 -> 返回支付参数」，前端拉起收银台。

```java
// OrderService.java —— 订单创建与支付编排
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {

    private final OrderMapper orderMapper;
    private final WxPayService wxPayService;
    private final PaySignService paySignService;

    public OrderService(OrderMapper orderMapper, WxPayService wxPayService,
                        PaySignService paySignService) {
        this.orderMapper = orderMapper;
        this.wxPayService = wxPayService;
        this.paySignService = paySignService;
    }

    /** 创建订单（用户提交订单时调用），返回商户订单号 */
    @Transactional
    public String createOrder(Long userId, String openid, Long goodsId, long amountFen) {
        Order order = new Order();
        order.setUserId(userId);
        order.setOpenid(openid);
        order.setGoodsId(goodsId);
        order.setAmountFen(amountFen);
        order.setStatus(OrderStatus.PENDING);
        order.setOutTradeNo(generateOutTradeNo()); // 如 202608201200019999 规则生成
        orderMapper.insert(order);
        return order.getOutTradeNo();
    }

    /** 支付编排：校验 -> 统一下单 -> 生成支付参数 */
    public Map<String, String> pay(Long userId, Long orderId) throws Exception {
        Order order = orderMapper.selectById(orderId);
        if (order == null || !order.getUserId().equals(userId)) {
            throw new BizException("订单不存在");
        }
        if (order.getStatus() != OrderStatus.PENDING) {
            throw new BizException("订单状态不允许支付");
        }
        String prepayId = wxPayService.createJsapiOrder(
                order.getOpenid(), order.getOutTradeNo(),
                order.getAmountFen(), "示例商城-商品订单");
        return paySignService.buildPayParams(prepayId);
    }

    private String generateOutTradeNo() {
        // 规则：yyyyMMddHHmmss + 6 位随机数，保证并发下唯一
        return LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMddHHmmss"))
                + String.format("%06d", ThreadLocalRandom.current().nextInt(1000000));
    }
}
```


### 场景二：支付结果双确认与失败兜底

场景：用户支付成功后回调延迟到达，前端需要可靠的「支付成功」反馈；支付失败或取消后允许重新发起支付。双确认方案：前端 success 后查订单状态；查询不到已支付时，后端主动调微信查单接口兜底（查单接口见 10.3）。

```js
// pages/order/pay.js —— 支付结果双确认（带查单兜底）
confirmOrderWithFallback() {
  // 第一次：查本地订单状态
  this.queryOrder((order) => {
    if (order.status === 'PAID') {
      wx.redirectTo({ url: `/pages/order/detail?orderId=${this.data.orderId}` });
      return;
    }
    // 第二次：后端主动查微信侧交易状态（兜底掉单）
    wx.request({
      url: `${app.globalData.baseUrl}/api/orders/${this.data.orderId}/sync`,
      method: 'POST',
      header: { Authorization: `Bearer ${wx.getStorageSync('token')}` },
      success: (res) => {
        const synced = res.data.data;
        if (synced.status === 'PAID') {
          wx.redirectTo({ url: `/pages/order/detail?orderId=${this.data.orderId}` });
        } else {
          wx.showToast({ title: '支付未完成', icon: 'none' });
        }
      }
    });
  });
},

queryOrder(cb) {
  wx.request({
    url: `${app.globalData.baseUrl}/api/orders/${this.data.orderId}`,
    method: 'GET',
    header: { Authorization: `Bearer ${wx.getStorageSync('token')}` },
    success: (res) => cb(res.data.data)
  });
}
```

```java
// OrderController.java —— 订单状态同步接口（主动查微信侧兜底）
@PostMapping("/{orderId}/sync")
public Result<OrderVO> sync(@PathVariable Long orderId,
                            @RequestAttribute Long userId) {
    Order order = orderService.getOwnOrder(orderId, userId);
    // 调微信查单接口，若微信侧已支付则补更新本地订单（掉单补偿，见 10.3）
    orderService.syncFromWechat(order);
    return Result.ok(orderService.toVO(order));
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 统一下单的金额必须来自服务端订单表，前端传任何金额字段都视为无效，杜绝改价攻击
2. 支付参数六要素全部由后端生成，小程序端只透传，paySign 签名保证参数不可篡改
3. 前端 success 回调后一律查询后端订单状态再跳转，禁止直接展示「支付成功」页
4. 金额单位统一用分（long），Java 用 long、数据库用 BIGINT，禁止用 double 存金额
5. 下单失败/超时允许用户重试，但 out_trade_no 每次重新生成，同一订单可重复下单（同一 prepay 重新获取）
6. 支付按钮加防重复点击（paying 标志），避免用户连点触发多次下单
7. 生产环境在支付接口前后埋点日志（下单请求/响应、支付参数返回），便于定位问题
8. 订单创建与统一下单失败时做好补偿：订单落库先于微信下单，微信侧失败订单可关闭重下

### 踩坑记录

坑 1：timeStamp 传了毫秒导致签名验证失败
结论：wx.requestPayment 报「支付验证签名失败」，收银台无法拉起。
原因：timeStamp 必须是秒级 10 位数字，代码里直接用了 System.currentTimeMillis() 的毫秒值。
解法：统一用 System.currentTimeMillis() / 1000 生成，返回前端前断言长度等于 10。

坑 2：金额单位错误（元当分传）
结论：用户支付金额与订单金额差 100 倍，或下单接口报金额参数错误。
原因：微信支付金额单位为分，接口文档写的是 total 以「分」为单位，实现时按元传入。
解法：金额字段统一用 long 类型以分存储；下单与回调比对时都做单位自检，必要时加日志。

坑 3：package 参数漏掉 "prepay_id=" 前缀
结论：收银台拉起后直接报「参数格式有误」或签名失败。
原因：package 字段必须完整传 "prepay_id=xxxx"，只传了 prepay_id 的值。
解法：拼装参数时固定 package = "prepay_id=" + prepayId，并加单元测试断言前缀。

坑 4：签名串顺序或换行符错误
结论：同样的参数在本地自测成功，线上 wx.requestPayment 报签名错误。
原因：待签名串顺序必须是 appId/timeStamp/nonceStr/package 且每行以 \n 结尾，顺序或末尾换行不对即失败。
解法：严格按文档拼接；把「生成签名」与「验签」封装成独立方法并写单测，用固定样例验证输出。

坑 5：前端 success 就当支付成功，未做后端确认
结论：用户未真实付款也能伪造 success 跳转成功页，或回调未到导致订单状态不一致。
原因：wx.requestPayment 的 success 仅代表用户完成支付操作，且前端可被篡改。
解法：所有业务放行（发货、发券）必须以服务端收到微信回调更新后的订单状态为准；前端只做引导。

坑 6：prepay_id 过期后仍用旧参数拉起支付
结论：用户下单后长时间未支付，再点击支付时报「订单已过期」或拉起失败。
原因：prepay_id 有效期 2 小时，过期后 package 中的 prepay_id 失效。
解法：支付前校验订单创建时间，超时重新调统一下单获取新 prepay_id；同时配合订单超时关闭机制。

坑 7：openid 与 appid 不匹配
结论：统一下单报「appid 与 openid 不匹配」。
原因：用户在小程序 A 登录拿到 openid，却在绑定商户号的小程序 B 下单，或用了公众号的 openid。
解法：下单前校验 openid 归属；一个用户多端时分别存储各端 openid，下单用与当前 AppID 对应的那个。

坑 8：out_trade_no 重复导致下单失败
结论：同一订单号第二次下单报「商户订单号重复」。
原因：out_trade_no 在同一 appid 下必须唯一，重试逻辑复用了旧订单号。
解法：每次创建支付都重新生成 out_trade_no（时间戳+随机数）；若复用旧号，需先查询原交易状态。
