## 概述

上线只是开始，让服务「看得见、可预警、能恢复」才是运维的核心。监控体系分四层：日志（发生了什么）、指标（现在什么状态）、告警（什么时候通知人）、预案（出事了怎么办）。小程序业务对可用性敏感，一次 5 分钟的全站故障就可能丢掉当天大部分订单，所以监控不是可选项，而是生产系统的组成部分。本章覆盖 logback 日志规范与集中收集（ELK/Loki）、Prometheus + Grafana 指标监控（含 Spring Boot Actuator 接入）、Alertmanager 告警（钉钉/企微通知）、应急预案与容量规划，学完可以搭出一套够用的小团队监控体系。

```text
监控体系四层：
1. 日志 —— 记录每次请求与异常，logback 落盘 + Loki/ELK 集中检索
2. 指标 —— 数值化状态（QPS、错误率、响应时间、JVM 内存），Prometheus 采集
3. 告警 —— 指标越界自动通知（钉钉/企微/邮件），Alertmanager 路由分发
4. 预案 —— 故障响应流程、回滚预案、降级方案，提前演练成文
```

## 日志收集

日志是排查问题的第一现场。Java 侧用 logback（Spring Boot 默认）按天滚动输出到固定目录，格式统一（时间、级别、线程、logger、消息），配合 logrotate 做系统级切割。单机 tail 够用，多机或历史检索需求出现后引入集中收集：轻量方案是 Loki（只收文本、按标签索引，Grafana 同生态），重量方案是 ELK（Elasticsearch + Logstash + Kibana，全文检索能力强但资源占用高）。

```xml
<!-- src/main/resources/logback-spring.xml —— 生产日志配置 -->
<configuration>
    <!-- 控制台输出（开发用） -->
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] %logger{36} - %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <!-- 文件输出：按天滚动，保留 15 天，单文件超 200MB 切割 -->
    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>/opt/weapp/logs/weapp-api.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>/opt/weapp/logs/weapp-api.%d{yyyy-MM-dd}.%i.log</fileNamePattern>
            <timeBasedFileNamingAndTriggeringPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedFNATP">
                <maxFileSize>200MB</maxFileSize>
            </timeBasedFileNamingAndTriggeringPolicy>
            <maxHistory>15</maxHistory>
        </rollingPolicy>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] %logger{36} - %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <!-- 错误日志单独一份，告警与排错直接看 error 文件 -->
    <appender name="ERROR_FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>/opt/weapp/logs/weapp-api-error.log</file>
        <filter class="ch.qos.logback.classic.filter.ThresholdFilter">
            <level>ERROR</level>
        </filter>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>/opt/weapp/logs/weapp-api-error.%d{yyyy-MM-dd}.log</fileNamePattern>
            <maxHistory>30</maxHistory>
        </rollingPolicy>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] %logger{36} - %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
        <appender-ref ref="FILE"/>
        <appender-ref ref="ERROR_FILE"/>
    </root>
</configuration>
```

```text
日志规范：
1. 日志级别：生产 INFO 起步，DEBUG 只在排查时临时开（改 logback-spring.xml 的 level）
2. 关键埋点：登录、支付下单、支付回调、退款、定时任务执行结果必须打日志
3. 异常日志要带上下文：订单号、用户 ID、请求参数摘要，否则无法定位
4. 禁止在日志里打印敏感信息：密码、token、身份证、手机号全量
5. 每行日志包含 traceId（MDC 注入，全链路关联），跨服务排查必备
6. 日志与代码一样要评审：无意义日志是噪音，关键日志缺失是事故隐患
```

系统级日志切割（logrotate）防止日志无限增长撑爆磁盘，同时按天归档便于检索：

```shell
# /etc/logrotate.d/weapp —— 应用日志切割配置
/opt/weapp/logs/*.log {
    daily
    rotate 15
    compress
    missingok
    notifempty
    copytruncate        # 先复制再清空，不影响 Java 进程持有的文件句柄
    dateext
}

# 手动测试切割（debug 模式看执行细节）
logrotate -d /etc/logrotate.d/weapp
```

集中收集方案选择：单机或 2-3 台服务器、预算有限，选 Loki + Promtail（资源占用低，Grafana 里和 Prometheus 指标同一入口查看）；日志量大、需要复杂全文检索与聚合分析，选 ELK。两者的日志采集端都只是把日志文件 tail 走，应用侧零改造。

```yaml
# promtail 配置（Loki 采集端，/etc/promtail/config.yml）
server:
  http_listen_port: 9080

positions:
  filename: /var/lib/promtail/positions.yaml

clients:
  - url: http://loki:3100/loki/api/v1/push

scrape_configs:
  - job_name: weapp-api
    static_configs:
      - targets: [localhost]
        labels:
          job: weapp-api
          __path__: /opt/weapp/logs/*.log
```

```text
集中收集要点：
1. Loki 查询语法（LogQL）：{job="weapp-api"} |~ "ERROR" —— 按标签过滤 + 正则匹配
2. Promtail 只增量读取日志文件（positions 记录偏移量），重启不重复采集
3. 日志要按应用/环境打标签（job、env），检索与告警都依赖标签
4. ELK 全量索引成本高，小团队日志量不大时 Loki 性价比明显更高
5. 日志保留策略：应用日志 15-30 天，审计类日志按合规要求更长
6. 错误日志文件（error.log）单独告警：出现 ERROR 即通知，不等指标恶化
```

## 指标监控

指标监控回答「现在系统健康吗」。标准组合是 Prometheus（采集 + 存储 + 告警规则）+ Grafana（可视化面板）。Spring Boot 应用通过 Actuator 暴露指标端点，配合 micrometer-registry-prometheus 把 JVM、HTTP、线程池、连接池指标暴露成 Prometheus 格式，Prometheus 定时抓取，Grafana 画图展示。小程序场景重点盯四类指标：接口 QPS 与错误率、响应时间（P95/P99）、JVM 内存与 GC、数据库连接池。

```xml
<!-- pom.xml 增加依赖 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

```yaml
# application.yml —— 暴露 Prometheus 端点（只对监控网段开放）
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,metrics
  endpoint:
    health:
      show-details: always
  metrics:
    tags:
      application: weapp-api
```

```shell
# 本地验证指标端点
curl http://127.0.0.1:8080/actuator/health
# {"status":"UP","components":{"db":{"status":"UP"},...}}

curl http://127.0.0.1:8080/actuator/prometheus | head -20
# HELP jvm_memory_used_bytes Used bytes of a given JVM memory pool.
# TYPE jvm_memory_used_bytes gauge
# jvm_memory_used_bytes{application="weapp-api",area="heap",id="G1 Eden Space",} 8.45E7
# HELP http_server_requests_seconds_max ...
# http_server_requests_seconds_max{application="weapp-api",method="GET",status="200",uri="/api/order/list",} 0.123
```

```yaml
# prometheus.yml —— Prometheus 采集配置（/etc/prometheus/prometheus.yml）
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: weapp-api
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ['10.0.0.11:8080', '10.0.0.12:8080']

  - job_name: node
    static_configs:
      - targets: ['10.0.0.11:9100', '10.0.0.12:9100']   # node_exporter 采集服务器指标
```

```shell
# 服务器节点指标采集（node_exporter）
wget https://github.com/prometheus/node_exporter/releases/download/v1.8.2/node_exporter-1.8.2.linux-amd64.tar.gz
tar xzf node_exporter-1.8.2.linux-amd64.tar.gz
./node_exporter-1.8.2.linux-amd64/node_exporter &
curl http://127.0.0.1:9100/metrics | head -5
```

```text
核心指标清单：
1. QPS 与错误率 —— http_server_requests_seconds_count / 5xx 计数，接口级聚合
2. 响应时间 —— http_server_requests_seconds（histogram），看 P95/P99 而非平均值
3. JVM —— 堆内存使用（jvm_memory_used_bytes）、GC 次数与耗时（jvm_gc_pause_seconds）
4. 连接池 —— 数据库连接活跃数（hikaricp_connections_active）、等待获取连接次数
5. 服务器 —— CPU（node_cpu_seconds_total）、内存（node_memory_MemAvailable_bytes）、磁盘（node_filesystem_avail_bytes）
6. 业务指标 —— 订单量、支付成功率等自定义 Counter/Gauge，用 @Timed 注解或 Micrometer API 埋点
```

Grafana 负责可视化：数据源指向 Prometheus，导入现成面板（如 Spring Boot 官方 dashboards 编号 12900、服务器面板 1860），把接口成功率、响应时间、JVM 内存做成大屏，管理员打开即知线上状态。

## 告警

告警是监控的出口：Prometheus 根据告警规则周期性评估指标，触发后把告警发给 Alertmanager，Alertmanager 负责去重、分组、静默，并推送到钉钉/企业微信/邮件。告警设计的原则是「少而准」：只告警需要人处理的问题，避免告警轰炸导致麻木。常规阈值：错误率 5 分钟持续超 1%、P95 响应时间超 2 秒、JVM 堆使用率持续超 85%、磁盘使用率超 80%、服务进程 DOWN。

```yaml
# prometheus 告警规则（/etc/prometheus/rules/weapp.yml）
groups:
  - name: weapp-alerts
    rules:
      - alert: ServiceDown
        expr: up{job="weapp-api"} == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 服务不可达"

      - alert: HighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          / sum(rate(http_server_requests_seconds_count[5m])) > 0.01
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "接口错误率超过 1%"

      - alert: HighResponseTime
        expr: |
          histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket[5m]))) > 2
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "接口 P95 响应时间超过 2 秒"

      - alert: HighJvmHeap
        expr: jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"} > 0.85
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "JVM 堆内存使用率超过 85%"

      - alert: DiskAlmostFull
        expr: node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"} < 0.2
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.mountpoint }} 磁盘剩余不足 20%"
```

```yaml
# alertmanager.yml —— 告警路由与通知（钉钉 webhook）
route:
  group_by: ['alertname']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h        # 同一告警 4 小时重复一次，避免轰炸
  receiver: dingtalk

receivers:
  - name: dingtalk
    webhook_configs:
      - url: 'https://oapi.dingtalk.com/robot/send?access_token=你的钉钉机器人token'
        send_resolved: true   # 恢复后也通知
```

```text
告警设计要点：
1. 告警规则必须有 for 持续时长（如 for: 5m），瞬时抖动不打扰人
2. 分级：critical（服务挂、错误率高）立即通知；warning（磁盘、内存）工作时间处理
3. repeat_interval 调大（4 小时起），避免同一告警反复刷屏
4. 钉钉/企微群机器人：群设置添加自定义机器人，拿 webhook 地址配置即可
5. 告警内容要可执行：带上服务名、实例、当前值、阈值，不要只发一串数字
6. 告警规则随业务演进维护：误报多的阈值调高，漏报的补规则
```

## 应急预案

预案解决「出了事怎么办」。没有预案的团队故障时靠现场发挥，有预案的团队按流程执行：发现（告警/用户反馈）→ 评估（影响面、严重级）→ 响应（止血优先）→ 恢复（修复或回滚）→ 复盘（根因、改进项）。止血优先意味着：先恢复服务，再查根因，不要一边故障一边调试。

```text
故障响应流程（RTO 目标 15 分钟内恢复）：
1. 发现 —— 告警触发或用户反馈，值班人确认故障属实并判断影响面
2. 通报 —— 故障群发通告（时间、影响、负责人），30 分钟内无进展升级
3. 止血 —— 首选回滚到上一个稳定版本（rollback.sh 一键执行）
4. 恢复验证 —— 健康检查 + 监控指标确认恢复，通知群解除告警
5. 定位 —— 恢复后复盘根因：日志、指标、变更记录三者对照
6. 改进 —— 输出复盘报告：根因、修复项、防再发措施、责任人、期限
```

回滚预案与降级方案是两类核心预案。回滚针对「新版本有问题」：git 回退 + 发布脚本回滚 + 数据库变更回滚（有 schema 变更时先评估兼容性）。降级针对「依赖有问题」：下游接口超时走本地缓存兜底、Redis 挂了走数据库直读、支付回调延迟则订单状态异步对账补偿。

```text
降级方案示例：
1. 接口降级 —— 核心接口（商品列表）Redis 缓存兜底，缓存失效返回旧缓存而非报错
2. 依赖降级 —— 微信接口超时返回 mock 数据并告警，不拖垮主流程
3. 限流 —— 突发流量对非核心接口限流（Sentinel/Resilience4j），保核心接口
4. 熔断 —— 下游连续失败自动熔断（快速失败），避免线程池耗尽雪崩
5. 静态兜底 —— 管理端首页数据用构建时生成的静态 JSON 兜底
6. 容灾 —— 数据库每日全量备份 + binlog 增量，支持按时间点恢复
```

```text
预案管理要点：
1. 预案要写成文档并放团队可见位置（Wiki），不是存在某个人脑子里
2. 每季度做一次故障演练：手动 kill 进程、断开 Redis、模拟流量尖峰
3. 变更管理：任何发布都有回滚方案，重大变更选低峰期并提前公告
4. 值班机制：告警必须有人响应，明确值班人与升级路径
5. 每次故障必复盘：产出「根因 + 改进项 + 责任人 + 截止日期」四件套
6. 备份要定期演练恢复：没验证过能恢复的备份等于没有备份
```

## 容量规划

容量规划回答「够不够、什么时候要扩容」。方法是对流量做评估：根据日活、单用户请求数、峰值倍数推算 QPS，再对照单实例承载能力（压测得出）计算实例数与带宽需求。2 核 4G 单实例 SpringBoot 通常能扛 200-500 QPS（看业务复杂度），小程序业务日常 QPS 远低于此，真正的压力来自秒杀、活动、节假日流量尖峰。

```text
容量估算方法：
1. 日活预估 —— 小程序日活 1 万，人均每天 50 次接口请求，日请求量 50 万
2. QPS 折算 —— 50 万请求集中在 12 小时，日均 QPS 约 12；峰值按 5-10 倍算，峰值约 60-120 QPS
3. 实例数 —— 单实例按 300 QPS 余量设计，120 QPS 峰值 1 台够用，为冗余上 2 台
4. 带宽 —— 平均响应 5KB，60 QPS 约 2.4Mbps，固定 5M 带宽够日常，活动期临时升配
5. 数据库 —— 连接数 = 实例数 × 每实例连接池大小，2 实例 × 20 = 40 连接，云数据库按 100 连接规格选
6. Redis —— 缓存命中率高（商品、配置、token），1G 内存足够日常，按峰值数据量 2 倍预留
```

扩容策略分垂直与水平：垂直扩容（升 CPU/内存/带宽）几分钟生效，适合临时扛峰值；水平扩容（加实例 + Nginx upstream 接入）是长期方案，无状态服务（JWT）天然支持。扩容触发条件要量化：CPU 持续 70% 以上、P95 响应时间持续超 2 秒、错误率上升、连接池打满。

```text
扩容执行清单：
1. 垂直扩容 —— 控制台升配，重启后生效；注意升配后 JVM -Xmx 同步调大
2. 水平扩容 —— 新机器部署同版本 jar，Nginx upstream 加节点，观察 15 分钟
3. 带宽扩容 —— 活动前 1-3 天临时升带宽，活动结束降回，按量计费最灵活
4. 数据库 —— 连接数打满先查慢 SQL（22.3 章有 SQL 优化基础），再考虑升级规格/读写分离
5. 容量监控 —— 用「当前值 / 阈值 / 扩容动作」三列表格，每周回顾趋势
6. 大促容量评审 —— 活动前一周按预估流量跑一次压测（JMeter/ab），确认余量
```

```shell
# 简单压测验证容量（ab 并发 50，持续 30 秒）
apt install -y apache2-utils
ab -n 3000 -c 50 https://api.example.com/api/health
# Requests per second:    412.34 [#/sec] (mean)
# Percentage of the requests served within a certain time (ms)
#   95%    482
#   99%    710

# 观察压测中服务器负载
top -bn1 | head -5
# %Cpu(s): 62.3 us ...  -> CPU 还有余量，单实例可再扛更高并发
```

```text
容量规划要点：
1. 容量是动态的，按周看趋势、按月做评估，活动前专项评审
2. 永远留 30% 以上余量：容量到 70% 就启动扩容流程，别等到打满
3. 压测数据（单实例 QPS 上限）要记录，评估扩容时直接套用
4. 无状态服务（JWT）优先水平扩容，避免垂直扩容的机器上限
5. 云数据库/Redis 的规格升级一般不停机，但要在低峰期操作
6. 成本与容量平衡：日常 2 实例冗余 + 活动期临时扩容，是性价比最高的组合
```

### 场景二：告警规则 + 钉钉通知 + 故障演练

把告警闭环跑通，并演练一次完整故障处置：

```text
步骤：
1. 钉钉群添加自定义机器人，复制 webhook 地址（加签方式配置密钥）

6. 演练二（恢复）：重启服务 -> 钉钉收到 ServiceDown resolved（恢复通知）
7. 演练三（磁盘告警）：临时写满 90% 磁盘（dd 大文件）-> 收到 DiskAlmostFull -> 清理文件
8. 演练复盘：确认告警延迟、通知可达、值班人响应流程顺畅，记录改进项
```

## 最佳实践与踩坑记录

### 最佳实践

1. 日志、指标、告警、预案四层都建起来才叫监控体系，只装个 Grafana 不算
2. 日志统一格式并带 traceId，指标按 application/instance 打标签，检索与聚合才有意义
3. 告警规则必须有 for 持续时长和分级，告警内容带「服务 + 实例 + 当前值 + 阈值」
4. 关键告警（服务 DOWN、错误率、磁盘、证书到期）必须接入群机器人并有人值班
5. 发布流程与监控联动：发布后 15-30 分钟盯错误率与响应时间面板，异常立即回滚
6. 应急预案成文 + 定期演练（季度故障演练），演练发现的问题纳入改进清单
7. 容量留 30% 余量，容量到 70% 启动扩容；压测数据存档，评估时直接套用
8. 数据库与 Redis 每日备份，且每月做一次恢复演练，备份可恢复才算有效

### 踩坑记录

```text
坑 1：日志无限增长撑爆磁盘，服务直接挂掉
结论：Java 服务运行几个月后磁盘 100%，日志文件写不进去，接口全部异常。
原因：应用日志与系统日志都没有配置切割与保留策略，无限累积。
解法：logback 按天滚动 + maxHistory 15；logrotate 兜底切割；磁盘使用率加告警（小于 20% 可用即告警）。

坑 2：日志里没有 traceId，多请求混在一起无法定位
结论：线上出问题时，同一用户的一次操作在日志里找不到完整链路。
原因：日志没有贯穿请求的 traceId，只能靠时间戳和关键字大海捞针。
解法：用 MDC 在过滤器里注入 traceId（UUID 或链路追踪 ID），logback pattern 里输出 %X{traceId}；有条件上 SkyWalking 全链路追踪。

坑 3：Actuator 端点全开且公网可访问，泄露敏感信息
结论：/actuator/env 直接暴露数据库密码、AppSecret 等配置项。
原因：management.endpoints.web.exposure.include 配了 *，且端口对外暴露。
解法：只暴露 health,info,prometheus,metrics；应用端口不绑公网（127.0.0.1），由 Nginx 反代；生产环境 management.server.port 独立端口。

坑 4：Prometheus 抓不到指标，面板全空
结论：Grafana 面板全部 No data，Prometheus targets 显示 DOWN 或抓取 4xx。
原因：metrics_path 不对（默认 /metrics，Spring Boot 是 /actuator/prometheus）、端口未放行、端点未暴露。
解法：scrape_configs 里显式配置 metrics_path: /actuator/prometheus；curl 本机端点验证 200；确认防火墙放行抓取端口。

坑 5：告警阈值用平均值，问题被平均掉
结论：接口 P95 已经 5 秒，平均值面板还显示 300ms，故障没被发现。
原因：平均值掩盖长尾，少量慢请求被大量快请求拉平。
解法：用 histogram_quantile 看 P95/P99；错误率用 rate() 看 5 分钟滑动窗口；平均值只做参考。

坑 6：告警轰炸，值班人把群消息静音后漏掉真告警
结论：磁盘告警每小时刷一次，群消息几百条，真出大事时没人看。
原因：repeat_interval 太短（默认 1 小时甚至更短），告警规则太敏感。
解法：repeat_interval 调到 4 小时以上；告警规则加 for 持续时长；分级管理（critical 才立即通知）；用 group_by 合并同类告警。

坑 7：钉钉机器人没有加签，webhook 泄露后被恶意刷消息
结论：钉钉群突然被大量垃圾告警消息刷屏。
原因：机器人安全设置没配加签/关键词，webhook 地址泄露后任何人可调用。
解法：机器人安全设置选「加签」，webhook 地址带 timestamp 与 sign 参数；或设置关键词（如「告警」）过滤。

坑 8：回滚时发现数据库表结构不兼容，旧版本起不来
结论：新版本改了表结构（加了字段），回滚到旧版本后 SQL 报错，服务起不来。
原因：数据库迁移只做了前向兼容，没有考虑回滚场景。
解法：数据库变更遵循「先加后删」策略（新字段带默认值、可空）；回滚前先评估 schema 差异；重要变更写回滚 SQL。

坑 9：容量评估只看峰值 QPS，忽略了慢 SQL 拖垮数据库
结论：接口 QPS 不高，但数据库 CPU 打满，服务整体变慢。
原因：某个列表接口没有索引/全表扫描，流量稍涨就拖垮数据库。
解法：慢查询日志（slow_query_log）开启并定期分析；容量评估包含数据库连接数与慢 SQL 检查；上线前跑 Explain 审核。

坑 10：演练时发现备份根本恢复不了
结论：数据库故障演练时，从备份恢复失败，数据全是坏的/不完整的。
原因：备份脚本只做了 mysqldump，从未验证过恢复流程，备份文件损坏或不全。
解法：备份后自动做一次「恢复到临时库 + 行数校验」；每月演练完整恢复流程；备份文件异地存储（对象存储）。

坑 11：证书到期没有监控，线上 HTTPS 静默失效
结论：某个凌晨小程序请求全部 SSL 报错，才发现证书过期。
原因：证书续期自动化失效（acme.sh 未配置或域名解析变动），又没有任何监控覆盖。
解法：加证书到期告警：blackbox_exporter 探测 https 端口或脚本解析证书有效期（剩余 15 天告警）；acme.sh 续期日志纳入检查。
```
