## 概述

后台是 SpringBoot 单体服务，部署方式从简单到工程化依次是：jar 手工部署（java -jar + nohup）、systemd 托管（开机自启 + 崩溃拉起 + 日志管理）、Docker 容器化（镜像构建 + docker-compose 编排 MySQL/Redis/Nginx）、CI/CD 自动化（GitHub Actions/Jenkins 构建测试部署）。本章把这四种方式全部讲透，并给出发布脚本与回滚脚本，让「代码提交 → 线上生效」的链路稳定可控。对中小团队来说，理解 jar 部署的原理、掌握 systemd 与 Docker 的实操、搭一条自动化流水线，就足以支撑小程序业务长期稳定运行。

```text
部署方式演进：
1. jar 手工部署 —— java -jar + nohup，适合学习与临时环境
2. systemd 托管 —— 开机自启、崩溃自动重启、journalctl 日志，生产单机首选
3. Docker 部署 —— 镜像打包环境，Dockerfile 声明依赖，构建一次到处运行
4. docker-compose —— app + mysql + redis + nginx 一键编排，环境复现最快
5. CI/CD —— 提交代码自动构建、测试、部署，消灭手工发布
6. 发布/回滚脚本 —— 无论哪种方式，都配脚本化发布与一键回滚
```

## jar 部署

SpringBoot 使用 Maven 或 Gradle 构建，产物是内置 Tomcat 的可执行 jar（fat jar）。打包后直接用 java -jar 启动即可，不需要单独装 Tomcat。jar 部署是所有其他部署方式的基础，理解它的启动参数与运行原理，才能在 systemd 和 Docker 里正确配置。

```shell
# 本地/CI 打包
cd /opt/weapp/weapp-api
mvn clean package -DskipTests
ls -lh target/
# -rw-r--r-- 1 root root 62M weapp-api-1.0.0.jar

# 上传到服务器
scp target/weapp-api-1.0.0.jar deploy@1.2.3.4:/opt/weapp/app/

# 服务器上直接启动（前台，会占住终端）
java -jar weapp-api-1.0.0.jar

# 后台运行（nohup + 输出日志）
nohup java -jar weapp-api-1.0.0.jar > /opt/weapp/app/app.log 2>&1 &

# 查看启动日志
tail -f /opt/weapp/app/app.log
# 2026-08-20 10:00:01.123  INFO 12345 --- [           main] c.w.weapp.WeappApplication : Started WeappApplication in 8.42 seconds
```

```text
java -jar 常用启动参数：
1. --server.port=8081 —— 覆盖端口（application.yml 之外的最高优先级）
2. --spring.profiles.active=prod —— 激活生产配置（application-prod.yml）
3. --spring.config.location=/opt/weapp/config/ —— 指定外部配置文件目录（敏感信息不入 jar）
4. -Xms512m -Xmx1024m —— 初始/最大堆内存，按机器配置设定
5. -Dfile.encoding=UTF-8 —— 文件编码，防止中文日志乱码
6. nohup ... & —— 后台运行；& 前加 </dev/null 防止 stdin 占用导致进程异常
```

生产环境的典型启动命令：

```shell
# 生产启动（外部配置 + prod 环境 + 内存限制）
nohup java -Xms512m -Xmx1024m \
  -Dfile.encoding=UTF-8 \
  -jar /opt/weapp/app/weapp-api-1.0.0.jar \
  --spring.profiles.active=prod \
  --spring.config.location=/opt/weapp/config/ \
  </dev/null > /opt/weapp/app/app.log 2>&1 &

# 停止旧进程（找 PID 后 kill）
jps -l | grep weapp-api
# 12345 /opt/weapp/app/weapp-api-1.0.0.jar
kill 12345
# 优雅停止（SpringBoot 会执行 @PreDestroy 与线程池收尾）
kill -TERM 12345
# 强杀（收尾失败时才用）
kill -9 12345
```

```text
jar 部署要点：
1. fat jar 自带 Tomcat，服务器只需要 JDK（生产装 OpenJDK 17 LTS，与开发版本一致）
2. 敏感配置（数据库密码、AppSecret）放外部配置文件或环境变量，不要打进 jar
3. 用 --spring.profiles.active=prod 区分环境，开发/测试/生产配置分离
4. 日志重定向到固定文件（app.log），配合 logrotate 切割，避免撑爆磁盘
5. 优雅停机用 kill -TERM（SIGTERM），SpringBoot 默认 30 秒内完成收尾
6. jps / ps -ef | grep java 确认进程状态，curl 健康检查端点确认服务就绪
```

## systemd 服务管理

nohup 方式启动的进程不会开机自启、崩溃后也不会自动拉起，生产环境必须用 systemd 托管。systemd 是 Linux 的进程管理标准：定义 service 文件描述「怎么启动、以什么身份、依赖什么」，由系统负责开机自启与崩溃重启，日志统一进入 journald。

```ini
# /etc/systemd/system/weapp-api.service
[Unit]
Description=Weapp API Service
# 网络就绪后再启动，MySQL/Redis 可加 After/Wants 依赖
After=network.target

[Service]
Type=simple
User=deploy
Group=deploy
WorkingDirectory=/opt/weapp/app
Environment="JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64"
Environment="SPRING_PROFILES_ACTIVE=prod"
ExecStart=/usr/bin/java -Xms512m -Xmx1024m -jar /opt/weapp/app/weapp-api-1.0.0.jar
# 崩溃后 5 秒自动重启
Restart=on-failure
RestartSec=5
# 启动超时与停止超时
TimeoutStartSec=120
TimeoutStopSec=60

[Install]
WantedBy=multi-user.target
```

```shell
# 加载配置并启动
systemctl daemon-reload
systemctl enable --now weapp-api
systemctl status weapp-api
# ● weapp-api.service - Weapp API Service
#    Loaded: loaded (/etc/systemd/system/weapp-api.service; enabled)
#    Active: active (running)

# 常用管理命令
systemctl start weapp-api      # 启动
systemctl stop weapp-api       # 停止（优雅停机）
systemctl restart weapp-api    # 重启
systemctl reload weapp-api     # 重新加载（Type=simple 不支持，等同 restart）
systemctl disable weapp-api    # 取消开机自启
systemctl enable weapp-api     # 设置开机自启

# 查看日志（journald 统一收集）
journalctl -u weapp-api -f                  # 实时跟踪
journalctl -u weapp-api --since "10 min ago" # 最近 10 分钟
journalctl -u weapp-api -n 200              # 最后 200 行
journalctl -u weapp-api -p err              # 只看错误级别
```

```text
systemd 要点：
1. [Unit] After=network.target —— 保证网络就绪后再启动，避免启动即连不上数据库
2. Restart=on-failure —— 非正常退出自动拉起；RestartSec=5 防止频繁重启风暴
3. User=deploy —— 用普通用户运行，禁止 root 跑业务进程
4. Environment= 注入环境变量（数据库密码、AppSecret），不进代码仓库
5. journalctl -u 服务名 查看日志，比 tail -f app.log 更规范（含启动/停止事件）
6. 每次改 service 文件都要 systemctl daemon-reload 重新加载，否则不生效
```

## Docker 部署

Docker 把应用连同运行环境（JDK、依赖、配置）打包成镜像，解决「在我机器上是好的」问题。SpringBoot 部署 Docker 的推荐姿势是多阶段构建：第一阶段用 Maven 镜像编译，第二阶段只把 jar 放进精简的 JRE 镜像，镜像小、构建快。单机多服务用 docker-compose 编排，一条命令拉起 app + mysql + redis + nginx 整套环境。

```dockerfile
# Dockerfile —— 多阶段构建
# 阶段一：编译
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /build
COPY pom.xml .
# 先拉依赖（利用层缓存，pom 不变时不会重新下载）
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn clean package -DskipTests

# 阶段二：运行
FROM eclipse-temurin:17-jre
WORKDIR /app
# 从构建阶段拷贝 jar
COPY --from=builder /build/target/weapp-api-1.0.0.jar app.jar
EXPOSE 8080
ENV SPRING_PROFILES_ACTIVE=prod
ENTRYPOINT ["java", "-Xms512m", "-Xmx1024m", "-jar", "app.jar"]
```

```shell
# 构建镜像
docker build -t weapp-api:1.0.0 .

# 运行容器
docker run -d --name weapp-api \
  -p 127.0.0.1:8080:8080 \
  -e SPRING_PROFILES_ACTIVE=prod \
  -e DB_PASSWORD=xxx \
  -v /opt/weapp/config:/app/config \
  -v /opt/weapp/logs:/app/logs \
  --restart unless-stopped \
  weapp-api:1.0.0

# 查看容器状态与日志
docker ps
docker logs -f weapp-api
docker logs --tail 200 weapp-api
docker exec -it weapp-api sh

# 停止/删除
docker stop weapp-api && docker rm weapp-api
```

```yaml
# docker-compose.yml —— 全栈编排（app + mysql + redis + nginx）
version: "3.8"

services:
  mysql:
    image: mysql:8.0
    container_name: weapp-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: root_pwd_123
      MYSQL_DATABASE: weapp
      MYSQL_USER: weapp
      MYSQL_PASSWORD: weapp_pwd_123
    volumes:
      - mysql_data:/var/lib/mysql
      - ./sql:/docker-entrypoint-initdb.d   # 首次启动自动执行初始化 SQL
    command: --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
    networks: [weapp_net]

  redis:
    image: redis:7-alpine
    container_name: weapp-redis
    restart: unless-stopped
    command: redis-server --requirepass redis_pwd_123 --appendonly yes
    volumes:
      - redis_data:/data
    networks: [weapp_net]

  app:
    build: .
    image: weapp-api:1.0.0
    container_name: weapp-api
    restart: unless-stopped
    depends_on:
      - mysql
      - redis
    environment:
      SPRING_PROFILES_ACTIVE: prod
      DB_HOST: mysql          # 服务名即主机名
      DB_PASSWORD: weapp_pwd_123
      REDIS_HOST: redis
      REDIS_PASSWORD: redis_pwd_123
    ports:
      - "127.0.0.1:8080:8080"   # 只绑定本机，由 Nginx 反代
    networks: [weapp_net]

  nginx:
    image: nginx:1.25
    container_name: weapp-nginx
    restart: unless-stopped
    depends_on:
      - app
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/weapp.conf:/etc/nginx/conf.d/weapp.conf:ro
      - /etc/nginx/ssl:/etc/nginx/ssl:ro
      - ./admin-dist:/usr/share/nginx/html:ro
    networks: [weapp_net]

volumes:
  mysql_data:
  redis_data:

networks:
  weapp_net:
    driver: bridge
```

```shell
# 一键启动整套环境
docker compose up -d --build
docker compose ps
# NAME         IMAGE              STATUS
# weapp-nginx  nginx:1.25         Up (healthy)
# weapp-api    weapp-api:1.0.0    Up
# weapp-mysql  mysql:8.0          Up (healthy)
# weapp-redis  redis:7-alpine     Up

# 查看各容器日志
docker compose logs -f app
docker compose logs --tail 100 mysql

# 停止/清理
docker compose down          # 停止并删除容器（数据卷保留）
docker compose down -v       # 连数据卷一起删（慎用，会丢数据）
```

```text
Docker 要点：
1. 多阶段构建让运行镜像只含 JRE（约 200MB），不要用带 Maven 的大镜像跑生产
2. 容器端口只绑定 127.0.0.1（-p 127.0.0.1:8080:8080），公网流量统一走 Nginx
3. 数据必须落盘：MySQL/Redis 挂 volume，日志目录挂到宿主机，容器删除不丢数据
4. --restart unless-stopped 让容器随 Docker 自启并崩溃重启（配合 systemd 管理 docker 服务）
5. 应用配置用环境变量注入（-e / environment），镜像保持与环境无关
6. 生产数据库建议单独部署（云数据库 RDS），不要与业务容器同机，避免资源争抢
```

## CI/CD 流水线

CI/CD 把「构建 → 测试 → 部署」自动化：代码推送到 Git 仓库后，流水线自动拉代码、跑测试、打包、上传服务器并重启服务。GitHub Actions 对 GitHub 仓库零成本开箱即用，Jenkins 适合自建 GitLab 的团队。核心思路一致：流水线是「发布脚本的自动化执行者」。

```yaml
# .github/workflows/deploy.yml —— GitHub Actions 部署流水线
name: Build and Deploy

on:
  push:
    branches: [ main ]          # main 分支推送即触发
  workflow_dispatch: {}        # 支持手动触发

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup JDK 17
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '17'

      - name: Build with Maven
        run: mvn clean package -DskipTests

      - name: Run Tests
        run: mvn test

      - name: Upload jar to server
        uses: appleboy/scp-action@v0.1.7
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.DEPLOY_KEY }}
          source: "target/weapp-api-1.0.0.jar"
          target: "/opt/weapp/releases/v1.0.0/"

      - name: Restart service
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.DEPLOY_KEY }}
          script: |
            sudo systemctl restart weapp-api
            sleep 5
            curl -sf http://127.0.0.1:8080/api/health || exit 1
```

```text
Jenkins 流水线（Groovy 简版）：
1. Jenkinsfile 放在仓库根目录，声明式语法 stage('构建') / stage('测试') / stage('部署')
2. 构建：sh 'mvn clean package -DskipTests'，制品归档 target/*.jar
3. 部署：ssh 到目标机执行发布脚本（与手工发布共用同一脚本）
4. 凭证管理：服务器密钥、云厂商密钥存 Jenkins 凭证，不在脚本里写明文
5. 触发：Webhook（Git 推送触发）或定时轮询，测试环境可加「构建后自动部署」
6. 流水线失败自动发通知（邮件/钉钉），构建产物保留 N 个版本便于回滚
```

```text
CI/CD 要点：
1. 流水线分三段：构建（compile/package）→ 质量（test/lint）→ 部署（上传+重启+健康检查）
2. 部署凭证用 Secrets（GitHub Actions secrets / Jenkins 凭证库），禁止明文入库
3. 部署最后一步必须做健康检查（curl 健康端点），失败即流水线失败，不允许「部署了但没起来」
4. 测试环境自动部署 + 生产环境手动确认（workflow_dispatch 或保护分支）是稳妥组合
5. 构建产物带版本号（v1.0.0），服务器上按版本目录归档，回滚时直接切软链
6. CI 机器只负责构建上传，不直接持有生产数据库权限，最小权限原则
```

## 发布与回滚脚本

无论手工部署还是 CI/CD 调用，发布动作都应该收敛成脚本：备份当前版本 → 上传新版本 → 切换软链 → 重启 → 健康检查 → 失败自动回滚。回滚是发布流程的一部分，不是事故后的补救，脚本化之后「一键回滚」才可能发生。

```bash
#!/usr/bin/env bash
# /opt/weapp/bin/deploy.sh —— 发布脚本
set -euo pipefail

APP_NAME="weapp-api"
APP_DIR="/opt/weapp/app"
RELEASES_DIR="/opt/weapp/releases"
CURRENT_LINK="$APP_DIR/current"          # 当前版本软链
HEALTH_URL="http://127.0.0.1:8080/api/health"
VERSION="${1:-$(date +%Y%m%d%H%M%S)}"    # 版本号，默认时间戳
NEW_RELEASE="$RELEASES_DIR/$VERSION"

echo "[deploy] 开始发布版本: $VERSION"

# 1. 备份当前版本（软链指向的旧 jar 复制到 backups）
mkdir -p "$RELEASES_DIR" "$APP_DIR/backups"
if [ -L "$CURRENT_LINK" ]; then
  OLD_VER=$(readlink "$CURRENT_LINK" | xargs basename)
  cp "$CURRENT_LINK" "$APP_DIR/backups/$OLD_VER.jar" 2>/dev/null || true
  echo "[deploy] 已备份旧版本: $OLD_VER"
fi

# 2. 新版本就位（deploy.sh 传入的 jar 放在 releases/VERSION/）
mkdir -p "$NEW_RELEASE"
if [ -f "/tmp/${APP_NAME}.jar" ]; then
  mv "/tmp/${APP_NAME}.jar" "$NEW_RELEASE/${APP_NAME}.jar"
fi
[ -f "$NEW_RELEASE/${APP_NAME}.jar" ] || { echo "[deploy] 找不到新 jar，中止"; exit 1; }

# 3. 切换软链指向新版本
ln -sfn "$NEW_RELEASE/${APP_NAME}.jar" "$CURRENT_LINK"

# 4. 重启服务并健康检查
sudo systemctl restart "$APP_NAME"
sleep 8
if curl -sf "$HEALTH_URL" > /dev/null; then
  echo "[deploy] 发布成功: $VERSION"
else
  echo "[deploy] 健康检查失败，自动回滚"
  bash /opt/weapp/bin/rollback.sh
  exit 1
fi
```

```bash
#!/usr/bin/env bash
# /opt/weapp/bin/rollback.sh —— 回滚脚本
set -euo pipefail

APP_NAME="weapp-api"
APP_DIR="/opt/weapp/app"
RELEASES_DIR="/opt/weapp/releases"
CURRENT_LINK="$APP_DIR/current"
HEALTH_URL="http://127.0.0.1:8080/api/health"

# 1. 找到上一个版本（releases 目录按时间倒序第二个）
TARGET=$(ls -1dt "$RELEASES_DIR"/*/ | sed -n '2p')
if [ -z "$TARGET" ]; then
  echo "[rollback] 没有可回滚的版本"
  exit 1
fi
echo "[rollback] 回滚到: $TARGET"

# 2. 切换软链
ln -sfn "$TARGET/${APP_NAME}.jar" "$CURRENT_LINK"

# 3. 重启并健康检查
sudo systemctl restart "$APP_NAME"
sleep 8
if curl -sf "$HEALTH_URL" > /dev/null; then
  echo "[rollback] 回滚成功"
else
  echo "[rollback] 回滚后仍不健康，请人工介入"
  exit 1
fi
```

```text
发布流程规范：
1. 发布前：备份数据库（mysqldump）、确认磁盘空间、确认新 jar 已上传 releases 目录
2. 发布中：切换软链 -> restart -> 健康检查，全程不超过 1 分钟
3. 发布后：观察监控（错误率、响应时间、JVM 内存）15-30 分钟再离开
4. 回滚条件：健康检查失败、错误率飙升、核心接口 5xx 超过阈值
5. 版本号规范：v1.0.0 语义化版本或时间戳，releases 目录保留最近 10 个版本自动清理
6. 发布窗口：业务低峰期（如凌晨 2-4 点）发布，重大版本提前通知运营
```

## 应用场景实战

### 场景一：jar 打包 + systemd 托管的单机生产部署

一台 2 核 4G 的 Ubuntu 服务器，把 SpringBoot 后台以 systemd 服务形式上线：

```text
步骤：
1. 服务器安装 JDK17：apt install -y openjdk-17-jdk，java -version 验证
2. 本地打包：mvn clean package -DskipTests，scp 上传 jar 到 /opt/weapp/app/
3. 外部配置：编写 /opt/weapp/config/application-prod.yml（数据库、Redis、微信配置）
4. 编写 /etc/systemd/system/weapp-api.service（User=deploy、Restart=on-failure）
5. systemctl daemon-reload && systemctl enable --now weapp-api
6. 验证：systemctl status、curl http://127.0.0.1:8080/api/health
7. 配好 Nginx 反代（22.2 章），公网 https://api.example.com/api/health 可访问
8. 模拟故障：kill -9 服务进程，5 秒后 systemd 自动拉起
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产环境用 systemd 或 Docker 托管进程，禁止裸 nohup 跑业务（无自启、无崩溃拉起）
2. 应用进程用专用部署用户（deploy）运行，禁止 root 跑服务，文件权限最小化
3. 配置与代码分离：数据库密码、AppSecret 走外部配置文件或环境变量，打入 jar 即泄露
4. 发布与回滚全部脚本化（deploy.sh/rollback.sh），CI/CD 与手工发布共用同一套脚本
5. 每个发布都带版本号并按目录归档（releases/v1.0.0/），软链切换实现秒级回滚
6. Docker 部署时数据卷必须持久化，容器可以随便删，数据不能丢
7. 部署完成的标准动作是健康检查，不是「进程起来了」；健康检查失败视为发布失败
8. 测试环境先部署验证，生产环境选低峰期发布，发布后观察监控 15-30 分钟

### 踩坑记录

```text
坑 1：nohup 启动后一关终端进程就死
结论：SSH 断开后 Java 进程跟着退出，线上服务掉线。
原因：nohup 只忽略挂断信号，但未正确重定向/未完全脱离终端会话（缺少 </dev/null 或未用 setsid）。
解法：用 systemd 托管；临时场景确保命令为 nohup java -jar xx.jar </dev/null > app.log 2>&1 &。

坑 2：生产环境 JDK 版本与开发不一致，启动报 UnsupportedClassVersionError
结论：jar 在本地能跑，服务器上启动报 UnsupportedClassVersionError。
原因：开发用 JDK 17 编译，服务器装的是 JDK 8/11，class 文件版本高于 JVM 支持版本。
解法：生产与开发统一 JDK 版本（推荐 OpenJDK 17 LTS）；用 java -version 与 maven compiler 版本核对。

坑 3：systemd 改完配置没 daemon-reload，重启不生效
结论：修改 service 文件后 systemctl restart 行为还是旧的。
原因：systemd 缓存了旧配置，修改文件后必须重新加载。
解法：每次改 /etc/systemd/system/*.service 后执行 systemctl daemon-reload 再 restart。

坑 4：数据库密码写进 application.yml 打进 jar，导致泄露
结论：jar 被反编译/分享后，生产数据库密码直接暴露。
原因：生产配置打包进了 fat jar，任何人拿到 jar 都能解压查看。
解法：生产配置放外部目录（--spring.config.location=/opt/weapp/config/）或环境变量注入，jar 里只留默认开发配置。

坑 5：Docker 容器启动顺序问题，app 启动时连不上 MySQL
结论：docker compose up 后 app 容器一直报 Connection refused，MySQL 还没就绪。
原因：depends_on 只保证容器启动顺序，不保证 MySQL 内部初始化完成（首次启动要初始化数据目录）。
解法：应用侧做重试（Spring Boot 连接池会自动重试，把初始化超时调大）；或配 healthcheck + depends_on condition: service_healthy。

坑 6：容器删了数据全没，重建后数据库是空的
结论：docker compose down 后重新 up，业务数据全部丢失。
原因：MySQL/Redis 没有挂 volume，数据存在容器可写层，容器删除即销毁。
解法：compose 里为 mysql/redis 配置 volumes 持久化；日常运维禁止 docker rm -f 数据容器，先备份。

坑 7：CI 流水线部署成功但服务没起来，流水线还显示绿色
结论：流水线显示部署成功，线上接口却 500/无法访问。
原因：部署步骤只执行了上传和重启，没有健康检查，服务起没起来无人知晓。
解法：部署步骤最后加 curl 健康检查，失败 exit 1 让流水线变红；配合 22.4 章监控兜底。

坑 8：回滚只替换了 jar，没重启或软链指错，回滚失败
结论：紧急回滚时发现线上还是新版本或服务直接挂了。
原因：回滚操作是手工多步操作（停-换文件-启），漏一步就失败，且没有验证。
解法：用 rollback.sh 脚本固化流程（软链切换 + 重启 + 健康检查）；releases 按版本归档，回滚目标明确。

坑 9：磁盘被日志和旧版本 jar 撑满，服务无响应
结论：服务器磁盘 100%，Java 服务写日志失败，接口全部异常。
原因：日志不切割、releases/backups 目录无限累积、Docker 镜像不清理。
解法：logrotate 按天/按大小切割（保留 7-14 天）；清理脚本定期删旧版本与悬空镜像；df -h 纳入监控告警。

坑 10：docker compose 与 docker-compose 命令差异导致 CI 脚本失败
结论：服务器上 docker compose 报 command not found，或 docker-compose 报版本语法错误。
原因：新版 Docker 用 compose 插件，旧版用独立 docker-compose 二进制，compose 文件版本声明也不一样。
解法：统一安装 docker-compose-plugin 并使用 docker compose 子命令；compose 文件去掉 version 字段（新语法）。
```
