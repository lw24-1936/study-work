## 概述

Nginx 是「小程序 + SpringBoot + Vue」全栈架构中的流量入口：它监听 80/443 端口，把 /api 开头的请求反向代理给后端 Java 服务，把静态资源（Vue 构建产物）直接返回给浏览器，同时承载 HTTPS 证书、负载均衡、Gzip 压缩等能力。小程序端只认识 https://api.example.com 这一个域名，Nginx 就是这个域名背后真正的「调度员」。本章覆盖 Nginx 的安装、配置结构、反向代理、静态资源、负载均衡与 HTTPS 全站配置，学完可以独立完成一个生产级的前后端分离站点。

```text
Nginx 在架构中的位置：
1. 统一入口 —— 所有外部流量只进 80/443，应用端口不对外暴露
2. 反向代理 —— /api 转发到 SpringBoot（8080），管理端接口同理
3. 静态资源 —— Vue dist 构建产物由 Nginx 直接返回，性能远高于 Tomcat
4. HTTPS 终结 —— 证书配置在 Nginx，后端服务不感知 HTTPS
5. 负载均衡 —— upstream 多实例轮询/权重分发，横向扩容的基石
6. 性能优化 —— Gzip 压缩、静态缓存、连接复用，减少后端压力
```

## Nginx 安装与配置结构

Nginx 在 Ubuntu 和 CentOS 上都有官方软件源，安装后即可使用 systemd 管理。核心概念是配置文件的层级结构：全局块（events/http）→ server 块（一个域名/端口一个站点）→ location 块（URL 路径匹配规则）。理解这个层级是配置 Nginx 的基础。

```shell
# Ubuntu 安装
apt update
apt install -y nginx
nginx -v
# nginx version: nginx/1.18.0 (Ubuntu)

# 启动并设置开机自启
systemctl enable --now nginx
systemctl status nginx
# ● nginx.service - A high performance web server and a reverse proxy server
#    Active: active (running)

# 校验配置语法（改配置后必跑）
nginx -t
# nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
# nginx: configuration file /etc/nginx/nginx.conf test is successful

# 重载配置（不中断连接）
systemctl reload nginx
```

```text
nginx.conf 目录结构：
1. /etc/nginx/nginx.conf —— 主配置：user/worker_processes/events/http 块
2. /etc/nginx/sites-available/ —— 站点配置（Ubuntu 惯例），一个域名一个文件
3. /etc/nginx/sites-enabled/ —— 软链启用的站点（Debian/Ubuntu 机制）
4. /etc/nginx/conf.d/*.conf —— CentOS 惯例的站点配置目录
5. /etc/nginx/mime.types —— 文件类型映射（静态资源响应 Content-Type）
6. /var/log/nginx/access.log / error.log —— 访问日志与错误日志
```

Ubuntu 默认安装会带一个 default 站点（监听 80 返回欢迎页），正式部署时把它禁用，避免配置冲突：

```shell
# 禁用默认站点
rm -f /etc/nginx/sites-enabled/default

# 新建业务站点配置
vim /etc/nginx/sites-available/weapp.conf

# 启用站点（软链到 sites-enabled）
ln -s /etc/nginx/sites-available/weapp.conf /etc/nginx/sites-enabled/weapp.conf
nginx -t && systemctl reload nginx
```

```text
配置结构要点：
1. worker_processes auto —— 自动按 CPU 核数开 worker，不要手动设过大
2. 每个业务站点单独一个 conf 文件，不要全堆在 nginx.conf 里
3. 修改配置先 nginx -t 校验再 reload，语法错误会导致整个 Nginx 拒绝启动
4. reload 是平滑重载（旧连接处理完才切），不要用 restart 打断在线连接
5. 日志按天/按大小切割由 logrotate 管理（/etc/logrotate.d/nginx）
6. 服务器块（server_name）用域名精确匹配，避免用默认 server 兜底导致串站
```

## 反向代理

反向代理是 Nginx 最核心的功能：客户端请求 Nginx，Nginx 把请求转发给内部的后端服务（SpringBoot 8080 端口），再把响应返回给客户端。客户端永远只跟 Nginx 打交道，后端服务可以安全地只监听内网。配置核心是 proxy_pass 指令，配合请求头透传把客户端真实信息带给后端。

```nginx
# /etc/nginx/sites-available/weapp.conf —— API 反向代理示例
server {
    listen 80;
    server_name api.example.com;

    # 后端 API 全部走 /api 前缀
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 超时与缓冲（小程序弱网环境建议放宽）
        proxy_connect_timeout 10s;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
    }
}
```

```text
proxy_pass 两种写法的区别（关键）：
1. location /api/ { proxy_pass http://127.0.0.1:8080; } —— 不带 URI，保留完整原始路径 /api/xxx
2. location /api/ { proxy_pass http://127.0.0.1:8080/; } —— 带 URI /，用 / 替换匹配到的 /api/ 前缀
3. 场景一后端 Controller 映射 @RequestMapping("/api/order") 时用不带 URI 写法
4. 场景二后端映射 @RequestMapping("/order") 时用带 URI 写法，前端请求 /api/order 被转成 /order
5. 两种写法混用是最常见的 404 事故源，确定后端路由设计后再选
6. SpringBoot 侧需要真实 IP 时，读 X-Forwarded-For 头并配置 server.forward-headers-strategy
```

微信小程序场景下后端通常保持 /api 前缀（Controller 层统一 @RequestMapping("/api")），Nginx 直接透传，前后端路径一致，排查问题最直观：

```nginx
# 透传写法（后端带 /api 前缀，推荐）
location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# 去掉前缀写法（后端不带 /api 前缀，如 /user/login）
location /api/ {
    proxy_pass http://127.0.0.1:8080/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

```text
反代要点：
1. 小程序端 wx.request 请求 https://api.example.com/api/order/list，Nginx 命中 /api/ location
2. 生产环境后端服务只监听 127.0.0.1:8080（application.yml 中 server.address 配置），不暴露公网
3. WebSocket（小程序 wx.connectSocket）需要额外配置 Upgrade 头：proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade";
4. 大文件上传（图片/视频）需要调大 client_max_body_size，默认 1M 会直接 413
5. 反代层可以统一做限流（limit_req）、IP 黑名单（deny）、请求大小限制
6. 后端返回的 Set-Cookie 走 HTTPS 时必须设置 Secure 属性，否则登录态丢失
```

## 静态资源部署

Vue 管理后台构建后的产物是纯静态文件（HTML/CSS/JS/图片），用 Nginx 直接服务比 Tomcat 快一个数量级，也不需要 Java 环境。核心是 root 与 alias 的区分：root 会把 location 的完整 URI 拼到目录后面，alias 则用指定目录直接替换 location 匹配部分。

```nginx
# Vue3 构建产物部署（root 用法）
server {
    listen 80;
    server_name admin.example.com;

    root /opt/weapp/admin-dist;      # 构建产物目录
    index index.html;

    # 前端 history 路由（Vue Router createWebHistory）
    # 刷新非首页路由时回退到 index.html，由前端路由接管
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 静态资源缓存（带 hash 的构建产物可长期缓存）
    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # 禁止访问隐藏文件
    location ~ /\. {
        deny all;
    }
}
```

```nginx
# alias 用法示例（图片目录映射到磁盘其他位置）
location /upload/ {
    alias /data/weapp/uploads/;
    expires 7d;
}
# 请求 /upload/avatar/1.png -> 磁盘 /data/weapp/uploads/avatar/1.png
```

前端项目构建（在开发机或 CI 上执行）：

```shell
# Vue3 项目构建
cd /opt/weapp/admin-web
npm install
npm run build
# 产物输出到 dist/ 目录

# 上传到服务器
rsync -avz --delete dist/ deploy@1.2.3.4:/opt/weapp/admin-dist/

# 服务器上确认文件就位
ls /opt/weapp/admin-dist/
# index.html  assets/  favicon.ico
```

```text
静态资源要点：
1. root 与 alias 选错 = 路径 404，规则：root 拼接 URI，alias 替换 URI 前缀
2. Vue history 路由必须配 try_files $uri $uri/ /index.html，否则刷新页面 404
3. 带 contenthash 的静态资源（assets/*.js 文件名带 hash）设置 immutable 长缓存
4. index.html 本身不缓存或短缓存（no-cache），否则发版后用户拿到旧页面
5. Gzip 压缩静态资源：gzip on; gzip_types text/css application/javascript application/json image/svg+xml;
6. 上传目录（/upload/）不要放在前端 dist 里，用 alias 指向独立磁盘目录，方便备份扩容
```

## 负载均衡

单机扛不住流量时，把 SpringBoot 部署成多实例，Nginx 用 upstream 定义后端服务器组，按策略把请求分发到不同实例。常用策略：轮询（默认，平均分发）、权重（weight，按机器性能分配）、ip_hash（同一 IP 固定到同一台，用于有状态服务）、least_conn（最少连接）。健康检查通过 max_fails 与 fail_timeout 实现：连续失败 N 次后把该实例标记为不可用，冷却一段时间再试探。

```nginx
# 负载均衡配置示例
upstream weapp_backend {
    # 默认轮询：请求依次分发到两台机器
    server 10.0.0.11:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=30s;
    # 权重模式：新机器/高性能机器多分流量
    # server 10.0.0.12:8080 weight=2;
    # 备用节点：前面都挂了才启用
    # server 10.0.0.13:8080 backup;

    keepalive 32;   # 与后端保持长连接，减少握手开销
}

server {
    listen 80;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://weapp_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

```text
负载均衡要点：
1. 轮询 —— 默认策略，适合无状态接口（JWT 无会话，小程序后台天然适合）
2. weight —— 按机器配置分配权重，新扩容机器先用小权重观察
3. ip_hash —— 同一 IP 固定一台后端，适合本地 Session 方案（不推荐，扩容后 hash 失效）
4. max_fails=3 fail_timeout=30s —— 30 秒内失败 3 次标记宕机，30 秒后再试探
5. backup 备用节点 —— 主节点全挂时才接管，适合低成本高可用
6. keepalive 32 —— 复用与后端的长连接，QPS 高时显著降低延迟与资源占用
```

灰度发布也可以借助负载均衡的权重实现：新版本实例先以 weight=1 接入，观察监控无异常后再逐步把权重调大，最后全部切换。这个思路在 22.3 章「发布脚本」里会再次用到。

## HTTPS 配置

证书在 22.1 章已通过 acme.sh 签发，Nginx 侧需要把证书文件配置到 server 块：ssl_certificate 指向完整证书链（fullchain），ssl_certificate_key 指向私钥。443 监听 + 80 跳转 443 是标准姿势。安全参数上建议启用 TLS 1.2/1.3，关闭旧协议，配置 HSTS 强制浏览器走 HTTPS。

```nginx
# 完整 HTTPS 站点配置（API + 前端静态资源同域名）
server {
    listen 443 ssl;
    http2 on;
    server_name api.example.com;

    # 证书文件（acme.sh 安装的路径）
    ssl_certificate     /etc/nginx/ssl/api.example.com.pem;
    ssl_certificate_key /etc/nginx/ssl/api.example.com.key;

    # 协议与加密套件
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off;

    # 会话缓存与 OCSP（提升握手性能）
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 10m;

    # 静态资源（前端 dist）
    root /opt/weapp/admin-dist;
    index index.html;
    location / {
        try_files $uri $uri/ /index.html;
    }

    # API 反向代理
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# HTTP 强制跳转 HTTPS
server {
    listen 80;
    server_name api.example.com;
    return 301 https://$host$request_uri;
}
```

```text
HTTPS 配置要点：
1. ssl_certificate 用 fullchain（含中间证书），只用域名证书会导致部分客户端握手失败
2. 80 端口只做 301 跳转，不要把业务配置在 80 上
3. 证书续期后必须 reload Nginx（acme.sh 的 reloadcmd 已配置）
4. TLS 1.0/1.1 已不安全，配置 ssl_protocols TLSv1.2 TLSv1.3 即可
5. HSTS（add_header Strict-Transport-Security "max-age=31536000"）让浏览器强制 HTTPS，注意先确认 HTTPS 稳定再开
6. 微信小程序对证书要求严格：证书链完整、域名匹配、不过期，三者缺一不可
```

## 应用场景实战

### 场景一：前后端分离站点完整上线（API 反代 + Vue 静态资源 + HTTPS）

以小程序后台 api.example.com 和管理端 admin.example.com 两个域名为例，完成一整套生产配置：

```text
步骤：
1. 服务器安装 Nginx（apt install nginx），禁用默认站点
2. 前端构建：cd admin-web && npm run build，rsync 上传 dist 到 /opt/weapp/admin-dist
3. 后端打包：mvn package 得到 weapp-api.jar，上传到 /opt/weapp/app/ 并启动（22.3 章详述）
4. 编写 /etc/nginx/sites-available/weapp.conf：
   - admin.example.com 443：静态资源 + history 路由回退
   - api.example.com 443：/api/ 反代到 127.0.0.1:8080
   - 两个 80 站点：301 跳转 HTTPS
5. 证书：acme.sh 签发 api.example.com 与 admin.example.com 两张证书
6. nginx -t 校验通过，ln -s 启用站点，systemctl reload nginx
7. 验证：浏览器访问 https://admin.example.com 正常；curl https://api.example.com/api/health 返回 200
8. 微信后台配置 request 合法域名 https://api.example.com，真机联调
```

```nginx
# /etc/nginx/sites-available/weapp.conf 完整配置
# ========== 管理端 admin.example.com ==========
server {
    listen 443 ssl;
    http2 on;
    server_name admin.example.com;

    ssl_certificate     /etc/nginx/ssl/admin.example.com.pem;
    ssl_certificate_key /etc/nginx/ssl/admin.example.com.key;
    ssl_protocols TLSv1.2 TLSv1.3;

    root /opt/weapp/admin-dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }
    location ~ /\. { deny all; }
}

# ========== 小程序接口 api.example.com ==========
server {
    listen 443 ssl;
    http2 on;
    server_name api.example.com;

    ssl_certificate     /etc/nginx/ssl/api.example.com.pem;
    ssl_certificate_key /etc/nginx/ssl/api.example.com.key;
    ssl_protocols TLSv1.2 TLSv1.3;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 10m;
    }
}

# ========== HTTP 跳转 HTTPS ==========
server {
    listen 80;
    server_name admin.example.com api.example.com;
    return 301 https://$host$request_uri;
}
```

```text
验收标准：
1. nginx -t 输出 syntax is ok / test is successful
2. https://admin.example.com 打开管理端登录页，登录后刷新页面不 404（history 路由生效）
3. curl -i https://api.example.com/api/health 返回后端 JSON（200）
4. http://api.example.com 自动 301 到 https
5. 小程序真机请求 https://api.example.com/api/... 正常，无 SSL 报错
6. 管理端发版后（重新 rsync dist），刷新页面看到新版本（index.html 不缓存）
```

### 场景二：双实例负载均衡 + 灰度切换

业务增长后把后端扩到两台机器（10.0.0.11 与 10.0.0.12），用 upstream 负载均衡，并演练一次灰度发布：

```text
步骤：
1. 两台机器各部署一份 weapp-api.jar（数据库共用，Redis 共用，无状态服务）
2. Nginx 配置 upstream weapp_backend 包含两台机器
3. 新版本发布演练：先在 10.0.0.11 部署 v2.0，Nginx 配置里 10.0.0.11 权重调大观察
4. 监控接口错误率与响应时间（22.4 章 Prometheus 监控），无异常后 10.0.0.12 也升级 v2.0
5. 全部升级完成，upstream 恢复正常轮询
6. 演练故障转移：手动停掉 10.0.0.11 的 Java 进程，观察请求全部由 10.0.0.12 承接
```

```nginx
# 灰度阶段的 upstream（v2.0 在 .11，v1.9 在 .12）
upstream weapp_backend {
    server 10.0.0.11:8080 weight=5 max_fails=3 fail_timeout=30s;  # 新版本多分流量
    server 10.0.0.12:8080 weight=1 max_fails=3 fail_timeout=30s;  # 旧版本少分流量
    keepalive 32;
}

# 故障转移验证：停掉 .11 后，请求仍 200（全部落到 .12）
# while true; do curl -s -o /dev/null -w "%{http_code}\n" https://api.example.com/api/health; sleep 1; done
```

```text
验收标准：
1. 连续请求 https://api.example.com/api/health，后端日志显示两台机器都有请求
2. 停掉其中一台 Java 进程，接口仍正常返回（max_fails 生效，请求自动切到存活节点）
3. 灰度期间新版本接口错误率无上升，监控面板确认后再全量
4. 数据库连接池与 Redis 连接数在双实例下翻倍，确认连接数上限足够
5. 会话/登录不受影响（JWT 无状态，双实例天然支持）
6. 回滚预案：出问题时把 upstream 里新版本节点 weight 设为 0 并 reload，流量即刻切回旧版
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每个业务站点独立 conf 文件、独立 server_name，域名精确匹配，禁止用 default_server 兜底多站点
2. 所有配置改动先 nginx -t 再 systemctl reload；reload 是平滑的，线上不要用 restart
3. 后端服务只监听 127.0.0.1，公网只暴露 80/443，数据库与 Redis 同理
4. 静态资源按「hash 资源长缓存 + index.html 不缓存」策略配置，发版立即生效且缓存命中率高
5. 反代层统一配置 client_max_body_size、Gzip、超时时间，避免每个 location 重复踩坑
6. 负载均衡优先轮询 + max_fails 健康检查，JWT 无状态架构下不需要 ip_hash
7. 证书路径、upstream 地址、端口等变量抽到 conf 文件顶部或单独文件，方便环境切换
8. 用 curl -I、nginx -t、systemctl status 三步验证任何配置变更，形成肌肉记忆

### 踩坑记录

```text
坑 1：proxy_pass 带不带末尾斜杠搞错，接口全部 404
结论：配置 /api/ 反代后，小程序请求全部 404，后端日志里路径多了或少了 /api。
原因：proxy_pass http://127.0.0.1:8080; 透传完整路径；带 / 的 proxy_pass http://127.0.0.1:8080/; 会替换掉 /api 前缀。
解法：确定后端 Controller 是否带 /api 前缀；不带前缀用带 / 的写法，带前缀用不带 / 的写法，并 nginx -t + curl 实测。

坑 2：Vue history 路由刷新页面 404
结论：管理端登录后刷新 /dashboard 页面直接 404，返回 Nginx 默认 404 页。
原因：前端用 history 模式路由，刷新时浏览器直接请求 /dashboard，Nginx 找不到对应静态文件。
解法：location / 加 try_files $uri $uri/ /index.html；构建用 hash 模式可规避，但不推荐。

坑 3：默认站点没禁用，访问域名打开的是 Nginx 欢迎页
结论：配置好 server_name 后访问域名，页面还是 Nginx 默认欢迎页。
原因：Ubuntu 默认站点 /etc/nginx/sites-enabled/default 监听 80，且作为默认 server 优先兜底。
解法：删除 sites-enabled/default，reload Nginx；确保自己站点配置语法正确。

坑 4：图片上传报 413 Request Entity Too Large
结论：小程序/管理端上传图片超过 1MB 全部失败，返回 413。
原因：Nginx 默认 client_max_body_size 1m，超出即拒绝。
解法：在 server 或 location 层配置 client_max_body_size 10m（按业务实际调整）；同时确认后端 SpringBoot 的 multipart 限制也调大。

坑 5：证书续期后没有 reload，线上仍报证书过期
结论：acme.sh 提示续期成功，但线上 HTTPS 仍提示证书过期。
原因：证书文件已更新，但 Nginx 还在用内存中的旧证书，未重新加载。
解法：acme.sh install-cert 时带上 --reloadcmd "systemctl reload nginx"；手动续期后务必 systemctl reload nginx 验证。

坑 6：小程序真机请求报「域名不合法」或 SSL 错误
结论：开发者工具关闭「不校验合法域名」时正常，真机预览全部失败。
原因：真机强制校验 request 合法域名与 HTTPS 证书链，域名白名单没配或证书链不完整。
解法：微信后台配置正确的 request 合法域名（不带端口）；证书用 fullchain 部署；用 openssl s_client 验证证书链。

坑 7：upstream 后端挂了但请求仍打到它，接口长时间超时
结论：一台后端宕机后，部分请求仍超时十几秒才返回。
原因：没有配置 max_fails/fail_timeout，Nginx 默认失败 1 次即标记不可用但 probe 周期长；或后端进程假死（端口通但无响应）。
解法：配置 max_fails=3 fail_timeout=30s；给后端加健康检查端点（/actuator/health），用 nginx_upstream_check_module 或外部探活。

坑 8：静态资源没有缓存配置，每次请求都打到磁盘
结论：管理端首屏加载慢，assets 请求全部 200（未命中缓存）。
原因：没配 expires/Cache-Control，浏览器每次都重新拉取资源。
解法：location /assets/ 配 expires 30d + immutable；index.html 配 no-cache；Gzip 开启 text/css、application/javascript 类型。

坑 9：WebSocket 反代失败，小程序 wx.connectSocket 连接不上
结论：小程序实时消息（聊天/通知）的 WebSocket 一直连接失败。
原因：Nginx 反代 WebSocket 需要显式传递 Upgrade/Connection 头，默认配置会把升级请求当普通 HTTP。
解法：location 里加 proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; 并调大 proxy_read_timeout 保持长连接。
```
