## 概述

Redis 是后台的「性能加速器」与「分布式协调器」：商品详情、首页推荐、验证码、登录 Token、购物车等高频读写场景全部落在 Redis 上，避免每次请求都压到 MySQL。本章覆盖 Redis 集成与序列化、缓存 key 设计、Spring Cache 注解、缓存穿透/击穿/雪崩三大问题、分布式锁与缓存一致性更新策略，是 17.4 数据库访问之上的重要一层。

```text
本章核心内容：
1. 集成配置 —— spring-boot-starter-data-redis、RedisTemplate/StringRedisTemplate、序列化
2. 缓存设计 —— key 规范（业务前缀:ID）、过期时间策略、热点与冷数据区分
3. Spring Cache —— @Cacheable/@CacheEvict/@CachePut 声明式缓存
4. 三大问题 —— 缓存穿透（空值/布隆过滤器）、击穿（互斥锁/逻辑过期）、雪崩（随机过期）
5. 分布式锁 —— Redisson 与 RedisTemplate setIfAbsent 两种实现
6. 缓存一致性 —— 先更新数据库再删缓存、延迟双删、最终一致性
```

## Redis 集成与序列化配置

Spring Boot 集成 Redis 只需引入 starter，自动配置会创建 RedisConnectionFactory、RedisTemplate 与 StringRedisTemplate 两个 Bean。StringRedisTemplate 是「key/value 都是 String」的特化版本，适合字符串场景（验证码、Token）；RedisTemplate 默认使用 JdkSerializationRedisSerializer，序列化后 key 带二进制乱码前缀，线上排查困难，因此生产环境都要显式配置 String 序列化 + JSON 序列化。

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

```yaml
# application.yml —— Redis 连接配置
spring:
  data:
    redis:
      host: localhost
      port: 6379
      password:                  # 无密码留空，生产必设密码
      database: 0                # 库编号：0 业务缓存 / 1 登录态 / 2 分布式锁，按环境规划
      timeout: 3s                # 连接超时
      lettuce:
        pool:
          max-active: 16         # 连接池最大连接数
          max-idle: 8
          min-idle: 2
```

```java
// config/RedisConfig.java —— RedisTemplate 序列化配置（String key + JSON value）
package com.example.mall.config;

import com.fasterxml.jackson.annotation.JsonAutoDetect;
import com.fasterxml.jackson.annotation.PropertyAccessor;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.jsontype.impl.LaissezFaireSubTypeValidator;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.data.redis.serializer.GenericJackson2JsonRedisSerializer;
import org.springframework.data.redis.serializer.StringRedisSerializer;

@Configuration
public class RedisConfig {

    @Bean
    public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory factory) {
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);

        // key / hash key 用 String 序列化：可读、无乱码前缀
        StringRedisSerializer stringSerializer = new StringRedisSerializer();
        template.setKeySerializer(stringSerializer);
        template.setHashKeySerializer(stringSerializer);

        // value 用 JSON 序列化：存储人类可读 JSON，跨语言可解析
        ObjectMapper objectMapper = new ObjectMapper();
        objectMapper.setVisibility(PropertyAccessor.ALL, JsonAutoDetect.Visibility.ANY);
        // 开启类型信息，反序列化时能还原对象类型（GenericJackson2JsonRedisSerializer）
        objectMapper.activateDefaultTyping(LaissezFaireSubTypeValidator.instance,
                ObjectMapper.DefaultTyping.NON_FINAL);
        GenericJackson2JsonRedisSerializer jsonSerializer =
                new GenericJackson2JsonRedisSerializer(objectMapper);

        template.setValueSerializer(jsonSerializer);
        template.setHashValueSerializer(jsonSerializer);
        template.afterPropertiesSet();
        return template;
    }
}
```

```java
public class CacheDemoService {

        stringRedisTemplate.opsForList().leftPush("queue:order", "10001");     // List
        stringRedisTemplate.opsForHash().put("cart:1001", "product:1", "2");   // Hash
        stringRedisTemplate.opsForSet().add("sale:today", "p1", "p2");         // Set
        stringRedisTemplate.opsForZSet().add("rank:hot", "product:1", 99.0);   // ZSet
    }
}
```

```text
集成与序列化要点：
1. 必须自定义 RedisTemplate 序列化：key 用 String，value 用 GenericJackson2JsonRedisSerializer
2. 默认 JdkSerialization 序列化 key 带 \xAC\xED 乱码前缀，且对象需实现 Serializable，排查困难
3. 纯字符串场景直接用 StringRedisTemplate，无需序列化配置
4. JSON 序列化开启 DefaultTyping 后能还原对象类型，但注意类型安全与升级兼容
5. 连接池（lettuce.pool）按并发量配置，超时 3s 防止 Redis 故障拖垮线程
6. 生产环境 Redis 必须设密码，数据库编号按用途规划，不跨环境混用
```

## 缓存设计与 key 规范

缓存设计的第一原则是「只缓存值得缓存的数据」：读多写少、数据量稳定、可容忍短暂不一致的数据适合缓存（商品详情、类目树、配置项）；读写都频繁或强一致要求的数据不适合（库存扣减、支付状态）。key 规范统一为「业务域:业务对象:标识」三段式，如 product:detail:1001、user:token:1001、sms:code:13800138000，可读性强、避免 key 冲突、便于按前缀批量清理。

```text
缓存 key 设计规范：
1. 三段式：业务域:对象:标识 —— product:detail:1001 / user:profile:1001 / cart:1001
2. key 区分业务域前缀，防止不同模块 key 撞车；同前缀便于 Redis CLI 批量扫描与清理
3. 过期时间分层：热点数据 30 分钟-1 小时，普通数据 10-30 分钟，验证码 5 分钟
4. 大 key 与小 key 分离：列表缓存（大）与单条详情（小）用不同 key，避免互相污染
5. 缓存内容只放展示所需字段，用 VO 序列化，不缓存整个 Entity（含敏感字段）
6. 过期时间加随机偏移（±30%），避免同一时刻批量过期（防雪崩）
7. 删除策略走「主动删除 + 过期兜底」双保险，不依赖 Redis 惰性删除
8. 线上用 info keyspace / bigkeys 定期检查 key 数量与体积，无引用 key 及时清理
```

```java
// service/ProductCacheService.java —— 手动缓存示例：查缓存-回源-回填
package com.example.mall.service.impl;

import com.example.mall.entity.Product;
import com.example.mall.mapper.ProductMapper;
import com.example.mall.vo.ProductVO;
import lombok.RequiredArgsConstructor;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.stereotype.Service;

import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;

@Service
@RequiredArgsConstructor
public class ProductCacheService {

    private final ProductMapper productMapper;
    private final RedisTemplate<String, Object> redisTemplate;

    private static final String KEY_PREFIX = "product:detail:";

    /** 查询商品：缓存命中直接返回，未命中查库并回填 */
    public ProductVO getProductDetail(Long id) {
        String key = KEY_PREFIX + id;

        // 1. 先查缓存
        Object cached = redisTemplate.opsForValue().get(key);
        if (cached != null) {
            return (ProductVO) cached;
        }

        // 2. 缓存未命中：查数据库
        Product product = productMapper.selectById(id);
        if (product == null) {
            return null;
        }
        ProductVO vo = convert(product);

        // 3. 回填缓存：基础 30 分钟 + 随机 0-9 分钟，防雪崩
        long expireMinutes = 30 + ThreadLocalRandom.current().nextInt(10);
        redisTemplate.opsForValue().set(key, vo, expireMinutes, TimeUnit.MINUTES);
        return vo;
    }

    /** 更新商品：先更新数据库，再删除缓存（见缓存一致性） */
    public void updateProduct(Product product) {
        productMapper.updateById(product);
        redisTemplate.delete(KEY_PREFIX + product.getId());
    }

    private ProductVO convert(Product product) {
        ProductVO vo = new ProductVO();
        vo.setId(product.getId());
        vo.setName(product.getName());
        vo.setPrice(product.getPrice());
        return vo;
    }
}
```

```text
缓存设计要点：
1. 缓存命中率是核心指标：命中率低于 70% 的缓存设计需要复盘（key 设计/过期时间/更新策略）
2. 读多写少 + 容忍秒级不一致是缓存的适用条件，先评估再上缓存
3. 缓存只放 VO 展示字段，不缓存密码等敏感数据；Redis dump 文件泄露风险要防范
4. 回填时设置过期时间（TTL 必须），防止「永不失效的脏数据」
5. 过期时间加随机偏移防批量失效；热点数据可考虑逻辑过期 + 异步续期
6. 每次缓存变更同步更新监控：命中率、延迟、key 数量
```

## Spring Cache 注解缓存

Spring Cache 提供声明式缓存：@Cacheable（先查缓存，未命中执行方法并回填）、@CachePut（执行方法并更新缓存）、@CacheEvict（执行方法并删除缓存）。开启方式：@EnableCaching 标注在启动类或配置类上，并配置 CacheManager（Redis 场景用 RedisCacheManager）。注解省去手写「查缓存-回源-回填」样板代码，适合缓存逻辑简单清晰的场景。

```java
// 启动类或配置类开启缓存
@SpringBootApplication
@EnableCaching
public class MallAdminApplication {
    public static void main(String[] args) {
        SpringApplication.run(MallAdminApplication.class, args);
    }
}
```

```java
// config/RedisCacheConfig.java —— RedisCacheManager 配置：统一 TTL 与 key 序列化
package com.example.mall.config;

import org.springframework.cache.CacheManager;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.cache.RedisCacheConfiguration;
import org.springframework.data.redis.cache.RedisCacheManager;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.serializer.GenericJackson2JsonRedisSerializer;
import org.springframework.data.redis.serializer.RedisSerializationContext;
import org.springframework.data.redis.serializer.StringRedisSerializer;

import java.time.Duration;

@Configuration
public class RedisCacheConfig {

    @Bean
    public CacheManager cacheManager(RedisConnectionFactory factory) {
        RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(30))                    // 默认过期 30 分钟
                .serializeKeysWith(RedisSerializationContext.SerializationPair
                        .fromSerializer(new StringRedisSerializer()))
                .serializeValuesWith(RedisSerializationContext.SerializationPair
                        .fromSerializer(new GenericJackson2JsonRedisSerializer()))
                .disableCachingNullValues();                          // 不缓存 null，防穿透依赖空值时要改

        return RedisCacheManager.builder(factory)
                .cacheDefaults(config)
                .build();
    }
}
```

```java
// service/ProductService.java —— 注解缓存使用
package com.example.mall.service.impl;

import com.example.mall.entity.Product;
import com.example.mall.mapper.ProductMapper;
import lombok.RequiredArgsConstructor;
import org.springframework.cache.annotation.CacheEvict;
import org.springframework.cache.annotation.CachePut;
import org.springframework.cache.annotation.Cacheable;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class ProductService {

    private final ProductMapper productMapper;

    /** 查询：缓存名为 product，key = product::1001 */
    @Cacheable(cacheNames = "product", key = "#id")
    public Product getById(Long id) {
        // 只有缓存未命中时才执行此方法
        return productMapper.selectById(id);
    }

    /** 更新：方法执行后把返回值写入缓存（key 相同则覆盖） */
    @CachePut(cacheNames = "product", key = "#product.id")
    public Product update(Product product) {
        productMapper.updateById(product);
        return product;
    }

    /** 删除：方法执行后删除缓存 key */
    @CacheEvict(cacheNames = "product", key = "#id")
    public void delete(Long id) {
        productMapper.deleteById(id);
    }

    /** 条件缓存：onlyIf 满足才写缓存，unless 满足不写缓存 */
    @Cacheable(cacheNames = "product", key = "#id",
            unless = "#result == null || #result.status != 1")
    public Product getOnSale(Long id) {
        return productMapper.selectById(id);
    }
}
```

注解缓存要注意的边界：方法不能是 private（走代理）；同类自调用失效（与 @Transactional 同源问题）；缓存 key 用 SpEL（#id、#product.id）；多级缓存（本地 + Redis）场景注解默认只有一级。注解适合「读多写少、方法粒度清晰」的场景，复杂业务（防击穿互斥锁、布隆过滤器）还是要手动控制缓存流程。

```text
Spring Cache 要点：
1. 三步启用：@EnableCaching + CacheManager Bean + 方法上标注注解
2. @Cacheable 查缓存未命中才执行方法；@CachePut 总是执行并写缓存；@CacheEvict 执行后删缓存
3. key 用 SpEL 表达式：#id 取参数，#result 取返回值，unless 为 true 不写缓存
4. 默认缓存名（cacheNames）会作为 key 前缀：product::1001
5. 自调用/private 方法注解不生效，与 @Transactional 的代理机制一致
6. 复杂场景（互斥锁、布隆、逻辑过期）用 RedisTemplate 手动实现更可控
```

## 缓存穿透击穿雪崩

缓存三大问题的本质与对策：

```text
三大问题对比：
1. 穿透 —— 查询不存在的数据：缓存没有、数据库也没有，请求每次都打到数据库
   对策：空值缓存（TTL 短）、布隆过滤器前置拦截、参数合法性校验
2. 击穿 —— 热点 key 过期瞬间：大量并发同时回源数据库，打爆单点
   对策：互斥锁（只放一个线程回源）、逻辑过期（异步刷新）、热点 key 永不过期+主动更新
3. 雪崩 —— 大量 key 同时过期或 Redis 宕机：数据库被集中打爆
   对策：过期时间加随机偏移、多级缓存（本地缓存兜底）、Redis 高可用（主从+哨兵/集群）、熔断降级
```

缓存穿透的空值缓存与布隆过滤器实现：

```java
// service/ProductService.java —— 空值缓存防穿透
public Product getByIdWithBlankCache(Long id) {
    String key = "product:detail:" + id;
    Object cached = redisTemplate.opsForValue().get(key);
    if (cached != null) {
        // 缓存了空标记（BLANK），直接返回 null，不再打库
        if ("BLANK".equals(cached)) {
            return null;
        }
        return (Product) cached;
    }
    Product product = productMapper.selectById(id);
    if (product == null) {
        // 不存在的 id 也写缓存：空值占位，TTL 缩短到 5 分钟
        redisTemplate.opsForValue().set(key, "BLANK", 5, TimeUnit.MINUTES);
        return null;
    }
    redisTemplate.opsForValue().set(key, product, 30, TimeUnit.MINUTES);
    return product;
}
```

```java
// util/ProductBloomFilter.java —— 布隆过滤器拦截不存在的 id
package com.example.mall.util;

import com.google.common.hash.BloomFilter;
import com.google.common.hash.Funnels;
import jakarta.annotation.PostConstruct;
import org.springframework.stereotype.Component;

import java.nio.charset.StandardCharsets;

@Component
public class ProductBloomFilter {

    /** 预计 10 万商品，误判率 1% */
    private final BloomFilter<String> filter =
            BloomFilter.create(Funnels.stringFunnel(StandardCharsets.UTF_8), 100_000, 0.01);

    @PostConstruct
    public void init() {
        // 启动时加载全部商品 id（也可定时增量更新）
        productIds().forEach(id -> filter.put(id));
    }

    public boolean mightContain(String id) {
        return filter.mightContain(id);
    }
}
```

```java
// 查询入口：先过布隆过滤器，一定不存在的直接返回，不再查缓存和库
public Product getByIdSafe(Long id) {
    if (!productBloomFilter.mightContain(String.valueOf(id))) {
        return null;   // 布隆判定不存在：直接返回，数据库零压力
    }
    return getByIdWithBlankCache(id);   // 布隆通过才走缓存+数据库
```

缓存击穿的互斥锁方案（Redis setIfAbsent 实现）与逻辑过期方案：

```java
// service/ProductService.java —— 互斥锁防击穿
public Product getByIdWithMutex(Long id) {
    String key = "product:detail:" + id;
    Product cached = (Product) redisTemplate.opsForValue().get(key);
    if (cached != null) {
        return cached;
    }
    // 缓存未命中：尝试获取锁（SET NX EX），只有一个线程能成功
    String lockKey = "lock:product:" + id;
    String lockValue = UUID.randomUUID().toString();
    Boolean locked = stringRedisTemplate.opsForValue()
            .setIfAbsent(lockKey, lockValue, 10, TimeUnit.SECONDS);
    if (Boolean.TRUE.equals(locked)) {
        try {
            // 双重检查：拿到锁后可能已有其他线程回填
            cached = (Product) redisTemplate.opsForValue().get(key);
            if (cached != null) {
                return cached;
            }
            Product product = productMapper.selectById(id);
            if (product != null) {
                redisTemplate.opsForValue().set(key, product, 30, TimeUnit.MINUTES);
            }
            return product;
        } finally {
            // 释放锁：先校验 value 再删，防止误删他人锁（Lua 脚本保证原子性）
            String script = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
            stringRedisTemplate.execute(
                    new DefaultRedisScript<>(script, Long.class),
                    List.of(lockKey), lockValue);
        }
    }
    // 没抢到锁：短暂自旋等待后重查缓存（或直接返回旧缓存）
    try {
        Thread.sleep(100);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
    return (Product) redisTemplate.opsForValue().get(key);
}
```

```text
三大问题实战要点：
1. 穿透三件套：参数合法性校验（id>0）+ 空值缓存（TTL 5 分钟）+ 布隆过滤器（可选项，数据量大时上）
2. 击穿只针对热点 key：互斥锁方案实现简单，注意锁要设置过期时间防死锁、释放要 Lua 校验
3. 逻辑过期方案：缓存不设 TTL，value 存「数据+过期时间戳」，过期后异步线程回源刷新，返回旧数据
4. 雪崩三件套：过期随机偏移 + 本地缓存（Caffeine 二级缓存）+ Redis 高可用与降级开关
5. 布隆过滤器有误判率（判定存在可能不存在），删除数据时无法从布隆删除，需要定期重建
6. 所有防御方案都要有「降级开关」，Redis 不可用时直接走数据库并告警
```

## 分布式锁

分布式锁解决「多实例（多台服务器）下互斥访问共享资源」的问题：单机 synchronized 只能锁住一个 JVM，微服务/集群部署时必须用 Redis、Zookeeper 等外部组件做分布式锁。两个主流实现：RedisTemplate 手写（setIfAbsent + Lua 释放，适合简单场景）、Redisson（官方推荐，内置看门狗自动续期、可重入、公平锁）。


```java
import org.redisson.api.RedissonClient;

import java.util.concurrent.TimeUnit;

        try {
            if (!lock.tryLock(3, TimeUnit.SECONDS)) {
                return false;   // 3 秒内没拿到锁，说明并发太激烈，直接失败

            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
```

手写 RedisTemplate 版本的关键点：加锁用 setIfAbsent(key, value, timeout)（SET NX EX 原子操作，value 存 UUID 标识 owner）；释放锁必须用 Lua 脚本「先比较 value 再删除」，防止「锁已过期被他人持有后，自己把别人的锁删掉」；锁必须设置过期时间防死锁。Redisson 的看门狗（Watchdog）机制解决「业务执行时间超过锁过期时间」的问题：默认锁 30 秒，业务未完成时每 10 秒自动续期，业务完成后主动释放。

```java
// service/SeckillService.java —— RedisTemplate 手写分布式锁（简单场景）
public boolean seckillSimple(Long productId, Long userId) {
    String lockKey = "lock:seckill:" + productId;
    String lockValue = UUID.randomUUID().toString();
    // SET NX EX：key 不存在才设置成功，10 秒自动过期防死锁
    Boolean locked = stringRedisTemplate.opsForValue()
            .setIfAbsent(lockKey, lockValue, 10, TimeUnit.SECONDS);
    if (!Boolean.TRUE.equals(locked)) {
        return false;
    }
    try {
        return doSeckill(productId, userId);
    } finally {
        // Lua 释放：value 匹配才删除，避免误删
        String script = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
        stringRedisTemplate.execute(new DefaultRedisScript<>(script, Long.class),
                List.of(lockKey), lockValue);
    }
}
```

```text
分布式锁要点：
1. 锁 key 按业务资源命名（lock:seckill:1001），粒度越小并发越高
2. 加锁必须原子（SET NX EX），释放必须 Lua 校验 owner，两者缺一不可
3. 锁必须设置过期时间，防止持有者宕机导致死锁；Redisson 看门狗自动续期解决长任务
4. tryLock 等待时间按业务设定：抢购场景等 3 秒拿不到就失败，不要无限等待
5. 锁内只放临界区代码，数据库事务与锁的顺序要一致（先拿锁再开事务，避免死锁）
6. 单机 Redis 锁在「主从切换」场景可能失效（主宕机锁未同步到从），强一致场景用 Redisson RedLock 或 Zookeeper
```

## 缓存一致性

缓存一致性解决「数据库更新了，缓存还是旧数据」的问题。主流的更新策略对比：

```text
更新策略对比：
1. 先删缓存再更新库 —— 更新期间可能被并发请求回填旧数据，不推荐
2. 先更新库再删缓存（Cache Aside）—— 业界主流：更新成功后删除缓存，下次读取回填新值
3. 延迟双删 —— 先删缓存 -> 更新库 -> 休眠 500ms -> 再删缓存，解决「回填旧值」竞态
4. 消息队列异步删缓存 —— 更新库后发 MQ，消费端删缓存，最终一致性
5. 订阅 binlog（Canal）—— 数据库变更自动同步删除缓存，与业务代码解耦
```

Cache Aside（先更新数据库再删缓存）是目前最常用的策略：更新操作「先写库、再删缓存」；查询未命中时回填。为什么不是「先删缓存再更新库」？因为删缓存后、更新库前，如果有并发读请求，会把旧数据回填到缓存，最终缓存里还是旧值。Cache Aside 的竞态窗口（删缓存前有请求读到了旧值并回填）用延迟双删兜底。

```java
// service/ProductService.java —— Cache Aside + 延迟双删
package com.example.mall.service.impl;

import lombok.RequiredArgsConstructor;
import org.springframework.scheduling.annotation.Async;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class ProductService {

    private static final String KEY_PREFIX = "product:detail:";

    private final ProductMapper productMapper;
    private final RedisTemplate<String, Object> redisTemplate;

    /** 更新商品：先更新数据库，再删缓存（Cache Aside） */
    public void updateProduct(Product product) {
        productMapper.updateById(product);
        redisTemplate.delete(KEY_PREFIX + product.getId());
    }

    /** 延迟双删：先删缓存 -> 更新库 -> 延时再删，兜底并发回填旧值 */
    public void updateProductDoubleDelete(Product product) {
        redisTemplate.delete(KEY_PREFIX + product.getId());   // 第一删
        productMapper.updateById(product);                     // 更新数据库
        // 休眠 500ms 让并发读请求完成「回填旧值」窗口，再删一次
        try {
            Thread.sleep(500);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        redisTemplate.delete(KEY_PREFIX + product.getId());   // 第二删
    }

    /** 异步删缓存版本：不阻塞主流程，配合消息队列语义 */
    @Async("asyncExecutor")
    public void deleteCacheAsync(Long id) {
        try {
            Thread.sleep(500);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        redisTemplate.delete(KEY_PREFIX + id);
    }
}
```

MySQL 与 Redis 之间没有本地事务，写库成功但删缓存失败就会产生脏缓存。补偿手段：删缓存失败重试（重试次数/退避）、把删除操作丢进 MQ 异步重试、订阅 binlog 由 Canal 统一处理。终极方案是让缓存从「主动维护」变为「被动订阅」：数据库变更 -> binlog -> Canal -> 删除/重建缓存，业务代码零侵入。

```text
缓存一致性要点：
1. 默认选 Cache Aside：先更新数据库，再删除缓存，简单且正确率高
2. 读多写少且容忍短暂不一致（秒级）才用缓存，强一致场景直接读库
3. 删缓存失败必须补偿：重试 / MQ / Canal binlog 订阅
4. 延迟双删的 500ms 是经验值，按业务读延迟调整；异步执行避免阻塞写请求
5. 缓存 key 统一由「更新方删除」而不是「查询方失效」，职责单一
6. 上线缓存前先明确「可容忍的不一致时间」，写进接口文档，避免后续扯皮
```

```java
// service/ProductDetailService.java —— 手动缓存 + 空值防穿透 + 随机过期
package com.example.mall.service.impl;

import com.example.mall.entity.Product;
import com.example.mall.mapper.ProductMapper;
import lombok.RequiredArgsConstructor;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.stereotype.Service;

import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;

@Service
@RequiredArgsConstructor
public class ProductDetailService {

    private static final String KEY_PREFIX = "product:detail:";
    private static final String BLANK = "BLANK";

    private final ProductMapper productMapper;
    private final RedisTemplate<String, Object> redisTemplate;

    public Product getDetail(Long id) {
        String key = KEY_PREFIX + id;
        Object cached = redisTemplate.opsForValue().get(key);
        if (cached != null) {
            if (BLANK.equals(cached)) {
                return null;                    // 空值命中：直接返回，不打库
            }
            return (Product) cached;            // 缓存命中
        }
        Product product = productMapper.selectById(id);
        if (product == null) {
            // 防穿透：不存在也缓存空值，TTL 5 分钟
            redisTemplate.opsForValue().set(key, BLANK, 5, TimeUnit.MINUTES);
            return null;
        }
        // 防雪崩：30 分钟 + 随机 0-9 分钟
        long ttl = 30 + ThreadLocalRandom.current().nextInt(10);
        redisTemplate.opsForValue().set(key, product, ttl, TimeUnit.MINUTES);
        return product;
    }
}
```

```java
// service/SeckillServiceImpl.java —— 带降级开关的秒杀
@Service
public class SeckillServiceImpl {

    private final RedissonClient redissonClient;
    private final StringRedisTemplate stringRedisTemplate;

    /** 降级开关：配置中心/数据库可动态修改；true 表示 Redis 不可用，直接走库 */
    @Value("${seckill.cache.fallback:false}")
    private boolean cacheFallback;

    public boolean seckill(Long productId, Long userId) {
        if (cacheFallback) {
            // 降级路径：直接数据库原子扣减，不抢分布式锁（保命优先）
            return directDeduct(productId);
        }
        RLock lock = redissonClient.getLock("lock:seckill:" + productId);
        try {
            if (!lock.tryLock(3, TimeUnit.SECONDS)) {
                return false;
            }
            return directDeduct(productId);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return false;
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }

    /** 原子扣减：UPDATE ... WHERE stock > 0，返回影响行数，1 表示扣减成功 */
    private boolean directDeduct(Long productId) {
        int rows = productMapper.deductStock(productId, 1);
        return rows == 1;
    }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. key 统一「业务域:对象:标识」三段式命名并写入团队规范，value 只放 VO 展示字段，禁止缓存 Entity 含敏感字段
2. 所有缓存必须设置 TTL（过期时间 + 随机偏移），杜绝永久缓存；过期时间按数据实时性要求分层设计
3. 查询链路统一「缓存 -> 数据库 -> 回填」顺序，回填失败不影响主流程（try-catch 吞掉并告警）
4. 更新策略默认 Cache Aside（先更新库再删缓存），删缓存失败要有重试或 MQ 补偿
5. 分布式锁优先用 Redisson（看门狗续期、可重入），手写版本务必 SET NX EX + Lua 释放
6. 穿透/击穿/雪崩三套防御按业务场景选配：空值缓存必上，布隆过滤器数据量大再上，互斥锁只给热点 key
7. Redis 单独部署监控：命中率、延迟、内存、bigkeys；生产密码 + 最小权限 + 不暴露公网端口
8. 缓存上线前定义好降级策略（开关 + 直接走库），Redis 故障时保证核心链路可用

### 踩坑记录

```text
坑 1：RedisTemplate 没配序列化，key 变成 \xAC\xED\x00\x05t 乱码
结论：redis-cli 里看到一堆乱码 key，按业务 key 无法排查。
原因：默认 JdkSerializationRedisSerializer 序列化 key，带二进制头。
解法：配置 StringRedisSerializer 做 key 序列化，value 用 GenericJackson2JsonRedisSerializer。

坑 2：缓存的对象反序列化失败，ClassCastException
结论：从缓存取出的对象强转报错，或类型信息缺失变成 LinkedHashMap。
原因：value 序列化没开启类型信息（DefaultTyping），反序列化无法还原具体类型；或实体类结构变更（加了字段/改了包名）。
解法：GenericJackson2JsonRedisSerializer 默认携带类型信息；实体类变更时注意兼容旧缓存，或加缓存版本号 key。

坑 3：先删缓存再更新库，并发下缓存被回填旧值
结论：更新后查询偶发拿到旧数据，且长时间不恢复。
原因：删除缓存后、更新库前，并发读请求把旧数据回填到缓存。
解法：改用 Cache Aside（先更新库再删缓存）；严格要求时用延迟双删或 MQ 异步删。

坑 4：删缓存失败导致脏数据长期存在
结论：更新数据库成功但缓存一直是旧值，用户看到过期信息。
原因：删除 Redis 的操作失败（网络抖动/超时），没有补偿机制。
解法：删除失败重试（重试 3 次 + 退避）；或投递 MQ 异步删除；或 Canal 订阅 binlog 统一处理。

坑 5：分布式锁没设过期时间，持有者宕机导致死锁
结论：秒杀接口永久失败，所有请求都拿不到锁。
原因：lock 后业务异常/进程宕机未 unlock，锁没有自动过期机制。
解法：加锁必须带超时（setIfAbsent 的 timeout 或 Redisson tryLock 的 leaseTime）；Redisson 看门狗兜底；监控锁 key 长期存在的告警。

坑 6：释放锁时误删了别人的锁
结论：A 线程刚释放锁，B 线程刚拿到锁，A 的删除操作把 B 的锁删了，导致并发进入临界区。
原因：释放锁只执行 del，没有校验持有者；或锁已过期被他人获取，原持有者 del 删掉新锁。
解法：value 存 UUID 标识，释放用 Lua「比较后删除」；Redisson 内部已实现，手写版本务必照抄。

坑 7：缓存穿透没防，大量不存在的 id 把数据库打挂
结论：数据库 CPU/连接数飙升，慢查询全是按 id 查不存在的行。
原因：接口对 id 无合法性校验，且不存在数据不缓存，每次请求都打库（可能被脚本恶意遍历）。
解法：参数校验 + 空值缓存（TTL 短）+ 布隆过滤器；配合接口限流。

坑 8：热点 key 过期瞬间，数据库被并发回源打爆（击穿）
结论：大促时某个爆款商品详情接口超时，数据库负载瞬间拉满。
原因：热点 key TTL 到点，大量并发请求同时未命中缓存，全部回源数据库。
解法：互斥锁只放一个线程回源；或热点 key 逻辑过期 + 异步刷新；热点 key 永不过期 + 主动更新。

坑 9：批量 key 同时过期，数据库雪崩
结论：凌晨 0 点后数据库突然高负载，一批接口全部变慢。
原因：同一批数据用了相同 TTL，同时过期后集中回源。
解法：TTL 加随机偏移（30 分钟 + random(0-10)）；本地缓存（Caffeine）二级兜底；Redis 集群 + 主从。

坑 10：@Cacheable 自调用不生效，每次请求都打数据库
结论：同一个 Service 内部方法调用了带 @Cacheable 的方法，缓存完全不命中。
原因：同类自调用不经过 Spring 代理，注解切面不执行（与 @Transactional 同源问题）。
解法：拆到不同 Bean 调用；或注入自身代理（@Lazy 注入 / AopContext.currentProxy()）；复杂逻辑直接改用 RedisTemplate 手动缓存。
```
