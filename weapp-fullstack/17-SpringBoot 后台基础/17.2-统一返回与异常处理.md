## 概述

小程序端（wx.request）与后台交互时，期望收到一种「固定结构」的 JSON，无论成功失败都能用同一套逻辑解析，这是统一响应体的价值。Spring Boot 后台通过 Result 封装 + 全局异常处理 + 业务异常 + 错误码四件套，实现「接口永远返回统一结构，业务异常与非业务异常都在一处收敛」。本章代码建立在 17.1 的分层工程之上。

```text
本章核心内容：
1. Result 封装 —— 统一响应体 Result<T>：code / message / data 三要素
2. 错误码 —— 枚举管理错误码，code 定义规范与归类
3. 业务异常 —— BusinessException 携带错误码抛出，代替裸 return 失败分支
4. 全局异常处理 —— @RestControllerAdvice + @ExceptionHandler 统一捕获
5. 兜底处理 —— 未知异常兜底、参数校验异常、HTTP 404/405 处理
6. 统一响应规范 —— 所有 REST 接口返回 Result，分页返回 PageResult
```

## Result 统一响应体封装

统一响应体（Unified Response Body）是前后端约定的数据契约：所有接口无论成功还是失败，HTTP 200 情况下 body 都是 `{"code": 200, "message": "success", "data": ...}`，前端 wx.request 封装只需解析这一种结构。code 表示业务状态码（200 成功，非 200 失败），message 是给用户或前端展示的提示文本，data 是业务数据（成功时有值，失败时可为 null）。

```java
// common/Result.java —— 统一响应体
package com.example.mall.common;

import lombok.Data;

@Data
public class Result<T> {

    private Integer code;
    private String message;
    private T data;

    public Result() {
    }

    public Result(Integer code, String message, T data) {
        this.code = code;
        this.message = message;
        this.data = data;
    }

    /** 成功：无数据 */
    public static <T> Result<T> success() {
        return new Result<>(200, "success", null);
    }

    /** 成功：带数据 */
    public static <T> Result<T> success(T data) {
        return new Result<>(200, "success", data);
    }

    /** 成功：自定义消息 */
    public static <T> Result<T> success(String message, T data) {
        return new Result<>(200, message, data);
    }

    /** 失败：默认错误码 500 */
    public static <T> Result<T> error(String message) {
        return new Result<>(500, message, null);
    }

    /** 失败：自定义错误码 */
    public static <T> Result<T> error(Integer code, String message) {
        return new Result<>(code, message, null);
    }

    /** 失败：从错误码枚举构造 */
    public static <T> Result<T> error(ErrorCode errorCode) {
        return new Result<>(errorCode.getCode(), errorCode.getMessage(), null);
    }
}
```

```java
// 使用示例：Controller 中返回成功与失败
@GetMapping("/{id}")
public Result<ProductVO> detail(@PathVariable Long id) {
    ProductVO product = productService.getProduct(id);
    if (product == null) {
        return Result.error(ErrorCode.PRODUCT_NOT_FOUND);   // 返回失败结构
    }
    return Result.success(product);                          // 返回成功结构
}
```

Result 泛型设计让 IDE 能推导 data 的类型，前端拿到后直接取 data 字段即可。一个常见误区是「HTTP 状态码当业务码用」：业务失败（如库存不足）时 HTTP 状态码仍是 200，只有系统级故障（如 404 路由不存在、500 服务器错误）才用非 200 的 HTTP 状态码。业务码放 body 里，HTTP 码管传输层，两者职责分离。

```text
Result 设计要点：
1. 三要素固定：code（业务码）+ message（提示）+ data（数据），前端只需解析这一种结构
2. code=200 表示成功，业务失败用其他码，与 HTTP 状态码分离
3. 静态工厂方法 success/error 屏蔽 new 过程，调用处语义清晰
4. data 用泛型 T，成功时携带业务数据，失败时为 null
5. 时间字段由 Jackson 统一格式化（17.1 已配置 date-format），保证前后端格式一致
6. 小程序端 wx.request 封装里统一处理：code!=200 时 showToast(message) 并 reject
```

## 错误码设计与业务异常

错误码（ErrorCode）用枚举统一管理，集中定义所有业务错误的编号与提示文案。code 定义规范：按模块分段（如 1xxx 用户模块、2xxx 商品模块、3xxx 订单模块），同一模块内的错误码连续编号；message 面向用户，写成「库存不足」「该商品已下架」这类可直接展示的文案，而不是「SQLException」这种技术描述。

```java
// common/ErrorCode.java —— 错误码枚举
package com.example.mall.common;

import lombok.Getter;

@Getter
public enum ErrorCode {

    // 通用错误 1000-1999
    SUCCESS(200, "success"),
    PARAM_ERROR(1000, "参数错误"),
    PARAM_MISSING(1001, "缺少必要参数"),
    UNAUTHORIZED(1002, "未登录或登录已过期"),
    FORBIDDEN(1003, "无权限访问"),
    NOT_FOUND(1004, "资源不存在"),
    SYSTEM_ERROR(1005, "系统繁忙，请稍后重试"),

    // 用户模块 2000-2999
    USER_NOT_FOUND(2000, "用户不存在"),
    USER_PASSWORD_ERROR(2001, "用户名或密码错误"),
    USER_ALREADY_EXISTS(2002, "用户已存在"),

    // 商品模块 3000-3999
    PRODUCT_NOT_FOUND(3000, "商品不存在"),
    PRODUCT_OFF_SHELF(3001, "商品已下架"),
    PRODUCT_STOCK_NOT_ENOUGH(3002, "商品库存不足"),

    // 订单模块 4000-4999
    ORDER_NOT_FOUND(4000, "订单不存在"),
    ORDER_STATUS_ERROR(4001, "订单状态不允许该操作");

    private final Integer code;
    private final String message;

    ErrorCode(Integer code, String message) {
        this.code = code;
        this.message = message;
    }
}
```

业务异常（BusinessException）是业务规则不满足时主动抛出的异常，它携带错误码，由全局异常处理器统一转为 Result。设计业务异常的意义：业务代码里「该失败就抛」，不再用返回 null + if 判断的方式散落处理失败分支，失败语义集中在异常对象里。

```java
// common/BusinessException.java —— 业务异常
package com.example.mall.common;

import lombok.Getter;

@Getter
public class BusinessException extends RuntimeException {

    private final Integer code;

    public BusinessException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.code = errorCode.getCode();
    }

    public BusinessException(ErrorCode errorCode, String detail) {
        super(detail);
        this.code = errorCode.getCode();
    }

    public BusinessException(Integer code, String message) {
        super(message);
        this.code = code;
    }
}
```

```java
// 业务代码中的使用：失败直接抛异常，不再返回 null
public void createOrder(CreateOrderDTO dto) {
    Product product = productMapper.selectById(dto.getProductId());
    if (product == null) {
        throw new BusinessException(ErrorCode.PRODUCT_NOT_FOUND);
    }
    if (product.getStatus() != 1) {
        throw new BusinessException(ErrorCode.PRODUCT_OFF_SHELF);
    }
    if (product.getStock() < dto.getQuantity()) {
        throw new BusinessException(ErrorCode.PRODUCT_STOCK_NOT_ENOUGH);
    }
    // 扣库存、生成订单...
}
```

```text
错误码与业务异常要点：
1. 错误码按模块分段编号（1xxx 通用 / 2xxx 用户 / 3xxx 商品 / 4xxx 订单），新模块申请新段
2. message 面向用户可展示，禁止把异常类名、SQL 语句直接当提示文案
3. BusinessException 继承 RuntimeException，不强制 try-catch，由全局处理器统一接住
4. 业务失败优先抛 BusinessException，不要吞异常、不要返回 null 让上层猜原因
5. 错误码一旦发布就尽量不修改含义，前端可能已按 code 做分支逻辑
6. 与 HTTP 状态码分离：业务失败 HTTP 仍 200，body 里 code 表达业务结果
```

## 全局异常处理

全局异常处理用 @RestControllerAdvice + @ExceptionHandler 把「散落在每个 Controller 的 try-catch」收敛到一个类中：任何 Controller 方法抛出异常，Spring MVC 都会路由到对应类型的 @ExceptionHandler 方法。全局异常处理器统一负责：业务异常转 Result、参数校验异常提取字段错误信息、未知异常兜底记录日志并返回友好提示。

```java
// common/GlobalExceptionHandler.java —— 全局异常处理
package com.example.mall.common;

import lombok.extern.slf4j.Slf4j;
import org.springframework.http.HttpStatus;
import org.springframework.validation.BindException;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.servlet.resource.NoResourceFoundException;

import java.util.stream.Collectors;

@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    /** 业务异常：转成对应错误码的 Result */
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusinessException(BusinessException e) {
        log.warn("业务异常：code={}, message={}", e.getCode(), e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    /** 参数校验异常：@RequestBody + @Valid 校验失败时抛出 */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleMethodArgumentNotValid(MethodArgumentNotValidException e) {
        String message = e.getBindingResult().getFieldErrors().stream()
                .map(FieldError::getDefaultMessage)
                .collect(Collectors.joining("；"));
        log.warn("参数校验失败：{}", message);
        return Result.error(ErrorCode.PARAM_ERROR.getCode(), message);
    }

    /** 参数绑定异常：GET 查询参数绑定失败（类型转换、格式错误） */
    @ExceptionHandler(BindException.class)
    public Result<Void> handleBindException(BindException e) {
        String message = e.getBindingResult().getFieldErrors().stream()
                .map(FieldError::getDefaultMessage)
                .collect(Collectors.joining("；"));
        log.warn("参数绑定失败：{}", message);
        return Result.error(ErrorCode.PARAM_ERROR.getCode(), message);
    }

    /** 资源不存在：Spring Boot 3.2+ 请求不存在的路径抛 NoResourceFoundException */
    @ExceptionHandler(NoResourceFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public Result<Void> handleNotFound(NoResourceFoundException e) {
        return Result.error(ErrorCode.NOT_FOUND.getCode(), "请求的资源不存在");
    }

    /** 兜底异常：未知异常记录完整堆栈，返回友好提示，不把堆栈泄露给前端 */
    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) {
        log.error("系统异常", e);
        return Result.error(ErrorCode.SYSTEM_ERROR);
    }
}
```

@ExceptionHandler 的匹配规则是「最精确优先」：抛出的异常先找类型完全匹配的处理器，找不到再沿继承链向上找。因此 BusinessException 会被业务处理器接住而不会落入 Exception 兜底；兜底处理器只处理真正的未知异常。@ResponseStatus(HttpStatus.NOT_FOUND) 可以让 404 场景同时返回非 200 的 HTTP 状态码，前端据此区分「业务失败」与「接口不存在」。

```text
全局异常处理要点：
1. @RestControllerAdvice 全局生效，等价于 @ControllerAdvice + @ResponseBody
2. @ExceptionHandler 按异常类型精确匹配，先精确后继承链，兜底 Exception 放最后
3. MethodArgumentNotValidException 处理 @RequestBody 校验失败，BindException 处理 GET 参数绑定失败
4. 兜底处理器必须 log.error 记录完整堆栈，方便线上排查
5. 不要对每个 Controller 写 try-catch 包业务异常，全局处理器一处收敛
6. 前端拿不到堆栈，message 永远是可读文案，技术细节只进日志
```

## 统一响应规范与分页返回

统一响应规范要求：所有 REST 接口的返回值类型统一为 Result<T>，包括分页查询。分页场景如果直接把 List 塞进 data，前端拿不到 total 总数无法渲染分页器，因此定义 PageResult<T> 承载分页元数据：records（当前页数据）、total（总条数）、pageNum、pageSize。小程序端「上拉加载更多」就是基于 pageNum/pageSize 增量请求。

```java
// common/PageResult.java —— 分页返回结构
package com.example.mall.common;

import com.baomidou.mybatisplus.core.metadata.IPage;
import lombok.Data;

import java.util.List;

@Data
public class PageResult<T> {

    private List<T> records;      // 当前页数据
    private Long total;           // 总记录数
    private Long pageNum;         // 当前页码
    private Long pageSize;        // 每页条数
    private Long pages;           // 总页数

    public static <T> PageResult<T> of(IPage<T> page) {
        PageResult<T> result = new PageResult<>();
        result.setRecords(page.getRecords());
        result.setTotal(page.getTotal());
        result.setPageNum(page.getCurrent());
        result.setPageSize(page.getSize());
        result.setPages(page.getPages());
        return result;
    }

    public static <T> PageResult<T> of(List<T> records, Long total, Long pageNum, Long pageSize) {
        PageResult<T> result = new PageResult<>();
        result.setRecords(records);
        result.setTotal(total);
        result.setPageNum(pageNum);
        result.setPageSize(pageSize);
        result.setPages((total + pageSize - 1) / pageSize);
        return result;
    }
}
```

```java
// 分页接口返回示例（MyBatis-Plus 分页，17.4 详解）
@GetMapping("/page")
public Result<PageResult<ProductVO>> page(@RequestParam(defaultValue = "1") long pageNum,
                                          @RequestParam(defaultValue = "10") long pageSize) {
    IPage<ProductVO> page = productService.pageProducts(pageNum, pageSize);
    return Result.success(PageResult.of(page));
}
```

统一响应规范落地还需要约定边界：返回类型必须是 Result，方法签名上写清楚；异常不「穿越」到响应层（不允许 Controller 直接 catch 后 return 半截数据）；文件下载、SSE 推送这类非 JSON 场景例外，单独约定。文件上传下载接口可以返回 void 或直接写 HttpServletResponse，但接口文档中要标注「非标准返回」。

```text
统一响应规范要点：
1. 所有 JSON 接口返回 Result<T>，禁止直接返回裸 List、裸 Map
2. 分页接口统一返回 PageResult<T>，包含 records/total/pageNum/pageSize
3. 异常统一抛给全局处理器，Controller 不 catch 业务异常（除了需要补偿逻辑的场景）
4. 成功 code=200 固定，新增接口不发明新的成功码
5. 文件下载、SSE 等非 JSON 场景在接口文档显式标注例外
6. 响应字段命名统一 camelCase，与 Jackson 默认配置一致，前端直接使用
```

## 应用场景实战

### 场景一：小程序登录接口的完整返回与异常链路

场景目标：实现 POST /api/auth/login 接口，演示成功返回 Result、密码错误抛 BusinessException、参数缺失被校验异常处理器接住三种情况的响应结构。

```text
步骤：
1. 创建 LoginDTO（用户名/密码，含校验注解，17.3 详解）
2. 创建 AuthController 调用 AuthService.login
3. AuthService 校验用户存在性与密码，失败抛 BusinessException
4. 用 curl 分别模拟：正确登录、密码错误、缺参数，观察三种返回结构
```

```java
// dto/LoginDTO.java
package com.example.mall.dto;

import jakarta.validation.constraints.NotBlank;
import lombok.Data;

@Data
public class LoginDTO {

    @NotBlank(message = "用户名不能为空")
    private String username;

    @NotBlank(message = "密码不能为空")
    private String password;
}
```

```java
// controller/AuthController.java
package com.example.mall.controller;

import com.example.mall.common.Result;
import com.example.mall.dto.LoginDTO;
import com.example.mall.service.AuthService;
import com.example.mall.vo.LoginVO;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/auth")
@RequiredArgsConstructor
public class AuthController {

    private final AuthService authService;

    @PostMapping("/login")
    public Result<LoginVO> login(@Valid @RequestBody LoginDTO dto) {
        return Result.success(authService.login(dto));
    }
}
```

```java
// service/AuthService.java 核心逻辑（简化版）
public LoginVO login(LoginDTO dto) {
    User user = userMapper.selectOne(new LambdaQueryWrapper<User>()
            .eq(User::getUsername, dto.getUsername()));
    if (user == null) {
        throw new BusinessException(ErrorCode.USER_NOT_FOUND);   // 抛业务异常
    }
    if (!passwordEncoder.matches(dto.getPassword(), user.getPassword())) {
        throw new BusinessException(ErrorCode.USER_PASSWORD_ERROR);
    }
    return new LoginVO(user.getId(), user.getNickname());
}
```

```bash
# 成功登录
curl -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"123456"}'
# {"code":200,"message":"success","data":{"id":1,"nickname":"管理员"}}

# 密码错误（业务异常被全局处理器接住）
curl -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"wrong"}'
# {"code":2001,"message":"用户名或密码错误","data":null}

# 缺参数（校验异常被 MethodArgumentNotValidException 处理器接住）
curl -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin"}'
# {"code":1000,"message":"密码不能为空","data":null}
```

三种情况前端 wx.request 拿到的是同一种 JSON 结构，request 封装里只需判断 code === 200 走成功分支，否则 toast message 并 reject，代码统一、心智负担小。

### 场景二：商品分页接口 + 库存扣减失败回滚

场景目标：实现 GET /api/products/page 分页接口与 POST /api/orders 下单接口，演示 PageResult 返回与事务中抛业务异常的回滚（数据库部分见 17.4，此处聚焦响应结构）。

```text
步骤：
1. ProductController 提供分页接口，返回 Result<PageResult<ProductVO>>
2. OrderController 提供下单接口，库存不足时抛 PRODUCT_STOCK_NOT_ENOUGH
3. curl 验证分页 JSON 结构（records/total/pageNum/pageSize）
4. curl 验证下单失败返回结构（code=3002，message=商品库存不足）
```

```java
// controller/ProductController.java —— 分页接口
package com.example.mall.controller;

import com.example.mall.common.PageResult;
import com.example.mall.common.Result;
import com.example.mall.service.ProductService;
import com.example.mall.vo.ProductVO;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/products")
@RequiredArgsConstructor
public class ProductController {

    private final ProductService productService;

    @GetMapping("/page")
    public Result<PageResult<ProductVO>> page(
            @RequestParam(defaultValue = "1") long pageNum,
            @RequestParam(defaultValue = "10") long pageSize) {
        return Result.success(productService.pageProducts(pageNum, pageSize));
    }
}
```

```bash
# 下单失败返回结构（业务码与 HTTP 状态码分离，HTTP 仍是 200）
curl -X POST http://localhost:8080/api/orders -H "Content-Type: application/json" \

# {"code":3002,"message":"商品库存不足","data":null}
```

```text
场景要点回顾：
1. 成功、业务失败、参数错误三种响应结构完全一致，前端一套解析逻辑
2. 分页 data 结构固定，小程序端 onPullDownRefresh/onReachBottom 直接取 records 追加
3. 业务失败不返回 null data 而返回错误 message，用户能看到明确提示
4. HTTP 状态码保持 200，避免 wx.request 把业务失败当网络错误处理
```

## 最佳实践与踩坑记录

### 最佳实践

1. Result 三要素 code/message/data 一旦上线就冻结结构，新增字段可以，删改字段要与前端同步排期
2. 错误码集中在一个枚举管理，按模块分段编号，message 面向用户可展示，代码评审时把「message 含异常类名/堆栈」作为红线
3. 业务失败一律抛 BusinessException，Controller 里不写「return Result.error」的业务判断，让失败路径全部走异常链路
4. 全局异常处理器里日志分级：业务异常 warn（不带堆栈），未知异常 error（带完整堆栈），避免日志噪音掩盖真问题
5. 分页查询统一用 PageResult，不要在 data 里塞 Map 或自定义结构，前端分页组件直接绑定字段
6. 接口文档（Swagger/OpenAPI）标注每个接口的返回结构，特别注明 HTTP 状态码与业务码的区分
7. 前端 wx.request 封装统一处理 code!=200：toast message + reject，业务代码只处理成功分支
8. 兜底异常返回「系统繁忙，请稍后重试」，不返回内部异常信息，防信息泄露

### 踩坑记录

```text
坑 1：Controller 自己 catch 异常返回 Result，全局处理器形同虚设
结论：同一个异常在不同接口返回结构不一致，有的带堆栈、有的返回 null。
原因：部分接口 try-catch 后手动 return Result.error，绕过了全局异常处理。
解法：代码评审强制规范，Controller 禁止 catch 业务异常；需要补偿逻辑的场景 catch 后重新 throw 或交给 AOP 处理。

坑 2：兜底异常返回了完整堆栈给前端
结论：线上接口报错，前端拿到一长串 SQLException/NullPointerException 堆栈。
原因：catch (Exception e) 后直接 return Result.error(500, e.getMessage()) 或 e.toString()。
解法：兜底处理器只返回固定文案，完整堆栈用 log.error(e) 记录到服务端日志。

坑 3：HTTP 状态码与业务码混淆，前端把业务失败当网络错误
结论：小程序端 wx.request 的 fail 回调频繁触发，用户看到「网络异常」。
原因：接口业务失败时返回了 4xx/5xx HTTP 状态码，wx.request 默认非 2xx 走 fail。
解法：业务失败保持 HTTP 200 + body code 非 200；只有系统级错误（404 路由、500 未知异常）才用非 200 状态码，前端封装区分处理。

坑 4：@ExceptionHandler(MethodArgumentNotValidException.class) 没生效，校验失败返回 Spring 默认结构
结论：校验失败返回 {"timestamp":...,"status":400,"error":"Bad Request"...}，不是 Result 结构。
原因：异常类型没匹配上——@RequestBody 校验失败抛 MethodArgumentNotValidException，而 GET 参数绑定失败抛 BindException，两者是不同类型；或只加了 @ControllerAdvice 没加 @ResponseBody。
解法：两个类型分别写处理器；@RestControllerAdvice 自带 @ResponseBody；确认处理器所在类被组件扫描。

坑 5：错误码复用导致前端分支逻辑错乱
结论：两个不同错误共用同一 code，前端按 code 分支时走了错误的逻辑。
原因：新接口偷懒复用了相近的错误码，比如「库存不足」与「商品不存在」都用 3000。
解法：每个错误独立编号，枚举注释写清使用场景；新增错误码不改动已有含义。

坑 6：全局处理器没处理 404，接口路径写错返回白屏/HTML
结论：小程序请求不存在的路径，返回的是 Spring Boot 默认 JSON 或 Whitelabel 错误页。
原因：Spring Boot 3.2+ 路径不存在抛 NoResourceFoundException，没写对应处理器时走默认错误页。
解法：增加 NoResourceFoundException 处理器返回 Result 结构；或配置 spring.mvc.throw-exception-if-no-handler-found=true 并自定义。

坑 7：分页返回 total 一直是 0 或 0 条记录
结论：分页接口返回空数据，前端分页器总页数永远 1。
原因：MyBatis-Plus 分页插件没注册（缺少 MybatisPlusInterceptor），分页 SQL 未生效；或 Page 对象没作为第一个参数传入。
解法：注册分页插件（见 17.4），分页方法第一个参数传 Page，后续参数为查询条件；确认 selectPage 而非 selectList。

坑 8：LoginVO/ProductVO 里出现 null 字段或密码字段泄露
结论：响应 JSON 里出现 password、idCard 等敏感字段或大量 null。
原因：VO 直接复制了 Entity 的全部字段，或没做字段裁剪。
解法：VO 只声明要返回的字段；密码等敏感字段不进 VO；全局配置 Jackson 忽略 null 字段（spring.jackson.default-property-inclusion=non_null）按需决定。
```
