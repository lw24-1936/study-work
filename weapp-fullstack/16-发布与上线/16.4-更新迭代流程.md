## 概述

小程序的竞争力来自迭代速度：需求 -> 开发 -> 提审 -> 发布 -> 数据验证 -> 下一个迭代，这个循环跑得越快越稳，产品进化就越快。但快不等于乱，迭代流程需要三样东西支撑：需求管理（做什么、为什么做）、版本计划（什么时候做、和谁一起做）、数据验证（做完效果如何、下一步做什么）。

迭代流程与前三章环环相扣：16.1 管「版本怎么编号、怎么过审」，16.2 管「怎么发布、怎么灰度」，16.3 管「上线后怎么看数据、怎么盯质量」，本章管「下一个版本做什么、怎么做决策」。AB 实验让需求决策从「拍脑袋」变成「数据说话」，发布复盘让每个版本都留下经验，版本节奏让大版本、小版本、热修复各归其位。

```text
更新迭代流程的核心要点：
1. 需求管理 —— 需求池 -> 评估 -> 排期，每个需求有明确价值
2. 版本计划 —— 迭代周期固定，功能按优先级进版本
3. AB 实验 —— 小流量对照实验，用数据验证产品假设
4. 发布复盘 —— 发布后对比数据，总结经验与问题
5. 版本节奏 —— 大版本/小版本/热修复三种节奏各司其职
6. 数据闭环 —— 迭代 -> 上线 -> 数据 -> 下一个迭代
```

## 版本迭代与需求管理

需求管理是迭代流程的入口。没有需求管理的团队，开发资源被各种「紧急需求」撕扯，版本质量持续下滑。需求管理的核心是一张「需求池」表：所有需求进池子，定期评估、排优先级、进版本。

```text
需求池管理：
1. 需求来源 —— 用户反馈、客服工单、数据分析、竞品观察、老板想法
2. 需求记录 —— 每个需求记录：描述、价值、成本、来源、状态
3. 价值评估 —— 影响多少用户、解决多大痛点、对核心指标贡献
4. 成本评估 —— 开发量、测试量、依赖（后端/设计/运营）
5. 优先级排序 —— 价值/成本比 + 战略方向 + 时效性综合排序
6. 状态流转 —— 待评估 -> 已排期 -> 开发中 -> 已上线 -> 已验证
```

需求评估要回答三个问题：解决什么问题（问题定义）、影响多大（用户规模与频次）、怎么验证（上线后看什么指标）。回答不了这三个问题的需求，不建议进版本。需求进入版本前必须完成：产品方案（页面与交互）、接口约定（后端联调）、验收标准（测试用例基础）。

需求池可以用看板工具（Trello、飞书、GitHub Projects）管理，也可以用最朴素的表格。关键是「单一事实来源」：需求状态只有一个权威视图，避免口头需求满天飞。下面的脚本演示如何从需求池数据生成版本需求清单：

```javascript
// gen-release-plan.js —— 从需求池生成版本计划
// 用法: node gen-release-plan.js backlog.json 1.4.0
const fs = require('fs');

const [file, version] = process.argv.slice(2);
if (!file || !version) {
  console.error('用法: node gen-release-plan.js backlog.json <版本号>');
  process.exit(1);
}

// backlog.json: [{ "id":"REQ-101","title":"会员积分体系","value":9,"cost":3,"status":"待评估" }]
const backlog = JSON.parse(fs.readFileSync(file, 'utf8'));
const candidates = backlog.filter((r) => r.status === '待评估');

// 简单评分：价值/成本 比排序，取前 N 个
candidates.sort((a, b) => (b.value / b.cost) - (a.value / a.cost));

const plan = candidates.slice(0, 5);
console.log(`===== 版本 ${version} 需求清单 =====`);
plan.forEach((r, i) => {
  console.log(`${i + 1}. ${r.id} ${r.title}（价值 ${r.value} / 成本 ${r.cost}，性价比 ${(r.value / r.cost).toFixed(1)}）`);
});
console.log(`\n预估工作量: ${plan.reduce((s, r) => s + r.cost, 0)} 人日`);
console.log('确认后请将对应需求状态更新为「已排期」');
```

```text
需求管理要点：
1. 单一事实来源 —— 需求池状态只有一处维护，杜绝口头需求
2. 三问评估 —— 解决什么问题 / 影响多大 / 怎么验证
3. 性价比排序 —— 价值/成本比是排期的基础，不是谁嗓门大谁先做
4. 依赖前置 —— 后端接口、设计稿在排期时确认，避免开发中卡壳
5. 需求冻结 —— 版本开发中禁止新增需求，新需求进下一版
6. 上线即验证 —— 每个需求带着验证指标上线，做完有交代
```

## 版本计划与迭代节奏

版本计划回答「这个版本做什么、什么时候发」。计划的前提是固定的迭代节奏：团队按固定的周期（例如两周一个迭代）滚动排期，而不是「做完就发、想发就发」。固定节奏让审核、测试、发布、复盘形成稳定节拍，也让运营和市场可以提前规划。

```text
迭代节奏示例（双周迭代）：
1. 第 1 周周初 —— 需求评审：从需求池选下个版本需求
2. 第 1 周 —— 开发 + 联调，第 1 周周末完成提测
3. 第 2 周周初 —— 测试 + 修复回归，提审
4. 第 2 周周末 —— 审核通过，发布（分阶段灰度）
5. 发布后一周 —— 数据观察 + 发布复盘
6. 周而复始 —— 复盘结论进入下一个迭代的需求评估
```

版本计划的内容：版本号、目标（本版本要达成什么业务指标）、需求清单（来自需求池）、里程碑（开发完成、提测、提审、发布）、风险与依赖（后端、设计、资质）。计划用脚本生成后，发布到团队共享文档，作为协作的基准。

迭代节奏容易犯的错是「为了赶节奏砍测试」：提审前测试不充分，审核被拒或线上事故，反而拖慢整体节奏。节奏是固定的，质量门槛也是固定的，两者冲突时砍范围而不是砍质量——把做不完的需求移到下一版，而不是压缩测试时间。

```text
版本计划要点：
1. 固定节拍 —— 双周或月度迭代，节奏固定可预期
2. 目标先行 —— 每个版本写清业务目标，不只是一堆功能
3. 里程碑清晰 —— 开发完成 / 提测 / 提审 / 发布四个节点
4. 砍范围不砍质量 —— 做不完移下一版，测试时间不能压缩
5. 计划要留缓冲 —— 审核 1-7 天不可控，提审时间点提前留余量
6. 计划即承诺 —— 版本计划发布后是团队的承诺，变更走评审
```

## AB 实验

AB 实验是数据驱动决策的核心工具：把用户随机分成两组，一组看新版（实验组），一组看旧版（对照组），通过指标对比判断新方案是否更优。小程序没有官方 AB 平台，通常自建或使用第三方（GrowingIO、神策等），核心逻辑是「稳定分流 + 指标埋点 + 显著性评估」。

```text
AB 实验流程：
1. 提出假设 —— 例如「新版首页把搜索框上移能提升搜索使用率」
2. 设计实验 —— 确定指标（主指标 + 辅助指标）、流量比例、时长
3. 稳定分流 —— 按用户 ID 哈希分桶，同一用户固定实验组
4. 埋点上报 —— 两组用户的行为数据分别记录
5. 跑够样本 —— 按预估效果计算最小样本量，跑够再评估
6. 显著性检验 —— 指标差异显著才下结论，否则视为无差异
```

稳定分流是 AB 实验的地基：同一用户每次进入都必须命中同一分组，否则用户「横跳」会污染数据。实现上多用「哈希分桶」：对 user_id 做哈希取模，映射到 0-99 的桶，实验组桶 < 比例阈值。下面是一个可直接运行的稳定分流与效果评估脚本：

```javascript
// ab-util.js —— AB 实验分流与效果评估
// 用法: node ab-util.js 或 node ab-util.js evaluate result.json
const crypto = require('crypto');

// 稳定分流：同一 userId + experimentId 永远命中同一分组
function assign(userId, experimentId, grayRatio) {
  const hash = crypto.createHash('md5')
    .update(`${experimentId}:${userId}`)
    .digest('hex');
  const bucket = parseInt(hash.slice(0, 8), 16) % 100; // 0-99
  return bucket < grayRatio ? 'experiment' : 'control';
}

// 效果评估：计算两组转化率与提升幅度
function evaluate(results) {
  // results: { experiment: { n: 4800, convert: 552 }, control: { n: 4720, convert: 488 } }
  const expRate = results.experiment.convert / results.experiment.n;
  const ctlRate = results.control.convert / results.control.n;
  const lift = ((expRate - ctlRate) / ctlRate * 100).toFixed(2);
  console.log(`实验组转化率: ${(expRate * 100).toFixed(2)}% (n=${results.experiment.n})`);
  console.log(`对照组转化率: ${(ctlRate * 100).toFixed(2)}% (n=${results.control.n})`);
  console.log(`相对提升: ${lift}%`);
  // 简单显著性判断：样本量足够且提升超过 1% 视为有效
  const enough = results.experiment.n >= 3000 && results.control.n >= 3000;
  console.log(Number(lift) > 1 && enough ? '结论: 实验组显著更优，可全量' : '结论: 差异不显著或样本不足，暂不下结论');
}

// 自测分流均匀性
function selfTest() {
  let exp = 0;
  const TOTAL = 10000;
  for (let id = 1; id <= TOTAL; id++) {
    if (assign(id, 'exp_home_search', 20) === 'experiment') exp++;
  }
  console.log(`分流自测: 20% 灰度，10000 用户实际命中 ${(exp / TOTAL * 100).toFixed(2)}%`);
}

const mode = process.argv[2];
if (mode === 'evaluate') {
  const file = process.argv[3];
  const results = JSON.parse(require('fs').readFileSync(file, 'utf8'));
  evaluate(results);
} else {
  selfTest();
}
```

实验评估要关注显著性：样本量不足时，观察到的差异可能是随机波动。经验法则：每组至少几千样本，核心指标差异超过 1 个百分点再考虑下结论；严谨团队用卡方检验或 t 检验。实验时长建议覆盖一个完整业务周期（至少一个周末），避免周中/周末流量结构差异干扰结论。

```text
AB 实验要点：
1. 假设先行 —— 没有明确假设与指标的实验是浪费流量
2. 稳定分流 —— 哈希分桶，同用户固定分组，禁止横跳
3. 样本充足 —— 每组几千样本起步，跑够再评估
4. 多指标 —— 主指标 + 辅助指标（防副作用，如转化升但投诉增）
5. 单次单实验 —— 同页面同流程不要并行多个实验，互相污染
6. 结论归档 —— 实验结论（含失败的）归档，防止重复实验
```

## 发布复盘

发布复盘是迭代闭环的最后一环：版本发布并观察一段时间后，团队坐下来回顾「目标达成没有、过程有什么问题、下次怎么改进」。复盘不是追责会，是流程改进会——产出物是改进动作，不是批评名单。

```text
发布复盘内容：
1. 目标对比 —— 版本目标指标 vs 实际数据（留存、转化、错误率）
2. 数据复盘 —— 灰度数据、版本分布、性能指标、异常事件
3. 过程复盘 —— 排期是否准确、测试是否充分、审核是否顺利
4. 问题清单 —— 线上问题、被拒原因、返工项逐条过
5. 改进动作 —— 每条问题落到具体改进项与负责人
6. 经验沉淀 —— 有效做法进流程文档，形成团队资产
```

数据对比是复盘的基础，口径要与发布前基线一致。下面的脚本对比发布前后的核心指标，输出变化幅度，作为复盘的输入：

```javascript
// release-review.js —— 发布前后数据对比
// 用法: node release-review.js before.json after.json
const fs = require('fs');

const [beforeFile, afterFile] = process.argv.slice(2);
if (!beforeFile || !afterFile) {
  console.error('用法: node release-review.js before.json after.json');
  process.exit(1);
}

// 两个 JSON 结构一致: { "uv": 12000, "retention": 24.5, "errorRate": 0.5, "paySuccessRate": 99.2 }
const before = JSON.parse(fs.readFileSync(beforeFile, 'utf8'));
const after = JSON.parse(fs.readFileSync(afterFile, 'utf8'));

const METRICS = [
  ['日访问用户', 'uv', '%'],
  ['次日留存率', 'retention', 'pp'],
  ['错误率', 'errorRate', '%'],
  ['支付成功率', 'paySuccessRate', '%']
];

console.log('===== 发布前后数据对比 =====');
METRICS.forEach(([label, key, unit]) => {
  if (before[key] === undefined || after[key] === undefined) return;
  let delta;
  if (unit === 'pp') {
    delta = (after[key] - before[key]).toFixed(2) + ' 个百分点';
  } else {
    delta = ((after[key] - before[key]) / before[key] * 100).toFixed(2) + '%';
  }
  const trend = after[key] > before[key] ? '↑' : after[key] < before[key] ? '↓' : '=';
  console.log(`${label.padEnd(8)} ${before[key]} -> ${after[key]}  (${delta}) ${trend}`);
});
console.log('\n复盘要点：指标变化是否达到版本目标？异常变化能否解释？');
```

```text
发布复盘要点：
1. 目标驱动 —— 先对版本目标，再对过程，数据说话
2. 基线一致 —— 对比口径与发布前一致，避免口径打架
3. 复盘及时 —— 发布后 3-5 天内完成，数据热乎、记忆清晰
4. 改进落地 —— 每条改进动作有负责人有截止时间
5. 不追责 —— 复盘针对流程与机制，不对人
6. 经验进库 —— 复盘结论沉淀到流程文档与需求池
```

## 版本节奏与热修复

版本节奏指不同类型版本的发布频率与规则。小程序迭代建议分三种节奏：大版本（新功能集合，走完整流程）、小版本（少量功能与优化，常规流程）、热修复（线上事故，加急审核快速上线）。三种节奏共用同一套提审-发布管线，区别在于频率、范围与审核通道。

```text
三种版本节奏：
1. 大版本（2.0.0）—— 重大改版/新业务线，周期 1-2 个月，全量回归测试
2. 小版本（1.4.0/1.4.1）—— 常规迭代，双周一个，走完整灰度
3. 热修复（1.3.1）—— 线上事故修复，修订号递增，加急审核
4. 规则 —— 大版本不得夹带小版本未验证功能；热修复只改问题代码
5. 节奏管理 —— 大版本错开排期，避免与节假日/大促冲突
6. 灰度纪律 —— 小版本默认灰度，热修复视影响面决定灰度比例
```

热修复是节奏管理的重点：线上事故发生时，目标是「最小改动、最快上线」。热修复分支只包含问题修复，不夹带任何新功能——夹带新功能会扩大回归范围，反而拖慢上线。热修复流程用 Git 分支管理：

```bash
#!/bin/bash
# hotfix.sh —— 热修复分支流程
# 用法: ./hotfix.sh 1.3.1 "修复支付回调超时"
set -e

VERSION=$1
DESC=$2
if [ -z "$VERSION" ] || [ -z "$DESC" ]; then
  echo "用法: ./hotfix.sh <修复版本号> <修复说明>"
  exit 1
fi

# 1. 从当前线上版本分支切热修复分支（示例从 master 切）
git checkout master
git pull origin master
git checkout -b hotfix/$VERSION

# 2. 修复代码 -> 提交（人工完成）
echo "请在 hotfix/$VERSION 分支完成修复并提交，然后继续执行:"
echo "  git add . && git commit -m \"[$VERSION] $DESC\""
echo "  git push origin hotfix/$VERSION"

# 3. 合并回主干并打 tag（修复验证通过后执行）
# git checkout master && git merge hotfix/$VERSION --no-ff
# git tag -a $VERSION -m "$DESC" && git push origin $VERSION
echo "修复完成后打 tag: $VERSION"
```

```text
版本节奏要点：
1. 节奏分离 —— 大版本/小版本/热修复走不同通道，互不干扰
2. 热修复最小化 —— 只改问题代码，严禁夹带新功能
3. 加急额度 —— 热修复优先用加急审核，额度留给事故
4. 分支规范 —— 热修复分支从线上版本切出，合并回主干
5. 回归最小集 —— 热修复验证问题场景 + 相邻功能冒烟
6. 事故分级 —— 影响支付/登录/核心流程的才是热修复，普通问题走常规迭代
```

## 应用场景实战

### 场景一：双周迭代完整跑一遍（计划 -> 开发 -> 提审 -> 灰度 -> 复盘）

以 1.4.0 版本为例，走完整迭代闭环：

```text
步骤：
1. 迭代启动：从需求池选 5 个需求，运行 gen-release-plan.js 生成计划
2. 计划评审：确认版本目标「提升下单转化率 2 个百分点」与里程碑
3. 开发两周：第 1 周完成开发与联调，第 2 周周初提测
4. 测试与修复：全量回归 + 真机验证，周五提审
5. 审核通过：分阶段发布 10% -> 50% -> 100%（见 16.2）
6. 数据观察：运行 release-review.js 对比发布前后转化率
7. 发布复盘：目标达成与否、过程问题、改进动作
8. 经验归档：复盘结论进入需求池与流程文档
```

```text
迭代运行检查点：
1. 计划在迭代第 1 天发布，全员对齐
2. 开发期间需求冻结，新增需求进需求池
3. 提测质量门槛：主流程用例全过才提审
4. 提审时间倒排：审核 1-7 天，发布日反推提审日
5. 灰度与监控联动：放量看错误率与转化（16.2 + 16.3）
6. 复盘在发布后 5 天内完成，改进动作有人认领
```

### 场景二：用 AB 实验决策「新版首页是否上线」

产品提了个假设：首页改版能提升次日留存。用 AB 实验验证：

```text
步骤：
1. 假设与指标：主指标次日留存，辅助指标首屏耗时、跳出率
2. 分流设计：experimentId = exp_home_v2，20% 用户进实验组
3. 埋点：两组用户行为都走统一埋点（16.3 tracker.js）
4. 跑两周：覆盖两个完整周末，样本量每组 5000+
5. 评估：运行 node ab-util.js evaluate result.json
6. 结论：实验组留存 26.1% vs 对照组 24.8%，提升 1.3 个百分点
7. 决策：差异显著且无副作用（首屏耗时未劣化），新版全量
8. 归档：实验结论记录「假设、数据、结论」，避免重复实验
```

result.json 示例：

```json
{
  "experiment": { "n": 5230, "convert": 1365 },
  "control": { "n": 5180, "convert": 1285 }
}
```

```text
AB 实验检查点：
1. 实验前写清假设与主指标，不写好不开实验
2. 分流稳定：同一用户固定分组，验证分流均匀性
3. 样本量：每组 5000 起步，跑满两周再评估
4. 防副作用：辅助指标检查新方案有没有引入新问题
5. 失败也归档：实验失败的结论同样有价值
6. 全量后回归：实验结论在全量后复验一次
```

## 最佳实践与踩坑记录

### 最佳实践

1. 固定迭代节拍（双周或月度），需求池、版本计划、发布复盘形成固定仪式，节奏稳定才能保证质量稳定
2. 需求三问过滤：每个需求回答「解决什么问题 / 影响多大 / 怎么验证」，答不上来的不进版本
3. 版本开发中需求冻结，新需求一律进下一版，杜绝「加一个小的」式的范围蔓延
4. AB 实验假设先行、稳定分流、跑够样本，结论用数据说话并归档（失败实验同样归档）
5. 发布复盘在发布后 3-5 天内完成，产出可落地的改进动作（负责人 + 截止时间），不做追责会
6. 热修复最小化：只改问题代码、走加急审核、验证最小回归集，严禁夹带新功能
7. 数据闭环贯穿始终：版本计划写目标指标，灰度观察指标，复盘对比指标，下一个迭代从复盘结论开始
8. 审核时间不可控（1-7 天），提审日按发布日倒排并留缓冲，把审核等待变成团队资源规划的确定性输入

### 踩坑记录

```text
坑 1：AB 实验分流不稳定，用户反复横跳
结论：同一天用户既看到新版又看到旧版，数据完全不可信。
原因：分流用随机数而非稳定哈希，或 userId 不稳定（未登录用户每次不同）。
解法：用 userId 哈希分桶（ab-util.js）；未登录用户用稳定设备 ID 或排除在实验外。

坑 2：样本量不足就下结论
结论：跑了 3 天 500 个样本就宣布新版更优，全量后效果打脸。
原因：样本量小，观察到的差异是随机波动。
解法：预估最小样本量，每组 5000 起步；覆盖完整业务周期再评估。

坑 3：多个实验同时跑在同一个页面，互相污染
结论：首页同时跑了两个实验，结论互相矛盾，无法归因。
原因：同页面同流程并行实验，用户分组交叉。
解法：同一页面同一时间只跑一个实验；实验排期管理，串行进行。

坑 4：版本开发中不断塞新需求，版本延期
结论：双周迭代拖成一个月，测试时间被挤压，提审质量下降。
原因：需求冻结规则没执行，开发中「加一个小的」不断发生。
解法：版本计划发布即冻结；新需求进需求池下一版；塞需求需走变更评审。

坑 5：热修复夹带新功能，回归范围失控
结论：线上事故修复版本带了一个新功能，测试不充分，上线又出新问题。
原因：热修复分支从开发分支切出，把未完成功能一起带上。
解法：热修复分支从线上版本切出，只合并修复提交；diff 审查确保最小改动。

坑 6：复盘只看数据不看问题，改进动作落空
结论：复盘会开完，改进动作没人跟进，同类问题下个版本再犯。
原因：复盘没有产出可执行动作，或动作没有负责人与时间点。
解法：每条问题对应一个改进动作 + 负责人 + 截止时间；下次复盘先检查上期动作。

坑 7：发布目标没有写进版本计划，无法评估成败
结论：版本上线了，但说不清「这个版本成不成功」。
原因：版本计划只列功能，没有目标指标。
解法：每个版本计划写清目标指标与目标值；复盘先对目标。

坑 8：审核等待期资源闲置，节奏被打乱
结论：提审后等 5 天，团队没事干，审核通过后又手忙脚乱发布。
原因：没有把审核期当作计划的一部分。
解法：提审后安排下个迭代的需求评估与复盘准备；提审日倒排并留缓冲。
```
