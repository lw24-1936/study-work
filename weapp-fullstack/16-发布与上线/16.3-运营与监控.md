## 概述

发布上线只是开始，运营与监控决定产品能走多远。小程序上线后有两件事必须持续做：一是看数据（用户从哪里来、在页面做什么、为什么流失），二是盯质量（页面报错、接口失败、性能劣化）。数据是运营决策的依据，监控是线上质量的保障，两者共同构成发布后的「仪表盘」。

微信官方提供的基础设施包括：后台数据助手（访问分析、用户画像、漏斗分析）、运维中心（接口监控、错误日志）、小程序助手（审核与违规消息提醒）。这些免费能力覆盖面广但深度有限，团队通常还要自建或接入第三方监控（Sentry、自研错误上报、企业微信/钉钉告警机器人），形成「官方能力 + 自建体系」的组合。

```text
运营与监控的核心要点：
1. 数据统计 —— 后台数据助手：访问分析、用户画像、漏斗分析
2. 错误监控 —— wx.onError 全局捕获，错误上报到自建后端
3. 告警 —— 错误率、接口失败率越线触发机器人通知
4. 小程序助手 —— 订阅审核结果、违规提醒等官方消息
5. 运营分析 —— 留存、转化、来源渠道，驱动迭代决策
6. 数据闭环 —— 监控发现问题 -> 定位 -> 修复 -> 复盘 -> 回归
```

## 数据统计与数据分析

微信后台「统计」模块是小程序数据的第一来源，无需任何埋点即可获得基础数据，核心功能包括：

```text
后台统计能力：
1. 访问分析 —— 访问人数（UV）、访问次数、人均停留时长、访问来源
2. 用户画像 —— 年龄、性别、地域、设备、网络环境分布
3. 漏斗分析 —— 自定义转化漏斗（如 首页 -> 商品 -> 下单 -> 支付）
4. 自定义分析 —— 通过 wx.reportAnalytics 上报的自定义事件
5. 实时数据 —— 当前时刻的访问量、分享量
6. 性能监控 —— 启动耗时、页面渲染耗时、接口调用情况
```

基础数据零成本获得，但业务指标（下单转化、会员注册、优惠券核销）必须靠自定义埋点。自定义分析的流程是：先在后台「统计 - 自定义分析」创建事件并拿到事件 ID，然后在小程序代码中调用 `wx.reportAnalytics(eventName, data)` 上报。下面是一个轻量埋点工具：

```javascript
// utils/tracker.js —— 自定义事件埋点工具
// 用法: const tracker = require('../../utils/tracker'); tracker.event('view_product', {id: 1001})
const TRACK_EVENTS = {
  view_product: 'view_product',   // 查看商品详情
  add_cart: 'add_cart',           // 加入购物车
  create_order: 'create_order',   // 提交订单
  pay_success: 'pay_success'      // 支付成功
};

function report(eventName, data) {
  if (!wx.reportAnalytics) return; // 基础库不支持时静默降级
  wx.reportAnalytics(eventName, Object.assign({}, data || {}));
}

function track(eventName, data) {
  // 业务埋点：统一入口，方便后续加采样、加字段
  report(eventName, data);
  // 同时输出到控制台，方便开发期联调观察
  if (wx.getSystemInfoSync().platform === 'devtools') {
    console.log('[tracker]', eventName, data);
  }
}

module.exports = {
  track,
  TRACK_EVENTS
};
```

页面访问埋点可以直接挂在页面生命周期上：

```javascript
// pages/product/product.js —— 页面访问与行为埋点示例
const tracker = require('../../utils/tracker');

Page({
  data: { productId: 1001 },

  onLoad(options) {
    this.setData({ productId: Number(options.id) });
  },

  onShow() {
    // 页面曝光埋点
    tracker.track('page_view', {
      page: 'product',
      productId: this.data.productId
    });
  },

  onAddCart() {
    tracker.track('add_cart', { productId: this.data.productId });
    wx.showToast({ title: '已加入购物车', icon: 'success' });
  },

  onBuyNow() {
    tracker.track('create_order', { productId: this.data.productId });
    // 下单逻辑...
  }
});
```

```text
数据统计要点：
1. 分层使用 —— 官方基础数据看大盘，自定义埋点看业务
2. 事件规范 —— 事件名统一命名（动词_名词），字段格式固定
3. 埋点先行 —— 功能开发时就规划埋点，上线后补埋点会丢数据
4. 口径统一 —— 转化率、留存率等指标口径团队内书面约定
5. 实时与日报 —— 实时数据应急用，日报用于周度运营分析
6. 隐私合规 —— 埋点数据不得包含手机号等个人信息，需匿名化
```

## 错误监控与上报

小程序运行在用户手机上，开发者无法直接看到报错，必须靠错误上报把线上异常「搬」回自己的监控系统。微信后台「运维中心」提供基础的错误日志查询，但实时性、检索能力有限，主流做法是自建错误上报链路：全局捕获 -> 上报后端 -> 汇总分析。

```text
错误捕获链路：
1. App.onError —— 捕获全局 JS 运行时错误
2. wx.onUnhandledRejection —— 捕获未处理的 Promise 拒绝
3. 页面级兜底 —— Page.onError 捕获页面渲染错误（基础库支持时）
4. 接口错误 —— wx.request fail 回调与业务错误码统一上报
5. 上报后端 —— 错误信息 POST 到自建 /api/monitor/error
6. 汇总分析 —— 按错误堆栈去重、按版本/机型/基础库聚合

```

小程序端全局错误捕获与上报实现：

```javascript
// app.js —— 全局错误捕获与上报
const ERROR_REPORT_URL = 'https://api.example.com/api/monitor/error';

function reportError(errInfo) {
  if (!errInfo) return;
  const sys = wx.getSystemInfoSync();
  const info = wx.getAccountInfoSync();
  // 组装错误上下文：版本、机型、基础库、页面栈
  const payload = {
    type: errInfo.type || 'js_error',
    message: errInfo.message || '',
    stack: errInfo.stack || '',
    page: getCurrentPages().length
      ? getCurrentPages()[getCurrentPages().length - 1].route
      : '',
    version: info.miniProgram.version,
    libVersion: info.miniProgram.libVersion,
    model: sys.model,
    system: sys.system,
    platform: sys.platform,
    ts: Date.now()
  };
  // 上报失败静默处理，避免错误上报本身引发新错误
  wx.request({
    url: ERROR_REPORT_URL,
    method: 'POST',
    data: payload,
    fail() { /* 静默 */ }
  });
}

App({
  onLaunch() {
    // 捕获未处理的 Promise 拒绝（基础库 2.10.0+）
    if (wx.onUnhandledRejection) {
      wx.onUnhandledRejection((res) => {
        reportError({ type: 'unhandled_rejection', message: res.reason, stack: res.reason && res.reason.stack });
      });
    }
  },

  onError(err) {
    // 全局 JS 错误
    reportError({ type: 'js_error', message: err && err.message, stack: err && err.stack });
  }
});
```

服务端接收错误上报（SpringBoot 控制器）：

```java
// ErrorReportController.java —— 接收小程序端错误上报
@RestController
@RequestMapping("/api/monitor")
public class ErrorReportController {

    @PostMapping("/error")
    public Result<Void> report(@RequestBody ErrorReportDTO dto) {
        // 1. 采样：错误量过大时只保留部分，防止存储被打爆
        // 2. 入库：错误明细写入日志/ES，按 version + stack 指纹聚合
        // 3. 告警：错误率越线触发告警（见告警体系章节）
        errorService.save(dto);
        return Result.success();
    }
}
```

```text
错误监控要点：
1. 三层捕获 —— onError + onUnhandledRejection + 接口错误码
2. 上下文完整 —— 版本、机型、基础库、页面栈是定位三要素
3. 上报去重 —— 同一堆栈聚合计数，按影响用户数排序处理
4. 上报降级 —— 上报请求本身失败要静默，不能引发连环错误
5. 隐私红线 —— 错误上报剔除用户手机号、登录凭证等敏感信息
6. 工具配合 —— 开发者工具「调试器 - Sources」与真机调试排查
```

## 告警体系

错误监控解决「看到问题」，告警解决「及时知道有问题」。告警体系的目标是在用户大规模受影响之前，把问题通知到责任人。告警链路由三部分组成：指标采集（错误率、接口失败率、性能指标）-> 阈值判断（越线触发）-> 通知渠道（企业微信/钉钉/飞书机器人、短信）。

```text
告警设计原则：
1. 指标选择 —— 错误率、接口失败率、核心接口耗时、支付成功率
2. 阈值设置 —— 环比基线 + 绝对值双重判断，避免误报
3. 分级通知 —— 严重（短信+电话）> 高（机器人@人）> 普通（群里记录）
4. 静默期 —— 同一问题 30 分钟内不重复告警，防止告警轰炸
5. 告警升级 —— 15 分钟无人响应自动升级到主管
6. 告警演练 —— 每月演练一次告警链路，确保通知真能到达
```

企业微信/钉钉/飞书机器人都提供 HTTP Webhook 接口，收到告警内容后推送到群聊。下面是告警发送脚本，可被定时任务或监控平台调用：

```javascript
// send-alert.js —— 发送告警到企业微信/钉钉/飞书机器人
// 用法: node send-alert.js <webhook_url> <标题> <内容> [级别]
const https = require('https');

const [webhook, title, content, level = '普通'] = process.argv.slice(2);
if (!webhook || !title || !content) {
  console.error('用法: node send-alert.js <webhook> <标题> <内容> [级别]');
  process.exit(1);
}

const url = new URL(webhook);
const body = JSON.stringify({
  msgtype: 'markdown',
  markdown: {
    content: `## [${level}] ${title}\n> ${content}\n> 时间: ${new Date().toLocaleString('zh-CN')}`
  }
});

const req = https.request({
  hostname: url.hostname,
  path: url.pathname + url.search,
  method: 'POST',
  headers: { 'Content-Type': 'application/json' }
}, (res) => {
  let data = '';
  res.on('data', (c) => (data += c));
  res.on('end', () => {
    console.log('告警已发送:', data.slice(0, 200));
  });
});
req.on('error', (e) => console.error('发送失败:', e.message));
req.write(body);
req.end();
```

结合错误上报数据做告警判断：定时任务（或监控平台）统计最近 5 分钟的错误率，与基线比较，越线则调用 send-alert.js。告警消息要包含定位信息：版本号、错误类型、影响用户数、疑似页面，让接收人不用登录后台就能判断优先级。

```text
告警要点：
1. 指标越线才告警 —— 不要「有错误就告警」，按错误率/失败率判断
2. 环比基线 —— 与发布前基线比较，绝对值阈值容易误报漏报
3. 消息自含定位 —— 版本、影响面、页面路径写进告警正文
4. 分级与升级 —— 严重告警必须有升级机制，不能只发群消息
5. 防轰炸 —— 静默期机制，同问题不重复刷屏
6. 链路演练 —— 告警脚本定期测试，Webhook 失效及时发现
```

## 小程序助手

「小程序助手」是微信官方提供的运营通知渠道，以小程序形式存在，同时支持订阅消息推送。管理员在小程序助手中订阅相关通知后，微信会把审核结果、违规提醒、能力变更等关键消息推送到管理员微信。

```text
小程序助手通知类型：
1. 审核结果 —— 提审通过 / 不通过原因即时推送
2. 违规提醒 —— 内容违规、类目违规、用户投诉处理通知
3. 能力变更 —— 接口下线、能力调整、规则更新公告
4. 运营周报 —— 每周访问数据、用户增长汇总
5. 新消息提醒 —— 用户反馈、客服消息
6. 安全提醒 —— 账号安全、资质到期、支付风险提示
```

订阅配置流程：管理员在小程序后台「设置 - 成员管理」添加为管理员/运营者，微信扫码绑定小程序助手，然后在助手内打开对应通知的订阅开关。注意：通知订阅是以个人微信为单位的，离职人员要同步移除后台成员权限，否则关键通知可能发到已离职的人那里。

小程序助手之外，微信还提供「订阅消息」能力（见第 11 章）用于业务触达，两者定位不同：小程序助手是官方运营通知，订阅消息是业务消息（订单、物流、活动）。运营团队应把两者结合：官方通知管合规与审核，订阅消息管用户触达。

```text
小程序助手要点：
1. 必开通知 —— 审核结果与违规提醒必须订阅，错过即风险
2. 权限同步 —— 成员离职及时移除后台权限，通知不落空
3. 与订阅消息区分 —— 官方通知 vs 业务消息，职责不同
4. 周报利用 —— 运营周报作为周度数据 Review 的输入
5. 安全提醒重视 —— 资质到期、支付风险类通知优先级最高
6. 多管理员 —— 核心通知至少两个管理员订阅，避免单点
```

## 运营数据分析

运营数据分析是把原始数据转化为决策的过程：用留存、转化、来源渠道等指标评估产品健康度，决定下一个迭代做什么。小程序特有的运营指标包括：

```text
核心运营指标：
1. 新增用户 —— 新访问用户数，来源渠道（搜索/扫码/分享/公众号）
2. 次日留存 —— 新增用户次日再次访问的比例，产品粘性第一指标
3. 转化漏斗 —— 访问 -> 注册 -> 下单 -> 支付各环节转化率
4. 分享率 —— 分享次数/访问次数，社交裂变能力
5. 复访率 —— 老用户回访频率与间隔
6. 客单价与 GMV —— 交易类小程序的商业核心指标
```

留存率与转化率的计算建议脚本化，保证口径一致。下面脚本从导出数据计算次日留存与漏斗转化：

```javascript
// analyze-metrics.js —— 留存与转化分析
// 用法: node analyze-metrics.js data.json
const fs = require('fs');

const file = process.argv[2];
if (!file) {
  console.error('用法: node analyze-metrics.js data.json');
  process.exit(1);
}

// data.json 结构:
// {
//   "dailyUsers": { "2026-08-18": 12000, "2026-08-19": 12500 },
//   "newUsers": { "2026-08-18": 3200 },
//   "nextDayReturn": { "2026-08-18": 860 },   // 8-18 新增用户中 8-19 回访人数
//   "funnel": { "visit": 12000, "register": 4500, "order": 2100, "pay": 1680 }
// }
const d = JSON.parse(fs.readFileSync(file, 'utf8'));

console.log('===== 留存分析 =====');
const day = Object.keys(d.newUsers)[0];
const retention = (d.nextDayReturn[day] / d.newUsers[day] * 100).toFixed(2);
console.log(`${day} 新增用户: ${d.newUsers[day]}`);
console.log(`次日留存率: ${retention}%`);

console.log('\n===== 转化漏斗 =====');
const f = d.funnel;
const steps = [
  ['访问', f.visit, null],
  ['注册', f.register, f.visit],
  ['下单', f.order, f.register],
  ['支付', f.pay, f.order]
];
steps.forEach(([name, value, prev]) => {
  const rate = prev ? (value / prev * 100).toFixed(2) + '%' : '-';
  console.log(`${name.padEnd(4)} ${String(value).padStart(7)}  转化率 ${rate}`);
});
console.log(`\n总转化率（支付/访问）: ${(f.pay / f.visit * 100).toFixed(2)}%`);
```

```text
运营数据分析要点：
1. 留存优先 —— 次日留存是产品健康度的第一信号，低于 20% 要警惕
2. 漏斗定位 —— 转化率骤降的环节就是优化重点
3. 来源归因 —— 用户来源渠道对比，投放决策看数据不看感觉
4. 周度复盘 —— 固定每周看一次数据周报，形成习惯
5. 指标口径 —— 转化率、留存率口径书面固定，全员一致
6. 数据驱动迭代 —— 每个迭代的目标指标写进版本计划（见 16.4）
```

## 应用场景实战

### 场景一：给小程序接入完整的错误监控与告警

从零搭建「捕获 -> 上报 -> 分析 -> 告警」链路：

```text
步骤：
1. 小程序端：app.js 增加 onError 与 onUnhandledRejection 全局捕获（见错误监控章节）
2. 服务端：SpringBoot 提供 /api/monitor/error 接口，错误入库并按堆栈指纹聚合
3. 监控任务：每 5 分钟统计最近 30 分钟错误率，与基线比较
4. 越线触发：调用 send-alert.js 推送企业微信群
5. 值班人收到告警：根据版本号与页面路径定位，决定回滚或热修
6. 修复后验证：错误率回落基线，告警自动解除
7. 每月演练：故意注入一个错误，验证告警链路全通
```

定时统计脚本（可部署为 cron 任务）：

```javascript
// check-error-rate.js —— 统计错误率并触发告警
// 用法: node check-error-rate.js <webhook> <基线错误率%>
const https = require('https');
const { execSync } = require('child_process');

const [webhook, baselineStr] = process.argv.slice(2);
const baseline = Number(baselineStr || 0.5); // 默认基线 0.5%

// 从错误上报服务查询最近 30 分钟错误率（此处用模拟数据演示）
// 实际实现: 查询错误库 count(最近30min) / 访问量(最近30min)
const errorRate = 1.2; // 模拟值
const visitCount = 8600;

if (errorRate > baseline * 2) {
  const msg = `小程序错误率异常：${errorRate}%（基线 ${baseline}%），30 分钟访问 ${visitCount} 次`;
  execSync(`node send-alert.js "${webhook}" "小程序错误率告警" "${msg}" "严重"`);
  console.log('已触发告警');
} else {
  console.log(`错误率 ${errorRate}%，在基线范围内`);
}
```

```text
监控接入检查点：
1. 上报接口先于小程序端接入完成，避免上线即丢错误
2. 错误数据按版本聚合，灰度期按版本对比错误率
3. 告警消息包含版本号与页面路径，接收人可立即定位
4. 告警阈值先松后紧，运行一周后按真实数据收紧
5. 演练常态化，告警链路每月验证一次
6. 错误上报与数据埋点分离，埋点数据不参与告警
```

步骤：

## 最佳实践与踩坑记录

### 最佳实践

1. 监控先行：上线第一周就把错误上报与告警搭好，没有监控的发布等于裸奔
2. 官方能力 + 自建体系组合：数据助手看大盘，自建监控看细节，小程序助手管通知，三层各司其职
3. 错误上报带上完整上下文（版本、机型、基础库、页面栈、时间），缺一项都可能无法定位
4. 埋点与监控分离：埋点数据量大且不紧急，走异步批量；错误上报实时且必须可靠
5. 告警阈值用「环比基线 + 绝对值」双判断，先松后紧，运行一两周再收紧
6. 指标口径文档化：留存、转化、错误率的口径书面固定，避免运营与开发各算各的
7. 每日看错误列表、每周看数据周报、每月演练告警链路，节奏固定化
8. 敏感信息零容忍：上报数据、埋点数据一律不含手机号、身份证、登录凭证，隐私合规是底线

### 踩坑记录

```text
坑 1：只挂了 onError，异步异常全部漏掉
结论：Promise 里抛的错、异步回调的错线上看不到，错误率被严重低估。
原因：onError 只捕获同步运行时错误，未处理 Promise 拒绝不在其内。
解法：补上 wx.onUnhandledRejection 捕获；接口请求统一封装，fail 与业务错误码都上报。

坑 2：错误上报接口挂了，线上错误全部丢失
结论：监控系统本身故障，问题暴露时已错过止损窗口。
原因：上报依赖后端接口，接口宕机或超时导致上报静默失败。
解法：上报接口独立部署降级容错；上报失败本地缓存（Storage 限量）稍后重试；监控告警链路本身也要监控。

坑 3：上报数据没有去重聚合，告警被刷屏
结论：一个页面循环报错，每分钟上千条，群消息被淹没，真问题被忽略。
原因：没有按堆栈指纹聚合，也没有静默期机制。
解法：按「版本 + 错误堆栈 + 页面」聚合计数；同一指纹 30 分钟静默；告警按影响用户数排序。

坑 4：告警阈值设置过低，狼来了效应
结论：阈值 0.1% 太敏感，频繁误报，团队对告警麻木，真告警无人响应。
原因：阈值拍脑袋，没有按真实数据校准。
解法：先记录一周真实错误率分布，阈值设在基线的 2 倍或 P99；误报记录反馈调参。

坑 5：小程序助手通知没订阅，错过违规提醒
结论：小程序因违规被限制能力，运营完全不知情，用户投诉后才被发现。
原因：管理员未在小程序助手订阅通知，或订阅人已离职。
解法：至少两个管理员订阅审核结果与违规提醒；成员离职同步移除后台权限。

坑 6：埋点随意命名，指标口径混乱
结论：同一个「支付成功」有 pay_success / pay_ok / 支付成功 三种叫法，数据无法聚合。
原因：埋点没有统一规范，各开发各起名。
解法：埋点事件名与字段名文档化（见 tracker.js 的 TRACK_EVENTS）；埋点变更走 review。

坑 7：只监控小程序端，后端接口问题发现滞后
结论：后端接口超时导致页面白屏，前端错误率没明显上升，问题藏了几天。
原因：前端错误监控覆盖不到后端故障，缺少接口维度监控。
解法：后端接口监控（耗时、失败率、状态码分布）与前端联动；前端上报接口失败并附耗时。

坑 8：错误上报携带用户手机号等敏感信息
结论：审核发现或用户投诉数据泄露，小程序被处罚。
原因：为方便定位问题，把用户手机号、openid 写进了上报数据。
解法：上报数据匿名化（用户维度用加密 ID）；敏感字段在服务端脱敏；配合 14 章隐私合规要求。
```
