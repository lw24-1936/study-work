## 概述

审核通过只是「可以上线」，真正把新版本交到用户手里的是发布环节。小程序发布有两种形态：全量发布（直接推送给所有用户）与分阶段发布（按比例灰度放量），配合回滚能力形成「小流量验证 → 逐步放量 → 全量 → 异常回退」的完整发布闭环。

发布环节的核心矛盾是「上线速度」与「线上风险」：功能想尽快到达用户，但新版本可能隐藏线上才暴露的问题（机型兼容、接口压力、业务逻辑缺陷）。分阶段发布正是化解这对矛盾的机制——先用 10% 流量验证，观察数据无异常再放到 50%、100%。本章围绕发布流程、全量发布、分阶段发布、灰度策略、回滚五个知识点展开，全部基于微信后台「版本管理」的真实操作。

```text
发布与灰度的核心要点：
1. 发布入口 —— 审核通过后，在后台「审核版本」点击发布
2. 全量发布 —— 一键推送给全部用户，简单直接但风险集中
3. 分阶段发布 —— 按 10% -> 50% -> 100% 比例逐步放量
4. 灰度验证 —— 小流量观察错误率、接口耗时、核心转化数据
5. 回滚 —— 异常时回退到上一个线上版本，发布历史的唯一后悔药
6. 后端配合 —— 小程序新版本常依赖新接口，后端需兼容老版本
```

## 发布流程与发布确认

审核通过后，「审核版本」区域的版本卡片出现「发布」按钮。点击发布前，微信会弹出发布确认弹窗，展示本次发布的版本号、版本描述，并让开发者选择发布方式（全量发布或分阶段发布）。这是发布前的最后一道人工确认关卡。

```text
发布确认流程：
1. 审核版本状态变为「审核通过（可发布）」
2. 点击「发布」，弹窗展示版本号与版本描述
3. 选择发布方式：全量发布 / 分阶段发布
4. 选择分阶段发布时设置首次放量比例（如 10%）
5. 确认后版本进入「线上版本」区域，状态为「发布中」
6. 发布不可撤销：确认后立即对目标用户生效，异常只能回滚
```

发布确认是一个高风险动作，团队内部建议配套「发布前 Checklist」与发布窗口制度：不在周五下午、节假日前夕发布大版本；发布人必须是了解该版本变更的人；发布前确认后端接口已上线且兼容。下面的脚本可以把发布确认从「口头承诺」变成「系统留痕」：

```javascript
// confirm-release.js —— 发布前确认单，防呆式发布检查
// 用法: node confirm-release.js 1.3.0
const readline = require('readline');

const version = process.argv[2];
if (!version) {
  console.error('用法: node confirm-release.js <版本号>');
  process.exit(1);
}

const CHECKS = [
  '后端接口已上线，且兼容旧版本小程序',
  '数据库迁移脚本已执行并验证',
  '灰度指标基线已记录（错误率、接口耗时、核心转化率）',
  '回滚预案已确认（上一个线上版本可回退）',
  '发布负责人确认（需输入姓名）'
];

const rl = readline.createInterface({ input: process.stdin, output: process.stdout });

function ask(question) {
  return new Promise((resolve) => rl.question(question, resolve));
}

(async () => {
  console.log(`===== 版本 ${version} 发布确认单 =====`);
  for (const check of CHECKS) {
    const ans = await ask(`[确认] ${check} (y/n): `);
    if (ans.trim().toLowerCase() !== 'y') {
      console.error(`发布中止：未确认「${check}」`);
      process.exit(1);
    }
  }
  const owner = await ask('[输入] 发布负责人姓名: ');
  if (!owner.trim()) {
    console.error('发布中止：缺少负责人');
    process.exit(1);
  }
  console.log(`\n版本 ${version} 发布确认单已签署，负责人: ${owner}`);
  console.log('请前往微信后台「版本管理 - 审核版本」点击发布');
  rl.close();
})();
```

```text
发布流程要点：
1. 发布入口 —— 审核版本卡片「发布」按钮，弹窗二次确认
2. 发布方式 —— 全量 or 分阶段，在发布确认弹窗中选择
3. 发布窗口 —— 避开周五下午与节假日前夕，预留观察期
4. 发布留痕 —— 确认单记录检查项与负责人，可追溯
5. 先审后端 —— 后端接口与数据变更先行上线并验证
6. 基线先行 —— 发布前记录错误率与核心指标基线，便于对比
```

## 全量发布

全量发布指审核通过后直接点击「发布」并选择全量，新版本立即对所有用户生效。全量发布是最简单的发布方式，操作成本最低，但风险也最集中：如果新版本存在线上问题，影响面瞬间扩大到全部用户。

```text
全量发布特点：
1. 操作简单 —— 一键发布，无需灰度配置
2. 生效快 —— 用户下次启动即拉取新版本
3. 风险集中 —— 问题瞬间影响全部用户，只能靠回滚止损
4. 适用场景 —— 修复型小版本、无后端依赖的纯前端改动、紧急合规调整
5. 不适用场景 —— 大版本改版、涉及支付/核心流程变更、后端接口重构
6. 发布后观察 —— 发布后 30 分钟内紧盯错误率与核心指标
```

全量发布并不等于「用户立刻全部更新」：微信客户端会在用户启动小程序时检查版本并下载更新，因此全量发布后的版本收敛是渐进的。可以通过 `wx.getUpdateManager()` 主动提示用户重启更新，加速版本收敛：

```javascript
// 全量发布后，用 UpdateManager 主动引导用户更新到新版本
// 建议放在 app.js 的 onLaunch 中调用
function checkUpdate() {
  if (!wx.canIUse('getUpdateManager')) return; // 基础库兼容
  const updateManager = wx.getUpdateManager();

  // 新版本下载完成，提示用户重启生效
  updateManager.onUpdateReady(function () {
    wx.showModal({
      title: '更新提示',
      content: '新版本已经准备好，是否重启应用？',
      success(res) {
        if (res.confirm) {
          updateManager.applyUpdate(); // 强制重启应用加载新版本
        }
      }
    });
  });

  // 新版本下载失败，静默等待下次启动重试
  updateManager.onUpdateFailed(function () {
    console.warn('新版本下载失败，用户下次启动将自动重试');
  });
}
```

全量发布后的版本收敛率可以通过线上版本分布观察：后台「版本管理 - 线上版本」可以看到当前各版本的用户占比，收敛率异常（长时间停留在旧版本）说明客户端更新受阻，需要排查基础库兼容或下载失败问题。

```text
全量发布要点：
1. 一键发布 —— 审核通过后选择全量，对所有用户生效
2. 渐进收敛 —— 用户启动时拉取新版本，不是瞬间全覆盖
3. 主动更新 —— 用 UpdateManager 提示用户重启，加速收敛
4. 30 分钟观察 —— 发布后紧盯错误率、接口失败率、崩溃率
5. 版本分布 —— 后台可查各版本用户占比，定位收敛异常
6. 谨慎使用 —— 大版本与高风险变更优先走分阶段发布
```

## 分阶段发布

分阶段发布（灰度发布）是微信后台提供的官方放量机制：发布时选择分阶段发布，设置首次放量比例（如 10%），之后在「线上版本」区域手动调整比例（50%、100%），或中途暂停。被选中的用户是随机的，比例代表「新版本覆盖的用户比例」。

```text
分阶段发布操作路径：
1. 审核通过后点击「发布」，选择「分阶段发布」
2. 设置首次放量比例，例如 10%（或固定数量用户）
3. 发布后观察灰度用户的数据：错误率、接口耗时、核心转化
4. 数据正常 -> 调整比例到 50%，继续观察
5. 数据仍正常 -> 调整到 100%，完成全量
6. 数据异常 -> 暂停发布或直接回滚，灰度用户回退到旧版本
```

分阶段发布的比例调整与暂停都在后台「版本管理 - 线上版本」操作。暂停发布后，已覆盖的灰度用户保持新版本，未覆盖用户继续使用旧版本；暂停状态下的版本可以继续观察，也可以直接回滚。分阶段发布的本质是把「发布」拆成多个可观察、可干预的小步骤。

除了使用后台的分阶段发布功能，业务侧还可以配合**服务端灰度开关**做更细的控制：例如新功能依赖后端新接口时，后端按用户维度做灰度（白名单、按 userId 哈希取模），小程序端根据接口返回的灰度标记决定走新流程还是旧流程。下面是一个典型的后端灰度分配实现（SpringBoot 风格）：

```java
// GrayReleaseUtil.java —— 基于 userId 哈希的服务端灰度分配
// 按 userId 稳定分桶：同一用户灰度期间始终命中同一分组，避免反复横跳
public class GrayReleaseUtil {

    /**
     * 判断用户是否命中灰度分组
     * @param userId   用户ID，稳定且均匀
     * @param grayRatio 灰度比例（0-100 的整数）
     * @return true 表示命中灰度组，走新逻辑
     */
    public static boolean inGrayGroup(Long userId, int grayRatio) {
        if (grayRatio <= 0) return false;
        if (grayRatio >= 100) return true;
        // 对 userId 取模分桶，保证分配均匀且同一用户结果稳定
        int bucket = Math.floorMod(userId, 100);
        return bucket < grayRatio;
    }

    public static void main(String[] args) {
        // 模拟 10% 灰度：统计命中比例是否接近 10%
        int grayRatio = 10;
        int total = 10000;
        int hit = 0;
        for (long id = 1; id <= total; id++) {
            if (inGrayGroup(id, grayRatio)) hit++;
        }
        System.out.printf("灰度比例 %d%%，实际命中 %.2f%%%n", grayRatio, hit * 100.0 / total);
        // 输出示例: 灰度比例 10%，实际命中 10.02%
    }
}
```

小程序端从后端拿到灰度标记后，决定渲染新页面还是旧页面：

```javascript
// 小程序端：根据后端灰度标记选择流程
function loadHomePage() {
  wx.request({
    url: 'https://api.example.com/v1/home/config',
    success(res) {
      const { grayEnabled } = res.data.data;
      if (grayEnabled) {
        // 灰度用户：走新版首页
        wx.redirectTo({ url: '/pages/home-v2/index' });
      } else {
        // 非灰度用户：走旧版首页
        wx.redirectTo({ url: '/pages/home/index' });
      }
    }
  });
}
```

```text
分阶段发布要点：
1. 官方灰度 —— 后台分阶段发布，按用户比例放量，可暂停
2. 比例节奏 —— 10% -> 50% -> 100%，每档观察至少 30 分钟
3. 随机覆盖 —— 灰度用户是随机比例，不是按地区/时间划分
4. 暂停机制 —— 异常时可暂停，已覆盖用户保持新版本
5. 服务端灰度 —— 后端按 userId 哈希分桶，稳定不跳组
6. 双端对齐 —— 前后端灰度开关必须同步，避免新旧接口混用
```

## 灰度策略

灰度策略解决的是「放量节奏怎么定、什么情况该停、什么情况该回滚」的问题。策略的核心是：每一档放量都是一次小规模实验，用数据说话，数据不达标就停。

```text
灰度观察指标（每档放量后必须盯）：
1. 错误率 —— 小程序端 JS 错误率、接口请求失败率
2. 接口耗时 —— 核心接口 P95 耗时与发布前基线的对比
3. 崩溃率 —— 页面异常退出、卡死比例
4. 核心转化 —— 下单转化率、登录成功率、支付成功率
5. 用户反馈 —— 客服工单量、差评、社媒舆情
6. 性能指标 —— 首屏耗时、启动耗时是否劣化
```

放量节奏建议：10% 观察 30 分钟到数小时 → 50% 观察数小时 → 100%。观察窗口内任何一项指标劣化超过阈值（例如错误率翻倍、支付成功率下降超过 1 个百分点）都应暂停放量，定位问题。灰度期间发现的问题要能快速定位到具体代码改动，这要求发布版本包含完整的变更清单。

灰度数据通常来自两个渠道：微信后台自带的数据助手（访问分析、性能监控）与自建监控（错误上报 + 接口监控）。自建监控的优势是指标可自定义、粒度细。下面的脚本演示如何用发布前后的错误率数据自动决策「放量 / 暂停 / 回滚」：

```javascript
// gray-decision.js —— 根据灰度指标自动给出放量建议
// 用法: node gray-decision.js metrics.json
const fs = require('fs');

const file = process.argv[2];
if (!file) {
  console.error('用法: node gray-decision.js metrics.json');
  process.exit(1);
}

// metrics.json 结构:
// {
//   "baseline": { "errorRate": 0.5, "p95ms": 320, "paySuccessRate": 99.2 },
//   "gray":     { "errorRate": 1.8, "p95ms": 410, "paySuccessRate": 98.1 },
//   "currentRatio": 10
// }
const m = JSON.parse(fs.readFileSync(file, 'utf8'));

const problems = [];
// 错误率劣化超过 2 倍
if (m.gray.errorRate > m.baseline.errorRate * 2) {
  problems.push(`错误率劣化: ${m.baseline.errorRate}% -> ${m.gray.errorRate}%`);
}
// P95 耗时劣化超过 30%
if (m.gray.p95ms > m.baseline.p95ms * 1.3) {
  problems.push(`P95 耗时劣化: ${m.baseline.p95ms}ms -> ${m.gray.p95ms}ms`);
}
// 支付成功率下降超过 1 个百分点
if (m.baseline.paySuccessRate - m.gray.paySuccessRate > 1) {
  problems.push(`支付成功率下降: ${m.baseline.paySuccessRate}% -> ${m.gray.paySuccessRate}%`);
}

if (problems.length > 0) {
  console.log('决策: 暂停放量，立即排查问题');
  problems.forEach((p) => console.log(`  - ${p}`));
  console.log('严重问题建议直接回滚（当前灰度比例: ' + m.currentRatio + '%）');
  process.exit(2);
}

if (m.currentRatio < 100) {
  const next = m.currentRatio >= 50 ? 100 : 50;
  console.log(`决策: 指标正常，建议放量到 ${next}%`);
} else {
  console.log('决策: 指标正常，已完成全量，进入发布后观察期');
}
process.exit(0);
```

```text
灰度策略要点：
1. 每档观察 —— 10% / 50% / 100% 每档留足观察时间
2. 指标阈值 —— 错误率翻倍、耗时 +30%、转化下降 1% 即停
3. 基线先行 —— 灰度前必须记录发布前基线，没有基线无法判断
4. 数据闭环 —— 灰度决策脚本化，减少人为拍脑袋
5. 双渠道 —— 微信数据助手 + 自建监控双保险
6. 变更清单 —— 灰度问题要能快速定位到具体改动点
```

## 回滚与发布历史

回滚是发布体系的最后一道防线：新版本在线上出现问题且短时间无法修复时，把线上版本回退到上一个正常版本。回滚的意义在于止损——让用户先恢复到可用状态，修复后的新版本走新的提审流程再上线。

```text
回滚机制：
1. 回退入口 —— 后台「版本管理 - 线上版本」的「回退」操作
2. 回退目标 —— 回退到上一个线上版本（历史版本需仍被平台保留）
3. 生效方式 —— 回退后用户启动拉取旧版本，效果同发布
4. 灰度版本回退 —— 分阶段发布中的版本可直接回退，已覆盖用户回旧版
5. 发布历史 —— 线上版本区域展示历次发布记录（版本号、时间、发布人）
6. 回滚不是修复 —— 回滚只是止损，问题仍需修复后重新提审发布
```

「发布历史」是回滚决策的依据：清晰的发布历史能快速定位「哪个版本引入的问题」「上一个正常版本是什么」。发布历史建议记录：版本号、发布时间、发布方式（全量/分阶段）、发布人、版本描述、回滚记录。后台自带发布历史，团队内部还可以维护一份更细的发布台账，与后端发版记录对应。

回滚决策要果断：发现线上事故，先回滚止损，再分析原因。犹豫不决每多一分钟，受影响用户就多一批。下面的脚本演示发布台账的维护与「自动找到上一个正常版本」的逻辑：

```javascript
// release-history.js —— 发布台账查询与回滚目标定位
// 用法: node release-history.js history.json
const fs = require('fs');

const file = process.argv[2];
if (!file) {
  console.error('用法: node release-history.js history.json');
  process.exit(1);
}

// history.json: [{ "version":"1.3.0","time":"2026-08-18 10:00","mode":"分阶段","status":"回滚" }, ...]
const history = JSON.parse(fs.readFileSync(file, 'utf8'));

console.log('===== 发布台账 =====');
history.forEach((h) => {
  const flag = h.status === '回滚' ? '[已回滚]' : h.status === '线上' ? '[线上]' : `[${h.status}]`;
  console.log(`${h.time}  ${h.version.padEnd(8)} ${h.mode.padEnd(6)} ${flag}`);
});

// 找当前线上版本与可回退目标
const online = history.filter((h) => h.status === '线上').pop();
const rollbackTarget = [...history]
  .reverse()
  .find((h) => h.status === '线上' && h.version !== online.version);

console.log(`\n当前线上版本: ${online ? online.version : '未知'}`);
console.log(`回滚目标版本: ${rollbackTarget ? rollbackTarget.version : '无（需重新提审）'}`);
```

```text
回滚要点：
1. 果断止损 —— 线上事故先回滚，再分析原因，不要犹豫
2. 目标明确 —— 回滚到上一个线上版本，台账要能自动定位
3. 回滚即发布 —— 回滚操作本身也是一次发布，同样要观察数据
4. 灰度可退 —— 分阶段发布中的版本回退影响面更小
5. 历史留痕 —— 发布台账记录版本、时间、方式、结果
6. 修复闭环 —— 回滚后修复问题，走提审重新发布，别停在回滚
```

## 应用场景实战

### 场景一：10% -> 50% -> 100% 完整灰度发布

以版本 1.3.0 为例，走一遍完整的分阶段发布流程：

```text
步骤：
1. 发布前：记录基线指标（错误率 0.5%、首页接口 P95 320ms、支付成功率 99.2%）
2. 审核通过后，后台点击「发布」，选择「分阶段发布」，比例填 10%
3. 确认后版本进入线上版本区域，状态「发布中（10%）」
4. 观察 30 分钟：运行 gray-decision.js metrics.json 检查指标
5. 指标正常 -> 后台调整比例到 50%，继续观察数小时
6. 指标正常 -> 后台调整比例到 100%，完成全量
7. 全量后再观察 24 小时，确认无异常后关闭灰度开关
8. 发布台账记录：1.3.0 分阶段发布，10% -> 50% -> 100%，状态线上
```

metrics.json 示例（灰度 10% 档数据）：

```json
{
  "baseline": { "errorRate": 0.5, "p95ms": 320, "paySuccessRate": 99.2 },
  "gray": { "errorRate": 0.6, "p95ms": 330, "paySuccessRate": 99.1 },
  "currentRatio": 10
}
```

```text
灰度发布检查点：
1. 每档放量前确认基线数据已记录
2. 10% 档观察 30 分钟以上，重点盯错误率与支付成功率
3. 50% 档观察数小时，覆盖更多机型与网络环境
4. 100% 前确认后端容量充足（灰度期压测过）
5. 全程保留灰度开关，问题随时暂停或回滚
6. 全量后 24 小时内保持高度关注
```

### 场景二：灰度期发现严重问题，立即回滚止损

假设 50% 放量后支付成功率从 99.2% 掉到 96.5%，需要立即止损：

```text
步骤：
1. 监控告警触发：支付成功率下降超过阈值
2. 确认问题：灰度用户支付报错率飙升，定位到新版本支付参数变更
3. 后台「线上版本」点击「回退」，回退到上一个线上版本 1.2.1
4. 回退后观察 30 分钟：支付成功率恢复基线
5. 客服同步话术：告知用户遇到问题重试即可
6. 修复 1.3.1（回退版本号递增），重新走提审 -> 发布流程
7. 复盘：支付参数变更为什么没有灰度前发现（缺支付链路联调测试）
```

回滚操作脚本化留痕（与 release-history.js 配合）：

```javascript
// rollback-record.js —— 记录一次回滚操作
// 用法: node rollback-record.js 1.3.0 1.2.1 "支付成功率下降"
const fs = require('fs');

const [badVersion, targetVersion, reason] = process.argv.slice(2);
if (!badVersion || !targetVersion || !reason) {
  console.error('用法: node rollback-record.js <问题版本> <回退目标> <原因>');
  process.exit(1);
}

const file = 'history.json';
const history = fs.existsSync(file) ? JSON.parse(fs.readFileSync(file, 'utf8')) : [];
history.push({
  version: badVersion,
  time: new Date().toISOString().slice(0, 16).replace('T', ' '),
  mode: '回滚',
  status: '已回滚',
  rollbackTo: targetVersion,
  reason
});
fs.writeFileSync(file, JSON.stringify(history, null, 2));
console.log(`已记录: ${badVersion} 回滚到 ${targetVersion}，原因: ${reason}`);
```

```text
回滚场景要点：
1. 告警触发即响应 —— 指标越线立即确认，不拖泥带水
2. 回退操作一分钟内完成 —— 后台回退按钮路径要熟练
3. 回退后验证 —— 确认指标恢复，不是回退了就完事
4. 修复版本号递增 —— 1.3.0 有问题，修复版叫 1.3.1，不重复用号
5. 回滚原因进台账 —— 为复盘与流程改进提供数据
6. 客服同步 —— 线上事故期间客服话术提前准备
```

## 最佳实践与踩坑记录

### 最佳实践

1. 默认分阶段发布：除紧急修复外，所有版本都走 10% -> 50% -> 100% 的灰度节奏，把「发布」变成可观察、可干预的流程
2. 发布前必须记录基线指标（错误率、P95 耗时、核心转化率），没有基线就没有灰度判断依据
3. 发布窗口固定化：工作日 10:00-16:00 发布，避开周五下午与节假日前夕，保证发布后有足够的观察时间
4. 灰度决策脚本化：指标数据进脚本自动判断「放量 / 暂停 / 回滚」，减少人为拍脑袋与通知不及时
5. 前后端灰度开关必须同步：后端接口灰度与小程序分阶段发布对齐，避免灰度用户调用到未就绪的接口
6. 发布台账与后端发版记录统一维护，回滚时能快速定位「上一个正常版本」及其配套后端版本
7. 回滚预案在发布前写好：明确谁有权回滚、回滚到哪个版本、回滚后如何通知用户
8. 用 UpdateManager 主动引导用户更新，缩短全量发布后的版本收敛时间

### 踩坑记录

```text
坑 1：误以为分阶段发布是按地区/时间维度灰度
结论：灰度用户是随机比例，运营想按城市灰度发现做不到。
原因：后台分阶段发布按用户比例随机分配，不提供地域/人群筛选。
解法：需要定向灰度用服务端灰度开关（按 userId 哈希分桶），小程序端根据标记分流。

坑 2：灰度期发现问题仍继续放量
结论：50% 档已发现错误率翻倍，仍推进到 100%，事故影响面扩大。
原因：放量节奏靠感觉，没有指标阈值与停手纪律。
解法：灰度决策脚本化（gray-decision.js），指标越线自动暂停；明确「暂停无需审批」。

坑 3：只回滚小程序端，后端没同步回滚
结论：用户回退到旧版本，但后端已切到新接口，新旧不兼容继续报错。
原因：小程序版本与后端版本联动关系没理清，回滚只做了前端动作。
解法：发布台账同时记录前后端版本；回滚预案写明配套后端回滚步骤。

坑 4：全量发布后发现严重问题，无法立即撤回
结论：全量发布后发现问题，只能等重新提审，用户持续受影响。
原因：全量发布没有中间状态，出问题只能回滚，而回滚后修复版本又要走审核。
解法：大版本一律分阶段发布；出问题先回滚止损，修复版本走加急审核。

坑 5：分阶段发布暂停后再次发布，比例逻辑混乱
结论：暂停后调整比例，覆盖用户范围与预期不符，部分用户反复横跳。
原因：暂停与恢复、比例调整对已覆盖用户的影响理解错误。
解法：暂停后先想清楚目标：观察则保持暂停，恢复则明确新比例，回滚则直接回退。

坑 6：新版本依赖后端新接口，灰度用户大面积报错
结论：小程序 1.3.0 上线，后端接口 1.3 尚未部署，灰度用户请求 404。
原因：前后端发布顺序错误，后端未先行或未做版本兼容。
解法：后端先上线并兼容旧版本；接口变更做版本化（/v1、/v2），小程序端兜底降级。

坑 7：缓存导致灰度用户看到旧版本，灰度数据失真
结论：灰度比例 10%，但实际新版本访问量远低于 10%，数据无法评估。
原因：客户端缓存、CDN 缓存、用户未重启导致版本收敛慢。
解法：用 UpdateManager 主动更新；灰度评估以接口侧数据为主，前端版本分布做参考。

坑 8：发布后没有对比基线，异常无法判断
结论：发布后错误率 1%，看起来不高，但发布前是 0.3%，实际已劣化 3 倍。
原因：没有发布前基线，拿绝对值当正常值。
解法：发布前记录基线；监控告警用「环比基线」而非绝对值阈值。
```
