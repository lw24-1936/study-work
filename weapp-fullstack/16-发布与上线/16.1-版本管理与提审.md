## 概述

小程序与普通 Web 应用最大的区别之一在于「版本」概念：代码写好不能直接上线，必须通过微信开发者工具上传到微信服务器，在后台提交审核，审核通过后手动发布，用户侧才会更新到新版本。版本管理与提审是发布上线的第一道关卡，直接决定功能上线的周期与风险。

提审链路涉及五个环节：版本号规范（给每个版本起一个可追溯的编号）、上传代码（把本地代码推到微信服务器）、提交审核（填写审核信息与材料）、审核流程（等待微信人工审核并跟踪状态）、审核材料（类目资质、截图、测试账号）。任何一个环节出问题都会导致审核被拒或上线延期，因此本章把这五个环节串成一条可执行的流水线来讲解。

```text
版本管理与提审的核心要点：
1. 版本号 —— 语义化版本号 x.y.z，与后台审核版本号区分管理
2. 上传 —— 开发者工具上传代码到微信服务器，形成开发版本
3. 提审 —— 后台提交审核，填写版本描述、测试账号、功能截图
4. 审核 —— 微信人工审核，一般 1-7 个工作日，支持状态查询
5. 材料 —— 类目资质、功能截图、测试账号、隐私协议
6. 红线 —— 内容违规、诱导分享、类目不匹配会被拒绝或封禁
```

## 版本号规范

版本号是版本管理的索引。小程序项目建议采用语义化版本号（Semantic Versioning），格式为 `主版本号.次版本号.修订号`，即 `x.y.z` 三段式：

```text
语义化版本号规则：
1. 主版本号 MAJOR —— 不兼容的 API 变更、重大改版（1.0.0 → 2.0.0）
2. 次版本号 MINOR —— 向后兼容的新功能（1.0.0 → 1.1.0）
3. 修订号 PATCH —— 向后兼容的缺陷修复（1.0.0 → 1.0.1）
4. 预发布版本 —— 可追加 -beta.1 / -rc.1 等后缀，如 1.2.0-rc.1
5. 递增规则 —— 升主版本号时次版本与修订号归零，升次版本时修订号归零
```

需要特别注意区分两套版本号：一套是**代码版本号**，由开发者在上传代码时填写，例如 `1.3.0`；另一套是**审核版本号**，由微信后台在提交审核时生成（如 `1.3.0.0`），用于标识这次审核动作本身。线上用户通过 `wx.getAccountInfoSync()` 获取到的是代码版本号，而审核记录、加急记录使用的是审核版本号，两者不要混为一谈。

版本号统一由脚本管理，避免人工手改出错。下面是一个完整的语义化版本号校验与比较脚本：

```javascript
// validate-version.js —— 语义化版本号校验与比较
// 用法: node validate-version.js 1.0.0 1.0.1
const VERSION_RE = /^(\d+)\.(\d+)\.(\d+)(?:-([0-9A-Za-z.-]+))?(?:\+([0-9A-Za-z.-]+))?$/;

function parseVersion(v) {
  const m = VERSION_RE.exec(String(v).trim());
  if (!m) return null;
  return {
    major: Number(m[1]),
    minor: Number(m[2]),
    patch: Number(m[3]),
    prerelease: m[4] || null,
    build: m[5] || null
  };
}

// 返回: a > b 为 1，a < b 为 -1，相等为 0；无法解析返回 null
function compareVersions(a, b) {
  const pa = parseVersion(a);
  const pb = parseVersion(b);
  if (!pa || !pb) return null;
  if (pa.major !== pb.major) return pa.major > pb.major ? 1 : -1;
  if (pa.minor !== pb.minor) return pa.minor > pb.minor ? 1 : -1;
  if (pa.patch !== pb.patch) return pa.patch > pb.patch ? 1 : -1;
  // 有预发布后缀的版本低于同数字正式版本（1.0.0-rc.1 < 1.0.0）
  if (pa.prerelease && !pb.prerelease) return -1;
  if (!pa.prerelease && pb.prerelease) return 1;
  if (pa.prerelease && pb.prerelease) {
    if (pa.prerelease === pb.prerelease) return 0;
    return pa.prerelease > pb.prerelease ? 1 : -1;
  }
  return 0;
}

const [a, b] = process.argv.slice(2);
if (!a || !b) {
  console.error('用法: node validate-version.js <版本A> <版本B>');
  process.exit(1);
}
const pa = parseVersion(a);
const pb = parseVersion(b);
if (!pa) { console.error(`版本号格式非法: ${a}`); process.exit(1); }
if (!pb) { console.error(`版本号格式非法: ${b}`); process.exit(1); }
const r = compareVersions(a, b);
console.log(`${a} vs ${b} -> ${r === 1 ? 'A 更新' : r === -1 ? 'B 更新' : '相同'}`);
```

小程序端可以在运行时拿到当前线上版本号，用于版本比对（例如提示用户升级、配合后端做功能开关）：

```javascript
// 获取当前小程序运行版本
const info = wx.getAccountInfoSync();
console.log('线上版本号:', info.miniProgram.version);       // 例如 1.3.0
console.log('基础库版本:', info.miniProgram.libVersion);    // 例如 3.4.6
console.log('运行环境:', info.miniProgram.envVersion);       // develop / trial / release
```

```text
版本号规范要点：
1. 三段式 x.y.z —— 主版本.次版本.修订号，语义化递增
2. 脚本管理 —— 用脚本校验、比较、递增版本号，杜绝手改
3. 双版本区分 —— 代码版本号（上传时填）与审核版本号（后台生成）分开记录
4. 运行时可读 —— wx.getAccountInfoSync() 可读当前线上版本
5. 与后端对齐 —— 小程序版本号与后台接口版本、APP 版本建立映射表
6. 禁止回退 —— 已发布的版本号不要复用，新代码必须用更大的版本号
```

## 上传代码与版本管理

代码开发完成后，第一步是把本地代码上传到微信服务器。上传动作在微信开发者工具中完成：点击工具栏右上角的「上传」按钮，工具会提示填写**版本号**与**项目备注**，确认后代码被打包上传，随后可以在小程序后台「管理 - 版本管理」页面的「开发版本」区域看到这条记录。

```text
上传代码流程：
1. 开发者工具编译通过（本地模拟器无报错）
2. 点击工具栏「上传」按钮，填写版本号（如 1.3.0）与项目备注
3. 上传成功后，后台「版本管理 - 开发版本」出现该版本记录
4. 可将开发版本「设为体验版」，生成体验版二维码供测试人员扫码验证
5. 测试通过后，在开发版本卡片点击「提交审核」
6. 提审后版本进入「审核版本」区域，与开发版本、线上版本并列展示
```

后台「版本管理」页是版本状态的唯一权威视图，包含三个区域：

```text
版本管理三个区域：
1. 开发版本 —— 已上传未提审的版本，可设体验版、可删除
2. 审核版本 —— 已提交审核的版本，显示审核中/通过/不通过状态
3. 线上版本 —— 已发布给用户的版本，可查看发布历史与回退
```

「上传备注」建议按固定格式书写，便于后续追溯：`[需求单号] 功能简述`。可以用 Git 提交记录自动生成上传备注，避免手写遗漏。下面脚本读取最近一次 tag 以来的提交记录，自动生成符合格式的上传备注：

```javascript
// gen-upload-notes.js —— 根据 Git 提交记录生成上传备注
// 用法: node gen-upload-notes.js 1.3.0
const { execSync } = require('child_process');

function run(cmd) {
  return execSync(cmd, { encoding: 'utf8' }).trim();
}

const newVersion = process.argv[2];
if (!newVersion) {
  console.error('用法: node gen-upload-notes.js <新版本号>');
  process.exit(1);
}

// 找最近一个版本 tag，没有则从第一次提交开始统计
let range = '';
try {
  const lastTag = run('git describe --tags --abbrev=0');
  range = `${lastTag}..HEAD`;
} catch (e) {
  range = 'HEAD';
}

const log = run(`git log --oneline --no-merges ${range}`);
const lines = log.split('\n').filter(Boolean);

console.log(`===== 版本 ${newVersion} 上传备注（复制到开发者工具）=====`);
lines.forEach((line, i) => {
  console.log(`${i + 1}. ${line.replace(/^\w+\s/, '')}`);
});
console.log('==============================================');
```

```text
上传代码要点：
1. 编译先行 —— 上传前先编译通过，避免把报错代码传上去
2. 备注规范 —— 上传备注写清需求单号与功能点，可追溯
3. 体验版 —— 提审前先设体验版给测试人员真机验证
4. 隐私协议 —— 涉及用户信息收集的，上传前在后台完成隐私协议配置
5. 版本唯一 —— 同一版本号不要重复上传覆盖，避免审核版本与代码版本错位
6. CI 可集成 —— 微信提供了命令行/HTTP 上传接口，可接入 CI 自动化
```

## 提交审核

开发版本测试通过后，在后台「版本管理 - 开发版本」区域点击该版本的「提交审核」，进入审核信息填写页。审核信息填写是否完整、准确，直接影响审核通过率与审核周期。

```text
提交审核必填/选填信息：
1. 版本描述 —— 必填，向审核人员说明本次版本的功能与改动，务必写清楚
2. 测试账号 —— 登录类小程序必填，提供可用的账号密码与角色说明
3. 功能页面 —— 选填，可提交功能页截图，帮助审核人员理解功能
4. 审核类目 —— 后台「设置 - 服务类目」配置，决定审核要求与可用能力
5. 加急审核 —— 可选，账号有加急额度时可在提审时勾选
6. 隐私协议 —— 涉及收集用户信息必须配置「用户隐私保护指引」并让用户同意
```

「版本描述」是审核人员理解产品的第一手资料，建议包含：本次版本解决什么问题、新增了哪些功能、如何操作体验、涉及哪些敏感能力（位置、相机、通讯录等）以及对应的授权弹窗说明。描述清晰的小程序审核通过率明显更高。

「测试账号」是审核人员实际体验产品时使用的凭证。有登录功能的小程序如果不提供测试账号，审核人员无法进入功能页，通常会直接判定「无法体验功能」而拒绝。测试账号要求：真实可用、权限完整（能访问到本次提审的所有功能）、在提审材料中写明账号与密码。

提审前可以用脚本对审核信息做一次完整性自检，把容易漏填的字段全部校验一遍：

```javascript
// check-audit-info.js —— 提交审核前校验审核信息完整性
// 用法: node check-audit-info.js release-info.json
const fs = require('fs');

const REQUIRED = [
  ['version', '版本号'],
  ['versionDesc', '版本描述'],
  ['testAccount', '测试账号'],
  ['testPassword', '测试密码'],
  ['categoryId', '审核类目ID'],
  ['privacyDoc', '隐私协议配置确认'],
  ['screenshotDir', '功能截图目录']
];

const file = process.argv[2];
if (!file) {
  console.error('用法: node check-audit-info.js release-info.json');
  process.exit(1);
}

let info;
try {
  info = JSON.parse(fs.readFileSync(file, 'utf8'));
} catch (e) {
  console.error(`读取 ${file} 失败: ${e.message}`);
  process.exit(1);
}

const missing = REQUIRED.filter(([key]) => !info[key] || String(info[key]).trim() === '');
if (missing.length > 0) {
  console.error('以下必填项缺失，请补充后再提审：');
  missing.forEach(([key, label]) => console.error(`  - ${label} (${key})`));
  process.exit(1);
}

// 版本描述长度检查
if (String(info.versionDesc).length < 20) {
  console.error('版本描述过短（少于 20 字），请补充功能说明');
  process.exit(1);
}

console.log('审核信息校验通过，可以提交审核');
console.log(`版本: ${info.version}`);
console.log(`描述: ${info.versionDesc}`);
console.log(`截图目录: ${info.screenshotDir}`);
```

```text
提交审核要点：
1. 描述写透 —— 版本描述按「问题 + 功能 + 操作路径」结构写
2. 账号必给 —— 登录类小程序必须提供可用测试账号
3. 类目匹配 —— 审核类目与业务功能严格匹配，类目错配必被拒
4. 隐私先行 —— 先配好隐私协议与用户隐私保护指引再提审
5. 截图辅助 —— 关键页面截图帮助审核人员快速理解功能
6. 可撤回 —— 审核中发现错误可撤回重新提审，撤回不影响版本
```

## 审核流程与状态

提交审核后，版本进入「审核版本」区域，状态为「审核中」。微信对代码进行机器预检（代码包大小、基础库版本、明显违规内容检测）后进入人工审核队列。官方口径的审核时长一般为 **1-7 个工作日**，实际多数小程序在 1-2 天内出结果，高峰期或特殊类目可能更久。

```text
审核状态流转：
1. 审核中 —— 代码进入微信审核队列，等待人工审核
2. 审核通过 —— 审核完成，版本可发布，进入「可发布」状态
3. 审核不通过 —— 后台展示失败原因，修改后重新提交审核
4. 审核被撤回 —— 开发者主动撤回，回到开发版本区域
5. 发布 —— 审核通过后手动发布，用户侧更新到新版本
6. 加急审核 —— 有额度的账号可在提审时勾选，插队审核，不降低审核标准
```

「加急审核」是微信提供给高信用账号的加速通道：提交审核时勾选加急，消耗账号的加急额度。额度与账号的历史审核通过率、违规记录相关，且加急只缩短排队时间，不改变审核标准——存在违规内容的版本加急也会被拒。加急额度有限，建议只在紧急修复、重大活动前使用。

审核状态除了在后台「版本管理」页查看，服务端也可以通过微信 API 查询。微信提供了 `wxa/getauditstatus` 接口（需服务端 access_token），适合把审核状态接入内部告警或自动化发布流程：

```javascript
// poll-audit.js —— 通过微信 API 轮询代码审核状态
// 用法: node poll-audit.js <access_token> <auditid>
// 注意: 必须由服务端调用，access_token 严禁出现在小程序代码中
const https = require('https');

const [token, auditid] = process.argv.slice(2);
if (!token || !auditid) {
  console.error('用法: node poll-audit.js <access_token> <auditid>');
  process.exit(1);
}

function callApi(path, body) {
  return new Promise((resolve, reject) => {
    const req = https.request({
      hostname: 'api.weixin.qq.com',
      path,
      method: 'POST',
      headers: { 'Content-Type': 'application/json' }
    }, (res) => {
      let data = '';
      res.on('data', (c) => (data += c));
      res.on('end', () => {
        if (!data) {
          reject(new Error('接口返回为空（网络异常或 token 失效）'));
          return;
        }
        try { resolve(JSON.parse(data)); } catch (e) { reject(e); }
      });
    });
    req.on('error', reject);
    req.write(JSON.stringify(body));
    req.end();
  });
}

// status: 0=审核通过, 1=审核中, 2=审核不通过
async function poll() {
  const res = await callApi(
    `/wxa/getauditstatus?access_token=${token}`,
    { auditid }
  );
  if (res.errcode !== 0) {
    console.error('查询失败:', res.errmsg || res.errcode);
    process.exit(1);
  }
  const statusMap = { 0: '审核通过', 1: '审核中', 2: '审核不通过' };
  console.log(`审核状态: ${statusMap[res.status] ?? res.status}`);
  if (res.status === 2) console.log(`不通过原因: ${res.reason || '见后台'}`);
  return res.status;
}

// 轮询：每 30 秒查一次，最多查 60 次（约 30 分钟）
async function main() {
  for (let i = 0; i < 60; i++) {
    const status = await poll();
    if (status !== 1) process.exit(0);
    await new Promise((r) => setTimeout(r, 30000));
  }
  console.log('轮询超时，请稍后手动查询');
}

main().catch((e) => {
  console.error(e.message);
  process.exit(1);
});
```

```text
审核流程要点：
1. 时长预期 —— 官方 1-7 个工作日，多数 1-2 天，特殊类目更久
2. 加急谨慎 —— 加急额度有限且不降低标准，留给紧急修复
3. 状态可查 —— 后台版本管理页 + 服务端 getauditstatus API
4. 不通过即改 —— 按失败原因逐条修复，避免重复提交相同问题
5. 撤回自由 —— 审核中可撤回，撤回后回到开发版本
6. 节假日慢 —— 春节、双十一等大促前后审核排队明显变长，提前规划
```

## 审核材料与类目资质

审核材料是审核通过的硬性条件。材料分为四类：类目资质证照、功能截图、测试账号、隐私协议。不同类目对资质的要求差异巨大，材料不全或与类目不匹配是审核被拒的高频原因。

```text
常见类目与资质要求：
1. 电商平台/商家自营 —— 营业执照；部分类目需食品经营许可证、出版物经营许可证
2. 餐饮 —— 营业执照 + 食品经营许可证
3. 医疗健康 —— 医疗机构执业许可证 / 相关行业资质，审核最严
4. 社交 —— 需提供增值电信业务经营许可证（ICP 许可证）或说明
5. 金融 —— 需金融监管资质，个人主体不可申请
6. 工具类 —— 多数只需营业执照/主体证件，资质要求低
```

类目配置位置在后台「设置 - 基本设置 - 服务类目」。一个小程序可配置多个类目，但每个类目都要有对应的资质支撑。类目还直接决定能力边界：例如「电商平台」类目才能开通微信支付中的电商能力，「社交-陌生人交友」类目需要额外资质。类目选错不仅审核被拒，还可能影响支付、订阅消息等能力的开通。

功能截图与测试账号是审核材料的「体验部分」：截图让审核人员快速了解页面形态，测试账号让审核人员能真正进入产品操作。隐私协议则是合规部分——小程序收集用户信息（头像、手机号、位置、相册等）必须在后台填写「用户隐私保护指引」，并在代码中通过隐私授权组件获取用户同意，否则审核直接拒绝。

材料目录建议纳入工程管理，用脚本自动生成材料清单，提审时对照检查：

```javascript
// gen-audit-checklist.js —— 扫描审核材料目录生成提审清单
// 用法: node gen-audit-checklist.js ./audit-materials
const fs = require('fs');
const path = require('path');

const dir = process.argv[2] || './audit-materials';
if (!fs.existsSync(dir)) {
  console.error(`目录不存在: ${dir}`);
  process.exit(1);
}

// 期望的材料结构:
// audit-materials/
//   category/    类目资质证照（营业执照、许可证等）
//   screenshots/ 功能截图
//   accounts/    测试账号说明
//   privacy/     隐私协议相关
const sections = [
  ['category', '类目资质'],
  ['screenshots', '功能截图'],
  ['accounts', '测试账号'],
  ['privacy', '隐私协议']
];

console.log('# 提审材料清单');
let empty = 0;
for (const [sub, label] of sections) {
  const subDir = path.join(dir, sub);
  const files = fs.existsSync(subDir)
    ? fs.readdirSync(subDir).filter((f) => !f.startsWith('.'))
    : [];
  console.log(`\n## ${label} (${files.length} 个文件)`);
  if (files.length === 0) {
    console.log('- [ ] 缺失，请补充');
    empty++;
  } else {
    files.forEach((f) => console.log(`- [x] ${f}`));
  }
}
console.log(`\n共 ${empty} 个材料目录缺失`);
process.exit(empty > 0 ? 1 : 0);
```

```text
审核材料要点：
1. 资质先行 —— 特殊类目资质办理周期长（许可证 1-4 周），提前申请
2. 类目匹配 —— 材料与类目严格对应，证照主体与小程序主体一致
3. 截图清晰 —— 截图覆盖核心功能页，注明页面用途
4. 账号可用 —— 提审前亲自登录测试账号验证一遍
5. 隐私必配 —— 收集任何用户信息都要配置隐私保护指引
6. 动态更新 —— 资质到期、换证后及时在后台更新，避免审核被拒
```

## 应用场景实战

### 场景一：一次完整提审流程（版本提升 → 上传备注 → 材料自检 → 提交审核）

以版本 1.2.3 → 1.3.0 为例，走完整提审链路：

```text
步骤：
1. 代码合并到主干分支，测试通过
2. 用脚本生成上传备注（gen-upload-notes.js 1.3.0），复制到开发者工具
3. 开发者工具点击「上传」，填版本号 1.3.0 与备注，上传成功
4. 后台「版本管理 - 开发版本」确认 1.3.0 已出现，点击「设为体验版」
5. 测试人员扫码体验版，验证新功能与回归用例
6. 后台「设置 - 基本设置 - 服务类目」确认类目与资质有效
7. 准备 release-info.json，运行 check-audit-info.js 自检
8. 后台开发版本卡片点击「提交审核」，填写版本描述、测试账号，提交
9. 审核中，用 poll-audit.js 或后台页面跟踪状态
```

release-info.json 示例：

```json
{
  "version": "1.3.0",
  "versionDesc": "新增会员中心与积分商城：用户可查看积分明细、兑换优惠券；修复支付回调偶发超时问题；优化首页首屏加载速度。体验路径：首页 -> 我的 -> 积分商城。",
  "testAccount": "audit_test@example.com",
  "testPassword": "Test@2026",
  "categoryId": "电商平台",
  "privacyDoc": "已配置隐私保护指引，涉及手机号与收货地址",
  "screenshotDir": "./audit-materials/screenshots"
}
```

```text
关键检查点：
1. 上传前本地编译零报错，真机预览通过
2. 上传备注包含需求单号，可回溯到需求文档
3. 测试账号在提审前 24 小时内登录验证过
4. 版本描述覆盖「新增 + 修复 + 体验路径」三部分
5. 隐私协议与代码中的授权弹窗一致
6. 提审后立即记录 auditid，便于后续查询状态
```

### 场景二：审核被拒后的快速处理流程

审核不通过是常态，关键在于快速定位原因并修复：

```text
步骤：
1. 后台「审核版本」查看不通过原因（如「类目与功能不符」「无法体验功能」）
2. 对照原因逐条修复：类目不符则调整类目或补充资质
3. 「无法体验功能」则检查测试账号：账号是否过期、是否缺少权限
4. 修复后在开发版本重新提交审核，版本号保持或递增修订号
5. 相同内容不要原样重复提交——审核人员会对比历史记录
6. 连续被拒 3 次以上，考虑联系客服或走申诉通道
```

脚本化的「被拒原因统计」可以帮助团队发现系统性审核问题：

```javascript
// audit-reject-stats.js —— 统计审核被拒原因，发现共性问题
// 用法: node audit-reject-stats.js rejects.json
const fs = require('fs');

const file = process.argv[2];
if (!file) {
  console.error('用法: node audit-reject-stats.js rejects.json');
  process.exit(1);
}

// rejects.json: [{"version":"1.2.0","reason":"类目与功能不符，需补充资质"}, ...]
const rejects = JSON.parse(fs.readFileSync(file, 'utf8'));
const stats = {};
rejects.forEach((r) => {
  const key = r.reason.slice(0, 12); // 按原因前缀归类
  stats[key] = (stats[key] || 0) + 1;
});

console.log('审核被拒原因统计（Top 5）：');
Object.entries(stats)
  .sort((a, b) => b[1] - a[1])
  .slice(0, 5)
  .forEach(([reason, count]) => console.log(`  ${count} 次: ${reason}...`));
```

```text
被拒处理要点：
1. 逐条修复 —— 原因写几条就修几条，不要只修第一条
2. 材料先行 —— 资质类问题先补材料再提审
3. 换人验证 —— 让没参与开发的同事用测试账号走一遍流程
4. 记录归档 —— 每次被拒原因归档统计，驱动类目与材料体系改进
5. 申诉通道 —— 认为误判可申诉，附上证明材料
6. 时间成本 —— 每次被拒重提至少多花 1-2 天，提审前务必自检
```

## 最佳实践与踩坑记录

### 最佳实践

1. 版本号统一用脚本管理（校验、比较、递增），禁止手工改号，杜绝「版本号重复覆盖」「版本号回退」这类低级错误
2. 上传备注与版本描述用固定模板：`[需求单号] 功能简述`，并与 Git 提交记录、需求文档建立对应关系，任何版本都可追溯
3. 提审前把「测试账号验证、隐私协议检查、类目资质有效期检查、功能截图更新」做成提审 Checklist，每次提审逐项打勾
4. 审核版本号与代码版本号分开记录：后台审核记录、加急记录用审核版本号，代码与线上版本用语义化版本号，建立映射表
5. 首次提审就把类目、资质、隐私协议一次配好，避免每个版本都因材料问题被拒
6. 加急审核额度留给紧急修复与活动前冲刺，日常迭代走常规审核，把额度当稀缺资源管理
7. 审核状态接入内部流程：服务端定时查询 getauditstatus，通过企业微信/钉钉机器人通知到发布负责人，缩短「审核通过但没人发布」的等待时间
8. 大促、节假日前后提前 1-2 周提审，规避审核排队高峰

### 踩坑记录

```text
坑 1：同一版本号重复上传，覆盖了已提审版本
结论：线上版本与开发版本指向的代码不一致，审核通过的版本与预期不符。
原因：上传时版本号填错或重复填写，微信以版本号标识开发版本，同号覆盖。
解法：版本号脚本化管理，上传前检查该版本号是否已存在；上传记录与 Git tag 绑定。

坑 2：混淆「代码版本号」与「审核版本号」
结论：查审核记录、对账时对不上号，以为版本丢失。
原因：提审时后台生成的审核版本号（如 1.3.0.0）与上传时填的代码版本号是两套编号。
解法：后台记录两套版本号的映射；代码注释与发布文档中明确标注。

坑 3：没提供测试账号，审核被拒「无法体验功能」
结论：登录类小程序不填测试账号，审核人员进不去页面，直接拒绝。
原因：审核人员不会自己注册账号，没有可用凭证就无法体验功能。
解法：提审必填真实可用的测试账号，写明账号密码与角色；提审前 24 小时内验证。

坑 4：类目资质与业务不匹配
结论：电商小程序选了工具类目，审核被拒且支付能力受限。
原因：类目选择随意，或资质证照与小程序主体不一致。
解法：按业务主场景选择类目，资质证照主体与小程序主体一致；不确定先咨询客服。

坑 5：隐私协议未配置或与代码行为不一致
结论：涉及收集用户信息的小程序提审被拒。
原因：代码里有获取位置/相册/手机号的逻辑，但后台未配置隐私保护指引，或指引描述与代码行为不符。
解法：提审前配置「用户隐私保护指引」；代码中调用隐私接口前弹窗征得同意。

坑 6：审核不通过后原样重复提交
结论：连续多次被拒，审核排队时间越来越长。
原因：没有按失败原因修复，或修复不彻底，审核人员对比历史提交发现相同问题。
解法：按原因逐条修复并自测；每次重提附上修改说明，让审核人员看到变化。

坑 7：加急审核用在不紧急的版本上
结论：紧急修复时没有加急额度，只能干等常规审核。
原因：加急额度有限，平时随便用完了。
解法：加急额度台账化管理，只用于线上事故修复与活动冲刺。

坑 8：提审后没有跟踪状态，审核通过了迟迟不发布
结论：审核通过后停留数天未发布，功能上线时间比预期晚。
原因：审核状态没人盯，或发布人不知道已通过。
解法：服务端轮询 getauditstatus 并推送通知；明确「审核通过即发布」的职责人。
```
