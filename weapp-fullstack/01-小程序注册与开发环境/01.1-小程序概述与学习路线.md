## 概述

微信小程序是微信生态内的轻量级应用形态，用户通过扫码、搜索、分享、下拉等入口直接打开，无需安装下载。它基于 WXML、WXSS、JavaScript 开发，运行在微信提供的双线程环境中，既能调用微信原生能力（登录、支付、消息、扫码），又能通过 HTTPS 与自有后台（SpringBoot 等）交互，是「前台轻应用 + 后台服务 + 管理端」全栈架构中最常见的前端形态。

```text
小程序的核心特征：
1. 免安装 —— 即用即走，不占桌面，入口在微信内
2. 双线程 —— 逻辑层 JS 与视图层 WXML/WXSS 分离，setData 通信
3. 强能力 —— 微信登录、支付、订阅消息、分享、扫码、定位等原生能力
4. 封闭审核 —— 代码需上传审核通过后才能发布，版本可控
5. 平台约束 —— 包体积上限、API 权限、类目资质均有明确限制
```

## 小程序是什么

微信小程序（WeChat Mini Program）是腾讯于 2017 年 1 月正式上线的一种应用形态。它运行在微信客户端内部，不需要用户主动安装，通过微信提供的入口（聊天分享、扫码、搜索、公众号菜单、下拉任务栏）即可打开使用。

从技术角度看，小程序不是普通的 HTML 页面，而是一套独立的开发体系：

```text
小程序技术栈：
1. WXML —— 类似 HTML 的模板语言，负责页面结构
2. WXSS —— 类似 CSS 的样式语言，引入 rpx 适配单位
3. JavaScript —— 逻辑层语言，负责数据处理与业务逻辑
4. JSON —— 配置文件（全局配置、页面配置、项目配置）
5. WXS —— 运行在视图层的小脚本语言，弥补 WXML 表达能力
```

小程序的项目由两部分组成：微信开发者工具负责本地开发调试，微信客户端提供运行时容器。开发者写好代码后上传到微信服务器，经过审核发布，用户侧才能通过微信访问。

小程序区别于传统 Web 应用的关键点：它运行在微信的 WebView + JS 引擎组合环境中，逻辑层（JS 线程）与视图层（渲染线程）分离，数据通过 setData 从逻辑层传到视图层，而不是像浏览器那样 DOM 直接可操作。这意味着开发者不能用 document/window 等浏览器 API，必须使用小程序自己的 API 体系（wx.*）。

## 平台生态与形态

微信小程序只是小程序生态的开端。目前国内主流小程序平台包括微信小程序、支付宝小程序、百度智能小程序、抖音小程序、QQ 小程序等，各自拥有独立的开发体系与 API，但核心思想一致：平台内运行、免安装、强入口。

```text
主流小程序平台对比：
1. 微信小程序 —— 用户量最大，能力最全（支付/消息/分享/扫码），电商与生活服务主阵地
2. 支付宝小程序 —— 依托支付宝，偏金融、政务、出行场景
3. 百度智能小程序 —— 依托百度搜索与信息流，偏内容与服务
4. 抖音小程序 —— 依托抖音短视频，偏内容电商与本地生活
5. QQ 小程序 —— 依托 QQ 社交关系链，偏年轻用户群
```

微信小程序按运行载体又可分为：

```text
微信小程序形态：
1. 普通小程序 —— 标准形态，微信内直接打开
2. 小游戏 —— 基于 Canvas/WebGL 的游戏形态，有独立开发框架
3. 企业微信小程序 —— 在企业微信内运行，面向企业内部与上下游协同
4. 微信小程序插件 —— 供其他小程序引用的能力包，一次开发多处使用
5. 半屏小程序 —— 从当前小程序拉起另一个小程序的轻量形态
```

同一套业务逻辑可以通过 Taro、uni-app 等跨端框架一次编写，编译到多个小程序平台，这是工程上常见的多端方案。本知识库以微信小程序为主，后台统一采用 SpringBoot，管理端采用 Vue，构成「小程序 + 后台 + 管理端」的完整全栈。

## 能力全景

小程序的能力体系可以划分为基础能力、开放能力与平台能力三层：

```text
小程序能力全景：
1. 基础能力 —— 页面渲染（WXML/WXSS）、逻辑处理（JS）、组件、API（网络/存储/路由/媒体/设备）
2. 开放能力 —— 微信登录、微信支付、订阅消息、分享、客服、广告、扫一扫、位置、蓝牙
3. 平台能力 —— 审核发布、版本管理、数据分析、灰度发布、内容安全检测、云开发
```

基础能力是开发者日常编码的主体，对应 wx 命名空间下数百个 API。按官方文档划分，wx API 分为以下几大类：

```text
wx API 分类：
1. 网络 —— wx.request / wx.uploadFile / wx.downloadFile / WebSocket
2. 存储 —— wx.setStorage / wx.getStorage / wx.removeStorage（含同步版本）
3. 路由 —— wx.navigateTo / wx.redirectTo / wx.switchTab / wx.navigateBack / wx.reLaunch
4. 界面 —— wx.showToast / wx.showModal / wx.showLoading / wx.showActionSheet / 导航栏
5. 媒体 —— 图片/录音/视频/音频/相机/直播组件相关 API
6. 设备 —— 系统信息/网络状态/剪贴板/震动/扫码/蓝牙/NFC/屏幕亮度
7. 开放接口 —— wx.login / wx.requestPayment / wx.requestSubscribeMessage / wx.shareAppMessage
8. 数据缓存 —— 本地缓存 / 数据预拉取 / 周期性更新
```

开放能力是微信小程序区别于普通 H5 的核心竞争力。登录（wx.login + code2session）让小程序免密获得用户身份；微信支付（wx.requestPayment）让交易闭环在微信内完成；订阅消息（wx.requestSubscribeMessage）让服务端可以主动触达用户；分享让产品获得社交裂变传播能力。这些能力是「小程序 + SpringBoot 后台」架构中的关键集成点，也是本知识库后续篇章的重点。

平台能力围绕开发运维全流程展开：代码上传、提审、发布、灰度、回滚是版本管理的标准动作；数据助手、错误监控、性能分析支撑线上运营；内容安全检测（security.msgSecCheck）处理用户生成内容的合规问题。

## 小程序 vs H5 vs App

选型时先弄清楚三者的边界。小程序介于 H5 与原生 App 之间：比 H5 能力更强（能调微信支付、订阅消息、原生组件），比 App 更轻（免安装、免更新、入口在微信内）。

```text
小程序 vs H5 vs App 对比：
1. 安装成本 —— H5 零成本打开；小程序免安装但需微信环境；App 需下载安装
2. 开发成本 —— H5 最低（Web 技术栈）；小程序中等（WXML/WXSS/JS 体系）；App 最高（原生双端）
3. 原生能力 —— H5 受限（浏览器沙箱）；小程序较强（微信开放能力）；App 最强（全系统 API）
4. 分发入口 —— H5 依赖 URL 传播；小程序微信内多入口（扫码/搜索/分享）；App 依赖应用市场
5. 审核发布 —— H5 随时发版；小程序需微信审核；App 需应用商店审核
6. 用户粘性 —— H5 最弱；小程序中弱（用完即走）；App 最强（桌面入口+推送）
7. 支付闭环 —— H5 微信内可用 JSAPI 支付（受限）；小程序微信支付最顺滑；App 需开放平台接入
8. 包体积 —— H5 无严格限制；小程序主包 2MB（可分包 20MB+）；App 数百 MB 无压力
```

典型选型结论：

```text
什么时候选什么：
1. 低频工具、内容展示、营销活动 -> H5（成本最低，可嵌入公众号/App WebView）
2. 需要微信生态流量、支付、消息触达 -> 小程序（电商、生活服务、社区、工具）
3. 高频使用、强离线、复杂交互、硬件能力 -> 原生 App 或 App+小程序组合
4. 成熟业务多端覆盖 -> App 承载核心体验，小程序承接微信流量，H5 做活动页
```

本知识库的场景设定为：小程序承担 C 端用户入口，SpringBoot 提供业务 API，Vue 搭建管理后台（B 端运营），三者组成完整的业务闭环。这是国内中小团队最主流的技术组合。

## 学习路线规划

学习微信小程序全栈，建议按「基础 → 进阶 → 业务能力 → 工程化 → 全栈 → 上线运营」六个阶段推进：

```text
阶段一：基础（注册、工具、语法）
1. 注册小程序账号，获取 AppID，安装微信开发者工具
2. 掌握 WXML 模板语法（数据绑定、条件渲染、列表渲染、事件）
3. 掌握 WXSS 样式（rpx、Flex、Grid、选择器）
4. 掌握 JS 逻辑层（App/Page 注册、生命周期、模块化、WXS）
5. 跑通第一个「请求后台数据并渲染」的页面

阶段二：进阶（组件与 API）
1. 熟练使用内置组件（视图容器、表单、导航、媒体）
2. 掌握自定义组件（Component、组件通信、behaviors、插槽）
3. 掌握核心 API（网络请求、存储、路由、界面交互）
4. 学习分包加载与性能优化（setData 优化、启动优化）

阶段三：业务能力（微信开放能力）
1. 登录体系（wx.login + code2session + token）
2. 微信支付（统一下单 + wx.requestPayment + 回调）
3. 订阅消息（前端订阅 + 服务端下发）
4. 分享、客服、扫码等开放能力

阶段四：工程化（测试与质量）
1. 单元测试（miniprogram-simulate + Jest）
2. 集成测试与自动化（miniprogram-automator）
3. 真机调试与性能分析
4. 安全与合规（内容安全、隐私协议、审核规范）

阶段五：全栈（后台与管理端）
1. SpringBoot 后台（分层架构、统一返回、异常处理、参数校验）
2. 认证与安全（JWT、Spring Security、接口签名、RBAC）
3. 微信集成服务端（access_token、登录对接、支付服务端、订阅消息服务端）
4. Vue 管理后台（Vue3 + Element Plus、路由权限、Pinia、axios 封装）

阶段六：上线运营（联调、部署、发布）
1. 前后端联调（API 设计、Swagger、抓包、跨域、环境管理）
2. 部署运维（服务器、域名、HTTPS、Nginx、Docker、CI/CD）
3. 发布上线（提审、灰度、发布、回滚、监控告警）
4. 全栈项目实战（电商、社区、预约、工具类）
```

本知识库的 24 个篇章与上述六个阶段一一对应：01-08 篇章覆盖阶段一二，09-12 篇章覆盖阶段三，13-16 篇章覆盖阶段四，17-20 篇章覆盖阶段五，21-24 篇章覆盖阶段六。

## 开发者资质与主体类型

注册小程序前需要明确账号主体，主体类型决定可用能力与认证流程。微信小程序支持以下主体：

```text
小程序主体类型：
1. 个人 —— 门槛最低，身份证即可注册；不能开通微信支付、部分类目受限（不能做电商交易/虚拟支付）
2. 企业 —— 最常用主体；营业执照注册，可开通支付、几乎所有类目；需对公账户验证
3. 个体工商户 —— 营业执照注册；可开通支付，类目较企业少
4. 政府/事业单位 —— 特殊主体；适合政务民生类小程序
5. 其他组织 —— 社会团体、民办非企业等，按组织类型提供资质
```

主体类型的选择直接影响后续能力：

```text
主体类型对能力的影响：
1. 微信支付 —— 仅企业、个体工商户、政府等非个人主体可开通
2. 类目范围 —— 个人主体类目少（工具、生活服务等部分类目），企业主体类目全
3. 认证标识 —— 企业可做微信认证（300 元/年），获得认证标识与更多接口权限
4. 名称保护 —— 认证后名称受保护，他人不可冒用
5. 广告流量主 —— 需主体为非个人，且满足流量要求
```

注册流程要点：

```text
注册步骤：
1. 访问微信公众平台（mp.weixin.qq.com）注册小程序账号
2. 选择主体类型，填写主体信息（个人身份证 / 企业营业执照等）
3. 完成主体验证（个人人脸识别 / 企业打款验证或法人微信验证）
4. 获取 AppID 与 AppSecret（AppSecret 用于后台调用微信接口，需妥善保管）
5. 根据业务选择类目，提交类目资质（部分类目需额外证件）
6. 下载安装微信开发者工具，用 AppID 创建项目
```

企业主体的微信认证（每年 300 元）会解锁更多能力：自定义菜单（小程序可配置更多入口）、获取用户 UnionID（多平台账号打通）、部分受限类目与接口权限。个人开发者如果业务涉及交易，需要以企业/个体工商户主体重新注册。

## 应用场景实战

### 场景一：从零注册一个企业小程序账号

以企业主体注册小程序为例，完整流程：

```text
步骤：
1. 打开 mp.weixin.qq.com，点击「立即注册」，选择「小程序」
2. 填写未注册过微信公众平台的邮箱，设置密码，激活邮箱
3. 选择主体类型为「企业」，填写企业名称、统一社会信用代码
4. 验证方式二选一：对公账户打款验证（小额随机金额）或法人微信扫码验证
5. 注册成功后进入小程序后台，在「设置 - 基本设置」查看 AppID
6. 在「开发 - 开发设置」生成 AppSecret，妥善保存（后台 code2session 等接口要用）
7. 在「设置 - 基本设置 - 服务类目」选择业务类目（如电商平台需要相应资质）
8. 如需微信支付，在「微信支付」入口申请商户号（需对公账户、营业执照等资质）
```

验证方式对比：对公打款验证需要企业有对公账户，验证周期 1-3 个工作日；法人微信验证即时完成，但需要法人本人微信操作。小团队通常选法人微信验证。

### 场景二：用开发者工具创建第一个 Hello World 项目

注册完成后，用 AppID 创建项目：

```text
步骤：
1. 下载微信开发者工具（稳定版），安装
2. 打开工具，选择「小程序」项目类型，点击「+」新建项目
3. 项目名称填「hello-miniprogram」，目录选本地空文件夹
4. AppID 填刚注册的 AppID（也可选「测试号」免注册体验）
5. 选择「不使用云服务」或「使用云开发」模板（本知识库默认不使用云开发，用自有 SpringBoot 后台）
6. 创建后项目自动生成 app.js / app.json / app.wxss / pages/index 等文件
7. 修改 pages/index/index.wxml，写入 <text>Hello WeChat</text>
8. 点击「编译」，模拟器显示 Hello WeChat
9. 点击「预览」，生成二维码，手机微信扫码真机预览
```

```text
生成的项目结构：
hello-miniprogram/
├── app.js                # 小程序逻辑入口（App 实例）
├── app.json              # 全局配置（页面注册、窗口、tabBar）
├── app.wxss              # 全局样式
├── project.config.json   # 开发者工具项目配置
├── sitemap.json          # 微信搜索收录配置
└── pages/
    └── index/            # 页面目录
        ├── index.js      # 页面逻辑
        ├── index.json    # 页面配置
        ├── index.wxml    # 页面结构
        └── index.wxss    # 页面样式
```

这个骨架就是后续所有篇章的基础：app.json 注册页面与全局配置，页面四件套承载结构与逻辑，wx.* API 连接微信能力，wx.request 对接 SpringBoot 后台。

## 最佳实践与踩坑记录

### 最佳实践

1. 个人开发者先规划好业务是否涉及交易、支付，涉及就提前准备企业/个体工商户主体，避免后期换号迁移成本
2. AppSecret 只存在服务端（SpringBoot 配置中心/环境变量），严禁写进小程序代码或提交到 Git 仓库
3. 项目创建初期就建立目录规范（pages/、components/、utils/、api/、static/），避免后期重构
4. 使用 Git 管理小程序代码，project.config.json 中设置 appid 用占位或本地配置，避免团队协作冲突
5. 学习阶段直接用测试号或自有 AppID 练手，生产环境再按主体要求注册正式账号
6. 起步先不用跨端框架（Taro/uni-app），直接学原生小程序，理解 WXML/WXSS 与双线程模型后再引入框架更扎实

### 踩坑记录

坑 1：个人主体注册后无法开通微信支付
结论：个人主体小程序不能开通微信支付，也不能做虚拟支付类业务。
原因：微信支付仅对企业、个体工商户等非个人主体开放，个人主体类目也不含电商交易类。
解法：业务涉及交易，注册前就选企业/个体工商户主体；已注册个人号的，用企业主体重新注册新号。

坑 2：AppSecret 泄露导致接口被恶意调用
结论：AppSecret 泄露后，攻击者可伪造 access_token 调用微信接口（如订阅消息群发）。
原因：AppSecret 相当于服务端调用微信接口的凭证，写进前端代码等于公开。
解法：立即在后台重置 AppSecret；小程序端只保留 AppID；所有微信接口调用放 SpringBoot 服务端。

坑 3：注册时选错主体类型，后期无法变更
结论：小程序主体类型注册后不可变更。
原因：平台规定主体信息（个人/企业/其他）一旦确认不能修改，只能注销重开。
解法：注册前确认清楚业务形态；企业有多个关联主体时确认用哪个主体注册。

坑 4：企业认证未做，部分接口权限拿不到
结论：未做微信认证的小程序无法使用部分能力（如获取用户 UnionID、部分类目接口）。
原因：平台将认证作为能力门槛，未认证主体能力受限。
解法：业务需要就做 300 元/年的微信认证；个人主体无法认证，需升级为企业主体。

坑 5：AppID 填了测试号，上线时才发现接口权限不对
结论：测试号只能本地调试，不能上传发布，也没有正式接口权限。
原因：测试号是微信提供的免注册体验环境，能力与正式号不同。
解法：开发第一天就用正式 AppID（未认证也能开发调试），测试号只用于临时体验。

坑 6：开发工具版本与基础库版本不一致导致真机表现不同
结论：模拟器运行正常，真机上组件样式或 API 行为不一致。
原因：开发者工具基础库版本与用户手机微信基础库版本存在差异。
解法：在 app.json 或后台设置最低基础库版本；用 canIUse 做能力检测；多台真机预览验证。
