## 概述

微信开放接口（Open API）是服务端与微信能力交互的唯一通道：登录换 openid、订阅消息下发、内容安全检查、用户手机号获取等，全部通过 https://api.weixin.qq.com 下的 REST 接口完成。绝大多数开放接口要求携带 access_token 作为调用凭证，access_token 的管理质量直接决定整个后台的稳定性——它是 2 小时有效期的全局唯一凭证，获取频率受限，一旦管理不当就会出现全站接口报错。

本章围绕 SpringBoot 服务端如何稳定地调用微信开放接口展开：access_token 的获取、缓存与提前刷新；统一 API 客户端封装；错误码识别与自动恢复；频率限制与退避重试。这套「缓存 + 封装 + 重试」体系是 19.2 登录对接、19.4 订阅消息服务端等所有微信集成的公共底座。

```text
微信开放接口调用的核心要点：
1. access_token 是调用大多数接口的全局唯一凭证，2 小时有效，每日获取上限约 2000 次
2. access_token 必须缓存（Redis）并提前刷新（约 1.5 小时），禁止每请求实时获取
3. 多实例部署时通过分布式锁保证同一时刻只有一个实例去微信刷新
4. 统一封装 WechatApiClient，access_token 自动注入，调用方零感知
5. 错误码区分「可自愈」（40001/42001 刷新重试）与「不可自愈」（45009 退避等待）
6. 频率限制配合指数退避重试 + 熔断，防止重试风暴打爆配额
```

## access_token 管理

access_token 是小程序调用微信开放接口的通行证，由 AppID + AppSecret 换取。获取接口：

```text
GET https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&appid=APPID&secret=APPSECRET
```

成功响应：

```json
{
  "access_token": "75_xxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "expires_in": 7200
}
```

失败响应形如：

```json
{
  "errcode": 40001,
  "errmsg": "invalid credential, access_token is invalid or not latest"
}
```

access_token 有四个必须正视的特性：

```text
access_token 的四个特性：
1. 有效期 2 小时（7200 秒），过期后所有携带它的接口调用全部失败
2. 全局唯一 —— 同一小程序同时只能有一个有效 access_token，后获取的会使先获取的失效
3. 获取有频率限制 —— 官方限制每日获取 2000 次，超限当天无法再获取
4. 获取接口本身不限制并发，但并发获取会造成 token 互相顶替失效，引发连锁报错
```

因此服务端必须做「获取一次、缓存复用、提前刷新」。核心策略：

```text
access_token 缓存策略：
1. 获取成功后写入 Redis，TTL 设为 5400 秒（1.5 小时），比官方有效期提前 30 分钟过期
2. 每次取用先读 Redis，命中直接返回，避免重复请求微信
3. Redis 中 token 过期（或不存在）时，才触发一次真实获取
4. 多实例部署时用 Redis SETNX 分布式锁，保证只有一个实例去微信刷新
5. 若微信返回 40001/42001（token 失效），主动删除缓存并刷新一次后重试
```

SpringBoot 实现一个线程安全的 access_token 服务（单实例场景）：

```java
package com.example.wechat.service;

import com.example.wechat.exception.WechatApiException;
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.http.ResponseEntity;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestTemplate;

import java.time.Duration;

@Slf4j
@Service
public class WechatAccessTokenService {

    private static final String TOKEN_KEY = "wechat:access_token";
    private static final String TOKEN_LOCK_KEY = "wechat:access_token:lock";
    /** 缓存 5400 秒（1.5 小时），比官方 7200 秒提前 30 分钟过期，留足刷新余量 */
    private static final long CACHE_TTL_SECONDS = 5400L;

    private final RestTemplate restTemplate;
    private final StringRedisTemplate redisTemplate;
    private final ObjectMapper objectMapper;

    @Value("${wechat.appid}")
    private String appid;

    @Value("${wechat.secret}")
    private String secret;

    public WechatAccessTokenService(RestTemplate restTemplate,
                                    StringRedisTemplate redisTemplate,
                                    ObjectMapper objectMapper) {
        this.restTemplate = restTemplate;
        this.redisTemplate = redisTemplate;
        this.objectMapper = objectMapper;
    }

    /** 获取 access_token：优先读缓存，未命中才触发刷新 */
    public String getAccessToken() {
        String cached = redisTemplate.opsForValue().get(TOKEN_KEY);
        if (cached != null && !cached.isEmpty()) {
            return cached;
        }
        return refreshAccessToken();
    }

    /** 从微信刷新 access_token 并写入 Redis */
    public synchronized String refreshAccessToken() {
        // 双检：进入锁后再次检查，避免重复刷新
        String cached = redisTemplate.opsForValue().get(TOKEN_KEY);
        if (cached != null && !cached.isEmpty()) {
            return cached;
        }
        String url = "https://api.weixin.qq.com/cgi-bin/token"
                + "?grant_type=client_credential&appid=" + appid + "&secret=" + secret;
        try {
            ResponseEntity<String> response = restTemplate.getForEntity(url, String.class);
            JsonNode json = objectMapper.readTree(response.getBody());
            if (json.has("access_token")) {
                String token = json.get("access_token").asText();
                redisTemplate.opsForValue().set(
                        TOKEN_KEY, token, Duration.ofSeconds(CACHE_TTL_SECONDS));
                log.info("access_token 刷新成功，TTL={}s", CACHE_TTL_SECONDS);
                return token;
            }
            throw new WechatApiException(
                    json.get("errcode").asInt(), json.get("errmsg").asText());
        } catch (WechatApiException e) {
            throw e;
        } catch (Exception e) {
            throw new WechatApiException(-1, "获取 access_token 失败: " + e.getMessage());
        }
    }

    /** 主动失效缓存，供 40001/42001 错误处理时强制刷新 */
    public void invalidate() {
        redisTemplate.delete(TOKEN_KEY);
    }
}
```

生产环境通常多实例部署，`synchronized` 只能锁住本机 JVM，跨实例仍需分布式锁。用 Redis SETNX 实现：

```java
/** 多实例安全的刷新（分布式锁版） */
public String refreshAccessTokenDistributed() {
    String cached = redisTemplate.opsForValue().get(TOKEN_KEY);
    if (cached != null && !cached.isEmpty()) {
        return cached;
    }
    // SETNX 抢锁，锁 10 秒自动释放，防止持锁实例宕机造成死锁
    Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(TOKEN_LOCK_KEY, "1", Duration.ofSeconds(10));
    if (!Boolean.TRUE.equals(locked)) {
        // 其他实例正在刷新，短暂等待后重读缓存
        try {
            Thread.sleep(200);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return getAccessToken();
    }
    try {
        // 抢到锁后再次检查，可能上一个持锁者已刷新完成
        cached = redisTemplate.opsForValue().get(TOKEN_KEY);
        if (cached != null && !cached.isEmpty()) {
            return cached;
        }
        return doFetchFromWechat();
    } finally {
        redisTemplate.delete(TOKEN_LOCK_KEY);
    }
}

private String doFetchFromWechat() {
    // 与 refreshAccessToken 中调用微信的部分一致，此处省略重复代码
    return refreshAccessToken();
}
```

要点总结：

```text
access_token 管理要点：
1. 缓存 TTL 设 5400 秒（1.5 小时），永远比官方 7200 秒提前过期，确保刷新发生在失效之前
2. 取用流程永远是「读缓存 → 命中返回 → 未命中才刷新」，99.9% 的请求不碰微信
3. 并发刷新必须加锁：单实例 synchronized，多实例 Redis SETNX
4. 刷新成功立即写缓存；刷新失败抛异常由上层决定是否降级
5. 40001/42001 表示 token 失效，主动 invalidate() 后重试一次
6. 每日 2000 次获取配额：正常缓存策略下每天只消耗个位数次数，配额几乎用不完
```

## API 调用封装

微信开放接口有上百个，如果每个业务方法都自己拼 URL、拼 access_token、解析响应、处理错误码，代码会迅速失控。正确做法是封装一个统一的 `WechatApiClient`，把「注入 access_token、发送请求、解析 JSON、识别错误码」全部收敛到一处，业务代码只关心业务参数。

```text
统一客户端的设计目标：
1. 单一入口 —— 所有微信开放接口调用都走 WechatApiClient，禁止散落 RestTemplate 裸调
2. access_token 自动注入 —— 调用方不用关心 token 从哪来、是否过期
3. 统一错误处理 —— errcode 非 0 统一抛 WechatApiException，业务侧按需捕获
4. 统一日志 —— 记录接口名、耗时、错误码，方便监控与排障
5. 可扩展 —— 新增接口只需加一个方法，复用底层骨架
```

完整实现（SpringBoot + RestTemplate）：

```java
package com.example.wechat.client;

import com.example.wechat.exception.WechatApiException;
import com.example.wechat.service.WechatAccessTokenService;
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.HttpEntity;
import org.springframework.http.HttpHeaders;
import org.springframework.http.MediaType;
import org.springframework.stereotype.Component;
import org.springframework.util.LinkedMultiValueMap;
import org.springframework.util.MultiValueMap;
import org.springframework.web.client.RestTemplate;
import org.springframework.web.util.UriComponentsBuilder;

import java.util.Map;

@Slf4j
@Component
public class WechatApiClient {

    /** 官方开放接口根地址 */
    private static final String API_BASE = "https://api.weixin.qq.com";

    private final RestTemplate restTemplate;
    private final WechatAccessTokenService accessTokenService;
    private final ObjectMapper objectMapper;

    public WechatApiClient(RestTemplate restTemplate,
                           WechatAccessTokenService accessTokenService,
                           ObjectMapper objectMapper) {
        this.restTemplate = restTemplate;
        this.accessTokenService = accessTokenService;
        this.objectMapper = objectMapper;
    }

    /**
     * GET 请求：自动注入 access_token
     * @param path       接口路径，如 /cgi-bin/message/subscribe/send
     * @param params     业务查询参数（不含 access_token）
     */
    public JsonNode get(String path, Map<String, Object> params) {
        String url = buildUrl(path, params, null);
        log.debug("wechat GET {}", url);
        String body = restTemplate.getForObject(url, String.class);
        return parseAndCheck(body);
    }

    /**
     * 原始 URL GET：不注入 access_token，用于 code2session 等「appid+secret 直接换」的接口
     * @param url 完整 URL（已含 appid/secret/js_code 等全部参数）
     */
    public JsonNode getRaw(String url) {
        log.debug("wechat GET(raw) {}", url);
        String body = restTemplate.getForObject(url, String.class);
        return parseAndCheck(body);
    }

    /**
     * POST 请求：自动注入 access_token，JSON 请求体
     * @param path  接口路径
     * @param params 查询参数（不含 access_token）
     * @param requestBody 请求体对象，自动序列化为 JSON
     */
    public JsonNode post(String path, Map<String, Object> params, Object requestBody) {
        String url = buildUrl(path, params, null);
        HttpHeaders headers = new HttpHeaders();
        headers.setContentType(MediaType.APPLICATION_JSON);
        try {
            HttpEntity<String> entity = new HttpEntity<>(
                    objectMapper.writeValueAsString(requestBody), headers);
            log.debug("wechat POST {} body={}", url, objectMapper.writeValueAsString(requestBody));
            String body = restTemplate.postForObject(url, entity, String.class);
            return parseAndCheck(body);
        } catch (WechatApiException e) {
            throw e;
        } catch (Exception e) {
            throw new WechatApiException(-1, "调用微信接口异常: " + e.getMessage());
        }
    }

    /** 拼 URL：统一追加 access_token */
    private String buildUrl(String path, Map<String, Object> params, String tokenOverride) {
        UriComponentsBuilder builder = UriComponentsBuilder.fromHttpUrl(API_BASE + path);
        if (params != null) {
            MultiValueMap<String, String> query = new LinkedMultiValueMap<>();
            params.forEach((k, v) -> query.add(k, String.valueOf(v)));
            builder.queryParams(query);
        }
        String token = tokenOverride != null
                ? tokenOverride : accessTokenService.getAccessToken();
        builder.queryParam("access_token", token);
        return builder.build().toUriString();
    }

    /** 解析响应并统一检查 errcode */
    private JsonNode parseAndCheck(String body) {
        JsonNode json;
        try {
            json = objectMapper.readTree(body);
        } catch (Exception e) {
            throw new WechatApiException(-1, "微信响应解析失败: " + body);
        }
        if (json.has("errcode") && json.get("errcode").asInt() != 0) {
            int errcode = json.get("errcode").asInt();
            throw new WechatApiException(errcode, json.path("errmsg").asText(""));
        }
        return json;
    }
}
```

public class SubscribeMessageService {

要点总结：

```text
API 封装要点：
1. 全部调用收敛到 WechatApiClient，业务层不直接操作 RestTemplate
2. access_token 由客户端统一注入，接口路径 + 业务参数是调用方的全部输入
3. errcode 非 0 统一抛 WechatApiException（含错误码），业务层按码处理
4. 日志记录接口路径、请求体、耗时，为监控和排障留证据
5. 新增接口 = 新增一个方法，复用 get/post 骨架，半小时内可接完一个新接口
6. RestTemplate 需配置合理的连接池与超时（connectTimeout 5s / readTimeout 10s）
```

## 错误码处理

微信开放接口的响应统一为 `{"errcode": 0, "errmsg": "ok"}` 结构（errcode 为 0 表示成功），或业务接口的成功响应不带 errcode。统一客户端已经把所有非 0 错误码转成了异常，业务侧要做的就是「识别错误码、决定怎么恢复」。

先定义异常类型：

```java
package com.example.wechat.exception;

/** 微信开放接口异常，携带 errcode/errmsg */
public class WechatApiException extends RuntimeException {

    private final int errcode;
    private final String errmsg;

    public WechatApiException(int errcode, String errmsg) {
        super("wechat api error: code=" + errcode + ", msg=" + errmsg);
        this.errcode = errcode;
        this.errmsg = errmsg;
    }

    public int getErrcode() {
        return errcode;
    }

    public String getErrmsg() {
        return errmsg;
    }
}
```

服务端日常打交道的高频错误码：

```text
高频错误码速查：
1. 40001 —— invalid credential：access_token 无效或已过期，最常见，刷新后重试即可
2. 40014 —— invalid access_token：token 格式错误或不存在，同样走刷新重试
3. 42001 —— access_token 超时：token 过期，刷新后重试
4. 45009 —— 接口调用超过限额：频率超限，需要退避等待，不可立即重试
5. 40003 —— invalid openid：openid 非法，检查参数来源
6. 41001 —— 缺少 access_token：请求未带 token，封装层 bug
7. 40029 —— invalid code：code 无效或已使用（code2session 场景）
8. 47003 —— 参数不符合要求：订阅消息 data 字段超长或类型不符
9. 43101 —— 用户拒收：用户未订阅或已取消订阅消息授权
10. 45011 —— API 调用太频繁，请稍候再试：业务触发的限流
```

错误码分两类处理策略——「可自愈」与「不可自愈」：

```text
错误码处理策略：
1. 可自愈（40001/40014/42001）：token 失效，invalidate() 清缓存 → 重新获取 → 重试原请求一次
2. 不可自愈（45009/47003/43101 等）：业务或配额问题，重试无意义，直接失败并告警/记录
3. 网络异常（连接超时、5xx）：属于「未知结果」，重试需谨慎，防止重复写数据
4. 统一在 WechatApiClient 层做一次 40001/42001 的自动重试，业务侧零成本自愈
5. 不可自愈错误要有日志 + 监控告警，避免线上静默失败
```

在客户端加入「token 失效自动刷新重试」：

```java
/** 支持 token 失效自动重试的 POST */
public JsonNode postWithAutoRetry(String path, Map<String, Object> params, Object requestBody) {
    try {
        return post(path, params, requestBody);
    } catch (WechatApiException e) {
        if (e.getErrcode() == 40001 || e.getErrcode() == 40014 || e.getErrcode() == 42001) {
            log.warn("access_token 失效（errcode={}），强制刷新后重试一次", e.getErrcode());
            accessTokenService.invalidate();
            return post(path, params, requestBody);
        }
        throw e;
    }
}
```

全局异常兜底（统一返回格式）：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(WechatApiException.class)
    public Result<Void> handleWechatApi(WechatApiException e) {
        log.error("微信接口调用失败: {}", e.getMessage());
        return Result.fail("WECHAT_API_ERROR", "微信接口调用失败，请稍后重试");
    }
}
```

要点总结：

```text
错误码处理要点：
1. errcode 为 0 才是成功，必须解析 JSON 判断，不能只看 HTTP 200
2. 40001/40014/42001 是「token 类」错误，统一走刷新重试，且只重试一次防止死循环
3. 45009 是频率超限，重试只会加重问题，必须退避等待或转异步
4. 业务层只捕获需要关心的错误码，其余交给全局异常处理
5. 所有 errcode 都要落日志，建立错误码监控大盘，异常波动能及时发现
6. 对外返回统一格式，不把微信 errmsg 原文透传给前端（避免泄露内部信息）
```

## 频率限制

微信对开放接口的调用有严格的配额体系。不同接口配额不同，且与账号类型、认证状态、历史调用量挂钩：

```text
接口配额的基本规则：
1. access_token 获取：每日 2000 次，是所有接口中最敏感的配额
2. 订阅消息发送：按小程序账号配置，通常远低于营销类接口的预期量
3. 内容安全检测（msgSecCheck）：有每分钟/每日配额，图片与文本分开计
4. 配额按「自然日」重置，超限后当天无法恢复
5. 部分接口的配额与账号历史调用量、违规情况动态相关，新号配额通常较低
6. 配额用尽返回 45009，需要等到次日或调整调用策略
```

超限（45009）时的处理绝不能是「立即重试」，而是分层策略：

```text
超限处理策略：
1. 识别 45009，停止当前请求的立即重试，避免重试风暴
2. 对可延后的业务（订阅消息、营销通知），转入 MQ 队列延迟执行，避开高峰
3. 对实时业务（内容安全检测），降级为「先放行后补检」或直接拒绝并提示稍后
4. 指数退避重试：第一次等 1s、第二次 2s、第三次 4s……最多 5 次封顶
5. 本地滑动窗口计数，预估配额消耗，剩余不足时提前限流自有入口
6. 配额使用量接入监控告警，消耗超过 80% 时预警，避免打满才发觉
```

指数退避重试的通用实现：

```java
/**
 * 带指数退避的重试封装
 * @param maxAttempts 最大尝试次数（含首次）
 * @param retryableCodes 命中这些错误码才重试（如 45009）
 */
public JsonNode postWithBackoff(String path, Map<String, Object> params,
                                Object requestBody, int maxAttempts,
                                Set<Integer> retryableCodes) {
    int attempt = 0;
    while (true) {
        try {
            return post(path, params, requestBody);
        } catch (WechatApiException e) {
            attempt++;
            boolean retryable = retryableCodes.contains(e.getErrcode());
            if (!retryable || attempt >= maxAttempts) {
                throw e;
            }
            // 指数退避：1s、2s、4s、8s...
            long waitMs = (long) Math.pow(2, attempt - 1) * 1000;
            log.warn("微信接口 errcode={}，{}ms 后进行第 {} 次重试",
                    e.getErrcode(), waitMs, attempt);
            try {
                Thread.sleep(waitMs);
            } catch (InterruptedException ie) {
                Thread.currentThread().interrupt();
                throw new WechatApiException(-1, "重试等待被中断");
            }
        }
    }
}
```

调用示例——订阅消息发送最多重试 3 次，45009 命中退避：

```java
Set<Integer> retryable = Set.of(45009, 45011, -1);  // -1 表示网络类异常
JsonNode result = wechatApiClient.postWithBackoff(
        "/cgi-bin/message/subscribe/send", Map.of(), body, 3, retryable);
```

要点总结：

```text
频率限制要点：
1. 配额按天结算，超限当天不可恢复，必须提前规划调用量
2. 45009 代表配额或频率问题，立即重试是错误做法，退避或异步才是正解
3. 重试上限必须封顶（建议 3-5 次），配合指数退避，防止雪崩
4. 高峰业务主动错峰：定时任务放凌晨，营销消息放低峰
5. 配额消耗要监控：剩余量、单接口调用量、45009 出现次数三个指标必看
6. 缓存 access_token 后每日获取次数个位数，配额瓶颈主要来自业务接口本身
```

### 场景一：搭建统一微信开放接口客户端并接入 Spring 容器

一个完整的生产级配置：RestTemplate 连接池 + 超时 + 客户端 Bean 装配。

```java
package com.example.wechat.config;

import org.apache.hc.client5.http.config.RequestConfig;
import org.apache.hc.client5.http.impl.classic.CloseableHttpClient;
import org.apache.hc.client5.http.impl.classic.HttpClients;
import org.apache.hc.client5.http.impl.io.PoolingHttpClientConnectionManager;
import org.apache.hc.core5.util.Timeout;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.client.HttpComponentsClientHttpRequestFactory;
import org.springframework.web.client.RestTemplate;

@Configuration
public class WechatHttpConfig {

    @Bean
    public RestTemplate wechatRestTemplate() {
        PoolingHttpClientConnectionManager cm = new PoolingHttpClientConnectionManager();
        cm.setMaxTotal(200);           // 连接池总连接数
        cm.setDefaultMaxPerRoute(50);  // 单路由最大连接数

        RequestConfig requestConfig = RequestConfig.custom()
                .setConnectTimeout(Timeout.ofSeconds(5))      // 建连超时
                .setConnectionRequestTimeout(Timeout.ofSeconds(5)) // 从池取连接超时
                .setResponseTimeout(Timeout.ofSeconds(10))    // 读响应超时
                .build();

        CloseableHttpClient httpClient = HttpClients.custom()
                .setConnectionManager(cm)
                .setDefaultRequestConfig(requestConfig)
                .build();

        HttpComponentsClientHttpRequestFactory factory =
                new HttpComponentsClientHttpRequestFactory(httpClient);
        return new RestTemplate(factory);
    }
}
```

应用配置（application.yml）：

```yaml
wechat:
  appid: wx1234567890abcdef        # 小程序 AppID，从 mp.weixin.qq.com 获取
  secret: ${WECHAT_SECRET}          # AppSecret，从环境变量注入，禁止写死
```

至此 WechatAccessTokenService、WechatApiClient 自动注入可用，业务代码只需：

@Service
public class SecurityCheckService {

### 场景二：access_token 防击穿与失效自愈

模拟一个 10 个实例的集群：凌晨缓存全部过期，瞬间涌入 10000 个请求。若每个请求都直接打微信换取 token，10 个实例并发获取会互相顶替，且瞬间消耗大量配额。防击穿方案：

```java
/** 防击穿：缓存未命中时，用分布式锁保护真实刷新，其余请求等待后复用 */
public String getAccessTokenSafe() {
    String cached = redisTemplate.opsForValue().get(TOKEN_KEY);
    if (cached != null && !cached.isEmpty()) {
        return cached;
    }
    // 抢锁（10 秒自动过期兜底）
    Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(TOKEN_LOCK_KEY, "1", Duration.ofSeconds(10));
    if (!Boolean.TRUE.equals(locked)) {
        // 没抢到锁：自旋等待（最多 3 秒），期间其他实例已完成刷新
        for (int i = 0; i < 15; i++) {
            try { Thread.sleep(200); } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                break;
            }
            cached = redisTemplate.opsForValue().get(TOKEN_KEY);
            if (cached != null && !cached.isEmpty()) {
                return cached;
            }
        }
        // 等待超时仍未拿到缓存，兜底直接刷新（概率极低）
        log.warn("等待 access_token 刷新超时，兜底直接获取");
        return doFetchFromWechat();
    }
    try {
        cached = redisTemplate.opsForValue().get(TOKEN_KEY);
        if (cached != null && !cached.isEmpty()) {
            return cached;
        }
        return doFetchFromWechat();
    } finally {
        redisTemplate.delete(TOKEN_LOCK_KEY);
    }
}
```

配合失效自愈：WechatApiClient 捕获 40001/42001 后清缓存重试，两次自愈逻辑叠加后，线上 access_token 问题基本做到「用户无感恢复」。

```text
场景二验证要点：
1. 压测 10 实例并发 10000 请求：微信 token 接口只被调用 1 次，其余 9999 个请求复用缓存
2. 主动清缓存模拟过期：15 秒内所有请求恢复，期间无 45009 报错
3. 注入 40001 模拟 token 被顶替：客户端自动刷新重试，业务成功率保持 100%
4. 监控指标：微信 token 接口日调用量、缓存命中率、自愈重试次数
```

## 最佳实践与踩坑记录

### 最佳实践

1. access_token 永远走 Redis 缓存，TTL 设 5400 秒提前刷新，禁止每次请求实时获取
2. 所有微信开放接口调用收敛到 WechatApiClient 单一入口，禁止业务代码散落 RestTemplate 裸调
3. AppSecret 只存在于服务端配置中心/环境变量，严禁写进代码、配置文件提交 Git 或出现在日志
4. 40001/42001 类错误在客户端层自动「清缓存 + 刷新 + 重试一次」，业务侧零感知自愈
5. 45009 类频率错误走指数退避（1s/2s/4s...封顶 3-5 次）或转异步队列，绝不立即重试
6. 所有 errcode 落日志并建立监控（调用量、错误码分布、45009 次数），异常波动及时告警
7. 接口调用统一配置超时（连接 5s / 读取 10s）与连接池，防止微信抖动拖垮线程池
8. 对外返回统一错误结构，不透传微信 errmsg 原文，避免泄露内部信息与造成前端困惑

### 踩坑记录

```text
坑 1：每个请求都实时获取 access_token，上线当天配额被打爆
结论：接口大面积报 45009，所有依赖 access_token 的接口全部不可用。
原因：没有缓存，每个请求都调用 token 接口，2000 次/日的配额几分钟内耗尽。
解法：access_token 写入 Redis 缓存复用；TTL 5400 秒提前刷新；监控每日获取次数。

坑 2：多实例并发刷新，token 互相顶替导致连锁报错
结论：集群部署后 40001 错误随机爆发，同一时刻部分请求成功部分失败。
原因：每个实例各自缓存各自的 token，后获取的 token 使先获取的失效，两边互踢。
解法：Redis 共享缓存 + SETNX 分布式锁，保证全局只有一个有效 token 和一次刷新。

坑 3：缓存 TTL 与官方有效期设成一样的 7200 秒
结论：缓存恰好过期瞬间，旧 token 已失效，刷新有网络延迟，期间请求全部 40001。
原因：TTL 与 token 生命周期完全对齐，边界时刻没有安全余量。
解法：TTL 设 5400 秒（1.5 小时），比 7200 秒提前 30 分钟过期，保证刷新发生在失效前。

坑 4：只判断 HTTP 200，不解析 errcode，业务数据异常
结论：接口返回 {"errcode":47003,...} 但 HTTP 200，代码误以为成功继续处理。
原因：微信开放接口错误走 HTTP 200 + errcode 非 0 的约定，只看状态码会漏判。
解法：统一客户端解析 JSON，errcode 非 0 一律抛 WechatApiException。

坑 5：AppSecret 提交到了 Git 仓库
结论：公开仓库被扫描工具扒出密钥，攻击者伪造 access_token 滥发订阅消息。
原因：开发时把 secret 写死在 application.yml 并随代码提交。
解法：立即在公众平台重置 AppSecret；改用环境变量/配置中心注入；Git 历史中的密钥一并清理。

坑 6：遇到 45009 立即重试，重试风暴把配额彻底打没
结论：超限后错误率不降反升，直到第二天才恢复。
原因：所有请求同时重试，重试本身又在消耗配额，形成恶性循环。
解法：45009 走指数退避或异步延迟重试；对调用入口做本地限流，超限直接拒绝。

坑 7：access_token 缓存在 JVM 内存而非 Redis
结论：单机正常，多实例时每台机器各刷各的 token，互相顶替，报错随机。
原因：本地缓存无法跨实例共享，违背「全局唯一」原则。
解法：统一存 Redis；JVM 内最多做二级缓存且必须设极短 TTL 与失效广播。

坑 8：restTemplate 无超时配置，微信抖动时线程全部挂起
结论：微信接口慢响应导致 Tomcat 线程池耗尽，整个服务不可用。
原因：默认 RestTemplate 无超时，连接一直挂着等待。
解法：配置 connectTimeout 5s / readTimeout 10s 与连接池；超时异常按「未知结果」处理并告警。
```
