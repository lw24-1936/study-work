## 概述

订阅消息是服务端主动触达用户的官方通道：订单状态变更、预约提醒、活动通知等场景，服务端可以下发一条微信消息，用户在小程序「服务通知」里查看。它的核心机制是「用户授权一次，服务端发送一条」——用户必须在小程序内通过 wx.requestSubscribeMessage 明确订阅过对应模板，服务端才有权下发，且一次性订阅的授权不能复用。整个下发链路对服务端的正确性要求很高：模板 ID 管理、字段格式、异步发送、失败重试、发送记录、拒收处理，缺一环都会导致「发不出」或「乱发」。

本章覆盖订阅消息服务端的完整实现：模板的申请与集中管理、消息发送 API 与 data 字段格式、基于 MQ 的异步发送与失败重试、任务调度兜底、发送记录表设计，以及频率限制与用户拒收的应对策略。

```text
订阅消息服务端的核心要点：
1. 模板在 mp.weixin.qq.com 后台申请，拿到 template_id 后集中管理，不散落代码
2. 发送接口 POST /cgi-bin/message/subscribe/send，需携带 access_token
3. data 字段按模板占位符（{{thing1.DATA}}）填充，thing 类型限 20 字、time 限特定格式
4. 发送走异步（MQ 队列）+ 失败重试 + 指数退避，不阻塞业务主流程
5. 每次发送落日志表，记录状态与错误码，支持追踪与统计
6. 43101 表示用户拒收/未订阅，需给用户打标停止发送，并引导重新订阅
```

## 模板管理

订阅消息模板在微信公众平台申请：登录 mp.weixin.qq.com → 「订阅消息」→ 「公共模板库」挑选或「选用模板」，审核通过后获得模板 ID。模板内容含关键字占位符，如：

```text
订单发货通知
{{thing1.DATA}} 发货提醒：您的订单已发货，请注意查收
{{time2.DATA}} 发货时间
{{thing3.DATA}} 快递公司
{{character_string4.DATA}} 快递单号
点击查看订单详情
```

模板选择要点：

```text
模板选择要点：
1. 从公共模板库挑选，关键词类型与业务字段一一对应（thing/time/number/character_string/amount/phone 等）
2. 每个模板最多 5 个关键字，字段顺序与类型申请后固定，不可随意增删
3. 模板审核需 1-3 个工作日，生产模板要提前申请，测试阶段用「测试模板」
4. 一个账号可申请多个模板，但每个模板有使用限制（一次性订阅/长期订阅）
5. 模板内容与关键字一旦审核通过，修改需重新审核，尽量一次设计到位
6. 模板 ID 要进配置/数据库管理，禁止硬编码在业务代码里
```

## 消息发送

发送接口定义：

```text
POST https://api.weixin.qq.com/cgi-bin/message/subscribe/send?access_token=ACCESS_TOKEN
```

请求体：

```json
{
  "touser": "oXk5v5FjYtUqM-xxxxxxxxxxxx",
  "template_id": "Tmpl-xxxxxxxxxxxxxxxxxxxxxxxx",
  "page": "pages/order/detail?id=1001",
  "data": {
    "thing1": { "value": "您的订单已发货" },
    "time2": { "value": "2026-08-20 10:30" },
    "thing3": { "value": "顺丰速运" },
    "character_string4": { "value": "SF1234567890" }
  },
  "miniprogram_state": "formal",
  "lang": "zh_CN"
}
```

data 字段类型与长度限制（最常见报错来源）：

```text
data 字段类型规范：
1. thing —— 20 个以内字符，不能含特殊符号（如 emoji、表情），最常用
2. time —— 固定格式：yyyy-MM-dd HH:mm 或 yyyy-MM-dd，或 "15:01"（time 类）
3. number —— 数字字符串，10 个以内字符
4. character_string —— 32 个以内字符，适合单号、订单号
5. amount —— 金额，1 个小数点，10 个以内字符，如 "99.50"
6. phrase —— 5 个以内汉字或 17 个英文字符
7. 超长或类型不符返回 47003，发送前本地校验能拦截大部分错误
```

服务端发送实现（同步版本 + 字段校验）：

```java
package com.example.message.service;

import com.example.wechat.client.WechatApiClient;
import com.example.wechat.exception.WechatApiException;
import com.fasterxml.jackson.databind.JsonNode;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;

import java.util.LinkedHashMap;
import java.util.Map;

@Slf4j
@Service
public class SubscribeMessageService {

    private static final String SEND_PATH = "/cgi-bin/message/subscribe/send";
    private static final int THING_MAX_LENGTH = 20;
    private static final int CHAR_STRING_MAX_LENGTH = 32;

    private final WechatApiClient wechatApiClient;

    @Value("${wechat.env:formal}")
    private String env;   // developer / trial / formal，与小程序版本对应

    public SubscribeMessageService(WechatApiClient wechatApiClient) {
        this.wechatApiClient = wechatApiClient;
    }

    /**
     * 发送订阅消息
     * @param openid     接收用户 openid
     * @param templateId 模板 ID
     * @param dataMap    占位符数据：key 为 thing1/time2 等，value 为业务值
     * @param page       点击消息跳转的小程序页面路径
     */
    public void send(String openid, String templateId,
                     Map<String, String> dataMap, String page) {
        Map<String, Object> body = new LinkedHashMap<>();
        body.put("touser", openid);
        body.put("template_id", templateId);
        if (page != null && !page.isEmpty()) {
            body.put("page", page);
        }
        // data 组装：{ "thing1": { "value": "xxx" } }
        Map<String, Object> data = new LinkedHashMap<>();
        for (Map.Entry<String, String> entry : dataMap.entrySet()) {
            String value = normalizeValue(entry.getKey(), entry.getValue());
            Map<String, String> item = new LinkedHashMap<>();
            item.put("value", value);
            data.put(entry.getKey(), item);
        }
        body.put("data", data);
        body.put("miniprogram_state", env);
        body.put("lang", "zh_CN");

        JsonNode result = wechatApiClient.post(SEND_PATH, Map.of(), body);
        log.info("订阅消息发送成功 openid={} templateId={}", openid, templateId);
    }

    /** 按占位符类型做长度校验与截断，避免 47003 */
    private String normalizeValue(String key, String value) {
        if (value == null) {
            return "";
        }
        if (key.startsWith("thing")) {
            // thing 类型最多 20 字，超出截断
            return value.length() > THING_MAX_LENGTH
                    ? value.substring(0, THING_MAX_LENGTH) : value;
        }
        if (key.startsWith("character_string")) {
            return value.length() > CHAR_STRING_MAX_LENGTH
                    ? value.substring(0, CHAR_STRING_MAX_LENGTH) : value;
        }
        return value;
    }
}
```

要点总结：

```text
消息发送要点：
1. 发送接口需要 access_token，走 19.1 的统一 WechatApiClient 自动注入
2. data 的 key 必须与模板占位符一致（thing1/time2/...），value 符合类型长度限制
3. page 必须以 pages/ 开头，可带查询参数；为空则不跳转
4. miniprogram_state 区分环境：formal 线上、trial 体验版、developer 开发版
5. 发送前本地校验字段长度，把 47003 拦截在调用微信之前
6. 发送结果以 errcode 判断：0 成功；43101 拒收；47003 参数错误；45009 频率超限
```

## 任务调度与异步发送

订阅消息发送不应阻塞业务主流程：用户下单成功后，同步逻辑只负责「把发送任务落库 + 丢进 MQ」，真正调微信的消费者异步执行。这样微信接口抖动、频率超限都不会拖慢主链路。

```text
异步发送架构：
1. 业务侧（下单/发货/退款）只做：组装消息任务 → 落库（待发送）→ 发 MQ
2. MQ 消费者：取任务 → 发送 → 更新状态与结果
3. 失败重试：可重试错误（45009 频率、网络异常）指数退避后重新入队，上限 5 次
4. 不可重试错误（43101 拒收、47003 参数）直接标记失败，不再重试
5. 定时任务兜底：扫描滞留的「重试中」任务，防止 MQ 消息丢失导致漏发
6. 任务表与发送日志表分离：任务表管流程，日志表管审计
```

业务侧入队：

```java
package com.example.message.mq;

import lombok.extern.slf4j.Slf4j;
import org.springframework.amqp.rabbit.core.RabbitTemplate;
import org.springframework.stereotype.Service;

import java.util.Map;

@Slf4j
@Service
public class SubscribeMessageProducer {

    public static final String EXCHANGE = "wechat.subscribe.exchange";
    public static final String ROUTING_KEY = "subscribe.send";

    private final RabbitTemplate rabbitTemplate;
    private final SubscribeMessageTaskMapper taskMapper;

    public SubscribeMessageProducer(RabbitTemplate rabbitTemplate,
                                    SubscribeMessageTaskMapper taskMapper) {
        this.rabbitTemplate = rabbitTemplate;
        this.taskMapper = taskMapper;
    }

    /** 业务侧调用：创建发送任务并入队（不阻塞主流程） */
    public Long enqueue(String openid, String templateId, String scene,
                        Map<String, String> data, String page) {
        // 1. 任务落库
        SubscribeMessageTask task = new SubscribeMessageTask();
        task.setOpenid(openid);
        task.setTemplateId(templateId);
        task.setScene(scene);
        task.setDataJson(writeJson(data));
        task.setPage(page);
        task.setStatus(0);   // 待发送
        taskMapper.insert(task);
        // 2. 丢进 MQ
        rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, task.getId());
        log.info("订阅消息任务入队 taskId={} openid={} templateId={}",
                task.getId(), openid, templateId);
        return task.getId();
    }
}
```

消费者与重试：

```java
package com.example.message.mq;

import lombok.extern.slf4j.Slf4j;
import org.springframework.amqp.rabbit.annotation.RabbitListener;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;
import java.util.Map;

@Slf4j
@Component
public class SubscribeMessageConsumer {

    private static final int MAX_RETRY = 5;
    private static final int RETRY_BASE_SECONDS = 60;   // 退避基数：1 分钟起

    private final SubscribeMessageTaskMapper taskMapper;
    private final SubscribeMessageService messageService;
    private final RabbitTemplate rabbitTemplate;

    @RabbitListener(queues = "wechat.subscribe.queue")
    public void consume(Long taskId) {
        SubscribeMessageTask task = taskMapper.selectById(taskId);
        if (task == null) {
            log.warn("订阅消息任务不存在 taskId={}", taskId);
            return;
        }
        task.setStatus(1);   // 发送中
        taskMapper.updateById(task);
        try {
            Map<String, String> data = parseData(task.getDataJson());
            messageService.send(task.getOpenid(), task.getTemplateId(), data, task.getPage());
            task.setStatus(2);   // 成功
            taskMapper.updateById(task);
        } catch (WechatApiException e) {
            handleFailure(task, e.getErrcode(), e.getErrmsg());
        } catch (Exception e) {
            handleFailure(task, -1, e.getMessage());
        }
    }

    /** 失败分类处理：可重试的退避重投，不可重试的直接失败 */
    private void handleFailure(SubscribeMessageTask task, int errcode, String errmsg) {
        boolean retryable = errcode == 45009 || errcode == 45011 || errcode == -1;
        if (retryable && task.getRetryCount() < MAX_RETRY) {
            int next = task.getRetryCount() + 1;
            // 指数退避：1 分钟、2 分钟、4 分钟…… 上限 5 次
            long delaySeconds = (long) Math.pow(2, task.getRetryCount()) * RETRY_BASE_SECONDS;
            task.setRetryCount(next);
            task.setStatus(4);   // 重试中
            task.setNextRetryAt(LocalDateTime.now().plusSeconds(delaySeconds));
            task.setErrcode(errcode);
            task.setErrmsg(truncate(errmsg));
            taskMapper.updateById(task);
            log.warn("订阅消息发送失败，{} 秒后重试 taskId={} errcode={}",
                    delaySeconds, task.getId(), errcode);
            // 延迟重投（RabbitMQ 延迟队列或定时扫描兜底，二选一）
            rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY_DELAY,
                    task.getId(), message -> {
                        message.getMessageProperties().setDelay((int) (delaySeconds * 1000));
                        return message;
                    });
        } else {
            task.setStatus(3);   // 失败
            task.setErrcode(errcode);
            task.setErrmsg(truncate(errmsg));
            taskMapper.updateById(task);
            log.error("订阅消息发送最终失败 taskId={} errcode={} errmsg={}",
                    task.getId(), errcode, errmsg);
            // 失败告警（钉钉/邮件），人工介入
            alertService.alert("订阅消息发送失败", task.getId() + " " + errmsg);
        }
    }
}
```

定时任务兜底（防止 MQ 消息丢失导致任务永远滞留）：

```java
package com.example.message.job;

import lombok.extern.slf4j.Slf4j;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;
import java.util.List;

@Slf4j
@Component
public class SubscribeMessageRetryJob {

    private final SubscribeMessageTaskMapper taskMapper;
    private final RabbitTemplate rabbitTemplate;

    /** 每 5 分钟扫描一次「重试中」且已到重试时间的任务，重新入队 */
    @Scheduled(fixedDelay = 5 * 60 * 1000)
    public void scanRetryTasks() {
        List<SubscribeMessageTask> tasks = taskMapper.selectByStatusAndTime(
                4, LocalDateTime.now(), 100);   // status=4 重试中, next_retry_at <= now
        for (SubscribeMessageTask task : tasks) {
            log.info("定时兜底重新入队 taskId={} retryCount={}",
                    task.getId(), task.getRetryCount());
            rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, task.getId());
        }
    }

    /** 每天凌晨扫描超过 24 小时仍未完成的「待发送」任务，补投一次 */
    @Scheduled(cron = "0 30 1 * * ?")
    public void scanStuckTasks() {
        List<SubscribeMessageTask> tasks = taskMapper.selectStuck(LocalDateTime.now().minusHours(24));
        for (SubscribeMessageTask task : tasks) {
            log.warn("发现滞留任务，重新入队 taskId={}", task.getId());
            rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, task.getId());
        }
    }
}
```

要点总结：

```text
任务调度与异步发送要点：
1. 发送必须异步：主流程只落库 + 发 MQ，微信抖动不影响下单等核心链路
2. 失败分类：45009/网络异常可重试，43101/47003 不可重试，直接失败
3. 重试指数退避（1m/2m/4m/8m/16m），上限 5 次，超过转人工告警
4. 延迟重投与定时扫描双保险，防止 MQ 消息丢失造成漏发
5. 任务表记录完整状态机：待发送 → 发送中 → 成功/失败/重试中
6. 幂等：同一 taskId 只发送一次，消费者重复投递时先查状态再决定是否发送
```

## 发送记录

每一次发送都要留痕：发了什么、给谁、结果如何。发送记录表既是审计依据，也是排查「用户为什么没收到」的第一现场。

```sql
CREATE TABLE `t_subscribe_message_log` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `task_id`       BIGINT          DEFAULT NULL COMMENT '关联任务 ID',
  `openid`        VARCHAR(64)     NOT NULL COMMENT '接收用户 openid',
```

## 频率限制与用户拒收

订阅消息不是营销群发通道，平台对其有严格的限制，服务端必须正视两类约束：接口频率与用户意愿。

```text
频率与配额规则：
1. 接口频率：发送接口有账号级配额，超限返回 45009（一天内不可恢复，需退避）
2. 一次性订阅：用户每授权一次，服务端可发送一条；发完即止，再次发送需重新授权
3. 长期订阅：仅政务民生、医疗、交通、金融等特定类目可申请，授权一次长期可发（有次数限制）
4. 用户可随时在「设置-订阅消息」中取消订阅某模板，取消后发送返回 43101
5. 43101 不重试：用户意愿问题，重试无意义且浪费配额
6. 每个用户每模板的发送次数要本地计数，防止「授权一次发多条」违规
```

用户授权计数管理：

```java
package com.example.message.service;

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

import java.time.Duration;

/**
 * 用户订阅授权计数：一次性订阅「授权一次 = 可发一条」
 */
@Service
public class SubscribeQuotaService {

    private static final String QUOTA_KEY = "wechat:sub_quota:";
    private static final Duration QUOTA_TTL = Duration.ofDays(30);

    private final StringRedisTemplate redisTemplate;

    /** 用户授权一次：计数 +1（前端 wx.requestSubscribeMessage 成功后回调服务端） */
    public void grant(String openid, String templateId) {
        String key = QUOTA_KEY + openid + ":" + templateId;
        Long count = redisTemplate.opsForValue().increment(key);
        if (count != null && count == 1) {
            redisTemplate.expire(key, QUOTA_TTL);
        }
    }

    /** 发送前检查：还有没有可用的发送次数 */
    public boolean hasQuota(String openid, String templateId) {
        String key = QUOTA_KEY + openid + ":" + templateId;
        String count = redisTemplate.opsForValue().get(key);
        return count != null && Long.parseLong(count) > 0;
    }

    /** 发送成功后扣减一次 */
    public void consume(String openid, String templateId) {
        String key = QUOTA_KEY + openid + ":" + templateId;
        redisTemplate.opsForValue().decrement(key);
    }
}
```

用户拒收（43101）处理：

```java
/** 43101 处理：给用户打拒收标签，后续不再对该用户发该模板 */
public void handleUserRejected(String openid, String templateId) {
    // 1. 拒收标签（Redis 或用户表字段）
    rejectTagService.tag(openid, templateId);
    // 2. 清除该用户该模板的授权计数（即使有剩余授权也不该再发）
    quotaService.clear(openid, templateId);
    // 3. 记录拒收日志，运营看板统计拒收率
    sendLogService.recordReject(openid, templateId);
    // 4. 统计拒收率，超过阈值（如 30%）的模板触发前端引导优化任务
}

/** 业务侧发送前统一入口：先查授权计数与拒收标签 */
public boolean canSend(String openid, String templateId) {
    if (rejectTagService.isRejected(openid, templateId)) {
        return false;   // 已拒收，直接跳过
    }
    return quotaService.hasQuota(openid, templateId);   // 有授权次数才发
}
```

要点总结：

```text
频率与拒收要点：
1. 45009 是账号级配额超限，走退避重试；43101 是用户拒收，不重试
2. 一次性订阅严格「一次授权一条」，本地 Redis 计数强制约束
3. 发送前检查 canSend：无授权、已拒收的用户直接跳过，节省配额
4. 43101 后给用户打标，避免每次任务都对着拒收用户空耗
5. 拒收率高（>30%）的模板要复盘：是不是订阅引导时机不对或内容打扰
6. 长期订阅模板同样受接口频率限制，且申请有类目门槛，不要误当群发通道
```

### 场景二：预约提醒的定时批量推送

预约类业务：用户预约成功后授权「预约提醒」模板，服务端每日定时扫描次日到期的预约，批量推送提醒。批量推送必须控制节奏，避免瞬间打爆接口配额。

```java
/** 每日 9 点：扫描次日预约，逐个推送提醒 */
@Scheduled(cron = "0 0 9 * * ?")
public void sendAppointmentReminders() {
    LocalDate tomorrow = LocalDate.now().plusDays(1);
    List<Appointment> appointments = appointmentMapper.selectByDate(tomorrow);
    int sent = 0;
    for (Appointment appointment : appointments) {
        // 1. 检查用户是否授权且未拒收
        String templateId = templateService.getActiveTemplate("appointment_remind")
                .getTemplateId();
        if (!subscribeQuotaService.canSend(appointment.getOpenid(), templateId)) {
            continue;
        }
        // 2. 组装数据
        Map<String, String> data = new LinkedHashMap<>();
        data.put("thing1", "您有预约即将开始");
        data.put("time2", appointment.getStartTime().format(
                DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm")));
        data.put("thing3", appointment.getServiceName());
        // 3. 入队异步发送（队列天然削峰）
        subscribeMessageProducer.enqueue(
                appointment.getOpenid(), templateId, "appointment_remind",
                data, "pages/appointment/detail?id=" + appointment.getId());
        sent++;
    }
    log.info("预约提醒任务入队完成 共 {} 条", sent);
}
```

```text
场景二验证要点：
1. 批量 1 万条预约：MQ 削峰，微信接口调用平稳，无 45009
2. 授权过期的用户自动跳过，不浪费配额
3. 定时任务失败可重跑：任务表状态保证不会重复发送
4. 发送记录看板：成功率、拒收率、各时段发送量一目了然
5. 长期订阅模板（如医疗类）同一用户可多次提醒，但要控制频次防打扰
```

## 最佳实践与踩坑记录

### 最佳实践

1. 模板 ID 集中入库管理，业务按 scene 取用，换模板只改库不动代码
2. 发送前本地校验字段类型与长度（thing 20 字、character_string 32 字），把 47003 拦截在调微信之前
3. 发送全部走 MQ 异步 + 任务表状态机，主流程永不阻塞
4. 失败分类处理：45009/网络异常退避重试（上限 5 次），43101/47003 直接失败不重试
5. 一次授权一条的计数用 Redis 强约束，canSend 前置检查，杜绝超发
6. 每次发送落日志表（脱敏 + 错误码），支撑排障、运营看板与审计
7. 订阅引导放在关键动作（下单、预约成功）后，用 wx.requestSubscribeMessage 一次引导 1-3 个模板
8. 43101 用户打标 + 拒收率监控，超过阈值复盘模板内容与引导时机

### 踩坑记录

```text
坑 1：用户没订阅就发送，全部返回 43101
结论：发送接口批量报 43101，消息全部失败，配额被白白消耗。
原因：没有记录用户授权状态，直接对所有用户发送。
解法：发送前查授权计数与拒收标签（canSend）；43101 后给用户打标停止发送。

坑 2：一次性订阅当成群发通道，超发被平台处罚
结论：同一用户反复收到同一模板多条消息，被用户投诉，账号能力受限。
原因：无视「一次授权一条」规则，授权一次发多条。
解法：Redis 授权计数强约束，发送一次扣一次；超发日志监控告警。

坑 3：thing 字段超 20 字，发送报 47003
结论：发送失败率 30%+，全部是 47003 参数错误。
原因：动态拼接的内容（如商品名+备注）超过 thing 类型 20 字限制。
解法：发送前按占位符类型本地校验与截断；超长内容精简或拆分到多个字段。

坑 4：time 字段格式错误（带了秒或中文）
结论：报 47003，时间字段被拒。
原因：time 只接受 yyyy-MM-dd HH:mm / yyyy-MM-dd，传了 HH:mm:ss。
解法：统一用 DateTimeFormatter 格式化后再传；本地校验正则。

坑 5：miniprogram_state 用错，测试环境收不到消息
结论：开发版/体验版测试收不到订阅消息，线上正常。
原因：发送时 miniprogram_state 固定为 formal，测试环境消息不会下发到开发版。
解法：按环境配置 state：开发/体验版用 developer/trial，线上用 formal。

坑 6：同步发送阻塞主流程，微信抖动拖垮下单接口
结论：微信接口慢时下单接口耗时从 50ms 涨到 3 秒，超时率飙升。
原因：下单事务里同步调微信发送接口。
解法：发送改异步（MQ + 任务表），主流程只入队，秒回。

坑 7：失败无限重试，重试风暴
结论：微信接口故障时消息堆积，重试请求打满配额，恢复后依然失败。
原因：失败立即重试且无上限，退避策略缺失。
解法：指数退避（1m/2m/4m...）+ 重试上限 5 次 + 定时兜底扫描，超限转人工告警。

坑 8：模板内容改版后，旧代码 data 格式不匹配
结论：模板审核通过后发送突然大面积 47003。
原因：后台改模板关键字顺序/类型，代码仍按旧占位符组装。
解法：模板登记表记录 keyword_spec；模板变更走配置更新流程；上线前用测试模板验证。

坑 9：忽略发送记录，用户说没收到无法排查
结论：客诉「没收到消息」时无据可查，只能口头安抚。
原因：没做发送日志，发送结果无留痕。
解法：每次发送落日志表（openid、模板、数据、状态、errcode、时间），支持按用户/模板快速检索。
```
