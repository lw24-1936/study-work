## 概述

组件库是自定义组件开发的规模化阶段：单个组件解决局部复用，组件库解决整站复用、设计一致性与研发效率。本章先讲组件设计规范（写出高质量、可维护组件的底线），再讲主题定制（CSS 变量、外部样式类、样式隔离三种机制），随后介绍 Vant Weapp、TDesign、WeUI、LinUI 等常用组件库的安装与引入方式，最后讲自建组件库的 npm 发布流程与组件库选型对比。

```text
组件库实践的核心内容：
1. 组件设计规范 —— 单一职责、props 命名、受控与非受控、事件命名 onXxx、组件文档
2. 主题定制 —— CSS 变量、外部样式类、官方样式隔离三种机制
3. 常用组件库 —— Vant Weapp / TDesign / WeUI / LinUI 的安装与 usingComponents 引入
4. 自建组件库 —— 组件目录管理、npm 发布、miniprogram_npm 构建
5. 选型对比 —— 按团队规模、定制需求、设计体系做取舍
6. 落地实战 —— 表单页搭建与主题化自建组件两个完整场景
```

## 组件设计规范

组件设计规范回答「什么样的组件是好组件」。核心原则是单一职责：一个组件只解决一个问题，按钮管点击、弹窗管展示、表单管收集，不要做「万能组件」。props 命名统一使用驼峰（camelCase），在 WXML 中使用时转为 kebab-case（短横线），例如组件属性 `maxCount` 在使用时写作 `max-count`。事件命名统一采用 `onXxx` 前缀（如 `onChange`、`onDelete`），与内置事件（tap、change、input）区分开，父组件通过 `bind:onChange` 监听。受控组件由父组件持有 value 并通过事件回调驱动更新，非受控组件内部自管理状态，一个成熟组件应同时支持两种模式。

```js
// components/stepper/index.js —— 同时支持受控与非受控的步进器组件
Component({
  properties: {
    value: { type: Number, value: 0 },   // 受控值：父组件传入
    min: { type: Number, value: 0 },
    max: { type: Number, value: 99 },
    step: { type: Number, value: 1 },
    disabled: { type: Boolean, value: false }
  },
  data: {
    innerValue: 0                        // 非受控模式下的内部状态
  },
  observers: {
    value(val) {                         // 父组件更新 value 时同步内部显示
      this.setData({ innerValue: val });
    }
  },
  lifetimes: {
    attached() {
      this.setData({ innerValue: this.data.value });
    }
  },
  methods: {
    onChangeTap(e) {
      if (this.data.disabled) return;
      const delta = Number(e.currentTarget.dataset.delta);
      const next = this.data.innerValue + delta * this.data.step;
      if (next < this.data.min || next > this.data.max) {
        // 到达边界时抛出 onLimit 事件，由父组件决定是否提示
        this.triggerEvent('onLimit', { min: this.data.min, max: this.data.max });
        return;
      }
      this.setData({ innerValue: next });
      // 事件名遵循 onXxx 规范，父组件用 bind:onChange 监听
      this.triggerEvent('onChange', { value: next });
    }
  }
});
```

```xml
<!-- components/stepper/index.wxml -->
<view class="stepper">
  <view class="stepper__btn" data-delta="-1" bindtap="onChangeTap">-</view>
  <view class="stepper__value">{{innerValue}}</view>
  <view class="stepper__btn" data-delta="1" bindtap="onChangeTap">+</view>
</view>
```

```css
/* components/stepper/index.wxss */
.stepper { display: flex; align-items: center; }
.stepper__btn {
  width: 60rpx; height: 60rpx; line-height: 60rpx;
  text-align: center; background: #f2f3f5; border-radius: 8rpx;
}
.stepper__value { min-width: 80rpx; text-align: center; }
```

```text
组件设计规范要点：
1. 单一职责 —— 一个组件只做一件事，功能膨胀就拆分
2. props 命名 —— JS 中驼峰 maxCount，WXML 中使用 max-count
3. 受控与非受控 —— 受控组件 value 由父组件持有，事件驱动更新；非受控组件内部自管理
4. 默认值 —— properties 中必须给 value 提供默认值，避免 undefined 参与计算
5. 事件命名 —— 自定义事件统一 onXxx 前缀，与内置事件区分
6. 组件文档 —— 每个组件配套 README，说明 props、事件、插槽、外部样式类与示例
```

## 主题定制

小程序自定义组件的样式默认与外界隔离，这给主题定制带来两个方向：一是通过 CSS 变量（自定义属性）穿透隔离传递主题色，二是通过外部样式类把样式控制权交给使用方。CSS 变量是继承属性，不受样式隔离限制，因此在 `page` 或 `app.wxss` 中定义 `--brand-color` 后，组件内部用 `var(--brand-color)` 即可读取。外部样式类通过 `externalClasses` 声明，使用方传入自定义 class 覆盖组件内部样式。样式隔离通过 `styleIsolation` 控制，可选 `isolated`（默认，互不影响）、`apply-shared`（页面样式可影响组件）、`shared`（双向影响）。

```css
/* app.wxss —— 全局主题变量，作为设计 token 统一管理 */
page {
  --brand-color: #07c160;
  --brand-color-light: #e8f8f0;
  --brand-radius: 12rpx;
  --text-color: #333333;
}
```

```css
/* components/custom-button/index.wxss —— 组件内部消费主题变量 */
.custom-button {
  background: var(--brand-color, #07c160);
  color: #ffffff;
  border-radius: var(--brand-radius, 8rpx);
}
```

```js
// components/custom-button/index.js —— 声明外部样式类
Component({
  externalClasses: ['custom-class', 'custom-icon-class'],
  properties: {
    text: { type: String, value: '' }
  }
});
```

```xml
<!-- 页面中使用：custom-class 覆盖按钮整体样式 -->
<custom-button text="提交" custom-class="page__submit-btn" />
```

```css
/* 页面 wxss */
.page__submit-btn {
  margin-top: 40rpx;
  box-shadow: 0 8rpx 24rpx rgba(7, 193, 96, 0.3);
}
```

```json
// components/custom-button/index.json —— 显式声明样式隔离级别
{
  "component": true,
  "styleIsolation": "isolated"
}
```

```text
主题定制三种机制：
1. CSS 变量 —— 在 page/app.wxss 定义 --xxx，组件内 var(--xxx) 读取；继承属性不受样式隔离限制
2. 外部样式类 —— externalClasses 声明 custom-class，使用方传 class 覆盖样式
3. 样式隔离 —— isolated 默认互不影响；apply-shared 页面样式可进组件；shared 双向影响
4. 旧版 addGlobalClass —— 等价于 apply-shared，新项目直接用 styleIsolation
5. 组件默认值兜底 —— var(--brand-color, #07c160) 第二个参数保证变量缺失时可回退
6. 设计 token 化 —— 颜色、圆角、字号统一收敛为变量表，主题切换只改变量
```

## 常用组件库

微信小程序生态有多个成熟的开源组件库，最常用的是 Vant Weapp（有赞出品，组件最全、star 最多）、TDesign（腾讯设计体系）、WeUI 小程序版（微信官方，样式最贴近原生）、LinUI（国内社区维护）。它们的接入方式高度一致：npm 安装依赖 → 开发者工具「工具 - 构建 npm」→ 在 app.json 或页面 json 的 usingComponents 中按路径注册组件。构建 npm 会在项目根目录生成 miniprogram_npm 目录，这是小程序运行组件库代码的最终形态。

```text
安装组件库通用四步：
1. npm 安装 —— 在项目根目录执行 npm i <组件库包名> -S --production
2. 构建 npm —— 开发者工具菜单「工具 - 构建 npm」（项目需先有 package.json）
3. 注册组件 —— app.json 或页面 json 的 usingComponents 中声明路径
4. 页面使用 —— WXML 中直接写 <van-button>、<t-button> 等自定义标签
```

Vant Weapp 是实战中使用率最高的组件库，安装与引入：

```bash
# 项目根目录初始化并安装（--production 避免把 devDependencies 打进来）
npm init -y
npm i @vant/weapp -S --production
```

```json
// app.json —— 全局注册常用组件（高频组件可全局注册，低频组件建议页面级注册）
{
  "style": "v2",
  "usingComponents": {
    "van-button": "@vant/weapp/button/index",
    "van-field": "@vant/weapp/field/index",
    "van-toast": "@vant/weapp/toast/index",
    "van-cell-group": "@vant/weapp/cell-group/index",
    "van-cell": "@vant/weapp/cell/index"
  }
}
```

```xml
<!-- 页面 WXML 使用 -->
<van-cell-group inset>
  <van-field label="收货人" placeholder="请输入姓名" value="{{name}}" bind:change="onNameChange" />
  <van-field label="手机号" type="number" placeholder="请输入手机号" value="{{phone}}" bind:change="onPhoneChange" />
</van-cell-group>
<van-button type="primary" size="large" loading="{{submitting}}" bind:click="onSubmit">
  提交订单
</van-button>
```

TDesign 小程序与 Vant 的路径结构不同：Vant 是 `@vant/weapp/组件名/index`，TDesign 是 `tdesign-miniprogram/组件名/组件名`，注意区分：

```bash
npm i tdesign-miniprogram -S --production
```

```json
{
  "usingComponents": {
    "t-button": "tdesign-miniprogram/button/button",
    "t-input": "tdesign-miniprogram/input/input",
    "t-toast": "tdesign-miniprogram/toast/toast"
  }
}
```

WeUI 小程序版由微信官方维护，组件前缀为 mp-：

```bash
npm i weui-miniprogram -S --production
```

```json
{
  "usingComponents": {
    "mp-dialog": "weui-miniprogram/dialog/dialog",
    "mp-cells": "weui-miniprogram/cells/cells",
    "mp-form": "weui-miniprogram/form/form"
  }
}
```

LinUI 组件命名以 l- 开头：

```bash
npm i lin-ui -S --production
```

```json
{
  "usingComponents": {
    "l-button": "lin-ui/button/index",
    "l-toast": "lin-ui/toast/index"
  }
}
```

```text
常用组件库速记：
1. Vant Weapp —— 组件最全、文档完善、CSS 变量主题定制，中小团队首选
2. TDesign 小程序 —— 腾讯设计体系出品，设计 token 规范统一，重设计一致性的团队选它
3. WeUI 小程序版 —— 官方出品，样式最贴近微信原生，工具类小程序常用
4. LinUI —— 组件丰富、API 友好，社区维护活跃度一般，适合二次封装
5. 路径差异 —— Vant 用 组件名/index，TDesign/WeUI 用 组件名/组件名，写错必报找不到组件
6. 构建 npm —— 接入任何 npm 组件库都绕不开「工具 - 构建 npm」生成 miniprogram_npm
```

## 自建组件库

当业务组件积累到一定数量，或需要跨项目复用、与设计体系深度绑定，就要把组件抽成自建组件库。起步阶段可以先在项目内建 `components/` 目录统一管理业务组件；规模扩大后发布到 npm（公共或私有仓库），其他项目安装后构建 npm 即可使用。微信官方对 npm 组件包有约定：package.json 中通过 `miniprogram` 字段指定组件入口目录，构建 npm 时微信以该目录作为组件包根路径。

```text
自建组件库两种形态：
1. 项目内组件目录 —— components/ 统一管理，页面 usingComponents 相对路径引用，适合单项目
2. npm 组件包 —— 发布到 npm/私有仓库，多项目复用，需要维护版本与文档
3. 发布路径 —— package.json 声明 miniprogram 字段指向 dist 构建产物
4. 使用路径 —— 安装依赖后构建 npm，usingComponents 写「包名/组件目录」
5. 私有仓库 —— 企业用 verdaccio 等自建 npm 源，包名加 @公司/ 前缀作用域
6. 版本治理 —— 语义化版本号 + changelog，破坏性变更必须升 major
```

自建组件库的 package.json 关键配置：

```json
{
  "name": "@your-team/weapp-ui",
  "version": "1.0.0",
  "description": "团队自建微信小程序组件库",
  "main": "dist/index.js",
  "miniprogram": "dist",
  "files": ["dist", "README.md"],
  "scripts": {
    "build": "node scripts/build.js",
    "publish:patch": "npm version patch && npm run build && npm publish"
  },
  "peerDependencies": {}
}
```

```text
自建组件库目录规范：
weapp-ui/
├── package.json          # miniprogram 字段指向 dist
├── dist/                 # 构建产物（发布内容）
│   ├── index.js
│   ├── button/
│   │   ├── index.js
│   │   ├── index.json
│   │   ├── index.wxml
│   │   └── index.wxss
│   └── toast/
├── src/                  # 源码（wxss 预处理、构建脚本入口）
└── README.md             # 组件库文档：安装、组件清单、主题定制说明
```

使用方接入自建组件库：

```bash
npm i @your-team/weapp-ui -S --production
```

```json
{
  "usingComponents": {
    "wu-button": "@your-team/weapp-ui/button/index"
  }
}
```

```text
构建 npm 背后的机制：
1. 项目根目录 package.json 声明依赖后，工具「构建 npm」执行打包
2. 产物输出到项目根目录 miniprogram_npm/ 下，按包名建目录
3. 使用方 usingComponents 中的「包名/组件目录」对应 miniprogram_npm/包名/组件目录
4. project.config.json 中 packNpmManually 可控制手动指定构建路径
5. 组件包内不要再引用其他 npm 包，避免构建嵌套依赖出错
6. 每次修改组件库重新 publish 后，使用方需重新 install 并构建 npm
```

## 组件库选型对比

选型没有绝对最优，取决于团队规模、设计体系、定制深度与维护成本。大厂或有设计团队的选 TDesign 这类设计体系完整的库；大多数业务团队选 Vant Weapp 图组件全、上手快；强定制、多端复用的团队最终会走向自建。实际工程中最常见的是混合策略：基础组件用成熟库，业务组件自建沉淀。

```text
组件库选型对比：
1. Vant Weapp —— 组件最全、社区最大、文档完善，主题通过 CSS 变量定制，适合大多数业务
2. TDesign 小程序 —— 腾讯设计体系，色彩/字号/间距 token 统一，适合设计一致性要求高的团队
3. WeUI 小程序版 —— 微信官方，样式最贴近原生，适合工具类、轻业务场景
4. LinUI —— 组件丰富 API 友好，但社区活跃度与更新频率一般
5. 自建组件库 —— 完全可控、无第三方包袱，但需要持续投入设计与维护成本
6. 混合策略 —— 成熟库打底 + 业务组件自建沉淀，中小团队最务实的路径
```

```text
选型决策建议：
1. 3 人以下或快速验证业务 —— Vant Weapp 直接上，别自研
2. 有专职设计团队、强品牌视觉 —— TDesign 或自建主题层
3. 组件需求以表单、弹窗、反馈为主 —— Vant Weapp 覆盖最全
4. 需要多端（H5/App）复用组件 —— 直接考虑 Taro/uni-app 生态组件库，绕开原生组件库
5. 业务组件重复出现 2 次以上 —— 抽进自建组件库，与第三方库并存
6. 团队能持续投入维护 —— 自建组件库长期收益最大，否则维护成本会拖垮业务
```

## 应用场景实战

### 场景一：用 Vant Weapp 搭建下单表单页

从零接入 Vant Weapp 并完成一个可提交的下单表单页，包含安装、构建 npm、注册组件与页面完整代码：

```bash
# 1. 项目根目录初始化 npm 并安装 Vant Weapp
npm init -y
npm i @vant/weapp -S --production
# 2. 打开微信开发者工具，菜单「工具 - 构建 npm」，生成 miniprogram_npm 目录
# 3. app.json 添加 "style": "v2" 并全局注册常用组件
```

```json
// app.json
{
  "pages": ["pages/order/order"],
  "style": "v2",
  "usingComponents": {
    "van-field": "@vant/weapp/field/index",
    "van-button": "@vant/weapp/button/index",
    "van-toast": "@vant/weapp/toast/index",
    "van-cell-group": "@vant/weapp/cell-group/index"
  }
}
```

```xml
<!-- pages/order/order.wxml -->
<view class="order-page">
  <van-cell-group inset>
    <van-field
      label="收货人"
      placeholder="请输入姓名"
      value="{{form.name}}"
      bind:change="onFieldChange"
      data-field="name"
    />
    <van-field
      label="手机号"
      type="number"
      maxlength="11"
      placeholder="请输入手机号"
      value="{{form.phone}}"
      bind:change="onFieldChange"
      data-field="phone"
    />
    <van-field
      label="收货地址"
      type="textarea"
      autosize
      placeholder="请输入详细地址"
      value="{{form.address}}"
      bind:change="onFieldChange"
      data-field="address"
    />
  </van-cell-group>

  <van-button
    type="primary"
    size="large"
    round
    loading="{{submitting}}"
    disabled="{{submitting}}"
    bind:click="onSubmit"
  >
    提交订单
  </van-button>
</view>
```

```js
// pages/order/order.js
Page({
  data: {
    form: { name: '', phone: '', address: '' },
    submitting: false
  },
  onFieldChange(e) {
    const field = e.currentTarget.dataset.field;
    this.setData({ [`form.${field}`]: e.detail });
  },
  onSubmit() {
    const { name, phone, address } = this.data.form;
    if (!name || !phone || !address) {
      wx.showToast({ title: '请填写完整信息', icon: 'none' });
      return;
    }
    if (!/^1\d{10}$/.test(phone)) {
      wx.showToast({ title: '手机号格式不正确', icon: 'none' });
      return;
    }
    this.setData({ submitting: true });
    // 实际项目走统一封装的 request，此处模拟提交
    setTimeout(() => {
      this.setData({ submitting: false });
      wx.showToast({ title: '下单成功', icon: 'success' });
    }, 800);
  }
});
```

```css
/* pages/order/order.wxss */
.order-page { padding: 24rpx; }
.order-page van-button { margin-top: 48rpx; }
```

```text
场景一关键步骤：
1. npm 安装 @vant/weapp 并执行「工具 - 构建 npm」
2. app.json 配置 "style": "v2" 并注册组件
3. 表单数据统一收敛到 data.form 对象，change 事件按 data-field 更新
4. 提交前做前端校验，提交中 loading + disabled 防重复点击
5. 业务代码只关注数据与逻辑，样式与交互交给组件库
```

### 场景二：自建主题可定制按钮组件

自建一个支持主题变量与外部样式类的按钮组件，并在页面中演示换肤，这是自建组件库的最小单元：

```js
// components/theme-button/index.js
Component({
  externalClasses: ['custom-class'],
  properties: {
    text: { type: String, value: '' },
    type: { type: String, value: 'primary' },   // primary | plain | danger
    disabled: { type: Boolean, value: false }
  },
  methods: {
    onTap() {
      if (this.data.disabled) return;
      this.triggerEvent('onClick', { type: this.data.type });
    }
  }
});
```

## 最佳实践与踩坑记录

### 最佳实践

1. 组件设计先写文档再写代码：props、事件、插槽、外部样式类清单先行，避免边写边加导致 API 混乱
2. props 统一驼峰命名并在 properties 中给出默认值，WXML 中使用 kebab-case，事件统一 onXxx
3. 组件内禁止直接操作页面数据或跨组件改状态，通信只走 properties、triggerEvent、插槽三条通道
4. 主题变量集中收敛在 app.wxss 的 page 选择器，形成设计 token 表，组件内一律 var() 读取并带兜底值
5. 第三方组件库按页面级注册，高频组件才全局注册到 app.json，控制首屏加载与包体积
6. npm 依赖锁定版本并提交 package-lock.json，升级组件库前先读 changelog，破坏性变更升 major
7. 同一 UI 片段在项目中重复出现 2 次以上就抽象成组件，沉淀进自建组件库
8. 组件库升级前先在「开发版」用真机回归一遍，重点验证主题变量、外部样式类与事件名是否兼容

### 踩坑记录

```text
坑 1：构建 npm 后组件仍提示「未找到 van-button」
结论：usingComponents 路径正确但组件不渲染，控制台报未找到组件。
原因：没有执行「工具 - 构建 npm」，项目根目录缺少 miniprogram_npm 目录，或 npm 安装时带了 devDependencies。
解法：确认 package.json 存在后重新构建 npm；安装用 npm i @vant/weapp -S --production；构建失败时删除 node_modules 与 miniprogram_npm 重装。

坑 2：Vant 组件样式异常，按钮/输入框与文档示例不一致
结论：组件功能正常但视觉错乱，如按钮内边距异常、字体偏大。
原因：未在 app.json 配置 "style": "v2"，小程序默认样式与组件库样式叠加冲突。
解法：app.json 添加 "style": "v2" 并重新编译；仍有问题检查基础库版本是否满足组件库要求。

坑 3：外部样式类不生效
结论：传入 custom-class 后样式没有任何变化。
原因：外部样式类名包含中划线等非法字符，或 externalClasses 声明的名字与使用方 class 名不一致；CSS 变量写法 var(--xxx) 拼写错误也会表现为样式不生效。
解法：externalClasses 名称只用字母、数字、下划线；使用方 class 名与声明保持一致；变量名对照组件库文档逐字符核对。

坑 4：组件样式被页面或全局样式污染
结论：组件在某个页面正常，在另一个页面样式错乱。
原因：组件 json 未配置 styleIsolation，或历史项目使用了 apply-shared/addGlobalClass 让页面样式进入了组件。
解法：新组件显式配置 "styleIsolation": "isolated"；排查页面 wxss 中是否有 .xxx 这类类名与组件内部类名冲突。

坑 5：页面中使用 page 选择器定义样式，组件内部不生效
结论：在页面 wxss 写 page { --brand-color: ... }，组件内 var(--brand-color) 读不到。
原因：组件默认 isolated 隔离，且 page 选择器样式只作用于页面；CSS 变量虽可继承，但 page 节点并非组件节点的父级样式来源（组件渲染在独立节点树内）。
解法：主题变量定义在 app.wxss 的 page 选择器（全局生效）或使用方页面根节点；组件内变量必须带兜底值 var(--brand-color, #07c160)。

坑 6：TDesign/WeUI 组件路径写错导致构建失败
结论：构建 npm 正常，但编译报「组件 t-button 不存在」。
原因：不同组件库路径结构不同：Vant 是 @vant/weapp/button/index，TDesign 是 tdesign-miniprogram/button/button，WeUI 是 weui-miniprogram/dialog/dialog，照搬 Vant 写法必然出错。
解法：以各组件库官方文档的 usingComponents 示例为准，复制粘贴路径，不要凭记忆手写。

坑 7：组件库升级后页面大面积报错
结论：升级 @vant/weapp 等依赖后，既有页面编译报错或交互异常。
原因：组件库 major 版本 API 不兼容，如组件路径、属性名、事件名变更；或新版本要求更高基础库。
解法：升级前读 changelog；用版本范围锁定（如 ^1.10.0）；升级后真机全量回归；必要时先在分支升级验证再合入主干。

坑 8：npm 包构建后体积暴增，首屏变慢
结论：引入组件库后主包体积明显增大，启动耗时上升。
原因：全局注册大量组件 + 组件库全量打进主包，没有按需使用；或组件库被错误放进了主包而非分包。
解法：低频组件改页面级注册；使用分包承载组件库；检查 project.config.json 的 packNpmRelationList 是否把 miniprogram_npm 放进了分包。
```
