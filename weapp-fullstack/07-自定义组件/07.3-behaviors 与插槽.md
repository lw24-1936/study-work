## 概述

behaviors 是小程序组件间的代码复用机制，类似前端常说的 mixin：把一组公共的 properties、data、methods、observers、lifetimes 抽成独立模块，多个组件通过 behaviors 数组引用，实现「写一次、处处用」。插槽（slot）是组件的内容分发机制，使用方可以在组件标签内传入自定义结构，组件在 wxml 中用 slot 节点占位渲染。behaviors 解决「组件之间共享逻辑」，插槽解决「同一个组件在不同页面展示不同内容」，两者都是组件库与复杂业务组件设计的基石。

```text
behaviors 与插槽核心概念：
1. Behavior() —— 构造器，声明可复用的组件配置片段
2. behaviors 数组 —— 组件构造器中引用一个或多个 behavior
3. 字段合并 —— 同名 properties/data/methods 按优先级覆盖，observers/lifetimes 合并执行
4. slot —— 组件 wxml 中的内容占位节点
5. multipleSlots —— options 开关，开启后支持具名多插槽
6. 作用域 —— 插槽内容在使用方作用域内渲染，访问不到组件内部数据
```

## behaviors 定义与复用

behaviors 用 Behavior 构造器创建，内容与 Component 构造器大同小异，可以包含 properties、data、methods、observers、lifetimes 等字段。组件通过 behaviors 数组引用，引用后这些字段会并入组件，就像写在组件里一样。

```js
// behaviors/checkable.js —— 公共「可选中」逻辑
module.exports = Behavior({
  properties: {
    checked: {
      type: Boolean,
      value: false
    }
  },
  data: {
    disabled: false
  },
  methods: {
    setChecked(value) {
      this.setData({ checked: value })
      this.triggerEvent('checkchange', { checked: value })
    },
    isChecked() {
      return this.data.checked
    }
  },
  observers: {
    checked(checked) {
      console.log('选中状态变化：', checked)
    }
  },
  lifetimes: {
    attached() {
      console.log('checkable behavior attached')
    }
  }
})
```

组件引用：

```js
// components/checkbox-item/checkbox-item.js
const checkable = require('../../behaviors/checkable')

Component({
  // 引用 behavior，checkable 里的字段全部并入本组件
  behaviors: [checkable],
  properties: {
    label: {
      type: String,
      value: ''
    }
  },
  methods: {
    onTap() {
      // 直接使用 behavior 提供的方法
      this.setChecked(!this.data.checked)
    }
  }
})
```

```xml
<!-- components/checkbox-item/checkbox-item.wxml -->
<view class="item {{checked ? 'active' : ''}}" bindtap="onTap">
  <view class="box">{{checked ? '✓' : ''}}</view>
  <text>{{label}}</text>
</view>
```

多个组件复用同一份逻辑：

```js
// components/radio-item/radio-item.js —— 复选组件
const checkable = require('../../behaviors/checkable')

Component({
  behaviors: [checkable],
  properties: {
    value: {
      type: String,
      value: ''
    }
  },
  methods: {
    onTap() {
      this.setChecked(!this.data.checked)
    }
  }
})
```

```text
behaviors 要点：
1. 创建 —— Behavior({...}) 返回可复用的配置片段，module.exports 导出
2. 引用 —— 组件构造器 behaviors: [b1, b2] 数组引入，可同时引多个
3. 内容 —— 支持 properties/data/methods/observers/lifetimes/relations 等字段
4. 复用 —— 组件库常用：把选中态、加载态、表单校验等公共逻辑抽成 behavior
5. 嵌套 —— behavior 内部也可以引用其他 behavior，形成继承链
6. 定位 —— 与 Vue mixin、React HOC 类似，但作用域与字段冲突规则是微信定制的
```

## 同名字段合并与覆盖规则

behaviors 与组件、behavior 与 behavior 之间可能定义同名字段，官方有一套明确的优先级规则。理解这套规则是使用 behaviors 不出诡异 bug 的前提。

```text
同名字段覆盖规则：
1. 组件自身定义 > 引用的 behavior 定义
2. 多个 behavior 之间，后引用（数组靠后）的 > 先引用的
3. 子 behavior（behavior 引用了其他 behavior）> 父 behavior
4. observers 不覆盖 —— 同名监听全部合并，按 behavior 顺序先执行，组件自身的最后执行
5. lifetimes 不覆盖 —— 同种生命周期全部执行，先执行 behavior 的，再执行组件自身的
6. properties 与 data 的覆盖规则一致 —— 字段整体覆盖，不进行深层合并
```

用代码验证覆盖规则：

```js
// behaviors/behavior-a.js
module.exports = Behavior({
  data: {
    name: '来自 A',
    color: 'red'
  },
  methods: {
    hello() {
      return 'hello from A'
    }
  },
  observers: {
    name(v) {
      console.log('A observer:', v)
    }
  },
  lifetimes: {
    attached() {
      console.log('A attached')
    }
  }
})
```

```js
// behaviors/behavior-b.js
module.exports = Behavior({
  data: {
    name: '来自 B',
    size: 10
  },
  methods: {
    hello() {
      return 'hello from B'
    }
  },
  observers: {
    name(v) {
      console.log('B observer:', v)
    }
  },
  lifetimes: {
    attached() {
      console.log('B attached')
    }
  }
})
```

```js
// components/merge-demo/merge-demo.js
const behaviorA = require('../../behaviors/behavior-a')
const behaviorB = require('../../behaviors/behavior-b')

Component({
  behaviors: [behaviorA, behaviorB],
  data: {
    name: '来自组件自身',
    extra: true
  },
  methods: {
    hello() {
      return 'hello from component'
    }
  },
  observers: {
    name(v) {
      console.log('组件 observer:', v)
    }
  },
  lifetimes: {
    attached() {
      console.log('组件 attached')
    }
  }
})
```

```text
上述示例的运行结果：
1. this.data.name === '来自组件自身'（组件自身 data 优先）
2. this.data.color === 'red'（A 独有的字段保留）
3. this.data.size === 10（B 独有的字段保留）
4. this.hello() 返回 'hello from component'（组件方法覆盖 behavior 方法）
5. 触发顺序 —— 日志依次为：A observer -> B observer -> 组件 observer
6. 生命周期 —— 日志依次为：A attached -> B attached -> 组件 attached
```

behavior 继承链示例：behavior 可以引用其他 behavior，冲突时「子」优先于「父」，整体规则与组件引用 behavior 一致：

```js
// behaviors/base-logger.js
module.exports = Behavior({
  data: {
    level: 'info'
  },
  methods: {
    log(msg) {
      console.log(`[${this.data.level}]`, msg)
    }
  }
})
```

```js
// behaviors/debug-logger.js —— 继承 base-logger 并覆盖
const baseLogger = require('./base-logger')

module.exports = Behavior({
  behaviors: [baseLogger],
  data: {
    // 子 behavior 覆盖父 behavior 的同名字段
    level: 'debug'
  }
})
```

```text
合并规则细节：
1. 覆盖是字段级 —— data.name 被覆盖后，A 里的 color、B 里的 size 仍会保留
2. 方法覆盖不可逆 —— 组件定义了 hello，behavior 里的 hello 被隐藏，无法再调用
3. observer 全执行 —— 想要「只执行一个」时，在 behavior 里用标记字段控制
4. 生命周期全执行 —— 依赖「谁先执行」的逻辑不要写死在 behavior 里
5. 顺序敏感 —— 多个 behavior 有同名 data 时，数组顺序决定胜出者，改顺序即改结果
6. 调试 —— 字段被意外覆盖时，先打印 this.data 与 Object.keys(this) 核对来源
```

## 默认插槽 slot

插槽让组件的使用方决定组件内部某块区域的内容。组件 wxml 中写一个 slot 节点，使用方在组件标签内写的内容会渲染到这个位置。没有写 slot 的组件，标签内的内容会被忽略。

```js
// components/custom-btn/custom-btn.js
Component({
  properties: {
    size: {
      type: String,
      value: 'default'
    }
  }
})
```

```xml
<!-- components/custom-btn/custom-btn.wxml -->
<view class="custom-btn btn-{{size}}">
  <!-- 默认插槽：使用方的内容渲染在这里 -->
  <slot></slot>
</view>
```

```css
/* components/custom-btn/custom-btn.wxss */
.custom-btn {
  display: inline-block;
  padding: 16rpx 32rpx;
  background: #07c160;
  color: #fff;
  border-radius: 8rpx;
}
.btn-small {
  padding: 8rpx 20rpx;
  font-size: 24rpx;
}
```

使用方传入任意内容：

```xml
<!-- pages/home/home.wxml -->
<custom-btn size="small">
  <text>加入购物车</text>
</custom-btn>

<custom-btn>
  <image src="/images/arrow.png" class="arrow-icon" />
  <text>查看详情</text>
</custom-btn>
```

```css
/* pages/home/home.wxss */
.arrow-icon {
  width: 24rpx;
  height: 24rpx;
  margin-right: 8rpx;
  vertical-align: middle;
}
```

```text
默认插槽要点：
1. 占位 —— 组件 wxml 中 <slot></slot> 是内容占位节点
2. 自由内容 —— 使用方可以传入文本、图片、按钮、甚至其他组件
3. 无内容时 —— slot 位置渲染为空，组件可以自行设计空态
4. 一个默认插槽 —— 不开启 multipleSlots 时组件只能有一个 slot
5. 样式归属 —— 插槽内容的样式在使用方作用域定义，组件 wxss 管不到
6. 布局 —— 插槽是内联渲染，配合组件外层结构实现「内容区 + 固定框架」的布局复用
```

## 具名插槽与多插槽

一个组件需要多个内容区域时，开启多插槽：在 Component 构造器的 options 中设置 multipleSlots: true，然后给每个插槽命名，使用方通过 slot="名字" 指定内容进哪个插槽。这是卡片、弹窗、列表等容器组件的基本能力。

```js
// components/goods-card/goods-card.js
Component({
  // 开启多插槽支持
  options: {
    multipleSlots: true
  },
  properties: {
    title: {
      type: String,
      value: ''
    }
  }
})
```

```xml
<!-- components/goods-card/goods-card.wxml -->
<view class="card">
  <view class="card-header">
    <!-- 具名插槽：头部区域 -->
    <slot name="header"></slot>
  </view>
  <view class="card-body">
    <!-- 未命名的 slot 是默认插槽：主体区域 -->
    <slot></slot>
  </view>
  <view class="card-footer">
    <!-- 具名插槽：底部操作区域 -->
    <slot name="footer"></slot>
  </view>
</view>
```

```css
/* components/goods-card/goods-card.wxss */
.card {
  margin: 24rpx;
  background: #fff;
  border-radius: 16rpx;
  overflow: hidden;
  box-shadow: 0 4rpx 16rpx rgba(0, 0, 0, 0.06);
}
.card-header {
  padding: 24rpx;
  border-bottom: 2rpx solid #f0f0f0;
}
.card-body {
  padding: 24rpx;
}
.card-footer {
  display: flex;
  justify-content: flex-end;
  align-items: center;
  padding: 16rpx 24rpx;
  border-top: 2rpx solid #f0f0f0;
}
```

使用方组合内容：

```xml
<!-- pages/home/home.wxml -->
<goods-card title="限时特价">
  <!-- slot 属性指定进入哪个插槽 -->
  <view slot="header">
    <text class="tag">新品</text>
    <text class="title">{{goods.name}}</text>
  </view>

  <!-- 没有 slot 属性的内容进入默认插槽 -->
  <image class="goods-img" src="{{goods.image}}" mode="aspectFill" />
  <text class="desc">{{goods.desc}}</text>

  <view slot="footer">
    <text class="price">¥{{goods.price}}</text>
    <button size="mini" type="primary" bindtap="onBuy">立即购买</button>
  </view>
</goods-card>
```

```text
具名插槽要点：
1. 开关 —— options.multipleSlots: true 之后具名插槽才生效，漏配是最高频的坑
2. 命名 —— <slot name="header"></slot>，使用方 slot="header" 匹配
3. 默认插槽 —— 不写 name 的 slot 接收所有未指定 slot 属性的内容
4. 可重复 —— 同名具名插槽在 wxml 中出现多次时，内容会重复渲染（一般用于循环骨架）
5. 与 wx:if 配合 —— 内容区可以包条件渲染，组件灵活控制展示
6. 嵌套组件 —— 插槽内容里可以再放自定义组件，实现多层组合
```

## 插槽作用域与使用场景

插槽内容虽然写在组件标签内，但它的数据作用域是使用方（父组件/页面），不是组件内部。也就是说，插槽里绑定组件内部的 data 字段是拿不到的。这是小程序插槽与 Vue 作用域插槽的关键差异：小程序插槽不能向内容传数据，需要数据时要把数据通过 properties 传给插槽里的子组件，或用抽象节点（详见 07.4）。

```js
// components/demo-box/demo-box.js —— 演示作用域限制
Component({
  data: {
    innerName: '组件内部名字',
    innerList: ['a', 'b', 'c']
  }
})
```

```xml
<!-- components/demo-box/demo-box.wxml -->
<view class="box">
  <slot></slot>
</view>
```

```xml
<!-- pages/home/home.wxml -->
<demo-box>
  <!-- 这里绑定的是页面的数据，拿不到组件的 innerName -->
  <text>{{innerName}}</text>
  <!-- 若页面没有 pageName 字段，这里渲染为空 -->
  <text>{{pageName}}</text>
</demo-box>
```

```js
// pages/home/home.js
Page({
  data: {
    pageName: '页面自己的名字'
  }
})
```

```text
插槽作用域限制：
1. 作用域 —— 插槽内容在「使用方作用域」内编译，绑定的是使用方的 data
2. 拿不到 —— 组件内部 data、methods 在插槽内容中不可见
3. 无作用域插槽 —— 小程序没有 Vue 那种「向插槽传数据」的机制
4. 传数据方案 —— 把数据通过 properties 传给插槽内的子组件
5. 兜底方案 —— 需要根据数据动态渲染不同内容时，用抽象节点 componentGenerics
6. 实践 —— 列表项自定义常用「外层容器组件 + 抽象节点/传入子组件」实现
```

插槽的典型使用场景：

```text
插槽使用场景：
1. 布局骨架 —— 卡片、弹窗、面板：固定框架 + 可变内容区
2. 操作区定制 —— 按钮组、页脚操作区，不同页面放不同按钮
3. 空态/加载态 —— 组件内 <slot name="empty"> 由使用方定制空状态插画
4. 列表项 —— 列表容器组件 + 具名插槽定制每一项
5. 导航栏 —— 左右插槽放自定义图标与操作，中间放标题
6. 组件库扩展点 —— 组件库提供骨架插槽，业务方在不改源码的情况下定制内容
```

## 应用场景实战

### 场景一：behaviors 抽取「选中态」逻辑，复用到多选与单选组件

业务里多选列表、单选列表、标签筛选都有「选中/取消选中 + 上报变化」的公共逻辑，抽成一个 checkable behavior，两个组件分别引用。

```js
// behaviors/checkable.js
module.exports = Behavior({
  properties: {
    checked: {
      type: Boolean,
      value: false
    }
  },
  methods: {
    toggle() {
      this.setChecked(!this.data.checked)
    },
    setChecked(value) {
      this.setData({ checked: value })
      this.triggerEvent('checkchange', { checked: value })
    }
  }
})
```

```js
// components/checkbox-item/checkbox-item.js —— 多选
const checkable = require('../../behaviors/checkable')

Component({
  behaviors: [checkable],
  properties: {
    label: { type: String, value: '' }
  },
  methods: {
    onTap() {
      this.toggle()
    }
  }
})
```

```js
// components/radio-item/radio-item.js —— 单选（互斥逻辑由父组件控制）
const checkable = require('../../behaviors/checkable')

Component({
  behaviors: [checkable],
  properties: {
    value: { type: String, value: '' }
  },
  methods: {
    onTap() {
      this.toggle()
    }
  }
})
```

```xml
<!-- components/checkbox-item/checkbox-item.wxml -->
<view class="check-item {{checked ? 'active' : ''}}" bindtap="onTap">
  <view class="box">{{checked ? '✓' : ''}}</view>
  <text>{{label}}</text>
</view>
```

```xml
<!-- pages/filter/filter.wxml -->
<view class="filter-panel">
  <view class="group-title">品类</view>
  <checkbox-item label="水果" bind:checkchange="onFilterChange" data-key="fruit" />
  <checkbox-item label="零食" bind:checkchange="onFilterChange" data-key="snack" />
  <view class="group-title">价格</view>
  <radio-item value="low" label="50 元以下" bind:checkchange="onFilterChange" data-key="price" />
  <radio-item value="high" label="50 元以上" bind:checkchange="onFilterChange" data-key="price" />
</view>
```

```js
// pages/filter/filter.js
Page({
  data: {
    selected: {}
  },
  onFilterChange(e) {
    const key = e.currentTarget.dataset.key
    const checked = e.detail.checked
    // 单选组内互斥：同 key 的其他项取消
    if (key === 'price' && checked) {
      this.setData({
        selected: {
          fruit: this.data.selected.fruit || false,
          price: true
        }
      })
      return
    }
    this.setData({
      ['selected.' + key]: checked
    })
  }
})
```

运行效果：两个组件共用同一套「选中状态 + 事件上报」逻辑，页面只处理业务差异（单选互斥、多选累积）。后续要加「半选状态」「禁用态」，只需改 behavior，两个组件同步生效。

### 场景二：具名插槽搭建商品卡片与弹窗骨架

用 multipleSlots 实现一个可复用的「商品卡片」组件和一个「确认弹窗」组件，页面组合使用，同一组件在不同位置展示不同内容。

```js
// components/goods-card/goods-card.js
Component({
  options: {
    multipleSlots: true
  }
})
```

```xml
<!-- components/goods-card/goods-card.wxml -->
<view class="card">
  <view class="card-img">
    <slot name="image"></slot>
  </view>
  <view class="card-info">
    <slot name="info"></slot>
  </view>
  <view class="card-action">
    <slot name="action"></slot>
  </view>
</view>
```

```js
// components/confirm-dialog/confirm-dialog.js
Component({
  options: {
    multipleSlots: true
  },
  properties: {
    visible: {
      type: Boolean,
      value: false
    }
  },
  methods: {
    onCancel() {
      this.triggerEvent('cancel')
    },
    onConfirm() {
      this.triggerEvent('confirm')
    },
    noop() {
      // 阻止冒泡：点击遮罩不关闭
    }
  }
})
```

```xml
<!-- components/confirm-dialog/confirm-dialog.wxml -->
<view class="dialog-mask" wx:if="{{visible}}" bindtap="onCancel">
  <view class="dialog" catchtap="noop">
    <view class="dialog-header">
      <slot name="header"></slot>
    </view>
    <view class="dialog-body">
      <slot></slot>
    </view>
    <view class="dialog-footer">
      <slot name="footer"></slot>
    </view>
  </view>
</view>
```

```xml
<!-- pages/home/home.wxml -->
<view class="home-page">
  <!-- 首页场景：横向卡片 -->
  <goods-card>
    <view slot="image">
      <image class="thumb" src="/images/apple.png" mode="aspectFill" />
    </view>
```

## 最佳实践与踩坑记录

### 最佳实践

1. behavior 文件名与导出名一致（behaviors/checkable.js 导出 checkable），按功能域组织目录，一个文件只放一个 behavior
2. behavior 中避免依赖组件私有字段，需要外部提供时在 behavior 内声明默认值，组件侧用覆盖规则按需定制
3. 组件自身不定义同名字段时，多个 behavior 的同名 data 依赖数组顺序，把「更通用的放前面、更具体的放后面」并加注释
4. observers 与 lifetimes 在同名时会全部执行，behavior 内的监听器只做「自己的事」，不要隐式假设其他 behavior 的执行结果
5. 插槽统一规划：每个组件最多 3-4 个插槽（header/body/footer/extra），超过说明组件职责过重，拆组件
6. 具名插槽在组件 wxml 中给 slot 外的包裹节点统一加 class 前缀（card-header 等），方便使用方按区域写样式
7. 弹窗、浮层类组件的插槽内容里注意事件冒泡，遮罩层点击用 catchtap 阻止冒泡
8. 插槽内容需要数据时，显式通过 properties 传子组件，或改用抽象节点（componentGenerics），不要依赖「插槽能拿到组件数据」的错误假设

### 踩坑记录

```text
坑 1：开了具名插槽但忘记 multipleSlots: true
结论：slot="header" 的内容不渲染，页面一片空白或内容错位。
原因：组件默认只支持一个默认插槽，具名插槽必须显式开启多插槽支持。
解法：组件构造器 options 中加 multipleSlots: true；改完重新编译再验证。

坑 2：behaviors 同名 data 被意外覆盖
结论：组件里定义的数据被 behavior 覆盖，或两个 behavior 的同名数据不是预期的那个值。
原因：字段覆盖规则是「组件自身 > 后引用的 behavior > 先引用的」，很多人误以为是「先引用优先」。
解法：牢记数组后面的优先；同名数据必须存在时，在组件自身显式定义，杜绝歧义。

坑 3：behavior 中的 methods 被组件方法覆盖后无法调用
结论：组件定义了同名的 loadData，behavior 里精心封装的方法被顶掉，报方法不存在或行为异常。
原因：methods 同名时组件方法覆盖 behavior 方法，且覆盖不可逆，被覆盖的方法无法再调用。
解法：命名时加前缀或语义区分（behavior 方法如 fetchData，组件方法如 loadData）；确需共存时组件方法内改调用别的命名。

坑 4：observers 同名不覆盖，多个监听重复执行
结论：行为看起来「执行了多次」，数据被重复处理或重复上报。
原因：observers 与 lifetimes 在同名时是合并执行，不是覆盖；behavior 与组件的监听都会跑。
解法：把「只执行一次」的逻辑下沉到业务层（如 setData 前判断值是否变化）；behavior 内监听只做派生，不做有副作用的操作。

坑 5：插槽里访问组件内部 data 拿不到
结论：插槽内容 {{innerName}} 渲染为空，以为组件数据没传对。
原因：插槽内容在使用方作用域编译，组件内部 data 对插槽内容不可见。
解法：把数据通过 properties 传给插槽内的子组件；或改用抽象节点让使用方注入渲染组件。

坑 6：behavior require 路径写错或循环引用
结论：编译报「Cannot find module」或「Maximum call stack size exceeded」。
原因：behavior 文件用相对路径 require，层级写错；或 behavior A 引用 B、B 又引用 A 形成循环。
解法：require 路径以当前文件为基准逐级核对；梳理 behavior 依赖为单向树，禁止循环引用。

坑 7：多个 behavior 顺序调整后表现突变
结论：只是调换了 behaviors 数组里两个 behavior 的顺序，组件行为就变了。
原因：同名 data/methods 的胜出者由数组顺序决定，顺序即优先级，属于预期但隐蔽的行为。
解法：明确依赖覆盖关系的字段在组件自身显式声明；依赖顺序的代码加注释，并在代码评审中提示。

坑 8：弹窗组件插槽内容点击穿透到遮罩层关闭
结论：点击弹窗内容区，弹窗被关闭。
原因：遮罩层绑定 bindtap 关闭，插槽内容的事件冒泡到遮罩层触发了关闭逻辑。
解法：弹窗容器用 catchtap 阻止冒泡（如 onNoop 空方法）；关闭逻辑只在遮罩层与关闭按钮上触发。
```
