## 概述

管理后台是典型的多页面协作场景：用户信息、权限、全局配置等数据需要跨组件共享，接口请求需要统一的鉴权、错误处理与提示。Pinia 是 Vue3 官方的状态管理库（取代 Vuex），以组合式 API 风格定义 store，天然支持 TypeScript 与模块拆分；axios 封装则把「token 注入、统一错误码处理、401 跳登录、错误提示」集中到拦截器里，业务代码只关心数据。本章覆盖 Pinia 的 defineStore 三件套（state/getters/actions）、持久化插件、axios 实例与拦截器、统一错误处理以及 API 模块化组织。

```text
状态管理与请求封装要点：
1. Pinia —— Vue3 官方状态库，setup 语法 + TS 类型推导，替代 Vuex
2. 持久化 —— pinia-plugin-persistedstate 一行配置，token 刷新不丢
3. 模块拆分 —— user/app/permission 各自独立 store，按需引用
4. axios 封装 —— create 实例统一 baseURL/timeout，拦截器处理横切逻辑
5. 双拦截器 —— 请求拦截注入 token，响应拦截统一解包与错误处理
6. 401 处理 —— token 失效自动清理并跳登录，附 redirect 回跳
7. API 模块化 —— api/ 目录按业务域一个文件一个函数，类型化返回
```

## Pinia 基础

Pinia 是 Vue3 官方的状态管理库，相比 Vuex 去掉了 mutations（actions 直接改 state）、支持 setup 语法、TypeScript 推导完整、支持多 store 实例。核心概念：`defineStore` 定义仓库，`state` 存数据、`getters` 派生数据（类似 computed）、`actions` 写业务动作（可异步）。管理后台最典型的使用：user store 保存 token 与用户信息，app store 保存侧边栏折叠、主题等 UI 状态。

```bash
npm install pinia
```

```ts
// src/main.ts —— 注册 Pinia
import { createApp } from 'vue'
import { createPinia } from 'pinia'
import App from './App.vue'

const app = createApp(App)
const pinia = createPinia()

app.use(pinia)
app.mount('#app')
```

setup 语法定义 store（推荐，组合式 API 风格）：

```ts
// src/stores/app.ts —— 应用 UI 状态
import { ref, computed } from 'vue'
import { defineStore } from 'pinia'

export const useAppStore = defineStore('app', () => {
  // state
  const sidebarCollapsed = ref(false)
  const device = ref<'desktop' | 'mobile'>('desktop')

  // getters（派生状态）
  const sidebarWidth = computed(() => (sidebarCollapsed.value ? '64px' : '220px'))

  // actions
  function toggleSidebar() {
    sidebarCollapsed.value = !sidebarCollapsed.value
  }

  function setDevice(value: 'desktop' | 'mobile') {
    device.value = value
  }

  return {
    sidebarCollapsed,
    device,
    sidebarWidth,
    toggleSidebar,
    setDevice
  }
})
```

组件中使用 store：

```vue
<template>
  <el-button @click="appStore.toggleSidebar()">
    {{ appStore.sidebarCollapsed ? '展开菜单' : '收起菜单' }}
  </el-button>
  <p>侧边栏宽度：{{ appStore.sidebarWidth }}</p>
</template>

<script setup lang="ts">
import { storeToRefs } from 'pinia'
import { useAppStore } from '@/stores/app'

const appStore = useAppStore()
// storeToRefs 解构 state/getters 保持响应性；actions 直接解构
const { sidebarCollapsed, sidebarWidth } = storeToRefs(appStore)
const { toggleSidebar } = appStore
</script>
```

state 直接修改与 $patch：

```ts
const appStore = useAppStore()

// 直接赋值（Pinia 允许）
appStore.sidebarCollapsed = true

// 批量修改用 $patch
appStore.$patch({
  sidebarCollapsed: true,
  device: 'mobile'
})

// 监听变化
appStore.$subscribe((mutation, state) => {
  console.log('store 变化：', mutation.type, state)
})
```

```text
Pinia 基础要点：
1. setup 语法 —— defineStore 传函数，ref 即 state，computed 即 getters，函数即 actions
2. storeToRefs —— 解构 state/getters 必须用它保持响应性，actions 直接解构
3. 无 mutations —— actions 可直接修改 state，代码量比 Vuex 少一半
4. 类型推导 —— TS 下 state/getters/actions 全自动推导，无需额外声明
5. 多实例 —— 同一个 store 可在任意组件 useStore 获取同一份状态
6. $patch —— 批量更新与 $subscribe 订阅，配合调试工具使用
```

## Pinia 模块拆分与持久化

后台项目按业务域拆分 store：user（登录态、用户信息、权限）、app（UI 状态）、permission（路由与菜单，也可并入 user）、settings（主题配置）。拆分原则：一个 store 只关心一件事，跨 store 引用用 `useXxxStore()` 在 action 内调用。持久化用官方推荐的 `pinia-plugin-persistedstate`：默认把整个 state 序列化到 localStorage，可配置只持久化指定字段。

```bash
npm install pinia-plugin-persistedstate
```

```ts
// src/main.ts —— 注册持久化插件
import { createPinia } from 'pinia'
import piniaPluginPersistedstate from 'pinia-plugin-persistedstate'

const pinia = createPinia()
pinia.use(piniaPluginPersistedstate)
```

```ts
// src/stores/user.ts —— 用户 store（token 持久化，权限不持久化）
import { defineStore } from 'pinia'
import { login as loginApi, getUserInfo as getUserInfoApi } from '@/api/auth'

export const useUserStore = defineStore('user', {
  state: () => ({
    token: '',
    name: '',
    avatar: '',
    roles: [] as string[],
    permissions: [] as string[] // 权限码：每次登录重新拉取，不持久化
  }),
  // 持久化配置：只存 token/name，权限与角色实时拉取
  persist: {
    key: 'admin-user',
    pick: ['token', 'name', 'avatar']
  },
  getters: {
    isLoggedIn: (state) => Boolean(state.token),
    hasPermission: (state) => {
      return (permission: string) => state.permissions.includes(permission)
    }
  },
  actions: {
    async loginAction(form: { username: string; password: string }) {
      const res = await loginApi(form)
      this.token = res.data.token
      // persist 插件自动把 token 写入 localStorage
    },
    async getUserInfo() {
      const res = await getUserInfoApi()
      this.name = res.data.name
      this.avatar = res.data.avatar
      this.roles = res.data.roles
      this.permissions = res.data.permissions
    },
    resetToken() {
      this.token = ''
      this.name = ''
      this.avatar = ''
      this.roles = []
      this.permissions = []
    }
  }
})
```

持久化的注意事项：token 放 localStorage 有 XSS 风险，生产环境可结合 httpOnly Cookie（后台设置）存储 token，前端只存非敏感状态；权限/角色每次登录重新拉取，保证后台改权后即时生效，不依赖本地缓存。

```text
模块拆分与持久化要点：
1. 拆分原则 —— 按领域拆分（user/app/settings），一个 store 一个职责
2. persist 配置 —— key 自定义存储键名，pick 只持久化必要字段
3. 敏感数据 —— 权限、角色不持久化，登录后实时拉取，改权即时生效
4. 存储介质 —— 默认 localStorage；高安全场景 token 用 httpOnly Cookie
5. 跨 store —— action 内 useXxxStore() 引用其他 store，避免循环依赖
6. 插件顺序 —— createPinia 后立即 use 插件，再注册到 app
```

## axios 实例与拦截器

axios 封装的核心是「实例化 + 双拦截器」：`axios.create` 生成带 baseURL、timeout 的实例；请求拦截器统一注入 token 与请求头；响应拦截器统一解包后台返回结构（code/message/data）、处理业务错误码、捕获 HTTP 错误并统一提示。封装后业务代码只需 `await api.xxx()` 拿到 data，错误处理全部收敛。

```bash
npm install axios
```

```ts
// src/utils/request.ts —— axios 统一封装
import axios from 'axios'
import type { AxiosInstance, AxiosResponse, InternalAxiosRequestConfig } from 'axios'
import { ElMessage } from 'element-plus'
import { useUserStore } from '@/stores/user'
import router from '@/router'

// 后台统一返回结构约定（对应 SpringBoot 统一返回，见 17.2）
export interface ApiResult<T = unknown> {
  code: number
  message: string
  data: T
}

const service: AxiosInstance = axios.create({
  baseURL: import.meta.env.VITE_APP_BASE_URL || '/api',
  timeout: 15000
})

// 请求拦截器：注入 token
service.interceptors.request.use(
  (config: InternalAxiosRequestConfig) => {
    const userStore = useUserStore()
    if (userStore.token) {
      config.headers.Authorization = `Bearer ${userStore.token}`
    }
    return config
  },
  (error) => Promise.reject(error)
)

// 响应拦截器：解包 + 统一错误处理
service.interceptors.response.use(
  (response: AxiosResponse<ApiResult>) => {
    const res = response.data

    // 业务错误码非 0/200 视为业务失败
    if (res.code !== 0 && res.code !== 200) {
      if (res.code === 401) {
        handleUnauthorized()
      } else {
        ElMessage.error(res.message || '请求失败')
      }
      return Promise.reject(new Error(res.message || 'Request Error'))
    }
    // 直接返回 data，业务代码不用再 .data.data
    return res.data as never
  },
  (error) => {
    // HTTP 层错误
    const status = error.response?.status
    if (status === 401) {
      handleUnauthorized()
    } else if (status === 403) {
      ElMessage.error('没有操作权限')
    } else if (status === 404) {
      ElMessage.error('接口不存在')
    } else if (status >= 500) {
      ElMessage.error('服务器开小差了，请稍后重试')
    } else if (error.code === 'ECONNABORTED') {
      ElMessage.error('请求超时，请检查网络')
    } else if (!error.response) {
      ElMessage.error('网络异常，无法连接服务器')
    }
    return Promise.reject(error)
  }
)

// 401 统一处理：清登录态并跳登录页（记录来源）
function handleUnauthorized() {
  const userStore = useUserStore()
  userStore.resetToken()
  const redirect = router.currentRoute.value.fullPath
  router.replace(`/login?redirect=${encodeURIComponent(redirect)}`)
  ElMessage.error('登录已过期，请重新登录')
}

// 类型化请求方法
export function get<T = unknown>(url: string, params?: object): Promise<T> {
  return service.get(url, { params }) as Promise<T>
}

export function post<T = unknown>(url: string, data?: object): Promise<T> {
  return service.post(url, data) as Promise<T>
}

export function put<T = unknown>(url: string, data?: object): Promise<T> {
  return service.put(url, data) as Promise<T>
}

export function del<T = unknown>(url: string, params?: object): Promise<T> {
  return service.delete(url, { params }) as Promise<T>
}

export default service
```

```text
axios 封装要点：
1. 单实例 —— baseURL/timeout 统一，换环境只改 .env 配置
2. 请求拦截 —— 统一注入 Authorization: Bearer token，业务零感知
3. 响应拦截 —— 解包 ApiResult 直接返回 data，调用方少一层取值
4. 错误分层 —— 业务错误码走响应体判断，HTTP 错误按 status 分类提示
5. 401 全局处理 —— 清 token + 跳登录 + redirect 回跳，一处实现处处生效
6. 类型泛型 —— get/post 方法带泛型，接口返回类型可推导
```

## 统一错误处理

错误处理设计的好坏直接影响排查效率。原则：能自动处理的自动处理（401 跳登录、token 刷新），需要用户感知的统一 toast，业务代码里只捕获「必须特殊处理」的错误，禁止每个页面都写 try/catch 弹提示。

```ts
// 业务调用示例：一般页面不用 try/catch，错误已由拦截器提示
import { get } from '@/utils/request'

async function loadList() {
  // 成功：res 即 data；失败：拦截器已提示并 reject，这里不再重复处理
  const res = await get<{ rows: any[]; total: number }>('/user/list', { page: 1 })
  rows.value = res.rows
}
```

需要特殊处理的场景（如删除前二次确认失败、并发取消）：

```ts
import { ElMessageBox } from 'element-plus'
import { del } from '@/utils/request'

async function handleDelete(id: number) {
  try {
    // 用户取消时 ElMessageBox 会 reject（catch 分支）
    await ElMessageBox.confirm('确定删除该记录吗？', '提示', { type: 'warning' })
  } catch {
    return // 用户点了取消，直接返回
  }

  // 二次确认通过后才真正调删除接口
  await del(`/user/${id}`)
  ElMessage.success('删除成功')
  loadList()
}
```

请求取消（切换页面/重复点击场景）：

```ts
import { get } from '@/utils/request'
import type { AxiosCanceler } from '@/utils/request'

// 方案：AbortController 取消
const controller = new AbortController()

async function loadData() {
  try {
    const res = await get('/order/list', { signal: controller.signal })
    // ...
  } catch (error) {
    if ((error as Error).name === 'CanceledError') {
      console.log('请求已被取消')
      return
    }
    throw error
  }
}

// 组件卸载时取消
onUnmounted(() => controller.abort())
```

错误码约定（与 SpringBoot 统一返回对应，见 17.2）：

```text
错误码约定：
1. code 0 / 200 —— 成功，data 为业务数据
2. code 401 —— 未登录或 token 过期，全局跳登录
3. code 403 —— 无权限，提示「没有操作权限」
4. code 400 —— 参数错误，提示后台返回的 message
5. code 500 —— 服务器异常，统一兜底提示
6. HTTP 层 —— 404 接口不存在、超时、断网分别提示
```

```text
统一错误处理要点：
1. 收敛原则 —— 错误提示只在拦截器出现一次，页面不重复弹
2. 401 特判 —— 清 token 跳登录，redirect 回跳来源页
3. 二次确认 —— 危险操作先 ElMessageBox.confirm，取消不调接口
4. 取消请求 —— 页面销毁/参数变化时 abort，避免竞态与无效响应
5. 错误码对齐 —— 前端错误码与后台统一返回约定完全一致
6. 日志留痕 —— 生产环境把 error 上报监控（22.4），不只在控制台
```

## API 模块化与 token 管理

API 模块化：api/ 目录下按业务域一个文件，每个接口一个导出函数，函数内声明类型（请求参数与返回数据），页面只 import 函数。好处：接口集中管理、改动只动一个文件、类型可复用、方便 mock 与替换。token 管理：登录接口返回 token 后存入 Pinia（持久化），请求拦截器自动读取；登出时清空本地与 store。

```ts
// src/api/auth.ts —— 认证模块
import { post, get } from '@/utils/request'

export interface LoginParams {
  username: string
  password: string
}

export interface LoginResult {
  token: string
}

export interface UserInfo {
  id: number
  name: string
  avatar: string
  roles: string[]
  permissions: string[]
}

// 登录
export function login(data: LoginParams) {
  return post<LoginResult>('/auth/login', data)
}

// 获取当前用户信息（含权限码）
export function getUserInfo() {
  return get<UserInfo>('/auth/user-info')
}

// 退出登录（通知后台失效 token，可选）
export function logout() {
  return post<void>('/auth/logout')
}
```

```ts
// src/api/user.ts —— 用户管理模块
import { get, post, put, del } from '@/utils/request'

export interface UserItem {
  id: number
  username: string
  nickname: string
  phone: string
  status: number
  createTime: string

export interface PageResult<T> {
  rows: T[]
  total: number

// 分页查询用户
export function listUser(params: { page: number; pageSize: number; keyword?: string }) {
  return get<PageResult<UserItem>>('/user/list', params)
}

// 新增用户

  return post<void>('/user', data)
}

// 更新用户

  return put<void>(`/user/${id}`, data)
}

// 删除用户

  return del<void>(`/user/${id}`)
}
```

token 管理（登录/登出全流程）：

```ts
// src/stores/user.ts —— token 相关 action（完整）
import { defineStore } from 'pinia'
import { login as loginApi, logout as logoutApi, getUserInfo } from '@/api/auth'
import { resetRouter } from '@/router'

export const useUserStore = defineStore('user', {
  state: () => ({
    token: localStorage.getItem('admin-token') || '',
    name: '',
    permissions: [] as string[]
  }),
  persist: { key: 'admin-user', pick: ['token', 'name'] },
  actions: {
    // 登录：拿 token 并持久化
    async loginAction(form: { username: string; password: string }) {
      const res = await loginApi(form)
      this.token = res.token
      localStorage.setItem('admin-token', this.token)
    },

    // 拉取用户信息与权限
    async fetchUserInfo() {
      const res = await getUserInfo()
      this.name = res.name
      this.permissions = res.permissions
    },

    // 登出：通知后台 + 清理本地 + 重置路由 + 跳登录
    async logoutAction() {
      try {
        await logoutApi()
      } catch {
        // 后台登出失败也继续本地清理，保证能退出
      }
      this.token = ''
      this.name = ''
      this.permissions = []
      localStorage.removeItem('admin-token')
      resetRouter()
      window.location.href = '/login'
    }
  }
})
```

```text
API 模块化与 token 管理要点：
1. 一域一文件 —— api/auth.ts、api/user.ts、api/order.ts，按后台模块对齐
2. 函数导出 —— 每个接口一个具名函数，页面 import 函数而非裸调 axios
3. 类型先行 —— 请求参数与返回结构声明 interface，与后台 DTO 对齐
4. token 生命周期 —— 登录写入（localStorage + store）-> 拦截器读取 -> 登出清理
5. 登出兜底 —— 后台登出失败也要完成本地清理，不阻塞退出
6. 双存储 —— store 内存态 + localStorage 持久态，刷新后 store 从持久层恢复
```

## 应用场景实战

### 场景一：登录流程全链路（表单 -> 接口 -> store -> 跳转）

```vue
<!-- src/views/login/index.vue —— 登录页（简化，完整校验见 20.5） -->
<template>
  <div class="login-page">
    <el-form ref="formRef" :model="form" :rules="rules" class="login-form">
      <h2 class="login-title">商城管理后台</h2>
      <el-form-item prop="username">
        <el-input v-model="form.username" placeholder="用户名" />
      </el-form-item>
      <el-form-item prop="password">
        <el-input v-model="form.password" type="password" placeholder="密码" show-password />
      </el-form-item>
      <el-button type="primary" class="login-btn" :loading="loading" @click="handleLogin">
        登 录
      </el-button>
    </el-form>
  </div>
</template>

<script setup lang="ts">
import { reactive, ref } from 'vue'
import { useRoute, useRouter } from 'vue-router'
import { useUserStore } from '@/stores/user'
import type { FormInstance } from 'element-plus'

const formRef = ref<FormInstance>()
const loading = ref(false)
const form = reactive({ username: '', password: '' })
const rules = {
  username: [{ required: true, message: '请输入用户名', trigger: 'blur' }],
  password: [{ required: true, message: '请输入密码', trigger: 'blur' }]
}

const userStore = useUserStore()
const route = useRoute()
const router = useRouter()

async function handleLogin() {
  // 1. 表单校验
  const valid = await formRef.value?.validate().catch(() => false)
  if (!valid) return

  loading.value = true
  try {
    // 2. 登录接口 -> token 存入 store（自动持久化）
    await userStore.loginAction({ username: form.username, password: form.password })
    // 3. 拉取用户信息与权限（守卫中也会做，这里双保险）
    await userStore.fetchUserInfo()
    // 4. 跳转：优先回来源页
    const redirect = (route.query.redirect as string) || '/'
    router.replace(redirect)
  } finally {
    loading.value = false
  }
}
</script>
```

```text
验证清单：
1. 空表单提交被校验拦截，按钮 loading 状态正常
2. 密码错误时拦截器弹出「用户名或密码错误」提示，页面无重复弹窗
3. 登录成功后 localStorage 出现 admin-token，刷新页面登录态保持
4. 访问 /system/user 被踢到登录页，登录后自动跳回 /system/user
5. 登出后 localStorage 无残留，直接访问业务页重新要求登录
6. 用错误 token 调接口，响应拦截器自动清理并跳登录
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一个请求封装（request.ts）全局唯一，baseURL 从环境变量读取，禁止页面里直接 new axios
2. API 模块与页面解耦：页面 import 函数，接口地址/参数变化只改 api/ 文件
3. 拦截器只做横切逻辑（token 注入、401、统一提示），业务判断放页面或 action
4. store 按领域拆分，token 持久化用 pick 白名单，权限等敏感数据不持久化
5. 所有接口函数带 TS 类型（入参/出参），与后台 DTO 对齐，前后端契约化
6. 危险操作（删除/批量操作）先二次确认再发请求，取消不产生请求
7. 页面销毁/搜索条件变化时取消进行中的请求，避免竞态覆盖新数据
8. 登录、拉取用户信息、注册动态路由的流程在守卫与登录页保持同一套调用，防止状态不一致

### 踩坑记录

```text
坑 1：拦截器里 useUserStore() 报错「getActivePinia was called with no active Pinia」
结论：请求在 Pinia 激活前发起，或工具函数在组件外调用 store。
原因：拦截器回调执行时没有活跃的 pinia 实例（如 main.ts 中注册顺序问题、或在非组件模块顶层调用）。
解法：确保 app.use(pinia) 先于所有请求执行；工具函数内 useUserStore() 延迟到函数体内调用；或 main.ts 中先 createPinia 再 app.use。

坑 2：响应拦截器返回 response.data 后页面拿不到数据
结论：页面 res.rows 报 undefined，或拿到的是整个响应对象。
原因：拦截器返回层级与页面取值层级不一致，多处 .data 叠加或缺失。
解法：统一约定拦截器返回 res.data（解包后的业务数据），页面直接用；类型上用泛型约束，杜绝 .data.data 混乱。

坑 3：401 跳登录无限循环
结论：跳转登录页后马上又被踢回登录页，或请求风暴。
原因：登录接口本身返回 401 也触发 handleUnauthorized；或 401 跳转后登录页又发请求。
解法：白名单请求（登录接口）跳过 401 处理；handleUnauthorized 内判断当前路由已是 /login 则不再跳转；跳转用 replace 避免历史堆积。

坑 4：持久化后 token 是旧账号的，切账号出问题
结论：A 登录后退出，B 登录看到 A 的数据。
原因：退出只清了 store，localStorage 里 persist 插件写入的数据没清（persist 插件在 state 变化时写回，但手动 resetToken 后未触发写回或写回了空值未删除键）。
解法：退出时同时 localStorage.removeItem('admin-user')；或 persist 配置 storage 自定义，resetToken 后调用 $reset() 触发持久化更新。

坑 5：ElMessage 在 axios 封装里报「is not defined」
结论：拦截器里 ElMessage.success/error 报错。
原因：按需引入（unplugin-auto-import）时组件自动导入生效，但 ElMessage 属于 API 风格，解析器未覆盖或使用位置在插件解析范围外。
解法：request.ts 顶部显式 import { ElMessage } from 'element-plus'；确认 AutoImport 的 ElementPlusResolver 已配置。

坑 6：token 过期后所有请求同时 401，弹一堆提示
结论：并发请求全部失败，页面弹出 N 个「登录已过期」。
原因：每个请求的响应拦截器都独立执行 handleUnauthorized。
解法：用全局标志 + 队列去重：第一个 401 触发跳转，后续 401 只 reject 不再弹窗；或跳转前判断 location 是否已在 /login。

坑 7：store 解构后失去响应性
结论：const { sidebarCollapsed } = useAppStore() 后页面不更新。
原因：直接解构 state 会丢失响应式代理，得到的是快照。
解法：state/getters 用 storeToRefs 解构；actions 直接解构不受影响；或整对象 appStore.xxx 访问。

坑 8：生产环境接口 404，开发环境正常
结论：本地代理正常，部署后所有接口 404。
原因：生产构建没有代理，baseURL 仍为 /api 相对路径，但 Nginx 未转发 /api 到后台。
解法：生产 .env 配完整域名 VITE_APP_BASE_URL；或 Nginx location /api 反向代理到后台（见 22.2）；构建时确认加载的是 .env.production。
```
