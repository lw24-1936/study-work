## 概述

一套代码要跑在多个环境：开发环境（本地联调）、测试环境（提测验收）、生产环境（线上运行）。三个环境的数据库、域名、密钥、日志级别都不一样，环境管理的本质是「一套代码，多套配置」，核心手段是配置文件与环境变量，进阶手段是 Nacos 这类配置中心。

环境管理的另一半是 Mock：前端在后端接口就绪前用假数据开发，联调时切换回真实接口。Mock 与真实接口的切换必须集中管理，否则会出现「代码上线了还在调 mock 接口」这种低级事故。本章把后端多环境、配置中心、Mock 方案、小程序与 Vue 的环境切换串起来讲。

```text
环境管理全景：
1. 三环境 —— 开发、测试、生产，配置隔离，代码同源
2. 切换手段 —— 配置文件（application-{profile}.yml）+ 环境变量
3. 配置中心 —— Nacos 集中管理，动态刷新，多服务共享
4. Mock —— 前端假数据先行，联调后切真实接口
5. 小程序 —— 编译模式 + 自定义编译条件切换环境
6. Vue —— .env 文件 + import.meta.env 运行时区分
```

## 开发/测试/生产环境划分

环境划分的本质是「数据与配置的隔离」：开发环境连本地数据库随便造数据，测试环境用独立测试库验证发布内容，生产环境用真实数据。三个环境的差异集中在数据库、Redis、域名、AppSecret/密钥、日志级别、接口文档开关等配置项。

```text
三环境配置差异对照：
1. 数据库 —— dev 本地库 / test 测试库（可重置）/ prod 生产库（严格备份）
2. Redis —— 各环境独立实例，禁止共用
3. 域名 —— localhost:8080 / test-api.example.com / api.example.com
4. 密钥 —— dev/test 用测试密钥，prod 用正式 AppSecret 与支付密钥
5. 日志级别 —— dev DEBUG / test INFO / prod INFO+WARN 告警
6. 文档开关 —— springdoc 仅 dev/test 开启，prod 关闭
7. 支付 —— dev/test 用沙箱（微信支付沙箱/模拟回调），prod 真实支付
```

环境隔离不到位是线上事故的头号来源：开发环境连了生产库、测试环境发真实短信、本地代码带着生产密钥提交——每一种都真实发生过。铁律三条：密钥不落库不提交（环境变量注入）、环境变量全局唯一（每个环境一套）、数据库连接串禁止写死在代码里。

```text
环境隔离铁律：
1. 密钥不进代码 —— AppSecret/支付密钥走环境变量或配置中心
2. 连接串不硬编码 —— 数据库/Redis 地址按环境注入
3. 数据可重置 —— 测试环境数据库可随时重建，不心疼
4. 沙箱先行 —— 支付、短信、消息推送 dev/test 一律沙箱
5. 环境标识 —— 返回体/页面带环境标识（如测试环境 banner），防止误操作
6. 权限分离 —— 生产环境运维权限收敛，变更走审批
```

## Spring Boot 多环境配置

Spring Boot 用 profile 机制管理多环境：主配置 application.yml 放公共配置，application-dev.yml、application-test.yml、application-prod.yml 放各环境差异配置，启动时通过 spring.profiles.active 指定激活哪个 profile。这是最基础也最可靠的环境切换方式。

```yaml
# application.yml —— 公共配置
server:
  port: 8080

spring:
  profiles:
    active: dev          # 默认激活 dev，部署时用启动参数覆盖
  application:
    name: mall-backend

mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl   # dev 打印 SQL
```

```yaml
# application-dev.yml —— 开发环境
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mall_dev?useUnicode=true&characterEncoding=utf8
    username: root
    password: dev123456
  data:
    redis:
      host: localhost
      port: 6379

wx:
  appid: wxdev000000000000
  secret: dev-secret-not-real
```

```yaml
# application-prod.yml —— 生产环境
spring:
  datasource:
    url: jdbc:mysql://${DB_HOST}:3306/mall_prod?useUnicode=true&characterEncoding=utf8
    username: ${DB_USER}
    password: ${DB_PASSWORD}       # 从环境变量注入，不落配置文件
  data:
    redis:
      host: ${REDIS_HOST}
      port: ${REDIS_PORT}

wx:
  appid: ${WX_APPID}
  secret: ${WX_APPSECRET}

springdoc:
  api-docs:
    enabled: false                  # 生产关闭接口文档
  swagger-ui:
    enabled: false
```

生产环境的敏感配置一律用 ${ENV_VAR} 占位符引用环境变量（部署时由运维注入），配置文件里只留占位符不写真实值。启动命令示例：java -jar mall.jar --spring.profiles.active=prod，profile 与 env 变量都可以覆盖 application.yml 里的默认值。

```text
Spring Boot 多环境要点：
1. 命名规范 —— application-{profile}.yml，dev/test/prod 三个
2. 激活方式 —— 启动参数 --spring.profiles.active=prod 或环境变量 SPRING_PROFILES_ACTIVE
3. 敏感配置 —— prod 用 ${ENV_VAR} 注入，禁止明文写在 yml
4. 日志分级 —— dev DEBUG 看细节，prod INFO 以上控制量
5. 文档开关 —— springdoc 按环境开启/关闭
6. 数据库迁移 —— 测试库用 Flyway/Liquibase 管理结构变更
```

## Nacos 配置中心与配置管理

项目规模上来后（多服务、多环境、频繁调整配置），本地配置文件开始力不从心：改个配置要重新打包发布，多服务配置散落各处难审计。Nacos（阿里开源）作为配置中心解决两件事：配置集中管理（一个控制台看所有服务的配置）与动态刷新（改配置推送到运行中的服务，不用重启）。

```text
Nacos 核心概念：
1. Data ID —— 配置的唯一标识，如 mall-backend-dev.yml
2. Group —— 配置分组，默认 DEFAULT_GROUP
3. Namespace —— 环境隔离，dev/test/prod 各一个命名空间
4. 动态刷新 —— @RefreshScope 注解的 Bean 可热更新配置
5. 配置优先级 —— Nacos 配置 > 本地 application.yml（可配置覆盖关系）
6. 服务注册 —— Nacos 同时承担注册中心职责（Spring Cloud Alibaba）
```

引入 Nacos 配置需要 Spring Cloud Alibaba 依赖，本地优先读取 Nacos 中的配置，找不到再读本地文件：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
```

```yaml
# bootstrap.yml —— 指定 Nacos 地址与配置归属
spring:
  application:
    name: mall-backend
  cloud:
    nacos:
      config:
        server-addr: nacos.example.com:8848
        namespace: ${NACOS_NAMESPACE}   # dev/test/prod 各一个 namespace
        file-extension: yml
      discovery:
        server-addr: nacos.example.com:8848
```

```text
配置项规范：
1. 命名 —— 小写驼峰 + 前缀分组（wx.appid、pay.mchId、sms.signName）
2. 注释 —— 每个配置项写明用途、取值范围、影响面
3. 分级 —— 常量进代码、环境相关进配置中心、密钥进密钥管理
4. 审计 —— 配置变更走 Nacos 权限控制与历史版本，可回滚
5. 敏感配置 —— Nacos 加密插件或对接 KMS，禁止明文存密钥
6. 文档 —— 配置清单随项目文档维护，标注每个配置项的来源
```

选择建议：单服务、小团队起步用 application-{profile}.yml + 环境变量足够，不要为配置中心而配置中心；多服务、需要动态调整、配置项多的项目再上 Nacos。

## Mock 数据方案

Mock（模拟数据）是前后端并行开发的桥梁：后端接口没写完，前端用 Mock 数据把页面先做出来。三个层次的 Mock 方案按需选择：本地 Mock（代码里写死假数据）、mockjs（拦截请求返回随机数据）、后端 Mock 接口（后端提供一个假实现）。

```text
Mock 方案对比：
1. 本地 Mock —— 前端代码里直接写假对象，最简单，但切换麻烦
2. mockjs —— 拦截 wx.request/axios，按模板生成随机数据，字段形态真实
3. 后端 Mock —— 后端先按文档实现假返回（写死 JSON 或开关控制），贴近真实
4. 抓包工具 Mock —— Charles Map Local 把响应映射到本地 JSON 文件
5. Apifox Mock —— 根据接口定义自动生成 Mock 响应，管理端调试可用
6. 选择标准 —— 单页面本地 Mock；列表交互 mockjs；全链路联调后端 Mock
```

mockjs 在小程序里的用法：在入口文件按环境开关加载 mock 模块，mock 模块里用 Mock.mock 拦截 wx.request：

```js
// mock/index.js —— 小程序 mock 入口
const Mock = require('./mock-miniprogram.js')  // mockjs 小程序适配版
const { mockEnable } = require('../config.js') // 总开关，环境切换时改

if (mockEnable) {
  // 拦截商品列表接口，返回模拟数据
  Mock.mock(/\/api\/v1\/products/, 'get', {
    code: 0,
    message: '成功',
    data: {
      total: 56,
      page: 1,
      pageSize: 10,
      'list|10': [{
        'id|+1': 1001,
        'name': '@ctitle(6, 12)',           // 随机中文标题
        'price|100-9999': 100,              // 随机价格（分）
        'stock|0-1000': 100,
        'status|0-1': 1,
        'image': '@image("400x400", "#4A7BF7", "MOCK")'
      }]
    }
  })
}
```

```text
Mock 使用要点：
1. 总开关 —— mockEnable 集中在 config.js，禁止散落页面
2. 数据真实 —— 字段名、类型、单位与接口文档完全一致
3. 边界覆盖 —— Mock 数据要包含空列表、超长文本、异常值场景
4. 时机 —— 后端接口自测通过即切真实接口，Mock 只做并行开发用
5. 收尾 —— 联调完成后删除/关闭 Mock，防止误上线
6. 线上兜底 —— 生产环境 mockEnable 必须为 false，构建时强制注入
```

联调时 Mock 与真实的切换统一走 config.js 一个开关，不要每个页面各自判断。常见的翻车姿势：页面里临时写死一段假数据，联调完忘了删，上线后页面数据永远不变——这类事故一律通过「Mock 集中管理 + 上线检查清单」来杜绝。

## 小程序环境切换

小程序没有像 Vue 那样的 .env 构建机制，环境切换靠编译模式与自定义编译条件：开发者工具「编译模式」里可以配置多个编译模式（开发/测试/生产），每个模式带自定义参数，代码里用 wx.getAccountInfoSync() 或编译条件参数读取当前环境。

```js
// utils/config.js —— 小程序环境配置
const accountInfo = wx.getAccountInfoSync()
// miniProgram.envVersion: develop（开发版）/ trial（体验版）/ release（正式版）
const envVersion = accountInfo.miniProgram.envVersion

const ENV_CONFIG = {
  develop: {                     // 开发版：工具模拟器与真机调试
    baseUrl: 'http://localhost:8080/api/v1',
    mockEnable: true
  },
  trial: {                       // 体验版：测试环境
    baseUrl: 'https://test-api.example.com/api/v1',
    mockEnable: false
  },
  release: {                     // 正式版：生产环境
    baseUrl: 'https://api.example.com/api/v1',
    mockEnable: false
  }
}

module.exports = {
  env: envVersion,
  baseUrl: ENV_CONFIG[envVersion].baseUrl,
  mockEnable: ENV_CONFIG[envVersion].mockEnable
}
```

微信官方接口 wx.getAccountInfoSync() 能拿到当前运行版本（develop/trial/release），天然区分三种环境，这是小程序环境切换的首选方案。测试环境想连特定后端，可以用自定义编译条件：工具「编译模式 → 添加编译模式 → 启动参数」，代码里读 options 或全局变量区分。

```text
小程序环境切换要点：
1. envVersion —— wx.getAccountInfoSync() 区分 develop/trial/release
2. 自定义编译条件 —— 工具里配置多个编译模式，各带不同参数
3. baseUrl 集中 —— 环境与 URL 映射只写在 config.js 一处
4. mock 开关 —— 与环境绑定，release 强制 false
5. 版本区分 —— 开发版/体验版/正式版各自独立调试
6. 真机调试 —— 真机调试模式属于 develop 环境，可连本地
```

## Vue 环境切换

Vue3 + Vite 用 .env 文件管理环境：项目根目录放 .env.development（npm run dev）、.env.production（npm run build）、.env.test（测试构建），变量以 VITE_ 前缀声明，代码里通过 import.meta.env 读取。Vite 在构建时按 mode 注入对应文件，天然支持多环境。

```text
Vue 环境文件结构：
1. .env.development —— 开发环境，npm run dev 时加载
2. .env.test —— 测试环境，npm run build:test 时加载
3. .env.production —— 生产环境，npm run build 时加载
4. 变量前缀 —— 只有 VITE_ 开头的变量会暴露给前端代码
5. 读取方式 —— import.meta.env.VITE_API_BASE_URL
6. 敏感数据 —— 前端环境变量没有秘密，密钥必须放后端
```

```text
# .env.development
VITE_API_BASE_URL=/api
VITE_MOCK_ENABLE=true

# .env.production
VITE_API_BASE_URL=/api
VITE_MOCK_ENABLE=false
```

```js
// src/config/index.js —— Vue 端读取环境配置
export default {
  baseURL: import.meta.env.VITE_API_BASE_URL || '/api',
  mockEnable: import.meta.env.VITE_MOCK_ENABLE === 'true'
}
```

axios 封装里使用该配置，VITE_MOCK_ENABLE 为 true 时走 mock 适配层（拦截请求返回假数据），false 时直连真实接口。package.json 里配置构建命令，让测试与生产构建各走各的环境文件：

```json
{
  "scripts": {
    "dev": "vite",
    "build:test": "vite build --mode test",
    "build": "vite build --mode production"
  }
}
```

```text
Vue 环境切换要点：
1. 文件命名 —— .env.{mode}，mode 由 --mode 参数指定
2. 前缀约束 —— VITE_ 前缀的变量才会打进前端包
3. 构建注入 —— 打包时变量固化，运行时改不了（这是特性不是缺陷）
4. mock 开关 —— 测试构建可开 mock，生产构建必须关
5. 反向代理 —— 生产环境 /api 由 Nginx 反代到后端（见 22.2）
6. 检查产物 —— 构建后确认产物里没有测试地址残留
```

## 应用场景实战

### 场景一：Spring Boot 三环境切换全流程

项目从本地开发到测试验收再到生产发布，环境切换流程：

```text
步骤：
1. 本地开发 —— application.yml 默认 profile=dev，连本地库，日志 DEBUG
2. 联调自测 —— 后端自测通过，通知前端联调，接口文档保持同步
3. 提交测试 —— 代码合并测试分支，CI 构建 jar 包 --spring.profiles.active=test
4. 测试验收 —— 测试环境独立库独立域名，验收通过出测试报告
5. 发布生产 —— 运维部署 --spring.profiles.active=prod，环境变量注入密钥
6. 配置校验 —— 生产启动后检查日志：连的库、用的域名、开关状态
7. 冒烟 —— 生产环境登录、下单、支付回调全链路冒烟
8. 回滚预案 —— 出问题回滚上一版本，配置随版本回滚
```

```text
场景一验证点：
1. 各环境数据库独立 —— 数据互不可见
2. 密钥由环境变量注入 —— 代码仓库无明文密钥
3. 文档开关 —— 生产环境 /doc.html 不可访问
4. 日志级别 —— 生产无 DEBUG 日志刷屏
```

### 场景二：小程序端 Mock 到真实的平滑切换

后端订单接口还在开发，小程序端先用 mockjs 并行开发订单列表与详情页，联调后切真实接口：

```text
步骤：
1. config.js 里 mockEnable=true，baseUrl 指向开发环境
2. mock/index.js 用 Mock.mock 拦截订单列表、详情、创建接口
3. 前端按接口文档字段开发页面，mock 数据字段与文档一致
4. 页面开发完成，后端接口也自测通过
5. 联调开始：mockEnable=false，请求真实后端
6. 逐接口验证：列表、详情、创建、错误场景
7. 差异处理 —— 字段、状态码与 mock 不一致的，以文档为准修正
8. 收尾 —— 确认 mock 开关在 release 环境恒为 false，构建产物无 mock 残留
```

```text
场景二验证点：
1. 并行效率 —— 后端未完成时前端页面已可交互
2. 契约一致 —— mock 字段与最终真实接口完全一致
3. 切换干净 —— 联调后无任何页面还在用假数据
4. 回归 —— 切换后订单主流程全链路走通
```

## 最佳实践与踩坑记录

### 最佳实践

1. 环境配置收敛：dev/test/prod 三套配置集中管理，敏感项一律环境变量注入
2. Mock 总开关化：mockEnable 只在 config.js 定义，页面不出现临时假数据
3. 构建期强制：小程序与 Vue 的 release/生产构建强制 mock=false，防止误上线
4. 环境标识：测试环境页面/接口带明显标识（banner、返回头），防误操作
5. 密钥零提交：AppSecret、支付密钥、数据库密码通过环境变量或 Nacos 注入，提交前用 git 扫描
6. 切换验证清单：每次环境切换后验证数据库、域名、日志、文档开关四项
7. 配置变更留痕：Nacos/配置文件变更记录原因与操作人，可回滚
8. 上线检查：合法域名、证书、CORS 白名单、环境标识随发布清单逐项核对

### 踩坑记录

```text
坑 1：开发环境连了生产数据库
结论：本地开发时不小心连上生产库，测试数据污染线上。
原因：本地 application.yml 里写了生产连接串，或复制粘贴了 prod 配置。
解法：本地配置一律用 dev 专属连接串；生产连接串只允许 ${ENV_VAR} 注入，禁止出现在仓库文件。

坑 2：AppSecret 被提交到 Git 仓库
结论：代码仓库里发现明文 AppSecret，微信接口被恶意调用风险。
原因：配置写在 application.yml 直接提交，没有走环境变量。
解法：立即重置 AppSecret；所有密钥改环境变量注入；配置 .gitignore 排除敏感配置文件；用 gitleaks 扫描历史提交。

坑 3：Mock 数据忘关，上线后页面数据不变
结论：生产环境页面显示的永远是假数据，真实接口没被调用。
原因：页面里写死了假数据，联调完没删；或 mock 开关没按环境强制关闭。
解法：mock 集中管理 + 构建期强制关闭；上线检查清单核对「无 mock 残留」。

坑 4：改了 application.yml 没重启，配置不生效
结论：修改端口/数据库后启动的仍是旧配置，排查半天。
原因：Spring Boot 配置在启动时加载，普通修改需重启（Nacos 动态刷新除外）。
解法：改配置后重启验证；用 Nacos 的场景给 Bean 加 @RefreshScope 实现热更新。

坑 5：小程序 release 环境还是调的测试地址
结论：正式版小程序请求的是 test-api 域名，数据混乱。
原因：环境判断逻辑写死或 envVersion 判断错误，release 没映射到生产 baseUrl。
解法：用 wx.getAccountInfoSync().miniProgram.envVersion 做映射，三环境映射集中在一处；上线前真机预览确认请求域名。

坑 6：测试环境发的真实短信/邮件
结论：测试环境触发短信发送，用户收到骚扰短信，被投诉。
原因：测试环境没有接入短信沙箱，代码里没做环境判断。
解法：短信、支付等外部服务 dev/test 一律沙箱；用配置项 sms.mock=true 控制，测试环境强制开启。

坑 7：生产环境接口文档未关闭
结论：生产环境 /doc.html 可访问，接口细节全部暴露。
原因：springdoc 没有按环境关闭，prod 配置缺失。
解法：application-prod.yml 设置 springdoc.api-docs.enabled=false、swagger-ui.enabled=false；验证生产访问 404。

坑 8：Vite 构建产物里残留测试环境地址
结论：生产页面请求打到测试服务器，登录状态错乱。
原因：构建命令没有区分 mode，或 .env 变量引用错误。
解法：按环境配置 build 脚本（build / build:test）；构建后检查产物 grep 测试域名；CI 里加产物校验步骤。
```
