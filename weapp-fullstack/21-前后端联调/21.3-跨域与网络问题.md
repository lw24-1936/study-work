## 概述

跨域与网络问题贯穿整个联调周期：Vue 管理端在浏览器里访问后端会触发 CORS 跨域拦截，小程序真机访问需要 HTTPS 合法域名，上线后还会遇到证书过期、DNS 解析、防火墙等网络故障。这些问题表面症状都是「请求失败」，但根因千差万别，必须按层次排查。

本章先讲清楚 CORS 的原理与后端配置（这是 Vue 端最常见的报错），再讲 HTTPS 证书的来龙去脉（小程序线上请求的硬性门槛），最后给出真机网络与通用网络异常的排查路径。理解了「同源、预检、证书链、合法域名」这四个概念，绝大多数网络类问题都能自己定位。

```text
网络问题全景：
1. 同源策略 —— 浏览器安全模型，前端跨域请求被拦截的本质原因
2. CORS —— 服务端声明允许跨域，Access-Control-Allow-Origin 响应头
3. 预检请求 —— 复杂请求先发 OPTIONS 探路，后端必须响应
4. HTTPS 证书 —— 小程序线上域名硬性要求，证书链必须完整
5. 合法域名 —— 小程序后台配置 request 域名白名单
6. 排查路径 —— DNS → 证书 → 连通性 → 防火墙 → 后端日志
```

## 同源策略与 CORS 原理

同源策略是浏览器的安全基石：协议、域名、端口三者完全一致才算同源，不同源的页面不能随意读取对方的资源。Vue 管理端运行在 http://localhost:5173，后端在 http://localhost:8080——端口不同即不同源，浏览器会拦截页面发出的跨域 XHR/fetch 请求。

CORS（Cross-Origin Resource Sharing，跨域资源共享）是服务端主动放行的机制：后端在响应头里声明 Access-Control-Allow-Origin 允许哪些来源访问，浏览器看到许可后才把响应交给页面。整个流程是「浏览器先拦截，后端开白名单」，所以 CORS 必须在后端配置，前端改代码解决不了。

```text
CORS 关键响应头：
1. Access-Control-Allow-Origin —— 允许的来源，如 http://localhost:5173 或 *
2. Access-Control-Allow-Methods —— 允许的方法，如 GET, POST, PUT, DELETE
3. Access-Control-Allow-Headers —— 允许的自定义请求头，如 Authorization, Content-Type
4. Access-Control-Allow-Credentials —— 是否允许携带 Cookie，true 时 Origin 不能为 *
5. Access-Control-Max-Age —— 预检结果缓存秒数，减少重复预检
6. Access-Control-Expose-Headers —— 允许前端读取的响应头白名单
```

注意：小程序 wx.request 不受同源策略约束（它运行在微信客户端而非浏览器），所以小程序端没有 CORS 问题；CORS 只影响浏览器端（Vue 管理后台、H5）。这是很多新手搞混的点——小程序联调报跨域，多半是误报或者问题根本不在 CORS。

## Spring Boot 后端 CORS 配置

Spring Boot 提供两档 CORS 配置：简单场景用 @CrossOrigin 注解直接标注在 Controller 或方法上；项目级统一配置用 WebMvcConfigurer 的 addCorsMappings 方法，全局生效、集中管理。生产环境建议用后者，并配合配置项动态指定允许的来源。

```java
// 方式一：注解式，适合单接口快速放行
@RestController
@RequestMapping("/api/v1/products")
@CrossOrigin(origins = "http://localhost:5173")
public class ProductController {
    // 接口实现省略
}
```

```java
// 方式二：全局配置，项目统一管理，推荐
@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:5173", "https://admin.example.com")
                .allowedMethods("GET", "POST", "PUT", "DELETE", "PATCH", "OPTIONS")
                .allowedHeaders("*")
                .allowCredentials(true)
                .maxAge(3600);
    }
}
```

allowedOrigins 明确列出可信来源，生产环境不要用 "*"（配合 allowCredentials(true) 时浏览器直接拒绝）。allowedMethods 记得包含 OPTIONS（预检用）与 PATCH。addMapping("/api/**") 只对 API 路径生效，静态资源不参与跨域。

```text
CORS 配置要点：
1. 作用域 —— addMapping("/api/**") 限定路径，避免全站放开
2. 来源白名单 —— 生产环境明确列出域名，禁止 *
3. 方法齐全 —— 必须包含 OPTIONS，PATCH 也常被漏掉
4. 凭据 —— 需要 Cookie 时 allowCredentials(true) 且 Origin 不能是 *
5. 环境差异 —— 开发/测试/生产来源不同，来源列表做成配置项
6. 网关场景 —— 经 Nginx/网关反代时，CORS 也可在网关层统一配置
```

如果项目引入了 Spring Security，还要注意 Security 过滤器链对 OPTIONS 预检请求的处理：预检请求不带认证头，会被认证过滤器拦截返回 401，前端表现为「预检失败」。需要放行 OPTIONS 方法（详见下方预检请求章节）。

## 预检请求 OPTIONS 详解

浏览器把跨域请求分为两类：简单请求（Simple Request）与预检请求（Preflighted Request）。满足全部条件（GET/POST/HEAD 方法、仅标准头、Content-Type 为 text/plain、multipart/form-data 或 application/x-www-form-urlencoded）的是简单请求，直接发出；否则浏览器先发一个 OPTIONS 预检请求询问服务器「允不允许这种跨域请求」，服务器响应许可后浏览器才发真实请求。

小程序登录、下单这类接口通常带 Authorization 头与 application/json 的 Content-Type，属于预检请求。前端 Network 面板看到「请求失败」下面跟着一条 OPTIONS 请求，就是预检被拦了。

```text
预检请求特征：
1. 触发条件 —— 自定义头（Authorization）、application/json、PUT/DELETE 等
2. 请求方式 —— 自动发出 OPTIONS，不带业务参数
3. 请求头 —— Access-Control-Request-Method 声明真实方法
4. 请求头 —— Access-Control-Request-Headers 声明要带的自定义头
5. 响应 —— 后端返回 2xx + Allow-* 头，浏览器才放行真实请求
6. 缓存 —— Access-Control-Max-Age 让浏览器一段时间内免重复预检
```

后端要保证 OPTIONS 请求能被正常响应。Spring MVC 的 CORS 配置会自动处理 OPTIONS；但如果项目里加了拦截器（Interceptor）或 Spring Security，常见坑是拦截器把 OPTIONS 也拦了。解决方式：在拦截器/过滤器链里放行 OPTIONS 请求。

```java
// Spring Security 场景：放行预检请求
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .cors(Customizer.withDefaults())   // 启用 Spring MVC 的 CORS 配置
        .csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()  // 放行预检
            .anyRequest().authenticated())
        .formLogin(Customizer.withDefaults());
    return http.build();
}
```

```text
预检排查要点：
1. Network 面板 —— 先看有没有 OPTIONS 请求，没有说明是简单请求
2. 预检 403 —— 拦截器或 Security 过滤链拦截了 OPTIONS
3. 预检 404 —— 网关/Nginx 没把 OPTIONS 转发到后端
4. 预检 200 但真实请求仍失败 —— 看 Allow-* 头是否包含目标方法
5. 提示 CORS error 但无 OPTIONS —— 看是不是服务器 500 且没带 CORS 头
6. 后端日志 —— OPTIONS 请求根本没进 Controller 属于正常，被拦才异常
```

## HTTPS 与证书

小程序线上环境要求所有 request 请求必须是 HTTPS 且证书有效，这是硬性门槛：微信不允许小程序请求 HTTP 明文接口。HTTPS = HTTP + TLS 加密，证书（SSL 证书）由 CA（证书颁发机构）签发，用于验证服务器身份并协商加密密钥。

```text
证书类型对比：
1. DV 证书 —— 仅验证域名所有权，签发快，个人/小团队首选
2. OV 证书 —— 验证组织信息，企业形象需求，审核 1-3 天
3. EV 证书 —— 最高级别，浏览器地址栏显示公司名，费用高
4. 免费证书 —— 阿里云/腾讯云/Let's Encrypt 提供，90 天有效期需自动续期
5. 通配符证书 —— *.example.com 覆盖所有子域名，多服务共用
6. 自签名证书 —— 仅本地测试用，线上会被微信/浏览器拒绝
```

证书部署到 Nginx 后，必须保证证书链完整：服务器下发的证书链要包含站点证书 + 中间证书（CA 根证书内置在客户端）。常见错误是只配了站点证书没配中间证书，浏览器/微信报「证书链不完整」或「证书不受信任」。验证用 https://myssl.com 或 openssl 检查。

```text
证书申请流程（以阿里云/腾讯云 DV 免费证书为例）：
1. 购买/申请免费证书 —— 云控制台 SSL 证书服务，选 DV 单域名
2. 绑定域名 —— 填写要保护的域名 api.example.com
3. 验证域名所有权 —— DNS 解析验证（添加 TXT 记录）或文件验证
4. 签发下载 —— 审核通过后下载 Nginx 格式证书包（pem + key）
5. 上传服务器 —— 放到 /etc/nginx/ssl/ 目录，设置 600 权限
6. 配置 Nginx —— 按下方配置填入证书路径并 reload
7. 验证 —— https://myssl.com 检测证书链、协议版本、部署评分
8. 到期续期 —— 免费证书 90 天，配置 certbot 或云平台自动续期
```

```text
Nginx 证书配置：
server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /etc/nginx/ssl/api.example.com.pem;      # 站点证书 + 中间证书
    ssl_certificate_key /etc/nginx/ssl/api.example.com.key;      # 私钥
    ssl_protocols       TLSv1.2 TLSv1.3;                         # 禁用 TLSv1.0/1.1
    ssl_ciphers         HIGH:!aNULL:!MD5;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

```text
证书要点：
1. 有效期 —— 免费证书 90 天，配置自动续期（certbot/certbot renew）
2. 证书链 —— pem 文件拼接站点证书 + 中间证书，顺序不能反
3. 私钥匹配 —— 证书与私钥必须配对，不配对握手直接失败
4. 协议版本 —— 仅启用 TLSv1.2/TLSv1.3，老旧协议有漏洞
5. 到期预警 —— 域名商/云监控配置证书到期告警，提前 30 天
6. 本地测试 —— 自签名证书 + 开发者工具「不校验」仅限开发
```

## 小程序真机网络与域名校验

小程序请求域名必须满足两个条件：HTTPS 协议，且域名已配置在小程序后台的 request 合法域名列表中。合法域名配置位置：小程序后台 → 开发管理 → 开发设置 → 服务器域名 → request 合法域名，保存后需要一段时间生效，体验版/正式版请求才会走该校验。

```text
合法域名配置流程：
1. 登录 mp.weixin.qq.com 小程序后台
2. 开发 → 开发管理 → 开发设置 → 服务器域名
3. 在 request 合法域名里添加 https://api.example.com
4. 域名必须备案且已配置 HTTPS（证书有效）
5. 保存后约 5 分钟生效，小程序端重新编译/发布
6. 修改域名会触发一次「修改服务器域名」校验，需管理员扫码确认
```

真机预览的两种模式差别很大：普通预览模式下，真机请求域名校验与正式版一致（未配置的域名请求失败，此时可以在开发者工具「详情 → 本地设置」勾选不校验合法域名，但该选项只对工具模拟器生效，真机预览依旧校验）；「真机调试」模式（工具右上角真机调试按钮）下手机连接工具，可以请求本地开发环境接口，方便看日志。线上用户访问的正式版则严格校验合法域名。

```text
真机网络约束：
1. 正式版 —— 必须 HTTPS + 合法域名白名单，缺一不可
2. 体验版 —— 同正式版校验，用于发布前测试
3. 真机调试 —— 可连本地开发环境，便于联调看日志
4. 普通预览 —— 走正式校验，但工具「不校验域名」勾选只影响模拟器
5. 开发阶段 —— 用真机调试模式代替预览，避免域名未配置的干扰
6. 上线前 —— 域名必须完成 ICP 备案与证书部署，提前 2-3 周准备
```

注意一个高频坑：本地开发时为了省事勾选了「不校验合法域名」，上线前忘记把域名配置进合法域名列表，结果体验版里所有请求失败。流程上应该把「合法域名配置」列为上线检查清单的固定项（详见 16.2 章节）。

小程序端可以在请求前检测网络状态，给出友好提示而不是直接失败：

```js
// utils/network.js —— 网络状态检测
function checkNetwork() {
  return new Promise((resolve) => {
    wx.getNetworkType({
      success(res) {
        // res.networkType: wifi / 4g / 3g / 2g / none
        if (res.networkType === 'none') {
          wx.showToast({ title: '网络已断开，请检查网络连接', icon: 'none' })
          resolve(false)
        } else {
          resolve(true)
        }
      },
      fail() {
        resolve(true) // 检测失败不阻塞请求，交给请求层处理
      }
    })
  })
}

module.exports = { checkNetwork }
```

弱网（2g/3g）场景还可以用 wx.onNetworkStatusChange 监听网络切换，在断网恢复后自动重试关键请求或刷新页面数据，这是提升弱网体验的常用手段，联调时配合 Charles 弱网模拟验证效果。

```text
网络检测要点：
1. wx.getNetworkType —— 请求前检测，none 时直接提示不发起请求
2. wx.onNetworkStatusChange —— 监听网络切换，恢复后刷新数据
3. 弱网策略 —— 2g/3g 时降低图片质量、延长超时时间
4. 请求重试 —— 仅对幂等接口（GET、查询类）做自动重试
5. 检测失败兜底 —— 检测 API 异常时放行请求，由 wx.request fail 处理
6. 联调验证 —— Charles Throttle 模拟 2g/3g 验证降级逻辑
```

## 网络异常排查

网络请求失败时，按层次从上往下排查，每层都有明确的验证手段。切忌跳过排查直接改代码，多数「玄学」网络问题都能在某一层找到实锤。

```text
网络排查五层：
1. DNS 层 —— nslookup api.example.com 看解析结果；域名未解析/解析到旧 IP
2. 连通层 —— ping 域名、telnet 域名 443 看端口通不通；防火墙/安全组拦截
3. 证书层 —— 浏览器访问看锁图标，openssl s_client -connect 域名:443 检查证书链
4. 应用层 —— curl -I https://api.example.com/api/v1/... 看后端是否响应
5. 代码层 —— Charles 抓包对比工具与小程序请求差异
```

```text
常用排查命令：
1. nslookup api.example.com —— 域名解析结果与 TTL
2. ping api.example.com —— 基础连通性（部分服务器禁 ping 属正常）
3. telnet api.example.com 443 —— 端口连通性，通不通一目了然
4. curl -v https://api.example.com/api/v1/products —— 完整握手与响应过程
5. openssl s_client -connect api.example.com:443 -servername api.example.com —— 证书链检查
6. dig api.example.com @8.8.8.8 —— 指定公共 DNS 验证解析
```

超时问题单独说明：小程序 wx.request 默认超时 60 秒（可配置 timeout），弱网下接口响应慢会导致请求超时。排查时先看 Charles 里接口真实耗时，再决定是优化接口（SQL、缓存）还是调超时时间。连接被重置（Connection reset）多半是防火墙/安全组/运营商干扰，配合 telnet 与服务器端日志定位。

```text
异常分类速查：
1. 请求未发出 —— 域名校验、代理配置、代码逻辑未执行
2. DNS 解析失败 —— 域名没解析、DNS 缓存、域名过期
3. 连接超时 —— 防火墙拦截、服务器宕机、安全组未放行端口
4. 证书错误 —— 证书过期、证书链不完整、域名不匹配
5. 400/401/403 —— 参数、Token、权限问题，看后端日志
6. 500/502/503 —— 后端异常、网关超时、服务未启动
7. 偶发失败 —— 弱网丢包、连接池耗尽、限流触发
```

## 应用场景实战

### 场景一：Vue 管理端跨域报错全流程解决

管理端开发环境访问后端接口，浏览器报 CORS error，按流程解决：

```text
步骤：
1. 复现 —— 打开管理端页面，Network 面板看到两条请求：OPTIONS 与 GET
2. 确认根因 —— OPTIONS 预检请求被拦截，或 GET 响应缺少 CORS 头
3. 后端配置 —— WebMvcConfigurer 全局 CORS，allowedOrigins 加 localhost:5173
4. 验证预检 —— 重新请求，OPTIONS 返回 200 + Allow-* 响应头
5. 验证真实请求 —— GET 返回 200，响应头带 Access-Control-Allow-Origin
6. 检查 Security —— 若 OPTIONS 仍 401，放行 OPTIONS 方法
7. 生产域名 —— 上线前把 https://admin.example.com 加入白名单
8. 收尾 —— 本地与生产各验证一次，CORS 配置纳入发布清单
```

```text
场景一验证点：
1. OPTIONS 请求返回 200 —— 预检放行
2. 响应头包含 Access-Control-Allow-Origin —— 与前端来源一致
3. 携带 Authorization 的请求成功 —— 自定义头在 Allow-Headers 中
4. 生产域名验证 —— 白名单覆盖线上管理端域名
```

### 场景二：小程序真机请求失败的逐层排查

线上体验版所有请求失败，用户反馈「页面打不开」，按五层排查：

```text
步骤：
1. 看报错 —— 微信提示「request:fail」，属于网络层失败
2. DNS 层 —— nslookup api.example.com，确认域名解析正常
3. 连通层 —— telnet api.example.com 443，确认端口可达
4. 证书层 —— 浏览器打开 https://api.example.com 检查证书是否过期/链是否完整
5. 应用层 —— curl 请求一个真实接口，确认后端服务正常响应
6. 域名校验 —— 检查小程序后台 request 合法域名是否包含该域名
7. 定位根因 —— 证书过期（微信严格校验证书有效性），续期后恢复
8. 复盘 —— 配置证书到期监控告警，避免再次发生
```

```text
场景二验证点：
1. 每层有实锤 —— 各层命令输出作为排查依据
2. 根因唯一 —— 最终定位到证书过期而非后端代码问题
3. 预防措施 —— 证书监控告警上线
4. 回归 —— 证书续期后真机请求恢复正常
```

## 最佳实践与踩坑记录

### 最佳实践

1. CORS 白名单化：生产环境 allowedOrigins 明确列出域名，来源做成配置项按环境注入
2. 小程序端无需 CORS：wx.request 不受同源策略约束，不要在 CORS 上浪费排查时间
3. 证书自动化：免费证书配置 certbot 自动续期 + 到期告警，提前 30 天提醒
4. 合法域名前置：开发期就把正式域名备好案、配好证书、加进合法域名列表
5. 排查分层进行：DNS → 端口 → 证书 → 应用 → 代码，每层有实锤再进下一层
6. 弱网必测：上线前 Charles 弱网模拟验证超时与重试逻辑
7. 上线清单化：证书有效期、合法域名、CORS 白名单列为发布检查项
8. 日志与监控：后端记录请求失败日志，配合网络监控快速定位线上网络问题

### 踩坑记录

```text
坑 1：CORS 配置了但浏览器还是报跨域
结论：响应头没有 Access-Control-Allow-Origin，前端仍然被拦截。
原因：项目引入了 Spring Security，Security 过滤链先于 MVC 的 CORS 处理，预检被 401 拦截。
解法：Security 配置里 .cors(Customizer.withDefaults()) 启用 MVC CORS 配置；放行 OPTIONS。

坑 2：allowedOrigins 配了 * 且开启 allowCredentials 导致请求直接失败
结论：浏览器报错「The value of the 'Access-Control-Allow-Origin' header ... must not be the wildcard」。
原因：allowCredentials(true) 时 Origin 不允许为 *，浏览器强制拒绝。
解法：明确列出来源域名；或按来源动态生成 Origin 回显。

坑 3：预检请求 OPTIONS 被网关返回 404
结论：前端报 CORS error，Network 面板 OPTIONS 请求 404。
原因：Nginx/网关只转发了 GET/POST 等常规方法，OPTIONS 没被转发到后端。
解法：Nginx location 里放开 OPTIONS：if ($request_method = OPTIONS) { return 204; } 或直接透传。

坑 4：微信提示「不在以下 request 合法域名列表中」
结论：体验版/正式版请求被拒，模拟器却正常。
原因：工具勾选了不校验域名只对本地模拟器生效，线上严格校验。
解法：小程序后台配置 request 合法域名（HTTPS + 备案），保存后重编译验证。

坑 5：HTTPS 证书过期，用户端大面积请求失败
结论：某天开始线上小程序所有请求失败，浏览器访问提示证书过期。
原因：免费证书 90 天有效期，没有续期也没有告警。
解法：certbot renew 自动续期 + 云监控证书到期告警；排查时用浏览器/curl 先验证证书。

坑 6：证书链不完整，iOS 微信里报「证书无效」
结论：Android 正常，iOS 微信报证书错误；浏览器有时也提示。
原因：服务器只下发站点证书，缺少中间证书，iOS 校验更严格。
解法：pem 文件拼接「站点证书 + 中间证书」后重载 Nginx；用 myssl.com 检测证书链完整性。

坑 7：真机预览连不上本地后端
结论：真机预览所有请求失败，模拟器正常。
原因：手机访问不到电脑的 localhost；或电脑防火墙拦截了 8080 端口。
解法：baseUrl 改用电脑局域网 IP；防火墙放行端口；手机与电脑同一网络。

坑 8：请求偶发超时，时好时坏
结论：接口偶尔 30 秒超时，重试后成功，无规律。
原因：后端连接池耗尽、慢 SQL 偶发、或运营商对长连接干扰。
解法：Charles 看真实耗时分布；后端加慢查询日志；wx.request 设置合理 timeout 并做失败重试（幂等接口）。
```
