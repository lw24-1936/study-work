## 概述

前后端联调的第一步，是把接口定义清楚。API 设计与规范章节解决三件事：接口怎么命名（RESTful 资源风格）、接口长什么样（统一返回结构、状态码、错误码）、接口怎么描述与维护（OpenAPI 文档、版本管理）。小程序端（wx.request）、SpringBoot 后端、Vue 管理端三方都遵循同一份接口约定，联调才能顺畅推进。

接口规范的价值在协作中体现：前端可以照着文档并行开发，后端可以照着文档自测，测试可以照着文档验收，新成员可以照着文档快速上手。没有规范的接口是联调事故的最大来源——字段命名随意、状态码乱用、数据结构天天变，每一处不一致都要用一次线上事故来偿还。

```text
API 设计的核心约定：
1. 资源命名 —— 接口围绕资源（名词）设计，URL 使用复数名词与小写
2. 方法语义 —— GET 查、POST 增、PUT 改、DELETE 删，语义与副作用严格对应
3. 状态码 —— HTTP 状态码表达传输层结果，业务码表达业务层结果
4. 统一返回 —— 所有接口返回 { code, message, data } 结构，前端统一解析
5. 文档先行 —— 接口文档（OpenAPI）先于编码，作为联调契约
6. 版本管理 —— /api/v1 前缀隔离不兼容变更，旧版本灰度下线
```

## RESTful 设计与 URL 规范

RESTful（Representational State Transfer，表述性状态转移）是一种基于资源的接口设计风格。核心思想：把业务对象抽象为资源（Resource），用 URL 定位资源，用 HTTP 方法表达对资源的操作，服务端不保存客户端状态（无状态）。在小程序电商项目里，用户、商品、订单、购物车、收货地址都是典型的资源。

URL 规范要点：资源用名词复数、统一小写、多词用连字符分隔、层级关系用 / 表达、过滤条件放查询参数。禁止在 URL 中编造动词（如 /getUser、/deleteOrder、/queryProductList），操作语义交给 HTTP 方法表达，这样 URL 才能保持稳定，接口数量也不会随业务动作膨胀。

```text
商品资源 URL 设计示例：
GET    /api/v1/products              — 商品列表（分页、关键词、分类过滤）
GET    /api/v1/products/{id}         — 商品详情
POST   /api/v1/products              — 新增商品（管理端）
PUT    /api/v1/products/{id}         — 全量更新商品
PATCH  /api/v1/products/{id}         — 部分更新（如下架、改价格）
DELETE /api/v1/products/{id}         — 删除商品
GET    /api/v1/products/{id}/skus    — 子资源：某商品下的 SKU 列表
POST   /api/v1/orders                — 创建订单（动作由方法表达，不是 /createOrder）
```

几个容易踩的命名细节：单个资源用路径参数定位，写 /products/100 而不是 /products?id=100；布尔字段与状态字段避免混用（isDeleted 与 status 二选一，不并存）；集合操作一律复数（products），不要一个列表用单数一个用复数；接口路径中不要出现版本无关的业务词（如 /new、/old），版本归属统一由 /api/v1 前缀管理。

```text
URL 设计要点：
1. 资源用名词复数 —— products、orders、users，禁止动词
2. 路径参数定位单资源 —— /api/v1/orders/{orderId}
3. 过滤条件放查询参数 —— ?status=1&page=1&pageSize=10
4. 子资源用层级表达 —— /api/v1/orders/{orderId}/items
5. 多词用连字符 —— order-items，不用下划线或驼峰
6. 统一前缀 —— /api/v1 开头，方便网关路由与版本隔离
7. 查询参数统一命名 —— page/pageSize/keyword/status 全项目一致
```

## HTTP 方法与状态码语义

HTTP 方法表达「对资源做什么」，语义必须与副作用严格对应：GET 只读不产生副作用（幂等且安全），POST 创建资源（不幂等，每次调用都新增），PUT 全量替换（幂等），PATCH 部分更新（幂等），DELETE 删除（幂等）。小程序端 wx.request 默认 method 是 GET，需要 POST 时显式指定。

状态码表达「这次请求的传输结果」，与业务码各司其职：HTTP 状态码由 Spring 容器按异常类型映射，业务码由业务代码显式返回。前端统一处理逻辑是：先看 HTTP 状态码判断网络层是否成功，再解析 body 里的 code 判断业务层是否成功，两层都过了才取 data。

```java
@RestController
@RequestMapping("/api/v1/products")
@Tag(name = "商品管理", description = "商品增删改查接口")
public class ProductController {

    @GetMapping
    @Operation(summary = "商品列表", description = "分页查询商品，支持关键词与分类过滤")
    public ApiResult<PageResult<ProductVO>> list(
            @Parameter(description = "页码，从 1 开始") @RequestParam(defaultValue = "1") int page,
            @Parameter(description = "每页条数") @RequestParam(defaultValue = "10") int pageSize,
            @Parameter(description = "搜索关键词") @RequestParam(required = false) String keyword) {
        return ApiResult.success(productService.pageQuery(page, pageSize, keyword));
    }

    @GetMapping("/{id}")
    @Operation(summary = "商品详情")
    public ApiResult<ProductVO> detail(@PathVariable Long id) {
        return ApiResult.success(productService.getById(id));
    }

    @PostMapping
    @Operation(summary = "新增商品")
    public ApiResult<Long> create(@RequestBody @Valid ProductCreateDTO dto) {
        return ApiResult.success(productService.create(dto));
    }

    @PutMapping("/{id}")
    @Operation(summary = "全量更新商品")
    public ApiResult<Void> update(@PathVariable Long id, @RequestBody @Valid ProductUpdateDTO dto) {
        productService.update(id, dto);
        return ApiResult.success();
    }

    @DeleteMapping("/{id}")
    @Operation(summary = "删除商品")
    public ApiResult<Void> delete(@PathVariable Long id) {
        productService.delete(id);
        return ApiResult.success();
    }
}
```

```text
常用 HTTP 状态码语义：
1. 200 OK —— 查询、更新成功，返回业务数据
2. 201 Created —— 创建成功，返回新资源 id 或 Location 头
3. 204 No Content —— 删除成功，无响应体
4. 400 Bad Request —— 参数缺失、格式错误（@Valid 校验失败）
5. 401 Unauthorized —— 未登录或 Token 过期
6. 403 Forbidden —— 已登录但无权限（如普通用户调管理端接口）
7. 404 Not Found —— 资源不存在或 URL 写错
8. 405 Method Not Allowed —— 方法不支持（GET 调了 POST 路径）
9. 409 Conflict —— 资源冲突（如订单已支付又发起支付）
10. 500 Internal Server Error —— 服务端未捕获异常
```

## 统一返回结构与错误码

所有接口统一返回 { code, message, data } 结构，这是全栈项目最核心的约定之一。前端封装 wx.request 时只需要解析一种结构，拦截器里统一判断 code：为 0 取 data，非 0 弹 toast 提示 message，40100 统一跳登录。结构一旦定稿就不允许某个接口私自改字段，否则所有前端调用点全部要跟着改。

```java
public class ApiResult<T> {
    private int code;       // 业务码：0 表示成功，非 0 表示失败
    private String message; // 提示信息，可直接展示给用户
    private T data;         // 业务数据，成功时承载响应体

    public static <T> ApiResult<T> success() {
        return new ApiResult<>(0, "成功", null);
    }

    public static <T> ApiResult<T> success(T data) {
        return new ApiResult<>(0, "成功", data);
    }

    public static <T> ApiResult<T> error(int code, String message) {
        return new ApiResult<>(code, message, null);
    }

    // 构造方法与 getter/setter 省略
}
```

错误码用枚举集中管理，禁止在 Controller 里散落魔法数字。错误码分三段位：4 开头是客户端问题（参数、鉴权、权限），5 开头是服务端问题（业务失败、系统异常），后三位是具体细分。这样前端可以根据段位决定处理策略：4 开头提示用户修正，5 开头提示稍后重试或上报。

```java
public enum ErrorCode {
    SUCCESS(0, "成功"),
    PARAM_ERROR(40000, "参数错误"),
    UNAUTHORIZED(40100, "未登录或登录已过期"),
    FORBIDDEN(40300, "无权限访问"),
    NOT_FOUND(40400, "资源不存在"),
    CONFLICT(40900, "资源状态冲突"),
    BIZ_ERROR(50000, "业务处理失败"),
    SYSTEM_ERROR(50001, "系统繁忙，请稍后重试");

    private final int code;
    private final String message;

    ErrorCode(int code, String message) {
        this.code = code;
        this.message = message;
    }

    public int getCode() { return code; }
    public String getMessage() { return message; }
}
```

配套一个全局异常处理器，把校验异常、业务异常、系统异常统一转成 ApiResult，保证任何情况下响应结构都不变形：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ApiResult<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + " " + f.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return ApiResult.error(ErrorCode.PARAM_ERROR.getCode(), msg);
    }

    @ExceptionHandler(BizException.class)
    public ApiResult<Void> handleBiz(BizException e) {
        return ApiResult.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public ApiResult<Void> handleOther(Exception e) {
        log.error("系统异常", e);
        return ApiResult.error(ErrorCode.SYSTEM_ERROR.getCode(), ErrorCode.SYSTEM_ERROR.getMessage());
    }
}
```

```text
统一返回结构要点：
1. code —— 业务码，0 成功，非 0 失败，由 ErrorCode 枚举统一定义
2. message —— 面向用户的提示文案，前端可直接 toast
3. data —— 成功时的业务数据，失败时为 null
4. 异常统一收敛 —— @RestControllerAdvice 兜底，响应结构永不变形
5. 错误码分段位 —— 4 开头客户端问题，5 开头服务端问题
6. 日志留痕 —— 系统异常必须打印堆栈，便于排查
```

## 分页与查询参数规范

列表接口必须分页，全项目统一 page/pageSize 参数名（从 1 开始），返回体统一用 PageResult 包装 total、page、pageSize、list 四个字段。小程序端做上拉加载（onReachBottom）时依赖 total 判断是否还有下一页，字段名不一致会导致列表永远加载不出第二页。

```java
public class PageResult<T> {
    private long total;     // 总条数
    private int page;       // 当前页码，从 1 开始
    private int pageSize;   // 每页条数
    private List<T> list;   // 当前页数据

    public static <T> PageResult<T> of(IPage<T> page) {
        PageResult<T> r = new PageResult<>();
        r.setTotal(page.getTotal());
        r.setPage((int) page.getCurrent());
        r.setPageSize((int) page.getSize());
        r.setList(page.getRecords());
        return r;
    }
    // getter/setter 省略
}
```

配合 MyBatis-Plus 的分页插件使用，Service 层只需返回 IPage，Controller 转成 PageResult：

```java
@Service
public class ProductServiceImpl implements ProductService {

    @Override
    public PageResult<ProductVO> pageQuery(int page, int pageSize, String keyword, Long categoryId) {
        LambdaQueryWrapper<Product> wrapper = new LambdaQueryWrapper<>();
        wrapper.like(StringUtils.hasText(keyword), Product::getName, keyword)
               .eq(categoryId != null, Product::getCategoryId, categoryId)
               .eq(Product::getStatus, 1)   // 只展示上架商品
               .orderByDesc(Product::getCreateTime);
        IPage<Product> p = productMapper.selectPage(new Page<>(page, pageSize), wrapper);
        return PageResult.of(p.convert(this::toVO));
    }
}
```

```text
分页规范要点：
1. 参数统一 —— page（从 1 开始）、pageSize，禁止 pageNum/limit 混用
2. 上限约束 —— 后端对 pageSize 做 max 限制（如 100），防止一次拉全表
3. 返回统一 —— total + page + pageSize + list 四件套
4. 排序稳定 —— 必须带 orderBy，否则翻页时数据顺序漂移、出现重复
5. 小程序端 —— 上拉加载用 page+1，滚动回顶用 page=1 重置
6. 下拉刷新 —— 刷新后页码归零，避免旧数据拼接
```

## Swagger 与 OpenAPI 3 接口文档

接口文档是前后端联调的契约，必须与代码同步生成，人工维护的 Word/Excel 文档注定过期。Spring Boot 3 项目用 springdoc-openapi 自动生成 OpenAPI 3 规范：启动项目后，GET /v3/api-docs 返回 JSON 规范，GET /swagger-ui.html 提供可视化页面，Controller 里的 @Tag、@Operation、@Parameter 注解自动映射成文档内容。

```xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.6.0</version>
</dependency>
```

OpenAPI 3 是 Swagger 2.0 的继任规范，接口描述、请求参数、响应结构全部结构化定义，可以被 Postman、Apifox、代码生成器直接消费。通过配置类可以定制文档基本信息（标题、版本、服务器地址），生产环境建议关闭文档端点防止泄露接口细节：

```java
@Configuration
public class OpenApiConfig {

    @Bean
    public OpenAPI mallOpenAPI() {
        return new OpenAPI()
                .info(new Info()
                        .title("商城小程序后端接口文档")
                        .description("微信小程序 + SpringBoot 全栈项目接口定义")
                        .version("v1.0.0")
                        .contact(new Contact().name("后端团队")))
                .addSecurityItem(new SecurityRequirement().addList("BearerAuth"))
                .components(new Components()
                        .addSecuritySchemes("BearerAuth",
                                new SecurityScheme()
                                        .type(SecurityScheme.Type.HTTP)
                                        .scheme("bearer")
                                        .bearerFormat("JWT")));
    }
}
```

```text
接口文档要点：
1. 注解驱动 —— @Tag 分组、@Operation 描述接口、@Parameter 描述参数
2. 自动生成 —— 文档随代码编译实时更新，不维护第二份
3. OpenAPI 3 —— 结构化 JSON，可导入 Postman/Apifox/生成客户端
4. 安全配置 —— JWT 认证信息写进 OpenAPI，方便在线调试
5. 生产关闭 —— profile=prod 时禁用文档端点
6. 在线调试 —— swagger-ui 里直接发请求，后端不用 Postman 也能自测
```

## Knife4j 增强 UI 与接口调试

Knife4j 是 Swagger UI 的国产增强版，把接口文档组织成左侧树形分组、右侧参数表格 + 在线调试面板的形态，比原生 swagger-ui 更适合中文团队。Spring Boot 3 使用 knife4j-openapi3-jakarta 版本，启动后访问 /doc.html 即可使用。

```xml
<dependency>
    <groupId>com.github.xiaoymin</groupId>
    <artifactId>knife4j-openapi3-jakarta-spring-boot-starter</artifactId>
    <version>4.5.0</version>
</dependency>
```

Knife4j 的在线调试比 Postman 更适合后端自测：文档里直接点「调试」，填好参数即可发送请求，返回体按 code/message/data 高亮展示；支持全局参数（如把 Token 配置成全局 header，所有接口自动携带）；还支持接口导出为 OpenAPI 3 JSON 或 Markdown，直接发给前端同学作为联调依据。

```text
Knife4j 使用要点：
1. 访问地址 —— 启动后访问 /doc.html（不是 /swagger-ui.html）
2. 全局参数 —— 配置全局 header 参数，调试登录态接口不用每次手填 Token
3. 在线调试 —— 接口右侧点「调试」，填参数、发请求、看响应
4. 文档导出 —— 导出 OpenAPI JSON 导入 Apifox/Postman
5. 分组管理 —— 按模块分组，与 Controller 的 @Tag 一一对应
6. 鉴权依赖 —— 依赖 springdoc-openapi，两者版本需配套
```

接口调试是联调前的自检环节：后端写完接口先自己在 Knife4j 里把成功、失败、边界三种情况各调一遍，确认结构符合约定，再通知前端开始联调。这能把「接口 500 了才发现是后端没写对」这种低效循环挡在联调之前。

```text
后端自测清单：
1. 正常路径 —— 正确参数能返回 code=0 与预期 data
2. 参数缺失 —— 不传必填参数返回 400 + 明确错误信息
3. 鉴权失败 —— 不带 Token 返回 40100
4. 数据不存在 —— 传不存在的 id 返回 40400，而不是 500
5. 边界值 —— 页码为 0、pageSize 超上限、超长字符串
6. 结构一致性 —— 响应字段与接口文档完全一致
```

## 接口版本管理

接口一旦上线被小程序端调用，就不能随便改字段名、改结构——旧版本小程序还在线上运行，微信审核发布有周期，改坏一个字段就是线上事故。所以不兼容变更必须通过版本隔离：URL 用 /api/v1 前缀区分大版本，v1 保持稳定不动，新逻辑写在 v2。

```text
版本化策略：
1. 路径版本 —— /api/v1/orders、/api/v2/orders，最直观，推荐默认
2. 参数版本 —— ?v=2，隐藏版本信息，但容易漏传，不推荐
3. 头版本 —— header 传 X-Api-Version: 2，URL 干净但调试不直观
4. 兼容策略 —— v1 与 v2 并存，v1 只修 bug 不加功能
5. 下线节奏 —— 统计 v1 调用量降为 0（旧版本小程序覆盖率足够）后再下线
6. 平滑迁移 —— 小步升级小程序并观察，禁止一天之内切换全部流量
```

Controller 层面保持两个版本并存，共享 Service 逻辑，只改 DTO/VO 映射：

```java
@RestController
@RequestMapping("/api/v2/orders")
@Tag(name = "订单管理 v2", description = "订单接口第二版")
public class OrderV2Controller {

    @PostMapping
    @Operation(summary = "创建订单 v2", description = "支持多地址与优惠券抵扣")
    public ApiResult<OrderVO> create(@RequestBody @Valid OrderCreateV2DTO dto) {
        // v2 新增 couponId 字段，v1 没有
        return ApiResult.success(orderService.createV2(dto));
    }
}
```

```text
版本管理要点：
1. 大版本 —— 不兼容变更（删字段、改类型、改语义）必须升版本
2. 小变更 —— 新增可选字段、新增接口属于兼容变更，直接加到 v1
3. 响应只增不删 —— v1 的 data 字段只能加不能删，前端容错
4. 文档标注 —— OpenAPI 中每个接口标注 since 版本与 deprecated 状态
5. 废弃标记 —— 老接口加 @Deprecated 并在文档中标注，给前端缓冲期
6. 下线条件 —— 旧版本小程序覆盖率达到阈值，经评估后下线
```

## 应用场景实战

### 场景一：商品模块接口从零设计到文档化

新商城项目要开发商品模块，后端按规范先设计接口再写代码：

```text
步骤：
1. 资源建模 —— 商品（product）、SKU（sku）、分类（category）三个资源
2. 接口清单 —— 每个资源列增删改查 + 列表，形成接口表格
3. 定义 DTO —— ProductCreateDTO（入参）、ProductVO（出参）字段对齐小程序端
4. 写 Controller —— 按 /api/v1/products 前缀 + @Tag/@Operation 注解
5. 统一返回 —— 全部返回 ApiResult，列表分页用 PageResult
6. 本地自测 —— 启动项目，Knife4j 里逐接口调试通过
7. 导出文档 —— OpenAPI JSON 导出给小程序端，开始联调
```

接口表格示例（联调前的契约）：

```text
商品模块接口契约：
1. GET    /api/v1/products?page=1&pageSize=10&keyword=手机&categoryId=3
   返回：ApiResult<PageResult<ProductVO>>
2. GET    /api/v1/products/{id}         返回：ApiResult<ProductVO>
3. POST   /api/v1/products              入参：ProductCreateDTO，返回：ApiResult<Long>
4. PUT    /api/v1/products/{id}         入参：ProductUpdateDTO，返回：ApiResult<Void>
5. PATCH  /api/v1/products/{id}/status  入参：{ status: 0|1 }，返回：ApiResult<Void>
6. DELETE /api/v1/products/{id}         返回：ApiResult<Void>
```

### 场景二：订单接口 v1 升级 v2 的兼容迁移

订单接口 v1 上线三个月后要支持「优惠券抵扣」能力，改动涉及创建订单入参增加 couponId 字段，且返回的 OrderVO 新增 discountAmount 字段。按兼容策略处理：

```text
步骤：
1. 评估 —— 新增字段属于兼容变更，v1 接口直接扩展，不升版本
2. 修改 v1 —— OrderCreateDTO 增加可选字段 couponId（不设 required）
3. 同步文档 —— Knife4j 自动更新，@Operation 描述中说明 v1.2 新增
4. 联调 —— 小程序端升级请求参数，后端在 Knife4j 验证新旧两种入参
5. 若遇不兼容变更 —— 新建 /api/v2/orders，v1 冻结只修 bug
6. 灰度下线 —— 统计 v1 调用量趋零后，评估下线并删除
```

```text
兼容性检查清单：
1. 新增可选参数不影响旧调用 —— 老请求体不传新字段也能成功
2. 新增返回字段不影响旧解析 —— 小程序端忽略未知字段即可
3. 类型与单位不变 —— id 一直是 Long，金额一直是分，禁止中途改单位
4. 语义不变 —— status 的取值含义 v1、v2 保持一致
5. 错误码不变 —— 同一失败场景返回同一错误码，前端拦截器不重写
```

## 最佳实践与踩坑记录

### 最佳实践

1. 接口先行：写代码前先产出接口清单（方法、路径、入参、出参、错误码），评审通过再动手，文档就是契约
2. 统一返回结构：全项目只有一种响应结构 ApiResult，禁止个别接口直接返回裸对象
3. 错误码枚举化：错误码集中定义在 ErrorCode，业务异常抛出 BizException(code, message)
4. 注解补齐：@Tag、@Operation、@Parameter 写完整，文档质量就是接口质量
5. 参数校验前置：@Valid + DTO 注解（@NotNull/@Size/@Pattern）在入口拦截脏数据
6. 分页上限约束：pageSize 服务端强制 max，防止恶意全量拉取拖垮数据库
7. 字段命名对齐：后端驼峰、前端小程序保持一致，时间统一返回时间戳或统一格式字符串
8. 版本只增不删：v1 字段只加不改不删，破坏性变更走新版本，灰度下线

### 踩坑记录

```text
坑 1：接口返回裸对象，前端解析结构分裂
结论：某个接口直接返回 List 而不是 ApiResult，前端 wx.request 封装无法统一拦截错误。
原因：后端图省事没走统一返回，破坏全项目约定。
解法：所有接口统一 ApiResult 包装；code review 阶段用文档对比检查每个接口签名。

坑 2：HTTP 状态码与业务码混用
结论：业务失败返回 HTTP 200 + code=500，前端拦截器只判断 statusCode，把失败当成功处理。
原因：错误码语义没有分层，业务码和状态码职责不清。
解法：状态码管传输层、业务码管业务层，前端两层都校验；后端异常处理器统一映射。

坑 3：PUT 和 PATCH 混用
结论：部分更新接口用了 PUT 全量替换，前端只传一个字段把其他字段清空成 null。
原因：对 HTTP 方法语义理解不一致，半更新接口误用 PUT。
解法：约定全量更新用 PUT、部分更新用 PATCH；文档中明确标注每个接口的更新语义。

坑 4：分页参数不统一（pageNum/limit 混用）
结论：小程序端传 page/pageSize，后端接收 pageNum/limit，列表接口永远分页错乱。
原因：接口契约没对齐，各写各的。
解法：全项目统一 page/pageSize；后端用 @RequestParam(defaultValue) 兜底，联调前先对接口清单。

坑 5：接口文档与实际代码不一致
结论：手写接口文档说返回 createTime，实际代码返回 timestamp，前端按文档解析得到 undefined。
原因：文档人工维护，代码改了文档没改。
解法：用 springdoc-openapi 注解自动生成文档，删掉人工文档；改动接口必须同步注解。

坑 6：金额用 Double 传输导致精度丢失
结论：订单金额 19.99 元经 Double 序列化后变成 19.990000000000002，对账不平。
原因：Double 是二进制浮点，无法精确表示十进制小数。
解法：金额统一用分（Long 整数）传输与存储，前端展示时除以 100；禁止接口出现 Double 金额。

坑 7：接口上线后删字段，线上小程序崩溃
结论：后端删除 v1 响应中的某字段，老版本小程序取不到数据白屏。
原因：没有版本意识，直接改坏了线上契约。
解法：字段只增不删；破坏性变更走 /api/v2；下线前统计旧版本调用量。

坑 8：pageSize 不设上限被恶意全量拉取
结论：调用方传 pageSize=1000000，一次查询拖垮数据库连接池。
原因：后端没有做参数上限校验。
解法：全局拦截或 DTO 校验 @Max(100)；分页查询强制 orderBy 避免大偏移性能问题。
```
