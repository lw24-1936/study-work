## 概述

小程序登录不是传统意义的「用户名密码登录」，而是「微信身份凭证换发」流程：小程序端调用 wx.login 拿到临时登录凭证 code，交给自己的后端，后端拿 code 向微信服务器换取用户的 openid（用户唯一标识）与 session_key，再基于 openid 建立自己的账号体系并签发 token。整个过程对用户完全静默，不需要任何授权弹窗，这是小程序登录与 H5/App 登录最大的区别。

本篇章围绕登录链路拆解六个核心问题：code 怎么拿、code 怎么换身份、openid 与 unionid 有什么区别、完整登录时序是什么样、静默登录与主动登录如何配合、登录失败如何兜底。理解这条链路，后续的会话保持（09.2）、用户信息获取（09.3）、用户中心与多端打通（09.4）才能串起来。后端侧的接口工程实现细节可参考 19.2-登录对接 篇章。

```text
登录流程核心要点：
1. wx.login 获取 code —— 临时登录凭证，5 分钟有效，只能使用一次
2. code2session 换身份 —— 后端用 code 换 openid 与 session_key
3. openid 是用户唯一标识 —— 同一小程序内稳定不变，不同小程序不同
4. unionid 是多端统一标识 —— 绑定微信开放平台后小程序/公众号/App 一致
5. 登录时序 —— wx.login -> 后端 code2session -> 签发 token -> 前端存储 -> 请求携带
6. 静默与主动 —— wx.login 全静默，头像昵称手机号等由用户主动填写
```

## wx.login 获取临时登录凭证

wx.login 是小程序登录的起点，调用后微信客户端会返回一个一次性临时凭证 code。这个 code 本身不包含任何用户信息，它的作用只有一个：作为「我是从这个小程序发起的合法登录请求」的凭证，交给后端去微信服务器兑换真实身份。code 有两条硬性约束：5 分钟内有效，且只能成功使用一次，使用后立即失效。

wx.login 不需要用户授权、不会弹任何窗口，也不依赖用户是否已登录微信（用户处于微信内即可调用）。它可以在小程序运行期间任意时刻调用，但通常放在启动流程（App.onLaunch 或首个页面 onLoad）中执行。需要注意的是，wx.login 返回的 code 与当前是否已登录无关：即使之前已经登录过，再次调用也会返回全新 code，所以「要不要调 wx.login」只取决于后端是否需要重新换取 openid 或刷新身份。

```js
// utils/login.js —— wx.login 封装成 Promise，便于登录流程复用
function wxLogin() {
  return new Promise((resolve, reject) => {
    wx.login({
      success(res) {
        if (res.code) {
          resolve(res.code)
        } else {
          reject(new Error('wx.login 未返回 code：' + res.errMsg))
        }
      },
      fail(err) {
        reject(new Error('wx.login 调用失败：' + err.errMsg))
      }
    })
  })
}

module.exports = { wxLogin }
```

```text
wx.login 使用要点：
1. 返回值只有 code —— 不含用户身份信息，openid 必须由后端去换
2. 5 分钟有效 —— 拿到 code 后尽快传给后端，不要缓存复用
3. 一次性 —— 无论兑换成功与否，用过一次后 code 即失效
4. 无授权弹窗 —— 属于静默能力，启动时可直接调用
5. 可重复调用 —— 每次调用返回全新 code，失败重试直接重新调
6. 失败场景 —— 网络异常或微信服务异常走 fail 回调，需要重试兜底
```

## code2session 换取 openid 与 session_key

code 换 openid 的动作只能发生在后端。小程序端拿到的 code 要传给自己的服务器，由服务器调用微信官方接口 code2session（jscode2session）完成兑换，接口地址为：

```text
GET https://api.weixin.qq.com/sns/jscode2session?appid=APPID&secret=SECRET&js_code=JSCODE&grant_type=authorization_code
```

接口必须携带四个参数：appid（小程序 AppID）、secret（小程序 AppSecret）、js_code（wx.login 拿到的 code）、grant_type（固定 authorization_code）。其中 AppSecret 是服务端专用密钥，只允许存放在后端配置（环境变量/配置中心）中，任何情况下都不能出现在小程序代码里。code2session 是 GET 请求，调用方需要能访问公网（国内服务器直连 api.weixin.qq.com 即可，无需代理）。

调用成功返回 openid、session_key，以及可能存在的 unionid（返回条件见下一节）。session_key 是微信会话密钥，用于解密微信返回的加密数据（如历史版本的手机号解密、开放数据解密），应当保存在后端与用户关联，严禁下发到小程序端。返回的 errcode 为 0 表示成功，非 0 表示失败，常见错误码：40029（js_code 无效）、40163（code 已被使用）、45011（调用频率超限，需稍后重试）、-1（系统繁忙）。

```java
// 后端 SpringBoot 示例：WechatApiClient.java —— 封装 code2session 调用
@Component
public class WechatApiClient {

    @Value("${wechat.appid}")
    private String appid;

    @Value("${wechat.secret}")
    private String secret;

    @Autowired
    private RestTemplate restTemplate;

    public Code2SessionResp code2Session(String code) {
        String url = "https://api.weixin.qq.com/sns/jscode2session"
                + "?appid=" + appid
                + "&secret=" + secret
                + "&js_code=" + code
                + "&grant_type=authorization_code";
        Code2SessionResp resp = restTemplate.getForObject(url, Code2SessionResp.class);
        if (resp == null) {
            throw new BizException("微信接口无响应");
        }
        if (resp.getErrcode() != null && resp.getErrcode() != 0) {
            throw new BizException("微信登录失败：" + resp.getErrmsg() + "（errcode=" + resp.getErrcode() + "）");
        }
        return resp;
    }
}
```

```json
{
  "openid": "oXk8T5x3jM2vQ9sYhLk4eWq1RzBcN",
  "session_key": "t0Q5mX8vY2nB4wK7eR9pL3sF6hJ1dG5a=",
  "unionid": "o6_bmjrPTlm6_2sgVt7hMZOPfL2M",

```

```text
code2session 使用要点：
1. 只能后端调用 —— AppSecret 必须留在服务端，接口地址不进小程序代码
2. 参数固定 —— appid + secret + js_code + grant_type=authorization_code
3. session_key 不下发 —— 保存后端并与用户关联，用于解密微信加密数据
4. unionid 不一定返回 —— 满足开放平台绑定条件时才返回
5. 错误码要处理 —— 40029/40163/45011 分别对应 code 无效、已使用、频率超限
6. 建议限流与缓存 —— 该接口有频率限制，登录接口要加频控防刷
```

## openid 与 unionid

openid 是微信用户在某个应用下的唯一标识。同一个微信用户，在不同的小程序里 openid 是不同的；但在同一个小程序里，openid 永远不变，即使卸载重装、更换手机也保持不变。openid 由小程序 AppID 与用户微信账号共同决定，因此它的完整语义是「某小程序下的某微信用户」，它本身不跨应用通用。

unionid 是微信开放平台体系下的统一用户标识。当小程序、公众号、App 绑定到同一个微信开放平台账号（且均为同一主体）后，同一微信用户在这些应用中拿到的 unionid 就是同一个。unionid 解决了多端账号打通问题：用户在小程序、公众号 H5、App 三个入口登录，后端拿到三个不同的 openid，但 unionid 相同，据此可以判断这是同一个人，合并到同一条用户记录。

需要注意，code2session 返回 unionid 是有条件的：小程序必须已完成微信认证（企业主体），且已绑定到微信开放平台账号；同时该用户需要在开放平台体系内有过交互记录（例如关注过同主体的公众号、或在绑定的 App 内登录过）。不满足条件时，接口只返回 openid 和 session_key，不返回 unionid，这不代表登录失败。

```text
openid 与 unionid 对比：
1. openid —— 应用级标识，同一小程序内唯一，跨小程序不通用
2. unionid —— 开放平台级标识，绑定后跨小程序/公众号/App 统一
3. 获取条件 —— openid 登录即得；unionid 需认证 + 开放平台绑定 + 用户有交互记录
4. 业务用途 —— openid 做主登录凭证；unionid 做多端用户合并
5. 设计原则 —— 用户表以自增 id 为主键，openid/unionid 建唯一索引
6. 常见误区 —— 拿 openid 当用户主键，换绑、多端合并时数据难以维护
```

## 登录时序完整链路

把前面几个环节串起来，就是一次完整的小程序登录。整条链路的核心原则：小程序端只负责「拿 code、存 token」，所有涉及密钥与身份判断的逻辑都在后端完成。时序如下：

```text
小程序端                      后端(SpringBoot)                 微信服务器
  |                              |                               |
  |-- wx.login() --------------->|                               |
  |<-- code ---------------------|                               |
  |                              |                               |
  |-- POST /api/auth/login ------|--> code2session(js_code) ---->|
  |     body: {code}             |<-- openid + session_key ------|
  |                              |                               |
  |                              |-- 按 openid 查用户/建用户 -----|
  |                              |-- 签发 token（JWT/随机串） ----|
  |<-- {token, user} ------------|                               |
  |                              |                               |
  |-- wx.setStorageSync 存 token -|                               |
  |                              |                               |
  |-- 后续请求 Header:            |                               |
  |     Authorization: Bearer xx -|--> 校验 token，识别用户 ------|
```

对应的后端登录接口实现：

```java
// AuthController.java —— 登录接口
@RestController
@RequestMapping("/api/auth")
public class AuthController {

    @Autowired
    private WechatApiClient wechatApiClient;

    @Autowired
    private UserService userService;

    @Autowired
    private TokenService tokenService;

    @PostMapping("/login")
    public Result<LoginVO> login(@RequestBody @Valid LoginDTO dto) {
        // 1. 用前端传来的 code 换 openid（内部含错误码校验）
        Code2SessionResp wxResp = wechatApiClient.code2Session(dto.getCode());
        // 2. 按 openid 查用户，不存在则注册（游客转正）
        User user = userService.findOrCreateByOpenid(wxResp.getOpenid(), wxResp.getUnionid());
        // 3. 签发登录令牌（JWT，有效期 7 天，内含 userId）
        String token = tokenService.createToken(user.getId());
        // 4. 返回 token 与脱敏后的用户信息
        return Result.ok(new LoginVO(token, UserVO.from(user)));
    }
}
```

```java
// LoginDTO.java / LoginVO.java —— 请求与响应模型
@Data
public class LoginDTO {
    @NotBlank(message = "code 不能为空")
    private String code;            // wx.login 获取的临时凭证
}

@Data
public class LoginVO {
    private String token;           // 登录令牌
    private UserVO user;            // 用户信息（脱敏）

    public LoginVO(String token, UserVO user) {
        this.token = token;
        this.user = user;
    }
}
```

前端登录方法封装：

```js
// utils/auth.js —— 登录 + 存储 token
const { wxLogin } = require('./login')

function login() {
  return wxLogin()
    .then((code) => {
      return new Promise((resolve, reject) => {
        wx.request({
          url: 'https://api.example.com/api/auth/login',
          method: 'POST',
          data: { code },
          success: (res) => {
            if (res.data.code === 0) {
              const { token } = res.data.data
              wx.setStorageSync('token', token)
              resolve(res.data.data)
            } else {
              reject(new Error(res.data.msg))
            }
          },
          fail: reject
        })
      })
    })
}

module.exports = { login }
```

```text
登录时序要点：
1. 第一步永远是 wx.login 拿 code，不是直接请求业务接口
2. code 只经过「小程序 -> 自己的后端」，不直达微信服务器
3. 后端负责 code2session、查建用户、签发 token 三个动作
4. token 由前端持久化存储，后续所有请求通过 Header 携带
5. 登录接口要幂等 —— 同一用户重复登录返回同一账号
6. 全程静默完成，用户无感知，界面可加 loading 防止重复点击
```

## 静默登录与主动登录

小程序登录体系天然分成两层：静默登录与主动登录。静默登录指 wx.login 这条链路，它不需要用户任何操作和授权，启动即完成，后端据此建立「游客/匿名」身份；主动登录指需要用户主动配合才能拿到的信息，包括头像、昵称、手机号、收货地址等，必须通过 button 组件（open-type）或输入框触发。

授权弹窗的时机是有讲究的：不要在启动时一上来就弹授权框，也不要为了「攒数据」在用户第一次进入就要求全套信息。正确做法是「用到再要」——用户提交订单时弹手机号验证、在个人中心引导完善头像昵称、使用定位功能时申请位置权限。微信 2021 年后对用户信息获取做了大调整：不再有「一次性授权拿全部用户信息」的弹窗，头像昵称改为用户主动选择填写，手机号改为快速验证组件，详见 09.3-用户信息获取。

静默登录与主动登录在工程上的配合方式：启动时静默登录建立账号 -> 界面正常浏览使用 -> 在关键业务节点（下单、评论、分享得奖励）按需引导用户完善信息 -> 完善后的信息通过资料更新接口回写用户中心。

```js
// app.js —— 启动即静默登录，全局只执行一次
const { login } = require('./utils/auth')

App({
  onLaunch() {
    // 本地已有 token 则跳过；否则静默登录建立账号
    if (!wx.getStorageSync('token')) {
      login().catch((err) => {
        console.error('静默登录失败：', err.message)
        // 不阻塞启动，业务接口 401 时会触发重新登录
      })
    }
  }
})
```

```js
// pages/profile/profile.js —— 个人中心：静默身份已建立，资料完善走主动填写
Page({
  data: {
    userInfo: null,
    hasLogin: false
  },
  onShow() {
    const userInfo = wx.getStorageSync('userInfo')
    this.setData({ userInfo, hasLogin: !!userInfo })
  },
  // 用户主动点击「完善资料」，跳转资料填写页
  goEditProfile() {
    if (!this.data.userInfo) {
      wx.navigateTo({ url: '/pages/profile/edit' })
    }
  }
})
```

```text
静默登录与主动登录要点：
1. 静默登录 —— wx.login 链路，无弹窗，建立基础账号身份
2. 主动登录 —— 头像/昵称/手机号等，用户主动填写或点按钮
3. 授权时机 —— 用到了才要，禁止启动即弹授权框
4. 渐进式完善 —— 先游客可用，关键节点再引导补全信息
5. 拒绝可降级 —— 用户拒绝填头像昵称也要能正常使用核心功能
6. 数据回写 —— 主动获取的信息统一走资料更新接口入库
```

## 登录失败处理

登录失败不能只弹一个 toast 了事，要按失败类型分层处理。第一类是 wx.login 本身失败：多发生在弱网、微信服务异常时，处理方式是重试（最多 2-3 次，带退避间隔），重试仍失败则提示「网络异常，请稍后重试」，并提供手动重试入口。第二类是 code2session 失败：code 无效（40029）或已使用（40163）说明 code 生命周期出了问题，处理方式是让前端重新调用 wx.login 拿新 code 再走一遍；频率超限（45011）则提示稍后再试，避免死循环。第三类是后端业务失败：查建用户或签发 token 异常，属于服务端问题，前端提示后记录日志即可。

工程上建议把登录封装成「可重试的单例流程」：App 启动时若多个页面同时触发登录，只允许一个登录请求在途，其余等待同一个 Promise 完成，避免重复调 wx.login、重复请求登录接口造成 code 浪费与接口压力。登录成功后统一广播「已登录」事件，正在等待的页面拿到结果后继续各自的初始化逻辑。

```js
// utils/auth.js —— 登录单例 + 自动重试（最多 3 次，间隔 500ms）
let loginPromise = null

function doLogin(retryCount) {
  return wxLogin()
    .then((code) => requestLogin(code))
    .catch((err) => {
      if (retryCount < 3) {
        return new Promise((resolve) => setTimeout(resolve, 500))
          .then(() => doLogin(retryCount + 1))
      }
      throw err
    })
}

function login() {
  if (!loginPromise) {
    loginPromise = doLogin(0).finally(() => {
      loginPromise = null
    })
  }
  return loginPromise
}
```

```text
登录失败处理要点：
1. 分层处理 —— wx.login 失败、code2session 失败、后端失败分别对待
2. 有限重试 —— 最多 2-3 次，带退避间隔，禁止无限循环
3. code 失效就重拿 —— 40029/40163 时重新 wx.login 换新 code
4. 登录单例 —— 并发触发只发一个请求，其余复用同一 Promise
5. 失败可恢复 —— 提示用户手动重试，不阻塞页面基本使用
6. 埋点记录 —— 登录失败率与错误码分布是登录质量的关键指标
```

## 应用场景实战

### 场景一：启动静默登录 + 首页拉取用户态数据

需求：小程序启动后静默登录，登录完成后立即用 token 请求「我的订单数量」等用户态接口；登录完成前页面显示加载态，失败则显示重试按钮。

```js
// pages/index/index.js
const { login } = require('../../utils/auth')
const { request } = require('../../utils/request')

Page({
  data: {
    loading: true,
    orderCount: 0,
    errorMsg: ''
  },

  onLoad() {
    this.init()
  },

  async init() {
    this.setData({ loading: true, errorMsg: '' })
    try {
      // 1. 确保登录态（内部有单例与重试）
      await login()
      // 2. 带 token 请求用户态接口
      const res = await request({ url: '/api/user/order-count' })
      this.setData({ orderCount: res.data.count, loading: false })
    } catch (err) {
      this.setData({ loading: false, errorMsg: '登录失败，请检查网络后重试' })
    }
  },

  onRetry() {
    this.init()
  }
})
```

```wxml
<!-- pages/index/index.wxml -->
<view wx:if="{{loading}}" class="loading">正在登录...</view>
```

### 场景二：下单前补登录的「先登录后购买」流程

需求：用户在商品详情页点击「立即购买」，此时本地无 token 或 token 已过期。流程要求先完成静默登录，再进入下单确认页，全程不打断用户操作节奏。

```js
// pages/goods/detail.js —— 下单前确保登录态
const { login } = require('../../utils/auth')

Page({
  onBuyNow() {
    wx.showLoading({ title: '正在登录...' })
    login()
      .then(() => {
        wx.hideLoading()
        wx.navigateTo({
          url: '/pages/order/confirm?goodsId=' + this.data.goods.id
        })
      })
      .catch(() => {
        wx.hideLoading()
        wx.showToast({ title: '登录失败，请重试', icon: 'none' })
      })
  }
})
```

```text
两个场景的共性设计：
1. 登录是前置条件而非页面 —— 用 await login() 保证登录完成后才发业务请求
2. 加载态与错误态齐全 —— 登录中 loading，失败可重试，不白屏
3. 登录单例复用 —— 多次触发不会重复调 wx.login、不会浪费 code
4. 失败可降级 —— 登录失败不阻断页面浏览，仅阻断需要登录的操作
```

## 最佳实践与踩坑记录

### 最佳实践

1. 登录封装成 Promise 单例（login() 全局复用），启动时只触发一次，页面各自 await，避免重复调 wx.login 浪费 code
2. AppSecret 与 code2session 调用只放后端，前端只接触 code 与 token，密钥不进代码仓库
3. 登录接口设计成幂等：同一 openid 重复登录返回同一 userId，不重复建用户
4. 用户表以自增 id 为主键，openid 建唯一索引，方便后续多端合并与账号解绑
5. 登录失败走「有限重试 + 手动重试入口」，不阻塞页面使用，弱网体验优先
6. 设计登录接口时一并规划会话有效期与续期机制（见 09.2），避免上线后返工
7. 用场景值（scene）与登录来源字段记录登录入口，为渠道分析留数据
8. 登录接口独立限流策略（按 IP/设备维度），防刷防抖，保护 code2session 配额

### 踩坑记录

```text
坑 1：缓存 code 复用导致 code2session 报 40163
结论：第一次兑换失败后再用同一个 code 兑换，返回「code been used」。
原因：code 一次性，第一次请求（哪怕失败于网络超时）已消耗该 code。
解法：不缓存 code；每次登录流程重新 wx.login 拿新 code；后端对 40163 明确返回让前端重取。

坑 2：把 code2session 请求写在小程序前端
结论：前端直连 api.weixin.qq.com 换取 openid，AppSecret 明文暴露在包里。
原因：开发者图省事，把微信接口地址与密钥直接写进小程序代码。
解法：AppSecret 只存服务端；code 传给自己的后端，由后端调 code2session。

坑 3：App.onLaunch 里 wx.login 未完成，首页就发业务请求导致 401
结论：首屏接口偶发 401，复现困难，弱网必现。
原因：登录是异步的，页面 onLoad 与登录回调存在竞态。
解法：登录封装成全局单例 Promise，请求模块先 await login() 再发业务请求。

坑 4：不做失败重试，弱网下登录失败直接白屏/卡加载
结论：电梯、地铁等弱网场景用户大量流失。
原因：wx.login 或登录接口一次失败就放弃，没有重试与降级。
解法：有限重试（3 次内、间隔退避）+ 失败提示 + 手动重试按钮。

坑 5：把 openid 当作业务主键使用
结论：用户注销、账号迁移、多端合并时数据关系全部错乱。
原因：openid 只是登录凭证维度，不适合做业务实体主键。
解法：自增 id 或雪花 id 做用户主键，openid/unionid 建唯一索引作为登录维度。

坑 6：unionid 没返回就当成登录失败
结论：部分用户 code2session 不返回 unionid，登录接口直接抛错。
原因：unionid 需要认证 + 开放平台绑定 + 用户交互记录，不是必然返回。
解法：unionid 为可选字段，openid 才是登录必需；unionid 缺失不阻断登录。

坑 7：登录接口被刷，微信 code2session 触发 45011 频率限制
结论：高峰期登录大面积失败，全端不可用。
原因：客户端异常循环重试或恶意刷接口，把 code2session 频率额度打满。
解法：登录接口加频控（同 IP/同设备限流）+ 客户端登录单例防重复请求。

坑 8：session_key 下发到前端用于解密
结论：前端拿到 session_key 可自行解密微信加密数据，存在数据被伪造风险。
原因：沿用了旧文档的做法，把 session_key 返回给客户端。
解法：session_key 只存后端（与用户关联），所有解密逻辑放服务端。
```
