## 概述

前三个篇章解决了「登录怎么来、会话怎么保、资料怎么拿」，本篇章解决「用户数据怎么存、怎么用」。用户中心是后台系统的数据基石：用户表设计决定账号体系的扩展性（自增 id 主键 + openid/unionid 索引 + 状态字段），unionid 打通决定多端用户能否合并，账号体系决定游客、微信、手机号三种身份如何共存，用户画像与会员体系则把用户数据变成运营资产。

本篇章覆盖五块内容：用户表字段与索引设计（含建表 SQL）、unionid 多端打通（微信开放平台绑定机制）、账号体系（游客模式/微信登录/手机号绑定）、用户画像（标签与行为数据）、会员体系（等级与积分）。后端数据库访问的工程细节见 17.4-数据库访问，权限模型见 18.4-权限模型与 RBAC。

```text
用户中心核心要点：
1. 用户表 —— 自增 id 主键，openid 唯一索引，unionid/phone 普通索引
2. 多端打通 —— unionid 依赖微信开放平台绑定，绑定后跨端统一
3. 账号体系 —— 游客/微信/手机号三种身份，按需绑定与合并
4. 用户画像 —— 标签 + 行为数据 + 来源渠道，支撑个性化运营
5. 会员体系 —— 等级 + 积分 + 成长值，激励留存与消费
6. 状态可控 —— status 字段支撑封禁/注销，不物理删数据
```

## 用户表设计

用户表是用户中心的核心表，设计原则：主键用自增 id（不用 openid 当主键，openid 只是登录维度，可能随账号体系演进变化）；openid 建唯一索引（同一小程序内一个用户一个 openid）；unionid、phone 建普通索引（多端合并、手机号检索用）；status 字段支撑封禁/注销（不物理删除，保留业务数据可追溯）；create_time/update_time 记录生命周期。

扩展设计：当业务需要多端认证（公众号、App、多个小程序）时，建议拆出独立的用户认证表（t_user_auth），一条用户记录对应多条认证记录（auth_type + openid/unionid + 绑定时间），用户表本身保持干净。手机号字段若为敏感数据可加密存储，查询走手机号哈希索引列。

```sql
-- 用户主表
CREATE TABLE `t_user` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '用户ID（主键）',
  `openid` VARCHAR(64) NOT NULL COMMENT '小程序 openid（登录凭证）',
  `unionid` VARCHAR(64) DEFAULT NULL COMMENT '开放平台 unionid（多端打通）',
  `nickname` VARCHAR(64) NOT NULL DEFAULT '' COMMENT '昵称',
  `avatar` VARCHAR(255) NOT NULL DEFAULT '' COMMENT '头像 URL',
  `phone` VARCHAR(20) DEFAULT NULL COMMENT '手机号（加密存储）',
  `gender` TINYINT NOT NULL DEFAULT 0 COMMENT '性别 0未知 1男 2女',
  `status` TINYINT NOT NULL DEFAULT 1 COMMENT '状态 1正常 0禁用 2注销',
  `level` INT NOT NULL DEFAULT 1 COMMENT '会员等级',
  `points` INT NOT NULL DEFAULT 0 COMMENT '积分余额',
  `session_version` INT NOT NULL DEFAULT 0 COMMENT '会话版本号（封禁/改密时递增）',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '注册时间',
  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_openid` (`openid`),
  KEY `idx_unionid` (`unionid`),
  KEY `idx_phone` (`phone`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

-- 用户认证表（多端认证扩展）
CREATE TABLE `t_user_auth` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `user_id` BIGINT UNSIGNED NOT NULL COMMENT '用户ID',
  `auth_type` VARCHAR(16) NOT NULL COMMENT '认证类型 wechat_mini/wechat_mp/wechat_app/phone',
  `openid` VARCHAR(64) NOT NULL COMMENT '该端 openid',
  `unionid` VARCHAR(64) DEFAULT NULL COMMENT 'unionid',
  `bind_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '绑定时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_type_openid` (`auth_type`, `openid`),
  KEY `idx_user_id` (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户认证表';
```

登录时的「查用户或建用户」逻辑（upsert 语义）：

```java
// UserService.java —— 按 openid 查建用户
@Transactional
public User findOrCreateByOpenid(String openid, String unionid) {
    User user = userMapper.selectByOpenid(openid);
    if (user == null) {
        user = new User();
        user.setOpenid(openid);
        user.setUnionid(unionid);
        user.setNickname("");
        user.setStatus(1);
        userMapper.insert(user);
    } else if (unionid != null && !unionid.equals(user.getUnionid())) {
        // 历史数据补全 unionid
        user.setUnionid(unionid);
        userMapper.updateById(user);
    }
    return user;
}
```

```text
用户表设计要点：
1. 自增 id 主键 —— openid 只是登录维度，业务实体用 id 关联
2. openid 唯一索引 —— 防止同一用户重复注册多条记录
3. unionid/phone 普通索引 —— 多端合并与手机号检索
4. status 字段 —— 封禁/注销用状态位，不物理删数据
5. 认证表扩展 —— 多端场景拆 t_user_auth，用户表保持干净
6. 敏感字段加密 —— 手机号加密存储，查询走哈希索引
```

## unionid 多端打通

unionid 是微信开放平台体系下的统一用户标识。打通的前提：在微信开放平台（open.weixin.qq.com）注册开放平台账号（企业主体，需认证，费用 300 元/年），把小程序、公众号、App 绑定到同一开放平台账号下（App 需已通过各应用商店审核上架，公众号需已认证）。绑定完成后，同一微信用户在这些应用里登录时返回的 unionid 就是同一个。

用户在小程序登录时，code2session 返回 unionid 的条件：小程序已认证并绑定开放平台，且该用户在开放平台体系内有交互记录（如关注过同主体公众号、登录过绑定的 App）。不满足时只返回 openid。打通后的小程序、公众号 H5、App 三个入口，后端会拿到三个不同的 openid，但 unionid 相同——据此合并到同一用户记录。

打通落地的工程要点：登录时 unionid 存在用户表；多端用户合并以 unionid 为准（同一 unionid 合并为一条用户记录，子账号数据归并）；存量数据需要跑迁移脚本按 unionid 去重合并；用户中心展示「多端登录」能力（如 App 登录后小程序免登，可基于 unionid 做会话互认）。

```text
unionid 多端打通链路：
1. 开放平台注册 —— 企业主体 + 认证（open.weixin.qq.com）
2. 应用绑定 —— 小程序/公众号/App 绑定到同一开放平台账号
3. 登录返回 —— 用户登录时 code2session/网页授权/SDK 返回同一 unionid
4. 用户合并 —— 后端按 unionid 合并多条 openid 记录
5. 会话互认 —— 同一 unionid 可做跨端免登（App 登录小程序免登）
6. 数据迁移 —— 存量用户跑脚本按 unionid 归并，避免重复账号
```

```java
// UserService.java —— 多端登录统一入口：openid 查不到就按 unionid 查
@Transactional
public User loginByAuth(String authType, String openid, String unionid) {
    User user = userMapper.selectByAuth(authType, openid);
    if (user == null && unionid != null) {
        user = userMapper.selectByUnionid(unionid);   // 多端合并：复用已有用户
    }
    if (user == null) {
        user = new User();
        user.setUnionid(unionid);
        user.setStatus(1);
        userMapper.insert(user);
    }
    // 记录/更新该端的认证绑定
    userAuthMapper.upsert(authType, openid, unionid, user.getId());
    return user;
}
```

```text
unionid 打通要点：
1. 前提 —— 开放平台账号（企业主体 + 认证）+ 应用绑定
2. 返回条件 —— 用户需在开放平台体系内有交互记录
3. 合并时机 —— 登录时按 unionid 查已有用户，复用而非新建
4. 认证表记录 —— 每端 openid 与 unionid 的绑定关系落 t_user_auth
5. 迁移脚本 —— 存量多账号数据按 unionid 归并
6. 注意 —— 个人主体小程序拿不到 unionid，打通需企业主体
```

## 账号体系设计

账号体系回答「一个用户有几种身份入口、如何共存」。小程序全栈项目典型的三种身份：游客模式（未完善资料，但有 openid 建立的匿名身份）、微信登录（默认主身份，openid 登录）、手机号登录绑定（手机号 + 验证码可作为 Web 端/公众号端入口，或作为找回凭证）。三种身份通过「绑定」动作归一到同一用户记录。

设计要点：游客数据不丢——游客产生的购物车、收藏、浏览记录在登录后按 openid 合并到正式账号；手机号绑定做唯一校验——一个手机号只能绑定一个账号，重复绑定要提示换绑或合并；解绑与换绑——手机号解绑需二次验证，微信身份与手机号解绑后账号仍有另一身份可用则保留账号。多端登录态互认（App 登录过、小程序免登）可基于 unionid 实现会话共享。

```sql
-- 手机号绑定示例：唯一约束保证一个手机号只绑一个账号
ALTER TABLE `t_user` ADD UNIQUE KEY `uk_phone` (`phone`);
```

```js
// 前端：手机号绑定 + 游客数据合并
Page({
  onBindPhone(e) {
    const { code } = e.detail
    if (!code) return
    wx.request({
      url: 'https://api.example.com/api/user/phone/bind',
      method: 'POST',
      header: { 'Authorization': 'Bearer ' + wx.getStorageSync('token') },
      data: { code },
      success: (res) => {
        if (res.data.code === 0) {
          wx.showToast({ title: '绑定成功' })
          // 绑定成功后合并游客数据（购物车/收藏）由后端按 openid 完成
        } else if (res.data.code === 40901) {
          // 手机号已被其他账号绑定
          wx.showModal({
            title: '手机号已被绑定',
            content: '该手机号已绑定其他账号，可切换登录或联系客服处理',
            showCancel: false
          })
        }
      }
    })
  }
})
```

```text
账号体系要点：
1. 游客模式 —— openid 静默建立匿名身份，先可用后完善
2. 微信登录 —— 默认主身份，openid 免密登录
3. 手机号绑定 —— 手机号+验证码做多端入口与找回凭证，唯一约束
4. 数据合并 —— 游客数据登录后按 openid/unionid 归并，不丢失
5. 解绑换绑 —— 解绑需二次验证，账号至少保留一个有效登录身份
6. 跨端互认 —— 同一 unionid 会话共享，App 登录小程序免登
```

## 用户画像构建

用户画像把用户数据变成可运营的资产，三个数据来源：标签（运营手动打标与规则自动打标）、行为数据（浏览、点击、收藏、加购、下单等埋点事件）、来源渠道（场景值 scene 与渠道参数）。画像的存储用「用户-标签多对多表」与「行为流水表」，行为流水按时间聚合出频次、偏好、价值分层。

埋点上报：小程序端自定义事件上报到自建埋点接口（或接入微信数据分析），上报浏览、点击、搜索、下单等关键事件，事件带 userId 与场景值。行为数据经过 ETL 聚合后写入用户标签：如「30 天内下单 ≥ 3 次」打「高活跃买家」标签、「收藏未购买」打「意向用户」标签。画像的应用：首页个性化推荐、运营触达（订阅消息、优惠券定向发放）、风控（异常行为识别）。

```sql
-- 用户标签表
CREATE TABLE `t_user_tag` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id` BIGINT UNSIGNED NOT NULL COMMENT '用户ID',
  `tag` VARCHAR(32) NOT NULL COMMENT '标签名',
  `source` VARCHAR(16) NOT NULL DEFAULT 'system' COMMENT '来源 system/operator/rule',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_tag` (`user_id`, `tag`),
  KEY `idx_tag` (`tag`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户标签表';

-- 行为流水表（埋点原始数据，按天分区）
CREATE TABLE `t_user_behavior` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id` BIGINT UNSIGNED NOT NULL COMMENT '用户ID',
  `event` VARCHAR(32) NOT NULL COMMENT '事件名 view/click/fav/cart/order',
  `scene` INT DEFAULT NULL COMMENT '来源场景值',
  `ext` JSON DEFAULT NULL COMMENT '扩展数据（商品ID等）',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_user_event` (`user_id`, `event`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='行为流水表';
```

## 会员体系设计

会员体系是用户运营的核心机制，两个基本盘：等级与积分。等级由成长值决定，成长值来自消费、签到、分享等行为，等级决定会员权益（折扣、免邮、专属客服）；积分是可变现的虚拟资产，可兑换优惠券、商品，也可做积分抵扣。设计上等级与积分独立演进：等级只升不降（或按周期保级），积分有获取与消耗两条流水。

工程要点：积分变更必须走「流水 + 余额」双写，且用事务/乐观锁防并发扣减（先查余额再改会导致超扣，用 update ... where points >= X 的原子更新或 Redis 扣减）；积分流水表记录每笔变更的来源与关联单号，支持对账与申诉；等级计算可以异步化（行为事件落库后由任务聚合），避免下单链路里同步算成长值拖慢主流程。

```sql
-- 积分流水表
CREATE TABLE `t_points_log` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id` BIGINT UNSIGNED NOT NULL COMMENT '用户ID',
  `change` INT NOT NULL COMMENT '变动值 正为增加 负为扣减',
  `balance` INT NOT NULL COMMENT '变动后余额',
  `type` VARCHAR(32) NOT NULL COMMENT '类型 order/signin/exchange/refund',
  `biz_id` VARCHAR(64) DEFAULT NULL COMMENT '关联业务单号',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_user` (`user_id`),
  KEY `idx_biz` (`biz_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='积分流水表';
```

```java
// PointsService.java —— 积分扣减：原子更新防超扣
@Transactional
public void deduct(Long userId, int points, String type, String bizId) {
    // 1. 原子扣减：余额不足则影响行数为 0
    int affected = userMapper.deductPoints(userId, points);   // update t_user set points = points - ? where id = ? and points >= ?
    if (affected == 0) {
        throw new BizException("积分不足");
    }
    // 2. 写流水（余额在流水里记录扣减后快照）
    User user = userMapper.selectById(userId);
    pointsLogMapper.insert(new PointsLog(userId, -points, user.getPoints(), type, bizId));
}
```

```text
会员体系要点：
1. 等级 —— 成长值驱动，决定权益；可设计周期保级
2. 积分 —— 获取与消耗双流水，独立于等级演进
3. 防超扣 —— 原子更新（where points >= ?）或 Redis 扣减
4. 流水对账 —— 每笔变更落流水，带关联单号可追溯
5. 异步计算 —— 成长值聚合异步化，不拖慢下单主链路
6. 合规 —— 积分属虚拟资产，规则公示，过期与注销规则清晰
```

## 应用场景实战

### 场景一：小程序 + 公众号 H5 的用户合并打通

需求：公司已有公众号 H5 商城（网页授权登录），现在上线小程序商城。要求：同一微信用户在两端的账号、订单、积分完全打通，H5 老用户在小程序登录后直接看到历史订单。

```text
实现步骤：
1. 开放平台注册并认证，把公众号与小程序的 AppID 绑定到同一开放平台账号
2. 用户表与 t_user_auth 表落库，两端登录都记录 openid + unionid
3. H5 端登录：网页授权 code 换 openid + unionid（公众号接口）
4. 小程序端登录：code2session 换 openid + unionid（09.1 流程）
5. 登录统一入口：openid 查不到时按 unionid 查已有用户并复用（loginByAuth）
6. 老用户首次小程序登录：按 unionid 命中 H5 账号，自动合并，订单积分延续
7. 验证：H5 老用户小程序登录后，个人中心展示历史订单与积分余额
```

```java
// 合并后的效果校验（伪代码）
User h5User = userService.loginByAuth("wechat_mp", h5Openid, h5Unionid);
User miniUser = userService.loginByAuth("wechat_mini", miniOpenid, miniUnionid);
// 两者 unionid 相同 -> loginByAuth 返回同一个 userId，订单与积分天然共享
assert h5User.getId().equals(miniUser.getId());
```

### 场景二：新用户「游客浏览 -> 微信登录 -> 手机号绑定」三段式转正

需求：新用户不登录先浏览商品、加购物车；结账时微信登录转正；会员日领取手机号专享券时绑定手机号。要求三个阶段数据无缝衔接。

```js
// pages/cart/cart.js —— 游客加购 -> 登录转正 -> 数据合并
const { login } = require('../../utils/auth')

Page({
  onCheckout() {
    wx.showLoading({ title: '正在登录...' })
    login()
      .then(() => {
        // 登录成功：后端按 openid 合并游客购物车，前端拉取最新购物车
        return this.fetchCart()
      })
      .then(() => {
        wx.hideLoading()
        wx.navigateTo({ url: '/pages/order/confirm' })
      })
      .catch(() => {
        wx.hideLoading()
        wx.showToast({ title: '登录失败，请重试', icon: 'none' })
      })
  },

  fetchCart() {
    return new Promise((resolve, reject) => {
      wx.request({
        url: 'https://api.example.com/api/cart/list',
        method: 'GET',
        header: { 'Authorization': 'Bearer ' + wx.getStorageSync('token') },
        success: (res) => { this.setData({ cart: res.data.data.list }); resolve() },
        fail: reject
      })
    })
  }
})
```

```text
两个场景的共性设计：
1. unionid 是合并的锚点 —— 多端账号按 unionid 归并
2. 认证记录完整 —— t_user_auth 保留每端绑定关系，可解绑可追溯
3. 游客数据不丢 —— 登录后按 openid 合并购物车/收藏
4. 渐进式转正 —— 游客可用 -> 登录转正 -> 手机号绑定，层层递进
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用户表主键用自增 id，openid/unionid 只做索引，为多端合并与账号演进留空间
2. 多端打通前先注册微信开放平台并完成认证，unionid 才能稳定返回
3. 登录统一入口（loginByAuth）按 auth_type + openid 查，查不到再按 unionid 合并，杜绝重复建号
4. 游客数据登录后按 openid 归并，购物车、收藏、浏览记录一律不丢
5. 手机号唯一约束 + 绑定冲突提示，避免一个手机号绑多个账号
6. 积分扣减用原子 SQL 或 Redis，配合流水表双写，保证不超扣、可对账
7. 封禁/注销用 status 状态位而非物理删除，业务数据可追溯
8. 行为埋点与标签表独立于业务表设计，画像与会员体系解耦演进

### 踩坑记录

```text
坑 1：用 openid 做主键，后期多端打通无法合并
结论：公众号与小程序两个 openid 各建一条用户记录，订单积分割裂。
原因：设计初期把 openid 当业务主键，没有预留 unionid 合并通道。
解法：自增 id 主键 + t_user_auth 认证表，登录按 openid 查、按 unionid 合并。

坑 2：openid 没建唯一索引，同一用户重复注册
结论：用户表出现多条同 openid 记录，登录时 selectOne 直接报错。
原因：并发登录（多设备同时首次进入）下查建逻辑没有唯一约束兜底。
解法：uk_openid 唯一索引 + 查建逻辑处理 DuplicateKey 重试。

坑 3：unionid 拿不到就当打通失败
结论：部分用户多端账号合并不了，运营投诉数据对不上。
原因：unionid 返回依赖认证、绑定与用户交互记录，不是必然返回。
解法：unionid 可选处理，缺失不阻断登录；引导用户关注公众号后补全。

坑 4：手机号不做唯一校验，一个手机号绑多个账号
结论：同手机号出现在多个账号，客服与风控混乱。
原因：绑定接口没加唯一约束与冲突检测。
解法：phone 唯一索引 + 绑定前校验，冲突时引导换绑或合并。

坑 5：积分扣减「先查后改」，并发下单超扣
结论：用户同时提交多笔订单，积分被扣成负数。
原因：select 余额 -> 判断 -> update 三步非原子，并发下互相覆盖。
解法：update ... where points >= ? 原子扣减，影响行数为 0 即余额不足。

坑 6：封禁用户直接 delete 数据
结论：用户历史订单、评论关联查询全部断裂，对账无据可查。
原因：用物理删除代替状态管理。
解法：status 字段（1 正常 0 禁用 2 注销），查询统一过滤，数据保留。

坑 7：游客数据不合并，用户登录后购物车「消失」
结论：用户加购后登录，购物车清空，投诉率高。
原因：游客 openid 与登录后没有做数据归并。
解法：登录成功后按 openid 把游客购物车/收藏合并进正式账号。

坑 8：多端打通没做存量数据迁移
结论：线上老用户多端账号历史割裂，新逻辑只对增量用户生效。
原因：只改了新登录逻辑，没跑存量去重合并脚本。
解法：上线前按 unionid 写迁移脚本归并存量用户，灰度验证后再全量。
```
