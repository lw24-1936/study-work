## 概述

09.1 篇章解决了「用户是谁」的问题：wx.login 换回 openid 并建立用户。但 openid 不能每次请求都拿去微信换一次身份，小程序与后端之间需要一个长期有效的「会话凭证」——token。token 由服务端在登录成功后签发，小程序端持久化保存，之后每次请求通过请求头携带，后端校验通过即认定请求来自该用户。

本篇章覆盖 token 的完整生命周期：签发（JWT 与随机串两种主流方案）、存储（小程序本地缓存与请求封装）、过期与续期（双 token、滑动续期、401 拦截）、登出（本地清除 + 服务端失效）、会话安全（泄露风险、HTTPS、有效期控制）。JWT 的原理细节见 18.1-JWT 认证 篇章，本篇章聚焦「会话怎么在小程序全栈体系里保持」。

```text
会话保持核心要点：
1. token 由服务端签发 —— 登录成功后生成，前端不参与签名逻辑
2. 本地持久化 —— wx.setStorageSync 存储，重启小程序不丢失
3. 请求携带 —— 统一在请求封装里加 Authorization 头，业务代码无感
4. 过期续期 —— 401 拦截 + 刷新 token 静默续期，用户无感知
5. 登出双清 —— 本地清 token + 服务端会话失效，缺一不可
6. 安全底线 —— HTTPS 传输、有效期控制、敏感信息不入库不入日志
```

## token 签发机制

token 由服务端在登录成功后签发，主流方案有两种：JWT（JSON Web Token）与「随机串 + Redis 服务端会话」。JWT 是自包含的无状态令牌：token 本身就是一段携带用户信息与过期时间的签名数据，服务端校验时无需查库；随机串方案则是「随机字符串 + Redis 中存放的会话记录」，服务端需要查 Redis 才能确认会话有效。

两种方案各有适用场景。JWT 的优势是校验快、天然支持多服务节点（无共享存储也能校验）；缺点是签发后难以主动失效（登出、封禁必须借助黑名单或版本号）。随机串 + Redis 的优势是可控性强：登出直接删 key、封禁直接失效、续期直接改过期时间；缺点是需要维护 Redis，且每个请求多一次 Redis 查询。中小型全栈项目常用「JWT 做 access token + Redis 做黑名单/刷新凭证」的组合方案。

```java
// TokenService.java —— JWT 签发（jjwt 依赖）
@Component
public class TokenService {

    @Value("${jwt.secret}")
    private String secret;          // 至少 32 字节随机串，配置中心管理

    @Value("${jwt.expire-seconds}")
    private long expireSeconds;     // 默认 7 天

    public String createToken(Long userId) {
        Date now = new Date();
        Date expireAt = new Date(now.getTime() + expireSeconds * 1000);
        return Jwts.builder()
                .setSubject(String.valueOf(userId))
                .claim("loginTime", now.getTime())
                .setIssuedAt(now)
                .setExpiration(expireAt)
                .signWith(SignatureAlgorithm.HS256, secret.getBytes(StandardCharsets.UTF_8))
                .compact();
    }

    public Long parseUserId(String token) {
        Claims claims = Jwts.parser()
                .setSigningKey(secret.getBytes(StandardCharsets.UTF_8))
                .parseClaimsJws(token)
                .getBody();
        return Long.valueOf(claims.getSubject());
    }
}
```

```java
// TokenService.java —— 随机串 + Redis 会话（Spring Data Redis）
@Component
public class TokenService {

    @Autowired
    private StringRedisTemplate redis;

    private static final String TOKEN_PREFIX = "weapp:token:";

    public String createToken(Long userId) {
        String token = UUID.randomUUID().toString().replace("-", "");
        // 会话有效期 7 天，存 userId 便于查询
        redis.opsForValue().set(TOKEN_PREFIX + token,
                String.valueOf(userId), Duration.ofDays(7));
        return token;
    }

    public Long parseUserId(String token) {
        String userId = redis.opsForValue().get(TOKEN_PREFIX + token);
        return userId == null ? null : Long.valueOf(userId);
    }

    public void invalidate(String token) {
        redis.delete(TOKEN_PREFIX + token);
    }
}
```

```text
token 签发要点：
1. 签发时机 —— 登录成功后立即签发，登录接口返回 token 与用户信息
2. JWT 方案 —— 自包含无状态，校验快；但登出/封禁需黑名单配合
3. Redis 方案 —— 随机串 + 会话记录，可控性强；每请求一次 Redis 查询
4. 密钥管理 —— JWT 签名密钥存配置中心，随机串方案无密钥但依赖 Redis 可用性
5. 载荷最小化 —— token 里只放 userId 等必要字段，不放大对象、不放大密钥
6. 有效期分级 —— access token 短时效（如 2 小时），刷新凭证长时效（如 7 天）
```

## token 存储方案

小程序端拿到 token 后必须持久化，否则每次冷启动登录态丢失。标准做法是 wx.setStorageSync('token', token) 存入本地缓存（同步版本，写入即完成，避免异步竞态）；读取时同样用同步版本 wx.getStorageSync('token')。token 不应该只存在内存变量里——小程序被系统回收后内存清空，登录态就丢了，用户要重新登录。

存储规范有三条硬性要求：第一，只存 token，不存 code（code 是一次性凭证，存下来没有任何复用价值，还容易被误用）；第二，敏感信息（手机号明文、session_key）不要和 token 一起存本地，本地缓存可被读取，只存业务必需数据；第三，读写统一封装在 auth 模块里，页面与业务代码不要直接操作 storage，便于统一处理过期、清理等逻辑。

请求携带 token 的方式是统一封装：所有 wx.request 走同一个 request 工具函数，函数内自动读取 token 并写入请求头 Authorization: Bearer xxx，业务代码无感知。后端从请求头解析 token 并校验，校验失败返回 401。

```js
// utils/request.js —— 统一请求封装，自动携带 token
const BASE_URL = 'https://api.example.com'

function request(options) {
  const token = wx.getStorageSync('token')
  return new Promise((resolve, reject) => {
    wx.request({
      url: BASE_URL + options.url,
      method: options.method || 'GET',
      data: options.data || {},
      header: {
        'Content-Type': 'application/json',
        'Authorization': token ? 'Bearer ' + token : '',
        ...options.header
      },
      success: (res) => {
        if (res.statusCode === 401) {
          // token 失效，交给统一处理器（见过期与续期一节）
          handleTokenExpired(options)
          return
        }
        resolve(res.data)
      },
      fail: (err) => reject(err)
    })
  })
}

module.exports = { request, BASE_URL }
```

```text
token 存储要点：
1. 同步读写 —— wx.setStorageSync / wx.getStorageSync，避免异步竞态
2. 不存 code —— code 一次性且 5 分钟过期，存它没有意义
3. 敏感信息隔离 —— 手机号明文、session_key 等不落本地缓存
4. 统一封装 —— 请求头由 request 工具统一加，业务代码不感知
5. 键名约定 —— 用 'token'、'userInfo' 等固定键名，登出时统一清理
6. 容量注意 —— 本地缓存有 10MB 上限，不要往缓存里塞大对象
```

## token 过期与续期

token 必须有有效期，否则泄露后永久有效，安全无从谈起。过期后怎么办，取决于续期方案设计。小程序场景最常用的是「双 token 方案」：access token 短时效（如 2 小时）用于业务请求，refresh token 长时效（如 7 天）专门用于换发新 access token；access token 过期时，前端用 refresh token 调刷新接口拿新 access token，全程静默。

另一种是「滑动续期」：access token 有效期较长（如 7 天），后端在每次请求校验时检查剩余有效期，若低于阈值（如 1 天）则在响应头或响应体里带上新 token，前端静默替换本地存储。滑动续期实现简单，但会引入「每个响应都可能带新 token」的约定，前端要统一处理。还有更简单的方案：启动时（App.onLaunch）检查 token 剩余有效期，将过期则先调刷新接口再进首页。

无论哪种方案，前端都要统一处理 401：所有请求共用一个「401 处理器」，处理器保证「同一时刻只有一个刷新请求在途」，其余 401 请求排队等待刷新完成后再重放。这个队列设计很关键，否则 N 个并发请求同时 401 会触发 N 次刷新请求，把刷新接口打爆。

```js
// utils/auth.js —— 双 token 方案：401 拦截 + 刷新队列重放
let refreshPromise = null   // 刷新单例：同一时刻只允许一个刷新请求
const pendingQueue = []     // 等待重放的请求队列

function handleTokenExpired(options) {
  // 1. 刷新请求已在途，直接排队等待重放
  if (refreshPromise) {
    pendingQueue.push(options)
    return
  }
  // 2. 发起刷新（refresh token 存在本地）
  const refreshToken = wx.getStorageSync('refreshToken')
  refreshPromise = new Promise((resolve, reject) => {
    wx.request({
      url: 'https://api.example.com/api/auth/refresh',
      method: 'POST',
      data: { refreshToken },
      success: (res) => {
        if (res.data.code === 0) {
          wx.setStorageSync('token', res.data.data.token)
          wx.setStorageSync('refreshToken', res.data.data.refreshToken)
          resolve()
        } else {
          // refresh token 也失效，只能重新登录
          reject(new Error('refresh token expired'))
        }
      },
      fail: reject
    })
  }).finally(() => {
    refreshPromise = null
  })

  refreshPromise
    .then(() => {
      // 3. 刷新成功，重放所有排队的请求
      pendingQueue.splice(0).forEach((opt) => request(opt))
    })
    .catch(() => {
      // 4. 刷新失败，清理登录态，跳转登录页
      pendingQueue.splice(0)
      wx.removeStorageSync('token')
      wx.removeStorageSync('refreshToken')
      wx.navigateTo({ url: '/pages/login/login' })
    })
}
```

```text
token 过期与续期要点：
1. access token 短时效 —— 泄露影响面小，默认 2 小时左右
2. refresh token 长时效 —— 只用于换发，不用于业务请求，默认 7 天
3. 401 统一拦截 —— 业务代码不感知，全部交给请求封装处理
4. 刷新单例 —— 并发 401 只发一个刷新请求，其余排队重放
5. 静默续期 —— 刷新过程无弹窗无跳转，用户无感知
6. 彻底失败兜底 —— refresh token 也失效则清理登录态、引导重新登录
```

## 登出与会话销毁

登出要做「双清」：前端清除本地 token 与用户缓存，后端使服务端会话失效。只清前端不通知后端，token 在服务端仍然有效，设备丢失或账号被盗时无法止损；只清后端不清前端，本地残留 token 会导致后续请求反复 401。

前端登出动作：调用登出接口（携带 token 通知后端销毁会话）-> 清除本地 token、refreshToken、userInfo 等所有登录态缓存 -> 跳转或刷新页面。需要容错：登出接口调用失败（弱网）也要继续清本地，不能因为接口失败就「登出不了」。后端登出动作：JWT 方案将 token 加入 Redis 黑名单（有效期与 token 剩余有效期一致）或递增用户会话版本号；随机串方案直接删除 Redis 会话 key。

```js
// utils/auth.js —— 登出：先通知后端，再清本地
const { request } = require('./request')

function logout() {
  return request({ url: '/api/auth/logout', method: 'POST' })
    .catch(() => {})          // 接口失败不阻断登出
    .finally(() => {
      wx.removeStorageSync('token')
      wx.removeStorageSync('refreshToken')
      wx.removeStorageSync('userInfo')
      // 可选：reLaunch 到首页或登录页
    })
}

module.exports = { logout }
```

```java
// AuthController.java —— 服务端登出
@PostMapping("/logout")
public Result<Void> logout(@RequestHeader(value = "Authorization", required = false) String authHeader) {
    String token = resolveToken(authHeader);
    if (token != null) {
        tokenService.invalidate(token);   // Redis 删 key / JWT 拉黑
    }
    return Result.ok();
}
```

```text
登出要点：
1. 前端后端都清 —— 本地缓存 + 服务端会话，缺一不可
2. 接口失败也要清本地 —— 登出不能被弱网卡住
3. JWT 需要黑名单 —— 无状态令牌只能靠 Redis 黑名单或版本号失效
4. 全量清理 —— token、refreshToken、userInfo 等登录相关键全部移除
5. 登出后跳转 —— 清理完成后 reLaunch 到登录页或首页
6. 服务端失效要有兜底 —— 即使客户端不调登出接口，token 也会自然过期
```

## 会话安全防护

会话安全的核心矛盾是：token 一旦泄露，等于账号被冒用。因此防护要覆盖「传输、存储、有效期、失效机制」四个层面。传输层面：小程序 request 合法域名强制 HTTPS，杜绝明文抓包；token 只放请求头，不放 URL 参数（URL 会进日志、可能被分享转发泄露）。存储层面：本地缓存只存必要数据，敏感信息脱敏；不给用户头像昵称等之外的隐私数据落盘。有效期层面：access token 短时效 + 刷新机制，控制泄露窗口；token 中不携带敏感信息，日志输出时脱敏。

失效机制层面要注意两个经典问题。一是「无状态 token 无法即时失效」：用户被封禁、改密后，已签发的 JWT 依然有效，需要 Redis 黑名单或「登录版本号」机制——用户表加 session_version 字段，签发 token 时写入版本，校验时比对，版本变更（封禁、登出、改密）则旧 token 全部失效。二是「会话固定」：登录成功后签发全新 token，不要复用登录前的旧会话，防止攻击者预置会话。

```java
// TokenService.java —— JWT + 登录版本号：封禁/改密后旧 token 立即失效
public boolean validate(String token, User user) {
    try {
        Claims claims = Jwts.parser()
                .setSigningKey(secret.getBytes(StandardCharsets.UTF_8))
                .parseClaimsJws(token)
                .getBody();
        // 版本号比对：签发时的版本必须等于用户当前版本
        Integer version = claims.get("ver", Integer.class);
        return version != null && version.equals(user.getSessionVersion());
    } catch (JwtException e) {
        return false;   // 签名错误 / 过期 / 篡改
    }
}
```

```text
会话安全要点：
1. HTTPS 必须 —— 小程序域名强制 https，明文传输等于裸奔
2. token 只走 Header —— 不放 URL、不进日志、不打印到控制台
3. 有效期分级 —— access 短 refresh 长，泄露窗口最小化
4. 版本号失效 —— 封禁/改密/登出后递增版本号，旧 token 全部作废
5. 登录后换新 —— 每次登录签发全新 token，不复用旧会话（防会话固定）
6. 服务端兜底校验 —— 高危操作（支付、改密）二次校验密码或验证码
```

## 应用场景实战

### 场景一：双 token 静默续期 + 请求重放

需求：access token 有效期 2 小时，refresh token 有效期 7 天。用户在会话中 token 过期，继续操作时多个接口同时 401，要求只发一次刷新请求，全部请求静默重放成功。

```js
// utils/request.js —— 完整版：401 拦截 + 刷新 + 重放（与 auth.js 配合）
const { refreshTokenAndRetry } = require('./auth')

let isRefreshing = false
const queue = []

function request(options) {
  const token = wx.getStorageSync('token')
  return new Promise((resolve, reject) => {
    wx.request({
      url: BASE_URL + options.url,
      method: options.method || 'GET',
      data: options.data || {},
      header: { 'Authorization': token ? 'Bearer ' + token : '' },
      success: (res) => {
        if (res.statusCode === 401) {
          // 排队等待刷新，刷新完成后按原参数重放
          queue.push({ options, resolve, reject })
          if (!isRefreshing) {
            isRefreshing = true
            refreshTokenAndRetry()
              .then(() => {
                queue.splice(0).forEach((item) => {
                  request(item.options).then(item.resolve).catch(item.reject)
                })
              })
              .catch(() => {
                queue.splice(0).forEach((item) => item.reject(new Error('登录已过期')))
                wx.removeStorageSync('token')
                wx.removeStorageSync('refreshToken')
                wx.navigateTo({ url: '/pages/login/login' })
              })
              .finally(() => { isRefreshing = false })
          }
          return
        }
        resolve(res.data)
      },
      fail: reject
    })
  })
}
```

### 场景二：7 天无操作自动登出 + 主动登出

需求：安全要求较高的业务（如管理类小程序），会话最长 7 天，7 天无操作自动登出；用户点击「退出登录」立即销毁前后端会话。

```js
// utils/session.js —— 7 天无操作自动登出
const { logout } = require('./auth')
const MAX_IDLE = 7 * 24 * 60 * 60 * 1000   // 7 天

let lastActive = Date.now()

function recordActive() {
  lastActive = Date.now()
}

function checkSession() {
  if (Date.now() - lastActive > MAX_IDLE) {
    logout()   // 双清：服务端失效 + 本地清理
  }
}

// 页面切前台时检查（App 级）
App({
  onShow() {
    checkSession()
  },
  onHide() {
    // 切后台记录时间，回到前台时若超期则登出
  }
})
```

```text
两个场景的共性设计：
1. 刷新逻辑收敛在请求层 —— 业务代码只发请求，不关心 401 与刷新
2. 重放队列 —— 多个并发 401 统一排队，刷新完成后按序重放
3. 双清兜底 —— 刷新失败/会话超期时本地与服务端同时清理
4. 用户无感 —— 正常续期静默完成，只有彻底失效才引导重新登录
```

## 最佳实践与踩坑记录

### 最佳实践

1. 采用「access token 短时效 + refresh token 长时效」双 token 方案，把泄露窗口控制在小时级
2. 刷新逻辑统一收敛在请求封装层，用单例保证同一时刻只有一个刷新请求在途
3. token 只存本地缓存（wx.setStorageSync），不存 code、不落全局变量、不进 URL
4. 登出双清：先调服务端失效接口（失败也继续），再清本地全部登录态键
5. 服务端用「会话版本号」实现即时失效：封禁、改密、登出递增版本，旧 token 全作废
6. 日志与埋点对 token 脱敏，只记录 userId 与时间，不记录完整令牌
7. 高危操作（支付、改密、解绑手机号）在 token 校验之外追加二次验证
8. 登录、刷新、登出三个接口独立限流，防止会话接口被刷

### 踩坑记录

```text
坑 1：token 只存内存变量，小程序重启后登录态丢失
结论：冷启动后所有请求 401，用户要重新登录，体验极差。
原因：token 只保存在 Page/App 的 data 或变量里，没有持久化。
解法：登录成功即 wx.setStorageSync('token', token)，启动时同步读取。

坑 2：并发 401 触发多次刷新，刷新接口被刷爆
结论：刷新接口瞬间收到 N 个并发请求，部分失败导致前端连环报错。
原因：每个 401 请求各自触发一次刷新，没有单例与排队机制。
解法：刷新用 Promise 单例，其余 401 请求进队列，刷新完成后统一重放。

坑 3：JWT 无状态，用户封禁后 token 依然有效
结论：封禁账号后该用户仍能正常调接口 7 天。
原因：JWT 校验只看签名与过期时间，签发后无法即时作废。
解法：用户表加 session_version，签发时写入、校验时比对，封禁时递增。

坑 4：登出只清本地，服务端会话残留
结论：用户点退出后，旧 token 仍可调接口，存在被盗用风险。
原因：只做了 wx.removeStorageSync，没有通知服务端失效。
解法：登出先调接口让服务端删会话/拉黑，再清本地，接口失败也要清本地。

坑 5：token 放进 URL 参数导致泄露
结论：抓包或日志里能看到完整 token，且分享链接会携带 token。
原因：请求参数里直接拼 token，URL 进了网关与业务日志。
解法：token 一律放 Authorization 请求头，禁止进 URL 与日志。

坑 6：access token 与 refresh token 用同一个值
结论：access 泄露等于 refresh 泄露，短时效设计失去意义。
原因：偷懒复用同一个 token，没有区分两种凭证。
解法：两种 token 分开签发，refresh token 只允许调刷新接口，不参与业务请求。

坑 7：刷新接口不校验 refresh token 归属
结论：拿任意有效 refresh token 就能换新 token，批量盗号风险。
原因：刷新接口只验 token 有效，没校验与当前用户/设备是否匹配。
解法：refresh token 绑定 userId，刷新时校验归属并轮换（每次刷新都换新）。

坑 8：token 有效期设 30 天且无续期机制
结论：泄露后攻击窗口长达一个月，风险不可控。
原因：为了「用户少登录」而无限拉长有效期。
解法：access 2 小时 + refresh 7 天 + 滑动续期，用户无感且窗口可控。
```
