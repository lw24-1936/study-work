## 概述

RBAC（Role-Based Access Control，基于角色的访问控制）是目前最主流的权限模型：不直接给用户授权，而是把权限授予角色，再把角色授予用户。用户与权限之间通过角色解耦，新增用户只需分配角色，调整权限只需改角色配置，权限管理从「一人一配」变成「角色模板化」，大幅降低管理成本。

本篇章承接 18.2 的 Spring Security 授权体系：Spring Security 负责「怎么判断」（hasRole/hasAuthority 的执行机制），RBAC 负责「判断依据从哪来」（用户-角色-权限的数据模型与查询）。配合菜单权限控制管理端页面可见性，配合数据权限控制行级数据范围，构成「接口权限 + 页面权限 + 数据权限」三层完整的权限体系。

```text
RBAC 权限模型的核心特征：
1. 三层解耦 —— 用户挂角色，角色挂权限，用户不直接挂权限
2. 五表模型 —— user、role、permission、user_role、role_permission
3. 权限粒度 —— 权限字符串按 模块:操作 命名（order:delete），支持按钮级控制
4. 菜单权限 —— 按用户权限动态生成菜单树，控制管理端页面可见性
5. 数据权限 —— 控制数据行范围：本人、本部门、全部，SQL 动态拼接
6. 缓存加速 —— 用户权限查询结果缓存到 Redis，避免每次请求查库
```

## RBAC 权限模型

RBAC 的核心思想是「权限不直接授予用户，而是通过角色中转」。这样做的好处：用户数量远大于角色数量，角色是稳定可复用的；权限调整只改角色，不用逐个改用户；一个用户可以拥有多个角色，权限取并集。

标准 RBAC 用五张表表达三组关系：用户表与角色表通过 user_role 关联（多对多），角色表与权限表通过 role_permission 关联（多对多）。建表语句：

```sql
-- 用户表
CREATE TABLE sys_user (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    username    VARCHAR(64)  NOT NULL UNIQUE,
    password    VARCHAR(128) NOT NULL,          -- BCrypt 哈希
    nickname    VARCHAR(64),
    dept_id     BIGINT,                          -- 所属部门，数据权限用
    status      TINYINT      DEFAULT 1,          -- 1 启用 0 禁用
    create_time DATETIME     DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_dept (dept_id)
) ENGINE = InnoDB COMMENT '用户表';

-- 角色表
CREATE TABLE sys_role (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    role_code   VARCHAR(64) NOT NULL UNIQUE,    -- 如 ADMIN / OPERATOR
    role_name   VARCHAR(64) NOT NULL,           -- 如 管理员 / 运营
    data_scope  TINYINT     DEFAULT 2,          -- 数据范围：1 本人 2 本部门 3 全部
    status      TINYINT     DEFAULT 1,
    create_time DATETIME    DEFAULT CURRENT_TIMESTAMP
) ENGINE = InnoDB COMMENT '角色表';

-- 权限表（菜单与按钮共用一张表）
CREATE TABLE sys_permission (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    perm_code   VARCHAR(128) NOT NULL UNIQUE,   -- 如 order:list / order:delete
    perm_name   VARCHAR(64)  NOT NULL,          -- 权限名称
    type        TINYINT      DEFAULT 1,         -- 1 菜单 2 按钮
    parent_id   BIGINT       DEFAULT 0,         -- 父菜单 ID，0 表示根
    path        VARCHAR(255),                   -- 菜单路由路径，按钮权限为空
    icon        VARCHAR(64),
    sort        INT          DEFAULT 0,         -- 排序号
    status      TINYINT      DEFAULT 1
) ENGINE = InnoDB COMMENT '权限表';

-- 用户-角色关联表
CREATE TABLE sys_user_role (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    PRIMARY KEY (user_id, role_id)
) ENGINE = InnoDB COMMENT '用户角色关联表';

-- 角色-权限关联表
CREATE TABLE sys_role_permission (
    role_id       BIGINT NOT NULL,
    permission_id BIGINT NOT NULL,
    PRIMARY KEY (role_id, permission_id)
) ENGINE = InnoDB COMMENT '角色权限关联表';
```

查询用户权限的核心 SQL（用户 → 角色 → 权限三级联查）：

```sql
SELECT DISTINCT p.perm_code
FROM sys_permission p
JOIN sys_role_permission rp ON rp.permission_id = p.id
JOIN sys_user_role ur        ON ur.role_id = rp.role_id
WHERE ur.user_id = #{userId}
  AND p.status = 1
ORDER BY p.sort ASC;
```

```text
RBAC 模型要点：
1. 用户与角色、角色与权限都是多对多，用中间表关联，避免冗余与维护爆炸
2. 权限字符串命名规范 模块:操作（order:list、order:delete），权限表按此唯一约束
3. 权限表同时承载菜单与按钮：type 区分，parent_id 组织菜单树
4. 数据范围（data_scope）挂在角色上，同一角色用户共享同一数据范围
5. 用户多角色时权限取并集，角色冲突（如同时有管理员与普通用户）以高权限为准
6. 建表时对 user_id、role_id 建索引，三级联查性能才有保障
```

## 菜单权限

菜单权限解决「管理端页面谁能看到」的问题。管理后台（Vue）的侧边栏菜单不是写死的，而是登录后由后台按用户权限动态下发：用户有哪些菜单权限，前端就渲染哪些菜单，没有权限的页面即使猜到路由也无法访问（路由守卫配合接口权限双重拦截）。

菜单表设计：权限表中的 type=1 记录即菜单，parent_id 表达层级，path 是前端路由路径，sort 控制排序。后台提供接口返回当前用户的菜单树，前端按树渲染。查询用户可见菜单的 SQL 与权限查询类似，只是过滤 type=1：

```sql
SELECT DISTINCT p.id, p.perm_name, p.path, p.parent_id, p.icon, p.sort
FROM sys_permission p
JOIN sys_role_permission rp ON rp.permission_id = p.id
JOIN sys_user_role ur        ON ur.role_id = rp.role_id
WHERE ur.user_id = #{userId}
  AND p.type = 1
  AND p.status = 1
ORDER BY p.sort ASC;
```

菜单树构建（把扁平列表组装成树形结构）：

```java
package com.example.service;

import com.example.entity.Menu;
import com.example.mapper.MenuMapper;
import org.springframework.stereotype.Service;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

@Service
public class MenuService {

    private final MenuMapper menuMapper;

    public MenuService(MenuMapper menuMapper) {
        this.menuMapper = menuMapper;
    }

    /** 查询用户菜单并组装成树 */
    public List<Map<String, Object>> getUserMenuTree(Long userId) {
        List<Menu> menus = menuMapper.selectMenusByUserId(userId); // 上面的 SQL
        Map<Long, Map<String, Object>> nodeMap = new HashMap<>();
        List<Map<String, Object>> roots = new ArrayList<>();

        // 第一遍：把实体转成节点并放入 Map
        for (Menu menu : menus) {
            Map<String, Object> node = new HashMap<>();
            node.put("id", menu.getId());
            node.put("name", menu.getPermName());
            node.put("path", menu.getPath());
            node.put("parentId", menu.getParentId());
            node.put("icon", menu.getIcon());
            node.put("children", new ArrayList<Map<String, Object>>());
            nodeMap.put(menu.getId(), node);
        }
        // 第二遍：挂接父子关系，parentId 为 0 或父节点不存在的是根
        for (Menu menu : menus) {
            Map<String, Object> node = nodeMap.get(menu.getId());
            Map<String, Object> parent = nodeMap.get(menu.getParentId());
            if (parent != null) {
                ((List<Map<String, Object>>) parent.get("children")).add(node);
            } else {
                roots.add(node);
            }
        }
        return roots;
    }
}
```

前端（Vue3 + Element Plus）动态渲染菜单的骨架：

```javascript

await menuStore.loadMenus(); // 内部调用后台接口

      <el-menu-item v-for="child in menu.children" :key="child.id" :index="child.path">
        {{ child.name }}
      </el-menu-item>
    </el-sub-menu>
    <el-menu-item v-else :index="menu.path">{{ menu.name }}</el-menu-item>
  </template>

```

```text
菜单权限要点：
1. 菜单与按钮共用权限表，type 区分，parent_id 组织层级
2. 管理端菜单动态下发：登录后拉取菜单树，前端按树渲染，不用写死
3. 前端隐藏菜单只是体验，接口权限（hasAuthority）才是真正的防线
4. 菜单树组装用两次遍历：先建节点 Map，再挂父子关系，避免递归 O(n²)
5. 路由守卫配合：前端根据权限表动态注册路由，无权限路由不注册
6. 按钮级权限用 v-permission 指令或自定义判断，控制「删除」「导出」等操作入口
```

## 数据权限

菜单权限控制「能不能进页面」，数据权限控制「进了页面能看到哪些数据行」。典型场景：销售只能看自己的订单，部门经理看本部门订单，老板看全部订单。数据权限挂在角色上（sys_role.data_scope），同一角色的用户共享同一数据范围。

```text
数据范围分级：
1. 全部数据 —— data_scope=3，管理员/老板，不加任何过滤条件
2. 本部门及以下 —— data_scope=4，部门经理，按 dept_id 递归查子部门
3. 本部门数据 —— data_scope=2，按 dept_id 过滤
4. 仅本人数据 —— data_scope=1，按 create_by 过滤
5. 自定义 —— data_scope=5，按角色配置的部门/用户集合过滤
6. 数据权限是行级控制，与接口权限（列级/操作级）正交，两者叠加生效
```

实现方案：注解 + AOP + 动态 SQL。定义 @DataScope 注解标记需要数据权限的方法，AOP 切面读取当前用户角色的 data_scope，拼装过滤条件放入 ThreadLocal，Mapper 的 SQL 中引用：

```java
package com.example.security.datascope;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

/** 标注需要数据权限过滤的方法，deptAlias/userAlias 指定 SQL 中表的别名 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface DataScope {
    String deptAlias() default "d";  // 部门表别名
    String userAlias() default "u";  // 用户表/创建人字段别名
}
```

```java
package com.example.security.datascope;

import org.aspectj.lang.JoinPoint;
import org.aspectj.lang.annotation.Aspect;
import org.aspectj.lang.annotation.Before;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class DataScopeAspect {

    @Before("@annotation(dataScope)")
    public void doBefore(JoinPoint point, DataScope dataScope) {
        // 从 SecurityContext 取当前登录用户及其角色
        LoginUser loginUser = SecurityUtils.getLoginUser();
        Integer scope = loginUser.getRole().getDataScope();
        Long deptId = loginUser.getDeptId();
        Long userId = loginUser.getUserId();

        StringBuilder condition = new StringBuilder();
        if (scope == 1) {
            // 仅本人：create_by = 当前用户
            condition.append(" AND ").append(dataScope.userAlias())
                    .append(".create_by = ").append(userId);
        } else if (scope == 2) {
            // 本部门：dept_id = 当前用户部门
            condition.append(" AND ").append(dataScope.deptAlias())
                    .append(".dept_id = ").append(deptId);
        } else if (scope == 4) {
            // 本部门及以下：dept_id IN (子部门集合)，用递归查询或冗余 path 字段
            condition.append(" AND ").append(dataScope.deptAlias())
                    .append(".dept_id IN (").append(deptService.getChildDeptIds(deptId)).append(")");
        }
        // scope == 3（全部）不加条件
        DataScopeContext.set(condition.toString());
    }
}
```

Mapper 的 SQL 使用 ${dataScope} 动态拼接（注意：条件内容是程序生成的受控字符串，不是用户输入，可安全使用 ${}）：

```xml
<select id="selectOrderPage" resultType="Order">
    SELECT o.id, o.order_no, o.amount, o.create_by
    FROM order o
    JOIN sys_user u ON u.id = o.create_by
    JOIN sys_dept d ON d.id = u.dept_id
    <where>
        <if test="orderNo != null and orderNo != ''">
            AND o.order_no LIKE CONCAT('%', #{orderNo}, '%')
        </if>
        ${dataScope}
    </where>
    ORDER BY o.create_time DESC
</select>
```

```text
数据权限要点：
1. 数据范围挂在角色上，五档分级：本人、本部门、本部门及以下、全部、自定义
2. 注解 + AOP + ThreadLocal 是主流实现：切面拼条件，Mapper 动态拼接
3. 动态 SQL 用 ${} 拼接时必须保证内容是程序生成的受控字符串，严禁拼接用户输入
4. 部门及以下用递归查询或维护 dept path 冗余字段（如 /1/2/3/），避免递归性能问题
5. 数据权限条件必须默认生效，漏配 = 数据越权，需要审计与测试覆盖
6. 行级数据权限与接口权限正交，接口无权限时数据权限条件不执行
```

## 权限设计

权限设计是安全体系的顶层规划，核心原则是「认证与授权分离、权限粒度适中、权限数据缓存加速」。

认证与授权分离：认证（Authentication）确认「你是谁」，由 18.1/18.2 的 JWT + Spring Security 解决；授权（Authorization）确认「你能干什么」，由 RBAC 模型提供数据、Security 表达式执行判断。两者独立演进：认证方式换了（JWT 换 OAuth2），授权模型不受影响；角色调整了，认证流程不动。

权限粒度设计：粒度过粗（只有管理员/普通用户两级）导致权限无法细分，业务增长后被迫「给普通用户开管理员权限」；粒度过细（每个按钮一个权限、甚至每个数据字段一个权限）导致配置工作量爆炸、性能下降。业界通行做法：接口级用 模块:操作 权限字符串，按钮级与接口级对齐，数据级用数据范围控制，不做到字段级。

```text
权限设计原则：
1. 认证与授权分离 —— JWT 管认证，RBAC + Security 管授权，互不耦合
2. 权限粒度适中 —— 模块:操作 两级命名（order:list、order:delete），不做到字段级
3. 角色收敛 —— 角色数量控制在两位数以内，避免「一人一角色」退化为直接授权
4. 权限缓存 —— 用户权限集缓存 Redis，TTL 30 分钟，角色变更时主动失效
5. 最小权限 —— 默认无权限，按需授予；新用户只给基础角色
6. 权限审计 —— 角色变更、权限分配记录日志，关键操作可追溯
```

权限缓存实现（避免每次请求都三级联查数据库）：

```java
package com.example.security.service;

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

import java.util.Set;
import java.util.concurrent.TimeUnit;

@Service
public class PermissionCacheService {

    private final StringRedisTemplate redisTemplate;
    private final PermissionMapper permissionMapper;

    public PermissionCacheService(StringRedisTemplate redisTemplate,
                                  PermissionMapper permissionMapper) {
        this.redisTemplate = redisTemplate;
        this.permissionMapper = permissionMapper;
    }

    /** 获取用户权限集，优先读缓存，未命中查库并回填 */
    public Set<String> getUserPermCodes(Long userId) {
        String key = "perm:user:" + userId;
        Set<String> cached = redisTemplate.opsForSet().members(key);
        if (cached != null && !cached.isEmpty()) {
            return cached;
        }
        Set<String> codes = permissionMapper.selectPermCodesByUserId(userId); // 三级联查
        if (codes != null && !codes.isEmpty()) {
            redisTemplate.opsForSet().add(key, codes.toArray(new String[0]));
            redisTemplate.expire(key, 30, TimeUnit.MINUTES);
        }
        return codes;
    }

    /** 角色变更/用户改角色后主动失效缓存，保证权限立即生效 */
    public void evictUserPerms(Long userId) {
        redisTemplate.delete("perm:user:" + userId);
    }
}
```

与 Spring Security 的对接：JWT 过滤器验签后，从缓存加载权限并写入 SecurityContext 的 GrantedAuthority，让 hasAuthority 表达式直接可用：

```java
// JwtAuthenticationFilter 中的权限装配（简版）
Set<String> permCodes = permissionCacheService.getUserPermCodes(userId);
List<GrantedAuthority> authorities = new ArrayList<>();
authorities.add(new SimpleGrantedAuthority("ROLE_" + role));
permCodes.forEach(code -> authorities.add(new SimpleGrantedAuthority(code)));
// 写入 SecurityContext，hasAuthority('order:delete') 即可生效
```

```text
权限设计要点：
1. 认证授权分离，各司其职；JWT 过期策略调整不影响授权模型
2. 权限字符串两级命名 模块:操作，保持粒度可控、配置可维护
3. 用户权限集缓存 Redis 减少查库压力，角色变更主动失效保证实时性
4. 默认最小权限，权限按需授予；接口兜底 authenticated 防漏配
5. 角色变更、权限分配全程审计日志，便于安全回溯
6. 权限模型是数据层支撑，最终由 Spring Security 表达式执行判断
```

## 应用场景实战

### 场景一：动态菜单 + 按钮权限的管理端接入

完整链路：用户登录管理端 → 后台返回 token 与用户信息 → 前端拉取菜单树渲染侧边栏 → 进入页面后按钮按权限显隐。后台提供两个接口：

```java
package com.example.controller;

import com.example.security.service.PermissionCacheService;
import com.example.service.MenuService;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import java.util.List;
import java.util.Map;
import java.util.Set;

@RestController
@RequestMapping("/api/menu")
public class MenuController {

    private final MenuService menuService;
    private final PermissionCacheService permissionCacheService;

    public MenuController(MenuService menuService, PermissionCacheService permissionCacheService) {
        this.menuService = menuService;
        this.permissionCacheService = permissionCacheService;
    }

    /** 当前用户的菜单树，前端侧边栏渲染 */
    @GetMapping("/tree")
    public List<Map<String, Object>> tree() {
        Long userId = (Long) SecurityContextHolder.getContext().getAuthentication().getPrincipal();
        return menuService.getUserMenuTree(userId);
    }

    /** 当前用户的全部权限字符串，前端用于按钮级控制 */
    @GetMapping("/perms")
    public Set<String> perms() {
        Long userId = (Long) SecurityContextHolder.getContext().getAuthentication().getPrincipal();
        return permissionCacheService.getUserPermCodes(userId);
    }
}
```

前端按钮权限指令（Vue3 自定义指令）：

后端接口再用 @PreAuthorize 双重保护（前端隐藏 + 后端拦截）：

```java
@DeleteMapping("/api/order/{id}")
@PreAuthorize("hasAuthority('order:delete')")
public void delete(@PathVariable Long id) {
    // 删除逻辑
}
```

### 场景二：订单查询的数据权限控制

给订单分页查询加上数据权限：销售只看本人订单，主管看本部门订单，管理员看全部。实现三步：Service 方法标注 @DataScope、AOP 切面拼条件（上文已实现）、Mapper SQL 引用条件。

```java
package com.example.service;

import com.example.security.datascope.DataScope;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class OrderQueryService {

    private final OrderMapper orderMapper;

    public OrderQueryService(OrderMapper orderMapper) {
        this.orderMapper = orderMapper;
    }

    /** 分页查询订单：AOP 自动按当前用户角色拼接数据范围条件 */
    @DataScope(deptAlias = "d", userAlias = "u")
    public List<Order> pageOrders(OrderQuery query) {
        // 从 ThreadLocal 取 AOP 拼接的 dataScope 条件，传给 Mapper
        query.setDataScope(DataScopeContext.get());
        return orderMapper.selectOrderPage(query);
    }
}
```

数据范围配置与验证：

```text
验证用例：
1. 普通销售（data_scope=1）：SQL 追加 AND u.create_by = 1001，只能查到自己的订单
2. 部门主管（data_scope=2）：SQL 追加 AND d.dept_id = 10，查到本部门所有订单
3. 部门经理（data_scope=4）：SQL 追加 AND d.dept_id IN (10,11,12)，含子部门
4. 管理员（data_scope=3）：不追加条件，查到全部订单
5. 接口层再叠加 @PreAuthorize：无 order:list 权限直接 403
6. 数据权限条件与业务条件（订单号、状态）用 AND 连接，互不干扰
```

该场景的关键点：数据权限是「查询时动态生效」的，同一份 Mapper SQL 被不同角色调用时自动附加不同条件，无需为每个角色写一套查询。权限配置在管理端角色页面调整后，用户下次请求即生效（配合缓存失效）。

## 最佳实践与踩坑记录

### 最佳实践

1. 权限命名统一 模块:操作（order:list、order:delete、user:resetPwd），在权限表唯一约束，命名规范写进团队约定，避免「orderList」「deleteOrder」混乱
2. 角色数量收敛：角色是权限的「模板」，控制在两位数以内；用户多角色取权限并集，避免「一人一角色」退化
3. 认证与授权严格分离：JWT 只放 uid/role 等身份声明，权限判断一律实时查权限缓存，不信任 token 内的权限快照
4. 菜单与按钮共用权限表，但查询接口分开：菜单树查 type=1，按钮权限查全部 perm_code，前端与后端各取所需
5. 用户权限缓存 Redis 并设置 TTL（30 分钟），角色变更、分配权限时主动失效，兼顾性能与实时性
6. 数据权限条件用注解 + AOP 统一生成，SQL 中 ${} 拼接的必须是程序生成的受控字符串，禁止任何用户输入直接进入
7. 部门及以下的数据范围用 dept path 冗余字段（/1/2/3/）或递归缓存，避免频繁递归查询拖垮数据库
8. 权限变更全程审计：谁在什么时间给谁加了什么权限，写操作日志表，安全事件可追溯

### 踩坑记录

```text
坑 1：用户直接挂权限，绕过角色，RBAC 退化成 ACL
结论：系统里出现「给张三单独加了 order:export 权限」的需求，权限表与用户直接关联。
原因：前期图省事把权限直接授予用户，角色形同虚设，权限配置爆炸且无法批量管理。
解法：坚持三层模型，需求归并到角色：建「导出专员」角色，把用户挂到角色下。

坑 2：权限字符串命名不统一，hasAuthority 永远匹配不上
结论：权限表存 order:delete，代码里写 hasAuthority('orderDelete')，接口一直 403。
原因：命名规范未统一，表数据与代码约定各写各的。
解法：统一 模块:操作 命名规范并唯一约束；新增权限走管理端配置，代码引用前先核对。

坑 3：hasRole 与 hasAuthority 混用，ROLE_ 前缀导致判断失效
结论：角色判断用 hasRole，权限判断用 hasAuthority，但权限数据里既有 ROLE_ADMIN 又有 ADMIN，部分判断失效。
原因：hasRole 自动补 ROLE_ 前缀，hasAuthority 不补，两套数据混在一起语义混乱。
解法：角色与权限分离存储：角色只放 sys_role（hasRole 用），权限只放 sys_permission（hasAuthority 用），互不混写。

坑 4：权限缓存不失效，改了角色权限用户端不生效
结论：管理员给用户加了新权限，用户刷新页面还是没有。
原因：用户权限集缓存了 Redis 且未设置失效机制，查库结果被缓存挡住。
解法：缓存设置 TTL；角色变更、用户角色调整接口主动调用 evictUserPerms 清缓存。

坑 5：数据权限条件拼接了用户输入，引发 SQL 注入
结论：数据权限的过滤条件如果直接用请求参数拼 SQL，攻击者可注入恶意条件。
原因：${} 直接拼接了未校验的用户输入（如部门 ID 字符串）。
解法：数据权限条件只由 AOP 根据 data_scope 与登录用户信息生成，参数化查询用 #{}，${} 仅限程序生成的受控字符串。

坑 6：菜单权限只做前端隐藏，接口没拦，越权访问成功
结论：前端没有「删除」按钮，但直接调接口还是能删。
原因：菜单/按钮隐藏只是前端体验，接口层没有对应的权限校验。
解法：每个敏感接口加 @PreAuthorize 或 URL 规则；前端隐藏与后端拦截必须成对出现。

坑 7：部门数据权限用递归查子部门，数据量大时接口超时
结论：本部门及以下的范围查询，每次请求递归查部门树，部门上千时明显变慢。
原因：递归查询每层一次数据库访问，层级深、部门多时开销巨大。
解法：部门表维护 path 冗余字段（/1/2/3/），用 LIKE 'path%' 一次查出所有子部门；或把部门树缓存到 Redis。

坑 8：数据权限条件在事务外的查询生效，关联查询漏加条件导致越权
结论：列表页数据权限正常，但详情页、导出、统计接口能看到全部数据。
原因：只给主查询方法加了 @DataScope，详情、导出、统计等关联查询遗漏。
解法：所有涉及数据行的查询方法统一标注 @DataScope；测试用例覆盖「不同角色查同一数据」的矩阵。
```
