## 概述

JWT（JSON Web Token）是一种基于 JSON 的开放标准（RFC 7519）令牌格式，用于在客户端与服务端之间安全地传递身份与授权信息。在小程序全栈架构中，JWT 承担登录态的载体：用户通过 wx.login 获取 code，后台用 code 换取 openid 并签发 JWT，小程序后续请求在 Authorization 头携带 token，后台验签通过即确认身份，无需服务端保存 session。

JWT 的核心价值是「自包含 + 无状态」：身份信息、角色、过期时间全部编码在 token 里，任何一台服务节点都能独立验签，天然适配分布式部署。代价是 token 在过期前难以主动吊销，因此生产实践普遍采用「短效 access token + 长效 refresh token」的双 token 模型。

```text
JWT 认证的核心特征：
1. 三段结构 —— Header.Payload.Signature，base64url 编码，点号分隔
2. 自包含 —— 用户身份、角色、过期时间等声明直接编码在 token 内
3. 无状态 —— 服务端不存 session，验签通过即信任，天然适合分布式
4. 签名防篡改 —— HS256/RS256 保证 payload 任何改动都会验签失败
5. 有效期可控 —— 过期时间由签发方声明，客户端无法自行延长
6. 双 token 模型 —— access token 短效 + refresh token 长效，兼顾安全与体验
```

## JWT 原理

JWT 由三部分组成，用点号（.）连接，形如 `eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMDAxIn0.9nQq2s7QvM...`。三段分别是 Header、Payload、Signature，每一段都是 base64url 编码后的字符串。

Header 是 JSON 对象，声明令牌类型与签名算法：

```json
{"alg": "HS256", "typ": "JWT"}
```

Payload 是 claims（声明）集合，既包含标准注册声明，也可以携带自定义声明：

```json
{
  "sub": "1001",
  "uid": 1001,
  "role": "admin",
  "iss": "weapp-backend",
  "iat": 1724133600,
  "exp": 1724140800
}
```

各声明含义：sub（subject）标识主体，通常放用户 ID 或用户名；iss（issuer）标识签发方；iat（issued at）签发时间；exp（expiration time）过期时间，验签时服务端会强制校验 exp 早于当前时间则拒绝。自定义声明如 uid、role 由业务自行定义，放在 payload 中随 token 一起传递。

Signature 是对前两段的签名：`HMACSHA256(base64url(Header) + "." + base64url(Payload), secret)`。服务端用同一把密钥对前两段重新计算签名，与第三段比对，一致才认为 token 未被篡改、确实由自己签发。签名覆盖完整的前两段编码串，所以 payload 中任意一位字符被修改，签名都会对不上。

base64url 编码与标准 base64 的区别：把 `+` 换成 `-`、`/` 换成 `_`，并去掉末尾的 `=` 填充，保证编码结果可以直接放进 URL、请求头而不被转义。需要特别强调的是，base64url 只是编码不是加密，Payload 里的内容任何人拿到 token 都能解码查看，因此敏感信息绝不能放进 payload。

签名算法选型上，HS256（HMAC-SHA256）用同一把对称密钥签名和验签，实现简单、性能好，适合单服务端或自建网关的封闭体系；RS256（RSA-SHA256）用私钥签名、公钥验签，适合多服务端共享验证、或需要第三方校验 token 的场景，代价是要维护密钥对且签名更长、计算更慢。小程序全栈项目后台是自家 SpringBoot，HS256 是默认选择。

```text
JWT 原理要点：
1. Header 声明算法，Payload 存声明，Signature 防篡改
2. base64url 是编码不是加密，payload 可被任何人解码读取
3. HS256 对称密钥，签名验签同一把 key；RS256 非对称，私钥签公钥验
4. exp、iat、sub、iss 是标准注册声明，业务声明自定义放 payload
5. 自定义声明只能放非敏感信息（uid、role），密码类数据禁止入 token
6. 签名覆盖 header 与 payload 的完整编码串，任何一位改动都会验签失败
```

## 签发与验证

Java 生态最常用的 JWT 库是 jjwt（io.jsonwebtoken）。0.11.x 版本拆分为 api、impl、jackson 三个模块，api 提供编译期 API，impl 与 jackson 是运行时实现，后者负责把 claims 序列化/反序列化为 JSON：

```xml
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-api</artifactId>
    <version>0.11.5</version>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-impl</artifactId>
    <version>0.11.5</version>
    <scope>runtime</scope>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-jackson</artifactId>
    <version>0.11.5</version>
    <scope>runtime</scope>
</dependency>
```

签发 token 的过程是：组装 claims、设置签发时间与过期时间、选择签名算法、调用 compact() 输出最终的 token 字符串。以 HS256 为例，完整的工具类：

```java
package com.example.security.jwt;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.SignatureAlgorithm;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import javax.crypto.SecretKey;
import java.nio.charset.StandardCharsets;
import java.util.Date;
import java.util.HashMap;
import java.util.Map;

@Component
public class JwtUtil {

    private final SecretKey key;
    private final long accessExpireMs;
    private final long refreshExpireMs;

    public JwtUtil(@Value("${jwt.secret}") String secret,
                   @Value("${jwt.access-expire-ms:7200000}") long accessExpireMs,
                   @Value("${jwt.refresh-expire-ms:604800000}") long refreshExpireMs) {
        // HS256 要求密钥至少 256 bit（32 字节），否则抛 WeakKeyException
        this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
        this.accessExpireMs = accessExpireMs;
        this.refreshExpireMs = refreshExpireMs;
    }

    /** 签发 access token：携带 uid、role 等业务声明 */
    public String createAccessToken(Long userId, String username, String role) {
        Map<String, Object> claims = new HashMap<>();
        claims.put("uid", userId);
        claims.put("role", role);
        return Jwts.builder()
                .setClaims(claims)
                .setSubject(username)
                .setIssuer("weapp-backend")
                .setIssuedAt(new Date())
                .setExpiration(new Date(System.currentTimeMillis() + accessExpireMs))
                .signWith(key, SignatureAlgorithm.HS256)
                .compact();
    }

    /** 签发 refresh token：只放 userId，不携带业务声明 */
    public String createRefreshToken(Long userId) {
        return Jwts.builder()
                .setSubject(String.valueOf(userId))
                .setIssuer("weapp-backend")
                .setIssuedAt(new Date())
                .setExpiration(new Date(System.currentTimeMillis() + refreshExpireMs))
                .signWith(key, SignatureAlgorithm.HS256)
                .compact();
    }

    /** 解析并验证 token，返回 claims；签名错误或过期抛 JwtException */
    public Claims parseToken(String token) {
        return Jwts.parserBuilder()
                .setSigningKey(key)
                .build()
                .parseClaimsJws(token)
                .getBody();
    }
}
```

对应的配置放入 application.yml，生产环境密钥通过环境变量注入：

```yaml
jwt:
  # 生产环境必须用环境变量/配置中心注入，禁止写死在代码里
  secret: "weapp-backend-jwt-secret-key-32bytes-minimum!!"
  access-expire-ms: 7200000      # access token 有效期 2 小时
  refresh-expire-ms: 604800000   # refresh token 有效期 7 天
```

验证 token 是一步完成的：用同一密钥重建解析器，parseClaimsJws 内部会同时校验签名合法性、exp 是否过期、以及结构是否完整。任何篡改、过期、格式非法都会抛出对应异常，业务侧统一捕获并按类型处理：

```java
try {
    Claims claims = jwtUtil.parseToken(token);
    Long userId = claims.get("uid", Long.class);
    String role = claims.get("role", String.class);
    // 验签通过：把身份写入请求上下文，业务接口直接使用
} catch (ExpiredJwtException e) {
    // token 过期：返回 401，提示客户端用 refresh token 刷新
} catch (JwtException e) {
    // 签名错误 / 格式非法：一律拒绝访问，防止伪造 token
}
```

```text
签发与验证要点：
1. jjwt 0.11.x 需引入 api/impl/jackson 三个依赖，impl 与 jackson 用 runtime scope
2. HS256 密钥必须不少于 32 字节，否则签发时抛 WeakKeyException
3. Jwts.builder 先 setClaims 再 signWith 最后 compact，顺序不可颠倒
4. parserBuilder().setSigningKey(key).build().parseClaimsJws(token) 一步完成验签与过期校验
5. 过期抛 ExpiredJwtException，篡改抛 SignatureException，需区分处理
6. 旧版直接 new JwtParser() 的写法已废弃，必须使用 builder 模式
```

## 无状态认证

传统 Session 认证的流程是：用户登录后服务端把会话信息存在内存或 Redis，返回一个随机 sessionId 给客户端，客户端后续请求携带 Cookie，服务端按 sessionId 反查会话。这套机制的问题在于服务端必须保存状态，多实例部署时要么做 session 黏滞，要么把 session 抽到共享存储，扩容与故障转移都比较麻烦。

JWT 无状态认证则完全不同：服务端不保存任何会话数据，token 本身自带身份信息。请求链路是：客户端登录拿到 token，后续每个请求在请求头携带 `Authorization: Bearer <token>`，服务端验签通过后直接从 claims 中取 userId、role 使用，全程不查 session、不查库。

```text
无状态认证流程：
1. 小程序 wx.login 拿 code，调后台 /api/auth/login 换取 token
2. 后台 code2session 换 openid，查用户表，签发 access token + refresh token
3. 小程序把 token 存本地 storage，后续请求统一带 Authorization: Bearer <token>
4. 后台过滤器/拦截器验签，通过则把 userId、role 写入请求上下文
5. 业务接口从上下文取当前用户，无需再查库确认身份
6. 分布式部署天然支持：任何节点都能独立验签，无需 session 同步
```

小程序端把 token 附加逻辑统一封装在请求工具里，业务代码无感知：

```javascript
// utils/request.js
const BASE_URL = 'https://api.example.com';

const request = (options) => {
  return new Promise((resolve, reject) => {
    wx.request({
      url: BASE_URL + options.url,
      method: options.method || 'GET',
      data: options.data || {},
      header: {
        'Content-Type': 'application/json',
        'Authorization': 'Bearer ' + wx.getStorageSync('accessToken')
      },
      success(res) {
        if (res.statusCode === 401) {
          // token 过期：尝试用 refresh token 刷新，成功后重放原请求
          refreshToken().then(() => {
            resolve(request(options));
          }).catch(() => {
            wx.removeStorageSync('accessToken');
            wx.removeStorageSync('refreshToken');
            wx.reLaunch({ url: '/pages/login/login' });
          });
          return;
        }
        resolve(res.data);
      },
      fail: reject
    });
  });
};

module.exports = request;
```

无状态并不是零成本。token 一旦签发，在过期之前无法被服务端主动作废，这是「无状态」与「可吊销」之间的根本矛盾。实际项目中用「短效 access + 长效 refresh + Redis 黑名单/吊销记录」来平衡：access 短效控制泄露窗口，refresh 可吊销保证封号、改密等场景能立即切断登录态。

```text
无状态认证要点：
1. 服务端零 session，验签通过即信任，天然支持水平扩容
2. token 通过 Authorization: Bearer 头传递而非 Cookie，规避 CSRF 风险
3. 小程序端统一在请求封装里附加 token，401 统一走刷新流程
4. 无状态意味着 token 过期前难以主动吊销，需黑名单机制兜底
5. 改密、封号等敏感操作后应让旧 token 立即失效，不能只靠过期
6. 无状态认证适合小程序 API 场景，浏览器场景还需防范 XSS 窃取 token
```

## token 刷新

access token 有效期短（分钟到小时级），把泄露后被冒用的窗口压到最小；refresh token 有效期长（天到周级），专门用来换取新的 access token，让用户在不重新输密码的前提下持续保持登录。两者分工不同，缺一不可。

```text
双 token 刷新流程：
1. 登录成功：签发 access token（2 小时）+ refresh token（7 天），refresh 落 Redis
2. 小程序正常请求：带 access token，有效期内一直可用
3. access 过期：后台返回 401，小程序携带 refresh token 调 /api/auth/refresh
4. 后台校验 refresh 签名、过期时间、与 Redis 中记录一致，通过则签发新 access
5. 小程序用新 access token 重放刚才失败的请求
6. refresh 也过期或已被吊销：返回 401，小程序清除 token 跳登录页
```

刷新接口的实现要点：refresh token 签发时落 Redis（key 关联 userId），刷新时必须与 Redis 中保存的值完全一致才放行，这样注销接口只要删除 Redis 记录，对应的 refresh token 立即失效：

```java
package com.example.controller;

import com.example.security.jwt.JwtUtil;
import io.jsonwebtoken.Claims;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.web.bind.annotation.*;

import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.TimeUnit;

@RestController
@RequestMapping("/api/auth")
public class AuthController {

    private final JwtUtil jwtUtil;
    private final StringRedisTemplate redisTemplate;

    public AuthController(JwtUtil jwtUtil, StringRedisTemplate redisTemplate) {
        this.jwtUtil = jwtUtil;
        this.redisTemplate = redisTemplate;
    }

    /** 登录成功签发双 token，refresh token 落 Redis 便于吊销与比对 */
    @PostMapping("/login")
    public Map<String, Object> login(@RequestBody Map<String, String> body) {
        // 此处简化：真实项目先走 18.2 的 AuthenticationManager 完成密码校验
        String username = body.get("username");
        Long userId = 1001L;
        String role = "admin";

        String accessToken = jwtUtil.createAccessToken(userId, username, role);
        String refreshToken = jwtUtil.createRefreshToken(userId);
        // Redis 记录 refresh token，TTL 与 refresh 有效期一致
        redisTemplate.opsForValue().set(
                "auth:refresh:" + userId, refreshToken, 7, TimeUnit.DAYS);

        Map<String, Object> data = new HashMap<>();
        data.put("accessToken", accessToken);
        data.put("refreshToken", refreshToken);
        data.put("expiresIn", 7200);
        return data;
    }

    /** 刷新接口：校验 refresh token 后签发新的 access token */
    @PostMapping("/refresh")
    public Map<String, Object> refresh(@RequestBody Map<String, String> body) {
        String refreshToken = body.get("refreshToken");
        Claims claims;
        try {
            claims = jwtUtil.parseToken(refreshToken);
        } catch (Exception e) {
            throw new RuntimeException("refresh token 无效或已过期");
        }
        Long userId = Long.valueOf(claims.getSubject());
        String stored = redisTemplate.opsForValue().get("auth:refresh:" + userId);
        if (stored == null || !stored.equals(refreshToken)) {
            // 与 Redis 记录不一致：说明已被吊销或被人重放，强制重新登录
            throw new RuntimeException("refresh token 已被吊销，请重新登录");
        }
        String username = claims.getSubject();
        String role = claims.get("role", String.class);
        String newAccess = jwtUtil.createAccessToken(userId, username, role);
        Map<String, Object> data = new HashMap<>();
        data.put("accessToken", newAccess);
        data.put("expiresIn", 7200);
        return data;
    }

    /** 注销：删除 Redis 中的 refresh token，access 靠短过期自然失效 */
    @PostMapping("/logout")
    public Map<String, Object> logout(@RequestHeader(value = "Authorization", required = false) String auth) {
        if (auth != null && auth.startsWith("Bearer ")) {
            Claims claims = jwtUtil.parseToken(auth.substring(7));
            Long userId = claims.get("uid", Long.class);
            redisTemplate.delete("auth:refresh:" + userId);
        }
        Map<String, Object> data = new HashMap<>();
        data.put("msg", "已注销");
        return data;
    }
}
```

安全要求更高的系统会做 refresh token 轮换：每次刷新不仅签发新 access，还同时签发新 refresh 并删除旧 refresh，即使旧 refresh 被窃取也只能用一次，把重放风险降到最低。轮换的代价是客户端需要同步更新本地存储的两个 token。

```text
token 刷新要点：
1. access 短效（分钟~小时）控制泄露风险，refresh 长效（天~周）保证体验
2. refresh token 必须落 Redis，刷新时逐字比对，吊销时直接删除
3. 刷新接口返回新 access，必要时同时轮换 refresh，旧 refresh 立即作废
4. 小程序端 401 后自动刷新并重放原请求，用户全程无感知
5. 刷新也失败才跳登录页，避免用户频繁重新登录
6. refresh token 泄露危害更大，传输必须走 HTTPS，存储于小程序 storage
```

## 安全注意

JWT 的安全边界由密钥、过期时间与吊销机制三者共同决定。密钥是整套体系的地基：HS256 下拿到密钥就等于拿到签发任意身份 token 的能力，因此密钥管理是第一优先级。过期时间是风险窗口的控制旋钮，需要结合业务对体验与安全的取舍来调节。吊销机制解决无状态认证「无法主动失效」的短板。

```text
JWT 安全注意：
1. 密钥必须不少于 32 字节且随机生成，生产环境用环境变量/配置中心注入
2. 密钥严禁写进代码、Git 仓库、前端代码；泄露等于所有 token 可被伪造
3. 密钥轮换：签发时携带 kid（key id），验证时按 kid 选择对应密钥
4. Payload 只放非敏感声明（uid、role），绝不放密码、手机号、身份证号
5. 过期时间权衡：太短频繁刷新体验差，太长泄露风险大，access 一般 15 分钟到 2 小时
6. 注销方案：access 靠短过期自然失效，refresh 走 Redis 删除，重要场景加黑名单
```

黑名单机制：签发 token 时设置 jti（唯一 ID），注销时把 jti 写入 Redis 黑名单，TTL 设为 token 剩余有效期，验证时先查黑名单再验签，实现单点吊销：

```java
/** 注销 access token：把 jti 加入黑名单，TTL 设为剩余有效期 */
public void revokeAccessToken(String token) {
    Claims claims = jwtUtil.parseToken(token);
    String jti = claims.getId();
    long remainMs = claims.getExpiration().getTime() - System.currentTimeMillis();
    if (remainMs > 0) {
        redisTemplate.opsForValue().set(
                "auth:blacklist:" + jti, "1", remainMs, TimeUnit.MILLISECONDS);
    }
}

/** 验证前检查黑名单 */
public boolean isBlacklisted(String token) {
    Claims claims = jwtUtil.parseToken(token);
    return Boolean.TRUE.equals(
            redisTemplate.hasKey("auth:blacklist:" + claims.getId()));
}
```

```text
安全注意要点：
1. 密钥即一切：HS256 下拿到密钥就能伪造任意身份的 token
2. 签发时设置 jti（唯一 ID），黑名单按 jti 吊销单个 token
3. 登录、改密、封号等事件要能立即让旧 token 失效，不能只靠过期
4. 小程序端 token 存 storage，注意别被异常上报、日志、分享链路带出
5. 服务端统一异常处理，把 JWT 异常映射为 401，不向客户端泄露内部细节
6. 所有携带 token 的请求必须走 HTTPS，防止中间人截获与重放
```

## 应用场景实战

### 场景一：登录签发 + 拦截器验签的完整链路

先用拦截器实现全局限流外的认证拦截。拦截器适合只做「验签 + 放行」的轻量场景，与 Spring MVC 天然集成，注册简单：

```java
package com.example.security.interceptor;

import com.example.security.jwt.JwtUtil;
import io.jsonwebtoken.Claims;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;

import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;

@Component
public class JwtAuthInterceptor implements HandlerInterceptor {

    private final JwtUtil jwtUtil;

    public JwtAuthInterceptor(JwtUtil jwtUtil) {
        this.jwtUtil = jwtUtil;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws Exception {
        if ("OPTIONS".equalsIgnoreCase(request.getMethod())) {
            return true; // 放行 CORS 预检请求
        }
        String auth = request.getHeader("Authorization");
        if (auth == null || !auth.startsWith("Bearer ")) {
            return unauthorized(response, "未携带 token");
        }
        try {
            Claims claims = jwtUtil.parseToken(auth.substring(7));
            request.setAttribute("userId", claims.get("uid"));
            request.setAttribute("role", claims.get("role"));
            return true;
        } catch (Exception e) {
            return unauthorized(response, "token 无效或已过期");
        }
    }

    private boolean unauthorized(HttpServletResponse response, String msg) throws Exception {
        response.setStatus(401);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"code\":401,\"msg\":\"" + msg + "\"}");
        return false;
    }
}
```

注册拦截器并配置放行路径，登录、刷新、公开接口不拦截：

```java
package com.example.config;

import com.example.security.interceptor.JwtAuthInterceptor;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class WebConfig implements WebMvcConfigurer {

    private final JwtAuthInterceptor jwtAuthInterceptor;

    public WebConfig(JwtAuthInterceptor jwtAuthInterceptor) {
        this.jwtAuthInterceptor = jwtAuthInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(jwtAuthInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns(
                        "/api/auth/login",
                        "/api/auth/refresh",
                        "/api/public/**");
    }
}
```

业务接口从请求属性中取当前用户，无需再解析 token：

```java
@RestController
@RequestMapping("/api/user")
public class UserController {

    @GetMapping("/profile")
    public Map<String, Object> profile(HttpServletRequest request) {
        Long userId = (Long) request.getAttribute("userId");
        String role = (String) request.getAttribute("role");
        // 按 userId 查库返回用户信息，此处省略 Mapper 调用
        Map<String, Object> data = new HashMap<>();
        data.put("userId", userId);
        data.put("role", role);
        return data;
    }
}
```

### 场景二：双 token 刷新 + 小程序端自动续期

小程序端把登录与刷新封装成独立模块，请求工具在 401 时自动续期并重放原请求，用户无感知：

```javascript
// utils/auth.js
const BASE_URL = 'https://api.example.com';

// 登录：wx.login 拿 code，后台换 token
const login = () => {
  return new Promise((resolve, reject) => {
    wx.login({
      success: (res) => {
        wx.request({
          url: BASE_URL + '/api/auth/login',
          method: 'POST',
          data: { code: res.code },
          success: (r) => {
            wx.setStorageSync('accessToken', r.data.accessToken);
            wx.setStorageSync('refreshToken', r.data.refreshToken);
            resolve(r.data);
          },
          fail: reject
        });
      },
      fail: reject
    });
  });
};

// 刷新：用 refresh token 换新的 access token
const refreshToken = () => {
  return new Promise((resolve, reject) => {
    const refreshToken = wx.getStorageSync('refreshToken');
    if (!refreshToken) {
      reject(new Error('no refresh token'));
      return;
    }
    wx.request({
      url: BASE_URL + '/api/auth/refresh',
      method: 'POST',
      data: { refreshToken },
      success: (r) => {
        wx.setStorageSync('accessToken', r.data.accessToken);
        resolve(r.data);
      },
      fail: reject
    });
  });
};

// 退出登录：通知后台吊销 refresh token，并清理本地
const logout = () => {
  return request({
    url: '/api/auth/logout',
    method: 'POST'
  }).finally(() => {
    wx.removeStorageSync('accessToken');
    wx.removeStorageSync('refreshToken');
    wx.reLaunch({ url: '/pages/login/login' });
  });
};

module.exports = { login, refreshToken, logout };
```

该场景的关键链路验证点：access token 过期后第一次请求返回 401，request.js 捕获后调用 refreshToken 换新 token，再递归重放原请求；若 refresh 也失效，则清理本地 token 跳转登录页。这里要注意防止并发请求同时触发多次刷新，实际项目可加一个「刷新中」标志位，多个 401 请求共享同一次刷新 Promise。

## 最佳实践与踩坑记录

### 最佳实践

1. 密钥长度严格按算法要求：HS256 必须不少于 32 字节，且用随机数生成，不要用「123456」这类弱口令，否则 jjwt 直接抛 WeakKeyException
2. 生产与开发使用不同密钥，通过环境变量注入；密钥轮换时给 token 加 kid 声明，验证时按 kid 选密钥，实现无感切换
3. access token 有效期按业务风险定：普通接口 2 小时，资金/管理类接口缩短到 15-30 分钟，并用 refresh token 机制兜底
4. refresh token 必须落 Redis 并与 userId 关联，注销接口删除即吊销；有条件就做 refresh 轮换，旧 refresh 用完即废
5. 小程序端把 token 附加、401 刷新、重放逻辑全部收敛到 request.js，业务代码不直接操作 token，避免漏带或重复实现
6. payload 只放 uid、role 这类非敏感且会频繁使用的声明，用户资料类数据请求时再查库，保证数据新鲜度
7. 服务端统一异常处理 JWT 异常：ExpiredJwtException 返回 401，其余 JwtException 返回 401，不暴露异常栈与内部信息
8. 所有鉴权相关接口（登录、刷新、注销）都要做限流，防止暴力撞库与 token 爆破

### 踩坑记录

```text
坑 1：HS256 密钥太短，启动或签发时报 WeakKeyException
结论：密钥少于 32 字节时 jjwt 拒绝工作，异常信息是 WeakKeyException: The specified key byte array is 16 bytes which is not secure enough。
原因：HS256 算法要求密钥至少 256 bit（32 字节），这是 jjwt 的安全底线。
解法：生成 32 字节以上的随机密钥，如 openssl rand -base64 48，通过环境变量注入。

坑 2：payload 里放了明文密码/手机号，token 泄露导致数据泄露
结论：token 泄露后攻击者 base64url 解码 payload 即可直接读取明文敏感字段。
原因：base64url 只是编码，任何人都能解码；开发者误以为「加密了」。
解法：payload 只放 uid、role 等非敏感声明；敏感数据一律服务端查库获取。

坑 3：无状态认证下封号/改密无法立即生效，旧 token 继续可用
结论：用户被封禁后，其未过期的 access token 仍能正常访问接口。
原因：服务端不保存会话，验签只看签名与过期时间，不感知账号状态。
解法：敏感操作校验账号状态；或用 Redis 黑名单按 jti 吊销，登录时维护 token 版本号。

坑 4：access token 有效期设 7 天，泄露后长时间可被冒用
结论：token 一旦被截获，攻击者在 7 天内都可以冒用该身份调用接口。
原因：有效期过长放大了泄露窗口，且无状态 token 难以提前作废。
解法：access 缩短到 2 小时以内，引入 refresh token 续期；敏感接口单独缩短。

坑 5：refresh token 只验签名不比对 Redis，注销形同虚设
结论：用户点击注销后，用旧 refresh token 仍能刷新出新的 access token。
原因：刷新接口只做了 JWT 验签，没有校验 Redis 中的吊销记录。
解法：签发时把 refresh 写入 Redis，刷新时逐字比对，注销时删除；比对不一致一律拒绝。

坑 6：token 里的角色/权限过期不更新，改权限后用户仍持有旧权限
结论：管理员调整用户角色后，用户旧 token 中的 role 声明仍是旧值，权限不生效。
原因：角色信息固化在 token 里，服务端验签不感知数据库的最新状态。
解法：权限判断不信任 token 内声明，每次请求从缓存/数据库读取最新权限；或缩短 access 有效期。

坑 7：小程序端多个 401 并发触发多次刷新，出现 token 覆盖竞态
结论：多个请求同时 401 时各自发起刷新，后一次刷新覆盖前一次，导致部分请求重放失败。
原因：刷新流程没有做并发控制，多个 Promise 同时执行。
解法：用一个标志位 + 共享 Promise 实现「刷新中只发一次，其余请求等待同一个 Promise」。

坑 8：JWT 库升级后旧代码编译不过，parser 与 builder 写法全变
结论：从 jjwt 0.9.x 升 0.11.x 后，new JwtParser()、setSigningKey 的用法全部废弃报错。
原因：0.11 起强制 builder 模式，并拆分了 api/impl/jackson 三个依赖。
解法：按 0.11 文档重写为 Jwts.builder() 与 Jwts.parserBuilder()，补齐三个依赖。
```
