## 概述

JWT 解决的是「你是谁」的认证问题，但接口安全还有另一层威胁：请求被篡改、被重放、被高频刷。接口签名与防重放机制解决的是「请求内容是否可信、请求是否新鲜、请求是否重复」的问题，是 JWT 之外的第二道防线，常用于开放 API、小程序后端接口、支付与下单等敏感操作。

核心思路是：客户端用约定的密钥对请求参数做签名，服务端用同样的规则重算签名并比对，签名一致说明参数未被篡改；再配合时间戳（timestamp）校验请求的新鲜度，配合 nonce（随机数）保证同一签名请求只能被处理一次，配合限流控制请求频率。四者组合，构成「防篡改 + 防重放 + 防刷」的完整方案。

```text
接口签名与防重放的核心机制：
1. 签名 —— appId + timestamp + nonce + 业务参数 + 密钥，哈希后比对，防篡改
2. 时间戳 —— 请求时间与服务器时间差超过窗口（如 5 分钟）直接拒绝，防过期重放
3. nonce —— 随机数唯一性，Redis 记录已用 nonce，同一请求只能成功一次
4. 幂等 —— 业务层用请求唯一 ID 保证重复提交只生效一次
5. 限流 —— 计数器/滑动窗口/令牌桶控制请求频率，防接口被刷爆
6. 组合使用 —— 签名管内容可信，时间戳+nonce 管新鲜与唯一，限流管频率
```

## 签名算法

接口签名的目的是保证请求参数在传输过程中未被篡改。基本模型是：客户端与服务器共享一把密钥（appSecret），客户端把请求参数按约定规则拼成字符串，加上密钥做哈希得到 sign；服务器用同样的规则重算 sign，与请求携带的 sign 比对，一致则参数可信。

一个成熟的签名协议包含以下要素：

```text
签名协议要素：
1. appId —— 调用方标识，服务端根据 appId 查对应的 appSecret，支持多端多密钥
2. timestamp —— 客户端生成签名的 Unix 时间戳（秒），参与签名防篡改
3. nonce —— 每次请求生成的随机字符串，参与签名且唯一，防重放的核心
4. sign —— 最终签名值，把上述字段与业务参数按规则拼接后哈希
5. 参与签名的参数 —— 所有业务参数必须参与签名，漏签的参数可被任意篡改
6. 密钥 —— appSecret 只存在于客户端与服务端，任何一方泄露都需立即更换
```

签名生成规则（以 SHA-256 为例）：把所有参与签名的参数按 key 字典序（ASCII 升序）排列，拼成 `key1=value1&key2=value2...` 的字符串，末尾拼接密钥，再整体做哈希。字典序拼接保证客户端与服务端无论参数顺序如何都能得到相同字符串：

```java
package com.example.security.sign;

import org.springframework.util.DigestUtils;

import java.nio.charset.StandardCharsets;
import java.util.Map;
import java.util.TreeMap;

public class SignUtil {

    /**
     * 生成签名：参数按 key 字典序拼接为 key=value&... 形式，末尾加 secret，再做 SHA-256
     * 注意：null 与空字符串参数不参与签名，客户端与服务端规则必须完全一致
     */
    public static String sign(Map<String, String> params, String secret) {
        TreeMap<String, String> sorted = new TreeMap<>(params); // 字典序排序
        StringBuilder sb = new StringBuilder();
        for (Map.Entry<String, String> entry : sorted.entrySet()) {
            String key = entry.getKey();
            String value = entry.getValue();
            if (value == null || value.isEmpty()) {
                continue; // 空值不参与签名
            }
            sb.append(key).append('=').append(value).append('&');
        }
        sb.append("secret=").append(secret);
        // SHA-256 十六进制摘要
        return DigestUtils.sha256Hex(sb.toString().getBytes(StandardCharsets.UTF_8));
    }
}
```

MD5 与 SHA-256 的选择：MD5 是 128 位摘要，碰撞攻击理论上可行，仅适合对安全性要求不高的场景；SHA-256 是 256 位摘要，是当前推荐选择。更进一步的方案是用 HMAC-SHA256（带密钥的哈希），把密钥融入哈希过程而不是简单拼接，抗长度扩展攻击能力更强：

```java
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.nio.charset.StandardCharsets;
import java.util.HexFormat;

/** HMAC-SHA256 签名：密钥参与哈希计算，比简单拼接更安全 */
public static String hmacSign(String content, String secret) throws Exception {
    Mac mac = Mac.getInstance("HmacSHA256");
    SecretKeySpec keySpec = new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256");
    mac.init(keySpec);
    byte[] digest = mac.doFinal(content.getBytes(StandardCharsets.UTF_8));
    return HexFormat.of().formatHex(digest);
}
```

```text
签名算法要点：
1. 参数按 key 字典序拼接，消除参数顺序差异，客户端服务端规则必须一字不差
2. 空值参数不参与签名，但约定必须统一，否则两侧结果不一致
3. SHA-256 优于 MD5；更高要求用 HMAC-SHA256，密钥融入哈希过程
4. appId 标识调用方，服务端按 appId 查 appSecret，支持多端独立密钥
5. 所有业务参数必须参与签名，漏签参数等于可被任意篡改
6. 签名比对用常量时间比较（MessageDigest.isEqual），防止时序攻击
```

## 时间戳校验

时间戳校验解决「请求是否新鲜」的问题。攻击者截获一个合法请求后，即使不知道密钥改不了内容，也可以原样重放——把同一个请求再发一遍。时间戳校验的核心是：客户端在请求头携带签名时的 Unix 时间戳，服务端校验该时间戳与服务器当前时间的差值，超过窗口（业界常用 5 分钟）就拒绝。

```text
时间戳校验流程：
1. 客户端发起请求时取当前 Unix 时间戳（秒级），放入请求头 X-Timestamp
2. 时间戳参与签名，防止攻击者事后篡改时间戳
3. 服务端收到请求，先取系统当前时间与请求时间戳做差
4. 差值绝对值超过窗口（如 5 分钟）→ 拒绝，提示「请求已过期」
5. 窗口内 → 继续 nonce 校验与签名比对
6. 客户端与服务端时间必须同步（NTP），否则正常请求会被误杀
```

实现示例（时间戳校验 + 过期拒绝）：

```java
/** 校验时间戳是否在允许窗口内 */
public static boolean checkTimestamp(String timestamp, long windowMs) {
    long ts;
    try {
        ts = Long.parseLong(timestamp) * 1000L; // 秒转毫秒
    } catch (NumberFormatException e) {
        return false;
    }
    long diff = Math.abs(System.currentTimeMillis() - ts);
    return diff <= windowMs; // 默认窗口 5 分钟
}
```

窗口大小的权衡：窗口越大，对客户端时钟偏差的容忍度越高，但重放攻击的可用时间也越长；窗口越小越安全，但客户端时钟不准时误杀率上升。5 分钟是通行选择，对时钟敏感的金融场景可收紧到 1 分钟。注意时间戳参与签名，攻击者无法通过修改时间戳来绕过窗口检查，因为改了就验签失败。

```text
时间戳校验要点：
1. 时间戳必须参与签名，否则攻击者可把时间戳改回窗口内绕过检查
2. 窗口通常 5 分钟，与业务风险匹配：风险越高窗口越小
3. 秒级时间戳与毫秒级要统一约定，解析后乘 1000 避免差 1000 倍
4. 服务器时间必须 NTP 同步，客户端时间不准会导致正常请求被拒
5. 时间戳校验只防「过期重放」，窗口内的重放要靠 nonce 解决
6. 拒绝时返回明确错误码（如 40001 请求过期），便于客户端对齐时钟后重试
```

## nonce 与防重放

时间戳把重放窗口限制在 5 分钟内，但窗口内的重放依然有效。nonce（Number used once，一次性随机数）解决这个问题：客户端每次请求生成一个随机字符串，服务端把「用过的 nonce」记录下来，同一 nonce 只允许出现一次。攻击者重放时携带的是同一个 nonce，服务端发现已存在直接拒绝。

nonce 的存储用 Redis 最合适：利用 SETNX 命令的原子性，同一 nonce 只能成功写入一次，配合 TTL 自动过期清理，天然实现「用一次即废」：

```java
package com.example.security.interceptor;

import com.example.security.sign.SignUtil;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;

import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.TimeUnit;

@Component
public class SignInterceptor implements HandlerInterceptor {

    /** 时间戳窗口：5 分钟 */
    private static final long MAX_AGE_MS = 5 * 60 * 1000L;

    private final StringRedisTemplate redisTemplate;
    private final AppSecretService appSecretService;

    public SignInterceptor(StringRedisTemplate redisTemplate, AppSecretService appSecretService) {
        this.redisTemplate = redisTemplate;
        this.appSecretService = appSecretService;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws Exception {
        // 1. 取签名相关请求头
        String appId = request.getHeader("X-App-Id");
        String timestamp = request.getHeader("X-Timestamp");
        String nonce = request.getHeader("X-Nonce");
        String sign = request.getHeader("X-Sign");
        if (appId == null || timestamp == null || nonce == null || sign == null) {
            return reject(response, "缺少签名参数");
        }

        // 2. 时间戳校验
        long ts;
        try {
            ts = Long.parseLong(timestamp) * 1000L;
        } catch (NumberFormatException e) {
            return reject(response, "时间戳格式错误");
        }
        if (Math.abs(System.currentTimeMillis() - ts) > MAX_AGE_MS) {
            return reject(response, "请求已过期");
        }

        // 3. nonce 防重放：SETNX 原子写入，成功说明首次使用，失败说明重复
        String nonceKey = "sign:nonce:" + appId + ":" + nonce;
        Boolean first = redisTemplate.opsForValue().setIfAbsent(
                nonceKey, "1", MAX_AGE_MS, TimeUnit.MILLISECONDS);
        if (first == null || !first) {
            return reject(response, "重复请求");
        }

        // 4. 组装参与签名的参数（请求头字段 + 业务参数）
        Map<String, String> params = new HashMap<>();
        params.put("appId", appId);
        params.put("timestamp", timestamp);
        params.put("nonce", nonce);
        request.getParameterMap().forEach((k, v) -> params.put(k, v[0]));

        // 5. 验签
        String appSecret = appSecretService.getSecret(appId);
        if (appSecret == null) {
            return reject(response, "无效的 appId");
        }
        String expect = SignUtil.sign(params, appSecret);
        if (!MessageDigest.isEqual(expect.getBytes(), sign.toLowerCase().getBytes())) {
            return reject(response, "签名校验失败");
        }
        return true;
    }

    private boolean reject(HttpServletResponse response, String msg) throws Exception {
        response.setStatus(403);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"code\":40301,\"msg\":\"" + msg + "\"}");
        return false;
    }
}
```

nonce 与幂等性的关系：nonce 防的是「同一个签名请求被重复发送」，幂等性防的是「同一笔业务被重复提交」。对下单、支付、转账这类操作，光有 nonce 还不够——客户端重试时可能生成新 nonce 但业务内容相同，服务端需要按业务唯一键（如订单号、请求唯一 ID）去重。幂等方案：客户端每次业务请求生成 requestId，服务端以 requestId 为键做 SETNX 占位，已存在则直接返回第一次的结果。

```text
nonce 与防重放要点：
1. nonce 每次请求随机生成且只允许使用一次，防窗口内重放
2. Redis SETNX 原子写入实现「用一次即废」，TTL 与时间戳窗口一致
3. nonce 必须参与签名，否则攻击者可以换新 nonce 重放旧请求
4. nonce key 带上 appId 前缀，隔离不同调用方，避免碰撞误杀
5. 敏感业务（下单/支付）叠加幂等设计：requestId 唯一键 + Redis 占位
6. 防重放是纵深防御的一环，与签名、时间戳、限流组合使用
```

## 接口防刷

签名与防重放解决「内容可信与不重复」，接口防刷解决「频率可控」。未限流的接口会被脚本、爬虫、撞库、恶意刷单打爆：下单接口被刷导致库存错乱，登录接口被刷导致账号被爆破，短信接口被刷导致话费流失。限流的本质是控制单位时间内的请求量，常见算法有计数器、滑动窗口、令牌桶、漏桶。

```text
常见限流算法对比：
1. 固定窗口计数器 —— 每分钟最多 N 次，实现简单，但窗口边界可突发 2 倍流量
2. 滑动窗口 —— 细粒度记录每个请求的时间点，窗口滑动统计，无边界突刺，内存开销大
3. 令牌桶 —— 恒定速率往桶里放令牌，请求消耗令牌，桶容量允许突发，适合流量整形
4. 漏桶 —— 恒定速率处理请求，超出即丢弃，绝对平滑，但无法应对突发流量
5. 分布式限流 —— 基于 Redis + Lua 实现原子计数，多实例共享计数
6. 混合策略 —— IP 限流 + 用户限流 + 接口限流叠加，各自独立计数
```

单机场景用 Guava RateLimiter 实现令牌桶最简单，按 IP 维护各自的限流器：

```java
package com.example.security.ratelimit;

import com.google.common.util.concurrent.RateLimiter;
import org.springframework.stereotype.Component;

import java.util.concurrent.ConcurrentHashMap;

@Component
public class IpRateLimiter {

    /** 每个 IP 一个令牌桶，每秒 10 个令牌，桶容量 10 允许小幅突发 */
    private final ConcurrentHashMap<String, RateLimiter> limiters = new ConcurrentHashMap<>();

    public boolean tryAcquire(String ip) {
        RateLimiter limiter = limiters.computeIfAbsent(ip, k -> RateLimiter.create(10.0));
        return limiter.tryAcquire(); // 拿不到令牌返回 false，不阻塞
    }

    /** IP 数量可能很大，定期清理不活跃的限流器 */
    public void evictIdle() {
        limiters.entrySet().removeIf(e -> !e.getValue().tryAcquire(0));
    }
}
```

分布式场景（多实例部署）单机限流会失效，必须用 Redis 原子计数。滑动窗口用 ZSet 实现：每个请求把时间戳写入 ZSet，统计窗口内数量：

```java
package com.example.security.ratelimit;

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.util.concurrent.TimeUnit;

@Component
public class RedisSlidingWindowLimiter {

    private final StringRedisTemplate redisTemplate;

    public RedisSlidingWindowLimiter(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    /**
     * 滑动窗口限流：ZSet 记录每个请求时间戳，统计窗口内请求数
     * key 形如 rate:ip:1.2.3.4，窗口 60 秒，上限 100 次
     */
    public boolean allow(String key, int windowSeconds, int maxCount) {
        long now = System.currentTimeMillis();
        long windowStart = now - windowSeconds * 1000L;
        String redisKey = "rate:" + key;
        // Lua 脚本保证检查+写入原子性，避免并发下超限
        String lua = "redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1]) " +
                     "local count = redis.call('ZCARD', KEYS[1]) " +
                     "if count < tonumber(ARGV[2]) then " +
                     "  redis.call('ZADD', KEYS[1], ARGV[3], ARGV[4]) " +
                     "  redis.call('EXPIRE', KEYS[1], ARGV[5]) " +
                     "  return 1 " +
                     "else return 0 end";
        Long result = redisTemplate.execute(
                (connection) -> connection.eval(
                        lua.getBytes(),
                        java.util.Collections.singletonList(redisKey.getBytes()),
                        java.util.List.of(
                                String.valueOf(windowStart).getBytes(),
                                String.valueOf(maxCount).getBytes(),
                                String.valueOf(now).getBytes(),
                                (now + "-" + Math.random()).getBytes(),
                                String.valueOf(windowSeconds).getBytes())));
        return Long.valueOf(1L).equals(result);
    }
}
```

限流的落地位置：最外层是 Nginx（按 IP 限流，挡住最粗粒度的攻击）；应用层按接口、按用户、按 IP 分别限流；敏感接口（验证码、支付）单独收紧。限流触发时返回 429（Too Many Requests）或业务码 42901，客户端收到后应退避重试。

```text
接口防刷要点：
1. 单机场景 Guava RateLimiter 令牌桶足够，多实例必须 Redis 分布式限流
2. Redis 限流用 Lua 脚本保证「检查+写入」原子性，避免并发超限
3. 滑动窗口 ZSet 方案要定期清理窗口外数据，防止 ZSet 无限膨胀
4. IP 限流 + 用户限流 + 接口限流叠加，各自独立计数、独立阈值
5. Nginx 层与应用层双层限流，粗粒度挡外层，细粒度控内层
6. 限流返回 429 并带 Retry-After 头，客户端按退避策略重试
```

## 应用场景实战

### 场景一：完整签名 + 防重放拦截器

将签名校验、时间戳校验、nonce 防重放整合为一个拦截器，注册到需要保护的接口路径上。小程序端与后台约定：请求头携带 X-App-Id、X-Timestamp、X-Nonce、X-Sign 四个字段，业务参数放 query 或 body，参与签名。

拦截器已在「nonce 与防重放」一节给出完整实现，这里补充注册与小程序端调用：

```java
package com.example.config;

import com.example.security.interceptor.SignInterceptor;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class SignWebConfig implements WebMvcConfigurer {

    private final SignInterceptor signInterceptor;

    public SignWebConfig(SignInterceptor signInterceptor) {
        this.signInterceptor = signInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(signInterceptor)
                .addPathPatterns("/api/sign/**"); // 只保护需要签名的接口
    }
}
```

小程序端签名工具（需要引入 crypto-js 或使用 wx 环境支持的库）：

```javascript
// utils/sign.js
const crypto = require('crypto-js');

const APP_ID = 'wx-mall-app';
const APP_SECRET = '与后台约定的密钥，只存在于代码包或后台下发';

// 生成签名：参数字典序拼接 + secret，SHA-256
const buildSign = (params, secret) => {
  const keys = Object.keys(params).sort();
  let str = '';
  keys.forEach((k) => {
    if (params[k] !== undefined && params[k] !== null && params[k] !== '') {
      str += k + '=' + params[k] + '&';
    }
  });
  str += 'secret=' + secret;
  return crypto.SHA256(str).toString();
};

// 带签名的请求封装
const signedRequest = (url, data) => {
  const timestamp = Math.floor(Date.now() / 1000);
  const nonce = Date.now().toString(36) + Math.random().toString(36).slice(2, 10);
  const sign = buildSign(Object.assign({}, data, {
    appId: APP_ID,
    timestamp: String(timestamp),
    nonce
  }), APP_SECRET);

  return new Promise((resolve, reject) => {
    wx.request({
      url,
      method: 'POST',
      data,
      header: {
        'Content-Type': 'application/json',
        'X-App-Id': APP_ID,
        'X-Timestamp': String(timestamp),
        'X-Nonce': nonce,
        'X-Sign': sign
      },
      success: resolve,
      fail: reject
    });
  });
};

module.exports = { signedRequest };
```

注意：小程序代码包可被反编译，密钥放前端只适合「防篡改」级别的保护。真正需要防伪造的开放接口，密钥应放在服务端（如云函数/网关）代签，或使用微信登录态 + 服务端签名。

### 场景二：下单接口幂等 + 限流组合

支付、下单类接口同时叠加防重放、幂等与限流。设计如下：

```text
下单接口防护组合：
1. 客户端生成 requestId（业务唯一 ID），下单请求携带
2. 服务端以 requestId 为键 SETNX 占位：已存在则直接返回首次处理结果（幂等）
3. 接口层按用户限流：每人每分钟最多 10 次下单，防脚本刷单
4. 参数校验通过后执行下单事务，成功后写入订单
5. 事务提交后更新 requestId 占位记录为「已处理」
6. 重试请求命中占位记录，返回原订单号，不重复扣库存
```

幂等实现：

```java
package com.example.service;

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

import java.util.concurrent.TimeUnit;

@Service
public class IdempotentService {

    private final StringRedisTemplate redisTemplate;

    public IdempotentService(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    /**
     * 尝试占位：成功说明首次请求，可以继续执行；失败说明重复请求
     * key 用业务前缀 + requestId，TTL 覆盖一次业务完整执行周期
     */
    public boolean tryLock(String requestId) {
        Boolean ok = redisTemplate.opsForValue().setIfAbsent(
                "idem:order:" + requestId, "1", 30, TimeUnit.MINUTES);
        return Boolean.TRUE.equals(ok);
    }

    /** 业务完成后记录结果，重复请求直接返回 */
    public void complete(String requestId, String orderNo) {
        redisTemplate.opsForValue().set(
                "idem:order:" + requestId, orderNo, 24, TimeUnit.HOURS);
    }

    /** 重复请求时取出首次处理结果 */
    public String getResult(String requestId) {
        return redisTemplate.opsForValue().get("idem:order:" + requestId);
    }
}
```

```java
// 下单接口：幂等占位 + 业务执行
@PostMapping("/api/order/create")
public Map<String, Object> createOrder(@RequestBody CreateOrderDTO dto) {
    if (!idempotentService.tryLock(dto.getRequestId())) {
        // 重复提交：返回首次结果
        String orderNo = idempotentService.getResult(dto.getRequestId());
        return Map.of("duplicated", true, "orderNo", orderNo);
    }
    String orderNo = orderService.create(dto); // 事务内扣库存、生成订单
    idempotentService.complete(dto.getRequestId(), orderNo);
    return Map.of("duplicated", false, "orderNo", orderNo);
}
```

这套组合保证：同一个 requestId 的请求无论被重放多少次，业务只执行一次；脚本高频刷单被限流拦截；篡改请求参数被签名校验拦截。

## 最佳实践与踩坑记录

### 最佳实践

1. 签名协议四要素缺一不可：appId 标识调用方、timestamp 防过期、nonce 防重放、sign 防篡改，且 timestamp 与 nonce 必须参与签名
2. 参数拼接规则（字典序、空值处理、编码方式）在客户端与服务端用同一份文档约束，任何一处不一致都会导致验签失败
3. 密钥分级管理：不同端（小程序、管理端、第三方）用不同 appId/appSecret，某端泄露只需更换该端密钥，不影响其他端
4. 敏感接口（下单、支付、退款、改密）必须叠加幂等设计，用 requestId 做业务唯一键，防止重试导致重复扣款
5. 限流分层落地：Nginx 按 IP 粗限流，应用层按接口、用户、IP 细限流，敏感接口单独收紧阈值
6. 分布式限流必须用 Redis Lua 脚本保证原子性，单机 RateLimiter 在多实例部署下会失效
7. 时间戳窗口按业务风险调节：普通接口 5 分钟，支付回调类接口 1 分钟，并确保服务器 NTP 同步
8. 验签失败、限流触发、重复请求要返回不同错误码（如 40301 签名失败、42901 限流、40901 重复），便于客户端区分处理

### 踩坑记录

```text
坑 1：客户端与服务端参数拼接规则不一致，签名永远校验失败
结论：客户端签的 sign 与服务端重算的 sign 总是不相等，接口全部 403。
原因：参数顺序、空值处理、编码方式（UTF-8/URL 编码）两侧实现不一致，拼接结果不同。
解法：用同一份协议文档约束规则；统一走字典序拼接；空值统一不参与签名；联调时打印两侧拼接串对比。

坑 2：body 参数没参与签名，修改 JSON 内容服务端不校验
结论：攻击者修改请求体里的金额、数量，签名校验依然通过。
原因：验签时只取了 query 参数和请求头，body 参数未参与签名计算。
解法：body 内容必须参与签名：解析 body 后把字段并入签名参数表，或对整个 body 做哈希参与签名。

坑 3：时间戳单位不一致，秒当毫秒用导致请求全部「过期」
结论：客户端发秒级时间戳，服务端按毫秒解析，差值巨大，所有请求被拒。
原因：时间戳单位约定不明，两端实现不一致。
解法：统一约定秒级（Unix 秒），服务端解析后乘 1000 转毫秒；接口文档里写明单位。

坑 4：nonce 只存内存 Map，多实例部署下重放拦截失效
结论：单实例测试防重放正常，多实例部署后同一 nonce 可以重复使用。
原因：nonce 存在单机内存，其他实例不感知，负载均衡后请求打到不同实例。
解法：nonce 存 Redis 共享存储，用 SETNX 保证跨实例唯一；key 带 appId 与时间窗。

坑 5：nonce 没参与签名，攻击者换新 nonce 绕过防重放
结论：重放攻击依然成功，防重放形同虚设。
原因：nonce 只放在请求头做查重，攻击者截获请求后换一个新的随机 nonce 即可通过。
解法：nonce 必须参与签名计算，改 nonce 必然导致验签失败。

坑 6：签名比对用 String.equals，存在时序攻击风险
结论：理论上攻击者可以通过响应时间逐字符猜出正确签名。
原因：String.equals 逐字符比较，遇到第一个不同字符就返回，比较时间泄露信息。
解法：用 MessageDigest.isEqual 做常量时间比较，比较时间与内容无关。

坑 7：固定窗口限流窗口边界可突发双倍流量
结论：每分钟限 100 次的接口，在第 59 秒和第 61 秒各放 100 次，实际 2 秒内 200 次。
原因：固定窗口计数器在窗口边界重置计数，边界两侧各有一个完整窗口额度。
解法：改用滑动窗口（ZSet 精确统计）或令牌桶（允许有限突发但整体速率受限）。

坑 8：幂等占位在事务提交前就标记完成，回滚后幂等失效
结论：下单事务回滚后，重试请求命中占位记录直接返回「成功」，用户永远拿不到订单。
原因：占位记录先于事务提交写入，事务失败后没有清理。
解法：占位与业务结果分离：tryLock 只占位，事务成功提交后才写入结果；失败清理占位允许重试。
```
