## 概述

小程序发布上线必须通过微信平台审核，审核规范围绕类目资质、内容规范、隐私合规三个维度展开。类目资质决定小程序能做什么业务（电商、医疗、金融等特殊类目需要对应资质证件），内容规范约束小程序不能有什么内容（违规信息、诱导分享、虚拟支付限制等），隐私合规决定接口与功能能否正常使用。

审核被拒并不可怕，可怕的是不了解规则反复踩坑浪费时间。掌握常见拒审原因（类目不符、功能未完成、违规内容、隐私问题）、申诉流程（修改重提、申诉入口、加急审核）与合规红线（赌博色情、诱导分享、虚拟支付、非法集资），可以大幅缩短从提审到上线的周期。本章结合真实审核场景给出完整的合规自查清单与提审实操。

```text
审核规范的核心要点：
1. 类目资质 —— 每个小程序选择服务类目，特殊类目（电商/医疗/金融等）需提交资质证件
2. 内容规范 —— 不得含违法违规内容，禁止诱导分享，iOS 端虚拟支付受限
3. 功能完整 —— 提审版本功能必须可完整体验，不能有占位页、空白页、测试数据
4. 隐私合规 —— 隐私保护指引声明与实际收集行为一致，隐私弹窗正常展示
5. 申诉机制 —— 拒审后可修改重提，对结果有异议可申诉，认证主体有加急审核权益
6. 红线底线 —— 赌博色情、诱导分享、虚拟支付违规、非法集资等红线一票否决
```

## 类目资质

小程序注册后需要在小程序后台「设置-基本设置-服务类目」选择业务类目。类目决定小程序可用的能力范围与审核标准：工具、生活服务等常规类目门槛低；电商、医疗、金融、教育、直播等类目属于特殊类目，需要提交对应的资质证件（营业执照、许可证等），资质不全直接拒审。

类目选择原则：按实际主营业务选择，一个类目对应一类业务；类目与实际功能不符（如做电商却选「工具」类目）会被拒审或后续被平台下架。类目调整会影响已上线的功能，变更类目需要重新提审。

提审前可以用「功能 → 类目 → 资质」的映射自查：把小程序的核心功能列出来，逐个确认属于哪个类目、是否需要资质、资质是否已提交并通过。以下是自查逻辑的工程化实现（后台资质管理系统可参考）：

```java
// CategoryChecker.java —— 功能-类目-资质映射自查（示例实现）
public class CategoryChecker {

    /** 功能点 -> 建议类目（示例映射表，实际以微信公众平台类目库为准） */
    private static final Map<String, String> FEATURE_CATEGORY = Map.ofEntries(
        Map.entry("商品销售", "商家自营"),
        Map.entry("在线支付交易", "电商平台/商家自营"),
        Map.entry("在线问诊", "医疗-互联网医院"),
        Map.entry("课程售卖", "教育-在线教育"),
        Map.entry("直播带货", "直播-电商直播")
    );

    /** 类目 -> 所需资质（示例） */
    private static final Map<String, List<String>> CATEGORY_CERT = Map.ofEntries(
        Map.entry("商家自营", List.of("营业执照", "食品经营许可证（含食品类目时）")),
        Map.entry("医疗-互联网医院", List.of("医疗机构执业许可证")),
        Map.entry("直播-电商直播", List.of("网络文化经营许可证"))
    );

    /** 提审前自查：功能是否被类目覆盖、资质是否齐备 */
    public static List<String> selfCheck(List<String> features) {
        List<String> problems = new ArrayList<>();
        for (String feature : features) {
            String category = FEATURE_CATEGORY.get(feature);
            if (category == null) {
                problems.add(feature + "：未找到匹配类目，请确认是否属于平台允许的业务");
                continue;
            }
            List<String> certs = CATEGORY_CERT.getOrDefault(category, List.of());
            if (!certs.isEmpty()) {
                problems.add(feature + "：类目[" + category + "]需资质 " + String.join("、", certs));
            }
        }
        return problems;
    }
}
```

```text
类目选择决策流程：
1. 列出全部核心功能（登录、交易、内容、直播、医疗等）
2. 逐功能匹配平台类目库，一个类目覆盖一类业务
3. 检查特殊类目的资质要求，评估资质办理周期与成本
4. 提交类目与资质审核（1-5 个工作日），通过后锁定类目
5. 提审前复查：类目能否覆盖全部功能，避免「功能超出类目」拒审
6. 后续新增业务超出类目范围时，先变更类目再上线新功能
```

```text
常见类目与资质要求：
1. 电商平台/商家自营 —— 电商平台需《增值电信业务经营许可证》（ICP 证）；商家自营卖食品需《食品经营许可证》
2. 医疗健康 —— 需《医疗机构执业许可证》或与持证机构合作证明，个人主体不可做医疗咨询
3. 金融 —— 支付、借贷、理财等需对应金融牌照（支付业务许可证等），无牌经营直接封禁
4. 教育培训 —— 学科类培训需办学许可证；非学科类（兴趣、职业技能）需相应资质或备案
5. 直播 —— 需《网络文化经营许可证》《信息网络传播视听节目许可证》等
6. 工具类 —— 门槛最低，但功能必须名副其实，不能挂工具卖内容
```

```text
类目资质实操要点：
1. 注册后第一时间确定类目，特殊资质（证件办理）周期长，要提前准备
2. 一个类目对应一类业务，多业务小程序选择与主营最匹配的类目
3. 资质证件上传后等待平台审核（1-5 个工作日），审核期间不可改类目
4. 类目与功能不符是最高频拒审原因之一，上线前自查「类目能否覆盖全部功能」
5. 个人主体可选类目少，涉及交易、医疗、金融的业务必须用企业主体
6. 类目变更会触发重新审核，且可能影响已上线功能，变更前评估风险
```

## 内容规范

内容规范约束小程序页面内展示与交互的内容：不得含有违法违规信息（色情低俗、赌博、暴力恐怖、分裂国家、谣言），不得诱导分享（分享解锁、强制关注、分享后抽奖），不得违规导流（诱导跳转外部 App、下载 App），虚拟支付需遵守平台规则（iOS 端虚拟商品不能使用微信支付）。

内容规范还覆盖页面文案与视觉：标题与内容必须一致、不得使用夸大宣传（「最便宜」「百分百有效」等广告法违禁词）、不得抄袭侵权（名称、Logo、内容版权）、不得有测试占位内容（「TODO」「测试」字样、空白页面、未实现按钮）。

```text
内容规范清单：
1. 禁止内容 —— 色情低俗、赌博、毒品、暴力恐怖、分裂国家、谣言虚假信息
2. 禁止诱导 —— 诱导分享/转发（分享解锁功能）、强制关注、诱导下载 App
3. 虚拟支付 —— iOS 端虚拟商品（会员、充值、虚拟币、在线课程）不能用微信支付
4. 广告合规 —— 不使用「最」「第一」「绝对」等广告法违禁词，医疗广告需备案
5. 版权合规 —— 名称、头像、内容、音乐、图片不得侵权，影视类需版权证明
6. 页面质量 —— 无空白页、无占位符、无测试数据、无不可用的按钮，功能可完整体验
```

```text
内容规范自查清单（提审前逐项打勾）：
1. 页面全部可访问，无「功能开发中」「TODO」等占位内容
2. 无诱导分享/关注文案与弹窗，分享按钮为微信原生能力
3. 虚拟商品在 iOS 端有合规的引导（如提示联系客服/到店）
4. 文案无广告法违禁词，无夸大虚假宣传
5. 使用的图片、音乐、字体均有授权或为免费商用
6. 用户协议、隐私政策、版权声明等必备文本完整可打开
```

文案合规可以工程化：把《广告法》违禁词与平台敏感词沉淀为词库，接入 CI 或提审前脚本自动扫描页面文案。以下是一个可集成到提审流程的违禁词扫描器：

```java
// AdWordScanner.java —— 页面文案违禁词扫描（提审前 CI 检查）
public class AdWordScanner {

    /** 广告法违禁词示例（正式词库建议按最新法规整理并定期更新） */
    private static final List<String> BANNED_WORDS = List.of(
        "最", "第一", "顶级", "国家级", "最佳", "绝无仅有",
        "百分百", "根治", "包治", "全网最低", "销量第一",
        "无效退款", "零风险", "稳赚", "保本"
    );

    /** 扫描一段文案，返回命中的违禁词 */
    public static List<String> scan(String text) {
        if (text == null || text.isEmpty()) {
            return List.of();
        }
        return BANNED_WORDS.stream()
            .filter(text::contains)
            .collect(Collectors.toList());
    }

    /** 扫描整个小程序页面文案集合，输出报告 */
    public static Map<String, List<String>> scanAll(Map<String, String> pageTexts) {
        Map<String, List<String>> report = new LinkedHashMap<>();
        pageTexts.forEach((page, text) -> {
            List<String> hits = scan(text);
            if (!hits.isEmpty()) {
                report.put(page, hits);
            }
        });
        return report;
    }
}
```

```text
文案合规实操：
1. 商品详情、活动页、弹窗文案重点扫描，「最」「第一」「根治」等词一律替换
2. 医疗、保健品类目文案管理最严，功效宣传必须有批文背书
3. 抽奖/概率玩法文案用词要谨慎（「必中」「稳赚」违规），概率需如实公示
4. 文案扫描接入提审流程：CI 检查不通过禁止上传提审
5. 词库随法规更新：广告法修订、平台新规出来后及时补充违禁词
6. 用户协议、隐私政策、售后说明等法律文本用标准模板并由法务/顾问审阅
```

## 常见拒审原因

微信审核不通过会给出具体原因，高频拒审原因集中在类目、功能、内容、隐私四类。理解这些原因能帮助开发者一次通过：类目不符（类目与实际功能不一致、资质不全）、功能未完成（空白页、占位、无法体验完整流程）、违规内容（测试数据、违规信息、诱导分享）、隐私问题（隐私指引未填、声明与实际不符、无注销入口）。

```text
高频拒审原因清单：
1. 类目不符 —— 实际功能与所选类目不匹配，或特殊类目缺少资质证件
2. 功能未完成 —— 审核员无法完整走通流程：空白页、登录失败、按钮无响应、提交报错
3. 违规内容 —— 页面含测试数据、违规文案、诱导分享、虚假宣传
4. 隐私问题 —— 未填写隐私指引、声明与实际收集不符、无隐私政策入口、无注销入口
5. 名称侵权 —— 名称含他人商标、知名品牌词、或与已有小程序重名
6. 支付违规 —— iOS 虚拟支付、未接入微信支付却引导其他支付方式
7. 外链违规 —— 诱导跳转外部 App/网页、二维码导流到 App 下载
8. 能力不符 —— 声明的能力（如直播、位置）实际未实现或实现不完整
```

```text
拒审信息解读：
1. 拒审通知会给出具体类目与描述，如「服务类目与你提交的代码审核不一致」
2. 部分拒审附带截图或录屏，仔细看审核员看到的问题页面
3. 「功能无法完整体验」类拒审，要自查登录态、测试账号、网络环境
4. 隐私类拒审先看后台隐私指引是否填写完整、是否与代码一致
5. 同一版本多次拒审会累计风险，严重者影响账号权重，务必逐条修复
6. 修复后重新提交，不要带着未解决的问题反复提审
```

拒审原因处理可以工程化：把历史拒审原因沉淀成分类枚举，每个分类对应标准处理动作与自查点，提审前跑一遍检查清单，从源头减少同类拒审。以下是一个团队内部使用的拒审原因分类处理模型：

```java
// ReviewIssueType.java —— 拒审原因分类与处理动作（团队自查模型）
public enum ReviewIssueType {
    CATEGORY_MISMATCH("类目不符", "核对类目库与实际功能，补交资质后重新提审"),
    FEATURE_INCOMPLETE("功能未完成", "用测试账号完整走通核心链路，录屏留存"),
    ILLEGAL_CONTENT("违规内容", "全局搜索测试/占位文案，删除违规与诱导分享内容"),
    PRIVACY_ISSUE("隐私问题", "核对隐私指引声明与实际收集行为，补齐弹窗与注销入口"),
    NAME_INFRINGEMENT("名称侵权", "自查名称商标冲突，改名或补充授权证明"),
    PAYMENT_VIOLATION("支付违规", "核对 iOS 虚拟支付规则，调整支付引导路径"),
    EXTERNAL_LINK("外链违规", "移除诱导跳转外部 App/网页的引导"),
    CAPABILITY_MISMATCH("能力不符", "声明的能力（直播/定位等）必须真实实现并可用");

    private final String label;
    private final String action;

    ReviewIssueType(String label, String action) {
        this.label = label;
        this.action = action;
    }

    /** 根据拒审描述归类并给出处理动作 */
    public static ReviewIssueType classify(String rejectReason) {
        if (rejectReason.contains("类目")) return CATEGORY_MISMATCH;
        if (rejectReason.contains("体验") || rejectReason.contains("功能")) return FEATURE_INCOMPLETE;
        if (rejectReason.contains("隐私")) return PRIVACY_ISSUE;
        if (rejectReason.contains("名称") || rejectReason.contains("商标")) return NAME_INFRINGEMENT;
        if (rejectReason.contains("支付")) return PAYMENT_VIOLATION;
        if (rejectReason.contains("诱导") || rejectReason.contains("分享")) return ILLEGAL_CONTENT;
        return ILLEGAL_CONTENT; // 兜底按内容问题处理
    }
}
```

```text
拒审处理优先级：
1. 先读完整拒审描述与截图，确认是「硬伤」（红线违规）还是「软伤」（体验/资质问题）
2. 硬伤（支付违规、诱导分享、违规内容）必须彻底删除相关功能，不是改文案能解决的
3. 软伤（功能未完成、隐私声明不全）按标准动作修复，修复后自测验证
4. 修复说明写清「原因 + 改动点 + 合规依据」，提高二次审核通过率
5. 同一问题二次出现时，检查是否是环境问题（审核员用不同机型/网络）
6. 拒审不影响已上线版本，线上版本照常运行，但新功能必须修复后才能发布
```

## 申诉流程

审核被拒后有两种处理路径：一是按拒审原因修改代码后重新提交（常规路径，修改完成即可再次提审）；二是对审核结果有异议时走申诉（认为审核误判或功能符合规范，提交说明与证据，平台人工复核）。认证主体还可使用加急审核权益加快审核速度。

```text
审核流程与申诉实操：
1. 提审入口 —— 开发者工具点击「上传」上传代码，到小程序后台「版本管理-开发版本」提交审核
2. 审核时长 —— 常规 1-7 个工作日，首次提审通常较慢，加急审核（认证主体权益）1-2 小时出结果
3. 修改重提 —— 拒审后修改代码重新上传提交，无需等待旧版本结束
4. 申诉入口 —— 小程序后台审核记录中点击「申诉」，填写申诉说明并附证据（截图/录屏/说明文档）
5. 申诉材料 —— 说清功能逻辑、合规依据、如何满足类目资质要求，证据要能证明「符合规范」
6. 审核发布 —— 审核通过后手动点击「发布」，正式版生效；紧急修复可走「快速发布」白名单（需申请）
```

```text
提审准备清单：
1. 测试账号与测试数据就绪，审核员可完整体验核心流程（登录-浏览-下单-支付）
2. 后端接口全部联调通过，测试环境数据可用（无敏感信息）
3. 隐私指引已填写并与代码一致，隐私弹窗正常
4. 类目资质已通过审核，类目能覆盖全部功能
5. 页面无占位内容、无违禁词、无诱导分享
6. 版本号、更新日志、截图描述填写完整（截图要真实清晰）
```

版本从开发到上线的完整状态流转，可以在后台实现为状态机，配合提审自动化：开发中（developing）→ 已上传（uploaded）→ 审核中（reviewing）→ 审核通过（approved）/ 审核拒绝（rejected）→ 已发布（released）→ 已回滚（rolled_back）。每个状态都有对应的操作与限制（如审核中的版本不可重复提审、已发布的版本不可删除）。

```java
// VersionStateMachine.java —— 提审版本状态机（后台版本管理参考）
public enum VersionState {
    DEVELOPING,   // 开发中：可上传新代码
    UPLOADED,     // 已上传：可提交审核
    REVIEWING,    // 审核中：不可重复提审
    APPROVED,     // 审核通过：可发布
    REJECTED,     // 审核拒绝：可修改后重新提交
    RELEASED,     // 已发布：线上生效
    ROLLED_BACK;  // 已回滚：回退到上一发布版本

    /** 状态机转移表：当前状态 -> 允许的操作 */
    public boolean canTransitTo(VersionState target) {
        return switch (this) {
            case DEVELOPING -> target == UPLOADED;
            case UPLOADED -> target == REVIEWING || target == REJECTED;
            case REVIEWING -> target == APPROVED || target == REJECTED;
            case APPROVED -> target == RELEASED || target == REJECTED;
            case REJECTED -> target == UPLOADED;          // 修改后重新上传提审
            case RELEASED -> target == ROLLED_BACK;
            case ROLLED_BACK -> target == RELEASED;       // 回滚后可再次发布
        };
    }
}
```

```text
提审与发布实操要点：
1. 开发者工具「上传」后，到后台「版本管理-开发版本」找到该版本提交审核
2. 审核中版本支持「撤回」，撤回后可修改重新上传，不占用审核次数
3. 审核通过后 7 天内未发布，版本会过期需重新提审
4. 加急审核：认证主体每个自然月有加急次数，重要版本可用（审核时效 1-2 小时）
5. 发布支持全量发布或分阶段发布（灰度），紧急修复可申请「快速发布」白名单
6. 每个版本的操作（上传/提审/发布/回滚）都有留痕，配合状态机便于追溯
```

## 合规红线

合规红线是绝对不可触碰的底线，触碰红线轻则拒审、下架，重则封禁账号甚至移交司法机关。红线包括：赌博（棋牌游戏、赌博工具、赌资充值）、色情低俗（情色内容、擦边直播）、诱导分享（强制分享解锁）、虚拟支付违规（iOS 端绕过规则）、非法集资与金融诈骗（无牌照理财、传销、刷单返利）、违禁品交易（管制刀具、处方药、烟草、野生动物制品）。

```text
合规红线清单（一票否决）：
1. 赌博 —— 棋牌赌博、赌博资讯、赌资交易，任何形式的赌博均封禁
2. 色情低俗 —— 情色内容、色情直播、擦边内容，平台机器审核+人工巡检双重打击
3. 诱导分享 —— 分享解锁功能、强制关注、诱导转发抽奖
4. 虚拟支付 —— iOS 端虚拟商品交易绕过微信支付规则
5. 非法集资 —— 无牌照理财、P2P、传销、刷单返利、高额回报承诺
6. 违禁品 —— 管制刀具、枪支、毒品、处方药、烟草、野生动物制品
7. 诈骗 —— 仿冒官方、钓鱼链接、虚假交易、套取用户信息
8. 侵权 —— 仿冒知名品牌、盗版影视音乐、抄袭他人代码资源
```

```text
红线风险自查：
1. 商业模式是否涉及「拉人头返利」「多级分销」——触碰传销红线
2. 是否承诺「高收益、稳赚不赔」的理财投资——触碰非法集资红线
3. 是否有任何形式的赌博或变相赌博（抽奖概率玩法的合规性）
4. iOS 端虚拟商品的支付路径是否合规（不能诱导用户用其他支付方式）
5. 用户生成内容是否有完整的内容安全检测（UGC 平台必须接检测）
6. 涉及医疗、金融、教育的宣传是否有资质背书与合规表述
```

红线违规的典型后果比拒审严重得多：拒审只是「版本不过」，红线违规是「账号受损」。以下是几类真实案例与处理复盘：

```text
红线案例复盘：
1. 棋牌类小程序：接入第三方支付做「房卡」充值，被判定变相赌博，账号直接封禁，商户号冻结
2. 内容社区：评论区出现色情引流信息且未接入内容安全检测，被平台巡检发现，小程序下架整改 30 天
3. 电商小程序：页面出现「分享 3 位好友立减 50 元」，被判诱导分享，功能删除后重新提审
4. 知识付费小程序：iOS 端引导用户「点击复制口令去浏览器支付」，被判虚拟支付违规与诱导外跳
5. 理财类小程序：宣称「年化收益 20% 稳赚不赔」，无金融牌照，被认定为非法集资宣传，主体被拉黑
6. 仿冒小程序：名称与头像仿冒知名品牌官方号，被品牌方投诉，账号注销且主体信用受损
```

```text
红线后的标准动作：
1. 收到违规通知后立即下线违规功能与内容，不要心存侥幸继续运营
2. 按平台要求提交整改说明：违规点、整改动作、预防措施（内容检测/人工审核/资质补办）
3. 涉及资金（赌博、诈骗、非法集资）的立即冻结相关交易并配合平台与监管调查
4. 建立红线巡检机制：每周人工巡检页面文案、UGC 内容、支付路径、外链引导
5. 红线案例沉淀进团队合规手册，新功能上线前对照红线清单评审
6. 严重违规（封禁/拉黑）后申诉成功率极低，预防远胜于补救
```

## 应用场景实战

### 场景一：电商小程序提审被拒后的完整修复流程

一个自营电商小程序首次提审被拒，拒审原因：「服务类目与你提交的代码审核不一致，且订单流程无法完整体验」。完整修复流程：核对类目 → 补齐资质 → 修复体验问题 → 自测走查 → 重新提审。

```text
修复流程步骤：
1. 查看拒审原因：后台「版本管理-审核记录」查看拒审描述与截图
2. 类目核对：实际功能是「自营商品销售」，应选择「商家自营」类目（而非「电商平台」）
3. 资质补齐：商家自营类目上传营业执照；销售食品的商品类目补《食品经营许可证》
4. 体验修复：审核员反馈订单无法支付 —— 排查测试商户号配置，配置测试商品与测试支付环境
5. 自测走查：用测试账号完整走「浏览-加购-下单-支付-订单查询」全流程，录屏留存
6. 重新提审：更新版本号与版本说明，附上「已修复内容」说明，提交审核
```

```java
// 提审自测脚本（伪代码）：自动走查核心链路
public class ReviewSmokeTest {

    public static void main(String[] args) {
        // 1. 登录（测试账号）
        String token = login("review_test", "test123456");
        // 2. 浏览商品列表
        assertOk(get("/api/product/list", token));
        // 3. 商品详情
        assertOk(get("/api/product/detail?productId=1001", token));
        // 4. 加入购物车
        assertOk(post("/api/cart/add", token, "{productId:1001, count:1}"));
        // 5. 提交订单
        String orderId = post("/api/order/create", token, "{addressId:1}");
        // 6. 发起支付（测试环境 mock 支付成功）
        assertOk(post("/api/order/pay", token, "{orderId:" + orderId + "}"));
        // 7. 订单查询
        assertOk(get("/api/order/detail?orderId=" + orderId, token));
        System.out.println("核心链路自测通过，可提审");
    }
}
```

### 场景二：内容社区小程序上线前的合规红线自查

一个带 UGC 评论与虚拟会员功能的内容社区小程序，上线前做一轮红线自查：内容安全是否就绪、虚拟支付是否合规、隐私是否完整、版权是否干净，全部通过后再提审。

```text
红线自查清单（内容社区）：
1. UGC 内容安全 —— 评论/发帖已接入 msgSecCheck + 本地敏感词过滤（见 14.1）
2. 举报通道 —— 页面提供内容举报入口，举报内容进人工审核队列
3. 虚拟支付 —— 会员、付费阅读属虚拟商品：iOS 端不做支付引导，页面提示「iOS 用户请联系客服开通」
4. 隐私指引 —— 已声明收集昵称、头像、手机号及用途；已配置隐私弹窗与隐私政策入口
5. 注销入口 —— 「设置-注销账号」真实可用，注销后数据匿名化
6. 版权合规 —— 封面图、配图均为免费商用图库或自产，音乐资源有授权
7. 名称规范 —— 名称无商标侵权，与已上线小程序不重名
8. 文案合规 —— 无「最」「第一」等违禁词，会员权益描述与实际一致
```

```js
// 页面自查：确认隐私弹窗、举报、注销三个必备入口存在
const REQUIRED_ENTRIES = ['privacyDialog', 'reportButton', 'logoutEntry']

function selfCheck() {
  const missing = REQUIRED_ENTRIES.filter((entry) => !checkExists(entry))
  if (missing.length > 0) {
    console.error('提审前必查项缺失：', missing)
    return false
  }
  console.log('合规入口齐全，可以提审')
  return true
}
```

```text
场景落地清单：
1. 提审前准备「审核走查表」：类目、资质、功能链路、隐私、内容安全逐项打勾
2. 核心业务链路用测试账号完整走一遍并录屏，作为申诉与自查证据
3. 虚拟商品提前确定合规方案：iOS 端引导策略、Android 端支付接入
4. UGC 平台必须有内容安全检测与举报通道，这是审核硬性要求
5. 名称、Logo、素材提前做版权自查，避免上线后侵权投诉下架
6. 首次提审选在工作日早上，审核回复更快，方便及时修复
```

## 最佳实践与踩坑记录

### 最佳实践

1. 类目资质先行：注册后第一周就确定类目并提交资质审核，资质办理（尤其 ICP 证、办学许可等）周期长，别等提审才发现
2. 建立「审核走查表」：每次提审前按类目、功能、内容、隐私四类逐项自查，把踩过的坑写进表格持续迭代
3. 提审版本用真实测试数据：准备专用测试账号（含测试支付），确保审核员能完整走通核心流程
4. 首次提审前先在开发者工具「上传」后做一次体验版真机自测，体验版与提审版本一致
5. 隐私合规前置：隐私指引、隐私弹窗、注销入口在开发阶段就实现，不要等拒审再补
6. UGC 功能必须配套内容安全检测与举报通道，这是平台巡检重点
7. 拒审后逐条修复并记录，修复说明写清楚「改了什么、为什么合规」，提高二次通过率
8. 关注平台规则更新（如 iOS 虚拟支付政策、隐私新规），新规上线前主动适配

### 踩坑记录

```text
坑 1：类目选错导致功能无法提审，反复被拒
结论：做自营电商选了「工具」类目，每次提审都被判「服务类目与代码审核不一致」。
原因：类目选择没有覆盖实际业务，或类目与功能完全不匹配。
解法：按主营功能选类目，涉及交易的业务选电商相关类目并补资质；类目调整需重新提审。

坑 2：提审版本带测试数据/占位页面
结论：审核员打开看到「测试」「TODO」「功能开发中」内容，判定功能未完成。
原因：提审前没有清理测试数据与占位符，测试开关未关。
解法：提审前全局搜索 TODO/测试/占位等关键词；用正式文案替换；自测页面全部可访问。

坑 3：审核员无法完整体验支付流程
结论：拒审原因「订单支付流程无法完整体验」，订单提交后支付失败。
原因：正式商户号未开通或配置错误，测试环境支付回调没打通。
解法：提前开通微信支付商户号并完成关联；配置测试商品与回调；用测试账号完整走支付链路并录屏。

坑 4：隐私指引未填写，提审直接被打回
结论：审核反馈「小程序涉及用户隐私信息，但未设置用户隐私保护指引」。
原因：后台未填写用户隐私保护指引，或填写不完整（缺用途、缺联系方式）。
解法：后台完整填写指引（信息类型、用途、联系方式）；与实际代码调用保持一致。

坑 5：诱导分享文案被拒
结论：页面出现「分享 3 个好友解锁课程」「转发朋友圈领红包」等文案，被判诱导分享。
原因：用利益诱导用户分享传播，违反平台分享规范。
解法：删除诱导文案与分享解锁逻辑；分享使用微信原生转发能力，不做利益绑定。

坑 6：iOS 端虚拟支付违规被警告/下架
结论：iOS 用户在小程序内购买会员，被平台判定虚拟支付违规，功能被下架整改。
原因：虚拟商品（会员、虚拟币、在线课程）在 iOS 端使用了微信支付。
解法：iOS 端不展示虚拟商品支付入口，引导用户通过客服/其他合规渠道；Android 端正常接入微信支付。

坑 7：名称带知名品牌词被拒
结论：名称包含「XX旗舰店」「XX官方」等字样，被判侵权或误导。
原因：名称使用了他人商标或品牌词，或与实际主体不符。
解法：名称用自有品牌/主体全称；查重后确认无冲突；认证主体可申请名称保护。

坑 8：被拒后反复提审不修改，账号风险升级
结论：同一版本连续提交 3 次都被拒，账号收到平台警告，审核变慢。
原因：没有理解拒审原因就盲目重提，或只改了表面问题。
解法：逐条理解拒审原因并真正修复；修复说明写清楚改动点；必要时走申诉说明合规依据。

坑 9：上线后被巡检发现历史违规内容下架
结论：上线数周后平台巡检发现社区里有未检测的违规帖子，小程序被下架整改。
原因：UGC 发布接口没有全部接入内容安全检测（只检测了发帖，没检测评论/昵称/图片）。
解法：所有 UGC 入口（帖子、评论、昵称、图片）统一接入内容安全检测；历史存量内容做一次全量扫描清理。
```
