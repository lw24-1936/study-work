## 概述

本篇章汇总系统设计方向的高频面试题，围绕本知识库的全栈项目展开：电商小程序系统设计（商品、购物车、订单、支付、库存的完整链路）、消息推送设计（订阅消息 + 定时任务）、高并发设计（缓存、限流、削峰）与整体架构设计（小程序、后台、管理端三层）。系统设计题考察的是从需求到方案的完整思考能力，回答时遵循「明确需求 -> 画流程 -> 定数据结构 -> 解决关键问题 -> 考虑扩展与异常」的结构。

```text
面试考察点概览：
1. 电商链路 —— 商品/购物车/订单/支付/库存的数据流与状态机
2. 库存方案 —— 超卖防护、扣减时机、回滚释放
3. 消息推送 —— 订阅消息 + 定时任务 + 批量下发
4. 高并发 —— 缓存、限流、削峰、异步化
5. 架构设计 —— 三层架构、模块拆分、扩展演进
6. 异常与兜底 —— 幂等、对账、重试、监控
```

## 电商小程序系统设计

**问题 1：设计一个电商小程序的核心模块与数据流**

```text
回答：
1. 核心模块：商品（商品/SPU/SKU）、购物车、订单、支付、库存、售后、用户
2. 主链路：浏览商品 -> 加入购物车 -> 提交订单（锁库存）-> 支付 -> 扣减库存 -> 发货 -> 完成
3. 数据模型：SPU（商品）包含多个 SKU（规格），SKU 才有价格与库存；订单关联 SKU 快照
4. 状态流转：购物车（本地/服务端）-> 订单（待支付/已支付/已发货/已完成/已取消/已退款）
5. 关键设计点：金额服务端计算、库存与订单一致性、支付回调幂等、超时关单
6. 表结构：user、spu、sku、cart、order、order_item、pay_record、stock 八张核心表
7. 面试回答结构：先讲模块划分，再讲一条完整链路的数据流，最后讲每个环节的异常处理
```

```text
主链路时序：
用户 -> 商品列表/详情 -> 加入购物车 -> 确认订单页 -> 创建订单(锁库存)
     -> 微信支付 -> 回调更新订单 -> 扣减库存/发货 -> 完成/售后
```

**问题 2：购物车设计有哪些方案**

```text
回答：
1. 方案一：纯本地存储（wx.setStorage）—— 简单，但多端不同步、清缓存丢失
2. 方案二：服务端存储（Redis Hash：userId -> skuId -> 数量）—— 多端同步、可做优惠计算，需登录
3. 方案三：本地 + 服务端合并 —— 未登录用本地，登录后上传合并，体验最好
4. 数据要点：购物车项含 skuId、数量、勾选状态、失效标记（商品下架/价格变化）
5. 结算校验：提交订单时重新校验价格与库存，不信任购物车缓存的价格
6. 陷阱：商品改价后购物车价格要提示「价格有变动」，结算以服务端最新价为准
7. 面试常问：Redis 里购物车用什么结构 —— Hash，field 是 skuId，value 是数量，HINCRBY 增减
```

**问题 3：订单创建与超时关闭怎么设计**

```text
回答：
1. 创建订单：校验购物车/商品 -> 计算金额 -> 生成订单号 -> 锁库存 -> 插入订单与明细（同一事务）
2. 订单号：雪花 ID 或时间戳 + Redis 自增，全局唯一、不可预测（防遍历）
3. 超时关闭：待支付订单 30 分钟未支付自动取消并释放库存
4. 实现方案一：定时任务扫描（每分钟扫待支付超时订单）—— 简单，有延迟（分钟级）
5. 实现方案二：延迟队列（Redis ZSet score 为到期时间戳，线程轮询到期元素）—— 秒级精度
6. 实现方案三：RabbitMQ 延迟消息插件 —— 可靠但引入 MQ 依赖
7. 关闭订单要同时释放库存并通知前端（轮询或订阅消息）
8. 面试回答加分：说明「关单与释放库存必须幂等，防止重复释放」
```

```text
延迟队列实现思路（Redis ZSet）：
1. 下单时 ZADD delay_queue 到期时间戳 订单号
2. 后台线程每 1s ZRANGEBYSCORE delay_queue 0 now 取到期订单
3. 逐个查订单状态，仍待支付则关闭并释放库存
4. ZREM 移除已处理订单，处理过程加分布式锁防重复
```

**问题 4：库存设计如何防止超卖**

```text
回答：
1. 超卖本质：并发下多个请求同时读到库存 > 0 并都通过校验
2. 方案一（数据库乐观锁）：UPDATE sku SET stock = stock - n WHERE id = ? AND stock >= n，影响行数为 0 则失败
3. 方案二（Redis 预扣）：DECR 原子扣减，扣减成功才允许下单，异步同步回数据库
4. 方案三（数据库行锁/悲观锁）：SELECT ... FOR UPDATE 锁行再扣减 —— 简单但吞吐低
5. 扣减时机：下单锁库存（预占），支付成功真正扣减；超时/取消释放
6. 释放库存：超时关单、用户取消、支付失败回滚，必须释放（加回库存）
7. 一致性：Redis 扣减 + 数据库对账兜底，异常时以数据库为准修正
8. 面试回答加分：强调「条件更新 WHERE stock >= n」是防超卖的关键，不是先查再减
```

```sql
-- 防超卖核心 SQL：条件更新原子扣减
UPDATE sku SET stock = stock - #{num}, version = version + 1
WHERE id = #{skuId} AND stock >= #{num};
-- 返回影响行数，0 表示库存不足
```

**问题 5：支付与订单状态一致性如何保证**

```text
回答：
1. 权威来源：微信支付回调（验签 + 幂等更新）是「已支付」的权威来源
2. 本地订单状态机：待支付 -> 已支付（回调触发）-> 已发货 -> 已完成；待支付 -> 已取消（超时关单）
3. 查单兜底：前端支付后查单，本地状态未更新时后台主动调用微信查单接口确认
4. 对账修正：定时任务对比本地订单与微信账单/查单结果，修正不一致状态
5. 金额校验：回调金额与订单金额不一致时告警并进入人工处理，不自动发货
6. 幂等要求：同一订单重复回调、重复查单、重复对账都不能产生副作用
7. 面试回答加分：把「回调权威 + 查单兜底 + 对账修正」称为支付一致性三保险
```

**问题 6：电商系统的异常场景如何兜底**

```text
回答：
1. 下单失败（库存不足/价格变化）：提示原因，购物车重新结算
2. 支付失败/取消：订单保持待支付，可重试支付（用同一订单号重新 requestPayment）
3. 回调丢失：查单兜底 + 对账修正，用户侧显示「支付确认中」
4. 发货失败：订单状态机支持重试发货，记录失败原因
5. 退款异常：退款单状态机 + 重试 + 人工介入入口
6. 监控告警：支付成功率、下单成功率、库存异常、关单延迟等指标监控
7. 面试回答重点：每个环节都要回答「失败了怎么办」，体现系统设计完整性
```

## 消息推送设计

**问题 1：电商场景的消息推送整体方案怎么设计**

```text
回答：
1. 消息类型：订单类（支付成功、发货、退款）、营销类（优惠券、活动）、提醒类（预约、到期）
2. 通道：订阅消息（小程序主动触达，需用户授权）、短信（强提醒，付费）、站内信（小程序内消息中心）
3. 触发方式：事件触发（支付回调里发发货通知）+ 定时触发（定时任务扫描到期数据批量下发）
4. 配额管理：一次性订阅消息按用户授权次数管理，服务端记录剩余次数
5. 发送链路：业务事件 -> 消息服务（组装模板）-> 队列削峰 -> 调用微信 subscribeMessage.send
6. 失败处理：失败码记录（43101 未授权、47003 参数错误），可重试的进重试队列
7. 面试回答结构：通道选择 -> 触发方式 -> 发送链路 -> 失败处理 -> 频率控制
```

**问题 2：定时任务批量发消息怎么设计**

```text
回答：
1. 任务类型：优惠券到期提醒（到期前 24h）、生日祝福、活动开奖、订单超时提醒
2. 实现：Spring @Scheduled 定时扫描目标用户（分页拉取，避免一次加载全部）
3. 批量发送注意：微信接口有频率限制，必须分批 + 限速（如每秒 N 条）+ 失败重试
4. 任务状态管理：任务表记录批次、进度、成功/失败数，支持重跑与断点续传
5. 幂等：同一用户同一模板同一业务单号只发一次（业务号唯一约束）
6. 分布式部署下定时任务防重复执行：分布式锁（Redis SETNX）保证单实例执行
7. 面试常问：几百万用户怎么发 —— 分页拉取 + 线程池并发 + 限速器控制，失败进重试队列
```

```text
定时任务批量发送流程：
1. 任务调度（分布式锁防重） -> 2. 分页查询目标用户（每页 1000）
3. 组装模板参数 -> 4. 限速发送（每秒 20 条） -> 5. 记录结果（成功/失败码）
6. 失败重试（最多 3 次，退避） -> 7. 任务汇总报告（成功数/失败数/耗时）
```

**问题 3：消息推送如何防打扰与控频**

```text
回答：
1. 订阅授权即同意，但授权不代表可以无限发：一次性订阅用完即止，重复授权引导要有节制
2. 频控策略：同一用户同一模板每日上限（如 3 条）、全局每日上限（如 5 条）
3. 时段控制：营销类消息只在 9:00-21:00 发送，避免深夜打扰
4. 退订机制：提供消息设置页（通知开关），尊重用户选择
5. 分群发送：按用户活跃度、消费偏好圈选人群，避免全员轰炸
6. 平台红线：高频无价值推送会被投诉与平台处罚，宁可少发不可滥发
7. 面试回答加分：提到「推送价值衡量」—— 用点击率、转化率评估推送 ROI 并持续调优
```

**问题 4：消息中心（站内信）怎么设计**

```text
回答：
1. 场景：无订阅授权的营销信息、订单流转记录、系统公告
2. 表设计：message（消息：标题/内容/类型/跳转链接）+ user_message（用户消息：user_id/message_id/已读状态）
3. 读取：列表分页 + 未读数角标（Redis 计数）
4. 标记已读：批量已读接口，未读数 INCR/DECR 原子更新
5. 与订阅消息配合：重要事件（退款结果）用订阅消息主动触达 + 站内信留痕
6. 清理策略：历史消息定期归档，控制表数据增长
7. 面试常问：未读数怎么存 —— 用户维度 Redis 计数，读消息时同步更新
```

**问题 5：推送链路的高可用与重试怎么设计**

```text
回答：
1. 队列削峰：事件入 MQ（RabbitMQ/Kafka），消费者异步发送，避免同步阻塞下单链路
2. 重试机制：发送失败按错误码分类 —— 可重试（网络、限流）进重试队列（指数退避），不可重试（参数错误）进死信/人工
3. 幂等：消息带业务唯一键，消费者去重，保证「至少一次」语义下不重复影响
4. 降级：微信接口异常时暂停发送（熔断），恢复后补发
5. 监控：发送成功率、队列积压量、失败码分布告警
6. 面试回答加分：说明「推送是异步旁路，不能阻塞核心交易链路」
```

## 高并发设计

**问题 1：高并发场景的通用设计手段有哪些**

```text
回答：
1. 缓存：读多写少数据放 Redis，降低数据库压力（商品详情、配置）
2. 限流：保护系统不被突发流量打垮（令牌桶/漏桶/计数器），返回友好提示
3. 削峰：请求先入队列异步处理（秒杀下单、批量任务），平滑波峰
4. 异步化：非核心链路（通知、日志、积分）异步执行，缩短响应时间
5. 分库分表：数据量大时按用户/订单分片，读写分离
6. 多级缓存：本地缓存（Caffeine）+ Redis + 数据库，逐级降级
7. 容量规划：压测确定单机 QPS 上限，按峰值估算实例数
8. 面试回答结构：从「入口（限流）- 中间（缓存/异步）- 存储（分片/读写分离）」三层组织
```

**问题 2：限流方案怎么选**

```text
回答：
1. 计数器（固定窗口）：简单，但窗口边界有双倍流量漏洞
2. 滑动窗口：Redis ZSet 记录时间戳，统计窗口内请求数 —— 精确但占内存
3. 漏桶：请求以恒定速率流出，适合保护下游（削峰填谷）
4. 令牌桶：桶内存令牌，突发可消费存量令牌，允许一定突发 —— 最常用（Guava RateLimiter）
5. 分布式限流：Redis + Lua 脚本实现令牌桶/滑动窗口，多实例共享计数
6. 限流粒度：接口级（登录、支付）、用户级、IP 级；超限返回 429 与提示
7. 面试常问：限流与熔断的区别 —— 限流控制流量进入，熔断在下游故障时快速失败保护自己
```

```lua
-- Redis 滑动窗口限流（Lua 脚本思路）
-- 每次请求：ZREMRANGEBYSCORE key 0 (now - window) 清理过期
-- 统计 ZCARD key；小于阈值则 ZADD 并返回 1（放行），否则返回 0（拒绝）
```

**问题 3：秒杀/抢购场景怎么设计**

```text
回答：
1. 分层拦截：静态页 CDN、商品详情缓存、按钮置灰（前端限流）
2. 入口限流：接口级限流 + 用户维度限频（一人一次，幂等键防重复提交）
3. 库存预扣：Redis DECR 原子扣减，扣减成功才进入下单流程
4. 异步下单：秒杀请求入 MQ，消费者串行/批量创建订单，DB 由 MQ 削峰保护
5. 结果查询：秒杀成功返回 token/排队号，前端轮询查询结果
6. 超时未支付释放库存：与普通订单同一套超时关单机制
7. 防作弊：同一设备/账号限购、IP 风控、黑名单
8. 面试回答重点：库存扣减时机（Redis 预扣 + DB 最终一致）、削峰（MQ）、防重复（幂等）
```

**问题 4：缓存与数据库一致性在电商中的实践**

```text
回答：
1. 商品详情：读多写少 —— 主动更新（改价后删缓存）+ 短 TTL + 定时刷新兜底
2. 库存：强一致需求 —— 以数据库为准，Redis 只做预扣与热销计数，对账修正
3. 购物车：Redis 为主，结算时以 DB 商品最新价校验
4. 通用原则：Cache Aside（先更库再删缓存），删除失败用延迟双删/消息重试
5. 容忍度：不同数据一致性要求不同，先定 SLA 再选方案
6. 面试常问：为什么先更库再删缓存 —— 并发读回填旧值概率最小，配合延迟双删可消除窗口
```

**问题 5：数据库层面如何支撑高并发**

```text
回答：
1. 索引优化：EXPLAIN 定位慢查询，覆盖索引减少回表
2. 读写分离：主库写、从库读，读多写少场景大幅扩展读能力（注意主从延迟）
3. 分库分表：订单/用户按 id 取模或范围分片；分片键要按业务查询维度选择
4. 连接池：合理配置最大连接数（HikariCP），防止连接耗尽
5. 事务优化：缩短事务时间、避免事务内远程调用与长查询
6. 冷热分离：历史订单归档到冷表/数仓，热表保持轻量
7. 面试常问：什么时候需要分表 —— 单表数据量千万级以上或写入 QPS 高，先做索引与归档再考虑分片
```

**问题 6：异步化改造的典型场景**

```text
回答：
1. 下单链路：创建订单（同步）-> 发送通知/积分/优惠券核销（MQ 异步）
2. 支付回调：更新订单（同步核心）-> 发货流程、消息推送、对账（异步）
3. 批量任务：数据导出、报表生成、消息群发（异步任务 + 进度查询）
4. 削峰：秒杀请求、预约高峰（先入队后处理）
5. 实现选型：轻量用 Redis List/Stream + 线程池；重量级用 RabbitMQ/Kafka
6. 注意事项：异步任务要幂等、可重试、有监控（积压、失败率）
7. 面试回答加分：说明「异步的前提是业务可最终一致，强一致链路不能异步」
```

**问题 7：如何评估系统容量与压测**

```text
回答：
1. 评估方法：峰值 QPS = 日活用户 x 人均请求数 / 秒数 x 峰值系数（通常 3-5 倍均值）
2. 单机能力：压测（JMeter/压测云）得出单实例 QPS 与 RT，作为扩容依据
3. 扩容模型：无状态服务水平扩展（Nginx 负载均衡）；有状态（会话/库存）需设计状态外置
4. 依赖容量：数据库连接数、Redis 内存、MQ 吞吐都要一起评估
5. 压测关注点：RT 分位数（P99）、错误率、资源使用率（CPU/内存/连接）
6. 兜底：容量不足时的降级预案（限流、关非核心功能、静态化）
7. 面试常问：QPS 5000 需要几台机器 —— 先压测单机能力，再按峰值与冗余系数估算
```

## 架构设计

**问题 1：小程序全栈项目的整体架构怎么描述**

```text
回答：
1. 三层架构：小程序（C 端用户入口）+ SpringBoot 后台（业务 API）+ Vue 管理端（B 端运营）
2. 数据层：MySQL（业务数据）+ Redis（缓存/会话/队列）+ 对象存储（图片等静态资源走 CDN）
3. 基础设施：Nginx（反代 + 静态 + HTTPS）、Docker（部署）、CI/CD（自动化流水线）
4. 微信侧依赖：登录（code2session）、支付（JSAPI）、订阅消息、内容安全
5. 通信规范：小程序与后台走 HTTPS JSON API，token 鉴权；管理端同域反代或 CORS
6. 监控体系：日志（ELK）、指标（Prometheus + Grafana）、告警、小程序后台性能面板
7. 面试回答结构：画一张三层拓扑图，逐层讲职责、关键依赖、安全与监控
```

```text
架构拓扑：
小程序(微信内) ──HTTPS/JSON──┐
管理端(Vue3+ElementPlus) ──HTTPS──┼──> Nginx ──> SpringBoot 服务(集群)
                                  │              ├── MySQL（业务数据/订单/用户）
                                  │              ├── Redis（缓存/会话/限流/队列）
                                  └── 微信开放能力（登录/支付/订阅消息/内容安全）
```

**问题 2：如何拆分业务模块**

```text
回答：
1. 单体优先：中小项目先做模块化单体（按业务分包：user、product、order、pay、message），避免过度设计
2. 模块边界：每个模块内聚自己的实体、Service、Controller，模块间通过 Service 接口调用
3. 拆微服务时机：团队规模、发布频率、模块间耦合度成为瓶颈时再拆（如订单与支付拆开）
4. 微服务配套：服务注册发现（Nacos）、网关（Spring Cloud Gateway）、分布式事务（Seata）成本高
5. 面试常问：什么时候不该上微服务 —— 单体能满足时上微服务是负资产（运维、调试、事务成本）
6. 本知识库实践：模块化单体 + 独立 job 模块（定时任务）即可覆盖绝大多数业务
```

**问题 3：管理端（Vue）与小程序端的职责与数据边界**

```text
回答：
1. 小程序端：C 端用户体验 —— 浏览、下单、支付、售后、个人中心
2. 管理端：B 端运营 —— 商品管理、订单处理、用户管理、数据看板、配置管理
3. 数据边界：两端共用同一后台 API，但接口权限不同（管理端用 RBAC 权限码控制）
4. 账号体系分离：小程序用户（openid 登录）与管理端运营账号（账号密码登录）是两套体系
5. 敏感操作审计：管理端的商品改价、退款审核等操作记录操作人与时间
6. 面试常问：管理端接口怎么防误操作 —— 权限校验 + 操作审计 + 二次确认 + 灰度发布
```

**问题 4：系统如何应对业务增长演进**

```text
回答：
1. 第一阶段（单机）：单体应用 + 单库，Redis 缓存热点，满足早期业务
2. 第二阶段（扩展）：应用集群 + Nginx 负载均衡，读写分离，静态资源上 CDN
3. 第三阶段（拆分）：按业务拆微服务，消息队列解耦，分库分表
4. 演进原则：按瓶颈演进，不提前设计；每一步都保持可回滚
5. 关键能力前置：日志与监控从第一天就建设，幂等与对账是扩展的基础
6. 面试回答加分：强调「架构演进跟着业务与痛点走」，而不是一步到位微服务
```

**问题 5：接口幂等性在系统中的实现**

```text
回答：
1. 场景：下单（重复提交）、支付回调（重复通知）、退款（重复申请）、领券（重复领取）
2. 方案一：唯一约束 —— 订单号、业务单号建唯一索引，重复插入报错被捕获忽略
3. 方案二：幂等键 —— 请求头/参数带 Idempotency-Key，Redis SETNX 记录，已存在直接返回上次结果
4. 方案三：状态机校验 —— 订单状态流转判断（已支付订单拒绝再次支付回调更新）
5. 组合使用：数据库唯一约束兜底 + Redis 幂等键拦截 + 状态机校验
6. 面试常问：幂等键怎么生成 —— 前端生成 UUID 或后端按业务要素（userId+skuId）hash
7. 陷阱：幂等键存储要设置过期时间，避免长期占用 Redis 内存
```

**问题 6：系统的可观测性怎么建设**

```text
回答：
1. 日志：结构化日志（JSON）+ 全链路 traceId 贯穿请求（MDC 透传），集中收集（ELK/Loki）
2. 指标：业务指标（下单量、支付成功率、退款率）+ 系统指标（QPS、RT、CPU、内存、GC）
3. 追踪：慢接口链路分析（SkyWalking/OpenTelemetry），定位跨服务耗时
4. 告警：错误率、RT 超阈值、队列积压、磁盘水位，分级通知（短信/企微/钉钉）
5. 小程序侧：微信后台性能面板（启动耗时、JS 错误）、wx.reportMonitor 自定义监控
6. 排障流程：告警 -> 看大盘 -> 看日志（traceId）-> 定位代码 -> 修复 -> 复盘
7. 面试回答加分：提到「没有监控的发布等于盲飞」，监控建设与功能开发同步
```

**问题 7：系统设计题的标准答题框架是什么**

```text
回答：
1. 澄清需求：用户量、QPS、数据量、一致性要求、可用性要求（先问清楚再设计）
2. 画主流程：核心用例的端到端时序（谁调谁、数据流方向）
3. 定数据模型：核心表结构与关系，关键字段（状态机、唯一约束）
4. 解决关键问题：并发（超卖）、一致性（支付回调）、性能（缓存）、可靠性（重试）
5. 异常与兜底：每个环节失败怎么办，幂等与对账
6. 扩展与演进：容量估算、水平扩展、拆分路径
7. 收尾：指出取舍（一致性 vs 性能、复杂度 vs 收益），展示工程判断力
```

## 面试重点总结

```text
高频考点编号：
1. 电商链路：商品(SPU/SKU) -> 购物车(Redis Hash) -> 订单(状态机) -> 支付(回调权威) -> 库存(条件更新)
2. 防超卖：UPDATE ... WHERE stock >= n 条件更新是核心，Redis 预扣 + DB 对账
3. 关单：定时任务扫描 / Redis 延迟队列，关单与释放库存必须幂等
4. 推送：事件触发 + 定时任务双通道，MQ 削峰，配额管理，失败码分类重试
5. 高并发：缓存（读多写少）+ 限流（令牌桶/滑动窗口）+ 削峰（MQ 异步）+ 分库分表
6. 一致性三保险：回调权威 + 查单兜底 + 对账修正；幂等键 + 唯一约束 + 状态机
7. 架构：模块化单体优先，三层（小程序/后台/管理端）职责与权限分离
8. 答题框架：澄清需求 -> 主流程 -> 数据模型 -> 关键问题 -> 异常兜底 -> 扩展演进
```

```text
设计题避坑清单：
1. 不要上来就画微服务，先确认规模与瓶颈
2. 不要只讲正常流程，异常处理（失败/重试/对账）占一半分数
3. 不要忘记数据模型，表结构与状态机是设计题的核心产出
4. 不要忽略幂等，支付/下单/退款类场景必谈幂等
5. 每讲一个方案都要说清取舍（复杂度、成本、一致性）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 所有写接口（下单、回调、退款、领券）先设计幂等方案：唯一约束 + 幂等键 + 状态机三重保障
2. 金额链路统一「分」单位，前端展示层再转换，全链路不出现浮点运算
3. 库存扣减用条件更新（WHERE stock >= n），禁止「先查后减」的非原子操作
4. 支付一致性用三保险：回调权威更新 + 前端查单兜底 + 定时对账修正
5. 消息推送走队列异步，业务主链路（下单/支付）不因推送失败而失败
6. 高并发先做缓存与限流，再考虑分库分表；每一步演进保留回滚方案
7. 日志从第一天带 traceId 结构化输出，监控告警与功能同步上线
8. 系统设计答题永远以「需求澄清 -> 主流程 -> 数据模型 -> 异常兜底」为主线

### 踩坑记录

坑 1：先查库存再扣减导致超卖
结论：秒杀场景库存显示有货，实际超卖了几十单。
原因：并发下多个请求同时 SELECT 到 stock > 0，都通过校验后各自 UPDATE，无原子性。
解法：改为条件更新 UPDATE ... WHERE stock >= n，影响行数为 0 即失败；高并发场景加 Redis 预扣。

坑 2：支付回调重复处理导致订单状态错乱
结论：同一订单回调收到多次，发货通知发了多遍，状态被覆盖。
原因：回调未做幂等处理，每次通知都直接更新状态。
解法：回调处理前查订单状态（已支付则直接返回 SUCCESS），更新条件带状态约束，业务单号唯一约束。

坑 3：订单超时关单与支付回调竞态
结论：用户刚好在超时瞬间支付成功，订单却被关闭并释放了库存。
原因：关单任务与支付回调并发执行，未做状态互斥。
解法：关单用条件更新（UPDATE order SET status=已取消 WHERE id=? AND status=待支付），回调同理；失败的一方以另一方结果为准，对账兜底。

坑 4：定时任务多实例重复执行
结论：优惠券到期提醒重复发送，用户收到多条相同消息。
原因：集群部署下每个实例都执行 @Scheduled 任务。
解法：任务执行前获取 Redis 分布式锁（SETNX + 过期时间），持锁实例执行，执行完释放；任务表记录批次进度。

坑 5：批量推送瞬时打爆微信接口
结论：一次性给 10 万用户发订阅消息，触发微信限流，大量 45009 报错。
原因：未限速批量调用，超出接口频控。
解法：批量任务分页拉取 + 限速器（如每秒 20 条）+ 失败进重试队列，任务拆分小批次执行。

坑 6：缓存删除失败导致数据长期不一致
结论：商品改价后用户仍看到旧价格，持续了很长时间。
原因：先更库后删缓存的删除操作失败（Redis 抖动），无重试机制。
解法：删除失败进消息队列重试；或延迟双删；热点数据配合短 TTL 兜底。

坑 7：秒杀直接操作数据库被打垮
结论：秒杀开始时数据库连接耗尽，整个系统不可用。
原因：所有请求同步查库扣库存，无缓存、无队列削峰。
解法：Redis 预扣库存拦截大部分请求，下单请求入 MQ 异步处理，DB 只承受队列消费的流量。

坑 8：订单号用自增 ID 被遍历
结论：通过订单号顺推可遍历他人订单数据。
原因：订单号用数据库自增主键，可预测。
解法：订单号用雪花 ID/时间戳+随机数生成，业务展示与主键分离；接口层再做归属校验。

坑 9：通知发送失败阻塞主流程
结论：支付成功后接口响应很慢，甚至因推送异常导致回调失败。
原因：发送订阅消息同步写在回调处理里，微信接口慢/超时拖累主链路。
解法：回调只更新订单状态（同步、快速），通知、积分等旁路逻辑进 MQ 异步执行。

坑 10：上线后没有监控，故障定位耗时数小时
结论：线上订单支付失败率升高，靠用户投诉才发现，排查无从下手。
原因：未建设指标与告警，日志无 traceId 无法串联链路。
解法：上线前接入 Prometheus + Grafana 告警（错误率/RT/队列积压），日志统一 traceId，监控大盘常态化巡检。
