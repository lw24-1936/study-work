## 概述

本篇章覆盖小程序进阶面试的高频考点：性能优化（分包加载、setData 优化、首屏提速）、登录流程（wx.login + code2session + token 会话）、微信支付（统一下单 + requestPayment + 回调）、订阅消息（前端订阅 + 服务端下发）以及安全（内容检测、接口安全、防刷）。这些内容直接对应真实业务闭环，面试中通常以「流程串讲 + 细节追问 + 异常处理」的形式考察。

```text
面试考察点概览：
1. 性能优化 —— 分包加载、setData 瘦身、首屏启动优化
2. 登录流程 —— wx.login、code2session、token 会话保持
3. 支付流程 —— 统一下单、requestPayment、支付回调
4. 订阅消息 —— 一次性订阅、长期订阅、服务端下发
5. 内容安全 —— msgSecCheck 检测、审核规范
6. 接口安全 —— 防刷、防重放、HTTPS 与签名
```

## 性能优化与分包加载

**问题 1：小程序包体积限制是什么，分包如何解决**

```text
回答：
1. 主包上限 2MB（未压缩代码），整体上限 20MB（2021 年后调整为主包 2MB + 总包 20MB）
2. 分包（subPackages）将业务拆分为主包 + 多个分包，分包只在进入对应页面时加载
3. 主包放公共代码（app.js/app.json、公共组件、tabBar 页面），分包放独立业务（如商家、用户中心）
4. 分包加载规则：进入分包页面时下载分包，不影响主包启动速度
5. 独立分包（independent）不依赖主包即可运行，适合活动页等轻量场景
6. 分包预下载（preloadRule）在特定页面出现时预下载目标分包，平衡加载时间
7. 面试常问：哪些资源放主包 —— 启动首屏必需、公共依赖、tabBar 相关
```

```json
{
  "pages": ["pages/index/index", "pages/cart/cart"],
  "subPackages": [
    { "root": "packageA", "pages": ["pages/shop/shop"] },
    { "root": "packageB", "pages": ["pages/user/user"] }
  ],
  "preloadRule": {
    "pages/index/index": { "network": "all", "packages": ["packageA"] }
  }
}
```

**问题 2：setData 性能优化有哪些手段**

```text
回答：
1. 只更新变化的字段：this.setData({ 'list[0].name': 'x' }) 用数据路径局部更新
2. 合并多次 setData：多个字段一次调用，减少通信次数
3. 避免放大数据：不要整体回传大数组，用路径或字段级更新
4. 避免高频 setData：滚动、拖拽等高频场景用节流/防抖或 WXS 响应式处理
5. 避免在 setData 中放大量一次性数据：超过 256KB 会明显卡顿，考虑分页或按需加载
6. 无关数据不放 data：仅视图需要的才 setData，减少渲染层 diff 成本
7. 面试加分：提到 setData 是异步渲染，同帧多次调用会合并，回调可用于渲染后处理
```

```js
// 局部更新示例：只更新第 3 项的名称
this.setData({ 'list[2].name': '新名称' });
// 合并更新
this.setData({ a: 1, b: 2, c: 3 });
```

**问题 3：如何优化小程序首屏启动速度**

```text
回答：
1. 代码层面：控制主包体积、按需注入（lazyCodeLoading: 'requiredComponents'）、去掉未使用的组件与库
2. 渲染层面：首屏只渲染关键内容，图片懒加载（image lazy-load）、骨架屏占位
3. 数据层面：首屏接口并行请求、优先渲染缓存数据再请求刷新、数据预拉取
4. 启动阶段：onLaunch 中避免阻塞操作（大 JSON 解析、同步存储大量数据）
5. 分包层面：首屏页面放主包，非首屏业务全部拆分包并按需预下载
6. 衡量指标：启动耗时（小程序后台性能面板）、首屏渲染耗时（Performance 面板）
7. 面试常问：如何定位启动慢 —— 先用体验评分/性能面板找耗时项，再针对性优化
```

**问题 4：小程序性能优化的常见指标与工具**

```text
回答：
1. 指标：启动耗时、页面渲染耗时、setData 次数与数据量、分包加载耗时、内存占用
2. 工具：微信开发者工具「性能」面板、真机调试、体验评分（后台「体验评分」功能）
3. 后台「运维中心 - 性能监控」可看线上启动、请求、渲染分布
4. 内存监控：wx.getPerformance() 获取性能数据；大列表注意 onReachBottom 分页
5. 陷阱：模拟器性能与真机差异大，性能问题必须真机验证
```

**问题 5：长列表如何渲染才不卡**

```text
回答：
1. 分页加载：onReachBottom 触底加载下一页，数据累积控制（如 20 条/页）
2. 避免一次性 setData 整个列表：新数据 append 到数组尾部用路径更新
3. 图片懒加载：image 组件 lazy-load 属性，滚动到可视区才加载
4. 复杂列表项抽成组件并做数据隔离，避免整页重渲染
5. 极致场景用虚拟列表（只渲染可视区），小程序可通过 scroll-view 自定义实现
6. 陷阱：不要用 setData 回传「全量 + 新增」的合并数组，应使用 path 追加
```

**问题 6：分包加载失败或超时怎么处理**

```text
回答：
1. 分包首次进入会触发下载，弱网下可能失败，页面会进入 fail 状态
2. 可在进入分包页面前用 wx.preloadSubpackage 预加载并监听状态
3. 处理策略：加载中展示 loading，失败提示重试；核心链路分包预下载降低失败率
4. 分包之间不能相互 require 资源（代码隔离），公共代码必须放主包
5. 陷阱：分包页面里引用了主包不存在的文件，真机会报「文件不存在」类错误，需静态检查
```

**问题 7：页面渲染卡顿的定位思路是什么**

```text
回答：
1. 先判断是 JS 逻辑卡顿还是渲染卡顿：用 Performance 面板看 Main 线程 vs 渲染线程耗时
2. 常见渲染卡顿原因：setData 数据过大/过于频繁、复杂布局（大量阴影/渐变/圆角）、图片尺寸过大
3. 常见逻辑卡顿原因：大循环、同步存储读写、JSON 解析大对象、正则回溯
4. 定位手段：分段 console.time 打点、真机 Performance、二分注释法
5. 优化优先级：先砍 setData 频率与数据量，再简化样式与图片，最后考虑重构组件结构
```

## 登录与会话保持

**问题 1：完整描述小程序登录流程**

```text
回答：
1. 小程序端调用 wx.login() 获取临时凭证 code（5 分钟有效、一次性）
2. 小程序将 code 通过 wx.request 发送到自有后台（SpringBoot）
3. 后台调用微信接口 code2session（appid + secret + code）换取 openid、session_key（unionid 视情况）
4. 后台用 openid 查用户表，不存在则创建用户，生成自己的登录凭证（JWT token）
5. 后台返回 token 给小程序，小程序存储（wx.setStorageSync）并在后续请求头携带
6. 后续请求后台校验 token 识别用户身份，session_key 保存在服务端用于解密数据/推送
7. 登录态失效（401）时重新走 wx.login 换新 token，静默续期
```

```text
时序：
小程序              后台                微信
wx.login() → code
  code ──────────────→  code2session(code)
                       ← openid/session_key
                       生成 token
  ← token ────────────
存 token，后续请求带 Authorization
```

追问：code 为什么不能给前端直接用？

```text
回答：
1. code 换 openid/session_key 需要 appid + AppSecret，AppSecret 只能存在服务端
2. 前端拿不到 openid 也拿不到 session_key，避免敏感身份数据泄露
3. 服务端统一管理 code2session 调用，可做日志、限流、风控
4. 安全性：openid 是业务系统的用户唯一标识，绝不能下发到前端由前端自报身份
```

**问题 2：session_key 有什么用，为什么不能下发前端**

```text
回答：
1. session_key 是微信下发的会话密钥，用于解密手机号（getPhoneNumber 的 encryptedData）等敏感数据
2. 只能保存在服务端，与 openid 关联存储（Redis），过期时间与微信保持一致
3. 一旦泄露，攻击者可解密用户手机号等敏感信息，属于高危数据
4. 业务系统用户身份用自己签发的 token（JWT），session_key 仅用于微信侧数据解密与推送
5. 陷阱：session_key 每次 code2session 都会更新，旧 key 失效，必须每次登录后重新获取
```

**问题 3：JWT 与 session 两种登录态方案怎么选**

```text
回答：
1. JWT：无状态，token 自包含用户信息与过期时间，服务端不用存会话；缺点是无法主动失效（除非黑名单）
2. Session：服务端存会话（Redis + sessionId），可主动踢人、控制失效；缺点是需要会话存储
3. 小程序场景推荐：JWT + Redis 黑名单/版本号，兼顾无状态与可控失效
4. token 过期处理：前端 401 拦截 -> 重新 wx.login 换 token -> 重放原请求（避免用户重操作）
5. 安全要点：token 存小程序本地缓存（非 storage 也可以，但注意 XSS 面小），HTTPS 传输
6. 面试常问：JWT 泄露了怎么办 —— 缩短有效期 + refresh token 机制 + 服务端黑名单
```

**问题 4：登录态过期如何无感续期**

```text
回答：
1. 方案一：token 有效期较短（如 2 小时），前端拦截 401 后静默调用 wx.login 重新登录并重放请求
2. 方案二：access token + refresh token，refresh token 长期有效，换取新 access token
3. 方案三：后台在 token 快过期时返回新 token（响应头或字段），前端更新本地
4. 关键：续期逻辑必须幂等，多请求并发 401 时只触发一次重新登录（加锁）
5. 陷阱：静默登录失败（网络/微信异常）要给出明确提示而不是无限重试
```

```js
// 并发 401 只触发一次重新登录
let reloginPromise = null;
const relogin = () => {
  if (!reloginPromise) {
    reloginPromise = new Promise((resolve, reject) => {
      wx.login({ success: (r) => doLogin(r.code).then(resolve).catch(reject).finally(() => { reloginPromise = null; }) });
    });
  }
  return reloginPromise;
};
```

**问题 5：unionid 与 openid 有什么区别**

```text
回答：
1. openid 是用户在某个小程序下的唯一标识，不同小程序（同一主体下不同 appid）openid 不同
2. unionid 是同一微信开放平台账号下多个应用（小程序/公众号/App）共用的唯一标识
3. 获取 unionid：已绑定微信开放平台账号的主体，code2session 时返回 unionid
4. 业务场景：多端打通（小程序 + 公众号 + App 同一用户体系）必须依赖 unionid
5. 陷阱：未绑定开放平台或用户未关注/未授权时可能拿不到 unionid，需兼容
```

**问题 6：用户信息获取（头像昵称）的现行方案是什么**

```text
回答：
1. wx.getUserInfo 已废弃（2021 年后新版本不再返回真实头像昵称），不能用它做实名收集
2. 现行方案：button open-type="chooseAvatar" 选择头像，input type="nickname" 输入昵称
3. 用户授权 getUserProfile 只能拿到「微信用户」的灰色头像与「微信用户」昵称，不再有真实数据
4. 手机号获取：button open-type="getPhoneNumber"，后台用 session_key 解密 code 换取手机号
5. 注意隐私合规：收集用户信息需在小程序后台配置《用户隐私保护指引》，弹窗授权
6. 面试常问：为什么 getUserInfo 废弃 —— 平台治理用户隐私，禁止默认收集
```

**问题 7：登录流程中常见的异常情况有哪些**

```text
回答：
1. wx.login 失败：微信版本过低、网络异常 —— 提示重试
2. code2session 失败：appid/secret 错误、code 过期或已使用 —— 重新 wx.login 换新 code
3. 后台服务不可用：登录接口超时 —— 前端 loading 与重试策略
4. session_key 过期：解密手机号失败 —— 重新登录后重试解密
5. token 校验失败（伪造/过期）—— 401 处理与重新登录
6. 多端同时登录：同一账号多设备 —— 服务端支持多 token 或互踢策略（业务决定）
7. 回答加分：登录失败要有兜底提示，不能静默卡死在 loading
```

## 支付流程

**问题 1：完整描述小程序微信支付流程**

```text
回答：
1. 小程序端用户点击支付，携带订单信息（订单号、金额）调用后台「统一下单」接口（自建接口）
2. 后台校验订单（金额、状态、用户身份），调用微信支付 API v3 的 JSAPI 下单接口（appid + mchid + openid + 金额）
3. 微信返回 prepay_id（预支付交易会话标识），后台用它生成签名支付参数（timeStamp、nonceStr、package、signType、paySign）
4. 后台把支付参数返回小程序，小程序调用 wx.requestPayment 拉起收银台
5. 用户输入密码确认支付，微信异步回调后台「支付结果通知」接口（通知地址需配置）
6. 后台收到回调验签解密后更新订单状态，返回成功应答（否则微信会重复通知）
7. 前端支付结果以 wx.requestPayment 的 success/fail 为准 + 主动查询订单状态兜底
```

追问：prepay_id 和 paySign 是谁生成的？

```text
回答：
1. prepay_id 由微信支付统一下单接口返回，生成前提是后台正确传 appid/mchid/openid/金额
2. paySign 由后台用商户私钥对 timeStamp、nonceStr、package（prepay_id=xxx）签名生成
3. 商户私钥（APIv3 密钥）绝不能出现在小程序端，签名必须服务端完成
4. 小程序端只负责把后台返回的参数原样传给 wx.requestPayment
```

**问题 2：为什么需要支付回调，回调失败怎么办**

```text
回答：
1. 支付回调（notify_url）是微信异步通知后台「支付成功」的权威渠道，用于更新订单状态、发货/发券
2. 回调失败场景：后台未应答成功（返回非 200 或应答格式错误）、网络问题、验签失败
3. 微信会按策略重试回调：频率为 15s/15s/30s/3m/10m/20m/30m/30m/30m/60m/3h/3h/3h/6h/6h，共 24 次
4. 后台处理要求：验签 + 解密（AES-GCM）+ 幂等处理（同一订单重复通知只处理一次）
5. 成功应答：返回 200 且 body 为 {"code":"SUCCESS"}，否则微信继续重试
6. 兜底：对账任务定时查询微信订单状态，与本地订单对比修正不一致数据
```

```text
回调应答格式（成功）：
HTTP 200
{"code": "SUCCESS"}

回调应答格式（失败）：
HTTP 200
{"code": "FAIL", "message": "订单不存在"}
```

**问题 3：如何保证支付金额不被篡改**

```text
回答：
1. 金额以分为单位（int），后台统一下单时重新从订单表取金额，不信任前端传的金额
2. 前端只传订单号，金额、商品明细全部由后台根据订单数据决定
3. 签名校验：后台请求微信支付用商户私钥签名，微信返回用微信平台证书验签
4. 支付回调中以微信返回的「实付金额」为准更新订单，与订单金额不一致走异常处理（退款/人工）
5. 面试常问：前端能不能传金额 —— 不能，前端传金额是典型的安全漏洞
```

**问题 4：wx.requestPayment 有哪些注意事项**

```text
回答：
1. 参数必须全部来自后台签名结果（timeStamp、nonceStr、package、signType、paySign），缺一不可
2. 必须在用户点击事件回调中调用（手势触发），不能异步延迟调用
3. 支付结果以回调为准：requestPayment 的 success 只是「用户完成收银台交互」，仍需查单确认
4. 用户取消支付走 fail 回调（errMsg 含 cancel），不要当异常报错
5. 基础库版本要求：老版本需 wx.requestPayment 参数为 package: 'prepay_id=xxx' 完整串
6. 陷阱：支付成功后立即跳转页面会导致回调未到达，先查单再跳转
```

**问题 5：支付回调与前端查单如何配合**

```text
回答：
1. 支付成功后前端调用「查询订单状态」接口（后台查本地订单 + 必要时查微信侧）
2. 后台订单状态流转：待支付 -> 支付中 -> 已支付 -> 已发货/已核销；回调更新为已支付
3. 时序竞争：用户支付成功但回调未到，前端查单应触发后台主动向微信查单（order query）
4. 轮询策略：支付后 3s/5s/10s 有限次查单，超过阈值提示「支付结果确认中」并给出订单详情页
5. 幂等要求：查单与回调更新订单都必须幂等，同一状态多次更新无副作用
```

**问题 6：退款流程怎么设计**

```text
回答：
1. 退款必须后台发起：调用微信支付退款接口（订单号/微信单号 + 退款金额 + 退款单号）
2. 退款原因与金额校验：退款金额不能超过实付金额；部分退款多次累计不能超总额
3. 退款结果也是异步通知（退款结果通知），后台更新退款单状态
4. 退款失败处理：余额不足（商户号资金不足）、原路退回限制等，记录失败原因并可重试
5. 对账：每日对账文件（下载账单）核对交易与退款流水，保证财务一致
6. 面试常问：部分退款 —— 微信支持，每次退款生成独立退款单号，注意总额校验
```

**问题 7：支付系统设计的核心原则是什么**

```text
回答：
1. 金额不信任前端：所有金额以服务端订单为准，前后端分离校验
2. 状态机驱动：订单状态（待支付/已支付/已取消/已退款/已关闭）用状态机管理，非法流转拒绝
3. 幂等设计：下单、回调、退款全部幂等，重复请求不产生重复效果
4. 回调与查单双通道：回调权威，查单兜底，对账修正
5. 资金安全：密钥分级管理（APIv3 密钥、商户私钥、平台证书），日志审计
6. 面试回答加分：提到「支付成功以回调为准 + 主动查单兜底 + 每日对账」三保险
```

## 订阅消息

**问题 1：订阅消息是什么，与模板消息有什么区别**

```text
回答：
1. 订阅消息是小程序向用户发送通知的能力，点击消息可跳回小程序对应页面
2. 历史：旧版「模板消息」在用户交互后 7 天内可多次下发，已被下线
3. 现行：一次性订阅（每次下发都需要用户主动授权，一次授权对应一条消息）
4. 长期订阅：仅部分类目可用（政务、医疗、金融等），需要类目资质申请
5. 获取授权：wx.requestSubscribeMessage 传入模板 id 列表，用户点「允许」后返回 accept
6. 下发通道：后台通过 access_token 调用 subscribeMessage.send 接口
7. 关键限制：一次性订阅授权一次只能发一条，用完即失效，需再次引导订阅
```

**问题 2：完整描述订阅消息的实现流程**

```text
回答：
1. 小程序后台（mp 平台）申请订阅消息模板，获得模板 id（tmplId）
2. 小程序端在合适的业务时机调用 wx.requestSubscribeMessage({ tmplIds: [tmplId] })
3. 用户点击允许后返回授权结果（accept/reject/ban），授权记录可由后台存储
4. 小程序将授权结果上报后台（含 openid 与接受的模板 id），后台记录「剩余可发次数 +1」
5. 业务触发时（如订单状态变化），后台组装模板数据调用 subscribeMessage.send
6. 发送成功即消耗一次授权，发送失败（41030 等）需记录并重试或引导重新订阅
7. 用户侧：微信「服务通知」中收到消息，点击跳转小程序页面
```

```text
关键返回码：
43101 —— 用户拒绝/未授权该模板（引导重新订阅）
40003 —— openid 无效
41030 —— 页面 path 不存在
47003 —— 模板参数不匹配（data 字段与模板占位符不一致）
```

**问题 3：如何提高订阅消息的授权率**

```text
回答：
1. 在用户最需要时请求：如支付成功后引导订阅「发货通知」，比冷启动弹窗转化高
2. 一次请求可带多个模板：wx.requestSubscribeMessage 的 tmplIds 支持数组，一次授权多个模板
3. 设计引导弹层：先解释订阅能带来什么价值，用户点「同意」后再调 wx.requestSubscribeMessage
4. 避免频繁打扰：同一模板未消耗完授权时不要重复弹窗（可用后台记录剩余次数）
5. 订阅失败后的补救：在消息中心/个人中心提供「开启通知」入口再次引导
6. 数据驱动：统计各场景订阅转化率，优化请求时机与话术
```

**问题 4：服务端发送订阅消息有什么注意点**

```text
回答：
1. 必须用 access_token 调用（subscribeMessage.send），access_token 需缓存（有效期 2 小时，每日限次）
2. 模板参数 data 必须与模板占位符完全匹配（如 {{thing1.DATA}} 传 thing1: { value: 'xxx' }）
3. 页面跳转 page 必须是小程序已发布页面路径，可带参数（path?key=value）
4. 发送频率与并发：批量发送用定时任务 + 队列削峰，避免瞬时打爆微信接口限流
5. 失败处理：记录失败原因（如 43101），用户再次授权后可重发
6. miniprogram_state 参数控制消息跳转环境（developer/trial/formal），正式环境传 formal
7. 陷阱：参数 value 有长度限制（不同字段类型不同，如 thing 类 20 字），超长发送失败
```

**问题 5：一次性订阅授权次数怎么管理**

```text
回答：
1. 后台为用户维护模板维度的「可发次数」：授权成功 +1，发送成功 -1
2. 可发次数为 0 时不再尝试发送，或在业务侧引导用户重新订阅
3. 授权与消费要防并发：发放与扣减用原子操作（Redis INCR/DECR 或数据库行锁）
4. 注意：用户删除小程序/取消订阅后授权会失效，发送失败后清理本地计数
5. 面试常问：怎么知道用户还有几次 —— 以服务端记录为准，微信侧不提供查询接口
```

**问题 6：订阅消息在电商场景的典型应用**

```text
回答：
1. 订单类：支付成功通知、发货通知、物流更新、退款结果
2. 营销类：优惠券到期提醒、活动开奖通知、会员权益提醒
3. 内容类：文章更新、预约提醒（到店前 1 小时）
4. 组合策略：支付成功后一次性请求多个模板（发货 + 到货 + 售后），供后续业务使用
5. 定时任务场景：优惠券过期前 1 天，定时任务扫描到期用户批量下发
6. 面试回答加分：说明「授权在业务节点、下发在事件触发、配额服务端管理」的闭环
```

**问题 7：订阅消息与模板消息相比有什么合规考量**

```text
回答：
1. 用户授权即同意，消息内容必须与订阅用途一致，不能借订阅发无关广告
2. 诱导订阅（强制订阅才能下单）会被平台处罚，授权必须可拒绝
3. 消息频率与内容受平台监管，频繁无价值推送会被限制甚至封禁模板
4. 隐私合规：订阅记录属用户个人信息，需在隐私保护指引中声明用途
5. 陷阱：把「订阅消息」当营销群发工具是红线，类目审核与日常监管都会拦截
```

## 安全与常见坑

**问题 1：内容安全检测怎么做**

```text
回答：
1. 微信提供内容安全接口：security.msgSecCheck（文本检测）与 security.mediaCheckAsync（图片/音视频异步检测）
2. 适用场景：用户发布的评论、昵称、头像、UGC 内容，上线前与上线后双重检测
3. 调用方式：后台用 access_token 调用，文本场景传 content，图片传 media_url
4. 检测结果：risky（违规）/ pass（通过）；异步检测需轮询/回调获取结果
5. 建议在发布时同步检测 + 定时任务复查历史内容，发现违规及时删除
6. 平台要求：涉及 UGC 的小程序必须接入内容安全能力，否则审核不通过
7. 本地兜底：敏感词库先过滤一次，降低调用量，微信检测为最终裁决
```

**问题 2：小程序接口安全有哪些要点**

```text
回答：
1. 必须 HTTPS：小程序强制 HTTPS 请求，后台配置合法域名与 SSL 证书
2. 身份认证：所有业务接口校验 token（JWT），用户身份从 token 解析，不信任前端传 userId
3. 越权防护：查询/修改数据必须校验数据归属（A 用户不能查 B 用户订单）
4. 参数校验：后端对入参做完整性校验（@Valid + 自定义规则），防注入与异常数据
5. 敏感数据加密传输：手机号等敏感字段解密后存储，日志脱敏
6. 防重放：接口签名（timestamp + nonce + sign）防止抓包重放攻击
7. 限流防刷：接口级限流（Redis 计数器/令牌桶），登录、验证码、支付类接口重点防护
```

```java
// 防重放签名校验核心逻辑（伪代码）
boolean valid = checkTimestamp(timestamp, 300)          // 时间窗 5 分钟
  && !redis.exists("nonce:" + nonce)                    // nonce 未使用过
  && sign.equals(signBySecret(params, secret));         // 签名一致
redis.setex("nonce:" + nonce, 300, "1");                // 记录 nonce
```

**问题 3：接口防刷有哪些手段**

```text
回答：
1. 频控：登录接口按手机号/设备/IP 限频（如 1 分钟 5 次），Redis INCR + 过期时间实现
2. 验证码：短信验证码（60s 间隔、有效期 5 分钟、错误次数锁定）
3. 行为风控：异常频率、异常时段、多设备同账号检测，触发后人工验证或封禁
4. token 与签名：登录后接口带 token；重要接口加签名与 nonce 防重放
5. 业务层防护：优惠券、秒杀等接口加幂等键，防止重复提交
6. 面试常问：登录接口被刷怎么防 —— 限频 + 验证码 + IP 黑名单 + 设备指纹
```

**问题 4：常见的小程序安全漏洞有哪些**

```text
回答：
1. 越权访问（IDOR）：直接改 URL 参数访问他人数据 —— 后端必须校验归属
2. 前端传金额/状态：下单金额、支付状态由前端传 —— 金额服务端取，状态服务端流转
3. AppSecret 泄露：写在代码里或提交仓库 —— 只存服务端，泄露立即重置
4. 敏感信息泄露：接口返回多余字段（手机号、openid）—— 响应 DTO 裁剪字段
5. 数据注入：WXML 注入（{{ }} 内容未转义导致的渲染问题）与 SQL 注入 —— 输入校验 + 参数化
6. 中间人攻击：非 HTTPS 或证书校验不当 —— 强制 HTTPS，后台校验证书
7. 回答加分：从「传输、身份、授权、数据、业务」五个维度组织答案
```

**问题 5：隐私合规有哪些硬性要求**

```text
回答：
1. 用户隐私保护指引：涉及用户信息（头像、位置、手机号、相册等）必须在小程序后台配置并弹窗告知
2. 最小化收集：只收集业务必需信息，不默认收集不必要数据
3. 用户授权管理：提供查看/删除个人信息途径（用户中心 - 账号注销）
4. 敏感权限：位置、相册、摄像头等 scope 权限在用户手势中申请，拒绝后给引导
5. 平台红线：违规收集（如强制授权才能用）会被下架处罚
6. 发布审核：类目资质、隐私协议、内容安全是提审必查项
```

**问题 6：小程序提审被拒的常见原因有哪些**

```text
回答：
1. 类目与资质不符：业务涉及的内容未匹配已选类目（如无资质做医疗咨询）
2. 隐私问题：未配置用户隐私保护指引、强制授权、收集与业务无关信息
3. 内容违规：页面存在违规内容、诱导分享、诱导关注
4. 功能不完整：关键功能无法使用（未配置合法域名导致请求失败）、测试账号缺失
5. 侵权风险：名称、Logo、内容涉嫌侵权
6. 解决思路：先看驳回理由与截图，对照「审核规范」逐条整改，复审前自测全流程
```

**问题 7：微信接口调用的频控与 quota 怎么理解**

```text
回答：
1. access_token 每日获取次数有限（如 2000 次），必须缓存复用（有效期 2 小时，提前刷新）
2. 部分接口有调用频率限制（如订阅消息发送、内容检测），超限返回错误码
3. 应对：批量任务用队列削峰、失败重试带退避、按接口统计调用量监控
4. 面试常问：access_token 在多实例部署下怎么管理 —— Redis 分布式锁 + 双检缓存，全局唯一
5. 陷阱：access_token 过期失效后其他接口报 40001，需统一刷新重试逻辑
```

**问题 8：上线前安全检查清单有哪些**

```text
回答：
1. 传输：全站 HTTPS，合法域名已配置，证书有效
2. 身份：所有业务接口鉴权，token 校验不遗漏，白名单接口最小化
3. 越权：抽样测试 A 用户能否操作 B 用户数据（改 userId 抓包验证）
4. 敏感数据：接口响应无多余敏感字段，日志脱敏（手机号、身份证）
5. 支付：金额服务端校验，回调验签，测试环境用沙箱/小额
6. 内容：UGC 已接入内容安全检测，敏感词过滤生效
7. 合规：隐私指引已配置，授权流程符合规范，类目资质齐全
```

## 最佳实践与踩坑记录

### 最佳实践

1. 登录态统一封装：请求拦截器自动带 token，401 自动静默续期并重放请求，登录流程对业务透明
2. 支付金额与状态全部以服务端为准，前端只传订单号，回调、查单、对账三通道保证一致
3. 订阅消息在支付成功、下单成功等「高价值时刻」引导授权，一次请求多个模板，服务端管理配额
4. 分包按业务域拆分，公共组件/工具放主包，首屏分包配置 preloadRule 预下载
5. setData 遵循「最小更新」原则：路径更新、合并调用、高频场景节流
6. 所有用户生成内容（昵称、评论、头像）接入 msgSecCheck + 本地敏感词双重检测
7. 微信接口调用统一封装：access_token 缓存刷新、错误码映射、失败重试带退避
8. 上线前按安全清单自查：越权抓包验证、敏感字段排查、HTTPS 与合法域名确认

### 踩坑记录

坑 1：code 重复使用导致登录失败
结论：第二次用同一个 code 调 code2session 报 invalid code。
原因：code 是一次性凭证，5 分钟有效，使用一次即失效。
解法：每次登录都重新 wx.login 获取新 code，前端不要缓存 code。

坑 2：支付成功跳转太快，订单状态未更新
结论：用户支付成功后立即跳详情页，显示「待支付」。
原因：支付回调是异步的，前端跳转时回调可能尚未到达后台。
解法：支付成功后先查单确认状态再跳转；查单接口在本地订单未支付时主动查微信侧。

坑 3：requestPayment 参数拼错导致拉起失败
结论：wx.requestPayment 报 package 参数错误。
原因：package 需要完整串 'prepay_id=xxx'，或参数未按后台签名原样传递。
解法：后端完整返回签名参数，前端原样透传，不自行拼接。

坑 4：订阅消息发送报 47003 参数不匹配
结论：subscribeMessage.send 返回 47003，消息发不出去。
原因：data 字段与模板占位符（如 {{thing1.DATA}}）不一致，或 value 超长。
解法：对照模板后台的字段类型与长度限制组装参数，发前本地校验。

坑 5：access_token 频繁刷新触发限流
结论：多个请求同时发现 token 过期，各自刷新导致接口报「超过每日调用上限」。
原因：未做全局缓存与互斥，多实例/多线程并发刷新。
解法：Redis 缓存 + 分布式锁（或双检锁）保证全局只有一个刷新方。

坑 6：接口返回多余字段导致敏感数据泄露
结论：订单接口返回了 user 对象，包含手机号、openid 等字段，被前端抓包看到。
原因：直接返回实体对象，未做 DTO 裁剪。
解法：响应统一用 DTO 只暴露必要字段，敏感字段彻底不返回。

坑 7：回调未正确应答导致微信重复通知
结论：同一支付通知被微信重试了几十次，订单状态被重复处理。
原因：回调逻辑异常未返回 {"code":"SUCCESS"}，且处理逻辑不幂等。
解法：回调先验签解密，幂等处理（状态判断 + 唯一约束），正确应答 SUCCESS。

坑 8：主包超 2MB 无法上传
结论：上传代码提示主包体积超限。
原因：图片、第三方库、未拆分包的业务代码都堆在主包。
解法：静态资源走 CDN、库按需引入、业务拆分包，主包只留启动必需代码。
