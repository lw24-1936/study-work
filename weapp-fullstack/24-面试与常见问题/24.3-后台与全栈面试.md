## SpringBoot 分层架构与工程实践

**问题 1：SpringBoot 项目如何分层，各层职责是什么**

```text
回答：
1. 典型分层：Controller（接口层）-> Service（业务层）-> Mapper/Repository（数据访问层）
2. Controller：接收请求、参数校验、调用 Service、返回统一结构，不写业务逻辑
3. Service：业务规则、事务管理、跨表操作、调用其他服务，是业务核心层
4. Mapper：SQL 访问与结果映射（MyBatis-Plus）或 JPA Repository，只做数据读写
5. 辅助层：DTO（入参/出参）、Entity（实体）、VO（视图对象）、Config（配置）、Util（工具）
6. 依赖方向：Controller 依赖 Service，Service 依赖 Mapper，禁止反向依赖与循环依赖
7. 面试常问：为什么要分层 —— 职责单一、可测试、可维护、方便多人协作并行开发
```

追问：Controller 层应该做什么，不该做什么？

```text
回答：
1. 该做：接收并转换入参、做基础参数校验、调用 Service、包装统一返回
2. 不该做：写 SQL、写业务规则、直接操作 Redis/第三方 SDK（这些放 Service）
3. 不该做：try-catch 包住全部业务逻辑（用全局异常处理器统一处理）
4. 不该做：在 Controller 里做权限判断细节（用 Spring Security 注解/过滤器统一拦截）
5. 判断标准：把 Controller 方法抽出来，业务逻辑应能独立复用
```

**问题 2：统一返回结构怎么设计**

```text
回答：
1. 通用结构：code（业务状态码）+ message（提示信息）+ data（数据体）+ timestamp
2. 成功 code=0 或 200，失败用业务码（如 401 未登录、403 无权限、404 资源不存在、500 服务异常）
3. 分页返回：PageResult 包含 list、total、page、size，避免把分页塞进 data 的零散字段
4. 实现方式：ResponseBodyAdvice 统一包装成功响应，@RestControllerAdvice 统一处理异常
5. 注意：包装逻辑要排除已包装对象与文件流等特殊返回，避免双重包装
6. 面试常问：code 与 HTTP status 的关系 —— 业务上习惯 HTTP 200 + 业务 code 判断，也有纯 HTTP 语义派，团队统一即可
```

```java
// 统一返回结构示例
public class R<T> {
    private int code;      // 0 成功，非 0 业务失败
    private String message;
    private T data;
    private long timestamp;
    public static <T> R<T> ok(T data) { /* ... */ }
    public static <T> R<T> fail(int code, String msg) { /* ... */ }
}
```

**问题 3：全局异常处理怎么实现**

```text
回答：
1. 使用 @RestControllerAdvice + @ExceptionHandler 统一捕获异常并转换为统一返回
2. 分类处理：业务异常（自定义 BizException，如余额不足）返回业务码与友好提示
3. 参数校验异常（MethodArgumentNotValidException）返回具体字段错误
4. 系统异常（Exception）记日志（含堆栈）返回「系统繁忙」类通用提示，不暴露内部细节
5. 注意顺序：@ExceptionHandler 按异常类型精确匹配，子类异常处理器优先于父类
6. 面试常问：为什么不直接在 Service 里 try-catch —— 统一处理避免代码重复、错误格式统一、日志统一
```

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BizException.class)
    public R<Void> handleBiz(BizException e) {
        return R.fail(e.getCode(), e.getMessage());
    }
    @ExceptionHandler(Exception.class)
    public R<Void> handleOther(Exception e) {
        log.error("系统异常", e);
        return R.fail(500, "系统繁忙，请稍后重试");
    }
}
```

**问题 4：参数校验怎么做**

```text
回答：
1. 使用 JSR-303 注解：@NotNull、@NotBlank、@Size、@Min/@Max、@Pattern 等标注在 DTO 字段上
2. Controller 参数加 @Valid/@Validated 触发校验，校验失败由全局异常处理器统一返回
3. 分组校验：@Validated(UpdateGroup.class) 实现新增/更新不同规则
4. 自定义校验：实现 ConstraintValidator 编写业务规则（如手机号格式、状态枚举）
5. 校验放哪层：入参格式校验在 Controller/DTO 层，业务规则校验（余额、库存）在 Service 层
6. 陷阱：@Valid 只校验一层，嵌套对象需在字段上加 @Valid 才会递归校验
```

**问题 5：事务管理有哪些要点**

```text
回答：
1. 使用 @Transactional 标注 Service 方法，默认只回滚 RuntimeException（RuntimeException 与 Error）
2. 陷阱一：@Transactional 只对 public 方法生效，同类内部调用（this.method()）不走代理，事务失效
3. 陷阱二：checked 异常（Exception）默认不回滚，需 rollbackFor = Exception.class
4. 陷阱三：事务方法里 try-catch 吞掉异常导致不触发回滚，应抛出或手动 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()
5. 事务边界：事务放在 Service 层（业务粒度），不要放在 Controller 或 Mapper 单条操作
6. 传播行为：REQUIRED（默认，加入已有事务）、REQUIRES_NEW（新开事务）等按需选择
7. 面试常问：事务中调用远程接口 —— 避免长事务持锁，远程调用放事务外或最终一致方案
```

**问题 6：MyBatis-Plus 与 JPA 怎么选**

```text
回答：
1. MyBatis-Plus：SQL 可控、复杂查询灵活、国内生态好；提供 CRUD 封装与分页插件
2. JPA/Hibernate：对象映射自动、联表查询方便（但复杂 SQL 与调优不直观）
3. 本知识库选用 MyBatis-Plus：中小项目开发效率高，SQL 可审查，团队上手快
4. 工程要点：逻辑删除（@TableLogic）、自动填充（create_time/update_time）、分页插件配置
5. 陷阱：实体字段与数据库列映射（驼峰转下划线）配置要一致，否则查询结果为空
```

## 认证与安全

**问题 1：JWT 的原理与结构是什么**

```text
回答：
1. JWT（JSON Web Token）由三部分组成：Header.Payload.Signature，用 . 拼接
2. Header：签名算法与 token 类型（{"alg":"HS256","typ":"JWT"}），Base64 编码
3. Payload：用户信息与声明（userId、角色、过期时间 exp、签发时间 iat），Base64 编码
4. Signature：Header + Payload + 密钥按算法生成，防止内容被篡改
5. 验证流程：服务端用密钥重算签名，与 token 中签名比对，一致则内容可信且未过期
6. 无状态：服务端不存会话，分布式部署天然支持，适合小程序后台
7. 注意：Payload 是 Base64 可解码的，不能放敏感信息（密码、手机号明文）
```

```text
JWT 结构示例：
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEwMDEsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzU1NTU1NTU1fQ.签名串
├─ Header(算法)  ─┴─ Payload(用户声明)  ─┴─ Signature(防篡改)
```

追问：JWT 的缺点是什么，如何弥补？

```text
回答：
1. 无法主动失效：token 签发后到期前一直有效，用户改密/踢人无法立即生效
2. 弥补方案一：Redis 黑名单（登出/改密时把 jti 加入黑名单直到过期）
3. 弥补方案二：版本号（user_version）存 Redis，校验时对比，版本变化即失效
4. 弥补方案三：缩短有效期（如 30 分钟）+ refresh token 续期机制
5. token 泄露风险：配合 HTTPS、前端不落日志、过期自动续期减少泄露窗口
```

**问题 2：Spring Security 在小程序后台如何集成**

```text
回答：
1. 核心组件：SecurityFilterChain 过滤器链、AuthenticationManager、UserDetailsService、PasswordEncoder
2. 配置要点：关闭 CSRF（无状态 API 不需要）、Session 无状态（STATELESS）、放行白名单（登录接口）
3. 认证流程：登录接口校验账号密码 -> 生成 JWT 返回 -> 后续请求带 Authorization: Bearer token
4. 鉴权实现：自定义 OncePerRequestFilter 解析 token 并放入 SecurityContext，再用注解 @PreAuthorize 控制
5. 密码存储：PasswordEncoder（BCrypt）加密，明文存储是严重漏洞
6. 角色权限：基于 RBAC 的权限字符串（如 'order:create'），@PreAuthorize("hasAuthority('order:create')")
7. 面试常问：小程序场景为什么不需要登录页 —— 前端 wx.login 换 token，Security 只做接口级认证
```

```java
// Security 配置核心骨架
@Bean
SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.csrf().disable()
        .sessionManagement().sessionCreationPolicy(SessionCreationPolicy.STATELESS)
        .and().authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .anyRequest().authenticated())
        .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
    return http.build();
}
```

**问题 3：JWT 认证的完整时序是什么**

```text
回答：
1. 小程序 wx.login 拿到 code，调后台登录接口
2. 后台 code2session 换 openid，查/建用户，生成 JWT（含 userId、角色、过期时间）
3. 返回 token 给小程序，前端存储并随请求头携带（Authorization: Bearer xxx）
4. 后台 JWT 过滤器解析 token：验签 -> 验过期 -> 加载用户权限 -> 放入 SecurityContext
5. Controller 通过 @AuthenticationPrincipal 或 SecurityContextHolder 获取当前用户
6. 所有业务方法用 userId 做数据归属校验，token 过期返回 401，前端触发重新登录
```

**问题 4：RBAC 权限模型怎么设计**

```text
回答：
1. RBAC：用户（User）-> 角色（Role）-> 权限（Permission），用户关联角色，角色关联权限
2. 表设计：user / role / permission 三张主表 + user_role / role_permission 两张关联表
3. 权限粒度：按钮级权限用权限码（如 user:delete），接口用 @PreAuthorize 校验权限码
4. 数据权限：行级权限（如只能看本部门数据）需在 SQL 层加条件，RBAC 只解决功能权限
5. 管理端场景：Vue 前端根据用户权限动态渲染菜单与按钮（hasPermission 指令）
6. 面试常问：超管与普通用户的区别 —— 超管角色拥有全部权限码，不要用 isAdmin 字段硬编码
7. 性能：用户权限缓存到 Redis，避免每次请求查库（权限变更时刷新缓存）
```

**问题 5：登录接口的安全设计有哪些**

```text
回答：
1. 限流防刷：按账号/IP 限频（Redis INCR + 过期），连续失败锁定（如 5 次锁 10 分钟）
2. 验证码：图形验证码或短信验证码，短信还要加 60 秒发送间隔与模板防刷
3. 密码安全：BCrypt 加密存储、传输走 HTTPS、日志不打印密码
4. 返回最小化：登录接口不返回密码哈希、不返回 openid/session_key
5. token 安全：设置合理有效期、登出接口使 token 失效（黑名单）、支持改密强制下线
6. 异常登录：异地/新设备登录告警，可选二次验证
7. 面试回答加分：从「前置（限流验证码）- 中置（加密鉴权）- 后置（失效审计）」三层组织
```

**问题 6：接口签名与防重放怎么做**

```text
回答：
1. 签名流程：参数（含 timestamp、nonce）按规则排序拼接 -> 加盐（secret）-> 摘要算法（HMAC-SHA256）生成 sign
2. 服务端校验：验 timestamp 时间窗（如 5 分钟）-> 查 nonce 是否用过（Redis setnx）-> 重算签名比对
3. 防重放原理：timestamp 限制时效，nonce 保证同一请求只能执行一次
4. 适用场景：非登录态接口（如支付回调、开放平台对接）、防刷关键接口
5. 注意：签名密钥服务端保管，前端小程序可用固定 appKey + 约定规则（或依赖 HTTPS + token 即可）
6. 陷阱：时间戳要防未来时间（时钟偏移），nonce 存储要有过期清理
```

**问题 7：越权漏洞（IDOR）如何防止**

```text
回答：
1. 核心原则：用户身份从 token 解析，业务操作的目标数据必须校验归属
2. 例：订单详情接口必须校验 order.userId == currentUser.id，而不是只按 orderId 查询
3. 实现方式：Service 层统一取当前用户（SecurityContextHolder），查询条件强制带 userId
4. 防止水平越权（同角色用户互访）与垂直越权（低权限访问高权限接口）
5. 测试方法：抓包修改 userId/orderId 验证是否被拦截，上线前必测
6. 面试常问：为什么只靠前端隐藏按钮不够 —— 接口是直接可调的，必须后端鉴权
```

## Redis 缓存与数据库设计

**问题 1：缓存穿透、击穿、雪崩分别是什么，如何解决**

```text
回答：
1. 穿透：查询不存在的 key，缓存和数据库都没有，请求直达数据库 —— 用空值缓存（短过期）或布隆过滤器前置拦截
2. 击穿：热点 key 过期瞬间，大量请求同时打数据库 —— 互斥锁重建缓存（SETNX）或逻辑过期 + 后台刷新
3. 雪崩：大量 key 同时过期或 Redis 宕机，请求全部打库 —— 过期时间加随机值、多级缓存、Redis 高可用（主从/集群）
4. 通用手段：限流降级（请求熔断、降级返回默认值）、数据库连接池保护
5. 面试回答重点：先说清楚三者的触发条件差异（查不到/单个热点过期/批量同时过期），再给方案
```

```text
三问题速记：
穿透 = 查空 -> 空值缓存 / 布隆过滤器
击穿 = 单点过期 -> 互斥锁 / 逻辑过期
雪崩 = 批量过期 / 宕机 -> 随机过期时间 / 多级缓存 / 高可用
```

追问：缓存和数据库一致性怎么保证？

```text
回答：
1. 更新策略：先更新数据库，再删缓存（Cache Aside），下次读取时重建
2. 为什么不先删缓存再更新库 —— 更新期间并发读会读到旧值并回填，造成长时间不一致
3. 删除失败兜底：延迟双删（更新后延迟 1s 再删一次）、消息队列重试删除
4. 读多写少的数据（商品详情）可容忍短时不一致；强一致场景直接读库或加版本号
5. 陷阱：缓存设置过长 TTL 会放大不一致窗口，热门数据 TTL 要短并配合主动刷新
```

**问题 2：Redis 缓存更新与失效策略有哪些**

```text
回答：
1. 主动更新：业务写操作后删除/更新缓存（Cache Aside），最常用
2. 定时刷新：定时任务周期性重建缓存（适合读多写少、实时性要求低的场景）
3. 过期失效：设置 TTL 自动过期，配合懒加载重建
4. 逻辑过期：value 里存过期时间，读取时发现过期由单线程异步重建，避免击穿
5. 选择依据：数据实时性要求、读频率、写频率，组合使用（如商品详情 = 主动更新 + TTL）
6. 陷阱：所有 key 同 TTL 会在同一时刻集体过期，必须加随机抖动
```

**问题 3：用户表怎么设计**

```text
回答：
1. 核心字段：id、openid（微信唯一标识，唯一索引）、unionid（多端打通，可空）、nickname、avatar、phone、status、create_time、update_time
2. 关联扩展：user_profile（扩展资料）、user_address（收货地址，一对多）、user_point（积分账户）按需拆分
3. openid 是登录凭证，不能作为业务展示 id；业务主键用自增 id 或雪花 id
4. 唯一约束：openid 唯一索引防止重复注册；unionid 非空时也建唯一索引
5. 逻辑删除：deleted 字段标记，配合 MyBatis-Plus @TableLogic
6. 性能：按手机号查询建索引；用户量大时按 user_id 分表或冷热分离
7. 面试常问：同一用户多账号 —— 手机号绑定 + 微信 openid 双通道，账号合并用 unionid 关联
```

```sql
CREATE TABLE `user` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '用户ID',
  `openid`      VARCHAR(64)  NOT NULL COMMENT '微信openid',
  `unionid`     VARCHAR(64)  DEFAULT NULL COMMENT '开放平台unionid',
  `nickname`    VARCHAR(64)  DEFAULT '' COMMENT '昵称',
  `avatar`      VARCHAR(255) DEFAULT '' COMMENT '头像URL',
  `phone`       VARCHAR(20)  DEFAULT NULL COMMENT '手机号',
  `status`      TINYINT      NOT NULL DEFAULT 1 COMMENT '1正常 0禁用',
  `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_openid` (`openid`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

**问题 4：订单表怎么设计**

```text
回答：
1. 主表 order：order_no（业务订单号，唯一）、user_id、total_amount（总金额，分）、status（状态机）、pay_time、cancel_time、create_time
2. 子表 order_item：order_id、sku_id、商品名快照、单价、数量、小计 —— 商品信息必须快照，商品改价不影响历史订单
3. 金额一律用分为单位的 int/bigint，避免浮点误差
4. 状态机：待支付 -> 已支付 -> 已发货 -> 已完成 / 已取消 / 已退款，非法流转拒绝
5. 订单号生成：时间戳 + 随机数 + 用户标识（雪花 id 或 Redis 自增），保证唯一且不可预测
6. 索引设计：user_id + create_time 联合索引（查用户订单列表）、order_no 唯一索引（回调/查单）
7. 拆表：量大后按 user_id 分表或按时间分区，支付流水单独建表（pay_record）
8. 面试常问：订单与库存的一致性 —— 下单锁库存（乐观锁/Redis 预扣），支付失败回滚释放
```

```sql
CREATE TABLE `order` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_no`      VARCHAR(32)  NOT NULL COMMENT '业务订单号',
  `user_id`       BIGINT       NOT NULL COMMENT '用户ID',
  `total_amount`  INT          NOT NULL COMMENT '总金额(分)',
  `status`        TINYINT      NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已发货 3已完成 4已取消 5已退款',
  `pay_time`      DATETIME     DEFAULT NULL,
  `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),
  KEY `idx_user_time` (`user_id`, `create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';
```

**问题 5：数据库索引设计的基本原则**

```text
回答：
1. 查询条件、排序、分组、唯一约束的列建索引；频繁更新的列慎建索引
2. 联合索引遵循最左前缀：查询要包含索引最左列，否则索引失效
3. 区分度：区分度低的列（status）单独建索引意义不大，可放联合索引末尾
4. 覆盖索引：查询字段都在索引内可避免回表，慢查询优化常用手段
5. 避免索引失效：对索引列做函数/运算、隐式类型转换、like '%xx' 都会失效
6. 排查手段：EXPLAIN 看 type（ref/range 优，ALL 全表扫描要优化）、慢查询日志
7. 面试常问：为什么查询慢 —— 先 EXPLAIN 看是否走索引，再看数据量与 SQL 写法
```

**问题 6：Redis 常用数据结构的业务场景**

```text
回答：
1. String：缓存、计数器（INCR 点赞/库存）、分布式锁（SETNX + 过期时间）、短信验证码
2. Hash：对象存储（用户信息、购物车按商品 id 存数量）
3. List：消息队列（LPUSH/BRPOP）、时间线、关注列表
4. Set：去重集合（已领券用户、共同关注）、抽奖池
5. ZSet：排行榜（分数排序）、延迟队列（score 为时间戳）、限流滑动窗口
6. 面试常问：购物车用什么结构 —— Hash（userId 维度，field 为 skuId，value 为数量），便于增减与去重
```

**问题 7：分布式锁怎么实现**

```text
回答：
1. Redis 实现：SET key value NX EX 30，value 用唯一请求标识（UUID），删除时先比对再删（Lua 保证原子）
2. 过期时间问题：业务执行超过锁过期时间会提前释放 —— 用看门狗续期或 Redisson 自动续期
3. 主从切换问题：Redis 主节点宕机锁丢失 —— 用 Redlock（多节点）或 etcd/ZooKeeper 实现强一致锁
4. 应用场景：秒杀扣库存、定时任务防重复执行、access_token 全局刷新
5. 面试回答加分：提到「释放锁要用 Lua 脚本保证 比对+删除 原子性」是高频追问点
```

```lua
-- 释放锁的 Lua 脚本（比对 value 后删除，保证原子性）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

## 前后端联调与部署上线

**问题 1：小程序请求后台的合法域名与 HTTPS 要求是什么**

```text
回答：
1. 小程序正式环境只能请求已配置的合法域名：request 合法域名、uploadFile 合法域名、downloadFile 合法域名、WebSocket 合法域名
2. 域名要求：必须 HTTPS（需有效证书）、域名需 ICP 备案、每个类目各 20 个（2023 年后 request 默认 200 个）
3. 配置位置：小程序后台「开发 - 开发设置 - 服务器域名」；开发工具可勾选「不校验合法域名」本地调试
4. 不支持 IP 直连、不支持 localhost（真机）；本地联调用内网穿透（ngrok/frp）映射到 HTTPS 域名
5. 证书要求：证书需完整链（含中间证书），不完整时真机请求报「证书校验失败」
6. 陷阱：域名配置后需重新编译/重新进入小程序才生效，配置有缓存
```

**问题 2：跨域问题在小程序后台怎么处理**

```text
回答：
1. 小程序环境本身不受浏览器同源策略限制（wx.request 不走浏览器 CORS），只要域名在合法域名列表即可
2. 跨域主要发生在管理端（Vue + axios 浏览器环境）：后台需配置 CORS
3. CORS 配置：Access-Control-Allow-Origin（指定来源，不要用 * 带凭证）、Allow-Methods、Allow-Headers、Allow-Credentials
4. 预检请求：复杂请求（自定义头、非简单方法）先发 OPTIONS，后台需响应 204 放行
5. 生产环境更优解：Nginx 反向代理同域部署（/api 前缀转发），避免跨域并统一入口
6. 面试常问：小程序为什么没有跨域 —— 小程序请求不经过浏览器，由微信客户端发起，不受 CORS 约束
```

```java
// SpringBoot CORS 配置片段
@Configuration
public class CorsConfig {
    @Bean
    public CorsFilter corsFilter() {
        CorsConfiguration cfg = new CorsConfiguration();
        cfg.addAllowedOrigin("https://admin.example.com");
        cfg.addAllowedMethod("*");
        cfg.addAllowedHeader("*");
        cfg.setAllowCredentials(true);
        UrlBasedCorsConfigurationSource src = new UrlBasedCorsConfigurationSource();
        src.registerCorsConfiguration("/**", cfg);
        return new CorsFilter(src);
    }
}
```

**问题 3：前后端联调的标准流程是什么**

```text
回答：
1. 先定接口契约：RESTful 路径、请求/响应结构、状态码定义、鉴权方式（Swagger/OpenAPI 文档先行）
2. 后端先行：按契约实现接口，Swagger 文档可在线调试，前端 mock 数据并行开发
3. 环境约定：dev（开发）、test（测试）、prod（生产）三套环境，配置管理统一
4. 联调要点：字段命名、空值处理、分页参数、错误信息可读性、时间格式（统一时间戳或 ISO8601）
5. 联调工具：Swagger UI、Apifox/Postman 集合共享、抓包工具（Charles/whistle）
6. 问题记录：联调问题单（接口文档驱动），修复后回归验证
7. 面试常问：接口文档谁来维护 —— 后端维护 OpenAPI 契约，前端基于契约开发与 mock
```

**问题 4：Nginx 在小程序全栈中的作用**

```text
回答：
1. 静态资源服务：管理端打包产物（dist）直接由 Nginx 托管
2. 反向代理：/api 转发到后端服务（SpringBoot），实现同域部署规避跨域
3. HTTPS 终结：SSL 证书挂在 Nginx，证书续期与卸载集中管理
4. 负载均衡：upstream 配置多台后端，轮询/权重分发
5. 静态缓存与压缩：gzip、静态资源缓存头，提升管理端加载速度
6. 常用配置：server 块、location 匹配、proxy_pass、日志格式
7. 陷阱：proxy_pass 的路径拼接（带不带 / 影响转发路径）、WebSocket 需配置 upgrade 头
```

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;
    ssl_certificate     /etc/nginx/cert/fullchain.pem;
    ssl_certificate_key /etc/nginx/cert/privkey.pem;

    location /api/ {
        proxy_pass http://127.0.0.1:8080/;   # 去掉 /api 前缀转发
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location / {
        root /var/www/admin;
        try_files $uri $uri/ /index.html;    # Vue history 路由回退
    }
}
```

**问题 5：Docker 部署 SpringBoot 应用的要点**

```text
回答：
1. 镜像构建：多阶段构建（maven 编译 -> jre 运行），减小镜像体积
2. 基础镜像：eclipse-temurin:17-jre（JDK17 对应）等精简运行时镜像
3. 启动命令：java -jar app.jar，配置通过环境变量注入（SPRING_PROFILES_ACTIVE、数据库连接）
4. 健康检查：HEALTHCHECK 或 SpringBoot Actuator /actuator/health 供容器编排探活
5. 资源限制：内存限制（-Xmx 与容器 limit 匹配，避免 OOM 被 kill）
6. 日志：容器日志打到 stdout，由 Docker 收集（json-file 或对接日志平台），挂载卷持久化
7. 编排：单机用 docker-compose（app + mysql + redis + nginx），多机用 K8s
8. 陷阱：时区问题（容器默认 UTC，加 TZ=Asia/Shanghai）、配置文件不打进镜像（挂载/环境变量）
```

**问题 6：CI/CD 流水线怎么设计**

```text
回答：
1. CI（持续集成）：代码 push -> 触发流水线 -> 编译、单元测试、代码扫描（SonarQube）-> 构建镜像
2. CD（持续部署）：镜像推送镜像仓库 -> 部署到测试环境 -> 自动化测试 -> 手工确认 -> 部署生产
3. 工具选型：GitLab CI / GitHub Actions / Jenkins；私有化团队常用 GitLab CI + Harbor 镜像仓库
4. 环境变量与密钥：CI 变量或 Vault 管理，密钥不写进代码仓库
5. 发布策略：蓝绿发布 / 滚动更新 / 金丝雀灰度，配合回滚（保留上一版本镜像）
6. 质量门禁：测试覆盖率、静态检查失败则阻断合并/发布
7. 面试常问：回滚怎么做 —— 保留版本镜像 tag，一键重新部署上一版本并暂停灰度
```

**问题 7：上线发布流程与监控告警怎么设计**

```text
回答：
1. 发布流程：提审（小程序）-> 审核通过 -> 灰度发布（后台可配灰度比例）-> 全量发布 -> 观察监控
2. 小程序侧：体验版验证 -> 提审 -> 发布；配合「版本回退」保留上一线上版本
3. 后台侧：部署新版本 -> 健康检查 -> 监控指标（QPS、错误率、RT、内存、CPU）
4. 告警体系：日志（ELK/Loki）、指标（Prometheus + Grafana）、告警（Alertmanager 通知钉钉/企微）
5. 关键告警项：5xx 错误率突增、接口 RT 超时、内存/磁盘告警、订单支付失败率
6. 审计与复盘：发布记录、变更单、故障复盘（时间线、影响面、改进项）
7. 面试常问：线上故障怎么排查 —— 先看监控大盘定位（错误率/慢接口），再看日志与链路追踪
```

## 全栈协作与项目管理

**问题 1：前后端职责边界如何划分**

```text
回答：
1. 前端（小程序/管理端）：页面渲染、交互逻辑、表单校验、请求封装、本地缓存、状态管理
2. 后端：业务规则、数据校验（服务端为准）、权限鉴权、事务、缓存、第三方对接（微信支付/消息）
3. 共同维护：接口契约（OpenAPI）、字段命名规范、错误码约定
4. 原则：安全相关的校验（金额、权限、归属）必须后端做，前端校验只提升体验
5. 面试常问：前端做了校验后端还要做吗 —— 要，前端校验可绕过，后端校验是安全底线
```

**问题 2：接口设计规范有哪些**

```text
回答：
1. RESTful 资源化：GET /orders、POST /orders、PUT /orders/{id}，动词放方法不放路径
2. 版本管理：/api/v1/ 前缀，破坏性变更升版本
3. 命名规范：小写 + 连字符（user-profile），字段统一驼峰，时间统一格式
4. 错误语义：业务错误码分段（1xxx 参数、2xxx 权限、3xxx 业务、5xxx 系统），文档可查
5. 分页统一：page + size + sort 参数，返回 PageResult 结构
6. 幂等设计：下单、支付回调等写接口支持幂等键（请求头 Idempotency-Key 或业务单号）
7. 面试常问：接口返回什么结构 —— 统一 R<T>（code/message/data），错误码有文档
```

**问题 3：多环境管理怎么做**

```text
回答：
1. 环境划分：本地（local）、开发（dev）、测试（test）、生产（prod），各自独立配置与数据库
2. SpringBoot：application-{env}.yml + spring.profiles.active 切换，敏感配置用环境变量/配置中心
3. 小程序侧：不同环境用不同 appid 或后台切换合法域名（开发工具多环境配置）
4. 数据隔离：测试库用脱敏数据，严禁生产数据倒入测试环境
5. 部署环境：dev/test 自动部署，prod 手动确认发布，权限分离
6. 面试常问：测试环境和生产环境配置差异怎么管理 —— 配置外置（环境变量 + 配置中心 Nacos），代码不打包环境差异
```

**问题 4：小程序全栈项目如何做技术选型**

```text
回答：
1. 前端：原生小程序（本知识库主线，便于理解原理）；跨端要求高可考虑 Taro/uni-app
2. 后端：SpringBoot 2.7+/3.x + MyBatis-Plus + Redis + MySQL，生态成熟、招聘友好
3. 管理端：Vue3 + Vite + Element Plus + Pinia + axios 封装
4. 基础设施：Nginx、Docker、GitLab CI；监控 Prometheus + Grafana
5. 选型依据：团队熟悉度、业务规模、招聘市场、维护成本，避免为技术而技术
6. 面试常问：为什么选 MyBatis-Plus 不选 JPA —— SQL 可控 + 团队熟悉 + 分页插件成熟
```

**问题 5：敏捷迭代与排期估算怎么沟通**

```text
回答：
1. 需求拆分：按用户故事拆（登录、下单、支付回调），每个故事可独立验收
2. 估时方法：相对估算（故事点）或时间估算（天/人日），留 20% 缓冲应对联调与测试
3. 依赖管理：前后端接口契约先行，前端 mock 并行开发，避免串行等待
4. 风险识别：第三方依赖（微信审核、支付资质、证书申请）提前申请，是常见延期点
5. 验收标准：每个需求定义 Done 标准（功能 + 测试 + 文档 + 联调通过）
6. 面试常问：接口还没好前端怎么开发 —— 契约先行 + mock 数据 + 联调环境切换
```

**问题 6：项目里如何保证代码质量**

```text
回答：
1. 规范：统一代码风格（.editorconfig + 格式化插件）、命名规范、提交信息规范（Conventional Commits）
2. 审查：MR/PR 强制 Code Review，重点关注安全（越权、注入）、性能（N+1 查询）、正确性
3. 测试：单元测试（JUnit + Mockito，Service 层核心逻辑）、接口测试（自动化）、关键路径回归
4. 静态检查：SonarQube 接入 CI，坏味道与重复代码门禁
5. 文档：接口文档（Swagger）、架构文档、部署文档随代码更新
6. 面试回答加分：提到「Code Review 清单」—— 越权、金额、幂等、日志脱敏、事务边界
```

## 面试重点总结

```text
高频考点编号：
1. 分层架构：Controller/Service/Mapper 职责边界，Controller 不写业务，Service 管事务
2. 统一封装：R<T> 返回结构 + @RestControllerAdvice 全局异常 + @Valid 参数校验
3. JWT：三段结构（Header/Payload/Signature）、无状态、主动失效用 Redis 黑名单/版本号
4. Spring Security：无状态过滤器链、BCrypt 密码、@PreAuthorize 权限码、RBAC 三表五关系
5. Redis：穿透（空值/布隆）、击穿（互斥锁/逻辑过期）、雪崩（随机 TTL/多级缓存），先更库再删缓存
6. 数据库：金额用分存储、订单商品快照、状态机、联合索引最左前缀、EXPLAIN 排查
7. 联调部署：小程序合法域名 + HTTPS、CORS 配置、Nginx 反代同域、Docker 多阶段构建、CI/CD 灰度回滚
8. 全栈协作：接口契约先行、mock 并行、安全校验后端兜底、多环境配置外置
```

## 最佳实践与踩坑记录

### 最佳实践

1. 接口统一返回 R<T>，业务异常用 BizException 抛出，全局异常处理器统一转换，Controller 不写 try-catch
2. 金额一律以分为单位 int 存储与传输，前端展示时再除以 100，杜绝浮点误差
3. 所有写接口（下单、支付回调、领券）做幂等设计，回调处理先查状态再更新
4. 用户身份从 token 解析，查询强制带 userId 条件，上线前做越权抓包测试
5. Redis key 统一前缀规范（如 user:info:{id}），集中管理过期时间与随机抖动
6. 配置外置：环境变量 + 多 profile，密钥走 CI 变量/配置中心，不提交仓库
7. Nginx 统一反代 /api 实现同域部署，管理端避免跨域并简化证书管理
8. 发布前按检查清单过一遍：HTTPS 证书、合法域名、越权用例、敏感字段、灰度回滚方案

### 踩坑记录

坑 1：@Transactional 不生效，数据没回滚
结论：Service 方法内调用同类另一个 @Transactional 方法，异常后数据未回滚。
原因：同类内部调用绕过 Spring 代理，事务注解失效。
解法：拆成两个 Bean 互相调用，或通过 AopContext.currentProxy() 调用；同时确认方法为 public。

坑 2：全局异常处理器没拦截到异常
结论：接口抛异常后返回了 500 默认错误页，而不是统一结构。
原因：异常被 Controller 内部 try-catch 吞掉，或异常发生在过滤器链（过滤器异常不走 @RestControllerAdvice）。
解法：业务代码不吞异常；过滤器层异常用 HandlerExceptionResolver 或全局 Filter 捕获处理。

坑 3：JWT 里放了手机号，被 Base64 解码泄露
结论：token 被截获后 Base64 解码 Payload 能看到手机号等敏感信息。
原因：JWT Payload 只是 Base64 编码，不是加密。
解法：Payload 只放 userId、角色、过期时间等非敏感声明；敏感信息服务端按 userId 查询。

坑 4：缓存击穿导致数据库被打挂
结论：热点商品详情缓存过期瞬间，QPS 全部打到数据库，接口超时。
原因：热点 key 过期无锁重建，大量请求同时回源。
解法：互斥锁（SETNX）重建缓存或逻辑过期 + 异步刷新；热点数据 TTL 加随机值防批量过期。

坑 5：小程序真机请求报「证书校验失败」
结论：开发者工具正常，真机 wx.request 全部失败，报证书错误。
原因：服务器证书链不完整（缺少中间证书），或域名证书与域名不匹配。
解法：用 SSL 检测工具检查证书链，Nginx 配置 fullchain.pem；确认合法域名与证书域名一致。

坑 6：管理端接口报跨域错误（CORS）
结论：Vue 管理端请求后台报 Access-Control-Allow-Origin 缺失，浏览器拦截。
原因：后台未配置 CORS 或配置了 * 且带凭证（* 不能与 credentials 同时用）。
解法：后台配置具体来源 + 允许方法/头 + credentials；生产环境用 Nginx 同域反代彻底规避。

坑 7：Nginx 反代后接口路径多了 /api 前缀报 404
结论：前端请求 /api/orders，Nginx 转发后 SpringBoot 找不到映射。
原因：proxy_pass 带不带尾斜杠的路径拼接规则不同，前缀未去掉。
解法：location /api/ { proxy_pass http://127.0.0.1:8080/; } 去掉前缀；或后端统一 context-path 接收。

坑 8：Docker 容器时间比北京时间慢 8 小时
结论：订单创建时间、日志时间全部差 8 小时。
原因：容器默认 UTC 时区。
解法：Dockerfile ENV TZ=Asia/Shanghai 并安装 tzdata；MySQL 连接 URL 加 serverTimezone=Asia/Shanghai。

坑 9：测试数据把生产用户信息污染了
结论：测试环境联调后，生产库出现测试账号数据。
原因：测试环境误连生产数据库，或测试脚本未做环境隔离。
解法：数据库连接配置按环境隔离且密码不同；测试环境使用脱敏数据，禁止生产库直连。

坑 10：接口文档与实现不一致导致联调返工
结论：前端按文档联调，字段名与后端实际返回不一致，反复沟通返工。
原因：文档未随代码更新，无契约校验。
解法：接口文档由 OpenAPI 注解自动生成并纳入 MR 审查；字段变更同步更新文档与 mock。
