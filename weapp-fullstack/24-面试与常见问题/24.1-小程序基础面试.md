## 概述

本篇章汇总微信小程序基础面试的高频考点，覆盖双线程模型、WXML 渲染原理、WXSS 与 rpx 适配、生命周期执行顺序、页面栈、组件通信、wx API 常见问题与基础库版本兼容。这些内容是小程序开发的底层原理，面试中常以「原理 + 追问 + 陷阱」的形式考察，也是后续进阶篇（性能、登录、支付）的基础。

```text
面试考察点概览：
1. 双线程模型 —— 逻辑层与视图层如何分工，setData 如何通信
2. 渲染原理 —— 数据绑定、条件渲染、列表渲染、key 的作用
3. 适配原理 —— rpx 换算规则与适配边界
4. 生命周期 —— onLoad/onShow/onReady/onHide/onUnload 执行顺序
5. 页面栈 —— 最多 10 层，五大路由 API 的区别
6. 组件与 API —— 组件通信方式、wx API 回调与基础库兼容
```

## 双线程模型与 WXML 渲染原理

**问题 1：请解释小程序的双线程模型**

```text
回答：
1. 小程序运行时分为逻辑层（App Service）与视图层（渲染层），两个线程相互独立
2. 逻辑层运行 JS 引擎：iOS 使用 JavaScriptCore，Android 使用 V8，开发者工具使用 NW.js
3. 视图层负责 WXML 模板与 WXSS 样式的解析渲染，运行在 WebView 中（iOS 为 WKWebView，Android 为 Chromium 内核）
4. 逻辑层与视图层不能直接共享数据，必须通过 setData 将数据从逻辑层传递到视图层
5. 双线程设计的原因：视图层 JS 被限制（不能操作 DOM、不能调用 wx API），保证渲染稳定与性能隔离
6. 因此小程序中不存在 document/window，必须使用 wx.* 体系 API
```

追问：为什么小程序要采用双线程而不是像浏览器一样单线程操作 DOM？

```text
回答：
1. 安全隔离：视图层脚本不可信，限制其能力可防止恶意代码操作渲染层
2. 性能隔离：逻辑层密集计算不阻塞渲染线程，setData 只传输数据而非 DOM 操作
3. 跨端一致性：双线程架构让同一套代码在 iOS/Android 表现一致
4. 代价：数据通信有序列化与传输开销，频繁或大量 setData 会造成性能瓶颈
```

**问题 2：setData 的原理是什么？为什么说它可能造成性能问题**

```text
回答：
1. 调用 this.setData({ key: value }) 时，数据会从逻辑层通过微信客户端原生桥接传输到视图层
2. 数据传输本质是 JSON 序列化 + 跨线程传递，视图层收到后 diff 出变化再更新渲染
3. this.data 会同步更新，但视图渲染是异步的，可通过第二个参数回调感知渲染完成
4. 性能问题来源：数据量大（序列化耗时）、频繁调用（通信次数多）、无意义更新（每次都全量传输变更数据）
5. 优化方向：只传变化的字段、合并多次 setData、避免在 setData 中放大数据（如把大数组整体回传）
```

```js
// setData 基础用法与回调
this.setData(
  { list: newList },
  () => { console.log('视图层渲染完成'); }
);
```

**问题 3：WXML 数据绑定 {{ }} 的渲染原理是什么？是单向还是双向**

```text
回答：
1. WXML 中 {{ }} 双大括号内可写表达式（简单运算、三元、字符串拼接、数组/对象取值），但不能写语句
2. 数据绑定是单向的：逻辑层数据变化通过 setData 驱动视图更新，视图层不能反向修改逻辑层数据
3. 视图层要改变数据，只能通过事件（bindtap 等）触发逻辑层方法，在方法内 setData
4. 模板中的 {{ }} 只在数据更新时重新求值，不存在浏览器中的脏检查机制
5. 常见的双向绑定需求（输入框）通过 input 事件 + setData 手动实现，没有 v-model 之类的语法糖
```

追问：{{ }} 内支持哪些表达式？

```text
回答：
1. 支持：算术运算 {{ a + b }}、逻辑运算 {{ a && b }}、三元 {{ a ? b : c }}、字符串拼接 {{ '前缀' + name }}
2. 支持：对象与数组取值 {{ obj.key }}、{{ arr[0] }}、组合使用 {{ [zero, 1, 2, 3, 4] }}
3. 不支持：语句（if/for/声明变量）、函数调用（{{ fn() }} 不生效，需借助 WXS 或预处理）
4. 大数据量模板中表达式应保持简单，复杂逻辑放 JS 侧或 WXS
```

**问题 4：wx:if 与 hidden 有什么区别，如何选择**

```text
回答：
1. wx:if 是条件渲染：为 false 时组件根本不创建/不渲染，切换时有创建销毁开销，初始渲染成本更低
2. hidden 始终渲染组件，仅通过 display: none 控制显示隐藏，切换开销小，但初始渲染成本更高
3. 选择原则：频繁切换（tab 切换、弹窗）用 hidden；低频切换或懒加载内容用 wx:if
4. wx:if 搭配 wx:elif / wx:else 实现多分支；block wx:if 可包裹多个节点而不新增节点
5. 面试常问：为什么 hidden 组件初始化也会执行生命周期 —— 因为组件已渲染，只是不可见
```

**问题 5：wx:for 列表渲染中 key 的作用是什么**

```text
回答：
1. key 用于标识列表中每一项的唯一性，帮助渲染层 diff 时复用节点、减少重渲染
2. 不写 key 时，列表重排会按位置复用节点，可能出现状态错乱（如 input 内容串位）
3. key 必须唯一且稳定，推荐用业务 id（如 {{item.id}}），不要用 index（索引变化导致复用错误）
4. 注意 key 的取值写法：wx:key="id" 表示取 item.id，wx:key="*this" 表示 item 本身是字符串/数字
5. 列表与 wx:for-index / wx:for-item 自定义索引与项变量名，避免嵌套循环变量冲突
```

**问题 6：小程序事件系统有哪些要点**

```text
回答：
1. 事件绑定用 bind 前缀（bindtap），阻止冒泡用 catch 前缀（catchtap）；还有 capture-bind / capture-catch 捕获阶段
2. 事件对象 e 中：e.currentTarget 是绑定事件的组件，e.target 是实际触发事件的组件（冒泡时两者可能不同）
3. 自定义数据通过 data-* 属性携带，在 e.currentTarget.dataset 中读取（属性名驼峰转换）
4. e.mark 可获取事件链上所有带 mark 的组件数据，用于跨组件取数
5. 事件冒泡会沿组件树向上传播，catch 可中断；捕获阶段从根向下，capture-catch 可中断捕获
6. 常见陷阱：dataset 中 data-user-id 需写成 e.currentTarget.dataset.userId（短横线转驼峰）
```

**问题 7：WXS 是什么？与普通 JS 有什么区别**

```text
回答：
1. WXS（WeiXin Script）是小程序的视图层脚本语言，可在 WXML 中直接调用，弥补模板表达式能力不足
2. 运行在视图层，与逻辑层 JS 隔离：不能调用 wx API、不能操作组件、不能 require 逻辑层模块
3. 语法接近 ES5，不支持 ES6+ 的大部分特性（箭头函数、let/const 部分支持、模板字符串不支持）
4. 典型用途：在模板中格式化金额、日期、价格，避免在 JS 中预处理每一条数据
5. 通过 <wxs module="format"> 定义模块，WXML 中 {{ format.price(item) }} 调用
6. 注意：WXS 中 Date 为独立实现，getDate 等个别方法与浏览器不一致，格式化日期需按 WXS 方式写
```

```xml
<wxs module="fmt">
  module.exports = {
    price: function (v) { return (v / 100).toFixed(2); }
  };
</wxs>
<text>{{ fmt.price(item.price) }}</text>
```

**问题 8：template、import、include 三种模板复用方式有什么区别**

```text
回答：
1. template 定义模板片段，通过 <template is="name" data="{{...}}" /> 引用，可传数据
2. import 只能引用 template，且作用域不传递：A import B，B import C，A 不能使用 C 的模板
3. include 是整体拷贝：将目标文件的全部内容（含非 template 代码）拷贝到当前位置，无作用域限制
4. 选择建议：纯模板复用用 import + template；需要共享整个文件内容（如公共 wxml 片段）用 include
5. 现代工程中更推荐自定义组件（Component）替代 template，能力更强、可传属性、可封装逻辑
```

**问题 9：逻辑层与视图层通信还有哪些限制**

```text
回答：
1. 传递的数据必须是可 JSON 序列化的，函数、Date 对象等会被丢失或转换，不要 setData 传函数
2. 数据大小有限制：单次 setData 数据建议不超过 256KB，过大可能渲染卡顿或警告
3. 频繁 setData 会被合并或丢弃（视图层来不及渲染），导致中间态丢失
4. 逻辑层无法直接读取视图层状态（如 DOM 高度），需通过 wx.createSelectorQuery() 异步查询
5. 组件内 data 更新同样走 setData，组件与页面之间数据不共享，需显式通信
```

## WXSS 与 rpx 适配原理

**问题 1：rpx 的适配原理是什么**

```text
回答：
1. rpx（responsive pixel）是微信小程序独有的响应式单位，以屏幕宽度为基准：750rpx 恒等于屏幕宽度
2. 换算公式：1rpx = 屏幕宽度(px) / 750，即设计稿 750 宽时 1px 设计稿 = 1rpx
3. 例：iPhone 6 宽度 375px，1rpx = 0.5px；iPhone X 宽度 375px 同样 1rpx = 0.5px
4. rpx 依据的是屏幕逻辑宽度（与 dpr 相关），不是物理像素，也不是固定像素值
5. 与 vw 的换算关系：1rpx = (100 / 750)vw = 0.1333vw
6. 适配边界：rpx 只按宽度等比缩放，高度、字体、边框在极端宽屏（iPad）下会异常放大
```

追问：在 iPad 或大屏上 rpx 会出现什么问题？

```text
回答：
1. iPad 屏幕逻辑宽度远大于手机（如 768px），750rpx 会渲染出很大的元素，页面被拉伸
2. 解决办法：页面容器设置 max-width（如 750rpx）并居中，限制内容最大宽度
3. 1px 边框在 rpx 下会被缩放为非整数像素，出现模糊，可用 px 或 transform: scale 处理
4. 字体建议用 px（设计规范字号固定），布局用 rpx，避免文字随屏幕无限放大
```

**问题 2：px、rpx、vw/vh、百分比分别在什么场景使用**

```text
回答：
1. rpx：布局尺寸、间距、宽高，跟随屏幕宽度等比缩放，是最常用的布局单位
2. px：固定尺寸，如 1px 边框、固定字号、头像尺寸等不随屏幕缩放的元素
3. vw/vh：相对视口，适合全屏页面、弹层定位（配合 rpx 使用可处理一些复杂场景）
4. 百分比：相对父容器，用于布局占比；注意百分比基准是父元素宽度，不是屏幕
5. 常见陷阱：rpx 在小屏手机可能小于 1px 被四舍五入，连续布局出现像素偏差
```

**问题 3：小程序 WXSS 支持哪些选择器，有什么限制**

```text
回答：
1. 支持：类选择器、id 选择器、标签选择器、后代选择器、并集选择器、属性选择器
2. 支持伪类：:hover（有限）、::after、::before；:first-child / :last-child 等大部分伪类可用
3. 不支持：通配符 * 选择器
4. 组件内样式隔离模式下，页面样式不能影响组件内部，组件样式默认也不影响外部
5. 常用布局：Flex（主轴/交叉轴）与 Grid 均支持，grid-template-columns 等属性可用
6. 全局样式写在 app.wxss，页面样式文件只作用于当前页面，组件样式只作用于组件
```

**问题 4：组件的样式隔离是怎么回事**

```text
回答：
1. Component 默认 styleIsolation: 'isolated'：组件内部样式不影响外部，外部样式（页面/app.wxss）也不影响组件内部
2. 可选值：apply-shared（页面样式可影响组件，组件样式不影响外部）、shared（互相影响，类似普通页面）
3. 穿透方式：组件根节点使用 :host 选择器可被外部样式影响（部分场景）；或通过 externalClasses 暴露外部类名
4. 陷阱：在组件 wxss 中直接写 .class 可能被隔离规则拦截，需理解 styleIsolation 与 :host
5. 面试常问：为什么组件样式写不生效 —— 优先检查 styleIsolation 与选择器是否命中组件内部节点
```

**问题 5：如何实现暗黑模式适配**

```text
回答：
1. 开启方式：app.json 中 themeLocation 指定 theme.json，配置 dark 主题下的导航栏/背景色
2. 样式层用媒体查询：@media (prefers-color-scheme: dark) 编写暗色样式
3. 也可用 CSS 变量：:root 定义 light 变量，暗色媒体查询内覆盖变量，组件与页面统一引用
4. 图片资源可提供暗色版本，用 CSS 变量控制 url 或使用小程序 image 的 mode 适配
5. 注意：暗黑模式需在微信「跟随系统」开启时生效，需真机验证深浅色切换
```

**问题 6：WXSS 与 CSS 相比有哪些差异**

```text
回答：
1. 基础语法与 CSS 一致，但新增 rpx 单位与全局样式隔离概念
2. 不支持部分 CSS 特性：如媒体查询中的部分语法、动画的某些属性在不同基础库支持度不同
3. 样式作用域：页面与组件样式默认隔离，app.wxss 为全局样式
4. 尺寸单位换算以 rpx 为主，1px 物理像素的实现需特殊处理（可用 transform 或直接 px）
5. 真机与模拟器对部分属性支持不一致（如 fixed 定位在输入框弹出键盘时的表现），需真机验证
```

**问题 7：1px 边框如何实现，为什么直接写 1px 会变粗**

```text
回答：
1. 高清屏 dpr=2/3 下，CSS 1px 实际占用 2/3 个物理像素行，视觉上偏粗
2. 方案一：transform: scale(0.5) 画 2px 再缩放为 1 物理像素
3. 方案二：使用 border 时配合媒体查询 -webkit-min-device-pixel-ratio 判断 dpr
4. 方案三：直接用 rpx（1rpx 在 375px 宽屏幕即 0.5px），实现简单但需注意非整数像素问题
5. 面试回答重点：说出 dpr 概念与 scale 方案即可，说明业务上常用 rpx 或工具类解决
```

**问题 8：页面样式与组件样式优先级如何理解**

```text
回答：
1. 同选择器优先级下，后加载的样式覆盖先加载的；页面 wxss 与组件 wxss 受隔离规则约束
2. 类选择器、id 选择器、内联 style 的优先级遵循 CSS 规则，!important 可用但应谨慎
3. 跨层覆盖：页面想覆盖组件样式，可用 styleIsolation: 'apply-shared' 或 externalClasses
4. 陷阱：在 app.wxss 定义组件同名类不会生效（isolated 隔离），这是新手最常见的「样式失效」
5. 调试技巧：使用开发者工具 WXSS 面板查看样式来源与覆盖链，而不是盲目加 !important
```

## 生命周期与页面栈

**问题 1：页面生命周期函数的执行顺序是什么**

```text
回答：
1. 首次打开页面：onLoad(options) → onShow() → onReady()
2. onLoad：页面初次加载时触发一次，可接收路由参数 options；页面未销毁不会再次触发
3. onShow：页面每次显示时触发（首次进入、从其他页面返回、切后台回前台）
4. onReady：页面初次渲染完成时触发一次，此时可操作 canvas、组件实例等渲染相关能力
5. onHide：页面隐藏时触发（跳转其他页面、切后台、打开半屏页面）
6. onUnload：页面销毁时触发（navigateBack 出栈、redirectTo 替换、reLaunch）
7. 完整流程：onLoad → onShow → onReady →（交互）→ onHide →（再次进入）→ onShow → ... → onUnload
```

追问：onLoad 与 onShow 有什么区别，什么时候该用哪个？

```text
回答：
1. onLoad 只执行一次，适合初始化数据、读取页面参数、拉取首次数据
2. onShow 每次显示都执行，适合刷新数据（从详情页返回列表页刷新状态）、统计曝光
3. 陷阱：把数据加载只写在 onLoad 中，从下级页面返回时数据不会刷新
4. 建议：首屏数据可在 onLoad 拉取，依赖「页面可见」状态刷新的逻辑放 onShow 并做防抖
```

**问题 2：App 的生命周期有哪些，与页面生命周期如何衔接**

```text
回答：
1. App 生命周期：onLaunch（小程序初始化时触发一次）→ onShow（小程序前台）→ onHide（小程序后台）
2. onLaunch 中可做：登录态检查、全局配置读取、版本更新检查（updateManager）
3. onError 捕获全局 JS 错误，onPageNotFound 处理页面不存在
4. 全局数据通过 getApp() 获取 App 实例上挂载的数据/方法
5. 衔接关系：先 App.onLaunch/onShow，再页面 onLoad/onShow；小程序切后台时页面先 onHide，App 再 onHide
6. 陷阱：onLaunch 中不能保证拿到用户信息（登录是异步的），需用回调或 Promise 通知后续逻辑
```

**问题 3：组件生命周期有哪些，与页面生命周期有什么不同**

```text
回答：
1. 组件生命周期（lifetimes）：created（实例创建，data 可用，不能 setData）→ attached（挂载到页面，可 setData）→ ready（组件渲染完成）→ moved → detached（销毁）
2. created 阶段不能调用 setData 与访问组件实例方法，attached 之后才安全
3. pageLifetimes 监听页面行为：show / hide / resize，用于组件感知页面显示状态
4. 组件没有 onLoad/onShow（除非通过 pageLifetimes），这是与 Page 最直观的差异
5. 陷阱：在 created 中请求数据可能丢失早期回调，建议在 attached 中发起
```

**问题 4：页面栈是什么？有什么限制**

```text
回答：
1. 页面栈是保存已打开页面的栈结构，getCurrentPages() 可获取当前页面栈实例数组
2. 限制：页面栈最多 10 层，超过后 navigateTo 会失败（fail 回调 reason 为 navigateTo:fail webview count limit exceed）
3. 栈顶是当前页面，navigateTo 入栈、navigateBack 出栈、redirectTo 替换栈顶
4. 实际场景：连续跳转详情页超过 10 层需要改用 redirectTo 或 reLaunch 控制栈深度
5. 面试常问：返回上一页时如何携带数据 —— 用 eventChannel（navigateTo 的 events）或全局变量/缓存
```

**问题 5：navigateTo、redirectTo、switchTab、reLaunch、navigateBack 有什么区别**

```text
回答：
1. navigateTo：保留当前页，跳转新页面入栈，可携带参数，不能跳 tabBar 页面
2. redirectTo：关闭当前页，用新页面替换，栈深度不变，不能跳 tabBar 页面
3. switchTab：跳转 tabBar 页面，会关闭所有非 tabBar 页面
4. reLaunch：关闭所有页面，打开新页面（可打开任意页面，包括 tabBar）
5. navigateBack：返回上一页，delta 指定返回层数；页面销毁触发 onUnload
6. 参数传递：url 后接 ?key=value，目标页 onLoad(options) 接收；参数需 encodeURIComponent 处理特殊字符
```

追问：navigateBack 如何向上一页传数据？

```text
回答：
1. 方式一：getCurrentPages() 获取上一页实例，直接调用其 setData 或方法（简单但耦合）
2. 方式二：使用事件通道 EventChannel（wx.navigateTo 的 events 参数 + 目标页 getOpenerEventChannel）
3. 方式三：全局变量（getApp().globalData）或本地缓存 wx.setStorageSync
4. 推荐：简单场景用方式一，跨页面复杂交互用 EventChannel
```

**问题 6：onReady 有什么特殊用途**

```text
回答：
1. onReady 在页面初次渲染完成后触发，此时才能安全获取渲染结果（查询节点、操作 canvas）
2. 查询节点：wx.createSelectorQuery() 在 onReady 中才能拿到正确尺寸
3. canvas 2d / webgl 初始化放在 onReady 中，onLoad 中调用可能拿到空对象
4. 注意 onReady 只触发一次，页面重新显示（onShow）时如需重新计算布局要自己处理
5. 陷阱：在 onLoad 中查询节点高度返回 0 —— 因为渲染尚未完成
```

**问题 7：页面参数传递有哪些方式，各自适用场景**

```text
回答：
1. URL 参数：navigateTo url 拼接，适合简单数据（id、类型），注意 encodeURIComponent
2. 全局数据：getApp().globalData，适合登录态、配置等跨页面共享数据
3. 本地缓存：wx.setStorageSync / getStorageSync，适合较大数据与持久化
4. EventChannel：navigateTo 时通过 events 传递回调，适合「详情页操作后通知列表页」
5. 组件间：properties / triggerEvent，页面内组件通信用
6. 陷阱：URL 传对象需 JSON.stringify + encodeURIComponent，中文与特殊字符不编码会截断
```

**问题 8：生命周期中常见的时序陷阱有哪些**

```text
回答：
1. onLoad 中调用需要渲染结果的 API（节点查询、canvas）拿不到数据 —— 应放 onReady
2. 只在 onLoad 拉数据，返回页面不刷新 —— 刷新逻辑应放 onShow 并防抖
3. setData 在 onHide/onUnload 后仍执行 —— 数据更新无效且浪费，应判断页面状态
4. App.onLaunch 中异步登录，页面 onLoad 时登录态未就绪 —— 用 Promise/回调统一等待
5. 组件 created 中 setData 报错 —— created 阶段不能 setData，移到 attached
6. 切后台再回前台，页面数据过期 —— 监听 App.onShow 或 pageLifetimes.show 刷新
```

## 组件与组件通信

**问题 1：为什么要使用自定义组件，与 template 有什么区别**

```text
回答：
1. 自定义组件（Component）封装结构 + 样式 + 逻辑，可复用、可传参、可向外发事件
2. template 只有结构复用，逻辑仍需写在页面 JS 中，无法真正封装
3. Component 有独立生命周期、data、methods、observers，行为像一个迷你页面
4. 组件可被多个页面复用，配合 behaviors 可进一步抽取公共逻辑
5. 面试回答重点：组件解决的是「功能单元复用」，template 解决的是「结构片段复用」
```

**问题 2：父组件如何向子组件传值**

```text
回答：
1. 通过 properties（属性）声明接收，父组件在 wxml 中 <my-comp title="{{t}}" /> 传值
2. properties 可声明类型（String/Number/Object/Array 等）与默认值，类型不符会有警告
3. 属性变化时可用 observers 监听（类似 watch），在属性变化后做处理
4. 注意：properties 中的值在子组件内部可通过 this.data 读取，也可 setData 到 data 中转
5. 陷阱：属性传对象时是引用传递，子组件内修改会污染父组件数据，应拷贝后修改
```

```js
// 子组件定义 properties
Component({
  properties: {
    title: { type: String, value: '默认标题' },
    item: { type: Object, value: {} }
  },
  observers: {
    'title': function (val) {
      console.log('title 变化为', val);
    }
  }
});
```

**问题 3：子组件如何向父组件传递事件和数据**

```text
回答：
1. 子组件调用 this.triggerEvent('事件名', detail, options) 抛出自定义事件
2. 父组件在 wxml 中 bind:事件名="handleFn" 监听，回调参数 e.detail 携带数据
3. options 可配置 bubbles（冒泡）、composed（跨组件边界）、capturePhase（捕获）
4. 与原生事件区分：自定义事件默认不冒泡，需要 bubbles: true 才可跨组件冒泡
5. 陷阱：事件名用小写或短横线风格，驼峰事件名在部分基础库绑定有问题
```

```js
// 子组件抛出事件
methods: {
  onTap() {
    this.triggerEvent('select', { id: this.data.item.id }, { bubbles: true });
  }
}
// 父组件监听
// <my-comp bind:select="onSelect" />
// onSelect(e) { const { id } = e.detail; }
```

**问题 4：组件间通信方式有哪些，如何选择**

```text
回答：
1. 父传子：properties 属性传值 —— 最常用
2. 子传父：triggerEvent 自定义事件 —— 最常用
3. 获取实例：父组件 this.selectComponent('#id') 调用子组件方法或读取数据
4. 全局通信：getApp().globalData、事件总线（自封装 EventBus）、全局 store（如 mobx-miniprogram）
5. 兄弟组件：通过共同父组件中转（属性 + 事件），或全局数据/事件总线
6. 跨页面：EventChannel、全局数据、本地缓存
7. 选择原则：同层就近通信用属性/事件，跨层级或跨页面用全局机制，避免过度设计
```

**问题 5：selectComponent 的用法与注意事项**

```text
回答：
1. this.selectComponent('#id') 或 '.class' 返回匹配的第一个组件实例
2. 返回实例后可调用其方法、读取 data、甚至触发其自定义方法
3. 页面中也可用 selectAllComponents 获取全部匹配实例
4. 注意：只能在组件挂载后调用（onReady 之后），onLoad 中调用返回 null
5. 该方式是命令式通信，耦合较高，优先用属性/事件，selectComponent 用于「父主动调用子」
```

**问题 6：behaviors 是什么，解决什么问题**

```text
回答：
1. behaviors 是组件间共享逻辑的机制（类似 mixin），可共享 data、properties、methods、生命周期
2. 多个组件通过 behaviors: [behaviorA] 引入公共逻辑，减少重复代码
3. 同名冲突规则：组件自身的 data/methods 优先级高于 behaviors，后引入的 behaviors 优先于先引入的
4. 页面也可使用 behaviors（Page 支持），常用于页面级公共逻辑抽取
5. 陷阱：behaviors 中定义生命周期会与组件自身生命周期合并执行，顺序为 behaviors 先、组件自身后
```

**问题 7：插槽（slot）如何使用**

```text
回答：
1. 默认插槽：组件 wxml 中写 <slot />，父组件传入的内容会渲染到该位置
2. 具名插槽：<slot name="header" />，父组件用 <view slot="header"> 指定插入位置
3. 组件需在 options 中声明 multipleSlots: true 才支持多个具名插槽（默认仅支持一个）
4. 插槽内容中的事件绑定仍指向父组件作用域，数据绑定指向父组件数据
5. 陷阱：组件内部插槽区域样式受组件样式隔离影响，外部传入节点样式用父页面类名控制
```

**问题 8：如何理解 Component 的 observers 与 computed 类能力**

```text
回答：
1. observers 监听 data/properties 变化，类似 Vue 的 watch，变化后执行回调
2. 可监听单字段 'a' 或组合字段 'a, b'，也可监听路径 'obj.a'
3. 组件没有内置 computed，通常用 observers + 派生字段实现，或用 behavior 封装
4. 注意：observers 中修改被监听字段会再次触发，需避免死循环；初始化时也可能触发一次
5. 与 setData 的关系：setData 改变字段会触发对应 observers，但 observers 中 setData 要谨慎控制频率
```

## wx API 与基础库兼容

**问题 1：wx.request 有哪些关键细节**

```text
回答：
1. 只能请求 HTTPS 域名，且域名需在小程序后台配置为 request 合法域名（开发工具可勾选不校验）
2. 默认超时 60 秒，可在 app.json 或 wx.request 的 timeout 字段配置
3. 并发请求数限制 10 个，超出部分会排队或失败（fail 提示）
4. 请求头默认带 content-type: application/json；GET 参数走 url，POST 走 data
5. 返回的 res.data 是响应体，statusCode 需自行判断（200 才是成功）
6. 没有 wx.requestSync 同步版本，如需串行可用 async/await + Promise 封装
7. 常见封装：统一 baseURL、统一鉴权头（Authorization: Bearer token）、统一错误提示与 401 跳登录
```

```js
// 封装后的请求示例
const request = (url, data = {}, method = 'GET') => {
  return new Promise((resolve, reject) => {
    wx.request({
      url: BASE_URL + url,
      method, data,
      header: { Authorization: 'Bearer ' + wx.getStorageSync('token') },
      success: (res) => {
        if (res.statusCode === 200) resolve(res.data);
        else if (res.statusCode === 401) { /* 登录态失效处理 */ }
        else reject(res);
      },
      fail: reject
    });
  });
};
```

**问题 2：wx API 的 success/fail/complete 回调与 Promise 风格怎么理解**

```text
回答：
1. 早期 wx API 全部是回调风格：success（成功）/ fail（失败）/ complete（无论成败都执行）
2. 基础库 2.10.2+ 大部分异步 API 支持 Promise 风格：不传 success/fail/complete 时返回 Promise
3. 混用注意：传了 success 回调就不会返回 Promise 的 then 结果，两者二选一
4. 推荐工程实践：统一用 async/await + Promise 封装，代码更线性
5. 陷阱：部分 API 仍只支持回调（如 wx.login 新版本支持 Promise），先查文档再写
```

**问题 3：wx.getStorageSync 与 wx.getStorage 有什么区别**

```text
回答：
1. 同步 API（Sync 后缀）：wx.getStorageSync / setStorageSync / removeStorageSync / clearStorageSync
2. 异步 API：wx.getStorage / setStorage / removeStorage，带 success/fail 回调
3. 同步 API 会阻塞 JS 线程，适合小数据频繁读写；大数据或频繁操作建议用异步版本
4. 存储上限：单个 key 最大 1MB，总上限 10MB（本地缓存），超出会失败
5. 数据会序列化为字符串存储，对象直接存取即可，Date 等特殊类型注意兼容
6. 面试常问：为什么用 sync 版本 —— 同步获取在生命周期中读取方便，但大量使用影响性能
```

**问题 4：小程序授权流程（用户信息、位置等）有什么坑**

```text
回答：
1. wx.getUserInfo 已废弃，头像昵称通过 open-type="chooseAvatar" 按钮 + input type="nickname" 获取
2. 位置等权限用 wx.authorize 申请，scope.userLocation 等需在用户点击事件中触发
3. 用户拒绝授权后 wx.authorize 直接 fail，需引导用户去设置页 wx.openSetting 重新授权
4. 授权状态可用 wx.getSetting 查询，再次调用不会弹窗而是直接 fail，需判断处理
5. 陷阱：不要在 onLoad 中直接调 wx.authorize，必须在用户点击等手势回调中调用
6. 注意隐私协议要求：涉及用户信息的接口需在小程序后台配置用户隐私保护指引
```

**问题 5：基础库版本兼容如何处理**

```text
回答：
1. 基础库是微信客户端内置的小程序运行时，版本由用户微信决定，开发者不能强制升级
2. 后台可设置最低基础库版本（低于该版本无法打开小程序），开发者工具中可设置调试用 libVersion
3. 能力检测用 wx.canIUse('api名.方法名.参数名') 判断 API、组件、属性是否可用
4. 获取当前基础库版本：wx.getSystemInfoSync().SDKVersion 或 wx.getAppBaseInfo()
5. 降级方案：低版本用替代 API 实现，或用低版本 API 兜底（如 getUserInfo 旧方案）
6. 陷阱：新 API 直接调用在低版本上会报 undefined，必须 canIUse 判断后再调用
```

```js
// 能力检测示例
if (wx.canIUse('getAppBaseInfo')) {
  wx.getAppBaseInfo();
} else {
  wx.getSystemInfoSync();
}
```

**问题 6：如何决定小程序的最低基础库版本**

```text
回答：
1. 依据：业务使用的 API/组件/特性的最低基础库要求，取最大值
2. 参考官方版本分布数据：覆盖率需达到业务可接受比例（如 99%+），其余用户提示升级微信
3. 设置位置：小程序后台「设置 - 基本设置 - 基础库最低版本」
4. 策略：新项目直接设较高版本（如 2.20+）减少兼容代码；老项目渐进提升并做好降级
5. 注意：设置过低版本意味着要为大量旧 API 写兼容分支，维护成本高
```

**问题 7：有哪些容易踩坑的 wx API 使用细节**

```text
回答：
1. wx.showToast 默认 icon 只有 success/none，loading 需 wx.showLoading 且要手动 hideLoading
2. wx.showModal 的 success 回调中 res.confirm 判断确认；新基础库支持 editable 输入框
3. wx.navigateTo 不能跳 tabBar 页，会 fail；switchTab 不能带参数
4. wx.setNavigationBarTitle 需在页面 onShow/onReady 中调用才生效（onLoad 中调用可能被覆盖）
5. wx.getSystemInfo 已废弃，新 API 拆分为 getWindowInfo/getDeviceInfo/getAppBaseInfo 等
6. 定时器 setInterval 在页面销毁后不会自动清理，需在 onUnload 中 clearInterval，防止内存泄漏
7. wx.login 每次调用都会换 code，code 5 分钟内有效且只能使用一次，不能缓存复用
```

**问题 8：页面数据初始化放在哪里最合适，为什么**

```text
回答：
1. 依赖渲染结果的（节点查询）放 onReady；依赖每次可见的（曝光、刷新）放 onShow
2. 纯数据初始化放 onLoad 即可，避免 onShow 重复请求
3. 组件实例相关操作（selectComponent）必须在 onReady 之后
4. 原则：能放 onLoad 不放 onShow，能放 onShow 不放 onReady，按依赖最小化选择
5. 面试回答加分点：提到 onLoad 只一次、onShow 每次、onReady 渲染完成后的三角关系
```

## 面试重点总结

```text
高频考点编号：
1. 双线程模型：逻辑层与视图层分离，setData 是唯一通信通道，序列化传输有性能成本
2. 渲染原理：{{ }} 单向绑定、wx:if 惰性 vs hidden 常驻、wx:for 必须配稳定 key
3. rpx 适配：750rpx = 屏幕宽度，按宽度等比缩放，大屏需 max-width 限制
4. 生命周期：onLoad(一次) → onShow(每次) → onReady(渲染完成一次)，页面栈最多 10 层
5. 组件通信：properties 下传、triggerEvent 上抛、selectComponent 命令式、全局机制兜底
6. 兼容性：canIUse 能力检测、最低基础库版本策略、wx API 回调与 Promise 双风格
```

```text
面试答题口诀：
1. 先讲原理（为什么这么设计），再讲用法（怎么用），最后讲坑（注意什么）
2. 涉及性能的题必答 setData 通信开销与优化方向
3. 涉及渲染的题必答 key 与 wx:if/hidden 选择依据
4. 涉及生命周期的题必答「一次 vs 每次 vs 渲染完成」的三角定位
5. 不会的题先确认基础库版本与场景，再给兼容方案，体现工程思维
```

## 最佳实践与踩坑记录

### 最佳实践

1. 页面数据请求统一封装（Promise + async/await），success/fail 里做统一错误提示与 401 处理
2. 列表渲染永远写 wx:key，用业务唯一 id，不用 index
3. 频繁切换的显隐用 hidden，低频懒加载用 wx:if
4. setData 只传变化字段，大列表用「数据路径」局部更新，避免整体回传
5. 定时器、事件监听在 onUnload / detached 中统一清理，防止内存泄漏
6. 涉及新 API 先查基础库要求，统一用 canIUse 做能力检测并写降级分支
7. 组件复用优先用 Component + properties/triggerEvent，template 只做纯结构复用
8. 页面栈超过 5 层的跳转链用 redirectTo 控制，避免 navigateTo 触发 10 层上限

### 踩坑记录

坑 1：onLoad 中查询节点高度返回 0
结论：在 onLoad 里用 createSelectorQuery 获取元素尺寸，结果全是 0。
原因：onLoad 时页面尚未渲染，节点还不存在。
解法：查询逻辑移到 onReady 中执行，或 onLoad 中通过 wx.nextTick 延迟。

坑 2：wx:for 不写 key，输入框内容串位
结论：列表重排或删除中间项后，input 里的旧值出现在错误行。
原因：无 key 时渲染层按位置复用节点，组件状态被错误复用。
解法：wx:key 绑定稳定唯一 id，删除、排序场景必须配 key。

坑 3：navigateTo 跳转 tabBar 页面失败
结论：点击后无反应，fail 回调提示 navigateTo:fail can not navigateTo a tabbar page。
原因：navigateTo/redirectTo 不能打开 tabBar 页面。
解法：改用 wx.switchTab；如需携带参数，用全局变量或缓存传递。

坑 4：组件内写的样式不生效
结论：自定义组件里写的类名样式在真机上完全无效。
原因：Component 默认 styleIsolation 为 isolated，页面样式与组件样式互相隔离。
解法：确认选择器命中组件内部节点；需要外部覆盖时设置 styleIsolation 或 externalClasses。

坑 5：setInterval 未清理导致页面卡顿
结论：页面反复进出后越来越卡，内存持续增长。
原因：页面销毁后定时器仍在执行，不断 setData 更新已销毁页面。
解法：onUnload / detached 中 clearInterval；setData 前判断页面状态。

坑 6：新 API 在低版本基础库报 undefined
结论：wx.getAppBaseInfo 等新 API 在部分用户手机上直接报错。
原因：用户微信基础库版本低于 API 要求版本。
解法：后台设置合理最低基础库版本，代码中 canIUse 判断后降级。

坑 7：setData 传函数导致数据丢失
结论：把函数放进 setData 对象，视图层拿到的值是空或报错。
原因：逻辑层与视图层通信走 JSON 序列化，函数无法序列化。
解法：只传可序列化数据；需要回调逻辑放 success 回调或事件处理。

坑 8：switchTab 无法携带 url 参数
结论：switchTab 后 onLoad(options) 拿不到参数，页面数据空白。
原因：switchTab 规范不允许带 query 参数。
解法：用全局变量（getApp().globalData）或本地缓存传递，onShow 中读取。
