## 概述

预约服务小程序是生活服务类业务（美容美发、健身、家政、医疗、汽车保养等）的标准 C 端形态：用户在小程序内完成「选服务 → 选门店 → 选日期时段 → 提交 → 支付/免费」的完整预约闭环，商家在 Vue 管理后台维护门店、服务与排期，处理订单与退款。它与电商小程序最大的区别在于核心资源是「时间 + 门店产能」而非商品库存，因此排期管理、时段容量控制、防超卖是后台设计的重中之重。

本篇章以「微信小程序 + SpringBoot 后台 + Vue 管理端」为例，完整讲解预约流程设计、排期表与时段容量、订阅消息通知、取消与改期的订单状态机，每个知识点都给出可运行的代码，最后提供两个完整场景和一线踩坑记录。建议与电商小程序的订单体系对照学习，两者共享支付、回调、状态机等大量设计。

```text
预约服务小程序核心知识点：
1. 预约流程 —— 选服务-选门店-选日期时段-提交-支付/免费，前端五步引导 + 后端订单落库
2. 排期管理 —— 排期表按「门店+日期+时段+服务」维度维护可预约容量，防止超卖
3. 消息通知 —— 一次性订阅消息 + 服务端定时任务发送预约成功/开始前提醒/结果通知
4. 取消与改期 —— 订单状态机（待支付-已支付-已完成-已取消）保证状态流转安全
5. 支付集成 —— 付费预约走微信支付，免费预约直接确认，取消退款走微信退款
6. 管理端 —— Vue 管理后台维护门店/服务/排期，处理订单、退款与经营数据
```

## 预约流程设计

预约流程是预约类小程序的业务主干，任何门店、排期、支付设计都围绕这条链路展开。标准流程分五步，每一步都是独立的页面或页面区块：

```text
预约五步流程：
1. 选服务 —— 服务列表/服务详情页，展示价格、时长、门店适用范围
2. 选门店 —— 门店列表（支持定位排序），展示营业时间与距离
3. 选日期时段 —— 日历选日期，按日加载时段格子，展示剩余可约数
4. 提交 —— 填写联系人姓名、手机号，确认订单信息
5. 支付/确认 —— 付费服务拉起微信支付；免费服务直接确认成功
```

前端五步的关键是「时段选择」：服务端必须返回每个时段的剩余容量，前端在格子上直接展示「剩 N」「已满」两种状态，并禁止选择已满时段。容量数据必须由服务端计算下发，前端不能自行推断，否则会出现界面显示可约、提交时却提示已满的体验断层。

小程序端时段选择与提交的完整代码：

```js
// pages/booking/confirm.js —— 确认预约页
Page({
  data: {
    service: null,       // 选中的服务
    shop: null,          // 选中的门店
    date: '',            // 选中的日期，格式 yyyy-MM-dd
    slotList: [],        // 当日可选时段列表
    selectedSlot: null,  // 当前选中的时段
    contactName: '',
    contactPhone: '',
    submitting: false
  },
  // 日期变化后重新拉取该日排期
  onDateChange(e) {
    this.setData({ date: e.detail.value, selectedSlot: null })
    this.loadSlots(e.detail.value)
  },
  loadSlots(date) {
    wx.request({
      url: `${getApp().globalData.baseUrl}/api/schedule/slots`,
      method: 'GET',
      data: {
        shopId: this.data.shop.id,
        serviceId: this.data.service.id,
        date: date
      },
      success: (res) => {
        if (res.data.code === 0) {
          this.setData({ slotList: res.data.data })
        }
      }
    })
  },
  selectSlot(e) {
    const slot = e.currentTarget.dataset.slot
    if (slot.available <= 0) {
      wx.showToast({ title: '该时段已约满', icon: 'none' })
      return
    }
    this.setData({ selectedSlot: slot })
  },
  submit() {
    if (!this.data.selectedSlot) {
      wx.showToast({ title: '请选择服务时段', icon: 'none' })
      return
    }
    if (!/^1\d{10}$/.test(this.data.contactPhone)) {
      wx.showToast({ title: '手机号格式不正确', icon: 'none' })
      return
    }
    this.setData({ submitting: true })
    wx.request({
      url: `${getApp().globalData.baseUrl}/api/order/create`,
      method: 'POST',
      data: {
        serviceId: this.data.service.id,
        shopId: this.data.shop.id,
        scheduleId: this.data.selectedSlot.scheduleId,
        contactName: this.data.contactName,
        contactPhone: this.data.contactPhone
      },
      success: (res) => {
        if (res.data.code !== 0) {
          wx.showToast({ title: res.data.msg, icon: 'none' })
          return
        }
        const order = res.data.data
        if (order.needPay) {
          // 付费预约：拉起微信支付（参数由后台统一下单生成）
          wx.requestPayment({
            timeStamp: order.payParams.timeStamp,
            nonceStr: order.payParams.nonceStr,
            package: order.payParams.package,
            signType: 'RSA',
            paySign: order.payParams.paySign,
            success: () => this.gotoResult(order.id, 'paid'),
            fail: () => this.gotoResult(order.id, 'unpaid')
          })
        } else {
          // 免费预约：直接确认成功
          this.gotoResult(order.id, 'free')
        }
      },
      complete: () => this.setData({ submitting: false })
    })
  },
  gotoResult(id, status) {
    wx.redirectTo({ url: `/pages/order/result?id=${id}&status=${status}` })
  }
})
```

预约流程设计的核心原则是「前端引导、后端校验」：前端把流程拆成清晰步骤降低用户门槛，后端对每一步做幂等与校验（服务是否可约、门店是否营业、时段是否还有容量、手机号格式），任何一步失败都要返回可读的中文错误信息并在前端 toast 展示。订单创建成功但支付未完成时，订单处于待支付状态，此时时段容量应处于「已占用」还是「未占用」需要产品决策：常见做法是下单即扣减容量并给 30 分钟支付宽限期，超时自动释放，防止用户反复占位。

```text
预约流程设计要点：
1. 五步流程 —— 选服务-选门店-选日期时段-提交-支付/免费，逐步降低决策成本
2. 时段数据 —— 剩余容量由服务端计算下发，前端只做展示与禁用
3. 表单校验 —— 联系人手机号等在前端正则预校验，后端再用注解二次校验
4. 付费/免费 —— 免费服务创建订单即成功；付费服务创建订单后拉取支付参数
5. 容量占用时机 —— 下单即扣减容量 + 30 分钟支付宽限期，超时自动释放
6. 幂等设计 —— 前端防重复提交（submitting 标志），后端按用户+时段做唯一约束
```

## 排期管理

排期管理是预约类小程序与电商类最大的差异点：电商卖的是库存商品，预约卖的是「某个门店在某个时间段的产能」。排期表的最小粒度是「门店 + 服务 + 日期 + 时段」，每个粒度维护总容量（capacity）与已预约数（booked_count）。

```text
排期表核心设计：
1. 排期维度 —— 门店+服务+日期+时段 唯一确定一个可预约单元（schedule_slot）
2. 时段模板 —— 管理端配置「每周几、几点到几点、容量」，批量生成未来 N 天排期
3. 休息日 —— 门店休息日、节假日不生成排期，或单独标记不可约
4. 容量控制 —— 预约时原子扣减 booked_count，达到 capacity 即满
5. 关闭/暂停 —— 管理端可临时关闭某时段（停约），不影响已约订单
6. 数据量 —— 14 天 × 每店每天 8 时段 × 多门店，用批量生成避免逐条插入
```

排期表建表语句：

```sql
-- schedule_slot.sql —— 时段排期表
CREATE TABLE schedule_slot (
    id           BIGINT PRIMARY KEY AUTO_INCREMENT,
    shop_id      BIGINT       NOT NULL COMMENT '门店ID',
    service_id   BIGINT       NOT NULL COMMENT '服务ID',
    biz_date     DATE         NOT NULL COMMENT '排期日期',
    start_time   VARCHAR(5)   NOT NULL COMMENT '开始时间 HH:mm',
    end_time     VARCHAR(5)   NOT NULL COMMENT '结束时间 HH:mm',
    capacity     INT          NOT NULL DEFAULT 1 COMMENT '该时段总容量',
    booked_count INT          NOT NULL DEFAULT 0 COMMENT '已预约数',
    status       TINYINT      NOT NULL DEFAULT 1 COMMENT '1可约 0暂停',
    version      INT          NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
    UNIQUE KEY uk_shop_service_date (shop_id, service_id, biz_date, start_time),
    KEY idx_shop_date (shop_id, biz_date)
) COMMENT '时段排期表';
```

排期由后台定时任务批量生成，避免运营每天手工建排期。生成逻辑：遍历所有门店，对每个门店按「时段模板 + 未来 N 天」插入排期，门店休息日跳过，重复数据用 INSERT IGNORE 去重（天然幂等，任务重复执行不会产生脏数据）：

```java
// ScheduleGenerateJob.java —— 每日凌晨生成未来 14 天排期
@Component
public class ScheduleGenerateJob {

    @Autowired
    private ShopMapper shopMapper;
    @Autowired
    private SlotTemplateMapper slotTemplateMapper;
    @Autowired
    private ScheduleMapper scheduleMapper;
    @Autowired
    private HolidayMapper holidayMapper;

    @Scheduled(cron = "0 30 0 * * ?") // 每天 00:30 执行
    public void generate() {
        List<Shop> shops = shopMapper.selectAll();
        for (Shop shop : shops) {
            for (SlotTemplate t : slotTemplateMapper.selectByShop(shop.getId())) {
                for (int i = 0; i < 14; i++) {
                    LocalDate day = LocalDate.now().plusDays(i);
                    if (holidayMapper.isHoliday(shop.getId(), day)) {
                        continue; // 门店休息日不生成排期
                    }
                    scheduleMapper.insertIgnore(ScheduleSlot.builder()
                            .shopId(shop.getId())
                            .serviceId(t.getServiceId())
                            .bizDate(day)
                            .startTime(t.getStartTime())
                            .endTime(t.getEndTime())
                            .capacity(t.getCapacity())
                            .bookedCount(0)
                            .status(1)
                            .build());
                }
            }
        }
    }
}
```

防超卖是排期管理的核心难点。「先查询剩余容量，再判断大于 0 后更新」的写法在并发下必然超卖：两个请求同时读到剩余 1，都通过判断，都执行更新，结果预约数变成 2。正确做法是让「判断 + 扣减」成为一条原子语句：

```sql
-- ScheduleMapper.xml —— 原子扣减容量（影响行数 = 1 才算成功）
UPDATE schedule_slot
SET booked_count = booked_count + 1, version = version + 1
WHERE id = #{scheduleId}
  AND status = 1
  AND booked_count < capacity;
```

```java
// ScheduleService.java —— 预约占用时段
public boolean tryOccupy(Long scheduleId) {
    // 优先走 Redis 扣减做前置校验（可选），数据库条件更新是最终防线
    return scheduleMapper.occupy(scheduleId) == 1;
}
```

高并发场景可以在数据库之前加一层 Redis 原子扣减，把热点请求挡在数据库外：用 `INCR schedule:slot:{id}` 与容量比对，超卖风险由数据库条件更新兜底；扣减失败（返回负数）时补偿 `DECR` 回去。无论哪一层实现，最终一致性都以数据库为准。

时段查询接口返回给前端的字段应包含：scheduleId、startTime、endTime、available（剩余可约数 = capacity - booked_count，SQL 中直接计算）、status。前端只消费这些字段，不做任何容量推算。

```text
排期管理要点：
1. 排期建模 —— 门店+服务+日期+时段为最小单元，唯一索引防重复
2. 批量生成 —— 定时任务按模板生成未来 N 天排期，INSERT IGNORE 幂等
3. 防超卖 —— 条件更新 UPDATE ... WHERE booked_count < capacity，影响行数判断成败
4. Redis 加速 —— 热点时段先用 Redis 原子扣减，数据库兜底保证最终一致
5. 状态管理 —— 暂停时段不影响已约订单，只禁止新预约
6. 容量释放 —— 取消/改期必须反向释放容量，防止排期表被占满
```

## 消息通知

预约类业务的用户触达高度依赖微信订阅消息：下单成功通知、服务开始前提醒、服务完成回访、取消确认等。订阅消息分两类：

```text
订阅消息类型：
1. 一次性订阅 —— 用户每点击一次授权，服务端获得一次发送额度，发完即失效
2. 长期订阅 —— 一次订阅可长期多次发送，仅限政务民生、医疗、交通、教育等公共服务类目
3. 授权时机 —— wx.requestSubscribeMessage 必须在用户点击行为（如提交订单）的调用栈内触发
4. 模板申请 —— 每个模板有唯一 tmplId，字段与内容需在公众平台审核通过
5. 额度管理 —— 服务端记录每个用户对每个模板的剩余额度，发送前检查
6. 发送通道 —— 服务端用 access_token 调 subscribeMessage.send 接口下发
```

小程序端在用户提交订单成功后、跳转结果页之前请求订阅授权。一次可以带多个模板 ID（如「预约成功通知」+「服务提醒」），返回结果以模板 ID 为 key：

```js
// pages/order/result.js —— 下单成功后请求订阅
subscribeNotify() {
  wx.requestSubscribeMessage({
    tmplIds: ['TMPL_APPOINT_SUCCESS', 'TMPL_APPOINT_REMINDER'],
    success: (res) => {
      // res['TMPL_APPOINT_SUCCESS'] 的值为 'accept' | 'reject' | 'ban'
      const granted = Object.keys(res)
        .filter(k => res[k] === 'accept')
        .map(k => k)
      // 把授予的模板额度上报服务端记账，发送前据此检查
      wx.request({
        url: `${getApp().globalData.baseUrl}/api/subscribe/record`,
        method: 'POST',
        data: { orderId: this.data.orderId, tmplIds: granted }
      })
    },
    fail: (err) => {
      // 用户拒绝或接口失败都不阻塞主流程，预约照常进行
      console.error('订阅授权失败', err)
    }
  })
}
```

服务端发送订阅消息的完整链路：取 access_token（带缓存）→ 检查用户对该模板的剩余额度 → 调 subscribeMessage.send 下发 → 处理错误码。access_token 必须缓存复用，频繁刷新会触发接口限流：

```java
// WechatTokenService.java —— access_token 缓存（建议用稳定版接口）
@Component
public class WechatTokenService {

    @Value("${wechat.appid}")
    private String appid;
    @Value("${wechat.secret}")
    private String secret;
    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    public String getStableAccessToken() {
        String cached = redisTemplate.opsForValue().get("wechat:access_token");
        if (cached != null) {
            return cached;
        }
        // 稳定版接口：POST https://api.weixin.qq.com/cgi-bin/stable_token
        // 参数：{"grant_type":"client_credential","appid":...,"secret":...,"force_refresh":false}
        // 返回：{"access_token":"...","expires_in":7200}
        String token = wechatClient.getStableToken(appid, secret);
        redisTemplate.opsForValue().set("wechat:access_token", token,
                Duration.ofSeconds(7000)); // 提前 200 秒过期，避免边界失效
        return token;
    }
}
```

```java
// SubscribeMessageService.java —— 发送预约提醒
public void sendReminder(Order order) {
    // 1. 检查额度：一次性订阅额度用一次少一次，无额度不发
    if (!subscribeRepo.hasQuota(order.getUserId(), TMPL_REMINDER)) {
        return;
    }
    // 2. 组装模板数据，字段名与模板审核通过的 key 一一对应
    Map<String, Object> data = new HashMap<>();
    data.put("thing1", Map.of("value", abbreviate(order.getServiceName(), 20)));
    data.put("time2", Map.of("value", order.getStartTime().format(DATE_TIME_FMT)));
    data.put("thing3", Map.of("value", abbreviate(order.getShopName(), 20)));
    // 3. 调用发送接口，扣减本地额度
    WechatResult result = wechatClient.subscribeSend(
            getStableAccessToken(),
            order.getOpenid(),
            TMPL_REMINDER,
            "pages/order/detail?id=" + order.getId(),
            data);
    if (result.getErrcode() == 43101) {
        // 43101：用户拒收/未订阅，注销本地额度，避免后续无效发送
        subscribeRepo.clearQuota(order.getUserId(), TMPL_REMINDER);
    }
}
```

定时提醒是预约业务的标配：服务开始前 2 小时提醒用户，减少爽约率。实现方式是 Spring 定时任务扫描「次日/当日即将开始」的已支付订单，逐个发送：

```java
// RemindJob.java —— 每日 08:00 发送当日预约提醒
@Component
public class RemindJob {

    @Scheduled(cron = "0 0 8 * * ?")
    public void sendTodayReminder() {
        // 查询今天有服务且状态为已支付的订单
        List<Order> orders = orderMapper.selectByDateAndStatus(LocalDate.now(), OrderStatus.PAID);
        for (Order order : orders) {
            try {
                subscribeMessageService.sendReminder(order);
            } catch (Exception e) {
                log.error("提醒发送失败 orderId={}", order.getId(), e);
            }
        }
    }
}
```

定时任务只做扫描和编排，单个发送失败不能中断整批任务，必须 try-catch 隔离并记录日志，方便事后补偿。发送成功与否建议落一张 message_log 表（订单号、模板、状态、错误码、时间），既便于排查「用户为什么没收到」，也是与用户沟通时的凭证。

```text
消息通知要点：
1. 授权时机 —— 订阅授权必须在用户点击的调用栈内触发，弹窗不能自己主动弹出
2. 一次性额度 —— 一次授权一次发送，服务端必须记账，发送前检查额度
3. 模板字段 —— 模板内容审核通过后不可改 key，发送数据需截断到模板要求长度
4. 错误处理 —— 43101 用户拒收/未订阅要注销额度，40003 openid 非法要记录告警
5. 定时提醒 —— 定时任务逐单发送，单条失败 try-catch 隔离，不阻塞整批
6. 发送留痕 —— message_log 表记录每次发送结果，支撑排查与用户沟通
```

## 取消与改期

取消与改期是预约业务里最容易出并发问题的部分，必须靠「订单状态机」把状态流转约束起来。核心状态与流转规则：

```text
订单状态机：
1. 待支付(0) —— 订单创建后未支付，可支付、可取消，超时自动取消
2. 已支付(1) —— 支付成功，可取消（按规则退全款/部分款）、可改期、可完成
3. 已完成(2) —— 服务完成，终态，不可再变更
4. 已取消(3) —— 未支付的取消，终态，不产生退款
5. 已退款(4) —— 已支付订单取消后全额/部分退款，终态
6. 非法流转 —— 已完成不能取消、已取消不能支付、已退款不能改期，一律拒绝
```

用 Java 枚举实现状态机，把「允许的流转」集中定义在一处，任何入口（取消、改期、支付回调、管理端操作）都走同一个校验：

```java
// OrderStatus.java —— 订单状态机
public enum OrderStatus {
    PENDING_PAY(0, "待支付"),
    PAID(1, "已支付"),
    COMPLETED(2, "已完成"),
    CANCELLED(3, "已取消"),
    REFUNDED(4, "已退款");

    private final int code;
    private final String desc;

    // 允许的状态流转表：key 为当前状态，value 为可达状态集合
    private static final Map<OrderStatus, Set<OrderStatus>> TRANSITIONS = Map.of(
            PENDING_PAY, Set.of(PAID, CANCELLED),        // 待支付 -> 支付成功 / 取消
            PAID, Set.of(COMPLETED, CANCELLED, REFUNDED), // 已支付 -> 完成 / 取消 / 退款
            COMPLETED, Set.of(),                          // 终态
            CANCELLED, Set.of(),                          // 终态
            REFUNDED, Set.of());                          // 终态

    public boolean canTransitTo(OrderStatus target) {
        return TRANSITIONS.getOrDefault(this, Set.of()).contains(target);
    }

    public int getCode() { return code; }
    public String getDesc() { return desc; }
}
```

取消订单的完整实现。要点：用 `SELECT ... FOR UPDATE` 行锁串行化同一订单的并发操作；先校验状态机，再校验取消时限（距开始不足 2 小时不可免费取消）；释放时段容量；已支付订单发起微信退款并置为已退款：

```java
// OrderService.java —— 取消订单
@Transactional
public void cancel(Long orderId, Long userId, String reason) {
    // 1. 行锁取出订单，防止并发取消/改期/支付回调同时操作
    Order order = orderMapper.selectByIdForUpdate(orderId);
    if (order == null || !order.getUserId().equals(userId)) {
        throw new BizException("订单不存在");
    }
    // 2. 状态机校验
    if (!order.getStatus().canTransitTo(OrderStatus.CANCELLED)) {
        throw new BizException("当前状态不可取消");
    }
    // 3. 取消时限：服务开始前 2 小时之外才允许免费取消
    if (order.getStartTime().isBefore(LocalDateTime.now().plusHours(2))) {
        throw new BizException("距服务开始不足 2 小时，不可取消");
    }
    // 4. 释放该订单占用的时段容量
    scheduleService.release(order.getScheduleId(), 1);
    // 5. 已支付则发起退款，未支付直接取消
    if (order.getStatus() == OrderStatus.PAID) {
        wechatPayService.refund(order.getOrderNo(), order.getPayAmount(), reason);
        order.setStatus(OrderStatus.REFUNDED);
    } else {
        order.setStatus(OrderStatus.CANCELLED);
    }
    orderMapper.updateById(order);
}
```

改期（换时段）本质上是一次「释放旧容量 + 占用新容量 + 更新订单」的原子操作。最容易被忽略的是：新时段校验与占用必须是原子操作，否则两个用户同时改期到同一个时段会双双成功造成超卖：

```java
// OrderService.java —— 改期
@Transactional
public void reschedule(Long orderId, Long userId, Long newScheduleId) {
    Order order = orderMapper.selectByIdForUpdate(orderId);
    if (order == null || !order.getUserId().equals(userId)) {
        throw new BizException("订单不存在");
    }
    if (!order.getStatus().canTransitTo(OrderStatus.PAID)) {
        throw new BizException("仅已支付订单可改期");
    }
    ScheduleSlot newSlot = scheduleMapper.selectById(newScheduleId);
    if (newSlot == null || newSlot.getStatus() != 1) {
        throw new BizException("目标时段不可约");
    }
    // 原子占用新时段：条件更新影响行数不为 1 说明已满或被暂停
    if (scheduleMapper.occupy(newScheduleId) != 1) {
        throw new BizException("目标时段已约满，请更换时段");
    }
    // 占用成功后再释放旧时段，顺序不能反（先释放后占用会瞬间超卖）
    scheduleService.release(order.getScheduleId(), 1);
    order.setScheduleId(newScheduleId);
    order.setStartTime(newSlot.getStartTime());
    orderMapper.updateById(order);
}
```

待支付订单的兜底清理：支付宽限期（如 30 分钟）结束后仍未支付，定时任务自动取消并释放容量。注意定时任务要与「用户刚好在超时那一刻完成支付」的场景做竞态处理，两个操作都走状态机校验即可保证安全：先到先得，后到者状态流转被拒绝。

```text
取消与改期要点：
1. 状态机 —— 所有状态流转集中校验，非法流转一律拒绝，杜绝「已取消后支付成功」
2. 行锁 —— SELECT FOR UPDATE 串行化同一订单的并发操作
3. 取消规则 —— 时限外免费取消，时限内按产品规则扣费或禁止
4. 改期原子性 —— 先原子占用新时段、成功后释放旧时段，顺序不能反
5. 退款 —— 已支付订单取消必须走微信退款并更新为已退款状态
6. 超时兜底 —— 待支付订单超时自动取消并释放容量，与手动支付竞态由状态机兜底
```

## 应用场景实战

### 场景一：小程序端预约下单完整链路

以「上门保洁」预约为例，串联选时段、提交、支付三个环节。假设后台已生成好排期，前端按流程逐步提交：

```text
步骤：
1. 首页进入服务详情，选择「2 小时日常保洁」
2. 门店列表选择「旗舰店」，进入预约页
3. 日历选择明天，加载当天 8 个时段的剩余容量
4. 选择「10:00-12:00（剩 3）」，填写联系人姓名与手机号
5. 点击提交，后端创建订单并返回 needPay=true 与支付参数
6. wx.requestPayment 拉起微信支付，支付成功后跳转结果页
7. 结果页请求订阅「预约成功」与「开始前提醒」两个模板
```

后端创建订单的完整实现（容量扣减 + 订单落库 + 统一下单）：

```java
// OrderService.java —— 创建预约订单
@Transactional
public OrderVO create(Long userId, CreateOrderDTO dto) {
    // 1. 校验服务、门店存在且可约
    ServiceInfo service = serviceMapper.selectById(dto.getServiceId());
    if (service == null || service.getStatus() != 1) {
        throw new BizException("服务不存在或已下架");
    }
    // 2. 原子占用时段容量，失败说明已满
    if (scheduleService.tryOccupy(dto.getScheduleId())) {
        throw new BizException("该时段已被约满");
    }
    ScheduleSlot slot = scheduleMapper.selectById(dto.getScheduleId());
    // 3. 创建订单，默认待支付
    Order order = Order.builder()
            .orderNo(genOrderNo())            // 业务订单号：日期+随机数，唯一索引
            .userId(userId)
            .openid(userService.getOpenid(userId))
            .shopId(dto.getShopId())
            .serviceId(dto.getServiceId())
            .scheduleId(dto.getScheduleId())
            .startTime(LocalDateTime.of(slot.getBizDate(), slot.getStartTime()))
            .amount(service.getPrice())       // 单位：分
            .status(OrderStatus.PENDING_PAY)
            .contactName(dto.getContactName())
            .contactPhone(dto.getContactPhone())
            .build();
    orderMapper.insert(order);
    // 4. 免费服务直接确认；付费服务调用统一下单生成支付参数
    if (order.getAmount() == 0) {
        order.setStatus(OrderStatus.PAID);
        orderMapper.updateById(order);
        return OrderVO.of(order, null, false);
    }
    PayParams payParams = wechatPayService.unifiedOrder(order);
    return OrderVO.of(order, payParams, true);
}
```

```text
场景一验收点：
1. 已满时段在前端置灰不可选，服务端同样拒绝（双端校验）
2. 支付成功回调更新状态为已支付，回调需验签且幂等
3. 待支付订单 30 分钟未支付被定时任务自动取消、容量自动释放
4. 同一时段并发抢约，最终预约数不超过容量
```

## 最佳实践与踩坑记录

### 最佳实践

1. 排期数据以「门店+服务+日期+时段」为最小维度建模，加唯一索引，任何维度缺一都容易造成排期混乱
2. 容量扣减必须原子化（数据库条件更新或 Redis Lua），禁止「先查后改」的两步写法
3. 订单状态流转集中到状态机枚举校验，配合 SELECT FOR UPDATE 行锁，从根上杜绝并发脏流转
4. 订阅消息额度在服务端记账，发送前检查、发送后扣减，错误码 43101 立即注销额度
5. 待支付订单设置支付宽限期，用定时任务兜底自动取消并释放容量，防止占坑
6. 前端展示的剩余容量统一由服务端计算下发，前端不做任何推断，避免界面与提交结果不一致
7. 时间统一使用 Asia/Shanghai，日期参数用 yyyy-MM-dd 字符串传输，避免时区与格式化歧义
8. 管理端排期支持时段模板批量生成（每周几、几点、容量），运营不用逐条创建

### 踩坑记录

```text
坑 1：先查后改导致时段超卖
结论：并发下预约数超过时段容量，多个用户同时约到同一个名额。
原因：先 SELECT booked_count 判断小于 capacity，再 UPDATE，两步之间被并发请求插队。
解法：改为条件更新 UPDATE ... SET booked_count=booked_count+1 WHERE booked_count<capacity，用影响行数判断成败；高并发再叠加 Redis 原子扣减。

坑 2：订单状态并发更新出现「已取消后支付成功」
结论：用户取消订单的同时完成支付，订单状态变成已取消但钱已扣。
原因：取消接口与支付回调没有串行化，两个请求同时读到旧状态并各自更新。
解法：所有状态变更先 SELECT ... FOR UPDATE 拿行锁，再走状态机校验，非法流转直接拒绝。

坑 3：订阅消息提醒大面积丢失
结论：用户预约成功却没收到任何提醒，客服被投诉。
原因：用户未授权订阅或额度已用完，服务端没检查额度就直接发送失败，且无日志留痕。
解法：发送前检查额度；发送后写 message_log；43101 注销额度；定时任务单条失败 try-catch 隔离并记录。

坑 4：改期/取消没有释放容量，排期表被占满
结论：用户取消后时段仍显示已约满，新用户无法预约。
原因：取消与改期逻辑里漏掉了 scheduleService.release，容量只增不减。
解法：取消、改期、退款、超时自动取消四类路径统一释放容量，并在单元测试中逐一断言。

坑 5：待支付订单永不关闭，长期占用容量
结论：大量用户下单不支付，时段被占满，真实用户无法预约。
原因：只做了下单扣容量，没有支付超时兜底。
解法：设置 30 分钟支付宽限期，定时任务扫描超时待支付订单自动取消并释放容量。

坑 6：access_token 频繁刷新触发微信限流
结论：定时提醒批量发送时报错，大量消息发送失败。
原因：每个订单发送前都重新获取 access_token，高频调用触发接口限流。
解法：access_token 缓存到 Redis（有效期 7200 秒，缓存 7000 秒），进程内统一从缓存取。

坑 7：前端显示可约、提交时提示已满
结论：用户选了显示「剩 1」的时段，提交时被告知已约满，体验很差。
原因：前端缓存了时段数据，或剩余容量由前端本地计算，与真实库存脱节。
解法：剩余容量一律服务端实时计算下发；提交时对「已满」错误做友好提示并提供换时段快捷入口。

坑 8：改期抢时段时两个用户同时成功
结论：两个用户改期到同一个只剩 1 个名额的时段，双双改期成功。
原因：先校验「剩余大于 0」再占用，校验与占用不是原子操作。
解法：改期直接调用条件更新占用新时段，影响行数不为 1 即拒绝，成功后再释放旧时段。
```
