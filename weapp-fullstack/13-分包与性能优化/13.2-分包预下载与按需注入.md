## 概述

分包解决了「包太大不能上传」的问题，但「进入分包页面时才下载分包」会带来等待：用户点进商品详情，白屏转圈等分包下载完成。预下载（preloadRule）让微信在空闲网络下提前把将要访问的分包缓存好，实现「下载与浏览并行」；按需注入（lazyCodeLoading）让启动时只解析首屏真正用到的组件代码，把「加载」与「解析」都变得按需。两者叠加，小程序既可以突破 2M 主包限制，又不必牺牲打开速度。

更进一步，分包异步化（require.async）打破了「分包之间不能互相引用」的硬约束：允许在运行时异步加载其他分包/主包的 JS 模块与自定义组件，让跨包复用不再依赖「抽到主包」这一条路。本章把预下载、按需注入、异步化、依赖分析与加载策略串成一条完整的「分包性能优化链」，理解每个机制的触发时机与代价，才能组合出最优方案。

```text
分包预下载与按需注入核心要点：
1. preloadRule —— app.json 中配置，进入指定页面时在后台预下载目标分包
2. network 参数 —— 预下载触发条件：wifi（默认，仅 WiFi 下预下载）或 all（所有网络）
3. lazyCodeLoading —— app.json 中 requiredComponents 配置，组件代码按需注入
4. require.async —— 运行时异步加载其他分包/主包的 JS 模块，返回 Promise
5. 异步组件 —— usingComponents 引用其他分包组件，框架按需异步加载对应分包
6. 依赖分析 —— 构建时自动分析代码依赖，公共代码放主包可被所有分包共享
```

## preloadRule 预下载

预下载的官方名称是「分包预下载」，配置字段为 app.json 中的 `preloadRule`。它声明「当用户进入某个页面时，微信在后台预先下载某些分包」，等用户真正跳转到这些分包页面时，分包已经缓存完毕，无需等待网络。

```json
{
  "pages": [
    "pages/index/index",
    "pages/detail/detail"
  ],
  "subpackages": [
    {
      "root": "packageGoods",
      "pages": ["pages/list/list", "pages/detail/detail"]
    },
    {
      "root": "packageLive",
      "pages": ["pages/room/room"]
    }
  ],
  "preloadRule": {
    "pages/index/index": {
      "network": "all",
      "packages": ["packageGoods"]
    },
    "pages/detail/detail": {
      "network": "wifi",
      "packages": ["packageLive"]
    }
  }
}
```

配置结构说明：`preloadRule` 是一个对象，键是「触发页面」的完整路径（必须是 app.json 中已注册的页面），值是一个对象，包含 `network` 与 `packages` 两个字段。`network` 指定预下载的网络环境：`wifi` 表示仅在 WiFi 下预下载（默认值，替用户省流量），`all` 表示所有网络下都预下载；`packages` 是预下载目标分包 root 列表，也可以填 `__APP__` 表示预下载主包（主包一般随启动加载，极少用到）。

触发时机要精确理解：当用户**进入**配置的页面时触发预下载，而不是小程序启动时。典型用法是「首页预下载商品分包」——用户大概率会在首页停留几秒再点进商品列表，这几秒正好完成后台下载。预下载在后台进行，不阻塞页面渲染，下载进度通过 `wx.getDownloadTask` 之类的机制不可见，属于「尽力而为」的优化：WiFi 切换、弱网、分包过大时都可能下载失败或部分失败，页面跳转时若分包未就绪，仍然会走常规的按需下载流程。

```text
preloadRule 配置要点：
1. 键 —— 触发页面完整路径（pages 数组里注册过的页面）
2. network —— wifi（默认，仅 WiFi 预下载）或 all（所有网络均预下载）
3. packages —— 预下载的分包 root 数组，可配置多个；__APP__ 表示主包
4. 时机 —— 进入触发页面时后台预下载，不阻塞当前页面渲染
5. 兜底 —— 预下载失败不影响功能，跳转分包时按常规按需加载
6. 建议 —— 用 all 的场景：明确知道用户马上要用的包；用 wifi 的场景：大包/低频包
```

预下载适合配合「漏斗路径」设计：分析用户行为，找到「高概率下一跳」的分包并提前下载。电商场景首页 → 商品分包、搜索结果页 → 详情分包、详情页 → 直播间分包，都是典型的预下载链路。预下载的包会进入微信的本地缓存，第二次访问直接命中缓存。

## 按需注入

按需注入（lazyCodeLoading）解决的是「启动时解析过多无用代码」的问题。默认情况下，小程序启动时框架会执行所有页面的 JS、注入所有页面与组件的代码；页面多了之后，即便只打开首页，其它页面的代码也要被解析执行，白白消耗启动时间。开启按需注入后，框架只注入「首屏真正用到的页面与组件」的代码，其它页面代码在使用时才注入。

```json
// app.json
{
  "lazyCodeLoading": "requiredComponents",
  "pages": [
    "pages/index/index",
    "pages/goods/goods"
  ]
}
```

`lazyCodeLoading: "requiredComponents"` 的含义是：代码按「必需组件」粒度按需注入。开启后，页面 JS 中的 Page() 注册、页面配置中 usingComponents 引用的组件，都会被延迟到页面真正被打开时才注入执行。首屏启动路径上只保留启动页及其直接使用的组件，启动解析的代码量显著下降。

按需注入的收益与代价：

```text
按需注入要点：
1. 配置 —— app.json 加 lazyCodeLoading: "requiredComponents" 即可全局开启
2. 粒度 —— 按页面 + 页面 usingComponents 声明的组件为粒度注入代码
3. 收益 —— 启动时注入代码量减少，首屏渲染更快，内存占用降低
4. 兼容 —— 基础库 2.11.1+ 支持；低版本基础库自动忽略该配置按全量注入
5. 约束 —— 全局注册的组件（app.json usingComponents）不受按需注入影响
6. 注意 —— 页面 json 中未声明的组件不会自动注入，需在 usingComponents 显式声明
```

使用按需注入时最容易犯的错：在 JS 里直接 `require` 某个组件文件，但页面 json 的 usingComponents 没声明它——按需注入后该组件代码不会被执行，组件行为异常。正确的做法是：所有组件都通过 usingComponents 显式声明，JS 里的组件相关逻辑（如通过 selectComponent 调用组件方法）依赖组件已注入。另外，如果业务代码里通过 `wx.getCurrentPages`、动态 require 等方式隐式依赖「所有页面都已注册」，开启按需注入后需要回归测试这些逻辑。

```text
按需注入 vs 传统注入对比：
1. 传统模式 —— 启动时注入所有页面与组件代码，页面越多启动越慢
2. 按需模式 —— 只注入首屏页面与其声明组件，其余代码延迟到使用时刻
3. 声明依赖 —— 按需模式下 usingComponents 就是注入清单，必须写全
4. 组合使用 —— 按需注入 + 分包 + 预下载是官方推荐的三件套
5. 回归 —— 开启后重点验证：动态 require、全局组件、插件引用是否正常
```

## 分包异步化

分包异步化（基础库 2.1.0+）是官方为解决「分包间不能互相引用」提供的运行时方案。它允许在分包（或主包）中异步加载其他分包内的 JS 模块与自定义组件，让跨包复用从「编译期硬约束」变成「运行时按需加载」。分包异步化的核心 API 是 `require.async`。

```js
// 分包 packageOrder 中异步加载 packageGoods 的模块
require.async('../packageGoods/utils/price.js').then((mod) => {
  const formatPrice = mod.formatPrice;
  this.setData({ total: formatPrice(9980) });
}).catch((err) => {
  console.error('分包异步加载失败：', err);
});
```

`require.async` 接收一个模块路径（相对当前文件），返回 Promise，模块加载并执行后 resolve 模块导出对象。注意路径写法：从当前分包跨到另一个分包，路径要按目录相对关系写（如上例 `../packageGoods/...`），也可以写成绝对路径形式。`require.async` 只能在分包或主包的 js 中使用，不能在 wxml 或 wxss 中调用。

除了 JS 模块，分包异步化还支持异步组件：在分包 A 中定义组件，分包 B 的页面通过 usingComponents 直接引用分包 A 的组件路径，框架会在页面真正渲染该组件时自动异步加载组件所在的分包。这在跨包复用自己的业务组件（如商品卡片）时非常有用：

```json
// packageOrder/pages/list/list.json
{
  "usingComponents": {
    "goods-card": "/packageGoods/components/goods-card/goods-card"
  }
}
```

```text
分包异步化要点：
1. require.async —— 异步加载其他分包/主包 JS 模块，返回 Promise，基础库 2.1.0+
2. 异步组件 —— usingComponents 直接引用其他分包组件，渲染时自动异步加载
3. 路径 —— 相对路径（../packageGoods/...）或绝对路径均可，按目录关系书写
4. 限制 —— 异步加载的模块不能包含页面注册、App 注册等启动期逻辑
5. 样式 —— 异步组件不继承 app.wxss 全局样式，样式需组件自带或显式引入
6. 网络 —— 异步加载走常规分包下载通道，弱网下可能失败，需 catch 兜底
```

分包异步化的典型误区：把「异步化」当成「随便引用」。异步加载的模块一旦包含 Page()、App() 或对主包启动期的强依赖，会因执行时机错乱而报错；异步组件默认拿不到 app.wxss 的全局样式，组件观感可能与主包组件不一致（需要组件自带样式）。因此工程上的正确姿势是：跨包复用「纯函数工具」用 require.async，跨包复用「展示组件」用异步组件，跨包复用「带全局样式的复杂组件」仍然优先抽到主包。

## 依赖分析

依赖分析是构建工具（微信开发者工具）在编译时自动执行的静态分析：从每个页面的 js/wxml/json 出发，沿着 require、import、usingComponents、模板引用等边，构建整棵依赖图，然后把依赖图划分到主包与各个分包。理解依赖分析，才能预判「什么代码会被打进哪个包」。

```text
依赖分析规则：
1. 入口 —— 每个页面是依赖图的根节点，wxml 引用的组件、js require 的模块都算依赖
2. 归属 —— 页面在哪个包，它的依赖默认进哪个包；被多个包引用的代码进主包
3. 公共代码 —— 同时被主包与分包（或多个分包）引用的模块自动进主包
4. 循环引用 —— 分包依赖主包是单向的，依赖分析保证依赖图无环
5. 产物 —— 开发者工具「代码依赖分析」面板可视化展示各包引用关系
6. 作用 —— 依据分析结果调整目录：该进主包的进主包，该拆分的拆分
```

开发者工具提供「代码依赖分析」面板（工具菜单 - 代码依赖分析），可以查看每个分包引用了哪些文件、哪些文件被多个包共享。实操中的典型动作：

```text
依赖分析实操：
1. 打开依赖分析面板，找出被 2 个以上分包引用的文件 —— 它们应抽到主包
2. 检查主包中是否混入「只有某个分包才用」的文件 —— 移到该分包
3. 检查分包之间是否有隐式引用（路径写错导致的编译期报错除外）
4. 关注 app.json 中全局 usingComponents —— 全局组件会进主包，能不用就不用
5. 定期在发布前跑一遍分析，防止「公共代码悄悄变成多份副本」
```

一个常见陷阱：主包 app.json 里配置了全局 usingComponents（如全局弹窗组件），这个组件会被所有页面引用，强制进主包，即使只有少数页面用到它。公共代码放主包的原则是「被多处共享才放主包」，全局组件天然符合「多处共享」，但如果只有一两个页面用，就应该改为页面级 usingComponents 声明，避免无关代码膨胀主包。

```text
依赖分析与体积的关系：
1. 主包体积 = 主包页面 + 公共依赖 + 全局组件/全局配置引用的资源
2. 分包体积 = 分包页面 + 分包私有依赖（不含已在主包的公共代码）
3. 公共代码只算一次 —— 抽到主包后所有分包共享，避免每个分包各存一份
4. 依赖越少越好 —— 减少第三方库全量引入，按需 import 可显著瘦身
5. 分析先行 —— 大版本重构前后各跑一次依赖分析，对比各包体积变化
```

## 加载优化

把预下载、按需注入、异步化与分包组合成完整的加载策略，是本章的落地点。加载优化的目标：首屏启动尽可能快（少下载、少解析），分包切换尽可能无感（提前下载、按需加载）。推荐的组合策略如下：

```text
加载优化组合策略：
1. 分包划分 —— 首屏路径（启动页 + tabBar + 公共代码）留在主包，其余全部分包
2. 预下载 —— 高频「下一跳」分包配置 preloadRule，network 按包大小与频次选择
3. 按需注入 —— 全局开启 lazyCodeLoading: requiredComponents，减少启动解析
4. 异步化 —— 跨包复用 JS 用 require.async，跨包复用组件用异步组件
5. 缓存 —— 分包下载后进本地缓存，二次访问零等待；发布新版本自动失效
6. 降级 —— 弱网/首次访问时预下载可能失败，保证按需加载链路始终可用
```

具体到一个电商小程序的加载链路：启动加载主包（含首页、tabBar、请求封装）→ 首页配置 preloadRule 预下载商品分包 → 用户点进商品列表时分包已缓存 → 商品列表按需注入自己的页面代码 → 详情页复用商品分包内组件（同包直接引用）→ 直播分包通过 preloadRule 在进入详情页时预下载。整条链路上没有「用户等待下载」的卡点。

```js
// 结合页面生命周期的降级示例：进入页面时检测分包是否就绪
Page({
  onLoad() {
    // 预下载由 preloadRule 负责，此处仅兜底校验
    wx.getStorageInfo({
      success: (res) => {
        console.log('当前缓存使用情况：', res.currentSize, '/', res.limitSize);
      }
    });
  }
});
```

预下载与按需注入的配合要点：预下载解决「包没下载」的问题，按需注入解决「代码被解析」的问题，两者互补不冲突。预下载把下载时间藏到「用户停留」里，按需注入把解析时间藏到「页面打开后」；前者针对分包、后者针对代码。启动优化的完整链路还包括渲染阶段优化（长列表、图片懒加载、骨架屏），见 13.4。

```text
加载优化检查清单：
1. 主包是否只剩首屏必需代码 —— 不是则继续拆分包
2. 高频下一跳分包是否配了 preloadRule —— 没有则补上
3. lazyCodeLoading 是否开启 —— 未开启先评估基础库版本与回归风险
4. 跨包复用是否走 require.async / 异步组件 —— 仍用 require 直引则改
5. 公共代码是否都进了主包 —— 依赖分析面板核对
6. 弱网与首访场景是否有兜底 —— 按需加载链路始终可用
```

## 应用场景实战

### 场景一：首页预下载商品分包 + 按需注入三件套

电商小程序首页流量最大，用户从首页进入商品列表/详情是最高频路径。配置「首页进入时预下载商品分包」，并全局开启按需注入：

```json
// app.json
{
  "lazyCodeLoading": "requiredComponents",
  "pages": [
    "pages/home/home",
    "pages/cart/cart"
  ],
  "subpackages": [
    {
      "root": "packageGoods",
      "pages": ["pages/list/list", "pages/detail/detail"]
    },
    {
      "root": "packageUser",
      "pages": ["pages/mine/mine"]
    }
  ],
  "preloadRule": {
    "pages/home/home": {
      "network": "all",
      "packages": ["packageGoods"]
    }
  }
}
```

首页是 tabBar 首页，用户几乎必然从它进入商品链路，所以 network 用 all（不区分 WiFi/流量，确保到达列表页时已就绪）；packageUser 是低频模块，不配置预下载，保持按需。为了验证预下载是否生效，可以在开发者工具中开启「网络面板」，观察进入首页后是否有 packageGoods 的下载请求：

```text
验证步骤：
1. 开发者工具打开「Network」面板，过滤分包域名请求
2. 冷启动进入首页，观察 packageGoods 相关下载请求是否出现
3. 立即跳转 packageGoods/pages/list/list，对比有无预下载的打开耗时
4. 真机上用「弱网」模式重复验证，确认降级链路可用
5. 在「详情-基本信息」查看分包体积与预下载配置是否生效
```

### 场景二：订单模块跨包复用商品模块组件（分包异步化）

订单列表要展示商品卡片，但商品卡片组件定义在 packageGoods 里。方案一抽到主包（通用组件确实值得），方案二用异步组件直接跨包引用。这里演示方案二 + require.async 的组合：

```json
// packageOrder/pages/list/list.json —— 跨包异步引用商品卡片组件
{
  "usingComponents": {
    "goods-card": "/packageGoods/components/goods-card/goods-card"
  }
}
```

```js
// packageOrder/pages/list/list.js
Page({
  data: {
    orders: [],
    goodsMap: {}
  },
  onLoad() {
    this.fetchOrders();
  },
  async fetchOrders() {
    try {
      const res = await wx.request({ url: 'https://api.example.com/orders' });
      // 异步加载商品分包中的工具模块（跨包复用纯函数）
      const { buildGoodsMap } = await require.async('../../packageGoods/utils/goods-map.js');
      const orders = res.data.data;
      this.setData({
        orders: orders,
        goodsMap: buildGoodsMap(orders)
      });
    } catch (err) {
      console.error('订单数据或分包模块加载失败：', err);
      wx.showToast({ title: '加载失败', icon: 'none' });
    }
  }
});
```

```text
场景二要点：
1. 异步组件 —— goods-card 跨包引用，渲染时自动异步加载 packageGoods
2. require.async —— 异步加载 goods-map.js 纯函数模块，避免重复实现
3. 错误兜底 —— 异步加载与网络请求统一 try/catch，失败给用户明确提示
4. 样式注意 —— 异步组件自带样式，不依赖 app.wxss 全局样式
5. 适用边界 —— 高频跨包组件仍建议抽主包；低频复用走异步化最合适
```

## 最佳实践与踩坑记录

### 最佳实践

1. preloadRule 只给「用户停留时间 > 下载时间」的链路配：进入页面后用户大概率停留几秒再跳转，预下载才有意义，否则纯浪费流量
2. 大分包用 wifi 预下载、关键小分包用 all：直播包、营销包动辄几百 KB，用 wifi 省用户流量；商品列表这类必跳分包用 all 保证体验
3. lazyCodeLoading 与分包一起上：分包解决「下载量」，按需注入解决「解析量」，两者叠加收益最大，单独开一个收益打折
4. 跨包复用先问一句「它该在主包吗」：高频公共组件抽主包，低频模块才用 require.async/异步组件，异步化不是免抽主包的借口
5. 依赖分析纳入发布流程：每次发版前看一遍「代码依赖分析」，发现分包间隐式引用、公共代码副本立即修正
6. 全局 usingComponents 慎用：全局组件进主包并被所有页面注入，只有真正全站使用的组件才放全局声明
7. 预下载失败要有心理预期：预下载是尽力而为，弱网、切换网络都可能失败，业务逻辑必须依赖常规按需加载链路
8. 开启按需注入后做一次全量回归：重点验证动态 require、全局组件、插件、分享进入等场景，按需注入会改变代码执行时机

### 踩坑记录

坑 1：preloadRule 配置的触发页面路径写错，预下载完全不生效
结论：首页进入后 Network 面板看不到任何分包预下载请求。
原因：preloadRule 的键必须是 pages 数组中注册过的页面完整路径，多写少写一个字符都不触发。
解法：对照 app.json pages 数组逐字复制路径；用开发者工具 Network 面板验证触发。

坑 2：network 配成 wifi，用户 4G 环境下预下载不执行
结论：4G 用户进入页面后分包没有预下载，跳转分包时明显卡顿。
原因：wifi 是默认值，仅 WiFi 网络触发预下载，流量网络被策略跳过。
解法：关键路径分包把 network 设为 all；大包继续用 wifi 以尊重用户流量。

坑 3：预下载的分包不在 packages 列表，跳转仍按需下载
结论：明明配置了 preloadRule，目标分包还是跳转时才下载。
原因：packages 里写的是分包 root，写成了页面路径或漏写该分包。
解法：packages 数组填分包 root（如 packageGoods），需要预下载多个分包就写多个 root。

坑 4：开启 lazyCodeLoading 后，动态 require 的组件行为异常
结论：按需注入开启后，某些页面组件渲染出来但事件不响应或方法未定义。
原因：组件未在页面 usingComponents 声明，按需注入机制没有注入它的代码。
解法：所有组件显式声明进 usingComponents；动态加载的场景改用 require.async 并处理 Promise。

坑 5：异步组件没有全局样式，跨包复用后样式崩了
结论：异步加载的组件在分包页面里显示错乱，颜色、间距与主包中不一致。
原因：异步组件不继承 app.wxss 全局样式，样式依赖被切断。
解法：组件样式全部内联在组件自己的 wxss 中；确需全局样式的组件抽到主包再引用。

坑 6：require.async 加载的模块里注册了 Page，运行时报错
结论：异步加载某模块后报「Page is not defined」或页面注册重复。
原因：异步化的模块只适合纯逻辑/工具，包含页面注册的模块执行时机不受控。
解法：页面始终走常规分包机制；require.async 只加载纯函数、工具、数据模块。

坑 7：预下载在弱网下失败，跳转分包长时间白屏
结论：弱网环境进入分包页面长时间 loading，体验很差。
原因：预下载失败后没有备用方案，跳转时走常规下载，弱网下载慢。
解法：页面 onLoad 先渲染本地缓存/骨架占位；把预下载失败纳入监控，分析失败率高的网络与包。

坑 8：全局 usingComponents 组件导致主包膨胀
结论：主包体积突然变大，排查发现全局弹窗组件被所有页面引用。
原因：app.json 全局组件强制进主包依赖图，即使只有少数页面使用。
解法：改为页面级 usingComponents；「全站通用」才保留全局声明。

坑 9：真机上第二次进入分包还走下载，缓存未命中
结论：预下载或按需下载过一次的分包，下次进入仍提示下载中。
原因：发布了新版本，分包 hash 变化，旧缓存自动失效需重新下载。
解法：这是正常机制，无需修复；关注发布节奏，避免高频发版导致缓存频繁失效。

坑 10：require.async 路径写错，分包跨引用报「模块不存在」
结论：跨分包 require.async 报错，模块找不到。
原因：路径按「当前文件 → 目标文件」的相对关系书写，写错层级或少了 root 前缀。
解法：用绝对路径 /packageGoods/utils/price.js 更稳妥；本地先在开发者工具中验证再发布。
