## 概述

用户对小程序的第一印象由两个时间决定：从点击到看到首页的「启动时间」，以及页面内容完整可用的「首屏时间」。启动优化解决「包加载与代码解析」的耗时，首屏与渲染优化解决「数据请求与视图绘制」的耗时。前两章的分包、预下载、按需注入、setData 优化解决的是「代码与数据链路」；本章聚焦渲染层：长列表、图片、骨架屏、懒加载、启动耗时统计，把「看到的快」与「交互的快」都做到位。

渲染与启动优化是「体验工程」：每个手段的收益可以用性能面板量化，但叠加起来的效果是用户可感知的——打开快一档、滚动不卡、图片渐显不白屏、首屏先出骨架再出内容。本章按「启动 → 渲染 → 图片 → 占位 → 按需」的顺序组织，最后给出可复用的场景实战与踩坑清单。

```text
渲染与启动优化核心要点：
1. 启动优化 —— 分包 + 缓存 + 代码瘦身，压缩启动耗时
2. 首屏优化 —— 首屏数据提前加载、页面预加载、骨架屏占位
3. 渲染优化 —— 长列表回收、渲染耗时分析、避免无效重渲染
4. 图片优化 —— 压缩、WebP、CDN、懒加载、尺寸匹配
5. 骨架屏 —— 首屏数据未到时的占位视图，消除白屏感
6. 懒加载 —— 图片按需加载、数据分页、组件按需注册
```

## 启动优化与首屏优化

小程序启动链路：微信客户端拉起小程序 → 下载代码包（首次或版本更新时）→ 解析并执行 App 与启动页代码 → 请求首屏数据 → 渲染首屏。启动优化压缩的是「下载、解析、执行」三段；首屏优化压缩的是「数据请求、渲染」两段。

```text
启动链路与优化点：
1. 下载代码包 —— 分包让启动只下载主包；版本发布后首次启动仍要下载新包
2. 解析执行 —— lazyCodeLoading 按需注入（13.2）；代码瘦身、去掉无用依赖
3. App onLaunch —— 减少同步阻塞：登录、初始化请求放异步或后置
4. 启动页渲染 —— 启动页代码精简；首屏数据请求与渲染并行
5. 首屏数据 —— 本地缓存优先展示，网络数据到达后增量更新
6. 统计 —— wx.getPerformance / 启动耗时上报，量化每次优化
```

启动优化的具体手段：主包瘦身（分包拆分，见 13.1）、按需注入（lazyCodeLoading，见 13.2）、预下载（preloadRule，见 13.2）、代码去重（删除无用依赖、按需引入库）。App.onLaunch 中的阻塞操作是隐形杀手：如果 onLaunch 里同步执行耗时逻辑（如读取大缓存、同步初始化 SDK），会直接拖慢启动。

```js
// app.js —— 启动路径上的异步化改造
App({
  onLaunch() {
    // 同步读取少量必要缓存（轻量，允许）
    const token = wx.getStorageSync('token');

    // 重活全部异步化：登录、预拉取、埋点初始化都不阻塞启动
    if (token) {
      // 后台刷新登录态，不等待结果
      wx.request({
        url: 'https://api.example.com/auth/refresh',
        method: 'POST',
        header: { Authorization: 'Bearer ' + token }
      });
    }
    // 数据预拉取（官方能力）：启动时后台预拉取首页数据
    wx.setBackgroundFetchToken(token);
  }
});
```

首屏优化关注「从进入页面到内容可见」：数据请求是主耗时。常见手法：首屏数据请求提前发起（onLoad 里立即请求，不等页面渲染完成）；用本地缓存先渲染旧数据（「先展示缓存，再刷新」）；关键接口合并（一次请求返回首屏所有数据，减少串行请求）；接口数据与渲染并行——onLoad 发起请求的同时页面先渲染静态骨架，数据到达后 setData 更新。

```text
首屏优化要点：
1. 请求前置 —— onLoad 立即发首屏请求，不与页面渲染串行
2. 缓存优先 —— 本地缓存旧数据先渲染，网络数据到达后更新
3. 接口合并 —— 首屏多个接口合并或并行，减少串行等待
4. 骨架屏 —— 数据未到时渲染占位结构，避免白屏（见骨架屏节）
5. 预加载 —— 页面预加载能力：进入页面 A 时预加载页面 B 的数据
6. 首屏埋点 —— 上报首屏耗时（性能面板/自定义埋点），持续观测
```

官方还提供「页面预加载」能力：在页面 A 的 onLoad 中调用 `wx.preloadPage` 或配置页面数据预取，在后台提前请求页面 B 的首屏数据，用户跳转 B 时数据已就绪。数据预拉取（wx.setBackgroundFetchData / setBackgroundFetchToken）则让微信在空闲时后台拉取指定接口数据存到本地，下次启动直接读取，适用于首页 feed、公告等可缓存数据。

## 渲染性能优化

渲染性能的核心矛盾是「数据规模 vs 渲染能力」。视图层每帧只能处理有限节点，数据量上去之后滚动、切换必然掉帧。渲染优化的手段按「结构、数据、测量」三条线展开。

```text
渲染性能优化手段：
1. 长列表回收 —— recycle-view 只渲染可视区节点，千条列表流畅滚动
2. 分页切片 —— 列表分页加载，滚动到底追加（见 13.3 场景一）
3. 避免整树重渲染 —— 数据下放组件、key 路径更新缩小 diff 范围
4. 静态内容模板化 —— 不变的节点用纯静态/模板，减少 diff 参与
5. 渲染耗时分析 —— Performance 面板看渲染耗时，定位卡顿页面
6. 样式优化 —— 避免复杂选择器与重排重绘，transform/opacity 动画优先
```

长列表是小程序渲染的最大挑战。官方方案 `recycle-view`（回收列表）只渲染可视区域附近的节点，滚动时复用节点，可以支撑千级列表；第三方方案（如 min-list、虚拟列表组件）思路相同。使用 recycle-view 时注意：列表项必须是自定义组件或简单节点，且需要配合固定行高/估算高度才能正确回收。

```xml
<!-- 使用 recycle-view 渲染长列表（官方回收列表） -->
<recycle-view scroll-y="{{true}}" batch="{{batchSetRecycleData}}">
  <recycle-item wx:for="{{list}}" wx:key="id">
    <view class="cell">
      <text>{{item.title}}</text>
      <text class="price">¥{{item.price}}</text>
    </view>
  </recycle-item>
</recycle-view>
```

```js
// pages/longlist/longlist.js —— recycle-view 数据分批设置
Page({
  data: {
    list: []
  },
  onLoad() {
    // 模拟 1000 条数据
    const list = [];
    for (let i = 0; i < 1000; i++) {
      list.push({ id: i, title: '商品' + i, price: (i % 100) + 1 });
    }
    // recycle-view 要求数据分批 setData（batch 机制），避免一次性大传输
    const batchSetRecycleData = {};
    for (let i = 0; i < list.length; i += 20) {
      batchSetRecycleData['list[' + i + ']'] = list.slice(i, i + 20);
    }
    this.setData(batchSetRecycleData);
  }
});
```

渲染耗时的测量：开发者工具 Performance 面板可以查看渲染耗时与 setData 耗时；真机上使用「性能分析」工具或 `wx.getPerformance()` 获取启动与渲染指标。定位卡顿的标准流程：先量化（哪个页面卡、滚动卡还是切换卡）→ 再定位（列表太大？图片太多？setData 太频繁？）→ 最后优化并复测。

```text
渲染性能优化要点：
1. 千条以上列表 —— recycle-view 回收渲染，普通 view 必卡
2. 百条级列表 —— 分页 + wx:key + 路径更新即可流畅
3. 图片是重灾区 —— 长列表每项大图，滚动时解码卡顿，必须懒加载
4. 动画用合成层 —— transform/opacity 不触发布局，比 top/left 动画流畅
5. 测量驱动 —— 每个优化前后用 Performance 面板对比，量化收益
6. 减少节点 —— 减少深层嵌套与无谓容器，节点数减半渲染成本减半
```

## 图片优化

图片是体积与渲染的双重重灾区：打包进代码包的图片撑爆分包体积，页面上未优化的图片拖慢加载与滚动。图片优化覆盖「体积、格式、网络、尺寸、加载方式」五个维度。

```text
图片优化五维度：
1. 压缩 —— 设计稿图片压缩后上传，PNG 转 WebP/JPEG，图标用 SVG
2. 格式 —— 优先 WebP（体积比 JPEG 小 30%+），兼容性差时 JPEG 兜底
3. CDN —— 图片存 CDN，加缩放参数按需生成尺寸，不传原图
4. 尺寸匹配 —— 显示 200px 宽就不要加载 1000px 原图，用 CDN 缩放
5. 懒加载 —— image 组件 lazy-load 属性，滚动到可视区才加载
```

小程序 image 组件的关键属性：`lazy-load`（图片延迟加载，滚动到可视区域再加载）、`mode`（裁剪/缩放模式，aspectFill 等比填充裁剪、widthFix 宽度固定高度自适应）、`webp`（支持 WebP 格式时优先加载 webp 后缀）。合理组合这三个属性是图片优化的最小成本方案：

```xml
<!-- 列表图片：懒加载 + 等比裁剪 + WebP 优先 -->
<image
  class="goods-cover"
  src="{{item.cover}}"
  mode="aspectFill"
  lazy-load="{{true}}"
  webp="{{true}}"
/>
```

```text
image 组件优化要点：
1. lazy-load —— 列表图片必开，滚动到可视区才发起加载
2. mode —— aspectFill（裁剪填满）用于封面图，widthFix 用于内容图
3. webp —— 开启后优先加载 .webp 资源，需 CDN 提供 webp 版本
4. CDN 缩放 —— url 加参数（如 ?w=200&h=200）让 CDN 返回小图
5. 占位 —— 加载完成前显示背景色/占位图，避免布局跳动
6. 预加载 —— 首屏关键图可用 wx.preloadImage 提前加载
```

服务端配合：SpringBoot 后台为图片资源提供统一访问入口（如 /files/{id}?w=200），内部调用 CDN 或图片处理服务生成缩略图。小程序端按展示尺寸拼接参数，避免大图小用。用户上传的图片上传时即做压缩（wx.compressImage）再传服务器，源头控制体积。

```js
// 上传前压缩图片
wx.chooseMedia({
  count: 1,
  mediaType: ['image'],
  success: (res) => {
    const tempPath = res.tempFiles[0].tempFilePath;
    wx.compressImage({
      src: tempPath,
      quality: 80,
      success: (r) => {
        // 压缩后的 r.tempFilePath 再走 uploadFile 上传
        wx.uploadFile({
          url: 'https://api.example.com/files',
          filePath: r.tempFilePath,
          name: 'file',
          success: (up) => {
            console.log('上传成功：', JSON.parse(up.data).url);
          }
        });
      }
    });
  }
});
```

```text
图片优化要点：
1. 上传压缩 —— wx.compressImage 上传前压缩，quality 80 保底
2. 格式转换 —— 大图转 WebP，图标用 SVG/base64 小图
3. CDN 缩放 —— 按展示尺寸请求，绝不传原图
4. 懒加载 —— 列表图 lazy-load，首屏图可 preloadImage
5. 缓存 —— CDN 与小程序缓存配合，二次访问零加载
6. 体积 —— 代码包内只留图标类小图，其余全部外链
```

## 骨架屏

骨架屏（Skeleton Screen）是首屏数据未返回时展示的灰色占位结构，模拟最终页面的轮廓。它解决的是「白屏焦虑」：用户看到内容结构在，就知道页面在加载，而不是坏了。实现方式有三类：手写占位节点、生成式骨架屏工具、组件库内置。

```xml
<!-- 手写骨架屏：占位结构与真实页面同构 -->
<view class="skeleton" wx:if="{{loading}}">
  <view class="skeleton-avatar" />
  <view class="skeleton-line" style="width: 60%;" />
  <view class="skeleton-line" style="width: 80%;" />
  <view class="skeleton-block" />
</view>

<!-- 真实内容：数据到达后渲染 -->
<view class="profile" wx:else>
  <image class="avatar" src="{{user.avatar}}" />
  <text class="name">{{user.name}}</text>
  <text class="desc">{{user.desc}}</text>
  <view class="content">{{user.content}}</view>
</view>
```

```css
/* skeleton 样式：灰色圆角块，可加轻微呼吸动画 */
.skeleton-avatar {
  width: 96rpx;
  height: 96rpx;
  border-radius: 50%;
  background: #f0f0f0;
  margin-bottom: 24rpx;
}
.skeleton-line {
  height: 32rpx;
  border-radius: 8rpx;
  background: #f0f0f0;
  margin-bottom: 16rpx;
}
.skeleton-block {
  height: 200rpx;
  border-radius: 12rpx;
  background: #f0f0f0;
  margin-top: 24rpx;
}
```

骨架屏的核心原则是「与真实页面同构」：占位结构的布局、比例与真实内容一致，这样数据到达时视图变化最小，不会出现内容跳动。进阶做法是「骨架屏生成」：官方开发者工具支持「生成骨架屏」能力（工具 - 生成骨架屏），从已完成的页面直接导出骨架屏代码；第三方工具（如骨架屏生成器、Sketch 插件）原理相同。

```text
骨架屏要点：
1. 出现时机 —— 页面 onLoad 即展示，loading 为 true 时渲染
2. 切换时机 —— 首屏数据 setData 成功后 loading 置 false，渲染真实内容
3. 同构 —— 占位结构与真实布局一致，避免数据到达时布局跳动
4. 动效 —— 骨架块加呼吸/闪烁动画，加载过程更自然
5. 生成 —— 开发者工具「生成骨架屏」一键导出，省去手写
6. 适用范围 —— 首屏数据慢的页面值得做；瞬时返回数据的页面不必
```

数据到达后的切换注意点：loading 状态切换与数据 setData 建议一次完成（`setData({ loading: false, user: data })`），避免先出真实内容再闪一下骨架，或骨架消失后内容未到又白屏。骨架屏与「缓存优先」策略配合时：有缓存先渲染缓存数据（loading 直接 false），无缓存再走骨架屏。

## 懒加载

懒加载（Lazy Loading）的核心思想：用的时候才加载。小程序里的懒加载覆盖三个层面——图片懒加载（lazy-load 属性）、数据分页加载（滚动到底再请求）、组件按需（lazyCodeLoading 与分包，见 13.2）。三者独立作用、叠加生效。

```text
懒加载三层面：
1. 图片懒加载 —— image 的 lazy-load 属性，滚动到可视区才加载图片
2. 数据分页 —— 列表滚动到底部触发下一页请求，避免一次拉全量
3. 组件/分包按需 —— lazyCodeLoading 按需注入、分包按需下载（13.2）
4. 触发时机 —— 滚动接近底部（onReachBottom）或可视区检测（IntersectionObserver）
5. 兜底 —— 懒加载失败要有降级：重试按钮、默认图、错误提示
6. 权衡 —— 首屏关键内容不懒加载，懒加载只用于非首屏/滚动区内容
```

图片懒加载的实现除了 image 组件的 lazy-load 属性，还可以用 `wx.createIntersectionObserver` 精确控制：监听某个容器进入视口时再动态设置图片 src。适用于自定义加载时机（如下拉刷新区域内的图片、轮播图预加载）。

```js
// 用 IntersectionObserver 实现自定义懒加载
Page({
  onReady() {
    this.observer = wx.createIntersectionObserver(this);
    this.observer
      .relativeToViewport({ bottom: 100 })
      .observe('.lazy-img', (res) => {
        if (res.intersectionRatio > 0) {
          // 进入可视区，加载真实图片
          this.setData({ 'item.src': this.data.item.realSrc });
          this.observer.disconnect();
        }
      });
  }
});
```

数据分页懒加载已经在前文（13.3 场景一）覆盖：onReachBottom 触发下一页、_loading 防重入、finished 判断结束。这里补充「接近底部提前加载」：列表很短时 onReachBottom 触发太晚，可以用 IntersectionObserver 监听「底部哨兵节点」，进入可视区提前 100px 就加载下一页，滚动体验更顺滑。

```text
懒加载要点：
1. 图片 —— lazy-load 属性是默认方案，复杂时机用 IntersectionObserver
2. 数据 —— 分页 + 哨兵节点提前加载，比到底才加载更顺滑
3. 组件 —— 按需注入（lazyCodeLoading）与分包是代码层懒加载
4. 防抖防重 —— 加载中标记 _loading，防止重复触发
5. 空态 —— 懒加载全部结束后展示「没有更多」空态
6. 首屏例外 —— 首屏可视内容立即加载，不做懒加载
```

## 应用场景实战

### 场景一：商品首页首屏优化（缓存 + 骨架屏 + 图片优化）

首页是流量入口，优化目标是「打开即有内容、滚动不卡」。组合缓存优先、骨架屏、图片懒加载三个手段：

```js
// pages/home/home.js
Page({
  data: {
    loading: true,
    banners: [],
    goods: []
  },
  onLoad() {
    // 1. 缓存优先：先渲染本地缓存，首屏秒开
    const cached = wx.getStorageSync('home_cache');
    if (cached && cached.expire > Date.now()) {
      this.setData({
        banners: cached.banners,
        goods: cached.goods,
        loading: false
      });
    }
    // 2. 网络请求刷新数据
    this.fetchHome();
  },
  fetchHome() {
    wx.request({
      url: 'https://api.example.com/home',
      success: (res) => {
        const { banners, goods } = res.data.data;
        this.setData({ banners, goods, loading: false });
        // 写缓存，5 分钟内有效
        wx.setStorageSync('home_cache', {
          banners, goods, expire: Date.now() + 5 * 60 * 1000
        });
      },
      fail: () => {
        // 无缓存且请求失败时保留骨架屏并提示
        if (!this.data.goods.length) {
          wx.showToast({ title: '网络异常', icon: 'none' });
        }
      }
    });
  }
});
```

### 场景二：直播列表页用回收列表 + 哨兵懒加载

直播列表可能有几百上千条，使用 recycle-view 回收渲染，并用底部哨兵节点提前加载下一页：

```xml
<!-- pages/live/live.wxml -->
<recycle-view scroll-y="{{true}}" batch="{{batchSetRecycleData}}" id="liveList">
  <recycle-item wx:for="{{list}}" wx:key="id">
    <view class="live-cell">
      <image src="{{item.cover}}" mode="aspectFill" lazy-load="{{true}}" />
      <text>{{item.title}}</text>
      <text>{{item.viewer}} 人在看</text>
    </view>
  </recycle-item>
</recycle-view>
<!-- 底部哨兵节点：进入可视区前 100px 提前加载下一页 -->
<view id="list-sentinel" class="sentinel">{{finished ? '没有更多了' : '加载中...'}}</view>
```

```js
// pages/live/live.js
Page({
  data: {
    list: [],
    page: 1,
    finished: false
  },
  onReady() {
    this.fetchPage(1);
    // 哨兵监听：滚到接近底部时提前加载
    this.sentinelObserver = wx.createIntersectionObserver(this);
    this.sentinelObserver
      .relativeToViewport({ bottom: 100 })
      .observe('#list-sentinel', (res) => {
        if (res.intersectionRatio > 0 && !this._loading && !this.data.finished) {
          this.fetchPage(this.data.page + 1);
        }
      });
  },
  fetchPage(page) {
    if (this._loading || this.data.finished) return;
    this._loading = true;
    wx.request({
      url: 'https://api.example.com/lives',
      data: { page, pageSize: 30 },
      success: (res) => {
        const list = this.data.list.concat(res.data.list);
        this.setData({
          list,
          page,
          finished: res.data.list.length < 30
        });
      },
      complete: () => { this._loading = false; }
    });
  },
  onUnload() {
    if (this.sentinelObserver) this.sentinelObserver.disconnect();
  }
});
```

```text
场景二要点：
1. recycle-view —— 千级直播列表只渲染可视区，滚动流畅
2. 哨兵节点 —— IntersectionObserver 提前 100px 触发加载下一页
3. 防重入 —— _loading 标记防止滚动抖动导致重复请求
4. 结束态 —— finished 为 true 时展示「没有更多了」
5. 资源释放 —— onUnload 断开 observer，避免内存泄漏
```

## 最佳实践与踩坑记录

### 最佳实践

1. 启动链路按「下载 → 解析 → 执行 → 数据 → 渲染」五段逐段优化：分包控下载、按需注入控解析、onLaunch 异步化控执行、缓存控数据、骨架屏控渲染
2. 首屏数据请求在 onLoad 立即发起，与页面渲染并行；关键接口合并成一个聚合接口，减少串行往返
3. 本地缓存做「秒开垫底」：首页等高频页面缓存最近一次数据，网络返回前先渲染缓存，再静默刷新
4. 图片统一走「压缩 → WebP → CDN 缩放 → 懒加载」流水线，上传图片时 wx.compressImage 压缩，展示时按尺寸请求
5. 千条级列表用 recycle-view，百条级列表用分页 + wx:key + 路径更新，不要硬渲染大列表
6. 骨架屏与真实页面同构，loading 与数据一次 setData 切换，避免布局跳动与二次闪烁
7. 所有懒加载加防重入与失败兜底：_loading 标记、重试入口、默认占位，懒加载失败不能白屏
8. 性能优化以测量为闭环：Performance 面板/启动耗时上报量化前后对比，每次发版关注性能指标波动

### 踩坑记录

坑 1：onLaunch 里同步请求登录，启动时间被拖长
结论：启动明显变慢，冷启动时间超标。
原因：onLaunch 里 wx.request 是异步的不会阻塞，但同步读取大缓存、同步初始化 SDK 会阻塞启动；多个串行初始化进一步拉长。
解法：onLaunch 只做轻量初始化，重活异步化；登录态刷新后台进行；用启动耗时上报验证。

坑 2：首屏数据接口串行请求，白屏时间等于多个接口之和
结论：首屏 3 个接口依次请求，白屏时间被拉长 3 倍。
原因：代码里上一个请求 success 里才发下一个请求，形成串行链。
解法：并行发起或后端合并聚合接口；只对存在依赖的请求保持串行。

坑 3：长列表一次性渲染，滚动卡成 PPT
结论：300 条数据一次 setData 渲染，真机滚动严重掉帧。
原因：视图层一次性创建数百节点，超出渲染能力。
解法：分页加载 + onReachBottom 追加；千级列表换 recycle-view。

坑 4：列表图片没开 lazy-load，滚动时疯狂加载图片
结论：列表滚动卡顿，Network 面板同时几十个图片请求。
原因：图片全部提前加载，解码与网络并发拖垮渲染线程。
解法：image 加 lazy-load="{{true}}"；首屏外的图片延迟到可视区加载。

坑 5：图片传原图，页面加载慢且流量大
结论：详情页大图加载慢，用户流量消耗大。
原因：CDN 返回原图，未按展示尺寸缩放。
解法：CDN 加缩放参数按需返回尺寸；上传时压缩；WebP 格式优先。

坑 6：骨架屏与真实内容布局不一致，数据到达时页面跳动
结论：骨架屏展示时布局正常，数据到达后内容整体位移。
原因：骨架占位的高度、间距与真实内容不一致。
解法：骨架屏与真实页面同构（相同尺寸比例）；切换时 loading 与数据一次 setData。

坑 7：懒加载哨兵节点被内容撑出屏幕外，永远不触发
结论：滚到底部也不加载下一页，哨兵节点从未进入可视区。
原因：哨兵节点在列表容器内部且被 recycle-view 回收，监听不到。
解法：哨兵放列表容器外（页面根节点下）；用 onReachBottom 兜底双保险。

坑 8：InterSectionObserver 没 disconnect，页面切换后报错
结论：页面 onUnload 后控制台报 observer 相关错误，偶发内存问题。
原因：observer 未销毁，继续回调操作已卸载的页面实例。
解法：onUnload 里 disconnect；回调里判断页面实例是否存在。

坑 9：缓存数据渲染后网络刷新，用户看到内容「跳变」
结论：缓存先显示旧数据，网络返回后整页内容突然变化。
原因：缓存与网络数据差异大，直接整体 setData 覆盖。
解法：缓存与实时数据差异可控时才用缓存优先；数据到达后平滑更新（如先更新非关键区域）。

坑 10：开了 webp 但 CDN 没提供 webp 资源，图片加载失败
结论：部分机型图片裂图或加载失败。
原因：webp 属性开启后按 .webp 请求资源，CDN 无此格式或旧机型不支持解码。
解法：CDN 提供 webp 版本并做好格式协商；低版本基础库/机型做兼容判断，不支持则回退 jpg。
