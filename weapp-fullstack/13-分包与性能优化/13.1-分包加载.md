## 概述

小程序对代码包体积有严格限制：主包不能超过 2M，整个小程序（主包 + 所有分包）不能超过 30M。当业务功能越来越多、代码包逼近上限时，必须通过分包（subpackage）把非首屏相关的页面与代码拆出去，让小程序启动时只加载主包，进入对应分包页面时才按需下载分包。分包加载是微信小程序工程化的第一道必做功课，也是后续预下载、按需注入、异步化等高级优化手段的基础。

分包的核心思想是「按需加载」：把启动路径上用不到的代码拆到独立的包里，以「首屏加载更快、总包可超过 2M、各模块边界清晰」三个收益换取「目录结构多一层、资源引用受限」两个代价。分包不是简单的目录整理，它涉及配置、体积、引用规则、入口限制等一整套约束，理解这些约束才能设计出既满足体积要求又不踩坑的分包方案。

```text
分包加载的核心要点：
1. 主包 —— 小程序启动时加载，包含启动页、tabBar 页面、公共组件与公共 JS
2. 分包 —— 进入分包页面时才加载，每个分包有独立的 root 目录与 pages 列表
3. 体积 —— 主包 ≤ 2M，单个分包 ≤ 2M，整个小程序（主包+所有分包）≤ 30M
4. 入口 —— 启动页与 tabBar 页面必须放在主包，分包页面只能作为二级入口
5. 引用 —— 分包可引用主包资源，主包与分包之间、分包与分包之间默认不可互相引用
6. 独立分包 —— 加 independent 字段后可独立于主包运行，适合秒开场景
```

## 分包概念

分包（subpackage）是指在小程序代码中，按照业务模块或功能边界，将一部分页面、组件、JS、样式与资源单独打包成一个代码包。小程序启动时只下载并执行主包，当用户导航到某个分包内的页面时，微信客户端才去下载并运行对应的分包。

为什么需要分包？小程序诞生之初整个代码包限制为 2M，业务稍微复杂就会撞上限；即使总包限制后来放宽到 30M，如果所有代码都在主包里，启动时就要全部下载解析，首屏自然变慢。分包让「体积」与「速度」两个问题同时得到缓解：

```text
分包带来的收益：
1. 突破 2M 限制 —— 单个包仍限 2M，但分包总数可达 30M，业务可随规模增长
2. 启动更快 —— 启动只加载主包，分包按需下载，首屏路径上的代码量最小化
3. 模块边界清晰 —— 每个分包独立编译独立发布，团队可并行维护不同业务模块
4. 代码隔离 —— 分包内的私有资源不会污染主包，目录职责一目了然
5. 配合预下载 —— 分包可配置预下载策略，在空闲网络下提前缓存（见 13.2）
```

主包与分包的关系可以概括为「一对多」：一个主包 + 零到多个分包。主包是启动的根，负责 App 生命周期、全局配置、tabBar、启动页与公共资源；分包是业务的枝，按模块承载各自独立的页面与私有代码。分包页面虽然拥有独立的页面路径，但它们共享同一个 App 实例、同一份全局配置（app.json 中的 window 等字段），用户体验上是完整的一个小程序。

什么时候该拆分包？判断标准很简单：主包体积逼近 2M 上限，或者启动/首屏时间明显受代码体积拖累，或者存在体量大但与首屏无关的模块（如商城商品详情、直播间、营销活动、后台管理页）。注意：分包不是越细越好，分包越多，分包间的重复代码越多、预下载策略越复杂，一般按「业务模块」而不是「页面数量」来划分。

```text
分包结构示例：
miniprogram/
├── app.js                  # 主包：App 实例
├── app.json                # 主包：全局配置（含 subpackages 声明）
├── app.wxss                # 主包：全局样式
├── pages/
│   ├── index/              # 主包：tabBar 首页
│   └── order/              # 主包：tabBar 订单页
├── packageGoods/           # 分包一：商品模块
│   ├── pages/list/         # 商品列表页
│   ├── pages/detail/       # 商品详情页
│   └── utils/price.js      # 分包私有工具
└── packageUser/            # 分包二：用户模块
    └── pages/profile/      # 个人主页（非 tabBar）
```

## subpackages 配置

分包在 app.json 中通过 `subpackages` 字段声明（官方同时兼容 `subPackages` 写法）。它是一个数组，每个元素是一个分包对象，包含两个必填字段：`root`（分包根目录，必须以 `/` 结尾或写相对路径）与 `pages`（分包内页面路径列表，相对 root 目录，无需写 .js 后缀）。

```json
{
  "pages": [
    "pages/index/index",
    "pages/order/order"
  ],
  "subpackages": [
    {
      "root": "packageGoods",
      "pages": [
        "pages/list/list",
        "pages/detail/detail"
      ]
    },
    {
      "root": "packageUser",
      "pages": [
        "pages/profile/profile"
      ],
      "independent": true
    }
  ]
}
```

配置完成后，分包页面的完整路径是「root + pages 中的相对路径」，例如上例中商品列表页的完整路径为 `packageGoods/pages/list/list`。跳转到分包页面与跳转普通页面没有区别，使用 `wx.navigateTo` 并传入完整路径即可：

```js
// 主包页面中跳转到分包页面
wx.navigateTo({
  url: '/packageGoods/pages/detail/detail?id=1001',
  success() {
    console.log('已进入商品详情分包页面');
  },
  fail(err) {
    console.error('跳转失败：', err);
  }
});
```

注意几个配置细节：`root` 不能以 `/` 开头也不能写成 `../` 形式，必须是项目内的合法相对目录；`pages` 数组不能为空；分包页面同样有各自的 `.json` 配置文件（页面标题、usingComponents 等），其使用 components 时若引用主包组件路径要写完整相对路径；分包 root 下未被 pages 引用的目录（如分包内的 components、utils、images）会被框架自动收集为分包的一部分，随分包一起打包下载。主包页面、tabBar 页面都不能出现在任何分包的 pages 中，否则编译直接报错。

```text
subpackages 配置要点：
1. subpackages 数组 —— 每个元素一个分包，root 定义根目录，pages 定义页面列表
2. root 写法 —— 相对项目根目录的目录名，不能以 / 开头，如 packageGoods
3. pages 写法 —— 相对 root 的相对路径，不带后缀，如 pages/list/list
4. 页面完整路径 —— root 与 pages 拼接，如 packageGoods/pages/list/list
5. 跳转 —— wx.navigateTo / wx.redirectTo 传完整路径即可，分包页面无特殊 API
6. 目录归属 —— 分包 root 下未被 pages 引用的文件（组件/工具/图片）也随分包打包
```

## 分包体积限制

分包体积限制是小程序平台的核心约束，编译与上传阶段都会被严格校验。当前规则如下：

```text
分包体积限制（正式版）：
1. 主包大小 ≤ 2M —— 启动时全部加载，超限无法上传
2. 单个分包大小 ≤ 2M —— 每个分包独立计算，超限无法上传
3. 整个小程序（主包 + 所有分包）≤ 30M —— 2023 年起由 20M 放宽至 30M
4. 校验时机 —— 开发者工具编译、上传代码时实时提示，超限直接拦截上传
5. 体积统计口径 —— 分包内所有文件（js/wxml/wxss/json/图片/字体等）压缩前或压缩后按平台规则累计
6. 例外 —— 通过 CDN 外链引用的图片、音视频等静态资源不计入代码包体积
```

理解体积统计口径很重要：分包体积统计的是代码包内所有文件的总大小，包括 js、wxml、wxss、json、图片、字体等一切被打包进目录的文件。因此体积优化有两类手段：一类是「减量」——压缩代码、删除无用依赖、用 CDN 外链图片；另一类是「搬家」——把大的静态资源从分包目录移到 CDN，或把公共依赖抽到主包由多个分包共享（共享代码只算一份体积，而如果每个分包各放一份，则每个分包都要计入 2M）。

查看体积的常用方式：开发者工具「详情」面板可以看到各分包大小；点击工具栏「上传」时，工具会弹出体积校验结果；发布后台「版本管理」页也会展示各代码包体积。本地开发时可以写一个简单的体积分析脚本来排查大文件：

```bash
# 终端中统计各目录体积（示例）
du -sh pages packageGoods packageUser
# 输出示例：
# 1.2M  pages
# 780K  packageGoods
# 320K  packageUser

# 找出单个超过 200K 的大文件
find . -type f -size +200k | xargs ls -lh
```

```text
体积管理要点：
1. 先看总量 —— 主包 2M 是硬限制，主包内只放启动必需代码与公共资源
2. 再看单包 —— 每个分包独立 2M，不要把大资源集中塞进某一个分包
3. 图片外链 —— 商品图、横幅等静态资源一律放 CDN，代码包内只留占位图
4. 公共依赖 —— 多个分包共用的库（如 dayjs、请求封装）抽到主包，避免重复打包
5. 定期体检 —— 每次发布前用体积工具检查，防止功能膨胀悄悄逼近上限
6. 留意压缩 —— 工具默认压缩 js/wxml/wxss，但图片需要开发者自己压缩后再放入
```

## 独立分包

普通分包依赖主包运行：主包负责 App 生命周期、全局配置与公共代码，分包页面被打开前必须先把主包加载好。独立分包（independent）则打破了这种依赖——通过给分包配置 `independent: true`，该分包可以独立于主包运行，用户从独立分包页面进入小程序时，微信不会下载主包，直接加载该分包即可。

```json
{
  "pages": [
    "pages/index/index"
  ],
  "subpackages": [
    {
      "root": "packageActivity",
      "pages": [
        "pages/sale/sale"
      ],
      "independent": true
    }
  ]
}
```

独立分包作为入口有两种触发方式：一是把独立分包页面配置为 `entryPagePath`（小程序启动默认打开的页面），二是通过分享卡片、扫码等外部链接直接进入独立分包页面。无论哪种方式，主包都不参与加载，因此打开速度远快于普通分包页面——这正是秒开营销活动页、秒开分享落地页的关键手段。

独立分包的能力边界必须牢记：独立分包不能使用主包中的任何资源（自定义组件、JS 模块、WXML/WXSS、图片、tabBar 配置等都不行），因为主包根本没被加载；App() 中的全局逻辑（如 onLaunch 里的登录初始化）不会为独立分包执行，需要开发者在独立分包页面自己的 onLoad 中补齐初始化逻辑；独立分包也不能引用其他分包。反过来，独立分包的资源同样不能被主包或其他分包引用。它就像一个小小程序，自己包圆自己。

```text
独立分包要点：
1. 配置 —— 分包对象加 independent: true 字段即可声明为独立分包
2. 入口 —— 可作为 entryPagePath 或通过分享/扫码直接打开，不加载主包
3. 秒开 —— 省去主包下载与解析，适合营销页、秒杀页等打开率敏感场景
4. 隔离 —— 不能用主包任何资源（组件/JS/样式/图片），App 生命周期不执行
5. 自足 —— 独立分包内需要自带登录态、请求封装等原本在主包的公共逻辑
6. 数量 —— 独立分包数量有限制，不要滥用；多数业务一个独立分包足矣
```

使用独立分包时，页面自包含的典型写法：页面 onLoad 中自行获取登录态（wx.getStorageSync 读取 token），自行封装请求（把请求函数复制一份到分包内或从 CDN 加载），页面 JSON 中引用的组件必须是分包内部的组件。如果业务强依赖主包的公共组件库（如弹窗、登录组件），那说明这个模块不适合做独立分包，应改回普通分包。

## 分包使用规则

分包不是简单的文件搬家，它有一整套引用与入口规则。这些规则是编译器的硬约束，违反会在编译或运行时报错。核心规则可以归纳为「入口归主包、引用只向上」：

```text
分包使用规则：
1. tabBar 页面必须放主包 —— 底部导航栏配置的页面不允许在分包中
2. 启动页必须在主包 —— entryPagePath 与 pages 数组第一项（默认启动页）都在主包
3. 分包可引用主包 —— 分包页面可 require 主包 JS、使用主包组件、主包图片与 app.wxss 全局样式
4. 主包不可引用分包 —— 主包 require 分包 JS、主包页面引用分包组件都会编译失败
5. 分包间不可互相引用 —— 普通分包 A 不能 require 分包 B 的代码或引用其组件
6. 跨包引用正解 —— 需要跨包引用时使用分包异步化（require.async，见 13.2）或把公共代码抽到主包
```

分包「引用只向上」的本质是依赖方向约束：主包是依赖树的最上层，分包只能依赖主包。这保证了构建时依赖关系无环：主包不依赖任何分包，分包依赖主包，因此可以任意调整分包划分而不影响主包完整性。违反规则最典型的报错是编译期的「模块 'xxx' 不在主包中，无法被主包引用」以及运行时对分包页面加载失败。

一个容易混淆的点：分包页面可以配置使用主包的自定义组件（usingComponents 指向主包 components 目录），因为分包依赖主包，主包组件已随主包加载；但反过来主包页面引用分包组件不行。分包内页面之间的互相跳转、分包内组件互相引用则完全正常，它们同属一个包。

```js
// 正确：分包内 require 主包公共模块
const request = require('../../utils/request.js');

// 错误：主包 require 分包模块，编译报错「无法找到模块 packageGoods/utils/price.js」
// const price = require('../packageGoods/utils/price.js');

// 正确：分包页面使用主包自定义组件
// 分包页面 list.json：
// { "usingComponents": { "nav-bar": "/components/nav-bar/nav-bar" } }
```

```text
分包使用规则小结：
1. 入口页面 —— 启动页、tabBar 页面、entryPagePath 一律在主包
2. 依赖方向 —— 分包 → 主包（允许），主包 → 分包、分包 → 分包（禁止）
3. 组件引用 —— 分包可 usingComponents 主包组件，主包/分包间反向引用不行
4. 全局配置 —— window 等全局配置对分包页面生效，分包有自己的页面 json 可覆盖
5. 异步化例外 —— require.async 可在运行时跨包加载，是规则 3/4 的官方解药
6. 独立分包 —— 依赖方向进一步收紧：不依赖主包也不可被任何包依赖
```

## 应用场景实战

### 场景一：电商小程序按业务模块拆分包

假设一个电商小程序包含首页、购物车、我的（tabBar，放主包）以及商品列表/详情、订单、直播三个业务模块。把后三个模块拆成三个分包，主包只留 tabBar 页面与公共代码。

```json
// app.json
{
  "pages": [
    "pages/home/home",
    "pages/cart/cart",
    "pages/mine/mine"
  ],
  "tabBar": {
    "list": [
      { "pagePath": "pages/home/home", "text": "首页" },
      { "pagePath": "pages/cart/cart", "text": "购物车" },
      { "pagePath": "pages/mine/mine", "text": "我的" }
    ]
  },
  "subpackages": [
    {
      "root": "packageGoods",
      "pages": [
        "pages/list/list",
        "pages/detail/detail"
      ]
    },
    {
      "root": "packageOrder",
      "pages": [
        "pages/list/list",
        "pages/detail/detail"
      ]
    },
    {
      "root": "packageLive",
      "pages": [
        "pages/room/room"
      ]
    }
  ]
}
```

页面间跳转：首页搜索跳转商品列表，商品列表跳详情，详情页加入购物车后跳转主包购物车页。

```js
// pages/home/home.js —— 首页跳转分包页面
goGoodsList() {
  wx.navigateTo({
    url: '/packageGoods/pages/list/list?keyword=' + this.data.keyword
  });
},

// packageGoods/pages/detail/detail.js —— 详情页回到主包 tabBar 页
goCart() {
  wx.switchTab({
    url: '/pages/cart/cart'
  });
}
```

目录结构随之变为：

```text
miniprogram/
├── app.js / app.json / app.wxss
├── utils/                    # 主包公共工具（request、auth）
├── components/               # 主包公共组件（nav-bar、loading）
├── pages/home|cart|mine      # 主包 tabBar 页面
├── packageGoods/             # 商品分包：pages/、components/、utils/
├── packageOrder/             # 订单分包
└── packageLive/              # 直播分包（直播 SDK 较大，独立成包便于预下载）
```

### 场景二：营销活动页做成独立分包实现秒开

运营经常要求「分享出去的活动页打开越快越好」。把活动页做成独立分包，用户从分享卡片进入时跳过主包加载，直开活动页。

```json
// app.json
{
  "pages": [
    "pages/home/home"
  ],
  "entryPagePath": "pages/home/home",
  "subpackages": [
    {
      "root": "packageActivity",
      "pages": [
        "pages/sale/sale"
      ],
      "independent": true
    }
  ]
}
```

独立分包页面需要自包含：不能依赖主包的请求封装与登录逻辑，所以页面内直接内联最小化请求能力：

```js
// packageActivity/pages/sale/sale.js
Page({
  onLoad(query) {
    // 独立分包不执行主包 App.onLaunch，自行完成初始化
    this.token = wx.getStorageSync('token') || '';
    this.fetchActivity(query.id);
  },
  fetchActivity(id) {
    wx.request({
      url: 'https://api.example.com/activity/' + id,
      header: { Authorization: 'Bearer ' + this.token },
      success: (res) => {
        this.setData({ activity: res.data.data });
      }
    });
  },
  // 分享活动页
  onShareAppMessage() {
    return {
      title: this.data.activity.title,
      path: '/packageActivity/pages/sale/sale?id=' + this.data.activity.id
    };
  }
});
```

```text
场景二要点：
1. independent: true —— 活动分包声明为独立分包
2. 自包含 —— 页面内完成 token 读取与请求，不依赖主包公共代码
3. 分享路径 —— onShareAppMessage 的 path 指向独立分包页面完整路径
4. 收益 —— 从分享卡片进入时只下载活动分包，秒开体验
5. 注意 —— App.onLaunch 不执行，登录态过期等全局逻辑需页面自行兜底
```

## 最佳实践与踩坑记录

### 最佳实践

1. 主包只放「启动必需」：App 逻辑、tabBar 页面、全局组件、公共 utils，其余一切按业务模块拆分包，主包体积稳定控制在 1.5M 以内留出余量
2. 按业务模块而不是页面数量划分分包：一个模块一个分包，模块内页面互相跳转无需跨包，避免「分包碎片化」导致依赖分析混乱
3. 公共代码抽到主包共享：多个分包共用的请求封装、工具库、基础组件放主包，既能减少重复体积，也避免分包间引用违规
4. 静态资源一律 CDN 外链：商品图、banner、音视频不打包进代码包，代码包内只放图标类小资源，从源头控制体积
5. 独立分包只给「秒开诉求」的模块用：营销页、分享落地页值得独立，普通业务页用独立分包反而丢失主包公共能力，得不偿失
6. 分包目录命名统一：packageXxx 前缀（packageGoods、packageOrder），与主包 pages 目录区分，工具脚本按前缀批量处理
7. 每次上传前查看体积面板：把「体积是否超限、哪个包最大」纳入发布检查清单，防止某个分包悄悄涨到 2M 上限
8. 依赖方向画成图：新页面加入前先确认它归属哪个包、依赖哪些包，违反「引用只向上」规则的设计尽早调整

### 踩坑记录

坑 1：tabBar 页面放进分包，编译直接报错
结论：tabBar 配置的 pagePath 不能在分包 pages 中，编译报「tabBar 页面不能放在分包中」。
原因：tabBar 需要随主包常驻，分包按需加载机制无法保证 tabBar 可用。
解法：tabBar 页面全部留在主包 pages 数组，分包的入口一律通过 navigateTo 进入。

坑 2：主包超过 2M，上传代码被拦截
结论：主包体积超 2M 时开发者工具上传失败，提示「主包大小超过 2M 限制」。
原因：主包所有文件累计超过限制，常见原因是图片、第三方库塞进了主包。
解法：用 du 定位大文件，图片迁 CDN、库迁移到引用它的分包或按需引入；主包只留启动必需。

坑 3：主包代码 require 分包模块，编译报「模块不存在」
结论：主包 js 里 require 分包路径，编译报错或运行时 undefined。
原因：主包不依赖分包，构建时不会把分包代码打进主包依赖图。
解法：公共逻辑抽到主包；确实需要跨包加载时改用 require.async（分包异步化，见 13.2）。

坑 4：两个分包互相引用资源，运行时白屏或报错
结论：分包 A 的页面使用分包 B 的组件，打开时组件加载失败、页面异常。
原因：分包间无依赖关系，分包 B 未被下载时其资源不可用，构建期也无法保证顺序。
解法：共享组件抽到主包；或确认基础库支持后使用分包异步化跨包引用。

坑 5：独立分包引用了主包组件，分享打开后白屏
结论：独立分包页面 usingComponents 指向主包 components，从分享进入时组件渲染失败。
原因：独立分包运行时主包不加载，主包组件文件不存在。
解法：独立分包只引用分包内部组件；公共组件若必须用，把该模块改回普通分包。

坑 6：图片打包进分包，分包体积莫名逼近 2M
结论：明明代码不多，分包体积却很大，上传提示超限。
原因：设计稿切图、用户头像占位等图片直接放进了分包目录，全部计入分包体积。
解法：图片上传 CDN，代码包内用网络地址；少量必须内嵌的图标用 base64 或压缩到最小。

坑 7：navigateTo 分包路径少了 root 前缀，页面找不到
结论：跳转报「页面路径不存在」或 fail: page not found。
原因：url 写成了 pages/list/list，缺少 packageGoods 前缀，与 app.json 注册路径不一致。
解法：跳转路径写完整路径 /packageGoods/pages/list/list；用路由封装统一管理路径常量，避免手写。

坑 8：调整分包目录后，真机上还是旧结构
结论：本地编译正常，真机上偶尔出现分包加载失败或页面 404。
原因：旧版本缓存了分包结构，或分包异步化场景下旧分包下载失败未重试。
解法：清理缓存（开发者工具清除缓存/真机上删除小程序重进）；发布新版本时关注「分包加载失败」类告警。

坑 9：独立分包入口未配置 entryPagePath，分享后从主包进入
结论：设置了 independent 但分享路径打开时仍然先加载主包，秒开效果没生效。
原因：仅声明独立分包不会自动让它成为入口，入口由分享路径/entryPagePath 决定。
解法：分享 path 直接指向独立分包页面；如需默认入口，在 app.json 配置 entryPagePath。

坑 10：分包内引用主包 WXS 文件失败
结论：分包 wxml 中 import 主包 WXS 模块，真机上报模块未找到。
原因：WXS 引用遵循同样的依赖方向规则，分包可引用主包 WXS，但路径必须正确且主包 WXS 不能引用分包资源。
解法：WXS 公共函数统一放主包，分包内引用时写相对/绝对正确路径；先确认主包 WXS 本身无跨包依赖。
