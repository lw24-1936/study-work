## 概述

基础库（Base Library）是微信客户端内置的一套运行库，小程序的所有 API（wx.*）与组件都来自基础库，相当于「小程序的系统」。用户手机上的微信版本不同，基础库版本就不同；基础库版本不同，可用的 API 与组件能力就不同。开发者必须理解版本差异，才能写出在绝大多数用户手机上都能正常运行的小程序。

版本兼容要解决的核心矛盾是「开发环境新、用户环境旧」：开发者工具默认使用最新基础库，开发时一切正常，但线上用户可能还运行着旧版基础库，新 API 调用直接报 undefined。解决方案是能力检测（canIUse）、最低基础库版本设置、以及针对旧版本的降级处理。本章是 02 系列中偏「运行环境」的一篇，与 13.4 渲染与启动优化、16.1 版本管理相互衔接。

```text
基础库与版本兼容的核心特征：
1. 随微信更新 —— 基础库跟随微信客户端版本升级，用户不更新微信就升不了级
2. API 来源 —— 所有 wx.* 接口、内置组件都由基础库提供
3. 开发者工具可选 —— 工具内可切换不同基础库版本模拟真机环境
4. 能力检测 —— wx.canIUse 可在运行期判断 API/组件/参数是否可用
5. 最低版本门槛 —— 线上可设置最低基础库版本，低于门槛的用户被拦截升级
6. 兼容策略 —— 特性检测优先于版本号判断，降级方案兜底
```

## 基础库版本概念

基础库版本号形如 2.32.3，采用「主版本.次版本.补丁版本」的三段式结构。每个版本对应微信客户端的一个发布周期：新版本基础库随微信 App 灰度发布，最终推送给所有用户。基础库与微信版本、开发者工具版本之间存在对应关系，微信开发者工具内置了各历史版本的基础库，方便开发者模拟旧环境。

```text
基础库版本认知：
1. 三段式版本号 —— 主版本.次版本.补丁，次版本递增通常带来新 API
2. 与微信版本绑定 —— 用户微信升级，基础库才会升级
3. 工具可切换 —— 开发者工具「详情 - 本地设置 - 调试基础库」可切换版本
4. 新 API 只增不减 —— 新版本新增 API，旧版本调用会报错
5. 部分 API 有最低版本要求 —— 文档中每个 API 都标注「基础库 x.y.z 起支持」
6. 废弃 API 仍保留 —— 微信对旧 API 采用渐进废弃，不立即删除
```

```js
// 获取当前环境的基础库版本号（SDKVersion）
Page({
  onLoad() {
    const info = wx.getSystemInfoSync()
    console.log('基础库版本', info.SDKVersion)
    console.log('微信版本', info.version)
    console.log('系统', info.platform, info.system)

    // 也可以使用 wx.getAppBaseInfo 获取（基础库 2.20.1 起）
    if (wx.getAppBaseInfo) {
      const appInfo = wx.getAppBaseInfo()
      console.log('SDKVersion', appInfo.SDKVersion)
    }
  }
})
```

每个 API 在官方文档中都标注了最低基础库版本，例如 wx.getAppBaseInfo 需要 2.20.1、wx.getWindowInfo 需要 2.20.1、skyline 渲染器需要更高版本。开发时养成查文档版本要求的习惯，是版本兼容的第一步。

```text
版本相关术语：
1. SDKVersion —— 当前基础库版本号，wx.getSystemInfoSync 可获取
2. 最低基础库版本 —— 小程序声明的运行门槛，低于此版本的用户无法打开
3. 调试基础库 —— 开发者工具中手动切换的模拟版本
4. 灰度版本 —— 微信分批推送的新基础库，部分用户先升级
5. 兼容性文档 —— 每个 API/组件标注支持的最低基础库版本
6. 版本分布 —— 小程序后台可查看线上用户的基础库版本分布
```

## 版本分布与灰度

用户手机上的基础库版本分布并不均匀：一部分用户长期不升级微信，停留在旧版；一部分用户使用最新版。新基础库发布时，微信采用灰度策略分批推送，先推送给小比例用户验证稳定性，再逐步扩大范围。因此「最新版 API」在线上可能只有一部分用户能用。

```text
版本分布规律：
1. 长尾明显 —— 总有少量用户停留在很旧的版本（如 1.x、2.0.x）
2. 新版本爬坡 —— 新基础库灰度期间，使用新版用户占比逐步上升
3. 后台可查 —— mp 后台「统计 - 用户画像」或「版本管理」可查看版本分布
4. 灰度期风险 —— 灰度版本若有 bug，先影响小部分用户
5. 企业用户滞后 —— 部分企业微信环境基础库更新更慢
6. 越新越激进 —— 新 API 使用越激进，兼容成本越高
```

小程序后台提供了线上用户的基础库版本分布数据，这是设置最低基础库版本的重要依据：如果 99% 的用户基础库版本都高于 2.20.0，那么把最低版本设置为 2.20.0 对用户影响极小，却能大幅简化兼容代码。查看路径为微信公众平台「统计 - 用户分析」或「开发 - 版本管理」相关模块。

```text
版本分布决策：
1. 查看线上版本分布后再定最低版本，不要拍脑袋
2. 最低版本定得越高，兼容代码越少，但拦截的用户越多
3. 官方通常建议最低版本不低于 2.10.0 左右（视业务而定）
4. 涉及支付等核心功能的页面，优先保证旧版本可用
5. 灰度期上线的新功能，用 canIUse 检测后优雅降级
6. 定期复查版本分布，随着时间推移可逐步提高最低版本
```

## canIUse 能力检测

wx.canIUse 是小程序提供的运行期能力检测 API，用于判断当前基础库是否支持某个 API、组件、属性或参数。它比「比较版本号字符串」更可靠，因为版本号比较容易出错（如 2.9.9 与 2.10.0 的字符串比较问题），而 canIUse 直接查询能力本身。

```js
// canIUse 的四种检测形式
const r1 = wx.canIUse('getSystemInfo')              // 检测 API 是否存在
const r2 = wx.canIUse('button.open-type.getUserInfo') // 检测组件属性（基础库 2.10.4 起支持这种写法）
const r3 = wx.canIUse('request.object.method')      // 检测 API 的参数
const r4 = wx.canIUse('map')                        // 检测组件是否存在

console.log('getSystemInfo 可用:', r1)
console.log('button open-type getUserInfo:', r2)
console.log('request.method 参数:', r3)
console.log('map 组件:', r4)
```

```text
canIUse 语法规则：
1. API 检测 —— wx.canIUse('apiName')，如 wx.canIUse('getLocation')
2. 参数检测 —— wx.canIUse('apiName.object.paramName')，如 wx.canIUse('request.object.timeout')
3. 组件检测 —— wx.canIUse('componentName')，如 wx.canIUse('camera')
4. 组件属性检测 —— wx.canIUse('componentName.property')，如 wx.canIUse('button.open-type')
5. 组件属性值检测 —— wx.canIUse('componentName.property.value')，如 wx.canIUse('button.open-type.getUserInfo')
6. 返回布尔值 —— 支持返回 true，不支持返回 false，不会抛异常
```

canIUse 的典型用法是「特性检测 + 分支处理」：检测到能力存在就使用新 API，否则走旧方案。相比直接判断版本号，特性检测在灰度环境下更准确——用户版本号可能相同，但能力因客户端配置不同而不同。

```js
// 特性检测 + 降级：新 API 不可用时回退到旧 API
Page({
  getWindowInfo() {
    if (wx.canIUse('getWindowInfo')) {
      return wx.getWindowInfo()
    }
    // 降级：旧版 API，仍被广泛支持
    const info = wx.getSystemInfoSync()
    return {
      windowWidth: info.windowWidth,
      windowHeight: info.windowHeight,
      statusBarHeight: info.statusBarHeight,
      safeArea: info.safeArea
    }
  }
})
```

```text
canIUse 使用要点：
1. 用特性检测代替版本号比较，版本号字符串比较有坑（如 2.9.9 vs 2.10.0）
2. 每个新 API 使用前先检测，检测失败走降级逻辑
3. 检测成本极低，可以在初始化阶段批量检测并存到全局
4. 组件属性检测写法注意层级：组件.属性.属性值
5. 检测通过不代表一定可用，部分能力还受权限、机型影响
6. 对不可用场景必须提供兜底，不能只提示「请升级微信」
```

## 最低基础库版本设置

最低基础库版本是小程序声明的运行门槛：低于该版本基础库的用户打开小程序时，会看到「请升级微信」的提示，无法进入小程序。设置位置有两个层面：一是 mp 后台（微信公众平台「设置 - 基本设置 - 基础库最低版本设置」），这是线上生效的门槛；二是 project.config.json 中的 libVersion 字段，它控制开发者工具调试时使用的基础库版本。

```text
最低版本设置的两个层面：
1. mp 后台设置 —— 线上生效，低于门槛的用户被拦截并提示升级微信
2. project.config.json 的 libVersion —— 仅影响开发者工具调试环境
3. 后台设置后需发布新版本才完全生效，且支持随时调整
4. 被拦截用户的比例 = 低于该版本的用户占比（后台版本分布可查）
5. 设置过高会误伤部分用户，设置过低则兼容负担大
6. app.json 中不存在 libVersion 字段，这是常见误解
```

```json
// project.config.json —— 开发者工具使用的基础库版本（工具侧）
{
  "setting": {
    "libVersion": "3.4.10"
  },
  "appid": "wx1234567890abcdef",
  "projectname": "my-miniprogram"
}
```

```text
project.config.json 要点：
1. libVersion 切换开发者工具的调试基础库，用于模拟旧环境
2. 工具「详情 - 本地设置」可视化切换，与直接改 json 等效
3. 上线门槛以 mp 后台设置为准，与 libVersion 无关
4. 团队协作时统一 libVersion，避免「我这能跑你那不能跑」
5. 调试旧版兼容问题时，把 libVersion 切到目标旧版本验证
6. 切换基础库后建议清缓存重新编译，避免旧代码残留
```

最低基础库版本与 iOS 系统版本类似：设置太低（如 1.0.0）等于没设，任何新 API 都要兼容；设置太高（如 3.0.0）会拦截大量用户。合理做法是结合后台版本分布，选择覆盖 95% 以上用户的版本作为门槛，剩余用户通过 canIUse 降级或升级提示处理。

```text
最低版本设置建议：
1. 先看后台版本分布，选覆盖绝大多数用户的版本
2. 新项目起步可设 2.10.0 左右，成熟后按数据上调
3. 设置门槛后仍要做 canIUse 检测，双保险
4. 大版本跨度升级（如 2.x 到 3.x）时评估破坏性变更
5. 后台调整最低版本即时生效，但建议随版本发布一起调整
6. 被拦截用户看到的是微信官方升级提示，无法自定义文案
```

## 兼容处理方案

即使设置了最低基础库版本，线上仍存在版本差异（门槛以下用户被拦截，门槛以上用户版本也各不相同），因此需要一套系统的兼容处理方案：特性检测（canIUse）、降级实现（polyfill / 旧 API 回退）、能力降级（简化功能）三层策略。

```text
兼容处理三层策略：
1. 特性检测 —— 使用新 API 前用 wx.canIUse 判断，不支持的走降级分支
2. 降级实现 —— 用旧 API 组合实现新 API 效果（如 getSystemInfoSync 拼 getWindowInfo）
3. 能力降级 —— 某些能力旧版本确实没有，则隐藏入口或简化交互
4. 初始化集中检测 —— 启动时批量检测能力，结果存全局，各页面复用
5. 统一封装 —— 把兼容逻辑封装成公共模块（如 utils/env.js），避免散落各页面
6. 真机验证 —— 用旧版本微信真机实测降级路径，模拟器不能完全替代
```

```js
// utils/env.js —— 集中管理环境检测与兼容判断
const env = {
  // 缓存检测结果，避免重复调用
  _cache: {},

  canUse(apiPath) {
    if (this._cache[apiPath] === undefined) {
      try {
        this._cache[apiPath] = wx.canIUse(apiPath)
      } catch (e) {
        this._cache[apiPath] = false
      }
    }
    return this._cache[apiPath]
  },

  // 统一的窗口信息获取（含降级）
  getWindowInfo() {
    if (this.canUse('getWindowInfo')) {
      return wx.getWindowInfo()
    }
    const info = wx.getSystemInfoSync()
    return {
      windowWidth: info.windowWidth,
      windowHeight: info.windowHeight,
      statusBarHeight: info.statusBarHeight,
      safeArea: info.safeArea
    }
  },

  // 判断是否支持暗黑模式适配
  supportDarkMode() {
    return this.canUse('getSystemInfoSync.theme') ||
      this.canUse('getAppBaseInfo')
  }
}

module.exports = env
```

```js
// 页面中使用统一封装
const env = require('../../utils/env')

Page({
  onReady() {
    const win = env.getWindowInfo()
    this.setData({
      statusBarHeight: win.statusBarHeight,
      windowWidth: win.windowWidth
    })
  }
})
```

除了 API 层面的兼容，还有渲染层面的兼容：新渲染引擎（Skyline）与旧渲染引擎（WebView）对部分组件、样式支持度不同；分包能力（13.1）要求基础库 2.3.0 以上。对于核心功能，可以采用「能力降级」：检测到不支持分包时回退到主包加载逻辑；检测到不支持新组件时用基础组件替代。

```text
兼容处理注意事项：
1. 兼容逻辑统一封装，禁止在业务代码里散落版本判断
2. 降级路径必须真机验证，模拟器基础库可以切版本但渲染有差异
3. 不要过度兼容 —— 覆盖 95% 以上用户即可，剩余用户引导升级
4. 兼容代码写清楚注释：为什么降级、何时可以删除
5. 新版本发布一段时间后，定期清理不再需要的降级分支
6. 灰度期新功能默认关闭，用开关控制逐步放量
```

## 应用场景实战

### 场景一：启动时统一能力检测与降级

在 App 的 onLaunch 中集中检测关键能力，把结果写入 globalData，各页面直接读取，避免每个页面重复调用 canIUse，同时统一处理降级策略。

```js
// app.js
const env = require('./utils/env')

App({
  globalData: {
    env: null,
    featureFlags: {}
  },

  onLaunch() {
    // 集中检测关键能力
    const featureFlags = {
      // 新窗口信息 API
      newWindowInfo: env.canUse('getWindowInfo'),
      // 暗黑模式跟随系统
      darkMode: env.supportDarkMode(),
      // 分包能力
      subPackages: env.canUse('wx.loadSubpackage'),
      // 半屏弹窗
      halfScreen: env.canUse('openHalfScreen')
    }
    this.globalData.featureFlags = featureFlags
    this.globalData.env = env
  }
})
```

```js
// pages/index/index.js —— 页面读取能力开关
const app = getApp()

Page({
  onLoad() {
    const flags = app.globalData.featureFlags
    // 支持半屏弹窗就用新交互，否则用普通弹窗
    if (flags.halfScreen) {
      this.showHalfScreenShare()
    } else {
      this.showNormalShareModal()
    }
  }
})
```

```text
场景一要点：
1. onLaunch 集中检测，一次性完成，各页面零成本读取
2. featureFlags 语义化命名，业务代码只关心「能力是否存在」
3. 检测结果缓存，避免页面级重复 canIUse
4. 每个能力都要有降级分支，不允许「不支持就报错」
5. 新能力灰度时通过开关控制，与基础库版本解耦
```

### 场景二：旧版基础库下的列表页兼容改造

一个老项目要接入新的图片懒加载组件和暗黑模式，但线上仍有用户基础库低于新组件要求，需要做兼容改造。

```js
// pages/list/list.js —— 组件级兼容
const app = getApp()

Page({
  data: {
    list: [],
    useLazyImage: true
  },

  onLoad() {
    const flags = app.globalData.featureFlags
    // 新图片懒加载组件需要基础库 2.1.0+，不满足则用普通 image
    this.setData({
      useLazyImage: flags.lazyImage
    })
  }
})
```

```xml
<!-- pages/list/list.wxml —— 按能力开关渲染不同组件 -->
<view class="list">
  <block wx:for="{{list}}" wx:key="id">
    <!-- 支持懒加载组件 -->
    <lazy-image
      wx:if="{{useLazyImage}}"
      src="{{item.cover}}"
      lazy-load="{{true}}"
    />
    <!-- 降级：普通 image，配合占位背景色 -->
    <image
      wx:else
      class="cover"
      src="{{item.cover}}"
      mode="aspectFill"
    />
  </block>
</view>
```

```js
// 暗黑模式降级：跟随系统的 theme 不可用时，用固定浅色主题
const env = require('../../utils/env')

Page({
  onLoad() {
    if (env.supportDarkMode()) {
      // 通过 wx.onThemeChange 监听主题变化
      wx.onThemeChange((res) => {
        this.setData({ theme: res.theme })
      })
    } else {
      // 旧版本固定浅色
      this.setData({ theme: 'light' })
    }
  }
})
```

```text
场景二要点：
1. 组件级能力用 wx:if 切换渲染，新旧组件互不干扰
2. 降级组件保持视觉一致性（占位色、宽高比例一致）
3. 主题能力按「支持/不支持」分流，不支持时固定默认主题
4. 兼容改造后重点回归旧版本微信真机：渲染、交互、数据三方面
5. 记录每个兼容分支对应的最低版本与清理时机，防止僵尸代码
```

## 最佳实践与踩坑记录

### 最佳实践

1. 开发时养成查文档「基础库版本要求」的习惯，新 API 使用前先确认最低版本
2. 统一封装环境检测模块（utils/env.js），canIUse 结果缓存复用，禁止业务代码散落版本判断
3. 用特性检测（canIUse）代替版本号比较，版本号字符串比较存在语义陷阱
4. 结合后台版本分布数据设置最低基础库版本，选择覆盖 95% 以上用户的版本作为门槛
5. 开发者工具调试基础库与线上最低版本保持同一策略：调试时切换旧版基础库验证兼容路径
6. 每个降级分支写注释说明「为什么降级、最低版本要求、何时可删除」，新版本发布后定期清理
7. 灰度期新功能用开关控制放量，先小范围验证再全量，与基础库版本解耦
8. 兼容改造后必须用旧版本微信真机回归，模拟器切基础库不能完全模拟真机差异

### 踩坑记录

坑 1：直接调用新 API，旧版基础库报错导致白屏
结论：线上部分用户打开小程序报错，页面无法渲染。
原因：新 API（如 wx.getWindowInfo）在旧基础库上不存在，调用即抛错，且错误发生在页面初始化流程中。
解法：所有新 API 调用前用 wx.canIUse 检测；把关键调用包在 try-catch 中；统一封装兼容模块。

坑 2：用版本号字符串比较判断能力，比较结果错误
结论：判断「基础库版本 >= 2.10.0」时，2.9.9 被误判为更高版本。
原因：字符串比较按字符逐位比较，'2.9.9' > '2.10.0'（'9' > '1'）。
解法：用 wx.canIUse 特性检测代替版本号比较；确需比较版本号时，拆分数字后按位比较。

坑 3：最低基础库版本设置过高，大量用户被拦截
结论：后台设置最低版本 3.0.0 后，用户反馈「打不开小程序」。
原因：线上仍有相当比例用户基础库低于 3.0.0，门槛一刀切拦截了这些用户。
解法：先查后台版本分布，按数据选择门槛；设置后观察被拦截比例，过高则下调。

坑 4：误以为 app.json 中有 libVersion 可配置
结论：在 app.json 中写 libVersion 字段，工具提示未知字段且不生效。
原因：libVersion 属于 project.config.json（开发者工具侧），app.json 无此字段。
解法：线上最低版本在 mp 后台「设置 - 基本设置」配置；工具调试版本在 project.config.json 或工具界面配置。

坑 5：canIUse 检测通过但真机仍报错
结论：wx.canIUse('getLocation') 返回 true，真机调用仍失败。
原因：能力存在但受权限、机型、用户设置限制（如未授权定位、部分安卓机型传感器缺失）。
解法：canIUse 只保证「基础库支持」，调用时仍需处理 fail 回调与授权流程；涉及权限的能力先 wx.authorize 或捕获拒绝。

坑 6：团队基础库版本不一致，出现「我这能跑你那不能跑」
结论：同一份代码，A 同事调试正常，B 同事页面报错。
原因：两人开发者工具的调试基础库版本不同，新版 API 在旧调试基础库上报错。
解法：project.config.json 统一 libVersion 并提交到 Git；工具内统一「详情 - 本地设置」的调试基础库。

坑 7：兼容分支过多，代码难以维护
结论：项目里到处是 if (wx.canIUse(...))，逻辑混乱，删也不敢删。
原因：没有统一封装和清理机制，兼容代码散落各页面。
解法：收敛到 utils/env.js 统一检测；每个分支标注最低版本与清理时机；随版本迭代定期清理过期分支。

坑 8：降级路径从未被验证，线上才暴露问题
结论：新版 API 正常，降级分支逻辑有 bug，旧版本用户功能异常。
原因：开发调试用的是最新基础库，降级路径从未被执行过。
解法：工具中切换旧版调试基础库专门验证降级路径；用旧版本微信真机回归；兼容改造纳入测试用例。
