## 概述

单元测试是测试金字塔的底座：对工具函数、组件逻辑等最小可测单元做隔离验证，不依赖网络、不依赖真机，在 Node 环境中毫秒级运行。小程序单元测试的标准组合是 Jest（测试框架与断言）+ miniprogram-simulate（微信官方出品的组件模拟工具），前者负责测试组织与断言，后者负责把小程序组件在 Node 环境里「渲染」出来，让测试能够加载组件、设置 properties、触发事件并断言渲染结果。

为什么小程序单元测试比普通 Web 项目更重要：小程序没有浏览器环境，无法像 Web 那样打开页面手工验证每个函数；同时小程序的双线程模型让调试成本更高。单元测试能在不打开开发者工具的情况下，快速验证「格式化函数对不对」「组件的某个分支逻辑是否生效」，是开发期反馈最快的一层质量保障。建议从纯函数（utils 模块）起步，再逐步覆盖组件逻辑，最后接入覆盖率统计驱动补测。

```text
单元测试的核心收益：
1. 反馈最快 —— 毫秒级运行，提交前全量跑一遍只需几秒到几十秒
2. 定位精准 —— 失败即定位到具体函数与断言，无需手工复现
3. 回归保险 —— 重构代码后一键验证行为未变，敢于改代码
4. 驱动设计 —— 不可测的代码往往是耦合过重的代码，测试倒逼解耦
5. 文档作用 —— 用例即「输入 -> 期望输出」的活文档，新人看测试快速理解行为
6. 覆盖度量 —— 覆盖率报告指出哪些分支从未执行，补测有据可依
```

## miniprogram-simulate 组件模拟测试

miniprogram-simulate 是微信官方提供的组件测试工具（npm 包 `miniprogram-simulate`），它把小程序组件（Component 构造器声明的组件）在 Node 环境里模拟渲染：解析组件目录下的 .wxml 模板、.wxss 样式与 .js 逻辑，生成一个可以查询、触发事件的模拟组件实例。测试代码通过 `simulate.load(path)` 加载组件文件，通过 `simulate.render(component)` 渲染出实例，再通过实例上的 `querySelector`、`dispatchEvent` 等 API 操作组件。它支持大多数常用组件能力：properties、data、methods、observers、生命周期、slot、组件间通信，但不支持 wx 原生 API（需 mock）与真实渲染（样式断言能力有限）。

安装与配置：miniprogram-simulate 通过 npm 安装，测试运行时需要编译组件代码（官方推荐配合 jest + 一个简易的模块转换，直接 require 组件的 .js 文件即可，组件目录下的 wxml/wxss 由 simulate 内部解析）。组件文件用 CommonJS 的 `Component({...})` 写法，simulate 在加载时会注入全局的 Component/Behavior/getApp 等函数，因此组件测试文件不需要额外 mock Component。需要注意：组件代码里不要引用 wx 对象，或引用处需用 jest mock 兜底。

```bash
# 安装依赖（项目根目录执行）
npm init -y
npm install --save-dev jest miniprogram-simulate
```

```javascript
// 被测组件：components/price-tag/index.js
Component({
  properties: {
    price: { type: Number, value: 0 },      // 单位：元
    originalPrice: { type: Number, value: 0 }
  },
  data: {
    discount: ''      // 折扣描述，如 8.5折 / 直降
  },
  observers: {
    'price, originalPrice': function (price, originalPrice) {
      let discount = '';
      if (price > 0 && originalPrice > price) {
        const ratio = Math.round((price / originalPrice) * 100) / 10;
        discount = ratio + '折';
      }
      this.setData({ discount });
    }
  },
  methods: {
    formatPrice(value) {
      return (value / 100).toFixed(2);   // 分转元
    }
  }
});
```

```javascript
// tests/price-tag.test.js —— 用 miniprogram-simulate 加载并渲染组件
const simulate = require('miniprogram-simulate');
const path = require('path');

// load 传入组件目录（目录内需有 index.js/index.wxml/index.json）
const component = simulate.load(path.join(__dirname, '../components/price-tag/index'));

test('组件能正常加载并渲染', () => {
  const id = simulate.load(path.join(__dirname, '../components/price-tag/index'));
  const comp = simulate.render(id);   // 渲染组件实例
  expect(comp.querySelector('.price-tag')).not.toBeNull();
});

test('properties 设置后渲染结果正确', () => {
  const comp = simulate.render(component);
  comp.setData({ price: 8500, originalPrice: 10000 });  // 直接改 data 触发 observers
  // 断言视图层文本
  const text = comp.querySelector('.discount').textContent;
  expect(text).toBe('8.5折');
});

test('触发事件后 methods 被调用', () => {
  const comp = simulate.render(component);
  // 触发组件内绑定的 tap 事件（假设 wxml 中有 bindtap="onTap"）
  comp.querySelector('.price-tag').dispatchEvent('tap');
  // 若 onTap 内调用了 triggerEvent，可断言组件向父级抛出的事件
});
```

```text
miniprogram-simulate 使用要点：
1. 安装 —— npm install --save-dev miniprogram-simulate，随 Jest 一起使用
2. 加载 —— simulate.load(组件目录绝对路径)，目录需含 index.js / index.wxml / index.json
3. 渲染 —— simulate.render(componentId) 得到组件实例，querySelector 查询节点
4. 数据 —— comp.setData 修改 data 触发 observers 与视图更新，再断言文本
5. 事件 —— dispatchEvent('tap') 模拟点击，组件内 triggerEvent 的事件可被监听断言
6. 局限 —— 不支持 wx 原生 API 与真实样式渲染，涉及 wx.* 处需 mock
```

## Jest 测试框架

Jest 是 Facebook 开源的 JavaScript 测试框架，内置断言库、mock 机制、覆盖率统计与 watch 模式，是当前小程序单元测试的事实标准。Jest 通过 `testEnvironment` 指定运行环境：小程序单元测试推荐 `node` 环境（组件由 simulate 模拟，不需要真实 DOM）；`jsdom` 环境适合需要 DOM API 的测试。Jest 的配置文件 `jest.config.js` 可设置 testMatch（测试文件匹配）、transform（模块转换，小程序项目常用 babel-jest 转译 ES 语法）、moduleNameMapper（路径别名映射）、collectCoverageFrom（覆盖率收集范围）。

Jest 的断言使用 `expect` + matcher：`toBe`（引用相等）、`toEqual`（深比较）、`toContain`（数组/字符串包含）、`toHaveBeenCalled`（mock 函数被调用）、`toThrow`（抛异常）。mock 是 Jest 的核心能力：`jest.fn()` 创建替身函数，`jest.mock()` 整体替换模块（如 wx API、request 模块），`jest.spyOn()` 监听对象方法。测试组织上，`describe` 分组、`test/it` 定义用例、`beforeEach/afterEach` 做前后置清理。

```javascript
// jest.config.js —— 小程序单元测试配置
module.exports = {
  testEnvironment: 'node',              // 组件由 simulate 模拟，无需 jsdom
  testMatch: ['**/tests/**/*.test.js'], // 测试文件位置
  collectCoverageFrom: [
    'utils/**/*.js',                     // 只统计业务代码，不统计测试文件
    'components/**/*.js'
  ],
  coverageReporters: ['text', 'lcov'],   // 终端摘要 + lcov 网页报告
  clearMocks: true,                      // 每个用例前自动清空 mock 调用记录
  transform: {
    '^.+\\.js$': 'babel-jest'            // ES 语法转译（配合 babel.config.js）
  }
};
```

```javascript
// utils/format.js —— 被测纯函数
function formatTime(ms) {
  const date = new Date(ms);
  const pad = (n) => (n < 10 ? '0' + n : '' + n);
  return `${date.getFullYear()}-${pad(date.getMonth() + 1)}-${pad(date.getDate())} ${pad(date.getHours())}:${pad(date.getMinutes())}`;
}

function calcDiscount(price, originalPrice) {
  if (!price || !originalPrice || originalPrice <= price) return null;
  return Math.round((price / originalPrice) * 100) / 10 + '折';
}

module.exports = { formatTime, calcDiscount };
```

```javascript
// tests/format.test.js —— 断言与 mock 基础用法
const { formatTime, calcDiscount } = require('../utils/format');

describe('formatTime 时间格式化', () => {
  test('正常时间戳格式化', () => {
    expect(formatTime(new Date('2026-08-20T10:30:00').getTime())).toBe('2026-08-20 10:30');
  });
  test('月份与日期补零', () => {
    expect(formatTime(new Date('2026-01-05T08:05:00').getTime())).toBe('2026-01-05 08:05');
  });
});

describe('calcDiscount 折扣计算', () => {
  test('正常折扣', () => {
    expect(calcDiscount(8500, 10000)).toBe('8.5折');
  });
  test('原价低于等于现价返回 null', () => {
    expect(calcDiscount(100, 100)).toBeNull();
    expect(calcDiscount(200, 100)).toBeNull();
  });
  test('零值输入返回 null', () => {
    expect(calcDiscount(0, 0)).toBeNull();
  });
});

// mock 用法示例：mock wx API
jest.mock('wx', () => ({
  getStorageSync: jest.fn(() => 'mock-token'),
  showToast: jest.fn()
}), { virtual: true });

test('mock 函数断言', () => {
  const fn = jest.fn();
  fn(1);
  fn(2);
  expect(fn).toHaveBeenCalledTimes(2);
  expect(fn).toHaveBeenCalledWith(1);
});
```

```text
Jest 关键概念速记：
1. 配置 —— jest.config.js 设置 testEnvironment（node/jsdom）、testMatch、覆盖率收集范围
2. 断言 —— expect + matcher：toBe/toEqual/toContain/toThrow/toHaveBeenCalled
3. mock —— jest.fn() 替身、jest.mock() 替换模块（wx API 用 virtual mock）、jest.spyOn() 监听
4. 组织 —— describe 分组、beforeEach/afterEach 清理、test.each 参数化批量用例
5. 运行 —— npx jest 跑全部；--watch 监听变更；--coverage 出覆盖率报告
6. 转译 —— ES 语法靠 babel-jest，组件里的 ES module 与模板字符串需转译
```

## 组件单元测试

组件单元测试的目标是验证组件的行为：properties 变化后 data 是否正确更新、用户交互后是否触发预期事件、observers 是否在依赖变化时执行、生命周期钩子是否按序调用。用 miniprogram-simulate 加载组件后，测试流程通常是：设置 properties（或 setData）-> 触发事件 -> 断言 data 变化与渲染文本 -> 断言 triggerEvent 抛出的自定义事件。组件测试中最容易出问题的是 wx API 的 mock：组件内部调用 wx.getStorageSync、wx.showToast 等必须在测试前 mock 掉，否则会报 `wx is not defined`。

事件触发是组件测试的核心动作：`comp.querySelector('.btn').dispatchEvent('tap')` 模拟点击，组件 methods 里绑定的处理函数被执行；如果处理函数内部调用 `this.triggerEvent('change', data)`，可以在渲染后的实例上用 `comp.eventListeners` 或在加载前注册监听来断言。对于 setData，simulate 会同步更新 data 与视图层，因此断言紧随其后即可。组件间的父子关系也可以测试：用 simulate 渲染父组件，子组件会被真实加载，从而验证父子通信链路。

```javascript
// components/counter/index.js —— 一个带事件抛出的简单计数器组件
Component({
  properties: {
    min: { type: Number, value: 0 },
    max: { type: Number, value: 99 }
  },
  data: { count: 0 },
  methods: {
    add() {
      if (this.data.count >= this.properties.max) {
        this.triggerEvent('limit', { max: this.properties.max });
        return;
      }
      this.setData({ count: this.data.count + 1 });
      this.triggerEvent('change', { count: this.data.count });
    },
    minus() {
      if (this.data.count <= this.properties.min) return;
      this.setData({ count: this.data.count - 1 });
      this.triggerEvent('change', { count: this.data.count });
    }
  }
});
```

```javascript
// tests/counter.test.js —— 完整的组件行为测试
const simulate = require('miniprogram-simulate');
const path = require('path');

// 全局 mock wx API（组件内若有调用）
global.wx = {
  showToast: jest.fn(),
  vibrateShort: jest.fn()
};

const counterId = simulate.load(path.join(__dirname, '../components/counter/index'));

describe('计数器组件', () => {
  let comp;

  beforeEach(() => {
    comp = simulate.render(counterId);   // 每个用例重新渲染，隔离状态
    jest.clearAllMocks();
  });

  test('初始渲染 count 为 0', () => {
    const text = comp.querySelector('.count').textContent;
    expect(text).toBe('0');
  });

  test('点击加号 count 加一并抛出 change 事件', () => {
    const changeHandler = jest.fn();
    comp.addEventListener('change', changeHandler);   // 监听组件自定义事件
    comp.querySelector('.btn-add').dispatchEvent('tap');
    expect(comp.data.count).toBe(1);
    expect(comp.querySelector('.count').textContent).toBe('1');
    expect(changeHandler).toHaveBeenCalledWith({ count: 1 });
  });

  test('达到 max 后触发 limit 事件且 count 不变', () => {
    comp.setData({ count: 98 });
    const limitHandler = jest.fn();
    comp.addEventListener('limit', limitHandler);
    comp.querySelector('.btn-add').dispatchEvent('tap');
    comp.querySelector('.btn-add').dispatchEvent('tap');
    expect(comp.data.count).toBe(99);
    expect(limitHandler).toHaveBeenCalledWith({ max: 99 });
  });

  test('点击减号不小于 min', () => {
    comp.querySelector('.btn-minus').dispatchEvent('tap');
    expect(comp.data.count).toBe(0);   // min 为 0，不能再减
  });
});
```

```text
组件单元测试标准流程：
1. 加载 —— simulate.load 组件目录，得到组件 id；mock 掉组件依赖的 wx API
2. 渲染 —— simulate.render 生成实例，beforeEach 里重建实例保证用例隔离
3. 设值 —— setData 或修改 properties 驱动 observers，模拟外部数据变化
4. 触发 —— querySelector 找节点 + dispatchEvent 触发 tap/input 等事件
5. 断言 —— 断 data 变化、渲染文本、triggerEvent 抛出的自定义事件（addEventListener 监听）
6. 边界 —— 覆盖 max/min 上下限、空数据、异常输入，验证 limit 等兜底事件
```

## 工具函数测试

工具函数（utils）是小程序项目里最值得优先单测的部分：时间格式化、金额转换、防抖节流、数据清洗、正则校验等纯函数，输入输出确定、无副作用，测试成本极低而收益极高。纯函数测试的核心是「输入 -> 期望输出」的对照表：把业务上定义的规则（如金额分转元、手机号校验、状态码映射）直接翻译成用例，规则变更时改用例即可，规则是否正确的判定也一目了然。

工具函数里常见的小程序特有问题：调用 wx API 的工具（如封装 wx.getStorageSync 的 storage 模块、封装 wx.request 的请求模块）不再是纯函数，测试时需要 mock wx 或 mock 依赖模块。推荐的边界：纯计算逻辑抽成纯函数放 utils（可测），与 wx 交互的逻辑薄薄包一层（mock 掉 wx 后测交互行为）。这样可以保持大部分代码可测，测试也不依赖真实环境。

```javascript
// utils/storage.js —— 封装 wx 存储 API（被测对象，需 mock wx）
function getToken() {
  return wx.getStorageSync('token') || '';
}

function setToken(token) {
  wx.setStorageSync('token', token);
}

function clearToken() {
  wx.removeStorageSync('token');
}

module.exports = { getToken, setToken, clearToken };
```

```javascript
// tests/storage.test.js —— mock wx 后的工具函数测试
jest.mock('wx', () => {
  const store = {};
  return {
    getStorageSync: jest.fn((key) => store[key]),
    setStorageSync: jest.fn((key, value) => { store[key] = value; }),
    removeStorageSync: jest.fn((key) => { delete store[key]; })
  };
}, { virtual: true });

const storage = require('../utils/storage');
const wx = require('wx');

describe('storage 工具（mock wx API）', () => {
  test('setToken 后 getToken 能取回', () => {
    storage.setToken('abc123');
    expect(storage.getToken()).toBe('abc123');
  });

  test('未设置时 getToken 返回空字符串', () => {
    storage.clearToken();
    expect(storage.getToken()).toBe('');
  });

  test('setToken 调用了 wx.setStorageSync', () => {
    storage.setToken('xyz');
    expect(wx.setStorageSync).toHaveBeenCalledWith('token', 'xyz');
  });
});
```

```javascript
// tests/format-param.test.js —— 参数化批量用例（test.each）
const { calcDiscount } = require('../utils/format');

// 一个表格覆盖全部规则分支
test.each([
  [8500, 10000, '8.5折'],
  [10000, 10000, null],        // 不打折
  [12000, 10000, null],        // 现价高于原价，异常数据
  [0, 100, null],              // 现价为 0
  [9999, 10000, '10折']        // 四舍五入到 10 折的边界
])('calcDiscount(%i, %i) -> %s', (price, original, expected) => {

});
```

```text
工具函数测试建议：
1. 优先测纯函数 —— 无副作用、输入输出确定，一表多用例（test.each）批量覆盖
2. 规则即用例 —— 业务规则（分转元、校验、状态映射）直接翻译成输入输出对照表
3. mock wx —— 涉及 wx API 的工具用 jest.mock('wx', ..., { virtual: true }) 替换
4. 分层设计 —— 纯计算逻辑放 utils，wx 交互薄封装，保持大多数代码可测
5. 边界必测 —— 0、空字符串、null、负数、超长字符串、精度边界
6. 异常路径 —— 输入非法时函数的兜底行为（返回 null/抛错/默认值）也要断言
```

## 覆盖率

覆盖率（Coverage）度量测试对代码的执行覆盖程度，Jest 内置 Istanbul 统计，运行 `npx jest --coverage` 即生成报告。四个常用指标：行覆盖率（Lines，被执行行数占比）、语句覆盖率（Statements）、分支覆盖率（Branches，if/switch 各分支是否都执行）、函数覆盖率（Functions，函数是否都被调用）。报告会列出每个文件的三项指标，未覆盖行会标红，直接指出「哪段代码从没被测过」——这是补测的最直接依据。

覆盖率数字本身不是目标，它的价值在于趋势与定位：新代码合入时覆盖率下降，说明新增逻辑没测；某文件覆盖率长期低于 50%，说明该模块是缺陷高发区。团队可以设定门槛（如新代码行覆盖率不低于 80%、核心模块不低于 85%），在 CI 上强制校验，低于阈值构建失败。但要警惕覆盖率虚高：只断言了「不报错」而没断言「结果正确」的用例，同样能推高覆盖率。所以覆盖率要与断言质量配合看——检查报告里有没有「跑过但没断言」的测试。

```bash
# 运行并输出覆盖率报告
npx jest --coverage

# 输出示例（text 报告摘要）
# ----------|---------|----------|---------|---------|-------------------
# File      | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s
# ----------|---------|----------|---------|---------|-------------------
# utils/format.js | 100 | 80 | 100 | 100 | 12
# components/counter/index.js | 92.3 | 87.5 | 100 | 91.6 | 24,31
```

```javascript
// jest.config.js 中的覆盖率门槛配置（低于阈值 CI 失败）
module.exports = {
  // ...其他配置
  coverageThreshold: {
    global: {
      statements: 75,
      branches: 70,
      functions: 80,
      lines: 75
    },
    'utils/**/*.js': {           // 核心工具模块要求更高
      statements: 90,
      lines: 90
    }
  }
};
```

```javascript
test('formatTime 收到非法时间戳时返回空字符串兜底', () => {
```

```text
覆盖率实践要点：
1. 指标 —— Lines/Branches/Functions/Statements 四个维度，分支覆盖率最能暴露漏测
2. 报告 —— text 终端摘要 + lcov 生成 html 网页版，红行即未覆盖代码
3. 门槛 —— coverageThreshold 设全局与核心模块阈值，CI 低于阈值构建失败
4. 趋势 —— 关注覆盖率随版本的升降，新代码合入导致下降说明没补测
5. 警惕虚高 —— 只跑不断言的用例会推高覆盖率，报告要与断言质量配合看
6. 定位缺陷 —— 长期低覆盖率的文件是缺陷高发区，优先补测与重构
```

## 应用场景实战

### 场景一：为电商小程序的「购物车组件」编写完整单元测试

购物车组件依赖商品数据、数量上限、选中状态，逻辑分支多，是单元测试的典型目标。完整流程：

```javascript
// components/cart-item/index.js —— 购物车单项组件（节选逻辑）
Component({
  properties: {
    item: { type: Object, value: null }   // { id, name, price(分), count, checked }
  },
  data: {
    displayPrice: '0.00',
    countText: '1'
  },
  observers: {
    item(item) {
      if (!item) return;
      this.setData({
        displayPrice: (item.price / 100).toFixed(2),
        countText: String(item.count)
      });
    }
  },
  methods: {
    toggleCheck() {
      this.triggerEvent('toggle', { id: this.properties.item.id });
    },
    changeCount(delta) {
      const next = this.properties.item.count + delta;
      if (next < 1 || next > 99) {
        this.triggerEvent('limit', { id: this.properties.item.id, count: this.properties.item.count });
        return;
      }
      this.triggerEvent('change', { id: this.properties.item.id, count: next });
    }
  }
});
```

### 场景二：用覆盖率报告驱动补测，把核心模块覆盖率从 60% 提升到 90%

工具函数与核心组件是业务的地基，覆盖率必须拉高。操作流程：

```text
补测流程：
1. 跑 npx jest --coverage，打开 lcov-report/index.html，找出低于 70% 的文件
2. 分析未覆盖行：utils/cart.js 的「优惠券金额封顶」分支没测、coupon 为空的分支没测
3. 针对未覆盖分支补用例：满减封顶（满 300 减 50 但订单 200 时按 200 算）、无优惠券场景
4. 重跑覆盖率，确认 Branches 指标提升；对仍低于门槛的行继续补
5. 在 jest.config.js 加上 coverageThreshold，把 utils/** 的门槛定为 lines 90 / branches 85
6. 接入 CI：npm test -- --coverage 作为提交流水线的一环，低于门槛构建失败
```

```javascript
// utils/cart.js —— 待补测的购物车计算函数（节选）
function calcCouponDiscount(orderAmount, coupon) {
  if (!coupon) return 0;                       // 分支 A：无优惠券
  if (orderAmount < coupon.threshold) return 0; // 分支 B：未达门槛
  const discount = Math.min(coupon.value, orderAmount); // 分支 C：封顶处理
  return discount;
}

module.exports = { calcCouponDiscount };
```

```javascript
// tests/cart.test.js —— 针对未覆盖分支补的用例
const { calcCouponDiscount } = require('../utils/cart');

test.each([
  [200, null, 0, '无优惠券'],
  [100, { threshold: 300, value: 50 }, 0, '未达门槛'],
  [350, { threshold: 300, value: 50 }, 50, '正常满减'],
  [200, { threshold: 300, value: 250 }, 200, '优惠金额超过订单金额，封顶']
])('calcCouponDiscount(%i, %j) -> %i (%s)', (amount, coupon, expected) => {
  expect(calcCouponDiscount(amount, coupon)).toBe(expected);
});
```

```text
场景二执行结果说明：
1. 4 个用例覆盖 3 个分支 + 封顶边界，分支覆盖率从 0 提升到 100
2. 覆盖率报告从「不知道缺什么」变成「明确列出未覆盖行号」
3. 门槛接入 CI 后，后续任何人新增逻辑忘记补测，构建会直接失败
4. 真实项目里覆盖率提升是渐进过程：先核心模块，再扩展，避免为数字而测
```

## 最佳实践与踩坑记录

### 最佳实践

1. 从纯函数开始建测试：utils 模块的格式化、校验、计算逻辑先测，成本最低、收益最稳，形成测试习惯后再覆盖组件
2. 组件测试统一套路：simulate.load -> render -> setData -> dispatchEvent -> 断言 data/文本/自定义事件，beforeEach 重建实例保证隔离
3. 全局 mock wx API 一次搞定：测试 setup 文件里用 jest.mock('wx', ..., { virtual: true }) 提供 getStorageSync/showToast 等常用替身
4. 边界值必测：max/min 上下限、空值、null、0、精度边界，这些分支正是覆盖率报告里的红行
5. 用 test.each 参数化批量用例：一张表格覆盖同一函数的所有规则分支，用例可读性强、维护成本低
6. 覆盖率设门槛但不设虚高目标：核心模块 90% 行覆盖，CI 强制校验，非核心模块 70% 即可
7. 测试与重构同行：重构后跑全量测试验证行为不变，敢于删代码、改结构
8. 测试文件与被测模块同构放置：tests/ 目录按 utils/、components/ 分组，路径清晰

### 踩坑记录

坑 1：组件测试报 wx is not defined
结论：simulate 渲染组件时组件内部调用 wx.getStorageSync 直接抛错，测试全红。
原因：miniprogram-simulate 只模拟组件渲染，不提供 wx 全局对象，组件里用 wx API 需要自己 mock。
解法：测试 setup 文件（jest setupFiles）里定义 global.wx 替身，或 jest.mock('wx', ..., { virtual: true })；组件层尽量少直接调 wx，抽成可 mock 的模块。

坑 2：component is not a function / 组件加载失败
结论：simulate.load 传入路径后报错，组件加载不出来。
原因：simulate.load 需要传入组件目录的绝对路径，且目录下必须同时存在 index.js、index.wxml、index.json；路径写错或文件名不符都会失败。
解法：用 path.join(__dirname, '../components/xxx/index') 拼绝对路径，确认组件目录三件套齐全（json 里必须有 component: true）。

坑 3：observer 不触发，断言 data 失败
结论：测试里改 properties 后 data 没更新，断言文本失败。
原因：simulate 对 observers 的触发依赖 setData 而非直接改 properties；另外 observers 里 setData 的数据要在断言前已同步。
解法：用 comp.setData({...}) 驱动观察者；若组件用 observers 监听 properties，测试里通过 setData 修改同名字段触发；必要时在断言前 await 一个 tick 或直接断言 comp.data。

坑 4：mock 不生效，测试还是走了真实 wx.request
结论：工具函数测试里 mock 了 request 模块，但用例仍发出真实网络请求，CI 环境直接超时。
原因：jest.mock 的模块路径与 require 的路径不一致（大小写、相对路径差异），或 mock 写在用例内部导致提升（hoisting）顺序问题。
解法：jest.mock 写在文件顶部；模块路径与业务代码完全一致（用路径别名映射 moduleNameMapper 统一）；request 封装里预留注入点（如 USE_MOCK 开关）双保险。

坑 5：覆盖率虚高但缺陷照出
结论：覆盖率报告 95%，上线还是出 bug，团队质疑测试价值。
原因：很多用例只断言「不报错」或只跑了流程没断言结果，Istanbul 统计的是执行而非验证。
解法：审查断言质量，每个用例必须有明确的期望断言；覆盖率门槛配合「关键分支必须有断言」的评审要求；用变异测试思路抽查断言有效性。

坑 6：测试之间互相污染，单个跑通过、全量跑失败
结论：npx jest 全量跑随机失败，单独跑某文件却通过。
原因：用例共享了模块级状态（如 mock 的 wx store、组件实例的全局缓存），或 beforeEach 没有重建实例。
解法：每个用例用 simulate.render 新建实例；jest.config.js 开 clearMocks: true；涉及共享状态的模块在 beforeEach/afterEach 里显式重置；避免测试文件间共享可变全局。

坑 7：组件升级后旧测试失效，没人维护
结论：组件加了个新 property，旧测试全挂，团队直接删掉测试文件。
原因：测试与组件强耦合，组件 API 变更没有同步更新测试，测试成了负担。
解法：组件 API 变更同步改测试，把「改组件必须改测试」写进代码评审 checklist；测试断言公共行为而非内部实现细节，减少脆弱耦合。
