## 概述

单元测试验证的是「单个函数对不对」，集成测试与自动化验证的是「整条链路通不通」。小程序的集成测试包含两个层面：一是模块间的集成（页面与组件、逻辑层与视图层、小程序与后台接口），二是端到端自动化——用官方 SDK 驱动真实小程序模拟用户操作，跑通登录、下单、支付这类完整业务流程。本章重点讲解 miniprogram-automator 的接入与使用、E2E 场景的编写规范、以及如何把自动化测试接入持续集成（CI）流水线，让每次提交都能自动验证主链路。

集成测试的定位是「承上启下」：向上承接单元测试验证过的模块，向下为真机与发布验证铺路。它解决的核心问题是「拼起来之后是否仍然正确」——单元测试全绿但接口字段对不上、页面跳转参数传错、登录态在页面间丢失，这些集成层缺陷只有链路级测试才能发现。自动化程度决定效率：手工回归一次主链路要 20 分钟，自动化后每次提交几分钟跑完，释放的人力用于探索性测试。

```text
集成测试与自动化的价值：
1. 链路验证 —— 登录-浏览-加购-下单-支付全流程，验证模块拼装后的正确性
2. 快速回归 —— 每次提交自动跑主链路，几分钟内发现破坏性变更
3. 真实环境 —— 连接开发者工具驱动真实小程序，比模拟器更接近用户行为
4. 接口联动 —— 小程序与 SpringBoot 后台的真实联调，字段与状态机一起验证
5. 版本守门 —— CI 接入后，主链路失败阻止合入与提审，质量门槛前移
6. 数据闭环 —— 测试数据准备与清理自动化，用例可重复执行
```

## miniprogram-automator 自动化 SDK

miniprogram-automator 是微信官方提供的小程序自动化测试 SDK（npm 包 `miniprogram-automator`），它通过 WebSocket 连接微信开发者工具（需开启「服务端口」），远程驱动开发者工具里运行的小程序：打开页面、执行 JS、查询节点、点击输入、截图断言。与 miniprogram-simulate 不同，automator 驱动的是「真实运行的小程序」，能拿到真实的页面栈、节点树与渲染结果，因此更适合 E2E 场景。

接入步骤：第一步安装依赖；第二步在开发者工具「设置 - 安全设置」里开启服务端口（默认 9420）；第三步写脚本用 `automator.launch({ projectPath, cliPath })` 启动工具并加载项目——cliPath 指向开发者工具安装目录下的 CLI 可执行文件（macOS 为 `/Applications/wechatwebdevtools.app/Contents/MacOS/cli`，Windows 为 `C:\Program Files (x86)\Tencent\微信web开发者工具\cli.bat`）。launch 成功后得到 miniProgram 实例，通过 `miniProgram.reLaunch('/pages/index/index')` 打开页面，`miniProgram.page()` 获取当前页面，`page.$(selector)` 查询节点，节点上调用 `.tap()`、`.input()`、`.scroll()` 模拟操作。

```bash
# 安装自动化 SDK
npm install --save-dev miniprogram-automator
```

```javascript
// e2e/launch.js —— 连接开发者工具并打开项目（公共启动模块）
const automator = require('miniprogram-automator');

async function launchApp() {
  const miniProgram = await automator.launch({
    projectPath: '/path/to/your/miniprogram',   // 项目绝对路径
    cliPath: '/Applications/wechatwebdevtools.app/Contents/MacOS/cli'
    // Windows 示例：
    // cliPath: 'C:\\Program Files (x86)\\Tencent\\微信web开发者工具\\cli.bat'
  });

  // 打开目标页面（每次用例从首页或指定页开始，保证状态干净）
  await miniProgram.reLaunch('/pages/index/index');
  await miniProgram.waitFor(500);   // 等待首屏渲染
  return miniProgram;
}

async function closeApp(miniProgram) {
  await miniProgram.close();   // 关闭连接
}

module.exports = { launchApp, closeApp };
```

```javascript
})().catch((e) => { console.error('E2E 失败:', e.message); process.exit(1); });
```

## E2E 测试场景

E2E（End-to-End）测试模拟真实用户的完整操作路径。小程序 E2E 的经典场景是「登录 -> 浏览商品 -> 加入购物车 -> 结算 -> 支付 -> 查看订单」这条核心交易链路，它串联了页面跳转、本地存储、网络请求、后台状态机（订单状态流转）与微信支付调起，任何一环断裂都会让用例失败。E2E 用例的编写原则：只覆盖核心业务链路（数量控制在 20 条以内）、每个用例独立初始化数据、断言业务结果而非中间细节、失败时输出截图与页面快照便于定位。

支付环节的 E2E 有特殊性：真实微信支付需要收银台交互，自动化无法完成。实践中的做法是「半模拟支付」：后端提供测试模式（测试商户号 + mock 支付回调），小程序端支付按钮调起支付后，测试脚本在回调层面验证订单状态变化，或通过后台测试接口直接模拟支付成功回调，断言订单从「待支付」变为「已支付」。登录环节同样需要测试账号体系：准备若干固定测试账号（手机号 + 验证码由测试环境后台直接签发），避免依赖真实短信。

```javascript
// e2e/order-flow.js —— 登录-下单-支付核心链路 E2E
const { launchApp, closeApp } = require('./launch');

async function run() {
  const miniProgram = await launchApp();
  try {
    // 1. 登录：输入测试账号手机号，测试环境验证码固定为 123456
    let page = await miniProgram.currentPage();
    await page.$('.input-phone').input('13800138000');
    await page.$('.btn-get-code').tap();
    await miniProgram.waitFor(800);
    await page.$('.input-code').input('123456');
    await page.$('.btn-login').tap();
    await miniProgram.waitFor(1500);

    // 2. 断言登录成功：跳转首页，本地有 token
    page = await miniProgram.currentPage();
    if (page.path !== 'pages/index/index') throw new Error('登录后未跳转首页');
    const token = await miniProgram.evaluate(() => wx.getStorageSync('token'));
    if (!token) throw new Error('登录后未写入 token');

    // 3. 浏览商品：从首页进入商品详情
    await page.$('.goods-item').tap();          // 点击第一个商品
    await miniProgram.waitFor(1000);
    page = await miniProgram.currentPage();
    if (page.path !== 'pages/goods/detail/index') throw new Error('未进入商品详情');

    // 4. 加购并去结算
    await page.$('.btn-add-cart').tap();
    await miniProgram.waitFor(500);
    await page.$('.btn-buy-now').tap();
    await miniProgram.waitFor(1000);

    // 5. 提交订单（测试环境订单金额固定，便于断言）
    page = await miniProgram.currentPage();
    await page.$('.btn-submit-order').tap();
    await miniProgram.waitFor(1500);

    // 6. 半模拟支付：测试环境点击支付后调用后台 mock 回调
    page = await miniProgram.currentPage();
    await page.$('.btn-pay').tap();
    await miniProgram.waitFor(2000);

    // 7. 断言订单状态：跳转订单详情且状态为已支付
    page = await miniProgram.currentPage();
    const statusText = await page.$('.order-status').text();
    if (!statusText.includes('已支付')) throw new Error(`订单状态异常: ${statusText}`);
    console.log('核心交易链路 E2E PASS');
  } finally {
    await closeApp(miniProgram);
  }
}

run().catch((e) => { console.error('E2E 失败:', e.message); process.exit(1); });
```

```javascript
// 每个用例执行前：清理该测试账号的历史订单，保证用例可重复

}

```

```text
E2E 场景编写规范：
1. 覆盖范围 —— 只覆盖核心链路（登录/交易/支付/消息），数量控制在 20 条以内
2. 用例隔离 —— 每条用例独立重置测试数据，同一用例跑 N 次结果一致
3. 断言业务结果 —— 断订单状态、跳转页面、存储内容，不断渲染细节
4. 失败定位 —— 失败时输出页面截图、当前页面栈、关键节点状态
5. 支付策略 —— 半模拟支付：后台测试接口模拟支付回调，断订单状态流转
6. 账号体系 —— 固定测试账号 + 测试环境验证码，不依赖真实短信
```

## 持续集成

持续集成（CI）把自动化测试接入流水线：每次代码提交（push / pull request）自动执行构建、静态检查、单元测试、E2E 测试，任何一环失败都阻止代码合入。小程序 CI 的典型流水线：lint（ESLint）-> 单元测试（Jest）-> 构建校验（`miniprogram-ci` 上传前校验）-> E2E（miniprogram-automator 连接开发者工具）-> 测试报告归档。E2E 环节是流水线中最特殊的一步，因为它依赖开发者工具的图形界面环境，常见的执行方案是「自建 Jenkins + 安装了开发者工具的 Linux/Windows 机器」或「GitHub Actions + macOS runner（开发者工具有 macOS 版）」。

miniprogram-ci 是微信官方提供的代码上传/预览 CI 工具（npm 包 `miniprogram-ci`），支持在无图形界面环境下上传代码、生成预览二维码、执行代码质量检查。它与 miniprogram-automator 的分工：automator 负责「跑测试」，miniprogram-ci 负责「传代码、做构建校验」。实践中 miniprogram-ci 通常作为流水线的构建与产物环节，automator 的 E2E 作为测试环节，两者配合完成「提交 -> 测试 -> 上传体验版」的自动化闭环。测试报告方面，Jest 输出 JUnit XML（jest-junit 插件）供 Jenkins/GitHub Actions 解析，覆盖率报告（lcov）归档为构建产物。

```yaml
# .github/workflows/ci.yml —— GitHub Actions 流水线示例
name: MiniProgram CI

on:
  push:
    branches: [main, develop]
  pull_request:

jobs:
  unit-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 18 }
      - run: npm ci
      - run: npx eslint .                    # 静态检查
      - run: npx jest --coverage --ci        # 单元测试 + 覆盖率
      - uses: actions/upload-artifact@v4     # 归档覆盖率报告
        with:
          name: coverage-report
          path: coverage/lcov-report/

  e2e-test:
    runs-on: macos-latest                     # 需要微信开发者工具（macOS 版）
    needs: unit-test
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - name: Install WeChat DevTools
        run: |
          # 下载并安装开发者工具（稳定版 CLI 安装包）
          curl -L -o devtools.dmg "https://servicewechat.com/wxa-dev-logic/download_redirect?type=darwin&from=mpwiki"
          hdiutil attach devtools.dmg
          cp -R "/Volumes/微信web开发者工具/微信web开发者工具.app" /Applications/
      - name: Enable service port
        run: /Applications/wechatwebdevtools.app/Contents/MacOS/cli --auto-port 9420
      - name: Run E2E
        run: node e2e/run-all.js            # 跑全部 E2E 用例
        env:
          TEST_BASE_URL: https://test-api.example.com
```

```javascript
// e2e/run-all.js —— 统一入口：串行跑所有用例，输出汇总
const { execSync } = require('child_process');
const fs = require('fs');

const cases = ['order-flow.js', 'login.js', 'message-subscribe.js'];
const results = [];

(async () => {
  for (const c of cases) {
    try {
      execSync(`node e2e/${c}`, { stdio: 'inherit' });
      results.push({ case: c, pass: true });
    } catch (e) {
      results.push({ case: c, pass: false });
    }
  }
  const failed = results.filter((r) => !r.pass);
  console.log(`\nE2E 汇总: ${results.length - failed.length}/${results.length} 通过`);
  if (failed.length > 0) {
    console.log('失败用例:', failed.map((f) => f.case).join(', '));
    process.exit(1);   // 失败则 CI 构建失败
  }
})();
```

```text
6. 定时回归 —— 主链路 E2E 可加定时任务（每日凌晨），弥补提交时漏跑
```

## 自动化实践

自动化实践解决的是「测试写好了怎么长期跑得稳」的问题。首先是分层策略：单元测试每次提交全量跑（快）；E2E 主链路在 PR 与合并时跑（中等）；完整回归（含定时任务）每天跑。其次是稳定性工程：E2E 用例最容易因环境波动误报——网络慢导致 waitFor 超时、测试数据被其他用例污染、开发者工具偶发卡死，常见对策是增加等待策略（轮询而非固定 sleep）、用例间数据隔离、失败自动重试（重试 1-2 次并记录）、失败时截图留证。再次是数据策略：测试环境提供 reset 接口，用例开始前重置账号与订单数据，用例结束后清理，保证可重复执行。

自动化实践还包括与开发者协作流程的整合：把「跑 E2E」挂在 PR 检查上，主链路挂了 PR 合不进去，质量问题在合入前暴露；把 E2E 从「测试人员的负担」变成「开发的默认动作」，开发提交前本地跑一遍受影响链路的用例。量化的角度，自动化实践可以用三个指标评估健康度：E2E 通过率（目标 95%+）、平均执行时长（目标 10 分钟内）、单测覆盖率趋势（核心模块稳定在 90%）。指标异常时优先处理「最脆」的用例——频繁误报的用例要么修稳，要么降级为手动，避免团队对红灯麻木。

```javascript
// e2e/utils/wait.js —— 稳定的等待策略：轮询替代固定 sleep
async function waitForText(miniProgram, selector, expectedText, timeout = 10000) {
  const start = Date.now();
  while (Date.now() - start < timeout) {
    const node = await miniProgram.currentPage().then((p) => p.$(selector)).catch(() => null);
    if (node) {
      const text = await node.text().catch(() => '');
      if (text && text.includes(expectedText)) return true;
    }
    await new Promise((r) => setTimeout(r, 500));   // 每 500ms 轮询一次
  }
  throw new Error(`等待超时: ${selector} 未出现文本 ${expectedText}`);
}

// e2e/retry.js —— 失败自动重试包装
async function withRetry(fn, retries = 2) {
  let lastErr;
  for (let i = 0; i <= retries; i++) {
    try {
      return await fn();
    } catch (e) {
      lastErr = e;
      console.warn(`第 ${i + 1} 次执行失败: ${e.message}，准备重试`);
      await new Promise((r) => setTimeout(r, 2000));
    }
  }
  throw lastErr;
}

module.exports = { waitForText, withRetry };
```

```text
自动化实践健康度清单：
1. 分层跑 —— 单测每次提交；E2E 主链路 PR 与合并时跑；完整回归每日定时
2. 等待策略 —— 用轮询 waitForText 替代固定 sleep，网络抖动不再误报
3. 失败重试 —— 环境类失败自动重试 2 次，重试仍失败才算真实失败
4. 数据隔离 —— 用例前置 reset 接口重置数据，用例间互不依赖
5. 失败留证 —— 失败时保存页面截图、页面栈、控制台日志，便于定位
6. 指标监控 —— E2E 通过率 95%+、平均时长 10 分钟内、核心覆盖率稳定
7. 红灯治理 —— 频繁误报的用例修稳或降级，避免团队对失败麻木
```

## 应用场景实战

### 场景一：为「登录 + 订阅消息授权」链路编写 E2E 用例

订阅消息是营销触达的关键能力，授权链路（点击按钮 -> 弹窗 -> 允许 -> 后端入库）值得自动化保护：

```javascript
// e2e/subscribe-flow.js —— 登录 + 订阅消息授权 E2E
const { launchApp, closeApp } = require('./launch');
const { prepareTestUser } = require('./helpers/cleanup');
const { waitForText } = require('./utils/wait');

async function run() {
  await prepareTestUser('13800138000');
  const miniProgram = await launchApp();
  try {
    // 登录
    let page = await miniProgram.currentPage();
    await page.$('.input-phone').input('13800138000');
    await page.$('.btn-get-code').tap();
    await miniProgram.waitFor(800);
    await page.$('.input-code').input('123456');
    await page.$('.btn-login').tap();
    await waitForText(miniProgram, '.page-title', '首页');

    // 进入订阅消息授权页
    page = await miniProgram.currentPage();
    await page.$('.btn-subscribe').tap();
    await miniProgram.waitFor(1500);

    // 微信订阅消息弹窗由系统渲染，automator 可通过 evaluate 模拟允许授权
    const granted = await miniProgram.evaluate(() => {
      return new Promise((resolve) => {
        wx.requestSubscribeMessage({
          tmplIds: ['TMPL_ID_XXX'],
          success: (res) => resolve(res['TMPL_ID_XXX'] === 'accept'),
          fail: () => resolve(false)
        });
      });
    });
    if (!granted) throw new Error('订阅消息授权未通过');

    // 断言后端记录（测试环境后台接口查询授权状态）
    const resp = await miniProgram.evaluate(() => {
      return new Promise((resolve) => {
        wx.request({
          url: 'https://test-api.example.com/api/user/subscribe-status',
          success: (r) => resolve(r.data)
        });
      });
    });
    if (!resp.data.subscribed) throw new Error('后端未记录订阅授权');
    console.log('订阅消息链路 E2E PASS');
  } finally {
    await closeApp(miniProgram);
  }
}

run().catch((e) => { console.error('E2E 失败:', e.message); process.exit(1); });
```

```text
场景一要点：
1. 订阅消息弹窗是系统 UI，自动化无法直接点击，用 evaluate 模拟授权回调
2. 断言落到后端：授权状态必须入库，前端 accept 不算闭环
3. 测试账号数据前置重置，重复执行结果一致
4. 该用例防止「模板消息改动导致授权链路失效」类回归
```

### 场景二：搭建 Jenkins 流水线，把 E2E 接到每次合并前

团队自建 GitLab + Jenkins，目标：合并到 develop 分支前自动跑 lint、单测、E2E 主链路：

```groovy
// Jenkinsfile —— 小程序自动化流水线
pipeline {

    TEST_BASE_URL = 'https://test-api.example.com'

      steps { checkout scm }

    stage('Install') {
      steps { sh 'npm ci' }
    }

      }
    }

    }
  }
}
```

## 最佳实践与踩坑记录

### 最佳实践

1. E2E 数量克制：只覆盖核心业务链路（登录、交易、支付、消息），20 条以内，其余细节下沉到单元测试与集成测试
2. 用轮询等待替代固定 sleep：waitForText 每 500ms 查一次节点状态，网络抖动不误报，执行时长还更短
3. 每个 E2E 用例前置重置测试数据，用例间完全隔离，保证可重复执行与并行安全
4. 断言业务结果不断言渲染细节：断订单状态、跳转路径、存储内容，组件样式变化不破坏用例
5. 支付用半模拟策略：后台测试接口模拟支付回调，断订单状态流转，避免依赖真实收银台
6. CI 分层执行：单测每次提交、E2E 在 PR 与合并时、完整回归每日定时，反馈速度与成本平衡
7. 失败留证三件套：页面截图、当前页面栈、控制台日志，失败用例可独立定位
8. 红灯治理常态化：频繁误报的用例修稳或降级手动，用通过率指标（95%+）守护自动化可信度

### 踩坑记录

坑 1：automator.launch 报 cliPath 不存在 / 连接超时
结论：E2E 脚本启动失败，提示找不到 cli 或 WebSocket 连接超时。
原因：cliPath 路径写错，或开发者工具未开启「服务端口」，或工具未登录。
解法：核对开发者工具安装路径下的 cli 可执行文件（macOS 在 .app/Contents/MacOS/cli）；在工具「设置-安全设置」勾选服务端口（默认 9420）；CI 机器上先手动登录一次开发者工具保持登录态。

坑 2：waitFor 固定等待导致用例偶发超时
结论：E2E 有时过有时挂，重跑又过，CI 红灯率 30%。
原因：固定 sleep 无法应对网络波动，弱网环境下页面渲染慢于等待时间。
解法：用轮询等待替代固定 sleep（waitForText 带超时上限）；关键节点用自动等待 API；超时上限放宽到 10 秒并记录实际耗时。

坑 3：测试数据互相污染，用例随机失败
结论：两个用例都依赖「购物车为空」的初始状态，前一个用例跑完购物车没清空，后一个用例断言失败。
原因：用例之间共享了同一测试账号与后台数据，没有前置重置。
解法：每条用例开头调用 reset 接口重置账号数据；必要时用独立测试账号隔离；用例结束后清理订单数据。

坑 4：支付链路自动化走到真实收银台，脚本卡死
结论：E2E 点击支付按钮后进入微信收银台，自动化无法操作，用例超时。
原因：测试环境没有配置 mock 支付，直接调起了真实微信支付。
解法：测试环境后台配置测试商户号并拦截支付；或小程序端接入测试模式开关；支付成功后由后台 mock 回调驱动订单状态，脚本只断言状态流转。

坑 5：CI 上开发者工具无法启动（headless 环境）
结论：Jenkins 机器没有图形界面，开发者工具启动失败，E2E 无法执行。
原因：开发者工具是 GUI 应用，纯 headless Linux 上无法直接运行。
解法：CI 构建机安装带图形环境的系统（macOS runner / 带 Xvfb 的 Linux）；或改用云真机/自建工具集群；miniprogram-ci 负责无界面构建校验，automator 只在有界面的机器跑。

坑 6：E2E 通过但线上还是出问题，自动化被质疑
结论：主链路 E2E 全绿，上线后还是出现「老用户登录态失效」事故。
原因：E2E 只覆盖了核心 happy path，没覆盖 token 过期、版本升级、多账号切换等场景。
解法：E2E 之外补充针对性用例：token 过期后自动刷新、账号切换后数据隔离；核心链路覆盖 happy path，风险场景用「错误推测清单」指导补充用例。

坑 7：PR 上跑 E2E 太慢，开发绕过检查合入
结论：每次 PR 跑 E2E 要 25 分钟，开发等不及直接合入，流水线形同虚设。
原因：E2E 用例过多且串行执行，反馈太慢逼着开发走捷径。
解法：PR 只跑核心 5-8 条用例；完整回归放每日定时任务；并行执行用例（多项目/多工具实例）；把「PR 必须通过」做成分支保护规则，从机制上杜绝绕过。
