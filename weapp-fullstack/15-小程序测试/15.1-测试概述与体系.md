## 概述

小程序全栈项目（小程序 + SpringBoot 后台 + Vue 管理端）涉及多端联动，任何一个环节出错都会直接呈现在用户面前：接口字段对不上、支付回调丢失、版本升级后老用户白屏。测试体系的目标是在这些故障到达用户之前把它们拦截下来，并且让「拦截」这件事可持续、可度量、可自动化。本章是 15 篇章的总纲，先建立全局的测试观，再在 15.2 至 15.4 分别展开单元测试、集成测试与自动化、真机调试与性能测试的具体做法。

测试不是发布前的最后一道工序，而是贯穿整个研发流程的质量活动。对小团队而言，合理的测试投入顺序是：先把工具函数和组件逻辑的单元测试跑起来（成本最低、收益最稳），再用 miniprogram-automator 覆盖核心业务链路（登录、下单、支付），最后靠真机调试与性能面板兜住模拟器发现不了的问题（渲染、内存、真机兼容）。

```text
小程序测试体系的四个层次：
1. 单元测试 —— 对工具函数、组件逻辑做最小粒度验证，毫秒级反馈，成本最低
2. 集成测试 —— 验证模块间协作：组件与组件、小程序与后台接口、数据流走向
3. 端到端测试（E2E）—— 用自动化 SDK 驱动真实小程序，模拟用户完整操作链路
4. 手工测试 —— 真机体验、视觉走查、边界场景补测，自动化覆盖不到的兜底手段
```

## 测试分层

测试分层（Test Pyramid）是测试体系设计的核心思想：底层单元测试数量最多、运行最快、成本最低；越往上测试数量越少、运行越慢、成本越高，但覆盖的集成度也越高。小程序项目的测试金字塔自下而上分为单元测试、集成测试、端到端测试与手工测试四层。

单元测试针对最小可测单元：纯函数（时间格式化、金额计算、数据清洗）、utils 模块、组件的单个方法。它们不依赖网络与真机，在 Node 环境用 Jest + miniprogram-simulate 直接运行，毫秒级完成，适合在每次提交时全量跑。集成测试验证模块间的协作：组件触发事件后是否正确调用接口、store 状态变化后页面渲染是否符合预期、小程序请求后台接口时参数与返回结构是否匹配。端到端测试使用 miniprogram-automator 连接微信开发者工具，模拟真实用户从登录到下单支付的完整操作。手工测试则覆盖自动化难以判断的部分：视觉还原度、动画流畅度、真机上的触摸手感。

```javascript
// 测试分层在 package.json 中的落地示例（scripts 片段）
{
  "scripts": {
    "test:unit": "jest --coverage",                 // 单元测试：毫秒级，提交前必跑
    "test:integration": "jest --config jest.integration.config.js", // 集成测试：需要 Mock 后端
    "test:e2e": "node e2e/run.js",                  // E2E：需要开发者工具与测试账号
    "test:all": "npm run test:unit && npm run test:integration"
  }
}
```

```text
各测试层级的定位与投入比：
1. 单元测试 —— 数量最多（建议占比 70%），验证单个函数/组件方法，跑得最快
2. 集成测试 —— 数量居中（约 20%），验证接口联调、组件协作、数据流
3. 端到端测试 —— 数量最少（约 10%），只覆盖核心业务链路，稳定压倒一切
4. 手工测试 —— 不追求数量，聚焦视觉、动效、真机兼容、边界场景
5. 投入节奏 —— 先建单元测试习惯，再补 E2E 主链路，手工测试按版本迭代安排
6. 判定标准 —— 单元测试失败必须修；E2E 失败先排查环境；手工测试问题进缺陷池排优先级
```

选择测试层级的判断依据：如果被测对象不依赖外部环境，就下沉到单元测试；如果必须依赖接口或跨组件协作，就上移到集成测试；如果是完整用户旅程，才值得写 E2E。盲目把所有逻辑都写成 E2E 是常见反模式——E2E 慢、脆、依赖环境，跑一次要几分钟，反馈太慢反而拖垮迭代。

## 测试环境

小程序项目的环境通常划分为开发环境（dev）、测试环境（test）与预发布环境（pre/prod staging），三者共用一套代码，区别在于后台接口地址与数据。开发环境面向开发者本人，接口指向本地 SpringBoot（http://localhost:8080）；测试环境面向测试人员与自动化脚本，接口指向部署在测试服务器上的后台，数据可随意造；预发布环境与生产环境同构（同版本、同配置、同数据库结构），用于发布前最后一轮验证。

环境切换的核心手段是配置文件 + 编译条件。小程序没有传统 Web 的 process.env，需要通过 project.config.json 的编译模式、或自定义构建条件（`__wxConfig.envVersion`）区分环境。实践中更常见的做法是维护一份环境配置模块，根据 `wx.getAccountInfoSync().miniProgram.envVersion`（develop/trial/release）自动选择后台地址，同时允许开发时通过全局变量手动覆盖。

```javascript
// config/env.js —— 多环境配置模块
const envMap = {
  develop: 'http://localhost:8080',   // 开发环境：本地 SpringBoot
  trial: 'https://test-api.example.com',   // 体验版：测试环境后台
  release: 'https://api.example.com'       // 正式版：生产后台
};

function getBaseUrl() {
  // 支持开发时手动覆盖，例如在 app.js 里 wx.setStorageSync('ENV_OVERRIDE', 'test')
  const override = wx.getStorageSync('ENV_OVERRIDE');
  if (override && envMap[override]) {
    return envMap[override];
  }
  try {
    const info = wx.getAccountInfoSync();
    return envMap[info.miniProgram.envVersion] || envMap.develop;
  } catch (e) {
    return envMap.develop;
  }
}

module.exports = { getBaseUrl, envMap };
```

```javascript
// utils/request.js —— 请求封装中接入环境地址与 Mock 开关
const { getBaseUrl } = require('../config/env');

const USE_MOCK = false; // 联调期可临时置 true，走本地 Mock 数据

function request(options) {
  if (USE_MOCK) {
    // 返回本地 mock 数据，不发起真实网络请求
    return mockRequest(options);
  }
  return new Promise((resolve, reject) => {
    wx.request({
      url: getBaseUrl() + options.url,
      method: options.method || 'GET',
      data: options.data,
      header: { 'Content-Type': 'application/json' },
      success: (res) => resolve(res.data),
      fail: (err) => reject(err)
    });
  });
}

module.exports = request;
```

后端 Mock 是集成测试环境的必备设施，常见方案有三种：一是开发环境直接跑本地 SpringBoot（真实后台，数据可控）；二是用 Mock 服务（如 Mockoon、WireMock、msw）按接口契约返回假数据，适合后台尚未就绪的前后端并行开发期；三是测试环境中通过数据库种子数据（seed data）准备固定测试集，保证自动化脚本每次运行的数据一致。无论哪种方案，Mock 数据必须与真实接口的字段结构完全一致，否则会掩盖字段缺失类缺陷。

```text
测试环境管理的要点：
1. 开发环境 —— 本地后台 + 本地数据库，随时改代码重启，数据随意造
2. 测试环境 —— 部署在测试服务器，供测试人员与 CI 自动化脚本使用，数据用种子脚本初始化
3. 预发布环境 —— 与生产同构，验证发布前的最后问题：配置、权限、数据迁移
4. 环境切换 —— 基于 envVersion 自动切换 baseURL，开发期允许手动覆盖
5. 后端 Mock —— 后台未就绪时用 Mock 服务并行开发，Mock 字段结构必须与真实接口一致
6. 环境隔离 —— 各环境数据库独立，严禁测试数据写进生产库；测试环境域名需在后台配置 request 合法域名
```

## 测试计划

测试计划是测试活动的作战地图，回答三个问题：测什么（范围）、怎么测（用例与策略）、何时测（里程碑）。小程序版本的典型测试范围包括：新增功能、受影响回归点（改动模块的上下游）、微信开放能力（登录、支付、订阅消息）的联调、兼容性（基础库版本、机型）、性能（启动耗时、页面渲染）。范围的确定依赖需求文档与代码改动清单，改动涉及支付、登录、存储等核心模块时必须把回归范围扩大。

冒烟测试（Smoke Test）是每次提测后的第一道关卡：用最短的时间验证主流程是否可跑通（能启动、能登录、核心页面能打开、核心接口有响应），冒烟不过直接打回，不进入详细测试。回归测试（Regression Test）则验证「新改动没有破坏旧功能」，优先级取决于模块变更频率与业务重要性：支付、登录、下单等核心链路每次必回归，边缘功能按版本抽查。测试计划的输出是一份包含测试范围、用例清单、执行人、时间节点、准入准出标准的文档。

```javascript
// 测试用例模板（可用对象结构沉淀为用例库）
const caseTemplate = {
  id: 'TC-2026-001',              // 用例编号
  module: '登录模块',              // 所属模块
  title: '手机号+验证码登录成功',    // 用例标题
  preconditions: ['手机号未注册', '验证码接口可用'],  // 前置条件
  steps: ['输入手机号', '点击获取验证码', '输入验证码', '点击登录'],
  expected: ['登录成功', '跳转首页', '本地写入 token'],
  priority: 'P0',                 // P0 核心 / P1 重要 / P2 一般
  type: '功能',                   // 功能/边界/异常/性能/兼容
  result: 'pass'                  // pass / fail / blocked
};
```

```text
测试计划的核心内容：
1. 测试范围 —— 新增功能 + 受影响回归点 + 开放能力联调 + 兼容性与性能
2. 用例设计 —— 按模块拆解，覆盖正常流、异常流、边界值，标注优先级 P0/P1/P2
3. 冒烟测试 —— 提测后第一关，跑通主流程，冒烟不过打回重提
4. 回归测试 —— 核心链路（登录/支付/下单）每次必回归，边缘功能抽查
5. 里程碑 —— 与开发排期对齐：开发完成 -> 冒烟 -> 详细测试 -> 回归 -> 准出
6. 准入准出 —— 准入：开发自测通过、接口文档就绪；准出：P0/P1 缺陷清零、回归全绿
```

测试计划不必做得过于庞大，中小团队一张表格就能承载：横轴是模块，纵轴是测试类型（功能/边界/异常/兼容），单元格是优先级与负责人。关键是让测试范围与代码改动对齐，防止「改了个样式，结果没人验支付」这类盲区。

## 测试用例设计

测试用例设计决定测试的有效性。四个最常用且最易上手的方法是等价类划分、边界值分析、场景法与错误推测。等价类划分把输入域分成若干「代表性等价」的集合，每个集合取一个代表值即可覆盖该集合的全部行为——例如年龄输入框，有效等价类是 0-120 的整数，无效等价类是负数、小数、非数字字符，各取一个代表值就能覆盖绝大多数缺陷。边界值分析针对等价类的边界（min、max、min-1、max+1）单独设计用例，因为大量缺陷恰恰集中在边界上：金额为 0、库存为 1、字符串长度为 0 或 255。场景法从用户视角出发，按业务事件流组织用例：登录 -> 浏览商品 -> 加入购物车 -> 结算 -> 支付 -> 查看订单，每个环节的主成功流与备选流（支付超时、库存不足、取消订单）都是用例。错误推测依赖经验：哪些地方容易写错？例如时间格式化对 0 点和 24 点的处理、金额除以 100 的精度丢失、分页参数第一页是 1 还是 0。

```javascript
// 以「订单金额校验」为例的测试用例集合
const priceCases = [
  // 等价类：有效类（正常金额）
  { input: 0.01, expected: 'pass',  desc: '最小有效金额' },
  { input: 9999.99, expected: 'pass', desc: '最大有效金额' },
  { input: 100.50, expected: 'pass', desc: '带两位小数的正常金额' },
  // 等价类：无效类
  { input: -1, expected: 'fail', desc: '负数金额' },
  { input: 0, expected: 'fail', desc: '零元金额（不允许）' },
  { input: 100.999, expected: 'fail', desc: '超过两位小数' },
  { input: 'abc', expected: 'fail', desc: '非数字字符串' },
  { input: null, expected: 'fail', desc: '空值' }
];

function validateAmount(amount) {
  if (typeof amount !== 'number' || Number.isNaN(amount)) return { ok: false, msg: '金额格式错误' };
  if (amount <= 0) return { ok: false, msg: '金额必须大于 0' };
  if (amount > 10000) return { ok: false, msg: '单笔金额超限' };
  const cents = Math.round(amount * 100);
  if (Math.abs(cents - amount * 100) > 1e-6) return { ok: false, msg: '金额最多两位小数' };
  return { ok: true, cents };
}

priceCases.forEach((c) => {
  const r = validateAmount(c.input);
  const actual = r.ok ? 'pass' : 'fail';
  console.log(`${c.desc} -> 期望:${c.expected} 实际:${actual} ${actual === c.expected ? 'OK' : 'FAIL'}`);
});
```

```text
四种用例设计方法速记：
1. 等价类划分 —— 输入域分组，每类取代表值，用最少用例覆盖最大范围
2. 边界值分析 —— 专攻 min/max/min-1/max+1，缺陷高发区（0、1、255、金额精度）
3. 场景法 —— 按用户业务流程组织用例，主成功流 + 备选流（超时/取消/库存不足）
4. 错误推测 —— 凭经验猜「哪里容易写错」：时区、分页起始值、除以 100 的精度
5. 组合策略 —— 等价类定骨架，边界值补细节，场景法串流程，错误推测查遗漏
6. 优先级 —— P0 核心流程必测；P1 重要功能；P2 边缘场景按资源排期
```

用例设计还有一个常被忽略的维度：数据准备。每条用例要写清前置数据（账号状态、库存、优惠券），否则执行时才发现数据对不上。自动化场景尤其依赖「用例可重复执行」——同一用例跑十次结果一致，需要测试数据能初始化、能清理。

## 测试左移

测试左移（Shift-Left Testing）指把质量活动从「发布前测试」前移到「开发过程中」：静态检查、代码评审、单元测试在编码阶段就介入，缺陷发现得越早，修复成本越低——编码期发现一个缺陷的成本是发布后发现的三十分之一。左移的落地手段包括：ESLint 静态检查（在 CI 与本地提交钩子中执行）、代码评审（合并请求时审查逻辑与边界处理）、提交即跑单元测试、接口契约先行（前后端先对齐字段定义再并行开发）。

代码评审是测试左移的核心环节，重点不是挑语法毛病，而是审查边界处理与异常路径：参数有没有校验、接口失败有没有兜底、setData 有没有频繁调用、token 过期有没有统一处理。静态检查（ESLint）能自动拦截一类低级问题：未声明变量、隐式类型转换、未使用的 import、console 残留。小程序项目还常用 miniprogram-api-typings 提供类型提示，用 TypeScript 或 JSDoc 在编译期消灭字段拼写错误。

```javascript
// .eslintrc.js —— 小程序项目静态检查配置（要点片段）
module.exports = {
  env: { es6: true, node: true },
  globals: { wx: 'readonly', App: 'readonly', Page: 'readonly', Component: 'readonly', getApp: 'readonly' },
  parserOptions: { ecmaVersion: 2020, sourceType: 'module' },
  rules: {
    'no-undef': 'error',           // 拦截 wx 拼错、未声明变量
    'no-unused-vars': 'warn',      // 未使用变量提示
    'no-console': 'off',           // 小程序端 console 保留（线上排查用），发布前可切 warn
    'no-dupe-keys': 'error',       // 对象重复键
    'eqeqeq': ['warn', 'smart']    // 强制 ===
  }
};
```

```text
测试左移的四个抓手：
1. 静态检查 —— ESLint 在本地与 CI 双跑，自动拦截低级语法与未定义变量问题
2. 代码评审 —— 合并请求评审聚焦边界处理：参数校验、异常兜底、setData 频率
3. 提交即测 —— Git 提交钩子（husky）跑单元测试，失败禁止提交
4. 契约先行 —— 前后端先对齐接口字段文档（Swagger），再并行开发，减少联调返工
5. 度量反馈 —— 用覆盖率与缺陷趋势反向驱动开发习惯，缺陷前移数量下降即见效
6. 团队节奏 —— 测试左移不是测试部的事，是每个开发者的默认动作
```

左移的终极形态是「质量内建」：每个开发者对自己交付的代码负责，单元测试、静态检查、自测清单是合入代码的默认前置条件，而不是等测试人员来验收。小团队没有专职测试时，左移几乎是唯一能保证质量的方式——宁可提交时多花两分钟跑测试，也不要发布后花两小时救火。

## 测试报告与缺陷管理

测试报告是测试活动的交付物，回答「这个版本能不能发」。一份合格的测试报告包含：测试范围与实际执行的对比（有没有漏测）、用例执行结果统计（总用例/通过/失败/阻塞）、缺陷统计（按模块与优先级分布、遗留缺陷清单）、风险项（已知问题与缓解措施）、结论（是否达到准出标准）。报告不必长篇大论，一张统计表 + 一段结论即可，关键是结论必须基于数据：P0/P1 缺陷清零、回归全绿、遗留 P2 有明确排期，才能签字放行。

缺陷管理（Bug 管理）是测试报告的数据来源，小团队用表格或极简缺陷系统即可。缺陷记录至少要包含：标题（一句话说清现象）、复现步骤、期望结果、实际结果、优先级（P0 阻塞发布/P1 重要/P2 一般）、责任人、状态（新建/修复中/待验证/关闭）。缺陷的「待验证」环节容易被跳过——开发说修好了就直接关闭，正确流程是修复后由测试按原步骤复测，验证通过才关闭，防止「修好 A 弄坏 B」。缺陷数据还能反哺测试设计：高频缺陷模块说明用例设计薄弱，缺陷趋势（新增/关闭曲线）能预警版本风险。

```javascript
// 缺陷记录模板（可用表格或轻量系统承载）
const bugTemplate = {
  id: 'BUG-2026-001',
  title: '订单列表下拉刷新后重复数据',
  module: '订单模块',
  priority: 'P1',                    // P0 阻塞发布 / P1 重要 / P2 一般
  severity: '中',
  steps: ['进入订单列表', '下拉刷新 3 次', '观察列表'],
  expected: '每次刷新数据不重复',
  actual: '第 2 次刷新后出现重复订单',
  owner: '张三',
  status: '待验证',                   // 新建/修复中/待验证/关闭
  created: '2026-08-20',
  closed: ''
};
```

```text
测试报告与缺陷管理要点：
1. 报告结构 —— 范围对比 + 用例统计 + 缺陷分布 + 风险项 + 放行结论
2. 结论看数据 —— P0/P1 清零、回归全绿、遗留 P2 有排期，才能准出
3. 缺陷五要素 —— 标题、复现步骤、期望/实际、优先级、责任人
4. 闭环流程 —— 新建 -> 修复 -> 待验证（复测）-> 关闭，跳过复测等于没修
5. 回归验证 —— 修复缺陷要验证「原问题消失 + 关联功能正常」
6. 数据反哺 —— 高频缺陷模块补用例；新增/关闭曲线预警版本风险
```

## 应用场景实战

### 场景一：为一个电商小程序制定首版测试计划

团队 5 人（3 前端 2 后端），无专职测试，两周一个版本。按测试体系制定如下计划：

```text
首版测试计划（电商小程序 v1.0）：
1. 测试范围：登录注册、商品列表与详情、购物车、下单支付、订单列表、个人中心；
   回归点：上版已发布的商品浏览与搜索；兼容性：iOS/Android 主流机型 + 基础库 2.30+
2. 用例规模：P0 用例 40 条（核心链路），P1 用例 60 条（重要功能），P2 用例 30 条（边缘）
3. 冒烟清单（10 条）：启动正常、首页加载、登录成功、商品可浏览、加购成功、
   下单成功、支付调起、支付回调、订单可见、退出登录
4. 自动化分工：工具函数与组件逻辑写 Jest 单元测试（15.2）；
   登录-下单-支付主链路写 miniprogram-automator E2E（15.3）；
   视觉与真机体验手工走查（15.4）
5. 里程碑：开发完成（D0）-> 冒烟（D1）-> 详细测试（D2-D5）-> 回归（D6）-> 提审（D7）
6. 准出标准：P0/P1 缺陷全部关闭，冒烟与回归全绿，支付回调在测试环境验证通过
```

执行要点：没有专职测试，开发按模块互相交叉测试（你测我的、我测你的），避免「自己写的代码自己测不出问题」的盲区；支付类用例必须在测试环境真实走一遍微信支付沙箱回调，不能只看前端调起成功。

### 场景二：用等价类与边界值设计「手机号 + 验证码登录」用例

登录是每个小程序的第一道门，字段少但边界多。用等价类与边界值方法设计：

```javascript
// 手机号校验函数（被测对象）
function validatePhone(phone) {
  if (typeof phone !== 'string' || phone.length !== 11) {
    return { ok: false, msg: '手机号必须为 11 位' };
  }
  if (!/^1[3-9]\d{9}$/.test(phone)) {
    return { ok: false, msg: '手机号格式不正确' };
  }
  return { ok: true };
}

// 等价类 + 边界值用例
const phoneCases = [
  // 有效等价类
  { input: '13800138000', expect: true,  desc: '正常 11 位手机号' },
  { input: '19912345678', expect: true,  desc: '19 号段（199 开头）' },
  // 边界值：长度边界
  { input: '1380013800',  expect: false, desc: '10 位（min-1）' },
  { input: '138001380000', expect: false, desc: '12 位（max+1）' },
  { input: '',             expect: false, desc: '空字符串（min 边界）' },
  // 无效等价类
  { input: '12800138000', expect: false, desc: '12 号段（不存在）' },
  { input: '1380013800a', expect: false, desc: '含字母' },
  { input: '138 0013 800', expect: false, desc: '含空格' },
  { input: null,          expect: false, desc: 'null' }
];

phoneCases.forEach((c) => {
  const r = validatePhone(c.input);
  const pass = r.ok === c.expect;
  console.log(`${pass ? 'PASS' : 'FAIL'} ${c.desc} -> ${c.input || '(空)'} 结果:${r.msg}`);
});
```

```text
验证码用例补充：
1. 验证码有效期：60 秒内有效，61 秒后提交应报「验证码已过期」
2. 验证码错误次数：连续错 5 次锁定，需等待或换手机号
3. 重复获取：60 秒内重复点击应提示「请勿频繁获取」
4. 空验证码：不输入直接提交，应提示「请输入验证码」
5. 场景流：获取验证码 -> 输错一次 -> 输对 -> 登录成功；获取 -> 过期 -> 重新获取 -> 成功
6. 错误推测：前后端时钟不一致导致有效期判断偏差；验证码日志泄露到测试报告
```

这套用例同时服务于手工执行与自动化脚本：`validatePhone` 可以放进 Jest 直接跑单测，登录流程用 miniprogram-automator 跑 E2E，手工只需补视觉与真机项，三层测试用同一份用例设计，避免重复劳动。

## 最佳实践与踩坑记录

### 最佳实践

1. 测试分层投入遵循金字塔原则：单元测试打底（70%），集成测试居中，E2E 只覆盖核心链路，避免把所有验证都堆在慢而脆的 E2E 上
2. 环境切换用 `wx.getAccountInfoSync().miniProgram.envVersion` 自动判断，杜绝「测试环境连了生产库」这类事故，开发期允许手动覆盖便于联调
3. 每个版本先定测试范围与冒烟清单再开发，冒烟不过不进入详细测试，把「测什么」的决策前置
4. 用例设计强制覆盖四个维度：等价类、边界值、场景法、错误推测，P0 用例必须能自动化
5. 测试左移落实到提交钩子：ESLint + 单元测试挂在 husky 上，CI 上再跑一遍，双保险
6. Mock 数据与真实接口字段结构严格一致，用 Swagger 契约生成 mock 模板，防止 Mock 掩盖字段缺陷
7. 测试数据可初始化、可清理，自动化用例保证可重复执行（同一用例跑十次结果一致）
8. 小团队没有专职测试就交叉测试：模块互测 + 自动化主链路 + 手工兜底视觉与真机

### 踩坑记录

坑 1：测试环境误连生产数据库，线上数据被测试脚本污染
结论：测试环境的登录、下单把数据写进了生产库，生产出现脏数据。
原因：环境切换只靠手动改常量，有人提测时把 baseURL 改成了生产地址忘了改回。
解法：环境地址一律由 envVersion 自动推导，禁止硬编码；测试环境用独立数据库并加只读保护；CI 脚本里校验 baseURL 非生产。

坑 2：冒烟测试流于形式，核心链路带病进入详细测试
结论：冒烟清单 10 条全过，详细测试第一天就发现登录失效，整个测试计划被打乱。
原因：冒烟用例被开发自测替代，测的是「能点」而不是「主流程通」。
解法：冒烟用例独立于开发自测，由测试人员或自动化脚本执行；冒烟失败直接打回，不计入测试工时。

坑 3：E2E 用例写太多，跑一次 40 分钟，CI 形同虚设
结论：自动化用例 200 条，每次 CI 要跑近一小时，失败率 30%，最后没人看结果。
原因：把本应下沉到单元测试的细节都写成了 E2E，且用例间存在数据依赖，串行执行。
解法：回归金字塔——细节逻辑下沉 Jest 单测，E2E 只留 20 条以内核心链路；用例独立初始化数据，支持并行。

坑 4：Mock 数据与真实接口字段不一致，上线后大面积报错
结论：联调期全绿，上线后首页列表字段解析失败，页面空白。
原因：Mock 返回的字段名是开发自拟的 `list`，真实后台返回 `records`，Mock 掩盖了字段不一致。
解法：Mock 模板从 Swagger/接口文档自动生成，前后端以契约为准；上线前在预发布环境用真实后台完整回归。

坑 5：只测了正常流，异常路径缺陷全在线上暴露
结论：支付超时、token 过期、网络中断这些场景从没测过，线上集中爆发。
原因：用例设计只写了主成功流，没有覆盖备选流与异常流。
解法：用例设计强制使用场景法补备选流（超时/取消/失败重试），错误推测列异常清单，P1 级异常用例纳入每版必测。

坑 6：测试计划没有准出标准，版本「永远测不完」
结论：提审前夜还在改缺陷，上线时间一拖再拖，团队疲于奔命。
原因：没有定义 P0/P1 缺陷清零、回归全绿的准出门槛，测试范围被无限追加。
解法：版本开始就定准出标准，P2 缺陷可挂起排期，超范围需求走变更评审，准出条件满足即提审。

坑 7：回归范围只看「改了什么」，不看「影响了什么」
结论：改了商品详情的展示逻辑，结果下单流程挂了，回归没覆盖到。
原因：回归测试只看 diff 涉及的模块，没有做影响面分析（调用链上下游）。
解法：改动评审时做影响面分析，列出调用方与被调用方，回归范围 = 改动模块 + 上下游依赖模块。
