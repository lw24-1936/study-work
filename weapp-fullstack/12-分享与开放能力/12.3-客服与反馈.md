## 概述

客服与反馈是产品与用户之间的双向沟通通道：用户在小程序内通过 contact 按钮进入客服会话咨询问题，通过意见反馈提交建议与投诉；开发者既可以使用微信托管的客服工作台，也可以把消息推送接入自己的 SpringBoot 后台形成工单体系。本章覆盖客服会话机制、contact 开放能力、意见反馈的两种方案与多客服处理流程。

```text
客服与反馈要点速览：
1. 入口 —— button open-type="contact" 进入客服会话
2. 会话 —— 用户发消息后 48 小时内可主动回复（窗口内最多 5 条）
3. 模式 —— 微信托管工作台与消息推送自建客服二选一
4. 反馈 —— open-type="feedback" 官方页或自建表单
5. 上下文 —— session-from 传递页面/订单等来源信息
6. 工单 —— 消息推送接入 SpringBoot，管理端（Vue）处理闭环
```

## 客服消息与会话机制

客服消息是用户与小程序之间的聊天消息。用户在小程序内点击客服按钮后进入客服会话（会话呈现在微信聊天界面中），可以发送文本、图片等消息；客服通过工作台或服务端接口回复。会话由微信承载，开发者不需要自己实现聊天界面。

客服消息有两种运行模式：托管模式与开发模式。托管模式下，开发者在小程序后台「客服」模块添加客服人员（绑定客服的微信），消息由微信网页版客服工作台直接处理，适合客服量不大、不需要自建系统的团队。开发模式则在「开发管理 → 开发设置 → 消息推送」中配置接收 URL（并设置 Token/EncodingAESKey 与消息加解密方式），微信把用户消息推送到开发者服务器，开发者自己实现回复逻辑，适合需要把客服与自有业务系统（订单、工单、CRM）打通的团队。

客服消息接口（开发模式）：发送客服消息调用 POST https://api.weixin.qq.com/cgi-bin/message/custom/send?access_token=xxx，消息类型支持 text（文本）、image（图片）、link（链接）、miniprogrampage（小程序卡片）等。平台规则：用户主动发送消息后的 48 小时内，客服可以给该用户下发消息，且窗口内同一用户最多收到 5 条客服消息，超限返回错误码 45047——这是做主动触达时必须遵守的硬约束。

```java
// KfMessageService.java —— 发送客服消息
@Service
public class KfMessageService {

    public void sendText(String openid, String content) {
        String token = wechatApi.getAccessToken();
        String url = "https://api.weixin.qq.com/cgi-bin/message/custom/send?access_token=" + token;

        Map<String, Object> body = new HashMap<>();
        body.put("touser", openid);
        body.put("msgtype", "text");
        body.put("text", Map.of("content", content));

        String resp = restTemplate.postForObject(url, body, String.class);
        JSONObject json = JSON.parseObject(resp);
        if (json.getIntValue("errcode") != 0) {
            // 45047 = 客服接口下行条数超过上限；40003 = openid 无效
            throw new BizException("发送客服消息失败：" + json.getString("errmsg"));
        }
    }
}
```

```text
客服消息机制要点：
1. 会话载体 —— 客服会话在微信聊天界面内，微信托管，无需自建聊天 UI
2. 两种模式 —— 托管工作台（后台配客服人员）与消息推送（自建逻辑）
3. 发送接口 —— custom/send，支持文本/图片/链接/小程序卡片
4. 48 小时窗口 —— 用户发消息后 48 小时内客服可主动下发
5. 条数限制 —— 窗口内同一用户最多 5 条，超限报 45047
6. 事件推送 —— 用户进入/结束会话有事件推送，可感知会话状态
```

## 客服组件与 contact 开放能力

进入客服会话的官方组件是 button 的 open-type="contact"（早期版本有独立的 contact-button 组件，现已废弃，统一用 button 实现）。点击后微信直接打开客服会话，无需用户授权、无需额外配置，是最简单的客服接入方式。按钮样式可以完全自定义，与普通 button 无异。

contact 按钮支持几个关键属性：session-from 自定义会话来源（比如传订单号、页面路径），客服工作台可以看到该来源，用于区分不同入口的咨询；send-message-title、send-message-path、send-message-img 与 show-message-card 组合使用，用户进入会话时微信会自动发送一条「小程序卡片」消息，把用户当前所在页面（如某个订单详情）直接带给客服，客服点卡片即可看到上下文，这是提升客服效率的关键配置。

```xml
<!-- pages/order/detail.wxml —— 订单页客服按钮 -->
<view class="kf-entry">
  <button
    class="kf-btn"
    open-type="contact"
    session-from="order:{{orderNo}}"
    send-message-title="订单 {{orderNo}} 咨询"
    send-message-path="/pages/order/detail?id={{orderId}}"
    send-message-img="https://cdn.example.com/order-card.png"
    show-message-card="{{true}}"
    bindtap="onKfTap"
  >
    联系客服
  </button>
</view>
```

```js
// pages/order/detail.js（节选）
Page({
  data: {
    orderId: '10086',
    orderNo: 'WX20260820123456'
  },

  onKfTap() {
    // 客服按钮点击埋点，统计各页面咨询量
    wx.request({
      url: 'https://api.example.com/stat/kf-click',
      method: 'POST',
      data: { page: 'order-detail', orderNo: this.data.orderNo }
    })
  }
})
```

```text
contact 开放能力要点：
1. 组件 —— button open-type="contact" 打开客服会话，contact-button 旧组件已废弃
2. 来源 —— session-from 传递自定义上下文，工作台可见，用于入口区分
3. 卡片 —— send-message-* 配置进入会话时的自动消息卡片，帮助客服定位问题
4. 样式 —— 按钮样式完全可自定义，无平台限制
5. 埋点 —— 按钮 bindtap 正常触发，可统计各入口咨询量
6. 无授权 —— 打开客服会话不需要用户授权与额外审核
```

## 意见反馈

意见反馈是用户提交建议与投诉的通道，有官方与自建两种方案。

官方方案：button 的 open-type="feedback" 直接打开微信自带的意见反馈页面，用户提交后，反馈内容出现在小程序后台「反馈」模块中（后台可查看与处理）。优点是零开发，缺点是无法关联用户身份、无法自定义字段、数据只能在微信后台查看，遇到问题难以定位到具体用户。

自建方案：自己实现反馈表单页（问题类型、描述、联系方式、截图上传），提交到 SpringBoot 后台落库，管理端（Vue）展示与处理。优点是字段可定制、与用户体系（openid/uid）打通、数据进自己的库便于统计与工单流转；缺点是反馈入口需要自己设计（常与 open-type="feedback" 并存，官方页兜底）。早期还有 wx.openFeedback 之类的 API，现已不可用，统一用 open-type="feedback" 按钮实现。

```xml
<!-- pages/feedback/feedback.wxml —— 自建反馈表单 -->
<form bindsubmit="onSubmit">
  <view class="form-item">
    <picker mode="selector" range="{{types}}" bindchange="onTypeChange">
      <view class="picker">问题类型：{{types[typeIndex]}}</view>
    </picker>
  </view>
  <view class="form-item">
    <textarea name="content" placeholder="请描述你遇到的问题（必填，500 字以内）" maxlength="500" />
  </view>
  <view class="form-item">
    <input name="contact" placeholder="联系方式（选填，便于我们联系你）" maxlength="50" />
  </view>
  <button class="submit-btn" form-type="submit" loading="{{submitting}}">提交反馈</button>
</form>
```

```js
// pages/feedback/feedback.js
Page({
  data: {
    types: ['功能异常', '体验建议', '内容问题', '投诉举报', '其他'],
    typeIndex: 0,
    submitting: false
  },

  onTypeChange(e) {
    this.setData({ typeIndex: Number(e.detail.value) })
  },

  onSubmit(e) {
    const content = (e.detail.value.content || '').trim()
    if (!content) {
      wx.showToast({ title: '请填写问题描述', icon: 'none' })
      return
    }
    if (this.data.submitting) return // 防连点
    this.setData({ submitting: true })

    wx.request({
      url: 'https://api.example.com/feedback/submit',
      method: 'POST',
      data: {
        type: this.data.types[this.data.typeIndex],
        content,
        contact: (e.detail.value.contact || '').trim()
      },
      success: (res) => {
        wx.showToast({ title: '提交成功，感谢反馈', icon: 'success' })
        setTimeout(() => wx.navigateBack(), 1500)
      },
      complete: () => this.setData({ submitting: false })
    })
  }
})
```

```java
// FeedbackController.java —— 反馈落库
@RestController
@RequestMapping("/feedback")
public class FeedbackController {

    @Autowired
    private FeedbackService feedbackService;

    @PostMapping("/submit")
    public Result<Void> submit(@RequestBody FeedbackReq req, @RequestHeader("X-Openid") String openid) {
        // 1. 内容安全校验（对接 msgSecCheck，见 14.1 内容安全篇）
        securityService.checkText(req.getContent());
        // 2. 落库并关联用户 openid，管理端可定位用户
        feedbackService.save(req, openid);
        return Result.ok();
    }
}
```

```text
意见反馈要点：
1. 官方入口 —— button open-type="feedback" 打开微信自带反馈页，后台查看
2. 自建入口 —— 自己实现表单 + SpringBoot 落库，字段与用户体系可定制
3. 双通道 —— 常见做法是自建表单为主、官方反馈页兜底
4. 旧 API —— wx.openFeedback 已不可用，统一用 open-type="feedback"
5. 关联用户 —— 自建方案把反馈与 openid 关联，问题可定位
6. 内容安全 —— 反馈内容建议过 msgSecCheck 再入库，避免违规内容
```

## 用户反馈处理与多客服

托管模式下，客服人员在小程序后台「客服」模块进入客服工作台接待用户；一个小程序可以绑定多个客服账号，用户进入会话后按接入顺序分配给在线客服，客服可以结束会话并查看历史记录。后台还支持配置欢迎语与关键词自动回复，适合非工作时间的兜底。

开发模式下，消息推送 URL 会收到用户消息与事件（用户进入会话 event=user_enter_tempsession、文本/图片消息等），开发者把消息落到自己的系统里，形成工单：客服在 Vue 管理端查看与回复，回复时调用 custom/send 下发。这里有一个重要的协议细节：收到推送后需要在 5 秒内响应微信服务器（被动回复或返回空串），超时微信会重试 3 次，用户可能收到重复消息；需要耗时处理的逻辑（查订单、查物流）应先在 5 秒内返回「已收到，正在处理」，再异步处理并通过 custom/send 主动下发结果。

```java
// WxMsgPushController.java —— 接收用户消息推送（明文模式简化示例）
@RestController
public class WxMsgPushController {

    @PostMapping(value = "/wx/msg", produces = "application/xml;charset=utf-8")
    public String onMsg(@RequestBody String xml) {
        Map<String, String> msg = XmlUtil.parseToMap(xml); // 简易 XML 解析
        String fromUser = msg.get("FromUserName");
        String msgType = msg.get("MsgType");

        // 事件：用户进入客服会话
        if ("event".equals(msgType) && "user_enter_tempsession".equals(msg.get("Event"))) {
            kfService.onUserEnter(fromUser, msg.get("SessionFrom"));
            return ""; // 事件无需回复
        }

        // 文本消息：先快速响应，再异步处理
        if ("text".equals(msgType)) {
            String content = msg.get("Content");
            // 5 秒内必须响应：先被动回复一句
            String quickReply = "<xml>"
                + "<ToUserName><![CDATA[" + fromUser + "]]></ToUserName>"
                + "<FromUserName><![CDATA[" + msg.get("ToUserName") + "]]></FromUserName>"
                + "<CreateTime>" + (System.currentTimeMillis() / 1000) + "</CreateTime>"
                + "<MsgType><![CDATA[text]]></MsgType>"
                + "<Content><![CDATA[收到，客服正在处理，请稍候]]></Content>"
                + "</xml>";
            // 异步：查订单/查物流，结果通过 custom/send 主动下发
            kfService.handleAsync(fromUser, content);
            return quickReply;
        }
        return "";
    }
}
```

```text
反馈处理要点：
1. 托管模式 —— 后台客服工作台接待，多客服按顺序接入，可配自动回复
2. 开发模式 —— 消息推送 URL 接收消息与事件，接入自建工单系统
3. 响应时限 —— 推送需 5 秒内响应，超时微信重试 3 次，用户收重复消息
4. 长耗时 —— 先快速响应「已收到」，再异步处理 + custom/send 下发结果
5. 会话感知 —— user_enter_tempsession 事件可感知用户进入会话，记录来源
6. 闭环 —— 消息落库成工单，Vue 管理端处理，48h 窗口内跟进
```

## 应用场景实战

### 场景一：电商订单客服（contact 按钮带订单上下文 + 服务端推送接收）

需求：订单详情页放客服按钮，session-from 带订单号；用户咨询后，服务端收到消息推送，自动查询订单状态并回复物流信息；复杂问题转人工。

```xml
<!-- pages/order/detail.wxml -->
<view class="order-card">
  <view class="order-no">订单号：{{orderNo}}</view>
  <view class="order-status">状态：{{statusText}}</view>
</view>
<button
  class="kf-btn"
  open-type="contact"
  session-from="order:{{orderNo}}"
  send-message-title="订单 {{orderNo}} 咨询"
  send-message-path="/pages/order/detail?id={{orderId}}"
  send-message-img="https://cdn.example.com/order-card.png"
  show-message-card="{{true}}"
>
  联系客服
</button>
```

```java
// KfService.java —— 消息接收后的自动回复逻辑
@Service
public class KfService {

    public void handleAsync(String openid, String content) {
        // 1. 落库记录会话消息（工单系统数据源）
        kfMessageMapper.insert(openid, content);

        // 2. 自动回复：识别订单号查询物流
        String orderNo = extractOrderNo(content);
        if (orderNo != null) {
            String logistics = orderService.queryLogistics(orderNo);
            kfMessageService.sendText(openid, "您的订单 " + orderNo + " 物流：" + logistics);
        } else if (content.contains("人工")) {
            // 3. 需要人工：在管理端生成待处理工单，由客服在 Vue 管理端回复
            workOrderService.create(openid, content, "pending");
            kfMessageService.sendText(openid, "已为您转接人工客服，请稍候");
        } else {
            kfMessageService.sendText(openid, "请问还有什么可以帮您？（回复「人工」转人工客服）");
        }
    }

    private String extractOrderNo(String content) {
        java.util.regex.Matcher m = java.util.regex.Pattern.compile("WX\\d{14}").matcher(content);
        return m.find() ? m.group() : null;
    }
}
```

效果：用户点客服按钮 → 会话打开并自动带上订单卡片 → 用户提问 → 服务端自动回复物流/转人工 → 全链路消息落库，可回溯。

### 场景二：反馈工单闭环（自建反馈页 + 管理端处理 + 客服消息回复）

需求：用户在小程序内提交反馈工单，运营在 Vue 管理端处理，处理完成后通过客服消息（48h 窗口内）或订阅消息通知用户结果。

小程序端提交（复用上文反馈表单代码）后，SpringBoot 保存工单：

```java
// FeedbackService.java
@Service
public class FeedbackService {

    public void save(FeedbackReq req, String openid) {
        Feedback feedback = new Feedback();
        feedback.setOpenid(openid);
        feedback.setType(req.getType());
        feedback.setContent(req.getContent());
        feedback.setContact(req.getContact());
        feedback.setStatus(0); // 0 待处理 / 1 处理中 / 2 已解决
        feedbackMapper.insert(feedback);
    }

    // 管理端调用：标记解决并通知用户
    public void resolve(Long id, String reply) {
        Feedback feedback = feedbackMapper.selectById(id);
        feedback.setStatus(2);
        feedback.setReply(reply);
        feedbackMapper.updateById(feedback);

        // 用户 48h 内发过消息才可用客服消息通知；否则走订阅消息
        if (kfMessageService.canPush(feedback.getOpenid())) {
            kfMessageService.sendText(feedback.getOpenid(), "您反馈的问题已处理：" + reply);
        } else {
            subscribeService.sendFeedbackResult(feedback.getOpenid(), reply);
        }
    }
}
```

管理端（Vue）提供工单列表页：按状态筛选、查看反馈内容与用户信息（openid 关联的用户昵称/手机号）、填写处理结果。整个反馈闭环：用户提交 → 工单入库 → 管理端处理 → 客服消息/订阅消息触达用户 → 用户确认。

## 最佳实践与踩坑记录

### 最佳实践

1. 客服按钮封装成统一组件（kf-button），自动带上页面路径与关键业务 ID（订单号/商品 ID）到 session-from
2. 消息推送的验签、加解密、XML 解析统一在服务端网关层处理，业务代码只面对结构化消息对象
3. 被动回复必须在 5 秒内完成，耗时逻辑（查单、查物流）先回「已收到」再异步处理并用 custom/send 下发结果
4. 充分利用 48 小时窗口做问题闭环：用户咨询未解决时，窗口内主动跟进结果，避免用户流失
5. 反馈表单字段精简（类型 + 描述 + 选填联系方式），降低提交门槛；提交按钮做防连点
6. 反馈与用户 openid 关联，管理端可定位用户，必要时关联订单与登录记录
7. 非工作时间配置欢迎语与关键词自动回复兜底，减少用户等待感
8. 反馈内容与客服消息内容对接 msgSecCheck 内容安全检测，避免违规内容入库（见 14.1 内容安全篇）

### 踩坑记录

```text
坑 1：contact 按钮在开发者工具里点了没反应
结论：模拟器里点击客服按钮毫无动静，以为代码写错。
原因：客服会话是微信客户端的原生能力，开发者工具无法模拟完整的客服会话。
解法：用「预览」生成真机预览，在手机微信中验证；工具内只能验证按钮渲染与样式。

坑 2：消息推送配置了却收不到用户消息
结论：用户发消息后服务端日志里没有任何推送记录。
原因：消息推送 URL 未启用、Token 验签失败、或 URL 未通过域名校验（必须 HTTPS 合法域名）。
解法：检查「消息推送」开关状态；确认 URL 是已配置的合法 HTTPS 域名；用后台「消息推送」页的测试功能验证验签。

坑 3：客服消息下发报 45047（条数超限）
结论：自动回复/主动触达失败，接口返回 45047。
原因：用户 48 小时内已收到 5 条客服消息，达到平台上限。
解法：控制主动下发频率，把可合并的信息合并成一条；重要通知优先保证，营销内容放弃或改走订阅消息。

坑 4：session-from 里的特殊字符导致工作台显示异常
结论：客服工作台里来源信息乱码或被截断。
原因：session-from 传入了中文、空格、换行等特殊字符，传输/展示未编码。
解法：session-from 只放安全字符（如 order:10086），中文与特殊字符先 encodeURIComponent。

坑 5：open-type="feedback" 的官方反馈页看不到用户是谁
结论：用户提交了反馈，但后台只有内容，无法联系与定位用户。
原因：官方反馈页不采集用户身份，反馈与 openid 无关联。
解法：重要场景用自建反馈表单（关联 openid）；官方反馈页只做兜底，必要时在反馈页引导用户留联系方式。

坑 6：被动回复超 5 秒，用户收到重复消息
结论：用户收到两三条相同的「已收到」回复。
原因：微信服务器 5 秒内未收到响应会重试 3 次，每次重试都会再触发一次业务逻辑。
解法：处理函数保持幂等（按消息 ID 去重）；长耗时逻辑异步化，5 秒内先返回空串或快速回复。

坑 7：自建反馈表单连点提交，生成重复工单
结论：一个用户提交了多条相同反馈，工单系统里全是重复数据。
原因：没有做提交防抖/幂等，用户手滑连点。
解法：submitting 标志位禁用按钮 + 服务端按 openid+内容 hash 幂等去重。

坑 8：想给用户发通知却用了订阅消息模板，用户没授权收不到
结论：客服主动通知发不出去，用户侧无感知。
原因：订阅消息需要用户提前授权，未授权用户无法接收；客服消息才是会话内的即时通道。
解法：会话场景（用户刚咨询过）用客服消息（48h 窗口内）；非会话场景用订阅消息并提前在关键路径引导授权。
```
