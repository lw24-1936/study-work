## 概述

本项目搭建一个统一的算法模型服务平台：把训练好的模型经 ONNX Runtime / TensorRT 优化推理，用 FastAPI / gRPC 提供服务接口，Docker 打包镜像，Kubernetes 编排部署和弹性伸缩，KServe/BentoML 统一模型管理，Prometheus/Grafana 监控运行状态。业务价值在于让算法团队「训练完就能上线」，把模型部署、推理加速、运维监控这些工程活儿标准化，缩短模型从训练到生产的周期。

```text
模型服务平台核心能力：
1. 服务框架 —— FastAPI（REST）+ gRPC（高性能 RPC）
2. 推理加速 —— ONNX Runtime 跨框架，TensorRT/OpenVINO 硬件加速
3. 容器化 —— Docker 镜像，环境一致、可移植
4. 编排部署 —— Kubernetes 弹性伸缩、滚动发布
5. 模型管理 —— KServe/BentoML 统一模型版本与部署
6. 监控告警 —— Prometheus 采集指标 + Grafana 可视化
```

```python
# 服务化主流程：模型加载 → 推理接口 → 监控埋点
from fastapi import FastAPI

app = FastAPI()
model = load_onnx_model("model.onnx")     # 加载 ONNX 模型

@app.post("/predict")
async def predict(inputs: dict):
    output = model.run(inputs["data"])    # 推理
    return {"prediction": output}
```

## 技术选型

| 环节 | 选择 | 理由 | 备选 |
|---|---|---|---|
| 服务框架 | FastAPI + gRPC | REST 通用易调试，gRPC 高吞吐低延迟 | Flask、Tornado |
| 推理引擎 | ONNX Runtime | 跨框架、跨平台，CPU/GPU 都能跑 | 直接跑 PyTorch |
| 硬件加速 | TensorRT / OpenVINO | NVIDIA GPU 用 TensorRT，Intel CPU 用 OpenVINO | TFLite（移动端） |
| 容器 | Docker | 环境一致性，一次打包到处运行 | 裸机部署 |
| 编排 | Kubernetes | 弹性伸缩、滚动发布、自愈 | Docker Compose（小规模） |
| 模型管理 | KServe / BentoML | 标准化的模型服务抽象，版本管理和滚动 | 自研部署脚本 |
| 监控 | Prometheus + Grafana | 指标采集 + 可视化的事实标准 | 商业 APM |

选型原则：服务框架按「延迟敏感度」选——对延迟要求高的内部调用用 gRPC，对外通用接口用 FastAPI。推理引擎按硬件选——NVIDIA GPU 用 TensorRT，Intel CPU 用 OpenVINO，通用场景用 ONNX Runtime。

```python
# 推理引擎统一抽象：不同后端实现同一接口
class InferenceEngine:
    def load(self, model_path): raise NotImplementedError
    def predict(self, inputs): raise NotImplementedError

class OnnxEngine(InferenceEngine):
    def load(self, model_path):
        import onnxruntime as ort
        self.session = ort.InferenceSession(model_path)
    def predict(self, inputs):
        return self.session.run(None, {"input": inputs})[0]
```

## 架构设计

平台分「模型 → 服务 → 编排 → 监控」四层。模型层做格式转换和推理优化，服务层暴露接口，编排层做容器化和调度，监控层采集运行指标。

```text
┌────────────────────────────────────────────────────┐
│ 模型层   PyTorch/TF 模型 → ONNX → TensorRT/OpenVINO  │
│          │                                         │
│ 服务层   FastAPI(REST) / gRPC 推理接口              │
│          │                                         │
│ 编排层   Docker 镜像 → Kubernetes 部署/伸缩/发布     │
│          │              KServe/BentoML 管理         │
│          │                                         │
│ 监控层   Prometheus 指标 → Grafana 面板 + 告警       │
└────────────────────────────────────────────────────┘
```

```python
# 模型到服务的完整流程
def deploy_model(torch_model, dummy_input, output_path):
    onnx_path = export_onnx(torch_model, dummy_input, output_path)   # 导出 ONNX
    engine = OnnxEngine(); engine.load(onnx_path)                     # 加载引擎
    app = build_fastapi(engine)                                       # 包服务
    image = build_docker_image(app)                                   # 打镜像
    k8s_deploy(image)                                                 # 部署 K8s
    return app
```

## FastAPI 与 gRPC

服务层对外提供两种接口：FastAPI 的 REST 接口通用、易调试、方便前端调用；gRPC 用 Protobuf 定义接口，二进制传输，高吞吐低延迟，适合服务间的高频调用。详见 [[16.1-服务框架]]。

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class PredictRequest(BaseModel):
    features: list[float]

@app.post("/predict")
async def predict(req: PredictRequest):
    output = model.predict([req.features])
    return {"prediction": output.tolist()}

@app.get("/health")
async def health():
    return {"status": "ok"}          # 健康检查，供 K8s 探针调用
```

```text
# gRPC 服务定义（protobuf）
service Predictor {
  rpc Predict(PredictRequest) returns (PredictResponse);
}
message PredictRequest { repeated float features = 1; }
message PredictResponse { repeated float prediction = 1; }
```

```text
FastAPI vs gRPC：
1. FastAPI —— REST + JSON，通用、易调试，适合对外和前端
2. gRPC —— Protobuf + HTTP/2，高性能、强类型，适合服务间调用
3. 选择 —— 对外用 FastAPI，内部高频调用用 gRPC，可同时提供
```

## ONNX Runtime

ONNX 是模型交换的开放格式，ONNX Runtime 是它的推理引擎。模型先转 ONNX，就能脱离训练框架、跨平台推理，CPU/GPU 都能跑。这是「训练框架无关」的关键一步，详见 [[16.3-推理优化]]。

```python
import torch
import onnxruntime as ort
import numpy as np

# 导出 PyTorch 模型为 ONNX
model = torch.nn.Linear(4, 2)
dummy = torch.randn(1, 4)
torch.onnx.export(model, dummy, "model.onnx", input_names=["input"], output_names=["output"])

# ONNX Runtime 加载推理
session = ort.InferenceSession("model.onnx")
inputs = np.random.randn(1, 4).astype("float32")
output = session.run(None, {"input": inputs})[0]
print(output)
```

```text
ONNX Runtime 要点：
1. 跨框架 —— PyTorch/TF/sklearn 都能导 ONNX
2. 跨平台 —— CPU/GPU/移动端同一份模型
3. 图优化 —— 算子融合、常量折叠，比直接跑框架快
4. 前置 —— 先导 ONNX，再决定用 ORT 还是 TensorRT/OpenVINO
```

## TensorRT 与 OpenVINO

硬件级推理加速：TensorRT 面向 NVIDIA GPU，OpenVINO 面向 Intel CPU/VPU。它们做算子融合、精度量化（FP16/INT8）、内存优化，推理吞吐可提升 3-5 倍，但需要按目标硬件构建引擎。

```python
import tensorrt as trt

# TensorRT 构建引擎（从 ONNX）
def build_trt_engine(onnx_path, fp16=True):
    logger = trt.Logger(trt.Logger.WARNING)
    builder = trt.Builder(logger)
    network = builder.create_network(1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
    parser = trt.OnnxParser(network, logger)
    with open(onnx_path, "rb") as f:
        parser.parse(f.read())
    config = builder.create_builder_config()
    if fp16:
        config.set_flag(trt.BuilderFlag.FP16)      # FP16 精度
    return builder.build_serialized_network(network, config)
```

```text
TensorRT vs OpenVINO：
1. TensorRT —— NVIDIA GPU，FP16/INT8 量化，算子融合
2. OpenVINO —— Intel CPU/核显，同思路的硬件加速
3. 代价 —— 需按硬件构建引擎，构建慢但推理快
4. 收益 —— 吞吐 3-5 倍，延迟显著下降
5. 折中 —— 想省事用 ONNX Runtime，追求极致再上 TensorRT/OpenVINO
```

## Docker

Docker 把模型 + 推理引擎 + 服务代码打包成镜像，保证「本地能跑，线上也能跑」。镜像分层构建，依赖固定版本，避免环境漂移导致的「我机器上没问题」。

```text
# Dockerfile：模型服务镜像
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY model.onnx .
COPY app.py .
EXPOSE 8000
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
```

```bash
# 构建 + 运行镜像
docker build -t model-service:v1.2 .
docker run -d -p 8000:8000 --gpus all model-service:v1.2
```

```text
Docker 要点：
1. 分层缓存 —— 依赖装在前，代码改在后，加速构建
2. 固定版本 —— requirements 锁版本，避免环境漂移
3. GPU 镜像 —— 用 nvidia/cuda 基础镜像，--gpus 挂载
4. 轻量 —— 用 slim 基础镜像，减小体积加快部署
```

## Kubernetes

Kubernetes 负责生产环境的编排：副本管理、弹性伸缩、滚动发布、自愈。模型服务作为 Deployment 部署，HPA 按 CPU/自定义指标自动扩缩容，滚动更新实现不中断发布。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: model-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: model-service
  template:
    metadata:
      labels:
        app: model-service
    spec:
      containers:
        - name: model-service
          image: model-service:v1.2
          ports:
            - containerPort: 8000
          resources:
            limits:
              nvidia.com/gpu: 1          # 申请 GPU
            requests:
              memory: "2Gi"
              cpu: "1000m"
          livenessProbe:
            httpGet: {path: /health, port: 8000}
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: model-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: model-service
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: {type: Utilization, averageUtilization: 70}
```

```text
Kubernetes 要点：
1. Deployment —— 副本管理，声明期望状态
2. HPA —— 按 CPU/内存/自定义指标自动伸缩
3. 滚动发布 —— 逐步替换旧副本，不中断服务
4. 探针 —— liveness/readiness 探针做健康检查和流量切换
5. GPU 调度 —— 通过 nvidia-device-plugin 申请 GPU 资源
```

## KServe 与 BentoML

KServe/BentoML 提供更高层的模型服务抽象，把「模型版本、部署策略、推理协议」标准化，屏蔽底层 K8s 细节。KServe 是 K8s 原生的模型服务 CRD，BentoML 是模型打包和服务的框架。

```python
import bentoml

# BentoML 打包模型
saved = bentoml.pytorch.save_model("my_model", torch_model)

# BentoML 定义服务
@bentoml.service
class ModelService:
    def __init__(self):
        self.model = bentoml.pytorch.load_model(saved)

    @bentoml.api
    def predict(self, features):
        return self.model(features)

# 构建镜像并部署：bentoml build / bentoml deploy
```

```text
KServe vs BentoML：
1. KServe —— K8s 原生 CRD，标准化推理协议，适合已有 K8s 平台
2. BentoML —— 端到端打包 + 服务 + 部署，开发体验好
3. 选择 —— 深度绑定 K8s 用 KServe，快速落地用 BentoML
4. 共同点 —— 都解决「模型版本管理 + 标准化部署」的问题
```

## Prometheus 与 Grafana

监控层用 Prometheus 采集指标（延迟、吞吐、错误率、GPU 利用率），Grafana 做可视化面板和告警。模型服务埋点暴露 /metrics 端点，Prometheus 定期抓取，详见 [[16.6-监控]]。

```python
from prometheus_client import Counter, Histogram, generate_latest
from fastapi import FastAPI, Response

app = FastAPI()
request_count = Counter("predict_requests_total", "预测请求总数")
latency = Histogram("predict_latency_seconds", "预测延迟")

@app.post("/predict")
async def predict(req: dict):
    request_count.inc()
    with latency.time():                    # 自动记录延迟
        output = model.predict(req["data"])
    return {"prediction": output}

@app.get("/metrics")
async def metrics():
    return Response(generate_latest(), media_type="text/plain")   # Prometheus 抓取端点
```

```text
监控指标：
1. 延迟 —— 请求耗时分布（P50/P99）
2. 吞吐 —— QPS，请求总数
3. 错误率 —— 失败请求占比
4. 资源 —— GPU 利用率、显存、CPU、内存
5. 告警 —— 延迟超标、错误率上升时 Grafana 告警
```

## 应用场景实战

### 场景一：PyTorch 模型全链路部署

```python
import torch
import numpy as np
import onnxruntime as ort
from fastapi import FastAPI
from pydantic import BaseModel

# 1. 训练好的模型
model = torch.nn.Sequential(torch.nn.Linear(4, 8), torch.nn.ReLU(), torch.nn.Linear(8, 2))
dummy = torch.randn(1, 4)
torch.onnx.export(model, dummy, "model.onnx", input_names=["input"], output_names=["output"])

# 2. ONNX Runtime 加载
session = ort.InferenceSession("model.onnx")

# 3. FastAPI 服务化
app = FastAPI()

class Req(BaseModel):
    features: list[float]

@app.post("/predict")
async def predict(req: Req):
    x = np.array([req.features], dtype="float32")
    out = session.run(None, {"input": x})[0]
    return {"prediction": out.tolist()}

# 4. 本地测试
import json
test = {"features": [0.1, 0.2, 0.3, 0.4]}
print(session.run(None, {"input": np.array([test["features"]], dtype="float32")})[0])
```

### 场景二：延迟监控埋点

```python
from prometheus_client import Counter, Histogram

request_count = Counter("predict_requests_total", "预测请求总数")
latency = Histogram("predict_latency_seconds", "预测延迟", buckets=[0.01, 0.05, 0.1, 0.5, 1.0, 2.0])

def predict_with_metrics(features):
    request_count.inc()
    with latency.time():
        return model.predict(features)

# 模拟一批请求，统计延迟分布
import time, random
for _ in range(100):
    time.sleep(random.random() * 0.05)
    predict_with_metrics([0.1, 0.2, 0.3, 0.4])
print(f"总请求数: {request_count._value.get()}")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 模型先导 ONNX 统一格式，再决定用 ORT 还是 TensorRT/OpenVINO 加速
2. 对外接口用 FastAPI（REST），内部高频调用用 gRPC，两者可并存
3. Docker 镜像固定依赖版本，用 slim 基础镜像减小体积
4. K8s 配 liveness/readiness 探针，滚动发布保证不中断
5. 推理埋点暴露 /metrics，Prometheus 抓取 + Grafana 告警
6. 模型版本用 KServe/BentoML 管理，支持多版本并存和灰度

### 踩坑记录

```text
坑 1：直接跑 PyTorch 权重上线，不做格式转换
结论：推理延迟高、依赖重、换环境各种版本冲突。
原因：训练框架自带推理慢，且依赖整个 PyTorch 环境。
解法：导 ONNX 用 ONNX Runtime 推理，按硬件再上 TensorRT/OpenVINO。

坑 2：Docker 镜像里依赖版本不固定
结论：本地能跑，线上容器里 import 失败或行为不一致。
原因：requirements.txt 没锁版本，构建时拉到了新版。
解法：锁死版本号（pip freeze），用 slim 基础镜像。

坑 3：K8s 没配探针，滚动发布时服务中断
结论：新副本还没就绪就接流量，返回 502。
原因：缺少 readiness 探针，K8s 不知道新副本何时可用。
解法：配 readiness/liveness 探针，就绪后再切换流量。

坑 4：GPU 服务没限制显存，多副本抢爆显存
结论：多个副本挤一块 GPU，OOM 导致容器被杀。
原因：没设置 GPU 资源限制和显存上限。
解法：按副本申请 GPU 资源，推理时限制显存（max_batch_size 等）。

坑 5：没埋监控指标，线上性能退化无感知
结论：模型变慢、错误率上升，出了问题才知道。
原因：服务没暴露指标，缺少可观测性。
解法：埋点延迟/吞吐/错误率，Prometheus + Grafana 告警。
```
