## 概述

企业级算法平台是一站式的机器学习基础设施，把「数据接入 → 特征工程 → 模型训练 → 评估注册 → 在线服务 → 监控反馈」全生命周期工程化、标准化，让算法工程师专注建模，让模型能稳定、可追踪地上线。

```text
企业级算法平台解决的核心问题：
1. 从「脚本建模」到「平台化」—— 流程标准化、可复现
2. 模型资产化管理 —— Registry 统一登记，版本可回溯
3. 训练到服务打通 —— 训练产物一键发布上线
4. 质量兜底 —— 监控 + A/B 保证线上效果可控
```

## 技术选型

```text
各环节的主流技术选型：
1. 数据 —— Spark/Flink 批流一体，Hive/Iceberg 数仓
2. 特征 —— Feast / 自研 Feature Store，离在线一致性
3. 训练 —— Kubernetes + Kubeflow / Argo，GPU 调度
4. 评估 —— MLflow / 自研评测，指标 + 报告
5. Registry —— MLflow Model Registry / 自研
6. Serving —— KServe / BentoML / Triton，多框架兼容
7. Monitoring —— Prometheus + Grafana，数据/模型漂移
8. A/B —— 分流平台，分层实验
```

## 数据

数据是平台的地基：统一接入、统一清洗、统一质量校验，保证训练和服务用的是同一份可信数据。

```text
数据层的职责：
1. 数据接入 —— 批(Spark)/流(Flink)统一管道
2. 数据质量 —— 缺失率、分布校验、Schema 校验
3. 数据血缘 —— 追踪每个特征的来源
4. 数据版本 —— 训练数据快照，可追溯
```

```python
# 数据质量校验示意
import pandas as pd

def validate(df):
    checks = {
        'missing_rate': df.isna().mean().max(),
        'row_count': len(df),
        'schema': list(df.columns),
    }
    assert checks['missing_rate'] < 0.1, '缺失率超标'
    assert checks['row_count'] > 1000, '数据量不足'
    return checks
```

## 特征

特征平台统一特征的「定义、计算、存储、服务」，核心是离在线一致性——训练用离线特征，服务用在线特征，两者口径必须完全一致。

```text
Feature Store 的核心能力：
1. 特征注册 —— 特征名、类型、来源统一登记
2. 离线特征 —— Spark 批量计算，供训练
3. 在线特征 —— 低延迟 KV 查询，供服务
4. 一致性 —— 同一套计算逻辑，离在线同口径
5. Point-in-time —— 避免特征穿越（用未来数据训练）
```

```python
# Feast 特征定义示意
from feast import Entity, Feature, FeatureView, ValueType

driver = Entity(name="driver", value_type=ValueType.INT64)
driver_stats = FeatureView(
    name="driver_stats",
    entities=[driver],
    features=[
        Feature(name="avg_trips", dtype=ValueType.FLOAT),
        Feature(name="total_trips", dtype=ValueType.INT64),
    ],
)
```

训练平台的关键点：

2. 资源调度 —— GPU 配额、优先级、排队
3. 分布式 —— DDP/FSDP 多卡多机训练

## 评估

评估是模型上线的质量关卡：离线指标不达标不允许注册上线，评估报告留档可追溯。

```text
评估环节：
1. 离线评估 —— 划分测试集算指标（AUC/NDCG/Recall@K）
2. 对比基准 —— 新模型 vs 线上模型的指标对比
3. 评估报告 —— 指标、切片、badcase 自动生成
4. 门禁 —— 指标阈值不达标自动拦截
```

```python
# 评估门禁示意
def gate(model_metrics, baseline_metrics, threshold=0.02):
    delta = model_metrics['auc'] - baseline_metrics['auc']
    if delta < threshold:
        raise RuntimeError(f'模型未达门禁，ΔAUC={delta:.4f}')
    return model_metrics
```

## Registry

模型注册中心统一管理模型资产：版本、元数据、依赖、评估报告，让「哪个模型在服务、怎么来的」可追溯。

```text
Model Registry 的能力：
1. 模型版本 —— 每次训练产出带版本的模型
2. 元数据 —— 训练配置、数据版本、代码 commit
3. 阶段流转 —— staging → production → archived
4. 回滚 —— 一键回退到历史版本
```

```python
# MLflow Registry 示意
import mlflow

mlflow.register_model("runs:/abc123/model", "recommender")
client = mlflow.tracking.MlflowClient()
client.transition_model_version_stage(
    name="recommender", version=3, stage="Production")
```

## Serving

Serving 层把注册的模型部署成可调用的服务，支持在线（低延迟）、批量（高吞吐）和流式三种模式。

```text
Serving 的要点：
1. 框架兼容 —— ONNX/TensorRT/PyTorch 统一封装
2. 弹性伸缩 —— 按 QPS 自动扩缩容
3. 灰度发布 —— Canary/Shadow 平滑切换
4. 多模型 —— 一个服务挂多个模型版本
```

```python
# BentoML 服务示意
import bentoml

@bentoml.service
class Recommender:
    def __init__(self):
        self.model = bentoml.sklearn.load_model("recommender:latest")

    @bentoml.api
    def predict(self, user_id: int):
        return self.model.recommend(user_id)
```

## Monitoring

监控是线上质量的兜底：性能指标 + 业务指标 + 模型效果 + 数据漂移，异常自动告警。

```text
监控维度：
1. 性能 —— 延迟、吞吐、错误率
2. 资源 —— GPU/CPU/内存利用率
3. 模型效果 —— 线上 CTR/转化率 vs 基线
4. 漂移 —— 数据漂移（特征分布变化）、概念漂移（标签关系变化）
5. 告警 —— 指标超阈值自动通知
```

```python
# 数据漂移检测示意（PSI）
import numpy as np

def psi(expected, actual, bins=10):
    e_hist, _ = np.histogram(expected, bins=bins)
    a_hist, _ = np.histogram(actual, bins=bins)
    e = e_hist / e_hist.sum() + 1e-10
    a = a_hist / a_hist.sum() + 1e-10
    return float(np.sum((a - e) * np.log(a / e)))
```

## A/B

A/B 实验是模型上线的最终验证：新模型分流到小流量，与线上模型对比业务指标，显著优于才放量。

```text
A/B 实验的关键：
1. 分流 —— 用户/请求维度稳定分流
2. 分层 —— 多个实验并行互不干扰
3. 指标 —— 核心业务指标（CTR/GMV）+ 护栏指标
4. 显著性 —— 样本量足够 + 显著性检验
5. 放量 —— 5% → 25% → 50% → 100% 逐步放量
```

## 自动化训练与部署

自动化把「训练 → 评估 → 注册 → 部署」串成 CI/CD 流水线，模型迭代不再靠手工操作。

```text
自动化流水线：
1. 触发 —— 定时/新数据/代码变更触发训练
2. 训练 → 评估 → 门禁 → 注册 → 灰度 → 全量
3. 回滚 —— 线上指标恶化自动回滚
4. 全链路可观测 —— 每个环节状态可查
```

```yaml
# CI/CD 流水线示意（伪配置）
stages:
  - name: train
    job: kubeflow-train
  - name: evaluate
    job: offline-eval
    gate: auc_delta > 0.02
  - name: register
    job: mlflow-register
  - name: deploy-canary
    job: kserve-deploy
    traffic: 5%
  - name: rollout
    job: kserve-rollout
    when: canary_metrics_ok
```

## 应用场景实战

### 场景一：一个新模型从训练到上线的完整链路

```python
# 伪代码：把各环节串起来
def pipeline(new_data_version):
    # 1. 数据 + 特征
    features = feature_store.get_offline_features(new_data_version)
    # 2. 训练
    model, metrics = train(features)
    # 3. 评估门禁
    if metrics['auc'] - baseline['auc'] < 0.02:
        raise RuntimeError('未过门禁')
    # 4. 注册
    version = register_model(model, metrics)
    # 5. 灰度部署
    deploy_canary(version, traffic=0.05)
    return version
```

## 最佳实践与踩坑记录

### 最佳实践

1. 特征离在线一致性是底线，用统一的 Feature Store 保证
2. 模型上线必过评估门禁 + A/B 验证，别裸奔上线
3. Registry 记录训练配置 + 数据版本 + 代码 commit，出问题能回溯
4. 监控四维度（性能/资源/效果/漂移）缺一不可
5. 灰度放量逐步推进，保留一键回滚能力
6. 自动化流水线要有失败告警和人工介入点

### 踩坑记录

```text
坑 1：训练和服务的特征口径不一致
结论：离线 AUC 很高，线上效果差，甚至出现特征穿越。
原因：训练用 Spark 批算，服务用实时特征，计算逻辑没统一。
解法：Feature Store 统一特征定义，离在线同一套逻辑。

坑 2：模型直接全量上线
结论：线上指标突然恶化，回滚手忙脚乱。
原因：没做灰度 + A/B，问题模型直接覆盖全量流量。
解法：Canary 5% 灰度 → 观察指标 → 逐步放量，保留回滚。

坑 3：Registry 只登记模型不记元数据
结论：线上出问题，不知道这个模型用什么数据、什么配置训的。
原因：模型注册时没关联训练配置、数据版本、代码 commit。
解法：Registry 强制记录完整元数据，形成可追溯链路。

坑 4：监控只看延迟错误率
结论：模型效果已经退化，业务指标下滑很久才被发现。
原因：缺数据漂移和概念漂移监控，效果退化不告警。
解法：加 PSI 数据漂移 + 线上效果基线对比告警。

坑 5：A/B 实验流量不稳定
结论：实验结论不可信，同一个用户一会儿对照组一会儿实验组。
原因：分流没按用户维度稳定哈希，或分层没做好。
解法：用户 ID 稳定哈希分流，分层实验避免相互污染。
```
