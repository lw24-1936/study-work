## 概述

测试与质量工具链保证代码「正确」且「整洁」：pytest 驱动自动化测试，coverage 度量覆盖率，hypothesis 做基于性质的测试，ruff/black 统一代码风格，pre-commit 把它们串成提交前的自动门禁。算法工程师的代码要经得起重构和上线，测试是底线。

```text
质量保障的层次：
1. 单元测试 —— pytest/unittest 验证单个函数/类的行为
2. 覆盖率 —— coverage 衡量测试覆盖了多少代码
3. 性质测试 —— hypothesis 用随机输入验证不变量
4. 风格与静态检查 —— ruff/black 统一风格、抓常见错误
5. 门禁 —— pre-commit 在每次提交前自动跑检查
```

```python
# 被测代码（src/calc.py）
def add(a, b):
    return a + b

def divide(a, b):
    if b == 0:
        raise ValueError("除数不能为 0")
    return a / b
```

## Pytest

`pytest` 是 Python 事实上的测试标准：用 `test_` 前缀函数发现测试，`assert` 断言，失败时给出丰富的上下文。它比 unittest 更简洁，插件生态（覆盖率、参数化、fixture）极其丰富。

```python
# test_calc.py
import pytest
from calc import add, divide

def test_add():
    assert add(2, 3) == 5

def test_divide():
    assert divide(10, 2) == 5.0

def test_divide_by_zero():
    with pytest.raises(ValueError):
        divide(1, 0)

@pytest.mark.parametrize("a,b,expected", [(1, 2, 3), (-1, 1, 0), (0, 0, 0)])
def test_add_param(a, b, expected):
    assert add(a, b) == expected
```

```text
pytest 要点：
1. 测试函数/文件以 test_ 开头，pytest 自动发现
2. pytest.raises 断言抛出的异常
3. @pytest.mark.parametrize 一次跑多组参数
```

## Unittest

`unittest` 是标准库自带的测试框架，基于类组织：继承 `TestCase`，用 `assertXxx` 方法断言。它风格偏 Java/JUnit，功能完整但样板代码多。老项目仍大量使用，新项目多倾向 pytest。

```python
import unittest
from calc import add, divide

class TestCalc(unittest.TestCase):
    def test_add(self):
        self.assertEqual(add(2, 3), 5)

    def test_divide(self):
        self.assertAlmostEqual(divide(1, 3), 0.333333, places=5)

    def test_divide_by_zero(self):
        with self.assertRaises(ValueError):
            divide(1, 0)

if __name__ == "__main__":
    unittest.main()
```

```text
unittest vs pytest：
1. unittest —— 标准库、类式组织、assertXxx 方法、样板多
2. pytest —— 第三方、函数式、assert 原生、简洁强大
3. pytest 能直接跑 unittest 写的测试，两者可共存
```

## Fixture

fixture 是 pytest 里准备测试前置条件（数据、对象、环境）的机制：用 `@pytest.fixture` 定义，测试函数以参数方式注入。它把「准备 → 测试 → 清理」的样板代码集中管理，支持作用域（function/class/module/session）。

```python
import pytest

@pytest.fixture
def sample_data():
    """准备测试数据，测试结束后清理。"""
    data = {"features": [1.0, 2.0, 3.0], "label": 1}
    yield data          # yield 前是准备，yield 后是清理
    data.clear()        # 清理

def test_data_shape(sample_data):
    assert len(sample_data["features"]) == 3

@pytest.fixture(scope="module")
def heavy_model():
    """module 作用域：整个模块只初始化一次，省去重复开销。"""
    return {"weights": [0.1, 0.2]}

def test_model_1(heavy_model):
    assert sum(heavy_model["weights"]) == pytest.approx(0.3)

def test_model_2(heavy_model):
    assert len(heavy_model["weights"]) == 2
```

```text
fixture 要点：
1. yield 语法分「准备」和「清理」两段
2. scope 控制生命周期，module/session 可复用昂贵资源
3. fixture 之间可依赖，自动按依赖顺序执行
```

## Mock

mock 用假对象替换真实依赖（网络、数据库、外部服务），隔离被测单元、控制返回值和验证调用。`unittest.mock.Mock` 和 `patch` 是核心，`@patch` 装饰器临时替换对象。

```python
from unittest.mock import Mock, patch

def fetch_price(client, symbol):
    return client.get(symbol)["price"]

# 手动注入假对象
fake = Mock()
fake.get.return_value = {"price": 100}
print(fetch_price(fake, "AAPL"))   # 100
fake.get.assert_called_once_with("AAPL")   # 验证调用

# 用 patch 替换模块里的真实对象
def load_data():
    import httpx
    return httpx.get("http://api/data")

with patch("httpx.get") as mock_get:
    mock_get.return_value.json.return_value = {"rows": 3}
    print(mock_get.return_value.json())    # {'rows': 3}
```

```text
mock 三件事：
1. 替换 —— 用假对象隔离外部依赖
2. 控制 —— 设定返回值/副作用，构造测试场景
3. 验证 —— assert_called_with 等检查调用行为
```

## Coverage

coverage 度量测试覆盖了代码的多少比例（行、分支）。`coverage run` 跑测试并采集数据，`coverage report` 输出报告。它帮你找到「没被测到的死角和风险代码」，是提升测试质量的导航图。

```bash
coverage run -m pytest tests/     # 采集覆盖率
coverage report                   # 命令行报告
coverage html                     # 生成 HTML 报告，可视化查看
```

```text
覆盖率指标：
1. 行覆盖率 —— 被执行到的代码行占比
2. 分支覆盖率 —— 被走到过的分支占比（更严格）
3. 覆盖率是必要条件不是充分条件，100% 不等于没问题
```

## Property-based Testing

基于性质的测试不写具体输入，而是声明「性质」（不变量），由工具自动生成大量随机输入验证。它比手写样例更能发现边界 bug，尤其适合算法函数（排序、编码、数值计算）。

```text
性质测试 vs 示例测试：
1. 示例测试 —— 固定输入，验证固定输出，覆盖面窄
2. 性质测试 —— 声明不变量，随机生成输入，覆盖面广
3. 性质示例：排序后有序、编码解码可逆、面积恒正
```

```python
from hypothesis import given, strategies as st

# 性质：任何列表排序后都是升序的
@given(st.lists(st.integers()))
def test_sorted_is_ordered(lst):
    result = sorted(lst)
    assert all(result[i] <= result[i + 1] for i in range(len(result) - 1))
```

## Hypothesis

Hypothesis 是 Python 主流的性质测试库：`@given` 声明输入策略（strategies），自动生成、收缩（shrink）最小反例。当性质被破坏时，它给出能复现的最小失败输入，是定位边界 bug 的利器。

```python
from hypothesis import given, strategies as st

# 性质：编码后再解码应还原（往返一致）
def encode(s: str) -> bytes:
    return s.encode("utf-8")

def decode(b: bytes) -> str:
    return b.decode("utf-8")

@given(st.text())
def test_roundtrip(s):
    assert decode(encode(s)) == s

# 性质：除法不改变符号（b 非 0 时）
@given(st.integers(), st.integers().filter(lambda x: x != 0))
def test_division_sign(a, b):
    assert (a / b > 0) == (a * b > 0)
```

```text
Hypothesis 的核心能力：
1. strategies —— 丰富的输入生成器（整数、文本、列表、自定义组合）
2. 收缩 shrink —— 失败时自动找最小反例
3. 反例缓存 —— 上次失败的输入会被记住，回归时优先重放
```

## Lint

Lint 指静态代码检查，找出未使用的变量、未定义的名称、潜在 bug 和风格问题。它不运行代码，只看源码结构。Python 的 lint 工具从早期的 pylint/flake8 演进到极速的 ruff。

```text
Lint 检查的典型问题：
1. 未使用的导入/变量
2. 未定义的名称（拼写错误）
3. 过长的行、命名不规范
4. 可能出错的写法（如 == 写成了 =）
```

```python
# 这些会被 lint 抓到
def buggy(x):
    unused = 10           # 未使用变量
    result = x + y        # y 未定义
    return result
```

## Ruff

`ruff` 是 Rust 写的极速 linter + formatter，一个工具替代 flake8/pylint/isort 的检查能力，速度比它们快数十倍。它集成了数百条规则（按类别分组），还能自动修复大部分问题。

```bash
ruff check .                 # 检查整个项目
ruff check --fix .           # 自动修复能修的问题
ruff format .                # 格式化代码（替代 black）
```

```text
ruff 的规则分组（可在 pyproject.toml 选择）：
[tool.ruff]
line-length = 88
[tool.ruff.lint]
select = ["E", "F", "I", "N", "UP"]   # 错误/未定义/导入排序/命名/升级
```

## Black

`black` 是「不妥协」的代码格式化工具：不做任何可配置的风格选择，把代码格式化为唯一的标准形式。它消灭了团队里关于格式的争论，让 diff 干净、风格统一。

```bash
black .                # 格式化整个项目
black --check .        # 只检查不修改（CI 用）
black --diff .         # 显示会做的修改
```

```python
# 格式化前（乱）
def f(  x,y   ):
    return  {  'a':x,'b':y}

# black 格式化后
def f(x, y):
    return {"a": x, "b": y}
```

```text
black 的设计哲学：
1. 零配置 —— 唯一标准格式，不争论、不纠结
2. 行宽默认 88，但可配置
3. 与 ruff format 兼容，二选一即可
```

## Pre-commit

`pre-commit` 是 git 钩子管理工具：在每次 `git commit` 前自动运行一组检查（格式化、lint、测试），不通过就阻止提交。它把质量门禁前移到本地提交点，坏代码进不了仓库。

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.4.0
    hooks:
      - id: ruff
      - id: ruff-format
  - repo: https://github.com/psf/black
    rev: 24.4.0
    hooks:
      - id: black
```

```bash
pre-commit install     # 安装 git 钩子
pre-commit run --all-files   # 手动全量运行
git commit -m "..."    # 之后每次提交自动触发
```

```text
pre-commit 的价值：
1. 门禁前移 —— 提交前就发现问题，CI 不再兜底
2. 团队统一 —— 所有人在同一套规则下提交
3. 快速反馈 —— 本地秒级检查，比 CI 等待快得多
```

## 应用场景实战

### 场景一：算法函数的完整测试（fixture + parametrize）

```python
import pytest

def softmax(scores):
    exps = [2.71828 ** s for s in scores]
    total = sum(exps)
    return [e / total for e in exps]

@pytest.fixture
def sample_scores():
    return [1.0, 2.0, 3.0]

def test_softmax_sums_to_one(sample_scores):
    probs = softmax(sample_scores)
    assert sum(probs) == pytest.approx(1.0, rel=1e-3)

@pytest.mark.parametrize("scores", [[0.0, 0.0], [5.0, 5.0], [-1.0, -1.0]])
def test_softmax_ties(scores):
    probs = softmax(scores)
    assert probs[0] == pytest.approx(probs[1])
```

### 场景二：用 mock 隔离外部依赖 + 覆盖率采集

```python
from unittest.mock import patch

def predict_with_service(client, features):
    resp = client.post("http://model/api", json=features)
    return resp.json()["prediction"]

def test_predict_with_service():
    fake_client = __import__("unittest.mock").Mock()
    fake_client.post.return_value.json.return_value = {"prediction": 0.83}
    result = predict_with_service(fake_client, {"f1": 1.0})
    assert result == 0.83
    fake_client.post.assert_called_once()
```

## 最佳实践与踩坑记录

### 最佳实践

1. 测试函数命名描述行为（test_divide_by_zero），而非 test_1、test_2
2. 一个测试只验证一件事，失败时定位清晰
3. 昂贵资源（模型、连接）用 module/session 级 fixture 复用
4. 外部依赖一律 mock，测试要快、要稳定、要可重复
5. 覆盖率盯「未覆盖分支」而非单纯刷到 100%
6. 关键算法函数用 hypothesis 验证不变量，抓边界 bug
7. pre-commit 挂 ruff + black，把风格问题挡在提交前

### 踩坑记录

```text
坑 1：测试依赖执行顺序
结论：测试之间共享状态，跑的顺序不同结果不同。
原因：测试间通过全局变量或可变 fixture 耦合。
解法：每个测试独立准备数据，用 fixture 隔离，不依赖顺序。

坑 2：mock 过度导致「测了个寂寞」
结论：把核心逻辑也 mock 掉了，测试全绿但实际是坏的。
原因：mock 的边界没划清，连被测单元本身都被替换。
解法：只 mock 外部依赖，被测逻辑用真实实现跑。

坑 3：只看覆盖率数字
结论：100% 覆盖率的代码仍有 bug，覆盖率被当成 KPI。
原因：覆盖率只说明「执行过」，不代表「验证了正确性」。
解法：关注断言质量，用 hypothesis 和边界测试补盲区。

坑 4：pre-commit 没装就提交
结论：本地能提交，坏代码推到 CI 才被发现，反馈慢。
原因：克隆仓库后没跑 pre-commit install。
解法：README 写明 pre-commit install 步骤，CI 也兜底检查。

坑 5：float 断言用 ==
结论：浮点运算 0.1 + 0.2 == 0.3 断言失败，测试误报。
原因：浮点精度误差导致判等失败。
解法：用 pytest.approx 或 math.isclose 做近似断言。
```
