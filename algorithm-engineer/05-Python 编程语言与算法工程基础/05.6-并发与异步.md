## 概述

并发与异步是 Python 里提升吞吐的三大手段：多线程、多进程、协程。它们解决的是同一个问题——让程序在等待 IO 或压榨 CPU 时别闲着，但各自的适用场景完全不同。理解 GIL 和 CPU-bound / IO-bound 的区分，是选对工具的前提。

```text
Python 并发三大模型：
1. 多线程 threading —— 共享内存，受 GIL 限制，适合 IO-bound
2. 多进程 multiprocessing —— 独立内存，绕过 GIL，适合 CPU-bound
3. 协程 asyncio —— 单线程事件循环，超高并发 IO，适合网络请求

选型口诀：
IO 密集 → 协程 or 线程；CPU 密集 → 进程
```

```python
import time
import threading

# 最小多线程示例：两个线程并行执行
def worker(name, delay):
    time.sleep(delay)
    print(f'{name} 完成')

t1 = threading.Thread(target=worker, args=('A', 1))
t2 = threading.Thread(target=worker, args=('B', 1))
t1.start(); t2.start()
t1.join(); t2.join()   # 总耗时约 1 秒而非 2 秒
```

## GIL

GIL（Global Interpreter Lock，全局解释器锁）是 CPython 的解释器级互斥锁：同一时刻只允许一个线程执行 Python 字节码。它是多线程无法加速 CPU 密集计算的根源。

```text
GIL 的关键事实：
1. 只锁字节码 —— 同一时刻只有一个线程跑 Python 代码
2. IO 不占锁 —— 线程在等待 IO 时会释放 GIL，所以 IO 密集多线程有效
3. 只影响 CPython —— PyPy、Jython 无 GIL；CPython 3.13 起可选禁用
4. 绕过方式 —— 用多进程，或把重计算下沉到 C 扩展（NumPy）里释放 GIL
```

```python
import threading
import time

# 证明 GIL：CPU 密集任务多线程并不比单线程快
def count(n=50_000_000):
    s = 0
    for i in range(n):
        s += i
    return s

start = time.perf_counter()
count(); count()
print(f'单线程耗时: {time.perf_counter() - start:.2f}s')

start = time.perf_counter()
ts = [threading.Thread(target=count) for _ in range(2)]
[t.start() for t in ts]; [t.join() for t in ts]
print(f'双线程耗时: {time.perf_counter() - start:.2f}s')  # 反而更慢（切换开销）
```

## threading

threading 是共享内存的多线程模型。线程间共享全局变量，靠 Lock、RLock、Event、Semaphore 等原语协调，适合 IO 密集任务（网络、文件、数据库）。

```text
threading 常用原语：
1. Thread —— 创建线程，start/join
2. Lock —— 互斥锁，保护临界区
3. RLock —— 可重入锁，同一线程可多次 acquire
4. Event —— 线程间信号通知
5. Semaphore —— 限流，控制并发数量
```

```python
import threading

# 用 Lock 保护共享计数器
counter = 0
lock = threading.Lock()

def increment(n=100_000):
    global counter
    for _ in range(n):
        with lock:            # 不加锁会得到错误结果（竞态）
            counter += 1

ts = [threading.Thread(target=increment) for _ in range(8)]
[t.start() for t in ts]; [t.join() for t in ts]
print(counter)   # 800000，正确；去掉 lock 会小于该值
```

## Queue

queue.Queue 是线程安全的 FIFO 队列，是「生产者-消费者」模式的标配。它内置锁和条件变量，多个线程同时 put/get 也安全，常配合 task_done 和 join 实现优雅退出。

```text
Queue 的核心方法：
1. put(item) —— 入队，队列满时默认阻塞
2. get() —— 出队，队列空时默认阻塞
3. task_done() —— 标记一个任务处理完成
4. join() —— 阻塞直到所有任务都被 task_done
5. maxsize —— 队列容量上限，实现背压
```

```python
import queue
import threading
import time

q = queue.Queue(maxsize=10)

def producer():
    for i in range(20):
        q.put(i)          # 队列满会自动阻塞，形成背压
        print(f'生产 {i}')

def consumer():
    while True:
        item = q.get()
        print(f'消费 {item}')
        time.sleep(0.1)
        q.task_done()

threading.Thread(target=producer).start()
threading.Thread(target=consumer, daemon=True).start()
q.join()                  # 等所有任务被消费完
print('全部完成')
```

## multiprocessing

multiprocessing 是独立内存的多进程模型，每个进程有自己的解释器和 GIL，因此能真正并行地跑满多核 CPU，是 CPU 密集任务的正确选择。代价是进程创建开销大、数据要序列化传递。

```text
multiprocessing 核心：
1. Process —— 创建子进程
2. Pool —— 进程池，map/apply_async 批量分发任务
3. Queue / Pipe —— 进程间通信（IPC）
4. Manager —— 跨进程共享的代理对象（慢，慎用）
5. 数据传递要 pickle 序列化 —— 传大对象有开销
```

```python
import multiprocessing as mp
import time

def heavy(n=30_000_000):
    return sum(i * i for i in range(n))

if __name__ == '__main__':
    start = time.perf_counter()
    with mp.Pool(processes=4) as pool:
        results = pool.map(heavy, [30_000_000] * 4)
    print(f'4 进程耗时: {time.perf_counter() - start:.2f}s')  # 约等于单任务时间
```

## concurrent.futures

concurrent.futures 是对线程和进程的统一高层抽象，提供 ThreadPoolExecutor 和 ProcessPoolExecutor。它把「提交任务」和「取回结果」解耦成 Future 对象，map / submit / as_completed 三件套覆盖绝大多数场景。

```text
concurrent.futures 优点：
1. 统一接口 —— 线程池/进程池只换一个类名
2. Future —— 异步结果句柄，可取消、可查状态
3. as_completed —— 谁先完成谁先处理，不用等慢任务
4. 自动管理 —— with 语句自动 shutdown，回收资源
```

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor, as_completed
import time

def fetch(url_id):
    time.sleep(0.5)            # 模拟 IO
    return f'url-{url_id} -> 200'

# IO 密集用线程池
with ThreadPoolExecutor(max_workers=8) as ex:
    futures = [ex.submit(fetch, i) for i in range(10)]
    for f in as_completed(futures):      # 完成一个打印一个
        print(f.result())

# CPU 密集换进程池，一行改动
def cpu(n):
    return sum(i * i for i in range(n))

with ProcessPoolExecutor(max_workers=4) as ex:
    print(list(ex.map(cpu, [5_000_000] * 4)))
```

## asyncio

asyncio 是单线程的协程并发模型：一个事件循环（event loop）在单个线程里调度成千上万个协程，靠「遇到 await 就切走」实现高并发，没有线程切换和锁的开销，是网络 IO 场景的王者。

```text
asyncio 关键概念：
1. 事件循环 —— 调度器，循环查询哪些协程可继续执行
2. 协程 —— async def 定义的函数，await 处让出控制权
3. Task —— 协程的调度单元，create_task 并发执行
4. gather —— 并发等待多个协程并收集结果
5. 前提 —— 必须用异步 IO 库（aiohttp、httpx.AsyncClient），否则会阻塞循环
```

```python
import asyncio

async def fetch(i):
    await asyncio.sleep(1)     # 模拟异步 IO，期间让出事件循环
    return f'task {i} done'

async def main():
    # gather 并发跑 5 个协程，总耗时约 1 秒
    results = await asyncio.gather(*[fetch(i) for i in range(5)])
    print(results)

asyncio.run(main())
```

## async / await

async 定义协程，await 挂起当前协程等待一个可等待对象（协程 / Task / Future）。协程不是线程：它只在显式 await 时切换，同一时刻只有一个协程在跑，因此无需加锁，但也不能执行阻塞代码。

```text
async / await 使用要点：
1. async def 定义协程，调用它只返回协程对象，不会执行
2. await 挂起并等待结果，是唯一的让出点
3. 三个可等待对象 —— 协程、Task、Future
4. 别在协程里调阻塞函数（time.sleep、requests）—— 会卡死整个循环
5. 阻塞代码用 await asyncio.to_thread() 丢到线程池
```

```python
import asyncio
import time

# 常见错误示范 vs 正确示范
async def bad():
    time.sleep(1)          # 阻塞！整个事件循环卡住

async def good():
    await asyncio.sleep(1) # 正确，非阻塞

async def blocking_call():
    # 把阻塞的 CPU/同步代码丢到线程池
    result = await asyncio.to_thread(time.sleep, 1)
    return result

async def demo():
    # 用 Task 手动调度
    t1 = asyncio.create_task(good())
    t2 = asyncio.create_task(good())
    await t1; await t2

asyncio.run(demo())
```

## CPU-bound / IO-bound

任务按瓶颈分成两类：CPU-bound 任务瓶颈在算力（数值计算、图像处理、模型推理），IO-bound 任务瓶颈在等待（网络、磁盘、数据库）。这个分类直接决定并发方案选型，是性能优化的第一判断。

```text
任务分类与选型对照：
1. CPU-bound → 多进程（multiprocessing / ProcessPoolExecutor）
2. IO-bound（低并发）→ 多线程（threading / ThreadPoolExecutor）
3. IO-bound（高并发）→ 协程（asyncio）
4. 混合任务 → 进程 + 协程组合（每个进程内跑事件循环）
```

```python
import time

# 用一段代码判断任务属于哪类：跑满单核就是 CPU-bound，空闲等 IO 就是 IO-bound
def classify(fn, *args):
    start = time.perf_counter()
    fn(*args)
    elapsed = time.perf_counter() - start
    return elapsed

def cpu_task():
    return sum(i * i for i in range(20_000_000))

def io_task():
    time.sleep(2)

print(f'CPU 任务耗时: {classify(cpu_task):.2f}s')  # 时间都在算
print(f'IO 任务耗时: {classify(io_task):.2f}s')    # 时间都在等
```

## 应用场景实战

### 场景一：批量下载（IO-bound → asyncio）

```python
import asyncio
import httpx
import time

URLS = [f'https://httpbin.org/delay/1?id={i}' for i in range(20)]

async def download(client, url):
    r = await client.get(url, timeout=10)
    return r.status_code

async def main():
    async with httpx.AsyncClient() as client:
        # 20 个请求并发，总耗时约 1 秒而不是 20 秒
        codes = await asyncio.gather(*[download(client, u) for u in URLS])
    print(codes)

start = time.perf_counter()
asyncio.run(main())
print(f'总耗时 {time.perf_counter() - start:.2f}s')
```

### 场景二：矩阵运算加速（CPU-bound → multiprocessing）

```python
import numpy as np
import multiprocessing as mp
import time

def matmul_seed(seed):
    np.random.seed(seed)
    a = np.random.randn(2000, 2000)
    b = np.random.randn(2000, 2000)
    return float((a @ b).sum())

if __name__ == '__main__':
    start = time.perf_counter()
    with mp.Pool(processes=4) as pool:
        pool.map(matmul_seed, range(4))
    print(f'4 进程矩阵乘法 {time.perf_counter() - start:.2f}s')
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先判断任务类型（CPU-bound 还是 IO-bound）再选并发方案，别一上来就开线程
2. 网络 IO 高并发场景优先 asyncio + aiohttp/httpx，几千并发毫无压力
3. CPU 密集任务用 multiprocessing 或 ProcessPoolExecutor，进程数不超过 CPU 核数
4. 线程共享数据必须加锁，优先用 queue.Queue 而不是裸列表 + 手写锁
5. 用 concurrent.futures 做高层封装，可读性和可维护性最好
6. 多进程入口必须加 `if __name__ == '__main__':`，否则会无限递归 spawn

### 踩坑记录

```text
坑 1：用多线程加速 CPU 密集任务
结论：开了 8 个线程，耗时反而比单线程更久。
原因：GIL 限制同一时刻只有一个线程执行字节码，线程切换还带来额外开销。
解法：CPU 密集用多进程，或把计算下沉到 NumPy/C 扩展释放 GIL。

坑 2：在协程里调用 requests / time.sleep
结论：整个事件循环被阻塞，所有协程全部卡死，并发退化成串行。
原因：同步阻塞调用不会让出事件循环，单线程被占满。
解法：换 httpx.AsyncClient / aiohttp，或用 asyncio.to_thread 包裹阻塞调用。

坑 3：多进程脚本忘记 if __name__ == '__main__'
结论：Windows 和 spawn 模式下子进程无限递归创建，直接崩溃。
原因：子进程会重新 import 主模块，顶层代码被反复执行。
解法：多进程入口一律包在 if __name__ == '__main__' 里。

坑 4：线程间用裸 list 共享数据不加锁
结论：计数器结果偏小，偶发数据损坏，且难以复现。
原因：i += 1 不是原子操作，读改写三步被线程切换打断。
解法：用 queue.Queue 或加 Lock，避免手写无锁共享结构。

坑 5：进程池传超大对象
结论：多进程比单进程还慢，内存暴涨。
原因：对象要 pickle 序列化传给子进程，大数组复制开销巨大。
解法：用共享内存（multiprocessing.shared_memory）或传小对象、在子进程内加载。
```
