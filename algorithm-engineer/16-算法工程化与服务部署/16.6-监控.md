## 概述

模型上线后，监控是保证它持续健康运行的眼睛。要监控两类东西：系统指标（延迟、吞吐、错误率、GPU/内存利用率，回答「服务跑得快不快、稳不稳」）和模型指标（数据漂移、概念漂移、模型性能，回答「模型还准不准」）。Prometheus + Grafana 是事实标准的技术栈，OpenTelemetry 提供统一的埋点与链路追踪。

```text
监控的两大维度：
1. 系统指标 —— 延迟/吞吐/错误率/GPU/内存，服务是否健康
2. 模型指标 —— 漂移/性能，模型效果是否退化
3. 技术栈 —— Prometheus 采集存储，Grafana 可视化告警
4. 可观测性 —— OpenTelemetry 统一 metrics/traces/logs
```

```python
# 一个带基础埋点的模型服务
import time
from prometheus_client import Counter, Histogram

REQUESTS = Counter("requests_total", "总请求数")
LATENCY = Histogram("predict_latency_seconds", "推理延迟")

def predict_with_metrics(model, x):
    REQUESTS.inc()
    with LATENCY.time():
        return model(x)
```

## Latency

延迟（Latency）是单个请求从发出到收到响应的时间。模型服务里关键看分位数：P50（中位数）、P95、P99。P99 尤其重要——它代表「最慢的那 1% 用户」的体验。延迟的组成包括网络传输、排队等待、模型推理、后处理，需要分段测量定位瓶颈。

```text
延迟的关键点：
1. 分位数 —— P50/P95/P99，P99 决定长尾体验
2. 组成 —— 网络 + 排队 + 推理 + 序列化
3. 影响因素 —— batch 大小、并发数、GPU 繁忙度
4. 与吞吐的关系 —— 延迟和吞吐是一对矛盾，需权衡
```

```python
import time
import numpy as np

def measure_latency(fn, n=1000):
    """测量推理延迟的分位数"""
    latencies = []
    for _ in range(n):
        t0 = time.perf_counter()
        fn()
        latencies.append(time.perf_counter() - t0)
    arr = np.array(latencies) * 1000  # 转毫秒
    return {
        "p50": np.percentile(arr, 50),
        "p95": np.percentile(arr, 95),
        "p99": np.percentile(arr, 99),
        "mean": arr.mean(),
    }

def fake_infer():
    time.sleep(0.002)          # 模拟 2ms 推理

stats = measure_latency(fake_infer, n=500)
for k, v in stats.items():
    print(f"{k}: {v:.2f} ms")
```

## Throughput

吞吐（Throughput）是单位时间能处理的请求数或数据量，通常用 QPS（每秒请求数）或 tokens/s（LLM 场景）衡量。它决定需要多少资源、多少副本。吞吐和延迟通常负相关——batch 越大吞吐越高，但单条延迟也越高，需要在二者间找到业务可接受的平衡点。

```text
吞吐的关键点：
1. QPS —— 每秒请求数，衡量服务容量
2. tokens/s —— LLM 场景的生成吞吐
3. 与 batch 关系 —— 大 batch 提吞吐、增延迟
4. 扩容依据 —— 吞吐压测决定副本数
```

```python
import time

def measure_throughput(fn, n=1000, concurrency=1):
    """测量吞吐（QPS）"""
    t0 = time.perf_counter()
    for _ in range(n):
        fn()
    elapsed = time.perf_counter() - t0
    return n / elapsed          # QPS

def fake_infer():
    x = sum(range(1000))

qps = measure_throughput(fake_infer, n=2000)
print(f"吞吐: {qps:.0f} QPS")
```

## Error Rate

错误率（Error Rate）是失败请求占总请求的比例。对模型服务，错误包括：4xx（参数错误）、5xx（服务内部错误）、超时、模型返回异常值。错误率飙升通常是服务故障或模型 bug 的信号，是需要告警的核心指标之一。

```text
错误率的关键点：
1. 计算 —— 错误请求数 / 总请求数
2. 分类 —— 4xx 客户端错、5xx 服务端错、超时
3. 告警阈值 —— 通常错误率 > 1% 就要告警
4. 关联 —— 错误率常和延迟、资源一起看定位根因
```

```python
from prometheus_client import Counter

# 错误率埋点：分别统计总请求和错误请求
REQUESTS = Counter("requests_total", "总请求数", ["status"])
ERRORS = Counter("request_errors_total", "错误请求数", ["error_type"])

def predict(req):
    REQUESTS.labels(status="ok").inc()
    try:
        result = model_infer(req)
    except TimeoutError:
        ERRORS.labels(error_type="timeout").inc()
        REQUESTS.labels(status="timeout").inc()
        raise
    except Exception:
        ERRORS.labels(error_type="internal").inc()
        REQUESTS.labels(status="error").inc()
        raise
    return result

def model_infer(req):
    return req
```

## GPU Utilization

GPU 利用率（GPU Utilization）衡量 GPU 计算单元的使用比例，是判断「GPU 是否被充分使用 / 是否成为瓶颈」的关键指标。但要注意：利用率高不代表效率高，还要看显存带宽利用率、是否空转等待数据。推理服务要同时关注 GPU 利用率（算力）和显存占用（容量）。

```text
GPU 利用率的关键点：
1. 利用率 —— GPU 计算单元使用百分比
2. 显存 —— 已用/总显存，决定能不能放更多模型
3. 空转 —— 利用率低可能是数据供给不足（IO bound）
4. 监控工具 —— nvidia-smi、DCGM 导出到 Prometheus
```

```bash
# nvidia-smi 查看 GPU 状态
nvidia-smi
# 持续监控
nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total --format=csv -l 1
```

## Memory

内存（Memory）监控包括系统内存和显存两类。内存泄漏是模型服务最常见的慢性问题——内存随时间缓慢增长，最终 OOM 崩溃。监控要关注：当前用量、增长趋势（是否泄漏）、是否接近上限。配合 GC 和对象生命周期分析定位泄漏源。

```text
内存监控的关键点：
1. 系统内存 —— 进程 RSS，检测泄漏
2. 显存 —— GPU 显存占用，多模型共享时的容量规划
3. 趋势 —— 内存只涨不跌 = 疑似泄漏
4. OOM —— 接近上限要告警，提前扩容或优化
```

```python
import psutil
import os

def report_memory():
    process = psutil.Process(os.getpid())
    rss = process.memory_info().rss / 1024**2      # MB
    vms = process.memory_info().vms / 1024**2
    sys_mem = psutil.virtual_memory()
    print(f"进程 RSS: {rss:.0f} MB, VMS: {vms:.0f} MB")
    print(f"系统内存: {sys_mem.percent}% 已用")

# 检测泄漏：间隔采样，观察 RSS 趋势
import time
for i in range(5):
    report_memory()
    time.sleep(1)
```

## Data Drift

数据漂移（Data Drift）是输入特征分布随时间发生了变化。比如用户年龄分布、商品价格分布变了。模型是在历史数据上训练的，输入分布变了，模型假设就可能失效。检测方法是对比「训练时的特征分布」和「线上当前的特征分布」的统计距离（PSI、KS、KL 散度）。

```text
数据漂移的关键点：
1. 定义 —— 输入特征分布变化
2. 原因 —— 用户群变化、季节变化、业务调整
3. 检测 —— PSI、KS、KL 散度等分布距离
4. 应对 —— 漂移超阈值触发重训练或人工核查
```

```python
import numpy as np

def psi(expected, actual, bins=10):
    """PSI（Population Stability Index）检测分布漂移"""
    expected = np.asarray(expected)
    actual = np.asarray(actual)
    # 按期望分布分箱
    edges = np.percentile(expected, np.linspace(0, 100, bins + 1))
    e_ratio, _ = np.histogram(expected, bins=edges)
    a_ratio, _ = np.histogram(actual, bins=edges)
    e_ratio = e_ratio / e_ratio.sum() + 1e-10
    a_ratio = a_ratio / a_ratio.sum() + 1e-10
    return float(np.sum((a_ratio - e_ratio) * np.log(a_ratio / e_ratio)))

# 训练时分布 vs 线上分布
train_feature = np.random.normal(0, 1, 10000)
online_feature = np.random.normal(0.5, 1.2, 10000)   # 分布漂移了
print(f"PSI: {psi(train_feature, online_feature):.4f}")
# PSI > 0.2 通常认为发生显著漂移
```

## Concept Drift

概念漂移（Concept Drift）是「输入到输出的映射关系」发生了变化，即同一个输入，正确答案变了。比如「用户对某类商品感兴趣」的规律变了、欺诈手段进化了。它比数据漂移更隐蔽——输入分布可能没变，但标签的规律变了，只能靠「预测 vs 真实标签」的持续对比来发现。

```text
概念漂移的关键点：
1. 定义 —— 输入到输出的关系变化（P(y|x) 变化）
2. 与数据漂移区别 —— 数据漂移是 P(x) 变，概念漂移是 P(y|x) 变
3. 检测 —— 需要真实标签反馈，持续对比预测准确率
4. 应对 —— 在线学习、定期重训练、缩短模型更新周期
```

```python
# 概念漂移检测：滑动窗口监控预测准确率
from collections import deque

class ConceptDriftMonitor:
    def __init__(self, window_size=1000):
        self.window = deque(maxlen=window_size)
        self.baseline_acc = 0.85

    def update(self, y_pred, y_true):
        """每来一个带真实标签的样本，更新准确率"""
        self.window.append(1 if y_pred == y_true else 0)

    def current_acc(self):
        if not self.window:
            return self.baseline_acc
        return sum(self.window) / len(self.window)

    def drifted(self, threshold=0.05):
        """当前准确率比基线掉超过阈值，判定漂移"""
        return (self.baseline_acc - self.current_acc()) > threshold

monitor = ConceptDriftMonitor()
# 模拟：概念漂移后预测越来越不准
import random
random.seed(0)
for i in range(500):
    correct = random.random() > (0.15 + 0.0006 * i)   # 准确率逐渐下降
    monitor.update(1 if correct else 0, 1)
print(f"当前准确率: {monitor.current_acc():.3f}")
print(f"发生概念漂移: {monitor.drifted()}")
```

## Model Performance

模型性能（Model Performance）监控是指持续追踪模型在实际业务上的效果指标（准确率、AUC、F1、业务转化率等）。它需要「真实标签反馈」，但很多场景标签有延迟（如推荐点击、风控逾期），所以要设计延迟反馈机制，把线上结果和后续真实标签关联起来做持续评估。

```text
模型性能监控的关键点：
1. 指标 —— 准确率/AUC/F1/业务指标（转化、留存）
2. 标签反馈 —— 真实标签可能延迟，需关联机制
3. 持续评估 —— 定期（如每天）用新样本重算指标
4. 趋势 —— 指标持续下滑 = 模型退化信号
```

```python
# 模型性能的持续评估
class PerformanceTracker:
    def __init__(self):
        self.predictions = []
        self.labels = []

    def log_prediction(self, pred_score, label=None):
        self.predictions.append(pred_score)
        if label is not None:          # 标签可能延迟到达
            self.labels.append(label)

    def compute_auc(self):
        # 简化的 AUC 计算（需真实标签齐全）
        from sklearn.metrics import roc_auc_score
        if len(self.labels) < 100:
            return None
        return roc_auc_score(self.labels, self.predictions[:len(self.labels)])

tracker = PerformanceTracker()
# 线上持续记录预测 + 延迟反馈的真实标签
for i in range(200):
    tracker.log_prediction(i / 200, 1 if i % 2 == 0 else 0)
print(f"滚动 AUC: {tracker.compute_auc():.3f}")
```

## Prometheus

Prometheus 是开源监控系统，用「拉取（pull）」模式定时从服务暴露的 /metrics 端点采集指标，用 PromQL 查询，支持告警规则。它是云原生监控的事实标准，K8s 生态原生集成。模型服务只需埋点暴露指标，Prometheus 自动采集。

```text
Prometheus 的关键点：
1. 拉取模式 —— 定时从目标 /metrics 端点拉数据
2. 指标类型 —— Counter（计数）、Gauge（瞬时值）、Histogram（分布）
3. PromQL —— 强大的查询语言做聚合、计算
4. 告警 —— Alertmanager 根据规则触发告警
```

```python
from prometheus_client import Counter, Gauge, Histogram, start_http_server

# 定义指标
REQUESTS = Counter("http_requests_total", "请求总数", ["endpoint"])
INFLIGHT = Gauge("in_flight_requests", "正在处理的请求数")
LATENCY = Histogram("http_request_duration_seconds", "请求延迟", ["endpoint"])

# 启动 metrics 端点
start_http_server(8000)     # Prometheus 会来 http://host:8000/metrics 拉取
```

## Grafana

Grafana 是开源的可视化和告警平台，连接 Prometheus 等数据源，用仪表盘（Dashboard）展示指标趋势、用告警规则触发通知。它是监控的「人机界面」——把 Prometheus 里的数据变成可看、可查、可告警的图表。

```text
Grafana 的关键点：
1. 数据源 —— 连接 Prometheus/MySQL 等多种数据源
2. 仪表盘 —— 拖拽式图表，展示延迟/吞吐/漂移趋势
3. 告警 —— 规则触发后通知到邮件/钉钉/微信
4. 面板类型 —— 时序图、Gauge、Heatmap、Table
```

```yaml
# Grafana 面板查询示例（PromQL）
# 展示 P99 延迟
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

# 展示 QPS

```

```text
推荐的模型服务监控面板：
1. 延迟面板 —— P50/P95/P99 时序图
2. 吞吐面板 —— QPS、tokens/s
3. 错误率面板 —— 4xx/5xx/超时占比
4. 资源面板 —— GPU 利用率、显存、内存
5. 漂移面板 —— 数据漂移 PSI、模型性能趋势
```

## OpenTelemetry

OpenTelemetry（OTel）是统一的可观测性标准，提供一套 API/SDK 采集 metrics（指标）、traces（链路追踪）、logs（日志），并支持导出到各种后端（Prometheus、Jaeger 等）。它的价值是「一次埋点，到处可用」，避免绑定单一厂商，是云原生可观测性的新标准。

```text
OpenTelemetry 的关键点：
1. 三大信号 —— metrics（指标）、traces（链路）、logs（日志）
2. 统一标准 —— 与后端解耦，一次埋点多后端导出
3. 自动埋点 —— 自动给框架（FastAPI 等）加追踪
4. 链路追踪 —— 跨服务追踪一次请求的完整路径
```

```python
# OpenTelemetry 埋点示例
from opentelemetry import trace, metrics
from opentelemetry.sdk.trace import TracerProvider

# 初始化 tracer
trace.set_tracer_provider(TracerProvider())
tracer = trace.get_tracer(__name__)

# 埋点：给推理函数加 span
def predict(text: str):
    with tracer.start_as_current_span("model.predict") as span:
        span.set_attribute("text.length", len(text))
        result = do_inference(text)
        span.set_attribute("score", result)
        return result

def do_inference(text):
    return 0.9
```

## 最佳实践与踩坑记录

### 最佳实践

1. 系统指标和模型指标都要监控，只监控系统指标发现不了「模型变笨了」
2. 延迟看 P99 而不是平均值，平均值会掩盖长尾问题
3. 错误率、延迟、资源三个维度联合告警，单一指标容易误报
4. 数据漂移用 PSI 定期检测，阈值触发重训练
5. 概念漂移依赖真实标签反馈，设计好延迟标签关联机制
6. 统一用 Prometheus + Grafana 采集展示，OpenTelemetry 做埋点标准化
7. 所有指标带版本标签，灰度期间能对比新旧模型表现

### 踩坑记录

```text
坑 1：只监控延迟吞吐，不监控模型效果
结论：服务跑得飞快，但模型早就漂移了，业务指标悄悄下滑。
原因：把模型服务当普通 Web 服务监控，忽略了模型指标。
解法：加数据漂移、概念漂移、模型性能三类模型指标。

坑 2：延迟只看平均值
结论：平均延迟 50ms 看起来很好，但 P99 已经 2 秒，长尾用户全跑光。
原因：平均值被大量快请求拉低，掩盖了慢请求。
解法：监控 P50/P95/P99 分位数，重点盯 P99。

坑 3：数据漂移和概念漂移混淆
结论：输入分布变了就急着重训练，结果发现模型其实没问题。
原因：没区分 P(x) 变化（数据漂移）和 P(y|x) 变化（概念漂移）。
解法：分别检测——分布距离测数据漂移，标签反馈测概念漂移。

坑 4：GPU 利用率 100% 就以为高效
结论：利用率高但吞吐上不去，可能是空转等待数据。
原因：利用率高不等于做有效计算，可能显存带宽瓶颈或 IO 等待。
解法：结合显存带宽利用率、吞吐、延迟综合判断，别只看利用率。

坑 5：内存缓慢泄漏没告警，半夜 OOM
结论：服务运行几天后突然 OOM 崩溃，重启又正常。
原因：内存趋势只涨不跌，但没设增长趋势告警。
解法：监控 RSS 增长趋势，设告警阈值，定期压测定位泄漏。
```
