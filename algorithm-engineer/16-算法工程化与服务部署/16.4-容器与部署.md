## 概述

模型服务最终要跑到生产环境，容器化是标准路径：用 Docker 把模型 + 依赖 + 运行环境打包成镜像，用 Kubernetes 编排容器在集群上调度、扩容、自愈，用 Helm 管理复杂的部署模板。容器与部署解决的核心问题是「在任意环境一致地跑起来，并稳定地跑下去」。

```text
容器化部署的分层：
1. 镜像层 —— Docker 打包应用 + 依赖，保证环境一致
2. 编排层 —— Kubernetes 调度、扩容、自愈、服务发现
3. 配置层 —— ConfigMap / Secret 注入配置，分离代码与配置
4. 网络层 —— Service / Ingress 暴露服务，GPU Scheduling 分配算力
```

```bash
# 一条命令构建并运行模型服务镜像
docker build -t model-service:v1 .
docker run --gpus all -p 8000:8000 model-service:v1
```

## Docker

Docker 用「镜像（Image）+ 容器（Container）」把应用和它的一切依赖打包，实现「一次构建，到处运行」。镜像是一层层叠加的只读文件系统，容器是镜像的运行实例。Dockerfile 是构建镜像的配方，声明基础环境、依赖安装、代码复制和启动命令。

```text
Docker 的核心概念：
1. 镜像 —— 只读的打包模板，由多层文件系统叠加
2. 容器 —— 镜像的运行实例，可启动/停止/删除
3. Dockerfile —— 声明如何构建镜像的配方文件
4. 分层缓存 —— 每层独立缓存，改代码只重建后续层
```

```text
# Dockerfile：模型服务镜像
FROM python:3.11-slim

WORKDIR /app

# 先装依赖（利用缓存：依赖不变时不重装）
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 再复制代码和模型
COPY app/ ./app/
COPY models/ ./models/

EXPOSE 8000

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```bash
# 常用 Docker 命令
docker build -t model-service:v1 .        # 构建镜像
docker images                              # 查看镜像
docker run -d --name ms -p 8000:8000 model-service:v1   # 运行容器
docker logs ms                             # 查看日志
docker exec -it ms bash                    # 进入容器
docker stop ms && docker rm ms             # 停止并删除
```

## Kubernetes

Kubernetes（K8s）是容器编排平台，负责把容器调度到多台机器上运行，并自动处理扩容、自愈、滚动更新、服务发现。它用声明式配置（YAML）描述期望状态，控制循环持续把实际状态调整到期望状态。核心对象有 Pod、Deployment、Service 等。

```text
Kubernetes 的核心对象：
1. Pod —— 最小调度单元，一个或多个容器共享网络和存储
2. Deployment —— 管理无状态应用的副本数、滚动更新、回滚
3. Service —— 给一组 Pod 提供稳定的访问入口（负载均衡）
4. Node —— 集群里的物理机/虚拟机，运行 Pod
5. Namespace —— 逻辑隔离不同环境（dev/staging/prod）
```

```yaml
# deployment.yaml —— 部署模型服务
apiVersion: apps/v1
kind: Deployment
metadata:
  name: model-service
spec:
  replicas: 3                      # 3 个副本
  selector:
    matchLabels:
      app: model-service
  template:
    metadata:
      labels:
        app: model-service
    spec:
      containers:
        - name: app
          image: model-service:v1
          ports:
            - containerPort: 8000
          resources:
            limits:
              nvidia.com/gpu: 1    # 申请 1 张 GPU
              memory: 4Gi
            requests:
              nvidia.com/gpu: 1
              memory: 2Gi
```

## Helm

Helm 是 Kubernetes 的包管理器，用「Chart」把一整套 K8s 资源（Deployment、Service、ConfigMap 等）模板化，用 values.yaml 传入不同环境的参数。它解决了「同一个应用部署到 dev/staging/prod 需要写多份几乎相同的 YAML」的问题。

```text
Helm 的核心概念：
1. Chart —— 应用的打包单元，含模板 + 默认值
2. values.yaml —— 可覆盖的配置参数
3. Release —— Chart 的一次部署实例
4. 模板渲染 —— Go template 把 values 渲染成 K8s YAML
```

```yaml
# values.yaml —— 不同环境用不同值
replicaCount: 3
image:
  repository: model-service
  tag: "v1"
gpu:
  enabled: true
  count: 1
```

```yaml
# templates/deployment.yaml —— 模板化 Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: app
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          resources:
            limits:
              nvidia.com/gpu: {{ .Values.gpu.count }}
```

```bash
# Helm 常用命令
helm install my-release ./chart          # 安装 release
helm upgrade my-release ./chart          # 升级
helm rollback my-release 1               # 回滚到版本 1
helm uninstall my-release                # 卸载
```

## GPU Scheduling

GPU 调度（GPU Scheduling）是 K8s 对 GPU 资源的管理：如何把需要 GPU 的 Pod 调度到有 GPU 的节点上，如何分配、隔离、限制 GPU。这依赖 NVIDIA 的 device plugin 把 GPU 作为可调度资源暴露给 K8s，支持整卡、MIG 分片、时间片共享等模式。

```text
GPU 调度的关键点：
1. device plugin —— nvidia-device-plugin 把 GPU 注册为 nvidia.com/gpu 资源
2. 资源申请 —— Pod 声明 resources.limits: nvidia.com/gpu: 1
3. MIG —— A100/H100 可把一张卡切成多个独立实例，细粒度分配
4. 时间片 —— 多个 Pod 共享一张 GPU，按时间片轮转
5. 拓扑感知 —— 尽量把 Pod 调度到 GPU 邻近的 CPU/内存
```

```yaml
# GPU Pod 资源声明
apiVersion: v1
kind: Pod
metadata:
  name: gpu-inference
spec:
  containers:
    - name: infer
      image: model-service:v1
      resources:
        limits:
          nvidia.com/gpu: 1        # 申请整张 GPU
```

```bash
# 查看集群 GPU 资源
kubectl get nodes -o json | jq '.items[].status.allocatable["nvidia.com/gpu"]'
kubectl describe node <gpu-node> | grep -A 5 "Allocated resources"
```

## Service Discovery

服务发现（Service Discovery）解决「服务之间怎么找到对方」的问题。在 K8s 里，Service 给一组 Pod 提供稳定的虚拟 IP 和 DNS 名，Pod 重启、扩缩容后 IP 会变，但 Service 名不变，调用方始终通过服务名访问。K8s 内置 DNS（CoreDNS）自动维护服务名到 IP 的映射。

```text
服务发现的关键点：
1. Service —— 稳定的虚拟 IP（ClusterIP）和 DNS 名
2. Label Selector —— Service 通过标签选择它代理的 Pod
3. DNS —— 集群内用 <service>.<namespace>.svc.cluster.local 访问
4. 负载均衡 —— Service 自动把流量分到后端多个 Pod
```

```yaml
# service.yaml —— 暴露模型服务
apiVersion: v1
kind: Service
metadata:
  name: model-service
spec:
  selector:
    app: model-service
  ports:
    - port: 8000
      targetPort: 8000
  type: ClusterIP        # 集群内访问
```

```python
# 应用内通过服务名访问其他服务（而非写死 IP）
import httpx

# 集群内服务发现：用服务名 + 端口
def call_feature_service(user_id: int):
    url = "http://feature-service.default.svc.cluster.local:8001/features"
    resp = httpx.get(url, params={"user_id": user_id})
    return resp.json()
```

## ConfigMap

ConfigMap 用来存「非敏感」的配置信息（如模型路径、超参、环境开关），以键值对形式注入 Pod（环境变量或挂载为文件）。它的价值是把配置和代码/镜像分离——同一个镜像，换个 ConfigMap 就能跑在不同环境、不同参数下，无需重新构建镜像。

```text
ConfigMap 的关键点：
1. 存非敏感配置 —— 模型路径、超参、开关、日志级别
2. 注入方式 —— 环境变量 or 挂载为文件
3. 热更新 —— 挂载文件方式可动态更新（需应用支持 reload）
4. 与镜像解耦 —— 改配置不改镜像
```

```yaml
# configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: model-config
data:
  MODEL_PATH: /models/bert-v1
  BATCH_SIZE: "32"
  LOG_LEVEL: info
```

```yaml
# 在 Deployment 里使用 ConfigMap
apiVersion: apps/v1
kind: Deployment
metadata:
  name: model-service
spec:
  template:
    spec:
      containers:
        - name: app
          image: model-service:v1
          envFrom:
            - configMapRef:
                name: model-config        # 全部键注入为环境变量
          volumeMounts:
            - name: config
              mountPath: /etc/model
      volumes:
        - name: config
          configMap:
            name: model-config            # 或挂载为文件
```

## Secret

Secret 用来存「敏感」信息（API key、数据库密码、模型仓库凭证），与 ConfigMap 类似但做了 Base64 编码，并设计上只给需要的 Pod 访问。它避免把密码明文写进镜像或 ConfigMap。生产环境通常再配合外部密钥管理系统（Vault、云 KMS）增强安全。

```text
Secret 的关键点：
1. 存敏感信息 —— 密码、token、证书、镜像仓库凭证
2. Base64 编码 —— 只是编码不是加密，RBAC 控制访问权限
3. 类型 —— Opaque（通用）、kubernetes.io/dockerconfigjson（镜像拉取凭证）
4. 最佳实践 —— 配合 RBAC + 外部 KMS，别只靠 Base64
```

```yaml
# secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: model-registry-cred
type: Opaque
data:
  username: YWRtaW4=        # base64("admin")
  password: c2VjcmV0       # base64("secret")
```

```bash
# 从字面量创建 Secret（自动编码）
kubectl create secret generic model-registry-cred \
  --from-literal=username=admin \
  --from-literal=password=secret
```

```yaml
# 在 Pod 里使用 Secret 作为环境变量
apiVersion: v1
kind: Pod
metadata:
  name: model-loader
spec:
  containers:
    - name: app
      image: model-service:v1
      env:
        - name: REGISTRY_USER
          valueFrom:
            secretKeyRef:
              name: model-registry-cred
              key: username
```

## Ingress

Ingress 是把集群内的服务暴露到集群外，并提供 HTTP/HTTPS 路由规则的资源。它通过域名/路径把外部请求转发到不同的 Service，通常还承担 TLS 终止、负载均衡。模型服务的对外 API 就通过 Ingress 暴露给业务方。

```text
Ingress 的关键点：
1. 对外入口 —— 把 Service 暴露到集群外
2. 路由规则 —— 按域名、路径转发到不同后端 Service
3. TLS —— 终止 HTTPS，配置证书
4. 控制器 —— Ingress 需要 Ingress Controller（如 nginx-ingress）实现
```

```yaml
# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: model-ingress
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /predict
            pathType: Prefix
            backend:
              service:
                name: model-service
                port:
                  number: 8000
```

```bash
# 查看 Ingress 状态
kubectl get ingress
kubectl describe ingress model-ingress
```

## 应用场景实战

### 场景一：模型服务从代码到集群的完整链路

```bash
# 1. 构建镜像
docker build -t registry.example.com/model-service:v1 .

# 2. 推送镜像到仓库
docker push registry.example.com/model-service:v1

# 3. 部署到 K8s
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f ingress.yaml

# 4. 验证
kubectl get pods -l app=model-service
kubectl logs -f deployment/model-service
curl https://api.example.com/predict -d '{"text":"hello"}'
```

### 场景二：用 Helm 管理多环境部署

```yaml
# values-dev.yaml（开发环境）
replicaCount: 1
image:
  tag: "dev-latest"
gpu:
  enabled: false
```

```yaml
# values-prod.yaml（生产环境）
replicaCount: 10
image:
  tag: "v1.2.0"
gpu:
  enabled: true
  count: 1
```

```bash
# 同一套 Chart，不同 values 部署到不同环境
helm install model-dev ./chart -f values-dev.yaml --namespace dev
helm install model-prod ./chart -f values-prod.yaml --namespace prod
helm upgrade model-prod ./chart -f values-prod.yaml --namespace prod
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用多阶段构建（multi-stage）缩小镜像体积，生产镜像别带编译工具链
2. 把依赖安装放 Dockerfile 前面，利用层缓存加速构建
3. 敏感信息只进 Secret，配置进 ConfigMap，镜像里不写死任何密码
4. Deployment 设 resources.requests/limits，尤其 GPU 一定要声明
5. 用 Helm 管理多环境，避免复制粘贴多份 YAML
6. 镜像打语义化 tag，别用 latest 上生产（无法回滚定位）
7. 服务间调用用服务名（服务发现），不写死 Pod IP

### 踩坑记录

```text
坑 1：镜像 tag 用 latest 上生产
结论：回滚时不知道 latest 到底是哪个版本，定位问题困难。
原因：latest 是可变的，同一 tag 可能对应不同镜像内容。
解法：镜像打语义化 tag（如 v1.2.0 或 commit hash），immutable。

坑 2：GPU Pod 没声明 resources，调度到无 GPU 节点
结论：Pod 卡在 Pending 状态，一直起不来。
原因：没声明 nvidia.com/gpu，调度器把它放到没有 GPU 的节点。
解法：显式声明 resources.limits: nvidia.com/gpu，并确保装了 device plugin。

坑 3：ConfigMap 挂载文件但应用不热加载
结论：改了 ConfigMap，服务还在用旧配置，以为生效了。
原因：挂载文件会更新，但应用启动时只读一次配置。
解法：应用实现配置热加载（监听文件变化），或改配置后滚动重启 Pod。

坑 4：把 Secret 明文提交进代码仓库
结论：密码泄露，安全审计不通过。
原因：图省事把 Secret YAML 明文放进 git。
解法：Secret 用外部 KMS/Sealed Secrets 管理，或至少 git 里只存加密形式。

坑 5：服务发现写死 Pod IP
结论：Pod 重启后 IP 变了，调用方连不上，服务不可用。
原因：把 Pod 的临时 IP 写进了调用方配置。
解法：通过 Service 名（DNS）访问，IP 变化对调用方透明。
```
