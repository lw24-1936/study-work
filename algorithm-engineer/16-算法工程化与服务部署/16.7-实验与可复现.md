## 概述

可复现（Reproducibility）是算法工程的基本功：任何一次实验，都应该能在任何时候、任何人手里，用同样的代码、数据、配置、随机种子复现出同样的结果。这需要 Git 管代码、DVC 管数据、Experiment Tracking 管实验、Configuration 管配置、Seed 固定随机性、Artifact 管产物、Model Card 记录模型档案。

```text
可复现的七大支柱：
1. 代码 —— Git 版本化，每个实验对应一个 commit
2. 数据 —— DVC 版本化大数据，Dataset Version 精确引用
3. 配置 —— 超参、路径全部进配置文件，不进代码
4. 随机性 —— Seed 固定，保证可重复
5. 实验 —— Experiment Tracking 记录每次实验的完整信息
6. 产物 —— Artifact 统一命名、存储、可追溯
7. 档案 —— Model Card 记录模型用途、限制、指标
```

```python
# 一个可复现实验的标准骨架
import random
import numpy as np
import torch

def set_seed(seed: int = 42):
    """固定所有随机源，保证可复现"""
    random.seed(seed)
    np.random.seed(seed)
    torch.manual_seed(seed)
    torch.cuda.manual_seed_all(seed)
    torch.backends.cudnn.deterministic = True

def run_experiment(config: dict, seed: int = 42):
    set_seed(seed)
    data = load_data(config["data_version"])
    model = build_model(config["model"])
    metrics = train_and_eval(model, data, config)
    save_artifact(model, config, metrics, seed)
    return metrics
```

## Git

Git 是代码版本控制的事实标准，记录每一次代码变更，支持分支、回滚、协作。对算法工程师，Git 的价值在于：每个实验结果都能对应到一个确定的代码版本（commit），「这个结果是用哪份代码跑出来的」这个问题的答案就是 commit hash。配合分支策略管理实验和主线的隔离。

```text
Git 在算法工程里的关键点：
1. commit —— 每次实验的代码快照，用 hash 精确定位
2. 分支 —— 实验分支隔离，主线保持稳定
3. 追踪 —— 结果可回溯到具体代码版本
4. 协作 —— 多人并行开发不冲突
```

```bash
# 算法实验的 Git 工作流
git init
git add .
git commit -m "feat: 加入 bert 分类模型基线"

# 开实验分支
git checkout -b exp/lr-0.01
# ... 改代码、跑实验 ...

# 记录实验对应的 commit
git log --oneline -1          # 拿到 commit hash，记进实验追踪

# 回滚到某个版本
git checkout <commit-hash>
```

```text
.gitignore 应忽略的内容：
1. 模型权重、数据集（用 DVC 管理）
2. 日志、checkpoint 临时文件
3. Python 缓存（__pycache__、.pyc）
4. 本地环境配置（.env）
```

## DVC

DVC（Data Version Control）是「数据版的 Git」，用 Git 管理大文件（数据、模型权重）的版本，把大文件本身存在远程存储（S3、GCS、NAS），只在 Git 里存一个指向内容的小元数据文件。它让「数据版本化」变得像代码版本化一样简单。

```text
DVC 的关键点：
1. 大文件版本化 —— 数据和模型权重不进 Git，用 DVC 追踪
2. 内容寻址 —— 用文件内容哈希命名，内容变则版本变
3. 远程存储 —— 大文件存 S3/NAS，Git 只存 .dvc 指针文件
4. 流水线 —— dvc.yaml 定义数据加工和训练的步骤依赖
```

```bash
# DVC 基本用法
dvc init                       # 初始化
dvc remote add -d myremote s3://my-bucket/dvc   # 配置远程存储

dvc add data/raw.csv           # 追踪数据，生成 raw.csv.dvc 指针
git add data/raw.csv.dvc .dvc/config
git commit -m "add dataset v1"

dvc push                       # 上传大文件到远程
dvc pull                       # 从远程拉取大文件

# 切回旧版本数据
git checkout <old-commit> && dvc checkout
```

## Dataset Version

数据集版本（Dataset Version）是给训练数据打版本号，保证「每个模型训练用的确切是哪份数据」可追溯。数据在持续更新、清洗、扩充，如果不版本化，就没法复现旧模型、也没法对比「换了数据效果变好还是变差」。DVC 的指针文件 + Git commit 就是最朴素的实现。

```text
数据集版本化的关键点：
1. 版本号 —— 每次数据变更产生新版本
2. 内容哈希 —— 用哈希标识数据内容，内容变则版本变
3. 精确引用 —— 训练时指定 data_version，不用「最新」
4. 血缘 —— 数据版本 → 训练 → 模型版本 的完整链
```

```python
# 数据集版本管理（配合 DVC 或自建）
import hashlib

def dataset_fingerprint(file_path: str) -> str:
    """用内容哈希作为数据版本标识"""
    h = hashlib.sha256()
    with open(file_path, "rb") as f:
        for chunk in iter(lambda: f.read(8192), b""):
            h.update(chunk)
    return h.hexdigest()[:16]      # 短哈希作为版本号

# 训练时精确引用数据版本
class DatasetRef:
    def __init__(self, name: str, path: str):
        self.name = name
        self.version = dataset_fingerprint(path)

    def __repr__(self):
        return f"{self.name}@{self.version}"

ref = DatasetRef("train", "raw.csv")
print(ref)                      # train@a3f9c2e1b8d47f0c
```

## Experiment Tracking

实验追踪（Experiment Tracking）是系统化记录每次实验的完整信息：代码 commit、数据版本、超参、随机种子、环境、指标、产物路径。它把「实验」从「跑完就忘」变成「可检索、可对比、可复现的资产」。MLflow Tracking、Weights & Biases 是主流工具。

```text
实验追踪要记录的信息：
1. 超参 —— learning rate、batch size、层数等
2. 代码版本 —— git commit hash
3. 数据版本 —— 训练/验证用的数据版本
4. 指标 —— 损失、准确率、AUC 等（每个 epoch）
5. 产物 —— 模型权重、日志的存储路径
6. 环境 —— Python 版本、依赖版本、GPU 型号
```

```python
import mlflow

# MLflow 实验追踪
with mlflow.start_run():
    # 记录参数
    mlflow.log_params({
        "lr": 0.01,
        "batch_size": 64,
        "seed": 42,
        "data_version": "v3",
    })
    # 记录代码版本
    mlflow.set_tag("git_commit", "a1b2c3d4")
    # 记录指标
    mlflow.log_metric("val_auc", 0.86)
    # 记录 artifact
    mlflow.log_artifact("model.pt")
```

## Configuration

配置管理（Configuration）是把所有可变参数（超参、路径、开关）从代码里抽出来放进配置文件（YAML/JSON），代码只读取配置。这样「改超参跑新实验」不用改代码，配置本身也可版本化、可对比。典型用 Hydra、OmegaConf 或 argparse 管理。

```text
配置管理的关键点：
1. 分离 —— 配置与代码分离，改参数不改代码
2. 版本化 —— 配置文件也进 Git，可回溯
3. 结构化 —— YAML/JSON 支持嵌套、列表、类型
4. 可覆盖 —— 命令行覆盖默认配置，方便批量实验
```

```python
import yaml

# config.yaml 配置文件
CONFIG = """
model:
  name: bert-base
  hidden: 768
training:
  lr: 0.001
  batch_size: 32
  epochs: 10
  seed: 42
data:
  version: v3
  path: /data/train.csv
"""

def load_config(config_path: str) -> dict:
    with open(config_path) as f:
        return yaml.safe_load(f)

def run(cfg: dict):
    model = build(cfg["model"])
    train(model, cfg["training"], cfg["data"])

def build(m): return m["name"]
def train(m, t, d): return t["lr"]

# 写入配置文件
with open("config.yaml", "w") as f:
    f.write(CONFIG)

cfg = load_config("config.yaml")
print(cfg["training"]["lr"])       # 0.001
```

## Seed

随机种子（Seed）是控制随机数生成器初始状态的整数。深度学习和机器学习训练里有大量随机性：权重初始化、数据打乱、dropout、数据增强。固定 seed 后，同样的代码和数据能跑出完全一致的结果（在同硬件同版本下）。可复现的底线就是：每次实验记录并固定 seed。

```text
Seed 的关键点：
1. 随机源 —— 权重初始化、数据 shuffle、dropout、增强
2. 全局固定 —— random、numpy、torch、cuda 都要设
3. 记录 —— 每次实验记录 seed，复现时用同一个
4. 注意 —— 跨硬件/跨版本结果可能仍不完全一致
```

```python
import random
import numpy as np
import torch

def set_seed(seed: int = 42):
    random.seed(seed)
    np.random.seed(seed)
    torch.manual_seed(seed)
    if torch.cuda.is_available():
        torch.cuda.manual_seed_all(seed)
    # 让 cuDNN 使用确定性算法（可能略慢，但可复现）
    torch.backends.cudnn.deterministic = True
    torch.backends.cudnn.benchmark = False

# 验证可复现性
set_seed(42)
a = torch.randn(5)
set_seed(42)
b = torch.randn(5)
print(torch.equal(a, b))          # True，结果完全一致
```

## Artifact

产物（Artifact）是实验产生的所有文件：模型权重、日志、评估报告、图表、预测结果。产物管理的核心是「统一命名、集中存储、可追溯」——知道每个产物是哪个实验、哪个 commit、哪份数据产出的。好的命名规范（含版本、日期、指标）让产物可检索。

```text
Artifact 管理的关键点：
1. 命名规范 —— 含模型名、版本、日期、关键指标
2. 集中存储 —— 统一存到对象存储（S3）或 MLflow artifact store
3. 关联 —— artifact 关联到实验记录（experiment id）
4. 保留策略 —— 定期清理无用产物，节约存储
```

```python
import os
import datetime

def build_artifact_path(model_name: str, version: str, metric: float) -> str:
    """统一命名规范生成产物路径"""
    date = datetime.date.today().isoformat()
    filename = f"{model_name}_{version}_{date}_auc{metric:.3f}.pt"
    return os.path.join("artifacts", model_name, filename)

path = build_artifact_path("bert-cls", "v1.2.0", 0.863)
print(path)
# artifacts/bert-cls/bert-cls_v1.2.0_2026-08-13_auc0.863.pt
```

## Model Card

模型卡（Model Card）是随模型一起发布的「说明书」，记录模型的用途、训练数据、评估指标、限制、伦理考量、使用方法。它让模型的使用者（可能是别的团队或未来的自己）能快速了解「这个模型是干嘛的、怎么用、有哪些坑」。Google 提出的 Model Cards 实践已成为负责任 AI 的标准。

```text
Model Card 应包含的内容：
1. 模型详情 —— 名称、版本、开发者、日期
2. 用途 —— 适用场景、目标用户、超出范围的使用
3. 训练数据 —— 数据来源、规模、划分方式
4. 评估指标 —— 在哪些数据集上、取得了什么指标
5. 限制与偏差 —— 已知的失败模式、偏见、伦理考量
6. 使用方法 —— 输入格式、输出格式、依赖环境
```

```text
# model_card.md 示例结构
# Model Card: bert-cls-v1.2.0

## 模型详情
- 名称: bert-cls
- 版本: v1.2.0
- 类型: 文本分类（二分类）
- 开发者: 算法团队
- 日期: 2026-08-13

## 用途
- 适用: 对中文短文本做情感分类（正面/负面）
- 不适用: 长文档、多标签、低资源语言

## 训练数据
- 来源: 内部标注数据 + 公开语料
- 规模: 训练 10w / 验证 1w / 测试 1w
- 版本: dataset@v3

## 评估指标
- 测试集 AUC: 0.863
- 测试集 F1: 0.79

## 限制与偏差
- 对口语化、含 emoji 的文本表现下降
- 训练数据以电商评论为主，其他领域泛化受限

## 使用方法
- 输入: {"text": "..."}
- 输出: {"label": "正面", "score": 0.93}
```

## 应用场景实战

### 场景一：端到端可复现实验流程

```python
# 完整可复现实验：config + seed + tracking + artifact
import yaml, random
import numpy as np

def run_reproducible_experiment(config_path: str, seed: int = 42):
    # 1. 加载配置
    with open(config_path) as f:
        cfg = yaml.safe_load(f)
    # 2. 固定随机种子
    random.seed(seed)
    np.random.seed(seed)
    # 3. 加载指定版本数据
    data = load(cfg["data"]["version"])
    # 4. 训练 + 记录
    metrics = train(cfg, data, seed)
    # 5. 保存产物（含版本和指标）
    artifact = f"{cfg['model']['name']}_{cfg['data']['version']}_auc{metrics['auc']:.3f}.pt"
    return artifact, metrics

def load(v): return v
def train(cfg, data, seed):
    return {"auc": 0.86}

print(run_reproducible_experiment("config.yaml"))
```

## 最佳实践与踩坑记录

### 最佳实践

1. 代码用 Git、数据用 DVC、实验用 MLflow，三者各管各的，别混
2. 每个实验记录完整的「代码 commit + 数据版本 + 超参 + seed + 指标」
3. 所有随机源（random/numpy/torch/cuda）统一用 set_seed 固定
4. 配置全部进 YAML/JSON，代码里不出现魔法数字
5. artifact 统一命名规范，含版本和关键指标，存到集中存储
6. 每个上生产的模型必须配 Model Card，记录用途、指标、限制
7. 定期清理过期 artifact，但保留生产模型的历史版本

### 踩坑记录

```text
坑 1：只固定 torch.manual_seed，没固定 numpy/cuda
结论：跑两次结果还是不一样，以为 seed 没用。
原因：数据增强用 numpy、dropout 用 cuda，这些随机源没固定。
解法：random、numpy、torch、cuda 全部设 seed，并开 cudnn.deterministic。

坑 2：数据不版本化，用「最新」训练
结论：复现旧模型时，数据已经变了，结果对不上。
原因：训练脚本直接读最新数据，没指定数据版本。
解法：用 DVC 给数据打版本，训练时精确引用 data_version。

坑 3：配置写死在代码里，改超参要改代码
结论：每次调参都要改源码、重新提交，易出错、难对比。
原因：lr、batch_size 等硬编码在脚本里。
解法：超参抽到 YAML/JSON 配置，代码只读配置。

坑 4：跨硬件复现结果对不上，怀疑自己代码错了
结论：GPU 型号不同、cuDNN 版本不同，浮点结果有微小差异。
原因：浮点运算不满足结合律，不同硬件/版本的累加顺序不同。
解法：接受微小误差（看指标是否一致），或严格固定硬件+环境版本。

坑 5：模型上线但没有任何文档
结论：接手的人不知道模型能干嘛、有啥坑，误用导致事故。
原因：只交了权重文件，没写 Model Card。
解法：每个模型配 Model Card，记录用途、限制、评估指标。
```
