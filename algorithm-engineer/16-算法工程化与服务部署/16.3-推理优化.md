## 概述

推理优化是在「模型已训练好」的前提下，让它在生产环境跑得更快、更省资源的一套技术。方向分三类：硬件层（CUDA、cuDNN、Tensor Core 榨干 GPU）、格式与运行时层（ONNX、TensorRT、OpenVINO、TorchScript、torch.compile 把模型编译成高效执行图）、模型层（Quantization、Pruning、Distillation 让模型本身变小变快）。

```text
推理优化的三大层次：
1. 硬件层 —— 理解 GPU 执行模型，利用 Tensor Core、算子融合榨性能
2. 运行时层 —— 把 PyTorch 模型导出/编译成高度优化的推理引擎
3. 模型层 —— 量化、剪枝、蒸馏，用精度换速度或直接变小模型
```

```python
import torch
import time

# 一个待优化的基准模型
model = torch.nn.Sequential(
    torch.nn.Linear(768, 3072),
    torch.nn.ReLU(),
    torch.nn.Linear(3072, 768),
).cuda().eval()

x = torch.randn(1, 768).cuda()

def benchmark(fn, n=100):
    torch.cuda.synchronize()
    t0 = time.time()
    for _ in range(n):
        fn()
    torch.cuda.synchronize()
    return (time.time() - t0) / n * 1000  # 毫秒/次

print(f"原始模型: {benchmark(lambda: model(x)):.3f} ms")
```

## CUDA

CUDA（Compute Unified Device Architecture）是 NVIDIA 的并行计算平台和编程模型，让程序用 GPU 上千个核心做大规模并行计算。深度学习框架（PyTorch/TensorFlow）底层都通过 CUDA 把张量运算分发到 GPU。理解 CUDA 的核心是理解「网格-块-线程」的三级并行结构和显存/全局内存的层次。

```text
CUDA 的核心概念：
1. 三级并行 —— grid（网格）→ block（块）→ thread（线程）
2. 内存层次 —— 全局内存 / 共享内存 / 寄存器，越近越快越稀缺
3. Kernel —— 在 GPU 上执行的函数，一次启动并行跑成千上万个线程
4. 显存传输 —— CPU-GPU 数据传输是瓶颈，要尽量少传、批量传
```

```python
# PyTorch 里的 CUDA 基础操作
import torch

print(torch.cuda.is_available())          # 是否有 GPU
print(torch.cuda.device_count())          # GPU 数量
print(torch.cuda.get_device_name(0))      # 显卡型号

# 张量在 CPU 和 GPU 之间搬移
x_cpu = torch.randn(1000, 1000)
x_gpu = x_cpu.cuda()                      # 搬到 GPU
y_gpu = x_gpu @ x_gpu                     # GPU 上矩阵乘法
y_cpu = y_gpu.cpu()                       # 搬回 CPU

# 查看显存占用
print(torch.cuda.memory_allocated() / 1024**2, "MB")
```

## cuDNN

cuDNN（CUDA Deep Neural Network library）是 NVIDIA 为深度神经网络提供的高度优化的算子库，封装了卷积、池化、归一化、激活、RNN 等常用算子，针对不同 GPU 架构做手工调优。PyTorch 的卷积和 LSTM 底层默认走 cuDNN，这也是「同一个模型在 NVIDIA GPU 上跑得快」的关键原因。

```text
cuDNN 的关键点：
1. 算子库 —— 卷积/池化/归一化/激活/RNN 等的高性能实现
2. 自动调优 —— benchmark 模式会为当前 GPU 选最快的卷积算法
3. 算法选择 —— 卷积有多种实现（im2col、FFT、Winograd），按需切换
4. 精度模式 —— 支持 FP32/TF32/FP16 等不同精度
```

```python
import torch

# 控制 cuDNN 行为
torch.backends.cudnn.benchmark = True     # 让 cuDNN 自动选最快卷积算法
torch.backends.cudnn.deterministic = False  # benchmark=True 时建议关掉确定性

# 一个会用到 cuDNN 的卷积模型
conv = torch.nn.Conv2d(3, 64, kernel_size=3, padding=1).cuda()
x = torch.randn(8, 3, 224, 224).cuda()
y = conv(x)                               # 底层调用 cuDNN
print(y.shape)                            # (8, 64, 224, 224)

# 允许 TF32 加速（Ampere 及以上 GPU）
torch.backends.cuda.matmul.allow_tf32 = True
```

## Tensor Core

Tensor Core 是 NVIDIA Volta 架构（V100）及以后 GPU 上专门做矩阵乘加（D=A×B+C）的硬件单元，能在一个时钟周期内完成 4×4 矩阵乘加，速度远超普通 CUDA Core。它是 FP16/TF32/INT8 混合精度训练和推理能大幅加速的硬件基础。

```text
Tensor Core 的关键点：
1. 矩阵乘加 —— 专为 4×4 矩阵乘累加设计，D = A·B + C
2. 混合精度 —— 支持 FP16、TF32、BF16、INT8，输入精度低于 FP32
3. 加速来源 —— FP16 训练可达 FP32 的数倍吞吐
4. 触发条件 —— 矩阵维度满足对齐要求（如 8 的倍数）才能高效利用
```

```python
import torch

# 用 FP16 混合精度触发 Tensor Core 加速
a = torch.randn(1024, 1024, device="cuda")
b = torch.randn(1024, 1024, device="cuda")

# FP32（普通 CUDA Core）
c32 = a @ b

# FP16（Tensor Core 加速，速度快数倍）
a16, b16 = a.half(), b.half()
c16 = a16 @ b16
print(c16.dtype)                          # torch.float16

# 检查当前 GPU 是否支持 Tensor Core
print(torch.cuda.get_device_capability(0))  # (7, 0) V100、(8, 0) A100
```

## ONNX

ONNX（Open Neural Network Exchange）是一种开放的模型交换格式，用统一的图结构描述神经网络，让「PyTorch 训练 → 导出 ONNX → 任意 ONNX 兼容运行时推理」成为可能。它解耦了训练框架和推理引擎，是模型跨框架、跨硬件部署的中间枢纽。

```text
ONNX 的核心价值：
1. 框架无关 —— PyTorch/TensorFlow/ONNX 都能导出/导入
2. 统一图表示 —— 用算子（op）和节点描述计算图
3. 生态丰富 —— 可被 TensorRT、ONNX Runtime、OpenVINO 消费
4. 版本演进 —— opset 版本管理算子的增减与语义变化
```

```python
import torch
import torch.onnx

class TinyNet(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = torch.nn.Linear(10, 2)

    def forward(self, x):
        return self.fc(x)

model = TinyNet().eval()
dummy = torch.randn(1, 10)

# 导出 ONNX
torch.onnx.export(
    model, dummy, "tiny.onnx",
    input_names=["input"],
    output_names=["output"],
    dynamic_axes={"input": {0: "batch"}, "output": {0: "batch"}},
    opset_version=17,
)
print("exported tiny.onnx")
```

## ONNX Runtime

ONNX Runtime（ORT）是微软开源的 ONNX 模型推理引擎，跨平台、跨硬件（CPU/GPU/多种加速器），支持图优化（算子融合、常量折叠）和执行 provider 切换。它是「导出 ONNX 之后」最常用、最易上手的推理运行时。

```text
ONNX Runtime 的特点：
1. 图优化 —— 自动做算子融合、常量折叠、冗余消除
2. Execution Provider —— CPU / CUDA / TensorRT / OpenVINO 等后端切换
3. 轻量易用 —— 几行代码加载 ONNX 模型推理
4. 跨平台 —— Windows/Linux/macOS/移动端/Web
```

```python
import onnxruntime as ort
import numpy as np

# 加载刚才导出的 ONNX 模型
sess = ort.InferenceSession(
    "tiny.onnx",
    providers=["CPUExecutionProvider"],   # 也可用 CUDAExecutionProvider
)

x = np.random.randn(1, 10).astype(np.float32)
outputs = sess.run(None, {"input": x})
print(outputs[0].shape)                    # (1, 2)

# 查看输入输出名称和形状
for inp in sess.get_inputs():
    print(inp.name, inp.shape)
```

## TensorRT

TensorRT 是 NVIDIA 的推理优化引擎，把 ONNX（或框架模型）编译成针对特定 GPU 高度优化的执行引擎：做算子融合、精度校准（FP16/INT8）、kernel 自动调优、显存优化。它是 NVIDIA GPU 上推理加速的「天花板」，延迟和吞吐通常优于通用运行时。

```text
TensorRT 的优化手段：
1. 层融合 —— 卷积 + BN + ReLU 合成一个 kernel，减少显存读写
2. 精度校准 —— INT8 量化需用校准集确定每层的量化范围
3. kernel 调优 —— 为当前 GPU 型号选最快的实现
4. 动态形状 —— 支持 batch 动态，但需指定 profile 范围
```

```python
import tensorrt as trt

logger = trt.Logger(trt.Logger.WARNING)
builder = trt.Builder(logger)
network = builder.create_network(1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
parser = trt.OnnxParser(network, logger)

# 解析 ONNX
with open("tiny.onnx", "rb") as f:
    if not parser.parse(f.read()):
        for i in range(parser.num_errors):
            print(parser.get_error(i))

config = builder.create_builder_config()
config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 1 << 30)  # 1GB
if builder.platform_has_fast_fp16:
    config.set_flag(trt.BuilderFlag.FP16)

serialized = builder.build_serialized_network(network, config)
with open("tiny.engine", "wb") as f:
    f.write(serialized)
print("built tiny.engine")
```

## TensorRT-LLM

TensorRT-LLM 是 NVIDIA 专门针对大语言模型推理优化的库，把 LLM 的整条推理链（KV Cache 管理、连续批处理、paged attention、张量并行、量化）都做了深度优化，提供类似标准 LLM API 的接口，吞吐和延迟远优于朴素实现。

```text
TensorRT-LLM 的关键技术：
1. 连续批处理 —— 请求到达即加入 batch，不等凑齐，提升吞吐
2. Paged KV Cache —— 类似虚拟内存的分页管理，减少显存碎片
3. 张量并行 —— 多 GPU 切分权重，跑超大规模模型
4. 量化 —— 支持 FP8/INT4/INT8，大幅降低显存占用
```

```python
# TensorRT-LLM 高层 API（简化示意）
# 实际使用需要 build 出 engine，再通过 runtime 推理
from tensorrt_llm import LLM, SamplingParams

# 加载已编译的 engine
llm = LLM(model="llama-engine", tensor_parallel_size=1)

params = SamplingParams(max_tokens=100, temperature=0.7)
outputs = llm.generate(["写一首关于算法的诗"], sampling_params=params)
for out in outputs:
    print(out.outputs[0].text)
```

## OpenVINO

OpenVINO 是 Intel 开源的推理优化工具包，针对 Intel CPU、集成显卡、VPU 优化，核心思想是把模型编译成中间表示（IR），再用针对 Intel 硬件的优化算子跑。它在「纯 CPU 环境」下通常比 PyTorch 原生推理快很多，是 Intel 硬件上部署的首选。

```text
OpenVINO 的特点：
1. CPU 优化 —— 针对 Intel CPU 指令集深度优化，无 GPU 也能快
2. 异构硬件 —— 支持 CPU / iGPU / VPU / NPU 混合执行
3. 模型优化器 —— 把 ONNX/TF/PyTorch 转成 IR 中间表示
4. INT8 量化 —— 自带 Post-Training Quantization 工具
```

```python
import openvino as ov

core = ov.Core()
# 编译 ONNX 模型为 OpenVINO 优化图
model = core.read_model("tiny.onnx")
compiled = core.compile_model(model, "CPU")

infer_request = compiled.create_infer_request()
import numpy as np
x = np.random.randn(1, 10).astype(np.float32)
out = infer_request.infer({"input": x})
print(out)
```

## TorchScript

TorchScript 是 PyTorch 的「可序列化 + 可优化」模型表示，把 Python 代码编译成独立于 Python 的图表示，既能在 C++ 环境运行，也能脱离 Python 解释器获得一定加速。导出方式有两种：tracing（跟踪实际执行）和 scripting（解析代码）。

```text
TorchScript 的两种导出方式：
1. Tracing —— 跑一遍记录走过的算子，控制流会被「固化」，动态分支丢失
2. Scripting —— 解析 Python 源码，保留 if/for 控制流，但部分 Python 语法不支持
3. 价值 —— 脱离 Python 部署到 C++，减少 Python 开销
4. 局限 —— 动态 shape、Python 动态特性支持有限，逐步被 torch.compile 取代
```

```python
import torch

class Model(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = torch.nn.Linear(10, 2)

    def forward(self, x):
        if x.dim() == 2:          # 控制流，tracing 会固化
            return self.fc(x)
        return self.fc(x.unsqueeze(0))

model = Model().eval()

# tracing 导出
traced = torch.jit.trace(model, torch.randn(1, 10))
traced.save("model_traced.pt")

# scripting 导出
scripted = torch.jit.script(model)
scripted.save("model_scripted.pt")

# 加载并推理
loaded = torch.jit.load("model_traced.pt")
print(loaded(torch.randn(1, 10)))
```

## torch.compile

torch.compile 是 PyTorch 2.x 的图编译加速器，只需一行代码包裹模型，就能在底层用 TorchInductor 自动做算子融合、kernel 生成和图优化，通常能获得 30%-2x 的加速，且几乎不需要改代码。它是目前 PyTorch 生态里「性价比最高」的推理/训练优化手段。

```text
torch.compile 的特点：
1. 零改动 —— 一行 torch.compile(model) 包裹即可
2. 图捕获 —— 把 eager 执行编译成优化后的图
3. 算子融合 —— Inductor 后端自动融合算子、生成高效 kernel
4. 模式 —— default / reduce-overhead / max-autotune 三档
```

```python
import torch
import time

model = torch.nn.Sequential(
    torch.nn.Linear(512, 1024),
    torch.nn.ReLU(),
    torch.nn.Linear(1024, 512),
).cuda()

x = torch.randn(32, 512).cuda()

# eager 模式基准
model.eval()
torch.cuda.synchronize()
t0 = time.time()
for _ in range(100):
    model(x)
torch.cuda.synchronize()
eager_ms = (time.time() - t0) / 100 * 1000

# torch.compile 优化
compiled = torch.compile(model, mode="reduce-overhead")
compiled(x)                    # 预热
torch.cuda.synchronize()
t0 = time.time()
for _ in range(100):
    compiled(x)
torch.cuda.synchronize()
compiled_ms = (time.time() - t0) / 100 * 1000

print(f"eager: {eager_ms:.3f} ms, compiled: {compiled_ms:.3f} ms")
```

## Quantization

量化（Quantization）是把模型权重和激活从 FP32（32 位浮点）降低到更低精度（FP16/INT8/INT4），从而减小模型体积、降低显存占用、加速推理。分为训练后量化（PTQ，无需重训）和量化感知训练（QAT，训练时模拟量化误差）。

```text
量化的关键概念：
1. 精度 —— FP16（半精度）、INT8（8 位整数）、INT4（4 位）
2. PTQ —— Post-Training Quantization，训练后直接量化，快但可能掉精度
3. QAT —— Quantization-Aware Training，训练时模拟量化，精度损失小
4. 校准 —— INT8 需要校准集确定每层的量化 scale 和 zero-point
5. 对称/非对称 —— 是否允许非零的 zero-point
```

```python
import torch

model = torch.nn.Sequential(
    torch.nn.Linear(256, 512),
    torch.nn.ReLU(),
    torch.nn.Linear(512, 256),
).eval()

# PyTorch 动态量化（INT8，适合 LSTM/Linear，无需校准集）
quantized = torch.quantization.quantize_dynamic(
    model, {torch.nn.Linear}, dtype=torch.qint8
)

# 对比模型大小
import io
def model_size(m):
    buf = io.BytesIO()
    torch.save(m.state_dict(), buf)
    return len(buf.getvalue()) / 1024

print(f"FP32 模型: {model_size(model):.1f} KB")
print(f"INT8 模型: {model_size(quantized):.1f} KB")
```

## Pruning

剪枝（Pruning）是删除模型中「不重要」的权重或神经元，减少参数量和计算量。分为结构化剪枝（剪掉整个神经元/通道，硬件友好）和非结构化剪枝（单个权重置零，稀疏化）。剪枝后通常需要微调恢复精度。

```text
剪枝的关键概念：
1. 非结构化 —— 单个权重置零，得到稀疏矩阵，但硬件加速难
2. 结构化 —— 剪掉整行/整列/整通道，真正减少计算量
3. 重要性度量 —— 权重绝对值、梯度、激活值等决定剪谁
4. 剪枝 + 微调 —— 剪完必须微调，否则精度掉得多
```

```python
import torch
import torch.nn.utils.prune as prune

model = torch.nn.Sequential(
    torch.nn.Linear(256, 512),
    torch.nn.ReLU(),
    torch.nn.Linear(512, 256),
)

# 对第一个 Linear 做 L1 非结构化剪枝，剪掉 50% 权重
prune.l1_unstructured(model[0], name="weight", amount=0.5)

# 查看稀疏度
sparsity = 100. * float(torch.sum(model[0].weight == 0)) / float(model[0].weight.nelement())
print(f"稀疏度: {sparsity:.1f}%")

# 去掉剪枝掩码，固化稀疏权重
prune.remove(model[0], "weight")
```

## Distillation

知识蒸馏（Distillation）是用一个大的教师模型（Teacher）「教」一个小的学生模型（Student），让学生的输出（软标签）逼近教师的输出分布，从而用小模型获得接近大模型的精度。它是「模型变小但精度不掉」的经典手段。

```text
蒸馏的关键概念：
1. 教师/学生 —— 大模型教小模型，学生用于部署
2. 软标签 —— 教师输出的概率分布（含类别间相似性），比硬标签信息更丰富
3. 温度 —— 软化概率分布的系数，温度越高分布越平缓
4. 损失组合 —— 学生硬标签损失 + 与教师软标签的 KL 散度
```

```python
import torch
import torch.nn.functional as F

# 蒸馏损失：学生软输出对齐教师软输出
def distillation_loss(student_logits, teacher_logits, labels, temperature=4.0, alpha=0.7):
    # 软目标损失（KL 散度）
    soft_student = F.log_softmax(student_logits / temperature, dim=1)
    soft_teacher = F.softmax(teacher_logits / temperature, dim=1)
    distill = F.kl_div(soft_student, soft_teacher, reduction="batchmean") * (temperature ** 2)
    # 硬目标损失
    hard = F.cross_entropy(student_logits, labels)
    return alpha * distill + (1 - alpha) * hard

# 模拟一次蒸馏
student_logits = torch.randn(4, 10, requires_grad=True)
teacher_logits = torch.randn(4, 10)
labels = torch.randint(0, 10, (4,))
loss = distillation_loss(student_logits, teacher_logits, labels)
print(loss.item())
```

## 应用场景实战

### 场景一：PyTorch 模型端到端 INT8 加速

```python
# 训练好的模型 → 导出 ONNX → TensorRT INT8 加速
import torch

class Net(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = torch.nn.Linear(128, 256)
        self.fc2 = torch.nn.Linear(256, 10)

    def forward(self, x):
        return self.fc2(torch.relu(self.fc1(x)))

model = Net().eval()
torch.onnx.export(model, torch.randn(1, 128), "net.onnx",
                  input_names=["input"], output_names=["output"], opset_version=17)

# 之后用 TensorRT 的 INT8 校准流程构建 engine
# 校准数据：从真实分布抽样，让 TensorRT 学习每层量化范围
import numpy as np
calib_data = [np.random.randn(1, 128).astype(np.float32) for _ in range(100)]
print(f"已导出 net.onnx，校准集 {len(calib_data)} 条")
```

### 场景二：量化 + 蒸馏组合优化小模型

```python
# 蒸馏出小模型后，再量化，得到又小又快的学生模型
import torch

class SmallStudent(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = torch.nn.Linear(64, 8)

    def forward(self, x):
        return self.fc(x)

student = SmallStudent().eval()

# 蒸馏完成后，对部署模型做动态量化
quantized_student = torch.quantization.quantize_dynamic(
    student, {torch.nn.Linear}, dtype=torch.qint8
)

# 量化后模型体积对比
import io
def size_of(m):
    buf = io.BytesIO()
    torch.save(m.state_dict(), buf)
    return len(buf.getvalue())

print(f"蒸馏学生模型: {size_of(student)} bytes")
print(f"量化后模型: {size_of(quantized_student)} bytes")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先跑通再优化：基准模型 + 正确的评测集，优化才有对比对象
2. 优先用 torch.compile 一行加速，零改动收益大
3. NVIDIA GPU 部署优先考虑 ONNX → TensorRT（或 TensorRT-LLM for LLM）
4. 纯 CPU / Intel 环境用 OpenVINO，比 PyTorch 原生快很多
5. 量化优先尝试 PTQ，精度不够再上 QAT
6. 剪枝/蒸馏后必须用原评测集验证精度，不能只看速度
7. 优化前先 profile，找出真正的瓶颈（算子还是显存带宽）再动手

### 踩坑记录

```text
坑 1：盲目上 INT8 量化导致精度大幅下降
结论：模型推理快了一半，但准确率掉 5 个点，业务指标崩了。
原因：未做校准或校准集与真实分布不一致，量化范围算错。
解法：用真实分布校准集做 PTQ，精度不达标改 QAT 或只量化部分层。

坑 2：ONNX 导出时动态 batch 没设好
结论：导出的模型只能跑固定 batch，线上变 batch 就报错。
原因：export 时没设 dynamic_axes，batch 维度被固化成 1。
解法：dynamic_axes 显式声明 batch 维度可变，或用 dynamic shape。

坑 3：torch.jit.trace 固化控制流
结论：含 if/for 的模型 trace 后分支丢失，线上输入走错路径。
原因：tracing 只记录一次执行路径，动态分支被固化。
解法：有控制流的模型用 torch.jit.script，或改用 torch.compile。

坑 4：剪枝后不微调直接上线
结论：参数量少了，但精度掉得厉害，得不偿失。
原因：剪枝删掉了部分信息，权重需要重新调整补偿。
解法：剪枝后必须做一轮微调（fine-tune），再用评测集验证。

坑 5：TensorRT 引擎跨 GPU 型号复用
结论：在 A100 上构建的 engine 拿到 V100 上跑报错或异常慢。
原因：TensorRT engine 针对具体 GPU 架构和型号优化，不可移植。
解法：每类 GPU 型号单独构建 engine，或用 runtime 构建而非预构建。
```
