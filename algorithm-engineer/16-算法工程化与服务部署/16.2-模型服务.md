## 概述

模型服务（Model Serving）是把训练好的模型变成可供业务系统调用的能力的过程。根据调用方式分为三类：批量推理（Batch）、在线推理（Online）和流式推理（Streaming）。要让服务稳定、可回滚、可迭代，还需要模型服务器（Model Server）、模型注册表（Model Registry）、模型版本管理（Model Versioning）以及灰度发布策略（Canary / Shadow / Blue-Green）。

```text
模型服务的核心环节：
1. 推理模式 —— Batch 离线批量、Online 在线实时、Streaming 流式输出
2. 服务载体 —— Model Server 负责加载模型、暴露接口、管理生命周期
3. 模型管理 —— Registry 集中存模型，Versioning 追踪每个版本
4. 发布策略 —— Canary/Shadow/Blue-Green 控制新模型上线风险
5. 一致性 —— 同一个模型版本在任何环境行为必须一致
```

```python
# 三种推理模式的最小对比
import time

def predict_once(model, x):
    return model(x)

# 1) Batch：一次处理一大批
def batch_inference(model, xs):
    return [model(x) for x in xs]

# 2) Online：来一个算一个，低延迟
def online_inference(model, x):
    t0 = time.time()
    y = model(x)
    return y, time.time() - t0

# 3) Streaming：边算边输出
def streaming_inference(model, x):
    for token in model.generate_stream(x):
        yield token
```

## Batch Inference

批量推理（Batch Inference / Offline Inference）是对一大块数据一次性做推理，不要求实时返回，关注吞吐量而非单条延迟。典型场景：每天凌晨对全量用户做推荐打分、对历史数据做标签补全、对语料库批量生成 embedding。

```text
批量推理的特点：
1. 离线 —— 数据已经准备好，不需要实时响应
2. 高吞吐 —— 关注单位时间处理量，延迟可以放宽到分钟/小时
3. 成本低 —— 可充分利用 GPU，用便宜的低优先级实例跑
4. 易调度 —— 适合定时任务、离线 pipeline 触发
```

```python
import numpy as np

# 批量推理：用矩阵运算一次算完，最大化 GPU 利用率
def batch_score(model_weights, X):
    # X: (n_samples, n_features)
    return X @ model_weights      # 一次矩阵乘法算完所有样本

X = np.random.randn(10000, 128)
w = np.random.randn(128)
scores = batch_score(w, X)
print(scores.shape)               # (10000,)

# 批量推理典型工作流
def offline_pipeline(model, data_loader):
    results = []
    for batch in data_loader:     # 逐个 batch 处理，避免 OOM
        results.append(model(batch))
    return np.concatenate(results)
```

## Online Inference

在线推理（Online Inference / Real-time Inference）是请求来了立刻返回结果，强约束延迟（通常 P99 < 几十到几百毫秒）。典型场景：搜索排序、推荐召回、风控反欺诈、在线客服。要求模型常驻内存、服务高可用、能水平扩展。

```text
在线推理的关键指标：
1. 延迟（Latency） —— P50/P99 都要达标，P99 决定用户体验
2. 吞吐（Throughput） —— 单实例 QPS，决定需要多少副本
3. 可用性 —— 服务 SLA，通常 99.9% 以上
4. 冷启动 —— 模型加载、连接建立的开销要可控
```

```python
# 在线推理服务：模型常驻内存 + 请求级推理
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()
MODEL = None                      # 全局常驻

@app.on_event("startup")
def load_model():
    global MODEL
    MODEL = load_my_model()       # 启动时加载一次

class Req(BaseModel):
    user_id: int
    item_id: int

@app.post("/rank")
def rank(req: Req):
    # 在线推理：低延迟，单条处理
    score = MODEL.predict(req.user_id, req.item_id)
    return {"score": score}

def load_my_model():
    return MyModel()

class MyModel:
    def predict(self, u, i):
        return 0.8
```

## Streaming Inference

流式推理（Streaming Inference）针对「输出是逐步产生的」场景，边生成边返回，典型就是 LLM 的 token 逐字输出、实时语音识别、视频流的逐帧处理。相比在线推理的「一次返回」，流式推理强调首 token 延迟（TTFT）和吞吐的平衡。

```text
流式推理的关键指标：
1. TTFT —— Time To First Token，首个 token 返回时间
2. 吞吐 —— 每秒生成的 token 数（tokens/s）
3. 背压 —— 消费端处理不过来时的流量控制
4. 传输 —— SSE / WebSocket / gRPC stream
```

```python
import asyncio
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

async def token_generator(prompt: str):
    # 模拟 LLM 逐 token 生成
    for token in ["你好", "，", "世界", "。"]:
        yield token
        await asyncio.sleep(0.1)

@app.post("/generate")
async def generate(prompt: str):
    # StreamingResponse 用 SSE 方式逐段返回
    return StreamingResponse(
        token_generator(prompt),
        media_type="text/event-stream",
    )
```

## Model Server

模型服务器（Model Server）是专门负责「加载模型 → 暴露推理接口 → 管理生命周期」的服务程序。它把模型加载、版本切换、批处理、GPU 调度、监控等通用能力封装起来，让算法工程师不用重复造轮子。常见的有 TorchServe（PyTorch）、Triton Inference Server（NVIDIA）、TF Serving、KServe。

```text
Model Server 提供的通用能力：
1. 模型加载 —— 启动时加载、热更新加载新版本
2. 推理接口 —— 统一的 HTTP/gRPC 推理协议
3. 动态批处理 —— 把并发请求攒成 batch 提升 GPU 利用率
4. 多模型管理 —— 同时托管多个模型、多个版本
5. 监控 —— 暴露延迟、吞吐、显存等指标
```

```python
# 用 TorchServe 风格：模型 handler 定义预处理/推理/后处理
# model_handler.py
class ModelHandler:
    def initialize(self, context):
        # 加载模型权重
        self.model = load_weights(context.system_properties)

    def preprocess(self, requests):
        # 批量预处理
        return [r.get("data") for r in requests]

    def inference(self, batch):
        # 批量推理
        return [self.model(x) for x in batch]

    def postprocess(self, outputs):
        # 批量后处理
        return [{"result": o} for o in outputs]

def load_weights(props):
    return lambda x: x * 2
```

## Model Registry

模型注册表（Model Registry）是集中管理「已训练模型」的仓库，记录每个模型的元数据：名称、版本、训练指标、状态（staging/production/archived）、依赖、所有者等。它让模型从「散落在训练脚本里」变成「可检索、可审批、可追溯的资产」。

```text
Model Registry 记录的关键信息：
1. 标识 —— 模型名 + 版本号（如 bert-classifier@v1.2.0）
2. 指标 —— 准确率、AUC、F1 等评估结果
3. 状态 —— 实验 / 预发布（staging）/ 生产（production）/ 归档（archived）
4. 血缘 —— 训练数据、代码 commit、超参数、训练时间
5. 审批 —— 从 staging 晋升 production 的流程与负责人
```

```python
# 简化版模型注册表（用 MLflow 风格 API）
import mlflow

# 注册一个模型版本
result = mlflow.register_model(
    model_uri="runs:/abc123/model",
    name="recommendation-model",
)

# 把某个版本晋升到生产
client = mlflow.tracking.MlflowClient()
client.transition_model_version_stage(
    name="recommendation-model",
    version=1,
    stage="Production",
)

# 查询生产环境的模型版本
prod = client.get_latest_versions("recommendation-model", stages=["Production"])
print(prod[0].version, prod[0].run_id)
```

## Model Versioning

模型版本管理（Model Versioning）给每个模型赋予唯一版本号，追踪模型的演进历史。好的版本管理能回答三个问题：线上跑的是哪个版本？这个版本是怎么来的？出问题能不能一键回滚？版本通常与「代码 + 数据 + 超参」三者的组合对应。

```text
模型版本管理的要点：
1. 语义化版本 —— 主版本（不兼容变更）/ 次版本（新增）/ 修订（修复）
2. 可复现 —— 版本要能追溯到代码、数据、超参的确切组合
3. 不可变 —— 一旦发布，版本内容不可修改，改动必须发新版本
4. 多版本共存 —— 同一模型不同版本可同时在线（用于灰度）
```

```python
# 语义化版本 + 不可变原则的简单实现
from dataclasses import dataclass
from typing import Any

@dataclass(frozen=True)          # frozen = 不可变
class ModelVersion:
    name: str
    version: str                 # 如 "1.2.0"
    code_commit: str             # 训练代码的 git commit
    dataset_hash: str            # 训练数据的哈希
    metrics: dict[str, Any]

    @property
    def full_id(self) -> str:
        return f"{self.name}@{self.version}"

v1 = ModelVersion("rec", "1.0.0", "abc123", "d4f5e6", {"auc": 0.82})
v2 = ModelVersion("rec", "1.1.0", "def456", "a1b2c3", {"auc": 0.85})
print(v1.full_id)                # rec@1.0.0
print(v1.metrics["auc"])         # 0.82
```

## Canary

金丝雀发布（Canary）是先让新模型只服务一小部分流量（如 5%），观察一段时间确认没问题后，再逐步扩大流量占比直到全量。名字来源于「矿井里的金丝雀」——让少量用户先「试毒」，出问题影响面可控。

```text
Canary 发布的流程：
1. 部署 —— 新版本模型上线，但只接收 5% 流量
2. 观察 —— 监控新版本的延迟、错误率、业务指标
3. 扩量 —— 指标正常则逐步 5% → 25% → 50% → 100%
4. 回滚 —— 指标异常立即切回旧版本
```

```python
# 金丝雀流量切分逻辑（按用户 ID 哈希）
import hashlib

def route_to_canary(user_id: str, canary_percent: float) -> bool:
    # 用哈希把用户稳定地分到金丝雀桶
    h = int(hashlib.md5(user_id.encode()).hexdigest(), 16)
    return (h % 100) < canary_percent

# 10% 金丝雀流量
for uid in ["u1", "u2", "u3", "u4", "u5"]:
    use_new = route_to_canary(uid, canary_percent=10)
    print(uid, "→", "new model" if use_new else "old model")
```

## Shadow

影子发布（Shadow / Shadow Deployment）是让新模型「影子模式」运行：新模型接收真实请求、产出预测，但预测结果不返回给用户，只用于和线上老模型对比、积累评估数据。它零风险地验证新模型在真实流量下的表现，是上线前最安全的一步。

```text
Shadow 发布的特点：
1. 零风险 —— 结果不返回用户，出问题不影响线上
2. 真实流量 —— 用真实数据验证，比离线评估更可信
3. 对比 —— 把新旧模型结果做对比，量化差异
4. 成本 —— 需要额外一份推理算力跑影子模型
```

```python
# 影子模式：新模型默默跑，结果只记录不返回
def shadow_predict(user_req):
    old_result = OLD_MODEL.predict(user_req)
    try:
        new_result = NEW_MODEL.predict(user_req)
        # 记录对比结果，不返回给用户
        log_compare(user_req, old_result, new_result)
    except Exception as e:
        log_error("shadow model failed", e)
    return old_result          # 只返回老模型结果

def log_compare(req, old, new):
    print(f"req={req} old={old} new={new}")

class _Model:
    def predict(self, x):
        return x * 2

OLD_MODEL = _Model()
NEW_MODEL = _Model()
print(shadow_predict(5))       # 返回老模型结果 10
```

## Blue-Green

蓝绿发布（Blue-Green）是准备两套完全独立的生产环境：蓝（Blue，当前版本）和绿（Green，新版本）。切换时把流量一次性从蓝切到绿，切换瞬间完成。它最大的优点是回滚极快——出问题立刻切回蓝即可，不需要重新部署。

```text
Blue-Green 发布的特点：
1. 两套环境 —— 蓝=当前生产，绿=待上线新版本
2. 一次性切换 —— 流量整体切到绿，无渐进过程
3. 秒级回滚 —— 出问题切回蓝，比重新部署快得多
4. 成本高 —— 需要两倍的资源同时在线
```

```text
蓝绿发布流程：
1. 部署绿色环境 —— 新版本模型部署到绿，蓝继续服务
2. 验证绿色 —— 对绿做冒烟测试，确认健康
3. 切换流量 —— 负载均衡把流量从蓝切到绿
4. 观察 + 回滚 —— 绿出问题立刻切回蓝，蓝保留一段时间后再下线
```

```python
# 蓝绿切换的最小实现：一个「当前环境」指针
class BlueGreenRouter:
    def __init__(self):
        self.blue = "model-v1"
        self.green = "model-v2"
        self.active = self.blue      # 当前生产指向蓝

    def switch_to_green(self):
        self.active = self.green     # 一次性切换

    def rollback(self):
        self.active = self.blue      # 秒级回滚

router = BlueGreenRouter()
print(router.active)                # model-v1（蓝）
router.switch_to_green()
print(router.active)                # model-v2（绿）
router.rollback()
print(router.active)                # model-v1（回滚）
```

## 应用场景实战

### 场景一：推荐系统模型的灰度上线

```python
# 综合运用 Registry + Versioning + Canary
class ModelService:
    def __init__(self):
        self.versions = {
            "v1": {"auc": 0.82, "status": "production"},
            "v2": {"auc": 0.85, "status": "staging"},
        }
        self.canary_percent = 10

    def predict(self, user_id: str, features):
        # 金丝雀判断 + 版本路由
        if self._is_canary(user_id) and self.versions["v2"]["status"] == "staging":
            return self._infer("v2", features)
        return self._infer("v1", features)

    def _is_canary(self, user_id: str) -> bool:
        h = hash(user_id) % 100
        return h < self.canary_percent

    def _infer(self, version: str, features):
        return {"version": version, "score": sum(features) * 0.5}

svc = ModelService()
print(svc.predict("user_1", [1, 2, 3]))   # 可能命中 v2
```

### 场景二：LLM 服务的流式 + 影子验证

```python
# 新 LLM 模型影子模式跑，对比输出质量，不返回用户
def chat_with_shadow(prompt: str):
    final_answer = ""
    # 老模型流式输出给用户
    for token in OLD_LLM.stream(prompt):
        final_answer += token
        yield token
    # 新模型影子跑一遍，只记录不返回
    try:
        new_answer = "".join(NEW_LLM.stream(prompt))
        record_evaluation(prompt, final_answer, new_answer)
    except Exception as e:
        log_error("shadow llm failed", e)

class _LLM:
    def stream(self, prompt):
        yield from ["好", "的", "。"]

OLD_LLM = _LLM()
NEW_LLM = _LLM()

def record_evaluation(p, old, new):
    print(f"prompt={p} old={old!r} new={new!r}")

def log_error(msg, e):
    print(msg, e)

for t in chat_with_shadow("你好"):
    pass
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先想清楚推理模式：离线任务用 Batch，实时服务用 Online，LLM 输出用 Streaming
2. 模型一律进 Model Registry，禁止「脚本直接加载本地权重文件」上生产
3. 版本号语义化 + 不可变，改任何东西都发新版本，不覆盖旧版本
4. 新模型上线走「Shadow → Canary → 全量」或「Blue-Green」渐进路径，别直接硬切
5. 每个版本记录完整血缘：代码 commit + 数据哈希 + 超参 + 评估指标
6. Model Server 打开动态批处理，显著提升 GPU 利用率
7. 生产模型至少保留上一个稳定版本，确保能秒级回滚

### 踩坑记录

```text
坑 1：新模型没走灰度直接全量切换
结论：一个隐藏 bug 直接打挂全量流量，影响所有用户。
原因：离线指标好不代表线上行为对，真实流量有长尾和噪声。
解法：先 Shadow 影子验证，再 Canary 小流量，最后才全量。

坑 2：模型版本不可追溯
结论：线上出问题查不到这个版本用的是什么数据、什么代码训练的。
原因：训练完直接存个 .pt 文件，没记录血缘信息。
解法：每次训练用 Registry 记录 code commit、数据哈希、超参、指标。

坑 3：金丝雀流量按请求随机切，导致同一用户结果不一致
结论：同一用户不同请求命中不同版本，体验不一致、难排查。
原因：按请求随机分配流量，而非按用户固定哈希。
解法：用 user_id 哈希固定分桶，同一用户稳定落在同一版本。

坑 4：Blue-Green 两套环境共用同一个数据库/缓存
结论：切流量时新旧版本读写同一份数据，出现脏数据。
原因：环境没做到真正隔离，只隔离了模型服务。
解法：涉及数据变更时要保证 schema 向后兼容，或用双写过渡。

坑 5：流式推理忽略背压
结论：消费端处理慢时，生成端无脑狂推导致内存堆积。
原因：没有流控，生产速度远大于消费速度。
解法：实现背压机制，消费端 ack 后再生成下一批 token。
```
