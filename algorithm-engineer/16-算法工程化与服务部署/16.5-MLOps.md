## 概述

MLOps 是把机器学习的「数据 → 特征 → 训练 → 评估 → 部署 → 监控」全流程工程化、自动化的一套实践，目标是让模型能像软件一样可靠地、可重复地、快速地迭代上线。核心是把流水线（Pipeline）拆成数据、特征、训练、评估四段，用 Model Registry 管理模型资产，用 MLflow/Kubeflow/BentoML 等工具落地。

```text
MLOps 的核心流水线：
1. Data Pipeline —— 采集、清洗、版本化数据
2. Feature Pipeline —— 特征计算、存储、线上线下一致
3. Training Pipeline —— 自动化训练、调参、记录实验
4. Evaluation Pipeline —— 评估、对比、审批、发布
5. Model Registry —— 模型版本、血缘、状态管理
```

```python
# MLOps 流水线的骨架示意
def ml_pipeline():
    data = load_and_clean_data()          # Data Pipeline
    features = compute_features(data)     # Feature Pipeline
    model = train_model(features)         # Training Pipeline
    metrics = evaluate_model(model)       # Evaluation Pipeline
    register_model(model, metrics)        # Model Registry
    return model, metrics

def load_and_clean_data(): return "raw"
def compute_features(d): return "feat"
def train_model(f): return "model"
def evaluate_model(m): return {"auc": 0.9}
def register_model(m, metrics): print("registered", metrics)
```

## Data Pipeline

数据流水线（Data Pipeline）负责把原始数据变成可用的训练数据：采集、清洗、去重、校验、划分，并做版本化。它是整个 MLOps 的地基——数据错了，后面全错。好的数据流水线要保证数据质量可监控、可追溯、可复现。

```text
Data Pipeline 的关键环节：
1. 采集 —— 从日志、数据库、消息队列拉取数据
2. 清洗 —— 去重、处理缺失值、过滤异常
3. 校验 —— 数据质量检查（schema、分布、空值率）
4. 版本化 —— 每次产出打版本号，训练时精确引用
5. 血缘 —— 记录数据从哪来、怎么加工
```

```python
import pandas as pd

def data_pipeline(raw_path: str) -> pd.DataFrame:
    # 1. 采集 + 读取
    df = pd.read_csv(raw_path)
    # 2. 清洗：去重、处理缺失
    df = df.drop_duplicates()
    df = df.dropna(subset=["label"])
    # 3. 校验：检查 schema 和范围
    assert set(["feature", "label"]).issubset(df.columns)
    assert df["label"].isin([0, 1]).all()
    # 4. 记录版本信息
    df.attrs["version"] = "v1.0.0"
    df.attrs["rows"] = len(df)
    return df

data = data_pipeline("raw.csv")
print(data.attrs)          # {'version': 'v1.0.0', 'rows': N}
```

## Feature Pipeline

特征流水线（Feature Pipeline）负责特征的计算、存储和线上线下一致性。核心挑战是「训练时算的特征」和「推理时算的特征」必须完全一致（training-serving skew）。Feast 这类 Feature Store 统一管理特征定义，让训练和在线推理复用同一套特征计算逻辑。

```text
Feature Pipeline 的关键点：
1. 特征计算 —— 离线和在线用同一套定义计算
2. 特征存储 —— 离线存历史特征，在线存实时特征
3. 一致性 —— 避免 training-serving skew
4. 复用 —— 多个模型共享特征，避免重复计算
```

```python
# 特征计算 + 一致性的核心思路
class FeatureTransformer:
    """训练和推理共用的特征计算逻辑"""
    def transform(self, df):
        df = df.copy()
        df["ratio"] = df["clicks"] / (df["impressions"] + 1)
        df["log_amount"] = df["amount"].apply(lambda x: __import__("math").log1p(x))
        df = df.fillna(0.0)
        return df

# 训练阶段
train_features = FeatureTransformer().transform(train_df)

# 推理阶段（同一套逻辑，保证一致）
online_features = FeatureTransformer().transform(online_df)
print("训练和推理共用同一 FeatureTransformer，避免 skew")
```

## Training Pipeline

训练流水线（Training Pipeline）把「训练模型」这件事自动化、可复现：触发训练、拉取数据、跑训练脚本、记录超参和指标、产出模型 artifact。它通常由调度器（如 Kubeflow Pipelines、Airflow）编排，把训练的每个步骤串起来。

```text
Training Pipeline 的关键点：
1. 触发 —— 定时、数据更新、代码提交触发训练
2. 可复现 —— 记录代码 commit、数据版本、超参、seed
3. 参数化 —— 超参作为 pipeline 参数传入，方便调参
4. 产出 —— 训练产物（模型权重 + 指标）进入 Registry
```

```python
def train_pipeline(data_version: str, hyperparams: dict):
    # 1. 加载指定版本的数据
    data = load_data(data_version)
    # 2. 用传入的超参训练
    model = train(data, **hyperparams)
    # 3. 记录超参 + 指标（实验追踪）
    log_params(hyperparams)
    metrics = evaluate(model, data)
    log_metrics(metrics)
    # 4. 保存 artifact
    save_model(model, "model.pt")
    return model, metrics

def load_data(v): return v
def train(d, **h): return h
def evaluate(m, d): return {"auc": 0.88}
def log_params(p): print("params", p)
def log_metrics(m): print("metrics", m)
def save_model(m, path): print("saved", path)
```

## Evaluation Pipeline

评估流水线（Evaluation Pipeline）在模型上线前系统化地评估它的质量：跑评测集、计算指标、和当前生产模型对比、生成评估报告，并触发审批。它是模型能否上线的「质检关卡」，把「我觉得模型好了」变成「有数据支撑模型好了」。

```text
Evaluation Pipeline 的关键点：
1. 离线评估 —— 在留出集/测试集上算指标
2. 对比 —— 新模型 vs 当前生产模型的指标对比
3. 切片 —— 按人群/场景切片评估，避免整体好但局部崩
4. 门禁 —— 指标低于阈值则阻断上线
```

```python
def evaluation_pipeline(candidate_model, current_model, test_data):
    # 1. 候选模型评估
    candidate_metrics = evaluate_model(candidate_model, test_data)
    # 2. 当前生产模型评估（同一测试集）
    current_metrics = evaluate_model(current_model, test_data)
    # 3. 对比 + 门禁
    diff = candidate_metrics["auc"] - current_metrics["auc"]
    threshold = 0.0
    approved = diff >= threshold
    return {
        "candidate": candidate_metrics,
        "current": current_metrics,
        "diff": diff,
        "approved": approved,
    }

def evaluate_model(m, d):
    return {"auc": 0.9}

report = evaluation_pipeline("new_model", "old_model", "test")
print(report["approved"])      # True / False
```

## Model Registry

模型注册表（Model Registry）在 MLOps 里是「模型资产的中央台账」：集中管理模型版本、血缘、状态流转（staging → production → archived）。它把「训练产出的模型文件」变成「可检索、可审批、可追溯的企业资产」，是连接训练侧和部署侧的枢纽。

```text
Model Registry 的关键点：
1. 版本 —— 每个模型有唯一版本号
2. 血缘 —— 追溯到数据版本、代码 commit、超参
3. 状态 —— staging / production / archived 的生命周期
4. 审批 —— 从 staging 晋升 production 需审批
```

```python
# 模型注册表状态流转（简化实现）
class ModelRegistry:
    def __init__(self):
        self.models = {}

    def register(self, name, version, metrics):
        self.models[f"{name}@{version}"] = {
            "metrics": metrics, "stage": "staging",
        }

    def promote_to_production(self, name, version):
        key = f"{name}@{version}"
        self.models[key]["stage"] = "production"

    def get_production(self, name):
        for k, v in self.models.items():
            if k.startswith(name) and v["stage"] == "production":
                return k, v
        return None

reg = ModelRegistry()
reg.register("rec", "1.0.0", {"auc": 0.82})
reg.promote_to_production("rec", "1.0.0")
print(reg.get_production("rec"))     # ('rec@1.0.0', {...})
```

## MLflow

MLflow 是最流行的开源 MLOps 平台之一，提供四大组件：Tracking（实验追踪）、Projects（代码打包）、Models（模型打包）、Registry（模型注册）。它的核心价值是「实验可追踪、模型可打包、版本可管理」，几行代码就能用，是团队快速落地 MLOps 的起点。

```text
MLflow 四大组件：
1. Tracking —— 记录参数、指标、artifact，可视化对比实验
2. Projects —— 用统一格式打包可复现的训练代码
3. Models —— 统一格式打包模型，支持多种 flavor（python/onnx）
4. Registry —— 模型版本和 stage 管理
```

```python
import mlflow
import torch
import mlflow.pytorch

# 实验追踪
with mlflow.start_run():
    mlflow.log_param("learning_rate", 0.01)
    mlflow.log_param("batch_size", 64)
    mlflow.log_metric("auc", 0.85)
    mlflow.log_metric("loss", 0.21)
    # 保存模型 artifact
    model = torch.nn.Linear(10, 1)
    mlflow.pytorch.log_model(model, "model")
```

```bash
# 启动 MLflow UI 查看实验
mlflow ui --host 0.0.0.0 --port 5000
```

## Kubeflow

Kubeflow 是跑在 Kubernetes 上的 ML 平台，把机器学习工作流容器化、编排化。核心是 Kubeflow Pipelines：用 DAG 定义数据、训练、评估各步骤，每个步骤跑在独立容器里，自动调度、可复用、可追踪。适合在 K8s 环境做大规模、标准化的训练编排。

```text
Kubeflow 的关键点：
1. Pipelines —— 用 DAG 定义 ML 工作流，步骤容器化
2. 可复用 —— 组件（component）可复用，参数化
3. K8s 原生 —— 每个步骤一个 Pod，资源隔离、可扩展
4. Notebook —— 集成 Jupyter，实验环境统一
```

```python
# Kubeflow Pipelines 组件定义（简化示意）
from kfp import dsl

@dsl.component
def train_step(data_uri: str) -> str:
    # 训练逻辑，返回模型路径
    return "s3://models/v1"

@dsl.component
def evaluate_step(model_uri: str) -> float:
    # 评估逻辑，返回指标
    return 0.85

@dsl.pipeline
def ml_pipeline(data_uri: str = "s3://data/v1"):
    train_task = train_step(data_uri=data_uri)
    evaluate_task = evaluate_step(model_uri=train_task.output)
```

## KServe

KServe 是 K8s 上的标准模型推理平台，把模型服务抽象成统一的 InferenceService 资源，支持多种推理框架（TensorFlow、PyTorch、ONNX、Triton 等），内置灰度（金丝雀）、自动扩缩容（可扩到 0）、请求路由。它是「模型服务标准化」的代表，和 Knative 深度集成。

```text
KServe 的关键点：
1. InferenceService —— 统一的模型服务资源抽象
2. 多框架 —— 一个接口支持 TF/PyTorch/ONNX/Triton 等 runtime
3. 灰度 —— 内置 canary 流量切分
4. 自动扩缩 —— 支持 scale-to-zero，按请求量扩缩容
```

```yaml
# kserve.yaml —— 定义一个推理服务
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: model-service
spec:
  predictor:
    pytorch:
      storageUri: s3://models/bert-v1
      resources:
        limits:
          nvidia.com/gpu: "1"
```

## BentoML

BentoML 是面向「模型打包 + 服务化」的框架，把训练好的模型 + 预处理逻辑 + 依赖打包成一个 Bento（标准格式），一键生成 Docker 镜像或部署到 K8s/云。它让「从模型到服务」这条路极短，适合中小团队快速上线模型。

```text
BentoML 的关键点：
1. Bento —— 模型 + 代码 + 依赖的标准打包格式
2. Service —— 用装饰器把模型封装成 HTTP 服务
3. 一键部署 —— 生成 Dockerfile、部署到 K8s/云
4. 多模型 —— 支持一个服务挂多个模型
```

```python
import bentoml

# 用装饰器把模型封装成服务
@bentoml.service
class TextClassifier:
    @bentoml.api
    def predict(self, text: str) -> str:
        # 预处理 + 推理 + 后处理
        return f"label for: {text}"

# 打包成 Bento（含模型和代码）
# bentoml build
```

```bash
# 生成 Docker 镜像并运行
bentoml containerize text_classifier:latest
docker run -p 3000:3000 text_classifier:latest
```

## Ray

Ray 是分布式计算框架，用于并行化机器学习的各个阶段：分布式训练（Ray Train）、超参调优（Ray Tune）、模型服务（Ray Serve）、数据处理（Ray Data）。它的特点是极简的 API 让 Python 代码轻松并行化、分布式化，是很多大模型训练和 RL 框架的底层引擎。

```text
Ray 的核心组件：
1. Ray Core —— 分布式任务和 actor 基础
2. Ray Train —— 分布式训练（PyTorch/TF 等）
3. Ray Tune —— 超参调优
4. Ray Serve —— 模型服务
5. Ray Data —— 分布式数据处理
```

```python
import ray

ray.init()

# 用 @ray.remote 把函数变成可分布式执行的任务
@ray.remote
def slow_compute(x):
    import time
    time.sleep(0.1)
    return x * x

# 并行执行 10 个任务
futures = [slow_compute.remote(i) for i in range(10)]
results = ray.get(futures)
print(results)               # [0, 1, 4, 9, ...]

ray.shutdown()
```

## Feast

Feast（Feature Store）是特征平台，统一管理特征的存储和服务：离线特征存历史数据供训练，在线特征存实时值供推理，并保证「训练和推理用同一套特征定义」，从根本上解决 training-serving skew。它是 ML 平台里「特征复用」的关键组件。

```text
Feast 的关键点：
1. 特征定义 —— 用 FeatureView 统一声明特征的计算和来源
2. 离线存储 —— 历史特征供训练（连数据仓库）
3. 在线存储 —— 实时特征供推理（连 Redis 等）
4. 一致性 —— 离线/在线同一套定义，避免 skew
```

```python
# Feast 特征定义（简化示意）
from feast import FeatureStore, Entity, FeatureView, Field
from feast.types import Float32

# 定义实体和特征视图
entity = Entity(name="user", join_keys=["user_id"])
feature_view = FeatureView(
    name="user_features",
    entities=[entity],
    schema=[Field(name="total_orders", dtype=Float32)],
    source="orders_table",
)

# 训练时拉取历史特征（离线）
store = FeatureStore(".")
training_df = store.get_historical_features(
    entity_df=entity_df, features=["user_features:total_orders"]
).to_df()

# 推理时拉取实时特征（在线）
online_features = store.get_online_features(
    entity_rows=[{"user_id": 123}],
    features=["user_features:total_orders"],
).to_dict()
```

## 应用场景实战

### 场景一：用 MLflow 打通「训练 → 注册 → 上线」

```python
import mlflow
from mlflow.tracking import MlflowClient

# 训练并追踪
with mlflow.start_run() as run:
    mlflow.log_param("lr", 0.01)
    mlflow.log_metric("auc", 0.86)
    # 注册模型
    mlflow.register_model(f"runs:/{run.info.run_id}/model", "rec-model")

# 把版本晋升到生产
client = MlflowClient()
client.transition_model_version_stage(
    name="rec-model", version=1, stage="Production"
)

# 查询生产模型
prod = client.get_latest_versions("rec-model", stages=["Production"])
print("生产模型:", prod[0].version)
```

### 场景二：Ray 并行化特征计算 + 训练评估

```python
import ray

ray.init(num_cpus=4)

# 用 Ray 并行处理多份数据分片
@ray.remote
def process_shard(shard):
    return sum(x for x in shard)

shards = [list(range(i * 100, (i + 1) * 100)) for i in range(4)]
results = ray.get([process_shard.remote(s) for s in shards])
print("并行计算结果:", results)

ray.shutdown()
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先落地实验追踪（MLflow Tracking），再谈平台化，否则实验全凭记忆
2. 特征统一走 Feature Store，训练和推理用同一套定义，杜绝 skew
3. 数据、特征、模型全部版本化，任何一次训练都可追溯复现
4. 评估流水线设「门禁阈值」，指标不达标自动阻断上线
5. 模型上线必须进 Registry 走状态流转，禁止绕过流程直接部署
6. 小团队从 BentoML/MLflow 起步，大团队上 Kubeflow/KServe 标准化
7. 用 Ray 加速分布式训练和调参，但先确认任务真需要分布式

### 踩坑记录

```text
坑 1：训练和推理用不同的特征计算逻辑
结论：离线 AUC 很高，线上效果很差，就是 training-serving skew。
原因：训练时特征 A 用历史统计值，推理时用实时值，逻辑不一致。
解法：特征统一进 Feature Store，离线在线共用同一套特征定义。

坑 2：实验不追踪，只靠文件名记参数
结论：跑了几十次实验，回头找不到最好的那次用了什么参数。
原因：没记录超参、数据版本、代码 commit。
解法：用 MLflow Tracking 自动记录每次实验的参数、指标、artifact。

坑 3：数据流水线不校验，脏数据直接训练
结论：模型训练到一半报错，或训出莫名其妙的结果。
原因：数据有缺失、类型错、标签异常，没做质量检查。
解法：流水线加 schema 校验、分布检查、空值率监控，异常即中断。

坑 4：模型绕过 Registry 直接部署
结论：线上模型来源不明，出问题无法追溯、无法回滚。
原因：训练完直接把权重文件拷到服务器，没走注册流程。
解法：所有模型必须注册进 Registry，从 Registry 拉取部署。

坑 5：KServe 服务没设自动扩缩，流量突增被打挂
结论：高峰期请求排队超时，服务不可用。
原因：副本数固定，没按流量自动扩缩容。
解法：配置 Knative 自动扩缩（HPA），设好最小/最大副本数。
```
