## 概述

ANN（Approximate Nearest Neighbor，近似最近邻）是向量检索的核心技术：在千万甚至亿级的向量库里，用「牺牲少量精度换极致速度」的方法快速找到与查询向量最相近的一批向量。它是双塔召回、以图搜图、语义搜索的底层引擎——没有它，embedding 召回无法在生产环境落地。

```text
ANN 的核心认知：
1. 精度换速度 —— 允许漏掉少量最近邻，把检索时间从秒级压到毫秒级
2. 三大流派 —— 哈希（LSH）、树/图（KD-Tree、HNSW）、量化/倒排（IVF、PQ）
3. 召回率指标 —— 用 Recall@k 衡量「找到的真最近邻比例」，而非是否精确
4. 内存是关键 —— PQ/OPQ 压缩向量，让亿级向量能塞进内存
```

## Brute Force

Brute Force（暴力检索 / 精确最近邻）遍历向量库里的每一条向量，逐一算距离取最小。它是唯一「100% 精确」的方法，也是所有 ANN 方法的「召回率上限基准」，常用于评估 ANN 索引到底损失了多少精度，以及小规模库（十万级以下）的直接检索。

```text
暴力检索的关键点：
1. 精确 —— 遍历所有向量，结果一定是真最近邻
2. 复杂度 —— O(N·d)，N 是库大小，d 是维度，库一大就扛不住
3. 基准 —— 任何 ANN 的 Recall 都是相对它的结果算出来的
4. 加速技巧 —— 矩阵化计算、SIMD、GPU 批量算距离
```

```python
import numpy as np

def brute_force_search(query, db, k=5):
    # 余弦相似度（向量已归一化时等价内积）
    sims = db @ query                 # [N]，批量矩阵乘
    idx = np.argsort(-sims)[:k]       # 降序取 Top-K
    return idx, sims[idx]

query = np.random.randn(128).astype(np.float32)
query = query / np.linalg.norm(query)
idx, sims = brute_force_search(query, db_vectors, k=5)
print("暴力检索 Top-5 相似度:", np.round(sims, 3))
```

## LSH

LSH（Locality-Sensitive Hashing，局部敏感哈希）用一组随机超平面（或随机投影）把向量哈希到桶里，保证「相似的向量大概率落到同一个桶」。查询时只对同桶向量算精确距离，用概率保证召回，适合高维空间，但召回率与哈希参数敏感。

```text
LSH 的关键点：
1. 核心性质 —— 相似向量哈希碰撞概率高，不相似的低
2. 随机超平面 —— 用 d 个超平面把向量映射成 d 位二进制码
3. 多表组合 —— 多个哈希表（或长码）提高召回，代价是更多桶要查
4. 高维有效 —— 维度越高，距离集中在均值附近，LSH 越能发挥作用
```

```python
import numpy as np

class RandomProjectionLSH:
    def __init__(self, n_bits=16, n_tables=4, seed=0):
        np.random.seed(seed)
        self.n_bits = n_bits
        self.n_tables = n_tables
        # 每张表一组随机超平面
        self.planes = [np.random.randn(n_bits, 128) for _ in range(n_tables)]
        self.tables = [{} for _ in range(n_tables)]

    def hash_vec(self, v, t):
        bits = (self.planes[t] @ v) >= 0      # 超平面两侧
        code = bits.dot(1 << np.arange(self.n_bits))   # 二进制 → 整数桶号
        return code

    def build(self, db):
        for i, v in enumerate(db):
            for t in range(self.n_tables):
                code = self.hash_vec(v, t)
                self.tables[t].setdefault(code, []).append(i)

    def search(self, q, k=5):
        cand = set()
        for t in range(self.n_tables):
            code = self.hash_vec(q, t)
            cand.update(self.tables[t].get(code, []))
        cand = list(cand)
        if not cand:
            return []
        sims = db_vectors[cand] @ q
        top = np.argsort(-sims)[:k]
        return [cand[i] for i in top]

lsh = RandomProjectionLSH(n_bits=8, n_tables=4)
lsh.build(db_vectors[:50_000])           # 先建 5 万条
print("LSH 检索结果:", lsh.search(query, k=5))
```

## KD-Tree

KD-Tree（K 维树）把空间按维度递归二分，构造一棵二叉树，查询时按「最近邻优先」遍历并剪枝。它在低维（几十维以内）效果很好、构建快，但维度一高（如 128 维 embedding）性能急剧退化，几乎退化成暴力检索，因此不适用于高维向量。

```text
KD-Tree 的关键点：
1. 空间划分 —— 每层选一个维度按中位数切分，节点是超平面
2. 查询剪枝 —— 维护当前最近距离，跳过不可能更近的子树
3. 维度诅咒 —— 维度高时切分效率骤降，性能逼近暴力检索
4. 适用 —— 地理坐标、低维特征（2~30 维）效果最佳
```

```python
from sklearn.neighbors import KDTree
import numpy as np

# 低维场景示例：2 维坐标点
points = np.random.randn(1000, 2)
tree = KDTree(points, leaf_size=30)
dist, ind = tree.query([[0.1, 0.1]], k=5)
print("KD-Tree 最近邻索引:", ind[0], "距离:", np.round(dist[0], 3))
```

```text
维度对 KD-Tree 的影响（概念性说明）：
维度 = 2    → 查询高效，远优于暴力
维度 = 20   → 性能接近暴力检索
维度 = 128  → 基本退化为暴力，应改用 LSH / HNSW / IVF-PQ
```

## HNSW

HNSW（Hierarchical Navigable Small World，分层可导航小世界图）是目前综合表现最好的图索引之一：把向量组织成多层「小世界图」，上层稀疏做快速跳转，底层稠密做精细搜索，配合贪心搜索在图上高效逼近最近邻，召回率高、查询快。

```text
HNSW 的关键点：
1. 多层图 —— 顶层节点少、边多，快速定位；底层节点全、边少，精细搜索
2. 贪心搜索 —— 从顶层入口节点出发，每步走向更近的邻居，逐层下钻
3. 参数 —— M（每节点连接数）、efConstruction（建图搜索宽度）、efSearch（查询宽度）
4. 代价 —— 高召回高速度，但内存占用大（图结构本身吃内存）
```

```python
import numpy as np

# 用 hnswlib 构建 HNSW 索引（若未安装则提示）
try:
    import hnswlib
    dim = 128
    index = hnswlib.Index(space="cosine", dim=dim)

    index.add_items(db_vectors[:50_000])
    index.set_ef(100)                 # 查询时搜索宽度
    labels, distances = index.knn_query(query.reshape(1, -1), k=5)

    print("hnswlib 未安装，可 pip install hnswlib 后运行；核心参数 M/ef 如上注释")
```

## IVF

IVF（Inverted File，倒排索引）先用聚类（如 K-Means）把向量库分成多个簇（cell），查询时只搜索与查询向量最近的若干个簇，而非全库。它把「全库暴力」缩小成「局部暴力」，大幅提速，是 FAISS 里最常用的索引组件之一。

```text
IVF 的关键点：
1. 聚类分桶 —— 训练 nlist 个聚类中心，每个向量归到最近的中心
2. 查询 —— 只访问 nprobe 个最近的簇，nprobe 越大越准越慢
3. 参数 —— nlist（簇数）、nprobe（查询探针数）
4. 与量化组合 —— IVF-PQ 是 FAISS 最经典的组合索引
```

```python
import numpy as np
from sklearn.cluster import KMeans

class SimpleIVF:
    def __init__(self, nlist=64, nprobe=4):
        self.nlist, self.nprobe = nlist, nprobe

    def build(self, db):
        self.kmeans = KMeans(n_clusters=self.nlist, n_init=1, random_state=0).fit(db)
        self.inverted = {i: [] for i in range(self.nlist)}
        for idx, v in enumerate(db):
            c = int(self.kmeans.predict(v.reshape(1, -1))[0])
            self.inverted[c].append(idx)

    def search(self, q, k=5):
        # 找最近的 nprobe 个簇中心
        center_sim = self.kmeans.cluster_centers_ @ q
        probe = np.argsort(-center_sim)[:self.nprobe]
        cand = [i for c in probe for i in self.inverted[c]]
        sims = db_vectors[cand] @ q
        top = np.argsort(-sims)[:k]
        return [cand[i] for i in top]

ivf = SimpleIVF(nlist=64, nprobe=8)
ivf.build(db_vectors[:50_000])
print("IVF 检索结果:", ivf.search(query, k=5))
```

## PQ

PQ（Product Quantization，乘积量化）把高维向量切成若干子段，每段用独立的码本（K-Means 聚类中心）量化成短码，用「几个短码」近似整条向量。它能把 128 维 float32 向量压到几十字节，内存省一个数量级，是亿级向量内存化的关键。

```text
PQ 的关键点：
1. 分段量化 —— 把 d 维切成 m 段，每段 d/m 维，各自聚类成 256 个中心
2. 压缩 —— 每段只存码本索引（1 字节），m 段共 m 字节，替代 4d 字节
3. 距离 —— 预计算「查询子段到各码本中心」的距离表，查表加速
4. 有损 —— 量化引入误差，m 越大越准但占用越多
```

```python
import numpy as np
from sklearn.cluster import KMeans

class SimplePQ:
    def __init__(self, m=16, nbits=8):
        self.m, self.nbits = m, nbits
        self.ks = 1 << nbits

    def build(self, db):
        d = db.shape[1]
        self.sub_d = d // self.m
        self.codebooks = []
        self.codes = np.zeros((len(db), self.m), dtype=np.uint8)
        for seg in range(self.m):
            sub = db[:, seg * self.sub_d:(seg + 1) * self.sub_d]
            km = KMeans(n_clusters=min(self.ks, len(sub)), n_init=1, random_state=0).fit(sub)
            self.codebooks.append(km.cluster_centers_)
            self.codes[:, seg] = km.predict(sub)

    def encode(self, v):
        # 每段找最近的码本中心，返回其索引作为短码
        codes = []
        for s in range(self.m):
            sub = v[s * self.sub_d:(s + 1) * self.sub_d]
            dist = np.linalg.norm(self.codebooks[s] - sub, axis=1)
            codes.append(int(np.argmin(dist)))
        return codes

pq = SimplePQ(m=16)
pq.build(db_vectors[:50_000])
print("压缩后单条向量占用:", pq.m, "字节（原 128×4=512 字节）")
print("码本数量:", len(pq.codebooks), "每本中心数:", pq.codebooks[0].shape[0])
```

## OPQ

OPQ（Optimized Product Quantization，优化乘积量化）在 PQ 之前先对向量做一次正交旋转（学习一个旋转矩阵 R），让各个子段上的数据分布更均匀、量化误差更小。它是 PQ 的精度增强版，只多一次矩阵乘法，却能在相同内存下显著提升召回率。

```text
OPQ 与 PQ 的区别：
1. PQ —— 直接按原始维度切段量化，子段间方差可能不均衡
2. OPQ —— 先乘旋转矩阵 R 再切段，使各子段方差均衡，量化更高效
3. 收益 —— 相同码长下召回率更高，或相同召回率下码更短
4. 代价 —— 多存一个旋转矩阵 + 查询时多一次矩阵乘
```

```python
import numpy as np

# OPQ 的核心：学习正交旋转矩阵（这里用随机正交矩阵示意）
def random_orthogonal(dim, seed=0):
    np.random.seed(seed)
    a = np.random.randn(dim, dim)
    q, _ = np.linalg.qr(a)          # QR 分解得到正交矩阵 Q
    return q

R = random_orthogonal(128)
# 先旋转再送入 PQ（复用了上一节的 PQ 结构）
rotated = (db_vectors[:50_000] @ R).astype(np.float32)
pq_opq = SimplePQ(m=16)
pq_opq.build(rotated)
print("OPQ 旋转矩阵形状:", R.shape, "| 旋转后仍为 128 维")
```

## ScaNN

ScaNN（Scalable Nearest Neighbors，Google 开源）的核心是「各向异性向量量化」（Anisotropic Quantization）：先把内积检索转化为 MIPS（最大内积搜索），再对量化误差按其对内积的影响加权，优先保留「对检索分数影响大」的分量，在相同压缩率下取得更高召回率。

```text
ScaNN 的关键点：
1. MIPS 转化 —— 用「附加维度」把内积变成 L2 距离，统一检索范式
2. 各向异性量化 —— 按分量对检索分数的重要性分配量化精度
3. 高召回 —— 在极高压缩率下仍保持高 Recall@k，内存效率突出
4. 适用 —— 大规模 embedding 检索（如双塔召回、语义检索）
```

```python
# ScaNN 的使用示意（概念级，需 pip install scann）
print("ScaNN 核心思路（伪代码级示意）：")
print("1. 对向量附加一个维度，把内积搜索转为 L2 距离搜索（MIPS 转化）")
print("2. 学习各向异性量化，让量化误差尽量不落在检索敏感的分量上")
print("3. 构建倒排 + 量化索引，查询时 nprobe 个 cell 内精确重排")
```

## FAISS

FAISS（Facebook AI Similarity Search）是 Meta 开源的向量检索库，把 IVF、PQ、HNSW、OPQ、LSH 等索引组件做成可自由组合的工厂模式，CPU/GPU 都能跑，是业界向量召回的事实标准。它的 `index_factory` 让用户用字符串描述「IVF + PQ + 重排」的组合。

```text
FAISS 的关键点：
1. 索引工厂 —— "IVF4096,PQ64" 这样的字符串直接描述索引结构
2. 组合灵活 —— 倒排（IVF）+ 量化（PQ/OPQ）+ 精排（refine）自由拼装
3. 训练/添加/检索 —— train → add → search 三步标准流程
4. 多后端 —— CPU 单机、GPU 加速、分布式（分布式靠外部分片）
```

```python
try:
    import faiss
    import numpy as np
    d = 128
    # 索引工厂：先 IVF 倒排，再 PQ 量化压缩
    index = faiss.index_factory(d, "IVF256,PQ32")
    index.train(db_vectors[:20_000])            # 训练聚类中心 + 码本
    index.add(db_vectors[:50_000])              # 添加向量
    index.nprobe = 16                           # 查询探针数
    D, I = index.search(query.reshape(1, -1), 5)
    print("FAISS 检索 Top-5:", I[0], "距离:", np.round(D[0], 3))
except ImportError:
    print("faiss 未安装，可 pip install faiss-cpu 后运行；工厂字符串如 IVF256,PQ32")
```

## DiskANN

DiskANN（Microsoft 开源）把索引构建在 SSD 上，用「图索引 + SSD 分页 + 内存缓存热数据」的方式，在单机内存装不下的超大规模（十亿级）向量库上实现低延迟高召回检索，解决「内存放不下、又要快」的矛盾。

```text
DiskANN 的关键点：
1. SSD 存图 —— 图索引本体放磁盘，突破内存容量上限
2. 热数据缓存 —— 常访问的节点驻留内存，冷数据按需从 SSD 读
3. 单机十亿级 —— 在一台机器上即可服务十亿向量，成本大幅下降
4. 适合场景 —— 内存不足以容纳全库、但需在线低延迟检索
```

```python
# DiskANN 的使用示意（概念级，需单独部署其服务）
print("DiskANN 核心设计（概念级说明）：")
print("1. 离线：构建图索引，通过重排优化节点在 SSD 上的物理布局（减少随机读）")
print("2. 在线：贪心搜索在图上遍历，热节点走内存、冷节点走 SSD 异步预取")
print("3. 结果：单机十亿向量，Recall@10 可到 95%+，延迟在毫秒级")
print("4. 对比：内存装不下全库时，DiskANN 是比分布式内存索引更省成本的方案")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先跑暴力检索拿到「精确 Top-K」作基准，再评估 ANN 索引的 Recall@k
2. 选索引看规模：小库暴力、中库 HNSW/IVF-PQ、大库 ScaNN/OPQ、超大盘 DiskANN
3. 向量先 L2 归一化，用余弦/内积检索，距离度量和训练时必须一致
4. nprobe/efSearch 是「召回率 vs 延迟」的旋钮，用线上压测确定最优值
5. IVF 类索引的 nlist 按「库大小开根号」附近取值，PQ 子段数按维度与内存预算选
6. 索引要支持增量更新（add/remove），并定期重建，避免量化码本过时

### 踩坑记录

```text
坑 1：向量没归一化却用内积/余弦检索
结论：检索结果与模型训练时计算的相似度不一致，召回质量下降。
原因：内积会放大向量模长的影响，未归一化时「模长大的向量」天然占优。
解法：入库和查询向量统一 L2 归一化，或统一改用明确的距离度量。

坑 2：nprobe/efSearch 设太小
结论：检索速度很快，但 Recall@10 掉到 70% 以下，大量好物品漏召回。
原因：探针数/搜索宽度太小，只搜了很少的簇或图分支，错过最近邻。
解法：以 Recall@k 为目标逐步加大 nprobe/efSearch，在延迟预算内取最大值。

坑 3：用 KD-Tree 检索高维 embedding
结论：128 维向量上 KD-Tree 查询比暴力还慢，白折腾。
原因：高维空间下 KD-Tree 的剪枝失效，退化甚至劣于暴力检索。
解法：高维向量用 LSH / HNSW / IVF-PQ，KD-Tree 只留给低维（<30 维）。

坑 4：PQ 子段数 m 设太小
结论：内存省了，但量化误差巨大，召回率断崖式下跌。
原因：m 太小导致每段维度过高、码本不够精细，近似向量失真严重。
解法：m 按「维度/子段维度 ≈ 8~16」选，量化后再实测 Recall 是否达标。

坑 5：只建索引不评估召回率
结论：索引看似正常，上线后推荐效果却比离线评估差一截。
原因：ANN 是有损检索，不量化「漏了多少最近邻」就不知道损失在哪。
解法：以暴力检索为基准，上线前必测 Recall@k，并观察在线召回指标。
```
