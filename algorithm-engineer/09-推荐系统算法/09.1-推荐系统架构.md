## 概述

推荐系统是一套「从海量物品中，为每个用户挑出他最可能感兴趣的一小撮物品」的工程系统。它不是一个单一模型，而是一条由数据、召回、排序、重排、在线服务、反馈闭环组成的流水线，每一环都决定了最终效果的上限。

```text
推荐系统架构的核心认知：
1. 漏斗结构 —— 从亿级候选（召回）到百级候选（排序）再到十级（重排），层层过滤
2. 召回求全、排序求准 —— 召回管「别漏掉」，排序管「排得对」
3. 特征是燃料 —— Feature Store 统一管理线上线下特征，保证一致性
4. 反馈闭环 —— 用户行为回流到数据层，驱动模型持续迭代
```

```python
# 推荐系统流水线的极简示意：从全量物品到最终展示列表
def recommend_pipeline(user_id, topk=10):
    candidates = recall(user_id)          # 召回：亿级 → 千级
    scored = rank(user_id, candidates)    # 排序：千级 → 百级（打分排序）
    final = rerank(user_id, scored)       # 重排：百级 → 十级（多样性/策略）
    return final[:topk]

# 每一环用不同模型/规则实现，下面各节分别展开
```

## 数据采集

数据采集是推荐系统的起点，负责把用户与系统的每一次交互（曝光、点击、收藏、购买、停留时长、负反馈）实时或近实时地记录下来。数据质量直接决定模型上限，是「垃圾进、垃圾出」的第一道闸口。

```text
采集的关键维度：
1. 曝光/点击/转化 —— 构成正负样本的基础，是监督信号来源
2. 上下文 —— 时间、地点、设备、来源渠道、query
3. 行为权重 —— 浏览 < 点击 < 收藏 < 加购 < 下单，时长与频次也编码强度
4. 负反馈 —— 不点、划走、举报、屏蔽，常被忽略却很重要
```

```python
import json
from datetime import datetime

# 埋点日志的典型字段设计（示例）
def build_event_log(user_id, item_id, event_type, extra=None):
    return {
        "user_id": user_id,
        "item_id": item_id,
        "event_type": event_type,      # expose / click / favorite / purchase
        "ts": int(datetime.now().timestamp()),
        "context": {"device": "android", "channel": "feed", "pos": 3},
        "extra": extra or {},
    }

event = build_event_log("u_1001", "item_889", "click")
print(json.dumps(event, ensure_ascii=False))
```

## 用户画像

用户画像把用户的属性、兴趣和行为抽象成结构化标签或向量，是召回和排序模型最主要的输入之一。画像分静态属性（年龄、性别、城市）与动态兴趣（近期点击品类、价格偏好、活跃时段），后者对推荐效果影响更大。

```text
用户画像的层次：
1. 基础属性 —— 人口统计、注册信息（静态、稀疏）
2. 行为画像 —— 由历史行为聚合出的兴趣分布（动态、最关键）
3. 实时画像 —— 会话内最近行为，捕捉短期兴趣漂移
4. 向量画像 —— 用 embedding 表达用户，供双塔召回直接点积
```

```python
from collections import Counter

# 从点击历史聚合出「品类兴趣分布」画像
click_history = ["数码", "数码", "图书", "运动", "数码", "图书", "运动", "运动"]
interest = Counter(click_history)
total = sum(interest.values())
profile = {cat: cnt / total for cat, cnt in interest.most_common()}
print("品类兴趣分布:", profile)
# {'数码': 0.375, '运动': 0.375, '图书': 0.25}
```

## Item Profile

Item Profile（物品画像）是物品侧的结构化描述：品类、品牌、价格、标签、关键词、内容 embedding、质量分、时效性等。它是内容推荐和向量召回的基础，决定了「物以类聚」能不能算得准。

```text
Item Profile 的构成：
1. 结构化属性 —— 类目、品牌、价格、地域、上架时间
2. 内容特征 —— 标题/正文/图片的 NLP 与 CV 特征、tag、关键词
3. 质量与热度 —— 质量分、CTR、转化率、库存、下架状态
4. 向量表示 —— item embedding，用于相似度召回与双塔模型
```

```python
# Item Profile 的字典结构示例
item_profile = {
    "item_id": "item_889",
    "category": "数码",
    "brand": "BrandX",
    "price": 2999.0,
    "tags": ["手机", "5G", "拍照"],
    "quality_score": 4.8,
    "ctr_7d": 0.12,          # 近 7 天点击率
    "embedding": None,       # 由模型生成的向量（见矩阵分解/深度推荐篇）
    "online": True,
}

def is_available(item):
    return item["online"] and item["quality_score"] >= 3.0

print(is_available(item_profile))   # True
```

## Feature Store

Feature Store（特征平台）统一管理特征的「离线训练」与「在线推理」两份定义，解决特征线上线下不一致这一推荐系统最常见的隐蔽 bug。它保证训练时用的特征和上线时算的特征用同一套代码、同一套口径。

```text
Feature Store 的核心价值：
1. 一致性 —— 训练/推理同源，避免 Training-Serving Skew
2. 复用 —— 特征只写一次，多个模型共享
3. 时点正确 —— 支持 point-in-time join，避免标签泄露
4. 低延迟 —— 在线特征存储支持毫秒级读取
```

```python
# 特征注册与拉取的抽象示意（离线批特征 + 在线实时特征）
class FeatureStore:
    def __init__(self):
        self.registry = {}       # 特征名 -> 定义
        self.online_store = {}   # 在线 KV 存储（如 Redis）

    def register(self, name, definition):
        self.registry[name] = definition

    def set_online(self, key, features):
        self.online_store[key] = features

    def get_online(self, key):
        return self.online_store.get(key, {})

fs = FeatureStore()
fs.register("user_age", "user 注册年龄，int，缺失填 -1")
fs.register("item_ctr_7d", "item 近 7 天 ctr，float，天级更新")
fs.set_online("u_1001", {"user_age": 28, "city_tier": 2})
print(fs.get_online("u_1001"))   # {'user_age': 28, 'city_tier': 2}
```

## Candidate Generation

Candidate Generation（召回 / 候选生成）从百万到亿级的全量物品中，用轻量、高召回率的方法捞出几百到几千个候选。它不追求精确排序，只追求「真正感兴趣的物品尽量别漏」，用多种召回通道互补来逼近高召回。

```text
召回通道的组合拳：
1. 多路召回 —— 协同过滤、向量、热门、地域、新物品、实时兴趣，各捞一批
2. 通道互补 —— 有的准、有的全、有的追新、有的兜底
3. 性能优先 —— 用倒排索引、向量索引、缓存，毫秒级返回
4. 上限决定论 —— 排序再强也救不回「没被召回的物品」
```

```python
# 多路召回 + 合并去重 + 通道来源标注
def multi_channel_recall(user_id):
    candidates = {}
    for channel, items in [
        ("user_cf", ["i_1", "i_2", "i_3"]),
        ("vector",  ["i_2", "i_4", "i_5"]),
        ("hot",     ["i_6", "i_7"]),
        ("fresh",   ["i_8", "i_4"]),
    ]:
        for it in items:
            candidates.setdefault(it, []).append(channel)
    return candidates

merged = multi_channel_recall("u_1001")
print("候选数:", len(merged), "| 通道标注:", merged["i_2"])
# 候选数: 8 | 通道标注: ['user_cf', 'vector']
```

## Ranking

Ranking（精排 / 排序）对召回出来的几百到几千个候选，用复杂模型（通常是深度 CTR/CVR 预估模型）精确打分，再按分数排序取 Top-N。它是整个漏斗里「算力最重、模型最复杂、对准确率影响最大」的一环。

```text
排序阶段的关键点：
1. 目标建模 —— CTR、CVR、时长、GMV 等，可单目标或多目标融合
2. 特征更全 —— 用户画像、物品画像、交叉特征、序列特征、上下文
3. 模型更重 —— 精排模型复杂度远高于召回，Latency 预算在几十毫秒
4. 分数可解释 —— 产出的是可排序的分数，也用于后续校准与融合
```

```python
import numpy as np

# 排序打分示意：用特征向量加权 + 非线性变换模拟 CTR 预估
def ctr_score(features, weights):
    z = np.dot(features, weights)
    return 1 / (1 + np.exp(-z))          # sigmoid 映射到 (0, 1)

weights = np.array([0.8, -0.3, 1.2])     # 假设已训练好的参数
candidates = {
    "i_1": np.array([1.0, 0.5, 0.2]),
    "i_2": np.array([0.3, 0.1, 0.9]),
    "i_4": np.array([0.6, 0.0, 0.7]),
}
ranked = sorted(candidates.items(), key=lambda kv: ctr_score(kv[1], weights), reverse=True)
print([(k, round(ctr_score(v, weights), 3)) for k, v in ranked])
```

## Re-ranking

Re-ranking（重排）在精排分数的基础上，施加业务规则与策略约束：打散同品类、去重相似内容、保证多样性、插入广告/运营位、控制作者配额、做冷启动保护等。它让最终列表既「准」又「好看、健康、符合业务目标」。

```text
重排的典型策略：
1. 多样性 —— 同类目打散，避免列表单调，提升浏览深度
2. 业务约束 —— 广告位、置顶位、运营强插、品牌保护
3. 公平性 —— 作者/店铺配额，防止头部垄断
4. 贪心 / MMR / 序列模型 —— 从简单规则到 learning-to-rerank
```

```python
# 基于 MMR（最大边际相关）的多样性重排示意
def mmr_rerank(items, scores, sim, lam=0.7):
    selected, remaining = [], list(items)
    while remaining:
        def gain(it):
            rel = scores[it]
            div = max([sim(it, s) for s in selected], default=0.0)
            return lam * rel - (1 - lam) * div
        best = max(remaining, key=gain)
        selected.append(best); remaining.remove(best)
    return selected

scores = {"i_1": 0.9, "i_2": 0.85, "i_3": 0.88, "i_4": 0.7}
cat = {"i_1": "数码", "i_2": "数码", "i_3": "图书", "i_4": "运动"}
sim = lambda a, b: 1.0 if cat[a] == cat[b] else 0.0
print(mmr_rerank(["i_1", "i_2", "i_3", "i_4"], scores, sim))
# 同品类 i_1/i_2 被拆开，得到更均衡的列表
```

## Online Serving

Online Serving（在线服务）把训练好的模型与特征装配成低延迟、高可用的在线推理服务。它要在严格的延迟预算内完成「取特征 → 召回 → 排序 → 重排 → 返回」全流程，并做好模型版本管理与灰度发布。

```text
在线服务的要求：
1. 低延迟 —— 端到端通常要求 100ms 以内，长尾要优化到几十毫秒
2. 高可用 —— 多副本、降级策略、兜底逻辑，失败不能白屏
3. 模型热更 —— 新模型无损上线，支持 A/B 与灰度
4. 缓存与异步 —— 画像缓存、结果缓存、异步日志落盘
```

```python
# 在线服务骨架：带降级与缓存的推荐接口
class ServingLayer:
    def __init__(self):
        self.cache = {}
        self.fallback = ["i_hot_1", "i_hot_2", "i_hot_3"]   # 兜底热门

    def serve(self, user_id):
        if user_id in self.cache:               # 命中缓存直接返回
            return self.cache[user_id]
        try:
            result = recommend_pipeline(user_id)
        except Exception:
            result = self.fallback             # 任何异常走兜底
        self.cache[user_id] = result
        return result

sl = ServingLayer()
print(sl.serve("u_1001"))
```

## Feedback Loop

Feedback Loop（反馈闭环）把上线后的真实用户行为（尤其是曝光后的点击/转化）回流到数据层，作为新的训练样本，驱动模型周期性或实时地更新。它是推荐系统「越用越准」的动力来源，也是发现效果问题的观测窗口。

```text
反馈闭环的组成：
1. 行为回流 —— 线上曝光与点击实时进入样本流
2. 指标监控 —— CTR、CVR、时长、留存、GMV 的实时看板
3. 模型迭代 —— 离线训练 → 评估 → 上线 → 再回流，形成闭环
4. 纠偏 —— 曝光偏差、位置偏差、流行度偏差需要被建模纠正
```

```python
# 反馈闭环的样本拼接示意：曝光日志 + 点击日志 → 训练样本
exposures = {"u_1001": [("i_1", 1), ("i_2", 0), ("i_3", 1)]}   # item, 是否点击
clicks = {"u_1001": [("i_1", 5), ("i_3", 2)]}                  # item, 停留秒数

def build_samples(exposures, clicks):
    samples = []
    for uid, exp_list in exposures.items():
        for item, clicked in exp_list:
            label = 1 if clicked else 0
            samples.append({"user": uid, "item": item, "label": label})
    return samples

print(build_samples(exposures, clicks))
```

## 应用场景实战

### 场景一：短视频 Feed 流的漏斗设计

```python
# 用数字模拟一个短视频 Feed 的漏斗：亿级候选 → 千人千面的几十条
def feed_funnel(total_pool=100_000_000):
    recalled = int(total_pool * 0.001)        # 多路召回：10 万
    ranked = int(recalled * 0.01)             # 精排后：1000
    reranked = int(ranked * 0.05)             # 重排后：50
    shown = 10                                # 首屏展示：10
    print(f"全量 {total_pool:,} → 召回 {recalled:,} → 精排 {ranked:,} → 重排 {reranked:,} → 展示 {shown}")

feed_funnel()
# 全量 100,000,000 → 召回 100,000 → 精排 1,000 → 重排 50 → 展示 10
```

### 场景二：电商「猜你喜欢」的架构落地

```text
电商猜你喜欢的典型链路：
1. 数据采集：曝光/点击/加购/下单全埋点
2. 召回：UserCF（买了又买）+ ItemCF（看了又看）+ 向量召回 + 新品/爆款通道
3. 精排：深度 CTR/CVR 预估，特征含用户画像、商品画像、行为序列
4. 重排：同店铺打散、价格带均衡、广告位插入
5. 在线：结果页接口 100ms 内返回，异常走爆款兜底
6. 反馈：点击/下单回流，天级更新模型，实时更新画像
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先搭通「采集 → 召回 → 排序 → 重排 → 服务 → 反馈」最小闭环，再逐环优化
2. 召回走多路互补，用「召回率」评估而不是「准确率」，排序才看准不准
3. 特征统一走 Feature Store，杜绝线上线下口径不一致
4. 在线服务必须带降级与兜底，任何依赖失败都不能影响主流程可用性
5. 反馈闭环要监控曝光偏差、位置偏差，样本不纠偏模型会越学越偏
6. 画像分静态/动态/实时三层，短期兴趣用实时画像，长期兴趣用行为聚合

### 踩坑记录

```text
坑 1：训练特征与线上特征口径不一致
结论：离线 AUC 很高，上线 CTR 反而跌，排查发现特征定义两边不同。
原因：离线用批处理算的「历史点击数」，线上用实时流算的「当前点击数」，分母窗口不同。
解法：特征统一在 Feature Store 定义，训练和推理调用同一份特征计算代码。

坑 2：召回只看准确率
结论：某召回通道准确率极高，但整体推荐效果变差，很多好物品根本没进候选。
原因：准确率高往往意味着召回太少、太保守，漏掉了大量潜在兴趣物品。
解法：召回阶段用召回率、覆盖率评估，允许多路召回引入「不那么准但更全」的通道。

坑 3：在线服务没有兜底
结论：特征服务抖动或模型超时，直接导致推荐接口报错，用户看到空白页。
原因：链路长、依赖多，任何一个环节失败都可能导致整体雪崩。
解法：每个依赖设超时与降级，最终兜底到热门/运营列表，保证永远有内容返回。

坑 4：忽略了反馈中的偏差
结论：模型学到「位置越靠前越容易被点」，而不是「内容越好越被点」。
原因：曝光本身受位置、流量分配影响，直接拿曝光点击当样本会放大马太效应。
解法：建模位置偏差、做负采样、用 IPS 等纠偏方法，或至少按位置分层分析。

坑 5：画像更新太慢导致兴趣滞后
结论：用户已经转去看别的品类，推荐还在推一周前的兴趣。
原因：画像只用天级批任务聚合，实时兴趣没进模型。
解法：加实时画像层，会话内行为秒级更新，与长期画像共同输入模型。
```
