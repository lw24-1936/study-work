## 概述

操作系统是硬件与应用之间的「管家」：管理 CPU、内存、磁盘、网络等资源，为程序提供统一抽象。算法工程师日常打交道的是进程、线程、内存和容器，理解这些能避免大量性能陷阱和生产事故。

```text
核心要点：
1. 资源管理 —— CPU 调度、内存分配、设备访问都归 OS 管
2. 抽象接口 —— 进程/线程/文件/虚拟内存是 OS 给的抽象
3. 隔离保护 —— 进程间隔离、用户态/内核态隔离
4. 容器基石 —— cgroups + namespace 是 Docker/K8s 的底层
```

## 进程

进程是「运行中的程序」，是资源分配的基本单位。每个进程有独立的地址空间、文件描述符等资源，进程间相互隔离。

```text
进程核心要素：
1. 地址空间 —— 独立虚拟内存，互不干扰
2. 状态 —— 就绪 / 运行 / 阻塞 / 结束
3. PCB —— 进程控制块，保存进程元信息
4. 上下文切换 —— 切换进程要保存/恢复寄存器、页表等
```

```python
# multiprocessing 创建进程
import multiprocessing as mp, os
def worker(name):
    print(f"进程 {name}，PID={os.getpid()}，父进程={os.getppid()}")
if __name__ == "__main__":
    procs = [mp.Process(target=worker, args=(i,)) for i in range(3)]
    [p.start() for p in procs]; [p.join() for p in procs]
```

```text
进程 vs 线程：进程是资源分配单位（独立地址空间、隔离强、切换贵）；线程是调度单位（共享地址空间、隔离弱、切换便宜）。
```

## 线程

线程是 CPU 调度的最小单位，同一进程内的线程共享地址空间，但各自拥有独立的栈和寄存器。

```text
线程核心概念：
1. 共享 —— 同进程线程共享堆、全局变量、文件描述符
2. 独立 —— 每个线程有自己的栈、程序计数器、寄存器
3. 竞争 —— 共享数据需加锁，否则数据竞争
4. GIL —— CPython 全局解释器锁，限制多线程并行计算
```

```python
# 线程 + 锁保护共享数据
import threading
counter = 0; lock = threading.Lock()
def inc(n):
    global counter
    for _ in range(n):
        with lock: counter += 1
threads = [threading.Thread(target=inc, args=(100000,)) for _ in range(8)]
[t.start() for t in threads]; [t.join() for t in threads]
print(f"counter = {counter}")   # 加锁后 = 800000
```

```python
# 不加锁的后果：数据竞争
counter = 0
def inc_no_lock(n):
    global counter
    for _ in range(n): counter += 1   # 非原子，丢更新
threads = [threading.Thread(target=inc_no_lock, args=(100000,)) for _ in range(8)]
[t.start() for t in threads]; [t.join() for t in threads]
print(f"counter = {counter}")   # 通常 < 800000
```

## 虚拟内存

虚拟内存为每个进程提供独立、连续的虚拟地址空间，通过页表映射到物理内存，实现进程隔离、内存超分配和按需加载。

```text
虚拟内存机制：
1. 地址映射 —— 虚拟地址 →（页表）→ 物理地址
2. 分页 —— 内存按固定大小页（通常 4KB）管理
3. 缺页中断 —— 访问不在内存的页时从磁盘换入
4. 交换（swap）—— 内存不够时把不活跃页换到磁盘
```

```python
# 查看进程内存：VMS 与 RSS
import psutil, os
proc = psutil.Process(os.getpid())
mem = proc.memory_info()
print(f"虚拟内存 VMS：{mem.vms/1e6:.1f} MB")
print(f"常驻内存 RSS：{mem.rss/1e6:.1f} MB")
# VMS 常远大于 RSS，差值是未真正占用的虚拟地址空间
```

```text
惰性分配：malloc 只「承诺」虚拟地址，真正访问时才分配物理页。大量分配 + 少量访问 → VMS 大、RSS 小。
```

## 文件系统

文件系统组织和管理磁盘数据，提供「文件 + 目录」抽象，负责把文件名映射到磁盘块，并管理权限、元数据和空闲空间。

```text
文件系统概念：
1. 文件 —— 命名的一串字节，有 inode 存元数据
2. inode —— 存权限、大小、数据块指针等元信息
3. 目录 —— 文件名到 inode 的映射表
4. 常见 —— ext4/xfs（本地）、tmpfs（内存）、NFS（共享）、S3（对象）
```

```python
# 文件元数据、硬链接、软链接
import os
path = "/tmp/fs_demo.txt"
open(path, "w").write("hello filesystem")
st = os.stat(path)
print(f"inode={st.st_ino} 大小={st.st_size} 权限={oct(st.st_mode & 0o777)}")
os.link(path, "/tmp/fs_hard.txt")      # 硬链接，同一 inode
os.symlink(path, "/tmp/fs_soft.txt")   # 软链接，指向路径
print("硬链接同 inode：", os.stat("/tmp/fs_hard.txt").st_ino == st.st_ino)
print("软链接是链接：", os.path.islink("/tmp/fs_soft.txt"))
```

## 系统调用

系统调用是用户程序请求内核服务的唯一合法入口：用户态程序通过 syscall 陷入内核态，由内核执行特权操作。

```text
系统调用特点：
1. 特权切换 —— 用户态 → 内核态 → 用户态，有开销
2. 分类 —— 进程控制 / 文件操作 / 内存管理 / 网络通信
3. 常见 —— fork、exec、open/read/write、mmap、socket
4. 定位 —— strace 能看到程序卡在哪个 syscall
```

```bash
# 观察一个程序的系统调用
strace -c python3 -c "print('hello')"
# 会看到 write 等 syscall 的调用次数与耗时统计
```

```text
为什么关心：syscall 是昂贵操作，减少调用次数（批量读写、缓冲）能显著提速。
```

## cgroups

cgroups（控制组）是 Linux 内核的「资源配额」机制，限制一组进程的 CPU、内存、磁盘 IO、网络等资源，是 Docker/K8s 资源限制的底层。

```text
cgroups 能限制：
1. CPU —— 使用比例 / 核心数
2. 内存 —— 上限，超了触发 OOM Kill
3. 磁盘 IO —— 读写带宽和 IOPS
4. 公平调度 —— 多任务按权重分享资源
```

```yaml
# K8s 资源限制最终落到 cgroups
resources:
  requests: {memory: "2Gi", cpu: "1"}
  limits:   {memory: "4Gi", cpu: "2"}   # 超 4Gi 被 OOM Kill
```

```bash
# 观察 cgroups
cat /sys/fs/cgroup/cgroup.controllers   # 支持的控制器
systemd-cgls                             # 查看 cgroup 树
```

## namespace

namespace 是 Linux 内核的「视图隔离」机制，让不同进程看到不同的系统资源视图。它与 cgroups 一起构成容器技术的两大基石。

```text
namespace 隔离类型：
1. PID —— 进程号隔离；NET —— 网络隔离
2. MNT —— 挂载点隔离；UTS —— 主机名隔离
3. IPC —— 进程间通信隔离；USER —— 用户/权限隔离

cgroups 限制「用多少」，namespace 决定「看得到什么」
Docker 容器 = namespace（隔离视图） + cgroups（限制资源） + 镜像文件系统
```

```bash
# 观察 namespace
ls -l /proc/self/ns/                    # 当前进程所属各 namespace
# net -> 'net:[4026531840]'，两个进程 ns 相同说明同 namespace

unshare --pid --fork --mount-proc bash  # 新 PID namespace，PID 从 1 开始
echo $$                                 # 自己是 PID 1
```

## 应用场景实战

### 场景一：定位容器内存超限被 OOM Kill

```python
# 内存失控进程：每次申请 10MB
import time
def leak():
    data = []
    while True:
        data.append(bytearray(10 * 1024 * 1024))
        print(f"已申请 {len(data) * 10} MB"); time.sleep(0.5)
```

```bash
# 用 docker 限制内存，观察 OOM
docker run -d --rm -m 100m --name leak python:3.11-slim python -c "
import time
d=[]
while True:
    d.append(bytearray(10*1024*1024)); time.sleep(0.3)"
sleep 5
docker inspect leak --format '{{.State.OOMKilled}}'   # 输出 true
```

### 场景二：CPU 密集任务多线程 vs 多进程

```python
import multiprocessing as mp, threading, time, math
def heavy(n):
    return sum(1 for i in range(2, n)
               if all(i % j for j in range(2, int(math.sqrt(i)) + 1)))
def run_threads():
    ts = [threading.Thread(target=heavy, args=(8000,)) for _ in range(4)]
    [t.start() for t in ts]; [t.join() for t in ts]
def run_processes():
    with mp.Pool(4) as p: p.map(heavy, [8000] * 4)
t0 = time.time(); run_threads();  t1 = time.time() - t0
t0 = time.time(); run_processes(); t2 = time.time() - t0
print(f"多线程（受 GIL 限制）{t1:.2f}s vs 多进程（真并行）{t2:.2f}s")
```

## 最佳实践与踩坑记录

### 最佳实践

1. CPU 密集任务用多进程，IO 密集任务用多线程或异步
2. 多线程共享数据必须加锁，或改用线程安全的数据结构
3. 训练任务容器必须设 resources.limits，防止 OOM 影响整机
4. 频繁读写的热数据放内存（tmpfs/mmap），冷数据落磁盘
5. 大文件读写用缓冲区批量操作，减少系统调用次数
6. 线上服务关注 RSS 和 swap，避免内存抖动

### 踩坑记录

```text
坑 1：CPU 密集任务用多线程没加速
结论：多线程跑计算，CPU 上不去，耗时和单线程差不多。
原因：CPython 的 GIL 让同一时刻只有一个线程执行字节码。
解法：CPU 密集改用 multiprocessing 多进程。

坑 2：容器没设内存 limit 导致整机 OOM
结论：一个训练任务内存失控，把整台机器拖死。
原因：没有 cgroups 限制，进程可无限吃内存。
解法：容器/Job 必须设 memory limit，并配 OOM 告警。

坑 3：多线程改共享变量结果对不上
结论：8 线程各加 10 万次，最终 counter 小于 80 万。
原因：counter += 1 是「读-改-写」三步，线程交错丢更新。
解法：加锁，或用原子操作、线程安全容器。

坑 4：忘了虚拟内存是惰性分配
结论：malloc 成功不代表内存到手，后续访问才分配物理页。
原因：OS 只在真正访问页时才分配物理内存。
解法：监控 RSS 而非 VMS，压测用真实数据访问。

坑 5：忽略系统调用开销，逐字节读写文件
结论：处理大文件慢得离谱，CPU 耗在 syscall 上。
原因：每次 read/write 都发生用户态-内核态切换。
解法：大缓冲区批量读写，或用 mmap 减少拷贝。
```
