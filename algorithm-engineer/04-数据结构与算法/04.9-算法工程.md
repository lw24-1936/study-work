## 概述

算法工程把「纸面上的算法」变成「生产可用的代码」：光知道 O(n log n) 不够，还要会实测性能（Benchmark）、定位瓶颈（Profiling）、利用多核（并行）、保证正确性（测试）、处理极端输入（边界与数据规模）。它是算法工程师区别于「只会刷题」的关键能力。

```text
算法工程的核心要点：
1. 实测优先 —— 复杂度是理论，benchmark 才是真相，常数项和缓存影响巨大
2. 先测量再优化 —— 用 Profiling 找到真正的瓶颈，别凭感觉瞎优化
3. 正确性兜底 —— 用单元测试 + 边界用例保证算法不出错
4. 规模意识 —— 先估算数据规模，再决定算法与数据结构选型
```

```python
# 工程化习惯：写算法时同步写测试 + 测性能
import time

def timeit(func, *args, repeat=1000):
    start = time.perf_counter()
    for _ in range(repeat):
        func(*args)
    return (time.perf_counter() - start) / repeat * 1e6   # 微秒

def fib(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

print(f'fib(100) 平均耗时: {timeit(fib, 100):.2f} 微秒')
```

## Benchmark

Benchmark（基准测试）是用「可重复、可对比」的方式测量代码的真实运行时间和资源消耗。它把「这个算法快不快」从主观感觉变成客观数字，是算法选型、优化前后对比、性能回归检测的基础工具。

```text
Benchmark 要点：
1. 多次重复取平均/中位数，消除噪声和预热影响
2. 固定输入规模，对比不同实现/算法的耗时与内存
3. 用 perf_counter（单调时钟）而非 time（受系统时间调整影响）

Python 工具：
- timeit 模块 —— 标准微基准
- pyperf —— 更严谨的基准测试库
```

```python
import timeit
import random

# 对比「列表去重」的两种实现
def dedup_set(data):
    return list(set(data))

def dedup_loop(data):
    seen = set()
    result = []
    for x in data:
        if x not in seen:
            seen.add(x)
            result.append(x)
    return result

data = [random.randint(0, 1000) for _ in range(10000)]

t_set = timeit.timeit(lambda: dedup_set(data), number=1000)
t_loop = timeit.timeit(lambda: dedup_loop(data), number=1000)
print(f'set 去重: {t_set:.4f}s, 循环去重: {t_loop:.4f}s')
print(f'内置 set 快 {t_loop / t_set:.1f} 倍')


# 对比 O(n²) vs O(n) 两数之和
def two_sum_brute(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return i, j

def two_sum_hash(nums, target):
    seen = {}
    for i, x in enumerate(nums):
        if target - x in seen:
            return seen[target - x], i
        seen[x] = i

nums = list(range(2000))
t1 = timeit.timeit(lambda: two_sum_brute(nums, 3997), number=10)
t2 = timeit.timeit(lambda: two_sum_hash(nums, 3997), number=1000)
print(f'暴力 O(n²): {t1:.4f}s(×10), 哈希 O(n): {t2:.4f}s(×1000)')
```

## Profiling

Profiling（性能剖析）定位代码里「时间/内存都花在哪了」：哪个函数最耗时、调用多少次、哪一行是热点。它把优化从「凭直觉」变成「有数据支撑」，避免在只占 1% 运行时间的代码上浪费精力。

```text
Profiling 工具：
- cProfile —— Python 标准剖析器，统计每个函数的调用次数和耗时
- line_profiler —— 逐行剖析，精确定位热点行
- memory_profiler —— 内存剖析，定位内存泄漏

流程：
1. cProfile 跑一遍，看「累计时间」排序，找热点函数
2. 对热点函数用 line_profiler 逐行分析
3. 只优化真正的瓶颈（80/20 法则）
```

```python
import cProfile
import pstats

def slow_part(n):
    total = 0
    for i in range(n):
        for j in range(n):
            total += i * j
    return total

def fast_part(n):
    return sum(i * (n * (n - 1) // 2) for i in range(n))

def mixed_workload():
    a = slow_part(200)      # 热点
    b = fast_part(200)      # 非热点
    return a + b


profiler = cProfile.Profile()
profiler.enable()
mixed_workload()
profiler.disable()

stats = pstats.Stats(profiler)
stats.sort_stats('cumulative')
stats.print_stats(5)   # 打印耗时前 5 的函数
```

## 并行

并行（Parallelism）利用多核 CPU 同时执行任务，突破单核瓶颈。CPU 密集型用 multiprocessing（绕开 GIL），IO 密集型用多线程或 asyncio，数据并行（如 map 处理大数组）用进程池最简单直接。

```text
并行策略：
1. 多线程 threading —— IO 密集型（网络、文件），受 GIL 限制 CPU 任务提速有限
2. 多进程 multiprocessing —— CPU 密集型，真正利用多核，绕开 GIL
3. 进程池 Pool.map —— 数据并行最简单的方式
4. asyncio —— 单线程协程，高并发 IO

加速上限（Amdahl 定律）：
- 可并行部分占比 p，核数 n → 加速比 = 1 / ((1-p) + p/n)
- 串行部分决定了加速的天花板
```

```python
from multiprocessing import Pool
import time

def cpu_bound(x):
    """模拟 CPU 密集任务：计算一个较大的斐波那契"""
    a, b = 0, 1
    for _ in range(x):
        a, b = b, a + b
    return a

if __name__ == '__main__':
    tasks = [200000] * 8

    # 串行
    start = time.perf_counter()
    serial = [cpu_bound(t) for t in tasks]
    serial_time = time.perf_counter() - start

    # 4 进程并行
    start = time.perf_counter()
    with Pool(4) as pool:
        parallel = pool.map(cpu_bound, tasks)
    parallel_time = time.perf_counter() - start

    print(f'串行: {serial_time:.2f}s, 4进程并行: {parallel_time:.2f}s')
    print(f'加速比: {serial_time / parallel_time:.2f}x')
```

## 测试

测试是算法正确性的兜底：用「边界用例 + 随机对照 + 已知答案」系统验证算法实现。算法代码尤其要测边界（空输入、单元素、重复元素、极值），并用「暴力解法」做对照测试（property-based testing 的思路）。

```text
测试层次：
1. 单元测试 —— 用 pytest/unittest 测单个函数
2. 边界测试 —— 空、单个、重复、极值、负数、越界
3. 对照测试 —— 用暴力算法验证高效算法的正确性
4. 随机测试 —— 随机生成输入，断言结果与朴素解一致

Python 工具：pytest（最流行）、unittest（标准库）、hypothesis（属性测试）
```

```python
import random

# 对照测试：用暴力解验证高效解（快速排序 vs 内置排序）
def quick_sort(arr):
    if len(arr) <= 1:
        return arr
    pivot = arr[len(arr) // 2]
    return (quick_sort([x for x in arr if x < pivot]) +
            [x for x in arr if x == pivot] +
            quick_sort([x for x in arr if x > pivot]))

def test_quick_sort_random():
    """随机 100 组输入，断言 quick_sort 与 sorted 结果一致"""
    for _ in range(100):
        arr = [random.randint(-100, 100)
               for _ in range(random.randint(0, 50))]
        assert quick_sort(arr) == sorted(arr), f'失败: {arr}'


def test_edge_cases():
    """边界用例"""
    assert quick_sort([]) == []          # 空
    assert quick_sort([5]) == [5]        # 单元素
    assert quick_sort([1, 1, 1]) == [1, 1, 1]   # 全重复
    assert quick_sort([3, -1, 0, 3, -1]) == sorted([3, -1, 0, 3, -1])


test_quick_sort_random()
test_edge_cases()
print('全部测试通过 ✓')
```

## 边界与数据规模

边界与数据规模意识是「工程化算法」的最后一块拼图：写算法前先问「输入有多大？边界情况有哪些？」。数据规模决定算法选型（n=10⁶ 只能用 O(n) 或 O(n log n)），边界情况决定代码健壮性（空输入、溢出、负数、重复、极值）。

```text
数据规模 → 算法复杂度速查（假设 1 秒约 10⁸ 次操作）：
- n ≤ 10：O(n!)、O(2ⁿ) 可接受（全排列、子集枚举）
- n ≤ 20：O(2ⁿ) 可接受
- n ≤ 10³：O(n²) 可接受
- n ≤ 10⁵：O(n log n) 可接受
- n ≤ 10⁶：O(n) 或 O(n log n) 可接受
- n ≤ 10⁸：只有 O(log n) 或 O(1)

必查边界：
1. 空输入 / 单元素
2. 全重复 / 全相同
3. 负数 / 零 / 极值（INT_MAX、INT_MIN）
4. 溢出（大数相加、乘法）
5. 输入已有序 / 逆序（对排序算法最坏）
```

```python
def safe_average(nums):
    """处理空输入和溢出边界"""
    if not nums:
        return 0.0          # 边界：空列表
    total = 0
    for x in nums:
        total += x
    return total / len(nums)


def binary_search_safe(arr, target):
    """处理空数组、防 mid 溢出、处理重复元素边界"""
    if not arr:
        return -1           # 边界：空数组
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = lo + (hi - lo) // 2   # 防 (lo+hi) 溢出
        if arr[mid] == target:
            # 找第一个等于 target 的位置（处理重复边界）
            while mid > 0 and arr[mid - 1] == target:
                mid -= 1
            return mid
        elif arr[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1


print(safe_average([]))                      # 0.0
print(binary_search_safe([], 5))             # -1
print(binary_search_safe([1, 2, 2, 2, 3], 2))   # 1（第一个 2）
```

## 应用场景实战

### 场景一：对比三种「判断素数」实现并选出最优

```python
import time, math

def is_prime_naive(n):
    if n < 2:
        return False
    for i in range(2, n):
        if n % i == 0:
            return False
    return True

def is_prime_sqrt(n):
    if n < 2:
        return False
    for i in range(2, int(math.sqrt(n)) + 1):
        if n % i == 0:
            return False
    return True

n = 999983   # 一个大素数

for name, func in [('朴素 O(n)', is_prime_naive),
                   ('开方 O(√n)', is_prime_sqrt)]:
    start = time.perf_counter()
    result = func(n)
    elapsed = time.perf_counter() - start
    print(f'{name}: {elapsed:.6f}s, 结果={result}')
# 开方优化从 O(n) 降到 O(√n)，对 100 万量级数字提速上千倍
```

### 场景二：用 multiprocessing 并行处理大数据批量任务

```python
from multiprocessing import Pool
import time

def process_chunk(chunk):
    """对一块数据做 CPU 密集处理"""
    return sum(x * x for x in chunk)

if __name__ == '__main__':
    data = list(range(2_000_000))

    # 串行
    start = time.perf_counter()
    serial = process_chunk(data)
    t_serial = time.perf_counter() - start

    # 4 进程并行（分块）
    chunk_size = len(data) // 4
    chunks = [data[i:i + chunk_size] for i in range(0, len(data), chunk_size)]
    start = time.perf_counter()
    with Pool(4) as pool:
        partial = pool.map(process_chunk, chunks)
    t_parallel = time.perf_counter() - start

    print(f'串行 {t_serial:.2f}s → 并行 {t_parallel:.2f}s, 加速 {t_serial / t_parallel:.2f}x')
    assert sum(partial) == serial   # 结果一致性校验
```

## 最佳实践与踩坑记录

### 最佳实践

1. 选型前先 benchmark，别只看理论复杂度，常数项和缓存局部性影响巨大
2. 优化前先 profiling，用数据定位热点函数，别在非瓶颈代码上浪费时间
3. CPU 密集用 multiprocessing 绕开 GIL，IO 密集用 asyncio/多线程
4. 算法代码必须配边界用例（空、单、重复、极值）+ 随机对照测试
5. 写算法前先估数据规模，n ≥ 10⁶ 就只能接受 O(n) 或 O(n log n)
6. 用 time.perf_counter() 计时，别用 time.time()（会被系统时钟调整干扰）

### 踩坑记录

```text
坑 1：多线程跑 CPU 密集任务反而更慢
结论：开了 8 线程，CPU 密集任务速度没提升甚至下降。
原因：GIL 全局锁，CPU 密集的 Python 代码无法真正并行，还多了线程切换开销。
解法：CPU 密集用 multiprocessing 多进程；IO 密集才用 threading/asyncio。

坑 2：只测一次就下结论
结论：单次 benchmark 结果波动大，误判 A 算法比 B 快。
原因：首次运行有预热、GC、缓存冷启动等噪声。
解法：多次重复取中位数，或用 timeit/pyperf 做严谨测量。

坑 3：忽略边界用例导致线上崩溃
结论：空列表、单元素、重复元素、INT 极值等边界没测，上线就报错。
原因：开发时只用正常数据测试，边界情况被遗漏。
解法：每次写算法都补空/单/重复/极值用例，配合随机对照测试。

坑 4：数据规模估算错误导致算法选型失败
结论：n=10⁶ 的数据上了 O(n²) 算法，跑几小时出不来。
原因：没先估算数据规模，凭经验选了低效算法。
解法：先问数据量，按「1 秒 10⁸ 次」速查表选合适的复杂度。

坑 5：并行任务忘了进程间通信开销
结论：小任务用多进程，进程创建 + 序列化开销比计算本身还大。
原因：multiprocessing 的进程启动和数据传输（pickle）有固定开销。
解法：任务粒度要足够大才并行；小任务用串行或 chunk 批量提交。
```
