## 概述

系统设计是算法工程师面试的高阶考察点：给定一个业务需求（如「设计一个推荐系统」），考察候选人能否从需求拆解、架构设计、技术选型到容量评估给出完整方案，而不是只会调模型。

```text
系统设计面试的考察维度：
1. 需求澄清 —— 主动问清规模、延迟、数据量
2. 架构分层 —— 召回/排序/服务/存储的清晰分层
3. 技术选型 —— 知道每层该用什么，为什么
4. 容量估算 —— QPS、存储、算力的大致计算
5. 权衡取舍 —— 一致性与可用性、精度与延迟
```

```text
答题框架（4 步法）：
1. 澄清需求 —— 用户量、QPS、延迟要求、数据规模
2. 顶层设计 —— 画架构图，讲清数据流
3. 分层细化 —— 逐层讲技术选型和关键设计
4. 容量与演进 —— 估算容量，讨论扩展和瓶颈
```

## 推荐系统

推荐系统的标准架构是「召回 → 粗排 → 精排 → 重排」的多阶段漏斗。

```text
推荐系统分层：
1. 召回 —— 从百万级候选中召回几百个（多路召回：CF/向量/热门）
2. 粗排 —— 简单模型快速过滤到几十个
3. 精排 —— 复杂模型精算分数（CTR/CVR 预估）
4. 重排 —— 多样性、业务规则、广告插入
```

```text
面试高频问题：
Q: 为什么需要多阶段，不能直接精排所有候选？
A: 精排模型复杂（如 DIN/DeepFM），对百万候选逐个推理延迟和
   算力不可接受。多路召回先缩小候选集到几百个，再精排，是
   「精度 vs 延迟」的权衡。
```

```python
# 召回-精排的伪代码结构
def recommend(user_id):
    candidates = multi_recall(user_id)     # 多路召回，几千 → 几百
    candidates = coarse_rank(candidates)   # 粗排，几百 → 几十
    candidates = fine_rank(candidates)     # 精排，几十 → 排序
    return rerank(candidates)              # 重排，多样性/规则
```

## 搜索系统

搜索系统 = 离线索引构建 + 在线查询处理（Query 理解 → 召回 → 排序 → 展示）。

```text
搜索系统链路：
1. Query 理解 —— 分词、纠错、改写、意图识别
2. 召回 —— 倒排索引(BM25) + 向量召回(ANN) 多路
3. 排序 —— Learning to Rank（相关性 + 业务特征）
4. 展示 —— 摘要、高亮、兜底
```

```text
面试高频问题：
Q: 倒排索引怎么构建和更新？
A: 离线全量构建 + 增量更新。文档分词后建立 term→posting list
   的映射，posting list 按文档 ID 排序，支持跳表加速求交。
   实时更新用双缓冲或段合并（segment merge）。
```

## 实时风控

实时风控要求在毫秒级对请求做风险判定，是「低延迟 + 高可用」的典型场景。

```text
实时风控的关键设计：
1. 实时特征 —— 用户/设备/行为特征毫秒级查询
2. 规则引擎 —— 黑白名单、阈值规则先行
3. 模型 —— 在线模型打分（LR/GBDT 或神经网络）
4. 决策 —— 通过/拦截/挑战（验证码）
5. 兜底 —— 模型超时降级为规则
```

```text
面试高频问题：
Q: 风控要求 <50ms 延迟，怎么设计？
A: 规则 + 轻量模型。特征全部预计算存 KV（Redis），规则引擎
   先过滤，模型用 LR/GBDT 这种轻量模型，超时降级为纯规则。
   模型和规则都走本地缓存 + 异步更新。
```

## CV 服务

CV 服务（如目标检测、OCR）是「重计算 + 批处理」场景，核心是 GPU 调度和吞吐优化。

```text
CV 服务的要点：
1. 模型 —— YOLO 等检测模型，TensorRT 加速
2. 推理 —— GPU 批处理，动态 batch 提升吞吐
3. 预处理 —— 图像解码/缩放放 CPU 端，别占 GPU
4. 队列 —— 请求排队，攒批后统一推理
5. 兜底 —— GPU 过载时降级/限流
```

```text
面试高频问题：
Q: 单张图片推理 GPU 利用率低，怎么优化？
A: 批处理（batching）。单张推理 GPU 喂不饱，把多个请求攒成
   batch 一起推理，吞吐能提升数倍。用动态 batch 在延迟和吞吐
   间平衡，配合 TensorRT 量化进一步加速。
```

## RAG 平台

RAG 平台 = 离线知识库构建 + 在线检索增强生成。

```text
RAG 平台架构：
1. 离线 —— 文档解析 → 分块 → 向量化 → 入库（向量库 + 倒排）
2. 在线 —— Query 理解 → 混合召回(向量+BM25) → 重排 → LLM 生成
3. 工程 —— 引用溯源、缓存、评估
```

```text
面试高频问题：
Q: 纯向量召回有什么问题，为什么需要混合检索？
A: 向量召回擅长语义相似，但对精确匹配（编号、专有名词）效果
   差。BM25 擅长关键词精确匹配。两者互补，用 RRF 融合再重排，
   兼顾语义和字面。
```

## Model Serving

模型服务的设计核心是「低延迟 + 高吞吐 + 版本管理」。

```text
Model Serving 设计：
1. 服务化 —— FastAPI/gRPC 封装推理接口
2. 推理引擎 —— ONNX Runtime/TensorRT 加速
3. 版本管理 —— Registry + 灰度（Canary/Blue-Green）
4. 弹性伸缩 —— 按 QPS/GPU 利用率自动扩缩容
5. 批处理 —— 在线小 batch，离线大 batch
```

## Feature Store

Feature Store 解决「特征口径不统一、离在线不一致、特征重复开发」三大问题。

```text
Feature Store 的核心：
1. 统一注册 —— 特征定义一处登记，多处复用
2. 离线特征 —— 批量计算，供训练
3. 在线特征 —— 低延迟查询，供服务
4. 一致性 —— 离在线同口径，避免训练服务不一致
5. Point-in-time —— 避免特征穿越
```

## ML Platform

ML Platform 是前几项的综合：覆盖数据、特征、训练、评估、部署、监控的完整机器学习基础设施。

```text
ML Platform 的完整能力：
1. 数据接入 —— 批流一体
2. 特征平台 —— Feature Store
3. 训练平台 —— K8s + GPU 调度 + 实验追踪
4. 评估 + Registry —— 模型版本化
5. Serving + 监控 —— 上线 + 漂移告警
6. A/B + 自动化 —— 灰度验证 + CI/CD
```

## 应用场景实战

### 场景一：设计一个短视频推荐系统

```text
澄清需求：
- 规模：DAU 1 亿，人均刷 100 条，QPS ≈ 10 万
- 延迟：<100ms
- 数据：视频库千万级，用户画像亿级

顶层设计：
召回(多路: 协同过滤/向量/热门/关注) → 粗排(轻量模型)
→ 精排(多目标: 点击/时长/完播) → 重排(多样性/去重)

关键点：
1. 向量召回用 FAISS/HNSW，视频 embedding 离线算好
2. 精排多目标融合，MMOE/ESMM 建模点击+时长
3. 特征全部在线化，<100ms 内完成特征拼接 + 推理
4. 容量：召回索引内存化，精排 GPU 批处理
```

### 场景二：设计一个 RAG 知识库问答系统

```text
澄清需求：
- 规模：10 万文档，QPS 100
- 延迟：<2s（含 LLM 生成）
- 要求：回答带引用，可追溯

顶层设计：
离线(解析→分块→向量化→入库) → 在线(Query→混合召回→重排→LLM→引用)

关键点：
1. 分块 512 token 带重叠，保留标题层级
2. 混合检索：向量(Top-20) + BM25(Top-20) → RRF 融合
3. 重排用 Cross-Encoder 精排到 Top-5
4. LLM 生成带引用编号，缓存高频问答
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先澄清需求再设计，别上来就画架构图
2. 分层要清晰，每层说清「做什么 + 用什么 + 为什么」
3. 主动做容量估算（QPS/存储/算力），体现工程素养
4. 明确讲权衡取舍，没有完美的方案，只有合适的取舍
5. 备选方案要能对比，别只报一个方案
6. 兜底和降级策略是加分项，体现线上稳定性意识

### 踩坑记录

```text
坑 1：不澄清需求直接设计
结论：方案和面试官预期错位，越答越偏。
原因：规模、延迟、数据量不同，方案完全不同。
解法：开场先问清 QPS、延迟、数据规模、一致性要求。

坑 2：只说技术选型不讲为什么
结论：听起来像背八股，没有设计思考。
原因：只列技术名词，没解释取舍逻辑。
解法：每个选型都说清「对比了什么、为什么选这个」。

坑 3：忽略容量估算
结论：方案在真实规模下不可行，暴露工程短板。
原因：没算 QPS/存储/算力，凭感觉设计。
解法：主动估算，如「QPS 10 万、单次 100ms → 需 1 万核算力」。

坑 4：设计不考虑兜底降级
结论：方案看起来很美好，但没考虑失败场景。
原因：只设计正常路径，忽略超时、过载、故障。
解法：每个关键环节讲清降级策略（模型超时→规则/缓存）。

坑 5：只答一个方案不对比备选
结论：显得思路单一，没有权衡能力。
原因：给出一个方案就停，不讨论替代方案。
解法：至少给 2 个方案，对比优劣后说明选型理由。
```
