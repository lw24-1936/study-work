## 概述

Agent（智能体）把 LLM 从「只会聊天」升级成「能干活」：它用 LLM 做大脑，通过「思考 → 调用工具 → 观察结果 → 再思考」的循环，自主完成需要多步操作的任务。相比纯生成，Agent 能查资料、写代码、操作软件、调用 API，把语言能力转化为真实世界的行动。

```text
Agent 的核心组成：
1. 大脑（LLM）—— 负责推理、决策、生成
2. 工具（Tools）—— 可调用的外部能力（搜索/计算器/代码/API）
3. 规划（Planning）—— 把复杂任务拆解成步骤
4. 记忆（Memory）—— 短期上下文 + 长期知识存储
5. 循环（Loop）—— 观察 → 思考 → 行动的闭环执行

关键挑战：幻觉导致错误行动、长程任务步数失控、工具调用格式不稳定
```

```python
# Agent 最小循环示意（伪代码）
class SimpleAgent:
    def __init__(self, llm, tools):
        self.llm = llm
        self.tools = {t.name: t for t in tools}

    def run(self, task):
        messages = [{"role": "user", "content": task}]
        for _ in range(10):                    # 最多 10 步
            reply = self.llm(messages)
            if reply.get("action") == "finish":
                return reply["answer"]
            tool = self.tools[reply["action"]]
            result = tool.run(reply["args"])
            messages.append({"role": "tool", "content": result})
        return "达到最大步数限制"

print('Agent 循环结构已定义：思考 → 调工具 → 观察 → 再思考')
```

## ReAct

ReAct（Reasoning + Acting，推理与行动）是最经典的 Agent 范式：把「思考（Thought）」和「行动（Action）」交替写进 prompt，模型先推理下一步该做什么，再调用工具，观察结果后继续推理，直到给出最终答案。它让推理过程可解释、可追踪。

```text
ReAct 循环：
Thought → Action → Observation → Thought → ... → Final Answer

三要素：
1. Thought —— 当前该做什么、为什么
2. Action —— 调用哪个工具、传什么参数
3. Observation —— 工具返回的结果，作为下一轮推理的依据

优势：推理可解释、错误可回溯；局限：每步都依赖 LLM 推理，长任务慢
```

```python
REACT_PROMPT = """你可以使用以下工具：
{tools}

请按以下格式回答：
Thought: 你的思考
Action: 工具名[参数]
Observation: 工具返回结果
...（重复）
Final Answer: 最终答案

问题：{question}
"""

def react_loop(llm, tool_executor, question, max_steps=8):
    context = REACT_PROMPT.format(tools="search[query]", question=question)
    for step in range(max_steps):
        output = llm(context)
        if "Final Answer" in output:
            return output.split("Final Answer:")[-1].strip()
        # 解析 Action 并执行
        action = output.split("Action:")[-1].split("\n")[0].strip()
        result = tool_executor(action)
        context += f"\nObservation: {result}\n"
    return "达到步数上限"

print('ReAct 循环模板已定义')
```

## Plan-and-Execute

Plan-and-Execute（先规划后执行）把任务分成两个阶段：先用 LLM 生成一个完整的步骤计划，再逐条执行，执行阶段通常不需要模型反复推理。它比 ReAct 更适合长程任务，因为「全局先想清楚」比「走一步看一步」更高效、更不容易跑偏。

```text
Plan-and-Execute 流程：
1. Planner —— LLM 把任务拆成 N 个明确步骤
2. Executor —— 按顺序执行每个步骤（可复用工具，无需每步推理）
3. Replan（可选）—— 某步失败时重新规划剩余步骤

优势：长任务开销小、计划可控可审查；局限：初始计划若错了会一路错
```

```python
def plan_and_execute(llm, executor, task):
    plan_prompt = f"请把以下任务拆解成可执行的步骤列表，每行一步：\n{task}"
    plan_text = llm(plan_prompt)
    steps = [s.strip("- ").strip() for s in plan_text.split("\n") if s.strip()]
    results = []
    for i, step in enumerate(steps, 1):
        result = executor(step)
        results.append((i, step, result))
    return steps, results

def fake_llm(p):
    return "- 搜索相关资料\n- 整理要点\n- 撰写报告"

def fake_executor(step):
    return f"已完成: {step}"

steps, results = plan_and_execute(fake_llm, fake_executor, "调研 Agent 技术")
for i, s, r in results:
    print(f'步骤{i}: {s} → {r}')
```

## Reflection

Reflection（反思）让 Agent 在执行一轮后，回头审视自己的输出：哪里错了、为什么错、怎么改进，然后带着反思重新执行。它常用于「生成 → 自我批评 → 修正」的迭代，能显著提升代码生成、写作等任务的质量。

```text
Reflection 流程：
1. 生成 —— 模型产出初版结果
2. 反思 —— 用批评提示词让模型（或另一个模型）找出问题
3. 修正 —— 根据反思意见重新生成
4. 循环 —— 反复直到满意或达到轮数上限

关键：批评者常和生成者用不同 prompt/模型，避免「自己夸自己」
```

```python
def reflect_and_refine(llm, critic, task, max_rounds=3):
    draft = llm(f"请完成：{task}")
    for r in range(max_rounds):
        feedback = critic(f"请指出以下输出的问题：\n{draft}")
        if "无问题" in feedback:
            break
        draft = llm(f"请根据反馈改进：\n反馈：{feedback}\n原输出：{draft}")
    return draft

def fake_critic(p):
    return "无问题"   # 模拟批评者认为已经很好

print('Reflection 反思-改进循环已定义')
```

## Tool Calling

Tool Calling（工具调用/函数调用）是 Agent 落地的基础能力：模型不直接生成答案，而是生成「结构化工具调用指令」（工具名 + JSON 参数），由外部程序执行后把结果回传。OpenAI 的 function calling、Anthropic 的 tool use 都是这一机制的标准化实现。

```text
工具调用的关键：
1. 工具描述 —— 每个工具要有清晰的名字、说明、参数 schema（JSON Schema）
2. 结构化输出 —— 模型输出 JSON 格式的调用参数，而非自由文本
3. 执行与回传 —— 程序执行工具，结果作为 tool 消息回填对话
4. 校验 —— 参数非法时重试或让模型修正

常见工具：搜索、计算器、代码解释器、数据库查询、浏览器
```

```python
import json

TOOLS_SCHEMA = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的天气",
            "parameters": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
            },
        },
    }
]

def get_weather(city):
    # 真实场景这里调 API
    return {"city": city, "temp": 26, "condition": "晴"}

def execute_tool_call(call):
    name = call["name"]
    args = json.loads(call.get("arguments", "{}"))
    if name == "get_weather":
        return get_weather(args["city"])
    raise ValueError(f"未知工具 {name}")

result = execute_tool_call({"name": "get_weather", "arguments": '{"city": "北京"}'})
print(f'工具执行结果: {result}')
```

## Planning

Planning（规划）是 Agent 把复杂任务分解为可执行子任务的能力。它是「长程任务」和「多步协作」的前提——没有规划，模型面对「做一整个项目」只会输出一段空话；有了规划，才能一步步推进。

```text
规划方法谱系：
1. 任务分解 —— 大任务拆小步骤（Plan-and-Execute、Tree of Thoughts）
2. 计划生成 —— 让 LLM 显式输出步骤清单
3. 动态重规划 —— 执行中根据反馈调整剩余计划
4. 层次规划 —— 高层目标 → 中层子任务 → 底层动作

评价标准：步骤是否可执行、是否覆盖目标、是否能在预算内完成
```

```python
def decompose_task(llm, task, granularity=3):
    prompt = (
        f"请把任务分解为 {granularity} 个可独立执行的子任务，"
        f"每个子任务要具体、可验证：\n{task}"
    )
    return [s.strip("- ").strip() for s in llm(prompt).split("\n") if s.strip()]

def fake_llm(p):
    return "- 收集数据\n- 清洗数据\n- 训练模型"

subtasks = decompose_task(fake_llm, "做一个房价预测模型")
print(f'拆解出的子任务: {subtasks}')
```

## Memory

Memory（记忆）让 Agent 跨对话、跨步骤保留信息：短期记忆（对话上下文、当前任务状态）和长期记忆（用户偏好、历史知识、已学到的经验）。没有记忆的 Agent 每次都是「失忆新人」，有了记忆才能个性化、避免重复犯错。

```text
记忆层级：
1. 短期/工作记忆 —— 当前对话上下文窗口，容量受 token 限制
2. 长期记忆 —— 外部存储（向量库/数据库/文件），跨会话持久化
3. 情景记忆 —— 过往交互事件，用于个性化
4. 语义记忆 —— 抽取出的通用知识/事实

实现：检索式记忆（向量检索 + 摘要），写回式记忆（把重要信息存库）
```

```python
class AgentMemory:
    def __init__(self):
        self.short_term = []          # 短期：当前对话
        self.long_term = {}           # 长期：键值存储

    def remember(self, key, value):
        self.long_term[key] = value

    def recall(self, key):
        return self.long_term.get(key, None)

    def add_message(self, msg):
        self.short_term.append(msg)
        if len(self.short_term) > 20:     # 超出窗口时压缩
            summary = f"（前 {len(self.short_term) - 5} 条已压缩）"
            self.short_term = [summary] + self.short_term[-5:]

mem = AgentMemory()
mem.remember("用户偏好", "喜欢简洁的答案")
mem.add_message("你好")
print(f'回忆用户偏好: {mem.recall("用户偏好")}')
```

## Routing

Routing（路由）把一个入口请求智能分发到最合适的下游处理器：可能是不同的 LLM、不同的工具、不同的 Agent 或不同的 prompt。它让一个系统能服务多类任务，把「专才」组合成「通才」，同时控制成本和延迟。

```text
路由策略：
1. LLM 分类 —— 用模型判断意图，再分发（最灵活）
2. 规则/关键词 —— 简单场景用规则匹配，快且可控
3. 嵌入相似度 —— 把请求与各处理器的描述做语义匹配
4. 分级路由 —— 简单问题走小模型，复杂问题升级大模型

典型应用：客服意图分流、模型成本分级、工具选择
```

```python
import numpy as np

def route_by_embedding(query_emb, route_descs_emb):
    # 用语义相似度选择最匹配的路由
    sims = query_emb @ route_descs_emb.T
    return int(np.argmax(sims))

# 3 个路由：技术支持 / 售前咨询 / 售后投诉
query_emb = np.array([[0.1, 0.9, 0.2]])
route_descs = np.array([
    [0.9, 0.1, 0.1],   # 技术支持
    [0.2, 0.2, 0.9],   # 售前咨询
    [0.1, 0.1, 0.9],   # 售后投诉
])
route_id = route_by_embedding(query_emb, route_descs)
print(f'请求被路由到处理器 {route_id}')
```

## Multi-Agent

Multi-Agent（多智能体）让多个 Agent 分工协作完成一个复杂任务：有的负责规划、有的负责写代码、有的负责审查、有的负责测试。它们通过消息传递协作，像一支小团队。相比单 Agent，多 Agent 能并行、能分工、能互相纠错，但也更复杂、成本更高。

```text
多智能体架构：
1. 主从式 —— 一个协调者 Agent 分配任务给多个执行者 Agent
2. 流水线式 —— 各 Agent 按阶段串行（需求 → 开发 → 测试 → 审查）
3. 辩论式 —— 多个 Agent 各自给出方案，互相辩论后汇总
4. 市场式 —— 任务竞价，Agent 认领自己擅长的任务

框架：AutoGen、CrewAI、LangGraph
```

```python
class MultiAgentSystem:
    def __init__(self):
        self.agents = {
            "planner": lambda t: f"计划: {t}",
            "coder": lambda t: f"代码: {t}",
            "reviewer": lambda t: f"审查: {t}",
        }

    def run_pipeline(self, task):
        plan = self.agents["planner"](task)
        code = self.agents["coder"](plan)
        review = self.agents["reviewer"](code)
        return {"plan": plan, "code": code, "review": review}

system = MultiAgentSystem()
result = system.run_pipeline("实现排序函数")
for k, v in result.items():
    print(f'{k}: {v}')
```

## Workflow

Workflow（工作流）把 Agent 的执行过程编排成有向图：节点是「步骤」（LLM 调用、工具调用、条件判断），边是「流转关系」。它比自由循环更可控、更可预测，适合生产环境的确定性流程，是 LangGraph 等框架的核心概念。

```text
Workflow 关键概念：
1. 节点（Node）—— 一个可执行单元（生成/工具/判断）
2. 边（Edge）—— 节点间的流转，可以是条件边
3. 状态（State）—— 在节点间传递的共享数据
4. 循环（Cycle）—— 允许回到之前的节点（如重试、反思）

与自由 Agent 对比：Workflow 显式定义路径，确定性更强、更易审计
```

```python
class Workflow:
    def __init__(self):
        self.nodes = {}
        self.edges = {}
        self.state = {}

    def add_node(self, name, fn):
        self.nodes[name] = fn

    def add_edge(self, src, dst):
        self.edges.setdefault(src, []).append(dst)

    def run(self, start):
        current = start
        while current in self.edges:
            self.nodes[current](self.state)
            current = self.edges[current][0]
        self.nodes[current](self.state)
        return self.state

wf = Workflow()
wf.add_node("生成", lambda s: s.update({"draft": "初稿"}))
wf.add_node("审查", lambda s: s.update({"review": "通过"}))
wf.add_edge("生成", "审查")
print(f'工作流执行结果: {wf.run("生成")}')
```

## Agent Evaluation

Agent Evaluation（Agent 评估）衡量 Agent 完成真实任务的成功率和质量。它比单纯评估「生成文本」难得多——Agent 的输出是一系列行动，要评估「最终是否达成目标」「过程是否高效」「工具是否用对」「是否在预算内」。

```text
评估维度：
1. 任务成功率 —— 最终结果是否满足需求（end-to-end）
2. 轨迹质量 —— 中间步骤是否合理、工具调用是否正确
3. 效率 —— 用了多少步/多少 token 完成
4. 鲁棒性 —— 对错误/异常输入的容错
5. 成本 —— 时间与 token 开销

方法：基准测试（WebArena、GAIA、SWE-bench）+ LLM-as-judge + 人工评审
```

```python
def evaluate_agent(runs):
    # 汇总多个任务的评估指标
    total = len(runs)
    success = sum(1 for r in runs if r["success"])
    avg_steps = sum(r["steps"] for r in runs) / total
    avg_cost = sum(r["tokens"] for r in runs) / total
    return {
        "成功率": success / total,
        "平均步数": avg_steps,
        "平均 token": avg_cost,
    }

runs = [
    {"success": True, "steps": 4, "tokens": 1200},
    {"success": True, "steps": 6, "tokens": 1800},
    {"success": False, "steps": 9, "tokens": 3000},
]
metrics = evaluate_agent(runs)
print(f'Agent 评估指标: {metrics}')
```

```python
def code_agent(llm, critic, requirement, max_rounds=3):
    code = llm(f"写代码：{requirement}")
    for r in range(max_rounds):
        feedback = critic(code)
        if feedback["pass"]:
            return code, r + 1
        code = llm(f"修复问题：{feedback['issue']}\n代码：{code}")
    return code, max_rounds

def fake_critic(code):

final_code, rounds = code_agent(fake_llm, fake_critic, "排序函数")
print(f'经 {rounds} 轮反思后代码:\n{final_code}')
```

## 最佳实践与踩坑记录

### 最佳实践

1. 工具描述写清楚（名字、用途、参数、示例），工具描述质量决定调用准确率
2. 复杂任务用 Plan-and-Execute 先规划，别让模型无脑逐步试错
3. 每步都设步数上限和超时，防止 Agent 陷入死循环烧 token
4. 关键操作（写文件、发消息、花钱）加人工确认，别让 Agent 无约束执行
5. 用结构化工具调用（function calling），别让模型自由文本里塞工具名
6. 长期记忆存向量库或数据库，别只依赖上下文窗口

### 踩坑记录

```text
坑 1：工具描述含糊导致调用错误
结论：模型把参数传错、或选错工具，任务反复失败。
原因：工具说明没写清参数类型、语义和边界。
解法：每个工具写清 JSON Schema + 使用示例，必要时 few-shot。

坑 2：Agent 陷入无限循环
结论：模型反复调用同一工具、观察同样的结果，烧光 token。
原因：没有步数上限，且 Observation 无法推动进展。
解法：设 max_steps + 超时，检测重复动作强制终止或换策略。

坑 3：无约束执行危险操作
结论：Agent 擅自删除文件、发送邮件、调用付费 API。
原因：把危险工具直接暴露给模型，无权限和确认机制。
解法：危险操作加 human-in-the-loop 确认，工具层做权限控制。

坑 4：让模型在自由文本里写工具调用
结论：工具名拼写错、参数格式乱，解析经常失败。
原因：没有用结构化 function calling，靠正则解析文本。
解法：用模型原生工具调用接口，拿到结构化 JSON 再执行。

坑 5：多 Agent 之间消息不收敛
结论：两个 Agent 互相「踢皮球」，任务迟迟不结束。
原因：缺少终止条件和协调者，对话无限延续。
解法：设全局协调者 + 轮次上限，明确各 Agent 职责边界。

坑 6：只评最终答案不评过程
结论：Agent 靠「撞大运」完成一次任务，但换输入就崩。
原因：评估只看端到端结果，忽略了轨迹和鲁棒性。
解法：同时评估轨迹质量、步数、成本，在多样本上测稳定性。
```
