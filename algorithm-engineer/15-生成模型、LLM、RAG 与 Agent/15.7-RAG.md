## 概述

RAG（Retrieval-Augmented Generation，检索增强生成）在 LLM 生成前先检索外部知识库，把命中的文档片段拼进 prompt 再让模型回答。它解决了 LLM 的两大痛点——知识过时（训练截止日期之后的事不知道）和幻觉（凭空编造），让模型能基于真实、可溯源的知识回答。

```text
RAG 的完整链路：
1. 离线索引 —— 文档加载 → 解析 → 清洗 → 分块 → 向量化 → 建索引
2. 在线检索 —— 用户问题 → 改写/扩展 → 检索（稀疏/稠密/混合）→ 重排
3. 生成 —— 压缩上下文 → 拼 prompt → LLM 生成 → 带引用输出
4. 评估 —— 检索质量 + 生成质量 + 端到端忠实度

核心价值：知识可更新、答案可溯源、幻觉可抑制
```

```python
from langchain_community.document_loaders import TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings

# RAG 最小闭环示例
loader = TextLoader("./docs/knowledge.txt")
docs = loader.load()
splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(docs)

vectorstore = Chroma.from_documents(chunks, OpenAIEmbeddings())
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})
hits = retriever.invoke("什么是向量检索？")
print(f'检索到 {len(hits)} 个相关片段')
```

## Document Loading

Document Loading（文档加载）负责把各种来源、各种格式的原始数据读进系统：PDF、Word、网页、数据库、Markdown、图片等。它是 RAG 的第一步，格式越杂，加载器越要健壮地处理编码、结构和异常。

```text
常见数据源与加载方式：
1. 文本类 —— TextLoader/Markdown 直接读
2. 网页 —— WebBaseLoader/Playwright 抓取并提取正文
3. PDF —— PyPDFLoader/PyMuPDF 提取文本与布局
4. Office —— Docx/PPT/XLSX 用对应解析器
5. 数据库 —— SQL/向量库直接查询导出

注意：加载阶段要保留元数据（来源、页码、标题），后面引用和溯源都用得上
```

```python
from langchain_community.document_loaders import (
    TextLoader, WebBaseLoader, PyPDFLoader, CSVLoader
)

# 多种格式加载
text_docs = TextLoader("./data/notes.txt").load()
web_docs = WebBaseLoader("https://example.com/article").load()
pdf_docs = PyPDFLoader("./data/paper.pdf").load()
csv_docs = CSVLoader("./data/table.csv").load()

for doc in pdf_docs[:2]:
    print(f'PDF 页 {doc.metadata.get("page")}: {doc.page_content[:50]}...')
print(f'共加载 {len(text_docs) + len(web_docs) + len(pdf_docs) + len(csv_docs)} 个文档')
```

## Parsing

Parsing（解析）把加载进来的原始内容转成结构化、可读的文本。对 PDF 和扫描件尤其关键——它们本质是「版式」而非「文本流」，需要还原标题层级、表格、段落顺序，否则分块和检索质量都会崩。

```text
解析的关键任务：
1. 提取文本 —— 从 PDF/图片里抽出文字（含 OCR）
2. 还原结构 —— 识别标题、段落、列表、表格、页眉页脚
3. 排序 —— 多栏、混排的阅读顺序要正确
4. 表格 —— 转成 Markdown 表格或结构化 JSON，别拆散单元格

工具：PyMuPDF、pdfplumber、unstructured、Marker、Docling
```

```python
import fitz   # PyMuPDF

def parse_pdf(path):
    doc = fitz.open(path)
    result = []
    for page_num, page in enumerate(doc):
        text = page.get_text("text")           # 提取纯文本
        blocks = page.get_text("blocks")       # 带坐标的块，可判断表格/栏
        result.append({
            "page": page_num + 1,
            "text": text,
            "n_blocks": len(blocks),
        })
    return result

# parsed = parse_pdf("./data/paper.pdf")
# print(parsed[0]["text"][:200])
print('解析器已定义：提取文本 + 块级结构信息')
```

## Cleaning

Cleaning（清洗）去除解析结果里的噪声：页眉页脚、页码、乱码、多余空白、广告、导航栏等。这些噪声若不清理，会被切进 chunk 污染向量库，检索时召回一堆无关内容。

```text
常见清洗动作：
1. 去页眉页脚 —— 每页重复的标题/页码/版权信息
2. 去乱码 —— 编码错误的字符、OCR 识别噪音
3. 规范化空白 —— 合并连续空格、去掉首尾空白
4. 去导航 —— 网页的菜单、侧栏、页脚链接
5. 去重 —— 相邻 chunk 重复内容、重复文档
```

```python
import re

def clean_text(text):
    # 去页眉页脚式重复行（如页码、版权）
    text = re.sub(r'^\s*第?\s*\d+\s*页\s*$', '', text, flags=re.M)
    # 合并连续空白
    text = re.sub(r'[ \t]+', ' ', text)
    # 去多余空行
    text = re.sub(r'\n{3,}', '\n\n', text)
    # 去常见乱码字符
    text = text.replace('\x00', '').replace('\ufffd', '')
    return text.strip()

dirty = "第 1 页\n\n\n这是正文内容……\x00含乱码\ufffd\n\n第 2 页"
print(clean_text(dirty))
```

## Chunking

Chunking（分块）把长文档切成一个个适合检索和塞进 prompt 的小片段。分块策略直接决定检索质量：块太大 → 噪声多、超上下文；块太小 → 语义破碎、丢失上下文。好的分块要在「语义完整」和「粒度合适」之间平衡。

```text
分块策略：
1. 固定大小 —— 按 token/字符数切，简单但不考虑语义
2. 递归切分 —— 按段落/句子/词优先级逐级下探（最常用）
3. 语义分块 —— 用 embedding 相似度找语义边界
4. 结构分块 —— 按标题/章节/表格切，保留文档结构

关键参数：
1. chunk_size —— 块大小（300-1000 token 常见）
2. chunk_overlap —— 相邻块重叠，防止语义被切断（10%-20%）
```

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

text = "第一段内容。" * 50 + "\n\n" + "第二段内容。" * 50

splitter = RecursiveCharacterTextSplitter(
    chunk_size=100,       # 每块 100 字符
    chunk_overlap=20,     # 相邻块重叠 20 字符
    separators=["\n\n", "\n", "。", " ", ""],
)
chunks = splitter.split_text(text)
print(f'切分后共 {len(chunks)} 块，第一块长度 {len(chunks[0])}')
print(f'首块内容: {chunks[0][:40]}...')
```

## Embedding

Embedding（向量化）把文本映射成高维稠密向量，让「语义相近的文本在向量空间里距离近」。它是稠密检索的地基：query 和 chunk 都变成向量后，用余弦相似度/内积就能算相关性。

```text
Embedding 关键点：
1. 模型 —— 开源 BGE/GTE/E5 系列，API 有 text-embedding-3 等
2. 维度 —— 常见 768/1024/1536，越高表达能力越强、存储越大
3. 归一化 —— 余弦相似度要求向量 L2 归一化
4. 指令前缀 —— 部分模型 query 侧需加 instruction，doc 侧不加
5. 语种 —— 中英文场景选多语模型，避免跨语种失效
```

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-small-zh-v1.5")

# 文档和查询分别编码
docs = ["如何训练神经网络", "北京今天天气很好", "梯度下降是优化算法"]
queries = ["神经网络的训练方法"]

doc_emb = model.encode(docs, normalize_embeddings=True)
q_emb = model.encode(queries, normalize_embeddings=True)

# 余弦相似度（归一化后等价于内积）
sims = q_emb @ doc_emb.T
for i, s in enumerate(sims[0]):
    print(f'相似度 {s:.3f} — {docs[i]}')
```

## Sparse Retrieval

稀疏检索（Sparse Retrieval）是经典的「词项匹配」检索：把文档和查询都表示成词袋/词频向量（大部分维度为 0，故称稀疏），用 BM25 这类算法打分。它的优点是精确匹配强、可解释、无需训练，缺点是「同义不同词」就匹配不上（词汇鸿沟）。

```text
稀疏检索代表：
1. TF-IDF —— 词频 × 逆文档频率，衡量词对文档的重要性
2. BM25 —— TF-IDF 的改进版，带长度归一化和饱和项
3. 倒排索引 —— 词 → 文档列表，检索时查表求交

特点：擅长关键词/专有名词/精确匹配，弱于语义泛化
```

```python
from rank_bm25 import BM25Okapi
import jieba

def tokenize(text):
    return list(jieba.cut(text))

corpus = [
    "机器学习是人工智能的分支",
    "深度神经网络使用梯度下降训练",
    "北京是中国的首都",
]
tokenized_corpus = [tokenize(d) for d in corpus]
bm25 = BM25Okapi(tokenized_corpus)

query = tokenize("神经网络怎么训练")
scores = bm25.get_scores(query)
for i, s in enumerate(scores):
    print(f'BM25 分数 {s:.2f} — {corpus[i]}')
```

## Dense Retrieval

稠密检索（Dense Retrieval）把 query 和 doc 都编码成稠密向量，用向量相似度做召回。它通过预训练 embedding 模型捕获语义，能跨越「同义不同词」的词汇鸿沟，但需要向量索引（如 HNSW/IVF）做近似最近邻搜索，且对专有名词不如稀疏检索精确。

```text
稠密检索流程：
1. 离线 —— 所有 chunk 编码成向量，建 ANN 索引
2. 在线 —— query 编码成向量，做 top-k 近似最近邻搜索
3. 打分 —— 余弦相似度/内积

索引：HNSW（图）、IVF（聚类）、PQ（乘积量化压缩）
```

```python
import faiss
import numpy as np

# 模拟已编码的文档向量（64 维，10000 条）
d = 64
np.random.seed(0)
doc_vectors = np.random.randn(10000, d).astype('float32')
faiss.normalize_L2(doc_vectors)

# 建 HNSW 索引（向量已 L2 归一化，用内积度量等价于余弦相似度）
index = faiss.IndexHNSWFlat(d, 32, faiss.METRIC_INNER_PRODUCT)
index.add(doc_vectors)

# 查询
q = np.random.randn(1, d).astype('float32')
faiss.normalize_L2(q)
distances, ids = index.search(q, k=5)
print(f'最近邻 id: {ids[0].tolist()}，相似度: {distances[0].round(3)}')
```

## Hybrid Search

混合检索（Hybrid Search）同时跑稀疏检索（BM25）和稠密检索（向量），再把两路结果融合。它取长补短：稀疏补稠密的「专有名词/精确匹配」，稠密补稀疏的「语义泛化」，是生产级 RAG 的标配。

```text
融合方法：
1. RRF（倒数排名融合）—— score = Σ 1/(k + rank)，简单且无需调参
2. 加权求和 —— 先归一化分数再按权重相加
3. 学习式 —— 训练一个小模型学融合权重

优势：精确 + 语义双保险，召回率和鲁棒性都更好
```

```python
def reciprocal_rank_fusion(rank_lists, k=60):
    # rank_lists: 多路检索的文档 id 排名列表
    scores = {}
    for ranks in rank_lists:
        for rank, doc_id in enumerate(ranks):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

# 稀疏路和稠密路各自返回的 top-5 文档 id
sparse_ranks = [3, 1, 7, 2, 9]
dense_ranks = [1, 7, 3, 5, 8]
fused = reciprocal_rank_fusion([sparse_ranks, dense_ranks])
print(f'RRF 融合后排名: {fused}')
```

## Reranking

Reranking（重排）在召回阶段拿到候选后，用一个更强的「交叉编码器」逐对精细打分，把最相关的片段排到最前面。召回用双塔（快、可预计算），重排用交叉编码器（慢、但 query-doc 联合建模更准），两者配合是标准范式。

```text
召回 vs 重排：
1. 召回 —— 双塔/BM25，速度快，从海量候选里捞出 top-50~100
2. 重排 —— 交叉编码器，query 和 doc 拼接后联合打分，精度高
3. 模型 —— bge-reranker、cohere rerank、cross-encoder 系列
4. 结果 —— 把 top-100 精排到 top-5~10 喂给 LLM
```

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-base")
query = "神经网络训练方法"
candidates = [
    "梯度下降是训练神经网络的核心优化算法",
    "北京是一座历史悠久的城市",
    "反向传播用于计算神经网络梯度",
]
pairs = [[query, c] for c in candidates]
scores = reranker.predict(pairs)
order = sorted(range(len(scores)), key=lambda i: scores[i], reverse=True)
for i in order:
    print(f'{scores[i]:.3f} — {candidates[i]}')
```

## Query Rewrite

Query Rewrite（查询改写）在检索前把用户原始问题改写成更适合检索的形式：补全省略的指代、纠正口语化、拆解歧义、扩展关键词。因为用户问法往往和文档写法差异很大，改写能显著提升召回率。

```text
改写目标：
1. 补全指代 —— "他"、"这个" 还原成具体实体
2. 口语转书面 —— "咋整" → "如何处理"
3. 澄清歧义 —— 多义词结合上下文消歧
4. 关键词扩展 —— 加同义词、领域术语

实现：规则 + LLM 改写（给 LLM 历史对话让它补全/规范化问题）
```

```python
# 用 LLM 做查询改写（伪代码示意）
def rewrite_query(llm, history, current_question):
    prompt = f"""
    对话历史：{history}
    当前问题：{current_question}
    请把当前问题改写成一个独立的、适合检索的完整问句。
    补全指代、规范化表达，只输出改写后的问题。
    """
    return llm(prompt).strip()

history = "用户：Transformer 是谁提出的？"
question = "它的核心机制是什么？"
print(f'改写后: {rewrite_query(lambda p: "Transformer 的核心机制是什么？", history, question)}')
```

## Multi-Query

Multi-Query（多查询）用 LLM 从一个问题生成多个「不同角度」的查询，分别检索后合并去重。它缓解了「单一查询措辞不佳导致召回差」的问题，能从多个视角捞回更多相关文档，提升召回覆盖率。

```text
Multi-Query 流程：
1. LLM 根据原问题生成 N 个不同表述的查询
2. 每个查询独立检索，各取 top-k
3. 合并去重，作为候选集合
4. （可选）接重排精排

适用：问题复杂、措辞差异大、单一查询召回不足的场景
```

```python
def multi_query_retrieve(llm, retriever, question, n=3):
    prompt = f"请为问题生成 {n} 个不同角度但语义等价的检索查询，每行一个：\n{question}"
    queries = [q.strip() for q in llm(prompt).split("\n") if q.strip()]
    queries.append(question)   # 原始问题也参与
    all_hits = {}
    for q in queries:
        for doc in retriever(q):
            all_hits[doc["id"]] = doc
    return list(all_hits.values())

def fake_llm(p):
    return "神经网络训练方法\n深度学习模型如何优化\n梯度下降算法原理"

def fake_retriever(q):
    return [{"id": i, "text": f"doc{i}"} for i in range(3)]

hits = multi_query_retrieve(fake_llm, fake_retriever, "怎么训练神经网络")
print(f'多查询合并后候选数: {len(hits)}')
```

## HyDE

HyDE（Hypothetical Document Embedding，假设性文档嵌入）不直接用 query 检索，而是先让 LLM「假装写一篇能回答这个问题的文档」，再用这篇假设文档的向量去检索真实文档。假设文档的措辞更接近语料库风格，能缓解 query 与 doc 的分布差异。

```text
HyDE 流程：
1. LLM 根据问题生成一篇「假设答案文档」
2. 对假设文档做 embedding
3. 用该向量检索真实知识库，找相似文档
4. 把真实文档交给 LLM 生成最终答案

适用：query 短、口语化，与文档风格差异大的场景
```

```python
def hyde_retrieve(llm, embed, index, question):
    prompt = f"请写一段能回答以下问题的说明性文字（不用准确，写风格即可）：\n{question}"
    hypothetical_doc = llm(prompt)
    hyp_emb = embed(hypothetical_doc)
    # 用假设文档向量检索
    scores, ids = index.search(hyp_emb, k=5)
    return ids

# 伪实现
def fake_embed(text):
    import numpy as np
    return np.random.randn(1, 64).astype('float32')

print('HyDE 检索流程已定义：先生成假设文档，再用其向量检索')
```

## Context Compression

Context Compression（上下文压缩）把召回的文档片段「压榨」成最相关、最精炼的内容再喂给 LLM，去掉冗余和无关部分。它既节省 token（降低成本、腾出上下文窗口），又减少噪声干扰，让模型聚焦真正有用的信息。

```text
压缩手段：
1. LLM 摘要 —— 对每个片段生成摘要，只保留与 query 相关的部分
2. 抽取式 —— 只保留含答案关键词的句子
3. 排序截断 —— 重排后只取前 k 个最相关片段
4. 上下文窗口管理 —— 按 token 预算分配各片段长度

目标：在有限的 prompt 空间里装下最多有用信息
```

```python
def compress_context(llm, query, docs, max_tokens=2000):
    # 逐片段抽取与 query 相关的句子（简化的抽取式压缩）
    compressed = []
    used = 0
    for doc in docs:
        prompt = f"问题：{query}\n片段：{doc}\n只输出与该问题直接相关的句子。"
        relevant = llm(prompt)
        est_tokens = len(relevant) // 2     # 粗略估算
        if used + est_tokens > max_tokens:
            break
        compressed.append(relevant)
        used += est_tokens
    return "\n".join(compressed)

def fake_llm(p):
    return "相关句：梯度下降是优化算法"

print(compress_context(fake_llm, "怎么训练", ["很长的文档..."], max_tokens=500))
```

## Citation

Citation（引用/溯源）让模型在回答里标注「这句话来自哪个文档的哪一段」，用户能点击跳回原文核实。它是抑制幻觉、建立信任的关键——让每个关键论断都有出处，而不是凭空生成。

```text
引用实现方式：
1. 显式编号 —— 每个检索片段编上 [1][2]，prompt 里要求模型在句尾标注
2. 后处理对齐 —— 生成后把答案句子和检索片段做相似度对齐，自动挂引用
3. 强制约束 —— 要求模型「只能引用给定片段」，禁止外推

注意：引用编号要映射回真实文档 + 页码，便于前端跳转
```

```python
def build_cited_prompt(question, docs):
    parts = [f"请根据以下资料回答问题，并在句尾标注来源编号，如 [1]。\n问题：{question}\n\n资料："]
    for i, doc in enumerate(docs, start=1):
        parts.append(f"[{i}] {doc}")
    parts.append("\n要求：只使用上述资料，每个关键论断标注来源编号。")
    return "\n".join(parts)

docs = ["Transformer 使用自注意力机制。", "BERT 是双向 Transformer 编码器。"]
prompt = build_cited_prompt("Transformer 用了什么机制？", docs)
print(prompt)
```

## RAG Evaluation

RAG Evaluation（RAG 评估）从「检索」和「生成」两个层面衡量系统质量，缺一不可。只测生成不看检索，可能「答得对但没用到知识库」；只测检索不看生成，可能「检索准但答案错」。核心指标是忠实度（答案是否忠于检索到的证据）。

```text
评估维度：
1. 检索质量 —— 召回率/命中率/MRR/NDCG（衡量有没有捞到对文档）
2. 生成质量 —— 忠实度（Faithfulness，答案是否忠于证据）
3. 答案相关性 —— 答案是否切题
4. 上下文相关性 —— 召回的片段是否真的相关

框架：RAGAS、TruLens、ARES；指标可用 LLM-as-judge 自动打分
```

```python
def faithfulness_score(claims, retrieved_docs):
    # 简化：答案的每个「论断」能否在检索文档中找到支撑
    supported = 0
    for claim in claims:
        if any(claim.split()[0] in doc for doc in retrieved_docs):
            supported += 1
    return supported / len(claims) if claims else 0.0

claims = ["Transformer 使用自注意力", "它由 Google 提出"]
docs = ["Transformer 使用自注意力机制", "Transformer 由 Google 在 2017 年提出"]
score = faithfulness_score(claims, docs)
print(f'忠实度得分: {score:.2f}')
```

### 场景二：带引用和重排的完整 RAG 流水线

```python
from langchain_community.vectorstores import Chroma
from sentence_transformers import CrossEncoder

def rag_pipeline(question, retriever, reranker, llm):
    # 召回
    candidates = retriever.invoke(question)
    # 重排
    pairs = [[question, c.page_content] for c in candidates]
    scores = reranker.predict(pairs)
    order = sorted(range(len(scores)), key=lambda i: scores[i], reverse=True)
    top = [candidates[i] for i in order[:5]]
    # 生成（带引用）
    context = "\n".join(f"[{i+1}] {d.page_content}" for i, d in enumerate(top))
    prompt = f"资料：\n{context}\n\n问题：{question}\n请回答并标注来源编号。"
    answer = llm(prompt)
    return answer, top

def fake_llm(p):
    return "根据 [1] 和 [3]，答案是……"

print('RAG 流水线定义完成：召回 → 重排 → 带引用生成')
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分块按文档结构和语义切，别硬按固定字数一刀切
2. 保留 chunk 的元数据（来源、页码、标题），引用和溯源都靠它
3. 生产环境用混合检索（BM25 + 向量）+ 重排，别只依赖单一稠密检索
4. query 侧和 doc 侧 embedding 用同一个模型，且注意是否需要指令前缀
5. 检索结果喂 LLM 前先压缩/重排截断，控制 token 成本
6. 上线前用 RAGAS 等框架测忠实度，防止「检索准但答案假」

### 踩坑记录

```text
坑 1：分块切断了关键语义
结论：检索出的片段是半句话，模型看不懂、答不对。
原因：固定字数切块，把跨句的因果关系切断。
解法：用递归/语义分块，加 chunk_overlap 保留上下文。

坑 2：query 和 doc 用不同 embedding 模型
结论：检索结果完全跑偏，相似度都接近 0。
原因：不同模型向量空间不对齐，相似度无意义。
解法：query/doc 统一用同一模型编码，换模型要重建索引。

坑 3：PDF 表格被解析成乱序文本
结论：表格数据检索时完全找不到，或语义错乱。
原因：纯文本提取丢失表格结构，单元格内容串行拼接。
解法：用结构化解析器把表格转 Markdown/JSON 再入库。

坑 4：只测生成不测检索
结论：系统评测分数很高，但答案其实没用知识库、全靠模型背。
原因：评估只看了答案质量，没看是否真的检索到证据。
解法：同时测检索命中率和答案忠实度，忠实度是底线。

坑 5：忽略 chunk 元数据导致无法引用
结论：模型标了 [3]，但前端无法跳转到原文出处。
原因：chunk 只存了文本，没存来源页码等元数据。
解法：加载/分块阶段就保留元数据，编号映射回原文位置。

坑 6：所有查询都套 HyDE/Multi-Query 拖慢速度
结论：简单关键词查询也被多轮 LLM 改写，延迟爆炸。
原因：过度优化召回，忽视了简单查询不需要复杂改写。
解法：对查询复杂度分类，简单查询直查，复杂查询才上改写/扩展。
```
