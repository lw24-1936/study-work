## 概述

MCP（Model Context Protocol，模型上下文协议）是 Anthropic 提出的开放协议，为 LLM 应用提供了一套「标准接口」来连接外部数据源和工具。它的定位类似 AI 界的 USB-C：以前每个 LLM 要对接每个工具都得写专用集成（M×N 问题），有了 MCP，工具只需实现一次 MCP Server，任何支持 MCP 的 Client 都能即插即用。

```text
MCP 的核心价值：
1. 标准化 —— 统一的工具/资源/提示接入方式，消除 M×N 集成
2. 即插即用 —— Server 实现一次，所有 MCP Client 通用
3. 安全边界 —— 明确的权限与上下文隔离机制
4. 生态 —— 社区积累了海量 MCP Server（数据库、浏览器、文件系统等）

架构：MCP Host（宿主应用）→ MCP Client（1:1 连 Server）→ MCP Server
```

```python
# MCP 最小 Server 示意（用官方 Python SDK 的概念结构）
from mcp.server import Server
from mcp.types import Tool, TextContent

app = Server("example-server")

@app.list_tools()
async def list_tools():
    return [Tool(name="add", description="两数相加", inputSchema={
        "type": "object",
        "properties": {
            "a": {"type": "number"},
            "b": {"type": "number"},
        },
        "required": ["a", "b"],
    })]

@app.call_tool()
async def call_tool(name, arguments):
    if name == "add":
        return [TextContent(type="text", text=str(arguments["a"] + arguments["b"]))]
    raise ValueError(f"未知工具 {name}")

print('MCP Server 结构已定义：暴露 add 工具')
```

## Client

MCP Client（客户端）是发起连接的主动方，内嵌在 LLM 应用（Host）里，负责与 MCP Server 建立连接、发现能力（列出工具/资源/提示）、发起调用、把结果回传给模型。一个 Host 可同时连多个 Server，每个 Server 对应一个独立 Client 连接。

```text
Client 职责：
1. 连接管理 —— 与 Server 建立/维护/关闭会话
2. 能力发现 —— 调用 list_tools/list_resources/list_prompts
3. 发起调用 —— call_tool/read_resource/get_prompt
4. 结果转换 —— 把 Server 返回的内容转成 LLM 可用的消息

关系：1 个 Host → 多个 Client → 每个 Client 连 1 个 Server
```

```python
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def connect_and_list_tools():
    params = StdioServerParameters(
        command="python",
        args=["my_server.py"],
    )
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            tools = await session.list_tools()
            return tools

# asyncio.run(connect_and_list_tools())
print('MCP Client 连接流程已定义：stdio 连接 → 初始化 → 列出工具')
```

## Server

MCP Server（服务器）是被连接方，封装了外部能力（数据库查询、文件操作、API 调用等），把它们以「工具、资源、提示」的形式暴露给 Client。Server 是能力提供者，是 MCP 生态里数量最多的一侧——每个第三方服务都可以做一个自己的 MCP Server。

```text
Server 提供三种原语：
1. Tool —— 可执行的动作（模型可调用）
2. Resource —— 只读数据（模型可读取的上下文）
3. Prompt —— 预定义的提示模板（用户可选）

Server 实现要点：能力声明 + 处理请求 + 返回结构化结果 + 错误处理
```

```python
from mcp.server import Server

app = Server("notes-server")

@app.list_resources()
async def list_resources():
    # 暴露可读资源（如笔记目录）
    return [{"uri": "notes://daily", "name": "每日笔记", "mimeType": "text/markdown"}]

@app.read_resource()
async def read_resource(uri):
    if uri == "notes://daily":
        return "今天的笔记内容……"
    raise ValueError(f"未知资源 {uri}")

print('MCP Server 资源能力已定义')
```

## Tool

Tool（工具）是 MCP 里「模型可调用的动作」：Server 声明工具的名字、描述和 JSON Schema 参数，Client 把它转成 LLM 的 function calling 定义，模型决定何时调用、传什么参数，Server 执行后返回结果。它是 MCP 最核心、用得最多的原语。

```text
Tool 的定义要素：
1. name —— 唯一标识，模型调用时引用
2. description —— 语义说明，直接影响模型选工具的准确性
3. inputSchema —— JSON Schema 定义参数类型和约束
4. 执行函数 —— 真正干活的逻辑
5. 返回 —— 结构化结果（文本/图片等 Content）

最佳实践：描述写清楚「什么时候用、参数什么意思、返回什么」
```

```python
from mcp.types import Tool, TextContent

WEATHER_TOOL = Tool(
    name="get_weather",
    description="查询指定城市当前天气，返回温度和天气状况",
    inputSchema={
        "type": "object",
        "properties": {
            "city": {"type": "string", "description": "城市名，如 北京"},
            "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]},
        },
        "required": ["city"],
    },
)

async def get_weather_handler(arguments):
    city = arguments["city"]
    unit = arguments.get("unit", "celsius")
    return [TextContent(type="text", text=f"{city}：26 度（{unit}）")]

print(f'工具已定义: {WEATHER_TOOL.name} — {WEATHER_TOOL.description}')
```

## Resource

Resource（资源）是 MCP 里「模型可读取的只读数据」，用 URI 标识。它和 Tool 的区别：Tool 是动作（改变状态），Resource 是数据（只读上下文）。比如文件内容、数据库记录、API 的 GET 结果都可以作为 Resource 暴露，供模型在对话中读取参考。

```text
Resource 特点：
1. URI 标识 —— 如 file:///docs/x.md、db://users/1
2. 只读 —— 不改变外部状态，可安全读取
3. 内容类型 —— mimeType 标注（文本/JSON/图片）
4. 用途 —— 给模型提供上下文，而非执行动作

与 Tool 对比：Tool=do（动作），Resource=read（数据）
```

```python
from mcp.types import Resource

RESOURCE_DEF = Resource(
    uri="file:///docs/company-policy.md",
    name="公司政策文档",
    description="公司内部政策说明",
    mimeType="text/markdown",
)

async def read_policy(uri):
    if uri == "file:///docs/company-policy.md":
        return "## 请假政策\n员工每年享有 10 天年假……"
    raise ValueError(f"未知资源 {uri}")

print(f'资源已定义: {RESOURCE_DEF.name} → {RESOURCE_DEF.uri}')
```

## Prompt

Prompt（提示模板）是 MCP 里「预定义的提示词」，Server 可以把常用的、精心设计的 prompt 模板暴露给用户，用户从 UI 里直接选用，而不用每次手写。它常带参数，让同一模板适配不同输入。

```text
Prompt 特点：
1. 模板化 —— 带占位参数，如 {{topic}}
2. 复用 —— 沉淀团队的最佳提示词，统一质量
3. 可发现 —— 用户能列出并选用 Server 提供的 prompt
4. 用途 —— 代码审查、总结、角色设定等固定范式

与 Tool/Resource 对比：Prompt 是「给模型的指令模板」，不是动作也不是数据
```

```python
from mcp.types import Prompt, PromptMessage

CODE_REVIEW_PROMPT = Prompt(
    name="code_review",
    description="对代码进行专业审查",
    arguments=[
        {"name": "language", "description": "编程语言", "required": True},
        {"name": "code", "description": "待审查代码", "required": True},
    ],
)

async def get_prompt(name, arguments):
    if name == "code_review":
        msg = (
            f"你是资深 {arguments['language']} 工程师，请审查以下代码，"
            f"指出问题并给改进建议：\n{arguments['code']}"
        )
        return [PromptMessage(role="user", content={"type": "text", "text": msg})]
    raise ValueError(f"未知提示 {name}")

print(f'Prompt 已定义: {CODE_REVIEW_PROMPT.name}')
```

## Transport

Transport（传输层）定义 MCP Client 和 Server 之间「怎么通信」。最常用的是 stdio（标准输入输出，Server 作为子进程启动）和 HTTP/SSE（远程 Server 走网络）。传输层是 MCP 的底层，负责消息的序列化和通道管理。

```text
两种主要 Transport：
1. stdio —— 本地进程，Client 启动 Server 子进程，通过 stdin/stdout 通信
   - 简单、无网络暴露，适合本地工具
2. Streamable HTTP / SSE —— 远程服务，走 HTTP 协议
   - 适合远程部署、多用户共享的 Server

选择：本地个人工具用 stdio，团队共享/云端用 HTTP
```

```python
# stdio 传输：Client 启动 Server 子进程
from mcp import StdioServerParameters
from mcp.client.stdio import stdio_client

stdio_params = StdioServerParameters(
    command="npx",                       # 用 npx 启动 Node 版 Server
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)

# 远程 HTTP 传输（概念示意）
remote_url = "https://mcp.example.com/sse"

print(f'stdio 参数: {stdio_params.command} {stdio_params.args}')
print(f'远程 HTTP 端点: {remote_url}')
```

## Authentication

Authentication（认证）回答「你是谁」——验证连接方的身份。MCP 支持在传输层或应用层做认证，比如 HTTP 传输用 OAuth 2.0 / Bearer Token，stdio 传输默认信任本地进程。认证是远程 MCP 部署的前提，否则任何人都能连上你的 Server。

```text
认证方式：
1. OAuth 2.0 —— 标准的授权码/客户端凭证流程，适合远程 HTTP Server
2. Bearer Token —— 简单令牌，Header 里带 Authorization
3. API Key —— 服务商常见的简单认证
4. mTLS —— 双向证书认证，企业级安全场景

注意：stdio 本地进程无网络认证，安全靠进程边界本身
```

```python
# HTTP 传输携带 Bearer Token 认证（概念示意）
import httpx

headers = {
    "Authorization": "Bearer YOUR_ACCESS_TOKEN",
    "Content-Type": "application/json",
}

def authenticated_request(url, payload):
    resp = httpx.post(url, json=payload, headers=headers)
    if resp.status_code == 401:
        raise PermissionError("认证失败：token 无效或过期")
    return resp.json()

print('认证请求已定义：Bearer Token 注入 + 401 处理')
```

## Authorization

Authorization（授权）回答「你能做什么」——在认证之后，限制连接方只能访问被允许的工具、资源和操作。它是细粒度的权限控制，防止一个拿到连接权限的 Client 越权访问敏感数据或执行危险操作。

```text
授权模型：
1. 范围（Scope）—— 声明客户端被授予的权限集合（如 read:files、write:db）
2. 资源级 —— 控制能读哪些 URI、能调哪些工具
3. 最小权限原则 —— 只授完成任务所需的最小权限
4. 用户同意 —— 敏感操作前要求用户显式确认

实现：Server 端在执行前校验 scope，拒绝越权请求
```

```python
class AuthorizationPolicy:
    def __init__(self):
        self.grants = {
            "client-a": {"tools": ["read_file", "search"], "resources": ["docs/*"]},
        }

    def can_call_tool(self, client_id, tool_name):
        allowed = self.grants.get(client_id, {}).get("tools", [])
        return tool_name in allowed

    def can_read_resource(self, client_id, uri):
        allowed = self.grants.get(client_id, {}).get("resources", [])
        return any(uri.startswith(p.replace("*", "")) for p in allowed)

policy = AuthorizationPolicy()
print(f'client-a 能否调用 delete_file: {policy.can_call_tool("client-a", "delete_file")}')
print(f'client-a 能否读 docs/x.md: {policy.can_read_resource("client-a", "docs/x.md")}')
```

## Security

Security（安全）是 MCP 的整体安全考量，覆盖认证、授权、输入校验、提示注入、数据泄露等多个维度。因为 MCP 把 LLM 和真实系统连起来，一个恶意 prompt 或一个越权 Server 就可能造成数据泄露或系统破坏，安全必须从设计阶段就考虑。

```text
安全威胁与对策：
1. 提示注入 —— 恶意内容诱导模型调用危险工具 → 工具描述加护栏、危险操作需确认
2. 越权访问 —— Client 访问了不该访问的资源 → 严格授权 + 最小权限
3. 数据外泄 —— 敏感数据被模型带出 → 输出审查、脱敏、审计日志
4. 恶意 Server —— 连上伪造的 Server 窃取上下文 → Server 白名单 + 签名校验
5. 供应链风险 —— 第三方 Server 含后门 → 审查 Server 来源、沙箱隔离

原则：默认不信任外部输入，关键操作人机确认，全程审计
```

```python
class SecureToolGateway:
    def __init__(self):
        self.blocked_patterns = ["rm -rf", "DROP TABLE", "shutdown"]
        self.audit_log = []

    def execute(self, tool_name, args, require_confirm=False):
        cmd = f"{tool_name}({args})"
        # 1. 危险操作拦截
        for pattern in self.blocked_patterns:
            if pattern in cmd:
                self.audit_log.append(f"BLOCKED: {cmd}")
                return "操作被安全策略拦截"
        # 2. 高风险操作人工确认
        if require_confirm:
            self.audit_log.append(f"CONFIRM_REQUIRED: {cmd}")
            return "需要人工确认"
        self.audit_log.append(f"ALLOWED: {cmd}")
        return "执行成功"

gateway = SecureToolGateway()
print(gateway.execute("shell", "rm -rf /"))
print(gateway.execute("db", "SELECT * FROM users", require_confirm=True))
print(f'审计日志条数: {len(gateway.audit_log)}')
```

## 应用场景实战

### 场景一：搭建文件系统 MCP Server 并接入 LLM

```python
# 一个暴露文件读写工具的 MCP Server（概念结构）
from mcp.server import Server
from mcp.types import Tool, TextContent

app = Server("fs-server")

@app.list_tools()
async def list_tools():
    return [
        Tool(name="read_file", description="读取文本文件内容",
             inputSchema={"type": "object",
                          "properties": {"path": {"type": "string"}},
                          "required": ["path"]}),
        Tool(name="list_dir", description="列出目录内容",
             inputSchema={"type": "object",
                          "properties": {"path": {"type": "string"}},
                          "required": ["path"]}),
    ]

@app.call_tool()
async def call_tool(name, arguments):
    import os
    if name == "list_dir":
        entries = os.listdir(arguments["path"])
        return [TextContent(type="text", text="\n".join(entries))]
    if name == "read_file":
        with open(arguments["path"], "r", encoding="utf-8") as f:
            return [TextContent(type="text", text=f.read())]
    raise ValueError(f"未知工具 {name}")

print('文件系统 MCP Server 已定义：read_file / list_dir')
```

### 场景二：HTTP 远程 MCP 的 OAuth 认证流程

```python
import httpx

def oauth_client_credentials(token_url, client_id, client_secret, scope):
    # OAuth 2.0 客户端凭证流程换取 access token
    resp = httpx.post(token_url, data={
        "grant_type": "client_credentials",
        "client_id": client_id,
        "client_secret": client_secret,
        "scope": scope,
    })
    resp.raise_for_status()
    token = resp.json()["access_token"]
    return token

def call_mcp_endpoint(endpoint, token, payload):
    headers = {"Authorization": f"Bearer {token}"}
    return httpx.post(endpoint, json=payload, headers=headers).json()

```

## 最佳实践与踩坑记录

### 最佳实践

1. 工具/资源描述写得详尽（用途、参数、返回），描述质量直接决定模型调用准确率
2. 本地个人工具用 stdio 传输，远程共享服务才用 HTTP + 认证
3. 遵循最小权限原则，只暴露完成任务所需的最小工具集合
4. 危险操作（删除、写入、付费）加人工确认，别让模型无约束执行
5. 全程记录审计日志，出了问题能追溯是哪个 Client 调了什么
6. 对外部 Server 建立白名单和来源审查，避免连上恶意 Server

### 踩坑记录

```text
坑 1：工具描述太简略导致模型瞎调
结论：模型调用时参数传错、或根本不用这个工具。
原因：description 只写了工具名，没写用途和参数语义。
解法：按「何时用 + 参数含义 + 返回什么」写全描述，附示例。

坑 2：stdio 本地工具直接暴露给远程调用
结论：本地文件系统 Server 被远程 Client 访问，数据泄露。
原因：stdio 无网络认证，却把 Host 暴露到了公网。
解法：本地工具只接本地 Host，远程访问必须走 HTTP + 认证。

坑 3：只认证不授权
结论：连上的 Client 通过认证后能调所有工具，越权删库。
原因：做了「你是谁」没做「你能做什么」，权限粒度缺失。
解法：认证 + 细粒度授权双管齐下，执行前校验 scope。

坑 4：忽略提示注入风险
结论：用户上传的恶意文档诱导模型调用了危险工具。
原因：把检索到的外部内容直接当指令，模型被注入。
解法：工具层加护栏拦截危险操作，外部内容与指令明确隔离。

坑 5：传输层选错导致多用户冲突
结论：多人共用 stdio Server，状态互相污染。
原因：stdio 是单进程私有通道，不适合多用户共享。
解法：多用户共享场景改用 HTTP/SSE 远程 Server。

坑 6：Server 无错误处理导致连接僵死
结论：Server 内部异常未捕获，Client 一直等不到响应。
原因：call_tool 抛异常没有转成结构化错误返回。
解法：Server 统一 try/except，异常转成标准错误响应。
```
