## 概述

推理（Inference）是 LLM 上线后真正服务用户的阶段：给定 prompt，模型逐 token 自回归地生成回答。它不像训练那样追求梯度更新，而是围绕「生成质量、速度、显存、吞吐」四个目标做工程优化——从采样策略到量化、到 KV Cache 管理，都是推理工程的核心战场。

```text
推理阶段的核心问题：
1. 生成质量 —— 用什么采样策略让输出既准确又多样（Greedy/Temperature/Top-K/Top-P/Beam）
2. 显存 —— 模型权重和 KV Cache 占显存，靠量化（INT8/INT4/FP8/GPTQ/AWQ）压缩
3. 速度 —— 逐 token 生成太慢，靠投机解码、连续批处理加速
4. 吞吐 —— 多请求并发共享 GPU，靠 Paged Attention 高效管理 KV Cache
```

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

# 最小推理示例：加载模型并生成
model_name = "gpt2"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name)

inputs = tokenizer("今天天气", return_tensors="pt")
outputs = model.generate(**inputs, max_new_tokens=20, do_sample=False)
print(tokenizer.decode(outputs[0], skip_special_tokens=True))
```

## Greedy

Greedy（贪心解码）每一步都选概率最高的那个 token，是最简单、最确定性的采样策略。它速度快、结果可复现，但容易陷入重复和「次优陷阱」——某一步选错后面无法回头。

```text
贪心解码：
在每一步 t，选 y_t = argmax P(y_t | y_<t)

特点：
1. 确定性 —— 同样的输入永远给同样的输出（temperature=0 等价）
2. 快 —— 每步只算 argmax，无随机采样开销
3. 局部最优 —— 只贪当前最优，可能错过全局更好的序列
4. 易重复 —— 高概率 token 之间互相强化，容易循环
```

```python
import torch

def greedy_decode(logits):
    # logits: (1, vocab_size)，取最大概率 token
    return torch.argmax(logits, dim=-1)

# 模拟一个 vocab 大小为 5 的 logits
logits = torch.tensor([[0.1, 0.2, 0.4, 0.25, 0.05]])
next_token = greedy_decode(logits)
print(f'贪心选中的 token id: {next_token.item()}（概率最大）')
```

## Temperature

Temperature（温度）通过缩放 logits 来控制输出分布的「尖锐程度」。温度越高分布越平、越随机、越有创意；温度越低分布越尖、越确定。它常与 Top-K/Top-P 组合使用。

```text
数学定义：
p_i = softmax(z_i / T)，T 是温度

效果：
1. T < 1 —— 分布更尖，高分 token 更突出，输出更确定
2. T = 1 —— 原始分布
3. T > 1 —— 分布更平，低分 token 概率抬升，输出更随机
4. T → 0 —— 退化为贪心解码
```

```python
import torch
import torch.nn.functional as F

def temperature_sampling(logits, temperature=1.0):
    logits = logits / temperature          # 缩放 logits
    probs = F.softmax(logits, dim=-1)
    return torch.multinomial(probs, num_samples=1)

logits = torch.tensor([[2.0, 1.0, 0.1, 0.05, 0.02]])
print(f'T=0.5 选: {temperature_sampling(logits, 0.5).item()}（更确定）')
print(f'T=2.0 选: {temperature_sampling(logits, 2.0).item()}（更随机）')
```

## Top-K

Top-K 采样在每一步只从概率最高的 K 个 token 里随机采样，其余 token 的概率直接置 0。它用一个「硬阈值」K 截断分布，避免低概率 token 干扰，同时保留一定多样性。

```text
Top-K 采样流程：
1. 对 logits 做 softmax 得到完整分布
2. 取概率最高的 K 个 token，其余置 0
3. 在剩下的 K 个 token 上重新归一化，随机采样

局限：
1. K 固定 —— 分布尖时 K 可能太大（混入垃圾 token），分布平时 K 太小（丢失多样性）
2. 无自适应性 —— 不随上下文分布形状调整
```

```python
import torch
import torch.nn.functional as F

def top_k_sampling(logits, k=5):
    probs = F.softmax(logits, dim=-1)
    top_k_probs, top_k_idx = torch.topk(probs, k)   # 取 top-k
    # 其余位置概率置 0，重新归一化
    filtered = torch.zeros_like(probs)
    filtered.scatter_(-1, top_k_idx, top_k_probs)
    filtered = filtered / filtered.sum(dim=-1, keepdim=True)
    return torch.multinomial(filtered, num_samples=1)

logits = torch.randn(1, 50)   # vocab 大小 50
print(f'Top-K=5 采样 token: {top_k_sampling(logits, 5).item()}')
```

## Top-P

Top-P（核采样 / Nucleus Sampling）动态选择「累计概率达到 p」的最小 token 集合，让截断阈值随分布形状自适应。它解决了 Top-K 固定 K 的缺陷，是目前最常用的采样策略之一。

```text
Top-P 采样流程：
1. 按概率从高到低排序 token
2. 累加概率，直到累计概率 ≥ p，保留这些 token
3. 在保留集合上重新归一化后随机采样

与 Top-K 对比：
1. Top-K 按「数量」截断，Top-P 按「概率质量」截断
2. 分布尖时 Top-P 自动保留更少 token，分布平时保留更多
3. 实践中常同时用 Top-K 和 Top-P（先 K 后 P 双重截断）
```

```python
import torch
import torch.nn.functional as F

def top_p_sampling(logits, p=0.9):
    probs = F.softmax(logits, dim=-1)
    sorted_probs, sorted_idx = torch.sort(probs, descending=True)
    cumsum = torch.cumsum(sorted_probs, dim=-1)
    # 累计概率超过 p 的位置 mask 掉
    keep = cumsum <= p
    keep[..., 0] = True    # 至少保留概率最高的一个
    masked = torch.where(keep, sorted_probs, torch.zeros_like(sorted_probs))
    filtered = torch.zeros_like(probs)
    filtered.scatter_(-1, sorted_idx, masked)
    filtered = filtered / filtered.sum(dim=-1, keepdim=True)
    return torch.multinomial(filtered, num_samples=1)

logits = torch.randn(1, 100)
print(f'Top-P=0.9 采样 token: {top_p_sampling(logits, 0.9).item()}')
```

## Beam Search

Beam Search（束搜索）在每一步同时维护 B 条「最有希望」的候选序列，是贪心的推广。它牺牲一定速度换取全局更优的序列，在翻译、摘要等「答案较确定」的任务上质量更高，但在开放生成里会让输出变平淡。

```text
束搜索流程：
1. 维护 beam_width=B 条候选序列及其累计对数概率
2. 每步对每条候选扩展 vocab 个后继，共 B*vocab 条
3. 按累计分数保留 top-B 条，重复直到结束或触发 EOS
4. 分数常用 log 概率累加，等价于避免浮点下溢

注意：
1. 长度惩罚 —— 短序列分数天然更高，需除以长度^α 归一化
2. 多样性 —— B 越大越确定，开放对话里反而僵硬
```

```python
import torch
import torch.nn.functional as F

def beam_search_step(seqs, scores, logits_fn, beam_width=3):
    new_seqs, new_scores = [], []
    for seq, score in zip(seqs, scores):
        logits = logits_fn(seq)                     # (vocab,)
        log_probs = F.log_softmax(logits, dim=-1)
        top_v, top_i = torch.topk(log_probs, beam_width)
        for v, i in zip(top_v, top_i):
            new_seqs.append(seq + [i.item()])
            new_scores.append(score + v.item())
    # 全局 top-B
    order = sorted(range(len(new_scores)), key=lambda j: new_scores[j], reverse=True)
    return [new_seqs[j] for j in order[:beam_width]], [new_scores[j] for j in order[:beam_width]]

# 伪 logits 函数（这里用固定分布模拟）
def fake_logits_fn(seq):
    return torch.randn(10)

seqs = beam_search_step([[0]], [0.0], fake_logits_fn, beam_width=3)
print(f'束搜索后候选序列数: {len(seqs)}（beam_width=3）')
```

## Quantization

量化（Quantization）把高精度浮点权重/激活映射到低精度整数或低比特浮点，从而压缩模型体积、降低显存、加速计算。它是 LLM 部署里最核心的压缩手段，代价是引入一定精度损失。

```text
量化核心概念：
1. 对称量化 —— x_q = round(x / s)，s 是缩放因子，零点是 0
2. 非对称量化 —— x_q = round((x - z) / s)，z 是零点，适合非对称分布
3. 权重量化 vs 激活量化 —— 权重静态可预量化，激活随输入动态变化更难
4. PTQ vs QAT —— 训练后量化（无需重训）vs 量化感知训练（精度更高）

量化后模型：
INT8 权重 ~1 字节/参数，INT4 ~0.5 字节/参数，对比 FP16 的 2 字节大幅缩小
```

```python
import torch

def symmetric_quantize(x, bits=8):
    # 对称线性量化到 int8
    qmax = 2 ** (bits - 1) - 1          # 127
    scale = x.abs().max() / qmax        # 缩放因子
    x_q = torch.round(x / scale).clamp(-qmax, qmax).to(torch.int8)
    return x_q, scale

def symmetric_dequantize(x_q, scale):
    return x_q.float() * scale

x = torch.randn(10) * 0.5
x_q, s = symmetric_quantize(x, bits=8)
x_hat = symmetric_dequantize(x_q, s)
print(f'量化误差: {(x - x_hat).abs().max().item():.4f}，缩放因子 {s:.4f}')
```

## GPTQ

GPTQ 是一种基于「逐层重建误差最小化」的 PTQ（训练后量化）方法，能把模型量化到 INT4/INT3/INT2 而精度损失很小。它的核心思想是：量化某一列的权重时，用二阶 Hessian 信息补偿其余权重，最小化该层输出误差。

```text
GPTQ 核心思想：
1. 逐层量化 —— 每层独立处理，不端到端重训
2. 误差补偿 —— 量化某列权重后，用 Hessian 逆矩阵更新剩余权重，抵消误差
3. 无需重训 —— 只需少量校准数据，几分钟到几十分钟完成
4. 精度好 —— INT4 下通常只有极小 perplexity 损失

适用：GPU 上追求「体积小 + 精度高」的 INT4 部署，代表库 AutoGPTQ/ExLlama
```

```python
# 使用 AutoGPTQ 做 4-bit 量化的示意（需安装 auto-gptq）
# pip install auto-gptq
from transformers import AutoTokenizer
from auto_gptq import AutoGPTQForCausalLM, BaseQuantizeConfig

model_name = "TheBloke/Llama-2-7B-GPTQ"
quantize_config = BaseQuantizeConfig(
    bits=4,                     # 4-bit 量化
    group_size=128,             # 分组大小
    desc_act=False,             # 是否用描述性激活
)

# 加载已量化的 GPTQ 模型
model = AutoGPTQForCausalLM.from_quantized(
    model_name, use_triton=False, quantize_config=quantize_config
)
print(f'GPTQ 模型加载完成，量化精度: {quantize_config.bits}bit')
```

## AWQ

AWQ（Activation-aware Weight Quantization）观察到「只有少数权重对输出影响大」，于是不对所有权重一视同仁地量化，而是保护那些「对应大激活」的重要权重通道，对它们用更高精度或用缩放因子补偿，从而在 INT4 下几乎不损失精度。

```text
AWQ 核心思想：
1. 激活感知 —— 根据激活幅值判断权重重要性（激活大 → 通道重要）
2. 保护重要通道 —— 对重要通道做缩放保护，减少量化误差
3. 无需重训/回传 —— 不依赖梯度，只用统计激活分布
4. 保持硬件友好 —— 不引入稀疏性，仍走标准 GEMM，推理更快

与 GPTQ 对比：GPTQ 靠 Hessian 重建，AWQ 靠激活统计，二者都免训练
```

```python
# 使用 AutoAWQ 量化模型的示意（需安装 autoawq）
# pip install autoawq
from awq import AutoAWQForCausalLM
from transformers import AutoTokenizer

model_path = "lmsys/vicuna-7b-v1.5"
quant_path = "vicuna-7b-v1.5-awq"

# 加载模型并量化到 4-bit
model = AutoAWQForCausalLM.from_pretrained(model_path)
tokenizer = AutoTokenizer.from_pretrained(model_path, trust_remote_code=True)

# 用校准数据量化
model.quantize(tokenizer, quant_config={
    "zero_point": True,        # 使用零点
    "q_group_size": 128,       # 分组大小
    "w_bit": 4,                # 4-bit 权重
    "version": "GEMM",
})
model.save_quantized(quant_path)
print(f'AWQ 量化完成，保存到 {quant_path}')
```

## INT8

INT8 量化把 FP32/FP16 权重压缩到 8-bit 整数，体积减半（相对 FP16），精度损失极小，几乎无损。它是「零风险」的量化起点，很多推理引擎默认支持，CPU 上还有专用指令加速。

```text
INT8 特点：
1. 体积 —— 1 字节/参数，FP16 的一半、FP32 的四分之一
2. 精度 —— 几乎无损，perplexity 损失可忽略
3. 加速 —— CPU 有 VNNI/Dot 指令，GPU 有 INT8 Tensor Core
4. 实现 —— 对称/非对称 + per-tensor/per-channel 缩放
```

```python
import torch

def int8_quantize_per_tensor(x):
    qmax = 127
    scale = x.abs().max() / qmax
    x_q = torch.round(x / scale).clamp(-qmax, qmax).to(torch.int8)
    return x_q, scale

def int8_matmul(a_q, a_scale, b_q, b_scale):
    # 用 int8 近似浮点矩阵乘
    return (a_q.float() @ b_q.float()) * (a_scale * b_scale)

a = torch.randn(4, 8)
b = torch.randn(8, 4)
a_q, a_s = int8_quantize_per_tensor(a)
b_q, b_s = int8_quantize_per_tensor(b)
approx = int8_matmul(a_q, a_s, b_q, b_s)
true = a @ b
print(f'INT8 矩阵乘最大误差: {(approx - true).abs().max().item():.4f}')
```

## INT4

INT4 量化把权重压到 4-bit 整数，体积是 FP16 的四分之一，能让 70B 模型跑进单张消费级显卡。它精度损失比 INT8 明显，所以几乎都要配合 GPTQ/AWQ 这类「误差补偿」或「激活感知」算法来保住质量。

```text
INT4 特点：
1. 体积 —— 0.5 字节/参数，7B 模型约 3.5GB
2. 精度 —— 裸量化损失大，需 GPTQ/AWQ 等算法补偿
3. 分组 —— group_size（如 128）越小精度越高、但开销越大
4. 硬件 —— 部分 GPU 无原生 INT4 算子，靠解包成 INT8/FP16 计算
```

```python
import torch

def int4_quantize(x, group_size=32):
    # 分组对称量化到 4-bit，返回每组的缩放因子
    qmax = 7
    x = x.float()
    n_groups = x.numel() // group_size
    scales = []
    x_q = torch.zeros_like(x)
    for g in range(n_groups):
        group = x[g * group_size:(g + 1) * group_size]
        scale = group.abs().max() / qmax
        scales.append(scale)
        x_q[g * group_size:(g + 1) * group_size] = torch.round(group / scale).clamp(-qmax, qmax)
    return x_q, torch.tensor(scales)

x = torch.randn(256) * 0.3
x_q, scales = int4_quantize(x, group_size=32)
print(f'INT4 量化，分组数 {len(scales)}，权重范围 {x_q.min().item()} ~ {x_q.max().item()}')
```

## FP8

FP8 是 8-bit 浮点格式（而非整数），有 E4M3（4 位指数 3 位尾数）和 E5M2（5 位指数 2 位尾数）两种变体。它比 INT8 有更大的动态范围，适合量化激活值（激活分布常有长尾），是 H100 等新硬件的原生支持格式。

```text
FP8 特点：
1. 浮点格式 —— 保留指数位，动态范围远大于 INT8
2. 两种变体 —— E4M3 精度高（前向权重/激活），E5M2 范围大（梯度）
3. 硬件 —— NVIDIA H100/H200 原生支持 FP8 Tensor Core
4. 混合精度 —— 常 FP8 计算 + FP16/FP32 累加，误差极小
```

```python
import torch

# PyTorch 对 FP8 的支持（torch.float8_e4m3fn）
def simulate_fp8(x):
    # 用 float8_e4m3fn 类型模拟 FP8 精度（需新版 PyTorch + 支持的硬件/模拟）
    if hasattr(torch, 'float8_e4m3fn'):
        x_fp8 = x.to(torch.float8_e4m3fn)
        return x_fp8.float()
    # 回退：手动模拟 3 位尾数舍入
    return x

x = torch.tensor([0.5, 1.0, 2.0, 0.125, 1e-4])
x_back = simulate_fp8(x)
print(f'FP8(E4M3) 模拟后: {x_back.tolist()}')
print('E4M3 可表示 [2^-6, 448] 范围，E5M2 可表示更大动态范围')
```

## Speculative Decoding

投机解码（Speculative Decoding）用一个小模型「草拟」多个候选 token，再用大模型并行「校验」这些 token，命中的直接采纳、未命中的回退重算。因为大模型校验一批 token 的耗时和生成一个 token 几乎一样，整体能获得 2-3 倍加速且不改输出分布。

```text
投机解码流程：
1. 小模型（draft）自回归生成 γ 个候选 token
2. 大模型（target）一次性前向，得到这 γ+1 个位置的概率
3. 逐位比对：draft token 概率 ≤ target 概率则接受，否则按修正分布采样
4. 接受 n 个 token 后，从未接受处继续，等价于大模型原生采样

关键：输出分布与大模型完全一致（无损加速）
```

```python
import torch

def speculative_verify(draft_tokens, target_logits, draft_logits):
    # target_logits: (seq_len, vocab)，draft_logits 同理
    accepted = []
    for i, t in enumerate(draft_tokens):
        target_p = torch.softmax(target_logits[i], -1)[t]
        draft_p = torch.softmax(draft_logits[i], -1)[t]
        # 无损拒绝采样：以 min(1, target_p/draft_p) 的概率接受
        # draft 概率不高于 target 时必接受，高于时按比例概率接受
        if torch.rand(1).item() <= target_p / draft_p:
            accepted.append(t)
        else:
            break
    return accepted

# 模拟 4 个草拟 token 的校验
draft = [10, 22, 33, 44]
target_logits = torch.randn(4, 100)
draft_logits = torch.randn(4, 100)
accepted = speculative_verify(draft, target_logits, draft_logits)
print(f'投机解码接受 {len(accepted)}/{len(draft)} 个 token')
```

## Continuous Batching

连续批处理（Continuous Batching）让多个请求共享同一批 GPU 前向计算，且允许请求「随时加入、随时退出」——某个序列生成到 EOS 就离开，腾出的位置立刻让新请求补上。相比传统「静态批处理」（等整批都结束），GPU 利用率大幅提升，是 vLLM 等引擎吞吐高的关键。

```text
连续批处理 vs 静态批处理：
1. 静态 —— 一批请求必须全部生成完才能换下一批，短请求要等长请求
2. 连续 —— 序列级的动态调度，有结束就让位，有空位就补新请求
3. 效果 —— GPU 计算单元保持满载，吞吐提升数倍
4. 挑战 —— 各序列长度不同，需要 Padding 或 Paged Attention 配合
```

```python
# 连续批处理调度逻辑示意（伪代码）
class ContinuousBatcher:
    def __init__(self, max_batch=8):
        self.max_batch = max_batch
        self.active = []    # 活跃序列

    def step(self, new_requests):
        # 先补位：有空位就加入新请求
        for req in new_requests:
            if len(self.active) < self.max_batch:
                self.active.append(req)
        # 每步各序列生成一个 token，结束的移除
        for req in self.active:
            token = req.generate_next_token()
            if token == req.eos_token:
                req.finished = True
        self.active = [r for r in self.active if not r.finished]
        return len(self.active)

batcher = ContinuousBatcher(max_batch=8)
print(f'当前活跃序列: {batcher.step(new_requests=[None]*5)}')
```

## Paged Attention

Paged Attention（分页注意力）借鉴操作系统的虚拟内存分页思想，把 KV Cache 切成固定大小的「页」，按需分配、不连续存储也能高效访问。它解决了 KV Cache 的内存碎片问题，让连续批处理能服务更多并发请求。

```text
Paged Attention 核心：
1. 分页 —— KV Cache 按固定 block 大小分页（如 16 token/页）
2. 按需分配 —— 序列变长时动态申请新页，不预留最大长度
3. 消除碎片 —— 传统预分配会导致大量内部/外部碎片，分页后浪费极少
4. 共享 —— 多请求（如 beam search、并行采样）可共享同一批前缀页

代表实现：vLLM，吞吐比 HuggingFace 默认推理高一个数量级
```

```python
# 分页 KV Cache 分配逻辑示意（伪代码）
class PagedKVCache:
    def __init__(self, block_size=16, num_blocks=256):
        self.block_size = block_size
        self.free_blocks = list(range(num_blocks))
        self.seq_blocks = {}    # seq_id -> [block_id, ...]

    def allocate(self, seq_id, n_tokens):
        n_blocks = (n_tokens + self.block_size - 1) // self.block_size
        if len(self.free_blocks) < n_blocks:
            raise MemoryError('KV Cache 页不足，触发抢占')
        blocks = [self.free_blocks.pop() for _ in range(n_blocks)]
        self.seq_blocks[seq_id] = blocks
        return blocks

    def release(self, seq_id):
        self.free_blocks.extend(self.seq_blocks.pop(seq_id))

cache = PagedKVCache(block_size=16, num_blocks=256)
blocks = cache.allocate('seq1', n_tokens=100)
print(f'序列 seq1 占用 {len(blocks)} 个页（100 token / 16 每页）')
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产环境默认用「temperature + top_p」组合，别单独用温度裸采样
2. 代码/数学/翻译等确定性任务用 Greedy 或低温度（T<0.3）
3. 创意写作/对话用 temperature 0.7-1.0 + top_p 0.9，避免重复
4. 部署先上 INT8 无损量化，显存不够再上 GPTQ/AWQ 的 INT4
5. 高并发服务优先选支持连续批处理 + Paged Attention 的引擎（vLLM/TGI）
6. 量化后必须用原任务评测集回测 perplexity/准确率，别只看体积

### 踩坑记录

```text
坑 1：Greedy 生成陷入重复循环
结论：长文本生成到一半开始反复输出同一句话。
原因：贪心每步选最大概率 token，高概率 token 互相强化形成死循环。
解法：加 temperature + top_p 采样，或对重复 n-gram 加惩罚。

坑 2：温度调太高输出乱码
结论：temperature=2.0 时输出毫无逻辑、频繁切换话题。
原因：温度过高使分布趋近均匀，token 选择变成纯随机。
解法：对话场景温度控制在 0.7-1.0，配合 top_p 双重约束。

坑 3：只量化权重没回测精度
结论：INT4 量化后体积小了，但线上任务准确率掉 5 个点。
原因：裸 INT4 量化误差大，或量化了激活导致误差累积。
解法：用 GPTQ/AWQ 补偿，量化后在真实任务集上回测。

坑 4：用静态批处理服务长尾请求
结论：一个生成 2000 token 的请求把整批短请求都拖慢。
原因：静态批处理要求整批全部结束才换批，短请求空等长请求。
解法：换支持连续批处理的引擎，序列结束即让位。

坑 5：KV Cache 预分配导致显存碎片
结论：显存没满却频繁 OOM，能服务的并发数远低于理论值。
原因：为每条序列预分配最大长度 KV Cache，浪费大量碎片空间。
解法：用 Paged Attention 按需分页分配，提升并发上限。

坑 6：投机解码用了不同 tokenizer
结论：小模型草拟的 token 和大模型 vocab 对不上，校验全失败。
原因：draft 模型和 target 模型必须共享同一套词表。
解法：确保两模型同 tokenizer，否则投机解码无法工作。
```
