## 概述

倒排索引（Inverted Index）是搜索引擎的基石数据结构：它把「文档 → 词」的正向关系反过来，建立「词 → 包含该词的文档列表」的映射。查询时不用扫描所有文档，而是直接定位到词，再取对应的文档列表求交并集，把全文检索从 O(N) 降到接近 O(查询词数)。

```text
倒排索引的核心结构：
1. Dictionary（词典）—— 所有词项的集合，提供「词 → 元数据」的映射
2. Posting List（倒排列表）—— 每个词对应的文档列表（含位置/词频等信息）
3. 正排索引 —— 补充「文档 → 字段内容」，用于相关性计算和结果展示

查询流程：
query 分词 → 查词典定位词项 → 取各自的 posting list → 求交/并集 → 打分排序
```

```python
# 倒排索引的最小实现：词 → 文档列表
def build_inverted_index(docs):
    index = {}
    for doc_id, text in docs.items():
        for word in text.split():
            index.setdefault(word, set()).add(doc_id)
    return index

docs = {
    'd1': '苹果 手机 发布',
    'd2': '小米 手机 评测',
    'd3': '苹果 电脑 评测',
}
index = build_inverted_index(docs)
print(index['苹果'])    # {'d1', 'd3'}
print(index['手机'])    # {'d1', 'd2'}
print(index['评测'])    # {'d2', 'd3'}
```

## Token

Token（词元）是倒排索引的最小索引单位，由「分词（Tokenization）+ 归一化（Normalization）」产生。英文按空格和标点切分，中文需要分词器（jieba 等）；归一化包括大小写折叠、词干提取（stemming）、词形还原（lemmatization），把「running/ran」都归一到「run」。

```text
Token 处理流水线：
1. Tokenization —— 把文本切成词元（英文按空白，中文需分词）
2. Lowercase —— Running → running
3. Stemming —— running/runs → run（词干提取，规则粗）
4. Lemmatization —— better → good（词形还原，词典准）
5. Stop Word 过滤 —— 去掉「的/了/是/a/the」等无检索价值的高频词
```

```python
import jieba

def tokenize_zh(text, stopwords=None):
    """中文分词 + 去停用词"""
    stopwords = stopwords or {'的', '了', '是', '在', '和'}
    tokens = [w for w in jieba.cut(text) if w.strip()]
    return [w for w in tokens if w not in stopwords]

def tokenize_en(text):
    """英文小写化 + 朴素切分"""
    return [w.lower().strip('.,!?') for w in text.split() if w.strip()]

print(tokenize_zh('苹果手机发布了新款产品'))
print(tokenize_en('Apple released a New iPhone!'))
```

## Dictionary

Dictionary（词典）是倒排索引中「所有词项」的集合，存储每个词到其 posting list 位置的映射。它的性能直接决定查询第一步「定位词」的快慢。常见实现是哈希表（O(1) 查找）或有序结构（支持前缀/范围查询）。

```text
Dictionary 需要存储的信息：
1. 词项本身（term）—— 字符串
2. 文档频率（DF）—— 出现该词的文档数，用于 IDF 计算
3. 指向 posting list 的指针/偏移 —— 定位倒排列表
4. 词项总数 —— 用于统计和相关性归一化

实现选择：
- 哈希表 —— O(1) 定位，但内存占用大、不支持前缀查询
- 有序数组 + 二分 —— 支持前缀/范围，查找 O(log n)
- FST/Trie —— 压缩内存，支持前缀，见后文
```

```python
class Dictionary:
    def __init__(self):
        self.term_to_meta = {}   # term -> {df, offset}

    def add(self, term, df, offset):
        self.term_to_meta[term] = {'df': df, 'offset': offset}

    def lookup(self, term):
        return self.term_to_meta.get(term)

dic = Dictionary()
dic.add('苹果', df=2, offset=0)
dic.add('手机', df=2, offset=10)
print(dic.lookup('苹果'))   # {'df': 2, 'offset': 0}
print(dic.lookup('不存在')) # None
```

## Posting List

Posting List（倒排列表/发布列表）是某个词对应的「文档列表」，每个 posting 通常记录文档 ID，以及词频（TF）、词在文档中的位置（positions，用于短语查询和 proximity）。它是倒排索引里数据量最大的部分，也是压缩和跳跃优化的重点。

```text
Posting 的结构（从简到全）：
1. 仅 docID —— 够做布尔检索
2. docID + TF —— 够算 TF-IDF/BM25
3. docID + TF + positions —— 够做短语查询、位置邻近打分

特点：
- 按 docID 升序排列（便于求交、也便于压缩差值）
- 词越常见，posting list 越长（Zipf 定律）
```

```python
# 带词频和位置的 posting list
def build_posting_with_positions(docs):
    postings = {}
    for doc_id, text in docs.items():
        for pos, word in enumerate(text.split()):
            if word not in postings:
                postings[word] = {}
            if doc_id not in postings[word]:
                postings[word][doc_id] = {'tf': 0, 'pos': []}
            postings[word][doc_id]['tf'] += 1
            postings[word][doc_id]['pos'].append(pos)
    return postings

docs = {'d1': '苹果 手机 苹果', 'd2': '小米 手机'}
p = build_posting_with_positions(docs)
print(p['苹果'])   # {'d1': {'tf': 2, 'pos': [0, 2]}}
print(p['手机'])   # {'d1': ..., 'd2': ...}
```

## Skip List

Skip List（跳表）是加在 posting list 上的「加速结构」：在长长的倒排列表里每隔一段距离放一个跳跃指针，求两个列表交集时可以直接「跳」过不可能匹配的区间，把求交复杂度从 O(m+n) 降到接近 O(m + n/skip)。

```text
跳表加速求交（AND）的原理：
1. 每隔 k 个 docID 存一个 skip pointer（记录 docID + 跳转偏移）
2. 求交时若当前 docID 小于目标，直接跳到「不超过目标」的最远跳跃点
3. 跳过大量无用的逐一比较，尤其当两个列表长度悬殊时收益巨大

代价：
- 额外的指针存储（约 1/k 的额外空间）
- 适合长列表；短列表收益不明显
```

```python
def intersect_with_skip(p1, p2, skip_every=4):
    """带跳表的列表求交（简化：用跳跃索引模拟）"""
    # 构建 p1 的跳跃索引
    skip = {}
    for i in range(0, len(p1), skip_every):
        skip[p1[i]] = i
    result, i, j = [], 0, 0
    while i < len(p1) and j < len(p2):
        if p1[i] == p2[j]:
            result.append(p1[i]); i += 1; j += 1
        elif p1[i] < p2[j]:
            # 尝试跳到不超过 p2[j] 的最远位置
            nxt = i + skip_every
            while nxt < len(p1) and p1[nxt] <= p2[j]:
                i = nxt
                nxt += skip_every
            i += 1
        else:
            j += 1
    return result

p1 = list(range(0, 100, 2))   # 偶数
p2 = [1, 3, 5, 50, 51, 98, 99]
print(intersect_with_skip(p1, p2))
```

## Segment

Segment（段）是倒排索引在磁盘上的物理分片单位，也是「不可变」的写入单元。写入时先建内存 buffer，攒到阈值就 flush 成一个不可变的 segment；查询时并行查所有 segment 再合并结果。这种「不可变段 + 增量写入」的设计让写入是顺序的、查询是并发的，是现代引擎（Lucene/Elasticsearch）的核心思想。

```text
Segment 的关键设计：
1. 不可变 —— 一旦写入就不再修改，避免锁、简化缓存
2. 增量写 —— 新文档进新 segment，更新/删除用「标记 + 合并」处理
3. 定期 Merge —— 后台把多个小 segment 合并成大 segment，减少查询扇出
4. 删除处理 —— 用删除位图（bitmap）标记，Merge 时真正物理删除

查询视角：query 会被分发到所有 segment，各自算分后做全局归并
```

```python
class Segment:
    def __init__(self, seg_id):
        self.seg_id = seg_id
        self.index = {}          # 段内的倒排索引
        self.deleted = set()     # 删除位图

    def add(self, doc_id, text):
        for w in text.split():
            self.index.setdefault(w, set()).add(doc_id)

    def delete(self, doc_id):
        self.deleted.add(doc_id)   # 标记删除，不物理移除

    def search(self, word):
        docs = self.index.get(word, set())
        return docs - self.deleted

seg = Segment(1)
seg.add('d1', '苹果 手机')
seg.add('d2', '苹果 电脑')
seg.delete('d1')
print(seg.search('苹果'))   # {'d2'} → d1 已被标记删除
```

## Compression

压缩（Compression）是倒排索引在大规模场景下的「刚需」：posting list 是索引里最占空间的部分，必须压缩才能装进内存/缓存。核心技巧是「差值编码 + 变长编码」——docID 按升序存差值（差值小），再用变长字节（Varint）或位打包（PForDelta）压缩，把大整数存成短字节。

```text
常用压缩技术：
1. Delta Encoding —— 存相邻 docID 的差值，把大数变小
2. Varint（VByte）—— 用 7bit + 1bit 延续位，小数 1 字节，大数多字节
3. PForDelta / SIMD —— 位打包 + 异常值单独存，适合 CPU 向量化
4. 词典压缩 —— FST / 前缀压缩，见下文

效果：posting list 通常能压到原始大小的 10%~20%
```

```python
def varint_encode(value):
    """Varint 编码：每字节 7bit 数据 + 1bit 延续标志"""
    out = []
    while value >= 0x80:
        out.append((value & 0x7F) | 0x80)   # 高位置 1 表示还有后续字节
        value >>= 7
    out.append(value)
    return bytes(out)

def varint_decode(data):
    value, shift = 0, 0
    for b in data:
        value |= (b & 0x7F) << shift
        if not (b & 0x80):
            break
        shift += 7
    return value

def delta_encode(doc_ids):
    """差值编码：存相邻差值，便于压缩"""
    return [doc_ids[0]] + [doc_ids[i] - doc_ids[i - 1] for i in range(1, len(doc_ids))]

doc_ids = [1000, 1003, 1005, 1010, 2000]
deltas = delta_encode(doc_ids)
print('原始:', doc_ids)
print('差值:', deltas)              # [1000, 3, 2, 5, 990] → 小数字多
print('varint(3):', varint_encode(3).hex())
print('varint(1000):', varint_encode(1000).hex())
```

## FST

FST（Finite State Transducer，有限状态转换器）是一种「带输出的」有限状态自动机，用来压缩存储词典：把大量词项共享公共前缀/后缀，节点合并成一张 DAG，同时每个词对应一个输出值（如 posting list 的偏移）。它是 Lucene 词典的核心实现，内存占用远小于哈希表。

```text
FST 与 Trie 的关系：
1. Trie —— 共享前缀的树，但节点多、内存大
2. FST —— 在 Trie 基础上做「最小化」（合并等价子结构），节点更少
3. 输出 —— 每条路径还能带一个输出值（term 的元数据/偏移）

特点：
- 内存极小 —— 词典往往比哈希表省一个数量级
- 支持前缀查询 —— 哈希表做不到
- 构建复杂 —— 需要最小化算法，但只构建一次、只读使用
```

```python
# 用第三方库简化演示 FST 的「前缀共享 + 输出」思想
# （生产用 lucene/OpenFST，这里用前缀树说明共享原理）
class TrieNode:
    def __init__(self):
        self.children = {}
        self.value = None   # 该词对应的输出值

class PrefixDict:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word, value):
        node = self.root
        for ch in word:
            node = node.children.setdefault(ch, TrieNode())  # 共享前缀
        node.value = value

    def prefix_search(self, prefix):
        node = self.root
        for ch in prefix:
            if ch not in node.children:
                return []
            node = node.children[ch]
        return self._collect(node, prefix)

    def _collect(self, node, prefix):
        out = []
        if node.value is not None:
            out.append((prefix, node.value))
        for ch, child in node.children.items():
            out.extend(self._collect(child, prefix + ch))
        return out

pd = PrefixDict()
pd.insert('苹果', 100)
pd.insert('苹果手机', 101)
pd.insert('苹果电脑', 102)
print(pd.prefix_search('苹果'))
# [('苹果', 100), ('苹果手机', 101), ('苹果电脑', 102)] → 前缀「苹果」被共享
```

## 应用场景实战

### 场景一：构建一个小型搜索引擎索引 + 布尔查询

```python
class MiniSearchIndex:
    def __init__(self):
        self.index = {}
        self.docs = {}

    def add_doc(self, doc_id, text):
        self.docs[doc_id] = text
        for w in text.split():
            self.index.setdefault(w, set()).add(doc_id)

    def search_and(self, query):
        """AND 查询：所有词都出现的文档"""
        words = query.split()
        if not words:
            return set()
        result = self.index.get(words[0], set())
        for w in words[1:]:
            result &= self.index.get(w, set())
        return result

    def search_or(self, query):
        result = set()
        for w in query.split():
            result |= self.index.get(w, set())
        return result

idx = MiniSearchIndex()
idx.add_doc('d1', '苹果 手机 发布 新 产品')
idx.add_doc('d2', '小米 手机 评测')
idx.add_doc('d3', '苹果 电脑 评测 发布')
print('AND(苹果 发布):', idx.search_and('苹果 发布'))   # d1, d3
print('OR(小米 电脑):', idx.search_or('小米 电脑'))     # d2, d3
```

### 场景二：带压缩的 docID 存储与恢复

```python
def compress_posting(doc_ids):
    """完整流程：差值 → varint → 字节流；再反向解压"""
    deltas = delta_encode(doc_ids)
    raw = b''.join(varint_encode(d) for d in deltas)
    # 解压
    decoded, i = [], 0
    while i < len(raw):
        j = i
        while raw[j] & 0x80:
            j += 1
        decoded.append(varint_decode(raw[i:j + 1]))
        i = j + 1
    # 还原差值
    restored = [decoded[0]]
    for d in decoded[1:]:
        restored.append(restored[-1] + d)
    return raw, restored

doc_ids = [1000, 1003, 1005, 1010, 2000, 2001, 5000]
compressed, restored = compress_posting(doc_ids)
print('压缩字节数:', len(compressed), '原始整数个数:', len(doc_ids))
print('还原正确:', restored == doc_ids)
```

## 最佳实践与踩坑记录

### 最佳实践

1. 词典用 FST/前缀树存，posting list 用差值 + Varint/PForDelta 压缩，二者分开优化
2. 分词后一定要做归一化（小写、词干、去停用词），否则「Apple/apple」查不到一起
3. 长 posting list 加跳表，求交性能有数量级提升，尤其布尔查询多词 AND 时
4. segment 保持不可变、定期 merge，控制 segment 数量避免查询扇出过大
5. 高频词（stop word 级）单独处理，别让它拖慢所有查询的求交
6. 中文场景分词质量直接决定索引质量，索引前先验证分词器效果

### 踩坑记录

```text
坑 1：忘了做大小写/词干归一化
结论：用户搜「Apple」查不到文档里的「apple」，召回缺失。
原因：token 阶段没有 lowercase + stemming，同一个词被当成不同词项。
解法：索引和查询用同一套归一化流水线，保证两边 token 一致。

坑 2：segment 太多导致查询变慢
结论：实时写入频繁 flush，segment 数量爆炸，每次查询扇出几百个文件。
原因：没有及时 merge，或 merge 策略太保守。
解法：定期后台 merge，限制最大 segment 数，平衡写入延迟与查询性能。

坑 3：posting list 不压缩导致内存爆掉
结论：大词表 + 长列表直接把内存打满，缓存命中率暴跌。
原因：原始 docID 用定长 int 存储，浪费大量空间。
解法：差值 + Varint/PForDelta 压缩，热列表常驻内存、冷列表落盘。

坑 4：删除文档只是标记，没真正回收
结论：删除大量文档后索引体积不降反增，查询还要过滤已删文档。
原因：删除位图 + 不可变 segment 的设计，物理删除只在 merge 时发生。
解法：定期 merge 触发真正的物理删除，回收磁盘空间。

坑 5：中文分词切错导致查不到
结论：用户搜「南京市长江大桥」切成了「南京市/长江大桥」，召回错误。
原因：分词歧义/新词未收录，分词器质量差。
解法：用 jieba/自研词典，定期补充领域新词，索引和查询同分词器。
```
