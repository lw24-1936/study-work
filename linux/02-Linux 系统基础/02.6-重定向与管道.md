## 概述

重定向和管道是 Linux 命令组合的核心，也是「Unix 哲学」——每个程序做好一件事、通过管道把小的工具组合成大的能力——的落地。重定向改的是「输入从哪来、输出到哪去」，管道把一条命令的输出直接喂给下一条命令的输入。掌握了它们，一条命令行的威力顶得上几十条分开敲。

```text
三个核心机制：
1. 标准流 —— 每个进程默认三个流：stdin(0) 输入、stdout(1) 输出、stderr(2) 错误
2. 重定向 —— 把流改到文件：> 覆盖、>> 追加、2> 错误、&> 全部
3. 管道 —— 把前一条的 stdout 接到后一条的 stdin，实现数据流水线
4. tee —— 管道三通，一份落文件一份继续传
5. xargs —— 把 stdin 转成命令行参数，喂给不读 stdin 的命令
```

## 核心概念

1. **三个标准流**：fd 0 标准输入、fd 1 标准输出、fd 2 标准错误。stdout 和 stderr 分开是刻意设计——正常结果走 stdout、报错走 stderr，重定向时能分别处理。
2. **重定向符号**：`>` 覆盖、`>>` 追加、`<` 读入、`2>` 错误流、`2>&1` 合并、`&>` 全部；`2>&1` 必须放在 `>` 之后。
3. **文件描述符表**：每个进程内核里有一张「打开文件表索引」，fd 就是这个索引的下标（0、1、2、3…）。重定向不是改命令，而是改这张表里某个下标的指向——`2>&1` 让 fd 2 指向 fd 1 此刻的同一目标。
4. **重定向顺序**：`> file 2>&1` 与 `2>&1 > file` 结果不同，因为 shell 从左到右依次执行每个重定向动作。前者两个流都进文件，后者 stderr 仍留在屏幕。
5. **exec 与自定义 fd**：`exec 3<>file` 在不启动新进程的前提下给当前 shell 打开 fd 3；`cmd >&3` 把输出写到 fd 3；`exec 3>&-` 关闭它。exec 改的 fd 会一直影响后续所有命令。
6. **noclobber 与 `>|`**：`set -o noclobber` 后 `>` 不能覆盖已存在文件，必须用 `>|` 强制覆盖；`>>` 追加不受限制。
7. **管道**：`|` 把 stdout 接到 stdin，只传 stdout（stderr 不进管道），典型链是「过滤 → 处理 → 统计 → 排序 → 取前」。
8. **管道缓冲区与背压**：管道是内核里一段有上限的内存缓冲（本机默认 16 页 = 64 KiB），写满后写端阻塞，读端消费后才继续——这叫背压（backpressure）。
9. **SIGPIPE**：读端提前退出后，写端继续写会收到 SIGPIPE（信号 13），进程默认终止，退出码 128+13=141。`yes | head -1` 就是典型。
10. **管道两侧的子 shell**：默认管道每一段都在独立子进程里执行，所以右边设置的变量传不回左边/父 shell；`shopt -s lastpipe` 可让最后一段在当前 shell 执行。
11. **匿名管道 vs 命名管道**：`|` 建的是匿名管道（无名称、只在亲缘进程间用）；`mkfifo` 建的是命名管道 FIFO（有路径名，任意进程可打开，打开时按方向阻塞）。
12. **进程替换与 /dev/fd**：`<(cmd)` 让 cmd 的输出以一个 `/dev/fd/N` 路径的形式暴露出来，可直接当文件名喂给 `diff`/`read`，本质是在幕后建了个管道。
13. **PIPESTATUS 与 pipefail**：管道整体退出码默认只看最后一条；`PIPESTATUS` 数组保存每段的真实退出码；`set -o pipefail` 让管道返回第一个失败段的退出码。
14. **tee**：管道三通，一份落文件、一份继续传，解决「既想保存又想继续处理」。
15. **缓冲**：stdio 输出到终端是行缓冲（遇换行 flush）、到文件/管道是块缓冲（攒满 4 KiB 或 8 KiB 才写），stderr 永远无缓冲——这是「输出顺序错乱」和「日志不实时」的根因。
16. **Here Document / Here String**：`<<EOF` 把多行文本当 stdin，`<<'EOF'` 禁止变量展开，`<<-EOF` 去掉行首 TAB；`<<<` 把单个字符串加换行当 stdin。
17. **xargs**：把 stdin 转成命令行参数，喂给不读 stdin 的命令（rm/mv/mkdir），含空格文件名用 -print0 + -0。

```text
重定向符号表：
1. cmd > file —— stdout 覆盖写 file
2. cmd >> file —— stdout 追加写 file
3. cmd < file —— 从 file 读入作 stdin
4. cmd 2> file —— stderr 写 file
5. cmd > file 2>&1 —— stdout 和 stderr 都进 file（顺序：先 > 再 2>&1）
6. cmd &> file —— 同上，更简写，bash 专用
```

```text
文件描述符与管道的深层要点：
1. fd 只是下标 —— 0/1/2 是约定，3 及以上可自定义；exec {fd}>file 让 bash 自动分配
2. 重定向从左到右生效 —— 顺序决定 2>&1 复制到的到底是「文件」还是「屏幕」
3. 管道有容量上限 —— 本机默认 64 KiB，写满即阻塞（背压），读端退出则写端收 SIGPIPE(13) → 141
4. 管道右侧是子 shell —— 变量改不回来；lastpipe 或进程替换可绕开
5. 退出码要显式取 —— 默认只看最后一段，PIPESTATUS / pipefail 才能看到全貌
6. 缓冲是隐形变量 —— 终端行缓冲、文件/管道块缓冲，同一程序表现不同
```

下面按「是什么 → 为什么 → 怎么用 → 边界/易错点」把每个概念展开。

### 标准输入输出错误

是什么：每个进程启动时默认打开三个文件描述符（fd）——fd 0 标准输入（stdin，读键盘）、fd 1 标准输出（stdout，写屏幕）、fd 2 标准错误（stderr，写屏幕）。为什么 stdout 和 stderr 要分开：正常结果和报错混在一起会污染数据——比如「日志统计」只想看结果，报错应该单独走；分开后才能 `> out 2> err` 各自落盘。怎么用：fd 编号就是重定向的目标，`>` 默认操作 fd 1，`2>` 操作 fd 2。

```shell
# 三个流的验证：stdout 和 stderr 各走各的
echo "这是正常输出"              # 走 fd 1 stdout
echo "这是错误输出" >&2          # 走 fd 2 stderr

# 分别重定向
ls /etc/passwd /nonexistent > out.txt 2> err.txt
# out.txt 得到 /etc/passwd（stdout），err.txt 得到 ls 的报错（stderr）

# 查看一个进程实际打开的 fd
ls -l /proc/$$/fd    # $$ 是当前 shell 的 pid，能看到 0/1/2 指向哪
```

```text
标准流要点：
1. fd 0/1/2 是约定 —— 1 和 2 都默认指向终端，所以平时 stdout 和 stderr 都显示在屏幕上
2. 分离的意义 —— 管道 | 只接 stdout，报错不混进数据流，这是「能安全组合命令」的前提
3. > 是 1> 的简写 —— cmd > f 等价 cmd 1> f，只重定向 stdout
4. 终端只是默认指向 —— fd 可被重定向到文件/管道/设备，命令自身无感知
```

### 文件描述符深入

是什么：fd 是进程打开文件表里的下标，0/1/2 只是「被约定俗成」的三个，进程完全可以使用 3、4、5…，甚至让 bash 自己挑号。为什么：`exec 3<>file` 能在不启动新进程的情况下给当前 shell 常驻一个「额外通道」，脚本里可以一边读一边写同一个文件、或把日志固定写到某个 fd，后续所有命令直接 `>&3` 复用。怎么用：`exec 3<>file` 打开、`cmd >&3` 写入、`exec 3>&-` 关闭；`{fd}` 语法让 bash 自动分配一个空闲号。

```shell
# 1) 手动指定 fd 3 打开一个「读写」文件（<> 是读写，> 只写，< 只读）
exec 3<>/tmp/rd-test/fd3.txt
echo "自定义 fd 3 写入" >&3        # 输出进 fd 3 指向的文件
ls -l /proc/$$/fd                  # 能看到 0/1/2/3 各指向哪

# 2) 关闭 fd 3
exec 3>&-
ls -l /proc/$$/fd                  # 3 消失了

# 3) bash 的 {var} 语法：让 bash 自己挑一个空闲 fd 号存进变量
exec {myfd}>/tmp/rd-test/vfd.txt
echo "分配到的 fd 号=$myfd"        # 例如 10
echo "写入变量 fd 的内容" >&$myfd
exec {myfd}>&-                     # 关闭
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ ls -l /proc/$$/fd          # 打开 fd 3、写入、再关闭前后对比

l-wx------ 1 root root 64  9月 12 11:21 1 -> pipe:[103553868]
l-wx------ 1 root root 64  9月 12 11:21 2 -> pipe:[103553868]
lrwx------ 1 root root 64  9月 12 11:21 3 -> /tmp/rd-test/fd3.txt
# —— 执行 exec 3>&- 之后 ——
总计 0
lrwx------ 1 root root 64  9月 12 11:21 0 -> /dev/null
l-wx------ 1 root root 64  9月 12 11:21 1 -> pipe:[103553868]
l-wx------ 1 root root 64  9月 12 11:21 2 -> pipe:[103553868]

$ exec {myfd}>/tmp/rd-test/vfd.txt; echo $myfd

```

注意实测里 `1` 和 `2` 都指向同一个 `pipe:[103553868]`——这是本工具把命令输出接到管道的缘故；在普通交互终端里它们指向 `pts/N`。真正要看的是「fd 号 → 目标」这张表。

```shell

```

```text
6. 每个进程的 fd 有软上限 —— ulimit -n，默认常为 1024
```

### 重定向

是什么：把进程的某个 fd 从默认的终端改指向文件（或设备/另一个 fd）。为什么：脚本自动化要保存输出、丢弃噪音、从文件喂输入，全靠重定向。怎么用：`>` 覆盖、`>>` 追加、`<` 读入、`2>` 错误、`2>&1` 复制 fd、`&>` 合并（bash 专用）；还有 Here Document `<<` 和 Here String `<<<` 喂输入。

```shell
# 覆盖 / 追加 / 输入
echo hello > log.txt          # 覆盖写
echo world >> log.txt         # 追加写
wc -l < access.log            # 从文件读入作 stdin（等价 wc -l access.log）

# 错误流单独处理
ls /ok /bad > out.txt 2> err.txt    # 正常和错误分开落盘

# 合并（两种写法）
ls /ok /bad > all.txt 2>&1          # POSIX 写法，2>&1 放 > 之后
ls /ok /bad &> all.txt              # bash 简写

# 丢弃
ls /etc > /dev/null 2>&1            # 正常和错误全进黑洞
```

```text
重定向要点：
1. > 是覆盖 —— 已有内容被清空，重要文件用 >> 或开 noclobber（见踩坑 4）
2. 2>&1 顺序敏感 —— 必须放 > file 之后，否则 stderr 复制的是「旧的」stdout（屏幕）
3. /dev/null 是黑洞 —— 写进去的数据直接丢弃，用于静默不需要的输出
4. 输入重定向少用 —— 多数命令直接收文件参数（grep x file），< 主要在 read/while 场景
```

### 管道

是什么：`|` 把前一条命令的 stdout 接到后一条命令的 stdin，形成数据处理流水线。为什么：不用落中间文件，数据流式地「过滤 → 处理 → 统计 → 排序 → 取前」，是 Unix 组合力的核心。怎么用：`cmd1 | cmd2 | cmd3`，每个环节只做一件事。边界：只传 stdout，stderr 不进管道；每段是独立子进程。

```shell
# 经典分析链：统计访问日志里出现最多的 IP
cat access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head

# 逐段解释：
# cat         输出全部日志到 stdout
# awk $1      取每行第一个字段（IP）
# sort        排序，让相同 IP 相邻
# uniq -c     统计每个 IP 出现次数
# sort -rn    按次数降序
# head        取前 10

# 把 stderr 也并入管道
ls /ok /bad 2>&1 | grep bad    # 不加 2>&1 时 stderr 直接上屏、不经过 grep
```

```text
管道要点：
1. 只传 stdout —— stderr 默认直接上屏，想进管道先 2>&1
2. 每段独立子进程 —— 变量在管道里不共享（见踩坑 5）
3. 流式处理 —— 数据边产生边传递，不用等前一条跑完，也不需要中间文件
4. 典型顺序 —— 早过滤（grep）放前面，减少下游数据量
```

### tee

是什么：管道三通，把 stdin 同时写到文件和 stdout，一份落盘、一份继续往后传。为什么：解决「既想保存中间结果、又想继续管道处理」——比「先存文件、再读文件」少一个步骤、能实时看输出。怎么用：`cmd | tee file`、`tee -a` 追加、多个文件 `tee f1 f2`。

```shell
# 边看边存
./deploy.sh | tee deploy.log          # 输出既上屏又写文件

# 落文件后继续过滤
cat access.log | tee all.log | grep 404   # all.log 存全量，继续筛 404

# 追加 + 多文件
echo "line" | tee -a history.log          # -a 追加不覆盖
df -h | tee /tmp/df.txt /tmp/df2.txt      # 同时写两个文件

# 写权限敏感文件（配合 sudo，见踩坑 3）
echo "nameserver 8.8.8.8" | sudo tee /etc/resolv.conf
```

```text
tee 要点：
1. 一份落盘一份继续 —— tee 的 stdout 可以再进下一个管道，实现「存 + 处理」双路
2. -a 追加 —— 默认覆盖，写历史记录用 -a
3. 配合 sudo —— 重定向 > 不经过 sudo（shell 处理），tee 经过 sudo，写系统文件用 sudo tee
4. 别滥用 —— 不需要留存时直接 | 传递，tee 多一次磁盘写
```

### xargs

是什么：把 stdin 转成命令行参数，喂给「不读 stdin、只收参数」的命令（rm/mv/mkdir/echo）。为什么：管道只能把数据送到下一条的 stdin，而 rm 这类命令根本不管 stdin，需要用 xargs 把 stdin 拆成参数传给它。怎么用：`find | xargs rm`，含空格文件名用 `-print0 | xargs -0`，`-n` 控制每次传几个、`-I {}` 占位、`-P` 并行。

```shell
# 基础：把文件名列表喂给 rm
find /tmp -name "*.tmp" -print0 | xargs -0 rm -f

# -n1 每次传一个参数（echo a b c 会拆成三次 echo）
echo "a b c" | xargs -n1 mkdir

# -I {} 占位符：参数放到命令中间
ls *.jpg | xargs -I {} mv {} images/

# 批量统计行数
find . -name "*.py" | xargs wc -l

# -P 并行执行（大批量操作提速）
find . -name "*.jpg" -print0 | xargs -0 -P 4 -I {} convert {} {}.png

# 空输入不执行（避免空参数报错）
find /tmp -name "*.tmp" -print0 | xargs -0 -r rm -f
```

```text
xargs 要点：
1. 目标命令不读 stdin —— 这才是用 xargs 的理由；读 stdin 的命令（grep/sort/wc）直接 | 即可
2. 默认按空白分词 —— 空格/换行都会拆，含空格文件名必须 -print0 + -0（见踩坑 2）
3. -I 与 -n 冲突 —— -I 会让 xargs 每次只传一个参数，别同时用
4. -r 防空执行 —— 输入为空时 xargs 默认还会跑一次命令，加 -r 跳过
5. -P 并行 —— 处理大量文件时并行提速，但注意目标命令是否线程安全
```

### 重定向顺序与 fd 复制

是什么：shell 对一条命令行上的重定向动作**从左到右逐个执行**，`2>&1` 不是「把 stderr 这个流接到 stdout 这个流」，而是「把 fd 2 复制（dup2）成 fd 1 此刻指向的那个目标」。为什么：只有分清「流」和「fd 当前指向」这两件事，才能解释 `> file 2>&1` 与 `2>&1 > file` 为什么写出两个完全不同的文件。怎么用：合并两流永远写 `> file 2>&1`（或 bash 的 `&> file`）；需要交换两个流时用 `3>&1 1>&2 2>&3`。

```shell
# 同一份命令、同样的两个重定向，只是换了先后顺序
ls /etc/hostname /nonexistent > order1.txt 2>&1    # 正确顺序：先 > 再 2>&1
ls /etc/hostname /nonexistent 2>&1 > order2.txt    # 错误顺序：先 2>&1 再 >
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ ls /etc/hostname /nonexistent > order1.txt 2>&1
$ ls /etc/hostname /nonexistent 2>&1 > order2.txt
$ echo "--- order1.txt = cmd > f 2>&1 ---"; cat order1.txt
--- order1.txt = cmd > f 2>&1 ---
ls: 无法访问 '/nonexistent': 没有那个文件或目录
/etc/hostname
$ echo "--- order2.txt = cmd 2>&1 > f ---"; cat order2.txt
--- order2.txt = cmd 2>&1 > f ---
/etc/hostname
# order1.txt 两个流都在（stderr 无缓冲，所以报错反而排在前面）；
# order2.txt 只有 stdout —— 报错被复制成了「屏幕上那个 stdout」，最终打到了终端，
# 所以运行第二条命令时终端上会直接看到 ls 的报错。这就是「顺序敏感」的硬证据。
```

```text
顺序敏感的逐步拆解：
1. cmd > f 2>&1  —— ① fd1 → f   ② fd2 ← 复制 fd1 的当前目标 = f      结果：两流都进 f
2. cmd 2>&1 > f  —— ① fd2 ← 复制 fd1 的当前目标（此时还是终端）② fd1 → f  结果：只有 stdout 进 f
3. cmd > f 2>&1 与 cmd &> f 等价，但 &> 是 bash 扩展，#!/bin/sh（dash）下会报语法错
4. cmd >> f 2>&1 是追加重定向的合并写法；bash 简写为 &>>
5. 简单规则 —— 想合并就在 > file 之后写 2>&1，永远别倒过来
```

```shell
# 交换 stdout 与 stderr：真正需要「复制」语义的场景要用第三个 fd 中转
cmd 3>&1 1>&2 2>&3 3>&-
# 逐段解释（从左到右执行）：
#   3>&1   把 fd3 复制成当前 fd1（真正的 stdout）
#   1>&2   把 fd1 复制成 fd2（stderr）
#   2>&3   把 fd2 复制成 fd3（保存下来的原 stdout）
#   3>&-   关闭临时中转 fd3
# 效果：原来写 stdout 的内容改走 stderr，写 stderr 的改走 stdout
# 典型用途：把命令的正常输出伪装成错误输出（只让 stderr 被上游日志系统收走）
```

```text
重定向顺序要点：
1. 从左到右执行 —— 每个重定向动作按书写顺序生效，后一个看到的 fd 状态是前面动作的结果
2. 复制的是「当前指向」—— 2>&1 复制的是执行到它那一刻 fd1 的目标，不是静态的 stdout 概念
3. 合并记忆法 —— 先开文件、再复制错误流：> file 2>&1（或 &>、&>>）
4. 交换用 fd3 中转 —— 3>&1 1>&2 2>&3 3>&-，没有第三条 fd 就换不了
5. &> / &>> / |& 都是 bash 扩展 —— 交叉引用 [[04.1-Bash 基础]]、[[04.5-输入输出重定向]]
```

### 管道机制与内核缓冲

是什么：`|` 由 shell 调用 `pipe(2)` 建立一对 fd（读端 + 写端），写端接前一条命令的 fd1，读端接后一条命令的 fd0，中间是内核里一段**没有名字的内存缓冲**。为什么：理解缓冲上限、阻塞（背压）与 SIGPIPE，才能解释「管道卡住」「日志不实时」「脚本莫名退出」这三类现象。怎么用：日常写法不变；排查时看 `/proc/<pid>/fd`（会显示 `pipe:[inode]`）、用 `strace -T -e trace=read,write` 看谁在阻塞。

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ cat /proc/sys/fs/pipe-max-size     # 单个管道可调整到的上限
1048576                              # = 1 MiB = 256 页
$ getconf PAGESIZE
4096
$ man 7 pipe | grep -A2 'Pipe capacity'
   Pipe capacity
       A  pipe  has  a  limited capacity.  If the pipe is full, then a write(2)
       pipe capacity.  Applications should not rely on a particular  capacity:
# man 7 pipe 正文口径：管道默认容量 16 页 = 65536 字节；本机页大小 4096 → 默认 64 KiB。
# 可用 fcntl(2) 的 F_SETPIPE_SZ 调大（上限就是 pipe-max-size 这个 sysctl），
# 也可以用 F_GETPIPE_SZ 读出当前值。手册明确说「应用不应依赖某个固定容量」——
# 换个内核/发行版默认值可能不同，脚本里别硬编码 64 KiB。
```

```text
管道机制的四个关键点：
1. 缓冲有上限 —— 默认 16 页（本机 64 KiB）；写端写满后 write() 阻塞，等读端消费
2. 背压（backpressure）—— 消费者慢会一路把生产者拖住，这是特性不是 bug；
   想解耦就用中间文件/消息队列，而不是无限加长管道
3. SIGPIPE —— 读端全部退出后，写端再 write() 会收到信号 13，进程默认终止，
   退出码 128+13=141；这就是 `yes | head -1` 里的 141
4. 单向 + 亲缘 —— 一条管道只能单向传；匿名管道无路径名，只能在 fork 出的亲缘进程间用
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ yes | head -1 > /dev/null; echo "PIPESTATUS=${PIPESTATUS[*]}"
PIPESTATUS=141 0
# 141 = 128 + 13(SIGPIPE)：head 拿到 1 行就退出并关闭读端，yes 继续写就被信号打死；
# 整条管道的默认退出码是 0（只看最后一段 head 成功），所以「管道成功」并不代表每一段都成功。
```

```shell
# 匿名管道 vs 命名管道 FIFO：前者没名字，后者有路径名、任意进程可打开
mkfifo /tmp/myfifo            # 创建一个命名管道（文件类型 p）
ls -l /tmp/myfifo             # 首字符 p 表示 pipe，不是普通文件
echo hello > /tmp/myfifo &    # 写端打开时会阻塞，直到有读端打开同一个 FIFO
cat /tmp/myfifo               # 读端一打开，写端解除阻塞，数据流通过后两边各自结束
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ mkfifo p1; ls -l p1
prw-r--r-- 1 root root 0  9月 12 11:32 p1
$ (echo fifo-data > p1 &); cat p1
fifo-data
# FIFO 的经典用途：不落盘地把数据从进程 A 交给无关进程 B（如把日志实时喂给分析程序），
# 代价是「打开即阻塞」——写端和读端必须成对出现，否则一方会一直等（见 Open 的阻塞语义）。
```

```shell
# 进程替换 <(cmd) >(cmd)：把命令的输出/输入伪装成一个 /dev/fd/N 路径
diff <(sort a.txt) <(sort b.txt)          # 比较两个「排序后」的流，不用临时文件
while read -r l; do echo "$l"; done < <(cat file)   # 喂 while 循环且不丢变量（见 04.6）
echo "文本" > >(cat)                       # 反向：把当前输出写进一个命令的 stdin
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ ls -l <(echo hi)
lr-x------ 1 root root 64  9月 12 11:32 /dev/fd/63 -> pipe:[103710611]
$ read line < <(echo "read-via-ps"); echo "line=[$line]"
line=[read-via-ps]
$ ls -l /dev/fd /dev/stdout /dev/stderr
lrwxrwxrwx 1 root root 13  7月 27 13:02 /dev/fd -> /proc/self/fd
lrwxrwxrwx 1 root root 15  7月 27 13:02 /dev/stderr -> /proc/self/fd/2
lrwxrwxrwx 1 root root 15  7月 27 13:02 /dev/stdout -> /proc/self/fd/1
# /dev/fd/N 就是「第 N 号 fd」的符号入口（指向 /proc/self/fd）；
# 进程替换分到的是 63 起的大号 fd，背后是一个匿名管道。
# POSIX sh（dash）不支持 <( )：换成显式 FIFO 或临时文件。
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ ( shopt -s lastpipe; echo hello | read v; echo "开了 lastpipe: v=[$v]" )
开了 lastpipe: v=[hello]
$ ( shopt -u lastpipe; echo hello | read w; echo "默认状态: w=[$w]" )
默认状态: w=[]
# 默认管道最后一段也在子进程里，read 拿到的变量随着子进程一起消失；
# shopt -s lastpipe 让最后一段在当前 shell 执行，变量就留下来了。
# 前提：当前 shell 没有开启作业控制（脚本里默认满足；交互式 shell 里 job control 是开的，
# 所以 lastpipe 主要用于脚本）。更通用的替代写法是进程替换：while read; do ...; done < <(cmd)
```

### 退出码与管道状态

是什么：管道的退出码默认取**最后一段**；每一段的真实退出码保存在 `PIPESTATUS` 数组里。为什么：只看最后一条会把中段失败完全吞掉——`grep 找不到 | sort` 看起来「成功」，实际数据早就是空的。怎么用：`set -o pipefail` 让管道返回第一个失败段的状态，或在管道后立刻读 `PIPESTATUS`。

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ false | true; echo "默认 PIPESTATUS=${PIPESTATUS[*]} rc=$?"
默认 PIPESTATUS=1 0 rc=0
$ set -o pipefail; false | true; echo "pipefail rc=$? PIPESTATUS=${PIPESTATUS[*]}"
pipefail rc=1 PIPESTATUS=1 0
# 默认 rc=0 —— 明明 false 失败了，管道却「成功」；PIPESTATUS 记录了 1 0。
# 开了 pipefail 后 rc=1 —— 返回第一个失败段（false）的退出码。
```

```text
PIPESTATUS 的用法细节：
1. 必须紧邻读取 —— 它是数组变量，下一条命令一执行就被覆盖，要先存下来：
   cmd1 | cmd2 | cmd3; rc=("${PIPESTATUS[@]}")
2. 只看某一段 —— ${PIPESTATUS[1]} 是第二段的码（数组从 0 开始）
3. lastpipe 无关 —— PIPESTATUS 在任何 shell 选项下都可用（bash 5 支持）
4. 与 $? 的关系 —— $? 等于最后一段的码；PIPESTATUS 是整条流水线的全貌
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ set -eo pipefail; yes | head -1 >/dev/null; echo "reached"
（没有任何输出，脚本在 yes | head 之后直接退出）
# 经典坑：yes 被 SIGPIPE 打断返回 141 → pipefail 让整条管道返回 141 → set -e 立即终止脚本。
# 表现是「只是 head 提前关掉管道，脚本却莫名其妙退出」，且不打印任何错误。
# 三种解法：
#   1) 末尾兜底：yes | head -1 >/dev/null || true
#   2) 明确接受 SIGPIPE：yes | head -1 >/dev/null; [ ${PIPESTATUS[0]} -eq 141 ] || exit 1
#   3) 这类场景干脆不开 pipefail（只在真正需要「中段失败要暴露」的脚本里开）
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ time ( sleep 1 | sleep 3 )        # time 关键字作用于整条管道
real    0m3.001s
user    0m0.001s
sys     0m0.001s
$ { time sleep 1; } | sleep 3       # 只给第一段计时
real    0m1.001s
user    0m0.000s
sys     0m0.001s
# 陷阱：bash 的 time 关键字加在管道上是「给整条管道计时」，
# 想只量其中一段必须把 time 包进单条命令：{ time cmd; } | other 或 cmd | time other。
# 另外 time 的输出走 stderr，写进日志时要 2>> 单独收，别污染数据流。
```

```text
退出码要点：
1. 默认只看最后一段 —— 管道「成功」不等于每段都成功
2. PIPESTATUS 要立刻存 —— 读之前别插别的命令
3. pipefail 是脚本级开关 —— 写脚本头部 set -euo pipefail 是有代价的，要懂 141 的存在
4. set -e 会因管道中段的 SIGPIPE 误伤 —— 141 不等于业务失败，不要盲目当成错误处理
5. time 与管道 —— 关键字 time 计整条管道，精确到段要用 { time ...; }
```

### tee 深入

是什么：tee 是「管道三通」——把 stdin 复制到每个文件参数，同时原样写到 stdout。为什么：既要留档又要继续处理时，它比「先落盘再读回来」少一次读、并且能实时看到进度。怎么用：`tee file`（覆盖）、`tee -a file`（追加）、`tee f1 f2`（多路）、`tee /dev/stderr`（回显到错误流）、`tee >(gzip > x.gz)`（写到子进程管道）。

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ printf 'l1\nl2\n' | tee /dev/stderr > /dev/null
l1
l2                        # 数据被 tee 送到 fd2 上，所以终端仍能看到，同时不影响管道往下传
$ echo "l3" | tee t1.txt t2.txt >/dev/null; wc -l t1.txt t2.txt
1 t1.txt
1 t2.txt                  # 一个 -a/多文件：一次写成两份
$ printf 'AAAAAAAAAAAAAAAAAAAA\nBBBBBBBBBB\n' | tee >(gzip > out.gz) | wc -l
2                         # 主流水线照常统计行数
$ zcat out.gz
AAAAAAAAAAAAAAAAAAAA
BBBBBBBBBB               # 旁路进程同时拿到了原始字节并压缩落盘
```

```text
写系统文件为什么必须 sudo tee：
1. 管道 `|` 和重定向 `>` 都是当前 shell 的动作 —— 打开文件的权限来自当前用户，不是 sudo
2. `echo x | sudo tee /etc/f` —— sudo 启动的是 tee 进程，tee 自己以 root 调 open(/etc/f) → 成功
3. `sudo echo x > /etc/f` —— `>` 由当前（非 root）shell 打开文件 → EACCES（Permission denied）
4. 等价替代 —— `sudo sh -c 'echo x > /etc/f'`，让 root shell 去执行整条命令（含重定向）
5. 追加同理 —— `echo x | sudo tee -a /etc/f`
```

```shell
# tee 的实用组合
cmd | tee checkpoint.txt | wc -l          # 中间落盘：下游崩了还能从 checkpoint 续跑
./deploy.sh 2>&1 | tee -a deploy.log      # 部署脚本：屏幕看进度 + 日志留全量（含报错）
cmd | tee >(gzip > out.gz) > /dev/null    # 压缩落盘但不落明文（旁路进程替换）
echo "warn" | tee /dev/stderr >/dev/null  # 只往 stderr 发一行，不污染 stdout 数据
```

```text
tee 的边界与替代品（本机实测 command -v 结果）：
1. sponge（moreutils）—— 本机未安装（MISSING）：它能「读完全部 stdin 再写目标文件」，
   解决 `sort f > f` 把源文件清空的问题；装了 moreutils 后可用 `sort f | sponge f`
2. pv —— 本机未安装（MISSING）：管道可视化进度条（`cat big.log | pv | gzip > x.gz`）
3. unbuffer（expect 包）—— 本机未安装（MISSING）：给下游造一个伪 tty 以触发行缓冲
4. script —— 本机已安装（/usr/bin/script）：`script -qc "cmd" /dev/null` 也能造伪 tty
5. stdbuf —— 本机已安装（/usr/bin/stdbuf）：调下游的 stdio 缓冲模式（-oL 行缓冲、-o0 无缓冲）
6. tee 的代价 —— 多一次写入 + 一次上下文切换；不需要留档时别加 tee
```

### 缓冲与实时输出

是什么：C 库（glibc）的 stdio 会根据「输出目标是不是终端」自动选择缓冲策略——**tty → 行缓冲**（遇到换行就 flush），**文件/管道 → 块缓冲**（攒满 4 KiB 或 8 KiB 才写，或程序退出时 flush），**stderr 永远无缓冲**。为什么：这是「同一命令在终端里实时、重定向到文件后却半天不吐字」「日志时间戳错乱」的根本原因，跟管道本身无关。怎么用：下游加 `--line-buffered`（grep/sed 都支持）、或前置 `stdbuf -oL`/`stdbuf -o0`，Python 用 `-u`。

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）——间隔 1 秒输出两行
$ ( printf 'a\n'; sleep 1; printf 'b\n' ) | grep 'a\|b' | while read l; do echo "$(date +%S)s $l"; done
18s a
18s b            ← 非 tty，grep 走块缓冲：两行攒到一起，退出时才一次性吐给下游
$ ( printf 'a\n'; sleep 1; printf 'b\n' ) | grep --line-buffered 'a\|b' | while read l; do echo "$(date +%S)s $l"; done
18s a
19s b            ← 加了 --line-buffered，逐行实时到达（时间戳差 1 秒）
# 结论：缓冲差异不是管道的锅，是下游进程的 stdio 策略；数据一模一样，到达节奏不同。
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ awk 'BEGIN{print "1"; system("sleep 1"); print "2"}' | while read l; do echo "$(date +%S)s $l"; done
59s 1
00s 2
$ stdbuf -o0 awk '<同一段脚本>' | while read l; do echo "$(date +%S)s $l"; done
00s 1
01s 2
# gawk 在调用 system() 前会 flush，所以这个例子两种写法都是「逐行」看到；
# 但用 stdbuf -o0 可以强制任何下游程序逐字节写出，是排查「日志不实时」的标准手段。
```

```text
处理缓冲问题的全套手段：
1. --line-buffered —— grep/sed 的专属开关，最省事（只对这两个命令有效）
2. stdbuf -oL / -o0 —— 用 LD_PRELOAD 改下游的 stdio 模式，对大多数 C 程序有效
   （-i 输入、-o 输出、-e 错误；-oL 行缓冲、-o0 无缓冲）
3. python3 -u —— Python 解释器层禁用 stdout/stderr 缓冲（等价 PYTHONUNBUFFERED=1）
4. unbuffer / script -qc —— 给下游造一个伪 tty，骗它走行缓冲（本机 unbuffer 未装，script 已装）
5. 程序内自己 flush —— awk 里 fflush() 或 fflush(stdout)；C 里 setvbuf()/fflush()
6. 无法改下游时 —— 上游用 `while read` 逐行转发，或干脆换掉缓冲策略差的工具
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）——tail -f 跟的是 inode 不是路径
$ printf 'l1\n' > rot.log; tail -f rot.log > tail.out & sleep 0.5
$ mv rot.log rot.log.1; printf 'l2-new-file\n' > rot.log     # 模拟 logrotate
$ kill %1; cat tail.out
l1                  ← 新文件里的 l2-new-file 完全没被看到
# tail -f 打开的是旧的 inode，文件被改名/新建后它还在跟那个旧 inode；
# 日志轮转场景要用 tail -F（--follow=name --retry）或 tail -f 配合无 copytruncate 的轮转策略
# （见 [[13.2-日志轮转与集中]]）。
```

```text
缓冲要点：
1. tty 与非 tty 两套策略 —— 终端行缓冲、文件/管道块缓冲，同一程序表现不同
2. stderr 不缓冲 —— 这也是「报错总比正常输出先出现」的原因
3. 排查顺序 —— 先怀疑下游缓冲，再怀疑管道/磁盘/网络
4. 实时性方案按性价比排 —— --line-buffered > stdbuf -o0 > -u > unbuffer/script
5. tail -f 跟 inode，tail -F 跟文件名 —— 日志轮转后者的行为才符合预期
```

### Here Document 与 Here String 深入

是什么：`<<EOF ... EOF` 是 here document——把中间多行文本当成命令的 stdin；`<<<` 是 here string——把单个字符串（**自动补一个换行**）喂给标准输入。为什么：脚本里要喂多行配置、SQL、JSON 时，比 `echo -e`、`printf` 拼接清晰得多。怎么用：`<<EOF`（展开变量/命令替换/算术）、`<<'EOF'`（原样，一个字都不解释）、`<<-EOF`（去掉每行行首的 TAB）。

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ X=WORLD
$ cat <<EOF
> hello $X      <- 未加引号
> EOF
hello WORLD      <- 变量被展开
$ cat <<'EOF'
> hello $X      <- 加了引号
> EOF
hello $X         <- 原样输出，变量不展开
# <<\EOF、<<"EOF" 与 <<'EOF' 等价，都是「禁止一切展开」；写配置文件时优先加引号。
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ cat <<-EOF
> 	前导 TAB 被吃掉（<<- 独有）
> 		两层 TAB 也只剩一层
> 	EOF
前导 TAB 被吃掉（<<- 独有）
两层 TAB 也只剩一层
# <<- 只去掉「行首的 TAB」，不去空格！
$ printf 'no-tab\n\twith-tab\n' | sed 's/^/[/;s/$/]/'

[\twith-tab]      ← 通过管道（而不是 heredoc）过来的 TAB 原样保留
# 所以 <<- 只解决「缩进用了 TAB」的脚本，用空格缩进的脚本仍会带着空格进 stdin。
```

```text
heredoc / here string 要点：
1. 引号决定展开 —— 无引号展开变量/命令/算术，加引号一律原样（写配置优先加引号）
2. <<- 只吃 TAB —— 行首空格不受影响，用空格缩进的脚本别指望它
3. <<< 补换行 —— 按字节统计会多 1，read/命令解析依赖这个换行
4. 结合重定向 —— `cmd <<EOF > out` 与 `> out` 在前效果一样，但推荐把重定向写在 heredoc 之前更易读
5. 可移植性 —— heredoc 是 POSIX 标准语法，dash/POSIX sh 都支持；`<<<` 和 `<()` 是 bash 扩展
6. 嵌套 heredoc —— heredoc 内部再出现 EOF 时用不同的定界符（如 SQL_END），避免提前结束
```

## 工作原理

进程默认继承三个文件描述符 0/1/2，指向终端。重定向的本质是内核在启动命令前，把这三个 fd 重新指向目标文件（覆盖或追加打开），命令自身无感知、还是往 fd 1 写。管道则是内核在两条命令之间建一个内存缓冲，前一条的 fd 1 接到缓冲的写端、后一条的 fd 0 接到读端，数据流式通过、无需落盘的中间文件。理解「fd 重指向」这个本质，2>&1 这类写法的含义就清楚了。

```text
底层机制：
重定向 = 启动命令前把 fd 0/1/2 重新指向文件（命令无感知）
管道 = 内核建内存缓冲，前条 fd1 → 写端，后条 fd0 ← 读端，流式传递不落盘
2>&1 = 把 fd2 复制成 fd1 当前指向（所以顺序重要）
```

重定向是 shell 处理的，不是命令处理的：`>` `<` `|` 这些符号由 shell 解析后，在启动命令前就改好了 fd，命令自己根本看不到这些符号。这也是「管道 + sudo」出问题的根源——`echo x > /etc/f` 时，`>` 的写文件动作由普通用户的 shell 执行，sudo 只作用在 echo 上，写文件还是没权限。

```text
执行顺序与作用域：
1. shell 解析命令行 → 发现重定向/管道 → 先设置好 fd → 再 fork 子进程执行命令
2. 管道每段是独立子进程 —— 变量、cd、环境变量改动都不影响父 shell
3. > file 由当前 shell 的权限打开 —— 不是命令的权限，这是 sudo 重定向失败的根因
4. 缓冲差异 —— stdout 到终端是行缓冲、到文件/管道是块缓冲，这也是「输出顺序错乱」的来源
```

把这两句话拆到系统调用层面，就能看清 shell 到底做了什么：

```text
重定向的内核链路（以 cmd > file 为例）：
1. shell 解析命令行，识别出 `>` 记号 —— 这一步只是「语法分析」，还没动任何文件
2. fork 出子进程（这就是「重定向由 shell 完成」的含义：打开文件的是子进程，不是 cmd）
3. 子进程调 open("file", O_WRONLY|O_CREAT|O_TRUNC, 0666) 拿到一个新 fd（比如 3）
   —— `>>` 换成 O_APPEND（不截断），`<` 换成 O_RDONLY（不创建）
   —— 权限位还要过一遍 umask，最终权限 = 0666 & ~umask
4. 调 dup2(3, 1) 把这个 fd 复制到 1 号下标上，然后 close(3)
   —— `2>&1` 就是 dup2(1, 2)；`n>&-` 就是 close(n)
5. exec 目标命令 —— 命令一开始运行，fd 1 已经指向文件了，它对「重定向」一无所知
6. 关键推论 —— 打开文件发生在 exec 之前、用的还是 shell 进程的权限与 umask，
   所以「sudo 命令 > 文件」必然失败，而失败时机是在命令启动之前
```

```text
管道的内核链路（cmd1 | cmd2）：
1. shell 调 pipe(2)，拿到一对 fd：fd[0] 读端、fd[1] 写端（内核里是一个 pipe_inode_info + 环形缓冲）
2. fork 出 cmd1：dup2(写端, 1) 让它的 stdout 进管道，随后关掉手上多余的读端
3. fork 出 cmd2：dup2(读端, 0) 让它的 stdin 来自管道，随后关掉多余的写端
4. 所有写端都关闭后，读端的 read() 返回 0（EOF）—— 这就是下游命令知道「上游结束了」的方式
5. 所有读端都关闭后，写端的 write() 触发 SIGPIPE(13) —— 这就是 `yes | head` 的 141
6. 管道不在任何真实文件系统上（pipefs 是内核伪文件系统），所以 ls 只能看到 `pipe:[inode]`，
   /proc/<pid>/fd 里显示的也是这个形式；它没有路径名，无法跨无亲缘关系的进程传递
7. 管道是单向字节流 —— 没有消息边界，「一行」是下游程序自己按 \n 切出来的概念
```

```text
为什么 shell 内置命令也要 fork（管道场景）：
1. 管道每段必须是独立进程才可能并行 —— 否则前一条没跑完后一条没法开始
2. 因此 `echo x | read v` 里的 read（bash 内建）也在子进程里执行，变量自然丢了
3. 唯一的例外是 shopt -s lastpipe：让最后一段不 fork，回到当前 shell 执行
4. 同类陷阱还有 `cd /x | ...`、`exit | ...` —— 内建命令在管道里对父 shell 没有任何副作用
```

## 配置文件解析

```text
shell 选项（影响重定向/管道行为，写在 ~/.bashrc 或脚本头）：
set -o noclobber    # 禁止 > 覆盖已存在的文件（要覆盖用 >| ）
set -o pipefail     # 管道任一命令失败即整个管道返回失败（默认只看最后一条）
shopt -s nullglob   # 无匹配时通配符展开为空，而不是保留字面 *.txt
```

```text
/bin/sh 指向的 shell 两系不同（Red Hat 系差异，bashism 可移植性）：
1. Ubuntu/Debian —— /bin/sh 是 dash（POSIX 最小实现，快但功能少）
2. Red Hat/CentOS/Rocky —— /bin/sh 是 bash（symlink 到 bash）
3. 影响 —— &>、<<<（Here String）、进程替换 <( ) 都是 bash 扩展（bashism），dash 不支持
4. 结论 —— 脚本用到这些语法时，Ubuntu 上必须写 #!/bin/bash 而非 #!/bin/sh，否则报语法错误；写可移植脚本用 POSIX 语法，或显式声明 #!/bin/bash
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ ls -l /bin/sh
lrwxrwxrwx 1 root root 4  3月 31  2024 /bin/sh -> dash
$ echo "$BASH_VERSION"
5.2.21(1)-release
# 本机（Ubuntu 24.04.4）的 /bin/sh 指向 dash；同一个脚本写成 #!/bin/sh 就跑在 dash 上，
# 写成 #!/bin/bash 才跑在 bash 5.2.21 上。这是「同一份脚本换个发行版就报语法错误」的根源。
```

```text
bashism 在 dash 上的表现（示例，非本机实测代码片段）：
| 写法              | bash | dash | 报错信息形态                            |
|-------------------|------|------|-----------------------------------------|
| cmd &> file       | 支持 | 失败 | Syntax error: "&" unexpected            |
| cmd >& file       | 支持 | 失败 | 同上（dash 只认 >file 2>&1）            |
| cmd |& cmd2       | 支持 | 失败 | 语法错误                                |
| read x <<< "abc"  | 支持 | 失败 | Syntax error: redirection unexpected    |
| diff <(a) <(b)    | 支持 | 失败 | Syntax error: "(" unexpected            |
| `[[ $a == $b ]]`  | 支持 | 失败 | command not found: [[                    |
| for i in {1..3}   | 支持 | 失败 | 字面量 {1..3} 被当成一个词（不报错但结果错） |
| arr=(a b c)       | 支持 | 失败 | Syntax error: "(" unexpected            |
| $'\n' 转义        | 支持 | 失败 | 字面量 $'\n'（不报错但结果错）           |
| local x=1         | 支持 | 支持 | ——（dash 也实现了 local）                |
| echo -e "\n"      | 支持 | 部分 | dash 的 echo 不认 -e，会原样打印 -e      |
```

```text
POSIX 模式与其它「sh 兼容」注意点：
1. bash --posix / set -o posix —— 让 bash 尽量贴 POSIX 行为，但仍然是 bash，
   不会退化成 dash；用它做兼容性自测比换 shell 更省事
2. dash 比 bash 快 —— 启动快、内存小，所以 Debian 系把 /bin/sh 指向它，
   系统启动脚本（/etc/init.d 等）用 dash 跑更利索
3. 可移植写法 —— 需要 bashism 就用 #!/usr/bin/env bash；要写「哪都能跑」的脚本，
   就只用 POSIX 语法（反引号之外用 $( )，合并流用 >file 2>&1，禁 `<<<`、`<()`、`[[ ]]`）
4. 想严格验证 —— 用 shellcheck（-s sh）静态扫一遍，或直接 dash -n script.sh 做语法检查
5. 交叉引用 —— 变量、条件、数组这些语法差异详见 [[04.1-Bash 基础]]，重定向的高级用法见 [[04.5-输入输出重定向]]
```


## 性能与调优

```text
管道/重定向性能注意：
1. 管道代替临时文件 —— 流式处理省磁盘 IO 和中间文件，大日志分析别先落盘再读
2. 早过滤早收敛 —— 管道里 grep 放前面，减少下游 awk/sort 处理的数据量
3. head 提前终止 —— sort | head 时 sort 会因 SIGPIPE 提前停，大数据量下收益明显
4. 少用无谓的 cat —— cat file | grep x 直接 grep x file，少一个进程一次管道
5. tee 别滥用 —— 不需要留存时别 tee，直接管道传递更快
6. xargs -P 并行 —— 大批量独立操作（图片转换、压缩）用 -P 多进程提速，注意目标命令线程安全
```

```text
两个容易忽略的性能细节：
1. 无谓的 cat（UUOC）—— cat file | grep x 会多启动一个 cat 进程、多一次管道拷贝，grep x file 直接读文件更快
2. sort | head 的 SIGPIPE —— head 拿到足够行数就退出，sort 写满管道缓冲后收到 SIGPIPE 停止，大数据量下能省掉完整排序
```

```text
# 实测输出（Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）——20 MB / 408163 行日志

# 不留清理负担」；只有在冷缓存或中间文件大到要写盘时，省下的那次完整回写才会显出 IO 差异。

$ time ( cat big.log | wc -l )
408163

$ time ( wc -l < big.log )
408163

# UUOC（无谓的 cat）：0.009s vs 0.004s —— 多一个进程、多一次管道拷贝，代价约翻倍。
```

```text
#   "xargs: 警告：选项 --max-args 和 --replace/-I/-i 互斥，已忽略之前的 --max-args 值"
# 想按个数分批只给 -n，想用占位符替换只给 -I，两者别同时写。
```

```text
性能要点补充：
1. 冷缓存才是管道的分水岭 —— page cache 命中时管道与中间文件基本打平（实测 0.139 vs 0.122s）
2. UUOC 有实测代价 —— cat f | wc -l 比 wc -l < f 慢约一倍（0.009 vs 0.004s）
3. 并行是最大的杠杆 —— xargs -P 在本机把 8 个 sleep 1 从 8.0s 压到 1.0s
4. -n 与 -I 互斥 —— 同时用会出警告且 -n 被忽略，二选一
5. pv 未安装 —— 本机 command -v pv 为空；要进度条需 apt install pv
6. 缓冲大小可由应用调 —— fcntl(F_SETPIPE_SZ) 可把管道缓冲调到最大 pipe-max-size（本机 1 MiB），
   但盲目调大会让「生产者跑太快、内存被吃掉」，一般交给内核默认值即可
```

## 安全与权限

```text
重定向/管道安全要点：
1. noclobber 防误覆盖 —— set -o noclobber 禁止 > 覆盖已有文件，防手滑清掉配置
2. 管道 + sudo —— echo x > /etc/f 用普通用户会失败，要 echo x | sudo tee /etc/f
3. 别把密码重定向进日志 —— 命令输出含凭据时注意落盘位置，防泄露
4. /dev/null 丢弃敏感输出 —— 不需要的报错/敏感信息进 /dev/null，别写进日志文件
5. 管道读不到变量 —— 管道各段独立子进程，变量作用域不共享，别依赖管道传变量
6. 重定向到敏感文件注意权限 —— > 写文件时别把机密内容写成 644，必要时 umask 077 或写后 chmod 600
```

```text
安全清单补充（重定向/管道视角）：
1. HISTIGNORE / HISTCONTROL —— 别让含密钥的命令落进 ~/.bash_history
   export HISTIGNORE='*token*:*password*:*secret*'
   export HISTCONTROL=ignorespace    # 以空格开头的命令不入历史

   · 服务端返回 502 页/HTML 错误页 → shell 把 HTML 当命令执行，报错但可能已半执行
   · 无法审计与回滚 → 出问题查不到「当时跑的是哪一版」

6. 日志注入 —— 用户可控内容被写进日志又用 grep/awk 解析时，注意换行/控制字符注入，
   必要时用 printf '%q' 转义或 tr -d '\r' 清洗
7. FIFO 权限 —— mkfifo 默认受 umask 影响；放在世界可写的 /tmp 下要防他人抢读，
```

```text
sudo tee 的权限链路（再强调一次，考试与踩坑高频）：
1. `echo x | sudo tee /etc/f` —— 管道由当前 shell 建立（无需权限），
   sudo 以 root 启动 tee，tee 自己 open("/etc/f", O_WRONLY|O_CREAT|O_TRUNC) → 成功

4. 需要 root 写多行时更稳的写法：sudo tee -a file <<'EOF' ... EOF
```

## 故障排查

```shell
# 1. 错误信息没进文件（2>&1 放错位置）
cmd > file 2>&1        # 正确：先 > 再 2>&1
# 检查顺序：cmd 2>&1 > file 是错的（stderr 还指向屏幕）

# 2. xargs 文件名被拆断
find . -print0 | xargs -0 <cmd>    # 用 NUL 分隔符处理空格文件名

# 3. 管道后段拿不到变量
echo $VAR | cmd        # 变量在管道外展开，不是传值
# 需要传值用：cmd <<< "$VAR" 或 echo "$VAR" | cmd

# 4. 管道命令失败但脚本没停
set -o pipefail        # 让管道失败能传播，配合 set -e 生效
```

```shell
# 5. 「cannot overwrite existing file」—— 开了 noclobber
set -o noclobber && echo x > exist.txt   # 报错，用 >| 强制覆盖

# 6. 输出顺序错乱 —— stdout 和 stderr 混合写文件时顺序不稳定

# 需要严格顺序时分开落盘再合并，或用 stdbuf 调缓冲

# 7. 管道中断「Broken pipe」—— 下游提前退出，上游还在写
yes | head -1          # head 拿到 1 行就退，yes 收到 SIGPIPE 报 Broken pipe（正常现象）
```

```shell
# 8. 脚本「莫名其妙」退出，且不打印任何错误 —— 多半是 pipefail + SIGPIPE(141)

# 实测复现：set -eo pipefail; yes | head -1 >/dev/null; echo reached  → 不会输出 reached
# 定位：set -o pipefail 打开后，管道中任何一段非零（含 141）都会让整条管道失败，set -e 随即退出
# 修复：给这类管道加 `|| true`，或判断 ${PIPESTATUS[0]} -eq 141 视为正常
```

```shell
# 9. 管道「卡住不返回」—— 上游在等一个永远不来的读端

echo hi > /tmp/f1         # 卡死在这（没有读者）——这是 FIFO 的语义，不是 bug
# 排查手段：
#   ps -ef | grep -E 'cat|tee|fifo'      # 看是谁停在那里
#   ls -l /proc/<pid>/fd                 # 看它打开的是 pipe:[...] 还是 fifo 路径

# 修复：保证读写两端都存在；或用 `exec 3<>/tmp/f1` 先把读写端一起打开，避免阻塞
```

## 常见问题

```text
Q1: 2>&1 和 &> 的区别？
A: 功能一样（合并 stdout 和 stderr），&> 是 bash 简写；2>&1 是 POSIX 写法、注意放 > 之后。

Q2: 管道传的是 stdout 还是 stderr？
A: 只传 stdout。想让 stderr 也进管道，先 2>&1 合并再传。

Q3: 什么时候用 tee？
A: 既要保存输出又要继续管道处理时（cmd | tee file | grep x），比「先存再重读」高效。

Q4: xargs 是干嘛的？
A: 把 stdin 转成命令行参数，喂给不读 stdin 的命令（rm/mv/mkdir）。

Q5: 为什么管道里的变量不共享？
A: 管道每段是独立子进程，变量作用域隔离。变量要在管道外设置或显式传值。

Q6: echo x > /etc/f 为什么权限不够，加了 sudo 也不行？
A: > 重定向由当前 shell（普通用户）执行，sudo 只作用在 echo 上。要用 echo x | sudo tee /etc/f，让 tee 在 sudo 权限下写文件。

Q7: xargs 和管道直接传有什么区别？
A: 管道把数据送到下一条的 stdin，xargs 把 stdin 拆成命令行参数传给命令。读 stdin 的命令（grep/sort）直接 | 即可，只收参数的命令（rm/mv）用 xargs。

Q8: 怎么让管道中间任一命令失败就整体失败？
A: set -o pipefail，配合 set -e 使用，管道返回非零退出码，脚本据此中止。

Q9: PIPESTATUS 和 $? 有什么区别？
A: $? 只反映管道最后一段的退出码；PIPESTATUS 是数组，按顺序保存每一段的退出码。它必须紧挨着管道读取，下一条命令执行后就被覆盖，所以要先存下来：cmd1 | cmd2; rc=("${PIPESTATUS[@]}")。

Q10: 为什么 `yes | head -1` 的结果里有 141？
A: head 拿够行数就退出并关闭读端，yes 继续 write 时收到 SIGPIPE（信号 13），128+13=141。这是管道的正常终止路径，不是错误；但开了 pipefail 后它会让整条管道「失败」。

Q11: 管道有缓冲区吗？写满了会怎样？
A: 有。内核 pipe 默认 16 页（本机页 4096 → 64 KiB），上限由 /proc/sys/fs/pipe-max-size 限制（本机 1048576 = 1 MiB），可用 fcntl 的 F_SETPIPE_SZ 调整。写满后写端 write() 阻塞，等读端消费——这就是背压（backpressure）。

Q12: 为什么重定向到文件后输出不实时了，屏幕上却正常？
A: glibc 的 stdio 会根据目标是不是 tty 切换缓冲：tty 行缓冲、文件/管道块缓冲（攒满约 4 KiB 或退出才写），stderr 永不缓冲。解决办法：grep/sed 加 --line-buffered，其他程序用 stdbuf -oL/-o0，Python 用 -u，或拿 script/unbuffer 造一个伪 tty。

Q13: 匿名管道和 FIFO 有什么区别？
A: 匿名管道（`|`）没有路径名、只在有亲缘关系的进程间传递；FIFO（mkfifo）是有路径名的文件（类型 p），任意进程都能打开，但 open 时会阻塞直到对端出现。

Q14: `<<'EOF'` 和 `<<EOF` 有什么区别？`<<-` 呢？
A: 加引号（或 <<\EOF）禁止一切展开，内容原样进 stdin；不加引号会展开 $VAR、$(cmd) 和算术。`<<-` 额外去掉每行行首的 TAB（只去 TAB，不去空格）。
```

## 面试题

```text
1. 三个标准文件描述符是什么？
   答：fd 0 stdin 标准输入、fd 1 stdout 标准输出、fd 2 stderr 标准错误，默认都指向终端。

2. 2>&1 为什么要放在 > 之后？
   答：2>&1 是把 stderr 复制成 stdout「当前」的指向。放在 > 之前时 stdout 还指向屏幕，stderr 也复制成屏幕，就没进文件。

3. 重定向和管道的本质区别？
   答：重定向把流改到文件，管道把一条命令的 stdout 接到另一条的 stdin（内存缓冲，不落盘）。

4. 怎么处理含空格文件名的批量操作？
   答：find -print0 | xargs -0，用 NUL 字符作分隔符，避免空格被拆断。

5. 如何让管道中任一命令失败就整体失败？
   答：set -o pipefail（配合 set -e），管道返回非零，脚本可据此中止。

6. 为什么 echo x > /etc/f 加 sudo 也写不进去？
   答：> 重定向由当前 shell（非 sudo）打开文件，sudo 只作用于 echo。正确写法 echo x | sudo tee /etc/f。

7. tee 和普通重定向的区别？
   答：tee 把 stdin 同时写到文件和 stdout（一份落盘一份继续传），普通重定向只能把输出指向一个目标。写系统文件时 tee 还能配合 sudo。

8. 解释 `cmd > file 2>&1` 与 `cmd 2>&1 > file` 的结果差异，内核层面发生了什么？
   答：重定向从左到右执行。第一种：先 open(file) 并把 fd1 指向它，再 dup2(1,2) 让 fd2 也指向 file → 两流都进文件。第二种：先 dup2(1,2)（此时 fd1 还指向终端），fd2 复制成终端，然后 fd1 才指向 file → file 里只有 stdout，stderr 打在屏幕上。

9. 怎么交换命令的 stdout 和 stderr？
   答：需要第三个 fd 中转：`cmd 3>&1 1>&2 2>&3 3>&-`。先把原 stdout 存到 fd3，再把 fd1 指向 stderr，把 fd2 指向保存下来的原 stdout，最后关闭 fd3。

10. PIPESTATUS 怎么用？为什么「读一次就没了」？
   答：它是数组变量，保存上一次管道每段的退出码；shell 执行下一条命令时该变量会被重新赋值，所以必须在管道之后立刻读取或先存起来（rc=("${PIPESTATUS[@]}")）。单看 $? 只知道最后一段的结果。

11. `set -e` 和 `pipefail` 一起用有什么坑？举一个真实例子。
   答：管道中段因 SIGPIPE 退出（退出码 141）会被 pipefail 判定为失败，set -e 随即终止脚本且不打印错误。例：`set -eo pipefail; yes | head -1 >/dev/null; echo reached` 不会输出 reached。解决办法是给这类管道加 `|| true`、显式判断 ${PIPESTATUS[0]} -eq 141，或不在这种脚本里开 pipefail。

12. `time cmd1 | cmd2` 计时的到底是谁？
   答：bash 的 time 关键字作用于整条管道，量到的是两段的总耗时（实测 sleep 1 | sleep 3 得到 3.001s）。只想量其中一段要包成单条命令：`{ time cmd1; } | cmd2` 得到 1.001s。time 的输出走 stderr。

13. 管道缓冲区有多大？写满会怎样？怎么查看和调整？
   答：默认 16 页（本机 4096B/页 → 64 KiB）。写满后写端 write() 阻塞等读端消费（背压）。上限由 /proc/sys/fs/pipe-max-size 给出（本机 1048576），可用 fcntl 的 F_SETPIPE_SZ/F_GETPIPE_SZ 调整；man 7 pipe 明确说应用不应依赖某个固定容量。

14. 为什么 `sudo echo x > /etc/f` 也写不进去？给出三种正确写法。
   答：`>` 由当前（非 root）shell 在 exec 之前完成 open()，sudo 只作用于 echo。正确写法：① `echo x | sudo tee /etc/f`；② `sudo sh -c 'echo x > /etc/f'`；③ 用具有写权限的编辑器/工具（如 sudoedit）或 `sudo tee -a` 追加。

15. `echo hello | read v` 为什么读不到 v？三种解法？
   答：管道每段都在子进程里执行，read 设置的变量随子进程结束消失。解法：① `shopt -s lastpipe` 让最后一段在当前 shell 执行；② 用进程替换 `read v < <(echo hello)`；③ 避免管道，用 here string `read v <<< "hello"`。

16. 什么情况下 `tail -f` 会「失灵」？怎么解决？
   答：日志被轮转（mv 后新建同名文件）时，tail -f 跟的是旧 inode，看不到新文件内容（本机实测：轮转后新写入的 l2-new-file 完全没被捕获）。解决：改用 tail -F（--follow=name --retry），或让 logrotate 用 copytruncate（inode 不变，但有丢日志窗口）。参见 [[13.2-日志轮转与集中]]。

17. 同一份脚本在 RHEL 上能跑、在 Ubuntu 上报语法错误，为什么？怎么写出两边都能跑的脚本？
   答：RHEL 的 /bin/sh 是 bash，Ubuntu 的 /bin/sh 是 dash（本机实测 /bin/sh -> dash，bash 版本 5.2.21）。&>、|&、`<<<`、`<()`、`[[ ]]`、数组、(()) 都是 bash 扩展，dash 会直接语法报错。要么把 shebang 写成 #!/usr/bin/env bash，要么只用 POSIX 语法（>file 2>&1 合并、[ ] 判断、避免数组），并用 shellcheck -s sh 或 dash -n 验证。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 分析日志用管道链一次性完成过滤/统计/排序，别存一堆中间文件
2. 既要保存又要继续处理时用 tee，比「先存再重读」高效
3. 脚本里静默不需要的输出用 > /dev/null 2>&1，需要留痕的用 >> 追加日志
4. find/xargs 处理文件名统一用 -print0 + xargs -0，防空格断词
5. 错误和正常输出分开落文件（> out 2> err），排查时能直接看到报错
6. 脚本头部开 set -euo pipefail，防管道中段失败静默吞掉
7. 写系统文件用 sudo tee，别用 sudo + > 重定向
8. 需要引用同一份输出两次时用 tee（或进程替换 tee >(cmd)），避免重复执行昂贵的上游命令
9. 管道链末尾留一个能反映真实结果的判断：`cmd | grep -q x` 时别忘了读 PIPESTATUS 或开 pipefail
10. 脚本头部按需开 set -euo pipefail，但要清楚 SIGPIPE(141) 会被当成失败而误伤脚本
11. 面向人的输出走 stderr、面向数据/下游的输出走 stdout，让管道和日志分流更自然
12. 长时间运行的脚本写日志时优先用逐行 flush 的方式（--line-buffered / stdbuf -oL / -u），否则重定向后就失去实时性
13. 需要写临时文件时用 mktemp 生成唯一路径并 trap 清理，不要用固定的 /tmp/xxx（防抢占与并发冲突）

### 踩坑记录

```text
坑 1：2>&1 放错位置导致错误没合并
结论：cmd 2>&1 > file 写出的文件里没有错误信息。
原因：2>&1 必须在 > file 之后，否则 stderr 先指向了旧的 stdout（屏幕）。
解法：正确顺序 cmd > file 2>&1，或直接用 cmd &> file。

坑 2：xargs 处理带空格的文件名断错
结论：find | xargs rm 遇到 "my file.txt" 被拆成两个参数。
原因：xargs 默认按空白分词，空格文件名被拆断。
解法：find -print0 | xargs -0，用 NUL 分隔符。

坑 3：管道里加 sudo 无效
结论：echo x | sudo tee file 不行，sudo 不在管道起点。
原因：管道只重定向 stdin，sudo 需要作用在写文件的命令上。
解法：用 sudo tee（echo x | sudo tee /etc/file），或 sudo sh -c '...'。

坑 4：用 > 覆盖了重要文件
结论：echo x > config.txt 把原配置覆盖了。
原因：> 是覆盖写，没有提示。
解法：重要文件用 >> 追加，或设置 noclobber（set -o noclobber 禁止覆盖）。

坑 5：管道里的命令读不到环境变量/变量不共享
结论：管道后段拿不到前段设置的变量。
原因：管道每段是独立子进程，变量作用域不共享。
解法：变量在管道外设置，或用子 shell 显式传值。

坑 6：xargs 输入为空时命令仍执行一次
结论：find 没匹配到文件时，xargs 还是跑了一次目标命令（可能带空参数报错）。
原因：xargs 默认在输入为空时也会执行一次命令。
解法：加 -r 参数（xargs -0 -r rm），输入为空直接跳过。

坑 7：管道输出顺序错乱
结论：cmd > file 2>&1 后，文件里 stdout 和 stderr 的顺序和屏幕上看到的不一致。
原因：重定向到文件是块缓冲、到终端是行缓冲，两个流合并后顺序不稳定。
解法：需要严格顺序时分开落盘（> out 2> err）再按需合并，或用 stdbuf -oL 调行缓冲。
```

```text
坑 8：set -e 配 pipefail，脚本因 SIGPIPE 静默退出
结论：脚本执行到 `yes | head -1 >/dev/null` 之后直接结束，不打印任何错误信息。
原因：head 提前关闭读端，yes 收到 SIGPIPE(13) 退出码 141；pipefail 把 141 当作管道失败，set -e 立即终止脚本。
解法：给这类管道加 `|| true`；或显式判断 ${PIPESTATUS[0]} -eq 141 视为正常；或这种脚本不开 pipefail。

坑 9：`sort f > f` 把源文件清空，结果什么都没了
结论：`sort data.txt > data.txt` 之后 data.txt 被清空（只剩空结果）。
原因：shell 在启动 sort 之前就以 O_TRUNC 打开了同一个文件，sort 读到的是刚被清空的内容。
解法：用 `sort -o data.txt data.txt`；或用 sponge（moreutils，本机未安装）；或先写临时文件再 mv 覆盖。

坑 10：重定向到文件后输出不再实时刷新
结论：`./task.sh > run.log` 后 tail -f run.log 半天没内容，脚本结束才一次性出现。
原因：stdout 指向非 tty 时走块缓冲（攒满约 4 KiB 或进程退出才写），而 stderr 无缓冲所以报错照常实时。
解法：程序侧加 --line-buffered、stdbuf -oL、python3 -u；或让脚本自己 fflush；排查手段见「故障排查 10」。

坑 11：日志轮转后 tail -f 看不到新内容
结论：mv 旧日志、新建同名文件后，tail -f 仍只跟被改名前的旧 inode（实测新写入的行完全不出现）。
原因：tail -f 按文件描述符（inode）跟随，不会按路径名重新打开文件。
解法：换成 tail -F（--follow=name --retry）；或让 logrotate 用 copytruncate（inode 不变，但有丢日志窗口）。

坑 12：FIFO 没有对端时一打开就挂住
结论：`echo hi > /tmp/f1`（没有任何读者）会一直卡住，脚本看起来像死锁。
原因：以只写方式 open FIFO 会阻塞，直到有进程以读方式打开它（反之亦然）。
解法：保证读写两端同时存在；或先用 `exec 3<>/tmp/f1` 同时持有读写端避免阻塞；排查用 timeout + ps 看停在哪个进程。

坑 13：heredoc 不加引号，变量被提前展开写进配置文件
结论：`cat <<EOF > /etc/app/conf` 里的 $DB_PASSWORD 被替换成明文写盘，未定义变量还会被 set -u 直接打断。
原因：无引号的 heredoc 会做变量、命令替换和算术展开，$ 不再字面保留。
解法：写配置一律用 `<<'EOF'`；确需替换的关键值用模板 + envsubst，并把生成的文件 chmod 600。

坑 14：exec 打开的 fd 忘了关，脚本跑久后报 Too many open files
结论：循环里反复 `exec 3>file` 而不关闭，fd 号一路涨到 ulimit -n（本机 1024）后 open 失败。
原因：exec 打开的是当前 shell 的 fd，不显式关闭就一直占用，而且会被后续子进程继承。
解法：配套写关闭语句（exec 3>&-）；或统一用 exec {var}>file 自动挑号再关闭；用 ls -l /proc/$$/fd 或 lsof -p $$ 排查泄漏。

坑 15：重定向新建的文件是 644，机密内容裸奔
结论：`echo "token=..." > secret.conf` 建出来的是 644，同机其他用户可直接读取。
原因：创建模式是 0666 再按 umask（常见 022）掩掉，得到 644，与内容敏感度无关。
解法：先 umask 077 再写，或写后 chmod 600；长期方案是把凭据放进专门的凭据文件/密钥管理，而不是随手重定向到普通文件。
```
