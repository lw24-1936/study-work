## 概述

FHS（Filesystem Hierarchy Standard，文件系统层级标准）规定了 Linux 根目录下每个目录该放什么，让不同发行版、不同程序的作者都能按约定找到文件。它的核心是「按用途分区，而不是按程序分区」——配置文件统一进 /etc、可变数据统一进 /var、可执行文件统一进 /usr。记住这张目录地图，排查「文件找不到、磁盘满了、程序装哪了」时就有了方向。

```text
FHS 三大分区逻辑：
1. 静态 vs 可变 —— /usr 存静态程序、/var 存运行时变化的数据（日志/缓存）
2. 共享 vs 独立 —— /usr 可跨机共享、/etc /var 是每台机器独立的本机配置
3. 真实 vs 虚拟 —— 普通目录落磁盘，/proc /sys /dev /run 是内核生成的内存文件系统
```

## 核心概念

1. **根目录职责**：/bin /sbin /lib 存基础命令和库（已合并到 /usr），/etc 存配置，/usr 存程序，/var 存可变数据（日志/缓存/数据库/队列），/home 存用户数据，/opt 存第三方独立软件，/boot 存内核引导文件。
2. **usr merge**：现代发行版把 /bin、/sbin、/lib 软链合并到 /usr 下，写脚本时 /usr/bin/xxx 和 /bin/xxx 等价。
3. **四个伪文件系统**：/proc /sys /dev /run 是内核在内存里动态生成的，不占磁盘、不能当普通文件编辑，但读它们能拿到 CPU/内存/进程/设备的一切运行信息。
4. **/etc 的定位**：系统级与软件级的配置都住这里（nginx、ssh、systemd），改配置先备份——它是「还原一台机器」最关键的目录之一。
5. **/usr 的定位**：只读的程序与共享数据，分 /usr/bin（命令）、/usr/lib（库）、/usr/share（架构无关数据）、/usr/local（手工编译安装）。生产/容器常只读挂载。
6. **/var 的定位**：可变数据聚集地——/var/log 日志、/var/cache 缓存、/var/lib 数据库、/var/spool 队列。磁盘告警第一眼先看它。
7. **/dev 的设备节点**：不是普通文件，是「设备入口」，每个节点由主设备号（major）和次设备号（minor）标识，内核靠这对数字路由到对应驱动。
8. **/run 与 /var/run**：/run 是 tmpfs（内存文件系统），放 PID 文件、socket、锁文件，重启自动清空；/var/run 在多数发行版是 /run 的软链。
9. **tmpfs 家族**：/run /dev/shm /tmp（部分发行版）都是 tmpfs——数据在内存 + swap 支撑，重启即失。/run 放运行时状态、/dev/shm 放 POSIX 共享内存、/tmp 放临时文件，三者定位和挂载参数不同。
10. **/usr/local vs /opt vs /srv**：都是「非包管理器」的地盘，但分工不同——/usr/local 放源码手工编译、/opt 放自包含第三方商业软件、/srv 放服务对外提供的数据，选错会让卸载/备份一团乱。
11. **/boot 与 EFI**：UEFI 启动的机器 /boot 下多一个 /boot/efi（ESP 分区，FAT32），放 EFI 引导程序；传统 BIOS 没有它。
12. **发行版差异**：Red Hat 系默认文件系统是 XFS（Debian 系默认 ext4）、有 /etc/sysconfig/ 目录（Debian 系没有），这些差异影响分区规划和管理习惯。
13. **FHS 标准的现状**：FHS（Filesystem Hierarchy Standard）由 Linux Foundation 维护，3.0 版（2015-05）之后基本停更，配套的 LSB 已废弃；现代 systemd 系统的事实标准补充是 file-hierarchy(7)，本机 `man 7 hier` 可读。
14. **XDG Base Directory**：用户级数据的新约定——配置进 ~/.config、数据进 ~/.local/share、状态进 ~/.local/state、缓存进 ~/.cache，系统级配置进 /etc/xdg；现代应用不再把 dotfile 撒在 $HOME 根下、也不再往 /etc 写用户数据。
15. **/etc 的细节**：/etc/skel 是新用户模板、/etc/alternatives 是 update-alternatives 软链、/etc/ld.so.conf.d + ldconfig 管动态库、/etc/localtime 是时区软链、/etc/default（Debian）与 /etc/sysconfig（RHEL）是服务参数、/etc/profile.d 是全局环境变量、/etc/systemd 放单元。
16. **/usr 的细节**：/usr/local 是手工编译的「小 /usr」（bin/sbin/lib/share/man/etc/src）、/usr/libexec 放内部可执行文件、/usr/lib64 是 64 位历史遗留、/usr/share 放 doc/man/locale 等架构无关数据、/usr/games 基本空置。
17. **持久化设备命名**：/dev/disk/by-uuid、by-label、by-partuuid、by-id、by-path 与 /dev/mapper（LVM/dm-crypt）让设备路径稳定；fstab 必须用 UUID/标签而不是 /dev/sda2（内核探测顺序会变）。
18. **安全挂载选项**：nosuid,nodev,noexec 缩小可写分区的攻击面，常用于 /tmp、/var/tmp、/home 与数据盘；副作用是 /tmp noexec 会让部分安装器/脚本失败。/boot 建议 ro,nosuid,nodev。
19. **systemd 挂载单元**：/etc/fstab 由 systemd-fstab-generator 转成 .mount 单元；.automount 与 x-systemd.automount 实现按需挂载，nofail、x-systemd.device-timeout 控制设备缺失时的行为；mount --bind 与容器 --rbind 是挂载空间的基础。
20. **只读根与 overlay**：overlayfs 把只读 lowerdir 与可写 upperdir 叠成 merged 视图，是容器镜像分层与容器 rootfs 的底层（本机 df 可见 /var/lib/docker/rootfs/overlayfs/<id>）；overlayroot 让根只读、写操作进临时层，加固设备常用。

```text
FHS 与 hier(7)/file-hierarchy(7) 的关系（标准自身已停更，要知道替代规范）：
1. FHS —— Filesystem Hierarchy Standard，3.0 版 2015-05 发布后基本停更；配套的 LSB（Linux Standard Base）已废弃，不再出新版
2. hier(7) —— 手册页，发行版对目录布局的约定，内容与 FHS 大体一致（本机 `man 7 hier` 可读）
3. file-hierarchy(7) —— systemd 提供的现代目录规范，细化了 FHS 没说清的部分：/run 运行时状态、
   /var/lib 持久化状态、~/.config（XDG）、/usr 只读、/etc 机器本地配置、/var/tmp 跨重启保留
4. 三者关系 —— FHS 给「大类约定」，hier(7) 给「本机实际布局」，file-hierarchy(7) 给「systemd 时代
   的运行时/用户级位置」，写文档或脚本时以 file-hierarchy(7) 为现代依据
```

```text
XDG Base Directory（用户级数据约定，取代往 /etc 和 $HOME 乱丢文件）：
1. $XDG_CONFIG_HOME（默认 ~/.config）—— 用户级配置，等价于「用户自己的 /etc」
2. $XDG_DATA_HOME（默认 ~/.local/share）—— 用户级数据（应用数据、字体、.desktop 文件）
3. $XDG_STATE_HOME（默认 ~/.local/state）—— 会话状态（历史、最近文件、用户日志），较新的规范
4. $XDG_CACHE_HOME（默认 ~/.cache）—— 可随时删除的缓存，丢了不影响功能
5. $XDG_DATA_DIRS（默认 /usr/local/share:/usr/share）—— 系统级数据目录搜索路径
6. $XDG_CONFIG_DIRS（默认 /etc/xdg）—— 系统级配置目录，/etc/xdg 是 XDG 版的「系统 /etc」
7. 为什么 —— 应用不再把 dotfile 撒在家目录根下，备份/迁移只需拷 ~/.config 与 ~/.local；
   用户配置也不需要 root 权限写 /etc，避免多用户机器上互相污染
```

```text
/etc 内的关键子项（本机实测）：
1. /etc/skel —— 新建用户时拷进家目录的模板，本机含 3 个文件：.bash_logout(220B)、
   .bashrc(3771B)、.profile(807B)；`useradd -m` 时复制进去
2. /etc/alternatives —— update-alternatives 生成的软链，本机实测：awk -> /usr/bin/mawk、
   arptables -> /usr/sbin/arptables-nft；改默认版本用 `update-alternatives --config awk`
3. /etc/ld.so.conf.d/ —— 动态库搜索路径片段，改完执行 ldconfig 重建缓存（/etc/ld.so.cache）
4. /etc/localtime —— 指向 /usr/share/zoneinfo/<区域> 的软链，改时区 = 换这条链
   （或 `timedatectl set-timezone Asia/Shanghai`）
5. /etc/default/ —— Debian 系服务参数（/etc/default/grub、/etc/default/ssh 等）；
   RHEL 系对应 /etc/sysconfig/（含 network-scripts/ 传统网卡配置）
6. /etc/profile.d/*.sh —— 登录 shell 加载的全局环境变量片段（PATH、别名、提示符）
7. /etc/systemd/ —— systemd 配置根：system/ 系统单元、user/ 用户单元、journald.conf、resolved.conf
8. /etc/xdg/ —— XDG 规范的系统级配置目录（与 /etc 的关系类似 ~/.config 与 $HOME）
```

```text
/usr 内部结构（本机 `ls /usr` 实测：bin games include lib lib64 libexec local sbin share src）：
1. /usr/local —— 手工编译安装的「小 /usr」：bin/ sbin/ lib/ share/ man/ etc/ src/ include/ games/；
   本机实测含上述子目录 + 用户放置的 jdk tar 包（不进包管理器数据库，卸载要自己删）
2. /usr/libexec —— 不供用户直接调用、只被其它程序调用的内部可执行文件（如 sshd 的 helper）
3. /usr/lib64 —— 64 位系统上的库目录（或指向 /usr/lib 的软链），历史遗留的 32/64 位分离
4. /usr/share —— 架构无关的共享数据：/usr/share/doc（文档）、man（手册页）、locale（本地化）、
   licenses、icons、zoneinfo（时区库）、applications（.desktop 入口）
5. /usr/games —— FHS 定义的游戏目录，现代发行版保留但基本空置
6. 只读性 —— /usr 不含任何运行时可变数据，生产/容器可 ro 挂载，升级用整目录原子切换
```

```text
持久化设备命名（为什么 /etc/fstab 不能写 /dev/sda2）：
1. /dev/disk/by-uuid/<UUID> —— 按文件系统 UUID；本机实测：93b40af2-6f5d-40e1-b057-593b6b7c7428 → ../../sda2
   （根分区）、2CA5-0507 → ../../sda1（ESP vfat）、EA4A-CF42 → ../../sdb1、50D27469D27454E6 → sdb3（NTFS）
2. /dev/disk/by-label/<标签> —— 按文件系统 label（e2label/xfs_admin 设置），可读性好但可能重名
3. /dev/disk/by-partuuid/<UUID> —— 按 GPT 分区 UUID（分区表级，与文件系统 UUID 不同）
4. /dev/disk/by-id/<厂商_序列号> —— 按硬盘序列号，扩容/热插拔/多盘机器最稳
5. /dev/disk/by-path/ —— 按物理链路（形如 pci-0000:00:17.0-ata-1），换线即变，少用
6. /dev/mapper/<名称> —— LVM 逻辑卷与 dm-crypt 的设备路径（如 /dev/mapper/ubuntu--vg-root）
7. 本机 /etc/fstab 真实写法：用的是 UUID 路径而不是设备名——
   /dev/disk/by-uuid/93b40af2-6f5d-40e1-b057-593b6b7c7428 /        ext4    defaults 0 1
   /dev/disk/by-uuid/2CA5-0507                          /boot/efi vfat    defaults 0 1
   /swap.img                                            none      swap    sw       0 0
   理由：/dev/sda2 这种名字由内核探测顺序决定，加盘/换口/加 NVMe 后可能变成 sdb2，
   写死会挂载错盘甚至起不来；UUID 跟文件系统走，认盘不认位置
```

```text
安全挂载选项实践（缩小可写分区的攻击面）：
1. nosuid —— 忽略分区上的 setuid/setgid 位，防用户可写的分区里藏提权程序
2. nodev —— 忽略分区上的设备节点，防在 /tmp 里造 /dev/sda 直接读裸盘
3. noexec —— 禁止在该分区执行程序（可执行映射/脚本启动被拒），防 tmp 目录当跳板
4. 典型组合 —— 数据/临时分区挂 nosuid,nodev,noexec；本机 /run 正是 rw,nosuid,nodev,noexec
   （`findmnt -t tmpfs` 实测 /run 带 size=2017064k,mode=755）
5. 副作用 —— /tmp 加 noexec 会让部分安装器、自解压安装包、pip/conda 的临时二进制、
   某些 CI 工具报「Permission denied」；加之前先评估业务，或给它们留一个关闭 noexec 的临时目录
6. /boot 建议 ro,nosuid,nodev —— 引导文件平时不需要写，只读挂载防篡改（升内核时临时 remount rw）
7. 继承 —— fstab 的第 4 字段直接写这些选项；systemd 挂载单元里 Options= 同样生效
```

```text
systemd 挂载单元（.mount / .automount，现代挂载的编排方式）：
1. .mount —— 一个挂载点对应一个 .mount 单元，文件名 = 路径转义（/ 变 -）：/mnt/data → mnt-data.mount，
   `systemctl start mnt-data.mount` 即挂载、`systemctl status` 看状态
2. systemd-fstab-generator —— 开机时读 /etc/fstab 自动生成 .mount/.swap 单元，
   fstab 与 systemd 是同一套系统；改完 fstab 执行 `systemctl daemon-reload`
3. .automount —— 按需挂载：访问挂载点目录时才真正 mount，闲置超时自动卸载
4. fstab 加 x-systemd.automount —— 给该行开启按需挂载（等价于配 .automount 单元），
   开机不再等这块盘，首次访问才挂
5. x-systemd.device-timeout=5s —— 设置等设备超时（默认 90s），磁盘没接时别拖慢启动
6. nofail —— 设备不存在也不报错、不阻塞启动（U 盘/外置盘写进 fstab 必备）
7. x-systemd.requires= / x-systemd.after= —— 声明依赖顺序（如等网络、等某个逻辑卷就绪）
8. mount --bind —— 把一个目录挂到另一个位置（同内容两个入口）；容器用 --rbind 递归 bind
   （把 / 整棵树连同子挂载点搬进容器），这是容器挂载命名空间的基础
```

```text
只读根与 overlay 分层（容器与嵌入式/加固系统的根文件系统做法）：
1. overlayfs 原理 —— 把 lowerdir（只读层）+ upperdir（可写层）叠成 merged 视图，
   改写落 upper、未改动文件走 lower；这就是 Docker 镜像分层与容器可写层的底层机制
2. 本机实证 —— root 分区上有多个 overlay 挂载点 /var/lib/docker/rootfs/overlayfs/<id>
   （df 实测可见），即容器 rootfs 用 overlayfs 叠在 /var/lib/docker 之上
3. overlayroot —— Ubuntu 的只读根方案：根以 ro 挂载、全部写操作进 tmpfs 或 overlay 上层，
   加固设备/自助终端用，重启即还原
4. 只读根的意义 —— 系统分区不可改 = 被入侵难持久化、掉电不易损坏文件系统
5. 代价 —— 系统更新需临时 remount rw 或整目录原子切换（ostree / A-B 双分区）
6. 容器镜像 —— 镜像各层是只读 lower，容器运行时加可写 upper；`docker diff` 看的就是 upper 的改动
```

```text
/tmp 与 /var/tmp 的清理策略（systemd-tmpfiles）：
1. /usr/lib/tmpfiles.d/tmp.conf —— 发行版默认：/tmp 10 天未访问删除、/var/tmp 30 天未访问删除
   （本机 /usr/lib/tmpfiles.d/ 实测含 00rsyslog.conf、apport.conf、cron-daemon-common.conf、
   dbus.conf、debian.conf、home.conf 等片段）
2. /etc/tmpfiles.d/ —— 本地覆盖目录，同名文件优先级高于 /usr/lib/tmpfiles.d，把默认规则拷来改即可
3. 语法 —— 形如 `d /run/lock 0775 root root 10d`：类型 / 路径 / 权限 / 属主 / 属组 / 存活期
4. 生效 —— systemd-tmpfiles --clean 执行清理，开机由 systemd-tmpfiles-clean.timer 触发
5. /tmp vs /var/tmp —— /tmp 重启即清（部分发行版是 tmpfs），/var/tmp 要求跨重启存活、保留更久（30 天）
6. 为什么区别对待 —— 应用把「需要跨重启的临时状态」放 /var/tmp、「随时可丢」的放 /tmp
```

```text
/proc 与 /sys 精选入口（排查时的高频文件）：
1. /proc/self —— 指向当前进程自己的目录；脚本里 readlink /proc/self 能拿到自己的 PID 上下文
2. /proc/<PID>/cwd —— 进程当前工作目录（软链，readlink 查看）
3. /proc/<PID>/exe —— 进程可执行文件；二进制被删后可 `cp /proc/<PID>/exe /tmp/recover` 抢救
4. /proc/<PID>/fd/ —— 进程打开的文件描述符，用来找进程占着哪个日志文件或哪个已删除文件
5. /proc/mounts —— 内核视角的当前挂载表；/etc/mtab 现在多半是 /proc/self/mounts 的软链或由工具合成
6. /sys/class/net —— 按类别列网卡（eth0/enp0s3 等）；/sys/class/block 列块设备
7. /sys/devices —— 完整设备树（按物理拓扑组织），排查设备归属时用
8. /sys/firmware/efi/efivars —— EFI 变量（本机以 efivarfs 挂载，df 实测 384K），
   内含 Secure Boot 与启动项相关信息
```

```text
容器镜像里的 FHS 差异（照搬发行版目录约定会踩空）：
1. Alpine —— musl libc + BusyBox：/bin /sbin /lib 未 usr-merge 且大量是 busybox 符号链接，
   没有 glibc 路径；用它当基础镜像，编译产物要静态链接或装 gcompat 兼容层
2. scratch —— 空镜像：连 /bin/sh、/etc、/lib 都不存在，只能塞静态编译的单一二进制
3. distroless —— 只保留应用运行所需的库与 ca-certificates，没有 shell、没有包管理器，
   调试只能靠拷贝静态 busybox 或开 ephemeral container
4. 后果 —— 依赖「/etc/passwd 存在」「有 /bin/bash」「手册在 /usr/share/man」的脚本在这些镜像里直接失败；
   镜像内不是完整 FHS，只是「所需子集 + 应用目录」
5. 实践 —— 写 Dockerfile 时别假设 shell 的存在与 FHS 完整，用绝对路径 + 显式声明依赖
```

```text
tmpfs 深入（本机 `findmnt -t tmpfs` 实测参数）：
1. /run —— rw,nosuid,nodev,noexec,size=2017064k,mode=755,inode64（约 1.9G 上限、禁止执行）
2. /dev/shm —— rw,nosuid,nodev,inode64（约 9.6G，POSIX 共享内存，权限 1777）
3. /run/lock —— rw,nosuid,nodev,noexec,size=5120k（仅 5M，放锁文件）
4. /run/user/1000 —— size=2017060k,nr_inodes=504265,mode=700,uid=1000,gid=1000（每个登录用户一个，
   属主独占，放用户级 socket/运行时文件）
5. size= 是上限不是已用 —— tmpfs 用多少算多少，不够会换到 swap（本机 swap 8G）
6. /dev/shm 与 docker --shm-size —— 容器默认共享宿主 /dev/shm（或限 64M），PostgreSQL/Chromium
   等用共享内存的程序常因 /dev/shm 太小而 OOM，需 `docker run --shm-size=1g`
```

```text
磁盘与目录规划实践（把 FHS 落到分区上）：
1. /var 单独分区 —— 日志/数据库/容器数据会撑爆根分区，/var 独立可防「日志写满导致系统起不来」
2. /var/lib/docker 单独大磁盘 —— 容器镜像与卷是磁盘大户，生产单独挂 SSD 并配 data-root
3. /usr 只读挂载 —— 生产可把 /usr 挂 ro，升级走原子切换，杜绝随手改系统文件
4. /home 加密 —— LUKS 或 fscrypt 加密家目录，笔记本丢失不泄数据
5. 预留 —— XFS 不能缩小，规划 /var /home 尺寸要留余量；ext4 可 resize2fs 缩容
6. 本机对照 —— df -h 实测 /dev/sda2 915G（已用 82G，10%）、/boot/efi 1.1G（已用 6.2M）；
   df -i 实测 inodes 60981248 已用 1397376（3%）——大分区别只盯空间，也要看 inode 余量
```

```text
根目录职责表：
1. /bin  —— 基本命令（ls/cp/mv），已合并到 /usr/bin
2. /sbin —— 系统管理命令（fdisk/ifconfig），已合并到 /usr/sbin
3. /etc  —— 系统与软件的配置文件（/etc/nginx、/etc/ssh）
4. /usr  —— 用户程序与只读数据（/usr/bin、/usr/lib、/usr/share、/usr/local 手工安装）
5. /var  —— 可变数据（/var/log 日志、/var/cache 缓存、/var/lib 数据库、/var/spool 队列）
6. /home —— 普通用户主目录，/root 是 root 用户主目录
7. /tmp  —— 临时文件，所有人可写，重启可能被清空
8. /opt  —— 第三方独立软件（/opt/xxx 整个应用装一个目录）
9. /lib  —— 共享库（libc 等），已合并到 /usr/lib
10. /boot —— 内核与引导文件（vmlinuz、initramfs、grub）
11. /mnt /media —— 临时挂载点 / 可移动介质挂载点
```

```text
四个伪文件系统：
1. /proc —— 进程与内核信息，/proc/cpuinfo 内存 cpuinfo、/proc/meminfo 内存、/proc/<pid>/ 每个进程的目录
2. /sys  —— 内核对象模型（sysfs），设备/驱动/总线/电源，/sys/class/net 看网卡
3. /dev  —— 设备文件入口，/dev/sda 磁盘、/dev/null 黑洞、/dev/zero、/dev/random
4. /run  —— 运行时数据（tmpfs，重启清空），PID 文件、socket 文件、/run/lock
```

```text
目录该放什么不该放什么（易错边界）：
1. /usr —— 只放「包管理器管的程序」，手工编译放 /usr/local，别污染包管理器领地
2. /var —— 只放「运行时变化的数据」，程序本体别放这（要放 /usr 或 /opt）
3. /tmp —— 只放「临时文件」，重要数据别放（可能被清）；持久化数据放 /home 或 /var
4. /opt —— 只放「自包含的第三方整包应用」，配置/日志仍建议外放 /etc、/var/log 遵守 FHS
5. /etc —— 只放「配置」，别放可执行文件和数据
```

```text
usr merge 的历史与现状（为什么 /bin /sbin /lib 全并进了 /usr）：
1. 由来 —— 早期磁盘小、/usr 常单独挂载，所以把「挂载 /usr 之前就得用的命令」单独放 /bin /sbin /lib，
   「装到 /usr 之后的程序」放 /usr/bin /usr/sbin /usr/lib，一套系统两套命令目录。
2. 合并 —— 2011-2012 年 Fedora 15/17 率先把 /bin /sbin /lib 软链到 /usr，Debian 8（Jessie，2015）、
   Ubuntu 16.04 跟进，之后所有主流发行版默认 usr merge。
3. 为什么 —— 消除「同一个命令两个位置」的混乱（/bin/sh 和 /usr/bin/sh 到底哪个是真的）；现代 initramfs
   启动早期就能挂载 /usr，不再需要单独保留 /bin 那一套。
4. 现状 —— /bin → usr/bin、/sbin → usr/sbin、/lib → usr/lib 都是软链，写脚本两条路径等价。
5. 分区影响 —— 合并后 /usr 必须和 / 在同一文件系统（以前 initramfs 只挂 / 和 /bin，/usr 可晚挂或独立分区；
   现代启动流程假定 /usr 启动早期即可用，单独分区/单独挂载容易起不来）。
```

```text
/usr/local vs /opt vs /srv 选型对比表（非包管理器软件的三个落脚点）：
目录        定位                    适用场景                         组织结构
/usr/local  源码手工编译安装        自己 make install 的程序         按 /usr 结构（bin/lib/share）
/opt        自包含第三方商业软件     Chrome/NVIDIA/Oracle 整包        /opt/<厂商>/<应用> 一个目录
/srv        服务对外提供的数据      网站根、FTP、Git 仓库数据        /srv/<服务名>/
选型结论：源码编译 → /usr/local；商业整包 → /opt；服务数据 → /srv（或用 /var/www 等发行版惯例）。
注意 /srv 是 FHS 定义但很多发行版默认不建、不强制，实际项目里服务数据更常落在 /var/www、/var/lib。
```

```text
tmpfs 详解（/run /dev/shm /tmp 三个内存盘的差异）：
1. tmpfs 本质 —— 数据存内存、不足时换到 swap，掉电/重启即失；df -h 看到的「大小」是上限不是已用。
2. /run —— 运行时状态（PID/socket/lock），size 默认约 50% 内存，带 noexec（禁止执行），重启清空。
3. /dev/shm —— POSIX 共享内存（shm_open/mmap 匿名共享），默认 50% 内存、权限 1777 世界可写。
4. /tmp —— 各发行版不同：Ubuntu 默认 /tmp 在磁盘上（不是 tmpfs），Fedora/Arch 可配成 tmpfs（systemd tmp.mount）。
5. size= 挂载参数 —— 限制 tmpfs 最大占用（如 size=2G），防某个 tmpfs 无限吃内存拖垮系统。
```

```text
/boot 的 efi 子目录与 /srv、/var/lib/docker（补全目录地图）：
1. /boot/efi —— UEFI 启动的 ESP（EFI System Partition），FAT32 格式，挂载在这里；
   里面 EFI/BOOT 和 EFI/ubuntu（或 EFI/redhat）放引导程序，删错了机器就起不来。
2. /var/lib/docker —— Docker 的数据根目录（容器/镜像/卷/网络元数据全在这），企业磁盘占用大户；
   迁移 Docker 数据盘、清理磁盘都针对它，生产环境常单独挂大磁盘。
3. /srv —— 服务对外提供的数据（网站根、FTP 目录），FHS 定义但非强制，很多发行版默认不建。
```

```text
设备节点的主次设备号（/dev 的工作原理）：
$ ls -l /dev/sda /dev/null
brw-rw---- 1 root disk 8, 0   /dev/sda    # b=块设备，8,0 = 主设备号,次设备号
crw-rw-rw- 1 root root 1, 3   /dev/null   # c=字符设备
major（主设备号）→ 内核路由到哪个驱动；minor（次设备号）→ 驱动区分是哪个具体设备
设备节点本身只是「入口标记」，真正读写由内核按这对数字转交驱动，所以 /dev 里其实没有真实数据。
```

```text
关键目录的默认权限（理解为什么普通用户能/不能写）：
/ 755、/etc 755、/usr 755 —— 系统目录，普通用户只读
/tmp 1777、/var/tmp 1777    —— 所有人可写 + sticky bit，防互删
/home/用户 700、/root 700   —— 用户主目录默认只自己可进
/var/log 755（内部文件多为 640）—— 日志只 root/adm 组可读
权限是 FHS 约定之外的另一层约束：目录「该放什么」+ 权限「谁能动」共同决定文件安全边界。
```

```text
FHS 里的其它目录（补全地图，别只知道前 11 个）：
1. /srv —— 服务数据（service data），如 /srv/www、/srv/ftp，放服务对外提供的数据
2. /mnt —— 管理员手动挂载的临时挂载点（mount /dev/sdb1 /mnt/data）
3. /media —— 系统自动挂载的可移动介质（U 盘/光盘），如 /media/user/USB
4. /lost+found —— fsck 修复后找回的孤儿文件碎片，每个 ext 文件系统根目录一个
5. /var/run → /run 软链 —— 运行时数据的兼容路径，老脚本写 /var/run 也指向 /run
```

```text
Red Hat 系与 Debian 系的 FHS 相关差异（管理 Red Hat/CentOS/RHEL 机器时要转换习惯）：
1. 默认文件系统 —— Red Hat 系默认 XFS（擅长大文件/高吞吐、不能 shrink）；Debian 系默认 ext4（成熟、能 shrink）
2. /etc/sysconfig/ —— Red Hat 系独有的配置目录：/etc/sysconfig/network（网络参数）、/etc/sysconfig/selinux
   （SELinux 开关）、/etc/sysconfig/network-scripts/（传统 ifcfg 网卡配置，NetworkManager 之前的主方式）；
   Debian 系没有这个目录，网络配 /etc/network/interfaces 或 netplan，服务参数配 /etc/default/。
3. 分区规划 —— RHEL 安装器默认用 LVM 把 /、/var、/home 等单独建逻辑卷，且因 XFS 不能 shrink，规划时要预留空间；
   Ubuntu 桌面默认常一个根分区 + swap。
4. 包文件分布 —— 查询文件归属用 rpm -qf / rpm -ql（Red Hat）vs dpkg -S / dpkg -L（Debian），命令不同、结论一致。
```

## 工作原理

FHS 靠「按用途分区」让所有程序遵循同一套位置约定：程序本体只读、放 /usr（可被多台机器共享挂载）；运行时的日志/缓存/数据库/锁文件会变化，放 /var 和 /run；每台机器不同的配置放 /etc。这种「静态数据与可变数据分离」是它跟 Windows「程序 + 数据 + 配置堆一个目录」最本质的区别，也决定了备份策略（备份 /etc 和 /var 就能还原这台机器的配置和业务数据）。

```text
为什么这样分（设计意图）：
1. /usr 只读共享 —— 同一份程序镜像可挂给多台机器，升级只动一处
2. /etc + /var 本机独立 —— 配置和数据是每台机器自己的，备份它们即可还原
3. /tmp /run 易失 —— 临时和运行时数据放内存/临时盘，重启自动清、不留垃圾
```

伪文件系统的工作原理是「内核即时生成，不落磁盘」：/proc 和 /sys 是内核暴露自身状态的接口——读 /proc/meminfo 时，内核当场计算当前内存使用情况返回，文件本身不存在于磁盘上（大小显示为 0）；/dev 里的设备节点则是指向驱动的入口，读 /dev/null 就是丢弃、读 /dev/random 就是取随机数；/run 是 tmpfs，数据存在内存里，掉电即失。理解这一点，就不会犯「往 /proc 里写配置当永久存储」的错误。

```text
伪文件系统三大特性（为什么「不能当普通文件编辑」）：
1. 不占磁盘 —— df -h 看 /proc /sys /dev 大小是 0，数据由内核实时生成
2. 内容动态 —— 读一次变一次（如 /proc/meminfo），不能缓存、不能备份
3. 写入受限 —— 少量文件可写但需特定格式（echo 特定值），改错影响内核，优先用 sysctl
```

```text
tmpfs 的工作原理（内存盘为什么「快但易失」）：
tmpfs 不落任何磁盘，数据直接放内核的页缓存（page cache）里，读写走内存、速度远超磁盘；
内存不够时这些页可以被换出到 swap（所以 tmpfs 占用量受 size= 和内存+swap 总量约束）。
代价：掉电/重启数据全丢，且它占的内存就是真实内存开销——/run 里塞大文件会直接吃内存。
这决定了它的用途边界：只放「能丢、要快、重启可重建」的数据（PID/socket/共享内存/临时文件）。
```

```text
usr merge 背后的启动流程变化（为什么 /usr 现在必须和 / 同一分区）：
早期：内核加载 initramfs → 只挂载 / 和 /bin /sbin /lib（这时 /usr 还不可用）→ 启动脚本再挂 /usr
     —— 所以 /usr 可以单独分区、甚至放网络盘（NFS 无盘工作站）。
现代：initramfs 直接挂载真正的根文件系统（含 /usr）→ systemd 启动时假定 /usr 立即可用
     —— 所以 /usr 必须和 / 在同一分区，单独挂载会导致启动早期找不到关键文件而失败。
```

```shell
mount --bind /data /mnt/data        # 把一个目录挂到另一个入口（同内容两个路径）
mount --rbind / /mnt/root           # 递归 bind（连子挂载点一起搬，容器常用）
findmnt -R /mnt/data                # 递归看某挂载点下的所有子挂载
umount -l /mnt/data                 # 懒卸载（忙时先摘掉目录项，闲时真正卸载）
```

## 配置文件解析

```text
/etc —— 系统与软件配置的家（FHS 里最核心的配置目录）：
/etc/fstab          # 文件系统挂载表（开机自动挂载）
/etc/passwd /etc/shadow   # 用户账号与密码哈希
/etc/ssh/sshd_config      # SSH 服务配置
/etc/nginx/nginx.conf     # nginx 配置
/etc/cron.d/              # 定时任务配置片段
```

```text
/etc/profile 与 /etc/environment —— 全局环境配置：
/etc/profile       # 登录 shell 全局初始化（PATH、umask），各发行版再 include /etc/profile.d/*.sh
/etc/environment   # 系统级环境变量（PAM 读它，不区分 shell）
```

```text
/var 下的关键子目录（磁盘告警时按这个顺序查）：
/var/log      # 日志（access.log、syslog、journal），最常撑爆磁盘
/var/cache    # 缓存（apt 缓存、包缓存），可安全清理
/var/lib      # 程序数据（mysql、docker、postgresql 数据目录都在这）
/var/spool    # 队列（邮件队列、打印队列、cron 的 at 队列）
/var/tmp      # 比 /tmp 更「持久」的临时文件（重启不清，但仍有清理策略）
```

```text
/etc/sysconfig/（Red Hat 系独有）—— Debian 系没有这个目录，管理红帽机器时的关键差异：
/etc/sysconfig/network              # 全局网络参数（HOSTNAME、GATEWAY 等）
/etc/sysconfig/selinux              # SELinux 模式（enforcing/permissive/disabled）
/etc/sysconfig/network-scripts/ifcfg-eth0   # 传统网络接口配置（NetworkManager 之前的主方式）
/etc/sysconfig/sshd                 # sshd 服务的启动参数
Debian 系对应物：网络配 /etc/network/interfaces 或 netplan（/etc/netplan/*.yaml），
服务参数配 /etc/default/<服务>（如 /etc/default/docker），所以「配置放哪」要按系别切换。
```

```text
/tmp 与 /var/tmp 的清理策略（为什么临时文件会「自动消失」）：
systemd-tmpfiles 按规则定期清理 /tmp 和 /var/tmp（默认 10 天/30 天没访问就删），
具体策略在 /usr/lib/tmpfiles.d/tmp.conf，可用 systemd-tmpfiles --clean 手动触发。
/tmp —— 每次重启或按 tmpfiles 规则清；/var/tmp —— 重启不清、但按更长时间规则清。
所以「临时文件能放几天」不是玄学，是 tmpfiles 的 Age 字段决定的。
```

```text
fstab 里的 systemd 专用挂载选项（x-systemd.*，现代 Ubuntu/RHEL 常用）：
/dev/disk/by-uuid/<UUID> /data ext4 defaults,nofail,x-systemd.device-timeout=5s,x-systemd.automount 0 2
nofail                       # 设备不存在也不报错、不阻塞启动（U 盘/外置盘必备）
x-systemd.device-timeout=5s  # 等设备最多 5 秒（默认 90s），缺盘时别拖慢启动
x-systemd.automount          # 首次访问该目录时才真正挂载（按需挂载）
x-systemd.requires=/mnt/base # 声明依赖：先挂 /mnt/base 再挂本行
x-systemd.idle-timeout=10m   # 配合 automount，闲置 10 分钟自动卸载
改完 /etc/fstab 要执行 `systemctl daemon-reload`，让 systemd-fstab-generator 重新生成 .mount 单元。
```

```text
/etc/ld.so.conf.d/ 与 ldconfig（动态库路径，和 FHS 的 /usr/lib 配合）：
/etc/ld.so.conf        # 主文件，通常只有一行 `include /etc/ld.so.conf.d/*.conf`
/etc/ld.so.conf.d/     # 各软件放自己的库路径片段（如 libc.conf、x86_64-linux-gnu.conf）
ldconfig               # 读上述配置 + 标准库目录（/lib /usr/lib /usr/local/lib），生成 /etc/ld.so.cache
ldconfig -p | grep <库名>   # 查某个库当前解析到哪个路径
# 手工编译的库装到 /usr/local/lib 后，必须 ldconfig 一次（或在 /etc/ld.so.conf.d/ 里加路径）才能被找到
```

```text
/etc 下与本机实测相关的小文件（速查）：
/etc/localtime     # 指向 /usr/share/zoneinfo/<区域> 的软链，改时区就换它
/etc/hostname /etc/hosts   # 主机名与静态名称解析
/etc/shells        # 系统认可的合法登录 shell 列表（chsh 依据它）
/etc/skel/         # 新用户家目录模板，本机含 .bash_logout(220B)/.bashrc(3771B)/.profile(807B)
/etc/alternatives/ # update-alternatives 的软链集中地，本机实测 awk -> /usr/bin/mawk
/etc/profile.d/    # 全局环境变量片段，登录时被 /etc/profile 逐个 source
/etc/default/      # Debian 系服务参数（RHEL 系对应 /etc/sysconfig/）
```

```text
/etc/tmpfiles.d/ 覆盖默认清理规则（自定义临时文件留存时间）：
/usr/lib/tmpfiles.d/tmp.conf   # 发行版默认：/tmp 10 天、/var/tmp 30 天未访问即清
/etc/tmpfiles.d/tmp.conf       # 建同名文件即覆盖默认（本地优先，升级不丢）
规则语法： 类型  路径          权限  属主 属组 存活期
示例：     d     /var/tmp/x   1777  root root 30d      # 目录，30 天未访问即清
生效：     systemd-tmpfiles --clean（开机由 systemd-tmpfiles-clean.timer 触发）
```

## 应用场景实战

### 场景一：磁盘满了，快速定位是哪个目录吃掉的

```shell
# 1. 先看哪个分区满了
df -h

# 2. 对满的分区逐层找大目录（/ 满了通常查 /var /usr /home /tmp）
du -sh /var/* 2>/dev/null | sort -rh | head -10

# 3. 常见元凶：日志（/var/log）、缓存（/var/cache）、数据库（/var/lib）、临时文件（/tmp）
ls -lhS /var/log | head
ls -lhS /tmp | head
```

```text
# 实测输出（本机真实分布）
$ du -sh /var /usr /home /tmp 2>/dev/null
36G     /var
8.8G    /usr
5.1G    /home
469M    /tmp
# /var 独占 36G，远超其它目录——典型的企业服务器形态：日志+数据库+容器数据都压在 /var
# 所以磁盘告警时第一眼就该看 /var 下的 /var/lib（数据库）、/var/log（日志）、/var/lib/docker（容器）。
```

### 场景二：装一个第三方软件到 /opt，并按 FHS 约定组织配置和日志

```shell
# 1. 软件本体装到 /opt/myapp
mkdir -p /opt/myapp/bin
cp ./myapp /opt/myapp/bin/

# 2. 配置文件放 /etc（系统级配置约定位置）
mkdir -p /etc/myapp
cp ./myapp.conf /etc/myapp/

# 3. 运行时数据放 /var（日志、PID 文件）
mkdir -p /var/log/myapp /run/myapp

# 4. 给用户加个 PATH，用软链暴露可执行文件
ln -s /opt/myapp/bin/myapp /usr/local/bin/myapp
```

### 场景三：查一个已安装软件的文件分布（FHS 实战）

```shell
# Debian 系：看 nginx 装的所有文件分别落在哪些 FHS 目录
dpkg -L nginx

# Red Hat 系：看 rpm 包的文件清单
rpm -ql nginx

# 反查：某个文件属于哪个包（丢了文件知道补哪个包）
dpkg -S /etc/nginx/nginx.conf      # Debian
rpm -qf /etc/nginx/nginx.conf      # Red Hat
```

```text
# 实测：nginx 包的文件严格按 FHS 分布（本机真实输出，Ubuntu 24.04）
$ dpkg -L nginx | grep -E '/(etc|usr|var)/' | head -20

/usr/sbin/nginx                # 可执行进 /usr/sbin
/usr/lib/nginx/                # 模块与库进 /usr/lib
/var/log/nginx/                # 日志进 /var/log
/run/nginx.pid                 # PID 文件进 /run
# 一个包的文件精确落位到五个 FHS 目录——这正是「按用途分区」在真实软件里的体现。
```

## 性能与调优

```text
FHS 相关的性能/容量优化：
1. /var 单独分区 —— 日志/数据库/容器都写 /var，单独分区避免它写满拖垮根分区
2. /tmp 挂 tmpfs —— 临时文件落内存，读写快且重启自动清；代价是占内存、大文件别放
3. 挂载 noatime —— 关掉 atime 更新，减少读文件时的磁盘写（日志/数据库场景收益明显）
4. /usr 只读 + 共享挂载 —— 只读挂载 + 共享镜像，容器/无盘场景省空间、提启动速度
5. 日志放 /var/log 并做轮转 —— 避免日志无限增长占满 /var（配合 logrotate）
6. 清理 /var/cache —— apt 缓存、包缓存可安全清（apt clean / dnf clean all），省出几个 G
```

```text
Red Hat 系（XFS）的分区/文件系统规划差异：
1. RHEL 默认 XFS —— 擅长大文件顺序读写/高吞吐，但 xfs 不支持 shrink（只能 grow），分区前要预留好空间
2. LVM 布局 —— RHEL 安装器默认 LVM，把 /、/var、/home、/boot 分成独立逻辑卷，便于单独扩容/隔离
3. /var 单独卷 —— 因日志/数据库写 /var，RHEL 默认就给它单独逻辑卷，满了只影响自己、不拖垮根
4. 排查工具 —— 查 XFS 用 xfs_info / xfs_growfs；ext4 用 tune2fs / resize2fs，命令别混用
```

```text
/tmp 挂 tmpfs 的利弊与决策（是否把 /tmp 放进内存）：
利 —— 临时文件读写快（编译/打包临时文件收益明显）、重启自动清、不写磁盘减少 SSD 磨损
弊 —— 占用内存（默认 50% RAM）、大文件（解压大包/视频转码）会撑爆内存触发 OOM
决策 —— 桌面/小临时文件场景适合；跑大文件处理的服务别把 /tmp 挂 tmpfs，或给 size= 限制
启用 —— systemd 系 systemctl enable --now tmp.mount；Ubuntu 默认不开（/tmp 在磁盘上）
```

## 安全与权限

```text
FHS 安全要点：
1. /tmp 必须有 sticky bit —— 所有人可写但只能删自己的文件（drwxrwxrwt），防互相删文件
2. /var/log 收紧权限 —— 日志含敏感信息，目录 750、文件 640，只 root 和 adm 组可读
3. /proc /sys 只读保护 —— 伪文件系统多只读，写错会影响内核，改参数用 sysctl
4. /usr 只读挂载 —— 生产/容器场景把 /usr 只读，防被入侵后篡改程序文件
5. 别把敏感数据放 /tmp /var/tmp —— 世界可读的临时目录，密钥/凭据绝不落这里
6. /dev 设备节点权限 —— 磁盘设备（/dev/sda）默认 root:disk 660，防普通用户直接读写裸设备绕过文件权限
```

```text
tmpfs 的安全面（内存盘不是「更安全」，是「易失 + 可写」）：
1. /dev/shm 1777 世界可写 —— 和 /tmp 一样有 sticky bit，但同样是攻击者放恶意文件的高发地
2. /run noexec —— 多数发行版给 /run 挂 noexec，防止在运行时目录执行恶意程序
3. tmpfs 不落磁盘 —— 敏感数据放 tmpfs 关机即无（有临时保密需求时反而合适），但内存取证仍可读到
4. size= 限制 —— 给 tmpfs 设 size= 防某个程序往 /run /dev/shm 狂写撑爆内存
```

## 故障排查

```shell
# 1. 文件找不到：确认该程序按 FHS 装在哪
dpkg -S <文件名>        # Debian 反查所属包
find / -name "<文件名>" 2>/dev/null   # 兜底全盘找

# 2. 磁盘满：按 FHS 逐层定位
df -h
du -sh /var/* 2>/dev/null | sort -rh | head

# 3. Read-only file system：/usr 或根被只读挂载了
mount | grep -E 'ro,|,ro '
mount -o remount,rw /    # 重新读写挂载（根分区）

# 4. /tmp 文件被清：确认 systemd-tmpfiles 清理策略
systemctl status systemd-tmpfiles-clean.timer

# 5. 程序报「找不到 PID 文件/socket」：查 /run 是否被清空（重启后正常现象）
ls -la /run/myapp
# /run 是 tmpfs，重启即清；程序要有能力在启动时重建这些文件

# 6. 磁盘显示有空间但报 No space left on device：inode 用完了
df -h /          # 空间还有
df -i /          # 但 inode 用完（大量小文件把 inode 占满）
find / -xdev -type f | wc -l   # 数文件总量，定位是哪个目录塞了几十万小文件
```

```shell
# 7. tmpfs 写满导致「内存不足」或程序写不进去
df -h /run /dev/shm            # 看 tmpfs 是否到了 size= 上限
findmnt -t tmpfs -o TARGET,SIZE,OPTIONS   # 看各 tmpfs 的 size= 限制
# /dev/shm 被写满：常见是某程序往共享内存狂写；解法是清掉或用 size= 限制

# 8. 误删 /boot/efi 导致 UEFI 机器起不来
ls /boot/efi/EFI/              # 确认引导程序目录还在（ubuntu/redhat 子目录）
# 起不来时用安装介质进救援模式，重新 grub-install 重建 EFI 引导程序
```

```shell
# 9. 设备名变了（/dev/sda2 变 /dev/sdb2）导致挂载错盘/起不来
ls -l /dev/disk/by-uuid/ | grep <UUID>    # 用 UUID 反查现在对应哪个设备
blkid                                     # 看每个分区的 UUID/TYPE
# 结论：fstab 一律写 /dev/disk/by-uuid/<UUID> 或 UUID=<UUID>，别写 /dev/sdXN
# 报错特征：进了 emergency mode，journalctl -xb 里看到 "Failed to mount ... /dev/sdXN"
```

```shell
# 10. 挂载单元启动失败 / 挂载点被跳过（示例）
systemctl --failed                       # 找出失败单元（.mount 很常见）
systemd-analyze verify /etc/fstab        # 校验 fstab 语法与依赖顺序
mount -a                                 # 手动按 fstab 挂一遍，直接看报错
# 常见原因：设备不存在又没写 nofail；UUID 写错；挂载点目录不存在；选项拼写错
```

```shell
# 11. 临时文件/日志莫名消失
systemd-tmpfiles --cat-config | grep -A2 '/tmp'   # 看 /tmp 实际清理规则来自哪个文件
systemctl list-timers | grep tmpfiles             # 看清理定时器上次/下次执行时间
# 结论：不是被系统「吞了」，是 tmpfiles 按 Age 到期清理；要留就放 /etc/tmpfiles.d/ 覆盖
```

```shell
# 12. 根文件系统变成只读（ro）（示例）
mount | grep ' / '                                  # 确认根是不是 ro
journalctl -k | grep -iE 'remount|ext4-fs error|I/O error'   # 看内核是否因 IO 错误自保置 ro
mount -o remount,rw /                               # 临时恢复读写
# 根被内核自动置 ro 通常是文件系统错误或磁盘故障的自保行为，先修数据再 remount
```

## 常见问题

```text
Q1: /bin 和 /usr/bin 有什么区别？
A: 现在没区别。usr merge 后 /bin 是 /usr/bin 的软链，两个路径等价。

Q2: 为什么磁盘告警先看 /var？
A: /var 是日志(/var/log)+数据库(/var/lib)+容器(/var/lib/docker)的聚集地，是企业服务器占空间的大头。

Q3: 手工装的软件放哪？
A: 第三方独立软件放 /opt/<app>（整个应用一个目录），自己编译的放 /usr/local，别污染包管理器领地。

Q4: /proc /sys 里的文件能改吗？
A: 多数只读，少量可写但要用正确格式（echo 特定值），改错可能影响系统，优先用 sysctl 命令。

Q5: /tmp 的文件能放重要数据吗？
A: 不能。它可能被 tmpfiles 定期清理、重启清空，重要数据放 /home 或 /var。

Q6: /run 和 /var/run 什么关系？
A: /run 是内存文件系统（tmpfs）放 PID/socket/锁文件，重启清空；/var/run 在多数发行版是 /run 的软链，两者等价。

Q7: /dev 里的文件是真文件吗？
A: 不是。是设备节点，只存主次设备号（major/minor），读写时内核按这对数字转交驱动，所以 ls -l 看到的是 b/c 开头而非 -（普通文件）。

Q8: /srv、/opt、/usr/local 都放第三方东西，怎么区分？
A: /opt 放自包含的整包商业/第三方软件；/usr/local 放手工源码编译的程序（按 /usr 的结构组织）；/srv 放服务对外提供的数据（网站根、FTP 目录）。数据放 /srv，程序放 /opt 或 /usr/local。

Q9: /run、/dev/shm、/tmp 都是 tmpfs 吗？有什么区别？
A: 不一定。/run 和 /dev/shm 几乎总是 tmpfs；/tmp 各发行版不同——Ubuntu 默认 /tmp 在磁盘上，Fedora/Arch 可配成 tmpfs。/run 放运行时状态（noexec）、/dev/shm 放共享内存（1777 世界可写）、/tmp 放临时文件。

Q10: 为什么现在 /usr 不能再单独分区了？
A: usr merge 后 /bin /sbin /lib 都并进 /usr，现代 initramfs 启动早期就挂载含 /usr 的根文件系统、systemd 假定 /usr 立即可用，/usr 单独挂载会导致启动早期找不到关键文件而失败，所以 /usr 必须和 / 同一分区。

Q11: 为什么 /etc/fstab 里不写 /dev/sda2 而写 UUID？
A: /dev/sdXN 由内核探测顺序决定，加盘/换盘位/加 NVMe 后可能变成 sdb2，写死会挂错盘甚至开不了机；UUID 跟文件系统走，认盘不认位置。用 ls -l /dev/disk/by-uuid/ 或 blkid 查映射，本机根分区就是 /dev/disk/by-uuid/93b40af2-6f5d-40e1-b057-593b6b7c7428。

Q12: XDG Base Directory 是什么？和 FHS 什么关系？
A: 用户级数据的约定——配置 ~/.config、数据 ~/.local/share、状态 ~/.local/state、缓存 ~/.cache，系统级配置 /etc/xdg；它补的是 FHS「只管系统级目录」留下的空白。现代应用把用户配置放 ~/.config 而不是 /etc，避免多用户互相污染、也不需要 root 权限写系统目录。

Q13: 挂载选项 nosuid,nodev,noexec 有什么用？
A: 缩小可写分区的攻击面——nosuid 忽略 setuid/setgid（防分区里藏提权程序）、nodev 忽略设备节点（防在 /tmp 造 /dev/sda 读裸盘）、noexec 禁执行（防 tmp 目录当跳板）。常用于 /tmp、/var/tmp、/home 和数据盘；注意副作用：/tmp 加 noexec 会让部分安装器、自解压包、CI 工具报 Permission denied。

Q14: overlayfs 是什么？和容器有什么关系？
A: 它把只读 lowerdir 与可写 upperdir 叠成 merged 视图，改写落 upper、未改动文件走 lower；Docker 镜像每层是只读 lower、容器运行时加一个可写 upper（本机 df 里能看到多条 /var/lib/docker/rootfs/overlayfs/<id>）。overlayroot 的只读根方案也基于同一机制。

Q15: systemd 的 .mount 和 /etc/fstab 是什么关系？
A: 同一套系统——开机时 systemd-fstab-generator 读 /etc/fstab 自动生成 .mount/.swap 单元，所以改完 fstab 要 systemctl daemon-reload 重新生成。单独写 .mount 单元可实现按需挂载（配 .automount）、依赖顺序、超时控制等 fstab 表达不了的能力。

Q16: 为什么系统里 /bin、/sbin、/lib 都成了软链？
A: 这是 usr merge：Fedora 15/17 率先、Debian 8 与 Ubuntu 16.04 跟进，把这三个目录软链到 /usr 下，消除「同一命令两个位置」的混乱；现代 initramfs 启动早期就能挂载 /usr，不再需要单独保留 /bin 那一套。
```

## 面试题

```text
1. FHS 的核心思想是什么？
   答：按用途分区而非按程序分区——配置进 /etc、可变数据进 /var、程序进 /usr，静态与可变数据分离。

2. /var 和 /tmp 放什么、区别是什么？
   答：/var 放持久化的可变数据（日志/缓存/数据库）；/tmp 放临时文件，可能重启清空、不持久。

3. /proc 是什么？占磁盘吗？
   答：内核生成的内存文件系统（procfs），暴露进程和内核状态，不占磁盘，随内核动态生成。

4. 为什么 /usr 可以只读挂载？
   答：/usr 只放静态程序文件，运行时不写，可只读挂载 + 跨机共享，提升安全和可维护性。

5. 备份一台服务器的配置和业务数据，最小要备哪些目录？
   答：/etc（配置）、/var（业务数据/日志）、/home（用户数据），配合软件清单即可还原。

6. /dev/sda 里的 8,0 是什么意思？
   答：主设备号 8 和次设备号 0。主设备号路由到磁盘驱动，次设备号区分具体磁盘。设备节点本身不存数据，只是驱动入口。

7. 为什么 /tmp 要有 sticky bit？
   答：/tmp 所有人可写（1777 权限），sticky bit 保证「只有文件属主和 root 能删除」，否则任何用户都能删别人的临时文件。

8. /proc 和 /sys 都暴露内核信息，区别是什么？
   答：/proc（procfs）偏「进程与内核运行状态」，是历史悠久的只读信息接口；/sys（sysfs）偏「内核对象模型」，按设备/驱动/总线结构化、可写（配合 udev 做设备管理）。读状态看 /proc，操作设备属性看 /sys。

9. usr merge 是什么？为什么 /bin 和 /usr/bin 现在等价？
   答：usr merge 是把 /bin /sbin /lib 软链合并到 /usr 下的历史变革（Fedora 15 率先、Debian 8/Ubuntu 16.04 跟进），消除「同一命令两个位置」的混乱；现代 initramfs 启动早期就能挂载 /usr，不再需要单独保留 /bin，所以 /bin 只是 /usr/bin 的软链、两条路径等价。

10. tmpfs 和普通磁盘文件系统有什么区别？什么数据适合放 tmpfs？
   答：tmpfs 数据存内存（不足换到 swap）、读写快但重启/掉电即失、df 看到的大小是上限不是已用；普通文件系统落磁盘、持久但慢。适合放「能丢、要快、可重建」的数据：/run 的 PID/socket、/dev/shm 的共享内存、临时文件；不适合放数据库、日志、用户数据。

11. Red Hat 系和 Debian 系在 FHS 上有什么关键差异？
   答：默认文件系统不同（Red Hat 系 XFS、Debian 系 ext4，XFS 不能 shrink）；Red Hat 系有 /etc/sysconfig/ 配置目录（网络/SELinux/服务参数）而 Debian 系没有（用 /etc/default/ 和 /etc/network/interfaces）；文件归属查询用 rpm -qf/-ql vs dpkg -S/-L。

12. 为什么 /etc/fstab 要用 UUID 而不是 /dev/sdXN？
   答：/dev/sdXN 由内核探测顺序决定，加盘/换盘位/加 NVMe 后名字会变，写死可能挂错盘甚至开不了机；UUID 绑定文件系统稳定不变。写成 /dev/disk/by-uuid/<UUID> 或 UUID=<UUID>，查映射用 ls -l /dev/disk/by-uuid/ 或 blkid。

13. XDG Base Directory 解决什么问题？
   答：解决「用户级配置/数据往哪放」——约定 ~/.config（配置）、~/.local/share（数据）、~/.local/state（状态）、~/.cache（缓存）与系统级 /etc/xdg；让应用不再往 $HOME 根下撒 dotfile、也不往 /etc 写用户数据，便于备份与多用户隔离。

14. 解释 overlayfs 在容器里的作用，以及只读根的意义。
   答：overlayfs 用只读 lowerdir + 可写 upperdir 叠成 merged 视图，镜像层只读、容器写层可写（本机 df 可见多条 /var/lib/docker/rootfs/overlayfs/<id>）。只读根（overlayroot）让根不可持久修改，被入侵难落地、掉电不易损坏文件系统，代价是升级要 remount rw 或原子切换（ostree/A-B 分区）。

15. systemd 的 .mount/.automount 与 fstab 什么关系？nofail、x-systemd.automount 干什么？
   答：systemd-fstab-generator 把 /etc/fstab 转成 .mount/.swap 单元，改完要 systemctl daemon-reload；nofail 让设备缺失不阻塞启动，x-systemd.automount 实现按需挂载（首次访问才真正挂），.automount 单元还能闲置超时自动卸载。

16. 临时文件清理由谁负责？/tmp 与 /var/tmp 保留期有何不同？
   答：systemd-tmpfiles 负责，规则在 /usr/lib/tmpfiles.d/tmp.conf（本机该目录还有 home.conf、debian.conf、dbus.conf 等片段），/etc/tmpfiles.d/ 可同名覆盖；默认 /tmp 10 天、/var/tmp 30 天未访问即清，systemd-tmpfiles --clean 手动触发，开机由 systemd-tmpfiles-clean.timer 触发。

17. 容器镜像里的 FHS 与常规发行版有何不同？
   答：Alpine 用 musl libc + BusyBox、未 usr-merge 且 /bin /lib 多为符号链接；scratch 是空镜像，连 /bin/sh、/etc、/lib 都没有；distroless 只有运行时库和证书、无 shell 无包管理器。镜像内不是完整 FHS，而是「所需子集 + 应用目录」，脚本不能假设 shell 与 /etc/passwd 存在。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 手工编译安装的软件放 /usr/local 或 /opt，别污染 /usr 的包管理器领地
2. 排查磁盘满按 FHS 定位：日志 /var/log、缓存 /var/cache、数据 /var/lib、临时 /tmp
3. 脚本里写临时文件用 /tmp，写 PID 文件和 socket 用 /run（重启自动清空，不留垃圾）
4. 读系统状态优先 /proc /sys，比装一堆监控工具更快更准
5. 改 /etc 下的配置前先备份，这个目录是所有软件配置的家
6. 给服务器分区时 /var 单独挂（或至少预留足够空间），日志和数据库都靠它
7. 数据目录（MySQL/PG/Docker）统一放 /var/lib，配合持久化磁盘和备份策略
8. /usr/local、/opt、/srv 三个「非包管理器」目录按用途选：编译 /usr/local、商业整包 /opt、服务数据 /srv
9. Red Hat 系机器上配置别去 /etc/default/ 找，要看 /etc/sysconfig/（网络、SELinux、服务参数都在这）

### 踩坑记录

```text
坑 1：把 /tmp 当成永久存储，重启后文件没了
结论：放 /tmp 的文件重启后丢失，或长时间不用被 systemd-tmpfiles 清理。
原因：/tmp 是临时目录，部分发行版用 tmpfiles 定时清空旧文件。
解法：要长期保留的文件放 /home 或 /var，别放 /tmp。

坑 2：往 /proc 里写数据「成功」了但没效果甚至报错
结论：以为能像普通文件一样编辑 /proc 下的内容。
原因：/proc /sys 是内核生成的内存文件系统，多数只读或需要特定格式写入。
解法：用专门的命令（sysctl、echo 特定值到特定文件）修改，别当普通文件编辑。

坑 3：直接 rm /bin 里的文件导致命令全挂
结论：删了系统命令，连 ls 都跑不了。
原因：/bin 是基础命令所在，删错导致系统无法操作。
解法：基础命令目录别乱动；误删后用 busybox 或救援模式恢复。

坑 4：装软件把文件散得到处都是，卸载时删不干净
结论：手工安装的软件可执行文件、库、配置、日志分散，卸载找不到。
原因：没按 FHS 约定归类，直接解压到根目录。
解法：第三方软件统一装 /opt/<app>，配置 /etc/<app>，日志 /var/log/<app>，卸载删整个目录即可。

坑 5：把数据库数据目录放在 /tmp 或内存盘，重启丢数据
结论：MySQL/PG 数据目录放错位置，重启后数据全丢。
原因：数据目录放在 tmpfs 或 /tmp 这类易失目录。
解法：持久化数据统一放 /var/lib（如 /var/lib/mysql），并挂到持久化磁盘。

坑 6：把程序日志写到 /usr 或程序目录，只读文件系统写失败
结论：程序在 /usr 下写日志报 Read-only file system。
原因：/usr 按 FHS 约定是只读共享目录，容器/只读根场景下不可写。
解法：运行时可变数据（日志/缓存/PID 文件）一律放 /var 和 /run。

坑 7：/var/log 占满根分区导致服务起不来
结论：日志把 /var 写满，mysql/nginx 等服务报「磁盘空间不足」启动失败。
原因：日志没有轮转（logrotate 未配或失效），持续增长直到占满分区。
解法：先 truncate -s 0 或 rm 掉大日志恢复服务，再配 logrotate 做轮转压缩，/var 单独分区隔离风险。

坑 8：把 /dev/shm 当成无限内存往里面写，触发 OOM 或内存告警
结论：程序往 /dev/shm 写大文件，机器内存被吃满甚至触发 OOM killer。
原因：/dev/shm 是 tmpfs，占用的就是真实内存（默认 50% RAM），不是磁盘。
解法：共享内存只放临时小数据，大文件别放；给 /dev/shm 设 size= 限制，或改用磁盘目录。

坑 9：在 Red Hat 系机器上找 /etc/default/ 没找到服务配置
结论：以为所有发行版都用 /etc/default/ 放服务参数，结果红帽机器上找不到。
原因：Red Hat 系用 /etc/sysconfig/ 放网络/SELinux/服务参数，Debian 系才用 /etc/default/。
解法：先识别系别（cat /etc/os-release），红帽系去 /etc/sysconfig/ 找，别套 Debian 的习惯。

坑 10：给 /tmp 加了 noexec，安装器/脚本跑不起来
结论：装上 noexec 后，某些安装器、自解压包、pip/conda 的临时二进制报 Permission denied。
原因：noexec 禁止在该分区执行任何程序，而这些工具习惯在 /tmp 里解出二进制再直接运行。
解法：评估业务再决定；确需 noexec 时给这类工具指定别的可执行临时目录（如 TMPDIR=/var/tmp 或专用目录）。

坑 11：fstab 写死 /dev/sda2，换盘/加盘后起不来
结论：加了新硬盘或换了盘位，根分区挂载失败、机器进 emergency mode。
原因：/dev/sdXN 由内核探测顺序决定，设备顺序一变名字就变，fstab 里写死的设备名指错盘。
解法：fstab 一律写 /dev/disk/by-uuid/<UUID> 或 UUID=<UUID>；已进救援模式就临时改 fstab 再重启。

坑 12：外置盘写进 fstab 没加 nofail，开机卡住
结论：U 盘/移动硬盘不在时，开机卡在「等待设备」甚至掉进 emergency mode。
原因：fstab 默认挂载失败会阻塞启动，systemd 等设备超时（默认 90s）后仍判定该挂载失败。
解法：外置盘行加 nofail,x-systemd.device-timeout=5s，需要按需挂载再加 x-systemd.automount。

坑 13：容器里 /dev/shm 太小，用共享内存的程序 OOM
结论：PostgreSQL/Chromium 等在容器里报共享内存不足、异常崩溃或直接 OOM。
原因：容器默认 /dev/shm 只有 64M（或跟宿主策略走），而 tmpfs 占的是真实内存。
解法：docker run 加 --shm-size=1g，或把需要大共享内存的进程改配到别的目录。

坑 14：把持久数据写进 overlay 的可写层（只读根/容器里）
结论：在容器或只读根系统里写的数据，重启/重建容器后全没了。
原因：写操作落在可写层（容器写层或 tmpfs upper），容器重建、系统重启该层即丢弃。
解法：持久数据用卷（volume/bind mount）挂到宿主持久位置（如 /var/lib/...），别落在 overlay 上层。
```
