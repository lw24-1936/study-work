## 概述

归档和压缩是两件事：归档（tar）把多个文件打包成一个文件，压缩（gzip/xz/zstd 等）把数据体积变小。Linux 习惯「先 tar 归档、再压缩」，所以常见 .tar.gz、.tar.xz 后缀。选压缩工具是在「压缩率、速度、CPU 消耗」之间权衡：xz 最省空间但最慢，gzip 均衡，zstd 又快压缩率又高（现代首选），zip 主要是和 Windows 互传用。

```text
归档 vs 压缩：
1. 归档 tar —— 只打包不压缩，把多文件合并成一个 .tar，保持目录结构
2. 压缩 gzip/xz/zstd —— 只压单个文件，所以要先 tar 再压
3. 组合后缀 —— .tar.gz（tar+gzip）、.tar.xz（tar+xz）、.tar.zst（tar+zstd）
4. 选型 —— 追求速度用 zstd，追求体积用 xz，通用兼容用 gzip，跨平台用 zip
```

## 归档工具 tar

tar 是标准的归档工具，核心动作是创建（-c）、解包（-x）、查看（-t），配合 -f 指定文件、-v 显示过程、-p 保留权限。现代 tar 能直接调压缩器（-z 走 gzip、-j 走 bzip2、-J 走 xz、--zstd 走 zstd），所以一条命令就能完成「归档 + 压缩」。记一个万能组合：打包用 `tar czf`，解包用 `tar xzf`。

```text
tar 常用选项：
1. 动作 —— -c 创建、-x 解包、-t 查看内容、-r 追加
2. 压缩 —— -z(gzip) / -j(bzip2) / -J(xz) / --zstd，不写则纯归档
3. 其他 —— -f 指定文件、-v 显示过程、-p 保留权限、-C 指定解包目录
```

```shell
# 打包 + 压缩（gzip）
tar czf backup.tar.gz /var/www /etc/nginx

# 解包到指定目录
tar xzf backup.tar.gz -C /tmp/restore

# 只看不解包
tar tzf backup.tar.gz

# 保留权限地打包（备份配置文件时重要）
tar cpzf etc-backup.tar.gz /etc
```

## 压缩工具 gzip bzip2 xz zstd zip

五个压缩工具各有定位。gzip 是老牌默认、速度压缩率均衡；bzip2 压缩率更高但明显更慢；xz（LZMA）压缩率最高、最省空间、也最慢；zstd 是 Facebook 开源的现代算法，压缩率接近 xz 但速度接近 gzip，还支持多线程，是当下首选；zip/unzip 是跨平台格式，Windows/macOS 都能直接解，适合互传。它们都只压单个文件，压目录得配合 tar。

```text
压缩工具对比：
1. gzip —— 均衡，.gz，兼容最好，默认选项
2. bzip2 —— 压缩率高、速度慢，.bz2，已被 xz/zstd 取代
3. xz —— 压缩率最高、最慢，.xz，追求体积用
4. zstd —— 压缩率高且快、支持多线程，.zst，现代首选
5. zip —— 跨平台，.zip，和 Windows 互传用
```

```shell
# 单文件压缩对比
gzip -9 big.log          # 最大压缩率
bzip2 big.log
xz -9 big.log
zstd -T0 big.log         # -T0 用满所有 CPU 核

# 解压
gzip -d big.log.gz
xz -d big.log.xz
unzip archive.zip        # 解压 zip
```

```text
# 实测（4.8M 重复文本，看各工具压缩后的体积）
$ ls -lh compdemo.txt compdemo.txt.gz compdemo.txt.bz2 compdemo.txt.xz compdemo.txt.zst
4.8M  compdemo.txt
12K   compdemo.txt.gz       # gzip：速度与体积均衡
957   compdemo.txt.bz2      # bzip2：更小但明显更慢
892   compdemo.txt.xz       # xz：接近最小
511   compdemo.txt.zst      # zstd：体积最小、速度还快，现代首选
# 换 4.8M 随机二进制再压：gzip 后仍是 4.8M——压缩效果取决于数据本身的可压缩性，
# 已压缩过的数据（图片/视频/随机数据）再压基本无收益，这是企业里「哪些该压哪些别压」的判断依据。
```

## 分卷

分卷把一个大归档切成多个固定大小的文件，方便存储或传输（比如绕过单文件大小限制）。两种方式：先用 tar 打成一个大包再 `split -b` 切成小片，解压时先 `cat` 拼回再 tar 解包；或者直接用 tar 输出到管道再 split。分卷后记得记录顺序，合并时顺序错了会解不开。

```text
分卷思路：
1. tar 打包 → split -b 切成 N 个固定大小文件
2. 恢复时 cat 按顺序拼接 → tar 解包
3. split 选项 —— -b 按字节（如 100M）、-d 数字后缀、-a 后缀位数
```

```shell
# 打包后分卷成每个 100MB
tar czf - /data | split -b 100M -d -a 3 - data.tar.gz.part

# 恢复：按顺序拼回再解包
cat data.tar.gz.part* > data.tar.gz
tar xzf data.tar.gz
```

## 增量备份

增量备份只备份自上次以来变化的文件，省空间省时间。tar 用 `--listed-incremental`（或 -g）配合快照文件实现：第一次全量并记录快照，之后每次只备份快照之后变化的文件。更常用的增量方案是 rsync（只传差异块）——tar 适合做历史版本留档，rsync 适合做镜像同步。

```text
增量备份方案：
1. tar -g 快照文件 —— 第一次全量 + 生成快照，之后只打包变化的文件
2. rsync —— 按差异块增量同步，适合镜像/异地备份
3. 时间粒度 —— 备份策略通常是「日增量 + 周全量」组合
```

```shell
# tar 增量备份
tar czg /var/backup/snapshot.snar -f inc-$(date +%F).tar.gz /data   # 首次全量 + 快照
tar czg /var/backup/snapshot.snar -f inc-$(date +%F).tar.gz /data   # 后续增量

# rsync 增量同步（只传差异）
rsync -avz --delete /data/ backup-server:/backup/data/
```

## 归档校验

归档后要校验完整性，防止传输或存储过程中损坏。三层校验：打包后用 sha256sum/md5sum 记录哈希、传输后比对；压缩文件用 gzip -t / xz -t / tar tf 检查是否能正常解开；备份恢复后抽查文件完整性。生产环境的备份一定要带校验，否则「备份是坏的」这种事故最致命。

```text
校验三层次：
1. 哈希校验 —— sha256sum 生成指纹，传输前后比对，检测损坏
2. 归档自检 —— gzip -t / tar tf 检查归档结构是否完整可解
3. 恢复校验 —— 恢复后抽查关键文件能否正常读取
```

```shell
# 生成校验和并保存
sha256sum backup.tar.gz > backup.tar.gz.sha256

# 传输后校验
sha256sum -c backup.tar.gz.sha256

# 归档自检
gzip -t backup.tar.gz && echo OK      # gzip 完整性
tar tzf backup.tar.gz > /dev/null && echo OK   # tar 可解
```

## 应用场景实战

### 场景一：备份站点目录并做增量 + 校验

```shell
# 1. 首次全量备份（带 gzip 压缩 + 生成快照）
tar czg /var/backup/site.snar -f /var/backup/site-full.tar.gz /var/www

# 2. 生成校验和
sha256sum /var/backup/site-full.tar.gz > /var/backup/site-full.tar.gz.sha256

# 3. 几天后做增量备份（只打包变化的文件）
tar czg /var/backup/site.snar -f /var/backup/site-inc-$(date +%F).tar.gz /var/www

# 4. 恢复前校验
sha256sum -c /var/backup/site-full.tar.gz.sha256
tar xzf /var/backup/site-full.tar.gz -C /tmp/restore
```

### 场景二：大文件分卷压缩后跨机器传输

```shell
# 1. 大目录打包 + zstd 压缩 + 分卷 1GB
tar cf - /data | zstd -T0 | split -b 1G -d -a 3 - /tmp/data.tar.zst.part

# 2. 分卷传到目标机器
scp /tmp/data.tar.zst.part* user@target:/backup/

# 3. 目标机拼回 + 解压
ssh user@target 'cat /backup/data.tar.zst.part* | zstd -d | tar xf - -C /restore'
```

## 最佳实践与踩坑记录

### 最佳实践

1. 打包用 `tar czf` 解包用 `tar xzf`，形成肌肉记忆，别每次查参数
2. 备份重要目录用 tar 加 -p 保留权限，配置文件权限丢了很麻烦
3. 大文件/大量文件优先 zstd，速度压缩率兼得且支持多线程
4. 备份一定要带 sha256 校验和，恢复前先校验
5. 生产备份用「日增量 + 周全量」策略，别每次全量浪费空间

### 踩坑记录

```text
坑 1：解包时覆盖了现有文件
结论：tar xzf 直接解到当前目录，同名文件被覆盖。
原因：tar 解包默认覆盖，没做路径隔离。
解法：先 tar tzf 看内容，再用 -C 解到独立目录，确认后再合并。

坑 2：分卷文件顺序错了解不开
结论：合并分卷后 tar 报错，解压失败。
原因：cat part* 按字典序拼接，part10 会排在 part2 前面。
解法：split 时用 -a 补零保证等长后缀，或按数字顺序明确拼接。

坑 3：用 tar 打包时把绝对路径打进去
结论：解包时文件被恢复到 /etc、/var 等原路径，覆盖系统文件。
原因：打包命令写了绝对路径（tar czf x.tar.gz /etc）。
解法：打包用相对路径（先 cd 到目标目录），或解包时用 -C 控制目标。

坑 4：gzip 压缩日志导致日志文件「消失」
结论：gzip big.log 后原文件没了，只剩 big.log.gz。
原因：gzip 默认压缩后删除原文件。
解法：要保留原文件用 gzip -k，或 gzip -c big.log > big.log.gz。

坑 5：zip 跨平台传输中文文件名乱码
结论：Linux 上 zip 打包的中文文件名，Windows 解压后乱码。
原因：zip 默认不记录 UTF-8 编码，Windows 按本地编码解析。
解法：用 unzip -O UTF-8 解压，或打包时用带 UTF-8 标志的工具（7z）。
```
