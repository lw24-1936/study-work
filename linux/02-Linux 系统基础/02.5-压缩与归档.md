## 概述

归档和压缩是两件事：归档（tar）把多个文件打包成一个文件，压缩（gzip/xz/zstd 等）把数据体积变小。Linux 习惯「先 tar 归档、再压缩」，所以常见 .tar.gz、.tar.xz 后缀。选压缩工具是在「压缩率、速度、CPU 消耗」之间权衡：xz 最省空间但最慢，gzip 均衡，zstd 又快压缩率又高（现代首选），zip 主要是和 Windows 互传用。

```text
归档 vs 压缩：
1. 归档 tar —— 只打包不压缩，把多文件合并成一个 .tar，保持目录结构
2. 压缩 gzip/xz/zstd —— 只压单个文件，所以要先 tar 再压
3. 组合后缀 —— .tar.gz（tar+gzip）、.tar.xz（tar+xz）、.tar.zst（tar+zstd）
4. 选型 —— 追求速度用 zstd，追求体积用 xz，通用兼容用 gzip，跨平台用 zip
5. zip 例外 —— zip 把「归档 + 压缩」合在一个命令里做，所以它同时是归档工具和压缩工具
```

## 核心概念

1. **归档工具 tar**：创建（-c）、解包（-x）、查看（-t），配合 -f 指定文件、-p 保留权限；现代 tar 能直接调压缩器（-z gzip / -j bzip2 / -J xz / --zstd）。
2. **压缩工具对比**：gzip 均衡、bzip2 压缩率高但慢（已过时）、xz 压缩率最高最慢、zstd 压缩率接近 xz 且快、支持多线程（首选）、zip 跨平台互传。
3. **分卷**：tar 打包后 split -b 切成固定大小文件，方便存储/传输，恢复时 cat 按顺序拼回。
4. **增量备份**：tar -g 快照文件实现「首次全量 + 之后只备变化文件」，rsync 按差异块增量同步。
5. **归档校验**：哈希（sha256sum）+ 归档自检（gzip -t / tar tf）+ 恢复后抽查三层。
6. **压缩器全景与选型**：现代 Linux 的压缩器按「速度-压缩率」排成一条光谱：lz4（最快、压得最少）→ zstd --fast → zstd → gzip → bzip2 → xz（最慢、压得最小）；7z 走 LZMA2 + 多线程 + 加密一体，lzip 用 LZMA 但容器更简单、带 CRC、原生支持分卷，brotli 用内置字典专攻 Web 文本，compress(.Z) 是 1980 年代 LZW 历史格式。
7. **tar 参数族**：除 c/x/t + f 外还有一整套维护与过滤参数——追加（-r）、只追更新（-u）、删成员（--delete）、拼接归档（-A）；过滤（--exclude/--exclude-from/--exclude-vcs）、切目录（-C）、改成员名（--transform）、剥目录层（--strip-components）、不跨挂载点（--one-file-system）、稀疏（--sparse）、数字属主（--numeric-owner）、跟随软链（-h）、保权限（-p）、保 atime（--atime-preserve）、写后校验（-W）、进度（--checkpoint）、多卷（-M/-L）。
8. **其它归档格式 cpio/ar**：cpio 把「读文件列表」与「打包」拆开，是 RPM 的原生格式（rpm2cpio x.rpm | cpio -idmv），RHEL 系 initramfs 也是 cpio 归档；ar 是更早的静态库/包归档格式，.deb 就是 ar 归档（内含 debian-binary + control.tar + data.tar）；bsdtar/libarchive 一套代码同时读 tar/cpio/zip/7z/iso/rpm。
9. **增量备份语义**：tar -g/--listed-incremental 用快照文件记录每个文件的 mtime/size/inode，快照为空是 0 级（全量）、有快照是 1 级（只备自快照以来变过的和新增的）；恢复必须按 0→1→2 顺序解包；它只记「新增/修改」不记「删除」。
10. **校验与完整性**：md5sum/sha256sum 出清单、sha256sum -c 逐条比对、单文件自检（gzip -t / xz -t / zstd --test / bzip2 -t）、归档列表自检（tar tf）、恢复前抽检。哈希只能防意外损坏，防篡改要靠 gpg 签名。
11. **跨平台与中文编码**：zip 条目名默认按创建时的本地编码存，检测到 UTF-8 才置 EFS 标志位；Linux 写 UTF-8、Windows 按 GBK 读就乱码，Windows 写 GBK、Linux 按 UTF-8 读也乱码。修法：unzip 加 -I GBK（Unix 主机归档）/ -O CP936（DOS-Windows 主机归档），兜底 iconv 改名。
12. **压缩炸弹与路径穿越**：压缩炸弹（decompression bomb）用超高压缩比数据堆出「几 KB 包解压成几十 GB」，解压时撑爆磁盘；路径穿越是归档成员名带 ../ 或绝对路径，解包时写到目标目录之外覆盖系统文件。防御靠「解包前先看清单 + 看待解压体积」。
13. **logrotate 压缩**：logrotate 支持 compresscmd/compressoptions/uncompresscmd 换压缩器（可直接指定 zstd），delaycompress 避免压到正在写的日志，copytruncate 适配不会重开句柄的程序，su 指定轮转文件属主，size 按体积触发。
14. **流式压缩**：不落中间 .tar，「tar cf - dir | gzip」直接把归档流喂给压缩器，省一次 GB 级写盘和一次读回；解包侧对应 tar xf - 从 stdin 读。
15. **多线程压缩的语义**：pigz/xz -T0/zstd -T0 都是把输入切块并行压缩再拼接——zstd 块大、压缩率损失极小，xz 的 -T 会限制每块字典大小、可能比单线程 -9 略大，pigz 与 gzip -6 基本持平；小文件用多线程可能因线程开销反而更慢。
16. **归档格式识别**：file 只认魔数不认后缀——.tar.gz 实际是 gzip 流（file 报 gzip compressed data），要再解一层才知道里面是 tar；.tar.zst 报 Zstandard compressed data、.tar.xz 报 XZ compressed data；.deb 报 Debian binary package、.rpm 报 RPM v3.0 bin。解不开先 file，别信后缀。
17. **Red Hat 系差异**：RHEL/CentOS/Rocky 默认装 gzip/xz/bzip2/zstd/cpio，7z（p7zip）要额外装；RHEL 9 起 rpm payload 默认 zstd（之前是 xz）；logrotate 在 /etc/logrotate.conf + /etc/logrotate.d/，SELinux enforcing 下新目录要用 restorecon -Rv 修上下文。
18. **备份策略与压缩的分层**：全量（每次都完整备份，恢复最快、空间最费）、差异（备自上次全量以来变化的，介于两者）、增量（只备自上次任意备份以来变化的，最省空间、恢复链最长）；压缩选型按数据冷热分层——热数据 zstd/lz4（解压快）、冷数据 xz -9（体积最小）、已压缩媒体只 tar 不压。

```text
压缩器选型速查（大致按速度从快到慢、压缩率从低到高）：
1. lz4 —— 速度 GB/s 级、压缩率最低，适合实时/热数据与内存页压缩；本机未安装
2. zstd --fast —— 很快、压缩率仍优于 gzip，在线日志落盘（journald 默认 zstd）常用
3. zstd 默认 -3 —— 速度是 gzip 的数倍、压得更小、原生多线程，系统归档默认首选
4. gzip —— 速度压缩率均衡、兼容性最好（任何 Unix 都有），跨系统交互仍常用
5. bzip2 —— 压缩率略高于 gzip、解压慢，已被 xz/zstd 取代，只见于老 .tar.bz2
6. xz（LZMA2）—— 压缩率最高、最慢、吃内存，冷数据长期归档与发行版镜像/包用
7. 7z —— LZMA2 + 多线程 + 分卷 + 加密一体，Windows 互传与超高压缩率；本机未安装
8. lzip —— LZMA 算法、容器极简且带 CRC、支持 .lz 分卷，长期归档/介质存储；本机未安装
9. brotli —— 面向 Web 文本（内置字典），HTML/CSS/JS 比 gzip 小约 20%；本机未安装
10. compress(.Z) —— 1980 年代 LZW 历史格式，现代发行版多已不带，仅解老归档用
```

```text
tar 参数族分组记忆：
1. 归档维护 —— r 追加到尾部、u 只追加更新的、--delete 删成员、A 拼接另一个 tar
2. 成员过滤 —— --exclude=模式、--exclude-from=文件、--exclude-vcs（跳过 .git/.svn 等）
3. 目录与命名 —— C 先切目录再打包、--transform 改写成员名、--strip-components=N 解包剥 N 层
4. 元数据保真 —— p 保权限、--same-owner/--no-same-owner 属主、--numeric-owner 存数字 uid/gid
5. 跟随链接 —— h 打包时跟随软链（默认存链接本身）、L 同上、--hard-dereference 硬链解引用
6. 特殊文件 —— --sparse 稀疏文件、--one-file-system 不跨挂载点、--atime-preserve 回写 atime
7. 完整性与进度 —— W 写后逐块校验、--checkpoint[=N] 每 N 条打一次进度
8. 多卷与流 —— M 多卷、L N 每卷 N KB、f - 写到 stdout（配合管道流式压缩）
9. 只解指定成员 —— tar xf a.tar 成员名、--wildcards 让成员名支持通配、--occurrence=N 只取第 N 个同名成员
```

```text
cpio 与 ar（RPM/DEB 的底座）：
1. cpio 三种模式 —— -o 从 stdin 读文件列表打包、-i 解包、-p 直接复制（pass-through）
2. 解 rpm —— rpm2cpio pkg.rpm | cpio -idmv（-d 建目录、-i 解包、-m 保 mtime、-v 打印）
3. 看 rpm 内容 —— rpm2cpio pkg.rpm | cpio -t（不解只列）
4. initramfs —— RHEL 系 /boot/initramfs-*.img 是 cpio（可能再套 gzip/zstd），file 认成 cpio archive
5. ar —— ar t x.deb 列成员（debian-binary / control.tar.* / data.tar.*），ar x 解出
6. 选择 —— 归档/备份用 tar，解发行版包用 cpio，看包结构用 ar，跨格式读用 bsdtar
```

```text
增量备份两套实现：
1. tar --listed-incremental（-g 快照）—— 0 级全量、1 级增量、恢复按序解；不记删除
2. rsync --link-dest —— 每次新目录 + 未变文件硬链接指向上一次，天然反映删除，目录即快照
3. 企业级去重 —— restic/borg 做内容分块去重 + 加密 + 增量，适合异地与云端备份
4. 快照文件最脆弱 —— .snar 丢了就没法继续增量，必须和数据分开存、一起备份
```

```text
校验的四个层次（从弱到强）：
1. 大小/条目数 —— tar tf | wc -l、ls -l，最弱，只防明显截断
2. 单文件自检 —— gzip -t / xz -t / zstd --test / bzip2 -t，验压缩流 CRC 完整性
3. 哈希清单 —— sha256sum 生成、sha256sum -c 校验，能抓字节翻转/截断，防不了篡改
4. 数字签名 —— gpg --detach-sign + gpg --verify，防篡改；密钥管理是前提
```

```text
压缩炸弹与路径穿越的防御：
1. 先看清单 —— tar tvf / unzip -l / rpm2cpio | cpio -t，别对来路不明的包直接解
2. 看待解压体积 —— gzip -l 报 uncompressed size 与 ratio、unzip -l 报 Length 总和
3. 比值告警 —— 正常文本 3~10 倍，几百倍以上基本是炸弹
4. 路径穿越 —— 成员名含 ../ 或 / 开头；GNU tar 默认剥离前导 /，并拒绝含 .. 的成员
5. 危险成员类型 —— 符号链接指向 /etc/passwd 再写文件（tar 有防护但仍要升级版本）
6. 降权解包 —— 不用 root 解包，必须 root 时加 --no-same-owner + -C 到独立目录
```

```text
logrotate 压缩相关指令：
1. compress —— 开启压缩（默认调 gzip）
2. compresscmd / uncompresscmd —— 换成 /bin/zstd 与 /bin/unzstd
3. compressoptions —— 传给压缩器的参数，如 -q 或 -19
4. compressext —— 压缩后缀，如 .zst
5. delaycompress —— 最近一次不压，下一轮再压（配合还在写的程序）
6. copytruncate —— 复制日志再清空原文件，适配不会重开句柄的程序，会丢窗口期日志
7. su user group —— 轮转后文件属主，避免日志跑到 root 名下
8. maxage / size —— 超龄清理、按体积触发轮转
```

```text
归档格式识别（file 报的魔数 vs 真实含义）：
1. .tar —— POSIX tar archive，直接 tar tf 可读
2. .tar.gz / .tgz —— gzip compressed data，外层 gzip，要解一层才是 tar
3. .tar.zst —— Zstandard compressed data，zstd -d 后是 tar
4. .tar.xz —— XZ compressed data，xz -d 后是 tar
5. .zip —— Zip archive data，归档压缩一体，unzip -l 直接看
6. .deb —— Debian binary package，其实是 ar 归档
7. .rpm —— RPM v3.0 bin，payload 是 cpio + 压缩
8. 后缀骗人 —— 改名不改内容，先 file 再决定用哪个命令解
```

```text
Red Hat 系与 Debian 系在压缩/归档上的差异：
1. 默认工具 —— RHEL 系默认 gzip/xz/bzip2/zstd/cpio/ar；7z 属 p7zip 需额外装
2. 包 payload —— RHEL 9+ rpm 用 zstd，RHEL 8 及以前多用 xz；Debian 系 .deb 内 data.tar 新版本也用 zstd
3. 解包命令 —— rpm2cpio + cpio（RHEL），dpkg-deb -x/-I/-c（Debian）
4. logrotate —— 两边都在 /etc/logrotate.conf + /etc/logrotate.d/，但随包发布的配置内容不同
5. SELinux —— RHEL 系 restoring 上下文用 restorecon -Rv，否则服务读不到解出来的文件
```

```text
备份策略与压缩分层：
1. 全量 —— 每次都完整备份，恢复最快、空间最费；适合关键配置与小数据
2. 差异 —— 备自上次全量以来的变化，介于全量与增量之间，恢复只需两份
3. 增量 —— 只备自上次任意备份以来的变化，最省空间、恢复链最长最脆弱
4. 冷热分层 —— 热数据 zstd/lz4（解压快）、冷数据 xz -9（体积最小）、已压缩媒体只 tar 不压
5. 3-2-1 —— 3 份副本、2 种介质、1 份异地；压缩只是省空间的辅助，不是策略本身
```

```text
流式压缩与多线程的语义：
1. 流式 —— tar cf - dir | zstd -T0 -o - > dir.tar.zst，省掉中间 tar 落盘
2. 解流 —— zstd -dc dir.tar.zst | tar xf - -C /restore
3. 多线程分块 —— pigz/xz -T/zstd -T 都是切块并行后拼接，块边界处压缩率略降
4. 线程上限 —— -T0 用满所有核，-T4 限 4 线程；小文件多线程可能更慢（线程开销）
5. 进度条 —— pv 夹在管道里看吞吐（本机未装，用 --checkpoint 或 --progress 替代）
```

```text
压缩前的判断：能压还是别压
1. 文本类（日志/源码/CSV/JSON/SQL）—— 压缩比分高，必压
2. 已压缩媒体（jpg/png/mp4/mp3/zip/gz）—— 冗余已消除，只 tar 不压（tar cf）
3. 随机/加密数据（密钥/密文/已加密备份）—— 熵最大无重复，压了更大
4. 稀疏文件 —— 加 --sparse 别让空洞变成实数据
5. 数据库文件 —— 直接压易不一致，先做逻辑导出或文件系统快照再压
```

```text
跨平台中文名乱码的成因与修复：
1. 成因 —— zip 条目名按创建端本地编码存，Linux UTF-8 与 Windows GBK 互读就乱
2. 判主机 —— zipinfo -v 看 host；Unix 归档 unzip -I、DOS/Windows 归档 unzip -O
3. Linux 修 —— unzip -I GBK x.zip（Unix 主机）或 unzip -O CP936 x.zip（Windows 主机）
4. 打包侧 —— 让 zip 按 UTF-8 存名字（部分版本 zip -UN=UTF8，或改用 7z/bsdtar 打包）
5. 兜底 —— iconv -f GBK -t UTF-8 批量改名，或用 convmv/midnight commander 处理
6. tar 一般没这问题 —— tar 存原始字节，同名文件在两端都能认，乱码主要是 zip
```

```text
压缩的 CPU 与 IO 权衡：
1. CPU 富余、磁盘/带宽紧张 —— 上高档（xz -9、zstd -19），省 IO
2. CPU 紧张、要低延迟 —— 降档（zstd --fast、lz4、gzip -1），CPU 换时间
3. 多核机器 —— 优先 zstd -T0 / pigz，别用单线程 bzip2/xz 默认档
4. 管道场景 —— 压缩器常和 tar/split/ssh 串成管道，瓶颈通常在磁盘或网络而非 CPU
5. 内存 —— xz 高压缩级别字典大（-9 单线程可吃数百 MB），小内存机器要降档或限字典
```

```text
按场景选工具：
1. 服务器日常归档 —— tar --zstd -cf（快、压得小、多线程）
2. 冷数据长期保存 —— tar -cJf 或 tar --zstd -19（体积优先，解压次数少）
3. 日志落盘/轮转 —— zstd 或 logrotate compresscmd=/bin/zstd
4. 与 Windows 互传 —— zip（必要时 7z），注意中文名编码
5. 发行版包 —— .deb 用 dpkg-deb、.rpm 用 rpm2cpio + cpio，别硬解
6. 网络传输前 —— 先压再 split/rsync，省带宽；但 ssh 已有压缩时再压收益有限
7. 备份 —— tar -g 做简单增量，rsync --link-dest 做快照，restic/borg 做去重加密
```

```text
压缩工具对比：
1. gzip —— 均衡，.gz，兼容最好，默认选项
2. bzip2 —— 压缩率高、速度慢，.bz2，已被 xz/zstd 取代
3. xz —— 压缩率最高、最慢，.xz，追求体积用
4. zstd —— 压缩率高且快、支持多线程，.zst，现代首选
5. zip —— 跨平台，.zip，和 Windows 互传用
```

```text
发行版包格式也靠「归档 + 压缩」（Red Hat 系差异）：
1. .deb（Debian/Ubuntu）—— ar 归档，内含 control.tar + data.tar，data.tar 用 xz/zstd 压缩
2. .rpm（Red Hat/CentOS/Rocky）—— cpio 归档 + 压缩 payload，现代 RHEL 用 xz/zstd
3. 查看：deb 用 dpkg-deb -I/-c，rpm 用 rpm2cpio x.rpm | cpio -t；两者都是「归档 + 压缩」在企业发行版里的落地
4. file 能识别：file x.deb 显示 Debian binary package、file x.rpm 显示 RPM v3.0 bin
```

下面按「是什么 → 为什么 → 怎么用 → 边界/易错点」把每个工具和概念展开。

### tar 归档

是什么：tar（tape archive）是归档工具，把多个文件/目录连同目录结构和元数据（权限、属主、时间戳）串成一个 .tar 文件，本身不压缩。为什么要先 tar 再压：gzip/xz/zstd 都是「单文件压缩器」，只能压一个文件，而目录是一堆文件，所以先用 tar 合成单流、再交给压缩器。怎么用：c 创建、x 解包、t 查看，f 指定文件，z/j/J/--zstd 直接接压缩器。

```shell
# 打包 + 压缩（各压缩器对应的选项）
tar czf app.tar.gz  app/          # -z gzip
tar cjf app.tar.bz2 app/          # -j bzip2
tar cJf app.tar.xz  app/          # -J xz
tar --zstd -cf app.tar.zst app/   # --zstd

# 解包 / 查看 / 只解部分
tar xzf app.tar.gz -C /tmp/restore        # 解到指定目录
tar tzf app.tar.gz                        # 只看文件列表
tar tzf app.tar.gz 'app/*.conf'           # 只看匹配的文件
tar xzf app.tar.gz -C /tmp app/a.txt      # 只解出单个文件

# 排除、相对路径、保留权限
tar czf backup.tar.gz --exclude='*.log' --exclude='.git' app/
tar -C /var/www -czf site.tar.gz .        # 用相对路径打包（见踩坑 3）
tar czpf etc-backup.tar.gz /etc           # p 保留权限位
```

```text
tar 要点：
1. 归档不压缩 —— .tar 大小约等于所有文件之和 + 头部开销，甚至略大
2. 选项组合记忆 —— czf 创建+xz 压缩+文件，xzf 解包，tzf 查看
3. p 保留权限 —— 备份配置文件必须加，否则解包后 setuid/权限位丢失
4. 绝对路径是坑 —— 打包写了 /etc 这种绝对路径，解包会回到原路径覆盖系统文件
```

### gzip

是什么：DEFLATE 算法（LZ77 + Huffman）的单文件压缩器，GNU 出品，后缀 .gz。为什么常用：速度与压缩率均衡、几乎无处不在、所有工具都兼容。怎么用：`gzip 文件` 压缩后默认删除原文件，-k 保留，-c 输出到 stdout，-1~-9 控制压缩级别，-d/-t 解压/测试。

```shell
gzip big.log              # 压缩（默认删除原文件，见踩坑 4）
gzip -k big.log           # 压缩但保留原文件
gzip -c big.log > big.log.gz    # 输出到 stdout，不删原文件
gzip -1 big.log           # 最快、体积较大
gzip -9 big.log           # 最慢、体积最小
gzip -d big.log.gz        # 解压
gunzip big.log.gz         # 同上
zcat big.log.gz | grep ERROR    # 不解压直接读内容
gzip -t big.log.gz && echo OK   # 只测完整性不落盘
```

```text
gzip 要点：
1. 单文件 —— 只能压一个文件，多文件要先 tar
2. 默认删原文件 —— 保留用 -k 或 -c
3. -1~-9 —— 级别越高越慢越小，日志归档常用 -6 平衡
4. 已压缩数据再压无收益 —— jpg/mp4/zip 再 gzip 体积几乎不变
```

### bzip2

是什么：BWT（Burrows-Wheeler Transform）+ 游程编码的单文件压缩器，后缀 .bz2。为什么曾流行：压缩率比 gzip 高 10%~15%；为什么过时：解压慢（尤其比 gzip 慢一个数量级）、不支持多线程，被 xz/zstd 取代。怎么用：命令和 gzip 几乎同名同参数。

```shell
bzip2 big.log             # 压缩
bzip2 -k big.log          # 保留原文件
bzip2 -9 big.log          # 最高压缩率
bzip2 -d big.log.bz2      # 解压
bunzip2 big.log.bz2       # 同上
bzcat big.log.bz2 | less  # 不解压直接读
bzip2 -t big.log.bz2      # 测完整性
```

```text
bzip2 要点：
1. 压缩率高但慢 —— 尤其解压慢，大文件体验差
2. 不支持多线程 —— 多核机器上吃不满 CPU
3. 已被取代 —— 新数据别再用 bzip2，旧 .tar.bz2 仍需会解（tar cjf/xjf）
```

### xz

是什么：LZMA2 算法的单文件压缩器，后缀 .xz。为什么追求体积用它：压缩率在主流工具里最高，常把几 GB 的文本/日志压到几分之一。怎么用：命令同 gzip，额外支持 -T 多线程。

```shell
xz -9 big.log             # 最高压缩率（默认就是 -6）
xz -k big.log             # 保留原文件
xz -T0 big.log            # -T0 用满所有 CPU 核多线程压缩
xz -d big.log.xz          # 解压
unxz big.log.xz           # 同上
xzcat big.log.xz | grep ERROR   # 不解压直接读
xz -t big.log.xz          # 测完整性
tar cJf backup.tar.xz /data     # tar 的 -J 走 xz
```

```text
xz 要点：
1. 压缩率最高、速度最慢 —— 冷数据/归档用，实时任务慎用
2. -T 多线程 —— xz 5.2+ 支持 -T0，能缓解「慢」的问题
3. 内存消耗大 —— LZMA2 高压缩级别吃内存，低内存机器压大文件要留意
4. 内核镜像/发行版包多用 .xz —— 追求最小体积的场合
```

### zstd

是什么：Facebook 出品的 Zstandard 算法压缩器，后缀 .zst。为什么现代首选：压缩率接近 xz、速度却快一个数量级，且天然支持多线程、压缩级别跨度大（1~19 和 --fast 负级别）。怎么用：命令同 gzip，-T0 多线程，--fast 极快。

```shell
zstd big.log              # 默认级别 3，又快又小
zstd -19 big.log          # 高压缩率（接近 xz）
zstd --fast big.log       # 最快速度（牺牲压缩率）
zstd -T0 big.log          # 多线程用满 CPU
zstd -d big.log.zst       # 解压
unzstd big.log.zst        # 同上
zstdcat big.log.zst | less    # 不解压直接读
tar --zstd -cf backup.tar.zst /data   # tar 直接走 zstd
```

```text
zstd 要点：
1. 速度与体积兼得 —— 同体积下速度比 xz 快数倍，同速度下体积比 gzip 小
2. 多线程 —— -T0 吃满 CPU，大文件压缩耗时大幅下降
3. 级别跨度大 —— --fast（最快）到 -19（最狠），按场景调
4. 现代 Linux 生态默认 —— 内核、systemd、包管理器都在引入 zstd
```

### zip 与 unzip

是什么：Info-ZIP 的归档 + 压缩一体工具，后缀 .zip。为什么用它：跨平台，Windows/macOS 原生支持，Linux 与 Windows 互传文件用。和 tar 的区别：zip 一个命令同时完成归档和压缩，且每个文件独立压缩（坏一个不影响其余）。怎么用：-r 递归、-9 高压缩、-e 加密、unzip -d 指定目录、-l 查看。

```shell
zip -r app.zip app/            # 递归打包 + 压缩
zip -9 -r app.zip app/         # 最高压缩率
zip -r backup.zip app --exclude '*.log'   # 排除
unzip app.zip                  # 解压到当前目录
unzip app.zip -d /tmp/restore  # 解压到指定目录
unzip -l app.zip               # 只看列表不解压
unzip -o app.zip               # 覆盖已存在文件（默认会询问）
unzip -n app.zip               # 不覆盖已存在文件
unzip -O UTF-8 app.zip         # 中文文件名指定 UTF-8（见踩坑 5）
zipinfo app.zip                # 查看压缩详情
zip -e -r sec.zip app/         # 交互式设密码加密
```

```text
zip 要点：
1. 归档 + 压缩一体 —— 不需要先 tar，一个命令搞定
2. 每文件独立压缩 —— 单个文件损坏不影响其他文件解压，这是相对 tar 流的优势
3. 中文乱码 —— Linux zip 默认不记 UTF-8 编码，Windows 解压乱码，用 unzip -O
4. 密码是弱加密 —— zip -e 的 ZipCrypto 可被暴力破解，别用它保护敏感数据
```

### 分卷

是什么：把一个大的归档/压缩文件按固定大小切成多个小文件，便于存储（如刻盘/上传限制）和传输。为什么：单文件太大时某些介质（FAT32 单文件上限 4GB、邮件附件限制）装不下。怎么用：split 按字节切块、按顺序拼回；zip 自带 -s 分卷。

```shell
# 方法一：tar + split 切块
tar czf - /data | split -b 100M -d -a 3 - data.tar.gz.part
# 参数：-b 每块 100M，-d 数字后缀，-a 3 后缀 3 位，- 从 stdin 读

# 恢复：按顺序拼回再解压
cat data.tar.gz.part000 data.tar.gz.part001 > data.tar.gz
tar xzf data.tar.gz

# 方法二：zip 自带分卷（最小分卷 64KB）
zip -r -s 64m big.zip /data    # 切成多个 64MB 的 .z01/.z02/...zip
# 解压时只对最后一个 .zip 文件操作，其余分卷自动读取
```

```text
分卷要点：
1. 顺序不能乱 —— 分卷是字节流的切片，顺序错了解不开（见踩坑 2）
2. 用 -a 补零 —— split -a 3 生成 part000/part001，字典序才正确，否则 part10 排 part2 前
3. 只切不压 —— split 只是切字节，不压缩，配合 tar 管道边压边切
4. zip -s 最小 64KB —— 传 1k 会报 minimum split size is 64 KB
```

### 增量备份

是什么：首次做全量备份，之后只备份自上次以来变化的文件，大幅减少备份时间和空间。为什么：海量数据天天全量备份既不现实也浪费空间。怎么用：tar -g 快照文件记录状态，首次全量、后续增量；rsync 按差异块同步更高效。

```shell
# tar 快照增量：首次全量 + 后续增量
tar czg /var/backup/snap.snar -f full-$(date +%F).tar.gz /data   # 首次：全量 + 生成快照
tar czg /var/backup/snap.snar -f inc-$(date +%F).tar.gz /data    # 后续：只备变化的文件

# 恢复：按时间顺序解包（先全量、再逐个增量）
tar xzfg /var/backup/snap.snar full.tar.gz -C /restore
tar xzfg /var/backup/snap.snar inc.tar.gz -C /restore

# rsync 增量：只传差异块
rsync -avz --delete /data/ backup-server:/backup/data/
rsync -av --link-dest=/backup/yesterday /data/ /backup/today/    # 硬链接去重
```

```text
增量备份要点：
1. 快照文件是核心 —— .snar 记录文件状态，丢失快照就无法做下一次增量
2. 恢复顺序严格 —— 先全量后增量，增量文件不能跳着解
3. 增量链脆弱 —— 中间一份增量损坏，之后的增量都失效，所以关键数据要定期重做全量
4. rsync 比 tar -g 更稳 —— 按差异块同步、支持断点续传、不依赖快照文件
```

### 归档校验

是什么：验证备份文件在传输/存储过程中没损坏、没被篡改。为什么：备份的价值在「恢复时能解出来」，不校验的备份等于没有备份。怎么用：三层校验——哈希比对、归档自检、恢复后抽查。

```shell
# 1. 生成校验和（备份时）
sha256sum backup.tar.gz > backup.tar.gz.sha256

# 2. 校验（传输/恢复前）
sha256sum -c backup.tar.gz.sha256        # 输出 OK 才继续

# 3. 归档自检：压缩层 + 归档层
gzip -t backup.tar.gz && echo "压缩层 OK"
tar tzf backup.tar.gz > /dev/null && echo "归档层 OK"

# 4. 数字签名防篡改（校验和只能防损坏，防不了被替换）
gpg --detach-sign backup.tar.gz          # 生成 .sig 签名
gpg --verify backup.tar.gz.sig backup.tar.gz   # 验签

# 5. 恢复后抽查：解包后确认文件数/大小对得上
tar tzf backup.tar.gz | wc -l            # 归档内文件数
```

```text
归档校验要点：
1. sha256sum 防损坏 —— 传输中字节翻转/截断都能检出
2. 校验和防不了篡改 —— 攻击者改了文件顺便改校验和，需要 gpg 签名才防
3. 三层都要做 —— 哈希 + 自检 + 抽查，任何一层漏了都可能「恢复时才发现坏」
4. 校验和要分开存 —— .sha256 和备份文件放一起，一起损坏就白校验
```

## 工作原理

压缩的原理是消除数据冗余：重复模式用更短的编码代替（LZ77 找重复串、Huffman 给高频字节短码），所以「重复文本能压到千分之一、随机数据几乎压不动」。归档 tar 本身不压缩，它把多文件的目录结构 + 元数据串成一个流，再交给压缩器处理，这就是「先 tar 再压」的由来。分卷则是把压缩后的字节流按固定大小切块，恢复时按原顺序拼接，顺序错了字节流就断、解不开。

```text
压缩与归档的原理：
压缩 = 消除冗余（重复串 + 熵编码）→ 数据越规律压得越小，已压缩/随机数据几乎无收益
tar 归档 = 目录结构 + 元数据串成单流（不压缩）→ 再交给 gzip/xz/zstd 压
分卷 = 字节流按固定大小切块 → 恢复按原顺序 cat 拼回
```

各压缩算法的差异本质是「找重复 + 熵编码」的两步怎么实现、用什么字典窗口：

```text
各压缩算法核心：
1. gzip/DEFLATE —— LZ77 滑动窗口（32KB）+ Huffman 编码，窗口小所以快但压不狠
2. bzip2 —— BWT 块变换 + 游程编码 + Huffman，窗口可达 900KB，压得狠但变换慢
3. xz/LZMA2 —— 大字典（可达 GB 级）+ 区间编码，字典越大重复串匹配越长，体积最小但慢、吃内存
4. zstd/Zstandard —— LZ77 变体 + FSE（有限状态熵编码）+ 大窗口，熵编码比 Huffman 更快，速度体积双赢
5. zip —— 每个文件独立 DEFLATE，不像 tar 流整体压，所以坏一个文件不影响其余
```

压缩的两个边界：已压缩数据（jpg/mp4/zip/gz）冗余已被消除，再压几乎无收益甚至变大（要加压缩器自己的头部）；随机/加密数据熵最大、没有重复模式可压，压了也白压。

### 原理补充：级别、窗口、块与校验

```text
压缩级别到底在调什么（以 gzip -1/-6/-9 和 zstd -1/-19 为例）：
1. 匹配搜索深度 —— 级别越高，找重复串时搜索的范围越远、候选越多，压得更狠但更费 CPU
2. 不是「压缩率线性提升」—— 拐点很明显，本机实测 gzip -6 → -9 体积只降 0.5% 而耗时涨 2.5 倍
3. zstd 的级别跨度更大 —— 1~19 加 --fast 负级别（-1~-131072），能一路换到「近乎不压只用存」的档
4. xz 的级别还改字典 —— -9 用 64 MiB 字典，压缩率与内存同步上涨，小内存机器要 --memlimit
5. 实用建议 —— gzip 用默认 6；zstd 用 3（在线）/19（归档）；xz 用默认 6，只在体积优先时上 9
```

```text
字典窗口（dictionary / window）决定能匹配多远的重复：
1. gzip/DEFLATE —— 32 KiB 滑动窗口，只能记住最近 32 KiB，所以大文件里远处的重复匹配不到
2. bzip2 —— 900 KiB 块变换（-1~-9 对应 100~900 KiB），块内做 BWT，块越大越狠
3. xz/LZMA2 —— 字典可到 64 MiB 甚至更大，长距离重复能命中，所以体积最小、内存最贵
4. zstd —— 窗口跟级别走（默认可到几 MiB），还支持 --long=27 这类超长窗口（需解压方支持）
5. 结论 —— 「压缩率高低」本质上是「能看多远 + 熵编码效率」，不是玄学
```

```text
tar 是流式格式（这是它一切限制的根源）：
1. 顺序读写 —— tar 是「头 + 数据 + 头 + 数据…」的流，必须从头顺序读完才知道后面有什么
2. 不能随机取成员 —— 想从 10 GB 归档里拿一个文件，tar 也得把前面的数据读过去
3. 追加容易（-r）—— 尾部直接续写，不用重建；但改中间（--delete）要重写整个归档，代价大
4. 一处损坏影响后续 —— 流式格式没有每块的独立索引，大文件坏了可能后面都读不出来
5. zip/7z 的对照 —— 每个成员独立压缩 + 中央目录索引，能随机取、坏一个不影响其余，代价是压缩率略低
```

```text
多线程压缩为什么「压缩率略降但仍然划算」：
1. 分块 —— 输入按固定大小切成独立块，每块单独做字典匹配，块之间不共享历史
2. 拼接 —— 各块压完按序写进同一个容器（zstd/pigz 的帧格式天然支持多帧拼接）
3. 解码端透明 —— 解压方按帧顺序解即可，不需要知道压的时候开了几个线程
4. 代价来源 —— 块边界处的长距离重复匹配不到，块越小损失越大（本机 pigz vs gzip -6 差 0.02%）
5. 权衡 —— 多核机器上「快 5 倍、大 0.02%」几乎永远是赚的，除非追求极限体积
```

```text
完整性校验是怎么嵌进压缩格式的：
1. gzip —— 尾部有 CRC32 + 原始长度（ISIZE），gzip -t 就是重算 CRC32 比对
2. bzip2 —— 每个块带 CRC，-t 逐块验
3. xz —— 每个块带 CRC32/CRC64 与 SHA-256 可选项，容器还带索引与索引校验
4. zstd —— 每帧默认带 xxHash64 校验，可用 --no-check 关掉（不推荐）
5. tar 层 —— tar 本身没有校验和（老 POSIX tar 只有 512 字节头的 checksum 校验头部完整性），
   所以「tar 内容损坏」只能靠外层的哈希清单或 gpg 签名来发现
6. 结论 —— gzip -t 只能证明「压缩流没坏」，证明不了「归档里的文件正确」；两层都要查
```

## 常用命令与配置

```shell
# 打包 + 压缩（gzip）/ 解包 / 只看不解包
tar czf backup.tar.gz /var/www /etc/nginx
tar xzf backup.tar.gz -C /tmp/restore
tar tzf backup.tar.gz

# 保留权限地打包（备份配置文件时重要）
tar cpzf etc-backup.tar.gz /etc
```

### tar 参数族：追加 / 更新 / 删除 / 拼接

```text
tar 参数族补充（按用途分组）：
1. 归档维护 —— r 追加尾部、u 只追加更新的、--delete 删成员、A 拼接另一个 tar
2. 成员过滤 —— --exclude=模式、--exclude-from=清单文件、--exclude-vcs（自动跳过 .git/.svn/.hg/CVS）
3. 目录切换 —— -C 先切目录再处理后续参数（打包/解包都可用，可多次出现）
4. 成员改名 —— --transform='s,旧,新,' 打包时改写成员名（支持 s/y/正则标志）
5. 剥目录层 —— --strip-components=N 解包时去掉前 N 层路径
6. 不跨挂载点 —— --one-file-system 只备份同一文件系统，不跟着进 /proc、/sys、其他挂载点
7. 稀疏文件 —— --sparse（-S）用空洞表示，避免稀疏文件被打成满体积
8. 属主处理 —— --numeric-owner 存数字 uid/gid（跨机器恢复更稳）、--same-owner/--no-same-owner 解包时是否还原属主
9. 链接处理 —— -h（--dereference）打包时跟随软链存内容、--hard-dereference 硬链解引用
10. 时间戳保真 —— -p 保权限、--atime-preserve 打包后把源文件 atime 改回去
11. 完整性 —— -W（--verify）写完立刻回读校验归档
12. 进度 —— --checkpoint[=N] 每处理 N 条打一次、--checkpoint-action=echo/dot 控制动作
13. 只处理指定成员 —— --wildcards 让成员名参数支持通配、--occurrence=N 只处理第 N 个同名成员
14. 多卷 —— -M 多卷模式、-L N 每卷 N KB（先把 tar 切卷，再用 -M 逐个喂）
```

### 校验与完整性（实测）

```shell
# 生成 + 校验哈希清单
sha256sum backup.tar.gz > backup.tar.gz.sha256
sha256sum -c backup.tar.gz.sha256        # 输出 文件名: OK / FAILED
sha256sum -c --quiet backup.tar.gz.sha256 # 只打印有问题的条目

tar tf backup.tar.gz > /dev/null && echo "归档层 OK"

# 看一眼压缩比与原始大小（gzip -l 直接报 ratio 和 uncompressed size）
gzip -l backup.tar.gz

# 防篡改：签名（校验和防不了「改文件顺手改校验和」）
gpg --detach-sign --armor backup.tar.gz
gpg --verify backup.tar.gz.asc backup.tar.gz

# 保持可恢复：解压后与原目录比对
diff -r /data /restore/data && echo "内容一致"
```

### 增量备份（实测）


```text
1. 只备变化 —— 未改动的 b.txt、keep.log 在 1 级里根本不出现
2. 不记删除 —— 移走 b.txt 后再增量，归档里只剩目录条目，恢复后 b.txt 依然在（来自 0 级）
```

```text
1. rsync --link-dest —— 每次生成一个新目录，未变文件硬链接指向昨天的目录（du 不重复占空间），
```

### logrotate 深入（用 zstd 压缩、copytruncate、delaycompress）

```text
/etc/logrotate.d/myapp —— 完整一点的轮转规则（用 zstd 压缩）：
/var/log/myapp/*.log {
    daily                 # 触发条件之一：按天（还有 weekly/monthly/hourly 与 size）
    rotate 7              # 保留 7 份历史
    compress              # 轮转后压缩旧日志
    compresscmd /usr/bin/zstd      # 换掉默认的 gzip
    uncompresscmd /usr/bin/unzstd  # 读旧日志时用哪个解压器
    compressext .zst               # 压缩后缀，改掉默认的 .gz
    compressoptions -q             # 传给压缩器的参数（zstd -q 安静模式，或 -19 高压缩）
    delaycompress         # 最近一次不压，等下一轮再压（避免压到还在写的文件）
    copytruncate          # 复制日志后清空原文件，适配不会重开句柄的程序
    create 0640 myapp myapp        # 轮转后新建日志文件的权限与属主
    su myapp myapp        # 以指定用户身份处理，避免日志落到 root 名下
    maxage 30             # 超过 30 天的归档直接删
    size 100M             # 体积触发（与 daily 同时写时，满足任一即轮转）
    missingok             # 文件不存在也不报错
    notifempty            # 空文件不轮转
    postrotate            # 轮转后执行（通常让服务重开日志句柄）
        systemctl reload myapp >/dev/null 2>&1 || true
    endscript
}
```

```shell

# 真跑一次 + verbose

# 指定状态文件（默认 /var/lib/logrotate/status，测试时别污染系统状态）

# 强制轮转（忽略 daily 时间条件）

```

```text
zstd -dc app.log.1.zst   → ERROR one / WARN two / INFO three（内容完整还原）
```

```text
copytruncate vs create（最容易选错的一对）：
1. create —— 轮转时把 app.log 改名，再新建一个同名空文件；程序必须能感知重开句柄
   （SIGHUP 或 systemctl reload），否则会继续往已被改名的旧 inode 里写
2. copytruncate —— 先 cp 一份再 truncate 原文件；程序不用重开句柄，但「复制完到清空之间」
   写入的日志会丢，且大日志复制会短暂占双份空间
3. 选 create 的场合 —— 支持重开句柄的服务（nginx、rsyslog 等），不丢日志
4. 选 copytruncate 的场合 —— 不支持重开的程序（部分 Java 应用、老服务），宁可丢极少日志
5. delaycompress 的作用 —— 刚轮转出来的 app.log.1 可能还有进程持有句柄在写，
   延后一轮再压，避免「压缩了还在写的文件」导致内容截断
6. compresscmd 的兼容 —— 换成 zstd 时必须同时改 uncompresscmd，否则 zcat/less 读旧日志会失败
```

```text
logrotate 其它容易踩的点：
1. su 与 create 配合 —— 不写 su，轮转后文件属主可能变成 root，服务再写就 Permission denied
2. maxage 与 rotate 是两套逻辑 —— rotate 按份数保留，maxage 按天数删除，别以为写了 rotate 就不会超龄
3. include /etc/logrotate.d —— 主配置最后 include 目录，规则冲突时后读的覆盖先读的
4. 状态文件 —— /var/lib/logrotate/status 记录「上次轮转时间」，删掉它会让所有规则立即重新轮转
5. logrotate 本身不压缩正在被写的日志 —— 它是先改名/复制，再对「旧文件」调压缩器
6. SELinux —— RHEL 系轮转新建的文件上下文可能不对，服务读不到，需 restorecon -Rv /var/log/<svc>
```

```shell
tar czg /var/backup/site.snar -f /var/backup/site-full.tar.gz /var/www

# 2. 生成校验和
sha256sum /var/backup/site-full.tar.gz > /var/backup/site-full.tar.gz.sha256

# 3. 几天后做增量备份（只打包变化的文件）
tar czg /var/backup/site.snar -f /var/backup/site-inc-$(date +%F).tar.gz /var/www

# 4. 恢复前校验
sha256sum -c /var/backup/site-full.tar.gz.sha256
tar xzf /var/backup/site-full.tar.gz -C /tmp/restore
```

### 场景二：大文件分卷压缩后跨机器传输

```shell
# 1. 大目录打包 + zstd 压缩 + 分卷 1GB

# 2. 分卷传到目标机器

# 3. 目标机拼回 + 解压

```

### 场景三：日志归档 + 定时清理（logrotate 压缩旧日志）

```shell
# 1. 服务日志目录当前状态
ls -lh /var/log/myapp/
# myapp.log         120M
# myapp.log.1        0B

# 2. 写一条 logrotate 规则：按天轮转 + gzip 压缩 + 保留 7 份
cat <<'EOF' > /etc/logrotate.d/myapp
/var/log/myapp/*.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    create 0640 myapp myapp
}
EOF

# 3. 手动触发一次轮转验证
logrotate -vf /etc/logrotate.d/myapp

# 4. 轮转后旧日志被 gzip 压缩

# myapp.log         0B
# myapp.log.1.gz    3.2M    <- 旧日志被压缩，节省 96% 空间

# 5. 需要看历史日志时不解压直接读
zcat /var/log/myapp/myapp.log.1.gz | grep ERROR
```

## 性能与调优

```text
压缩性能调优：
1. zstd 多线程 —— zstd -T0 用满 CPU，大文件压缩快数倍；tar --zstd 直接走 zstd
2. 压缩级别取舍 —— gzip -1 快但大、-9 小但慢，日志归档用 -6 平衡，冷数据用 xz -9
3. 别压已压缩数据 —— 图片/视频/压缩包/随机数据再压无收益还费 CPU，直接打包不压
4. 压缩 vs IO 权衡 —— 网络慢、CPU 闲时多压缩；网络快、CPU 忙时轻压缩或只 tar
5. 增量而非全量 —— 海量数据用 tar -g 快照增量或 rsync，别每次全量压
6. 压缩级别基准 —— 同样的数据，zstd -3 速度是 gzip -9 的数倍且体积相当，冷归档才用 xz -9
7. 清理包缓存 —— apt 缓存在 /var/cache/apt（apt clean 清理，Debian/Ubuntu），dnf 缓存在 /var/cache/dnf（dnf clean all 清理，Red Hat 系），都是可安全回收的空间
```

```text
常见数据选型速查：
1. 文本/日志/源码 —— 可压缩性极好，压！gzip/zstd 都能压到 1/10 甚至更小
2. 数据库备份 —— 文本 dump 可压（用 zstd），二进制库文件（InnoDB 数据文件）基本压不动
3. 图片/音视频/office —— 已是压缩格式，直接 tar 归档不压缩（-cJf 换成 -cf）
4. 传输大量小文件 —— tar 先打包再压比逐文件压高效（省掉每文件的头部开销）
```

```text
从这组数字能直接读出的结论：
1. zstd 默认档性价比碾压 —— 比 gzip -6 快约 16 倍，体积只有它的 1/3，日常归档没有理由再用 gzip
2. gzip -1 → -9 几乎白费 —— 体积只降 0.5%（4124976 → 4104924），耗时涨 2.5 倍，别指望调级别救体积
3. pigz 是 gzip 的纯加速 —— 同级别下体积与 gzip 基本一致（差 0.02%），耗时降到 1/5，多核机器应替换 gzip
4. xz 的体积优势是真的但要付时间 —— 8.3% vs zstd 的 14.9%，体积少 44% 但耗时是 zstd 的 56 倍
5. bzip2 已经没有位置 —— 体积不如 xz、速度不如 zstd/gzip，只在解老 .tar.bz2 时才会碰到
6. 语料决定结论 —— 这份语料含二进制，纯文本日志的 gzip 比通常在 8~12 倍，xz 能到 30 倍以上
```

```text
多线程压缩的真实语义（-T / pigz 到底快在哪）：
1. 原理 —— 把输入切成独立块并行压缩，最后按序拼接成一条合法压缩流
2. 代价 —— 块边界处字典被截断，压缩率比单线程略低（本机 pigz 比 gzip -6 大 0.02%，可忽略）
3. xz -T 的特殊性 —— 多线程模式每块字典受限，追求极限体积时才需要 -T1 -9
4. 小文件不进多线程 —— 几 MB 以下启动线程的开销可能超过收益，管道里别盲目加 -T0
5. 看线程数 —— nproc 决定 -T0 的上限；容器里 nproc 可能报的是宿主核数，要用 -T4 这类显式值限流
```

```text
流式压缩：省磁盘也省一次读写
1. 传统两步 —— tar 先落一个 10 GB 的 .tar（占 10 GB 磁盘），再 gzip 读一遍写 .tar.gz
2. 流式一步 —— tar cf - | zstd -T0 > x.tar.zst，中间流不落盘，磁盘峰值只有最终文件
3. 解压侧对应 —— zstd -dc x.tar.zst | tar xf - -C /restore
4. 加进度 —— pv 夹在管道中间看吞吐（本机未装 pv，可用 tar --checkpoint=1000 --checkpoint-action=echo）
5. 好处 —— 备份到远端时省一次落盘：tar cf - | zstd -T0 | ssh host 'cat > /backup/x.tar.zst'
```

```text
CPU 与磁盘带宽的取舍：
1. 磁盘是瓶颈（HDD/网络盘）—— 多花 CPU 换体积，xz -9 / zstd -19
2. CPU 是瓶颈（小机器、跑着业务）—— 降档或只 tar 不压，zstd --fast / lz4 / gzip -1
3. 内存要算进去 —— xz -9 单线程可吃数百 MB 字典，容器内存受限时用 --memlimit 或降档
4. 已压数据别压 —— jpg/mp4/zip/gz 再压体积几乎不变还白烧 CPU（tar cf 而非 czf）
5. 度量方法 —— time 包一层、/usr/bin/time -v 看 CPU 与峰值内存，别凭感觉
```

## 安全与权限

```text
归档安全要点：
1. 保留权限防提权 —— 备份/解包用 -p 保留权限位，防解包后文件权限丢失导致安全策略失效
2. 警惕路径穿越 —— 解包前先 tar tzf 看内容，防恶意归档解出 ../ 路径覆盖系统文件
3. 压缩炸弹 —— 小压缩包解出超大文件（zip bomb），解包前看解出大小、限制磁盘
4. 备份加密 —— 备份含敏感数据时先 tar 再 gpg/openssl 加密，别明文落盘或裸传
5. 校验防篡改 —— sha256 校验和防传输损坏，也防备份被静默篡改
6. zip 密码别当加密用 —— zip -e 的 ZipCrypto 弱加密可暴力破解，敏感数据用 gpg 或 7z AES-256
```

```shell
# 备份加密：tar + gpg 对称加密
tar czf - /data | gpg --symmetric --cipher-algo AES256 -o backup.tar.gz.gpg
# 解密恢复
gpg --decrypt backup.tar.gz.gpg | tar xzf - -C /restore

# 解包前检查路径（防路径穿越）
tar tzf suspicious.tar.gz | grep '\.\./'    # 出现 ../ 说明可疑

# 解包前预估大小（防压缩炸弹）
tar tzvf suspicious.tar.gz | awk '{sum += $3} END {print sum}'   # 累加解出后的总字节数
```

```text
# 实测结论
1. GNU tar 对 ../ 是「剥离 + 直接拒绝」两段防护，退出码 2，文件不会写到目标目录之外
2. 绝对路径同理 —— 打包时 tar 剥离前导 /，解包时不再还原（这就是那条 Removing leading / 警告）
3. 旧版本 tar/cpio/bsdtar 有过「符号链接先建、再往里写文件」的穿越手法，务必保持工具版本新
4. zip 侧的风险 —— unzip 对 ../ 成员较宽松，解压来路不明的 zip 前先 unzip -l 扫一遍
5. 防御姿势 —— 非 root 解包、解到空目录、先看清单、拒绝含 ../ 或绝对路径的成员
```

```text
历史 CVE 类型（归档/压缩工具的通病，2026 年仍是同类问题在换皮）：
1. 路径穿越类 —— 成员名 ../ 或绝对路径写到目标之外（tar/cpio/unzip 都出过）
2. 符号链接穿越类 —— 先解出指向 /etc 的软链，再通过该链写文件
3. 解析器内存破坏 —— 畸形归档头/超长名字/越界索引导致崩溃或执行（xz 的 liblzma 事件是教科书案例）
4. 解压资源耗尽 —— 炸弹导致的磁盘/内存 DoS，通常靠配额与限额而非补丁解决
5. 防御要点 —— 发行版安全更新要跟、解包用最小权限、容器里给 /tmp 和备份目录设配额
```

```text
解包时的权限与属主安全：
1. --no-same-owner —— 以 root 解包时不要把归档里的 uid/gid 当真（防归档里塞了 uid=0 的文件）
2. --no-same-permissions —— 忽略归档里的权限位，用 umask 决定
3. -p/--preserve-permissions —— 只在「恢复自己备份的系统目录」时用，解陌生包反而危险
4. umask 与 setuid —— 归档里带 setuid 位 + root 解包 = 直接提权，恢复系统文件才需要它
5. 用最小权限账户解包 —— 不用 root 解包就不存在属主/setuid 提权问题（最优默认）
6. 加密与签名 —— 敏感备份 gpg --symmetric 或 7z AES-256；zip -e 的 ZipCrypto 已可秒破，别用
```

## 常见问题

```text
Q1: tar 和 gzip 有什么区别？
A: tar 归档（多文件打包成一个，不压缩），gzip 压缩（只压单文件）。所以先 tar 再 gzip。

Q2: 哪个压缩工具最好？
A: 没有绝对最好。zstd 速度和压缩率兼得、支持多线程，现代首选；追求体积用 xz；兼容用 gzip。

Q3: 为什么压缩图片/视频没效果？
A: 这些格式本身已压缩，冗余已消除，再压无收益甚至变大。判断依据是数据可压缩性。

Q4: 增量备份怎么实现？
A: tar -g 快照文件（首次全量 + 后续只备变化文件），或 rsync 按差异块增量同步。

Q5: 解压后文件权限变了？
A: 打包时没加 -p 保留权限。用 tar cpzf / tar xpzf，备份配置文件尤其要带 -p。

Q6: zip 和 tar.gz 有什么区别？
A: zip 归档和压缩一体、每文件独立压缩（坏一个不影响其余）、跨平台；tar.gz 是先 tar 再 gzip、整体流式压缩、压缩率更高、保留更多元数据。跨 Windows 传用 zip，Linux 内部备份用 tar.gz。

Q7: 不解压怎么查看压缩文件内容？
A: tar tzf 看归档列表，zcat/bzcat/xzcat/zstdcat 直接读压缩文本内容，unzip -l 看 zip 列表。

Q8: 分卷文件怎么判断顺序？
A: split -a 3 -d 生成等长数字后缀（part000/part001），按数字顺序拼回即可；不要依赖通配符默认的字典序（part10 会排在 part2 前）。

Q9: zstd 和 gzip 到底差多少？
A: 本机 8.8 MiB 混合语料实测：gzip -6 用 0.509 s 压到 4124976 字节，zstd 默认档用 0.031 s 压到 1375396 字节——快约 16 倍、体积只有 1/3。日常归档没有理由再用 gzip。

Q10: tar 的 -r 和 -u 有什么区别？
A: 两者都是往归档尾部追加。区别是 -r 无条件追加你指定的文件（哪怕归档里已有同名成员，会再存一份），-u 只在「文件的 mtime 比归档里同名成员新」时才追加。实测 -u 追加后归档里会出现两个 a/1.txt。

Q11: tar 增量备份能恢复被删除的文件吗？
A: 能，但方向相反——tar --listed-incremental 只记录「新增/修改」，不记录「删除」。源里删掉的文件在后续增量里根本不出现，恢复时它依然会从 0 级里被解出来。要能反映删除就用 rsync --link-dest 快照式备份。

Q12: 压缩包里的中文文件名乱码，unzip -O CP936 为什么没用？
A: 因为 -O 只作用于 DOS/Windows/OS2 主机创建的归档。unzip 6.00 帮助里写得很明确：-O 是 DOS/Windows/OS2、-I 是 UNIX 归档。本机实测 Linux 的 zip 3.0 建的包（host=unix）只有 unzip -I GBK 能恢复名字，-O GBK 和 -O CP936 都无变化。

Q13: 怎么判断一个压缩包是不是压缩炸弹？
A: 解包前看解压后体积。gzip -l 直接报 uncompressed size 与 ratio（本机实测 10217 字节的 .gz 解出 10485760 字节、ratio 99.9%，约 1026:1）；zip 用 unzip -l 加一遍 Length 列；tar 用 tar tvf | awk '{sum+=$3} END{print sum}'。正常文本 3~10 倍，几百上千倍就要警惕。

Q14: tar 的 --sparse 有什么用？
A: 让稀疏文件的「空洞」在归档里也保持空洞。本机实测：100 MiB 的稀疏文件（实际占 0 字节）不加 --sparse 打出来是 104867840 字节，加了 -S 只有 10240 字节，差 1 万倍。虚拟机镜像、数据库文件、容器层常是稀疏文件，备份脚本该带上。

Q15: logrotate 能把默认的 gzip 换成 zstd 吗？
A: 能。写 compresscmd /usr/bin/zstd、uncompresscmd /usr/bin/unzstd、compressext .zst（三者要一起改），compressoptions 传参。本机实测 logrotate -d 会打印 "compress_prog is now /usr/bin/zstd"，真轮转后产出 app.log.1.zst，file 认成 Zstandard compressed data，zstd -dc 能完整读回。

Q16: .deb 包用 tar 解不开是正常的吗？
A: 正常，因为 .deb 是 ar 归档不是 tar。实测 ar t nginx_*.deb 输出 debian-binary / control.tar.zst / data.tar.zst 三个成员——要先 ar x 把内层 tar 取出来再解，或者直接用 dpkg-deb -x/-c/-I。file 会告诉你是 Debian binary package。
```

## 面试题

```text
1. 归档和压缩的区别？
   答：归档把多文件合并成一个（tar，不压体积），压缩减小数据体积（gzip/xz/zstd，只压单文件）。

2. gzip、xz、zstd 怎么选？
   答：xz 压缩率最高最慢，gzip 均衡通用，zstd 压缩率高且快、支持多线程，是现代首选。

3. 什么是增量备份？tar 怎么做？
   答：只备份自上次以来变化的文件。tar 用 -g 快照文件（--listed-incremental），首次全量、之后增量。

4. 分卷压缩怎么恢复？
   答：先 cat 按顺序拼接分卷文件，再解压（cat part* | zstd -d | tar xf -）。

5. 怎么校验备份完整性？
   答：sha256sum 生成校验和、传输后 sha256sum -c 比对，归档用 gzip -t / tar tf 自检。

6. 为什么不能压缩 jpg/mp4 这类文件？
   答：它们本身已经是压缩格式，冗余已被消除，再压无收益甚至变大；随机/加密数据同理（熵最大无重复模式）。

7. zip 和 tar 在实现上的关键差异？
   答：zip 每个文件独立压缩（坏一个不影响其余），tar 把多文件串成单流整体压缩（压缩率更高、坏一处影响后续）。zip 归档压缩一体，tar 需配合 gzip/xz/zstd。

8. tar 的 -z/-j/-J/--zstd 分别对应什么？现在该怎么选？
   答：-z=gzip、-j=bzip2、-J=xz、--zstd=zstd。新落的归档用 --zstd（快、压得小、多线程），体积优先的冷归档用 -J（xz），只有老脚本和跨系统兼容还留 -z。

9. cpio 和 tar 有什么区别？为什么解 RPM 要用 cpio？
   答：tar 的输入是「文件名列表 + 目录树遍历」，cpio 的输入是「从 stdin 读一串文件名」。rpm 内部用的正是 cpio 归档格式，所以 rpm2cpio pkg.rpm | cpio -idmv 是解 rpm 的标准姿势；RHEL 系的 initramfs 也是 cpio（实测 file /boot/initrd.img-... 报 ASCII cpio archive）。

10. .deb 包的结构是什么？
    答：.deb 是 ar 归档，含三个成员：debian-binary（版本号）、control.tar.*（控制信息）、data.tar.*（实际文件）。本机实测 Ubuntu 24.04 的 nginx 包是 control.tar.zst + data.tar.zst，也就是内层已经是 zstd。看结构 ar t、解内容 dpkg-deb -x。

11. tar --listed-incremental 的增量语义有什么坑？
    答：三坑。一是只记新增/修改、不记删除（实测移走文件后增量里只剩目录条目，恢复后文件还在）；二是必须按 0→1→2 顺序解，漏一份或跳着解就得到错树；三是快照文件（.snar，本机 104 字节）丢了就没法继续做增量，必须单独保存。

12. 校验和（sha256sum）能防篡改吗？
    答：不能。哈希只能发现「意外损坏/传输截断」，因为攻击者改文件时可以顺手改哈希清单。要做到防篡改必须用非对称签名（gpg --detach-sign + gpg --verify）或者从可信渠道拿哈希值。三个层次：gzip -t（流完整）→ sha256sum -c（内容未损坏）→ gpg 验签（未被替换）。

13. 什么是压缩炸弹？怎么防？
    答：用超高压缩比数据构造的包，几 KB 解出几十 GB 撑爆磁盘。本机实测 1017 字节的 .gz 解出 10485760 字节（1026:1）。防御是解包前先看清单和体积（gzip -l 的 uncompressed/ratio、unzip -l 的 Length 列），限制解包目录配额，绝不用 root 直接解来路不明的包。

14. tar 解包被拒绝、报「成员名称包含 ..」是什么意思？
    答：这是 GNU tar 的路径穿越防护。实测对成员名带 ../ 的归档，tar 报「从成员名中删除开头的 ../」「成员名称包含 ..」并以退出码 2 结束，一个文件都不落盘。绝对路径同理，tar 会剥离前导 / 不再还原。旧版本的 tar/bsdtar/cpio 这类防护更弱，要保持版本更新。

15. 多线程压缩（pigz / xz -T0 / zstd -T0）的原理和代价？
    答：把输入切成独立块并行压缩再按序拼接成一条流，解码端按帧顺序解。代价是块边界处的长距离匹配失效，压缩率略降——本机实测 pigz 比 gzip -6 只大 0.02%（4114975 vs 4124976），耗时从 0.509 s 降到 0.102 s。小文件用多线程可能因线程开销更慢。

16. 为什么说「备份不校验等于没有备份」？
    答：因为备份的唯一价值是在恢复时能解出来，而损坏/截断往往在恢复那一刻才暴露。完整做法是四件事：备份时生成 sha256 清单、冷备时 gpg 签名、定期 gzip -t / tar tf 自检、定期真解一份并 diff 比对。只做前三件不做最后一件，仍然可能拿到一个「完整但内容错」的备份。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 打包用 `tar czf` 解包用 `tar xzf`，形成肌肉记忆，别每次查参数
2. 备份重要目录用 tar 加 -p 保留权限，配置文件权限丢了很麻烦
3. 大文件/大量文件优先 zstd，速度压缩率兼得且支持多线程
4. 备份一定要带 sha256 校验和，恢复前先校验
5. 生产备份用「日增量 + 周全量」策略，别每次全量浪费空间
6. 冷数据归档用 xz -9（体积最小），热数据/频繁访问用 zstd（解压快）
7. 已压缩的图片/音视频直接 tar 归档不压缩（tar cf 而不是 tar czf），省 CPU 又不会变大
8. 归档脚本一律写死 zstd 而不是 gzip：本机实测同语料快 16 倍、体积 1/3，解压也更快
9. 备份脚本加 `--exclude-vcs --one-file-system`，避免把 .git 打包进去、避免跟着进 /proc 和其他挂载点
10. 稀疏文件（虚拟机镜像、数据库文件）打包加 `--sparse`，本机实测 100 MiB 稀疏文件从 104 MB 降到 10 KB
11. 解包永远先 `tar tvf` 看清单，再 `-C` 到一个空目录；绝不在系统根目录或业务目录里直接解来路不明的包
12. 跨机器恢复用 `--numeric-owner`，避免目标机 uid/gid 映射不同导致文件归错人
13. 增量备份的快照文件（.snar）单独存一份，丢了整条增量链就断了；同时定期重做 0 级全量
14. 备份完成后一定跑一次真恢复演练（解到临时目录 + diff），只做 sha256 校验证明不了「能恢复」

### 踩坑记录

```text
坑 1：解包时覆盖了现有文件
结论：tar xzf 直接解到当前目录，同名文件被覆盖。
原因：tar 解包默认覆盖，没做路径隔离。
解法：先 tar tzf 看内容，再用 -C 解到独立目录，确认后再合并。

坑 2：分卷文件顺序错了解不开
结论：合并分卷后 tar 报错，解压失败。
原因：cat part* 按字典序拼接，part10 会排在 part2 前面。
解法：split 时用 -a 补零保证等长后缀，或按数字顺序明确拼接。

坑 3：用 tar 打包时把绝对路径打进去
结论：解包时文件被恢复到 /etc、/var 等原路径，覆盖系统文件。
原因：打包命令写了绝对路径（tar czf x.tar.gz /etc）。
解法：打包用相对路径（先 cd 到目标目录），或解包时用 -C 控制目标。

坑 4：gzip 压缩日志导致日志文件「消失」
结论：gzip big.log 后原文件没了，只剩 big.log.gz。
原因：gzip 默认压缩后删除原文件。
解法：要保留原文件用 gzip -k，或 gzip -c big.log > big.log.gz。

坑 5：zip 跨平台传输中文文件名乱码
结论：Linux 上 zip 打包的中文文件名，Windows 解压后乱码。
原因：zip 默认不记录 UTF-8 编码，Windows 按本地编码解析。
解法：用 unzip -O UTF-8 解压，或打包时用带 UTF-8 标志的工具（7z）。

坑 6：tar 解压报「Removing leading / from member names」后文件落到错误位置
结论：打包时写了绝对路径，解包文件没有回到预期路径，而是落到了 -C 目录下的相对子路径。
原因：tar 出于安全自动剥离绝对路径开头的 /，防止解包覆盖系统文件。
解法：打包前先 cd 到目标父目录再用相对路径，别直接 tar czf x.tar.gz /etc 这种写法。

坑 7：zip -s 分卷时用了小于 64KB 的分卷大小
结论：zip -s 1k 直接报错 Invalid command arguments (minimum split size is 64 KB)。
原因：zip 的分卷大小下限是 64KB，比 split 的粒度粗。
解法：分卷需求低于 64KB 用 split 切；zip 分卷用 64k 及以上的单位（64k/64m）。

坑 8：以为 unzip -O CP936 能治所有中文乱码
结论：对一个 Linux（host=unix）建的 GBK 名字 zip，unzip -O CP936 和 -O GBK 都完全没效果，名字依旧乱码。
原因：unzip 6.00 的 -O 只作用于 DOS/Windows/OS2 归档，-I 才作用于 UNIX 归档；本机这个包的 host 字段是 unix。
解法：先 zipinfo -v 看主机类型，UNIX 归档用 unzip -I GBK，DOS/Windows 归档用 -O CP936；实在不行用 iconv -f GBK -t UTF-8 批量改名兜底。

坑 9：以为 tar -u 会「更新」归档里的同名文件
结论：-u 只是在尾部又存了一份新副本，归档里出现两个 a/1.txt，解包时后者覆盖前者，但归档体积白涨。
原因：tar 是流式格式，改不了中间已有的成员，-u 的语义是「遇到更新的文件就追加」。
解法：需要真正替换成员就用 --delete 删掉再加，或者干脆重新打一个归档；频繁改成员说明该换 zip/7z 这类有索引的格式。

坑 10：用 tar -g 做增量，结果恢复出来已经删掉的文件还在
结论：源里删掉的 b.txt 在后续增量里根本不出现，恢复（先解 0 级）后它依然存在。
原因：--listed-incremental 只记录 mtime/size/inode 变化，不记录删除事件。
解法：需要反映删除就用 rsync --link-dest 快照式备份（新目录里没有就是删了）；用 tar 就必须接受「增量恢复是叠加语义」。

坑 11：打包稀疏文件把磁盘打爆
结论：100 MiB 的稀疏文件（实际占 0 字节）不加 --sparse 打出来是 104867840 字节，虚拟机镜像/数据库文件能瞬间顶满备份盘。
原因：tar 默认按「逻辑大小」逐块读，空洞被读成真实的 0 字节写进归档。
解法：打包加 -S/--sparse；本机实测同一文件 104867840 → 10240 字节（省 1 万倍）。

坑 12：以为 gzip -t 通过就说明备份没问题
结论：gzip -t 只验了压缩流的 CRC32，归档里的文件内容错、少文件、权限丢失它一概不报。
原因：校验分四层——压缩流（gzip -t）、内容哈希（sha256sum -c）、防篡改（gpg 验签）、可恢复性（真解 + diff），每层管的事不同。
解法：四层都做，尤其最后一层「解到临时目录 diff 一遍」，这是唯一能证明备份可用的动作。

坑 13：logrotate 换成 zstd 后老日志读不了
结论：只改了 compresscmd /usr/bin/zstd，没改 uncompresscmd，zcat/less 读 .zst 归档报错。
原因：logrotate 靠 uncompresscmd 决定「读旧日志时用哪个解压器」，默认仍是 gunzip。
解法：compresscmd、uncompresscmd、compressext 三个一起改（本机实测 -d 输出会打印 compress_prog is now /usr/bin/zstd），或者读的时候显式 zstdcat。

坑 14：从归档里解出一个带 setuid 的文件
结论：以 root 解包一份来路不明的 tar，归档里带的 setuid 位和 root 属主被原样还原，等于直接留下一个提权后门。
原因：GNU tar 以 root 运行时默认倾向还原属主与权限位。
解法：陌生归档用最小权限账户解；必须用 root 时加 --no-same-owner 和 --no-same-permissions，只在恢复自己的系统备份时才用 -p。
```
