## 概述

Linux 里「一切皆文件」：普通文件、目录、设备、管道、socket 都是文件，用同一套接口操作。每个文件的核心是 inode——它存着文件的元数据（权限、属主、大小、时间戳、数据块指针），而文件名只是目录项（dentry）里的一个标签，指向 inode。理解「文件名 → 目录项 → inode → 数据块」这条链，硬链接、符号链接、时间戳这些概念就都通了。

```text
文件的三层结构：
1. 文件名 —— 只是目录项里的一个名字，不是文件的本质
2. inode —— 文件的元数据（权限/属主/大小/时间戳/数据块指针），一个文件一个 inode
3. 数据块 —— 文件真正的内容，inode 里的指针指向它
关键推论：多个文件名可以指向同一个 inode（硬链接），删除文件 = 断开目录项链接
```

## 核心概念

1. **七种文件类型**：ls -l 首字符标识——`-` 普通文件、`d` 目录、`l` 软链、`c` 字符设备、`b` 块设备、`p` 管道、`s` socket。file 命令识别内容类型比扩展名可靠。
2. **inode 与目录项**：inode 存元数据和数据块指针、不存文件名；目录项是「文件名 → inode 号」映射。删除 = 断开链接，链接数归零且无进程占用才释放数据块。
3. **硬链接 vs 软链**：硬链接是同一 inode 的多个名字（删一个不影响、不能跨分区、不能链目录）；软链是存路径的独立文件（可跨分区、可链目录、目标删了断链）。
4. **三个时间戳**：atime 访问时间、mtime 内容修改时间、ctime inode 元数据变更时间（chmod/chown 也变）。

```text
七种文件类型（ls -l 首字符）：
1. - 普通文件 —— 文本、二进制、数据，最常规的文件
2. d 目录 —— 目录也是一种文件，内容是目录项列表
3. l 符号链接 —— 软链，存目标路径，可跨文件系统、可指向目录
4. c 字符设备 —— 按字节流访问的设备（键盘 /dev/tty、终端）
5. b 块设备 —— 按块访问的设备（磁盘 /dev/sda，可随机读写）
6. p 管道 FIFO —— 命名管道，进程间单向数据流
7. s socket —— 本地进程间通信的 socket 文件（如 /run/mysqld/mysqld.sock）
```

```text
inode 关键点：
1. inode 存什么 —— 权限、属主属组、大小、时间戳、链接数、数据块指针，不存文件名
2. 目录项存什么 —— 文件名 ↔ inode 号的映射，目录文件的内容就是一张表
3. 链接数 —— inode 被几个目录项引用，ls -l 第二列；归零才可释放
4. 打开计数 —— 进程 open 的文件即使删除，进程还持有 inode，空间不释放
```

```text
硬链接 vs 符号链接：
1. 硬链接 —— 同一 inode 的多个名字，删原文件不影响（链接数>1），不能跨分区、不能链目录
2. 符号链接 —— 存路径的独立文件，可跨分区、可链目录，目标删除即断链
3. 判断 —— 硬链接 ls -i 看 inode 号相同；软链 ls -l 首字符是 l
4. 选型 —— 备份/别名多用软链，需要「同一文件多个入口」且不依赖路径时用硬链
```

5. **umask 与默认权限**：umask 是「屏蔽位」不是权限本身，新建文件/目录时从基线上减掉对应位；基线是目录 777、文件 666（文件天生不带 x）。默认权限 = 基线 & ~umask，所以 umask 022 得到目录 755/文件 644，umask 027 得到 750/640，umask 077 得到 700/600。
6. **三个特殊权限位**：SetUID（4xxx，执行时以文件属主身份，如 /usr/bin/passwd 的 `-rwsr-xr-x`）、SetGID（2xxx，执行时以文件属组身份；用在目录上让新建文件继承目录属组）、Sticky（1xxx，只在目录上有意义，目录内文件只有属主/目录属主/root 能删，如 /tmp）。
7. **文件属性 chattr/lsattr**：作用在 inode 上、比权限更底层。`+i` 不可变（连 root 都不能改/删/改名）、`+a` 只追加（只能 `>>`，不能覆盖）、`+e` 表示该文件用 extent 组织数据块（ext4 默认，关不掉）。ext4 支持 +i/+a，XFS 基本不支持。
8. **扩展属性 xattr**：文件上挂的「键值对」，分 user.\*（普通用户）、trusted.\*（仅 root）、security.\*（capabilities、SELinux 上下文）、system.\*（ACL 等）四个命名空间。`getfattr`/`setfattr` 读写，备份时必须显式保留。
9. **ACL 访问控制列表**：权限九位不够用时，给「某个具体用户/组」单独授权。`getfacl`/`setfacl` 操作，`ls -l` 权限位末尾的 `+` 就是 ACL 标志，机制细节见 [[05.3-特殊权限与 ACL]]。
10. **稀疏文件**：文件里的「空洞」不分配数据块，读出来全是 0。所以 `ls -l`/`stat` 的 size（逻辑大小）和 `du`（实际占用）能差出几个数量级，典型是虚拟机镜像和数据库文件。
11. **设备文件与主次设备号**：`/dev` 下的节点只是「内核认设备的入口」，不是设备本身；ls -l 的大小列显示 `major, minor`，major 对应驱动（可在 /proc/devices 对照）、minor 对应具体实例。字符设备按字节流、块设备按块随机访问。
12. **inode 表的分配策略**：ext4 在 mkfs 时预留「固定数量」的 inode 表（总数写死在超级块，建完不能改），小文件多会把 inode 先耗尽；XFS 的 inode 动态分配，几乎没有 inode 耗尽问题。
13. **FIFO 与 socket 文件**：FIFO（`p`）是文件系统里的命名管道，没有存储，写端单独打开会阻塞；socket（`s`）是本地通信端点，大小恒为 0，靠文件权限控制谁能连。
14. **符号链接的解析规则**：相对软链的解析基准是「软链自身所在目录」；软链的权限位恒为 `lrwxrwxrwx`（chmod 改的是目标）；`readlink`/`realpath` 用来确认它到底指向哪。
15. **file 命令与魔数**：file 靠 `/usr/share/misc/magic.mgc` 里的魔数规则读文件头判类型，比扩展名可靠；`-b` 只输出类型、`-i` 输出 MIME、`-k` 列出全部匹配。
16. **创建时间 birth time**：atime/mtime/ctime 之外的第四个时间戳，ext4/XFS 支持，`stat` 的 Birth 行或 `stat -c '%w'` 查看；它由内核算、只读，复制文件无法保留（没有能设置它的系统调用）。
17. **atime 更新策略**：atime 每次读都更新会带来写放大，于是有 relatime（默认，只在 atime 早于 mtime/ctime 或超过一天时更新）、noatime（完全不更新）、strictatime（每次都更新）、lazytime（先在内存攒着批量落盘）四种策略。
18. **ls -l 一行怎么读**：第 1 个字段首字符是类型、后面 9 位是权限（含特殊位）；第 2 个字段是硬链接数；3/4 是属主属组；5 是大小（设备文件处是 major, minor）；6~8 是 mtime；最后是文件名，权限位末尾的 `.` 表示 SELinux 上下文、`+` 表示有 ACL。

```text
umask 与默认权限：
1. 基线 —— 目录 777、文件 666（内核强制去掉文件的 x 位，让文件默认不可执行）
2. 公式 —— 默认权限 = 基线 & ~umask
3. umask 022 —— 目录 755(rwxr-xr-x)、文件 644(rw-r--r--)
4. umask 027 —— 目录 750(rwxr-x---)、文件 640(rw-r-----)
5. umask 077 —— 目录 700(rwx------)、文件 600(rw-------)
6. 本机实测 —— 登录后 umask=0022；子 shell 里 umask 027 建出 drwxr-x--- 和 -rw-r-----
7. 来源 —— 登录会话由 pam_umask 模块按 /etc/login.defs 的 UMASK 设置（本机 UMASK 022），
   shell 启动脚本（/etc/profile、~/.profile）通常不再改；systemd 服务由 unit 的 UMask= 决定（默认 0022）
8. 只作用于新建 —— umask 不改已有文件权限，改已有权限用 chmod；umask 是「创建时遮罩」，不是「权限本身」
9. 常见坑 —— 设了默认 ACL 的目录里，新建文件权限还要和 umask「与」一次，umask 太严会把 ACL 想给的位遮掉
```

```text
三个特殊权限位（数值叠加在 rwx 之前）：
1. SetUID 4xxx（u+s）—— 执行时以「文件属主」身份运行。本机 /usr/bin/passwd 是 -rwsr-xr-x，
   普通用户执行时以 root 身份改 /etc/shadow；属主位没有 x 时显示大写 S
2. SetGID 2xxx（g+s）—— 对可执行文件：执行时以「文件属组」身份运行（本机 /usr/bin/crontab 是 -rwxr-sr-x）；
   对目录：目录内新建的文件/子目录自动继承该目录的属组，而不是创建者的主组（团队共享目录的标准做法）
3. Sticky 1xxx（o+t）—— 只在目录上有意义：目录内的文件只有「文件属主、目录属主、root」能删除/改名。
   本机 /tmp、/dev/shm、/var/tmp 都是 drwxrwxrwt（最后一位 t）
4. 设置 —— chmod u+s / chmod 4755、chmod g+s / chmod 2755、chmod +t / chmod 1777
5. 查找 —— find / -perm -4000 找 SUID、-perm -2000 找 SGID、-perm -1000 找 Sticky
6. 安全 —— SUID root 程序是提权面，越少越好；机制、ACL 与 sudo 的配合见 [[05.3-特殊权限与 ACL]]、[[05.4-提权与 sudo]]
```

```text
文件属性（chattr/lsattr，作用在 inode 上，比权限更底层）：
1. +i 不可变（immutable）—— 连 root 都不能修改、删除、改名、加硬链接。本机实测：chattr +i 后 rm 报
   「不允许的操作」（Operation not permitted），chattr -i 后才能删
2. +a 只追加（append-only）—— 只能以追加方式写（>>），不能覆盖（>）、不能截断。本机实测：+a 后 >> 成功，> 报「不允许的操作」
3. +e extent —— 表示该文件用 extents 映射数据块，ext4 上创建文件时默认带上，无法用 chattr 关闭；
   lsattr 里普通文件一般只看到 e
4. 其他常用位 —— +A 不更新 atime、+c 自动压缩、+d 不被 dump 备份、+j 日志式写入、+s 安全删除、+u 可恢复删除、+S 同步写入
5. 查看 —— lsattr 文件；lsattr -d 目录；lsattr -R 递归
6. 支持差异 —— ext2/3/4 支持 +i/+a/+A/+j 等；XFS 只支持很少几个（如 +r 实时卷、+d nodump），
   在 XFS 上 chattr +i 会报 Operation not supported，这是 XFS 与 ext4 的典型差异
7. 目录也能加 —— chattr +i 目录后，目录内新建/删除条目都报错（本机实测 touch 新文件报「不允许的操作」），
   适合给「关键配置目录」上锁
8. 典型用途 —— 给 /etc/passwd、/etc/shadow、证书、审计日志上 +i 防篡改防误删；上锁前先 chattr -i，改完再 chattr +i
```

```text
扩展属性 xattr（文件上挂的键值对，不占 inode 里的固定字段）：
1. 命名空间（前缀决定谁能读写）——
   user.*     普通用户可读写；信任边界靠文件权限
   trusted.*  仅 root（CAP_SYS_ADMIN）可读写
   security.* 安全模块用：security.capability（capabilities）、security.selinux（SELinux 上下文）、security.ima
   system.*   内核内部用：system.posix_acl_access/system.posix_acl_default（ACL 就存在这里）
2. 工具 —— getfattr -d 文件（列出）、getfattr -n user.k -e text 文件（看单个）、
   setfattr -n user.k -v v 文件（设置）、setfattr -x user.k 文件（删除）、getfattr -m - -d 文件（列全部命名空间）
3. 本机情况 —— 未安装 attr 包（/usr/bin/getfattr、/usr/bin/setfattr 不存在），
   但 xattr 本身在使用中：getcap /usr/bin/ping 输出 cap_net_raw=ep，这就是 security.capability 属性
4. capabilities 为什么用 xattr —— 让普通用户执行 ping 也能建 raw socket，而不必给整个程序开 SUID root
5. SELinux —— 安全上下文存在 security.selinux 属性里，cp -Z/restorecon 就是在改它（Ubuntu 默认用 AppArmor，机制不同）
6. 备份必须带上 —— cp --preserve=xattr、rsync -aX、tar --xattrs（默认 tar/cp 可能丢掉 xattr，
   一旦丢失，capabilities 和 SELinux 上下文都没了）
7. 列不出来不是「没有」 —— ls -l 看不到 xattr，要用 getfattr/attr 类工具或 getcap 才能看到
```

```text
ACL 访问控制列表（权限九位放不下时的补充机制）：
1. 一句话 —— 给「某个具体用户/组」单独授权，不用把文件属组改掉
2. 查看 —— getfacl 文件；ls -l 权限位末尾出现 + 说明该文件有 ACL
3. 设置 —— setfacl -m u:alice:rw 文件（给用户 alice rw）、setfacl -m g:devs:rx 文件（给组 devs rx）
4. 默认 ACL —— setfacl -m d:u:alice:rw 目录，目录内「新建」的文件自动继承这条规则（d: 前缀 = default）
5. mask —— ACL 里有个 mask 项，它和权限位的「组」位共用同一组比特，mask 决定 ACL 条目的有效上限
6. 与 umask 的冲突 —— 目录有默认 ACL 时，新建文件权限 = (默认权限 & ~umask)，umask 太严会把 ACL 想给的位遮掉
7. 深入 —— ACL 语法、mask 换算、继承规则、setfacl -R/-b/-k 的完整用法见 [[05.3-特殊权限与 ACL]]
```

```text
稀疏文件（逻辑大小 ≠ 实际占用）：
1. 成因 —— 文件里没写过数据的区间是「空洞」（hole），不分配数据块，读出来全是 0
2. 两个大小 —— ls -l/stat 的 Size 是逻辑大小；du（或 stat 的 Blocks×512）看实际占用
3. 本机实测 —— truncate -s 512M big.img 后 stat 显示 size=536870912 blocks=0，du 显示 0；
   同一文件 du --apparent-size 显示 512M
4. 建空洞的方法 —— truncate -s 512M f.img（最快）；写文件时用 lseek 跳过一段再写，中间自然留洞
5. dd 建洞（示例，本机策略拦截未实测）—— dd if=/dev/zero of=f.img bs=1M count=0 seek=64
6. 预分配对比 —— fallocate -l 256M fa.img 是「真分配」：本机实测 blocks=524296、du 257M，
   和 truncate 的「假大小」完全不同；预分配用于避免写时碎片和 ENOSPC
7. 拷贝 —— 现代 coreutils 的 cp 默认用 SEEK_HOLE 探测空洞并保留（本机实测 cp big.img big.copy 后 blocks 仍是 0）；
   但 `cat f > f2` 会一路顺序读把洞填成实零（本机实测 cat.copy blocks=1048584、du 513M）
8. 打包 —— tar 默认按内容打包会把洞写成实零（本机实测 t.tar 536872960 字节、blocks=1048584），
   tar -cSf 保留稀疏（本机实测 tS.tar 只有 10240 字节）
9. 碎片查看 —— filefrag 文件：本机 fallocate 出来的 fa.img 是「11 extents found」，truncate 出来的 big.img 是「0 extents」
10. 典型场景 —— 虚拟机 qcow2/raw 镜像、容器镜像层、数据库数据文件、core dump
```

```text
设备文件与主次设备号：
1. 本质 —— /dev 下的节点只是「内核识别设备的入口」，不是设备本身；ls -l 的大小列显示 major, minor
2. major 号 —— 标识驱动/设备类，可在 /proc/devices 对照（本机：1 mem、4 tty、5 /dev/tty、8 sd、7 loop）
3. minor 号 —— 同一驱动下的实例编号：本机 /dev/sda=8:0、/dev/sda2=8:2、/dev/null=1:3、/dev/tty=5:0
4. 字符设备 c —— 按字节流顺序访问、通常无缓存：/dev/null(1,3)、/dev/urandom(1,9)、/dev/tty(5,0)、/dev/tty0(4,0)
5. 块设备 b —— 按固定块随机访问、有页缓存：/dev/sda(8,0)、/dev/sda2(8,2)
6. 创建 —— mknod /dev/xxx c 1 3 需要 CAP_MKNOD（root 或带该 capability）；普通用户会 Operation not permitted
7. 持久命名 —— udev 生成 /dev/disk/by-uuid、by-partuuid、by-label，指向真实设备节点，避免 sda/sdb 顺序漂移
8. stat 取号 —— stat -c '%t:%T' 输出十六进制主次号，stat -c '%D' 是文件所在设备的 st_dev
9. 误建风险 —— 在 /dev 下随手指一个 major/minor 并放开权限，等于给了别人直接读写设备的通道
```

```text
inode 数量与分配策略（ext4 固定 vs XFS 动态）：
1. ext4 —— mkfs 时预留固定 inode 表。本机 dumpe2fs -h /dev/sda2：Inode count 60981248、Inode size 256、
   Inode blocks per group 512；总数写在超级块里，格式化之后无法再增加
2. df -i —— 显示 inode 总数/已用/可用/百分比。本机 /dev/sda2：60981248 总数、已用约 139 万（3%）
3. 耗尽 —— ext4 上小文件数量超过 inode 数就报 No space left on device，而 df -h 显示还有大把空间
4. XFS —— inode 从空闲空间按需动态分配，df -i 不体现固定上限，几乎没有 inode 耗尽问题；
   Red Hat 系默认 XFS，遇到「空间不足」先看数据块和配额
5. mkfs 调优 —— ext4 可用 -i bytes-per-inode（默认 16384）或 -N 直接指定数量；建完不可改
6. tmpfs —— 内存文件系统的 inode 数由挂载参数 nr_inodes 决定；本机 /run 有 2521327 个 inode
7. 内核侧上限 —— /proc/sys/fs/nr_open（本机 1048576）是单进程可打开 fd 上限；
   /proc/sys/fs/file-max（本机 9223372036854775807）是系统级上限
```

```text
FIFO 与 socket 文件实战：
1. FIFO（p）—— mkfifo 创建，文件系统里的「命名管道」，没有存储：数据只在读端打开时才流动
2. 阻塞行为 —— 只以写方式打开会阻塞到有读端。本机实测：timeout 2 sh -c 'echo hi > mypipe' 到点被杀（exit=124），
   说明写端单独打开确实挂住了；用 O_NONBLOCK 打开则不阻塞（写满会 EAGAIN）
3. 大小恒为 0 —— FIFO 不存数据，ls -l 的大小是 0；stat -c '%F' 输出 fifo
4. socket（s）—— Unix domain socket 文件，双向通信端点。本机 /run/docker.sock：srw-rw---- size=0 mode=660
5. 谁在监听 —— ss -xl 能看到 socket 文件形式的监听端点（本机 /run/snapd.socket、containerd 的 shim socket）
6. 权限即门槛 —— socket 文件权限决定谁能连：docker.sock 是 root:docker 660，把用户加进 docker 组才能用
7. socket activation —— systemd 可以先用 .socket unit 监听，首个连接到来再拉起对应服务（见 [[10.3-编写 Service Unit]]）
```

```text
符号链接深入：
1. 相对 vs 绝对 —— 相对软链的解析基准是「软链自身所在目录」，不是建链时的工作目录；
   所以 `ln -s target link` 里的 target 是相对 link 所在目录解释的，目录一挪就断
2. 权限位恒为 lrwxrwxrwx —— 软链的 rwx 只是占位符，chmod 作用在「目标」上。
   本机实测：chmod 700 demo.soft 之后，目标 demo.txt 变成 -rwx------，而软链仍显示 lrwxrwxrwx
3. 大小 = 路径字符串长度 —— ls -l 里软链的大小是它存的目标路径字节数（本机 demo.soft 存 "demo.txt" 8 字节）
4. 解析工具 —— readlink 看它存的原始路径（本机输出 demo.txt），readlink -f / realpath 解析到最终真实路径（/tmp/fx2/demo.txt）
5. 原子切换 —— 部署时用 `ln -sfn <新版本> <软链名>` 原地替换；更严格的做法是先建临时链再 `mv -T`，
   避免「删了再建」之间出现软链不存在的空窗
6. 追踪进程 —— /proc/<pid>/cwd 就是指向进程当前工作目录的软链（本机 /proc/self/cwd -> /tmp/fx2），
   /proc/<pid>/exe、/proc/<pid>/root 同理
7. 目录不能硬链 —— 内核禁止（防目录成环），目录共享用软链或 bind mount
8. 断链判断 —— 目标不存在时 ls -l 里链接目标仍显示，但用 file/readlink -f 或 `test -e` 立刻能看出失效
```

```text
file 命令原理（靠魔数，不靠扩展名）：
1. 三步判据 —— ①看文件系统元数据（stat：普通/目录/软链/设备）；②比对魔数（文件头特征字节）；
```

```text

1. 第四个时间戳 —— atime（访问）/mtime（改内容）/ctime（改 inode）之外，ext4（inode extra 字段）与 XFS 记录创建时间

7. 用途 —— 定位「文件是哪次部署/解压产生的」，比 mtime 更接近「真实产生的时刻」
```

```text
四种 atime 更新策略（挂载选项）：
1. atime（严格老行为）—— 每次读都更新 atime，读操作也可能产生磁盘写，开销大
2. relatime（Linux 默认）—— 只在「atime 早于 mtime/ctime」或「上次更新超过 24 小时」时才写回；
   本机 / 的真实挂载选项就是 rw,relatime
3. noatime —— 完全不更新 atime，读操作零额外写；日志、数据库、邮件队列这类读多写多的场景收益最大
4. strictatime —— 每次读都严格更新（配合审计「谁读过这个文件」时才需要）
5. nodiratime —— 只关闭「目录」的 atime 更新，文件照旧
6. lazytime —— atime/mtime 变更先在内存里攒着、稍后批量落盘，减少写放大；断电时可能丢部分时间戳更新
7. 验证 —— findmnt -no OPTIONS /（本机输出 rw,relatime）、mount | grep ' / '、cat /proc/mounts
8. 提醒 —— 这些策略只影响 atime 是否更新，不改变 mtime/ctime 语义，也不影响文件内容
```

```text
ls -l 一行 9 个字段怎么读：
1. 字段 1 —— 首字符 = 文件类型（- d l c b p s）；后面 9 位 = 权限三位一组（属主/属组/其他），
   其中属主位的 s/S、属组位的 s/S、其他位的 t/T 是特殊权限位
2. 字段 2 —— 硬链接数（指向该 inode 的目录项个数）。普通文件通常是 1；
   目录天然 >=2：自己 + `.`，每多一个子目录再由子目录的 `..` 加一
3. 字段 3/4 —— 属主、属组（ls -n 显示 UID/GID 数字）
4. 字段 5 —— 大小：普通文件是字节数；目录是目录项表的大小（与里面文件总量无关）；
   设备文件处显示 major, minor；软链是目标路径字符串长度
5. 字段 6/7/8 —— 最近修改时间（mtime）的「月 日 时:分」，超过半年的文件显示「月 日 年」
6. 字段 9 —— 文件名；软链后跟 `-> 目标路径`
7. 附加标记 —— 权限位末尾的 `.` 表示有 SELinux 安全上下文（RHEL 系常见）、`+` 表示有 ACL 扩展属性
8. 常用变体 —— ls -i 加 inode 号、ls -n 数字属主、ls -Z SELinux 上下文、ls -lu/-lc 换显 atime/ctime
```

### 七种文件类型逐个拆解

普通文件（`-`）是「数据 + inode」的组合，分文本和二进制两类，但 Linux 不靠扩展名区分——`.txt` 可能是二进制、`.bin` 可能是文本，判断内容类型要用 file 命令（读文件头魔数）。

```shell
file /etc/passwd       # ASCII text
file /bin/ls           # ELF 64-bit executable（二进制可执行文件）
file photo.jpg         # JPEG image data
stat -c '%F' /etc/passwd   # 输出 regular file
```

要点：扩展名只是给人看的约定，Linux 内核和 shell 都不据此判断类型；`file` 靠 /etc/magic 里的魔数规则识别内容，比扩展名可靠得多。

目录（`d`）本质也是一种文件，它的「内容」是一张「文件名 → inode 号」的映射表，不是文件数据本身。所以目录的大小一般很小（几 KB），和里面文件多大无关。

```shell
ls -ld /tmp            # 看目录本身的属性，首字符 d
stat -c '%F %s' /tmp   # directory + 目录项表的大小（不是里面文件总和）
ls -i /tmp             # 列目录项时顺带看每个条目的 inode 号
```

要点：目录里「文件名」存在目录项表里，「文件内容」存在 inode 指向的数据块里，两者分离正是硬链接能「一个 inode 多个名字」的前提。

符号链接（`l`）是一个独立的小文件，内容存的是「目标路径字符串」，不占目标文件的数据；删除软链本身不影响目标，删除目标则软链断链。

```shell
ln -s /etc/passwd pw          # 建软链，pw 里存 "/etc/passwd" 这个字符串
ls -l pw                      # lrwxrwxrwx ... pw -> /etc/passwd
readlink pw                   # 输出 /etc/passwd（它存的路径）
readlink -f pw                # 递归解析出最终真实路径
```

要点：软链有「目标删除即断链」的固有风险；`readlink` 看它存的原始路径、`readlink -f` 解析到最终目标（常用于脚本里校验目标存在）。

字符设备（`c`）按字节流访问（键盘、终端、/dev/null），块设备（`b`）按固定大小的块随机访问（磁盘）。两者在 `ls -l` 里的大小列被「主设备号, 次设备号」（major, minor）替代。

```shell
ls -l /dev/null /dev/tty /dev/sda
# crw-rw-rw- 1 root root 1, 3 ... /dev/null   （字符设备，major=1 minor=3）
# crw-rw-rw- 1 root tty  5, 0 ... /dev/tty    （字符设备，major=5 minor=0）
# brw-rw---- 1 root disk 8, 0 ... /dev/sda    （块设备，major=8 minor=0）
stat -c '%F %t:%T' /dev/sda   # block special file + major:minor（十六进制）
```

要点：major 号标识设备驱动、minor 号标识同驱动下的具体设备；设备节点只是「内核识别设备的入口」，不是设备本身，mknod 可以手工创建设备节点。

管道 FIFO（`p`）是命名管道，提供进程间单向数据流，没有「存储」概念——写端数据只有读端在读时才传递；socket（`s`）是本地 Unix domain socket 文件，进程间双向通信用。

```shell
mkfifo /tmp/mypipe             # 创建命名管道
ls -l /tmp/mypipe              # prw-r--r-- ... /tmp/mypipe（首字符 p）
stat -c '%F' /tmp/mypipe       # fifo

# 终端 1：echo hello > /tmp/mypipe   （写端，会阻塞等读端）
# 终端 2：cat /tmp/mypipe            （读端，输出 hello，双方同时结束）

ls -l /run/mysqld/mysqld.sock  # srwxrwxrwx ...（首字符 s，Unix domain socket）
stat -c '%F' /run/mysqld/mysqld.sock   # socket
```

要点：FIFO 必须「读写两端同时打开」数据才流动，单独开写端会阻塞；socket 文件的大小通常显示 0，它只是通信端点、不存数据。

### inode 与目录项深入

inode 存的是「除了文件名和内容之外的几乎所有元数据」：文件类型与权限、属主属组、大小、三个时间戳、链接数、以及指向数据块的指针（ext4 用「12 个直接指针 + 间接/双重间接/三重间接指针」组织）。目录项（dentry）只存两样：文件名、inode 号。

```shell
stat /etc/passwd                # 一次性看全 inode 元数据
ls -li /etc/passwd              # 第一列 inode 号、第三列链接数
df -i /                         # 文件系统的 inode 总数与使用率
dumpe2fs -h /dev/sda1 | grep -i "inode count"   # ext4 看 inode 总数（需 root）
```

要点：inode 数量在格式化时确定，海量小文件场景 inode 会比磁盘容量先耗尽（df -i 100% 但 df -h 还有空间）；inode 和文件名的分离，决定了「改文件名/移动文件（同分区）」不会动 inode 和数据块。

**链接数 vs 打开计数**是两回事：链接数是「目录项里有多少个名字指向这个 inode」（ls -l 第二列，硬链接数）；打开计数是「当前有多少进程 open 了这个 inode」。删除文件（unlink）只减链接数，只有链接数归零且打开计数归零，数据块才真正释放——这是「rm 了文件但进程还开着句柄，磁盘不释放」的完整解释。

```shell
ls -l /etc/passwd               # 第二列 = 链接数（通常是 1）
lsof /etc/passwd                # 谁打开了这个文件
lsof +L1 | grep deleted         # 找「已删除但被进程占用」的文件
```

### 硬链接 vs 符号链接深入

硬链接用 `ln` 创建，等于给同一 inode 再挂一个名字（链接数 +1），删除任意一个名字，另一个名字仍能读到数据；软链用 `ln -s` 创建，是独立 inode，存目标路径。

```shell
echo hello > a.txt
ln a.txt a.hard              # 硬链接：a.txt 和 a.hard 同一 inode
ln -s a.txt a.soft           # 软链：a.soft 存 "a.txt" 这个路径
ls -li a.txt a.hard a.soft   # 硬链接 inode 相同、链接数=2；软链 inode 不同、首字符 l
```

硬链接的限制：不能跨文件系统（不同分区的 inode 表各自独立）、不能链接目录（内核禁止，防目录成环）、只有 root 或同属主才能建。软链没有这些限制，代价是「目标删了断链」。

```shell
ln /data/file /tmp/hard      # 报 Invalid cross-device link（跨分区）
ln /data /tmp/dirlink        # 报 hard link not allowed for directory（目录）
```

要点：判断「是不是同一文件」别比对文件名，比对 inode 号（ls -i 或 stat -c %i）；目录的硬链接数天然 ≥2（目录自己 + 它的 `.`，每多一个子目录 `..` 又 +1），这是 ls -ld 目录第二列常大于 2 的原因。

### 三个时间戳深入

atime（Access）读内容时更新，mtime（Modify）改内容时更新，ctime（Change）改 inode 元数据（内容、权限、属主、链接数）时更新——注意 ctime 也会跟着 mtime 一起变（改内容必然改 inode），但反过来 chmod 只改 ctime 不动 mtime。

```shell
echo a > f.txt
stat -c 'atime=%x mtime=%y ctime=%z' f.txt
cat f.txt                    # 读内容 → atime 变
chmod 600 f.txt              # 改权限 → ctime 变，mtime 不变
echo b >> f.txt              # 改内容 → mtime 和 ctime 都变
ls -lu f.txt                 # 按 atime 排序显示
ls -l  f.txt                 # 默认显示 mtime
ls -lc f.txt                 # 显示 ctime
```

要点：三个时间戳用 `ls -lu/-l/-lc` 分别查看，或用 `stat` 一次看全；find 的 `-atime/-mtime/-ctime` 就是按这三个时间戳过滤；因为 atime 读一次变一次、开销大，很多挂载用 relatime/noatime 降低更新频率。

## 工作原理

文件访问的完整链路是「文件名 → 目录项 → inode → 数据块」：程序用路径找文件时，内核先在目录项里查文件名对应的 inode 号，再读 inode 拿到权限、大小和数据块指针，最后按指针读数据块。「删除文件」只是把目录项里这条映射删掉（链接数 -1），当链接数为 0 且没有进程持有该 inode 时，数据块才被标记为空闲。这就是「rm 了文件但进程还开着句柄，磁盘不释放」的底层原因。

```text
访问链路与删除本质：
文件名 → 目录项（dentry 表）→ inode（元数据 + 数据块指针）→ 数据块（真实内容）
删除 = 断开目录项链接（链接数-1）；链接数=0 且无进程占用 → 数据块真正释放
```

再往下两层，是 inode 和目录项在内存/磁盘上的具体组织方式：

**inode 内部结构（以 ext4 为例）**：inode 表是分区格式化时预留的一片连续区域，每个 inode 固定大小（ext4 默认 256 字节）。存元数据外，最关键的是「数据块指针」——12 个直接指针指向文件前 12 个数据块（小文件直接覆盖），加 1 个间接、1 个双重间接、1 个三重间接指针，逐级扩展支持大文件。文件越大，指针层级越深。

**目录项缓存（dcache）**：路径解析每次都要「读目录 inode → 找目录项」，很慢。内核用 dcache 把解析过的「目录项 → inode」映射缓存起来，下次同一路径直接命中，这也是「第二次访问同一路径明显变快」的原因。dentry 是纯内存结构，落盘后只剩下「文件名 + inode 号」这一条记录。

```text
inode 结构要点：
1. inode 表格式化时预留，inode 数量固定（df -i 可见），耗尽了就报 No space left on device
2. 数据块指针 = 12 直接 + 1 间接 + 1 双重间接 + 1 三重间接，小文件用直接指针、大文件逐级扩展
3. dentry 是内存缓存（dcache），加速重复路径解析；落盘的目录项只存「文件名 + inode 号」
```

## 配置文件解析

```text
/etc/magic —— file 命令的魔数数据库：
# 记录各文件格式的「魔数」（文件头特征字节），file 靠它识别内容类型而非扩展名
# 例：PDF 文件头是 %PDF-，ELF 可执行文件头是 \x7fELF
# 自定义魔数规则可追加到 /etc/magic 或 ~/.magic
```

```text
/proc/sys/fs —— 文件系统相关的内核参数（与 inode 相关的运行时配置）：
/proc/sys/fs/inode-max        # 系统 inode 上限（只读）
/proc/sys/fs/file-max         # 系统打开文件句柄上限
# 用户级限制看 /etc/security/limits.conf 的 nofile
```

```text
/etc/fstab —— 挂载选项（控制 atime 更新时间戳的行为）：
/dev/sda1  /data  ext4  defaults,noatime  0 0
# noatime  —— 完全不更新 atime（读文件零写入，日志/数据库分区收益大）
# relatime  —— 只在 atime 早于 mtime/ctime 时才更新（多数发行版默认，折中方案）
# 挂载选项影响的是「读文件会不会顺带写 atime」，对 mtime/ctime 无影响
```

## 应用场景实战

### 场景一：排查「文件删了但磁盘空间没释放」

```shell
# 1. 磁盘满，先看占用
df -h /

# 2. 找「已删除但仍被进程占用」的文件（lsof 显示 deleted）
lsof +L1 | grep deleted

# 3. 找到占用进程后，重启或 kill 该进程释放空间
# 例：nginx 的日志被删了但进程还开着文件句柄
systemctl restart nginx
df -h /    # 空间回来了
```

### 场景二：给可执行程序建软链并校验时间戳属性

```shell

ls -l /usr/local/bin/tool        # l 开头，箭头指向真实路径
readlink -f /usr/local/bin/tool  # 解析出最终真实路径

# 3. 用 stat 核对属性（权限/时间戳/类型）
stat -c '%F %a %U %y' /opt/app/bin/tool
```

### 场景三：排查「磁盘有空间却报 No space left on device」（inode 耗尽）

```shell
# 1. 现象：写文件报 No space left on device，但 df -h 显示磁盘还有空间
df -h /

# 2. 看 inode 使用率——海量小文件场景大概率 100%
df -i /

# 3. 定位是哪个目录攒了大量小文件
find / -xdev -type f 2>/dev/null | cut -d/ -f2 | sort | uniq -c | sort -rn | head
find /var/spool -type f | wc -l       # 对可疑目录精确数文件数量

# 4. 清理小文件或迁移到新分区，inode 使用率下降后恢复写入
rm -rf /var/spool/clientmqueue/*      # 例：清掉堆积的邮件队列小文件
df -i /
```

```text
Red Hat 系差异：inode 耗尽主要是 ext 系列文件系统的特征——ext4 在 mkfs 时预留固定数量的 inode（df -i 能看到总数，海量小文件先耗尽 inode 而非空间）。Red Hat/CentOS/Rocky/AlmaLinux 默认文件系统是 XFS，inode 动态分配，几乎没有「inode 耗尽」问题（df -i 基本恒不满），更常见的是数据块或配额耗尽。所以遇到「No space left on device 但 df -h 有空间」，先看文件系统类型：ext4 查 df -i，XFS 查数据块和 xfs_quota。
```

## 性能与调优

```text
inode / 时间戳相关性能优化：
1. 挂载 noatime —— 关闭 atime 更新，读文件不再产生磁盘写（日志/数据库收益大）
2. 防 inode 耗尽 —— 海量小文件场景 inode 比容量先耗尽，df -i 监控 inode 使用率
3. 稀疏文件省空间 —— 逻辑大小大、实际占用小（Blocks < Size），备份用 tar -S 保留稀疏
4. 少用全盘 find —— 全盘遍历 IO 重，优先 locate 索引或用 -prune 排除大目录
5. 硬链接省空间 —— 需要多份相同大文件时用硬链接，只占一份磁盘（如容器镜像分层）
6. 用 stat -c 批量取属性 —— 脚本里取大小/时间戳用 stat -c，比 ls -l 输出好解析、也更快
7. 减少目录项数量 —— 一个目录塞几十万文件，ls/find 都慢，按子目录分片存储
```

## 安全与权限

```text
文件类型与属性安全要点：
1. 软链攻击（symlink race）—— 高权限程序操作可被换掉的软链目标，注意 TOCTOU 竞态
2. SUID 文件风险 —— 属主是 root 且带 SUID 的程序是提权面，定期审查（find / -perm -4000）
3. 断链检查 —— 软链目标被删后脚本静默失效，用 readlink -f 校验
4. socket 文件权限 —— /run 下的 socket 靠文件权限控制谁能连（如 mysql.sock 660）
5. /tmp sticky bit —— 防其他用户删你的文件，检查 drwxrwxrwt
6. 设备节点权限 —— /dev 下块/字符设备节点权限决定谁能直接读写磁盘，误建节点 = 安全洞
```

## 常见问题

```text
Q1: 硬链接和软链怎么选？
A: 需要「同一文件多个入口、不依赖路径」用硬链接；需要跨分区、指向目录、跟随路径用软链。

Q2: 为什么删了文件磁盘没释放？
A: 进程还持有被删文件的 inode，链接数归零但打开计数>0，数据块没释放。lsof +L1 找、重启进程。

Q3: atime、mtime、ctime 分别什么时候变？
A: atime 读内容时变，mtime 改内容时变，ctime 改内容/权限/属主（inode 元数据）都变。

Q4: chmod 改了权限，为什么 mtime 没变但 ctime 变了？
A: mtime 只记录内容修改，chmod 改的是 inode 元数据、归 ctime 管。

Q5: 为什么目录不能建硬链接？
A: 内核禁止（防目录环），目录共享用软链或 bind mount。

Q6: stat 里 Blocks 和 Size 为什么差很多？
A: Size 是逻辑大小（字节），Blocks 是实际占用的 512 字节块数；稀疏文件逻辑大、实际占用小，两者差距大属正常。

Q7: 块设备和字符设备有什么区别？
A: 块设备按固定块随机读写、有缓存（磁盘）；字符设备按字节流顺序访问、通常无缓存（键盘、串口）。ls -l 里分别显示 b 和 c。

Q8: 能查到文件的创建时间（birth time）吗？
A: 部分文件系统（ext4、xfs）支持，stat 的 Birth 字段或 stat -c '%w' 查看；不支持的文件系统显示 -，只能用 mtime 当近似值。

Q9: umask 是什么？新建文件和目录的权限怎么算出来？
A: umask 是「屏蔽位」，不是权限本身。公式：目录 = 777 & ~umask、文件 = 666 & ~umask（文件永远没有 x）。
   本机 umask 022 → 目录 755、文件 644；umask 027 → 750/640；umask 077 → 700/600。它只影响「新建」，不改已有文件。

Q10: chmod 000 和 chattr +i 有什么区别？
A: chmod 改的是权限位，root 用 CAP_DAC_OVERRIDE 照样能读写；chattr +i 是 inode 层的不可变属性，
   连 root 都不能改/删/改名，必须先 chattr -i 解锁。ls -l 看权限、lsattr 看属性，两者是两层。

Q11: 扩展属性 xattr 是什么，怎么查看和备份？
A: 挂在文件上的键值对，分 user.*（普通用户）、trusted.*（root）、security.*（capabilities、SELinux 上下文）、
   system.*（ACL 等）四个命名空间。用 getfattr/setfattr（attr 包）读写；capabilities 可用 getcap 看。
   备份必须显式保留：cp --preserve=xattr、rsync -aX、tar --xattrs，否则能力和安全上下文会丢。

Q12: 稀疏文件怎么识别、怎么创建？
A: 识别看「两个大小」：stat 的 size（逻辑）远大于 blocks×512（实际占用），或 du 远小于 ls -l 的大小。
   创建用 truncate -s 512M f.img（本机实测 blocks=0）、或 dd seek 跳过空洞（示例）；
   注意 fallocate 是「真分配块」（本机实测 256M 文件 blocks=524296），别把它当稀疏。

Q13: 为什么文件删除后 cp 出来的副本比原文件大很多？
A: 源文件是稀疏的，而顺序拷贝（cat/重定向、不支持空洞探测的工具）会把空洞按零填满写出。
   本机实测：512M 稀疏文件 cat 之后 blocks 从 0 变成 1048584（约 513M）。用 cp 或 cp --sparse=always 可保住空洞。

Q14: 设备文件的 major/minor 到底怎么用？
A: major 标识驱动/设备类，minor 是同类里的实例编号，可在 /proc/devices 对照名字；
   ls -l 的大小列显示 major, minor（本机 /dev/sda 是 8, 0，/dev/null 是 1, 3）。
   内核 open 节点时用这对号找到对应驱动；mknod 手工建节点就是手写这对号（需要 CAP_MKNOD）。

Q15: FIFO 和 socket 文件有什么区别？
A: FIFO（p）是单向的命名管道，数据只在读端打开时流动，写端单独打开会阻塞（本机实测 timeout 后 exit=124）；
   socket（s）是双向通信端点，有 Unix domain socket 的文件名、传输效率更高。
   两者 ls -l 大小都是 0，都不存数据，只是一条通道。

Q16: 怎么让一个目录里新建的文件自动属于某个组？
A: 给目录设 SetGID：chmod g+s 目录（或 chmod 2775），之后目录内新建文件继承目录的属组而不是创建者的主组；
   再配合 umask 002（或默认 ACL）才能让同组可读写，这是团队共享目录的标准配置。

Q17: 为什么 lsattr 里每个文件都有个 e？能去掉吗？
A: e 表示该文件用 extents 映射数据块，是 ext4 格式化时 features 里带上的（本机 dumpe2fs 的 features 含 extent），
   创建文件时自动带上，不能用 chattr 关闭。它不是「问题」，是 ext4 的正常标志。

Q18: atime 会影响性能吗？现在默认用哪种策略？
A: 会——严格每次读都更新 atime 会带来额外写。Linux 默认用 relatime（只在 atime 早于 mtime/ctime 或超过一天时更新），
   本机 / 就是 rw,relatime；读密集场景可上 noatime，需要在内存攒批可上 lazytime，审计需求才用 strictatime。
```

## 面试题

```text
1. inode 里存什么、不存什么？
   答：存权限、属主属组、大小、时间戳、链接数、数据块指针；不存文件名（文件名在目录项里）。

2. 硬链接和软链的本质区别？
   答：硬链接是同一 inode 的多个目录项（删一个不影响、不能跨分区/链目录）；软链是存路径的独立文件（目标删了断链）。

3. 删除文件的本质是什么？
   答：断开目录项与 inode 的链接（链接数-1），链接数归零且无进程占用时数据块才释放。

4. 为什么「rm 大日志后磁盘没释放」？
   答：进程还持有文件句柄（打开计数>0），数据块未释放。lsof +L1 找 deleted 文件、重启进程。

5. 三个时间戳的区别？
   答：atime 访问时间、mtime 内容修改时间、ctime inode 元数据变更时间（chmod/chown 也变 ctime）。

6. 怎么判断一个文件是不是软链？怎么找到它指向哪？
   答：ls -l 首字符是 l；readlink 看它存的路径，readlink -f 解析到最终真实路径。

7. 磁盘还有空间却报 No space left on device，为什么？
   答：inode 耗尽了。df -i 看 inode 使用率是否 100%，清理小文件或迁移到 inode 更多的分区。

8. 块设备和字符设备的区别？
   答：块设备按块随机读写（磁盘 /dev/sda，首字符 b），字符设备按字节流顺序访问（键盘 /dev/tty，首字符 c），大小列显示主:次设备号。

9. inode 和文件名到底是什么关系？
   答：inode 只描述文件本身（元数据 + 数据块位置），文件名只是目录里「名字 → inode 号」的一条目录项映射。同一个 inode 可以有多个名字（硬链接），也可以暂时没有名字（进程已 unlink 但仍打开的 deleted 文件）。内核里根本没有「文件名」这个概念，只有目录项（dentry）。`ls -i` 看到的就是名字对应的 inode 号。

10. 为什么硬链接不能跨文件系统？
    答：硬链接的本质是「同一个 inode 多挂一个目录项」，而 inode 号只在单个文件系统内唯一。跨文件系统时两边 inode 表各自独立，编号相同也不代表同一个文件，内核无法用 inode 号把两个 fs 串起来，所以 `ln` 直接报 Invalid cross-device link。软链接存的是路径字符串、不依赖 inode 号，所以能跨文件系统、跨挂载点。本机 / 是 sda2(ext4)、/boot/efi 是 sda1(vfat)，在 / 里给 /boot/efi 下的文件建硬链接必然失败。

11. ext4 的固定 inode 表和 XFS 的动态分配各自有什么取舍？
    答：ext4 在 mkfs 时就把 inode 总数写进超级块，之后不能改——优点是 df -i 有确定上限、元数据布局紧凑、inode 查找快；缺点是海量小文件会先把 inode 用光（df -h 还有空间却报 No space left on device），事后只能重建文件系统。XFS 按需从空闲空间动态分配 inode，几乎不会 inode 耗尽，代价是没有固定上限、df -i 的数字意义不大（更该看数据块和 xfs_quota）。本机 / 是 ext4：`df -i /` 显示 inodes 60981248、已用 1397376(3%)，这个 60981248 就是建 fs 时定死的上限。

12. 符号链接的权限为什么恒为 rwxrwxrwx（l 位）？
    答：软链自己不承载数据，打开它只是「先读路径、再重定向到目标」，权限检查最终发生在目标文件上（内核路径解析时用目标的 inode 做权限判定），所以软链自身的三段权限位没有实际访问控制意义，内核就统一显示为 lrwxrwxrwx。Linux 下 `chmod` 作用在软链上会跟随到目标文件，想改软链本身得用 `chmod -h`（GNU 扩展）。注意这跟硬链接不同：硬链接就是目标本身，没有独立权限。

13. `chattr +i` 是在哪一层生效的？VFS 还是文件系统？
    答：在文件系统层。immutable 标志存在 inode 的扩展属性区（ext4 的 EXT4_IMMUTABLE_FL，由 lsattr 读出），「是否允许写/改属性/链接/删除」的检查由具体文件系统在 open、unlink、rename 等操作里做，VFS 只在通用路径上放行。所以 +i 只在支持该标志的文件系统上有效（ext2/3/4、XFS、btrfs 等），换到 vfat 这类不支持的文件系统就不生效；另外 root 也不能直接覆盖，必须先 chattr -i。

14. xattr 和 capabilities 是什么关系？
    答：capabilities 是 xattr 的一种具体用途——文件能力就存放在安全命名空间的 xattr 里（security.capability），`getcap /usr/bin/ping` 看到类似 cap_net_raw+ep 即说明该文件带了 capability xattr。所以「怎么备份 capabilities」本质上就是「怎么备份 xattr」：普通 cp/rsync 默认不带 -X/-A 会丢，tar 默认带 security.* 命名空间，但换 fs 不支持 xattr 或用 --no-xattrs 也会丢。本机 root 分区是 ext4，user_xattr 默认开启，无需在挂载选项里显式写。

15. 为什么 `cp` 出来的副本比原文件大很多？稀疏文件在 `ls -l` 里看到的大小和实际占用为什么不一样？
    答：稀疏文件的「逻辑大小」和「实际占用块」是分离的——逻辑上有一堆空洞（内容全 0、没真正落盘），`ls -l` / `stat` 的 Size 显示的是逻辑大小，而 `stat` 的 Blocks（×512）才是真实占用的块数。cp 默认按逻辑大小逐字节读出来再写，会把所有空洞都变成实数据块，副本真实占用因此暴涨。要保留稀疏用 `cp --sparse=always`、`rsync -S`、`tar -S` 或 `dd conv=sparse`。`du -h` 和 `ls -l` 差得多的文件多半就是稀疏文件。

16. `stat` 里有 birth time，为什么 `cp` 之后就不保留了？
    答：birth time（创建时间）是文件系统「分配 inode 那一刻」写下的只读元数据，没有对应的可写系统调用接口——`touch -a/-m/-t` 只能改 atime/mtime，`utimensat` 也设不了 btime。cp/rsync 复制时是在目标 fs 上**新建**一个 inode，btime 自然就是「现在」，源文件的 btime 搬不过去。所以 btime 天生不可复制、不可伪造；只有 mtime/atime 能在 `cp -p` / `rsync -t` 时保留，ctime 也保留不了（它跟着元数据变更走）。

17. relatime 和 noatime 在性能和语义上怎么权衡？
    答：atime 每读一次文件就要更新 inode，写 inode 会带来额外 I/O 和元数据竞争。三种策略：strictatime 每次都更新（语义最准、最慢）；noatime 完全不更新（最快，但破坏依赖 atime 的工具语义，如某些备份/归档/邮件程序判断「未读」）；relatime（默认）只在「atime 早于 mtime/ctime」或「距上次 atime 超过 24 小时」时才更新，兼顾语义正确性和开销。本机 / 的挂载参数就是 rw,relatime（`findmnt /` 可见），tmpfs 也普遍带 relatime。

18. 设备文件的 major/minor 号怎么理解？`/proc/devices` 是干什么的？
    答：设备文件本身不存数据，它只把「打开这个文件」翻译成「用 major:minor 找内核里的设备驱动」。major 号标识用哪个驱动/设备类，minor 号标识这个驱动下的第几个实例。`ls -l /dev/sda` 的大小列显示的就是 `8, 0` 这样的主:次号；`/proc/devices` 列出当前内核已注册的字符/块设备驱动对应的 major 号（名字 ↔ major 对照表），minor 的具体含义由各驱动自己定义。手工 mknod 时 major/minor 抄错，就会打开到错误设备或直接失败。

19. SetUID 有哪些安全风险？noexec / nosuid 挂载选项是干什么的？
    答：SetUID（rws 的 s 位）让程序以文件属主（通常是 root）身份运行，是经典提权面——程序一旦有漏洞（命令注入、路径污染、缓冲区溢出），攻击者就能借它拿到 root。内核因此提供挂载级加固：nosuid 让该挂载点上的 SetUID/SetGID 位失效（不能借它提权），noexec 让该挂载点上的文件不能直接执行（挡住「传到可写分区再执行」的落地攻击）。本机 tmpfs 就是典型：/run 挂载参数是 rw,nosuid,nodev,noexec,relatime（`findmnt -t tmpfs` 可见），/dev/shm 是 nosuid,nodev——把「可写内存盘」当不可信区域加固。

20. umask 怎么影响新建文件的权限？
    答：umask 是一个掩码，新建文件时内核拿基础权限减掉被掩掉的位置。基础权限：普通文件 0666（默认不带执行位，除非显式 chmod 或由编译器创建）、目录 0777。最终权限 = 基础权限 & ~umask。常见取值：022 → 文件 644、目录 755；027 → 文件 640、目录 750；077 → 文件 600、目录 700。umask 是「进程级」属性，只影响之后新建的文件，对已有文件无效，也不像 chmod 那样直接设权限。这也是坑 12 的根源：umask 设成 027/077 后组内成员读不到新建文件。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 判断文件内容类型用 file 命令，别信扩展名（Linux 不靠扩展名）
2. 给程序建别名用软链（ln -s），跨分区、指向目录都行
3. 备份工具按 mtime 增量判断，改权限导致 ctime 变化不会误触发 mtime 备份
4. 排查磁盘不释放先 lsof +L1 找 deleted 文件，重启占用进程
5. 软链要检查目标存在性，避免「断链」在脚本里静默失效
6. 监控 inode 使用率用 df -i，海量小文件场景比 df -h 更早报警
7. 软链目标用绝对路径，避免「相对路径软链 + 移动目录」导致的断链
8. 脚本里取文件属性用 stat -c，字段精确、比解析 ls -l 输出可靠

### 踩坑记录

```text
坑 1：删了日志文件磁盘空间没回来
结论：rm 掉大日志，df 看磁盘还是满的。
原因：进程还持有被删文件的 inode（文件句柄），数据块没释放。
解法：lsof +L1 找 deleted 文件，重启或 kill 占用进程。

坑 2：把硬链接当软链用，以为删原文件软链还在
结论：ln a.txt b.txt 建的是硬链接，删除 a.txt 后 b.txt 内容居然还在。
原因：硬链接指向同一 inode，链接数>1 数据不释放。
解法：明确区分 ln（硬链接）和 ln -s（软链），需要「跟随路径」的用 -s。

坑 3：软链指向被删，脚本静默失败
结论：软链目标删了，脚本读软链拿到空/报错但没显式报。
原因：软链断链后操作目标文件时静默失败。
解法：脚本里先 readlink -f 校验目标存在，或加 set -e 让错误显性。

坑 4：chmod 后备份工具做了全量备份
结论：只改了权限，备份却把文件全量重传。
原因：备份工具用 ctime 判断变化，chmod/chown 都会更新 ctime。
解法：了解备份工具的判据（mtime 还是 ctime），权限变更后手动触发或接受全量。

坑 5：给目录建硬链接失败
结论：ln /data /backup 报 Operation not permitted。
原因：目录不能建硬链接（内核禁止，防环）。
解法：目录共享用软链或 bind mount，别用硬链接。

坑 6：磁盘有空间却报 No space left on device
结论：df -h 还有几百 G，写小文件却报空间不足。
原因：海量小文件把 inode 耗尽了，df -i 显示 100%。
解法：df -i 排查 inode，清理小文件或迁移到 inode 更多的分区。

坑 7：用相对路径建软链，移动目录后断链
结论：ln -s target link 里 target 写的是相对路径，把 link 所在目录挪走后软链失效。
原因：相对软链解析基准是「软链自身所在目录」，不是建链时的工作目录。
解法：软链目标用绝对路径；或用 readlink 确认后再移动，移动后重新建链。

坑 8：chattr +i 之后连 root 都删不掉文件
结论：给关键配置加了 chattr +i，后来升级软件要覆盖它，rm/mv/写入全报 Operation not permitted（不允许的操作）。
原因：+i（immutable）是 inode 属性、比权限更底层，root 也绕不过；它不是「权限不足」，是内核直接拒绝。
解法：先 chattr -i 文件解除，改完再 chattr +i 锁回去；排查时 lsattr 看属性位，别只盯着 ls -l 的权限。

坑 9：cp/tar 备份把 capabilities 和 SELinux 上下文弄丢了
结论：备份还原后给二进制设的 capabilities（如 cap_net_raw）没了，程序行为变了。
原因：capabilities 与 SELinux 上下文都存在 xattr（security.capability / security.selinux）里，
     cp/tar 默认不一定带上，xattr 丢了能力就没了。
解法：备份用 cp --preserve=xattr、rsync -aX、tar --xattrs；还原后用 getcap/restorecon 校验。

坑 10：用 cat 或重定向「拷贝」稀疏文件，磁盘瞬间被撑爆
结论：512M 的稀疏镜像用 cat img > copy 复制后，目标变成实打实的 513M，磁盘告急。
原因：顺序读会把空洞按零填满再写出，空洞结构丢失（本机实测 blocks 从 0 变成 1048584）。
解法：用 cp（现代 coreutils 默认保留空洞）、cp --sparse=always、rsync -S；打包用 tar -cSf 或支持稀疏的格式。

坑 11：chmod 改软链权限，结果改的是被指向的文件
结论：chmod 600 /etc/nginx/sites-enabled/xxx 想「限制软链」，却发现目标文件权限被改成了 600。
原因：软链的权限位恒为 lrwxrwxrwx 且不可改；chmod 默认跟随软链作用到目标（GNU chmod 在目标是软链时甚至拒绝改）。
解法：要知道软链的权限由目标决定；真要限制访问就改目标文件的权限或它所在目录的权限。

坑 12：umask 太严（027/077）导致组内成员读不到新建文件
结论：共享目录里同事新建的文件是 -rw-r-----/-rw-------，同组用户打不开，团队协作失败。
原因：umask 在创建时逐个屏蔽位，新建文件的组权限位被抹掉；目录若没设 SetGID 还会属组错乱。
解法：共享目录统一用 SetGID（chmod g+s）+ 合适的 umask（组内协作常用 002），
     或在目录上配默认 ACL（见 [[05.3-特殊权限与 ACL]]）；注意 systemd 服务默认 UMask=0022，要更严在 unit 里显式写 UMask=。

坑 13：mknod 手工建设备节点，major/minor 抄错或类型搞反
结论：mknod /dev/mytty c 8 0 建出来的节点读写全乱、访问不存在的设备，甚至能裸写磁盘。
原因：major 决定驱动、minor 决定实例，类型（c/b）写反或号码抄错都会指到别的设备上；
     字符设备与块设备不能混用（块设备要按块访问）。
解法：用 /proc/devices 与真实节点（stat -c '%t:%T %F' /dev/xxx）核对号码；优先靠 udev 自动建节点，
     手工建的临时节点用完删掉，权限别放开。
```
