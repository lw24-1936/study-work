## 概述

eBPF（extended Berkeley Packet Filter）让用户态程序在不改内核源码、不重启的前提下，把沙箱化的程序注入内核，在特定事件（系统调用、网络包、函数进出、tracepoint）上执行，用于可观测性、网络、安全和性能分析。bcc 是提供 C/Python 前端 + 大量现成工具的工具集，bpftrace 是类 awk 的高级追踪语言，两者都构建在 eBPF 之上。核心价值是「内核可编程 + 安全（verifier 静态校验）+ 高性能（JIT 编译）」。

```text
eBPF 三大能力：
内核可编程   不重编内核即可挂载程序到 kprobe/tracepoint/XDP/socket 等钩子
安全沙箱      verifier 静态校验（无死循环/越界/非法指针），通过才可加载
高性能        JIT 编译成本地机器码，运行开销极低，适合生产环境持续开启
```

## 核心概念

### eBPF 原理

eBPF 是内核内置的一个寄存器式虚拟机，程序用受限的 C 写（或经编译器），通过 bpf() 系统调用加载，先经 verifier 静态校验（确保不崩溃内核、有界循环、合法内存访问），再 JIT 编译成本地指令，最后挂载到 hook 点。程序通过 map（键值存储）与用户态交换数据，通过 helper 函数（受限的内核函数白名单）获取数据。它从经典 BPF（cBPF，只用于网络包过滤、tcpdump 的过滤表达式）扩展而来，指令集和功能大幅增强。

```c
// 最小 eBPF 程序（C 源码，经 clang 编译成 eBPF 字节码）
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

SEC("tracepoint/syscalls/sys_enter_execve")
int trace_execve(void *ctx)
{
    char comm[16];
    bpf_get_current_comm(&comm, sizeof(comm));   // helper：取当前进程名
    bpf_printk("exec: %s\n", comm);              // 打印到 trace_pipe
    return 0;
}

char LICENSE[] SEC("license") = "GPL";
```

```text
eBPF 执行链路：
用户态写 C → clang 编成 eBPF 字节码 → bpf() 系统调用提交
→ verifier 静态校验 → JIT 编译成本地码 → 挂载到 hook（kprobe/tracepoint/XDP...）
→ 事件触发时执行 → 结果经 map/ringbuf 回传用户态
```

### bcc

bcc（BPF Compiler Collection）是一套工具集 + 前端库，让 eBPF 程序用 Python（或 Lua）写，内嵌的 C 代码在运行时经 clang/LLVM 现场编译成 eBPF 字节码加载。bcc 自带大量现成工具（execsnoop、opensnoop、biotop、tcptop 等），也提供 Python 库（bcc.BPF）用于写自定义追踪器。定位是「生产可用的可观测性工具集 + 快速开发库」。

```bash
# 安装 bcc（Debian/Ubuntu）
sudo apt install bpfcc-tools python3-bpfcc linux-headers-$(uname -r)

# 自带工具（位于 /usr/sbin 或 /usr/share/bcc/tools）
sudo /usr/share/bcc/tools/execsnoop      # 追踪所有 exec 调用
sudo /usr/share/bcc/tools/opensnoop      # 追踪所有 open 调用
sudo /usr/share/bcc/tools/biotop         # 磁盘 IO top
sudo /usr/share/bcc/tools/tcptop         # TCP 流量 top
```

### bpftrace

bpftrace 是一门类 awk 的高级追踪语言，语法极简：`probe /condition/ { action }`，probe 指定挂载点（kprobe/tracepoint/uprobe/usdt），action 里可读参数、聚合、打印。底层自动把脚本转成 eBPF 并加载。适合快速定位问题、临时排查，一行命令就能追踪某个系统调用或函数。

```bpftrace
// 追踪 openat 系统调用：打印进程名和打开的文件
tracepoint:syscalls:sys_enter_openat
{
    printf("%-6d %-16s %s\n", pid, comm, str(args->filename));
}

// 统计每个进程的系统调用次数（Ctrl-C 时输出汇总）
tracepoint:raw_syscalls:sys_enter
{
    @count[comm] = count();
}
```

```bash
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
```

### 可观测性与性能

eBPF 是目前 Linux 可观测性的标准底座，能做四类观测：追踪（tracing，系统调用/函数/kprobe/uprobe）、剖析（profiling，采样 CPU 栈生成火焰图）、网络（socket/XDP 层看流量/丢包/重传）、以及性能计数器（perf event）。相比传统工具（strace 慢、perf 无逻辑、SystemTap 危险），eBPF 安全、低开销、可编程，是生产环境「持续开启」的观测手段。

```text
可观测性四象限（eBPF 覆盖）：
追踪 tracing    系统调用/内核函数进出，参数与返回值（execsnoop/opensnoop）
剖析 profiling  CPU 采样 + 栈，生成火焰图（profile 工具）
网络观测        socket/TC/XDP 层，连接、流量、丢包、重传、延迟
性能事件        perf event / PMC 计数器，缓存未命中、分支预测等
```

## 工作原理

eBPF 完整工作流程分「编译 → 校验 → JIT → 挂载 → 触发 → 回传」六步：

1. **编译**：用户态 C 代码经 clang（`-target bpf`）编成 eBPF 字节码，或 bpftrace 脚本被前端转成 eBPF。
2. **校验 verifier**：内核 verifier 对字节码做静态分析——检查指令数上限、无无限循环（有向图遍历）、所有内存访问有边界检查、指针合法、helper 调用参数合法。任何违反直接拒绝加载。
3. **JIT 编译**：通过校验后，字节码被 JIT 编译成本机架构（x86_64/ARM64）的机器码，执行效率接近原生内核代码。
4. **挂载**：编译后的程序挂到 hook 点——kprobe（内核函数进出）、tracepoint（内核静态埋点）、uprobe（用户态函数）、XDP（网卡驱动早期收包路径）、socket filter、cgroup 等。
5. **触发**：hook 事件发生时（如某系统调用被调用），eBPF 程序在上下文中执行，读取上下文参数（如 openat 的文件名）。
6. **回传**：程序把结果写入 map（哈希/数组/ringbuf 等内核-用户共享存储），用户态程序读 map 聚合、展示。

```text
bpf() 系统调用贯穿全程：
BPF_PROG_LOAD       加载程序（触发 verifier + JIT）
BPF_MAP_CREATE      创建 map
BPF_MAP_UPDATE/LOOKUP  读写 map
BPF_OBJ_PIN         把程序/map 钉到 bpffs（/sys/fs/bpf）持久化
```

## 常用命令与配置

```bash
# 环境检查
uname -r                                   # 内核版本（建议 5.x+ 特性完整）
grep CONFIG_BPF /boot/config-$(uname -r)   # 内核是否启用 BPF（=y）
grep CONFIG_DEBUG_INFO_BTF /boot/config-$(uname -r)  # BTF（CO-RE 需要）

# 查看已加载的 eBPF 程序（bpftool）
sudo bpftool prog list                     # 列出所有加载的程序（id/类型/挂载点）
sudo bpftool prog show id 123              # 看某个程序的详情
sudo bpftool prog dump xlated id 123       # 反汇编（字节码/机器码）
sudo bpftool map list                      # 列出所有 map
sudo bpftool map dump id 10                # dump 某个 map 内容

# 挂载 bpffs（程序持久化）
sudo mount -t bpf bpf /sys/fs/bpf          # 挂载 bpffs
ls /sys/fs/bpf                             # 看 pinned 的程序/map

# 运行 bpftrace / bcc 工具
sudo bpftrace -l 'tracepoint:syscalls:*'   # 列出可用 tracepoint
sudo bpftrace -l 'kprobe:do_sys_open*'     # 列出可挂的 kprobe 点
```

```text
eBPF 运行前置条件：
1. 内核 4.x+（5.x/6.x 特性更完整：BTF/CO-RE/ringbuf）
2. root 权限（或 CAP_BPF/CAP_PERFMON 能力）
3. 内核头文件（bcc 现场编译需要）+ clang/llvm
4. CONFIG_BPF=y、CONFIG_DEBUG_INFO_BTF=y（BTF 类型信息）
```

## 配置文件解析

eBPF 本身无传统配置文件，配置主要体现在「内核 config」和「bpftool 特性探测」：

```bash
# /boot/config-$(uname -r) —— 内核 BPF 相关编译开关
CONFIG_BPF=y                  # 必须
CONFIG_BPF_SYSCALL=y          # bpf() 系统调用
CONFIG_BPF_JIT=y              # JIT 编译（强烈建议，否则解释执行慢）
CONFIG_BPF_JIT_ALWAYS_ON=y    # 强制 JIT（防 JIT 喷射攻击面）
CONFIG_BPF_EVENTS=y           # perf/kprobe 事件支持
CONFIG_DEBUG_INFO_BTF=y       # BTF 类型信息（CO-RE 可移植性基础）
CONFIG_BPF_LSM=y              # BPF LSM（安全模块）支持

# /proc/sys/net/core/bpf_jit_enable —— 运行时 JIT 开关
cat /proc/sys/net/core/bpf_jit_enable   # 1 = 开 0 = 关
```

```text
配置要点：
CONFIG_BPF_JIT          JIT 编译，解释执行慢 10 倍以上，生产必开
CONFIG_DEBUG_INFO_BTF   内核 BTF 类型信息，bpftrace/bcc 的 CO-RE（一次编译到处运行）依赖它
bpf_jit_enable          运行时开关，写 1 开启 JIT（多数发行版默认开）
```

## 应用场景实战

### 场景一：用 bpftrace 追踪 openat 并统计各进程打开文件数

```bash
# 一条命令追踪 openat：打印进程、PID、打开的文件名
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%-6d %-16s %s\n", pid, comm, str(args->filename)); }'
```

```text
示例输出：
PID    COMM             FILE
12034  nginx            /var/log/nginx/access.log
12034  nginx            /etc/nginx/nginx.conf
998    sshd             /etc/passwd
```

```bash
# 统计每个进程的 openat 次数（Ctrl-C 输出汇总）
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @count[comm] = count(); }'
```

```text
示例输出（Ctrl-C 后）：
@count[nginx]: 1203
@count[sshd]: 87
@count[systemd]: 45
```

### 场景二：用 bcc Python 写一个 exec 追踪器

```python
#!/usr/bin/env python3
# exec_tracer.py — bcc Python 追踪所有 execve 调用
from bcc import BPF

prog = """
#include <uapi/linux/ptrace.h>
#include <linux/sched.h>

TRACEPOINT_PROBE(syscalls, sys_enter_execve) {
    char comm[16];
    bpf_get_current_comm(&comm, sizeof(comm));
    bpf_trace_printk("exec: %-16s pid=%d\\n", comm, bpf_get_current_pid_tgid() >> 32);
    return 0;
}
"""

b = BPF(text=prog)
print("Tracing execve... Ctrl-C to exit")
try:
    b.trace_print()
except KeyboardInterrupt:
    pass
```

```bash
sudo python3 exec_tracer.py
```

```text
示例输出：
exec: bash           pid=12034
exec: ls             pid=12035
exec: grep           pid=12036
```

```text
场景对照：
bpftrace 适合 —— 临时排查、一行命令快速看结果、不写复杂逻辑
bcc Python 适合 —— 需要自定义 map 聚合、输出格式、和业务逻辑集成的场景
两者底层都是 eBPF，区别在「写法的抽象层级」
```

## 性能与调优

```text
1. JIT 必开 —— 解释执行比 JIT 慢 10 倍以上，确认 bpf_jit_enable=1、CONFIG_BPF_JIT=y
2. 用 map 聚合而非逐条打印 —— bpf_trace_printk 每次输出都走 trace_pipe，高频会拖慢系统；先用 map 计数，最后一次性输出
3. 用 ringbuf 替代 perf buffer —— 新内核 ringbuf 支持多 CPU 各自独立缓冲区、无锁、内存效率更高
4. 采样优于全量追踪 —— 高频事件（如每个网络包）用采样（perf event 采样）代替全量挂载，降低开销
5. 挂载点选开销最小的 —— tracepoint 比 kprobe 稳定（kprobe 依赖函数符号可能变）；能在驱动早期做的用 XDP（最快）
6. CO-RE（一次编译到处运行）—— 依赖内核 BTF，避免为每个内核版本重编，bcc 5.x+/libbpf 生态已支持
7. 生产常驻工具控制输出频率 —— 聚合输出限流、直方图代替逐条打印，避免观测本身成为瓶颈
```

## 安全与权限

```text
1. verifier 是第一道防线 —— 程序必须通过静态校验（无越界、无死循环、指针合法），未通过直接拒绝，这是 eBPF 能进内核的核心安全保证
2. 能力分离（5.6+）—— 不再必须 root：CAP_BPF（加载程序）+ CAP_PERFMON（读 perf 数据）+ CAP_NET_ADMIN（网络类），按最小能力授权
3. 限制非特权加载 —— kernel.unprivileged_bpf_disabled=1 时只有特权用户能加载 eBPF，防普通用户注入恶意程序
4. 防 JIT 攻击面 —— CONFIG_BPF_JIT_ALWAYS_ON + 常量盲化（constant blinding），防止把可写内存转成可执行代码（JIT spraying）
5. 别用 --unsafe 绕过校验 —— bcc 有 debug 选项可跳过部分检查，仅限受控调试环境，生产禁用
6. 追踪敏感数据要克制 —— eBPF 能读到密码/密钥（如 open 的文件内容、socket 数据），追踪器本身要最小权限部署、输出脱敏
```

## 故障排查

### bpftrace 报「Error attaching probe」/ 权限错误

```bash
# 确认以 root 跑，或检查能力
sudo bpftrace -e 'kprobe:do_sys_open { @ = count(); }'
# 报 Operation not permitted -> 检查非特权 BPF 是否被禁
cat /proc/sys/kernel/unprivileged_bpf_disabled   # 1 = 非特权禁用
```

### 报「BTF: type data not found」/ CO-RE 相关错误

```bash
# BTF 信息缺失，检查内核是否带 BTF
ls /sys/kernel/btf/vmlinux                        # 有 = 正常
grep CONFIG_DEBUG_INFO_BTF /boot/config-$(uname -r)  # 应为 y
# 缺失则用非 CO-RE 工具（老版本 bcc 工具）或升级内核
```

### 程序加载失败（verifier 拒绝）

```bash
# 看详细拒绝原因
sudo bpftool prog load prog.o /sys/fs/bpf/prog 2>&1
# 或用 bcc 看 verifier log：BPF(text=prog, debug=4) 会打印 verifier 详细日志
# 常见：访问未初始化的 map、循环无界、栈越界、helper 参数类型错
```

### eBPF 程序已加载但看不到输出

```bash
# bpf_trace_printk 的输出在 trace_pipe
sudo cat /sys/kernel/debug/tracing/trace_pipe
# 确认挂载点被触发（比如 openat 事件有没有发生）
sudo bpftool prog list | grep kprobe
```

## 常见问题

```text
Q1: eBPF 和传统 BPF（cBPF）什么关系？
A: cBPF 是早期的包过滤虚拟机（tcpdump 的过滤表达式编译成它），只有两个寄存器、只能挂在网络包路径。eBPF 是它的扩展：10 个寄存器、可挂到 kprobe/tracepoint/XDP 等任意钩子、有 map 和 helper、JIT 编译，从「包过滤」扩展成「内核通用可编程引擎」。

Q2: eBPF 程序为什么安全？会不会搞崩内核？
A: 靠 verifier 静态校验：加载前逐个指令检查，保证程序无死循环（有界）、所有内存访问有边界、指针合法、helper 参数类型正确。校验不过就拒绝加载，所以理论上不会崩溃内核。加上 JIT 常量盲化等防攻击措施。

Q3: bcc 和 bpftrace 怎么选？
A: bpftrace 语法极简（类 awk），适合临时排查、一行命令快速看结果；bcc 用 Python 写，能自定义 map、聚合逻辑、输出格式，适合做长期运行的监控工具或集成进现有系统。底层都是 eBPF。

Q4: 为什么有时需要 root，有时普通用户也行？
A: 老内核加载 eBPF 要 root。5.6+ 引入能力分离：CAP_BPF 加载程序、CAP_PERFMON 读 perf 数据、CAP_NET_ADMIN 网络操作，可按最小能力授权给非 root 用户（如容器）。kernel.unprivileged_bpf_disabled=1 时则强制只有特权用户。

Q5: 什么是 CO-RE？为什么重要？
A: CO-RE（Compile Once, Run Everywhere）依赖内核 BTF 类型信息，让 eBPF 程序不用为每个内核版本重新编译，一次编译到处运行。没有它，访问内核结构体字段要靠硬编码偏移（内核一变就失效），是 eBPF 生态可维护性的关键。
```

## 面试题

```text
1. eBPF 是什么？和内核模块相比有什么优势？
   答：eBPF 是内核内置的沙箱化虚拟机，用户态程序经 verifier 校验后注入内核在 hook 点执行，用于可观测性/网络/安全。相比内核模块：不需要重编内核、verifier 保证不崩溃内核、JIT 性能高、可动态挂载/卸载、更安全（模块一旦写错直接 panic）。

2. verifier 做了什么？为什么是 eBPF 安全性的关键？
   答：verifier 对字节码做静态分析：遍历指令图确保无死循环（有界执行）、所有内存访问有边界检查、寄存器/指针类型合法、helper 调用参数正确。任何违反拒绝加载。它保证注入内核的代码不会访问非法内存、不会无限循环，是「允许用户代码进内核」的安全前提。

3. eBPF 程序怎么和用户态交换数据？
   答：通过 map（内核-用户共享的键值存储）和 ringbuf/perf buffer。eBPF 程序把结果写入 map（如直方图、计数），用户态程序读 map 聚合展示。map 由 bpf() 系统调用的 BPF_MAP_CREATE 创建，可 pinned 到 /sys/fs/bpf 跨进程共享。

4. kprobe 和 tracepoint 区别？
   答：kprobe 动态插桩任意内核函数（无需内核预埋点，灵活但依赖函数符号、可能随内核版本变），tracepoint 是内核预埋的静态埋点（稳定、有 ABI 保证、开销更低，但只能挂内核定义好的点）。性能敏感和长期维护优先 tracepoint，临时探任意函数用 kprobe。

5. XDP 是什么？为什么快？
   答：XDP（eXpress Data Path）是网卡驱动收到包后最早期的处理钩子，在包进入内核网络栈、分配 skb 之前直接处理，可做丢包/转发/修改。因为跳过了内核网络栈的绝大部分处理，且可在网卡硬件上 offload，延迟和吞吐远优于传统 netfilter/iptables。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 能用 tracepoint 就不用 kprobe（tracepoint 稳定、开销低、有 ABI 保证）
2. 高频事件用 map 聚合 + 限流输出，别逐条 bpf_trace_printk
3. 开启 BTF/CO-RE，一次编译到处运行，避免为每个内核版本维护程序
4. 生产用 bpftool 把程序/map pin 到 /sys/fs/bpf，实现进程间共享和持久化
5. 按最小能力授权（CAP_BPF/CAP_PERFMON），别一律 root；追踪输出脱敏
6. 观测工具本身设开销预算，采样代替全量、直方图代替逐条，别让监控拖垮系统
7. 新特性优先用 ringbuf 替代 perf buffer（无锁、多 CPU 独立、内存效率高）

### 踩坑记录

```text
坑 1：高频事件逐条 printf 把系统拖慢
结论：开了追踪器后系统负载骤升、应用变慢。
原因：bpf_trace_printk 每次输出都写 trace_pipe，高频事件（每个包/每次 syscall）下成为瓶颈。
解法：先写 map 聚合，结束或按间隔输出；输出用限流和直方图。

坑 2：kprobe 挂的函数名随内核版本变了，程序失效
结论：内核升级后追踪器 attach 失败或静默无数据。
原因：kprobe 依赖内核函数符号，函数改名/被内联后挂载点不存在。
解法：优先 tracepoint；确需 kprobe 时用 bpftool 探测符号是否存在，或用 CO-RE 适配。

坑 3：忘开 BTF 导致 CO-RE 工具报 type data not found
结论：bpftrace/bcc 新版工具运行报 BTF 相关错误。
原因：内核没编 CONFIG_DEBUG_INFO_BTF，/sys/kernel/btf/vmlinux 不存在。
解法：升级带 BTF 的内核，或用不依赖 BTF 的旧版工具（老 bcc 工具按偏移硬编码）。

坑 4：普通用户跑 bpftrace 报 Operation not permitted
结论：非 root 用户执行追踪命令失败。
原因：老内核要 root；新内核有 CAP_BPF/CAP_PERFMON 但未授权，或 unprivileged_bpf_disabled=1 禁了非特权加载。
解法：root 跑，或给用户/容器授予 CAP_BPF+CAP_PERFMON 能力；检查并调整 unprivileged_bpf_disabled。

坑 5：verifier 拒绝程序却看不懂报错
结论：程序 load 失败，报一堆寄存器/边界错误。
原因：常见是循环无界、访问未初始化 map、栈越界、helper 参数类型不符，verifier 日志晦涩。
解法：bcc 用 BPF(text=prog, debug=4) 看 verifier 详细日志；循环给编译期可判定的上界；栈用 BPF_STACK 宏管理。

坑 6：把 eBPF 当万能药，观测成本失控
结论：长期开启大量追踪器，监控系统本身吃掉可观 CPU。
原因：每个挂载点都有固定开销（事件触发执行 + map 写），叠加多个高频追踪器成本很高。
解法：按需开启、采样代替全量、设置观测开销预算，追踪器本身也要被监控。
```
