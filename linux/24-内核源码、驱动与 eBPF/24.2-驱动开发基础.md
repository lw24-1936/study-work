## 概述

Linux 驱动是运行在内核空间、负责管理硬件设备的内核代码。字符设备是最常见、最基础的一类设备模型（键盘、串口、/dev/null 等），以字节流方式访问；设备树是描述硬件拓扑与资源配置的数据结构（ARM/嵌入式平台的标准做法）；模块开发是「按需加载/卸载内核代码」的标准开发方式，不必每次改代码都重编整个内核；内核调试则依赖 printk、动态调试、ftrace、kprobe、crash dump 这套工具链。四者构成驱动开发从「写代码 → 加载 → 跑起来 → 排查」的完整闭环。

```text
驱动开发四大知识点：
字符设备   内核三大设备模型之一，/dev 下的字节流设备，file_operations 定义行为
设备树     硬件描述语言（.dts → .dtb），让内核「自动发现」平台设备并绑定驱动
模块开发   内核模块 = 动态加载的内核代码，module_init / module_exit 生命周期
内核调试   printk + 动态调试 + ftrace + kprobe + crash dump
```

## 核心概念

### 字符设备

Linux 把设备分三类：字符设备（char，按字节流顺序访问，如 /dev/tty、/dev/null、键盘）、块设备（block，按块随机访问，如磁盘）、网络设备（net，收发网络包，无设备节点）。字符设备通过「主设备号 major + 次设备号 minor」标识：主设备号对应驱动、次设备号区分同一驱动的多个实例。用户态通过 /dev 下的设备节点访问，open/read/write/ioctl 系统调用最终落到驱动 file_operations 结构体里对应的函数指针。

```c
// file_operations：字符设备的行为接口（简化示意）
struct file_operations fops = {
    .owner   = THIS_MODULE,
    .read    = dev_read,      // 应用 read()  -> 这里
    .write   = dev_write,     // 应用 write() -> 这里
    .open    = dev_open,      // 应用 open()  -> 这里
    .release = dev_release,   // 应用 close() -> 这里
    .unlocked_ioctl = dev_ioctl,  // 应用 ioctl() -> 这里
};
```

```text
字符设备要点：
主设备号 major  对应驱动（register_chrdev 注册时指定或动态分配）
次设备号 minor  区分同一驱动的多个设备实例
设备节点        /dev/xxx，由 mknod 或 udev 自动创建，是用户态访问的入口
```

### 设备树

设备树（Device Tree，DT）是一种描述硬件的数据结构：用 .dts（device tree source）源码书写，经 dtc 编译器编译成 .dtb（binary）二进制，由 bootloader（U-Boot）加载进内存传给内核。内核启动时解析它，把每个节点实例化成 platform_device，让驱动通过 platform_driver 的 compatible 匹配来「发现」并绑定设备。相比 x86 的 ACPI/自动枚举，设备树解决了 ARM 等平台「硬件不可枚举、配置各异」的问题——同一份内核镜像 + 不同 .dtb 即可适配不同板卡。

```dts
// example.dts — 设备树源码片段
/dts-v1/;

/ {
    compatible = "vendor,myboard";
    #address-cells = <1>;
    #size-cells    = <1>;

    mydev: mydevice@10000000 {
        compatible = "vendor,mydriver";   // 与驱动的 of_device_id 匹配
        reg = <0x10000000 0x1000>;        // 寄存器基址 + 长度
        interrupts = <0 25 4>;            // 中断号（含触发类型）
        status = "okay";                  // 使能该节点
    };
};
```

```bash
# 编译 / 反编译设备树
dtc -I dts -O dtb -o example.dtb example.dts      # .dts -> .dtb
dtc -I dtb -O dts -o example.dts example.dtb      # .dtb -> .dts（反编译）

# 查看运行内核解析后的设备树
ls /sys/firmware/devicetree/base/                 # 根节点
cat /sys/firmware/devicetree/base/mydevice@10000000/compatible   # 读 compatible
```

### 模块开发

内核模块是「运行时可加载/卸载」的内核代码，是驱动开发的标准形态——不必每次改代码都重编整个内核。模块有明确的生命周期：module_init 注册加载入口（insmod 时调用）、module_exit 注册注销（rmmod 时调用）。模块通过 insmod 加载、rmmod 卸载、modprobe 自动处理依赖。模块必须在「与运行内核同版本」的内核源码树/头文件下编译。

```c
// hello_module.c — 最小可编译内核模块
#include <linux/module.h>
#include <linux/kernel.h>

static int __init hello_init(void)
{
    printk(KERN_INFO "hello: module loaded\n");
    return 0;                 // 返回非 0 表示加载失败
}

static void __exit hello_exit(void)
{
    printk(KERN_INFO "hello: module unloaded\n");
}

module_init(hello_init);      // 加载入口
module_exit(hello_exit);      // 卸载入口

MODULE_LICENSE("GPL");        // 许可证，非 GPL 会触发内核 taint 警告
MODULE_AUTHOR("study-notes");
MODULE_DESCRIPTION("minimal kernel module");
```

```makefile
# Makefile — 对接内核 Kbuild 体系
obj-m += hello_module.o

KERNEL_DIR ?= /lib/modules/$(shell uname -r)/build

all:
	make -C $(KERNEL_DIR) M=$(PWD) modules
clean:
	make -C $(KERNEL_DIR) M=$(PWD) clean
```

```bash
make                              # 编译出 hello_module.ko
sudo insmod hello_module.ko       # 加载
sudo lsmod | grep hello           # 确认已加载
sudo rmmod hello_module           # 卸载
dmesg | tail                      # 看 printk 输出
```

### 内核调试

内核没有像用户态那样方便的 gdb 单步调试（要 kgdb 双机或 qemu），日常调试主要靠「打点输出 + 动态追踪 + 崩溃转储」：printk 是最基本的日志（分级 KERN_DEBUG~KERN_EMERG，看 dmesg），dynamic debug 可运行时开关指定文件的 pr_debug，ftrace 是内核自带函数级追踪器，kprobe 可动态插桩任意内核函数，crash dump（kdump/kexec + crash 工具）用于内核 panic 后离线分析现场。

```bash
# printk 分级输出，看内核日志
dmesg | tail -50
echo 8 > /proc/sys/kernel/printk   # 提升控制台日志级别（8 = 全部上屏）

# dynamic debug：运行时打开某模块的 pr_debug
echo 'module hello_module +p' > /sys/kernel/debug/dynamic_debug/control

# ftrace：追踪某个内核函数
cd /sys/kernel/debug/tracing
echo function > current_tracer
echo do_sys_open > set_ftrace_filter
cat trace                         # 看 do_sys_open 的调用记录
echo nop > current_tracer          # 关闭

# kprobe：动态插桩任意函数
echo 'p:myprobe do_sys_open filename=+0(%si):string' > kprobe_events
echo 1 > events/kprobes/myprobe/enable
cat trace
echo 0 > events/kprobes/myprobe/enable
```

```text
内核调试手段对比：
printk        最简单，生产环境可能刷屏，靠分级过滤
dynamic debug 运行时开关、无需重编，pr_debug 专属
ftrace        函数级追踪 + 调用图，开销低，定位性能/调用路径
kprobe        任意函数插桩、无源码侵入，定位变量值
crash dump    内核 panic 时存内存镜像，离线分析死机现场
```

## 工作原理

驱动工作的核心是「注册 → 匹配 → 回调」：

1. **模块加载**：insmod 把 .ko 载入内核，调用 module_init 注册的 init 函数，init 里 register_chrdev 向 VFS 注册字符设备（拿到主设备号），再 class_create + device_create 创建 /dev 节点。
2. **用户态打开设备**：应用 open("/dev/hello")，VFS 根据设备节点的主次设备号找到对应的 file_operations，生成 struct file 并调用驱动的 open。
3. **读写回调**：read/write 系统调用经 VFS 转到驱动的 read/write，驱动通过 copy_to_user/copy_from_user 在内核态和用户态之间搬运数据，或直接操作硬件寄存器（ioremap + readl/writel）。
4. **硬件交互**：驱动通过 request_irq 注册中断处理、ioremap 映射寄存器、DMA 搬数据，把硬件行为翻译成 VFS 语义。
5. **模块卸载**：rmmod 调 module_exit，注销设备号、销毁节点、释放资源。

```text
字符设备读写调用链：
用户态 read(fd) → sys_read 系统调用 → VFS → 驱动的 fops->read
        → copy_to_user(buf, kbuf, len) → 返回用户态

中断路径：硬件中断 → 驱动 ISR（request_irq 注册）→ 唤醒等待队列 → read 返回数据
```

## 常用命令与配置

```bash
# 模块生命周期
insmod module.ko              # 加载（不处理依赖）
rmmod module                  # 卸载
modprobe module               # 加载并自动处理依赖（读 modules.dep）
modprobe -r module            # 卸载并处理依赖
lsmod                         # 列出已加载模块（Size / Used by）
modinfo module.ko             # 看模块元信息（参数/许可证/依赖）
depmod -a                     # 重建模块依赖库

# 设备节点
mknod /dev/hello c 240 0      # 手工创建字符设备节点（主 240 次 0）
ls -l /dev/hello              # 看设备号（c 开头 = 字符设备）

# 内核日志与符号
dmesg | tail -50              # 看 printk 输出
dmesg -w                      # 实时跟踪内核日志
cat /proc/modules             # 已加载模块（同 lsmod）
cat /proc/devices             # 已注册的主设备号及名称
cat /proc/iomem               # 物理内存地址映射（寄存器）
cat /proc/interrupts          # 中断统计

# 模块参数
modinfo -p module.ko          # 看模块可接受的参数
insmod module.ko param=value  # 加载时传参
```

```text
模块加载要点：
insmod vs modprobe  insmod 只加载单个 .ko，modprobe 会先加载依赖模块（读 modules.dep）
rmmod 失败原因     模块被引用（lsmod 看 Used by 列）或没配 module_exit
printk 等级        KERN_EMERG(0) ~ KERN_DEBUG(7)，数字越大越不紧急，控制台默认只显示一定级别以上
```

### 内核模块 Makefile

```makefile

obj-m += hello_module.o         # 目标模块（m = 编译为模块，y = 编进内核）
hello_module-objs := a.o b.o   # 多文件模块

KERNEL_DIR ?= /lib/modules/$(shell uname -r)/build   # 内核构建目录
PWD := $(shell pwd)

all:
	make -C $(KERNEL_DIR) M=$(PWD) modules   # 进入内核构建系统编译
```

```text
Makefile 要点：
obj-m           声明编译为模块；多源文件用 <name>-objs 指定
KERNEL_DIR      指向运行内核的构建目录（/lib/modules/$(uname -r)/build）
-C ... M=...    内核 Kbuild 系统从 M 目录取源码编译，生成 .ko
版本一致性      .ko 必须与运行内核版本一致，否则 insmod 报 Invalid module format
```

## 应用场景实战

### 场景一：从零写一个可读写的字符设备驱动

完整可编译的字符设备驱动，加载后 /dev/hello_chrdev 可读可写：

```c
// hello_chrdev.c — 完整字符设备驱动（可读可写）
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/uaccess.h>
#include <linux/device.h>
#include <linux/string.h>

#define DEVICE_NAME "hello_chrdev"
#define CLASS_NAME  "hello"

static int major_num;
static char msg[256] = "hello from kernel\n";
static struct class  *my_class;
static struct device *my_device;

static ssize_t dev_read(struct file *fp, char __user *buf,
                        size_t len, loff_t *off)
{
    size_t n = strlen(msg);
    if (*off >= n)
        return 0;                            // EOF
    if (len > n - *off)
        len = n - *off;
    if (copy_to_user(buf, msg + *off, len))  // 内核态 -> 用户态
        return -EFAULT;
    *off += len;
    return len;
}

static ssize_t dev_write(struct file *fp, const char __user *buf,
                         size_t len, loff_t *off)
{
    if (len > sizeof(msg) - 1)
        len = sizeof(msg) - 1;
    if (copy_from_user(msg, buf, len))       // 用户态 -> 内核态
        return -EFAULT;
    msg[len] = '\0';
    return len;
}

static struct file_operations fops = {
    .owner = THIS_MODULE,
    .read  = dev_read,
    .write = dev_write,
};

static int __init chrdev_init(void)
{
    major_num = register_chrdev(0, DEVICE_NAME, &fops);   // 0 = 动态分配主设备号
    if (major_num < 0) {
        printk(KERN_ALERT "hello_chrdev: register_chrdev failed\n");
        return major_num;
    }
    my_class = class_create(THIS_MODULE, CLASS_NAME);     // 用于 udev 自动建节点
    if (IS_ERR(my_class)) {
        unregister_chrdev(major_num, DEVICE_NAME);
        return PTR_ERR(my_class);
    }
    my_device = device_create(my_class, NULL, MKDEV(major_num, 0),
                              NULL, DEVICE_NAME);          // 自动创建 /dev/hello_chrdev
    if (IS_ERR(my_device)) {
        class_destroy(my_class);
        unregister_chrdev(major_num, DEVICE_NAME);
        return PTR_ERR(my_device);
    }
    printk(KERN_INFO "hello_chrdev: loaded, major=%d\n", major_num);
    return 0;
}

static void __exit chrdev_exit(void)
{
    device_destroy(my_class, MKDEV(major_num, 0));
    class_destroy(my_class);
    unregister_chrdev(major_num, DEVICE_NAME);
    printk(KERN_INFO "hello_chrdev: unloaded\n");
}

module_init(chrdev_init);
module_exit(chrdev_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("study-notes");
MODULE_DESCRIPTION("minimal read/write char device driver");
```

```makefile
# Makefile
obj-m += hello_chrdev.o
KERNEL_DIR ?= /lib/modules/$(shell uname -r)/build

all:
	make -C $(KERNEL_DIR) M=$(PWD) modules
clean:
	make -C $(KERNEL_DIR) M=$(PWD) clean
```

```bash
make                              # 生成 hello_chrdev.ko
sudo insmod hello_chrdev.ko
ls -l /dev/hello_chrdev           # 设备节点已自动创建（c 开头，主设备号动态分配）
cat /dev/hello_chrdev             # 读到 "hello from kernel"
echo "hi from userspace" > /dev/hello_chrdev   # 写入
cat /dev/hello_chrdev             # 读回 "hi from userspace"
sudo rmmod hello_chrdev           # 卸载，/dev 节点自动消失
```

```text
流程：写驱动 C 代码 → Makefile → make 出 .ko → insmod 加载 → /dev 节点自动出现 → 读写验证 → rmmod
register_chrdev(0,...) 传 0 让内核动态分配主设备号，避免和已有设备冲突
class_create + device_create 让 udev 自动在 /dev 下建节点，省去手工 mknod
```

### 场景二：带模块参数的驱动（运行时配置）

给驱动加模块参数，加载时从命令行传参、运行时从 /sys 读写：

```c
// param_demo.c — 带模块参数的驱动（节选核心部分）
#include <linux/module.h>
#include <linux/kernel.h>

static int count = 1;                    // 默认值
static char *name = "default";

module_param(count, int, S_IRUGO);       // 参数名 / 类型 / 权限（0644 只读）
module_param(name, charp, S_IRUGO);      // charp = 字符串指针
MODULE_PARM_DESC(count, "device count");
MODULE_PARM_DESC(name, "device name");

static int __init demo_init(void)
{
    printk(KERN_INFO "param_demo: count=%d name=%s\n", count, name);
    return 0;
}
static void __exit demo_exit(void) {}
module_init(demo_init);
module_exit(demo_exit);
MODULE_LICENSE("GPL");
```

```bash
sudo insmod param_demo.ko count=4 name="mydev"   # 加载时传参
dmesg | tail -1                                  # 示例输出：param_demo: count=4 name=mydev
cat /sys/module/param_demo/parameters/count       # 运行时读参数（示例输出：4）
```

```text
module_param 三要素：变量名、类型（int/bool/charp/数组）、sysfs 权限（S_IRUGO 只读，S_IRUGO|S_IWUSR 可写）
加载后参数可在 /sys/module/<name>/parameters/ 下读写（权限允许时）
```

## 性能与调优

```text
1. 中断处理要快 —— ISR 只做必要的事（读寄存器、清中断），重活丢给下半部（tasklet / workqueue / threaded irq），避免长时间关中断
2. 减少内核态/用户态拷贝 —— 高频小数据用 mmap 直接映射，大数据用 DMA 绕过 CPU
3. 自旋锁 vs 互斥锁 —— 临界区极短（纳秒级）且可能在原子上下文用 spinlock，可能睡眠用 mutex；别在 spinlock 里 sleep
4. 批量处理 —— 读写用环形缓冲区，一次系统调用搬多块，降低系统调用和锁竞争开销
5. 打印克制 —— 热路径别用 printk（会拖慢并刷爆日志），用 tracepoint / 计数器替代
6. 内存分配 —— 高频分配用内存池/预分配，避免频繁 kmalloc 带来的碎片和延迟
```

## 安全与权限

```text
1. 用户态指针必须校验 —— copy_to_user / copy_from_user 是唯一安全的搬运方式，绝不能用 memcpy 直接读用户态指针（可被篡改导致内核崩溃/提权）
2. 长度与边界检查 —— read/write/ioctl 的参数先校验（count、索引、越界），防止缓冲区溢出
3. 模块签名与 Secure Boot —— 内核启用模块签名后，未签名的 .ko 无法加载，防恶意模块注入
4. 权限最小化 —— /dev 节点、sysfs 参数文件的权限设最小（如参数只读 S_IRUGO），ioctl 里校验能力（capable(CAP_SYS_ADMIN)）
5. 许可证与 taint —— 非 GPL 模块加载会让内核进入 tainted 状态，厂商调试时可能拒绝支持，谨慎用专有模块
6. 别直接访问任意物理地址 —— 寄存器必须 ioremap 后通过 readl/writel 访问，禁止裸指针访问，防止踩到保留内存
```

## 故障排查

### 模块加载失败

```bash
dmesg | tail                       # 看具体报错（最常见入口）
# 常见报错：
# Unknown symbol xxx         -> 缺依赖（modprobe 代替 insmod，或 export 符号）
# Invalid module format      -> 内核版本不匹配（重编）
# disagrees about version    -> 编译用的头文件与运行内核不一致
modinfo module.ko                 # 核对 vermagic 与运行内核版本
uname -r                          # 运行内核版本
```

### 驱动加载了但设备节点没出现

```bash
ls /dev | grep hello               # 看节点在不在
cat /proc/devices | grep hello     # 看主设备号注册了没
# 没注册 -> init 里 register_chrdev 失败，看 dmesg
# 注册了没节点 -> 没调 device_create / 没装 udev，手工 mknod 兜底：
sudo mknod /dev/hello c 240 0      # 240 换成 /proc/devices 里的实际主设备号
```

### 读写返回错误 / 数据不对

```bash
dmesg | tail                       # 看驱动有没有打错误日志
# 常见：copy_to_user 失败（EFAULT，用户缓冲非法）
# read 返回 0 但设备有数据 -> 驱动 off 计算错 / 缓冲区没刷新
cat /proc/interrupts                # 若是中断设备，看中断次数有没有涨（没涨 = 中断没触发/没注册）
```

### 内核 panic / oops 定位

```bash
dmesg | grep -A20 "Oops"           # 找 oops 的 RIP、调用栈、寄存器
# 用 addr2line 把地址翻译成源码行：
addr2line -e hello_chrdev.ko 0x1a3   # 0x1a3 是 oops 里的偏移
# 更完整：配 kdump + crash 工具离线分析 vmcore
```

## 常见问题

```text
Q1: insmod 和 modprobe 区别？
A: insmod 只加载指定的单个 .ko，不处理依赖；modprobe 会读 modules.dep 自动加载依赖模块，还支持配置参数和黑名单。日常用 modprobe，测试单个新模块用 insmod。

Q2: 为什么模块编译报错「/lib/modules/xxx/build 不存在」？
A: 没装对应运行内核的构建环境。安装内核头文件/开发包：Debian 系 sudo apt install linux-headers-$(uname -r)，Red Hat 系 sudo dnf install kernel-devel。

Q3: 主设备号是什么？为什么要动态分配？
A: 主设备号标识「哪类设备（哪个驱动）」，次设备号区分同类设备的实例。老驱动写死主设备号，新驱动 register_chrdev(0,...) 让内核动态分配，避免和已占用号冲突（冲突会导致设备行为错乱）。

Q4: rmmod 报「Module is in use」怎么办？
A: 模块被引用（有进程打开着 /dev 节点，或被其他模块依赖）。lsmod 看 Used by 列找到占用者，关掉对应进程/先卸载依赖模块，再 rmmod。

Q5: printk 的输出去哪了？为什么终端看不到？
A: printk 输出进内核环形缓冲（dmesg 查看），是否刷到控制台取决于消息级别和 /proc/sys/kernel/printk 的 console_loglevel。级别数字大于 console_loglevel 的才上屏，KERN_INFO(6) 默认不上屏。
```

## 面试题

```text
1. Linux 有哪几类设备？字符设备和块设备区别？
   答：字符设备、块设备、网络设备三类。字符设备按字节流顺序访问（键盘、串口、/dev/null），无缓存、不随机寻址；块设备按块随机访问（磁盘），有页缓存，可挂载文件系统。网络设备不映射 /dev 节点，通过 socket 收发。

2. 用户态 read 系统调用是怎么到达驱动的 read 函数的？
   答：用户态 read(fd) → glibc 封装 → sys_read 系统调用陷入内核 → VFS 根据 fd 找到 struct file 和对应的 file_operations → 调用 fops->read → 驱动 read 里 copy_to_user 把内核数据拷回用户态。

3. 设备树解决了什么问题？compatible 属性怎么用？
   答：设备树用数据结构描述硬件拓扑和资源，解决 ARM 等平台硬件不可枚举、配置各异的问题，同一内核镜像 + 不同 dtb 适配不同板卡。驱动里 of_device_id 表的 compatible 字符串与设备树节点 compatible 匹配，内核据此把节点绑定到对应 platform_driver。

4. 模块加载流程？module_init 和 module_exit 作用？
   答：insmod 把 .ko 载入内核 → 内核做符号重定位、版本校验 → 调用 module_init 注册的 init 函数（注册设备号/申请资源）→ 加载完成。rmmod 调 module_exit 注销资源。两者分别是模块生命周期的入口和出口。

5. 内核态怎么和用户态安全地传数据？为什么不能用 memcpy？
   答：用 copy_to_user / copy_from_user。用户态指针可能是非法地址（未映射、只读、被篡改），直接 memcpy 会触发内核 oops 甚至被利用提权；copy_* 函数会做地址合法性检查，失败返回非 0。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 注册设备号用动态分配（register_chrdev(0,...)），避免主设备号冲突
2. 用 class_create + device_create 自动创建 /dev 节点，别依赖手工 mknod
3. 中断处理分离：ISR 只做最小工作，重活交给 workqueue/tasklet（threaded irq 更稳）
4. 用户态数据一律走 copy_to_user / copy_from_user，参数先校验再使用
5. 模块编译环境装齐（linux-headers-$(uname -r)），.ko 与运行内核版本严格一致
6. 模块参数、/dev 节点、sysfs 文件权限设最小，ioctl 危险操作加 capable 校验
7. 用 pr_debug + dynamic debug 替代裸 printk，生产环境可开关、不刷屏

### 踩坑记录

```text
坑 1：直接 memcpy 用户态指针导致内核 oops
结论：驱动一读写就 panic，定位到 copy 环节。
原因：把用户态传入的指针当内核指针用 memcpy，遇到非法地址直接触发 oops。
解法：一律用 copy_to_user / copy_from_user，并检查返回值处理 -EFAULT。

坑 2：编译通过但 insmod 报 Invalid module format
结论：模块加载失败，内核提示版本不匹配。
原因：编译用的内核头文件（linux-headers）与运行内核版本不一致，或跨机器拷贝 .ko。
解法：安装与 uname -r 一致的头文件重编，modinfo 核对 vermagic。

坑 3：rmmod 报 Module is in use
结论：模块无法卸载。
原因：有进程仍打开 /dev 节点，或模块被其他模块依赖（lsmod 的 Used by 列）。
解法：关闭占用进程、先卸载依赖模块；并核对模块引用计数逻辑。

坑 4：中断没触发，设备没反应
结论：驱动加载正常但收不到数据。
原因：忘 request_irq 注册中断、或中断号/触发方式（边沿/电平）配错、没清中断标志位。
解法：cat /proc/interrupts 看该中断计数是否增长，核对设备树/ACPI 的中断号与触发类型。

坑 5：热路径里 printk 拖慢系统还刷爆日志
结论：高频打印导致性能骤降，/var/log 快速涨满。
原因：printk 有锁和串口开销，每次调用都写日志缓冲，热路径调用是灾难。
解法：热路径用 tracepoint/计数器/ratelimit（printk_ratelimited），日志用 pr_debug 动态开关。

坑 6：spinlock 里调用可能睡眠的函数导致死锁
结论：持有自旋锁时系统卡死（有时报 scheduling while atomic）。
原因：spinlock 持有期间关抢占、不能睡眠，调了 kmalloc(GFP_KERNEL)/copy_to_user 等可能睡眠的函数。
解法：可能睡眠的场景用 mutex；确需 spinlock 时临界区保持纳秒级、只用原子操作和非睡眠 API。
```
