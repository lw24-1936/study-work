## 概述

内核源码阅读是深入理解 Linux 的必经之路——系统调用怎么进内核、进程怎么被调度、内存怎么分配、文件怎么写进磁盘、网络包怎么从网卡到用户态，答案都在源码里。Linux 内核是用 C（少量汇编）写的单体内核，源码以 Linux 5.x/6.x 系列为主，核心代码集中在几个顶层目录：`kernel/`（进程调度等核心子系统）、`mm/`（内存管理）、`fs/`（文件系统与 VFS）、`net/`（网络协议栈）、`drivers/`（设备驱动，体积最大）。读源码的关键不是通读，而是「带着问题、借助交叉引用工具、顺着一条调用链往下钻」。

```text
内核源码五大阅读入口：
kernel/  进程调度、信号、时间、模块等核心子系统（sched/ 是调度器）
mm/      内存管理（伙伴系统、slab、VMA、缺页处理）
fs/      文件系统（VFS 抽象层 + ext4/xfs 等具体实现）
net/     网络协议栈（socket 层、TCP/IP 实现）
drivers/ 设备驱动（体积最大，按总线/设备分类）
```

## 核心概念

### 内核源码结构

获取源码有几种方式，读源码常用「本地 git 仓库 + 交叉引用」组合。

```shell
# 1. 从 kernel.org 克隆主线（体积大，约 1GB+，可 --depth 浅克隆）
git clone --depth 1 https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git

# 2. 从发行版包拿对应版本源码（贴合你跑的版本）
sudo apt install linux-source      # Debian/Ubuntu，源码装到 /usr/src/
sudo dnf download --source kernel  # RHEL 系

# 3. 建交叉引用索引（cscope + ctags，vim/emacs 里跳转用）
cd linux
make cscope                        # 生成 cscope.out（需装 cscope）
make tags                          # 生成 tags（ctags）
# 4. 快速定位符号/定义
grep -rn "do_fork" kernel/ include/ | head
```

顶层目录速览（Linux 6.x）：

```text
arch/      架构相关（x86/ arm64/ riscv/...），启动、中断、汇编
kernel/    核心子系统：sched/（调度）signal/ time/ module.c fork.c
mm/        内存管理：page_alloc.c（伙伴）slub.c（slab）memory.c（缺页）
fs/        文件系统：VFS 抽象 + ext4/ xfs/ btrfs/ 等实现
net/       网络协议栈：core/ ipv4/（含 TCP）socket.c
drivers/   设备驱动（最大目录，按 block/net/usb/gpu 等分类）
include/   头文件（linux/sched.h 定义 task_struct 等核心结构）
init/      启动初始化（start_kernel 入口）
block/     块设备 I/O 与 IO 调度器
security/  LSM 安全模块框架（SELinux/AppArmor）
ipc/       进程间通信（消息队列/共享内存/信号量）
lib/       内核库函数
scripts/   编译/配置辅助脚本
```

```text
读源码两条腿：
本地 rg/grep + cscope/ctags 跳转（离线、可改、可调试）
在线交叉引用 Elixir Bootlin（elixir.bootlin.com）按版本点符号跳转，适合查特定版本
```

### 进程调度

调度器负责「决定哪个进程在哪个 CPU 上跑多久」，代码在 `kernel/sched/`。Linux 默认调度类是 **CFS（Completely Fair Scheduler，完全公平调度器）**，实现于 `kernel/sched/fair.c`。核心数据结构是 `task_struct`（定义于 `include/linux/sched.h`），每个进程/线程一个；调度实体是 `sched_entity`，里面有个关键字段 **vruntime（虚拟运行时间）**。

CFS 的核心思想：给每个进程累计「实际运行时间按权重折算后的虚拟时间」vruntime，调度时总是选 **vruntime 最小的进程**（即「亏欠 CPU 最多」的进程）先跑，用红黑树（按 vruntime 排序）组织就绪队列，保证所有进程按权重公平分享 CPU。nice 值（-20 到 +19）决定权重——nice 越低权重越高，vruntime 增长越慢，分到的 CPU 越多。

```c
// include/linux/sched.h 中的 task_struct（节选，仅示意结构）
struct task_struct {
    volatile long            state;    // 进程状态：TASK_RUNNING/TASK_INTERRUPTIBLE 等
    int                      prio;     // 动态优先级
    int                      static_prio;  // 静态优先级（nice）
    struct sched_entity      se;       // CFS 调度实体
    struct mm_struct        *mm;       // 内存描述符（内核线程为 NULL）
    pid_t                    pid;
    struct task_struct      *parent;   // 父进程
    // ... 省略大量字段
};

// 调度实体中的虚拟运行时间（同一头文件）
struct sched_entity {
    u64    vruntime;                   // 虚拟运行时间（CFS 排序依据）
    u64    exec_start;                 // 本次开始运行的时间
    // ...
};
```

```shell
# 从用户态观察调度器行为
cat /proc/<pid>/sched          # 看某进程的调度信息（含 vruntime）
cat /proc/<pid>/status | grep -E 'State|voluntary'   # 进程状态与切换次数
chrt -p <pid>                  # 看实时调度策略与优先级
nice -n -5 ./my_program        # 以 nice=-5（更高权重）启动
taskset -c 0 ./my_program      # 绑定到 CPU 0（调度域观察）
```

```text
CFS 调度要点：
选谁跑 = vruntime 最小的进程（红黑树左叶子），公平地按权重分 CPU
vruntime = 实际运行时间 × (NICE_0_LOAD / 进程权重)，nice 越低权重越大 vruntime 涨得越慢
调度类 = 实时（SCHED_FIFO/RR，先于普通进程）+ CFS（SCHED_NORMAL）+ 空闲（idle）
入口：schedule() → __schedule() → pick_next_task()（按调度类优先级选）
```

### 内存管理

内存管理代码在 `mm/`，管理「物理页的分配回收」和「进程虚拟地址空间的映射」两大块。

- **伙伴系统（Buddy System）**：物理页框分配器，`mm/page_alloc.c`。把空闲页按 2 的幂次（order 0/1/2...）组成链表，申请时找合适的 order 拆分，释放时相邻的空闲伙伴合并，解决内存碎片。`alloc_pages()` / `__get_free_pages()` 是内核分配的入口。
- **slab/slub 分配器**：`mm/slub.c`（现代默认），在伙伴系统之上做「小对象缓存」，给 `task_struct`、`inode` 等高频小对象提供缓存复用，避免每次都要找伙伴系统。
- **VMA 与缺页处理**：进程的虚拟地址空间由 `vm_area_struct`（VMA，定义于 `include/linux/mm_types.h`）描述，一个 VMA 是一段连续虚拟区间（代码段/堆/栈/映射文件）。进程访问未映射的地址触发缺页异常，`mm/memory.c` 的 `handle_mm_fault()` 处理：分配物理页、建页表、从文件/匿名页填内容。

```shell
# 观察内存管理运行状态
cat /proc/meminfo                 # 内存概览（Buddy 相关见 /proc/buddyinfo）
cat /proc/buddyinfo               # 各 zone 各 order 的空闲页块数（伙伴系统状态）
cat /proc/slabinfo                # slab 缓存对象统计（如 task_struct、inode 的缓存）
cat /proc/<pid>/maps              # 进程的 VMA 列表（虚拟地址区间映射）
cat /proc/<pid>/smaps             # 每个 VMA 的详细内存占用
cat /proc/zoneinfo                # 各内存 zone 的详细信息（含水位、回收统计）
```

```text
内存管理三层：
伙伴系统（page_alloc.c）   物理页框按 2^n 分配/合并，解决外碎片
slab/slub（slub.c）        小对象缓存复用（task_struct/inode），减少伙伴系统调用
VMA + 缺页（memory.c）     进程虚拟地址空间描述 + 按需分配物理页（惰性分配）
核心结构：struct page（物理页）、vm_area_struct（VMA）、mm_struct（进程地址空间）
```

### 文件系统

文件系统代码在 `fs/`，核心是 **VFS（Virtual File System Switch，虚拟文件系统切换）**——一层抽象，让系统调用和上层不关心底层是 ext4 还是 xfs 还是 tmpfs。VFS 定义了几个关键操作接口（`include/linux/fs.h`），每个具体文件系统去实现：

- `struct super_block`：挂载的文件系统实例。
- `struct inode`：一个文件/目录的内核表示（元数据：权限、大小、时间）。
- `struct file_operations`：文件操作集（`open`/`read`/`write`/`mmap`...），是核心抽象。
- `struct inode_operations`：inode 操作集（`create`/`lookup`/`unlink`...）。

一次 `read()` 的调用路径：用户态 `read` → `fs/read_write.c` 的 `ksys_read()` → `vfs_read()` → 找到 `file->f_op->read`（具体文件系统的 read，如 ext4 的）→ 读块 → 拷贝回用户态。理解 VFS 就是理解「所有文件操作都要经过这几个函数指针」。

```shell
# 观察文件系统状态
cat /proc/filesystems              # 内核已注册的文件系统（含 nodev 的虚拟文件系统）
cat /proc/mounts                   # 当前挂载点及对应文件系统类型
mount | grep -E 'ext4|xfs|tmpfs'   # 看常用文件系统挂载
cat /proc/self/mountinfo           # 更详细的挂载信息（含挂载 ID、传播属性）
# 用 strace 看一次 open/read 的系统调用（用户态视角，对应内核 VFS 入口）
strace -e trace=openat,read cat /etc/hostname
```

```text
VFS 抽象要点：
super_block   挂载实例；inode   文件元数据；dentry   目录项缓存（路径到 inode）
file_operations   文件操作集（read/write/mmap...）—— 具体文件系统实现
inode_operations  inode 操作集（create/lookup/unlink...）
read 路径：read → ksys_read → vfs_read → f_op->read（ext4 等实现）→ 块设备
看懂 VFS = 看懂「一切皆文件」怎么通过函数指针分发到不同底层
```

### 网络子系统

网络代码在 `net/`，从下到上大致是：网卡驱动 → 设备层（`net_device`）→ 协议栈（IP/TCP/UDP）→ socket 层。核心数据结构是 `struct sk_buff`（`include/linux/skbuff.h`），网络数据包在内核里就以 skb 形式在各层之间传递。

- **socket 层**：`net/socket.c`，系统调用 `socket()`/`bind()`/`connect()`/`send()`/`recv()` 的入口，抽象出 `struct socket`，通过协议族（`AF_INET` 等）分发到具体协议实现。
- **TCP/IP 实现**：`net/ipv4/` 目录，TCP 协议栈拆成多个文件——`tcp_input.c`（接收路径、拥塞控制）、`tcp_output.c`（发送路径）、`tcp_ipv4.c`（TCP over IPv4 的 socket 操作）、`tcp_cong.c`（拥塞控制算法插件）。三次握手、滑动窗口、拥塞控制都在这里。
- **接收路径**：网卡中断 → NAPI 轮询收包 → `netif_receive_skb()` → 按协议上送 IP 层 → 路由 → TCP 层 → socket 接收队列 → 唤醒等待的进程。

```shell
# 观察网络子系统运行状态
cat /proc/net/tcp                 # 所有 TCP 连接（含状态、四元组）
cat /proc/net/sockstat            # socket 统计（TCP/UDP/RAW 各多少）
cat /proc/net/dev                 # 各网卡收发统计（字节/包/错误）
cat /proc/net/snmp                # TCP/UDP/IP 协议层统计（重传、丢包等）
ss -s                             # socket 汇总
ethtool -S eth0                   # 网卡硬件统计（驱动层，丢包/错误）
```

```text
网络分层与源码位置：
socket 层（net/socket.c）    syscall 入口 + 协议族分发
TCP/IP 栈（net/ipv4/）       tcp_input.c 收/tcp_output.c 发/tcp_cong.c 拥塞控制
设备层（net/core/dev.c）     net_device 抽象 + 收包分发 netif_receive_skb
核心结构：sk_buff（数据包载体）、net_device（网卡）、sock（socket 内核态）
接收路径：网卡中断 → NAPI 轮询 → IP 层 → TCP 层 → socket 队列 → 用户态
```

## 工作原理

### 一次 read() 系统调用在内核的完整路径

以「读一个普通文件」为例，把前面几个子系统串起来，理解它们如何协作：

```text
read(fd, buf, n) 系统调用（用户态）
  → fs/read_write.c: ksys_read()
  → fs/read_write.c: vfs_read()           ← VFS 层，检查权限、找 file_operations
  → ext4 的 read 实现（fs/ext4/file.c）    ← 具体文件系统
  → 读页缓存 page cache（mm/filemap.c）    ← 内存管理：页缓存命中则直接拷贝
  → 未命中则读块设备（block/ + drivers/）  ← 块设备 I/O，触发磁盘读
  → copy_to_user()                        ← 把数据从内核拷贝回用户态缓冲
```

```text
关键认知：
页缓存（page cache）是文件系统与内存管理的结合点——读文件先查缓存，命中零磁盘 IO
copy_to_user 是必须的拷贝：内核态和用户态地址空间隔离，数据要跨边界拷贝一次
看懂了这条路径，就理解了「系统调用 → VFS → 文件系统 → 页缓存 → 块设备」五层协作
```

### CFS 调度器如何保证公平

```text
CFS 公平性机制：
1. 每个就绪进程维护 vruntime（虚拟运行时间），运行时间越少 vruntime 越小
2. 调度器用红黑树按 vruntime 排序，树最左节点 = 最「吃亏」的进程
3. 时钟 tick 到来时更新当前进程 vruntime，若出现更小的 vruntime 就抢占
4. 进程睡眠醒来 vruntime 会被「补偿」，保证交互型进程响应快
调度周期内，权重相同的进程分到相同 CPU 时间，nice 不同的按权重比例分配
```

## 配置文件解析

### 内核 .config（编译配置）

`.config` 决定哪些代码编译进内核，读源码时对照它理解「这块代码在你的内核里到底启没启用」。

```text
# .config 关键项（读源码对照）
CONFIG_SCHED_DEBUG=y        # 调度器调试（/proc/sched_debug 才可用）
CONFIG_SLUB=y               # 内存用 SLUB 分配器（对应 mm/slub.c）
CONFIG_EXT4_FS=y            # ext4 编译进内核（=m 则作为模块）
CONFIG_TCP_CONG_CUBIC=y     # 默认拥塞控制算法（net/ipv4/tcp_cubic.c）
CONFIG_DEBUG_INFO=y         # 带调试符号（crash/perf 能看到函数名）
```

```shell
# 查看当前运行内核的编译配置
zcat /proc/config.gz | grep -E 'CONFIG_(SCHED|SLUB|EXT4|TCP_CONG)'    # 若内核开启 CONFIG_IKCONFIG_PROC
# 或从 /boot 读
grep -E 'CONFIG_(SCHED|SLUB|EXT4|TCP_CONG)' /boot/config-$(uname -r)
```

```text
.config 与源码对应：某功能代码目录（如 net/ipv4/tcp_cubic.c）只有对应 CONFIG 打开才会被编译
用 CONFIG_IKCONFIG_PROC=y 内核可直接 /proc/config.gz 读配置，比猜准
```

## 应用场景实战

### 场景一：追踪「进程如何被创建」——从 fork 到 exec 的调用链

用交叉引用工具顺着 `fork()` 系统调用往下钻，理解进程创建的完整链路：

```shell
# 1. 定位 fork 系统调用定义
grep -rn "SYSCALL_DEFINE0(fork)" kernel/
# kernel/fork.c: SYSCALL_DEFINE0(fork) → kernel_clone()

# 2. 看 kernel_clone 做了什么（创建 task_struct、复制资源）
grep -n "kernel_clone" kernel/fork.c | head

# 3. 看子进程如何进入调度（wake_up_new_task 把新进程挂进就绪队列）
grep -n "wake_up_new_task" kernel/fork.c kernel/sched/core.c

# 4. 追踪新进程被调度运行
grep -n "schedule_tail\|context_switch" kernel/sched/core.c | head

# 5. 观察实际效果
strace -f -e trace=fork,execve /bin/sh -c 'ls /tmp'   # 看用户态 fork/exec 序列
```

```text
fork 调用链：
fork → kernel_clone → copy_process（复制 task_struct/mm/fs）→ wake_up_new_task（进就绪队列）
→ schedule() 时机到 → context_switch（切换上下文）→ 子进程在用户态接着跑
exec 则是在 fork 基础上加载新程序、替换地址空间（mm）
```

### 场景二：追踪一次 TCP 连接的建立（三次握手）

从 socket 系统调用到 TCP 握手完成，理解网络子系统的关键路径：

```shell
# 1. socket 系统调用入口
grep -n "SYSCALL_DEFINE3(socket" net/socket.c
# 2. connect 入口（TCP 三次握手从这里发起）
grep -n "SYSCALL_DEFINE3(connect" net/socket.c
# 3. TCP 的 connect 实现
grep -n "tcp_v4_connect\|tcp_connect" net/ipv4/tcp_ipv4.c net/ipv4/tcp_output.c | head
# 4. 三次握手状态机（SYN_SENT → SYN_RECV → ESTABLISHED）
grep -n "TCP_SYN_SENT\|TCP_ESTABLISHED" include/net/tcp_states.h

# 5. 用 ss 观察真实握手状态
ss -tan state syn-sent        # 正在发 SYN 的连接
ss -tan state established     # 已建立的连接
# 6. 抓包对照内核状态机（可选，需 tcpdump）
# tcpdump -i lo tcp port 80 -n
```

```text
TCP 三次握手路径：
connect → tcp_v4_connect（client）→ tcp_connect 发 SYN（SYN_SENT）
→ server 收 SYN → 回 SYN+ACK（SYN_RECV）→ client 回 ACK → ESTABLISHED
状态定义在 include/net/tcp_states.h，状态机与抓包看到的一一对应
```

## 性能与调优

```text
1. 索引构建优化 —— 全量 cscope/ctags 索引耗时，只对关心的目录建索引（make cscope 前先 make tags）
2. 用 rg 代替 grep —— ripgrep 快得多，大仓库全文检索秒级返回
3. 在线交叉引用分流 —— 查特定版本符号用 Elixir Bootlin，本地只保留自己改动的版本
4. 读源码结合 perf —— 用 perf top/perf record 看热点函数，再读对应源码，比漫无目的通读高效
5. 对照 proc/sysfs —— /proc/<pid>/sched、/proc/buddyinfo 等运行态数据和源码字段一一对应
6. 精简配置加速编译 —— 只想看某子系统，make localmodconfig 裁剪无关模块，编译更快
```

## 安全与权限

```text
1. 源码来源可信 —— 只从 kernel.org 或发行版官方源取源码，校验签名（内核发布有 GPG 签名）
2. 不直接改生产内核 —— 源码阅读和改内核是两回事，改动内核要重新编译测试，别在生产机上试
3. 调试内核用虚拟机 —— 加打印/改代码的调试放 VM/容器，内核崩溃不会影响真实系统
4. 内核符号泄露 —— 生产内核关闭 kptr_restrict（/proc/sys/kernel/kptr_restrict=1），别暴露内核指针
5. 权限理解 —— 读源码理解 uid/gid/capability 在内核怎么校验（security/ + kernel/capability.c）
6. 漏洞视角 —— 读源码同时关注 CVE 修复 commit，理解漏洞根因是提升安全能力的高效路径
```

## 常见问题

```text
Q1: 内核源码这么多，从哪开始读？
A: 别通读。从一条具体调用链开始：先读系统调用（read/fork/socket），顺着往下钻到对应子系统，配合 cscope 跳转和 git blame。或者从自己遇到的性能/故障问题反向读源码。

Q2: task_struct 和 sched_entity 什么关系？
A: task_struct 是进程的完整描述（一个进程/线程一个），内嵌 sched_entity（se 字段）作为 CFS 的调度实体。调度器只关心 se 里的 vruntime 等字段，不关心 task_struct 的其它部分。

Q3: 伙伴系统和 slab 分配器有什么区别，为什么要两层？
A: 伙伴系统分配物理页框（以页为单位、2 的幂次），适合大块内存但分配小对象会浪费整页；slab/slub 在页之上做小对象缓存（如 task_struct 几百字节），复用已分配页，减少伙伴系统调用和碎片。

Q4: VFS 层的作用是什么？
A: VFS 提供统一的文件操作抽象（file_operations/inode_operations 等函数指针），让系统调用和上层代码不关心底层是 ext4/xfs/tmpfs 还是网络文件系统，实现「一切皆文件」的统一接口。

Q5: 网络包在内核里用什么结构承载？
A: struct sk_buff（简称 skb），一个数据包从网卡驱动到协议栈到 socket 都靠它在各层传递，携带数据、协议头指针、接口信息等。理解 skb 就理解了网络数据包的内核视角。

Q6: 读内核源码和看 /proc、sysfs 什么关系？
A: 源码是「实现」，/proc 和 sysfs 是「运行态的窗口」——/proc/<pid>/sched 对应 CFS 的 vruntime，/proc/buddyinfo 对应伙伴系统，两者对照读，既懂原理又能观察真实状态。
```

## 面试题

```text
1. Linux 进程调度的 CFS 是什么？怎么保证公平？
   答：CFS 是完全公平调度器，为每个进程维护 vruntime（虚拟运行时间，按权重折算），调度器总选 vruntime 最小的进程运行，用红黑树组织就绪队列，使所有进程按权重比例公平分享 CPU。nice 值决定权重，nice 越低权重越大。

2. 一次 read() 系统调用在内核里怎么走？
   答：read → ksys_read → vfs_read（VFS 层，找 file_operations）→ 具体文件系统 read（如 ext4）→ 页缓存（命中直接 copy_to_user，未命中读块设备）→ 拷贝回用户态。

3. 伙伴系统是什么？为什么还要 slab 分配器？
   答：伙伴系统按 2 的幂次分配物理页框，相邻空闲伙伴可合并，减少外部碎片，适合大块内存；slab/slub 在其上做小对象缓存复用，避免为几百字节的小对象浪费整页，提升分配效率。

4. VFS 的核心数据结构有哪些？
   答：super_block（挂载实例）、inode（文件元数据）、dentry（目录项缓存）、file_operations（文件操作集）、inode_operations（inode 操作集）。具体文件系统通过实现这些函数指针接入 VFS。

5. TCP 三次握手在内核哪个目录、哪些文件实现？
   答：net/ipv4/ 目录，tcp_ipv4.c（TCP over IPv4 的 socket 操作与 connect）、tcp_input.c（接收路径与握手状态机）、tcp_output.c（发送路径，含发 SYN）、tcp_cong.c（拥塞控制）。状态定义在 include/net/tcp_states.h。

6. 内核源码顶层目录结构怎么划分？
   答：arch/（架构相关）、kernel/（调度/信号/时间等核心）、mm/（内存管理）、fs/（文件系统与 VFS）、net/（网络协议栈）、drivers/（设备驱动，最大）、include/（头文件）、block/（块 I/O）、security/（LSM）等。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 带着问题读，不漫无目的通读——从一个系统调用或一个故障现象出发，顺调用链往下钻
2. 建好 cscope/ctags 索引再开读，跳转定义/引用是读 C 大仓库的基本功
3. 对照 /proc 与 sysfs 运行态读源码，代码结构和真实数据互相印证
4. 读不懂就看 git blame 和提交信息，理解这段代码当初为什么这么写、改过什么
5. 用 Elixir Bootlin 在线交叉引用查特定版本，避免本地只有最新版、对不上自己跑的版本
6. 结合 perf 热点反向读源码——性能瓶颈函数往往是理解机制的最佳入口
7. 遇到内核崩溃/异常，读 panic 调用栈 + 反汇编定位到源码行，比查文档快

### 踩坑记录

```text
坑 1：克隆了最新主线源码，但和线上跑的版本对不上
结论：读到的实现和生产内核行为不一致，越读越困惑。
原因：主线是 6.x 最新版，生产可能是 5.x/发行版打了补丁的版本。
解法：读与生产匹配的版本（git checkout 对应 tag，或 apt source 拿发行版源码）。

坑 2：没建索引就硬 grep，读大仓库效率极低
结论：grep 全仓库慢、跳转靠人肉找，读源码进度停滞。
原因：没用 cscope/ctags，缺交叉引用能力。
解法：先 make cscope && make tags，配合 rg 快速检索，跳转定义/引用。

坑 3：把内核源码里的结构体字段名记混，凭印象解读导致理解偏差
结论：把 nice 和 prio、vruntime 和实际运行时间混淆，原理讲错。
原因：task_struct/sched_entity 字段多，没对照真实头文件核实。
解法：关键结构（task_struct、sk_buff、inode）以 include/ 里的真实定义为准。

坑 4：直接在开发机上改内核做实验，一次 panic 影响其它工作
结论：内核改动触发崩溃，影响同机开发环境。
原因：改内核/加打印没在隔离环境做。
解法：内核实验放虚拟机或容器，崩溃不影响真实环境，可随时回滚。

坑 5：只看代码不看运行态，理解停留在纸面
结论：知道 CFS 有红黑树，但不知道实际怎么观察 vruntime、怎么验证。
原因：没把 /proc/<pid>/sched、/proc/buddyinfo 等和代码对应起来。
解法：每读一个子系统，同步看对应 proc/sysfs 输出，代码与数据互证。

坑 6：读内核源码时被大量宏和配置开关绕晕
结论：看不懂 SYSCALL_DEFINE、各种 CONFIG_ 条件编译，以为代码「不完整」。
原因：内核用大量宏生成代码、条件编译裁剪，直接读源码像读天书。
解法：先了解预处理宏（SYSCALL_DEFINEn、list_head、container_of），对照 .config 看哪些分支编译进去了。
```
