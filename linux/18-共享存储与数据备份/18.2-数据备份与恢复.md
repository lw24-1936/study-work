## 概述

数据备份是「防止数据丢失的最后防线」——误删、磁盘损坏、勒索病毒、机房灾难，都靠备份兜底。核心三件事：**备份策略**（3-2-1 原则 + 备份类型组合）、**备份工具**（tar/rsync/快照/数据库专用工具）、**备份验证**（恢复演练，证明备份真的能恢复）。

最重要的认知：**备份的价值 = 能恢复**。不能恢复的备份等于没有——所以「定期恢复演练」和「备份监控告警」与备份本身同等重要。备份不是「做了就行」，而是一个需要持续验证的闭环：

```text
数据 → 备份策略（全量/增量组合）→ 备份工具执行 → 备份验证（校验和/恢复演练）
   ↑                                                              ↓
   └──────── 发现备份失效 → 修复 → 重新备份 ←─────────────────────┘
```

## 核心概念

### 1. 3-2-1 备份原则

```text
3 —— 3 份数据副本（原始数据 + 2 份备份）
2 —— 2 种不同介质（如本地磁盘 + 异地磁盘/磁带/云存储，防单一介质故障）
1 —— 1 份异地副本（异地机房/云，防火灾、水灾、勒索、物理灾难）
```

落地方法：

- 3 份副本：生产数据 1 份 + 本机/同机房备份 1 份 + 异地备份 1 份，共 3 份。
- 2 种介质：不要「两块盘都在同一台机器」——同一 RAID 卡、同一机柜都算「同一种风险」；至少一份在另一台机器/另一块物理存储上。
- 1 份异地：异地 ≠ 另一台机器，必须是不同物理位置（跨机房/云存储/磁带送库房），防区域性灾难。
- 进阶：关键数据做 **离线（air-gap）备份**——备份介质平时不联网（磁带、离线硬盘、冷存储），勒索软件无法加密离线副本。

### 2. 备份类型：全量 / 增量 / 差异

| 类型 | 备份内容 | 备份量 | 备份速度 | 恢复速度 | 恢复复杂度 |
|---|---|---|---|---|---|
| 全量备份 | 所有数据 | 最大 | 最慢 | 最快（一份搞定） | 最低 |
| 增量备份 | 上次任意备份后的变化 | 最小 | 最快 | 最慢（需全量+一串增量依次恢复） | 最高（链条长，一环坏全毁） |
| 差异备份 | 上次**全量**后的变化 | 中（随时间增长） | 中 | 较快（只需全量+最近一次差异） | 中 |

典型组合：**每周日全量 + 每天增量**（数据量大、备份窗口小）；或**每周日全量 + 每天差异**（恢复更快但备份量递增）。关键点：增量/差异备份必须依赖一个有效的全量备份，**全量备份损坏 = 所有增量/差异全部失效**。

### 3. RPO 与 RTO

- **RPO（Recovery Point Objective，恢复点目标）**：最多能丢多少数据（时间维度）。备份频率决定 RPO——每小时备份一次，最多丢 1 小时数据。
- **RTO（Recovery Time Objective，恢复时间目标）**：故障后多久必须恢复业务。恢复流程/介质决定 RTO。
- 设计备份策略时先定这两个指标：RPO 定备份频率，RTO 定恢复手段（本地快照秒级恢复 vs 磁带慢恢复）。

### 4. 备份工具分类

1. **归档类**：`tar`/`cp`——整目录打包成文件，适合全量、迁移、保留历史版本。
2. **同步类**：`rsync`——增量同步，镜像目录到本地/远程，无版本历史。
3. **文件系统级**：`dump`/`restore`（ext 系列）、`xfsdump`（XFS）——文件系统原始格式备份，可带增量级别。
4. **快照类**：LVM 快照（COW）、文件系统快照（btrfs/xfs 的 fsfreeze 配合）——秒级一致性副本。
5. **数据库专用**：`mysqldump`/`pg_dump`/`xtrabackup`——逻辑/物理备份 + binlog/WAL 增量，保证一致性。
6. **版本化去重类**：`restic`/`borg`/`duplicity`——加密 + 内容去重 + 快照历史，现代增量备份首选。

### 5. 备份窗口与保留策略

- **备份窗口**：备份执行占用的时间（必须在业务低峰内完成，别和业务抢 IO）。
- **保留策略**：保留多少份历史（如「日备保留 7 份、周备保留 4 份、月备保留 12 份」），平衡恢复需求与存储成本。
- **容量估算**：备份大小 ≈ 数据量 × 压缩率 × 版本数；增量策略下 ≈ 全量 × 1 + 日均变化量 × 保留天数。

## 工作原理

### 1. rsync 增量同步原理

```text
rsync -av /src/ /dst/
 ① 遍历源目录，生成文件列表（路径、大小、mtime、权限）
 ② 与目标端文件列表比对：
    - 大小 + mtime 相同 → 跳过（快速检查，默认）
    - 大小/mtime 不同 → 进入差异传输
 ③ 差异传输（rolling checksum 分块）：
    - 目标文件按 700 字节左右分块，算弱校验和 + 强校验和
    - 源文件滚动比对，找出相同块直接复用
    - 只传输真正变化的块，重组目标文件
 ④ 属性（权限/属主/时间）同步；--delete 时删除目标端多余文件
```

所以「第二次 rsync 几乎瞬间完成」：文件没变时只交换列表与校验元数据，不传数据。`--dry-run` 只做 ①②④ 的预览不写文件。

### 2. tar 归档原理

- `tar` 把文件树按顺序写入归档流（含元数据：路径、权限、属主、时间），本身**不压缩**；`-z`（gzip）/`-j`（bzip2）/`-J`（xz）是管道后接压缩器。
- 归档是顺序写，适合全量备份；增量能力弱（`--listed-incremental` 用快照文件记录，体验一般），所以 tar 主打「全量 + 保留多份历史」。
- 恢复 `tar xf` 按顺序解出，损坏发生在中间会导致后续文件丢失——这也是校验与测试恢复重要的原因。

### 3. LVM 快照原理（Copy-on-Write）

```text
打快照前：快照区为空，快照只是「指向原卷的元数据指针」
  原卷写操作 A：先把 A 要覆盖的旧块复制到快照区（COW），再写新数据
  快照读操作：读到快照区 → 返回旧块；没被改过的 → 读原卷
结果：快照始终呈现「打快照那一刻」的数据状态，且不冻结业务
```

- 快照区大小 ≈ 打快照到删除快照期间的「数据变化量」，不是整个卷的大小；变化量超过快照区则快照失效（overflow）。
- 快照期间原卷写性能略降（每次覆盖多一次 COW 拷贝）。
- 备份流程：打快照 → 挂载快照 → 从快照备份 → 卸载并删除快照（快照不能代替备份，它是「一致性备份的抓手」）。

### 4. 数据库备份原理（mysqldump + binlog）

- **mysqldump**：逻辑备份，把数据导出为 SQL 语句，跨版本/跨架构可恢复，但恢复慢、大库耗时长。
- **一致性**：InnoDB 用 `--single-transaction`（MVCC 一致性快照）不需要锁表；MyISAM 需 `--lock-tables` 或停写。
- **增量**：MySQL 的 binlog 记录所有写操作，**全量 mysqldump + 定期备份 binlog** 可实现时间点恢复（PITR）——恢复到全量时刻 + 重放 binlog 到指定时间点。
- PostgreSQL 对应：`pg_dump`（逻辑）+ WAL 归档（增量）；或 `pg_basebackup`（物理）+ WAL。

### 5. restic/borg 去重原理

- 数据切成小块（chunk，默认约 1MB 内），按内容哈希（SHA-256）去重：**相同内容的块只存一份**。
- 快照 = 块引用列表（清单），多版本共享未变化块，空间占用 ≈ 全量 + 各版本增量变化。
- 加密在客户端完成（restic 用 AES-256 加密块 + scrypt 密钥派生），仓库里看不到明文。
- 代价：首次备份慢（切块+哈希），恢复时按引用重组（`restic restore latest`）。

## 常用命令与配置

### tar（全量归档）

```shell
# 打包压缩（czf = 创建 gzip 压缩归档）
tar czvf /backup/etc_$(date +%F).tar.gz /etc

# 排除目录/文件
tar czvf /backup/home.tar.gz --exclude='home/*/.cache' \
        --exclude='*.log' /home

# 查看归档内容（不展开）
tar tzvf /backup/etc_2026-08-19.tar.gz | head
tar tzf /backup/etc_2026-08-19.tar.gz >/dev/null && echo '归档可读'   # 完整性粗检

# 恢复
tar xzvf /backup/etc_2026-08-19.tar.gz -C /restore/etc
tar xzvf /backup/etc_2026-08-19.tar.gz -C / -C etc   # 只解出 etc/ 子路径
```

### rsync（增量同步）

```shell
# 本地目录镜像（-a 归档保留属性，-v 显示，--delete 同步删除）
rsync -av --delete /data/ /backup/data/

# 远程备份（走 SSH 加密通道）
rsync -avz /data/ backup@192.168.1.50:/backup/data/

# 限带宽（KB/s），避免打满生产网络
rsync -av --bwlimit=5000 /data/ /backup/data/

# 增量快照：--link-dest 硬链接复用上一份未变化文件
rsync -av --delete --link-dest=/backup/snap/2026-08-18 \
      /data/ /backup/snap/2026-08-19/

# 只读预览（先看会传什么，不写目标）
rsync -av --dry-run /data/ /backup/data/
```

### dump/restore（ext 文件系统）

```shell
# 全量备份 /dev/sdb1 到文件
dump -0uf /backup/rootfs_$(date +%F).dump /dev/sdb1
# 增量（-1 级别 1，只备份上次 0 级后的变化）
dump -1uf /backup/rootfs_inc1.dump /dev/sdb1
# 恢复
restore -rf /backup/rootfs_2026-08-19.dump        # 交互式恢复
restore -tf /backup/rootfs_2026-08-19.dump | head # 查看内容
```

### LVM 快照

```shell
# 打快照（-s 快照，-L 快照区大小，-n 名字）
lvcreate -L 10G -s -n snap_mysql /dev/vgdata/lv_mysql

# 挂载快照备份（快照是只读的一致视图）
mkdir -p /mnt/snap
mount -o ro /dev/vgdata/snap_mysql /mnt/snap
rsync -av /mnt/snap/ /backup/mysql/
umount /mnt/snap

# 用完删除快照
lvremove /dev/vgdata/snap_mysql
```

### 数据库备份

```shell
# MySQL：全量逻辑备份
mysqldump --single-transaction --routines --triggers \
          --databases mydb > /backup/mydb_$(date +%F).sql

# 压缩存储
mysqldump --single-transaction mydb | gzip > /backup/mydb_$(date +%F).sql.gz

# 恢复
mysql mydb < /backup/mydb_2026-08-19.sql

# PostgreSQL
pg_dump -Fc mydb -f /backup/mydb_$(date +%F).dump
pg_restore -d mydb /backup/mydb_2026-08-19.dump
```

### restic（版本化 + 加密 + 去重）

```shell
restic init -r /backup/repo                # 初始化仓库（设密码）
restic -r /backup/repo backup /data        # 备份（可多次，自动增量去重）
restic -r /backup/repo snapshots           # 查看快照
restic -r /backup/repo restore latest --target /restore   # 恢复最新
restic -r /backup/repo check               # 校验仓库完整性
restic -r /backup/repo forget --keep-daily 7 --keep-weekly 4 --prune  # 保留策略
```

## 配置文件解析

### 备份自动化脚本模板（带日志、保留策略、失败告警）

```shell
#!/bin/bash
# /opt/scripts/backup.sh —— 每日备份脚本
set -euo pipefail

BACKUP_DIR=/backup/daily
DATA_DIR=/data
LOG=/var/log/backup.log
KEEP_DAYS=7                          # 保留策略：日备留 7 天
DATE=$(date +%F_%H%M%S)

log() { echo "$(date '+%F %T') $*" >> "$LOG"; }

log "===== 备份开始 ====="
mkdir -p "$BACKUP_DIR"

# ① 数据目录 rsync 增量镜像（--delete 保持镜像一致）
if rsync -av --delete "$DATA_DIR/" "$BACKUP_DIR/data/" >> "$LOG" 2>&1; then
    log "数据目录备份 OK"
else
    log "ERROR: 数据目录备份失败"
    echo "数据备份失败，请检查 $LOG" | mail -s "[备份告警] $(hostname)" ops@example.com
    exit 1
fi

# ② 配置文件归档（tar 全量，按日期命名）
tar czf "$BACKUP_DIR/etc_$DATE.tar.gz" -C / etc/hosts etc/hostname 2>/dev/null \
    && log "配置归档 OK" || { log "ERROR: 配置归档失败"; exit 1; }

# ③ 数据库备份（mysqldump + gzip）
mysqldump --single-transaction mydb 2>>"$LOG" | gzip > "$BACKUP_DIR/mydb_$DATE.sql.gz" \
    && log "数据库备份 OK" || { log "ERROR: 数据库备份失败"; exit 1; }

# ④ 保留策略：清理 7 天前的日备
find "$BACKUP_DIR" -name 'etc_*.tar.gz' -mtime +$KEEP_DAYS -delete
find "$BACKUP_DIR" -name 'mydb_*.sql.gz' -mtime +$KEEP_DAYS -delete
log "===== 备份完成 ====="
```

### 定时任务配置

```shell
# cron：每天凌晨 3 点执行
# 0 3 * * * /opt/scripts/backup.sh

# systemd timer（更推荐，自带状态查询）：
# /etc/systemd/system/backup.service
# [Service]
# ExecStart=/opt/scripts/backup.sh
# /etc/systemd/system/backup.timer
# [Timer]
# OnCalendar=*-*-* 03:00:00
# Persistent=true          # 上次没跑（关机）补跑
# [Install]
# WantedBy=timers.target
systemctl daemon-reload
systemctl enable --now backup.timer
systemctl list-timers | grep backup    # 查看下次执行时间
```

### rsnapshot 配置（rsync 快照轮换经典工具）

```ini
# /etc/rsnapshot.conf（Ubuntu: apt install rsnapshot；RHEL: dnf install rsnapshot）
snapshot_root   /backup/snapshots/      # 快照根目录
cmd_rsync       /usr/bin/rsync
retain          daily   7               # 日快照保留 7 份
retain          weekly  4               # 周快照保留 4 份
retain          monthly 12              # 月快照保留 12 份
backup          /data/  localhost/      # 备份源：本地目录
backup          backup@192.168.1.50:/srv/  remote/   # 备份源：远程（SSH）

# 实际执行
# rsnapshot daily && rsnapshot weekly && rsnapshot monthly
```

rsnapshot 底层就是 rsync + `--link-dest` 硬链接轮换：同一文件多份快照只占一份空间，目录结构呈现为完整的历史快照。

```shell
#     weekly
#     rotate 12
#     compress
#     missingok

```

## 应用场景实战

### 场景一：用 tar 做每周全量归档

需求：服务器配置与数据每周归档一份，保留 4 周，用于「回滚到上周状态」。

```shell
# ① 打包（排除缓存与日志）
mkdir -p /backup/weekly
tar czvf /backup/weekly/srv_$(date +%F).tar.gz \
    --exclude='/srv/app/cache' \
    --exclude='/srv/app/*.log' \
    /srv/app

# ② 校验归档可读（恢复前必做）
tar tzf /backup/weekly/srv_$(date +%F).tar.gz >/dev/null && echo '归档 OK'

# ③ 保留策略：只留最近 4 份
ls -t /backup/weekly/*.tar.gz | tail -n +5 | xargs -r rm -f

# ④ 恢复演练：解到临时目录比对
mkdir -p /tmp/restore_test
tar xzf /backup/weekly/srv_2026-08-16.tar.gz -C /tmp/restore_test
diff -rq /tmp/restore_test/srv/app /srv/app | head
```

适用场景：数据量小、变化不大、需要「整包历史」的服务器配置/小应用。

### 场景二：rsync 每日增量 + --link-dest 快照轮换

需求：数据目录每天备份，保留 30 天历史，且任意一天都能单独恢复。

```shell
# ① 首次全量快照
rsync -av /data/ /backup/snap/daily.0/

# ② 之后每天：以昨天的快照为基础做增量，生成新快照
rsync -av --delete --link-dest=/backup/snap/daily.0/ \
      /data/ /backup/snap/daily.1/
# 没变化的文件通过硬链接指向 daily.0 的同名文件——不占新空间

# ③ 轮换（保留 N 份）
# 简单方案：find /backup/snap -maxdepth 1 -type d -name 'daily.*' \
#           | sort | head -n -30 | xargs -r rm -rf
# 复杂方案直接上 rsnapshot（自动轮换 + 定时）

# ④ 恢复某天快照
cp -a /backup/snap/daily.7/ /restore/     # 硬链接快照直接复制即可用
# 注意：cp -a 保留硬链接结构；要独立副本用 cp -a --reflink=auto 或 rsync -a
```

核心原理：`--link-dest` 让未变化的文件在快照间共享 inode（硬链接），**空间占用 ≈ 全量 + 每天变化量**，但每个快照目录看起来都是完整目录，恢复任意一天都只需复制一个目录。

### 场景三：LVM 快照备份数据库（一致性）

需求：MySQL 数据目录在线备份，要求备份点数据一致，不停库。

```shell
# ① 确认卷信息
lvs                                          # vgdata/lv_mysql，容量 100G
# ② 打快照（快照区给变化量的 1.5~2 倍余量）
lvcreate -L 20G -s -n snap_mysql /dev/vgdata/lv_mysql
# ③ 挂载快照（只读）
mkdir -p /mnt/snap
mount -o ro /dev/vgdata/snap_mysql /mnt/snap
# ④ 从快照复制数据（比 mysqldump 快得多，物理一致）
rsync -av /mnt/snap/var/lib/mysql/ /backup/mysql_snap/
# ⑤ 卸载并删除快照
umount /mnt/snap
lvremove -f /dev/vgdata/snap_mysql
```

注意：快照备份的是「文件系统视图」，MySQL 的 innodb 数据文件在快照时是 crash-consistent 的，恢复时正常走 InnoDB 崩溃恢复即可；更严格的方案是先 `FLUSH TABLES WITH READ LOCK` 或使用 xtrabackup。快照是备份的辅助手段，**快照卷本身不是备份**（与数据同盘，盘坏全没）。

### 场景四：mysqldump 全量 + binlog 增量（时间点恢复）

需求：每天全量备份数据库，且能恢复到「任意时间点」（比如误删表的 10:32）。

```shell
# ① 每日全量
mysqldump --single-transaction --master-data=2 \
          --all-databases | gzip > /backup/mysql/full_$(date +%F).sql.gz
# --master-data=2 记录 binlog 位置（恢复起点）

# ② 增量：定期备份 binlog 日志
mkdir -p /backup/mysql/binlog
mysqlbinlog --read-from-remote-server -h localhost \
    --raw --stop-never binlog.000123 2>/dev/null &
# 或简单方案：把 /var/lib/mysql/binlog.* 每天 rsync 到备份机

# ③ 恢复（模拟误删恢复）：
# 3.1 恢复全量
gunzip < /backup/mysql/full_2026-08-18.sql.gz | mysql
# 3.2 重放 binlog 到误删时间点之前
mysqlbinlog --stop-datetime='2026-08-19 10:31:59' \
    /backup/mysql/binlog/binlog.000123 | mysql
# 数据恢复到 10:31:59 的状态，误删操作（10:32）未被重放
```

同理 PostgreSQL：`pg_basebackup`（物理全量）或 `pg_dump`（逻辑全量）+ WAL 归档 + `pg_restore`/PITR。

### 场景五：异地备份（rsync over SSH）

需求：关键数据同步到异地机房/云端，满足 3-2-1 的「1 份异地」。

```shell
# ① 免密登录（SSH 密钥，不用密码）
ssh-keygen -t ed25519
ssh-copy-id backup@192.168.2.50     # 异地备份机

# ② 加密通道 rsync（走 SSH 默认加密）
rsync -avz --delete --bwlimit=5000 \
      /backup/daily/ backup@192.168.2.50:/backup/remote/

# ③ 定时（cron / timer）每天凌晨 4 点同步
# 0 4 * * * rsync -avz --delete /backup/daily/ backup@192.168.2.50:/backup/remote/ >> /var/log/backup.log 2>&1

# ④ 云存储（对象存储，如 S3/OSS/COS）
# aws s3 sync /backup/daily/ s3://my-company-backup/daily/ --storage-class STANDARD_IA
# 或 rclone copy /backup/daily/ oss:bucket/daily/ --transfers 8
```

异地备份要点：**先本地备份，再同步到异地**（避免生产直接被异地任务拖垮）；带宽限制（--bwlimit）；传输加密（SSH/HTTPS）；异地副本做保留策略清理。

## 性能与调优

1. **增量优先**：能增量就别全量。全量备份数据量 × N 份，增量备份 ≈ 全量 × 1 + 变化量 × N。rsync 增量、restic/borg 去重、数据库 binlog 都是增量思路。
2. **压缩权衡**：`rsync -z`、`tar z` 压缩省空间省带宽，但吃 CPU。判断标准：**网络/存储是瓶颈就压缩，CPU 是瓶颈就别压**。文本、数据库导出压缩率 5~10 倍；已压缩的媒体文件再压徒劳（用 `--skip-compress` 或直接不压）。
3. **带宽限制**：生产环境 rsync 加 `--bwlimit=5000`（KB/s）限速，避免备份把业务网络打满；异地备份更要限。
4. **备份窗口规划**：大备份放业务低峰（凌晨 2~4 点），用 `ionice -c2 -n7`（低优先级 IO）避免抢业务磁盘。
5. **并行与分批**：多目录并行备份（`xargs -P` 或多个 timer）可缩短窗口，但注意 IO/带宽争抢；大数据库考虑物理备份（xtrabackup/pg_basebackup）代替逻辑导出（mysqldump 大库恢复太慢）。
6. **去重省空间**：restic/borg 内容去重 + 快照共享块，多版本历史空间 ≈ 全量 + 增量变化；rsnapshot 用硬链接达到类似效果（rsync --link-dest）。
7. **校验开销**：`--checksum` 全量校验慢；默认快速检查（大小+mtime）快但可能漏检「内容变了时间没变」的文件——敏感目录定期做一次全校验（`rsync -c`）。
8. **文件数瓶颈**：海量小文件（百万级）时，rsync 的文件列表遍历和 tar 的元数据写入是主要开销；考虑先打包（tar）再传输，或用 restic 的并行切块。
9. **监控备份耗时**：备份脚本记录开始/结束时间与耗时（`time`），趋势异常（越来越慢）提示数据增长或 IO 退化，提前扩容。
10. **存储选型**：备份存储用大容量低速盘（HDD 即可）或对象存储冷归档，别把热数据的高性能盘浪费在备份上；参考 [[18.4-存储性能与容量]]。

## 安全与权限

1. **备份必须加密**：备份数据包含全部业务敏感信息，异地/云端备份必须加密——restic/borg 原生加密；tar/rsync 场景用 GPG（`gpg -c` 对称加密或 `--encrypt-files`）或走加密通道（SSH/HTTPS）+ 磁盘加密（LUKS）。
2. **备份仓库密码保管**：restic/borg 密码丢失 = 备份永远无法恢复。密码要用密码管理器/密钥库保管，并**写入应急预案文档**；可以加 `--password-command` 从保险库读取。
3. **备份文件权限**：备份目录 `chmod 700 /backup`、文件 600，防止同机其他用户读取敏感备份；备份脚本用专用账号（非 root 尽量，但 tar 系统目录需要 root，可接受脚本 root + 目录收紧）。
4. **传输加密**：远程 rsync 一律走 SSH（`rsync -e ssh` 或默认 SSH），不要用老式 rsync daemon 明文协议（`rsync://` 端口 873 明文）；云存储用 HTTPS。
5. **防勒索（air-gap）**：勒索软件会加密「能访问到的所有数据」，包括在线备份。对策：异地离线备份（备份介质平时不挂载/不联网）、对象存储的版本控制 + 不可变存储（immutable）、备份账号最小权限且与业务账号隔离。
6. **备份账号最小权限**：备份机只开 SSH + rsync，禁止任意命令执行（限制命令）；备份账号不能登录业务主机执行危险操作。
7. **审计**：备份作业记录（谁、何时、备份了什么）纳入审计日志，配合 [[23.3-安全审计]]；恢复操作也要记录，防止「内部删数据 + 从备份恢复掩盖」的路径被滥用。
8. **密钥与证书**：SSH 密钥、GPG 密钥、云存储密钥统一管理，定期轮换；密钥泄露 = 备份数据泄露。

## 故障排查

### 案例一：备份失败（磁盘满 / 网络断）

```shell
# 症状：备份脚本退出码非 0，备份文件缺失或大小为 0
tail -50 /var/log/backup.log          # ① 看备份日志（脚本必须写日志）
df -h /backup                         # ② 备份目标磁盘满了吗
du -sh /backup/*                      # ③ 哪个备份占满的
ping 192.168.2.50                     # ④ 异地备份机通不通
rsync -av --dry-run /data/ /backup/data/   # ⑤ 重放一次看报错
journalctl -u backup.service --since today   # ⑥ systemd timer 方式查服务日志

# 常见处理
# 磁盘满：清理过期备份（find -mtime +N -delete）或扩容
# 网络断：恢复网络后手动重跑备份脚本，确认退出码 0
```

### 案例二：恢复失败（备份损坏 / 不完整）

```shell
# 症状：恢复时报错，解出的文件缺失或打不开
tar tzf /backup/etc_2026-08-19.tar.gz >/dev/null   # ① tar 包可读性粗检
gzip -t /backup/etc_2026-08-19.tar.gz              # ② gzip 完整性校验
restic check -r /backup/repo                       # ③ restic 仓库完整性
mysql < /backup/mydb_2026-08-19.sql && echo '恢复 OK'   # ④ 试恢复
diff -rq /restore_test/srv /srv/app                # ⑤ 恢复后与源比对
md5sum /backup/data/important.db                   # ⑥ 与源文件校验和对比

# 根因方向
# 备份时源数据正在写（无快照/无锁）→ 备份本身不一致
# 备份介质坏道/静默损坏 → 异地多副本 + 定期校验
# 压缩管道中断（磁盘满）→ 归档截断，tar 报 unexpected EOF
```

### 案例三：备份一直没更新（脚本没跑 / 定时任务失效）

```shell
# 症状：备份目录最新文件还是上周的
ls -lt /backup/daily/ | head                      # ① 看最新备份时间
systemctl list-timers | grep backup               # ② timer 存在吗、上次触发时间
systemctl status backup.timer                     # ③ timer 状态（Activated/Running）
grep backup /var/log/cron.log 2>/dev/null         # ④ cron 执行记录（cron 未开 cron.log 则看 journalctl）
journalctl -u backup.timer -u backup.service --since "3 days ago"   # ⑤ 服务日志
timedatectl                                       # ⑥ 机器时间对吗（时间漂移导致定时跑错点）

# 常见原因
# 机器关机/休眠错过窗口（timer 加 Persistent=true 补跑）
# 脚本被手动执行过但 cron/timer 没 enable
# 脚本路径/权限问题（ExecStart 路径错、脚本无执行权限）
# 环境变量缺失（cron 环境 PATH 极简，脚本内用绝对路径）
```

### 案例四：恢复出来的数据不一致（数据库备份时机错误）

```text
症状：从备份恢复数据库后，数据缺失/外键报错/表损坏。
原因：备份时数据库正在写入——tar 直接拷数据目录、mysqldump 没用
      --single-transaction 且库在写，都会拿到不一致的中间状态。
      InnoDB 单文件备份恢复时可能触发崩溃恢复，MyISAM 直接损坏。
解法：mysqldump 加 --single-transaction（InnoDB 一致性快照）；
     或先 FLUSH TABLES WITH READ LOCK / 停库再备份；
     或 LVM/文件系统快照后从快照备份；
     恢复后跑 mysqlcheck / 业务自检脚本验证。
```

### 案例五：异地备份机空间被占满

```shell
# 症状：异地同步失败，目标机 df 100%
df -h /backup                                    # ① 确认满盘
du -sh /backup/* | sort -h                       # ② 找出大块头
find /backup -name '*.tar.gz' -mtime +30 -delete # ③ 按保留策略清理
# 预防：异地机同样配置 logrotate/保留策略脚本；
#       rsync 加 --delete 保持镜像一致（但确认删除策略无误再开）
```

## 常见问题

```text
Q1: 全量、增量、差异备份怎么选？
A: 数据量小、恢复要快 → 全量（简单可靠）；数据量大 → 定期全量（如每周）
   + 每天增量（省空间省时间，但恢复要全量+一串增量串起来，链条别断）；
   要恢复快又不想天天全量 → 每周全量 + 每天差异（只需全量+最近一次差异）。
   记住：增量/差异都依赖全量，全量备份必须有效且可恢复。

Q2: 为什么说「不演练的备份 = 没有备份」？
A: 备份可能因为磁盘坏道、脚本 bug、权限变化、压缩截断等原因悄悄失效，
   平时不发现，真到要恢复时才发现恢复不了就晚了。定期做恢复演练
   （解压到临时目录、试恢复数据库、对比校验和），把「能恢复」变成
   可验证的事实，而不是假设。

Q3: 数据库能直接 rsync/tar 备份吗？
A: 不能。运行中的数据库持续写数据，直接拷数据文件/目录会拿到不一致
   的中间状态，恢复时数据损坏。必须先保证一致性：mysqldump 用
   --single-transaction（InnoDB 一致性快照）、或 FLUSH TABLES WITH
   READ LOCK、或停库、或打 LVM 快照后从快照备份。

Q4: rsync 和 restic/borg 怎么选？
A: 只要「目录镜像/同步」用 rsync（简单、通用、能双向同步）；要「历史
   版本 + 加密 + 内容去重」用 restic/borg（restic 简单、S3 支持好；
   borg 压缩率更高但客户端复杂）。生产建议：关键目录 rsync 镜像 +
   restic 版本化双保险。

Q5: 3-2-1 原则具体怎么落地？
A: ① 生产数据 1 份；② 同机房备份机/本机备份 1 份（不同介质，如另一块
   磁盘或磁带）；③ 异地（另一机房/云存储/离线磁带）1 份。共 3 份副本、
   至少 2 种介质、1 份异地。预算有限时先保证「另一台机器 + 异地」，
   单一介质/单一机房的备份在灾难面前等于没有。

Q6: 备份要保留多少份历史？
A: 取决于恢复需求与成本：一般「日备保留 7~14 份、周备保留 4~8 份、
   月备保留 12 份、年备长期」；数据库 binlog/WAL 保留覆盖最近一次全量
   的时间。原则：保留周期 ≥ 最慢的恢复排查周期（误删发现可能要几天），
   再叠加监管合规要求（如等保要求日志/备份留存半年）。
```

## 面试题

```text
1. 3-2-1 备份原则是什么？为什么这样设计？
   答：3 份数据副本（原始 + 2 份备份）、2 种不同介质、1 份异地。
   设计思想是冗余分层：多副本防单份损坏，多介质防单一介质故障
   （两块盘坏一块还有另一块），异地防区域性灾难（火灾/水灾/勒索）。
   任何单一故障点都不能同时摧毁所有副本。

2. 增量备份和差异备份有什么区别？恢复速度为什么不同？
   答：增量备份备份「上次任意备份（含上次增量）」以来的变化，量最小、
   备份最快，但恢复要按顺序重放全量+一串增量，链条长、慢且脆；差异
   备份备份「上次全量」以来的变化，量随时间增长，但恢复只需全量+
   最近一次差异，更快更稳。空间换恢复速度的取舍。

3. 为什么数据库备份前要打快照/锁表？如何做到不停库？
   答：运行中的数据库持续写数据，直接备份会拿到不一致的中间状态。
   方案：InnoDB 用 mysqldump --single-transaction（MVCC 一致性快照）
   不停库；或 LVM 快照（COW 冻结文件系统视图）后从快照备份；或
   FLUSH TABLES WITH READ LOCK（短暂只读）。核心是保证备份点是
   crash-consistent 的。

4. 如何验证备份是有效的？
   答：三层验证：① 备份后立即校验（tar tzf 可读、gzip -t、restic
   check、mysqldump 文件非空且结尾完整）；② 定期恢复演练——解压到
   临时目录、试恢复数据库并跑自检、对比文件校验和（md5sum）；
   ③ 监控备份作业本身——定时任务执行状态、备份日志告警、备份产物
   大小趋势异常告警。验证不等于「备份命令执行成功」，而是「能恢复」。

5. 备份被勒索软件加密了怎么办？如何预防？
   答：预防是关键：① air-gap 离线备份（磁带/离线硬盘，平时不联网）；
   ② 异地备份（勒索一般只加密本机房在线资源）；③ 对象存储不可变
   （immutable/版本控制）；④ 备份账号最小权限、与业务隔离。已加密
   时：立即隔离受感染主机（拔网线），不要删被加密数据（可能被解密），
   用离线/异地/不可变副本恢复，同时报警与取证。

6. 设计一个生产环境的备份方案（数据量 1TB，MySQL 为主）？
   答：① 策略：每日 mysqldump 全量（凌晨低峰）+ binlog 持续备份实现
   任意时间点恢复（RPO 分钟级）；② 工具：mysqldump + rsync（本地镜像）
   + restic（加密去重版本化，异地 S3）；③ 保留：日备 14 份、周备 8 份、
   月备 12 份；④ 异地：restic 仓库同步到异地对象存储（加密传输）；
   ⑤ 验证：每周恢复演练（恢复到一个临时实例跑自检），备份日志告警；
   ⑥ 容量：全量压缩后约 200GB + 日增量约 10GB，预留 3 倍余量。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 备份遵循 3-2-1 原则：3 份副本、2 种介质、1 份异地；关键数据加离线（air-gap）副本。
2. 数据库备份前保证一致性：`--single-transaction` / 锁表 / 快照，绝不在运行中直接拷数据文件。
3. 定期做恢复演练（恢复 + 校验 + 对比），把「能恢复」变成已验证的事实；演练结果记录在案。
4. 备份自动化（cron/systemd timer）+ 失败告警（邮件/webhook）+ 备份产物监控（大小/时间戳异常）。
5. 备份脚本全部使用绝对路径（cron 环境 PATH 极简），加 `set -euo pipefail`，写日志，退出码非 0 必告警。
6. 备份数据加密（restic 原生 / GPG / LUKS），异地与云端备份必须加密；密钥与密码妥善保管并写入应急预案。
7. 备份保留策略明确并自动执行（日/周/月/年分层），清理过期备份，防止备份盘写满后静默失败。
8. rsync 镜像用 `--delete` 保持一致性（确认策略后），异地同步加 `--bwlimit` 限速避免影响业务网络。
9. 备份源与备份目标分离（不同机器/磁盘），避免同盘同毁；备份机自身也要有监控。
10. 变更管理：升级数据库、迁移目录、换备份工具前，先做一次全量备份再动手——「变更前必有备份」是铁律。

### 踩坑记录

```text
坑 1：备份了但从来没演练过，真出事恢复不了
结论：备份做了几年，真删库了发现备份是坏的/恢复不了。
原因：没做恢复演练，备份损坏/不完整（磁盘坏道、脚本 bug、截断）一直
     没被发现。
解法：定期做恢复演练（删库→恢复→验证），备份后立即做完整性校验
     （tar tzf / gzip -t / restic check），把演练纳入例行运维。

坑 2：数据库直接备份，数据不一致
结论：数据库运行中直接 tar 备份数据目录，恢复后发现数据损坏。
原因：备份时数据库在写，拷到的是不一致的中间状态（InnoDB 需要崩溃
     恢复、MyISAM 直接损坏）。
解法：备份前打快照（LVM 快照）或 mysqldump --single-transaction 或
     停库/锁表，保证备份点 crash-consistent；恢复后跑自检验证。

坑 3：rsync 没加 --delete，删除的文件还留在备份
结论：源删了文件，备份里还有，备份越积越大且「删不掉的东西」还在。
原因：rsync 默认不删目标端多余文件。
解法：镜像类备份加 --delete（确认删除策略无误）；要保留历史就明确用
     版本化方案（--link-dest/rsnapshot/restic），别混用。

坑 4：备份都在同一块盘/同一机房，一起毁
结论：备份和原始数据在同一块磁盘，盘坏了全没；或备份都在同一机房，
     机房火灾全没。
原因：没遵循 3-2-1（异地/多介质），备份成了「心理安慰」。
解法：至少一份备份在另一台机器/另一块物理介质上；关键数据加异地副本
     （异地机房/云存储/离线磁带）。

坑 5：备份失败没告警，出事才发现备份是空的
结论：备份脚本失败（磁盘满/网络断/权限错），一直没人知道，恢复时发现
     备份是空目录/旧文件。
原因：备份没监控，失败静默——cron 只执行不通知。
解法：脚本失败发告警（mail/webhook）；定时检查备份产物（大小、时间戳、
     退出码）；备份日志纳入监控告警（如 zabbix/prometheus 检查 backup.log）。

坑 6：cron 里脚本跑不起来，手动执行却正常
结论：手动跑 backup.sh 一切正常，cron 定时执行却报错失败。
原因：cron 环境 PATH 极简、HOME 不同，脚本里用了相对路径或依赖
     ~/.bashrc 的环境变量。
解法：脚本内全用绝对路径；开头 export PATH=/usr/local/sbin:/usr/local/bin:
     /usr/sbin:/usr/bin:/sbin:/bin；用 systemd timer（环境更可控）
     替代 cron。

坑 7：恢复时发现全量备份损坏，增量全部作废
结论：周全量 tar 包损坏，依赖它的所有日增量备份全部无法使用。
原因：增量/差异备份都依赖全量，全量坏了链条就断了；全量包本身没做
     校验。
解法：全量备份后立即校验（gzip -t/tar tzf）；全量也保留最近 2 份
     （上一份全量 + 新全量）；做恢复演练时重点验证「全量+增量链」能
     完整恢复。

坑 8：恢复演练把生产环境搞挂了
结论：在生产的数据库实例上「试恢复」，把线上数据覆盖了。
原因：演练直接在环境上执行恢复命令，没有隔离。
解法：演练用独立环境/临时实例/临时目录，恢复目标与生产物理隔离；
     演练前备份当前状态；演练步骤写成文档，逐步确认。

坑 9：mysqldump 备份大库超时/太慢，备份窗口被拖垮
结论：100GB 的库 mysqldump 要跑 40 分钟，和业务高峰撞车。
原因：逻辑导出逐行生成 SQL，大库天然慢；窗口规划不合理。
解法：大库改用物理备份（xtrabackup/LVM 快照+文件复制，分钟级）；
     逻辑导出分批/限速；窗口放业务低峰；增量用 binlog。

坑 10：异地备份带宽占满，业务网络卡顿
结论：异地 rsync 同步时线上业务网络延迟飙升。
原因：备份没限速，把出口带宽打满。
解法：rsync 加 --bwlimit 限速（如 5000KB/s）；异地同步避开业务高峰；
     大文件分批传；必要时走独立专线/存储 VLAN。
```
