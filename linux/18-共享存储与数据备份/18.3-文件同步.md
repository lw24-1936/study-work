## 概述

文件同步解决「多台机器/多份位置保持数据一致」。核心工具链分两档：rsync 做增量同步（只传变化的部分，定时/按需触发），inotify + lsyncd 做实时同步（文件变化立即同步）。同步不等于备份——同步是「让两份数据一致」，备份是「保留历史版本可回退」，二者解决的问题不同，生产环境通常组合使用。

选型一句话：能容忍分钟级延迟用 rsync 定时任务（简单可靠），要求低延迟实时一致（双机热备、实时备份）用 lsyncd，双向改动用 unison，跨网络多机分布式同步用 Syncthing，配置文件版本化用 git/etckeeper。

```text
# 实测（本机 rsync 已装，版本 3.2.7）
$ rsync --version | head -1
rsync  version 3.2.7  protocol version 31
```

```text
同步工具全景：
1. rsync —— 增量同步（只传变化），定时/按需触发，单向
2. inotify + lsyncd —— 实时同步（文件变化立即触发 rsync）
3. unison —— 双向同步，两端都可改，冲突需仲裁
4. Syncthing —— 分布式 P2P 同步，无中心服务器
5. git / etckeeper —— 版本化同步，保留每次变更历史
```

## 核心概念

### 1. 同步 vs 备份

同步（sync）是镜像：让两端内容一致，源端删除目标端也跟着删（加 --delete 时）；备份（backup）是保留：保留历史版本，源端删了还能从备份恢复。把 rsync 备份脚本写成「不加 --delete 的镜像」等于既没有镜像一致性也没有历史版本，两头不靠。

| 维度 | 同步 | 备份 |
|---|---|---|
| 目标 | 两端数据一致 | 保留历史可回退 |
| 删除 | 默认跟随源（--delete） | 不跟随，保留已删文件 |
| 版本 | 无版本概念 | 按时间点保存快照 |
| 典型工具 | rsync、lsyncd、unison | rsync + --link-dest、restic、borg |

### 2. rsync 增量同步

rsync 是「增量」的：只传变化的部分。两次同步之间文件没变就直接跳过（对比大小 + mtime），文件变了则分块算校验和，只传真正变化的块。大目录重复同步时几乎瞬间完成，这是它比 scp/cp 强的地方。

### 3. inotify

inotify 是内核提供的文件系统事件通知机制：对目录/文件注册监听后，创建、修改、删除、移动等事件由内核主动通知用户态程序，不需要轮询扫描。inotifywait 是命令行封装，lsyncd 底层就是靠它。

### 4. lsyncd

lsyncd（Live Syncing Daemon）把 inotify 事件和 rsync 粘在一起：监听源目录 → 文件变化 → 延迟合并（delay）→ 触发 rsync 同步到目标。对用户来说表现是「文件一改，几秒内就到目标端」。

### 5. 双向同步（unison）与分布式同步（Syncthing）

rsync 是单向的（源 → 目标），双向同步两端都改会互相覆盖。unison 是经典双向同步工具：两端各自记录版本，同步时检测冲突（同一文件两端都改），让用户仲裁或保留一份副本。Syncthing 是 P2P 分布式同步：多台机器互相同步，无中心服务器，走自有协议（22000/tcp 数据、21027/udp 发现），适合跨网络多节点场景。

### 6. 版本化同步（git / etckeeper）

配置文件这种「文本 + 需要历史回退」的数据，用 git 管理比 rsync 合适：每次变更都有提交记录，改坏了能回滚到任意历史版本。etckeeper 把 /etc 纳入 git 管理，apt/dnf 装包导致配置变化时自动提交，是 Linux 服务器配置管理的事实标准。

```text
选型速查：
- 单向、定时、大目录 → rsync
- 单向、实时、低延迟 → lsyncd + inotify
- 双向、两端都可写 → unison
- 多机、跨网络、P2P → Syncthing
- 配置文件、要历史版本 → git / etckeeper
```

## 工作原理

### 1. rsync 增量同步算法（滚动校验块）

rsync 的增量传输分两层判断：

第一层是「快速检查」（quick check）：对比源和目标的文件大小 + mtime，两者都相同就认为文件没变，整个跳过——这是重复同步大目录「瞬间完成」的原因。

第二层是文件内容变了（大小或 mtime 不同）时的「滚动校验块」（rolling checksum）算法，核心流程：

```text
发送端（源）文件按固定块大小切块（rsync 3.x 按文件大小动态定块，
小文件小块、大文件大块），对每个块计算两个校验和：
1. 弱校验和（rolling checksum，基于 Adler-32）——可 O(1) 滚动更新
2. 强校验和（rsync 3.x 用 MD5）——确认匹配的最终依据

流程：
1. 接收端（目标）把自己的文件同样分块，算出每块的校验和清单发给发送端
2. 发送端用滚动校验和在自己的文件上逐字节滑动窗口，找出与目标
   校验和匹配的块（弱校验和命中后再用强校验和确认，避免碰撞）
3. 发送端只传输「匹配块的位置引用 + 不匹配的差异数据」，接收端
   据此重组出新文件
```

滚动校验和的巧妙之处：窗口每滑动一个字节，新窗口的校验和可以在旧值基础上 O(1) 更新（去掉头字节、加上尾字节），不用重新计算整个窗口，所以匹配查找是线性的。这也是 rsync 名字的来源（remote sync 的增量差分思想）。文件差异很小时（比如 2MB 文件只改了几十字节），实际传输的数据量可能只有几 KB。

### 2. inotify 原理

inotify 是内核文件系统事件机制（fsnotify 框架的用户态接口）：

```text
用户态 inotify_init() 建实例 → inotify_add_watch() 注册目录/文件
→ 内核在 VFS 层挂上监听 → 事件发生（IN_CREATE/IN_MODIFY/IN_DELETE/
IN_MOVED_FROM/IN_MOVED_TO/IN_CLOSE_WRITE/IN_ATTRIB...）→ 事件写入
inotify 队列 → 用户态 read() 取事件处理
```

关键限制都在内核参数里：`/proc/sys/fs/inotify/max_user_watches`（单个用户最多 watch 数，默认几千到几万）、`max_user_instances`、`max_queued_events`（事件队列上限，队列满了丢事件）。海量小文件场景就是 watch 数不够/事件队列溢出，表现为监听失效、同步漏文件。

### 3. lsyncd 工作流

```text
lsyncd 工作流：
inotify 监听源目录 → 收到变化事件（IN_CREATE/IN_MODIFY/IN_DELETE...）
→ 事件在 delay 窗口内合并（比如 delay=1，1 秒内的连续变化合并成一次）
→ 触发 rsync 把变化的文件同步到目标
→ 目标端 rsync 结束后继续监听，循环
```

delay 合并是关键设计：文本编辑器保存文件会产生多次事件（create/modify/close_write），如果没有合并，一次保存触发多次 rsync；合并后一次保存只触发一次。lsyncd 还支持 maxProcesses 并行跑多个 rsync 进程（大量文件变化时）。

### 4. etckeeper / git 版本化原理

etckeeper 本质是「git 仓库 + 钩子」：init 时把 /etc 变成 git 仓库，之后每次 apt/dnf 安装、卸载、升级包时通过包管理器钩子自动 `git commit` 配置变更，还带一个每日自动提交（cron/timer）。查询历史用 `etckeeper vcs log`（等价 git log），回滚用 git checkout 到某个提交。要点：/etc 下可能有密钥等敏感文件，仓库本身要控制权限，密码类文件（shadow）内容变化也会进历史。

### 5. 双向同步冲突原理

双向同步的难点不是传输，是冲突仲裁：两端同时修改同一文件，同步时不知道该听谁的。unison 的做法是记录每端的文件版本（时间戳 + 内容指纹），同步时发现「同一文件两端都改了」就标记为冲突，默认保留两份副本（.unison 后缀），或让用户选边。所以双向同步适合「同一时刻只有一端在改」的工作流（笔记本 + 台式机不同时开机），不适合双写热备。

## 配置文件解析

### 1. /etc/lsyncd/lsyncd.conf.lua

lsyncd 配置是 Lua 语法（Ubuntu 主配置默认 `settings` 块 + sync 块）：

```lua
-- /etc/lsyncd/lsyncd.conf.lua（示例）
settings {
    logfile    = "/var/log/lsyncd/lsyncd.log",   -- 日志文件
    statusFile = "/var/log/lsyncd/lsyncd.status", -- 状态文件
    nodaemon   = false,                            -- 后台运行
}

sync {
    default.rsync,                                 -- 用 rsync 模式（还有 default.rsyncssh）
    source    = "/data/",                          -- 监听源目录
    target    = "backup:/backup/data/",            -- 目标（本地路径或 user@host:path）
    delay     = 1,                                 -- 变化后延迟 1 秒同步（合并连续变化）
    maxProcesses = 1,                              -- 最多并行 rsync 进程数
    delete    = true,                              -- 同步删除（默认 true）
    exclude   = { "*.log", "*.tmp" },              -- 排除规则
    rsync     = {                                  -- 透传给 rsync 的参数
        archive = true,                            -- 相当于 -a
        compress = false,                          -- -z
        bwlimit = 1000,                            -- 限速 1MB/s
    }
}
```

字段说明：

```text
source      要监听的源目录（绝对路径）
target      同步目标：本地路径，或 用户@主机:路径（走 SSH，配免密）
delay       收到变化后延迟 N 秒再同步，合并高频连续变化，避免频繁 rsync
maxProcesses 变化文件多时并行 rsync 的进程数上限
delete      是否同步删除（true = 目标端多余文件也删，慎用）
exclude     排除的文件/目录（Lua 字符串数组）
rsync       透传给 rsync 的选项（archive/compress/bwlimit 等）
```

### 2. /etc/rsyncd.conf（daemon 模式）

rsync daemon 模式让目标端跑 rsync --daemon 服务（监听 873/tcp），客户端用双冒号访问模块。配置示例：

```ini
# /etc/rsyncd.conf（示例，Ubuntu 包 rsync 自带；Red Hat 系路径相同）
uid = rsync
gid = rsync
use chroot = yes
max connections = 10
pid file = /var/run/rsyncd.pid
log file = /var/log/rsyncd.log

[backup]                  # 模块名，客户端访问 rsync://host/backup
path = /backup/data       # 实际目录
read only = no            # 允许写入
auth users = rsyncuser    # 认证用户
secrets file = /etc/rsyncd.secrets   # 用户名:密码 文件（权限 600）
hosts allow = 192.168.1.0/24
```

daemon 模式不走 SSH，默认明文传输，必须配认证 + 防火墙限制来源，一般只在可信内网用。

### 3. etckeeper 相关配置

```text
/etc/etckeeper/etckeeper.conf —— 主配置（VCS=git、AVOID_COMMIT 等）
/etc/apt/apt.conf.d/90etckeeper —— apt 钩子（装包后自动 commit）
/etc/cron.daily/etckeeper —— 每日自动提交（Ubuntu 默认）
```

## 应用场景实战

### 场景一：定时同步目录到备份机

最经典的用法：rsync 增量同步 + cron 定时 + flock 防重入 + 日志。注意源路径结尾的 /（带 / 复制目录内容）。

```shell
#!/bin/bash
# /usr/local/bin/sync_backup.sh —— 定时同步脚本
# flock 防止上一次没跑完又启动（并发同步会冲突）
exec flock -n /var/lock/sync_backup.lock -c '
rsync -avz --delete \
    --exclude="*.log" --exclude="cache/" \
    /data/ backup:/backup/data/ >> /var/log/sync.log 2>&1
'
```

```text
# crontab -e
# 每小时整点同步一次
0 * * * * /usr/local/bin/sync_backup.sh
# 日志看结果
tail -f /var/log/sync.log
```

### 场景二：Web 集群代码分发

发布新版本时把代码同步到 N 台 Web 节点，排除运行时文件（日志、缓存、上传目录），并保证删除同步：

```shell
# 发布机到 3 台 Web 节点
for host in web1 web2 web3; do
  rsync -avz --delete \
    --exclude='runtime/' --exclude='*.log' --exclude='.git/' \
    /srv/app/ deploy@$host:/srv/app/ >> /var/log/deploy.log 2>&1
done

# 上线前先预演：-n 只列出会传什么，确认排除规则生效
rsync -avzn --delete --exclude='runtime/' /srv/app/ deploy@web1:/srv/app/
```

注意点：发布前先 --dry-run 预演；--delete 保证节点上被删掉的旧文件也清掉，避免残留文件互相干扰（PHP 应用常见）。

### 场景三：双机实时热备（lsyncd + inotify）

主备两台机器，主机的 /data 变化实时同步到备机。配置 /etc/lsyncd/lsyncd.conf.lua：

```lua
settings {
    logfile    = "/var/log/lsyncd/lsyncd.log",
    statusFile = "/var/log/lsyncd/lsyncd.status",
}

sync {
    default.rsyncssh,          -- 走 SSH 的 rsync（比 default.rsync 更安全）
    source = "/data/",
    host   = "backup",         -- 备机 SSH 别名（~/.ssh/config 配好）
    targetdir = "/backup/data/",
    delay  = 2,
    exclude = { "*.tmp" },
}
```

```shell
# 2. 写配置后启动

# 3. 验证：改 /data 下文件，2 秒后看备机是否已同步
echo test > /data/test.txt

# 4. 看日志确认触发
tail -f /var/log/lsyncd/lsyncd.log
```

### 场景四：时间点快照备份（--link-dest）

每天做一份「完整」快照，但未变化的文件通过硬链接复用上一份，磁盘只占增量空间。删除文件时用 rename 而不是 rm（防止某天的快照被 --delete 波及）：

```shell
#!/bin/bash
# /usr/local/bin/snapshot.sh —— 每日快照，保留 7 天
DATE=$(date +%F)
BASE=/backup/snapshots
PREV=$(ls -1 $BASE | tail -1)          # 上一份快照目录名

# 1. 生成新的硬链接快照（相对上一份）
rsync -av --delete \
    --link-dest=$BASE/$PREV/ \
    /data/ $BASE/$DATE/

# 2. 清理 7 天前的快照（先 rename 再删，防误删）
OLD=$(ls -1 $BASE | head -1)
[ "$OLD" != "$DATE" ] && mv $BASE/$OLD /tmp/.snap-trash-$OLD
rm -rf /tmp/.snap-trash-$OLD
```

原理：第一份快照全量占用空间，之后每天只占「变化部分」+ 每个文件一个目录项的开销。所有快照目录里的文件通过硬链接共享同一份数据，只有变化过的文件才新占空间。

### 场景六：带宽受限环境限速同步

公网/跨机房同步会抢占业务带宽，用 --bwlimit 限速 + --timeout 防卡死：


## 性能与调优

```text
1. 增量是核心 —— rsync 只传变化，大目录重复同步很快，别用 cp/scp 全量复制
2. 压缩取舍 —— -z 压缩传输省带宽，但 CPU 开销增加，内网千兆不加 -z 更快
3. 大文件断点续传 —— -P（--partial --progress），中断后从断点继续，别重传
4. lsyncd delay 合并 —— 高频变化场景配 delay（1~5 秒），避免每次变化触发一次 rsync
5. 海量小文件 —— inotify 每个文件都要监听，几十万小文件场景 lsyncd 开销大，改定时 rsync
6. --checksum 慎用 —— 按内容校验和判断变化比 mtime 准确但慢得多（全文件读盘），
   只在 mtime 不可靠的场景（网络文件系统、同步后两端 mtime 不一致）用
7. 大目录首次同步 —— 首传是全量，之后才是增量；首传选业务低峰，必要时并行
   （分目录多个 rsync 并发，别用一个进程串行）
8. --stats 验收 —— 看 Literal data 与实际传输量，确认增量生效
```

```text
--stats 关键指标解读：
Total file size             —— 文件总大小（不变）
Total transferred file size —— 需要传输的文件大小（只含变化的文件）
Literal data                —— 实际传输的差异字节（增量核心指标）
Matched data                —— 通过校验和匹配复用、未传输的字节
speedup                     —— 总大小 / 实际传输量，越大增量效果越好
```

## 安全与权限

```text
1. 远程同步走 SSH —— rsync 远程默认 SSH 加密传输；daemon 模式（873 端口）是
   明文，只限可信内网 + 认证
2. 权限保留 —— -a 保留权限/属主/时间，同步后目标与源一致；-o/-g 保留属主/
   属组需要 root 权限，普通账号同步会丢属主
3. 同步账号最小权限 —— SSH 同步账号只给源目录读、目标目录写，别用 root；
   密码登录关闭，只留密钥
4. --delete 危险 —— 会删目标端多余文件，目标路径写错会误删数据；先 --dry-run
   预览，生产脚本里把目标路径写死
5. daemon 认证 —— rsyncd.secrets 权限 600，密码明文中继，配合 hosts allow
   限制来源 IP
6. 防火墙 —— 远程 SSH 同步只需 22 端口；daemon 模式开 873/tcp 并限制来源
7. 敏感文件 —— 同步前确认排除规则，避免把 .env/密钥/数据库口令同步到
   不该去的主机；etckeeper 仓库里 shadow 等敏感文件历史要控制访问
```

## 故障排查

### 案例 1：rsync 退出码 11（传输错误/中断）

```shell
# 症状：rsync 报 rsync: [sender] write error: Broken pipe (32)
# 或 rsync error: some files/attrs were not transferred (see previous errors) (code 23)
rsync -avz /data/ backup:/backup/data/
echo $?     # 11 = 传输中断（网络断开/对端崩溃/磁盘满），23 = 部分文件未传
```

排查顺序：先看是否网络抖动（重试一次）；再看目标端磁盘是否满（df -h）；加 --partial 让中断的文件保留断点，重跑续传；大文件长传加 --timeout 防假死。退出码速查：0 成功、11 传输错误、12 协议错误、23 部分文件未传、24 源文件消失（正常，文件在同步过程中被删了）、30 认证失败。

### 案例 2：SSH 认证失败 / 免密失效

```shell
# 症状：rsync 报 Permission denied (publickey) / Host key verification failed
ssh backup 'echo ok'          # 先单独测 SSH，缩小范围
ssh-copy-id backup            # 重发公钥
# 排查项：密钥权限（~/.ssh 700、authorized_keys 600）、known_hosts 变更
# （重装系统后 host key 变了要清 known_hosts 旧条目）、账号是否被禁
```

### 案例 3：lsyncd 不触发同步

```shell
systemctl status lsyncd                    # 服务在跑吗
journalctl -u lsyncd -n 50                 # 日志报什么
ls /var/log/lsyncd/lsyncd.log              # 事件日志
# 常见原因：
# 1. source 路径写错或不存在（lsyncd 启动即报错）
# 2. inotify watch 耗尽：cat /proc/sys/fs/inotify/max_user_watches，
#    调大 sysctl fs.inotify.max_user_watches=524288
# 3. SSH 免密失效（default.rsyncssh 模式）：手动 ssh 测试
# 4. exclude 规则误伤：把要同步的文件排除了
```

### 案例 4：同步后权限/属主不对

```shell
# 症状：目标端文件权限/属主和源不一致
ls -l /backup/data/
# 原因 1：没加 -a（丢权限/时间/属主）
# 原因 2：-o/-g 需要 root，普通账号同步属主变同步账号
# 解法：加 -a；跨机属主不一致时用 --chown=user:group --chmod 显式指定，
# 或目标端用 root 账号 + --numeric-ids
```

### 案例 5：cron 里的 rsync 没执行

```shell
# 症状：手动跑脚本正常，cron 不执行或报错
# 排查：
# 1. 脚本没加执行权限：chmod +x /usr/local/bin/sync_backup.sh
# 2. cron 环境 PATH 精简：脚本里写全路径（/usr/bin/rsync），别依赖 PATH
# 3. 输出没重定向：cron 会把 stdout 邮件给 root，脚本里加 >> /var/log/sync.log 2>&1
# 4. 看 cron 日志：grep sync_backup /var/log/syslog（或 journalctl -u cron）
```

## 常见问题

```text
Q1: rsync 源路径结尾的 / 有什么影响？
A: /data/ 复制「目录内容」到目标（目标直接是 data 下的文件）；
   /data 复制「目录本身」（目标出现 data 目录名）。加不加 / 结果不同，
   习惯上备份用 /data/（带斜杠），目标端路径不要带斜杠。

Q2: rsync 和 scp 有什么区别？
A: rsync 增量（只传变化、断点续传、--delete、--exclude、--link-dest），
   scp 全量复制。重复同步大目录 rsync 快得多；一次性传文件 scp 够用。

Q3: 什么时候用 lsyncd 而不是 rsync 定时任务？
A: 需要低延迟实时同步（双机热备、实时备份）用 lsyncd；能容忍分钟级延迟
   用 rsync 定时任务（更简单可靠、无守护进程依赖）。

Q4: lsyncd 监听海量小文件为什么慢/失效？
A: inotify 每个文件都要建立 watch，几十万小文件导致 watch 数耗尽
   （max_user_watches）、事件队列溢出（max_queued_events 丢事件）。
   这种场景改定时 rsync，或缩小监听范围（只监听变更频繁的子目录）。

Q5: rsync 退出码 11 是什么意思？
A: 传输错误：网络断开、对端进程崩溃、目标磁盘满。排查网络/磁盘，
   加 --partial 断点续传重试。23 = 部分文件没传完（看具体报错），
   24 = 源文件在同步过程中被删（正常现象）。

Q6: 双向同步怎么做？rsync 能双向吗？
A: rsync 是单向的，双向同步容易互相覆盖。双向场景用 unison（冲突检测
   + 仲裁）、Syncthing（多机 P2P），或业务上明确主从方向（各目录单向）。

Q7: 同步中断后怎么恢复？
A: 加 -P（--partial --progress）保留不完整文件，重跑同一命令即从断点
   续传；远程大文件再加 --timeout 和 --contimeout 防卡死；cron 场景用
   flock 保证不会多个 rsync 并发。

Q8: --link-dest 是什么？和普通备份有什么区别？
A: 把「未变化的文件」硬链接到指定目录，生成一份逻辑完整、物理共享
   的快照：每天一份快照目录，磁盘只占增量。比纯 rsync 镜像多「时间点
   回退」能力，比全量复制省空间。

Q9: 同步和备份是一回事吗？
A: 不是。同步是让两端一致（源删目标也删），备份是保留历史（源删了还能
   恢复）。生产上正确的姿势：同步保证多机一致，备份（快照/版本化）保证
   可回退，两者组合使用。
```

## 面试题

```text
1. rsync 的增量同步是怎么实现的？
   答：两层。第一层快速检查：对比大小 + mtime，相同就跳过整个文件。
   第二层滚动校验块：文件分块（块大小按文件大小动态定），接收端把每块
   的弱校验和（rolling checksum）+ 强校验和（MD5）清单发给发送端，发送端
   用滚动校验和在本地逐字节滑动窗口匹配，只传不匹配的差异块和位置引用。
   滚动校验和可 O(1) 更新，匹配查找是线性的。

2. inotify 和轮询（polling）有什么区别？
   答：inotify 是事件驱动——内核在 VFS 层监听，文件变化主动通知用户态，
   低延迟、无空转开销；轮询是定时全量扫描，有延迟，海量文件时 CPU/IO
   开销大。实时同步（lsyncd）依赖 inotify；轮询在 inotify 不可用或要
   兼容网络文件系统（NFS 不支持 inotify）时才用。

3. 双向同步怎么做？冲突怎么处理？
   答：rsync 单向，双向要用 unison/Syncthing 这类带冲突检测的工具。
   冲突指同一文件两端都修改：工具记录两端版本，检测到冲突后保留两份
   副本或让用户仲裁。实践上双向同步只适合「同一时刻一端在写」的工作流，
   双写热备必须用分布式锁/数据库级别的方案。

4. 为什么 rsync 要加 --delete？有什么风险？
   答：不加 --delete，源端删除的文件在目标端会残留，两端不一致。
   但 --delete 会删目标端文件：目标路径写错、源目录挂载失败（源变空）
   都会造成大规模误删。安全用法：先 --dry-run 预演、脚本里写死目标
   路径、源是网络挂载时检查挂载状态再同步。

5. rsync 和 cp/scp 的区别？什么时候用 rsync？
   答：rsync 增量差分、断点续传、支持删除/排除/快照/限速；cp/scp 全量
   复制、无增量概念。重复同步、大目录、跨机增量传输、备份快照用 rsync；
   单次小量复制 cp/scp 更简单。

6. lsyncd 的工作原理？
   答：lsyncd 用 inotify 监听源目录，收到变化事件后在 delay 窗口内合并
   （避免一次保存触发多次同步），然后调用 rsync（或 rsyncssh）把变化同步
   到目标，支持 maxProcesses 并行。表现是「文件一改几秒内到目标端」。

7. 如何保证同步任务的可靠性？
   答：① flock 互斥锁防止并发（cron 上次没跑完下次又启动）；② 日志
   重定向到文件，配合监控（grep 退出码/错误关键字告警）；③ rsync 加
   --timeout 防卡死、-P 断点续传；④ lsyncd 场景监控 inotify 事件队列
   （max_queued_events 溢出会丢事件）；⑤ 定期做恢复演练，验证目标端
   数据可用。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 定时同步用 rsync + cron + flock 锁，实时热备用 lsyncd，双向用 unison/Syncthing，配置版本化用 etckeeper
2. rsync 加 --delete 保持完全一致（否则删除不同步），但所有带 --delete 的命令先 --dry-run 预演
3. 源路径用 /data/（带斜杠复制内容），目标路径不带斜杠，脚本里写死
4. 大文件传输加 -P（进度 + 断点续传），远程大文件加 --timeout
5. lsyncd 配 delay 合并连续变化，避免频繁触发 rsync
6. 同步任务日志重定向 + flock 锁 + 退出码检查，防止并发和静默失败
7. 时间点回退需求用 --link-dest 快照，别只做镜像
8. 敏感文件（.env/密钥）加进 --exclude，别同步到不该去的主机
9. 公网/跨机房同步加 --bwlimit 限速，错峰执行
10. Red Hat 系装 lsyncd 先加 EPEL 仓库；daemon 模式服务名是 rsyncd

### 踩坑记录

```text
坑 1：rsync 没加 --delete，删除不同步
结论：源删了文件，目标端还有（两端不一致）。
原因：rsync 默认不删目标端多余文件。
解法：加 --delete 完全同步，或接受保留历史（备份场景反而推荐不加）。

坑 2：rsync 路径结尾的 / 写错
结论：rsync /data 和 /data/ 结果不同，备份目录结构错乱。
原因：源路径结尾的 / 影响「复制目录本身还是目录内容」。
解法：/data/ 复制内容到目标，/data 复制目录本身（含 data 目录名）；
     目标端路径统一不带斜杠。

坑 3：lsyncd 监听海量小文件，性能差/漏同步
结论：lsyncd 监听目录文件巨多，CPU/内存高，甚至漏文件。
原因：inotify 每个文件都要 watch，海量文件耗尽 watch 数和事件队列。
解法：减少监听范围（只监听变更频繁子目录），或改用定时 rsync；
     必要时调大 fs.inotify.max_user_watches。

坑 4：rsync 大文件传输中断，重来又从头
结论：传大文件断线，重试从头开始，白传几小时。
原因：没加 -P（断点续传），中断后重传整个文件。
解法：加 -P 支持断点续传；再加 --timeout 防假死。

坑 5：同步任务并发跑，数据错乱
结论：cron 同步任务上次没跑完，下次又启动，两个 rsync 互相干扰。
原因：没加锁，并发同步可能冲突（尤其 --delete 场景）。
解法：flock 锁，或确保同步任务互斥。

坑 6：--link-dest 快照被 --delete 误删
结论：某天快照目录消失或只剩一半，历史快照损坏。
原因：快照脚本里 --delete 直接作用在快照目录树上，或清理脚本直接 rm
     当天快照（正被 rsync 引用时）。
解法：清理用「先 mv 到临时目录再删」，--link-dest 指向的上游目录
     不要参与 --delete 清理。

坑 7：rsync 报退出码 11，任务静默失败
结论：cron 里 rsync 中断没人知道，备份一直没更新。
原因：网络抖动/对端磁盘满导致传输错误，脚本没检查退出码。
解法：脚本里检查 $?，非 0 报警；日志关键字（error/rsync error）接入监控。

坑 8：SSH 免密突然失效，同步全挂
结论：所有走 SSH 的 rsync/lsyncd 突然报 Permission denied。
原因：重装系统 host key 变更（known_hosts 校验失败）、密钥权限被改、
      authorized_keys 被覆盖。
解法：ssh backup 'echo ok' 单独测；清 known_hosts 旧条目重连；
      ~/.ssh 700、authorized_keys 600。

坑 9：cron 里 rsync 找不到命令
结论：手动跑脚本正常，cron 里报 rsync: command not found。
原因：cron 环境 PATH 精简，不包含 /usr/bin。
解法：脚本里用全路径 /usr/bin/rsync，或脚本开头 export PATH。

坑 10：daemon 模式同步不了
结论：rsync 双冒号同步报 Connection refused / auth failed。
原因：873 端口没开（防火墙）、rsyncd 服务没起、secrets 文件权限不对。
解法：开防火墙 873/tcp 限来源；systemctl start rsyncd；secrets 文件
     权限 600；用户名密码核对。
```
