## 概述

文件同步解决「多台机器/多份位置保持数据一致」：rsync 增量同步（只传变化的部分，定时同步）、inotify + lsyncd 实时同步（文件变化立即同步）。rsync 是「按需/定时同步」，lsyncd 是「实时同步」（基于 inotify 监听文件变化）。选型：定时同步用 rsync，实时同步（双机热备、实时备份）用 lsyncd。

```text
# 实测（本机 rsync 已装）
$ rsync --version | head -1
rsync version 3.2.7
```

```text
两种同步方式：
1. rsync —— 增量同步（只传变化），定时/按需触发
2. inotify + lsyncd —— 实时同步（文件变化立即触发）
```

## 核心概念

1. **rsync 增量同步**：只传「变化的部分」（用校验和/大小/时间判断变化），不重传整个文件，所以同步大目录很快。
2. **inotify**：内核的文件变化通知机制，监听目录/文件的变化事件（创建/修改/删除），变化时通知用户态。
3. **lsyncd**：基于 inotify 的实时同步工具，监听文件变化 → 触发 rsync 同步到目标。
4. **定时 vs 实时**：rsync 定时同步有延迟但简单可靠，lsyncd 实时同步低延迟但依赖 inotify。

```text
rsync 增量原理：
只传「变化的文件」——对比大小/时间/校验和，没变的跳过
```

## 工作原理

1. **rsync 增量同步原理**：rsync 对比源和目标文件的「大小 + mtime」做快速判断，变化了再分块算校验和精确找出差异块，只传输差异部分。文件没变就完全跳过，所以重复同步大目录时几乎瞬间完成。
2. **inotify 原理**：内核 inotify 接口监控目录，文件变化（IN_CREATE/IN_MODIFY/IN_DELETE 等事件）时产生事件，lsyncd 读取事件并触发对应动作。
3. **lsyncd 工作流**：lsyncd 用 inotify 监听源目录 → 收到变化事件（可配 delay 合并连续变化）→ 调用 rsync 把变化同步到目标。

```text
inotify + lsyncd 原理：
文件变化 → inotify 通知内核 → lsyncd 收到事件 → 触发 rsync 同步到目标
```

## 常用命令与配置

```shell
rsync -avz /data/ backup:/backup/data/        # 增量同步到远程
rsync -avz --delete /data/ backup:/backup/data/  # 同步删除
rsync -avz --exclude='*.log' /data/ /backup/   # 排除文件
rsync -avz -P 大文件 backup:/backup/           # -P 显示进度 + 断点续传
```

```text
rsync 关键选项：
-a   归档模式（保留权限/时间/软链）
-z   压缩传输（网络传输省流量）
--delete  同步删除（目标端多余文件也删）
--exclude 排除文件
-P   显示进度 + 断点续传
```

```shell
apt install lsyncd           # 安装
systemctl enable --now lsyncd   # 启用
systemctl status lsyncd      # 状态
```

## 配置文件解析

```text
# lsyncd 配置（/etc/lsyncd/lsyncd.conf.lua 示例）
sync {
    default.rsync,
    source = "/data/",
    target = "backup:/backup/data/",
    delay = 1,        -- 变化后延迟 1 秒同步（合并连续变化）
}
```

```text
lsyncd 配置字段：
source  —— 要监听的源目录
target  —— 同步目标（本地路径或 用户@主机:路径）
delay   —— 收到变化后延迟 N 秒再同步（合并高频连续变化，避免频繁 rsync）
delete  —— 是否同步删除（默认 true，目标端多余文件也删）
exclude —— 排除的文件/目录
```

```text
rsync 远程同步格式：
rsync [选项] 源路径 目标路径
源/目标若是远程：用户@主机:路径（走 SSH）
```

## 应用场景实战

### 场景一：定时同步目录到备份机

```shell
# 1. rsync 增量同步
rsync -avz --delete /data/ backup:/backup/data/
# 2. 配 cron 每小时同步
# 0 * * * * rsync -avz --delete /data/ backup:/backup/data/ >> /var/log/sync.log 2>&1
```

### 场景二：双机实时热备（lsyncd）

```shell
# 1. 装 lsyncd
apt install lsyncd
# 2. 配置（监听 /data，变化即同步到 backup）
# 3. 启用
systemctl enable --now lsyncd
# 4. 验证：改 /data 下的文件，看是否立即同步
```

## 性能与调优

```text
1. 增量是核心 —— rsync 只传变化，大目录重复同步很快，别用 cp/scp 全量复制
2. 压缩取舍 —— -z 压缩传输省带宽，但 CPU 开销增加，网络慢才用
3. 大文件断点续传 —— -P（--partial --progress），中断后从断点继续，别重传
4. lsyncd delay 合并 —— 高频变化场景配 delay 合并，避免每次变化都触发一次完整 rsync
5. 海量小文件 —— inotify 每个文件都要监听，海量小文件场景 lsyncd 开销大，改用定时 rsync
```

## 安全与权限

```text
1. 远程同步走 SSH —— rsync 远程默认 SSH 加密传输，别用明文 rsync 协议
2. 权限保留 —— -a 保留文件权限/属主，同步后目标权限和源一致
3. 同步账号权限 —— 同步用的 SSH 账号给最小权限（只读源/只写目标），别用 root
4. --delete 危险 —— 会删目标端多余文件，目标选错会误删数据，先 --dry-run 预览
```

## 故障排查

```shell
# 1. 同步不生效/文件没过去
rsync -avzn /data/ backup:/backup/data/   # --dry-run 预览会传什么（不真传）
# 看是否路径/权限/排除规则问题

# 2. rsync 报权限/认证失败
ssh backup 'echo ok'                      # 先测 SSH 通不通、免密配好没

# 3. lsyncd 不同步
systemctl status lsyncd                   # lsyncd 在跑吗
journalctl -u lsyncd -n 50                # lsyncd 日志报什么

# 4. 同步任务卡住/没跑完
ps aux | grep rsync                       # rsync 进程在不在
ls /var/log/sync.log                      # 同步日志
```

## 常见问题

```text
Q1: rsync 源路径结尾的 / 有什么影响？
A: /data/ 复制「目录内容」到目标，/data 复制「目录本身」（含 data 目录名）。加不加 / 结果不同。

Q2: rsync 和 scp 有什么区别？
A: rsync 增量（只传变化，支持断点续传、--delete、排除），scp 全量复制。重复同步大目录 rsync 快得多。

Q3: 什么时候用 lsyncd 而不是 rsync 定时任务？
A: 需要低延迟实时同步（双机热备、实时备份）用 lsyncd；能容忍分钟级延迟的用 rsync 定时任务（更简单可靠）。

Q4: lsyncd 监听海量小文件为什么慢？
A: inotify 每个文件都要建立监听，海量小文件（几十万）导致监听开销大、内存高。这种场景改用定时 rsync。
```

## 面试题

```text
1. rsync 的增量同步是怎么实现的？
   答：对比源和目标的文件大小+mtime 快速判断，变化了再分块算校验和精确找出差异块，只传差异部分，没变的跳过。

2. inotify 和轮询（polling）有什么区别？
   答：inotify 是事件驱动（文件变化内核主动通知，低延迟低开销），轮询是定时扫描（有延迟、海量文件开销大）。实时同步靠 inotify。

3. 双向同步怎么做？rsync 能双向吗？
   答：rsync 是单向的，双向同步容易冲突。双向场景用专门工具（如 unison、syncthing），或明确主从方向。

4. 为什么 rsync 要加 --delete？有什么风险？
   答：不加 --delete 目标端多余的（源已删的）文件会残留，两端不一致；但 --delete 会删目标端文件，目标选错会误删，先 --dry-run 预览。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 定时同步用 rsync，实时热备用 lsyncd
2. rsync 加 --delete 保持完全一致（否则删除不同步）
3. 大文件传输加 -P（进度 + 断点续传）
4. lsyncd 配 delay 合并连续变化，避免频繁同步
5. 同步任务重定向日志 + flock 锁，防止并发

### 踩坑记录

```text
坑 1：rsync 没加 --delete，删除不同步
结论：源删了文件，目标端还有（两端不一致）。
原因：rsync 默认不删目标端多余文件。
解法：加 --delete 完全同步，或接受保留历史。

坑 2：rsync 路径结尾的 / 写错
结论：rsync /data 和 /data/ 结果不同。
原因：源路径结尾的 / 影响「复制目录本身还是目录内容」。
解法：/data/ 复制内容到目标，/data 复制目录本身（含 data 目录名）。

坑 3：lsyncd 监听海量小文件，性能差
结论：lsyncd 监听目录文件巨多，CPU/内存高。
原因：inotify 每个文件都要监听，海量文件开销大。
解法：减少监听范围，或改用定时 rsync（海量小文件不适合实时）。

坑 4：rsync 大文件传输中断，重来又从头
结论：传大文件断线，重试从头开始。
原因：没加 -P（断点续传），中断后重传整个文件。
解法：加 -P 支持断点续传。

坑 5：同步任务并发跑，数据错乱
结论：cron 同步任务上次没跑完，下次又启动。
原因：没加锁，并发同步可能冲突。
解法：flock 锁，或确保同步任务互斥。
```
