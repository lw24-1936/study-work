## 概述

存储管理三件事：性能评估（磁盘够不够快）、容量规划（磁盘够不够用）、老化与替换（磁盘寿命管理）。核心工具：iostat 测性能、df/du 看容量、smartctl 看健康（SMART 检测磁盘老化）。关键认知：磁盘会老化（HDD 坏道、SSD 有写入寿命），要提前规划替换，别等磁盘坏了才处理；容量要看「增长率」而不是「当前值」，阈值 80% 提醒、90% 告警。

```text
# 实测（本机存储现状，Ubuntu 24.04）
$ df -h /
/dev/sda2  915G  62G  807G  8%  /
$ df -i /
/dev/sda2  60981248 inodes  1067136 已用  2%  /
# 空间用 8%、inode 用 2%，存储很充裕；两块盘：sda 931.5G（ext4 根分区），
# sdb 119.2G（Windows 分区残留，ntfs）
```

```text
存储管理三件事：
1. 性能评估 —— iostat 看 IOPS/吞吐/延迟/繁忙度
2. 容量规划 —— df/du 看空间与 inode，按增长率预测
3. 老化替换 —— smartctl/SMART 监控健康，提前换盘
```

## 核心概念

### 1. 吞吐（throughput）

每秒读写的数据量（iostat 里 rkB/s / wkB/s），单位 MB/s。大文件顺序 IO 看吞吐：日志归档、视频处理、数据库全表扫描。HDD 顺序读 ~150-250MB/s，SATA SSD ~500MB/s，NVMe 2-7GB/s。

### 2. IOPS

每秒 IO 次数（iostat 里 r/s / w/s）。小文件随机 IO 看 IOPS：数据库随机读写、邮件存储、代码编译。HDD 随机 IOPS 只有 100-200，SSD 几万到几十万，NVMe 可达百万级。IOPS 和吞吐的关系：吞吐 ≈ IOPS × 单次 IO 大小（4K 随机读 10000 IOPS ≈ 40MB/s 吞吐）。

### 3. 延迟（await）

单次 IO 从发出到完成的时间（iostat 的 await，包含排队 + 服务时间），单位 ms。SSD 通常 <1ms，HDD 几 ms~几十 ms（随机 IO 含寻道）。延迟是「体验」指标：数据库事务、交互应用对延迟敏感，吞吐够大但延迟抖动也会出问题。

### 4. 队列深度（queue depth）与 aqu-sz

队列深度 = 同时在途（排队 + 正在处理）的 IO 请求数。iostat 的 aqu-sz 是平均队列长度。队列深度和性能的关系（Little 定律）：队列中请求数 = 到达率 × 平均耗时。设备饱和时队列越长、延迟越高；现代 SSD 靠深队列并行发挥性能（NVMe 队列深度 32/64 常见），HDD 深队列只增加排队延迟。

### 5. 繁忙度（%util）

磁盘忙碌时间占比（iostat %util），接近 100% 表示设备饱和。注意：%util 在多队列设备（NVMe）上可能失真（按 inflight 时间统计，可能超过 100%），判断饱和要结合 await 和队列长度，别只看 %util。

### 6. SMART

磁盘自监测、分析和报告技术：磁盘固件持续记录健康数据（重新分配扇区、擦写次数、通电时长、温度），smartctl/smartd 读取这些属性，用于预警老化。HDD 关键看坏道类属性（Reallocated_Sector_Ct），SSD 关键看写入寿命类（Wear_Leveling_Count、Media_Wearout_Indicator）。

### 7. inode 与容量

文件系统容量分两块：数据块（文件内容）和 inode（文件元数据：名字、权限、数据块指针）。df -h 看数据块用量，df -i 看 inode 用量。海量小文件场景 inode 先耗尽：df -h 显示还有空间，但创建文件报 No space left on device。ext4 默认 inode 数在格式化时定死（本机 60981248 个），XFS 可动态分配 inode。

### 8. HDD / SSD / NVMe 对比

```text
类型        随机读IOPS   顺序读    随机读延迟   写入寿命       适用
HDD 7200    ~100-200    150-250MB/s  5-15ms    无（机械磨损）  归档、大文件顺序读写
SATA SSD    10k-100k    ~500MB/s     0.1-0.5ms 有限（P/E cycles）通用业务盘
NVMe SSD    100k-1M+    2-7GB/s      0.02-0.1ms 有限（更高寿命）数据库、高并发
```

## 工作原理

### 1. IO 链路与 iostat 统计原理

```text
应用 write() → 页缓存（page cache，异步落盘）→ 内核块层（IO 调度器
排队/合并）→ 设备驱动 → 磁盘控制器 → 物理介质
应用 read() → 页缓存（未命中才下盘）→ 块层 → 驱动 → 介质
```

iostat 从内核的块设备统计（/proc/diskstats，基于 blk-mq 每队列统计）读取各层的 IO 请求数和耗时，换算成吞吐、IOPS、await、%util。await 高 = IO 慢（设备慢或排队久），%util 高 = 设备忙碌（饱和信号）。

### 2. HDD vs SSD vs NVMe 的物理差异

```text
HDD：磁头机械寻道 + 盘片旋转，随机 IO 要移动磁头（几 ms~十几 ms），
     顺序 IO 靠连续扇区预读，快但远低于 SSD；磨损是机械部件（电机/磁头）
SSD（SATA/NVMe）：闪存芯片，无机械部件，随机 IO 也快；但闪存单元
     擦写次数有限（P/E cycles），写放大（WA）会加速寿命消耗，
     靠磨损均衡（wear leveling）+ 预留空间（over-provisioning）延长寿命
NVMe：走 PCIe 直连 + 多队列（blk-mq），队列深度并行度高，延迟更低、
     吞吐更高；SATA SSD 受 AHCI 单队列限制，并行度低
```

### 3. SMART 原理

磁盘固件持续监测自身健康（ECC 纠错率、坏道重映射计数、擦写计数、温度、通电时长），写入磁盘的 SMART 属性区。smartctl 读取这些属性，smartd 守护进程定期自检并在指标异常时告警（邮件/脚本）。HDD 坏道重映射 = 物理坏块被备用扇区替代；SSD 磨损均衡计数接近上限 = 寿命将尽。

### 4. 队列深度与性能的关系

```text
Little 定律：L = λ × W
L = 队列中平均请求数（aqu-sz）
λ = IO 到达率（IOPS）
W = 平均完成时间（await）

推论：
- 设备未饱和时，深队列能提升吞吐（SSD 靠并行），延迟略增
- 设备饱和后，队列越长延迟线性增长，吞吐不再上升
- iostat 判读：await 高 + aqu-sz 大 + %util 高 = 饱和排队；
  await 高 + aqu-sz 小 + %util 低 = 设备本身慢（老化/坏道重试）
```

### 5. LVM 扩展原理（简述）

LVM 把多块物理盘（PV）聚合成卷组（VG），再切成逻辑卷（LV）挂载。扩容 = lvextend 扩大 LV → 文件系统感知新大小（ext4 用 resize2fs 在线扩展，XFS 用 xfs_growfs，只能扩不能缩）。因为不需要重建分区，LVM 是生产环境在线扩容的标准方案，详见 [[06.3-逻辑卷管理 LVM]]。

### 常用命令速查

```shell
# 性能
iostat -x 1 5                # 实时看吞吐/IOPS/延迟/繁忙度（每 1 秒采样 5 次）
iostat -d sda 2              # 只看某块盘的吞吐
sar -d 1 5                   # 历史/实时磁盘统计（sysstat 包）
iotop                        # 哪个进程在狂读写（交互式，需 root）
pidstat -d 1                 # 按进程看 IO（sysstat 包）
iostat -x 1 2 | grep -w sda  # 提取单盘行，方便脚本监控

# 容量
df -h                        # 空间用量
df -i                        # inode 用量（小文件多时也关注）
du -sh /var/* | sort -rh | head   # 哪个目录增长快
du -x --max-depth=1 / | sort -rh | head   # 从根找大目录（-x 不跨文件系统）
lsof +L1                     # 已删除但被进程占用的文件（占空间不释放）

# 健康
smartctl -a /dev/sda         # 查看磁盘健康（SMART 全部数据）
smartctl -H /dev/sda         # 健康状态（PASSED/FAILED）
smartctl -A /dev/sda         # SMART 属性（老化指标）
smartctl -t short /dev/sda   # 跑短自检（约 2 分钟）
smartctl -t long /dev/sda    # 跑长自检（数小时）

# 压测（fio 需安装）
fio --name=randread --rw=randread --bs=4k --size=1G --numjobs=1 --runtime=30 --group_reporting
fio --name=seqwrite --rw=write --bs=1M --size=2G --runtime=30 --group_reporting

# 文件系统工具
fsck /dev/sda2               # 检查修复（须先卸载或只读挂载）
tune2fs -l /dev/sda2 | head  # ext4 文件系统信息（块数/inode 数）
xfs_repair -n /dev/vg/lv     # XFS 只读检查（Red Hat 系）
```

## 配置文件解析

### 1. /etc/smartd.conf（SMART 守护进程）

smartd 后台定期自检 + 指标异常告警，不用手动跑 smartctl：

```text
# /etc/smartd.conf（示例）
# 所有设备：健康检查失败发邮件给 root；每周日 02:00 短自检
DEVICESCAN -m root -M test

# 单设备写法：/dev/sda -H -m root -s (S/../../7/02)
#   -H      健康状态（SMART overall-health）异常时告警
#   -m root 告警邮件收件人
#   -M test 首次启动发测试邮件
#   -s (S/../../7/02)  每周日 02:00 短自检（S=short；L=long）
```

```text
SMART 关键属性（smartctl -A 输出，ID 列）：
5   Reallocated_Sector_Ct      重新分配扇区数（HDD 坏道，>0 需警惕，持续增长必换盘）
9   Power_On_Hours             通电时长
177 Wear_Leveling_Count        磨损均衡计数（SSD，接近上限 = 寿命将尽）
187 Reported_Uncorrect         无法纠正的错误
194 Temperature_Celsius        温度（过高加速老化）
197 Current_Pending_Sector     待重映射扇区（读失败待定，可能发展成坏道）
198 Offline_Uncorrectable      离线不可纠正错误
233 Media_Wearout_Indicator    介质磨损指示（SSD，剩余寿命百分比）
241 Total_LBAs_Written         累计写入量（SSD，算每日写入量估寿命）
```

### 2. 挂载参数（/etc/fstab）

```text
# /etc/fstab（示例，ext4 根分区）
UUID=xxxx-xxxx  /  ext4  defaults,noatime  0 1
#                          ^^^^^^^^
# 常用优化参数：
# noatime      不更新访问时间（减少写 IO，数据库/日志盘推荐）
# nodiratime   不更新目录访问时间
# commit=60    数据提交间隔秒数（默认 5，调大减少写盘频率，崩溃丢数据窗口变大）
# barrier=0    ext4 关闭写屏障（换性能，掉电一致性风险，生产不建议）
# usrquota,grpquota  启用配额（quota 工具链）
# 挂载参数改动生效：mount -o remount /  （或重启）
```

Red Hat 系默认文件系统是 XFS，fstab 里 XFS 的配额参数是 `uquota,gquota`（或 prjquota 项目配额），与 ext4 的 usrquota/grpquota 不同。

### 3. IO 调度器配置

调度器是内核块层决定「IO 请求按什么顺序下发」的策略，可运行时切换：

```text
# 查看/切换当前调度器
cat /sys/block/sda/queue/scheduler        # 方括号内是当前生效的
echo none > /sys/block/sda/queue/scheduler  # 临时切换（重启失效）

# 永久生效：udev 规则
# /etc/udev/rules.d/60-iosched.rules
ACTION=="add|change", KERNEL=="sd*", ATTR{queue/scheduler}="mq-deadline"

# 调度器选择：
# none      —— NVMe/高性能 SSD，不做排序，减少开销（内核自动默认）
# mq-deadline —— HDD/普通 SSD，保证每个请求有截止时间，防饿死（本机 sda 默认）
# bfq       —— 桌面/多用户交互场景，按进程公平分配带宽
# 内核参数：elevator=none 可开机指定（grub 内核命令行）
```

### 4. 配额工具配置（quota vs xfs_quota）

```text
ext4 系（Ubuntu 默认）：quota 工具链
1. 挂载加 usrquota：/etc/fstab 对应行加 usrquota,grpquota
2. apt install quota
3. quotacheck -cug /   （生成配额数据库 aquota.user/aquota.group）
4. quotaon /           （开启配额）
5. edquota -u alice    （交互式设置软/硬限额）
   setquota -u alice 500M 600M 10000 12000 /   （命令行设置：软/硬块、软/硬 inode）

XFS 系（Red Hat 默认）：xfs_quota（配额是 XFS 内建功能，无需数据库文件）
1. 挂载加 uquota：/etc/fstab 加 uquota,gquota 后 remount
2. xfs_quota -x -c 'limit bsoft=500m bhard=600m user alice' /data
3. xfs_quota -x -c 'report -u' /data     （查看配额使用）
```

### 5. Red Hat 系差异对照

| 项 | Ubuntu | Red Hat 系（RHEL/CentOS/Rocky） |
|---|---|---|
| 默认文件系统 | ext4 | XFS |
| 容量命令 | df -h / df -i（两系相同） | 同左；XFS 无 df -i 的 inode 上限概念（动态 inode） |
| 配额工具 | quota（quotacheck/quotaon/edquota） | xfs_quota（XFS 内建） |
| 扩容命令 | lvextend + resize2fs | lvextend + xfs_growfs（XFS 只能扩不能缩） |
| smartmontools | apt install smartmontools | dnf install smartmontools（包名相同） |
| sysstat（iostat/sar） | apt install sysstat | dnf install sysstat |
| fio / iotop | apt install fio iotop | dnf install fio iotop |
| fsck | e2fsck（ext4）/ fsck | xfs_repair（XFS，不能挂载时用） |
| 调度器 | none/mq-deadline/bfq | 同左（内核 5.0+ 行为一致） |

## 应用场景实战

### 场景一：磁盘空间告警，做容量规划

```shell
# 1. 看当前用量
df -h
# 2. 找增长源头（从根开始逐层找大目录）
du -x --max-depth=1 / 2>/dev/null | sort -rh | head
# 3. 记录历史（每天 df 快照，或监控系统采集 df 指标）
df -h / | awk 'NR==2{print strftime("%F"), $5}' >> /var/log/df-history.log
# 4. 算增长率，预测满的时间
#    例：当前 60%，一周前 53%，日增长 1% → 40 天后到 100%
#    按 80% 告警阈值算：20 天后触发告警，需提前扩容/清理
# 5. 已删除但被进程占用的空间（df 显示满但 du 找不出）
lsof +L1 | head
```

```text
容量规划要点：
- 阈值：80% 提醒、90% 告警、95% 紧急（写满 = 服务不可写，数据库直接挂）
- 增长率 = (当前用量 - 历史用量) / 天数，按线性外推预测，波动大的业务
  同时看周/月趋势
- 预留：业务扩容、日志突增、临时文件都要预留，别卡着 90% 规划
- inode 同样监控：df -i 超过 80% 也要告警（小文件场景）
```

## 性能与调优

```text
1. 先分清「慢」和「忙」 —— await 高是设备慢，%util 高是饱和；前者换盘，
   后者分流/加盘。一上来就调参数容易南辕北辙
2. 换 SSD —— 随机 IO 密集（数据库、编译、邮件）场景 HDD 换 SSD 收益最大，
   延迟降一个数量级
3. IO 调度器 —— SSD/NVMe 用 none（减少调度开销），HDD 用 mq-deadline/bfq；
   本机 sda（HDD）实测默认 mq-deadline
4. 挂载参数 —— 日志/数据库盘加 noatime 减少写 IO；commit 调大减少落盘
   频率（权衡崩溃丢失窗口）
5. 预读 —— 顺序读为主的场景调大 readahead：blockdev --setra /dev/sda
   （单位 512 字节扇区）或写 /sys/block/sda/queue/read_ahead_kb（KB）
6. 数据库/高 IO 服务独立磁盘 —— 别和日志/系统盘混用，IO 竞争互相拖累；
   用 LVM/RAID 把热点盘隔开
7. 压测基线 —— 用 fio 测出新盘的吞吐/IOPS/延迟基线，后续对比判断是否
   退化（同样的盘跑同样参数，IOPS 掉 30%+ 就是有问题）
8. 分层存储 —— 热数据上 SSD/NVMe，温数据 HDD，冷数据归档/对象存储；
   数据库热表单独放 NVMe 盘，历史分区迁移到 HDD
```

```text
fio 压测参数速查：
--rw=randread/randwrite/read/write  随机/顺序 读/写
--bs=4k/1M                          块大小（模拟小文件随机/大文件顺序）
--size=1G --runtime=30              数据量/时长
--numjobs=4                         并发进程数
--group_reporting                   汇总报告
输出看：IOPS=、BW=（吞吐）、lat avg/p99（延迟）
```

## 安全与权限

```text
1. 磁盘健康检测权限 —— smartctl 读 SMART 需要 root（或 sudo）；生产用
   smartd 守护进程 + sudo 权限收敛，别把 root 密码散出去
2. 替换磁盘前备份 —— 换盘前先备份 + 验证备份可恢复（恢复演练），
   别直接拔盘；RAID 阵列换盘先确认阵列状态（degraded 时别乱拔）
3. 磁盘加密 —— 敏感数据盘用 LUKS 加密（cryptsetup luksFormat），防物理
   偷盘泄露；注意加密盘 SMART/性能监控仍可用，但 fsck 要在解密后进行
4. 配额与权限 —— 配额是软限制不是安全边界（内核强制但可被绕过），
   权限控制仍靠 ACL/属主；quota 数据库文件（aquota.*）权限 600
5. 监控数据权限 —— 容量/性能监控数据含业务规模信息（io 特征、目录结构），
   访问权限控制，别把 Grafana/Prometheus 裸暴露公网
6. 日志审计 —— 磁盘替换/扩容操作记审计日志（谁、哪块盘、何时），
   生产变更可追溯
```

## 故障排查

### 案例 1：磁盘 IO 慢，服务卡顿

```shell
# 1. 全局确认是不是磁盘问题
iostat -x 1 5
# 判读矩阵：
#   await 高 + %util 低 + aqu-sz 小 → 设备本身慢（老化/坏道重试/机械盘随机 IO）
#   await 高 + %util 高 + aqu-sz 大 → 饱和排队（负载超过设备能力）
# 2. 找进程
iotop -o
pidstat -d 1
# 3. 慢 → 查 SMART（坏道重试会让延迟暴涨）→ 换盘
#    忙 → 分流：业务错峰、缓存、加盘（LVM/RAID）
# 4. 验证：优化后再采 iostat 对比
```

### 案例 2：df 显示有空间，但写不进文件

```shell
# 症状：创建文件报 No space left on device，df -h 却还有空间
# 1. 查 inode
df -i
# inode 100% → 海量小文件耗尽元数据。找小文件大户：
find / -xdev -type f | wc -l
du --inodes -x / 2>/dev/null | sort -rh | head
# 解法：清理小文件（缓存/临时文件）、合并到归档、或迁移到 inode 多的
#      文件系统（XFS 动态 inode 不受限）
# 2. 另一种可能：已删除文件仍被进程占用
lsof +L1
# 解法：重启对应进程（或 kill），空间即释放；注意别 kill 错关键服务，
#      先确认是哪个进程（常见：日志被删但 logger 还握着 fd）
```

### 案例 3：文件系统只读（Read-only file system）

```shell
# 症状：写入报 Read-only file system，dmesg 有 EXT4-fs error / I/O error
# 1. 看内核日志定位原因
dmesg | tail -50
journalctl -k | grep -i 'ext4\|io error'
# 2. 确认是否硬件问题：SMART + 自检
smartctl -H /dev/sda
smartctl -t short /dev/sda
# 3. 硬件没问题（偶发错误/脏文件系统）：重新挂载读写，或卸载后 fsck
mount -o remount,rw /          # 紧急恢复可写（只读保护数据，确认安全再开）
umount /data && fsck -f /dev/sda2   # 卸载后强制检查（生产维护窗口做）
mount /data
# 4. 硬件坏（SMART FAILED/大量 IO error）：数据先备份，换盘
# 注意：只读挂载是内核的自我保护（避免错误扩散），先诊断再强行 remount,rw
```

### 案例 4：SMART 健康异常 / FAILED

```shell
# 症状：smartctl -H 报 FAILED，或属性异常
smartctl -A /dev/sda | grep -E 'Reallocated|Pending|Uncorrect|Wear'
# 判读：
# HDD：Reallocated_Sector_Ct 增长 / Current_Pending_Sector >0 → 坏道在发展
# SSD：Wear_Leveling_Count 接近上限 → 寿命将尽
# 处理：
# 1. 立即备份数据（先备份再排查，磁盘故障随时可能恶化）
# 2. 确认备份可恢复后申请换盘
# 3. RAID 场景：标记坏盘 hotspare 顶上，在线替换
# 4. 换完跑一次长自检 + fio 压测验证新盘
```

### 案例 5：LVM 扩容后 df 没变大

```shell
# 症状：lvextend 成功，df -h 容量没变
# 原因：忘了扩展文件系统（lvextend 只扩了逻辑卷层）
# 检查：
lvs /dev/vgdata/lvdata          # 逻辑卷大小（已扩）
df -h /data                     # 文件系统大小（未变）
# 解法：
resize2fs /dev/vgdata/lvdata    # ext4
xfs_growfs /data                # XFS（注意参数是挂载点不是设备）
# 验证：df -h /data 看到新容量
# 踩过的坑：XFS 用 resize2fs 会报错（不识别 XFS），先确认文件系统类型
#          （blkid /dev/vgdata/lvdata 或 df -T）
```

## 常见问题

```text
Q1: await 和 %util 怎么区分「慢」还是「忙」？
A: await 高 + %util 低 = 设备本身慢（老化/坏道重试/机械盘随机 IO），换盘；
   %util 高 + 队列深 = 设备饱和（负载太高），加盘/分流。两个都高 = 又慢
   又忙，先解决慢（换盘）。

Q2: SSD 为什么会有写入寿命？
A: 闪存靠「擦写」存储数据（写前先擦），每个单元的擦写次数有限
   （P/E cycles，TLC 约 1000 次级别）。写满寿命后单元失效、坏块增多。
   用 SMART 的 Wear_Leveling_Count / Media_Wearout_Indicator 监控，
   同时关注 Total_LBAs_Written 算每日写入量，估算剩余寿命。

Q3: 容量规划为什么看「增长率」而不是「当前值」？
A: 当前 8% 但每天 +1%，40 天就满；当前 60% 但每月 +1%，两年都没事。
   看增长率能算出「预计满的时间」，在 80% 阈值前提前扩容或清理。

Q4: 磁盘健康检查多久做一次？
A: 用 smartd 守护进程持续监控（后台自检 + 指标异常告警），不用手动跑；
   关键业务盘每周一次短自检、每月一次长自检（smartd 的 -s 计划），
   替换周期参考厂商 MTBF 和 SMART 趋势。

Q5: IOPS、吞吐、延迟是什么关系？
A: 吞吐 = IOPS × 单次 IO 大小（4K 随机 10000 IOPS ≈ 40MB/s）；延迟是
   单次 IO 完成时间。三个指标互相制约：IO 越小 IOPS 越高但吞吐越低，
   设备饱和后 IOPS 和吞吐到顶、延迟线性增长。看业务：大文件顺序看
   吞吐，小文件随机看 IOPS，交互/事务看延迟。

Q6: inode 满和空间满有什么区别？
A: 空间满 = 数据块耗尽（df -h 100%），inode 满 = 元数据耗尽
   （海量小文件，df -i 100%）。inode 满时 df -h 还有空间却写不进文件。
   小文件多的场景（缓存目录、邮件存储）两个指标都要监控。

Q7: 磁盘变成只读怎么办？
A: 先 dmesg 看原因（EXT4-fs error / I/O error），确认是否硬件问题
   （SMART/自检）；硬件没问题就 umount + fsck 修复后重新挂载；硬件坏了
   先备份再换盘。只读是内核保护，别急着 remount,rw 掩盖问题。

Q8: LVM 在线扩容的完整步骤？
A: ① 确认是 LVM（lsblk/pvdisplay）；② 新盘 pvcreate + vgextend 进卷组
   （或卷组有剩余空间）；③ lvextend -L +10G 扩逻辑卷；④ resize2fs
   （ext4）或 xfs_growfs（XFS，参数是挂载点）；⑤ df -h 验证。漏了第 ④
   步 df 不会变。

Q9: 怎么给用户限制磁盘用量？
A: 配额：ext4 用 quota 工具链（fstab 加 usrquota → quotacheck → quotaon
   → edquota/setquota）；XFS 用 xfs_quota（挂载加 uquota → xfs_quota
   limit）。配额设软/硬两级：软配额超了有宽限期，硬配额直接拒绝写入。
```

## 面试题

```text
1. 怎么判断一块磁盘「慢」还是「忙」？
   答：iostat -x 看 await 和 %util。await 高 + %util 低 + 队列浅 = 设备
   响应慢（老化/坏道重试/机械盘），换盘；%util 高 + 队列深 = 设备饱和
   （负载超能力），加盘/分流。两个都高先解决慢。

2. HDD 和 SSD 的性能差异在哪？为什么？
   答：HDD 机械寻道 + 盘片旋转，随机 IO 要移动磁头（5-15ms），随机 IOPS
   只有 100-200；SSD 闪存无机械部件，随机 IO 也快（<1ms，IOPS 万级），
   NVMe 走 PCIe 多队列可达百万 IOPS。代价是 SSD 有写入寿命（P/E cycles）
   和写放大。

3. 磁盘 inode 满和空间满有什么区别？怎么排查？
   答：空间满 = 数据块耗尽（df -h），inode 满 = 元数据耗尽（海量小文件，
   df -i）。inode 满时 df -h 有空间但创建文件报 No space left on device。
   排查：df -i 确认，find/du --inodes 找小文件大户，清理或迁移到
   XFS（动态 inode）。

4. 怎么提前发现磁盘要坏？
   答：SMART 监控（smartctl/smartd）：HDD 看 Reallocated_Sector_Ct 是否
   增长、Current_Pending_Sector 是否 >0（坏道发展）；SSD 看
   Wear_Leveling_Count / Media_Wearout_Indicator（寿命）。指标异常 +
   定期自检（short/long），发现老化提前备份换盘。

5. IOPS、吞吐、延迟、队列深度四者的关系？
   答：吞吐 = IOPS × IO 大小；延迟 = 排队 + 服务时间；Little 定律
   L = λ × W（队列长度 = 到达率 × 完成时间）。设备未饱和时深队列提高
   吞吐（SSD 并行），饱和后队列加深、延迟线性涨。iostat 里 aqu-sz 是
   队列长度，await 是完成时间。

6. LVM 在线扩容的流程？ext4 和 XFS 有什么不同？
   答：pvcreate/vgextend（新盘进卷组）→ lvextend 扩逻辑卷 → 文件系统
   感知：ext4 用 resize2fs（在线安全），XFS 用 xfs_growfs（参数是挂载点，
   只能扩不能缩）。缩容 XFS 必须重建。

7. 生产环境怎么给磁盘做容量规划？
   答：监控 df -h/df -i 历史趋势算增长率，线性外推预测满的时间；阈值
   80% 提醒、90% 告警；预留业务扩容/日志突增空间；小文件场景同时监控
   inode；超阈值动作按预案执行（清理日志/归档/扩容/加盘）。

8. iostat 里哪些指标说明磁盘饱和了？
   答：%util 接近 100% + aqu-sz 持续增大 + await 上升但 IOPS/吞吐不再
   增长 = 饱和。注意 NVMe 多队列下 %util 可能失真（按 inflight 统计），
   结合 await 趋势和队列深度判断，别只看 %util 一个数。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 存储性能看 iostat 的 await 和 %util，先分清「慢」和「忙」再动手
2. 容量规划看「增长率」，阈值 80% 提醒 90% 告警，别等 100%
3. 定期 smartctl 检查磁盘健康（smartd 常驻），老化指标异常提前替换
4. SSD 关注写入寿命（Wear_Leveling/Media_Wearout），HDD 关注坏道（Reallocated/Pending）
5. 磁盘替换前先备份 + 验证备份可恢复，RAID 场景先确认阵列状态
6. LVM 扩容三步缺一不可：lvextend → resize2fs/xfs_growfs → df 验证
7. 新盘上线先 fio 压测建基线，之后定期复测对比退化
8. 高 IO 服务独立磁盘（LVM/RAID 隔离），别和日志/系统盘混用
9. 已删除文件占空间先 lsof +L1 找进程，别盲目重启服务
10. Red Hat 系 XFS 注意：扩容用 xfs_growfs、修复用 xfs_repair、配额用 xfs_quota

### 踩坑记录

```text
坑 1：只看空间用量，忽略 inode
结论：df 显示空间够，但创建文件报 No space left on device。
原因：inode 用满（大量小文件），df -i 能看出。
解法：df -i 纳入监控，小文件多的场景（缓存/邮件/编译产物）关注 inode。

坑 2：容量规划只看当前值，忽略增长率
结论：磁盘当前够用，突然就满了，服务不可写。
原因：没看增长率，日志/数据增长快（日增几个百分点）。
解法：记录历史趋势（df 快照或监控采集），按增长率预测满的时间，
     80% 阈值前扩容。

坑 3：磁盘坏了才换，数据丢失
结论：磁盘彻底坏了才处理，数据丢了。
原因：没做 SMART 健康检测，没提前预警。
解法：smartd 常驻 + 定期 smartctl 检查，老化指标异常（Reallocated
     增长/Pending >0/寿命将尽）就提前替换。

坑 4：SSD 用满写入寿命还继续写
结论：SSD 写入寿命耗尽，出现坏块/数据丢失。
原因：没关注 SSD 的 Wear_Leveling / Media_Wearout 指标，也不知道
     每天写多少。
解法：监控写入量（Total_LBAs_Written 算日均），寿命快尽时提前换盘；
     日志/临时数据不要全堆在 SSD 上。

坑 5：替换磁盘时没验证备份
结论：换盘前备份了，恢复时发现备份是坏的。
原因：备份没验证过，以为备份了就行。
解法：备份后验证可恢复（定期恢复演练），再换盘；RAID 换盘先确认
     阵列状态。

坑 6：只看 %util 判断磁盘饱和
结论：%util 100% 以为饱和了，实际设备还在正常服务；或 %util 低但
     延迟很高。
原因：%util 在多队列设备（NVMe）上按 inflight 时间统计可能失真；
     单看一个指标会误判。
解法：%util + await + aqu-sz 三个一起看，再结合 IOPS/吞吐是否到顶。

坑 7：df 满但 du 找不到大文件
结论：df 显示 100%，du 加起来却对不上，空间被「吃掉」了。
原因：文件被删除但进程还持有 fd（常见：日志被 logrotate 删了但
     logger 没重启），空间要等进程释放。
解法：lsof +L1 找 deleted 文件对应进程，重启/重载进程释放空间。

坑 8：XFS 用 resize2fs 扩容报错
结论：lvextend 后按 ext4 习惯跑 resize2fs，报 unrecognized filesystem。
原因：Red Hat 系默认 XFS，扩容命令是 xfs_growfs（参数是挂载点），
     resize2fs 只认 ext 系。
解法：先 df -T / blkid 确认文件系统类型；XFS 用 xfs_growfs /挂载点。

坑 9：扩容后忘了扩展文件系统，df 没变
结论：lvextend 成功了，df -h 容量还是老样子，以为扩容失败。
原因：lvextend 只扩了逻辑卷层，文件系统没感知新大小。
解法：lvextend 后必须 resize2fs（ext4）/ xfs_growfs（XFS），再 df 验证。

坑 10：SMART 自检期间以为磁盘坏了
结论：跑 smartctl -t long 时业务 IO 明显变慢，以为盘坏了。
原因：自检是磁盘控制器密集读盘，会占用设备带宽，属正常现象。
解法：长自检安排在维护窗口/低峰；短自检影响小；监控脚本遇到自检
     期间的延迟抖动先看 smartctl -l selftest 结果再定性。
```
