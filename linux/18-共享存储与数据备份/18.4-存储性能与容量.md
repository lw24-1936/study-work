## 概述

存储管理三件事：性能评估（磁盘够不够快）、容量规划（磁盘够不够用）、老化与替换（磁盘寿命管理）。核心工具：iostat 测性能、df 看容量、smartctl 看健康（SMART 检测磁盘老化）。关键认知：磁盘会老化（尤其 SSD 有写入寿命），要提前规划替换，别等磁盘坏了才处理。

```text
# 实测（本机存储现状）
$ df -h / 
/dev/sda2  915G  62G  807G  8%  /
$ df -i /
/dev/sda2  60981248 inodes  1064499 已用  2%  /
# 空间用 8%、inode 用 2%，存储很充裕
```

## 核心概念

1. **吞吐（throughput）**：每秒读写的数据量（rkB/s / wkB/s），大文件顺序 IO 看吞吐。
2. **IOPS**：每秒 IO 次数（r/s / w/s），小文件随机 IO 看 IOPS。
3. **延迟（await）**：单次 IO 的平均等待时间，SSD 通常 <1ms，HDD 几 ms~几十 ms。
4. **繁忙度（%util）**：磁盘忙碌时间占比，接近 100% = 饱和。
5. **SMART**：磁盘自监测机制，记录重新分配扇区、写入寿命等健康指标，用于预警老化。

```text
存储性能指标：
1. 吞吐 rkB/s/wkB/s —— 每秒读写 KB
2. IOPS r/s/w/s —— 每秒读写次数
3. 延迟 await —— 单次 IO 等待（SSD <1ms，HDD 几~几十 ms）
4. 繁忙度 %util —— 接近 100% = 饱和
```

## 工作原理

1. **性能指标原理**：IO 是「应用 → 内核 → 块设备」的链路，iostat 从内核统计各层的 IO 请求数和耗时。await 高 = IO 慢（设备慢或排队），%util 高 = 设备饱和。
2. **HDD vs SSD**：HDD 机械寻道（磁头移动），随机 IO 慢、顺序 IO 快；SSD 无机械部件，随机 IO 也快，但有「写入寿命」（闪存擦写次数有限）。
3. **SMART 原理**：磁盘固件持续记录健康数据（坏道重映射、擦写次数、通电时长），smartctl 读取这些属性判断磁盘是否接近寿命终点。

```text
HDD 机械寻道 → 随机 IO 慢；SSD 无机械部件 → 随机快但有写入寿命
SMART = 磁盘固件记录健康指标 → smartctl 读取预警老化
```

## 常用命令与配置

```shell
iostat -x 1 5           # 实时看吞吐/延迟/繁忙度
iostat -d sda           # 某块盘的吞吐
df -h                   # 空间用量
df -i                   # inode 用量（小文件多时也关注）
du -sh /var/* | sort -rh | head   # 哪个目录增长快

smartctl -a /dev/sda          # 查看磁盘健康（SMART 数据）
smartctl -H /dev/sda          # 健康状态（PASSED/FAILED）
smartctl -A /dev/sda          # SMART 属性（看老化指标）

fio --name=test --rw=randread --size=1G   # 压测随机读（fio 需装）
```

## 配置文件解析

```text
容量规划数据源与配置：
监控系统（Prometheus/Grafana 等）记录 df 历史 —— 看增长率趋势
告警阈值 —— 80% 提醒、90% 告警，别等 100%

SMART 检测配置（smartd 守护进程）：
/etc/smartd.conf         —— smartd 配置，定期自检 + 邮件告警
# 例：/dev/sda -H -m root   —— 健康检查失败时给 root 发邮件
```

```text
SMART 老化指标：
1. Reallocated_Sector_Ct 重新分配扇区（HDD 坏道）
2. Wear_Leveling_Count 写入寿命（SSD）
3. Power_On_Hours 通电时长
4. 指标异常 = 磁盘老化，提前替换
```

## 应用场景实战

### 场景一：磁盘空间告警，做容量规划

```shell
# 1. 看当前用量和增长
df -h
# 2. 记录历史（每天 df 快照，或监控系统）
# 3. 算增长率，预测满的时间
# 如：当前 60%，每天 +1%，40 天后满 → 提前清理或扩容
# 4. 找增长源头
du -sh /* 2>/dev/null | sort -rh | head
```

### 场景二：定期检查磁盘健康，提前替换

```shell
# 1. 定期 SMART 检查（cron 每周）
smartctl -H /dev/sda
# 2. 看老化指标
smartctl -A /dev/sda | grep -E 'Reallocated|Wear|Power_On'
# 3. 发现老化 → 备份数据 + 换盘
```

## 性能与调优

```text
1. IO 慢先看 await 和 %util —— await 高是设备慢，%util 高是饱和，区分「慢」和「忙」
2. 换 SSD —— 随机 IO 密集的场景 HDD 换 SSD 收益最大
3. 调整 IO 调度器 —— SSD 用 none/mq-deadline（减少调度开销），HDD 用 mq-deadline/bfq
4. 数据库/高 IO 服务独立磁盘 —— 别和日志/系统盘混用，IO 竞争互相拖累
5. 压测基线 —— 用 fio 测出新盘的吞吐/IOPS/延迟基线，后续对比判断是否退化
```

## 安全与权限

```text
1. 磁盘健康检测权限 —— smartctl 读 SMART 需要 root（或 sudo）
2. 替换磁盘前备份 —— 换盘前先备份 + 验证备份可恢复，别直接拔盘
3. 磁盘加密 —— 敏感数据盘用 LUKS 加密，防物理偷盘泄露数据
4. 监控数据权限 —— 容量/性能监控数据含业务信息，访问权限控制
```

## 故障排查

```shell
# 1. 磁盘 IO 慢
iostat -x 1 5                       # await 高还是 %util 高
iotop                               # 哪个进程在狂读写
# await 高 = 设备问题（老化/坏了），%util 高 = 负载饱和（加盘/分流）

# 2. 磁盘快满
df -h && df -i                      # 空间/inode 用量
du -sh /* 2>/dev/null | sort -rh | head   # 谁占的多

# 3. 磁盘健康异常
smartctl -H /dev/sda                # 健康状态 FAILED？
smartctl -A /dev/sda | grep -E 'Reallocated|Wear'   # 老化指标
```

## 常见问题

```text
Q1: await 和 %util 怎么区分「慢」还是「忙」？
A: await 高（设备响应慢）= 磁盘本身慢/老化；%util 高（设备饱和）= 负载太高。前者换盘，后者加盘/分流。

Q2: SSD 为什么会有写入寿命？
A: 闪存靠擦写存储数据，擦写次数有限（P/E cycles）。写满寿命后坏块增多，用 SMART 的 Wear_Leveling_Count 监控。

Q3: 容量规划为什么看「增长率」而不是「当前值」？
A: 当前 8% 但每天 +1%，40 天就满。看增长率能提前预判满的时间，提前清理或扩容。

Q4: 磁盘健康检查多久做一次？
A: 用 smartd 守护进程持续监控（后台自检），关键指标异常自动告警，不用手动定期跑。
```

## 面试题

```text
1. 怎么判断一块磁盘「慢」还是「忙」？
   答：iostat -x 看 await 和 %util。await 高 = 设备响应慢（慢），%util 高 = 设备饱和（忙）。慢换盘，忙分流/加盘。

2. HDD 和 SSD 的性能差异在哪？
   答：HDD 机械寻道，随机 IO 慢（几十 ms）、顺序快；SSD 无机械部件，随机 IO 也快（<1ms），但有写入寿命限制。

3. 磁盘 inode 满和空间满有什么区别？
   答：空间满 = 数据块耗尽（df -h），inode 满 = 元数据耗尽（海量小文件，df -i）。inode 满时 df -h 还有空间却写不进。

4. 怎么提前发现磁盘要坏？
   答：用 SMART（smartctl/smartd）监控重新分配扇区（HDD 坏道）、写入寿命（SSD）等指标，指标异常提前备份 + 换盘。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 存储性能看 iostat 的 await 和 %util，别只看吞吐
2. 容量规划看「增长率」，阈值 80% 提醒 90% 告警
3. 定期 smartctl 检查磁盘健康，老化提前替换
4. SSD 关注写入寿命（Wear_Leveling），HDD 关注坏道（Reallocated）
5. 磁盘替换前先备份 + 验证备份可恢复

### 踩坑记录

```text
坑 1：只看空间用量，忽略 inode
结论：df 显示空间够，但创建文件报错。
原因：inode 用满（大量小文件），df -i 能看出。
解法：df -i 也纳入监控，小文件多的场景关注 inode。

坑 2：容量规划只看当前值，忽略增长率
结论：磁盘当前够用，突然就满了。
原因：没看增长率，日志/数据增长快。
解法：记录历史趋势，按增长率预测，提前扩容。

坑 3：磁盘坏了才换，数据丢失
结论：磁盘彻底坏了才处理，数据丢了。
原因：没做 SMART 健康检测，没提前预警。
解法：定期 smartctl 检查，老化指标异常就提前替换。

坑 4：SSD 用满写入寿命还继续写
结论：SSD 写入寿命耗尽，出现坏块/数据丢失。
原因：没关注 SSD 的 Wear_Leveling（写入寿命）指标。
解法：SSD 监控写入量，寿命快尽时提前换盘。

坑 5：替换磁盘时没验证备份
结论：换盘前备份了，恢复时发现备份是坏的。
原因：备份没验证过，以为备份了就行。
解法：备份后验证可恢复（定期恢复演练），再换盘。
```
