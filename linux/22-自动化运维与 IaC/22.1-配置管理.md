## 概述

配置管理解决「几十上百台服务器怎么统一管理」的问题——装同样的软件、改同样的配置、发同样的文件，靠 SSH 一台台手动登录既不现实也容易出错。Ansible 是这类工具的标杆：**无 agent（代理）架构**，控制机通过 SSH 直连目标机，用 YAML 写的 playbook 描述「目标状态」，执行时幂等地把机器收敛到目标状态。和 Puppet/Chef（需要装 agent）、SaltStack（需要 minion）相比，Ansible 零部署成本、上手最快，是 Linux 运维配置管理的主流选择。

```text
配置管理核心价值：把「逐台人肉操作」变成「声明式批量收敛」
- 无 agent：SSH 直连，目标机不用装任何东西（只需 Python）
- 幂等：重复执行结果一致，不重复改
- 声明式：playbook 描述「目标状态」，Ansible 算怎么做
- 批量：一个命令/剧本同时作用于几十上百台
- 可审计：playbook 即文档，配置变更可版本化
```

## 核心概念

### Ansible 概述

Ansible 由 Red Hat 维护，架构极简：**控制机（control node）** 装 Ansible，**受管机（managed node）** 只需要 SSH + Python（几乎每台 Linux 都有）。控制机通过 SSH 把一个个小任务（模块）推送到目标机执行、回收结果。没有常驻 agent，也没有中央服务器，这就是它和 Puppet/Chef 最大的区别。

```text
Ansible 核心组件：
- 控制机（control node）    装 Ansible 的机器，发命令/跑 playbook
- 受管机（managed node）    被管理的目标机，只需 SSH + Python
- inventory                 主机清单，定义管哪些机器、怎么分组
- module                    模块，执行具体操作的单元（装包/拷文件/起服务）
- playbook                  剧本，YAML 写的任务清单，编排多个模块
- role                      角色，可复用的任务/模板/变量集合
```

```shell
# 验证 Ansible 安装与版本
ansible --version
# 示例输出：
# ansible [core 2.16.x]
#   config file = /etc/ansible/ansible.cfg
#   python version = 3.12.x

# 用 ansible-doc 看任意模块的文档（内置几百个模块，这是你的字典）
ansible-doc -l | wc -l          # 看模块总数
ansible-doc yum                 # 看 yum 模块用法
ansible-doc -s copy             # 精简版（参数列表）
```

```text
Ansible 要点：
- 无 agent，SSH 推送，目标机零部署
- 一切用 YAML 描述，可读性强、可版本化
- 模块化：几百个内置模块，覆盖装包/文件/服务/用户/网络
- 幂等：模块设计保证「重复执行 = 一次执行」的效果
```

### inventory（主机清单）

inventory 定义「管理哪些机器、怎么分组」，是 Ansible 的「花名册」。默认文件 `/etc/ansible/hosts`，也可用 `-i` 指定自定义文件。支持分组（group）、组变量、主机变量、嵌套组、动态 inventory（从云厂商 API 拉主机列表）。

```ini
# inventory.ini —— 主机清单
[web]                          # 组名
web1.example.com               # 组内主机
web2.example.com ansible_host=10.0.0.12 ansible_user=deploy   # 主机变量

[db]
db1.example.com
db2.example.com

[app:children]                 # 嵌套组：app 组包含 web 和 db
web
db

[all:vars]                     # 组变量（对所有主机生效）
ansible_ssh_private_key_file=/home/deploy/.ssh/id_rsa
```

```shell
# 用 inventory 做操作
ansible-inventory -i inventory.ini --list          # 解析 inventory 成 JSON 看结构
ansible-inventory -i inventory.ini --graph         # 树状查看分组
ansible -i inventory.ini all -m ping               # 对所有主机 ping（连通性测试）
ansible -i inventory.ini web -m ping               # 只对 web 组
ansible -i inventory.ini 'web:&db' -m ping         # web 和 db 交集（复杂模式）
```

```yaml
# inventory 也支持 YAML 格式（等价）
all:
  children:
    web:
      hosts:
        web1.example.com:
        web2.example.com:
    db:
      hosts:
        db1.example.com:
```

```text
inventory 要点：
- 分组（[]）是核心，按角色分 web/db/app
- 变量优先级：主机变量 > 组变量 > all 变量（越具体越优先）
- ansible_host 指定真实 IP，ansible_user 指定连接用户
- 动态 inventory 可对接 AWS/GCP/阿里云 API 自动发现主机
```

### module（模块）

模块是 Ansible 执行具体操作的「原子单元」——装包、拷文件、起服务、改配置都是一个个模块。每个模块幂等：`yum` 模块装已装的包会跳过，`copy` 模块拷一样的文件会跳过。用 `ansible` 命令可以临时（ad-hoc）调用单个模块，这是快速排查和一次性操作的首选。

```shell
# ad-hoc：临时调用单个模块（不用写 playbook）
ansible web -i inventory.ini -m ping                      # ping 模块：连通性
ansible web -i inventory.ini -m command -a "uptime"       # command：执行命令
ansible web -i inventory.ini -m yum -a "name=nginx state=present"   # 装 nginx
ansible web -i inventory.ini -m service -a "name=nginx state=started enabled=yes"  # 起服务
ansible web -i inventory.ini -m copy -a "src=nginx.conf dest=/etc/nginx/nginx.conf"  # 拷文件
ansible web -i inventory.ini -m user -a "name=deploy group=deploy state=present"   # 建用户
ansible web -i inventory.ini -m setup                    # 采集目标机信息（facts）
```

```text
常用模块分类：
命令执行    command（默认，无 shell 特性）/ shell（支持管道重定向）/ raw（最低层）
包管理      yum / apt / dnf / pip
文件        copy / template / file / lineinfile / fetch / get_url
服务        service / systemd
用户权限    user / group / authorized_key（免密登录）
系统信息    setup / hostname / cron
网络        uri / git / docker_container
```

```text
模块要点：
- 幂等设计：state=present/absent 描述期望状态，已满足就跳过
- command 模块不经过 shell（不支持管道），要管道用 shell 模块
- setup 模块自动采集 facts（主机名/IP/CPU/OS），playbook 里可引用
- 几百个模块记不住？ansible-doc -l 随时查
```

### playbook（剧本）

playbook 是 YAML 写的「任务编排清单」，把多个模块按顺序组织起来，描述一整台机器的目标状态。一个 playbook 可含多个 play，每个 play 针对一组主机执行一系列 task，task 之间可加 handlers（变更触发）、变量、模板、条件。playbook 是 Ansible 的核心，ad-hoc 只适合一次性操作，批量配置一定用 playbook。

```yaml
# site.yml —— 安装并启动 nginx 的 playbook
---
- name: 部署 Web 服务器          # play 名称
  hosts: web                    # 作用于 web 组
  become: yes                   # 提权（sudo）
  vars:                         # play 级变量
    nginx_port: 80

  tasks:                        # 任务列表（顺序执行）
    - name: 安装 nginx
      yum:                      # 用 yum 模块
        name: nginx
        state: present

    - name: 拷贝站点配置
      template:                 # 模板模块（可带变量渲染）
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: restart nginx     # 变更了触发 handler

    - name: 启动并开机自启 nginx
      service:
        name: nginx
        state: started
        enabled: yes

  handlers:                     # 处理器：被 notify 触发才执行
    - name: restart nginx
      service:
        name: nginx
        state: restarted
```

```shell
# 跑 playbook
ansible-playbook -i inventory.ini site.yml         # 执行
ansible-playbook -i inventory.ini site.yml --check # 干跑（不实际改，看会做什么）
ansible-playbook -i inventory.ini site.yml --list-tasks   # 列出任务不执行
ansible-playbook -i inventory.ini site.yml -v      # 加详细输出（-vvv 更详细）
ansible-playbook -i inventory.ini site.yml --limit web1  # 只跑 web1
```

```text
playbook 要点：
- play（对哪组主机）→ tasks（做什么，顺序执行）
- vars 定义变量，template 渲染配置，handlers 变更才触发
- become: yes 提权执行（对应 sudo）
- --check 干跑、--limit 限定主机、-v 看细节
- 幂等：重复执行，已满足的任务显示 ok/跳过，不重复改
```

### role（角色）

role 是把「任务、模板、变量、处理器」打包成可复用单元的组织方式。当 playbook 越写越长、多套环境（web/db/监控）要复用，就把它们拆成 role。role 有固定的目录结构，`ansible-galaxy` 可以创建、下载、分享 role（类似包管理器）。

```text
role 目录结构（标准约定）：
roles/
└── nginx/                  # 角色名
    ├── tasks/main.yml      # 主任务（入口，必填）
    ├── handlers/main.yml   # 处理器
    ├── templates/          # Jinja2 模板
    ├── files/              # 静态文件
    ├── vars/main.yml       # 变量（高优先级，一般不覆盖）
    ├── defaults/main.yml   # 默认变量（低优先级，可被覆盖）
    └── meta/main.yml       # 角色元信息（依赖、作者）
```

```shell
# 创建 role 骨架
ansible-galaxy init roles/nginx
# 示例输出：
# - Role roles/nginx was created successfully

# 从社区下载 role（Ansible Galaxy）
ansible-galaxy install geerlingguy.nginx     # 下载 nginx 角色
ansible-galaxy list                          # 列出已装角色
```

```yaml
# 使用 role 的 playbook（清爽，逻辑全在 role 里）
---
- name: 部署 Web 集群
  hosts: web
  become: yes
  roles:
    - nginx                  # 应用 nginx 角色
    - { role: monitoring, tags: ['monitor'] }   # 带参数的 role
```

```text
role 要点：
- 复用：一份 role 多处用，多环境/多项目共享
- 目录结构是强约定（tasks/templates/vars/defaults/handlers）
- defaults 放可覆盖的默认值，vars 放不该被覆盖的固定值
- ansible-galaxy 管理 role 的创建/下载/分享
```

## 工作原理

Ansible 无 agent 架构的执行流程：

```text
一次 ansible-playbook 的执行过程：
1. 解析 inventory，确定目标主机列表和变量
2. 解析 playbook，把 YAML 转成内部任务队列
3. 对每台目标机，SSH 建立连接（免密/密码）
4. 把当前 task 的模块代码打包，通过 SFTP 传到目标机的临时目录
5. 目标机本地执行模块（用目标机自己的 Python），返回 JSON 结果
6. 控制机回收结果，判断 ok/changed/failed，继续下一个 task
7. 全部 task 跑完，汇总输出（ok=成功没变 / changed=成功有变更 / failed=失败）
```

关键机制——**幂等**：每个模块执行前先检查目标状态是否已符合（装 nginx 前先看装没装，拷文件前先比内容），已符合就返回 ok 不动作，不符合才执行并返回 changed。所以「重复执行 playbook」是安全的，这也是配置管理区别于「脚本一把梭」的本质。

```text
Ansible 没有 agent 的原因和代价：
- 原因：零部署，目标机不用装东西，SSH 是现成的
- 代价：每台机器每次任务都要重新建 SSH 连接 + 传模块，比常驻 agent 慢
- 缓解：开启 SSH 长连接复用（ControlPersist）、pipelining、加大并发 forks
```

```text
执行结果状态：
ok       任务执行成功且系统本来就是这个状态（没变更）
changed  任务执行成功且改了系统（有变更）
failed   任务执行失败（playbook 默认中断）
skipped  条件不满足被跳过
```

## 常用命令与配置

```shell
# 核心命令
ansible <pattern> -m <module> -a "<args>"    # ad-hoc 单模块操作
ansible-playbook <playbook.yml>              # 跑 playbook
ansible-inventory --list                     # 解析 inventory
ansible-doc <module>                         # 查模块文档
ansible-vault encrypt/decrypt <file>         # 加密/解密敏感文件
ansible-galaxy init/install <role>           # 角色管理
ansible-config list                          # 看所有配置项

# ad-hoc 常用组合
ansible all -i inv.ini -m ping                       # 连通性
ansible web -i inv.ini -m command -a "df -h"         # 看磁盘
ansible web -i inv.ini -m yum -a "name=htop state=present"   # 批量装
ansible web -i inv.ini -m setup -a "filter=ansible_os_family"  # 采集 facts
ansible web -i inv.ini -m shell -a "ps aux | grep nginx | wc -l"  # shell 管道

# playbook 常用参数
ansible-playbook site.yml --check --diff      # 干跑 + 看 diff
ansible-playbook site.yml --tags nginx        # 只跑带 nginx 标签的任务
ansible-playbook site.yml --skip-tags reboot  # 跳过某些标签
ansible-playbook site.yml --limit web1        # 限定主机
ansible-playbook site.yml -f 20               # 并发 20 台（默认 5）
```

```text
命令要点：
- ad-hoc 用 -m 指定模块、-a 传参数，适合一次性/排错
- playbook 才是批量配置主力，--check 干跑是上线前必做
- --tags/--skip-tags 精准控制执行范围
- -f 并发数，机器多了调大加速
```

## 配置文件解析

### ansible.cfg（Ansible 自身配置）

```ini
# ansible.cfg
[defaults]
inventory = inventory.ini        # 默认 inventory 文件
forks = 20                       # 并发执行的主机数（默认 5）
host_key_checking = False        # 关闭首次连接 SSH 指纹确认（内网可关）
remote_user = deploy             # 默认连接用户
become = True                    # 默认提权
become_method = sudo             # 提权方式
gathering = smart                # facts 采集策略

[privilege_escalation]
become_user = root               # 提权到 root

[ssh_connection]
pipelining = True                # 减少 SSH 连接开销（加速）
control_path = %(directory)s/%%h-%%r   # SSH 长连接复用（加速）
```

```text
ansible.cfg 查找顺序（后加载覆盖先加载）：
1. 环境变量 ANSIBLE_CONFIG 指定的文件
2. 当前目录 ./ansible.cfg
3. 用户目录 ~/.ansible.cfg
4. 系统默认 /etc/ansible/ansible.cfg
```

### playbook YAML 结构解析

```yaml
---
- name: play 名称
  hosts: web                    # 目标组（或 all）
  become: yes                   # 是否提权
  gather_facts: yes             # 是否采集 facts
  vars:                         # 变量
    app_port: 8080
  vars_files:                   # 变量文件
    - vars/secret.yml
  tasks:
    - name: 任务名
      module_name:              # 模块名
        param1: value1          # 模块参数
      when: ansible_os_family == "RedHat"   # 条件
      tags: [deploy]            # 标签
      notify: restart app       # 触发 handler
  handlers:
    - name: restart app
      service: name=app state=restarted
```

```text
YAML 要点：
- 缩进严格（空格，不用 Tab），层级错 = 语法错
- --- 分隔文档，tasks 是核心列表
- 变量用 {{ var }}，模板文件用 .j2 后缀（Jinja2 语法）
- when 条件、tags 标签、notify 触发是三大控制机制
```

## 应用场景实战

### 场景一：批量初始化一批 Web 服务器

给 10 台新服务器统一装 nginx、拷配置、开防火墙、建部署用户，一个 playbook 搞定：

```yaml
# init-web.yml
---
- name: 初始化 Web 服务器
  hosts: web
  become: yes
  vars:
    deploy_user: deploy

  tasks:
    - name: 安装基础软件包
      yum:
        name: "{{ item }}"
        state: present
      loop:                       # 循环装多个包
        - nginx
        - git
        - htop

    - name: 创建部署用户并加 sudo
      user:
        name: "{{ deploy_user }}"
        groups: wheel
        state: present

    - name: 配置部署用户免密登录
      authorized_key:
        user: "{{ deploy_user }}"
        state: present
        key: "{{ lookup('file', '~/.ssh/id_rsa.pub') }}"

    - name: 拷贝 nginx 配置
      template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: reload nginx

    - name: 开放 80/443 端口
      firewalld:
        service: "{{ item }}"
        permanent: yes
        state: enabled
      loop:
        - http
        - https

    - name: 启动 nginx 并开机自启
      service:
        name: nginx
        state: started
        enabled: yes

  handlers:
    - name: reload nginx
      service:
        name: nginx
        state: reloaded
```

```shell
# 上线前干跑验证
ansible-playbook -i inventory.ini init-web.yml --check --diff
# 正式执行
ansible-playbook -i inventory.ini init-web.yml
# 示例输出：
# PLAY RECAP ************************
# web1.example.com : ok=7  changed=6  unreachable=0  failed=0
# web2.example.com : ok=7  changed=6  unreachable=0  failed=0
```

### 场景二：滚动更新应用（用 role + 模板 + handlers）

把应用部署封装成 role，配置文件用模板渲染（端口、环境可参数化），配置变了自动重启：

```yaml
# roles/myapp/tasks/main.yml
---
- name: 上传应用包
  copy:
    src: myapp.jar
    dest: /opt/myapp/myapp.jar
  notify: restart myapp

- name: 渲染配置文件
  template:
    src: application.yml.j2
    dest: /opt/myapp/application.yml
  notify: restart myapp

- name: 启动应用服务
  systemd:
    name: myapp
    state: started
    enabled: yes
```

```yaml
# roles/myapp/handlers/main.yml
---
- name: restart myapp
  systemd:
    name: myapp
    state: restarted
```

```yaml
# roles/myapp/templates/application.yml.j2 —— Jinja2 模板
server:
  port: {{ app_port }}
spring:
  datasource:
    url: jdbc:mysql://{{ db_host }}:3306/app
    username: {{ db_user }}
```

```yaml
# deploy.yml —— 用 role 的 playbook，变量可覆盖
---
- name: 部署应用
  hosts: app
  become: yes
  roles:
    - myapp
  vars:
    app_port: 8080
    db_host: 10.0.0.20
    db_user: appuser
```

```shell
# 执行：改配置（template 变化）→ 触发 handler 重启 → 滚动生效
ansible-playbook -i inventory.ini deploy.yml
```

```text
场景二体现的三件事：
1. role 复用：myapp 角色可以在 test/prod 多环境复用
2. 模板渲染：同一份模板 + 不同变量 = 不同环境的配置
3. handlers：配置变了才重启，没变不重启（幂等 + 减少无效重启）
```

## 性能与调优

```text
1. 加大并发 forks —— 默认 5 台并行，几十上百台机器时调大（forks=50）
2. SSH 长连接复用 —— control_path + ControlPersist，避免每任务重复建连
3. 开启 pipelining —— 减少 SSH 连接次数，显著加速（对大部分模块生效）
4. facts 采集策略 —— 不需要 facts 时 gather_facts: no，或 gathering=smart 缓存
5. 关闭 host_key_checking —— 内网批量首连免指纹确认（公网谨慎）
6. 用 Mitogen 插件 —— 第三方加速插件，能提速数倍（可选）
```

```ini
# 性能相关配置（ansible.cfg）
[defaults]
forks = 50
gathering = smart
host_key_checking = False

[ssh_connection]
pipelining = True
control_path = %(directory)s/%%h-%%r
control_persist = 60s
```

```text
性能要点：
- 瓶颈通常是 SSH 建连开销，不是执行本身
- pipelining + 长连接复用是性价比最高的两个开关
- 机器多先加大 forks，再考虑 Mitogen
- 幂等性保证「慢但重复跑无害」，别为了快牺牲幂等
```

## 安全与权限

```text
配置管理安全要点：
1. 最小权限 —— 连接用户用普通用户 + become 提权，别直接用 root 免密登录
2. 密钥管理 —— 敏感变量（密码/密钥）用 ansible-vault 加密，别明文进 git
3. 免密登录 —— 用 authorized_key 公钥认证，禁密码认证（禁 root 密码登录）
4. inventory 里的凭据 —— ansible_ssh_pass 别写明文，用 vault 或 SSH agent
5. 审计 —— playbook 版本化（git），谁改了什么可追溯
```

```shell
# ansible-vault 加密/解密敏感文件
ansible-vault encrypt vars/secrets.yml      # 加密（会提示输入密码）
ansible-vault edit vars/secrets.yml         # 编辑（解密后打开）
ansible-vault decrypt vars/secrets.yml      # 解密
# 跑带加密文件的 playbook
ansible-playbook site.yml --ask-vault-pass  # 运行时输入 vault 密码
```

```yaml
# 加密后的 secrets.yml（内容不可读）
# $ANSIBLE_VAULT;1.1;AES256
# 66386439653236336462626566653063336164663966303231363934653561363964363833313662...
```

```text
安全要点：
- ansible-vault 用 AES256 加密，密码走 --ask-vault-pass 或 vault 密码文件
- 别把 vault 密码文件提交到 git
- 目标机上的临时文件（模块执行）Ansible 会自动清理
- 内网可关 host_key_checking，公网务必保留防中间人
```

## 故障排查

```shell
# 1. 连接失败（unreachable）
ansible web -i inv.ini -m ping -vvv       # -vvv 看 SSH 详细握手过程
# 常见：SSH 不通/端口、用户不对、密钥不对、指纹确认卡住

# 2. 模块执行失败（failed）
ansible-playbook site.yml -v              # 看具体哪个 task 失败、报什么错

# 3. 语法检查（playbook 写错了）
ansible-playbook site.yml --syntax-check  # 只查语法不执行

# 4. 干跑看会做什么
ansible-playbook site.yml --check --diff  # 不实际改，看 diff

# 5. inventory 解析对不对
ansible-inventory -i inv.ini --list       # 看解析出的主机/变量
```

### 常见故障定位

```text
unreachable      连不上：SSH 不通、用户/密钥错、host_key 确认卡住
failed           任务失败：模块参数错、目标机缺依赖（如缺 Python）、权限不够
changed 但结果不对：变量渲染错、模板语法错，--check --diff 看差异
"using a SSH password instead of a key"：提示用密码，说明没配免密
```

## 常见问题

```text
Q1: Ansible 和 Puppet/Chef/SaltStack 有什么区别？
A: Ansible 无 agent（SSH 直连，目标机零部署）、YAML 简单；Puppet/Chef 要装 agent、有自己的 DSL；SaltStack 要装 minion、快但部署重。Ansible 胜在零部署 + 上手快，适合中小规模快速自动化。

Q2: 什么是幂等？为什么重要？
A: 幂等指「重复执行结果一致」——已装好的包不会再装、已就绪的服务不会再起。幂等保证重复跑 playbook 安全，也保证「目标状态收敛」，这是配置管理和「脚本一把梭」的本质区别。

Q3: command 和 shell 模块有什么区别？
A: command 不经过 shell（不支持管道/重定向/变量展开，更安全更快），shell 经过 shell（支持管道等）。能用 command 就别用 shell，shell 有注入风险且破坏幂等性判断。

Q4: handlers 有什么用？什么时候执行？
A: handlers 是被 notify 触发的任务，只有「对应的 task 状态是 changed」时才执行（如配置变了才重启服务）。它把「变更检测」和「副作用动作」解耦，避免每次都重启。

Q5: facts 是什么？有什么作用？
A: facts 是 setup 模块自动采集的目标机信息（主机名/IP/OS/CPU/内存），playbook 里可用 `{{ ansible_os_family }}` 等变量引用，做条件判断（如不同发行版用不同包管理器）。

Q6: become 和 remote_user 是什么关系？
A: remote_user 是 SSH 连接用户（通常普通用户），become 是「连接后提权」（become_user 默认 root）。最佳实践：普通用户连接 + become 提权，避免直接用 root 免密。
```

## 面试题

```text
1. Ansible 为什么叫「无 agent」架构？有什么优缺点？
   答：目标机不装任何 agent，控制机通过 SSH 直连推送模块执行。优点：零部署、上手快、目标机无额外进程；缺点：每次任务都要重建 SSH 连接、传模块，大规模下比常驻 agent 慢（靠长连接复用/pipelining/forks 缓解）。

2. 说一下 Ansible 的核心组件和它们的关系？
   答：inventory（主机清单，管哪些机器）、module（执行单元，装包/文件/服务）、playbook（YAML 任务编排，组织多个模块）、role（可复用的任务/模板/变量集合）。playbook 引用 inventory 里的主机，通过模块执行任务，复杂逻辑封装成 role。

3. 什么是幂等？Ansible 怎么保证幂等？
   答：幂等是重复执行结果一致。Ansible 的模块执行前先检查目标状态（装包前看装没装、拷文件前比内容），已符合就返回 ok 不动作。因此重复跑 playbook 安全，系统收敛到目标状态后不再变化。

4. handlers 和普通 task 有什么区别？
   答：handlers 只在被 notify 且对应 task 状态为 changed 时执行（如配置变了才重启服务）。普通 task 每次 play 都跑。handlers 把「变更检测」和「副作用」解耦，避免无意义重启。

5. role 的目录结构是怎样的？
   答：roles/<name>/ 下分 tasks/main.yml（主任务）、handlers/（处理器）、templates/（Jinja2 模板）、files/（静态文件）、vars/（高优先级变量）、defaults/（低优先级默认变量）、meta/（元信息）。这是强约定，ansible-galaxy init 自动生成。

6. 怎么管理 playbook 里的敏感信息（密码/密钥）？
   答：用 ansible-vault 对含敏感变量的文件 AES256 加密（encrypt/edit/decrypt），执行时 --ask-vault-pass 输入密码，或配 vault 密码文件。明文敏感信息不进 git。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 配置用 playbook + role 组织，别用一堆零散 ad-hoc 命令（不可版本化、不可复用）
2. 上线前必跑 `--check --diff` 干跑，看清楚会改什么再真执行
3. 敏感信息（密码/密钥）用 ansible-vault 加密，别明文写 playbook/inventory
4. 普通用户连接 + become 提权，别直接用 root 免密登录
5. 用 role 复用（多环境共享），变量用模板渲染，配置和代码分离
6. playbook 加 tags，方便按需执行部分任务（如只跑部署不跑监控）
7. 全部版本化（git），playbook 即文档，变更可追溯、可回滚

### 踩坑记录

```text
坑 1：YAML 缩进用了 Tab 报语法错
结论：playbook 报语法错误，看起来内容没写错。
原因：YAML 严格用空格缩进，混入 Tab 会解析失败。
解法：编辑器设置 Tab 转空格，写完先 `ansible-playbook --syntax-check`。

坑 2：command 模块里写管道不生效
结论：`command: ps aux | grep nginx` 执行结果不对，报错或管道被当参数。
原因：command 模块不经过 shell，管道/重定向/变量展开都不支持。
解法：需要 shell 特性（管道等）改用 shell 模块，否则优先 command。

坑 3：改了配置但服务没重启
结论：template 改了配置，但 nginx 还是老配置在跑。
原因：task 里没加 notify 触发 handler，配置变了服务不会自动重启。
解法：给「改配置」的 task 加 notify，配合 handler 在 changed 时重启。

坑 4：password 明文写进 playbook 提交了 git
结论：数据库密码泄露到代码仓库。
原因：为了省事把密码写死，没走 vault 或变量外部化。
解法：敏感值用 ansible-vault 加密的 vars 文件，或从环境变量/外部密钥系统注入。

坑 5：host_key_checking 导致首次连接卡住
结论：批量执行卡在 SSH 首次连接，一直等指纹确认。
原因：目标机指纹不在 known_hosts，SSH 交互式询问「是否信任」。
解法：内网关 host_key_checking=False，或提前把目标机指纹加入 known_hosts。

坑 6：facts 采集太慢拖慢整个 playbook
结论：几百台机器跑 playbook，光采集 facts 就好久。
原因：每台都采集完整 facts，量大时开销明显。
解法：不需要 facts 的 play 设 gather_facts: no，或 gathering=smart 用缓存。

坑 7：变量优先级搞混，改了 group_vars 不生效
结论：改了 group_vars 变量但结果没变，被别的变量覆盖。
原因：变量优先级是 主机变量 > play vars > role vars > role defaults 等，越具体越优先。
解法：理清优先级，用 `ansible -m debug -a "var=xxx"` 打印变量实际值排查。
```
