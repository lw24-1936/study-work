## 概述

配置与密钥管理解决两个问题：应用配置（数据库地址、开关、限流参数等）如何集中管理、动态下发；密钥（数据库密码、API Key、证书私钥）如何安全存储、按需取用、防止泄露。配置中心（Apollo、Nacos、Consul 等）管「非敏感的配置」，Vault 管「敏感的密钥」，变更管理（change management）则是保证「改配置/密钥」这个动作本身可控、可审计、可回滚。三者结合，让配置和密钥从「散落在各机器各文件」变成「集中、版本化、受控」。

```text
配置与密钥管理核心要点：
1. 配置中心：集中存配置，环境隔离（dev/prod）、动态刷新、灰度发布、版本回滚
2. Vault：密钥的集中保险箱，静态/动态密钥、加密存储、按策略授权、租约到期自动失效
3. 变更管理：改配置/密钥走审批 + 审计 + 回滚，避免"谁改了什么不知道"
4. 配置和密钥分开：配置中心管普通配置，敏感值进 Vault，别把密码混进普通配置
```

## 核心概念

### 配置中心

配置中心把散落在各机器 `/etc/xxx.conf`、代码里的配置集中到一处，应用启动/运行时拉取。核心能力：

1. **集中管理**：一个平台管所有应用、所有环境的配置，改一处全网生效。
2. **环境隔离**：dev / staging / prod 各自独立的配置 namespace，互不影响。
3. **动态刷新**：改配置无需重启应用，实时推送到客户端（或客户端定时拉）。
4. **版本与回滚**：每次变更留版本记录，出问题一键回滚到上一版。
5. **灰度发布**：新配置先发给部分实例，验证无问题再全量。

主流实现：**Apollo**（携程开源，Java 生态常用，功能全）、**Nacos**（阿里开源，配置 + 服务发现一体）、**Consul**（HashiCorp，KV + 服务发现）、**etcd**（K8s 底座，强一致 KV）。

```yaml
# 应用侧的配置（以 Nacos 为例，application.yaml）
spring:
  application:
    name: order-service
  cloud:
    nacos:
      config:
        server-addr: 127.0.0.1:8848
        file-extension: yaml
        namespace: prod          # 环境隔离：生产命名空间
        group: ORDER_GROUP
# 应用启动时从 Nacos 拉取 order-service.yaml，改动后可动态刷新
```

```text
配置中心要解决的痛点：
改配置要登录每台机器改文件 + 重启 → 集中改一处、动态生效
配置散落难审计 → 集中留版本、可追溯可回滚
多环境配置易混 → namespace/group 环境隔离
```

### Vault 密钥管理

HashiCorp Vault 是「密钥的保险箱」：所有密钥加密存储（加密后落盘，内存解密），通过**策略（policy）**控制谁、能读哪个路径、能做什么操作。核心特性：

1. **静态密钥（Static Secrets）**：手动写入的密钥（API Key、密码），存在 KV 引擎。
2. **动态密钥（Dynamic Secrets）**：Vault 临时到目标系统（数据库、云厂商）生成短期凭据，租约到期自动失效/吊销。数据库密码不再长期固定，而是「用一次生成一个、几分钟后自动作废」。
3. **加密即服务（Encryption as a Service）**：transit 引擎让应用调 Vault 做加解密，密钥本身永不离开 Vault。
4. **多种认证方式（Auth Methods）**：token、AppRole（机器/应用）、Kubernetes、LDAP 等，应用拿到「短期 token」才能读密钥。

```shell
# 开发模式启动（生产用正式模式，需 unseal）
vault server -dev -dev-root-token-id=root &

# 写一个静态密钥
vault kv put secret/myapp db_password="S3cret!" api_key="ak-123456"

# 读回来
vault kv get secret/myapp

# 启用数据库动态密钥引擎（以 PostgreSQL 为例）
vault secrets enable database
vault write database/config/postgres \
  plugin_name=postgresql-database-plugin \
  allowed_roles="readonly" \
  connection_url="postgresql://{{username}}:{{password}}@127.0.0.1:5432/mydb?sslmode=disable" \
  username="vaultadmin" password="vaultadminpass"

# 定义一个角色（生成短期只读凭据）
vault write database/roles/readonly \
  db_name=postgres \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl="1h" max_ttl="24h"

# 应用申请动态凭据
vault read database/creds/readonly
```

```text
示例输出（vault read database/creds/readonly）：
Key                Value
---                -----
lease_id           database/creds/readonly/AbCdEf...
lease_duration     1h
password           A1b2C3d4e5
username           v-token-readonly-xYz...
# 这个凭据 1 小时后自动被 Vault 吊销
```

### 变更管理

变更管理（Change Management）保证「改配置/密钥/系统」这个动作受控，核心三要素：

1. **审批**：变更前提交申请，说明改什么、为什么、影响面、回滚方案，经审批才执行。
2. **审计**：谁、何时、改了什么，全程留痕，可追溯。
3. **回滚**：任何变更都要有回滚方案，出问题快速恢复。

在配置/密钥场景落地：配置中心留版本记录 + 一键回滚；Vault 每次操作有 audit log；重大变更（生产密钥轮换、配置大改）走变更单 + 灰度 + 观察期。

```text
变更管理流程：
提交变更申请（内容/影响/回滚方案）→ 审批 → 灰度执行 → 观察验证 → 全量或回滚

为什么重要：生产事故一大来源是"配置/密钥乱改"，变更管理把"改"变成可预期、可追溯、可逆的动作
```

## 工作原理

### 配置中心的工作模型

配置中心是「客户端/服务端」结构：

1. **服务端（Server）**：存配置、管理版本、处理变更。配置按 namespace + group + 应用名组织。
2. **客户端（Client）**：应用启动时连服务端拉取配置；运行期通过「长轮询/推送」感知变更，动态刷新内存里的配置。
3. **下发流程**：管理员改配置 → 服务端保存新版本 → 通知客户端 → 客户端拉新值应用（可能需要 @RefreshScope 之类的刷新机制）。

### Vault 的工作模型

Vault 的读写链路围绕「认证 → 授权 → 加密存取」：

1. **认证（Auth）**：客户端用某种方式证明身份（AppRole 的 role_id/secret_id、K8s 的 ServiceAccount），拿到一个短期 token。
2. **授权（Policy）**：Vault 用 policy 判断这个 token 有没有权限读/写请求的路径。policy 是 HCL 写的「路径 → 能力」规则。
3. **加密存取**：写入时用 barrier 密钥加密后落盘；读取时解密返回。动态密钥则 Vault 直接去目标系统生成并跟踪租约。
4. **租约与吊销**：动态密钥有 TTL，到期 Vault 自动调目标系统吊销；也可手动 revoke。

```text
Vault 安全模型：
认证（你是谁）→ 策略授权（你能干什么）→ 加密存储（落盘是密文）
barrier 密钥由 unseal key 保护，Vault 重启后处于 sealed 状态，需 unseal 才能解密
```

## 常用命令与配置

### Vault 常用命令

```shell
# 服务生命周期
vault server -dev                    # 开发模式（内存、免 unseal，勿用于生产）
vault operator init                  # 初始化，输出 unseal key 和 root token
vault operator unseal <key>          # 解封（需要达到 unseal 阈值）
vault status                         # 查看 sealed/是否就绪
vault login <token>                  # 登录拿 token

# KV 密钥
vault kv put secret/myapp key=value  # 写（v1 引擎直接 put）
vault kv get secret/myapp            # 读
vault kv list secret/                # 列路径
vault kv delete secret/myapp         # 删除

# 引擎与认证
vault secrets enable -path=db database   # 启用数据库引擎
vault secrets list                    # 列出引擎
vault auth enable approle             # 启用 AppRole 认证
vault auth list                       # 列出认证方式

# 策略与 token
vault policy write readonly readonly.hcl   # 写策略
vault policy list                     # 列策略
vault token create -policy=readonly  # 生成带策略的 token
vault lease revoke <lease_id>        # 手动吊销租约
vault audit enable file file_path=/var/log/vault-audit.log   # 开审计
```

### 配置中心（Apollo/Nacos）常见操作

```shell
# Nacos 通过 Open API 操作配置
curl -X POST "http://127.0.0.1:8848/nacos/v1/cs/configs" \
  -d "dataId=order-service.yaml&group=ORDER_GROUP&content=timeout: 30"

curl "http://127.0.0.1:8848/nacos/v1/cs/configs?dataId=order-service.yaml&group=ORDER_GROUP"
```

```text
Vault 高频：kv put/get 读写密钥，policy 授权，operator unseal 解封
配置中心高频：改配置 → 发布 → 灰度 → 回滚，核心是版本管理
```

## 配置文件解析

### Vault 策略文件（policy.hcl）

```hcl
# readonly.hcl —— 只读策略
path "secret/data/myapp/*" {
  capabilities = ["read", "list"]   # 只允许 read/list
}

path "database/creds/readonly" {
  capabilities = ["read"]            # 允许申请只读数据库凭据
}

# 写策略并绑定
# vault policy write readonly readonly.hcl
# vault token create -policy=readonly
```

```text
policy 是 Vault 授权的核心：path "路径" { capabilities = [...] }
capabilities：create / read / update / delete / list / sudo / deny
默认拒绝（deny by default），只有显式授权的路径可访问
```

### Vault 服务配置（config.hcl）

```hcl
# vault 生产配置示例
storage "raft" {              # 存储后端（raft 内置 HA，或 consul/文件）
  path = "/opt/vault/data"
  node_id = "node1"
}

listener "tcp" {
  address     = "0.0.0.0:8200"
  tls_disable = false          # 生产必须开 TLS
  tls_cert_file = "/etc/vault/tls.crt"
  tls_key_file  = "/etc/vault/tls.key"
}

ui = true                       # 开 Web UI

# 自动解封（生产常用云 KMS 自动 unseal）
seal "awskms" {
  region     = "us-east-1"
  kms_key_id = "xxxx"
}
```

```text
关键配置：
storage     密钥密文存哪（raft 内置 / consul 外置 / 文件）
listener    监听与 TLS（生产必须 HTTPS）
seal        解封方式（手动 unseal key / 云 KMS 自动解封）
ui          是否开 Web 界面
```

## 应用场景实战

### 场景一：应用通过 Vault 动态获取数据库凭据

需求：应用连数据库，但不想把数据库密码写死在配置文件/环境变量里，改用 Vault 动态凭据，密码每小时轮换。

```shell
# 1. 启用数据库引擎 + 配置连接（Vault 用管理员账号连库生成短期凭据）
vault secrets enable database
vault write database/config/myapp \
  plugin_name=postgresql-database-plugin \
  allowed_roles="app-role" \
  connection_url="postgresql://{{username}}:{{password}}@db.internal:5432/appdb?sslmode=disable" \
  username="vault-admin" password="SuperAdminPass"

# 2. 定义角色：生成 1 小时有效、只读业务表的凭据
vault write database/roles/app-role \
  db_name=myapp \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT,INSERT,UPDATE,DELETE ON appdb.public.orders TO \"{{name}}\";" \
  default_ttl="1h" max_ttl="24h"

# 3. 启用 AppRole 认证，给应用发身份
vault auth enable approle
vault write auth/approle/role/myapp-role token_ttl=1h token_max_ttl=4h
vault read auth/approle/role/myapp-role/role-id    # 拿到 role_id
vault write -f auth/approle/role/myapp-role/secret-id   # 拿到 secret_id

# 4. 应用侧流程：用 role_id/secret_id 登录拿 token → 用 token 申请动态凭据
vault write auth/approle/login role_id=<role_id> secret_id=<secret_id>
vault read database/creds/app-role   # 拿到临时 username/password 连库
```

```text
要点：密码不再长期固定，每次申请一个 1 小时有效的临时账号，到期 Vault 自动吊销
应用要集成 Vault 客户端（或 sidecar）自动完成"登录→取凭据→续期/重取"
凭据泄露的爆炸半径被限制在 1 小时内，比写死密码安全得多
```

### 场景二：配置中心灰度发布 + 回滚

需求：某服务的超时参数要从 5s 调到 10s，先在 10% 实例灰度验证，再全量；出问题一键回滚。

```text
以 Apollo 为例的操作流程：
1. 在 Apollo 配置中心改 timeout=10，保存为"未发布"状态
2. 发布时选"灰度发布"，指定 10% 的实例（按 IP 或标签圈定）
3. 观察 10% 实例的监控（超时、错误率），验证无异常
4. 确认后"全量发布"到所有实例
5. 出问题：Apollo 里"回滚"到上一版本，或直接发布回 timeout=5
```

```shell
# 若用 Nacos + 应用侧 @RefreshScope（Spring Cloud）实现动态刷新
# 应用代码：配置类加 @RefreshScope，改配置后调 /actuator/refresh 或自动感知
curl -X POST "http://app:8080/actuator/refresh"
```

```text
灰度发布的核心：新配置只给部分实例，观察无误再全量，把变更风险圈在最小范围
回滚靠版本记录：配置中心每次发布留版本，一键回到上一版
```

## 性能与调优

```text
1. 配置客户端缓存 + 长轮询 —— 客户端本地缓存配置，变更走推送/长轮询，别每次请求都拉服务端
2. Vault 连接复用 —— 应用侧 Vault 客户端保持长连接 + token 缓存续期，别每请求都登录取 token
3. 配置按 namespace/group 拆分 —— 别把所有配置塞一个文件，按服务拆分减少单文件变更影响面
4. Vault 用 raft HA + 负载均衡 —— 多节点 + VIP/负载均衡，读写分流，提高可用性
5. 动态密钥 TTL 权衡 —— TTL 短更安全但续期频繁，TTL 长性能好但泄露窗口大；按敏感度分级
6. 配置热更新范围控制 —— 只对真正需要动态刷新的配置开 refresh，全量热更新会拖慢应用
7. 审计日志异步落盘 —— Vault audit 走异步写，别让审计拖慢密钥读写
```

## 安全与权限

```text
1. 配置与密钥分离 —— 密码/密钥进 Vault，普通配置进配置中心，别把密钥混进配置中心（配置中心通常加密弱）
2. Vault 生产必须 TLS + unseal —— 默认 HTTP 明文，生产 listener 开 TLS；unseal key 分片保管
3. 最小权限策略 —— policy 只授应用需要读的路径，deny by default，别用 root token 跑应用
4. 配置中心权限分级 —— 生产 namespace 的发布权限只给少数人，普通开发者只能改测试环境
5. 审计全开 —— Vault 开 audit log，配置中心开操作日志，谁读了什么密钥、改了什么配置可追溯
6. 密钥定期轮换 —— 静态密钥定期换，动态密钥靠 TTL 自动换；泄露立即 revoke
7. 敏感配置加密 + 脱敏 —— 配置中心里的敏感项（即便不该放这）也要加密，界面展示脱敏
```

## 故障排查

### Vault 无法读取密钥（permission denied）

```shell
# 1. 看当前 token 有没有权限
vault token lookup          # 查看 token 关联的 policy
vault policy read readonly  # 看策略内容，确认是否覆盖目标路径
# 2. 路径对不对（v2 KV 引擎路径带 data/ 前缀）
vault kv list secret/       # 确认路径实际存在
```

### 应用连不上配置中心 / 拿不到配置

```shell
# 1. 网络连通性 + 端口
curl http://127.0.0.1:8848/nacos/v1/cs/configs?dataId=test  # 或对应配置中心健康检查
# 2. namespace/group/dataId 是否匹配（最容易配错）
# 3. 应用侧日志看拉取配置的报错（地址、命名空间不对）
```

### 动态凭据到期应用报数据库连接失败

```shell
# 凭据到期被吊销，应用还在用旧凭据
# 排查：看 vault 的租约状态
vault list sys/leases/lookup/database/creds/app-role
# 解决：应用要支持凭据续期/重取（Vault Agent 自动处理），别用死缓存
```

## 常见问题

```text
Q1: 配置中心和 Vault 有什么区别？都要用吗？
A: 配置中心管「普通非敏感配置」（地址、开关、参数），Vault 管「敏感密钥」（密码、证书、API Key）。两者配合：普通配置进配置中心，密钥进 Vault。小规模也可只用其一，但生产建议分离。

Q2: 静态密钥和动态密钥的区别？
A: 静态密钥是人工写入的固定值（存 KV 引擎）；动态密钥是 Vault 临时到目标系统生成的短期凭据，带 TTL 到期自动吊销。动态密钥更安全（泄露窗口短、无需人工轮换）。

Q3: Vault 的 sealed 状态是什么意思？
A: Vault 重启后是 sealed（密封），内存里的解密密钥丢失、无法读任何数据，需用 unseal key 解封。这是安全设计：防止有人直接拷贝磁盘数据 + 内存 dump 拿到明文。

Q4: 配置改了应用不生效怎么办？
A: 检查应用是否支持动态刷新（@RefreshScope / 监听变更），刷新机制是否触发，客户端缓存是否过期。不支持热更新的配置需要重启应用。

Q5: 动态密钥到期了应用会怎样？
A: 凭据被 Vault 吊销，应用再用旧凭据连库会失败。应用侧要用 Vault Agent/客户端自动续期和重取，而不是缓存死凭据。

Q6: 变更管理为什么重要？
A: 生产事故很多源于"乱改配置/密钥"。变更管理让每次改动都经过审批、留审计、有回滚方案，把"改"从不可控变成可预期可逆。
```

```text
1. 什么是配置中心？解决什么问题？
   答：集中管理应用配置的平台。解决：配置散落各机器难管理、改配置要重启、多环境配置易混、变更难审计难回滚。提供集中管理、环境隔离、动态刷新、版本回滚、灰度发布。

2. Vault 是怎么保证密钥安全的？
   答：三层——加密存储（落盘是密文，barrier 密钥保护，重启 sealed 需 unseal）；认证 + 策略授权（deny by default，最小权限）；动态密钥 + 租约（临时凭据到期自动吊销）。审计日志全程留痕。

3. 静态密钥和动态密钥哪个更安全？为什么？
   答：动态密钥。静态密钥固定、长期有效、泄露后需人工发现并轮换；动态密钥按需生成、TTL 到期自动失效，泄露窗口短、无需人工轮换，且每个实例可用不同凭据。

4. 配置灰度发布怎么实现？
   答：配置中心保存新版本 → 发布时圈定部分实例（按 IP/标签）先下发 → 观察监控指标无异常 → 全量发布。出问题回滚到上一版本。

5. 数据库密码怎么管理最安全？
   答：用 Vault 动态凭据——Vault 用管理员账号临时生成短期只读/读写账号，应用每次申请、TTL 到期自动吊销，密码不再长期写死，泄露影响被限制在 TTL 窗口内。

6. 密钥泄露后怎么应急处置？
   答：立即在 Vault 吊销/轮换该密钥（静态密钥 revoke + 换新，动态密钥直接 revoke 租约）→ 查审计日志定位泄露范围和时间 → 评估受影响系统 → 全量轮换 + 复盘补策略。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 配置与密钥分离：普通配置进配置中心，密钥进 Vault，职责清晰
2. Vault 生产开 TLS + unseal 分片保管 + 最小权限策略 + 全量审计
3. 数据库/云凭据用动态密钥（TTL 短），杜绝长期写死的密码
4. 配置变更走灰度发布 + 版本回滚，重大变更走审批单
5. 应用侧集成 Vault Agent/客户端自动续期，别缓存死凭据
6. 环境严格隔离（namespace/策略），开发只碰测试、生产权限收紧
7. 密钥定期轮换 + 泄露演练，验证吊销和回滚流程真的可用

### 踩坑记录

```text
坑 1：把密钥写进配置中心明文
结论：密码/API Key 以明文存在配置中心，泄露面扩大。
原因：图省事把密钥当普通配置一起下发，配置中心加密能力弱。
解法：密钥进 Vault，配置中心只放非敏感配置；若必须放则加密 + 界面脱敏。

坑 2：生产 Vault 用 -dev 模式跑
结论：数据存内存、免 unseal、无持久化，重启全丢且无安全隔离。
原因：开发模式方便，直接拿上生产。
解法：生产用正式模式（raft/consul 存储 + unseal + TLS + 多节点 HA）。

坑 3：动态密钥 TTL 设太长，等于写死密码
结论：TTL 设 30 天，动态密钥形同静态密钥，泄露窗口巨大。
原因：怕续期麻烦把 TTL 调很大。
解法：按敏感度设合理 TTL（分钟~小时级），应用侧用 Vault Agent 自动续期，别靠拉长 TTL 偷懒。

坑 4：改了配置不生效，排查半天发现没触发刷新
结论：配置中心改了值，应用还是老配置。
原因：应用不支持热更新，或没触发 refresh 机制，客户端缓存没失效。
解法：确认配置是否标注可动态刷新 + 刷新机制是否触发，不支持热更新的配置重启应用。

坑 5：Vault 重启后 sealed，应用全挂
结论：Vault 重启进入 sealed，应用读不到密钥，服务雪崩。
原因：没配自动 unseal（云 KMS），重启后要人工 unseal，半夜无人操作。
解法：生产配云 KMS 自动解封，或 unseal 值班流程 + 高可用减少单点重启。

坑 6：root token 拿来跑应用
结论：应用用 root token，任何路径都能读写，一个应用被攻破 = 全部密钥泄露。
原因：图省事用 root token，没建最小权限策略。
解法：每个应用建独立 AppRole + 最小权限 policy，只授需要的路径，禁止应用用 root token。
```
