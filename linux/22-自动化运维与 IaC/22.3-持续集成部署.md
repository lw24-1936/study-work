## 概述

持续集成（Continuous Integration，CI）指「代码频繁合并到主干，每次合并自动构建 + 测试，尽早发现问题」；持续部署（Continuous Deployment/Delivery，CD）指「通过测试的代码自动发布到环境」。核心价值：把「开发 → 构建 → 测试 → 部署」这条流水线自动化，缩短交付周期、减少手工发布出错。工具层面，Git 是版本控制地基（代码进仓库才有流水线可跑），GitLab CI 与 Jenkins 是两大主流流水线引擎（把流水线写成代码或配置，触发即执行）。

```text
CI/CD 核心要点：
1. CI 持续集成：频繁合入主干 + 自动构建测试，早发现问题（提交即触发）
2. CD 持续部署/交付：测试通过自动发布，一键/零人工上线
3. Git 是地基：分支/合并/标签管理代码版本，流水线围绕 Git 事件触发
4. GitLab CI 与 Jenkins 是流水线引擎：前者内置、配置即 YAML，后者插件生态、Jenkinsfile 即代码
5. 部署流水线 = 阶段化（构建→测试→打包→部署），每阶段可自动/需审批
```

## 核心概念

### Git 版本控制基础

Git 是分布式版本控制系统，每个开发者本地有完整仓库副本，核心对象是「提交（commit）」——一次提交就是一个快照。工作区三态：工作目录（working tree）、暂存区（staging area / index）、本地仓库（repository）。日常流转：改文件 → `git add` 进暂存 → `git commit` 进本地仓库 → `git push` 推到远程。

```shell
# 初始化 / 克隆
git init                          # 新仓库
git clone https://gitlab.com/team/app.git   # 克隆远程

# 日常工作流
git status                        # 看当前状态（改了哪些文件）
git add app.py                    # 加入暂存区（或 git add .）
git commit -m "fix: 修复登录超时" # 提交
git push origin main              # 推到远程 main 分支

# 分支与合并
git branch feature-login          # 建分支
git checkout feature-login        # 切分支（或 git switch）
git checkout -b feature-x         # 建并切换
git merge feature-login           # 合并到当前分支
git branch -d feature-login       # 删分支

# 查看历史
git log --oneline --graph         # 提交历史（图形式）
git diff                          # 看未暂存的改动
git diff HEAD~1                   # 看最近一次提交改了什么
git blame app.py                  # 看每行代码是谁改的
```

```text
分支模型：
Git Flow（main/develop/feature/release/hotfix，重流程，适合版本化发布）
Trunk-based（都在 main 上小步提交 + 特性开关，适合高频发布）
Feature branch（每个特性一个分支，合并前 MR/PR 评审）——最常用
```

### GitLab CI / Jenkins 流水线引擎

- **GitLab CI**：GitLab 内置的 CI/CD，配置写在一个 `.gitlab-ci.yml` 文件（进仓库），由 GitLab Runner（可装在任意机器/Docker）执行。优点：与代码同库、配置即代码、开箱即用、原生 Docker。
- **Jenkins**：独立部署的开源 CI/CD 服务器，靠插件生态支持一切（构建、部署、通知），流水线写 Jenkinsfile（声明式/脚本式）。优点：插件极丰富、灵活、可独立于代码平台；缺点：要自己部署维护、插件多易出兼容问题。

```yaml
# .gitlab-ci.yml 最小示例
stages:          # 定义阶段（顺序执行）
  - build
  - test
  - deploy

build-job:       # 阶段内的 job
  stage: build
  script:
    - echo "编译中..."
    - make build
  artifacts:     # 产物，供后续 job 下载
    paths:
      - bin/

test-job:
  stage: test
  script:
    - make test
  only:
    - main       # 只在 main 分支跑

deploy-job:
  stage: deploy
  script:
    - ./deploy.sh
  environment:
    name: production
```

```text
Job（作业）= 流水线最小执行单元，Runner 拉取后在独立环境跑
Stage（阶段）= 一组 job 的顺序分组，前一个 stage 全成功才进下一个
Pipeline（流水线）= 一次触发产生的完整执行过程
Runner = 实际执行 job 的机器/容器（GitLab Runner 需单独注册）
```

### 部署流水线

部署流水线把「代码提交 → 生产运行」拆成阶段，每阶段是质量关卡。典型阶段：**构建（build）→ 单元测试（test）→ 打包镜像（package）→ 部署测试环境（deploy-staging）→ 部署生产（deploy-prod，需审批）**。发布策略决定「怎么把新版本切到生产」：

```text
三种发布策略：
1. 蓝绿部署（blue-green）—— 备一套全新环境，切流量过去，失败快速切回
2. 金丝雀发布（canary）—— 先放 5% 流量给新版本，观察无问题逐步放大
3. 滚动更新（rolling）—— 逐个替换实例，逐步淘汰旧版本（K8s 默认）

流水线分层：
build → test → package → deploy(staging) → deploy(prod)
前几层自动执行，生产部署常加 manual 审批关卡
```

## 工作原理

CI/CD 的完整闭环是「Git 事件触发 → Runner 拉代码 → 逐阶段执行 → 产物/部署 → 反馈」：

1. **触发**：开发者 push 代码 / 提交 MR，GitLab 收到 Webhook 事件，创建一条 Pipeline。
2. **调度**：GitLab 把 Pipeline 里的 job 按 stage 顺序分发给可用的 Runner；Runner 拉取代码、在隔离环境（Docker）执行 job 的 script。
3. **执行与传递**：每个 job 产出结果，`artifacts`（产物，如编译好的二进制、测试报告）传给后续 job，`cache`（依赖缓存，如 node_modules）加速后续构建。
4. **部署**：deploy 阶段把产物推到目标环境（SSH 上传、docker push、kubectl apply 等），`environment` 记录部署目标、支持回滚。
5. **反馈**：结果（成功/失败）回写到 GitLab 的 MR/提交状态，失败通知相关人员。

Jenkins 同理，只是触发靠 SCM 轮询/Webhook，job 由 Jenkins Master 调度给 Agent 节点执行。

```text
一条流水线的生命周期：
push 代码 → Webhook 触发 Pipeline → Runner 按 stage 执行 job → artifacts/cache 传递 → 部署 → 状态回写 + 通知

失败即停：某 stage 的 job 失败，后续 stage 不执行（除非配 allow_failure）
manual 关卡：deploy-prod 常配 when: manual，需人点确认才进生产
```

## 配置文件解析

### .gitlab-ci.yml 结构

```yaml
# 全局默认
default:
  image: node:20          # 所有 job 默认的 Docker 镜像
  before_script:
    - npm ci              # 每个 job 执行前的公共步骤

stages:                   # 阶段顺序
  - build
  - test
  - deploy

variables:                # 全局变量（可被 job 覆盖）
  APP_VERSION: "1.0.0"

# job 定义
build:
  stage: build
  script:
    - npm run build
  artifacts:
    paths: [dist/]        # 产物，供后面 job 下载
  only: [main, tags]      # 触发条件

test:
  stage: test
  script:
    - npm test
  cache:                  # 依赖缓存，加速
    key: "$CI_COMMIT_REF_SLUG"
    paths: [node_modules/]

deploy:
  stage: deploy
  script:
    - docker build -t app:$APP_VERSION .
    - docker push registry/app:$APP_VERSION
  environment:
    name: production
    url: https://app.example.com
  when: manual            # 手动确认才执行
```

```text
关键字段：
stages        阶段顺序，job 按 stage 分组串行
script        job 要执行的 shell 命令（核心）
image         job 运行的 Docker 镜像（隔离环境）
artifacts     产物（传给后续 job 的文件）
cache         缓存（依赖等，加速但不保证存在）
environment   部署环境（记录目标、支持回滚）
only/rules    触发条件（分支/标签/MR 等）
when: manual  手动关卡（生产部署常用）
```

### Jenkinsfile（声明式流水线）

```groovy
pipeline {
    agent any                        // 任意 agent 节点执行
    environment {
        APP_VERSION = '1.0.0'
    }
    stages {
        stage('Build') {
            steps {
                sh 'npm run build'   // 执行 shell
            }
        }
        stage('Test') {
            steps {
                sh 'npm test'
            }
        }
        stage('Deploy') {
            when { branch 'main' }   // 只在 main 分支
            steps {
                sh './deploy.sh'
            }
        }
    }
    post {
        failure {
            // 失败时通知
            echo '构建失败，发送通知'
        }
    }
}
```

```text
Jenkinsfile 两种风格：声明式（pipeline{}，结构清晰、推荐）与脚本式（node{}，更灵活）
agent 指定在哪执行（any / label / docker），steps 是具体步骤
post 是构建后的钩子（success/failure/always）
```

## 应用场景实战

### 场景一：GitLab CI 构建 Docker 镜像并推送

需求：一个 Go 服务，push 到 main 后自动编译、打 Docker 镜像、推到镜像仓库。

```yaml
# .gitlab-ci.yml
stages:
  - build
  - push

build:
  stage: build
  image: golang:1.22
  script:
    - go build -o app .
  artifacts:
    paths: [app]

docker-build:
  stage: push
  image: docker:24
  services:
    - docker:24-dind          # Docker-in-Docker，让 job 里能用 docker
  script:
    - docker build -t registry.example.com/myapp:$CI_COMMIT_SHORT_SHA .
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD registry.example.com
    - docker push registry.example.com/myapp:$CI_COMMIT_SHORT_SHA
  only:
    - main
```

```text
要点：CI_COMMIT_SHORT_SHA 是内置变量（短提交号），给镜像打唯一版本
docker:dind 让 job 容器内能起 docker daemon 构建镜像
密钥（CI_REGISTRY_USER/PASSWORD）配在 GitLab 的 CI/CD Variables 里，不写进仓库
```

### 场景二：Jenkins 流水线部署到测试环境 + 手动发布生产

需求：Jenkins 监听 Git 仓库，测试环境自动部署，生产部署需人工点确认。

```groovy
// Jenkinsfile
pipeline {
    agent any
    stages {
        stage('构建测试') {
            steps {
                sh 'mvn clean package'
            }
        }
        stage('部署测试环境') {
            steps {
                sh 'scp target/app.jar test-server:/opt/app/ && ssh test-server "systemctl restart app"'
            }
        }
        stage('部署生产') {
            input {                       // 人工确认关卡
                message '确认发布生产？'
                ok '发布'
            }
            steps {
                sh 'scp target/app.jar prod-server:/opt/app/ && ssh prod-server "systemctl restart app"'
            }
        }
    }
    post {
        success { echo '发布完成' }
        failure { echo '流水线失败' }
    }
}
```

```text
input 指令 = 手动关卡，流水线停在这等人点「发布」
生产部署用 SSH 上传 + systemctl 重启（部署方式见 [[10.2-systemd]]）
更规范的做法是打镜像 + K8s 滚动更新，而不是裸 SSH 传 jar
```

## 性能与调优

```text
1. 用 cache 缓存依赖 —— node_modules / .m2 / go mod cache，避免每次重下依赖，构建从分钟级降到秒级
2. artifacts 只传必要产物 —— 别把整个仓库传下去，传编译产物即可，减小传输和存储
3. 并行 job —— 同一 stage 内无依赖的 job 自动并行，拆细（单元测试/集成测试分开跑）
4. Runner 按需扩 —— 任务多时加 Runner（Docker executor 起多个），或上 K8s executor 自动弹性
5. 分层缓存镜像 —— Docker 构建用多阶段 + 缓存层，依赖不变时不重编译
6. 减少无用触发 —— only/rules 限定分支和路径，避免每次 push 全量跑
7. 测试并行/分片 —— 大测试套件按文件分片并行，缩短 test 阶段
```

## 安全与权限

```text
1. 密钥不进仓库 —— 数据库密码、镜像仓库凭据配在 GitLab CI/CD Variables（masked/protected）或 Jenkins 凭据管理，别写进 .gitlab-ci.yml/Jenkinsfile
2. 保护分支 + protected variables —— 生产部署的变量设 protected，只有保护分支（main）能访问，防 MR 里偷密钥
3. Runner 最小权限 —— Runner 跑的是任意代码（MR 可能带恶意脚本），别用 root 高权限账号，Docker executor 隔离
4. 依赖供应链 —— 锁依赖版本，构建时校验依赖来源，防投毒
5. 构建产物签名/扫描 —— 镜像推送前做漏洞扫描（Trivy 等），发布前校验签名
6. 生产部署加审批 + 审计 —— manual 关卡 + 操作日志，谁、何时、部署了什么版本可追溯
7. 密钥轮换 —— CI 变量里的密钥定期轮换，泄露后立即作废（动态密钥见 [[22.4-配置与密钥管理]]）
```

## 故障排查

### Pipeline 卡住 / Runner 不接 job

```shell
# 1. 看 runner 是否在线、有没有 pending job
gitlab-runner list          # runner 机器上查看
gitlab-runner verify        # 校验配置
# 2. 看 runner 日志
journalctl -u gitlab-runner -f
# 3. 确认 runner 的 tag 与 job 的 tags 匹配、runner 是否 enabled 到该项目
```

### 构建失败定位

```shell
# 在 GitLab CI 界面点进失败的 job 看日志，或本地复现
gitlab-runner exec docker build   # 本地用相同镜像模拟执行 job（需装 runner）
# Jenkins：进 job 的 Console Output 看报错栈
```

### 推送镜像 401 / 部署 SSH 拒绝

```shell
# 401：镜像仓库凭据错/过期
docker login registry.example.com -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD
# SSH 拒绝：目标机没加公钥/防火墙拦
ssh -v deploy@test-server   # 看详细握手定位
```

## 常见问题

```text
Q1: CI 和 CD 分别是什么？区别？
A: CI 持续集成 = 频繁合入 + 自动构建测试（保证代码能合、能跑）；CD 持续部署/交付 = 测试通过自动发布（保证能上线）。CI 是 CD 的前提。

Q2: GitLab CI 和 Jenkins 怎么选？
A: 代码托管在 GitLab 且想要开箱即用 → GitLab CI（配置即 YAML，和代码同库）；需要极强灵活性/存量插件生态/独立于代码平台 → Jenkins。两者流水线思想一致。

Q3: artifacts 和 cache 有什么区别？
A: artifacts 是「产物」，会传给后续 job、可下载、进存储（构建结果）；cache 是「缓存」，加速后续构建（依赖包），不保证存在、不跨 pipeline 传递。

Q4: 为什么生产部署要加手动关卡（manual）？
A: 防止代码一合就自动上生产造成事故。手动关卡让人在发布前确认（看变更、看测试结果），是「持续交付（人工触发）」和「持续部署（全自动）」的分界。

Q5: 蓝绿部署和金丝雀发布有什么区别？
A: 蓝绿 = 备一套完整新环境，整体切流量（简单、回滚快，但资源翻倍）；金丝雀 = 新版本先接小比例流量，观察无问题逐步放量（省资源、风险渐进，但需流量控制能力）。

Q6: 流水线失败了怎么快速定位？
A: 看失败 job 的日志（报错栈 + 退出码）→ 本地用相同镜像/环境复现 → 区分是代码问题、依赖问题还是环境/凭据问题。
```

## 面试题

```text
1. 什么是持续集成？它解决什么问题？
   答：频繁把代码合入主干，每次合入自动构建+测试。解决"集成地狱"——多人长期各自开发、最后合并时冲突和 bug 爆发。CI 让问题在合并时就暴露。

2. 一次完整的 CI/CD 流水线包含哪些阶段？
   答：构建（build）→ 测试（test，单元/集成）→ 打包（package，打镜像/产物）→ 部署测试（deploy-staging）→ 部署生产（deploy-prod，加审批）。各阶段顺序执行，前失败后不执行。

3. Git 的暂存区（staging area）是干什么的？
   答：工作区与仓库之间的中间层，git add 把改动放入暂存区、git commit 把暂存区内容提交。作用：选择性提交——一次提交只含想提交的文件/改动，不是全部工作区内容。

4. 蓝绿部署、金丝雀发布、滚动更新三者的区别？
   答：蓝绿=两套环境整体切流量（回滚最快、资源翻倍）；金丝雀=新版本小流量灰度逐步放大（风险渐进、需流量控制）；滚动=逐个替换实例（省资源、回滚慢）。

5. Jenkins 的声明式流水线和脚本式流水线区别？
   答：声明式（pipeline{}）结构固定、易读易维护、有内置 post/when 等；脚本式（node{}）用 Groovy 任意写、灵活但难维护。推荐声明式。

6. 怎么保证 CI/CD 的密钥安全？
   答：密钥不进仓库，放 CI/CD 变量系统（masked + protected，生产变量只保护分支可用）；Runner 用最小权限；动态密钥用 Vault 注入（见 [[22.4-配置与密钥管理]]）；定期轮换。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 流水线配置即代码（.gitlab-ci.yml / Jenkinsfile 进仓库），可评审可回滚
2. 构建产物和依赖用 cache 缓存、artifacts 传递，构建提速
3. 生产部署加 manual 关卡 + 保护分支 + protected 变量，防误发
4. 密钥一律走 CI/CD 变量系统或 Vault，绝不写进仓库
5. 提交信息规范（conventional commits），配合 changelog 自动生成
6. 失败通知 + 结果回写 MR，让开发者第一时间知道构建状态
7. 构建镜像做漏洞扫描 + 版本唯一（commit sha 打 tag），可追溯可回滚

### 踩坑记录

```text
坑 1：密钥写进了 .gitlab-ci.yml 或 Jenkinsfile
结论：密钥泄露进仓库，任何有读权限的人都看得到。
原因：图省事把数据库密码/镜像凭据直接写配置文件。
解法：密钥放 CI/CD Variables（masked + protected）或 Vault 注入，已泄露的立即轮换。

坑 2：cache 和 artifacts 搞混，产物没传给下一步
结论：后续 job 拿不到构建产物，报文件不存在。
原因：把产物配成 cache（cache 不保证传递），或没配 artifacts。
解法：要传给后续 job 的文件用 artifacts，依赖加速才用 cache。

坑 3：Runner 用 root 高权限账号跑 MR 代码
结论：恶意 MR 里的脚本在 Runner 上以 root 执行，主机被入侵。
原因：Runner 执行的是未审代码，却给了过高权限。
解法：Runner 用最小权限 + Docker/K8s 隔离执行，生产 Runner 与普通 Runner 分开。

坑 4：生产部署全自动没加审批，代码一合直接上线
结论：带 bug 的代码自动上生产，造成线上事故。
原因：deploy-prod 没配 when: manual，追求"全自动"丢了安全阀。
解法：生产阶段加手动关卡（manual/input），发布前人工确认变更和测试结果。

坑 5：镜像 tag 用 latest，回滚找不到版本
结论：latest 覆盖后无法定位和回滚到具体版本。
原因：镜像只打 latest 标签，每次推送覆盖。
解法：镜像 tag 用 commit sha / 版本号（$CI_COMMIT_SHORT_SHA），保持唯一可追溯。

坑 6：改了 .gitlab-ci.yml 不生效
结论：推了新配置但流水线行为没变。
原因：YAML 语法错（缩进/引号）导致 job 被跳过，或 only/rules 没匹配到当前分支。
解法：先跑 YAML 校验/CI lint，看 Pipeline 页确认 job 是否真的被创建、触发条件是否命中。
```
