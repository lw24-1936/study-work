## 概述

基础设施即代码（Infrastructure as Code，IaC）指「用代码文件描述、管理和版本化基础设施（服务器、网络、存储、负载均衡等），而不是手工在控制台点击」。核心价值：可版本化（进 Git）、可复用、可审计、可自动化，同一套代码在任何环境跑出相同结果。Terraform 是 HashiCorp 出品的开源 IaC 工具，用声明式的 HCL 语言描述目标状态，通过 Provider 调用各云厂商 API 创建/管理资源，并用 State 文件跟踪「代码定义」与「真实资源」的映射关系。

```text
IaC 核心要点：
1. 基础设施用代码描述，进 Git 版本化，可评审、可回滚、可审计
2. Terraform 声明式（描述"最终状态"），不像 Ansible 命令式（描述"执行步骤"）
3. Provider 对接各云（AWS/阿里云/腾讯云/K8s 等），一套语法管多云
4. State 文件记录真实资源 ID 与配置的映射，是 Terraform 的"账本"
```

## 核心概念

### Terraform 与 HCL

Terraform 是声明式 IaC 工具：你只写「我要什么」（最终状态），Terraform 计算「怎么从现状变到目标」。配置用 HCL（HashiCorp Configuration Language）书写，文件后缀 `.tf`。与 Ansible 的命令式（写「先装包、再改配置、最后起服务」这些步骤）不同，Terraform 描述的是目标，执行顺序由 Terraform 自己根据依赖关系推断。

```shell
# 安装 Terraform（Ubuntu/Debian 示例，走 HashiCorp 官方源）
wget -O- https://apt.releases.hashicorp.com/gpg | sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] https://apt.releases.hashicorp.com $(lsb_release -cs) main" | sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt update && sudo apt install -y terraform

# 验证安装
terraform version
```

```text
示例输出：
Terraform v1.7.5
on linux_amd64
```

### 基础设施定义：Provider / Resource / Data Source

三个核心概念构成「基础设施定义」：

1. **Provider**：对接某个云/平台的插件，负责把 HCL 翻译成目标平台的 API 调用。常见有 `hashicorp/aws`、`aliyun/alicloud`、`hashicorp/azurerm`、`hashicorp/kubernetes`、`hashicorp/docker`。
2. **Resource**：要管理的最小资源单元（一台 ECS、一个 VPC、一条安全组规则）。`resource "类型" "名字" { ... }`。
3. **Data Source**：只读地查询「已存在」的资源，不创建、不管理。典型用途是拿到已有 VPC 的 ID、AMI 的 ID。

```hcl
# 声明 Provider（阿里云示例）
terraform {
  required_providers {
    alicloud = {
      source  = "aliyun/alicloud"
      version = "~> 1.220"
    }
  }
}

provider "alicloud" {
  region = "cn-hangzhou"
}

# Data Source：查询已有的可用区
data "alicloud_zones" "default" {
  available_resource_creation = "VSwitch"
}

# Resource：创建一台 ECS 实例
resource "alicloud_instance" "web" {
  instance_type        = "ecs.c6.large"
  image_id             = "ubuntu_22_04_x64_20G_alibase_20230607.vhd"
  security_groups      = [alicloud_security_group.web.id]
  vswitch_id           = alicloud_vswitch.web.id
  system_disk_category = "cloud_essd"
  system_disk_size     = 40
  host_name            = "web-01"
}

# Resource：创建安全组，开放 22 和 80 端口
resource "alicloud_security_group" "web" {
  name   = "web-sg"
  vpc_id = alicloud_vpc.main.id
}
```

```text
要点：
resource 块 = 要创建/管理的东西（写操作）
data 块 = 只读查询已有资源（读操作），引用方式 data.<类型>.<名字>.<属性>
引用资源属性用 <类型>.<名字>.<属性>，如 alicloud_instance.web.id
```

### 变量、输出与模块

- **Variable**：输入参数，把可变的配置抽出来（区域、实例规格、环境名）。定义用 `variable` 块，赋值用 `.tfvars` 文件或命令行 `-var`。
- **Output**：输出值，apply 后打印出来（如实例公网 IP），也可被其他模块/脚本引用。
- **Module**：把一组资源封装成可复用组件（如「一套 Web 服务 = ECS + 安全组 + 负载均衡」），类似函数。模块有输入（variable）和输出（output）。

```hcl
# variables.tf —— 定义输入
variable "region" {
  type    = string
  default = "cn-hangzhou"
}

variable "instance_count" {
  type    = number
  default = 2
}

# outputs.tf —— 定义输出
output "instance_ips" {
  value = alicloud_instance.web[*].public_ip
}

# main.tf —— 引用变量
resource "alicloud_instance" "web" {
  count         = var.instance_count   # count 实现批量创建
  instance_type = "ecs.c6.large"
  # ...
}
```

```text
运行：terraform plan -var="region=cn-beijing" 或 -var-file=prod.tfvars
变量优先级：命令行 -var > *.auto.tfvars > terraform.tfvars > 变量 default
```

### 状态管理：State / Backend / Lock

State（状态文件）是 Terraform 的账本，记录「代码里定义的资源」与「云端真实资源 ID」的映射。执行 `apply` 时 Terraform 对比 State 与云上实际，算出要创建/更新/删除哪些资源。State 三种关键机制：

1. **State 文件**：默认本地 `terraform.tfstate`（JSON）。含资源 ID、属性、依赖关系、敏感值。
2. **Backend（后端）**：State 存哪。默认 `local`（本地文件）；团队协作要配 `remote` 后端（S3、阿里云 OSS、Consul、Terraform Cloud），让多人共享同一份 State。
3. **Lock（锁）**：防止多人同时 apply 冲突。local 后端无锁，S3 后端配 DynamoDB、阿里云 OSS 后端配表格存储实现锁。

```hcl
# 配置远程后端（S3 + DynamoDB 锁）
terraform {
  backend "s3" {
    bucket         = "my-company-tfstate"      # 存 state 的桶
    key            = "prod/network/terraform.tfstate"  # state 路径
    region         = "us-east-1"
    encrypt        = true                      # 加密存储
    dynamodb_table = "terraform-lock"          # 锁表
  }
}
```

```text
State 的作用：
1. 映射真实资源 ID（resource 名字 ↔ 云端 id）
2. 计算 diff（对比 state 与云上实际，发现 drift 漂移）
3. 存依赖关系和资源属性，供 output / 引用
State 敏感：可能含密钥明文，必须加密 + 不进 Git + 控权限
```

### Workspace 与多环境隔离

Workspace 用「同一份代码 + 不同的 State」隔离环境（dev / staging / prod）。每个 workspace 是独立的一份 state，切换 workspace 即切换 state，实现「一套代码管多环境」。默认 workspace 叫 `default`。更严格的隔离（不同账号/不同权限）建议用「目录结构拆分 + 不同 backend」，workspace 只适合轻量级环境区分。

```shell
# 创建并切换 workspace
terraform workspace new dev      # 创建 dev 环境
terraform workspace list         # 列出所有环境
terraform workspace select prod  # 切换到 prod
# 在代码里用 terraform.workspace 区分环境
```

```hcl
# 用 workspace 名决定实例数量（dev 1 台、prod 3 台）
resource "alicloud_instance" "web" {
  count         = terraform.workspace == "prod" ? 3 : 1
  instance_type = "ecs.c6.large"
  # ...
}
```

## 工作原理

Terraform 执行分三步，核心是「声明式 + 依赖图 + 状态对比」：

1. **terraform init**：初始化工作目录，下载 Provider 插件、初始化 Backend（连 State）。首次使用必须先 init。
2. **terraform plan**：读取配置 → 读取 State → 调用 Provider 查询云上实际资源 → 三者对比，算出「要做什么」（create / update / delete），输出执行计划但不动任何东西。
3. **terraform apply**：按 plan 的计划，通过 Provider 调云 API 实际执行，成功后回写 State。

依赖关系靠「依赖图（DAG）」：Terraform 解析代码里资源之间的引用（如 ECS 引用 `alicloud_security_group.web.id`），构建有向无环图，按拓扑序执行（先建安全组、再建 ECS），无依赖的资源可并行（`-parallelism` 控制并发数）。

```text
声明式工作流：
代码(.tf) + State(现状) + 云上实际 → plan 算差异 → apply 执行 → 回写 State

幂等性：同一份代码 apply 两次，第二次无差异（0 changes）——因为 State 已和目标一致
漂移(drift)：有人手工在控制台改了资源，云上实际 ≠ State，下次 plan 会检测到并尝试拉回
```

## 常用命令与配置

```shell
terraform init              # 初始化：下载 provider、初始化 backend（每次换环境/加 provider 后先跑）
terraform init -upgrade     # 升级 provider 到新版本
terraform plan              # 预览变更（不执行），输出 +create/-destroy/~update
terraform plan -out=tfplan  # 把计划存成文件，apply 时用
terraform apply             # 执行变更（会交互确认 yes）
terraform apply -auto-approve     # 跳过确认直接执行（CI 里常用）
terraform apply tfplan      # 应用已保存的计划文件
terraform destroy           # 销毁所有资源（按 state 反删）
terraform fmt               # 格式化 .tf 代码
terraform fmt -check        # 只检查格式是否规范（CI 里用）
terraform validate          # 校验语法和引用是否正确（不查云）
terraform providers         # 查看当前用到的 provider
terraform output            # 打印所有 output 值
terraform output instance_ips   # 打印指定 output
terraform state list        # 列出 state 里的所有资源
terraform state show alicloud_instance.web   # 查看某资源详情
terraform state mv          # 在 state 内移动/重命名资源（重构用）
terraform state rm          # 从 state 移除（不删真实资源）
terraform import            # 把已有资源导入 state（接管存量）
terraform refresh           # 只刷新 state（拉取云上实际，不改资源）
terraform workspace list/new/select/delete   # workspace 管理
terraform graph             # 输出依赖图（DOT 格式，可视化）
terraform console           # 交互式 REPL，调试表达式/引用
```

```text
最常用的三条：init（初始化）→ plan（预览）→ apply（执行）
改配置后安全流程：fmt → validate → plan → apply
```

## 配置文件解析

一个典型 Terraform 项目目录结构与关键文件：

```text
project/
├── main.tf          # 主配置：provider + resource
├── variables.tf     # 输入变量定义
├── outputs.tf       # 输出定义
├── terraform.tfvars # 变量赋值（dev/prod 各一份）
└── .terraform/      # init 下载的 provider 插件（勿提交）
```

```hcl
# main.tf 完整示例（阿里云 ECS + 安全组）
terraform {
  required_version = ">= 1.5"
  required_providers {
    alicloud = {
      source  = "aliyun/alicloud"
      version = "~> 1.220"
    }
  }
}

provider "alicloud" {
  region = var.region
}

# 安全组：放行 22 与 80
resource "alicloud_security_group" "web" {
  name   = "${var.env}-web-sg"
  vpc_id = var.vpc_id
}

resource "alicloud_security_group_rule" "ssh" {
  type              = "ingress"
  ip_protocol       = "tcp"
  port_range        = "22/22"
  security_group_id = alicloud_security_group.web.id
  cidr_ip           = "0.0.0.0/0"
}

# ECS 实例
resource "alicloud_instance" "web" {
  count           = var.instance_count
  instance_type   = "ecs.c6.large"
  image_id        = var.image_id
  security_groups = [alicloud_security_group.web.id]
  vswitch_id      = var.vswitch_id
  host_name       = "${var.env}-web-${count.index + 1}"

  tags = {
    Name = "${var.env}-web-${count.index + 1}"
    Env  = var.env
  }
}

output "web_public_ips" {
  value = alicloud_instance.web[*].public_ip
}
```

```text
字段含义：
terraform 块    版本约束 + provider 来源 + backend 配置
provider 块     云平台接入（region 等认证之外的配置）
resource 块     要管理的资源（count 批量、tags 标记）
variable        输入（region/env/vpc_id 等），terraform.tfvars 赋值
output          输出（实例 IP 等），apply 后打印、供引用
```

## 应用场景实战

### 场景一：用 Terraform 一键创建云主机 + 安全组

需求：新项目上线，需要 2 台 Web 主机 + 放行 22/80 的安全组。手工要在控制台点十几次，用 Terraform 一条命令搞定。

```hcl
# main.tf
provider "alicloud" {
  region = "cn-hangzhou"
}

resource "alicloud_security_group" "web" {
  name = "web-sg"
}

resource "alicloud_security_group_rule" "allow_web" {
  type              = "ingress"
  ip_protocol       = "tcp"
  port_range        = "80/80"
  security_group_id = alicloud_security_group.web.id
  cidr_ip           = "0.0.0.0/0"
}

resource "alicloud_security_group_rule" "allow_ssh" {
  type              = "ingress"
  ip_protocol       = "tcp"
  port_range        = "22/22"
  security_group_id = alicloud_security_group.web.id
  cidr_ip           = "0.0.0.0/0"
}

resource "alicloud_instance" "web" {
  count           = 2
  instance_type   = "ecs.c6.large"
  image_id        = "ubuntu_22_04_x64_20G_alibase_20230607.vhd"
  security_groups = [alicloud_security_group.web.id]
  host_name       = "web-${count.index + 1}"
}
```

```shell
# 初始化 + 预览 + 执行
terraform init
terraform plan
terraform apply -auto-approve
# 全部建完后查看输出 / 销毁
terraform state list
terraform destroy -auto-approve
```

```text
要点：count = 2 批量建 2 台；count.index 从 0 开始，主机名 web-1/web-2
安全组规则用独立 resource，避免在 security_group 内联规则造成「改规则要重建组」
```

### 场景二：terraform import 接管存量资源 + workspace 多环境

需求：公司已有一批手工建的云主机，想纳入 Terraform 管理（代码化），同时要区分测试/生产环境。

```shell
# 1. 先在代码里写好对应 resource 块，再 import 绑定
terraform import alicloud_instance.web[0] i-bp1xxxxxxxxxxxxx

# 2. import 后 plan 会显示代码与真实资源的差异，逐步对齐直到 0 changes
terraform plan

# 3. workspace 隔离环境
terraform workspace new test
terraform workspace new prod
terraform workspace select prod
terraform apply -var-file=prod.tfvars   # 生产用 prod 变量
```

```text
import 只是把真实资源 ID 写进 state，不会自动生成代码——代码要自己先写好并与之对齐
import 后立即 plan，把代码补到和真实资源一致，否则下次 apply 会误删/误改
workspace 隔离的是 state（环境间互不影响），不隔离权限——真要权限隔离用不同 backend/账号
```

## 性能与调优

```text
1. 并发度 -parallelism —— 默认 10，云 API 限流报错时可调低（如 3），网络好可调高
2. 大项目拆 state —— 一个 state 管几百资源 plan/apply 会慢，按服务/网络拆多个 state（分区）
3. 模块化 —— 复用模块减少重复代码，也减少 plan 计算量
4. 减少不必要的 refresh —— plan 前会全量 refresh，资源多时慢；-refresh=false 跳过（慎用，可能算错 diff）
5. 用 -target 局部操作 —— 只想改某个资源时 terraform apply -target=xxx，跳过全量
6. 远程 state 加锁 —— 本地 state 无锁，多人协作用远程后端避免并发冲突（锁本身也防止重复计算）
7. provider 版本固定 —— 锁住版本，避免升级导致大量无谓 diff
```

## 安全与权限

```text
1. 敏感值不进 state —— state 是明文 JSON，含密钥/密码；用 sensitive 标记 output，远程后端开 encrypt
2. state 文件不进 Git —— .gitignore 加 terraform.tfstate、terraform.tfstate.backup、.terraform/、*.tfvars（含密钥的）
3. Provider 凭据走环境变量 —— 阿里云用 ALICLOUD_ACCESS_KEY/SECRET_KEY，别写进 .tf；AWS 用 AWS_ACCESS_KEY_ID
4. 最小权限 IAM —— 给 Terraform 用的账号只授它需要的权限（能建 ECS 但不删 VPC），别用 root/管理员
5. state 访问权限 —— 远程 state（OSS/S3）单独桶、加密、最小读写权限，state 泄露 = 基础设施泄露
6. 代码评审 + 变更审批 —— apply 前 plan 出 diff 给人审，大变更走审批流（配合 CI 的 plan/apply 分离）
7. tfvars 里的密码 —— 交给 Vault/CI 变量注入，别明文提交仓库（见 [[22.4-配置与密钥管理]]）
```

## 故障排查

### plan/apply 报 state lock 冲突

```shell
# 1. 看是否有人/进程还占着锁
terraform plan   # 报 Error acquiring the state lock
# 2. 等对方释放，或确认无人占用后强制解锁（S3+DynamoDB 后端）
terraform force-unlock <lock_id>
# 3. 阿里云 OSS 后端，锁存在表格存储，用 force-unlock 同样处理
```

```text
锁 ID 从报错信息里拿。force-unlock 危险：只在确认没别人在 apply 时用，否则会造成并发写 state 损坏
```

### plan 与实际资源不一致（drift 漂移）

```shell
# 有人手工改了控制台，state 和云上对不上
terraform refresh          # 拉取云上实际，更新 state
terraform plan             # 再 plan，会显示要把资源拉回代码定义的状态
terraform apply            # 决定：拉回（apply）还是把代码改成实际值
```

### Provider 认证失败

```shell
# 认证相关环境变量没设或过期
export ALICLOUD_ACCESS_KEY="LTAI..."
export ALICLOUD_SECRET_KEY="..."
terraform plan    # 还报错就 terraform validate + 查 provider 文档确认环境变量名
```

## 常见问题

```text
Q1: Terraform 和 Ansible 有什么区别？什么时候用哪个？
A: Terraform 声明式、管基础设施（创建/删除云资源、管 State），Ansible 命令式、管配置（装机、改配置、起服务）。常见组合：Terraform 建机器 → Ansible 配置机器。

Q2: plan 和 apply 有什么区别？能不能跳过 plan？
A: plan 只算差异、不改任何东西（预览）；apply 才真正执行并回写 State。生产必须 plan 先看 diff 再 apply，别 -auto-approve 盲执行。

Q3: terraform.tfstate 为什么要重点保护？
A: State 存了真实资源 ID 和（可能）敏感值，谁拿到 State 谁就知道你全部基础设施布局，且能直接 apply 操纵。必须加密 + 不进 Git + 最小权限。

Q4: 手动在控制台改了资源，Terraform 会怎样？
A: 下次 plan 检测到漂移（drift），State 与云上不一致。Terraform 会尝试把资源拉回代码定义的状态（apply），或你主动把代码改成实际值（承认现状）。

Q5: import 能把资源"变成"代码吗？
A: 不能。import 只是把已有资源 ID 写进 State 建立映射，代码要自己写。import 完必须 plan 对齐，否则下次 apply 会按代码"纠正"资源造成误删。

Q6: 多个环境（dev/prod）怎么做隔离？
A: 轻量用 workspace（同一代码不同 State）；严谨用目录拆分 + 不同 backend/账号（权限、网络都隔离）。生产推荐后者。
```

## 面试题

```text
1. 什么是 IaC？有什么好处？
   答：基础设施用代码描述、版本化、自动化管理。好处：可复用（同一套代码多环境）、可审计（Git 历史）、可回滚、减少手工操作失误、团队协作。

2. Terraform 的 State 是干什么的？为什么重要？
   答：State 记录代码定义与真实资源 ID 的映射，是计算 diff 的依据。重要：它决定了 apply 时创建/更新/删除哪些资源，含敏感信息，损坏或丢失会导致 Terraform 无法正确管理资源（甚至重复创建）。

3. Terraform 声明式和 Ansible 命令式有什么区别？
   答：声明式描述"目标状态"（我要 3 台机器），Terraform 自己算怎么达成；命令式描述"执行步骤"（先装包再改配置）。声明式幂等、更易维护；命令式更直观、适合复杂配置逻辑。

4. State 为什么要加锁（Lock）？
   答：防止多人同时 apply 写坏 State。没有锁时两个 apply 并发读同一 State，后写覆盖先写，导致 State 与实际脱节。远程后端（S3+DynamoDB、OSS+表格存储）提供锁。

5. 漂移（drift）是什么？怎么处理？
   答：云上资源被手工改动，与 State/代码不一致。处理：terraform refresh 更新 State，再决定 apply 拉回（以代码为准）或改代码（承认实际值）。

6. terraform plan 的原理？
   答：读代码 → 读 State → 调 Provider 查询云上实际，三者对比算出 create/update/delete 差异，输出计划不执行。依赖引用关系构建 DAG 决定执行顺序。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 代码进 Git，.gitignore 排除 state 文件、.terraform/ 和含密钥的 tfvars
2. 改配置固定走 fmt → validate → plan → apply 流程，plan 结果入库/给人审
3. State 用远程后端（OSS/S3）+ 加密 + 锁，团队协作必备
4. 环境隔离优先目录拆分 + 不同 backend，workspace 只用于轻量区分
5. Provider 版本锁定（required_providers 里写 ~>），避免升级引入意外 diff
6. 复用模块（Module）封装重复资源组，减少复制粘贴和漂移
7. 敏感值标记 sensitive，凭据走环境变量/Vault 注入，绝不写进 .tf

### 踩坑记录

```text
坑 1：state 文件提交进了 Git
结论：State 泄露到仓库，含资源 ID 和可能的敏感值，安全风险 + 团队互相覆盖。
原因：.gitignore 没排除 terraform.tfstate，误提交。
解法：.gitignore 加 terraform.tfstate*、.terraform/，已提交的从历史清除并换远程后端。

坑 2：terraform import 后直接 apply 把资源删了
结论：import 完没对齐代码，apply 按代码"纠正"资源，导致真实资源被改/删。
原因：import 只建映射不生成代码，代码与真实资源不一致。
解法：import 后立刻 plan，把代码补到与真实资源一致（0 changes）再继续。

坑 3：本地 state 多人同时 apply 互相覆盖
结论：State 被并发写坏，基础设施状态错乱。
原因：local 后端没有锁，两个人在两台机器同时 apply。
解法：换远程后端（S3+DynamoDB / OSS+表格存储）获得锁，或用 Terraform Cloud。

坑 4：改了安全组内联规则导致组重建
结论：把规则写进 security_group 的 ingress 内联块，改一条规则 Terraform 要重建整个组，服务中断。
原因：内联规则是资源属性，改了属性 = 资源要重建。
解法：规则用独立的 security_group_rule 资源定义，改动只增删单条规则。

坑 5：apply 时手滑确认错了环境
结论：误在 prod 执行了破坏性变更（如 destroy）。
原因：workspace/目录切换没确认当前环境，-auto-approve 盲执行。
解法：apply 前看 plan 输出、明确当前 workspace；生产环境去掉 -auto-approve，加审批流程。

坑 6：依赖循环导致 plan 报错
结论：terraform plan 报 cycle 错误，无法构建执行图。
原因：资源 A 引用 B 的属性、B 又引用 A 的属性，形成环。
解法：检查引用关系打断循环，把共同依赖抽成独立资源或 data source。
```
