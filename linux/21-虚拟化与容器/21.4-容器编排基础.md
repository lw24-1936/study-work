## 概述

Kubernetes（K8s）是 Google 开源的容器编排平台，解决的核心问题是「容器多了之后怎么管」——单机 Docker 跑十几个容器还能手动管，上千个容器跨几十台机器时，调度、扩缩容、服务发现、滚动更新、故障自愈都只能交给编排系统。Kubernetes 用声明式 API 描述「期望状态」，控制循环不断把「实际状态」往「期望状态」收敛，这是它和「人肉执行命令」的本质区别。

```text
Kubernetes 核心价值：把「人肉运维」变成「声明式自愈」
- 调度：自动决定容器跑在哪个节点
- 扩缩容：副本数改了自动增删 Pod
- 服务发现：Service 给一组 Pod 一个稳定访问入口
- 滚动更新 / 回滚：Deployment 无中断升级
- 自愈：Pod 挂了自动重启、节点挂了自动迁移
```

## 核心概念

### Kubernetes 概念

Kubernetes 集群分两层：**控制平面（Control Plane）** 和 **数据平面（Worker 节点）**。控制平面负责决策（调度、状态存储、API），数据平面负责真正跑容器（kubelet + 容器运行时）。

```text
控制平面（master）：
- kube-apiserver   唯一入口，所有操作都走它（REST API）
- etcd             集群状态存储（key-value，所有对象都存这里）
- kube-scheduler   决定 Pod 调度到哪个节点
- kube-controller-manager  运行各种控制器（Deployment/ReplicaSet 等）

数据平面（worker 节点）：
- kubelet          节点代理，接收调度、拉镜像、启停容器
- kube-proxy       维护网络规则，实现 Service 的流量转发
- 容器运行时       真正跑容器（containerd/CRI-O，见 21.5）
```

Kubernetes 一切皆对象，所有资源都是 API 对象（Pod、Service、Deployment……），用 YAML/JSON 声明，通过 apiserver 提交。

```yaml
# 声明式：我只说「我要 3 个 nginx 副本」，怎么做到是系统的事
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 3          # 期望副本数
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
```

### Pod

Pod 是 Kubernetes 的**最小调度单元**，一个 Pod 里可以放一个或多个容器。同 Pod 的容器共享网络命名空间（共享 IP 和端口空间）和存储卷，通过 localhost 互相通信。Pod 是「临时、易失」的——它随时会被调度器重建，IP 会变，所以不要直接依赖 Pod IP。

```yaml
# 单容器 Pod（最常见）
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80
```

```yaml
# 多容器 Pod：主容器 + sidecar，共享网络
apiVersion: v1
kind: Pod
metadata:
  name: app-with-sidecar
spec:
  containers:
    - name: app
      image: myapp:1.0
    - name: log-collector        # sidecar 收集日志
      image: filebeat:8.0
```

```shell
# 用命令直接创建 Pod（教学用，生产都用 YAML）
kubectl run nginx-pod --image=nginx:1.25 --port=80
kubectl get pods
kubectl logs nginx-pod
kubectl exec -it nginx-pod -- /bin/sh
kubectl delete pod nginx-pod
```

```text
Pod 要点：
- 最小调度单元，一 Pod 多容器共享网络/存储
- Pod 是临时的，IP 会变，别依赖 Pod IP
- 容器内探针（liveness/readiness）决定 Pod 是否健康
- pause 容器是 Pod 的「根基」，先起它再挂业务容器
```

### Service

Pod 会重建、IP 会变，客户端没法直接连 Pod。Service 解决这个问题：用**标签选择器（selector）** 绑定一组 Pod，给它们一个**稳定的虚拟 IP（ClusterIP）和 DNS 名**，流量通过 Service 自动负载均衡到后端 Pod。Service 是「服务发现 + 负载均衡」的载体。

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc
spec:
  selector:
    app: nginx            # 选择带 app=nginx 标签的 Pod
  ports:
    - port: 80            # Service 对外端口
      targetPort: 80      # 转发到 Pod 的端口
      protocol: TCP
  type: ClusterIP         # 默认：仅集群内可访问
```

Service 四种类型：

```text
ClusterIP    默认，集群内部虚拟 IP，只能集群内访问
NodePort     在每个节点开一个端口（30000-32767），外部可通过 节点IP:端口 访问
LoadBalancer 云厂商提供，自动创建外部负载均衡器（AWS ELB / GCP LB）
ExternalName 把 Service 映射到集群外域名（CNAME）
```

```shell
kubectl get svc                 # 看 Service 和分配的 ClusterIP
kubectl describe svc nginx-svc  # 看 Service 详情（含 Endpoints）
kubectl get endpoints nginx-svc # 看 Service 实际选中的后端 Pod IP
```

```text
Service 要点：
- 用 selector 绑定 Pod，给稳定 IP + DNS 名
- ClusterIP 是虚拟 IP，由 kube-proxy 用 iptables/IPVS 规则实现
- 访问 Service 会自动负载均衡到后端 Pod
- Service 不变，后端 Pod 随便换，这就是服务发现
```

### Deployment

Deployment 是管理无状态应用的控制器，负责维护「期望副本数」。你声明要 3 个副本，Deployment 通过创建 ReplicaSet 来保证实际有 3 个 Pod，少了补、多了删、挂了重启。它还提供**滚动更新**和**回滚**能力——改镜像版本时逐个替换 Pod，全程不中断服务。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deploy
spec:
  replicas: 3                # 期望副本数
  selector:
    matchLabels:
      app: nginx
  template:                  # Pod 模板（Deployment 据此创建 Pod）
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
```

```shell
kubectl apply -f deploy.yaml       # 创建/更新 Deployment
kubectl get deployments            # 看 Deployment 状态（READY/AVAILABLE）
kubectl rollout status deployment/nginx-deploy   # 看滚动更新进度
kubectl set image deployment/nginx-deploy nginx=nginx:1.26  # 更新镜像触发滚动更新
kubectl rollout history deployment/nginx-deploy             # 看历史版本
kubectl rollout undo deployment/nginx-deploy               # 回滚到上一版本
kubectl scale deployment/nginx-deploy --replicas=5         # 扩缩容
```

```text
Deployment 要点：
- 声明式副本管理（期望状态），少了补多了删
- 滚动更新：逐个替换 Pod，全程不中断（可配 maxSurge/maxUnavailable）
- 回滚：rollout undo 一键回退
- 层次：Deployment 管 ReplicaSet，ReplicaSet 管 Pod
```

### kubectl

kubectl 是操作 Kubernetes 的命令行工具，读 `~/.kube/config` 里的集群凭证，把命令转成对 apiserver 的 REST 请求。日常排查、部署、运维全用它。

```shell
# 集群与上下文
kubectl version                          # 客户端/服务端版本
kubectl cluster-info                     # 集群信息
kubectl config current-context           # 当前上下文（连的哪个集群）
kubectl get nodes                        # 看节点状态

# 资源查看（get/describe）
kubectl get pods -A                      # 所有命名空间的 Pod
kubectl get pods -o wide                 # 更多列（IP、节点）
kubectl get all                          # 常见资源一览
kubectl describe pod nginx-deploy-xxx    # 详情（事件、状态）

# 增删改（apply/delete/edit）
kubectl apply -f deploy.yaml             # 声明式创建/更新
kubectl delete -f deploy.yaml            # 删除
kubectl edit deployment/nginx-deploy     # 直接编辑在线对象

# 调试
kubectl logs -f nginx-deploy-xxx         # 跟踪日志
kubectl exec -it nginx-deploy-xxx -- /bin/sh   # 进容器
kubectl get events --sort-by=.metadata.creationTimestamp   # 看集群事件

# 输出格式
kubectl get pods -o yaml                 # 完整 YAML
kubectl get pods -o jsonpath='{.items[*].metadata.name}'   # jsonpath 提取字段
```

```text
kubectl 要点：
- 所有命令走 apiserver，kubeconfig 决定连哪个集群
- get 看现状，describe 看详情和事件，apply 声明式变更
- -o wide/yaml/json/jsonpath 控制输出
- 加 -n <namespace> 指定命名空间，-A 查全部
```

## 工作原理

Kubernetes 的核心是**控制循环（reconciliation loop，也叫 reconcile 循环）**，配合**声明式 API**：

1. **声明期望状态**：用户通过 `kubectl apply` 提交 YAML，apiserver 把对象存进 etcd。
2. **控制器监听变化**：每个控制器（Deployment 控制器、ReplicaSet 控制器）watch apiserver，发现自己负责的对象「实际状态 ≠ 期望状态」。
3. **执行调和动作**：控制器调用 apiserver 创建/修改/删除资源，让实际状态往期望状态收敛。

整个过程是**幂等**的——控制器反复跑，最终一定收敛到期望状态；中途出错（节点挂了）也没关系，下个循环继续补。

```text
一次「kubectl apply deploy.yaml（replicas=3）」的完整流程：
1. kubectl 把 YAML 转成 JSON，POST 到 apiserver
2. apiserver 校验（RBAC 权限、字段合法性）后写入 etcd
3. Deployment 控制器 watch 到新 Deployment，创建 ReplicaSet
4. ReplicaSet 控制器 watch 到 ReplicaSet，创建 3 个 Pod（此刻 Pod 无节点、Pending）
5. kube-scheduler 看哪些 Pod 没调度，选节点后把 nodeName 写回 Pod
6. 目标节点 kubelet 发现分配给自己的 Pod，拉镜像、调 CRI 起容器
7. kubelet 上报容器状态，Pod 变 Running，ReplicaSet/Deployment 状态同步
```

关键点：调度器和控制器都只是「观察者」，不断读 apiserver、写回决策，没有谁「命令」谁，系统靠状态收敛而非指令传递运行——这就是声明式模型的精髓。

```text
声明式 vs 命令式：
命令式（Docker 风格）：docker run / docker stop，你告诉系统「每一步做什么」
声明式（K8s 风格）：apply YAML，你告诉系统「我要什么状态」，系统自己算怎么做
声明式的好处：幂等、可重复、可审计（YAML 即文档），自动化友好
```

## 配置文件解析

以一个完整的 Deployment + Service YAML 为例，逐字段解析：

```yaml
apiVersion: apps/v1          # API 组/版本，决定对象属于哪个 API
kind: Deployment             # 资源类型
metadata:                    # 元数据：名字、命名空间、标签、注解
  name: nginx-deploy         # 名字（同命名空间内唯一）
  namespace: default         # 命名空间
  labels:                    # 标签：用于选择器匹配（key=value）
    app: nginx
spec:                        # 规格：期望状态（各资源差异最大的部分）
  replicas: 3                # Deployment：期望副本数
  selector:                  # 选择器：匹配哪些 Pod 归它管
    matchLabels:
      app: nginx
  strategy:                  # 更新策略
    type: RollingUpdate      # 滚动更新
    rollingUpdate:
      maxUnavailable: 1      # 更新时最多几个 Pod 不可用
      maxSurge: 1            # 更新时最多多出几个 Pod
  template:                  # Pod 模板
    metadata:
      labels:
        app: nginx           # Pod 的标签，必须被 selector 匹配
    spec:
      containers:            # 容器列表
        - name: nginx
          image: nginx:1.25  # 镜像（仓库/名:标签）
          ports:
            - containerPort: 80
          resources:         # 资源请求与上限
            requests:
              cpu: 100m      # 100m = 0.1 核
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
          env:               # 环境变量
            - name: TZ
              value: Asia/Shanghai
          readinessProbe:    # 就绪探针：通过了才接流量
            httpGet:
              path: /
              port: 80
          livenessProbe:     # 存活探针：失败就重启容器
            httpGet:
              path: /healthz
              port: 80
```

```yaml
# 配套 Service
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc
spec:
  selector:
    app: nginx               # 必须匹配上面 Pod 的标签
  ports:
    - port: 80
      targetPort: 80
  type: ClusterIP
```

```text
字段要点：
apiVersion + kind   决定这是什么资源（v1/apps/v1/batch/v1...）
metadata.name       唯一标识，selector/labels 是「绑定的绳子」
spec                期望状态，Deployment 的 spec 核心是 replicas/selector/template
requests/limits     资源请求（调度依据）与上限（超了被 OOMKill/限流）
probe               存活探针（重启）vs 就绪探针（摘流量）
```

## 应用场景实战

### 场景一：部署一个 Web 应用到集群（Deployment + Service 完整流程）

从零部署一个 Nginx，集群内可访问，外部通过 NodePort 访问：

```yaml
# 1. 保存为 web.yaml，一个文件两个对象（用 --- 分隔）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  selector:
    app: web
  type: NodePort          # 每个节点开端口，外部可访问
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080     # 指定节点端口（30000-32767）
```

```shell
# 2. 部署
kubectl apply -f web.yaml
# 输出（示例）：
# deployment.apps/web created
# service/web-svc created

# 3. 验证 Deployment 副本数
kubectl get deploy web
# 示例输出：
# NAME   READY   UP-TO-DATE   AVAILABLE   AGE
# web    3/3     3            3           20s

# 4. 验证 Service 和 Pod
kubectl get svc web-svc
# 示例输出：
# NAME      TYPE       CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
# web-svc   NodePort   10.96.100.50    <none>        80:30080/TCP   30s

kubectl get pods -l app=web -o wide
# 示例输出（3 个 Pod 分布在不同节点）：
# NAME                  READY   STATUS    IP            NODE
# web-7c9f8b5d4-abc12   1/1     Running   10.244.1.5    node1
# web-7c9f8b5d4-def34   1/1     Running   10.244.2.8    node2
# web-7c9f8b5d4-ghi56   1/1     Running   10.244.1.9    node1

# 5. 集群内访问（curl 任意节点 30080 端口，或集群内 curl ClusterIP）
curl http://10.96.100.50
# 6. 外部访问：浏览器打开 http://<任意节点IP>:30080
```

### 场景二：滚动升级 + 一键回滚

应用要发新版本，全程不中断服务，出问题能立刻回退：

```shell
# 1. 更新镜像版本（触发滚动更新）
kubectl set image deployment/web nginx=nginx:1.26

# 2. 实时看更新进度（旧 Pod 逐个下线、新 Pod 逐个上线）
kubectl rollout status deployment/web
# 示例输出：
# Waiting for deployment "web" rollout to finish: 1 out of 3 new replicas updated...
# deployment "web" successfully rolled out

# 3. 查看更新历史
kubectl rollout history deployment/web
# 示例输出：
# REVISION  CHANGE-CAUSE
# 1         <none>
# 2         <none>

# 4. 发现新版本有问题，回滚到上一版
kubectl rollout undo deployment/web

# 5. 回滚到指定版本
kubectl rollout undo deployment/web --to-revision=1

# 6. 扩缩容（副本数改了，Deployment 自动增删 Pod）
kubectl scale deployment/web --replicas=5
kubectl get pods -l app=web
# 示例输出：5 个 Pod
```

```text
滚动更新机制：
Deployment 维护多个 ReplicaSet，每次更新建一个新 ReplicaSet
新 RS 按 maxSurge/maxUnavailable 逐个加 Pod、旧 RS 逐个减 Pod
旧 RS 保留（不清空），所以 rollout undo 能秒回滚
```

## 性能与调优

```text
1. 资源配置 —— 每个容器都要配 requests/limits，requests 是调度依据
   （没配 requests 会导致调度失衡、节点过载）
2. 副本数与 HPA —— 静态 replicas 应对不了流量波动，上 HorizontalPodAutoscaler
   按 CPU/内存/自定义指标自动扩缩容
3. 就绪探针 —— readinessProbe 配好，Pod 没就绪别接流量，避免「起了但 502」
4. 存活探针 —— livenessProbe 别太灵敏（太短误杀），初始延迟 initialDelaySeconds 给足
5. 资源配额 —— 用 ResourceQuota/LimitRange 限制命名空间总资源，防一个应用吃光集群
6. 调度优化 —— nodeSelector/affinity 把 Pod 绑到合适节点，污点容忍避免乱调度
```

```yaml
# HPA：按 CPU 自动扩缩容（2~10 个副本）
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # CPU 平均 70% 触发扩容
```

## 安全与权限

Kubernetes 安全四层：认证（你是谁）、授权（你能干嘛）、准入控制（干之前拦一道）、运行时隔离（Pod 之间/容器与宿主机之间）。

```text
1. 认证 —— 用户/ServiceAccount 身份，kubeconfig 里存证书/token
2. 授权 —— RBAC（Role + RoleBinding），最小权限原则
3. 准入控制 —— Admission Webhook 拦不合规请求（如禁 root 容器）
4. 网络策略 —— NetworkPolicy 限制 Pod 间流量（默认全通，要显式收紧）
5. Pod 安全 —— securityContext 禁 root、禁特权、只读根文件系统
```

# RBAC：给 dev 命名空间建只读角色并绑定
apiVersion: rbac.authorization.k8s.io/v1

  namespace: dev
  name: pod-reader

  - apiGroups: [""]
    resources: ["pods"]

## 故障排查

排查 Pod 问题的标准顺序：`describe`（看事件）→ `logs`（看应用日志）→ 按状态分类处理。

```shell
# 1. Pod 状态总览
kubectl get pods -o wide
# 状态含义：Pending（没调度/拉镜像）、CrashLoopBackOff（反复重启）、
#          ImagePullBackOff（拉镜像失败）、Error、Completed

# 2. 看事件（排错第一入口，事件里通常直接写了原因）
kubectl describe pod <pod-name>
# 重点看 Events 段：FailedScheduling（资源不够/污点）、
#                  Failed to pull image（镜像名错/没权限）、
#                  Back-off restarting failed container（容器起不来）

# 3. 看应用日志
kubectl logs <pod-name>              # 当前容器
kubectl logs <pod-name> -c <name>    # 多容器指定
kubectl logs <pod-name> --previous   # 上一个崩溃容器的日志

# 4. 进容器排查
kubectl exec -it <pod-name> -- /bin/sh

# 5. 看节点状态（Pod 全挂可能是节点问题）
kubectl get nodes
kubectl describe node <node>          # 看节点压力（MemoryPressure/DiskPressure）
```

### 常见故障定位

```text
Pending：       调度不了。查 describe 事件（资源不够/污点/卷挂不上）
ImagePullBackOff：拉镜像失败。镜像名/标签写错、私有仓库没配 imagePullSecret
CrashLoopBackOff：容器反复崩溃。logs --previous 看崩溃日志，多是启动参数/依赖没就绪
Running 但连不上：Service selector 没匹配 Pod 标签，查 endpoints 是否为空
```

## 常见问题

```text
Q1: Pod 和容器是什么关系？和 Docker 容器一样吗？
A: Pod 是最小调度单元，一个 Pod 可含一个或多个容器，同 Pod 容器共享网络/存储。Docker 容器约等于「单容器 Pod」，但 K8s 的最小单位是 Pod 不是容器。

Q2: ClusterIP 是真实 IP 吗？为什么 ping 不通？
A: ClusterIP 是虚拟 IP，只存在于 kube-proxy 维护的 iptables/IPVS 规则里，不绑定任何网卡，所以 ping 不通（它是 TCP/UDP 转发规则不是网络接口）。

Q3: Deployment 和 ReplicaSet 和 Pod 什么关系？
A: Deployment 管 ReplicaSet，ReplicaSet 管 Pod。每次更新建新 ReplicaSet，旧 ReplicaSet 保留用于回滚。Deployment 提供滚动更新/回滚，ReplicaSet 只负责「保副本数」。

Q4: livenessProbe 和 readinessProbe 有什么区别？
A: liveness 失败会重启容器（容器没救了），readiness 失败只摘流量不重启（容器还没准备好）。错配会导致「服务反复重启」或「Pod 一直没流量」。

Q5: Service 找不到后端 Pod 怎么办？
A: 先查 `kubectl get endpoints <svc>`，为空说明 selector 没匹配到 Pod。核对 Service 的 selector 和 Pod 的 labels 是否一致（拼写、大小写）。

Q6: 怎么查看某个 Pod 到底跑在哪个节点？
A: `kubectl get pods -o wide` 的 NODE 列，或 `kubectl get pod <name> -o jsonpath='{.spec.nodeName}'`。
```

## 面试题

```text
1. 说一下 Kubernetes 的架构？
   答：控制平面（apiserver 唯一入口、etcd 存状态、scheduler 调度、controller-manager 跑控制器）+ 数据平面（kubelet 管节点容器、kube-proxy 管网络、容器运行时跑容器）。所有对象经 apiserver 操作，状态存 etcd。

2. 什么是声明式 API？和命令式有什么区别？
   答：声明式是描述「期望状态」（apply YAML 说我要 3 个副本），系统通过控制循环自动收敛；命令式是描述「执行步骤」（docker run、docker stop）。声明式幂等、可重复、自动化友好。

3. Pod 重启后 IP 变了，客户端怎么稳定访问？
   答：用 Service。Service 用 selector 绑定一组 Pod，提供稳定的 ClusterIP 和 DNS 名，客户端访问 Service 而不是 Pod IP，Pod 随便重建都不影响。

4. 滚动更新是怎么做到不中断服务的？
   答：Deployment 建新 ReplicaSet，按 maxSurge/maxUnavailable 逐个起新 Pod、停旧 Pod，同时保证可用副本数不低于阈值。新 Pod 就绪（readiness 通过）后才接流量，旧 Pod 才停。

5. 容器反复 CrashLoopBackOff 怎么排查？
   答：先 `kubectl describe pod` 看事件，再 `kubectl logs <pod> --previous` 看上次崩溃日志。常见原因：启动命令错、依赖服务没起、资源 limits 太小被 OOMKill、探针配置错。

6. 一个 Pod 里多个容器共享什么？适合什么场景？
   答：共享网络命名空间（同一 IP、端口空间）和存储卷，通过 localhost 通信。适合 sidecar 模式（主容器 + 日志采集/代理）、init 容器做初始化。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一切用 YAML 声明 + `kubectl apply`，别用 `kubectl run/create` 直接裸起（不可版本化、不可审计）
2. 每个容器配 requests/limits，requests 是调度依据，不配会调度失衡
3. 探针配全：readinessProbe（摘流量）+ livenessProbe（重启），initialDelaySeconds 给足避免误杀
4. 用标签（labels）统一组织资源，Service/Deployment 靠 selector 绑定，标签体系要规范
5. 用命名空间（namespace）隔离环境（dev/test/prod），配 ResourceQuota 限制资源
6. 生产禁 Pod 跑 root，drop capabilities，开 NetworkPolicy 收紧网络
7. 灰度/金丝雀发布用 Deployment 的滚动更新 + 分阶段验证，保留回滚能力

### 踩坑记录

```text
坑 1：Service 建好了但访问不通
结论：curl ClusterIP 连接超时，后端 Pod 正常。
原因：Service 的 selector 和 Pod 的 labels 不匹配，endpoints 为空。
解法：`kubectl get endpoints <svc>` 确认是否为空，核对 selector 与 Pod labels 拼写一致。

坑 2：没配 requests，节点被某个 Pod 吃满
结论：单个 Pod 占用大量 CPU，同节点其他 Pod 被挤垮。
原因：没配 requests 调度器不知道 Pod 要多少资源，随便往满节点塞。
解法：每个容器配 requests/limits，用 ResourceQuota 限制命名空间总量。

坑 3：livenessProbe 太灵敏，服务反复重启
结论：Pod 频繁重启，日志显示健康检查失败。
原因：liveness 探测间隔太短/超时太短，启动慢的应用还没起来就被判死。
解法：liveness 配 initialDelaySeconds + 合理周期，用 readiness 区分「没就绪」和「真挂了」。

坑 4：直接依赖 Pod IP，Pod 重建后连接全断
结论：客户端缓存了 Pod IP，Pod 一重建就访问失败。
原因：Pod 是临时的，IP 每次重建都可能变。
解法：客户端只访问 Service 的 ClusterIP/DNS 名，不要缓存 Pod IP。

坑 5：改镜像直接 rollout，出了问题才发现
结论：滚动更新后新版本有 bug，线上故障。
原因：没做灰度验证，一次性全量滚动。
解法：分阶段更新（先 1 个副本观察），出问题立刻 `kubectl rollout undo` 回滚。

坑 6：用 latest 标签做镜像版本
结论：同版本号拉到的镜像内容不一样，回滚/审计乱套。
原因：latest 是浮动标签，每次 push 都变，无法确定具体版本。
解法：镜像用不可变标签（版本号/commit hash），配合 `imagePullPolicy: IfNotPresent`。

坑 7：Secret 明文写进 YAML 提交 git
结论：数据库密码泄露到代码仓库。
原因：为了省事把 Secret 的 stringData 明文写在 YAML 里。
解法：Secret 用外部注入（sealed-secrets/外部密钥管理），YAML 里只引用不写明文。
```
