## 概述

「容器运行时」不是只有 Docker 一个。Docker 其实是一层「开发者友好的外壳」，它底下调用的是真正跑容器的组件（containerd、runc）。随着 Kubernetes 在 1.24 版本弃用 Docker 作为运行时、全面转向 CRI（容器运行时接口），运行时生态分化成清晰的三层：**OCI 规范层**（统一容器/镜像标准）、**CRI 接口层**（K8s 与运行时之间的桥梁）、**运行时实现层**（Podman、containerd、CRI-O、LXC 等具体工具）。理解这层生态，才能搞清「K8s 里跑的到底是什么」。

```text
容器运行时生态三层：
- OCI 规范：runtime-spec（怎么跑容器）+ image-spec（镜像格式），统一标准
- CRI 接口：Kubernetes 定义的运行时接口，kubelet 只认 CRI
- 实现：Podman（无守护进程替代 Docker）、containerd（K8s 默认运行时）、
        CRI-O（专为 K8s 设计）、LXC/LXD（系统容器）、runc/crun（底层 OCI 运行时）
```

## 核心概念

### OCI 规范与运行时

OCI（Open Container Initiative）是 Linux 基金会下的开放标准，定义了两件事：**runtime-spec**（容器的运行规范——怎么用 rootfs + config.json 起一个容器）和 **image-spec**（镜像格式——分层、manifest、config 的结构）。有了 OCI，任何符合 OCI 的镜像都能被任何符合 OCI 的运行时运行，厂商不互相锁定。

OCI 运行时（runc、crun、gVisor、Kata）是**最底层**的执行器，负责真正创建 namespace、cgroup、挂载 rootfs 并启动容器进程。它不管镜像拉取、不管网络编排，只干「给定 rootfs 和配置，把容器进程跑起来」这一件事。

```text
OCI 运行时分类：
runc     最主流的 OCI 运行时，Go 写的，containerd/Docker 默认用它
crun     C 写的轻量运行时，启动更快、内存更低（RHEL 系默认）
gVisor   用户态内核，每个容器一个「假内核」，强隔离（Google 出品）
Kata     轻量虚拟机（MicroVM），每个容器一个 VM，安全隔离（机密计算场景）
```

```shell
# 直接用 runc 跑一个 OCI 容器（绕过 Docker，理解底层）
# 1. 准备一个 rootfs（随便拉个镜像解包，或直接用系统目录）
mkdir -p /tmp/rootfs && cd /tmp/rootfs
# 2. 生成 OCI 配置（config.json）
runc spec                       # 生成默认 config.json
# 3. 用 runc 起容器（直接跑宿主机的 /bin/sh，共享内核）
runc run mycontainer            # 进入容器 shell，exit 退出
# 4. 查看/删除容器
runc list                       # 列出 runc 管理的容器
runc delete mycontainer
```

```text
runc 要点：
- 最底层执行器：只管「按 config.json + rootfs 起容器进程」
- 不拉镜像、不配网络，这些是上层（containerd/Docker）的事
- 一个容器 = 一个 runc 进程，退出即容器结束
- 对应容器原理里的 namespace + cgroup（见 21.2）
```

### CRI（容器运行时接口）

CRI（Container Runtime Interface）是 Kubernetes 定义的**运行时接口标准**，规定 kubelet 通过 gRPC 调用运行时的哪些方法（创建/启动/停止容器、拉镜像、看状态）。它把「K8s 需要什么」和「具体运行时怎么实现」解耦——只要实现 CRI 的运行时都能接进 K8s。

```text
CRI 解决什么问题：
- 早期 K8s 通过 dockershim 直接调 Docker，被 Docker 绑定
- Docker 自身大而全（镜像、网络、存储都管），K8s 只想用「跑容器」那部分
- CRI 定义了标准 gRPC 接口，containerd/CRI-O 都实现它，K8s 不再依赖 Docker
- K8s 1.24 起正式移除 dockershim，运行时只能走 CRI
```

```text
CRI 的 gRPC 接口分两组：
RuntimeService   容器生命周期：CreateContainer/StartContainer/StopContainer/ListContainers...
ImageService     镜像管理：PullImage/ListImages/RemoveImage...

kubelet（客户端） → 通过 CRI gRPC → containerd/CRI-O（服务端）→ 调 runc 起容器
```

```shell
# 查看 K8s 节点当前用的 CRI 运行时
kubectl get nodes -o wide
# 在节点上直接看（containerd 方式）
crictl version                  # crictl 是 CRI 的命令行客户端
crictl ps -a                    # 看容器（等价 docker ps，但走 CRI 接口）
crictl images                   # 看镜像
crictl pull nginx:1.25          # 拉镜像
crictl logs <container-id>      # 看容器日志
```

```text
CRI 要点：
- K8s 定义的运行时接口，gRPC 协议，实现了解耦
- crictl 是调试 CRI 的标准客户端（直接对话 containerd/CRI-O）
- dockershim 移除后，containerd 和 CRI-O 是两大 CRI 实现
```

### Podman

Podman 是 Red Hat 主导的容器引擎，**命令和 Docker 几乎一样（`podman run/build/push`）**，但关键差异是：**无守护进程（daemonless）**、**默认 rootless（非 root 运行）**。Docker 有一个常驻的 dockerd 守护进程，所有容器都归它管（root 权限、单点）；Podman 每个容器直接 fork 子进程，不依赖守护进程，还支持用普通用户身份跑容器，安全性和 systemd 集成更好。

```shell
# Podman 命令（与 Docker 高度兼容，很多场景能直接 alias docker=podman）
podman pull nginx:1.25
podman run -d --name web -p 8080:80 nginx:1.25   # 起容器
podman ps
podman logs web
podman stop web && podman rm web
podman build -t myapp:1.0 .                      # 构建镜像（Dockerfile 通用）
podman images
podman push myapp:1.0 registry.example.com/myapp:1.0

# rootless：普通用户直接跑容器（无 root）
podman run --rm -it alpine:3.20 /bin/sh          # 普通用户身份，无守护进程

# Pod 概念：Podman 原生支持 pod（多容器共享网络，对标 K8s 的 Pod）
podman pod create --name mypod -p 8080:80        # 建一个 pod
podman run -d --pod mypod nginx:1.25             # 容器加进 pod
```

```text
Podman vs Docker：
            Docker                    Podman
架构        客户端 + dockerd 守护进程    无守护进程，直接 fork
权限        默认 root（守护进程）       默认 rootless（普通用户）
兼容性      docker CLI                 podman CLI 兼容 docker 命令
Pod         不支持原生 pod            原生支持 pod
systemd      需额外配置               可用 systemd 管理容器（generate systemd）
```

```text
Podman 要点：
- 无守护进程：容器是独立子进程，dockerd 挂了不影响已跑容器
- rootless：默认非 root，配合 user namespace 隔离，安全
- 命令兼容 Docker，迁移成本低
- 原生支持 pod，与 K8s 概念对齐
```

### containerd

containerd 是从 Docker 中剥离出来的**核心容器运行时**（2017 年捐给 CNCF），负责镜像管理 + 容器生命周期管理。它现在是 Kubernetes 的**默认 CRI 运行时**（几乎所有主流发行版的 K8s 都用 containerd），也是 Docker 底层调用链上的一环：Docker → containerd → runc。containerd 只做「运行时该做的事」，网络、存储交给 CNI/CSI 插件。

```shell
# containerd 的命令行客户端是 ctr（低层）和 nerdctl（Docker 风格，推荐）
# 用 ctr（containerd 原生客户端，偏底层）
ctr images pull docker.io/library/nginx:1.25   # 拉镜像（注意要写全 docker.io/）
ctr images list                                # 列镜像
ctr run --rm docker.io/library/nginx:1.25 test /bin/sh   # 跑容器

# 用 nerdctl（Docker 兼容风格，日常使用更方便）
nerdctl run -d --name web -p 8080:80 nginx:1.25
nerdctl ps
nerdctl images
nerdctl build -t myapp:1.0 .
nerdctl compose up                              # 支持 docker-compose 风格

# containerd 服务管理
systemctl status containerd
systemctl restart containerd
```

```text
containerd 调用链：
K8s kubelet → CRI 插件（containerd 内置）→ containerd → runc → 容器进程
Docker      → containerd → runc → 容器进程

containerd 要点：
- K8s 默认 CRI 运行时，CNCF 毕业项目
- 只做镜像 + 容器生命周期，网络/存储靠 CNI/CSI 插件
- ctr 是底层客户端（命令生硬），nerdctl 是 Docker 风格（日常用）
- 配置文件 /etc/containerd/config.toml
```

### LXC 与 LXD

LXC（Linux Containers）是**最老的容器技术**（2008 年，Docker 的前辈），通过 liblxc 直接调用内核的 namespace + cgroup 创建容器，本质是「轻量级系统容器」——更像一台轻量虚拟机（带完整 init 进程、可装多个服务），而非 Docker 那种「单进程应用容器」。LXD 是 LXC 之上的管理守护进程（提供 REST API、镜像仓库、集群管理），类似「LXC 的 Docker 化封装」。

```shell
# LXC（底层工具）
lxc-create -t download -n mycontainer -- -d ubuntu -r noble -a amd64  # 建容器
lxc-start -n mycontainer -d             # 后台启动
lxc-attach -n mycontainer               # 进入容器
lxc-ls -f                               # 列容器
lxc-stop -n mycontainer && lxc-destroy -n mycontainer   # 停止/销毁

# LXD（现代管理方式，命令风格像 Docker）
lxd init                                # 初始化 LXD（配置存储池/网络）
lxc launch ubuntu:noble c1              # 从镜像仓库拉并启动容器
lxc list                                # 列容器
lxc exec c1 -- bash                     # 进容器
lxc stop c1 && lxc delete c1            # 停止/删除
```

```text
LXC/LXD vs Docker：
LXC/LXD  系统容器：完整 init 进程，像轻量 VM，可跑多个服务，长期运行
Docker   应用容器：单进程为主，用完即弃，面向微服务
选择     LXD 适合「轻量虚拟机」场景（多服务、桌面、CI 沙箱）
         Docker/containerd 适合「单应用单容器」的微服务场景
```

## 工作原理

容器运行时的工作分「编排层」和「执行层」，一层一层往下调用，最终落到 OCI 运行时创建 namespace + cgroup：

```text
Kubernetes 场景完整调用链：
kubelet（节点代理）
  └─> CRI gRPC（RuntimeService/ImageService）
        └─> containerd / CRI-O（容器运行时：镜像管理 + 容器生命周期）
              └─> runc / crun（OCI 运行时：真正创建容器进程）

Docker 场景（已逐渐被取代）：
docker CLI → dockerd（守护进程，大而全）
  └─> containerd → runc → 容器进程
```

一次 `kubectl run nginx` 的底层过程：

```text
1. kubelet 收到「要起一个 nginx 容器」的调度结果
2. kubelet 通过 CRI 调 containerd 的 PullImage（拉 nginx 镜像）
3. containerd 从 registry 拉镜像、解包成 OCI 格式（layers + manifest）
4. kubelet 调 CreateContainer/StartContainer
5. containerd 生成 OCI 配置（config.json：进程、挂载、namespace、cgroup）
6. containerd 调 runc 创建容器：clone 新 namespace → 设置 cgroup 限制 →
   挂载 rootfs → exec 容器进程（nginx）
7. runc 起的进程变成容器，nginx 作为 PID 1 运行
```

关键理解：**runc 起完容器就退出**，容器进程由 containerd 的 shim 进程托管（shim 保证「运行时重启不影响已跑容器」）。这就是为什么 containerd 升级/重启时，已经跑着的容器不受影响。

```text
分层职责一句话：
OCI 规范   定标准（镜像长啥样、容器怎么跑）
OCI 运行时 干脏活（runc/crun 真正创建容器进程）
containerd 管生命周期（拉镜像、起停、状态跟踪）+ 实现 CRI
Podman     面向用户的完整工具（daemonless + rootless）
LXC/LXD    系统容器路线（轻量 VM，非应用容器）
```

## 配置文件解析

### containerd 配置（/etc/containerd/config.toml）

```toml
# /etc/containerd/config.toml（关键段）
version = 2

[plugins."io.containerd.grpc.v1.cri"]
  # 镜像加速：配置 registry 镜像（国内拉镜像常用）
  [plugins."io.containerd.grpc.v1.cri".registry]
    [plugins."io.containerd.grpc.v1.cri".registry.mirrors]
      [plugins."io.containerd.grpc.v1.cri".registry.mirrors."docker.io"]
        endpoint = ["https://registry-1.docker.io"]

  # 沙箱（pause）镜像：K8s 每个 Pod 先起一个 sandbox 容器
  sandbox_image = "registry.k8s.io/pause:3.9"

  # 运行时配置
  [plugins."io.containerd.grpc.v1.cri".containerd]
    # 默认运行时
    default_runtime_name = "runc"
    [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
      runtime_type = "io.containerd.runc.v2"
```

```text
containerd 配置要点：
- version = 2 是新格式（v1 已废弃）
- registry.mirrors 配镜像加速/私有仓库
- sandbox_image 是每个 Pod 的 pause 容器镜像
- runtimes 可挂多个运行时（runc/gVisor/Kata），按 RuntimeClass 选择
```

### Podman 的 rootless 存储与配置

```shell
# Podman rootless 存储位置（普通用户）
~/.local/share/containers/storage/    # 镜像/容器数据
# 配置文件
/etc/containers/registries.conf        # registry 配置
/etc/containers/storage.conf           # 存储驱动配置
# 生成 systemd 服务（容器随系统自启）
podman generate systemd --name web --files   # 生成 .service 文件
systemctl --user enable --now container-web.service
```

## 应用场景实战

### 场景一：无 Docker 环境用 Podman 跑 Web 服务（rootless）

在不让装 Docker（或不想装守护进程）的机器上，用 Podman 以普通用户跑一个 Nginx：

```shell
# 1. 普通用户直接跑容器（无 root、无守护进程）
podman run -d --name web -p 8080:80 nginx:1.25
# 2. 验证
curl http://localhost:8080
# 示例输出：Nginx 欢迎页 HTML
podman ps
# 示例输出：
# CONTAINER ID  IMAGE       COMMAND         CREATED      STATUS      PORTS
# 3f2a...       nginx:1.25  nginx -g daemon 2 minutes    Up 2 min    0.0.0.0:8080->80/tcp

# 3. 看容器以哪个用户运行（rootless 特性：容器内是 root，映射到宿主普通用户）
podman top web user
# 4. 生成 systemd 服务让容器开机自启
podman generate systemd --name web --new --files
systemctl --user enable --now container-web.service
```

```text
rootless 的价值：
- 容器逃逸/漏洞最多只拿到普通用户权限，不是 root，攻击面大减
- 无守护进程，单点故障少，systemd 直接管理容器进程
```

### 场景二：K8s 节点上用 crictl 排查容器问题

K8s 节点上没有 docker 命令（运行时是 containerd），排查容器要用 crictl：

```shell
# 1. 列出节点上所有容器（含 kube-system 的基础容器）
crictl ps -a
# 示例输出：
# CONTAINER   IMAGE                              CREATED        STATE    NAME
# 9f2b3c...   registry.k8s.io/pause:3.9          5 hours ago    Running  sandbox
# 7a1d2e...   nginx:1.25                         5 hours ago    Running  nginx

# 2. 看某个业务容器的日志
crictl logs 7a1d2e...

# 3. 拉镜像（排查 ImagePullBackOff 时手动验证）
crictl pull nginx:1.25
# 示例输出：
# Image is up to date for sha256:...

# 4. 查看容器详情（挂载、环境变量、namespace）
crictl inspect 7a1d2e... | less

# 5. 确认节点用的 CRI 运行时
crictl info | grep -A5 runtime
```

```text
为什么用 crictl 而不是 docker ps：
K8s 1.24 后 dockershim 移除，节点上根本没有 docker 命令
crictl 直接走 CRI 接口，对话 containerd/CRI-O，是节点排错的标准工具
```

## 性能与调优

```text
1. 运行时选择 —— crun 比 runc 启动更快、内存更低（C 实现），对启动敏感场景可换 crun
2. 存储驱动 —— containerd 默认 overlayfs（快），别用 vfs（慢，仅测试）
3. 镜像加速 —— 配置 registry mirrors 或本地缓存，减少拉镜像时间
4. 日志驱动 —— 限制容器日志大小（log-opt max-size），防磁盘被日志写满
5. 资源限制 —— 运行时层配 cgroup 限制（--memory/--cpus），防单容器吃满宿主
```

```shell
# Podman 限制资源
podman run -d --name app --memory 512m --cpus 1.5 myapp:1.0
# containerd 日志大小限制（nerdctl）
nerdctl run -d --log-opt max-size=10m --log-opt max-file=3 nginx:1.25
```

```text
性能要点：
- 镜像分层复用：相同基础层只拉一次，多容器共享
- 拉镜像慢优先查 registry mirrors 和网络，别急着换存储驱动
- cgroup 限制是运行时级的，配合 K8s 的 requests/limits（见 21.4）
```

## 安全与权限

```text
容器运行时安全要点：
1. rootless 优先 —— Podman rootless 跑，容器内 root 映射成宿主普通用户
2. 别挂 docker.sock —— 挂载 /var/run/docker.sock 等于给容器 root 权限
3. 最小 capabilities —— 默认 drop 所有 capabilities，按需 add
4. 只读根文件系统 + 无特权模式 —— 减容器逃逸面
5. 镜像扫描 —— 用 Trivy/Clair 扫镜像漏洞，别跑来路不明的镜像
6. 运行时隔离 —— 多租户/敏感负载用 gVisor/Kata（强隔离运行时）
```

```shell
# 检测容器是否特权/挂载了 docker.sock
podman inspect web --format '{{.HostConfig.Privileged}}'   # 应为 false
podman inspect web --format '{{json .Mounts}}'             # 看是否挂了 docker.sock

# 镜像漏洞扫描（Trivy）
trivy image nginx:1.25        # 扫镜像漏洞
# 示例输出：按严重级别列出 CVE（Critical/High/Medium/Low）
```

```text
安全等级（隔离强度从弱到强）：
普通 runc 容器（共享内核，隔离弱）
  < rootless runc（user namespace，权限降级）
  < gVisor（用户态内核，syscall 拦截）
  < Kata（每容器一个 MicroVM，硬件级隔离，接近虚拟机）
```

```shell
# containerd 服务异常
systemctl status containerd          # 看服务状态
journalctl -u containerd -n 50       # 看 containerd 日志
ctr version                          # 客户端/服务端版本（确认通信）

# Podman 容器问题

podman logs <name>                   # 日志

# 镜像拉取失败
# 排查顺序：网络 → registry 配置 → 镜像名/标签
```

### 常见故障定位

```text
containerd 起不来：     看 journalctl，常见是 config.toml 语法错（v2 格式不对）
容器 Exited/CrashLoop： 看 logs，多是容器内进程退出（启动命令/依赖问题）
拉镜像超时：            registry 网络不通，配镜像加速 mirrors 或换源
crictl 连不上运行时：   确认 containerd.sock 路径 + CRI 插件已启用
```

## 常见问题

```text
Q1: Docker、containerd、runc 是什么关系？
A: Docker 是完整工具链（CLI + dockerd + 网络存储），dockerd 底层调用 containerd 管容器生命周期，containerd 底层调 runc 真正创建容器进程。三层：Docker（用户体验层）→ containerd（容器管理层）→ runc（OCI 执行层）。

Q2: K8s 为什么弃用 Docker 当运行时？
A: Docker 大而全，K8s 只需要「跑容器」那一小部分，还要额外维护 dockershim 去适配。用 CRI 接口直接对接 containerd/CRI-O，少了 dockershim 一层，更精简。注意「弃用」的是 Docker 作为运行时，Docker 构建的镜像仍是 OCI 标准，K8s 照常能跑。

Q3: Podman 和 Docker 命令一样，能直接替换吗？
A: 大部分命令兼容（run/ps/build/push），可以 `alias docker=podman`。差异在架构：Podman 无守护进程、默认 rootless。个别依赖 docker.sock 的编排工具（如 docker-compose 老版本）需要适配（用 podman-compose）。

Q4: crictl、ctr、nerdctl、podman、docker 命令怎么选？
A: K8s 节点排错用 crictl（走 CRI）；日常用 containerd 用 nerdctl（Docker 风格）；底层调试 containerd 用 ctr；无守护进程需求用 podman；单机开发用 docker。

Q5: LXC/LXD 和 Docker 容器有什么区别？
A: LXC/LXD 是「系统容器」，带完整 init 进程、像轻量虚拟机、可跑多服务长期运行；Docker 是「应用容器」，单进程为主、面向微服务。想「轻量 VM」用 LXD，想「单应用打包」用 Docker/containerd。

Q6: 什么是 sandbox（pause）容器？为什么每个 Pod 都有一个？
A: pause 容器是 Pod 的「根基容器」，它先启动并持有 Pod 的网络命名空间和 IP，Pod 里其他容器共享它的网络。它什么都不做（只有 pause 系统调用），但保证 Pod 网络稳定存在。
```

## 面试题

```text
1. 容器运行时的调用链是怎样的？
   答：K8s kubelet 通过 CRI gRPC 调 containerd/CRI-O，containerd 负责镜像管理和容器生命周期，再调 runc（OCI 运行时）真正创建 namespace/cgroup、挂载 rootfs、启动容器进程。Docker 则是 CLI → dockerd → containerd → runc。

2. OCI 是什么？为什么需要它？
   答：OCI 是开放容器标准，定义 runtime-spec（怎么跑容器）和 image-spec（镜像格式）。它让镜像和运行时解耦：任何 OCI 镜像能被任何 OCI 运行时运行，避免厂商锁定（Docker 镜像能跑在 Podman/containerd 上）。

3. CRI 解决了什么问题？
   答：K8s 早期通过 dockershim 直连 Docker，被 Docker 绑定。CRI 定义了标准 gRPC 接口，containerd/CRI-O 等运行时只要实现 CRI 就能接入 K8s，解耦了 K8s 和具体运行时，也让 K8s 1.24 能移除 dockershim。

4. Podman 相比 Docker 有什么优势？
   答：无守护进程（daemonless，容器是独立进程，无单点）、默认 rootless（普通用户跑容器，安全）、命令兼容 Docker（迁移成本低）、原生支持 pod（与 K8s 概念对齐）。

5. 什么是 rootless 容器？为什么更安全？
   答：以非 root 用户运行容器，配合 user namespace 把容器内 root 映射到宿主普通用户。即使容器逃逸或提权，攻击者拿到的也只是普通用户权限，不是宿主 root，攻击面大幅缩小。

6. runc 和 crun、gVisor、Kata 有什么区别？
   答：runc（Go）和 crun（C）是标准 OCI 运行时，共享宿主内核、隔离弱但性能好；gVisor 用用户态内核拦截 syscall，隔离强；Kata 每容器一个轻量 VM，硬件级隔离，接近虚拟机安全性，用于多租户/机密计算。
```

## 最佳实践与踩坑记录

### 最佳实践

1. K8s 生产运行时首选 containerd（CNCF 毕业、默认选择），别再用 Docker 当运行时
2. 单机/开发无守护进程需求用 Podman（rootless 更安全），命令兼容 Docker
3. 节点排错统一用 crictl（走 CRI，不依赖某个运行时特有的命令）
4. 镜像拉取配 registry mirrors 或本地缓存，减少公网拉取延迟
5. 限制容器日志大小（log-opt max-size），防磁盘被日志写满
6. 敏感/多租户负载用 gVisor 或 Kata 强隔离运行时，普通负载用 runc/crun
7. 定期扫镜像漏洞（Trivy/Clair），禁用来路不明的镜像

### 踩坑记录

```text
坑 1：节点上敲 docker ps 报 command not found
结论：K8s 1.24+ 的节点没有 docker 命令，docker ps 报找不到命令。
原因：dockershim 移除后，节点运行时是 containerd，只有 crictl/ctr/nerdctl。
解法：节点排错用 `crictl ps -a`，或装 nerdctl 获得 Docker 风格命令。

坑 2：ctr 拉镜像报 not found，但镜像确实存在
结论：ctr pull nginx:1.25 报错找不到镜像。
原因：ctr 是底层客户端，镜像名必须写全 registry 前缀（docker.io/library/nginx:1.25），不像 docker 会自动补全。
解法：用 nerdctl（自动补全）或写全 `docker.io/library/` 前缀。

坑 3：容器把宿主磁盘写满
结论：宿主磁盘 100%，排查发现是容器日志无限增长。
原因：没限制容器日志大小，日志驱动默认不轮转。
解法：配 `--log-opt max-size=10m --log-opt max-file=3` 限制日志。

坑 4：挂载 docker.sock 导致容器逃逸
结论：容器里挂了 docker.sock 后，容器内能操作宿主机 Docker，等于拿到 root。
原因：/var/run/docker.sock 是 Docker 的 root 权限入口，挂进容器等于交钥匙。
解法：别挂 docker.sock，需要编排能力用官方 API 或改成无守护进程方案。

坑 5：改了 containerd 配置没生效
结论：改了 config.toml 后 containerd 还是老行为。
原因：改完没重启 containerd，或 config.toml 还是 version=1 老格式。
解法：`systemctl restart containerd`，并确认配置是 version=2 新格式。

坑 6：rootless Podman 拉镜像/起容器权限报错
结论：普通用户跑 Podman 报权限不足。
原因：rootless 需要 user namespace 支持，某些内核/发行版没开，或子 uid/gid 没映射。
解法：确认内核开启 user namespace，检查 /etc/subuid、/etc/subgid 映射。

坑 7：runc 起的容器 containerd 一重启就「消失」
结论：containerd 升级重启后，运行中的容器状态异常。
原因：没理解 shim 机制，runc 起完容器就退出，容器由 shim 托管，但 shim 没正确关联。
解法：确认 containerd 的 shim 进程正常（ps 看 containerd-shim），重启 containerd 前先确认 shim 存活。
```
