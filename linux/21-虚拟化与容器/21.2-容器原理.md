## 概述

容器（Container）本质上是「共享宿主内核、但被隔离的进程组」——它不是一个轻量虚拟机，而是 Linux 内核两大特性（namespace + cgroups）组合出来的进程级隔离：namespace 负责「看不见」（隔离视图），cgroups 负责「用不多」（限制资源）。容器与虚拟机的根本区别：虚拟机有独立 Guest 内核，容器共享宿主内核，所以容器启动毫秒级、密度高、但隔离性弱于虚拟机。

```text
容器 = namespace（隔离视图）+ cgroups（限制资源）+ 镜像分层（可移植交付）
对比虚拟机：容器共享宿主内核（轻、快、弱隔离），虚拟机独立内核（重、慢、强隔离）
```

## 核心概念

### namespace（命名空间隔离）

namespace 是 Linux 内核的「视图隔离」机制——把系统全局资源（PID、网络、挂载点、主机名等）划分成多个互相不可见的命名空间，同一台宿主机上的进程可以各自活在独立的世界里。内核提供 8 类 namespace：

- **PID**：进程号隔离，容器里的进程在容器内看自己是 PID 1
- **Network**：网络栈隔离，独立网卡/IP/路由/iptables
- **Mount**：挂载点隔离，独立文件系统视图
- **UTS**：主机名/域名隔离
- **IPC**：System V IPC / POSIX 消息队列隔离
- **User**：UID/GID 隔离（容器内 root 可映射成宿主普通用户）
- **Cgroup**：cgroup 视图隔离
- **Time**：时钟隔离（内核 5.6+）

进程通过 `clone()` / `unshare()` 系统调用创建新的 namespace，通过 `setns()` 加入已有 namespace。

```shell
# 用 unshare 手动体验 PID namespace 隔离
sudo unshare --pid --fork --mount-proc /bin/bash
# 进入新命名空间后，进程号从 1 重新开始
echo $$        # 输出 1（当前 shell 是命名空间里的 PID 1）
ps -ef         # 只能看到本命名空间内的少数进程，看不到宿主的其它进程
# 退出（exit）后回到宿主命名空间
```

```text
查看命名空间：
ls -l /proc/$$/ns/          # 每个进程的 namespace 符号链接
lsns                        # 列出系统所有命名空间
每个 namespace 用 inode 号标识，两个进程 inode 相同 = 同处一个命名空间
```

### cgroups（控制组资源限制）

cgroups（control groups）负责「记账 + 限制 + 隔离」资源：CPU、内存、磁盘 IO、网络带宽、进程数等。没有 cgroups，一个容器里的失控进程（如内存泄漏、死循环）能拖垮整台宿主机。cgroups 有两个版本：

- **v1**：每个资源子系统（cpu/memory/blkio…）各自一棵层级树，互不关联，管理割裂
- **v2**：统一层级，单一 `/sys/fs/cgroup` 树，用控制器（controller）按需启用，现代默认

```shell
# 查看当前进程归属的 cgroup
cat /proc/self/cgroup
# 0::/user.slice/user-0.slice/session-1.scope   （v2 风格）

# 手动创建一个 cgroup 并限制内存（v2）
sudo mkdir /sys/fs/cgroup/demo
echo "100M" > /sys/fs/cgroup/demo/memory.max       # 限制 100M 内存
echo "50000 100000" > /sys/fs/cgroup/demo/cpu.max  # CPU 配额：每 100ms 周期用 50ms（50% 单核）
echo $$ > /sys/fs/cgroup/demo/cgroup.procs         # 把当前 shell 加入该 cgroup
# 之后该 shell 及其子进程的内存/CPU 都受此 cgroup 限制
```

### 镜像分层（OverlayFS / 写时复制）

容器镜像由多个「只读层」叠加而成，最上面是一层可写的「容器层」。底层用 OverlayFS（或 aufs）联合挂载，上层文件覆盖下层同名文件，删除下层文件用 whiteout 标记。写文件时走**写时复制（Copy-on-Write，COW）**——下层只读层的文件被修改时，先复制到上层再改，原层永不改动。这样不同镜像可以共享相同的基础层（如都基于 ubuntu 层），省磁盘、加快分发。

```shell
# 手动演示 OverlayFS 分层
mkdir -p /tmp/ovl/{lower,upper,work,merged}
echo "来自基础层" > /tmp/ovl/lower/base.txt      # 下层（只读，模拟镜像层）
echo "旧内容"   > /tmp/ovl/lower/file.txt
sudo mount -t overlay overlay \
  -o lowerdir=/tmp/ovl/lower,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work \
  /tmp/ovl/merged
cat /tmp/ovl/merged/base.txt        # 能看到下层的文件
echo "新内容" > /tmp/ovl/merged/file.txt        # 修改触发写时复制
cat /tmp/ovl/lower/file.txt         # 旧内容（下层不变）
cat /tmp/ovl/upper/file.txt         # 新内容（复制到上层改）
cat /tmp/ovl/merged/file.txt        # 新内容（联合视图取上层）
sudo umount /tmp/ovl/merged
```

### 容器运行时（OCI / runc / containerd）

容器运行时（Container Runtime）是真正「创建并运行容器」的组件，分低层和高层：

- **低层运行时**：直接操作 namespace/cgroups 把进程跑起来，最典型是 **runc**（OCI Runtime 标准参考实现，Docker/containerd/CRI-O 都用它）
- **高层运行时**：管理镜像、网络、容器生命周期，如 **containerd**（Docker 背后的运行时）、**CRI-O**（K8s 专用的 CRI 实现）
- **OCI（Open Container Initiative）**：容器镜像格式（image-spec）和运行时接口（runtime-spec）的开放标准，保证「谁家的镜像谁家的运行时都能互跑」

```shell
# 用 runc 直接运行一个符合 OCI 规范的容器（不经过 Docker）
mkdir -p /tmp/mycontainer && cd /tmp/mycontainer
runc spec                            # 生成 config.json（OCI 运行时规范）
# 编辑 config.json 里的 root.path 指向 rootfs，然后准备 rootfs（可从镜像 tar 解出）
runc run mycontainer                 # 前台运行
runc list                            # 列出 runc 管理的容器
```

```text
运行时层次：
Docker/containerd/CRI-O（高层，管镜像+网络+生命周期）
        ↓ 都调用
runc（低层，直接建 namespace + cgroups 跑进程）
OCI 标准统一了镜像格式与运行时接口，避免生态割裂
```

## 工作原理

容器启动时，运行时按 OCI 规范做三件事：

1. **建 namespace**：用 `clone()` / `unshare()` 为容器进程创建独立的 PID/Network/Mount/UTS/IPC/User 等命名空间，进程看不到宿主的世界。
2. **挂 cgroup**：把容器进程写进独立的 cgroup 子组，按资源配额限制 CPU/内存/IO。
3. **pivot_root / chroot + 挂载根文件系统**：把镜像的分层文件系统（OverlayFS 联合挂载）挂成容器的根目录，再 `pivot_root` 切换进去，容器进程看到的根目录就是镜像的内容。

镜像分层的读写路径：读文件时 OverlayFS 从最上层往下找，第一个命中的层返回；写文件时若文件在下层只读层，先复制到可写层（COW）再写；删除文件时在可写层放一个 whiteout 字符设备掩盖下层文件。

```text
容器启动三步：
clone/unshare 建 namespace → 挂 cgroup 限资源 → pivot_root 切到镜像根文件系统
镜像读写：
读 = 从顶层往下找第一个命中；写 = COW 复制到可写层再改；删 = whiteout 掩盖
```

## 常用命令与配置

```shell
# namespace 相关
lsns                                    # 列出所有命名空间
lsns -t pid                             # 只看 PID 命名空间
sudo nsenter -t <PID> -m -u -i -n -p    # 进入指定进程的所有命名空间（调试容器必用）
unshare --net /bin/bash                  # 新建一个 network namespace 并进入

# cgroup 相关
cat /proc/self/cgroup                    # 当前进程的 cgroup
systemd-cgls                             # 树状查看 cgroup（systemd 管理）
cat /sys/fs/cgroup/memory.max            # 查看根 cgroup 内存上限

# 镜像/容器运行时相关（Docker 层面）
docker image ls                          # 看镜像与分层
docker image history <image>             # 看镜像每一层是怎么构建的
docker inspect <container> | grep -i pid # 看容器进程的宿主 PID（可 nsenter 进去）
```

```text
调试容器进程的套路：
docker inspect 拿宿主 PID → nsenter -t PID -m -u -i -n -p 直接进它的命名空间
lsns 看命名空间全景；systemd-cgls 看资源树
```

## 配置文件解析

OCI 运行时规范用 `config.json` 描述「怎么跑一个容器」，runc 靠它启动；cgroup 配额则写在 cgroup 文件系统里。

```json
{
  "ociVersion": "1.1.0",
  "process": {
    "terminal": true,
    "user": { "uid": 0, "gid": 0 },
    "args": ["sh"],
    "cwd": "/"
  },
  "root": {
    "path": "rootfs",
    "readonly": true
  },
  "hostname": "mycontainer",
  "linux": {
    "namespaces": [
      { "type": "pid" },
      { "type": "network" },
      { "type": "mount" },
      { "type": "ipc" },
      { "type": "uts" }
    ],
    "resources": {
      "memory": { "limit": 134217728 },
      "cpu": { "quota": 50000, "period": 100000 }
    }
  }
}
```

```text
字段含义：
process.args     容器启动执行的命令（PID 1）
root.path/readonly  根文件系统路径 + 是否只读
linux.namespaces    要创建的命名空间类型（与 namespace 概念一一对应）
linux.resources     资源配额（对应 cgroup 的 memory.max / cpu.max）
runc 读这个文件，建 namespace、挂 cgroup、切 rootfs，容器就跑起来了
```

## 应用场景实战

### 场景一：不装 Docker，纯手搓一个「最小容器」

用 unshare + chroot 手工体验容器是怎么被「拼」出来的：

```shell
# 1. 准备一个最小根文件系统（借一个带 busybox 的 rootfs）
mkdir -p /tmp/minirootfs/{bin,proc}
cp /bin/busybox /tmp/minirootfs/bin/ 2>/dev/null || echo "需先安装 busybox"

# 2. 隔离 PID + Mount 命名空间，挂 proc，chroot 进去
sudo unshare --pid --fork --mount-proc --mount /bin/sh -c '
  mount -t proc proc /tmp/minirootfs/proc
  chroot /tmp/minirootfs /bin/sh
'
# 3. 现在这个 shell 的根目录被切到了 minirootfs，PID 从 1 起，
#    看不到宿主的进程和文件——这就是容器最核心的两步：namespace + chroot/pivot_root
```

### 场景二：用 cgroup 限制一个「失控」进程，验证它跑不爆宿主机

制造一个持续吃内存的进程，用 cgroup 把它内存封顶，验证 cgroup 的兜底作用：

```shell
# 1. 建 cgroup 并设 50M 内存上限
sudo mkdir /sys/fs/cgroup/demo
echo "50M" > /sys/fs/cgroup/demo/memory.max
echo $$ > /sys/fs/cgroup/demo/cgroup.procs   # 把当前 shell 纳入限制

# 2. 跑一个持续分配内存的程序（放进同一 cgroup）
python3 -c 'import time; a=[]
while True:
    a.append(bytearray(10_000_000)); time.sleep(0.05)' &

# 3. 观察：进程内存涨到 50M 附近就被内核触发 OOM 杀掉（或触发回收）
#    而宿主机其它进程不受影响 —— 这就是 cgroup 保证「一个容器不拖垮全机」的机制
```

```text
场景一演示 namespace（隔离）+ chroot（切根）—— 容器的两个地基
场景二演示 cgroup（限资源）—— 容器安全多租户的兜底，OOM 只杀容器内进程不连坐宿主
```

## 性能与调优

```text
1. 容器本身开销极小 —— 与裸进程相当（共享内核，无 Guest OS），瓶颈多在应用而非容器层
2. 镜像层别太多 —— 每条 RUN 指令一层，层数多会拖慢拉取和挂载；合并相关命令减少层数
3. 写密集型负载避免写进镜像层 —— 写时复制 + 可写层会带来额外开销，用 volume 挂载数据目录
4. 合理设 cgroup 配额 —— CPU limit 设太低会频繁 CPU throttling，导致响应抖动
5. 用 overlay2 存储驱动 —— 比旧版 aufs/devicemapper 快，且 inode 充足
6. 镜像瘦身 —— 用多阶段构建 + alpine 基础镜像，减小层体积加快分发
```

## 安全与权限

```text
1. 容器共享内核 —— 隔离弱于虚拟机，生产跑不可信代码用「不可变镜像 + 最小权限」
2. 少用 privileged —— --privileged 等于把宿主设备全暴露，能不用就不用
3. 用 user namespace —— 把容器内 root 映射成宿主普通用户，降低逃逸后的权限
4. 设只读根文件系统 + 内存/CPU 上限 —— 防容器内写坏镜像、防资源耗尽
5. 注意 /proc /sys 暴露 —— 默认挂载的宿主内核信息可能泄露，必要时屏蔽挂载
6. seccomp / AppArmor / SELinux —— 内核安全模块限制容器能调用的系统调用
```

## 故障排查

### 容器内进程看不到 / 宿主进程能「看到」容器进程

```shell
# 容器 PID 1 对应宿主哪个进程？
docker inspect -f '{{.State.Pid}}' <container>   # 拿宿主 PID
ps -p <PID> -o pid,ppid,cmd                     # 在宿主看它
# 进程「看不见」是 PID namespace 隔离，进程本身仍在宿主上（这是容器本质）
```

### cgroup 限制不生效

```shell
# 确认走的是 cgroup v2 还是 v1
mount | grep cgroup
# v2：单一 /sys/fs/cgroup；v1：/sys/fs/cgroup/{cpu,memory,...} 多目录
# 确认进程是否真的进了目标 cgroup
cat /proc/<PID>/cgroup
# 若容器里看 /sys/fs/cgroup 还是根，检查挂载方式（容器要挂自己的 cgroup 视图）
```

## 常见问题

```text
Q1: 容器和虚拟机到底差在哪？
A: 容器共享宿主内核、只隔离进程（namespace+cgroups），启动毫秒级、密度高；虚拟机有独立 Guest 内核，隔离强但重。容器是「进程级隔离」，虚拟机是「硬件级隔离」。

Q2: namespace 和 cgroups 各管什么？
A: namespace 管「隔离视图」——进程/网络/挂载/主机名等互相看不见；cgroups 管「限制资源」——CPU/内存/IO 封顶。两者配合：隔离 + 限额，缺一不可。

Q3: 为什么镜像能共享基础层？
A: 镜像由只读层叠加（OverlayFS），不同镜像只要基础层相同（如都基于 ubuntu），宿主只存一份，靠写时复制在各自的容器层做修改，所以省空间。

Q4: 容器里的 root 和宿主 root 一样吗？
A: 默认一样（都是宿主 root，有逃逸风险），开了 user namespace 后容器内 root 映射成宿主普通用户，权限被降级。这就是为什么默认不推荐容器跑 root。

Q5: runc 和 containerd、Docker 什么关系？
A: runc 是低层运行时（真正建 namespace 跑进程），containerd 是高层运行时（管镜像/生命周期），Docker 在 containerd 之上提供 CLI 和完整用户体验，最终都落到 runc。
```

## 面试题

```text
1. 容器和虚拟机的本质区别？
   答：容器共享宿主内核，是进程级隔离（namespace+cgroups），轻量、启动快、密度高但隔离弱；虚拟机有独立内核，硬件级隔离，重、慢但隔离强。

2. 什么是写时复制（COW）？在镜像里怎么用？
   答：下层只读层的文件被修改时，先复制到可写层再改，原层不动。镜像借此实现多层共享——基础层只存一份，各容器各自 COW，省空间且启动快。

3. namespace 有哪些类型？各自隔离什么？
   答：PID（进程号）、Network（网络栈）、Mount（挂载点）、UTS（主机名）、IPC（进程间通信）、User（UID/GID）、Cgroup（cgroup 视图）、Time（时钟）。容器主要用前六种。

4. cgroups v1 和 v2 区别？
   答：v1 每个子系统（cpu/memory/blkio）各自一棵层级树、管理割裂；v2 统一到单一层级（/sys/fs/cgroup），控制器按需启用，现代默认。

5. 什么是 OCI 标准？为什么需要它？
   答：OCI 是开放容器标准，统一了镜像格式（image-spec）和运行时接口（runtime-spec），让镜像和运行时跨厂商互操作，避免 Docker 一家独大导致的生态锁死。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一个容器一个进程（PID 1 就是业务进程），别在容器里跑多进程混装
2. 镜像层尽量少，用多阶段构建 + alpine 基础镜像瘦身
3. 数据写进 volume，不写进容器可写层（COW 慢且随容器删除丢失）
4. 生产容器配资源上限（memory/cpu），防止单容器拖垮宿主
5. 非必须不给 privileged，root 容器加 user namespace 降权
6. 理解 namespace/cgroups 再上手编排工具，排查问题能直击本质

### 踩坑记录

```text
坑 1：把容器当虚拟机用，往里塞 sshd + 多个服务
结论：容器越用越像虚拟机，失去轻量优势还难维护。
原因：没理解容器是「单进程隔离」模型，沿用虚拟机「一机多服务」思维。
解法：一个容器一个进程，多服务用多容器 + 编排（[[21.4-容器编排基础]]）。

坑 2：数据写在容器可写层，删容器就丢
结论：容器一删数据没了。
原因：容器可写层随容器生命周期销毁，写时复制层不是持久存储。
解法：持久数据用 volume / bind mount 挂载，别写进镜像或可写层。

坑 3：没配内存上限，容器内存泄漏拖死宿主
结论：一个容器 OOM，全宿主机服务全挂。
原因：没设 cgroup 内存限制，容器内存失控时内核只能杀宿主进程。
解法：docker run 配 --memory，或 K8s 里设 resources.limits。

坑 4：容器内 root 逃逸拿到宿主权限
结论：容器被攻破后攻击者获得宿主 root。
原因：默认容器内 root 就是宿主 root，没有 user namespace 降权，逃逸即提权。
解法：开 user namespace / 非 root 运行 / seccomp+AppArmor 收紧系统调用。

坑 5：镜像层数过多，拉取和启动都慢
结论：镜像体积大、构建慢、分发慢。
原因：每条 RUN 都是一层，装一个包用了几十条 RUN 指令。
解法：合并 RUN 指令（&& 连接）、多阶段构建、选 alpine 等精简基础镜像。
```
