## 概述

综合调优工具是「性能分析的终极武器」：perf（内核采样，看 CPU 热点）、bcc/bpftrace（基于 eBPF，动态追踪内核和用户态）、火焰图（可视化热点，一眼看出瓶颈函数）。从「系统慢」到「定位到具体函数」就靠这套工具链。核心思想：采样 + 追踪 + 可视化，把「哪慢」精确到「哪个函数慢」。

```text
综合调优工具链：
1. perf —— 内核采样分析，CPU 热点
2. eBPF —— 内核可编程，bcc/bpftrace 基于它做动态追踪
3. 火焰图 —— 可视化热点，火焰越长越耗时
```

```text
# 实测（本机 perf 已装）
$ perf --version
perf version 7.0.12
```

## perf

perf 是内核级性能分析工具，采样「CPU 在哪个函数上耗时」，生成热点报告。核心用法：`perf top`（实时热点）、`perf record` + `perf report`（采样 + 报告）、`perf stat`（统计 CPU 周期/缓存/分支）。能精确定位「哪个进程哪个函数在耗 CPU」，是 CPU 性能分析的终极工具。

```shell
perf top                   # 实时看热点函数
perf stat ./myapp          # 统计（CPU 周期、缓存缺失、分支）
perf record -g ./myapp     # 采样 + 记录调用栈
perf report                # 生成热点报告
perf record -g -p <PID> -- sleep 10 && perf report   # 分析运行中进程
```

```text
perf 三大用法：
1. perf top —— 实时热点（哪个函数在耗 CPU）
2. perf stat —— 统计（周期/缓存/分支）
3. perf record + report —— 采样记录 + 离线报告
```

## bcc 与 bpftrace 与 eBPF

eBPF 是「内核里的安全虚拟机」——允许在不改内核的情况下，动态挂载程序追踪内核/用户态事件。bcc 和 bpftrace 是 eBPF 的工具集：bcc 提供现成工具（execsnoop 看进程启动、biolatency 看 IO 延迟、tcplife 看 TCP 连接），bpftrace 是高级脚本语言（快速写追踪脚本）。用途：动态追踪系统行为，排查「常规工具看不到」的问题。

```shell
# bcc 工具（需装 bpfcc-tools）
execsnoop                 # 追踪进程 exec（谁启动了新进程）
biolatency                # 磁盘 IO 延迟分布
tcplife                   # TCP 连接生命周期
# bpftrace 脚本
bpftrace -e 'tracepoint:syscalls:sys_enter_open { printf("%s %s\n", comm, str(args->filename)); }'
```

```text
eBPF 家族：
1. eBPF —— 内核安全虚拟机，动态挂载追踪程序
2. bcc —— 现成工具集（execsnoop/biolatency/tcplife）
3. bpftrace —— 脚本语言，快速写追踪脚本
```

## 火焰图

火焰图（flame graph）是「性能采样的可视化」——横轴是函数占比（越宽越耗时），纵轴是调用栈（越深调用越深），颜色区分类型。一眼看出「哪个函数最耗时」：火焰最宽的地方就是热点。生成：perf record 采样 → perf script 转文本 → FlameGraph 脚本生成 SVG。是性能分析的「必学可视化」——报告里贴一张火焰图，比一堆数字直观。

```shell
# 生成火焰图流程
perf record -g ./myapp
perf script > out.perf
# 用 Brendan Gregg 的 FlameGraph 脚本
stackcollapse-perf.pl out.perf > out.folded
flamegraph.pl out.folded > flame.svg
```

```text
火焰图读法：
1. 横轴 —— 函数耗时占比（越宽越耗时）
2. 纵轴 —— 调用栈（从下到上是调用链）
3. 热点 —— 最宽的平台就是瓶颈函数
4. 颜色 —— 区分类型（用户态/内核态/不同模块）
```

## 应用场景实战

### 场景一：系统慢，用火焰图定位瓶颈函数

```shell
# 1. perf 采样（记录调用栈）
perf record -g -p <PID> -- sleep 30
# 2. 生成火焰图
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
# 3. 打开 flame.svg，看最宽的函数 = 瓶颈
```

### 场景二：用 bpftrace 追踪特定系统调用

```shell
# 追踪谁在打开文件
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
# 追踪 IO 延迟（bcc biolatency）
biolatency -m
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先 top/vmstat 定位方向，再用 perf/bcc 深入定位函数
2. 火焰图是性能报告的首选可视化，直观且专业
3. perf record 要 -g（记录调用栈）才能生成火焰图
4. eBPF 工具（bcc/bpftrace）排查「常规工具看不到」的动态行为
5. 生产环境采样用「限时采样」（-- sleep N），别一直开着

### 踩坑记录

```text
坑 1：perf record 没加 -g，生成不了火焰图
结论：perf record 采样了，但生成火焰图没有调用栈。
原因：没加 -g 参数，没记录调用栈。
解法：perf record -g 记录调用栈。

坑 2：perf 报权限不足
结论：perf record/top 报 permission error。
原因：perf_event_paranoid 限制非 root 采样。
解法：root 执行，或调低 /proc/sys/kernel/perf_event_paranoid。

坑 3：bcc/bpftrace 没装，命令不存在
结论：execsnoop/bpftrace 报 command not found。
原因：bcc/bpftrace 是单独的工具集，要装 bpfcc-tools/bpftrace。
解法：apt install bpfcc-tools bpftrace。

坑 4：eBPF 程序加载失败（内核不支持）
结论：bpftrace 报无法加载 BPF 程序。
原因：内核太老不支持某些 eBPF 特性，或权限不够。
解法：升级内核，或确认内核编译了 BPF 支持。

坑 5：火焰图看反了方向
结论：把火焰图的「宽」当成「调用深」，误判瓶颈。
原因：横轴是耗时占比（宽=耗时），纵轴是调用栈（深=调用链）。
解法：记「最宽的平台 = 最耗时的函数」，不是最深。
```
