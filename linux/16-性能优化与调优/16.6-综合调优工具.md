## 概述

综合调优工具是「性能分析的终极武器」：perf（内核采样，看 CPU 热点）、bcc/bpftrace（基于 eBPF，动态追踪内核和用户态）、火焰图（可视化热点，一眼看出瓶颈函数）。从「系统慢」到「定位到具体函数」就靠这套工具链。核心思想：**采样 + 追踪 + 可视化**，把「哪慢」精确到「哪个函数慢」。

```text
综合调优工具链三层：
1. 采样层 —— perf（perf top / perf stat / perf record + report）
2. 追踪层 —— ftrace（内核自带）、strace（系统调用）、eBPF 动态追踪（bcc / bpftrace）
3. 可视化层 —— 火焰图（FlameGraph，SVG 交互图）
辅助层 —— gdb / pstack / jstack（看线程栈与调试）
```

使用原则：**先 top/vmstat 定方向，再用 perf 定位热点函数，最后用 eBPF/strace/gdb 深入动态行为**。工具本身不产生结论，结论来自对「采样分布 + 调用栈 + 事件序列」的解读。

## 核心概念

### 1. perf

内核级性能分析工具（perf_event 子系统的前端），两大能力：

- **计数（counting）**：`perf stat`，统计 CPU 周期、指令、缓存命中/缺失、分支等硬件事件总数，回答「总量多少、比率多少」。
- **采样（sampling）**：`perf record` + `perf report`、`perf top`，周期性地打断 CPU 记录「当前执行到哪个函数（含调用栈）」，回答「时间花在哪个函数」。

三大用法：

```text
perf top                   —— 实时热点（哪个函数在耗 CPU）
perf stat <命令>           —— 统计（周期/缓存/分支/上下文切换）
perf record -g + report    —— 采样记录 + 离线报告（可生成火焰图）
```

### 2. 采样与计数（sampling vs counting）

- **计数**：硬件计数器累加，开销极小，适合「总量」问题（这条链路 cache miss 多不多、分支预测差不高）。
- **采样**：按固定频率（默认 4000Hz）打断 CPU 记录 PC（程序计数器）和调用栈，统计「每个函数被采到的次数占比」。采样有**统计误差**——采样次数足够多（万级）才可信，采样间隔内的短命函数可能漏掉。
- 两者互补：`perf stat` 说「cache miss 高」，`perf record` 说「高在哪个函数」。

### 3. eBPF

内核里的「安全虚拟机」。允许在不改内核、不重启、不装内核模块的前提下，把用户写的小程序挂到内核 hook 点（kprobe 内核函数、tracepoint 内核事件、uprobe 用户态函数、socket 层等），事件触发时执行并回传数据。关键点：**程序先过 verifier 校验（内存安全、有界循环、指令数受限），再经 JIT 编译成本机指令**，出错不会搞崩内核。

### 4. bcc（BPF Compiler Collection）

eBPF 的 Python/Lua 工具集，提供大量开箱即用的现成工具：

```text
execsnoop    —— 谁在启动新进程（exec 事件）
biolatency   —— 磁盘 IO 延迟分布直方图
tcplife      —— TCP 连接生命周期（四元组/时长/字节数）
opensnoop    —— 谁在打开什么文件
runqlat      —— 调度器运行队列延迟
```

Ubuntu 包名 `bpfcc-tools`，安装后命令带 `-bpfcc` 后缀（`execsnoop-bpfcc`）；Red Hat 系包名 `bcc-tools`，命令不带后缀。

### 5. bpftrace

eBPF 的高级脚本语言（awk 风格），一行命令就能写追踪程序：`PROBE /FILTER/ { ACTION }`。适合快速验证假设（谁在 open 文件、谁在 connect、某函数调用频率），复杂工具用 bcc，临时脚本用 bpftrace。

```text
# bpftrace 脚本结构
bpftrace -e 'PROBE /FILTER/ { ACTION }'
PROBE   —— 挂载点（kprobe:vfs_read / tracepoint:syscalls:sys_enter_openat / uprobe:...）
FILTER  —— 可选，/comm == "nginx"/ 只处理特定进程
ACTION  —— 事件触发时执行（printf 打印 / @map 计数 / hist() 直方图）
```

### 6. ftrace

内核自带的追踪框架（零额外依赖，`/sys/kernel/tracing/`），支持 function tracer（记录每个函数调用）、function_graph（调用图）、事件追踪（tracepoint）、kprobe/uprobe 动态探针。bpftrace 的事件源之一也是 tracepoint；**内核崩了、perf 没装时，ftrace 是兜底**。

### 7. 火焰图（flame graph）

性能采样的可视化，横轴是函数耗时占比（采样次数占比）、纵轴是调用栈（从下到上是调用链），**最宽的平台就是热点函数**。SVG 可交互（点击放大、搜索）。生成链路：

```text
perf record -g 采样 → perf script 转文本 → stackcollapse-perf.pl 折叠调用栈
→ flamegraph.pl 渲染 SVG
```

### 8. strace / ltrace

- **strace**：基于 ptrace 追踪进程的系统调用（参数 + 返回值 + 耗时），回答「程序在调什么系统调用、为什么慢」。
- **ltrace**：追踪动态库函数调用（`printf`、`malloc` 等），**本机未装**（Ubuntu `apt install ltrace`）。
- 局限：ptrace 机制使目标进程大幅变慢（每系统调用两次陷入），**生产环境慎用**；大批量追踪用 `-c` 汇总或改用 eBPF 工具。

### 9. gdb / pstack / jstack

- **gdb**：交互式调试器，可 attach 运行中进程看线程栈（`gdb -p <PID>`）、断点、单步。
- **pstack**：打印进程所有线程的栈（内部就是 gdb 的 `thread apply all bt`），Red Hat 系有包，Ubuntu 无。
- **jstack**：Java 专用，打印 JVM 进程线程栈（含锁信息），定位死锁、线程卡死、CPU 热点线程。

### 10. 调试符号（debug symbols）

perf/gdb 要显示函数名必须能解析符号：

```text
用户态：二进制未 strip（含 .symtab）或装 -dbgsym / -debuginfo 包
   ELF 里只有 .dynsym（动态符号）时函数名不全，需要用 addr2line 或装 debuginfo
内核态：/proc/kallsyms（kptr_restrict=1 时非 root 看不到地址）+ 内核 debuginfo 包
   （Ubuntu linux-image-*-dbgsym / Red Hat kernel-debuginfo）
```

## 工作原理

### 1. perf 采样原理（PMU 周期中断）

```text
PMU 硬件计数器每溢出 N 次（周期采样）触发中断
  → 内核记录当前 CPU 的 PC（程序计数器）与寄存器
  → -g 时同时回溯调用栈（fp 帧指针或 dwarf 展开）
  → 中断返回继续执行；样本写入环形缓冲 → perf.data
统计：每个函数被采到的样本数 ≈ 该函数的 CPU 占用比例
```

被采到次数越多 = 占用 CPU 越多，即热点。注意：**采样看的是「CPU 时间」分布**——sleep/IO 等待不占 CPU，不会出现在热点里（这正是「CPU 高但函数全在等锁」这类问题需要锁分析工具的原因）。

### 2. perf stat 计数原理

硬件性能计数器（固定计数器 + 通用计数器）累加事件数，读一次起始值、程序结束再读一次，差值即总量。**计数器数量有限**（现代 x86 每核约 6 个通用计数器），`perf stat` 同时列的事件超过硬件能力时会**分时复用（multiplexing）**，输出里的 `(83.02%)` 百分比就是复用比例——比例越低越不准，可减少事件数或用 `perf stat -M`（Metric 组）。

### 3. eBPF 加载与执行链路

```text
用户写 C（bcc）或 bpftrace 脚本
  → LLVM 编译成 eBPF 字节码
  → 内核 verifier 校验（类型安全、无越界、无死循环、指令数 ≤ 1M）
  → JIT 编译成本机指令（CONFIG_BPF_JIT_ALWAYS_ON=y 实测已开）
  → 挂载到 hook 点（kprobe / tracepoint / uprobe / perf event）
  → 事件触发执行，结果写入 BPF map 或 perf 环形缓冲，用户态读取
```

verifier 校验失败（如未检查的指针解引用、循环边界未知）程序直接拒绝加载，报错信息在内核日志或 bpftrace 的 stderr。

### 4. ftrace 原理

内核编译时在函数入口插入 mcount/fentry 桩（`CONFIG_FTRACE_MCOUNT_USE_CC=y` 实测），运行时通过 `set_ftrace_filter` 指定追踪哪些函数，桩跳转到 ftrace 回调（function tracer 记录调用、function_graph 记录进出栈）。**静态桩只覆盖编译时启用 ftrace 的函数**（`available_filter_functions` 列出），动态 kprobe 用指令改写（int3/断点）挂任意内核函数。

### 5. strace 的 ptrace 原理

```text
ptrace(PTRACE_TRACEME) 或 attach
  → 目标进程每次系统调用进入/退出都停住（SIGTRAP 给 tracer）
  → tracer 读取寄存器拿参数/返回值，打印后继续
代价：每个系统调用两次陷入 + 两次唤醒，进程可能慢 10~100 倍
```

### 6. 火焰图生成链路（实测全通）

```text
perf record -g -o perf.data -- <命令>    # 采样（必加 -g 才有调用栈）
perf script -i perf.data                  # 转文本：每样本一行调用栈
stackcollapse-perf.pl perf.data > out.folded   # 折叠成「栈;栈;栈 计数」
flamegraph.pl out.folded > flame.svg      # 渲染 SVG
```

本机 FlameGraph 脚本未装（`git clone https://github.com/brendangregg/FlameGraph` 即得，脚本是纯 Perl，无需编译）。

## 配置文件解析

工具类没有传统意义上的大配置文件，真正的「配置」是三类：**内核参数**（决定权限与行为）、**调试符号文件**（决定能不能看到函数名）、**脚本/工具本身**（bpftrace 脚本、FlameGraph 脚本）。

### 1. 内核参数（实测本机默认值）

```shell
cat /proc/sys/kernel/perf_event_paranoid   # 本机实测 = 4：采样权限等级
cat /proc/sys/kernel/kptr_restrict         # 本机实测 = 1：是否隐藏内核符号地址
cat /proc/sys/kernel/unprivileged_bpf_disabled  # 本机实测 = 2：非 root 禁加载 eBPF
cat /proc/sys/kernel/yama/ptrace_scope     # 本机实测 = 1：ptrace attach 限制
```

`perf_event_paranoid` 等级含义（值越大限制越严）：

| 值 | 含义 |
|---|---|
| -1 | 无限制（最开放，内核 profiling 也放行） |
| 0 | 禁止非特权用户访问 raw 事件和内核 tracing |
| 1 | 禁止非特权用户访问 CPU 事件（perf stat 用户态计数仍可） |
| 2 | 禁止内核 profiling（内核符号不可采样） |
| 3 | 禁止所有事件访问（非特权 perf 完全不可用） |
| 4 | 6.10+ 内核新增档位，完全禁用非特权 perf（Ubuntu 24.04 实测默认 4） |

本机为 4：**普通用户任何 perf 事件都无法访问**，root（CAP_PERFMON/CAP_SYS_ADMIN）不受影响——上面所有实测均为 root 执行。Red Hat 系（RHEL 8/9）默认是 2 或 3，通常不需要动。

### 2. 内核编译选项（决定工具可用性）

```text
$ grep -E 'CONFIG_BPF|CONFIG_KPROBES|CONFIG_UPROBES|CONFIG_FTRACE|CONFIG_PERF_EVENTS' /boot/config-$(uname -r)
CONFIG_BPF=y          CONFIG_HAVE_EBPF_JIT=y    CONFIG_BPF_SYSCALL=y
CONFIG_BPF_JIT=y      CONFIG_BPF_JIT_ALWAYS_ON=y
CONFIG_BPF_UNPRIV_DEFAULT_OFF=y      # 默认禁非特权 BPF（与 unprivileged_bpf_disabled=2 呼应）
CONFIG_PERF_EVENTS=y  CONFIG_KPROBES=y          CONFIG_UPROBES=y
CONFIG_FTRACE=y       CONFIG_FTRACE_SYSCALLS=y  CONFIG_BPF_EVENTS=y
```

内核没编这些选项时，perf/bpftrace 会直接报事件/探针不支持——先用 `/boot/config-$(uname -r)` 确认，别盲目重装工具。

### 3. 调试符号文件布局

```text
/usr/lib/debug/                 —— debuginfo 包安装位置（Ubuntu/Red Hat 通用约定）
~/.debug/                       —— perf 自动下载/缓存的符号（build-id 目录结构）
/usr/lib/debug/.build-id/xx/xxxx...    —— 按 build-id 组织的符号文件
内核符号：/proc/kallsyms（kptr_restrict=1 时非 root 只有名字没有地址）
```

perf 解析符号失败时按「二进制是否 strip → 是否装 debuginfo → build-id 是否匹配」三步查。

```text
# 多行脚本文件（含变量、map、直方图）
```

## 应用场景实战

### 场景一：进程 CPU 飙高，定位热点函数

```shell
# 1. 找到 CPU 高的进程
top -b -n 1 | head -15          # %CPU 列，记下 PID

# 2. 实时看该进程的热点函数（函数级，比 top 的进程级细一层）
perf top -p <PID> --stdio       # 或交互模式 perf top -p <PID>

# 3. 采样记录调用栈，生成离线报告
perf record -g -p <PID> -- sleep 30
perf report                     # 看 Children/Self 两列定位
# Self 高 = 函数自身耗 CPU（热点本体）；Children 高 Self 低 = 调用方责任

# 4. 结合源码确认（perf annotate 看热点函数的指令级分布）
perf annotate -p <PID>          # 或 perf annotate <符号名>
```

判读：**Self 列最大的函数就是 CPU 花在哪**；如果 Self 分布均匀但 Children 高，说明热点在调用树深处，沿 Children 最高的路径往下钻。

### 场景二：生成火焰图（全流程）

```shell
# 1. 采样（-g 必加；-F 99 调低频率减少开销，99Hz 是经典值）
perf record -g -F 99 -p <PID> -- sleep 60

# 2. 转文本 + 折叠 + 渲染（FlameGraph 脚本需先 git clone）
git clone https://github.com/brendangregg/FlameGraph /opt/FlameGraph
perf script -i perf.data | /opt/FlameGraph/stackcollapse-perf.pl > /tmp/out.folded
/opt/FlameGraph/flamegraph.pl /tmp/out.folded > /tmp/flame.svg

# 3. 浏览器打开 flame.svg：最宽的平台 = 热点；点平台看调用链
```

```text
# 本机实测采样文件（场景一相同的 python 任务）：
$ perf record -g -F 99 -o /tmp/perf.data -- python3 -c 'sum(range(10**8))'
[ perf record: Woken up 8 times to write data ]
[ perf record: Captured and wrote 2.107 MB /tmp/perf.data (15587 samples) ]
```

### 场景三：bpftrace 动态追踪（谁在打开文件 / 谁在读盘）

```shell
# 1. 追踪所有 openat 系统调用，按进程计数（谁在频繁开文件）
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
# 本机 4 秒实测：milvus 179 次、redis-server 40 次、systemd-oomd 36 次

# 2. 追踪 vfs_read 内核函数（读 IO 通用入口），按进程计数
bpftrace -e 'kprobe:vfs_read { @[comm] = count(); }'

# 3. 看打开的具体文件名（过滤只输出自己关心的进程）
bpftrace -e 'tracepoint:syscalls:sys_enter_openat
             /comm == "nginx"/
             { printf("%s -> %s\n", comm, str(args->filename)); }'

# 4. 磁盘 IO 延迟直方图（等价 bcc 的 biolatency）
bpftrace -e 'kprobe:blk_account_io_start { @start[tid] = nsecs; }
             kprobe:blk_account_io_done /@start[tid]/ {
                 @usecs = hist((nsecs - @start[tid]) / 1000);
                 delete(@start[tid]); }'
```

bpftrace 与 strace 的取舍：**strace 全量追踪会让进程慢 10 倍以上**，bpftrace 的 kprobe/tracepoint 挂载几乎无感（事件触发才执行），生产环境排查首选 bpftrace；strace 适合短时间、少量进程的精确参数/返回值观察。

### 场景四：strace 排障（程序启动失败 / 突然变慢）

```shell
# 1. 程序启动失败但没报错信息：看最后的系统调用和 errno
strace -f -o /tmp/app.strace ./myapp
tail -20 /tmp/app.strace          # 最后失败的调用（ENOENT/EACCES/EPIPE...）

# 2. 只看文件访问类调用（排查配置文件/日志路径问题）
strace -f -e trace=openat,statx ./myapp

# 3. 变慢：按耗时排序找最慢的系统调用（-c 汇总 + -T 单次耗时）
strace -c -T ./myapp 2>&1 | sort -k3 -rn | head
# seconds 列最大的 syscall 就是慢点（常见：fsync/select/connect 超时）

# 4. 看网络连接行为（connect/accept 失败排查）
strace -f -e trace=connect,accept,read,write -p <PID>
```

## 性能与调优

### 1. 采样频率与开销

- `perf record` 默认 4000Hz（每核），生产环境建议 **-F 99 或 -F 199**（每核每秒 99/199 次），开销可忽略且样本数足够统计。
- 频率越高越准但开销越大；**高频率采样本身会改变被测程序的时序**（Heisenbug 效应）。
- 样本量评估：火焰图至少几千样本（每个热点函数 ≥ 数十样本）才可信，样本太少会漏掉短命函数。

### 2. 事件选择（perf record 的 -e）

| 场景 | 事件 |
|---|---|
| CPU 热点（默认） | `cpu/cycles/P`（用户态+内核）或 `cpu-clock` |
| 时间占比（含睡眠等待） | `cpu-clock` / `task-clock` |
| 缓存失效 | `cache-misses`、`cache-references` |
| 分支预测 | `branch-misses`、`branches` |
| 调度/上下文切换 | `sched:sched_switch`、`context-switches` |
| 内存分配 | `kmem:kmalloc`、`kmem:kmem_cache_alloc` |
| 系统调用 | `raw_syscalls:sys_enter`、`syscalls:sys_enter_*` |

### 3. 调用栈采集方式：fp vs dwarf

- **fp（帧指针）**：默认方式，靠 `%rbp` 回溯。**开销小**，但二进制编译时 `-fomit-frame-pointer`（发行版默认开）会导致栈回溯中断，表现为「栈在某个函数断了」。
- **dwarf**：`perf record --call-graph dwarf`，靠调试信息展开栈帧，**栈更完整**，但开销大（每次采样要解 DWARF）。
- 取舍：采样服务进程（发行版二进制）优先 `--call-graph dwarf,16384`；自己编译且开了帧指针（`-fno-omit-frame-pointer`）可用默认 fp。
- 也可以不重编译：用 `perf probe` + 手动 unwind，或直接接受「栈断在中间」的现状（火焰图顶部仍然准确）。

### 4. 符号解析提速

- 采样时 `perf record` 会同步读所有进程的 maps 文件（本机实测报 maps 超时），进程多时加 `--proc-map-timeout 5000`。
- 报告时 `perf report --symfs <符号目录>` 指定外部符号；`perf buildid-cache -a <二进制>` 手动登记符号。
- 内核符号被 kptr_restrict 隐藏时 root 不受影响；非 root 调 `perf_event_paranoid` 到 ≤2 且 `kptr_restrict=0` 才能看内核栈（生产不建议放开）。

### 5. eBPF 程序自身开销

- eBPF 程序挂在**事件热路径**上（如每包、每系统调用），逻辑越重放大效应越明显：`tracepoint:syscalls:sys_enter_*` 全量挂载 + 重逻辑会把系统调用吞吐打下来。
- 控制手段：filter 前置（`/comm == "nginx"/`）、map 计数代替逐事件 printf、`bpftrace -c <命令>` 限定追踪窗口。
- verifier 限制指令数（旧内核 4096，新内核放宽到 100 万），复杂逻辑拆多个探针或用 bcc 的 C 程序。

### 6. 火焰图瘦身

- 合并调用：`stackcollapse-perf.pl --all` 合并所有线程；`--inline` 展开内联。
- 过滤噪声：`perf report` 里 `--percent-limit 0.5` 只看占比 >0.5% 的符号；折叠后用 grep 去掉已知噪声栈。
- Java 火焰图：`perf record -g -F 99 -p <JAVA_PID> -- sleep 30` + `stackcollapse-perf.pl` 后接 `stackcollapse-jstack.pl`（JIT 符号需 `-XX:+PreserveFramePointer` 或 perf-map-agent）。

### 7. 工具链选型速查

```text
症状                          → 首选工具
CPU 高、找热点函数            → perf top / perf record -g + 火焰图
整机慢、方向不明              → top/vmstat → perf record -a -g
进程启动失败/文件路径问题     → strace -f -e trace=openat
谁在读写文件/网络/磁盘        → bpftrace（kprobe/tracepoint）或 bcc 工具
线程卡死/死锁                → jstack（Java）/ gdb thread apply all bt（C/C++）
内核函数调用链               → ftrace function_graph 或 bpftrace kprobe
缓存/分支硬件指标            → perf stat -e cache-misses,branch-misses
锁竞争/调度延迟              → perf lock / perf sched / runqlat(bcc)
```

## 安全与权限

### 1. perf_event_paranoid 等级（权限模型）

本机实测默认 **4**（Ubuntu 24.04 + 6.10+ 内核）：非特权用户完全无法使用 perf。生产环境**不要为了调试把 paranoid 降到 0/-1**——perf 的采样能力可被用来读内核符号地址（配合漏洞利用）、侧信道测量其他进程（如密钥处理时间）。正确做法：

- 临时排查用 root / sudo；长期授权给运维账号加 **CAP_PERFMON**（`setcap cap_perfmon+ep <工具>` 或 systemd AmbientCapabilities）。
- 只放开必要能力：采样用户态（paranoid≤3）与采样内核（paranoid≤2）权限不同，按需最小化。

### 2. kptr_restrict 与内核符号

`kptr_restrict=1`（本机实测）时，非特权进程读 `/proc/kallsyms` 只能看到 `0000000000000000`，perf 报告里内核符号退化为地址——**这是防泄漏设计**（内核基址是 KASLR 的核心机密），不是 perf 坏了。root 不受影响（实测 perf report 能看到 `[kernel.kallsyms]` 符号名，但地址仍显示）。

### 3. eBPF 加载权限

- `unprivileged_bpf_disabled=2`（本机实测）：非特权用户无法加载 eBPF 程序，且该值由内核启动参数固定（`CONFIG_BPF_UNPRIV_DEFAULT_OFF=y` 也印证内核默认关闭非特权 BPF）。
- 加载 eBPF 需要 **CAP_BPF**（+ CAP_PERFMON/CAP_SYS_ADMIN 视 hook 类型），容器内需要特权模式或 `--cap-add BPF`，k8s 下用特权 DaemonSet 或 seccomp profile 放开。
- 为什么默认关：eBPF 程序能读内核任意内存（helper 限制下仍强），非特权 BPF 是历史攻击面（如 Spectre 缓解前的 retpoline 绕过）。

### 4. verifier：eBPF 的安全边界

verifier 保证：内存访问有界（数组越界拒绝）、指针不能任意泄漏、循环有界或带 bound、指令数受限。**eBPF 程序崩溃/出错只影响自身，不会 panic 内核**——这是与内核模块的本质区别（内核模块写错直接 oops/panic）。代价是 verifier 通过率低、复杂程序要改写，这是「安全换表达力」的取舍。

### 5. ptrace 权限（strace/gdb 的 attach 门槛）

`yama/ptrace_scope=1`（本机实测）：**非 root 只能 attach 自己的子进程**（不能 attach 别人的进程），防 ptrace 窃取（注入读取 SSH 密钥等）。root 不受限（`CAP_SYS_PTRACE`）。容器内 gdb/strace 默认只能调容器内进程——宿主机 attach 容器进程会像实测那样拿到「不同 PID 命名空间」警告。

### 6. 调试符号与信息泄露

生产二进制**建议 strip + 单独保管 debuginfo**（内部用），避免把符号表直接暴露给攻击者；perf 调试用 `/usr/lib/debug` 的 debuginfo 包即可。内核符号同理：生产不装 kernel-debuginfo，排查时才装。

### 7. Red Hat 系差异

RHEL/CentOS 默认启用 SELinux（targeted），`deny_ptrace` 布尔值默认关但部分策略会拦 `ptrace_attach`，perf attach 服务进程可能被 AVC 拒绝（日志在 `/var/log/audit/audit.log`），需要 `setsebool -P deny_ptrace 0` 或写自定义策略。Ubuntu 默认 AppArmor 对 perf/strace 无额外拦截（实测 root 直接可用）。

## 故障排查

### 案例一：perf 报权限不足（Permission error）

```shell

#   Error: You may not have permission to collect stats.
#   Consider tweaking /proc/sys/kernel/perf_event_paranoid
# 1. 查当前等级
cat /proc/sys/kernel/perf_event_paranoid      # 本机实测 = 4（最严）
# 2. 解决（按优先级）
sudo perf record -g ...                       # ① root 执行（推荐，不改变系统配置）
sudo sysctl -w kernel.perf_event_paranoid=2   # ② 临时放开到「禁内核 profiling」档
echo 2 > /proc/sys/kernel/perf_event_paranoid # ③ 或直接写（重启失效）
# ④ 长期授权：setcap cap_perfmon+ep /usr/bin/perf 或 systemd AmbientCapabilities=CAP_PERFMON
# ⑤ 持久化：/etc/sysctl.d/99-perf.conf 写 kernel.perf_event_paranoid=2
```

注意：把 paranoid 降到 2 以下才能采样内核态（能看到 `[kernel.kallsyms]` 的栈）；只排查用户态程序用 3 即可。

### 案例五：perf record 采样量异常（0 样本 / 大量 lost）

```shell
# 症状1：perf record 结束显示 (0 samples)
#    事件选错或进程已退出：先 perf top -p <PID> 确认有事件；
#    cpu-clock 事件对纯睡眠进程也几乎无样本（sleep 不占 CPU，正常）
# 症状2：perf top 显示 lost: N/N（样本丢失）
#    采样频率太高或 ring buffer 太小：
perf record -g -F 99 ...                  # 降频率
perf record -m 64 ...                     # 加大 mmap 缓冲（页数，默认约 1MB）
# 症状3：perf record 报 "perf_event_open failed" / "Operation not permitted"
#    cgroup/容器限制（memory.max、pids.max）或 seccomp 过滤了 perf_event_open

#    该线程是 JIT（JVM/Node/V8）或动态生成代码：JVM 加 -XX:+PreserveFramePointer

```

## 常见问题

```text
Q1: perf top 和 top 命令的区别？
A: top 看「进程级别」的 CPU 占用，perf top 看「函数级别」的热点——能看出
   是进程里哪个函数在耗 CPU。排查顺序通常是 top 找进程 → perf top -p 找函数。

Q2: eBPF 和普通内核模块有什么区别？
A: eBPF 程序先经过 verifier 校验（类型安全、无死循环、指令数受限），在
   沙箱内运行，出错/崩溃不影响内核，且无需编译安装即可动态加载；内核模块
   直接进内核地址空间，写错直接 oops/panic，加载还要匹配内核版本。代价是
   eBPF 表达力受限（不能任意循环、不能随意访问内存）。

Q3: 火焰图怎么看？
A: 横轴宽 = 该函数占用采样比例（耗时），纵轴深 = 调用链（从下到上是调用
   者关系）。最宽的平台就是瓶颈函数，往上叠的是它的调用者。注意是「宽」
   不是「深」——窄而高的尖塔是深调用链但占比小，不是瓶颈。

Q4: perf record 为什么要 -g？
A: -g 记录调用栈（call graph）。没有栈就看不到调用链，只能统计到顶层
   函数（如 libc 的入口），无法定位「哪个调用路径」在耗 CPU，也无法生成
   火焰图。生产二进制默认 -fomit-frame-pointer 时建议 --call-graph dwarf。

Q5: 生产环境能用 perf 吗？开销多大？
A: 能，但要点：① 权限——root 或 CAP_PERFMON，别降 paranoid 到 2 以下
   （会开放内核符号采样）；② 频率——-F 99 限频，开销可忽略；③ 限时——
   -- sleep N 只采一段时间，别长挂；④ 结果及时清理 perf.data（可能数百 MB）。

Q6: strace 让程序慢很多，为什么？怎么办？
A: ptrace 机制让目标进程每次系统调用都陷入 tracer 两次（进入+退出），
   系统调用密集的程序可能慢 10~100 倍。替代：bpftrace/bcc 的 tracepoint
   挂载（几乎无感）；strace 只用 -c 汇总或短时间窗口；或 strace -e 只追踪
   关心的系统调用类型减少干扰。

Q7: 装了 debuginfo 包还是看不到函数名？
A: 三步查：① build-id 是否匹配——perf buildid-list 与文件的实际 build-id
   比对（perf buildid-cache -a 手动登记）；② 符号路径——perf report --symfs
   或 ~/.debug 缓存；③ 内核符号——kptr_restrict=1 时非 root 无地址，root
   不受影响；JIT 代码（JVM）需 -XX:+PreserveFramePointer + perf-map-agent。

Q8: perf stat 里某些事件显示 <not counted> 是什么？
A: 事件与 NMI watchdog 冲突（watchdog 占用了硬件计数器），或事件在
   当前 CPU 上不支持。本机实测 sleep 1 的 instructions 即 <not counted>
   （nmi_watchdog=1）。解法：临时 echo 0 > /proc/sys/kernel/nmi_watchdog
   释放计数器，测完恢复；或换用 perf stat -e task-clock 等不受影响的计数。

Q9: 容器里能用 perf/bpftrace 吗？
A: 默认受限：perf_event_open 可能被 seccomp 拦、cgroup 限制采样对象；
   bpftrace 需要 CAP_BPF/CAP_SYS_ADMIN；gdb/strace attach 只能碰容器内
   进程（PID 命名空间隔离）。生产容器建议在宿主机对容器进程做 perf 采样
   （root + -- sleep N 限时），或给专用排查容器加特权。

Q10: 怎么判断「CPU 高」是业务问题还是系统问题？
A: perf record -a -g 全系统采样后看热点分布：热点在业务进程用户态函数
   → 业务代码问题；在内核函数（如 tcp_sendmsg、_raw_spin_lock、do_sys_open）
   → 系统层问题（网络/IO/锁）；分布均匀且伴随高 iowait → IO 瓶颈。
   配合 mpstat/vmstat 的 us/sy/wa 列先定方向。
```

## 面试题

```text
1. perf 的采样原理是什么？和计数（counting）有什么区别？
   答：perf 采样是 PMU 硬件计数器每溢出 N 次触发中断，内核记录当前 CPU
   的 PC（及 -g 时的调用栈），统计每个函数被采到的次数占比，次数多 =
   CPU 热点；计数（perf stat）是硬件计数器累加事件总量。采样回答「时间
   花在哪」，计数回答「总量多少」；采样有统计误差，计数受计数器数量限制
   （多事件时分时复用）。

2. eBPF 为什么安全（相比内核模块）？
   答：eBPF 程序先经过 verifier 静态校验——类型安全、内存访问有界、循环
   必须有界、指令数受限、指针不能任意泄漏——再经 JIT 编译在受限上下文
   执行，出错只影响自身，不会导致内核崩溃；而内核模块直接运行在内核
   地址空间，写错直接 oops/panic。eBPF 的代价是表达力受限。

3. 火焰图的横轴和纵轴分别代表什么？怎么快速定位瓶颈？
   答：横轴是函数耗时占比（采样次数占比，越宽越耗时），纵轴是调用栈
   （自下而上为调用链）。最宽的平台即瓶颈函数；沿最宽平台向上看是它的
   调用者，向下看是它的被调用者。注意宽≠深：窄而高的塔是深调用链但占比
   小。

4. 定位「某个进程 CPU 飙高」的完整工具链？
   答：top 找进程 → perf top -p <PID> 找热点函数（函数级）→ perf record -g
   -F 99 -p <PID> -- sleep 30 采样 → perf script + stackcollapse-perf.pl +
   flamegraph.pl 生成火焰图 → 结合源码定位。注意发行版二进制帧指针被优化
   掉时用 --call-graph dwarf。

5. bpftrace 和 strace 的适用场景与取舍？
   答：strace 基于 ptrace，能精确看到系统调用参数与返回值，但让目标进程
   慢 10~100 倍，适合短时间、小进程的精确观察；bpftrace 基于 eBPF，挂
   kprobe/tracepoint 几乎无性能影响，能追踪内核函数和统计分布（直方图、
   map 计数），适合生产环境动态追踪。经验法则：生产用 bpftrace，调试台
   用 strace。

6. perf_event_paranoid 是什么？生产环境怎么设？
   答：perf 采样权限等级，值越大限制越严：-1 全开、2 禁内核 profiling、
   3 禁所有事件、4（6.10+ 内核新增，Ubuntu 24.04 默认）完全禁非特权 perf。
   生产环境不建议降到 2 以下（内核符号采样是攻击面）；排查用 root 或给
   工具 CAP_PERFMON，服务授权用 systemd AmbientCapabilities。

7. 火焰图生成的全流程命令？
   答：perf record -g -F 99 -p <PID> -- sleep 30；perf script -i perf.data；
   stackcollapse-perf.pl 折叠成「栈路径 计数」；flamegraph.pl 渲染 SVG。
   数据源不限于 perf——bpftrace 采样、jstack 线程栈、dtrace 输出都能折叠
   成火焰图（stackcollapse-* 系列脚本）。

8. 内核里怎么确认 perf/eBPF 可用？（没有工具时的判断）
   答：查 /boot/config-$(uname -r)：CONFIG_PERF_EVENTS=y、CONFIG_BPF=y、
   CONFIG_BPF_SYSCALL=y、CONFIG_KPROBES=y、CONFIG_UPROBES=y、CONFIG_FTRACE=y
   对应 perf/bpftrace/ftrace 的可用性；再查 /sys/kernel/tracing/available_tracers
   与 available_filter_functions（本机实测 10 万+ 函数可追踪）。权限层看
   /proc/sys/kernel/perf_event_paranoid 与 unprivileged_bpf_disabled。
```

## 最佳实践与踩坑记录

### 最佳实践

1. **先 top/vmstat 定方向，再用 perf 定位函数**——直接上 perf 容易在错误的方向上浪费采样时间。
2. **perf record 必加 -g**（记录调用栈），否则没有调用链、没有火焰图；发行版二进制加 `--call-graph dwarf`。
3. **生产采样用限时 + 限频**：`-F 99 -p <PID> -- sleep 30`，采完即删 perf.data（GB 级常见）。
4. **先 perf stat 看方向再 record 深挖**：cache-misses/branch-misses 高的场景，热点函数未必是 CPU 最热的那个。
5. **生产环境动态追踪首选 bpftrace/bcc**，strace 只用于短时间精确观察（ptrace 开销大）。
6. **权限最小化**：root/CAP_PERFMON 采样，不降 paranoid 到 2 以下；kptr_restrict 保持默认。
7. **火焰图是性能报告的首选可视化**：perf + 火焰图（或 Java 的 jstack + 火焰图）输出直观、可交互、可存档。
8. **符号问题先查 build-id 与 debuginfo**：装 debuginfo 包 + `perf buildid-cache`，比对着地址猜函数名高效得多。
9. **排查容器服务用宿主机采样**：宿主机 root `perf record -p <宿主机PID> -- sleep N` 能看到容器进程（含内核栈），比进容器受限环境强。
10. **一次只改一个变量**：采样对比「改前/改后」基线，参数调整（采样频率、事件、dwarf）别混在一次实验里。
11. **Red Hat 系先查 SELinux**：perf attach/strace 被 AVC 拦时先看 /var/log/audit/audit.log，`setsebool -P deny_ptrace 0` 再排查。

### 踩坑记录

```text
坑 1：perf record 没加 -g，生成不了火焰图
结论：perf record 采样了，但生成火焰图没有调用栈，全是一层「秃顶」。
原因：没加 -g 参数，没记录调用栈。
解法：perf record -g 记录调用栈；发行版二进制（fomit-frame-pointer）用 --call-graph dwarf。

坑 2：perf 报权限不足（Permission error）
结论：perf record/top 报 You may not have permission to collect stats。
原因：perf_event_paranoid 限制非 root 采样（本机实测默认 4，最严）。
解法：root 执行；或临时调低 /proc/sys/kernel/perf_event_paranoid 到 2~3；
     长期授权用 setcap cap_perfmon+ep /usr/bin/perf。

坑 3：火焰图看反了方向
结论：把火焰图的「宽」当成「调用深」，误判瓶颈函数。
原因：横轴是耗时占比（宽=耗时），纵轴是调用栈（深=调用链）。
解法：记「最宽的平台 = 最耗时的函数」，不是最深；窄而高的尖塔不是瓶颈。

坑 4：发行版二进制栈回溯中断，火焰图出现断栈
结论：自己编译的程序火焰图完整，服务进程（nginx/java 等）栈在中途断掉。
原因：发行版编译默认 -fomit-frame-pointer，fp 回溯失败。
解法：perf record --call-graph dwarf 重采；或程序编译加 -fno-omit-frame-pointer。

坑 5：bcc/bpftrace 没装或命令不存在
结论：execsnoop/bpftrace 报 command not found。
原因：bcc/bpftrace 是单独的工具集，且 Ubuntu 的 bcc 命令带 -bpfcc 后缀。
解法：Ubuntu apt install bpfcc-tools bpftrace（命令 execsnoop-bpfcc）；
     Red Hat dnf install bcc-tools bpftrace（命令无后缀）。

坑 6：eBPF 程序加载失败（内核不支持或权限不够）
结论：bpftrace 报无法加载 BPF 程序 / Operation not permitted。
原因：内核太老缺 BPF 配置、unprivileged_bpf_disabled=2（本机实测）非 root
     必失败、verifier 拒绝复杂程序。
解法：sudo 执行；/boot/config-$(uname -r) 确认 CONFIG_BPF/KPROBES 配置；
     简化程序（加 filter、拆探针）过 verifier。

坑 7：perf stat 某些事件 <not counted>，误以为机器不支持
结论：perf stat sleep 1 里 instructions 显示 <not counted>，以为是内核问题。
原因：NMI watchdog 占用了硬件计数器（本机实测 nmi_watchdog=1）。
解法：临时 echo 0 > /proc/sys/kernel/nmi_watchdog 释放，测完恢复；或减少
     同时统计的事件数（复用比例 (83%) 越低越不准）。

坑 8：gdb/strace attach 容器进程，栈全是 ?? / 报错
结论：宿主机 gdb -p 容器内 redis，bt 全是裸地址，且报 PID 命名空间警告。
原因：容器内进程与宿主机不在同一 PID/挂载命名空间，gdb 读不到容器里的
     可执行文件与 maps，符号全丢。
解法：进容器内 attach，或用 gdbserver 远程连；perf 采样容器进程反而推荐
     在宿主机做（能看到内核栈）。

坑 9：perf record 采了一堆数据，report 里全是 [unknown]
结论：perf report 大量 [unknown]，热点无法定位到函数。
原因：二进制 stripped 且没装 debuginfo；或 JIT 代码（JVM/Node）无符号；
     kptr_restrict=1 时非 root 的内核符号也只有地址。
解法：装 debuginfo 包 / perf buildid-cache -a 登记符号；JVM 加
     -XX:+PreserveFramePointer + perf-map-agent；内核栈用 root 采样。

坑 10：采样频率拉满导致生产服务抖动
结论：perf record 默认 4000Hz 采生产服务，服务出现可感知延迟抖动。
原因：采样中断本身有开销，频率越高对被测程序的时序干扰越大。
解法：-F 99 限频（火焰图样本量足够）；限时采样；避免在高峰期全系统 -a 采样。
```
