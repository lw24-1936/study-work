## 概述

综合调优工具是「性能分析的终极武器」：perf（内核采样，看 CPU 热点）、bcc/bpftrace（基于 eBPF，动态追踪内核和用户态）、火焰图（可视化热点，一眼看出瓶颈函数）。从「系统慢」到「定位到具体函数」就靠这套工具链。核心思想：采样 + 追踪 + 可视化，把「哪慢」精确到「哪个函数慢」。

```text
综合调优工具链：
1. perf —— 内核采样分析，CPU 热点
2. eBPF —— 内核可编程，bcc/bpftrace 基于它做动态追踪
3. 火焰图 —— 可视化热点，火焰越长越耗时
```

```text
# 实测（本机 perf 已装）
$ perf --version
perf version 7.0.12
```

## 核心概念

1. **perf**：内核级性能分析工具，采样「CPU 在哪个函数上耗时」，生成热点报告。三大用法：`perf top`（实时热点）、`perf stat`（统计 CPU 周期/缓存/分支）、`perf record` + `perf report`（采样 + 离线报告）。
2. **eBPF**：内核里的「安全虚拟机」，允许在不改内核的情况下，动态挂载程序追踪内核/用户态事件。
3. **bcc / bpftrace**：eBPF 的工具集。bcc 提供现成工具（execsnoop 看进程启动、biolatency 看 IO 延迟、tcplife 看 TCP 连接），bpftrace 是高级脚本语言（快速写追踪脚本）。
4. **火焰图（flame graph）**：性能采样的可视化，横轴是函数耗时占比、纵轴是调用栈，最宽的平台就是热点函数。

```text
核心概念：
perf 采样 CPU 热点 + eBPF 动态追踪内核 + 火焰图可视化热点
```

## 工作原理

1. **perf 采样原理**：内核定时器周期性地触发中断，记录「当前 CPU 正在执行哪个函数」（配合 -g 记录调用栈），统计每个函数被采样到的次数。被采到次数越多 = 占用 CPU 越多，即热点。
2. **eBPF 原理**：用户写的追踪程序先过内核 verifier（校验内存安全、无死循环），编译成 eBPF 字节码，挂载到内核 hook 点（kprobe 内核函数、tracepoint 内核事件、uprobe 用户态函数），事件触发时执行并回传数据。
3. **火焰图生成**：`perf record -g` 采样 → `perf script` 转成文本 → `stackcollapse-perf.pl` 把调用栈折叠成「函数→计数」→ `flamegraph.pl` 渲染成 SVG。

```text
工作链路：
perf 采样（定时器中断记录函数栈）→ perf script 转文本 → 折叠调用栈 → flamegraph 生成 SVG
eBPF 程序：verifier 校验 → 字节码挂到 kprobe/tracepoint/uprobe → 事件触发执行
```

## 常用命令与配置

```shell
# perf：CPU 热点分析
perf top                   # 实时看热点函数
perf stat ./myapp          # 统计（CPU 周期、缓存缺失、分支）
perf record -g ./myapp     # 采样 + 记录调用栈（-g 必加，否则没火焰图）
perf report                # 生成热点报告
perf record -g -p <PID> -- sleep 10 && perf report   # 分析运行中进程

# bcc 工具（需装 bpfcc-tools）
execsnoop                 # 追踪进程 exec（谁启动了新进程）
biolatency                # 磁盘 IO 延迟分布
tcplife                   # TCP 连接生命周期

# bpftrace 脚本
bpftrace -e 'tracepoint:syscalls:sys_enter_open { printf("%s %s\n", comm, str(args->filename)); }'
```

```text
perf 三大用法：
1. perf top —— 实时热点（哪个函数在耗 CPU）
2. perf stat —— 统计（周期/缓存/分支）
3. perf record + report —— 采样记录 + 离线报告
```

## 配置文件解析

工具类没有大配置文件，关键是几个内核参数和脚本结构：

```shell
# 影响 perf/eBPF 权限的内核参数
cat /proc/sys/kernel/perf_event_paranoid   # 采样权限等级（0~3，越低越开放）
cat /proc/sys/kernel/kptr_restrict          # 是否隐藏内核地址（影响 perf 解析符号）
cat /proc/sys/kernel/unprivileged_bpf_disabled  # 是否禁非 root 加载 eBPF
```

```text
bpftrace 脚本结构（probe / filter / action）：
bpftrace -e 'PROBE /FILTER/ { ACTION }'
PROBE   —— 挂载点（kprobe:vfs_read / tracepoint:syscalls:sys_enter_open）
FILTER  —— 可选，/comm == "nginx"/ 只处理特定进程
ACTION  —— 事件触发时执行（printf 打印参数/统计 map）
```

```text
perf 相关文件：
perf.data —— perf record 的采样输出（perf report 读它）
~/.debug/ 或 /usr/lib/debug —— 调试符号（perf 解析函数名需要）
```

## 应用场景实战

### 场景一：系统慢，用火焰图定位瓶颈函数

```shell
# 1. perf 采样（记录调用栈）
perf record -g -p <PID> -- sleep 30
# 2. 生成火焰图
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
# 3. 打开 flame.svg，看最宽的函数 = 瓶颈
```

### 场景二：用 bpftrace 追踪特定系统调用

```shell
# 追踪谁在打开文件
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
# 追踪 IO 延迟（bcc biolatency）
biolatency -m
```

## 性能与调优

```text
1. 采样频率 —— perf record 默认 4000Hz，频率越高越准但开销越大；生产环境用默认或调低
2. 限时采样 —— 生产环境用 -- sleep N 限时，别长时间开着采样
3. eBPF 开销 —— eBPF 程序在事件热路径上，verifier 限制指令数和循环，别在超高频事件上挂重逻辑
4. 火焰图调优 —— 加 --call-graph dwarf（比默认 fp 更全的栈帧，需 -g 编译）
```

## 安全与权限

```text
1. perf_event_paranoid —— 值越大限制越严（>=2 不允许非 root 采样其他进程），root 执行或调低
2. eBPF verifier —— 内核校验 eBPF 程序内存安全/无死循环，防恶意程序搞崩内核
3. eBPF 加载权限 —— 需要 CAP_BPF / CAP_SYS_ADMIN（root 或显式授权），unprivileged_bpf_disabled=1 禁非 root
4. kptr_restrict —— 隐藏内核地址，防攻击者用 perf 读内核符号做漏洞利用
```

## 故障排查

```shell
# 1. perf 报权限不足
# 症状：perf record/top 报 permission error
cat /proc/sys/kernel/perf_event_paranoid   # 等级过高
# 解决：root 执行，或 echo 1 > /proc/sys/kernel/perf_event_paranoid

# 2. eBPF 程序加载失败
# 症状：bpftrace 报无法加载 BPF 程序
uname -r                                   # 内核版本是否太老
grep CONFIG_BPF /boot/config-$(uname -r)   # 内核是否编译了 BPF 支持

# 3. 火焰图没有栈帧（只有地址没有函数名）
# 原因：perf record 没加 -g，或二进制没有调试符号
file ./myapp                               # 是否 stripped
```

## 常见问题

```text
Q1: perf top 和 top 命令的区别？
A: top 看「进程级别」的 CPU 占用，perf top 看「函数级别」的热点——能看出是进程里哪个函数在耗 CPU。

Q2: eBPF 和普通内核模块有什么区别？
A: eBPF 经过 verifier 校验、在安全沙箱里运行，出错/崩溃不影响内核；内核模块直接进内核，写错直接 panic。

Q3: 火焰图怎么看？
A: 横轴宽 = 该函数占用采样比例（耗时），纵轴深 = 调用链。最宽的平台就是瓶颈，往上看是它的调用者。

Q4: perf record 为什么要 -g？
A: -g 记录调用栈（call graph），没有栈就没法折叠成火焰图，只能看到顶层函数看不到调用链。
```

## 面试题

```text
1. perf 的采样原理是什么？
   答：内核定时器周期性触发中断，记录当前 CPU 执行的函数（及调用栈），统计每个函数被采样到的次数，次数多 = CPU 热点。

2. eBPF 为什么安全（相比内核模块）？
   答：eBPF 程序先经过 verifier 校验（内存访问安全、无死循环、指令数受限），在沙箱里运行，不会导致内核崩溃。

3. 火焰图的横轴和纵轴分别代表什么？
   答：横轴是函数耗时占比（越宽越耗时），纵轴是调用栈（从下到上是调用链）。最宽的平台即瓶颈函数。

4. 定位「某个进程 CPU 飙高」的完整工具链？
   答：top 找进程 → perf top -p <PID> 找热点函数 → perf record -g 采样生成火焰图 → 结合源码定位到具体函数。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先 top/vmstat 定位方向，再用 perf/bcc 深入定位函数
2. 火焰图是性能报告的首选可视化，直观且专业
3. perf record 要 -g（记录调用栈）才能生成火焰图
4. eBPF 工具（bcc/bpftrace）排查「常规工具看不到」的动态行为
5. 生产环境采样用「限时采样」（-- sleep N），别一直开着

### 踩坑记录

```text
坑 1：perf record 没加 -g，生成不了火焰图
结论：perf record 采样了，但生成火焰图没有调用栈。
原因：没加 -g 参数，没记录调用栈。
解法：perf record -g 记录调用栈。

坑 2：perf 报权限不足
结论：perf record/top 报 permission error。
原因：perf_event_paranoid 限制非 root 采样。
解法：root 执行，或调低 /proc/sys/kernel/perf_event_paranoid。

坑 3：bcc/bpftrace 没装，命令不存在
结论：execsnoop/bpftrace 报 command not found。
原因：bcc/bpftrace 是单独的工具集，要装 bpfcc-tools/bpftrace。
解法：apt install bpfcc-tools bpftrace。

坑 4：eBPF 程序加载失败（内核不支持）
结论：bpftrace 报无法加载 BPF 程序。
原因：内核太老不支持某些 eBPF 特性，或权限不够。
解法：升级内核，或确认内核编译了 BPF 支持。

坑 5：火焰图看反了方向
结论：把火焰图的「宽」当成「调用深」，误判瓶颈。
原因：横轴是耗时占比（宽=耗时），纵轴是调用栈（深=调用链）。
解法：记「最宽的平台 = 最耗时的函数」，不是最深。
```
