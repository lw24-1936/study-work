## 概述

性能分析不是「上来就跑工具」，而是「有方法地定位瓶颈」。核心：性能指标（衡量「慢不慢」）、USE 方法（针对每个资源查利用率/饱和度/错误）、容量规划（提前算资源够不够）、基线（记录正常状态，对比异常）。方法论的价值：避免瞎调优，先找到「真正的瓶颈」再动手。

完整的性能调优走「六步法」：定目标 → 建基线 → 压测复现 → 定位瓶颈 → 实施优化 → 复测验证。每一步都有明确的工具和产出，本文各章节按这条主线展开。

```text
性能分析四要素：
1. 性能指标 —— 延迟、吞吐、利用率（衡量快慢）
2. USE 方法 —— 每个资源查 U（利用率）S（饱和度）E（错误）
3. 容量规划 —— 提前估算资源需求，避免超载
4. 基线 —— 记录正常状态，异常时对比

调优六步法：定目标 → 建基线 → 压测复现 → 定位瓶颈 → 优化 → 复测验证
```

## 核心概念

### 1. 延迟 latency

单次操作的耗时（响应时间、IO 延迟 await）。交互系统关心延迟——用户点一下等多久。延迟还有尾延迟（tail latency）的概念：p99/p999 延迟比平均值更能反映「最差体验」，平均值会被大量快请求拉低，掩盖个别慢请求。

```text
延迟指标速记：
RT（响应时间）＝ 服务处理时间 + 排队时间 + 网络传输时间
平均值掩盖问题，看 p99/p999 尾延迟
```

### 2. 吞吐 throughput

单位时间处理量（QPS、MB/s、请求数/秒）。批处理系统关心吞吐——单位时间能干多少活。吞吐与延迟通常此消彼长：并发压到一定程度后，延迟飙升、吞吐反而下降（拐点即瓶颈点）。

### 3. 利用率 utilization

资源使用百分比（CPU%、%util）。资源告警关心利用率——资源快用满了没。注意区分「平均值」和「峰值」：CPU 平均 50% 但高峰期 100% 的机器，告警阈值要按峰值设计。

### 4. USE 方法

对每个资源（CPU/内存/磁盘/网络）依次查「利用率 U、饱和度 S、错误 E」三个问题，系统地排查不遗漏。由 Brendan Gregg 提出，是性能定位的黄金法则：

- U（Utilization）：资源忙不忙（CPU%、内存使用、磁盘 %util）
- S（Saturation）：排队多不多（运行队列、内存换出、IO 等待）——「有任务在等资源」比利用率更能反映瓶颈
- E（Errors）：出没出错（网络丢包、磁盘错误、OOM）——错误直接指向故障

```text
USE 方法提问模板（对每个资源问三句）：
U：这个资源用满了吗？
S：有任务在排队等它吗？
E：它有错误吗？
```

### 5. RED 方法

面向「服务」而不是「资源」的监控方法（Tom Wilkie 提出），适合跟踪每个服务的三个指标：

- R（Rate）：每秒请求数
- E（Errors）：每秒错误数（4xx/5xx）
- D（Duration）：请求耗时分布（直方图）

```text
USE vs RED：
USE —— 面向资源（CPU/内存/磁盘/网络），回答「系统哪里是瓶颈」
RED —— 面向服务（请求/错误/耗时），回答「服务健不健康」
配合使用：RED 发现服务变慢 → USE 定位是哪个资源瓶颈
```

### 6. 四黄金信号

Google SRE 定义的四个最核心监控指标，任何系统先保证这四个信号可观测：

1. 延迟（Latency）：请求处理耗时，尤其区分成功/失败请求的延迟
2. 流量（Traffic）：系统承载的请求量（QPS、连接数）
3. 错误（Errors）：显式错误（5xx）和隐式错误（返回 200 但内容错误）
4. 饱和度（Saturation）：资源快满的程度，如 CPU 利用率、队列长度

### 7. 基线 baseline

系统正常状态下的指标记录，异常时对比基线快速发现偏差。没有基线，连「CPU 60% 算不算异常」都判断不了。基线来源：监控系统的历史数据（sar、Prometheus）、上线前的压测记录、同配置机器的横向对比。

```text
基线三要素：
1. 指标集合 —— 固定采集哪些指标（CPU/内存/IO/网络/应用层）
2. 时间段 —— 覆盖业务高峰/低谷的完整周期
3. 更新机制 —— 业务变化后重新打基线
```

### 8. 木桶效应与瓶颈识别

系统性能由最短的那块板决定——瓶颈资源。CPU/内存/IO/网络四类资源中，只要一类饱和，整体性能就上不去。扩容非瓶颈资源毫无收益，先找短板再投钱。

### 9. 80/20 法则

80% 的性能问题集中在 20% 的代码/资源上；20% 的热点请求贡献 80% 的流量。优化时先抓大头：perf/top 排序后处理前几个热点，别在占比 1% 的冷路径上抠细节。

### 10. 单指标陷阱

只看单一指标容易误判：CPU 正常但系统慢，可能是磁盘 IO 排队；内存充足但频繁 swap，可能是应用内存模式问题；load 高不一定是 CPU 忙（含等 IO 的进程）。方法论的价值就是把「单指标直觉」升级成「多指标交叉验证」。

## 工作原理

### 步骤一：明确目标与指标

先回答「用户/业务到底关心什么」：交互系统关心延迟，批处理关心吞吐，容量告警关心利用率。目标没定，后面所有优化都没有评判标准。

```text
产出：指标定义表
系统类型      | 主指标      | 辅助指标
Web 服务      | p99 延迟    | QPS、错误率
批处理任务    | 吞吐        | 单任务耗时、资源利用率
数据库        | QPS/延迟    | 缓存命中率、IO 延迟
```

### 步骤二：建立基线

在正常业务状态下连续采集一段时间的指标，记录「正常值范围」。基线用监控系统长期记录，别只靠临时跑命令——临时采样拿不到「历史趋势」。

```text
工具：sar（历史 CPU/内存/IO）、监控系统（Prometheus + Grafana）、应用日志
产出：基线报告（各指标的正常区间、高峰/低谷时段特征）
```

### 步骤三：压测复现

没有压力就没有数据。用压测工具模拟真实负载（ab/wrk/siege 或业务脚本），把「偶发慢」变成「可复现、可观测」的问题。压测环境要尽量接近生产：同样的配置、同样的数据规模。

```text
工具：ab（简单 HTTP 压测）、wrk（高并发 HTTP）、siege（持续负载）
产出：压测报告（QPS、延迟分布、错误率、各资源利用率）
```

### 步骤四：定位瓶颈

用 USE 方法逐个资源查 U/S/E，找到「U 高或 S 高」的资源，就是瓶颈。再深入该资源定位到进程、函数。

```text
工具：top/vmstat/mpstat（CPU）、free/vmstat（内存）、iostat（磁盘）、ss/netstat（网络）
产出：瓶颈结论（哪个资源 + 哪个进程/函数 + 证据链）
```

### 步骤五：实施优化

针对瓶颈做优化，一次只改一处，改完观察再改下一处。优化手段按代价从小到大：先调参数（配置、内核参数），再改代码/架构（缓存、异步、分布式）。

### 步骤六：复测验证

用与优化前相同的方法重新压测/采样，对比基线量化收益。验证通过的标准：指标改善 + 无副作用（稳定性、其他资源没被拖垮）。

```text
验证三问：
1. 目标指标改善了多少？（对比基线，不是拍脑袋）
2. 其他指标有没有恶化？（延迟好了，吞吐是不是降了）
3. 长时间运行稳定吗？（短期优化不代表长期稳定）
```

### USE 方法四类资源清单

| 资源 | 利用率 U | 饱和度 S | 错误 E | 常用工具 |
|---|---|---|---|---|
| CPU | %Cpu(s) 的 us/sy、mpstat 每核利用率 | 运行队列长度（vmstat r 列、sar -q runq-sz）、load average | 硬错误少见，关注软中断占比 | top、mpstat、vmstat、sar -u、perf |
| 内存 | free 的 used/available、内存占用率 | swap 换入换出（si/so）、页换页率 | OOM 日志、dmesg 的 out of memory | free、vmstat、sar -r、dmesg |
| 磁盘 | iostat 的 %util、busy 时间 | 等待队列长度、await 升高、svctm 对比 | I/O error、dmesg 磁盘错误、smartctl | iostat -x、sar -d、dmesg、smartctl |
| 网络 | 网卡吞吐（sar -n DEV）、带宽占用 | 发送/接收队列积压、TCP 重传率 | 丢包（netstat -i）、CRC 错误、接口 down | sar -n DEV、ss、netstat -i、ethtool -S |

### 瓶颈识别路线图

```text
症状（用户报：系统慢/接口超时/任务跑不完）
  │
  ▼
怀疑资源（CPU？内存？磁盘 IO？网络？——先不猜，用数据说话）
  │
  ▼
工具验证（四资源交叉采样：vmstat 一眼看四类，再分别深入）
  │
  ├─ CPU：us/sy 高 + r 列大 → mpstat 每核 → top 找进程 → perf 找函数
  ├─ 内存：si/so 高、available 低 → free → 找占用大户 → 查 OOM 日志
  ├─ 磁盘：wa 高、%util 高 → iostat -x → 找进程（pidstat -d）→ 查文件/日志
  └─ 网络：吞吐高、重传/丢包 → ss/netstat → 定位连接 → 查应用
  │
  ▼
根因确认（证据链：指标异常 + 对应进程/代码 + 复现实验）
```

## 常用命令与配置

按「先整体后局部」的顺序组织：先一眼看全貌，再深入可疑资源。

```shell
# 整体状态（四个资源各看一眼）
uptime                # load average + 运行时长
vmstat 1 5            # r/b 列（CPU/IO 队列）、si/so（内存）、in/cs（中断/切换）、us/sy/wa（CPU）
free -h               # 内存总量/可用量
iostat -x 1 5         # 磁盘 %util、await
ss -s                 # 网络连接统计

# 分资源深入
top                   # CPU/内存实时，按 %CPU 排序找进程
mpstat -P ALL 1       # 每核 CPU 利用率
pidstat 1 3           # 每个进程的 CPU 占用
sar -u 1 1            # CPU 采样（实时或历史）
sar -q 1 1            # 运行队列与负载
pidstat -d 1          # 每个进程的磁盘 IO
sar -n DEV 1 1        # 网卡流量
```

| 层面 | 命令 | 核心指标 |
|---|---|---|
| 综合 | uptime、vmstat | load、r/b 列、in/cs、us/sy/wa |
| CPU | top、mpstat、pidstat、sar -u | %Cpu(s)、每核利用率、进程 %CPU |
| 内存 | free、vmstat（si/so）、sar -r | available、swap 换入换出 |
| 磁盘 | iostat -x、pidstat -d、sar -d | %util、await、r/s、w/s |
| 网络 | ss、netstat -i、sar -n DEV | 连接数、丢包、重传、吞吐 |

## 配置文件解析

性能数据的历史记录靠 sysstat（sar）采集。Ubuntu/Debian 下由两个文件控制：`/etc/default/sysstat`（总开关）和 `/etc/cron.d/sysstat`（采集周期）。

```text
# /etc/default/sysstat（Debian/Ubuntu，控制是否启用 sar 采集）
ENABLED="false"    # true 才启用采集；Ubuntu 默认 false，需手动改

# /etc/cron.d/sysstat（采集周期，cron 方式）
5-55/10 * * * * root command -v debian-sa1 > /dev/null && debian-sa1 1 1
59 23 * * * root command -v debian-sa1 > /dev/null && debian-sa1 60 2
# 每 10 分钟采一次（debian-sa1 1 1），每天 23:59 汇总（debian-sa1 60 2）

# 历史数据文件
/var/log/sysstat/saNN    # NN = 当月日期，如 sa19 是 19 号的数据
```

```shell
# 看历史资源使用（容量规划的基础数据）
sar -u -f /var/log/sysstat/sa$(date +%d)   # 当天 CPU 历史
sar -r -f /var/log/sysstat/sa$(date +%d)   # 内存历史
sar -d -f /var/log/sysstat/sa$(date +%d)   # 磁盘历史
sar -q -f /var/log/sysstat/sa$(date +%d)   # 运行队列历史
```

```text
sar 配置要点：
1. /etc/cron.d/sysstat 定义采集频率（默认 10 分钟一次）
2. 数据存 /var/log/sysstat/saNN（NN 是日期），定期轮转
3. 容量规划看历史趋势就靠这些采集数据，历史没采 = 事后查不了
```

| 项目 | Ubuntu（本机实测） | RHEL/CentOS |

## 应用场景实战

### 场景一：用 USE 方法系统排查「系统变慢」

对四个资源逐项查 U/S/E，先收集证据再下结论：

```shell
# CPU：利用率 + 运行队列
top && vmstat 1 5
# 内存：使用 + 换出 + OOM
free -h && vmstat 1 5    # 看 si/so
# 磁盘：利用率 + 等待 + 错误
iostat -x 1 5
# 网络：吞吐 + 丢包 + 错误
ss -s && netstat -i
```

判定逻辑：哪个资源的「U 高」或「S 高」就是瓶颈。例：vmstat 的 wa 列 60% + iostat 的 %util 90% → 磁盘瓶颈；us 95% + r 列 16 → CPU 瓶颈；si/so 持续非零 → 内存压力。

### 场景二：记录基线，异常时对比

```shell
# 1. 记录正常基线
uptime && free -h && iostat -x 1 3 > baseline.txt
# 2. 异常时采集同样指标
uptime && free -h && iostat -x 1 3 > current.txt
# 3. 对比找偏差
diff baseline.txt current.txt
```

脚本化之后可以做成定时任务：每小时采一次存成带时间戳的文件，配合监控系统（Prometheus/node_exporter）形成长期基线。注意基线要覆盖业务高峰时段，只采凌晨的低谷数据会高估容量。

### 场景三：压测验证容量

上线前用压测确认系统能扛住预期流量，并找出「拐点」——QPS 不再增长甚至下降的点：

```shell
# 示例：ab 压测 10000 请求、100 并发（本机未装 ab，命令供生产环境参考）
ab -n 10000 -c 100 http://127.0.0.1:8080/api
# 关注输出：Requests per second、Time per request（含 90% 分位）、Failed requests
# 逐步加并发：-c 10 → -c 50 → -c 100 → -c 200，观察延迟拐点
```

```text
压测结果解读：
QPS 随并发线性增长    —— 容量还有余量，继续加压
QPS 增长放缓/下降     —— 到达拐点，此时延迟往往也在飙升
Failed requests > 0   —— 服务已过载或连接被拒
结论示例：8 核 16G 机器，单实例极限 QPS 2000，p99 50ms
```

### 场景四：容量规划，看趋势不看当前值

容量规划回答「什么时候需要扩容」。方法：用 sar 历史数据看增长趋势，按增长率推算达到阈值（通常 70% 预警）的时间。

```shell
# 每周看一眼 CPU 历史趋势
sar -u -f /var/log/sysstat/sa$(date +%d) | awk 'NR>3 {sum+=$8; n++} END {print "平均 idle:", sum/n}'
# 对比本月与上月的日均峰值，算月增长率
```

```text
推算示例：
磁盘使用率当前 60%，月均增长 5% → 达到 85% 需要 (85-60)/5 = 5 个月
结论：4 个月内扩容或清理，预留 1 个月采购/实施周期
注意：趋势推算要排除一次性事件（大版本升级、数据导入），用中位数而非均值
```

### 场景五：性能问题复盘报告模板

每次调优或故障处理后输出复盘报告，沉淀为团队资产：

```text
性能问题复盘报告
一、问题描述（现象 + 影响面 + 时间线）
二、目标指标（延迟/吞吐/利用率，哪个指标不达标）
三、排查过程（USE 方法四资源逐项排除，附证据数据）
四、根因结论（哪个资源 + 哪个进程/函数 + 为什么之前没发现）
五、优化措施（改了什么参数/代码，一次一处）
六、复测结果（优化前后对比数据表）
七、遗留问题与后续动作（监控补点、容量预警、定期压测）
```

## 性能与调优

```text
调优总原则：
1. 先定位再调优 —— 用 USE 方法找到真正的瓶颈资源，别盲目加资源
2. 指标对齐目标 —— 交互系统优化延迟、批处理优化吞吐、告警看利用率
3. 基线驱动 —— 调优前后对比基线，量化「改进了多少」
4. 一次改一处 —— 调优一次只改一个参数，改完观察，避免互相干扰
5. 趋势优先 —— 容量规划看增长率，别只看当前值
6. 先参数后架构 —— 先试内核参数/配置（代价小、可回滚），不行再动架构
```

### 1. 调优优先级：先业务后系统

先确认是不是业务/代码层问题（慢查询、大对象、N+1 查询、锁等待），再动系统层。业务层优化（改一条 SQL、加一个索引、加缓存）的收益通常远大于系统层（调内核参数、换硬件）。系统层调优是兜底，不是第一选择。

### 2. 调优与稳定性权衡

激进调优（如把 swappiness 调到 0、关掉 THP、极限绑核）可能带来短期收益，但副作用常在流量高峰才暴露。原则：生产环境的调优参数要可回滚、有监控、先小流量验证。性能优化和稳定性的平衡点：优化幅度控制在「显著改善 + 不触发新风险」的区间，宁稳勿险。

### 3. 调优前后对比方法论

```text
对比控制变量清单：
1. 同样的压测工具/参数（并发数、请求量、持续时间）
2. 同样的时间段（避开业务高峰差异）
3. 同样的数据规模（缓存冷热、数据量一致）
4. 只改一个变量（本次调优的参数）
5. 多次采样取中位数（排除抖动）
```

只有控制变量，对比才有意义——「昨天加了参数今天变快了」可能只是业务低谷。

### 4. 单指标陷阱的规避

交叉验证是核心：结论必须有两个以上独立指标支持。例：判断 CPU 瓶颈，不能只看 load，要看 r 列 + us/sy + mpstat 每核；判断磁盘瓶颈，不能只看 %util，要看 await 是否随并发升高。指标之间互相印证，误判概率大幅下降。

## 安全与权限

```text
1. sar 数据权限 —— /var/log/sysstat 含性能数据（可能反映业务规模），限定 root 可读
2. 监控采集权限 —— 监控 agent 只给读指标所需的最小权限，别用 root 跑
3. perf 采样权限 —— 采样其他进程需要权限（perf_event_paranoid），别为采样放全权
4. 基线保密 —— 基线反映业务规模与容量，属于内部数据，别外泄
5. 压测安全 —— 压测对生产产生真实负载，先限流/低峰期执行，别压垮生产
6. 报告脱敏 —— 复盘报告中的 IP、实例名、业务量级对外发布前脱敏
```

## 故障排查

### 案例一：系统变慢，定位瓶颈资源

```shell
# 1. 看整体负载
uptime
# 2. 逐个资源查 U/S/E（vmstat 一眼看四类）
vmstat 1 5      # CPU（us/sy/r）+ 内存（si/so）+ IO（wa）
iostat -x 1 5   # 磁盘 await/%util
free -h         # 内存 available
ss -s           # 网络
# 3. 哪个资源 U 高 + S 高，就是瓶颈，再深入该资源
```

典型判定：us 高 + r 大 → CPU；wa 高 + %util 高 → 磁盘；si/so 持续非零 → 内存；重传/丢包 → 网络。

### 案例二：load 高但 CPU 不高

load 包含「等 IO 的进程」。现象：load 10+，但 top 显示 us/sy 很低、id 很高。看 vmstat 的 wa 列：wa 高说明大量进程在等磁盘 IO。此时查 iostat 找慢盘、pidstat -d 找等 IO 的进程，问题在磁盘层。

### 案例三：虚拟机 st 高，宿主机超卖

云主机上 top 的 %Cpu(s) 里 st（steal）高，说明宿主机 CPU 超卖，本机时间片被其他虚拟机抢走。st 高时本机 CPU 利用率虚低（us 低但系统慢），优化本机参数没用，只能换实例规格/迁移宿主机。判定：`top` 看 st 列、`mpstat -P ALL` 看 %steal 列。

### 案例四：iowait 高但磁盘 %util 低

现象：wa 30% 以上，但 iostat %util 只有 20%。常见原因：随机小 IO 多（%util 反映的是「有请求的时间占比」，随机 IO 时设备一直在服务但利用率算不高）；或者瓶颈不在磁盘而在文件系统/存储网络（NFS、云盘）。解法：看 iostat 的 r/s、w/s 与 await 分布，await 高但 %util 低往往是延迟型慢（网络存储），不是吞吐型饱和。

## 常见问题

```text
Q1: load 高一定是 CPU 不够吗？
A: 不一定。load 包含「等 IO 的进程」，load 高可能是 IO 瓶颈（看 vmstat 的 wa 列区分），不是 CPU 问题。

Q2: 性能分析为什么要有方法论？
A: 避免瞎调优。方法论（USE 方法）让你系统地排查，先找到真正的瓶颈再动手，而不是上来就「加内存/换 CPU」。

Q3: 基线有什么用？
A: 基线记录正常状态，出问题时对比基线快速发现「哪里偏离了正常」。没有基线，连「CPU 60% 算不算异常」都判断不了。

Q4: USE 方法和 RED 方法有什么区别？
A: USE 面向资源（CPU/内存/磁盘/网络的利用率/饱和度/错误），RED 面向服务（请求速率/错误/耗时）。RED 发现服务变慢，USE 定位是哪个资源瓶颈，两者配合。

Q5: 只看 CPU 指标会犯什么错？
A: 单指标陷阱。CPU 正常但系统慢可能是磁盘 IO 排队（wa 高）、内存换页（si/so 高）或网络问题。结论要两个以上指标交叉验证。

Q6: 什么时候做压测？
A: 三个时机：上线前容量验证（确认能扛预期流量）、优化前后对比（量化收益）、故障复现（把偶发问题变成可复现问题）。压测要控制变量，别压垮生产。

Q7: 调优后怎么验证有效？
A: 用与优化前相同的方法复测，对比基线：目标指标是否改善、其他指标是否恶化、长时间运行是否稳定。三个都通过才算有效。
```

## 面试题

```text
1. USE 方法是什么？
   答：对每个资源（CPU/内存/磁盘/网络）依次查三个问题——利用率 U、饱和度 S、错误 E，系统地定位瓶颈资源，避免遗漏。利用率高说明资源忙，饱和说明有任务在排队等资源（比利用率更能反映瓶颈），错误直接指向故障。

2. RED 方法与四黄金信号？
   答：RED 面向服务监控：Rate（每秒请求数）、Errors（每秒错误数）、Duration（请求耗时分布）。四黄金信号是 Google SRE 的四个核心指标：延迟、流量、错误、饱和度。两者都强调「先可观测，再优化」。

3. 延迟和吞吐有什么区别？怎么取舍？
   答：延迟是单次操作的耗时（响应时间），吞吐是单位时间处理量（QPS）。交互系统关心延迟，批处理关心吞吐，两者可能冲突（并发高时延迟会升高）。取舍看业务类型，优化前先定主指标。

4. 怎么判断 CPU 是否饱和？
   答：三个指标交叉验证：load average 与 CPU 核数对比（load > 核数说明有进程排队）、vmstat 的 r 列（运行队列长度持续大于核数）、us/sy 占比。注意 load 含等 IO 的进程，需结合 wa 列区分是 CPU 还是 IO 瓶颈。

5. 什么是单指标陷阱？举例说明。
   答：只凭一个指标下结论导致误判。例：CPU 利用率正常但系统慢——实际是磁盘 IO 排队；load 高就加 CPU——实际是 IO 等待；内存 free 少就加内存——实际是缓存策略正常。解法：多指标交叉验证 + 基线对比。

6. 容量规划为什么看趋势不看当前值？
   答：当前值够用不代表将来够用，增长率决定什么时候满。要记录历史趋势 + 预测增长，在达到瓶颈前（如 70% 预警）扩容。一次性事件（大版本升级、数据导入）会污染趋势，要用中位数而非均值。

7. 调优的完整流程是什么？
   答：六步：明确目标与指标 → 建立基线 → 压测复现 → USE 方法定位瓶颈 → 实施优化（一次改一处，先参数后架构）→ 复测验证（控制变量对比基线）。关键纪律：先定位再调优、一次只改一处、验证看数据。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 性能分析先用 USE 方法系统排查，别上来就猜「加内存」
2. 明确「用户关心延迟还是吞吐」，指标不同，优化方向完全不同
3. 建立基线，出问题对比基线快速定位
4. 容量规划看「趋势」不看「当前值」，提前扩容
5. 用监控系统记录历史，别靠临时跑命令
6. 压测控制变量：同样的工具、并发、时间段、数据规模，只改一个变量
7. 结论用两个以上指标交叉验证，避开单指标陷阱
8. 压测负载用 timeout 包裹或结束后确认清理，避免孤儿进程长期占资源

### 踩坑记录

```text
坑 1：上来就调优，没定位瓶颈
结论：系统慢就加内存/换 CPU，结果瓶颈在磁盘 IO。
原因：没先分析瓶颈在哪，盲目调优。
解法：先用 USE 方法定位真正的瓶颈，再针对性调优。

坑 2：load 高就判断 CPU 不够
结论：load 高就加 CPU，结果 load 还是高。
原因：load 包含等 IO 的进程，load 高可能是 IO 瓶颈不是 CPU。
解法：看 vmstat 的 wa（等 IO），wa 高说明是 IO 问题。

坑 3：没基线，出问题不知道「正常值是多少」
结论：CPU 60% 不知道算不算异常。
原因：没记录基线，没有对比参照。
解法：建基线（监控系统记录常态），异常时对比。

坑 4：容量规划只看当前值，忽略增长趋势
结论：磁盘当前够用，3 个月后突然满了。
原因：没看增长率，只看了当前值。
解法：看历史趋势 + 预测增长，提前扩容。

坑 5：性能指标选错（用吞吐衡量交互系统）
结论：批处理系统优化吞吐，但用户关心的是单次延迟。
原因：指标和目标不匹配。
解法：先明确「用户/业务关心什么指标」，再优化。

坑 6：只看单指标，忽略交叉验证
结论：CPU 利用率正常就排除 CPU，实际是 CPU 调度/锁问题。
原因：单指标反映不全面，CPU 利用率低但运行队列长（r 列大）同样是 CPU 瓶颈。
解法：load、r 列、us/sy、mpstat 每核多个指标一起看。

坑 7：调优一次改多个参数
结论：一次改了 5 个内核参数，变快了但不知道是哪个起的作用，出问题也无法回滚。
原因：多个变量同时变化，无法归因。
解法：一次只改一个参数，记录变更清单，逐个验证。

坑 8：压测环境与生产配置不一致
结论：压测 10 万 QPS 无压力，上线被压垮。
原因：压测机配置更高、缓存更热、数据规模更小，结论失真。
解法：压测环境复刻生产（同配置、同数据量、冷缓存），结论注明环境差异。

坑 9：压测负载没清理干净
结论：压测脚本父进程退出，后台忙循环变孤儿进程，负载居高不下持续几小时。
原因：后台子进程未被回收，仍在占用 CPU（本机实测：6 个忙循环跑满 8 核中 6 个，load 冲到 8.89）。
解法：压测命令用 timeout 包裹，结束后 ps 检查残留进程并 kill。
```
