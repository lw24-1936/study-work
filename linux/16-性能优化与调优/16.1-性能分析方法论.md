## 概述

性能分析不是「上来就跑工具」，而是「有方法地定位瓶颈」。核心：性能指标（衡量「慢不慢」）、USE 方法（针对每个资源查利用率/饱和度/错误）、容量规划（提前算资源够不够）、基线（记录正常状态，对比异常）。方法论的价值：避免瞎调优，先找到「真正的瓶颈」再动手。

```text
性能分析四要素：
1. 性能指标 —— 延迟、吞吐、利用率（衡量快慢）
2. USE 方法 —— 每个资源查 U（利用率）S（饱和度）E（错误）
3. 容量规划 —— 提前估算资源需求，避免超载
4. 基线 —— 记录正常状态，异常时对比
```

## 性能指标

性能三个核心指标：延迟（latency，单次操作耗时，如响应时间）、吞吐（throughput，单位时间处理量，如 QPS）、利用率（utilization，资源使用百分比）。三者关系：利用率高 → 延迟可能升高、吞吐可能下降。分析性能先明确「用户关心哪个」——交互系统关心延迟，批处理关心吞吐，资源告警关心利用率。

```text
三大性能指标：
1. 延迟 latency —— 单次耗时（响应时间、IO 延迟 await）
2. 吞吐 throughput —— 单位时间处理量（QPS、MB/s）
3. 利用率 utilization —— 资源使用百分比（CPU%、%util）
```

```shell
# 快速看整体
uptime        # 负载（综合指标）
vmstat 1 5    # CPU/内存/IO 概览
```

## USE 方法

USE 方法（Utilization-Saturation-Errors）是性能分析的黄金法则：对每个资源（CPU/内存/磁盘/网络），依次查三个问题——利用率（Utilization，资源忙不忙）、饱和度（Saturation，资源排队多不多）、错误（Errors，有没有出错）。这样系统地排查，不会漏掉瓶颈。例：CPU 利用率 100% + 运行队列长（饱和）→ CPU 是瓶颈。

```text
USE 方法（对每个资源查三件事）：
U 利用率 Utilization —— 资源用了多少（CPU%、内存使用、磁盘 %util）
S 饱和度 Saturation —— 排队多少（运行队列、内存换出、IO 等待）
E 错误 Errors —— 出没出错（网络丢包、磁盘错误、OOM）
```

```text
# 实测（本机，8 核 + load 0.91，健康）
$ uptime
23:34 up 22 days, load average: 0.91, 0.98, 1.05
$ nproc
8
# load 0.91 < 8 核，CPU 未饱和，系统健康
```

## 容量规划

容量规划是「提前算资源够不够、什么时候要扩容」。思路：记录资源使用趋势 → 预测增长 → 在达到瓶颈前扩容。关键：看「增长率」而不是「当前值」——当前够用但增长快，也要提前规划。用监控系统（Prometheus/Grafana）记录历史趋势，配合容量模型（如「每增长 10% 用户，CPU 需求 +15%」）预测。

```text
容量规划思路：
1. 记录趋势 —— 监控历史数据（CPU/内存/磁盘增长曲线）
2. 预测增长 —— 按业务增长率推算未来需求
3. 提前扩容 —— 在达到瓶颈前（如 70% 就预警）扩容
4. 预留余量 —— 别用到 100% 才加资源
```

```shell
# 看磁盘使用趋势（容量规划的基础数据）
df -h
# 用 sar 看历史资源使用
sar -u -f /var/log/sysstat/sa$(date +%d)
```

## 基线

基线（baseline）是「系统正常状态下的指标记录」——记录了 CPU 常态 20%、内存常态 60%、磁盘 await 常态 5ms 等。有了基线，出问题时「对比基线」就能快速发现异常（CPU 突然 90% = 异常）。基线要定期更新（业务变化后基线也变）。监控告警阈值就是基于基线设的（如基线 CPU 20%，告警设 80%）。

```text
基线的意义：
1. 记录正常态 —— CPU/内存/磁盘的常态值
2. 对比异常 —— 出问题时对比基线，快速发现偏差
3. 告警依据 —— 阈值基于基线设（基线 + 余量）
4. 定期更新 —— 业务变化后重新录基线
```

## 应用场景实战

### 场景一：用 USE 方法系统排查「系统变慢」

```shell
# 对每个资源查 U/S/E
# CPU：利用率 + 运行队列
top && vmstat 1 5
# 内存：使用 + 换出 + OOM
free -h && vmstat 1 5    # 看 si/so
# 磁盘：利用率 + 等待 + 错误
iostat -x 1 5
# 网络：吞吐 + 丢包 + 错误
ss -s && netstat -i
```

### 场景二：记录基线，异常时对比

```shell
# 1. 记录正常基线
uptime && free -h && iostat -x 1 3 > baseline.txt
# 2. 异常时采集同样指标
uptime && free -h && iostat -x 1 3 > current.txt
# 3. 对比找偏差
diff baseline.txt current.txt
```

## 最佳实践与踩坑记录

### 最佳实践

1. 性能分析先用 USE 方法系统排查，别上来就猜「加内存」
2. 明确「用户关心延迟还是吞吐」，指标不同
3. 建立基线，出问题对比基线快速定位
4. 容量规划看「趋势」不看「当前值」，提前扩容
5. 用监控系统记录历史，别靠临时跑命令

### 踩坑记录

```text
坑 1：上来就调优，没定位瓶颈
结论：系统慢就加内存/换 CPU，结果瓶颈在磁盘 IO。
原因：没先分析瓶颈在哪，盲目调优。
解法：先用 USE 方法定位真正的瓶颈，再针对性调优。

坑 2：load 高就判断 CPU 不够
结论：load 高就加 CPU，结果 load 还是高。
原因：load 包含等 IO 的进程，load 高可能是 IO 瓶颈不是 CPU。
解法：看 vmstat 的 wa（等 IO），wa 高说明是 IO 问题。

坑 3：没基线，出问题不知道「正常值是多少」
结论：CPU 60% 不知道算不算异常。
原因：没记录基线，没有对比参照。
解法：建基线（监控系统记录常态），异常时对比。

坑 4：容量规划只看当前值，忽略增长趋势
结论：磁盘当前够用，3 个月后突然满了。
原因：没看增长率，只看了当前值。
解法：看历史趋势 + 预测增长，提前扩容。

坑 5：性能指标选错（用吞吐衡量交互系统）
结论：批处理系统优化吞吐，但用户关心的是单次延迟。
原因：指标和目标不匹配。
解法：先明确「用户/业务关心什么指标」，再优化。
```
