## 概述

性能分析不是「上来就跑工具」，而是「有方法地定位瓶颈」。核心：性能指标（衡量「慢不慢」）、USE 方法（针对每个资源查利用率/饱和度/错误）、容量规划（提前算资源够不够）、基线（记录正常状态，对比异常）。方法论的价值：避免瞎调优，先找到「真正的瓶颈」再动手。

```text
性能分析四要素：
1. 性能指标 —— 延迟、吞吐、利用率（衡量快慢）
2. USE 方法 —— 每个资源查 U（利用率）S（饱和度）E（错误）
3. 容量规划 —— 提前估算资源需求，避免超载
4. 基线 —— 记录正常状态，异常时对比
```

## 核心概念

1. **延迟 latency**：单次操作耗时（响应时间、IO 延迟 await）。交互系统关心延迟——用户点一下等多久。
2. **吞吐 throughput**：单位时间处理量（QPS、MB/s）。批处理系统关心吞吐——单位时间能干多少活。
3. **利用率 utilization**：资源使用百分比（CPU%、%util）。资源告警关心利用率——资源快用满了没。
4. **USE 方法**：对每个资源（CPU/内存/磁盘/网络）依次查「利用率 U、饱和度 S、错误 E」三个问题，系统地排查不遗漏。
5. **基线 baseline**：系统正常状态下的指标记录，异常时对比基线快速发现偏差。
6. **容量规划**：按「增长率」预测资源需求，在达到瓶颈前扩容。

```text
三大性能指标：
1. 延迟 latency —— 单次耗时（响应时间、IO 延迟 await）
2. 吞吐 throughput —— 单位时间处理量（QPS、MB/s）
3. 利用率 utilization —— 资源使用百分比（CPU%、%util）
三者关系：利用率高 → 延迟可能升高、吞吐可能下降
```

## 工作原理

USE 方法（Utilization-Saturation-Errors）是性能分析的黄金法则，核心逻辑是「对每个资源查三件事」：

1. **利用率 Utilization**：资源忙不忙（CPU%、内存使用、磁盘 %util）。忙说明资源被大量使用。
2. **饱和度 Saturation**：排队多不多（运行队列、内存换出、IO 等待）。饱和说明「有任务在等资源」，比利用率更能反映「瓶颈」。
3. **错误 Errors**：出没出错（网络丢包、磁盘错误、OOM）。错误直接指向「故障」。

系统排查就是「先明确用户关心哪个指标 → 用 USE 方法逐个资源查 → 定位瓶颈资源 → 深入该资源」。例：CPU 利用率 100% + 运行队列长（饱和）→ CPU 是瓶颈，再深入看是哪个进程/函数吃 CPU。

```text
USE 方法（对每个资源查三件事）：
U 利用率 Utilization —— 资源用了多少（CPU%、内存使用、磁盘 %util）
S 饱和度 Saturation —— 排队多少（运行队列、内存换出、IO 等待）
E 错误 Errors —— 出没出错（网络丢包、磁盘错误、OOM）
```

## 常用命令与配置

```shell
# 快速看整体
uptime        # 负载（综合指标）
vmstat 1 5    # CPU/内存/IO 概览
# 分资源看
top           # CPU/内存实时
free -h       # 内存
iostat -x 1 5 # 磁盘 IO
ss -s         # 网络
```

```text
# 实测（本机，8 核 + load 0.91，健康）
$ uptime
23:34 up 22 days, load average: 0.91, 0.98, 1.05
$ nproc
8
# load 0.91 < 8 核，CPU 未饱和，系统健康
```

```text
分资源指标采集对照：
CPU   —— top / mpstat / vmstat（us/sy/wa）
内存 —— free -h / vmstat（si/so）
磁盘 —— iostat -x（await/%util）
网络 —— ss / netstat -i（丢包/错误）
```

## 配置文件解析

性能数据的历史记录靠 sysstat（sar）采集，配置在 /etc/sysstat/ 和 /etc/cron.d/sysstat：

```text
# /etc/default/sysstat（Debian/Ubuntu，控制是否启用 sar 采集）
ENABLED="true"

# /etc/sysstat/sysstat（RHEL/CentOS）
# 采集间隔（分钟）
# 默认每 10 分钟采集一次，数据存 /var/log/sysstat/saNN
```

```shell
# 看历史资源使用（容量规划的基础数据）
sar -u -f /var/log/sysstat/sa$(date +%d)   # 当天 CPU 历史
sar -r -f /var/log/sysstat/sa$(date +%d)   # 内存历史
df -h                                      # 看磁盘使用趋势
```

```text
sar 配置要点：
1. /etc/cron.d/sysstat 定义采集频率（默认 10 分钟一次）
2. 数据存 /var/log/sysstat/saNN（NN 是日期），定期轮转
3. 容量规划看历史趋势就靠这些采集数据
```

## 应用场景实战

### 场景一：用 USE 方法系统排查「系统变慢」

```shell
# 对每个资源查 U/S/E
# CPU：利用率 + 运行队列
top && vmstat 1 5
# 内存：使用 + 换出 + OOM
free -h && vmstat 1 5    # 看 si/so
# 磁盘：利用率 + 等待 + 错误
iostat -x 1 5
# 网络：吞吐 + 丢包 + 错误
ss -s && netstat -i
```

### 场景二：记录基线，异常时对比

```shell
# 1. 记录正常基线
uptime && free -h && iostat -x 1 3 > baseline.txt
# 2. 异常时采集同样指标
uptime && free -h && iostat -x 1 3 > current.txt
# 3. 对比找偏差
diff baseline.txt current.txt
```

## 性能与调优

```text
1. 先定位再调优 —— 用 USE 方法找到真正的瓶颈资源，别盲目加资源
2. 指标对齐目标 —— 交互系统优化延迟、批处理优化吞吐、告警看利用率
3. 基线驱动 —— 调优前后对比基线，量化「改进了多少」
4. 一次改一处 —— 调优一次只改一个参数，改完观察，避免互相干扰
5. 趋势优先 —— 容量规划看增长率，别只看当前值
```

## 安全与权限

```text
1. sar 数据权限 —— /var/log/sysstat 含性能数据，限定 root 可读（性能数据可能泄露业务信息）
2. 监控采集权限 —— 监控 agent 只给读指标所需的最小权限，别用 root 跑
3. perf 采样权限 —— 采样其他进程需要权限（perf_event_paranoid），别为采样放全权
4. 基线保密 —— 基线反映业务规模，别外泄
```

## 故障排查

### 系统变慢，定位瓶颈资源

```shell
# 1. 看整体负载
uptime
# 2. 逐个资源查 U/S/E
vmstat 1 5      # CPU（us/sy）+ 内存（si/so）+ IO（wa）
iostat -x 1 5   # 磁盘 await/%util
free -h         # 内存 available
ss -s           # 网络
# 3. 哪个资源 U 高 + S 高，就是瓶颈，再深入该资源
```

## 常见问题

```text
Q1: load 高一定是 CPU 不够吗？
A: 不一定。load 包含「等 IO 的进程」，load 高可能是 IO 瓶颈（看 vmstat 的 wa 列区分），不是 CPU 问题。

Q2: 性能分析为什么要有方法论？
A: 避免瞎调优。方法论（USE 方法）让你系统地排查，先找到真正的瓶颈再动手，而不是上来就「加内存/换 CPU」。

Q3: 基线有什么用？
A: 基线记录正常状态，出问题时对比基线快速发现「哪里偏离了正常」。没有基线，连「CPU 60% 算不算异常」都判断不了。

Q4: 延迟、吞吐、利用率三者怎么取舍？
A: 看业务类型——交互系统优化延迟，批处理优化吞吐，资源告警看利用率。三者有取舍，利用率高会牺牲延迟/吞吐。
```

## 面试题

```text
1. USE 方法是什么？
   答：对每个资源（CPU/内存/磁盘/网络）依次查三个问题——利用率 U、饱和度 S、错误 E，系统地定位瓶颈资源，避免遗漏。

2. 延迟和吞吐有什么区别？
   答：延迟是单次操作的耗时（响应时间），吞吐是单位时间处理量（QPS）。交互系统关心延迟，批处理关心吞吐，两者可能冲突（并发高时延迟会升高）。

3. 怎么判断 CPU 是否饱和？
   答：load average 与 CPU 核数对比——load > 核数说明有进程排队（饱和）。但要注意 load 含等 IO 的进程，需结合 vmstat 的 wa 列判断是 CPU 还是 IO 瓶颈。

4. 容量规划为什么看趋势不看当前值？
   答：当前值够用不代表将来够用，增长率决定什么时候满。要记录历史趋势 + 预测增长，在达到瓶颈前（如 70% 预警）扩容。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 性能分析先用 USE 方法系统排查，别上来就猜「加内存」
2. 明确「用户关心延迟还是吞吐」，指标不同
3. 建立基线，出问题对比基线快速定位
4. 容量规划看「趋势」不看「当前值」，提前扩容
5. 用监控系统记录历史，别靠临时跑命令

### 踩坑记录

```text
坑 1：上来就调优，没定位瓶颈
结论：系统慢就加内存/换 CPU，结果瓶颈在磁盘 IO。
原因：没先分析瓶颈在哪，盲目调优。
解法：先用 USE 方法定位真正的瓶颈，再针对性调优。

坑 2：load 高就判断 CPU 不够
结论：load 高就加 CPU，结果 load 还是高。
原因：load 包含等 IO 的进程，load 高可能是 IO 瓶颈不是 CPU。
解法：看 vmstat 的 wa（等 IO），wa 高说明是 IO 问题。

坑 3：没基线，出问题不知道「正常值是多少」
结论：CPU 60% 不知道算不算异常。
原因：没记录基线，没有对比参照。
解法：建基线（监控系统记录常态），异常时对比。

坑 4：容量规划只看当前值，忽略增长趋势
结论：磁盘当前够用，3 个月后突然满了。
原因：没看增长率，只看了当前值。
解法：看历史趋势 + 预测增长，提前扩容。

坑 5：性能指标选错（用吞吐衡量交互系统）
结论：批处理系统优化吞吐，但用户关心的是单次延迟。
原因：指标和目标不匹配。
解法：先明确「用户/业务关心什么指标」，再优化。
```
