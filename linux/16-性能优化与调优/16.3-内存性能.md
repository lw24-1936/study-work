## 概述

内存性能分析回答四个问题：**「内存够不够」「谁在吃内存」「有没有泄漏」「为什么在换出」**。涉及的核心机制：页缓存（page cache，文件缓存，可回收）、内存水位（watermark，触发回收的阈值）、swap（换出到磁盘的匿名页）、缺页故障（page fault，分配/加载内存页）、OOM（内存耗尽杀进程）、NUMA（多节点内存）、大页（HugePages/THP）。

判断内存问题的核心指标：

```text
内存性能四要素：
1. 页缓存 —— 文件缓存，可回收，占满空闲内存是正常行为
2. 内存水位 —— min/low/high 阈值，触发 kswapd 回收
3. swap —— 换出到磁盘，si/so 持续高 = 内存真不够（抖动）
4. 内存分配 —— 进程 malloc/匿名页，泄漏看 RSS 趋势
```

内存问题的两种典型形态：**「不够 → 换出 → 变慢」**（thrashing，系统抖动）和**「泄漏 → 耗尽 → OOM」**（进程被杀）。分析时先看 available（真实可用），再看 si/so（是否在换出），最后用 ps/pidstat 定位大户。

本机是 Ubuntu 24.04（8 核 i5-8300H，19Gi 内存），以下实测数据均来自本机。

## 核心概念

### 1. 页缓存 page cache

文件内容的缓存：读文件时内容先进页缓存，下次读直接命中缓存（实测缓存命中读 1.4GB/s，磁盘读只有 33MB/s，差 40 倍）；写文件时先写进页缓存标记为脏页，由内核后台异步写回磁盘。页缓存**可回收**——内存紧张时内核优先回收它，所以 `MemAvailable`（含可回收缓存）才是真实可用。页缓存尽量占满空闲内存是设计行为，「buff/cache 高」不是问题。

### 2. 匿名页 anonymous page

进程通过 malloc/堆分配的内存（数据段、栈），**没有文件对应**，不能像页缓存那样直接回收，只能换出到 swap。RSS 里大部分是匿名页。判断「谁在吃内存」主要看匿名页（`/proc/meminfo` 的 AnonPages，本机实测 8.8Gi）。

### 3. 内存水位 watermark

内核给每个内存 zone 设 min/low/high 三个水位：

```text
min  —— 低于它：分配时同步直接回收（进程阻塞，最坏情况）
low  —— 低于它：唤醒 kswapd 后台异步回收
high —— 高于它：停止回收
```

实测本机 Normal zone：min 15613 页（约 61Mi）、low 19767、high 23921（4KiB/页）。水位由 `min_free_kbytes` 和 `watermark_scale_factor` 决定。

### 4. swap 与抖动 thrashing

swap 是内存不够时的缓冲：把冷匿名页换出到磁盘（swap 分区/文件），需要时再换入。**si/so（swap in/out）持续高 = 内存真不够、系统在抖动**——内核反复换入换出，磁盘成为瓶颈，系统极慢。本机实测 si/so 为 0，但 swpd 显示历史换出约 480Mi。

### 5. 缺页故障 page fault

进程访问的页不在页表时触发 page fault，分两种：

- **次要缺页 minor fault**：页已在物理内存（页缓存命中、匿名页首次写时复制），只建立映射，快。本机累计 pgfault 32.8 亿次。
- **主要缺页 major fault**：页不在内存，要从磁盘读（冷文件读、swap 换入、mmap 文件首次访问），慢（毫秒级）。本机累计 pgmajfault 仅 4.3 万次，说明基本没有磁盘缺页。

`ps` 的 fault 列、`vmstat` 的 `pgmajfault`、`sar -B` 的 `majflt/s` 都能看。major fault 突增说明内存不足导致频繁磁盘 IO 或冷启动。

### 6. RSS / VSZ / PSS

- **VSZ**：虚拟内存大小（申请了多少，含未实际分配的）。
- **RSS**：常驻物理内存（实际占了多少），内存泄漏看 RSS 趋势。
- **PSS**：按共享比例分摊后的内存（/proc/PID/smaps 每页的 Pss），统计容器/多进程总占用更准。

### 7. NUMA 内存

多路服务器每个 CPU 有自己的本地内存，访问本地快（延迟低）、访问远端慢。`numactl --hardware` 查看节点拓扑，`numastat` 看本地/远端命中。本机单节点（1 node，8 CPU），无远端内存问题。

### 8. HugePages 与 THP

- **显式大页 HugePages**：预分配 2MiB/1GiB 大页，进程通过 mmap(MAP_HUGETLB) 使用，减少 TLB miss。本机 HugePages_Total=0（未配置）。
- **透明大页 THP**：内核自动把连续 2MiB 区域合并成大页（khugepaged 后台扫描）。本机模式为 `madvise`（仅显式建议的映射使用）。数据库场景常关闭或改 madvise（见性能与调优）。

### 9. OOM Killer

内存耗尽且无法回收时，内核选择「最该杀」的进程 SIGKILL。选择依据是 oom_score（内存占用归一化分数 + oom_score_adj 调整值）。关键进程用 `echo -1000 > /proc/PID/oom_score_adj` 保护。

### 10. cgroup 内存限制

容器/服务通过 cgroup 限制内存：cgroup v1 是 `memory.limit_in_bytes`，v2（本机实测 cgroup2fs）是 `memory.max`、`memory.current`、`memory.stat`。超限触发 cgroup 级 OOM（只杀组内进程，不连累整机）。

## 工作原理

### 1. 页缓存与脏页回写

```text
写路径：write() → VFS → 页缓存（标记脏页）→ 后台 flusher 线程异步写回磁盘
读路径：read()  → VFS → 页缓存命中？→ 命中直接返回（不碰磁盘）
                          → 未命中 → 缺页 → 文件系统 → 块层 → 磁盘 → 填充页缓存
```

脏页不会立刻写盘，由 flusher 线程按两种阈值触发：

- `vm.dirty_background_ratio`（实测 10%）：脏页占总内存 10% 时**后台**异步写回，不阻塞应用。
- `vm.dirty_ratio`（实测 20%）：脏页占 20% 时，写进程**同步**阻塞强制写回（防止脏页无限膨胀导致掉电丢数据过多）。

另有时间阈值：`dirty_expire_centisecs`（实测 3000 = 30 秒，脏页超过 30 秒必须写回）、`dirty_writeback_centisecs`（实测 500 = 5 秒，flusher 唤醒周期）。`/proc/vmstat` 里 `nr_dirty`（实测 128 页）、`nr_dirty_threshold`（326861 页）能看当前脏页量。

### 2. 内存回收链与 kswapd

```text
进程要内存（缺页分配）
  → 空闲页足够？直接分配
  → 不够且低于 low 水位 → kswapd 后台异步回收（不阻塞）
  → 不够且低于 min 水位 → 分配路径同步直接回收（direct reclaim，进程阻塞）
  → 回收顺序：干净页缓存（最快）→ 脏页写回后回收 → 匿名页换出到 swap
  → 还是不够 → OOM Killer 杀进程
```

回收时先回收**文件页**（页缓存），因为换出到磁盘要写盘、慢；swap 是最后手段。`/proc/vmstat` 的 `pgscan_kswapd`/`pgsteal_kswapd`（本机实测各约 978 万/937 万次）反映 kswapd 的回收工作量。

### 3. OOM 全流程

触发条件：内核在 direct reclaim 后仍无法满足分配请求（通常同时伴随 order 分配失败）。流程：

1. `out_of_memory()` 被调用；
2. `select_bad_process()` 遍历进程计算 **oom_score**：内存使用量（RSS + swap + 页表等，按整机内存归一化到 0-1000 分）+ `oom_score_adj`（-1000 ~ +1000，直接加减分）；
3. 杀掉得分最高的进程（SIGKILL），记录 dmesg 日志；
4. 若 `panic_on_oom=1`（本机实测 0）则直接内核 panic 重启。

dmesg 输出解读（示例）：

```text
Out of memory: Killed process 1234 (java) total-vm:10485760kB, anon-rss:2097152kB, file-rss:0kB, shmem-rss:0kB, UID:0 pgtables:20480kB oom_score_adj:0
```

要点：`total-vm` 是虚拟内存（大不代表啥），`anon-rss` 是匿名页占用（**判断「谁吃内存」的关键**），`oom_score_adj` 是被杀时的调整值。受害者通常是「占用最大的非特权进程」；`oom_score_adj=-1000` 的进程（如 systemd、sshd）不会被杀。

### 4. NUMA 分配与 THP 合并

- NUMA 默认分配策略是 local-first（优先本地节点），`numactl --interleave` 可交错分配均衡负载。`numastat` 的 `numa_hit`/`numa_miss`/`other_node` 反映远端访问量——miss/other 高说明内存分配与 CPU 节点错位，性能受损。
- THP：khugepaged 后台把相邻的 512 个 4KiB 页合并成 2MiB 大页。好处是 TLB 覆盖范围大 512 倍；坏处是合并需要连续内存、可能触发内存压缩（compaction）导致偶发延迟尖刺，数据库（Oracle/MySQL/PG）场景常见性能抖动，所以常关闭或改 madvise。

### 5. cgroup v2 内存可见性

本机 cgroup2fs（容器环境）。容器内 `free` 看到的是**宿主机**总内存，不是容器限额——这是容器内存可见性的经典误区。要看容器真实用量：

```text
/sys/fs/cgroup/memory.current   当前用量（含 page cache）
/sys/fs/cgroup/memory.max      上限（max = 无限制）
/sys/fs/cgroup/memory.stat     anon/file/slab 细分
```

page cache 在 cgroup 间**共享**：两个容器读同一文件，缓存只计一份，回收时按需回收。

## 应用场景实战

### 场景一：内存不够，定位是「真不够」还是「缓存占满」

```shell
# 1. 看 available（真实可用）——别只看 free 列
free -h

# 2. 看是否在换出（si/so）
vmstat 1 5
# si/so=0 → 只是缓存占满（正常），available 充足就不用管
# si/so 持续高 → 真不够，继续查

# 3. 看内存压力（PSI）
cat /proc/pressure/memory
# some 持续 >60% 说明内存分配在排队，需要加内存或减负载

# 4. 找内存大户
ps aux --sort=-%mem | head
```

判断口诀：**available 高 + si/so=0 = 健康（缓存占满只是表象）；available 低 + si/so 高 = 真不够**。

### 场景二：定位 swap 被谁占用

```shell
# 1. 确认 swap 用量
free -h                    # 交换：480Mi used
# 2. 找每个进程的 VmSwap（谁在 swap 里）
grep -h '^VmSwap:' /proc/[0-9]*/status | sort -t: -k2 -nr | head -5
# 本机实测最大 VmSwap 约 110044 kB（约 107Mi）
# 3. 结合 RSS 看：RSS 小但 VmSwap 大 = 该进程冷页被换出（内存压力下的正常现象）
# 4. 如果 swap 持续增长且 si/so 高 → 加内存或限制大户
```

swap 使用量 ≠ 抖动：**只有 si/so 高才说明在频繁换入换出**；单纯「swap 有占用」说明曾经换出过冷页，未必是问题。

### 场景三：排查内存泄漏

```shell
# 1. 找可疑进程（内存持续涨的）
top -o %MEM
# 2. 持续观察 RSS 是否单调增长（每 5 秒采样）
pidstat -r -p <PID> 5
# 3. 看单进程内存明细（Rss/Pss/Swap 各区域）
cat /proc/<PID>/smaps | grep -E '^(Rss|Pss|Swap):' | head
# 4. Java 进程看堆（GC 后堆不回落 = 泄漏）
jstat -gcutil <PID> 1000
# 5. C/C++ 程序用 valgrind 检测（开发环境）
valgrind --leak-check=full ./your_program
# 或编译时开 ASAN
gcc -fsanitize=address -g your_program.c -o your_program
```

判断标准：**RSS 持续单调增长、GC/重启后不回落 = 泄漏**；涨到某个上限后稳定 = 合理缓存（JVM 堆、连接池）。valgrind 输出看 `definitely lost` / `indirectly lost` 行；ASAN 在程序退出时打印泄漏报告（LeakSanitizer）。

### 场景四：OOM 之后快速定位与防护

```shell
# 1. 确认 OOM 发生与受害者
dmesg | grep -i 'out of memory'
journalctl -k | grep -i -E 'oom|killed process'
# 输出示例：Out of memory: Killed process 1234 (java) total-vm:... anon-rss:2097152kB ...

# 2. 谁的内存最大
ps aux --sort=-%mem | head
# 3. 保护关键进程（数据库/网关，调 oom_score_adj 负值）
echo -500 > /proc/<PID>/oom_score_adj        # 临时
# 持久化：写 /etc/systemd/system/<svc>.service 的 [Service] 段
#   OOMScoreAdjust=-500
# 4. 根治：限制内存大户（cgroup 或调应用 Xmx）
```

注意 dmesg 里 `anon-rss` 是核心证据——被杀进程当时的**匿名页**占用；`oom_score_adj` 说明是否带保护分。

### 场景五：数据库服务器内存调优（swappiness + THP）

```shell
# 数据库场景三件套：
# 1. 降低换出积极度，避免页缓存被换出拖慢查询
sysctl -w vm.swappiness=10
# 2. THP 改 madvise（保留给显式大页应用，避免数据库偶发延迟尖刺）
echo madvise > /sys/kernel/mm/transparent_hugepage/enabled
# 3. 关键进程 OOM 保护
echo -500 > /proc/<db_pid>/oom_score_adj
# 持久化：写入 /etc/sysctl.conf 与 systemd unit
```

本机实测 THP 模式已是 `always [madvise] never`（当前用 madvise），符合数据库推荐配置。

### 场景六：用 cgroup 限制容器/服务内存

```shell
# cgroup v2 示例：给某个服务限 2Gi
mkdir -p /sys/fs/cgroup/my-service
echo 2G > /sys/fs/cgroup/my-service/memory.max
# 把进程放进去
echo <PID> > /sys/fs/cgroup/my-service/cgroup.procs
# 观察
cat /sys/fs/cgroup/my-service/memory.current
cat /sys/fs/cgroup/my-service/memory.stat   # anon/file 细分
# 超限行为：进程组内触发 OOM（只杀组内进程），不会拖垮整机
# 容器场景由 Docker/K8s 自动管理（--memory 参数 → memory.max）
```

## 性能与调优

### 1. swappiness（换出积极度）

```text
Ubuntu/Debian 默认 60，RHEL 7+ 默认 30（更倾向保留页缓存）
调优场景：
  0-10   数据库/缓存服务：尽量别把页缓存换出去（MySQL/Redis/ES）
  10-20  RHEL 文档推荐的通用值（平衡）
  60     桌面/通用默认：换出更积极，留内存给文件缓存
  100    极端：频繁换出（基本没人用）
注意：swappiness 只影响「页缓存 vs 匿名页」的回收偏好，不影响
回写速度；调 0 不意味着完全禁用 swap（内存极端紧张仍会换出）。
```

### 2. overcommit（内存超额分配）

```text
/proc/sys/vm/overcommit_memory：
  0  启发式（默认）：明显超限的分配拒绝，一般超限的放行
  1  总是允许：malloc 永不失败（危险，程序可能因访问未映射内存被杀）
  2  禁止超过 CommitLimit：CommitLimit = swap + RAM × overcommit_ratio%
本机实测：overcommit=0，Committed_AS 31.7Gi > CommitLimit 18.5Gi
（%commit 111%，启发式模式下正常，说明内存分配承诺远超物理内存）
```

`Committed_AS` 是所有进程「承诺」的内存总和（含没实际使用的），超限但能跑正是因为大部分承诺没被兑现。**别被 `sar -r` 的 %commit >100% 吓到**，启发式模式下这是常态。

### 3. min_free_kbytes 与水位

```text
本机实测 67584 KiB（约 66Mi，约整机 0.33%）
调大（如 1%）：内存紧张时更早回收，分配阻塞更少，但可用内存变少
调小：可用内存多，但接近耗尽时分配路径直接回收会卡顿
经验：min_free_kbytes ≈ 内存的 0.5%-1% 在内存压力大的机器上更稳
      （内核默认按 zone 大小自动算，通常不用手动改）
```

### 4. 页缓存与脏页调优

```text
写密集场景（日志采集、批量导入）：
  dirty_ratio 20% 太大 → 脏页堆积，一次性写回造成 IO 尖峰
  可调小 dirty_background_ratio（如 5%）让回写更均匀
掉电安全敏感（数据库）：
  保持 data=ordered + barrier（ext4 默认），别为了性能关 barrier
普通服务：默认值即可，别乱动
```

### 5. HugePages / THP 权衡

```text
显式大页（HugePages）：
  优点：TLB 覆盖大、内存确定（不换出）、数据库大缓冲池常用
  缺点：预分配占内存、需要应用支持（Oracle SGA 用 lock_sga + hugepages）
THP（透明大页）：
  优点：零配置享受大页
  缺点：khugepaged 合并需连续内存 → compaction → 偶发延迟尖刺；
        数据库（Oracle/MySQL/PG）与 Redis 场景建议 madvise 或 never
本机实测：THP=madvise（推荐配置）；HugePages_Total=0
```

### 6. NUMA 调优

```text
numactl --hardware        看节点拓扑（本机 1 节点）
numastat                  看命中统计：numa_hit/local_node 高 = 正常
numa_miss/other_node 高    = CPU 与内存节点错位（进程跑在 A 节点、
                           内存分配在 B 节点）→ 用 numactl --cpunodebind 绑定
numactl --interleave=all  内存交错分配（平衡但远端延迟高，不常用）
```

## 安全与权限

```text
1. sysctl 权限 —— 修改 /proc/sys/vm/* 需要 root；改错参数（如
   min_free_kbytes 调极小、overcommit=1）会影响整机稳定性，改前评估
2. 内存敏感信息 —— 进程内存含密钥/凭证；/proc/<PID>/mem 读写、
   core dump（/proc/sys/kernel/core_pattern）都需 root，生产环境
   建议限制 core dump 并加密敏感服务内存
3. OOM 保护 —— 关键进程设 oom_score_adj 负值（-500~-1000），
   防止被误杀；反过来对可牺牲的批处理进程可设正值
4. cgroup 限额 —— 用 cgroup（Docker --memory / systemd MemoryMax）
   限制单服务内存，防止一个进程吃满整机触发全局 OOM
5. 内核参数持久化文件 /etc/sysctl.conf 权限 —— 普通用户不可写，
   防止恶意改 swappiness/min_free_kbytes 破坏系统
```

## 故障排查

### 案例一：内存抖动（thrashing）——系统突然极慢

```shell
# 1. 看是否在疯狂换页
vmstat 1 5
# si/so 持续几千到几万 = 抖动确认
# 2. 看 available 是否见底
free -h
# 3. 看 PSI 压力（full 列代表整机卡顿程度）
cat /proc/pressure/memory
# 4. 找大户
ps aux --sort=-%mem | head
# 5. 临时止血：swapoff/限制进程（有风险，先备份）
# 根治：加内存，或限制内存大户（cgroup），或调低应用内存配置（如 Xmx）
```

**核心机制**：内存不足 → 内核把冷匿名页换出到磁盘 → 进程一访问又换入 → 磁盘成为瓶颈 → CPU 空闲但系统极慢（load 高、iowait 高、CPU 卡在换页上）。本机实测 si/so=0，未抖动；若出现此症状说明内存缺口明显。

### 案例二：进程被 OOM Killer 杀掉

```shell
# 1. 确认 OOM 与受害者
dmesg | grep -i 'out of memory'
journalctl -k | grep -i -E 'oom|killed process'
# 2. 看被杀进程的 anon-rss（当时占了多少匿名内存）
# 3. 看触发前的内存压力（sar 历史）
sar -r -f /var/log/sysstat/sa$(date +%d) | tail -20
# 4. 定位内存增长源（泄漏还是突增流量）
ps aux --sort=-%mem | head
# 5. 防护：关键进程 oom_score_adj 调负；内存大户限制 Xmx/cgroup
```

注意：OOM 日志里 `oom_score_adj` 字段是受害者被杀时的保护分；若受害者是**你自己的关键服务**，先看它为什么涨到最大，别急着改内核参数。

### 案例三：内存泄漏定位（RSS 持续增长）

```shell
# 1. 确认「单调增长」而非「涨到上限稳定」
pidstat -r -p <PID> 5    # 采样 10 分钟看趋势
# 2. 细分内存区域（Rss vs Swap vs 哪个映射在涨）
cat /proc/<PID>/smaps | awk '/^Rss:/{sum+=$2} END{print sum" kB"}'
# 或看 smaps_rollup（内核 4.14+）
cat /proc/<PID>/smaps_rollup
# 3. Java：jstat -gcutil 看堆与 GC；堆在 Full GC 后不回落 = 泄漏
# 4. C/C++：valgrind --leak-check=full（开发期）或 ASAN 编译
# 5. 容器：看 cgroup 的 memory.stat 里 anon 是否持续涨
cat /sys/fs/cgroup/<容器>/memory.stat | grep '^anon'
```

泄漏的特征是「无限单调增长」；JVM 堆、连接池、缓存会「涨到上限后稳定」，两者要区分开。

### 案例四：swap 被神秘占用 / 页缓存脏页堆积

```shell
# 1. swap 占用高但 si/so=0 → 历史换出（冷页），不是当前问题
grep -h '^VmSwap:' /proc/[0-9]*/status | sort -t: -k2 -nr | head -5
# 2. shmem/tmpfs 也可能占内存（/dev/shm 等）
grep '^Shmem' /proc/meminfo   # 本机实测 Shmem 1.69Gi
# 3. 脏页堆积导致卡顿：看 nr_dirty 是否接近阈值
grep -E 'nr_dirty|nr_dirty_threshold' /proc/vmstat
# 本机实测：nr_dirty 128 页，阈值 326861 页 → 远未堆积
# 4. 手动刷盘（临时止血）
sync
```

## 常见问题

```text
Q1: free 显示 free 很少，是不是内存不够？
A: 不是。free 列不含可回收页缓存，要看 available（含可回收缓存）才是
   真实可用。页缓存占满空闲内存是设计行为。本机 free 1.7Gi 但
   available 7.6Gi，健康。

Q2: 页缓存越涨越高，是内存泄漏吗？
A: 不是。页缓存尽量占满空闲内存（不用白不用），进程需要时内核会回收。
   真正的泄漏看进程 RSS 是否单调无限增长，不是看 buff/cache。

Q3: swappiness=0 能完全禁用 swap 吗？
A: 不能。0 只是「尽量避免换出」，内存极端紧张时仍会换出。真正禁用
   用 swapoff。RHEL 7+ 默认 30，Ubuntu 默认 60，数据库常调 10 左右。

Q4: 什么时候该加内存？
A: available 长期很低 + si/so 持续高（系统在抖动）时。若只是页缓存
   占满、available 充足，加内存是浪费。

Q5: swap 用了 480Mi 但 si/so=0，系统有问题吗？
A: 没有。si/so 是「当前是否在换入换出」，swap 有占用说明曾经换出过
   冷页（历史行为），只要现在不抖动就是健康的。抖动看 si/so 不看
   swap 占用。

Q6: OOM 后第一件事做什么？
A: 先看 dmesg/journalctl 确认受害者是谁、当时 anon-rss 多大，再看
   ps 找当前大户，判断是泄漏还是突增。不要急着重启或改内核参数。

Q7: 容器里 free 看到的为什么不是我的限额？
A: 容器共享宿主机内核，free 读的是宿主机 meminfo。真实容器内存要看
   /sys/fs/cgroup/memory.current（cgroup v2）或 docker stats。page
   cache 在容器间共享，回收也是全局的。

Q8: Committed_AS 超过 CommitLimit 会怎样？
A: overcommit=0（启发式）下这是常态（本机 %commit 111%），因为大部分
   「承诺」内存并未实际使用。只有 overcommit=2 时才严格拒绝超限分配，
   一般不建议开。
```

## 面试题

```text
1. free 输出的 used、buff/cache、available 分别是什么？判断内存够不够看哪个？
   答：used 是「总内存 - free - buff/cache」的账目值，包含大量可回收页
   缓存，不代表真不够；buff/cache 是文件缓存（可回收）；available 是
   内核估算的「可分配给新进程的内存量」（free + 可回收缓存），判断内存
   够不够看 available。used 高而 available 高 = 健康。

2. 页缓存是什么？脏页如何写回？dirty_ratio 与 dirty_background_ratio 区别？
   答：页缓存是文件内容的缓存，加速读写。脏页由 flusher 线程异步写回：
   dirty_background_ratio（默认 10%）触发后台异步写回（不阻塞应用）；
   dirty_ratio（默认 20%）触发写进程同步阻塞写回。另有时间阈值
   dirty_expire_centisecs（30 秒）。

3. kswapd 何时被唤醒？min/low/high 水位如何工作？
   答：空闲内存低于 low 水位时唤醒 kswapd 后台异步回收，高于 high 停止；
   低于 min 水位时分配路径直接回收（同步，进程阻塞）。min 太低会导致
   内存一紧张就卡，min_free_kbytes 可调大。

4. OOM Killer 如何选择受害者？如何保护关键进程？
   答：select_bad_process 遍历进程算 oom_score = 内存占用（RSS+swap+
   页表，归一化 0-1000）+ oom_score_adj 调整，杀得分最高者。保护：
   echo -500 > /proc/PID/oom_score_adj（systemd unit 写 OOMScoreAdjust）。
   -1000 表示永不参与 OOM 选择。

5. 如何定位内存泄漏？
   答：三步：① pidstat -r 观察 RSS 是否单调无限增长（涨到上限稳定是
   合理缓存）；② /proc/PID/smaps 看哪个区域在涨；③ Java 用 jstat 看
   GC 后堆是否回落，C/C++ 用 valgrind --leak-check=full 或 ASAN
   （-fsanitize=address）检测。

6. THP 的优缺点？数据库为什么常关闭？
   答：优点：2MiB 大页减少 TLB miss，零配置；缺点：khugepaged 合并需要
   连续内存，触发 compaction（内存压缩）造成偶发延迟尖刺，数据库对延迟
   敏感（Oracle/MySQL/PG）常见抖动，所以改 madvise（仅显式请求的映射
   用大页）或 never。

7. NUMA 架构下本地/远端内存是什么？怎么观察？
   答：每个 CPU 节点有本地内存，访问本地快、远端慢（要过互联总线）。
   numactl --hardware 看拓扑，numastat 看 numa_hit/numa_miss/other_node；
   miss/other 高说明进程与内存错位，用 numactl --cpunodebind 绑核优化。

8. swappiness 调优场景？
   答：数据库/缓存服务调低（10 左右），避免页缓存被换出拖慢查询；桌面
   默认 60；RHEL 7+ 默认 30（更倾向保留缓存）。注意 0 不禁止换出，
   只是尽量不用。调低后要观察 si/so 与命中率变化，别拍脑袋。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 判断内存够不够看 **available + si/so**，不是 free 或 used
2. 页缓存占满是正常的（空闲内存本就该被缓存用），别清缓存（drop_caches 后下次读回源磁盘反而变慢）
3. swap 持续换出（si/so 高）= 真不够，加内存或限制大户；swap 有占用≠抖动
4. 数据库服务器 swappiness 调低（10 左右）+ THP 改 madvise + OOM 保护
5. 内存泄漏早期发现：监控 RSS 趋势（单调增长 = 泄漏，涨到顶稳定 = 缓存）
6. OOM 排查先看 dmesg 的 anon-rss 与 oom_score_adj，再决定措施
7. 容器/多服务用 cgroup 限内存，防止单进程拖垮整机
8. 内核参数持久化写 /etc/sysctl.d/，别只 echo 临时生效

### 踩坑记录

```text
坑 1：看 free 列判断内存不够，误判
结论：free 只有 1.7Gi 就以为内存爆了要加内存。
原因：free 列不含可回收页缓存，available（7.6Gi）才是真实可用。
解法：看 available（free -h 最后一列），或看 si/so 是否在换出。

坑 2：页缓存占满以为是内存泄漏
结论：buff/cache 越涨越高，怀疑服务泄漏。
原因：页缓存尽量占满空闲内存是设计行为，可回收。
解法：看进程 RSS 是否增长；缓存涨是正常的，泄漏看 RSS 趋势。

坑 3：swappiness 调成 0 以为禁用 swap
结论：swappiness=0 后内存紧张还是用了 swap。
原因：0 只是「尽量避免」，极端紧张时仍会换出匿名页。
解法：真正禁用用 swapoff（不推荐长期），或接受「0=尽量不用」。

坑 4：内存泄漏和合理缓存分不清
结论：进程 RSS 一直涨，分不清是泄漏还是 JVM 堆。
原因：JVM 堆、连接池会涨到上限后稳定，真泄漏无限涨。
解法：观察趋势是「涨到顶稳定」还是「单调无限涨」；Java 用 jstat
     看 Full GC 后是否回落。

坑 5：内存抖动（thrashing）没及时发现
结论：系统响应极慢，查 CPU 发现空闲，一头雾水。
原因：内存不够 + 反复换页，磁盘成为瓶颈，CPU 反而空闲。
解法：vmstat 看 si/so 持续高 + PSI full 高 → 加内存或限制大户。

坑 6：min_free_kbytes 调太大浪费内存
结论：为了「防卡」把 min_free_kbytes 调到几个 GiB。
原因：min 水位保留的内存不可用，过大白白浪费大量内存。
解法：按内存 0.5%-1% 量级调整，观察 zoneinfo 与分配延迟再微调。

坑 7：OOM 后盲目重启服务，没查 dmesg
结论：服务被杀，重启后过几天又死，反复折腾。
原因：没看 OOM 日志，不知道是谁、为什么被杀。
解法：先 dmesg | grep -i oom 看受害者 anon-rss 与触发时间，再定位
     增长源，最后才重启。

坑 8：数据库开着 THP，偶发延迟尖刺
结论：MySQL/Oracle 查询偶发几十 ms 尖刺，排查无果。
原因：THP=always 时 khugepaged/compaction 偶发阻塞分配路径。
解法：echo madvise > /sys/kernel/mm/transparent_hugepage/enabled
     （生产可配合 systemd/grub 持久化）。

坑 9：echo 改内核参数重启丢失
结论：sysctl -w vm.swappiness=10 后重启又变回 60。
原因：运行时修改不持久化。
解法：写入 /etc/sysctl.d/99-memory.conf（sysctl -p 生效）。

坑 10：容器里看 free 以为内存泄漏
结论：容器内存监控显示占用暴涨，以为是应用问题。
原因：容器看到的是宿主机 meminfo，page cache 共享且全局统计。
解法：看 /sys/fs/cgroup/memory.current（cgroup v2）或 docker stats。
```
