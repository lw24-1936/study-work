## 概述

CPU 性能分析回答「CPU 够不够、谁在吃、为什么慢」：负载（load，系统忙不忙）、上下文切换（进程切换开销）、中断（硬件事件开销）、CPU 亲和性（把进程绑到固定核）、perf（深入分析 CPU 热点）。排查「CPU 飙高」先 top 找进程，再 perf 深入看是哪个函数在耗 CPU。

```text
CPU 性能五要素：
1. 负载 load —— 运行队列长度，超核数说明 CPU 饱和
2. 上下文切换 —— 进程频繁切换的开销（cs 高 = 切换频繁）
3. 中断 —— 硬件事件打断 CPU（网卡/磁盘中断）
4. CPU 亲和性 —— 把进程绑到固定核，减少缓存失效
5. perf —— 采样分析 CPU 热点函数
```

## 核心概念

### 1. 核数与超线程

物理核（core）是真正独立执行指令的单元；超线程（Hyper-Threading）把一个物理核虚拟成两个逻辑 CPU（thread），共享执行单元和缓存。超线程核适合「两个线程错峰使用不同执行单元」的场景，但两个逻辑核争抢资源时，单个线程的实际吞吐会打折。判断方式：`lscpu -e` 看 CORE 列，CORE 号相同的 CPU 是超线程兄弟。

```text
# 本机 lscpu -e（8 个逻辑 CPU，CORE 列 0-3 各出现两次 = 4 物理核 + 超线程）
CPU NODE SOCKET CORE ...
  0    0      0    0
  1    0      0    1
  2    0      0    2
  3    0      0    3
  4    0      0    0     <- 与 CPU0 同 CORE，超线程兄弟
  5    0      0    1     <- 与 CPU1 同 CORE
  6    0      0    2     <- 与 CPU2 同 CORE
  7    0      0    3     <- 与 CPU3 同 CORE
```

### 2. CPU 频率与 cpufreq

CPU 频率决定单核执行速度。现代 CPU 有动态调频（intel_pstate / acpi-cpufreq），通过调速器（governor）在最小/最大频率间调整：performance（固定最高频，功耗高）、powersave（省电优先，本机 Ubuntu 默认）、ondemand/schedutil（按负载动态调）。频率影响的是「快慢」，核数影响的是「并行度」——瓶颈在单线程延迟时调频率，瓶颈在并发时加核。

### 3. CPU 缓存 L1-L3

缓存是 CPU 和内存之间的速度缓冲：L1（每核私有，最快最小）、L2（每核私有）、L3（多核共享）。缓存命中率决定「数据从哪层拿」：命中 L1 约 1ns，访问内存约 100ns。缓存敏感型应用（数据库、热路径）要避免进程在核间漂移——每次迁移都要重新预热缓存，这就是 CPU 亲和性的价值。

### 4. NUMA

NUMA（非均匀内存访问）下，每个 CPU 节点绑定一部分物理内存，访问本节点内存快、跨节点慢。两路/多路服务器常见。工具：`numactl --hardware` 看节点分布，`numactl --cpunodebind=0 --membind=0 ./app` 把进程和内存绑到同一节点。单节点机器（如本机）无此问题，跨节点访问惩罚在虚拟化/多路环境才明显。

### 5. 负载 load average

「运行队列 + 不可中断进程」的平均数，1/5/15 分钟三个值。load ≈ CPU 核数 = 刚好满载，load > 核数 = CPU 饱和。注意 load 含「等 IO 的进程」，load 高不一定是 CPU 不够。load 是滑动平均，压载停止后需要时间回落（本机实测：忙循环结束后 1 分钟 load 仍居高，约 2-3 分钟后回到正常）。

```text
负载判断：
load < 核数     CPU 空闲，健康
load ≈ 核数     CPU 满载
load > 核数     CPU 饱和，有进程排队（注意可能是 IO 等待）
```

### 6. CPU 利用率 us/sy/ni/id/wa/hi/si/st

top 的 %Cpu(s) 行各列含义：

| 列 | 含义 | 高时说明 |
|---|---|---|
| us | 用户态时间（业务代码） | 应用在算，正常的热点 |
| sy | 内核态时间（系统调用/内核代码） | 系统调用多、锁竞争、IO 操作 |
| ni | nice 调整过的用户态时间 | 有进程被调过优先级 |
| id | 空闲 | 越低越忙 |
| wa | 等待 IO 完成 | 磁盘/网络 IO 慢，CPU 在干等 |
| hi | 硬中断 | 硬件事件多（网卡/磁盘） |
| si | 软中断 | 网络收发包处理重 |
| st | steal，被虚拟机管理程序偷走的时间 | 宿主机超卖，其他虚拟机抢了本机 CPU |

### 7. 上下文切换 context switch

CPU 在进程间切换的开销——保存/恢复进程状态（寄存器、栈、内存映射）。分为自愿切换（cswch，进程主动让出，如等 IO/锁）和非自愿切换（nvcswch，时间片耗尽被抢占）。切换太频繁浪费 CPU 在切换上：每秒几万次切换意味着大量时间没花在业务上。

### 8. 中断与软中断

硬件通过中断通知 CPU「有事件」（网卡收包、磁盘完成 IO、定时器）。上半部（硬中断）处理紧急部分，下半部（软中断 ksoftirqd）处理耗时部分。中断太频繁会打断 CPU 正常执行。多队列网卡（MSI-X）把中断分散到多个核，配合 irqbalance 自动均衡，避免单核被打满。

### 9. CPU 亲和性 affinity

把进程绑定到固定 CPU 核（taskset/cgroup cpuset），避免进程在核之间漂移导致缓存失效。适用场景：缓存敏感进程（数据库）、实时性要求高的进程、核隔离（独占核）。风险：绑定限制了并行度，绑错核（绑到繁忙核/超线程兄弟核）反而更慢。

### 10. CPU 密集型 vs IO 密集型

CPU 密集型：计算为主（科学计算、压缩、加解密、视频转码），特征 us 高、CPU 是瓶颈，优化方向是算法、多核并行、绑核。IO 密集型：大部分时间在等 IO（Web 服务、数据库、消息队列），特征 wa 高/us 低、CPU 利用率不高但并发高，优化方向是异步、缓存、连接池，CPU 核数用来承载并发而不是算力。

## 工作原理

### CFS 调度器与 nice 值

Linux 默认调度器是 CFS（完全公平调度器）。核心思路：为每个可运行进程维护虚拟运行时间 vruntime，调度器总是选 vruntime 最小的进程上 CPU，保证公平。

- nice 值范围 -20 ~ 19，越小优先级越高（负值需要 root）
- nice 值通过权重（weight）影响 vruntime 的增长速度：nice 0 权重 1024，nice 每差 1，权重差约 1.25 倍，nice -20 权重 88761
- 权重高的进程 vruntime 增长慢，被选中上 CPU 的机会多

```text
nice 值速查：
-20 ~ 19，默认 0
nice 越低 → 权重越高 → 分到 CPU 时间越多
普通用户只能调高（降低优先级），调低（负值）需要 root
```

### load average 的计算

load 是「处于运行状态 + 不可中断等待（等 IO）」进程数的指数移动平均，1/5/15 分钟对应三个衰减系数。进程在跑或在等 IO 都计入 load，所以 load 高要区分「CPU 忙（us/sy 高）」还是「等 IO（wa 高）」。

```text
# 实测（本机 8 核 + load 1.66，健康）
$ uptime
13:08:44 up 23 days, 6 min,  3 users,  load average: 1.66, 1.27, 1.42
$ nproc
8
# load 1.66 << 8 核，CPU 很空闲（load < 核数 = 健康）
```

### 上下文切换机制

一个核同一时刻只能跑一个进程（线程），切换时内核保存当前进程的寄存器/栈/页表指针，恢复下一个进程的状态。切换开销包括：上下文保存恢复、TLB 刷新、缓存失效。cs（每秒切换）几万说明进程太多或频繁调度；高并发应用（每请求一线程模型）天然切换高，此时换线程池/协程模型收益明显。

### 中断与多队列

硬件通过中断请求 CPU 处理事件。现代网卡支持多队列（RSS/MSI-X），每个队列有独立中断号，可绑定到不同核。`/proc/interrupts` 可以看到每个中断源在各核的分布；irqbalance 服务自动把中断均衡到多核，避免单个核被中断打满。

```text

```

### cpufreq 调速器

cpufreq 在 `performance`（固定最高频）和 `powersave`（省电，intel_pstate 下实际是「按需自动调频」）等调速器之间选择。Ubuntu 桌面默认 powersave，服务器场景常改 performance 换取稳定低延迟（避免频率爬升延迟），代价是功耗和发热。调频工具：cpupower、tuned（RHEL）。

## 常用命令与配置

```shell
uptime                 # 看负载
cat /proc/loadavg      # 负载 + 运行/总进程数
nproc                  # CPU 核数（对比 load）
top                    # %Cpu(s) 行 + 进程 %CPU；按 1 展开每核
mpstat -P ALL 1        # 每核利用率
vmstat 1 5             # cs 列 = 上下文切换，in 列 = 中断
pidstat 1 3            # 每个进程的 CPU 占用
pidstat -w 1 3         # 每个进程的自愿/非自愿切换
sar -u 1 1             # CPU 利用率（实时或历史）
sar -q 1 1             # 运行队列与负载
ps -eo pid,comm,%cpu --sort=-%cpu | head   # 进程按 CPU 排序
```

CPU 相关状态和调优参数都在 /proc 和 /sys 下：

```text
/proc/loadavg                                  —— 负载 + 进程数
0.91 0.98 1.05 1/1203 23887
# 1/5/15 分钟负载 | 运行进程/总进程 | 最近 PID

/proc/interrupts                               —— 每个中断源在各核的分布

/sys/fs/cgroup/cpu.max                         —— cgroup v2 的 CPU 限额（配额/周期，微秒）
```

### cgroup CPU 限制（cgroup v2）

容器/服务限 CPU 用 cgroup。v2 下 `cpu.max` 格式为「配额 周期」（微秒）：`20000 100000` = 每 100ms 周期内最多用 20ms，即 0.2 核。v1 对应 `cpu.cfs_quota_us` / `cpu.cfs_period_us`。本机是 cgroup v2（`/sys/fs/cgroup` 为 cgroup2fs）。

```shell
# 创建临时 cgroup 并设 0.2 核限制（本机实测通过）
mkdir -p /sys/fs/cgroup/demo-cpu
cat /sys/fs/cgroup/demo-cpu/cpu.max        # 默认 max 100000 = 不限
echo 20000 100000 > /sys/fs/cgroup/demo-cpu/cpu.max
cat /sys/fs/cgroup/demo-cpu/cpu.max        # 20000 100000 = 0.2 核
rmdir /sys/fs/cgroup/demo-cpu
```

```text
# 实测（本机 cgroup v2）
$ stat -fc %T /sys/fs/cgroup/
cgroup2fs
$ cat /sys/fs/cgroup/cgroup.controllers
cpuset cpu io memory hugetlb pids rdma misc dmem
# cpu 控制器在列，说明可用 cpu.max 限额
```

## 应用场景实战

### 场景一：CPU 飙高，定位到函数

```shell
# 1. top 找吃 CPU 的进程
top
# 2. 多线程进程用 -H 看哪个线程飙
top -H -p <PID>
# 3. perf 看该进程的热点函数（实时）
perf top -p <PID>
# 4. 或采样后生成报告（更稳，生产推荐）
perf record -g -p <PID> -- sleep 10
perf report
```

perf report 的火焰图思路：`perf record -g` 记录调用栈，`perf report` 看占比最高的函数，逐层下钻到具体代码。热点函数占比 > 30% 基本就是优化目标。

### 场景二：load 高，判断是 CPU 还是 IO

```shell
# 1. 看 load
uptime
# 2. 看 vmstat 的 wa（等 IO）和 us/sy（CPU）
vmstat 1 5
# wa 高 → IO 瓶颈；us/sy 高 → CPU 瓶颈
# 3. 看谁在等 IO / 谁在吃 CPU
iostat -x 1 5     # 磁盘层确认
pidstat -d 1      # 哪个进程在等 IO
pidstat 1 3       # 哪个进程在吃 CPU
```

判定口诀：`r 列大 + us 高` = CPU 瓶颈；`wa 高 + %util 高` = 磁盘瓶颈；`r 列大 + wa 低 + us 低` = 大量进程在等 IO（不可中断睡眠 D 状态）。

### 场景三：多核负载不均，绑核均衡

单进程占满一个核、其他核空闲时，优化方向看进程模型：多线程进程用 `taskset -pc 0-3 <PID>` 让它跑在多个核上；多个独立进程按核分布用 `taskset -c <核> <命令>` 分别绑定。

```shell
# 8 核机器，4 个计算进程分别绑到 0/1/2/3 核（避免和网卡中断/系统进程挤在一起）
taskset -c 0 ./worker1 &
taskset -c 1 ./worker2 &
taskset -c 2 ./worker3 &
taskset -c 3 ./worker4 &
# 绑完用 mpstat -P ALL 1 验证各核分布是否均匀
```

### 场景四：上下文切换过高排查

```shell
# 1. 确认切换量：vmstat 的 cs 列，持续几万/秒说明异常
vmstat 1 5
# 2. 定位切换大户：pidstat -w（cswch 自愿 / nvcswch 非自愿）
pidstat -w 1 5
# 3. 按原因处理
#    nvcswch 高 → 线程太多 / 优先级竞争 → 线程池化、减少线程数
#    cswch 高   → 等锁/等 IO → 查锁竞争（perf lock）、换无锁结构、加缓存
```

### 场景五：cgroup 限制服务 CPU

多租户/容器场景限制单服务 CPU 占用：

```shell
# 方式一：cgroup v2 直接限额（0.2 核，实测通过）
mkdir -p /sys/fs/cgroup/app-limit
echo 20000 100000 > /sys/fs/cgroup/app-limit/cpu.max
echo <PID> > /sys/fs/cgroup/app-limit/cgroup.procs

# 方式二：systemd 单元限制（生产更常用）
systemctl set-property myservice.service CPUQuota=50%
# CPUQuota=50% = 半核；之后 systemctl restart myservice.service 生效

# 方式三：docker 容器限制
docker run --cpus=2 myimage    # 最多 2 核
```

## 性能与调优

### 1. 进程优先级：nice / renice

交互式应用（数据库、Web 服务）优先级调高（负 nice），批处理/备份任务调低，保证关键时刻关键进程先拿 CPU。注意：nice 只影响 CPU 时间分配，不影响 IO 优先级（那是 ionice 的事）；nice 调整对「CPU 已饱和」的场景帮助有限，饱和时先解决「为什么饱和」。

```text
nice 实战要点：
1. 普通用户只能调高（正 nice，降优先级），调低需 root
2. renice 对运行中进程生效，无需重启
3. 负 nice 用在工作负载高时的核心服务（如数据库），别滥用
4. 优先级是「权重」不是「独占」：nice 再高也不能保证实时性（那是 rt 调度）
```

### 2. taskset 绑核与 numactl

绑核的取舍：

| 场景 | 做法 | 收益 |
|---|---|---|
| 缓存敏感（数据库热路径） | taskset 固定核 | 缓存命中率稳定，避免迁移抖动 |
| NUMA 多路机器 | numactl 绑节点 + 绑内存 | 避免跨节点访问惩罚 |
| 关键进程隔离 | cgroup cpuset 独占核 | 防止其他进程抢占 |
| 普通服务 | 不绑 | 保留调度器灵活性，核空闲时充分利用 |

教训：先测量再绑。绑核前用 mpstat 看各核负载，把进程绑到空闲核；绑到繁忙核或超线程兄弟核反而更慢。

### 3. irqbalance 与中断绑核

高吞吐网卡场景：确认网卡支持多队列（`ethtool -L eth0 combined N`），配合 irqbalance 把中断均衡到多核；极端场景手动写 `/proc/irq/<IRQ>/smp_affinity` 把网卡队列中断固定到不同核。注意：本机未装 irqbalance（Ubuntu 默认），RHEL 默认启用；中断绑核改动要谨慎，误绑可能把中断全压到一个核。

### 4. cpufreq 调速器选择

```shell
# 查看当前调速器（本机实测 powersave）
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
cat /sys/devices/system/cpu/cpufreq/policy0/scaling_available_governors
# performance powersave   <- 本机可用列表

# 切换（需 root）
cpupower frequency-set -g performance
# RHEL 用 tuned 更省事：tuned-adm profile throughput-performance
```

服务器低延迟场景推荐 performance：省掉频率爬升的延迟和抖动；代价是功耗/发热上升。笔记本/开发机 powersave 即可。

### 5. 内核参数与线程模型

```text
CPU 相关调优清单：
1. 线程模型 —— 每请求一线程 → 线程池/协程，减少切换和内存开销
2. 锁竞争 —— 热点锁拆分/无锁结构，sy 高 + nvcswch 高优先查锁
3. perf_event_paranoid —— 生产调低（如 1）方便采样，别调 -1 全放
4. 中断均衡 —— 多队列 + irqbalance，避免单核被打满
5. 亲和性 —— 关键进程绑核，普通进程不绑
6. 优先级 —— 核心服务负 nice，批处理正 nice
```

## 安全与权限

```text
1. perf 采样权限 —— perf_event_paranoid 控制能否采样其他进程（本机 4 = 最严），生产默认较严；调低前评估风险
2. 中断亲和配置 —— 改 /proc/irq/*/smp_affinity 要 root，乱改可能把中断压到单核影响网络
3. 亲和性隔离 —— 关键进程绑专属核，但要防其他进程抢占（cgroup cpuset 更彻底）
4. nice 滥用 —— 提优先级（负 nice）要 root，普通用户只能降优先级
5. /proc 信息泄露 —— /proc/interrupts、/proc/loadavg 等对普通用户可读，是信息收集面；高安全环境用 hidepid 挂载
6. 云主机 st 高 —— st 是宿主机超卖信号，不是本机可优化的，别在本机瞎调
```

## 故障排查

### 案例一：CPU 飙高定位（进程 → 线程 → 函数）

```shell
# 1. 找进程
top -o %CPU
# 2. 找线程（多线程进程哪个线程飙）
top -H -p <PID>
# 3. 定位到函数
perf top -p <PID>
# 4. 判断单核还是多核（决定是「换算法」还是「加并行」）
mpstat -P ALL 1
```

```text
本机实测示范：6 个忙循环把 8 核吃满 6 个核
top 直接看到 6 个 bash 各 92.3% → 定位到进程层
若换成真实业务：java 进程飙高 → top -H 找线程 → perf record -g -p <PID> 采样
→ perf report 看热点函数 → 优化对应代码
```

### 案例二：load 高但 CPU 不高

```shell
# 1. 看 vmstat 的 wa（等 IO）
vmstat 1 5
# 2. wa 高 → IO 瓶颈，查磁盘
iostat -x 1 5
# 3. 看是谁在等 IO
pidstat -d 1
```

判定：`load 高 + us/sy 低 + wa 高` = 进程在等磁盘 IO（D 状态），CPU 不是瓶颈。典型场景：慢磁盘、日志刷盘、数据导入。

### 案例三：单核飙高、多核空闲

现象：整体 CPU 不高但系统响应慢，某进程 %CPU 100%。判定：`mpstat -P ALL` 看是否单个核 100% 其他核空闲。原因：单线程应用（Redis 单线程模式、Python GIL、单线程处理循环）。解法：多线程/多进程化、或绑核保证稳定性能、或换更快的单核（高频 CPU）。

### 案例四：上下文切换过高

现象：CPU 不忙但系统响应慢，vmstat cs 列几万/秒。排查：`pidstat -w 1 5` 看 cswch/nvcswch 大户。nvcswch 高 → 线程数过多或优先级竞争 → 线程池化；cswch 高 → 锁/IO 等待 → 查锁竞争、加缓存、异步化。

### 案例五：常见 CPU 性能问题案例

```text
1. 死循环：进程 100% 单核，perf 看热点函数是业务循环 → 加超时/熔断，代码审查
2. GC 频繁（Java/Go）：us 不高但 sy 高、GC 线程忙碌 → 调堆大小/GC 策略，查内存泄漏
3. 线程过多：每请求一线程，几千线程疯狂切换，nvcswch 高 → 线程池化/协程
4. 锁竞争：sy 高 + cswch 高，perf lock 看热点锁 → 锁拆分、读写锁、无锁结构
5. 系统调用风暴：sy 高 + in 高，频繁 read/write 小 IO → 批量读写、缓存、零拷贝
判定共同点：先 top 定位进程，再 perf/pidstat 定位原因，别凭感觉猜
```

## 常见问题

```text
Q1: load 和 CPU 使用率有什么区别？
A: load 是「运行 + 等 IO 的进程数」，CPU 使用率是「CPU 忙的时间比例」。load 高 + CPU 低 = 大量进程在等 IO（不是 CPU 瓶颈）。

Q2: 多核机器为什么单核飙高，整体不高？
A: 单进程（或单线程）只跑在一个核上，该核 100% 但其他核空闲。用 mpstat -P ALL 看每核，或 top 按 1 展开。

Q3: 上下文切换高怎么办？
A: 先 pidstat -w 找切换大户，区分自愿/非自愿：非自愿高通常是线程太多或优先级竞争，自愿高通常是锁/IO 等待。减少进程数、用线程池、优化锁竞争。

Q4: perf 和 top 的区别？
A: top 看「哪个进程吃 CPU」，perf 看「进程的哪个函数吃 CPU」。先 top 找进程，再 perf 深入函数。

Q5: us 高和 sy 高分别说明什么？
A: us 高是业务代码在算（应用热点）；sy 高是内核态开销大——系统调用多、锁竞争、IO 操作、内存分配。sy 高优先查系统调用和锁，us 高优先查业务算法。

Q6: 怎么判断应用是 CPU 密集型还是 IO 密集型？
A: 看 vmstat 的 us/wa 比例和 CPU 利用率：us 持续高、CPU 吃满 = CPU 密集型（优化算法/并行）；wa 高、CPU 空闲但响应慢 = IO 密集型（优化异步/缓存/连接）。也可以 pidstat 看进程 %CPU 与 %wait。

Q7: 什么时候用 taskset 绑核？
A: 缓存敏感进程（数据库热路径）、NUMA 多路机器、关键进程隔离时用；普通服务不绑。绑核前用 mpstat 看核负载，先测再绑，绑错反而更慢。
```

## 面试题

```text
1. load average 是怎么计算的？
   答：运行队列长度 + 不可中断等待（等 IO）进程数的指数移动平均，1/5/15 分钟三个值。与核数对比判断饱和：load > 核数说明有进程排队。但 load 含等 IO 的进程，要结合 vmstat 的 r 列、wa 列区分是 CPU 忙还是等 IO。

2. CFS 调度器是怎么工作的？
   答：CFS 为每个可运行进程维护虚拟运行时间 vruntime，每次选 vruntime 最小的进程上 CPU，保证公平。nice 值通过权重影响 vruntime 增长速度：nice 越低权重越高（-20 权重 88761，0 权重 1024），vruntime 增长越慢、分到 CPU 越多。

3. 上下文切换为什么影响性能？
   答：切换要保存/恢复进程状态（寄存器、栈、内存映射），还会刷新 TLB、失效缓存，有固定开销。切换频繁（cs 高）时 CPU 大量时间花在切换而非业务上。高并发场景线程过多会放大这个开销。

4. 中断和上下文切换有什么区别？
   答：中断是硬件通知 CPU 处理事件（网卡收包/磁盘完成），打断当前执行去跑中断处理程序；上下文切换是进程/线程间的切换。两者都会打断 CPU 正常执行。多队列网卡 + irqbalance 能把中断分散到多核。

5. nice 值的范围和作用？
   答：范围 -20 ~ 19，默认 0，越小优先级越高。负值需要 root 权限。作用是通过 CFS 权重调整进程的 CPU 时间分配比例。注意 nice 只管 CPU 时间，不管 IO 优先级（那是 ionice），对已饱和的系统帮助有限。

6. CPU 亲和性有什么用途和风险？
   答：用途是减少进程在核间漂移导致的缓存失效、隔离核心给关键进程、NUMA 场景避免跨节点访问。风险是绑定限制了并行度，绑错核（绑到繁忙核/超线程兄弟核）反而更慢。原则：先测再绑，普通进程不绑。

7. 超线程对性能有什么影响？
   答：超线程把一个物理核虚拟成两个逻辑 CPU，共享执行单元和缓存。适合两个线程错峰使用不同资源（一个算数一个等内存）的场景，能提升约 10-30% 的整机吞吐；但两个逻辑核抢同一物理核资源时，单线程性能不升反降。判断用 lscpu -e 看 CORE 列，绑核时避免把两个任务绑到超线程兄弟核。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先 top 找进程，再 perf 深入找函数，逐层定位
2. load 高先区分 CPU（us/sy + r 列）还是 IO（wa），别混为一谈
3. 上下文切换高看 pidstat -w，区分自愿/非自愿，再对症处理
4. CPU 亲和性按需用（缓存敏感/隔离核心），先看核负载再绑，别盲目绑
5. perf 是终极工具，但先会用 top/vmstat/mpstat 再上 perf
6. 单核瓶颈看 mpstat -P ALL 每核，别只看整体平均值
7. 压测负载用 timeout 包裹，结束后检查残留进程（本机实测孤儿忙循环把 load 顶到 8.89）
8. 多线程进程飙高用 top -H 先定位线程，再决定优化方向

### 踩坑记录

```text
坑 1：load 高就加 CPU，结果是 IO 瓶颈
结论：load 高，加了 CPU 还是高。
原因：load 含等 IO 的进程，wa 高说明是 IO 瓶颈。
解法：vmstat 看 wa，wa 高查 IO（iostat），不是 CPU。

坑 2：只看整体 CPU，忽略单核飙高
结论：多核机器某进程 %CPU 100%，整体 CPU 不高。
原因：单核跑满，其他核空闲，负载不均。
解法：mpstat -P ALL 看每核，top 按 1 看每核负载。

坑 3：上下文切换高，误以为是 CPU 慢
结论：CPU 不忙但系统响应慢，cs 很高。
原因：进程频繁切换，CPU 浪费在切换上。
解法：pidstat -w 找切换大户，区分自愿/非自愿，减少进程数/优化调度。

坑 4：perf 报权限不足
结论：perf top/record 报 permission error。
原因：perf 需要权限（内核 perf_event 限制，本机 paranoid=4）。
解法：用 root，或临时调整 /proc/sys/kernel/perf_event_paranoid。

坑 5：CPU 亲和性绑错导致性能下降
结论：taskset 绑定后反而更慢。
原因：绑定限制了并行，或绑到的核已被其他进程占用（或绑到超线程兄弟核）。
解法：先测再绑，绑定前用 mpstat 了解核的负载分布。

坑 6：云主机 st 高，误当成自己 CPU 忙
结论：us 不高但系统很慢，怎么调都没用。
原因：st（steal）高说明宿主机超卖，时间片被其他虚拟机抢走。
解法：top/mpstat 看 st 列确认，换实例规格或迁移，本机调优无效。

坑 7：us 不高就排除 CPU，实际是 sy 高
结论：us 10% 但系统卡顿，以为 CPU 没问题。
原因：sy（内核态）高——系统调用风暴、锁竞争、频繁小 IO 读写。
解法：看 sy 列 + pidstat 的 %system，perf 查内核热点，优化系统调用和锁。

坑 8：压测忙循环没清理，负载持续不降
结论：压测结束几小时后 load 还很高。
原因：后台子进程成孤儿继续烧 CPU（本机实测 6 个忙循环跑满 6 核，load 冲到 8.89）。
解法：压测命令用 timeout 包裹，结束后 ps 检查残留并 kill。

坑 9：GC 频繁误判为 CPU 不够
结论：Java 服务 CPU 高就加核，问题依旧。
原因：GC 线程占 CPU 是内存问题的表象——堆太小或内存泄漏。
解法：perf 看热点是否为 GC 相关函数，查堆大小/GC 日志，先解决内存再谈 CPU。
```
