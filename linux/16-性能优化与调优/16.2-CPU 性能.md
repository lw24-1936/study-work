## 概述

CPU 性能分析回答「CPU 够不够、谁在吃、为什么慢」：负载（load，系统忙不忙）、上下文切换（进程切换开销）、中断（硬件事件开销）、CPU 亲和性（把进程绑到固定核）、perf（深入分析 CPU 热点）。排查「CPU 飙高」先 top 找进程，再 perf 深入看是哪个函数在耗 CPU。

```text
CPU 性能五要素：
1. 负载 load —— 运行队列长度，超核数说明 CPU 饱和
2. 上下文切换 —— 进程频繁切换的开销（cs 高 = 切换频繁）
3. 中断 —— 硬件事件打断 CPU（网卡/磁盘中断）
4. CPU 亲和性 —— 把进程绑到固定核，减少缓存失效
5. perf —— 采样分析 CPU 热点函数
```

## 核心概念

1. **负载 load average**：「运行队列 + 不可中断进程」的平均数，1/5/15 分钟三个值。load ≈ CPU 核数 = 刚好满载，load > 核数 = CPU 饱和。注意 load 含「等 IO 的进程」，load 高不一定是 CPU 不够。
2. **上下文切换 context switch**：CPU 在进程间切换的开销——保存/恢复进程状态。切换太频繁浪费 CPU 在切换上。
3. **中断 interrupt**：硬件通知 CPU「有事件」的机制（网卡收包、磁盘完成 IO、定时器）。中断太频繁打断 CPU 正常执行。
4. **CPU 亲和性 affinity**：把进程绑定到固定 CPU 核，避免进程在核之间漂移导致缓存失效。
5. **perf**：内核级性能分析工具，采样「CPU 花在哪个函数上」。

```text
负载判断：
load < 核数     CPU 空闲，健康
load ≈ 核数     CPU 满载
load > 核数     CPU 饱和，有进程排队（注意可能是 IO 等待）
```

## 工作原理

1. **负载怎么算**：load 是「处于运行状态 + 不可中断等待（等 IO）」的进程数的指数移动平均。进程在跑或在等 IO 都计入 load，所以 load 高要区分「CPU 忙（us/sy 高）」还是「等 IO（wa 高）」。
2. **上下文切换**：一个核同一时刻只能跑一个进程，进程切换时内核保存当前进程的寄存器/栈，恢复下一个进程的状态。切换有固定开销，cs（每秒切换）几万说明进程太多或频繁调度。
3. **中断**：硬件通过中断请求 CPU 处理事件，CPU 暂停当前执行去跑中断处理程序。中断多队列（网卡）能把中断分散到多个核，避免单核被打满。

```text
# 实测（本机 8 核 + load 0.91）
$ uptime
23:34 up 22 days, load average: 0.91, 0.98, 1.05
$ nproc
8
# load 0.91 << 8 核，CPU 很空闲（load < 核数 = 健康）
```

## 常用命令与配置

```shell
uptime                 # 看负载
cat /proc/loadavg      # 负载 + 运行/总进程数
nproc                  # CPU 核数（对比 load）
mpstat -P ALL 1        # 每核利用率
vmstat 1 5             # cs 列 = 上下文切换，in 列 = 中断
pidstat -w 1           # 每个进程的切换次数
```

```text
# 实测（本机 vmstat 的 cs 列）
$ vmstat 1 2 | tail -1
 1 3 87688 231440 1389912 8652744  0  0  0 20 6744 7564  7  0 78 14
# in=7564（中断/秒）、cs=6744（上下文切换/秒），8 核下正常
```

CPU 亲和性与 perf：

```shell
taskset -c 0-3 ./myapp        # 绑定到 0-3 核
taskset -p <PID>              # 看进程的亲和性
taskset -pc 0-3 <PID>         # 修改运行中进程的亲和性
perf top                      # 实时看热点函数
perf record -g ./myapp        # 采样记录（-g 记录调用栈）
perf report                   # 生成报告（看热点）
perf stat ./myapp             # 统计（CPU 周期、缓存、分支等）
```

```text
# 实测（本机 perf 已装）
$ perf --version
perf version 7.0.12
```

## 配置文件解析

CPU 相关状态和调优参数都在 /proc 下：

```text
# /proc/loadavg —— 负载 + 进程数
0.91 0.98 1.05 1/1203 23887
# 1/5/15 分钟负载 | 运行进程/总进程 | 最近 PID

# /proc/interrupts —— 每个中断源在各核的分布
# 实测（本机 /proc/interrupts，8 核）
$ cat /proc/interrupts | head -5
         CPU0  CPU1  CPU2  CPU3  CPU4  CPU5  CPU6  CPU7
   0:     45    0    0    0    0    0    0    0  timer
   9:     0  13428613 0    0    0    0    0    0  acpi
# 每个中断源在 8 个核上的分布，acpi 集中在 CPU1
```

```text
调优参数：
/proc/sys/kernel/perf_event_paranoid   perf 采样权限（越大越严）
/proc/irq/<IRQ>/smp_affinity           中断绑核（十六进制掩码）
irqbalance 服务                         自动均衡中断到多核
```

## 应用场景实战

### 场景一：CPU 飙高，定位到函数

```shell
# 1. top 找吃 CPU 的进程
top
# 2. perf 看该进程的热点函数
perf top -p <PID>
# 3. 或采样后生成报告
perf record -g -p <PID> -- sleep 10
perf report
```

### 场景二：load 高，判断是 CPU 还是 IO

```shell
# 1. 看 load
uptime
# 2. 看 vmstat 的 wa（等 IO）和 us/sy（CPU）
vmstat 1 5
# wa 高 → IO 瓶颈；us/sy 高 → CPU 瓶颈
# 3. 看谁在等 IO
iostat -x 1 5
```

## 性能与调优

```text
1. 负载均衡 —— 多核机器某进程单核飙高，看 mpstat -P ALL 是否负载不均
2. 减少切换 —— 进程数太多导致 cs 高，用进程池/线程池减少进程数
3. 中断亲和 —— 高吞吐网卡配多队列 + irqbalance，把中断分散到多核
4. 亲和性按需 —— 缓存敏感进程（数据库）绑核，但别盲目绑（限制并行）
5. nice 调整 —— 非关键进程降优先级（nice），让关键进程优先拿 CPU
```

## 安全与权限

```text
1. perf 采样权限 —— perf_event_paranoid 控制能否采样其他进程，生产默认较严
2. 中断亲和配置 —— 改 /proc/irq/*/smp_affinity 要 root，别乱改（可能影响网络）
3. 亲和性隔离 —— 关键进程绑专属核，但要防其他进程抢占（cgroup cpuset 更彻底）
4. nice 滥用 —— 提优先级（负 nice）要 root，普通用户只能降优先级
```

## 故障排查

### CPU 飙高定位

```shell
# 1. 找进程
top -o %CPU
# 2. 找线程（多线程进程哪个线程飙）
top -H -p <PID>
# 3. 定位到函数
perf top -p <PID>
# 4. 判断单核还是多核
mpstat -P ALL 1
```

### load 高但 CPU 不高

```shell
# 1. 看 vmstat 的 wa（等 IO）
vmstat 1 5
# 2. wa 高 → IO 瓶颈，查磁盘
iostat -x 1 5
# 3. 看是谁在等 IO
pidstat -d 1
```

## 常见问题

```text
Q1: load 和 CPU 使用率有什么区别？
A: load 是「运行 + 等 IO 的进程数」，CPU 使用率是「CPU 忙的时间比例」。load 高 + CPU 低 = 大量进程在等 IO（不是 CPU 瓶颈）。

Q2: 多核机器为什么单核飙高，整体不高？
A: 单进程（或单线程）只跑在一个核上，该核 100% 但其他核空闲。用 mpstat -P ALL 看每核，或 top 按 1 展开。

Q3: 上下文切换高怎么办？
A: 先 pidstat -w 找切换大户，通常是进程/线程太多或频繁调度。减少进程数、用连接池/线程池、优化锁竞争。

Q4: perf 和 top 的区别？
A: top 看「哪个进程吃 CPU」，perf 看「进程的哪个函数吃 CPU」。先 top 找进程，再 perf 深入函数。
```

## 面试题

```text
1. load average 是怎么计算的？
   答：运行队列长度 + 不可中断等待（等 IO）进程数的指数移动平均，1/5/15 分钟三个值。与核数对比判断饱和，但要区分 CPU 忙还是等 IO。

2. 上下文切换为什么影响性能？
   答：切换要保存/恢复进程状态（寄存器、栈、内存映射），有固定开销。切换频繁（cs 高）时 CPU 大量时间花在切换而非业务上。

3. 中断和上下文切换有什么区别？
   答：中断是硬件通知 CPU 处理事件（网卡收包/磁盘完成），上下文切换是进程/线程间的切换。两者都会打断 CPU 正常执行。

4. CPU 亲和性有什么用途和风险？
   答：用途是减少进程在核间漂移导致的缓存失效、隔离核心给关键进程。风险是绑定限制了并行，绑错核（被其他进程占用）反而更慢。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先 top 找进程，再 perf 深入找函数，逐层定位
2. load 高先区分 CPU（us/sy）还是 IO（wa），别混为一谈
3. 上下文切换高看 pidstat -w，可能是进程太多/频繁调度
4. CPU 亲和性按需用（缓存敏感/隔离核心），别盲目绑
5. perf 是终极工具，但先会用 top/vmstat/mpstat 再上 perf

### 踩坑记录

```text
坑 1：load 高就加 CPU，结果是 IO 瓶颈
结论：load 高，加了 CPU 还是高。
原因：load 含等 IO 的进程，wa 高说明是 IO 瓶颈。
解法：vmstat 看 wa，wa 高查 IO（iostat），不是 CPU。

坑 2：只看整体 CPU，忽略单核飙高
结论：多核机器某进程 %CPU 100%，整体 CPU 不高。
原因：单核跑满，其他核空闲，负载不均。
解法：mpstat -P ALL 看每核，top 按 1 看每核负载。

坑 3：上下文切换高，误以为是 CPU 慢
结论：CPU 不忙但系统响应慢，cs 很高。
原因：进程频繁切换，CPU 浪费在切换上。
解法：pidstat -w 找切换大户，减少进程数/优化调度。

坑 4：perf 报权限不足
结论：perf top/record 报 permission error。
原因：perf 需要权限（内核 perf_event 限制）。
解法：用 root，或调整 /proc/sys/kernel/perf_event_paranoid。

坑 5：CPU 亲和性绑错导致性能下降
结论：taskset 绑定后反而更慢。
原因：绑定限制了并行，或绑到的核已被其他进程占用。
解法：先测再绑，绑定前了解核的负载分布。
```
