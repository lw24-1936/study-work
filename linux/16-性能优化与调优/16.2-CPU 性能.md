## 概述

CPU 性能分析回答「CPU 够不够、谁在吃、为什么慢」：负载（load，系统忙不忙）、上下文切换（进程切换开销）、中断（硬件事件开销）、CPU 亲和性（把进程绑到固定核）、perf（深入分析 CPU 热点）。排查「CPU 飙高」先 top 找进程，再 perf 深入看是哪个函数在耗 CPU。

```text
CPU 性能五要素：
1. 负载 load —— 运行队列长度，超核数说明 CPU 饱和
2. 上下文切换 —— 进程频繁切换的开销（cs 高 = 切换频繁）
3. 中断 —— 硬件事件打断 CPU（网卡/磁盘中断）
4. CPU 亲和性 —— 把进程绑到固定核，减少缓存失效
5. perf —— 采样分析 CPU 热点函数
```

## 负载

负载（load average）是「运行队列 + 不可中断进程」的平均数，1/5/15 分钟三个值。判断：load ≈ CPU 核数 = 刚好满载，load > 核数 = CPU 饱和（有进程在排队）。注意 load 包含「等 IO 的进程」，所以 load 高不一定是 CPU 不够——可能是 IO 瓶颈（看 vmstat 的 wa 列区分）。用 uptime 或 /proc/loadavg 查看。

```text
# 实测（本机 8 核 + load 0.91）
$ uptime
23:34 up 22 days, load average: 0.91, 0.98, 1.05
$ nproc
8
# load 0.91 << 8 核，CPU 很空闲（load < 核数 = 健康）
```

```shell
uptime                 # 看负载
cat /proc/loadavg      # 负载 + 运行/总进程数
nproc                  # CPU 核数（对比 load）
```

```text
负载判断：
load < 核数     CPU 空闲，健康
load ≈ 核数     CPU 满载
load > 核数     CPU 饱和，有进程排队（注意可能是 IO 等待）
```

## 上下文切换

上下文切换（context switch）是 CPU 在进程间切换的开销——保存/恢复进程状态。切换太频繁会「浪费 CPU 在切换上而不是干活上」。vmstat 的 cs 列是每秒切换次数，`pidstat -w` 看每个进程的切换。cs 高（几万/秒）+ CPU 高 = 可能进程太多/频繁调度，考虑减少进程数或调整。

```text
# 实测（本机 vmstat 的 cs 列）
$ vmstat 1 2 | tail -1
 1 3 87688 231440 1389912 8652744  0  0  0 20 6744 7564  7  0 78 14
# in=7564（中断/秒）、cs=6744（上下文切换/秒），8 核下正常
```

```shell
vmstat 1 5              # cs 列 = 上下文切换
pidstat -w 1            # 每个进程的切换次数
```

## 中断

中断（interrupt）是硬件通知 CPU「有事件」的机制——网卡收到包、磁盘完成 IO、定时器触发都会产生中断。中断太频繁会打断 CPU 正常执行。`/proc/interrupts` 看每个中断源的中断次数，`vmstat` 的 in 列是每秒中断数。网卡多队列、中断亲和性（irqbalance）能优化中断分布。

```text
# 实测（本机 /proc/interrupts，8 核）
$ cat /proc/interrupts | head -5
         CPU0  CPU1  CPU2  CPU3  CPU4  CPU5  CPU6  CPU7
   0:     45    0    0    0    0    0    0    0  timer
   9:     0  13428613 0    0    0    0    0    0  acpi
# 每个中断源在 8 个核上的分布，acpi 集中在 CPU1
```

```shell
cat /proc/interrupts      # 中断分布
vmstat 1 5                # in 列 = 每秒中断数
irqbalance --status       # 中断亲和性（均衡分布）
```

## CPU 亲和性

CPU 亲和性（affinity）把进程绑定到固定 CPU 核，避免「进程在核之间漂移导致缓存失效」。用 taskset 设置：`taskset -c 0-3 命令`（绑定到 0-3 核）。适合「CPU 缓存敏感」的场景（如数据库、高性能计算），也能用于「隔离核心」（把关键进程绑到专属核，其他进程避开）。但盲目绑定可能适得其反（限制并行）。

```shell
taskset -c 0-3 ./myapp        # 绑定到 0-3 核
taskset -p <PID>              # 看进程的亲和性
taskset -pc 0-3 <PID>         # 修改运行中进程的亲和性
```

```text
CPU 亲和性用途：
1. 减少缓存失效 —— 进程固定核，缓存热数据不丢
2. 隔离核心 —— 关键进程绑专属核，避开其他进程
3. 注意 —— 盲目绑定限制并行，按需用
```

## perf

perf 是内核级性能分析工具——采样分析「CPU 花在哪个函数上」，生成热点报告。`perf top`（实时看热点函数）、`perf record`（采样记录）+ `perf report`（生成报告）。能精确到「哪个进程的哪个函数在耗 CPU」，是 CPU 性能分析的终极工具。

```text
# 实测（本机 perf 已装）
$ perf --version
perf version 7.0.12
```

```shell
perf top                 # 实时看热点函数
perf record -g ./myapp   # 采样记录（-g 记录调用栈）
perf report              # 生成报告（看热点）
perf stat ./myapp        # 统计（CPU 周期、缓存、分支等）
```

## 应用场景实战

### 场景一：CPU 飙高，定位到函数

```shell
# 1. top 找吃 CPU 的进程
top
# 2. perf 看该进程的热点函数
perf top -p <PID>
# 3. 或采样后生成报告
perf record -g -p <PID> -- sleep 10
perf report
```

### 场景二：load 高，判断是 CPU 还是 IO

```shell
# 1. 看 load
uptime
# 2. 看 vmstat 的 wa（等 IO）和 us/sy（CPU）
vmstat 1 5
# wa 高 → IO 瓶颈；us/sy 高 → CPU 瓶颈
# 3. 看谁在等 IO
iostat -x 1 5
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先 top 找进程，再 perf 深入找函数，逐层定位
2. load 高先区分 CPU（us/sy）还是 IO（wa），别混为一谈
3. 上下文切换高看 pidstat -w，可能是进程太多/频繁调度
4. CPU 亲和性按需用（缓存敏感/隔离核心），别盲目绑
5. perf 是终极工具，但先会用 top/vmstat/mpstat 再上 perf

### 踩坑记录

```text
坑 1：load 高就加 CPU，结果是 IO 瓶颈
结论：load 高，加了 CPU 还是高。
原因：load 含等 IO 的进程，wa 高说明是 IO 瓶颈。
解法：vmstat 看 wa，wa 高查 IO（iostat），不是 CPU。

坑 2：只看整体 CPU，忽略单核飙高
结论：多核机器某进程 %CPU 100%，整体 CPU 不高。
原因：单核跑满，其他核空闲，负载不均。
解法：mpstat -P ALL 看每核，top 按 1 看每核负载。

坑 3：上下文切换高，误以为是 CPU 慢
结论：CPU 不忙但系统响应慢，cs 很高。
原因：进程频繁切换，CPU 浪费在切换上。
解法：pidstat -w 找切换大户，减少进程数/优化调度。

坑 4：perf 报权限不足
结论：perf top/record 报 permission error。
原因：perf 需要权限（内核 perf_event 限制）。
解法：用 root，或调整 /proc/sys/kernel/perf_event_paranoid。

坑 5：CPU 亲和性绑错导致性能下降
结论：taskset 绑定后反而更慢。
原因：绑定限制了并行，或绑到的核已被其他进程占用。
解法：先测再绑，绑定前了解核的负载分布。
```
