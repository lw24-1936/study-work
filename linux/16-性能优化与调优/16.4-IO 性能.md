## 概述

IO 性能分析回答「**磁盘快不快、瓶颈在哪、谁在读写**」：IO 栈（应用→VFS→页缓存→块层→设备）、IO 指标（IOPS/吞吐/延迟/队列深度）、IO 调度器（内核怎么排序请求）、文件系统（ext4/XFS 与挂载参数）、磁盘类型（HDD/SSD/NVMe）。磁盘是系统最慢的部件之一，IO 瓶颈会拖垮一切。

核心指标：

```text
IO 性能三要素：
1. IO 调度器 —— 内核排序 IO 请求的策略（mq-deadline/none/bfq/kyber）
2. 吞吐与延迟 —— iostat 的 rkB/s（吞吐）、await（延迟）、%util（繁忙度）
3. 队列深度 —— 设备队列里排队的请求数（aqu-sz），饱和的直接信号
```

IO 问题两种典型形态：**「设备饱和 → 排队变长 → 延迟升高」**和**「应用同步等 IO → 进程 D 状态 → load 高 CPU 闲」**。分析路线：top 看 iowait → iostat 看哪个盘慢/饱和 → pidstat/iotop 找进程 → 看盘类型与调度器 → 针对性调优。

本机是 Ubuntu 24.04 笔记本（根盘为 1TB HDD + 一块 119GB SSD 从盘），以下实测数据均来自本机。

## 核心概念

### 1. IO 栈

从应用到底层设备的完整链路，每层都可能成为瓶颈：

```text
应用层        read()/write()/fsync()/mmap
  ↓ 系统调用
VFS 层        虚拟文件系统：统一接口、页缓存、dentry/inode 缓存
  ↓
文件系统层    ext4/xfs/btrfs：inode 索引、块映射、日志（journal）
  ↓
页缓存层      读命中直接返回；写缓存为脏页，后台异步回写
  ↓
块层          bio 请求 → IO 调度器（mq-deadline/none/bfq）→ blk-mq 多队列
  ↓
驱动层        AHCI/NVMe 驱动、DMA 传输、中断
  ↓
物理设备      HDD（机械寻道）/ SSD / NVMe
```

### 2. 三个核心指标：IOPS / 吞吐 / 延迟

- **IOPS**：每秒 IO 次数（iostat 的 r/s + w/s）。衡量「处理了多少次请求」——数据库随机小 IO 场景最看重 IOPS。
- **吞吐 throughput**：每秒读写的数据量（rkB/s/wkB/s）。衡量「传了多少数据」——顺序大 IO 场景（备份、视频）最看重吞吐。
- **延迟 await**：单次 IO 从发出到完成的平均时间。SSD <1ms，HDD 几 ms~几十 ms。await 高 = IO 慢。

小 IO 看 IOPS，大 IO 看吞吐，两者都要时看延迟。**磁盘类型决定上限**：本机 HDD 实测顺序读 33MB/s、随机写 25.6MB/s，而缓存命中读 14.9GB/s——差了三个数量级。

### 3. iostat -x 关键字段

```text
r/s w/s          每秒读写次数（IOPS）
rkB/s wkB/s      每秒读写 KB（吞吐）
rrqm/s wrqm/s    每秒合并的请求数（%rrqm/%wrqm 是合并比例）
r_await w_await  读/写平均延迟（ms）
rareq-sz wareq-sz 平均请求大小（KB）
aqu-sz           平均队列深度（排队请求数，饱和直接信号）
%util            设备忙时间占比（≈饱和程度）
```

新版 sysstat（12+）已**移除 svctm 列**（旧版用它估设备服务时间，误差大），判断设备能力用 `await + aqu-sz + %util` 组合。

### 4. IO 调度器 scheduler

决定「内核把请求按什么顺序发给磁盘」：

```text
mq-deadline  默认：读/写双队列按到期时间排序 + 合并相邻请求，
             读优先（读延迟敏感）。HDD 减少寻道，兼顾延迟与吞吐。
none         不调度：请求直通设备队列。SSD/NVMe 无寻道，省 CPU 省延迟。
bfq          公平调度：按进程分配带宽，桌面/多租户场景。
kyber        延迟目标调度：动态调整队列深度保延迟，部分云环境默认。
```

### 5. 队列深度与 blk-mq

- **队列深度**：设备队列能排多少请求（`nr_requests`）。深 → 并发多、吞吐高，但延迟可能升高；浅 → 延迟低、吞吐受限。
- **blk-mq（多队列）**：现代内核默认。每个 CPU 一个软件队列，设备侧多个硬件队列（NVMe 每队列独立中断），并发 IO 不再争一把锁。本机 SATA HDD 只有 1 个硬件队列（AHCI 限制）。

### 6. 文件系统与挂载参数

- **ext4**（Ubuntu 默认）：日志文件系统，inode 固定数量（本机实测 60981248 个），适合通用与中小文件。
- **XFS**（RHEL 8+ 默认）：动态 inode、大文件/大并发性能好，适合大数据。
- 挂载参数：`noatime`（关 atime 更新省写）、`barrier`（ext4 保序，防掉电乱序）、`data=ordered`（日志模式，先写数据再记日志）。

### 7. 磁盘类型对比

```text
HDD    机械：寻道慢，随机 IO 差（本机实测随机 4k 写 25.6MB/s、await 15-22ms）
       顺序尚可（33MB/s），适合冷数据/顺序日志
SSD    闪存：随机快（~500MB/s 级），无寻道，IOPS 高
NVMe   PCIe 直连：3-7GB/s，多队列（每队列独立中断），延迟 <0.1ms
随机 vs 顺序：HDD 随机/顺序差距 10 倍以上，SSD 差距小（2-3 倍）
```

### 8. 脏页回写与 D 状态

- **脏页回写**：应用 write 只写页缓存，flusher 线程按 `dirty_background_ratio`（后台）/`dirty_ratio`（同步阻塞）阈值回写。iostat 看到的写盘滞后于应用写调用。
- **D 状态**：进程阻塞在不可中断的 IO 等待（等磁盘/NFS），`ps` 的 STAT 列显示 D。D 进程多 + load 高 + CPU 闲 = IO 瓶颈（或磁盘/NFS 故障）。

## 工作原理

### 1. 完整 IO 数据流

```text
【读路径】
read() → VFS → 页缓存命中？→ 命中：直接拷贝返回（0 次磁盘 IO，本机实测
                             缓存命中读 1.4GB/s）
              → 未命中：page fault → 文件系统定位块（ext4 读 inode/块映射）
                → 构造 bio → 调度器排队 → 驱动 DMA → 磁盘读出
                → 数据写入页缓存 → 返回应用（下次命中缓存）

【写路径】
write() → VFS → 写入页缓存，标记脏页 → 立即返回（快，不碰磁盘）
  → flusher 线程异步回写：dirty_background_ratio（10%）后台刷
  → dirty_ratio（20%）时写进程同步阻塞刷（防脏页无限膨胀）
  → fsync()/O_DIRECT：绕过页缓存，同步写盘（数据安全换速度）

【调度路径】
bio → mq-deadline：按 deadline 排序（读优先）+ 合并相邻扇区请求
   → blk-mq 软件队列（每 CPU 一个）→ 硬件队列 → DMA → 设备
```

### 2. 调度器工作机制

- **mq-deadline**：维护读、写两个队列，请求按「到期时间」排序，读请求优先（等待超过 deadline 的请求提升优先级）；相邻扇区请求合并成一个大请求（本机实测 %rrqm 可达 81%）。HDD 上合并排序直接减少寻道次数。
- **none**：请求直接进设备队列，不做合并排序。SSD/NVMe 随机访问无代价，调度器的排序合并反而增加 CPU 开销与延迟。
- 调度器是**每块设备**一个配置（`/sys/block/<设备>/queue/scheduler`），切换即时生效，当前队列中的请求完成后按新策略处理。

### 3. %util 与队列深度的关系（判断饱和的关键）

```text
%util = 设备忙于 IO 的时间占比（采样周期内）
单队列时代（HDD）：%util 100% ≈ 设备真的满了（一个时刻只能做一个 IO）
多队列时代（SSD/NVMe）：
  %util 100% 未必饱和 —— 设备可以同时服务多个队列的请求，
  忙 100% 但仍能吞吐更多 IO（并发吸收）
正确判断饱和的组合拳：
  ① %util 持续 100%
  ② aqu-sz 持续增长（请求排队越来越多）
  ③ await 随负载上升（排队时间变长）
  三者同时出现才是真饱和；只看 %util 会误判（常见坑）
```

### 4. 回写与掉电安全

```text
ext4 日志模式（挂载时指定，本机根分区未显式指定即默认 ordered）：
  data=ordered  先写数据块，再写日志 —— 崩溃后文件内容一致（默认，推荐）
  data=writeback 只保证元数据一致 —— 快但崩溃可能文件内容损坏
  data=journal  数据和元数据都进日志 —— 最安全最慢
barrier=1（默认开）：确保日志提交前数据先落盘（防乱序）
写密集场景别为性能乱关 barrier/data=ordered —— 掉电=数据损坏风险
```

### 5. blk-mq 与 NVMe 多队列

```text
传统单队列：全局一把锁，高并发下 CPU 争锁成为瓶颈
blk-mq（内核 4.x 起默认）：
  软件队列：每 CPU 一个，本 CPU 提交的请求不跨核锁
  硬件队列：NVMe 每队列一个独立中断 + 独立提交队列，
            多核并发直接并行下发，IOPS 线性扩展
实测：本机 SATA 盘 sda/sdb 各只有 1 个硬件队列（AHCI 接口限制），
      NVMe 盘通常是 4-16 个（每队列绑定不同 CPU/中断）
```

$ hdparm -tT /dev/sda2

## 配置文件解析

### 1. 块设备队列参数（/sys/block/<设备>/queue/）

```text
scheduler         调度器（none/mq-deadline/bfq/kyber）—— 每盘独立
nr_requests       队列深度（请求上限，大 = 高吞吐，小 = 低延迟）
read_ahead_kb     预读大小（顺序读调大，随机读调小）
rotational        1=机械盘 0=SSD（内核据此默认调整队列深度等）
write_cache       设备写缓存策略（write back / write through）
io_poll           是否支持轮询模式（NVMe 低延迟优化）
```

### 实测（本机）——队列参数

```text
$ for d in /sys/block/sd[a-z]; do [ -e "$d/queue" ] && echo \
> "$(basename $d): scheduler=$(cat $d/queue/scheduler) rotational=$(cat $d/queue/rotational) \
> nr_requests=$(cat $d/queue/nr_requests) read_ahead_kb=$(cat $d/queue/read_ahead_kb)"; done
sda: scheduler=none [mq-deadline]  rotational=1 nr_requests=64 read_ahead_kb=8192
sdb: scheduler=none [mq-deadline]  rotational=0 nr_requests=64 read_ahead_kb=128

$ blockdev --getra /dev/sda     # 预读（扇区，512B/扇区）：16384 扇区 = 8MiB
16384
$ ls /sys/block/sda/mq/ | grep -cE '^[0-9]+$'   # blk-mq 硬件队列数
1
$ cat /sys/block/sda/queue/write_cache
write back
```

- HDD（sda）预读 8192KiB（大，适合顺序读）；SSD（sdb）只有 128KiB（SSD 随机快，大预读无意义）。
- 硬件队列数 1（SATA AHCI），NVMe 会是 4-16 个。

### 2. 文件系统参数（tune2fs / 挂载选项）

```text
ext4 用 tune2fs/dumpe2fs 查看（本机实测）：
  Block size 4096 / Inode count 60981248 / Reserved block 12195737（5%）
  Filesystem features: has_journal ext_attr dir_index extent 64bit
                       flex_bg sparse_super large_file metadata_csum ...
  默认挂载选项：user_xattr acl（atime 策略由挂载参数决定）
XFS 用 xfs_info/xfs_admin（RHEL 默认文件系统，本机未装/无 XFS 盘）
挂载参数（/etc/fstab）：
  noatime           不更新访问时间（省大量写 IO）
  barrier=1         保序（ext4 默认，别关）
  data=ordered      日志模式（ext4 默认）
  nobarrier         仅适合有电池保护的 RAID 卡场景
```

### 3. 持久化调度器设置（echo 是临时的）

```text
echo none > /sys/block/sda/queue/scheduler 只对本次开机生效，重启丢失。
持久化两种方式：
1. udev 规则（推荐）—— 设备出现时自动应用：
   /etc/udev/rules.d/60-io-scheduler.rules：
   ACTION=="add|change", KERNEL=="sd*[!0-9]", ATTR{queue/scheduler}="none"
2. systemd 服务（rc.local）—— 开机后执行：
   [Service] ExecStart=/bin/sh -c 'echo none > /sys/block/sda/queue/scheduler'
```

## 应用场景实战

### 场景一：磁盘 IO 慢，定位瓶颈在哪一层

```shell
# 1. 总览：iowait 高不高、有没有 D 状态进程
top -bn1 | grep '%Cpu'            # wa 列高 = 大量时间在等 IO
ps -eo state,pid,comm | grep '^D' # D 进程多 = IO 阻塞

# 2. 定位哪个盘、慢在哪（延迟 vs 饱和）
iostat -x sda sdb 1 5
# await 高 + %util 低 → 设备本身慢（HDD 特性/坏道）
# %util 100% + aqu-sz 涨 + await 涨 → 设备饱和（负载超上限）

# 3. 找是哪个进程在狂读写
pidstat -d 1            # 或 iotop（需安装）
# 4. 区分「应用同步 IO」还是「内核回写」：
cat /proc/vmstat | grep -E 'nr_dirty'   # 脏页多+写盘滞后 = 回写压力
# 5. 看盘类型与调度器是否匹配
cat /sys/block/sda/queue/rotational
cat /sys/block/sda/queue/scheduler
```

本机实测（空闲态）：r_await 15ms / w_await 22ms（HDD 正常）、%util 12%、无 D 进程——磁盘不是当前瓶颈。

### 场景二：SSD 上把调度器切成 none 并持久化

```shell
# 1. 确认是 SSD（rotational=0）
cat /sys/block/sdb/queue/rotational
# 2. 切换调度器（即时生效）
echo none > /sys/block/sdb/queue/scheduler
# 3. 验证
cat /sys/block/sdb/queue/scheduler
# 4. 持久化（udev 规则，重启不丢）
cat > /etc/udev/rules.d/60-io-scheduler.rules <<'EOF'
ACTION=="add|change", KERNEL=="sd*[!0-9]", ATTR{queue/rotational}=="0", ATTR{queue/scheduler}="none"
EOF
udevadm control --reload-rules
```

注意：RHEL 8+ 中 mq-deadline 仍是默认；RHEL 9 对 NVMe 默认 none。切换前确认盘类型，**别把 HDD 切 none**（HDD 需要调度器排序减少寻道）。

### 场景三：数据库 4k 随机 IO 压测与优化（fio）

```shell
# fio 未安装，以下为标准压测模板（apt install fio 后执行）
# 场景 A：4k 随机读（模拟数据库查询，最看重 IOPS 与延迟）
fio --name=randread --rw=randread --bs=4k --iodepth=32 --numjobs=8 \
    --size=2G --direct=1 --ioengine=libaio --runtime=60 --time_based
# 看输出：read: IOPS=..., BW=...MiB/s, lat (usec): avg=...

# 场景 B：128k 顺序写（模拟日志/备份写入，最看重吞吐）
fio --name=seqwrite --rw=write --bs=128k --iodepth=16 --numjobs=4 \
    --size=2G --direct=1 --ioengine=libaio --runtime=60 --time_based

# 场景 C：70/30 混合读写（模拟 OLTP 混合负载）
fio --name=mix --rw=rw --rwmixread=70 --bs=8k --iodepth=32 --numjobs=8 \
    --size=2G --direct=1 --ioengine=libaio --runtime=60 --time_based
```

```text
参数含义与调参方向：
  --bs=4k     数据库页大小（InnoDB 默认 16k，按实际调）
  --iodepth   队列深度：32-64 是数据库推荐区间（过高延迟升）
  --numjobs   并发进程数：模拟多连接，8 ≈ 8 核并发
  --direct=1  绕过页缓存，测真实磁盘（必须）
  --ioengine=libaio  异步 IO（高并发必选）
优化动作（压测后按瓶颈选）：
  IOPS 不够 → SSD/NVMe 或增加 numjobs 摊满多队列
  延迟高    → 降 iodepth、切 none 调度器、确认数据盘独立
  吞吐不够 → 顺序场景调大 bs、检查 RAID 条带与文件系统块大小
```

### 场景四：顺序写场景（日志/备份）回写调优

```shell
# 症状：写盘突刺（iostat w/s 周期性飙高），应用写调用并不慢
# 原因：脏页攒到 dirty_background_ratio（10%）才后台刷，一刷一大波
# 优化 1：让回写更均匀（写密集机器）
sysctl -w vm.dirty_background_ratio=5
sysctl -w vm.dirty_ratio=15
# 优化 2：日志盘挂载关 atime（省一半元数据写）
#   /etc/fstab: UUID=xxx /data ext4 defaults,noatime 0 2
# 优化 3：确认日志模式 ordered（默认，别为性能改 writeback）
tune2fs -l /dev/sda2 | grep -i 'Default mount options'
# 优化 4：观察回写是否跟得上
cat /proc/vmstat | grep -E 'nr_dirty|nr_writeback'
```

### 场景五：预读（readahead）调优

```shell
# 顺序读场景（视频流、批量导出）：调大预读
blockdev --setra /dev/sda 32768        # 16MiB（临时）
# 或持久化 udev：ATTR{queue/read_ahead_kb}="16384"

# 随机读场景（数据库）：调小，避免预读浪费
blockdev --setra /dev/sdb 256          # 128KiB

# 查看当前值
blockdev --getra /dev/sda              # 本机实测 16384 扇区 = 8MiB
cat /sys/block/sda/queue/read_ahead_kb # 本机实测 8192 KiB
```

原则：**顺序读调大预读，随机读调小预读**。预读是「赌你继续往下读」，随机负载赌不中就是白读浪费带宽。

## 性能与调优

### 1. 调度器选择（对比表）

```text
调度器        适用场景                特点
mq-deadline  HDD / 通用默认          读优先 + deadline 排序 + 合并，减寻道
none         SSD / NVMe             直通无调度，省 CPU 低延迟
bfq          桌面 / 多租户共享盘     按进程公平分配带宽，防一个进程吃满
kyber        低延迟敏感（云盘）       动态调节队列深度保延迟目标

Ubuntu 24.04 实测：sda（HDD）默认 mq-deadline，可选 none；
内核默认 NVMe 设备为 none。
Red Hat 系差异：
  RHEL 8  默认 mq-deadline（含 NVMe）
  RHEL 9  NVMe 默认 none
切换命令：echo <scheduler> > /sys/block/<dev>/queue/scheduler
```

### 2. 按负载类型调优清单

```text
数据库（随机 4k 小 IO）：
  SSD/NVMe + none 调度器 + 预读调小 + iodepth 32-64
  独立数据盘/日志盘（避免日志写拖查询读）
日志/备份（顺序大 IO）：
  HDD 也行但看吞吐；预读调大；noatime；dirty 参数调均匀
桌面/多用户（混合负载）：
  bfq 调度器；iowait 高时先查单进程 IO 大户
写密集 + 掉电安全：
  保持 data=ordered + barrier；别乱关（本机 ext4 默认开启）
```

### 3. 文件系统挂载参数调优

```text
noatime：不更新访问时间——大量小读写的服务（Web 静态、代码库）
         可显著减少元数据写（省 30-50% 写 IO）。注意 nodiratime 已并入。
relatime：内核默认（本机实测 rw,relatime）——atime 有界更新，折中。
barrier=1：ext4 默认，保序防掉电乱序；只有带电池保护的 RAID 卡才考虑关。
data=ordered：ext4 默认日志模式（先数据后日志），崩溃一致性好；
     writeback 模式更快但崩溃可能文件内容损坏（生产不建议）。
日志盘独立：日志放 SSD（或单独盘），元数据写不拖数据写。
```

### 4. 脏页回写调优

```text
vm.dirty_background_ratio（默认 10%）：后台异步回写阈值
vm.dirty_ratio（默认 20%）：写进程同步阻塞阈值
写密集机器的两类调法：
  想更均匀：background 调小（5%）→ 回写更勤更碎，避免 IO 突刺
  想更高吞吐：接受突刺，把 background 调大（20%）→ 攒得多一次刷
调完看 /proc/vmstat 的 nr_dirty 与 iostat 的 w/s 形态验证
```

### 5. RAID 与 LVM 对 IO 的影响（概念）

```text
RAID（详见 [[06.4-RAID]]）：
  RAID0 条带：吞吐 ≈ 盘数 × 单盘，无冗余
  RAID1/10：镜像，读并行，写双份
  RAID5/6：校验盘，小随机写有写惩罚（读-改-写），数据库慎用
LVM（详见 [[06.3-逻辑卷管理 LVM]]）：
  条带化（lvcreate -i2 -I64）可提吞吐；快照会放大写 IO（COW）
对齐：文件系统块大小（4k）与 RAID 条带/SSD 擦除块对齐，避免 IO 放大
```

## 安全与权限

```text
1. 调度器/队列参数修改 —— echo 到 /sys/block 需要 root；改错
   （如 HDD 切 none）影响整盘性能，改前确认盘类型与负载
2. iotop 权限 —— 查看其他进程 IO 需要 root（或 CAP_SYS_ADMIN）
3. fio 压测 —— 生产环境直接压测会打满磁盘影响线上业务；用测试盘
   或低负载档位（--runtime 短、--numjobs 小），并通知业务方
4. dd/hdparm 直读裸设备 —— 有数据覆盖风险（写裸盘前再三确认设备名）
5. smartctl/badblocks —— 扫描会占用大量 IO（badblocks 只读扫描也
   会拉高磁盘负载），生产环境避开业务高峰
6. 挂载参数改动 —— /etc/fstab 写错会导致开机失败（如 noatime 拼错、
   UUID 错误），改后先 mount -o remount 验证再重启
```

## 故障排查

### 案例一：iowait 高——是应用同步 IO 还是内核回写

```shell
# 排查路线图（自上而下）：
# ① 确认确实是 IO 问题：top 的 wa 高、load 高但 CPU 闲
top -bn1 | grep '%Cpu'              # wa >20% 持续 = IO 等待严重
# ② 哪个盘在忙：iostat -x
iostat -x 1 5
# ③ 是应用同步 IO 还是内核回写？看 vmstat bo 与脏页
vmstat 1 5                          # bo 高 + bi 低 = 在写回
cat /proc/vmstat | grep -E 'nr_dirty|nr_writeback'
# ④ 应用同步 IO：pidstat -d 找进程（或 iotop）
pidstat -d 1 | sort -k3 -nr | head
# ⑤ 内核回写：dirty 参数调优 + 找谁在大量写文件（lsof +D）
# ⑥ D 状态进程：ps -eo state,pid,comm | grep '^D'
```

本机实测：wa=0.0、PSI io some avg10=13.79（有后台压力但未到瓶颈）、无 D 进程——IO 健康。

### 案例二：D 状态进程堆积——load 高、CPU 闲、应用卡死

```shell
# 1. 找 D 状态进程
ps -eo state,pid,comm | grep '^D'
# 2. 看阻塞在内核哪里
cat /proc/<PID>/stack    # 需要 root，输出内核栈（如 ext4 / NFS 函数）
# 3. 常见原因排查
#    - 磁盘硬件故障：dmesg | grep -i 'I/O error'
#    - NFS 挂载卡死：网络断、服务端慢 → D 进程堆在 nfs 栈
#    - 磁盘 IO 饱和：iostat %util 100%
# 4. 处理：D 状态杀不掉（不可中断），只能等 IO 恢复或重启机器
```

D 状态（TASK_UNINTERRUPTIBLE）进程**不能被 kill**，只能等内核 IO 完成；大量 D 进程 + 无 IO 活动 = 磁盘/NFS 故障，看 dmesg 找硬件错误。

### 案例三：磁盘饱和——%util 100% + 排队增长

```shell
# 1. 确认真饱和（三个信号一起看）
iostat -x sda 1 5
#    %util≈100% + aqu-sz 持续增长 + await 随负载上升 = 真饱和
# 2. 是读还是写饱和
iostat -d sda 1         # r/s vs w/s、rkB/s vs wkB/s
# 3. 谁在打
pidstat -d 1            # iotop 更直观（需安装）
# 4. 处置优先级：
#    找异常进程 → 限流/停掉 → 降负载（错峰、限速）
#    → 硬件升级（SSD→NVMe、加盘 RAID）→ 应用层优化（索引、批量）
```

注意：**SSD/NVMe 上 %util 100% 未必饱和**（多队列并发吸收），务必结合 aqu-sz 与 await 判断；HDD 上 %util 100% 基本等于真满了。

### 案例四：磁盘硬件故障（坏道/SMART 报错）

```shell
# 1. 内核报错（最快信号）
dmesg | grep -i -E 'I/O error|blk_update_request|ata.*failed'
# 2. SMART 健康（本机 smartctl 未装，apt install smartmontools）
smartctl -a /dev/sda
#    重点属性：
#    Reallocated_Sector_Ct      重映射扇区（>0 持续涨 = 盘在坏）
#    Current_Pending_Sector     待重映射扇区（>0 = 有坏块在等）
#    Offline_Uncorrectable      不可纠正错误
#    UDMA_CRC_Error_Count       接口错误（线缆/接口问题）
# 3. 坏道扫描（只读，生产避开高峰）
badblocks -sv /dev/sda2
# 4. 处置：备份 → 换盘；接口错误先换线/换口
```

SMART 阈值经验：Reallocated/Pending 扇区数**持续增长**是换盘信号（个位数波动可观察），同时出现 dmesg I/O error 应立刻备份。

## 常见问题

```text
Q1: await 高是什么原因？
A: await 是单次 IO 平均等待时间。原因：HDD 寻道（正常 10-30ms）、
   设备饱和排队（aqu-sz 涨）、磁盘老化坏道（smartctl）、回写突刺。
   SSD 上 await >10ms 基本就是饱和或故障。

Q2: SSD 为什么用 none 调度器？
A: SSD/NVMe 无寻道，随机访问代价低，调度器的排序/合并反而增加 CPU
   开销和延迟。none 直发最快。HDD 不能切 none（无排序=寻道乱飞）。

Q3: IOPS 和吞吐有什么区别？
A: IOPS 是每秒请求次数（小 IO 场景重要，如数据库随机读写）；吞吐是
   每秒数据量（大 IO 场景重要，如视频/备份）。小 IO 看 IOPS，大 IO
   看吞吐，两者都要看延迟。

Q4: %util 100% 就是磁盘坏了吗？
A: 不是。%util 是设备忙时间占比，100% 只说明「一直在忙」。HDD 上
   基本等于饱和；SSD/NVMe 多队列并发时 100% 未必饱和（还能加负载）。
   结合 aqu-sz 增长 + await 上升判断，硬件是否坏看 smartctl/dmesg。

Q5: dd 测速为什么那么快/那么慢？
A: 快（14.9GB/s）是因为读到了页缓存，不是磁盘速度；慢（25MB/s）才
   是 HDD 真实速度。测磁盘必须绕过缓存：dd 加 oflag=direct（写）/
   iflag=direct（读），或用 hdparm -tT 的 buffered 行。

Q6: iowait 高是不是 CPU 问题？加 CPU 有用吗？
A: 没用。iowait 是 CPU 等待 IO 完成的时间占比，高说明瓶颈在磁盘。
   加 CPU 只会让更多线程排队等 IO。正确做法：iostat 定位盘 →
   pidstat 找进程 → 优化 IO（SSD/调度器/应用层）。

Q7: 随机读慢怎么优化？
A: 按顺序：① 确认盘类型（HDD 随机本来就慢，换 SSD）；② 调度器
   SSD 切 none；③ 预读调小（随机读预读浪费）；④ 应用层 iodepth 调高
   增加并发（fio 验证）；⑤ 数据库类优化索引减少随机 IO。

Q8: 写了文件但 iostat 没立刻看到写盘，正常吗？
A: 正常。write 只进页缓存（脏页），flusher 线程按 dirty_background_
   ratio（10%）或 dirty_expire_centisecs（30 秒）异步回写。要立即
   落盘用 fsync/sync。iostat 看到写盘是滞后且成批的。
```

## 面试题

```text
1. 描述一次 read() 的完整 IO 路径。
   答：read() → VFS → 页缓存命中？命中直接返回（零磁盘 IO）；未命中
   触发缺页 → 文件系统（ext4）定位 inode 与块 → 构造 bio → IO 调度器
   （mq-deadline 排序合并）→ blk-mq 队列 → 驱动 DMA → 磁盘读出 → 写入
   页缓存 → 返回。write 路径则是先写页缓存标记脏页，由 flusher 异步
   回写，fsync/O_DIRECT 才同步落盘。

2. await、svctm、%util 分别衡量什么？
   答：await 是单次 IO 平均完成时间（含排队+服务，衡量延迟）；svctm
   是纯服务时间（旧版 iostat 指标，误差大，sysstat 12+ 已移除，用它
   计算能力已不推荐）；%util 是设备忙时间占比（衡量繁忙度）。组合看：
   await 高 + %util 低 = 设备本身慢；%util 100% + aqu-sz 涨 = 饱和排队。

3. IOPS 和吞吐的区别？分别适合什么场景？
   答：IOPS = 每秒 IO 次数，随机小 IO 场景（数据库 4k 读写）看它；
   吞吐 = 每秒数据量，顺序大 IO 场景（备份、视频、日志）看它。评估
   磁盘能力要两者分别测（fio 分 rw=randread 与 rw=write 两组）。

4. 常见 IO 调度器及选择依据？
   答：mq-deadline（默认，读优先+deadline 排序+合并，HDD 减少寻道）；
   none（直通，SSD/NVMe 无寻道场景，省 CPU 低延迟）；bfq（进程公平
   分配带宽，桌面/多租户）；kyber（延迟目标调度）。选择依据是盘类型
   与负载：机械盘用 mq-deadline，SSD/NVMe 用 none，多租户共享用 bfq。

5. SSD 上 %util 100% 一定饱和吗？
   答：不一定。%util 基于「忙/闲」时间统计，单队列时代 ≈ 饱和；SSD/
   NVMe 多队列可并发服务多个请求，设备 100% 忙但仍能吞吐更多 IO。
   真饱和要看 aqu-sz（排队深度）持续增长 + await 随负载上升。

6. iowait 高怎么排查？
   答：① top 确认 wa 高、load 高但 CPU 闲；② iostat -x 定位哪块盘、
   区分慢（await 高）与饱和（%util 高 + aqu-sz 涨）；③ pidstat -d/
   iotop 找 IO 大户；④ 区分应用同步 IO 与内核回写（vmstat bo、
   nr_dirty）；⑤ 看 D 状态进程与 dmesg 硬件错误；⑥ 按瓶颈调优
   （调度器/预读/SSD/应用层）。

7. fio 压测的关键参数有哪些？
   答：--rw（read/write/randread/randwrite/rw 混合）、--bs（块大小，
   数据库 4k-16k）、--iodepth（队列深度，32-64 常见）、--numjobs
   （并发进程数，模拟多连接）、--direct=1（绕过页缓存，必须）、
   --ioengine=libaio（异步 IO）、--size/--runtime/--time_based
   （时长控制）。输出看 IOPS、BW（吞吐）、lat avg/p99。

8. noatime、barrier、data=ordered 分别是什么？有什么风险？
   答：noatime 是不更新访问时间，减少元数据写 IO（省写放大）；
   barrier 是 ext4 的 IO 保序屏障，防掉电时日志与数据乱序（默认开，
   关闭有数据损坏风险）；data=ordered 是日志模式，先写数据再记日志，
   崩溃后数据一致（默认），writeback 模式更快但崩溃可能文件损坏。
   三者的共同点是：为性能关闭安全特性前，必须评估掉电/崩溃风险。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 判断 IO 性能用 `iostat -x`，看 **await + %util + aqu-sz** 三个组合，别只看一个
2. SSD/NVMe 用 none 调度器，HDD 用 mq-deadline——先确认 rotational 再切
3. 调度器/预读/队列参数的修改要 udev 持久化，别只 echo（重启丢失）
4. 测磁盘速度必须绕过页缓存（`oflag=direct` / `hdparm -tT` buffered 行）
5. 数据库随机 IO：SSD + none + 预读调小 + iodepth 32-64（fio 验证）
6. 顺序读调大预读，随机读调小预读（read_ahead_kb / blockdev --setra）
7. 写密集机器：noatime + dirty_background_ratio 调小让回写均匀
8. 保持 data=ordered + barrier 默认（掉电安全 > 那点性能）
9. 压测用 fio 分级（低并发起步），生产环境避开业务高峰
10. 磁盘故障看三处：dmesg I/O error、smartctl 属性趋势、iostat 异常

### 踩坑记录

```text
坑 1：只看吞吐不看延迟
结论：磁盘吞吐看着还行，但 await 高达几十 ms，应用照样卡。
原因：吞吐是「总量」，延迟是「单次体验」，HDD 随机小 IO 高延迟
     正是数据库卡的根源。
解法：iostat -x 同时看 r_await/w_await；延迟敏感场景优先优化延迟。

坑 2：HDD/SSD 调度器用反
结论：SSD 还用 mq-deadline 觉得性能没发挥；或 HDD 切了 none 之后
     随机 IO 暴跌。
原因：没按盘类型选调度器。SSD 无寻道用 none 省开销；HDD 需要
     mq-deadline 排序减少寻道。
解法：先 cat /sys/block/*/queue/rotational 确认盘类型再切。

坑 3：%util 100% 就判断磁盘坏了/饱和，直接换盘
结论：换盘后问题依旧，%util 还是 100%。
原因：%util 只是忙时间占比；SSD/NVMe 多队列并发下 100% 未必饱和；
     也可能是应用疯狂写（回写突刺）或调度问题。
解法：结合 aqu-sz（排队增长=饱和）与 await（上升=排队），再决定
     是限流、调优还是换硬件。

坑 4：改了调度器重启又变回去
结论：echo none > scheduler 之后重启恢复 mq-deadline。
原因：/sys 是运行时伪文件系统，重启即失。
解法：udev 规则（/etc/udev/rules.d/60-io-scheduler.rules）持久化。

坑 5：预读调太大，随机读反而变慢
结论：read_ahead_kb 调到 16MiB，数据库随机读性能下降。
原因：预读适合顺序读；随机读时预读的页大多用不上，白读浪费磁盘
     带宽和缓存。
解法：按负载类型调——顺序读调大、随机读调小（数据库 128-256KiB）。

坑 6：生产环境直接 fio/dd 压测，打满磁盘
结论：压测 2 分钟，线上业务卡死 10 分钟（排队请求堆积）。
原因：压测占满设备队列，真实业务请求全部排队。
解法：用测试盘/低档位（--numjobs 2 --runtime 30）先小规模验证，
     生产压测要申请变更窗口。

坑 7：dd 测速测到的是内存速度
结论：dd 读 1GB 显示 14GB/s，以为磁盘很快，实际磁盘只有 33MB/s。
原因：读命中页缓存（文件刚写过/常读），没碰磁盘。
解法：读加 iflag=direct、写加 oflag=direct，或用 hdparm -tT 的
     buffered 行，才是真实磁盘速度。

坑 8：iowait 高当成 CPU 忙，加 CPU 无济于事
结论：load 20 以为 CPU 不够，加核后更卡。
原因：iowait 是等 IO 的时间，D 状态进程也计入 load；瓶颈在磁盘。
解法：top wa 高 + CPU idle 高 = IO 瓶颈；iostat 定位盘后优化 IO，
     不是加 CPU。

坑 9：乱关 barrier/data=ordered 追求性能，掉电丢数据
结论：为了写性能关 barrier 改 writeback，一次断电文件损坏。
原因：保序与日志模式是崩溃一致性的保障。
解法：保持默认（data=ordered + barrier=1）；只有带电池保护的
     RAID 卡才考虑关 barrier，且要有备份验证流程。

坑 10：df -h 显示有空间，但服务写不进去
结论：磁盘没满却报 no space left。
原因：inode 耗尽（小文件海量场景）。df -i 看 inode 使用率。
解法：df -i 确认；删小文件或迁移到 inode 更多的文件系统（XFS
     动态 inode 是 RHEL 默认的原因之一）。
```
