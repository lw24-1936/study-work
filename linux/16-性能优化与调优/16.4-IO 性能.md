## 概述

IO 性能分析回答「磁盘快不快、IO 瓶颈在哪」：IO 调度器（内核怎么排序 IO 请求）、磁盘吞吐与延迟（iostat 的 rkB/s 和 await）、块设备调优（队列深度、调度器选择）。磁盘是系统最慢的部件之一，IO 瓶颈会拖垮一切。核心指标：await（IO 延迟）、%util（设备繁忙度）、r/s w/s（IOPS）。

```text
IO 性能三要素：
1. IO 调度器 —— 内核排序 IO 请求的策略（mq-deadline/none/bfq）
2. 吞吐与延迟 —— iostat 的 rkB/s（吞吐）、await（延迟）
3. 块设备调优 —— 调度器选择、队列深度、预读
```

## IO 调度器

IO 调度器决定「内核怎么排序发给磁盘的 IO 请求」——合并相邻请求、排序减少磁盘寻道。现代多队列调度器：mq-deadline（默认，兼顾延迟和吞吐）、none（不调度，适合 SSD/NVMe）、bfq（公平调度，适合桌面）、kyber（低延迟）。SSD/NVMe 用 none（随机访问快，调度反而浪费），HDD 用 mq-deadline。查看/切换调度器在 /sys/block/<设备>/queue/scheduler。

```text
# 实测（本机 IO 调度器）
$ cat /sys/block/sda/queue/scheduler
none [mq-deadline]
# 当前用 mq-deadline，none 可选（NVMe/SSD 推荐 none）
```

```text
调度器选择：
mq-deadline  默认，兼顾延迟和吞吐，HDD 适用
none         不调度，SSD/NVMe 适用（随机访问快，调度浪费）
bfq          公平调度，桌面/多任务适用
kyber        低延迟，适合对延迟敏感的场景
```

```shell
cat /sys/block/sda/queue/scheduler    # 看调度器
echo none > /sys/block/sda/queue/scheduler   # 切换（SSD 用 none）
```

## 磁盘吞吐与延迟

磁盘性能两个核心指标：吞吐（throughput，每秒读写的 KB/MB）和延迟（latency，单次 IO 的等待时间 await）。iostat -x 看：rkB/s/wkB/s（吞吐）、await（平均延迟）、r/s w/s（IOPS）、%util（繁忙度）。判断：await 高（>10ms）说明 IO 慢，%util 接近 100% 说明设备饱和。SSD 的 await 通常 <1ms，HDD 几 ms~几十 ms。

```shell
iostat -x 1 5           # 扩展指标（吞吐/延迟/繁忙度）
iostat -d sda 1         # 看某块盘的吞吐
```

```text
iostat -x 关键指标：
r/s w/s     IOPS（每秒读写次数）
rkB/s wkB/s 吞吐（每秒读写 KB）
await       平均延迟（高 = IO 慢，SSD <1ms，HDD 几~几十 ms）
%util       设备繁忙度（接近 100% = 饱和）
```

## 块设备调优

块设备调优参数（/sys/block/<设备>/queue/）：scheduler（调度器）、nr_requests（队列深度）、read_ahead_kb（预读）、rotational（是否机械盘）。调优方向：SSD 用 none 调度器 + 大队列深度，机械盘用 mq-deadline + 适当预读，数据库磁盘调大预读（顺序读多）。核心：根据「盘类型（SSD/HDD）+ 负载（顺序/随机）」选调度器和队列参数。

```shell
# 看块设备参数
cat /sys/block/sda/queue/scheduler      # 调度器
cat /sys/block/sda/queue/nr_requests    # 队列深度
cat /sys/block/sda/queue/read_ahead_kb  # 预读大小
cat /sys/block/sda/queue/rotational     # 1=机械盘 0=SSD

# 调优示例：SSD 设 none + 大队列
echo none > /sys/block/sda/queue/scheduler
echo 1024 > /sys/block/sda/queue/nr_requests
```

## 应用场景实战

### 场景一：磁盘 IO 慢，定位瓶颈

```shell
# 1. iostat 看磁盘延迟和繁忙度
iostat -x 1 5
# await 高 + %util 100% = 磁盘饱和
# 2. 找是哪个进程在狂读写
pidstat -d 1
# 3. 看磁盘类型（SSD 还是 HDD）
cat /sys/block/sda/queue/rotational
```

### 场景二：SSD 上把调度器切成 none 提升性能

```shell
# 1. 确认是 SSD（rotational=0）
cat /sys/block/sda/queue/rotational
# 2. 切换调度器
echo none > /sys/block/sda/queue/scheduler
# 3. 验证
cat /sys/block/sda/queue/scheduler
# 4. 持久化（udev 规则或启动脚本）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 判断 IO 性能用 iostat -x，看 await 和 %util
2. SSD/NVMe 用 none 调度器，HDD 用 mq-deadline
3. 先确认盘类型（rotational）再调调度器
4. 找 IO 大户用 pidstat -d 或 iotop
5. 数据库磁盘调大预读（read_ahead_kb），顺序读多时有效

### 踩坑记录

```text
坑 1：只看吞吐不看延迟
结论：磁盘吞吐还行，但 await 很高（几十 ms）。
原因：延迟高说明 IO 慢（寻道/排队），吞吐高不代表体验好。
解法：iostat -x 看 await，延迟高查原因（机械盘/队列/坏道）。

坑 2：SSD 还用 mq-deadline，没切 none
结论：SSD 性能没发挥，还在用 HDD 的调度器。
原因：没根据盘类型切调度器，SSD 用 none 更快。
解法：确认 rotational=0，echo none > scheduler。

坑 3：%util 100% 就判断磁盘坏了
结论：%util 100% 就换盘，其实还有优化空间。
原因：%util 接近 100% 只说明有 IO 排队，可能是调度/队列问题。
解法：结合 await 和 IOPS 判断，先调调度器/队列。

坑 4：改了调度器重启又变回去
结论：echo none > scheduler 重启后恢复 mq-deadline。
原因：直接 echo 是临时的，不持久化。
解法：udev 规则或 rc.local 持久化调度器设置。

坑 5：预读调太大反而变慢
结论：read_ahead_kb 调很大，随机读场景反而慢。
原因：预读适合顺序读，随机读时预读浪费（读了不用）。
解法：按负载类型调预读，顺序读调大、随机读调小。
```
