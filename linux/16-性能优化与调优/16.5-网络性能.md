## 概述

网络性能分析回答三个问题：**「网络快不快」「瓶颈在哪一段」「怎么调优」**。核心指标四个维度：

```text
网络性能四要素：
1. 带宽/吞吐 —— 每秒能传多少数据（带宽打满 = 瓶颈）
2. 延迟 —— RTT 往返时间（高延迟影响交互，尤其长链路）
3. TCP 调优 —— 缓冲、队列、连接参数（决定吞吐上限与连接数上限）
4. 网卡多队列 —— 多核并行收包（单核收包是常见隐形瓶颈）
```

网络瓶颈的典型形态只有几种：**带宽打满**（吞吐到上限）、**TCP 参数没调优**（缓冲小跑不满、队列小连不上）、**单核收包**（某核 softirq 100%）、**连接/端口耗尽**（TIME_WAIT 或 fd 上限）。本文按「指标 → 工具 → 参数 → 实战」的顺序，把定位与调优方法讲透。

本机是 Ubuntu 24.04 笔记本：有线网卡 enp59s0（alx 驱动）当前**未插线（DOWN）**，实际活动网卡是 WiFi 的 wlp0s20f3；同时跑着 Docker（docker0/br-* 桥、十余个 veth）和 tailscale0 隧道。以下实测数据均来自本机（内核 7.0.0-28-generic，8 核）。

## 核心概念

### 1. 带宽、吞吐与线速

- **带宽（bandwidth）**：链路的理论最大传输速率，单位 bps（bit/s），如千兆=1Gbps、WiFi 协商速率、10G 网卡。
- **吞吐（throughput）**：实际测得的传输速率，单位 bps 或 B/s（byte/s）。**吞吐 < 带宽**才是常态，差距太大说明有瓶颈。
- **线速（wire speed）**：物理层每秒能处理的包数上限。**小包限制**：10Gbps 以太网跑 64 字节小包时上限约 14.88 Mpps（百万包/秒），这是 PPS 指标的上限来源——带宽再大，包处理不过来也白搭。

### 2. 延迟与 RTT

- **RTT（Round Trip Time）**：数据往返时间，ping 测的是 ICMP 往返，TCP 连接级 RTT 用 `ss -ti` 看。
- **延迟构成**：传播延迟（光速/距离，绕地球半圈约 130ms）+ 排队延迟（路由器缓冲，bufferbloat 的根源）+ 处理延迟 + 传输延迟。
- **延迟与交互**：交互式应用（数据库、RPC、Web 首包）对延迟敏感；延迟高 ≠ 带宽不够，两者要分开测。

### 3. 丢包与重传

- 丢包（packet loss）发生在：队列溢出（网卡/路由器）、链路错误（误码率）、防火墙丢弃。
- 丢包的直接后果是 **TCP 重传**：超时重传（RTO，毫秒~秒级）和快速重传（收到 3 个重复 ACK）。`netstat -s` 的 `segments retransmited`、`ss -ti` 的 retrans 字段都能看到重传。
- 重传率高 = 网络劣化信号：先看丢包位置（mtr 分段），再看是否拥塞。

### 4. PPS（包每秒）与转发性能

- **PPS（Packets Per Second）**：包处理能力指标，与带宽是两个维度：带宽看「字节」，PPS 看「包数」。
- Linux 软件转发/收包受 CPU 中断与协议栈开销限制：普通服务器单核软中断收包通常 1~2 Mpps 级别；要达到线速小包转发需要 **多队列 RSS + 多核并行**，或 **DPDK（用户态轮询）**、**XDP（eBPF 数据面）** 等旁路技术。
- 测试 PPS 常用内核自带 **pktgen**（`/proc/net/pktgen/` 配置，发高速测试包）或 DPDK pktgen。

### 5. 连接数与并发

- **连接数**（socket 数量）受三层限制：`ulimit -n`（进程级 fd）、`fs.file-max`（全局 fd）、端口范围 `ip_local_port_range`（客户端四元组受端口数限制）。
- **并发**（concurrent connections）是「同时存在的连接」，与**新建速率**（connections/s，受 CPU、队列、accept 速度限制）是两回事。短连接高新建速率会撞 TIME_WAIT 和端口耗尽。

### 6. BDP（带宽延迟积）

**BDP = 带宽 × RTT**，物理含义是「这条链路上最多能同时在途的数据量」。TCP 的发送窗口（受接收窗口 rwnd 和拥塞窗口 cwnd 限制）**必须 ≥ BDP 才能跑满带宽**，否则「链路空着但发不出去」。

```text
例子：100Mbps × RTT 35ms（本机 WiFi 实测级别）
BDP = 100e6 bit/s × 0.035 s ÷ 8 = 437.5 KB
→ TCP 窗口至少要有 437KB，本机 tcp_rmem max=32MB，绰绰有余；
  但如果 rmem/wmem 默认 max 只有 64KB，千兆+30ms 的链路只能跑 ~17Mbps。
```

### 7. TCP 连接队列（SYN 队列与 accept 队列）

高并发下新连接不是直接进应用，而是先排队：

- **SYN 队列（半连接队列）**：收到 SYN 但三次握手未完成的连接，长度由 `tcp_max_syn_backlog` 控制。
- **accept 队列（全连接队列）**：握手已完成、等应用 `accept()` 取走的连接，长度 = `min(应用 listen 的 backlog, net.core.somaxconn)`。
- 队列满的表现：SYN 队列满丢 SYN（客户端 SYN 重传）；accept 队列满丢连接（`ss -lnt` 的 Recv-Q 持续 >0 是信号），详见故障排查案例一。

### 8. TIME_WAIT

主动关闭方在收到 FIN 后进入 TIME_WAIT，等待 **2MSL（通常 60s，`tcp_fin_timeout` 相关）**，作用是「让迟到的旧包在网络中消亡」+「让最后 ACK 能重发」。大量短连接 → 大量 TIME_WAIT → 客户端端口耗尽（`ip_local_port_range` 实测 32768~60999，约 2.8 万个端口，最坏情况 60s 内新建超过这个数就报 `Cannot assign requested address`）。

### 9. 拥塞控制算法

TCP 靠拥塞控制决定「发多快」，经典演进：

- **Reno**：丢包即减半窗口（loss-based 的老祖宗）。
- **Cubic**：Linux 默认，丢包后窗口呈立方曲线恢复，适合中低丢包的长肥管道。
- **BBR**：Google 提出，不再等丢包，而是用「带宽估计 + RTT 估计」建模发送速率，在**高带宽长延迟**链路上明显优于 cubic；模块名 `tcp_bbr`，RHEL 8+/Ubuntu 内核均自带。

### 10. 网卡 offload（TSO/GSO/GRO）

**offload = 把协议栈的活下放给网卡硬件做**：

- **TSO（TCP Segmentation Offload）/ GSO（Generic Segmentation Offload）**：发送侧，应用一次交一个 64KB 大包，网卡/内核负责切成 MTU 大小的段，减少 CPU 逐段处理。
- **GRO（Generic Receive Offload）/ LRO**：接收侧，把多个小段合并成大包再交给协议栈，减少中断与协议栈开销。
- 影响：**排查时 offload 会"骗人"**——GRO 开启时 tcpdump 可能看到 64KB 的"巨包"；TSO 开启时抓包会看到 `checksum incorrect`（校验和由网卡填，抓包点是"未完成"状态）。详见故障排查案例五。

### 11. 多队列与 RSS/RPS

- **RSS（Receive Side Scaling）**：网卡硬件按四元组哈希，把流量分散到多个 RX 队列，每个队列中断绑到不同 CPU 核，多核并行收包。
- **RPS（Receive Packet Steering）**：软件版 RSS——单队列网卡在内核里按哈希把包分发到多个 CPU 的 softnet 队列，缓解单核瓶颈（`/sys/class/net/<dev>/queues/rx-*/rps_cpus`）。
- **RFS（Receive Flow Steering）**：让处理某连接的 CPU 和被哈希到的 CPU 一致，提高缓存命中。
- 检查手段：`ethtool -l`（队列数）、`ethtool -S`（每队列计数）、`/proc/interrupts`（中断分布）、`mpstat -P ALL`（软中断分布）。

## 工作原理

### TCP 吞吐为什么受 BDP 限制

发送方的发送速率由「**窗口 / RTT**」决定：吞吐 ≈ 窗口大小 ÷ RTT。窗口 = min(接收窗口 rwnd，拥塞窗口 cwnd)。链路带宽大、RTT 大（长肥管道）时，窗口必须 ≥ BDP 才能让管道始终有数据在飞。这就是「调大 tcp_rmem/tcp_wmem 就能提速」的原理——不是玄学，是把窗口上限抬高到 ≥ BDP。现代内核还支持**窗口缩放（window scaling，`ss -ti` 里的 `wscale:10,10`）**，把窗口从 64KB 上限扩到 GB 级，但**应用必须显式读大缓冲**才能受益（`SO_RCVBUF`/`SO_SNDBUF`，内核会按 tcp_rmem 区间自动调整）。

### 一次连接的建立：三次握手与双队列

```text
客户端                          服务端
  │  SYN                    ① 进 SYN 队列（tcp_max_syn_backlog）
  │───────────────────────→│ ② 回 SYN+ACK（tcp_synack_retries 重试）
  │  SYN+ACK               │
  │←───────────────────────│
  │  ACK                   │ ③ 移入 accept 队列（min(backlog, somaxconn)）
  │───────────────────────→│ ④ 应用 accept() 取走，进入业务
```

任何一个队列满：SYN 队列满 → 直接丢 SYN 或开 syncookies（`tcp_syncookies=1` 实测已开）；accept 队列满 → 丢弃已完成握手的连接，客户端表现为「连接超时/被重置」。**`ss -lnt` 的 Recv-Q 就是 accept 队列当前积压数，Send-Q 就是 backlog 上限**——这是排查连接被拒的第一手数据。

### 收包路径：中断 → NAPI → softirq

```text
网卡收到包 → DMA 到内存 ring buffer → 触发硬中断（IRQ）
  → NAPI 调度（关闭中断、轮询批量收包，避免中断风暴）
  → softirq（ksoftirqd/当前 CPU 处理 NET_RX_SOFTIRQ）
  → GRO 合并 → 协议栈 → 应用
```

- 单队列网卡：所有包的中断集中一个核，高 PPS 时该核 softirq 打满（`mpstat -P ALL` 看 si 列）→ 系统整体 CPU 不高但吞吐上不去。
- 多队列 + RSS：哈希分流到 N 个队列，中断分散到 N 个核，线性扩展收包能力。
- 中断处理不了时：ring buffer 溢出 → 网卡丢包（`ethtool -S` 的 `rx_dropped`/`rx_missed`、`ip -s link` 的 dropped 列）。

### TIME_WAIT 的生命周期与端口回收

```text
主动关闭方发 FIN → 收到对端 FIN+ACK → 回最后一个 ACK → TIME_WAIT（2MSL≈60s）
  → 超时后 socket 消失，端口释放
```

- 端口复用手段：`tcp_tw_reuse`（新内核默认值 2=仅 loopback 生效，非 loopback 默认不复用）、`tcp_tw_recycle`（**已从内核移除**，4.12+，别再用）、调小 `tcp_fin_timeout`（不建议低于 30，会破坏 2MSL 语义）。
- 更健康的解法：**长连接/连接池**（从根上减少 TIME_WAIT 产生），见常见问题 Q2。

### 拥塞控制如何工作（Reno → Cubic → BBR）

```text
Reno/Cubic（loss-based）：慢启动翻倍 → 线性增窗 → 丢包（队列溢出）→ 减窗
  → 问题：把「队列打满丢包」当拥塞信号，在深队列路由器上制造 bufferbloat
BBR（model-based）：周期性测「最大带宽 + 最小 RTT」→ 按模型直接限速
  → 不靠丢包探测，填满管道但不灌爆队列 → 长肥管道吞吐高、延迟稳定
```

### Nagle 与延迟 ACK 的交互

- **Nagle 算法**：发送方积攒小包，等前一个包被 ACK 才发下一个（减少小包数量）；代价是**小包延迟**。
- **延迟 ACK**：接收方最多等 40ms 才回 ACK（攒多个包回一个）。
- 两者叠加 = 「发一个等 ACK、收方又故意等」→ 交互式小包请求延迟飙到 40ms+。实时性要求高的程序要设 **TCP_NODELAY**（禁 Nagle），并让收方及时 ACK。

## 配置文件解析

### sysctl 机制

网络参数通过 sysctl 读写，`sysctl -w` 临时生效（重启丢失），持久化写在 `/etc/sysctl.conf` 或 `/etc/sysctl.d/*.conf`（按文件名顺序，后者覆盖前者），`sysctl -p` 重载。内核热路径参数在 `/proc/sys/net/` 下直接对应。

### TCP 调优参数完整清单（含本机实测默认值）

| 参数 | 本机/内核默认 | 作用与调优方向 |
|---|---|---|
| `net.core.somaxconn` | 4096（实测） | accept 队列上限，高并发调大到 4096~65535，并同步应用 backlog |
| `net.ipv4.tcp_max_syn_backlog` | 2048（实测） | SYN 半连接队列长度，防握手瓶颈 |
| `net.ipv4.tcp_syn_retries` | 6 | SYN 重传次数，内网可调小加快失败 |

| `net.ipv4.tcp_rmem` | 4096 131072 33554432（实测） | 读缓冲 min/default/max，长肥管道把 max 抬高到 ≥BDP |
| `net.ipv4.tcp_wmem` | 4096 16384 4194304（实测） | 写缓冲同上 |

## 应用场景实战

### 场景一：带宽与吞吐测试（iperf3 双向）

```shell
# 服务端（接收方）
iperf3 -s

# 客户端单向测下行（服务端→客户端，默认方向）
iperf3 -c <服务器IP> -t 30

# 客户端反向测上行（客户端→服务端，必须测，很多环境上下行不对称）
iperf3 -c <服务器IP> -R -t 30

# 并行 4 流（多 TCP 流榨干带宽，单流受窗口/BDP 限制可能跑不满）
iperf3 -c <服务器IP> -P 4 -t 30

# UDP 模式测最大带宽与丢包率（-b 限速，超速即丢包）
iperf3 -c <服务器IP> -u -b 1000M -t 10
```

判读：单流吞吐接近带宽上限 → 链路健康；**多流才跑满而单流跑不满 → TCP 窗口/BDP 问题**；UDP 模式高丢包 → 网络设备瓶颈或 QoS 限速。本机 iperf3 未装（`apt install iperf3`），测试时注意别在生产高峰期跑满带宽影响业务。

### 场景二：高并发 Web 的 TCP 参数调优

高并发短连接 Web（如 Nginx + 大量客户端）的完整调优链：

```shell
# 1. 队列：accept 队列 + SYN 队列
sysctl -w net.core.somaxconn=4096
sysctl -w net.ipv4.tcp_max_syn_backlog=4096
#    同时改应用层：Nginx 的 listen backlog、Tomcat 的 acceptCount
#    （实际队列 = min(应用 backlog, somaxconn)，两边都要调）

# 2. 短连接 TIME_WAIT：先确认内核版本与默认值
sysctl net.ipv4.tcp_tw_reuse      # 新内核默认 2（仅 loopback 生效）
#    非 loopback 场景内核不再默认复用：优先改长连接/连接池；
#    确实要复用再显式 sysctl -w net.ipv4.tcp_tw_reuse=1（需 tcp_timestamps=1）

# 3. 端口范围（客户端出口）与 fd 上限
sysctl -w net.ipv4.ip_local_port_range="10240 65535"
ulimit -n 65535                     # 或 systemd LimitNOFILE=65535

# 4. 持久化
cat >> /etc/sysctl.d/99-network-tuning.conf <<'EOF'
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 4096
net.ipv4.ip_local_port_range = 10240 65535
EOF
sysctl -p /etc/sysctl.d/99-network-tuning.conf
```

### 场景三：大带宽长延迟链路的 BBR 调优

跨国/跨地域链路（带宽大、RTT 100ms+）cubic 经常跑不满，BBR 实测效果明显：

```shell
# 1. 确认内核支持并加载模块（本机实测）
modprobe tcp_bbr
sysctl net.ipv4.tcp_available_congestion_control
# 实测结果：reno cubic → modprobe 后变成 reno cubic bbr

# 2. 切换全局默认算法（只影响新连接，老连接保持原算法）
sysctl -w net.ipv4.tcp_congestion_control=bbr
# 持久化：echo 'net.ipv4.tcp_congestion_control=bbr' >> /etc/sysctl.d/99-network-tuning.conf

# 3. 配套：抬高缓冲到 ≥BDP（BBR 也需要窗口足够大）
sysctl -w net.ipv4.tcp_rmem="4096 131072 67108864"
sysctl -w net.ipv4.tcp_wmem="4096 16384 67108864"

# 4. 验证生效
sysctl net.ipv4.tcp_congestion_control   # 应为 bbr
ss -ti | head -1                          # 新连接显示 bbr 而非 cubic
```

- **bridge 模式**（默认）：veth pair + 每容器独立 netns + iptables/nftables NAT 与 FORWARD 过滤。多一层 netfilter + conntrack 处理，**PPS 高的流量有明显开销**（实测本机规则集 242 行，FORWARD 链 policy drop）。

## 性能与调优

### 1. 调优决策矩阵

```text
症状                          → 首选调优
高并发连接被拒/握手慢         → somaxconn + backlog + tcp_max_syn_backlog
TIME_WAIT 多、端口耗尽        → 长连接/连接池 ＞ tcp_tw_reuse（新内核默认仅 loopback）
大带宽长延迟跑不满            → tcp_rmem/wmem 抬到 ≥BDP + BBR
小包/高 PPS 吞吐上不去        → 多队列 RSS + 中断亲和 + RPS；再不行 XDP/DPDK
单核 softirq 100%             → 多队列 + irqbalance/绑核
延迟高、重传多                → mtr 定位路径 + 查带宽打满/队列溢出
短连接每秒新建量大            → 连接池 + 端口范围扩大 + tcp_fastopen
```

### 2. 拥塞控制算法选型

| 算法 | 类型 | 适用 | 不适用 |
|---|---|---|---|
| cubic | loss-based | 通用默认、中等丢包 | 深队列瓶颈（bufferbloat）、极长肥管道 |
| bbr | model-based | 高带宽长延迟、跨国链路、CDN 回源 | 突发小流量场景收益有限；与部分网络设备/拥塞丢包策略冲突时可能加剧重传 |
| reno | loss-based | 兼容性兜底 | 大窗口场景效率低 |

切换前**必须压测对比**：`iperf3 -c <IP> -t 60` 分别跑 cubic 与 bbr，看吞吐、RTT、重传三项。BBR 适合「带宽大、RTT 大、丢包低」的管道，不是万能药。

### 3. offload 开关与排查影响

- 生产环境一般**保持 TSO/GSO/GRO 开启**（省 CPU，吞吐更高）。
- 排查抓包时：GRO 开启会看到合并后的"大包"（>MTU），TSO 开启会看到 `checksum incorrect`——**先 `ethtool -K <网卡> gro off gso off tso off` 再抓包**，还原真实网络形态。
- 小包转发/特殊场景（如某些 DPDK 共存、虚拟化嵌套）offload 可能与驱动冲突，实测对比开关前后的吞吐与 CPU 再决定。

### 4. RSS/RPS/RFS

- RSS：网卡硬件哈希分流（`ethtool -l/-L`），收包并行度 = 队列数。
- RPS：单队列网卡的软件补救（rps_cpus 位图）。
- RFS：rps_flow_cnt + rps_sock_flow_entries，让处理核与收包核一致（高吞吐+低延迟兼得）。
- 判断是否需要：`mpstat -P ALL 1` 出现单核 si 高、`/proc/interrupts` 中断集中一个核、softnet_stat 的 time_squeeze 持续增长。

### 5. bond/team 与负载均衡

多网卡聚合（详见本库 19 章）：bond 模式 0~6 中，**mode 0（balance-rr）与 mode 4（802.3ad LACP）** 能提升吞吐；**mode 1（active-backup）** 只做冗余。team 是 RHEL 7 引入的 bond 替代品（用户态控制更灵活），**RHEL 9 已弃用 team 推荐回归 bond**。注意：mode 0 的多流负载均衡不保证单流提速（单 TCP 流仍走单网卡），且依赖交换机端口聚合配置。

### 6. PPS 与高性能转发（DPDK/XDP 简述）

Linux 默认协议栈软中断收包：单核约 1~2 Mpps。追求线速小包（10G 14.88 Mpps）的路径：

- **DPDK**：用户态轮询驱动，绕过内核协议栈，典型应用 VPP/OVS-DPDK，能到 10Mpps+，代价是独占网卡、放弃内核 TCP。
- **XDP（eBPF）**：在驱动层收包前挂 eBPF 程序处理，DPDK 的七成功力、不丢内核协议栈（可 redirect/丢弃/封装）。
- 工程上先做 RSS + 多核 + 绑核 + 调大 netdev_budget，通常能到 3~5 Mpps，再考虑旁路技术。

## 安全与权限

### 1. sysctl 的 root 权限

网络参数全部只读需要 root：`sysctl -w` 改错参数（如把 `ip_forward` 开成 1、把 rp_filter 关掉）**影响整机网络与安全**。上线前备份：`sysctl -a > /tmp/sysctl.bak`，改完压测 + 回滚演练。

### 2. SYN flood 与 syncookies

```shell
# 队列满时用 cookie 机制响应 SYN，不占队列（本机实测默认已开）
sysctl net.ipv4.tcp_syncookies      # 实测 = 1
```

配合：调大 `tcp_max_syn_backlog`（队列兜底）、限速（nftables limit / 云厂商 DDoS 防护）。注意 syncookies 开启时部分高级 TCP 特性（如大窗口协商）会被禁用，属正常现象。

### 3. rp_filter 反欺骗

Ubuntu 默认 `net.ipv4.conf.all.rp_filter=2`（实测 /etc/sysctl.d/10-network-security.conf）：严格模式校验「源地址是否可达」，防 IP 欺骗；**多网卡/负载均衡/某些 VPN 场景会误丢包**，出现"单向不通"先查它。

### 4. 防火墙与 conntrack 开销

每包都要过 netfilter 钩子 + conntrack 建表（本机实测 nftables 规则集 242 行）。高 PPS 场景 conntrack 表满会**静默丢新连接**（`dmesg` 报 nf_conntrack: table full）。对策：`sysctl net.netfilter.nf_conntrack_max` 调大、精简规则、或数据面换成 eBPF/ipvs。

### 5. 测速与扫描的合规风险

- iperf 满带宽测试会**挤占业务流量**，避开高峰期，必要时 QoS 限速。
- 扫描/压测目标确认有授权；`mtr`/`ping` 探测运营商设备也可能被限流。

## 故障排查

### 案例一：高并发连接被拒（accept 队列溢出）

```shell
# 1. 先看监听队列积压：Recv-Q 持续 >0 = accept 来不及
ss -lnt
#    实测本机就有 backlog 极小的监听端口：
LISTEN 0      5      0.0.0.0:8888    0.0.0.0:*    # 上限只有 5，并发一上来必丢
# 2. 看协议栈累计：队列溢出与 SYN 丢弃计数
netstat -s | grep -iE 'listen queue|SYN.*dropped|SYN.*overflow'
# 3. 检查两边配置
sysctl net.core.somaxconn                 # 内核上限
#    应用 backlog：Nginx listen backlog / Java acceptCount / Redis tcp-backlog
# 4. 极端快速失败可选
sysctl -w net.ipv4.tcp_abort_on_overflow=1   # 队列满直接 RST，客户端立即感知
```

### 案例二：带宽跑不满（BDP / 单核 / offload）

```shell
# 1. 实测吞吐与延迟
iperf3 -c <服务器IP> -t 30          # 吞吐离带宽上限多远
ping -c 20 <服务器IP>               # RTT 多大（算 BDP 对照窗口）
# 2. 计算 BDP，比对 tcp_rmem/wmem max
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem
# 3. 看是否单核收包瓶颈
mpstat -P ALL 1                     # 某核 si 接近 100%？
grep <网卡> /proc/interrupts        # 中断是否全挤在一个核
cat /proc/net/softnet_stat          # time_squeeze 列持续增长？
# 4. 看 offload 是否被意外关闭
ethtool -k <网卡> | grep -E 'gro|gso|tso|checksum'
# 5. 单流 vs 多流对比定位窗口问题
iperf3 -c <IP> -P 1 -t 10 && iperf3 -c <IP> -P 4 -t 10
```

### 案例三：延迟高、重传多

```shell
# 1. 端到端与逐跳
ping -c 10 <目标>
mtr -rwc 10 <目标>                  # 哪一跳开始劣化
# 2. 协议栈累计重传
netstat -s | grep -iE 'retransmited|fast retransmits|timeout retransmits'
# 3. 连接级 RTT/重传（实时）
ss -ti | grep <目标IP>              # rtt 字段；有重传时出现 retrans 计数
# 4. 检查带宽是否打满 / 队列溢出（丢包根源）
sar -n DEV 1 5 | grep <网卡>
sar -n EDEV 1 5 | grep <网卡>       # rxdrop/txdrop 列
```

高重传常见根因：带宽打满（吞吐到顶 + 队列溢出）、运营商 QoS 限速、网卡/交换机故障（错误计数涨）、防火墙丢包（mtr 某跳开始全丢且最终不通）。

### 案例四：TIME_WAIT 大量与端口耗尽

```shell
# 1. 统计 TIME_WAIT
ss -tan state time-wait | wc -l          # 本机实测仅 6 个（长连接为主）
ss -s                                    # timewait 字段
# 2. 端口范围（客户端能开多少个出站连接）
sysctl net.ipv4.ip_local_port_range      # 实测 32768 60999 ≈ 2.8 万个
# 3. 是否在回收/复用
netstat -s | grep -iE 'recycled|time wait'
# 4. 端口耗尽症状：应用报 Cannot assign requested address
# 解法优先级：连接池/长连接 ＞ 扩大 ip_local_port_range ＞ tcp_tw_reuse=1
#   （新内核 tcp_tw_reuse 默认 2 只对 loopback 生效，非 loopback 需显式开 1）
```

### 案例五：tcpdump 看不到分片、checksum incorrect

```shell
# 症状1：抓包看到 64KB 的"巨包"——GRO 把多个段合并了（不是 bug）
# 症状2：抓包看到 checksum incorrect——TSO/校验和 offload，网卡还没填校验和
# 排查时临时关闭 offload，还原真实报文
ethtool -K <网卡> gro off gso off tso off
tcpdump -i <网卡> -nn -c 100 tcp port 80
ethtool -K <网卡> gro on gso on tso on     # 排查完恢复
```

## 常见问题

```text
Q1: ping 正常但传输慢，为什么？
A: ping 只测延迟不测吞吐。慢的可能：带宽打满、TCP 缓冲小于 BDP、丢包触发
   重传、单核收包。用 iperf3 测吞吐、ss -ti 看 RTT/窗口、mpstat 看 softirq
   分布，逐项排除。

Q2: TIME_WAIT 多是什么问题？一定要开 tcp_tw_reuse 吗？
A: 大量短连接必然产生 TIME_WAIT（主动关闭方要等 2MSL）。新内核（6.x）
   tcp_tw_reuse 默认值 2 只对 loopback 生效，非 loopback 默认不复用——
   这是安全考虑。更优解是长连接/连接池，从源头减少 TIME_WAIT；端口不够
   再扩 ip_local_port_range。

Q3: bbr 拥塞算法有什么用？什么时候用？
A: bbr 用「带宽估计 + 最小 RTT 估计」建模发送速率，不靠丢包判断拥塞，
   适合高带宽长延迟（跨国、CDN 回源）场景，常比 cubic 跑得满、延迟更稳。
   切换前压测对比，别盲上。

Q4: 单核 CPU 高但整体不高，和网络什么关系？
A: 典型是网卡单队列收包：中断/softirq 全压在一个核。多队列 + RSS 分流 +
   irqbalance/绑核，或 RPS 软件分流。mpstat -P ALL 看 si 列验证。

Q5: somaxconn 和应用的 backlog 是什么关系？
A: accept 队列实际长度 = min(应用 listen 的 backlog, net.core.somaxconn)。
   只调 somaxconn 而应用 backlog 小，或反之，都没用。ss -lnt 的 Send-Q
   列直接显示实际生效的 backlog。

Q6: 网卡队列溢出在哪看？
A: 三层：ip -s link 的 RX-DRP / netstat -i 的 RX-DRP；ethtool -S 的
   rx_dropped/rx_missed（硬件级）；softnet_stat 的 time_squeeze（软件
   softnet 队列处理不过来）。

Q7: 容器（Docker）网络比宿主机慢，正常吗？
A: 正常。bridge 模式多一层 veth + netfilter（NAT/conntrack）开销；host
   模式共享网络栈最快。k8s 里 Cilium(eBPF)/Calico 比 iptables 数据面快。

Q8: 抓包看到 checksum incorrect，网卡坏了吗？
A: 不是。TSO/校验和 offload 开启时，抓包点在网卡填校验和之前，看到的是
   "未完成"状态。ethtool -k 确认 offload 状态即可，或关掉再抓。
```

## 面试题

```text
1. BDP 是什么？和 TCP 吞吐有什么关系？
   答：BDP = 带宽 × RTT，是链路上「同时在途」的数据量上限。TCP 发送窗口
   （min(rwnd, cwnd)）必须 ≥ BDP 才能跑满带宽，否则链路空着但发不出去。
   调大 tcp_rmem/tcp_wmem 就是把窗口上限抬到 ≥ BDP；窗口缩放（wscale）
   让窗口能超过 64KB。

2. 高并发时连接被拒，怎么排查？
   答：三层队列：SYN 队列（tcp_max_syn_backlog）满丢 SYN；accept 队列
   （min(应用 backlog, somaxconn)）满丢已完成握手的连接。用 ss -lnt 看
   Recv-Q 积压与 Send-Q 上限，netstat -s 看溢出计数；调大两边并压测。

3. 网卡多队列解决什么问题？RSS 和 RPS 的区别？
   答：解决单核收包瓶颈——单队列网卡所有中断集中一个核，高 PPS 时该核
   softirq 打满。RSS 是网卡硬件按四元组哈希分流到多队列；RPS 是内核软件
   模拟（单队列网卡把包哈希分发到多核）。RFS 进一步让处理核=收包核。

4. TIME_WAIT 为什么多？tcp_tw_reuse 安全吗？
   答：主动关闭方必须等 2MSL（60s），短连接高频新建必然堆积。tcp_tw_reuse
   依赖时间戳（PAWS）复用 TIME_WAIT 端口，语义上安全，但新内核默认值 2
   只对 loopback 生效（防止非 loopback 上的复用被滥用）。工程上优先
   长连接/连接池，其次扩端口范围。

5. 带宽大但 TCP 单流跑不满，可能原因？
   答：① 窗口 < BDP（缓冲小）；② 单核收包瓶颈；③ 拥塞算法不匹配
   （cubic 在深队列链路丢包减窗）；④ 丢包导致重传。验证：iperf3 单流 vs
   多流对比、ss -ti 看窗口、mpstat 看 softirq。

6. TSO/GSO/GRO 是什么？对排查有什么影响？
   答：发送侧 TSO/GSO 把大包切段下放给网卡/内核，接收侧 GRO 把小段合并，
   都为了减 CPU 开销。影响：GRO 开启时 tcpdump 看到 64KB 巨包，TSO 开启
   时看到 checksum incorrect——抓包前先 ethtool -K 关掉 offload。

7. 怎么判断网络瓶颈是「带宽」还是「延迟」还是「包处理」？
   答：带宽瓶颈看 sar -n DEV 利用率接近上限 + iperf3 吞吐到顶；延迟瓶颈
   看 ping/mtr RTT 高而吞吐正常（交互慢）；包处理瓶颈看单核 softirq 100%、
   PPS 高但带宽利用率低、softnet_stat time_squeeze 增长。
```

## 最佳实践与踩坑记录

### 最佳实践

1. **指标分层**：带宽用 iperf3 测、延迟用 ping/mtr 测、PPS 看 ethtool -S/softnet_stat，别用 ping 判断一切。
2. **调优前备份基线**：`sysctl -a > /tmp/sysctl.bak` + 压测数据存档，一次只改一个参数，改后压测对比。
3. **队列两边一起调**：somaxconn 与应用 backlog 是 min 关系，Nginx/Java/Redis 都要改。
4. **TIME_WAIT 先改架构再改参数**：连接池/长连接优先，tcp_tw_reuse 是兜底。
5. **BBR 上线前压测**：cubic vs bbr 各跑一轮 iperf3，看吞吐/RTT/重传三项再定。
6. **多队列是标配**：高吞吐机器检查 RSS 队列数与中断分布，irqbalance（RHEL）或手动绑核（Ubuntu）。
7. **抓包前关 offload**：tcpdump 前 `ethtool -K gro off gso off tso off`，看完恢复。
8. **容器网络按场景选**：性能敏感服务用 host 模式或 eBPF 数据面（Cilium），别默认全走 iptables NAT。

### 踩坑记录

```text
坑 1：只测 ping 不测吞吐，判断不出带宽瓶颈
结论：ping 全通就以为网络没问题，实际带宽早已打满。
原因：ping 只测延迟/可达性，不测吞吐。
解法：iperf3 双向测吞吐，与带宽上限对比；sar -n DEV 看利用率。

坑 2：TCP 缓冲没抬到 BDP，大带宽跑不满
结论：千兆/万兆链路实际传输只有几百 Mbps。
原因：窗口上限小于 BDP（带宽×RTT），链路空着发不出去。
解法：tcp_rmem/tcp_wmem 的 max 抬到 ≥BDP，长肥管道配合 BBR。

坑 3：只调 somaxconn 没调应用 backlog，连接照样被拒
结论：sysctl somaxconn 调大了，高并发还是握手失败。
原因：accept 队列 = min(应用 backlog, somaxconn)，应用侧 backlog 没动。
解法：两边一起调，用 ss -lnt 的 Send-Q 验证实际生效值。

坑 4：单核 CPU 高但整体不高，以为是程序问题
结论：程序没写错，网络吞吐就是上不去，某核 100%。
原因：网卡单队列，收包中断全在一个核（softirq 打满）。
解法：多队列 RSS（ethtool -l/-L）+ 中断亲和 + RPS；mpstat -P ALL 验证。

坑 5：新内核开 tcp_tw_reuse 没效果
结论：开了 tcp_tw_reuse=1，TIME_WAIT 还是大量堆积。
原因：6.x 内核默认值 2 只对 loopback 复用；且复用需要 tcp_timestamps=1。
解法：确认内核版本与当前值，非 loopback 显式设 1；更优解是长连接/连接池。

坑 6：bbr 没压测就上生产，某些场景反而变差
结论：切 bbr 后部分链路重传率上升、吞吐下降。
原因：bbr 适合高带宽长延迟低丢包管道，与网络设备丢包策略/突发流量场景
     冲突时表现不佳。
解法：测试环境 cubic vs bbr 压测对比，按链路特性选。

坑 7：抓包看到 64KB 巨包 / checksum incorrect，误判网络故障
结论：tcpdump 抓到超大包或校验和错误，以为网卡/网络坏了。
原因：GRO 合并收包、TSO/校验和 offload 在抓包点还没完成。
解法：抓包前 ethtool -K <网卡> gro off gso off tso off，排查完恢复。

坑 8：Docker 容器吞吐低就怀疑镜像/应用
结论：容器内 iperf3 只有宿主机一半吞吐，以为是应用问题。
原因：bridge 模式多一层 veth + netfilter NAT/conntrack 开销。
解法：对比 host 模式；数据面换 eBPF/ipvs；确认 conntrack 表没满
     （dmesg 查 nf_conntrack: table full）。
```
