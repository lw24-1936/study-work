## 概述

网络性能分析回答「网络快不快、瓶颈在哪」：吞吐（每秒传多少数据）、延迟（RTT，往返时间）、TCP 调优（缓冲、连接参数）、网卡多队列（多核并行处理收包）。核心指标：带宽利用率、丢包率、RTT。网络瓶颈通常在「带宽打满」或「TCP 参数没调优」或「单核处理收包」。

```text
网络性能四要素：
1. 吞吐 —— 每秒传输量（带宽打满 = 瓶颈）
2. 延迟 —— RTT（往返时间），高延迟影响交互
3. TCP 调优 —— 缓冲、连接参数（影响吞吐和连接数）
4. 网卡多队列 —— 多核并行收包（单核收包是瓶颈）
```

## 核心概念

1. **吞吐 throughput**：每秒传输的数据量（带宽）。测吞吐用 iperf，带宽打满（吞吐到上限）= 带宽瓶颈。
2. **延迟 RTT**：数据往返时间，ping 测。高延迟影响交互（尤其长距离链路）。
3. **BDP（带宽延迟积）**：带宽 × RTT，是「链路上在途的数据量」。TCP 缓冲要配够 BDP 才能跑满带宽。
4. **TCP 调优参数**：缓冲区（tcp_rmem/tcp_wmem）、连接队列（somaxconn、tcp_max_syn_backlog）、TIME_WAIT 复用（tcp_tw_reuse）、拥塞算法（bbr）。
5. **网卡多队列 multi-queue**：网卡多个收发队列 + RSS 哈希分发，让多核并行处理收包，解决「单核收包瓶颈」。

```text
吞吐 vs 延迟：
1. 吞吐 —— 每秒传输量（带宽），iperf 测
2. 延迟 —— RTT 往返时间，ping 测
3. BDP —— 带宽×延迟积，TCP 缓冲要配够才能跑满带宽
```

## 工作原理

1. **BDP 限制吞吐**：TCP 有拥塞控制，发送窗口受「接收缓冲 + 拥塞窗口」限制。带宽大、延迟高（长肥管道）时，窗口必须 ≥ BDP 才能跑满带宽，否则「链路空着但发不出去」。调大 tcp_rmem/tcp_wmem 就是解决这个。
2. **连接队列**：高并发时新连接先排队（SYN 队列 → accept 队列），队列太小连接被丢（SYN 重传或 RST）。somaxconn 限制 accept 队列长度。
3. **网卡收包**：网卡收到包产生中断 → CPU 处理。单队列网卡所有包的中断都到一个核，高吞吐时单核打满（softirq 高），多队列 + RSS 把流量哈希分发到不同队列，中断绑到不同核并行处理。

```text
网络瓶颈三种典型：
1. 带宽打满 —— 吞吐到上限，加带宽或压缩/限流
2. TCP 参数没调优 —— 缓冲小跑不满、队列小连不上
3. 单核收包 —— 某核 softirq 100%，多队列 + 中断亲和
```

## 常用命令与配置

```shell
iperf3 -s               # 服务器端
iperf3 -c 服务器IP      # 客户端测吞吐
ping -c 10 目标         # 测 RTT（延迟）
ss -i                   # 看 TCP 连接的 RTT/吞吐
ss -s                   # 网络连接统计
ethtool -l eth0         # 看网卡队列数
ethtool -S eth0 | grep queue   # 看每队列统计
cat /proc/interrupts | grep <网卡>   # 中断分布
```

```text
TCP 调优参数：
tcp_rmem/tcp_wmem    读写缓冲区（BDP 大调大）
somaxconn            监听队列（高并发调大）
tcp_max_syn_backlog  SYN 队列（防 SYN flood）
tcp_tw_reuse         TIME_WAIT 复用（短连接）
tcp_congestion_control  拥塞算法（bbr 高吞吐）
```

## 配置文件解析

TCP/网络参数通过 sysctl 配置，持久化在 /etc/sysctl.conf（或 /etc/sysctl.d/*.conf）：

```text
# /etc/sysctl.conf 里的网络调优项
net.core.somaxconn = 1024               # accept 队列最大长度
net.ipv4.tcp_max_syn_backlog = 4096     # SYN 队列长度
net.ipv4.tcp_rmem = 4096 87380 6291456  # 读缓冲（min default max）
net.ipv4.tcp_wmem = 4096 16384 4194304  # 写缓冲
net.ipv4.tcp_tw_reuse = 1               # TIME_WAIT 复用
net.ipv4.tcp_congestion_control = bbr   # 拥塞算法
```

```shell
# 查看 TCP 参数
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem
sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog
# 临时生效
sysctl -w net.core.somaxconn=1024
# 持久化
echo 'net.core.somaxconn=1024' >> /etc/sysctl.conf
sysctl -p
```

```text
参数含义：
tcp_rmem/tcp_wmem  三段值（min/default/max），内核按需在区间内自动调整
somaxconn          应用 listen 的 backlog 上限（配合应用层的 backlog）
tcp_tw_reuse       短连接场景复用 TIME_WAIT，减少端口/连接耗尽
```

## 应用场景实战

### 场景一：测网络吞吐，定位带宽瓶颈

```shell
# 1. 服务器端起 iperf
iperf3 -s
# 2. 客户端测吞吐
iperf3 -c <服务器IP>
# 3. 测延迟
ping -c 10 <服务器IP>
# 吞吐接近带宽上限 = 带宽瓶颈；RTT 高 = 延迟问题
```

### 场景二：高并发 Web 调优 TCP 参数

```shell
# 1. 调大连接队列
sysctl -w net.core.somaxconn=4096
sysctl -w net.ipv4.tcp_max_syn_backlog=4096
# 2. TIME_WAIT 复用（短连接）
sysctl -w net.ipv4.tcp_tw_reuse=1
# 3. 持久化
echo -e 'net.core.somaxconn=4096\nnet.ipv4.tcp_tw_reuse=1' >> /etc/sysctl.conf
sysctl -p
```

## 性能与调优

```text
1. 高并发 Web —— 调大 somaxconn + backlog + tcp_tw_reuse
2. 大带宽长延迟（跨国）—— 调大 TCP 缓冲（tcp_rmem/wmem）+ bbr
3. 高吞吐收包 —— 网卡多队列 + 中断亲和（irqbalance），解决单核瓶颈
4. 短连接场景 —— tcp_tw_reuse 复用 TIME_WAIT，避免端口耗尽
5. 一次改一个参数 —— 网络调优互相影响，改前记录旧值，改后压测对比
```

## 安全与权限

```text
1. sysctl 权限 —— 改网络参数要 root，改错影响全机网络
2. SYN flood 防护 —— tcp_max_syn_backlog + tcp_syncookies（防 SYN 泛洪攻击）
3. iperf 测速 —— 别在生产高峰期跑满带宽测速（影响业务）
4. 拥塞算法 —— bbr 对某些场景反而变差，上线前测试环境压测
```

```shell
# SYN cookie 防护（防 SYN flood）
sysctl -w net.ipv4.tcp_syncookies=1
```

## 故障排查

### 高并发连接被拒

```shell
# 1. 看监听队列是否溢出（dropped/overflowed）
ss -s
# 2. 看 SYN 队列丢包
netstat -s | grep -i 'SYN.*dropped\|overflowed'
# 3. 检查 somaxconn 和应用 backlog
sysctl net.core.somaxconn
```

### 带宽跑不满

```shell
# 1. iperf 测实际吞吐
iperf3 -c <服务器IP>
# 2. 看是否丢包
ping -c 20 <服务器IP>
# 3. 看单核是否打满（收包瓶颈）
mpstat -P ALL 1   # 某核 softirq 高
# 4. 看网卡队列数
ethtool -l eth0
```

## 常见问题

```text
Q1: ping 正常但传输慢，为什么？
A: ping 只测延迟，不测吞吐。可能是带宽打满、TCP 缓冲小（BDP 限制）、或丢包。用 iperf 测吞吐定位。

Q2: TIME_WAIT 多是什么问题？
A: 短连接（大量频繁建立/断开）产生大量 TIME_WAIT 连接，可能耗尽端口。用 tcp_tw_reuse 复用，或改长连接/连接池。

Q3: bbr 拥塞算法有什么用？
A: bbr 基于「带宽 + RTT」估计拥塞，适合长肥管道（高带宽长延迟），比传统 loss-based 算法（cubic）更能跑满带宽。

Q4: 单核 CPU 高但整体不高，和网络什么关系？
A: 可能是网卡单队列，收包中断都集中在一个核（softirq 打满）。网卡多队列 + RSS + 中断亲和解决。
```

## 面试题

```text
1. BDP 是什么？和 TCP 吞吐有什么关系？
   答：BDP = 带宽 × RTT，是链路上「在途的数据量」。TCP 发送窗口必须 ≥ BDP 才能跑满带宽，否则链路空着发不出去，这就是调大 TCP 缓冲的原因。

2. 高并发时连接被拒是什么原因？
   答：监听队列（somaxconn/backlog）太小，新连接来不及 accept 被丢。调大 net.core.somaxconn + 应用 backlog，以及 tcp_max_syn_backlog。

3. 网卡多队列解决什么问题？
   答：解决「单核收包瓶颈」。单队列网卡所有包的中断集中一个核，高吞吐时该核 softirq 打满。多队列 + RSS 哈希分发 + 中断亲和，让多核并行收包。

4. TIME_WAIT 状态太多怎么办？
   答：短连接场景调 tcp_tw_reuse 复用，或改长连接/连接池减少连接建立频率，避免端口耗尽。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 测网络性能用 iperf（吞吐）+ ping（延迟），别只看一个
2. 高并发 Web 调大 somaxconn + backlog + tw_reuse
3. 大带宽长延迟（跨国）调大 TCP 缓冲 + bbr
4. 高吞吐场景看网卡多队列，单核收包是常见瓶颈
5. 网络调优一次改一个参数，改前记录旧值

### 踩坑记录

```text
坑 1：只测 ping 不测吞吐，判断不出带宽瓶颈
结论：ping 正常就以为网络没问题，其实带宽打满。
原因：ping 只测延迟，不测吞吐。
解法：iperf 测吞吐，看是否接近带宽上限。

坑 2：TCP 缓冲没调大，大带宽跑不满
结论：千兆/万兆带宽，实际传输只有几百兆。
原因：TCP 缓冲太小，受 BDP（带宽×延迟）限制跑不满。
解法：调大 tcp_rmem/tcp_wmem，配合 bbr。

坑 3：高并发连接被拒，somaxconn 太小
结论：并发高时新连接失败（SYN 被丢）。
原因：监听队列 somaxconn 太小，连接来不及处理被丢。
解法：调大 net.core.somaxconn + 应用的 backlog。

坑 4：单核 CPU 高但整体不高，网卡收包瓶颈
结论：网络吞吐上不去，某个 CPU 核 100%。
原因：网卡单队列，收包集中在一个核处理。
解法：网卡多队列（RSS）+ 中断亲和性（irqbalance）。

坑 5：bbr 切了没评估就上生产
结论：切 bbr 后某些场景反而变差。
原因：bbr 适合长肥管道（高带宽长延迟），不是万能。
解法：测试环境压测对比，再决定。
```
