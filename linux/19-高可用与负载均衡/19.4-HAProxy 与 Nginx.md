## 概述

HAProxy 和 Nginx 是主流的「反向代理 + 负载均衡」软件，都能做四层（TCP/UDP）和七层（HTTP）负载均衡。HAProxy 是专业的负载均衡器（性能强、功能专一，做四层/七层 LB 很强），Nginx 是「Web 服务器 + 反向代理」全能型（既能当 Web 服务器，又能做反向代理和 LB）。核心能力：负载均衡（把流量分到多台后端）、健康检查（剔除故障后端）、会话保持（同用户固定后端）、限流（保护后端）。

```text
# 实测（本机 nginx 版本 + 站点配置）
$ nginx -v
nginx version: nginx/1.24.0 (Ubuntu)
$ ls /etc/nginx/sites-enabled/
default  deepseek-harness.conf  new-admin.conf
# 本机 nginx 1.24.0，跑了 3 个站点（含反向代理配置）
```

## 核心概念

1. **四层 vs 七层**：四层（L4）只看 IP+端口，转发 TCP/UDP 流（性能高、不看内容）；七层（L7）解析 HTTP，按 URL/域名/头路由（功能强）。
2. **upstream / backend**：后端服务器组（多个真实服务器）。
3. **健康检查**：定期探测后端是否存活，故障自动剔除、恢复自动加回。
4. **会话保持（session persistence）**：同一用户请求固定到同一后端（Cookie 或源 IP 哈希）。
5. **限流（rate limiting）**：限制请求速率，保护后端不被刷爆。

```text
核心概念：
四层(L4) vs 七层(L7) + upstream(后端组) + 健康检查 + 会话保持 + 限流
```

## 工作原理

反向代理负载均衡的工作流程：

1. **客户端请求 → 代理**：客户端访问代理（VIP/域名），代理接收请求。
2. **选后端**：代理按「调度算法」（轮询/最少连接/哈希）+「健康检查结果」（剔除故障后端）选一个后端。
3. **转发**：代理把请求转发给选中的后端（四层直接转发 TCP 流，七层解析 HTTP 后转发）。
4. **返回**：后端处理后响应经代理回给客户端（七层可做缓存/改写响应）。

四层和七层的区别在「转发前是否解析内容」：四层是「管道」（透明转发字节流），七层是「解析后重建」（能改头、路由、缓存）。

```text
工作流程：
客户端 → 代理 → 调度算法+健康检查选后端 → 转发 → 后端处理 → 响应回客户端
四层=透明转发字节流；七层=解析 HTTP 后路由/改写
```

## 配置文件解析

Nginx 反向代理 + 负载均衡配置（本机真实风格）：

```nginx
# /etc/nginx/conf.d/app.conf
upstream backend {             # 后端服务器组
    server 192.168.1.11:8080 weight=3;   # weight 权重
    server 192.168.1.12:8080 weight=1;
    server 192.168.1.13:8080 backup;     # 备用（其他都挂才用）
    # keepalive 32;                      # 到后端的连接复用
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://backend;       # 转发到 upstream
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;   # 传递真实客户端 IP
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # 健康检查（Nginx 用 upstream 的 max_fails/fail_timeout）
    upstream backend {
        server 192.168.1.11:8080 max_fails=3 fail_timeout=30s;
    }

    # 限流
    limit_req_zone $binary_remote_addr zone=one:10m rate=10r/s;
    location /api/ {
        limit_req zone=one burst=20 nodelay;
        proxy_pass http://backend;
    }
}
```

```text
关键配置：
upstream    后端组（weight 权重、backup 备用、max_fails 健康检查）
proxy_pass  转发目标
X-Real-IP / X-Forwarded-For  传递真实客户端 IP（否则后端看到的是代理 IP）
limit_req   限流（rate 速率 + burst 突发）
```

## 应用场景实战

### 场景一：Nginx 反向代理到后端应用（本机真实场景）

```text
# 本机 deepseek-harness.conf / new-admin.conf 就是反向代理：
# 外部访问 80/8082 → nginx 反向代理 → 后端 127.0.0.1:3080 / 8081
# 好处：统一入口、TLS 终结、负载均衡、隐藏后端
```

```nginx
# 典型反代配置
server {
    listen 8082;
    server_name _;
    location / {
        proxy_pass http://127.0.0.1:8081;   # 转发到后端
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

### 场景二：多后端负载均衡 + 健康检查

```nginx
upstream app {
    server 10.0.0.1:8080 max_fails=2 fail_timeout=10s;  # 失败 2 次剔除 10 秒
    server 10.0.0.2:8080 max_fails=2 fail_timeout=10s;
    server 10.0.0.3:8080 max_fails=2 fail_timeout=10s;
}
```

## 性能与调优

```text
1. 连接复用 —— upstream 配 keepalive，复用到后端的连接（减少握手开销）
2. 调度算法 —— 后端性能不均用 weight 加权，长连接用 least_conn
3. 缓存 —— 静态内容/可缓存响应配 proxy_cache，减轻后端压力
4. 缓冲 —— proxy_buffering 配置合理，避免慢客户端拖垮后端
5. worker 数 —— worker_processes = CPU 核数，充分利用多核
```

## 安全与权限

```text
1. 传递真实 IP —— 配 X-Real-IP/X-Forwarded-For，后端才能拿到真实客户端 IP（审计/风控需要）
2. 隐藏后端 —— 反向代理隐藏后端真实地址，后端只对内网开放
3. TLS 终结 —— 在代理层做 HTTPS（证书集中管理），后端走 HTTP
4. 限流防刷 —— limit_req 限流，防 DDoS/爬虫刷爆后端
5. 请求头校验 —— 后端若信任 X-Forwarded-For，要确保它来自可信代理（防伪造 IP）
```

## 故障排查

### 后端 502 Bad Gateway

```shell
# 1. 看 nginx 错误日志
tail -f /var/log/nginx/error.log
# 2. 检查后端是否存活
curl http://127.0.0.1:8081/health
# 3. 看 upstream 状态
nginx -T | grep -A5 upstream
# 4. 检查后端端口监听
ss -tlnp | grep 8081
```

### 后端被剔除（健康检查失败）

```shell
# 1. 确认健康检查配置
nginx -T | grep -E 'max_fails|fail_timeout'
# 2. 手动测后端
curl -I http://<后端>:8080/
# 3. 看后端自己的错误日志
```

## 常见问题

```text
Q1: 四层和七层负载均衡怎么选？
A: 只需转发 TCP/UDP（如数据库、Redis）用四层；要按 URL/域名/头路由（HTTP）用七层。

Q2: 会话保持怎么做？
A: 七层用 Cookie 粘滞（ip_hash 或 cookie），四层用源 IP 哈希。注意会话保持会破坏负载均衡均匀性。

Q3: Nginx 和 HAProxy 怎么选？
A: 都要 Web 服务器 + 反向代理用 Nginx；纯负载均衡（尤其四层/高并发）用 HAProxy（性能更强、LB 功能更专）。

Q4: 后端拿到的是代理 IP 不是客户端 IP，怎么办？
A: 配 X-Real-IP / X-Forwarded-For 头传递真实 IP，后端从这些头取。
```

## 面试题

```text
1. 反向代理和正向代理的区别？
   答：反向代理代理「服务端」（客户端不知道真实后端），正向代理代理「客户端」（服务端不知道真实客户端）。

2. 负载均衡的调度算法有哪些？
   答：轮询/加权轮询、最少连接、源地址哈希、一致性哈希。按场景选：性能不均加权、长连接最少连接、要会话保持哈希。

3. 健康检查怎么实现？
   答：主动探测（定期发请求探活）或被动（根据请求失败判断）。Nginx 用 max_fails/fail_timeout，HAProxy 用 check 选项。

4. 502 是什么原因？
   答：代理转发后端时后端不可用（挂了/超时/端口不对），代理返回 502 Bad Gateway。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 反向代理必配 X-Real-IP / X-Forwarded-For 传递真实客户端 IP
2. upstream 配 keepalive，复用后端连接减少握手
3. 配健康检查（max_fails/fail_timeout），故障后端自动剔除
4. TLS 在代理层终结，后端走内网 HTTP
5. 用 limit_req 限流，保护后端不被刷爆

### 踩坑记录

```text
坑 1：没传 X-Forwarded-For，后端拿到的是代理 IP
结论：后端日志全是代理 IP，看不到真实客户端，审计/风控失效。
原因：反向代理默认不转发客户端 IP 头。
解法：配 proxy_set_header X-Real-IP 和 X-Forwarded-For。

坑 2：502 就重启代理，没看后端
结论：报 502 就重启 nginx，重启后还是 502。
原因：502 是「后端不可用」，根因在后端（挂了/超时/端口不对），不在代理。
解法：看 nginx error.log + 后端日志 + curl 后端健康检查。

坑 3：upstream 没配 keepalive，连接频繁重建
结论：高并发下性能差，握手开销大。
原因：默认每次请求新建到后端的连接。
解法：upstream 配 keepalive N，复用后端连接。

坑 4：会话保持配了导致负载不均
结论：配了 ip_hash 后，某台后端负载明显高于其他。
原因：源 IP 哈希把某些热点 IP 都固定到同一后端。
解法：评估是否需要会话保持，或用一致性哈希（后端增减时少漂移）。

坑 5：后端信任 X-Forwarded-For 被伪造 IP
结论：攻击者伪造 XFF 头绕过 IP 限制/风控。
原因：后端直接信任 XFF，而攻击者可以自填这个头。
解法：后端只信任「来自可信代理」的 XFF，或代理层覆盖 XFF。
```
