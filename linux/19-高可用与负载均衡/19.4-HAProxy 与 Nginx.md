## 概述

HAProxy 和 Nginx 是主流的「反向代理 + 负载均衡」软件。**HAProxy** 是专职负载均衡器（支持四层 TCP/UDP 与七层 HTTP，性能强、功能专一，号称单进程可扛数十万并发连接）；**Nginx** 是「Web 服务器 + 反向代理 + 负载均衡」全能型选手（既能托管静态站点，又能做反代和 LB）。两者都具备负载均衡、健康检查、会话保持、限流等核心能力，是 [[19.3-LVS 负载均衡]] 之下最常见的一层。

```text
HAProxy 与 Nginx 定位：
HAProxy —— 专职反向代理/负载均衡器，四层(TC P/UDP)+七层(HTTP)通吃，
           高并发、健康检查精细、ACL 路由灵活
Nginx   —— Web 服务器 + 反向代理，七层 HTTP 路由/静态缓存/限流见长，
           也有 stream 模块做四层
分工    —— 入口大流量用 LVS，业务路由层用 HAProxy/Nginx，Web 托管用 Nginx
```

## 核心概念

1. **四层 vs 七层**：四层（L4）只看 IP+端口，透明转发 TCP/UDP 字节流（性能高、不看内容，适合数据库/Redis/任意协议）；七层（L7）解析 HTTP，按域名/URL/Header/Cookie 路由（功能强，能做 TLS 终结、改写、缓存）。
2. **反向代理（Reverse Proxy）**：代理「服务端」，客户端只认识代理（VIP/域名），不知道真实后端；与正向代理（代理客户端出网）相反。
3. **upstream / backend**：后端服务器组（一组真实服务器），负载均衡就是在这组机器里选一台转发。
4. **调度算法（balance）**：轮询（roundrobin）、加权轮询、最少连接（leastconn）、源地址哈希（source）、一致性哈希等。
5. **健康检查**：主动（定期探测后端，HAProxy 的 `check`/Nginx Plus 或第三方模块）或被动（根据真实请求失败率，Nginx 的 `max_fails`/`fail_timeout`）剔除故障后端。
6. **会话保持（session persistence）**：同一用户固定到同一后端，手段：Cookie 粘滞（HAProxy `cookie`）、源 IP 哈希（Nginx `ip_hash`/HAProxy `source`）。
7. **限流（rate limiting）**：限制请求速率/并发，保护后端（Nginx `limit_req`/`limit_conn`、HAProxy `rate-limit` 类 ACL）。
8. **ACL（访问控制列表）**：HAProxy 的条件匹配机制，按路径/头/源 IP 等条件做路由或动作。
9. **TLS 终结（TLS termination）**：在代理层解密 HTTPS，后端走内网 HTTP，证书集中管理。

```text
核心概念：
四层(L4) vs 七层(L7) + 反向代理 + upstream(后端组) + 调度算法
+ 健康检查 + 会话保持 + 限流 + ACL + TLS 终结
```

## 工作原理

### 反向代理负载均衡的工作流程

1. **客户端请求 → 代理**：客户端访问代理（VIP/域名/端口），代理接受连接。
2. **选后端**：代理按调度算法（轮询/最少连接/哈希）从「健康的后端集合」里选一台。
3. **转发**：四层直接转发 TCP 字节流（两端套接字对拷）；七层解析 HTTP 后重建请求转发（可改写 Host/路径/头）。
4. **返回**：后端响应经代理回给客户端；七层可做缓存（Nginx proxy_cache）、改写（sub_filter）、压缩。

```text
工作流程：
客户端 → 代理 → 调度算法 + 健康检查（剔除故障后端）→ 选中后端
       → 转发（L4 透传字节流 / L7 重建 HTTP 请求）→ 后端处理
       → 响应回客户端（L7 可缓存/改写）
```

### 四层 vs 七层的本质区别

| 维度 | 四层（L4） | 七层（L7） |
|------|-----------|-----------|
| 关注内容 | IP:端口 | HTTP 方法/URL/域名/Header/Body |
| 转发方式 | 字节流透传 | 解析后重建请求 |
| 性能 | 更高（少解析） | 略低（需解析） |
| 能力 | 任意 TCP/UDP 协议 | 路由、改写、缓存、限流、TLS |
| 典型场景 | MySQL、Redis、gRPC、长连接 | Web API、静态站、微服务网关 |

### 两者的事件驱动模型（为什么都能扛高并发）

- **Nginx**：master 管理进程 + worker 进程（默认 = CPU 核数），每个 worker 用 epoll 事件循环处理大量连接（异步非阻塞），worker 之间无锁竞争。`worker_processes auto` + `worker_connections` 决定并发上限。
- **HAProxy**：单进程多线程（2.0+ 支持 `nbthread`），基于 epoll/kqueue 的事件循环 + 内存池 + 零拷贝转发，性能极高且资源占用稳定。

```text
# 实测（本机）——Nginx 主配置（worker 模型 + 8 核）
$ grep -vE '^\s*#|^\s*$' /etc/nginx/nginx.conf | head -8
```


## 配置文件解析

### 1. Nginx：upstream + 反向代理完整解析

```nginx
# /etc/nginx/conf.d/app.conf
# —— upstream 块：后端服务器组（必须在 http 上下文内）
upstream backend {
    # 调度算法：默认轮询；least_conn 最少连接；ip_hash 源 IP 哈希
    # 注意：ip_hash 与 weight 同时配置时权重按比例生效
    least_conn;

    server 192.168.1.11:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 192.168.1.12:8080 weight=1 max_fails=3 fail_timeout=30s;
    server 192.168.1.13:8080 backup;          # 备用：其他全挂才启用
    server 192.168.1.14:8080 down;            # 手动摘除（维护中）

    keepalive 32;      # 每个 worker 保留 32 条到后端的空闲连接（长连接复用）
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://backend;            # 转发到 upstream 组
        proxy_http_version 1.1;               # 与后端 keepalive 必须 1.1
        proxy_set_header Connection "";       # 清空 hop-by-hop 头（keepalive 需要）

        # 传递真实客户端信息
        proxy_set_header Host $host;                       # 保留原始 Host
        proxy_set_header X-Real-IP $remote_addr;           # 客户端真实 IP
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;        # http/https 标记

        # 超时控制
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
    }

    # 故障转移：对 502/504 等错误重试下一个后端
    proxy_next_upstream error timeout http_502 http_503 http_504;
}

# —— 主动健康检查（开源版需要第三方 nginx_upstream_check_module；
#    Nginx Plus 内置 health_check；开源版常用被动检查 max_fails/fail_timeout）
# 被动检查语义：fail_timeout 窗口内失败 max_fails 次 → 摘除 fail_timeout 秒
```

```text
关键配置语义：
upstream            后端组（least_conn/ip_hash 算法，weight 权重）
server backup/down  备用节点 / 手动摘除
max_fails/fail_timeout  被动健康检查（30s 内失败 3 次摘除 30s）
keepalive 32        复用到后端的连接（必须配 proxy_http_version 1.1）
proxy_pass          转发目标（http://组名 或 直接 http://IP:port）
proxy_next_upstream 上游错误时的故障转移策略
X-Real-IP / X-Forwarded-For   传递真实客户端 IP（后端审计/风控依赖）
```

### 2. Nginx：本机真实配置解析（deepseek-harness.conf 关键片段）

本机 `/etc/nginx/conf.d/deepseek-harness.conf` 就是「TLS 终结 + 反向代理 + WebSocket 升级」的完整实例，核心片段：

```nginx
# TLS 终结：证书放在代理层，后端 127.0.0.1:3080 走明文 HTTP
server {
    listen 100.71.112.119:443 ssl;          # 只在 Tailscale IP 上监听 443
    server_name lw-vostro-7580.tailc6bb9f.ts.net;

    ssl_certificate     /etc/nginx/ssl/lw-vostro-7580.tailc6bb9f.ts.net.crt;
    ssl_certificate_key /etc/nginx/ssl/lw-vostro-7580.tailc6bb9f.ts.net.key;
    ssl_protocols TLSv1.2 TLSv1.3;

    location / {
        proxy_pass http://127.0.0.1:3080;   # 单后端反代（无 upstream 组）
        proxy_http_version 1.1;

        # WebSocket 升级头（map 生成的连接升级值）
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        proxy_buffering off;                # 流式场景关缓冲（SSE/长轮询）
        proxy_cache off;
        proxy_read_timeout 3600s;           # 长连接场景超时拉长
        proxy_send_timeout 3600s;
    }
}
```

另一个本机站点 `new-admin.conf` 展示了「静态 SPA + 动态 API 分流 + 静态长缓存」：

```nginx
server {

    }
}
```

### 3. HAProxy：haproxy.cfg 完整逐段解析

```haproxy
# /etc/haproxy/haproxy.cfg

# ---------- global：进程级参数 ----------
global
    log /dev/log local0 info        # 日志（/var/log/haproxy.log）
    maxconn 100000                  # 全局最大并发连接
    nbthread 4                      # 线程数（2.0+，与 CPU 核数匹配）
    user haproxy                    # 降权运行（安全）
    group haproxy
    ssl-default-bind-ciphersuites TLS_AES_128_GCM_SHA256:TLS_AES_256_GCM_SHA384
    stats socket /run/haproxy/admin.sock mode 660 level admin   # Unix socket 管理口

# ---------- defaults：默认值（被下面各段继承） ----------
defaults
    mode http                       # 默认七层；TCP 段单独覆盖
    log global
    option httplog
    option dontlognull
    timeout connect 5s              # 连接后端超时
    timeout client  30s             # 客户端侧超时
    timeout server  30s             # 后端侧超时
    timeout check   3s              # 健康检查超时
    errorfile 503 /etc/haproxy/errors/503.http

# ---------- frontend：入口（监听 + ACL 路由） ----------
frontend http-in
    bind *:80
    # ACL：按路径/域名/头做条件匹配
    acl is_api       path_beg /api/           # URL 以 /api/ 开头
    acl is_static    path_end .css .js .png   # 静态资源
    acl is_admin     hdr(host) -i admin.example.com   # 按域名
    use_backend api_servers      if is_api
    use_backend static_servers   if is_static
    default_backend web_servers               # 兜底后端

# ---------- backend：后端组 + 调度 + 健康检查 + 会话保持 ----------
backend web_servers
    balance roundrobin              # 算法：roundrobin/leastconn/source/uri
    option httpchk GET /health      # 主动健康检查（HTTP GET /health）
    http-check expect status 200    # 期望状态码
    cookie SERVERID insert indirect nocache   # Cookie 会话粘滞
    server web1 192.168.1.11:8080 weight 3 check cookie web1
    server web2 192.168.1.12:8080 weight 1 check cookie web2
    server web3 192.168.1.13:8080 check backup    # 备用节点

backend api_servers
    balance leastconn               # 长连接/耗时 API 用最少连接
    option httpchk GET /api/health
    server api1 192.168.1.21:8080 check inter 3s fall 2 rise 3
    server api2 192.168.1.22:8080 check inter 3s fall 2 rise 3
    # check 参数详解：inter 探测间隔、fall 连续失败 N 次判死、
    #                rise 连续成功 N 次判活（默认 inter 2s fall 3 rise 2）

backend static_servers
    balance roundrobin
    option httpchk GET /
    server static1 192.168.1.31:80 check
    server static2 192.168.1.32:80 check

# ---------- TCP 负载（四层）：MySQL/Redis 等任意协议 ----------
frontend mysql-in
    bind *:3306
    mode tcp                        # 四层模式
    default_backend mysql_servers

backend mysql_servers
    mode tcp
    balance leastconn               # 长连接用最少连接
    option tcp-check                # TCP 健康检查（可带协议内容）
    tcp-check connect
    tcp-check send "select 1;\n"    # 真正验证 MySQL 可用
    server db1 10.0.0.11:3306 check weight 1
    server db2 10.0.0.12:3306 check weight 1

# ---------- SSL 终止 + 强制跳转 ----------
frontend https-in
    bind *:443 ssl crt /etc/haproxy/certs/example.com.pem
    # crt 证书文件 = 证书 + 私钥拼接的 .pem（多证书 crt 目录）
    http-request redirect scheme https unless { ssl_fc }   # HTTP 跳 HTTPS
    default_backend web_servers

# ---------- 统计页（运维入口，务必限制访问） ----------
listen stats
    bind *:8404
    mode http
    stats enable
    stats uri /stats                # http://IP:8404/stats
    stats realm HAProxy\ Statistics
    stats auth admin:ChangeMe123    # 基础认证
    stats refresh 5s                # 自动刷新
    stats admin if LOCALHOST        # 仅本机可启停后端（admin 操作）
```

```text
haproxy.cfg 段结构：
global    —— 进程级（日志/连接上限/线程/降权）
defaults  —— 默认值模板（timeout/option 被继承）
frontend  —— 入口：bind 监听 + ACL 匹配 + use_backend 路由
backend   —— 后端组：balance 算法 + server 定义（权重/check/backup）
listen    —— 独立小服务（如 stats 统计页）
server 参数：
  weight N      权重（roundrobin/leastconn 生效）
  check         启用健康检查
  inter 3s      探测间隔
  fall 2 / rise 3   连续失败 2 次判死、成功 3 次判活
  backup        备用（其他全挂才启用）
  cookie xxx    Cookie 粘滞标识
```

### 场景二：Nginx upstream 多后端负载均衡 + 被动健康检查

```nginx
upstream api_servers {
    server 10.0.0.1:8080 weight=2 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 weight=2 max_fails=3 fail_timeout=30s;
    server 10.0.0.3:8080 weight=1 max_fails=3 fail_timeout=30s;

server {
    listen 80;
    server_name api.example.com;
    location / {
        proxy_pass http://api_servers;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_next_upstream error timeout http_502 http_503 http_504;
    }
}
```

```text
验证与观察：

$ curl -sI http://localhost/ | grep -i server          # 后端响应头
$ tail -f /var/log/nginx/access.log                    # 看分发到不同后端
# 摘除某后端：把 server 行改为 down 或删掉 → reload → 连接平滑切换
```

### 场景三：HAProxy HTTP 负载均衡 + 统计页（示例）

```text
架构：
客户端 → HAProxy(:80, frontend http-in)
```

### 场景四：HAProxy TCP 四层转发（MySQL/Redis，示例）

```text
需求：应用连 haproxy-ip:3306，由 HAProxy 分发到两台 MySQL，
      同一会话固定同一台（避免主从延迟读不一致）。

frontend mysql-in
    bind *:3306
    mode tcp
    default_backend mysql_servers

backend mysql_servers
    mode tcp
    balance leastconn
    option tcp-check
    tcp-check connect
    tcp-check send "select 1;\n"
    server db1 10.0.0.11:3306 check weight 1
    server db2 10.0.0.12:3306 check weight 1

验证：
$ mysql -h haproxy-ip -P 3306 -u app -p -e "select 1"   # 业务视角连通
$ ss -tlnp | grep 3306
# 注意：四层模式看不到 HTTP 内容，日志只记录连接建立/关闭
```

### 场景五：四层 vs 七层选型决策表

| 维度 | LVS（四层，内核态） | HAProxy（四+七层） | Nginx（七层为主） |
|------|--------------------|--------------------|------------------|
| 工作位置 | 内核 ip_vs 模块 | 用户态进程 | 用户态进程 |
| 性能 | 最高（百万级连接） | 高（数十万并发） | 高（七层略逊 HAProxy） |
| HTTP 路由 | 不支持 | ACL 路由（强） | location/server_name（强） |
| 健康检查 | 无（Keepalived 配合） | 主动检查（精细） | 被动 max_fails（开源）；主动需 Plus/第三方模块 |
| 会话保持 | -p / sh | Cookie / source | ip_hash / sticky |
| 缓存 | 无 | 无（官方不推荐做缓存） | proxy_cache（强） |
| 静态文件 | 无 | 弱 | 强（Web 服务器本职） |
| 配置方式 | 命令行（ipvsadm） | 单一 haproxy.cfg | 多文件 include |
| 典型角色 | 入口大流量分发 | 纯 LB / 四层 TCP 转发 | Web 托管 + 反代 + 网关 |

```text
选型速记：
入口超大规模 → LVS；纯四层 TCP 转发（DB/Redis）→ HAProxy 或 LVS；
HTTP 业务路由 + 缓存 + 静态站 → Nginx；只要「负载均衡」一件事 → HAProxy；
两者都行时：团队熟悉哪个用哪个，Nginx 生态更通用。
```

## 性能与调优

```text
Nginx 调优：
1. worker_processes auto（= CPU 核数）；worker_connections 调大
   （8 核 × 768 = 约 6 千并发上限，压测前先算这个数）
2. 到后端连接复用：upstream 配 keepalive N + proxy_http_version 1.1
   + proxy_set_header Connection "" —— 减少 TCP 握手/慢启动开销
3. 静态资源：sendfile on、open_file_cache、expires 长缓存
4. 缓冲：proxy_buffering on（默认）防慢客户端拖垮后端；
   流式场景（SSE/WS）关缓冲
5. gzip on 压缩文本响应；TLS 用 TLS1.3 + session tickets 减少握手
6. limit_req/limit_conn 限流保护后端

HAProxy 调优：
1. maxconn 与 ulimit -n 匹配（连接数上限受文件描述符限制）
2. nbthread 与核数匹配；绑核（cpu-map）可进一步降低延迟
3. timeout 合理设置：client/server 过短会误杀慢业务，过长浪费连接
4. 长连接后端用 leastconn；短连接用 roundrobin
5. 开启 stats 页 + 日志，用数据驱动调优（看 session rate / errors）

通用：
- 压测工具 ab / wrk / hey，压测时观察 CPU、连接数、延迟分位
- 连接数耗尽（Too many open files）是代理层最常见瓶颈：
  ulimit -n 调大（systemd 里 LimitNOFILE=65535）
- 看真实指标：ss -s（连接统计）、ss -tlnp、/proc/sys/net/core/somaxconn
```

## 安全与权限

```text
1. 真实 IP 传递与防伪造
   代理必须设置 X-Real-IP / X-Forwarded-For，后端才能拿到客户端 IP；
   但 XFF 可伪造：后端只应信任「来自可信代理」的 XFF，或代理覆盖
   （proxy_set_header X-Forwarded-For $remote_addr 直接写死客户端 IP）。

2. TLS 终结在代理层
   证书集中在代理管理，后端走内网 HTTP；证书轮换只需动代理。
   ssl_protocols 至少 TLSv1.2；关闭弱加密套件。

3. 隐藏后端
   后端只监听内网 IP（防火墙限制来源），客户端永远无法直连后端。

4. 限流防刷
   Nginx：limit_req_zone + limit_req（速率 + burst）；
   HAProxy：stick-table + http-request track-sc0 做 IP 限速。

5. 统计页保护
   HAProxy stats 必须配认证（stats auth），admin 操作限制本机
   （stats admin if LOCALHOST），生产建议绑内网 IP 或走 VPN。

6. 降权运行
   nginx 默认 worker 以 www-data 运行；haproxy 以 haproxy 用户运行，
   避免 root 权限被利用。

7. Red Hat 系差异（EPEL / SELinux / firewalld）
   - haproxy 包在 RHEL 默认仓库没有，需启用 EPEL：dnf install epel-release
     && dnf install haproxy
   - RHEL 自带 nginx 版本较旧，EPEL 或 nginx 官方仓库提供新版本
   - SELinux：nginx 反向代理连接后端默认被拒（502），需
     setsebool -P httpd_can_network_connect 1；
     haproxy 绑定非标准端口需 semanage port -a -t http_port_t -p tcp 8404
   - firewalld 放行：firewall-cmd --permanent --add-port=80/tcp
     --add-port=8404/tcp && firewall-cmd --reload
```

## 故障排查

### 案例 1：后端 502 Bad Gateway

```text
现象：访问站点间歇性/全部 502，页面显示 Bad Gateway。

排查步骤：
  1. nginx 错误日志：tail -f /var/log/nginx/error.log
     （关键行：connect() failed (111: Connection refused) while connecting to upstream）
  2. 确认后端进程活着：ss -tlnp | grep 8081；ps aux | grep 后端进程
  3. 直接测后端：curl -sI http://127.0.0.1:8081/health
  4. 看完整配置展开：nginx -T | grep -A8 'upstream'
  5. 检查代理超时：proxy_read_timeout 太短会 504（网关超时）

根因（按概率）：
  a. 后端挂了/没监听 —— Connection refused
  b. 后端地址/端口配错 —— 配了不存在的 IP
  c. 后端响应太慢超时 —— 504 Gateway Timeout
  d. SELinux（Red Hat）拦截代理连后端 —— 502 且审计日志被拒

解法：按上面顺序定位；后端恢复后 502 自动消失（无需重启 nginx）；
      Red Hat 上先看 setsebool -P httpd_can_network_connect 1。
```

### 案例 2：后端摘除不生效（请求还往故障后端打）

```text
现象：运维把某台后端 down 了/进程停了，但代理还在往它发请求。

排查步骤：
  1. 检查摘除方式：改配置后是否 reload（nginx -s reload 是平滑生效）
  2. 健康检查是否生效：nginx -T | grep -E 'max_fails|fail_timeout'
  3. 看连接是否被复用：keepalive 长连接可能还挂在旧后端上
  4. HAProxy：stats 页看该 server 状态是否 UP/DOWN

根因：
  a. 只改了文件没 reload
  b. 被动健康检查参数问题：max_fails 太大/fail_timeout 太短，
     后端还没被判死就继续接流量；或健康检查路径后端返回 200 但业务已坏
  c. 长连接复用：keepalive 池里的连接仍指向旧后端（一般会在下次请求
     时发现断开重连，但短时间会报错）

解法：主动摘除用 down 标记 + reload；被动摘除调优 max_fails/fail_timeout
      （如 3/30s）；关键服务上主动健康检查（Nginx Plus / 第三方模块 /
      HAProxy 的 check）。
```

### 案例 3：会话保持失效，用户登录态反复丢失

```text
现象：用户操作中突然被登出/购物车清空，日志显示请求打到不同后端。

排查步骤：
  1. 确认粘滞配置是否生效：nginx -T | grep -E 'ip_hash|sticky'
     / haproxy 配置 cookie 行
  2. 看响应是否带 Set-Cookie（HAProxy cookie insert）
  3. 确认后端是否也配了 session 共享（Redis）
  4. 检查是否跨代理层（LVS 层 -p 与七层粘滞不一致）

根因：
  a. 只做了 LVS 层持久连接，七层没配粘滞（或反过来）
  b. Cookie 被后端覆盖/同名冲突，粘滞 Cookie 丢失
  c. 后端重启/扩容导致 hash 重排（ip_hash 对后端增减敏感）
  d. 用户 IP 变化（移动网络）导致 source/ip_hash 失效

解法：
  分层明确：四层用 -p/sh、七层用 cookie/ip_hash，选一层做粘滞；
  后端会话共享（Redis）才是根治（无状态后端不需要粘滞）；
  hash 类算法用一致性哈希（HAProxy 2.4+ consistent hash）减少漂移。
```

### 案例 4：连接数耗尽（Too many open files / 大量 TIME_WAIT）

```text
现象：高并发下代理报 "Too many open files"，新连接失败；
      ss -s 看到大量 TIME_WAIT。

排查步骤：
  1. ulimit -n 当前值：cat /proc/<pid>/limits | grep 'open files'
  2. 连接统计：ss -s；ss -tlnp | wc -l
  3. 看 TIME_WAIT 来源：ss -tan state time-wait | wc -l
  4. systemd 服务限制：systemctl show nginx | grep LimitNOFILE

根因：
  a. 进程 fd 上限太低（默认 1024）——系统提示 Too many open files
  b. 短连接业务没做 keepalive 复用，每请求新建连接 → 大量 TIME_WAIT
  c. somaxconn/backlog 太小，accept 队列溢出

解法：
  systemd 单元配 LimitNOFILE=65535（或更大）并 reload daemon；
  upstream keepalive + proxy_http_version 1.1 复用连接；
  net.core.somaxconn=4096、net.ipv4.tcp_tw_reuse=1（出向）；
  观察期用 ss -s 对比优化前后连接数。
```

## 常见问题

```text
Q1: 四层和七层负载均衡怎么选？
A: 只转发 TCP/UDP（数据库、Redis、gRPC 等任意协议）用四层
   （LVS/HAProxy mode tcp/Nginx stream）；要按域名/URL/Header 路由、
   做缓存/TLS 终结/改写用七层（Nginx/HAProxy mode http）。

Q2: 会话保持怎么做？
A: 四层用源 IP 哈希或 LVS -p；七层用 Cookie 粘滞（HAProxy cookie
   insert、Nginx ip_hash/sticky）。注意粘滞会牺牲均衡性；根治方案是
   后端无状态化 + 会话存 Redis，就不需要粘滞。

Q3: Nginx 和 HAProxy 怎么选？
A: 需要 Web 服务器（静态托管、缓存）→ Nginx；纯负载均衡尤其是
   四层 TCP/高并发 → HAProxy（LB 功能更专、健康检查更精细）；
   两者都能做七层 HTTP 路由，团队熟哪个用哪个。

Q4: 后端拿到的是代理 IP，不是客户端 IP，怎么办？
A: 代理配 X-Real-IP / X-Forwarded-For 头传递真实 IP，后端从这些头取；
   后端只信任来自可信代理的头（防伪造），代理侧覆盖 XFF 更安全。

Q5: 健康检查有哪些方式？
A: 主动：代理定期探测后端（HAProxy check + option httpchk、
   Nginx Plus health_check）；被动：按真实请求失败情况判断
   （Nginx 开源版 max_fails/fail_timeout）。生产建议主动为主、
   被动兜底。

Q6: 502 / 503 / 504 分别代表什么？
A: 502 Bad Gateway：代理连不上后端或后端返回非法响应；
   503 Service Unavailable：代理无可用后端（全被健康检查摘除）；
   504 Gateway Timeout：代理转发后等待后端响应超时。

Q7: Nginx 开源版能做主动健康检查吗？
A: 默认不行（只有被动 max_fails），需要编译第三方模块
   nginx_upstream_check_module，或换 HAProxy/Nginx Plus。

Q8: 限流怎么做？
A: Nginx limit_req_zone + limit_req（速率+burst）、limit_conn（并发）；
   HAProxy 用 stick-table + http-request track-sc0 计数限速。
   代理层限流是保护后端的第一道闸。

Q9: TLS 终止在代理层有什么要注意的？
A: 证书集中管理、后端走内网 HTTP；注意：① 传递 X-Forwarded-Proto
   让后端知道原始协议（http/https）；② 强制跳转 https 防降级；
   ③ 长连接 + TLS 会话复用减少握手开销。
```

## 面试题

```text
1. 反向代理和正向代理的区别？
   答：反向代理代理「服务端」——客户端不知道真实后端，代理统一入口
   （负载均衡、TLS 终结、隐藏后端）；正向代理代理「客户端」——
   服务端不知道真实客户端（翻墙、缓存、内网出网审计）。

2. Nginx 负载均衡支持哪些算法？分别适合什么场景？
   答：轮询（默认，短连接均匀）；weight 加权轮询（异构后端）；
   least_conn（长连接/耗时不均）；ip_hash（会话保持）；
   fair（按响应时间，第三方）；url_hash（缓存类按 URL 打散）。
   hash 类后端增减会重排，注意一致性哈希。

3. 健康检查的实现与区别？
   答：主动——代理定时探测（HAProxy check + httpchk、Nginx Plus），
   准确但占资源；被动——按真实请求失败数判断（Nginx 开源
   max_fails/fail_timeout），零额外开销但有滞后。
   生产通常主动为主、被动兜底。

4. 502/504 的排查思路？
   答：502 是「连不上/响应非法」——查后端进程、端口、防火墙、
   SELinux、upstream 配置；504 是「连上但超时」——查后端处理耗时、
   proxy_read_timeout 是否太短、后端连接池是否耗尽。先看
   /var/log/nginx/error.log 的 connect() failed 与 upstream timed out。

5. 会话保持的实现方案与坑？
   答：方案：ip_hash（源 IP）、Cookie 粘滞（HAProxy cookie insert、
   Nginx sticky）、LVS -p 持久连接。坑：热点 IP 粘连导致负载不均；
   后端增减导致 hash 重排丢会话；用户 IP 变化（移动网络）失效。
   根治：后端无状态 + 会话 Redis 共享，彻底不依赖粘滞。

6. 高并发下代理的性能瓶颈在哪？怎么优化？
   答：瓶颈常在三处：文件描述符上限（Too many open files）、
   连接建立开销（握手/慢启动）、单核事件循环（旧版 HAProxy）。
   优化：ulimit/systemd LimitNOFILE 调大；upstream keepalive 复用
   连接；worker/thread 与核数匹配；TLS 会话复用；压测（wrk/ab）
   验证后再扩实例。

7. LVS / HAProxy / Nginx 怎么分工？
   答：LVS 内核态四层，扛入口最大流量（百万级连接），只做 IP:端口
   分发；HAProxy 专职 LB，四层 TCP（DB/Redis）与七层 HTTP 都行，
   健康检查精细；Nginx Web 服务器 + 反代，七层路由/缓存/静态最强。
   典型：LVS → Nginx 集群 → 应用。

8. 如何防止用户伪造 X-Forwarded-For 绕过风控？
   答：代理层覆盖（proxy_set_header X-Forwarded-For $remote_addr
   直接写客户端 IP，丢弃用户自带的 XFF）；后端只接受来自可信代理
   的连接；或记录代理连接的真实 IP（$remote_addr）作为权威来源。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 反向代理必配 X-Real-IP / X-Forwarded-For / X-Forwarded-Proto，后端审计、风控、日志都依赖
2. upstream 配 keepalive + proxy_http_version 1.1 + 清空 Connection 头，复用到后端的连接
3. 健康检查用「与业务一致」的探活路径（HAProxy httpchk GET /health 期待 200），别只查端口
4. TLS 在代理层终结，证书集中管理；生产只开 TLSv1.2+，强制 http→https 跳转
5. limit_req/limit_conn 限流 + 代理层防刷，保护后端是第一优先
6. 改配置三步走：nginx -t / haproxy -c 验证 → reload（平滑）→ 观察日志与指标
7. 摘除后端用 down 标记 + reload，恢复后去掉 down 再 reload，杜绝粗暴重启
8. 会话保持选一层做（四层 -p 或七层 cookie），别两层都配互相打架
9. 静态资源分离：独立 location + expires 长缓存（带 hash 文件名 immutable），动态走反代
10. 上线前压测（wrk/ab）并把文件描述符上限、somaxconn、worker 数调到位

### 踩坑记录

```text
坑 1：没传 X-Forwarded-For，后端拿到的是代理 IP
结论：后端日志全是代理 IP，真实客户端不可见，审计/风控/限流全失效。
原因：反向代理默认不转发客户端 IP 头。
解法：配 proxy_set_header X-Real-IP $remote_addr 和
     X-Forwarded-For $proxy_add_x_forwarded_for；后端从这些头取值。

坑 2：一报 502 就重启代理，重启完还是 502
结论：502 时重启 nginx，服务没恢复，还中断了正常连接。
原因：502 是「后端不可用」，根因在后端（挂了/超时/端口错/SELinux），
     不在代理，重启代理治标不治本。
解法：tail error.log 看 connect() failed 指向哪个后端 → 查后端进程、
     端口、防火墙、SELinux；后端恢复后 502 自动消失。

坑 3：upstream 没配 keepalive，高并发下握手开销巨大
结论：压测 QPS 上不去，后端看到大量新建连接，CPU 被打在握手上。
原因：默认每个请求都新建到后端的 TCP 连接（无连接复用）。
解法：upstream 配 keepalive 32 + proxy_http_version 1.1
     + proxy_set_header Connection ""。

坑 4：配了 ip_hash 后负载严重不均
结论：某台后端连接数是其他的数倍，热点用户全压一台。
原因：源 IP 哈希把公司出口 NAT 等热点 IP 固定到同一后端；
     且后端增减时 hash 重排，还会引发会话大面积迁移。
解法：评估是否真需要粘滞；热点场景换 Cookie 粘滞或后端 Redis
     共享会话；hash 算法用一致性哈希减少漂移。

坑 5：后端信任 X-Forwarded-For，被伪造 IP 绕过风控
结论：攻击者自填 XFF 头（如 127.0.0.1），绕过 IP 白名单/限流。
原因：代理默认把客户端传入的 XFF 追加/透传，后端直接信任。
解法：代理覆盖 XFF（写死 $remote_addr），后端只接受可信代理连接，
     禁止客户端直连后端。

坑 6：健康检查路径写错，全部后端被摘除
结论：503 Service Unavailable，所有请求失败，代理日志一堆 check 失败。
原因：option httpchk GET /health 路径不存在或返回非 200，
     HAProxy 把所有后端判死。
解法：先 curl -sI http://后端/health 确认探活路径真实可达；
     检查 http-check expect status 200；staging 先验证再上线。

坑 7：keepalive 长连接 + 后端摘除，旧连接短暂报错
结论：reload 摘除后端后，少量请求仍报 502/超时。
原因：keepalive 池里残留指向已摘除后端的空闲连接，复用瞬间失败。
解法：摘除前先 down 标记并等待 keepalive 连接自然过期；
     配合 proxy_next_upstream error timeout 自动重试下一后端。

坑 8：文件描述符上限没调，高并发连接数耗尽
结论：业务高峰报 Too many open files，新连接全失败。
原因：进程 fd 上限 1024（默认），并发连接轻松打满。
解法：systemd 单元 LimitNOFILE=65535 + systemctl daemon-reload
     重启；同步调大 net.core.somaxconn；用 ss -s 观察连接数。

坑 9：SELinux 拦截反代连后端（Red Hat 系）
结论：RHEL 上 nginx 配置全对，curl 后端通，但通过代理就是 502。
原因：SELinux 默认禁止 httpd（nginx）作为客户端连接任意网络端口。
解法：setsebool -P httpd_can_network_connect 1；审计确认为
     sealert -a /var/log/audit/audit.log。

坑 10：TLS 终止后后端拿不到协议信息
结论：后端强制 https 重定向逻辑失效，回调地址变成 http。
原因：代理 TLS 终止后未传递原始协议，后端以为请求是 http。
解法：proxy_set_header X-Forwarded-Proto $scheme；
     后端从该头判断原始协议。
```
