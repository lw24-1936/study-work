## 概述

Keepalived 是 Linux 上实现高可用的经典工具，基于 **VRRP 协议**（Virtual Router Redundancy Protocol，虚拟路由冗余协议）实现「主备切换 + VIP 漂移」。核心能力：多台机器组成一个「VRRP 组（虚拟路由器）」，组内按优先级选举出一个 **MASTER** 持有虚拟 IP（VIP），MASTER 挂了 VIP 自动漂移到 **BACKUP** 节点，客户端始终访问 VIP，切换无感知。Keepalived 还内置**健康检查（vrrp_script）**——不仅机器挂了能切换，**服务挂了（nginx/haproxy 进程异常）也能触发切换**，常配合 Nginx/HAProxy/LVS 做高可用负载均衡入口。

```text
Keepalived 解决什么：
多台机器共享一个「虚拟 IP（VIP）」，MASTER 持 VIP 对外服务，
MASTER 挂了 VIP 漂移到 BACKUP，客户端无感知。
避免负载均衡器/网关/入口反代成为单点故障（SPOF）。
```

```text
本文架构线索：
VRRP 协议（怎么选主、怎么漂移）→ keepalived.conf（怎么配置）
→ vrrp_script（服务级健康检查）→ notify 脚本（切换动作）
→ 常见故障（脑裂/VIP 不漂移/切换后服务不可用）
```

## 核心概念

1. **VIP（Virtual IP，虚拟 IP）**：对外暴露的地址，不属于任何一台真实机器，故障时在节点间漂移。客户端只访问 VIP，永远不感知后端是哪台机器。VIP 是 keepalived 一切工作的载体。

2. **虚拟路由器（Virtual Router）**：一个 VRRP 组 = 一台「逻辑路由器」，由多台真实机器组成，对外以同一个虚拟路由器标识（VRID，0~255）和 VIP 呈现。主备节点 `virtual_router_id` 必须一致，才能组成同一个虚拟路由器。

3. **MASTER / BACKUP**：组内角色。**MASTER** 持有 VIP 对外服务、周期发送 VRRP 通告；**BACKUP** 监听通告待命，MASTER 失联后按优先级竞选接管。同一虚拟路由器内同一时刻必须只有**一个 MASTER**。

4. **priority 优先级（0~255）**：竞选依据，**数值高者成为 MASTER**。典型配置主 100、备 90。特殊值：**0** = 主动放弃（MASTER 正常退出/重启时先通告 priority 0，让 BACKUP 立即接管，不用等超时）；**255** = 保留值，表示拥有真实 IP 地址的路由器（一般不用于实例配置）。

5. **advert_int 通告间隔**：MASTER 发送 VRRP 通告的周期（秒，默认 1）。BACKUP 在 **3 × advert_int + skew_time** 内收不到通告即判 MASTER 故障。skew_time 与 priority 相关（优先级越低等待越长，避免多 BACKUP 同时抢主打架）。

6. **nopreempt 非抢占**：MASTER 恢复后是否自动抢回 VIP。默认抢占（preempt）；配置 `nopreempt` 后，只要当前 MASTER 还健康，恢复的节点不抢回，避免来回切换抖动。

7. **vrrp_script 健康检查脚本**：keepalived 自带的「服务级体检」——周期执行脚本/命令，失败则给实例降分（weight），优先级跌破备节点后触发切换。**这是「机器活着但服务挂了」也能自动切换的关键**。

8. **组播 vs 单播**：VRRP 通告默认走组播（224.0.0.18，协议号 112）。**公有云 VPC 大多禁组播**，需改用单播模式（`unicast_src_ip` + `unicast_peer` 指定对端地址）。

```text
Keepalived 核心要素：
VIP（漂移地址）+ VRID（组标识）+ MASTER/BACKUP（角色）
+ priority（竞选分数）+ advert_int（心跳）+ vrrp_script（服务体检）
```

## 工作原理

### 1. VRRP 报文

```text
VRRP 通告报文（IPv4）关键字段：
Version (4bit) + Type (4bit)     # 版本 3 / 类型 1=通告
VRID (8bit)                      # 虚拟路由器 ID（组标识）
Priority (8bit)                  # 0~255，竞选分数
Count IP Addrs (8bit)            # 本通告包含的 VIP 数量
Adver Int (8bit)                 # 通告间隔（秒）
Checksum                         # 校验和
IP Address(es)                   # VIP 列表（一个虚拟路由器可带多个 VIP）
Authentication                   # 认证字段（PASS 密码 / AH 头）
组播地址：224.0.0.18（IPv4） 目的端口/协议：IP 协议号 112
```

### 2. 状态机与选举

```text
VRRP 状态机：Initialize（初始化）→ Backup（备）⇄ Master（主）

1. 启动：所有节点进入 Initialize → 立即转 BACKUP
2. 竞选：BACKUP 按 priority 比较——
   收到通告：priority 比自己低 → 忽略，继续 BACKUP
             priority 比自己高 → 尊重对方，保持 BACKUP
             priority 相等 → 比真实 IP 大小（大者胜）
3. 胜出：无人比自己强（或收到 priority=0 放弃通告）→ 转 MASTER
4. MASTER 职责：绑定 VIP + 周期发通告（advert_int）+ 处理对端通告
5. 失主：3 × advert_int + skew_time 未收到通告 → 降级 BACKUP（旧 VIP 释放）
   （此时其他 BACKUP 按同样规则竞选，最终唯一 MASTER 接管 VIP）
```

### 3. VIP 漂移过程（检测→切换→接管→恢复）

```text
T0   MASTER 宕机（断电/内核崩溃/被 kill）
T1   3s（1s×3 超时 + skew_time）后 BACKUP 判定 MASTER 失联        [检测]
T2   BACKUP 转 MASTER：绑定 VIP 到网卡                              [切换]
T3   发送免费 ARP（gratuitous ARP）宣告 VIP → 新 MAC，
     交换机刷新 MAC 表、客户端刷新 ARP 缓存                        [接管]
T4   新连接全部打到新 MASTER，服务无缝接管
T5   原 MASTER 恢复上线：默认抢占（priority 高）→ 重新选举抢回 VIP
     或配置 nopreempt → 保持现状，原主以 BACKUP 身份归队            [恢复]
```

```text
关键点：VIP 漂移的「灵魂」是免费 ARP——
不宣告 ARP，交换机 MAC 表还是旧的，流量照样发往死掉的旧 MASTER。
所以「VIP 已绑但访问不通」优先怀疑 ARP/交换机学习问题。
```

### 4. 健康检查联动（服务级切换）

```text
vrrp_script 机制：
1. 周期执行脚本（如 killall -0 nginx / curl -s http://127.0.0.1/health）
2. 成功返回 0，失败返回非 0
3. 失败时给实例 priority 减 weight（如 -20）：
   主节点：100 → 80，低于备节点 90 → 备节点竞选胜出，切换
   备节点：90 → 70，更不可能当主（防止备节点自身有故障时抢主）
4. 脚本恢复成功 → priority 回升，按抢占策略回归
本质：把「服务健康」折算进「竞选分数」，让选举结果反映真实可用性
```

## 常用命令与配置

```shell
# ---------- 安装 ----------
apt install keepalived            # Debian/Ubuntu（本机未装，如实标注）
dnf install keepalived            # CentOS/RHEL/Fedora

# ---------- 服务管理（systemd，见 [[10.3-编写 Service Unit]]）----------

systemctl restart keepalived

# ---------- 观察 VIP 归属（核心验证手段：VIP 在谁身上谁就是主）----------
ip addr show | grep 192.168.1.100        # 示例：VIP 在本机 = 本机是 MASTER
ip -br addr                               # 实测：本机无 VIP（未部署 keepalived）

# ---------- 观察切换日志 ----------
journalctl -u keepalived -f               # 关注 Entering MASTER/BACKUP、VRRP 事件
tail -f /var/log/syslog | grep -i keepalived   # Debian/Ubuntu 另一处日志

# ---------- 抓 VRRP 报文（验证心跳是否在走）----------
tcpdump -i eth0 vrrp -nn                  # 示例：应看到 224.0.0.18 的 VRRP 通告
tcpdump -i wlp0s20f3 vrrp -nn             # 实测：本机 tcpdump 可用，但无 keepalived 无报文

# ---------- 验证切换（演练）----------
systemctl stop keepalived                 # 停主节点 → 到备节点看 VIP 是否漂移
ip addr show | grep 192.168.1.100         # 备节点 3~5s 内出现 VIP = 切换成功
curl -I http://192.168.1.100/             # 业务验证
```

## 配置文件解析

### 1. 双机 Nginx HA 完整配置（逐行解析）

```ini
# ============ 主节点 /etc/keepalived/keepalived.conf ============
global_defs {
    router_id LVS_1              # 节点标识：本机在 VRRP 网络中的名字，每台唯一
    enable_script_security       # 脚本运行安全限制（路径需绝对路径）
}

# 健康检查脚本：检测 nginx 是否活着（进程级）
vrrp_script chk_nginx {
    script "/usr/bin/killall -0 nginx"   # 进程存在返回 0；nginx 挂了返回非 0
    interval 2                            # 每 2 秒检查一次
    weight -20                            # 检查失败：实例 priority -20（100→80）
    timeout 2                             # 脚本执行超时 2 秒（防脚本卡死拖垮检查）
    fall 2                                # 连续 2 次失败才生效（防抖动误判）
    rise 2                                # 连续 2 次成功才恢复（防抖动恢复）
}

# VRRP 实例：一个实例管一组 VIP
vrrp_instance VI_1 {
    state MASTER               # 初始角色（仅初始，实际由 priority 决定）
    interface eth0             # VIP 绑定网卡：必须选心跳可达的物理网卡
    virtual_router_id 51       # 组 ID（1~255）：主备必须一致，不同组用不同 ID
    priority 100               # 竞选分数：主 100
    advert_int 1               # 通告间隔 1 秒（主备必须一致）
    nopreempt                  # 可选：不抢占（防止主恢复后抖动）
    # preempt_delay 30         # 可选：抢占延时 30 秒（主恢复后 30s 才抢回）

    authentication {           # 心跳认证：防伪造 VRRP 包
        auth_type PASS         # PASS（明文密码）/ AH（IPSec 认证头，较老）
        auth_pass 1111         # 密码：主备必须一致（8 位以内）
    }

    virtual_ipaddress {        # VIP 列表：可配多个，全部随漂移
        192.168.1.100/24 dev eth0    # VIP + 掩码 + 绑定网卡
    }

    track_script {             # 关联健康检查：脚本失败 → 实例降分 → 可能切换
        chk_nginx
    }

    # 切换动作回调：角色变化时执行（发通知/切流量/告警）
    notify_master "/etc/keepalived/notify.sh MASTER"   # 成为主时执行
    notify_backup "/etc/keepalived/notify.sh BACKUP"   # 变回备时执行
    notify_fault  "/etc/keepalived/notify.sh FAULT"    # 进入故障态时执行
}
```

```ini
# ============ 备节点配置：仅以下两处不同 ============
vrrp_instance VI_1 {
    state BACKUP               # 初始角色：BACKUP
    priority 90                # 优先级：90（比主低）
    # 其余字段（virtual_router_id/advert_int/auth_pass/VIP）与主完全一致
}
```

### 2. notify 脚本示例

```bash
#!/bin/bash
# /etc/keepalived/notify.sh —— 角色变化动作（示例）
# $1 = MASTER/BACKUP/FAULT
case "$1" in
    MASTER)
        # 成为主：刷新 ARP、启动业务、通知监控
        arping -c 3 -I eth0 -s 192.168.1.100 192.168.1.100 >/dev/null 2>&1
        systemctl start nginx
        curl -s -X POST -d 'role=master' http://monitor.local/ha-event
        ;;
    BACKUP)
        systemctl stop nginx   # 备节点不对外服务（可选策略）
        ;;
    FAULT)
        curl -s -X POST -d 'state=fault' http://monitor.local/ha-event
        ;;
esac
exit 0
```

### 3. 双 VIP 互为主备（两台机器互为对方的备）

```ini
# 机器 A：实例 VI_1 当主（priority 100）+ 实例 VI_2 当备（priority 90）
vrrp_instance VI_1 {
    state MASTER; virtual_router_id 51; priority 100
    virtual_ipaddress { 192.168.1.100/24 }
}
vrrp_instance VI_2 {
    state BACKUP; virtual_router_id 52; priority 90
    virtual_ipaddress { 192.168.1.101/24 }
}

# 机器 B：正好反过来 —— VI_1 当备（90）、VI_2 当主（100）
vrrp_instance VI_1 {
    state BACKUP; virtual_router_id 51; priority 90
    virtual_ipaddress { 192.168.1.100/24 }
}
vrrp_instance VI_2 {
    state MASTER; virtual_router_id 52; priority 100
    virtual_ipaddress { 192.168.1.101/24 }
}
# 效果：A 持 192.168.1.100（nginx 流量入口），B 持 192.168.1.101（如管理面/其他业务），
# 互为备机，两台机器都在干活，资源利用率翻倍
```

```text
关键字段速记：
virtual_router_id   组 ID，主备必须相同；不同组用不同 ID（同一网卡可跑多个组）
priority            竞选分数，高的当主；差值建议 ≥20（防抖动）
advert_int          通告间隔，主备必须一致
virtual_ipaddress   VIP 列表，随角色漂移
track_script        服务健康检查联动（服务挂了也能切换）
nopreempt           不抢占（防二次抖动）
notify_master/backup/fault   角色变化回调（通知/动作）
```

## 应用场景实战

### 场景一：双机 Nginx 高可用（最经典的入口 HA）

```text
架构：
192.168.1.10（主 nginx，priority 100）──VIP 192.168.1.100── 对外服务
192.168.1.11（备 nginx，priority 90） ──主挂后 3~5s 接管 VIP──

实施步骤：
1. 两台机器装 nginx + keepalived，nginx 配置一致（同站点、同 upstream）
2. 主节点配置：state MASTER + priority 100 + VIP 192.168.1.100/24 + track_script chk_nginx
3. 备节点配置：state BACKUP + priority 90 + 其余完全一致
4. systemctl enable --now keepalived，验证 VIP 在主节点
5. 演练一（进程级）：kill nginx 主进程 → 观察 track_script 降分 → 切换
6. 演练二（节点级）：systemctl stop keepalived（主）→ VIP 漂移 → curl 仍 200
7. 配 notify 脚本：MASTER 时发免费 ARP，防止交换机 MAC 表未刷新
适用：Nginx/HAProxy 反代入口、网关、一切「无状态 + 对外暴露」的组件
```

### 场景二：LVS + Keepalived（负载均衡器高可用）

```text
架构：
                  VIP 192.168.1.100（漂移）
        ┌──────────────┴──────────────┐
   LVS1（主，priority 100）      LVS2（备，priority 90）
        └──────────────┬──────────────┘
                 后端 Web 1 / 2 / 3（real server）

要点：
1. Keepalived 负责 LVS director 本身的高可用（VIP 漂移）
2. LVS 负责把流量分发到多台后端（见 [[19.3-LVS 负载均衡]]）
3. keepalived.conf 中配置 virtual_server 段：Keepalived 内置 LVS 管理
   （real server 的 IPVS 规则由 keepalived 下发，健康检查自动摘除故障后端）
4. director 挂掉 → VIP 漂移到备 director → 备机接管 IPVS 规则，流量不中断
5. 后端 real server 需配 lo 回环 VIP + arp_ignore/arp_announce（DR 模式）
本机验证：modprobe ip_vs 成功、/proc/net/ip_vs 可读（IP Virtual Server
version 1.2.1），说明内核 LVS 能力就绪；ipvsadm 未安装（安装：apt install
ipvsadm / dnf install ipvsadm）。
```


### 场景三：双 VIP 互为主备（资源利用率翻倍）

```text
背景：Active-Standby 的备机闲置是浪费；业务有两个入口（如 www 与 admin）
```

### 场景四：健康检查脚本实战（进程 / 端口 / 页面三档）

```bash
#!/bin/bash
# /etc/keepalived/chk_nginx.sh —— 三档检查：进程 → 端口 → 页面（示例）
# 返回 0 = 健康；返回非 0 = 故障（触发 track_script 降分）
# 档位一：进程存在
if ! killall -0 nginx 2>/dev/null; then exit 1; fi
# 档位二：端口在监听
ss -tln | grep -q ':80 ' || exit 1
# 档位三：页面真实可用（加超时，防脚本卡死）
curl -fsS --max-time 3 http://127.0.0.1/healthz >/dev/null 2>&1 || exit 1
exit 0
```

```ini
# 对应 keepalived.conf（脚本方式：比 killall 命令更全面）
vrrp_script chk_nginx {
    script "/etc/keepalived/chk_nginx.sh"
    interval 2          # 每 2 秒
    timeout 3           # 脚本最长 3 秒
    weight -20          # 失败降 20 分
    fall 2              # 连续 2 次失败才算故障（防抖动）
    rise 2              # 连续 2 次成功才恢复
}
```

```text
档位选择：进程级最轻（killall -0）但「进程在、服务不可用」检测不到；
端口级覆盖监听缺失；页面级最真实但开销大（curl 每 2 秒一次）。
生产建议：核心入口用端口级 + 低频页面级组合（如 interval 5 的页面检查）。
```

### 场景五：公有云 VPC 单播模式（组播被禁的解法）

```text

}
注意：
1. 云厂商安全组要放行协议 112（VRRP）或指定端口（keepalived 单播默认 112）

   使用云厂商 HA 产品（SLB 多可用区、RDS 高可用版）替代自建
```

## 性能与调优

```text
1. 切换速度：检测时间 = 3 × advert_int + skew_time
   默认 1s×3 = 3 秒 + 少量 skew；要更快调小 advert_int（如 0.5s→约 1.5s 检出），
   但过小在弱网/无线环境易误判（心跳与业务共用链路时更明显）
2. skew_time 公式（RFC 5798）：skew = (256 - priority) / 256 × 通告间隔
   priority 90 → 约 0.65s；priority 250 → 约 0.02s
   作用：让「更可能当主的」BACKUP 先竞选，减少无谓的多次竞选
3. 抖动预防：priority 差值拉大（≥20）+ nopreempt + fall/rise 计数
   （fall 2 可滤掉单次脚本抖动；nopreempt 防止恢复后二次切换）
4. 健康检查开销：interval 2~5s 合适；脚本必须轻量 + timeout；
   页面级 curl 检查降频（interval 5+）；避免在脚本里做重查询/大页面
5. 多实例多 VIP：一个 vrrp_instance 一个 VIP 组；同一网卡可跑多个实例
   （不同 virtual_router_id），但别让一台机器的实例数过多（通告互扰）
6. 抢占延时：preempt_delay（如 30s）让恢复的节点先确认业务就绪再抢回
7. 通告与业务带宽：VRRP 通告极小（几十字节），但心跳建议走独立网卡/网络，
   避免业务洪峰时通告丢失造成误切换
```

```text
调优核对表：
□ 检测时间（3×advert_int + skew）≤ 业务容忍时间
□ 主备 priority 差 ≥ 20，避免一抖动就翻转
□ 关键切换配了 nopreempt 或 preempt_delay
□ 健康检查脚本轻量、带 timeout、带 fall/rise 计数
□ 上线前完成「停主 / 杀服务 / 断网」三种演练并记录切换耗时
```

## 安全与权限

```text
1. 心跳认证：authentication { auth_type PASS; auth_pass xxx } 必配！
   不配认证 = 任何人都能发 VRRP 通告：伪造高 priority 通告可把真主挤下线
   （VRRP 劫持）。主备 auth_pass 必须一致，否则收不到心跳（互相视为非法包）
2. 心跳网络隔离：VRRP 走独立网卡/VLAN，业务拥塞不误判心跳，
   攻击者不易顺着业务网伪造通告
3. 防火墙放行（Ubuntu，实测 ufw active）：
   ufw allow proto 112 from <对端IP>        # 放行 VRRP 协议（组播/单播）
   # 或按服务：ufw allow vrrp（部分版本支持）
4. 配置文件权限：keepalived.conf 含认证口令 → chmod 600 /etc/keepalived/keepalived.conf
5. 运行权限：keepalived 需 root 配 VIP/ARP；脚本（vrrp_script/notify）要
   避免用 root 执行不可信逻辑，enable_script_security + 脚本路径写绝对路径
6. VIP 的 ARP 安全：切换靠免费 ARP；确认交换机不抑制 gratuitous ARP
   （部分交换机默认限速），否则切换后流量仍发往旧节点
```

## 故障排查

### 案例一：VIP 不漂移（主挂了，备节点没接管）

```shell
# 1. 主节点真的挂了吗（还是网络分区/服务挂）？
ping -c 3 <主节点IP>
# 2. 备节点 keepalived 状态与日志（核心证据）
systemctl status keepalived
journalctl -u keepalived -n 50
#    关注：是否 "Entering BACKUP state" 后一直没变化；有无 "smtp_alert" 报错
# 3. 配置核对：priority / virtual_router_id / advert_int / auth_pass
grep -E 'state|priority|virtual_router_id|advert_int|auth_pass' /etc/keepalived/keepalived.conf
# 4. 心跳通不通（抓包验证，本机 tcpdump 实测可用）
tcpdump -i eth0 vrrp -nn          # 备节点应能看到主的通告；看不到 = 网络/防火墙问题
# 5. 防火墙是否拦截协议 112
ufw status verbose                # Ubuntu（实测 ufw active）
# 6. VIP 是否已被别的节点占着（网络里藏了个“老主”）
ip addr show | grep 192.168.1.100
```

```text
典型根因：
- 主备 priority 相同 → 竞选不稳定，备永远抢不到
- virtual_router_id 不一致 → 不在同一个虚拟路由器，互不感知
- auth_pass 不一致 → 通告被当非法包丢弃
- 防火墙拦了 VRRP（协议 112）→ 收不到通告
- interface 配错（如 VIP 绑 eth0 但心跳走 eth1）
- 备节点 keepalived 没起来/配置语法错误
```

### 案例二：脑裂（两台机器同时持 VIP，双 MASTER）

```shell
# 1. 确认脑裂：两台机器都执行，都显示 VIP = 脑裂
ip addr show | grep 192.168.1.100
# 2. 找心跳断点（网络分区/防火墙/网卡）
ping -c 3 <对端IP>
tcpdump -i eth0 vrrp -nn          # 对端通告是否到达本机
# 3. 查防火墙/安全组是否放行协议 112
ufw status verbose
# 4. 查网卡是否 up（本机教训：enp59s0 就是 DOWN 状态）
ip -br link | grep -E 'UP|DOWN'
# 5. 应急：立即手动降级一台，保单主
systemctl stop keepalived         # 停掉一台，VIP 自动回到另一台
```

```text
典型根因：
- 心跳链路断（交换机故障/网线/防火墙拦组播/网卡 down）
- 云环境组播被禁但没改单播（VPC 禁组播 → 心跳互相收不到 → 双主）
- 两台 virtual_router_id 不一致（各成一主）
根治：恢复心跳链路 + 防火墙放行 + 确认组 ID/认证一致 +
     云环境改 unicast_src_ip/unicast_peer + 配脑裂监控告警
```

### 案例三：切换成功了，但服务不可用（新主访问不通）

```shell
# 1. VIP 在谁身上（确认切换完成）
ip addr show | grep 192.168.1.100
# 2. 备节点服务真的起来了？（keepalived 只保证 VIP，不保证业务进程）
systemctl status nginx
ss -tlnp | grep ':80 '
# 3. 没配 track_script 的话，服务挂了根本不会切换——
#    此时主节点活着但 nginx 挂了，VIP 不动，谁都访问不了
grep -A3 'track_script' /etc/keepalived/keepalived.conf
# 4. 防火墙/安全组是否对新主放行 VIP 端口
ufw status verbose
# 5. ARP 学习问题：新主发免费 ARP 了吗（notify_master 里 arping）？
ip neigh show | grep 192.168.1.100
```

```text
典型根因：
- track_script 没配置 → 服务级故障不触发切换（机器活着白搭）
- 备节点服务没自启（systemctl enable nginx 没做）
- notify_master 里没发免费 ARP → 交换机/客户端 MAC 表还是旧主
- 两台防火墙规则不一致，备机接管后端口被自己拦了
根治：track_script 检测服务 + 服务 enable 自启 + notify 里 arping +
     防火墙规则两台统一 + 演练验证「切换后 curl 通过」
```

### 案例四：频繁主备切换（抖动）

```shell
# 1. 统计切换频率（一分钟多次 = 抖动）
journalctl -u keepalived | grep -c "Entering MASTER"
# 2. 网络质量（丢包/抖动是元凶）
ping -c 100 <对端IP> | grep -E 'loss|rtt'
# 3. 健康检查脚本是否误报（脚本自身卡顿/超时设置太短）
sh -x /etc/keepalived/chk_nginx.sh; echo $?   # 手动执行看返回值是否稳定
# 4. 看 priority 差距
grep priority /etc/keepalived/keepalived.conf
```

```text
典型根因：
- advert_int 太小（<1s）+ 心跳走弱网（WiFi/共享链路）
- 健康检查脚本偶发超时（无 timeout、脚本太重）→ 周期性降分切换
- 主备 priority 差太小（1~2）→ 轻微波动即翻转
根治：advert_int 1~2s + 脚本加 timeout/fall/rise + priority 差 ≥20
     + nopreempt 或 preempt_delay
```

## 常见问题

```text
Q1: 主备都配了 state MASTER 会怎样？
A: state 只是初始角色，实际主从由 priority 决定。两台都 MASTER 时，
   priority 高的持 VIP，正常不冲突——但 priority 必须不同且差距够大，
   否则选举不稳定甚至互相抢。正确姿势：按 priority 定主从，state 随意。

Q2: 主节点恢复后是否自动切回？
A: 默认抢占：主恢复（priority 高）后自动抢回 VIP。配置 nopreempt 则不抢，
   当前 MASTER 保持，直到它故障。有状态服务建议 nopreempt + 人工确认切回，
   防止「主刚恢复还没就绪就抢回」导致二次抖动。

Q3: 心跳走组播还是单播？
A: 默认组播（224.0.0.18），适合机房内网（交换机支持组播）。
   公有云 VPC 大多禁组播，必须改单播：unicast_src_ip + unicast_peer 指定对端。

Q4: Keepalived 能检查应用健康吗（不只是机器）？
A: 能。vrrp_script 自定义检查脚本（killall 进程 / ss 端口 / curl 页面），
   失败按 weight 给实例降分，跌破备节点后触发切换。这是「服务挂了也切」的关键。

Q5: weight 怎么设置比较合理？
A: 原则：主节点失败后分数要低于备节点。例：主 100 备 90，weight -20
   → 主失败后 80 < 90，备胜出。若 weight 只 -5（95 > 90），主服务挂了也不切换。
   备节点也配同一脚本：备失败后 90-20=70，更不可能抢主（防备带病上位）。

Q6: 一个网卡上可以跑多个 VIP 吗？
A: 可以。一个 vrrp_instance 可以带多个 virtual_ipaddress；也可以建多个
   vrrp_instance（不同 virtual_router_id）跑多个 VIP 组，用于「双 VIP 互备」。

Q7: 切换后客户端还是连不上，怎么办？
A: 按序排查：VIP 是否漂移（ip addr）→ 新主服务是否就绪（ss）→
   免费 ARP 是否发出（notify_master 里的 arping）→ 交换机 MAC 表是否刷新
   → 防火墙是否放行。多数「切了连不上」是 ARP/防火墙问题，不是 keepalived 问题。

Q8: keepalived 日志在哪里看？
A: journalctl -u keepalived -f（systemd 统一日志）；Debian/Ubuntu 也有
   /var/log/syslog（grep keepalived）。切换事件关键词：Entering MASTER /
   Entering BACKUP / Killing all the VRRP / VRRP_Instance(VI_1) ...
```

## 面试题

```text
1. VRRP 协议如何选举 MASTER？
   答：同一虚拟路由器（VRID）内按 priority 比较，最高者成为 MASTER 持有
   VIP；收到更高 priority 通告则保持 BACKUP，相等时比源 IP 大小（大者胜）。
   MASTER 失联（3×advert_int + skew_time 无通告）后剩余 BACKUP 重新竞选。

2. Keepalived 怎么判断主节点挂了？
   答：BACKUP 监听 MASTER 的 VRRP 通告（advert_int，默认 1s），
   连续 3×advert_int + skew_time 没收到通告即判定 MASTER 故障，
   进入竞选流程接管 VIP。另有 vrrp_script 服务级检查：服务挂了降分触发切换。

3. 脑裂怎么发生？Keepalived 如何避免？
   答：网络分区/组播不通/防火墙拦截导致主备互收不到心跳，双双转 MASTER
   都持 VIP。避免：① authentication 认证防伪造；② 组播/单播配置正确、
   防火墙放行协议 112；③ 云环境改 unicast 单播；④ 监控检测双主立即告警；
   ⑤ 必要时结合 fencing（如共享存储的锁/仲裁）杜绝双写。

4. 为什么用 VIP 而不是切换 DNS 记录？
   答：VIP 漂移是秒级（3~5s）且对客户端透明——VIP 不变、免费 ARP 更新
   MAC，客户端连接无感知；DNS 切换受 TTL 缓存影响（分钟~小时级），
   客户端缓存旧 IP 期间全部失败。VIP 方案 RTO 远小于 DNS 方案。

5. keepalived 的 nopreempt 和 preempt_delay 有什么区别？
   答：nopreempt：MASTER 恢复后不抢回 VIP（当前主一直持有直到故障）；
   preempt_delay：仍抢占，但恢复后延迟 N 秒（如 30s）再抢，
   给恢复节点留出业务就绪时间。有状态服务用 nopreempt 或较大 delay 防抖动。

6. 云环境（VPC）部署 keepalived 要注意什么？
   答：① VPC 禁组播 → 用 unicast_src_ip/unicast_peer 单播；② 安全组放行
   协议 112（VRRP）；③ 部分云厂商安全组不支持协议放行，可考虑云 LB
   （SLB/ALB）替代自建 HA；④ 云主机 HA 注意「热迁移」——迁移期间网卡
   抖动可能触发误切换，调大 advert_int/fall 计数。

7. track_script 的 weight 设错会怎样？举例说明。
   答：weight 过小会导致「服务挂了但不切换」。例：主 100 备 90，
   weight -5：主服务挂 → 100-5=95，仍 > 90，备不接管，业务中断。
   正确配置：weight ≤ -(主优先级 - 备优先级 - 1)，如 -20（100-20=80 < 90）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 主备 priority 设不同且差距 ≥20（主 100、备 90），靠 priority 决定主从
2. 必配 vrrp_script 健康检查（track_script），服务挂了也能切换，不只机器挂
3. 心跳加 authentication 认证（PASS + 一致密码），防 VRRP 伪造劫持
4. virtual_router_id / advert_int / auth_pass / VIP 主备必须完全一致
5. 上线前做三种演练：停 keepalived、杀服务进程、断网线，记录切换耗时
6. 切换动作走 notify_master 脚本：发免费 ARP（arping）+ 通知监控
7. 云环境（VPC 禁组播）用 unicast_src_ip/unicast_peer 单播心跳
8. 有状态服务配 nopreempt 或 preempt_delay，防主恢复后二次抖动
9. 健康检查脚本轻量 + timeout + fall/rise 计数，脚本本身纳入测试
10. 监控双主（脑裂）与切换事件，切换要可追溯、可复盘（journalctl）

### 踩坑记录

```text
坑 1：云环境组播被禁，心跳不通
结论：云主机上 keepalived 心跳不通，主备互相收不到通告，频繁误切换甚至双主。
原因：VRRP 默认组播（224.0.0.18），云 VPC 大多禁组播。
解法：配 unicast_src_ip / unicast_peer 改用单播心跳；
     安全组放行协议 112。

坑 2：忘了配认证，被伪造心跳攻击
结论：有人发伪造 VRRP 通告（高 priority），把真主挤下线，业务中断。
原因：没配 authentication，任何机器都能参与选举（VRRP 劫持）。
解法：配置 auth_type PASS + auth_pass，主备一致；配置文件 chmod 600。

坑 3：state 和 priority 理解反了
结论：以为把备机的 state 改成 MASTER 就能当主，改了之后主从没变。
原因：state 只是初始角色，实际主从由 priority 决定。
解法：改 priority 才真正改变主从；state 只作初始标记，两台可都写 BACKUP。

坑 4：主备的 virtual_router_id 不一致
结论：主备心跳不通，各自都成为 MASTER，双主持 VIP（脑裂）。
原因：virtual_router_id 是组标识，不一致就不在同一个虚拟路由器。
解法：确认主备的 virtual_router_id 相同；不同组才用不同 ID。

坑 5：主恢复后抢占导致二次抖动
结论：主节点恢复抢回 VIP，但业务还没完全就绪，又切回备，来回抖。
原因：默认抢占，主一恢复立刻抢回，未等业务就绪。
解法：配 nopreempt 不抢占，或 preempt_delay 30 留出就绪时间；
     有状态服务人工确认后再切回。

坑 6：weight 设太小，服务挂了不切换
结论：nginx 挂了，VIP 不漂移，业务长时间中断。
原因：weight -5，主 100→95 仍大于备 90，备节点不会接管。
解法：weight ≤ -(主-备-1)，如 -20；并验证「杀进程 → 切换」演练通过。

坑 7：防火墙拦了 VRRP 通告，备机永远收不到心跳
结论：备节点一直处于 BACKUP 且无日志报错，主真挂了也不切换。
原因：ufw/firewalld/安全组拦截了协议 112（VRRP），通告到不了备机。
解法：ufw allow proto 112（Ubuntu）/ firewall-cmd --add-service=vrrp（RHEL）；
     tcpdump -i eth0 vrrp 验证通告可达。

坑 8：notify_master 里没发免费 ARP，切换后流量仍打旧主
结论：VIP 已漂移到新主，但客户端/交换机还是把流量发往旧主 MAC，访问失败。
原因：切换只绑了 VIP，没宣告 ARP 刷新，交换机 MAC 表保持旧条目。
解法：notify_master 里执行 arping（如 arping -c 3 -I eth0 -s <VIP> <VIP>）；
     或确认网络设备对 gratuitous ARP 不抑制。
```
