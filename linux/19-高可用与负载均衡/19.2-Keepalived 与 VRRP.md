## 概述

Keepalived 是 Linux 实现高可用的经典工具，基于 VRRP 协议（虚拟路由冗余协议）实现「主备切换 + VIP 漂移」。核心能力：多台机器组成一个「VRRP 组」，组内选举一个主节点持有虚拟 IP（VIP），主节点挂了 VIP 自动漂移到备节点，客户端访问 VIP 无感知切换。Keepalived 还内置健康检查（主节点服务挂了也能触发切换），常配合 Nginx/HAProxy/LVS 做高可用负载均衡。

```text
Keepalived 解决什么：
多台机器共享一个「虚拟 IP（VIP）」，主节点持 VIP 对外服务，
主挂了 VIP 漂移到备，客户端无感知。避免负载均衡器/网关成为单点故障。
```

## 核心概念

1. **VIP（虚拟 IP）**：对外暴露的地址，不绑定具体机器，故障时漂移。客户端始终访问 VIP。
2. **MASTER / BACKUP**：主备角色。主节点持 VIP，备节点待命，主挂了备接管。
3. **priority 优先级**：决定谁当主，优先级高的抢到 VIP（通常主 100、备 90）。
4. **advert_int 心跳间隔**：主节点定期广播 VRRP 通告，备节点 N 次没收到就认为主挂了，触发切换。
5. **nopreempt 非抢占**：主恢复后是否抢回 VIP（默认抢占，配 nopreempt 不抢）。

```text
Keepalived 核心要素：
VIP（漂移地址）+ MASTER/BACKUP（角色）+ priority（优先级）+ advert_int（心跳）
```

## 工作原理

VRRP 协议的工作原理：

1. **选举主节点**：组内按 priority 选举，优先级最高的成为 MASTER，持有 VIP。多台机器组成一个 VRRP 组（virtual_router_id 相同）。
2. **心跳通告**：MASTER 定期（advert_int，默认 1 秒）发送 VRRP 通告报文（组播），宣告「我还活着，我是主」。
3. **故障检测**：BACKUP 节点监听通告，连续 3 次（3×advert_int）没收到通告 = 判定 MASTER 挂了。
4. **VIP 漂移**：BACKUP 判定主挂后，自己提升为 MASTER，接管 VIP（通过 ARP 广播宣告 VIP 的新 MAC 地址），完成切换。
5. **健康检查**：Keepalived 还能检查「VIP 之外的服务」（如 Nginx 是否正常），服务挂了即使机器没挂也触发切换。

```text
VRRP 工作流程：
priority 选举主 → 主广播心跳 → 备监听心跳 → 主挂(3次超时) → 备接管 VIP → ARP 宣告
```

## 常用命令与配置

```shell
# 安装（本机未装，示例）
apt install keepalived        # Debian/Ubuntu
dnf install keepalived        # CentOS/RHEL

# 启动与管理
systemctl enable --now keepalived
systemctl status keepalived
systemctl restart keepalived

# 查看 VIP 在哪个节点
ip addr show | grep <VIP>

# 查看切换日志
journalctl -u keepalived -f
tail -f /var/log/syslog | grep -i keepalived
```

```text
配置位置：/etc/keepalived/keepalived.conf
主备两台机器配置几乎相同，只有 priority（和 state）不同
```

## 配置文件解析

完整解析 Keepalived 配置（主节点示例，备节点改 priority）：

```ini
# /etc/keepalived/keepalived.conf
global_defs {
    router_id LVS_1          # 节点标识（唯一）
}

vrrp_instance VI_1 {
    state MASTER             # 初始角色 MASTER/BACKUP
    interface eth0           # VIP 绑定的网卡
    virtual_router_id 51     # VRRP 组 ID（同一组的主备必须一致）
    priority 100             # 优先级（高者为主，备设 90）
    advert_int 1             # 心跳间隔（秒）

    authentication {         # 心跳认证
        auth_type PASS       # PASS / AH
        auth_pass 1111       # 密码（主备一致）
    }

    virtual_ipaddress {
        192.168.1.100/24     # 虚拟 IP（VIP）
    }
}

# 健康检查：nginx 挂了也切换
vrrp_script chk_nginx {
    script "killall -0 nginx"   # 检查 nginx 进程
    interval 2                  # 每 2 秒检查
    weight -20                  # 失败降 20 优先级（低于备则切换）
}
vrrp_instance VI_1 {
    track_script {
        chk_nginx              # 关联健康检查
    }
}
```

```text
关键字段：
virtual_router_id  组 ID，主备必须相同（不同组用不同 ID）
priority          优先级，高的抢主（主 100 备 90）
advert_int        心跳间隔，主备一致
virtual_ipaddress VIP，对外服务地址
vrrp_script       健康检查脚本，服务挂了降优先级触发切换
```

## 应用场景实战

### 场景一：Nginx 高可用（双机主备）

```text
架构：
192.168.1.10 主 nginx（priority 100）── VIP 192.168.1.100
192.168.1.11 备 nginx（priority 90） ── 主挂后接管 VIP

配置步骤：
1. 两台机器都装 nginx + keepalived
2. 主节点 keepalived.conf 设 state MASTER + priority 100
3. 备节点设 state BACKUP + priority 90
4. 启动后，主持 VIP；客户端访问 VIP
5. 停主节点 → 备节点 3 秒内接管 VIP → 客户端无感知
```

### 场景二：LVS + Keepalived（负载均衡器高可用）

```text
架构：两个 LVS 负载均衡器 + Keepalived 做 VIP 漂移
LVS1（主）── VIP 192.168.1.100 ──→ 后端多台 Web
LVS2（备）── 主挂后接管 VIP
Keepalived 保证 LVS 本身不挂，LVS 分担后端流量
```

## 性能与调优

```text
1. 切换速度 —— 检测时间 = advert_int × 3，默认 1s×3=3 秒切换；要更快调小 advert_int
2. 抖动预防 —— 网络抖动导致频繁切换，调大 advert_int 或配 nopreempt
3. 健康检查开销 —— vrrp_script 别太频繁（interval 2s 合适），太重影响主节点
4. 多 VIP —— 一个实例一个 VIP，多个 VIP 配多个 vrrp_instance
```

## 安全与权限

```text
1. 心跳认证 —— authentication 配置 auth_pass，防止伪造心跳攻击（把主挤下线）
2. 心跳网络隔离 —— VRRP 走组播，确保防火墙放行（或改单播 unicast）
3. VIP 的 ARP —— 切换靠 ARP 广播，确保交换机不抑制免费 ARP
4. 权限 —— keepalived 以 root 运行（要配 VIP），配置目录权限 600
```

## 故障排查

### VIP 没漂移

```shell
# 1. 确认主节点真的挂了（还是网络分区）
ping <主节点IP>
# 2. 看备节点 keepalived 日志
journalctl -u keepalived -n 50
# 3. 检查优先级和状态
cat /etc/keepalived/keepalived.conf | grep -E 'state|priority'
# 4. 检查 VRRP 通告（组播是否被防火墙挡）
tcpdump -i eth0 vrrp
```

### 脑裂（双主都持 VIP）

```shell
# 两台机器都执行，看是否都有 VIP
ip addr show | grep <VIP>
# 都有 = 脑裂，检查心跳网络 + 防火墙组播
```

## 常见问题

```text
Q1: 主备都配了 state MASTER 会怎样？
A: state 只是初始角色，实际由 priority 决定。都 MASTER 时 priority 高的持 VIP，不冲突（但要保证 priority 不同）。

Q2: 主节点恢复后是否自动切回？
A: 默认抢占（主恢复抢回 VIP），配 nopreempt 则主恢复后不抢（避免二次抖动）。

Q3: 心跳走组播还是单播？
A: 默认组播（224.0.0.18），云环境（VPC）常禁组播，要改 unicast 单播。

Q4: Keepalived 能检查应用健康吗？
A: 能，用 vrrp_script 自定义检查脚本（如 curl 检查服务），挂了降优先级触发切换。
```

## 面试题

```text
1. VRRP 协议怎么选举主节点？
   答：按 priority 选举，优先级最高的成为 MASTER 持有 VIP；主挂后备节点优先级最高者接管。

2. Keepalived 怎么判断主节点挂了？
   答：BACKUP 监听 MASTER 的心跳通告（advert_int），连续 3 次没收到判定主挂，触发切换。

3. 脑裂怎么发生的？Keepalived 怎么避免？
   答：网络分区时主备都认为对方挂了、都抢 VIP。避免：心跳认证（防伪造）+ 组播/单播配置正确 + 必要时 fence。

4. 为什么用 VIP 而不是直接切 DNS？
   答：VIP 漂移是秒级无感知切换，DNS 切换有缓存延迟（TTL），客户端感知明显。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 主备 priority 设不同（主 100、备 90），靠 priority 决定主从
2. 配 vrrp_script 健康检查，服务挂了也能切换（不只机器挂）
3. 心跳加 authentication 认证，防止伪造心跳
4. 上线前测试切换（停主节点验证 VIP 漂移）
5. 云环境（VPC 禁组播）用 unicast 单播心跳

### 踩坑记录

```text
坑 1：云环境组播被禁，心跳不通
结论：云主机上 Keepalived 心跳不通，频繁误切换。
原因：VRRP 默认组播（224.0.0.18），云 VPC 常禁组播。
解法：配 unicast_src_ip / unicast_peer 改用单播心跳。

坑 2：忘了配认证，被伪造心跳攻击
结论：有人发伪造 VRRP 包，把主节点挤下线。
原因：没配 authentication，任何包都能参与选举。
解法：配置 auth_type PASS + auth_pass，主备一致。

坑 3：state 和 priority 理解反了
结论：以为 state 决定主从，改了 state 没改 priority，主从不变。
原因：state 只是初始角色，实际主从由 priority 决定。
解法：改 priority 才真正改变主从，state 只是初始标记。

坑 4：主备的 virtual_router_id 不一致
结论：主备心跳不通，各自都成主，双主持 VIP。
原因：virtual_router_id 是组标识，不一致就不在同一组。
解法：确认主备的 virtual_router_id 相同（不同组才用不同 ID）。

坑 5：主恢复后抢占导致二次抖动
结论：主节点恢复抢回 VIP，但主还没完全就绪，又切回备，反复抖。
原因：默认抢占，主一恢复就抢回，可能没就绪。
解法：配 nopreempt 不抢占，或主就绪后再手动切回。
```
