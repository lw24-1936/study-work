## 概述

LVS（Linux Virtual Server，Linux 虚拟服务器）是章文嵩博士于 1998 年发起的内核级负载均衡项目，现已是 Linux 内核自带模块 `ip_vs`（IP Virtual Server）。它工作在**四层（传输层）**：只根据 IP 地址和端口做转发决策，不解析 HTTP 内容，因此吞吐极高，单机可支撑百万级并发连接，是生产环境最常见的「入口四层负载均衡」方案。

LVS 的核心定位是**流量分发**：客户端访问虚拟 IP（VIP），LVS 调度器（Director）按调度算法把请求转发给后端真实服务器（RS），并管理连接跟踪。七层的精细路由（按 URL/域名/Header）、缓存、改写交给 Nginx/HAProxy（见 [[19.4-HAProxy 与 Nginx]]），两者叠加构成经典的「四层 LVS + 七层 Nginx」分层架构：

```text
LVS 定位：
内核态四层负载均衡（ip_vs 模块），只转发、不看内容，性能极高
负责「把流量分发到后端多台服务器」
七层逻辑（HTTP 路由/缓存/改写）交给 Nginx/HAProxy
```

LVS 三种转发模式：NAT（网络地址转换）、DR（直接路由，最常用）、TUN（IP 隧道）。配合 Keepalived（见 [[19.2-Keepalived 与 VRRP]]）可实现 Director 高可用，是互联网公司入口层的经典组合。

## 核心概念

1. **VS（Virtual Server）**：虚拟服务，对外暴露的「VIP + 端口」（如 `192.168.1.100:80`），客户端只访问它，不知道后端的真实地址。
2. **VIP（Virtual IP）**：虚拟 IP，Director 上对外服务的 IP，通常由 Keepalived 管理并可漂移。
3. **DIP（Director IP）**：Director 与 RS 通信使用的真实 IP。
4. **RIP（Real Server IP）**：RS 的真实 IP。
5. **RS（Real Server）**：真实服务器，后端实际处理请求的机器（Web、DB、Redis 等）。
6. **Director**：调度器，运行 LVS 的机器，负责把流量按算法转发到 RS。
7. **调度算法**：决定「下一个请求分给哪个 RS」的策略，LVS 共支持 10 种（rr/wrr/lc/wlc/lblc/lblcr/dh/sh/sed/nq）。
8. **连接跟踪表（ip_vs_conn）**：内核为每个被转发的连接维护一条记录（五元组 + 转发模式），是 LVS 会话能力的基础。
9. **持久连接（persistence）**：`-p` 参数，同一源 IP 在一段时间内固定转发到同一 RS，用于会话保持。

```text
核心术语：
CIP（客户端 IP）→ VIP（虚拟 IP）→ Director 调度器 → DIP/RIP（真实服务器）
VS 虚拟服务（VIP:端口） 由 Director 上的 ip_vs 内核模块实现
```

## 工作原理

LVS 的工作核心是**数据包在内核态被改写/封装后转发**，整个过程不经过用户态，因此比任何用户态代理都快。三种模式的本质区别在于「数据包如何到达 RS、RS 如何回包」：

### 1. NAT 模式（Network Address Translation）

Director 同时改写数据包的**源 IP 和目标 IP**：请求进来时把目标 IP 从 VIP 改成 RS 的 RIP（DNAT），并记录连接；RS 回包时必须回到 Director，Director 再把源 IP 改回 VIP（SNAT）后转发给客户端。

- 所有流量（进 + 出）都经过 Director，Director 是瓶颈（CPU/带宽）。
- 优点：RS 无需任何特殊配置（不需要绑 VIP、不需要改 ARP），RS 可以是任何操作系统；支持端口映射（VIP:80 → RIP:8080）。
- 缺点：回程流量也走 Director，吞吐上限低，不适合大流量。

### 2. DR 模式（Direct Routing，最常用）

Director **只改目标 MAC 地址**（把包的二层目的 MAC 改成 RS 网卡的 MAC），不改 IP。包到达 RS 后，RS 发现目标 IP 是自己的 VIP（需在 lo 上绑定 VIP），正常处理；**回包直接以 VIP 为源地址发给客户端，不经 Director**。

- 请求经 Director，响应直连客户端，Director 压力极小，吞吐最高。
- 要求：RS 与 Director 必须在**同一物理网段**（二层可达）；RS 要在 lo 上绑 VIP（/32）；RS 必须抑制对 VIP 的 ARP 响应（否则 RS 会抢答 VIP 的 ARP，导致流量混乱）。
- 不支持端口映射（RS 的端口必须与 VIP 端口一致）。

```text
DR 模式 ARP 问题详解：
为什么 RS 要绑 VIP？        —— RS 收到目标 IP = VIP 的包后，本地路由/接口上要有这个
                             IP 才能收下；回包源地址也用 VIP（客户端才认）。
为什么必须抑制 ARP？        —— 若不抑制，客户端广播「谁是 192.168.1.100」时，
                             Director 和所有 RS 都会应答，客户端 ARP 缓存随机指向
                             某台 RS，VIP 流量直接打穿到单台 RS，负载均衡失效。
两个内核参数（在 RS 上设）：
  arp_ignore=1   只应答「目标 IP 是本接口地址」的 ARP 请求
                 （RS 的 lo:0 有 VIP，但物理网卡没有 VIP，故不响应）
  arp_announce=2 总是用「最优本地地址」做 ARP 应答源地址，
                 避免 RS 用自己的物理 IP 应答 VIP 的 ARP
```

### 3. TUN 模式（IP Tunneling）

Director 把原始 IP 包**整体封装进一个新的 IP 包**（IP-in-IP 隧道）发给 RS；RS 解封装后处理请求，回包直接以 VIP 为源发给客户端（同 DR）。

- 适合 RS 跨网段/跨机房（隧道可穿透三层网络）。
- 缺点：每个包多一层 IP 头（约 20 字节开销），MTU 需注意（建议 1450 或以下），RS 需支持隧道接口（tunl0）并绑 VIP。

### 三种模式完整对比表

| 维度 | NAT | DR（最常用） | TUN |
|------|-----|--------------|-----|
| 流量路径 | 进出都经 Director | 进经 Director，出直连 RS | 进经 Director（隧道封装），出直连 RS |
| 回程处理 | Director 做 SNAT 改回 VIP | RS 直接以 VIP 回包 | RS 直接以 VIP 回包 |
| 包改写 | 源/目标 IP 都改 | 只改目标 MAC | 新 IP 头封装（IP-in-IP） |
| 性能 | 低（Director 是瓶颈） | 最高 | 中（封装开销） |
| 部署要求 | RS 无特殊要求 | 同网段 + lo 绑 VIP + 抑制 ARP | 跨网段 + tunl0 隧道 + 绑 VIP |
| 端口映射 | 支持（VIP:80→RIP:8080） | 不支持（端口必须一致） | 不支持 |
| 适用场景 | 小规模、RS 异构 | 同机房 HTTP/HTTPS 集群 | 跨机房、异地容灾 |

### 调度算法详解（10 种）

| 算法 | 全称 | 策略 | 适用场景 |
|------|------|------|----------|
| rr | Round Robin | 轮流分发，无状态 | 请求时长均匀的短连接 |
| wrr | Weighted RR | 按权重比例轮流 | 后端性能不均（weight 1~100） |
| lc | Least Connections | 发给连接数最少的 RS（active×256+inactive 比较） | 长连接/时长不均 |
| wlc | Weighted LC | 最少连接 + 权重，**LVS 默认算法** | 通用首选 |
| lblc | Locality-Based LC | 按目标 IP 就近分给最近用过的 RS | 缓存类服务（目标 IP 有局部性） |
| lblcr | LBL with Replication | lblc + 复制（目标 IP 可复制到多台 RS） | 缓存类服务高可用 |
| dh | Destination Hashing | 按目标 IP 哈希，固定目标→固定 RS | 防火墙标记多端口场景 |
| sh | Source Hashing | 按源 IP 哈希，同源→同 RS | **会话保持**（无 Cookie 场景） |
| sed | Shortest Expected Delay | (active+1)×256/weight 最小者 | 权重差异大时更平滑 |
| nq | Never Queue | sed 基础上空闲 RS 优先 | 与 sed 类似，响应更快 |

```text
选型速记：
连接时长均匀 → rr/wrr；时长不均 → wlc；要会话保持 → sh 或 -p 持久连接；
后端异构 → wrr/sed/nq；缓存类 → lblc/lblcr
```

## 常用命令与配置

```shell
# ---------- 安装 ----------
apt install ipvsadm          # Debian/Ubuntu
dnf install ipvsadm          # CentOS/RHEL（内核 ip_vs 模块已内置）
# 内核模块（一般随 ipvsadm 安装自动加载，也可手动）：
modprobe ip_vs
modprobe ip_vs_rr ip_vs_wrr ip_vs_lc ip_vs_wlc ip_vs_sh   # 各算法模块

# ---------- 管理虚拟服务 VS ----------
ipvsadm -A -t 192.168.1.100:80 -s wrr      # 添加 TCP 虚拟服务，wrr 算法
ipvsadm -E -t 192.168.1.100:80 -s wlc      # 修改算法
ipvsadm -D -t 192.168.1.100:80             # 删除 VS
ipvsadm -A -u 192.168.1.100:53 -s rr       # UDP 服务（DNS 等）

# ---------- 管理真实服务器 RS ----------
ipvsadm -a -t 192.168.1.100:80 -r 192.168.1.11 -g -w 1    # -g = DR 模式
ipvsadm -a -t 192.168.1.100:80 -r 192.168.1.12 -g -w 2    # -w 权重
ipvsadm -e -t 192.168.1.100:80 -r 192.168.1.12 -g -w 3    # 修改权重
ipvsadm -d -t 192.168.1.100:80 -r 192.168.1.11            # 摘除 RS
ipvsadm -a -t 192.168.1.100:80 -r 192.168.1.11 -m         # -m = NAT 模式
ipvsadm -a -t 192.168.1.100:80 -r 10.0.0.11 -i            # -i = TUN 模式

# ---------- 会话保持（持久连接） ----------
ipvsadm -A -t 192.168.1.100:80 -s rr -p 3600   # 同源 IP 3600 秒内固定到同一 RS

# ---------- 查看 ----------
ipvsadm -L -n                 # 列出规则（-n 不反解域名）
ipvsadm -L -n --stats         # 统计：连接数/进出包/进出字节
ipvsadm -L -n --rate          # 速率统计：每秒连接/包/字节
ipvsadm -L -n -c              # 当前连接跟踪表（每行一条活动连接）
ipvsadm -L -n -t 192.168.1.100:80   # 只看某个 VS
ipvsadm -Z                    # 清零统计计数

# ---------- 保存 / 恢复 ----------
ipvsadm-save > /etc/ipvsadm.rules        # 导出为规则文件（iptables 风格）
ipvsadm-restore < /etc/ipvsadm.rules     # 导入
# Ubuntu 开机自动恢复：systemctl enable ipvsadm（依赖 /etc/ipvsadm.rules）
# RHEL 系：保存到 /etc/sysconfig/ipvsadm，systemctl enable ipvsadm
```

```text
ipvsadm 选项速查：
-A/-E/-D   添加/修改/删除 VS       -a/-e/-d   添加/修改/删除 RS
-t/-u/-f   TCP/UDP/防火墙标记服务   -s         调度算法（10 种）
-r         RS 地址[:端口]          -g/-i/-m   DR/TUN/NAT 三种模式
-w         RS 权重（0~65535）     -p         持久连接超时（秒）
-S         导出规则（同 ipvsadm-save） -R    导入规则（同 ipvsadm-restore）
```

## 配置文件解析

LVS 本身**没有独立守护进程和配置文件**（规则直接进内核），但有三类「配置文件/脚本」配套使用：

### 1. 规则文件 /etc/ipvsadm.rules（ipvsadm-save 导出格式）

```text
# 由 ipvsadm-save 生成的规则文件，与 iptables-save 同风格
-A -t 192.168.1.100:80 -s wrr -p 3600
-a -t 192.168.1.100:80 -r 192.168.1.11:80 -g -w 1
-a -t 192.168.1.100:80 -r 192.168.1.12:80 -g -w 1
```

- 首行注释 `-A` 开头为 VS 行，`-a` 开头为 RS 行，与命令行参数一一对应。
- 恢复：`ipvsadm-restore < /etc/ipvsadm.rules`。
- Ubuntu 下 `/etc/default/ipvsadm` 配置 `SAVE_ON_STOP=yes` 可自动保存。

### 2. RS 端配置脚本（DR 模式关键，可在 RS 上做成 systemd 或 rc.local）

```bash
#!/bin/bash
# /usr/local/bin/lvs-rs-dr.sh —— DR 模式 RS 端初始化
VIP=192.168.1.100

# 1. lo 绑定 VIP（/32，掩码必须是 32，避免 RS 用 VIP 去响应同网段广播）
ip addr add ${VIP}/32 dev lo

# 2. 抑制 ARP：只答本接口地址的 ARP、用最优地址应答
sysctl -w net.ipv4.conf.all.arp_ignore=1
sysctl -w net.ipv4.conf.all.arp_announce=2
sysctl -w net.ipv4.conf.lo.arp_ignore=1
sysctl -w net.ipv4.conf.lo.arp_announce=2

# 3. 可选：确保默认路由仍走物理网卡（回包直连客户端的前提）
ip route | grep default
```

持久化到 /etc/sysctl.conf（重启不丢）：

```text
net.ipv4.conf.all.arp_ignore = 1
net.ipv4.conf.all.arp_announce = 2
net.ipv4.conf.lo.arp_ignore = 1
net.ipv4.conf.lo.arp_announce = 2
```

```text
内核参数取值解析（arp_ignore / arp_announce）：
arp_ignore：
  0 —— 默认：只要本机任意接口有目标 IP 就应答（RS 绑了 lo VIP 会抢答，错误）
  1 —— 只应答「目标 IP 属于收到请求的接口」的 ARP（RS 物理网卡无 VIP → 不应答，正确）
arp_announce：
  0 —— 默认：用任意本地地址应答
  1 —— 尽量选择目标子网内的地址
  2 —— 总是用「请求接口上」的最优地址应答（与 VIP 无关的最优地址，正确）
```

### 3. Keepalived 的 LVS 配置段（Director 高可用 + 健康检查）

```text
# /etc/keepalived/keepalived.conf —— LVS 相关段（VRRP 段见 [[19.2-Keepalived 与 VRRP]]）
virtual_server 192.168.1.100 80 {
    delay_loop 6              # 健康检查周期 6 秒
    lb_algo wrr               # 调度算法（对应 ipvsadm -s wrr）
    lb_kind DR                # 转发模式（对应 -g，NAT 写 NAT、TUN 写 TUN）
    persistence_timeout 50    # 持久连接 50 秒（对应 -p 50）
    protocol TCP              # 协议（TCP/UDP）

    real_server 192.168.1.11 80 {
        weight 1
        HTTP_GET {            # 应用层健康检查（比 TCP_CHECK 更准确）
            url {
                path /health  # 检查 /health 返回 2xx/3xx
                status_code 200
            }
            connect_timeout 3
            nb_get_retry 3
            delay_before_retry 3
        }
    }
    real_server 192.168.1.12 80 {
        weight 2
        TCP_CHECK {           # 简单 TCP 端口检查
            connect_timeout 3
            nb_get_retry 3
            delay_before_retry 3
        }
    }
}
```

Keepalived 会根据检查结果自动执行 `ipvsadm -a/-d` 把故障 RS 摘除、恢复后加回，无需人工干预。

## 应用场景实战

### 场景一：DR 模式 Web 集群负载均衡（最常用）

```text
架构：
客户端 → VIP 192.168.1.100:80（Director，运行 LVS + 两块网卡/同网段）
        → RS1 192.168.1.11（Web1，lo:0 绑 VIP + ARP 抑制）
        → RS2 192.168.1.12（Web2，lo:0 绑 VIP + ARP 抑制）

实施步骤：
1. Director：
   ipvsadm -A -t 192.168.1.100:80 -s wrr
   ipvsadm -a -t 192.168.1.100:80 -r 192.168.1.11 -g -w 1
   ipvsadm -a -t 192.168.1.100:80 -r 192.168.1.12 -g -w 1
   ipvsadm-save > /etc/ipvsadm.rules
2. RS1/RS2：lo 绑 VIP + arp_ignore=1/arp_announce=2（见「配置文件解析」脚本）
3. 验证：
   ipvsadm -L -n --stats        # 看 InActConn/ActiveConn 与字节数增长
   ipvsadm -L -n -c             # 看连接跟踪表
   客户端 curl http://192.168.1.100/ 多次，两台 RS 轮流出流量
```

关键点：DR 模式**回包直连客户端**，Director 只处理入向流量，吞吐远高于 NAT。

### 场景二：LVS + Keepalived 双 Director 高可用

```text
架构：
                VIP 192.168.1.100（由 Keepalived 管理，漂移）
   Director1（主，Keepalived MASTER）  Director2（备，Keepalived BACKUP）
                ↓            ↓
        RS1 192.168.1.11    RS2 192.168.1.12   RS3 192.168.1.13

要点：
1. 两台 Director 各装 keepalived + ipvsadm，配置完全相同的 virtual_server 段
2. 主挂掉后 VRRP 心跳超时（如 3 秒），VIP 漂移到备机，
   备机接管 LVS 规则（keepalived 启动时自动恢复 ipvsadm 规则）
3. RS 的 lo:0 上也要绑 VIP，但 ARP 抑制保证只有持有 VIP 的 Director 响应 ARP
4. real_server 健康检查自动剔除故障 RS，切换过程对客户端透明
```

### 场景三：四层 LVS + 七层 Nginx 分层架构（互联网经典架构）

```text
客户端 → VIP（LVS 四层，分发 TCP 流）
        → Nginx 集群（七层，按 URL/域名路由、静态缓存、限流、TLS 终结）
              → 应用服务器集群（Java/PHP/Python）
              → 数据库 / Redis / 对象存储

为什么分层：
  LVS    —— 扛入口大流量（内核态百万级并发），对客户端透明
  Nginx  —— 做七层精细路由（/api 走 A 集群、/static 走 CDN）、
            健康检查、缓存、限流，把请求转给具体应用
  好处   —— 单层故障不影响全局；LVS 层可以水平扩展（多 VIP + DNS/ECMP 轮询）
```

### 场景四：NAT 模式转发 MySQL（端口映射 + RS 零配置）

```text
需求：对外暴露 192.168.1.100:3306，后端两台 MySQL 分别在 10.0.0.11:3306、
      10.0.0.12:3306，且希望 VIP:3306 → RIP:3307（端口映射）。

Director：
  ipvsadm -A -t 192.168.1.100:3306 -s wlc -p 600
  ipvsadm -a -t 192.168.1.100:3306 -r 10.0.0.11:3307 -m
  ipvsadm -a -t 192.168.1.100:3306 -r 10.0.0.12:3307 -m
  echo 1 > /proc/sys/net/ipv4/ip_forward

注意：
- NAT 模式 RS 不需要绑 VIP、不需要改 ARP —— 这正是异构/跨网段后端的优势
- -p 600 让同一数据库会话固定到同一台 MySQL（避免主从复制延迟导致的读不一致）
- 数据库读写分离时，写流量建议用 Keepalived 只挂主库
```

## 性能与调优

```text
1. 模式选择是第一性能决策
   同网段 → DR（回包直连，Director 只处理入向流量，吞吐最高）
   跨网段 → TUN（有封装开销，MTU 调小到 1450 左右）
   小规模/异构 RS → NAT（简单，但 Director 进出都扛，是瓶颈）

2. 调度算法匹配业务特征
   短连接、时长均匀 → rr/wrr；长连接、时长不均 → wlc；
   需要会话保持 → sh 或 -p 持久连接（-p 会降低均衡性，超时别设太长）

3. 连接超时调优（默认 tcp 900s / tcpfin 120s / udp 300s）
   ipvsadm --set 300 30 120        # tcp / tcpfin / udp 超时（秒）
   # 短连接业务把 tcp 超时调小，避免连接跟踪表被 TIME_WAIT 类连接塞满

4. 连接跟踪表容量
   ipvsadm -L -n -c | wc -l        # 看当前连接数
   # 表大小由内核参数决定，海量短连接场景关注 ip_vs_conn 复用与超时

5. Director 内核侧调优
   - 网卡多队列（ethtool -L eth0 combined 8）+ RPS/RFS 分摊软中断
   - 关闭没用的 offload 或按需开启 GRO/LRO（看网卡型号）
   - /proc/sys/net/ipv4/vs/ 下：timeout、amemthresh、drop_entry 等
     （连接表满时 drop_entry=1 可丢新连接保老连接，慎用）

6. 横向扩展消除单 Director 瓶颈
   单 Director 再快也有上限，入口量级再大时：
   - 多 VIP + DNS 轮询（客户端按域名解析到不同 Director）
   - ECMP（等价多路径）：多台 Director + 交换机 ECMP 把流量散到多台
   - 每台 Director 的 LVS 规则保持一致（配置管理工具下发）

7. SYNPROXY（防 SYN Flood，内核 3.12+）
   配合 nftables/iptables 在 LVS 前做 SYN 代理，减缓 SYN Flood 冲击
```

## 安全与权限

```text
1. ARP 安全（DR 模式核心）
   RS 必须 arp_ignore=1 / arp_announce=2，否则 RS 抢答 VIP 的 ARP，
   VIP 流量直接打穿到单台 RS，负载均衡完全失效（见踩坑 1）。

2. 防火墙放行
   Director 上放行 VIP 端口（80/443 等）与 keepalived 的 VRRP 协议
   （vrrp 组播 224.0.0.18 / 协议号 112）；
   Ubuntu ufw：ufw allow 80/tcp；ufw allow proto vrrp
   RHEL firewalld：firewall-cmd --permanent --add-port=80/tcp
   NAT 模式还需放行 conntrack 相关（nf_conntrack 自动处理回程）。

3. 权限
   ipvsadm 修改内核规则需 root（sudo）；只读查看 -L 一般也需 root。
   建议只给运维账号 sudo 授权 ipvsadm/keepalived 两个命令。

4. 防 DDoS
   LVS 内核态转发抗 SYN Flood 能力强于用户态代理，配合 SYNPROXY
   和 keepalived 的 RS 健康检查，可扛住较大入口攻击；
   但 RS 应用层仍是瓶颈，需 RS 侧限流/扩容配合。

5. RS 侧加固
   DR 模式下 RS 直接暴露给客户端回包，建议 RS 只监听 VIP 对应服务端口，
   其余端口防火墙关闭；RS 的 lo:0 VIP 配置只在内网运维脚本中存在。

6. Red Hat 系差异（RHEL 8+ nftables 后端）
   RHEL 8/9 默认防火墙后端是 nftables（firewalld），对 LVS 的影响：
   - 放行规则统一用 firewall-cmd 管理（--add-port / --add-rich-rule）
   - NAT 模式依赖的 conntrack 规则在 nftables 下行为一致，但注意
     firewalld 的 zone 策略：Director 的 VIP 端口需显式放行，
     且保证 RS 回包路径上的接口属于允许的 zone
   - 内核 ip_vs 系列模块在 RHEL 8+ 依然可用（modprobe ip_vs），
     无需额外内核包；规则持久化路径为 /etc/sysconfig/ipvsadm
```

## 故障排查

### 案例 1：DR 模式 RS 收不到包（流量进不来）

```text
现象：客户端访问 VIP 超时，Director 上 ipvsadm -L -n --stats 显示
      InActConn 在涨（请求到了 Director），但 RS 上抓包看不到任何请求。

排查步骤：
  1. Director 确认请求到达：ipvsadm -L -n --stats / ipvsadm -L -n -c
  2. RS 确认 lo 是否绑了 VIP：ip addr show lo | grep 192.168.1.100
  3. RS 确认 ARP 参数：cat /proc/sys/net/ipv4/conf/all/arp_ignore
  4. RS 抓包确认：tcpdump -i eth0 host 192.168.1.100 -nn
  5. 检查 RS 防火墙：ufw status / firewall-cmd --list-all

根因（按概率排序）：
  a. RS 没绑 lo VIP —— 包到达 RS 但被内核丢弃（无本地地址匹配）
  b. RS 抢答 ARP —— 客户端 ARP 缓存指向了错误 RS 或 Director 未应答
  c. RS 防火墙 drop 了 VIP 流量
  d. 同网段但有交换机端口隔离/VLAN 问题（二层不通）

解法：
  执行 RS 初始化脚本（lo 绑 VIP + arp_ignore=1/arp_announce=2），
  放行防火墙端口，arping 验证 VIP 可达（arping -I eth0 -c 3 -U 192.168.1.100）。
```

### 案例 2：NAT 模式请求有进无回（回包不通）

```text
现象：NAT 模式配置正确，ipvsadm -L -n --stats 显示连接在建立，
      但客户端收不到响应（超时）。

排查步骤：
  1. Director 是否开启转发：cat /proc/sys/net/ipv4/ip_forward（必须为 1）
  2. 连接表状态：ipvsadm -L -n -c —— 看状态是 NONE/SYN_RECV 还是 ESTABLISHED
  3. RS 默认路由是否指向 Director：ip route（NAT 模式 RS 回包必须经 Director）
  4. Director 防火墙：是否 drop 了 conntrack 状态（iptables -L -n）

根因：
  a. ip_forward=0 —— 最常见，内核不转发
  b. RS 默认路由不指向 Director —— RS 回包走其他路径，conntrack 对不上
  c. Director 防火墙策略丢弃 FORWARD 链流量（如默认 DROP 未放行）

解法：
  echo 1 > /proc/sys/net/ipv4/ip_forward（并写入 sysctl.conf）
  RS 默认路由指向 Director；FORWARD 链放行（iptables -P FORWARD ACCEPT
  或按需精细化放行）。
```

### 案例 3：负载严重不均（某台 RS 忙死、其他空闲）

```text
现象：ipvsadm -L -n --stats 显示两台 RS 的 ActiveConn/字节数差异巨大，
      甚至一台 RS 被打挂。

排查步骤：
  1. 确认算法：ipvsadm -L -n（Scheduler 列）
  2. 看持久连接：ipvsadm -L -n（Flags 列有 Persist 说明开了 -p）
  3. 对比请求时长：后端应用访问日志统计平均耗时（长请求会让 rr 失衡）
  4. 看权重：ipvsadm -L -n（Weight 列，wrr/wlc 受权重影响）

根因：
  a. 算法与业务不匹配：rr 分给长连接业务 → 改成 wlc
  b. -p 持久连接过长：热点源 IP 全粘在一台 RS → 缩短或去掉 -p
  c. 权重配错：wrr 下 weight 与真实性能不符 → 校正权重
  d. 健康检查失效：某台 RS 已半死但仍被分发（服务端口通、应用挂）→
     改用 HTTP_GET 应用层检查

解法：
  ipvsadm -E -t VIP:80 -s wlc 换算法；调整 -p 超时；
  keepalived 的 real_server 检查从 TCP_CHECK 升级为 HTTP_GET/SSL_GET。
```

### 案例 4：Keepalived 主备不切换 / 频繁误切换

```text
现象：主 Director 宕机后 VIP 不漂移；或主备正常时 VIP 频繁跳变，连接闪断。

排查步骤：
  1. 心跳：tcpdump -i eth0 vrrp（VRRP 组播 224.0.0.18 是否互通）
  2. 状态：ip addr show（VIP 当前在哪台）；journalctl -u keepalived
  3. 检查优先级与配置：keepalived.conf 的 priority/state 是否一致
  4. 健康检查误判：real_server 检查路径/端口是否写错

根因：
  a. VRRP 组播被防火墙拦截（常见：云厂商安全组不支持组播）→ 改单播
  b. 两台 priority 相同且都是 MASTER —— 主备互抢
  c. keepalived 健康检查把正常 RS 误判为故障，触发反复摘除/加回
  d. 网卡名/IP 写错，VIP 绑不上

解法：
  VRRP 组播不通时配置 unicast_peer（对方 IP）单播；
  主备 priority 明确区分（如 100/90）；健康检查用与业务一致的探活路径；
  journalctl 看 keepalived 日志逐条核对。
```

## 常见问题

```text
Q1: LVS 为什么性能高？
A: 转发逻辑跑在内核态 ip_vs 模块（不进用户态），只做四层转发
   （不解析 HTTP），DR 模式回包还直连客户端，单机吞吐可达百万级连接。

Q2: DR 模式回包不走 Director，客户端会不会有问题？
A: 不会。DR 模式设计就是「进经 Director、出直连」：RS 以 VIP 为源地址
   直接回包，客户端只认识 VIP，无所谓包从哪台机器回来。

Q3: DR 模式 RS 为什么必须绑 VIP 在 lo 上？
A: 两个原因：① RS 收到「目标 IP = VIP」的包后，本机接口必须有该地址
   内核才收；② 回包源地址必须是 VIP，客户端才认。绑在 lo（而非 eth0）
   是为了配合 ARP 抑制，避免 RS 在物理网卡上应答 VIP 的 ARP。

Q4: 三种模式怎么选？
A: 同网段、追求性能 → DR；跨网段/跨机房 → TUN；RS 异构、要端口映射、
   小规模 → NAT。生产 HTTP 入口几乎都是 DR。

Q5: 会话保持怎么做？
A: 两种：① -p 持久连接（同源 IP 在超时内固定到同 RS，四层通用）；
   ② sh 源地址哈希算法。注意 -p 会破坏均衡性，超时设业务可接受的
   最短值；七层场景（Cookie 粘滞）交给 Nginx/HAProxy。

Q6: 调度算法怎么选？
A: 请求时长均匀用 rr/wrr；时长不均用 wlc（默认算法）；会话保持用 sh；
   缓存类服务用 lblc/lblcr；后端异构用 sed/nq。拿不准先用 wlc。

Q7: LVS 和 Nginx/HAProxy 负载均衡的区别？
A: LVS 是内核态四层（只看 IP:端口，性能最高，不能按 URL 路由）；
   Nginx/HAProxy 是用户态七层（能按域名/URL/Header 路由，功能丰富，
   性能低于 LVS）。经典组合是 LVS 扛入口 + Nginx 做七层路由。

Q8: LVS 支持 UDP 吗？支持健康检查吗？
A: 支持：ipvsadm -A -u VIP:端口。LVS 本身不主动做健康检查，
   健康检查由 Keepalived 完成（TCP_CHECK/HTTP_GET 探测，自动摘除故障 RS）。

Q9: NAT 模式支持端口映射吗？
A: 支持：-r 后写 RIP:端口（如 -r 10.0.0.11:8080），VIP:80 → RS:8080。
   DR/TUN 不支持端口映射（RS 端口必须与 VIP 一致）。
```

## 面试题

```text
1. LVS 三种转发模式的区别？生产怎么选？
   答：NAT 进出都经 Director（改源/目标 IP，Director 是瓶颈，RS 零配置，
   支持端口映射）；DR 只改目标 MAC、回包直连客户端（性能最高，要求同网段
   + RS 绑 VIP + 抑制 ARP）；TUN 用 IP-in-IP 隧道封装（跨网段，有封装开销）。
   同网段生产首选 DR，跨机房用 TUN，小规模异构用 NAT。

2. DR 模式为什么要抑制 ARP？具体怎么配？
   答：RS 绑了 lo VIP 后，若不抑制，RS 会应答「谁是 VIP」的 ARP 请求，
   客户端的 ARP 缓存随机指向某台 RS，VIP 流量打穿单机、负载均衡失效。
   配置：RS 上 arp_ignore=1（只应答本接口地址的 ARP）、arp_announce=2
   （用最优本地地址应答），VIP 绑在 lo 上（/32），写入 sysctl.conf。

3. LVS 支持哪些调度算法？分别适合什么场景？
   答：10 种：rr（轮询，短连接均匀）、wrr（加权轮询，异构后端）、
   lc（最少连接，长连接）、wlc（加权最少连接，默认，通用首选）、
   lblc/lblcr（局部性最少连接，缓存类）、dh/sh（目标/源地址哈希，
   sh 用于会话保持）、sed/nq（最短预期延迟/永不排队，异构后端更平滑）。

4. 为什么 LVS 能扛百万级并发？
   答：① 工作在内核态 ip_vs 模块，数据包不进用户态、无进程上下文切换；
   ② 只做四层转发，不解析 HTTP 内容；③ DR 模式回包直连客户端，
   Director 只处理一半流量；④ 连接跟踪表是内核哈希表，查找 O(1)。

5. LVS 单点故障怎么解决？
   答：双 Director + Keepalived（VRRP）：两台 Director 配置相同的
   ipvsadm 规则和 virtual_server 检查，主备通过 VRRP 心跳协商，
   主宕机后 VIP 在数秒内漂移到备机，备机接管转发，对客户端透明。

6. 你们公司的四七层架构怎么搭的？
   答：入口 DNS → LVS（四层，按 VIP:80/443 分发到 Nginx 集群）→
   Nginx（七层，按域名/URL 路由、TLS 终结、限流、静态缓存）→
   应用服务器。LVS 扛流量、Nginx 做路由，各司其职；LVS 层用
   Keepalived 双机高可用，Nginx 层多实例 + 健康检查自动摘除。

7. LVS 的会话保持方案有哪些？有什么代价？
   答：-p 持久连接或 sh 源地址哈希（四层）；Nginx 层可加 Cookie 粘滞。
   代价是负载不均：热点源 IP 全部压到同一台 RS，所以 -p 超时尽量短、
   或用一致性哈希减少后端增减时的会话漂移。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 同网段一律用 DR 模式（性能最高），跨网段才考虑 TUN，NAT 仅限小规模/异构场景
2. RS 端 lo 绑 VIP + arp_ignore=1/arp_announce=2 做成初始化脚本并持久化（sysctl.conf），每台 RS 必须一致
3. 调度算法按业务特征选：拿不准先用默认 wlc；短连接均匀用 wrr
4. 会话保持用 -p 时超时取业务可接受的最短值，避免热点粘连
5. 规则用 ipvsadm-save 持久化并纳入配置管理，重启不丢、变更可审计
6. Director 必须配 Keepalived 双机高可用（VRRP），避免单点
7. Keepalived 健康检查用应用层探测（HTTP_GET 检查 /health），别只查端口
8. 上线前用 ab/wrk 压测验证吞吐，用 ipvsadm -L -n --stats 观察分发表
9. 变更流程：先 ipvsadm -d 摘 RS → 验证 → 再 -a 加回，杜绝粗暴重启
10. 四七层分层：LVS 只做四层分发，七层路由交给 Nginx，各层独立伸缩

### 踩坑记录

```text
坑 1：DR 模式 RS 没抑制 ARP，抢了 VIP
结论：客户端流量随机打到某台 RS 上，负载均衡完全失效，故障难定位。
原因：RS 在 lo 绑了 VIP，但没设 arp_ignore/arp_announce，
     RS 也响应「谁是 VIP」的 ARP 请求。
解法：RS 上设 arp_ignore=1、arp_announce=2（all 和 lo 都要），
     写入 /etc/sysctl.conf 持久化。

坑 2：DR 模式 RS 没绑 lo VIP，收不到任何请求
结论：Director 连接表在涨（InActConn 增加），RS 上 tcpdump 却抓不到包。
原因：RS 本机没有「目标 IP = VIP」的地址，内核直接丢弃该包。
解法：RS 的 lo 绑 VIP（ip addr add VIP/32 dev lo），注意掩码必须 /32，
     否则 RS 会用 VIP 参与同网段 ARP 广播。

坑 3：NAT 模式 Director 成瓶颈，吞吐上不去
结论：压测 2 万 QPS 就上不去，Director CPU/带宽打满。
原因：NAT 进出流量都经 Director（回包也要 SNAT），Director 是必经之路。
解法：同网段改 DR 模式（回包直连）；必须 NAT 时给 Director 上
     万兆网卡 + 多队列，或拆多组 VIP 分担。

坑 4：规则没持久化，重启后 LVS 全丢
结论：Director 重启后 ipvsadm -L 为空，业务全部直连失败。
原因：ipvsadm 规则只存在内核里，重启即失，没做 save/restore。
解法：ipvsadm-save > /etc/ipvsadm.rules + systemctl enable ipvsadm
     （RHEL 用 /etc/sysconfig/ipvsadm + systemctl enable ipvsadm）。

坑 5：rr 算法 + 长请求，负载严重不均
结论：某台 RS CPU 100%、其他空闲，业务偶发超时。
原因：rr 只看顺序不看负载，一个长请求（如大报表）把某台 RS 占满后
     新请求还继续分发过来。
解法：换 wlc（加权最少连接）或 sed/nq；关键接口单独设 VS 隔离。

坑 6：keepalived 健康检查只查端口，应用假死没被摘除
结论：RS 进程活着、端口通，但应用已无响应（线程池耗尽），
     请求全打在这台「半死」RS 上。
原因：TCP_CHECK 只验证 TCP 握手，验证不了应用可用性。
解法：real_server 改用 HTTP_GET（检查 /health 返回 200）
     或自定义 MISC_CHECK 脚本探测业务关键路径。

坑 7：Director 防火墙没放行 VIP 端口
结论：客户端访问 VIP 无响应，ipvsadm 规则看起来完全正确。
原因：ufw/firewalld 默认策略拦截了 VIP 端口（或 FORWARD 链 DROP），
     NAT 模式尤其容易踩 FORWARD 链的坑。
解法：ufw allow 80/tcp（firewalld：firewall-cmd --add-port=80/tcp）；
     NAT 模式确保 FORWARD 链放行；keepalived 放行 vrrp 协议。

坑 8：-p 持久连接设太长，热点 IP 全粘一台
结论：一台 RS 连接数是其他台的几十倍，反复告警。
原因：-p 3600 让同源 IP 一小时内都固定到同一 RS，
     公司出口 NAT IP 是热点，全压一台。
解法：-p 超时改短（如 50~300 秒）或用 sh 算法按需保持；
     热点场景评估去掉持久连接、改应用层 Cookie 粘滞。

坑 9：DR 模式回包被 RS 防火墙丢（非对称路由被 state 防火墙拦）
结论：客户端能建连但收不到响应，Director 一切正常，RS 抓包有请求无响应。
原因：RS 启用了 stateful 防火墙，回包从 RS 直连客户端，
     但该连接在 RS 上「入向包」没被防火墙记录为 established，
     回包被当作无效包丢弃（非对称路由场景）。
解法：RS 防火墙放行 VIP 相关连接（或对 VIP 流量关闭 state 过滤），
     确认 RS 默认路由可直连客户端网段。
```
