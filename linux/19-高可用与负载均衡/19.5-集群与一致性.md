## 概述

集群（Cluster）是把多台服务器组织成一个整体对外提供服务的架构，核心目标是**高可用**（一台挂了别的顶上）和**扩展性**（加机器就能扛更多流量）。而「一致性」（Consistency）是集群绕不开的数学题：多节点之间数据如何保持一致、允许短暂不一致到什么程度、网络分区时到底保数据还是保可用——这些选择直接决定集群的架构形态。

集群按用途分为四大类：

- **高可用集群（HA Cluster）**：主备/主主切换，保证服务不中断。如 Keepalived 双机热备、Pacemaker/Corosync 资源集群。
- **负载均衡集群（LB Cluster）**：多台机器分摊流量，如 LVS、HAProxy、Nginx（详见 [[19.2-Keepalived 与 VRRP]]、[[19.3-LVS 负载均衡]]、[[19.4-HAProxy 与 Nginx]]）。
- **计算集群（HPC/分布式计算）**：把计算任务切分到多节点并行，如 MPI、Hadoop/Spark 集群。
- **存储集群（Storage Cluster）**：多节点共享或复制存储，如 NFS 集群、Ceph、GlusterFS（参见 [[18.1-共享存储]]、[[06.4-RAID]]）。

一致性是这一切的基石：数据库主从复制、Redis 集群、etcd/ZooKeeper 协调服务、分布式锁，本质上都在回答「多节点怎么达成共识」。而**共识算法（Paxos/Raft）**就是分布式系统领域的「原子弹」——etcd 用 Raft 实现强一致 KV 存储，Kubernetes 把全部集群状态（Pod、Service、ConfigMap……）都放在 etcd 里，consul 用它做服务发现，ZooKeeper 用 ZAB 协议做分布式协调。

## 核心概念

### 1. 集群分类

| 类型 | 目的 | 典型实现 | 一致性要求 |
|------|------|----------|------------|
| 高可用集群 | 服务不中断（故障转移） | Keepalived/VRRP、Pacemaker+Corosync | 状态仲裁（Quorum） |
| 负载均衡集群 | 流量分摊、扩展吞吐 | LVS、HAProxy、Nginx | 无状态居多，无强一致要求 |
| 计算集群 | 并行计算、缩短任务时间 | MPI、Hadoop/Spark、K8s 调度 | 计算任务切分，重结果汇总 |
| 存储集群 | 容量扩展、数据冗余 | NFS 集群、Ceph、GlusterFS、RAID | 强一致/最终一致取决于实现 |

注意**高可用集群 ≠ 负载均衡集群**：HA 是「备胎机制」（一台挂了另一台顶上，同一时刻通常只有一台在工作），LB 是「分工机制」（多台同时干活分摊流量）。两者常组合使用（LB 后面挂 HA 池）。

### 2. CAP 定理

CAP 定理（Eric Brewer 提出，2000 年）指出：分布式系统在**网络分区（Partition）**发生时，无法同时满足以下三者，最多取其二：

- **C（Consistency，一致性）**：所有节点同一时刻读到相同的数据。写操作要么全部节点成功，要么全部失败。
- **A（Availability，可用性）**：任何请求都能在合理时间内得到响应（不保证响应是最新数据）。
- **P（Partition tolerance，分区容错性）**：网络分区（节点间通信中断）时系统仍能继续运行。

**关键理解**：不是「三个里随便选两个」，而是 **P 必须选**——只要是多节点分布式系统，网络分区就必然存在（交换机故障、机房光缆被挖断、节点宕机），无法假设网络永远可靠。所以真正的选择题是：**分区发生时，保 C 还是保 A？**

- **CP 系统**：分区时拒绝服务以保证一致。etcd、ZooKeeper、HBase 是 CP。etcd 在丢失 Quorum 时会拒绝所有写请求（宁可不可用，也不给旧数据）。
- **AP 系统**：分区时继续服务，容忍数据短暂不一致（事后收敛）。Cassandra、DynamoDB、Eureka 是 AP。
- **CA 系统**：单机数据库（无分区概念），或严格意义上只在「不分区」的假设下成立。

| 系统 | 选择 | 说明 |
|------|------|------|
| etcd / ZooKeeper | CP | 配置/元数据必须精确，宁可短暂不可用 |
| MySQL 主从 | 折中 AP/CP | 主库写、从库异步复制：分区时主库照常写（AP），但从库数据可能滞后 |
| Redis Cluster | 折中 | 槽位归属节点写本地，分区时部分槽位不可用（可用性下降） |
| Cassandra | AP | 最终一致，分区时继续读写 |
| Eureka（Netflix） | AP | 注册中心保可用，各节点自持注册表，最终一致 |

**现实落点**：大多数系统是「分区时降级」的折中——正常时强一致，分区时保可用、恢复后收敛（最终一致），或分区时保一致、拒绝一部分请求。CAP 的价值不是让你二选一，而是让你**在设计时想清楚分区发生时的取舍优先级**。

### 3. BASE 理论

BASE（Basically Available、Soft state、Eventually consistent）是 AP 路线的工程化总结，与 ACID 相对：

- **BA（基本可用）**：分区/故障时允许部分功能降级（如限流、只读），而不是整体不可用。
- **S（软状态）**：允许系统中间状态存在（数据副本之间可以不一致）。
- **E（最终一致）**：没有持续更新的前提下，经过一段时间（通常毫秒~秒级），所有副本最终收敛到一致。

BASE 适用于：缓存、搜索索引、社交 feed、订单状态展示等「短暂读到旧数据可接受」的场景。**业务上不可接受的强一致场景**（转账、库存扣减、分布式锁）必须走 CP 或加锁协调。

### 4. 一致性模型

从强到弱排列：

1. **强一致（Strong Consistency）**：写完成后，任何节点读到的都是最新值。Raft/Paxos 多数派提交实现。
2. **线性一致（Linearizability）**：强一致的最严格形式——所有操作看起来像在某个时间点原子发生，且与真实时间顺序一致。etcd 默认读（linearizable read）就是线性一致。
3. **顺序一致（Sequential Consistency）**：所有节点看到相同顺序的操作序列，但该顺序不一定与真实时间一致（允许「读旧」但顺序不乱）。
4. **因果一致（Causal Consistency）**：有因果关系的操作按序可见，无因果关系的可乱序。
5. **最终一致（Eventual Consistency）**：无新写入后，副本最终一致。异步主从复制、DNS、Gossip 协议都是最终一致。
6. **会话一致 / 单调读**：工程化变体，保证「自己写的自己能读到」「读不会倒退」，比最终一致体验好。

### 5. 共识算法（Paxos / Raft / ZAB）

共识（Consensus）解决「多个节点就某个值达成一致，且少数节点故障不影响结论」。三大算法：

- **Paxos**（Leslie Lamport，1990 年提出）：第一个被证明正确的共识算法，理论价值极高，但工程实现复杂难懂。Google Chubby 用它。分 Basic Paxos（单值共识）和 Multi-Paxos（日志复制）。
- **Raft**（Diego Ongaro，2014 年）：为「可理解性」而生的 Paxos 简化版，把共识拆成**领导者选举、日志复制、安全性**三个子问题，用强领导者模型大幅简化。etcd、consul、K8s 生态、TiKV 都用它。
- **ZAB**（ZooKeeper Atomic Broadcast）：ZooKeeper 专用协议，类似 Raft 的领导者 + 原子广播，保证「事务的顺序性」。

三者本质相同（多数派投票 + 编号递增 + 法定人数确认），区别在工程组织方式，详见「工作原理」节的对比表。

### 6. Quorum（法定人数）与脑裂

- **Quorum**：达成共识所需的最少节点数。Raft 要求**多数派**：N 节点集群需要 `⌊N/2⌋+1` 票。
- **奇数节点原则**：集群节点数取 3/5/7 等奇数，使多数派计算不会出现平票。4 节点容忍度与 3 节点相同（都只能挂 1 台），多花钱不提升容错。
- **脑裂（Split Brain）**：网络分区导致两个「多数派」各自为政，出现两个 leader、两个主库同时写，数据分叉。**Quorum 机制 + Fencing（隔离）**是防脑裂的两道防线（详见「工作原理」）。

### 7. 分布式协调服务定位

| 组件 | 协议 | 一致性 | 典型用途 |
|------|------|--------|----------|
| etcd | Raft | CP/线性一致 | K8s 配置存储、服务发现、分布式锁、选主 |
| ZooKeeper | ZAB | CP（顺序一致） | 分布式协调、配置、命名、选主（Hadoop/Kafka 生态） |
| Consul | Raft | CP | 服务发现 + 健康检查 + KV + 多数据中心 |
| Redis Cluster | 槽位哈希 | 最终一致（主从异步） | 缓存/数据分片 |

etcd 与 ZooKeeper 详细对比见「工作原理」节表格。

## 工作原理

### 1. Raft 共识算法详解

Raft 把共识问题拆成三个子问题，全程围绕一个**强领导者（Strong Leader）**：

#### 角色

- **Leader（领导者）**：唯一处理写请求的节点。所有写请求必须经过 Leader 转发到集群；Leader 定期发心跳。
- **Follower（跟随者）**：被动接收 Leader 的日志复制与心跳，响应投票请求。多数派节点是 Follower。
- **Candidate（候选者）**：选举超时后 Follower 自荐竞选，向其他节点请求投票，获得多数票后变 Leader。

#### 任期（Term）

时间被切成递增的**任期**（term，单调递增整数）。每次选举开始一个新任期；任期号随每个 RPC（心跳、投票、日志复制）一起传递，**过期任期的消息一律拒绝**——这是防止「旧 Leader 复活乱写」的关键机制。

#### 选举流程

```text
① Follower 在 election-timeout（随机 150~300ms）内没收到 Leader 心跳
        ↓
② 自增 term，转为 Candidate，投自己一票，向所有节点发 RequestVote
        ↓
③ 每个节点「先到先得」：同一任期内只投一票（投票给日志至少不落后于自己的候选者）
        ↓
④ 获得多数派（含自己）选票 → 成为新 Leader，立刻发心跳（AppendEntries）确立地位
   （平票则等待随机超时后重新竞选——随机超时保证最终会有人胜出）
```

**为什么能选出唯一 Leader**：多数派投票保证任意两个候选者不可能都拿到多数票（两个多数派必有交集）；随机 election-timeout 让平票僵局自动打破。

#### 日志复制

```text
① 客户端写请求 → Leader 追加为本地日志条目（含 term 与 index）
② Leader 并行把日志条目发给所有 Follower（AppendEntries）
③ 大多数节点（Quorum）确认写入后，Leader 把条目标记为「已提交」（committed）
④ Leader 在下次心跳/下一条日志里带上 commitIndex，Follower 应用日志到状态机
⑤ 客户端收到写成功响应 —— 只有「已提交」才返回成功
```

**Raft 安全性质**：已提交的日志条目绝不会丢失——新 Leader 必须包含所有已提交条目（投票时校验日志新旧：term 大者新，term 相同 index 大者新）；Leader 只覆盖自己任期内的冲突条目，绝不删除已提交条目。

#### 读请求

etcd 提供两种读：

- **线性一致读（默认）**：Leader 收到读请求后先向多数派确认自己仍是 Leader（ReadIndex），再读本地状态机——保证读到最新已提交数据。
- **串行读（Serializable）**：任意节点直接读本地数据，可能读到旧值，但性能最高（Follower 可分担读）。

#### 与 Paxos 对比

| 维度 | Paxos | Raft |
|------|-------|------|
| 提出时间 | 1990（论文 1998 发表） | 2014 |
| 领导者 | 多领导者可并行提案（Basic Paxos），Multi-Paxos 才引入 Leader | 强领导者：写必须经 Leader |
| 选举 | 无显式选举流程，提案竞争 | 显式任期 + 随机超时选举 |
| 可理解性 | 公认难懂，工程实现差异大 | 为教学而设计，论文配图讲透 |
| 日志 | 无统一日志模型 | 明确日志条目（term, index）+ 提交机制 |
| 使用方 | Google Chubby、TiDB PD（Multi-Paxos 变体） | etcd、consul、TiKV、K8s、MongoDB 副本集 |

### 2. ZAB 协议（ZooKeeper）

ZAB（ZooKeeper Atomic Broadcast）分两个阶段：

- **恢复模式（Recovery）**：Leader 挂了后，集群选出新 Leader，并让所有 Follower 以 Leader 的事务日志为准（丢弃未提交事务）。
- **广播模式（Broadcast）**：写请求经 Leader 生成事务（zxid 单调递增），广播给 Follower，多数派 ACK 后提交。

与 Raft 的区别：ZAB 面向「事务顺序广播」，保证 zxid 全局有序；Raft 面向「日志复制 + 状态机」。两者都能保证强一致与故障恢复，工程结构不同。

### 3. etcd 工作流程（Raft 落地）

etcd 是 Raft 的 Go 语言标杆实现，其核心工作流：

```text
写请求：client → Leader（HTTP/gRPC）→ 追加日志 → 复制到 Follower → 多数派确认 → 提交 → 返回
读请求：linearizable 读 → Leader 确认任期 → 读状态机
watch：  client 订阅前缀 → 版本号（revision）变化时推送增量事件（MVCC 实现）
lease：  client 租约（TTL）→ Leader 定期续约 → 过期自动删除关联键
```

etcd 的关键数据结构是 **MVCC + 版本号**：每个键有 `create_revision`、`mod_revision`、`version`，所有历史版本都保留（直到 compact 压缩），watch 就是基于 revision 的增量推送。这也是 `etcdctl get --write-out=json` 能看到完整版本信息的原因（见「常用命令」实测）。

### 4. 脑裂与 Fencing（隔离）

**脑裂的根源**：网络分区时，两个分区各自认为自己是「活的」，如果没有仲裁机制，就会同时出现两个主节点写数据。

两道防线：

1. **Quorum 仲裁**：写操作必须多数派确认。分区后只有包含多数派的那个分区能继续写，少数派分区自动降级为只读/不可用——**物理上杜绝双主**。etcd/ZooKeeper 丢失 Quorum 后直接拒绝写。
2. **Fencing（栅栏/隔离）**：仲裁判定某节点失联后，主动把它「物理隔离」——STONITH（Shoot The Other Node In The Head，Pacemaker 术语）即**断电/重启故障节点**，防止它复活后继续写共享资源。Fencing 是**必选项而非可选项**：如果只做 Quorum 不 fencing，被隔离节点恢复后可能带着旧状态回来覆盖新数据。

```text
例：3 节点 etcd，节点间网络被切断，节点 A 与 B、C 隔离
    A 自己凑不齐 2 票 → 拒绝写（CP 选择：保一致，牺牲可用）
    B、C 有 2 票（多数派）→ 正常服务
    若 A 是旧 Leader，会因 term 过期被 B/C 拒绝 —— 不会出现双主
```

### 5. 集群节点数设计（容错计算）

Raft/多数派集群的容错上限：**N 节点可容忍 ⌊(N-1)/2⌋ 台故障**。

| 节点数 | 多数派（Quorum） | 可容忍故障 | 说明 |
|--------|------------------|------------|------|
| 1 | 1 | 0 | 无高可用，仅用于开发/测试（本机即此形态） |
| 3 | 2 | 1 | 生产最低配置，etcd/K8s 控制面默认 3 副本 |
| 5 | 3 | 2 | 滚动升级 + 容忍一台故障时仍有冗余 |
| 7 | 4 | 3 | 大规模生产，通常不必要（成本高） |
| 4 | 3 | 1 | **偶数节点不推荐**：容错与 3 节点相同，还容易在「2 vs 2」分区时整体不可用 |

**为什么必须奇数**：4 节点多数派是 3，容错 1，和 3 节点一样；但网络恰好把 4 节点分成 2+2 时，两个分区都凑不齐 3 票，集群整体不可用（3+1 分区则小分区 1 台被牺牲，大分区 3 台正常）。5 vs 7 同理，奇数节点避免「平票死锁」场景。

## 配置文件解析

### 1. etcd 配置（etcd.yml / 启动参数）

etcd 支持 `--flag` 启动参数和配置文件两种方式。K8s 静态 Pod 或容器场景多用参数；systemd 场景常见 `/etc/etcd/etcd.conf.yml`。关键配置项：

```yaml
# /etc/etcd/etcd.conf.yml —— 3 节点集群示例
name: etcd-node1                          # 节点唯一名称
data-dir: /var/lib/etcd                   # 数据目录（WAL + snapshot + member）
listen-client-urls: https://10.0.0.1:2379 # 客户端监听（应用连这个）
listen-peer-urls: https://10.0.0.1:2380   # 节点间 Raft 通信监听
advertise-client-urls: https://10.0.0.1:2379   # 对外广播的 client 地址
initial-advertise-peer-urls: https://10.0.0.1:2380  # 对外广播的 peer 地址
initial-cluster: |                        # 初始集群成员（全部节点）
  etcd-node1=https://10.0.0.1:2380,
  etcd-node2=https://10.0.0.2:2380,
  etcd-node3=https://10.0.0.3:2380
initial-cluster-state: new                # new=新建集群；existing=加入已有集群
initial-cluster-token: etcd-cluster-1     # 集群唯一 token，防止串集群

# --- 高可用/性能相关 ---
heartbeat-interval: 100                   # Leader 心跳间隔(ms)，默认 100
election-timeout: 1000                    # 选举超时(ms)，默认 1000（建议 5~10 倍心跳）
max-request-bytes: 1572864                # 单请求上限（默认 1.5MB）
quota-backend-bytes: 8589934592           # 后端存储配额（默认 2GB，超了只读）
auto-compaction-mode: periodic            # 历史版本自动压缩
auto-compaction-retention: 1              # 保留 1 小时（periodic 单位小时）
snapshot-count: 100000                    # 每 N 条日志触发一次快照
```

**关键字段速记**：

```text
listen-client-urls   客户端端口 2379 —— 应用/K8s API Server 连这里
listen-peer-urls     节点间端口 2380 —— Raft 通信（必须全节点互通）
initial-cluster      初始成员列表，3 节点全列出
initial-cluster-state new（首建）/ existing（扩容加入）
auto-compaction      历史版本压缩，不配会无限膨胀
quota-backend-bytes  空间配额，超了集群进入只读保护（mvcc: database space exceeded）
```

**本机容器启动方式**（1Panel 起的单节点开发环境，无 TLS、无认证）：

```text
docker run ... quay.io/coreos/etcd:v3.5.5
  /usr/local/bin/etcd --name default --data-dir /etcd-data
  --listen-client-urls http://0.0.0.0:2379 --advertise-client-urls http://0.0.0.0:2379
  --listen-peer-urls http://0.0.0.0:2380 --initial-advertise-peer-urls http://localhost:2380
  --initial-cluster default=http://localhost:2380 --initial-cluster-state new
```

### 场景二：Kubernetes 为什么用 etcd（配置存储 + 控制面一致性）

K8s 是「声明式控制循环」架构：**所有状态都进 etcd，所有组件都 watch etcd**。

```text
kubectl apply → API Server → 写入 etcd（/registry/... 前缀）→ 触发 watch 事件
    → Controller Manager / Scheduler 收到事件 → 做出决策 → 写回 etcd
    → kubelet 收到调度结果 → 拉镜像起 Pod → 上报状态到 etcd

etcd 承担的职责：
① 集群唯一事实来源：Pod/Service/ConfigMap/Secret/Deployment 全部资源对象
② 分布式锁/选主：多个 controller 副本通过 etcd lease 选主，同一时刻只有一个干活
③ 强一致保证：API Server 多副本时，写请求必须多数派确认，杜绝配置分叉
④ watch 机制：控制循环的"事件总线"，避免轮询
```

**为什么是 etcd 而不是 ZooKeeper**：

- etcd 原生支持 **watch + MVCC 版本号**，天然契合 K8s 的 resourceVersion 乐观并发控制；
- gRPC 协议 + Go 生态（K8s 也是 Go），集成成本低；
- 简单可靠的 Raft 实现，运维面小；
- 2014 年 K8s 选型时 etcd 是唯一同时满足「强一致 + watch + 轻量」的方案（此后 ZooKeeper 生态逐渐退出 K8s 控制面）。

K8s 控制面高可用 = 3 个 API Server + 3 个 etcd（或 etcd 独立部署），任一 etcd 挂一台不影响集群。

### 场景三：MySQL 主从复制 + 读写分离

```text
架构：主库(写) ── binlog ──→ 从库1(读) / 从库2(读)
     应用：写走主库，读走从库（配合读写分离中间件如 ShardingSphere / MyCat / ProxySQL）

实施步骤：
1. 主库配置：log_bin=ON，server-id=1，binlog_format=ROW
2. 主库建复制账号：CREATE USER 'repl'@'%' IDENTIFIED BY 'xxx';
   GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
3. 从库配置：server-id=2（唯一！）
4. 从库 CHANGE MASTER TO MASTER_HOST='主IP', MASTER_USER='repl', ...;
5. 从库 START SLAVE; SHOW SLAVE STATUS\G 验证两个 Running=Yes
6. 主库先导出再导入初始数据（或直接用 xtrabackup 物理备份做从库）

故障切换：主库挂 → 选一个从库提升为主（STOP SLAVE; RESET SLAVE ALL;
手动改应用写入口，或交给 MHA / Orchestrator / 半自动切换平台）
```

**一致性取舍**：MySQL 异步复制是最终一致（主写成功即返回，从库异步追赶）；半同步复制（rpl_semi_sync_master_enabled=1）等至少一个从库 ACK 才返回，牺牲一点写延迟换「主挂时不丢已确认事务」。这是典型「CAP 折中：正常时强一致，分区时主库照常可用」的设计。

### 场景四：Redis 主从 + 哨兵 / Redis Cluster

```text
方案 A：主从 + 哨兵（Sentinel，推荐中小规模）
  1 主 2 从 + 3 哨兵（哨兵奇数个，自己也是多数派集群）
  主挂 → 哨兵多数派判定客观下线 → 选从提升为主 → 客户端感知新主（自动故障转移）
  适用：单写多读、数据量单机放得下

方案 B：Redis Cluster（大规模分片）
  16384 个哈希槽，N 主 N 从，槽位分布在各主节点
  key 按 CRC16(key)%16384 路由到槽位所属节点
  主挂 → 从自动提升（cluster-enabled yes + cluster-node-timeout）
  适用：数据量大、需要横向扩展写能力

一致性：主从异步复制 → 最终一致；cluster 模式下主写从备，
多数派只在「选主」时起作用（cluster 元数据用 gossip，不是强一致共识）
```


### 场景五：分布式锁（etcd / Redis / ZooKeeper 三实现对比）

**分布式锁的硬性要求**：互斥（同一时刻只有一个持有者）、防死锁（持有者挂了锁要能释放）、防误删（只能释放自己的锁）、可重入（可选）。

```text
方案 A：Redis（SET NX EX + Lua 释放）——快，但极端场景有缺陷（主从切换可能丢锁）
  加锁：SET lock:order:1001 <uuid> NX EX 30
  释放：Lua 脚本校验 value==uuid 才 DEL
  续租：Redisson 看门狗（watchdog）自动续期，默认 30s

方案 B：etcd（lease + revision 比较）——强一致，可靠性最高
  加锁：etcdctl lock /lock/order-1001    # 阻塞式抢锁
  或：PUT /lock/order-1001 带 lease（TTL），lease 过期自动释放 → 天然防死锁
  续租：KeepAlive 续租，进程退出租约消失 → 锁自动释放

方案 C：ZooKeeper（临时顺序节点）
  创建临时顺序节点 /lock/lock_0000000001 → 序号最小者持锁
  持锁者会话断开 → 临时节点自动删除 → 下一序号节点获锁（watch 通知）
```

**选型**：对锁可靠性要求极高（防超卖、防重复支付）→ etcd/ZooKeeper；性能优先且可接受极小概率失效 → Redis。分布式锁的完整工程细节（续租、重试、Redlock 争议）参见 [[14.4-任务可靠性]]。

### 场景六：Pacemaker + Corosync 高可用集群（Red Hat 系生态）

```text
架构：3 节点 + 共享存储（或 DRBD）+ 浮动 IP + 服务资源

资源组示例（VIP + 应用 + 存储挂载）：
  pcs resource create vip ocf:heartbeat:IPaddr2 ip=10.0.0.100 cidr_netmask=24 \
      op monitor interval=5s
  pcs resource create web ocf:heartbeat:apache \
      op monitor interval=10s
  pcs resource group add webgrp vip web        # 打包成组，同生共死同机运行

  pcs constraint order start vip then start web   # 启动顺序
  pcs constraint colocation add web with vip      # 同机互斥（同机）

  pcs stonith create fence-node1 fence_xvm pcmk_host_list=node1
  # 或 fence_ipmilan（IPMI 带外管理）/ fence_scsi（SCSI 持久保留）
  # 不配 STONITH 时 Pacemaker 会拒绝启动资源（默认 stonith-enabled=true）

故障演练：pcs cluster stop node2 → 观察资源自动漂移到剩余节点 → 恢复后自动回切
```

**为什么必须配 Fencing**：节点「假死」（网络不通但进程还活着）时，如果不物理隔离它，它可能继续写共享存储，导致脑裂数据损坏。STONITH 直接断电/重启该节点，是「宁可错杀、不可漏杀」的暴力但正确的做法。

## 性能与调优

### 1. 共识算法的性能开销

- **写放大**：一次写 = 本地 WAL fsync + 复制到 Follower + 多数派确认，写延迟 ≈ 2 倍单机延迟（网络 RTT 主导）。3 节点跨机房部署时 RTT 直接决定写性能。
- **吞吐瓶颈**：Leader 是单点，所有写都过 Leader；日志复制是串行的（同一条日志按 index 顺序提交）。
- **对比**：单机 Redis 写延迟亚毫秒，etcd 跨机房 3 节点写延迟通常 2~10ms，Redis Cluster 单分片仍是单机性能。**强一致是拿延迟换正确性**。

### 2. etcd 调优清单

```text
① 磁盘：etcd 对 fsync 延迟敏感 → 用 SSD/NVMe，禁用写缓存延迟大的磁盘；
   WAL 与 snapshot 分目录放不同磁盘可进一步降竞争
② 心跳/选举：heartbeat-interval=100ms（默认），election-timeout 设为 5~10 倍
   （默认 1000ms）；跨地域部署要加大心跳间隔避免网络抖动触发无谓选举
③ 网络：peer 通信走内网/专线，避免跨公网；3 节点同机房为主，跨机房做
   "3+2" 或 "5 节点跨 3 机房"（2-2-1 分布，多数派 3 票）——保证任意机房故障
   时仍可能凑齐多数派（设计时算好：2 机房同时故障即整体不可用，可接受）
④ 历史版本膨胀：开启 auto-compaction（periodic，如每小时保留 1h 版本），
   否则 db 无限增长；compact 后空间不归还 → 定期 defrag（低峰期执行）
⑤ 空间配额：quota-backend-bytes 默认 2GB，超了进入只读保护
   （mvcc: database space exceeded），要监控并扩容
⑥ 客户端：etcd 客户端必须连「多个端点」并做重试（K8s API Server 就是这么配的），
   避免 Leader 切换时单点失败；使用 watch 而非轮询
```

### 3. 主从复制延迟优化

```text
MySQL：半同步复制（等 1 从 ACK）、并行复制（MTS，多线程回放）、
      大事务拆分、从库机器性能对齐主库
Redis：repl-backlog 调大（增量复制不断链）、主从同机房、
      避免主库大 key 阻塞生成 RDB
监控指标：Seconds_Behind_Master（MySQL）、master_repl_offset 差值（Redis）
```

### 4. 容量与规模规划

```text
etcd 适合「小数据 + 高可靠」：单库建议 < 8GB（官方推荐 2GB 配额），
K8s 生产集群 etcd 数据量通常几十~几百 MB（大量资源对象但单个很小）。
etcd 不适合存大数据/高频写（如日志、埋点），那是 Kafka/时序库的活。

节点数：3 起步、5 封顶（绝大多数场景 3 够用，5 用于更大规模或滚动升级冗余）；
不要 4/6 偶数；不要 7+（成本高收益低，跨机房 5 节点 2-2-1 是最优形态）。
```

### 5. ZooKeeper / Redis Cluster 调优要点

```text
ZooKeeper：3 节点（读写均衡）、5 节点（读多）、snapCount 控制快照频率、
           tickTime 默认 2000ms（session 超时 = 2~20 倍 tickTime）
Redis Cluster：分片数 = 主节点数（不要超过 CPU 核数太多）、
               槽位均衡（reshard 时小步迁移）、cluster-node-timeout 别太小
               （网络抖动会误判主节点故障触发频繁切换）
```

## 安全与权限

### 1. etcd 安全基线

```text
① 传输加密：client 与 peer 全部 TLS（--client-cert-auth --peer-cert-auth），
   证书用内部 CA 签发，K8s 场景由 kubeadm 自动生成
② 认证授权：etcdctl user add root → auth enable → 按角色授权
   （root 全权；app 角色只读 /registry/... 前缀，最小权限）
③ 网络隔离：2379 只对 API Server/运维网段开放，2380 仅集群内网互通；
   公网暴露 = 裸奔（无认证时任何人可读写全部配置）
④ 备份加密：snapshot 文件包含 Secret 明文 → 备份要加密存储、限制访问
⑤ 审计：开启访问日志，异常 member 变化（member add）立即告警
```

etcd 认证实操（示例）：

```shell
etcdctl user add root            # 创建 root 用户
etcdctl auth enable              # 开启认证（开启后所有操作要带 --user）
etcdctl role add app-reader
etcdctl role grant-permission app-reader read /registry --prefix
etcdctl user add app-user
etcdctl user grant-role app-user app-reader
# 验证：etcdctl --user app-user get /registry --prefix 可读；put 会被拒
```

### 2. Redis 安全

```text
本机教训（实测）：Redis 配了 requirepass 后，redis-cli ping 直接 NOAUTH ——
这正是"没配密码的 Redis 被公网扫描爆破"的防御前提。

① 必配 requirepass（强密码）+ masterauth（主从互连密码）
② 禁危险命令：rename-command FLUSHALL ""、rename-command KEYS ""（防扫描）
③ 绑定内网 IP（bind 127.0.0.1 或内网地址），禁止 0.0.0.0 裸奔
④ protected-mode yes（默认，公网无密码拒绝连接）
⑤ 主从复制账号最小权限（MySQL 同理：只授 REPLICATION SLAVE）
```

### 3. ZooKeeper / Consul

```text
ZooKeeper：默认无认证 → 至少配 digest 认证（addauth digest user:pass），
           端口 2181 别暴露公网；leader 选举端口 3888、数据同步 2888 仅内网
Consul：ACL 默认关闭 → 开启 acl { enabled = true }，token 管理；
        gossip 加密（encrypt 密钥），RPC 用 TLS
```

### 5. 分布式锁的安全细节

```text
① 锁 value 必须是唯一标识（UUID，如 e79680de-...，见"常用命令"实测），
   释放时校验，防止释放别人的锁
② 锁要带过期时间（防持有者崩溃死锁）+ 续租（长任务防锁提前过期）

```

## 故障排查

### 案例一：etcd 集群不可用（丢失 Quorum / 选举失败）

```shell
# 症状：应用报 etcd server: request timed out；kubectl 无响应
# 排查步骤：

# ① 各节点健康检查（哪台能通、哪台失联）
etcdctl endpoint health --endpoints=10.0.0.1:2379,10.0.0.2:2379,10.0.0.3:2379
# 输出里 unhealthy 的节点就是问题点

# ② 看成员与 leader
etcdctl endpoint status --write-out=table
# 若没有 IS LEADER=true 的节点 → 选举失败/未达成 Quorum

# ③ 看日志（选举超时、网络分区、磁盘 fsync 慢都会在这里）
journalctl -u etcd -n 100 --no-pager | grep -E 'leader|election|timeout|error'
# 常见报错：
#   "no leader elected"        —— 多数派未达成，集群只读
#   "failed to send out heartbeat" —— 网络问题
#   "apply request took too long"  —— 磁盘慢，fsync 卡顿

# ④ 检查网络与端口（peer 2380 是否互通）
ss -tlnp | grep 2380
ping -c 3 10.0.0.2 && nc -vz 10.0.0.2 2380

# ⑤ 磁盘性能（etcd 对 fsync 敏感）
iostat -x 1 | grep -E 'vda|sda'
```

**处理**：

```text
结论：3 节点挂 2 台（或网络分区成 1+2）→ 只剩 1 票凑不齐多数派 2 票，集群只读。
解法：恢复故障节点（重启/修网络）；如果是永久故障则 member remove 后用
     新节点 member add 替换（注意：先 remove 再 add，别直接加第 4 台）。
     极端情况（多数派全损）：用 snapshot 在新集群恢复（数据可能丢失一部分，
     这是 CP 系统的代价——保护的是「不给出错误数据」而非「不丢数据」）。
```

### 案例二：脑裂（Split Brain）与 fencing 失效

```text
典型场景：双节点 Keepalived/主备集群，心跳线（VRRP 专线）断了，
但业务网络还通 → 两个节点都认为对方死了，都抢 VIP → 双主同时写。

排查：
① 看 VIP 落在哪（ip addr show | grep 10.0.0.100，两个节点都有 = 已脑裂）
② 看心跳日志：keepalived 日志里 VRRP 状态反复 MASTER↔BACKUP 抖动
③ 查仲裁机制是否生效（有没有配置 quorum/fencing）

解法：
① 加仲裁节点（第三台 witness/票权节点）——2 节点集群必配，否则必然脑裂
② 配 fencing/STONITH：判定失联后强制断电故障节点（Pacemaker 场景必须）
③ 存储层兜底：共享存储用 SCSI-3 持久预留（PR），双写时第二个写者被存储拒绝
④ 恢复后人工裁决：以数据新的一方为准，旧方数据回滚/丢弃，别盲目合并
```

**本机相关**（单节点 etcd 无脑裂风险，但可以演示 Quorum 概念）：本机 etcd 是 1 节点，Quorum=1，任何时刻都有多数派，所以永远健康——这正是「1 节点无高可用」的注脚。

### 案例三：etcd 空间满（mvcc: database space exceeded）

```shell
# 症状：写请求报错
etcdserver: mvcc: database space exceeded

# 排查
docker exec etcd etcdctl endpoint status --write-out=table   # 看 DB SIZE
docker exec etcd etcdctl alarm list                          # 有 NOSPACE 告警
df -h /var/lib/etcd                                          # 磁盘是否满

# 处理（顺序很重要！）
etcdctl alarm disarm          # ① 先解除告警（此时只读保护解除）
etcdctl compact 123456        # ② 压缩历史版本（revision 之前的全删）
etcdctl defrag                # ③ 碎片整理，归还空间给文件系统
# 注意：defrag 是阻塞操作，低峰期做；3 节点要逐个节点做
# 根治：配 auto-compaction（periodic/1h）+ 监控 db size + 调大 quota-backend-bytes
```

### 案例四：Redis 主从切换后数据不一致 / 哨兵误判

```text
症状：主库没挂但哨兵触发切换（网络抖动导致），切完后部分数据"丢失"
原因：主从异步复制，从库落后主库；哨兵主观下线阈值（down-after-milliseconds）
     设太小，网络抖动即误判
排查：
  redis-cli info replication        # 看新主/从偏移量差距
  redis-cli info sentinel           # 哨兵视角的 leader 与 failover 次数
  redis-cli -p 26379 sentinel get-master-addr-by-name mymaster
解法：
① down-after-milliseconds 调大（如 30000），减少误判
② 对一致性敏感的数据不要只靠 Redis 主从（加 etcd 锁/双写补偿）
③ 切换后核对 repl offset，落后过多的从库做全量重同步
```

### 案例五：ZooKeeper 会话过期与 leader 选举抖动

```text
症状：客户端频繁报 Session expired；zkServer.sh status 显示 leader 反复变化
原因：客户端 GC 停顿/网络延迟超过 sessionTimeout（默认 40s 上限）；
     tickTime 与 sessionTimeout 配置不当
排查：
  zkServer.sh status                     # 看角色
  tail -f /var/log/zookeeper/zookeeper.out   # 看 election 日志
  jstack <zk_pid> | grep -A5 'quorum'    # 看是否有线程卡死
解法：
① 客户端合理设置 sessionTimeout（3~10 倍 tickTime）
② 服务端 tickTime 与集群网络状况匹配，避免跨机房部署
③ 监控 GC（ZooKeeper 是 Java，Full GC 会丢心跳）
```

### 排查通用套路

```text
① 先确认是「网络分区」还是「节点故障」：ping / nc 端口 / 看对端日志
② 再确认「仲裁是否达成」：member list / endpoint status / pcs status
③ 最后看「数据是否一致」：revision 对比、repl offset、binlog 位置
④ 一切恢复操作先备份（etcd snapshot save 永远最先做）
```

## 常见问题

Q1: 主从复制的延迟会导致什么问题？
A: 读从库可能读到旧数据（主已更新、从还没同步）。业务上表现为「刚下单查不到订单」「改了配置不生效」。解决：强一致读走主库、读写分离中间件配「写后读同路由」、或业务接受最终一致。

Q2: 主主复制为什么容易出问题？
A: 两个主都能写，并发写同一行会冲突（自增 ID 冲突、数据互相覆盖、删除互相打架）。实践中「双主」几乎都做成「逻辑单写」——写只进一个主，另一个主只是热备，靠复制保证两边数据一致，切换时才启用。

Q3: 强一致和最终一致怎么选？
A: 配置/元数据/协调/锁（etcd、ZooKeeper、注册中心）必须强一致，错了就是全局事故；数据量大、容忍短暂不一致（缓存、日志、feed、计数）用最终一致。判断标准：**读到的旧数据会不会造成业务损失**。

Q4: 分布式锁为什么要设过期时间？设了过期时间为什么还要续租？
A: 过期时间防止持有锁的节点崩溃导致锁永不释放（死锁）；但任务还没跑完锁就过期会被别人抢走，所以长任务要续租（看门狗自动续期）。两者结合：崩溃有兜底、运行不误伤。

Q5: 脑裂是怎么发生的？怎么防？
A: 网络分区 + 没有仲裁机制（或仲裁失效），两个分区各自选出主节点同时写数据。防：①奇数节点多数派仲裁（etcd/Raft 天然免疫）；②Fencing/STONITH 物理隔离失联节点；③共享存储加 SCSI-3 PR；④双节点集群必须加第三方仲裁节点。

Q6: 为什么 etcd 集群要奇数节点？4 节点不行吗？
A: 多数派投票机制下，4 节点的容错（1 台）与 3 节点相同，却可能被 2+2 分区整体打死（两边都凑不齐 3 票）；3 节点最多挂 1 台仍可用，1+2 分区时小分区自动降级、大分区 2 票正常工作。奇数节点保证任意分区都有一边是多数派。

Q7: etcd 的 watch 和 MySQL binlog 订阅有什么区别？
A: etcd watch 是「MVCC 版本号驱动的增量事件推送」，天然支持前缀/范围监听、断线续传（从指定 revision 恢复），是控制循环的基石；binlog 订阅（如 Canal）是「日志回放」思路，用于数据同步到异构存储。etcd watch 面向协调，binlog 面向复制。

Q8: Redis 主从和 Redis Cluster 是什么关系？
A: Cluster 是分片架构（16384 槽位分布到多主），每个分片内部仍是主从复制；主从+哨兵是「单分片高可用」。规模小用主从+哨兵，规模大（数据超单机内存/写超单机）用 Cluster。

## 面试题

1. **简述 CAP 定理，为什么分布式系统必须选 P？**
   答：CAP 指分布式系统在网络分区时无法同时保证一致性（C）、可用性（A）、分区容错性（P）。P 是必须选的，因为网络分区是客观存在（交换机故障、机房断网），无法假设网络永远可靠。真正的选择是分区时保 C（如 etcd，拒绝写）还是保 A（如 Cassandra，继续服务最终一致）。

2. **Raft 的 Leader 选举过程是怎样的？如何保证不会选出两个 Leader？**
   答：Follower 在选举超时（随机 150~300ms）内没收到心跳就自增任期转 Candidate，先投自己再广播 RequestVote；获得多数派选票即成为 Leader 并立即发心跳。不会双 Leader 的原因：①多数派投票——两个候选者不可能同时拿到多数票（多数派必有交集）；②每任期每个节点只投一票；③随机超时打破平票僵局；④旧 Leader 复活后因任期过期被拒绝。

3. **etcd 怎么保证写不丢失？写请求的完整路径是什么？**
   答：写请求 → Leader 追加本地日志（WAL fsync）→ 并行复制到 Follower → 多数派确认 → 标记已提交 → 返回客户端成功。只要返回成功，该日志就一定存在于多数派节点上，即使部分节点宕机也不会丢；新 Leader 选举时会校验日志新旧（term/index），保证已提交条目不丢失。

4. **说说 Paxos 和 Raft 的区别，为什么 Raft 更流行？**
   答：两者都是多数派共识算法，正确性等价。Paxos 理论最早（1990）但实现复杂、难以理解，工程实现差异大；Raft 通过强领导者模型（写必须经 Leader）、显式任期选举、日志复制三阶段拆分，把共识算法变得可教学、可工程化。因此 etcd、consul、TiKV、K8s 等现代系统都选 Raft，Paxos 主要在 Google Chubby 和学术领域。

5. **什么是脑裂？如何用 Quorum 和 Fencing 防止？**
   答：脑裂是网络分区导致两个分区同时出现主节点、同时写数据。Quorum 防止：写必须多数派确认，分区后只有多数派分区能写，少数派自动降级（etcd 丢失 Quorum 直接拒写）。Fencing 兜底：仲裁判定失联后物理隔离故障节点（STONITH 断电），防止其复活后带旧状态写共享存储。两者配合才能根治。

6. **Kubernetes 为什么选 etcd 而不是 ZooKeeper 做配置存储？**
   答：①etcd 原生 MVCC + watch，revision 版本号正好支撑 K8s 的 resourceVersion 乐观并发与声明式控制循环；②gRPC 协议与 K8s（Go 语言）天然契合；③Raft 实现简单可靠、运维成本低、社区活跃；④etcd 支持 lease（选主/锁）与 TTL，API Server 多副本选主直接可用。ZooKeeper 的 ZAB 侧重顺序广播，watch 是一次性的（需重复注册），集成成本更高。

7. **设计一个分布式锁，如何保证互斥、防死锁、防误删？**
   答：互斥用原子抢占（Redis SET NX / etcd 带 lease 的 PUT / ZK 临时节点）；防死锁用 TTL/lease 过期自动释放 + 持有者崩溃兜底；防误删用唯一标识（UUID）作为锁 value，释放时校验匹配才删（Redis 用 Lua 保证原子）；长任务用看门狗续租。极端可靠性场景（防超卖）建议 etcd 实现而非 Redis（Redis 主从切换可能丢锁）。

8. **集群 3 节点和 5 节点怎么选？7 节点有必要吗？**
   答：3 节点容忍 1 台故障，满足绝大多数生产需求（K8s 控制面默认 3 副本）；5 节点容忍 2 台故障，用于更大规模或需要滚动升级期间仍有冗余的场景；7 节点以上成本高、收益低，几乎没必要——跨机房部署时 5 节点按 2-2-1 分布是最优形态（任意单机房故障仍可凑齐 3 票多数派）。

## 最佳实践与踩坑记录

### 最佳实践

1. **强一致集群（etcd/ZooKeeper）用奇数节点（3/5）**，多数派决策，容量规划按「容忍 (N-1)/2 故障」计算。
2. **配置/元数据/锁用强一致（Raft），大数据高吞吐用最终一致（异步复制）**——别用 etcd 存日志和埋点。
3. **etcd 必配 auto-compaction + 监控 db size**，否则历史版本膨胀会触发只读保护。
4. **etcd 备份常态化**：cron 定时 `etcdctl snapshot save`，备份异地存储，恢复前先演练。
5. **分布式锁三件套**：过期时间 + 唯一标识（释放校验）+ 续租看门狗。
6. **主从复制监控延迟**：MySQL `Seconds_Behind_Master`、Redis `master_repl_offset` 差值，延迟超阈值告警。
7. **集群通信全链路加密 + 认证**：etcd TLS + user/role、Redis requirepass + masterauth、consul ACL，端口仅对内网开放。
8. **滚动升级守则**：一次一个节点，升级完等它 catch up（endpoint health + 日志无滞后）再动下一个。
9. **脑裂预案要演练**：定期做网络分区演练（切断某节点网卡），验证 Quorum 与 fencing 是否真的生效。

### 踩坑记录

坑 1：偶数节点集群脑裂选不出主
结论：4 节点 etcd，2 节点挂掉后集群直接不可用。
原因：偶数节点 + 多数派（>2 需 3 票），2 台故障后只剩 2 票无法过半；且 2+2 网络分区时两边都凑不齐 3 票。
解法：奇数节点（3/5/7），容忍 (N-1)/2 台故障；跨机房用 5 节点 2-2-1 分布。

坑 2：分布式锁没设过期时间，持有者崩溃导致死锁
结论：持有锁的节点宕机，锁永不释放，所有抢锁方永久阻塞。
原因：没设锁 TTL，节点崩溃后锁残留。
解法：锁设过期时间（Redis EX / etcd lease / ZK 临时节点会话断开自动删除），长任务配续租看门狗。

坑 3：释放锁没校验标识，把别人的锁删了
结论：A 的锁过期后 B 抢到锁，A 的清理逻辑执行 DEL，把 B 的锁删了，B 的互斥失效。
原因：释放时只按 key 删除，没有校验 value 是不是自己的。
解法：锁带唯一 UUID value，释放用 Lua 脚本校验「值匹配才删」（或 etcd 的 revision 比较删除），保证原子性。

坑 4：主从延迟导致读到旧数据，业务出 bug
结论：主库写入成功后，应用从从库读到的还是旧值，用户看到数据"消失"。
原因：异步复制有延迟，从库数据滞后（网络抖动、从库机器弱、大事务）。
解法：强一致读走主库；读写分离中间件配写后读路由；监控延迟并告警；关键业务接受不了就上强一致存储。

坑 5：强一致集群用于高频写入，性能雪崩
结论：用 etcd 存高频业务数据，写延迟高、Leader 成瓶颈，集群被打挂。
原因：强一致要多数派确认 + WAL fsync，写吞吐远低于单机；Leader 单点串行复制。
解法：高频大数据用异步复制（MySQL/Redis 主从、消息队列），强一致只用于配置/元数据/锁。

坑 6：etcd 不配 auto-compaction，数据库无限膨胀触发只读
结论：运行几个月后写请求报 `mvcc: database space exceeded`，集群进入只读保护，业务全挂。
原因：etcd 保留所有历史版本（MVCC），没人压缩 + 磁盘配额打满。
解法：配 `--auto-compaction-mode=periodic --auto-compaction-retention=1`；已满时按顺序 alarm disarm → compact → defrag（逐个节点、低峰期）。

坑 7：2 节点高可用集群没配仲裁，心跳断线必脑裂
结论：Keepalived 双机心跳线断开，两台都抢 VIP 变成双主，共享数据被两边写坏。
原因：2 节点没有多数派概念，没有任何仲裁机制判断谁该活。
解法：双节点必须加第三方仲裁（witness 节点/票权）；或直接上 3 节点 Raft 集群；数据层配 fencing（STONITH/SCSI PR）兜底。

坑 8：Redis 主从切换丢锁/丢数据，被"Redis 分布式锁很可靠"误导
结论：用 Redis SETNX 做防超卖锁，主库挂掉切换后新主没有锁记录，两个请求同时进临界区，超卖。
原因：Redis 主从是异步复制，锁记录可能还没复制到从库；主从切换后锁"消失"。
解法：对锁可靠性要求极高用 etcd/ZooKeeper 实现；用 Redis 则接受极小概率失效，或配 RedLock（仍有争议）；业务侧做幂等兜底（数据库唯一约束）。

坑 9：etcd 升级/扩容顺序错误，直接 member add 把集群搞坏
结论：某节点永久故障，未 remove 就直接 member add 新节点，集群成员数变成 4，Quorum 计算混乱。
原因：etcd 成员管理必须先 remove 故障成员再 add 新成员，节点数变化要维持奇数。
解法：`etcdctl member remove <id>` → 新机器配好启动 → `etcdctl member add <name> --peer-urls=...`；每步验证 member list 与 endpoint health。
