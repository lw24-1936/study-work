## 概述

集群与一致性解决「多节点协同工作 + 数据一致」：主从复制（一主多从，读扩展）、主主复制（双主，双向同步）、共享存储集群（多节点共享同一存储）、分布式锁（协调多节点互斥访问）。核心难点是「一致性」——多节点数据如何保持一致（强一致 vs 最终一致）。数据库集群（主从）、缓存集群、分布式协调（etcd/ZooKeeper）都建立在这些概念上。

```text
# 实测（本机跑着 etcd，分布式一致性 KV）
$ ss -tlnp | grep 2379
LISTEN 0.0.0.0:2379  docker-proxy   # etcd（容器），2379 客户端端口
# etcd 用 Raft 共识算法保证多节点强一致
```

## 核心概念

1. **主从复制（master-slave）**：一个主（写）+ 多个从（读，同步主的数据）。写走主，读走从（读扩展）。主挂了从提升为主（配合高可用）。
2. **主主复制（master-master）**：两个都是主，双向同步。理论上都能写，但冲突处理复杂（通常还是「逻辑上一主一写」）。
3. **共享存储集群**：多节点共享同一存储（NFS/共享磁盘），数据在共享存储上，节点无状态。
4. **分布式锁**：多节点互斥访问共享资源，保证同一时刻只有一个节点操作（防止并发冲突）。
5. **一致性模型**：强一致（所有节点读到一样的数据，如 Raft/Paxos）、最终一致（短暂不一致后收敛，如异步复制）。

```text
核心概念：
主从复制（读写分离）+ 主主复制（双活）+ 共享存储（数据集中）+ 分布式锁（互斥协调）
一致性：强一致（Raft/Paxos）vs 最终一致（异步复制）
```

## 工作原理

**主从复制**：主库写数据 → 生成 binlog → 从库拉取 binlog → 回放（数据同步到从库）。异步（主不等从确认）或半同步（等至少一个从确认）。读写分离：写走主、读走从。

**一致性（Raft 共识，etcd 用）**：集群选举一个 leader，所有写都经 leader，leader 把写复制到多数派（过半节点）确认后才提交。这样「多数派一致」保证强一致——即使少数节点挂了，多数派仍能达成一致。

**分布式锁**：多个节点抢锁（如 Redis SETNX / etcd 租约 / ZooKeeper 临时节点），抢到的持有锁执行操作，其他节点等待。要处理「锁过期、锁释放」等边界问题。

```text
主从复制：主写 binlog → 从拉取回放 → 数据同步（异步/半同步）

Raft 共识（etcd）：
选 leader → 写经 leader → 复制到多数派 → 确认后提交 → 强一致

分布式锁：
抢锁 → 持有执行 → 释放（注意锁超时/续租）
```

## 常用命令与配置

```shell
# etcd 集群操作（本机有 etcd）
etcdctl member list            # 集群成员
etcdctl endpoint health        # 各节点健康
etcdctl put foo bar            # 写（经 leader）
etcdctl get foo                # 读
etcdctl endpoint status --write-out=table   # 看 leader 是谁

# Redis 主从（示例）
redis-cli info replication     # 看主从角色
redis-cli replicaof 主IP 6379  # 设为某主的从

# MySQL 主从（示例）
mysql -e "SHOW SLAVE STATUS\G" # 从库同步状态
mysql -e "SHOW MASTER STATUS"  # 主库 binlog 位置
```

```text
集群常用命令：
etcdctl member list / endpoint health  查集群成员和 leader
redis-cli info replication            查主从角色
SHOW SLAVE STATUS                     查 MySQL 从库同步
```

## 配置文件解析

etcd 集群配置（本机 etcd 场景，容器内 /etc/etcd/etcd.yml）：

```yaml
# etcd 集群配置关键项
name: etcd-node1                    # 节点名
data-dir: /var/lib/etcd             # 数据目录
listen-client-urls: http://0.0.0.0:2379     # 客户端端口
listen-peer-urls: http://0.0.0.0:2380       # 集群内通信端口
initial-cluster: |
  etcd-node1=http://10.0.0.1:2380,   # 集群成员列表
  etcd-node2=http://10.0.0.2:2380,
  etcd-node3=http://10.0.0.3:2380
initial-cluster-state: new           # new=新集群 existing=加入已有集群
```

```text
关键字段：
listen-client-urls  客户端端口（2379，应用连这个）
listen-peer-urls    节点间端口（2380，Raft 通信）
initial-cluster     集群成员列表（所有节点）
cluster-state       new（新建）/ existing（加入）
```

## 应用场景实战

### 场景一：MySQL 主从 + 读写分离

```text
架构：
主库（写）── binlog ──→ 从库1（读）
                    └─→ 从库2（读）
应用：写走主库，读走从库（负载均衡/路由中间件分发）

配置：
1. 主库开 binlog（log_bin=on，server-id=1）
2. 从库 server-id=2，CHANGE MASTER 指向主库
3. 从库 START SLAVE，同步主库数据
4. 应用层读写分离
```

### 场景二：分布式锁（Redis 实现）

```text
# 抢锁
SET lock_key unique_value NX EX 30   # NX=不存在才设，EX=30秒过期
# 释放锁（Lua 保证原子：值匹配才删）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
# 用途：定时任务防重复执行、库存扣减防超卖、分布式协调
```

## 性能与调优

```text
1. 主从延迟 —— 半同步复制（等从确认）降低延迟但影响写性能；异步快但可能丢数据
2. 读写分离 —— 从库分担读压力，但要注意「主从延迟」导致读旧数据
3. 一致性开销 —— 强一致（Raft 等多数派）写性能低于单机，适合配置/元数据（etcd），不适合高频大数据
4. 分布式锁 —— 锁粒度要细（别一把大锁），锁超时要合理（避免死锁 vs 提前释放）
```

## 安全与权限

```text
1. 集群通信加密 —— etcd 的 peer 通信配 TLS，防止 Raft 消息被窃听/篡改
2. 认证 —— etcd 配 client 证书认证（--client-cert-auth），别裸奔
3. 主从复制账号 —— MySQL 从库复制账号最小权限（只给 REPLICATION SLAVE）
4. 分布式锁 —— 锁要带唯一标识（value），释放时校验，防「释放别人的锁」
```

## 故障排查

### 主从同步延迟/中断

```shell
# MySQL 从库看同步状态
mysql -e "SHOW SLAVE STATUS\G" | grep -E 'Slave_IO_Running|Slave_SQL_Running|Seconds_Behind_Master'
# 两 Running 都是 Yes 且 Seconds_Behind_Master 不大 = 正常
# No = 同步中断，看 Last_Error 报错
```

### etcd 集群 leader 选举异常

```shell
# 看集群健康
etcdctl endpoint health
# 看谁是 leader
etcdctl endpoint status --write-out=table
# 看日志（选举/网络问题）
journalctl -u etcd -n 50
```

## 常见问题

```text
Q1: 主从复制的延迟会导致什么问题？
A: 读从库可能读到旧数据（主已更新、从还没同步）。解决：强一致读走主库，或接受最终一致。

Q2: 主主复制为什么容易出问题？
A: 两个主都能写，并发写冲突难处理（自增 ID 冲突、数据覆盖）。实践中常「双主但逻辑单写」。

Q3: 强一致和最终一致怎么选？
A: 配置/元数据/协调（etcd）要强一致；数据量大、容忍短暂不一致（缓存、日志）用最终一致。

Q4: 分布式锁为什么要设过期时间？
A: 防止持有锁的节点挂了导致锁永不释放（死锁）。过期时间 + 续租机制（看门狗）。
```

## 面试题

```text
1. 主从复制和主主复制的区别？
   答：主从一写多读（读写分离、读扩展），主主双向写（双活，但冲突复杂）。

2. Raft 怎么保证一致性？
   答：选举 leader，写经 leader 复制到多数派，过半确认才提交。多数派一致保证即使少数节点挂也能达成一致。

3. 分布式锁的实现要点？
   答：原子抢锁（SET NX）、唯一标识（防释放别人的锁）、过期时间（防死锁）、续租（长任务）。

4. 为什么多数派（过半）能保证强一致？
   答：任意两个多数派必有交集，所以「已提交的写」一定被至少一个节点记住，不会丢失。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 强一致集群（etcd）用奇数节点（3/5），多数派决策
2. 配置/元数据用强一致（Raft），大数据量用最终一致
3. 分布式锁设过期时间 + 唯一标识 + 续租（看门狗）
4. 主从复制监控同步延迟（Seconds_Behind_Master）
5. 集群通信配 TLS 加密 + 认证，别裸奔

### 踩坑记录

```text
坑 1：偶数节点集群脑裂选不出主
结论：4 节点 etcd，2 节点挂后集群不可用。
原因：偶数节点 + 多数派（>2 需 3 票），2 挂只剩 2 无法过半。
解法：奇数节点（3/5/7），容忍 (n-1)/2 节点挂。

坑 2：分布式锁没设过期时间，死锁
结论：持有锁的节点挂了，锁永不释放，其他节点全卡住。
原因：没设锁过期，节点崩溃后锁残留。
解法：锁设过期时间（EX），长任务配续租（看门狗自动续期）。

坑 3：释放锁没校验标识，释放了别人的锁
结论：A 的锁过期了 B 抢到，A 又来释放，把 B 的锁删了。
原因：释放时只按 key 删，没校验是不是自己持有。
解法：锁带唯一 value，释放用 Lua 校验「值匹配才删」。

坑 4：主从延迟导致读旧数据
结论：主库写入后，从库读到的还是旧值。
原因：异步复制有延迟，从库数据滞后。
解法：强一致读走主库，或接受最终一致（配合业务容忍度）。

坑 5：强一致集群用于高频写入，性能差
结论：用 etcd/Raft 存高频写数据，写性能差。
原因：强一致要多数派确认，写延迟高，不适合高频大数据。
解法：高频大数据用异步复制（主从/缓存），强一致只用于配置/元数据。
```
