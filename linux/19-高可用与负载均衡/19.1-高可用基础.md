## 概述

高可用（High Availability，HA）指「系统通过**冗余**和**故障转移**，把停机时间压缩到业务可容忍的范围，持续对外提供服务」。核心目标是**消除单点故障（SPOF）**——任何一台机器、一块网卡、一条链路挂了，服务都不能中断。高可用不是「不坏」，而是「坏了能快速恢复且用户无感知」。

高可用的四个关键机制：

1. **心跳（Heartbeat）**：节点间定期互发探测包，检测对方存活状态。
2. **冗余（Redundancy）**：多副本部署（主备/多活），一个挂了另一个顶上。
3. **仲裁（Quorum）**：出现分歧（如网络分区）时按多数派裁决，防止「双主」。
4. **故障转移（Failover）**：主节点故障时自动把服务、VIP、资源切换到备节点。

```text
高可用核心目标：消除单点故障（SPOF），任何单点挂了服务不中断
设计四原则：消除单点 + 快速检测 + 快速切换 + 自动化（无人值守）
```

## 核心概念

高可用围绕以下几个核心概念展开：

1. **可用性指标（几个 9）**：可用性 = 正常运行时间 ÷ 总时间。业界用「9 的个数」衡量，每个 9 对应一年内允许的停机时间：

| 可用性 | 一年停机时间 | 对系统的要求 |
|--------|-------------|-------------|
| 99%    | 87.6 小时（3.65 天） | 常规运维，可接受计划内维护 |
| 99.9%（三个 9） | 8.76 小时 | 允许重启恢复，需快速响应 |
| 99.99%（四个 9） | 52.6 分钟 | 必须自动故障转移 |
| 99.999%（五个 9） | 5.26 分钟 | 全冗余 + 自动恢复 + 完善监控演练 |
| 99.9999%（六个 9） | 31.5 秒 | 电信级，代价极高，普通业务用不起 |

2. **单点故障 SPOF（Single Point of Failure）**：系统中「挂了就整体不可用」的节点。典型 SPOF 清单：电源、网卡、交换机、链路、网关、主机、存储、数据库、负载均衡器、DNS、证书过期、人（唯一会操作的人休假）。高可用的第一步永远是「画架构图，圈出所有单点」。

3. **冗余（Redundancy）**：为每个 SPOF 准备副本。分四个层面：**硬件冗余**（双电源/双网卡/RAID）、**网络冗余**（双链路/多运营商/ECMP）、**服务冗余**（主备/多副本部署）、**数据冗余**（主从复制/多副本存储/备份）。

4. **MTBF / MTTR 与可用性公式**：**MTBF**（Mean Time Between Failures，平均无故障时间）= 总运行时间 ÷ 故障次数，衡量「多容易坏」；**MTTR**（Mean Time To Repair，平均修复时间）= 总修复时间 ÷ 故障次数，衡量「坏多久能修好」。可用性 = MTBF ÷ (MTBF + MTTR)。例：MTBF = 100 天、MTTR = 1 小时（约 0.042 天），可用性 = 100 / 100.042 ≈ 99.96%。**想提升可用性：要么提高 MTBF（换硬件/加冗余），要么降低 MTTR（自动化切换/监控告警），后者成本通常低得多。**

5. **故障转移 Failover / 故障恢复 Failback**：Failover 是主节点故障时把服务自动切到备节点；Failback 是主节点恢复后把服务切回来。按是否自动分「自动切换」和「手动切换」；按主恢复后是否抢回分「抢占式（preempt）」和「非抢占式（nopreempt）」。

6. **Active-Active vs Active-Standby**：**Active-Standby（主备）**：一台干活一台待命，切换简单但备机闲置浪费；**Active-Active（双活/多活）**：所有节点同时对外服务（DNS 轮询、LVS、数据库多写），利用率高但需要处理并发冲突、会话一致性、脑裂风险更大。选型原则：业务简单选主备，追求资源利用率且能处理一致性选双活。

7. **健康检查（Health Check）**：主动探测节点/服务是否健康的机制，是故障检测的依据。探测层级：机器（ping）→ 端口（TCP connect）→ 应用（HTTP 状态码/响应内容）→ 业务逻辑（脚本模拟真实请求）。

8. **脑裂（Split-Brain）**：网络分区时，主备都收不到对方心跳，都认为对方挂了，于是**同时接管资源（如都抢 VIP、都做写入）**，造成数据冲突。脑裂是高可用系统最危险的故障，**宁可短暂不可用，不可双主**。

9. **仲裁（Quorum）**：出现分歧时的裁决机制，常见「多数派投票」：奇数节点集群（3/5/7），需要超过半数节点存活才能对外服务，少数派自动降级/停止服务，从机制上杜绝双主。

10. **优雅降级（Graceful Degradation）**：资源不足时主动关闭非核心功能，保住核心服务（如缓存集群挂掉后直连数据库但限流，搜索不可用但下单可用），是「可用性」与「完整性」的权衡。

11. **RPO / RTO**：容灾指标。**RPO**（Recovery Point Objective）= 最多能丢多少数据（如 5 分钟，对应同步/异步复制的选择）；**RTO**（Recovery Time Objective）= 多久必须恢复业务（如 30 分钟，对应自动切换还是手动切换）。**HA 解决 RTO（快速恢复），备份/复制解决 RPO（少丢数据）**，两者互补：高可用 ≠ 灾备，高可用防「节点故障」，灾备防「机房级灾难」。

```text
可用性公式速记：
可用性 = MTBF / (MTBF + MTTR) ≈ 1 - MTTR/MTBF
提升路径：加冗余提高 MTBF（贵），自动化切换降低 MTTR（便宜）
```

## 工作原理

高可用的完整闭环是「**检测 → 切换 → 接管 → 恢复**」四步循环：

```text
故障转移时序（以双机主备 + VIP 为例）：
T0  主节点故障（宕机/断网/服务挂）
T1  心跳超时：备节点连续 N 次（如 3 次 × 1s）没收到主的心跳 → 判定故障   [检测]
T2  备节点提升角色，绑定 VIP，发免费 ARP 宣告新 MAC                    [切换]
T3  交换机/客户端学习新 MAC，新连接打到新主，服务接管                    [接管]
T4  主节点修复后重启，按策略抢回或保持（nopreempt）                     [恢复]
目标：T0→T3 全自动，且 T3-T0 < 业务容忍时间（如 <10s）
```

1. **心跳检测原理**：主备通过专用心跳线或网络定期互发探测包（VRRP 通告、TCP ping、自定义报文）。心跳间隔通常 1~3 秒；连续 N 次未收到 = 判对方故障。**检测时间 = 心跳间隔 × 失败次数**：间隔 1s × 3 次 = 3 秒检出。

2. **故障判断的难点**：收不到心跳有两种可能——**机器真挂了** 或 **网络分区了（机器还活着但网络断了）**。若不加区分直接切换，就可能出现脑裂。业界手段：**仲裁节点**（引入独立的第三方观察者）、**fencing（隔离）**（确认接管前先把疑似故障节点物理隔离——断网/断电/STONITH，防止它复活后继续写共享资源）、**多路径心跳**（心跳走双链路，两条都断才判挂）。

3. **健康检查类型对比**：

| 探测方式 | 检测层级 | 优点 | 缺点 | 典型实现 |
|---------|---------|------|------|---------|
| ICMP ping | 机器可达性 | 简单、开销小 | 机器活着但服务挂了也判正常 | keepalived 无内置 ping，靠脚本 |
| TCP 端口 | 服务监听 | 覆盖「进程没起/端口没监听」 | 端口监听 ≠ 应用可用 | HAProxy `option tcp-check` |
| HTTP 状态码 | 应用层 | 覆盖业务入口 | 只验入口不验依赖 | HAProxy `httpchk`、curl 脚本 |
| 业务脚本 | 业务逻辑 | 最真实（查依赖、验数据） | 脚本本身要健壮，别把脚本 bug 当故障 | keepalived `vrrp_script`、consul 健康检查 |

4. **脑裂的成因与防线**：

```text
成因：网络分区（交换机故障/心跳线断/防火墙拦截心跳）→ 主备互相失联 → 双双接管
防线（从机制到实现）：
1. 仲裁 Quorum：奇数节点多数派投票，少数派自动降级（etcd、Pacemaker 的 quorum）
2. Fencing/STONITH：接管前先物理隔离对方（断电/断网），防复活后数据冲突
3. 多路径心跳：心跳走独立网卡 + 业务网双通道，降低误判
4. 防脑裂协议本身：如 VRRP 的 priority/抢占规则、主备共享存储的锁
5. 监控兜底：检测到双主立即告警 + 人工介入
```

5. **高可用的层次**：**主机层**（双机热备、集群）、**网络层**（VIP 漂移、双链路、ECMP）、**应用层**（无状态多副本 + 负载均衡、有状态靠会话复制/一致性）、**数据层**（主从复制、共享存储、分布式存储）。层次越低故障越常见（网卡/电源 > 主机 > 应用 bug），但层次越高切换越复杂。**实际方案往往是多层组合**：网络层 VIP 漂移（秒级）+ 数据层主从复制（保数据）+ 应用层无状态设计（随便切）。

```text
检测时间公式：T_检测 = 心跳间隔 × 失败次数
切换时间公式：T_切换 = T_检测 + T_角色提升 + T_资源接管（绑 VIP + ARP 宣告）+ T_服务就绪
```

## 常用命令与配置

高可用本身没有统一的命令，但排查和验证 HA 状态有固定套路。以下「实测」为本机真实输出，「示例」为需在 HA 环境执行的命令。

```shell
# ---------- 看本机网卡与地址（判断 VIP 归属：VIP 在哪个节点谁就是主）----------
ip -br addr                    # 实测：wlp0s20f3 UP 192.168.1.167/24，enp59s0 DOWN
ip addr show | grep <VIP>      # 精确查 VIP 在不在本机

# ---------- 看路由与网关 ----------
ip route show                  # 实测：default via 192.168.1.1 dev wlp0s20f3
ping -c 2 -W 2 <网关IP>        # 实测：0% packet loss，rtt ~1.4-2.1ms

# ---------- 看服务监听（健康检查对象）----------
ss -tlnp                       # 实测：nginx :80、sshd :22、MySQL :3306、Redis :6379
systemctl status nginx         # 实测：active (running)，nginx/1.24.0

# ---------- 心跳与集群相关 ----------
journalctl -u keepalived -f    # 示例：Keepalived 切换日志（本机未安装）
etcdctl member list            # 示例：etcd 集群成员
etcdctl endpoint health        # 示例：etcd 各节点健康
```

```shell
# 模拟故障转移演练（以 keepalived 双机为例）
# 1. 记录当前 VIP 归属
ip addr show | grep 192.168.1.100
# 2. 停主节点 keepalived（或直接关机模拟宕机）
systemctl stop keepalived
# 3. 到备节点确认 VIP 已漂移过来（应在 3~5 秒内）
ip addr show | grep 192.168.1.100
# 4. 验证服务可用（访问 VIP）
curl -I http://192.168.1.100/
```

```text
HA 设计要点（配置层面）：
1. 心跳间隔 1~3 秒 —— 太短误判、太长切换慢
2. 失败次数 2~3 次 —— 与间隔相乘得到检测时间，按业务容忍度定
3. 仲裁 —— 奇数节点（3/5/7），多数派决策
4. fence —— 故障节点必须能「隔离」（断电/STONITH），防它继续写
5. 演练 —— 上线前、每季度停主验证，切换能力是「练」出来的
```

## 配置文件解析

HA 的「配置」散落在各组件：keepalived.conf（VIP 漂移）、systemd unit（服务托管）、集群软件（etcd/Pacemaker）。以 Keepalived 为例解析核心字段（完整见 [[19.2-Keepalived 与 VRRP]]）：

```ini
# /etc/keepalived/keepalived.conf 关键段
vrrp_instance VI_1 {
    state MASTER            # 角色：MASTER 主 / BACKUP 备（仅初始角色）
    interface eth0          # VIP 绑定的网卡（务必选心跳可达的物理网卡）
    virtual_router_id 51    # VRRP 组 ID（主备必须一致）
    priority 100            # 优先级（高的为主，备通常 90）
    advert_int 1            # 心跳间隔（秒）
    authentication {        # 心跳认证（防伪造 VRRP 包）
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
        192.168.1.100/24    # 虚拟 IP（VIP，故障时漂移的地址）
    }
    track_script {
        chk_nginx           # 健康检查：nginx 挂了降优先级触发切换
    }
}
```

```text
字段含义：
state            MASTER/BACKUP，只是初始角色，实际主从由 priority 决定
priority         优先级，高者持 VIP（主 100 / 备 90，必须不同）
advert_int       心跳通告间隔，主备必须一致
virtual_ipaddress VIP，主节点持有，故障时漂移到备
track_script     健康检查联动，服务挂了自动降级触发切换
```

高可用「配置」的另一半是**服务托管**：用 systemd 保证进程崩溃自拉起（[[10.3-编写 Service Unit]] 的 `Restart=always`），与 HA 的节点级切换互补——**进程级故障交给 systemd，节点级故障交给 keepalived/集群**，别都堆在一个层面。

## 应用场景实战

### 场景一：双机主备（Keepalived + Nginx，秒级切换）

```text
架构：
192.168.1.10（主 nginx，priority 100）──VIP 192.168.1.100── 对外服务
192.168.1.11（备 nginx，priority 90） ──主挂 3s 内接管 VIP──

实施步骤：
1. 两台机器装 nginx + keepalived，nginx 配置一致
2. 主 keepalived.conf：state MASTER + priority 100 + VIP 192.168.1.100/24
3. 备 keepalived.conf：state BACKUP + priority 90 + 相同 VIP/组 ID
4. 启动 keepalived，验证 VIP 在主节点（ip addr show | grep 192.168.1.100）
5. 演练：systemctl stop keepalived（主）→ 备节点 3~5s 内持 VIP → curl 访问 VIP 仍 200
6. 配 track_script 检测 nginx 进程，nginx 挂了同样触发切换
适用：网关、负载均衡器、入口反代等无状态或有状态可控的入口组件
```

### 场景二：数据库高可用（VIP + 主从复制）

```text
架构：MySQL 主从复制（数据冗余）+ VIP 漂移（服务冗余）
192.168.1.10（MySQL 主，持有 VIP 192.168.1.200）  ← 客户端连 VIP
192.168.1.11（MySQL 从，半同步复制，备机）

关键点：
1. 数据层切换比入口层复杂：切换前要保证「数据不丢或丢得可控」
   半同步复制（RPO≈0）> 异步复制（可能丢几秒数据）
2. 主挂后：从库补齐 binlog → 提升为主 → 抢 VIP → 业务重连
3. 原主恢复后不能直接加回（防止双写）：先作为从库补齐数据再归队
4. 这类切换通常配合脚本/Orchestrator 做「数据补 + 角色提升」两步，
   不能只靠 keepalived 裸切——裸切可能导致「原主复活后双主写库」
```

### 场景三：三节点仲裁集群（etcd / 分布式锁，多数派裁决）

```text
架构：3 节点 etcd（奇数节点 = 天然仲裁）
node1 node2 node3 —— 任意 2 个存活即可对外（多数派 2/3）

价值：
1. 分布式锁：多个业务节点抢锁，锁协调者挂了不会脑裂（锁在 quorum 里）
2. 配置/选主协调：配合控制器做「谁该是主」的裁决，天然防脑裂
3. 与双机主备对比：双机是「2 选 1 无仲裁」，3 节点是「3 票选 2」——
   网络分区时少数派（1 节点）自动降级，不会出现双主

注意：etcd 本身也要 HA！etcd 3 节点里挂 2 个，集群就不可用了。
```

### 场景四：公有云负载均衡（SLB/ALB）替代自建 HA

```text
背景：自建 keepalived 在公有云 VPC 里常因组播被禁而受限
方案：
1. 用云厂商 SLB/ALB（四层/七层负载均衡）：本身多可用区冗余，天生 HA
2. 后端挂多台 ECS，SLB 自动摘除故障后端（健康检查）
3. 数据库用云 RDS：主备切换由云平台托管，业务只连连接串
4. 混合：入口用云 LB，内部自建集群用 keepalived 单播模式（见 19.2）

取舍：云 LB 免运维但贵、功能受限；自建 HA 灵活但运维成本高。
```

### 场景五：判断系统是否需要高可用（决策表）

```text
问三个问题：
1. 有单点故障吗？—— 单机部署的数据库/LB/网关/核心服务 = 有
2. 挂了影响多大？—— 核心交易（钱/用户数据）vs 内部工具（报表）
3. 能容忍多久？  —— 分钟级（手动切换）vs 秒级（自动切换）

决策：
内部工具/实验环境   —— 不做 HA，做好备份
一般业务           —— 入口双机 + 数据主从（99.9%~99.99%）
核心交易           —— 全链路冗余 + 自动切换 + 演练（99.99%+）
记住：HA 是成本，只有「停机损失 > HA 成本」才值得上
```

## 性能与调优

```text
1. 切换时间是核心指标：T = 心跳间隔 × 失败次数 + 接管时间
   例：1s × 3 + 绑 VIP/ARP 0.5s ≈ 3.5s
   要更快：advert_int 0.5s（但误判风险↑）；要更稳：失败次数 3~5
2. 心跳开销：心跳包很小（VRRP 通告约几十字节），但太频繁（<0.5s）
   在弱网/无线环境（如本机 wlp0s20f3 WiFi）抖动大，易误判——
   HA 心跳建议走有线独立网卡
3. 健康检查开销：探测频率与脚本复杂度直接吃 CPU/连接数；
   脚本里别做重活（如每次都 curl 大页面），interval 2~5s 合适
4. 备机利用率：Active-Standby 备机闲置是浪费，方案：
   - 双 VIP 互为主备（两台各持一个 VIP，互为对方的备，见 19.2）
   - 备机跑只读副本/离线任务（注意别把备机打挂）
5. 容量规划：HA 集群按「N+1」规划（1 台冗余），平时负载建议 <50%，
   保证单节点故障后剩余节点扛得住（双机场景 <50%，三机 <66%）
6. 故障检测时间的极致优化：监控告警也要快（秒级采集），
   别等用户报障才发现切换了
```

```text
调优核对表：
□ 心跳间隔 × 失败次数 ≤ 业务容忍时间
□ 切换后服务就绪时间（nginx 预热/连接池）已纳入总切换时间
□ 备机已做「切换演练」验证（不演练等于没有 HA）
□ 双活场景已处理会话一致性与数据冲突
```

## 安全与权限

```text
高可用安全要点：
1. 心跳认证 —— VRRP 等协议加认证（auth_pass），防止伪造心跳包
   把主节点挤下线（典型攻击：伪造高优先级 VRRP 通告抢 VIP）
2. 心跳网络隔离 —— 心跳走独立网卡/VLAN，与业务流量隔离：
   业务拥塞不会误判心跳；攻击者也不容易顺着业务网打心跳
3. fencing 权限 —— 隔离故障节点的操作（断电/STONITH）必须强管控，
   只给运维 root/专门管理口，防止误操作把健康节点给 fence 了
4. 仲裁节点安全 —— 仲裁节点（etcd/consul）是「最终裁决者」，
   要独立部署、严格访问控制、加 TLS，仲裁节点被攻破 = 集群被接管
5. 管理面与数据面分离 —— HA 管理端口（如 2379、集群 API）不要暴露公网
```

**Red Hat 系差异（SELinux）**：RHEL/CentOS 上 keepalived 受 SELinux 约束，服务要连接/检测后端（如 LVS real server 或健康检查端口）可能被拒，需放行：

```shell
# RHEL 系：放行 keepalived 连接任意端口（默认策略只允许连 80 等少数端口）
setsebool -P keepalived_connect_any 1
# 查看是否被 SELinux 拦截
ausearch -m avc -ts recent | grep -i keepalived
```

## 故障排查

### 案例一：VIP 不漂移（主挂了备没接管）

```shell
# 1. 确认主节点是否真的不可达（还是网络分区）
ping -c 3 <主节点IP>          # 通则可能只是服务挂，不通才是机器/网络问题
# 2. 看备节点 keepalived 状态与日志
systemctl status keepalived   # 是否 active，是否反复重启
journalctl -u keepalived -n 50   # 找 "Entering BACKUP"/"Priority" 字样
# 3. 核对配置：优先级/组 ID/心跳间隔是否主备一致
grep -E 'state|priority|virtual_router_id|advert_int' /etc/keepalived/keepalived.conf
# 4. 抓 VRRP 报文，看备节点是否收到主的通告
tcpdump -i eth0 vrrp -nn      # 示例：本机需在 HA 环境执行
# 5. 检查防火墙是否拦截 VRRP（组播 224.0.0.18 / 协议 112）
```

```text
典型根因：
- priority 主备设成一样 → 抢不到主
- 防火墙挡了 VRRP 通告 → 备节点收不到心跳，永远处于 BACKUP
- 心跳走错网卡（interface 配错）→ 通告发到不相关网段
- 备节点 keepalived 没起来 / 配置语法错
```

### 案例二：脑裂（两台同时持 VIP）

```shell
# 在两台机器分别执行，都显示 VIP = 脑裂
ip addr show | grep 192.168.1.100
# 查心跳链路（网络分区？）
ping -c 3 <对端心跳IP>
# 查心跳被谁拦了（防火墙/交换机）
tcpdump -i eth0 vrrp -nn
# 应急：手动降级一台（停掉它的 keepalived，保一台服务）
systemctl stop keepalived
```

```text
典型根因：心跳链路断/防火墙拦组播/网卡 down/虚拟路由 ID 不一致
根治：修复心跳链路 + 确认防火墙放行 VRRP + 恢复后重新验证单主
```

### 案例三：切换成功了但服务不可用

```shell
# 1. VIP 已漂移但访问失败：先看 VIP 在谁身上
ip addr show | grep 192.168.1.100
# 2. 备节点服务真的起来了吗（keepalived 只管 VIP，不管服务进程）
systemctl status nginx
ss -tlnp | grep :80
# 3. 防火墙/安全组是否放行了 VIP 的端口
nft list ruleset | grep -E 'tcp dport 80'    # 实测：本机 nft 可用
# 4. 客户端是否还在连旧 MAC（ARP 缓存）
ip neigh show | grep 192.168.1.100
```

```text
典型根因：没配 track_script（只检测机器心跳，不检测服务）、
服务没设开机自启（systemctl enable）、防火墙没同步放行 VIP。
根治：track_script 检测服务 + 服务自启 + 防火墙规则两台一致。
```

### 案例四：主备频繁切换（抖动）

```shell
# 看切换频率
journalctl -u keepalived | grep -c "Entering MASTER"   # 一分钟内多次 = 抖动
# 看网络质量（丢包/延迟抖动）
ping -c 100 <对端IP> | grep -E 'loss|rtt'
# 看是不是健康检查脚本误报（脚本本身超时/依赖挂）
sh -x /etc/keepalived/check_nginx.sh                    # 手动执行看是否稳定返回 0
```

```text
典型根因：心跳间隔太小（<1s）+ 网络抖动；健康检查脚本超时设置太短；
主备 priority 差太小（差 1~2，一抖动就翻转）。
根治：调大 advert_int、给脚本加超时、priority 差拉大到 20~30。
```

## 常见问题

```text
Q1: 主备切换了，但服务连不上？
A: 检查 VIP 是否漂移成功（ip addr）、备节点服务是否就绪（ss -tlnp）、
   防火墙/安全组是否放行 VIP 端口、客户端 ARP 缓存是否刷新（ip neigh）。

Q2: 心跳正常但频繁主备切换（抖动）？
A: 心跳间隔太小或网络抖动，调大 advert_int；或健康检查脚本误报
   （脚本超时设置太短），手动执行脚本验证；priority 差距拉大。

Q3: 主节点恢复后，会不会又切回来（抢占）？
A: 默认抢占（主恢复就抢回 VIP）；配 nopreempt 则不抢，避免二次抖动。
   有状态服务建议 nopreempt + 主就绪后手动切回。

Q4: 高可用和负载均衡的区别？
A: 高可用 = 冗余 + 故障转移（一台挂了另一台顶上）；负载均衡 = 多台分担流量
   （[[19.3-LVS 负载均衡]]、[[19.4-HAProxy 与 Nginx]]）。常组合：HA 保证 LB
   本身不挂，LB 负责把流量分给后端多台。

Q5: 双机主备和奇数节点集群选哪个？
A: 双机简单便宜，但没有仲裁——网络分区会脑裂；3 节点集群（etcd/Pacemaker）
   有多数派仲裁，防脑裂但成本高。业务容忍「短暂不可用」选双机，核心数据
   服务选带仲裁的集群。

Q6: 高可用和灾备（容灾）是一回事吗？
A: 不是。HA 防单点故障（RTO 分钟级，同机房/同城），灾备防机房级灾难
   （异地双活/备份恢复，RPO/RTO 小时级~天级）。HA 是日常，灾备是兜底。

Q7: 可用性 99.9% 和 99.99% 差多少？
A: 一年停机时间从 8.76 小时降到 52.6 分钟，差一个数量级；
   每提升一个 9，冗余和自动化成本指数上升，按业务价值选档。

Q8: 为什么「机器没挂但服务挂了」也要切换？
A: 用户感知的是服务不是机器。所以健康检查要探测到应用层（HTTP/业务脚本），
   只做 ping 级探测的服务级 HA 是半成品。
```

## 面试题

```text
1. 什么是脑裂？如何避免？
   答：网络分区时主备都认为对方挂了、同时接管资源导致双主、数据冲突。
   避免：仲裁（奇数节点多数派投票）+ fencing（物理隔离故障节点）+
   多路径心跳降低误判。

2. 心跳检测为什么不能只靠「收不到心跳就判挂」？
   答：收不到心跳有两种可能——机器挂了或网络分区（机器活着但网络断了）。
   直接切换会引发脑裂。所以要有仲裁/fencing 区分「机器挂」和「网络断」，
   或通过第三方仲裁节点确认后再切换。

3. 可用性公式是什么？如何提升可用性？
   答：可用性 = MTBF / (MTBF + MTTR)。提升两条路：提高 MTBF（加冗余、
   换更可靠硬件，贵）或降低 MTTR（自动切换、监控告警、演练，便宜）。
   工程上优先压 MTTR。

4. 故障转移为什么要有 fencing（隔离）？
   答：防止「脑裂后数据冲突」——故障节点可能没真挂（只是网络分区），
   复活后继续写共享存储导致数据损坏；fencing（断电/断网/STONITH）
   在接管前强制隔离它，保证同一时刻只有一个节点写。

5. 双机热备为什么不推荐用于核心数据库？
   答：双机没有仲裁，网络分区必然脑裂（双主写库）；数据库切换还涉及
   数据补齐（binlog）和角色提升，裸切可能丢数据或双写。核心数据库
   建议半同步复制 + 仲裁（Orchestrator/3 节点）或云 RDS 托管切换。

6. RPO 和 RTO 分别是什么？与 HA 什么关系？
   答：RPO = 最多可丢的数据量（决定复制方式：同步 RPO≈0 / 异步可能丢
   几秒）；RTO = 最长恢复时间（决定切换方式：自动秒级 / 手动分钟级）。
   HA 主要优化 RTO（快速切换），备份/复制优化 RPO（少丢数据）。

7. 99.99% 可用性的一年允许停机多久？要满足它需要什么？
   答：52.6 分钟。需要：自动故障转移（检测+切换全自动，秒级）、
   监控告警（分钟级发现）、定期演练（保证切换真的可用）、
   冗余覆盖全链路（网络/主机/应用/数据）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 核心服务上 HA，按 SPOF 清单逐个消除：负载均衡器/网关/数据库/唯一入口优先
2. 心跳间隔设 1~3 秒、失败次数 2~3 次，切换时间 = 间隔 × 次数 ≤ 业务容忍度
3. 仲裁用奇数节点（3/5/7），多数派决策防脑裂；核心数据服务必须带仲裁
4. 健康检查探测到应用层（HTTP/业务脚本），不只 ping——「机器活着服务挂了」也要切
5. 定期做故障转移演练（停主/断网/杀进程三种都练），切换能力是练出来的
6. 监控心跳和切换事件（journalctl/告警），切换了要能及时发现并复盘
7. 有状态服务用 nopreempt 防二次抖动，主恢复后人工确认再切回
8. 高可用和备份都要做：HA 防停机（RTO），备份防误删/灾难（RPO）
9. 管理面与数据面隔离：仲裁/管理端口不暴露公网，心跳走独立网络
10. 先画架构图圈 SPOF 再选型：双机主备 / 3 节点仲裁 / 云 LB，按业务价值定档

### 踩坑记录

```text
坑 1：脑裂没防住导致数据损坏
结论：网络分区时主备都抢资源，双主同时写数据冲突，数据损坏。
原因：双机方案没有仲裁/fencing 机制，无法区分「机器挂」和「网络断」。
解法：核心数据服务引入奇数节点仲裁（多数派投票）+ fence 隔离故障节点；
     双机方案明确「容忍短暂不可用，不容忍双主」。

坑 2：心跳间隔太短，频繁误切换
结论：网络一抖动主备就来回切，服务持续不稳定。
原因：advert_int 设太小（<1s）+ 心跳走弱网（如 WiFi/共享链路），
     一抖就判对方挂。
解法：心跳间隔设 1~3 秒；心跳走独立有线网卡；配 nopreempt 避免恢复后二次切换。

坑 3：主备都配 MASTER 且 priority 相同
结论：两个节点都持 VIP，直接脑裂，服务时通时断。
原因：priority 相同无法区分谁优先；state 只是初始角色，不是主从依据。
解法：主 priority 100、备 90（差距至少 20），实际主从由 priority 决定。

坑 4：只做了主备，没做监控和演练
结论：切换发生了没人知道，或真故障时发现切不过去（备机起不来/配置过期）。
原因：没监控切换事件，没演练验证切换有效性，备机配置与主机长期漂移。
解法：监控心跳/切换事件并告警；每季度演练（停主、断网、杀进程）；
     演练后检查备机配置与主机一致。

坑 5：切换后客户端还连着旧主
结论：切换完成后部分客户端请求仍然失败。
原因：客户端缓存了旧主的 MAC/连接（ARP 缓存未刷新），或客户端直连
     真实 IP 而非 VIP。
解法：切换时发免费 ARP（gratuitous ARP）刷新交换机/客户端缓存；
     客户端一律按 VIP 访问，禁止缓存真实 IP。

坑 6：只做了服务级 HA，数据层还是单点
结论：入口双机切换了，但数据库单机一挂，整个业务还是瘫。
原因：HA 只覆盖了应用/入口层，数据层（DB/存储）仍是 SPOF。
解法：按层次梳理：网络层（VIP/双链路）+ 应用层（多副本）+ 数据层
     （主从复制/共享存储），缺哪层补哪层。

坑 7：健康检查脚本本身成了故障源
结论：脚本每 2 秒 curl 大页面/查重 SQL，把主节点 CPU 打满，反而触发切换。
原因：健康检查脚本太重、无超时、无缓存，探测本身拖垮业务。
解法：脚本轻量化（进程/端口级优先，页面级降频）、加超时（timeout 5s）、
     interval 2~5s，脚本输出固定 0/1 并测脚本自身稳定性。

坑 8：备机配置与主机漂移，切换后行为不一致
结论：真切换后发现备机缺模块/少配置/版本旧，服务起不来。
原因：备机平时不干活，没人更新它，与主机配置长期不一致。
解法：配置用 CM（Ansible/脚本）统一管理；备机定期做切换演练；
     备机也纳入监控（进程、版本、配置一致性）。
```
