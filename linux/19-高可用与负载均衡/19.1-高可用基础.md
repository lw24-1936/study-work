## 概述

高可用（High Availability，HA）指「系统通过冗余和故障转移，减少停机时间，持续提供服务」。核心目标是消除单点故障（SPOF）——任何一台机器/组件挂了，服务不中断。四个关键机制：心跳（检测对方存活）、脑裂（双主同时抢资源，必须避免）、仲裁（多数派裁决，决定谁做主）、故障转移（主挂了自动切到备）。高可用是所有生产系统的基石。

```text
高可用核心目标：消除单点故障（SPOF），任何单点挂了服务不中断
```

## 核心概念

高可用围绕几个核心概念展开：

1. **可用性指标**：用「几个 9」衡量，99.9%（一年宕机 8.76 小时）、99.99%（52.6 分钟）、99.999%（5.26 分钟）。可用性 = 正常运行时间 / 总时间。
2. **单点故障 SPOF**：系统中「挂了就整体不可用」的节点，高可用的核心就是消除它。
3. **冗余**：多副本（主备/多活），一个挂了另一个顶上。
4. **故障转移 failover**：主节点故障时自动切到备节点，分「自动」（心跳检测 + 自动切换）和「手动」。

```text
可用性「几个 9」：
99.9%   一年宕机 8.76 小时（可接受，需重启恢复）
99.99%  一年宕机 52.6 分钟（需自动故障转移）
99.999% 一年宕机 5.26 分钟（需全冗余 + 自动恢复）
```

## 工作原理

高可用的工作原理是「心跳检测 → 故障判断 → 故障转移」三步循环：

1. **心跳机制**：主备节点互相定期发心跳（网络包/心跳线），检测对方是否存活。心跳间隔通常 1~3 秒，连续 N 次未收到心跳 = 判对方故障。
2. **故障判断**：收到心跳没？收到 = 正常，没收到（超时） = 对方可能挂了。注意「可能」——网络分区（网络断了但机器没挂）也会导致收不到心跳。
3. **故障转移**：判主故障后，备节点接管（抢 VIP、提升为主、接管资源），完成切换。

关键难点是**脑裂**——网络分区时，主备都以为对方挂了，都尝试接管资源，导致「双主」同时写数据（数据损坏）。脑裂的解决靠**仲裁**：引入第三方的多数派投票（如奇数节点集群、共享存储的 fence 机制），「谁拿到多数票谁做主」，少数派自动降级。

```text
高可用三步循环：
心跳检测 → 故障判断 → 故障转移

脑裂（split-brain）：
网络分区时主备都以为对方挂了 → 双主抢资源 → 数据冲突
解决：仲裁（多数派投票）+ fence（隔离故障节点）
```

## 常用命令与配置

高可用本身没有固定命令，但排查高可用问题常用这些：

```shell
# 看服务在哪个节点（VIP 在哪）
ip addr show | grep <VIP>
# 看集群成员（以 etcd 为例）
etcdctl member list          # 集群成员
etcdctl endpoint health      # 各节点健康
# 看心跳/集群日志
journalctl -u keepalived -f   # Keepalived 日志
# 模拟故障转移
systemctl stop keepalived    # 停主节点，观察 VIP 是否漂移
```

```text
高可用配置要点：
1. 心跳间隔 —— 1~3 秒，太短误判、太长切换慢
2. 仲裁 —— 奇数节点（3/5/7），多数派决策
3. fence —— 故障节点要「隔离」（断电/STONITH），防它继续写
```

## 配置文件解析

以 Keepalived 为例，解析高可用配置的核心字段（完整见 19.2）：

```ini
# /etc/keepalived/keepalived.conf 关键段
vrrp_instance VI_1 {
    state MASTER            # 角色：MASTER 主 / BACKUP 备
    interface eth0          # VIP 绑定的网卡
    virtual_router_id 51    # VRRP 组 ID（主备必须一致）
    priority 100            # 优先级（高的为主）
    advert_int 1            # 心跳间隔（秒）
    authentication {        # 心跳认证（防伪造）
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
        192.168.1.100       # 虚拟 IP（VIP，漂移的地址）
    }
}
```

```text
字段含义：
state          MASTER/BACKUP，初始角色（实际由 priority 决定）
priority       优先级，高的抢到主（BACKUP 通常 100-优先级差）
advert_int     心跳间隔，主备要一致
virtual_ipaddress  VIP，主节点持有，故障时漂移到备
```

## 应用场景实战

### 场景一：双机主备（Keepalived + 服务）

```text
架构：
192.168.1.10 (主 nginx)  ──VIP 192.168.1.100──  对外提供服务
192.168.1.11 (备 nginx)  ──VIP 漂移── 主挂了接管

流程：
1. 主节点持 VIP，对外服务
2. 主挂了 → 心跳超时 → 备节点抢 VIP → 成为新主
3. 客户端访问 VIP，无感知切换
```

### 场景二：判断系统是否需要高可用

```text
问三个问题：
1. 有单点故障吗？—— 数据库/负载均衡器/应用单机部署
2. 挂了影响多大？—— 核心业务 vs 内部工具
3. 能容忍多久？—— 分钟级（手动切换）vs 秒级（自动切换）
答案决定：是否上 HA、上多重的 HA
```

## 性能与调优

高可用系统的性能调优重点在「切换速度」和「资源开销」：

```text
1. 心跳间隔 —— 太小（<1s）频繁心跳消耗资源，太大切换慢；1~3s 平衡
2. 故障检测时间 —— 心跳间隔 × 失败次数 = 检测时间，别太长（如 3s×3=9s 才切换）
3. 切换开销 —— 备节点要能快速接管（预热、共享会话），否则切换后冷启动慢
4. 资源冗余 —— 备节点平时闲置，可做「双活」提升利用率
```

## 安全与权限

```text
高可用安全要点：
1. 心跳认证 —— VRRP 心跳加 auth（防止伪造心跳把主挤下线）
2. 心跳隔离 —— 心跳走独立网卡/网络，别和业务流量混（防业务拥塞误判）
3. fence 权限 —— 隔离故障节点的操作要 root，防误操作
4. 仲裁节点安全 —— 仲裁节点（如 etcd）要独立、安全，别和业务同机
```

## 故障排查

### 脑裂排查（双主同时持 VIP）

```shell
# 1. 确认脑裂（两个节点都有 VIP）
# 在两台机器分别执行
ip addr show | grep <VIP>
# 两台都有 = 脑裂
# 2. 查心跳（网络分区？）
ping <对端心跳IP>
# 3. 查 keepalived 日志
journalctl -u keepalived -n 50
# 4. 解决：恢复心跳网络，或手动降级一台（停 keepalived）
```

## 常见问题

```text
Q1: 主备切换了，但服务连不上？
A: 检查 VIP 是否漂移成功（ip addr）、备节点服务是否就绪、防火墙是否放行 VIP。

Q2: 心跳正常但频繁主备切换（抖动）？
A: 心跳间隔太小或网络抖动，调大 advert_int，或检查网络质量。

Q3: 主节点恢复后，会不会又切回来（抢占）？
A: 看 nopreempt 配置——默认抢占（主恢复抢回 VIP），配 nopreempt 则不抢占（避免二次抖动）。

Q4: 高可用和负载均衡的区别？
A: 高可用 = 冗余 + 故障转移（一台挂了另一台顶上），负载均衡 = 多台分担流量。常组合：HA 保证 LB 本身不挂，LB 分担后端流量。
```

## 面试题

```text
1. 什么是脑裂？如何避免？
   答：网络分区时主备都认为对方挂了、同时抢资源导致双主。避免：仲裁（多数派投票）+ fence（隔离故障节点）。

2. 心跳检测为什么不能只靠「收不到心跳就判挂」？
   答：网络分区会导致收不到心跳，但对方可能没挂（只是网络断了）。所以要仲裁/fence 区分「机器挂」和「网络断」。

3. 可用性 99.9% 和 99.99% 差多少？
   答：99.9% 一年宕 8.76 小时，99.99% 宕 52.6 分钟，差一个数量级。每提升一个 9 成本指数上升。

4. 故障转移为什么要有 fence？
   答：防止「脑裂」——故障节点可能没真挂，继续写共享存储导致数据冲突，fence 强制隔离它。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 核心服务上 HA，消除单点故障（负载均衡器/数据库/网关优先）
2. 心跳间隔设 1~3 秒，太小误判、太大切换慢
3. 仲裁用奇数节点（3/5/7），多数派决策防脑裂
4. 定期做故障转移演练，验证切换真的有效
5. 监控心跳和切换事件，切换了要能及时发现

### 踩坑记录

```text
坑 1：脑裂没防住导致数据损坏
结论：网络分区时主备都抢资源，双主同时写数据冲突。
原因：没有仲裁/fence 机制，无法区分「机器挂」和「网络断」。
解法：引入奇数节点仲裁（多数派投票）+ fence 隔离故障节点。

坑 2：心跳间隔太短，频繁误切换
结论：网络抖动导致主备频繁切换，服务不稳定。
原因：advert_int 设太小（<1s），网络一抖就判对方挂。
解法：心跳间隔设 1~3 秒，配 nopreempt 避免恢复后二次切换。

坑 3：主备都配 MASTER 且 priority 相同
结论：两个节点都持 VIP，脑裂。
原因：priority 相同无法区分谁优先，state 只是初始角色。
解法：主 priority 100、备 90（必须不同），实际由 priority 决定。

坑 4：只做了主备，没做监控和演练
结论：切换发生了但没人知道，或真切换时发现切不过去。
原因：没监控切换事件，没演练验证切换有效性。
解法：监控心跳/切换，定期演练（停主节点看是否正常切换）。

坑 5：切换后客户端还连着旧主
结论：切换后部分客户端请求失败。
原因：客户端缓存了旧主的连接/地址，没及时切到新主。
解法：VIP 漂移 + ARP 宣告，客户端按 VIP 访问（不缓存真实 IP）。
```
