## 概述

系统监控回答三个问题：**「现在什么状态」「谁在吃资源」「当时发生了什么」**。top/htop 看总览（CPU/内存/进程），vmstat 看内存与 CPU 动态，iostat 看磁盘 IO，mpstat 看每个 CPU 核心，sar 看历史（后台采集），pidstat 看单进程的 CPU/内存/IO。这些工具分工明确，配合起来能定位「CPU 飙高」「内存不够」「IO 慢」「负载高」等绝大多数性能问题。

监控不只是「会敲命令」，更要有**方法论**：

- **USE 法（Utilization / Saturation / Errors）**：对每种资源（CPU/内存/磁盘/网络）问三个问题——利用率多少（是否接近 100%）、饱和度多少（排队多长）、错误多少（报错/丢包）。这是 Brendan Gregg 提出的经典排查框架。
- **红黑法（状态指标 vs 资源指标）**：红色指标是「状态类」——结果对错、通不通、活不活（如进程是否存活、端口是否监听）；黑色指标是「资源类」——消耗了多少（CPU/内存/IO）。先看红（服务挂了没有），再看黑（资源够不够）。

本机是 Ubuntu 环境，sysstat 工具族齐全。以下实测数据均来自本机（8 核 Intel i5-8300H，Ubuntu 内核 7.0.0-28-generic）。

## 核心概念

### 1. 监控方法论：USE 法

对每种资源（CPU、内存、磁盘、网络、文件系统）依次检查利用率、饱和度、错误：

| 资源 | 利用率（Utilization） | 饱和度（Saturation） | 错误（Errors） |
|---|---|---|---|
| CPU | top 的 %Cpu(s) 使用率 | load average、vmstat r 列、runq-sz | 机器检查（mce）、日志报错 |
| 内存 | free 的 used/available | vmstat si/so（换入换出）、swap 使用 | OOM killer 日志 |
| 磁盘 | iostat %util | iostat await/aqu-sz、vmstat b 列 | dmesg 的 I/O error、smartctl 错误 |
| 网络 | sar -n DEV 的带宽利用率 | 网卡队列溢出、TCP 重传、ss 的 backlog drop | 丢包率、网卡错误计数 |

排查顺序：**先利用率（是否打满）→ 再饱和度（排队多长）→ 最后错误（有没有坏）**。利用率高不一定有问题，饱和度高（排队很长）才是性能恶化的直接信号。

### 2. 红黑法（状态指标 vs 资源指标）

| 类型 | 含义 | 例子 | 监控方式 |
|---|---|---|---|
| 红（状态） | 服务/进程「活不活、通不通、对不对」 | 进程存活、端口监听、HTTP 200、主从复制状态 | 探针/心跳，告警要即时 |
| 黑（资源） | 资源「用了多少、剩多少」 | CPU%、内存、磁盘、带宽 | 采样曲线，看趋势与阈值 |

排查思路：**先红后黑**——服务挂了先查状态（进程在不在、端口通不通），别一上来就调 CPU；服务活着但慢，才查资源（黑）。这套方法论在本库 [[16.1-性能分析方法论]] 有完整展开。

### 3. load average 三个值

`load average: 2.47, 2.25, 2.04` 分别代表 **1 分钟、5 分钟、15 分钟** 的平均负载：运行队列中「可运行（R）+ 不可中断（D）」的进程/线程数的时间加权平均。

- **R 状态**：正在运行或等待 CPU 的进程。
- **D 状态**：不可中断睡眠——通常阻塞在磁盘/网络 IO 上，**即使 CPU 空闲也会算进 load**。

判断基准：**load 与 CPU 核数比较**。8 核机器 load 长期 >8 说明 CPU 饱和；load 长期 > 核数 × 0.7 就该警惕。三个值一起看趋势：1 分钟 > 15 分钟说明负载在上升。

**load average ≠ CPU 使用率**：CPU 使用率是「CPU 忙的时间占比」（0-100%），load 是「等待调度的进程数」（无上限）。IO 阻塞会让 load 高而 CPU 空闲——这是最常见的误判点，详见「故障排查案例一」。

### 4. top 输出逐行逐列解读

top 第一屏就是整台机器的心脏：

```text
top - 12:37:32 up 22 days, 23:35,  3 users,  load average: 2.47, 2.25, 2.04
任务: 421 total,   2 running, 419 sleeping,   0 stopped,   0 zombie
%Cpu(s): 16.2 us,  6.9 sy,  0.0 ni, 71.9 id,  5.0 wa,  0.0 hi,  0.0 si,  0.0 st
MiB Mem :  19697.9 total,   1171.5 free,  11599.4 used,   8452.8 buff/cache
MiB Swap:   8192.0 total,   7999.4 free,    192.6 used.   8098.5 avail Mem
```

**第 1 行**：当前时间、开机时长（up 22 days）、登录用户数、load average 三值。

**第 2 行**：进程总数与状态分布。**zombie 数量 >0 且持续增长**说明有进程没被父进程回收（僵尸进程），是程序缺陷的信号。

**第 3 行 %Cpu(s)** 是 CPU 时间片分配，各列含义：

| 列 | 含义 | 说明 |
|---|---|---|
| us | user | 用户态时间占比（跑业务代码） |
| sy | system | 内核态时间占比（系统调用、内核工作） |
| ni | nice | 低优先级（nice 值调整过）进程的时间 |
| id | idle | 空闲时间 |
| wa | iowait | **等待磁盘/网络 IO 完成的时间**——wa 高说明 IO 是瓶颈 |
| hi | hardware irq | 硬中断 |
| si | software irq | 软中断 |
| st | steal | **被虚拟化宿主机抢占的时间**——云主机 st 高说明被邻居「偷走」了 CPU |

**第 4/5 行内存**：total/free/used/buff/cache/available，其中 **buff/cache 是磁盘缓存（可回收），available 才是系统实际可分配的内存**——判断内存不足看 available，别只看 free。

**进程列表列**：PID（进程号）、USER（属主）、PR/NI（优先级/nice 值）、VIRT（虚拟内存）、RES（常驻物理内存）、SHR（共享内存）、S（状态）、%CPU（**单核百分比**——8 核机器单进程 100% 只占 1 核）、%MEM、TIME+（累计 CPU 时间）、COMMAND。

**进程状态 S 列**：R=运行、S=睡眠、D=不可中断睡眠（等 IO）、T=停止、Z=僵尸、I=空闲内核线程。**D 状态进程多 = IO 阻塞严重**。

**top 交互键**：`1` 看每核 CPU、`P` 按 CPU 排序、`M` 按内存排序、`c` 显示完整命令行、`H` 线程模式、`k` 杀进程、`W` 保存配置到 ~/.toprc、`q` 退出。

### 5. vmstat 各列含义

`vmstat 1 3` 每秒采样 3 次，一屏看全系统动态：

| 组 | 列 | 含义 | 关注点 |
|---|---|---|---|
| procs | r | 运行队列长度（等待 CPU 的进程数） | **长期 > 核数 = CPU 饱和** |
| procs | b | 阻塞在 IO 上的进程数 | **持续 >0 = IO 瓶颈** |
| memory | swpd | 已使用的 swap 量 | 持续增长 = 内存压力 |
| memory | free | 空闲内存 | 结合 available 判断 |
| memory | buff/cache | 缓冲/缓存 | 可回收，不算「不够用」 |
| swap | si | 每秒从磁盘换入内存的量 | **持续 >0 = 内存不足信号** |
| swap | so | 每秒换出到磁盘的量 | **持续 >0 = 内存不足信号** |
| io | bi | 每秒从块设备读入的块数 | 读 IO 活动 |
| io | bo | 每秒写出的块数 | 写 IO 活动 |
| system | in | 每秒中断数 | 异常飙升说明硬件/驱动问题 |
| system | cs | 每秒上下文切换数 | 过高说明进程/线程频繁切换 |
| cpu | us/sy/id/wa/st | 同 top 的 %Cpu(s) | wa 高查 IO，st 高查虚拟化 |

### 6. iostat 关键指标（await / %util）

`iostat -x 1 3` 输出每块盘的扩展指标，关键列：

| 指标 | 含义 | 判断 |
|---|---|---|
| r/s、w/s | 每秒读/写请求次数（IOPS） | 与磁盘标称 IOPS 对比 |
| rkB/s、wkB/s | 每秒读写吞吐 | 与磁盘带宽对比 |
| r_await、w_await | 读/写平均延迟（毫秒） | **>20ms 偏慢，>100ms 很慢**（机械盘） |
| aqu-sz | 平均请求队列长度 | 高 = 排队严重 |
| %util | 设备繁忙时间占比（**不是利用率上限**） | **持续 >70% 需警惕，接近 100% = 饱和** |

两个重要辨析：

- **%util 高 ≠ 一定慢**：%util 是「设备有请求在处理的时间占比」，机械盘 100% util 通常意味着饱和；但 SSD 并发能力强，%util 100% 时延迟可能依然很低。**要看 await 和 IOPS 综合判断**。
- **await 高 + %util 低**：设备并不忙但单个请求很慢——可能是磁盘坏道重试、队列深度受限、或底层设备问题（如云盘被限流）。

### 7. free：buff/cache 与 available

```text
$ free -h
               total        used        free      shared  buff/cache   available
内存：          19Gi        11Gi       1.1Gi       1.3Gi       8.3Gi       7.9Gi
交换：         8.0Gi       192Mi       7.8Gi
```

- **buff/cache 8.3Gi**：内核把空闲内存用作磁盘缓存（读缓存 + 写缓冲），**应用需要时内核会自动回收**，所以「free 只有 1.1Gi」不代表内存不够。
- **available 7.9Gi**：内核预估「在不触发 swap 的前提下还能分给应用多少内存」——**判断内存是否够用只看 available**。
- 本机 total 19Gi、used 11Gi、available 7.9Gi：内存健康。

### 8. swap 与内存压力判断

- swap 是磁盘上的交换空间（本机 8.0Gi，仅用了 192Mi）。**swap 有使用 ≠ 内存不足**——内核可能把长期不活跃的页换出去，属正常回收。
- 真正的内存压力信号：**vmstat 的 si/so 持续 >0**（频繁换入换出，磁盘来回倒腾），或 swap 使用持续增长且 available 接近 0。
- 内存不足的最终表现：**OOM killer 杀进程**（dmesg 里看 oom-kill），比 swap 飙高更严重。

### 9. sysstat 工具族（sar / sadc / sadf）

sysstat 包提供完整监控家族：

| 命令 | 作用 |
|---|---|
| sar | 查看 CPU/内存/磁盘/网络等历史或实时统计（全能选手） |
| sadc | 后台采集器（sa1 封装），把数据写入 /var/log/sysstat/saXX |
| sa1 / sa2 | 采集与日报脚本（由 cron/timer 调用） |
| sadf | 把 sar 数据导出为 CSV/XML/JSON 等格式 |
| iostat | 磁盘与 CPU 统计 |
| mpstat | 每核 CPU 统计 |
| pidstat | 进程级 CPU/内存/IO 统计 |

sar 是唯一能「事后回溯」的工具：只要后台采集开着，就能查任何一天任何时段的指标。

### 10. 监控频率与数据保留

- **实时监控**：`sar 1 5`、`vmstat 1 5` 等，间隔 1 秒、采几次——排查当下问题用。
- **后台采集**：sysstat 默认**每 10 分钟**采一次（本机实测 /etc/cron.d/sysstat 与 systemd timer 都是 10 分钟粒度），存为 /var/log/sysstat/saXX，每天一个文件。
- **数据保留**：默认 7 天（Ubuntu 的 /etc/cron.daily/sysstat 会清理旧文件），可通过 /etc/sysstat/sysstat 里的 `HISTORY` 参数调整（见配置文件解析）。
- 原则：**10 分钟粒度适合看趋势和基线，秒级问题要靠实时命令现场抓**——两者互补，不是替代关系。

## 工作原理

### 内核计数器模型

所有监控工具的底层数据源都是**内核维护的计数器**：CPU 时间片（各模式累计 jiffies）、内存页、磁盘 IO 次数与字节、网络收发字节、进程状态等，都记录在 /proc（进程与系统信息）和 /sys（设备与内核参数）伪文件系统里。工具定时读取这些计数器、**计算两次采样的差值**，除以时间间隔，就得出「每秒的 CPU 使用率 / IO 量 / 网络流量」。

```text
内核计数器（/proc、/sys）→ 工具定时采样 → 计算差值/时间 → 每秒使用率、IOPS、带宽
```

### top 的采样原理

top 是**实时采样器**：启动时读一次 /proc/stat 和 /proc/<pid>/stat 的 CPU 计数，之后默认每 3 秒刷新一次，用两次读数之差算百分比。所以 top 的 %CPU 是「过去 3 秒的平均」，不是瞬时值；第一次显示的数字是「开机以来的累计平均」。

### load average 的计算

内核维护一个运行队列长度（R + D 状态任务数），load average 是它的**指数加权移动平均**（类似温度计的阻尼效应）：1 分钟平均权重最高、15 分钟最平滑。因此：

- 三个值接近 = 负载稳定；1 分钟 >> 15 分钟 = 负载刚起来（如发布、定时任务）。
- 短时尖峰（1 分钟高、15 分钟低）往往不必惊慌，**持续高于核数才需要处理**。

### sar 后台采集链路

Ubuntu（systemd 时代）的采集链路是两条并行通道，本机实测：

```text
通道 A（传统 cron 路径，systemd 下已失效）：
/etc/cron.d/sysstat → debian-sa1 → 检查 ENABLED → sa1 → sadc → saXX
   但 debian-sa1 开头就检查 [ -d /run/systemd/system ] 存在则 exit 0，
   所以 systemd 系统上 cron 路径实际不干活

通道 B（systemd timer 路径，本机实际生效）：
sysstat-collect.timer（OnCalendar=*:00/10，每 10 分钟）
    → sysstat-collect.service → /usr/lib/sysstat/sa1 1 1 → sadc → /var/log/sysstat/saXX
sysstat-summary.timer（每天 00:07）→ 生成日报 sarXX
```

**重要实测发现**：本机 /etc/default/sysstat 里 `ENABLED="false"`，但 /var/log/sysstat/sa19 今天仍在每 10 分钟更新——因为 systemd timer 直接调 sa1，**绕过了 debian-sa1 里的 ENABLED 检查**。Ubuntu 22.04+ 上「ENABLED 控制采集开关」的说法只对 sysvinit/手动执行 debian-sa1 成立，对 systemd timer 不成立（详见「故障排查案例二」和踩坑记录）。

### 实测（本机）——load 与计数器

```text
$ uptime
 12:37:31 up 22 days, 23:35,  3 users,  load average: 2.47, 2.25, 2.04

$ cat /proc/loadavg
2.47 2.25 2.04 3/2597 3104800
# 2.47=1分钟均值 2.25=5分钟 2.04=15分钟；3/2597=当前运行/总任务数；3104800=最近 PID
```

8 核机器 load 2.47，load/核 = 0.31，**健康**（<0.7 警戒线）。1 分钟值略高于 15 分钟值，负载轻微上升。

## 常用命令与配置

### 总览与负载

```shell
top                  # 实时总览（按 CPU 排序，3 秒刷新）
top -u alice         # 只看某用户
top -p 1234          # 只看某进程
top -H -p 1234       # 看某进程的所有线程
top -b -n 1 | head   # 批处理模式抓一次（适合脚本/记录现场）
uptime               # 快速看 load average 三值
cat /proc/loadavg    # 更细的 loadavg（含运行/总任务数）
```

### CPU 专项

```shell
mpstat -P ALL 1 3    # 每核 CPU（定位单核飙高）
mpstat 1 3           # 总体 CPU
sar -u 1 5           # CPU 实时（interval count）
sar -u -f /var/log/sysstat/sa18   # 看某天的历史 CPU
sar -q               # 运行队列与 load 历史
```

### 内存专项

```shell
free -h              # 内存总览（看 available，别只看 free）
vmstat 1 5           # 内存动态 + si/so 换入换出
vmstat -s            # 内存汇总统计（一次快照）
sar -r 1 3           # 内存使用率、commit、dirty 页
sar -S 1 3           # swap 使用
cat /proc/meminfo    # 最细粒度内存计数器
```

### 磁盘 IO 专项

```shell
iostat -x 1 3        # 磁盘扩展指标（await/%util 关键）
iostat -x -p sda 1 3 # 只看某块盘
iostat -d 1 3        # 简化视图
sar -d 1 3           # 磁盘 IO（tps/await/%util）
pidstat -d 1         # 按进程看磁盘读写（谁在狂写盘）
iotop                # 实时 IO 排行（需 apt install iotop）
df -h                # 文件系统容量（磁盘满≠IO 慢，别混淆）
```

### 网络专项

```shell
sar -n DEV 1 3       # 每网卡收发流量（rxkB/s/txkB/s）
sar -n TCP,ETCP 1 3  # TCP 连接与重传
ss -s                # 连接统计总览（TCP/UDP/状态分布）
ss -tlnp             # 监听端口与进程
iftop                # 实时带宽排行（需 apt install iftop）
nethogs eth0         # 按进程看带宽（需 apt install nethogs）
```

### 进程专项

```shell
ps aux --sort=-%cpu  # 按 CPU 降序的进程快照
ps aux --sort=-rss   # 按内存降序
pidstat 1 5          # 所有进程每秒 CPU（含 %wait 等待时间）
pidstat -p 1234 1    # 某进程
pidstat -r 1         # 进程内存
pidstat -d 1         # 进程磁盘 IO
pstree -p 1234       # 进程树（找父子关系）
```

## 配置文件解析

### /etc/default/sysstat（Debian/Ubuntu）

```text
# /etc/default/sysstat —— sysstat 采集总开关（传统路径）
ENABLED="false"     # true=开启采集；false=关闭
```

注意：本机实测为 `false`，但采集仍在进行——**systemd 系统的采集由 timer 驱动，此开关只影响 cron.d/debian-sa1 路径**（见工作原理）。

### /etc/cron.d/sysstat（传统 cron 采集周期）

```text
# 每 10 分钟采一次（分钟 5-55 每 10 分钟）
5-55/10 * * * * root command -v debian-sa1 > /dev/null && debian-sa1 1 1
# 每天 23:59 额外采一次 60 秒间隔 2 次，用于轮转统计文件
59 23 * * * root command -v debian-sa1 > /dev/null && debian-sa1 60 2
```

### systemd timer（Ubuntu 22.04+ 实际生效的采集器）

```text
$ systemctl list-timers | grep sysstat
sysstat-collect.timer    # OnCalendar=*:00/10 —— 每 10 分钟采集
sysstat-summary.timer    # 每天 00:07 —— 生成日报

# sysstat-collect.service 内容（关键行）：
ExecStart=/usr/lib/sysstat/sa1 1 1   # 直接调 sa1，不走 debian-sa1 的 ENABLED 检查
```

管理命令：

```shell
systemctl status sysstat            # sysstat.service（重置日志，active exited 正常）
systemctl list-timers | grep sysstat # 看两个 timer 是否在跑
systemctl disable --now sysstat-collect.timer   # 想彻底停采集用这个（不是改 ENABLED）
```

### 历史数据文件 /var/log/sysstat/

```text
$ ls -la /var/log/sysstat/ | tail -10
-rw-r--r-- 1 root root 1127752  8月 15 23:50 sa15
-rw-r--r-- 1 root root  995032  8月 16 23:50 sa16

-rw-r--r-- 1 root root  982600  8月 18 23:50 sa18

```

每天一个 `saXX` 文件（约 1MB/天），`sarXX` 是日报。查看历史：`sar -f /var/log/sysstat/sa18 -u`（见场景六）。

### 保留天数 HISTORY（/etc/sysstat/sysstat）

```text
# /etc/sysstat/sysstat（Debian/Ubuntu）
HISTORY=7    # 保留 7 天，改大则 sa 文件保留更久
```

Red Hat 系对应配置在 **/etc/sysconfig/sysstat**（参数 `HISTORY`），与 Ubuntu 的 /etc/default/sysstat 路径不同。

### ~/.toprc（top 个性化配置）

top 交互界面里按 `W` 可把当前设置（排序键、显示列、颜色）写入 ~/.toprc，下次启动自动生效。脚本化使用时可用 `top -b` 配合环境变量覆盖（如 `top -b -n 1 -o %MEM`）。

### Red Hat 系差异对照

| 项 | Ubuntu/Debian | Red Hat（RHEL/CentOS/Rocky） |
|---|---|---|
| 安装 | `apt install sysstat` | `yum install sysstat` / `dnf install sysstat` |
| 总开关文件 | /etc/default/sysstat（ENABLED） | 无 ENABLED 概念，装完即采集 |
| 采集配置 | /etc/cron.d/sysstat + systemd timer | /etc/cron.d/sysstat（sa1 直接跑，**默认启用**） |
| 默认状态 | **ENABLED=false，需手动开启** | **安装后默认采集**（sar 直接有历史） |
| 保留配置 | /etc/sysstat/sysstat（HISTORY） | /etc/sysconfig/sysstat（HISTORY） |
| 调优配套 | tuned 可装（`apt install tuned`） | tuned 默认集成（`tuned-adm profile`） |

**核心差异**：Red Hat 系 sysstat 装完即用（cron 直接调 sa1），Ubuntu 传统上需要把 ENABLED 改成 true（在 sysvinit 时代）；systemd 时代 Ubuntu 由 timer 驱动，天然在采——但很多老教程仍写着「必须改 ENABLED=true」，注意甄别。

### 场景四：load average 高，按 USE 法逐步排除

## 性能与调优

### 1. 采样间隔的选择

- **实时排查**：1 秒间隔、采 3-5 次（`vmstat 1 5`），够看趋势。
- **后台采集**：10 分钟粒度（sysstat 默认），够看天级趋势和基线。
- 别把实时命令挂成常驻脚本（如 `top -b -d 1` 无限跑）——**监控本身消耗 CPU 和 IO**，太密的采样在繁忙机器上是额外负担。

### 2. 监控自身的开销

- top/vmstat/iostat 这类瞬时命令开销可忽略（毫秒级）。
- 常驻采集器（sysstat 的 sadc）每 10 分钟采一次，写一个约 1MB 的文件，开销极小。
- 进程级监控（pidstat 对全系统、perf）开销随监控目标数量增长，生产环境按需开。

### 3. sa 历史数据的保留与磁盘

每天约 1MB/天（本机实测 sa 文件 0.5-1.1MB），默认保留 7 天。保留期调整：

```shell
# Ubuntu：/etc/sysstat/sysstat
HISTORY=30    # 保留 30 天
```

注意 HISTORY 改大后，/var/log/sysstat 目录的磁盘占用按天线性增长；配合 logrotate 或定期清理，别让监控数据把盘占满。

### 4. 监控基线：正常值 vs 异常值

**基线 = 某台机器在业务正常运行时的典型指标区间**。没有基线，「load 3」无法判断好坏——对 2 核机器是灾难，对 32 核机器是空闲。建立方法：sar 历史数据跑一周以上，统计各时段均值与峰值，形成「正常区间」。

常见性能指标健康阈值（经验值，具体业务具体调）：

| 指标 | 健康线 | 警戒线 | 异常线 | 看什么命令 |
|---|---|---|---|---|
| CPU 使用率（长期平均） | <50% | >70% | >90% 持续 | top、sar -u |
| load / 核数 | <0.7 | 0.7-1.0 | >1.0 持续 | uptime、sar -q |
| 内存 available | >总内存 30% | <20% | <10% 且 si/so>0 | free -h、vmstat |
| 磁盘 %util | <50% | >70% | 持续 100% | iostat -x |
| 磁盘 await | <20ms | 20-100ms | >100ms | iostat -x |
| 网络带宽利用率 | <50% | >70% | 持续 >90% | sar -n DEV |
| swap si/so | 0 | 偶发 >0 | 持续 >0 | vmstat |

> 阈值不是死的：数据库服务器的磁盘 await 天然比 Web 服务器高；SSD 的 %util 100% 可能依然健康。**基线优先于通用阈值**。

### 5. 监控数据的「前」与「后」

- 上线前：跑一轮负载测试，用 sar -o 存现场数据，形成发布前基线。
- 上线后：发布窗口内的 sar 数据与基线对比，验证无性能回退。
- 故障后：立即用 `sar -o /tmp/xxx 1 60` 记录现场，别让故障现场的数据丢了。

## 安全与权限

### 1. 进程信息泄露（top/ps）

top/ps 会显示**所有进程的命令行参数**——其他用户进程的命令行里可能含密码/密钥（如 `mysql -p密码`、`curl -H "Authorization: ..."`）。默认情况下普通用户只能看到自己的进程（受 /proc 权限控制），root 可以看到全部。

### 2. /proc 的 hidepid 加固

```shell
# 挂载 /proc 时限制 hidepid=2（仅本用户可见）：
mount -o remount,hidepid=2 /proc
# 或写入 /etc/fstab：
proc /proc proc defaults,hidepid=2 0 0
```

hidepid=2 后，其他用户的进程 PID、命令行、环境全部不可见——多租户/共享服务器强烈建议开启（注意会影响监控代理读取全量进程数据，需权衡）。

### 3. sar 历史数据的权限

/var/log/sysstat/saXX 默认 root 可读写、其他用户只读（`-rw-r--r--`）。sa 文件包含全天 CPU/内存/磁盘/网络明细，**间接反映业务负载规律**，生产环境建议收紧为 root 专属（`chmod 600 /var/log/sysstat/sa*`）。

### 4. 监控工具的提权面

- pidstat -d、iotop 等看其他用户进程需要 root。
- 用 sudo 给运维账号**白名单式授权**（只允许指定监控命令），别直接给 ALL：

```text
# /etc/sudoers.d/monitor
ops ALL=(root) NOPASSWD: /usr/bin/iostat, /usr/bin/vmstat, /usr/bin/sar, /usr/bin/pidstat, /usr/bin/mpstat
```

### 5. 监控数据外发

监控数据（尤其含进程名、命令行、用户信息的 ps/pidstat 输出）属于敏感数据，**别随手贴到工单/群聊/外部平台**；对接监控平台时走内网 + 认证（详见 [[13.4-监控体系]] 的安全章节）。

## 故障排查

### 案例一：load average 高但 CPU 不高

**现象**：uptime 显示 load 8+，但 top 里 %Cpu(s) 的 id（空闲）还有 70%。

**排查**：

```shell
# 1. 看 CPU 分布：wa 高 = 在等 IO，不是 CPU 忙
vmstat 1 5
# 2. 看不可中断进程（D 状态 = 阻塞在 IO 上）
top -b -n 1 | awk '$8=="D"' | head
# 3. 定位 IO 瓶颈盘
iostat -x 1 3
```

**结论**：load 包含 D 状态（等 IO）进程，**IO 阻塞时 CPU 闲着但 load 照样高**。本机实测第二行 vmstat：b=1、wa=12%，r 列只有 2-3——运行队列不长，但 IO 队列在排队，load 2.47 里相当一部分是「等 IO」贡献的。解决方向是 IO（磁盘性能/并发写/换 SSD），不是加 CPU。

### 案例二：sar 查不到历史数据

**现象**：`sar` 命令能用，但 `sar -u -f /var/log/sysstat/sa18` 报「没有数据」，或目录里根本没有 sa 文件。

**排查**：

```shell
# 1. 确认 sysstat 服务/timer 状态
systemctl list-timers | grep sysstat
systemctl status sysstat --no-pager | head -6
# 2. 看采集配置文件
grep ENABLED /etc/default/sysstat
# 3. 看历史文件是否生成
ls -la /var/log/sysstat/
# 4. 手动触发一次采集验证
/usr/lib/sysstat/sa1 1 1 && ls -la /var/log/sysstat/
```

**结论**（Ubuntu 22.04+）：采集由 systemd timer（sysstat-collect.timer）驱动，直接调 sa1；**改 ENABLED=true 不是必须的**（本机实测 ENABLED=false 但 sa 文件照常生成）。若真的没数据：先 `systemctl enable --now sysstat-collect.timer`，再手动 `sa1 1 1` 验证写入；Red Hat 系则是确认 cron.d/sysstat 存在且 cron 服务在跑。

### 案例三：单核飙高、多核空闲

**现象**：某进程 %CPU 100%，但系统总体 CPU 使用率只有 20% 多，load 也不高。

**排查**：

```shell
# 1. 确认是不是单核热点
mpstat -P ALL 1 3     # 某核 usr+sys 接近 100%，其他核空闲
# 2. 确认进程的 CPU 亲和性
taskset -pc <PID>
# 3. 多线程进程看线程分布
top -H -p <PID>
```

**结论**：单线程程序天然只占 1 核（本机实测 CPU7 usr+sys ≈ 65% 就是单核热点）；多线程程序若所有线程挤在同一核（亲和性设置、锁竞争、GIL），也是单核飙高。解决：多进程/多线程改造、taskset 分散亲和性、或用 `perf` 查热点函数（[[16.2-CPU 性能]] 有深入方法）。

### 案例四：free 显示还有内存，服务却被 OOM 杀

**现象**：free -h 显示 free 还有 2GB，但 dmesg 里出现 oom-killer，服务被 kill。

**排查**：

```shell
# 1. 确认是否真的被 OOM
dmesg | grep -i "out of memory\|oom-kill" | tail
# 2. 看 available（不是 free）——cache 能否回收
free -h
# 3. 看是不是瞬时内存尖峰（如大批量任务同时启动）
sar -r -f /var/log/sysstat/saXX | sort -k3 -n | tail
# 4. 看单进程内存占用排行
ps aux --sort=-rss | head
```

**结论**：free 低不代表不够（buff/cache 可回收），**OOM 杀进程看的是 available + 瞬时分配**——最典型的是多个大内存进程同时启动（内存尖峰），或某个进程 RSS 突增（内存泄漏）。解法：限制单进程内存（ulimit -v、cgroup 的 memory.limit）、错峰启动、或给关键服务加 oom_score_adj 保护（[[08.3-Swap 与 OOM]] 详述）。

## 常见问题

```text
Q1: htop 命令不存在？
A: htop 不是默认安装（Ubuntu 默认只有 top）。apt install htop 即可；
   不想装就用 top，交互键 1/P/M/c/H 覆盖 90% 需求。

Q2: load average 高就一定是 CPU 不够？
A: 不一定。load 包含「等待 IO 的不可中断进程（D 状态）」，wa 高说明是 IO
   瓶颈不是 CPU。先 vmstat 看 wa 和 r/b 列再下结论。

Q3: sar 查不到历史数据？
A: Ubuntu 22.04+ 检查 systemd timer（systemctl list-timers | grep sysstat）；
   传统路径改 /etc/default/sysstat 的 ENABLED="true"。Red Hat 系装完默认采集，
   检查 /etc/cron.d/sysstat。手动验证：/usr/lib/sysstat/sa1 1 1。

Q4: iostat 的 %util 100% 就是磁盘瓶颈？
A: 不一定。%util 只是「设备忙的时间占比」，SSD 并发能力强、%util 100% 但
   延迟可能很低；要结合 await（延迟）、r/s w/s（IOPS）和吞吐综合判断。
   反过来 %util 低但 await 高，可能是坏道重试或设备被限流。

Q5: free 的 free 列还有 1GB，为什么还卡？
A: 看 available 不看 free。buff/cache 里的页缓存是「可用内存」的一部分，
   available 才是内核预估可分配给应用的内存；free 少但 available 充足 =
   内存健康。

Q6: top 里进程 %CPU 超过 100% 正常吗？
A: 正常。top 的 %CPU 是单核百分比，多线程进程可以超过 100%（如 200% =
   用满 2 核）。8 核机器单进程最高 800%。判断瓶颈看「相对核数」，不是绝对值。

Q7: swap 用了很多，是不是内存不够？
A: 不一定。内核会把长期不活跃的页换出（主动回收），swap 有占用≠内存压力。
   真正的信号是 vmstat 的 si/so 持续 >0（频繁换入换出）+ available 接近 0。

Q8: vmstat 的 r 列和 load average 有什么关系？
A: r 是「当前采样瞬间」的运行队列长度（R 状态），load 是「一段时间」的
   指数加权平均（含 D 状态）。r 长期接近/超过核数 = CPU 饱和；
   load 高但 r 不高 = 多半是 IO 阻塞（D 状态）贡献的。

Q9: sar 和 pidstat 都看 CPU，区别是什么？
A: sar 是系统级历史监控（后台采集、事后回溯、看整体趋势）；pidstat 是
   进程级实时监控（定位具体哪个进程/线程吃资源）。排查先 sar 定位时段，
   再 pidstat 定位进程。

Q10: 云主机 top 里的 st（steal）很高说明什么？
A: st 是被虚拟化宿主机「偷走」的 CPU 时间——宿主机上其他虚拟机在抢 CPU。
   st 持续 >10% 说明云主机 CPU 资源被超卖挤压，找云厂商或升级实例规格，
   本地调优无效。
```

## 面试题

```text
1. load average 和 CPU 使用率的区别？
   答：load average 是运行队列（R + D 状态）长度的指数加权平均，单位是
   「任务数」；CPU 使用率是 CPU 忙的时间占比。load 高而 CPU 空闲，通常是
   不可中断进程（等 IO）造成的——load 衡量「饱和度」，CPU 使用率衡量
   「利用率」，两者不能互相替代。

2. top 里的 us/sy/wa/st 分别代表什么？wa 高怎么排查？
   答：us=用户态、sy=内核态、wa=等待 IO、st=被虚拟化抢占。wa 高说明 CPU
   在等磁盘/网络 IO 完成，用 iostat -x 看哪块盘 await/%util 高，vmstat
   看 b 列和 bi/bo，再用 pidstat -d / iotop 定位读写进程。

3. 怎么定位「单核飙高、多核空闲」？
   答：mpstat -P ALL 1 3 看每核——某核 usr+sys 接近 100% 而其他核空闲，
   说明单线程程序或锁竞争/亲和性导致的热点。继续用 top -H -p 看线程，
   taskset -pc 查亲和性，perf top 查热点函数。

4. iostat 的 await、svctm、%util 分别指什么？怎么判断磁盘饱和？
   答：await=平均 IO 完成延迟（排队 + 服务时间）；svctm=平均服务时间
   （2.6 内核后已无真实意义，可忽略）；%util=设备繁忙时间占比。判断饱和：
   await 高 + %util 持续接近 100% + aqu-sz 队列持续增长 = 磁盘饱和；
   await 高但 %util 低 = 设备不忙但单请求慢（坏道/限流）。

5. 如何判断内存不足？free 的 buff/cache 和 available 是什么关系？
   答：看 available（内核预估可分配内存）而不是 free；buff/cache 是磁盘
   缓存、可回收，回收后计入 available。内存不足的信号：available 持续
   走低 + vmstat si/so 持续 >0 + 出现 OOM kill。swap 有使用不一定不足。

6. sar 为什么能查历史？数据存在哪？怎么调整保留天数？
   答：sysstat 的后台采集器 sadc 通过 cron/timer 定时采样（默认每 10 分钟），
   写入 /var/log/sysstat/saXX（每天一个文件，约 1MB）。保留天数由
   /etc/sysstat/sysstat（Ubuntu）或 /etc/sysconfig/sysstat（RHEL）的
   HISTORY 参数控制。

7. 监控频率怎么定？10 分钟粒度够吗？
   答：分层定。实时排查看秒级（sar 1 5、vmstat 1 5）；趋势与基线用
   sysstat 的 10 分钟粒度足够（一天 144 个点）；秒级以下的抖动问题靠
   故障时现场抓（top -b 存文件、sar -o 落盘），不能事后靠 10 分钟粒度
   定位。监控粒度要与告警/复盘需求匹配，太密浪费存储，太疏看不到尖峰。

8. 一台机器 load 8、CPU 空闲 60%，怎么一步步排查？
   答：按 USE 法：① vmstat 看 wa（IO 等待）和 r/b 列——wa 高、b>0 说明
   IO 阻塞；② top 找 D 状态进程；③ iostat -x 看哪块盘 await/%util 高；
   ④ 定位读写进程（pidstat -d/iotop）；⑤ 若 wa 不高、r 列高，才是 CPU
   排队问题，再看 mpstat 每核分布与进程线程数。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 排查顺序固定：**top 总览 → vmstat 分方向（CPU/IO/内存）→ 专项工具（iostat/mpstat/pidstat）深入**，别一上来就翻某个工具的细节。
2. 先红后黑：先确认服务/进程状态（红），再查资源消耗（黑）；服务都挂了就别浪费时间调 CPU 参数。
3. 磁盘性能只看 `iostat -x` 的 await 和 %util，普通模式（无 -x）看不到延迟，信息量不够。
4. 单核问题用 `mpstat -P ALL`，多线程进程用 `top -H -p` 看线程；`taskset` 查亲和性。
5. 事后分析一律 `sar -f /var/log/sysstat/saXX`；故障现场用 `sar -o` 落盘，别只靠屏幕。
6. 先建基线再定阈值：用一周 sar 历史算出正常区间，阈值跟着基线走（CPU 70%/内存 available 30%/磁盘 util 70%/网络 70% 只是通用起点）。
7. Ubuntu 22.04+ 采集由 systemd timer 驱动，管理用 `systemctl list-timers | grep sysstat`，别被老教程的 ENABLED 误导（见坑 5）。
8. 监控数据是敏感数据：进程命令行含密钥、sa 文件反映业务负载，权限收紧（hidepid、chmod 600），外发要脱敏。

### 踩坑记录

```text
坑 1：htop 命令不存在
结论：敲 htop 报 command not found。
原因：htop 不是默认安装，Ubuntu 只预装 top。
解法：apt install htop，或直接用 top（交互键 1/P/M/c/H 覆盖大部分需求）。

坑 2：load average 高就以为是 CPU 不够
结论：load 8+，加了 CPU 也没用，问题依旧。
原因：load 包含「等待 IO 的不可中断进程（D 状态）」，IO 阻塞时 CPU 空闲
     但 load 照样高——看错了方向。
解法：vmstat 看 wa 和 r/b 列，wa 高说明是 IO 瓶颈；iostat 定位磁盘。

坑 3：只看 top 的 %CPU 忽略单核飙高
结论：某进程 %CPU 100%，但系统整体 CPU 才 20%，以为没压力。
原因：%CPU 是单核百分比，多核机器一个 100% 的进程只占 1/8 的算力；
     单线程程序天然只能吃满 1 核。
解法：mpstat -P ALL 看每核分布，top 按 1 看每核；判断瓶颈用
     「load/核数」和「整体使用率」，不是单进程 %CPU。

坑 4：iostat 的 %util 100% 就急着换磁盘
结论：%util 100% 就判定硬件瓶颈换盘，其实还有优化空间。
原因：%util 接近 100% 只说明「设备忙」，SSD 并发下 %util 100% 延迟可能
     很低；机械盘 + 小 IO 随机写也可能把 util 打满但吞吐不高。
解法：结合 await（延迟）和 r/s w/s（IOPS）综合判断；先看是不是进程
     读写模式问题（日志刷盘、全表扫描）再考虑换硬件。

坑 5：改 ENABLED=true 想开采集，改了没用/改 ENABLED=false 想停，停不掉
结论：Ubuntu 22.04+ 上 ENABLED 改来改去，sa 文件照常生成。
原因：采集由 systemd timer（sysstat-collect.timer）直接调 sa1 完成，
     绕过了 debian-sa1 脚本里的 ENABLED 检查；ENABLED 只影响 cron.d
     路径（systemd 下 debian-sa1 直接 exit 0）。
解法：开/停采集用 systemctl enable/disable --now sysstat-collect.timer
     sysstat-summary.timer；ENABLED 只在 sysvinit 或手动执行 debian-sa1
     时有效。

坑 6：sar 有历史但查不到某天的数据
结论：sar -f /var/log/sysstat/saXX 报错或没数据。
原因：HISTORY 保留期外的 sa 文件已被清理；或当天机器关机/采集没跑；
     或文件权限不对（非 root 用户读不了）。
解法：ls /var/log/sysstat/ 确认文件存在；调大 HISTORY 保留期；
     用 root 或 sudo 查历史。

坑 7：free 还有 1GB 就判定内存不足，去加内存
结论：free 显示只剩 1GB，加完内存还是「不够」。
原因：free 列不含可回收的 buff/cache，判断内存是否够用要看 available。
解法：看 available 列（本机 free 1.1Gi 但 available 7.9Gi，完全健康）；
     确认内存压力看 vmstat si/so 和 dmesg 的 OOM。

坑 8：用 sar 10 分钟粒度回溯秒级抖动，什么都看不到
结论：复盘时说「当时 CPU 飙到 100%」，sar 历史里最高才 30%。
原因：10 分钟采样粒度太粗，秒级尖峰被平均掉了。
解法：故障时用 sar -o /tmp/xxx 1 60 秒级落盘现场数据；
     常驻监控要秒级粒度用 Prometheus（[[13.4-监控体系]]）。

坑 9：pidstat -d 报权限不足
结论：普通用户跑 pidstat -d 看不到其他用户的进程 IO。
原因：读其他进程的 IO 计数器需要 root 权限（/proc/<pid>/io）。
解法：sudo 运行；运维账号在 sudoers 白名单里加 pidstat/iostat 等命令
     （见安全与权限章节）。
```
