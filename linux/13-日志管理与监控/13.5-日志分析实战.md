## 概述

日志分析实战 = 从海量日志里「检索定位 + 分析原因 + 追踪审计」。核心思路：先用 grep/journalctl 检索出相关日志，再用 awk/sort 统计聚合（找出异常模式），最后按时间线追踪还原事件。工具组合：journalctl（systemd 日志）+ grep/awk/sed（三剑客）+ 时间线分析。这是「日志会用」到「日志分析得好」的关键。

```text
日志分析三板斧：
1. 检索 —— grep/journalctl 过滤出相关日志
2. 聚合 —— awk/sort/uniq 统计，找异常模式
3. 追踪 —— 按时间线还原事件，定位根因
```

## 核心概念

1. **日志检索**：从日志里快速找到「相关的那几行」，先缩小范围（时间/服务/级别），再搜关键词。
2. **异常定位**：从日志里找到「异常在哪、什么原因」，用 awk+sort+uniq 做聚合统计，看出异常模式。
3. **审计追踪**：按时间线还原「谁在什么时候做了什么」，数据源是 auth.log + history + auditd + 应用日志。

```text
检索技巧：
1. 先缩小范围（服务/时间/级别），再搜关键词
2. 多模式 grep -E 'a|b'，排除噪音 grep -v
3. 正则表达式（03 章）做精确匹配
```

## 工作原理

日志分析的本质是「过滤 → 聚合 → 关联」：

1. **过滤**：用时间、服务、级别、关键词把海量日志缩小到相关的那几行。
2. **聚合**：用 awk/sort/uniq 对字段做分组统计（状态码、错误类型、来源 IP），找出「什么最多/什么异常」。
3. **关联**：按时间线把分散的日志串起来，还原事件的前因后果（错误往往是结果，原因在之前的日志）。

```text
日志分析流程：
过滤（时间/服务/级别/关键词）→ 聚合（awk/sort/uniq 统计）→ 关联（时间线还原事件）
```

## 常用命令与配置

```shell
# 按服务 + 时间 + 级别过滤
journalctl -u nginx --since "1 hour ago" -p err
# grep 关键词检索
grep -i 'error' /var/log/syslog | tail
# 多模式 + 排除
grep -E 'error|fail' /var/log/app.log | grep -v 'known_issue'
# 按时间范围
journalctl --since "2026-08-18 10:00" --until "2026-08-18 12:00"
# 统计 nginx 状态码分布（找异常）
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
# 统计失败登录来源
grep 'Failed password' /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn
```

## 配置文件解析

日志分析要先了解日志格式，才能正确取字段。nginx 的 access log 格式由 log_format 定义：

```text
# nginx 默认 combined 格式
log_format combined '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" "$http_user_agent"';
```

```text
字段位置（awk 按空格分列）：
$1 客户端 IP | $4 [时间] | $6 "请求方法 | $7 请求路径 | $9 状态码 | $10 响应字节数
```

```text
syslog 日志格式：
时间 主机名 进程名[PID]: 消息内容
# 例：8月18 23:20:17 lw-Vostro-7580 systemd[1]: Starting sysstat-collect.service...
```

## 应用场景实战

### 场景一：nginx 大量 401，定位异常请求

```shell
# 1. 统计状态码分布
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
# 2. 看 401 的请求都是什么接口
awk '$9==401{print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
# 3. 看 401 的来源 IP
awk '$9==401{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
```

### 场景二：安全审计——追踪某时段谁登录了

```shell
# 1. 看登录记录
grep 'Accepted' /var/log/auth.log
# 2. 按用户和 IP 聚合
grep 'Accepted' /var/log/auth.log | awk '{print $9, $11}' | sort | uniq -c
# 3. 追踪某用户的后续操作
grep 'session opened' /var/log/auth.log | grep 'user'
```

## 性能与调优

```text
1. 大文件检索 —— 别 grep 全量日志，先 journalctl --since 缩小时间，或 tail 截取
2. 建索引 —— 日志量巨大用 ELK/Loki 建索引，检索从秒级 O(n) 变成毫秒级
3. 聚合前置 —— 用 awk 一次读完做统计，别 grep 多次重复扫
4. 正则开销 —— 复杂正则慢，能用固定字符串（grep -F）就用
```

## 安全与权限

```text
1. 日志权限 —— auth.log 等含敏感信息，分析结果别外传
2. 命令历史 —— .bash_history 可能含明文密码，审计时注意保护
3. auditd 权限 —— 审计日志只有 root 可读，防篡改
4. 合规 —— 等保/CIS 要求日志审计追踪，保留期限要达标
```

## 故障排查

### 日志量太大 grep 卡死

```shell
# 1. 先看文件大小
ls -lh /var/log/app.log
# 2. 缩小时间范围再搜
journalctl --since "1 hour ago" -p err
# 3. 或只搜最近 N 行
tail -n 100000 /var/log/app.log | grep 'error'
```

### 聚合统计没排序看不出重点

```shell
# 正确：排序倒序看 TOP
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head
# 错误：没排序，结果平铺看不出「什么最多」
```

## 常见问题

```text
Q1: 日志量巨大，grep 全量搜很慢？
A: 先缩小范围（时间/服务），或 tail 截取最近，或建索引（ELK/Loki）。

Q2: 只看 error 日志为什么定位不到根因？
A: 错误往往是结果，原因在之前的日志。grep -C 5 看上下文，或按时间线还原。

Q3: 多个日志时间对不上？
A: 时间格式/时区不同，或没配 NTP。统一 NTP 时间同步，分析前对齐时间格式。

Q4: 日志里没报错就是没问题？
A: 不一定。应用可能没打日志，或级别太高没记录。确认日志级别合适，关键操作要打日志。
```

## 面试题

```text
1. 日志分析的核心思路？
   答：过滤（缩小范围）→ 聚合（awk/sort/uniq 统计找异常）→ 关联（时间线还原事件）。

2. 怎么统计 nginx 日志里各状态码的数量？
   答：awk '{print $9}' access.log | sort | uniq -c | sort -rn，$9 是状态码字段。

3. 日志量太大检索慢怎么优化？
   答：先按时间/服务缩小范围，或用 ELK/Loki 建索引，把 O(n) 扫描变成索引查询。

4. 安全审计追踪看哪些数据源？
   答：auth.log（登录）、.bash_history（命令历史）、auditd（系统调用审计）、应用日志。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 日志分析先缩小范围（服务/时间/级别），再搜关键词
2. 用 awk+sort+uniq 做聚合统计，别一行行肉眼看
3. 结合时间线还原事件，别孤立看单条日志
4. 安全审计关注 auth.log + history + auditd
5. 日志分析能力 = grep/awk/sed 三剑客 + 时间线思维

### 踩坑记录

```text
坑 1：日志量大，grep 全量搜很慢
结论：grep 全量日志卡半天。
原因：日志文件巨大，全量扫描慢。
解法：先缩小范围（时间/服务），或 grep 配合 tail/head，或建索引（ELK/Loki）。

坑 2：只看错误日志，忽略上下文
结论：只 grep error，没看错误前后的日志，定位不到根因。
原因：错误往往是结果，原因在之前的日志里。
解法：grep -C 5（前后 5 行）看上下文，或按时间线还原。

坑 3：日志时间时区/格式不一致，时间线对不上
结论：多个日志的时间对不上，追踪混乱。
原因：不同日志时间格式/时区不同，或没配 NTP 时间不同步。
解法：统一 NTP 时间同步，分析前先对齐时间格式。

坑 4：聚合统计忘了排序，看不出重点
结论：awk 统计了但没排序，结果一堆平铺。
原因：没 sort -rn 倒序，看不出「什么最多」。
解法：awk ... | sort | uniq -c | sort -rn，倒序看 TOP。

坑 5：把「日志里没报错」当「没问题」
结论：日志没 error，以为系统正常，其实有问题没记日志。
原因：应用可能没打日志，或日志级别太高没记录。
解法：确认日志级别合适（debug/info），关键操作要打日志。
```
