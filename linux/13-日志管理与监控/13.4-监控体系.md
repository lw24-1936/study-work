## 概述

单机监控工具（top/sar，见 [[13.3-系统监控]]）只能看单台机器的当下与历史，几十上百台机器就需要一个**监控体系**：统一的采集、存储、可视化、告警。现代开源监控的事实标准是 **Prometheus 全家桶**：

```text
监控体系架构（Prometheus 全家桶）：
各服务器 node_exporter（暴露机器指标，:9100）
      ↑ Prometheus 定时拉取（scrape，默认 15s）
      ↓ 本地时序数据库（TSDB）存储
  Grafana 查询可视化（数据源 → 面板 → 仪表盘）
  Alertmanager 告警（分组/去重/静默 → 邮件/钉钉/微信/webhook）
```

另外两条路线：**Zabbix**（传统 Agent 模式，适合纯基础设施、自带报表告警）、**云厂商监控**（阿里云 CMS / AWS CloudWatch，开箱即用但绑定云平台）。选型没有绝对优劣——见「核心概念」的选型对比表。

本机实测环境：Ubuntu（apt 可直接安装 `prometheus-node-exporter` 包），Prometheus/Grafana/Zabbix 未安装；node_exporter 通过 apt 部署成功并抓取了真实 /metrics 数据（见工作原理）。

## 核心概念

### 1. 监控层次（四层模型）

一个完整的监控体系覆盖四个层次，从下往上：

| 层次 | 监控什么 | 典型指标 | 工具 |
|---|---|---|---|
| 基础设施 | 机房/服务器/网络设备/电源 | 温度、风扇、UPS、交换机流量、光模块 | IPMI、SNMP、云监控 |
| 操作系统 | CPU/内存/磁盘/网络/进程 | node_exporter 的 node_* 指标 | node_exporter、Zabbix agent |
| 应用 | 中间件/数据库/框架 | QPS、RT、连接数、GC、慢查询 | 应用 exporter（mysqld_exporter 等） |
| 业务 | 用户视角的可用性与体验 | 下单成功率、支付延迟、转化率 | 埋点、业务指标 API |

**越往下越标准化**（所有机器指标大同小异），**越往上越定制化**（业务指标千差万别）。监控体系建设的顺序：先把 OS 层铺满（投入产出比最高），再补基础设施层，最后做应用/业务层。

### 2. 监控四黄金信号（Google SRE 提出）

| 信号 | 含义 | 例子 | 典型告警 |
|---|---|---|---|
| 延迟 Latency | 请求多久返回 | HTTP 响应时间 P99、数据库查询耗时 | P99 > 500ms 持续 5 分钟 |
| 流量 Traffic | 系统承接多少请求 | QPS、带宽、并发连接数 | QPS 突然下跌 50%（异常） |
| 错误 Errors | 请求失败率 | HTTP 5xx 比例、异常数 | 错误率 > 1% |
| 饱和度 Saturation | 资源有多满、排队多长 | CPU/内存/磁盘利用率、队列长度 | CPU > 90% 持续 10 分钟 |

**四黄金信号是「服务视角」**：从用户请求的角度判断服务健康；**USE 法是「资源视角」**（利用率/饱和度/错误，见 [[16.1-性能分析方法论]]）：从资源的角度判断瓶颈。两者互补——服务慢先看黄金信号定位到「哪个环节慢」，再用 USE 法看「那个环节的哪个资源饱和」。

### 3. Prometheus 架构组件

| 组件 | 角色 | 默认端口 | 说明 |
|---|---|---|---|
| Prometheus Server | 采集 + 存储 + 查询 + 规则评估 | 9090 | 核心：定时 scrape、TSDB 存储、PromQL 查询、告警规则评估 |
| node_exporter | 暴露操作系统指标 | 9100 | 每台机器部署一个，指标名 node_* 前缀 |
| 其他 exporter | 暴露应用/中间件指标 | 各自端口 | mysqld_exporter(9104)、blackbox_exporter(9115，探活)、nginx_exporter 等 |
| pushgateway | 接收一次性任务推送 | 9091 | 短生命周期任务（批处理/定时任务）主动推指标 |
| Alertmanager | 告警通知 | 9093 | 分组/去重/静默/抑制，通知邮件/钉钉/微信/webhook |
| Grafana | 可视化 | 3000 | 数据源 + 面板 + 仪表盘三级结构 |

**Pull 模型**（Prometheus 主动拉取）vs **Push 模型**（Zabbix 默认 agent 推、prometheus pushgateway）：pull 让 Prometheus 掌握主动权——能自动发现目标、能判断目标存活（up 指标）、采集行为可控；push 适合无法被拉取的场景（NAT 后、短生命周期任务）。

### 4. Prometheus 指标类型

| 类型 | 语义 | 典型例子 | 查询方式 |
|---|---|---|---|
| counter | 只增不减的计数器（重启归零） | node_cpu_seconds_total、请求总数 | `rate()` / `increase()` 算速率 |
| gauge | 可增可减的瞬时值 | node_memory_MemAvailable_bytes、温度 | 直接用、avg/max/min |
| histogram | 分桶计数（累计桶 + sum + count） | 请求延迟分布 | `histogram_quantile(0.99, ...)` 算 P99 |
| summary | 客户端预计算分位数 | 延迟分位数（不可跨实例聚合） | 直接用 _quantile 系列 |

**counter 必须用 rate()/increase() 转换**——裸的 counter 只增不减，看绝对值没有意义；`rate(node_xxx_total[5m])` 才是「每秒速率」。histogram 在服务端聚合算分位数（可跨实例），summary 在客户端算（不能跨实例 sum，会失真）。

### 5. 指标命名、标签、job/instance、up

- **指标名**：`node_cpu_seconds_total`，命名规范 `<命名空间>_<子系统>_<单位>[_total]`，counter 通常以 `_total` 结尾。
- **标签 label**：指标的维度，`node_cpu_seconds_total{cpu="0", mode="idle"}` 里的 `cpu`、`mode`。**标签是查询分组（by）和过滤（{}）的基础，但标签值组合越多基数越高**——高基数是 TSDB 性能杀手（见性能与调优）。
- **job / instance**：每个采集目标自动带 `job`（采集任务名，来自 scrape_configs 的 job_name）和 `instance`（target 地址，如 `192.168.1.10:9100`）标签。
- **up 指标**：Prometheus 对每个 target 自动生成 `up{job=..., instance=...}`，**1 = 抓取成功，0 = 抓取失败**——「目标存活」监控就用它：`up == 0` 告警。

### 6. 时序数据库 TSDB 与采样

Prometheus 自带本地 TSDB：数据按 `<指标名 + 标签集> → 时间序列` 组织，每条序列是一串 (时间戳, 值) 样本，按 2 小时一个块压缩存储。关键参数：**采集间隔**（scrape_interval，默认 15s）、**评估间隔**（evaluation_interval，默认 15s）、**保留期**（--storage.tsdb.retention.time，默认 15 天）。采样频率与保留期直接决定磁盘占用（见性能与调优）。

### 7. Zabbix 核心概念（对照理解）

| Zabbix 概念 | 含义 | Prometheus 对应 |
|---|---|---|
| Agent | 部署在目标机的采集程序（主动/被动两种模式） | node_exporter |
| Item | 一条采集项（如 CPU 使用率） | 指标 metric |
| Trigger | 触发条件（表达式，如 item > 90 持续 5 分钟） | 告警规则 alert rule |
| Action | 触发后执行的动作（通知/远程命令） | Alertmanager 的 route + receiver |
| Template | 预定义 item/trigger 的模板，套到主机上 | 规则文件 + 仪表盘模板 |
| Mediatype | 通知渠道（邮件/短信/脚本） | receiver |

Zabbix 是 **push + pull 混合**：agent 主动模式（agent 连 server 上报）适合 NAT 环境，被动模式（server 轮询 agent）与 Prometheus 类似。Zabbix 自带 Web UI、报表、自动发现，传统运维（网络设备/Windows 服务器/纯基础设施）场景比 Prometheus 生态开箱即用；但 PromQL + Grafana 的灵活性和云原生（K8s）支持是 Zabbix 比不了的。

### 8. 监控选型对比

| 维度 | Prometheus + Grafana | Zabbix | 云监控（阿里云 CMS / CloudWatch） |
|---|---|---|---|
| 架构 | pull（+pushgateway），TSDB | agent 主动/被动，关系型数据库存配置 | 云平台内置 agent |
| 部署成本 | 中（多组件要编排） | 中（server+agent+DB） | 低（开箱即用） |
| 可视化 | Grafana（最强） | 自带 Web UI（够用） | 自带（一般） |
| 告警 | Alertmanager 灵活（路由/静默/抑制） | 自带 trigger/action | 自带，绑短信/电话 |
| 云原生（K8s） | 事实标准（kube-prometheus） | 弱 | 绑定自家云 |
| 动态发现 | 服务发现（K8s/consul/文件） | 网络发现/自动发现 | 云资源自动接入 |
| 适合场景 | 云原生、微服务、开发团队 | 传统基础设施、网络设备、Windows | 单一云厂商、不想自运维 |
| 学习曲线 | PromQL 有门槛 | 概念多但文档全 | 低 |

**选型建议**：新项目/云原生选 Prometheus；纯传统机房（交换机/Windows/老应用）选 Zabbix；单云厂商图省事用云监控；大厂通常是 Prometheus 为主 + 云监控兜底告警通道。

## 工作原理

### Pull 模型的数据流

```text
采集周期（默认 15s）：
Prometheus → HTTP GET target:9100/metrics → 解析文本格式指标
         → 附加 job/instance 标签 → 写入本地 TSDB → 按 2h 块压缩

查询：
Grafana（或 Prometheus UI）→ PromQL 查询 → TSDB 扫描 → 绘图

告警：
Prometheus 每 evaluation_interval 评估规则文件中的 expr
   → 持续 for 时长后变为 firing → 推给 Alertmanager
   → Alertmanager 按 route 分组/去重 → 按 receiver 通知
   → 静默/抑制规则在通知前拦截
```

### 时序数据模型

一行指标就是一个样本：`指标名{标签=值,...} 值 时间戳`。例如本机实测抓到的：

```text
node_load1 2.47
node_memory_MemAvailable_bytes 8.510992384e+09
node_cpu_seconds_total{cpu="0",mode="idle"} 1.92225181e+06
```

相同「指标名 + 标签集」的样本按时间排列就是一条时间序列。PromQL 查询本质是：**选序列（匹配标签）→ 做时间范围聚合（rate/avg_over_time）→ 做维度聚合（sum by）**。

### 实测（本机）——node_exporter 部署与 /metrics 抓取

```shell
# Ubuntu 安装（注意包名带 prometheus- 前缀）
sudo apt install -y prometheus-node-exporter
sudo systemctl start prometheus-node-exporter
# 验证指标暴露
curl -s localhost:9100/metrics | head -8
```

```text
$ curl -s localhost:9100/metrics | head -8
# HELP go_gc_duration_seconds A summary of the pause duration of garbage collection cycles.
# TYPE go_gc_duration_seconds summary
go_gc_duration_seconds{quantile="0"} 0
go_gc_duration_seconds{quantile="0.25"} 0
go_gc_duration_seconds{quantile="0.5"} 0
go_gc_duration_seconds{quantile="0.75"} 0
go_gc_duration_seconds{quantile="1"} 0
go_gc_duration_seconds_sum 0
go_gc_duration_seconds_count 0
```

/metrics 输出格式：`# HELP` 说明 + `# TYPE` 类型声明 + 指标行。**go_* 指标是 exporter 自身的运行时指标**（Go 进程内存/GC），不是机器指标；机器指标是 `node_*` 前缀。

```text
$ curl -s localhost:9100/metrics | grep -c "^node_"
2655        # 本机共 2655 个 node_* 指标行

$ curl -s localhost:9100/metrics | grep -E "^node_(cpu_seconds_total|memory_MemAvailable_bytes|load1|filesystem_avail_bytes|network_receive_bytes_total)"
node_cpu_seconds_total{cpu="0",mode="idle"} 1.92225181e+06
node_cpu_seconds_total{cpu="0",mode="iowait"} 21468.58
node_cpu_seconds_total{cpu="0",mode="system"} 8644.14
node_cpu_seconds_total{cpu="0",mode="user"} 22274.59
node_memory_MemAvailable_bytes 8.510992384e+09
node_load1 2.47
node_filesystem_avail_bytes{device="/dev/sda2",fstype="ext4",mountpoint="/"} 8.66365976576e+11
node_network_receive_bytes_total{device="br-3b8a83784ecf"} 6.2343186e+07
```

实测解读：`node_cpu_seconds_total` 带 `cpu`/`mode` 标签（counter，要用 rate() 转速率）；`node_memory_MemAvailable_bytes` 是 gauge（本机 8.5GB，与 `free -h` 的 available 7.9Gi 对应，数值差异是抓取时刻不同）；`node_load1` 2.47 与 uptime 一致。**注意 exporter 暴露的是裸计数器，所有「每秒/百分比」都要用 PromQL 现算**——这是与 sar 的最大区别。

### 本机其他端口说明

```text
$ ss -tlnp | grep -E ":9090|:9100|:3000"
LISTEN 0  4096  *:9100  *:*  users:(("prometheus-node",pid=3105838,fd=3))
LISTEN 0  511   0.0.0.0:3000  *:*  users:(("node",pid=1660949,fd=24))
```

本机 3000 端口是 Node.js 业务服务（**不是 Grafana**），9100 是我们刚装的 node_exporter；9090（Prometheus）、9093（Alertmanager）、3000（Grafana）均未被占用。**部署前先 ss -tlnp 查端口占用，避免撞端口**（Grafana 与常见 Node 服务都爱用 3000，见踩坑记录坑 3）。

```shell
# 启动
./prometheus --config.file=prometheus.yml --storage.tsdb.retention.time=15d &
```

## 配置文件解析

### prometheus.yml（Prometheus 主配置）

```yaml
# prometheus.yml
global:
  scrape_interval: 15s        # 全局采集间隔（默认 15s）
  evaluation_interval: 15s    # 告警规则评估间隔

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['localhost:9093']

rule_files:
  - /etc/prometheus/rules/*.yml    # 告警规则文件（可多个）

scrape_configs:
  - job_name: 'node'               # job 名会作为标签
    static_configs:
      - targets: ['192.168.1.10:9100', '192.168.1.11:9100']
        labels:
          env: 'prod'              # 附加自定义标签
    # 服务发现替代静态列表：
    # file_sd_configs: [{files: ['/etc/prometheus/targets/*.yml']}]
    # kubernetes_sd_configs: [...]  # K8s 自动发现
```

关键字段：`scrape_interval`（采集频率，秒级指标可调 5s，量大调 30s）、`job_name`（一个 job 一组 target）、`targets`（host:port 列表）。**rule_files 里的规则文件改了要 curl -X POST /-/reload 才生效**。

### 告警规则文件（Prometheus 侧定义触发条件）

```yaml
# /etc/prometheus/rules/node.yml
groups:
  - name: node-rules
    rules:
      - alert: NodeDown                # 告警名
        expr: up == 0                  # 触发条件（PromQL）
        for: 2m                        # 持续 2 分钟才触发（防抖动）
        labels:
          severity: critical           # 自定义标签，供 Alertmanager 路由
        annotations:
          summary: "节点 {{ $labels.instance }} 挂了"
          description: "{{ $labels.instance }} 已停止上报，持续 2 分钟"

      - alert: HighCPU
        expr: 100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 90
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} CPU 使用率超过 90%"
```

关键字段：`expr`（PromQL 表达式，结果非空即触发）、`for`（**持续时长——防瞬时抖动误报的关键**）、`labels`（自定义标签，Alertmanager 据此路由）、`annotations`（告警内容模板，可用 {{ $labels.xxx }} 引用标签）。

### alertmanager.yml（告警通知配置）

```yaml
# alertmanager.yml
route:
  group_by: ['alertname', 'instance']   # 按什么分组
  group_wait: 30s        # 组内第一条告警等多久再发（聚合窗口）
  group_interval: 5m     # 组内新告警的发送间隔
  repeat_interval: 4h    # 同一告警重复通知的间隔
  receiver: 'default'
  routes:                                # 路由树：按标签分流
    - matchers: ['severity=critical']
      receiver: 'phone'                  # 严重告警走电话/短信
    - matchers: ['severity=warning']
      receiver: 'email'

receivers:
  - name: 'default'
    webhook_configs:
      - url: 'http://dingtalk-hook/xxx'  # 钉钉/企业微信 webhook
  - name: 'email'
    email_configs:
      - to: 'ops@example.com'
        smarthost: 'smtp.example.com:465'
```

**告警路由树**：Alertmanager 收到告警后按 route 树匹配标签（severity/环境/服务）分流到不同 receiver；同组告警合并成一条通知（group_by），避免告警风暴；`repeat_interval` 控制「同一个问题多久催一次」，4h 是合理起点。**静默 silence**：维护窗口在 Alertmanager Web UI 或 API 里挂静默（匹配标签 + 过期时间），维护期间不打扰。

### node_exporter 的 systemd 托管（Ubuntu 实测）

```text
# /usr/lib/systemd/system/prometheus-node-exporter.service（Ubuntu 实测内容）
[Service]
Restart=on-failure
User=prometheus
EnvironmentFile=/etc/default/prometheus-node-exporter
ExecStart=/usr/bin/prometheus-node-exporter $ARGS
ExecReload=/bin/kill -HUP $MAINPID
[Install]
WantedBy=multi-user.target
```

要点：**以非 root 用户（prometheus）运行**（最小权限）、`Restart=on-failure`（挂了自动拉起）、`EnvironmentFile` 提供 ARGS 扩展参数（如加 `--web.listen-address=:9101` 改端口）。自建服务照这个模板写即可。

### Red Hat 系差异

| 项 | Ubuntu/Debian | Red Hat（RHEL/CentOS/Rocky） |
|---|---|---|
| node_exporter 安装 | `apt install prometheus-node-exporter`（包名带前缀，二进制同名） | 无官方 RPM：下载官方 tarball 自装，或 Grafana/COPR 仓库 |
| exporter 服务 | systemd unit 自带（User=prometheus） | 自写 systemd unit（参考上方模板） |
| 防火墙放行 9100 | `ufw allow 9100/tcp` | `firewall-cmd --add-port=9100/tcp --permanent && --reload` |
| 强制访问控制 | AppArmor（一般不管 exporter） | **SELinux 默认 enforcing，exporter 监听端口/读 /proc 可能被拒**，需 `setsebool -P ...` 或放行策略 |
| Prometheus 安装 | tarball 或 `apt install prometheus`（仓库版较旧） | tarball 或 COPR 仓库 |
| Grafana 安装 | apt 官方仓库 | yum 官方仓库（rpm） |

**SELinux 是 Red Hat 系特有坑**：exporter 想监听非标准端口或被 SELinux 拒绝访问 /proc 时，先 `ausearch -m avc -ts recent` 查拒绝记录，再针对性放行（`semanage port -a -t http_port_t -p tcp 9100` 之类），别直接 `setenforce 0`。

### 场景二：CPU/内存/磁盘告警规则（PromQL 实战）

```yaml
# /etc/prometheus/rules/node.yml
groups:
  - name: node-basic
    rules:
      # CPU 使用率 > 90%（核心公式：100 - idle 比例）
      - alert: HighCPU
        expr: 100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 90
        for: 5m
        labels: {severity: warning}
        annotations:
          summary: "{{ $labels.instance }} CPU 超 90%"

      # 内存 available 不足 10%（gauge 直接用）
      - alert: LowMemory
        expr: node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes < 0.1
        for: 10m
        labels: {severity: critical}

      # 磁盘可用空间不足 10%
      - alert: DiskAlmostFull
        expr: node_filesystem_avail_bytes{fstype=~"ext4|xfs"} / node_filesystem_size_bytes{fstype=~"ext4|xfs"} < 0.1
        for: 5m
        labels: {severity: critical}

      # 节点失联（up 指标）
      - alert: NodeDown
        expr: up{job="node"} == 0
        for: 2m
        labels: {severity: critical}
```

**PromQL 要点**：counter 指标（node_cpu_seconds_total）必须 `rate(metric[5m])` 转速率；gauge 指标（内存/磁盘）直接比值；`avg by (instance)` 按实例聚合；标签过滤 `{mode="idle"}`、正则 `{fstype=~"ext4|xfs"}`。**写规则前先在 Prometheus Graph 页把 expr 跑一遍确认有数据**（坑 4 的教训）。

### 场景三：Grafana 仪表盘搭建

```text
1. 数据源：Configuration → Data Sources → Prometheus → URL http://prometheus:9090 → Save & Test
2. 新建仪表盘：+ → Dashboard → Add panel
3. 面板类型（按指标形状选）：
   - Time series 时间序列：CPU/内存/流量曲线（最常用）
   - Stat 仪表盘：单值大数字（当前 CPU、可用内存百分比）
   - Gauge 仪表盘：带阈值的仪表（磁盘使用率，绿黄红）
   - Heatmap 热图：延迟分布随时间（histogram_quantile 系列）

4. 变量（Variable）：仪表盘顶部下拉框（如选实例/环境），查询里用 $instance 引用
```

**仪表盘设计原则**：一屏讲一个故事（如「节点健康总览」）；黄金信号优先（延迟/流量/错误/饱和度）；关键面板配告警阈值线（如 CPU 90% 画红线）；少即是多——**仪表盘是给人快速判断用的，不是指标展览馆**；用变量减少重复面板。

Zabbix 的模板机制让「接入一台机器」变成纯 Web 操作（比 Prometheus 手写 yaml 快），代价是灵活性低——自定义指标要写 UserParameter 脚本。**两套都熟、按场景选**是加分项。

### 场景六：监控覆盖检查清单（上线前逐项打勾）

```text
□ CPU：使用率/load 曲线 + CPU>90% 告警（node_cpu_seconds_total）
□ 内存：available/swap + 内存不足告警（node_memory_MemAvailable_bytes）
□ 磁盘：容量使用率 + 磁盘满告警（node_filesystem_*_bytes）；inode 用完告警
□ 磁盘 IO：util/await 曲线（node_disk_*）——容量告警≠性能告警，两个都要
□ 网络：出入带宽 + 网卡错误/丢包（node_network_*）
□ 进程：关键进程存活（up{job="process"} 或 process_exporter）
□ 端口：关键端口监听（blackbox_exporter tcp 探测）
□ 证书：HTTPS 证书剩余天数（blackbox_exporter ssl 探测或 x509 exporter）
□ 服务探活：HTTP 可用性/延迟（blackbox_exporter http 探针）
□ 备份：备份任务是否成功（cron 结束后 pushgateway 上报结果，或 exporter 查备份日志）
□ 日志：错误日志告警（mtail/vector 提取日志指标）
□ 节点失联：up == 0 告警
□ 时间同步：node_timex / chrony exporter（时间漂移会引发证书/认证连环故障）
```

**覆盖原则**：监控的不是「有什么指标」，而是「业务依赖什么」——用户访问的端口、写数据的磁盘、发出去的证书、每天跑的备份，全都要有对应的「状态 + 告警」。

## 性能与调优

### 1. 采集间隔与评估间隔

- 默认 15s 够绝大多数场景；秒级敏感（如交易系统）可调 5s，但要算存储账。
- 存储量估算：`指标数 × 标签组合数 × (86400/间隔秒) × 8字节 × 保留天数`。1000 条序列、15s 间隔、15 天 ≈ 1000 × 5760 × 8 × 15 ≈ 690MB（实际含索引压缩会更大）。
- **别全局统一调小间隔**——按 job 单独设（scrape_configs 里可覆盖全局 scrape_interval），热点 job 5s、普通 job 30s。

### 2. TSDB 保留期与磁盘

```shell
./prometheus --storage.tsdb.retention.time=15d   # 数据保留 15 天
./prometheus --storage.tsdb.retention.size=50GB  # 或用容量上限（达到即删最旧块）
```

**容量上限优先于时间上限**（--storage.tsdb.retention.size）：磁盘就那么大，按容量设上限最稳。监控盘要独立分区，**别和业务数据抢盘**（TSDB 写放大 + 占满盘会导致 Prometheus 自己挂掉）。

### 3. 高基数标签（TSDB 性能杀手）

**标签值组合数 = 基数**。`node_cpu_seconds_total` 的 cpu 标签 8 核 × 8 mode = 64 条序列没问题；但若把 `user_id`、`request_id`、IP 当标签，每秒新增几万个新组合，TSDB 索引爆炸、查询变慢、内存吃光。规则：

- 标签用于「可枚举的有限维度」（实例、环境、区域、服务名）。
- 禁止：用户 ID、订单号、IP（除非是固定机器列表）、时间戳。
- 高基数数据用日志/其他存储，别塞 Prometheus。
- 用 `promtool` 或 UI 的 TSDB Status 页查序列数增长。

### 4. recording rule 预计算

高频查询（如仪表盘每次加载都跑全量 CPU 聚合）直接打 TSDB 很贵。用 recording rule 预计算：

```yaml
groups:
  - name: recording
    rules:
      - record: instance:cpu_usage:rate5m
        expr: 100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
```

之后仪表盘直接查 `instance:cpu_usage:rate5m`，查询负载降低一个数量级。**命名规范 `<level>:<metric>:<op>`（instance:cpu_usage:rate5m）**。

### 5. 监控体系自身的高可用

单机 Prometheus 挂了监控就瞎了。方案由简到繁：

| 方案 | 做法 | 适用 |
|---|---|---|
| 双实例 + 联邦 | 主实例从备实例 federation 拉 `up` 等关键指标，主挂备顶上 | 小规模 |
| Prometheus 联邦 | 子 Prometheus 各管一片（按机房/业务），根 Prometheus 聚合关键指标 | 中规模 |
| Thanos / VictoriaMetrics | sidecar 上传 TSDB 块到对象存储，querier 统一查询、无限保留 | 大规模（K8s 事实标准） |
| 告警通道兜底 | Alertmanager 高可用（集群模式）+ 云监控/电话兜底 | 任何规模都建议 |

**最朴素的兜底**：监控机本身的 CPU/内存/磁盘用云监控或外部 ping 盯着，保证「监控自己挂了」也有人知道（监控的监控）。

### 6. 监控自身开销

node_exporter 每 15s 被拉一次，CPU 占用可忽略（<0.1 核）；真正吃资源的是**高频高基数抓取**（秒级 × 上万序列）。大规模部署用 `--collector.disable-defaults` 裁剪不需要的采集器（如不关心 netstat 就不采），并把 Prometheus 与 exporter 分开部署。

## 安全与权限

### 1. 认证与 TLS（默认全裸奔）

**Prometheus/Grafana/node_exporter 默认无认证**，生产环境必须补：

- **Grafana**：自带登录（默认 admin/admin，**首登必须改**）+ 反向代理加 SSO/2FA。
- **Prometheus**：无内置认证，前面挂 nginx 反向代理 + Basic Auth / 客户端证书；或直接内网隔离。
- **node_exporter**：数据含主机名、进程信息、磁盘路径——只允许 Prometheus 网段访问；用 `--web.listen-address=127.0.0.1:9100` 配合 Prometheus 走 SSH 隧道，或用 `--web.config` 启用 Basic Auth/TLS。

```shell
# node_exporter 启用认证（--web.config 指向 yaml）
./node_exporter --web.config.file=web.yml
# web.yml：
#   basic_auth_users:
#     prom: <bcrypt hash>
#   tls_server_config:
#     cert_file: server.crt
#     key_file: server.key
```

### 2. 端口暴露边界

- 9100（node_exporter）/9090（Prometheus）/9093（Alertmanager）/3000（Grafana）**一律不暴露公网**；Grafana 走 HTTPS 反代 + 认证，其余走内网/VPN。
- 云环境配合安全组：只放行监控网段来源 IP，别开 0.0.0.0/0。
- 防火墙差异：Ubuntu `ufw allow from <监控网段> to any port 9100`；RHEL `firewall-cmd --permanent --add-rich-rule='rule family=ipv4 source address=10.0.0.0/8 port port=9100 protocol=tcp accept'`。

### 3. exporter 最小权限

- node_exporter 以**专用非 root 用户**运行（Ubuntu 包默认 User=prometheus）；自装时创建专用用户，别 root 跑。
- 自定义 exporter 同理：只给读取所需文件的权限，不给 shell。
- 监控数据（磁盘路径、进程名、业务指标）是敏感信息：仪表盘共享链接要过期，导出数据脱敏。

### 4. Grafana 权限模型

组织（Organization）→ 用户/团队 → 角色（Viewer/Editor/Admin）→ 数据源权限。原则：**只读用户给 Viewer**、仪表盘编辑给 Editor、数据源管理和用户管理仅 Admin；每个团队独立组织；第三方集成用 API Key（只读）而不是管理员密码。

## 故障排查

### 案例一：Prometheus target down，拉不到指标

**现象**：Prometheus UI 的 Targets 页显示节点 down，Grafana 对应面板无数据。

**排查**：

```shell
# 1. 看 target 状态（health=down 的 instance）
curl -s localhost:9090/api/v1/targets | jq '.data.activeTargets[] | select(.health=="down")'
# 2. 手动 curl 目标，看是网络还是服务问题
curl -v 目标IP:9100/metrics
# 3. 本机侧确认 exporter 在跑、端口在听
systemctl status prometheus-node-exporter   # 或 ps aux | grep node_export
ss -tlnp | grep 9100
# 4. 防火墙/安全组放行检查（Ubuntu ufw / RHEL firewalld / 云安全组）
```

**结论**：按「Prometheus → 网络 → 目标机 → exporter 进程」逐层排除。常见原因：exporter 没起/崩了、9100 被防火墙挡、target 地址写错（IP 变了）、exporter 换了监听端口但配置没更新。**up == 0 告警就是干这个的——先确保它生效，节点失联才能被发现**。

### 案例二：Grafana 无数据但 Prometheus 有数据

**现象**：Prometheus Graph 页能查到数据，Grafana 面板空白。

**排查**：

```shell
# 1. 数据源连接测试：Configuration → Data Sources → Prometheus → Save & Test
# 2. 面板查询与 Prometheus 对比：编辑面板 → 用同样的 PromQL 在 Explore 页跑
# 3. 检查时间范围：面板右上角时间范围/时区（UTC vs 本地时区错位常见）
# 4. 检查变量：用了 $instance 变量但变量查询没返回值 → 面板查不到序列
# 5. 检查数据源 URL 可达性：Grafana 容器/机器能不能访问 Prometheus 地址
#    （docker 部署常见坑：localhost 在容器里指容器自己）
```

**结论**：顺序排查「数据源 → 查询 → 时间 → 变量」。最高频的三个坑：数据源 URL 写错（容器里 localhost）、时区/时间范围不对、变量查询返回空。

### 案例三：TSDB 磁盘被占满，Prometheus 起不来

**现象**：Prometheus 日志报 `Error opening DB` / 磁盘 100%，服务反复重启。

**排查**：

```shell
# 1. 看数据目录占用
du -sh <prometheus-data-dir>
# 2. 检查保留期设置
ps aux | grep prometheus | grep -o 'storage.tsdb.retention[^ ]*'
# 3. 看是不是高基数指标爆炸（序列数暴增）
#    Prometheus UI → Status → TSDB Status → Head Stats 的 series 数
# 4. 找新增的高基数标签来源（最近加的 exporter/埋点）
```

**结论**：TSDB 写放大 + 保留期太长 + 高基数标签是三大元凶。解法：设 `--storage.tsdb.retention.size`（容量上限）；清理/删除高基数 job；必要时用 `--storage.tsdb.min-block-duration` 调块周期。**监控盘独立分区 + 容量告警**是事前预防的关键。

### 案例四：告警风暴刷屏

**现象**：一次故障收到几百条告警（每台机器每个指标各报一条），真正的问题被淹没。

**排查**：

```shell
# 1. Alertmanager UI 看 Alerts 页：确认是不是同一根因触发了多条
# 2. 检查 group_by 配置：有没有按 alertname/instance 分组聚合
# 3. 检查是否缺抑制：宿主机 down 时，其上的服务告警应该被抑制
# 4. 检查 for 时长：瞬时抖动是不是被立刻触发了
```

**结论**：告警风暴是配置问题不是运气问题——**分组（group_by）合并同类项、for 防抖动、抑制（inhibit_rules）压雪崩、repeat_interval 控制催办频率、静默管理维护窗口**，五件套齐了才不会有风暴（详见场景四）。

## 常见问题

```text
Q1: Prometheus 拉不到 node_exporter 的指标？
A: 按链路排查：① exporter 进程在不在（systemctl status prometheus-node-exporter）；
   ② 端口在不在（ss -tlnp | grep 9100）；③ 本机 curl localhost:9100/metrics
   通不通；④ 监控机 curl 目标IP:9100/metrics 通不通（防火墙/安全组）；
   ⑤ target 地址/端口配置对不对。90% 是防火墙或 target 写错。

Q2: 告警频繁误报或该报不报？
A: 误报多：for 时长太短（抖动触发）、阈值太低。该报不报：expr 写错
   （rate 窗口、标签过滤、类型用错——counter 忘加 rate()）、evaluation
   间隔与 for 不匹配。铁律：先在 Prometheus Graph 页把 expr 跑通再写规则。

Q3: 告警太多刷屏？
A: Alertmanager 五件套：group_by 分组合并、group_wait/group_interval
   聚合窗口、repeat_interval 控制催办频率、inhibit_rules 抑制雪崩、
   silence 管理维护窗口。分级（critical/warning/info）分流到不同渠道。

Q4: node_exporter 重启后没了？
A: 手动 ./node_exporter 启动没有托管。Ubuntu 用 apt 装（自带 systemd
   unit）或自写 unit：Restart=on-failure + User=非root + ExecStart 指向
   二进制，systemctl enable 开机自启。

Q5: Prometheus 和 Zabbix 怎么选？
A: 云原生/微服务/开发团队用 Prometheus（PromQL + Grafana + K8s 生态）；
   传统机房/网络设备/Windows/老应用用 Zabbix（agent 开箱即用、自带
   Web UI 和报表）；单云厂商图省事用云监控。可以并存：Prometheus 为主，
   云监控兜底告警通道。

Q6: Grafana 里 CPU 使用率的 PromQL 怎么写？
A: 100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)。
   原理：idle 占比 × 100 是空闲率，100 减掉就是使用率；rate 窗口 5m 平滑。
   想看每核分布去掉 avg by 的聚合，按 cpu 标签保留。

Q7: 监控数据存多久？磁盘不够怎么办？
A: 默认 15 天（--storage.tsdb.retention.time），建议同时设容量上限
   --storage.tsdb.retention.size；需要长期保留用 Thanos/VictoriaMetrics
   把旧块归档到对象存储。采样间隔 × 指标基数 × 保留期 = 磁盘需求，先算账再定。

Q8: 为什么不能用 IP 或用户 ID 当指标标签？
A: 标签值组合数 = 基数。IP/用户 ID 值域大且不断增长，序列数爆炸式增长
   （高基数），TSDB 索引膨胀、内存和查询开销飙升。标签只用于可枚举的
   有限维度（实例、环境、服务），高基数维度用日志/其他存储。

Q9: pushgateway 什么时候用？
A: 短生命周期任务（cron 批处理、一次性脚本）来不及被 pull 就结束了，
   由任务结束时 push 一次指标到 pushgateway，Prometheus 从 pushgateway
   拉取。注意 pushgateway 是「任务结束就忘」的桥，不是长存指标库——
   服务型指标（进程存活等）别往里推。

Q10: 监控数据算敏感数据吗？
A: 算。指标含主机名、磁盘路径、进程信息、业务量，能反推业务结构和
   规模。node_exporter/Prometheus 默认无认证，生产必须内网隔离 +
   认证/TLS（见安全与权限）；仪表盘分享要限时，数据导出要脱敏。
```

## 面试题

```text
1. Prometheus 为什么用「拉取」而不是「推送」？
   答：① 采集主动权在监控端——Prometheus 决定抓谁、何时抓、抓多快，
   目标挂了立刻知道（up 指标），推送模式目标失联往往「静默消失」；
   ② 配置集中——新机器加进 targets 即被监控，不用在目标机上改配置；
   ③ 易于调试——curl /metrics 就能手工验证。代价：NAT/防火墙后的目标
   拉不到，所以有 pushgateway 兜底短生命周期任务。

2. counter、gauge、histogram 的区别？CPU 使用率用哪个怎么算？
   答：counter 只增（重启归零），用于计数，查询必须 rate()/increase()
   转速率；gauge 可增可减，用于瞬时值（内存、温度）；histogram 分桶
   计数，用于延迟分布，用 histogram_quantile 算 P99。CPU 使用率 =
   100 - idle 占比：rate(node_cpu_seconds_total{mode="idle"}[5m]) 得
   空闲速率占比，乘 100 减掉即使用率；node_cpu_seconds_total 本身是
   counter。

3. 告警为什么要设 for 5m？Alertmanager 的分组/抑制/静默各解决什么问题？
   答：for 是持续时长——CPU 瞬时飙到 90% 可能只是抖动，持续 5 分钟才
   是问题，避免误报轰炸。分组（group_by）把同类告警合并成一条通知，
   解决刷屏；抑制（inhibit_rules）用高优先级告警压住低优先级同类
   （宿主机挂了就抑制其上的服务告警），解决雪崩；静默（silence）在
   维护窗口按规则屏蔽告警，解决「知道要出事就别吵」。

4. Prometheus 高基数问题是什么？怎么预防？
   答：时间序列按「指标名 + 标签组合」区分，标签值组合数即基数。
   用户 ID、IP、请求 ID 做标签会让序列数爆炸（高基数），拖垮 TSDB
   内存与查询。预防：标签只放可枚举有限维度；高基数维度走日志/其他
   存储；用 TSDB Status 页和 promtool 监控序列数增长；recording rule
   预聚合降低查询压力。

5. Prometheus 与 Zabbix 架构差异？
   答：Prometheus 是 pull 模型 + TSDB + PromQL，服务发现强（K8s），
   生态围绕云原生，可视化靠 Grafana；Zabbix 是 agent 主动/被动混合 +
   关系型数据库存配置 + 自带 Web UI/报表/自动发现，适合传统基础设施。
   Prometheus 灵活但组件多，Zabbix 开箱即用但扩展要写脚本。

6. 监控体系怎么分层？四黄金信号是什么？
   答：四层：基础设施（机房/网络设备）、操作系统（CPU/内存/磁盘）、
   应用（中间件/数据库）、业务（用户视角可用性）。四黄金信号（SRE）：
   延迟（请求多慢）、流量（请求多少）、错误（失败率）、饱和度（资源
   多满）；对应服务健康；资源瓶颈用 USE 法（利用率/饱和度/错误）查。

7. 一条 PromQL：如何查「每台机器的 5 分钟平均 CPU 使用率」？
   答：100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)。
   拆解：rate(metric[5m]) 算每秒增量；{mode="idle"} 过滤空闲态；
   avg by (instance) 按机器聚合所有核；100 减得使用率。要求按核展示
   去掉聚合：100 - (rate(node_cpu_seconds_total{mode="idle"}[5m]) * 100)
   会保留 cpu 标签。

8. 监控体系自身挂了怎么办？
   答：分层兜底：① 告警通道高可用——Alertmanager 集群 + 云监控/电话
   兜底；② 监控机自身纳入外部监控（云监控盯监控机存活）；③ 数据高可用
   ——Prometheus 联邦（根实例聚合子实例关键指标）、Thanos/VM（块归档
   对象存储，可重建）；④ 关键告警（节点失联、磁盘满）除了 Prometheus
   还要有独立通道（cron 脚本 + 短信 API 之类），保证「监控的监控」。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先铺 OS 层再往上：所有机器统一装 node_exporter 接入，投入产出比最高；再补应用/业务层。
2. 告警规则铁律：**先在 Graph 页把 expr 跑通再写规则**；for 至少 5m 防抖动；分级（critical/warning/info）分渠道。
3. 告警五件套配齐：分组、聚合窗口、repeat_interval、抑制、静默——没有这五样迟早告警风暴。
4. 标签纪律：只放可枚举有限维度；用 recording rule 预聚合高频查询；定期看 TSDB 序列数。
5. 存储双上限：`--storage.tsdb.retention.time` + `--storage.tsdb.retention.size` 都设，监控盘独立分区并配容量告警。
6. Ubuntu 用 apt 装 node_exporter（自带 systemd unit + 非 root 用户），别裸跑二进制；Red Hat 自装也要写 systemd unit（模板见配置文件解析）。
7. 安全默认内网隔离：exporter/Prometheus/Grafana 不暴露公网，Grafana 首登改密 + HTTPS 反代，export 只读 API Key。
8. 上线前过一遍监控覆盖检查清单（场景六）：进程、端口、证书、备份、日志、时间同步这些「容易漏但出事很疼」的都要有。

### 踩坑记录

```text
坑 1：Prometheus 拉不到 node_exporter 的指标
结论：Prometheus 里 target 是 down，Grafana 一片空白。
原因：9100 端口没开/防火墙挡/配置的 target 地址写错（IP 或端口）。
解法：curl 目标IP:9100/metrics 逐层测（本机 → 监控机 → 防火墙/安全组），
     确认 exporter 进程和监听端口，再核对 prometheus.yml 的 targets。

坑 2：Ubuntu 上照着网上教程装 node_exporter，命令不存在
结论：apt 装完执行 node_exporter 报 command not found。
原因：Ubuntu 仓库的包名和二进制都带前缀：包叫 prometheus-node-exporter，
     二进制是 /usr/bin/prometheus-node-exporter（上游才叫 node_exporter）。
解法：apt install prometheus-node-exporter 后，服务是
     prometheus-node-exporter.service，二进制是 prometheus-node-exporter；
     或下载官方 tarball 自装（Red Hat 系推荐）。

坑 3：Grafana 和 Node 服务抢 3000 端口
结论：Grafana 启动失败，日志报 bind :3000 address already in use。
原因：3000 是 Grafana 默认端口，也是 Node.js/前端项目的惯用端口，
     本机实测 3000 被一个 Node 服务占用。
解法：启动前 ss -tlnp | grep 3000 查占用；改 Grafana 端口
     （grafana.ini 的 http_port=3001），或让业务服务换端口。

坑 4：告警规则 expr 写错，一直触发或不触发
结论：HighCPU 告警要么永远 firing 要么永远不响。
原因：PromQL 写错——counter 忘加 rate()、标签过滤写错、rate 窗口与
     采集间隔不匹配（如 [1m] 但采集 15s 没问题，[5s] 就报错）。
解法：先在 Prometheus 的 Graph 页执行 expr 看曲线对不对，再写规则；
     promtool check rules 校验语法。

坑 5：告警太多被刷屏
结论：一次故障收到几百条告警，手机被打爆，真问题被淹没。
原因：没分组去重，每台机器每个指标单独一条；宿主机挂了连带其上的
     所有服务告警一起发。
解法：Alertmanager 配 group_by（按 alertname 分组）、抑制规则
     （inhibit_rules 压雪崩）、repeat_interval 拉长催办间隔。

坑 6：node_exporter 裸跑，重启后没了
结论：node_exporter 手动 ./node_exporter 启动，机器一重启就不在了。
原因：没有 systemd 托管，进程是前台跑的。
解法：apt 安装自带 unit；自装写 unit：Restart=on-failure、User=非root、
     systemctl enable。别 nohup 裸跑（没有守护和自启）。

坑 7：docker 部署的 Grafana 连不上 Prometheus
结论：Grafana 容器里配数据源 URL=http://localhost:9090，Save & Test 失败。
原因：localhost 在容器里指容器自己，不是宿主机的 Prometheus。
解法：用宿主机 IP 或 docker 网络里的服务名
     （docker-compose 里用服务名 prometheus:9090）；host 网络模式用
     localhost 才行。

坑 8：TSDB 数据把磁盘写满，Prometheus 挂掉
结论：监控机磁盘 100%，Prometheus 起不来，监控盲区。
原因：没设保留期/容量上限，指标基数膨胀，TSDB 写放大把盘写满。
解法：--storage.tsdb.retention.size=50GB 容量上限 + 独立分区 +
     磁盘容量告警；用 TSDB Status 查高基数来源并治理。

坑 9：修改告警规则后不生效
结论：rule_files 改了 yaml，告警还是按旧规则跑。
原因：Prometheus 不会自动检测规则文件变化，需要热重载。
解法：curl -X POST localhost:9090/-/reload（或 SIGHUP 进程）；
     改了 prometheus.yml 同理。排查时先确认 reload 成功
     （日志出现 "Completed loading of configuration"）。

坑 10：维护窗口忘了关静默，告警全被吞
结论：发版维护完，服务真挂了也没收到告警。
原因：维护时挂的 silence 到期没自动清，或 matchers 写宽了把正常告警
     也屏蔽了。
解法：silence 必须带 endsAt 到期自动失效；matchers 精确到 alertname +
     实例；定期 audit 活动中的 silence（Alertmanager UI 一眼可见）。
```
