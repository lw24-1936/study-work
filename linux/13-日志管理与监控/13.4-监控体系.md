## 概述

单机监控工具（top/sar）只能看单台机器，多台机器需要一个「监控体系」：Prometheus（采集存储指标）+ node_exporter（暴露机器指标）+ Grafana（可视化）+ Alertmanager（告警）。架构是「拉取式」：Prometheus 定时从各机器的 node_exporter 拉指标 → 存时序库 → Grafana 查询展示 → Alertmanager 触发告警。这是现代运维监控的事实标准。

```text
监控体系架构（Prometheus 全家桶）：
各服务器 node_exporter（暴露指标）
      ↑ Prometheus 定时拉取（scrape）
      ↓ 存储时序数据库
  Grafana 查询可视化
  Alertmanager 告警通知（邮件/钉钉/微信）
```

## 核心概念

1. **Prometheus**：时序数据库 + 采集 + 查询的监控系统，用「拉取」模式（主动去各目标 scrape 指标），PromQL 是查询语言。
2. **node_exporter**：部署在每台机器上的指标暴露器——把 CPU/内存/磁盘/网络等系统指标暴露成 HTTP 接口（默认 9100），供 Prometheus 拉取。指标名 `node_*` 前缀。
3. **Grafana**：可视化面板，把 Prometheus 的指标画成图表、仪表盘，数据源 + 面板 + 仪表盘三级结构。
4. **Alertmanager**：Prometheus 的告警组件——分组/去重/静默，通知到邮件/钉钉/微信/PagerDuty。

```text
Prometheus 核心概念：
1. 拉取模式 —— Prometheus 主动 scrape 目标，不是目标推给 Prometheus
2. node_exporter —— 每台机器部署，暴露 :9100 系统指标
3. PromQL —— 查询语言，rate()/increase() 等函数
4. 时序数据 —— 指标名 + 标签 + 时间戳 + 值
```

## 工作原理

Prometheus 是「拉取式」监控：每个采集周期（默认 15s），Prometheus 向配置里的 target（如各机器的 node_exporter:9100）发起 HTTP 请求，抓取 /metrics 指标，存入本地时序库。Grafana 通过数据源连 Prometheus，用 PromQL 查询并画图。告警时，Prometheus 评估告警规则（如 CPU>90% 持续 5 分钟），触发后发到 Alertmanager，由它分组去重后通知。

```text
拉取式监控流程：
node_exporter 暴露 /metrics → Prometheus 定时 scrape → 存时序库 → Grafana PromQL 查询画图
告警：Prometheus 评估规则 → Alertmanager 分组/去重/静默 → 通知渠道
```

```text
# 实测（本机端口：3000=node 服务、8082=nginx，未装 Prometheus/9100）
$ ss -tlnp | grep -E ':9090|:9100|:3000'
LISTEN 0.0.0.0:3000  node      # 这是 Node 服务，不是 Grafana
# 本机未部署 Prometheus(9090)/node_exporter(9100)，以上为通用说明
```

## 常用命令与配置

```shell
# 启动 node_exporter（默认 9100）
./node_exporter
# 验证指标暴露
curl localhost:9100/metrics | head
# 启动 Prometheus（默认 9090）
./prometheus --config.file=prometheus.yml
# 重载 Prometheus 配置（不重启）
curl -X POST localhost:9090/-/reload
# 看 target 抓取状态
curl localhost:9090/api/v1/targets
```

## 配置文件解析

Prometheus 主配置 prometheus.yml 定义采集目标：

```yaml
# prometheus.yml 采集配置（示例）
scrape_configs:
  - job_name: 'node'
    static_configs:
      - targets: ['192.168.1.10:9100', '192.168.1.11:9100']
```

告警规则文件（Prometheus 里定义触发条件）：

```yaml
# Prometheus 告警规则（示例）
groups:
  - name: node
    rules:
      - alert: HighCPU
        expr: 100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 90
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "CPU 使用率超过 90%"
```

```text
关键字段：
job_name      采集任务名（一个 target 组一个 job）
targets       要抓取的地址列表（host:port）
expr          告警的 PromQL 表达式
for           持续多久才触发（避免抖动误报）
```

## 性能与调优

```text
1. 采集间隔 —— 默认 15s，指标多可放宽到 30s，降低抓取和存储压力
2. 时序存储 —— 设保留期（--storage.tsdb.retention.time），防磁盘占满
3. 高基数标签 —— 别用 IP/用户 ID 当标签，标签值太多拖垮时序库
4. 告警聚合 —— 用 recording rule 预计算，减少查询负载
```

## 安全与权限

```text
1. 认证 —— Prometheus/Grafana 默认无认证，生产要加反向代理 + 认证
2. TLS —— /metrics 默认明文，跨网用 HTTPS 或 TLS
3. 端口暴露 —— node_exporter 9100 别暴露公网，只允许 Prometheus 抓取
4. Grafana 权限 —— 组织/角色/数据源权限分级，别所有人 admin
```

## 故障排查

### Prometheus target down，拉不到指标

```shell
# 1. 看 target 状态
curl localhost:9090/api/v1/targets | grep -A3 down
# 2. 手动 curl 目标验证
curl -v 目标IP:9100/metrics
# 3. 确认防火墙/安全组放行 9100
```

### Grafana 无数据但 Prometheus 有

## 常见问题

```text
Q1: Prometheus 拉不到 node_exporter 的指标？
A: 9100 端口没开/防火墙挡/target 地址不对。curl 目标:9100/metrics 测试网络和防火墙。

Q2: 告警频繁误报或该报不报？
A: PromQL 表达式错误（rate 窗口、标签过滤写错）。先在 Prometheus Graph 页调试 PromQL 再写规则。

Q3: 告警太多刷屏？
A: 没分组去重。Alertmanager 配 group_by，同类告警合并成一条。

Q4: node_exporter 重启后没了？
A: 手动启动没做 systemd 托管。给 node_exporter 写 systemd service 开机自启。
```

## 面试题

```text
1. Prometheus 为什么用「拉取」而不是「推送」？
   答：拉取模式 Prometheus 掌握采集主动权，能自动发现 target、判断目标存活；推送模式（pushgateway）用于短生命周期任务。

2. node_exporter 的作用？
   答：部署在每台机器，把系统指标（CPU/内存/磁盘/网络）暴露成 HTTP 接口，供 Prometheus 拉取。

3. 告警为什么要设 for 5m 而不是立刻触发？
   答：避免瞬时抖动（CPU 短暂飙高）造成误报，持续一段时间才确认是真实问题。

4. Prometheus 时序数据存储怎么控制？
   答：设 --storage.tsdb.retention.time 保留期，避免数据无限增长占满磁盘。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每台机器都装 node_exporter，统一接入 Prometheus
2. 告警规则设「持续 for 5m」，避免抖动误报
3. 用 Grafana 现成的 dashboard 模板，别从零画
4. 告警分级别（critical/warning），不同级别不同渠道
5. 维护期用 Alertmanager 静默，避免告警轰炸

### 踩坑记录

```text
坑 1：Prometheus 拉不到 node_exporter 的指标
结论：Prometheus 里 target 是 down，拉不到数据。
原因：9100 端口没开/防火墙挡/配置的 target 地址不对。
解法：curl 目标:9100/metrics 测试，确认网络和防火墙。

坑 2：告警规则 expr 写错，一直触发或不触发
结论：告警频繁误报，或该报不报。
原因：PromQL 表达式错误（如 rate 窗口、标签过滤写错）。
解法：先在 Prometheus 的 Graph 页调试 PromQL，确认结果再写规则。

坑 3：Grafana 显示无数据，但 Prometheus 有数据
结论：Grafana 面板空白，Prometheus 里能查到。
原因：Grafana 数据源没配好，或时间范围/查询写错。
解法：检查数据源连接，面板编辑里先用同样的 PromQL 测试。

坑 4：告警太多被刷屏
结论：一个问题触发几十条告警，手机被打爆。
原因：没分组/去重，每台机器每个指标都单独告警。
解法：Alertmanager 配分组（group_by），同类告警合并成一条。

坑 5：node_exporter 直接裸跑，重启后没了
结论：node_exporter 手动启动，重启后不在了。
原因：没做 systemd 托管。
解法：给 node_exporter 写 systemd service，开机自启。
```
