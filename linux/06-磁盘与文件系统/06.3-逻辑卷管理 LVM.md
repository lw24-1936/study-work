## 概述

LVM（Logical Volume Manager，逻辑卷管理）在物理分区之上加了一层抽象，让磁盘容量可以动态调整——不用重新分区就能扩容、缩容、跨盘合并。核心是三层结构：PV（物理卷，即磁盘/分区）→ VG（卷组，多个 PV 组成的池）→ LV（逻辑卷，从 VG 里划分的「虚拟分区」）。传统分区「定死了大小不好改」，LVM 解决了这个痛点。

```text
LVM 三层结构：
物理磁盘/分区 → PV 物理卷 → VG 卷组（池）→ LV 逻辑卷（虚拟分区）
1. PV —— pvcreate 把分区标记为物理卷
2. VG —— vgcreate 把多个 PV 聚成一个容量池
3. LV —— lvcreate 从池里划出逻辑卷，上面建文件系统
# 本机未用 LVM（sda2 直接是 ext4 分区），以下为通用操作示例
```

## 核心概念

### PV / VG / LV 三层

理解三层才能看懂 LVM 的灵活性。PV 是最底层（磁盘/分区被标记为物理卷），VG 把多个 PV 聚合成一个大池子（容量 = 所有 PV 之和），LV 从池子里按需划分（想划多少划多少，不够了再扩）。好处：LV 可以跨多块物理盘、在线扩容（不停机）、快照。查看用 pvs/vgs/lvs。

```shell
pvs                              # 查看物理卷
vgs                              # 查看卷组
lvs                              # 查看逻辑卷
pvdisplay /dev/sdb1              # 物理卷详情
vgdisplay vgdata                 # 卷组详情
lvdisplay /dev/vgdata/lvdata     # 逻辑卷详情
```

```text
LVM 三层：
1. PV 物理卷 —— 磁盘/分区被 pvcreate 标记，最小物理单元
2. VG 卷组 —— 多个 PV 聚成的容量池，容量 = 所有 PV 之和
3. LV 逻辑卷 —— 从 VG 划出的虚拟分区，可动态扩缩，上面建文件系统
```

每一层的「是什么 → 为什么 → 怎么用 → 边界」：

- PV（Physical Volume）：把整盘或分区「初始化」成 LVM 能用的物理卷，本质是在盘头写一段 LVM 元数据（标识 + 所属 VG）。为什么需要它：LVM 不认裸盘，必须先标记。怎么用：`pvcreate /dev/sdb1`。边界：一个 PV 只能属于一个 VG。
- VG（Volume Group）：多个 PV 组成的容量池，容量是各 PV 之和。为什么要 VG：把多块盘「拼」成一个大池，LV 才能跨盘、动态伸缩。怎么用：`vgcreate vgdata /dev/sdb1 /dev/sdc1`。边界：VG 是管理边界，缩容/移除 PV 要先把数据迁走（pvmove）。
- LV（Logical Volume）：从 VG 划出的「虚拟分区」，上面建文件系统、挂载使用，设备路径 /dev/<VG名>/<LV名>。为什么：对上层它就是普通块设备，但能在线扩缩、打快照。怎么用：`lvcreate -L 100G -n lvdata vgdata`。边界：LV 大小受 VG 剩余空间限制；扩 LV 还得扩文件系统才生效。

```text
LV 设备路径：
1. /dev/vgdata/lvdata —— 符号链接，指向 device-mapper 设备
2. /dev/mapper/vgdata-lvdata —— dm 设备的真实路径
3. 两者等价，fstab/mount 用哪个都行（推荐 /dev/mapper/ 形式，UUID 更稳）
```

### PE / LE：extent 概念

VG 把空间切成固定大小的「物理扩展（PE，Physical Extent）」，默认 4MiB。LV 由若干「逻辑扩展（LE，Logical Extent）」组成，LE 和 PE 一一映射。所以 LV 的容量总是 PE 大小的整数倍。PE 大小在建 VG 时用 `-s` 指定（vgcreate -s 8M），改不了（要改只能重建 VG）。

```text
PE / LE：
1. PE 物理扩展 —— VG 空间的最小分配单元，默认 4MiB
2. LE 逻辑扩展 —— LV 的组成单元，与 PE 一一映射
3. 容量整数倍 —— LV 大小 = LE 数 × PE 大小，建 VG 时 -s 指定 PE 大小
4. PE 大小权衡 —— 小 PE 空间利用率高，大 PE 大容量卷更省元数据
```

## 工作原理

LVM 的核心是「extent 映射」：VG 把空间分成固定大小的 extent（PE，默认 4MiB），LV 是一串 extent 的集合。LV 到 PV 的映射由内核的 device-mapper（dm 设备）维护——/dev/vgdata/lvdata 实际是 dm 设备的符号链接，读写时 dm 按映射表把逻辑地址翻译成物理地址（哪个 PV 的哪个 extent）。所以 LV 可以跨盘、可以动态扩缩（改映射表就行，不动数据）。

快照用「写时复制（COW）」：打快照时几乎不占空间，之后源卷数据变化时，先把旧数据复制到快照区再写新数据，快照里保留的是「变化前的旧数据」，从而能还原到打快照那一刻的状态。

```text
LVM 工作原理：
1. extent 映射 —— VG 空间分 PE（默认 4MiB），LV 是一串 PE，dm 设备维护 LV→PV 映射
2. 动态扩缩 —— 改映射表即可（lvextend/lvreduce），不搬动数据
3. 快照 COW —— 写时复制，源卷变化时旧数据复制到快照区，还原到快照时刻
4. device-mapper —— /dev/vg/lv 是 dm 设备的符号链接，内核按映射表寻址
```

device-mapper 是 LVM 的底层引擎，也是 Docker 存储、dm-crypt 加密、multipath 多路径的共同底座。`dmsetup ls` 能看到所有 dm 设备，`dmsetup table` 看映射规则。

```shell
dmsetup ls                        # 列出所有 dm 设备（LVM/Docker/加密都用它）
dmsetup table vgdata-lvdata       # 看某个 LV 的 extent 映射规则
```

```text
快照 COW 细节：
1. 创建快照 —— 只记录「快照那一刻的指针/元数据」，几乎不占空间
2. 源卷写入 —— 写某块前先把该块的旧数据复制到快照区，再写新数据
3. 快照内容 —— 保留的是「变化前的旧数据」，所以能还原到快照时刻
4. 快照满 —— 快照区写满后快照失效（IO 中断），要预留足够空间
```

## 常用命令与配置

创建 LVM 的完整流程：分区/整盘做 PV → 建 VG → 建 LV → 格式化 → 挂载。五步走通后，/dev/vgdata/lvdata 就是一个可以正常使用的逻辑卷。逻辑卷的设备路径是 /dev/<卷组名>/<逻辑卷名>。

```shell
# 1. 创建物理卷
pvcreate /dev/sdb1 /dev/sdc1
# 2. 创建卷组（把两个 PV 聚成池）
vgcreate vgdata /dev/sdb1 /dev/sdc1
# 3. 创建逻辑卷（从池里划 100G）
lvcreate -L 100G -n lvdata vgdata
# 4. 格式化
mkfs.ext4 /dev/vgdata/lvdata
# 5. 挂载
mount /dev/vgdata/lvdata /data
```

```shell
# lvcreate 的两种容量写法
lvcreate -L 100G -n lvdata vgdata         # 按大小（G/M）
lvcreate -l 100%FREE -n lvdata vgdata     # 按 PE 数 / 百分比（占满 VG 剩余空间）
# 建 VG 时指定 PE 大小
vgcreate -s 8M vgdata /dev/sdb1           # PE 8MiB（默认 4MiB）
```

扩容：先 lvextend 扩逻辑卷（加容量，可跨盘），再 resize2fs 扩文件系统（让文件系统用上新空间）。VG 池不够时先加 PV（vgextend）扩充池。XFS 用 xfs_growfs 代替 resize2fs。

```shell
# 1. 池不够先加 PV
pvcreate /dev/sdd1
vgextend vgdata /dev/sdd1
# 2. 扩逻辑卷（+50G）
lvextend -L +50G /dev/vgdata/lvdata
# 3. 扩文件系统（ext4 用 resize2fs，XFS 用 xfs_growfs）
resize2fs /dev/vgdata/lvdata
# 4. 验证
df -h /data
```

```shell
# ext4 一步到位：lvextend 加 -r 自动 resize 文件系统（免第二步）
lvextend -L +50G -r /dev/vgdata/lvdata
# XFS 在线扩容（挂载状态下直接 grow，无需 umount）
xfs_growfs /data
```

缩容比扩容危险得多，且 ext4 缩容需要先卸载（不能在线缩）。流程：先 umount → e2fsck 检查 → resize2fs 缩文件系统 → lvreduce 缩逻辑卷 → 重新挂载。注意缩容顺序不能反——必须先缩文件系统再缩逻辑卷，否则数据损坏。XFS 不支持缩容（只能备份重建）。

```shell
# 缩容（先卸载，顺序不能反）
umount /data
e2fsck -f /dev/vgdata/lvdata          # 检查
resize2fs /dev/vgdata/lvdata 50G      # 先缩文件系统
lvreduce -L 50G /dev/vgdata/lvdata    # 再缩逻辑卷
mount /dev/vgdata/lvdata /data
```

快照：LVM 快照是逻辑卷某一时刻的只读副本，用「写时复制」实现——快照只记录变化，所以创建快、占用小。用途：备份前先打快照（保证备份数据一致性）、升级前打快照（失败可回滚）。

```shell
# 创建快照（记录 lvdata 的当前状态）
lvcreate -L 10G -s -n lvdata_snap /dev/vgdata/lvdata
# 挂载快照读取数据
mount /dev/vgdata/lvdata_snap /mnt/snap
# 用完删除快照
umount /mnt/snap
lvremove /dev/vgdata/lvdata_snap
```

```shell
# 移除旧盘（先把数据迁走再摘盘，三步不可省）
pvmove /dev/sdd1                    # 把 sdd1 上的数据迁到其他 PV
vgreduce vgdata /dev/sdd1           # 从 VG 摘除 sdd1
pvremove /dev/sdd1                  # 抹掉 PV 标记，盘可复用
```

```text
常用命令速查：
1. pvcreate / pvs / pvdisplay —— 建物理卷、查看物理卷
2. vgcreate / vgs / vgextend / vgreduce —— 建/扩/缩卷组
3. lvcreate / lvs / lvextend / lvreduce —— 建/扩/缩逻辑卷
4. pvmove —— 迁移 PV 上的数据（移除 PV 前必做）
5. lvremove / vgremove / pvremove —— 删除逻辑卷/卷组/物理卷
6. -r 选项 —— lvextend/lvreduce 加 -r 自动 resize 文件系统（ext4）
```

## 配置文件解析

LVM 的全局配置在 /etc/lvm/lvm.conf，常见要改的：filter（限制哪些设备被 LVM 识别，防止 LVM 扫到无关设备）、devices 段（扫描设备）。VG/LV 的元数据存储在 PV 上（不是配置文件），用 vgcfgbackup/vgcfgrestore 备份恢复。

```shell
grep -vE '^\s*#|^\s*$' /etc/lvm/lvm.conf | head   # 看生效配置
vgcfgbackup vgdata                    # 备份 VG 元数据到 /etc/lvm/backup/
vgcfgrestore vgdata                   # 恢复 VG 元数据
```

```text
LVM 配置要点：
1. /etc/lvm/lvm.conf —— 全局配置，filter 决定扫描哪些设备
2. VG/LV 元数据在 PV 上 —— 不在配置文件里，用 vgcfgbackup 备份
3. 多路径/存储场景 —— 用 filter 精确指定设备，防止 LVM 误扫
```

LVM 的元数据分两处落盘：/etc/lvm/backup/（每次 vg 操作后自动备份的 VG 元数据快照）+ /etc/lvm/archive/（历史版本，每次改动留一份）。PV 盘头上也存一份当前元数据（LVM 认盘靠它）。filter 用设备路径/正则控制 LVM 扫描范围，典型的「只扫本地盘、跳过别的」配置：

```text
# lvm.conf 里 filter 配置示例（只接受 /dev/sd* 和 /dev/mapper/*，拒绝其余）
filter = [ "a|^/dev/sd.*|", "a|^/dev/mapper/.*|", "r|.*|" ]
# a 接受、r 拒绝，按顺序匹配；a 的盘才被 LVM 扫描
```

```text
元数据落点：
1. PV 盘头 —— 当前生效的 VG/LV 元数据，LVM 识别盘靠它
2. /etc/lvm/backup/ —— 每次操作后自动备份的元数据快照
3. /etc/lvm/archive/ —— 历史版本，每次改动留一份，误操作可回滚
4. vgcfgrestore —— 用 backup 里的元数据重建 PV 盘头（盘头损坏时救 VG）
```

## 应用场景实战

### 场景一：根分区满了，用 LVM 在线扩容

```shell
# 1. 确认根分区是 LVM
df -h / && lvs
# 2. 加新盘并扩 VG
pvcreate /dev/sdc1
vgextend vgroot /dev/sdc1
# 3. 在线扩根逻辑卷和文件系统
lvextend -L +50G /dev/vgroot/lvroot
resize2fs /dev/vgroot/lvroot
df -h /
```

### 场景二：数据库备份前打快照保证一致性

```shell
# 1. 打快照（冻结数据状态）
lvcreate -L 20G -s -n mysql_snap /dev/vgdata/lv_mysql
# 2. 从快照备份（不影响运行中的数据库）
mount /dev/vgdata/mysql_snap /mnt/snap
tar czf /backup/mysql.tar.gz /mnt/snap
# 3. 清理快照
umount /mnt/snap
lvremove /dev/vgdata/mysql_snap
```

### 场景三：旧盘退役，pvmove 迁移数据后摘盘

```shell
# 1. 确认要退役的 PV 及其数据分布
pvs -o+pv_used
# 2. 把 sdd1 上的数据迁到 VG 内其他 PV（数据不丢、在线迁移）
pvmove /dev/sdd1
# 3. 从 VG 摘除该 PV
vgreduce vgdata /dev/sdd1
# 4. 抹掉 PV 标记，盘可以下线/复用
pvremove /dev/sdd1
```

```text
场景三要点：
1. pvmove 在线迁移 —— 不需要卸载、不中断业务，数据在后台搬
2. 目标 PV 要够空间 —— pvmove 前先 vgs 确认 VG 剩余空间能容纳要迁的数据
3. 顺序不能省 —— pvmove → vgreduce → pvremove，跳过 pvmove 直接 vgreduce 会丢数据
```

## 性能与调优

LVM 的性能要点：LV 可以用条带化（lvcreate --stripes N，数据分散到多块 PV 并行读写，提升吞吐）；VG 的 PE 大小（默认 4MiB）影响空间利用率；快照会拖慢源卷（每次写都要 COW），用完及时删。LV 本身性能接近裸分区（dm 映射开销极小），不必担心 LVM 拖慢性能。

```text
LVM 性能要点：
1. 条带化 —— lvcreate --stripes N 分散到多 PV 并行读写，提升吞吐
2. PE 大小 —— 默认 4MiB，影响空间分配粒度
3. 快照开销 —— 快照在时源卷每次写都要 COW，用完及时删
4. dm 开销 —— 映射开销极小，LV 性能接近裸分区
```

```shell
# 条带化 LV（数据分散到 2 块 PV 并行读写）
lvcreate -L 200G -i 2 -n lvstripe vgdata
# 镜像 LV（-m 1 表示一份镜像，数据写两份，读性能也可提升）
lvcreate -L 100G -m 1 -n lvmirror vgdata
```

```text
调优选择：
1. 条带化 -i N —— 顺序大块读写提速明显，随机 IO 收益小
2. 镜像 -m 1 —— 数据冗余、读可并行，代价是写两份、空间翻倍
3. 快照 —— 生产环境控制数量和时间，用完即删，否则源卷写放大
4. 大多数场景 —— 默认线性 LV 已够用，条带/镜像只在明确需要时用
```

## 安全与权限

LVM 本身不加密，敏感数据可在 LV 上叠 LUKS 加密（加密层在 LVM 之上或之下都行，常见「LUKS 在 LV 之上」）。权限方面：LVM 操作要 root；VG 里移除 PV 前必须先 pvmove 迁移数据（防数据丢失）。快照是只读副本，但快照区本身占 VG 空间，别让快照撑爆 VG。

```text
LVM 安全要点：
1. 加密 —— 敏感数据在 LV 上叠 LUKS 加密（cryptsetup luksFormat）
2. 权限 —— LVM 管理命令要 root 权限
3. 移除 PV 先 pvmove —— vgreduce 前迁移数据，防止丢数据
4. 快照空间 —— 快照占 VG 空间，监控别撑爆
```

```shell
# LUKS 加密叠在 LV 之上（先建 LV 再加密，常见做法）
cryptsetup luksFormat /dev/vgdata/lvdata       # 初始化加密
cryptsetup open /dev/vgdata/lvdata cryptdata   # 打开，映射到 /dev/mapper/cryptdata
mkfs.ext4 /dev/mapper/cryptdata                 # 在加密设备上格式化
mount /dev/mapper/cryptdata /data               # 挂载使用
```

```text
快照空间管理：
1. 快照区大小 = 源卷在快照生命周期内的「变化量」估计值，不是源卷大小
2. 快照写满 → 快照失效、源卷 IO 可能中断
3. lvs 监控快照的 Data% 列，超 80% 就该清理或扩快照
```

## 故障排查

### 缩容顺序反了导致数据损坏

```shell
# 症状：先 lvreduce 再 resize2fs，文件系统损坏
# 正确顺序：先 resize2fs 缩文件系统，再 lvreduce 缩逻辑卷
# 已损坏则：e2fsck -f 尝试修复，严重时从备份恢复
```

### 快照空间满了导致 IO 中断

```shell
# 1. 看快照使用情况
lvs -a vgdata
# 2. 快照 100% 了，删除快照恢复
lvremove /dev/vgdata/lvdata_snap
# 3. 后续快照设足够空间（源卷变化量的估计值）
```

### VG 不激活导致 LV 设备不存在

```shell
# 症状：重启后 /dev/vgdata/lvdata 不存在，但 pvs 能看到 PV
# 1. 看 VG 激活状态（vgchange -ay 激活）
vgchange -ay vgdata
# 2. 确认 LV 设备出现了
ls -l /dev/vgdata/
# 3. 重新挂载
mount /dev/vgdata/lvdata /data
```

```text
VG 激活排查：
1. lv 设备不存在先 vgdisplay 看 VG 状态（active/inactive）
2. vgchange -ay 激活 VG —— 常见于新盘迁移、集群共享存储接管场景
3. 配置文件 filter 误拦 —— 看 /etc/lvm/lvm.conf 是否把盘拒之门外
```

## 常见问题

```text
Q1: LVM 和普通分区比有什么优势？
A: 可以动态扩缩容（不停机）、跨盘合并、打快照，不用重新分区。

Q2: 扩容为什么 lvextend 后 df 看容量没变？
A: 扩了逻辑卷还得扩文件系统（resize2fs/xfs_growfs），两层要都扩。

Q3: XFS 能缩容吗？
A: 不能。XFS 只支持扩容，缩容只能备份数据、重建小卷、恢复数据。

Q4: 快照能当备份吗？
A: 不能。快照是 COW 的临时副本（依赖源卷，源卷坏快照也坏），只用于备份前的瞬时一致快照，真正备份要另存。

Q5: 移除一块旧盘的正确步骤？
A: pvmove /dev/sdX 迁移数据 → vgreduce vgX /dev/sdX 摘除 → pvremove /dev/sdX 抹标记。跳过 pvmove 会丢数据。

Q6: LVM 设备路径 /dev/vg/lv 和 /dev/mapper/vg-lv 什么关系？
A: 两者指向同一个 device-mapper 设备，前者是后者的符号链接，等价，fstab/mount 用哪个都行。
```

## 面试题

```text
1. LVM 三层结构是什么？
   答：PV（物理卷）→ VG（卷组，多个 PV 的池）→ LV（逻辑卷，从池里划分），三层分离实现动态扩缩。

2. LVM 在线扩容的原理？
   答：LV 是 extent 集合，lvextend 给 LV 加 extent（改映射表），resize2fs 让文件系统用上新空间，全程不卸载、不动数据。

3. 缩容为什么必须先缩文件系统？
   答：逻辑卷和文件系统是两层，先缩逻辑卷会截断文件系统正在用的空间导致损坏，必须先缩文件系统再缩逻辑卷。

4. LVM 快照的实现原理？
   答：写时复制（COW），打快照时记录源卷状态，源卷变化时把旧数据复制到快照区，快照保留变化前的数据。

5. PE 和 LE 是什么关系？
   答：PE 是 VG 空间的物理分配单元（默认 4MiB），LE 是 LV 的逻辑组成单元，两者一一映射，LV 容量 = LE 数 × PE 大小。

6. pvmove 的作用和使用前提？
   答：把某 PV 上的数据在线迁移到 VG 内其他 PV，用于移除旧盘前保护数据；前提是目标 PV 剩余空间足够容纳要迁的数据。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 系统盘用 LVM 管理，扩容不用重分区，运维友好
2. 扩容顺序：lvextend 先扩逻辑卷，再 resize2fs/xfs_growfs 扩文件系统
3. 缩容顺序相反：先缩文件系统，再 lvreduce 缩逻辑卷，且 ext4 要先卸载
4. 备份/升级前打 LVM 快照，保证数据一致性、失败可回滚
5. VG 留 20% 余量，快照也要占空间，别把池用满
6. 移除 PV 先 pvmove 再 vgreduce，顺序不能省
7. 扩容用 lvextend -r 一步到位（ext4 自动 resize 文件系统），减少漏步骤

### 踩坑记录

```text
坑 1：扩容顺序反了，文件系统没变大
结论：lvextend 后 df 看容量没变。
原因：逻辑卷和文件系统是两层，扩了逻辑卷还得扩文件系统。
解法：扩逻辑卷 lvextend 后必须 resize2fs（ext4）或 xfs_growfs（XFS）。

坑 2：缩容顺序反了导致数据损坏
结论：先 lvreduce 缩逻辑卷，再 resize2fs，文件系统损坏。
原因：必须先缩文件系统再缩逻辑卷，反过来会截断数据。
解法：严格按「resize2fs 缩文件系统 → lvreduce 缩逻辑卷」顺序。

坑 3：XFS 想缩容发现不支持
结论：XFS 文件系统 lvreduce 前 resize 失败。
原因：XFS 不支持在线/离线缩容，只能扩不能缩。
解法：XFS 需要缩容只能备份数据、重建小卷、恢复数据。

坑 4：快照空间满了导致 IO 中断
结论：快照卷满了，被快照的逻辑卷 IO 报错。
原因：写时复制快照会随源卷变化增长，满了就无法记录变化。
解法：快照设足够空间（源卷变化量的估计值），用完及时删除。

坑 5：vgreduce 移除 PV 前没迁移数据
结论：直接 vgreduce 移除还有数据的 PV，数据丢失。
原因：PV 上有逻辑卷的数据，直接移除会破坏。
解法：先 pvmove 把数据迁到别的 PV，再 vgreduce 移除。

坑 6：扩容时 VG 空间不够直接报错
结论：lvextend -L +50G 报 insufficient free space。
原因：VG 池剩余空间不足，没先加盘扩池。
解法：先 pvcreate + vgextend 加 PV 扩池，再 lvextend。

坑 7：重启后 LV 设备不存在
结论：/dev/vgdata/lvdata 没了，挂载失败。
原因：VG 未激活（inactive），或 lvm.conf filter 把盘拒之门外。
解法：vgchange -ay vgdata 激活 VG；检查 filter 配置是否误拦。
```
