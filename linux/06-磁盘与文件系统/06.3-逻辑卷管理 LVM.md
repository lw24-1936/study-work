## 概述

LVM（Logical Volume Manager，逻辑卷管理）在物理分区之上加了一层抽象，让磁盘容量可以动态调整——不用重新分区就能扩容、缩容、跨盘合并。核心是三层结构：PV（物理卷，即磁盘/分区）→ VG（卷组，多个 PV 组成的池）→ LV（逻辑卷，从 VG 里划分的「虚拟分区」）。传统分区「定死了大小不好改」，LVM 解决了这个痛点。

```text
LVM 三层结构：
物理磁盘/分区 → PV 物理卷 → VG 卷组（池）→ LV 逻辑卷（虚拟分区）
1. PV —— pvcreate 把分区标记为物理卷
2. VG —— vgcreate 把多个 PV 聚成一个容量池
3. LV —— lvcreate 从池里划出逻辑卷，上面建文件系统
# 本机未用 LVM（sda2 直接是 ext4 分区），以下为通用操作示例
```

## 核心概念

理解三层才能看懂 LVM 的灵活性。PV 是最底层（磁盘/分区被标记为物理卷），VG 把多个 PV 聚合成一个大池子（容量 = 所有 PV 之和），LV 从池子里按需划分（想划多少划多少，不够了再扩）。好处：LV 可以跨多块物理盘、在线扩容（不停机）、快照。查看用 pvs/vgs/lvs。

```shell
pvs                              # 查看物理卷
vgs                              # 查看卷组
lvs                              # 查看逻辑卷
pvdisplay /dev/sdb1              # 物理卷详情
vgdisplay vgdata                 # 卷组详情
lvdisplay /dev/vgdata/lvdata     # 逻辑卷详情
```

```text
LVM 三层：
1. PV 物理卷 —— 磁盘/分区被 pvcreate 标记，最小物理单元
2. VG 卷组 —— 多个 PV 聚成的容量池，容量 = 所有 PV 之和
3. LV 逻辑卷 —— 从 VG 划出的虚拟分区，可动态扩缩，上面建文件系统
```

## 工作原理

LVM 的核心是「extent 映射」：VG 把空间分成固定大小的 extent（PE，默认 4MiB），LV 是一串 extent 的集合。LV 到 PV 的映射由内核的 device-mapper（dm 设备）维护——/dev/vgdata/lvdata 实际是 dm 设备的符号链接，读写时 dm 按映射表把逻辑地址翻译成物理地址（哪个 PV 的哪个 extent）。所以 LV 可以跨盘、可以动态扩缩（改映射表就行，不动数据）。

快照用「写时复制（COW）」：打快照时几乎不占空间，之后源卷数据变化时，先把旧数据复制到快照区再写新数据，快照里保留的是「变化前的旧数据」，从而能还原到打快照那一刻的状态。

```text
LVM 工作原理：
1. extent 映射 —— VG 空间分 PE（默认 4MiB），LV 是一串 PE，dm 设备维护 LV→PV 映射
2. 动态扩缩 —— 改映射表即可（lvextend/lvreduce），不搬动数据
3. 快照 COW —— 写时复制，源卷变化时旧数据复制到快照区，还原到快照时刻
4. device-mapper —— /dev/vg/lv 是 dm 设备的符号链接，内核按映射表寻址
```

## 常用命令与配置

创建 LVM 的完整流程：分区/整盘做 PV → 建 VG → 建 LV → 格式化 → 挂载。五步走通后，/dev/vgdata/lvdata 就是一个可以正常使用的逻辑卷。逻辑卷的设备路径是 /dev/<卷组名>/<逻辑卷名>。

```shell
# 1. 创建物理卷
pvcreate /dev/sdb1 /dev/sdc1
# 2. 创建卷组（把两个 PV 聚成池）
vgcreate vgdata /dev/sdb1 /dev/sdc1
# 3. 创建逻辑卷（从池里划 100G）
lvcreate -L 100G -n lvdata vgdata
# 4. 格式化
mkfs.ext4 /dev/vgdata/lvdata
# 5. 挂载
mount /dev/vgdata/lvdata /data
```

扩容：先 lvextend 扩逻辑卷（加容量，可跨盘），再 resize2fs 扩文件系统（让文件系统用上新空间）。VG 池不够时先加 PV（vgextend）扩充池。XFS 用 xfs_growfs 代替 resize2fs。

```shell
# 1. 池不够先加 PV
pvcreate /dev/sdd1
vgextend vgdata /dev/sdd1
# 2. 扩逻辑卷（+50G）
lvextend -L +50G /dev/vgdata/lvdata
# 3. 扩文件系统（ext4 用 resize2fs，XFS 用 xfs_growfs）
resize2fs /dev/vgdata/lvdata
# 4. 验证
df -h /data
```

缩容比扩容危险得多，且 ext4 缩容需要先卸载（不能在线缩）。流程：先 umount → e2fsck 检查 → resize2fs 缩文件系统 → lvreduce 缩逻辑卷 → 重新挂载。注意缩容顺序不能反——必须先缩文件系统再缩逻辑卷，否则数据损坏。XFS 不支持缩容（只能备份重建）。

```shell
# 缩容（先卸载，顺序不能反）
umount /data
e2fsck -f /dev/vgdata/lvdata          # 检查
resize2fs /dev/vgdata/lvdata 50G      # 先缩文件系统
lvreduce -L 50G /dev/vgdata/lvdata    # 再缩逻辑卷
mount /dev/vgdata/lvdata /data
```

快照：LVM 快照是逻辑卷某一时刻的只读副本，用「写时复制」实现——快照只记录变化，所以创建快、占用小。用途：备份前先打快照（保证备份数据一致性）、升级前打快照（失败可回滚）。

```shell
# 创建快照（记录 lvdata 的当前状态）
lvcreate -L 10G -s -n lvdata_snap /dev/vgdata/lvdata
# 挂载快照读取数据
mount /dev/vgdata/lvdata_snap /mnt/snap
# 用完删除快照
umount /mnt/snap
lvremove /dev/vgdata/lvdata_snap
```

## 配置文件解析

LVM 的全局配置在 /etc/lvm/lvm.conf，常见要改的：filter（限制哪些设备被 LVM 识别，防止 LVM 扫到无关设备）、devices 段（扫描设备）。VG/LV 的元数据存储在 PV 上（不是配置文件），用 vgcfgbackup/vgcfgrestore 备份恢复。

```shell
grep -vE '^\s*#|^\s*$' /etc/lvm/lvm.conf | head   # 看生效配置
vgcfgbackup vgdata                    # 备份 VG 元数据到 /etc/lvm/backup/
vgcfgrestore vgdata                   # 恢复 VG 元数据
```

```text
LVM 配置要点：
1. /etc/lvm/lvm.conf —— 全局配置，filter 决定扫描哪些设备
2. VG/LV 元数据在 PV 上 —— 不在配置文件里，用 vgcfgbackup 备份
3. 多路径/存储场景 —— 用 filter 精确指定设备，防止 LVM 误扫
```

## 应用场景实战

### 场景一：根分区满了，用 LVM 在线扩容

```shell
# 1. 确认根分区是 LVM
df -h / && lvs
# 2. 加新盘并扩 VG
pvcreate /dev/sdc1
vgextend vgroot /dev/sdc1
# 3. 在线扩根逻辑卷和文件系统
lvextend -L +50G /dev/vgroot/lvroot
resize2fs /dev/vgroot/lvroot
df -h /
```

### 场景二：数据库备份前打快照保证一致性

```shell
# 1. 打快照（冻结数据状态）
lvcreate -L 20G -s -n mysql_snap /dev/vgdata/lv_mysql
# 2. 从快照备份（不影响运行中的数据库）
mount /dev/vgdata/mysql_snap /mnt/snap
tar czf /backup/mysql.tar.gz /mnt/snap
# 3. 清理快照
umount /mnt/snap
lvremove /dev/vgdata/mysql_snap
```

## 性能与调优

LVM 的性能要点：LV 可以用条带化（lvcreate --stripes N，数据分散到多块 PV 并行读写，提升吞吐）；VG 的 PE 大小（默认 4MiB）影响空间利用率；快照会拖慢源卷（每次写都要 COW），用完及时删。LV 本身性能接近裸分区（dm 映射开销极小），不必担心 LVM 拖慢性能。

```text
LVM 性能要点：
1. 条带化 —— lvcreate --stripes N 分散到多 PV 并行读写，提升吞吐
2. PE 大小 —— 默认 4MiB，影响空间分配粒度
3. 快照开销 —— 快照在时源卷每次写都要 COW，用完及时删
4. dm 开销 —— 映射开销极小，LV 性能接近裸分区
```

## 安全与权限

LVM 本身不加密，敏感数据可在 LV 上叠 LUKS 加密（加密层在 LVM 之上或之下都行，常见「LUKS 在 LV 之上」）。权限方面：LVM 操作要 root；VG 里移除 PV 前必须先 pvmove 迁移数据（防数据丢失）。快照是只读副本，但快照区本身占 VG 空间，别让快照撑爆 VG。

```text
LVM 安全要点：
1. 加密 —— 敏感数据在 LV 上叠 LUKS 加密（cryptsetup luksFormat）
2. 权限 —— LVM 管理命令要 root 权限
3. 移除 PV 先 pvmove —— vgreduce 前迁移数据，防止丢数据
4. 快照空间 —— 快照占 VG 空间，监控别撑爆
```

## 故障排查

### 缩容顺序反了导致数据损坏

```shell
# 症状：先 lvreduce 再 resize2fs，文件系统损坏
# 正确顺序：先 resize2fs 缩文件系统，再 lvreduce 缩逻辑卷
# 已损坏则：e2fsck -f 尝试修复，严重时从备份恢复
```

### 快照空间满了导致 IO 中断

```shell
# 1. 看快照使用情况
lvs -a vgdata
# 2. 快照 100% 了，删除快照恢复
lvremove /dev/vgdata/lvdata_snap
# 3. 后续快照设足够空间（源卷变化量的估计值）
```

## 常见问题

```text
Q1: LVM 和普通分区比有什么优势？
A: 可以动态扩缩容（不停机）、跨盘合并、打快照，不用重新分区。

Q2: 扩容为什么 lvextend 后 df 看容量没变？
A: 扩了逻辑卷还得扩文件系统（resize2fs/xfs_growfs），两层要都扩。

Q3: XFS 能缩容吗？
A: 不能。XFS 只支持扩容，缩容只能备份数据、重建小卷、恢复数据。

Q4: 快照能当备份吗？
A: 不能。快照是 COW 的临时副本（依赖源卷，源卷坏快照也坏），只用于备份前的瞬时一致快照，真正备份要另存。
```

## 面试题

```text
1. LVM 三层结构是什么？
   答：PV（物理卷）→ VG（卷组，多个 PV 的池）→ LV（逻辑卷，从池里划分），三层分离实现动态扩缩。

2. LVM 在线扩容的原理？
   答：LV 是 extent 集合，lvextend 给 LV 加 extent（改映射表），resize2fs 让文件系统用上新空间，全程不卸载、不动数据。

3. 缩容为什么必须先缩文件系统？
   答：逻辑卷和文件系统是两层，先缩逻辑卷会截断文件系统正在用的空间导致损坏，必须先缩文件系统再缩逻辑卷。

4. LVM 快照的实现原理？
   答：写时复制（COW），打快照时记录源卷状态，源卷变化时把旧数据复制到快照区，快照保留变化前的数据。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 系统盘用 LVM 管理，扩容不用重分区，运维友好
2. 扩容顺序：lvextend 先扩逻辑卷，再 resize2fs/xfs_growfs 扩文件系统
3. 缩容顺序相反：先缩文件系统，再 lvreduce 缩逻辑卷，且 ext4 要先卸载
4. 备份/升级前打 LVM 快照，保证数据一致性、失败可回滚
5. VG 留 20% 余量，快照也要占空间，别把池用满

### 踩坑记录

```text
坑 1：扩容顺序反了，文件系统没变大
结论：lvextend 后 df 看容量没变。
原因：逻辑卷和文件系统是两层，扩了逻辑卷还得扩文件系统。
解法：扩逻辑卷 lvextend 后必须 resize2fs（ext4）或 xfs_growfs（XFS）。

坑 2：缩容顺序反了导致数据损坏
结论：先 lvreduce 缩逻辑卷，再 resize2fs，文件系统损坏。
原因：必须先缩文件系统再缩逻辑卷，反过来会截断数据。
解法：严格按「resize2fs 缩文件系统 → lvreduce 缩逻辑卷」顺序。

坑 3：XFS 想缩容发现不支持
结论：XFS 文件系统 lvreduce 前 resize 失败。
原因：XFS 不支持在线/离线缩容，只能扩不能缩。
解法：XFS 需要缩容只能备份数据、重建小卷、恢复数据。

坑 4：快照空间满了导致 IO 中断
结论：快照卷满了，被快照的逻辑卷 IO 报错。
原因：写时复制快照会随源卷变化增长，满了就无法记录变化。
解法：快照设足够空间（源卷变化量的估计值），用完及时删除。

坑 5：vgreduce 移除 PV 前没迁移数据
结论：直接 vgreduce 移除还有数据的 PV，数据丢失。
原因：PV 上有逻辑卷的数据，直接移除会破坏。
解法：先 pvmove 把数据迁到别的 PV，再 vgreduce 移除。
```
