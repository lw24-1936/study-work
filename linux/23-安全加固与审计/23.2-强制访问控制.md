## 概述

强制访问控制（Mandatory Access Control，MAC）是 Linux 传统「自主访问控制」（DAC）之外的第二层权限模型。DAC 里文件属主可以随意 chmod 把权限放出去，一旦进程被攻破（如拿到 root），就能访问任何资源；MAC 则由系统统一强制执行一套策略，即便 root 或属主也不能越界——被攻破的进程（哪怕是 root 起的）也只能在策略允许的范围内活动，把「漏洞被利用后的横向移动」死死按住。Linux 两大实现：SELinux（RHEL/CentOS/Fedora）和 AppArmor（Ubuntu/SUSE）。

```text
MAC 两大实现：
SELinux   基于「安全上下文标签 + 类型强制」，策略精细、默认随 RHEL 系分发（targeted 策略）
AppArmor  基于「文件路径 + 配置文件」，简单直观、Ubuntu/SUSE 默认启用
共同点    内核强制、root 也不能绕过、都是"进程只能访问被允许的资源"
```

## 核心概念

### 自主访问控制与强制访问控制（DAC vs MAC）

理解 MAC 先要理解它和 DAC 的区别：

- **DAC（Discretionary Access Control，自主访问控制）**：资源属主「自主」决定谁能访问——就是经典的 rwx 权限 + ACL。问题是：权限跟着「属主」走，root 拥有全部权限，一旦进程以 root 身份被攻破，整个系统沦陷。
- **MAC（Mandatory Access Control，强制访问控制）**：系统管理员制定统一策略，由内核「强制」执行，属主和 root 都无法绕过。它回答的问题是「这个进程被允许访问哪些资源」，与「进程以谁的身份跑」无关。DAC 允许的操作，MAC 仍可拒绝，两者是「与」的关系。

```text
DAC vs MAC：
DAC  属主自主授权，root 全权，权限跟着"身份"走（rwx/ACL）
MAC  系统强制策略，root 也不能越界，权限跟着"进程+资源标签"走
关系 两层叠加，DAC 放行后 MAC 还要放行，操作才真正成功（缺一不可）
```

### SELinux

SELinux 的核心是「安全上下文（security context）」+「类型强制（Type Enforcement，TE）」。每个进程和文件都带一个标签（label），如 `system_u:system_r:httpd_t:s0`，格式为「用户:角色:类型:级别」。策略规则规定「类型 A 的进程能不能访问类型 B 的文件」，例如 `httpd_t` 进程只允许读 `httpd_sys_content_t` 类型的文件——即使 httpd 以 root 跑，它也只能读被标记为 web 内容的文件，读不到 `/etc/shadow`。

运行模式三种：

- **enforcing**：强制执行策略，违规操作被拒绝并记录（默认生产状态）
- **permissive**：不拒绝，但记录违规日志（排错用，看「如果强制会拒绝什么」）
- **disabled**：完全关闭

```shell
# 查看状态与模式
getenforce                # 输出 Enforcing / Permissive / Disabled
sestatus                  # 详细信息（模式 + 策略版本 + 当前进程上下文）

# 切换模式（临时，重启失效；永久改 /etc/selinux/config）
setenforce 0              # 临时切到 permissive
setenforce 1              # 临时切到 enforcing

# 查看文件/进程的安全上下文
ls -Z /var/www/html       # 文件标签
ps -eZ | grep httpd       # 进程标签
```

```text
SELinux 要点：
安全上下文  用户:角色:类型:级别，如 system_u:system_r:httpd_t:s0
类型强制    规则决定"类型 A 能否访问类型 B"，与用户身份/root 无关
三种模式    enforcing 强制 / permissive 只记录 / disabled 关闭
标签来源    文件标签由策略 + 路径规则自动分配（restorecon 恢复默认）
```

### AppArmor

AppArmor 走的是「按路径」的路子：给每个程序写一个 profile（配置文件），声明这个程序能访问哪些文件路径、能做什么（读写/执行/网络/挂载）。规则直接写路径（如 `/var/www/** rw`），比 SELinux 的类型标签更直观。profile 两种模式：

- **enforce**：强制，违规即拒绝
- **complain**：只记录不拒绝（排错用，类比 SELinux 的 permissive）

```shell
# 查看状态
aa-status                        # 列出已加载的 profile 及其模式

# 查看某进程是否被 AppArmor 约束
sudo aa-status | grep -A5 '<进程名>'

# 切换 profile 模式
sudo aa-complain /etc/apparmor.d/usr.sbin.nginx   # 切到 complain（只记录）
sudo aa-enforce /etc/apparmor.d/usr.sbin.nginx    # 切回 enforce

# 加载/重载一个 profile
sudo apparmor_parser -r /etc/apparmor.d/usr.sbin.nginx
```

```text
AppArmor 要点：
按路径   profile 直接写文件路径 + 权限（/var/www/** rw），比 SELinux 标签直观
模式     enforce 强制 / complain 只记录不拒绝
profile 位置 /etc/apparmor.d/，一个程序一个 profile
适用     Ubuntu/SUSE 默认；Docker 默认用 AppArmor 保护容器进程
```

### 策略与排错

「策略」是 MAC 的灵魂——SELinux 的策略是类型规则集合（targeted 策略只约束关键服务，mls 策略更严格），AppArmor 的策略就是各程序的 profile。排错的核心思路一致：**先确认是 MAC 拦截了操作（查日志），再决定是「改策略放行」还是「修标签/profile」**，而不是一上来就 `setenforce 0` 或关掉 AppArmor 逃避问题。

```shell
# SELinux 排错三件套
grep 'denied' /var/log/audit/audit.log | tail       # 看被拒绝的操作
sealert -a /var/log/audit/audit.log                 # 人性化解读 + 给修复建议（setroubleshoot）
audit2allow -a -M mypol                             # 从拒绝日志生成放行策略模块
semodule -i mypol.pp                                # 加载生成的策略模块

# AppArmor 排错三件套
sudo journalctl -k | grep -i apparmor               # 看内核日志里的 DENIED
sudo aa-logprof                                     # 交互式：根据拒绝日志补全 profile
sudo aa-complain <profile>                          # 先切 complain 收集日志再补规则
```

```text
排错核心思路：
1. 先看日志确认"是不是 MAC 拦的"（SELinux 看 audit.log 的 denied，AppArmor 看内核日志 DENIED）
2. 是 MAC 拦截 → 改策略/修标签/补 profile 放行，而不是关掉 MAC
3. 不是 MAC 拦截 → 回到 DAC 权限、防火墙、服务本身排查
4. 修复后 restorecon / apparmor_parser -r 重新加载，验证放行
```

## 工作原理

MAC 在内核层做「访问裁决」，流程可以概括为「每次访问都过一道内核策略检查」：

1. **DAC 先判**：进程访问资源，内核先走传统 rwx/ACL 检查，DAC 拒绝就直接拒绝。
2. **MAC 再判**：DAC 放行后，进入 LSM（Linux Security Modules，Linux 安全模块）钩子。LSM 是内核里的一层「策略裁决接口」，SELinux 和 AppArmor 都是挂在 LSM 上的具体实现。
3. **查策略**：SELinux 根据「主体类型（进程标签）→ 客体类型（文件标签）」查类型规则；AppArmor 根据「进程的 profile → 文件路径」查路径规则。
4. **裁决**：策略允许则放行，拒绝则返回 EACCES/EPERM，并写一条审计日志（SELinux 写 audit.log 的 AVC 记录，AppArmor 写内核日志的 DENIED）。

关键点：这个检查发生在**内核层、每一次系统调用**，所以属主、root、capability 都无法绕过——它是真正的「强制」。

```text
MAC 工作流程：
进程访问资源 → DAC（rwx/ACL）拒绝？ → 拒绝
                    ↓ 放行
             LSM 钩子 → SELinux 查类型规则 / AppArmor 查路径规则
                    ↓
             允许 → 放行；拒绝 → EACCES + 写审计日志（AVC / DENIED）

位置：内核层每次系统调用都查，root 与属主都无法绕过
```

## 常用命令与配置

```shell
# === SELinux 状态与模式 ===
getenforce / sestatus               # 查模式
setenforce 0|1                      # 临时切 permissive/enforcing
# 永久：/etc/selinux/config 里 SELINUX=enforcing

# === SELinux 标签 ===
ls -Z /path                         # 看文件标签
ps -eZ | grep <proc>                # 看进程标签
restorecon -Rv /var/www/html        # 恢复目录默认标签（-R 递归 -v 显示）
chcon -t httpd_sys_content_t /custom/index.html   # 手动改单个文件类型标签
semanage fcontext -a -t httpd_sys_content_t "/custom(/.*)?"   # 永久定义路径默认标签
restorecon -Rv /custom              # 应用上面定义的标签

# === SELinux 布尔值（开关型策略项） ===
getsebool -a                        # 列出所有布尔值
setsebool -P httpd_can_network_connect on   # 允许 httpd 联网（-P 永久）
semanage port -a -t http_port_t -p tcp 8080  # 允许 httpd 监听 8080 端口

# === AppArmor 状态与模式 ===
aa-status                           # 列出 profile 与模式
aa-enforce /etc/apparmor.d/<name>   # 切 enforce
aa-complain /etc/apparmor.d/<name>  # 切 complain
apparmor_parser -r /etc/apparmor.d/<name>   # 重载 profile
```

```text
命令分组记忆：
状态模式  getenforce/setenforce、aa-status/aa-enforce/aa-complain
标签      ls -Z / chcon / restorecon / semanage fcontext
开关      getsebool/setsebool、semanage port
排错      audit2allow / sealert、aa-logprof
```

## 配置文件解析

### /etc/selinux/config（SELinux 主配置）

```ini
# /etc/selinux/config
SELINUX=enforcing          # 模式：enforcing / permissive / disabled
SELINUXTYPE=targeted       # 策略类型：targeted（约束关键服务）/ mls（更严格，少用）
```

```text
字段要点：
SELINUX    永久模式，改完重启（或 setenforce 临时切）生效
SELINUXTYPE targeted 只约束关键服务，其它进程跑 unconfined_t 不受限；mls 全约束但配置复杂
disabled 改 enforcing 需要 relabel（重启时自动 touch /.autorelabel）
```

### /etc/apparmor.d/*（AppArmor profile 文件）

每个 profile 一个文件，文件名通常是程序路径把 `/` 换成 `.`（如 `/usr/sbin/nginx` → `usr.sbin.nginx`）。

```text
# /etc/apparmor.d/usr.sbin.nginx（简化示例）
#include <tunables/global>          # 引入公共变量定义

/usr/sbin/nginx {                   # profile 名 = 受约束的程序路径
  #include <abstractions/base>      # 引入公共权限集合（库/设备等）

  capability net_bind_service,      # 允许绑定 1024 以下端口
  network tcp,                      # 允许 TCP 网络

  /etc/nginx/** r,                  # 读配置
  /var/log/nginx/** rw,             # 读写日志
  /var/www/** r,                    # 读网站内容
  /run/nginx.pid rw,                # 读写 pid 文件

  deny /etc/shadow r,               # 显式拒绝读 shadow（默认就拒绝，这里强调）
}
```

```text
profile 语法要点：
路径权限    /path/** rw  —— ** 递归，r 读 w 写 x 执行 m 内存映射 l 链接
capability  声明进程需要的 Linux capability（net_bind_service 等）
include     抽象层 abstractions/* 预定义公共权限，减少重复
deny 规则   显式拒绝（默认未声明的都拒绝，deny 用于强调/覆盖 include）
```

## 应用场景实战

### 场景一：SELinux 拦截 Web 服务访问自定义目录，排错并放行

把网站根目录放到非默认路径（如 `/srv/web`），httpd 报 403 或读不到文件——经典 SELinux 标签问题。正确做法是「修标签」而不是关 SELinux。

```shell
# 1. 现象：curl 返回 403
curl http://localhost/ 2>&1 | head

# 2. 查 SELinux 是否拦截
grep denied /var/log/audit/audit.log | tail -3
# 示例输出（type=AVC 记录表示 SELinux 拒绝）：
# type=AVC msg=audit(...): avc:  denied  { getattr } for  pid=1234 comm="httpd"
#   path="/srv/web/index.html" dev="sda1" ino=42
#   scontext=system_u:system_r:httpd_t:s0
#   tcontext=unconfined_u:object_r:default_t:s0 tclass=file

# 3. 看当前目录标签（default_t 是"未定义"标签，httpd 读不到）
ls -Z /srv/web

# 4. 永久定义路径默认标签 + 恢复
semanage fcontext -a -t httpd_sys_content_t "/srv/web(/.*)?"
restorecon -Rv /srv/web
ls -Z /srv/web        # 确认变成 httpd_sys_content_t

# 5. 验证恢复访问
curl -I http://localhost/
```

```text
排错关键：看 audit.log 的 avc denied → 确认 scontext/tcontext → semanage fcontext 定义标签 → restorecon 恢复
要点：用 semanage fcontext 定义"路径默认标签"是持久化的，直接 chcon 改标签重启/relabel 后会丢
```

### 场景二：为自定义程序写一个最小 AppArmor profile

为一个自己写的服务（如 `/opt/app/bin/myserver`）写最小权限 profile，只给它需要的路径和权限。

```shell
# 1. 新建 profile 骨架
sudo tee /etc/apparmor.d/opt.app.bin.myserver <<'EOF'
#include <tunables/global>

/opt/app/bin/myserver {
  #include <abstractions/base>

  capability net_bind_service,
  network tcp,

  /opt/app/bin/myserver mr,
  /etc/myserver.conf r,
  /var/log/myserver/** rw,
  /var/lib/myserver/** rw,
}
EOF

# 2. 加载并切到 enforce
sudo apparmor_parser -r /etc/apparmor.d/opt.app.bin.myserver
sudo aa-enforce /etc/apparmor.d/opt.app.bin.myserver

# 3. 启动服务，观察是否被拦
sudo systemctl start myserver
sudo journalctl -k | grep -i 'apparmor.*DENIED'   # 有 DENIED 就说明 profile 漏了权限

# 4. 交互式补全（根据日志自动建议规则）
sudo aa-logprof
# 按提示选择 Allow / Deny，自动把缺失路径补进 profile
```

```text
最小 profile 写法：include 公共抽象 → 声明 capability/network → 逐个路径授权（能读的读、能写的写）
排错闭环：跑起来 → journalctl 看 DENIED → aa-logprof 补规则 → 重载
```

## 性能与调优

```text
1. MAC 裁决发生在系统调用路径上，有极小的常数开销——普通业务可忽略（个位数百分比内）
2. SELinux 用 AVC 缓存（Access Vector Cache）缓存已裁决结果，重复访问同一类型不重复查策略，开销更低
3. AppArmor 用 DFA（确定有限自动机）匹配路径规则，profile 大时匹配仍是线性、可预测
4. permissive / complain 模式开销与 enforcing 相当（照样记录），别把"排错模式"当"提速手段"
5. 真正的性能注意：高并发 + 大策略下，SELinux 的 AVC 缓存 miss 率会影响吞吐，可加大缓存或用 audit2allow 精简规则
```

```text
结论：MAC 性能开销很小（<1%~5%），不是关掉它的理由。关掉 MAC 换来的性能提升远小于安全损失
```

## 安全与权限

```text
1. 生产永远 enforcing / enforce 模式，permissive/complain 只用于排错，排完切回
2. 不要用 setenforce 0 或禁用 AppArmor 来"解决"服务问题——那是绕过不是修复，会留下隐患
3. 生成的自定义策略（audit2allow 产物）要人工审查：它只从日志推断"放行"，可能放得太宽，别盲目加载
4. restorecon / relabel 会重置标签——迁移文件、改挂载点后要 restorecon，否则默认标签（default_t）会让服务读不到
5. MAC 日志本身含敏感信息（访问路径/进程），审计日志访问也要控制（配合 23.3 审计）
6. 容器注意：Docker 默认用 AppArmor 保护容器进程，自定义容器可加自定义 profile 收紧容器内进程权限
```

## 故障排查

### SELinux 导致服务异常（最典型）

```shell
# 1. 确认是不是 SELinux 拦的
grep -E 'denied|AVC' /var/log/audit/audit.log | tail -20

# 2. 快速验证：临时切 permissive 看问题是否消失（只做诊断，别停在这）
setenforce 0
# 复现操作 → 若正常，说明是 SELinux 拦截
setenforce 1        # 立即切回 enforcing

# 3. 用 sealert 拿人性化建议
sealert -a /var/log/audit/audit.log

# 4. 按建议修复：改布尔值 / 改端口标签 / 改文件标签
setsebool -P <bool> on
semanage port -a -t <type> -p tcp <port>
semanage fcontext -a -t <type> '<path>(/.*)?' && restorecon -Rv <path>

# 5. 验证
grep denied /var/log/audit/audit.log | tail
```

```text
SELinux 排错三板斧：
1. 查日志（audit.log 的 AVC denied）确认拦截
2. sealert 给建议（该改布尔值/端口/标签）
3. 对症修复 + 验证，而不是 setenforce 0 了事
```

### AppArmor 拦截导致程序起不来

```shell
# 1. 查内核日志里的 DENIED
sudo journalctl -k | grep -i 'apparmor.*DENIED' | tail

# 2. 确认该进程的 profile 和模式
sudo aa-status | grep -B2 -A8 '<程序名>'

# 3. 切 complain 收集完整拒绝记录（不中断服务）
sudo aa-complain /etc/apparmor.d/<profile>

# 4. 交互式补全 profile
sudo aa-logprof

# 5. 切回 enforce 并重载验证
sudo aa-enforce /etc/apparmor.d/<profile>
sudo apparmor_parser -r /etc/apparmor.d/<profile>
```

```text
AppArmor 排错三板斧：
1. journalctl -k 看 DENIED
2. aa-complain 收集记录（服务不断）
3. aa-logprof 补规则 → aa-enforce 切回
```

## 常见问题

```text
Q1: SELinux 和 AppArmor 怎么选？
A: 看发行版——RHEL/CentOS/Fedora 用 SELinux，Ubuntu/SUSE 用 AppArmor，两者都挂在 LSM 上，别同时启用（会冲突）。不跨发行版迁移时用系统默认的那个即可。

Q2: setenforce 0 和修改 /etc/selinux/config 区别？
A: setenforce 0 是运行时临时切 permissive，重启恢复；改 config 的 SELINUX= 是永久配置。生产排错只用 setenforce 0 做「诊断」，确诊后改回 1 并修复策略/标签。

Q3: disabled 改回 enforcing 为什么系统要 relabel？
A: disabled 状态下文件没打标签，直接开 enforcing 会导致所有进程访问都被拒。需要 touch /.autorelabel 后重启，系统重新给全盘文件打标签。

Q4: permissive 模式会不会漏掉攻击？
A: permissive 只记录不拒绝，等于 MAC 失效，只适合「排错窗口」。生产长期 permissive 等于白装 SELinux——记得排完切回 enforcing。

Q5: 为什么 root 也绕不过 MAC？
A: 因为 MAC 裁决在内核 LSM 钩子层、每次系统调用都查，规则依据「进程类型/路径」而非「用户身份」。root 只是 DAC 层面的全权，MAC 层面仍受策略约束。

Q6: AppArmor profile 里没写的路径默认是允许还是拒绝？
A: 默认拒绝（deny-by-default）。profile 只放行显式声明的路径，没写的都拒绝。所以最小 profile 就是「只写程序真正需要的路径」。
```

## 面试题

```text
1. DAC 和 MAC 的区别？
   答：DAC（自主访问控制）由资源属主决定权限，root 全权，可被攻破后失控；MAC（强制访问控制）由系统统一策略在内核强制执行，属主和 root 都不能越界，进程只能访问策略允许的资源。两层叠加，DAC 放行后 MAC 还要放行。

2. SELinux 的三种模式？
   答：enforcing（强制，违规拒绝并记录）、permissive（不拒绝只记录，排错用）、disabled（关闭）。生产用 enforcing，排错临时切 permissive，disabled 改 enforcing 需 relabel。

3. SELinux 的安全上下文是什么？
   答：进程和文件带的标签，格式「用户:角色:类型:级别」，如 system_u:system_r:httpd_t:s0。类型强制（TE）规则决定「类型 A 的进程能否访问类型 B 的文件」。

4. 服务被 SELinux 拦了，正确排错流程？
   答：先 grep audit.log 的 avc denied 确认拦截 → sealert 拿建议 → 对症修复（setsebool 改布尔值 / semanage port 改端口 / semanage fcontext + restorecon 改文件标签）→ 验证。不要 setenforce 0 了事。

5. AppArmor 的 enforce 和 complain 模式区别？
   答：enforce 强制拒绝违规访问；complain 只记录不拒绝（类比 SELinux 的 permissive），用于收集规则再 aa-logprof 补 profile。

6. SELinux 和 AppArmor 的模型差异？
   答：SELinux 基于「标签 + 类型强制」，策略精细但标签体系复杂；AppArmor 基于「文件路径 + profile」，规则直观简单。SELinux 默认 RHEL 系，AppArmor 默认 Ubuntu/SUSE。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产保持 enforcing / enforce，permissive / complain 只做短时排错窗口，排完立即切回
2. 排错先查日志确认「是 MAC 拦截」，再修策略/标签/profile，别关 MAC 逃避
3. 自定义目录配 SELinux 用 `semanage fcontext` 定义路径默认标签再 `restorecon`，别用 chcon 临时改
4. 自定义 AppArmor profile 坚持最小权限（deny-by-default），用 aa-logprof 按真实访问补全
5. 迁移文件/改挂载点后执行 restorecon，避免 default_t 标签导致服务读不到
6. 审计 MAC 的拒绝日志（audit.log / 内核日志），异常 AVC/DENIED 是入侵信号，接入告警

### 踩坑记录

```text
坑 1：服务异常，一上来就 setenforce 0 或关 AppArmor
结论：服务恢复了，但 MAC 形同虚设，长期留下安全隐患。
原因：把"绕过"当"修复"，没定位真正的策略/标签问题。
解法：用 permissive/complain 只做诊断，确诊后改策略/标签/profile 放行，切回 enforcing。

坑 2：用 chcon 改标签，重启或 relabel 后又变回 default_t
结论：改完当时能访问，过段时间又 403。
原因：chcon 只改当前文件标签，不改变"路径默认标签"策略，relabel 时被重置。
解法：semanage fcontext -a -t <type> '<path>(/.*)?' 定义持久标签，再 restorecon 应用。

坑 3：audit2allow 生成的策略模块直接加载，放权过宽
结论：服务能跑了，但策略放行了远超需要的权限，等于开了口子。
原因：audit2allow 只从日志推断"放行什么"，不看最小必要性，可能把高风险访问一起放行。
解法：人工审查生成的 .te 规则，只保留业务真正需要的，再 semodule -i 加载。

坑 4：disabled 改 enforcing 没 relabel，开机所有进程访问被拒
结论：系统启动后大量服务异常、无法正常使用。
原因：disabled 状态文件无标签，直接 enforcing 导致全盘拒绝。
解法：touch /.autorelabel 后重启，系统自动重打全盘标签再进入 enforcing。

坑 5：SELinux 和 AppArmor 同时启用，行为异常且难排查
结论：两个 LSM 同时裁决，规则互相干扰，排错一头雾水。
原因：两者都是 LSM 实现，同时启用会叠加/冲突。
解法：只启用发行版默认的那个，另一个禁用，别混用。

坑 6：自定义目录挂载后忘记 restorecon，服务读不到文件
结论：迁移/新挂载的目录里文件标签是 default_t，服务被 SELinux 拦。
原因：新文件继承挂载点/默认标签，不符合服务要求的类型标签。
解法：semanage fcontext 定义路径标签 + restorecon -Rv 目录，并纳入部署流程。
```
