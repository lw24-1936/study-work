## 概述

入侵检测（Intrusion Detection）指「持续监测系统，发现未经授权的访问、篡改和攻击行为」，入侵响应（Incident Response）指「发现入侵后，按固定流程遏制、清除、恢复并复盘」。安全加固（23.1）是「防」，入侵检测是「发现防不住的那部分」，应急响应是「出事后把损失降到最小」。三大支柱：文件完整性校验（AIDE，发现文件被篡改）、漏洞扫描（发现可被利用的缺口）、应急响应流程（出事后的标准动作）。

```text
入侵检测与响应三大支柱：
文件完整性校验（AIDE）   基线快照对比，发现文件被篡改/被植入后门
漏洞扫描                 主动探测已知漏洞（CVE），补在被利用之前
应急响应流程             检测 → 遏制 → 根除 → 恢复 → 复盘，出事后止损
```

## 核心概念

### 入侵检测系统（IDS）分类

按数据来源分两大类：

- **HIDS（Host-based，基于主机）**：装在单台主机上，监控文件、日志、进程、系统调用。AIDE、OSSEC、rkhunter 属此类。优点是能看清单机细节，缺点是只覆盖单机、要逐台部署。
- **NIDS（Network-based，基于网络）**：旁路抓包分析网络流量，检测端口扫描、恶意载荷、异常流量。Snort、Suricata、Zeek 属此类。优点是全局视野、无侵入，缺点是看不到加密流量和主机内部行为。

按检测方式分：

- **误用检测（签名/Signature）**：和已知攻击特征库比对，命中即告警。准确率高，但对未知攻击（0day）无能为力。
- **异常检测（Anomaly）**：建立正常行为基线，偏离基线即告警。能发现未知攻击，但误报率高。

两个关键指标：**误报（False Positive）**——正常行为被判成攻击；**漏报（False Negative）**——攻击没被检出。IDS 调优本质是在两者之间找平衡。

```shell
# 以 Suricata（NIDS）为例：安装后配置网卡抓包
sudo apt install suricata
sudo suricata -c /etc/suricata/suricata.yaml -i eth0 &   # 监听 eth0
# 以 rkhunter（HIDS，查 rootkit）为例
sudo apt install rkhunter
sudo rkhunter --update        # 更新特征库
sudo rkhunter --check --sk    # 全面检查（--sk 跳过按键等待）
```

```text
IDS 分类：
HIDS 基于主机（文件/日志/进程/系统调用）→ AIDE / OSSEC / rkhunter
NIDS 基于网络（流量分析）           → Snort / Suricata / Zeek
误用检测 = 特征比对（准、但抓不到 0day）；异常检测 = 偏离基线（抓 0day、误报高）
```

### 文件完整性校验（AIDE）

AIDE（Advanced Intrusion Detection Environment）是最经典的 HIDS 工具，核心思路：在系统「干净」时对关键文件/目录生成一份基线快照（含权限、属主、大小、哈希、mtime 等属性），之后定期对比，任何属性变化都说明文件被动过——典型场景是攻击者替换了 `ls`、`ps`、`sshd` 等二进制（rootkit），或往 `/etc/passwd` 塞了账号。

工作流程：初始化生成基线库 → 日常 `--check` 对比 → 有合法变更时 `--update` 更新基线。基线库必须存在只读介质或离线保管，否则攻击者连 AIDE 数据库一起改，检测就失效。

```shell
# Debian/Ubuntu 安装与初始化
sudo apt install aide aide-common
sudo aideinit                   # 生成基线库 aide.db（初次建立快照）

# RHEL/CentOS 安装与初始化
sudo yum install aide
sudo aide --init                # 生成 /var/lib/aide/aide.db.new.gz
sudo mv /var/lib/aide/aide.db.new.gz /var/lib/aide/aide.db.gz

# 日常检查（对比当前状态与基线）
sudo aide --check               # 输出差异清单，退出码 0=一致 非0=有变化

# 合法变更后更新基线（如打了补丁、改了配置）
sudo aide --update              # 生成新基线 db.new，人工核对后替换 db
```

```text
AIDE 三件事：
aide --init    建立基线快照（系统干净时做，库要离线保管防被一起篡改）
aide --check   对比当前状态 vs 基线，任何属性变化都列出（检测篡改）
aide --update  合法变更后更新基线（先人工核对差异，确认不是入侵再更新）
```

### 漏洞扫描

漏洞扫描是「主动找缺口」：用工具探测系统/应用是否存在已知漏洞（CVE）、错误配置、弱口令，赶在攻击者利用之前修补。分类：

- **系统漏洞扫描**：Nessus、OpenVAS（Greenbone）扫描整个网络/主机，出漏洞报告。
- **本机配置审计**：Lynis 检查本机安全配置（权限、内核参数、服务加固），给出加固建议。
- **合规基线扫描**：OpenSCAP 按 SCAP 内容（CIS/STIG 等基准）评估合规性。
- **容器/依赖扫描**：Trivy、Grype 扫镜像和软件依赖的已知 CVE。

```shell
# 1. Lynis 本机安全审计（轻量、无 agent，适合快速自查）
sudo apt install lynis
sudo lynis audit system --quick        # 快速审计
sudo lynis show suggestions            # 只看向量建议（Warnings/Suggestions）

# 2. Nmap 脚本引擎做漏洞探测（对目标主机）
nmap -sV --script=vuln 192.168.1.10    # 版本探测 + 常见漏洞脚本
nmap -sV --script vulners 192.168.1.10 # 对接 vulners 漏洞库

# 3. Trivy 扫本机文件系统 / 容器镜像的已知 CVE
trivy fs /                             # 扫整机文件系统
trivy image nginx:1.25                 # 扫镜像

# 4. 系统已知安全补丁缺口（按发行版）
sudo apt list --upgradable             # Debian 系：可升级包
sudo yum update --security             # RHEL 系：只打安全更新
```

```text
漏洞扫描工具分层：
Nessus/OpenVAS  全网漏洞扫描（C/S，出报告，重）      → 周期性全网扫描
Lynis           本机配置审计（轻量、无 agent）       → 单机快速自查
OpenSCAP        合规基线评估（CIS/STIG 基准）        → 等保/CIS 测评
Trivy/Grype     容器镜像与依赖 CVE 扫描              → CI/CD 流水线
```

### 应急响应流程

应急响应（Incident Response）是入侵发生后的标准化处置，业界通用 6 阶段（SANS PICERL / NIST 模型）：

1. **准备（Preparation）**：提前建好响应团队、应急预案、取证工具包、备份。
2. **检测与识别（Identification）**：确认是否真的被入侵，识别入侵范围、攻击时间线。
3. **遏制（Containment）**：先止血——隔离主机（断网）、封账号、封 IP、保留现场证据，防止扩散。
4. **根除（Eradication）**：清除后门、恶意进程、恶意文件、被篡改的账号。
5. **恢复（Recovery）**：从干净备份恢复业务，逐步上线，持续监控确认无残留。
6. **复盘（Lessons Learned）**：写事件报告，找根因，补短板，更新预案。

核心原则：**先遏制再根除、先取证再清理**——一上来就 `rm` 删掉恶意文件会把证据也删了，无法追溯攻击路径。

```text
应急响应 6 阶段（PICERL）：
准备 → 检测与识别 → 遏制 → 根除 → 恢复 → 复盘
核心原则：
1. 先取证再清理 —— 保留内存/磁盘/日志证据，别急着 rm
2. 先遏制再根除 —— 先断网/封账号止血，再慢慢清后门
3. 全程留痕      —— 每一步操作记录时间与命令，保证可追溯
```

## 工作原理

### AIDE 的工作原理

AIDE 的核心是「属性基线对比」。初始化时，它按配置文件里定义的规则（监视哪些路径、记录哪些属性），对每个目标文件计算一组属性值（权限、inode、链接数、属主属组、大小、修改/访问/变更时间、哈希值等），序列化后写入基线数据库。之后每次 `--check`，它用同样规则重新计算当前文件属性，与基线逐条对比，凡不一致的（新增、删除、属性变化）都写进报告。

```text
AIDE 对比流程：
初始化：目标文件 → 按规则采集属性（权限/inode/大小/mtime/哈希）→ 写基线库 aide.db
检查：  目标文件 → 重新采集属性 → 与基线逐条 diff → 输出「新增/删除/变化」清单
关键：  基线库必须离线/只读保管，否则攻击者改文件的同时把基线也改了
```

### 应急响应的取证逻辑

检测到入侵后，第一优先级不是删东西，而是**固定证据**——因为内存里的进程信息、网络连接、登录会话断电即失。经典顺序：先保内存（`ps`/`ss`/`lsof` 快照、必要时内存 dump）→ 再保磁盘（关键日志、可疑文件、时间戳）→ 再看时间线（登录、文件修改、计划任务）。证据固定后才谈遏制与根除。

```text
取证优先级（易失性从高到低）：
内存/寄存器 → 网络连接/进程 → 磁盘 → 日志/备份介质
先快照易失数据，再处理持久数据；时间线靠文件 mtime + 日志时间戳 + 登录记录交叉印证
```

## 常用命令与配置

```shell
# ---- 文件完整性（AIDE）----
sudo aide --init        # 初始化基线
sudo aide --check       # 对比检查（退出码 0=一致）
sudo aide --update      # 合法变更后更新基线
sudo aide --compare     # 对比两个数据库

# ---- 本机安全审计（Lynis）----
sudo lynis audit system --quick       # 快速审计
sudo lynis audit system               # 完整审计
sudo lynis show suggestions           # 看建议清单
sudo lynis show details FILE-6310     # 看某条建议详情

# ---- 漏洞/基线扫描 ----
nmap -sV --script=vuln <目标>         # nmap 漏洞脚本
sudo oscap xccdf eval --profile <profile> --results r.xml <ssg-ds.xml>   # OpenSCAP
trivy fs /                            # Trivy 扫本机
trivy image <镜像>                    # Trivy 扫镜像

# ---- 应急响应排查（发现异常后）----
last -20                     # 最近登录记录
lastb -20                    # 失败登录（暴力破解痕迹）
who && w                     # 当前登录用户与活动
ss -tlnp                     # 当前监听端口
ss -antp                     # 所有已建立连接（找可疑外连）
ps auxf                      # 进程树（找可疑进程）
find / -mtime -1 -type f 2>/dev/null   # 最近 1 天被修改的文件
crontab -l && cat /etc/crontab        # 计划任务（攻击者常留后门）
cat /etc/passwd | awk -F: '$3==0{print}'   # 所有 UID=0 账号（找隐藏特权账号）
journalctl -u sshd -n 50    # sshd 最近日志
```

```text
应急排查五连：last（谁登录过）→ ss（连到哪）→ ps（跑着什么）→ find -mtime（改了什么）→ crontab（留了什么后门）
```

## 配置文件解析

### /etc/aide/aide.conf

AIDE 配置核心是「规则定义 + 监视路径选择」。规则是一组属性字母的缩写组合，选择行把某个路径和某组规则绑定。

```text
# 属性字母含义（常见子集）
p 权限   i inode  n 硬链接数  u 属主  g 属组  s 大小
m mtime  a atime  c ctime     S 检测大小增长
md5 / sha256   哈希算法
acl   扩展 ACL   xattrs 扩展属性   selinux SELinux 上下文
```

```text
# /etc/aide/aide.conf 关键片段（Debian/Ubuntu 实际布局）
database=file:/var/lib/aide/aide.db          # 当前基线库
database_out=file:/var/lib/aide/aide.db.new  # update 时输出的新库

# 规则组定义（预置组合，可直接复用）
Binlib = p+i+n+u+g+s+b+m+c+md5+sha1

# 选择行：路径 + 规则组
/etc        p+i+n+u+g+s+m+c+md5              # /etc 全量监控（不含子目录，需显式递归）
/etc/passwd p+i+n+u+g                       # 单文件只查权限/属主类属性
/bin        Binlib                          # /bin 用 Binlib 组
/boot       p+i+n+u+g+s+m+c+md5+sha1
!/var/log                                   # ! 前缀 = 排除该路径（日志常变，跳过）
```

```text
配置要点：
选择行「目录」默认不递归 —— 要监控子目录得逐条写或用「= 递归」写法（版本相关）
排除项用 ! 前缀（如 /var/log、/proc、/tmp，这些高频变化，纳入只会制造噪音）
规则越细（加 sha256）检测越强但越慢，/bin /usr/bin /sbin /usr/sbin 建议带哈希
```

## 应用场景实战

### 场景一：用 AIDE 检测 Web 目录被植入 webshell

攻击者拿到 Web 服务器权限后，常在网站目录塞 webshell（一句话木马）。用 AIDE 把网站目录纳入监控，篡改一发生就能定位到具体文件。

```shell
# 1. 部署后立刻对网站目录建立基线
sudo aideinit                       # 首次初始化（假设已配置监控 /var/www/html）

# 2. 业务正常运行一段时间后，定期检查（可放 cron 每天跑）
sudo aide --check
# 示例输出（发现异常）：
# File: /var/www/html/upload/shell.php
#   Size     : 0                            , 297
#   Sha256   : xxxxx                        , yyyyy
# 说明 /var/www/html/upload/shell.php 是新出现且带内容的文件，高度可疑

# 3. 立即核对该文件，确认为 webshell 后进入应急响应（先取证再清理）
stat /var/www/html/upload/shell.php     # 记录 mtime/属主，定位上传时间与途径
```

```text
AIDE 的价值：把「网站目录被塞文件」从「不知道」变成「第二天早上报告里列出来」
日常化：把 aide --check 挂进 cron，配合邮件告警，实现「篡改即发现」
```

### 场景二：发现主机被入侵后的完整应急响应

假设监控告警发现某台 Web 服务器 CPU 异常飙升、有异常外连，按 6 阶段走一遍：

```shell
# 阶段 1-2 检测与识别：确认入侵、固定证据
who; w                                  # 当前登录用户
last -20                                # 历史登录（看有没有陌生 IP）
ss -antp                                # 所有连接，找可疑外连（如连到矿池/陌生 IP）
ps auxf --sort=-%cpu | head -20         # CPU 最高的进程（挖矿木马常占满 CPU）
lsof -p <可疑PID>                       # 看可疑进程打开了哪些文件
ls -la /tmp /var/tmp                    # 看临时目录有无可疑脚本/二进制
crontab -l; cat /etc/crontab; ls /etc/cron.d/   # 计划任务有无后门

# 阶段 3 遏制：先止血，防扩散
# 3.1 保留证据（取证优先于清理）
cp -a /var/log/auth.log /var/log/syslog /root/forensics/   # 备份关键日志
# 3.2 断网隔离（防止横向移动/数据外传），生产环境用防火墙或拔网线
# 3.3 封掉攻击者账号/改密码
passwd -l <被利用账号>                  # 锁定可疑账号
# 3.4 杀掉恶意进程（先取证后 kill）
kill -STOP <可疑PID>                    # 先挂起（保留现场可继续取证）再 kill -9

# 阶段 4 根除：清后门
# 用 AIDE 对比 + 手工核查，删除 webshell/木马/恶意计划任务，修复被改的系统文件

# 阶段 5 恢复：从干净备份恢复业务，逐步放开访问
# 阶段 6 复盘：写事件报告（时间线、攻击路径、根因、整改项），更新预案
```

```text
应急响应铁律：
先取证（备份日志/内存快照/可疑文件）→ 再遏制（断网/锁账号/kill）→ 后根除（清后门）→ 恢复 → 复盘
「rm -rf 删了再说」会毁掉证据，导致无法追溯攻击路径、不知道还有什么残留
```

## 性能与调优

```text
1. AIDE 监控范围 —— 只监控关键路径（/etc /bin /usr/bin /sbin /usr/sbin /boot），
   排除高频变化目录（/var/log /tmp /proc /dev /run），减少噪音与检查耗时
2. AIDE 规则粒度 —— 对二进制目录用带哈希的规则（sha256），对纯配置目录可用
   p+i+n+u+g 轻量规则，平衡检测强度与扫描速度
3. AIDE 检查调度 —— 全量检查放凌晨低峰（cron），别在业务高峰抢 IO
4. Lynis 用 --quick —— 跳过耗时测试（如全盘找 SUID 文件），日常快查、定期全查
5. NIDS 性能 —— Suricata 用多线程 + 只抓内网流量，配合 BPF 过滤减抓包量，避免丢包漏检
6. 漏洞扫描调度 —— 全网 Nessus/OpenVAS 扫描放维护窗口，扫描会消耗目标资源、可能触发 IPS 告警
```

## 安全与权限

```text
1. AIDE 基线库保护 —— aide.db 必须放只读介质或离线保管，别留在可被攻击者写的位置，
   否则攻击者连文件带基线一起改，检测形同虚设
2. 扫描器凭证最小化 —— Nessus/OpenVAS 的登录扫描账号只用只读权限，别拿 root 做扫描凭证
3. 扫描结果保密 —— 漏洞报告含系统弱点和可利用细节，只存安全团队可访问的位置，别落公网
4. 应急取证权限 —— 取证操作要 root 权限，但保留现场时别用会改写文件的操作
5. IDS 防绕过 —— 攻击者可能先杀 HIDS 进程/改其配置，把 AIDE 数据库和配置也纳入监控
6. 隔离不彻底的风险 —— 遏制阶段断网要彻底（含内网横向流量），只封公网入口挡不住内网扩散
```

## 故障排查

### AIDE 每次检查都报大量「变化」，没法区分正常与异常

```shell
# 1. 看具体哪些文件在变
sudo aide --check | head -50
# 2. 判断变化来源：合法变更（日志轮转/补丁）还是异常（篡改）
#    - 日志类文件常变 → 应该用 ! 排除
#    - 系统二进制不该变 → 变了就是入侵或误报
# 3. 把高频合法变化的路径加进排除项，重做基线
sudo aide --update        # 核对 diff 确认无误后更新基线
```

### 应急排查中找不到可疑进程（进程被隐藏）

```shell
# 攻击者用 rootkit 隐藏进程/文件，常规 ps/ls 看不到
rkhunter --check --sk          # rootkit 扫描
chkrootkit                     # 另一款 rootkit 检测
# 对比内核视角与用户态视角（rootkit 常改 syscall 表导致两者不一致）
# 最稳妥：从干净 LiveCD 启动后挂载原磁盘做离线取证，绕过被篡改的系统
```

## 常见问题

```text
Q1: AIDE 和 Tripwire 什么关系？
A: 都是文件完整性校验工具，原理相同（基线快照对比）。Tripwire 商用为主，AIDE 是开源替代，功能覆盖大部分需求，是 Linux 上的默认选择。

Q2: AIDE 能实时检测篡改吗？
A: 不能。AIDE 是「定期批量对比」，要等下一次 --check 才报告。要实时检测需要配合 inotify（如 OSSEC/Samhain 的实时文件监控）或 auditd 审计规则。

Q3: 漏洞扫描会误报吗？怎么处理？
A: 会。尤其基于版本号的扫描（看到旧版本就报漏洞，但补丁可能已回移）。处理：确认漏洞前提条件是否满足、查发行版安全公告（CVE 是否已修）、必要时人工验证后再定级处置。

Q4: 应急响应第一步应该做什么？
A: 固定证据（取证优先于清理）：备份日志、快照进程与网络连接、保存可疑文件。别急着删东西或重启——重启会丢掉内存里的关键证据。

Q5: 主机已被入侵，直接重装系统最省事，为什么要取证复盘？
A: 重装能清掉这台机器，但不知道攻击怎么进来的、还动了哪些机器、数据有没有外泄。不复盘根因，同样手法会再次得手，损失重复发生。

Q6: HIDS 和 NIDS 该上哪个？
A: 不是二选一，而是互补：NIDS 看网络全局、抓扫描和横向移动；HIDS 看单机文件/进程、抓落地后的动作。生产环境建议 NIDS + 关键主机 HIDS 组合。
```

## 面试题

```text
1. IDS 的误报和漏报是什么？如何平衡？
   答：误报是正常行为被判成攻击，漏报是攻击没被检出。签名检测漏报少但抓不到未知攻击，异常检测能抓未知攻击但误报高。平衡靠调阈值、丰富基线、白名单过滤，并结合威胁情报。

2. AIDE 检测文件篡改的原理？基线库为什么必须离线？
   答：初始化时对目标文件采集属性（权限/属主/大小/mtime/哈希）生成基线，之后重新采集对比，不一致即报警。基线库必须离线/只读，否则攻击者改文件的同时把基线也改了，对比结果永远一致，检测失效。

3. 应急响应 6 阶段是什么？为什么「先取证再清理」？
   答：准备 → 检测识别 → 遏制 → 根除 → 恢复 → 复盘。先取证是因为内存、网络连接、进程等易失证据断电即失，且删掉恶意文件会破坏攻击路径的追溯线索。

4. 发现服务器 CPU 100%、有异常外连，你的排查思路？
   答：固定证据（who/last/ss/ps 快照、备份日志）→ 定位可疑进程（ps 按 CPU 排序、lsof 看它的文件与外连）→ 查持久化（crontab、启动项、新账号）→ 遏制（断网、kill、锁账号）→ 根除后门 → 恢复 → 复盘。

5. 漏洞扫描和渗透测试的区别？
   答：漏洞扫描是自动化、非破坏性地发现已知漏洞和错误配置，速度快、覆盖面广但浅；渗透测试是人工/半自动模拟真实攻击、验证漏洞可利用性，深但慢、成本高。两者互补：扫描做日常基线，渗透做深度验证。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 新机器上线第一件事跑 `aide --init` 建基线，别等出事了才想起没留快照
2. AIDE 基线库放只读/离线介质，检查结果发邮件告警并留档
3. `aide --check` 挂进 cron 每天跑一次，关键主机配 OSSEC/auditd 做实时补充
4. 漏洞扫描分两层：Lynis 本机自查（高频）+ Nessus/OpenVAS 全网扫描（周期），高危 CVE 建立修复 SLA
5. 提前写好应急预案和应急响应工具包（取证脚本、LiveCD、干净二进制），出事时别临时找工具
6. 应急响应严格按「先取证 → 遏制 → 根除 → 恢复 → 复盘」顺序，全程留痕
7. 复盘报告必须落到整改项并跟踪闭环，否则同类事件会重复发生

### 踩坑记录

```text
坑 1：出事后先 rm -rf 删可疑文件，把证据也删了
结论：后门清掉了，但攻击路径再也无法追溯，不知道还有什么残留。
原因：应急响应缺乏「取证优先于清理」意识，把清理当成第一动作。
解法：先备份日志、快照进程/网络、保存可疑文件，取证完成后再清理。

坑 2：AIDE 基线库留在本机可写目录，被攻击者一起篡改
结论：攻击者改文件的同时更新了基线，aide --check 永远显示一致，检测失效。
原因：基线库没做只读/离线保护，与监控目标同机同权限。
解法：基线库放只读介质或离线保管，本机只留一份副本并监控其本身。

坑 3：AIDE 监控了 /var/log /tmp，每天报几百条变化
结论：告警噪音太大，真正的篡改被淹没，团队逐渐忽略报告。
原因：把高频变化目录纳入监控，没有用 ! 排除。
解法：排除日志/临时/伪文件系统等高频变化路径，只监控关键系统路径。

坑 4：漏洞扫描直接对生产系统做登录扫描，触发告警甚至打挂服务
结论：扫描造成业务抖动，还触发 IPS/安全设备告警。
原因：扫描放业务高峰、用高并发、登录扫描凭证权限过大。
解法：扫描放维护窗口、控制并发、登录凭证用只读账号，先沟通再扫。

坑 5：遏制阶段只断公网，没断内网，攻击者横向移动继续扩散
结论：单台止血了，但攻击者已通过内网跳到其它机器。
原因：低估了横向移动，隔离范围只覆盖对外入口。
解法：遏制阶段内网/公网一并隔离，同时排查同网段其它主机有无异常。

坑 6：复盘只写报告不改流程，同类事件重复发生
结论：同样的入侵手法第二次得手，损失翻倍。
原因：复盘结论停留在文档，没有落到整改项、没跟踪闭环。
解法：复盘产出「整改任务 + 责任人 + 期限」，跟踪到关闭，更新预案与监控规则。
```
