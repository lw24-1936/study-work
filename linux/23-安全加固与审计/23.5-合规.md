## 概述

合规（Compliance）指「系统的安全配置和管理，满足法规、标准或行业基线的要求」。区别于入侵检测（找攻击）和加固（堵漏洞），合规回答的是「我的系统有没有达到某套标准规定的最低安全水位」。国内最主流的是**等保（等级保护 MLPS 2.0）**，国际通用的是 **CIS 基线（CIS Benchmarks/Controls）**。合规落地靠两件事：一套明确的安全基线标准 + 一套自动化检查工具（Lynis / OpenSCAP / CIS-CAT / 自研脚本）。

```text
合规三要素：
标准     等保 2.0（GB/T 22239）国内强制；CIS Benchmarks 国际通用基线
基线     把标准翻译成一条条可检查的配置项（口令策略/SSH/审计/权限/日志）
检查工具  Lynis / OpenSCAP / CIS-CAT / 自研脚本，自动化评估偏差、出整改清单
```

## 核心概念

### 等保（等级保护 MLPS 2.0）

等级保护（Multi-Level Protection Scheme，MLPS）是我国网络安全领域的基础制度，核心标准是 GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》（即等保 2.0）。它按系统受侵害时对「国家安全/社会秩序/公共利益/公民法人权益」的损害程度，把保护对象分为 **5 个安全保护等级**：

```text
等保 5 级：
一级   自主保护     一般系统，损害轻微
二级   指导保护     一般重要系统，损害一般（常见于内部系统）
三级   监督保护     重要系统，损害严重（企业生产/政务/金融常见，强制测评）
四级   强制保护     特别重要系统，损害特别严重（国家级）
五级   专控保护     极端重要系统（最高，涉密场景）
```

等保建设全流程 5 步：**定级 → 备案 → 建设整改 → 等级测评 → 监督检查**。三级及以上系统必须定期（一般每年）由测评机构开展等级测评，不合格要整改。技术层面，等保 2.0 把安全要求拆成多个层面：物理安全、通信网络安全、区域边界安全、计算环境安全（主机/应用/数据）、管理中心、安全管理制度。

```text
等保 2.0 安全层面（技术部分）：
物理安全          机房/设备物理防护
通信网络安全      网络架构、传输加密、入侵防范
区域边界安全      边界防火墙/访问控制/恶意代码防范
计算环境安全      主机加固、身份鉴别、访问控制、安全审计、入侵防范、数据完整性
管理中心          集中管控、审计管理、安全策略管理
```

### CIS 基线（CIS Benchmarks 与 CIS Controls）

CIS（Center for Internet Security，互联网安全中心）是全球通用的安全基线权威来源，两套核心产物：

- **CIS Benchmarks（配置基线）**：针对每种操作系统/软件（Linux 发行版、Nginx、MySQL、Docker、K8s 等）给出逐条可验证的加固配置项，每条含「描述 / 影响 / 审计方法 / 修复方法」。每条项有 **Profile 分级**：Level 1（最小影响、普遍适用、不影响业务功能）和 Level 2（纵深防御、适合高安全要求、可能影响功能）。
- **CIS Controls（安全控制措施，v8 共 18 条）**：从组织层面给 18 类关键控制（资产清点、漏洞管理、账户管理、日志审计等），按实施组（IG1/IG2/IG3）分优先级，偏管理流程。

等保是「法规强制、需测评定级」，CIS 是「业界最佳实践、自愿采用、逐条可自动化检查」——企业常见做法是把 CIS 基线作为等保测评的落地抓手。

```text
CIS 与等保对比：
CIS Benchmarks  自愿、逐条可脚本检查、Level1/Level2 分级、跨厂商通用
等保 MLPS       法规强制、按级测评、国内合规必备、定级备案测评流程
二者关系：CIS 是「怎么查怎么改」的操作手册，等保是「必须达到什么」的制度要求
```

### 安全基线检查工具

把标准变成可执行检查的工具分四类：

- **Lynis**：轻量、无 agent 的本机安全审计，检查 300+ 项配置，输出「硬化指数（Hardening Index）」和逐条建议，适合单机快速自查。
- **OpenSCAP + SCAP Security Guide（SSG）**：按 SCAP 标准（XCCDF/OVAL）做合规评估，内置 CIS、STIG、PCI-DSS、等保（部分发行版）等多套 Profile，支持自动修复（--remediate），是自动化合规的核心。
- **CIS-CAT Pro**：CIS 官方评估工具，逐条对照 CIS Benchmarks 打分，报告权威，但完整版需订阅。
- **自研脚本**：把高频检查项（口令策略、SSH、空口令、SUID、审计）写成 shell 脚本，灵活、贴合企业自身基线，但需自己维护。

```shell
# 1. Lynis 本机审计（快速出硬化指数）
sudo lynis audit system --quick
sudo lynis show suggestions           # 列出建议整改项
sudo lynis show details AUTH-9229     # 查看某条建议的修复方法

# 2. OpenSCAP 合规评估（先看有哪些 Profile）
oscap info /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml
# 按 CIS Profile 评估并出报告
sudo oscap xccdf eval \
  --profile xccdf_org.ssgproject.content_profile_cis \
  --results /tmp/cis-results.xml \
  --report /tmp/cis-report.html \
  /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml

# 3. OpenSCAP 自动修复（慎用，先评估后修复）
sudo oscap xccdf eval --remediate \
  --profile xccdf_org.ssgproject.content_profile_cis \
  /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml

# 4. 自研脚本式抽查（口令与 SSH 基线）
grep -E '^(minlen|minclass|dcredit|ucredit|lcredit|ocredit)' /etc/security/pwquality.conf
grep -E '^(PermitRootLogin|PasswordAuthentication|PermitEmptyPasswords)' /etc/ssh/sshd_config
awk -F: '($2==""){print $1" 空口令!"}' /etc/shadow
```

```text
检查工具选型：
Lynis        单机快速自查、日常体检（轻量、无 agent）
OpenSCAP     自动化合规评估 + 批量修复（CIS/STIG/PCI 多 Profile，企业主力）
CIS-CAT Pro  官方权威打分（等保/CIS 测评报告，需订阅）
自研脚本     贴合企业自定义基线、嵌入巡检流水线（灵活、需维护）
```

## 工作原理

### 合规评估的工作流程

合规不是「装个扫描器跑一下」就完事，而是一个「基线定义 → 自动评估 → 偏差修复 → 复评闭环」的循环：

1. **基线定义**：选定标准（等保某级 / CIS Level 1），把要求翻译成机器可检查的规则（配置项 + 期望值），规则来源是 SSG 的 XCCDF 内容或自研脚本。
2. **自动评估**：工具逐条检查实际配置 vs 期望值，产出「通过 / 失败 / 未评估」清单和报告（HTML/XML）。
3. **偏差修复**：对失败项人工整改，或工具自动修复（--remediate / 配置下发）。
4. **复评闭环**：整改后重新评估，直到达标；把评估纳入周期巡检（CI/CD 或 cron）。

```text
合规闭环：
选标准（等保 X 级 / CIS L1）→ 定基线（可检查的配置规则）
→ 评估（Lynis/OpenSCAP 跑分）→ 修复（整改或自动修复）→ 复评达标
关键：基线必须「可自动检查」，含糊的「应加强口令管理」无法落地，必须是
     「口令最小长度 >= 12、复杂度包含大小写数字特殊字符」
```

### SCAP 协议栈（OpenSCAP 底层）

OpenSCAP 背后是 SCAP（Security Content Automation Protocol）协议族，把安全内容标准化：

```text
SCAP 组件：
XCCDF   检查清单语言（定义「检查什么、期望什么」+ Profile 分组）
OVAL    漏洞/配置检查语言（定义每条检查的具体技术判定逻辑）
CVE/CVSS 漏洞编号与评分
CPE     平台命名（描述目标系统/软件）
SSG（scap-security-guide） 把这些组织成各发行版可用的数据流文件（*-ds.xml）
```

评估时 `oscap xccdf eval` 读入 `-ds.xml` 数据流，按 `--profile` 选取一组 XCCDF 规则，每条规则内部调用 OVAL 脚本判定，最后汇总成报告。

## 常用命令与配置

```shell
# ---- Lynis ----
sudo lynis audit system --quick        # 快速审计（跳过耗时项）
sudo lynis audit system                # 完整审计
sudo lynis show suggestions            # 整改建议清单
sudo lynis show details <TEST-ID>      # 单条建议的修复方法
sudo lynis show hardening-index        # 硬化指数（百分比）

# ---- OpenSCAP ----
oscap info <ssg-ds.xml>                # 列出所有可用 Profile
oscap xccdf eval --profile <p> --results r.xml --report r.html <ssg-ds.xml>   # 评估
oscap xccdf eval --remediate --profile <p> <ssg-ds.xml>                        # 自动修复
oscap oval eval --results oval-r.xml <oval.xml>   # OVAL 漏洞检查
oscap xccdf generate report r.xml > report.html    # 从结果 XML 重新生成报告

# ---- 自研脚本式抽查（高频基线项）----
# 口令有效期与最小长度
grep -E '^(PASS_MAX_DAYS|PASS_MIN_DAYS|PASS_MIN_LEN)' /etc/login.defs
# 密码复杂度
cat /etc/security/pwquality.conf | grep -v '^#'
# SSH 安全项
sshd -T | grep -E 'permitrootlogin|passwordauthentication|permitemptypasswords|x11forwarding'
# 空口令账号
awk -F: '($2==""){print "空口令: "$1}' /etc/shadow
# 是否开启审计
systemctl is-enabled auditd
# umask 与权限
grep -E '^\s*umask' /etc/profile /etc/bashrc 2>/dev/null
```

```text
高频基线检查点：
口令策略（长度/复杂度/有效期） · SSH（禁 root 远程/禁空口令）· 空口令账号
审计开启（auditd）· 关键文件权限（/etc/shadow 600）· 最小服务（关无用服务）
```

## 配置文件解析

### /etc/security/pwquality.conf（口令复杂度）

口令复杂度是等保和 CIS 都必查的一项，对应 PAM 的 `pam_pwquality` 模块。

```text
# /etc/security/pwquality.conf 关键项
minlen = 12          # 口令最小长度（CIS L1 建议 14）
minclass = 4         # 至少包含的字符类别数（大写/小写/数字/特殊，4=全要）
dcredit = -1         # 数字字符数要求（负数 = 至少 1 个）
ucredit = -1         # 大写字母（至少 1 个）
lcredit = -1         # 小写字母（至少 1 个）
ocredit = -1         # 特殊字符（至少 1 个）
maxrepeat = 3        # 同一字符最多连续重复次数
difok = 8            # 新旧口令至少不同的字符数
enforce_for_root     # 对 root 同样生效
```

```text
生效前提：/etc/pam.d/common-password（Debian）或 system-auth/password-auth（RHEL）
含 password requisite pam_pwquality.so ... 一行，模块才会读取此文件
```

### /etc/ssh/sshd_config（SSH 基线）

```text
PermitRootLogin no            # 禁止 root 直接 SSH 登录（改用 sudo）
PasswordAuthentication no     # 禁用口令登录（只留密钥，CIS L2 建议）
PermitEmptyPasswords no       # 禁止空口令
MaxAuthTries 4                # 限制尝试次数（防暴力破解）
ClientAliveInterval 300       # 空闲超时（秒）
ClientAliveCountMax 0         # 超时即断开（防挂机会话）
Protocol 2                    # 只允许 SSHv2
X11Forwarding no              # 关闭 X11 转发（不需要时）
AllowUsers alice bob          # 白名单（仅允许列出的用户）
```

```text
sshd_config 改完要 systemctl reload sshd（或 restart）才生效
用 sshd -T 查看「生效后的实际值」（合并了 include 的其它配置，比直接 grep 文件准）
```

## 应用场景实战

### 场景一：用 OpenSCAP 对一台 RHEL 主机做 CIS 基线评估并整改

从零到达标走完整流程，覆盖「评估 → 看报告 → 修复 → 复评」：

```shell
# 1. 安装 OpenSCAP 与安全内容
sudo dnf install -y openscap-scanner scap-security-guide

# 2. 看有哪些 Profile 可用（找 cis 相关）
oscap info /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml | grep -i cis

# 3. 按 CIS Profile 评估，出 XML 结果 + HTML 报告
sudo oscap xccdf eval \
  --profile xccdf_org.ssgproject.content_profile_cis \
  --results /tmp/cis-results.xml \
  --report /tmp/cis-report.html \
  /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml
# 报告里每项标注 pass / fail / notchecked，fail 项给出修复建议

# 4. 查看失败项数量（从结果 XML 统计）
grep -c 'result="fail"' /tmp/cis-results.xml

# 5. 自动修复（对可修复项，先确认再执行）
sudo oscap xccdf eval --remediate \
  --profile xccdf_org.ssgproject.content_profile_cis \
  /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml

# 6. 复评确认达标
sudo oscap xccdf eval \
  --profile xccdf_org.ssgproject.content_profile_cis \
  --report /tmp/cis-report-after.html \
  /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml
```

```text
流程：装工具 → 看 Profile → 评估出报告 → 分析 fail 项 → 修复 → 复评
注意：--remediate 会直接改系统配置（可能影响业务），生产环境先在测试机验证，
     对「不能自动修」的项按报告建议手工整改
```

### 场景二：自研巡检脚本批量检查多台服务器的口令与 SSH 基线

等保测评和日常巡检经常要一次检查一批机器，写个脚本批量跑，输出统一的偏差清单：

```shell
#!/bin/bash
# baseline-check.sh —— 批量检查口令/SSH/账号/审计四项基线
HOSTS="10.0.0.11 10.0.0.12 10.0.0.13"
for h in $HOSTS; do
  echo "===== $h ====="
  ssh root@$h '
    echo "[口令策略]"; grep -v "^#" /etc/security/pwquality.conf | grep -v "^$" | head -6
    echo "[空口令账号]"; awk -F: '\''($2==""){print $1}'\'' /etc/shadow
    echo "[SSH]"; sshd -T | grep -iE "permitrootlogin|passwordauthentication|permitemptypasswords"
    echo "[审计]"; systemctl is-enabled auditd 2>/dev/null
    echo "[隐藏特权账号]"; awk -F: '\''($3==0){print $1}'\'' /etc/passwd
  '
done
```

```shell
# 运行并保存结果
bash baseline-check.sh > baseline-report.txt 2>&1
# 用 grep 汇总所有不合格项
grep -E '空口令|yes|root' baseline-report.txt
```

```text
自研脚本的价值：贴合企业自己的基线清单、一次覆盖所有机器、结果可存档供测评
局限：检查项要靠自己维护，覆盖面不如 OpenSCAP/CIS-CAT 全，适合做补充而非替代
```

## 性能与调优

```text
1. Lynis 用 --quick —— 跳过全盘 SUID/大目录扫描等耗时测试，日常快查、定期全查
2. OpenSCAP 评估放低峰 —— 全 Profile 评估要逐条执行 OVAL 脚本、读大量文件，有 IO 开销
3. 分 Profile 评估 —— 只跑目标 Profile（如 cis），别一次性加载全量规则，评估更快
4. 修复分批做 —— --remediate 一次改几百项容易改出问题，分模块（口令/SSH/审计）逐批修
5. 结果缓存与增量 —— 巡检脚本只对「变了」的项重查，避免每次全量拉配置
6. 评估频率分级 —— 关键系统每周、一般系统每月，扫描本身也占资源，别高频全量扫
```

## 安全与权限

```text
1. 修复脚本权限 —— 自研基线脚本含 ssh root 免密登录配置，密钥要妥善保管，脚本文件 chmod 700
2. 评估结果保密 —— 合规报告暴露系统全部弱点和偏差，等同攻击者「加固清单」，只存安全团队位置
3. 自动修复谨慎 —— --remediate 直接改生产配置，可能锁死 SSH/账户，先在测试机验证并留回滚
4. 扫描账号最小权限 —— 批量巡检用只读账号（sudo 读权限），别全机器 root 免密
5. 免密登录用密钥 + 白名单 —— 巡检 ssh 只允许跳板机来源 IP，禁口令登录
6. 修复本身引入风险 —— 强制改口令策略/禁 root 登录可能把人锁在门外，改前留后门窗口和回滚方案
```

## 故障排查

### OpenSCAP 评估报「Profile 不存在」

```shell
# 1. 列出实际可用的 Profile 名字（发行版/版本不同 Profile 名不同）
oscap info /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml | grep -i profile
# 2. 用完整 Profile ID（不要只写 cis，要写 xccdf_org.ssgproject.content_profile_cis）
# 3. Ubuntu 用 ssg-ubuntu2204-ds.xml，Profile 是 cis_level1_server / standard 等
oscap info /usr/share/xml/scap/ssg/content/ssg-ubuntu2204-ds.xml
```

### Lynis 报告某些项「未检查 / 无法确定」

```shell
# 未检查常因缺少对应组件（如没装 auditd、没配 cron）
# 1. 看具体原因
sudo lynis show details <TEST-ID>
# 2. 装回缺失组件后重跑
sudo apt install auditd
sudo lynis audit system --quick
```

## 常见问题

```text
Q1: 等保和 CIS 是什么关系，都要做吗？
A: 等保是国内法规强制（尤其三级以上系统必须测评备案），CIS 是国际自愿的最佳实践基线。国内企业以等保为准，但常借 CIS 的逐条可检查项做落地抓手，两者互补不冲突。

Q2: 等保二级和三级区别？
A: 主要是「重要程度 + 强制力度」：三级系统损害后果严重，必须每年由测评机构开展等级测评、测评结果报监管；二级系统要求相对宽松。企业生产/政务/金融系统普遍按三级定级。

Q3: Lynis 硬化指数多少算合格？
A: 没有绝对及格线，Hardening Index 是「已通过项 / 可检查项」的百分比，参考值 70 以上算良好。更该看的是 suggestions 清单里有没有高危项（如空口令、root 远程登录、无审计），高危项应清零。

Q4: OpenSCAP 自动修复安全吗，能直接在生产跑吗？
A: 不安全直接跑。--remediate 会批量改配置（可能锁账户、断 SSH、影响服务）。正确做法：先在测试/镜像环境验证，确认无副作用后，再在生产分模块逐步修复并保留回滚手段。

Q5: 合规检查一年做一次够吗？
A: 不够。等保测评是年度强制，但配置会随日常变更漂移（新服务、新账号、改配置）。建议把基线检查做成周期巡检（关键系统每周/每月），并纳入新机器上线流程，实现持续合规。
```

## 面试题

```text
1. 等保 2.0 的 5 个等级和定级流程？
   答：一级自主保护、二级指导保护、三级监督保护、四级强制保护、五级专控保护，损害后果逐级加重。流程：定级 → 备案 → 建设整改 → 等级测评 → 监督检查，三级以上每年测评。

2. CIS Benchmarks 的 Level 1 和 Level 2 区别？
   答：Level 1 是最小影响、普遍适用、不影响业务功能的基础配置；Level 2 是纵深防御、适合高安全要求环境，但可能影响功能或需特殊环境。实际按系统重要性选 Profile。

3. 怎么把「合规要求」落地成可自动检查？
   答：把每条要求翻译成可验证的配置规则（配置项 + 期望值），用 OpenSCAP（XCCDF/OVAL 规则）或自研脚本逐条评估，产出 pass/fail 清单，fail 项整改后复评，形成闭环。

4. OpenSCAP 和 Lynis 的区别？
   答：OpenSCAP 基于 SCAP 标准（XCCDF/OVAL），按 CIS/STIG/PCI-DSS 等官方 Profile 做严格合规评估，支持自动修复和标准报告，适合正式合规测评；Lynis 是轻量本机审计，检查项自研、出硬化指数和建议，适合日常快速自查。

5. 为什么合规检查不能「一次通过就完事」？
   答：系统配置持续变化（新装服务、新开账号、日常变更），一次达标不代表一直达标，存在「配置漂移」。需要把合规检查做成周期性巡检 + 上线门禁，实现持续合规。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先定级再选基线：明确等保等级/CIS Profile，别拿「最强配置」一刀切，过度加固会影响业务
2. 基线可自动检查：每条要求落到「配置项 + 期望值」，能用脚本/OpenSCAP 验证，拒绝含糊表述
3. 评估与修复分离：先评估出报告、人工审 fail 项，再分批修复，别上来就 --remediate 全量改
4. 合规进流水线：新机器上线模板即合规、周期巡检（cron/CI）持续评估，防配置漂移
5. 高危项清零：空口令、root 远程登录、无审计、弱口令策略这类高危偏差优先修，别只看总分
6. 报告留档备查：每次评估的 XML/HTML 报告存档，等保测评和审计要能出示历史记录
7. 修复留回滚：改口令策略/禁 root 登录前，保留一个可回滚的窗口或手段，防止把自己锁在门外

### 踩坑记录

```text
坑 1：直接在生产跑 oscap --remediate，把 SSH 登录改挂了
结论：修复后 SSH 连不上，人进不去系统，故障比原来还严重。
原因：自动修复批量改 sshd/账户配置（禁 root、禁口令），没在测试环境验证副作用。
解法：先在测试机/镜像验证，确认无副作用再分模块修，修复前留回滚手段。

坑 2：基线只做一次，后续变更导致「配置漂移」回归不达标
结论：测评时才发现一堆新偏差，被动整改。
原因：合规检查做成一次性动作，没有周期巡检和上线门禁。
解法：把评估纳入 cron/CI 周期跑，新机器模板即合规，变更触发复评。

坑 3：把 Lynis 硬化指数当唯一指标，忽略高危项
结论：总分挺高，但空口令账号/root 远程登录等致命项一直没修。
原因：只看百分比分数，没逐条看 suggestions 里的高危项。
解法：高危项（空口令、无审计、root 远程登录）单独清零，分数只做参考。

坑 4：自研巡检脚本用 root 口令免密登录，密钥泄露等于全盘沦陷
结论：巡检脚本的 root 密钥被窃，攻击者直连所有服务器。
原因：批量巡检图省事用 root + 口令/弱密钥，权限过大、保护不足。
解法：巡检用只读账号、密钥登录 + 来源 IP 白名单、脚本与密钥 chmod 700。

坑 5：照搬 CIS Level 2 到生产，业务功能被改挂
结论：禁口令登录、强口令策略等改动导致业务无法登录、接口认证失败。
原因：Level 2 是纵深防御 Profile，部分项会破坏现有业务假设，未评估影响就全上。
解法：按系统重要性选 Level 1 起步，逐项评估对业务影响，高危项优先、影响项缓改。

坑 6：合规报告公网可读，等于把弱点清单送给攻击者
结论：报告暴露全部失败项和系统信息，被攻击者利用。
原因：报告存到了公网可访问的目录/对象存储，未做访问控制。
解法：报告只存安全团队可访问位置，加密存储，分享走内部权限通道。
```
