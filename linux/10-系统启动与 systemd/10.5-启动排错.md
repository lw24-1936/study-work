## 概述

系统起不来（或启动卡住）时的排错三板斧：单用户模式（rescue，改密码/修配置）、grub 修复（重装引导加载器）、急救模式（emergency，最坏情况）。核心思路：先判断「卡在哪一步」——是 GRUB 引导问题、内核问题、还是服务启动问题，再对症下药。`systemctl --failed` 看失败的服务、`systemd-analyze` 看启动耗时、journalctl -b 看本次启动日志。

排错的黄金法则是「先定位阶段，再选工具」：不同阶段对应不同环境和不同命令，进错环境只会浪费时间。

```text
启动排错三板斧：
1. 单用户模式 rescue —— 挂文件系统 + root shell，改密码、修配置
2. grub 修复 —— grub-install 重装引导、update-grub 重新生成配置
3. 急救模式 emergency —— 最精简环境，兜底修复
```

```text
# 实测（本机当前无启动失败的服务）
$ systemctl --failed
0 loaded units listed.
```

```text
排错四问（先自问，再动手）：
1. 卡在哪一步？GRUB 界面 / 内核加载 / 登录前
2. 最近改了什么？fstab / 内核 / 驱动 / 分区 / 装了双系统
3. 日志说了什么？journalctl -b -1 / dmesg / 屏幕最后输出
4. 有没有回退手段？旧内核 / 备份配置 / Live 盘
```

## 核心概念

1. **单用户模式（rescue.target）**：挂载文件系统 + 启动基础服务 + 给 root shell，用于改密码、修配置。
2. **grub 修复**：GRUB 引导加载器损坏时重装（grub-install）或重新生成配置（update-grub）。
3. **急救模式（emergency.target）**：最精简环境，几乎只挂根分区给单 shell，最坏情况兜底。
4. **chroot 修复**：从 Live USB 启动，挂载损坏系统的根分区，chroot 进去修——引导完全损坏时的标准手段。
5. **启动日志**：journalctl -b（本次）/-b -1（上次），定位启动失败原因。

```text
排障定位：先判断卡在哪一步
GRUB 界面/grub rescue>  → 引导问题
内核加载中（黑屏/panic）→ 内核或 initramfs 问题
登录前（服务起不来）   → 服务/fstab 问题
```

### 单用户模式（rescue.target）

是什么：只挂本地文件系统 + 起基础服务，给一个 root shell 的排障环境，对应老 runlevel 1。

为什么：系统改坏配置、忘密码后，正常登录进不去，需要「绕过正常启动、直接拿 shell 改东西」。

怎么用：开机 GRUB 内核命令行加 `systemd.unit=rescue.target` 或 `single`，Ctrl+X 启动；根分区只读先 `mount -o remount,rw /`。

边界/易错点：根分区默认只读；网络默认不起；需要 root 密码（sulogin）才能进 shell。

### grub 修复

是什么：GRUB 引导加载器或它的配置文件（grub.cfg）损坏后的修复，分「重装引导代码」（grub-install）和「重新生成配置」（update-grub）两件事。

为什么：引导代码在 MBR/ESP 上、配置文件在 /boot 上，都可能被误操作或装系统覆盖，坏了就进不了系统。

怎么用：grub.cfg 损坏 → update-grub；引导程序损坏 → grub-install /dev/sda（UEFI 还要 --target=x86_64-efi --efi-directory=/boot/efi）。

边界/易错点：grub.cfg 损坏通常还能进救援模式，引导程序损坏连菜单都没有（grub rescue>）；UEFI 和 BIOS 的安装命令不同，别搞混。

### 急救模式（emergency.target）

是什么：几乎只挂根分区（只读）给一个 shell 的最小环境，连基础服务都不起。

为什么：rescue 都进不去（基础 target/sysinit 坏了、fstab 损坏）时，需要一个最小到极致的兜底。

怎么用：开机内核命令行加 `systemd.unit=emergency.target`；改东西先 `mount -o remount,rw /`。

边界/易错点：环境极简，很多命令/设备不可用；只适合「把改坏的配置改回去」。

### chroot 修复

是什么：从 Live USB/安装盘启动，手动挂载损坏系统的根分区和虚拟文件系统，chroot 切进去执行修复命令。

为什么：引导完全损坏、连救援模式都进不去时，Live 系统是「独立于本机引导」的最后手段。

怎么用：mount 根分区到 /mnt → mount --bind dev/proc/sys → chroot /mnt → grub-install / update-grub / 改密码。

边界/易错点：chroot 进去等于拿到该系统的 root 权限，Live 环境要可信；忘记挂 /proc /sys 会导致命令报错。

### initramfs 修复

是什么：initramfs 是内核启动时用的临时根文件系统镜像（/boot/initrd.img-*），带磁盘驱动和挂根分区的逻辑，坏了根分区就挂不上。

为什么：改过 LVM/RAID/加密/磁盘驱动后，initramfs 里的旧配置和新磁盘布局对不上，需要重建。

怎么用：update-initramfs -u（Debian/Ubuntu）或 dracut -f（RHEL）重建当前内核的 initramfs。

边界/易错点：只重建当前内核；装了多个内核时要针对对应版本重建，重建后确认 GRUB 选的是哪个内核。

## 工作原理

启动排错的原理是「逐层进入更底层环境」：正常系统进不去，就进 rescue（较完整）、再不行进 emergency（最精简）、再不行从 Live 系统 chroot（完全脱离本机引导）。

1. **rescue/emergency 的进入**：内核命令行加 systemd.unit=rescue.target 或 emergency.target，systemd 不拉起完整服务，直接给 root shell。
2. **grub 修复**：grub-install 把引导代码写回 MBR/GPT，update-grub 重新扫描内核生成 grub.cfg。
3. **chroot**：挂载根分区 + 虚拟文件系统（proc/sys/dev）→ chroot 切换根 → 在损坏系统里执行修复命令。

```text
排障环境层级（从上到下越底层）：
正常系统 → rescue（挂文件系统 + 基础服务）→ emergency（只挂根分区）→ Live + chroot
```

```text
「先定位阶段」怎么落地（看屏幕最后输出）：
1. 看到 grub> / grub rescue> 提示符 → 引导程序/配置问题 → grub 修复
2. 看到内核 panic / 卡在「Loading initial ramdisk」→ 内核或 initramfs → update-initramfs / 换内核
3. 看到 emergency mode 提示 / 卡在服务启动 → fstab 或服务 → 进 rescue 改配置
```

```text
systemd 启动失败为什么会掉进 emergency/rescue：
1. fstab 里某个非 nofail 的挂载失败 → 直接进 emergency mode 让你修
2. 关键服务（local-fs、sysinit）起不来 → 依赖它的 target 到不了 → 掉 rescue
3. 根文件系统损坏 / 参数错 → 挂不上根 → 最坏掉 initramfs shell 或 emergency
```

## 常用命令与配置

```shell
systemctl --failed             # 看失败的服务
systemd-analyze                # 看启动耗时
journalctl -b                  # 本次启动日志
journalctl -b -1               # 上次启动日志（排查启动失败关键）
journalctl -xb                 # 启动日志 + 详细说明

# grub 修复
update-grub                    # 重新生成 grub.cfg
grub-install /dev/sda          # 重装 GRUB 到磁盘（BIOS）
# UEFI 重装（注意 --target 和 --efi-directory）
grub-install --target=x86_64-efi --efi-directory=/boot/efi

# initramfs / 内核修复
update-initramfs -u            # 重建当前内核 initramfs（Debian/Ubuntu）
dracut -f                      # 重建 initramfs（RHEL/CentOS）

# 进入救援/紧急模式（GRUB 内核命令行）
# systemd.unit=rescue.target
# systemd.unit=emergency.target
```

## 配置文件解析

```text
启动排错涉及的配置：
/etc/fstab               开机挂载表（错一行就卡 emergency）
/boot/grub/grub.cfg      引导配置（update-grub 生成）
/etc/default/grub        GRUB 配置源
/etc/systemd/system/default.target  默认 target 链接
/boot/vmlinuz-*          内核镜像
/boot/initrd.img-*       initramfs 镜像
```

```text
GRUB 内核命令行排障参数：
systemd.unit=rescue.target     进救援模式
systemd.unit=emergency.target  进紧急模式
single                         老式单用户（等价 rescue）
init=/bin/bash                 绕过 systemd 直接给 bash
rd.break                       在 initramfs 阶段中断，进 shell
nomodeset                      禁用内核显卡驱动（黑屏时用）
root=/dev/sda2                 手动指定根分区
```

```text
fstab 排错关键字段：
<设备>  <挂载点>  <类型>  <选项>  <dump>  <pass>
选项里加 nofail —— 挂载失败也不阻断启动（非关键分区必加）
选项里加 noauto —— 开机不自动挂（按需挂的盘）
根分区 pass=1、其他 pass=2 —— fsck 检查顺序，写错可能导致 fsck 卡住
```

## 应用场景实战

### 场景一：忘了 root 密码，单用户模式重置

```shell
# 1. 开机 GRUB 菜单按 e，linux 行末尾加 systemd.unit=rescue.target
# 2. Ctrl+X 启动，进入单用户模式
# 3. 根分区改读写 + 重置密码
mount -o remount,rw /
passwd root
# 4. 重启
reboot
```

### 场景二：改坏 fstab 导致启动卡住

```shell
# 1. 启动卡在 emergency mode，按提示输入 root 密码进入
# 2. 根分区改读写
mount -o remount,rw /
# 3. 检查并修复 fstab
cat /etc/fstab
vi /etc/fstab        # 注释掉错误的挂载行
# 4. 重启验证
reboot
```

### 场景三：双系统装 Windows 后 GRUB 被覆盖，用 Live 盘 chroot 修复

```shell
# 1. 用 Live USB 启动，进终端
# 2. 找到 Linux 根分区（假设 /dev/sda2 是根，/dev/sda1 是 ESP）
lsblk
# 3. 挂载根分区
mount /dev/sda2 /mnt
# 4. 挂载虚拟文件系统（chroot 前必须）
mount --bind /dev /mnt/dev
mount --bind /proc /mnt/proc
mount --bind /sys /mnt/sys
# 5. UEFI 还要挂 ESP
mount /dev/sda1 /mnt/boot/efi
# 6. chroot 进去
chroot /mnt
# 7. 重装引导 + 重新生成配置
grub-install --target=x86_64-efi --efi-directory=/boot/efi
update-grub
# 8. 退出并卸载
exit
umount -R /mnt
reboot
```

```text
场景三要点：
1. chroot 前 mount --bind /dev /proc /sys 是硬性步骤，漏了 grub-install 会报错
2. UEFI 必须挂 ESP 再 grub-install，否则引导代码没地方写
3. BIOS 机器省略挂 ESP，grub-install /dev/sda 直接写 MBR
```

## 性能与调优

```text
1. 启动慢定位 —— systemd-analyze blame 找慢服务，critical-chain 看关键路径
2. 减少排障时间 —— 保留旧内核、配置可回滚（改前备份），出问题快速回退
3. 精简自启 —— 不必要的服务 disable 掉，减少启动环节出错的概率
4. 提前演练 —— 平时演练 rescue 进法，真出问题时手不生
5. 非关键分区加 nofail —— fstab 里加 nofail，单块数据盘挂了也不拖垮开机
```

## 安全与权限

```text
1. rescue/emergency 绕开登录 —— 物理接触机器的人能进救援模式改密码，是安全边界
2. GRUB 密码 —— 给 GRUB 菜单和编辑加密码，防止未授权进救援模式
3. 改 fstab 前 mount -a 测试 —— 别改坏配置直接重启
4. Live 盘权限 —— chroot 修复等于获得了系统的 root 权限，Live 环境本身要可信
5. emergency 常免密进 root shell —— 比 rescue 更危险，物理访问必须锁死（机房门禁 + BIOS 密码）
6. 排错时别乱贴日志 —— journalctl 输出可能含主机名/路径等敏感信息，外发求助前脱敏
```

## 故障排查

### 启动失败完整排查流程

```shell
# 1. 判断卡在哪：GRUB 界面 / 内核 / 登录前
# 2. 进救援模式看日志
journalctl -xb | tail -50
# 3. 看失败的服务
systemctl --failed
# 4. 检查 fstab（最常见元凶）
cat /etc/fstab && blkid
# 5. 检查磁盘/文件系统
fsck -f /dev/sda2
```

### grub rescue> 提示符下的手动引导

```shell
# 1. 找分区（哪个分区有 /boot/grub）
ls
ls (hd0,gpt2)/
# 2. 设置 root 和 prefix
set root=(hd0,gpt2)
set prefix=(hd0,gpt2)/boot/grub
# 3. 加载 normal 模块并进入菜单
insmod normal
normal
```

### 内核 panic / 根分区挂不上

```shell
# 1. 看内核最后输出定位
dmesg | tail -30
# 2. 根分区挂不上：进 initramfs shell（内核命令行加 rd.break），检查 initramfs
# 或从旧内核启动（GRUB 菜单选 Advanced options）
# 3. 重建 initramfs（改了磁盘/LVM/加密/驱动后常需要）
update-initramfs -u
# 4. 检查根分区是否在 initramfs 里能识别
lsinitramfs /boot/initrd.img-$(uname -r) | grep -E 'lvm|dm-crypt'
```

### 启动卡在某个服务一直转圈

```shell
# 1. 看是哪个服务卡住（屏幕最后一行，或启动日志末尾）
journalctl -b | tail -30
# 2. 看该服务的状态
systemctl status <服务名>
# 3. 临时跳过该服务先进系统：GRUB 内核命令行加 systemd.mask=<服务名>
# 或进救援模式 systemctl mask <服务名>，再重启
# 4. 定位后修复：看服务日志、改配置，或直接 disable
journalctl -u <服务名> -n 100
```

## 常见问题

```text
Q1: 进救援模式根分区只读怎么办？
A: mount -o remount,rw / 重新挂载为读写，再改密码/配置。

Q2: grub rescue> 提示符怎么处理？
A: ls 找分区、set root/prefix、insmod normal、normal 手动引导，进去后 update-grub 修复。

Q3: 双系统装 Windows 后 Linux 进不去？
A: Windows 覆盖了 GRUB，用 Live USB 启动 chroot，grub-install + update-grub 重装。

Q4: 排查启动失败看哪次日志？
A: journalctl -b -1 看上次启动（失败那次）的日志，-b 默认是当前启动。

Q5: 内核 panic 或根分区挂不上怎么救？
A: 先从 GRUB 选旧内核启动；不行就 rd.break 进 initramfs shell 检查 initramfs，update-initramfs -u 重建；再不行 Live 盘 chroot 修。

Q6: 改了 fstab 重启卡 emergency，怎么快速定位？
A: emergency mode 里 cat /etc/fstab，比对 blkid 输出找 UUID 写错的行；或用 systemctl --failed 看哪个挂载单元失败。

Q7: 单用户模式和急救模式先试哪个？
A: 先 rescue（环境完整、工具多），rescue 进不去再 emergency（兜底）。能进 rescue 别进 emergency。

Q8: 启动卡在某个服务一直转圈怎么办？
A: 看 journalctl -b 末尾定位是哪个服务，systemctl status 看它状态；临时用 systemd.mask=<服务名> 跳过它先进系统，再修复或 disable。
```

## 面试题

```text
1. 启动失败怎么系统性地排查？
   答：先判断卡在哪一步（GRUB/内核/服务），再对症——引导问题 grub-install，内核/initramfs 问题 update-initramfs，服务/fstab 问题进救援模式修。

2. rescue 和 emergency 的区别？
   答：rescue 挂文件系统 + 基础服务，环境较完整；emergency 只挂根分区，最精简，是 rescue 进不去时的兜底。

3. grub.cfg 损坏和 GRUB 引导程序损坏怎么区分、怎么修？
   答：grub.cfg 损坏通常还能进救援模式，update-grub 重新生成；引导程序损坏连菜单都没有（grub rescue>），要 grub-install 重装。

4. 改了 fstab 为什么可能起不来？
   答：fstab 是开机挂载依据，写错导致挂载失败，systemd 进 emergency mode。改前应 mount -a 测试。

5. chroot 修复的完整步骤？为什么 chroot 前要挂 /dev /proc /sys？
   答：挂根分区 → mount --bind /dev /proc /sys → chroot → 修。挂这三个是因为 chroot 后的环境要用到设备节点、进程信息、sysfs，不挂会导致命令报错或行为异常。

6. 什么时候需要重建 initramfs？
   答：改了磁盘布局（LVM/RAID）、根分区加密、磁盘驱动后。否则 initramfs 里还是旧配置，根分区可能挂不上。

7. 单用户模式和直接 init=/bin/bash 的区别？
   答：单用户（rescue）还走 systemd、起基础服务、挂文件系统；init=/bin/bash 完全绕过 systemd，直接给个最原始的 bash，连 systemd 都没有，更底层也更难用。

8. systemd.mask= 内核参数是干嘛的？
   答：开机时临时屏蔽（mask）一个 unit，跳过有问题的服务先进系统排错，配合救援模式用。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 系统起不来先判断卡在哪步：GRUB 界面 → grub 问题；内核加载中 → 内核/initramfs；登录前 → 服务/fstab
2. 忘密码/改坏配置进单用户模式修，比重装系统快得多
3. 改 fstab/磁盘配置后，先用 mount -a 测试再重启
4. 双系统装 Windows 会覆盖 GRUB，装前备份引导
5. 定期用 systemctl --failed 检查有没有失败的服务，别等起不来才查
6. 升级内核保留旧内核，起不来先切旧内核回滚
7. 非关键分区 fstab 加 nofail，别让一块数据盘拖垮开机

### 踩坑记录

```text
坑 1：单用户模式里根分区只读，改不动东西
结论：进了 rescue，passwd/vi 都报只读文件系统。
原因：rescue 挂载的根分区默认只读，要先 remount。
解法：mount -o remount,rw / 改读写，再操作。

坑 2：改 fstab 前没 mount -a 测试，重启起不来
结论：fstab 写错直接重启，开机卡 emergency。
原因：fstab 错误导致挂载失败，系统进不了正常状态。
解法：改完 fstab 先 mount -a 测试，能挂上再重启。

坑 3：grub rescue> 提示符下不知道怎么办
结论：开机显示 grub rescue>，进不了系统。
原因：GRUB 找不到引导配置/分区（分区变了或配置损坏）。
解法：rescue 里 ls 找分区、set root/prefix、insmod normal、normal 手动引导。

坑 4：双系统装 Windows 后 GRUB 没了
结论：装了 Windows，开机直接进 Windows，Linux 进不去。
原因：Windows 覆盖了 MBR/引导，GRUB 被冲掉。
解法：Live USB 启动 chroot，grub-install + update-grub 重装 GRUB。

坑 5：journalctl -b 看错启动日志
结论：排查启动问题，journalctl 看到的是当前这次还是上次的日志分不清。
原因：journalctl -b 默认当前启动，-b -1 才是上次启动。
解法：排查启动失败用 journalctl -b -1（上次启动的日志），看失败原因。

坑 6：chroot 修复漏挂 /proc /sys，命令报错
结论：chroot 进去后 grub-install/apt 报错，以为是系统坏了。
原因：没 mount --bind /dev /proc /sys，chroot 环境缺设备节点和进程信息。
解法：chroot 前把 /dev /proc /sys 三个都 bind 挂上（UEFI 再挂 ESP）。

坑 7：改了磁盘配置没 update-initramfs，重启根分区挂不上
结论：改了 LVM/加密/驱动后重启，卡在 initramfs 或根分区挂不上。
原因：initramfs 里还是旧磁盘配置，找不到新布局。
解法：改磁盘/LVM/加密配置后 update-initramfs -u（或 dracut -f），再重启。
```
