## 概述

systemd 是现代 Linux 的初始化系统（PID 1）和服务管理器，负责开机拉起所有服务、管理服务生命周期（启动/停止/重启/自启）、记录日志（journald）。它用「unit」统一管理各种资源——服务（service）、定时器（timer）、目标（target）、套接字（socket）、挂载（mount）。systemctl 是管理 unit 的命令，几乎所有服务操作都靠它。

```text
systemd 核心概念：
1. unit —— 统一的管理单元，有 service/timer/target/socket/mount 等类型
2. systemctl —— 管理 unit 的命令（启动/停止/自启/查看）
3. 依赖关系 —— unit 之间的 After/Requires/Wants，决定启动顺序
4. journald —— systemd 的日志系统，journalctl 查看
```

```text
# 实测（本机 systemd 版本）
$ systemd --version | head -1
systemd 255 (255.4-1ubuntu8.17)
```

systemd 不只是「启动服务的脚本替换」，它把原本分散的工具（SysV init 脚本、inittab、atd、crond、syslogd、xinetd 等）统一到一个框架里，用「声明式 unit 文件 + 依赖图 + cgroup 资源隔离 + 统一日志」覆盖了服务的全生命周期。

## 核心概念

1. **unit**：systemd 管理的基本单元，每种类型对应一类资源。service（服务）、timer（定时任务）、target（启动目标）、socket（套接字激活）、mount（挂载）、slice（资源分组）。
2. **systemctl**：管理 unit 的统一命令，启动/停止/自启/查看状态。
3. **依赖关系**：unit 之间的 After/Before（顺序）、Requires（强依赖）、Wants（弱依赖）、Conflicts（互斥）。
4. **target**：一组服务的集合，代表系统运行状态（multi-user/graphical），对应老的运行级别。
5. **journald**：systemd 的日志守护进程，收集服务输出，journalctl 查询。

```text
unit 类型速查：
service  服务（nginx/mysql/sshd），最常用
timer    定时任务（对应 cron）
target   启动目标/运行级别（multi-user/graphical）
socket   套接字激活（按需启动服务）
mount    挂载点（对应 /etc/fstab 的挂载）
slice    资源分组（cgroup 隔离）
```

下面按「是什么 → 为什么 → 怎么用 → 边界/易错点」展开。

### unit（管理单元）

- **是什么**：systemd 把「要管理的东西」统一抽象成 unit，一个 unit 用一个 `.service`/`.timer`/`.target` 等后缀的文件描述，unit 名 = 文件名（如 `nginx.service`）。
- **为什么**：统一抽象后，所有资源（服务/定时器/挂载/套接字）用同一套 systemctl 命令管理，依赖关系也能跨类型表达（比如 timer 触发 service、socket 激活 service）。
- **怎么用**：`systemctl list-units` 看活动 unit，`list-unit-files` 看所有已安装 unit，`systemctl cat` 看单个 unit 内容。

```shell
systemctl list-units --type=service        # 活动的 service
systemctl list-units --type=target         # 活动的 target
systemctl list-unit-files --type=service   # 所有 service（含未激活的）
systemctl cat nginx.service                # 看 unit 文件内容
```

- **边界/易错点**：unit 名字要带后缀（`nginx.service`），不带后缀 systemctl 默认补 `.service`。单位文件分「系统级」（`/etc/systemd/system/`）和「用户级」（`~/.config/systemd/user/`，用 `systemctl --user` 管理，不用 sudo）。`list-units` 只列已加载到内存的活动 unit，`list-unit-files` 才列全磁盘上的。

### systemctl（管理命令）

- **是什么**：管理 unit 的统一 CLI，所有操作（start/stop/restart/reload/enable/disable/status/daemon-reload）都通过它。
- **为什么**：一个命令搞定「立即控制」和「开机自启」两类操作，避免记忆一堆 `/etc/init.d/xxx start` 脚本路径。
- **怎么用**：见「常用命令与配置」节的完整命令表。
- **边界/易错点**：`start` 和 `enable` 是两回事（立即启动 vs 开机自启），很多人搞混。改 unit 文件后必须 `daemon-reload`，否则 systemd 还在用内存里的旧配置。

### 依赖关系（After/Before/Requires/Wants/Conflicts）

- **是什么**：unit 之间通过 `[Unit]` 段的指令声明顺序和依赖。`After=`/`Before=` 只定顺序不定依赖；`Requires=` 强依赖（依赖方失败本单元也失败）；`Wants=` 弱依赖（尽力拉起，失败不影响）；`Conflicts=` 互斥。
- **为什么**：依赖图是 systemd 能并行启动的基础——没有依赖关系的 unit 可以同时起，有依赖的按顺序等，比 SysV 串行快得多。
- **怎么用**：见「配置文件解析」节的详细示例。
- **边界/易错点**：`After=` 只是「排在后面」，不会自动把对方拉起来，要真正「依赖」必须同时写 `After=` + `Requires=`/`Wants=`。顺序和依赖是两套正交的概念，新手常只写 `After=` 以为就依赖了。

### target（启动目标）

- **是什么**：一组 unit 的集合，代表一个系统状态。`multi-user.target`（多用户无桌面）、`graphical.target`（带图形界面）、`emergency.target`（急救 shell）、`rescue.target`（单用户）。
- **为什么**：对应老的 SysV 运行级别（runlevel），但比运行级别灵活——target 之间也能有依赖，可以自定义中间状态。
- **怎么用**：`systemctl get-default` 看默认，`set-default` 改，`isolate` 切换。

```shell
systemctl get-default                    # 当前默认 target
systemctl set-default multi-user.target  # 设为多用户模式
systemctl isolate rescue.target          # 切到单用户/救援模式
systemctl list-dependencies multi-user.target   # 看 target 拉起哪些东西
```

- **边界/易错点**：target 和运行级别的映射不是完全等价（runlevel 3 → multi-user.target，runlevel 5 → graphical.target），但 systemd 保留了 `runlevelN.target` 兼容别名。`isolate` 切 target 会停掉新 target 不需要的服务，别在生产的 graphical 和 multi-user 之间乱切。

### journald（日志系统）

- **是什么**：systemd 的日志守护进程（`systemd-journald`），收集内核、服务、systemd 自身的日志，存到 `/var/log/journal/`（二进制格式），`journalctl` 查询。
- **为什么**：统一日志来源（不再每个服务各写各的日志文件），按 unit、时间、优先级过滤，还能关联启动次数（`-b`）。
- **怎么用**：见「常用命令与配置」节。

```shell
journalctl -u nginx -n 50        # 某服务最近 50 条日志
journalctl -b                    # 本次启动以来的日志
journalctl -p err -b             # 本次启动的 error 级日志
journalctl -f                    # 实时跟踪（等同 tail -f）
```

- **边界/易错点**：journald 默认日志是易失的（存 `/run/log/journal/`，重启清空），要持久化得改 `/etc/systemd/journald.conf` 的 `Storage=persistent` 并建 `/var/log/journal/` 目录。journal 是二进制格式，别用 `grep` 直接读文件，用 `journalctl` 过滤。

## 工作原理

systemd 作为 PID 1，启动流程是「树形依赖 + 并行启动」：

1. **启动**：内核 exec systemd（PID 1）→ 挂载文件系统 → 到达 basic.target（基础系统）。
2. **依赖解析**：systemd 读所有 unit 文件，构建依赖图，从默认 target 出发，按 After/Requires/Wants 确定启动顺序。
3. **并行启动**：无依赖关系的 unit 并行启动（比 SysV init 串行快），有依赖的按顺序等待。
4. **生命周期管理**：systemctl start/stop/restart 控制服务，Restart= 策略决定崩溃后是否自动拉起。
5. **日志**：服务的 stdout/stderr 被 systemd 捕获进 journald，journalctl 按服务过滤查询。

```text
启动模型：
default.target → basic.target → 各服务（按依赖排序，无依赖并行）

vs 老 SysV init：
SysV 串行启动（一个接一个，慢）
systemd 依赖图 + 并行启动（快）
```

依赖解析的细节——顺序（After/Before）和依赖（Requires/Wants）是两套正交的东西：

```text
After=network.target     只保证「排在 network.target 之后启动」，不保证 network.target 被启动
Wants=network.target     只保证「network.target 会被尝试启动」，不保证先后顺序
Requires=network.target  强依赖，network.target 失败则本单元也失败

正确表达「网络就绪后再启动、且依赖网络」的写法是同时写两条：
After=network.target
Wants=network.target
```

一次典型的目标依赖链（`systemctl list-dependencies` 的输出结构）：

```text
multi-user.target         默认运行目标
├─ basic.target           基础系统（挂载、sockets、timers 就绪）
│  ├─ sockets.target      各种套接字激活
│  ├─ timers.target       定时器
│  └─ slices.target       cgroup 资源分组
├─ sshd.service           SSH 服务
├─ cron.service           定时任务
└─ docker.service         容器引擎
```

## 常用命令与配置

```shell
systemctl start nginx          # 立即启动
systemctl stop nginx           # 停止
systemctl restart nginx        # 重启
systemctl reload nginx         # 重载配置（不中断服务）
systemctl enable nginx         # 开机自启
systemctl disable nginx        # 取消自启
systemctl enable --now nginx   # 自启 + 立即启动
systemctl status nginx         # 看状态
systemctl daemon-reload        # 改单元文件后重载
systemctl list-units --type=service --state=running   # 运行中的服务
systemctl list-unit-files --type=service              # 所有 service 单元文件
```

```text
enable vs start（关键区别）：
1. start —— 立即启动，但重启后不自动起
2. enable —— 设置开机自启，但不立即启动
3. enable --now —— 两者都做（自启 + 立即启动）
```

更多常用操作：

```shell
systemctl is-active nginx       # 是否在运行（返回 active/inactive）
systemctl is-enabled nginx      # 是否开机自启（返回 enabled/disabled）
systemctl is-failed nginx       # 是否处于失败状态
systemctl mask nginx            # 彻底禁用（符号链接指向 /dev/null）
systemctl unmask nginx          # 解除 mask
systemctl reset-failed nginx    # 清除 failed 状态
systemctl list-dependencies nginx      # 看依赖树（正向）
systemctl list-dependencies nginx --reverse   # 看谁依赖它（反向）
systemctl show nginx            # 看 unit 的所有属性（键值对）
systemctl kill -s SIGTERM nginx # 给服务主进程发信号
systemctl cat nginx             # 看 unit 文件完整内容
systemctl list-sockets          # 看套接字激活
systemctl list-timers           # 看定时器
```

## 配置文件解析

```text
unit 文件位置（优先级从高到低）：
/etc/systemd/system/      系统管理员自定义（覆盖用）
/run/systemd/system/      运行时生成
/usr/lib/systemd/system/  软件包自带（默认）

依赖关系指令（unit 文件的 [Unit] 段）：
After=/Before=   启动顺序（在某某之后/之前）
Requires=        强依赖，依赖方失败则本单元也失败
Wants=           弱依赖，依赖方失败不影响本单元
Conflicts=       互斥，不能同时启动
```

```ini
# /etc/systemd/system/nginx.service 结构示例
[Unit]
Description=nginx web server
After=network.target

[Service]
Type=simple
ExecStart=/usr/sbin/nginx

[Install]
WantedBy=multi-user.target
```

`[Unit]` 段和 `[Install]` 段的完整常用字段：

```ini
[Unit]
Description=nginx web server       # 描述（status/list 里显示）
Documentation=man:nginx(8)         # 文档链接
After=network.target               # 启动顺序：排在其后
Before=shutdown.target             # 启动顺序：排在其前
Requires=network.target            # 强依赖
Wants=network-online.target        # 弱依赖
Conflicts=apache2.service          # 互斥，不能同时起
ConditionPathExists=/etc/nginx/nginx.conf   # 条件：文件存在才启动

[Install]
WantedBy=multi-user.target         # enable 时挂到该 target 的 .wants/ 下
RequiredBy=multi-user.target       # enable 时挂到 .requires/ 下（强依赖）
Alias=www.service                  # 别名
```

`enable` 的本质——它只是创建符号链接：

```text
systemctl enable nginx 实际做的是：
在 /etc/systemd/system/multi-user.target.wants/ 下建一个指向 nginx.service 的符号链接
disable 就是删掉这个链接
所以「enable = 在某个 target 的 .wants 目录里挂符号链接」
WantedBy=multi-user.target 告诉 enable 该把链接挂到哪个 target 下
```

## 应用场景实战

### 场景一：查看服务状态和自启情况

```shell
# 1. 看服务是否在运行
systemctl is-active nginx
# 2. 看是否开机自启
systemctl is-enabled nginx
# 3. 看完整状态（含最近日志）
systemctl status nginx
# 4. 看服务依赖谁
systemctl list-dependencies nginx
```

### 场景二：分析开机启动慢的元凶

```shell
# 1. 总启动时间
systemd-analyze
# 2. 各服务启动耗时排行
systemd-analyze blame | head -5
```

```text
# 实测（本机）
$ systemd-analyze blame | head -3
2min 33.159s docker.service
2min 6.774s fwupd-refresh.service
46.127s containerd.service
# docker.service 拖了 2 分 33 秒，是开机慢的头号元凶
```

### 场景三：让服务崩溃自动拉起 + 延迟启动非关键服务

一个常见的运维组合：关键服务配 `Restart=always` 自动拉起，非关键服务延迟启动不挡关键路径。以 Nginx 为例：

```ini
# /etc/systemd/system/nginx.service.d/override.conf（drop-in 覆盖，不改原文件）
[Service]
Restart=always
RestartSec=5
```

```shell
# 1. 用 drop-in 目录覆盖配置，不动软件包自带的原文件
systemctl edit nginx        # 自动创建 override.conf 并打开编辑器

# 2. 重载并验证
systemctl daemon-reload
systemctl restart nginx
systemctl show nginx -p Restart -p RestartSec   # 确认覆盖生效

# 3. 非关键服务延迟启动（改用 timer 触发，见 [[14.2-systemd timer]]）
systemctl list-timers
```

```text
drop-in 覆盖机制：
/etc/systemd/system/nginx.service.d/*.conf 会叠加在原 unit 之上
优先级高于 /usr/lib/systemd/system/nginx.service
好处：软件包升级不会覆盖你的定制，systemctl cat 能看到合并结果
```

## 性能与调优

```text
1. 并行启动 —— systemd 已按依赖并行，别把无关服务串成 Requires 链
2. 精简自启 —— systemctl list-unit-files --state=enabled 清理不必要的自启服务
3. 延迟启动 —— 非关键服务用 timer 或 Requires 弱依赖延后，别挡关键路径
4. 启动耗时 —— systemd-analyze blame/critical-chain 定位瓶颈服务
5. 资源限制 —— 用 slice + CPUQuota/MemoryLimit 限制服务资源，防单个服务拖垮系统
```

```shell
systemd-analyze critical-chain          # 启动关键路径（逐层展开）
systemd-analyze critical-chain nginx.service   # 看某服务的关键路径
systemctl list-unit-files --state=enabled --type=service   # 可精简的自启服务
```

```text
启动慢的常见原因与对策：
1. 服务互相串行等待 —— 检查是否有不必要的 Requires 链，弱依赖改用 Wants
2. 单个服务耗时过长 —— blame 定位，优化该服务自身（如数据库预热）
3. 网络等待 —— After=network.target 只保证「网卡起来」，要真联网用 network-online.target
4. 自启服务太多 —— disable 不用的（蓝牙、打印、snap 相关服务）
5. 磁盘慢 —— 机械盘上服务并发读盘会互相拖，SSD 上不明显
```

## 安全与权限

```text
1. 最小权限运行 —— 服务的 User=/Group= 指定非 root 用户，别默认 root 跑
2. 沙盒加固 —— unit 可配 NoNewPrivileges、ProtectSystem、PrivateTmp 等隔离
3. mask 禁用 —— systemctl mask 彻底禁用一个服务（防止被意外激活）
4. 别直接 kill —— systemd 托管的服务直接 kill 会被按 Restart= 策略拉起，用 systemctl stop
5. 审计 —— journalctl 记录服务日志，异常行为有迹可查
```

```shell
systemctl mask nginx          # 禁用（连手动 start 都不行）
systemctl unmask nginx        # 解除
systemctl show nginx -p User -p NoNewPrivileges   # 看服务安全相关配置
```

```text
mask 和 disable 的区别：
disable  取消开机自启，但仍可手动 start
mask     把 unit 符号链接到 /dev/null，start 都不行（彻底封死）
用途     mask 用于「某个服务必须永远不能跑」的场景（如老的 telnetd）
```

```shell
# 审计：看服务相关的安全属性
systemctl show nginx -p User -p Group -p NoNewPrivileges -p ProtectSystem -p PrivateTmp
# 看某个 unit 是否被 mask
systemctl is-enabled nginx     # 输出 masked 即被 mask
```

## 故障排查

### 服务起不来

```shell
# 1. 看状态和退出原因
systemctl status nginx
# 2. 看服务日志（关键）
journalctl -u nginx -n 50
# 3. 看依赖是否满足
systemctl list-dependencies nginx
# 4. 看完整单元配置
systemctl cat nginx
```

### 服务反复重启 / 改了配置不生效

```shell
# 反复重启：看 Restart 策略和崩溃原因
systemctl show nginx -p Restart -p RestartSec
journalctl -u nginx -f          # 实时看崩溃日志
# 改了配置不生效：忘了 daemon-reload
systemctl daemon-reload
```

### 服务状态是 masked / failed / inactive 分别怎么办

```shell
# masked：被 mask 了，解除才能启动
systemctl unmask nginx
systemctl start nginx

# failed：启动失败，清除失败状态后排查
systemctl --failed              # 列出所有失败的服务
systemctl reset-failed nginx    # 清除 failed 标记
journalctl -u nginx -n 50       # 看失败原因

# inactive：没在运行，检查 enable 状态和依赖
systemctl status nginx
systemctl is-enabled nginx
```

## 常见问题

```text
Q1: reload 和 restart 的区别？
A: reload 平滑重载配置（不中断连接），restart 停止再启动（短暂中断）。支持热重载的服务（nginx）用 reload。

Q2: enable 了为什么重启后服务没起来？
A: enable 只设自启，当时没 start；或依赖的服务没起来。用 enable --now，重启后查 status 和依赖。

Q3: stop 了服务为什么又自己起来了？
A: 配了 Restart=always，或 socket 激活/定时器又拉起了它。要彻底停用 disable + mask。

Q4: 改 unit 文件为什么不生效？
A: systemd 缓存了旧单元文件，改完要 systemctl daemon-reload 再 restart。

Q5: list-units 和 list-unit-files 有什么区别？
A: list-units 列出「已加载到内存的活动 unit」，list-unit-files 列出「磁盘上所有已安装 unit 文件」（含未激活的）。查「装了哪些服务」用后者。

Q6: systemctl mask 之后 start 会怎样？
A: 报「Unit xxx is masked」拒绝启动。mask 把 unit 链接到 /dev/null，是比 disable 更彻底的禁用。解除用 unmask。

Q7: 服务进程被 kill 了会自动重启吗？
A: 取决于 Restart= 策略。Restart=always 会拉起，Restart=no 不会，Restart=on-failure 只在异常退出时拉起。systemd 默认通过 cgroup 跟踪主进程，主进程退出即触发策略判断。
```

## 面试题

```text
1. systemd 相比 SysV init 的优势？
   答：并行启动（依赖图而非串行）、统一 unit 管理、socket 激活按需启动、journald 统一日志、cgroup 资源管理。

2. Requires 和 Wants 的区别？
   答：Requires 强依赖，依赖方失败本单元也失败；Wants 弱依赖，依赖方失败不影响本单元，启动时尽力拉起。

3. systemd 是怎么做到并行启动的？
   答：读所有 unit 文件构建依赖图，从默认 target 出发，无依赖的 unit 并行启动，有依赖的按 After/Requires 排序等待。

4. daemon-reload 是干嘛的？
   答：重新加载 systemd 的 unit 文件（改了 service 文件后），让 systemd 重新读配置，否则改动不生效。

5. After= 和 Requires= 有什么区别？
   答：After= 只定启动顺序（排在其后），不产生依赖；Requires= 是强依赖（失败会连累本单元）。两者正交，常配合使用。

6. enable 底层做了什么？
   答：在目标 target 的 .wants/（或 .requires/）目录下创建指向 unit 文件的符号链接，disable 就是删链接。WantedBy= 指定挂到哪个 target 下。

7. systemd 怎么判断一个服务「启动成功」？
   答：取决于 Service 段的 Type=。Type=simple 认为 fork 完即就绪；forking 等 PIDFile 出现；notify 等 sd_notify 信号；oneshot 等命令退出。选错 Type 会误判状态。

8. socket 激活是什么？有什么用？
   答：systemd 先监听 socket，有连接进来才按需启动对应服务。好处是省资源、加快启动（服务不必开机就起），典型是 sshd.socket、docker.socket。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 服务操作用 systemctl，别直接 kill 进程（systemd 会再拉起）
2. enable 和 start 是两回事，要自启 + 启动用 enable --now
3. 改 unit 文件后必须 systemctl daemon-reload，否则不生效
4. 服务起不来先 systemctl status + journalctl -u 看日志
5. 开机慢用 systemd-analyze blame 定位慢服务
6. 定制服务配置用 systemctl edit 建 drop-in 覆盖，别直接改软件包自带文件
7. 要「网络真正可用」再启动的服务，用 After=network-online.target，别用 network.target

### 踩坑记录

```text
坑 1：改 unit 文件没 daemon-reload，改动不生效
结论：改了 service 文件，systemctl restart 还是老配置。
原因：systemd 缓存了旧单元文件，要 daemon-reload 重新加载。
解法：改 unit 文件后 systemctl daemon-reload，再 restart。

坑 2：enable 了但重启后服务没起来
结论：systemctl enable nginx 后，重启 nginx 没自启。
原因：enable 只设自启，当时没 start；或依赖的服务没起来。
解法：enable --now 一次到位，重启后 systemctl status 排查依赖。

坑 3：systemctl stop 后服务又自己起来了
结论：stop 了服务，过一会又 running。
原因：服务配了 Restart=always，或 socket 激活/定时器又拉起了它。
解法：要彻底停用 disable + mask（mask 防止被激活）。

坑 4：systemctl restart 和 reload 用错
结论：改配置后 restart，服务中断了（reload 可以不断）。
原因：restart 是停止再启动（中断），reload 是重载配置（不断连接）。
解法：支持热重载的服务（nginx）用 reload，不支持才 restart。

坑 5：直接 kill 进程，systemd 反复重启它
结论：kill 了服务进程，systemd 又把它拉起来。
原因：systemd 托管服务，进程退出会按 Restart= 策略重启。
解法：正确停服务用 systemctl stop，别直接 kill。

坑 6：只写 After= 没写 Wants=/Requires=，依赖不生效
结论：服务 A 里写了 After=B.service，以为 B 会先启动，结果 B 根本没起。
原因：After= 只定顺序不产生依赖，不会自动拉起 B。
解法：要真依赖就同时写 After= + Wants=（或 Requires=）。

坑 7：After=network.target 但服务还是报「连不上网」
结论：服务启动时 DNS/网络没真正可用。
原因：network.target 只代表「网络管理服务起来了」，不代表网卡拿到 IP、网络可用。
解法：要网络真正可用用 After=network-online.target（并确保有服务提供该 target）。
```
