## 概述

Service Unit 是 systemd 的服务定义文件，告诉 systemd「怎么启动、怎么重启、什么用户跑、日志去哪」。把自己写的程序托管给 systemd，就写一个 .service 文件，放到 /etc/systemd/system/ 下，就能获得开机自启、崩溃重启、日志收集。核心是三个段：[Unit]（描述+依赖）、[Service]（怎么跑，Type/ExecStart/Restart）、[Install]（怎么自启）。

```text
Service Unit 三段结构：
1. [Unit] —— Description 描述、After 启动顺序、Requires 依赖
2. [Service] —— Type 启动类型、ExecStart 启动命令、Restart 重启策略
3. [Install] —— WantedBy 指定 target，决定开机自启
```

写 Service Unit 的完整闭环是：写 `.service` 文件 → `daemon-reload` 重载 → `enable --now` 自启并启动 → `status`/`journalctl -u` 验证。日志集成是其中容易被忽略但很重要的一环——服务往 stdout/stderr 打印的内容会被 systemd 自动捕获进 journald，不需要自己写日志文件。

## 核心概念

1. **Type**：进程的启动/后台化方式。simple（默认，前台运行）、forking（程序自己 fork 到后台）、oneshot（执行一次就退）、notify（启动后发通知）。选错会导致 systemd 误判服务状态。
2. **ExecStart**：启动命令（绝对路径）。还有 ExecStop（停止命令）、ExecReload（重载命令）。
3. **Restart**：崩溃重启策略。no（不重启）、on-failure（失败才重启）、always（总是重启），配合 RestartSec（重启间隔）。
4. **User/Group**：以什么用户运行（别默认 root）。
5. **WantedBy**：指定挂到哪个 target，决定开机自启（通常 multi-user.target）。

```text
Type 启动类型：
simple   默认，前台运行，ExecStart 进程就是服务主体
forking  程序自己 fork 到后台（老式 daemon），需配 PIDFile
oneshot  执行一次就退出（初始化脚本）
notify   启动后发 sd_notify 通知 systemd「就绪」
```

下面按「是什么 → 为什么 → 怎么用 → 边界/易错点」展开。

### Type（启动类型）

- **是什么**：告诉 systemd「怎么判断服务启动成功了」，决定了 systemd 跟踪哪个进程、何时认为服务「就绪」。
- **为什么**：程序有前台运行、自己 fork 后台、执行一次就退、发通知等不同行为，systemd 必须知道才能正确判断状态；选错会导致「服务明明在跑，systemd 却以为它秒退并反复重启」。
- **怎么用**：四种类型的选型口诀见下表。

```text
Type     适用程序                          就绪判定                   需要额外配置
simple   前台运行（Java/Node/Python/Go）   ExecStart 进程 fork 完成即就绪  无（默认）
forking  老式 daemon（自己 fork 到后台）    PIDFile 出现即就绪        PIDFile= 路径
oneshot  一次性初始化脚本                   ExecStart 命令退出即就绪  RemainAfterExit=yes
notify   支持 sd_notify 的程序            收到 READY=1 通知即就绪    程序里调 sd_notify
dbus     通过 D-Bus 注册的服务            D-Bus 名字出现即就绪      BusName=
idle     类似 simple 但等所有任务完成才跑   同 simple               （几乎不用）
```

```shell
# 查一个服务的 Type 和主进程
systemctl show nginx -p Type -p MainPID -p SubState
# 查主进程状态（active(running) / active(exited) / activating）
systemctl status nginx | head -5
```

- **边界/易错点**：最容易踩的是「会 fork 的程序配了 simple」——主进程 fork 出子进程后就退出，systemd 以为服务结束，触发 Restart 策略反复重启。反过来「前台程序配了 forking」也会卡在 activating 状态等不到 PIDFile。不确定时先用 `Type=simple` 且程序别自己 daemonize（很多程序有 `--foreground`/`-D` 选项强制前台）。

### ExecStart / ExecStop / ExecReload（执行命令）

- **是什么**：`ExecStart` 是启动命令，`ExecStop` 是停止命令，`ExecReload` 是重载命令，都必须写绝对路径。
- **为什么**：systemd 不像 shell 那样有完整的 PATH 和变量环境，用绝对路径才可靠；`ExecStop`/`ExecReload` 让 stop/reload 有明确行为（默认 stop 是发 SIGTERM，不一定够）。
- **怎么用**：命令里可以用 `$VAR` 引用环境变量，还可以配 `ExecStartPre`/`ExecStartPost` 在启动前后跑额外命令。

```ini
[Service]
Type=simple
ExecStart=/opt/myapp/bin/myapp --config /etc/myapp/config.yaml
ExecStartPre=/usr/bin/mkdir -p /var/run/myapp          # 启动前建目录
ExecStartPost=/bin/sleep 1                              # 启动后延时
ExecStop=/opt/myapp/bin/myapp-stop                       # 停止命令（可省略，默认 SIGTERM）
ExecReload=/bin/kill -HUP $MAINPID                       # 重载（发 HUP 信号）
```

- **边界/易错点**：`ExecStart` 不是 shell 解析的，`|`、`>`、`&&` 等 shell 语法无效，要复杂逻辑就包一个脚本再 ExecStart 调脚本。`$MAINPID` 是 systemd 注入的特殊变量（主进程 PID），只在 `ExecReload`/`ExecStop` 里可用。命令写相对路径会因 PATH 精简而报「找不到文件」。

### Restart / RestartSec（重启策略）

- **是什么**：`Restart=` 决定主进程退出后 systemd 是否拉起，`RestartSec=` 是两次重启之间的间隔秒数。
- **为什么**：进程崩溃自动拉起是「服务自愈」的关键，但配错会变成「启动即崩溃→疯狂重启」的死循环。
- **怎么用**：三种策略的语义。

```text
Restart=no          退出后不重启（默认）
Restart=on-failure  只在异常退出时重启（退出码非 0、被信号杀死、超时），正常退出不重启
Restart=always      无论为何退出都重启（含正常退出，RestartSec 后拉起）
Restart=on-abnormal 信号杀死/超时才重启（比 on-failure 少「非 0 退出码」这一项）
```

```ini
[Service]
ExecStart=/opt/myapp/bin/myapp
Restart=on-failure
RestartSec=10
```

- **边界/易错点**：`Restart=always` 对「正常退出」也重启，如果程序是「跑完就退」的一次性任务，会无限循环。systemd 有默认重启限速（`StartLimitIntervalSec`/`StartLimitBurst`，默认 10 秒内 5 次），超过会放弃并报「start request repeated too quickly」——这是保护机制，但也可能掩盖真正的崩溃根因。生产服务一般用 `on-failure` + `RestartSec=5~10`。

### User / Group（运行用户）

- **是什么**：指定服务以哪个用户/组运行，默认是 root。
- **为什么**：最小权限原则——服务被攻破或出 bug 时，用非 root 用户跑能限制破坏面（不能写系统目录、不能提权）。
- **怎么用**：建专用用户，配 `User=`/`Group=`，并保证该用户对工作目录、数据目录、日志有权限。

```ini
[Service]
User=deploy
Group=deploy
WorkingDirectory=/opt/myapp
```

```shell
# 建专用用户（无登录 shell，防别人用它登进来）
useradd -r -s /usr/sbin/nologin -d /opt/myapp deploy
# 把数据目录属主给该用户
chown -R deploy:deploy /opt/myapp /var/lib/myapp
```

- **边界/易错点**：配了 `User=deploy` 但该用户对目录没读写权限，服务起不来（报 permission denied）。有些服务需要绑特权端口（<1024）或写特权文件，得用 `AmbientCapabilities=CAP_NET_BIND_SERVICE` 授权，而不是干脆改回 root。

### WantedBy（自启目标）

- **是什么**：`[Install]` 段里的指令，告诉 `systemctl enable` 把符号链接挂到哪个 target 的 `.wants/` 目录下，从而决定开机自启。
- **为什么**：`enable` 的本质就是建符号链接，`WantedBy` 决定链接挂哪，挂对 target 服务才会在正确时机自启。
- **怎么用**：用户服务用 `multi-user.target`（多数服务），需要图形界面的挂 `graphical.target`。

```ini
[Install]
WantedBy=multi-user.target
```

- **边界/易错点**：没有 `[Install]` 段（或没有 `WantedBy=`）的 unit 无法 `enable`（会报「unit does not support enable」），但仍可手动 `start`。改 `WantedBy` 后要重新 `disable` + `enable` 才会更新链接位置。

## 工作原理

systemd 启动一个 service 的流程：

1. **读 unit 文件** → 解析 [Unit]/[Service]/[Install] 三段。
2. **按 Type 判断「就绪」**：simple 认为 fork 完即就绪；forking 要等 PIDFile 出现；notify 要等 sd_notify 信号；oneshot 等命令退出。
3. **监控进程**：systemd 把服务进程放进 cgroup，跟踪主进程存活。
4. **崩溃处理**：主进程退出时按 Restart= 策略决定是否拉起，间隔 RestartSec 秒。
5. **日志收集**：服务的 stdout/stderr 被 systemd 捕获进 journald。

```text
关键：Type 决定 systemd 怎么判断「服务是否起来了」
Type=simple 配了会 fork 的程序 → 主进程 fork 后退了 → systemd 以为服务秒退 → 反复重启
```

日志集成的完整链路（知识点的第 3 项）：

```text
服务进程写 stdout/stderr
      ↓
systemd 用管道/套接字捕获（不依赖服务自己写文件）
      ↓
systemd-journald 落盘（/run/log/journal/ 易失 或 /var/log/journal/ 持久）
      ↓
journalctl -u <服务名> 查询
```

```ini
# 日志相关字段（控制 stdout/stderr 去哪）
[Service]
StandardOutput=journal     # stdout 进 journald（默认）
StandardError=journal      # stderr 进 journald（默认）
SyslogIdentifier=myapp     # 日志里的标识名（默认是服务名）
# 也可以显式写文件（但一般不推荐，journald 已统一收集）：
# StandardOutput=append:/var/log/myapp/out.log
```

```text
为什么推荐日志交给 journald 而不是自己写文件：
1. journalctl -u myapp 一条命令查，不用记日志路径
2. 日志随服务生命周期管理，不会散落一堆文件
3. 自动带时间戳、优先级、启动次数（-b 过滤本次启动）
4. 配合 logrotate/journald.conf 做轮转和大小限制
```

## 常用命令与配置

```shell
# 写完 service 文件后
systemctl daemon-reload          # 重载单元文件
systemctl enable --now myapp     # 自启 + 启动
systemctl status myapp           # 看状态
systemctl cat myapp              # 看完整单元配置
journalctl -u myapp -f           # 实时看服务日志

# 常用查询
systemctl show myapp -p Type -p ExecStart -p Restart   # 看关键参数
```

```shell
# 验证 unit 文件语法和正确性
systemd-analyze verify /etc/systemd/system/myapp.service   # 语法/依赖校验
systemd-analyze security myapp        # 安全加固评分（列出可加的保护项）
systemctl list-dependencies myapp     # 看依赖
systemctl show myapp | grep -E '^(ExecStart|Type|Restart|User)='   # 过滤关键配置
```

## 配置文件解析

一个完整的 service 文件分三段，文件放 /etc/systemd/system/xxx.service（用户自定义）或 /usr/lib/systemd/system/（软件包自带）。

```ini
[Unit]
Description=My Application
After=network.target

[Service]
Type=simple
User=deploy
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/bin/myapp
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```text
常用字段含义：
Description     服务描述（status 里显示）
After           启动顺序（网络就绪后再起）
Type            启动类型（simple/forking/oneshot/notify）
ExecStart       启动命令（绝对路径）
Restart         重启策略（no/on-failure/always）
RestartSec      重启间隔（秒）
User/Group      运行用户（别用 root）
WorkingDirectory 工作目录
Environment     环境变量
PIDFile         forking 型需要的 PID 文件路径
WantedBy        挂到哪个 target（自启）
```

`[Service]` 段完整常用字段（含进程管理和资源限制）：

```ini
[Service]
# 进程与生命周期
Type=simple
ExecStart=/opt/myapp/bin/myapp
ExecStartPre=/usr/bin/mkdir -p /var/run/myapp
ExecStop=/bin/kill -TERM $MAINPID
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=10
TimeoutStartSec=30          # 启动超时（默认 90s）
TimeoutStopSec=30           # 停止超时（默认 90s）
KillMode=control-group      # 停止时杀整个 cgroup（默认）
KillSignal=SIGTERM          # 停止先发 TERM，超时后 SIGKILL

# 用户与权限
User=deploy
Group=deploy
WorkingDirectory=/opt/myapp
Environment="APP_ENV=production"
EnvironmentFile=/etc/myapp/env          # 从文件读环境变量（可含 KEY=VALUE）
UMask=0027

# 资源限制（cgroup）
LimitNOFILE=65536           # 文件描述符上限
CPUQuota=200%               # CPU 配额（2 核）
MemoryMax=512M              # 内存上限
TasksMax=512                # 进程/线程数上限
```

`Environment` 和 `EnvironmentFile` 的区别：

```text
Environment=       直接在 unit 里写 KEY=VALUE，适合少量变量
EnvironmentFile=   从文件读 KEY=VALUE（一行一个），适合多变量/含敏感信息
                   文件权限要收紧（chmod 600），因为可能存密码/密钥
注意：Environment= 里写 $VAR 不会被 shell 展开，要用 ${VAR} 或直接写死值
```

## 应用场景实战

### 场景一：把自己写的 Java 服务托管给 systemd

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My Java App
After=network.target

[Service]
Type=simple
User=deploy
WorkingDirectory=/opt/myapp
Environment="JAVA_OPTS=-Xmx2g -Xms2g"
ExecStart=/usr/bin/java $JAVA_OPTS -jar /opt/myapp/app.jar
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

```shell
systemctl daemon-reload
systemctl enable --now myapp
systemctl status myapp
journalctl -u myapp -f
```

### 场景二：排查服务起不来的原因

```shell
# 1. 看状态和退出原因
systemctl status myapp
# 2. 看详细日志
journalctl -u myapp -n 50
# 3. 看单元文件的配置是否正确
systemctl cat myapp
# 4. 手动跑 ExecStart 命令，看报错
/opt/myapp/bin/myapp
```

### 场景三：托管 Python 服务 + 日志集成

用 Python 的 HTTP 服务做例子，重点演示「日志交给 journald、崩溃自动拉起」：

```python
# /opt/pyapp/server.py —— 简单 HTTP 服务，日志打到 stdout（systemd 自动收集）
import http.server
import logging
import sys

logging.basicConfig(stream=sys.stdout, level=logging.INFO,
                    format="%(asctime)s %(levelname)s %(message)s")

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        logging.info("request: %s", self.path)
        body = b"hello from pyapp\n"
        self.send_response(200)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

if __name__ == "__main__":
    logging.info("pyapp starting on :8000")
    http.server.HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()
```

```ini
# /etc/systemd/system/pyapp.service
[Unit]
Description=Python Demo HTTP Service
After=network.target

[Service]
Type=simple
User=deploy
WorkingDirectory=/opt/pyapp
ExecStart=/usr/bin/python3 /opt/pyapp/server.py
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```shell
# 部署 + 验证日志集成
systemctl daemon-reload
systemctl enable --now pyapp
curl http://127.0.0.1:8000/          # 触发一次请求，产生日志
journalctl -u pyapp -n 10            # 能看到 server.py 打出的 INFO 日志
# 模拟崩溃自动拉起（kill 主进程，看 Restart=on-failure 是否生效）
systemctl kill -s SIGKILL pyapp
sleep 6
systemctl status pyapp               # 应已自动重启回 running
```

## 性能与调优

```text
1. Restart=on-failure 而非 always —— always 连正常退出也重启，on-failure 只拉崩溃的
2. RestartSec 设合理间隔 —— 太短疯狂重启刷日志，太长故障恢复慢（5-10 秒常见）
3. TimeoutStartSec/TimeoutStopSec —— 启动/停止超时时间，防止服务卡住不返回
4. LimitNOFILE —— 调大文件描述符上限，高并发服务（nginx/db）必须配
5. Nice/OOMScoreAdjust —— 调整服务优先级和 OOM 权重
```

```ini
[Service]
ExecStart=/opt/myapp/bin/myapp
Restart=on-failure
RestartSec=10
TimeoutStopSec=30
LimitNOFILE=65536
```

```text
更多调优项：
1. CPUQuota/MemoryMax —— 用 cgroup 限制资源，防单个服务吃满 CPU/内存拖垮整机
2. Nice=-5 —— 提高服务调度优先级（负值高优先级）；OOMScoreAdjust=-500 降低被 OOM 概率
3. TasksMax —— 限制线程/进程数，防 fork 炸弹
4. KillMode=control-group —— 停止时杀整个 cgroup（默认），避免残留子进程
5. Nice/OOMScore 只对关键服务调，别乱调——优先级定错会让其他服务饿死
```

## 安全与权限

```text
1. 独立用户运行 —— User=deploy，别用 root，最小权限
2. 沙盒加固 —— NoNewPrivileges=yes（禁止提权）、PrivateTmp=yes（私有 /tmp）、ProtectSystem=strict（只读系统目录）
3. 资源限制 —— CPUQuota/MemoryMax 用 cgroup 限制，防单个服务拖垮系统
4. 环境变量安全 —— 别在 Environment= 里写明文密码，用 EnvironmentFile= 引用权限受控的文件
5. 可写目录最小化 —— ReadWritePaths 显式指定可写路径，其余只读
```

```ini
[Service]
User=deploy
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=full
ReadWritePaths=/var/lib/myapp
MemoryMax=512M
```

```text
沙盒指令速查：
NoNewPrivileges=yes      禁止服务再提权（setuid/sudo 失效）
PrivateTmp=yes           独立的 /tmp 和 /var/tmp，防临时文件被其他进程偷看
ProtectSystem=full/strict  系统目录只读（full 保留 /etc /boot /usr 可读，strict 全只读）
ProtectHome=yes          家目录不可见/只读
ReadOnlyPaths=/etc       指定只读路径
ReadWritePaths=/var/lib/myapp  允许写的路径
CapabilityBoundingSet=   裁剪进程能力（默认全给，可收紧）
PrivateDevices=yes       私有 /dev，只留最小设备节点
```

```shell
# 让服务绑定特权端口（<1024）而不用 root
# 用 AmbientCapabilities 授予 CAP_NET_BIND_SERVICE，User= 仍是非 root
systemctl show nginx -p User -p AmbientCapabilities
# 评估一个服务的加固程度，看能加哪些保护
systemd-analyze security myapp
```

## 故障排查

### 服务启动失败 / 反复重启

```shell
# 1. 看退出码和原因
systemctl status myapp
# 2. 看日志（关键，通常直接给出报错）
journalctl -u myapp -n 50
# 3. 验证 ExecStart 命令能否手动跑通
systemctl cat myapp | grep ExecStart
# 4. 检查 Type 是否选对（forking 程序配 simple 会反复重启）
systemctl show myapp -p Type -p MainPID -p SubState
```

### 服务卡在 activating / 起不来但没报错

```shell
# 1. 卡 activating：看是不是 Type 选错或超时
systemctl show myapp -p Type -p TimeoutStartSec -p SubState
# 2. 语法/依赖校验（写错字段、依赖不满足会在这里暴露）
systemd-analyze verify /etc/systemd/system/myapp.service
# 3. 手动以服务同样的方式跑，看是否卡住
sudo -u deploy /opt/myapp/bin/myapp
```

### 环境变量/权限问题导致起不来

```shell
# 1. 环境变量没生效：看最终 ExecStart 展开后的样子
systemctl cat myapp
# 2. 权限问题：用服务同用户手动跑复现
sudo -u deploy /opt/myapp/bin/myapp
# 3. 查 journal 里的 permission denied
journalctl -u myapp -n 50 | grep -i -E 'denied|permission|not found'
```

## 常见问题

```text
Q1: Type 怎么选？
A: 前台运行的程序（Java/Node/Python）用 simple；老式 daemon（自己 fork 后台）用 forking + PIDFile；初始化脚本用 oneshot；启动后能发通知的用 notify。

Q2: 服务启动后 systemd 说 active(exited) 或反复重启？
A: 多半是 Type 选错——会 fork 的程序配了 simple，主进程退了 systemd 以为服务结束。

Q3: 手动能跑，systemd 跑却报找不到文件？
A: systemd 环境精简，PATH 不完整。用绝对路径，配 Environment= 和 WorkingDirectory=。

Q4: Restart=always 和 on-failure 怎么选？
A: always 无论为何退出都重启（含正常退出），on-failure 只拉崩溃/异常退出的。生产服务用 on-failure + RestartSec。

Q5: 服务日志去哪了？怎么统一查？
A: 服务的 stdout/stderr 被 systemd 捕获进 journald，用 journalctl -u 服务名 查。别自己写日志文件，journald 已统一收集，还带时间戳和启动次数过滤。

Q6: ExecStart 里能写管道、重定向吗？
A: 不能，ExecStart 不是 shell 解析，|、>、&& 等 shell 语法无效。要复杂逻辑就包一个脚本，ExecStart 调脚本。

Q7: 为什么服务频繁重启后报「start request repeated too quickly」？
A: systemd 有重启限速（StartLimitIntervalSec/StartLimitBurst，默认 10 秒 5 次），超过就放弃启动。这是保护机制，说明服务有持续崩溃的根因，先 journalctl 排查再启动。
```

## 面试题

```text
1. service 文件的三段分别是什么？
   答：[Unit] 描述和依赖（Description/After/Requires），[Service] 运行定义（Type/ExecStart/Restart），[Install] 自启定义（WantedBy）。

2. Type=simple 和 Type=forking 的区别？
   答：simple 前台运行，ExecStart 进程就是服务主体；forking 程序自己 fork 到后台，父进程退出，systemd 靠 PIDFile 找主进程。

3. 为什么改 service 文件后要 daemon-reload？
   答：systemd 缓存了已加载的单元文件，daemon-reload 让它重新读盘上的配置，否则改动不生效。

4. Restart=always 会有什么问题？
   答：崩溃的服务会进入「启动→崩溃→重启」死循环刷日志。应配合 RestartSec 间隔，并优先排查崩溃根因。

5. Type=oneshot 和 RemainAfterExit 是干嘛的？
   答：oneshot 是执行一次就退出的初始化脚本（如初始化数据库、刷配置），RemainAfterExit=yes 让 systemd 在命令退出后仍把 unit 视为 active，否则退完就是 inactive。

6. 服务的 stdout/stderr 是怎么被 journald 收集的？
   答：systemd 用管道/套接字捕获服务的 stdout/stderr（StandardOutput=journal 默认开启），转发给 systemd-journald，再通过 journalctl 查询，不需要服务自己写日志文件。

7. User= 指定非 root 用户后，服务怎么绑定 80 端口？
   答：用 AmbientCapabilities=CAP_NET_BIND_SERVICE 授予绑定特权端口的能力，同时保持非 root 运行，兼顾最小权限。

8. drop-in 覆盖（service.d/*.conf）有什么用？
   答：在不修改软件包自带 unit 文件的前提下叠加/覆盖配置，软件包升级不会覆盖你的定制，systemctl edit 会自动创建。systemctl cat 能看到合并后的最终配置。
```

## 最佳实践与踩坑记录

### 最佳实践

1. Type 选对：Java/Node 等前台程序用 simple，老式 fork 程序用 forking + PIDFile
2. 生产服务配 Restart=on-failure + RestartSec，崩溃自动拉起但避免疯狂重启
3. 用独立用户跑服务（User=deploy），别用 root
4. 服务日志交给 journald，别自己写文件（journalctl 统一查）
5. 改 service 文件后 systemctl daemon-reload，再 restart
6. 定制配置用 systemctl edit 建 drop-in，别直接改软件包自带文件
7. 写完先 systemd-analyze verify 校验语法，再 daemon-reload + enable --now

### 踩坑记录

```text
坑 1：Type=simple 配了会 fork 的程序，服务反复重启
结论：Type=simple 配 forking 程序，systemd 以为服务秒退，反复重启。
原因：forking 程序的主进程 fork 后退了，simple 模式下 systemd 以为服务结束了。
解法：会 fork 的程序用 Type=forking + PIDFile，前台程序才用 simple。

坑 2：改 service 文件没 daemon-reload
结论：改了 ExecStart，restart 还是跑旧命令。
原因：systemd 缓存了旧单元文件。
解法：改完 systemctl daemon-reload。

坑 3：Restart=always 导致启动即崩溃的服务疯狂重启
结论：服务起不来，systemd 无限重启刷日志。
原因：always 不管为何退出都重启，崩溃服务进入死循环。
解法：用 on-failure + RestartSec 间隔，先排查崩溃原因再启动。

坑 4：环境变量/依赖路径没配，服务起不来
结论：ExecStart 命令手动能跑，systemd 跑却报找不到文件。
原因：systemd 环境精简，PATH 不完整，相对路径/环境变量缺失。
解法：用绝对路径，配 Environment=，WorkingDirectory= 指定工作目录。

坑 5：User= 指定的用户没权限，服务起不来
结论：配了 User=deploy 但服务启动失败报权限错误。
原因：deploy 用户没有该目录/文件的读写权限。
解法：确认运行用户对工作目录、日志、数据目录有权限（chown）。

坑 6：ExecStart 里写了 shell 语法（管道/重定向/&&）不生效
结论：ExecStart 里写 `echo x > /tmp/a.log` 或 `a && b`，服务行为不对或报错。
原因：ExecStart 不是 shell 解析，|、>、&& 是 shell 语法，systemd 直接当参数传给程序。
解法：把复杂逻辑放进脚本，ExecStart 调脚本；或用 ExecStartPre 替代 && 的串联。

坑 7：oneshot 服务没有 RemainAfterExit，状态一直是 inactive
结论：初始化脚本跑完退了，systemctl status 显示 inactive，依赖它的服务认为它没就绪。
原因：oneshot 命令退出后 systemd 默认把 unit 标记为 inactive，除非 RemainAfterExit=yes。
解法：需要「执行完仍算 active」的 oneshot 加 RemainAfterExit=yes。
```
