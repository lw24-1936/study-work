## 概述

Linux 内存分两大类：页缓存（文件内容的缓存，可随时回收）和匿名页（进程运行时数据，不能直接回收、只能换出到 swap）。理解这两类，才能看懂 free 里「used 很高但 available 还很多」的现象——因为 used 里包含了可回收的页缓存。内存不足时内核按「水位线」触发回收：先回收页缓存，再换出匿名页到 swap。

```text
内存两大分类：
1. 页缓存（page cache）—— 文件内容的缓存（读过的文件、写过的数据），可随时回收
2. 匿名页（anonymous page）—— 进程堆栈、动态分配的内存，不能直接回收，只能换出到 swap
关键结论：free 的 used 含页缓存，不代表「内存不够」，available 才是真实可用
```

## 核心概念

### 页缓存

页缓存（page cache）是内核缓存的「文件内容」——进程读文件时，内容先缓存到内存，下次读直接命中（不碰磁盘）；写文件先写缓存，由内核异步刷到磁盘（脏页回收）。好处是加速文件读写、充分利用空闲内存。缺点：缓存占太多内存时，看起来「内存满了」，但这些缓存是可回收的——内存紧张时内核会自动回收页缓存腾空间。

```text
页缓存机制：
1. 读缓存 —— 文件读过的内容缓存，重复读命中内存，不碰磁盘
2. 写缓存 —— 写文件先写缓存（脏页），异步刷盘（pdflush/内核线程）
3. 可回收 —— 内存紧张时优先回收页缓存，不影响进程
```

### Buffer 与 Cache

free 里的 buff/cache 是两种缓存：Buffer 是块设备元数据缓存（如文件系统元数据、inode），Cache 是页缓存（文件内容）。日常不必细究两者区别，把它们统一理解为「可回收的文件缓存」。重点记结论：`free -h` 的 available 列 = free + 可回收的 buff/cache，才是判断「内存够不够」的正确指标。

```text
# 实测（本机 free -h）
$ free -h
               total   used   free  shared  buff/cache  available
内存：          19Gi   10Gi   329Mi  823Mi   9.5Gi       8.7Gi
交换：         8.0Gi    76Mi   7.9Gi
# 关键：used=10Gi（看着很多），但 available=8.7Gi（真实可用还很多）
# 因为 used 里包含了 9.5Gi 的 buff/cache（可回收的页缓存）
```

```text
# 实测（/proc/meminfo 关键项）
MemTotal:     20170620 kB   # 总内存 19.2Gi
MemFree:        337436 kB   # 完全空闲 329Mi
MemAvailable:  9108076 kB   # 可用（含可回收缓存）8.7Gi
Buffers:       1575652 kB   # 块设备元数据缓存 1.5Gi
Cached:        6221412 kB   # 页缓存 5.9Gi
AnonPages:     8858572 kB   # 匿名页 8.4Gi
```

### 匿名页

匿名页是「没有文件对应的内存」——进程的堆、栈、malloc 出来的内存，都属于匿名页。和页缓存（有文件、可回收）不同，匿名页不能直接丢弃（丢了进程数据就没了），只能「换出到 swap」。所以判断「进程实际占用多少内存」看匿名页 + 进程自己的私有内存（RSS），而不是把页缓存算进去。

```text
匿名页 vs 页缓存：
1. 匿名页 —— 进程堆栈/动态内存，无文件对应，只能换出到 swap
2. 页缓存 —— 文件内容缓存，有文件对应，可直接丢弃回收
3. 进程内存 = 匿名页 + 私有页，页缓存是共享的、不算进程独占
```

### 内存水位线

内核用「水位线」（watermark）管理内存回收的触发时机：min、low、high 三个水位线（对应 /proc/zoneinfo 里的 wmarks）。内存低于 low 水位 → 后台回收（kswapd 线程开始回收）；低于 min 水位 → 直接回收（分配内存的进程自己回收，可能阻塞）；高于 high 水位 → 停止回收。min_free_kbytes 参数设置 min 水位（保留给紧急情况的空闲内存）。

```text
# 实测（本机 min 水位）
$ cat /proc/sys/vm/min_free_kbytes
67584
# min 水位约 66MB——低于它就触发紧急回收
```

```text
三个水位线：
1. min —— 最低水位，低于它直接回收（同步、可能阻塞分配）
2. low —— 低水位，低于它后台回收（kswapd 异步回收）
3. high —— 高水位，高于它停止回收
```

### 回收机制

内存紧张时内核按「代价从小到大」回收：先回收可回收的页缓存（干净页直接丢弃、脏页先刷盘再丢弃），还不够就换出匿名页到 swap（代价高，因为要写磁盘），再不够就触发 OOM Killer 杀进程。回收由两个机制驱动：kswapd 线程（后台、异步、水位低时）和直接回收（分配时内存不够、同步、可能阻塞）。

```text
回收顺序（代价递增）：
1. 干净页缓存 —— 直接丢弃（没写过，最便宜）
2. 脏页缓存 —— 刷盘后丢弃（要写磁盘）
3. 匿名页 —— 换出到 swap（写 swap，代价高）
4. OOM Killer —— 杀进程（最后手段）
```

## 工作原理

内存回收是「水位线驱动」的闭环：kswapd 内核线程周期性检查水位，空闲内存低于 low 水位时开始后台回收；若分配内存时发现已低于 min 水位，则触发「直接回收」（当前进程同步回收，可能阻塞）。回收按代价排序——先丢弃干净页缓存，再刷脏页丢弃，再换出匿名页到 swap。当物理内存和 swap 都耗尽，回收也救不了，才轮到 OOM Killer。

```text
回收触发流程：
空闲内存 < low 水位 → kswapd 后台异步回收
空闲内存 < min 水位 → 分配进程直接回收（同步，阻塞）
回收顺序：干净页缓存 → 脏页缓存 → 匿名页换出 → OOM Killer
```

## 常用命令与配置

```shell
free -h                     # 看总量 + available
cat /proc/meminfo            # 详细内存分类
vmstat 1 5                   # 动态看 si/so（换出）和 free 变化
echo 3 > /proc/sys/vm/drop_caches   # 释放页缓存（应急）
sysctl vm.min_free_kbytes    # 看 min 水位
```

```text
判断内存压力：available 低 + si/so 持续非 0 = 真紧张
页缓存被回收（cache 下降）是正常回收，不是故障
```

## 配置文件解析

内存回收相关内核参数都在 /proc/sys/vm/，持久化写 /etc/sysctl.conf：

```text
vm.min_free_kbytes = 67584        # min 水位，保留空闲内存（防死锁）
vm.dirty_ratio = 20               # 脏页占内存 20% 时同步刷盘
vm.dirty_background_ratio = 10    # 脏页占 10% 时后台刷盘
vm.dirty_expire_centisecs = 3000  # 脏页存活 30s 后刷盘
vm.swappiness = 60                # 换出积极度
vm.vfs_cache_pressure = 100       # 回收 inode/dentry 缓存的积极度
```

```shell
sysctl -w vm.dirty_ratio=10       # 临时调整
echo 'vm.dirty_ratio=10' >> /etc/sysctl.conf   # 持久化
```

## 应用场景实战

### 场景一：判断服务器内存到底够不够

```shell
# 1. 看 available（真实可用），别只看 free
free -h
# 2. available 长期低于 10% 才说明内存紧张
# 3. 看是否在换出（swap 的 si/so）
vmstat 1 5
# 4. 看谁占内存
ps aux --sort=-%mem | head
```

### 场景二：手动释放页缓存（内存紧张时应急）

```shell
# 查看当前缓存
free -h
# 释放页缓存（echo 3 释放 pagecache + dentries + inodes）
sync
echo 3 > /proc/sys/vm/drop_caches
free -h    # 观察缓存释放
```

## 性能与调优

```text
1. 别动 drop_caches —— 缓存重建要回源读磁盘，反而慢，只应急用
2. 脏页参数 —— 写入密集型调低 dirty_ratio，让脏页及时刷盘，避免集中刷盘打满 IO
3. vfs_cache_pressure —— 大量小文件的机器调高（>100）加速回收 dentry 缓存
4. swappiness —— 数据库调低（10-20），尽量用物理内存
5. 内存监控 —— 持续观察 available 和 si/so，别等 OOM 才发现
```

## 安全与权限

```text
1. drop_caches 要 root —— 释放缓存影响全局，只 root 可写 /proc/sys/vm/drop_caches
2. /proc/meminfo 泄露内存信息 —— 默认所有用户可读，含内存布局信息（低风险）
3. 共享内存的匿名页 —— 多进程共享的匿名页（如共享内存）回收时要注意同步
4. 别让单进程吃满 —— 用 cgroups 限制，防止一个进程的匿名页占光内存触发全局 OOM
```

## 故障排查

### 内存紧张 / 频繁换出

```shell
# 1. 看 available 和 swap 用量
free -h
# 2. 看换出趋势
vmstat 1 5
# 3. 找匿名页大户
ps aux --sort=-%mem | head
```

### 脏页堆积导致 IO 飙升

```shell
# 1. 看脏页数量
grep -E 'Dirty|Writeback' /proc/meminfo
# 2. 看当前脏页参数
sysctl vm.dirty_ratio vm.dirty_background_ratio
# 3. 写入密集场景调低参数，及时刷盘
```

## 常见问题

```text
Q1: 为什么 used 很高但 available 还很多？
A: used 里包含可回收的页缓存（buff/cache）。available = free + 可回收缓存，才是真实可用，看它别只看 used。

Q2: 页缓存可以回收吗？
A: 可以。干净页缓存直接丢弃，脏页缓存先刷盘再丢弃。内存紧张时内核自动回收页缓存腾空间。

Q3: 匿名页为什么不能直接回收？
A: 匿名页是进程的堆栈/动态内存，没有文件对应，丢了数据就没了。只能换出到 swap（写磁盘），代价比回收页缓存高。

Q4: kswapd 是什么？
A: 内核的后台回收线程，空闲内存低于 low 水位时异步回收页缓存和匿名页，避免等到内存耗尽才回收。
```

## 面试题

```text
1. 页缓存和匿名页的区别？
   答：页缓存是文件内容缓存（有文件、可直接回收），匿名页是进程堆栈/动态内存（无文件、只能换出到 swap）。

2. 内存回收的顺序？
   答：先回收干净页缓存（丢弃）→ 脏页缓存（刷盘后丢弃）→ 匿名页换出到 swap → OOM Killer 杀进程，代价递增。

3. free 的 available 是什么意思？
   答：available = free + 可回收的 buff/cache，代表「不给进程造成压力时能拿出的内存」，是判断内存够不够的正确指标。

4. 水位线（watermark）的作用？
   答：min/low/high 三个水位线控制回收时机——低于 low 后台回收（kswapd），低于 min 直接回收，高于 high 停止。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 判断内存够不够看 available，不是 free、也不是 used
2. 页缓存是「用了等于白用」——空闲内存本来就会被缓存占满，正常现象
3. 内存持续紧张看 swap 的 si/so，持续换出说明真不够、该加内存
4. drop_caches 只用于应急/测试，别当日常优化（缓存重建反而慢）
5. 进程内存看 RSS（ps/top），别把共享的页缓存算进某个进程

### 踩坑记录

```text
坑 1：看 free 的 free 列以为内存不够
结论：free 只有 300M，以为内存快爆了。
原因：free 列不含可回收的页缓存，available 才是真实可用。
解法：看 available 列（free -h），或 echo 3 > drop_caches 后观察。

坑 2：把 buff/cache 当「内存泄漏」
结论：缓存越涨越高，以为程序泄漏内存。
原因：页缓存会尽量占满空闲内存，这是设计行为不是泄漏。
解法：看进程 RSS 是否持续增长，缓存涨是正常的（可回收）。

坑 3：手动 drop_caches 导致性能骤降
结论：echo 3 > drop_caches 后，数据库/IO 变慢。
原因：缓存被清空，后续 IO 全部回源读磁盘，重建缓存需要时间。
解法：drop_caches 只应急用，日常别动；内存管理交给内核。

坑 4：脏页太多导致 IO 飙升
结论：写入峰值时 io 突然飙升、系统卡顿。
原因：脏页累积太多，内核集中刷盘，IO 打满。
解法：调低 vm.dirty_ratio/dirty_background_ratio，让脏页及时刷盘。

坑 5：匿名页持续增长不回收，怀疑内存泄漏
结论：进程 RSS 一直涨，swap 也用满了。
原因：可能真泄漏（free 没释放），也可能是有意缓存（如 JVM 堆）。
解法：先确认是「泄漏」还是「合理占用」（JVM 看堆、应用看内存曲线），再定位。
```
