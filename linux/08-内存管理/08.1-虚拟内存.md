## 概述

虚拟内存让每个进程拥有「独立的、连续的、假想的大地址空间」，实际数据分散在物理内存和磁盘里。核心机制：虚拟地址空间（进程看到的假象）、分页（内存按固定大小页管理）、页表（虚拟地址到物理地址的映射）、TLB（页表缓存，加速翻译）、mmap（文件映射到内存）。虚拟内存带来隔离（进程互不干扰）和「内存超售」（物理内存不够时换出到磁盘）。

```text
虚拟内存五要素：
1. 虚拟地址空间 —— 每个进程独立的大地址空间（64 位系统可达 EB 级）
2. 分页 —— 内存按 4KB（通常）页管理，是分配/换页的基本单位
3. 页表 —— 虚拟地址 → 物理地址的映射表，每个进程一份
4. TLB —— 页表的高速缓存，加速地址翻译（缺页时性能骤降）
5. mmap —— 把文件/设备映射到进程地址空间，像访问内存一样访问文件
```

## 虚拟地址空间

每个进程有独立的虚拟地址空间——进程「以为」自己独占一大块连续内存，实际由内核映射到分散的物理页。好处：隔离（进程 A 碰不到进程 B 的内存）、安全（地址空间随机化 ASLR 防攻击）、简化（程序不用关心物理内存布局）。64 位进程的地址空间分用户态（低地址）和内核态（高地址）两部分。

```shell
# 看进程的虚拟地址空间布局
cat /proc/self/maps
```

```text
# /proc/self/maps 结构（示意）
地址范围        权限  偏移  设备 inode  路径
00400000-...   r-xp  0     08:01 xxxx   /usr/bin/cat   # 代码段
...            rw-p  ...                          [heap]   # 堆
...            rw-p  ...                          [stack]  # 栈
# 每行是一段映射：代码段、数据段、堆、栈、动态库、匿名映射
```

## 分页

分页把内存（物理和虚拟）都切成固定大小的「页」（通常 4KB）。虚拟内存和物理内存之间按「页」为单位映射和交换——不是按字节、按文件，而是按页。分页的好处：内存管理粒度统一、换页（page out）到磁盘是按页、缺页（page fault）也是按页。大页（HugePage，2MB/1GB）能减少页表项、提升大内存应用性能。

```shell
# 查看页大小
getconf PAGESIZE         # 通常 4096（4KB）
grep Hugepagesize /proc/meminfo    # 大页大小
```

```text
# 实测
$ getconf PAGESIZE
4096
# 默认页 4KB，内存按 4KB 一页管理
```

## 页表与 TLB

页表是「虚拟页 → 物理页」的映射表，每个进程一份，存在内存里。CPU 每次访问内存都要查页表翻译地址（虚拟→物理），这个翻译很频繁，于是有了 TLB（Translation Lookaside Buffer）——页表的高速缓存，存最近用过的映射。TLB 命中就快，未命中（TLB miss）要去查页表、甚至触发缺页，性能骤降。这也是「大页能提升性能」的原因：同样的 TLB 能覆盖更多内存。

```text
页表与 TLB：
1. 页表 —— 虚拟地址到物理地址的映射表，多级结构（减少占用）
2. TLB —— 页表的高速缓存（CPU 内），加速地址翻译
3. TLB miss —— 缓存未命中，要查页表，慢
4. 缺页 page fault —— 页不在物理内存，要从磁盘换入，最慢
```

## 内存映射 mmap

mmap 把文件（或设备）映射到进程的虚拟地址空间，之后访问内存地址就等于读写文件——由内核负责把改动同步回磁盘。相比 read/write（要拷贝到用户缓冲区），mmap 减少了一次拷贝（零拷贝的关键技术之一）。用途：高效文件读写、进程间共享内存、加载动态库。Java 的 MappedByteBuffer、Nginx 的 sendfile 底层都用了 mmap。

```text
mmap 优势与用途：
1. 零拷贝 —— 文件直接映射到进程地址空间，少一次内核→用户拷贝
2. 用途 —— 高效文件读写、共享内存、动态库加载、sendfile 零拷贝
```

```shell
# 用 dd 或 python 做 mmap 文件映射（示意）
python3 -c "
import mmap
with open('/tmp/test.txt','r+b') as f:
    mm = mmap.mmap(f.fileno(), 0)
    print(mm.readline())
    mm.close()
"
```

## 应用场景实战

### 场景一：看一个进程的内存映射，理解它的内存构成

```shell
# 1. 看进程的地址空间映射
cat /proc/$(pgrep -f nginx | head -1)/maps | head -20
# 2. 看堆/栈/共享库各自占多少
cat /proc/$(pgrep -f nginx | head -1)/smaps | grep -E '^(Size|Rss)' | head
```

### 场景二：大内存应用启用大页提升性能

```shell
# 1. 查看大页支持
grep Huge /proc/meminfo
# 2. 配置大页数量（2MB 大页）
sysctl vm.nr_hugepages=1024
# 3. 应用使用大页（需应用支持，如 JVM -XX:+UseLargePages）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 大内存应用（数据库/JVM）考虑大页，减少 TLB miss、提升性能
2. 高频读写大文件用 mmap，比 read/write 少一次拷贝
3. 别用「free 的 free 列」判断内存够不够，要看 available（含可回收缓存）
4. 理解缺页和 TLB miss 是内存性能的关键指标，配合 perf 分析
5. 进程内存映射看 /proc/<pid>/maps 和 smaps，比 ps 的 RSS 更细

### 踩坑记录

```text
坑 1：mmap 映射大文件后内存暴涨
结论：mmap 一个 10G 文件，进程内存占用飙升。
原因：mmap 建立映射时可能触发大量缺页，把文件内容读进页缓存。
解法：大文件 mmap 用 MAP_NORESERVE 或按需访问，别一次全读。

坑 2：mmap 文件映射后修改没落盘
结论：mmap 改了内容，以为会自动写回，结果文件没更新。
原因：mmap 的改动先改内存页，回写是异步的（脏页回收）。
解法：关键数据 msync 显式刷盘，别依赖异步回写。

坑 3：大页配了应用没生效
结论：设了 nr_hugepages，应用内存占用没变化。
原因：应用没显式启用大页（JVM 要 -XX:+UseLargePages），或没权限。
解法：确认应用支持大页并显式开启，必要时调整内核参数。

坑 4：把虚拟内存（VSZ）当实际占用（RSS）看
结论：ps 里 VSZ 几十 G 以为内存爆了。
原因：VSZ 是虚拟地址空间大小（含未提交的），RSS 才是实际物理内存。
解法：看内存占用用 RSS（或 top 的 RES），别被 VSZ 吓到。

坑 5：页大小和文件系统块大小混淆
结论：以为改 PAGESIZE 能优化文件 IO。
原因：页是内存管理单位，文件系统块是磁盘 IO 单位，两回事。
解法：内存优化看页/大页，磁盘 IO 优化看文件系统块和调度器。
```
