## 概述

虚拟内存让每个进程拥有「独立的、连续的、假想的大地址空间」，实际数据分散在物理内存和磁盘里。核心机制：虚拟地址空间（进程看到的假象）、分页（内存按固定大小页管理）、页表（虚拟地址到物理地址的映射）、TLB（页表缓存，加速翻译）、mmap（文件映射到内存）。虚拟内存带来隔离（进程互不干扰）和「内存超售」（物理内存不够时换出到磁盘）。

```text
虚拟内存五要素：
1. 虚拟地址空间 —— 每个进程独立的大地址空间（64 位系统可达 EB 级）
2. 分页 —— 内存按 4KB（通常）页管理，是分配/换页的基本单位
3. 页表 —— 虚拟地址 → 物理地址的映射表，每个进程一份
4. TLB —— 页表的高速缓存，加速地址翻译（缺页时性能骤降）
5. mmap —— 把文件/设备映射到进程地址空间，像访问内存一样访问文件
```

虚拟内存解决三个实际问题：隔离（进程 A 写越界不影响进程 B）、安全（ASLR 随机化地址防攻击）、超售（进程申请的总内存可以超过物理内存，按需分配）。代价是地址翻译有开销——这是 TLB、大页存在的根本原因。理解虚拟内存的入口是 `/proc/<pid>/maps`：它把进程「以为」的内存布局原样展示出来。

## 核心概念

### 虚拟地址空间

每个进程有独立的虚拟地址空间——进程「以为」自己独占一大块连续内存，实际由内核映射到分散的物理页。好处：隔离（进程 A 碰不到进程 B 的内存）、安全（地址空间随机化 ASLR 防攻击）、简化（程序不用关心物理内存布局）。64 位进程的地址空间分用户态（低地址）和内核态（高地址）两部分。

为什么需要它：如果没有虚拟地址，进程直接操作物理地址，一个进程写坏内存会影响整个系统，也无法同时运行多个程序。虚拟地址空间让每个进程的地址从 0 开始、互不重叠，内核负责把「虚拟页」翻译成「物理页」。

```shell
# 看进程的虚拟地址空间布局
cat /proc/self/maps
```

```text
# /proc/self/maps 结构（示意）
地址范围        权限  偏移  设备 inode  路径
00400000-...   r-xp  0     08:01 xxxx   /usr/bin/cat   # 代码段
...            rw-p  ...                          [heap]   # 堆
...            rw-p  ...                          [stack]  # 栈
# 每行是一段映射：代码段、数据段、堆、栈、动态库、匿名映射
```

用户态进程的典型布局（从低地址到高地址）：代码段 text（只读可执行）→ 数据段 data/bss（全局变量）→ 堆 heap（malloc 向上增长）→ 动态库映射区（libc、ld）→ 栈 stack（向下增长）→ vdso/vsyscall（内核映射的快速系统调用页）。每段是一段虚拟地址区间，对应一段映射。

```text
虚拟地址空间要点：
1. 进程看到的是「连续的假象」，实际映射到分散的物理页
2. 布局：text → data/bss → heap → mmap 区 → stack → vdso
3. VSZ（虚拟大小）含未提交的映射，RSS 才是真实物理占用
4. 64 位地址空间大部分是空洞（未映射），访问空洞地址触发段错误
```

易错点：`ps` 的 VSZ 列常是几十 GB，容易误判为「内存爆了」——那是虚拟地址空间大小（含预留但未提交的），真实占用看 RSS。另一个易错点：把「地址空间连续」误解为「物理内存连续」——虚拟连续不代表物理连续，这正是分页存在的意义。

### 分页

分页把内存（物理和虚拟）都切成固定大小的「页」（通常 4KB）。虚拟内存和物理内存之间按「页」为单位映射和交换——不是按字节、按文件，而是按页。分页的好处：内存管理粒度统一、换页（page out）到磁盘是按页、缺页（page fault）也是按页。大页（HugePage，2MB/1GB）能减少页表项、提升大内存应用性能。

为什么按页不按字节：按字节管理映射表会大到无法承受（每个字节一条映射），按页则只需「页号 → 页帧号」的映射，页表规模可控。页大小是「管理粒度」和「内部碎片」的权衡：页太大浪费内存（一个变量独占一页），页太小页表项太多。4KB 是历史权衡结果。

```shell
# 查看页大小
getconf PAGESIZE         # 通常 4096（4KB）
grep Hugepagesize /proc/meminfo    # 大页大小
```

```text
# 实测
$ getconf PAGESIZE
4096
# 默认页 4KB，内存按 4KB 一页管理
```

```shell
# 查看大页与透明大页状态
grep Huge /proc/meminfo                     # 大页各项（Total/Free/Rsvd）
cat /sys/kernel/mm/transparent_hugepage/enabled   # THP 是否开启
```

```text
分页要点：
1. 页是内存管理的统一单位：分配、映射、换页、缺页都按页
2. 默认页 4KB；大页 2MB（HugePage）或 1GB，减少页表项
3. THP（透明大页）—— 内核自动合并小页成大页，应用无感知
4. 页大小是「管理粒度 vs 内部碎片」的权衡
```

易错点：页（内存管理单位）和文件系统块（磁盘 IO 单位，常 4KB）是两套东西，改 PAGESIZE 不会优化磁盘 IO。大页不是开箱即用——要么应用显式 mmap（`MAP_HUGETLB`），要么依赖 THP，JVM 还要 `-XX:+UseLargePages`。

### 页表与 TLB

页表是「虚拟页 → 物理页」的映射表，每个进程一份，存在内存里。CPU 每次访问内存都要查页表翻译地址（虚拟→物理），这个翻译很频繁，于是有了 TLB（Translation Lookaside Buffer）——页表的高速缓存，存最近用过的映射。TLB 命中就快，未命中（TLB miss）要去查页表、甚至触发缺页，性能骤降。这也是「大页能提升性能」的原因：同样的 TLB 能覆盖更多内存。

为什么页表要多级：64 位地址空间巨大，如果只有一级页表，每个进程需要上百万个页表项（还大部分是空洞）。多级页表（x86-64 常用 4 级或 5 级）按需分配，只有用到的地址区间才建立中间页表，大幅节省内存。翻译路径：PGD → PUD → PMD → PTE（4 级），每一级各查一次。

```text
页表与 TLB：
1. 页表 —— 虚拟地址到物理地址的映射表，多级结构（减少占用）
2. TLB —— 页表的高速缓存（CPU 内），加速地址翻译
3. TLB miss —— 缓存未命中，要查页表，慢
4. 缺页 page fault —— 页不在物理内存，要从磁盘换入，最慢
```

```shell
# 用 perf 看 TLB miss 和缺页次数
perf stat -e dTLB-load-misses,dTLB-loads,page-faults,minor-faults ls -R /usr/share > /dev/null
```

```text
地址翻译代价（从快到慢）：
TLB 命中（约 1 个周期）→ TLB miss 查页表（几十~上百周期）→ 缺页换入（微秒~毫秒级）
```

易错点：TLB miss 不等于缺页——TLB miss 只是缓存没命中，页可能还在内存里（查页表就能拿到物理页）；缺页是页本身不在物理内存，要换入。多核下 TLB 要跨核失效（TLB shootdown），改页表权限会触发一次所有核的 TLB 刷新，频繁 mprotect 会拖慢多线程程序。

### 内存映射 mmap

mmap 把文件（或设备）映射到进程的虚拟地址空间，之后访问内存地址就等于读写文件——由内核负责把改动同步回磁盘。相比 read/write（要拷贝到用户缓冲区），mmap 减少了一次拷贝（零拷贝的关键技术之一）。用途：高效文件读写、进程间共享内存、加载动态库。Java 的 MappedByteBuffer、Nginx 的 sendfile 底层都用了 mmap。

为什么能少一次拷贝：read 的路径是「磁盘 → 页缓存（内核）→ 用户缓冲区」，mmap 直接把页缓存映射进用户地址空间，进程直接读写页缓存，省掉「内核 → 用户」这次拷贝。写文件的回写（脏页刷盘）也由内核异步完成，进程无需关心。

```text
mmap 优势与用途：
1. 零拷贝 —— 文件直接映射到进程地址空间，少一次内核→用户拷贝
2. 用途 —— 高效文件读写、共享内存、动态库加载、sendfile 零拷贝
```

```shell
# 用 dd 或 python 做 mmap 文件映射（示意）
python3 -c "
import mmap
with open('/tmp/test.txt','r+b') as f:
    mm = mmap.mmap(f.fileno(), 0)
    print(mm.readline())
    mm.close()
"
```

```shell
# C 语言 mmap 关键参数（示意，编译需 gcc）
# mmap(addr, length, prot, flags, fd, offset)
# prot:  PROT_READ | PROT_WRITE          # 读写权限
# flags: MAP_SHARED（改动写回文件/共享） | MAP_PRIVATE（私有，写时复制）
#        MAP_ANONYMOUS（匿名映射，不关联文件，用于 malloc 大块内存）
# 收尾：msync 显式刷盘，munmap 解除映射
```

```text
mmap 关键区分：
1. MAP_SHARED —— 多进程共享同一映射，改动写回文件（共享内存）
2. MAP_PRIVATE —— 写时复制（COW），改动不写回文件（如 fork 后的内存）
3. MAP_ANONYMOUS —— 匿名映射，malloc 大块内存的底层实现
```

易错点：mmap 建立映射时可能触发大量缺页，把文件内容读进页缓存，表现为「进程内存暴涨」；改动是异步回写的，关键数据要 `msync` 显式刷盘；映射的文件被截断后访问会触发 SIGBUS（不是段错误），要处理。

## 工作原理

CPU 访问内存的完整翻译流程：程序给出虚拟地址 → 硬件拆出页号和页内偏移 → 先查 TLB（命中直接得物理地址）→ TLB miss 则查多级页表 → 页表项指向物理页 → 组合成物理地址访问内存。若页表项显示「页不在物理内存」（缺页），触发 page fault，内核从磁盘/swap 把页换入，再重新执行该指令。

```text
地址翻译流程：
虚拟地址 → 拆页号+偏移 → 查 TLB（命中即得物理地址）
         → TLB miss → 查多级页表 → 页表项 → 物理页
         → 页不在内存 → page fault → 内核换入 → 重试
```

64 位虚拟地址的拆分（x86-64 4 级页表，示意）：高 16 位未用（符号扩展）→ PGD 9 位 → PUD 9 位 → PMD 9 位 → PTE 9 位 → 页内偏移 12 位（4KB 页）。每级页表项指向下一级页表的物理地址，最后 PTE 存物理页帧号 + 权限位（读/写/执行/用户态）。

```text
多级页表翻译（x86-64 4 级）：
虚拟地址 = [PGD 索引 | PUD 索引 | PMD 索引 | PTE 索引 | 页内偏移]
每一级查一张页表，取下一级页表基址，最终 PTE 给出物理页帧号
权限位（PTE 里）：可读 / 可写 / 可执行 / 用户态可访问
```

缺页（page fault）分两类：次缺页（minor fault，页已在内存、只是页表没建立，如写时复制）和主缺页（major fault，页要从磁盘/swap 换入）。性能上 major fault 才是真开销，minor fault 只是页表维护。进程的缺页统计在 `/proc/<pid>/stat` 的第 10、12 字段。

```shell
# 看进程的缺页次数（第 10=minor，第 12=major）
awk '{print "minor_faults="$10, "major_faults="$12}' /proc/self/stat
```

## 常用命令与配置

```shell
getconf PAGESIZE            # 页大小
cat /proc/<pid>/maps        # 进程地址空间映射
cat /proc/<pid>/smaps       # 各映射的详细内存（Size/Rss）
pmap -x <pid>               # 进程内存映射汇总
grep Huge /proc/meminfo     # 大页信息
```

```text
看虚拟内存用 /proc/<pid>/maps（布局）和 smaps（详细用量），
pmap 是它们的友好封装，比 ps 的 RSS 更细
```

```shell
cat /proc/<pid>/smaps_rollup     # 进程内存汇总（Pss/Private/Shared 一页）
awk '{print $10, $12}' /proc/<pid>/stat   # minor/major 缺页次数
grep -E '^(VmSize|VmRSS|VmData|VmStk)' /proc/<pid>/status   # VSZ/RSS/数据段/栈
perf stat -e page-faults <命令>   # 统计命令的缺页
getconf PAGESIZE                  # 页大小
```

```text
smaps vs smaps_rollup：
smaps 逐段列出每个映射的 Size/Rss/Pss（内存归属统计用 Pss，按共享比例折算）
smaps_rollup 直接给汇总，看进程总内存更快
```

## 配置文件解析

虚拟内存相关参数集中在 /proc/sys/vm/，可通过 /etc/sysctl.conf 持久化：

```text
vm.nr_hugepages = 1024         # 预留大页数量（2MB/页）
vm.overcommit_memory = 0       # 内存超售策略（0 启发式/1 总是/2 严格）
vm.min_free_kbytes = 67584     # min 水位，保留给紧急情况的空闲内存
vm.swappiness = 60             # 换出积极度
```

```shell
sysctl vm.nr_hugepages=1024    # 临时调整大页
sysctl -p                      # 从 /etc/sysctl.conf 加载持久化配置
```

```text
与虚拟内存相关的其它参数：
vm.max_map_count = 65530       # 单个进程最大映射段数（mmap 数量上限）
vm.mmap_min_addr = 65536       # mmap 最低地址，防 NULL 指针映射攻击
kernel.randomize_va_space = 2  # ASLR 强度（0 关/1 部分/2 全开）
vm.nr_overcommit_hugepages     # 透明大页的超售预留
```

```shell
sysctl vm.max_map_count=262144   # 大量 mmap 的应用（如 Elasticsearch）调高
cat /proc/sys/vm/max_map_count   # 查看当前值
```

## 应用场景实战

### 场景一：看一个进程的内存映射，理解它的内存构成

```shell
# 1. 看进程的地址空间映射
cat /proc/$(pgrep -f nginx | head -1)/maps | head -20
# 2. 看堆/栈/共享库各自占多少
cat /proc/$(pgrep -f nginx | head -1)/smaps | grep -E '^(Size|Rss)' | head
```

```shell
# 3. 汇总看进程的 Pss（按共享比例折算的真实占用）
cat /proc/$(pgrep -f nginx | head -1)/smaps_rollup
# 4. 用 pmap 看每段映射和 RSS
pmap -x $(pgrep -f nginx | head -1) | head -30
```

场景解读：maps 第一列是虚拟地址区间（连续假象），第二列权限，最后是映射来源。堆 `[heap]`、栈 `[stack]`、动态库（libc.so、ld.so）各占一段。Pss（Proportional Set Size）把共享库内存按共享进程数折算，比 RSS 更准确反映单个进程「摊到」的内存——排查「谁吃了内存」用 Pss 而不是 RSS。

### 场景二：大内存应用启用大页提升性能

```shell
# 1. 查看大页支持
grep Huge /proc/meminfo
# 2. 配置大页数量（2MB 大页）
sysctl vm.nr_hugepages=1024
# 3. 应用使用大页（需应用支持，如 JVM -XX:+UseLargePages）
```

```shell
# 4. JVM 启用大页（需预留大页后重启应用）
java -XX:+UseLargePages -Xms8g -Xmx8g -jar app.jar
# 5. 验证大页被使用（HugePages_Free 下降）
grep -E 'HugePages_(Total|Free|Rsvd)' /proc/meminfo
```

场景解读：1024 个 2MB 大页 = 2GB 预留内存。大页启动后这部分内存被锁定（不会被换出），所以要预先规划好用量，别留太多浪费内存、也别留太少导致应用申请大页失败。

### 场景三：诊断「内存明明够，程序却报 Cannot allocate memory」

```shell
# 1. 确认物理内存和虚拟内存都够
free -h
# 2. 查进程映射段数是否触及 max_map_count 上限
cat /proc/sys/vm/max_map_count
grep -c '' /proc/<pid>/maps    # 该进程当前的映射段数
# 3. 查是否 overcommit 严格模式下申请被拒（CommitLimit 耗尽）
cat /proc/sys/vm/overcommit_memory
grep -E 'CommitLimit|Committed_AS' /proc/meminfo
```

```shell
# 4. 确认是「映射段太多」就调高上限
sysctl vm.max_map_count=262144
```

场景解读：「Cannot allocate memory」不一定是物理内存不够，常见两种：一是 mmap 段数超过 `max_map_count`（大量小映射，如 Elasticsearch 的 Lucene 索引）；二是 `overcommit_memory=2` 时 `Committed_AS` 逼近 `CommitLimit`，内核拒绝新的虚拟内存申请。先看这两个再怀疑物理内存。

## 性能与调优

```text
1. 大页减少 TLB miss —— 数据库/JVM 用大页，同样 TLB 覆盖更多内存，减少地址翻译开销
2. 大文件读写用 mmap —— 少一次拷贝，但注意大文件映射的缺页开销
3. 关注缺页 —— perf stat 看 page-faults，缺页多说明频繁换入，内存不够或访问模式差
4. 进程内存看 RSS 不看 VSZ —— VSZ 是虚拟地址空间（含未提交），RSS 才是真实占用
5. 内存布局敏感 —— 大数组连续访问（顺序）比随机跳转快，缓存/TLB 友好
```

```text
6. 用 perf 分 TLB miss 和缺页 —— dTLB-load-misses 高说明地址翻译瓶颈，major-faults 高说明内存不够
7. THP 适合顺序大内存，随机小访问可能反而慢 —— THP 有合并/拆分的开销，延迟敏感场景按需关闭
8. mmap 顺序读大文件性能好，随机小块读反而比 read 慢（缺页频繁）
```

```shell
# 区分 TLB miss 和缺页
perf stat -e dTLB-load-misses,dTLB-loads,page-faults,major-faults <命令>
```

## 安全与权限

```text
1. ASLR 地址随机化 —— 内核随机化堆/栈/库的基址，防缓冲区溢出攻击（/proc/sys/kernel/randomize_va_space）
2. /proc/<pid>/maps 泄露 —— 映射信息含地址布局，默认仅属主和 root 可读
3. mmap 共享内存权限 —— 共享映射的文件权限决定其他进程能否读写
4. 别把敏感数据 mmap 到共享区域 —— 共享映射可被其他进程看到
```

```text
5. mmap_min_addr 防 NULL 映射 —— 内核拒绝映射到低于 mmap_min_addr 的地址，防空指针解引用攻击
6. 锁定内存（mlock）防换出 —— 敏感数据（密钥）用 mlock 锁在内存，避免换出到 swap 被读
7. W^X（可写不可执行）—— 现代内核默认数据页不可执行，防 shellcode 注入
```

```shell
cat /proc/sys/kernel/randomize_va_space   # 看 ASLR 强度（2 = 全开）
cat /proc/sys/vm/mmap_min_addr            # 看 mmap 最低地址（默认 65536）
```

## 故障排查

### 内存占用异常 / 缺页频繁

```shell
# 1. 看进程内存映射分布，定位异常段
pmap -x <PID> | tail
# 2. 看系统缺页情况
vmstat 1 5    # 关注 bi/bo 和 si/so
# 3. 用 perf 统计缺页
perf stat -e page-faults <命令>
```

### mmap 映射后内存暴涨

```shell
# 1. 看进程 RSS 和映射大小差异
ps -o pid,rss,vsz,cmd -p <PID>
# 2. 看具体哪个映射占得多
cat /proc/<PID>/smaps | grep -E '^(Size|Rss)' | head
```

### 报「Cannot allocate memory」但内存充足

```shell
# 1. 查映射段数是否到上限
grep -c '' /proc/<PID>/maps
cat /proc/sys/vm/max_map_count
# 2. 查 overcommit 是否严格限制
grep -E 'CommitLimit|Committed_AS' /proc/meminfo
# 3. 查系统级内存 cgroup 限制
cat /sys/fs/cgroup/memory.max 2>/dev/null
```

## 常见问题

```text
Q1: VSZ 和 RSS 有什么区别？
A: VSZ 是虚拟地址空间大小（含未提交的映射，看着很大），RSS 是实际占用的物理内存。判断占用看 RSS。

Q2: 大页为什么能提升性能？
A: 大页（2MB/1GB）页表项更少，同样的 TLB 能覆盖更多内存，减少 TLB miss 和地址翻译开销，大内存应用收益明显。

Q3: mmap 和 read/write 有什么区别？
A: mmap 把文件映射到地址空间，访问内存即读写文件，少一次内核→用户拷贝；read/write 要显式拷贝到用户缓冲区。mmap 更省拷贝但管理复杂。

Q4: 缺页（page fault）是坏事吗？
A: 不一定。首次访问新分配的页、换回被换出的页都会缺页，属正常；但频繁缺页说明内存紧张或访问模式差，影响性能。

Q5: TLB miss 和缺页是一回事吗？
A: 不是。TLB miss 只是地址翻译缓存没命中，页可能还在物理内存，查页表即可；缺页是页本身不在内存，要换入（代价高得多）。

Q6: 次缺页（minor fault）和主缺页（major fault）的区别？
A: minor fault 是页已在内存、只是页表没建立（如写时复制），几乎零成本；major fault 要从磁盘/swap 换入，开销大。看 major fault 才是真性能指标。

Q7: 程序报「Cannot allocate memory」但 free 还有很多内存，为什么？
A: 常见三种：mmap 段数超过 vm.max_map_count、overcommit_memory=2 时 CommitLimit 耗尽、cgroup 内存限制。先查这三项再怀疑物理内存。
```

## 面试题

```text
1. 虚拟内存的作用？
   答：进程隔离（各自独立地址空间）、内存超售（物理不够换磁盘）、简化编程（进程以为独占连续内存）、安全（ASLR）。

2. 地址翻译的流程？
   答：虚拟地址拆页号+偏移 → 查 TLB（命中得物理地址）→ miss 查多级页表 → 得到物理页 → 访问内存；页不在则触发缺页换入。

3. TLB 是什么？TLB miss 会怎样？
   答：TLB 是页表的高速缓存，加速虚拟→物理地址翻译。miss 要去查页表（多级、慢），甚至触发缺页，性能骤降。

4. 为什么用大页？
   答：大页减少页表项数量，同样大小的 TLB 覆盖更多内存，降低 TLB miss，提升大内存应用（数据库/JVM）性能。

5. 为什么页表要多级（如 4 级）？
   答：64 位地址空间巨大，单级页表每个进程要上百万页表项且大部分是空洞。多级页表按需分配中间页表，只建用到的区间，大幅省内存。

6. mmap 实现零拷贝的原理？
   答：read 要「磁盘 → 页缓存 → 用户缓冲区」两次拷贝；mmap 直接把页缓存映射进用户地址空间，进程直接读写页缓存，省掉内核→用户这次拷贝。

7. 写时复制（COW）是怎么回事？
   答：fork 后父子进程共享同一物理页并标记只读，任一方写时触发缺页、内核复制一份新页再写。避免 fork 时立即复制全部内存，省时省内存。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 大内存应用（数据库/JVM）考虑大页，减少 TLB miss、提升性能
2. 高频读写大文件用 mmap，比 read/write 少一次拷贝
3. 别用「free 的 free 列」判断内存够不够，要看 available（含可回收缓存）
4. 理解缺页和 TLB miss 是内存性能的关键指标，配合 perf 分析
5. 进程内存映射看 /proc/<pid>/maps 和 smaps，比 ps 的 RSS 更细
6. 统计单个进程真实占用用 Pss（按共享比例折算），多进程共享库时比 RSS 准
7. 排查「内存够但报 Cannot allocate memory」先查 max_map_count 和 overcommit

### 踩坑记录

```text
坑 1：mmap 映射大文件后内存暴涨
结论：mmap 一个 10G 文件，进程内存占用飙升。
原因：mmap 建立映射时可能触发大量缺页，把文件内容读进页缓存。
解法：大文件 mmap 用 MAP_NORESERVE 或按需访问，别一次全读。

坑 2：mmap 文件映射后修改没落盘
结论：mmap 改了内容，以为会自动写回，结果文件没更新。
原因：mmap 的改动先改内存页，回写是异步的（脏页回收）。
解法：关键数据 msync 显式刷盘，别依赖异步回写。

坑 3：大页配了应用没生效
结论：设了 nr_hugepages，应用内存占用没变化。
原因：应用没显式启用大页（JVM 要 -XX:+UseLargePages），或没权限。
解法：确认应用支持大页并显式开启，必要时调整内核参数。

坑 4：把虚拟内存（VSZ）当实际占用（RSS）看
结论：ps 里 VSZ 几十 G 以为内存爆了。
原因：VSZ 是虚拟地址空间大小（含未提交的），RSS 才是实际物理内存。
解法：看内存占用用 RSS（或 top 的 RES），别被 VSZ 吓到。

坑 5：页大小和文件系统块大小混淆
结论：以为改 PAGESIZE 能优化文件 IO。
原因：页是内存管理单位，文件系统块是磁盘 IO 单位，两回事。
解法：内存优化看页/大页，磁盘 IO 优化看文件系统块和调度器。

坑 6：映射的文件被截断后进程崩溃（SIGBUS）
结论：mmap 的文件被另一个进程 truncate 后，访问映射区进程收到 SIGBUS 崩溃。
原因：映射页对应的文件内容已不存在，内核发 SIGBUS（区别于越界访问的 SIGSEGV）。
解法：处理 SIGBUS 信号，或映射前用文件锁协调，别让文件被随意截断。

坑 7：大量 mmap 段触发 max_map_count 限制
结论：程序报 Cannot allocate memory，但 free 内存充足。
原因：进程映射段数超过 vm.max_map_count（默认 65530），mmap 被拒。
解法：调高 vm.max_map_count，或应用侧减少映射段数（复用映射、合并）。
```
