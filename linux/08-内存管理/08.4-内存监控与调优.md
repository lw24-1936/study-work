## 概述

内存监控回答三个问题：现在内存够不够（free/vmstat）、谁在吃内存（top/ps）、有没有泄漏（趋势观察）。调优手段主要是 cgroups 内存限制（容器/服务级硬限制）和内核参数（swappiness、dirty_ratio）。核心原则：先监控定位、再针对性调优，别一上来乱改参数。

```text
监控 + 调优全景：
1. 看总量 —— free -h（available 是真实可用）、vmstat（换出趋势）
2. 看分布 —— top/ps 按内存排序找大户
3. 看趋势 —— sar 历史数据，判断是否泄漏
4. 调优 —— cgroups 限内存、swappiness/dirty 参数
```

内存监控的完整闭环是「采集 → 判断 → 定位 → 处置」：先用 free/vmstat/top 采集即时状态，用 sar/监控系统采集历史趋势；再判断是真紧张（available 低 + 换出）还是假紧张（页缓存占满）；然后定位到具体进程；最后用 cgroups 限制或内核参数调优来处置。四个工具各管一段，缺一段就查不全。

## 核心概念

### free 与 vmstat 与 top 与 sar

**是什么**：free 读 /proc/meminfo 给内存总量快照，核心字段是 available（真实可用内存，含可回收的页缓存）；vmstat 给动态采样，重点看 si/so（换入/换出）判断是否在换出；top 给实时进程视图，按 RES/%MEM 找内存大户；sar 是后台定时采集的历史数据，用于看趋势、判断泄漏。

**为什么**：单看 free 的 used 会误判——used 里含可回收的 buff/cache，不代表真紧张；单看 top 看不到历史趋势，漏掉慢泄漏。四个工具配合才能同时回答「够不够」「谁在吃」「是不是在涨」三个问题。

**怎么用**：先 `free -h` 看 available，再 `vmstat 1 5` 看 si/so 是否持续非 0，然后 `top -o %MEM` 或 `ps aux --sort=-%mem` 找大户，最后 `sar -r` 回看历史趋势。

**边界/易错点**：free 的老版本没有 available 字段，只有 free/buffers/cached，判断「够不够」得自己算（free + buffers + cached 可回收部分）；top 的 VIRT 是虚拟地址空间大小（含未实际占用的 mmap/库），RES 才是常驻物理内存，看占用要看 RES 不看 VIRT；vmstat 的 si/so 字段语义是 swap in/swap out，so 持续高才是内存紧张信号。

```text
# 实测（本机 free -h）
$ free -h
               total   used   free  shared  buff/cache  available
内存：          19Gi   10Gi   329Mi  823Mi   9.5Gi       8.7Gi
交换：         8.0Gi    76Mi   7.9Gi
# 判断：available=8.7Gi 充足，swap 几乎没用，内存健康
```

```text
# 实测（vmstat，si/so=0 说明无换出）
$ vmstat 1 2
r b  free  buff  cache  si so  bi bo  us sy id wa
0 0 337416 1575652 8400068 0 0  7 101  1  0 97  2
# si/so（换入/换出）都是 0 = 没在换出，内存够
```

```shell
free -h                    # 总量快照
free -h -w                 # 新版拆分 buff 和 cache 两列
free -s 2                  # 每 2 秒刷新一次
vmstat 1 5                 # 动态监控（看 si/so）
vmstat -s                  # 统计摘要（各类内存计数）
top                        # 实时，M 按内存排序
top -o %MEM                # 直接按内存占用排序
ps aux --sort=-%mem | head # 内存大户排行
ps -eo pid,rss,vsz,comm --sort=-rss | head   # RSS/VSZ 排行
sar -r 1 5                 # 内存历史（需 sysstat）
sar -B 1 5                 # 换页活动（pgpgin/pgpgout）
sar -W 1 5                 # 换入换出（pswpin/pswpout）
```

```text
free 字段含义：
total     物理内存总量
used      已用（含 buff/cache，不等于程序真实占用）
free      完全空闲（未分配任何用途）
shared    tmpfs/shared memory 占用
buff/cache 内核用作页缓存/块缓存（可回收，程序需要时释放）
available 真实可用内存 = free + 可回收的页缓存（判断够不够看它）
```

```text
vmstat 关键字段：
r b       运行/阻塞队列进程数
swpd      已用 swap 量
free      空闲内存
buff cache 缓冲区/页缓存
si so     swap in / swap out（换入/换出），so 持续高 = 内存紧张
bi bo     块设备读入/写出
us sy id wa 用户态/内核态/空闲/等待 IO 的时间占比
```

### 内存泄漏排查

**是什么**：内存泄漏是「进程内存只增不减」——分配了不释放。排查步骤：先确认是否真泄漏（RSS 持续增长 vs 波动），再看是哪个进程（top 排序），然后定位到进程内（堆分析、代码排查）。关键工具：`top`/`ps` 看 RSS 趋势、`pmap` 看进程内存映射、Java 用 jmap/jstat、C 用 valgrind。判断标准：RSS 随时间单调增长且不回落 = 疑似泄漏。

**为什么**：泄漏进程会把物理内存一点点吃掉，最终触发全局 OOM 杀掉其他无辜进程（不是泄漏进程自己被优先杀，取决于 OOM score）。早发现能在「只涨到 2G」时处理，晚发现就是「半夜 OOM 全站挂」。

**怎么用**：采样 RSS 画趋势图（`top -p PID -d 5` 或监控系统），确认单调增长后，按进程类型选工具——Java 用 `jstat -gcutil` 看老年代是否持续涨、`jmap -dump` 导出堆用 MAT 分析；C/C++ 用 valgrind --leak-check；Python 用 tracemalloc。

**边界/易错点**：RSS 涨不一定是泄漏——JVM 堆、连接池、各种缓存会涨到配置上限后稳定，这是「合理增长」不是泄漏；泄漏的特征是「单调无限涨、不回落」。另外 RSS 不含已换出的部分，进程内存被换出后 RSS 会「下降」，别把「被 swap 出去」误判成「内存释放了」。

```shell
# 1. 持续观察进程 RSS 是否只增不减
top -p <PID> -d 5
# 2. 看进程内存映射分布
pmap -x <PID> | tail
# 3. 看进程各段内存占用（比 pmap 更细）
cat /proc/<PID>/smaps_rollup
# 4. Java 进程看堆
jmap -heap <PID>          # 堆使用
jstat -gcutil <PID> 1000  # GC 情况（老年代 O 列持续涨 = 疑似泄漏）
jmap -dump:format=b,file=/tmp/heap.bin <PID>  # 导出堆供 MAT 分析
# 5. C/C++ 进程
valgrind --leak-check=full --log-file=vg.log ./app
# 6. Python 进程
python3 -m tracemalloc  # 或代码里 import tracemalloc 追踪分配栈
```

```text
内存泄漏判断：
1. RSS 单调增长不回落 —— 疑似泄漏
2. RSS 波动（涨了会降） —— 正常（如缓存、GC）
3. 区分「泄漏」和「合理增长」—— JVM 堆、连接池缓存会涨到上限后稳定
```

```text
按语言选排查工具：
Java     jstat -gcutil（看老年代）、jmap -dump + MAT/Eclipse 分析
C/C++    valgrind --leak-check、AddressSanitizer（-fsanitize=address）
Python   tracemalloc、objgraph、pympler
Go       pprof（runtime/pprof + go tool pprof）
Node.js  --inspect + Chrome Memory 快照对比
```

### cgroups 内存限制

**是什么**：cgroups 能按「进程组」硬限制内存：memory.max 设上限、超过就回收或 OOM。这是容器（Docker --memory）和 systemd 服务（MemoryMax=）内存隔离的底层。

**为什么**：相比「放任进程吃内存」，cgroups 内存限制能防止单个服务/容器吃满整机内存拖垮其他服务——多租户、容器化的内存隔离都靠它。没有限制时，一个泄漏的容器就能触发全局 OOM 杀掉宿主机上的所有服务。

**怎么用**：systemd 服务用 `systemctl set-property <svc> MemoryMax=1G`（或单元文件 `[Service] MemoryMax=`）；Docker 用 `docker run --memory 512m`；直接操作 cgroup v2 文件系统写 `/sys/fs/cgroup/<路径>/memory.max`。另有 memory.high（软限制，先限流不 OOM）、memory.swap.max（限制 swap 用量）、memory.oom.group（组内一起 OOM）。

**边界/易错点**：memory.max 设太小会导致进程频繁被 OOM 或一直 GC 抖动；cgroup v1（memory.limit_in_bytes）和 v2（memory.max）接口名不同，写脚本要对版本；Docker 的 `--memory-swap` 默认 = --memory 时表示完全禁用容器 swap，若不设则容器可用宿主 swap，需明确语义再配。

```shell
# systemd 服务内存限制
systemctl set-property nginx MemoryMax=1G
# 单元文件写法
# [Service]
# MemoryMax=1G
# MemoryHigh=800M      # 软限制，先限流不 OOM
# MemorySwapMax=0      # 禁用 swap

# Docker 容器内存限制（底层 cgroups）
docker run --memory 512m --memory-swap 512m myapp
# 查看 cgroup 内存
systemd-cgtop
# 直接读写 cgroup v2（无 systemd/docker 时的底层做法）
cat /sys/fs/cgroup/system.slice/nginx.service/memory.max
echo 1073741824 > /sys/fs/cgroup/system.slice/nginx.service/memory.max
```

```text
cgroups 内存限制：
1. memory.max —— 硬上限，超过触发回收/限制
2. memory.high —— 软限制，先限流（减慢分配），OOM 前缓冲
3. memory.swap.max —— 该 cgroup 允许的 swap 上限
4. memory.oom.group —— 超限时整组一起 OOM（还是只杀组内某进程）
5. 用途 —— 防止单容器/服务吃满整机，多租户隔离
6. Docker --memory、systemd MemoryMax 都是它的封装
```

```text
cgroup v1 vs v2 接口名对照：
限制        v1                            v2
硬上限      memory.limit_in_bytes         memory.max
软限制      memory.soft_limit_in_bytes    memory.high
swap 上限   memory.memsw.limit_in_bytes   memory.swap.max
当前用量    memory.usage_in_bytes         memory.current
```

## 工作原理

这些监控工具的数据源是 /proc/meminfo——内核维护的内存统计（MemTotal/MemFree/MemAvailable/Cached/AnonPages 等），free/vmstat/top 都是读它并加工展示。cgroups 的内存限制原理是：内核在内存分配时检查进程所在 cgroup 的 memory.max，超过上限就对该 cgroup 内触发回收，回收不掉则对该 cgroup 触发 OOM（只杀组内进程，不影响组外）。

```text
监控数据流：内核统计 → /proc/meminfo → free/vmstat/top 读取展示
cgroup 限制：分配内存时查 memory.max → 超限先回收组内 → 回收无效则组内 OOM
```

/proc/meminfo 的几个关键字段和它们的关系：MemAvailable 是内核估算的「不换出也能满足新分配」的内存量，不是简单的 free + cache；Cached 是页缓存（文件读写的缓存，可回收）；AnonPages 是匿名页（堆/栈等，不可直接回收，只能换出）；Buffers 是块设备元数据缓存。free 命令的 available 就是直接读 MemAvailable，所以现在判断内存够不够看 available 就够，不必自己算。

```text
/proc/meminfo 关键字段：
MemTotal     物理内存总量
MemFree      完全空闲内存
MemAvailable 可用内存（内核估算，含可回收页缓存）—— free 的 available 读它
Buffers      块设备元数据缓存
Cached       页缓存（文件读写缓存，可回收）
SwapCached   已换出又换回的缓存页
Active/Inactive 活跃/不活跃页（回收候选来源）
AnonPages    匿名页（堆/栈），只能换出不能直接回收
```

OOM 触发顺序（cgroup 内）：进程申请内存 → 内核检查所在 cgroup 的 memory.max → 未超直接分配；超了先做内存回收（回收页缓存、压缩匿名页等）→ 回收后仍超则从该 cgroup 内挑 OOM score 最高的进程杀掉。整机层面同理，只是作用域是整机 memory。这就是「限制住 cgroup」能保护组外进程的原因：OOM 只发生在组内。

## 常用命令与配置

```shell
free -h                    # 总量 + available
free -h -w                 # 拆分 buff/cache
vmstat 1 5                 # si/so 换出趋势
top -o %MEM                # 按内存排序实时监控
ps aux --sort=-%mem        # 内存大户排行
pmap -x <PID>              # 进程内存映射
smem -tk                   # 按 PSS 统计（比 RSS 更准，需装 smem）
sar -r 1 5                 # 历史趋势（sysstat）
sar -B 1 5                 # 换页活动
docker stats               # 容器资源使用
systemd-cgtop              # cgroup 内存用量（systemd 视角）
```

```text
排查内存问题三步：free 看总量 → vmstat 看趋势 → top/ps 找大户
泄漏判断：RSS 单调涨不回落 = 疑似泄漏，波动 = 正常
```

关于 PSS（proportional set size）：RSS 把共享库整段算进每个进程，多个进程共享同一库时会重复计数，导致「所有进程 RSS 加起来超过物理内存」。PSS 按共享比例均摊（共享库内存 / 共享进程数），更接近真实占用，`smem -tk` 或 `/proc/PID/smaps` 里的 Pss 行能看到。排查「内存去哪了」时，如果 RSS 求和远大于物理内存，用 PSS 才能看出真实分布。

```shell
# PSS 更准的用法
smem -tk                   # 按 PSS 统计用户级占用
smem -k -P java            # 只看 java 进程的 PSS
grep -i pss /proc/<PID>/smaps | awk '{s+=$2} END {print s" kB"}'
```

## 配置文件解析

```text
# /etc/sysctl.conf —— 内存调优内核参数
vm.swappiness = 60               # 换出积极度（0-100，越小越优先用内存）
vm.dirty_ratio = 20              # 脏页同步刷盘阈值
vm.dirty_background_ratio = 10   # 脏页后台刷盘阈值
vm.min_free_kbytes = 67584       # 保留空闲内存
vm.vfs_cache_pressure = 100      # 目录/inode 缓存回收压力（越小越留缓存）
vm.overcommit_memory = 0         # 内存超额分配策略（0 启发式 / 1 允许 / 2 禁止）

# systemd 服务单元 —— 服务级内存限制
[Service]
MemoryMax=1G                # 内存硬上限
MemorySwapMax=0             # 允许的 swap 上限
MemoryHigh=800M             # 软限制（先限流不 OOM）
```

```shell
sysctl -p                        # 加载 sysctl 参数
sysctl vm.swappiness             # 查看当前值
sysctl -w vm.swappiness=10       # 临时改（重启失效）
systemctl set-property nginx MemoryMax=1G   # 运行时限制服务内存
systemctl show nginx -p MemoryCurrent    # 看服务当前内存用量
```

```text
swappiness 取值含义：
0     尽量不换出，先把页缓存回收掉（内存用满优先）
60    默认，内存与 swap 平衡使用
100   积极换出，尽量把匿名页换到 swap

dirty 参数：
dirty_background_ratio 达到后由内核后台线程异步刷盘
dirty_ratio            达到后进程自身同步刷盘（会阻塞写进程）
写入密集场景调低两者，让脏页及时落盘，避免 IO 尖峰和内存被脏页占满
```

## 应用场景实战

### 场景一：定位内存大户并判断是否泄漏

```shell
# 1. 找内存 TOP 进程
ps aux --sort=-%mem | head -5
# 2. 盯可疑进程的 RSS 趋势（隔 5 秒采样）
top -p <PID> -d 5
# 3. 看系统是否在换出（换出说明真紧张）
vmstat 1 5
```

```text
# 实测（本机内存大户 TOP3）
$ ps aux --sort=-%mem | head -4
PID     %MEM  COMMAND
1007465  9.3  java ...nacos-server.jar          # nacos 注册中心
4187862  8.6  chrome ...puppeteer (headless)    # 无头浏览器（还吃 39% CPU）
6001     3.5  java ...jenkins.war               # jenkins
# 内存大头是 java 服务 + puppeteer 浏览器，符合一台开发/CI 机的特征
```

### 场景二：给容器设内存限制防止拖垮宿主机

```shell
# 1. 限制某容器最多用 512M
docker run -d --memory 512m --memory-swap 512m --name app myapp:latest
# 2. 观察容器内存使用
docker stats app
# 3. 超过限制时容器会被 OOM 杀（可在 docker logs 里看到）
docker logs app | grep -i oom
# 4. 宿主机侧看 OOM 记录
dmesg | grep -i 'killed process'
```

### 场景三：Java 服务内存缓慢增长，用 jstat 定位老年代泄漏

```shell
# 1. 找到 java 进程 PID
ps aux | grep java | grep -v grep
# 2. 持续看 GC 和老年代占用（O 列 = Old 区使用率，1000ms 采样一次）
jstat -gcutil <PID> 1000
# 3. 若 O 列每次 Full GC 后仍不回落、持续逼近 100%，导出堆分析
jmap -dump:format=b,file=/tmp/heap.hprof <PID>
# 4. 用 MAT / jvisualvm 打开 heap.hprof，看 dominator tree 找最大对象
# 5. 确认泄漏后改代码，或临时加 -Xmx 限制堆上限并配告警，避免拖垮整机
```

```text
jstat -gcutil 输出解读：
S0 S1 E O M ... YGC YGCT FGC FGCT GCT
E  Eden 区使用率，O 老年代使用率，M 元空间使用率
FGC/Full GC 次数，FGCT Full GC 耗时
判断泄漏：Full GC 后 O 列仍不降、持续逼近 100% = 老年代有对象无法回收 = 泄漏
```

## 性能与调优

```text
1. 先监控再调优 —— free/vmstat/top 定位问题，再决定改哪个参数
2. 容器/服务必设内存上限 —— MemoryMax/--memory，防止单点吃满整机
3. 数据库调低 swappiness —— 10-20，缓存留内存
4. 写入密集调脏页参数 —— dirty_ratio 调低，及时刷盘避免 IO 尖峰
5. 内存告警阈值 —— 配 Prometheus 等监控，available 低于阈值告警，别等 OOM
```

调优要有目标：先明确是「内存不够用」（available 低、换出）还是「内存没用满」（缓存堆积、换出过少）。前者优先查泄漏/加限制/加内存，后者调 swappiness/vfs_cache_pressure 让缓存及时回收。乱改参数最典型的是把 swappiness 调成 0 以为能「禁用 swap」——实际上 swappiness=0 只是「尽量不主动换出」，真内存耗尽照样换出，要禁用 swap 得 `swapoff -a`。

```text
不同负载的内存调优倾向：
数据库/缓存服务  swappiness=10，内存优先，避免热数据被换出
写入密集服务    dirty_background_ratio/dirty_ratio 调低（如 5/10），及时刷盘
多租户/容器环境 每个服务配 MemoryMax，宿主机保留 10-20% 余量
桌面/开发机      保持默认，别乱调
```

## 安全与权限

```text
1. 调整内核参数要 root —— sysctl 写 /proc/sys/vm/* 需要 root
2. 容器内存限制要设上限 —— 不设 --memory 的容器能拖垮宿主机
3. pmap/jmap 看进程内存可能泄露敏感信息 —— 只对自己有权限的进程用
4. 别用 drop_caches 当日常 —— 影响全局缓存，应急才用
```

内存相关操作的安全性：`/proc/<PID>/smaps`、`/proc/<PID>/mem` 能读进程内存映射甚至内容，普通用户只能读自己的进程（ptrace 权限限制），root 能读所有进程——所以生产上 sudo 权限要收紧，避免运维账号 `cat /proc/1/mem` 这类越权。另外 `echo 3 > /proc/sys/vm/drop_caches` 能瞬间清掉页缓存「让 free 变大」，但这只是把缓存丢了、不影响真实内存压力，且会短暂抬高 IO（缓存重新建立），属于应急手段，不能当日常优化。

## 故障排查

### 内存缓慢耗尽（慢泄漏）

```shell
# 1. 看历史趋势（sar 或监控系统）
sar -r | tail -20
# 2. 找 RSS 单调增长的进程
ps aux --sort=-%mem | head
# 3. 盯该进程 RSS
top -p <PID> -d 5
```

### 容器 OOM / 宿主机内存告警

```shell
# 1. 看哪个容器内存告急
docker stats
# 2. 看 OOM 记录（宿主机内核日志）
dmesg | grep -i 'killed process'
# 3. 确认容器内存限制是否合理
docker inspect <容器> | grep -i memory
```

### 内存被页缓存占满但 available 正常（假紧张）

```shell
# 1. free 显示 used 高、free 低
free -h
# 2. 确认 available 还充足，说明是页缓存
free -h -w
# 3. 看谁在用缓存（文件读写大户）
vmstat 1 5
# 4. 真需要释放时（应急）
echo 3 > /proc/sys/vm/drop_caches
```

```text
「used 高但 available 高」判断：used 里大头是 buff/cache（页缓存），
程序需要内存时内核会自动回收页缓存，所以 available 充足 = 没问题，
不用 drop_caches。drop_caches 只影响「看起来」，不影响真实可用性。
```

## 常见问题

```text
Q1: 怎么判断内存是否真的不够？
A: 看 available（低）+ si/so 持续非 0（在换出）。used 高不代表不够，可能只是页缓存。

Q2: RSS 一直涨就是泄漏吗？
A: 不一定。JVM 堆、连接池缓存会涨到配置上限后稳定。泄漏的特征是「单调无限涨、不回落」。

Q3: 容器怎么限制内存？
A: Docker 用 --memory 和 --memory-swap，底层是 cgroups 的 memory.max。超过限制容器会被 OOM 杀。

Q4: sar 和 vmstat 有什么区别？
A: sar 是后台定时采集的历史数据（看趋势、判断泄漏），vmstat 是实时采样（看当前瞬时状态）。

Q5: free 里 available 和 free 的区别？
A: free 是完全空闲的内存，available 是真实可用（free + 可回收的页缓存）。判断够不够看 available，不看 free。

Q6: VIRT 和 RES 哪个才是进程真实占用？
A: RES（常驻内存）是真实占用的物理内存；VIRT 是虚拟地址空间（含 mmap 的库、未实际使用的地址），通常远大于 RES。看占用看 RES。

Q7: 为什么所有进程的 RSS 加起来超过物理内存？
A: RSS 把共享库整段算进每个进程，共享库被重复计数。用 PSS（按共享比例均摊）或 smem -t 看才接近真实分布。

Q8: swappiness 设成 0 就能禁用 swap 吗？
A: 不能。swappiness=0 只是尽量不主动换出，内存真耗尽照样换。禁用 swap 要 swapoff -a。
```

## 面试题

```text
1. 怎么排查内存泄漏？
   答：确认 RSS 单调增长不回落 → top/ps 找泄漏进程 → pmap/jmap/valgrind 定位到进程内，区分「真泄漏」和「合理缓存增长」。

2. cgroups 内存限制的原理？
   答：内核分配内存时检查 cgroup 的 memory.max，超限先回收组内内存，回收无效则对该 cgroup 触发 OOM（只影响组内进程）。

3. free 里 available 和 free 的区别？
   答：free 是「完全空闲」内存，available 是「可用」内存（free + 可回收的页缓存），available 才反映真实可用量。

4. 容器没设内存限制有什么风险？
   答：单个容器内存泄漏会吃满宿主机，触发全局 OOM，拖垮其他容器和服务。每个容器都要设 --memory 上限。

5. vmstat 的 si 和 so 分别是什么？内存紧张看哪个？
   答：si=swap in（换入）、so=swap out（换出）。so 持续非 0 且数值大，说明系统在频繁换出，内存紧张。

6. /proc/meminfo 里 MemFree 和 MemAvailable 的区别？
   答：MemFree 是未分配任何用途的物理内存；MemAvailable 是内核估算的「不换出也能满足新分配」的量，含可回收的页缓存，比 MemFree 更能反映真实可用。

7. top 里 VIRT、RES、SHR 分别指什么？
   答：VIRT 虚拟地址空间大小、RES 常驻物理内存（真实占用）、SHR 共享内存。判断进程占用看 RES。

8. 怎么给 systemd 服务限制内存？
   答：单元文件 [Service] 段配 MemoryMax=1G（硬上限）、MemoryHigh（软限制）、MemorySwapMax（swap 上限），或运行时 systemctl set-property <svc> MemoryMax=1G。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 判断内存够不够看 available + si/so，别只看 free 或 used
2. 持续监控内存趋势（sar/Prometheus），泄漏要在早期发现
3. 容器/多服务环境必须配 cgroups 内存限制，防止单点吃满整机
4. 排查泄漏先确认「真泄漏」还是「合理增长」，再看进程内堆
5. 数据库服务器调低 swappiness，内存用满优先于换出
6. 看进程真实占用用 RES/PSS，别被 VIRT 的大数字误导

### 踩坑记录

```text
坑 1：用 free 的 used 判断内存紧张，误判
结论：used 90% 就以为内存不够，其实是页缓存。
原因：used 含可回收的 buff/cache，不代表真实紧张。
解法：看 available 和 si/so，这两项才反映真实内存压力。

坑 2：内存泄漏和缓存增长分不清
结论：进程 RSS 一直涨，以为是泄漏，其实是正常缓存。
原因：JVM 堆、连接池、缓存会涨到配置上限后稳定，不是无限涨。
解法：看 RSS 是否「单调无限涨」还是「涨到顶稳定」，后者正常。

坑 3：容器没设内存限制，一个容器 OOM 拖垮整机
结论：某个容器内存泄漏，吃满宿主机内存，其他服务全挂。
原因：容器没设 --memory 限制，不受约束地吃内存。
解法：每个容器都设 --memory 和 --memory-swap，宿主机保留余量。

坑 4：只看瞬时内存不看趋势，漏掉慢泄漏
结论：瞬时 free 看着正常，但内存随时间缓慢耗尽。
原因：慢泄漏每天涨一点，瞬时快照看不出来。
解法：用 sar -r 或监控系统看历史趋势，配内存告警阈值。

坑 5：vmstat 的 si/so 看反了
结论：把 si（swap in）当 swap out，判断反了。
原因：si=换入、so=换出，都是「swap」前缀容易混。
解法：记「so=swap out（换出，内存紧张信号）」，so 持续高 = 内存不够。

坑 6：看 VIRT 判断进程占用，被大数字误导
结论：top 里 VIRT 几个 G，以为进程吃了几 G 内存。
原因：VIRT 是虚拟地址空间，含 mmap 的库和未实际使用的地址，RES 才是真实物理占用。
解法：看 RES 或 PSS，别拿 VIRT 下结论。

坑 7：把 drop_caches 当日常优化，反复清缓存
结论：定期 echo 3 > drop_caches 想「释放内存」，结果 IO 忽高忽低。
原因：drop_caches 只是丢缓存，不解决真实内存压力，缓存还得重建。
解法：页缓存是正常的，available 充足就不用管；真紧张才从泄漏/限制/加内存下手。
```
