## 概述

当物理内存不够时，内核有两手：换出到 swap（把冷匿名页写到磁盘，腾出内存）和 OOM Killer（实在不行就杀进程）。swap 是「缓冲」，OOM 是「最后手段」。相关机制：交换（swap 分区/文件）、swappiness（控制换出积极度）、OOM Killer（按 oom_score 杀进程）、内存超售（overcommit，允许进程申请超过实际内存）。理解这些才能解释「进程被莫名杀掉」和「内存不够时系统的行为」。

```text
Swap 与 OOM 全景：
1. 交换 swap —— 内存不够时把冷匿名页换出到磁盘，腾物理内存
2. swappiness —— 0-100，控制换出积极度（默认 60）
3. OOM Killer —— 内存耗尽时按 oom_score 杀进程，最后手段
4. 内存超售 overcommit —— 允许进程申请超过实际内存，内核按策略决定给不给
```

## 核心概念

### 交换 swap

swap 是「内存不够时的缓冲」——物理内存紧张时，内核把不活跃的匿名页换出到 swap（写磁盘），腾出物理内存给活跃进程；需要时再换入（swap in）。swap 的意义是「避免内存紧张时直接 OOM 杀进程」，给系统缓冲时间。但 swap 在磁盘上、速度远慢于内存，大量换出换入（swap 抖动）会拖垮系统。swap 状态用 `free -h` 的 swap 行或 `vmstat` 的 si/so 列观察。

```text
# 实测（本机 swap 状态）
$ swapon --show
NAME      TYPE SIZE  USED PRIO
/swap.img file   8G 76.7M   -1
# 8G swap 文件，只用了 76.7M——内存充足时几乎不换出
```

```shell
free -h              # swap 用量
vmstat 1 5           # si/so 列 = 每秒换入/换出的 KB
swapon --show        # 查看 swap 设备
```

### swappiness

swappiness（0-100）控制「内核多积极地用 swap」。值越高，越早、越积极地把匿名页换出；值越低，越倾向用满物理内存再说。默认 60（均衡）。数据库服务器常调低到 10-20（尽量用物理内存、避免缓存被换出）；需要激进换出的场景调高。它不「禁用」swap——swappiness=0 只是「尽量避免」，内存极端紧张时仍会换出。

```text
# 实测（本机默认 swappiness）
$ cat /proc/sys/vm/swappiness
60
# 默认 60：均衡策略
```

```shell
sysctl vm.swappiness=10              # 临时调低（数据库常用）
echo 'vm.swappiness=10' >> /etc/sysctl.conf   # 持久化
```

### OOM Killer

OOM（Out Of Memory）Killer 是内存彻底耗尽时的最后手段——内核给每个进程算一个 oom_score（值越高越可能被杀），内存耗尽时杀掉 score 最高的进程腾内存。排查「进程被莫名杀掉」就看 dmesg/日志里的 OOM 记录。可以用 oom_score_adj 调整进程的 OOM 优先级（-1000 表示永不杀，如关键服务）。

```shell
# 查看进程的 OOM 分数
cat /proc/<PID>/oom_score
cat /proc/<PID>/oom_score_adj
# 排查 OOM 记录
dmesg | grep -i 'out of memory'
grep -i 'oom' /var/log/kern.log /var/log/syslog 2>/dev/null | tail
```

```text
# 实测（本机无 OOM 记录）
$ dmesg | grep -i 'out of memory'
（空）—— 本机没发生过 OOM，内存够用
```

```text
OOM Killer 要点：
1. oom_score —— 内核算的「该被杀程度」，越高越容易被杀
2. oom_score_adj —— 手动调整，-1000 = 永不杀（保护关键进程）
3. 触发 —— 内存耗尽且回收无效时，杀 score 最高的进程
```

### 内存超售与隔离

内存超售（overcommit）指「允许进程申请超过实际物理内存的内存」——因为进程申请了不一定用（惰性分配），内核默认乐观地批准申请，真用到时再分配。overcommit_memory 参数控制策略：0（启发式，默认）、1（总是超售）、2（严格限制，不允许超售）。容器/虚拟化的内存超售是「多个实例共享物理内存、超量分配」，隔离靠 cgroups 的 memory.max 硬限制。

```text
# 实测（本机 overcommit 策略）
$ cat /proc/sys/vm/overcommit_memory
0
# 0 = 启发式（默认），内核估计是否批准超额申请
```

```text
overcommit_memory 三档：
0 启发式 —— 内核估计，合理申请就批（默认）
1 总是超售 —— 永远批准（风险高）
2 严格 —— 不允许超售，按 CommitLimit 限制
```

## 工作原理

swap 的换出换入是「匿名页的迁徙」：内存紧张时，kswapd 或直接回收选出最久没用的匿名页，把内容写到 swap 区，页表标记为「在 swap 上」，物理页腾出来；进程访问到该页时触发缺页，内核从 swap 读回（swap in）。OOM Killer 则是在回收和换出都无效后触发：内核遍历进程算 oom_score（综合内存占用、oom_score_adj 等），杀掉 score 最高的进程释放内存。

```text
swap 换出换入流程：
内存紧张 → 选冷匿名页 → 写 swap 区 → 页表标记 → 物理页腾出
访问该页 → 缺页 → 从 swap 读回（swap in）

OOM Killer 触发：
内存耗尽 + 回收/换出无效 → 遍历进程算 oom_score → 杀 score 最高者
```

## 常用命令与配置

```shell
swapon --show          # 查看 swap 设备/文件
swapon /swapfile       # 启用 swap
swapoff /swapfile      # 停用 swap
free -h                # 看 swap 用量
vmstat 1 5             # si/so 换出趋势
cat /proc/<PID>/oom_score      # 看进程 OOM 分数
echo -1000 > /proc/<PID>/oom_score_adj   # 保护关键进程
```

```text
swap 管理三件套：swapon 启用、swapoff 停用、swapon --show 查看
OOM 优先级：oom_score_adj 范围 -1000~1000，-1000 永不杀
```

## 配置文件解析

```text
# /etc/fstab —— swap 设备/文件，开机自动挂载
/swap.img    none    swap    sw    0    0

# /etc/sysctl.conf —— swap/OOM 相关内核参数
vm.swappiness = 60            # 换出积极度（0-100）
vm.overcommit_memory = 0      # 内存超售策略（0/1/2）
vm.overcommit_ratio = 50      # overcommit=2 时的超售比例（%）
vm.panic_on_oom = 0           # OOM 时是否触发内核 panic（0 不 panic）
```

```shell
sysctl -p                       # 加载 /etc/sysctl.conf
swapon --show                   # 确认 swap 已挂载
```

## 应用场景实战

### 场景一：进程被 OOM 杀了，排查原因

```shell
# 1. 看 OOM 记录，找到被杀进程
dmesg | grep -i 'killed process' | tail
# 2. 看系统日志里的 OOM 详情
journalctl -k | grep -i oom | tail
# 3. 确认是不是内存不足 + 谁占内存
free -h
ps aux --sort=-%mem | head
```

### 场景二：保护关键服务不被 OOM 杀

```shell
# 1. 找到关键服务的 PID
pgrep -f 'critical-service'
# 2. 设 oom_score_adj=-1000（永不杀）
echo -1000 > /proc/$(pgrep -f critical-service)/oom_score_adj
# 3. 验证
cat /proc/$(pgrep -f critical-service)/oom_score_adj
```

## 性能与调优

```text
1. swap 放独立磁盘 —— swap 和数据库/日志盘分开，避免 IO 互相拖累
2. 数据库调低 swappiness —— 10-20，让数据尽量留物理内存
3. swap 别当内存用 —— 持续换出（so 高）说明真该加内存，别靠调参数硬撑
4. 关键服务 oom_score_adj=-1000 —— 防 OOM 误杀核心进程
5. 容器设 --memory-swap —— 控制容器能用的 swap，防止一个容器换爆磁盘
```

## 安全与权限

```text
1. oom_score_adj 要 root —— 调整 OOM 优先级影响进程存活，只 root 可写
2. swap 文件权限 —— swapfile 建议 600，防止被普通用户读（含内存数据）
3. overcommit=2 谨慎 —— 严格模式可能让合法的大额申请失败，生产默认 0
4. panic_on_oom —— 安全敏感场景可设 1，OOM 时直接 panic 而不是悄悄杀进程
```

## 故障排查

### 系统变慢 / swap 抖动

```shell
# 1. 看 swap 用量和换出趋势
free -h
vmstat 1 5
# 2. so（换出）持续高 = 内存真不够
# 3. 找吃内存大户
ps aux --sort=-%mem | head
```

### 进程被 OOM 杀

```shell
# 1. 查 OOM 记录
dmesg | grep -i 'killed process'
journalctl -k | grep -i oom
# 2. 看内存和 swap 是否耗尽
free -h
# 3. 确认被杀进程，评估加内存或限流
```

## 常见问题

```text
Q1: swap 是必要的吗？
A: 强烈建议配（哪怕几 G）。它给内存紧张一个缓冲，避免直接 OOM 杀进程。但别指望 swap 替代物理内存。

Q2: swappiness=0 就完全不用 swap 了吗？
A: 不是。0 只是「尽量避免」，内存极端紧张时仍会换出。要彻底禁用用 swapoff。

Q3: 进程为什么会被 OOM Killer 杀？
A: 内存耗尽且回收/换出都无效时，内核杀 oom_score 最高的进程腾内存。日志里 grep 'killed process' 能看到。

Q4: 怎么保护关键进程不被 OOM 杀？
A: 设 oom_score_adj=-1000（永不杀），但注意这样可能让系统在内存耗尽时没进程可杀、直接卡死。
```

## 面试题

```text
1. swappiness 是什么？数据库服务器怎么调？
   答：swappiness（0-100）控制换出积极度，越高越积极用 swap。数据库调低到 10-20，尽量用物理内存。

2. OOM Killer 怎么选进程杀？
   答：内核给每个进程算 oom_score（综合内存占用、oom_score_adj），杀 score 最高的进程。oom_score_adj=-1000 可保护进程永不杀。

3. overcommit_memory 的三种策略？
   答：0 启发式（默认，合理申请就批）、1 总是超售（永远批，风险高）、2 严格（按 CommitLimit 限制，不允许超售）。

4. swap 抖动是什么？怎么解决？
   答：内存不足 + swap 满载，内核反复换入换出，IO 打满、系统极慢。解决：加物理内存，或处理吃内存的进程。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 服务器要配 swap（兜底防 OOM），但别依赖 swap 当内存用
2. 数据库服务器 swappiness 调低（10-20），避免缓存被换出
3. 关键服务设 oom_score_adj=-1000 保护，别让它被 OOM 误杀
4. 持续换出（vmstat si/so 非 0）说明内存真不够，加内存别调参数硬撑
5. 排查进程被杀先看 dmesg/journalctl 的 OOM 记录，别瞎猜

### 踩坑记录

```text
坑 1：进程莫名被杀，找不到原因
结论：服务跑着跑着没了，日志没报错。
原因：内存耗尽触发 OOM Killer，杀了 score 最高的进程。
解法：dmesg/journalctl 查 OOM 记录，找到被杀进程和时间点。

坑 2：以为 swappiness=0 就禁用 swap
结论：设 swappiness=0 后系统还是用了 swap。
原因：0 只是「尽量避免」，内存极端紧张时仍会换出。
解法：要禁用 swap 就 swapoff -a，或接受 0=尽量不用。

坑 3：关键服务被 OOM 杀了导致故障
结论：数据库被 OOM 杀，服务中断。
原因：内存耗尽时 OOM 按 score 杀，数据库占内存大、容易被选中。
解法：给关键服务设 oom_score_adj=-1000 保护，同时监控内存加告警。

坑 4：overcommit_memory 设成 2 导致分配失败
结论：改 overcommit_memory=2 后，程序 malloc 报失败。
原因：严格模式不允许超售，大额申请被拒。
解法：理解 overcommit 语义，默认 0 即可，别乱改 2。

坑 5：swap 用满导致系统卡死（swap 抖动）
结论：swap 用满、si/so 持续高，系统响应极慢。
原因：内存不足 + swap 也满，内核反复换入换出，IO 打满。
解法：加物理内存，或找出吃内存的进程处理，别让 swap 长期满载。
```
