## 概述

当物理内存不够时，内核有两手：换出到 swap（把冷匿名页写到磁盘，腾出内存）和 OOM Killer（实在不行就杀进程）。swap 是「缓冲」，OOM 是「最后手段」。相关机制：交换（swap 分区/文件）、swappiness（控制换出积极度）、OOM Killer（按 oom_score 杀进程）、内存超售（overcommit，允许进程申请超过实际内存）。理解这些才能解释「进程被莫名杀掉」和「内存不够时系统的行为」。

```text
Swap 与 OOM 全景：
1. 交换 swap —— 内存不够时把冷匿名页换出到磁盘，腾物理内存
2. swappiness —— 0-100，控制换出积极度（默认 60）
3. OOM Killer —— 内存耗尽时按 oom_score 杀进程，最后手段
4. 内存超售 overcommit —— 允许进程申请超过实际内存，内核按策略决定给不给
```

这套机制要连起来看：物理内存紧张 → 换出冷匿名页到 swap 缓冲 → swap 也满、换出换入打转（swap 抖动）→ 回收/换出都无效 → OOM Killer 杀进程。超售（overcommit）则是「事前」策略：内核允许进程申请超出物理内存的虚拟内存，真用到时才分配，用不完就没事，用超了就进入上面的回收/OOM 流程。

## 核心概念

### 交换 swap

swap 是「内存不够时的缓冲」——物理内存紧张时，内核把不活跃的匿名页换出到 swap（写磁盘），腾出物理内存给活跃进程；需要时再换入（swap in）。swap 的意义是「避免内存紧张时直接 OOM 杀进程」，给系统缓冲时间。但 swap 在磁盘上、速度远慢于内存，大量换出换入（swap 抖动）会拖垮系统。swap 状态用 `free -h` 的 swap 行或 `vmstat` 的 si/so 列观察。

```text
# 实测（本机 swap 状态）
$ swapon --show
NAME      TYPE SIZE  USED PRIO
/swap.img file   8G 76.7M   -1
# 8G swap 文件，只用了 76.7M——内存充足时几乎不换出
```

```shell
free -h              # swap 用量
vmstat 1 5           # si/so 列 = 每秒换入/换出的 KB
swapon --show        # 查看 swap 设备
```

为什么要有 swap：内存紧张时，如果匿名页无处可去，内核只能直接 OOM 杀进程；有 swap 就能先把冷匿名页换出，给系统一个缓冲，把「立刻杀进程」变成「变慢但还能跑」。swap 换出的是「冷页」（很久没用），换入发生在进程访问被换出的页时（触发缺页）。

```text
swap 换出换入要点：
1. 换出对象 —— 冷匿名页（不是页缓存，页缓存直接丢弃即可）
2. swap in/out —— vmstat 的 si（换入）/so（换出）列，持续非 0 = 在换
3. swap 抖动 —— swap 满 + 频繁换入换出，IO 打满、系统极慢
4. 意义 —— 兜底防 OOM，不替代物理内存
```

```shell
# 创建并启用一个 swap 文件（完整流程）
fallocate -l 2G /swapfile        # 预分配 2G 文件
chmod 600 /swapfile              # 收紧权限（含内存数据）
mkswap /swapfile                 # 格式化为 swap
swapon /swapfile                 # 启用
echo '/swapfile none swap sw 0 0' >> /etc/fstab   # 开机自动挂载
```

易错点：`fallocate` 预分配的 swap 文件在某些文件系统（如 ext4 老版本）上不能直接 mkswap，要用 `dd if=/dev/zero of=/swapfile bs=1M count=2048` 实际写零。swap 文件必须 600 权限，否则普通用户可能读到换出的内存数据。

### swappiness

swappiness（0-100）控制「内核多积极地用 swap」。值越高，越早、越积极地把匿名页换出；值越低，越倾向用满物理内存再说。默认 60（均衡）。数据库服务器常调低到 10-20（尽量用物理内存、避免缓存被换出）；需要激进换出的场景调高。它不「禁用」swap——swappiness=0 只是「尽量避免」，内存极端紧张时仍会换出。

```text
# 实测（本机默认 swappiness）
$ cat /proc/sys/vm/swappiness
60
# 默认 60：均衡策略
```

```shell
sysctl vm.swappiness=10              # 临时调低（数据库常用）
echo 'vm.swappiness=10' >> /etc/sysctl.conf   # 持久化
```

```text
swappiness 取值含义：
0     —— 尽量避免换出（不是禁用，极端紧张仍会换）
1-59  —— 偏保守，优先用物理内存
60    —— 默认，均衡
100   —— 激进换出，尽量腾物理内存
```

易错点：swappiness 不是「换出比例」，而是「内核在回收时优先回收页缓存还是优先换出匿名页」的倾向权重。swappiness=0 不代表禁用 swap（要禁用用 swapoff）；swappiness=100 也不会把内存全换出去（只是尽量优先换匿名页）。

### OOM Killer

OOM（Out Of Memory）Killer 是内存彻底耗尽时的最后手段——内核给每个进程算一个 oom_score（值越高越可能被杀），内存耗尽时杀掉 score 最高的进程腾内存。排查「进程被莫名杀掉」就看 dmesg/日志里的 OOM 记录。可以用 oom_score_adj 调整进程的 OOM 优先级（-1000 表示永不杀，如关键服务）。

```shell
# 查看进程的 OOM 分数
cat /proc/<PID>/oom_score
cat /proc/<PID>/oom_score_adj
# 排查 OOM 记录
dmesg | grep -i 'out of memory'
grep -i 'oom' /var/log/kern.log /var/log/syslog 2>/dev/null | tail
```

```text
# 实测（本机无 OOM 记录）
$ dmesg | grep -i 'out of memory'
（空）—— 本机没发生过 OOM，内存够用
```

```text
OOM Killer 要点：
1. oom_score —— 内核算的「该被杀程度」，越高越容易被杀
2. oom_score_adj —— 手动调整，-1000 = 永不杀（保护关键进程）
3. 触发 —— 内存耗尽且回收无效时，杀 score 最高的进程
```

oom_score 的计算综合了进程的内存占用（匿名页 + 页表 + swap 等）和 oom_score_adj 的调节值——内存占用越大、oom_score_adj 越正，越容易被杀。oom_score_adj 范围 -1000（永不杀）到 1000（优先杀）。

```shell
# 看系统所有进程的 oom_score 排序，找出最可能被杀的
for p in /proc/[0-9]*; do
  [ -r "$p/oom_score" ] && echo "$(cat $p/oom_score) $(cat $p/comm 2>/dev/null) ${p##*/}"
done | sort -rn | head
```

易错点：给关键进程设 oom_score_adj=-1000 是「双刃剑」——它确实保护了该进程，但内存真耗尽时内核没进程可杀，可能直接触发内核 panic 或系统卡死。所以保护关键进程的同时要配好内存监控和告警。

### 内存超售与隔离

内存超售（overcommit）指「允许进程申请超过实际物理内存的内存」——因为进程申请了不一定用（惰性分配），内核默认乐观地批准申请，真用到时再分配。overcommit_memory 参数控制策略：0（启发式，默认）、1（总是超售）、2（严格限制，不允许超售）。容器/虚拟化的内存超售是「多个实例共享物理内存、超量分配」，隔离靠 cgroups 的 memory.max 硬限制。

```text
# 实测（本机 overcommit 策略）
$ cat /proc/sys/vm/overcommit_memory
0
# 0 = 启发式（默认），内核估计是否批准超额申请
```

```text
overcommit_memory 三档：
0 启发式 —— 内核估计，合理申请就批（默认）
1 总是超售 —— 永远批准（风险高）
2 严格 —— 不允许超售，按 CommitLimit 限制
```

为什么能超售：进程 malloc 只是「登记」虚拟内存，不一定真的写（惰性分配），而且 fork 后大量内存是写时复制的（共享）。所以「申请总量」往往远大于「实际用到的」，严格禁止超售会浪费大量内存。内核用启发式估计「申请总量是否离谱」，离谱才拒绝。

```shell
# 看超售相关的账本
grep -E 'CommitLimit|Committed_AS' /proc/meminfo
# CommitLimit = 允许承诺的虚拟内存上限（overcommit=2 时生效）
# Committed_AS = 系统当前承诺的总量（含未真正使用的）
```

```shell
# cgroup 隔离：限制某个进程/容器的内存（v2 接口）
echo 1G > /sys/fs/cgroup/<group>/memory.max       # 硬限制，超了触发该组 OOM
echo 800M > /sys/fs/cgroup/<group>/memory.high    # 软限制，超了先回收再限
```

```text
内存超售与隔离要点：
1. overcommit —— 允许申请超额内存，因为申请≠使用（惰性分配 + COW）
2. overcommit=2 —— 按 CommitLimit 严格限制，超售不批准
3. 容器隔离 —— cgroup memory.max 硬限制 + memory.high 软限制
4. 容器超售 —— 宿主机总内存 < 各容器 memory.max 之和（超卖），赌它们不同时打满
```

## 工作原理

swap 的换出换入是「匿名页的迁徙」：内存紧张时，kswapd 或直接回收选出最久没用的匿名页，把内容写到 swap 区，页表标记为「在 swap 上」，物理页腾出来；进程访问到该页时触发缺页，内核从 swap 读回（swap in）。OOM Killer 则是在回收和换出都无效后触发：内核遍历进程算 oom_score（综合内存占用、oom_score_adj 等），杀掉 score 最高的进程释放内存。

```text
swap 换出换入流程：
内存紧张 → 选冷匿名页 → 写 swap 区 → 页表标记 → 物理页腾出
访问该页 → 缺页 → 从 swap 读回（swap in）

OOM Killer 触发：
内存耗尽 + 回收/换出无效 → 遍历进程算 oom_score → 杀 score 最高者
```

OOM 的完整触发链：进程申请内存 → 触发分配 → 找不到空闲页 → 触发回收（kswapd/直接回收）→ 回收也不够 → 检查是否可换出/换入 → 仍不够 → 触发 OOM Killer。OOM Killer 除了看 oom_score，还考虑「谁最该被杀」——默认倾向杀「内存占用大、刚启动、非特权」的进程，而跳过正在退出的进程、init 进程和被 oom_score_adj 保护的进程。

```text
OOM Killer 选进程的依据：
1. 内存占用大（匿名页多）—— 释放的内存多
2. oom_score 高 —— 综合占用 + oom_score_adj
3. 跳过 —— 正在退出的进程、PID 1（init）、oom_score_adj=-1000 的进程
4. 目的 —— 用最小的「误杀代价」释放最多的内存
```

```text
swap 管理三件套：swapon 启用、swapoff 停用、swapon --show 查看
OOM 优先级：oom_score_adj 范围 -1000~1000，-1000 永不杀
```

```shell
swapoff -a && swapon -a      # 重新挂载所有 swap（改 swappiness 后生效测试用）

```

## 配置文件解析

```text
# /etc/fstab —— swap 设备/文件，开机自动挂载
/swap.img    none    swap    sw    0    0

# /etc/sysctl.conf —— swap/OOM 相关内核参数
vm.swappiness = 60            # 换出积极度（0-100）
vm.overcommit_memory = 0      # 内存超售策略（0/1/2）
vm.overcommit_ratio = 50      # overcommit=2 时的超售比例（%）
vm.panic_on_oom = 0           # OOM 时是否触发内核 panic（0 不 panic）
```

```shell
sysctl -p                       # 加载 /etc/sysctl.conf
swapon --show                   # 确认 swap 已挂载
```

```text
补充参数：
vm.overcommit_kbytes —— 新版用绝对值替代 overcommit_ratio（二选一）
vm.panic_on_oom —— 1 时 OOM 直接内核 panic（安全敏感场景），0 杀进程
vm.oom_kill_allocating_task —— 1 时优先杀触发 OOM 的进程（而非 score 最高者）
vm.swap_ratio / vm.swappiness —— swap 换出倾向的调节
```

```shell
# 多块 swap 时用 PRIO 控制优先级（值越高越先用）
# swapon -p 100 /dev/sdb2    # 指定优先级挂载
```

## 应用场景实战

### 场景一：进程被 OOM 杀了，排查原因

```shell
# 1. 看 OOM 记录，找到被杀进程
dmesg | grep -i 'killed process' | tail
# 2. 看系统日志里的 OOM 详情
journalctl -k | grep -i oom | tail
# 3. 确认是不是内存不足 + 谁占内存
free -h
ps aux --sort=-%mem | head
```

```shell
# 4. 看 OOM 记录的完整上下文（含被杀进程的内存占用、oom_score）
journalctl -k | grep -B5 -A15 'Out of memory' | tail -60
```

场景解读：OOM 日志会写清楚「Out of memory: Killed process <pid> (<name>)」以及触发时各进程的内存分布。拿到被杀进程后，看它当时占了多少内存、oom_score 多少，再决定是给它设 oom_score_adj 保护、加内存、还是限制它的内存（cgroup）。

### 场景二：保护关键服务不被 OOM 杀

```shell
# 1. 找到关键服务的 PID
pgrep -f 'critical-service'
# 2. 设 oom_score_adj=-1000（永不杀）
echo -1000 > /proc/$(pgrep -f critical-service)/oom_score_adj
# 3. 验证
cat /proc/$(pgrep -f critical-service)/oom_score_adj
```

```shell
# 4. 用 systemd 固化（OOMScoreAdjust 选项，重启后仍生效）
systemctl edit critical-service
# 写入：
# [Service]
# OOMScoreAdjust=-1000
```

场景解读：`echo -1000 > /proc/<pid>/oom_score_adj` 是临时保护（进程重启/机器重启就失效），生产要用 systemd 的 `OOMScoreAdjust=-1000` 固化到 unit 里。但记住：保护关键服务的同时，其他进程被杀的概率上升，内存耗尽时可能没进程可杀导致系统卡死，必须配套内存监控。

### 场景三：内存紧张导致 swap 抖动，定位并缓解

```shell
# 1. 确认 swap 抖动：swap 用量高 + si/so 持续非零
free -h
vmstat 1 5
# 2. 找正在大量换入换出的进程
ps aux --sort=-%mem | head
# 3. 看是哪个进程的匿名页被换出最多
smem -s swap 2>/dev/null | head    # 按 swap 用量排序（可能需安装）
```

```shell
# 4. 缓解：降低换出压力（临时），再评估加内存
sysctl vm.swappiness=10
# 5. 找出吃内存大户，限制其内存或重启
systemctl restart <吃内存的服务>
```

场景解读：swap 抖动的特征是 swap 用满 + si/so 持续高 + 系统响应极慢（IO 全被换入换出占满）。短期缓解是调低 swappiness（少换出）、处理吃内存的进程；根本解决是加物理内存或给进程做 cgroup 限制。别指望靠调参数长期硬撑。

## 性能与调优

```text
1. swap 放独立磁盘 —— swap 和数据库/日志盘分开，避免 IO 互相拖累
2. 数据库调低 swappiness —— 10-20，让数据尽量留物理内存
3. swap 别当内存用 —— 持续换出（so 高）说明真该加内存，别靠调参数硬撑
4. 关键服务 oom_score_adj=-1000 —— 防 OOM 误杀核心进程
5. 容器设 --memory-swap —— 控制容器能用的 swap，防止一个容器换爆磁盘
```

```text
6. SSD 上 swap 优先 —— swap 是随机小 IO，SSD 延迟远低于机械盘，换入换出更顺畅
7. 内存型负载关 swap 不如调低 swappiness —— 彻底 swapoff 会让匿名页无处可去、更早 OOM
8. 监控 si/so 趋势 —— 偶发换出正常，持续换出是加内存的信号
```

## 安全与权限

```text
1. oom_score_adj 要 root —— 调整 OOM 优先级影响进程存活，只 root 可写
2. swap 文件权限 —— swapfile 建议 600，防止被普通用户读（含内存数据）
3. overcommit=2 谨慎 —— 严格模式可能让合法的大额申请失败，生产默认 0
4. panic_on_oom —— 安全敏感场景可设 1，OOM 时直接 panic 而不是悄悄杀进程
```

```text
5. swap 里的数据可能泄露 —— swap 分区/文件含换出的内存数据，加密磁盘上 swap 也要加密
6. swapoff 时机 —— 停用 swap 前确认内存足够，否则 swapoff 过程中可能触发 OOM
7. cgroup 隔离防单容器拖垮宿主机 —— 多租户/容器场景必须设 memory.max，否则一个容器 OOM 前会耗尽宿主机内存
```

## 故障排查

### 系统变慢 / swap 抖动

```shell
# 1. 看 swap 用量和换出趋势
free -h
vmstat 1 5
# 2. so（换出）持续高 = 内存真不够
# 3. 找吃内存大户
ps aux --sort=-%mem | head
```

### 进程被 OOM 杀

```shell
# 1. 查 OOM 记录
dmesg | grep -i 'killed process'
journalctl -k | grep -i oom
# 2. 看内存和 swap 是否耗尽
free -h
# 3. 确认被杀进程，评估加内存或限流
```

### swap 被写满但系统还有空闲内存

```shell
# 1. 看 swappiness 是否过高（激进换出）
cat /proc/sys/vm/swappiness
# 2. 看 swap 里换出了多少（SwapCached 是「swap 和内存都有一份」的页）
grep -E 'SwapTotal|SwapFree|SwapCached' /proc/meminfo
# 3. 调低 swappiness 减少后续换出，已换出的页会随访问慢慢换回
sysctl vm.swappiness=10
```

## 常见问题

```text
Q1: swap 是必要的吗？
A: 强烈建议配（哪怕几 G）。它给内存紧张一个缓冲，避免直接 OOM 杀进程。但别指望 swap 替代物理内存。

Q2: swappiness=0 就完全不用 swap 了吗？
A: 不是。0 只是「尽量避免」，内存极端紧张时仍会换出。要彻底禁用用 swapoff。

Q3: 进程为什么会被 OOM Killer 杀？
A: 内存耗尽且回收/换出都无效时，内核杀 oom_score 最高的进程腾内存。日志里 grep 'killed process' 能看到。

Q4: 怎么保护关键进程不被 OOM 杀？
A: 设 oom_score_adj=-1000（永不杀），但注意这样可能让系统在内存耗尽时没进程可杀、直接卡死。

Q5: overcommit 是什么？为什么默认允许超售？
A: 允许进程申请超过物理内存的虚拟内存。因为进程申请≠真正使用（惰性分配 + fork 写时复制），严格禁止会浪费内存，所以默认启发式批准。

Q6: SwapCached 是什么？它和 swap 用量有什么关系？
A: SwapCached 是「已换出到 swap、但又被换回内存、swap 里还留有一份副本」的页。这类页再次被换出时无需重写磁盘，直接复用。swap 的 USED 里不含纯 SwapCached。

Q7: 容器被 OOM 杀和宿主机 OOM 杀有什么区别？
A: 容器有 cgroup 内存限制（memory.max）时，超限先触发「容器内 OOM」（只杀容器里的进程）；没有 cgroup 限制时，容器会耗尽宿主机内存、触发宿主机级 OOM，殃及其他容器。
```

## 面试题

```text
1. swappiness 是什么？数据库服务器怎么调？
   答：swappiness（0-100）控制换出积极度，越高越积极用 swap。数据库调低到 10-20，尽量用物理内存。

2. OOM Killer 怎么选进程杀？
   答：内核给每个进程算 oom_score（综合内存占用、oom_score_adj），杀 score 最高的进程。oom_score_adj=-1000 可保护进程永不杀。

3. overcommit_memory 的三种策略？
   答：0 启发式（默认，合理申请就批）、1 总是超售（永远批，风险高）、2 严格（按 CommitLimit 限制，不允许超售）。

4. swap 抖动是什么？怎么解决？
   答：内存不足 + swap 满载，内核反复换入换出，IO 打满、系统极慢。解决：加物理内存，或处理吃内存的进程。

5. swap 和物理内存的关系？能不能用 swap 替代内存？
   答：swap 是磁盘上的缓冲，速度远慢于内存，不能替代。它只是内存紧张时给匿名页换出的去处，避免直接 OOM。持续用 swap 说明内存真不够。

6. oom_score 和 oom_score_adj 的区别？
   答：oom_score 是内核动态算的「该被杀程度」（随内存占用变化），oom_score_adj 是管理员手动设的偏移（-1000~1000），加进 score 里调节谁先被杀。

7. 为什么建议服务器配 swap，即使内存很大？
   答：内存峰值/突发流量时，swap 给系统一个缓冲窗口，把「立刻 OOM 杀进程」变成「变慢但还能服务」。没有 swap，匿名页无处换出，内存一紧张就直接 OOM。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 服务器要配 swap（兜底防 OOM），但别依赖 swap 当内存用
2. 数据库服务器 swappiness 调低（10-20），避免缓存被换出
3. 关键服务设 oom_score_adj=-1000 保护，别让它被 OOM 误杀
4. 持续换出（vmstat si/so 非 0）说明内存真不够，加内存别调参数硬撑
5. 排查进程被杀先看 dmesg/journalctl 的 OOM 记录，别瞎猜
6. swap 文件权限设 600，防止换出数据被普通用户读
7. 容器/多租户场景设 cgroup 内存限制，防止单容器拖垮宿主机

### 踩坑记录

```text
坑 1：进程莫名被杀，找不到原因
结论：服务跑着跑着没了，日志没报错。
原因：内存耗尽触发 OOM Killer，杀了 score 最高的进程。
解法：dmesg/journalctl 查 OOM 记录，找到被杀进程和时间点。

坑 2：以为 swappiness=0 就禁用 swap
结论：设 swappiness=0 后系统还是用了 swap。
原因：0 只是「尽量避免」，内存极端紧张时仍会换出。
解法：要禁用 swap 就 swapoff -a，或接受 0=尽量不用。

坑 3：关键服务被 OOM 杀了导致故障
结论：数据库被 OOM 杀，服务中断。
原因：内存耗尽时 OOM 按 score 杀，数据库占内存大、容易被选中。
解法：给关键服务设 oom_score_adj=-1000 保护，同时监控内存加告警。

坑 4：overcommit_memory 设成 2 导致分配失败
结论：改 overcommit_memory=2 后，程序 malloc 报失败。
原因：严格模式不允许超售，大额申请被拒。
解法：理解 overcommit 语义，默认 0 即可，别乱改 2。

坑 5：swap 用满导致系统卡死（swap 抖动）
结论：swap 用满、si/so 持续高，系统响应极慢。
原因：内存不足 + swap 也满，内核反复换入换出，IO 打满。
解法：加物理内存，或找出吃内存的进程处理，别让 swap 长期满载。

坑 6：用 fallocate 建的 swap 文件 mkswap 报错
结论：fallocate 预分配 swap 文件后 mkswap 提示「swapfile has holes」。
原因：fallocate 产生的是稀疏文件（有空洞），swap 需要连续分配的块，老内核/老文件系统不支持。
解法：用 dd if=/dev/zero of=/swapfile bs=1M count=2048 实际写零，再 mkswap。

坑 7：给关键进程设 -1000 保护后系统内存耗尽直接卡死
结论：保护了数据库，但内存真耗尽时没进程可杀，系统无响应。
原因：-1000 进程永不杀，其他进程又不足以释放足够内存，内核反复回收无果、陷入僵局。
解法：保护关键进程的同时必须配内存监控告警和 cgroup 限制，别让系统走到「无进程可杀」的死路。
```
