## 概述

当物理内存不够时，内核有两手：换出到 swap（把冷匿名页写到磁盘，腾出内存）和 OOM Killer（实在不行就杀进程）。swap 是「缓冲」，OOM 是「最后手段」。相关机制：交换（swap 分区/文件）、swappiness（控制换出积极度）、OOM Killer（按 oom_score 杀进程）、内存超售（overcommit，允许进程申请超过实际内存）。理解这些才能解释「进程被莫名杀掉」和「内存不够时系统的行为」。

```text
Swap 与 OOM 全景：
1. 交换 swap —— 内存不够时把冷匿名页换出到磁盘，腾物理内存
2. swappiness —— 0-100，控制换出积极度（默认 60）
3. OOM Killer —— 内存耗尽时按 oom_score 杀进程，最后手段
4. 内存超售 overcommit —— 允许进程申请超过实际内存，内核按策略决定给不给
```

## 交换 swap

swap 是「内存不够时的缓冲」——物理内存紧张时，内核把不活跃的匿名页换出到 swap（写磁盘），腾出物理内存给活跃进程；需要时再换入（swap in）。swap 的意义是「避免内存紧张时直接 OOM 杀进程」，给系统缓冲时间。但 swap 在磁盘上、速度远慢于内存，大量换出换入（swap 抖动）会拖垮系统。swap 状态用 `free -h` 的 swap 行或 `vmstat` 的 si/so 列观察。

```text
# 实测（本机 swap 状态）
$ swapon --show
NAME      TYPE SIZE  USED PRIO
/swap.img file   8G 76.7M   -1
# 8G swap 文件，只用了 76.7M——内存充足时几乎不换出
```

```shell
free -h              # swap 用量
vmstat 1 5           # si/so 列 = 每秒换入/换出的 KB
swapon --show        # 查看 swap 设备
```

## swappiness

swappiness（0-100）控制「内核多积极地用 swap」。值越高，越早、越积极地把匿名页换出；值越低，越倾向用满物理内存再说。默认 60（均衡）。数据库服务器常调低到 10-20（尽量用物理内存、避免缓存被换出）；需要激进换出的场景调高。它不「禁用」swap——swappiness=0 只是「尽量避免」，内存极端紧张时仍会换出。

```text
# 实测（本机默认 swappiness）
$ cat /proc/sys/vm/swappiness
60
# 默认 60：均衡策略
```

```shell
sysctl vm.swappiness=10              # 临时调低（数据库常用）
echo 'vm.swappiness=10' >> /etc/sysctl.conf   # 持久化
```

## OOM Killer

OOM（Out Of Memory）Killer 是内存彻底耗尽时的最后手段——内核给每个进程算一个 oom_score（值越高越可能被杀），内存耗尽时杀掉 score 最高的进程腾内存。排查「进程被莫名杀掉」就看 dmesg/日志里的 OOM 记录。可以用 oom_score_adj 调整进程的 OOM 优先级（-1000 表示永不杀，如关键服务）。

```shell
# 查看进程的 OOM 分数
cat /proc/<PID>/oom_score
cat /proc/<PID>/oom_score_adj
# 排查 OOM 记录
dmesg | grep -i 'out of memory'
grep -i 'oom' /var/log/kern.log /var/log/syslog 2>/dev/null | tail
```

```text
# 实测（本机无 OOM 记录）
$ dmesg | grep -i 'out of memory'
（空）—— 本机没发生过 OOM，内存够用
```

```text
OOM Killer 要点：
1. oom_score —— 内核算的「该被杀程度」，越高越容易被杀
2. oom_score_adj —— 手动调整，-1000 = 永不杀（保护关键进程）
3. 触发 —— 内存耗尽且回收无效时，杀 score 最高的进程
```

## 内存超售与隔离

内存超售（overcommit）指「允许进程申请超过实际物理内存的内存」——因为进程申请了不一定用（惰性分配），内核默认乐观地批准申请，真用到时再分配。overcommit_memory 参数控制策略：0（启发式，默认）、1（总是超售）、2（严格限制，不允许超售）。容器/虚拟化的内存超售是「多个实例共享物理内存、超量分配」，隔离靠 cgroups 的 memory.max 硬限制。

```text
# 实测（本机 overcommit 策略）
$ cat /proc/sys/vm/overcommit_memory
0
# 0 = 启发式（默认），内核估计是否批准超额申请
```

```text
overcommit_memory 三档：
0 启发式 —— 内核估计，合理申请就批（默认）
1 总是超售 —— 永远批准（风险高）
2 严格 —— 不允许超售，按 CommitLimit 限制
```

## 应用场景实战

### 场景一：进程被 OOM 杀了，排查原因

```shell
# 1. 看 OOM 记录，找到被杀进程
dmesg | grep -i 'killed process' | tail
# 2. 看系统日志里的 OOM 详情
journalctl -k | grep -i oom | tail
# 3. 确认是不是内存不足 + 谁占内存
free -h
ps aux --sort=-%mem | head
```

### 场景二：保护关键服务不被 OOM 杀

```shell
# 1. 找到关键服务的 PID
pgrep -f 'critical-service'
# 2. 设 oom_score_adj=-1000（永不杀）
echo -1000 > /proc/$(pgrep -f critical-service)/oom_score_adj
# 3. 验证
cat /proc/$(pgrep -f critical-service)/oom_score_adj
```

## 最佳实践与踩坑记录

### 最佳实践

1. 服务器要配 swap（兜底防 OOM），但别依赖 swap 当内存用
2. 数据库服务器 swappiness 调低（10-20），避免缓存被换出
3. 关键服务设 oom_score_adj=-1000 保护，别让它被 OOM 误杀
4. 持续换出（vmstat si/so 非 0）说明内存真不够，加内存别调参数硬撑
5. 排查进程被杀先看 dmesg/journalctl 的 OOM 记录，别瞎猜

### 踩坑记录

```text
坑 1：进程莫名被杀，找不到原因
结论：服务跑着跑着没了，日志没报错。
原因：内存耗尽触发 OOM Killer，杀了 score 最高的进程。
解法：dmesg/journalctl 查 OOM 记录，找到被杀进程和时间点。

坑 2：以为 swappiness=0 就禁用 swap
结论：设 swappiness=0 后系统还是用了 swap。
原因：0 只是「尽量避免」，内存极端紧张时仍会换出。
解法：要禁用 swap 就 swapoff -a，或接受 0=尽量不用。

坑 3：关键服务被 OOM 杀了导致故障
结论：数据库被 OOM 杀，服务中断。
原因：内存耗尽时 OOM 按 score 杀，数据库占内存大、容易被选中。
解法：给关键服务设 oom_score_adj=-1000 保护，同时监控内存加告警。

坑 4：overcommit_memory 设成 2 导致分配失败
结论：改 overcommit_memory=2 后，程序 malloc 报失败。
原因：严格模式不允许超售，大额申请被拒。
解法：理解 overcommit 语义，默认 0 即可，别乱改 2。

坑 5：swap 用满导致系统卡死（swap 抖动）
结论：swap 用满、si/so 持续高，系统响应极慢。
原因：内存不足 + swap 也满，内核反复换入换出，IO 打满。
解法：加物理内存，或找出吃内存的进程处理，别让 swap 长期满载。
```
