## 概述

DNS 把「域名」解析成「IP 地址」（如 www.example.com → 1.2.3.4）。Linux 的解析流程：先查 /etc/hosts（本地静态映射），再查 DNS 服务器（/etc/resolv.conf 指定）。主机名（hostname）是机器的名字，用 hostnamectl 管理。dig/nslookup/host 是 DNS 查询工具（dig 最强大）。理解解析流程和这几个配置文件，才能排查「域名解析不了」。

本机是 Ubuntu 24.04 桌面版：systemd-resolved 管理 DNS（resolv.conf 指向 stub 127.0.0.53），跑着 Tailscale（resolv.conf 里带了它的 search 域，hosts 里手动加了 github.com 的映射），解析链路上每个环节都有真实可查的输出，非常适合当样本。

```text
DNS 解析流程：
应用请求域名 → 查 /etc/hosts（本地）→ 查 DNS 服务器（resolv.conf）
1. /etc/hosts —— 本地静态映射，优先于 DNS
2. /etc/resolv.conf —— 指定 DNS 服务器地址
3. 缓存 —— systemd-resolved / nscd 缓存解析结果
```

## 核心概念

1. **域名解析**：域名 → IP 的过程，分本地解析（/etc/hosts）和远程解析（DNS 服务器）。
2. **/etc/hosts**：本地静态映射表，优先级最高，改它立即生效。
3. **/etc/resolv.conf**：指定 DNS 服务器，现代系统由 systemd-resolved 管理。
4. **systemd-resolved**：本地 DNS 缓存/转发服务，resolv.conf 指向它的 stub（127.0.0.53）。
5. **主机名（hostname）**：机器标识，static（静态）/transient（临时）/pretty（显示名）三种。
6. **DNS 记录类型**：A/AAAA/CNAME/MX/NS/TXT/SRV/PTR，每种记录解决一类问题。
7. **TTL 与缓存**：解析结果按 TTL 缓存，决定「更新速度」与「查询频率」的权衡。

下面按「是什么 → 为什么 → 怎么用 → 边界/易错点」展开核心概念。

### 域名层级与 FQDN

- **是什么**：域名是树状层级结构，从右往左：根（`.`）→ 顶级域（TLD，如 `.com`/`.cn`）→ 二级域（如 `example.com`）→ 子域（如 `www.example.com`）。完整的「主机名.子域.二级域.顶级域.」叫 FQDN（完全限定域名，末尾的根点可省略书写）。
- **为什么**：层级结构让 DNS 可以分布式管理——每层只管自己下面的一层，13 组根服务器只负责告诉你「.com 的服务器在哪」。
- **怎么用**：`dig example.com.` 查询末尾带根点就是 FQDN 形式；`hostname -f` 查看本机 FQDN。
- **边界/易错点**：resolv.conf 里配了 search 域时，不带点的主机名（如 `web01`）会被补成 `web01.<search域>.` 查询，这是「内网短主机名能解析」的原理，也是「查询慢/多出奇怪请求」的常见来源。

### DNS 记录类型

| 类型 | 全称 | 作用 | 示例 |
|---|---|---|---|
| A | Address | IPv4 地址映射 | `example.com. 189 IN A 172.66.147.243` |
| AAAA | IPv6 Address | IPv6 地址映射 | `example.com. IN AAAA 2606:4700::1` |
| CNAME | Canonical Name | 别名指向另一个域名 | `www → example.com.` |
| MX | Mail Exchange | 邮件服务器（带优先级，越小越优先） | `10 mx.maillb.baidu.com.` |
| NS | Name Server | 该域的权威 DNS 服务器 | `ns4.baidu.com.` |
| TXT | Text | 任意文本（SPF/DKIM/DMARC 验证常用） | `"v=spf1 include:..."` |
| SRV | Service | 服务定位（域名:端口，微服务/AD 域控用） | `_sip._tcp.example.com` |
| PTR | Pointer | 反向解析：IP → 域名 | `8.8.8.8.in-addr.arpa. → dns.google` |
| SOA | Start of Authority | 区域起始记录（主 DNS、刷新周期） | 每个 zone 第一条 |

### 递归查询 vs 迭代查询

- **是什么**：递归查询 = 「帮我查到底，最后给我答案」（客户端 → 本地 DNS 服务器）；迭代查询 = 「告诉你下一个该问谁，你自己接着问」（本地 DNS 服务器 → 根 → 顶级 → 权威）。
- **为什么**：客户端只认一个 DNS 地址（resolv.conf 里的 nameserver），它替你把整个链路跑完；服务器之间用迭代避免每台服务器都要缓存全世界的答案。
- **怎么用**：`dig +trace example.com` 能看到完整的迭代过程——从根服务器开始一级一级问下去。
- **边界/易错点**：递归查询要求你的 DNS 服务器有递归能力（开在 53 端口）；公共 DNS（8.8.8.8/223.5.5.5）都是递归服务器。

### 解析器链路（libc → nsswitch → resolv.conf）

- **是什么**：应用程序（curl、浏览器）调用 libc 的 `getaddrinfo()`，libc 按 `/etc/nsswitch.conf` 的 `hosts:` 行决定查询顺序（`files` = /etc/hosts，`dns` = DNS 服务器），最终走 /etc/resolv.conf 里配置的服务器。
- **为什么**：nsswitch 这一层让系统可以灵活组合多种「名字来源」（本地文件、DNS、NIS、LDAP、mDNS），不必改应用。
- **怎么用**：`getent hosts 域名` 走的就是这条真实链路——它和 dig 的结果不一致时，一定是 nsswitch 或 hosts 在起作用。
- **边界/易错点**：dig/nslookup/host 是「绕过 libc 直接查 DNS」的工具，所以它们的结果不能代表应用实际解析结果；判断「应用解析到哪」要用 getent。

### systemd-resolved 与 stub（127.0.0.53）

- **是什么**：systemd-resolved 是 Ubuntu/Debian 默认的本地 DNS 缓存与转发服务。它监听 127.0.0.53:53（stub），resolv.conf 指向它；应用把查询发给 stub，resolved 再转发给真正的上游 DNS（从 DHCP/NetworkManager 拿到），并缓存结果。
- **为什么**：把「DNS 配置来源」和「解析服务」解耦——网卡 DHCP 拿到什么 DNS 由 NetworkManager 交给 resolved，应用永远只认 127.0.0.53，切换网络不用改任何配置文件。
- **怎么用**：`resolvectl status` 看每个网卡的上游 DNS，`resolvectl query` 用 resolved 查，`resolvectl flush-caches` 清缓存，`resolvectl set-dns <网卡> <IP>` 改某网卡 DNS。
- **边界/易错点**：resolv.conf 有 stub（127.0.0.53）、static（手动写 nameserver 且不用 resolved）、uplink（直接用上游地址）三种模式；直接改 resolv.conf 会被 systemd-resolved 覆盖，正确姿势是 resolvectl/nmcli。

### 主机名（hostname）

- **是什么**：机器在网络中的标识。分三种：static（/etc/hostname，持久化）、transient（内核当前名，重启恢复）、pretty（带大小写的展示名，可含空格）。
- **为什么**：主机名用于 SSH 提示符、日志标识、集群节点发现（很多监控/编排工具按主机名区分机器），统一用 hostnamectl 管理三种名字。
- **怎么用**：`hostnamectl` 查看、`hostnamectl set-hostname web01` 设置（同时更新 static + transient）、`hostname` 快速查看当前名。
- **边界/易错点**：改主机名后必须同步 /etc/hosts 里 `127.0.1.1` 的映射，否则部分服务（sudo、某些数据库）反向解析会拿到旧名字或解析失败；主机名别用下划线（不符合 DNS 命名规范），别放敏感信息。

```text
# 实测（本机 /etc/hosts，注意 github.com 的手动映射）
$ grep -vE '^\s*#|^\s*$' /etc/hosts
127.0.0.1 localhost
127.0.1.1 lw-Vostro-7580
140.82.112.3 github.com
140.82.113.5 api.github.com
::1 ip6-localhost ip6-loopback
# 前两行是本地主机名（127.0.1.1 是 Debian/Ubuntu 给主机名的专用映射），
# 后两行手动把 github.com 指到正确的 IP（绕过被污染的 DNS 结果）
```

## 工作原理

### 完整解析链路

```text
浏览器/curl
   │  getaddrinfo("www.example.com")
   ▼
libc (glibc NSS)
   │  读 /etc/nsswitch.conf 的 hosts: files mdns4_minimal [NOTFOUND=return] dns
   ├── files → /etc/hosts 命中？ → 直接返回（synthetic 合成结果）
   ├── mdns4_minimal → .local 域名走 mDNS（没有 .local 立即跳过）
   └── dns → 读 /etc/resolv.conf → nameserver 127.0.0.53
                    │
                    ▼
        systemd-resolved（stub 127.0.0.53）
           │  先查自己的缓存 → 命中直接回
           │  按网卡路由规则选上游：wlp0s20f3 → 192.168.1.1
           ▼
        上游 DNS（192.168.1.1 路由器 / 8.8.8.8 / 223.5.5.5）
           │  递归查询：根(.) → .com → example.com 权威服务器
           ▼
        权威 DNS → A 记录 172.66.147.243 → 沿原路返回并逐级缓存
```

### dig 输出逐行解读

```text
# 实测（本机 dig example.com 完整输出）
$ dig example.com

; <<>> DiG 9.18.39-0ubuntu0.24.04.5-Ubuntu <<>> example.com
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 37658
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 65494
;; QUESTION SECTION:
;example.com.			IN	A

;; ANSWER SECTION:
example.com.		189	IN	A	172.66.147.243
example.com.		189	IN	A	104.20.23.154

;; Query time: 9 msec
;; SERVER: 127.0.0.53#53(127.0.0.53) (UDP)
;; WHEN: Wed Aug 19 12:20:02 CST 2026
;; MSG SIZE  rcvd: 72

逐行含义：
status: NOERROR      —— 查询成功（SERVFAIL=上游出错、NXDOMAIN=域名不存在）
flags: qr rd ra      —— qr=响应、rd=要求递归、ra=支持递归；aa 出现代表权威答案
QUESTION SECTION     —— 问了什么（example.com 的 A 记录）
ANSWER SECTION       —— 答案：两条 A 记录；189 是剩余 TTL 秒数，IN=Internet 类
Query time: 9 msec   —— 查询耗时（本地 stub 缓存命中时 <1ms）
SERVER: 127.0.0.53#53 —— 实际应答的服务器（走的是 systemd-resolved stub）
MSG SIZE rcvd: 72    —— 响应报文大小（EDNS 协商后的 UDP 载荷）
```

### nsswitch 的解析顺序控制

```text
# 实测（本机 /etc/nsswitch.conf 的 hosts 行）
$ grep '^hosts' /etc/nsswitch.conf
hosts:          files mdns4_minimal [NOTFOUND=return] dns

顺序语义：
files               先查 /etc/hosts
mdns4_minimal       仅 .local 结尾的域名走 mDNS 组播解析（Avahi）
[NOTFOUND=return]   若前面的源明确回答「没有」，立即返回，不再往下查
dns                 最后走 DNS 服务器

修改为 files dns     = 去掉 mDNS（服务端常用，避免 .local 查询拖慢）
修改为 dns files     = DNS 优先（不推荐，会掩盖 hosts 的作用）
```

### search 域与 FQDN 补全

- resolv.conf 里的 `search tailc6bb9f.ts.net` 声明搜索域：查询不带点的主机名（如 `web01`）时，解析器依次尝试 `web01.`、`web01.tailc6bb9f.ts.net.`，直到命中或全部失败。
- 本机 search 域来自 Tailscale MagicDNS——TS 网内主机名（如 `lw-vostro-7580`）不加域也能解析，就是这个机制。
- **易错点**：search 域太多/太长，每个不存在的短名都会引发 N 次额外查询（每次都要等到超时或 NXDOMAIN），是「DNS 慢」的隐形原因。

### TTL 与缓存机制

- 每条 DNS 记录自带 TTL（秒），解析器（resolved/nscd）按 TTL 缓存；TTL 归零前不再向上游发起相同查询。
- 缓存层级：应用层（resolved 缓存）→ 上游 DNS（8.8.8.8 缓存）→ 权威服务器（记录源头）。
- 改 DNS 记录后「全世界生效要等 TTL 时间」：紧急变更应先把权威 TTL 调小（如 60s），等记录更新后再调回。
- 排错时缓存会骗人：`resolvectl flush-caches` 清本机缓存，`dig @8.8.8.8` 绕过本地缓存直接问上游。

## 常用命令与配置

```shell
# DNS 查询三兄弟
dig example.com                # 完整解析（问题/答案/耗时/服务器）
dig example.com +short         # 只要结果（IP 列表）
dig @8.8.8.8 example.com       # 指定 DNS 服务器查询（绕过本地）
dig +trace example.com         # 从根服务器开始迭代追踪（看完整解析链）
dig example.com MX             # 查 MX 记录
dig -x 8.8.8.8                 # 反向解析（PTR）
dig example.com +noall +answer # 只要 ANSWER 段
nslookup example.com           # 交互式查询（老工具，输出简洁）
nslookup example.com 8.8.8.8   # 指定服务器
host example.com               # 最简洁（A + MX 一起给）
host -t TXT example.com        # 查指定类型

# 走真实应用链路（nsswitch）的查询——排错首选
getent hosts example.com       # 应用实际能解析到什么（hosts + DNS 综合结果）
getent ahosts example.com      # 含 IPv6 的完整结果

# systemd-resolved 管理
resolvectl status              # 看每张网卡的上游 DNS 和协议状态
resolvectl query example.com   # 用 resolved 解析（能看到是否 synthetic/cache）
resolvectl flush-caches        # 清 DNS 缓存
resolvectl statistics          # 缓存命中率统计
resolvectl set-dns wlp0s20f3 223.5.5.5   # 给指定网卡设 DNS（永久）
resolvectl dns                 # 查看当前各网卡 DNS

# 主机名
hostnamectl                    # 查看主机名详情
hostnamectl set-hostname web01 # 设置主机名（永久，改 /etc/hostname）
hostname                       # 快速看当前主机名
hostname -f                    # 看 FQDN（需要 DNS/主机映射配合）
hostname -i                    # 解析主机名得到 IP（走 hosts/DNS）
```

## 配置文件解析

```text
DNS 相关配置文件：
/etc/hosts          本地静态映射（优先级最高，nsswitch files 源）
/etc/resolv.conf    DNS 服务器配置（nameserver/search/options 行）
/etc/nsswitch.conf  解析顺序（hosts: files ... dns）
/etc/hostname       静态主机名
/etc/gai.conf       地址族优先级（IPv4/IPv6 谁优先，影响解析结果排序）
/run/systemd/resolve/stub-resolv.conf   resolved 生成的 stub 配置（resolv.conf 的实链目标）

Red Hat 系差异：
/etc/sysconfig/network        HOSTNAME= 定义主机名
/etc/sysconfig/network-scripts/ifcfg-<iface>   DNS1=/DNS2=/SEARCH= 定义网卡 DNS
/etc/resolv.conf              RHEL 6- 直接静态管理；RHEL 7+ 由 NetworkManager 生成
```

```text
# 实测（本机 /etc/resolv.conf，由 systemd-resolved 管理）
$ cat /etc/resolv.conf
# This is /run/systemd/resolve/stub-resolv.conf managed by man:systemd-resolved(8).
# Do not edit.
# ...（头部注释说明：此文件是 stub 模式，由 systemd-resolved 动态生成）
nameserver 127.0.0.53
options edns0 trust-ad
search tailc6bb9f.ts.net
# 127.0.0.53 是 systemd-resolved 的 stub，真正上游 DNS 用 resolvectl status 看；
# search 域来自 Tailscale MagicDNS；直接编辑此文件会被 systemd-resolved 覆盖
```

```text

stub     nameserver 127.0.0.53 —— resolved 缓存+转发（Ubuntu 桌面默认）
static   手写 nameserver 8.8.8.8 —— 不使用 resolved，直接问上游
uplink   nameserver 直接写上游 IP —— resolved 仍然运行但应用绕过它

静态模式配置：/etc/systemd/resolved.conf
[Resolve]

FallbackDNS=8.8.8.8
DNSSEC=allow-downgrade
Cache=yes
```

```text
  → 改完 nmcli connection reload 生效
RHEL 8+ 推荐 nmcli：nmcli con mod enp59s0 ipv4.dns "223.5.5.5" ipv4.dns-search "example.com"
```

## 性能与调优

```text
1. 本地缓存 —— systemd-resolved/nscd/dnsmasq 缓存解析结果，减少重复远程查询；
   resolvectl statistics 看命中率，命中率低说明应用重复查询多，可加应用层缓存
2. 就近 DNS —— 配延迟低的 DNS（ISP 或就近的公共 DNS），ping 测延迟；
   国内常用 223.5.5.5（阿里）/ 119.29.29.29（腾讯）/ 114.114.114.114（114）
3. 预取/并行 —— 应用层做 DNS 预解析、多记录并行查询（HTTP 客户端连接池预热）
4. TTL 权衡 —— 缓存 TTL 短则解析新但查询多，长则省查询但更新慢；
   权威服务器上把稳定记录 TTL 调大（3600+），变更期临时调小
5. search 域 —— resolv.conf 的 search 域太长会导致补全域名额外查询，精简；
   短主机名解析失败的场景优先用 hosts 而不是靠 search 域兜底
6. 并发上限 —— 高并发解析服务注意 /etc/resolv.conf 的 options timeout/attempts，
   默认超时 5s 会让故障放大成「每个查询卡 5 秒」，可调小并依赖缓存
7. IPv6 优先级 —— /etc/gai.conf 控制 AAAA/A 谁优先，双栈环境按需调整，
   避免「AAAA 不通拖慢整体连接」（可用 curl -4/-6 对比验证）
```

```shell
# 测量解析耗时（对比本机 stub 与公共 DNS）
dig example.com | grep 'Query time'          # 走 127.0.0.53（可能命中缓存）
dig @223.5.5.5 example.com | grep 'Query time'   # 直连阿里 DNS
ping -c 3 223.5.5.5                          # 测 DNS 服务器网络延迟
# 清缓存后再测才是真实上游耗时
resolvectl flush-caches && dig example.com | grep 'Query time'
```

## 安全与权限

```text
1. DNS 污染/劫持 —— 上游 DNS 被污染（如返回假 IP）会解析到恶意地址；
   用可信 DNS（DoH/DoT 公共解析）+ DNSSEC 校验；hosts 手动固定关键域名（本机 github.com 即此做法）
2. /etc/hosts 篡改 —— hosts 优先级最高，被篡改可把域名劫持到钓鱼 IP；
   注意文件权限（root:root 644），关键机器可 chattr +i 加不可变属性
3. 加密 DNS —— DoH/DoT 加密 DNS 查询，防中间人窃听/篡改解析内容；
   resolved 支持：resolvectl dnssec 启用校验，DNSOverTLS=yes（见本机 Protocols 里的
   DNSOverTLS=no，默认未开）
4. 缓存投毒 —— 攻击者伪造 DNS 响应注入缓存（Kaminsky 攻击）；
   现代解析器随机化端口/Query ID + 0x20 大小写随机化缓解，保持系统更新
5. 隐私 —— 解析记录会暴露访问过的域名；公共 DNS 的日志策略各不相同，
   敏感环境用自建 DNS（[[20.2-DNS 服务]]）+ DoT 上行
6. 权限 —— /etc/hosts、/etc/resolv.conf、/etc/hostname 属 root，普通用户不能改；
   hostnamectl/resolvectl 需要 root 或 polkit 授权
7. 主机名泄露 —— 主机名会出现在日志/SSH banner/网络里，别在主机名里放敏感信息
```

```shell
# 启用 DNSSEC 与 DoT（systemd-resolved，Ubuntu）
sudo mkdir -p /etc/systemd/resolved.conf.d
sudo tee /etc/systemd/resolved.conf.d/dnssec-dot.conf <<'EOF'
[Resolve]
DNSSEC=allow-downgrade
DNSOverTLS=opportunistic
EOF
sudo systemctl restart systemd-resolved
resolvectl status | grep -E 'DNSSEC|DNSOverTLS'   # 验证生效
```

## 故障排查

### 子案例一：域名解析失败（SERVFAIL / NXDOMAIN / timeout）

```shell
# 症状：dig example.com 报错或超时
# 1. 看错误类型
#    NXDOMAIN  = 域名确实不存在（或 search 域补全逻辑问题）
#    SERVFAIL  = 上游 DNS 本身解析失败（递归出问题、权威不可达）
#    timeout   = 网络不通 / 上游 DNS 不可达
dig example.com
# 2. 绕过本地直连公共 DNS，确认问题在哪一层
dig @8.8.8.8 example.com
# 3. 检查本地 DNS 服务与上游
resolvectl status
systemctl status systemd-resolved
# 4. 网络层确认 DNS 服务器可达
ping -c 2 192.168.1.1
# 5. 抓包看查询是否发出、有没有响应
sudo tcpdump -i wlp0s20f3 -n 'udp port 53' -c 10
```

### 子案例二：解析到错误 IP（hosts 残留 / 缓存 / 污染）

```shell
# 症状：域名能解析，但 IP 不对（连不上或连到错误服务器）
# 1. 应用真实链路解析到哪（可能被 hosts 劫持）
getent hosts example.com
# 2. 检查 hosts 有无错误映射（最常见原因，改过 hosts 忘了删）
grep example.com /etc/hosts
# 3. 绕过本地缓存问公共 DNS（排除本地缓存/污染）
dig @8.8.8.8 example.com
# 4. 本地缓存中的旧结果（TTL 内改了记录没生效）
resolvectl flush-caches && getent hosts example.com
# 5. 结果对比：
#    getent 与 dig @8.8.8.8 一致但不对 → 上游 DNS 被污染/权威记录错了
#    getent 与 dig 不一致 → hosts 或本地缓存问题
```

### 子案例三：DNS 查询慢 / 超时

```shell
# 症状：解析要好几秒，网页加载慢
# 1. 对比本机与公共 DNS 耗时
dig example.com | grep 'Query time'
dig @223.5.5.5 example.com | grep 'Query time'
# 2. 检查 search 域（短名查询会尝试 N 次补全，每次等到超时）
cat /etc/resolv.conf | grep search
# 3. 用 +time 限制超时看真实往返：查询一个不存在的短主机名
dig +time=2 +tries=1 nosuchhost
# 4. 检查上游 DNS 是不是不通（DHCP 给了已失效的 DNS）
resolvectl status | grep 'DNS Servers'
# 5. 多 DNS 场景注意 timeout/attempts：options timeout:2 attempts:2
echo 'options timeout:2 attempts:2' | sudo tee -a /etc/resolv.conf   # 静态模式
```

### 子案例四：主机名相关故障（旧名字残留 / 解析不一致）

```shell
# 症状：改了主机名，SSH/日志/服务还显示旧名
# 1. 当前主机名
hostnamectl status
# 2. /etc/hostname 内容（hostnamectl set-hostname 应已同步）
cat /etc/hostname
# 3. /etc/hosts 的 127.0.1.1 映射是否还是旧名（最常见原因）
grep 127.0.1.1 /etc/hosts
# 4. 反向解析验证（hostname -i 走 hosts/DNS 解析本机名）
hostname -i
getent hosts $(hostname)
# 5. 内核/hosts 缓存重载（改 hosts 一般立即生效，个别服务需重启）
# 6. 集群里其他机器 /etc/hosts 也要同步新主机名
```

## 常见问题

```text
Q1: 改了 resolv.conf 为什么被覆盖？
A: resolv.conf 由 systemd-resolved 生成（stub 模式），手动改会被覆盖。
   用 resolvectl set-dns（Ubuntu）或 nmcli connection modify ipv4.dns（NetworkManager）改。

Q2: 域名解析到错误 IP？
A: 先查 /etc/hosts 有没有错误映射（优先级最高），再看本地缓存
   （resolvectl flush-caches），最后 dig @8.8.8.8 对比排除上游污染。

Q3: dig 和 nslookup 结果不一致？
A: nslookup 可能走不同解析路径（系统解析器/缓存/搜索域）。以 dig 为准，
   对比 dig @8.8.8.8 排除本地干扰；要判断「应用实际解析到哪」用 getent hosts。

Q4: 改了主机名但有些服务还显示旧名字？
A: /etc/hosts 里的 127.0.1.1 旧映射没同步。改主机名后同步 /etc/hosts 的
   127.0.1.1 映射，并重启依赖主机名的服务。

Q5: getent hosts 和 dig 结果不一样？
A: 正常现象：getent 走 nsswitch（先查 hosts 文件，还受 mdns4_minimal 影响），
   dig 直接查 DNS 服务器。hosts 里有映射时 getent 返回 hosts 的 IP 而 dig 返回 DNS 的。
   以 getent 为准判断应用行为，以 dig 为准判断 DNS 本身。

Q6: 内网短主机名（如 gitlab）解析不了？
A: 需要 search 域配合：resolvectl set-domain <网卡> "~example.internal"，
   或直接写 /etc/hosts。短名不带点才会触发 search 域补全，带点（gitlab.example.internal.）
   是 FQDN 直查。

Q7: 改了 DNS 记录很久还不生效？
A: TTL 缓存问题。本地 resolvectl flush-caches，上游各递归服务器要等原 TTL 过期；
   紧急变更先在权威侧把 TTL 调小（如 60）再改记录。

Q8: ping 域名通但 curl/浏览器打不开？
A: 优先怀疑 IPv6：getent ahosts 看是否解析出 AAAA，而 IPv6 路由不通导致连接挂起。
   用 curl -4 强制 IPv4 验证；或 /etc/gai.conf 调整地址族优先级。
```

## 面试题

```text
1. Linux 解析域名的完整流程？
   答：应用调 getaddrinfo() → libc 按 /etc/nsswitch.conf 的 hosts 行顺序解析 →
   先查 /etc/hosts（files），命中即返回；未命中走 dns → 读 /etc/resolv.conf 的
   nameserver（Ubuntu 上是 systemd-resolved 的 stub 127.0.0.53）→ resolved 查缓存、
   转发给上游 DNS → 上游递归查询根/顶级/权威服务器返回结果并缓存。

2. /etc/hosts 和 DNS 的优先级？
   答：/etc/hosts 优先级高于 DNS（nsswitch.conf 的 hosts: files ... dns，files 在前）。
   改 hosts 立即生效、覆盖 DNS 结果；所以 hosts 是「快速覆盖解析结果」的手段，
   也是「错误映射污染解析」的高发地。

3. systemd-resolved 的 stub（127.0.0.53）是什么？
   答：本地 DNS 缓存/转发服务的入口，resolv.conf 指向它；应用查询发给 stub，
   resolved 再转发给真正的上游 DNS（由 DHCP/NetworkManager 提供，resolvectl status 查看），
   实现本地缓存 + 按网卡动态选择上游 + 统一管理 DNS 配置。

4. dig 相比 nslookup 的优势？
   答：dig 输出更详细（完整解析过程、权威服务器、TTL、耗时、服务器地址），
   支持 +short、+trace、@指定服务器、按类型查询，是 DNS 排错的首选工具；
   nslookup 输出简洁但信息少，历史遗留的交互式工具。

5. 递归查询和迭代查询的区别？
   答：递归 = 我替你查到底（客户端 → 本地 DNS，一次请求拿最终答案）；
   迭代 = 我只告诉你下一个问谁（本地 DNS → 根 → TLD → 权威，逐级获取指引）。
   客户端与本地 DNS 之间是递归，服务器之间是迭代。

6. CNAME 和 A 记录有什么区别？什么场景用 CNAME？
   答：A 记录直接把域名映射到 IP；CNAME 把域名映射到另一个域名（别名），
   最终还要再查目标域名的 A 记录。CDN、云负载均衡（域名会变，IP 不固定）、
   www 与裸域统一时用 CNAME；A 记录用于必须固定 IP 的场景（邮件、数据库直连）。

7. TTL 的作用是什么？
   答：DNS 记录的缓存有效期（秒）。TTL 短 → 记录更新快但查询多、负载高；
   TTL 长 → 省查询但变更生效慢。运维变更 DNS 时应先调小 TTL 再改记录。

8. 怎么判断域名被 DNS 污染/劫持了？
   答：对比多家可信 DNS：dig @8.8.8.8、dig @223.5.5.5 结果不一致，
   或结果 IP 归属可疑（whois/反查），而权威侧（dig +trace 或 dig @权威服务器）结果正常，
   说明中间层被污染。对策：DoH/DoT、DNSSEC、hosts 固定关键域名、换可信 DNS。
```

## 最佳实践与踩坑记录

### 最佳实践

1. DNS 排错用 dig（最详细），看「解析流程 + 哪个环节出错」；判断应用行为用 getent
2. /etc/hosts 优先级高于 DNS，改 hosts 能快速覆盖解析结果，但用完必须删
3. 测试环境改 hosts 指到测试服务器，加注释（# temp for test），防止遗忘
4. 主机名改完同步 /etc/hosts 的 127.0.1.1 映射，避免旧名字残留
5. 理解 systemd-resolved 的 stub（127.0.0.53），改 DNS 用 resolvectl/nmcli，别直接改 resolv.conf
6. 改权威 DNS 记录前先把 TTL 调小，变更完再调回，缩短故障窗口
7. hosts 文件定期审计（对比备份），防止积累垃圾映射；关键机器考虑 chattr +i
8. 生产环境禁止依赖「别人的 resolv.conf 是静态的」——统一用系统管理的 DNS 配置方式

### 踩坑记录

```text
坑 1：改了 resolv.conf 被 systemd-resolved 覆盖
结论：直接改 /etc/resolv.conf 的 nameserver，重启/重连后又被改回。
原因：resolv.conf 是 systemd-resolved 动态生成的（stub 模式），手动改无效。
解法：resolvectl set-dns <网卡> <IP>，或 nmcli connection modify ipv4.dns，
     静态环境可在 /etc/systemd/resolved.conf 配 DNS=。

坑 2：/etc/hosts 里有错误映射导致解析到错误 IP
结论：域名解析到错误的 IP，排查半天发现是 hosts 写错了（测试残留）。
原因：hosts 优先级最高，有映射就先用它，不查 DNS，且不报任何错。
解法：getent hosts 域名 看应用实际走哪，grep 域名 /etc/hosts 检查，
     删掉错误行，养成「临时映射加注释、用完即删」的习惯。

坑 3：改了主机名但 /etc/hosts 没同步
结论：hostnamectl set-hostname 后，sudo/SSH/监控还显示旧主机名。
原因：/etc/hosts 里的 127.0.1.1 旧映射没更新，反向解析拿到旧名。
解法：改主机名后同步 /etc/hosts 的 127.0.1.1 映射，重启相关服务。

坑 4：dig 和 nslookup 结果不一致
结论：dig 查的 IP 和 nslookup 查的不一样，以为系统坏了。
原因：两者走的解析路径不同（一个绕系统解析器、一个直查），还有 search 域/缓存差异。
解法：以 dig 为准（最直接），对比 dig @8.8.8.8 排除本地 DNS 干扰；
     判断应用实际解析结果用 getent hosts。

坑 5：DNS 查询慢，忘了用本地缓存
结论：每次解析都远程查询，页面加载慢。
原因：没配 DNS 缓存（systemd-resolved 被禁用/nscd 没装/服务端裸 resolv.conf）。
解法：启用 systemd-resolved 缓存，或本地搭 dnsmasq 缓存（[[20.2-DNS 服务]]）；
     resolvectl statistics 验证命中率。

坑 6：getent 和 dig 结果不一致，怀疑系统坏了
结论：curl 连的 IP 和 dig 查的不一样，服务访问异常。
原因：getent 走 nsswitch（files 优先），hosts 里有映射就返回 hosts 的 IP；
     dig 直查 DNS 服务器，两者结果不同是设计如此，不是故障。
解法：用 getent hosts 判断应用行为，用 dig 判断 DNS 本身；排查时两个都要看。

坑 7：search 域太长/太多导致解析慢或解析异常
结论：查询短主机名卡好几秒，或偶发解析失败。
原因：search 域补全要逐个尝试（web01. → web01.a.ts.net → web01.b.ts.net），
     每个失败都要等超时（默认 5s）或收到 NXDOMAIN。
解法：精简 search 域（只留必需的），短主机名走 /etc/hosts，
     或 options timeout:2 attempts:1 收紧超时。

坑 8：内网 DNS 配到 resolv.conf 不生效
结论：把 nameserver 写成内网 DNS（如 192.168.10.53），但查询还是走别的 DNS。
原因：Ubuntu 的 resolv.conf 是 stub 模式，nameserver 必须写 127.0.0.53；
     上游由 resolved 按网卡管理，直接写内网 IP 会被覆盖/忽略。
解法：resolvectl set-dns <网卡> 192.168.10.53，配合 set-domain 指定域名走该 DNS。

坑 9：改完 DNS 记录迟迟不生效
结论：权威服务器改了 A 记录，客户端还是旧 IP。
原因：各级缓存 TTL 未过期（本地 resolved、上游 8.8.8.8、ISP DNS 都可能缓存）。
解法：本地 resolvectl flush-caches；上游只能等 TTL 过期；
     下次变更先调小 TTL（如 60s）再改记录，等传播完调回。
```
