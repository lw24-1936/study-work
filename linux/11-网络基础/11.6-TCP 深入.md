## 概述

TCP 是可靠的传输层协议，核心机制：三次握手（建立连接）、四次挥手（关闭连接）、状态机（连接的生命周期状态）、TIME_WAIT（主动关闭方等待）、Keepalive（探测死连接）、拥塞控制（防止网络拥塞）。理解这些，才能看懂 `ss -tan` 里的各种状态、排查「连接堆积」「端口耗尽」「TIME_WAIT 过多」等线上问题。

```text
TCP 六要素：
1. 三次握手 —— SYN → SYN+ACK → ACK，建立连接
2. 四次挥手 —— FIN → ACK → FIN → ACK，关闭连接
3. 状态机 —— LISTEN/ESTABLISHED/TIME_WAIT 等状态
4. TIME_WAIT —— 主动关闭方等待 2MSL，防止残留包
5. Keepalive —— 定时探测，检测死连接
6. 拥塞控制 —— 慢启动/拥塞避免，防止网络拥塞
```

```text
TCP vs UDP 一句话：
TCP  可靠、有序、有连接（握手/重传/拥塞控制），代价是延迟和开销 —— 网页/文件/数据库
UDP  不可靠、无序、无连接，代价是可能丢包 —— DNS/音视频/游戏/实时传输
```

## 核心概念

TCP 的可靠性靠十个机制支撑：三次握手、四次挥手、状态机、序列号与确认号、滑动窗口、拥塞控制、超时重传、连接队列、TIME_WAIT、Keepalive。下面逐一展开。

### 三次握手

三次握手建立连接：客户端发 SYN → 服务端回 SYN+ACK → 客户端发 ACK，连接建立（ESTABLISHED）。为什么三次？因为要「双方都确认对方的收发能力」——两次不够（服务端不确定客户端能收到自己的 SYN+ACK），三次正好。握手失败（如 SYN 发出去没 ACK）就是「SYN_SENT」状态，大量 SYN_SENT 说明连不上目标。

```text
三次握手（带序列号）：
客户端                          服务端
  --- SYN (seq=x) ----------------->
  <-- SYN+ACK (seq=y, ack=x+1) -----
  --- ACK (seq=x+1, ack=y+1) ------>
  连接建立（双方进入 ESTABLISHED）
```

```text
# 实测（本机 tcpdump 抓到的真实握手，省略 options 细节）
$ timeout 15 tcpdump -i any -c 8 -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0'
12:21:46.671789 wlp0s20f3 Out IP 192.168.1.167.51334 > 116.140.43.136.443: Flags [S], seq 1300311516, win 64240, options [mss 1460,sackOK,TS val 958073291 ecr 0,nop,wscale 10], length 0
12:21:46.697049 wlp0s20f3 In  IP 116.140.43.136.443 > 192.168.1.167.51334: Flags [S.], seq 2537011155, ack 1300311517, win 65535, options [mss 1440,sackOK,TS val 3845935446 ecr 958073291,nop,wscale 10], length 0
8 packets captured
# 第 1 包 [S]：客户端 seq=1300311516（x），win 64240，通告 mss 1460、SACK、时间戳、wscale 10
# 第 2 包 [S.]：服务端 seq=2537011155（y），ack=1300311517（x+1）——确认收到客户端的 SYN
# 第 3 包 [.] ack=y+1 未截到（被后续数据包淹没），但握手已完成
# 注意服务端 mss 1440 < 客户端 1460：实际用较小值（MTU 路径差异）
```

### 四次挥手

四次挥手关闭连接：主动方发 FIN → 被动方回 ACK → 被动方发 FIN → 主动方回 ACK，连接关闭。为什么四次？因为 TCP 是「全双工」——双方各有一个方向要关闭，所以 FIN 和 ACK 分开（比握手多一次）。主动关闭方最后进入 TIME_WAIT 状态，等待 2MSL 后才完全关闭。

```text
四次挥手：
主动方                          被动方
  --- FIN (seq=m) --------------->
  <-- ACK (ack=m+1) -------------  半关闭：主动方不再发数据，还能收
  <-- FIN (seq=n) ---------------  被动方数据发完后也关闭
  --- ACK (ack=n+1) ------------->
  主动方进入 TIME_WAIT，等 2MSL 后关闭
```

为什么挥手是四次而握手是三次：握手时服务端的 SYN 和 ACK 可以合并成一个包（SYN+ACK，因为服务端没有「还要先发完数据」的问题）；挥手时被动方收到 FIN 后可能还有数据要发，ACK 和 FIN 必须分开（被动方要先 ACK 表示收到 FIN，等自己数据发完再发 FIN）。

### 状态机

TCP 连接有一系列状态（`ss -tan` 的 State 列）：LISTEN（监听）、SYN_SENT（发了 SYN 等 ACK）、SYN_RECV（收到 SYN 回了 ACK 等确认）、ESTABLISHED（已建立）、FIN_WAIT（关闭中）、CLOSE_WAIT（收到 FIN 但自己没关）、TIME_WAIT（主动关闭等待）、CLOSED（关闭）。排查连接问题就是看「哪些状态堆积」——CLOSE_WAIT 堆积说明服务没正确关闭连接（代码 bug），TIME_WAIT 过多说明短连接频繁。

```text
# 实测（本机 TCP 连接状态统计）
$ ss -tan | awk 'NR>1{print $1}' | sort | uniq -c
      1 CLOSE-WAIT
     10 ESTAB
     53 LISTEN
      9 SYN-SENT
      4 TIME-WAIT
# 53 个 LISTEN（本机跑了很多 docker 容器端口映射），10 个 ESTAB（正常连接）
# 9 个 SYN-SENT 值得关注：chrome 连被墙的 Google IP 全部卡在 SYN_SENT（见故障排查案例）
```

```text
关键状态含义：
LISTEN     监听中，等连接（服务端 bind+listen 后）
SYN_SENT   发了 SYN 等对方 ACK（连不上时会堆积）
SYN_RECV   收到 SYN 回了 SYN+ACK 等确认（半连接队列里）
ESTAB      已建立（正常通信）
FIN_WAIT_1 发了 FIN 等对方 ACK
FIN_WAIT_2 收到 ACK，等对方 FIN
CLOSE_WAIT 收到 FIN 但自己没调 close（服务代码没 close，会泄漏）
LAST_ACK   发了 FIN 等对方最后的 ACK
TIME_WAIT  主动关闭方等待 2MSL（短连接多时会堆积）
CLOSED     完全关闭
```

```text
状态机迁移（简化）：
客户端视角：CLOSED → SYN_SENT → ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
服务端视角：CLOSED → LISTEN → SYN_RECV → ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED
```

### 序列号与确认号

TCP 的每个字节都有序号（seq），接收方用确认号（ack）告诉对方「下一个期望收到的字节」。这是可靠传输的地基：接收方能据此检测丢包（seq 跳号）、去重（重复 seq）、排序（乱序重组）。

```text
seq 与 ack 的关系：
发送方发 (seq=100, len=50)  —— 表示这包数据是字节 100~149
接收方回 ack=150           —— 表示 100~149 已收到，期望下一个字节是 150
初始 seq 不是 0 而是随机数（防预测攻击/防旧包混淆），三次握手时交换

# 实测（本机 tcpdump 数据阶段，seq/ack 递增关系一目了然）
12:22:22.484259 IP 116.140.43.136.443 > 192.168.1.167.41928: Flags [P.], seq 27:683, ack 1, win 750, length 656
12:22:22.486740 IP 192.168.1.167.41928 > 116.140.43.136.443: Flags [.], ack 707, win 1040, length 0
# 服务端发 seq 27:683（27 起 656 字节），客户端回 ack 707（=27+656+27，下一条 seq 707 继续）
# win 750 是缩放后的窗口值（wscale 10，实际 750×1024=768000 字节）
```

### 滑动窗口与流量控制

接收方在 ACK 里通告自己的接收窗口（win），告诉发送方「我还能收多少字节」，发送方据此控制一次能发多少未确认数据——这就是流量控制，防止发送方把接收方缓冲区打爆。窗口是动态的：接收方处理慢，窗口变小；处理快，窗口变大。现代 TCP 用窗口缩放（window scaling，wscale 选项）把窗口从 64KB 扩展到最大 1GB，适应高速网络。

```text
窗口机制：
1. 发送窗口 = min(接收方通告的 rwnd, 拥塞窗口 cwnd)
2. 已发送未确认的数据量不能超过窗口
3. 接收方每次 ACK 都更新通告窗口（win 字段）
4. 窗口为 0 时发送方停止发送，等对方窗口更新（zero window 探测）
```

```text
# 实测（本机参数，窗口缩放开启）
$ sysctl net.ipv4.tcp_window_scaling net.ipv4.tcp_rmem net.ipv4.tcp_wmem
net.ipv4.tcp_window_scaling = 1
net.ipv4.tcp_rmem = 4096	131072	33554432   # 接收缓冲 min/默认/max（字节）
net.ipv4.tcp_wmem = 4096	16384	4194304    # 发送缓冲 min/默认/max
# tcp_rmem max 32MB：配合 wscale 才能在长肥管道上跑满带宽
```

### 拥塞控制

拥塞控制是 TCP「防止把网络塞爆」的机制：通过慢启动（slow start，逐步加大发送窗口）、拥塞避免（达到阈值后线性增长）、快速重传/恢复（丢包时快速恢复）动态调整发送速率。核心是「拥塞窗口 cwnd」——根据网络状况（丢包、RTT）自适应调整。算法有 cubic（Linux 默认）、reno、bbr（Google 的，高吞吐场景优）。Linux 用 `sysctl net.ipv4.tcp_congestion_control` 查看/设置。

```text
拥塞控制四阶段：
1. 慢启动 —— cwnd 从 1 开始指数增长（每 RTT 翻倍），快速探测可用带宽
2. 拥塞避免 —— cwnd 达到 ssthresh 后线性增长（每 RTT +1），缓慢逼近上限
3. 快重传 —— 收到 3 个重复 ACK 立即重传丢失包（不用等 RTO 超时）
4. 快恢复 —— 重传后 cwnd 减半而不是回到 1，避免带宽断崖

丢包判定两种：
- 超时重传（RTO 到期）→ 网络可能很糟，cwnd 回到 1（慢启动重来）
- 重复 ACK（3 次）→ 网络还行，走快重传/快恢复，cwnd 减半
```

```text
算法对比：
cubic    Linux 默认，BIC 改进，适合大部分场景（尤其高带宽长链路）
reno     经典算法，线性恢复，拥塞窗口增长慢，性能一般
bbr      Google 提出，不靠丢包判拥塞（用带宽×RTT 建模），高吞吐低延迟
vegas    基于延迟的算法，丢包少但激进抢占弱，实际部署少
```

```shell
sysctl net.ipv4.tcp_congestion_control          # 看当前算法（本机 cubic）
sysctl net.ipv4.tcp_available_congestion_control  # 看内核可用算法列表
sysctl -w net.ipv4.tcp_congestion_control=bbr   # 切 bbr（需内核模块支持）
```

```text
# 实测（本机拥塞算法与 BBR 可用性）
$ sysctl net.ipv4.tcp_congestion_control
net.ipv4.tcp_congestion_control = cubic
# Ubuntu 22.04 内核默认编译了 bbr 模块，切 bbr 前确认：
$ sysctl net.ipv4.tcp_available_congestion_control
reno cubic bbr   # 有 bbr 即可直接切换（示例输出）
Red Hat 系差异：RHEL 8+ 同样内置 bbr；老内核（3.x）需 modprobe tcp_bbr 或升级内核
```

### 超时重传（RTO）

发送方发出数据后启动定时器，超时未收到 ACK 就重传——超时时间叫 RTO（Retransmission Timeout）。RTO 不是固定值，而是根据实测 RTT 动态计算（SRTT 平滑 + RTTVAR 抖动），还要指数退避（重传一次 RTO 翻倍），避免网络拥塞时重传风暴。SYN 重传也走同样的退避逻辑。

```text
RTO 计算（RFC 6298）：
SRTT = 0.875*SRTT + 0.125*RTT           平滑 RTT
RTTVAR = 0.75*RTTVAR + 0.25*|SRTT-RTT|  抖动
RTO = SRTT + 4*RTTVAR                    初始下限 1 秒
重传一次后 RTO 翻倍（退避）：1s → 2s → 4s → 8s → 16s → 32s → 64s（上限）
```

```text
# 实测（本机 SYN 重传的退避现场：ss -ti 看 SYN-SENT 连接的 RTO）
$ ss -ti | head -8
SYN-SENT  0  1  192.168.1.167:40300  172.253.117.139:https
	 cubic rto:64000 backoff:6 mss:524 pmtu:1500 rcvmss:88 advmss:1460 cwnd:1 ssthresh:7
	 segs_out:11 lastsnd:1984521161 retrans:1/10 lost:1
# rto:64000 = RTO 已退避到 64 秒（1s→2s→...→64s 第 7 次重传）；backoff:6 = 已退避 6 次
# mss:524 = 重传多次后把 MSS 降到最小（探测路径 MTU 失败的自保行为）
# retrans:1/10 = 发了 10 个包重传 1 个；这个连接对端根本不可达（Google IP 被墙）
```

### 半连接队列与全连接队列

服务端 listen 后内核维护两个队列：半连接队列（SYN 队列，存收到 SYN 还没完成握手的连接，长度 tcp_max_syn_backlog）和全连接队列（accept 队列，存已完成握手等应用 accept 的连接，长度 backlog=min(somaxconn, listen 的 backlog 参数)）。队列满的症状：半连接满 = 客户端 SYN 无响应（SYN 洪水特征）；全连接满 = 握手完成但应用不 accept，客户端连接建立慢/超时。

```text
两个队列在握手流程中的位置：
客户端 SYN → 半连接队列（SYN_RECV）→ 收到 ACK 完成握手 → 全连接队列（ESTABLISHED 等 accept）
→ 应用 accept() 取走 → 正常通信

查看方式：
ss -lnt 的 Send-Q 列 = 全连接队列长度上限（backlog）
Recv-Q 列 = 当前积压的已完成握手但没被 accept 的连接数
ss -lnt state syn-recv 看半连接队列里的连接
```

```text
# 实测（本机 ss -lnt 的队列长度）
$ ss -lnt | head -8
State  Recv-Q Send-Q  Local Address:Port   Peer Address:Port
LISTEN 0      4096    0.0.0.0:3306         0.0.0.0:*    # docker-proxy（MySQL）
LISTEN 0      511     0.0.0.0:3000         0.0.0.0:*    # node 服务
LISTEN 0      511     0.0.0.0:80           0.0.0.0:*    # nginx
LISTEN 0      5       0.0.0.0:8888         0.0.0.0:*    # python3 服务（backlog 只给了 5！）
# Send-Q = backlog 上限：docker-proxy 4096、nginx 511、python3 只有 5
# Recv-Q = 当前积压数（都是 0 = 没有排队等待 accept 的连接）
# python3 服务 backlog=5：并发瞬间打进来很容易溢出（高并发应用要调大）
```

```shell
sysctl net.ipv4.tcp_max_syn_backlog   # 半连接队列上限（本机 2048）
sysctl net.core.somaxconn             # 全连接队列全局上限（本机 4096）
ss -lnt | awk 'NR>1 && $2>0'          # 找出有积压的监听端口（Recv-Q 不为 0）
```

### TIME_WAIT

TIME_WAIT 是「主动关闭方」在关闭后等待 2MSL（约 60 秒）的状态——作用：确保最后一个 ACK 到达（丢了对方会重发 FIN，需要时间等它）、让残留的旧包消亡（防止旧包串到新连接）。TIME_WAIT 是正常的、必要的，但「短连接频繁」（如高频 HTTP 请求）时会产生大量 TIME_WAIT，耗尽端口（默认约 2.8 万个）。调优：内核参数 tcp_tw_reuse（复用 TIME_WAIT）、减少短连接（长连接/连接池）。

```text
为什么是 2MSL：
MSL（Maximum Segment Lifetime）= 报文在网络上的最大存活时间（Linux 默认 60 秒）
1 个 MSL 等自己最后的 ACK 到达对方（以及对方可能重发的 FIN 回来）
2 个 MSL 保证「旧连接的所有报文都已消亡」——新连接的四元组复用后不会收到旧包
所以 tcp_fin_timeout 默认 60 秒（Linux 的 TIME_WAIT 计时实际由它控制）

TIME_WAIT 堆积的端口消耗：
本地端口范围 32768~60999 = 28232 个端口
每个短连接占一个（本地端口, 远端 IP, 远端端口）三元组
短连接频率 × 60 秒 > 28232 就会端口耗尽 → 新连接报 Cannot assign requested address
```

```shell
ss -tan state time-wait | wc -l        # 统计 TIME_WAIT 数量
sysctl net.ipv4.tcp_tw_reuse           # 查看复用参数（本机 = 2，见下）
sysctl -w net.ipv4.tcp_tw_reuse=1      # 开启 TIME_WAIT 复用（临时）
cat /proc/sys/net/ipv4/ip_local_port_range   # 本地端口范围
```

```text
# 实测（本机 TIME_WAIT 与端口范围）
$ ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | grep -i time
      4 TIME-WAIT
$ cat /proc/sys/net/ipv4/ip_local_port_range
32768	60999
# 端口范围 32768~60999 共 28232 个可用端口
# TIME_WAIT 只有 4 个（本机短连接少），正常水平；若上万个就要处理了

tcp_tw_reuse 取值（内核 5.x 起支持 2）：
0 = 不复用；1 = 允许复用（新连接四元组不冲突时）；2 = 仅回环地址复用
# 本机实测 net.ipv4.tcp_tw_reuse = 2（Ubuntu 22.04 默认，只对 loopback 复用，安全）
# 注意：tcp_tw_reuse 只对「发起连接方」生效，服务端（被动方）TIME_WAIT 不受它控制
```

```text
TIME_WAIT 要点：
1. 正常状态 —— 主动关闭方都要经历，约 60 秒
2. 堆积原因 —— 短连接频繁（每次请求都新建连接）
3. 端口耗尽 —— 大量 TIME_WAIT 占端口，新连接失败（Cannot assign requested address）
4. 解法 —— 客户端场景 tcp_tw_reuse；更优是长连接/连接池；服务端场景调 tcp_max_tw_buckets
```

### Keepalive

TCP Keepalive 是「探测死连接」的机制——连接长时间没数据时，定期发探测包，对端不响应就判定连接已死并关闭。用途：防止「对端宕机但连接还挂着」导致的资源泄漏（如 SSH 长时间不操作、数据库连接池）。内核参数 tcp_keepalive_time（多久开始探测）、tcp_keepalive_intvl（探测间隔）、tcp_keepalive_probes（探测次数）。注意：TCP Keepalive 是协议层探测，和应用层心跳（HTTP keep-alive）不是一回事。

```shell
sysctl net.ipv4.tcp_keepalive_time       # 默认 7200 秒（2 小时）
sysctl net.ipv4.tcp_keepalive_intvl      # 探测间隔 75 秒
sysctl net.ipv4.tcp_keepalive_probes     # 探测次数 9 次
```

```text
# 实测（本机 Keepalive 参数，Ubuntu 默认值）
```

## 工作原理

TCP 连接在 Linux 内核里是一条「状态机」，状态迁移由收发报文的类型驱动：服务端 bind+listen 进入 LISTEN，收到 SYN 回 SYN+ACK 进 SYN_RECV，收到 ACK 进 ESTABLISHED。关闭时主动方发 FIN 进 FIN_WAIT，收到 FIN 回 ACK 进 TIME_WAIT；被动方收到 FIN 进 CLOSE_WAIT（等应用调 close）。内核把连接表暴露在 /proc/net/tcp 和 netlink，ss/netstat 从这里读状态。

```text
连接生命周期（完整状态迁移）：
客户端：CLOSED → SYN_SENT → ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
服务端：CLOSED → LISTEN → SYN_RECV → ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED

内核视角：
1. 每个连接是内核 socket 对象（struct tcp_sock），状态记录在连接表里
2. ss 读 netlink socket、netstat 读 /proc/net/tcp，都是同一份状态
3. 状态堆积 = 某一步卡住（CLOSE_WAIT 卡在应用没 close，SYN_SENT 卡在连不上）
4. 连接建立走两个队列：半连接队列（SYN_RECV）→ 全连接队列（等 accept）
```

```text
# 实测（本机 /proc/net/tcp 与内核连接表）
$ ls /proc/net/tcp /proc/net/tcp6
/proc/net/tcp  /proc/net/tcp6
$ head -2 /proc/net/tcp
  sl  local_address rem_address   st tx_queue rx_queue tr tm->when retrnsmt   uid  timeout inode
   0: 00000000:4C4E 00000000:0000 0A 00000000:00000000 00:00000000 00000000   115        0 360634 1
# st=0A（十六进制）是 LISTEN；0x4C4E=19530 端口；地址小端序存储
# netstat 就是解析这个文件的；ss 走 netlink 更高效
```

滑动窗口与拥塞窗口共同决定发送速率：`实际发送窗口 = min(接收方通告窗口 rwnd, 拥塞窗口 cwnd)`。rwnd 管「别把接收方打爆」（流量控制），cwnd 管「别把网络塞爆」（拥塞控制）。数据发出后，接收方每收一段就回 ACK（可能捎带延迟确认），发送方用「未确认字节数 < 窗口」来节制发送节奏。

```text
发送节奏：
1. 应用 write → 内核发送缓冲区 → 按窗口大小分包发出
2. 收到 ACK → 窗口前移 → 继续发
3. 窗口为 0（接收方忙）→ 停止发送，定期发窗口探测
4. 丢包（重复 ACK/RTO）→ 快重传或超时重传 + 缩小 cwnd
```

## 应用场景实战

### 场景一：CLOSE_WAIT 堆积，排查服务没关闭连接

线上服务连接数只增不减，ss 看到大量 CLOSE_WAIT：

```shell
# 1. 看 CLOSE_WAIT 堆积量
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c
# 2. 定位到具体进程和端口
ss -tanp | grep CLOSE-WAIT
# 3. 按本地端口聚合，找出哪个服务在泄漏
ss -tan | awk '$1=="CLOSE-WAIT"{print $4}' | sort | uniq -c | sort -rn
```

```text
# 实测（本机 CLOSE-WAIT 现状，正常量级）
$ ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | grep -i close
      1 CLOSE-WAIT
# 只有 1 个：正常。若上千个就是服务端没 close 的代码 bug
判定：CLOSE_WAIT = 本端服务收到对端 FIN 后没调 close（或 close 慢/被阻塞）
排查方向：连接池不回收、异常分支没关 socket、read 循环没退出、GC 延迟（JVM）
```

### 场景二：TIME_WAIT 过多导致端口耗尽

高并发短连接服务（如大量请求第三方 API）报 `Cannot assign requested address`：

```shell
# 1. 统计 TIME_WAIT
ss -tan state time-wait | wc -l
# 2. 看是否接近端口上限
cat /proc/sys/net/ipv4/ip_local_port_range   # 32768 60999 = 约 2.8 万个
# 3. 客户端场景：开启复用
sysctl -w net.ipv4.tcp_tw_reuse=1
# 4. 更优解：应用层用连接池/长连接，从源头减少短连接
```

```text
# 实测（本机端口范围与 TIME_WAIT 量）
$ cat /proc/sys/net/ipv4/ip_local_port_range
32768	60999
$ ss -tan state time-wait | wc -l
5
# 5 个 TIME_WAIT 完全正常。判断「多不多」的标准不是绝对数，
# 而是「新连接是否失败」：没失败就不用动
处理优先级：连接池/长连接 > tcp_tw_reuse > 扩大端口范围
tcp_tw_reuse 只对发起方生效；服务端（被动方）TIME_WAIT 靠 tcp_max_tw_buckets 兜底
```

### 场景三：半连接队列满（SYN 洪水 / 握手背压）

服务突然连不上，客户端报「connect timeout」，服务端 ss 看到 SYN_RECV 堆积：

```shell
# 1. 服务端看半连接队列（SYN_RECV 数量）
ss -tan state syn-recv | wc -l
# 2. 看全连接队列积压（Recv-Q 不为 0 的监听端口）
ss -lnt | awk 'NR>1 && $2>0'
# 3. 看队列满的统计（netstat -s 有溢出计数）
netstat -s | grep -iE 'overflow|drop'
# 4. 应急：确认 syncookies 开着（队列满时兜底）
sysctl net.ipv4.tcp_syncookies
# 5. 调大队列
sysctl -w net.ipv4.tcp_max_syn_backlog=4096
sysctl -w net.core.somaxconn=4096
# 应用层 listen 的 backlog 也要同步调大（如 nginx 的 listen backlog 指令）
```

```text
判定：SYN_RECV 堆积 + 客户端 SYN 无响应 = 半连接队列满
可能原因：
1. 真 SYN 洪水（攻击）—— syncookies 兜底 + 防火墙限速（见安全章节）
2. 应用 accept 太慢 → 全连接队列满 → 半连接队列也堵 —— 查应用处理能力
3. backlog 配太小（如 python3 服务的 5）—— 调 somaxconn 和应用 backlog
```

### 场景四：BBR 启用与效果验证

跨地域大文件传输带宽利用率低（cubic 丢包敏感），切 BBR 提升吞吐：

```shell
# 1. 确认内核支持
sysctl net.ipv4.tcp_available_congestion_control   # 应含 bbr
# 2. 切换（需要 root）
sysctl -w net.ipv4.tcp_congestion_control=bbr
# 3. 持久化
echo 'net.ipv4.tcp_congestion_control=bbr' > /etc/sysctl.d/99-bbr.conf
sysctl -p /etc/sysctl.d/99-bbr.conf
# 4. 验证生效（新连接才用新算法）
sysctl net.ipv4.tcp_congestion_control
ss -ti | grep -m1 bbr
# 5. 效果对比：iperf3 测切换前后的吞吐和重传
iperf3 -c <对端> -t 60
```

```text
# 实测（本机当前为 cubic，切换命令如上）
$ sysctl net.ipv4.tcp_congestion_control
net.ipv4.tcp_congestion_control = cubic
注意：切换算法影响该主机所有新连接，先在测试机压测对比再上生产

```

## 性能与调优

```text
1. TIME_WAIT 多优先用连接池/长连接，其次才 tcp_tw_reuse（别一上来就改内核参数）
2. 高吞吐/长肥管道（跨地域大文件传输）可试 bbr，比 cubic 更能利用带宽
3. tcp_fin_timeout 调小能加速回收 FIN_WAIT_2 连接，但太短可能丢 FIN
4. tcp_keepalive_time 默认 2 小时太长，内网服务可调到分钟级快速发现死连接
5. 端口耗尽先看 ip_local_port_range 和连接复用情况，别盲目扩大范围
6. 高并发服务调大 somaxconn + 应用 backlog（nginx listen backlog、Java 的 backlog 参数）
7. 长连接空闲场景可关 tcp_slow_start_after_idle=0，避免空闲后 cwnd 重置导致首包慢
8. TCP_NODELAY 关闭 Nagle 算法：小包场景（交互/游戏）降低延迟，代价是包数增加
```

```text
Nagle 算法与延迟确认：
Nagle —— 小数据包攒着等 ACK 一起发（减少小包），但会引入延迟；交互场景用 TCP_NODELAY 关掉
延迟确认 —— 接收方故意等 40ms 再回 ACK（凑更多数据一起确认），与 Nagle 叠加会互相等待
经典坑：Nagle（发送方）+ 延迟确认（接收方）互相等 = 40ms 级延迟，TCP_NODELAY 可破
Java：socket.setTcpNoDelay(true)；Go：net.Dialer 默认已禁用 Nagle
```

```text
40G/长肥管道（BDP 大）调优要点：
BDP（带宽延迟积）= 带宽 × RTT = 40Gbps × 100ms = 500MB —— 窗口必须能覆盖它
1. tcp_rmem/tcp_wmem max 调到 64MB+（默认 32MB 不够）
2. 确认 tcp_window_scaling=1（wscale 支持 1GB 窗口）
3. tcp_congestion_control=bbr（cubic 在高丢包长链路下难跑满）
4. 多队列网卡 + RSS/多核收包（irqbalance），单核处理不过来
5. 关闭 tcp_slow_start_after_idle（长连接场景）
6. 检查 ethtool 是否协商到全速 + 无误码（rx_crc_errors）
7. 用 iperf3 -P 多流验证单流是否成为瓶颈
```

## 安全与权限

```text
1. SYN 洪泛 —— 攻击者发大量 SYN 不完成握手，占满半连接队列（防护：tcp_syncookies + tcp_max_syn_backlog + 防火墙限速）
2. tcp_tw_recycle 已废弃（内核 4.12 移除）：NAT 下会误杀连接，别再用（本机实测该文件已不存在）
3. TCP Keepalive 不加密、不鉴权，别用它传递敏感数据，只用于探测死活
4. 改内核参数要 root，生产变更先压测：bbr/cubic 切换影响所有连接
5. 连接状态暴露进程/端口信息，ss -tanp 输出含进程名，排查时注意脱敏
6. 端口扫描（nmap -sS）是 SYN 洪泛的近亲：-sS 半开扫描只发 SYN 不收 ACK，未授权扫描违规
7. 未授权连接（accept 队列被恶意占满）会拖垮服务，配合防火墙白名单 + 连接数限制（nf_conntrack 限制）
```

```text
SYN 洪水防护组合拳：
1. net.ipv4.tcp_syncookies = 1   —— 队列满时用 Cookie 验证客户端（无状态，不占队列）
2. net.ipv4.tcp_max_syn_backlog 调大 —— 给正常连接更多队列空间
3. nftables 限速 —— 对单 IP 的 SYN 速率限制（见 [[12.2-nftables]]）
4. 应用层 —— 缩短 accept 处理时间，避免队列被占满
原理：syncookies 开启后，服务端不回 SYN_RECV 队列条目，而是把连接状态编码进
SYN+ACK 的 seq 里（Cookie），客户端回 ACK 时携带 Cookie 校验通过才建连接——
攻击者伪造 IP 发 SYN 时根本收不到 Cookie 也就无法完成握手，半连接队列不再被耗尽
```

```text
# 实测（本机安全相关参数）
$ sysctl net.ipv4.tcp_syncookies net.ipv4.tcp_abort_on_overflow
net.ipv4.tcp_syncookies = 1        # SYN Cookie 已开启
net.ipv4.tcp_abort_on_overflow = 0 # 队列满时丢弃新连接（不 RST），防信息泄露
```

## 故障排查

### 案例一：CLOSE_WAIT 堆积（连接泄漏）

现象：服务连接数持续增长不回落，重启才恢复。

```shell
# 1. 统计各状态的连接数
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c
# 2. CLOSE_WAIT 多 = 本端服务没 close，定位进程
ss -tanp | grep CLOSE-WAIT
# 3. 按端口聚合找服务
ss -tan | awk '$1=="CLOSE-WAIT"{print $4}' | sort | uniq -c | sort -rn
# 4. 查代码：收到 FIN（对端关闭）后是否漏调 close/未释放 socket
```

```text
# 实测（本机 CLOSE-WAIT 只有 1 个，正常；堆到成百上千就是故障）
$ ss -tan | awk 'NR>1{print $1}' | sort | uniq -c
      1 CLOSE-WAIT
     10 ESTAB
     53 LISTEN
      9 SYN-SENT
      4 TIME-WAIT
根因方向：
- 代码：异常分支没 close、read 到 EOF 没退出循环、连接池借出不还
- 框架：线程池拒绝策略直接丢任务（socket 没人关）、GC 暂停导致 close 延迟
- 验证：strace -p <pid> -e trace=close 看 close 调用频率；堆 dump 数 socket 对象
```

### 案例二：半连接队列满（握手背压）

现象：客户端 connect 超时，服务端 CPU 不高但新连接进不来。

```shell
# 1. 服务端看 SYN_RECV 堆积
ss -tan state syn-recv | wc -l
# 2. 看监听队列积压（Recv-Q 列）
ss -lnt | awk 'NR>1 && $2>0'
# 3. 看溢出计数
netstat -s | grep -iE 'overflow|drop'
# 4. 应急：调大队列 + 确认 syncookies
sysctl -w net.ipv4.tcp_max_syn_backlog=4096
sysctl -w net.core.somaxconn=4096
sysctl net.ipv4.tcp_syncookies
# 5. 根治：应用 accept 要快（线程池/事件循环别阻塞）
```

```text
判定表：
SYN_RECV 多 + 客户端 SYN 无响应    半连接队列满（SYN 洪水或服务端不回包）
Recv-Q 持续 >0                    全连接队列满（应用 accept 慢）
应用 accept 慢的常见原因：单线程 accept、线程池满、accept 后同步处理阻塞
```

### 案例三：端口耗尽（Cannot assign requested address）

现象：日志报 `java.net.BindException: Cannot assign requested address` 或 `connect: Cannot assign requested address`。

```shell
# 1. 看 TIME_WAIT 数量与端口范围
ss -tan state time-wait | wc -l
cat /proc/sys/net/ipv4/ip_local_port_range
# 2. 看四元组是否真的被占满（2.8 万个 TIME_WAIT 才是问题）
ss -tan | grep -c TIME-WAIT
# 3. 客户端场景：复用 TIME_WAIT
sysctl -w net.ipv4.tcp_tw_reuse=1
echo 'net.ipv4.tcp_tw_reuse=1' >> /etc/sysctl.conf
# 4. 根治：连接池（HTTP 连接池、数据库连接池），减少新建连接
```

```text
# 实测（本机端口范围，判断依据）
$ cat /proc/sys/net/ipv4/ip_local_port_range
32768	60999
# 可用端口 = 60999-32768+1 = 28232 个
# 短连接 TPS × 60 秒（TIME_WAIT 时长）> 28232 就会耗尽
# 例：500 TPS 的短连接服务，60 秒内产生 30000 个 TIME_WAIT，超过 28232，必然耗尽
```

### 案例四：连接建立慢（SYN 重传）

现象：连服务要等几秒到几十秒，通了之后一切正常。

```shell
# 1. 客户端看卡在 SYN_SENT 的连接
ss -tan state syn-sent
# 2. 看重传细节（rto/backoff/retrans）
ss -ti | grep -A1 SYN-SENT
# 3. 服务端抓包确认 SYN 到没到
timeout 10 tcpdump -i any -nn 'tcp port <端口>' -c 20
```

```text
# 实测（本机 SYN-SENT 现场：chrome 连被墙的 Google IP）
$ ss -tanp | grep SYN-SENT | head -3
SYN-SENT  0  1  192.168.1.167:36492  74.125.195.102:443  users:(("chrome",pid=4148777,fd=46))
SYN-SENT  0  1  192.168.1.167:40300  172.253.117.139:443  users:(("chrome",pid=66169,fd=86))
$ ss -ti | grep -A1 '74.125' | head -3
	 cubic rto:64000 backoff:6 mss:524 cwnd:1 ssthresh:7 retrans:1/10 lost:1
# rto 已退避到 64 秒 = 重传了 7 次还没成功
# 判定：SYN 发出无响应 = 对端防火墙 DROP / 路由不可达 / 对端没监听且不回 RST
排查：ping 对端（通不通）、nc -zv 对端端口（refused=服务没起，超时=防火墙/路由）、
tcpdump 看是否有 [S.] 回来（没有 = 被丢弃）
```

## 常见问题

```text
Q1: TIME_WAIT 多了要不要担心？
A: 先看是否真的端口耗尽（新连接失败）。没耗尽就正常，耗尽才用连接池/tcp_tw_reuse 解决。
   判断标准是「新连接是否失败」，不是绝对数量。

Q2: CLOSE_WAIT 和 TIME_WAIT 的区别？
A: CLOSE_WAIT 是被动方收到 FIN 没 close（代码 bug，会泄漏，要查代码）；
   TIME_WAIT 是主动方关闭后的正常等待（2MSL），短连接多时会堆积。

Q3: TCP Keepalive 和 HTTP keep-alive 是同一个吗？
A: 不是。TCP Keepalive 传输层探测死连接（内核参数 tcp_keepalive_*）；
   HTTP keep-alive 应用层复用连接发请求（Connection 头）。

Q4: 三次握手为什么不是两次或四次？
A: 两次无法让服务端确认客户端能收到（服务端不确定自己的 SYN+ACK 是否被收到）；
   三次正好双向确认收发能力。四次没必要——服务端可把 SYN+ACK 合并。

Q5: 为什么主动关闭方要等 TIME_WAIT？
A: 两个作用：确保最后一个 ACK 到达（丢了对方会重发 FIN，需要时间等待）；
   让旧连接残留包消亡（2MSL 后网络里不会有旧包，防止串到新连接）。

Q6: 半连接队列和全连接队列满了有什么区别？
A: 半连接满 = 客户端 SYN 无响应（SYN 洪水特征，tcp_max_syn_backlog 控制）；
   全连接满 = 握手完成但应用不 accept（Recv-Q 积压，somaxconn/backlog 控制）。
   半连接满用 syncookies 兜底，全连接满要查应用处理能力。

Q7: tcp_tw_reuse 对服务端有效吗？
A: 无效。tcp_tw_reuse 只对「主动发起连接方」生效（客户端）；
   服务端的 TIME_WAIT 靠 tcp_max_tw_buckets 兜底（超限强制回收）或改长连接。

Q8: 为什么抓包看到服务端回了 SYN+ACK 但客户端还重传 SYN？
A: 回包被中间设备丢弃（防火墙/路由），或客户端没收到。在客户端抓包确认
   [S.] 是否到达；没到就查客户端到服务端的路径（mtr）和防火墙。
```

## 面试题

```text
1. 三次握手和四次挥手的过程？
   答：三次握手 SYN(seq=x) → SYN+ACK(seq=y,ack=x+1) → ACK(ack=y+1) 建立连接；
   四次挥手 FIN → ACK → FIN → ACK 关闭连接，主动方最后进 TIME_WAIT 等 2MSL。

2. 为什么挥手比握手多一次？
   答：TCP 全双工，双方各有一个方向要关闭。握手时服务端可把 SYN 和 ACK 合并；
   挥手时被动方收到 FIN 后可能还有数据要发，ACK 和 FIN 必须分开。

3. CLOSE_WAIT 堆积说明什么？
   答：被动方收到 FIN 后应用没调 close（或 close 被阻塞），是代码 bug，会导致连接泄漏。
   排查：ss -tanp 定位进程 → 查代码异常分支/连接池 → 堆 dump 数 socket 对象。

4. TIME_WAIT 的作用和影响？
   答：作用 1 确保最后 ACK 到达（对方重发 FIN 时有时间响应）；
   作用 2 让旧包在 2MSL 内消亡，防止串到新连接。影响：短连接频繁时堆积耗端口。

5. 拥塞控制的慢启动和拥塞避免？
   答：慢启动 cwnd 从 1 指数增长快速探测带宽；达 ssthresh 后转拥塞避免线性增长；
   丢包时快重传（3 个重复 ACK）+ 快恢复（cwnd 减半），超时则 cwnd 回到 1。

6. SYN 洪水怎么防护？
   答：tcp_syncookies=1（队列满时无状态验证，不占队列）；tcp_max_syn_backlog 调大；
   nftables 对单 IP 限 SYN 速率；应用层加快 accept 处理。

7. BBR 和 cubic 的区别？
   答：cubic 用丢包判断拥塞（丢包就降窗口），高丢包长链路上难跑满；
   BBR 用「带宽 × RTT」建模（不把丢包当拥塞信号），高吞吐低延迟，适合长肥管道。

8. 端口耗尽（Cannot assign requested address）怎么解决？
   答：先看 ip_local_port_range（默认 2.8 万个）和 TIME_WAIT 量；
   优先连接池/长连接，其次客户端开 tcp_tw_reuse，最后才是扩端口范围。

9. TCP 如何保证可靠传输？
   答：四层保障：seq/ack 确认（丢包检测与排序）、超时重传（RTO 动态计算 + 退避）、
   滑动窗口流量控制（防接收方被打爆）、拥塞控制（防网络被塞爆）+ 校验和（数据完整性）。

10. 什么是 Nagle 算法和延迟确认？为什么它们会互相拖累？
   答：Nagle 把多个小包合并发送（减少小包数）；延迟确认是接收方等 40ms 再回 ACK。
   两者叠加会互相等待（发送方等 ACK 才发，接收方等数据才回 ACK），产生 40ms 级延迟，
   交互场景用 TCP_NODELAY 关 Nagle 解决。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用 ss -tan 看连接状态，别只看「有没有连接」，要看「状态是否异常堆积」
2. CLOSE_WAIT 堆积 = 代码没正确 close 连接（对端关了本端没关），查代码不是查网络
3. TIME_WAIT 过多 = 短连接频繁，用连接池/长连接，或客户端 tcp_tw_reuse
4. TCP Keepalive 和 HTTP keep-alive 是两回事，别混为一谈
5. 高吞吐/长肥管道场景可试 bbr 拥塞算法，先测试机压测再上生产
6. 高并发服务提前调大 somaxconn + 应用 backlog（别等队列满了才改）
7. 排查连接问题先 ss -s 看全局、再 ss -tanp 定位进程、最后 tcpdump 抓包确认
8. 内核参数改动写 /etc/sysctl.d/ 独立文件 + 注释，别堆在 /etc/sysctl.conf
9. 服务端开启 tcp_tw_reuse 无效，别白费功夫；用 tcp_max_tw_buckets 兜底

### 踩坑记录

```text
坑 1：CLOSE_WAIT 堆积以为是网络问题
结论：连接堆积在 CLOSE_WAIT，以为是网络故障。
原因：CLOSE_WAIT 是本端服务收到 FIN 没 close，是代码 bug 不是网络问题。
解法：查服务代码，确保收到 FIN 后正确关闭 socket；异常分支也要关。

坑 2：TIME_WAIT 多就盲目调参数
结论：TIME_WAIT 多，直接改 tcp_tw_reuse/tw_recycle。
原因：TIME_WAIT 是正常的，盲目改参数可能引入新问题（tw_recycle 在 NAT 下会误杀连接）。
解法：先确认是否真的端口耗尽，优先用连接池/长连接解决；tw_recycle 内核已删除。

坑 3：TCP Keepalive 和 HTTP keep-alive 搞混
结论：以为配了 HTTP keep-alive 就能探测死连接。
原因：两个是不同的东西，HTTP keep-alive 是复用连接，不探测死活。
解法：探测死连接用 TCP Keepalive（内核参数）或应用层心跳。

坑 4：SYN_SENT 堆积，连不上目标
结论：连接卡在 SYN_SENT 状态，连不上服务器。
原因：SYN 发出去了但没收到 ACK，目标不可达/防火墙挡。
解法：排查目标 IP 可达性（ping）、防火墙、目标服务是否监听（nc -zv）。

坑 5：改拥塞算法没评估就上生产
结论：直接把算法改成 bbr，某些场景反而变差。
原因：不同算法适合不同场景，bbr 适合长肥管道，不是万能（小带宽/低延迟场景收益小）。
解法：先在测试环境 iperf3 压测对比，再决定是否切换。

坑 6：backlog 调了 somaxconn 但应用没生效
结论：sysctl somaxconn=4096 改了，nginx 队列还是 511。
原因：全连接队列 = min(somaxconn, 应用 listen 的 backlog 参数)，
nginx 默认 listen backlog 511，还要在 nginx.conf 里调 listen 80 backlog=4096。
解法：两层都调（sysctl + 应用配置）；python3 服务默认 backlog=5 更要显式指定。

坑 7：抓包看到服务端回 SYN+ACK，客户端还是重传 SYN
结论：只抓了服务端网卡，以为客户端收到了。
原因：回包可能在中间被丢弃（防火墙/路由），客户端根本没收到。
解法：两端都抓包对比，客户端没收到 [S.] 就查中间路径（mtr/防火墙）。

坑 8：长连接服务偶发卡顿，忘了 Nagle 和延迟确认
结论：交互式长连接偶发 40ms 级延迟。
原因：发送方 Nagle 攒小包 + 接收方延迟确认互相等待。
解法：交互场景 TCP_NODELAY 关 Nagle；本机时间戳/窗口缩放确认开启。

坑 9：端口范围改了没重启，新连接还是失败
结论：echo 写 ip_local_port_range 立即生效，但程序报错依旧。
原因：端口耗尽时已有 TIME_WAIT 还没释放（60 秒），改范围只解决未来，
且旧连接四元组仍占用；要等 TIME_WAIT 自然过期或复用开启。
解法：改范围 + tcp_tw_reuse 组合，等 60 秒观察，根治用连接池。

坑 10：生产环境直接 sysctl -w 改参数
结论：sysctl -w 改完重启失效，变更也没记录。
原因：-w 只改内存，不写文件；生产变更要有记录可回滚。
解法：写 /etc/sysctl.d/99-xxx.conf + sysctl -p 加载，变更走评审流程。
```
