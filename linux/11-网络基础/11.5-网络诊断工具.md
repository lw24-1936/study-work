## 概述

网络诊断工具回答「通不通、谁在连、连不上为什么、流量长啥样」：ping/traceroute 测连通、ss/netstat 看连接、nc 测端口、tcpdump 抓包分析、mtr 综合诊断、ethtool 看网卡。排查网络问题先「ping 测连通 → ss 看端口 → nc 测具体端口 → tcpdump 抓包深挖」。这些工具各有分工，配合起来能定位绝大多数网络问题。

```text
网络诊断工具分工：
1. 连通性 —— ping（测通）、traceroute（测路径）、mtr（每跳丢包）
2. 连接查看 —— ss / netstat（看连接和监听端口）
3. 端口测试 —— nc（测某端口通不通）
4. 抓包分析 —— tcpdump（看流量内容，配合 Wireshark）
5. DNS 查询 —— dig / host / nslookup（域名解析排错）
6. 网卡信息 —— ethtool / ip -s（速度/双工/驱动/统计）
7. 带宽测试 —— iperf3（端到端吞吐量）
```

排查链路是「由近及远、由粗到细」：先本机（ss 看监听）→ 网关（ping 网关）→ 目标端口（nc）→ 路径（traceroute/mtr）→ 报文（tcpdump）。每一步都缩小问题范围，最后定位到具体一跳或具体进程。

## 核心概念

六类工具分四组：连通性（ping/traceroute/tracepath/mtr）、连接查看（ss/netstat）、深挖（nc/tcpdump/ethtool/ip）、查询（dig/host）。下面逐一展开。

### ping 与 traceroute 连通性

ping 用 ICMP 测「通不通 + 延迟」，是最基础的连通性测试。traceroute 显示数据包到目标经过的「每一跳」，定位「断在哪一跳」。ping 不通不一定网络不通（可能禁 ICMP），traceroute 能看清路径。注意：traceroute 部分系统默认不装（本机 Ubuntu 就没装，要 tracepath 或单独装 traceroute）。

```text
# 实测（本机工具可用性）
$ for t in ping traceroute tracepath mtr dig host nc tcpdump nmap ethtool netstat ss arp iperf3; do
>   command -v $t >/dev/null 2>&1 && echo "$t: 有" || echo "$t: 无"; done
ping: 有    traceroute: 无    tracepath: 有    mtr: 有
dig: 有     host: 有          nc: 有          tcpdump: 有
nmap: 无    ethtool: 有       netstat: 有     ss: 有
arp: 有     iperf3: 无
# 本机 traceroute/nmap/iperf3 未装，用 tracepath/mtr 替代 traceroute
# Ubuntu 装 traceroute：apt install traceroute；装 nmap：apt install nmap
```

```shell
ping -c 4 8.8.8.8            # 测外网连通 + 延迟
ping -c 4 192.168.1.1        # 测网关连通
tracepath 8.8.8.8            # 替代 traceroute（iputils 自带）
mtr 8.8.8.8                  # 动态 traceroute
```

```text
# 实测（本机 ping 网关与公网）
$ ping -c 3 192.168.1.1
PING 192.168.1.1 (192.168.1.1) 56(84) bytes of data.
64 bytes from 192.168.1.1: icmp_seq=1 ttl=64 time=3.08 ms
64 bytes from 192.168.1.1: icmp_seq=2 ttl=64 time=2.94 ms
64 bytes from 192.168.1.1: icmp_seq=3 ttl=64 time=1.24 ms
--- 192.168.1.1 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2002ms
rtt min/avg/max/mdev = 1.235/2.418/3.083/0.838 ms

$ ping -c 3 223.5.5.5
64 bytes from 223.5.5.5: icmp_seq=1 ttl=52 time=13.1 ms
...
rtt min/avg/max/mdev = 13.056/13.197/13.347/0.118 ms
# 网关 ttl=64（一跳内，初始 64 减 0）；公网 ttl=52（初始 64 减 12，即经过了 12 跳）
# 每跳路由器 TTL 减 1，用 64 减去收到的 TTL 可粗略估算跳数
```

ping 输出字段解读：`icmp_seq` 是包序号（乱序/丢失时跳号）、`ttl` 是剩余生存时间（64 减收到的值 = 经过的路由跳数，64-52=12 跳）、`time` 是往返延迟、`mdev` 是延迟抖动（越大越不稳定）。`0% packet loss` 说明链路通，`time 2002ms` 是总耗时。

### ss 与 netstat 连接查看

ss 是现代的连接查看工具（替代 netstat），看「谁在监听、谁在连接」。关键用法：`ss -tlnp` 看监听端口（t=tcp、l=listen、n=数字、p=进程）、`ss -tan` 看所有连接及状态、`ss -s` 看汇总统计。netstat 是老命令（net-tools 包），功能等价。排查「服务起来了没」「端口被谁占了」「连接状态异常」都用 ss。

```text
# 实测（本机监听端口，ss -tlnp 截取）
$ ss -tlnp | head -20
State  Recv-Q Send-Q  Local Address:Port   Peer Address:Port  Process
LISTEN 0      4096    0.0.0.0:19530        0.0.0.0:*    users:(("docker-proxy",pid=4578,fd=8))
LISTEN 0      4096    0.0.0.0:3306         0.0.0.0:*    users:(("docker-proxy",pid=5773,fd=8))
LISTEN 0      511     0.0.0.0:3000         0.0.0.0:*    users:(("node",pid=1660949,fd=24))
LISTEN 0      4096    0.0.0.0:2379         0.0.0.0:*    users:(("docker-proxy",pid=3740,fd=8))
LISTEN 0      4096    0.0.0.0:22           0.0.0.0:*    users:(("sshd",pid=1577,fd=3))
LISTEN 0      511     0.0.0.0:80           0.0.0.0:*    users:(("nginx",pid=565634,fd=5))
LISTEN 0      4096    0.0.0.0:6379         0.0.0.0:*    users:(("docker-proxy",pid=4218,fd=8))

# Send-Q 列是监听队列长度（backlog），docker-proxy 默认 4096、nginx 511、python3 服务可能只有 5
```

```shell
ss -tlnp              # 看监听端口 + 进程
ss -tan               # 看所有 TCP 连接 + 状态
ss -s                 # 连接统计
ss -tlnp | grep :80   # 看 80 端口被谁监听
ss -tan state established   # 只看已建立连接
netstat -tlnp         # 等价（老命令）
```

```text
ss 与 netstat 输出对比（同一时刻本机）：
ss -tlnp 与 netstat -tlnp 列出的监听端口一致，但：
1. ss 直接读内核 netlink socket，快且全；netstat 读 /proc/net/tcp，大连接数下可能截断
2. netstat 进程列显示 "565634/nginx: maste"，ss 显示完整 users:(("nginx",pid=565634,fd=5))
3. 新装系统默认没有 netstat（net-tools 不再默认装），ss 属于 iproute2 必装
Red Hat 系差异：RHEL/CentOS 8+ 同样默认只有 ss（netstat 在 net-tools 包，yum install net-tools）
```

### nc 端口测试

nc（netcat）是「网络瑞士军刀」——测端口通不通（nc -zv）、收发数据、做简易服务器/客户端。测端口是最常用场景：`nc -zv 主机 端口` 测试某端口是否开放。比 telnet 更通用（telnet 很多系统不装）。还可用 nc 传文件、测 UDP、做端口转发。

```text
# 实测（本机 nc 端口探测）
$ nc -zv -w 3 192.168.1.1 22
nc: connect to 192.168.1.1 port 22 (tcp) failed: Connection refused
$ nc -zv -w 3 192.168.1.167 80
Connection to 192.168.1.167 80 port [tcp/http] succeeded!
$ nc -zvu -w 3 192.168.1.1 53
Connection to 192.168.1.1 53 port [udp/domain] succeeded!
$ nc -zv -w 3 192.168.1.1 81
nc: connect to 192.168.1.1 port 81 (tcp) failed: Connection refused
# 22 端口被拒（网关没开 SSH）、80 通（本机 nginx）、UDP 53 通（网关做 DNS 转发）
# Connection refused = 端口没监听；超时无响应 = 防火墙丢弃（DROP）
```

```shell
nc -zv 192.168.1.10 22        # 测 22 端口通不通（v=verbose, z=只测不传数据）
nc -zv 127.0.0.1 80           # 测本机 80 端口
nc -zv -u 127.0.0.1 53        # 测 UDP 端口（-u）
echo "test" | nc 127.0.0.1 80  # 发数据测试
nc -l 1234                    # 监听 1234 端口做简易服务器
```

`Connection refused` 与超时的区别：refused 说明对端回了 RST（端口没监听但有主机响应）；超时说明 SYN 石沉大海（防火墙 DROP 或主机不可达）。这个区别是判断「防火墙挡了」还是「服务没起」的关键。

### tcpdump 抓包

tcpdump 是命令行抓包工具——抓取经过网卡的网络包，分析流量内容。排查「请求发没发出去」「握手在哪失败」「协议异常」时用。关键：`tcpdump -i 网卡` 指定网卡、`port 80` 过滤端口、`host 1.2.3.4` 过滤主机、`-w 文件` 存包（用 Wireshark 分析）。抓包要 root 权限。

```shell
tcpdump -i wlp0s20f3 port 80          # 抓 80 端口流量
tcpdump -i any host 192.168.1.10      # 抓某主机的流量
tcpdump -i any tcp port 22 -w ssh.pcap # 抓包存文件
tcpdump -i any -n icmp                # 抓 ICMP（ping）
timeout 8 tcpdump -i any -c 5 -nn 'tcp port 443'   # 抓 5 个包自动退出
```

```text
tcpdump 常用过滤器（BPF 语法）：
1. port 80 / port 443 —— 指定端口（tcp port 80 更精确）
2. host 1.2.3.4 / net 192.168.1.0/24 —— 指定主机/网段
3. tcp / udp / icmp —— 指定协议
4. tcp flags：'tcp[tcpflags] & tcp-syn != 0' 只抓 SYN 包（看握手/重传）
5. -w 文件 —— 存包，用 Wireshark 图形化分析
6. -n / -nn —— 不解析主机名/服务名（更快更干净）
```

```text
# 实测（本机抓 SYN/SYN+ACK，过滤握手指令）
```

### mtr 与 ethtool

mtr 是 ping + traceroute 的结合体——动态显示每一跳的丢包率和延迟，持续观察网络质量（比单次 traceroute 更直观，能看出「哪一跳在丢包」）。ethtool 看网卡硬件信息（速度、双工、驱动、是否支持千兆）。排查「网速慢」「丢包」「网卡跑在半双工」用这俩。

```shell
mtr 8.8.8.8               # 动态 traceroute，看每跳丢包
mtr -r -c 10 8.8.8.8      # 报告模式（10 个包，-r 一次性输出）
mtr -r -c 5 -n 223.5.5.5  # -n 不反解域名（更快）
ethtool wlp0s20f3         # 看网卡信息
ethtool -S wlp0s20f3      # 看网卡统计（丢包/重试）
ethtool -i wlp0s20f3      # 看驱动和固件
```

### dig 与 host DNS 查询

dig 是最强大的 DNS 查询工具（显示解析全过程：状态、flags、TTL、权威服务器），host 是简洁版（只给结果）。排查「域名解析不了」「解析到旧 IP」用 dig。

```text
# 实测（本机 dig/host 查询 baidu.com）
$ dig +short baidu.com
111.63.65.247
111.63.65.103
124.237.177.164
110.242.74.102

$ dig baidu.com | grep -E 'status|ANSWER SECTION' -A2
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 42375
;; flags: qr rd ra; QUERY: 1, ANSWER: 4, AUTHORITY: 0, ADDITIONAL: 1
;; ANSWER SECTION:
baidu.com.		537	IN	A	124.237.177.164
baidu.com.		537	IN	A	111.63.65.103

$ host baidu.com
baidu.com has address 111.63.65.247
baidu.com has address 110.242.74.102
baidu.com has address 124.237.177.164
baidu.com has address 111.63.65.103
# status: NOERROR = 解析成功；ANSWER: 4 = 4 条 A 记录（多 IP 负载均衡）；TTL 537 秒
# flags: qr=响应 rd=递归请求 ra=递归可用；NOERROR 但 ANSWER: 0 则域名存在但无记录
```

```shell
dig baidu.com                 # 完整查询（含权威与耗时）
dig @8.8.8.8 baidu.com        # 指定 DNS 服务器查询（对比解析差异）
dig -x 110.242.70.57          # 反向解析（IP → 域名）
host baidu.com                # 简洁版
nslookup baidu.com            # 老工具，交互式
```

### 带宽工具（iperf3）

iperf3 是端到端带宽测试工具：服务端 `iperf3 -s`，客户端 `iperf3 -c 服务器IP`，测出真实的 TCP 吞吐量（区别于网卡标称速率）。定位「应用慢到底是带宽不够还是延迟高」用 iperf3 + ping/mtr 组合。本机未装，Ubuntu 用 `apt install iperf3`，RHEL 用 `yum install iperf3`。

```shell
# 服务端（目标机）
iperf3 -s -p 5201
# 客户端（测试机）
iperf3 -c 192.168.1.10 -t 10          # 10 秒下行测试（默认客户端→服务端）
iperf3 -c 192.168.1.10 -R             # 反向测试（服务端→客户端）
iperf3 -c 192.168.1.10 -P 4           # 4 并发流（多流打满带宽）
iperf3 -c 192.168.1.10 -u -b 100M     # UDP 模式测极限（测丢包率）
```

```text
# 示例（iperf3 未安装，此为预期输出形态）
$ iperf3 -c 192.168.1.10
Connecting to host 192.168.1.10, port 5201
[ ID] Interval           Transfer     Bitrate         Retr
[  5]   0.00-10.00  sec   1.09 GBytes   938 Mbits/sec  12  sender
[  5]   0.00-10.00  sec   1.09 GBytes   938 Mbits/sec        receiver
# Bitrate 938 Mbits/sec 接近千兆上限；Retr 12 次重传说明链路有轻微丢包
# 若测出远低于网卡速率（如千兆网卡只有 100M），查 ethtool 协商速率与 mtr 丢包
```

## 工作原理

这些工具各自从内核不同位置取数据：ping 发 ICMP echo 请求、按回包算 RTT；traceroute 靠递增 IP 头的 TTL（每跳路由器减一，减到 0 回 ICMP time exceeded）逐跳探测；ss 从内核的 netlink socket 直接读连接表（比 netstat 读 /proc/net 更快更全）；tcpdump 用 libpcap + BPF 过滤器在内核抓包拷贝到用户态；ethtool 通过 ioctl/ethtool 协议读网卡驱动寄存器。

```text
各工具数据来源：
ping         主动发 ICMP echo request，收 echo reply 算 RTT 与丢包
traceroute   递增 TTL，收集每跳 ICMP time exceeded，定位路径
ss           读内核 netlink socket 连接表（快、全）
netstat      读 /proc/net/tcp 等文件（老实现，可能截断）
tcpdump      内核 BPF 过滤器 + libpcap 抓包拷贝到用户态
ethtool      ioctl/ethtool 协议读网卡驱动寄存器（速度/双工/驱动）
ip neigh     读内核邻居表（ARP 缓存），ip -s 读网卡统计
dig          UDP 53 端口向 DNS 服务器发查询报文
```

traceroute 原理细节：第一个包 TTL=1，第一跳路由器 TTL 减到 0 后丢弃并回 ICMP time exceeded（Type 11），源地址就是第一跳 IP；第二个包 TTL=2 到第二跳；以此类推直到目标回 ICMP echo reply 或端口不可达。中间跳不响应 ICMP（回包被禁）就显示 `*`。tracepath 是同一思路的简化实现（不依赖 UDP/ICMP 特殊端口，还顺带做 MTU 发现——本机实测输出里能看到 `pmtu 1500` 降到 `1480` 的过程）。

tcpdump 原理细节：libpcap 把 BPF 过滤器编译进内核（或 eBPF），内核只把匹配的包拷贝到用户态，避免全量拷贝。抓包本身是「旁路监听」：包照常转发，不影响业务，但高流量下拷贝开销大会造成 CPU 高和抓包丢包（tcpdump 输出的 `packets dropped by kernel`）。

ss 原理细节：netlink 是内核与用户态通信的 socket 机制，ss 用 NETLINK_INET_DIAG 直接从内核连接表拿数据；netstat 遍历 /proc/net/tcp（内核导出的一份文本快照）。大连接数（上万）时 /proc 文本解析慢、且单行缓冲区可能截断，ss 更可靠。

```text
# 实测（本机 /proc/net/tcp 存在，netstat 的数据来源）
$ ls /proc/net/tcp* /proc/net/udp
/proc/net/tcp  /proc/net/tcp6  /proc/net/udp
$ head -2 /proc/net/tcp
  sl  local_address rem_address   st tx_queue rx_queue tr tm->when retrnsmt   uid  timeout inode
   0: 00000000:4C4E 00000000:0000 0A 00000000:00000000 00:00000000 00000000   115        0 360634 1
# 地址是小端序十六进制：00000000:4C4E = 0.0.0.0:19530（0x4C4E=19530），st=0A 是 LISTEN
```

## 应用场景实战

### 场景一：服务端口不通，逐层排查

线上报「访问 8080 端口失败」，从本机到远端逐层缩小范围：

```shell
# 1. 看服务有没有监听端口（本机）
ss -tlnp | grep 8080
# 2. 本机回环测（排除网卡/防火墙因素）
nc -zv 127.0.0.1 8080
# 3. 本机用局域网 IP 测（排除防火墙本机规则）
nc -zv 192.168.1.167 8080
# 4. 远程机测（目标机 IP）
nc -zv 192.168.1.167 8080
# 5. 抓包看请求到没到（目标机上执行）
timeout 10 tcpdump -i any -nn 'tcp port 8080' -c 20
```

```text
判定逻辑：
1 无输出        服务没起来 / 监听在别的端口（如 127.0.0.1:8080 只监听回环）
2 失败          服务确实没监听，直接查服务日志
3 失败、2 成功   防火墙本机规则挡了（ufw/nftables 没放行该端口）
4 失败、3 成功   中间设备（云安全组/公司防火墙）挡了
5 有 SYN 无 SYN+ACK   目标防火墙 DROP；有 RST   端口没监听
```

### 场景二：网络慢、丢包，定位问题段

应用访问慢，先分清是「链路问题」还是「网卡问题」还是「服务端问题」：

```shell
# 1. mtr 看每一跳的丢包率（定位丢包段）
mtr -r -c 20 -n <目标IP>
# 2. 看网卡是否跑在半双工/低速、有没有大量重试
ethtool <网卡> | grep -E 'Speed|Duplex'
ethtool -S <网卡> | grep -E 'retry|drop'
ip -s link show <网卡>
# 3. 看连接状态是否异常堆积
ss -s
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c
# 4. 端到端吞吐量实测（排除主观感受）
iperf3 -c <对端> -t 10
```

```text
# 实测（本机 WiFi 网卡统计，注意 tx_retries）
$ ethtool -S wlp0s20f3 | head -10

     rx_packets: 19302386
     rx_bytes: 11956406406
     rx_dropped: 1886
     tx_packets: 11426405
     tx_bytes: 8830574193

# tx_retries 80 万次：WiFi 空口重传（信号弱/干扰的正常现象），有线网卡该值应为 0
# rx_dropped 1886：接收丢包，可能因缓冲区满，量大时配合 dmesg 看网卡报错
```

### 场景三：抓包确认 SYN 重传（连接建立慢）

用户反馈「连某服务要等很久才通」，用 tcpdump + ss -ti 确认是否 SYN 重传：

```shell
# 1. 目标机上抓 SYN 流量（同时发起连接）
timeout 30 tcpdump -i any -nn 'tcp port 443' -c 50 -w /tmp/syn.pcap
# 2. 客户端上统计卡在 SYN_SENT 的连接
ss -tan state syn-sent | wc -l
ss -ti | grep -A1 SYN-SENT | head -6
```

```text
# 实测（本机 ss -ti 看到的 SYN-SENT 连接内部状态）
$ ss -ti | head -8
SYN-SENT  0  1  192.168.1.167:40300  172.253.117.139:https
	 cubic rto:64000 backoff:6 mss:524 pmtu:1500 rcvmss:88 advmss:1460 cwnd:1 ssthresh:7
	 segs_out:11 lastsnd:1984521161 retrans:1/10 lost:1
# rto:64000 = 重传超时已退避到 64 秒；backoff:6 = 已退避 6 次
# mss:524 = 因重传把 MSS 降到最小；retrans:1/10 = 10 个包里重传 1 个
# 这是典型「对端不可达/被防火墙丢 SYN」的表现，与 tcpdump 看到的重复 [S] 互相印证
```

## 性能与调优

```text
1. 抓包量大时用 -w 存文件离线分析，别 -i any 全量刷终端（刷屏 + 高 CPU）
2. tcpdump 加过滤（port/host/protocol/tcp flags）缩小抓取范围，降低 CPU 和内核丢包
3. 高流量抓包用 -c 限量 + timeout 包裹，避免 tcpdump 一直跑（本机实测 timeout 8 tcpdump -c 5 模式）
4. ss 比 netstat 快（直接读 netlink），高频监控脚本用 ss；大连接数（10 万+）差距更明显
5. mtr 持续观察能看出「抖动/间歇性丢包」，比单次 traceroute 更能定位性能问题
6. ethtool 查网卡是否协商到低速/半双工，这是网速慢的常见根因；WiFi 卡看 tx_retries 判断空口质量
7. iperf3 测吞吐用多流（-P 4）和反向（-R），单流测不出多队列网卡的真实能力
8. 延迟抖动看 ping 的 mdev：正常内网 <1ms，mdev 大说明链路拥塞或无线干扰
```

```text
性能指标速查（正常参考值）：
内网 ping 延迟      < 2ms，丢包 0%
公网 ping 延迟      10-50ms（国内骨干），丢包 < 1%
TCP 重传率          正常 < 0.1%（ss -ti 的 retrans/segs_out）
网卡 rx/tx dropped  长时间增长 = 中断/队列问题
WiFi tx_retries     信号差时正常几千次/小时，暴涨说明干扰严重
```

## 安全与权限

```text
1. tcpdump 抓包要 root（或 CAP_NET_RAW），抓到的明文内容含敏感数据（密码/token/业务数据），别外发
2. 抓包文件（.pcap）可能含密码/token/内网拓扑，脱敏后再共享；报障时只给过滤后的片段
3. nc 可做端口转发/反弹 shell，是攻击常用工具——服务器上非必要不装、装了限制使用
4. ping/ICMP 常被防火墙禁，别因为 ping 不通就武断判「服务挂了」
5. 对外诊断暴露内网信息（traceroute 的每跳 IP、内网网段），报障时注意脱敏
6. 生产环境抓包先评估流量（tcpdump 高流量下会丢包且占 CPU），用 -c 限量 + 过滤
7. nmap 扫描在未授权环境下是违规行为，只对自有/已授权资产使用
8. ss -tanp 输出含进程名和连接对方 IP，脱敏后再贴日志/工单
```

```text
权限相关：
- tcpdump 需要 root 或 cap_net_raw：setcap cap_net_raw+ep /usr/sbin/tcpdump
- 普通用户看 ss -tan 可以，看 -p（进程）需要 root
- ping 需要 CAP_NET_RAW（Ubuntu 上普通用户可用，是 setcap 过）
- ethtool -S / ip -s link 普通用户可看，ethtool 改参数需要 root
```

## 故障排查

### 案例一：连不上服务——从端口到抓包逐层定位

```shell
# 1. 本机监听确认
ss -tlnp | grep <端口>          # 没输出 = 服务没起来或没监听
# 2. 本机回环测
nc -zv 127.0.0.1 <端口>         # 失败 = 服务没监听
# 3. 跨机测
nc -zv <目标IP> <端口>          # 失败 = 防火墙/路由挡了
# 4. 抓包确认请求到没到（目标机上）
timeout 10 tcpdump -i any host <目标IP> and port <端口> -nn -c 20
# 5. 看 SYN_SENT 堆积与重传细节（客户端上）
ss -tan state syn-sent
ss -ti | grep -A1 SYN-SENT
```

```text
# 实测（本机存在大量 SYN-SENT：chrome 连 172.253.117.139/74.125.x 等 Google IP 全部卡住）
$ ss -tanp | grep SYN-SENT | head -4
SYN-SENT  0  1  192.168.1.167:36492  74.125.195.102:443  users:(("chrome",pid=4148777,fd=46))
SYN-SENT  0  1  192.168.1.167:40300  172.253.117.139:443  users:(("chrome",pid=66169,fd=86))
# 这些 IP 在本网络不可达（被墙），SYN 无人应答，连接长期挂在 SYN-SENT 并周期性重传
# 判定：ping 目标不通 + ss 卡 SYN-SENT + tcpdump 只见 [S] 不见 [S.] = 路由/防火墙丢弃
```

### 案例二：网速慢 / 丢包定位

```shell
# 1. 网卡协商速率/双工
ethtool eth0 | grep -E 'Speed|Duplex'
# 2. 每跳丢包
mtr -r -c 20 8.8.8.8
# 3. 连接状态堆积
ss -s
# 4. 网卡统计（重试/丢包）
ethtool -S eth0 | grep -iE 'drop|retry'
ip -s link show eth0
```

```text
判定要点：
- ethtool 显示 Speed: 100Mb/s 而网卡是千兆 = 网线/协商问题，换线或强制协商
- mtr 只有最后一跳丢包、中间全好 = 目标机自身问题（防火墙限速、CPU 满）
- mtr 中间某跳持续丢包但后面恢复 = 中间设备限速/不响应，一般不是故障
- tx_retries 暴涨（WiFi）= 无线干扰/离 AP 远；rx_dropped 增长 = 收包缓冲区不足
```

### 案例三：DNS 解析失败

```shell
# 1. 看配置的 DNS 服务器
cat /etc/resolv.conf
resolvectl status | grep -A2 'DNS Servers'
# 2. 直接问指定的 DNS 服务器
dig @8.8.8.8 baidu.com
dig @127.0.0.53 baidu.com
# 3. 对比本地 hosts 是否有劫持
grep baidu /etc/hosts
# 4. 测 DNS 服务器可达性（UDP 53）
nc -zvu 8.8.8.8 53
```

```text
判定要点：
- 本机通、换 DNS 服务器通 = 原 DNS 服务器问题，改 resolv.conf 或上游
- 所有 DNS 都不通 = UDP 53 被防火墙挡 / DNS 服务器宕机
- dig 返回 SERVFAIL = 上游递归失败；NXDOMAIN = 域名确实不存在
- hosts 里有对应行 = 本地劫持优先，删掉后再测
```

## 常见问题

```text
Q1: ping 不通但服务能访问？
A: 目标禁了 ICMP（防火墙挡 ping），但 TCP 服务正常。用 nc -zv 测端口、curl 测服务。

Q2: traceroute 中间全是 * 是不是断了？
A: 不是。中间路由器不响应 ICMP（星号不代表断），只要最后一跳能到就行。
   本机实测 223.5.5.5 第 6/7 跳 100% 丢包，但第 8 跳（目标）0% 丢包，链路正常。

Q3: ss 和 netstat 数字对不上？
A: 以 ss 为准。ss 直接读内核 netlink，netstat 读 /proc 且可能截断（大连接数下尤其明显）。

Q4: tcpdump 报 permission denied？
A: 抓包要 root 权限，加 sudo 或给用户 CAP_NET_RAW 能力（setcap cap_net_raw+ep）。

Q5: 为什么 netstat 报 command not found？
A: netstat 在 net-tools 包，新系统默认不装，用 ss 替代或 apt install net-tools
   （RHEL 系：yum install net-tools）。

Q6: tcpdump 抓到 0 个包，是不是网卡不对？
A: 先确认过滤条件与网卡：-i any 抓所有网卡；host/port 写错会过滤掉所有包。
   本机实测 -i any 'icmp or tcp port 80' 抓 0 包 = 当时确实没有匹配流量，不是抓包失败。

Q7: mtr 中间跳丢包 50% 以上，链路是不是断了？
A: 不一定。运营商中间设备常对 ICMP 限速（本机实测第 3 跳 60% 丢包但延迟正常）。
   看最后一跳：丢包 0% + 延迟稳定 = 实际可用；最后一跳也丢 = 才是真问题。

Q8: nc -zv 报 Connection refused 和超时有什么区别？
A: refused = 对端回了 RST（主机通、端口没监听）；超时 = SYN 无响应（防火墙 DROP 或主机不可达）。
```

## 面试题

```text
1. ss 和 netstat 的区别？
   答：ss 直接读内核 netlink socket（NETLINK_INET_DIAG），更快更全；netstat 读 /proc/net/tcp
   文本文件（老实现，大连接数可能截断）。现代系统用 ss，netstat 需要单独装 net-tools。

2. traceroute 的原理？
   答：递增 IP 头的 TTL（1,2,3...），每跳路由器 TTL 减一，减到 0 时丢弃并回 ICMP time exceeded
   （Type 11），源地址即该跳 IP。收到目标的 echo reply 或端口不可达即结束。

3. tcpdump 的过滤是在哪做的？
   答：内核态用 BPF 过滤器（libpcap 编译下发），只把匹配的包拷贝到用户态，避免全量拷贝的开销。
   现代内核用 eBPF 实现同样机制。

4. ping 为什么不能完全代表服务可用？
   答：ping 只测 ICMP 通不通，服务端口通不通、应用层正不正常要 nc/curl 测。
   且很多防火墙禁 ICMP，ping 不通不代表服务挂。

5. 怎么判断网络慢是「链路丢包」还是「网卡协商问题」？
   答：mtr 看每跳丢包率定位链路（最后一跳丢包才是真问题）；ethtool 看 Speed/Duplex 确认网卡
   是否跑在低速/半双工；ethtool -S / ip -s 看网卡统计的重传与丢包。

6. nc 测端口时 Connection refused 和超时分别说明什么？
   答：refused = 对端回了 RST，主机通但端口没监听（服务没起）；超时 = SYN 无响应，
   防火墙 DROP 或主机/路由不可达。据此区分「服务问题」还是「网络问题」。

7. 如何判断一个 SYN 包被重传了？
   答：tcpdump 里看到同一五元组、相同 seq 的 [S] 出现多次（间隔按 RTO 退避增长），
   或用 ss -ti 看 SYN-SENT 连接的 rto/backoff/retrans 计数。

8. mtr 中间跳丢包高但目标正常，怎么解释？
   答：中间设备对 ICMP 限速/不响应（ICMP 优先级低），不代表链路故障；
   以最后一跳的丢包率和延迟为准，配合 iperf3 实测吞吐确认。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 看连接/端口统一用 ss（现代），netstat 是老命令别依赖（新系统默认没有）
2. 测端口用 nc -zv，比 telnet 通用（telnet 很多系统不装）且能区分 refused/超时
3. 抓包用 tcpdump -i any + 过滤条件 + -c 限量（或 timeout 包裹），别抓全量刷屏
4. 排查丢包用 mtr 看每一跳，比单次 traceroute 直观；重点看最后一跳
5. 网速异常查 ethtool 协商速率 + ethtool -S 统计（重试/丢包），别只测 ping
6. 排查顺序固定：本机 ss → 网关 ping → 目标端口 nc → 路径 mtr → 报文 tcpdump
7. 存包用 -w 写 pcap，配合 Wireshark 图形化看握手/重传/乱序，比终端肉眼强
8. DNS 问题先 dig 指定服务器（@8.8.8.8）对比，别直接改 resolv.conf

### 踩坑记录

```text
坑 1：ss 和 netstat 混用，结果对不上
结论：ss 和 netstat 显示的数量不一致。
原因：ss 读内核 netlink 直接、netstat 读 /proc 且可能截断。
解法：统一用 ss，结果以 ss 为准。

坑 2：tcpdump 抓包量大，把自己卡死
结论：tcpdump -i any 没过滤，抓包把终端刷爆、CPU 打满。
原因：全量抓包量大，输出/存文件爆炸，内核拷贝丢包。
解法：加过滤（port/host/protocol/tcp flags），-c 限量，timeout 包裹，或 -w 存文件。

坑 3：ping 不通就判断服务挂了
结论：ping 目标不通，但服务其实正常（能 curl 通）。
原因：目标禁 ICMP，ping 被防火墙挡了。
解法：用 nc -zv 测端口、curl 测服务，别只看 ping。

坑 4：netstat 命令不存在
结论：敲 netstat 报 command not found。
原因：netstat 在 net-tools 包，新系统不默认装（Ubuntu 22.04+/RHEL 8+ 都这样）。
解法：用 ss 替代，或 apt/yum install net-tools。

坑 5：traceroute 显示 * * * 以为断了
结论：traceroute 中间几跳全是 *，以为网络断。
原因：中间路由器不响应 ICMP（星号不代表断，目标能到就行）。
解法：看最后一跳能不能到，中间 * 是正常的；用 mtr 持续观察更准。

坑 6：traceroute 命令不存在，以为没法看路径
结论：敲 traceroute 报 command not found，放弃排查。
原因：traceroute 是独立包（traceroute），Ubuntu 默认不装；tracepath 在 iputils 里默认有。
解法：先用 tracepath 或 mtr 顶替，需要时 apt/yum install traceroute。

坑 7：抓包文件直接外发，泄露敏感信息
结论：把 tcpdump -w 的 pcap 原样发给第三方，里面全是明文业务数据。
原因：抓包内容含密码/token/内网拓扑。
解法：只导出过滤后的片段（tcpdump -r 文件 再过滤），或脱敏后外发。

坑 8：WiFi 网卡 ethtool 看不到 Speed，以为网卡坏了
结论：ethtool wlp0s20f3 只有 Link detected，没有 Speed/Duplex。
原因：WiFi 网卡不走 ethtool 的速率协商接口，信息天然少。
解法：速率用 iw dev <网卡> link 看；ethtool 主要用 -i（驱动）和 -S（统计）。

坑 9：mtr 中间跳丢包 60% 就报故障
结论：mtr 显示第 3 跳丢包 60%，直接判定链路故障。
原因：运营商中间设备对 ICMP 限速（本机实测 124.167.4.229 丢 60% 但延迟正常）。
解法：看最后一跳丢包率与延迟，配合 iperf3 实测吞吐再下结论。

坑 10：nc 测 UDP 端口假阳性
结论：nc -zvu 对 UDP 端口返回 succeeded，以为服务正常。
原因：UDP 无连接，对端不回应也算「成功」（-z 对 UDP 只能确认 ICMP port unreachable 的失败）。
解法：UDP 端口要实际收发数据验证（如 dig @服务器 查询），nc -z 只作参考。
```
