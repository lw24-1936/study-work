## 概述

排查故障不是「凭感觉乱试」，而是「有方法地定位根因」。核心四步：故障分类（是什么类型的问题）、分层排查（按层逐层排除）、信息收集（收集证据，别急着改）、根因分析（找到根本原因，不是表象）。掌握方法论，排查从「碰运气」变成「有章法」，能更快、更准地定位问题。

```text
排查方法论四步：
1. 故障分类 —— 资源类/网络类/配置类/代码类，先判断类型
2. 分层排查 —— 从底层到上层（硬件→系统→应用→代码）逐层排除
3. 信息收集 —— 收集日志/指标/现场，别急着动手改
4. 根因分析 —— 找根本原因，不是治标（5 why 法）
```

## 核心概念

先给故障分类，判断「是什么类型的问题」：资源类（CPU/内存/磁盘不够）、网络类（连不上/丢包/延迟）、配置类（改错了配置）、代码类（程序 bug）。分类能缩小排查方向——磁盘满和网络不通的排查路径完全不同。快速分类靠「症状 + 关键命令」：磁盘满看 df、CPU 高看 top、网络不通看 ping/ss。

```text
故障分类：
1. 资源类 —— CPU 飙高/内存不够/磁盘满/句柄耗尽
2. 网络类 —— 连不上/丢包/延迟/端口不通
3. 配置类 —— 改错配置（fstab/网络/服务）
4. 代码类 —— 程序 bug（崩溃/泄漏/死循环）
```

## 工作原理

排查方法论的「工作原理」是三层递进：**分层排查**（从底层到上层逐层排除，像剥洋葱）、**信息收集**（先观察后动手，保留现场）、**根因分析**（追到根本原因，不是表象）。

分层排查的典型层次：硬件 → 内核/驱动 → 系统服务 → 网络 → 应用 → 代码。例：服务访问不了，先查进程在不在（系统层）→ 端口监听没（网络层）→ 日志报什么（应用层）。分层的好处：不漏层、不跳层，每层确认正常再往下。

```text
分层排查（自下而上）：
硬件 → 内核/驱动 → 系统服务 → 网络 → 应用 → 代码
# 例：服务访问不了
1. 进程在不在？        ps aux | grep xxx
2. 端口监听没？        ss -tlnp | grep 端口
3. 网络通不通？        ping/nc
4. 日志报什么？        journalctl -u xxx
```

```text
信息收集原则：
1. 先观察后动手 —— 别一上来就重启/重装
2. 保留现场 —— 改之前记录原状态（配置备份）
3. 完整信息 —— 错误日志 + 系统状态 + 时间线
```

```text
根因分析方法：
1. 5 Why —— 连续追问「为什么」，追到根本原因
2. 对比法 —— 正常状态 vs 异常状态，找差异
3. 时间线 —— 还原「出事前后」发生了什么
```

## 常用命令与配置

排查前先「收集信息」——日志、指标、现场状态，别急着改。常见错误：一上来就重启服务（现场没了，更难查）。信息收集的命令按层组织：

```shell
# 快速收集现场信息
dmesg | tail -20           # 内核错误
journalctl -xe             # 最近的系统日志
top -b -n 1 | head         # CPU/内存快照
df -h && free -h           # 磁盘/内存
ss -tlnp                   # 端口
```

```text
按层收集命令：
硬件/内核   dmesg、journalctl -k
系统服务    journalctl -u <服务>、systemctl status
资源        top、free、df、iostat、vmstat
网络        ss、ping、ip、tcpdump
应用        tail -f 应用日志
```

## 配置文件解析

排查配置类故障，要熟悉「关键配置文件在哪、改了什么」——配置类故障的核心是「对比改之前和改之后」：

```text
常见故障配置文件位置：
/etc/fstab           —— 挂载（改错可能导致启动失败）
/etc/ssh/sshd_config —— SSH（改错可能把自己锁外面）
/etc/sysctl.conf     —— 内核参数（网络/内存调优）
/etc/rsyslog.conf    —— 日志（改错日志不落盘）
/etc/systemd/ 单元   —— 服务（改错服务起不来）
/etc/sudoers         —— sudo 权限（改错 sudo 不能用）
```

```shell
# 排查配置类故障的标准动作
diff <(备份的原配置) <(当前配置)     # 对比改动
systemd-analyze verify <unit>        # 校验 systemd 单元语法
sshd -t                              # 校验 sshd_config 语法
```

## 应用场景实战

### 场景一：服务访问不了，分层排查

```shell
# 1. 应用层：进程在不在
ps aux | grep <服务>
# 2. 网络层：端口监听没
ss -tlnp | grep <端口>
# 3. 系统层：日志报什么
journalctl -u <服务> -n 50
# 4. 资源层：资源够不够
df -h && free -h
```

### 场景二：用 5 Why 追根因

```text
问题：凌晨备份任务失败
Why1: 为什么失败？磁盘空间不足
Why2: 为什么磁盘不足？备份文件没清理
Why3: 为什么没清理？清理脚本没跑
Why4: 为什么没跑？cron 配置丢了
Why5: 为什么配置丢了？上次升级覆盖了 crontab
根因：升级流程没保护 cron 配置 → 修复：备份 crontab + 升级后校验
```

## 性能与调优

排查效率本身就是「性能」——方法论能显著缩短 MTTR（平均修复时间）：

```text
1. 建立「症状 → 命令」速查表 —— 见症状直接跑对应命令，别现场翻手册
2. 沉淀排查文档 —— 解决一次记录一次，同类问题下次秒定位
3. 监控先行 —— 提前配好监控和告警，故障发生时已有现场数据，不用临时抓
4. 用脚本固化高频检查 —— 把「df/free/ss/dmesg」打包成一个 healthcheck 脚本，一键收集现场
```

## 安全与权限

```text
1. 排查用只读命令优先 —— df/ps/ss/dmesg 只读无害，别急着改配置/重启
2. 改配置前备份 —— cp /etc/xxx /etc/xxx.bak，改错能回滚
3. 别在排查时泄露信息 —— 日志/配置贴出去打码（密码、密钥、内网 IP）
4. 审计命令记录 —— 排查过程中的高危操作（kill/reboot/改配置）走审计，方便复盘
```

## 故障排查

方法论本身就是「怎么排查故障」，这里给一个可直接套用的决策流：

```text
故障来了，按这个顺序走：
1. 定性 —— 什么症状？（服务挂了/变慢/报错/连不上）
2. 分类 —— 资源/网络/配置/代码，哪一类？
3. 分层 —— 自下而上逐层排除（硬件→系统→网络→应用→代码）
4. 收集 —— 日志 + 指标 + 时间线，保留现场
5. 根因 —— 5 Why 追到根本，别停在表象
6. 验证 —— 修复后确认不再复现，记录到文档
```

## 常见问题

```text
Q1: 排查和调试有什么区别？
A: 排查（troubleshooting）是定位「系统哪里出了问题」的通用方法，调试（debugging）是定位「程序代码哪里错了」的具体技术。排查是框架，调试是其中「代码类」故障的手段。

Q2: 为什么强调「别一上来就重启」？
A: 重启会丢失崩溃现场（日志、进程状态、内存、core 文件），起来后可能又挂，但现场没了更难查。先收集信息再重启。

Q3: 5 Why 要问几次？
A: 没有固定次数，问到「根因」为止——通常是「流程/配置/代码」这类可执行动作的原因，而不是「运气不好」这种不可行动的表象。

Q4: 分层排查和故障分类什么关系？
A: 分类先缩小「方向」（资源还是网络），分层再沿着该方向逐层排除。分类是粗定位，分层是精定位。
```

## 面试题

```text
1. 你遇到一个线上故障，第一件事做什么？
   答：先定性 + 收集现场（日志/指标/状态），别急着重启。分类判断类型，再分层定位，最后根因分析。

2. 什么是根因分析（RCA）？和治标有什么区别？
   答：RCA 找「根本原因」（磁盘满是因为日志没轮转），治标只处理表象（删文件）。治标问题会复发，RCA 才能彻底解决。

3. 分层排查为什么自下而上？
   答：底层故障（硬件/内核/网络）会影响上层，但上层故障不影响底层。自下而上能先排除「地基问题」，避免在上层白查。

4. 5 Why 的边界在哪（什么时候该停）？
   答：追到「可执行动作」为止——能落到「改配置/加监控/补流程」这类具体动作，就是根因；再往下就是超出职责范围的空话。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先分类再排查，别上来乱试命令
2. 分层排查自下而上，不漏层不跳层
3. 先收集信息再动手，别一上来就重启（现场没了）
4. 找根因别治标（5 Why 追到根本）
5. 排查过程记录（改了啥、看到啥），方便回溯和复盘

### 踩坑记录

```text
坑 1：一上来就重启服务，现场没了
结论：服务挂了直接重启，起来后又挂，但现场没了难查。
原因：重启丢失了崩溃现场（日志/状态/内存）。
解法：先收集信息（日志/状态）再重启，保留现场。

坑 2：治标不治本，问题反复出现
结论：磁盘满就删文件，过几天又满。
原因：只处理表象（删文件），没找根因（为什么一直满）。
解法：5 Why 追根因（可能是日志没轮转/某进程狂写）。

坑 3：跳层排查，漏掉中间层
结论：服务连不上，只查了应用日志，其实是网络层防火墙挡了。
原因：没按层排查，跳过了网络层。
解法：分层逐层排查，每层确认正常再往下。

坑 4：信息没收集全就下结论
结论：只看一条报错就判断原因，实际是另一个问题。
原因：信息不完整，误判根因。
解法：收集完整信息（日志+指标+时间线）再分析。

坑 5：不记录排查过程，下次同样问题又从头查
结论：同样的问题过几天又出现，忘了上次怎么查的。
原因：没记录排查过程。
解法：记录排查步骤和结果，沉淀成文档（就是本知识库的意义）。
```
