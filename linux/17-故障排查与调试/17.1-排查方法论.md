## 概述

排查故障不是「凭感觉乱试」，而是「有方法地定位根因」。完整方法论把一次排障拆成七步：**定性 → 分类 → 分层 → 收集 → 假设 → 根因 → 修复验证**，每一步都有对应的工具和产出。核心思想是「**证据驱动**」：先观察、先收集，再动手，最后用验证闭环确认修复有效。

```text
排查七步法：
1. 定性     —— 症状是什么？（挂了/变慢/报错/连不上），确定故障边界
2. 分类     —— 资源类/网络类/配置类/代码类，先判断类型缩小方向
3. 分层     —— 硬件→内核→系统→网络→应用→代码，逐层排除
4. 收集     —— 收集日志/指标/现场快照，保留证据
5. 假设     —— 基于证据提出根因假设（5 Why / 二分法）
6. 根因     —— 验证假设，确认根本原因而非表象
7. 修复验证 —— 修复 + 回滚预案 + 验证不复现 + 复盘沉淀
```

两个核心原则贯穿始终：

1. **先止血后根治**：服务不可用先恢复（重启/回滚/降级），恢复后带着现场再深挖根因，别在业务受损时慢慢查。
2. **可观测性先行**：平时就配好监控、日志、追踪，故障发生时才有「事前数据」可用；临时抓数据往往只能抓到「事中」和「事后」。

## 核心概念

### 1. 故障分类树

先给故障分类，判断「是什么类型的问题」，分类能缩小排查方向——磁盘满和网络不通的排查路径完全不同。快速分类靠「症状 + 关键命令」：磁盘满看 `df`、CPU 高看 `top`、网络不通看 `ping/ss`。

```text
故障分类树：
1. 资源类 —— CPU 飙高/内存不够/磁盘满/句柄耗尽/inode 耗尽
2. 网络类 —— 连不上/丢包/延迟/端口不通/DNS 解析失败
3. 配置类 —— 改错配置（fstab/网络/服务）/配置没生效/路径不对
4. 代码类 —— 程序 bug（崩溃/泄漏/死循环/竞态）
5. 外部依赖 —— 上游接口变慢/第三方服务挂/证书过期
6. 人为操作 —— 误删/误改/误发布（先问「最近改了什么」）
```

### 2. 三大思维方法

- **五问法（5 Why）**：连续追问「为什么」，从表象追到根本原因。每层回答都要基于事实，不能编。问到「可执行动作」为止（能落到改配置/加监控/补流程）。
- **二分法**：把问题域一分为二，判断故障在哪一半，反复二分快速收敛。按网络分层二分（客户端/服务端）、按架构分层二分（接入层/应用层/数据层）、按时间分段二分（故障从哪个时间点开始）。
- **排除法**：逐项排除不可能的环节。配合分层排查，每确认一层正常就排除一层，剩余范围越小越接近根因。

### 3. 关键指标

```text
MTTR  —— Mean Time To Repair，平均修复时间（衡量排障速度）
MTBF  —— Mean Time Between Failures，平均故障间隔（衡量稳定性）
RCA   —— Root Cause Analysis，根因分析（找根本原因的过程）
SLO   —— Service Level Objective，服务目标（排障优先级依据）
```

方法论的价值就是用标准化流程降低 MTTR：同样的故障，有章法的人比乱试的人快一个数量级。

### 4. RCA 与治标的区别

**治标**只处理表象（磁盘满就删文件），问题会复发；**RCA** 追到根本原因（日志不轮转导致磁盘满），修复后不再复发。RCA 的输出是「原因链 + 修复动作 + 防复发措施」，而不是「一个操作」。

### 5. SRE 排障思维

- **假设驱动**：每步都带着「可证伪的假设」去查（「我猜是网络层，证据是 ping 不通」），验证假设而不是漫无目的地翻日志。
- **可观测性先行**：日志（Logging）、指标（Metrics）、追踪（Tracing）三支柱提前配好。故障时先看仪表盘，再决定要不要深入。
- **变更即风险**：绝大多数故障由变更引发（发布/配置/流量调整），排障第一步永远是查变更。

## 工作原理

排查方法论的「工作原理」是三层递进：**分层排查**（从底层到上层逐层排除，像剥洋葱）、**信息收集**（先观察后动手，保留现场）、**根因分析**（追到根本原因，不是表象）。

### 分层排查模型

典型层次：硬件 → 内核/驱动 → 系统服务 → 网络 → 应用 → 代码。例：服务访问不了，先查进程在不在（系统层）→ 端口监听没（网络层）→ 日志报什么（应用层）。分层的好处：不漏层、不跳层，每层确认正常再往下。

```text
分层排查（自下而上）：
硬件 → 内核/驱动 → 系统服务 → 网络 → 应用 → 代码
# 例：服务访问不了
1. 进程在不在？        ps aux | grep xxx
2. 端口监听没？        ss -tlnp | grep 端口
3. 网络通不通？        ping/nc
4. 日志报什么？        journalctl -u xxx
```

为什么自下而上？底层故障（硬件/内核/网络）会影响上层，但上层故障不影响底层。先排除「地基问题」，避免在上层白查。

### 时间线梳理

故障排查的第一步不是跑命令，而是**还原时间线**：故障发生前发生了什么、故障时刻系统在做什么、事后有什么异常。

```text
时间线三问：
1. 故障前 —— 最近 24h 内有什么变更？（发布/配置/流量/依赖）
2. 故障时 —— 报错日志/监控曲线的拐点在哪一刻？
3. 故障后 —— 有没有自动恢复/重启/自愈动作干扰判断？

# 快速抓取「最近发生了什么」
journalctl --since "10 min ago" --no-pager | wc -l   # 最近日志量
journalctl -p err -b --no-pager | tail               # 本次启动的 error 级
dmesg | tail                                         # 内核尾部消息
```

### 信息收集原则

```text
信息收集原则：
1. 先观察后动手 —— 别一上来就重启/重装（现场没了）
2. 保留现场 —— 改之前记录原状态（配置备份、进程列表、网络连接快照）
3. 完整信息 —— 错误日志 + 系统状态 + 时间线，三者缺一不可
4. 日志优先级 —— 先看 error 级别，再按时间窗口缩小范围
```

日志阅读技巧：先看 error 级别（`journalctl -p err -b`），圈定时间窗口（故障前后 10 分钟），再按服务过滤。不要从头到尾读完整日志——那是大海捞针。

### 应急 vs 根治

```text
先止血后根治：
1. 止血 —— 恢复服务优先：重启/回滚/降级/切流量（业务不中断是第一位）
2. 保留 —— 止血前先留证据（快照命令输出、日志段、core 文件）
3. 根治 —— 服务恢复后，用现场证据做 RCA，出修复方案
4. 验证 —— 修复上线后持续观察，确认不再复发
```

### 复现与验证

- **最小复现**：构造最小化复现条件（最小输入、最简环境），复现成功 = 假设成立的强证据。
- **变更回滚验证**：如果是变更引起，回滚变更后观察是否恢复；恢复 = 变更嫌疑坐实。
- **修复验证**：修复后跑「故障注入」或压测确认不复现，再走发布流程。

### Red Hat 系差异：崩溃报告与 sosreport

```text
Ubuntu（Debian 系）                 Red Hat 系（RHEL/CentOS/Fedora）
ubuntu-bug <包名>                   abrt-cli report（ABRT 自动收集）
/var/crash/（apport 报告）          /var/spool/abrt/（ABRT 报告）
/var/log/syslog                     /var/log/messages
journalctl -p err -b（两者通用）    journalctl -p err -b（两者通用）
内核崩溃：kerneloops 守护进程       kerneloops 服务 + abrtd
收集报告：ubuntu-bug 交互式提交     sosreport（一键打包系统诊断信息）
```

`sosreport` 是 Red Hat 系的一键诊断打包工具（生成 tar.xz 报告包，含 dmesg/日志/配置/网络状态），Ubuntu 上没有；Ubuntu 对应的是 `ubuntu-bug` + `/var/crash/` 下的 apport 报告。本机实测：`ubuntu-bug` 和 `kerneloops` 可用，`sosreport`、`abrt-cli` 不可用（RHEL 专有）。

## 配置文件解析

排查配置类故障，要熟悉「关键配置文件在哪、改了什么」——配置类故障的核心是「对比改之前和改之后」：

```text
常见故障配置文件位置：
/etc/fstab           —— 挂载（改错可能导致启动失败）
/etc/ssh/sshd_config —— SSH（改错可能把自己锁外面）
/etc/sysctl.conf     —— 内核参数（网络/内存调优）
/etc/rsyslog.conf    —— 日志（改错日志不落盘）
/etc/systemd/ 单元   —— 服务（改错服务起不来）
/etc/sudoers         —— sudo 权限（改错 sudo 不能用）
/etc/nginx/、/etc/mysql/ 等 —— 应用配置（改错服务拒绝启动）
```

```shell
# 排查配置类故障的标准动作
diff <(备份的原配置) <(当前配置)     # 对比改动
systemd-analyze verify <unit>        # 校验 systemd 单元语法
sshd -t                              # 校验 sshd_config 语法
nginx -t                             # 校验 nginx 配置语法
visudo -c                            # 校验 sudoers 语法
```

### 「最近变更」检查清单

变更管理意识是排障的第一直觉：**故障大概率来自最近 24 小时的某个变更**。按维度过一遍：

```text
最近变更检查清单：
1. 代码 —— 最近部署了什么版本？有没有发布窗口？
2. 配置 —— 谁改过配置？改了什么？（git 历史/备份 diff）
3. 依赖 —— 依赖的中间件/库/证书有没有升级或过期？
4. 资源 —— 磁盘/内存/连接数有没有到达上限？
5. 流量 —— 有没有大促/压测/流量调度变化？
6. 环境 —— 有没有升级内核/换硬件/改网络拓扑？
```

检查变更的利器：配置文件备份（`.bak`）、git 历史、CMDB 变更记录、发布系统日志。没有变更记录的环境，排障会慢一个量级。

## 应用场景实战

### 场景一：服务访问不了，分层排查

```shell
# 1. 应用层：进程在不在
ps aux | grep <服务>
# 2. 网络层：端口监听没
ss -tlnp | grep <端口>
# 3. 系统层：日志报什么
journalctl -u <服务> -n 50
# 4. 资源层：资源够不够
df -h && free -h
```

```text
# 实测（本机）——以 nginx:80 为例走一遍
$ ss -tlnp | grep :80
LISTEN 0 511 0.0.0.0:80 0.0.0.0:* users:(("nginx",pid=565634,fd=5),...)
$ journalctl -u nginx -n 5 --no-pager
（显示 nginx 最近启动/重载日志，无 error 即网络层正常）
```

本机 nginx 监听正常：分层排查走到第 2 步即可确认「进程在、端口在」，接下来查应用日志和防火墙。

### 场景二：用 5 Why 追根因

```text
问题：凌晨备份任务失败
Why1: 为什么失败？磁盘空间不足
Why2: 为什么磁盘不足？备份文件没清理
Why3: 为什么没清理？清理脚本没跑
Why4: 为什么没跑？cron 配置丢了
Why5: 为什么配置丢了？上次升级覆盖了 crontab
根因：升级流程没保护 cron 配置 → 修复：备份 crontab + 升级后校验
```

### 场景三：CPU 飙高，二分定位热点

```text
1. 二分：先确认是「内核态」还是「用户态」耗时
   top 看 %sy 与 %us 比例；us 高 → 用户态程序问题；sy 高 → 内核/系统调用问题
2. 二分：top 找出 CPU 大户进程（%CPU 列），锁定目标
3. 二分：perf top 定位热点函数（用户态符号或内核符号）
4. 验证：perf record -g 采样 + 火焰图确认调用链

# 实测（本机）top 前几名
4187862 root  109.1% chrome       # 用户态程序占 CPU 大户
3096327 root   18.2% hermes       # 本 agent 进程
```

### 场景四：变更回滚验证

```text
背景：昨晚发布 v2.3 后，接口超时率上升
1. 先止血：回滚到 v2.2，观察 10 分钟
2. 验证：超时率回落 → 变更嫌疑坐实
3. 定位：对比 v2.3 与 v2.2 的 diff，找到引入问题的代码
4. 根治：修复后重新发布，灰度观察
原则：回滚是验证手段也是止血手段；回滚前保留现场（日志、配置、流量数据）
```

### 场景五：磁盘告警，先止血后根治

```shell
# 1. 止血：找到大文件/大目录临时清理，恢复可用空间
df -h                       # 确认哪个分区满
du -sh /* 2>/dev/null | sort -rh | head    # 找大目录
lsof +L1                    # 找「删除但未释放」的文件（进程还占着）
# 2. 根治：定位谁在写、为什么写满
journalctl -p err -b | grep -i disk        # 相关报错
# 3. 防复发：日志轮转、清理策略、磁盘监控告警
```

## 性能与调优

排查效率本身就是「性能」——方法论能显著缩短 MTTR：

```text
1. 建立「症状 → 命令」速查表 —— 见症状直接跑对应命令，别现场翻手册
2. 沉淀排查文档 —— 解决一次记录一次，同类问题下次秒定位
3. 监控先行 —— 提前配好监控和告警，故障发生时已有现场数据，不用临时抓
4. 用脚本固化高频检查 —— 把「df/free/ss/dmesg」打包成一个 healthcheck 脚本，一键收集现场
5. 工具链分级 —— 先快后慢：ps/top/ss 秒级定位，strace/perf 分钟级深入，避免一上来就用重武器
```

```shell
# 一键 healthcheck 脚本（固化高频检查）
#!/bin/bash
# healthcheck.sh —— 一键收集排障现场
echo "===== $(date '+%F %T') ====="
uptime
echo "--- 内存 ---";      free -h
echo "--- 磁盘 ---";      df -h | head -10
echo "--- CPU 大户 ---";  top -b -n1 | head -15
echo "--- 失败单元 ---";  systemctl --failed --no-pager
echo "--- 内核错误 ---";  dmesg | tail -10
echo "--- 最近错误日志 ---"; journalctl -p err -b --no-pager | tail -10
```

排查效率的另一个维度是「并行不串行」：多个人工并行收集不同层的信息（一人查网络、一人查应用、一人查变更），而不是一个人从头查到尾。

## 安全与权限

```text
1. 排查用只读命令优先 —— df/ps/ss/dmesg 只读无害，别急着改配置/重启
2. 改配置前备份 —— cp /etc/xxx /etc/xxx.bak，改错能回滚
3. 别在排查时泄露信息 —— 日志/配置贴出去打码（密码、密钥、内网 IP、token）
4. 审计命令记录 —— 排查过程中的高危操作（kill/reboot/改配置）走审计，方便复盘
5. 权限最小化 —— 用普通用户先查，需要 root 时 sudo 单条执行，别整个 shell 切 root
6. 生产操作双人复核 —— 高危变更（重启/删数据/改防火墙）双人复核或走变更审批
7. 核心转储安全 —— core 文件可能含内存中的敏感数据，检查 /proc/sys/kernel/core_pattern 的落盘策略
```

```text
# 实测（本机）——core 转储策略
$ cat /proc/sys/kernel/core_pattern
|/usr/share/apport/apport -p%p -s%s -c%c -d%d -P%P -u%u -g%g -F%F -- %E
$ ulimit -c
0
# Ubuntu 默认把 core 交给 apport 处理（管道式），本机 ulimit -c 为 0（不产生 core）
# Red Hat 系默认 core_pattern 为 core 或 /var/lib/systemd/coredump（systemd-coredump）
```

## 故障排查

方法论本身就是「怎么排查故障」，这里给一个可直接套用的决策流：

```text
故障来了，按这个顺序走：
1. 定性 —— 什么症状？（服务挂了/变慢/报错/连不上）
2. 分类 —— 资源/网络/配置/代码，哪一类？
3. 分层 —— 自下而上逐层排除（硬件→系统→网络→应用→代码）
4. 收集 —— 日志 + 指标 + 时间线，保留现场
5. 假设 —— 提出可证伪的根因假设
6. 根因 —— 5 Why 追到根本，验证假设成立
7. 验证 —— 修复后确认不再复现，记录到文档
```

### 子案例一：磁盘写满导致服务假死

```text
症状：应用接口全部超时，进程还在但响应极慢
1. 定性：变慢类故障；df -h 发现 / 分区 100%
2. 分类：资源类（磁盘）
3. 收集：du 找大目录，lsof +L1 找已删除未释放文件
4. 根因：应用日志未轮转 + 某进程持续写日志
5. 修复：先清出空间止血（截断大日志），再配置 logrotate 轮转
6. 验证：df 回落，接口恢复，观察 24h 未再满
```

### 子案例二：端口不通，网络层二分

```text
症状：客户端连不上 8080 端口
1. 二分：本机测还是跨机测？本机 ss -tlnp 确认监听正常 → 问题在链路
2. 二分：防火墙？iptables -L / ufw status 检查放行规则
3. 二分：路由/安全组？ping 通但端口不通 → 大概率防火墙/安全组
4. 根因：云安全组未放行 8080
5. 修复：放行规则 → 验证：telnet/nc 连通
经验：ping 通 + 端口不通 = 防火墙/安全组问题的高概率信号
```

### 子案例三：负载高但 CPU 空闲

```text
症状：load average 飙到 30，但 top 里 %Cpu 空闲 90%+
1. 定性：负载高；分类：资源类（负载）
2. 关键判断：load 高而 CPU 闲 → 进程在 D 状态（不可中断睡眠，等 IO）
3. 收集：top 看 D 状态进程；iostat 看磁盘 IO；dmesg 看 IO 错误
4. 根因：磁盘故障/慢盘导致 IO 阻塞，进程全部卡在 IO 等待
5. 修复：更换磁盘/修复 RAID → 验证：load 回落
经验：load 高 ≠ CPU 高，先分清 R（运行）和 D（IO 等待）状态进程
```

## 常见问题

```text
Q1: 排查和调试有什么区别？
A: 排查（troubleshooting）是定位「系统哪里出了问题」的通用方法，调试（debugging）是定位「程序代码哪里错了」的具体技术。排查是框架，调试是其中「代码类」故障的手段。

Q2: 为什么强调「别一上来就重启」？
A: 重启会丢失崩溃现场（日志、进程状态、内存、core 文件），起来后可能又挂，但现场没了更难查。先收集信息再重启。实在要重启，先跑一遍快照命令留证据。

Q3: 5 Why 要问几次？
A: 没有固定次数，问到「根因」为止——通常是「流程/配置/代码」这类可执行动作的原因，而不是「运气不好」这种不可行动的表象。

Q4: 分层排查和故障分类什么关系？
A: 分类先缩小「方向」（资源还是网络），分层再沿着该方向逐层排除。分类是粗定位，分层是精定位。

Q5: 故障时先恢复服务还是先查根因？
A: 先止血（恢复服务），但止血前保留现场证据（快照/日志）。业务恢复后带着证据做 RCA。极端情况（几分钟内可定位）可以边查边恢复，但不要牺牲业务可用性去「慢慢查」。

Q6: 没有监控系统，故障时怎么收集历史数据？
A: 靠时间线：journalctl --since 指定时间窗口、/var/log/ 下各日志的 mtime、atop/sar 的历史归档（若装了）、shell history、cron 执行记录。事后能还原多少取决于平时留了多少痕迹——这也是「可观测性先行」的意义。

Q7: 排查中改错了配置导致问题扩大怎么办？
A: 立即回滚到备份（这也是改配置前必须备份的原因）。同时把「改了什么」记下来，回滚后对比 diff 确认恢复原状，再重新评估方案。
```

## 面试题

```text
1. 你遇到一个线上故障，第一件事做什么？
   答：先定性 + 收集现场（日志/指标/状态），别急着重启。分类判断类型，再分层定位，最后根因分析。若服务不可用，先按预案止血（回滚/切流量），止血前保留现场证据。

2. 什么是根因分析（RCA）？和治标有什么区别？
   答：RCA 找「根本原因」（磁盘满是因为日志没轮转），治标只处理表象（删文件）。治标问题会复发，RCA 才能彻底解决。RCA 输出的是原因链 + 修复动作 + 防复发措施。

3. 分层排查为什么自下而上？
   答：底层故障（硬件/内核/网络）会影响上层，但上层故障不影响底层。自下而上能先排除「地基问题」，避免在上层白查。

4. 5 Why 的边界在哪（什么时候该停）？
   答：追到「可执行动作」为止——能落到「改配置/加监控/补流程」这类具体动作，就是根因；再往下就是超出职责范围的空话。

5. 线上服务变慢，你的排查顺序是什么？
   答：先看监控曲线确认时间点和影响面（是整体慢还是个别接口慢）→ top/uptime 看负载与资源 → 分层定位（网络/应用/数据库）→ 检查最近变更 → 必要时 strace/perf 深入（见 17.2/16.6）。全程带着假设去验证。

6. 怎么证明你的修复真的有效？
   答：三层验证：一、症状消失（接口恢复、告警解除）；二、不复现（持续观察 + 必要时故障注入/压测复现路径）；三、根因侧验证（触发根因的条件不再存在，如磁盘监控已上线、logrotate 已配置）。

7. 故障复盘报告应该包含哪些内容？
   答：现象（用户视角看到的）、时间线（故障发生到恢复的完整过程）、根因（原因链）、影响范围（时长/用户/损失）、临时措施（止血动作）、根治措施（长期修复）、改进项（监控/流程/演练），最后要有明确的负责人和截止时间。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先分类再排查，别上来乱试命令
2. 分层排查自下而上，不漏层不跳层
3. 先收集信息再动手，别一上来就重启（现场没了）
4. 找根因别治标（5 Why 追到根本）
5. 排查过程记录（改了啥、看到啥），方便回溯和复盘
6. 先查「最近变更」——绝大多数故障由变更引发
7. 先止血后根治——服务不可用时恢复优先，证据先留
8. 每次故障都做复盘，把改进项落到监控、告警、文档上

### 踩坑记录

```text
坑 1：一上来就重启服务，现场没了
结论：服务挂了直接重启，起来后又挂，但现场没了难查。
原因：重启丢失了崩溃现场（日志/状态/内存）。
解法：先收集信息（日志/状态/快照）再重启，保留现场。

坑 2：治标不治本，问题反复出现
结论：磁盘满就删文件，过几天又满。
原因：只处理表象（删文件），没找根因（为什么一直满）。
解法：5 Why 追根因（可能是日志没轮转/某进程狂写），并加监控防复发。

坑 3：跳层排查，漏掉中间层
结论：服务连不上，只查了应用日志，其实是网络层防火墙挡了。
原因：没按层排查，跳过了网络层。
解法：分层逐层排查，每层确认正常再往下。

坑 4：信息没收集全就下结论
结论：只看一条报错就判断原因，实际是另一个问题。
原因：信息不完整，误判根因。
解法：收集完整信息（日志+指标+时间线）再分析。

坑 5：不记录排查过程，下次同样问题又从头查
结论：同样的问题过几天又出现，忘了上次怎么查的。
原因：没记录排查过程。
解法：记录排查步骤和结果，沉淀成文档（就是本知识库的意义）。

坑 6：不看日志瞎猜，靠「试试」定位
结论：怀疑是 A 问题就改 A 的配置，不行再改 B，反复试错浪费时间还可能引入新问题。
原因：没有证据驱动的假设，凭直觉乱试。
解法：先看日志和指标拿到证据，再提出可证伪的假设，验证一个假设再动下一个。

坑 7：忽略了「最近改了什么」
结论：排查了半天代码和配置，最后发现是昨天发布的版本引入的问题。
原因：没有变更管理意识，把变更因素排除在排查范围外。
解法：排查第一步先查最近 24h 变更（发布/配置/流量/依赖），回滚验证最快。

坑 8：止血时没留证据就回滚/重启
结论：回滚后服务恢复了，但根因永远查不清——现场被自己清掉了。
原因：回滚/重启前没保留快照、日志段、进程状态。
解法：任何恢复动作前先跑一遍快照命令留档，再执行止血。

坑 9：应急处理时凭记忆改配置，不回滚预案
结论：应急时改了一个参数，问题没解决还忘了改过什么，后续排查被误导。
原因：应急操作没记录、没备份、没有回滚预案。
解法：改任何配置前先备份 + 记录改动，先想好怎么回滚再动手。
```
