## 概述

排查故障不是「凭感觉乱试」，而是「有方法地定位根因」。核心四步：故障分类（是什么类型的问题）、分层排查（按层逐层排除）、信息收集（收集证据，别急着改）、根因分析（找到根本原因，不是表象）。掌握方法论，排查从「碰运气」变成「有章法」，能更快、更准地定位问题。

```text
排查方法论四步：
1. 故障分类 —— 资源类/网络类/配置类/代码类，先判断类型
2. 分层排查 —— 从底层到上层（硬件→系统→应用→代码）逐层排除
3. 信息收集 —— 收集日志/指标/现场，别急着动手改
4. 根因分析 —— 找根本原因，不是治标（5 why 法）
```

## 故障分类

先给故障分类，判断「是什么类型的问题」：资源类（CPU/内存/磁盘不够）、网络类（连不上/丢包/延迟）、配置类（改错了配置）、代码类（程序 bug）。分类能缩小排查方向——磁盘满和网络不通的排查路径完全不同。快速分类靠「症状 + 关键命令」：磁盘满看 df、CPU 高看 top、网络不通看 ping/ss。

```text
故障分类：
1. 资源类 —— CPU 飙高/内存不够/磁盘满/句柄耗尽
2. 网络类 —— 连不上/丢包/延迟/端口不通
3. 配置类 —— 改错配置（fstab/网络/服务）
4. 代码类 —— 程序 bug（崩溃/泄漏/死循环）
```

## 分层排查

分层排查：从底层到上层逐层排除，像剥洋葱。典型层次：硬件 → 内核/驱动 → 系统服务 → 应用 → 代码。例：服务访问不了，先查进程在不在（系统层）→ 端口监听没（网络层）→ 日志报什么（应用层）。分层的好处：不漏层、不跳层，每层确认正常再往下。

```text
分层排查（自下而上）：
硬件 → 内核/驱动 → 系统服务 → 网络 → 应用 → 代码
# 例：服务访问不了
1. 进程在不在？        ps aux | grep xxx
2. 端口监听没？        ss -tlnp | grep 端口
3. 网络通不通？        ping/nc
4. 日志报什么？        journalctl -u xxx
```

## 信息收集

排查前先「收集信息」——日志、指标、现场状态，别急着改。关键原则：先观察后动手、保留现场（改之前记录原状态）、收集完整信息（错误日志 + 系统状态 + 时间线）。常见错误：一上来就重启服务（现场没了，更难查）。信息收集的命令：dmesg（内核）、journalctl（服务日志）、top/free/df（资源）、ss（网络）。

```shell
# 快速收集现场信息
dmesg | tail -20           # 内核错误
journalctl -xe             # 最近的系统日志
top -b -n 1 | head         # CPU/内存快照
df -h && free -h           # 磁盘/内存
ss -tlnp                   # 端口
```

```text
信息收集原则：
1. 先观察后动手 —— 别一上来就重启/重装
2. 保留现场 —— 改之前记录原状态（配置备份）
3. 完整信息 —— 错误日志 + 系统状态 + 时间线
```

## 根因分析

根因分析（RCA）找「根本原因」，不是「表象」——表象是「服务挂了」，根因是「磁盘满导致写不了日志，日志写不了导致服务崩溃」。方法：5 Why（连续问 5 个为什么，追到根）、对比法（正常 vs 异常状态对比）、时间线还原（出事前后发生了什么）。治标（重启服务）不治本（磁盘还会满），根因分析才能彻底解决。

```text
根因分析方法：
1. 5 Why —— 连续追问「为什么」，追到根本原因
2. 对比法 —— 正常状态 vs 异常状态，找差异
3. 时间线 —— 还原「出事前后」发生了什么
```

```text
# 5 Why 示例（服务挂了的根因）
服务挂了 → 为什么？写日志失败 → 为什么？磁盘满 → 为什么？日志没轮转 → 为什么？没配 logrotate → 根因：缺日志轮转配置
```

## 应用场景实战

### 场景一：服务访问不了，分层排查

```shell
# 1. 应用层：进程在不在
ps aux | grep <服务>
# 2. 网络层：端口监听没
ss -tlnp | grep <端口>
# 3. 系统层：日志报什么
journalctl -u <服务> -n 50
# 4. 资源层：资源够不够
df -h && free -h
```

### 场景二：用 5 Why 追根因

```text
问题：凌晨备份任务失败
Why1: 为什么失败？磁盘空间不足
Why2: 为什么磁盘不足？备份文件没清理
Why3: 为什么没清理？清理脚本没跑
Why4: 为什么没跑？cron 配置丢了
Why5: 为什么配置丢了？上次升级覆盖了 crontab
根因：升级流程没保护 cron 配置 → 修复：备份 crontab + 升级后校验
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先分类再排查，别上来乱试命令
2. 分层排查自下而上，不漏层不跳层
3. 先收集信息再动手，别一上来就重启（现场没了）
4. 找根因别治标（5 Why 追到根本）
5. 排查过程记录（改了啥、看到啥），方便回溯和复盘

### 踩坑记录

```text
坑 1：一上来就重启服务，现场没了
结论：服务挂了直接重启，起来后又挂，但现场没了难查。
原因：重启丢失了崩溃现场（日志/状态/内存）。
解法：先收集信息（日志/状态）再重启，保留现场。

坑 2：治标不治本，问题反复出现
结论：磁盘满就删文件，过几天又满。
原因：只处理表象（删文件），没找根因（为什么一直满）。
解法：5 Why 追根因（可能是日志没轮转/某进程狂写）。

坑 3：跳层排查，漏掉中间层
结论：服务连不上，只查了应用日志，其实是网络层防火墙挡了。
原因：没按层排查，跳过了网络层。
解法：分层逐层排查，每层确认正常再往下。

坑 4：信息没收集全就下结论
结论：只看一条报错就判断原因，实际是另一个问题。
原因：信息不完整，误判根因。
解法：收集完整信息（日志+指标+时间线）再分析。

坑 5：不记录排查过程，下次同样问题又从头查
结论：同样的问题过几天又出现，忘了上次怎么查的。
原因：没记录排查过程。
解法：记录排查步骤和结果，沉淀成文档（就是本知识库的意义）。
```
