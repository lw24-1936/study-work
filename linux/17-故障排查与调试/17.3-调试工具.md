## 概述

调试工具用于「程序崩溃 / 卡死 / 行为异常 / 内存问题」的深度分析，是故障排查方法论（[[17.1-排查方法论]]）的「最后一公里」：前面的 top/free/dmesg 只能定位到进程，调试工具负责定位到**函数、代码行、甚至变量值**。按场景把工具分成五类：

```text
调试工具五类：
1. 交互式调试 —— gdb（断点/单步/看变量/看栈/attach 运行中进程）
2. 崩溃取证   —— coredump（core_pattern/ulimit -c/gdb 分析 core）
3. 动态追踪   —— strace/ltrace（系统调用/库调用）、jstack（Java 线程）
4. 内存调试   —— valgrind memcheck（泄漏/越界）、ASAN（编译期插桩）
5. 二进制分析 —— addr2line/nm/objdump/readelf/strings（无源码逆向定位）
6. 内核调试   —— oops 解读、kdump + crash 工具
```

核心场景：**程序段错误（segfault）崩溃**，靠 coredump + gdb 定位崩溃发生在哪一行；**进程卡死**，靠 pstack/gdb 抓全线程栈看卡在哪个函数；**内存泄漏**，靠 valgrind/ASAN 定位泄漏点。工具本身不产生结论，结论来自对「断点命中的上下文 + 调用栈 + 变量值」的解读。

## 核心概念

1. **gdb**：Linux 标准调试器，基于 ptrace。三种启动方式：`gdb ./myapp`（启动调试）、`gdb -p <PID>`（附加运行中进程）、`gdb ./myapp core`（分析 coredump）。能力：断点（break/watch）、单步（next/step/finish）、查看变量与内存（print/x）、调用栈（bt/frame）、线程（info threads/thread apply all bt）。gdb 也能当「穷人版 pstack」用：`gdb -p <PID> -batch -ex 'thread apply all bt'`。
2. **coredump（核心转储）**：程序收到致命信号（SIGSEGV/SIGABRT/SIGBUS/SIGILL）时，内核把进程的**内存映像 + 寄存器 + 调用栈 + 打开的文件描述符**写入 core 文件，随后进程退出。core 文件路径/处理方式由 `/proc/sys/kernel/core_pattern` 决定；是否生成受 `ulimit -c` 控制。core 是「事故现场照片」，事后用 `gdb 程序 core` 回放崩溃瞬间。
3. **pstack / eu-stack**：打印进程**所有线程的调用栈**，回答「卡死的进程卡在哪个函数」。pstack 是 Red Hat 系工具（Ubuntu 无包）；eu-stack 来自 elfutils。两者本质都是 gdb 的 bt 封装，gdb 全平台可替代。
4. **addr2line**：把「崩溃地址（虚拟地址/函数偏移）」翻译成「源文件:行号」，依赖 DWARF 调试信息。配合崩溃日志（dmesg segfault 行、日志里的 RIP 地址）无需 core 也能定位。
5. **strace / ltrace**：strace 跟踪**系统调用**（文件/网络/信号/进程），回答「程序在做什么、卡在哪个 syscall、为什么打不开文件」；ltrace 跟踪**动态库函数调用**（printf/malloc 等）。生产排查「假死/慢/权限错误」的首选。
6. **valgrind memcheck**：动态二进制插桩的内存调试器，检测**越界读写、使用未初始化内存、双重释放、内存泄漏**。程序变慢 10~50 倍，用于测试环境复现。
7. **ASAN（AddressSanitizer）**：编译器（gcc/clang）编译期插桩的内存错误检测器，`-fsanitize=address` 即可，比 valgrind 快一个数量级（慢 2~3 倍），能抓 use-after-free/栈越界/堆越界，现已是内存调试首选，CI 必备。
8. **jstack / jmap / jstat**：Java 排查三件套。jstack 打线程 dump（查死锁/线程卡住）；jmap 打堆 dump/查堆直方图（内存泄漏取证）；jstat 看 GC 与堆区实时数据（`-gcutil` 看 Full GC 频率）。对应 [[16.6-综合调优工具]] 中的 JVM 调优。
9. **pdb**：Python 标准调试器（`python3 -m pdb app.py`），支持断点/单步/打印变量；生产上更常用 faulthandler（`faulthandler.enable()`，崩溃自动打 Python 栈）。
10. **内核 oops / panic / kdump**：内核态崩溃叫 oops（可继续运行，但可能已损坏）；致命时 panic（停机）。kdump 机制：系统启动时用 kexec 预留一块内存给「捕获内核」，主内核 panic 时跳到捕获内核把内存转储成 vmcore，事后用 `crash` 工具分析。
11. **debuginfod / debuginfo 包**：符号服务。Ubuntu 有 debuginfod（`https://debuginfod.ubuntu.com`，gdb 自动按需下载符号）；Red Hat 用 `dnf debuginfo-install <包>` 装 dbgsym 等价物。发行版二进制普遍 stripped，装了符号包才能看到函数名。
12. **容器内调试**：容器本质是受限命名空间 + cgroup 的进程，gdb attach 容器进程在**宿主机视角**做（`gdb -p 容器内PID`），需 root/CAP_SYS_PTRACE；Docker 默认 seccomp profile 允许同容器内 ptrace，但宿主机 attach 容器进程要特权。

## 工作原理

### 1. ptrace 与 gdb 断点实现

gdb 的一切基于 ptrace 系统调用（[[15.1-系统调用]]）：`PTRACE_ATTACH` 附加目标进程（发送 SIGSTOP 暂停它），`PTRACE_PEEKDATA/POKEDATA` 读写目标内存，`PTRACE_GETREGS/SETREGS` 读写寄存器，`PTRACE_CONT/SINGLESTEP` 控制执行。断点分三类：

```text
软件断点：把目标地址的指令首字节替换为 int3（0xCC）软中断。
          执行到该处 CPU 触发 #BP 异常 → 内核把信号发给 gdb →
          gdb 恢复原字节、停下等指令。开销小，数量不限。
硬件断点（watch 变量）：利用 CPU 调试寄存器 DR0~DR3，值变化时中断。
          不修改指令，适合 ROM/只读内存，数量最多 4 个。
单步：置 EFLAGS 的 TF（陷阱标志）位，执行一条指令后触发 #DB 异常。
```

条件断点 `break foo if i==100` 是「软件断点 + 命中后求值条件」，条件不满足自动继续——注意它仍有断点命中开销。

### 2. coredump 生成流程

```text
致命信号（SIGSEGV 等）→ 内核 do_coredump():
  ① 检查 RLIMIT_CORE（ulimit -c）是否为 0，为 0 直接不生成
  ② 按 /proc/sys/kernel/core_pattern 决定去向：
     纯路径（如 /tmp/core.%e.%p）→ 直接写文件
     以 | 开头（如 |/usr/share/apport/apport ...）→ 通过管道交给
       用户态程序处理（apport/systemd-coredump），core 数据从 stdin 流入
  ③ 按 /proc/<PID>/coredump_filter 决定包含哪些内存段
  ④ 生成 ELF 格式 core：程序头（寄存器、NT_FILE 段映射、NT_PRPSINFO）
     + 各内存段内容（真实内存快照）
  ⑤ 进程退出，shell 提示 Segmentation fault (core dumped)
```

注意管道模式（`|`）下**不落盘**：core 数据直接进 apport/systemd-coredump，找不到 core 文件是正常的，要看目标程序的输出（apport 写 `/var/crash/*.crash`，systemd-coredump 进 journal + `/var/lib/systemd/coredump/`）。`core_pipe_limit`（本机实测 10）限制同时处理的管道 core 数，超限的 core 被丢弃。

### 3. 各工具原理一句话

```text
addr2line：解析 ELF 的 .debug_line 段（DWARF），把虚拟地址映射到 文件:行号
nm：读符号表（.symtab 静态符号 / .dynsym 动态符号），列出函数与全局变量地址
objdump：反汇编（-d 代码段）、查看段（-h）、导出符号（-t）
readelf：ELF 文件头/程序头/节头/动态段的全方位查看器（更底层）
strings：从二进制里提取可打印字符串（版本号、错误消息、路径线索）
strace：ptrace + 在每次系统调用出入点截获（PTRACE_SYSCALL），
        记录 syscall 号、参数、返回值、errno
ltrace：用 LD_PRELOAD 或断点技术拦截动态库函数调用（printf/malloc/strcpy）
valgrind：把程序翻译成中间码（VEX），插入内存检查指令后 JIT 执行；
          memcheck 用「影子内存」记录每字节的合法/已定义状态
ASAN：编译期在每次读写前插入检查代码（shadow memory 技术），
      运行时越界立刻报「地址 + 栈 + 分配点」
jstack：通过 JVM attach API 让 JVM 在安全点生成 Thread Dump（纯文本线程栈）
pdb：Python 解释器内嵌调试器，通过 sys.settrace 实现单步与断点
kdump：kexec 启动时保留一块内存给捕获内核；panic 时跳转过去，
       用 /proc/vmcore 把主内核内存导出为 vmcore，crash 工具离线分析
```

## 常用命令与配置

### gdb 会话命令速查

```text
启动方式：
  gdb ./myapp                启动调试（run 后开始执行）
  gdb ./myapp core           分析 coredump（不执行，直接看崩溃现场）
  gdb -p <PID>               附加运行中进程（会 SIGSTOP 暂停它）
  gdb -batch -ex '命令' ...  非交互批量执行（脚本化）

会话内命令：
  break main / break 42 / break foo if i==100   设断点（函数/行/条件）
  info breakpoints            查看断点列表
  delete 1 / disable 1        删/禁断点
  watch var / watch *(int*)p  变量 watch（硬件断点，值变化即停）
  run <args>                  开始运行
  next (n) / step (s)         单步：n 不进入函数，s 进入函数
  finish                      跑完当前函数并返回（停在调用处）
  continue (c)                继续运行到下一个断点
  print var / p *p            打印变量（可带表达式 p a+b）
  x/16xb 0x7fff...            查看内存（x 格式 数量 单位 地址）
  bt / bt full                调用栈（full 带局部变量）
  frame 0 / up / down         切换栈帧
  info threads                列出所有线程
  thread 3 / thread apply all bt   切线程 / 全线程打印栈
  info registers              查看寄存器
  set var x=10                修改变量（调试神器）
  set pagination off          关闭分页（脚本化必须）
  quit (q)                    退出
```

### strace / 其他工具

```shell
# strace：追踪系统调用
strace -f -p <PID>                  # 附加进程跟踪所有子线程（生产抓现场）
strace -c ls /tmp                   # 统计各 syscall 调用次数/耗时
strace -e trace=openat,read -p <PID>  # 只跟 openat/read
strace -tt -T -f ./myapp            # 带微秒时间戳和耗时（慢在哪一步）
strace -o /tmp/trace.log -p <PID>   # 输出到文件（避免刷屏）

# ltrace（Ubuntu 需 apt install ltrace）
ltrace -p <PID>                     # 跟踪库函数调用
ltrace ./myapp                      # 看 malloc/strlen 等调用序列

# Java 三件套
jstack <PID>                        # 线程 dump（看卡住/死锁）
jstack -l <PID>                     # -l 带锁信息（死锁检测）
jmap -heap <PID>                    # 堆配置与使用
jmap -histo <PID> | head -20        # 堆对象直方图（找泄漏对象）
jstat -gcutil <PID> 1000            # 每秒看 GC 百分比/次数（Full GC 风暴）

# Python
python3 -m pdb app.py               # 调试器启动
python3 -X faulthandler app.py      # 崩溃时自动打印 Python 调用栈
```

### valgrind 与 ASAN

```shell
# valgrind memcheck（未装：Ubuntu apt install valgrind；RHEL dnf install valgrind）
valgrind --leak-check=full --show-leak-kinds=all ./myapp

```

### core dump 配置

```shell
ulimit -c unlimited            # 当前 shell 允许生成 core（0 = 禁止）
ulimit -c 0                    # 关闭
echo 'core' > /proc/sys/kernel/core_pattern        # 临时：写当前目录 core
echo '|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h' \
     > /proc/sys/kernel/core_pattern               # 临时：交给 systemd-coredump
echo 1 > /proc/sys/kernel/core_uses_pid            # core 文件名带 PID
sysctl -w kernel.core_pattern='/var/crash/core.%e.%p'   # sysctl 方式临时设置
# 持久化：写入 /etc/sysctl.d/99-core.conf
echo 'kernel.core_pattern=/var/crash/core.%e.%p' > /etc/sysctl.d/99-core.conf
sysctl -p /etc/sysctl.d/99-core.conf
```

## 配置文件解析

### /proc/sys/kernel/core_pattern

```text
# 实测（本机 Ubuntu 24.04 默认值）
$ cat /proc/sys/kernel/core_pattern
|/usr/share/apport/apport -p%p -s%s -c%c -d%d -P%P -u%u -g%g -F%F -- %E

字段解析：
|                          —— 管道模式：core 数据从 stdin 交给 apport，不落盘
/usr/share/apport/apport   —— 处理程序（Ubuntu 的崩溃报告收集器）
-p%p  进程 PID        -s%s  信号号（11=SIGSEGV）
-c%c  RLIMIT_CORE    -d%d  dumpable 标志
-P%P  全局 PID（容器外视角） -u%u -g%g  UID/GID
-F%F  coredump_filter 值
%E    可执行文件完整路径

常见替代格式：
core                      —— 当前工作目录生成名为 core 的文件
/tmp/core.%e.%p           —— 指定目录 + 可执行名(%e) + PID(%p)
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h   —— RHEL 系默认
```

要点：以 `|` 开头的模式**不写文件**；Ubuntu 的 apport 把崩溃包写到 `/var/crash/*.crash`；RHEL 的 systemd-coredump 把 core 存到 `/var/lib/systemd/coredump/` 并用 journal 记录元数据（`coredumpctl info` 查看）。**Red Hat 系差异**：RHEL 用 `coredumpctl list` 列崩溃、`coredumpctl gdb` 直接进 gdb；Ubuntu（apport 模式）下这些命令不可用（本机实测 `coredumpctl: 未找到命令`）。

### /proc/<PID>/coredump_filter 与 core_uses_pid

```text
# 实测（本机默认）
$ cat /proc/self/coredump_filter
00000033

位含义（按 bit）：
bit0 0x01 匿名私有内存（堆/栈）        —— 默认包含
bit1 0x02 匿名共享内存（mmap MAP_ANON|MAP_SHARED）—— 默认包含
bit2 0x04 文件映射私有内存（.so 代码段）
bit3 0x08 文件映射共享内存
bit4 0x10 ELF 文件头页（私有映射）     —— 默认包含（gdb 恢复符号需要）
bit5 0x20 ELF 文件头页（共享映射）     —— 默认包含
bit6 0x40 hugepage 私有   bit7 0x80 hugepage 共享

0x33 = 0x01|0x02|0x10|0x20：含匿名内存 + ELF 头页，不含文件映射数据段。
省空间技巧：echo 0x31 > /proc/<PID>/coredump_filter 只留匿名私有内存
（核心数据都在匿名段，文件映射段可由可执行文件重映射，core 可小很多）。
core_uses_pid（本机实测 0）：=1 时文件名自动带 .PID。
```

### 其他相关配置

```text
~/.gdbinit / 系统 /etc/gdb/gdbinit —— gdb 启动脚本：
  set pagination off         关闭分页（脚本化调试别卡在 more）
  set print pretty on        结构体美化打印
  set debuginfod enabled off 关闭符号自动下载（内网/慢速环境）
  set print thread-events off 减少刷屏

/etc/default/apport —— Ubuntu apport 开关（enabled=0 关闭崩溃接管，
  改回内核直接写 core 文件）

/etc/systemd/coredump.conf —— systemd-coredump 行为（Storage=external|journal）
  （RHEL/CentOS 用）

/etc/abrt/abrt.conf —— RHEL 崩溃收集服务配置（abrt-cli list 查看）

/etc/security/limits.conf —— 持久化 ulimit：
  * soft core unlimited    # 所有用户 core 无限制
  * hard core unlimited
```

## 应用场景实战

### 场景一：程序段错误崩溃，用 coredump + gdb 定位

**现象**：程序跑着跑着退出，终端报 `Segmentation fault (core dumped)`，或日志里只有一句「signal 11 (SIGSEGV)」。

**定位过程**：先确认 core 是否生成、去了哪：

```shell
# 1. 启用 core 生成
ulimit -c unlimited
# 2. 确认 core 去向（管道模式 = 被 apport/systemd-coredump 接管）
cat /proc/sys/kernel/core_pattern
# 3. 复现崩溃
./myapp
# 4. 找 core：当前目录 / /var/crash / /var/lib/systemd/coredump
ls -lh core* /var/crash/*.crash 2>/dev/null
# 5. 用 gdb 分析（程序 + core 一起给）
gdb ./myapp core
(gdb) bt              # 看崩溃时的完整调用栈
(gdb) frame 0         # 切到崩溃帧（最里层）
(gdb) info locals     # 崩溃点的局部变量值
(gdb) p ptr           # 打印疑似问题变量（NULL 指针一目了然）
```

```text
# 实测（本机）——内核记录的进程 segfault 消息（dmesg）
$ dmesg | grep -iE 'segfault|general protection' | tail -3
[1941166.633145] hermes[1380836]: segfault at 8 ip 00000000018ca951 sp 00007da238ff86d0 error 4 in python3.12[1483951,1600000+8ca000] likely on CPU 2 (core 2, socket 0)
[1942744.873651] hermes[1477508]: segfault at 8 ip 00000000018ca951 sp 000078c2f3ffe6d0 error 6 in python3.12[1483951,1600000+8ca000] likely on CPU 3 (core 3, socket 0)

字段解读：
segfault at 8           —— 访问的地址 0x8（典型 NULL 指针 + 偏移 8 的字段访问）
ip 00000000018ca951     —— 崩溃指令地址（配合 addr2line 可转行号）
```

**根因**：空指针解引用 / 访问已释放内存 / 数组越界 / 栈溢出。**解决**：gdb 看 bt + 变量值定位代码行，修复后回归；预防：编译加 `-g -fno-omit-frame-pointer`、CI 跑 ASAN、上线保留带符号版本。

### 场景二：进程卡死（CPU 0% 但无响应），抓全线程栈

**现象**：服务不响应请求，CPU 占用却很低——典型的**死锁/等待**，不是死循环。**定位**：打印所有线程栈，看线程们卡在哪个锁/哪个函数。

```shell
# 1. 找 PID
ps aux | grep myapp
# 2. 抓全线程栈（pstack 在 Ubuntu 无包，用 gdb 等价命令）
gdb -p <PID> -batch -ex 'thread apply all bt' 2>/dev/null
# 3. 看锁等待（futex 相关调用是死锁高发区）
strace -f -p <PID> -e trace=futex 2>&1 | head -20
```

```text
# 实测（本机）——gdb 批量模式对发行版二进制读取（attach 需 root/ptrace 权限）
$ cat /proc/sys/kernel/yama/ptrace_scope
1    # YAMA 默认档：仅父进程可 attach 子进程；root 不受限
$ gcore --help | head -1
usage:  gcore [-a] [-o prefix] pid1 [pid2...pidN]   # gcore 也可离线打 core

示例输出（thread apply all bt 节选）：
Thread 3 (Thread 0x7f...):
#0  __futex_abstimed_wait_common (...) at futex-internal.c
#1  pthread_cond_timedwait (...) 
#2  worker_thread () at worker.c:88     ← 线程在等条件变量
Thread 1 (Thread 0x7f...):
#0  __lll_lock_wait (...)                ← 主线程在等锁
#1  pthread_mutex_lock (...) 
#2  main () at main.c:120                ← 死锁现场
```

**根因**：死锁（锁顺序不一致）、等待外部资源（DB 连接池耗尽、NFS 挂起）、信号量泄漏。**解决**：栈显示 `pthread_mutex_lock` 互相等待 → 检查加锁顺序；等外部资源 → 看对应服务；预防：加锁按固定顺序、`timeout` 保护、监控线程状态。

### 场景三：内存泄漏 / 越界，用 valgrind 与 ASAN

**现象**：进程 RSS 持续上涨，重启后回落（泄漏）；或偶尔崩溃/数据被改写（越界）。**定位**：

```shell
# 1. 确认泄漏：观察 RSS 是否只涨不跌
ps -o pid,rss,vsz,comm -p <PID>
# 2. valgrind 跑一遍（测试环境；程序慢 10~50 倍）
valgrind --leak-check=full --show-leak-kinds=all ./myapp 2>&1 | tail -30
# 3. ASAN 重新编译跑（快，CI 用）
gcc -g -fsanitize=address -o myapp_asan myapp.c
./myapp_asan
```

```text
示例（valgrind 报告解读）：

==12345==    at 0x4848899: malloc (vg_replace_malloc.c:...)
==12345==    by 0x4012B4: create_node (list.c:17)      ← 泄漏分配点
==12345==    by 0x4013A1: main (main.c:52)             ← 调用链
==12345== LEAK SUMMARY:
==12345==   definitely lost: 40 bytes in 1 blocks      ← 确定泄漏
==12345==   indirectly lost: 0 bytes in 0 blocks
==12345==   still reachable: 2,048 bytes in 1 blocks   ← 可忽略（全局量）
```

**根因**：malloc/new 后未 free/delete、错误路径提前 return、容器/缓存无限增长。**解决**：按 valgrind/ASAN 的「分配点 + 调用栈」修代码；预防：RAII/智能指针、限制缓存上限、监控 RSS 告警。valgrind 与 ASAN 取舍：valgrind 不用改编译（适合现有二进制、查泄漏）；ASAN 要重新编译但快、能抓 use-after-free。

### 场景四：无源码二进制分析（addr2line / nm / objdump / strings）

**现象**：只有崩溃日志里的地址，或一个不知道是什么的二进制。**定位**：

```shell
# 1. 先看是什么文件
file ./myapp
# 2. 看 ELF 头（架构/类型/入口点）
readelf -h ./myapp
# 3. 查符号表（stripped 则只有动态符号）
nm -D ./myapp | grep -i ' foo\| main'      # -D 动态符号
# 4. 崩溃地址转源码行（配合 dmesg 的 ip 地址）
addr2line -e ./myapp -f 0x18ca951          # -f 同时给函数名
# 5. 反汇编看崩溃指令附近
objdump -d ./myapp | grep -A 5 '18ca951'
# 6. 提取字符串找线索（版本/路径/错误消息）
strings ./myapp | grep -iE 'error|version|/var/'
```

### 场景五：Java 服务卡死 / 高 CPU，jstack 定位

**现象**：Java 服务无响应或某线程占满 CPU。**定位**（jstack 已装，本机实测）：

```shell
jstack <PID> > /tmp/jstack.txt        # 线程 dump
grep -n 'deadlock\|BLOCKED\|WAITING' /tmp/jstack.txt
jstack -l <PID> | grep -A 5 'Found one Java-level deadlock'   # 死锁检测
jmap -histo <PID> | head -20          # 堆对象直方图（泄漏嫌疑对象）
jstat -gcutil <PID> 1000 5            # GC 状况（Full GC 风暴 → 卡顿）
```

```text

    jstack [-l][-e] <pid>
        (to connect to running process)
```

**根因**：线程池耗尽（外部依赖慢）、死锁、Full GC 风暴、业务死循环。**解决**：按 dump 里 BLOCKED/WAITING 链定位；高 CPU 用 `top -H -p <PID>` 找线程号再 `jstack` 里对 nid（十六进制）；预防：线程池参数、GC 监控、连接超时。

### 场景六：内核 oops / panic，kdump 分析

**现象**：dmesg 出现 oops（含 RIP/调用栈），极端情况整机 panic 重启。**定位**：

```shell
# 1. 看 oops 现场
dmesg | grep -A 30 -i 'BUG:\|Oops:' | tail -40
# 2. 确认 panic 策略
cat /proc/sys/kernel/panic_on_oops       # 1 = oops 也 panic（重负载保护）
cat /proc/sys/kernel/panic                # 非 0 = panic 后自动重启秒数
# 3. kdump 配置（RHEL/Ubuntu 都支持）
systemctl status kdump                    # Ubuntu: apt install linux-crashdump
cat /etc/default/kdump-tools              # USE_KDUMP=1 预留 crashkernel 内存
# 4. 分析 vmcore（crash 工具，需内核符号）
crash /usr/lib/debug/boot/vmlinux-$(uname -r) /var/crash/*/vmcore
crash> bt                                 # 内核态调用栈
crash> log                                # 崩溃前内核日志
```

```text
示例（内核 oops 关键字段解读）：
BUG: unable to handle kernel NULL pointer dereference at 0000000000000000
RIP: 0010:my_driver_ioctl+0x1c/0x80 [mydrv]   ← 崩溃函数+偏移（模块名）
Call Trace:                                     ← 内核调用栈
  <TASK>
  __x64_sys_ioctl+0x.../...
  do_syscall_64+0x.../...
  entry_SYSCALL_64_after_hwframe+0x...
RIP: 0010:... Code: ... 48 8b 03 48 89 df ...  ← 崩溃指令机器码
```

**根因**：内核/驱动 bug、硬件异常（EDAC/MCE 记录）、模块与内核版本不匹配。**解决**：升级内核/驱动；开 kdump 留证；panic_on_oops 视业务取舍（默认 0 可继续运行但状态可能已损坏）。**Red Hat 系差异**：RHEL 的 kdump 由 `kdump.service` + `/etc/kdump.conf` 管理，`crashkernel=auto` 内核参数预留内存，`sosreport` 一键收集全套诊断包。

## 性能与调优

```text
1. core 文件体积 —— core 是内存快照，大程序 core 数 GB。
   控制手段（按性价比排序）：
   a) coredump_filter 只留匿名内存段（echo 0x31 > .../coredump_filter）
   b) ulimit -c 限制大小（如 ulimit -c 1048576 = 1GB 上限）
   c) 管道模式交给 systemd-coredump，配 Storage=external + 定期清理
   d) 崩溃频繁时先看日志定位，别每个 crash 都存全量 core
2. gdb attach 开销 —— attach 会 SIGSTOP 暂停目标进程：
   生产环境用 -batch 一条命令拿栈立刻退出，别开交互会话挂着；
   重活（>1s 全线程 bt）选业务低峰做。
3. -g 与 -O2 共存 —— -g 只加 DWARF 调试信息不改代码生成，
   -g -O2 完全兼容且推荐（调试优化版行为更接近生产）；
   真正影响栈回溯的是 -fomit-frame-pointer（发行版默认开），
   自研程序建议 -fno-omit-frame-pointer 或调试时用 DWARF 栈回溯。
4. debuginfod —— 按需从符号服务器下载调试信息（本机 gdb 默认启用），
   内网环境可自建 debuginfod 或改本地 dbgsym 源；下载会略慢，
   批量脚本里 set debuginfod enabled off。
5. 采样/插桩开销对照 —— strace 慢 10~100 倍、valgrind 慢 10~50 倍、
   ASAN 慢 2~3 倍、gdb 断点命中时显著变慢。生产只做短时取证，
   常驻检测用 eBPF（[[16.6-综合调优工具]]）。
6. 符号管理 —— 发布时 strip 生产件，符号文件（.debug）归档到
   符号服务器，崩溃时按 build-id 找回，比带符号发布安全且省空间。
```

## 安全与权限

```text
1. ptrace 权限（YAMA）—— /proc/sys/kernel/yama/ptrace_scope：
   0 = 任意同 uid 进程可互 attach；1 = 仅父进程可 attach 子进程（默认，本机实测=1）；
   2 = 仅 root；3 = 禁止（含 root，需重启恢复）。
   gdb -p 报 Operation not permitted 先看这个值；root 不受 YAMA 限制。
   生产建议保持 1：防普通用户互相 dump 进程内存（窃取 token/密钥）。
2. core 文件含敏感数据 —— core 是内存全快照：密码、密钥、Token、
   加密中间量都在里面。管控：core 文件权限 600、目录受限、
   核心系统（CA/支付）直接关 core 或托管到安全位置、定期清理。
3. 调试符号泄露 —— 生产二进制 strip：无符号包攻击者逆向成本高一个量级；
   但崩溃排查也难，折中 = 符号归档到内部服务器，按需 debuginfod。
4. core_pattern 管道执行 —— 以 | 开头的 core_pattern 会把 core 数据
   喂给指定程序执行（root 上下文）。非 root 不可写该文件（需 CAP_SYS_ADMIN），
   但配置文件（/etc/sysctl.d）若被篡改等于提权通道，注意文件权限。
5. 容器与 seccomp —— Docker 默认 seccomp profile 允许容器内 ptrace 自身进程；
   宿主机 attach 容器进程需要：宿主机 root + 容器 --cap-add=SYS_PTRACE，
   否则 gdb -p 报权限错误。kubernetes 默认禁止 SYS_PTRACE，
   调试容器需显式加 capability（securityContext）。
6. 调试会话审计 —— 生产 attach 操作留痕（who/时间/目的），
   避免调试行为本身成为安全事故（有人 attach 后 dump 了业务数据）。
```

## 故障排查

### 案例一：程序崩溃了但找不到 core 文件

```shell
# 症状：Segmentation fault 出现，但当前目录/指定目录都没有 core
# 排查 1：core 开关是否为 0
ulimit -c                          # 0 = 未启用（本机实测默认 0）
# 排查 2：core 被谁接管了
cat /proc/sys/kernel/core_pattern  # | 开头 = 管道交给 apport/systemd-coredump
#   本机实测：|/usr/share/apport/apport ... → core 落在 /var/crash/*.crash
#   排查 3：管道模式是否超限被丢弃
cat /proc/sys/kernel/core_pipe_limit   # 本机实测 10，超出并发数会被丢
# 解决：ulimit -c unlimited；想落盘就改 core_pattern 为普通路径
```

### 案例二：gdb bt 只有地址，没有函数名和源码行

```shell
# 症状：(gdb) bt 输出全是 0x7f... 地址，无符号
# 排查：二进制是否 stripped
file ./myapp                       # 输出含 "stripped" = 没符号
nm ./myapp | head -3               # 无输出 = 无 .symtab（本机实测 ls 即如此）
# 解决：a) 自研程序：重新编译加 -g，或从发布流水线找回带符号版本
#      b) 发行版程序：装调试符号
#         Ubuntu:  apt install <包>-dbgsym（需启用 ddebs 源）
#         Red Hat: dnf debuginfo-install <包>     ← Red Hat 系差异
#      c) 应急：gdb 自动 debuginfod 下载（本机默认指向 debuginfod.ubuntu.com）
```

### 案例三：gdb -p 报 Operation not permitted / ptrace 权限不足

```shell
# 症状：非 root attach 别人的进程
gdb -p 1234
# ptrace: Operation not permitted.
# 排查：
id                                   # 是否同用户
cat /proc/sys/kernel/yama/ptrace_scope   # 1 = 仅父进程可 attach 子进程
# 解决：a) 同用户同进程树（父进程 attach 子进程）不受限
#      b) root/sudo 执行（root 不受 YAMA 限制）
#      c) 确有需求才调低 ptrace_scope（写 /etc/sysctl.d/99-ptrace.conf
#         kernel.yama.ptrace_scope=0，重启生效）——有安全代价，慎用
```

### 案例四：attach 容器内进程拿不到栈 / 报错

```shell
# 症状：宿主机 gdb -p <容器内PID> 报权限错误，或栈全是 ???
# 排查：
#   容器内 PID 与宿主机 PID 不同（PID namespace 隔离），
#   容器内看到的 PID 在宿主机上不是同一个号
# 解决：
#   a) 在容器内执行 gdb（同 PID 空间），或 docker exec -it <容器> gdb -p <PID>
#   b) 宿主机 attach：用宿主机视角的 PID（ps aux 里看到的），
#      且容器需 --cap-add=SYS_PTRACE，进程需 --privileged 或同 uid
#   c) 栈全是 ??：容器内缺符号/debuginfod，或二进制在容器层被 strip，
#      按案例二装符号
```

## 常见问题

```text
Q1: gdb 里 next 和 step 有什么区别？
A: next（n）单步执行但不进入函数（把整个函数调用当一步）；step（s）会进入
   函数内部逐条执行。想跳过库函数用 next，想跟进自己写的函数用 step；
   配合 finish 可以「跟进去看两眼再跳出来」。

Q2: core 文件为什么有时找不到？
A: 三个原因：① ulimit -c 为 0（没启用，本机实测默认 0）；② core_pattern
   是管道模式，core 被 apport/systemd-coredump 接管，落在 /var/crash 或
   journal 里而不是当前目录；③ core_pipe_limit 并发超限被丢弃。
   依次查 ulimit -c → cat /proc/sys/kernel/core_pattern → core_pipe_limit。

Q3: pstack 命令不存在怎么办？
A: pstack 是 Red Hat 系工具，Ubuntu 无官方包。pstack 本质就是 gdb 的 bt，
   用 gdb -p <PID> -batch -ex 'thread apply all bt' 完全替代；
   RHEL 系还可装 elfutils 用 eu-stack -p <PID>。

Q4: 编译加 -g 会影响程序性能吗？
A: 基本不影响。 -g 只添加 DWARF 调试信息段，不改代码生成和优化，
   运行时速度/内存几乎无差别，只是文件变大。建议 -g -O2 一起用：
   生产可 strip 发布、保留带符号副本用于线上崩溃分析。

Q5: 怎么用 gdb 观察一个变量什么时候被改？
A: watch 变量（硬件断点，用 CPU 调试寄存器，最多 4 个）：
   (gdb) watch myvar        # 写入即停
   (gdb) watch -l myvar     # 按地址观察，避免同名变量混淆
   (gdb) rwatch myvar       # 只读时停
   (gdb) awatch myvar       # 读写都停
   注意 watch 依赖硬件断点资源，多线程下默认只观察当前线程。

Q6: valgrind 跑程序慢得离谱，正常吗？
A: 正常。valgrind 是动态二进制插桩 + JIT 翻译，程序慢 10~50 倍、
   内存翻倍，只适合测试环境复现。生产环境的内存问题用 ASAN（重编译，
   慢 2~3 倍）或监控 RSS + jmap -histo（Java）定位。

Q7: 生产环境能 gdb -p 吗？有什么注意？
A: 能，但注意：attach 会 SIGSTOP 暂停进程（服务短暂无响应），
   优先用 -batch 一条命令拿栈立刻退出；避开业务高峰；attach 前确认
   ptrace_scope（root 或同用户）；容器进程要 SYS_PTRACE 权限；
   操作留痕。拿线程栈用 jstack（Java，安全点快照，基本无感）更优。

Q8: 内核 oops 和用户态 segfault 有什么区别？
A: oops 是内核态崩溃（驱动/内核代码 bug），dmesg 记录 RIP/调用栈，
   进程不退出（内核继续运行但状态可能已损坏）；segfault 是用户态进程
   收到 SIGSEGV，只杀进程本身。oops 默认不会 panic（panic_on_oops=0），
   但生产核心服务建议 panic_on_oops=1 + kdump 留证，避免带病运行。
```

## 面试题

```text
1. gdb 的断点是怎么实现的？
   答：软件断点在目标地址写入 int3（0xCC）软中断指令，执行到该处 CPU 触发
   #BP 异常，内核把信号转给调试器，gdb 恢复原指令后停下等待命令；
   watch 变量用 CPU 调试寄存器（DR0~DR3）实现硬件断点，不修改指令；
   单步靠设置 EFLAGS 的 TF 陷阱标志位。底层都是 ptrace 系统调用。

2. coredump 是怎么产生的？完整分析流程是什么？
   答：进程收到致命信号（SIGSEGV/SIGABRT/SIGBUS/SIGILL）时内核执行
   do_coredump：检查 RLIMIT_CORE → 按 core_pattern 写文件或管道转交 →
   按 coredump_filter 收集内存段 → 生成 ELF core → 进程退出。
   分析流程：ulimit -c unlimited 复现 → 找到 core（注意管道模式落点）→
   gdb 程序 core → bt 看调用栈 → frame 定位崩溃帧 → 结合源码修 bug。

3. 段错误怎么定位到具体代码行？
   答：① 开 coredump（ulimit -c unlimited）复现，gdb 程序 core → bt；
   ② 无 core 时用 dmesg 的 segfault 行里 ip 地址 + addr2line -e 程序 -f 地址
   转函数和行号（需要符号）；③ 都没符号就 objdump 反汇编崩溃地址附近。
   最稳的是编译 -g 保留符号。

4. 程序卡死（不是崩溃）怎么排查？
   答：先确认状态：CPU 高 = 死循环（top -H -p 找线程，perf/jstack 定位函数）；
   CPU 低 = 死锁或等资源（pstack/gdb thread apply all bt 看线程栈，
   找 pthread_mutex_lock/futex 互相等待，jstack 找 BLOCKED/WAITING 链）；
   网络等外部资源用 strace -f -p 看卡在哪个 syscall（read/futex/connect）。

5. strace 的工作原理和开销？
   答：基于 ptrace，在每次系统调用进入/退出点截获（PTRACE_SYSCALL），
   记录调用号、参数、返回值、errno。每次 syscall 两次陷入内核 + 两次
   ptrace 通知，程序慢 10~100 倍。所以生产只短时取证，长时监控用
   eBPF（[[16.6-综合调优工具]]）或只跟踪特定 syscall（-e trace=）。

6. valgrind 和 ASAN 有什么区别？怎么选？
   答：valgrind 是运行时动态二进制插桩，不改编译，慢 10~50 倍，擅长
   泄漏检测；ASAN 是编译期插桩（shadow memory），要重新编译，慢 2~3 倍，
   能抓 use-after-free、栈/堆越界，CI 首选。选型：现有二进制/黑盒 → valgrind；
   有源码/CI → ASAN；两个都要 → 先 ASAN 后 valgrind 查泄漏。

7. 内核 oops 和 panic 是什么关系？kdump 怎么工作？
   答：oops 是内核态异常（能记录日志继续跑，但可能已损坏）；panic 是致命
   内核错误（停机）。panic_on_oops=1 时 oops 也触发 panic。kdump 用 kexec
   预留内存加载捕获内核，主内核 panic 时跳转捕获内核，把内存写成 vmcore，
   事后用 crash 工具分析 bt/log——是内核崩溃唯一的「事故现场」。

8. 生产环境线上崩溃，你怎么在「不影响业务」的前提下取证？
   答：按影响从小到大：① 日志/dmesg（无侵入）→ ② jstack 线程 dump
   （Java 安全点快照）→ ③ gdb -batch 一条命令抓全线程栈立即退出
   （秒级暂停）→ ④ strace -f -p 短时取证（慢但信息全）→ ⑤ gcore 打 core
   再离线分析（暂停最短）→ ⑥ 影响最大的是长时间 attach/valgrind，
   尽量在低峰或灰度实例做。同时确认 ulimit -c/core_pattern 让崩溃有 core 留存。
```

## 最佳实践与踩坑记录

### 最佳实践

1. **崩溃类问题先开 core 再复现**：`ulimit -c unlimited` + 确认 core_pattern 落点，别靠猜——core 是唯一的「事故现场」。
2. **编译永远带 -g**：调试信息不拖性能，`-g -O2` 兼容；发布 strip，符号归档到符号服务器按 build-id 找回。
3. **卡死先分「CPU 高还是低」**：高 = 死循环（perf/jstack 找热点函数），低 = 死锁/等资源（全线程栈 + strace 看 syscall），方向错了白查半天。
4. **生产取证用 -batch 一条命令**：`gdb -p <PID> -batch -ex 'thread apply all bt'` 秒级完成，别开交互会话挂着暂停业务。
5. **地址转行号用 addr2line**：dmesg/日志里的崩溃地址（ip 字段）直接 `addr2line -e 程序 -f 地址`，没有 core 也能定位。
6. **内存问题分两步**：CI 用 ASAN（快、抓越界），测试环境 valgrind（泄漏详情），生产用 RSS 监控 + 堆 dump 取证。
7. **发行版二进制没符号先装符号包**：Ubuntu dbgsym、RHEL `debuginfo-install`，或靠 debuginfod 自动下载，比反汇编快一个量级。
8. **Java 卡死用 jstack 而非 gdb**：jstack 是安全点快照基本无感，gdb attach JVM 反而可能加剧卡顿。
9. **core 文件当敏感资产管**：里面是内存全快照，权限 600、目录受限、定期清理、核心系统关 core。
10. **内核态问题走 kdump 流程**：panic_on_oops + crashkernel 预留 + 事后 crash 工具分析，别只靠 dmesg 碎片。

### 踩坑记录

```text
坑 1：编译没加 -g，gdb 看不到源码和变量
结论：gdb bt 只有地址，print 变量报 No symbol，定位无从下手。
原因：编译没加 -g（无 DWARF 调试信息），或发布件被 strip 过。
解法：编译加 -g；发布保留带符号版本；发行版程序装 dbgsym/debuginfo 包。

坑 2：ulimit -c 没设，程序崩溃没 core 文件
结论：程序段错误崩溃了，但目录里找不到 core。
原因：默认 ulimit -c=0（本机实测默认 0），内核直接丢弃 core。
解法：ulimit -c unlimited 启用；服务进程在 systemd unit 里
     LimitCORE=infinity 持久化。

坑 3：core 文件找不到，被 core_pattern 转走了
结论：设了 ulimit -c unlimited，当前目录还是没有 core。
原因：core_pattern 是管道模式（本机实测转给 apport），core 不落盘。
解法：cat /proc/sys/kernel/core_pattern 看去向——apport 落 /var/crash，
     systemd-coredump 落 journal/var/lib/systemd/coredump；
     需要文件形式就改成 /tmp/core.%e.%p 等普通路径。

坑 4：生产程序频繁崩溃，core 文件塞满磁盘
结论：core 巨大（内存快照），频繁崩溃把磁盘占满引发次生故障。
原因：core 是完整内存映像，大程序 core 数 GB；未限大小、未清理。
解法：coredump_filter 只留匿名段（0x31）；ulimit -c 限大小；
     崩溃收集自动化（保留最近 N 个 + 上传分析后删除）。

坑 5：用 gdb 附加生产进程，服务卡顿/连接中断
结论：gdb -p 之后业务连接大量超时。
原因：attach 会 SIGSTOP 暂停整个进程，期间所有线程冻结。
解法：用 -batch 一条命令拿栈立刻退出；低峰操作；
     纯看栈用 gcore 打文件离线看；Java 用 jstack。

坑 6：attach 别人的进程报 Operation not permitted
结论：gdb -p <PID> 报 ptrace: Operation not permitted。
原因：YAMA ptrace_scope=1（默认），只允许父进程 attach 子进程；
     非 root 用户 attach 无关进程被拒。
解法：sudo 执行；确认同用户；确需放开才调低 ptrace_scope（有安全代价）。

坑 7：容器里进程崩了，宿主机找不到 core 也 attach 不上
结论：容器内 PID 和宿主机 PID 对不上，core 目录也找不到。
原因：PID namespace 隔离；容器缺 SYS_PTRACE 权限；core_pattern 落点
     在容器外视角不同。
解法：docker exec 进容器内调试（同 PID 空间）；宿主机 attach 用
     宿主视角 PID + --cap-add=SYS_PTRACE；core 落点看宿主机 core_pattern。

坑 8：dmesg 里 segfault 的 ip 地址，addr2line 转不出行号
结论：addr2line -e myapp 0x... 输出 ??:0。
原因：地址是共享库（libc 等）内的偏移，或二进制没符号/stripped。
解法：ip 后面 in <库>[基址+偏移] 指明库，用对应库文件转；
     无符号就装 debuginfo；崩溃地址要先减去库基址再转。

坑 9：valgrind 在 CI 里跑挂了/超时
结论：valgrind 跑测试套件超时甚至 OOM。
原因：插桩后慢 10~50 倍、内存翻倍，CI 资源预算没算上。
解法：CI 用 ASAN（快）替代 valgrind 做越界检测；
     valgrind 只跑指定用例并加大 timeout/内存。

坑 10：gdb 分析 core 时一直卡在 debuginfod 下载
结论：gdb 打开 core 后长时间无响应/网络超时。
原因：gdb 默认尝试从符号服务器下载符号，内网/慢速环境卡住。
解法：~/.gdbinit 加 set debuginfod enabled off；
     或先装好对应 dbgsym/debuginfo 包再分析。
```
