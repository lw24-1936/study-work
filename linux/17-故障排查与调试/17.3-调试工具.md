## 概述

调试工具用于「程序崩溃/卡死/行为异常」的深度分析：gdb（交互式调试器，断点/单步/看变量）、pstack（打印线程栈）、addr2line（地址转源码行）、coredump 分析（程序崩溃时留下内存快照，事后分析崩溃点）。核心场景：程序段错误（segfault）崩溃，靠 coredump + gdb 定位崩溃在哪一行。

```text
# 实测（本机调试工具）
$ for t in gdb addr2line pstack; do command -v $t >/dev/null && echo "$t: 有" || echo "$t: 无"; done
gdb: 有
addr2line: 有
pstack: 无
# gdb/addr2line 已装，pstack 需单独装（可用 gdb 的 thread apply all bt 替代）
```

```text
调试工具四件套：
1. gdb —— 交互式调试（断点/单步/看变量/看栈）
2. pstack —— 打印进程的线程栈（看卡在哪）
3. addr2line —— 地址转源码行（配合崩溃地址）
4. coredump —— 崩溃时的内存快照，事后分析
```

## gdb 调试

gdb 是 Linux 的标准调试器：设断点、单步执行、查看变量、查看调用栈。核心用法：`gdb 程序`（启动调试）、`gdb -p PID`（附加到运行中进程）、`gdb 程序 core文件`（分析 coredump）。关键命令：break（断点）、run（运行）、next/step（单步）、print（看变量）、backtrace/bt（看调用栈）、thread apply all bt（看所有线程栈）。

```shell
gdb ./myapp                # 启动调试
gdb -p <PID>               # 附加到运行中进程
gdb ./myapp core           # 分析 coredump
```

```text
gdb 常用命令：
break 函数/行   设断点
run            运行
next / step    单步（next 不进入函数，step 进入）
print 变量     查看变量
backtrace (bt) 查看调用栈
thread apply all bt  查看所有线程栈
quit           退出
```

## pstack 与 addr2line

pstack 打印进程的所有线程栈——「卡住的进程」用 pstack 看它卡在哪个函数（不用 gdb 也能快速看栈）。addr2line 把「崩溃地址」转成「源码文件:行号」——配合崩溃日志里的地址（如 `./myapp[0x401234]`）定位崩溃点。两者都是「快速定位」的轻量工具，比完整的 gdb 调试更快捷。

```shell
# pstack 看进程线程栈（卡在哪）
pstack <PID>
# 或用 gdb 替代（pstack 本质是 gdb 的 bt）
gdb -p <PID> -batch -ex 'thread apply all bt'

# addr2line 地址转源码行
addr2line -e ./myapp 0x401234
# 输出：/path/to/source.c:42 （崩溃在 source.c 第 42 行）
```

```text
pstack vs addr2line：
1. pstack —— 打印线程栈，看「卡在哪个函数」
2. addr2line —— 地址转源码行，看「崩溃在哪一行」
3. 都是轻量定位工具，比完整 gdb 快
```

## coredump 分析

coredump 是「程序崩溃时的内存快照」——程序段错误（segfault）等致命信号触发，内核把进程内存、寄存器、调用栈写到 core 文件，事后用 gdb 分析崩溃点。启用 coredump：`ulimit -c unlimited`（允许生成 core），core 文件路径由 /proc/sys/kernel/core_pattern 决定。分析：`gdb 程序 core` → bt 看崩溃时的调用栈。

```text
# 实测（本机 core_pattern，Ubuntu 用 apport 处理崩溃）
$ cat /proc/sys/kernel/core_pattern
|/usr/share/apport/apport -p%p -s%s ...
# Ubuntu 的 core 转给 apport 崩溃报告器，不是直接写 core 文件
```

```shell
ulimit -c unlimited          # 允许生成 core 文件
cat /proc/sys/kernel/core_pattern   # 看 core 文件路径
# 程序崩溃后
gdb ./myapp core             # 分析 core
(gdb) bt                     # 看崩溃时的调用栈
(gdb) info registers         # 看寄存器
(gdb) frame 0                # 看崩溃的栈帧
```

```text
coredump 分析流程：
1. 启用 —— ulimit -c unlimited
2. 复现 —— 程序崩溃生成 core 文件
3. 分析 —— gdb 程序 core，bt 看崩溃点
4. 定位 —— 崩溃的函数 + 参数，找 bug
```

## 应用场景实战

### 场景一：程序段错误崩溃，用 coredump 定位

```shell
# 1. 启用 coredump
ulimit -c unlimited
# 2. 复现崩溃（程序生成 core 文件）
./myapp
# 3. 分析 core
gdb ./myapp core
(gdb) bt                     # 看崩溃时的调用栈
(gdb) frame 0                # 定位崩溃的函数
# 4. 结合源码找 bug
```

### 场景二：程序卡死，pstack 看卡在哪

```shell
# 1. 找卡死的进程
ps aux | grep myapp
# 2. 打印线程栈
pstack <PID>
# 或
gdb -p <PID> -batch -ex 'thread apply all bt'
# 看所有线程栈，定位卡在哪个函数（死锁/死循环/等待）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 程序崩溃先启用 coredump（ulimit -c unlimited）+ gdb 分析，别靠猜
2. 编译时加 -g（调试符号），否则 gdb 看不到源码行和变量名
3. 卡死的进程用 pstack（或 gdb bt）看线程栈，定位死锁/死循环
4. 崩溃日志里的地址用 addr2line 转源码行，快速定位
5. 生产环境的 core 文件很大，别无限生成（配 core 大小限制）

### 踩坑记录

```text
坑 1：编译没加 -g，gdb 看不到源码和变量
结论：gdb bt 只有地址没有函数名/源码行。
原因：编译没加 -g（调试符号），二进制被 strip 了。
解法：编译加 -g，或保留带符号的版本用于调试。

坑 2：ulimit -c 没设，程序崩溃没 core 文件
结论：程序段错误崩溃了，但找不到 core 文件。
原因：默认 ulimit -c=0，不生成 core。
解法：ulimit -c unlimited 启用 core 生成。

坑 3：core 文件找不到，被 core_pattern 转走了
结论：设了 ulimit -c unlimited，但目录里没 core 文件。
原因：core_pattern 把 core 转给别的程序（如 apport），不是写当前目录。
解法：cat /proc/sys/kernel/core_pattern 看 core 去哪了。

坑 4：生产程序一直崩，core 文件塞满磁盘
结论：core 文件巨大，频繁崩溃把磁盘占满。
原因：core 是完整内存快照，大程序 core 几 GB。
解法：配 core 大小限制（ulimit -c 限制 KB），或 crash 后及时清理。

坑 5：用 gdb 附加生产进程，服务卡顿
结论：gdb -p 生产进程，服务短暂卡住。
原因：gdb attach 会暂停进程（SIGSTOP）。
解法：生产环境谨慎 attach，用 -batch 快速拿栈就退出。
```
