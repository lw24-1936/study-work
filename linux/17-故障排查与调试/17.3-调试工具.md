## 概述

调试工具用于「程序崩溃/卡死/行为异常」的深度分析：gdb（交互式调试器，断点/单步/看变量）、pstack（打印线程栈）、addr2line（地址转源码行）、coredump 分析（程序崩溃时留下内存快照，事后分析崩溃点）。核心场景：程序段错误（segfault）崩溃，靠 coredump + gdb 定位崩溃在哪一行。

```text
# 实测（本机调试工具）
$ for t in gdb addr2line pstack; do command -v $t >/dev/null && echo "$t: 有" || echo "$t: 无"; done
gdb: 有
addr2line: 有
pstack: 无
# gdb/addr2line 已装，pstack 需单独装（可用 gdb 的 thread apply all bt 替代）
```

```text
调试工具四件套：
1. gdb —— 交互式调试（断点/单步/看变量/看栈）
2. pstack —— 打印进程的线程栈（看卡在哪）
3. addr2line —— 地址转源码行（配合崩溃地址）
4. coredump —— 崩溃时的内存快照，事后分析
```

## 核心概念

1. **gdb**：Linux 的标准调试器，设断点、单步执行、查看变量、查看调用栈。核心用法：`gdb 程序`（启动调试）、`gdb -p PID`（附加运行中进程）、`gdb 程序 core文件`（分析 coredump）。
2. **pstack**：打印进程所有线程栈，看「卡住的进程」卡在哪个函数（不用完整 gdb 也能快速看栈）。
3. **addr2line**：把「崩溃地址」转成「源码文件:行号」，配合崩溃日志里的地址定位崩溃点。
4. **coredump**：程序崩溃时内核把内存、寄存器、调用栈写到 core 文件，事后用 gdb 分析崩溃点。

```text
核心概念：
gdb 交互调试 + pstack 看线程栈 + addr2line 地址转行号 + coredump 事后分析崩溃点
```

## 工作原理

1. **gdb 调试原理**：同样基于 ptrace 附加目标进程。断点的实现是「在目标地址写入 int3（0xCC）软中断指令」——程序执行到断点触发中断，内核暂停进程并通知 gdb，gdb 读寄存器/内存、等用户下指令（单步/继续/看变量）。
2. **coredump 生成原理**：程序收到致命信号（SIGSEGV 段错误、SIGABRT 等）时，内核把进程的地址空间（内存）、寄存器、调用栈、打开的文件描述符等信息写入 core 文件，之后进程退出。core 文件路径由 `/proc/sys/kernel/core_pattern` 决定。
3. **addr2line 原理**：读取二进制里的调试信息（DWARF），把「虚拟地址」映射到「源文件 + 行号」。

```text
gdb 断点：目标地址写 int3 软中断 → 执行到断点触发中断 → 内核暂停通知 gdb → gdb 读状态等指令
coredump：致命信号触发 → 内核写内存/寄存器/栈到 core 文件 → 事后 gdb 程序 core 分析
```

## 常用命令与配置

```shell
gdb ./myapp                # 启动调试
gdb -p <PID>               # 附加到运行中进程
gdb ./myapp core           # 分析 coredump
```

```text
gdb 常用命令：
break 函数/行   设断点
run            运行
next / step    单步（next 不进入函数，step 进入）
print 变量     查看变量
backtrace (bt) 查看调用栈
thread apply all bt  查看所有线程栈
quit           退出
```

```shell
# pstack 看进程线程栈（卡在哪）
pstack <PID>
# 或用 gdb 替代（pstack 本质是 gdb 的 bt）
gdb -p <PID> -batch -ex 'thread apply all bt'

# addr2line 地址转源码行
addr2line -e ./myapp 0x401234
# 输出：/path/to/source.c:42 （崩溃在 source.c 第 42 行）
```

## 配置文件解析

```shell
ulimit -c unlimited          # 允许生成 core 文件
cat /proc/sys/kernel/core_pattern   # 看 core 文件路径（决定 core 写哪/转给谁）
```

```text
core_pattern 字段解析：
|/usr/share/apport/apport -p%p -s%s ...
│                              │   └── %s 信号号
│                              └── %p 进程 PID
└── 以 | 开头 = 把 core 通过管道转给 apport 处理，不是直接写 core 文件

常见格式：
core             —— 当前目录生成名为 core 的文件
/tmp/core.%e.%p  —— 指定目录 + 可执行文件名(%e) + PID(%p)
```

```text
gdb 初始化文件（~/.gdbinit）：
set pagination off        # 关闭分页（脚本化调试别卡在 more）
set print pretty on       # 结构体/数组美化打印
```

## 应用场景实战

### 场景一：程序段错误崩溃，用 coredump 定位

```shell
# 1. 启用 coredump
ulimit -c unlimited
# 2. 复现崩溃（程序生成 core 文件）
./myapp
# 3. 分析 core
gdb ./myapp core
(gdb) bt                     # 看崩溃时的调用栈
(gdb) frame 0                # 定位崩溃的函数
# 4. 结合源码找 bug
```

### 场景二：程序卡死，pstack 看卡在哪

```shell
# 1. 找卡死的进程
ps aux | grep myapp
# 2. 打印线程栈
pstack <PID>
# 或
gdb -p <PID> -batch -ex 'thread apply all bt'
# 看所有线程栈，定位卡在哪个函数（死锁/死循环/等待）
```

## 性能与调优

```text
1. core 文件大小 —— core 是完整内存快照，大程序 core 几 GB，配 ulimit -c 限制大小或及时清理
2. gdb attach 开销 —— gdb -p 会 SIGSTOP 暂停进程，生产环境用 -batch 快速拿栈就退出
3. 调试符号 —— 编译加 -g 才有符号，生产二进制 strip 后 gdb 只有地址；保留带符号版本
4. coredump 过滤 —— /proc/<PID>/coredump_filter 控制 core 里包含哪些内存段（省空间）
```

## 安全与权限

```text
1. ptrace 权限 —— gdb -p 附加需要 ptrace 权限（root 或同用户），受 YAMA 限制
2. core 文件含敏感数据 —— core 里有内存（密码/密钥/token），core 文件权限和清理要管好
3. 调试符号泄露 —— 生产二进制别带符号（strip），否则攻击者逆向更容易
4. core_pattern 可被利用 —— 以 | 开头的 core_pattern 会执行命令，别让非 root 改它
```

## 故障排查

```shell
# 1. 程序崩溃但找不到 core 文件
ulimit -c                          # 是否为 0（0 = 不生成 core）
cat /proc/sys/kernel/core_pattern  # core 是否被转走（apport 等）

# 2. gdb bt 只有地址没有函数名/源码行
file ./myapp                       # 是否 stripped（无符号）
# 解决：编译加 -g，保留带符号版本

# 3. gdb -p 报 ptrace 权限不足
cat /proc/sys/kernel/yama/ptrace_scope
# 解决：root 执行，或调低 ptrace_scope
```

## 常见问题

```text
Q1: gdb 里 next 和 step 有什么区别？
A: next 单步执行但不进入函数（把函数调用当一步），step 会进入函数内部单步。想跳过函数用 next，想跟进去用 step。

Q2: core 文件为什么有时找不到？
A: 三个原因：ulimit -c 为 0（没启用）、core_pattern 把 core 转给别的程序（如 apport）、core 写到了别的地方。cat core_pattern 看它去哪了。

Q3: pstack 命令不存在怎么办？
A: pstack 本质是 gdb 的 bt，用 gdb -p <PID> -batch -ex 'thread apply all bt' 替代。

Q4: 编译加 -g 会影响程序性能吗？
A: -g 只加调试信息（DWARF 段），不改代码优化，运行时性能基本无影响，只是二进制变大。生产可 strip 后保留带符号副本。
```

## 面试题

```text
1. gdb 的断点是怎么实现的？
   答：在目标地址写入 int3（0xCC）软中断指令，程序执行到断点触发中断，内核暂停进程通知 gdb，gdb 读状态后等用户指令。

2. coredump 是怎么产生的？分析流程是什么？
   答：程序收到致命信号（SIGSEGV/SIGABRT），内核把内存/寄存器/调用栈写到 core 文件。分析：gdb 程序 core → bt 看调用栈 → frame 定位崩溃点。

3. 段错误（segfault）怎么定位到具体代码行？
   答：启用 coredump → 复现崩溃 → gdb 程序 core → bt 看崩溃栈 → 结合 addr2line 或源码定位到行。

4. 程序卡死（不是崩溃）怎么排查？
   答：pstack <PID>（或 gdb -p -batch -ex 'thread apply all bt'）打印所有线程栈，看卡在哪个函数——死锁/死循环/等待锁。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 程序崩溃先启用 coredump（ulimit -c unlimited）+ gdb 分析，别靠猜
2. 编译时加 -g（调试符号），否则 gdb 看不到源码行和变量名
3. 卡死的进程用 pstack（或 gdb bt）看线程栈，定位死锁/死循环
4. 崩溃日志里的地址用 addr2line 转源码行，快速定位
5. 生产环境的 core 文件很大，别无限生成（配 core 大小限制）

### 踩坑记录

```text
坑 1：编译没加 -g，gdb 看不到源码和变量
结论：gdb bt 只有地址没有函数名/源码行。
原因：编译没加 -g（调试符号），二进制被 strip 了。
解法：编译加 -g，或保留带符号的版本用于调试。

坑 2：ulimit -c 没设，程序崩溃没 core 文件
结论：程序段错误崩溃了，但找不到 core 文件。
原因：默认 ulimit -c=0，不生成 core。
解法：ulimit -c unlimited 启用 core 生成。

坑 3：core 文件找不到，被 core_pattern 转走了
结论：设了 ulimit -c unlimited，但目录里没 core 文件。
原因：core_pattern 把 core 转给别的程序（如 apport），不是写当前目录。
解法：cat /proc/sys/kernel/core_pattern 看 core 去哪了。

坑 4：生产程序一直崩，core 文件塞满磁盘
结论：core 文件巨大，频繁崩溃把磁盘占满。
原因：core 是完整内存快照，大程序 core 几 GB。
解法：配 core 大小限制（ulimit -c 限制 KB），或 crash 后及时清理。

坑 5：用 gdb 附加生产进程，服务卡顿
结论：gdb -p 生产进程，服务短暂卡住。
原因：gdb attach 会暂停进程（SIGSTOP）。
解法：生产环境谨慎 attach，用 -batch 快速拿栈就退出。
```
