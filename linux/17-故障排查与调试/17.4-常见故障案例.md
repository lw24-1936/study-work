## 概述

六个最常见的 Linux 故障：磁盘满（df 100%）、OOM（内存耗尽杀进程）、CPU 飙高（进程吃满 CPU）、网络异常（连不上/丢包）、无法登录（SSH/认证问题）、文件句柄耗尽（fd 用满）。每个故障都有「症状 → 排查命令 → 解决」的标准路径，掌握这些案例，能快速处理日常 90% 的故障。

```text
六大常见故障：
1. 磁盘满 —— df 100%，写不进文件
2. OOM —— 内存耗尽，进程被 OOM Killer 杀
3. CPU 飙高 —— 进程吃满 CPU，系统变慢
4. 网络异常 —— 连不上/丢包/端口不通
5. 无法登录 —— SSH/认证失败
6. 文件句柄耗尽 —— fd 用满，打不开文件
```

## 应用场景实战

以下六个案例按「症状 → 排查 → 解决」的标准路径逐一展开。

### 磁盘满

磁盘满的症状：写文件报 No space left、服务报错写不进日志。排查：`df -h` 看哪个分区满 → `du -sh` 逐层找大目录 → 定位大文件。特殊：df 显示没满但报 no space（inode 用满，df -i 看）。解决：删大文件/日志、清理缓存、配 logrotate。注意「删了文件但 df 不降」= 文件被进程占用（lsof 找 deleted 文件）。

```shell
df -h                          # 哪个分区满
du -sh /var/* | sort -rh | head   # 哪个目录占空间
df -i                          # inode 是否用满（大量小文件）
lsof +L1                       # 被删除但还占空间的文件
```

```text
磁盘满排查：
1. df -h 看分区 → 2. du 找大目录 → 3. 定位大文件
特殊：df 没满但报错 = inode 满（df -i）；删了文件不降 = 进程占用（lsof +L1）
```

### OOM

OOM（内存耗尽）的症状：进程莫名被杀、dmesg 有 Out of memory 记录。原因：内存不够 + swap 也满，内核触发 OOM Killer 杀进程（按 oom_score）。排查：`dmesg | grep -i oom` 找记录、`free -h` 看内存、`ps --sort=-%mem` 找大户。解决：加内存、找泄漏、保护关键进程（oom_score_adj）。

```shell
dmesg | grep -i 'out of memory'   # OOM 记录
free -h                          # 内存状态
ps aux --sort=-%mem | head        # 内存大户
cat /proc/<PID>/oom_score         # OOM 分数
```

```text
OOM 排查：
1. dmesg 确认 OOM → 2. free 看内存 → 3. ps 找大户 → 4. 解决（加内存/限内存/保护关键进程）
```

### CPU 飙高

CPU 飙高的症状：系统变慢、某个进程 %CPU 100%。排查：`top` 找进程 → `mpstat -P ALL` 看是否单核 → `perf top`/`pidstat` 定位到函数/线程。原因：死循环、计算密集、无限递归。解决：找到进程后 kill 或修代码（死循环/递归）。

```shell
top                             # 找吃 CPU 的进程
mpstat -P ALL 1                 # 单核还是多核
top -H -p <PID>                 # 看进程的线程（哪个线程飙）
perf top -p <PID>               # 定位到函数
```

```text
CPU 飙高排查：
1. top 找进程 → 2. mpstat 看核 → 3. top -H 找线程 → 4. perf 定位函数
原因：死循环/递归/计算密集 → 解决：kill 或修代码
```

### 网络异常

网络异常的症状：服务连不上、丢包、延迟高。排查（分层）：`ip addr`（IP 配了没）→ `ping`（通不通）→ `ss -tlnp`（端口监听没）→ `nc -zv`（端口通不通）→ `tcpdump`（抓包看流量）。原因：IP 配置错、防火墙挡、服务没起、DNS 问题。解决：逐层定位后修复。

```shell
ip addr && ip route            # IP 和路由
ping -c 3 <目标>              # 连通性
ss -tlnp                      # 端口监听
nc -zv <IP> <端口>            # 端口测试
tcpdump -i any port <端口>    # 抓包
```

```text
网络异常分层排查：
IP 配置 → 连通性 → 端口 → 抓包，逐层定位
```

### 无法登录

无法登录的症状：SSH 连不上、密码错误、密钥失效。排查：`ss -tlnp | grep 22`（sshd 在不在）→ `tail /var/log/auth.log`（认证日志）→ 检查 sshd_config（是否禁了密码/root）。原因：sshd 没起、防火墙挡 22、密码/密钥错、配置改错（如先关密码又没配密钥）。解决：看 auth.log 定位，必要时控制台/救援模式恢复。

```shell
ss -tlnp | grep :22            # sshd 在不在
tail -f /var/log/auth.log      # 认证日志
grep 'Failed password' /var/log/auth.log | tail   # 失败登录
systemctl status sshd          # sshd 状态
```

```text
无法登录排查：
1. sshd 在不在（ss）→ 2. 认证日志（auth.log）→ 3. 配置检查（sshd_config）
常见坑：改 sshd_config 后把自己锁外面（先配密钥再关密码）
```

### 文件句柄耗尽

文件句柄（fd）耗尽的症状：Too many open files 报错、服务打不开文件/连接。原因：进程打开的文件/连接数超过 ulimit -n 限制（默认 1024）。排查：`ulimit -n` 看限制、`lsof -p <PID> | wc -l` 看进程打开数、`lsof | awk` 统计。解决：调高 ulimit（或 limits.conf）、修代码（句柄泄漏）。

```text
# 实测（本机文件句柄相关）
$ ulimit -n
1024                          # 单个进程默认上限 1024
$ cat /proc/sys/fs/file-max
9223372036854775807           # 系统级上限（极大）
$ lsof 2>/dev/null | wc -l
330847                        # 本机当前打开 33 万文件/连接（含 Docker/Chrome）
# 对比：进程级 1024 是瓶颈，系统级上限很大
```

```shell
ulimit -n                      # 进程句柄上限
lsof -p <PID> | wc -l          # 某进程打开多少
lsof 2>/dev/null | awk '{print $1}' | sort | uniq -c | sort -rn | head   # 谁打开最多
ulimit -n 65535                # 临时调高
```

```text
文件句柄耗尽排查：
1. ulimit -n 看限制 → 2. lsof 看谁打开多 → 3. 调高限制或修句柄泄漏
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每个故障都按「症状 → 排查 → 解决」路径走，别跳步骤
2. 磁盘满先 df 定位分区，再 du 定位目录，别乱删
3. OOM 先看 dmesg 确认，再看内存大户
4. 网络异常按分层排查（IP→连通→端口→抓包）
5. 服务进程的 ulimit 提前调高（limits.conf），别等耗尽才处理

### 踩坑记录

```text
坑 1：删了文件但磁盘空间没释放
结论：rm 删了大文件，df 看还是满的。
原因：文件被进程占用（句柄没释放），删除只是删了目录项。
解法：lsof +L1 找 deleted 文件，重启占用进程释放。

坑 2：df 显示没满但报 no space
结论：df -h 空间还有，写文件报 No space left。
原因：inode 用满（大量小文件），df -i 能看出。
解法：df -i 查 inode，删海量小文件。

坑 3：进程莫名被杀，以为是 bug
结论：服务偶尔被 kill，代码查不出问题。
原因：OOM Killer 杀的（内存不够）。
解法：dmesg 查 OOM 记录，找内存大户。

坑 4：改 sshd_config 后 SSH 连不上
结论：改了配置重启 sshd，自己连不上了。
原因：先关了密码认证又没配好密钥，或改了端口没放行。
解法：改前先验证（配好密钥再关密码），改端口先放行防火墙。

坑 5：Too many open files，以为是系统上限
结论：报句柄耗尽，就去调系统 file-max。
原因：瓶颈是进程级 ulimit -n（1024），不是系统级。
解法：调高进程的 ulimit（limits.conf / 服务配置），并查句柄泄漏。
```
