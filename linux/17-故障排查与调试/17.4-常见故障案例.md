## 概述

本篇章是「故障排查方法论」（[[17.1-排查方法论]]）的实战案例库：每个案例按**现象 → 定位过程 → 根因 → 解决与预防**四段式展开，覆盖磁盘、内存、CPU、服务、网络、进程、时间、内核等高频生产故障。核心思想：**90% 的故障是资源耗尽 + 配置错误 + 依赖故障三类**，先对号入座再走命令，别上来就乱翻。

```text
本库十大高频故障（即本文应用场景实战的场景一~十）：
1.  磁盘满          —— df 100% / inode 满 / 删除未释放
2.  内存泄漏与 OOM  —— RSS 上涨 / 进程被 OOM Killer 杀
3.  CPU 100%        —— 单进程吃满 / 死循环 / 高并发
4.  服务无法启动    —— systemd 失败 / 依赖缺失 / 配置错误
5.  网络不通        —— 分层排查（链路/IP/端口/应用）
6.  端口被占用      —— bind 失败 / 服务起不来
7.  进程假死        —— D 状态 / 死锁 / 等外部资源
8.  时区与时间不同步 —— 日志时间错乱 / 认证失败
9.  系统缓慢        —— load 高 / iowait 高 / 内存压力
10. 内核模块加载失败 —— vermagic 不匹配 / 签名拒绝
```

## 核心概念

1. **故障四分类**：**资源型**（磁盘/内存/CPU/句柄耗尽）、**进程型**（崩溃/假死/死锁/启动失败）、**网络型**（不通/丢包/端口冲突）、**系统型**（时间不同步/内核模块/内核 panic）。先归类，再选工具集。
2. **四段式排查法**：现象（先记录准确症状与影响面）→ 定位（用命令逐步缩小范围，每步有输出依据）→ 根因（找到「为什么」）→ 解决与预防（止血 + 根治 + 防复发）。跳过定位直接改配置是故障处理大忌。
3. **证据链**：排查过程 = 收集证据（日志时间线、命令输出、快照）。`journalctl`、`dmesg`、`/var/log` 是权威证据；`history`/操作记录是复盘依据。故障处理完必须能讲出「证据 → 结论」链条，而不是「感觉是某某问题」。
4. **先止血再根治**：线上故障先恢复业务（重启/扩容/降级/限流），拿到证据后再深挖根因。顺序错了（先修代码）会拉长故障时间。
5. **监控是故障的一半**：没有监控，故障只能在发生后被动发现；有了监控（[[13.3-系统监控]]），大部分故障在告警阶段就被处理了。

```text
故障 → 关键命令 → 典型根因（速查）：
磁盘满      df -h / df -i / du / lsof +L1    —— 大文件、日志不轮转、inode 耗尽、删除未释放
OOM        dmesg / free / ps --sort=-%mem    —— 内存泄漏、内存不足、swap 满
CPU 飙高   top / top -H / pidstat / perf     —— 死循环、递归、高并发、GC 风暴
启动失败    systemctl status / journalctl -xe —— 依赖缺失、配置错、端口占用、权限
网络不通    ip / ping / ss / nc / tcpdump     —— 配置错、防火墙、服务没起、DNS
端口占用    ss -tlnp / lsof -i                —— 端口冲突、残留进程、TIME_WAIT 堆积
进程假死    ps stat / strace -p / gdb bt      —— D 状态、死锁、等外部资源
时间异常    timedatectl / chronyc / ntpq      —— NTP 停摆、时区配错、硬件时钟漂移
系统缓慢    uptime / vmstat / mpstat / iostat —— 负载高、IO 慢、内存压力、换页
模块失败    dmesg / modprobe / modinfo        —— vermagic 不匹配、签名、依赖模块缺失
```

## 工作原理

1. **磁盘满原理**：文件系统把「数据块」和「inode（元数据）」分开消耗。大文件耗尽数据块（`df -h` 满）；海量小文件耗尽 inode（`df -i` 满，`df -h` 看着还有空间却写不进）。日志不轮转是磁盘满头号原因；「rm 了空间不释放」是因为文件仍被进程占用（deleted 状态，句柄未关）。
2. **OOM 原理**：内存不足 + swap 也满时，内核触发 OOM Killer，按 `oom_score`（内存占用 + 其他因子）选择进程杀掉释放内存；`oom_score_adj` 可调权重（-1000 免疫）。被杀的进程 dmesg 里有 `Out of memory: Killed process` 记录。内存泄漏的典型曲线：RSS 只涨不跌、重启回落。
3. **CPU 100% 原理**：单进程死循环/无限递归（单核飙）或高并发/多线程（多核飙）。区分「单核飙」和「多核飙」用 `mpstat -P ALL`；区分「哪个线程」用 `top -H -p`；定位到函数用 perf 采样（[[16.6-综合调优工具]]）或 jstack（Java GC 风暴也是 CPU 大户）。
4. **systemd 启动失败原理**：`systemctl start` 后 systemd 按依赖图启动（After/Requires/Wants），失败原因集中在：依赖服务没起、二进制/配置文件不存在、配置语法错误、端口被占用（bind 失败）、权限/SELinux 拒绝。systemd 会把退出码、失败单元写进 journal。
5. **网络不通原理**：数据包路径 = 本机 IP/路由 → 链路 → 对端防火墙 → 对端服务监听 → 应用协议。任何一层断都会表现为「连不上」，必须分层排查：`ip addr`（配置）→ `ping`（链路）→ `ss`（本地监听）→ `nc`（端口）→ `tcpdump`（内容）。
6. **端口占用原理**：端口是 (IP, 协议, 端口) 三元组，同一端口只能被一个监听者持有。服务起不来报 `Address already in use` 时，用 `ss -tlnp` 反查占用者；TIME_WAIT 大量堆积也会让新连接失败（连接复用/`tcp_tw_reuse`）。
7. **进程假死原理**：D 状态 = 不可中断睡眠（等内核 IO，如 NFS/磁盘），kill 不掉，只能等 IO 恢复或重启；死锁 = 多线程互等锁（CPU 低、无响应）；等外部资源 = 连接池/数据库/锁服务耗尽。三种「假死」的 CPU 特征不同，是区分关键。
8. **时间同步原理**：系统时间由内核维护，NTP/chrony 客户端周期性与时间服务器校时；`timedatectl` 管时区与 NTP 开关。时间不同步的后果：日志时间线错乱、Kerberos/TLS 证书校验失败、分布式事务错乱。RTC（硬件时钟）与系统时钟分离，`hwclock --systohc` 同步。
9. **系统缓慢原理**：load average = 可运行 + 不可中断进程数均值（1/5/15 分钟），8 核机器 load 持续 >8 说明 CPU 排队。但 load 高 ≠ CPU 忙：D 状态进程（IO 卡住）也算入 load，`vmstat` 的 `r`（运行队列）和 `wa`（IO 等待）、`iostat` 的 `%util` 才能区分 CPU/IO/内存瓶颈。
10. **内核模块加载失败原理**：`modprobe` 加载 .ko 时内核校验：文件格式、**vermagic**（内核版本 + SMP/PREEMPT 等编译选项，必须与运行内核一致）、模块签名（CONFIG_MODULE_SIGN_FORCE 时签名必须有效）、依赖模块。任一项不过都报 `Required key not available` / `Invalid module format` 等错误，dmesg 有详情。

## 常用命令与配置

```shell
# ---------- 磁盘 ----------
df -h                          # 分区使用率
df -i                          # inode 使用率（海量小文件场景）
du -sh /var/* | sort -rh | head   # 大目录排行
du -ah /var/log | sort -rh | head -10   # 大文件排行
lsof +L1                       # 被删除但仍被占用的文件（空间不释放）
find / -xdev -size +1G 2>/dev/null     # 全盘找大文件（xdev 不跨挂载点）

# ---------- 内存 ----------
free -h                        # 内存 + swap 总览
dmesg | grep -i 'out of memory'        # OOM 记录（含被杀的进程）
ps aux --sort=-%mem | head     # 内存大户
cat /proc/<PID>/oom_score      # 某进程 OOM 分数
cat /proc/<PID>/oom_score_adj  # 某进程 OOM 权重（-1000 免疫）

# ---------- CPU ----------
top                            # 进程 CPU 排行
top -H -p <PID>                # 看进程内哪个线程飙
mpstat -P ALL 1                # 单核还是多核（ALL 逐核）
pidstat 1                      # 按进程/线程的 CPU 统计
perf top -p <PID>              # 定位到函数（root/低 paranoid）

# ---------- 服务/进程 ----------
systemctl status <svc> --no-pager    # 服务状态 + 最近日志
systemctl --failed --no-pager        # 所有失败单元
journalctl -u <svc> -n 50 --no-pager # 服务日志
journalctl -xe                       # 最近错误 + 提示
ps -eo pid,stat,wchan:20,comm | grep -E '^ *[0-9]+ D'   # D 状态进程
strace -f -p <PID>                   # 卡在哪（短时取证）
gdb -p <PID> -batch -ex 'thread apply all bt'   # 全线程栈

# ---------- 网络 ----------
ip addr && ip route            # IP 与路由配置
ping -c 3 <目标>               # 链路连通性
ss -tlnp                       # 本机监听端口 + 进程
ss -tnp | grep <端口>          # 连接状态（ESTABLISHED/TIME_WAIT）
nc -zv <IP> <端口>             # 端口连通测试
tcpdump -i any port <端口> -n  # 抓包看流量（root）
dig +short <域名>              # DNS 解析

# ---------- 时间/系统 ----------
timedatectl                    # 时区 + NTP 状态
timedatectl set-timezone Asia/Shanghai
systemctl status systemd-timesyncd   # NTP 客户端状态
chronyc tracking / ntpq -p     # chrony / ntp 服务器状态
uptime && vmstat 1 3           # load + 运行队列 + IO 等待
iostat -x 1 3                  # 磁盘 %util/await（需 sysstat）

# ---------- 内核模块 ----------
modprobe <模块>                # 加载（带依赖）
modinfo <模块>.ko              # 查看 vermagic/依赖/签名
dmesg | tail -20               # 加载失败详情
```

## 应用场景实战

> 说明：每个场景 = 一个完整故障案例，按「现象 / 定位过程 / 根因 / 解决与预防」四段式组织。命令输出带「实测（本机）」的为本机真实执行结果。

### 场景一：磁盘满（df 100% / inode 满 / 删除未释放）

**现象**：写文件报 `No space left on device`，服务写日志失败告警，数据库插入报错；有时 `df -h` 明明有空间却写不进（inode 满）。

**定位过程**：

```shell
# ① 哪个分区满了
df -h
# ② inode 是否用满（大量小文件场景必查）
df -i
# ③ 逐层找大目录：先看一级，再深入
du -sh /var/* /home/* /opt/* 2>/dev/null | sort -rh | head
# ④ 找大文件
du -ah /var/log 2>/dev/null | sort -rh | head -10
# ⑤ 是否删了文件但空间没释放（deleted 文件）
lsof +L1
```

```text
# 实测（本机）——健康基线：磁盘和 inode 都很充裕
$ df -h | head -4
文件系统        大小  已用  可用 已用% 挂载点
tmpfs           2.0G  4.4M  2.0G    1% /run
/dev/sda2       915G   62G  807G    8% /
$ df -i | head -4
文件系统         Inodes   已用I    可用I 已用I% 挂载点
tmpfs           2521327    2037  2519290     1% /run
/dev/sda2      60981248 1067061 59914187     2% /

# 实测（本机）——确实存在「删除未释放」的文件（lsof +L1 输出）
$ lsof +L1 2>/dev/null | head -5
COMMAND    PID USER   FD   TYPE DEVICE SIZE/OFF NLINK     NODE NAME
systemd-l 1173 root  txt    REG    8,2   285264     0 57837556 /usr/lib/systemd/systemd-logind (deleted)
(sd-pam)  1624   lw  txt    REG    8,2   137792     0 57837489 /usr/lib/systemd/systemd-executor (deleted)
1panel-ag 1656 root    2u   REG    8,2     7953     0  4459458 /opt/1panel/log/1Panel-2026-07-27.log (deleted)
pipewire  1783   lw  36u   REG    0,1     2312     0     1043 /memfd:pipewire-memfd:flags=0x0000000f,... (deleted)
# NLINK=0 且 NAME 带 (deleted) = 文件已被 rm，但进程句柄还开着，空间未释放
```

**根因**：① 日志不轮转（`/var/log` 常见，无 logrotate 或 copytruncate 配置不当）；② 海量小文件耗尽 inode（`df -i` 100% 而 `df -h` 未满）；③ 大文件被进程占用后删除，空间不释放（NLINK=0）；④ 备份/临时文件残留。

**解决与预防**：

```shell
# 止血：先腾空间恢复业务
rm -f /var/log/old/*.log        # 确认可删后再删
# 删除未释放：找到占用进程并重启/重开日志（日志文件场景：logrotate copytruncate）
lsof +L1 | awk '$5=="REG" && $7==0 {print $2}' | sort -u   # 占用 PID
systemctl restart <占用服务>    # 或 kill -HUP 让服务重开日志
# inode 满：删海量小文件（如 /tmp、邮件队列、PHP session）
find /var/tmp -type f -mtime +7 -delete
# 根治：配置日志轮转
#   /etc/logrotate.d/myapp：daily rotate 7 compress copytruncate
# 预防：磁盘监控告警（used% ≥ 80% 告警）；日志量预估 + 归档策略；
#       日志落独立分区，防写满根分区
```

### 场景二：内存泄漏与 OOM（进程被杀）

**现象**：服务进程 RSS 持续上涨、重启后回落；或进程突然消失、dmesg 有 `Out of memory: Killed process` 记录；严重时系统整体卡顿（内存压力换页）。

**定位过程**：

```shell
# ① 内存总览（used/available/swap 是否打满）
free -h
# ② 确认是否 OOM 及被杀进程
dmesg | grep -i 'out of memory' | tail
grep -i 'out of memory' /var/log/syslog | tail
# ③ 内存大户排行
ps aux --sort=-%mem | head -10
# ④ 观察目标进程 RSS 走势（泄漏特征：只涨不跌）
watch -n 5 'ps -o pid,rss,%mem,comm -p <PID>'
# ⑤ 看 OOM 权重，判断为什么杀的是它
cat /proc/<PID>/oom_score /proc/<PID>/oom_score_adj
```

```text
# 实测（本机）——内存总览（19Gi 总量，swap 8Gi 基本未用，健康）
$ free -h
               total        used        free      shared  buff/cache   available
内存：          19Gi        11Gi       1.5Gi       1.8Gi       8.3Gi       7.4Gi
交换：         8.0Gi       493Mi       7.5Gi
# 实测（本机）——当前无 OOM 记录（健康基线）
$ dmesg 2>/dev/null | grep -iE 'out of memory|oom-kill' | tail -3
（无输出 = 本机近期没有 OOM）
$ grep -i 'out of memory' /var/log/syslog 2>/dev/null | tail -3
（无输出）
```

**根因**：① 代码内存泄漏（malloc/new 未释放，参考 [[17.3-调试工具]] valgrind/ASAN）；② 缓存/容器无限增长（无上限的 LRU/缓存池）；③ 物理内存本身不足（过度售卖）；④ swap 配置不当（vm.swappiness 过高导致换页抖动）；⑤ 并发峰值内存估算错误。

**解决与预防**：

```shell
# 止血：重启服务（泄漏场景下 RSS 回落到基线，业务恢复）
systemctl restart <svc>
# 定位泄漏（测试环境）：valgrind --leak-check=full ./myapp
# 定位泄漏（Java）：jmap -histo <PID> | head -20 对比两次快照差异对象
# 保护关键进程（不让 OOM Killer 误杀核心服务）
systemctl set-property <svc> OOMScoreAdjust=-900     # systemd 服务
echo -1000 > /proc/<PID>/oom_score_adj               # 手工（-1000 免疫）
# 预防：内存监控告警（used% ≥ 85%）；容器设 memory limit + OOMKilled 检测；
#       关键服务 OOMPolicy=stop（systemd 配置）；
#       压测确定峰值内存，按峰值 +20% 预留
```

### 场景三：CPU 100%（进程吃满 CPU）

**现象**：top 里某进程 %CPU 持续 100%+，系统响应变慢；Java 服务表现为 GC 线程狂转。

**定位过程**：

```shell
# ① 找吃 CPU 的进程
top -bn1 | head -12
# ② 单核还是多核
mpstat -P ALL 1 3
# ③ 进程内哪个线程飙
top -H -p <PID>
# ④ 定位到函数（C/C++）
perf top -p <PID>
# ⑤ Java 进程：线程 dump 找 RUNNABLE 热点线程，jstat 看是否 GC 风暴
jstack <PID> | grep -A 20 'nid=0x...'   # nid 用 printf '%x' 线程号 换算
jstat -gcutil <PID> 1000 5
```


### 场景四：服务无法启动（systemd 失败）

**现象**：`systemctl start <svc>` 后服务起不来，或起来秒退（crash loop）；客户端连不上该服务。

**定位过程**：

```shell
# ① 状态 + 失败原因
systemctl status <svc> --no-pager
# ② 最近错误日志（journalctl -xe 是官方提示入口）
journalctl -u <svc> -n 50 --no-pager
# ③ 系统整体失败单元
systemctl --failed --no-pager
# ④ 检查常见三要素：二进制存在性、配置语法、端口占用
which <二进制> || ls -l <二进制路径>
<服务> -t          # 很多服务自带配置检查（nginx -t / sshd -t）
ss -tlnp | grep <端口>   # 端口是否被占
```

**根因**：① 依赖服务没起（unit 缺 After/Requires，或依赖本身失败）；② 二进制/配置文件路径错误或权限不足；③ 配置语法错误（改配置后没 `-t` 验证）；④ 端口被占用（见场景六）；⑤ crash loop（进程启动即崩，Exit code 非 0，常见配置错/依赖缺失）；⑥ 资源不足（fork 失败、句柄上限）。

```shell
#   - crash loop（State=auto-restart）→ 前台跑二进制看真实报错：
sudo -u <用户> <二进制>    # 前台执行，错误直接打到终端
# 预防：改配置先语法检查（-t）；发布流程带 systemd unit 校验；
#       服务自检（healthcheck）+ 启动超时；依赖服务用 Requires + After
```

### 场景五：网络不通（分层排查）

**现象**：客户端连不上服务、跨主机 ping 不通、丢包/延迟高、DNS 解析失败。

**定位过程**（严格按层，一层不通先解决本层）：

```shell
# ① 本机 IP/路由配置
ip addr && ip route
# ② 链路连通性（先 ping 网关，再 ping 目标）
ping -c 3 <网关>
ping -c 3 <目标IP>
# ③ DNS
dig +short <域名> || nslookup <域名>
# ④ 目标端口监听（本机视角）
ss -tlnp | grep <端口>
# ⑤ 端口连通（对端防火墙是否放行）
nc -zv <目标IP> <端口>
# ⑥ 抓包看真实流量（判断是丢包还是被防火墙 RST）
tcpdump -i any host <目标IP> and port <端口> -n
```

### 场景六：端口被占用（bind 失败）

**现象**：服务启动报 `Address already in use` / `bind: Cannot assign requested address`；新服务起不来，但明明「没有部署过」这个端口。

**定位过程**：

```shell
# ① 反查端口占用者（-t TCP -l 监听 -n 数字 -p 进程）
ss -tlnp | grep <端口>
# ② 或按进程查它监听了哪些端口
ss -tlnp | grep <PID>
# ③ 老命令 lsof 亦可（ss 更快更全）
lsof -i :<端口>
# ④ 排查残留进程（服务已删/已停但进程还活着）
ps aux | grep <旧服务名>
```

```shell
# 端口规划：服务端口登记表（配置中心/文档），新服务上线先查表；
# 预防：监控端口监听状态（该监听的没监听、不该监听的出现了都告警）
```

### 场景七：进程假死（D 状态 / 死锁 / 等外部资源）

**现象**：进程还在（ps 能看到），但业务完全不响应；kill 不掉或 kill 后一直不退出；CPU 占用很低（区别于死循环）。

**定位过程**：

```shell
# ① 看进程状态（D=不可中断睡眠，最常见假死）
ps -eo pid,stat,wchan:24,comm | grep -E ' D| D$| D '
# ② 看系统 IO 是否异常（D 状态通常伴随 IO 卡住）
vmstat 1 3
iostat -x 1 3
# ③ strace 看卡在哪个系统调用（D 状态 strace 也跟不进去，看其他线程）
strace -f -p <PID> -e trace=network,file,futex 2>&1 | head
# ④ 全线程栈（死锁一眼可见）
gdb -p <PID> -batch -ex 'thread apply all bt' 2>/dev/null
```

```text

$ vmstat 1 2

# b=0 表示没有进程阻塞在 IO 上；若 b 持续 >0 且 wa 高 = IO 卡住（D 状态温床）

示例（D 状态进程）：
$ ps -eo pid,stat,wchan:24,comm | grep ' D'
 1234 D+   rpc_wait_bit_killable   nfsd        ← 等 NFS 响应（网络文件系统挂死）

```

**根因**：① **D 状态**：NFS 挂载点失联（server 挂了/网络断了，内核 IO 无限重试）、磁盘硬件故障（坏道/控制器卡死）；② **死锁**：多线程锁顺序不一致互相等待（Java 用 jstack 查 deadlock，C/C++ 用 gdb bt 看 pthread_mutex_lock 环）；③ **等外部资源**：数据库连接池耗尽、消息队列积压、分布式锁服务失联；④ 信号处理死循环（SIGSTOP 后无人 SIGCONT，进程 T 状态）。

**解决与预防**：

```shell
# D 状态：kill -9 无效（不可中断），只能等 IO 恢复或重启
#   ① 检查 NFS 挂载：mount | grep nfs，尝试 umount -f 或重启 client
#   ② 磁盘硬件：dmesg | grep -iE 'i/o error|ata|scsi' 看是否有 IO 错误
# 死锁：重启服务临时恢复 → 分析线程 dump 锁链 → 修代码（锁顺序统一）
# 等外部资源：看连接池/依赖服务状态；给所有外部调用加超时
# 预防：NFS 用 soft 挂载（默认 hard 会无限重试）；外部调用全加超时+熔断；
#       监控进程状态（D/T 状态数量告警）；连接池监控（[[13.3-系统监控]]）
```

### 场景八：时区与时间不同步

**现象**：日志时间戳与本地时间差 8 小时（时区错）；不同机器日志时间对不上（不同步）；证书/认证报时间错误；定时任务在错误时间执行。

**定位过程**：

```shell
# ① 时区 + 系统时间 + NTP 状态
timedatectl
# ② 是否开启 NTP 同步
timedatectl show-timesync | head -5   # 或 systemctl status systemd-timesyncd
# ③ 时间服务器状态（chrony 系）
chronyc tracking && chronyc sources -v
# ④ ntpd 系
ntpq -p
# ⑤ 硬件时钟与系统时钟偏差
hwclock --show
```

```text

#             NTP service: inactive 都是异常信号
```

**根因**：① 时区配置错误（容器默认 UTC、机房机器没设本地时区）；② NTP 服务未启用/被防火墙挡（UDP 123）；③ 时间服务器不可达（内网无 NTP、公网被禁）；④ 硬件时钟漂移（RTC 电池/晶振，无 NTP 的机器越跑越偏）；⑤ 虚拟化环境时钟源问题（VM 未启用 kvm-clock 等）。

**解决与预防**：

```shell
# 改时区
timedatectl set-timezone Asia/Shanghai
# 启用/重启 NTP 同步
timedatectl set-ntp true
systemctl restart systemd-timesyncd
# chrony（RHEL 默认）：vim /etc/chrony.conf 配 pool，systemctl restart chronyd
# 内网环境：自建 NTP/chrony 服务器，客户端指向内网地址
# 预防：初始化脚本统一时区；监控 System clock synchronized 状态；
#       证书类服务对时间敏感，纳入告警（时间偏移 > 阈值告警）
```

### 场景九：系统缓慢（load 高 / iowait 高 / 内存压力）

**现象**：操作卡顿、命令执行慢、SSH 反应迟钝；`uptime` 的 load average 持续高于核数。

**定位过程**：

```shell
# ① load 总览（1/5/15 分钟趋势：15 分钟高说明持续已久）
uptime
# ② 区分瓶颈类型：CPU 忙 / IO 忙 / 内存压力
vmstat 1 5          # r=运行队列（CPU），b=阻塞（IO），wa=IO 等待，si/so=换页
mpstat -P ALL 1 3   # us/sy 高 = CPU 瓶颈；%iowait 高 = IO 瓶颈
iostat -x 1 3       # %util 接近 100% = 磁盘饱和；await 高 = 延迟大
free -h             # available 低 + si/so 频繁 = 内存压力
# ③ 找元凶进程
top -o %CPU -o %MEM -bn1 | head -15
```

```text
$ vmstat 1 2

 0  0 505792 1545392  44740 8627532    0    0     9   103 3334    5  1  0 96  2  0  0

# 判读口诀：wa 高 = 磁盘慢；r 高 = CPU 排队；si/so 非 0 = 内存不足在换页
```

**根因**：① CPU 饱和：业务增长/死循环/GC 风暴（见场景三）；② **IO 饱和**：磁盘慢（机械盘/共享存储/RAID 降级）、日志写入风暴、数据库刷盘；③ 内存压力：available 耗尽触发换页（swap 抖动，见场景二）；④ 网络瓶颈（网卡打满，`sar -n DEV 1 3`）；⑤ 单机资源被某个进程独占（大查询/备份任务）。

**解决与预防**：

```shell
# 按瓶颈类型对症：
#   CPU 饱和 → 场景三的定位 + 扩容（垂直/水平）或优化算法
#   IO 饱和 → iostat 找热盘热文件；日志降噪/异步写；RAID 状态检查
#             （[[06.4-RAID]]：降级阵列 IO 会骤降）；机械盘换 SSD
#   内存压力 → 加内存/调 swappiness/查泄漏（场景二）
#   网络 → sar -n DEV 看吞吐；业务低峰跑大流量任务
# 预防：容量规划（按峰值 +30% 余量）；性能基线 + 趋势告警；
#       慢查询/大任务错峰调度
```

### 场景十：内核模块加载失败

**现象**：`modprobe <模块>` 报错，设备驱动/特性不可用；`insmod` 报 `Invalid module format`；dmesg 里有 taint 或签名错误。

**定位过程**：

```shell
# ① 加载并看报错
modprobe <模块> 2>&1
# ② dmesg 看内核拒绝的详细原因（关键证据）
dmesg | tail -20
# ③ 检查模块与运行内核是否匹配
uname -r                              # 运行内核版本
modinfo <模块>.ko | grep -E 'vermagic|depends|signature'
# ④ 已加载模块列表里找依赖
lsmod | grep <依赖模块>
```

```text
# 实测（本机）——内核模块加载/卸载的真实日志（签名校验 + taint 机制）
$ dmesg | tail -8
[1987138.779760] hello: module verification failed: signature and/or required key missing - tainting kernel
[1987138.779932] Hello, kernel! (init, count=3)
[1987138.824293] Goodbye, kernel! (exit)
[1987182.491805] Hello, kernel! (init, count=1)
[1987182.500073] Goodbye, kernel! (exit)
# 解读：未签名模块在 Ubuntu 上允许加载但「taint 内核」（污染标记：
#       后续 oops 不再被信任，也进不了自动报告流程）；
#       RHEL 在 CONFIG_MODULE_SIG_FORCE 开启时直接拒绝加载
```

**根因**：① **vermagic 不匹配**：模块用别的内核版本/配置编译（最常见，`uname -r` 与编译内核不一致）；② 模块签名拒绝：Secure Boot 开启或内核强制签名校验（RHEL 常见，`Required key not available`）；③ 依赖模块缺失（modinfo 的 depends 字段）；④ 模块与硬件不匹配/已废弃；⑤ 权限问题（非 root 加载）。

**解决与预防**：

```shell
# vermagic 不匹配：必须用与运行内核匹配的模块
#   Ubuntu：apt install linux-modules-extra-$(uname -r)
#   RHEL：dnf install kernel-devel kernel-modules-extra
# 源码编译场景：模块与内核一起编译（DKMS 管理），或
#   编译前确认 make -C /lib/modules/$(uname -r)/build
# 签名拒绝（RHEL/Secure Boot）：
#   mokutil --import MOK.der 导入签名密钥（shim/MOK 流程）
#   或关闭 Secure Boot（需控制台操作）
# 依赖缺失：modprobe 会自动拉依赖，报 Unknown symbol 时按 modinfo 补模块
# 预防：驱动版本与内核版本绑定管理；升级内核后重装驱动（DKMS 自动）；
#       硬件驱动变更走变更流程并验证
```

## 性能与调优

```text
故障预防体系（比「会修」更重要）：
1. 资源监控先行 —— CPU/内存/磁盘/网络/句柄全维度监控 + 分级告警
   （[[13.3-系统监控]]）：磁盘 ≥80% 预警、≥90% 严重；内存 available
   低于 20% 预警；CPU 持续 100% 告警；D 状态进程数量告警。
2. 容量规划 —— 按峰值 +30% 余量规划内存/磁盘/CPU；磁盘按日志增速
   预估 90 天占用；内存按压测峰值规划；swap 建议 = 内存 0.5~1 倍
   （服务器 8~16G 常见），或大内存机器关 swap 防抖动（结合业务权衡）。
3. 日志治理 —— logrotate 必须配（daily + rotate N + compress）；
   日志落独立分区；journald 配 SystemMaxUse 限制；
   大日志量上集中日志（[[13.5-日志分析实战]]）。
4. 变更管理 —— 防火墙/安全组、内核、驱动、配置变更走审批 + 回滚预案；
   大量故障是「昨天改了啥」造成的——改前备份、改后验证。
5. 自愈与降级 —— 服务崩溃自动重启（Restart=always + RestartSec）；
   关键服务 OOMPolicy/oom_score_adj 保护；外部依赖超时 + 熔断；
   磁盘满自动清理（日志轮转兜底）。
6. 演练与文档 —— 定期故障演练（磁盘满/断网/杀进程）；把每次故障
   处理过程沉淀成 runbook，故障复盘进入知识库。
```

## 安全与权限

```text
1. 登录类故障的边界 —— 排查「无法登录」时别泄露密码哈希/密钥：
   auth.log 里只有认证结果，处理时要区分「暴力破解」和「正常失败」，
   频繁 Failed password 应触发 fail2ban（见 [[23.4-入侵检测与响应]]）。
2. 强制访问控制 —— Ubuntu 默认 AppArmor，RHEL 默认 SELinux（Enforcing）。
   服务起不来/文件打不开且权限正确时，查强制访问控制日志：
   Ubuntu：dmesg/journalctl 里 apparmor="DENIED" 记录
   RHEL：  ausearch -m avc -ts recent / journalctl | grep avc
   Red Hat 系差异（SELinux vs AppArmor）：
     RHEL：SELinux 拒绝 → setenforce 0 临时验证 → 正确做法是写策略
           （chcon/semanage fcontext/audit2allow 生成模块）
     Ubuntu：AppArmor 拒绝 → 查 profile（aa-status），临时 aa-complain 验证
   防火墙同理：RHEL 是 firewalld（firewall-cmd），Ubuntu 是 ufw——
   查端口不通时先确认「自己家的防火墙」是哪一套。
3. 实测（本机）——AppArmor 拒绝记录（dmesg 真实输出）：
   [1985357.359633] audit: type=1400 audit(...): apparmor="DENIED" operation="open"
     class="file" profile="snap.snap-store.snap-store" name="/proc/sys/vm/max_map_count"
     requested_mask="r" denied_mask="r" fsuid=1000 ouid=0
   [1986393.573471] audit: type=1400 audit(...): apparmor="DENIED" operation="capable"
     class="cap" profile="man_groff" pid=3107689 comm="preconv" capability=2
     capname="dac_read_search"
   解读：snap 应用被 profile 限制读 /proc/sys/vm/max_map_count；
   man 手册页渲染被限制 capability——都属于「策略预期内的拒绝」，
   但同样格式的记录在业务服务上出现 = 故障根因，要学会读它。
4. 排查操作权限 —— 抓包（tcpdump）、strace/gdb attach 需 root 或对应
   权限；kill 前必须确认进程归属（ps -fp 看用户/启动时间/命令行），
   误杀生产进程是比故障本身更严重的事故。
5. 日志即证据 —— auth.log/syslog/journald 保留策略（rotate 周期）要满足
   安全审计需求；删日志/清 history 会破坏故障取证，属高危操作。
6. 故障报告渠道差异（Red Hat 系）—— Ubuntu 崩溃上报用 ubuntu-bug/apport，
   RHEL 用 abrt-cli（崩溃收集）+ sosreport（全套诊断包一键收集：
   sosreport 输出 tar 包，含内核日志/配置/资源快照，报给厂商/内部
   排查前先跑它）；这两个「取证打包」工具在对方发行版上都没有。
```

### 案例一：先对号入座——故障快速决策树

```text
业务不可用/变慢？
```

### 案例二：日志取证——把「时间线」拼出来

```shell

# ⑤ 系统级文本日志清单
```

## 常见问题

```text
Q1: 磁盘满了，删文件后 df 还是不降？
A: 文件被进程占用（句柄未释放），rm 只删了目录项，数据块还被
   进程引用。用 lsof +L1 找 NLINK=0 的 deleted 文件，重启占用进程
   或 kill -HUP 让它重开日志，空间立即释放。

Q2: df -h 显示有空间，但写文件报 No space left？
A: inode 用满（海量小文件占光元数据）。df -i 确认（100% 即满），
   清理小文件（/tmp、session、邮件队列等），或扩容/重建文件系统
   （inode 数量在 mkfs 时决定，ext4 可用 -I 调整，xfs 无法在线增 inode）。

Q3: OOM Killer 怎么决定杀哪个进程？
A: 按 oom_score（内存占用为基数 + 惩罚因子），分数越高越可能被杀；
   关键进程用 oom_score_adj=-1000 免疫（systemd 用
   OOMScoreAdjust=-900），或设 OOMPolicy=stop 让 systemd 杀掉重启。
   被杀进程在 dmesg 有 Out of memory: Killed process <PID> (<名字>)。

Q4: 进程 kill 不掉怎么办？
A: 先 ps -eo stat,wchan 看状态：D（不可中断）→ kill 无效，等 IO 恢复
   或重启（NFS 场景用 soft 挂载预防）；T（停止）→ kill -9 后
   kill -CONT；Z（僵尸）→ 杀不掉但也不占资源，等父进程 reap；
   正常 S/R 状态 kill 不掉 → 检查是否在信号处理里屏蔽了信号。

Q5: 服务起来就秒退（crash loop）怎么查？
A: 三步：① journalctl -u <svc> -n 50 看退出前最后输出；
   ② sudo -u <用户> 前台手动跑二进制，错误直接打终端（最有效）；
   ③ 查配置语法（nginx -t/sshd -t）+ 端口占用 + 依赖文件权限。
   注意 systemd 的 Restart=always 会把崩溃伪装成「反复重启」，
   看 status 里的 Main PID 是否每次都变 + journal 的退出码。

Q6: 端口不通，ping 通但 nc 连不上，是什么问题？
A: ping 只验证 IP 层。nc 连不上 = TCP 层被拒：① 目标端口没监听
   （ss -tlnp 确认）；② 防火墙/安全组拦截（本地 ufw/firewalld、
   云安全组、对端 iptables）；③ 服务监听在 127.0.0.1 而外部访问
   需要 0.0.0.0（bind 地址错误，非常常见）；④ SYN 被丢弃（半连接
   队列满，ss -tn state syn-recv 统计）。

Q7: 时区没问题，但两台机器日志时间对不上？
A: 时区相同 ≠ 时间同步。用 timedatectl 看 System clock synchronized
   是否 yes；chronyc sources（chrony）/ ntpq -p（ntpd）看偏移量；
   两台机器对同一 NTP 源的偏移都应在毫秒级。常见根因：一台没配
   NTP、防火墙挡了 UDP 123、虚拟机时钟源问题。

Q8: load average 很高，但 top 里没有进程 CPU 高，为什么？
A: load 包含「可运行」+「不可中断睡眠」两类进程：D 状态进程（IO 卡住）
   也算 load。用 vmstat 看 b（阻塞）和 wa（IO 等待）、iostat -x 看
   磁盘 %util，大概率是磁盘/存储瓶颈而不是 CPU。这就是「load 高
   但 CPU 空闲」的经典解释。
```

## 面试题

```text
1. 一个服务突然变慢，你怎么排查？
   答：先定性分类（资源/网络/配置/代码），再按类查：uptime 看 load、
   top 看 CPU、free 看内存、df 看磁盘、vmstat 看 IO 与换页、ss 看网络；
   定位到瓶颈类型后深入（CPU → perf/jstack；IO → iostat；内存 → 泄漏
   排查；网络 → 分层排查）。关键是从「系统慢」收敛到「哪个资源、
   哪个进程、哪个函数」，每步都有输出依据，不猜。

2. 磁盘满和 inode 满有什么区别？怎么区分？
   答：磁盘满 = 数据块耗尽（大文件，df -h 100%）；inode 满 = 元数据
   耗尽（海量小文件，df -i 100%，df -h 还有空间却写不进）。写文件
   报 No space left 时两个都看；清理方向不同：前者删大文件/日志，
   后者删小文件（find -type f | wc -l 统计，rm 批量清理）。

3. 进程频繁被杀，代码查不出问题，可能是什么？
   答：OOM Killer。dmesg | grep -i 'out of memory' 找 Killed process
   记录，free 看内存是否耗尽 + swap 是否打满，ps --sort=-%mem 找内存
   大户；根因通常是内存泄漏（RSS 只涨不跌）或容量不足；关键进程用
   oom_score_adj 保护。

4. 为什么说「瓶颈是进程级 ulimit -n，不是系统级 file-max」？
   答：file-max 是系统级上限（本机实测 9223372036854775807，几乎不会
   撞）；单个进程受 ulimit -n 限制（默认 1024，本机实测），高并发
   服务打开连接数先撞进程级上限（Too many open files）。调优对象是
   进程的 nofile（limits.conf 或 systemd LimitNOFILE），并排查句柄泄漏。

5. 端口被占用，怎么安全地解决？
   答：ss -tlnp | grep <端口> 反查占用进程 → ps -fp <PID> 确认是什么
   （不能见 PID 就杀，可能杀错生产服务）→ 分情况：残留进程 kill 掉；
   业务冲突则协商换端口或停旧服务；确认释放后重启新服务。预防靠
   端口登记表 + 监听状态监控。

6. 进程 D 状态是什么？怎么处理？
   答：D = 不可中断睡眠，进程在内核态等待 IO 完成（典型：NFS 失联、
   磁盘故障），期间连 kill -9 都无法打断，只能等 IO 恢复或重启。
   定位：ps -eo stat,wchan 看等待点、vmstat b 列看阻塞数、dmesg 看
   IO 错误；预防：NFS 用 soft 挂载 + 超时、磁盘健康监控、存储链路冗余。

7. 公司内部 10 台机器时间不同步，你怎么处理？
   答：统一时区（timedatectl set-timezone，如 Asia/Shanghai）；统一
   NTP 源（自建 chrony 服务器，客户端指向内网源，避免公网不可达）；
   检查防火墙放行 UDP 123；监控 System clock synchronized 状态和
   偏移量；虚拟化环境确认时钟源（kvm-clock 等）。时间问题影响日志
   对齐、证书校验和分布式一致性，要当基础设施治理来做。

8. 讲一个你印象最深的线上故障，怎么排查的？
   答：（结合本文案例讲一个完整四段式，重点突出「证据链」）例如：
   现象——服务频繁重启；定位——dmesg 发现 OOM Killed process，
   ps 发现内存大户 RSS 持续上涨，两次 jmap -histo 对比发现某个缓存
   对象只增不减；根因——缓存无上限且 key 永不失效；解决——重启止血
   + 代码加容量上限和淘汰策略 + 监控 RSS 告警 + oom_score_adj 保护
   过渡期；复盘——补监控盲区、写 runbook。面试时展现「证据→结论」
   的推理过程比背命令重要。
```

## 最佳实践与踩坑记录

### 最佳实践

1. **每个故障按「现象 → 定位 → 根因 → 解决与预防」四段式走**，先记录现象和影响面再动手，别跳步骤直接改配置。
2. **磁盘满先 df 定位分区，再 du 定位目录，最后才删**；删之前确认文件用途（备份/日志/临时），删错数据无法恢复。
3. **OOM 先看 dmesg 确认再下结论**：dmesg 的 Killed process 行是「谁被杀了」的铁证，比猜代码靠谱。
4. **网络异常按分层排查**（IP → 链路 → 端口 → 抓包），一层不通先解决本层；云环境优先查安全组。
5. **服务进程的 ulimit 提前调高**（limits.conf / systemd LimitNOFILE），别等 Too many open files 才处理。
6. **改配置先验证再重启**：`nginx -t`、`sshd -t`、`systemd-analyze verify`；改 SSH 先确认密钥可用再关密码认证（防自锁）。
7. **kill 前必确认**：`ps -fp <PID>` 看用户、命令行、启动时间，确认不是别的业务再动手。
8. **假死先分型再动手**：D 状态（等 IO）kill 无效、死锁（等锁）重启+修代码、等资源（超时+熔断）——处理方式完全不同。
9. **监控告警先于故障处理**：把每次故障的「发现方式」补成监控规则，让下次故障变成告警而不是事故。
10. **故障后必复盘并沉淀**：更新 runbook、速查表和本文档，横向排查同类隐患，让一次故障的价值最大化。

### 踩坑记录

```text
坑 1：删了文件但磁盘空间没释放
结论：rm 删了大文件，df 看还是满的，业务继续写失败。
原因：文件被进程占用（句柄未释放），删除只删了目录项，数据块仍被引用。
解法：lsof +L1 找 deleted 文件 → 确认占用进程 → 重启或 kill -HUP
     让其重开文件；日志场景配置 logrotate copytruncate。

坑 2：df 显示没满但报 no space
结论：df -h 空间还有 30%，写文件却报 No space left on device。
原因：inode 用满（海量小文件占光元数据），df -i 才是真凶。
解法：df -i 确认 → 清理小文件（find 批量删）；容器/tmp 目录是重灾区；
     文件系统规划时预估 inode 需求。

坑 3：进程莫名被杀，以为是代码 bug
结论：服务偶发消失，翻代码查了两天没结果。
原因：OOM Killer 杀的（内存峰值超限），dmesg 里明明白白。
解法：dmesg | grep -i 'out of memory' 先查；再看 free/内存大户；
     容器场景看 docker inspect 的 OOMKilled 字段；
     关键服务 oom_score_adj 保护 + 容量评估。

坑 4：改 sshd_config 后 SSH 连不上（自锁）
结论：改了配置重启 sshd，自己再也连不上了。
原因：先关了 PasswordAuthentication 又没配好密钥，或改了端口没放行
     防火墙/安全组，或 sshd -t 没验就重启。
解法：改前 sshd -t 验证；先配好密钥确认能登录再关密码；
     改端口先放行防火墙；救急走控制台/救援模式改回来。

坑 5：Too many open files，以为调系统上限就行
结论：报句柄耗尽，去调 /proc/sys/fs/file-max，问题依旧。
原因：瓶颈是进程级 ulimit -n（默认 1024），不是系统级 file-max；
     而且不查泄漏就调上限只是延缓问题。
解法：先 lsof -p <PID> | wc -l 看增长趋势（泄漏则修代码）；
     确认正常需求再调 limits.conf/systemd LimitNOFILE；
     高并发服务（连接池）尤其注意。

坑 6：端口起不来，一查是上个版本的服务没停干净
结论：新版本部署启动报 Address already in use，配置明明没冲突。
原因：旧进程残留（上次部署 kill 失败/重启时旧容器没删）。
解法：ss -tlnp | grep <端口> 反查 → ps -fp 确认 → kill 干净再启动；
     部署脚本加「先停旧、确认端口释放、再启新」的步骤。

坑 7：ping 通但业务连不上，以为是对方问题
结论：客户端 ping 服务器通，SSH 也通，但 8080 端口连不上，
     一度以为是对方服务挂了。
原因：服务监听在 127.0.0.1（只本机可连）或防火墙/云安全组没放行
     该端口——ping 只证明 IP 层通，不代表端口通。
解法：分层排查：ss -tlnp 看监听地址（0.0.0.0 vs 127.0.0.1）；
     nc -zv 测端口；ufw/firewalld/安全组逐层核对；
     监听地址改 0.0.0.0 或按需绑定网卡。

坑 8：进程 kill -9 都杀不掉
结论：进程卡死，kill -9 后进程还在。
原因：D 状态（不可中断睡眠，等 IO）——NFS 失联、磁盘故障，
     kill 信号无法送达。
解法：ps -eo stat,wchan 确认 D 状态 → 查 NFS/磁盘（dmesg IO 错误）；
     等 IO 恢复或重启机器；预防 NFS 用 soft 挂载 + 超时。

坑 9：容器时间慢 8 小时，宿主机正常
结论：容器内 date 和宿主机差 8 小时，日志时间全乱。
原因：容器镜像默认 UTC 时区（/etc/localtime 没设置），
     宿主机是 CST。
解法：容器启动挂载 /etc/localtime 或镜像内 ln -sf
     /usr/share/zoneinfo/Asia/Shanghai /etc/localtime；
     Docker 用 -e TZ=Asia/Shanghai（部分基础镜像支持）；
     统一基础镜像时区规范。

坑 10：升级内核后驱动模块加载失败
结论：升级内核后网卡驱动 modprobe 报错，网络功能异常。
原因：驱动模块是针对旧内核编译的，vermagic（内核版本+编译选项）
     与运行内核不匹配；签名校验（Secure Boot）也可能拒绝。
解法：装与内核匹配的模块包（linux-modules-extra-$(uname -r)）；
     用 DKMS 管理的驱动会自动随内核重建；Secure Boot 环境导入
     MOK 密钥；升级内核前确认驱动兼容性。
```
