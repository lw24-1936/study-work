## 概述

系统追踪是「看程序在系统层面做了什么」——strace 追踪系统调用（程序请求内核做什么）、ltrace 追踪库函数调用（程序调用什么库函数）。这是排查「程序卡住、报错、行为异常」的利器：程序日志说不清时，追踪它的系统调用能看出「它到底在等什么、失败在哪」。核心是「用系统调用的视角看程序行为」。

```text
# 实测（本机追踪工具）
$ for t in strace ltrace; do command -v $t >/dev/null && echo "$t: 有" || echo "$t: 无"; done
strace: 有
ltrace: 无
# strace 已装，ltrace 需单独装
```

```text
系统追踪两工具：
1. strace —— 追踪系统调用（read/write/open/connect），看程序请求内核什么
2. ltrace —— 追踪库函数调用（malloc/strcpy），看程序调用什么库函数
```

## 核心概念

1. **系统调用（syscall）**：用户态程序请求内核服务的唯一接口（读文件 open/read、发网络 connect、分配内存 mmap）。
2. **strace**：追踪「程序 → 内核」的系统调用，看 read/write/open/connect 及其参数和返回值。
3. **ltrace**：追踪「程序 → libc」的库函数调用，看 malloc/strcpy/printf 等库层面行为。
4. **区别**：strace 看内核层面（覆盖大部分关键行为），ltrace 看库层面（定位到具体库函数时用）。日常排查用 strace 居多。

```text
strace vs ltrace：
1. strace —— 系统调用（内核接口），read/write/open/connect
2. ltrace —— 库函数（libc 接口），malloc/strcpy/printf
3. 日常排查 —— strace 居多，ltrace 定位库函数时用
```

## 工作原理

strace 依赖内核的 ptrace 机制：strace 用 `ptrace(PTRACE_ATTACH)` 附加到目标进程，之后目标进程每次进入/退出系统调用时，内核会暂停它并通知 strace，strace 读取系统调用号、参数和返回值，再放行进程继续。ltrace 原理类似，但 hook 的是动态链接器/PLT 里的库函数调用。

系统调用追踪的核心是「发起什么系统调用 → 参数 → 返回值」：程序卡住（卡在 read 等数据/connect 等连接）、文件打不开（open 返回 ENOENT + 路径）、网络连不上（connect 返回 ECONNREFUSED）。追踪时关注「关键调用 + 返回值」，尤其是失败的系统调用（返回值是负的错误码）。

```text
strace 原理：ptrace 附加进程 → 目标每次进出系统调用内核暂停并通知 strace → strace 记录调用号/参数/返回值
追踪要点：关注「关键调用 + 返回值」，失败的系统调用返回负错误码（-ENOENT = 文件不存在）
```

## 常用命令与配置

```shell
strace ls                        # 追踪整个程序的系统调用
strace -p 1234                   # 追踪运行中的进程
strace -e trace=file ls          # 只看文件相关
strace -e trace=network curl example.com   # 只看网络相关
strace -c ls                     # 统计系统调用
strace -f ls                     # 追踪子进程（-f fork）
strace -t -T -o trace.log ./myapp  # 带时间戳 + 耗时 + 输出到文件
```

```shell
# 看程序卡在哪（追踪运行中进程，看最后停在哪个调用）
strace -p <PID>
# 看文件操作失败（ENOENT = 文件不存在）
strace -e trace=open,openat ./myapp 2>&1 | grep -i 'no such'
```

## 配置文件解析

strace 本身无配置文件，输出格式和权限由参数与内核参数决定：

```text
strace 输出格式（每行一次系统调用）：
read(3, "hello\n", 1024) = 6
│   │       │          │    └── 返回值（6 字节 / -1 错误码）
│   │       │          └── 缓冲区大小
│   │       └── 传入数据
│   └── fd（文件描述符 3）
└── 系统调用名
```

```shell
# 影响追踪权限的内核参数（YAMA 安全模块）
cat /proc/sys/kernel/yama/ptrace_scope   # 0=全开 1=仅父子进程 2=仅 root 3=全禁
```

## 应用场景实战

### 场景一：程序卡住不动，strace 看它在等什么

```shell
# 1. 追踪卡住的进程
strace -p <PID>
# 末尾输出显示它卡在哪个系统调用：
# 如 read(3, ...) 卡住 = 在等数据（网络/管道没数据）
# 如 connect(...) 卡住 = 在等连接建立（目标不可达/防火墙）
```

### 场景二：程序报「文件打不开」，追踪真实路径

```shell
# 1. 追踪文件操作
strace -e trace=open,openat,stat ./myapp 2>&1 | grep -iE 'no such|enoent'
# 2. 输出会显示它尝试打开的文件路径，就是找不到的那个
# 3. 对比程序配置里的路径，找差异（相对路径/权限/大小写）
```

## 性能与调优

系统追踪能定位性能问题：`strace -c` 统计「哪个系统调用最多/最耗时」，`strace -T`（显示每个调用耗时）。定位思路：如果程序慢，看它「在哪个系统调用上耗时间」——比如大量 read 小数据（IO 碎片）、频繁 poll（空转）、connect 超时（网络慢）。配合 perf 定位 CPU 热点、strace 定位系统调用热点。

```shell
strace -c ./myapp          # 统计：哪个系统调用最耗时
strace -T ./myapp          # 显示每个调用的耗时
strace -T -e trace=read,write ./myapp   # 只看读写耗时
```

```text
性能定位思路：
1. CPU 热点 —— perf（哪个函数耗 CPU）
2. 系统调用热点 —— strace -c（哪个调用最多/最耗时）
3. IO 慢 —— strace -T 看 read/write 耗时，或 iostat
```

## 安全与权限

```text
1. ptrace_scope —— YAMA 安全模块限制「谁能 ptrace 谁」，默认 1（只能追踪子进程）
2. 追踪别的用户的进程需要 root —— ptrace 有权限限制，非 root 只能追自己的进程
3. strace 会暴露敏感数据 —— 系统调用的参数/缓冲区内容（密码、token）会打出来，输出文件要防泄露
4. 生产环境谨慎追踪 —— strace 有性能开销，限时采样，别长时间挂生产进程
```

## 故障排查

```shell
# 1. strace 报 ptrace 权限不足
# 症状：strace -p 别的用户的进程报 Permission denied
cat /proc/sys/kernel/yama/ptrace_scope
# 解决：root 执行，或 echo 0 > /proc/sys/kernel/yama/ptrace_scope

# 2. strace 全量输出刷屏找不到重点
# 解决：-e trace=xxx 过滤，或 -c 统计看重点

# 3. strace 生产进程导致性能下降
# 解决：限时采样（strace -p PID -f -tt -T -o 文件），跑一会就 kill
```

## 常见问题

```text
Q1: strace 和 ltrace 都追踪，有什么区别？
A: strace 追踪系统调用（内核接口），ltrace 追踪库函数调用（libc 接口）。strace 覆盖大部分关键行为，日常优先用。

Q2: strace 输出里的 ENOENT 是错误吗？
A: 不一定。很多 ENOENT 是程序「探测文件在不在」的正常行为（如查找库文件路径）。要关注关键调用的返回值，区分探测性失败和真实错误。

Q3: 程序卡住了怎么用 strace 定位？
A: strace -p <PID> 附加进程，看输出末尾停在哪个系统调用：read 卡住=等数据，connect 卡住=等连接，poll 卡住=等事件。

Q4: strace 会影响被追踪程序的性能吗？
A: 会。每个系统调用都要暂停-记录-放行，有显著开销。生产环境限时采样或先用 -c 统计。
```

## 面试题

```text
1. strace 的底层原理是什么？
   答：基于内核 ptrace 机制，附加到目标进程后，每次进出系统调用内核暂停目标并通知 strace，strace 记录系统调用号、参数和返回值。

2. 一个进程卡住不动，你怎么定位它在等什么？
   答：strace -p <PID> 附加，看输出末尾停在哪个系统调用——read 等数据、connect 等连接、poll 等事件，据此判断卡点。

3. strace 和 perf 定位性能问题有什么分工？
   答：perf 定位 CPU 热点（哪个函数耗 CPU），strace -c/-T 定位系统调用热点（哪个 syscall 最多/最耗时）。一个看函数、一个看调用。

4. 为什么 strace 追踪别人的进程会 Permission denied？
   答：ptrace 有权限限制（YAMA 安全模块 ptrace_scope），默认只允许追踪自己的子进程。追踪其他用户的进程需要 root。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 程序卡住/失败先 strace，看它在等哪个系统调用
2. 用 -e trace=xxx 过滤（file/network/process），别全量看刷屏
3. 追踪运行中进程用 strace -p PID，不影响程序
4. 性能定位用 strace -c 统计 + -T 看耗时
5. strace 有性能开销，生产环境限时采样

### 踩坑记录

```text
坑 1：strace 全量输出太大看不过来
结论：strace 程序刷屏，找不到重点。
原因：没过滤，程序系统调用太多。
解法：strace -e trace=xxx 过滤，或 -c 统计看重点。

坑 2：strace 生产进程导致性能下降
结论：strace -p 生产进程，服务变慢。
原因：strace 跟踪每个系统调用，有显著开销。
解法：限时采样（strace -p PID -f -tt -T -o 文件，跑一会就 kill），或先 -c。

坑 3：把探测性失败（ENOENT）当真错误
结论：strace 看到一堆 ENOENT 就以为程序有问题。
原因：很多 ENOENT 是程序「探测文件在不在」的正常行为。
解法：关注「关键调用 + 返回值」，区分探测性失败和真实错误。

坑 4：strace 报 ptrace 权限不足
结论：strace -p 别的用户的进程报 Permission denied。
原因：ptrace 有权限限制（YAMA 安全模块）。
解法：root 执行，或调整 /proc/sys/kernel/yama/ptrace_scope。

坑 5：ltrace 不存在就以为不能追踪库函数
结论：ltrace 报 command not found。
原因：ltrace 不是默认安装。
解法：apt install ltrace，或先用 strace（覆盖大部分场景）。
```
