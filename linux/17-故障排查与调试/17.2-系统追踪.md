## 概述

系统追踪是「看程序在系统层面做了什么」——**不修改代码、不重启服务**，从外部观察进程的运行行为。核心工具链五层：

```text
系统追踪工具链五层：
1. 调用追踪 —— strace（系统调用）/ ltrace（库函数调用）
2. 资源关联 —— lsof（打开的文件/端口/进程关联）
3. 内核追踪 —— ftrace（内核自带，函数级追踪）
4. 采样分析 —— perf（事件采样，定位 CPU 热点，详见 16.6）
5. 动态追踪 —— bpftrace / bcc（eBPF，kprobe/uprobe/tracepoint 任意挂载）
```

这是排查「程序卡住、报错、行为异常」的利器：程序日志说不清时，追踪它的系统调用能看出「它到底在等什么、失败在哪」。核心思想是「**用系统调用的视角看程序行为**」：程序的一切 IO、网络、内存操作最终都会变成系统调用，追踪系统调用就是看程序与内核打交道的完整记录。

```text
# 实测（本机）——追踪工具可用性
$ uname -r

$ for t in strace ltrace lsof perf bpftrace execsnoop-bpfcc atop htop systemtap lttng; do
>   command -v $t >/dev/null 2>&1 && echo "$t: 有" || echo "$t: 无"; done
```

## 核心概念

### 1. 系统调用（syscall）

用户态程序请求内核服务的唯一接口：读文件 `open/read`、发网络 `connect/send`、分配内存 `mmap/brk`、创建进程 `fork/execve`。系统调用是「程序 → 内核」的边界，追踪它就能还原程序的全部 IO 行为。详见 [[15.1-系统调用]]。

### 2. strace 与 ltrace

- **strace**：追踪「程序 → 内核」的系统调用，看 `read/write/open/connect` 及其参数和返回值。
- **ltrace**：追踪「程序 → libc」的库函数调用，看 `malloc/strcpy/printf` 等库层面行为。
- **区别**：strace 看内核层面（覆盖大部分关键行为），ltrace 看库层面（定位到具体库函数时用）。日常排查用 strace 居多。

```text
strace vs ltrace：
1. strace —— 系统调用（内核接口），read/write/open/connect
2. ltrace —— 库函数（libc 接口），malloc/strcpy/printf
3. 日常排查 —— strace 居多，ltrace 定位库函数时用
```

### 3. lsof

「列出打开的文件」（LiSt Open Files）——Linux 下一切皆文件，lsof 能回答三个经典问题：**谁占了这个端口**（`-i`）、**谁打开了这个文件**（进程级 fd）、**删了但没释放的是谁**（`deleted` 状态）。是「进程 ↔ 文件/端口/网络连接」关联关系的反查神器。

### 4. ftrace

内核自带的追踪框架，零外部依赖，挂在 `/sys/kernel/tracing/`（tracefs）。支持 function tracer（记录每个函数调用）、function_graph（函数调用图）、事件追踪（tracepoint）、kprobe/uprobe 动态探针。**内核崩了、perf 没装时，ftrace 是兜底**。

### 5. perf

内核 perf_event 子系统的前端，两大能力：**计数**（`perf stat`，硬件事件总量）与**采样**（`perf record`/`perf top`，定位 CPU 热点函数）。与 strace 的分工：perf 看「哪个函数耗 CPU」，strace 看「哪个系统调用最多/最慢」。详见 [[16.6-综合调优工具]]。

### 6. bpftrace / bcc（eBPF）

eBPF 是内核里的「安全虚拟机」：把用户写的小程序挂到内核 hook 点（kprobe 内核函数、uprobe 用户态函数、tracepoint 内核事件），事件触发时执行并回传数据，程序先过 verifier 校验再 JIT 编译，出错不会搞崩内核。bpftrace 是 awk 风格的一行脚本语言（`PROBE /FILTER/ { ACTION }`），bcc 是 Python 工具集（execsnoop/opensnoop/biolatency 等开箱工具）。**无需改代码、无需重启、无需装内核模块**，是生产环境动态追踪的首选。

### 7. SystemTap（简述）

与 eBPF 定位类似的动态追踪框架（脚本 → C → 内核模块），Red Hat 系（RHEL/CentOS）历史上支持最好，但需要安装 kernel-debuginfo 且编译模块有开销，近年已被 eBPF 体系取代。Ubuntu 下安装繁琐（systemtap 包 + debuginfo），一般不推荐新项目使用。

### 8. 探针类型：kprobe / uprobe / tracepoint

```text
kprobe     —— 内核函数动态探针（任意内核函数入口/出口，如 vfs_read）
uprobe     —— 用户态函数动态探针（任意用户程序函数，如 nginx 的 ngx_http_process_request）
tracepoint —— 内核预埋的静态事件点（如 syscalls:sys_enter_openat，稳定 ABI，推荐优先）
区别：tracepoint 稳定且开销最小；kprobe/uprobe 可挂任意函数但依赖符号名，内核版本升级可能失效
```

## 工作原理

### strace 的 ptrace 原理

strace 依赖内核的 ptrace 机制：strace 用 `ptrace(PTRACE_ATTACH)` 附加到目标进程，之后目标进程每次进入/退出系统调用时，内核会暂停它并通知 strace，strace 读取系统调用号、参数和返回值，再放行进程继续。

```text
strace 原理：
ptrace(PTRACE_ATTACH) 附加进程 → 目标每次进出系统调用内核暂停并通知 strace
→ strace 读取调用号/参数/返回值 → 放行进程继续
追踪要点：关注「关键调用 + 返回值」，失败的系统调用返回负错误码（-ENOENT = 文件不存在）
```

系统调用追踪的核心是「发起什么系统调用 → 参数 → 返回值」：程序卡住（卡在 read 等数据/connect 等连接）、文件打不开（open 返回 ENOENT + 路径）、网络连不上（connect 返回 ECONNREFUSED）。追踪时关注「关键调用 + 返回值」，尤其是失败的系统调用。

### strace 输出结构

```text
strace 输出格式（每行一次系统调用）：
read(3, "hello\n", 1024) = 6
│   │       │          │    └── 返回值（6 字节 / -1 错误码）
│   │       │          └── 缓冲区大小
│   │       └── 传入数据
│   └── fd（文件描述符 3）
└── 系统调用名
```

### ftrace 的 tracefs 原理

ftrace 通过 tracefs 伪文件系统（`/sys/kernel/tracing/`）交互：向 `current_tracer` 写追踪器名（如 `function_graph`）开启追踪，追踪结果写入 `trace` 文件，`available_filter_functions` 列出所有可追踪的内核函数（本机实测 **100375 个**），事件目录 `events/` 下列出全部 tracepoint。

### perf 的采样原理

perf 利用 CPU 硬件性能计数器（PMU），按固定频率（默认 4000Hz）周期性打断 CPU，记录当前执行的 PC（程序计数器）和调用栈，统计「每个函数被采到的次数占比」。采样有统计误差——采样次数足够多（万级）才可信。

### eBPF 的工作原理

```text
eBPF 程序生命周期：
1. 用户态写 BPF 字节码（bpftrace/bcc 编译）
2. 内核 verifier 校验（内存安全、有界循环、指令数受限）
3. JIT 编译成本机指令
4. 挂载到 hook 点（kprobe/uprobe/tracepoint/socket 层）
5. 事件触发时执行，通过 map/perf ring buffer 回传数据
安全保证：verifier 拒绝危险程序，出错只影响该探针，不会搞崩内核
```

### 追踪开销对比

```text
追踪工具开销对比（经验值）：
strace     —— 每个系统调用暂停-记录-放行，程序变慢 10~100 倍（最重）
ltrace     —— 类似 strace，库函数级，开销同样显著
lsof       —— 只读 /proc 快照，开销极小
perf top   —— 硬件计数器采样，开销约 1%~5%，可长期运行
perf record—— 采样 + 记录调用栈，开销略高于 perf top
ftrace     —— 内核函数级，function tracer 开销小，function_graph 较大
bpftrace   —— eBPF 事件驱动，只处理匹配事件，开销极低（微秒级）
```

**结论**：strace 是「重武器」——定位精确但开销巨大（10-100 倍减速），生产环境必须限时采样；perf 采样和 bpftrace 低开销，适合生产长期观测。

## 常用命令与配置

### strace 全参数

```shell
strace ls                        # 追踪整个程序的系统调用
strace -p 1234                   # 追踪运行中的进程（附加）
strace -f ls                     # 追踪子进程（-f fork，多进程程序必加）
strace -ff -o log ./myapp        # 每个进程单独一个日志文件（log.PID）
strace -e trace=file ls          # 只看文件相关（open/stat/unlink...）
strace -e trace=network curl example.com   # 只看网络相关（connect/sendto...）
strace -e trace=process ./myapp  # 只看进程相关（fork/exec/exit...）
strace -e trace=read,write ./myapp         # 只看指定调用
strace -c ls                     # 统计系统调用（次数/耗时/错误数）
strace -t ls                     # 带时间戳（秒）
strace -tt -T -o trace.log ./myapp  # 带微秒时间戳 + 每调用耗时 + 输出到文件
strace -s 256 ./myapp            # 加大字符串显示长度（默认 32 字节）
strace -p PID -f -tt -T -o /tmp/trace.log   # 生产附加推荐组合：限时运行后 kill
```

### ftrace 操作

```shell
# 开启 function_graph 追踪（需要 root）
echo function_graph > /sys/kernel/tracing/current_tracer
echo 1 > /sys/kernel/tracing/tracing_on
# 触发要观察的操作，然后：
head -50 /sys/kernel/tracing/trace        # 查看追踪结果
# 关闭并复位
echo 0 > /sys/kernel/tracing/tracing_on
echo nop > /sys/kernel/tracing/current_tracer
```

### bpftrace 一行脚本集

```shell

bpftrace -e 'tracepoint:syscalls:sys_enter_execve { printf("%s %s\n", comm, str(args->filename)); }'  # 谁在启动进程

bpftrace -e 'tracepoint:tcp:tcp_connect { printf("%s -> %s:%d\n", comm, ntop(args->saddr), args->dport); }'  # TCP 连接
bpftrace -e 'tracepoint:syscalls:sys_enter_write { @[comm, str(args->buf, 20)] = count(); }'  # 谁在写什么内容
```

## 配置文件解析

### tracefs（ftrace 的「配置文件」）

ftrace 无传统配置文件，全部通过 `/sys/kernel/tracing/`（tracefs）下的伪文件交互：

```text
/sys/kernel/tracing/ 关键文件：
current_tracer        —— 当前追踪器（nop/function/function_graph/...）
available_tracers     —— 可用的追踪器列表
available_filter_functions —— 可追踪的内核函数列表（本机实测 100375 个）
events/               —— tracepoint 事件目录（events/syscalls/ 等）
trace                 —— 追踪结果缓冲区（读它拿数据）
tracing_on            —— 追踪总开关（1 开 0 关）
kprobe_events         —— 动态 kprobe 定义
instances/            —— 独立追踪实例（互不干扰）
```

```text
# 实测（本机）——tracefs 状态
$ cat /sys/kernel/tracing/available_tracers
timerlat osnoise hwlat blk mmiotrace function_graph wakeup_dl wakeup_rt wakeup function nop
$ cat /sys/kernel/tracing/current_tracer
nop
$ ls /sys/kernel/tracing/events/ | head -12
alarmtimer  amd_cpu  asoc  avc  block  bpf_test_run  bpf_trace  bridge
btrfs  capability  cfg80211  cgroup
$ grep -c . /sys/kernel/tracing/available_filter_functions
100375
# function_graph/wakeup 等追踪器均可用；events/ 下有丰富的 tracepoint 类别
```

### 影响追踪权限的内核参数

```text
/proc/sys/kernel/yama/ptrace_scope —— YAMA 安全模块限制「谁能 ptrace 谁」
  0 = 任意进程可被追踪（最宽松）
  1 = 仅父子进程（默认，本机实测值）
  2 = 仅 root
  3 = 完全禁止（内核编译期选项，运行期不可调）

# 实测（本机）
$ cat /proc/sys/kernel/yama/ptrace_scope
1
```


### 调试符号（debuginfo）

追踪/调试要看到「函数名」而不是裸地址，需要调试符号：

```text
Ubuntu:   配置 ddebs 源后 apt install <包>-dbgsym；内核符号在 linux-image-$(uname -r)-dbgsym
Red Hat:  dnf debuginfo-install <包名>；内核符号 kernel-debuginfo-$(uname -r)
没有符号时：perf top 显示 [unknown] 裸地址，uprobe 无法按函数名挂载（可用偏移量挂载）
```

## 应用场景实战

### 场景一：追踪 nginx worker 的 accept/read/write

```shell
# 1. 找到 nginx worker 进程
ps aux | grep 'nginx: worker'
# 2. 追踪网络相关系统调用（accept 连接、读请求、写响应）
strace -p <worker_PID> -e trace=accept,accept4,read,write -tt -T -o /tmp/nginx_trace.log
# 3. 触发一次请求后停止追踪（Ctrl+C），分析输出
```

```text
# 实测（本机）——本机 nginx 正在监听 80，worker 进程列表
$ ss -tlnp | grep :80
LISTEN 0 511 0.0.0.0:80 0.0.0.0:* users:(("nginx",pid=565634,fd=5),("nginx",pid=1406300,fd=5),...)
# 输出会显示：accept4() 返回新连接 fd → read(fd, "GET / HTTP/1.1...") 读请求
# → write(fd, "HTTP/1.1 200 OK...") 写响应 → close(fd)
# 关注点：read 返回 0（连接关闭）、accept4 返回 EAGAIN（无新连接，正常轮询）
```

### 场景二：strace -c 统计热点系统调用

```shell
# 程序慢，先看「时间花在哪个系统调用」
strace -c ./myapp
# 再看具体耗时分布
strace -T -e trace=read,write ./myapp 2>&1 | awk '$NF > 0.1 {print}'   # 找出耗时 >100ms 的调用
```

```text
定位思路：
1. calls 列很大 —— 调用次数异常（如疯狂 read 1 字节 = IO 碎片化）
2. seconds 列很大 —— 单次调用慢（如 read 卡在网络/磁盘）
3. errors 列很大 —— 大量失败调用（如 open ENOENT 反复探测、connect 超时）
4. 典型病案：频繁 poll 空转（等事件无事发生）、getdents64 大量小目录读取、mmap 反复映射
```

### 场景三：附加运行中进程排查「假死」

```shell
# 程序日志不再输出、接口无响应但进程还在（假死）
strace -p <PID> -f -tt -T -o /tmp/hang.log
# 等几秒后 kill strace（Ctrl+C），看输出末尾停在哪个系统调用
```

```text
假死定位口诀：
read(3, ...)    卡住 —— 在等数据（网络/管道/终端没人发数据）
connect(...)    卡住 —— 在等连接建立（目标不可达/防火墙丢包/半连接队列满）
poll/select/epoll_wait 卡住 —— 在等事件（正常等待 vs 异常空等需结合超时参数判断）
futex(...)      卡住 —— 线程在等锁（死锁/锁竞争）
write(...)      卡住 —— 写阻塞（管道对端不读/磁盘 IO 挂起）
```

```text
# 实测（本机）——strace -f 附加 curl 子进程（DNS 解析阶段）
$ strace -f -e trace=connect curl -s -m 3 https://example.com -o /dev/null
connect(3, {sa_family=AF_UNIX, sun_path="/var/run/nscd/socket"}, 110) = -1 ENOENT
connect(3, {sa_family=AF_UNIX, sun_path="/var/run/nscd/socket"}, 110) = -1 ENOENT
strace: Process 3116717 attached
[pid 3116717] connect(7, {sa_family=AF_UNIX, sun_path="/var/run/nscd/socket"}, 110) = -1 ENOENT
[pid 3116717] connect(7, {sa_family=AF_INET, sin_port=htons(53), sin_addr=inet_addr("127.0.0.53")}, 16) = 0
# 解读：先探测 nscd（ENOENT 属正常探测），实际走 127.0.0.53:53
# （systemd-resolved 本地 DNS 缓存）解析，-f 正确追踪到了 fork 出的子进程
```

### 场景四：lsof 定位「删了但没释放」的文件

```shell
# 磁盘 df 显示满，但 du 找不到大文件 —— 大概率有进程占着已删除文件
lsof +L1                 # 列出所有 deleted 但仍被打开的文件
ls -l /proc/*/fd 2>/dev/null | grep deleted
# 找到后：重启该进程释放（或 kill），空间立即回收
```

```text
原理：进程 open 一个文件后，文件被 unlink，但进程的 fd 仍指向该 inode——
磁盘空间要等进程关闭 fd 才释放。df 看的是 inode 占用（还满），du 按文件名统计（找不到）。
这是「df 满但 du 找不到」的经典原因。
```

### 场景五：ftrace 看内核函数调用链

```shell
# 以追踪 do_sys_open（内核打开文件路径）为例
echo function_graph > /sys/kernel/tracing/current_tracer
echo do_sys_open > /sys/kernel/tracing/set_ftrace_filter   # 只追踪该函数
echo 1 > /sys/kernel/tracing/tracing_on
ls /tmp >/dev/null        # 触发一次文件访问
echo 0 > /sys/kernel/tracing/tracing_on
head -40 /sys/kernel/tracing/trace
echo nop > /sys/kernel/tracing/current_tracer               # 复位
```

### 场景六：bpftrace 一行脚本实战集

```shell
# 1. 谁在频繁打开文件（配合「文件打开失败」排查）
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm, str(args->filename)] = count(); }'
# 2. 谁在启动新进程（配合「进程频繁重启」排查）
bpftrace -e 'tracepoint:syscalls:sys_enter_execve { printf("%s exec: %s\n", comm, str(args->filename)); }'
# 3. 统计系统调用频率 TOP10
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }' | sort -t' ' -k3 -rn | head
# 4. 追踪 TCP 连接建立
bpftrace -e 'tracepoint:tcp:tcp_connect { printf("%s -> %s:%d\n", comm, ntop(args->saddr), args->dport); }'
# 5. 查看某用户态函数的调用频率（uprobe，需函数符号）
bpftrace -e 'uprobe:/usr/sbin/nginx:ngx_http_process_request { @[comm] = count(); }'
```

## 性能与调优

### 追踪开销管理

追踪工具是「用性能换可见性」，必须清楚代价：

```text
strace    —— 每个系统调用都要 ptrace 暂停-记录-放行，程序慢 10~100 倍
            生产环境附加：限时采样（-tt -T -o 文件，跑 10~30 秒就 kill）
ltrace    —— 同类开销，且需要符号，更少用于生产
perf      —— 硬件计数器采样，开销约 1%~5%，可长时间运行（生产可接受）
ftrace    —— function 追踪器开销小；function_graph 记录调用图开销大，短时用
bpftrace  —— eBPF 事件驱动 + 内核侧聚合，只回传聚合结果，开销极低（生产推荐）
lsof      —— 只读 /proc 快照，开销可忽略
```

```text
生产环境追踪红线：
1. strace 生产进程限时采样，最多几十秒，别挂一晚上
2. 优先 bpftrace/perf 这类低开销工具做生产观测
3. 追踪前评估目标进程的 syscall 频率（高 IO 进程 strace 后果最严重）
4. 先 -c 统计再决定要不要 -T 看耗时，别一上来全量输出
5. 追踪结果落文件，别让输出直接打满终端/日志盘
```

### 调优思路：从「慢」到「定位」

```text
1. 先粗后细：top → perf top（CPU 热点）→ 需要时 strace -c（syscall 热点）
2. strace -T 找慢调用：read/write 慢 = IO 问题；connect 慢 = 网络问题
3. strace -c 找多调用：调用次数异常 = 逻辑问题（反复 open/stat/轮询）
4. 内核层深入用 ftrace/bpftrace，用户态热点用 perf
5. 火焰图可视化：perf record -g + FlameGraph，一眼看出瓶颈调用链
```

## 安全与权限

```text
1. ptrace_scope —— YAMA 安全模块限制「谁能 ptrace 谁」，默认 1（只能追踪子进程）
2. 追踪别的用户的进程需要 root —— ptrace 有权限限制，非 root 只能追自己的进程
3. strace 会暴露敏感数据 —— 系统调用的参数/缓冲区内容（密码、token）会打出来，输出文件要防泄露
4. 生产环境谨慎追踪 —— strace 有性能开销，限时采样，别长时间挂生产进程
5. bpftrace 需要 root —— eBPF 程序加载需要 CAP_BPF/CAP_SYS_ADMIN 等权限
6. 追踪数据脱敏 —— trace 文件可能含用户数据（文件内容片段、URL、请求体），存放与分享注意脱敏
7. uprobe 注入有风险 —— 在生产二进制上挂 uprobe 前先在小流量验证，避免符号/偏移错误
```

## 故障排查

### 子案例一：strace 报 ptrace 权限不足

```text
症状：strace -p <别人的进程> 报 ptrace: Operation not permitted / Permission denied
排查：cat /proc/sys/kernel/yama/ptrace_scope（本机实测为 1，仅父子进程）
原因：YAMA 安全模块默认禁止跨进程追踪（非父子关系、非 root）
解决：root 执行；或用 sudo 提权；特殊场景临时 echo 0 > /proc/sys/kernel/yama/ptrace_scope
      （临时放开，用完恢复；生产环境优先用 systemd 的 service 内嵌追踪或容器内同权限）
```

### 子案例二：strace 全量输出刷屏找不到重点

```text
症状：strace ./myapp 输出几万行，找不到关键调用
原因：没过滤，程序系统调用太多（启动期加载库就几百次 open）
解决：
  1. -e trace=file / network / process 按类别过滤
  2. -c 先统计，看哪类调用异常再针对性 -e trace=xxx
  3. -ff -o log 每个进程分文件，避免多进程输出交错
  4. grep 失败返回值：strace -e trace=openat ./myapp 2>&1 | grep -i '= -1'
```

### 子案例三：strace 生产进程导致性能下降

```text
症状：strace -p 生产进程后，服务 RT 明显上升
原因：strace 每个系统调用都暂停进程，高 syscall 频率进程会被拖慢 10 倍以上
解决：
  1. 立即 kill strace 恢复服务
  2. 换低开销方案：perf top（采样）/ bpftrace（eBPF）/ execsnoop-bpfcc
  3. 必须 strace 时：限时采样（-tt -T -o 文件，跑 10~30 秒），选低峰期
  4. 事后复盘：追踪前先评估进程 syscall 频率（vmstat 的 sy 列）
```

### 子案例四：perf/bpftrace 报权限不足或无符号

```text
症状：perf top 报 Permission denied；或 perf top 里全是 [unknown]
原因1：perf_event_paranoid 限制非特权采样（/proc/sys/kernel/perf_event_paranoid > 1）
解决1：sudo perf；或 sysctl kernel.perf_event_paranoid=1（临时调整）
原因2：没有调试符号，内核/程序符号解析不出函数名
解决2：Ubuntu 装 linux-image-$(uname -r)-dbgsym；Red Hat 系 dnf debuginfo-install kernel
      用户态程序装对应 -dbgsym/-debuginfo 包
```

## 常见问题

```text
Q1: strace 和 ltrace 都追踪，有什么区别？
A: strace 追踪系统调用（内核接口），ltrace 追踪库函数调用（libc 接口）。strace 覆盖大部分关键行为，日常优先用。

Q2: strace 输出里的 ENOENT 是错误吗？
A: 不一定。很多 ENOENT 是程序「探测文件在不在」的正常行为（如查找库文件路径、探测 nscd 是否存在）。要关注关键调用的返回值，区分探测性失败和真实错误。

Q3: 程序卡住了怎么用 strace 定位？
A: strace -p <PID> 附加进程，看输出末尾停在哪个系统调用：read 卡住=等数据，connect 卡住=等连接，poll 卡住=等事件，futex 卡住=等锁。

Q4: strace 会影响被追踪程序的性能吗？
A: 会。每个系统调用都要暂停-记录-放行，有显著开销（10~100 倍减速）。生产环境限时采样或先用 -c 统计，或换 perf/bpftrace 低开销方案。

Q5: lsof 显示文件 "deleted" 是什么意思？磁盘空间会回来吗？
A: 表示文件已被删除但仍有进程持有 fd，空间被 inode 占用，df 显示满、du 找不到。重启/关闭该进程后空间才释放。用 lsof +L1 定位。

Q6: bpftrace 和 strace 什么关系，能替代吗？
A: 都是追踪工具但定位不同：strace 追踪「单个进程的系统调用」最直观（含参数和返回值）；bpftrace 是系统级事件追踪（任意进程、内核函数、用户函数），开销低但需要写探针脚本。查单个进程行为用 strace，查系统级模式用 bpftrace。

Q7: ftrace 和 perf 都能看内核函数，怎么选？
A: ftrace 是内核自带、零依赖，看「函数调用序列/调用图」最直接（function_graph）；perf 侧重「采样统计哪个函数耗 CPU 多」。内核行为序列问题用 ftrace，热点统计用 perf。
```

## 面试题

```text
1. strace 的底层原理是什么？
   答：基于内核 ptrace 机制，附加到目标进程后，每次进出系统调用内核暂停目标并通知 strace，strace 记录系统调用号、参数和返回值。还可以用 -c 做统计、-T 看耗时。

2. 一个进程卡住不动，你怎么定位它在等什么？
   答：strace -p <PID> 附加，看输出末尾停在哪个系统调用——read 等数据、connect 等连接、poll 等事件、futex 等锁，据此判断卡点。注意结合 -f 追踪子进程，避免漏掉 fork 出的工作进程。

3. strace 和 perf 定位性能问题有什么分工？
   答：perf 定位 CPU 热点（哪个函数耗 CPU），strace -c/-T 定位系统调用热点（哪个 syscall 最多/最耗时）。一个看函数、一个看调用。开销上 perf 采样低、strace 高，生产优先 perf/bpftrace。

4. 为什么 strace 追踪别人的进程会 Permission denied？
   答：ptrace 有权限限制（YAMA 安全模块 ptrace_scope，默认 1 仅父子进程）。追踪其他用户的进程需要 root，或调整 /proc/sys/kernel/yama/ptrace_scope。

5. kprobe、uprobe、tracepoint 有什么区别？生产上优先用哪个？
   答：kprobe 挂内核函数动态探针、uprobe 挂用户态函数、tracepoint 是内核预埋静态事件点。tracepoint 有稳定 ABI、开销最小，能覆盖的场景优先用；需要追踪任意函数时用 kprobe/uprobe，但要意识到符号可能随版本变化。

6. 磁盘显示满但 du 找不到大文件，怎么排查？
   答：大概率是「删除但未释放」的文件：lsof +L1 列出 deleted 文件，找到持有进程后重启/关闭它，空间释放。原理：fd 仍指向已 unlink 的 inode，df 按 inode 统计仍满，du 按文件名统计找不到。

7. 生产环境怎么安全地使用追踪工具？
   答：先评估开销（strace 最重，限时采样；perf/bpftrace 低开销）；追踪结果落文件并脱敏；附加生产进程前确认权限（ptrace_scope/root）；追踪窗口选低峰期；用完立即恢复并检查服务指标无异常。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 程序卡住/失败先 strace，看它在等哪个系统调用
2. 用 -e trace=xxx 过滤（file/network/process），别全量看刷屏
3. 多进程程序必须加 -f（或 -ff -o 分文件），否则只看到主进程
4. 追踪运行中进程用 strace -p PID，不重启程序
5. 性能定位用 strace -c 统计 + -T 看耗时，先粗后细
6. strace 有性能开销，生产环境限时采样，优先 bpftrace/perf
7. lsof 三件套：-i 反查端口、+L1 找 deleted 文件、+D 查目录占用
8. ftrace 用完必须复位（echo nop > current_tracer），避免一直开着耗资源
9. bpftrace 一行脚本先小范围验证（filter 限定 comm），再放开全系统

### 踩坑记录

```text
坑 1：strace 全量输出太大看不过来
结论：strace 程序刷屏，找不到重点。
原因：没过滤，程序系统调用太多（启动期仅加载库就有数百次调用）。
解法：strace -e trace=xxx 过滤，或 -c 统计看重点，或 grep '= -1' 只看失败。

坑 2：strace 生产进程导致性能下降
结论：strace -p 生产进程，服务变慢。
原因：strace 跟踪每个系统调用，有显著开销（10~100 倍）。
解法：限时采样（strace -p PID -f -tt -T -o 文件，跑一会就 kill），或先 -c，或换 perf/bpftrace。

坑 3：把探测性失败（ENOENT）当真错误
结论：strace 看到一堆 ENOENT 就以为程序有问题。
原因：很多 ENOENT 是程序「探测文件在不在」的正常行为（如查库路径、探测 nscd）。
解法：关注「关键调用 + 返回值」，区分探测性失败和真实错误。

坑 4：strace 报 ptrace 权限不足
结论：strace -p 别的用户的进程报 Permission denied。
原因：ptrace 有权限限制（YAMA 安全模块 ptrace_scope 默认 1）。
解法：root 执行，或调整 /proc/sys/kernel/yama/ptrace_scope（临时，用完恢复）。

坑 5：ltrace 不存在就以为不能追踪库函数
结论：ltrace 报 command not found。
原因：ltrace 不是默认安装。
解法：apt install ltrace（Ubuntu）/ dnf install ltrace（Red Hat），或先用 strace（覆盖大部分场景）。

坑 6：多进程程序没加 -f，只看到主进程
结论：strace ./myapp 只见主进程的调用，工作进程的行为完全看不到。
原因：myapp fork 出的子进程默认不被追踪。
解法：strace -f 跟随子进程；-ff -o log 每个进程单独文件，避免输出交错。

坑 7：ftrace 开着忘复位，一直耗资源
结论：function_graph 追踪开启后忘记关闭，系统变慢、trace 缓冲区狂写。
原因：追踪器持续记录所有匹配函数调用。
解法：用完立刻 echo nop > current_tracer 复位；脚本里用 trap 保证退出时复位。

坑 8：perf top 全是 [unknown] 看不出函数
结论：perf 采样结果全是地址，没有符号名。
原因：没有安装调试符号（内核 dbgsym/debuginfo、程序 -dbgsym 包）。
解法：Ubuntu 装 linux-image-$(uname -r)-dbgsym 及程序 dbgsym 包；Red Hat 用 dnf debuginfo-install。

坑 9：bpftrace 脚本一上来就跑全系统
结论：脚本没加过滤，输出爆炸 + 在无关进程上浪费资源。
原因：PROBE 没限定 /comm == "xxx"/ 过滤条件。
解法：先加 comm/pid 过滤小范围验证，再逐步放开；用 @map + count() 聚合代替逐条 printf。

坑 10：lsof 查端口没输出就断定端口没监听
结论：lsof -i :8080 无输出，以为服务没起，其实服务在监听。
原因：lsof 需要权限看所有进程的 fd，非 root 只能看到自己的进程。
解法：用 root/sudo 执行；或交叉验证 ss -tlnp（内核视角，无权限问题）。
```
