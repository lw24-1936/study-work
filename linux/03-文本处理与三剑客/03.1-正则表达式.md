## 概述

正则表达式是描述字符串模式的语法，也是 grep、sed、awk 三剑客共用的匹配引擎。核心就六类语法：元字符、字符类、量词、锚点、分组、交替——掌握这六类就能写出精确的匹配模式。Linux 里正则分三种方言：BRE（基础正则，grep/sed 默认）、ERE（扩展正则，grep -E / sed -r）、PCRE（Perl 兼容正则，grep -P，功能最强）。先记住三剑客各自默认用哪种，写的时候才不踩「该转义没转义」的坑。

```text
三种正则方言：
1. BRE 基础正则 —— grep/sed 默认，+ ? | ( ) { } 都要加反斜杠转义才生效
2. ERE 扩展正则 —— grep -E / sed -r / awk，元字符直接写不用转义
3. PCRE Perl 正则 —— grep -P，额外支持 \d \w \s 及前瞻后瞻等高级特性
```

任何复杂正则都能拆成四类零件：**原子**（普通字符、`.`、字符类）、**量词**（决定重复几次）、**位置**（`^ $ \b` 锚点）、**结构**（分组 `()` 和交替 `|`）。写之前先想清楚「我要匹配什么原子、重复几次、从哪个位置开始」，比上来就堆元字符快得多。

本文所有「实测」块的版本基线（本机 Ubuntu 24.04.4 LTS / kernel 7.0.0-28-generic，采集于 2026-09-12）：

```text
$ grep --version | head -1
grep (GNU grep) 3.11
$ sed --version | head -1
sed (GNU sed) 4.9
$ awk --version
mawk 1.3.4 20240123
$ rg --version | head -1
ripgrep 14.1.0
$ locale | head -3
LANG=zh_CN.UTF-8
LANGUAGE=
LC_CTYPE="zh_CN.UTF-8"
```

版本很重要：`\d` 这类简写、`-P` 前瞻后瞻的边界、locale 下的字符语义，都会随实现和版本变化。**下面的断言一律以这份基线为准，换机器请先自己 `grep --version` / `awk --version` 复核。**

### 三种方言的对照表

选方言是第一决策，选错了后面全是坑。下表是本机实测过的事实（逐条证据在「核心概念」和「配置文件解析」里）：

| 方言 | 谁在用 | 元字符 `+ ?` | 括号与花括号 | `\d \w \s` | 前瞻 / 后瞻 | 匹配引擎 |
|---|---|---|---|---|---|---|
| BRE | grep 默认、sed 默认 | 需要转义 `\+ \?` | 需要转义 `\( \) \{ \}` | `\w \s` 可用（GNU 扩展）、`\d` 不可用 | 不支持 | GNU grep 的混合引擎，线性时间 |
| ERE | grep -E、sed -E / sed -r、awk | 不需要转义 | 不需要转义 | `\w \s` 可用（GNU 扩展）、`\d` 不可用 | 不支持 | 同上，线性时间 |
| PCRE2 | grep -P | 不需要转义 | 不需要转义 | 全部可用 | 支持 | NFA 回溯，可能指数级退化 |

```text
选方言的三条实用规则：
1. 默认用 ERE —— grep -E / sed -E / awk，元字符不用转义，可读性和正确率最高
2. 要 \d \s 简写、前瞻后瞻、非贪婪 ? 才用 grep -P（PCRE2，代价是回溯风险与平台可得性）
3. 只有维护老脚本、或明确要跟 POSIX BRE 对齐时才写裸 BRE
```

```text
一个反直觉但实测确认的点（GNU grep 3.11）：
$ echo 'a1' | grep -E '\d' ; echo $?
1                      # 不匹配！GNU grep 的 ERE 里 \d 不是数字类
$ echo 'd'  | grep -oE '\d'
d                      # \d 被当成字面字符 d
$ echo 'a1' | grep -oP '\d'
1                      # 只有 -P 才是「数字」
$ echo 'a1_' | grep -oE '\w+'
a1_                    # 而 \w 在 ERE 里确实可用
$ printf 'a\tb\n' | grep -cE '\s'
1                      # \s 在 ERE 里也可用
```

结论：GNU grep 把 `\w`、`\W`、`\s`、`\S`、`\b`、`\B` 当扩展接受（BRE/ERE 都认），但**唯独不认 `\d`** —— `\d` 只在 `grep -P` 下才是数字类。很多教程把「GNU grep 支持 `\d`」写成通用结论，是错的。

### 跨发行版差异（Red Hat / CentOS / RHEL vs Debian / Ubuntu）

正则语法本身是 POSIX 标准，跨发行版真正会变的不是语法，而是**「默认装的实现 + 默认的 locale + /bin/sh 是谁」**这三件事。写要在两台机器都跑的脚本前，先看这四条：

```text
1. 默认 awk 不是一个实现
   Red Hat / CentOS / RHEL 系默认装 gawk（GNU awk）；
   Debian / Ubuntu 系默认装 mawk。
   本机实测（Ubuntu 24.04）：
     $ awk --version
     mawk 1.3.4 20240123
     $ command -v gawk      （无输出，未安装）
   后果：gawk 专有扩展（gensub / asort / asorti / IGNORECASE / FPAT / --csv / match(s,r,arr) 第三参数）
        在 Ubuntu 默认 awk 下直接不可用，报错形如：
     $ awk 'BEGIN{print gensub(/a/,"b","g","aaa")}'
     awk: line 2: function gensub never defined
     $ awk 'BEGIN{a[1]=3;a[2]=1;n=asort(a);print n}'
     awk: line 2: function asort never defined
     $ awk 'BEGIN{IGNORECASE=1; print ("ABC" ~ /abc/) ? "matched" : "not-matched"}'
     not-matched                                        # IGNORECASE 被静默忽略
     $ awk 'BEGIN{ if (match("abc123", /[0-9]+/, m)) print m[0]; else print "no" }'
     awk: line 1: syntax error at or near ,             # match 第三参数也不支持
   写法：文档里凡出现 gawk 扩展，都要标「gawk 专有」，缺 gawk 时用 sudo apt install gawk
        （Red Hat 系：sudo dnf install gawk）安装，或改用 POSIX 等价写法。
2. /bin/sh 不是同一个 shell
   Debian / Ubuntu 的 /bin/sh 指向 dash，Red Hat / CentOS 指向 bash。
   本机实测：
     $ readlink -f /bin/sh
     /usr/bin/dash
   后果：`[[ "$s" =~ 正则 ]]` 是 bash 专属写法，在 #!/bin/sh（dash）下直接语法报错；
        dash 也不支持 bash 的数组、`=~`、部分扩展 glob。
   写法：#! 行显式写 #!/bin/bash，或只用 POSIX 的 case/glob 做模式匹配。
3. locale 默认值不一样
   RHEL / CentOS minimal 安装常是 LANG=C（或 en_US.UTF-8），
   Ubuntu 桌面中文环境默认 zh_CN.UTF-8（本机实测 LANG=zh_CN.UTF-8）。
   后果：[a-z] 的范围解释、grep -i 的大小写折叠、. 按字节还是按字符，全都随 locale 变化 ——
        同一个正则脚本在两台机器上给出不同结果（本节的 locale 实测块有完整证据）。
   写法：要跨机器稳定就显式 LC_ALL=C；要正确处理中文/多语言文本就保持 UTF-8 locale，别一刀切。
4. grep -P 的可得性不一样
   GNU grep 的 -P 依赖编译时的 PCRE2 支持，主流发行版的 grep 包都带（本机 grep 3.11 的 -P 实测可用）；
   但 busybox grep（Alpine、大量精简容器镜像）没有 -P、没有 --include、没有 -z；
   RHEL / CentOS 7 自带的 GNU grep 是 2.20（较老），RHEL 8/9 已是 3.x。
   写法：教学示例优先 BRE/ERE，PCRE 单独标注「依赖 -P」；容器内排查前先 grep --version 确认。
```

注：第 1、2 条是两大发行版系的**默认行为**差异，第 4 条里 RHEL 各版本的具体版本号未在本机实测（本机是 Ubuntu 24.04），以上按发行版默认包参考，写脚本前以目标机器的 `--version` 输出为准。

## 核心概念

正则的语法骨架就是下面七块，掌握它们就能拼出任意模式。本文示例统一用 `/tmp/demo.txt` 作样本，先准备一份模拟日志：

```shell
cat > /tmp/demo.txt <<'EOF'
2026-08-18 10:00:01 INFO  user=alice action=login  ip=10.0.0.1
2026-08-18 10:00:05 ERROR user=bob   action=query  ip=10.0.0.2
2026-08-18 10:01:00 WARN  user=carol action=login  ip=10.0.0.3
2026-08-18 10:01:10 ERROR user=alice action=upload ip=10.0.0.1
2026-08-18 10:02:00 INFO  user=dave  action=logout ip=10.0.0.4
2026-08-18 10:02:30 ERROR user=eve   action=login  ip=10.0.0.5
EOF
```

### 元字符与字符类

元字符是有特殊含义的符号，字符类用来匹配「某一类字符」。最常用的元字符：`.` 匹配任意单字符、`*` 前一字符重复零次或多次、`^ $` 行首行尾、`[]` 字符类、`\` 转义、`()` 分组、`|` 交替。字符类 `[0-9]` 匹配数字、`[a-zA-Z]` 匹配字母、`[^0-9]` 取反匹配非数字。组合起来就能描述「一个 IP 地址」这类模式。

```text
元字符速查：
1. .   任意单字符；   * 前一字符 0 次或多次
2. []  字符类，[0-9] 数字、[^0-9] 取反；  - 在 [] 里表范围
3. ^ $ 行首 / 行尾锚点；   \ 转义，让元字符变字面量
4. ()  分组捕获；   | 交替（或）
```

```text
字符类三种写法：
1. 枚举   [abc] —— a、b、c 任一
2. 范围   [0-9] [a-z] [A-Z] [0-9a-fA-F]（十六进制）
3. 取反   [^0-9] —— 非数字
POSIX 字符类（与 locale 无关，跨机器结果一致）：
[[:digit:]] 数字  [[:alpha:]] 字母  [[:alnum:]] 字母数字
[[:space:]] 空白  [[:upper:]]/[[:lower:]] 大小写  [[:punct:]] 标点
PCRE 简写（grep -P）：
\d 数字=[0-9]   \w 单词字符=[a-zA-Z0-9_]   \s 空白=[ \t\n\r\f]
```

```text
匹配字面量元字符要转义：\. \* \[ \] \+ \? \( \) \|
要匹配字面 . 写 \.，要匹配字面 [ 写 \[。
固定字符串匹配用 grep -F，完全跳过正则引擎（. 就是 .，不是任意字符）。
```

```shell
# 用字符类 + 量词提取 IP 地址
grep -Eo '[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+' /tmp/demo.txt | sort -u
```

```text
# 实测
10.0.0.1
10.0.0.2
10.0.0.3
10.0.0.4
10.0.0.5
# [0-9]+ 匹配连续数字，\. 匹配字面点号——四段拼成一个 IP 模式
```

```shell
# 用 [A-Z]+ 提取日志级别，配合 -o 只输出匹配片段
grep -oE '[A-Z]+' /tmp/demo.txt | sort | uniq -c
```

```text
# 输出（按级别统计各出现几次）
      3 ERROR
      2 INFO
      1 WARN
```

```text
字符类易错点：
- [a-z] 在 C locale 下只匹配 26 个 ASCII 小写字母；要覆盖带重音字符用 [[:lower:]]
- - 在 [] 中间表范围，放开头或结尾才是字面量：[-az] 匹配 -、a、z
- ^ 在 [] 开头表取反，放中间是字面量：[a^b] 匹配 a、^、b
- ] 要当字面量得放开头：[]a] 匹配 ]、a
```

### 字符类与 locale（实测定量）

同一份模式在 `LC_ALL=C` 和 UTF-8 locale 下匹配到的东西可能完全不同，这是正则里最容易「一台机器对、另一台错」的地方。本机默认 `LANG=zh_CN.UTF-8`（`locale` 输出见概述的版本基线块），下面四组是当场实跑的结果。

第一组：`[a-z]` 在 UTF-8 locale 下会把带重音的 `é` 也算进范围；C locale 不会。

```shell
printf 'é\n' > /tmp/accent.txt
grep -c '[a-z]' /tmp/accent.txt            # zh_CN.UTF-8（本机默认）
LC_ALL=C grep -c '[a-z]' /tmp/accent.txt   # C locale，按字节
grep -c '[[:lower:]]' /tmp/accent.txt      # POSIX 类：与 locale 无关，行为可预期
```

```text
# 实测
$ grep -c '[a-z]' /tmp/accent.txt
1
$ LC_ALL=C grep -c '[a-z]' /tmp/accent.txt
0
$ grep -c '[[:lower:]]' /tmp/accent.txt
1
```

第二组：`[[:alpha:]]` 在 UTF-8 locale 下把汉字当字母；C locale 下汉字是 3 个非字母字节，匹配不到。

```shell
printf '北京\n' | grep -c '[[:alpha:]]'
printf '北京\n' | LC_ALL=C grep -c '[[:alpha:]]'
```

```text
# 实测
$ printf '北京\n' | grep -c '[[:alpha:]]'
1
$ printf '北京\n' | LC_ALL=C grep -c '[[:alpha:]]'
0
```

第三组：`.` 是按「字符」还是按「字节」匹配，直接决定多字节汉字会不会被拆碎。

```shell
printf '张三\n' > /tmp/cn.txt
grep -o '.' /tmp/cn.txt
LC_ALL=C grep -o '.' /tmp/cn.txt | od -c | head -1
```

```text
# 实测
$ grep -o '.' /tmp/cn.txt
张
三
$ LC_ALL=C grep -o '.' /tmp/cn.txt | od -c | head -1
0000000 345  \n 274  \n 240  \n 344  \n 270  \n 211  \n
# C locale 下一个 . 只吃一个字节，UTF-8 汉字 3 字节 → 输出 6 段孤立字节（od 里的 345/274/240/344/270/211）
# 结论：处理中文必须保持 UTF-8 locale；只有纯 ASCII 场景才用 LC_ALL=C 提速/求稳定
```

第四组：locale 还改变 `sort` 的顺序语义（正则本身不排序，但「提取 + 排序统计」是正则最常见的下游，顺序不一致会让对账结果对不上）。

```shell
printf '张三\n李四\n赵六\n王五\n' > /tmp/f3.txt
sort /tmp/f3.txt
LC_ALL=C sort /tmp/f3.txt
```

```text
# 实测
$ sort /tmp/f3.txt
李四
王五
张三
赵六
$ LC_ALL=C sort /tmp/f3.txt
张三
李四
王五
赵六
# 默认走 zh_CN.UTF-8 的本地化排序（不是拼音，也不等于字节序）；LC_ALL=C 才是确定的字节序
```

```text
locale 相关的三条操作纪律：
1. 脚本里用 [a-z] [0-9] 这类范围，先想清楚「我要的是 ASCII 还是本地字符」；
   要 ASCII 就 LC_ALL=C，要本地语义就用 [[:alpha:]] [[:digit:]] 这类 POSIX 类。
2. 提取中文用 grep -o '正则'，别在 C locale 下用 . 拼多字节字符。
3. 结果要跨机器可比对，就在管道最前面显式 LC_ALL=C（排序、去重、统计都受益）。
```

```text
尚未生成的 locale 不会报错，而是静默落到 C 语义 —— 这是比「报错」更危险的坑：
$ locale -a | head -6
C
C.utf8
POSIX
zh_CN.utf8
zh_SG.utf8
$ LC_ALL=en_US.UTF-8 sort /tmp/f3.txt    # en_US.UTF-8 根本没生成
张三
李四
王五
赵六
# 没有任何报错/告警，但排序已经变成字节序（C 语义）—— 你以为在用 en_US，其实在用 C。
# 对照：perl 遇到同样情况会明确告警
$ LC_ALL=xx_YY.UTF-8 perl -e 'print "ok\n"'
perl: warning: Setting locale failed.
perl: warning: Please check that your locale settings:
# 所以：别用「没报错」判断 locale 生效了，locale -a 里没生成的 locale 名就是无效的。
```

### 量词

量词控制「前一个元素重复几次」。`*` 是零次或多次、`+` 是一次或多次、`?` 是零次或一次、`{n}` 精确 n 次、`{n,}` 至少 n 次、`{n,m}` n 到 m 次。注意量词只作用于紧挨着它的那个元素，想对一组字符起作用要用分组。在 BRE 里 `{}` 要写成 `\{ \}`，ERE 里直接写。

```text
量词速查：
1. * 零次或多次（可为空）；  + 一次或多次（至少一次）
2. ? 零次或一次（可选）；    {n} 恰好 n 次
3. {n,} 至少 n 次；  {n,m} n 到 m 次
```

```shell
# {1,3} 限定数字段 1~3 位（BRE 要转义，ERE 不用）
grep -E '10\.0\.0\.[0-9]{1,3}' /tmp/demo.txt | head -1
```

```text
# 输出：匹配 10.0.0. 后跟 1~3 位数字的行
2026-08-18 10:00:01 INFO  user=alice action=login  ip=10.0.0.1
```

```text
量词易错点：
- 量词只作用于紧挨它的前一个元素：ab+ 匹配「a + 一个或多个 b」，不匹配 abab
- 想重复多个字符要分组：(ab)+ 匹配 ab 重复一次或多次
- 量词默认贪婪（尽量多匹配），后面加 ? 变懒惰，见「贪婪与懒惰」
- {n,m} 的 m 可省略表无上限：{n,} 至少 n 次
```

```shell
# {2} 恰好两次：匹配含连续两个 0 的行
echo '10.00.0.1' | grep -E '0{2}'
# 输出：10.00.0.1（10.00 里的 00 是连续两个 0）
```

```text
量词的三个边界实测（GNU grep 3.11，ERE）：

1. {,3} 不是合法量词 —— 下限必须写出来，缺省下限只支持写成 {0,3}
$ echo '{1,3}' | grep -E '{1,3}'
grep: 警告：表达式以 {...} 开头
{1,3}
# 虽然命中了，但那是因为引擎把它当「字面量 {1,3}」匹配的，同时给出警告。
# 想表达「0 到 3 次」必须写 {0,3}。

2. {0,n} 可以匹配空串 —— 结果往往「全命中」，容易误判成模式写对了
$ echo 'zzz' | grep -E 'a{0,3}'
zzz
# a{0,3} 允许 0 次重复，空串在任意位置都成立，所以任何行都命中。
# 这类模式只能用来做「可选片段」的拼接，不能单独当过滤条件。

3. BRE 里花括号不转义就不是量词
$ echo 'aaa'  | grep 'a\{3\}'
aaa
$ echo 'a{3}' | grep 'a{3}'
a{3}
# 第二条匹配的是字面文本 a{3} —— 这就是「BRE 的 { } 必须转义」的实证。
# 所以维护老 BRE 脚本时，看到裸写的 { } 要意识到它是字面量而不是量词。
```

### 锚点

锚点不匹配字符，只匹配位置。`^` 匹配行首、`$` 匹配行尾，`\< \>`（BRE）或 `\b`（PCRE）匹配单词边界。锚点的价值是「锁定位置」——比如 `^ERROR` 只匹配行首是 ERROR 的行，避免匹配到正文中间出现的 ERROR。日志分析里「统计以某状态码结尾的行」就用 `$`。

```text
锚点速查：
1. ^ 行首；   $ 行尾
2. \< \> 单词边界（BRE/ERE）；   \b 单词边界（PCRE）
3. 典型用法 —— ^ERROR 行首报错、$ 行尾匹配、^$ 空行
```

```shell
# ^ 锁定行首时间前缀，[01] 匹配 10:0 后跟 0 或 1
grep -E '^2026-08-18 10:0[01]' /tmp/demo.txt
```

```text
# 实测（只匹配 10:00 和 10:01 开头的行，10:02 被排除）
2026-08-18 10:00:01 INFO  user=alice action=login  ip=10.0.0.1
2026-08-18 10:00:05 ERROR user=bob   action=query  ip=10.0.0.2
2026-08-18 10:01:00 WARN  user=carol action=login  ip=10.0.0.3
2026-08-18 10:01:10 ERROR user=alice action=upload ip=10.0.0.1
```

```text
锚点易错点：
- $ 匹配行尾，但若行尾有 \r（Windows 换行符），$ 会匹配不到真实行尾，先 dos2unix 或 tr -d '\r'
- ^$ 匹配空行；^[[:space:]]*$ 匹配只有空白的行
- \b 是 GNU 扩展，POSIX 只保证 \< \>；跨平台脚本优先用 \< \>
- 锚点是零宽断言，不消耗字符，只「卡位置」
```

```text
单词边界的多种写法，本机实测（GNU grep 3.11）：三种写法结果一致，选可移植性最好的
$ echo 'cat catalog' | grep -o '\<cat\>'
cat
$ echo 'cat catalog' | grep -oE '\bcat\b'
cat
$ echo 'cat catalog' | grep -ow 'cat'
cat
# 推荐顺序：grep -w（最直观）> \<cat\>（POSIX 保证）> \bcat\b（GNU 扩展）
# 只有 grep -P 时 \b 与 \b 的取反 \B 才完全对齐 PCRE 语义：
$ echo 'cat' | grep -cE '\Bca'
0
# \B 是「非单词边界」，cat 开头的 c 处在单词边界上，所以不匹配 —— 符合预期

注意：awk（mawk 1.3.4）的正则不认 \b 和 \< \>，本机实测：
$ echo 'cat catalog' | awk '{gsub(/\bcat\b/,"X"); print}'
cat catalog                       # 完全没有替换，\b 在 mawk 里不是单词边界
$ echo 'cat catalog' | awk '{gsub(/[[:<:]]cat[[:>:]]/,"X"); print}'
awk: line 1: regular expression compile failed (bad class -- [], [^] or [)
$ echo 'cat catalog' | awk '{gsub(/\<cat\>/,"X"); print}'
cat catalog                       # \< \> 在 mawk 里同样无效
# mawk 下要按「整词」处理，只能用显式字符类把边界写出来：
$ echo 'cat catalog' | awk '{gsub(/(^|[^a-zA-Z0-9_])cat([^a-zA-Z0-9_]|$)/,"X"); print}'
Xcatalog
# 注意这个写法会把分隔符一起替换掉（上面的空格被吃掉了），需要的话要在替换串里补回 \1 \2。
```

```text
CRLF（Windows 换行）会让 $ 锚点失效 —— 这是「模式明明对却匹配不到」的头号原因，实测：
$ printf 'a\r\n' > /tmp/cr1.txt
$ grep -c '^a$' /tmp/cr1.txt
0                                # 匹配不到！因为行尾其实是 \r\n，$ 定位在 \n 之前、\r 之后
$ grep -c '^a.$' /tmp/cr1.txt
1                                # . 把 \r 吃掉了才「看起来对」—— 这是假成功，别被它骗
$ file /tmp/cr1.txt
/tmp/cr1.txt: ASCII text, with CRLF line terminators
# 正确做法：先规范换行，再跑锚点正则（本机未装 dos2unix，用 sed/tr/perl 等价替代）
$ sed 's/\r$//' /tmp/cr1.txt | od -c | head -1
0000000   a  \n
$ tr -d '\r' < /tmp/cr1.txt | od -c | head -1
0000000   a  \n
$ perl -pe 's/\r\n/\n/g' /tmp/cr1.txt | od -c | head -1
0000000   a  \n
# 三种替代都能得到纯 \n 结尾；写要做锚点的正则前，先确认输入换行符是 \n。
```

### 分组与反向引用

分组 `()` 做两件事：一是把多个字符当成一个整体（量词就能作用于整组），二是捕获匹配内容供反向引用 `\1 \2` 复用。反向引用最常见的是「匹配一对重复内容」，比如找连续重复的单词 `\b(\w+)\s+\1\b`。sed 里 `\1` 用来在替换里引用捕获组（`sed -E 's/(user)=(\w+)/\1名\2/'` 这种），awk 用 match 或 gensub。

```text
分组要点：
1. (abc)+ 把 abc 当整体重复；  (a|b) 分组内交替
2. \1 \2 反向引用第 1、2 个捕获组，匹配与之前相同的内容
3. 捕获组按左括号从左到右编号；   (?:...) 非捕获组（PCRE）
```

```shell
# 用分组 + 反向引用匹配「重复出现的单词」
echo "hello hello world" | grep -Eo '\b([a-z]+) \1\b'
# 输出：hello hello
```

```text
捕获组编号规则（按左括号出现顺序）：
- (a)(b)       → \1=a  \2=b
- (a(b))(c)    → \1=ab  \2=b  \3=c（嵌套组也按左括号顺序编号）
- (?:...)      → 非捕获组，参与分组但不编号、不占用 \1（PCRE）
- 反向引用匹配「与捕获组相同的文本」，不是「重复同样的模式」
```

```shell
# 找连续重复的单词（真实文档里常见的手误）
echo 'the the cat' | grep -E '\b([a-z]+) \1\b'
# 输出：the the cat
```

```text
分组编号实测（sed -E 把三个捕获组直接打出来看编号）：
$ echo 'abc' | sed -E 's/(a(b))(c)/[\1][\2][\3]/'
[ab][b][c]
# 编号完全按「左括号出现的先后」：\1 是最外层的第一个左括号 → ab
#                                    \2 是嵌在里面的第二个左括号 → b
#                                    \3 是第三个左括号 → c
# 坑：直觉会以为 \1 是「最早匹配完的那个」—— 不是，是最早开括号的那个。

反向引用在 BRE / ERE 下都可用，不需要 -P（实测）：
$ echo 'abab' | grep -E '^(ab)\1$'
abab
$ echo 'abab' | grep '^\(ab\)\1$'
abab

替换里引用「整个匹配」用 &（sed 专有语法，正则本身没有）：
$ echo 'price=100' | sed -E 's/[0-9]+/[&]/'
price=[100]
$ echo 'user=alice' | sed -E 's/(\w+)=(\w+)/[\1:\2]/'
[user:alice]
# 注意 sed -E 里的 \w 是 GNU 扩展（本机 GNU sed 4.9 可用），换实现可能失效，
# 可移植写法是把 \w+ 展开成 [a-zA-Z0-9_]+。
```

### 交替

交替 `|` 表示「或」，匹配左右任意一个。它通常和分组配合，限定交替的作用范围——`(ERROR|WARN)` 匹配 ERROR 或 WARN，而不写括号的 `ERROR|WARN` 其实也能用，但一旦和别的模式拼接就要小心优先级（`|` 优先级最低，会把整句切成左右两半）。查日志时 `grep -E 'ERROR|WARN|FATAL'` 是最常用的「多级别一起看」写法。

```shell
# 交替匹配多个用户名
grep -E 'user=(alice|bob)' /tmp/demo.txt
```

```text
# 实测
2026-08-18 10:00:01 INFO  user=alice action=login  ip=10.0.0.1
2026-08-18 10:00:05 ERROR user=bob   action=query  ip=10.0.0.2
2026-08-18 10:01:10 ERROR user=alice action=upload ip=10.0.0.1
```

```text
交替易错点：
- | 优先级最低：^a|b$ 是「(^a) 或 (b$)」，不是「a 或 b 且行首行尾」，想后者写成 ^(a|b)$
- 交替分支的匹配语义随引擎不同：GNU grep -E / sed 是 POSIX 的「最左最长」（leftmost-longest），
  grep -P（PCRE2）是「最左优先」（leftmost-first）。很多教程写「左边的分支优先」只对 PCRE 成立
- 多关键词场景也可用 grep -e 或 -f 模式文件，见 [[03.2-grep]]
```

```text
交替的两组实测（GNU grep 3.11 / GNU sed 4.9）：

1. | 优先级最低，会把模式切成「左半边 | 右半边」两段
$ echo 'b' | grep -E '^a|b$'
b
$ echo 'xax' | grep -cE '^a|b$'
0                                # xax 既不以 a 开头、也不以 b 结尾 → 不匹配（说明被拆成了两段）
$ printf 'a\nb\nc\n' | grep -E '^(a|b)$' | tr '\n' ' '
a b                              # 想表达「整行就是 a 或 b」必须给交替加括号

2. 交替分支的匹配语义随引擎不同（本文纠正的一个流传很广的说法）
$ echo 'ab' | grep -oE '(a|ab)'
ab                               # GNU grep 的 ERE 引擎是 POSIX「最左最长」：选了更长的 ab
$ echo 'ab' | grep -oP '(a|ab)'
a                                # grep -P（PCRE2）是「最左优先」：选了写在前面的 a
$ echo 'ab' | sed -E 's/(a|ab)/[\1]/'
[ab]                             # sed 同样是最左最长
$ echo 'ab' | grep -oE 'a|ab'
ab                               # 不加括号也一样：最左最长
# 结论：「分支按书写顺序先到先得」只对 PCRE 成立，对 grep -E / sed 不成立。
# 实践上想让两个引擎都给同一结果：把更具体的分支写在前面（(ab|a)），或干脆避免有重叠前缀的交替。
```

### 贪婪与懒惰

量词默认是「贪婪」的——尽量多匹配；在量词后加 `?` 变成「懒惰」——尽量少匹配。这个区别在匹配带分隔符的内容时最明显：`<.*>` 会从第一个 `<` 一直吃到最后一个 `>`（跨过中间所有内容），`<.*?>` 则停在第一个 `>`。写正则时如果结果「匹配过头了」，基本都是贪婪在作怪，给量词加 `?` 即可。

```shell
# 贪婪 vs 懒惰（PCRE 演示）
echo 'a<tag>content</tag>b' | grep -oP '<.*>'     # 贪婪：<tag>content</tag>
echo 'a<tag>content</tag>b' | grep -oP '<.*?>'    # 懒惰：<tag>
```

```text
# 输出对比
$ echo 'a<tag>content</tag>b' | grep -oP '<.*>'
<tag>content</tag>
$ echo 'a<tag>content</tag>b' | grep -oP '<.*?>'
<tag>
```

```text
控制匹配范围的三种办法：
1. 懒惰量词 .*? —— 尽量少匹配
2. 排除字符类 [^>]* —— 用「非 > 字符」替代任意字符，最精确也最高效
3. 占有量词 a++ / 原子组 (?>...)（PCRE）—— 禁止回溯
```

```shell
# 排除字符类提取标签内容（不用懒惰量词也精确）
echo 'a<tag>content</tag>b' | grep -oP '<[^>]*>'
# 输出：<tag> 和 </tag> 各占一行
```

### BRE 与 ERE 与 PCRE

三种方言的核心差异在「元字符要不要转义」和「支持哪些特性」。BRE 里 `+ ? | ( ) { }` 都要加 `\` 才当元字符，否则是字面量；ERE 里这些直接就是元字符；PCRE 在 ERE 基础上多了 `\d \w \s` 简写、前瞻后瞻、非捕获组等。实战建议：能用 `grep -E` 就优先 ERE（不用转义、不易错），需要 `\d` 简写或复杂模式才上 `grep -P`。

```shell
# PCRE 的 \d 简写：提取 IP 更简洁
grep -Po '\d+\.\d+\.\d+\.\d+' /var/log/nginx/access.log | sort -u
```

```text
# 实测（真实 nginx 日志里提取到的 IP）
100.115.7.80
151.0.0.0
# \d 等价于 [0-9]，PCRE 写法更短。151.0.0.0 是异常来源地址，正是用正则才揪出来的。
```

```text
PCRE 独有特性（grep -P 专属，BRE/ERE 不支持）：
1. 简写 \d \w \s 及取反 \D \W \S
2. 前瞻 (?=...) 后瞻 (?<=...) 负前瞻 (?!...) 负后瞻 (?<!...)
3. 非捕获组 (?:...) 命名组 (?<name>...) 原子组 (?>...)
4. 占有量词 a*+ a++ a?+（匹配后不回溯）
```

```shell
# 前瞻：匹配「后面跟着 alice 的 ERROR 行」
grep -P 'ERROR(?=.*alice)' /tmp/demo.txt
# 后瞻：提取 user= 后面的用户名
grep -oP '(?<=user=)\w+' /tmp/demo.txt | head -3
```

```text
# 输出
$ grep -P 'ERROR(?=.*alice)' /tmp/demo.txt
2026-08-18 10:01:10 ERROR user=alice action=upload ip=10.0.0.1
$ grep -oP '(?<=user=)\w+' /tmp/demo.txt | head -3
alice
bob
carol
```

### 零宽断言（前瞻与后瞻，仅 PCRE）

前面提过前瞻后瞻是 `grep -P` 专属，这里给全。它们是**零宽断言**：只检查「某个位置前后是不是满足条件」，本身不消耗任何字符，所以可以拿来当「附加条件」而不影响匹配结果的长度。

```text
四种断言（grep -P，PCRE2）：
1. (?=...)   正前瞻：当前位置后面必须能匹配 ...        「后面是」
2. (?!...)   负前瞻：当前位置后面必须不能匹配 ...      「后面不是」
3. (?<=...)  正后瞻：当前位置前面必须能匹配 ...        「前面是」
4. (?<!...)  负后瞻：当前位置前面必须不能匹配 ...      「前面不是」
```

```shell
grep -P 'ERROR(?=.*alice)' /tmp/demo.txt          # 「ERROR 行里还带 alice」
grep -P 'ERROR(?!.*alice)' /tmp/demo.txt          # 「ERROR 行里不带 alice」
grep -oP '(?<=user=)\w+' /tmp/demo.txt | head -3  # 后瞻当「提取器」用
grep -oP '(?<!action=)login' <<< 'xlogin action=login'
```

```text
# 实测（本机 GNU grep 3.11，-P 可用）
$ grep -P 'ERROR(?=.*alice)' /tmp/demo.txt
2026-08-18 10:01:10 ERROR user=alice action=upload ip=10.0.0.1
$ grep -P 'ERROR(?!.*alice)' /tmp/demo.txt
2026-08-18 10:00:05 ERROR user=bob   action=query  ip=10.0.0.2
2026-08-18 10:02:30 ERROR user=eve   action=login  ip=10.0.0.5
# 一正一负刚好把 3 行 ERROR 分成两类：带 alice 的 1 行 + 不带 alice 的 2 行

$ grep -oP '(?<!action=)login' <<< 'xlogin action=login'
login
# 负后瞻只放过了左边不是 action= 的那个 login；action=login 里的 login 被排除了

$ grep -P '(?<=user=)\w+' /tmp/demo.txt | head -1   # 断言「前面是 user=」再取单词字符
alice
```

```text
PCRE 其余高级特性实测（都能跑通，BRE/ERE 一律不支持）：
$ grep -oP '(?:ab)+' <<< 'ababab'
ababab                            # 非捕获组：分组但不占用编号
$ grep -oP '(?<user>alice)' /tmp/demo.txt | head -1
alice                             # 命名组：GNU grep 的 -o 只输出整体匹配，命名组本身不改变输出
$ echo 'aaab' | grep -oP 'a++b'
aaab                              # 占有量词：匹配后不回溯
$ echo 'aaab' | grep -oP '(?>a+)b'
aaab                              # 原子组：效果同上，禁掉回溯
$ grep -oP '\p{Han}+' <<< 'abc 北京上海 xyz'
北京上海                          # \p{Han} 是 Unicode 属性类，只有 PCRE 才有，比 [\x{4e00}-\x{9fa5}] 干净
```

```text
三个使用纪律：
- 断言必须是「真正零宽的需求」才用：能写成 [^x]* 的优先写字符类（更快也更可移植）
- 后瞻断言在 PCRE2 里要求定长前缀（(?<=user=) 长度固定没问题；(?<=\w+) 这种变长前缀会报错）
- 非 GNU 平台的 grep（BSD/macOS 自带、busybox）没有 -P，用不了任何断言 —— 脚本要移植就别依赖
```

### 常见业务模式速查（全部本机实测通过）

下面这些模式是运维脚本里出现频率最高的，直接抄改即可。每条都用 `grep -E` 或 `grep -P` 在本机跑过，输出来自实际执行。

```shell
# 1. IPv4 —— 宽松版：只要求 4 段 1~3 位数字
grep -E '^([0-9]{1,3}\.){3}[0-9]{1,3}$' /tmp/ip-list.txt
# 2. IPv4 —— 严格版 0-255：排除 999 / 256 这类越界值
grep -E '^((25[0-5]|2[0-4][0-9]|1?[0-9]{1,2})\.){3}(25[0-5]|2[0-4][0-9]|1?[0-9]{1,2})$' /tmp/ip-list.txt
```

```text
# 实测（/tmp/ip-list.txt 里混了合法与非法样本）

192.168.1.255
256.1.1.1
999.999.999.999
172.16.254.1

$ grep -E '^((25[0-5]|2[0-4][0-9]|1?[0-9]{1,2})\.){3}(25[0-5]|2[0-4][0-9]|1?[0-9]{1,2})$' /tmp/ip-list.txt
10.0.0.1
192.168.1.255

# 严格版正确排除了 256.1.1.1 / 999.999.999.999 / 1.2.3 / 1.2.3.4.5
# 拆解：25[0-5] → 250-255；2[0-4][0-9] → 200-249；1?[0-9]{1,2} → 0-199

```shell
# 3. 邮箱（务实版，不是 RFC 严格版）

# 7. 用户名：字母开头 + 字母数字下划线，总长 3~16
printf 'alice_01\n1bob\nab\nalice-bob\nzhang_san_li\n' | grep -E '^[a-zA-Z][a-zA-Z0-9_]{2,15}$'
# 8. 十六进制颜色 #RGB / #RRGGBB

## 工作原理

正则引擎的匹配过程是「从左到右扫描 + 回溯」：

1. 引擎从字符串第一个字符开始，尝试匹配整个模式；失败就换到下一个起点重试。
2. 遇到量词（`* + {n,m}`）时先「贪婪」地尽量多吃，若后续子模式匹配失败，再「回溯」吐出字符重新尝试。
3. 回溯是正则匹配的代价来源——模式写得越有歧义（多个量词嵌套），回溯次数越多。

Linux 工具背后的引擎分两类：PCRE（grep -P）是 NFA 回溯引擎，支持前瞻/后瞻但最坏是「指数级」时间；BRE/ERE（grep/sed/awk）传统上由 DFA 或受限引擎实现，无回溯、保证线性时间，但功能少（无前瞻）。这就是「灾难性回溯」（catastrophic backtracking）的根源——写错一个 PCRE 模式可能把 CPU 打满。

```text
匹配流程：定位起点 → 逐子模式尝试 → 贪婪多吃 → 失败回溯 → 换起点重试
BRE/ERE：无回溯，线性时间，功能少（无前瞻/后瞻）
PCRE：NFA 回溯，功能强，但可能指数级退化（灾难性回溯）
```

```text
回溯实例：模式 a+a+b 匹配字符串 aaab（NFA 回溯引擎）
1. a+ 贪婪吃掉 aaa，剩下 b；下一个 a 去匹配 b 失败
2. 回溯：a+ 吐出最后一个 a（吃 aa），a 匹配到第 3 个 a，b 匹配到第 4 个 b 成功
3. 若输入更长，回溯次数随之增长；(a+)+b 这类嵌套量词则指数级增长
```

### 引擎差异：为什么 grep -E 不会挂死而 grep -P 会

「回溯」这个说法只对回溯型引擎成立。GNU 工具链里其实是两种引擎并存，理解这一点能解释大部分「同一个病态模式，一个命令秒回、另一个卡死」的现象。

```text
三类引擎：
1. DFA（确定性有限自动机）—— 无回溯，一次扫描出结果，线性时间 O(n*m)
   优点：不会灾难性爆炸；缺点：不支持反向引用、不支持捕获组（或需额外一趟）
2. 混合实现（GNU grep / GNU sed 用的）：以 DFA/位并行算法为主，遇到需要子匹配与反向引用时才
   落到回溯路径——所以 GNU grep 的 BRE/ERE 既快又能支持 \1 反向引用
3. NFA 回溯（PCRE2，grep -P 用）：逐分支试错，天然支持捕获组/断言/反向引用，
   但最坏时间是指数级
```

```text
实测：同一个病态模式，两个引擎的结局完全不同（GNU grep 3.11）
$ printf 'a%.0s' $(seq 1 30) > /tmp/a30.txt; printf 'b\n' >> /tmp/a30.txt
$ time -p grep -E '^(a+)+$' /tmp/a30.txt ; echo "exit=$?"
real 0.00
user 0.00
sys 0.00
exit=1
$ time -p grep -P '^(a+)+$' /tmp/a30.txt ; echo "exit=$?"
grep: /tmp/a30.txt: 超过 PCRE 的回溯限制
real 0.02
user 0.02
sys 0.00
exit=2

# ERE 走线性引擎：30 个 a 后面跟 b，模式不匹配，0.00 秒给出结论，退出码 1（正常的「无匹配」）
# PCRE 走回溯引擎：命中回溯上限，0.02 秒后报错退出，退出码 2（「出错」，不是「无匹配」）
# 注意退出码差别很重要：脚本里 if grep ... 时，2 和 1 的含义完全不同
```

```text
回溯上限的触发阈值实测（输入 = n 个 a 再加一个 b，模式 ^(a+)+$）：
$ n=20 → 正常返回（退出码 1，无匹配）
$ n=25 → grep: 超过 PCRE 的回溯限制
$ n=30 → grep: 超过 PCRE 的回溯限制
$ n=40 → grep: 超过 PCRE 的回溯限制
# 只有 5 个字符的差距，就从「秒回」变成「触发上限」—— 这个曲线的斜率就是指数级。
# grep 之所以还能全身而退，是因为 PCRE2 有回溯上限兜底（默认报错退出），不是因为它算得快。
# 换成没有上限的回溯实现（如某些语言的 re 库），同样的输入会直接把 CPU 打满。
```

```text
mawk 的引擎也自成一派（别把它当成 grep 那种实现）：
- 支持 gsub/sub 的子匹配替换，但**不支持 \b \< \> 这类单词边界**（实测见「锚点」一节）
- 不支持 gawk 的 gensub/asort/IGNORECASE（报错原文见「概述」的跨发行版块）
- 所以「同一份正则在三剑客里通用」这句话只在基础语法层面成立，边界类扩展必须逐工具验证
```

```text
匹配单元与记录边界（两个常被忽略的引擎细节）：
1. 「一个字符」到底是几字节，由 locale 决定（本机默认 zh_CN.UTF-8）：
   $ printf '张三\n' > /tmp/cn.txt
   $ grep -o '.' /tmp/cn.txt           $ LC_ALL=C grep -o '.' /tmp/cn.txt | od -c | head -1
   张                                  0000000 345  \n 274  \n 240  \n 344  \n 270  \n 211  \n
   三
2. 记录边界默认是 \n，所以 . 匹配不到换行：
   $ printf 'aXb\nc\n' > /tmp/ml.txt
   $ grep -c 'a.*b' /tmp/ml.txt
   1                                    # 只命中第一行；grep 逐行处理，模式永远看不到 \n
   若用 -z 把记录边界改成 NUL，整段内容变成一条记录，此时 . 仍不吃 \n（PCRE 默认）
   $ printf 'a\nb\0' > /tmp/mlz.txt
   $ grep -zoP 'a.b' /tmp/mlz.txt | od -c | head -1
   0000000                              # 空：. 不吃 \n，a.b 匹配不到 a\nb
   $ grep -zoP '(?s)a.b' /tmp/mlz.txt | od -c | head -1
   0000000   a  \n   b  \0                # 加 (?s) 开 DOTALL，. 才匹配换行
```

## 常用命令与配置

正则是被 grep/sed/awk 消费的「模式语言」，常用命令围绕这三个工具的正则入口展开：

```shell
# grep —— 正则最常见的宿主
grep -E '模式' 文件        # ERE 匹配
grep -P '模式' 文件        # PCRE（支持 \d \w \s 前瞻后瞻）
grep -oE '模式' 文件       # 只输出匹配到的片段
grep -oP '(?<=user=)\w+' 文件   # 后瞻提取字段
# sed —— 正则替换
sed -E 's/模式/替换/g' 文件
# awk —— 正则做行匹配 / 字段匹配
awk '/模式/' 文件
awk '$3 ~ /模式/' 文件     # 对第 3 个字段做正则匹配
```

```text
按目的选工具：
- 只判断「有没有匹配」      → grep -q
- 提取匹配片段（如 IP/时间）→ grep -oE
- 替换文本                  → sed -E 's/.../.../g'
- 字段级匹配/统计           → awk '$n ~ /.../'
```

### 正则入口矩阵：同一个正则在哪些工具里能跑

正则不是某一条命令的参数，而是**多个工具共用的模式语言**。下表把常见入口和它们的方言、限制一次列清（本机实测项见后面）：

| 工具 | 正则入口 | 方言 | 典型用途 | 平台/依赖 |
|---|---|---|---|---|
| grep | `grep -E 're'` / `grep 're'` | ERE / BRE | 行过滤、提取 | 所有 POSIX 系统 |
| grep | `grep -P 're'` | PCRE2 | 断言、`\d`、非贪婪 | 需要 `-P`（GNU grep 编译带 PCRE2） |
| grep | `grep -F 'str'` | 无（字面量） | 搜固定字符串 | 所有 POSIX 系统，最快 |
| sed | `sed -E 's/re/rep/g'` | ERE | 流式替换、删除 | GNU sed 还支持 `-r`（等价 `-E`） |
| awk | `awk '/re/'`、`$n ~ /re/` | ERE | 字段级匹配、统计 | 实现相关（本机 mawk） |
| perl | `perl -ne 'print if /re/'` | PCRE | 最完整、一行式脚本 | 需要 perl（本机 v5.38.2） |
| rg | `rg 're'` | Rust regex（默认）/ PCRE2（`--pcre2`） | 递归快速搜索 | 需要装 ripgrep（本机 14.1.0） |
| bash | `[[ $s =~ re ]]` | ERE（bash 内建） | 脚本内判断/取子串 | 仅 bash，dash/sh 不支持 |
| find | `-regex`（整路径匹配）/ `-name`（glob，非正则） | Emacs 风格（GNU find 默认） | 按名字找文件 | 注意 `-name` 不是正则 |

```shell
# 同一个「提取 user= 后面的名字」需求，四种入口的写法
grep -oP '(?<=user=)\w+' /tmp/demo.txt | head -3        # grep -P：后瞻
grep -oE 'user=[a-z]+'  /tmp/demo.txt | head -3         # grep -E：不依赖断言
perl -ne 'print "$1\n" if /user=(\w+)/' /tmp/demo.txt | head -3   # perl：$1 捕获组
rg -o 'user=\w+' /tmp/demo.txt | head -3                # rg：默认引擎
```

```text
# 实测
$ grep -oE 'user=[a-z]+' /tmp/demo.txt | head -3
user=alice
user=bob
user=carol
$ perl -ne 'print "$1\n" if /user=(\w+)/' /tmp/demo.txt | head -3
alice
bob
carol
$ rg -o 'user=\w+' /tmp/demo.txt | head -3
user=alice
user=bob
user=carol
```

```text
bash 的 =~ 是脚本里做校验最方便的方式 —— 匹配结果直接进 BASH_REMATCH 数组：
$ s='ip=10.0.0.7'
$ if [[ $s =~ ([0-9]{1,3}\.){3}[0-9]{1,3} ]]; then echo "BASH_REMATCH[0]=${BASH_REMATCH[0]}"; fi
BASH_REMATCH[0]=10.0.0.7
# 注意两点：
#   1. =~ 右边不要加引号！写成 =~ "正则" 会退化成字面字符串比较（bash 的老坑）
#   2. =~ 是 bash 内建，dash（Debian/Ubuntu 的 /bin/sh）不支持 —— 脚本第一行要写 #!/bin/bash

rg（ripgrep）默认用的不是 PCRE，而是 Rust regex 引擎：更快、保证线性时间，但**不支持 lookaround 与反向引用**：
$ rg -o '(?<=user=)\w+' /tmp/demo.txt
rg: regex parse error:
    (?:(?<=user=)\w+)
       ^^^^
$ rg --pcre2 -o '(?<=user=)\w+' /tmp/demo.txt | head -3
alice
bob
carol
# 加 --pcre2 切到 PCRE2 后端才能用断言 —— 这是「同一份正则换个工具就报错」的又一个实例，
# 也是「选了哪个引擎」比「会不会写正则」更影响结果的原因。
```

```text
多模式与模式文件（三剑客都支持「一次匹配多个模式」）：
$ grep -e ERROR -e WARN /tmp/demo.txt | wc -l      # -e 逐条给模式
$ printf 'ERROR\nWARN\n' > /tmp/pat.txt
$ grep -f /tmp/pat.txt /tmp/demo.txt | wc -l       # -f 从文件读模式（一行一个）
# 等价 ERE 写法（模式少时更直观，模式多时 -f 更好维护）：
$ grep -cE 'ERROR|WARN' /tmp/demo.txt
```

```text
# 实测
$ grep -e ERROR -e WARN /tmp/demo.txt | wc -l
4
$ printf 'ERROR\nWARN\n' > /tmp/pat.txt
$ grep -f /tmp/pat.txt /tmp/demo.txt | wc -l
4
$ grep -cE 'ERROR|WARN' /tmp/demo.txt
4
# 三种写法结果一致（ERROR 3 行 + WARN 1 行）。模式文件里一行一个模式，支持注释行（#开头）需自行过滤。
```

```text
find 的名字匹配不是正则（常见误解）：
$ find /etc/nginx -name '*.conf'          # -name 用的是 shell glob，* 表示任意字符
$ find /etc/nginx -regex '.*\.conf$'      # -regex 才是正则，而且默认匹配「整条路径」
# GNU find 的 -regex 默认是 Emacs 风格正则（与 grep -E 不完全一样），要 POSIX ERE 加 -regextype posix-extended
# 本机未装 fd（command -v fd 无输出），示例统一用 find。
```

## 配置文件解析

正则本身没有独立的配置文件，但它的行为受 locale 环境变量影响，这是最容易被忽略的「配置」点：

```text
1. LC_ALL / LC_COLLATE —— 影响 [a-z]、[A-Z] 这类范围的解释。
   默认 C locale 下 [a-z] 只匹配 26 个 ASCII 小写字母；
   在 en_US.UTF-8 等 locale 下，[a-z] 可能把带变音符号的字符也纳入范围，行为不一致。
2. 建议用 POSIX 字符类 [[:alpha:]] [[:digit:]] [[:space:]] 代替 [a-zA-Z] [0-9]，
   语义明确、不受 locale 影响，跨机器结果一致。
3. 多字节编码（UTF-8）下，. 匹配的是「字符」还是「字节」取决于工具和 locale 设置。
4. 追求速度的场景可临时 export LC_ALL=C，多字节 locale 下的匹配会显著变慢。
   ↑ 这一条需要按实测修正：本机 GNU grep 3.11 在 129MB 文本上对比 UTF-8 locale 与 LC_ALL=C，
     吞吐差异落在噪声范围内（数字见「性能与调优」）。locale 真正会改变的是**匹配结果**
     （[a-z] 的范围、grep -i 的大小写折叠、. 按字节还是按字符），而不是「一定显著变慢」。
     所以 LC_ALL=C 的理由应该是「要确定的结果」，不是玄学的「更快」。
```

### locale 变量的优先级与作用范围（实测）

```text
优先级从高到低：LC_ALL  >  LC_<类别>（LC_COLLATE/LC_CTYPE/...）  >  LANG
- LC_ALL 一旦非空，覆盖一切，其它变量全部失效
- 类别级变量只改一个维度：LC_COLLATE 管排序/范围，LC_CTYPE 管「什么是字符」、大小写折叠
- LANG 是兜底默认值，只在 LC_ALL 为空且具体类别未设时生效
```

```text
# 实测（同一份中文样本 /tmp/f3.txt，看排序结果是本地化序还是字节序）
$ LC_ALL=C LC_COLLATE=zh_CN.UTF-8 sort /tmp/f3.txt
张三
李四
王五
赵六
# LC_ALL=C 胜出 → 字节序。即使 LC_COLLATE 显式要求 zh_CN.UTF-8 也无效

$ LC_COLLATE=C sort /tmp/f3.txt
张三
李四
王五
赵六
# 只设类别级变量同样能拿到字节序 → 说明类别级变量确实生效

$ LC_ALL= LANG=zh_CN.UTF-8 sort /tmp/f3.txt
李四
王五
张三
赵六
# LC_ALL 置空后 LANG 接管 → 又变回本地化序

$ printf '张三\n' | LC_ALL=C LC_CTYPE=zh_CN.UTF-8 grep -o '.' | tr '\n' '|'
�|�|�|�|�|�|
# LC_ALL=C 同样压掉了 LC_CTYPE → . 仍按字节匹配，中文被拆成 6 段
# 结论：脚本里想「局部改变行为」，要么用 LC_ALL，要么确认没有任何 LC_ALL 存在（包括父 shell 残留）
```

```text
其它与正则行为相关的环境变量：
1. POSIXLY_CORRECT —— 让部分 GNU 工具退回严格 POSIX 行为（各工具差异大，不建议依赖）
2. GREP_COLORS —— 控制 grep 高亮颜色，只影响输出着色、不影响匹配结果
3. GREP_OPTIONS —— 旧版用来设默认选项，新版 GNU grep 已废弃；本机实测被忽略：
   $ GREP_OPTIONS='-i' grep -c 'error' /tmp/demo.txt
   0
   # 期望的「-i 忽略大小写后应命中 3 行 ERROR」并没有发生 → GREP_OPTIONS 已不起作用，别写进脚本
4. shell 别名 —— 多数发行版默认 alias grep='grep --color=auto'，交互式与脚本行为差异多来自这里；
   脚本里要用 command grep 或 /usr/bin/grep 绕过别名
```

```text
/bin/sh 与 shebang 也是「配置」的一部分（影响同一份正则脚本能不能跑）：
- Debian/Ubuntu 的 /bin/sh 是 dash（本机实测 readlink -f /bin/sh → /usr/bin/dash），Red Hat/CentOS 是 bash
- dash 不支持 bash 的 [[ =~ ]]、数组、部分扩展 glob
- 所以「正则相关」的脚本第一行别偷懒写 #!/bin/sh，写 #!/bin/bash；
  真要 POSIX 兼容就用 case 的 glob 匹配（注意 glob 与正则语法不同，没有量词和交替）
```

### 场景二：校验一批配置项里的 IP 地址格式是否合法

```shell
# 匹配合法 IPv4（0-255 每段），不合法的行会被过滤掉
grep -E '^([0-9]{1,3}\.){3}[0-9]{1,3}$' /tmp/ip-list.txt
# 更严格的 0-255 校验用 PCRE 或 awk 判断，纯正则写全比较啰嗦
```

```text
严格 0-255 校验（每段限制在 0~255，排除 999 这类越界值）：
grep -E '^((25[0-5]|2[0-4][0-9]|1?[0-9]{1,2})\.){3}(25[0-5]|2[0-4][0-9]|1?[0-9]{1,2})$' 文件

### 场景三：校验邮箱地址格式（注册/告警配置里常见）

```shell
# 用 ERE 做一次「够用」的邮箱格式校验（不是 RFC 严格版）

### 场景四：用「提取 + 排序 + 计数」三连统计日志里的用户与日期

正则负责提取，`sort | uniq -c` 负责统计 —— 这是运维日报最常用的组合。注意统计结果要稳定，管道首部加上 `LC_ALL=C`。

```shell
# 每个用户出现了几次（-o 把 user=xxx 逐个抠出来，再交给 sort/uniq 计数）
grep -oE 'user=[a-z]+' /tmp/demo.txt | sort | uniq -c | sort -rn
# 日志里覆盖了哪几天（先用 -o 抠出「日期 时间」，再让 awk 取第一列去重）
grep -oE '^[0-9-]+ [0-9:]+' /tmp/demo.txt | awk '{print $1}' | sort -u
# 每个 IP 被访问了几次
grep -oE 'ip=[0-9.]+' /tmp/demo.txt | sort | uniq -c | sort -rn
```

### 场景五：处理 Windows 传来的 CRLF 文件（先规范化，再跑锚点正则）

跨平台交付的日志、配置、CSV 常带 `\r\n`。此时 `$` 锚点会失效，必须先把换行统一成 `\n`。本机**没装 dos2unix**（`command -v dos2unix` 无输出），所以用 sed/tr/perl 三种等价替代。

```shell
printf 'a\r\nb\r\n' > /tmp/crlf.txt
file /tmp/crlf.txt                              # 先确认：CRLF line terminators
grep -c '^a$' /tmp/crlf.txt                     # 清洗前：匹配不到
sed 's/\r$//' /tmp/crlf.txt | grep -c '^a$'     # 替代 1：sed 删行尾 \r
tr -d '\r' < /tmp/crlf.txt | grep -c '^a$'      # 替代 2：tr 删所有 \r
perl -pe 's/\r\n/\n/g' /tmp/crlf.txt | grep -c '^a$'   # 替代 3：perl 整体替换
```

```text
# 实测
$ file /tmp/crlf.txt
/tmp/crlf.txt: ASCII text, with CRLF line terminators
$ grep -c '^a$' /tmp/crlf.txt
0
$ sed 's/\r$//' /tmp/crlf.txt | grep -c '^a$'
1
$ tr -d '\r' < /tmp/crlf.txt | grep -c '^a$'
1
$ perl -pe 's/\r\n/\n/g' /tmp/crlf.txt | grep -c '^a$'
1
# 清洗前 0、清洗后 1 —— 「模式没错、就是匹配不到」的典型现场。
# 三种替代的差别：
#   sed 's/\r$//'   只删「行尾的 \r」，文件中间的孤立 \r 会保留（最保守，推荐）
#   tr -d '\r'      删除所有 \r（包括正文里有意义的老式回车，可能破坏内容）
#   perl -pe        最直白地做 CRLF→LF 整体替换
```

### 场景六：中文文本的匹配、提取与字段处理

中文场景的关键是**保持 UTF-8 locale**（否则 `.` 会把汉字拆成字节，见「核心概念」的实测）。同时中文通常出现在逗号/制表符分隔的字段里，`grep -o` 抠片段 + `awk -F` 取字段是最顺手的组合。

```shell
printf '张三,25,北京\n李四,30,上海\n' > /tmp/f2.txt
grep -n '北京' /tmp/f2.txt              # 带行号搜中文
grep -c ',' /tmp/f2.txt                 # 数逗号出现「行数」
grep -oE ',[0-9]+,' /tmp/f2.txt         # 把中间的数字字段连两边逗号一起抠出来
awk -F, '$3=="北京"{print $1}' /tmp/f2.txt   # 按字段精确比较，取出对应的人名
```

```text
# 实测
$ grep -n '北京' /tmp/f2.txt
1:张三,25,北京
$ grep -c ',' /tmp/f2.txt
2
$ grep -oE ',[0-9]+,' /tmp/f2.txt

,30,
$ awk -F, '$3=="北京"{print $1}' /tmp/f2.txt

# 注意第三行的输出：-o 连着两边的逗号一起输出（因为模式里把逗号写进了匹配），
# 若只想要数字，写成 grep -oP '(?<=,)[0-9]+(?=,)' 或 grep -oE '[0-9]+'（当心后者会匹配到别的数字）。

### 场景八：大文件提数的工具与方言选型（实测计时）

同样的「提取 IP」需求，换成不同工具/方言，耗时能差一倍以上。下面是在本机 500000 行 / 31MB 的模拟日志上跑的结果（每种跑 3 次取稳定值）。

```shell
# 造样本：50 万行 nginx 风格日志（约 31MB）
seq 1 500000 | awk '{printf "2026-08-18 10:%02d:%02d INFO user=u%s action=login ip=10.0.%d.%d\n", $1%60, $1%60, $1%1000, $1%255, $1%255}' > /tmp/app500k.log
# 三种写法，计时对比
grep -cE '10\.0\.[0-9]+\.[0-9]+' /tmp/app500k.log     # ERE：推荐默认
grep -cP '\d+\.\d+\.\d+\.\d+'    /tmp/app500k.log     # PCRE
rg   -c '10\.0\.[0-9]+\.[0-9]+'  /tmp/app500k.log     # ripgrep
```

## 性能与调优

```text
1. 量词后加 ? 改懒惰、用 [^...] 字符类替代 .*，减少回溯次数
2. 能锚定就锚定（^ $），引擎少扫描无关位置
3. 避免多个量词嵌套（如 (a+)+b），这是灾难性回溯的典型写法
4. 复杂匹配用 PCRE 的原子组/占有量词（*+ ++）禁止回溯
5. 大文件先 grep -oE 缩小范围，再对结果做精细处理
6. 固定字符串搜索用 grep -F，跳过正则引擎，速度提升明显
7. 设 LC_ALL=C 可加快多字节 locale 下的匹配
```

```shell
# 灾难性回溯实测：这个模式对「很多 a + 结尾 b」的输入会长时间卡死
# echo 'aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaab' | grep -P '(a+)+b'
# 上面这行别真跑，会打满 CPU；改写成 grep -P 'a+b' 或锚定即可
```

## 安全与权限

```text
1. ReDoS —— 把用户输入直接拼进正则，配合灾难性回溯可打满 CPU（拒绝服务）
2. 正则注入 —— 用户输入里的 ( ) | 等元字符改变匹配语义，应先转义或用固定字符串匹配（grep -F）
3. grep -P 的 PCRE 回溯上限 —— 极端模式会报 "backtrack limit exceeded"，别误判成 bug
4. 日志/配置里用正则提取的敏感数据（token/密码）别写进输出或日志，防泄露
```

```shell
# 正则注入示例：本想匹配字面 "admin|root"，结果被 | 拆成两个分支
pattern='admin|root'
grep -E "$pattern" /etc/passwd      # 会同时匹配 admin 和 root 两行
grep -F "$pattern" /etc/passwd      # -F 固定字符串，只匹配字面 "admin|root"
```

## 故障排查

```text
「模式不匹配」排查顺序：
1. 方言对不对 —— 默认 BRE，+ ? | ( ) { } 要转义；改用 grep -E 再试
2. 锚点/边界 —— ^ $ 锁了行首行尾？末尾的 \r（Windows 换行）会让 $ 失效
3. 特殊字符 —— . * [ 要匹配字面量得转义，或直接 grep -F 固定字符串
4. 先 echo '样本' | grep '模式' 在最小样本上验证，再上全量

「匹配过头」排查：
- 大概率是贪婪（.* 吃太多），量词加 ? 或换成 [^...] 字符类

「PCRE 报 backtrack limit exceeded」：
- 模式触发灾难性回溯，重写模式（去嵌套量词、用占有量词），不是 bug
```

## 常见问题

```text
Q1: BRE 和 ERE 到底怎么选？
A: 日常用 grep -E / sed -E / awk（ERE），元字符不用转义。只有老脚本兼容才用 BRE。

Q2: grep '正则' 和 grep -E '正则' 结果不一样？
A: grep 默认 BRE，+ ? | ( ) 是字面量；-E 切 ERE 后这些才当元字符。写法不同导致匹配结果不同。

Q3: .* 和 [^ ]* 有什么区别？
A: .* 匹配任意字符（含空格、不含换行），[^ ]* 只匹配非空格。提取「一个词」用后者更精确。

Q4: 什么时候必须用 grep -P？
A: 需要 \d \w \s 简写、前瞻 (?=...) 后瞻 (?<=...)、非捕获组 (?:...) 时。这些 BRE/ERE 不支持。

Q5: grep 里 \w \s 为什么有时能用有时不能用？
A: \w \s \d 是 PCRE 简写，严格只在 grep -P 下保证可用；GNU grep 在 BRE/ERE 里也把它当扩展接受，但 POSIX/BSD 实现不支持。跨平台脚本要么用 grep -P，要么写 [a-zA-Z0-9_] / [[:space:]]。

Q6: [0-9]{1,3} 为什么能匹配到 999？
A: 它只限制「1 到 3 位数字」，不限制数值范围。要校验 0-255 的 IP 段，写成 (25[0-5]|2[0-4][0-9]|1?[0-9]{1,2})。

Q7: 捕获组 () 和非捕获组 (?:...) 的区别？
A: 捕获组记录匹配内容、可被 \1 反向引用；非捕获组只做分组不编号、不占 \1（PCRE）。嵌套分组多时用 (?:...) 能避免编号混乱。

Q8: grep -o 能一次输出一行里的多个匹配吗？
A: 能。grep -oE '[0-9]+' 会把每行的每个数字各输出一行；同一行有多个匹配就输出多行，配 -n 时行号会重复出现——这是预期行为，不是 bug。

Q9: 正则能拿来解析 JSON / HTML 吗？
A: 不能可靠解析。这两类格式有嵌套结构，正则没有递归能力，只能做「平坦字段提取」。JSON 用 jq / python -m json.tool，HTML 用解析器；正则留给日志字段、脱敏这类一行一记录的场合。

Q10: awk 里怎么写「懒惰量词」？
A: POSIX ERE 没有懒惰量词，用排除字符类替代：把 <.*> 写成 <[^>]*>；或者用 sub / index / substr 手工截取。想用 ? 后缀得换 gawk（也不支持懒惰）或用 perl / grep -P。

Q11: ^$ 能匹配空行吗？怎么删空行？
A: 匹配。grep -vE '^$' 删掉真正的空行；要连「只有空格的行」一起删用 grep -vE '^[[:space:]]*$'。

Q12: 怎么定位一条慢正则？
A: 先看耗时随输入规模的增长曲线（time + 逐级放大的输入）；对比同一模式在 grep -E（线性 DFA）与 grep -P（回溯）下的表现；重点查嵌套量词 (x+)+ / (x*)*、无锚定的多分支 .*a.*b.*，再按「换 [^x]* / 加锚点 / 减少分支」的顺序改。

Q13: 什么时候必须用 grep -F？
A: 匹配固定字符串时。grep -F 不解析元字符、走更快的路径，能避免「金额 $1.99、路径 a.txt、含 ( ) 的串」被当正则解释，也避免 . 匹配到别的字符。
```

## 面试题

```text
1. 贪婪匹配和懒惰匹配的区别？
   答：贪婪量词尽量多匹配（.* 吃到最后一个 >），懒惰量词尽量少匹配（.*? 停在第一个 >）。量词后加 ? 变懒惰。

2. 什么是回溯？为什么会有灾难性回溯？
   答：量词先尽量多吃、匹配失败再吐出字符重试的过程叫回溯。多个量词嵌套（(a+)+b）会让回溯次数指数增长，即灾难性回溯，可造成 ReDoS。

3. BRE、ERE、PCRE 三种方言的差异？
   答：BRE 元字符要转义（+ ? | ( ) { }），ERE 直接写，PCRE 在 ERE 基础上加 \d \w \s 简写和前瞻后瞻。

4. 写一个匹配合法 IP 地址的正则，注意什么？
   答：数字段要 0-255 限制，不能只写 [0-9]{1,3}（会匹配 999）。严格版每段 (25[0-5]|2[0-4][0-9]|1?[0-9]{1,2})。

5. 反向引用有什么用？举个实际场景。
   答：反向引用 \1 匹配「与捕获组相同的文本」，用于匹配成对/重复内容：找连续重复单词 \b([a-z]+) \1\b、匹配成对 HTML 标签 <([a-z]+)>.*</\1>。sed 替换里 \1 引用捕获组做重组。

6. 什么是前瞻/后瞻？grep 里怎么用？
   答：零宽断言，只匹配位置不消耗字符。前瞻 (?=...) 后瞻 (?<=...)，负前瞻 (?!...)。grep 里只有 -P 支持：grep -P 'ERROR(?=.*alice)' 匹配「后面有 alice 的 ERROR 行」。

7. 怎么避免正则的灾难性回溯？
   答：避免嵌套量词（(a+)+b 改成 a+b）、用排除字符类 [^x]* 替代 .*、尽量锚定 ^$、PCRE 用占有量词 a++ 或原子组 (?>...) 禁止回溯。

8. POSIX 字符类 [[:alpha:]] 与 PCRE 简写 \w 有什么区别？可移植性如何？
   答：[[:alpha:]] 是 POSIX 标准字符类，grep -E / sed -E / awk 都认；\w 是 PCRE 简写，只有 grep -P 保证可用（GNU grep 在 BRE/ERE 下当扩展接受，BSD/busybox 不认）。跨平台脚本用 [[:alpha:]]、[0-9A-Za-z_] 这类标准写法，或显式声明依赖 GNU grep + -P。

9. 为什么 awk 里没有懒惰量词？怎么替代？
   答：POSIX ERE 规范只有贪婪量词，没有「量词后加 ?」的懒惰语义（gawk 也没有，那是 PCRE/perl 的扩展）。替代办法是用排除字符类把「吃到指定边界」表达出来，例如 <[^>]*> 取单个标签、"[^"]*" 取引号内内容；复杂截取用 index/substr。

10. 什么情况下不该用正则？
   答：需要递归/嵌套结构（JSON、HTML、括号匹配）、需要类型与转义语义（CSV 的引号内逗号、shell 引号）、需要精确数值范围（IP、端口、日期合法性）时，正则只是脆弱的近似。这些场景用专用解析器或校验逻辑，正则只负责「先粗筛」。

11. 怎么写出「不回溯/难 ReDoS」的安全正则？
   答：避免嵌套量词 (x+)+，改成单个量词；用具体字符类 [^x]* 代替 .*；尽量加 ^ 与 $ 锚定，减少无锚定的多分支；限定长度上限 {1,64}；不可信输入不要用 -P（PCRE 回溯引擎）；BRE/ERE 本身是线性 DFA，不存在灾难性回溯。

12. locale 会怎样影响正则？生产脚本怎么固定行为？
   答：影响字符类范围（[a-z] 在部分 UTF-8 locale 下会纳入带变音字符）、. 与 {n} 的计数单位（字符还是字节）、[[:alpha:]] 的判定。生产脚本要么显式 export LC_ALL=C（按字节、结果最稳，但处理中文要小心），要么固定 C.UTF-8 / zh_CN.UTF-8（按字符），不要依赖登录环境的 LANG。

13. 反向引用为什么会显著增加开销？
   答：反向引用要求引擎记住捕获内容并在后续位置逐字符比较，DFA 无法直接表达（GNU grep 遇反向引用会退回较慢的实现），PCRE 里还会叠加回溯。经验法则：能用两次简单匹配凑出来的结果，不要硬写反向引用。

14. 用正则做日志字段提取和脱敏，完整做法是什么？
   答：提取用 grep -oE 抓「字段=值」；脱敏用 sed -E 保留字段名、把值换成掩码；只想看某类记录时用 sed -nE 配 p 只打印替换成功的行。要点是把模式锚定在字段名上（user=、ip=），避免误伤正文里同样形状的字符串。

实测：
```text
$ printf '2026-09-12 10:00:01 INFO user=alice action=login ip=10.0.0.7\n2026-09-12 10:00:05 ERROR user=bob action=query ip=192.168.1.23\n' > /tmp/reg-demo.log
$ grep -oE 'user=[a-z]+|ip=[0-9.]+' /tmp/reg-demo.log
user=alice
ip=10.0.0.7
user=bob
ip=192.168.1.23
$ sed -E 's/(ip=)[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+/\1***.***.***.***/' /tmp/reg-demo.log
2026-09-12 10:00:01 INFO user=alice action=login ip=***.***.***.***
2026-09-12 10:00:05 ERROR user=bob action=query ip=***.***.***.***
$ sed -nE 's/.*ERROR user=([a-z]+).*/\1/p' /tmp/reg-demo.log
bob
```

15. 正则里的「零宽」是什么意思？举两个实用例子。
   答：零宽断言只匹配位置、不消耗字符，所以可以在替换里不丢内容。常用两个：前瞻 (?=...) 与后瞻 (?<=...)，都只在 -P/PCRE 下可用。例子：grep -P 'ERROR(?=.*alice)' 找后面带 alice 的 ERROR 行；sed -E 里想「只替换后面跟 = 的 key」则要用 perl -pe 或 grep -P 组合。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 能用 grep -E 就用 ERE，元字符不用转义、可读性最好
2. 需要 \d \w \s 简写或复杂匹配才用 grep -P
3. 匹配结果「过头了」先怀疑贪婪，量词后加 ? 改懒惰
4. 提取 IP 用 `[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+` 或 PCRE `\d+\.\d+\.\d+\.\d+`
5. 复杂正则先在少量数据上验证，再上全量，避免误匹配
6. 用 POSIX 字符类（[[:digit:]]、[[:alpha:]]、[[:space:]]）代替 [0-9] [a-z]，跨 locale 结果一致
7. 固定字符串匹配优先 grep -F，既快又不会被元字符坑

### 踩坑记录

```text
坑 1：在 BRE 里裸写 + ? | 当成字面量匹配
结论：grep 'a+' 匹配的是字面 "a+"，不是「一个或多个 a」。
原因：grep 默认 BRE，+ 要写成 \+ 才是量词。
解法：用 grep -E 切到 ERE，或显式转义 grep 'a\+'。

坑 2：贪婪匹配把整段都吃进去
结论：<.*> 从第一个 < 吃到最后一个 >，中间内容全被包进来。
原因：.* 默认贪婪，尽量多匹配。
解法：量词后加 ? 变懒惰 <.*?>，或改更精确的字符类 <[^>]*>。

坑 3：忘了 . 不匹配换行
结论：跨行匹配时 .* 匹配不到换行符，结果为空。
原因：正则默认逐行处理，. 不匹配 \n。
解法：跨行用 grep -P 配合 -z，或按行处理用 awk/sed 拼。

坑 4：grep 里 \d 不生效
结论：grep '\d+' 匹配不到数字。
原因：\d 是 PCRE 简写，grep 默认 BRE/ERE 不认。
解法：用 grep -P '\d+'，或 ERE 里写 [0-9]+。

坑 5：字符类里 - 放错位置被当范围
结论：[a-z] 想匹配 a、-、z 三个字符却写成范围。
原因：- 在 [] 中间表示范围，要放开头或结尾才是字面量。
解法：写成 [-az] 或 [az-]，把 - 放首尾。

坑 6：反向引用编号错位
结论：嵌套分组时 \1 \2 引到的内容和预期不符。
原因：捕获组按左括号出现顺序编号，不是按「匹配到的先后」或「谁更靠外」。
解法：数清楚左括号顺序，或用 (?:...) 让不关心的组不占编号。

坑 7：[a-z] 在非 C locale 下范围扩大
结论：同一正则在一台机器匹配「é」，另一台不匹配。
原因：en_US.UTF-8 等 locale 下 [a-z] 会把带变音字符纳入范围，行为随 locale 漂移。
解法：用 [[:lower:]] 或 [[:alpha:]]，或统一 export LC_ALL=C。

坑 8：分支没有分组，锚点只管一半
结论：grep -E '^a|b$' 命中的是「行首是 a」或「行尾是 b」，下面三行 ax / xb / ab 全部命中。
原因：| 优先级最低，整个模式被切成 ^a 和 b$ 两个分支，不是「同一个串既以 a 开头又以 b 结尾」。
解法：要整体锚定必须分组：grep -E '^(a|b)$'。

实测：
```text
$ printf 'ax\nxb\nab\n' | grep -nE '^a|b$'
1:ax
2:xb
3:ab
```

坑 9：POSIX 字符类少写一层方括号
结论：grep -E '[:alpha:]' 直接报错，GNU grep 提示「字符类的语法是 [[:space:]],而非 [:space:]」。
原因：POSIX 字符类本身是双括号 [[:alpha:]]；少一层时 [...] 被当成普通字符集合，里面是 a l p h a : 这些单字符。
解法：写 [[:alpha:]]；\w 只在 grep -P（PCRE）下可靠。

实测：
```text
$ printf 'alpha\nzzz\n' | grep -nE '[:alpha:]'
grep: 字符类的语法是 [[:space:]],而非 [:space:]
```

坑 10：把「grep 有 ReDoS 风险」当通说
结论：默认的 BRE/ERE 走线性时间 DFA 引擎、不回溯，不会灾难性回溯；ReDoS 只出现在 -P（PCRE2 回溯引擎）。
原因：两种引擎模型不同——DFA 不维护回溯状态栈，PCRE2 靠量词回溯。
解法：处理不可信输入时避免 grep -P；PCRE2 有回溯上限，超限是报错而不是挂死。

实测（同样的嵌套量词，25000 个 a 的长行）：
```text
$ time grep -cE '^(a+)+$' /tmp/redos.txt
real	0m0.001s          # ERE 线性引擎，秒回
$ grep -cP '^(a+)+$' /tmp/redos.txt
grep: /tmp/redos.txt: 超过 PCRE 的回溯限制
```

坑 11：. 和 {n} 计的是字节还是字符，取决于 locale
结论：LC_ALL=C 下 '^.{2}' 从「中文字」里切出的是「中」的前两个字节（半个字符，后续必乱码）；zh_CN.UTF-8 下切出的是「中文」两个字。
原因：C locale 按字节匹配多字节字符。
解法：处理中文必须让 locale 是 UTF-8（脚本里显式 export LC_ALL=zh_CN.UTF-8 或用 C.UTF-8），前提是该 locale 已生成（locale -a 可查）。

实测：
```text
$ printf '中文字\n' | LC_ALL=C grep -oE '^.{2}' | od -c
0000000 344 270  \n        # 半个汉字的两个字节
$ printf '中文字\n' | LC_ALL=zh_CN.UTF-8 grep -oE '^.{2}'
中文
```

坑 12：在 mawk 里用 match(s, r, m) 三参数
结论：Ubuntu 默认 awk 是 mawk，match($0, /re/, m) 直接语法错误。
原因：第三参数（捕获数组）是 gawk 扩展，mawk 的 match() 只接受两个参数。
解法：装 gawk（sudo apt install gawk）或改用 POSIX 就有的 RSTART / RLENGTH 配合 substr。

实测：
```text
$ echo '<a><b>' | awk '{match($0, /<[^>]*>/, m); print m[0]}'
awk: line 1: syntax error at or near ,
```

坑 13：sed 替换里 & 与 \1 混用
结论：sed 's/user=\(.*\)/[&]/' 得到 [user=alice]（& 是整个匹配），不是 [alice]。
原因：& 代表整个匹配内容，\1 才是第一个捕获组。
解法：要组内内容用 \1，要整个匹配用 &，想输出字面 & 写 \&。

实测：
```text
$ echo 'user=alice' | sed 's/user=\(.*\)/[\1]/'
[alice]
$ echo 'user=alice' | sed 's/user=.*/[&]/'
[user=alice]
```

坑 14：\b 不是 POSIX，跨实现会失效
结论：\b（词边界）是 GNU grep 的扩展、PCRE 也有，但 POSIX ERE 里没有它，mawk / POSIX sed 不保证可用。
原因：各实现扩展不一致。
解法：只用 GNU grep 时可以直接写 \b；要跨平台就写显式边界（如 (^|[^0-9A-Za-z_])），或统一走 grep -P。

实测：
```text
$ echo 'foo bar foobar' | grep -oE '\bfoo\b'
foo
```
