## 概述

本项目目标：把一组后端 Web 服务器，用「Keepalived + HAProxy」搭成一套对外高可用的负载均衡集群。Keepalived 负责负载均衡器（LB）自身的主备冗余和 VIP 漂移，HAProxy 负责把流量按算法分发到多台后端；再叠一层 LVS 作为四层转发的高性能方案对比。全程覆盖：VIP 漂移、健康检查、故障切换演练。

技术栈：Keepalived（VRRP 协议）、HAProxy（七层负载均衡）、LVS/IPVS（四层负载均衡）、Nginx（后端 Web 服务）。

前置条件：至少 4 台 Linux 主机（2 台 LB + 2 台后端 Web），均装好操作系统、配好静态 IP、能互相通信；LB 节点需要内核开启 IP 转发（LVS DR 模式还要关 ARP 响应）。下文 IP 规划：LB1 `192.168.1.10`、LB2 `192.168.1.11`、VIP `192.168.1.100`、Web1 `192.168.1.21`、Web2 `192.168.1.22`。

```text
交付物：一套双机主备的 LB 集群，客户端只访问 VIP，任意一台 LB 或后端挂了业务不中断，且能按步骤验证切换
```

## 核心概念

本项目涉及的技术点：

1. **VRRP（虚拟路由冗余协议）**：Keepalived 的底层协议，多台路由器/主机组成一个 VRRP 组，选举出一台 MASTER 持有虚拟 IP（VIP），其余为 BACKUP。MASTER 周期性发 VRRP 通告（advertisement），BACKUP 超时未收到就抢占 VIP 成为新 MASTER。
2. **VIP 漂移**：VIP 不是绑定在物理网卡上的固定地址，而是「跟角色走」——谁当 MASTER 谁持有。MASTER 挂了，VIP 自动「漂」到 BACKUP，客户端无感知，这就是 LB 自身高可用的核心。
3. **Keepalived**：实现了 VRRP 协议的高可用软件，通过 `keepalived.conf` 声明 VIP、优先级、心跳间隔、健康检查脚本，做 LB 的主备切换。
4. **HAProxy**：七层（HTTP）负载均衡器，能按 URL、Header、Cookie 做转发，支持多种调度算法和健康检查，比四层 LVS 更灵活。
5. **LVS/IPVS**：四层（TCP/UDP）负载均衡器，工作在内核态，转发性能高，但只看 IP+端口，不理解 HTTP。常与 Keepalived 搭配做「高可用 LVS」。
6. **调度算法**：决定请求分给哪台后端。轮询（rr）、加权轮询（wrr）、最少连接（lc）、源地址哈希（sh）等。

```text
核心概念：
Keepalived（VRRP 主备 + VIP 漂移）→ 保证 LB 本身不挂
HAProxy / LVS（流量分发）→ 把请求打到多台后端
二者叠加 = 高可用 + 负载均衡，消除 LB 和后端两个层面的单点故障
```

## 工作原理

整体链路是「VIP 漂移保证 LB 高可用，调度算法分发保证后端分担流量」两层机制：

1. **VIP 漂移（Keepalived 主备）**：LB1（priority 100，MASTER）和 LB2（priority 90，BACKUP）组成 VRRP 组。MASTER 每 `advert_int`（1 秒）发一次 VRRP 通告，BACKUP 连续 3 次没收到就认定 MASTER 挂了，自己抢 VIP、发免费 ARP 通告「VIP 现在归我」，成为新 MASTER。客户端缓存的 VIP→MAC 映射被免费 ARP 刷新，流量切到新 MASTER。
2. **健康检查（Keepalived 脚本）**：`vrrp_script` 定时跑脚本探测本机 HAProxy 是否存活，挂了就把 priority 降 20，低于对端则主动让出 VIP。这样「HAProxy 挂了」和「整机挂了」都能触发漂移，避免 VIP 还挂在服务已死的节点上。
3. **七层转发（HAProxy）**：客户端请求打到 VIP:80 → 内核把 VIP 的流量交给 HAProxy 监听 → HAProxy 按 `balance` 算法选一台后端 → 建立新连接转发请求。HAProxy 会主动探测后端 `/health` 路径，连续失败 `fall` 次就摘除该后端。
4. **四层转发（LVS DR 模式）**：LVS 只改二层 MAC 不改 IP 报文，把请求的 MAC 改成选中后端的 MAC，后端直接回包给客户端（不经过 LVS），因此回程不占 LB 带宽，性能最高。

```text
两层保障：
LB 层：Keepalived 检测 LB 存活 → MASTER 挂了 VIP 漂到 BACKUP
后端层：HAProxy 检测后端健康 → 挂了摘除，恢复后自动加回
故障切换链路：检测到异常 → 摘除/漂移 → 流量收敛到存活节点 → 无感知
```

## 常用命令与配置

```shell
# Keepalived
systemctl status keepalived          # 服务状态
journalctl -u keepalived -f          # 看 VIP 漂移日志
ip addr show eth0                    # 看 VIP 是否在本机（MASTER 持有）
cat /var/run/keepalived.pid          # 进程 PID

# HAProxy
systemctl status haproxy
haproxy -c -f /etc/haproxy/haproxy.cfg   # 校验配置语法（改配置必跑）
systemctl reload haproxy                  # 热加载（不停服务）

# LVS / ipvsadm
ipvsadm -L -n                        # 查看转发规则和后端
ipvsadm -L -n --stats                # 看每台后端连接数统计
ipvsadm -C                           # 清空所有规则

# 内核参数（LB 节点，DR 模式需要）
sysctl -w net.ipv4.ip_forward=1      # 开启 IP 转发
```

```text
配置要点：
1. 主备 priority 必须不同（如 100/90），相同会双主脑裂
2. virtual_router_id 主备必须一致，且同网段不同 VRRP 组不能撞 ID
3. 改 HAProxy 配置先 haproxy -c 校验，再用 reload 热加载，别 restart
4. 后端健康检查路径（/health）要在后端真实存在，否则会被全部摘除
```

## 配置文件解析

### /etc/keepalived/keepalived.conf（LB1，MASTER）

```text
global_defs {
    router_id LB01                    # 本机标识，主备不同
    vrrp_skip_check_adv_addr
}

vrrp_script chk_haproxy {             # 健康检查脚本：探测 HAProxy 是否存活
    script "/usr/bin/killall -0 haproxy"
    interval 2                        # 每 2 秒探测一次
    weight -20                        # 失败后 priority 减 20
    fall 3                            # 连续 3 次失败才判定异常
    rise 2                            # 连续 2 次成功才恢复
}

vrrp_instance VI_1 {
    state MASTER                      # 初始角色：MASTER（实际由 priority 定）
    interface eth0                    # VIP 绑定的网卡
    virtual_router_id 51              # VRRP 组 ID，主备必须一致
    priority 100                      # 优先级，高的当 MASTER
    advert_int 1                      # VRRP 通告间隔（秒）
    authentication {                  # 心跳认证，防伪造 VRRP 报文
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
        192.168.1.100/24 dev eth0     # VIP，漂移的地址
    }
    track_script {
        chk_haproxy                   # 关联健康检查脚本
    }
}
```

```text
字段含义：
state         MASTER/BACKUP，只是初始角色，实际由 priority 决定
priority      优先级，MASTER 比 BACKUP 高（常见 100/90）
advert_int    通告间隔，主备要一致；3×advert_int 未收到通告即判挂
weight -20    健康检查失败时 priority 减 20，低于对端则让出 VIP
track_script  把脚本检查结果关联到本实例，异常时触发降级/漂移
```

LB2 配置与 LB1 几乎一样，只改四处：`router_id LB02`、`state BACKUP`、`priority 90`、注释里说明是备机。其余（`virtual_router_id 51`、`auth_pass 1111`、`advert_int 1`）必须完全一致。

### /etc/haproxy/haproxy.cfg

```text
global
    log 127.0.0.1 local2 info         # 日志走本地 syslog
    maxconn 4096                      # 单进程最大连接数
    user haproxy
    group haproxy
    daemon

defaults
    mode http                         # 默认七层 HTTP 模式
    log global
    option httplog                    # 记录 HTTP 请求日志
    option dontlognull
    option http-server-close
    option forwardfor                 # 追加 X-Forwarded-For，透传客户端 IP
    retries 3
    timeout connect 5s
    timeout client 30s
    timeout server 30s

frontend web_front
    bind *:80                         # 监听 VIP:80（VIP 漂到哪台就由哪台监听）
    default_backend web_back

backend web_back
    balance roundrobin                # 轮询算法
    option httpchk GET /health        # 健康检查：GET 后端 /health
    server web1 192.168.1.21:80 check inter 3s fall 3 rise 2
    server web2 192.168.1.22:80 check inter 3s fall 3 rise 2

listen stats
    bind *:8404                       # 统计页端口
    stats enable
    stats uri /stats
    stats auth admin:admin123
```

```text
关键字段：
balance roundrobin   调度算法（还有 leastconn 最少连接、source 源地址哈希）
option httpchk       健康检查方式，GET /health 返回 200 才算健康
check inter 3s       每 3 秒探测；fall 3 连续 3 次失败摘除；rise 2 连续 2 次成功加回
option forwardfor    加 X-Forwarded-For 头，让后端拿到真实客户端 IP
```

## 应用场景实战

目标：4 台主机搭「Keepalived + HAProxy」双主备 LB 集群，后端 2 台 Nginx，VIP `192.168.1.100` 对外服务。从零到故障演练共 8 步。下文命令在对应主机执行，前缀标注执行位置。

### 步骤一：环境准备（4 台主机统一）

每台机器先做基础配置：主机名、静态 IP、时间同步、关闭 SELinux/防火墙放行端口。

```shell
# 以 LB1 为例，其余 3 台同理（IP 换成各自地址）
hostnamectl set-hostname lb1
timedatectl set-timezone Asia/Shanghai
systemctl enable --now chrony

# 关闭 SELinux（临时 + 永久，生产可改为按需放行）
setenforce 0
sed -i 's/^SELINUX=enforcing/SELINUX=permissive/' /etc/selinux/config

# 防火墙放行端口（firewalld 为例；Ubuntu 用 ufw allow）
firewall-cmd --permanent --add-port=80/tcp --add-port=8404/tcp
firewall-cmd --reload
```

解释：主机名和时间同步是后续排障定位的基础（日志时间错乱会误导判断）；SELinux 对 VIP 绑定、HAProxy 监听非标准端口会拦截，先放宽松；防火墙放行 80（业务）和 8404（HAProxy 统计页）。

验证：

```shell
# 4 台互相能 ping 通
ping -c 2 192.168.1.11
```

示例输出：

```text
PING 192.168.1.11 (192.168.1.11) 56(84) bytes of data.
64 bytes from 192.168.1.11: icmp_seq=1 ttl=64 time=0.31 ms
```

### 步骤二：部署后端 Web 服务器（Web1、Web2）

两台后端装 Nginx，各提供一个区分度高的首页和健康检查路径。

```shell
# Web1、Web2 都执行
apt install -y nginx          # RHEL 系：dnf install -y nginx
systemctl enable --now nginx
```

```shell
# Web1：写健康检查路径 + 首页（标记主机名便于验证轮询）
echo 'ok' > /usr/share/nginx/html/health
echo '<h1>web1</h1>' > /usr/share/nginx/html/index.html
systemctl reload nginx

# Web2 同理，首页标记 web2
echo 'ok' > /usr/share/nginx/html/health
echo '<h1>web2</h1>' > /usr/share/nginx/html/index.html
systemctl reload nginx
```

解释：HAProxy 的健康检查 `option httpchk GET /health` 需要后端真实返回 200，这里写一个内容为 `ok` 的静态文件即可；首页写不同主机名，后续用 curl 观察轮询时能看到请求被分发到 web1/web2 交替出现。

验证：

```shell
curl -s http://192.168.1.21/health
curl -s http://192.168.1.22/
```

示例输出：

```text
ok
<h1>web2</h1>
```

### 步骤三：LB 节点安装 Keepalived 和 HAProxy

```shell
# LB1、LB2 都执行
apt install -y keepalived haproxy          # RHEL 系：dnf install -y keepalived haproxy
systemctl enable keepalived haproxy
```

解释：两个软件都交给 systemd 管理并开机自启。Keepalived 负责 VIP 漂移，HAProxy 负责流量分发，二者独立运行、通过 `vrrp_script` 的 `killall -0 haproxy` 做关联。

验证：

```shell
keepalived --version | head -n 1
haproxy -v | head -n 1
```

示例输出：

```text
Keepalived v2.2.7 (02/14,2023)
HAProxy version 2.6.9-2ubuntu1 2023/03/27
```

### 步骤四：配置 HAProxy 负载均衡（LB1、LB2 相同）

把上面「配置文件解析」里的 haproxy.cfg 写入 `/etc/haproxy/haproxy.cfg`，先备份默认配置。

```shell
cp /etc/haproxy/haproxy.cfg /etc/haproxy/haproxy.cfg.bak
```

```shell
# 校验配置语法，通过再加载
haproxy -c -f /etc/haproxy/haproxy.cfg
systemctl reload haproxy
```

解释：`haproxy -c` 是静态语法校验，任何拼写错误都会在这里报出来，通过后再 `reload` 热加载（不中断现有连接）。`frontend` 监听 `*:80`，后端 `web_back` 用 `roundrobin` 轮询分发到 web1/web2。

验证：

```shell
# 本地直接打 LB1 的 80 端口，连续请求能看到轮询交替
for i in 1 2 3 4; do curl -s http://192.168.1.10/; done
```

示例输出：

```text
<h1>web1</h1>
<h1>web2</h1>
<h1>web1</h1>
<h1>web2</h1>
```

### 步骤五：配置 Keepalived 主备（LB1 为 MASTER、LB2 为 BACKUP）

LB1 写 MASTER 配置（priority 100），LB2 写 BACKUP 配置（priority 90），其余参数一致。

```shell
# LB1
cat > /etc/keepalived/keepalived.conf <<'EOF'
global_defs {
    router_id LB01
    vrrp_skip_check_adv_addr
}
vrrp_script chk_haproxy {
    script "/usr/bin/killall -0 haproxy"
    interval 2
    weight -20
    fall 3
    rise 2
}
vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 100
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
        192.168.1.100/24 dev eth0
    }
    track_script {
        chk_haproxy
    }
}
EOF
systemctl restart keepalived
```

解释：LB2 复制同一份，只改 `router_id LB02`、`state BACKUP`、`priority 90`。`interface eth0` 要和实际网卡名一致（用 `ip link` 确认，云主机常见 `ens33`/`eth0`）；`virtual_router_id 51` 主备必须相同，且同网段内不同 VRRP 组不能撞 ID（撞了会互相影响）；`auth_pass 1111` 也要一致，否则心跳认证失败、双主。

验证（LB1 应持 VIP，LB2 不持）：

```shell
ip addr show eth0 | grep 192.168.1.100
```

示例输出：

```text
    inet 192.168.1.100/24 scope global secondary eth0
```

### 步骤六：通过 VIP 验证负载均衡

客户端（或任意一台主机）访问 VIP，确认走 LB 集群且能正常分发。

```shell
# 连续请求 VIP，看到 web1/web2 交替 = 负载均衡生效
for i in 1 2 3 4; do curl -s http://192.168.1.100/; done

# 看 HAProxy 统计页（需要已放行 8404 端口）
curl -s -u admin:admin123 http://192.168.1.100:8404/stats | head -n 5
```

示例输出：

```text
<h1>web1</h1>
<h1>web2</h1>
<h1>web1</h1>
<h1>web2</h1>
```

解释：请求打到 VIP，由当前 MASTER（LB1）的 HAProxy 接住，轮询分发到两台后端。统计页能看到每台后端的健康状态、连接数、会话数。

### 步骤七：故障切换演练（VIP 漂移）

这是本项目最关键的一步——验证「挂了真的能切」。分三个场景演练。

场景 A：MASTER 整机宕机

```shell
# 在 LB1 上停掉 keepalived（模拟 LB1 挂了）
systemctl stop keepalived
```

```shell
# 立即到 LB2 看 VIP 是否漂移过来
ip addr show eth0 | grep 192.168.1.100
```

示例输出：

```text
    inet 192.168.1.100/24 scope global secondary eth0
```

解释：LB1 停止发 VRRP 通告，LB2 约 3 秒后（3×advert_int）判定 MASTER 挂了，抢占 VIP、发免费 ARP，成为新 MASTER。客户端无感知，继续访问 VIP 仍通。

```shell
# 客户端侧验证：VIP 仍可访问
curl -s http://192.168.1.100/
```

场景 B：MASTER 上的 HAProxy 挂了（服务挂、机器没挂）

```shell
# 在 LB1 上停 HAProxy（先恢复 keepalived，让 LB1 重新当 MASTER）
systemctl start keepalived
sleep 3
systemctl stop haproxy
```

解释：LB1 的 `chk_haproxy` 脚本探测到 HAProxy 挂了，连续 `fall 3` 次后 priority 100-20=80，低于 LB2 的 90，于是主动让出 VIP，LB2 接管。这验证了「VIP 不会挂在服务已死的节点上」——单靠 VRRP 主备只能防整机挂，加健康检查脚本才能防「机器活着但服务挂了」。

```shell
# 在 LB2 确认 VIP 已漂移，在 LB1 确认 VIP 已释放
ip addr show eth0 | grep 192.168.1.100   # LB2 有、LB1 无
```

场景 C：后端挂了（HAProxy 摘除）

```shell
# 在 Web1 上停 Nginx，模拟后端故障
systemctl stop nginx
```

```shell
# 连续请求 VIP，应全部命中 web2（web1 被摘除）
for i in 1 2 3 4; do curl -s http://192.168.1.100/; done
```

示例输出：

```text
<h1>web2</h1>
<h1>web2</h1>
<h1>web2</h1>
<h1>web2</h1>
```

解释：HAProxy 连续 3 次探测 web1 的 `/health` 失败（`fall 3`），把 web1 标记为 DOWN 并摘除，流量全走 web2。恢复 web1（`systemctl start nginx`）后，`rise 2` 连续 2 次成功会把它自动加回。

### 步骤八：LVS 四层方案对比（可选进阶）

同一套 Keepalived 主备，把转发层从 HAProxy 换成内核态的 LVS（DR 模式），吞吐更高但失去七层能力。

```shell
# 后端 Web 节点：DR 模式要绑定 VIP 到 lo 并抑制 ARP 响应（2 台都执行）
ip addr add 192.168.1.100/32 dev lo
echo 1 > /proc/sys/net/ipv4/conf/lo/arp_ignore
echo 2 > /proc/sys/net/ipv4/conf/lo/arp_announce
echo 1 > /proc/sys/net/ipv4/conf/all/arp_ignore
echo 2 > /proc/sys/net/ipv4/conf/all/arp_announce
```

```shell
# LB 节点：配置 ipvsadm 轮询规则（LB1、LB2 相同）
ipvsadm -A -t 192.168.1.100:80 -s rr
ipvsadm -a -t 192.168.1.100:80 -r 192.168.1.21:80 -g
ipvsadm -a -t 192.168.1.100:80 -r 192.168.1.22:80 -g
ipvsadm -L -n
```

解释：`-A` 添加虚拟服务（VIP:80）、`-s rr` 轮询；`-a` 添加真实服务器、`-g` 是 DR 直接路由模式。DR 模式后端回包直接给客户端、不经过 LB，所以 LB 只扛入站流量，性能最高。代价是 LVS 不检查 HTTP，后端进程活着但接口报错它也照转发，通常要再配 Keepalived 的健康检查或换用 HAProxy 做七层。

验证：

```shell
ipvsadm -L -n
```

示例输出：

TCP  192.168.1.100:80 rr

  -> 192.168.1.22:80              Route   1      0          0

## 性能与调优

```text
1. 调度算法选型 —— 后端性能一致用 roundrobin；性能不均用 leastconn 或加权（weight）；要会话保持用 source（源地址哈希）或 cookie 插入
2. HAProxy 连接数 —— maxconn 按内存调，每连接约消耗几 KB；worker 进程数 = CPU 核数（nbproc/nbthread）
3. 健康检查间隔 —— inter 3s 平衡了「切换速度」和「探测开销」；要求秒级摘除后端可降到 1s，但探测流量翻倍
4. LVS DR 模式回包不经过 LB —— 吞吐最高，适合大流量；NAT 模式要经过 LB 回包，LB 成瓶颈
5. Keepalived advert_int —— 默认 1s，切换时间 ≈ 3×advert_int；调小切换更快但心跳更敏感，网络抖动易误切换
6. 开启 HAProxy 的 httpclose/keep-alive 复用 —— 减少后端新建连接开销
```

```shell
# 调 HAProxy 线程数（多核机器，需 HAProxy 1.8+）
# /etc/haproxy/haproxy.cfg 的 global 段加：
#   nbthread 4
# 改完 haproxy -c 校验 + reload
haproxy -c -f /etc/haproxy/haproxy.cfg && systemctl reload haproxy
```

## 安全与权限

```text
1. VRRP 心跳加认证 —— auth_pass 防止伪造 VRRP 通告把 MASTER 挤下线（同网段恶意节点可构造低优先级通告）
2. HAProxy 统计页加认证 + 限制来源 —— stats auth 必须有，且只对内网/运维网段开放 8404 端口，别裸奔到公网
3. 心跳与业务分流 —— 生产环境 VRRP 心跳走独立网卡/VLAN，避免业务拥塞导致误判脑裂
4. 配置权限 —— keepalived.conf / haproxy.cfg 属 root，权限 644 或更严，防止被篡改
5. 后端直连防护 —— VIP 只是入口，后端 80 端口应只允许 LB 访问，防止绕过 LB 直连后端
```

```shell
# 限制 HAProxy 统计页只允许运维网段访问（防火墙示例）
firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="10.0.0.0/24" port port="8404" protocol="tcp" accept'
firewall-cmd --reload
```

## 故障排查

### VIP 双主（两台都有 VIP，脑裂）

```shell
# 两台 LB 分别执行，都有 VIP = 脑裂
ip addr show eth0 | grep 192.168.1.100

# 排查 1：virtual_router_id 是否一致
grep virtual_router_id /etc/keepalived/keepalived.conf

# 排查 2：auth_pass 是否一致（不一致会导致心跳互不认，各自为主）
grep auth_pass /etc/keepalived/keepalived.conf

# 排查 3：心跳网络是否互通（VRRP 组播/单播被交换机或防火墙挡了）
tcpdump -i eth0 -nn vrrp

# 排查 4：防火墙是否挡了 VRRP 协议（协议号 112）
firewall-cmd --list-all
```

### VIP 不漂移（主挂了备没接管）

```shell
# 看 keepalived 日志，找没切换的原因
journalctl -u keepalived -n 50

# 常见原因：priority 一样 / state 都写成 MASTER / 备机 keepalived 没起来
systemctl status keepalived
```

### 后端全部被摘除

```shell
# 场景：HAProxy 把后端全标记 DOWN，流量打不进去
# 排查 1：后端 /health 路径是否真的返回 200
curl -s -o /dev/null -w '%{http_code}\n' http://192.168.1.21/health
# 排查 2：看 HAProxy 统计页后端状态（DOWN 的原因）
curl -s -u admin:admin123 http://192.168.1.100:8404/stats | grep -A3 web_back
```

### 切换后客户端还连旧主

```shell
# 场景：切换完成但客户端请求仍打到旧 LB 上失败
# 原因：客户端/交换机缓存了旧 VIP→MAC 的 ARP 表，未及时刷新
# 排查：在客户端清 ARP 缓存重试
ip neigh flush all          # 或 arp -d 192.168.1.100
curl -s http://192.168.1.100/
```

## 常见问题

```text
Q1: Keepalived 主备切换，为什么实际由 priority 决定而不是 state？
A: state 只是初始角色声明，VRRP 选举实际比 priority——谁高谁当 MASTER。所以 priority 相同时即使 state 不同也可能双主。

Q2: HAProxy 和 LVS 怎么选？
A: 需要按 URL/Header/Cookie 转发、做七层健康检查、需要日志和统计，用 HAProxy；只做纯四层大流量转发、追求最高吞吐，用 LVS。生产常组合：LVS 在前面抗流量，后面再挂 HAProxy 做七层。

Q3: 为什么健康检查脚本失败了要让 priority 减 20，而不是直接停 keepalived？
A: 减 priority 是「优雅降级」——HAProxy 挂了让出 VIP 给备机，但 keepalived 本身还活着，HAProxy 恢复后（weight 回升）能自动抢回主。直接停 keepalived 则恢复后还得手动拉起，且丢失主备状态。

Q4: VIP 漂移后客户端为什么还能继续用同一个 IP 访问？
A: 靠免费 ARP（gratuitous ARP）——新 MASTER 广播「VIP 的 MAC 是我」，交换机/客户端的 ARP 缓存被刷新，后续流量自动指向新 MASTER，对客户端透明。

Q5: 后端健康检查用 TCP 探测和 HTTP 探测区别？
A: TCP 探测只确认端口能连（进程活着但接口报错也判健康），HTTP 探测确认接口真能正常响应。生产优先 HTTP 探测（option httpchk GET /health），避免「服务假活」。
```

## 面试题

```text
1. 说说 Keepalived 的高可用原理？
   答：基于 VRRP 协议。多台节点组成 VRRP 组，按 priority 选举 MASTER 持有 VIP；MASTER 周期性发 VRRP 通告，BACKUP 超时未收到就抢占 VIP 成为新 MASTER，并通过免费 ARP 通知网络，实现 IP 层无缝切换。

2. 什么是脑裂？Keepalived 怎么防？
   答：脑裂是主备同时认为自己是 MASTER、都持有 VIP，导致双主抢资源。Keepalived 通过 VRRP 组 ID 一致 + 心跳认证（auth_pass）+ priority 唯一来避免；更彻底要靠仲裁机制（奇数节点多数派投票）或 fence 隔离。

3. HAProxy 的调度算法有哪些？分别适用什么场景？
   答：roundrobin（轮询，后端性能一致）、leastconn（最少连接，长连接/耗时不均场景）、source（源地址哈希，会话保持）、uri（URL 哈希，缓存友好）。加权变体用于后端性能不均时按权重分配。

4. LVS 三种转发模式（NAT/DR/TUN）区别？
   答：NAT 模式改 IP、进出都经 LB，LB 是瓶颈；DR 模式改 MAC、后端直接回包，性能最高但要求 LB 和后端同网段；TUN 模式 IP 隧道，支持跨网段但后端要支持隧道协议。生产最常用 DR。

5. 后端一台服务器挂了，HAProxy 多久能摘除它？
   答：由 health check 参数决定：inter 3s × fall 3 = 约 9 秒判定失败并摘除；恢复后 inter 3s × rise 2 = 约 6 秒自动加回。要更快可调小 inter，但增加探测开销。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 主备 priority 明确不同（100/90），virtual_router_id 和 auth_pass 主备严格一致
2. 健康检查用「脚本探测服务」而非只探测进程，HAProxy 挂了要能触发 VIP 漂移
3. 后端健康检查用 HTTP 探测（/health 真实返回 200），不用裸 TCP 探测
4. 改 HAProxy 配置先 `haproxy -c` 校验再 `reload` 热加载，别 `restart`
5. 定期做故障切换演练（停主节点、停服务、停后端三种场景都要练）
6. VIP 切换、后端摘除/加回都要有监控告警，切换了要能第一时间发现
7. HAProxy 统计页加认证并只对内网开放，别暴露公网

### 踩坑记录

```text
坑 1：主备 priority 都写 100，双主脑裂
结论：两台 LB 都持有 VIP，客户端请求时而通时而失败。
原因：priority 相同无法区分主备，VRRP 选举结果不确定。
解法：主 100、备 90（或任何不同值），实际由 priority 决定角色。

坑 2：virtual_router_id 撞了同网段别的 VRRP 组
结论：两组 VRRP 实例互相干扰，VIP 乱漂。
原因：同网段内 VRRP 按 virtual_router_id 分组，ID 撞车会串组。
解法：每套 Keepalived 集群用唯一 ID，上线前先查网段内已用 ID。

坑 3：auth_pass 主备不一致，心跳互不认
结论：主备各自为主，出现双主。
原因：认证密码不一致，VRRP 报文被对方丢弃，都认为对方挂了。
解法：auth_type 和 auth_pass 主备严格一致，配置改动主备同步。

坑 4：健康检查脚本路径不存在，VIP 频繁漂移
结论：keepalived 反复判异常，VIP 在主备之间来回跳。
原因：script 里写的脚本/命令路径不存在或没执行权限，weight 持续扣减。
解法：先手动跑一遍脚本确认能执行、返回码正确，再写进 keepalived.conf。

坑 5：后端 /health 路径没配，HAProxy 把后端全摘除
结论：所有后端被标记 DOWN，VIP 通但没有任何后端可用，请求 503。
原因：option httpchk GET /health 探测的路径后端不存在，返回 404 被判定失败。
解法：后端真实提供 /health 返回 200，或用返回码匹配（http-check expect status 200）。

坑 6：改了 HAProxy 配置直接 restart，正在跑的请求被切断
结论：restart 会中断所有已建立连接，线上用户请求失败。
原因：restart 是停进程再起，reload 才是热加载。
解法：改完先 haproxy -c 校验，再 systemctl reload haproxy 平滑生效。

坑 7：LVS DR 模式没在后端绑 VIP 到 lo，回包走错路由
结论：后端直接回包但源 IP 是 VIP，客户端或交换机丢弃回包，连接超时。
原因：DR 模式后端要用 lo 绑定 VIP 并抑制 ARP，否则 VIP 不生效。
解法：后端 lo 加 VIP（/32），arp_ignore=1、arp_announce=2 抑制 ARP 响应。
```
