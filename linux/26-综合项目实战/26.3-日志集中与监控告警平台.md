## 概述

本项目目标：把多台服务器的日志、指标、告警统一收拢到一个平台，解决「出问题要一台台 SSH 上去翻日志」的低效。分三层：rsyslog/journald 做日志集中，Prometheus + Grafana 做指标采集与可视化，Alertmanager 做告警路由与通知。

技术栈：rsyslog（日志转发与集中）、journald（systemd 日志）、Prometheus（指标采集与时序存储）、node_exporter（主机指标）、Grafana（可视化）、Alertmanager（告警管理）。

前置条件：完成 26.1 基础环境（主机互通、时间同步、防火墙可放行端口）；至少 3 台主机——1 台监控节点（`monitor`，IP `192.168.1.100`）+ 2 台业务节点（`server01`/`server02`）。

```text
交付物：日志统一收到 monitor 的 /var/log/remote/，Prometheus 采集所有主机指标，
Grafana 展示仪表盘，Alertmanager 在指标异常时发邮件/告警
```

## 核心概念

本项目涉及的技术点：

1. **rsyslog 日志集中**：各节点把日志通过 UDP/TCP 转发到中心服务器，中心服务器按来源 IP 分目录存储，实现「一处看所有机器日志」。
2. **journald**：systemd 的日志组件，采集服务（systemd unit）的标准输出和系统日志；通过 `ForwardToSyslog=yes` 可把 journal 日志转给 rsyslog 再集中转发。
3. **Prometheus**：拉取式（pull）指标采集 + 时序数据库（TSDB），用 PromQL 查询指标；配套 node_exporter 暴露主机 CPU/内存/磁盘/网络指标。
4. **Grafana**：接入 Prometheus 作为数据源，用仪表盘可视化指标，是监控的「看板」。
5. **Alertmanager**：接收 Prometheus 触发告警规则产生的告警，做分组、抑制、静默，路由到邮件/企业微信/钉钉等接收端。

```text
核心概念：
rsyslog/journald（日志集中）→ Prometheus + node_exporter（指标采集）→ Grafana（可视化）→ Alertmanager（告警）
```

## 工作原理

1. **日志集中链路**：业务节点产生日志 → journald 采集 → `ForwardToSyslog` 转给本地 rsyslog → rsyslog 按规则通过 UDP/TCP 转发到 monitor 的 514 端口 → monitor 的 rsyslog 接收 → 按来源 IP/程序名分目录落盘 `/var/log/remote/`。
2. **Prometheus 采集链路**：node_exporter 在每台被监控节点监听 9100 端口暴露 `/metrics` → Prometheus 按 `scrape_interval`（默认 15s）定期 HTTP GET 拉取指标 → 存进本地 TSDB → 用户用 PromQL 查询。
3. **告警链路**：Prometheus 定时评估 `rule_files` 里的告警规则 → 命中（表达式为真且持续 `for` 时长）→ 把告警推送给 Alertmanager（默认 9093 端口）→ Alertmanager 按 `route` 分组、去重、抑制、静默 → 发到 `receivers` 配置的邮件/Webhook。

```text
链路汇总：
日志：业务节点 journald → rsyslog → (UDP/TCP 514) → monitor rsyslog → /var/log/remote/
指标：node_exporter(:9100) ← Prometheus 拉取 → TSDB → PromQL 查询 → Grafana 展示
告警：Prometheus 规则评估 → Alertmanager(:9093) → 分组/抑制/静默 → 邮件/Webhook
```

## 常用命令与配置

```shell
# rsyslog（日志集中）
systemctl status rsyslog              # 状态（RHEL 系也是 rsyslog）
rsyslogd -N1                          # 校验配置语法
logger -p user.info "test log"        # 手工发一条测试日志
tail -f /var/log/syslog               # Debian/Ubuntu 看系统日志
tail -f /var/log/messages             # RHEL 系看系统日志

# Prometheus / node_exporter
systemctl status prometheus
promtool check config /etc/prometheus/prometheus.yml   # 校验 Prometheus 配置
promtool check rules /etc/prometheus/rules/            # 校验告警规则
curl -s http://localhost:9100/metrics | head            # 看 node_exporter 指标
curl -s http://localhost:9090/api/v1/query?query=up     # PromQL 查询（up=1 存活）

# Grafana / Alertmanager
systemctl status grafana-server
systemctl status alertmanager
amtool check-config /etc/alertmanager/alertmanager.yml  # 校验 Alertmanager 配置
amtool alert list                                       # 查看当前告警
curl -s http://localhost:9090/api/v1/alerts             # 看 Prometheus 当前告警状态
```

```text
配置要点：
1. 日志转发优先 TCP（可靠），量大或局域网可信环境可 UDP（省开销，但会丢包）
2. Prometheus 是拉取式，被监控节点要放行 9100、监控节点要能访问到
3. 改 Prometheus/Alertmanager 配置后先 promtool/amtool 校验，再 reload
```

## 配置文件解析

### /etc/rsyslog.conf 或 /etc/rsyslog.d/50-default.conf（日志服务器接收端）

```text
# 加载 UDP/TCP 接收模块
module(load="imudp")
input(type="imudp" port="514")

module(load="imtcp")
input(type="imtcp" port="514")

# 模板：按来源 IP 分目录、按程序名分文件
$template RemoteLogs, "/var/log/remote/%FROMHOST-IP%/%PROGRAMNAME%.log"
*.* ?RemoteLogs
```

### /etc/rsyslog.d/remote.conf（业务节点转发端）

```text
# 转发所有级别日志到日志服务器（@=UDP，@@=TCP）
*.* @192.168.1.100:514
```

### /etc/systemd/journald.conf（journald 转 rsyslog）

```text
[Journal]
ForwardToSyslog=yes
```

### /etc/prometheus/prometheus.yml（Prometheus 主配置）

```yaml
global:
  scrape_interval: 15s        # 采集间隔
  evaluation_interval: 15s    # 规则评估间隔

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['localhost:9093']

rule_files:
  - /etc/prometheus/rules/*.yml

scrape_configs:
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']
  - job_name: 'node'
    static_configs:
      - targets: ['192.168.1.100:9100', '192.168.1.11:9100', '192.168.1.12:9100']
```

### /etc/prometheus/rules/node.yml（告警规则）

```yaml
groups:
  - name: node_alerts
    rules:
      - alert: NodeDown
        expr: up == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "节点 {{ $labels.instance }} 宕机"
```

### /etc/alertmanager/alertmanager.yml（告警路由）

```yaml
global:
  resolve_timeout: 5m
  smtp_smarthost: 'smtp.example.com:587'
  smtp_from: 'alertmanager@example.com'
  smtp_auth_username: 'alertmanager@example.com'
  smtp_auth_password: 'password'

route:
  group_by: ['alertname']
  group_wait: 10s
  group_interval: 10s
  repeat_interval: 1h
  receiver: 'default'

receivers:
  - name: 'default'
    email_configs:
      - to: 'ops@example.com'
```

```text
关键字段：
scrape_interval      采集频率，越短越实时、越吃资源
rule_files           告警规则文件路径（Prometheus 负责评估）
targets              采集目标列表（静态配置；动态用 file_sd/consul_sd）
group_by             分组键，同一组告警合并成一条通知
repeat_interval      同一告警重复通知间隔，防轰炸
```

## 应用场景实战

目标：3 台主机（monitor `192.168.1.100`、server01 `192.168.1.11`、server02 `192.168.1.12`），日志集中到 monitor，Prometheus 采集全部主机指标，Grafana 展示，Alertmanager 在宕机/CPU 过高/磁盘满时发邮件。共 8 步。

### 步骤一：环境准备与架构规划

```shell
# 三台主机确认互通、时间同步、主机名正确
# 在每台执行：
hostnamectl set-hostname monitor      # 分别设 monitor / server01 / server02
systemctl enable --now chrony         # 时间同步（日志时间戳和指标对齐都依赖它）
chronyc sources -v

# monitor 放行相关端口（业务节点只在 monitor 拉取时访问 9100，可限源）
sudo ufw allow 9090/tcp     # Prometheus
sudo ufw allow 9093/tcp     # Alertmanager
sudo ufw allow 3000/tcp     # Grafana
sudo ufw allow 514/udp      # rsyslog 接收
sudo ufw allow 514/tcp      # rsyslog 接收
# RHEL 系：sudo firewall-cmd --permanent --add-port={9090,9093,3000}/tcp --add-port=514/{tcp,udp} && sudo firewall-cmd --reload
```

解释：时间不同步会导致日志时间错乱、指标对不齐，先统一；monitor 放行 9090/9093/3000 供访问面板，514 供接收日志。业务节点的 9100 只需对 monitor 开放。

### 步骤二：配置日志服务器（monitor 接收端）

编辑 `/etc/rsyslog.conf`（或新建 `/etc/rsyslog.d/50-remote.conf`）：

```text
module(load="imudp")
input(type="imudp" port="514")

module(load="imtcp")
input(type="imtcp" port="514")

$template RemoteLogs, "/var/log/remote/%FROMHOST-IP%/%PROGRAMNAME%.log"
*.* ?RemoteLogs
& stop
```

```shell
sudo rsyslogd -N1                    # 校验语法
sudo systemctl restart rsyslog
sudo ss -tulnp | grep 514            # 确认监听
```

示例输出：

```text
udp   UNCONN 0      0            0.0.0.0:514       0.0.0.0:*    users:(("rsyslogd",pid=812,fd=7))
tcp   LISTEN 0      128          0.0.0.0:514       0.0.0.0:*    users:(("rsyslogd",pid=812,fd=8))
```

解释：`imudp`/`imtcp` 加载 UDP/TCP 输入模块并监听 514；`RemoteLogs` 模板把日志按来源 IP 建目录、按程序名建文件，`%FROMHOST-IP%` 是 rsyslog 内置属性；`*.* ?RemoteLogs` 把所有来源的日志套用模板写入；`& stop` 表示规则命中后不再继续写本地文件，避免重复。

### 步骤三：配置业务节点日志转发（server01/server02）

在每台业务节点写 `/etc/rsyslog.d/remote.conf`：

```text
*.* @192.168.1.100:514
```

开启 journald 转发，编辑 `/etc/systemd/journald.conf`：

```text
[Journal]
ForwardToSyslog=yes
```

```shell
sudo rsyslogd -N1
sudo systemctl restart rsyslog systemd-journald
# 手工发一条测试日志
logger -p user.info "hello from $(hostname)"
```

回 monitor 验证：

```shell
tail -f /var/log/remote/192.168.1.11/user.log
```

示例输出：

```text
Aug 19 14:20:01 server01 admin: hello from server01
```

解释：`@` 是 UDP、`@@` 是 TCP，生产建议 TCP（可靠，日志不丢）；`ForwardToSyslog=yes` 让 journald 把 systemd 采集的日志（服务 stdout、内核日志）转交本地 rsyslog，再统一转发，这样「journalctl 里能看到」的日志也能集中到 monitor。

### 步骤四：安装 Prometheus（monitor）

```shell
# 下载官方二进制（以 2.53 为例，版本按最新替换）
cd /tmp
wget https://github.com/prometheus/prometheus/releases/download/v2.53.0/prometheus-2.53.0.linux-amd64.tar.gz
tar xzf prometheus-2.53.0.linux-amd64.tar.gz
sudo mkdir -p /etc/prometheus /var/lib/prometheus
sudo cp prometheus-2.53.0.linux-amd64/prometheus promtool /usr/local/bin/
sudo cp -r prometheus-2.53.0.linux-amd64/consoles prometheus-2.53.0.linux-amd64/console_libraries /etc/prometheus/
```

写 systemd unit `/etc/systemd/system/prometheus.service`：

```ini
[Unit]
Description=Prometheus
After=network.target

[Service]
User=prometheus
Group=prometheus
ExecStart=/usr/local/bin/prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/var/lib/prometheus \
  --web.listen-address=:9090
Restart=always

[Install]
WantedBy=multi-user.target
```

```shell
sudo useradd --no-create-home --shell /usr/sbin/nologin prometheus
sudo chown -R prometheus:prometheus /etc/prometheus /var/lib/prometheus
sudo systemctl daemon-reload
sudo systemctl enable --now prometheus
curl -s http://localhost:9090/-/healthy
```

示例输出：

```text
Prometheus is Healthy.
```

解释：官方发行版是编译好的二进制，解压即用；systemd unit 指定 `--config.file` 和 `--storage.tsdb.path`（时序数据落盘目录）；`--web.listen-address=:9090` 指定监听端口。用独立 `prometheus` 用户跑，最小权限。

### 步骤五：部署 node_exporter（所有节点）

在 monitor、server01、server02 三台都装：

```shell

```

写 `/etc/systemd/system/node_exporter.service`：

```ini

After=network.target

[Service]
User=node_exporter
Group=node_exporter
ExecStart=/usr/local/bin/node_exporter
Restart=always

[Install]

```

```shell

curl -s http://localhost:9100/metrics | head -n 5
```

示例输出：

```text
# HELP node_cpu_seconds_total Seconds the CPUs spent in each mode.
# TYPE node_cpu_seconds_total counter
node_cpu_seconds_total{cpu="0",mode="idle"} 1.325801e+06
```

解释：node_exporter 默认监听 9100，暴露 `/metrics` 的文本格式指标；`node_cpu_seconds_total`、`node_memory_MemAvailable_bytes`、`node_filesystem_avail_bytes` 等是后续告警规则和仪表盘要用的核心指标。

### 步骤六：配置 Prometheus 采集目标与告警规则

写 `/etc/prometheus/prometheus.yml`（完整配置见「配置文件解析」），重点是 `scrape_configs` 三个 target 指向三台机器的 9100。再写告警规则 `/etc/prometheus/rules/node.yml`：

```yaml
groups:
  - name: node_alerts
    rules:
      - alert: NodeDown
        expr: up == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "节点 {{ $labels.instance }} 宕机"
      - alert: HighCPUUsage
        expr: 100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} CPU 使用率超过 80%"
      - alert: HighDiskUsage
        expr: (node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) * 100 < 10
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} 根分区可用空间低于 10%"
```

```shell
sudo chown -R prometheus:prometheus /etc/prometheus
promtool check config /etc/prometheus/prometheus.yml
promtool check rules /etc/prometheus/rules/node.yml
sudo systemctl restart prometheus
curl -s 'http://localhost:9090/api/v1/query?query=up'
```

示例输出：

```text
{"status":"success","data":{"resultType":"vector","result":[
{"metric":{"__name__":"up","instance":"192.168.1.100:9100","job":"node"},"value":[1724059201,"1"]},
{"metric":{"__name__":"up","instance":"192.168.1.11:9100","job":"node"},"value":[1724059201,"1"]},
{"metric":{"__name__":"up","instance":"192.168.1.12:9100","job":"node"},"value":[1724059201,"1"]}]}}
```

解释：`up == 0` 表示采集目标不可达（node_exporter 挂了或节点宕机），是最基础的存活告警；CPU 规则用 `rate(...[5m])` 算 5 分钟平均 CPU 使用率，`for: 5m` 要求持续 5 分钟才告警，避免瞬时抖动误报；`{{ $labels.instance }}` 是模板变量，告警内容里带上实例名。

## 性能与调优

```text
1. 日志转发选型 —— 高可靠场景用 TCP（imtcp），高吞吐局域网可信环境用 UDP（少握手、省开销）
2. scrape_interval 平衡 —— 15s 是通用值；抓取目标多（>100）时调到 30s~60s，降低 Prometheus 自身负载
3. 日志磁盘配额 —— /var/log/remote 会持续增长，配 logrotate 轮转 + 保留天数，别让日志写满磁盘
4. TSDB 保留期 —— Prometheus 默认保留 15 天（--storage.tsdb.retention.time），按磁盘容量调整
5. node_exporter 采集项裁剪 —— --collector.disable-defaults 只开需要的 collector，减少暴露面
6. Grafana 查询优化 —— 大时间范围聚合用 avg/rate 而非原始点，减少 Prometheus 查询压力
```

```shell
# 调整 TSDB 保留期到 30 天（在 ExecStart 里加参数）
--storage.tsdb.retention.time=30d
```

## 安全与权限

```text
1. 最小权限 —— Prometheus/Alertmanager/node_exporter 都用独立无 shell 用户（nologin）跑
2. 端口收敛 —— node_exporter 的 9100 只对 monitor 开放，不对公网；Grafana/Prometheus 面板走内网或加认证
3. 日志防篡改 —— /var/log/remote 目录权限收紧（700），只有 root/rsyslog 可读写，防止业务节点互相看日志
4. Grafana 强密码 —— 默认 admin/admin 首次登录必须改，生产接 LDAP/OAuth
5. SMTP 凭证 —— Alertmanager 的 smtp_auth_password 别明文进仓库，用环境变量或配置管理注入
6. 日志内容脱敏 —— 集中日志可能含敏感信息（密码、token），转发前在 rsyslog 用 mmrfc5424/自定义规则做脱敏
```

```shell
# 收紧日志目录权限
sudo chmod 700 /var/log/remote
# 只放行 monitor 访问 node_exporter（业务节点上执行，假设 monitor 为 192.168.1.100）
sudo ufw allow from 192.168.1.100 to any port 9100
```

## 故障排查

### 日志收不到（monitor 的 /var/log/remote 没新文件）

```shell
# 1. 确认 monitor 监听 514
sudo ss -tulnp | grep 514
# 2. 确认业务节点能连通
nc -vz 192.168.1.100 514
# 3. 确认业务节点 rsyslog 转发配置生效
sudo rsyslogd -N1 && sudo systemctl status rsyslog
# 4. 看业务节点本地日志有没有转发报错
sudo tail -f /var/log/syslog | grep rsyslog
# 常见原因：防火墙挡 514、转发方向写反（@@ 写成 @）、rsyslog 没重启
```

### Prometheus 显示 target down

```shell
# 1. 看 target 状态和报错
curl -s http://localhost:9090/api/v1/targets | grep -A5 down
# 2. 从 Prometheus 机器直接 curl node_exporter
curl -s http://192.168.1.11:9100/metrics | head
# 常见原因：node_exporter 没启动、9100 被防火墙挡、scrape_configs 里 IP 写错
```

### 告警没触发 / 没收到邮件

```shell
# 1. 看规则是否命中（Prometheus 侧）
curl -s http://localhost:9090/api/v1/alerts
# 2. 看 Alertmanager 是否收到告警
amtool alert list
# 3. 看 Alertmanager 日志（SMTP 报错常在这）
sudo journalctl -u alertmanager -n 50
# 常见原因：for 时长未满足、SMTP 配置错（端口/密码/SSL）、route 的 receiver 名拼错
```

## 常见问题

```text
Q1: rsyslog 转发用 UDP 还是 TCP？
A: 局域网可信环境、能容忍少量丢失用 UDP（省开销、吞吐高）；跨网段或要求不丢日志用 TCP（@@）。生产建议 TCP。

Q2: journald 和 rsyslog 什么关系？
A: journald 是 systemd 的日志采集组件（管服务 stdout、内核日志），rsyslog 是传统 syslog 服务。两者可配合：journald 采集后用 ForwardToSyslog=yes 转给 rsyslog，rsyslog 再集中转发，各取所长。

Q3: Prometheus 为什么是拉取式而不是推送式？
A: 拉取式由 Prometheus 主动抓取，天然知道「目标是否存活」（抓不到就是 down），且被监控端无需配置监控端地址，更简单；推送式（pushgateway 场景）用于短生命周期任务。

Q4: Grafana 和 Prometheus 的分工？
A: Prometheus 负责采集 + 存储 + 查询（PromQL），Grafana 只负责展示和告警通知呈现，本身不存数据。仪表盘数据都来自 Prometheus 数据源。

Q5: Alertmanager 的 group_by 和 repeat_interval 干嘛用？
A: group_by 把同组告警合并成一条通知（比如一次宕机导致 10 条告警只发 1 封邮件）；repeat_interval 控制同一告警多久重复通知一次，防止告警风暴刷屏。
```

## 面试题

```text
1. 设计一个日志集中方案，你会怎么选型？
   答：业务节点 journald 采集 → ForwardToSyslog 转 rsyslog → TCP 514 转发到中心 → 中心按来源 IP 分目录落盘 + logrotate 轮转。量大上 ELK（Filebeat + Elasticsearch + Kibana）做全文检索，日志归档走冷存储。

2. Prometheus 的核心架构和采集模型？
   答：拉取式（pull）——Prometheus 定时 HTTP GET 各 exporter 的 /metrics 抓取指标存入本地 TSDB，用 PromQL 查询。组件含 Prometheus Server（采集+存储）、exporter（暴露指标）、Alertmanager（告警）、Grafana（可视化）。

3. 一条告警从产生到通知经历了什么？
   答：Prometheus 按 evaluation_interval 评估 rule_files → 表达式为真且持续 for 时长 → 生成告警推送 Alertmanager → Alertmanager 按 route 分组/抑制/静默 → 发到 receivers（邮件/Webhook）。

4. 如何避免告警风暴（一次故障刷几百条通知）？
   答：Alertmanager 用 group_by 把相关告警合并成一条通知；group_wait 等一段收集窗口再发；repeat_interval 控制重复通知间隔；抑制规则（inhibit）用高等级告警抑制低等级告警；静默（silence）在计划维护时临时压制。

5. up == 0 和 target down 是一回事吗？
   答: 是。up 是 Prometheus 内置指标，抓取成功为 1、失败为 0；up == 0 即该 target 不可达（exporter 挂了/节点宕机/网络不通）。是监控里最基础的存活告警。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 日志转发用 TCP，业务关键日志宁慢不丢；日志服务器磁盘单独分区并配 logrotate
2. 时间同步先做好（chrony），否则日志时间戳和指标时间轴对不齐，排查痛苦
3. 告警规则加 `for` 时长（1m~5m），过滤瞬时抖动，只报持续性问题
4. Alertmanager 配 group_by + repeat_interval + 抑制规则，防止告警风暴
5. 用 promtool/amtool 校验配置再 reload，别直接 restart 载入可能写错的配置
6. 关键告警（宕机/磁盘满）接双通道（邮件 + 企业微信/钉钉），避免邮件漏看
7. Grafana 导入社区仪表盘（Node Exporter Full 1860）起步，再按业务裁剪

### 踩坑记录

```text
坑 1：rsyslog 转发方向写反，日志收不到
结论：monitor 的 /var/log/remote 一直没新文件。
原因：转发配置里 @@ 写反了方向，或把接收端也配了转发规则。
解法：业务节点只配 `*.* @@日志服务器:514`，monitor 只配 input 接收；两边职责分开。

坑 2：UDP 转发丢日志，排查半天以为服务没写
结论：少量日志莫名丢失，找不到完整上下文。
原因：UDP 无连接无确认，网络抖动或 rsyslog 队列满时静默丢包。
解法：关键日志改 TCP（@@），rsyslog 配 action 队列缓冲（queue.type="linkedlist"）减少丢包。

坑 3：node_exporter 起来了但 Prometheus 一直 down
结论：target 状态 down，报 connection refused。
原因：业务节点防火墙没放行 9100，或只放行了对公网。
解法：业务节点放行 9100 且限定来源为 monitor IP（ufw allow from 192.168.1.100 to any port 9100）。

坑 4：告警规则命中但收不到邮件
结论：Prometheus 里告警状态是 firing，邮箱却没动静。
原因：Alertmanager 的 smtp 配置错（端口/SSL/密码），或 route 的 receiver 名与 receivers 里定义不一致。
解法：journalctl -u alertmanager 看 SMTP 报错；amtool check-config 校验配置；receiver 名字必须一一对应。

坑 5：磁盘被日志/TSDB 写满，监控平台自己挂了
结论：/var/log/remote 或 /var/lib/prometheus 把根分区写满，Prometheus 停止写入。
原因：没配 logrotate 轮转，没设 TSDB 保留期，日志无限增长。
解法：日志目录单独分区 + logrotate 保留 N 天；Prometheus 设 --storage.tsdb.retention.time=30d。

坑 6：告警风暴，一次宕机刷几百封邮件
结论：故障时邮箱被刷屏，真正重要告警被淹没。
原因：没配 group_by，每个 instance 每条规则各发一封，repeat_interval 太短。
解法：group_by: ['alertname'] 合并，repeat_interval 设 1h 以上，加 inhibit 规则用高等级抑制低等级。
```
