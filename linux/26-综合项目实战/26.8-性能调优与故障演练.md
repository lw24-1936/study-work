## 概述

本项目目标：掌握「用数据说话」的性能调优闭环，以及「主动制造故障」的混沌演练。性能调优不是凭感觉改参数，而是「压测 → 定位瓶颈 → 调优 → 再压测验证」的循环；混沌演练则反过来——故意注入故障（CPU 打满、内存耗尽、网络延迟、进程被杀），验证系统在故障下的表现和自愈能力。

本项目覆盖四个环节：压测（ab/wrk 测吞吐与延迟）、火焰图定位（perf 采样 + 栈聚合可视化找热点）、内存/IO/网络调优（sysctl、调度器、TCP 参数）、混沌演练（chaosblade 故障注入）。

技术栈：压测工具 ab/wrk、性能分析 perf + FlameGraph、系统观测 vmstat/iostat/pidstat/sar、故障注入 chaosblade。

前置条件：一台压测机 + 一台被测机（压测机别和被压服务同机，否则结果被干扰），已部署一个 Web 服务（如 26.2 的 nginx），有 root 或 sudo 权限。

```text
交付物：一份性能基线报告 + 一套可复用的调优方法 + 一次完整混沌演练记录（注入了什么、系统如何反应、如何恢复）
```

## 核心概念

本项目涉及的技术点：

1. **压测（load testing）**：用工具模拟并发请求，测出系统在特定负载下的吞吐量（QPS）、延迟（P50/P95/P99）和资源占用。ab（ApacheBench）简单直接，wrk 支持 Lua 脚本、并发能力更强。压测的产物是「性能基线」，后续调优都拿它对比。
2. **火焰图定位（flame graph）**：perf 以固定频率（如 99Hz）采样 CPU 调用栈，把采样到的栈按「调用关系 + 出现次数」聚合成一张 SVG 图——x 轴宽度 = 采样占比，越宽的栈越消耗 CPU。一眼定位热点函数，是 CPU 性能分析的利器。
3. **内存/IO/网络调优**：内存调 vm.swappiness、dirty 参数、排查泄漏；IO 调磁盘调度器、noatime、用 fio 测真实吞吐；网络调 TCP 参数（somaxconn、tw_reuse、缓冲区）、网卡多队列。
4. **混沌演练（chaos engineering）**：主动向生产/准生产注入故障（CPU 打满、内存泄漏、磁盘 IO 打满、网络延迟、进程 kill），观察系统是否按预期降级、告警是否触发、能否自愈，验证「系统对故障的假设」。

```text
调优闭环（四步循环）：
压测建基线 → 观测定位瓶颈（perf/火焰图/vmstat/iostat）→ 针对性调优 → 再压测验证收益
混沌演练（主动找茬）：
定义稳态 → 注入故障 → 观察反应 → 恢复与复盘 → 加固
```

## 工作原理

四个环节的底层机制：

1. **压测原理**：工具维护一个并发连接池，持续发请求并计时，统计完成数/总耗时得出 QPS 和延迟分布。核心规律是 Little's law：`并发数 = QPS × 平均响应时间`——想压到高 QPS，要么提并发、要么降延迟。当系统到达瓶颈（CPU/内存/连接数饱和），延迟会急剧上升、QPS 不再增长，这个拐点就是容量上限。
2. **perf 采样原理**：perf 基于内核 perf_event 子系统，可用硬件性能计数器（cycles、cache-miss 等）或软件事件（cpu-clock）。`perf record -F 99` 每秒 99 次（频率取质数 99 减少锁同步伪影）触发中断、记录当时进程的调用栈；`perf report` 把栈聚合成调用树统计。它靠「采样」而非「插桩」，开销低（<5%），适合生产在线分析。
3. **火焰图原理**：把 perf 的采样栈按「每一层调用」累加计数，横向堆叠成条。最底部是入口函数，越往上越靠叶函数；某条的宽度 = 该函数出现在采样栈里的次数占比。宽而平的条 = 直接消耗 CPU 的热点，宽且上面还压着别的 = 被调用者拖累。
4. **混沌工程原理**：核心是「验证假设」。生产系统的稳定性假设（「Nginx 挂了会自动拉起」「数据库主库挂断会切从库」）平时不成立时不会被发现。混沌演练就是主动击穿这些假设：定义稳态指标 → 注入故障 → 观察稳态是否被打破 → 恢复 → 把发现的问题反馈加固。

```text
perf 采样 vs 火焰图关系：
perf record 采样（原始栈）→ perf script 导出文本 → stackcollapse 折叠成「栈路径 计数」→ flamegraph 渲染成 SVG
CPU 热点 = 火焰图上最宽的条；横轴是采样占比，纵轴是调用栈深度
```

## 常用命令与配置

```shell
# 压测
ab -n 10000 -c 100 http://127.0.0.1/        # ab：1 万请求、100 并发
ab -k -n 10000 -c 100 http://127.0.0.1/     # -k 启用 keep-alive
wrk -t4 -c100 -d30s http://127.0.0.1/       # wrk：4 线程、100 连接、压 30 秒
wrk -t4 -c100 -d30s --latency http://127.0.0.1/   # 输出延迟分布

# perf 与火焰图
perf stat -p <pid> sleep 10                 # 统计进程 10 秒的硬件事件
perf record -F 99 -g -p <pid> -- sleep 30   # 99Hz 采样进程 30 秒（-g 记调用栈）
perf report --stdio                         # 文本化看调用树
perf top -g                                 # 实时看热点
perf script > out.perf                      # 导出采样栈

# 系统观测
vmstat 1 5                                  # 内存/CPU/IO/swap 每秒采样
iostat -x 1                                 # 磁盘 IO 扩展指标（await/util/r/s）
pidstat -u 1                                # 每个进程 CPU 占用
mpstat -P ALL 1                             # 每核 CPU
sar -n DEV 1                                # 网络设备流量
free -h                                     # 内存/swap
ss -s                                       # 连接状态统计

# 磁盘/网络调优
cat /sys/block/sda/queue/scheduler          # 看磁盘调度器
echo mq-deadline > /sys/block/sda/queue/scheduler   # 设调度器（NVMe 用 none）
sysctl vm.swappiness=10                     # 降低 swap 倾向
sysctl net.core.somaxconn=65535             # 监听队列上限

# 混沌演练（chaosblade）
blade create cpu fullload --cpu-percent 80            # CPU 打满 80%
blade create mem load --mode ram --mem-percent 80     # 占 80% 内存
blade create disk burn --read --size 1024             # 磁盘读压力 1024M
blade create network delay --time 3000 --offset 100 --interface eth0 --local-port 8080   # 8080 端口延迟 3 秒
blade create process kill --process nginx             # 杀掉 nginx 进程
blade status --type create                             # 查看正在执行的注入
blade destroy <uid>                                    # 撤销某个注入
```

```text
工具分工：
ab           轻量、够用，适合快速压 HTTP 接口；并发模型老、不支持脚本
wrk          多线程事件驱动，压测能力强，Lua 脚本可自定义请求，适合高并发场景
perf         内核级性能分析，采样 CPU 栈、硬件事件，火焰图的原始数据来源
FlameGraph   Brendan Gregg 的脚本集，把 perf 栈渲染成火焰图
vmstat/iostat/sar  系统级观测，分别看内存/CPU、磁盘 IO、网络
chaosblade   阿里的混沌工程工具，一条命令注入 CPU/内存/磁盘/网络/进程故障
```

## 配置文件解析

### /etc/sysctl.d/99-network-tuning.conf（网络调优）

```text
net.core.somaxconn = 65535              # 监听 socket 的 accept 队列上限
net.core.netdev_max_backlog = 65535     # 网卡收包队列上限
net.ipv4.tcp_max_syn_backlog = 8192     # SYN 队列上限（抗并发建连）
net.ipv4.tcp_syncookies = 1             # SYN 队列满时启用 cookie 抗 SYN 洪水
net.ipv4.tcp_tw_reuse = 1               # 复用 TIME_WAIT 连接（客户端场景）
net.ipv4.tcp_fin_timeout = 30           # FIN_WAIT_2 超时缩短，减少半连接占用
net.ipv4.ip_local_port_range = 1024 65000   # 本地临时端口范围（压测机常要调大）
net.core.rmem_max = 16777216            # 接收缓冲区上限（16M）
net.core.wmem_max = 16777216            # 发送缓冲区上限（16M）
net.ipv4.tcp_rmem = 4096 87380 16777216     # TCP 接收缓冲 min/default/max
net.ipv4.tcp_wmem = 4096 65536 16777216     # TCP 发送缓冲 min/default/max
```

### /etc/security/limits.conf（文件描述符/资源限制）

```text
*       soft    nofile  65535       # 普通用户单进程可打开文件数（soft 上限）
*       hard    nofile  65535       # hard 上限（root 可再调高）
root    soft    nofile  1000000
```

### /etc/fstab（磁盘挂载优化）

```text
# 生产数据盘挂载去 atime，减少每次读的写放大
/dev/mapper/rl-data  /data  xfs  defaults,noatime  0  2
```

### tuned 调优 profile（RHEL 系）

```shell
tuned-adm list                 # 列出所有 profile（throughput-performance/latency-performance/...）
tuned-adm profile throughput-performance   # 切到吞吐优先 profile
tuned-adm active               # 查看当前生效 profile
```

解释：tuned 是 RHEL 的自动化调优框架，一个 profile 打包了一组 sysctl/调度器/电源策略，`throughput-performance` 适合 Web/数据库，`latency-performance` 适合低延迟交易系统，比手改参数省事且经过验证。

## 应用场景实战

目标：被测机 `203.0.113.20` 上跑 nginx（静态页 + 一个 PHP 动态页），压测机 `203.0.113.21` 从外部压。从建基线到调优到混沌演练，共 9 步。

### 步骤一：建立性能基线

动手调优前，先记录系统当前状态，否则调完不知道「有没有变好」：

```shell
# 1. 系统负载与 CPU
uptime
# 2. 内存与 swap
free -h
# 3. CPU 型号与核数（决定压测目标）
lscpu | grep -E 'Model name|^CPU\(s\)'
# 4. 磁盘与 IO 调度器
lsblk && cat /sys/block/sda/queue/scheduler
# 5. 网络连接状态
ss -s
```

解释：`uptime` 的 load average 是「1/5/15 分钟平均的活跃任务数」，长期 > CPU 核数说明过载；`lscpu` 看核数，压测目标一般先定「单机 QPS 上限」，再和核数对照判断是否合理；`ss -s` 看 TIME_WAIT/ESTAB 分布，短连接多的话 TIME_WAIT 会堆积。

示例输出：

```text
 14:02:11 up 5 days,  3:44,  1 user,  load average: 0.08, 0.12, 0.10
               total        used        free      shared  buff/cache   available
Mem:            15Gi       2.1Gi       4.2Gi       256Mi       9.1Gi        12Gi
Swap:          2.0Gi          0B       2.0Gi
Model name:            Intel(R) Xeon(R) Gold 6248 CPU @ 2.50GHz
CPU(s):                4
```

### 步骤二：ab 压测 Web 服务

从压测机对 nginx 静态页压测，拿第一份 QPS/延迟数据：

```shell
# 1 万请求、100 并发
ab -n 10000 -c 100 http://203.0.113.20/
# 加 keep-alive（贴近真实浏览器行为，结果会明显更好）
ab -k -n 10000 -c 100 http://203.0.113.20/
```

解释：`-n` 总请求数、`-c` 并发连接数。不带 `-k` 每次请求都新建 TCP 连接（三次握手 + TIME_WAIT 开销），带 `-k` 复用连接——两个结果差异大，报告里要写清楚测的是哪种。重点看 Requests per second（QPS）和 Time per request（单个请求平均耗时，别和第二个「并发平均」混淆）。

示例输出（节选）：

```text
Concurrency Level:      100
Time taken for tests:   2.846 seconds
Complete requests:      10000
Failed requests:        0
Requests per second:    3513.94 [#/sec] (mean)
Time per request:       28.458 [ms] (mean)
Time per request:       0.285 [ms] (mean, across all concurrent requests)
Transfer rate:          4231.55 [Kbytes/sec] received
```

解释：3513 QPS、平均 28ms 就是本机静态页的初始基线。注意 `Time per request` 有两行：28.458ms 是「用户感知的单个请求延迟」，0.285ms 是「服务器处理吞吐的换算值」，别混淆。

### 步骤三：wrk 进阶压测

ab 并发模型弱，高并发场景换 wrk：

```shell
# 4 线程、100 连接、压 30 秒，输出延迟分布
wrk -t4 -c100 -d30s --latency http://203.0.113.20/
# 提升并发到 500，看吞吐拐点
wrk -t4 -c500 -d30s --latency http://203.0.113.20/
```

解释：wrk 的 `-t` 是压测线程数、`-c` 是总连接数、`-d` 时长；`--latency` 输出 P50/P90/P99 延迟分布，比 ab 只给平均值有用得多——平均值会掩盖长尾，P99 才是用户体验的真实指标。把并发从 100 提到 500，观察 QPS 是否线性增长：若 QPS 不再涨、P99 飙升，说明已到容量瓶颈。

示例输出（节选）：

```text
Running 30s test @ http://203.0.113.20/
  4 threads and 100 connections
  Thread Stats   Avg      Stdev     Max   +/- Stdev
    Latency     7.22ms   12.05ms 210.33ms   92.18%
    Req/Sec     3.89k   610.30     5.62k    78.33%
  Latency Distribution
     50%    3.84ms
     75%    7.98ms
     90%   15.12ms
     99%   48.55ms
  466748 requests in 30.03s, 562.14MB read
Requests/sec:  15542.98
```

解释：wrk 压出 15542 QPS（比 ab 高，因为事件驱动 + 长连接复用），P99 是 48.55ms——这就是本机 nginx 静态页的容量参考，作为后续调优的对照基线。

### 步骤四：CPU 热点定位（perf）

压测时系统 CPU 打满、QPS 上不去，用 perf 找热点进程和热点函数：

```shell
# 1. 先找谁在吃 CPU（压测期间另开终端在被测机跑）
top -bn1 | head -n 15
pidstat -u 1 5
# 2. 对热点进程采样 30 秒（假设 nginx worker pid=12345）
perf record -F 99 -g -p 12345 -- sleep 30
# 3. 文本化看调用树（--stdio 便于脚本/文本查看）
perf report --stdio --no-children | head -n 40
```

解释：`top`/`pidstat` 先定位「哪个进程」吃 CPU（可能是 nginx worker，也可能是别的）；`perf record -F 99 -g` 以 99Hz 采样该进程 30 秒、记录调用栈；`perf report --no-children` 显示「每个函数自身消耗的 CPU 占比」（不加 `--no-children` 会把被调用者的开销也算到调用者头上，干扰判断）。

示例输出（节选）：

```text
# Overhead  Command  Shared Object     Symbol
    34.21%  nginx    nginx             [.] ngx_http_core_find_config_phase
    12.03%  nginx    nginx             [.] ngx_http_parse_request_line
     8.77%  nginx    libc-2.34.so      [.] memcpy
```

解释：`ngx_http_core_find_config_phase` 占 34% 说明大量时间花在请求匹配阶段，是热点；文本版能看数字，但火焰图更直观（下一步）。

### 步骤五：火焰图生成与解读

把 perf 采样栈渲染成火焰图：

```shell
# 1. 导出采样栈
perf script > out.perf
# 2. 下载 FlameGraph 脚本集（一次性）
git clone https://github.com/brendangregg/FlameGraph.git
# 3. 折叠栈 + 生成火焰图
perf script | ./FlameGraph/stackcollapse-perf.pl > out.folded
./FlameGraph/flamegraph.pl out.folded > flame.svg
# 4. 用浏览器打开 flame.svg（本地 scp 下来或直接传图）
```

解释：`stackcollapse-perf.pl` 把每行「栈帧列表 + 计数」折叠成「完整栈路径 1 次」的格式；`flamegraph.pl` 据此渲染 SVG。火焰图上 x 轴是采样占比、y 轴是栈深度，最宽的「平顶」就是 CPU 热点——点击可交互缩放。

示例输出（描述火焰图形态，浏览器里看 SVG）：

```text
底部最宽的条：__libc_start_main → main → ngx_worker_process_cycle
中间热点：ngx_http_core_find_config_phase（占整图约 1/3 宽度）
顶部细条：memcpy / ngx_http_parse_request_line 等叶子函数
```

解释：`find_config_phase` 那条又宽又平，是直接烧 CPU 的地方；`memcpy` 是叶子、宽度小，说明拷贝不是主因。有了这张图就能锁定「调哪个函数、优化哪段逻辑」，而不是瞎猜。

### 步骤六：内存调优

先观测内存和 swap 行为，再针对性调：

```shell
# 1. 看内存与 swap 状态
free -h
vmstat 1 5
# 2. 看是不是 swap 频繁换页（si/so 持续非 0 说明在换页）
vmstat -s | grep -E 'swap'
# 3. 降低 swap 倾向（立即生效 + 永久写入）
sysctl vm.swappiness=10
echo 'vm.swappiness=10' > /etc/sysctl.d/99-swappiness.conf
# 4. 调 dirty 参数（写缓存回收节奏，IO 密集场景）
sysctl vm.dirty_ratio=15 vm.dirty_background_ratio=5
```

解释：`vmstat` 的 `si`/`so` 列是 swap 换入换出，持续非零说明物理内存不够、在换页，这是性能杀手；`vm.swappiness=10` 让内核「优先用内存、少用 swap」（默认 60 太激进，内存稍紧张就开始换页）；`vm.dirty_ratio` 控制脏页占比阈值，调低能让写缓存更早刷盘，避免突发大量写 IO。

排查内存泄漏（以某服务内存持续增长为例）：

```shell
# 5. 看进程内存随时间变化
pidstat -r -p <pid> 1 10
# 6. 看 OOM 记录
dmesg | grep -i -E 'oom|killed process'
```

示例输出：

```text
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 1  0      0 4218048 934212 9536204  0    0     0    12  114  210  3  1 96  0  0
```

解释：`si`/`so` 全 0、free 还有 4G、cache 9G——说明内存充足、无换页，`cache` 高是正常的（内核把空闲内存用来缓存文件，需要时会释放，`free -h` 的 available 才是真正可用量）。

### 步骤七：IO 调优

```shell
# 1. 看磁盘 IO 压力（await 高 = IO 排队，util 满 = 磁盘饱和）
iostat -x 1
# 2. 用 fio 测真实磁盘吞吐/延迟（随机写 4K）
fio --name=randwrite --ioengine=libaio --rw=randwrite --bs=4k --size=1G --numjobs=4 --runtime=30 --time_based --filename=/tmp/fio.test
# 3. 看磁盘调度器并切换（HDD 用 mq-deadline，NVMe SSD 用 none）
cat /sys/block/sda/queue/scheduler
echo mq-deadline > /sys/block/sda/queue/scheduler
# 4. 数据盘挂载去 atime（/etc/fstab 加 noatime 后）
mount -o remount /data
```

解释：`iostat -x` 重点看 `await`（单次 IO 平均等待时间）和 `%util`（磁盘忙碌度）——`await` 持续几十 ms、`%util` 接近 100% 就是磁盘瓶颈；fio 用 `libaio` 引擎、`randwrite` 随机写测最坏情况，`--numjobs=4` 四路并发；调度器 HDD 用 `mq-deadline`（兼顾吞吐和延迟）、NVMe 直接用 `none`（绕过调度、直通硬件）。

示例输出：

```text
Device            r/s     w/s     rkB/s     wkB/s   await  r_await  w_await  %util
sda              12.00  280.00    356.0   8920.0    2.31     1.02     2.87  65.20
```

解释：`await` 2.31ms、`%util` 65%——磁盘没到瓶颈，`w/s` 280 说明写请求多，如果应用是读多写少却看到写多，就要查是不是日志/缓存刷盘太频繁。

### 步骤八：网络调优

```shell
# 1. 看连接状态分布（TIME_WAIT 堆积说明短连接多）
ss -s
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn
# 2. 写网络调优参数并生效（内容见配置文件解析节）
sysctl --system
# 3. 查网卡是否有丢包/重传
ethtool -S eth0 | grep -E 'drop|error'
netstat -s | grep -E 'retransmit|listen'
# 4. 查网卡多队列（高吞吐要开多队列分散到多核）
ethtool -l eth0
```

解释：`ss -tan` 统计各状态连接数，TIME_WAIT 过多（短连接 + 高并发）会占端口和内存，用 `tcp_tw_reuse` 复用；`ethtool -S` 看网卡统计的丢包/错误计数；`netstat -s` 里的 `retransmit` 是重传数，高说明网络拥塞/丢包；多队列（`ethtool -l` 看 Combined 队列数）把收包分散到多核，是万兆网卡的标配。

示例输出：

```text
Total: 428 (kernel 456)
TCP:   402 (estab 120, closed 268, timewait 260, ...)
```

解释：`timewait 260` 远大于 `estab 120`，是典型的短连接场景（如 PHP 直连 MySQL 每次新建连接），调 `tcp_tw_reuse` 能复用 TIME_WAIT 连接、缓解端口耗尽。

### 步骤九：chaosblade 混沌演练

安装 chaosblade 并注入几类故障，验证系统反应：

```shell
# 1. 下载并解压 chaosblade（阿里开源，二进制免安装）
wget https://github.com/chaosblade-io/chaosblade/releases/download/v1.7.4/chaosblade-1.7.4-linux-amd64.tar.gz
tar -zxvf chaosblade-1.7.4-linux-amd64.tar.gz
cd chaosblade-1.7.4 && ./blade version
# 2. 注入 CPU 打满 80%（模拟 CPU 突增）
./blade create cpu fullload --cpu-percent 80
# 3. 观察系统反应（另开终端）
uptime && top -bn1 | head -n 5
# 4. 查看注入并撤销
./blade status --type create
./blade destroy <上一步返回的 UID>
```

解释：`blade create cpu fullload --cpu-percent 80` 起一个烧 CPU 的进程占 80% 核；`blade status` 列出当前注入、`blade destroy <uid>` 撤销。演练时要观察：load 是否飙升、监控告警是否触发、业务延迟是否恶化、撤销后是否自动恢复。

其余几类故障注入：

```shell
# 内存占 80%（模拟内存泄漏/耗尽）
./blade create mem load --mode ram --mem-percent 80
# 磁盘读压力（模拟磁盘打满）
./blade create disk burn --read --size 1024
# 网络延迟 3 秒 + 抖动 100ms（模拟网络抖动）
./blade create network delay --time 3000 --offset 100 --interface eth0 --local-port 8080
# 杀掉 nginx 进程（模拟进程崩溃，验证 systemd 是否自动拉起）
./blade create process kill --process nginx
# 验证 nginx 是否被 systemd 自动拉起
systemctl status nginx
```

解释：`mem load --mode ram` 分配内存占满 80%，可验证 OOM killer 是否会杀掉不该杀的进程；`network delay` 给 8080 端口加 3 秒延迟，验证超时重试和熔断逻辑；`process kill --process nginx` 杀 nginx，验证 systemd 的 `Restart=always` 是否真的能拉起——很多「以为配了自愈」的系统，演练一次就现原形。

演练记录模板：

```text
故障注入：cpu fullload 80%
稳态假设：CPU 打满时 nginx 响应延迟仍 <100ms、告警在 1 分钟内触发
观察结果：load 从 0.1 涨到 3.2，P99 延迟从 48ms 涨到 210ms，CPU 告警 45 秒后触发
结论：业务延迟明显恶化但未中断，告警及时；加固项 = 为 CPU 加自动扩容/限流阈值
```

## 性能与调优

```text
1. USE 方法（资源视角）—— 对每类资源（CPU/内存/磁盘/网络）查 Utilization（利用率）、Saturation（饱和）、Errors（错误），先定位是哪类资源到瓶颈再深挖
2. RED 方法（服务视角）—— Rate（请求速率）、Errors（错误率）、Duration（延迟），从服务指标倒推
3. 调优要「先测后调」—— 没基线就调，调完不知道有没有用，甚至越调越差
4. 一次只改一个变量 —— 同时改多个参数，性能变了不知道是谁的功劳
5. 优先用 tuned 这种经过验证的 profile，再手工微调个别参数
6. 火焰图看 on-CPU 热点；IO 等待、锁等待要看 off-CPU 火焰图（perf sched record）
```

```shell
# 一键切 tuned 吞吐优先 profile（RHEL 系）
tuned-adm profile throughput-performance
tuned-adm active
```

## 安全与权限

```text
1. perf 采样需要权限 —— perf_event_paranoid 默认（2）下非 root 只能采样自己的进程；生产分析可能要 root 或调低该值
2. 压测别打生产 —— 压测流量会真实消耗资源、可能把生产打挂；用独立的压测机 + 准生产环境
3. chaosblade 是「危险的合法工具」—— 它真的会打满 CPU/杀进程，演练只在灰度/准生产做，且有明确时间窗和回退
4. 压测/演练要留痕 —— 记录注入的 UID、时间、观察结果，出问题能快速 blade destroy 撤销
```

```shell
# 查看 perf_event_paranoid 当前级别（3 最严，非 root 基本禁采样）
cat /proc/sys/kernel/perf_event_paranoid
# 演练前确认能快速撤销（列出所有注入）
./blade status --type create
```

## 故障排查

### load 很高但 CPU 使用率低

```shell
# 症状：load average 5+，但 top 看 CPU us+sy 很低
# 1. 看是不是 IO 等待（wa 高）
vmstat 1 5
# 2. 看是不是 D 状态进程（不可中断睡眠，通常是等 IO）
ps -eo stat,pid,comm | grep '^D'
# 3. 看是不是僵尸进程堆积
ps -eo stat,pid,comm | grep '^Z'
# 定位：wa 高 → 磁盘 IO 瓶颈（回到步骤七）；D 进程 → 卡在 IO/网络；Z 进程 → 父进程没回收
```

### 内存充足却 OOM / 服务被杀

```shell
# 症状：dmesg 里出现 Out of memory: Killed process
# 1. 看 OOM 记录，确认被杀的是谁、当时什么状态
dmesg -T | grep -i -E 'oom|killed'
# 2. 看是不是 cgroup 限制而非物理内存不足
cat /sys/fs/cgroup/memory/memory.limit_in_bytes 2>/dev/null
# 3. 看是不是 overcommit 策略太激进
sysctl vm.overcommit_memory
```

### 磁盘 IO 满，await 飙升

```shell
# 症状：iostat await 几十 ms、%util 100%
# 1. 找是谁在疯狂读写
pidstat -d 1
# 2. 看是不是日志刷盘/备份/数据库在跑
iotop -o
# 3. 临时缓解 + 根治
# 缓解：调 dirty 参数让写更平滑；根治：换 SSD、加 noatime、拆分日志盘
```

### 网络重传高、连接建立慢

```shell
# 症状：netstat -s 里 retransmit 高，用户反映「连接慢」
# 1. 看重传和队列溢出计数
netstat -s | grep -E 'retransmit|overflow|dropped'
ss -s
# 2. 看 listen 队列是否溢出（SYN 被丢弃）
ss -lnt | grep <port>
# 3. 对症：somaxconn 调大、tcp_max_syn_backlog 调大、检查网卡丢包（ethtool -S）
```

## 常见问题

```text
Q1: 压测结果里 QPS 很高，但用户还是说慢，为什么？
A: 压测通常打的是静态页/理想路径，生产有动态逻辑、数据库、网络链路。要看 P99/P99.9 延迟而非平均值，且压测要贴近真实流量（读多写少、长尾请求、慢 SQL），否则测出来的「高 QPS」不反映真实体验。

Q2: ab 和 wrk 测同一服务结果差很多，信哪个？
A: 都信，但要看条件。ab 默认短连接（除非 -k），wrk 长连接复用 + 事件驱动，wrk 结果通常更高。真实场景介于两者之间——浏览器是长连接、但会有新连接。报告里写清楚「什么工具、什么连接模式、什么并发」，别只报一个裸数字。

Q3: 火焰图上函数很宽，是不是就是性能瓶颈？
A: 大概率是，但要看宽度是不是「自身消耗」（--no-children 视角）。一个函数宽可能只是「被频繁调用」（它是别人的热点），也可能是「自己烧 CPU」。结合 perf report 的 self 占比判断，宽且自身占比高的才是真热点。

Q4: 调优到底调什么，有没有万能参数？
A: 没有。CPU 瓶颈优化代码/加核、内存瓶颈降 swap/查泄漏、IO 瓶颈换盘/调调度器、网络瓶颈调缓冲区/多队列。先定位是哪类资源饱和（USE 方法），再动对应参数，别上来就 sysctl 乱调。

Q5: 混沌演练会不会把生产搞挂？
A: 会的，所以不在生产做。先在准生产/灰度环境演练，注入强度从小到大，设好时间窗和快速回退（blade destroy）。混沌工程的价值恰恰是「在可控环境里发现假设错误」，而不是赌生产没事。
```

## 面试题

```text
1. 如何定位一个 CPU 密集型的性能瓶颈？
   答：先用 top/pidstat 定位热点进程，再 perf record -F 99 -g 采样调用栈，perf report/火焰图找热点函数；用 perf stat 看 cycles/cache-miss 判断是算力不足还是缓存失效。定位后针对性优化代码或加核。

2. 火焰图的 x 轴、y 轴分别代表什么？怎么读？
   答：x 轴是采样占比（函数出现在采样栈里的比例，越宽越热），y 轴是调用栈深度（底部入口、顶部叶子）。读法：找又宽又平的「平顶」，那就是直接烧 CPU 的函数；自顶向下是调用链，宽度收窄说明调用在分叉。

3. load average 和 CPU 使用率有什么区别？
   答：load average 是「可运行 + 不可中断睡眠（D 状态）的任务数」的平均值，反映的是系统整体的忙碌/排队程度；CPU 使用率只是 CPU 忙不忙。load 高但 CPU 低通常是 IO 等待（D 进程）或僵尸进程，不是算力问题。

4. 系统内存充足但频繁 swap，怎么排查和调优？
   答：查 vm.swappiness（默认 60 太激进，调低到 10）、查是不是有进程泄漏内存导致真实可用内存不足（pidstat -r 看增长）、查 cgroup 内存限制。确认后调 swappiness 或扩内存。

5. 什么是混沌工程？它和「故障演练」是一回事吗？
   答：混沌工程是通过主动注入故障（CPU/内存/网络/进程）来验证系统稳定性假设的实践，是系统化的故障演练。传统故障演练多为人工、低频、预设剧本；混沌工程强调「定义稳态 → 注入 → 观测 → 自动化/常态化」。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 调优前先建基线，调完同条件再压测对比，用数据说话
2. 压测机与被测服务分机部署，否则压测进程自己抢资源干扰结果
3. 看延迟分布用 P95/P99，别只看平均值（平均值掩盖长尾）
4. 火焰图 + perf report 结合看，on-CPU 用 perf record，IO/锁等待用 off-CPU（perf sched record）
5. 一次只改一个参数，改完验证再改下一个
6. 混沌演练只在准生产/灰度做，设时间窗、留 blade destroy 快速回退
7. 演练记录「稳态假设 → 观察结果 → 加固项」，让每次演练都有产出

### 踩坑记录

```text
坑 1：压测机和被测服务同机，结果失真
结论：压测结果忽高忽低、复现不了，调优无从下手。
原因：压测进程自己占 CPU/内存/网络，和被压服务抢资源，测的不是服务真实能力。
解法：压测机单独部署，压测时在压测机上观察资源、确保压测工具本身不是瓶颈。

坑 2：只看平均延迟，忽略长尾
结论：平均值看着很好，上线后部分用户抱怨卡。
原因：平均值被大量快请求拉低，掩盖了 P99/P99.9 的长尾延迟。
解法：wrk 加 --latency 看 P50/P90/P99 分布，重点盯 P99。

坑 3：同时改多个 sysctl 参数，性能变化不知道谁的功劳
结论：调完性能提升了，但说不清哪个参数起作用，回退时无从下手。
原因：一次改一堆参数，没有控制变量。
解法：一次只改一个，改完同条件压测验证，记录每次的收益。

坑 4：TIME_WAIT 堆积导致端口耗尽
结论：压测机/代理报 Cannot assign requested address，连接建立失败。
原因：短连接高并发下大量 TIME_WAIT，本地端口用完（默认 ip_local_port_range 太小）。
解法：调大 ip_local_port_range、开 tcp_tw_reuse（客户端场景），服务端则从连接复用/长连接下手。

坑 5：chaosblade 注入后忘了撤销，留着故障过夜
结论：演练结束后 CPU 还被打满、网络还有延迟，影响后续任务甚至生产。
原因：只注入没记录 UID、没及时 blade destroy。
解法：每次注入记 UID，演练结束立即 blade destroy，用 blade status 确认已清空。

坑 6：直接在生产上开 perf record 长时间采样，拖慢业务
结论：生产服务延迟上升，用户投诉。
原因：虽然采样开销通常 <5%，但长时间 + 高频（-F 999）会放大开销，尤其热点进程。
解法：采样频率用 99Hz、时长控制在 30 秒内，尽量在准生产复现，生产只做短采样。
```
