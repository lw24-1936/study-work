## 概述

本项目目标：把一个简单的 Web 应用从「裸代码」一路推到「Kubernetes 集群可滚动更新部署」，完整走完容器化全链路。覆盖四个环节：写 Dockerfile 构建镜像 → 用 Docker Compose 本地编排多容器 → 推到镜像仓库并部署到 K8s（Deployment + Service）→ 滚动更新与回滚。

技术栈：Docker（镜像构建与运行）、Docker Compose（本地多容器编排）、Kubernetes（Deployment/Service/探针/滚动更新）、kubectl（集群操作）、Python Flask（示例应用）。

前置条件：一台 Linux 主机已装 Docker（`docker --version` 可用）、Docker Compose 插件；一个可用的 K8s 集群（minikube / kubeadm / 云托管均可）和已配置好的 `kubectl` 上下文。

```text
交付物：一个应用从源码 → Dockerfile → 镜像 → Compose 本地跑 → K8s 集群部署 → 滚动更新 v1→v2 → 回滚，每一步都有可运行命令和验证
```

## 核心概念

本项目涉及的技术点：

1. **Dockerfile**：描述镜像构建步骤的文本文件，每条指令生成一层镜像。核心指令 `FROM`（基础镜像）、`COPY`（拷贝文件）、`RUN`（构建时执行命令）、`CMD`（容器启动命令）、`ENV`（环境变量）、`EXPOSE`（声明端口）。
2. **镜像与容器**：镜像是只读的、分层存储的模板；容器是镜像的运行实例，加了一层可写层。同一镜像可跑无数个容器。
3. **Docker Compose**：用 YAML 声明多容器应用的编排文件（`docker-compose.yml`），一条命令拉起整个应用栈（应用 + 依赖服务），本地开发/测试常用。
4. **Kubernetes（K8s）**：容器编排平台，管理容器的调度、扩缩容、滚动更新、自愈。核心对象：Pod（最小调度单元）、Deployment（管理 Pod 副本和滚动更新）、Service（稳定的访问入口）、Namespace（逻辑隔离）。
5. **Deployment**：声明「期望副本数」和 Pod 模板，控制器持续把实际状态调成期望状态；滚动更新靠它实现。
6. **Service**：给一组 Pod 提供稳定的虚拟 IP 和 DNS 名，Pod 重建后 IP 会变，但 Service 不变，客户端始终访问 Service。
7. **滚动更新（Rolling Update）**：逐个替换旧版本 Pod，全程保持服务可用；配合就绪探针（readinessProbe）做到「新 Pod 就绪才接入流量、旧 Pod 排空后才下线」。
8. **探针**：livenessProbe（存活探针，失败重启容器）、readinessProbe（就绪探针，失败摘除流量）、startupProbe（启动探针，慢启动应用用）。

```text
核心概念：
Dockerfile（构建镜像）→ Compose（本地编排）→ K8s（集群编排）
K8s 四件套：Pod（跑容器）+ Deployment（副本与滚动更新）+ Service（稳定入口）+ 探针（健康自愈）
```

## 工作原理

容器化到 K8s 部署的完整链路，每一层都在解决「怎么把代码稳定地跑起来并持续迭代」：

1. **镜像构建**：`docker build` 逐条执行 Dockerfile 指令，每条生成一个只读层；构建时会把构建上下文（代码目录）发给 Docker daemon，`COPY` 从中拷贝文件。分层的好处是：只改代码层时，依赖层复用缓存，构建飞快。
2. **容器运行**：`docker run` 基于镜像加一层可写层创建容器，通过 Linux 命名空间（隔离进程/网络/挂载）和 cgroup（限制 CPU/内存）实现轻量隔离，共享宿主机内核。
3. **Compose 编排**：`docker compose up` 解析 YAML，按依赖顺序创建网络、卷和容器；`depends_on` 声明启动顺序，`restart: unless-stopped` 声明崩溃自动拉起。
4. **K8s 调度**：`kubectl apply` 把 Deployment 提交给 API Server → 控制器创建 ReplicaSet → Scheduler 给 Pod 挑节点 → kubelet 在节点上拉镜像起容器。
5. **滚动更新**：更新 Deployment 镜像后，控制器按 `rollingUpdate` 策略（`maxSurge` 最多多出几个新 Pod、`maxUnavailable` 最多几个不可用）逐个替换：先起新版本 Pod → 就绪探针通过后接入 Service → 再删一个旧版本 Pod → 循环直到全部换新。任一环节失败可 `kubectl rollout undo` 回滚。

```text
链路：
源码 → docker build（Dockerfile 分层构建）→ 镜像 → docker push（仓库）→ kubectl apply（Deployment）→ Scheduler 调度 → kubelet 拉镜像跑 Pod → Service 暴露 → 滚动更新迭代
```

## 常用命令与配置

```shell
# 镜像
docker build -t myapp:v1 .                    # 按 Dockerfile 构建镜像
docker images                                  # 列出本地镜像
docker rmi myapp:v1                            # 删除镜像
docker tag myapp:v1 registry.example.com/myapp:v1   # 打仓库标签
docker push registry.example.com/myapp:v1      # 推到仓库

# 容器
docker run -d -p 8080:8080 --name myapp myapp:v1   # 后台跑容器并映射端口
docker ps -a                                    # 看所有容器
docker logs -f myapp                            # 看容器日志
docker exec -it myapp bash                      # 进容器
docker rm -f myapp                              # 强删容器

# Compose
docker compose up -d --build                    # 构建并后台起整个栈
docker compose ps                               # 看编排容器状态
docker compose logs -f app                      # 看某服务日志
docker compose down                             # 停止并删除整个栈

# Kubernetes
kubectl get pods -o wide                        # 看 Pod 及所在节点
kubectl get deployments                         # 看 Deployment
kubectl get svc                                 # 看 Service
kubectl describe pod <pod名>                    # 看 Pod 详情（排障关键）
kubectl logs -f <pod名>                         # 看 Pod 日志
kubectl apply -f deployment.yaml                # 声明式部署
kubectl rollout status deployment/myapp         # 看滚动更新进度
kubectl rollout undo deployment/myapp           # 回滚
kubectl scale deployment/myapp --replicas=5     # 扩缩容
```

```text
配置要点：
1. 镜像 tag 用语义化版本（v1/v2），别用 latest（无法定位、回滚困难）
2. kubectl apply 是声明式，重复执行幂等，改 YAML 再 apply 即可
3. 排障先 kubectl describe（事件）+ kubectl logs（日志），别急着删 Pod
```

## 配置文件解析

### Dockerfile

```dockerfile
FROM python:3.12-slim                    # 基础镜像，slim 体积小
WORKDIR /app                             # 工作目录，后续指令相对它
COPY requirements.txt .                  # 先拷依赖清单（独立层，缓存友好）
RUN pip install --no-cache-dir -r requirements.txt   # 装依赖
COPY app.py .                            # 再拷代码（改动频繁的放后面）
ENV APP_VERSION=v1                       # 环境变量
EXPOSE 8080                              # 声明端口（仅文档作用，真正映射靠 -p）
HEALTHCHECK --interval=5s --timeout=3s \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8080/health')" || exit 1
CMD ["python", "app.py"]                 # 启动命令（exec 形式，能收到信号）
```

```text
分层与缓存：COPY/RUN 各生成一层，依赖在代码前拷，改代码时依赖层命中缓存，构建快
CMD exec 形式（["python","app.py"]）让 PID 1 是 python，能正确收到 SIGTERM 优雅退出
```

### docker-compose.yml

```yaml
services:
  app:
    build: .                              # 用当前目录 Dockerfile 构建
    image: myapp:${APP_VERSION:-v1}        # 镜像 tag 从环境变量读，默认 v1
    ports:
      - "8080:8080"                        # 宿主机:容器端口映射
    environment:
      - APP_VERSION=${APP_VERSION:-v1}
    restart: unless-stopped                # 崩溃/重启自动拉起
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8080/health')"]
      interval: 5s
      timeout: 3s
      retries: 3
```

```text
${APP_VERSION:-v1}  从环境变量或 .env 文件读版本，缺省 v1，实现「一套 YAML 多版本」
restart: unless-stopped  进程崩溃自动重启，手动 stop 不重启
```

### deployment.yaml（K8s）

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  labels:
    app: myapp
spec:
  replicas: 3                             # 期望副本数
  selector:
    matchLabels:
      app: myapp                          # 必须匹配模板 labels
  strategy:
    type: RollingUpdate                   # 滚动更新策略
    rollingUpdate:
      maxSurge: 1                         # 更新期间最多多出 1 个新 Pod
      maxUnavailable: 0                   # 更新期间 0 个不可用（保证服务不中断）
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: myapp
        image: registry.example.com/myapp:v1
        imagePullPolicy: IfNotPresent
        ports:
        - containerPort: 8080
        env:
        - name: APP_VERSION
          value: "v1"
        readinessProbe:                   # 就绪探针：通过才接入流量
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5
        livenessProbe:                    # 存活探针：失败重启容器
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 10
        resources:                        # 资源请求和上限
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 256Mi
```

### service.yaml（K8s）

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  type: ClusterIP                         # 集群内部访问；对外可用 NodePort/LoadBalancer
  selector:
    app: myapp                            # 通过标签选中 Pod
  ports:
  - port: 80                              # Service 端口
    targetPort: 8080                      # 转发到 Pod 的端口
    protocol: TCP
```

```text
滚动更新关键参数：
maxSurge=1 / maxUnavailable=0  更新时最多多 1 个新 Pod、保持 0 个不可用，服务全程在线
readinessProbe  新 Pod 就绪才进 Service 后端，没就绪的 Pod 不会接流量
Service selector 靠标签关联 Pod，Pod 重建后 IP 变了也自动纳入
```

## 应用场景实战

目标：Flask 应用从源码推到 K8s，完成 v1 → v2 滚动更新和回滚。共 8 步。示例应用返回版本号和主机名，便于观察滚动更新的「新旧 Pod 交替」。

### 步骤一：准备应用源码

创建项目目录和 3 个文件：`app.py`（应用）、`requirements.txt`（依赖）。

```shell
mkdir -p ~/myapp && cd ~/myapp
```

```python
# app.py：返回版本号和主机名，滚动更新时靠版本号区分新旧
import os
from flask import Flask, jsonify

app = Flask(__name__)
VERSION = os.environ.get("APP_VERSION", "v1")

@app.route("/")
def index():
    return jsonify({
        "version": VERSION,
        "hostname": os.uname().nodename,
        "status": "ok",
    })

@app.route("/health")
def health():
    return "ok", 200

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8080)
```

```text
# requirements.txt
flask==3.0.3
```

解释：应用监听 `0.0.0.0:8080`（容器内必须绑 0.0.0.0，绑 127.0.0.1 外部访问不到）；`/health` 返回 200 给探针用；`/` 返回 `version` 和 `hostname`，滚动更新时能看到返回的 version 从 v1 变成 v2。

验证（本地先跑通再容器化）：

```shell
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
python app.py &
sleep 2
curl -s http://127.0.0.1:8080/
```

示例输出：

```text
{"hostname":"localhost.localdomain","status":"ok","version":"v1"}
```

### 步骤二：编写 Dockerfile 并构建镜像

把上面「配置文件解析」里的 Dockerfile 写入项目目录。

```shell
cd ~/myapp
# 写好 Dockerfile 后构建，-t 指定镜像名和 tag
docker build -t myapp:v1 .
```

解释：`docker build` 把当前目录作为构建上下文发给 daemon，逐层执行 Dockerfile。`.dockerignore` 建议排除 `venv/`、`__pycache__/` 等，否则这些大目录会进上下文拖慢构建。

验证：

```shell
docker images | grep myapp
```

示例输出：

```text
myapp       v1        3f2a1c9b8d7e   10 seconds ago   130MB
```

### 步骤三：本地运行容器验证

```shell
# -d 后台跑，-p 宿主机:容器端口映射，--name 命名容器
docker run -d -p 8080:8080 --name myapp-v1 -e APP_VERSION=v1 myapp:v1

# 验证健康检查路径和接口
curl -s http://127.0.0.1:8080/health
curl -s http://127.0.0.1:8080/
docker ps --filter name=myapp-v1
```

示例输出：

```text
ok
{"hostname":"a1b2c3d4e5f6","status":"ok","version":"v1"}
```

解释：`hostname` 变成容器 ID 前缀，说明请求确实打到容器里了。`-e APP_VERSION=v1` 覆盖镜像里的默认环境变量，接口返回对应版本。

```shell
# 用完清理
docker rm -f myapp-v1
```

### 步骤四：编写 docker-compose.yml 本地编排

把上面「配置文件解析」里的 docker-compose.yml 写入项目目录，实现「一条命令起整个栈」。

```shell
cd ~/myapp
docker compose up -d --build
docker compose ps
```

解释：`--build` 强制重新构建镜像再启动；`${APP_VERSION:-v1}` 从环境变量读版本，切版本只需 `APP_VERSION=v2 docker compose up -d --build`，不用改 YAML。

验证：

```shell
docker compose logs -f app      # 看应用日志
curl -s http://127.0.0.1:8080/
docker compose down             # 验证完停止并清理
```

示例输出：

```text
{"hostname":"a1b2c3d4e5f6","status":"ok","version":"v1"}
```

### 步骤五：推送镜像到仓库

K8s 集群各节点要从仓库拉镜像，需先把镜像推到可访问的仓库（示例用自建 registry，实际可用 Docker Hub / 云厂商镜像仓库）。

```shell
# 打仓库标签并推送
docker tag myapp:v1 registry.example.com/myapp:v1
docker push registry.example.com/myapp:v1

# 若用本地私有 registry，先起一个
docker run -d -p 5000:5000 --name registry registry:2
docker tag myapp:v1 localhost:5000/myapp:v1
docker push localhost:5000/myapp:v1
```

解释：K8s 默认从镜像名里的仓库地址拉取，所以镜像必须带完整仓库前缀。私有仓库要在 K8s 节点配置认证（`imagePullSecrets`）或仓库地址可达，否则 `kubectl apply` 后 Pod 会 `ImagePullBackOff`。

验证：

```shell
docker images | grep myapp
```

### 步骤六：编写 K8s YAML 并部署

把上面「配置文件解析」里的 deployment.yaml 和 service.yaml 写入项目目录，部署到集群。

```shell
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml

# 看滚动部署进度（3 个副本逐个就绪）
kubectl rollout status deployment/myapp
kubectl get pods -o wide
kubectl get svc myapp
```

示例输出：

```text
deployment "myapp" successfully rolled out
NAME                     READY   STATUS    RESTARTS   AGE   IP           NODE
myapp-7d9c8b6f5-abcde    1/1     Running   0          30s   10.244.1.5   node1
myapp-7d9c8b6f5-fghij    1/1     Running   0          30s   10.244.1.6   node1
myapp-7d9c8b6f5-klmno    1/1     Running   0          30s   10.244.2.3   node2
```

解释：Deployment 控制器创建 ReplicaSet 并拉起 3 个 Pod，Scheduler 把它们分散到不同节点。Service 通过 `selector: app: myapp` 把 3 个 Pod 纳入后端。

验证（集群内访问 Service）：

```shell
# 用临时 Pod 在集群内访问 Service 的 80 端口
kubectl run curlpod --rm -i --tty --image=curlimages/curl -- sh -c 'curl -s http://myapp/'
```

示例输出：

```text
{"hostname":"myapp-7d9c8b6f5-abcde","status":"ok","version":"v1"}
```

### 步骤七：滚动更新 v1 → v2 与回滚

改代码版本并重新构建、推送，再更新 Deployment 镜像，观察新旧 Pod 交替。

```shell
# 1. 改代码版本并重新构建（假设把 app.py 里 VERSION 默认值或镜像 ENV 改成 v2）
docker build -t myapp:v2 .
docker push registry.example.com/myapp:v2

# 2. 更新 Deployment 镜像（或改 deployment.yaml 的 image 再 apply）
kubectl set image deployment/myapp myapp=registry.example.com/myapp:v2

# 3. 实时看滚动更新：新旧 Pod 交替，全程服务在线
kubectl rollout status deployment/myapp
kubectl get pods -w
```

解释：`kubectl set image` 改镜像触发滚动更新。`maxSurge=1`、`maxUnavailable=0` 保证任意时刻至少 3 个可用 Pod——先起 1 个新 Pod，就绪后接入流量，再删 1 个旧 Pod，循环到全部换新。`-w` 持续监听能看到新旧 Pod 交替变化。

验证（连续请求，观察 version 从 v1 变 v2）：

```shell
kubectl run curlpod --rm -i --tty --image=curlimages/curl -- sh -c 'for i in 1 2 3 4 5; do curl -s http://myapp/; echo; done'
```

示例输出：

```text
{"hostname":"myapp-7d9c8b6f5-fghij","status":"ok","version":"v1"}
{"hostname":"myapp-6c5d8e9f2-pqrst","status":"ok","version":"v2"}
{"hostname":"myapp-6c5d8e9f2-pqrst","status":"ok","version":"v2"}
{"hostname":"myapp-6c5d8e9f2-uvwxy","status":"ok","version":"v2"}
{"hostname":"myapp-6c5d8e9f2-uvwxy","status":"ok","version":"v2"}
```

回滚（发现 v2 有问题，退回 v1）：

```shell
# 回滚到上一个版本
kubectl rollout undo deployment/myapp
kubectl rollout status deployment/myapp
# 看历史版本，可指定回滚到某次 revision
kubectl rollout history deployment/myapp
```

解释：`rollout undo` 回滚到上一个 revision，Deployment 记录每次更新的 revision，`rollout history` 列出可回滚的版本。回滚同样是滚动进行的，不停服。

### 步骤八：扩缩容与完整交付验证

```shell
# 扩到 5 副本，秒级生效
kubectl scale deployment/myapp --replicas=5
kubectl get pods -o wide

# 完整交付验证清单
kubectl get deployment myapp          # 期望/可用副本数一致
kubectl get svc myapp                 # Service 就绪
kubectl get pods -o wide              # 全部 Running 且 READY 1/1
kubectl top pods                      # 资源占用（需 metrics-server）
```

解释：`kubectl scale` 改副本数，Deployment 控制器自动补齐或缩掉 Pod，这就是声明式——你只声明「要 5 个」，K8s 负责达到目标状态。交付前跑一遍验证清单，确认副本数、Service、Pod 状态、资源占用都正常。

示例输出：

```text
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
myapp   5/5     5            5           10m
```

## 性能与调优

```text
1. 镜像体积 —— 用 slim/alpine 基础镜像、多阶段构建（build 阶段装依赖，runtime 阶段只拷产物），镜像小拉取快、启动快
2. 分层缓存 —— Dockerfile 里「依赖在前、代码在后」，只改代码时依赖层命中缓存，构建从分钟级降到秒级
3. 资源请求与上限 —— requests 保证调度不超卖，limits 防止单容器吃满节点；requests 设太小会被 OOM 杀，limits 设太大浪费
4. 探针间隔 —— readinessProbe 太频繁增加开销，太慢拖慢滚动更新；生产常见 periodSeconds 5~10s
5. 滚动更新速度 —— maxSurge 调大（如 2）更新更快但瞬间资源占用高；maxUnavailable 调大更快但可能短暂降容量
6. 副本数与 HPA —— 固定 replicas 应对不了流量波动，配 HorizontalPodAutoscaler 按 CPU/内存自动伸缩
```

```shell
# 多阶段构建示例（Go 应用）：build 阶段编译，runtime 阶段只放二进制
# FROM golang:1.22 AS build
# WORKDIR /src
# COPY . .
# RUN go build -o /app/server .
# FROM alpine:3.19
# COPY --from=build /app/server /usr/local/bin/server
# CMD ["server"]
```

## 安全与权限

```text
1. 容器内别用 root —— Dockerfile 里 USER 指定非 root 用户，K8s 加 securityContext（runAsNonRoot: true）强制
2. 镜像来源可信 —— 只从官方镜像/自建仓库拉，别跑来路不明的镜像（可能带后门）
3. 私有仓库认证 —— 用 imagePullSecrets 存凭据，别把密码写进 YAML 明文
4. 最小权限 —— 容器只挂必要卷、只开必要端口；K8s 用 RBAC 限制 ServiceAccount 权限，别给 Pod 集群管理员权限
5. 敏感信息走 Secret —— 数据库密码等用 K8s Secret 或外部密钥管理，不写进环境变量明文/镜像
6. 镜像扫描 —— 上线前用扫描工具（trivy 等）查镜像漏洞，及时更新基础镜像
```

```yaml
# Pod 安全上下文示例（非 root + 只读根文件系统）
# securityContext:
#   runAsNonRoot: true
#   runAsUser: 1000
#   readOnlyRootFilesystem: true
```

## 故障排查

### Pod 一直 ImagePullBackOff

```shell
# 拉镜像失败，看具体原因
kubectl describe pod <pod名> | grep -A10 Events

# 常见原因：镜像 tag 不存在 / 仓库地址不通 / 私有仓库没认证
kubectl get events --sort-by=.lastTimestamp | tail -n 10
```

### Pod CrashLoopBackOff（反复重启）

```shell
# 容器起来就崩，看日志找原因
kubectl logs <pod名> --previous     # 看上一次崩溃的日志
kubectl describe pod <pod名>        # 看退出码、探针失败记录

# 常见原因：命令/入口错误、依赖缺失、livenessProbe 探针失败、内存超限被 OOM 杀
```

### 滚动更新卡住不前进

```shell
kubectl rollout status deployment/myapp
kubectl get pods -o wide             # 看是不是新 Pod 一直没就绪
kubectl describe pod <新pod名>       # 看 readinessProbe 是否一直失败

# 常见原因：新镜像有问题（就绪探针不过）、资源不够调度不上、镜像拉不下来
# 处理：kubectl rollout undo deployment/myapp 先回滚止血
```

### Service 访问不到 Pod

```shell
# 排查 selector 是否匹配 Pod 标签
kubectl get pods --show-labels
kubectl describe svc myapp           # 看 Endpoints 是否为空
kubectl get endpoints myapp

# Endpoints 为空 = selector 没匹配到任何 Pod（标签写错/端口写错）
```

### 本机 docker 端口被占用

```shell
# 端口映射冲突
docker ps                            # 看已有容器占用了哪些端口
ss -tlnp | grep 8080                 # 看宿主机谁占着 8080
# 处理：换映射端口 -p 8081:8080，或停掉占用的容器/进程
```

## 常见问题

```text
Q1: Dockerfile 里 CMD 用 exec 形式和 shell 形式有什么区别？
A: exec 形式（["python","app.py"]）直接 exec 进程，PID 1 是应用本身，能收到 SIGTERM 优雅退出；shell 形式（python app.py）会包一层 /bin/sh，PID 1 是 sh，信号传不到应用，容器停止要等超时强杀。

Q2: EXPOSE 和 -p 端口映射什么关系？
A: EXPOSE 只是声明「这个容器监听哪些端口」，是文档性质的，不实际映射；真正对外暴露靠 -p（或 compose 的 ports）。EXPOSE 写对能帮后来者读懂容器用哪些端口。

Q3: Deployment 和 Pod 什么关系？为什么不能直接建 Pod？
A: Pod 是最小调度单元但「一次性」——挂了就没了、IP 会变。Deployment 是更高级的控制器，声明期望副本数并持续保证，Pod 挂了自动重建、支持滚动更新和回滚。生产永远用 Deployment 管 Pod，不直接建裸 Pod。

Q4: 就绪探针和存活探针有什么区别？
A: readinessProbe 失败 = Pod 不健康，从 Service 后端摘除（不接流量）但不重启；livenessProbe 失败 = 容器死循环/僵死，直接重启容器。就绪探针管「能不能接流量」，存活探针管「进程还活不活」。

Q5: 滚动更新和重新创建（Recreate）更新有什么区别？
A: Recreate 先删光所有旧 Pod 再建新的，期间服务完全中断；RollingUpdate 逐个替换，全程保持可用。生产默认用 RollingUpdate，只有「新旧版本不能并存」（如数据库 schema 不兼容）才用 Recreate。
```

## 面试题

```text
1. 说说 Docker 镜像的分层机制，为什么这样设计？
   答：每条 Dockerfile 指令生成一个只读层，层之间用联合文件系统叠加，容器加一层可写层。好处是构建缓存——没变的层直接复用，只重建变化层；同一基础镜像的层在多个镜像间共享，节省磁盘和拉取带宽。

2. K8s 里 Deployment、ReplicaSet、Pod 的关系？
   答：Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod。Deployment 声明期望状态（副本数、镜像、更新策略），每次更新创建新 ReplicaSet 并滚动切换，旧 ReplicaSet 保留用于回滚；ReplicaSet 保证任意时刻有指定数量的 Pod 副本在运行。

3. Service 是怎么做到 Pod 重建后 IP 不变、访问不中断的？
   答：Service 通过 selector 标签动态关联 Pod，本身有稳定的虚拟 IP（ClusterIP）和 DNS 名。Pod 重建后 IP 变了，但标签没变，Service 的 Endpoints 自动更新指向新 Pod，客户端始终访问 Service 的稳定地址，不感知后端变化。

4. 滚动更新时如何做到零停机？
   答：rollingUpdate 策略控制 maxSurge（最多多出的新 Pod 数）和 maxUnavailable（最多不可用的 Pod 数）。设为 maxSurge=1、maxUnavailable=0 时，先起新 Pod，等就绪探针通过、接入 Service 后，再删旧 Pod，循环替换，任意时刻都有全部副本在服务，实现零停机。

5. 容器和虚拟机有什么区别？
   答：虚拟机是硬件级虚拟化，每个 VM 有独立 Guest OS，隔离强但开销大、启动慢；容器是 OS 级虚拟化，共享宿主机内核，用命名空间隔离进程、cgroup 限制资源，轻量、秒级启动、密度高，但隔离性弱于 VM。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 镜像 tag 用语义化版本（v1/v2）或 commit hash，禁止用 latest（无法定位、回滚困难）
2. Dockerfile 依赖在前、代码在后，充分利用分层缓存；写 .dockerignore 排除 venv/缓存
3. 容器内绑 0.0.0.0、用非 root 用户跑，配 HEALTHCHECK 和 K8s 就绪/存活探针
4. 滚动更新策略设 maxSurge=1、maxUnavailable=0，配合就绪探针实现零停机
5. Deployment 设 requests/limits，防止资源超卖和 OOM 杀
6. 敏感信息走 Secret，镜像推私有仓库用 imagePullSecrets，不写明文
7. 上线前镜像扫描漏洞，基础镜像及时更新

### 踩坑记录

```text
坑 1：镜像 tag 用 latest，回滚时不知道上一版是什么
结论：出问题想回滚，发现 latest 已被覆盖，找不到稳定旧版本。
原因：latest 是可变标签，每次 push 覆盖，无版本语义。
解法：用 v1/v2 或 commit hash 做 tag，每次发布打新标签，保留历史版本。

坑 2：容器里应用绑 127.0.0.1，宿主机和集群访问不到
结论：容器起来正常，但 curl 宿主机端口连不上。
原因：绑 127.0.0.1 只监听容器内回环，端口映射/Service 都转发不进去。
解法：应用监听 0.0.0.0（或直接不绑具体地址），容器网络才能接住外部流量。

坑 3：K8s Pod 一直 ImagePullBackOff
结论：Pod 起不来，describe 显示拉镜像失败。
原因：镜像 tag 不存在、仓库地址不可达，或私有仓库没配认证。
解法：确认镜像已 push、tag 正确，私有仓库配 imagePullSecrets，并核对集群节点能访问仓库。

坑 4：滚动更新卡死，新 Pod 一直没就绪
结论：rollout status 卡住，新版本始终上不了线。
原因：新镜像有 bug 导致就绪探针失败，或集群资源不够新 Pod 调度不上。
解法：先 kubectl rollout undo 回滚止血，再查新镜像就绪探针日志和资源配额，修好再更新。

坑 5：容器用 root 跑，被攻破后直接拿到宿主机权限
结论：容器被入侵后攻击者以 root 提权到宿主机。
原因：容器内默认 root，且没做安全上下文限制，容器逃逸后权限直接是宿主机 root。
解法：Dockerfile 里 USER 切非 root，K8s securityContext 加 runAsNonRoot、runAsUser。

坑 6：compose 里 depends_on 以为能等依赖就绪
结论：应用连不上数据库，因为数据库容器刚起还没 ready。
原因：depends_on 只保证启动顺序，不等待依赖服务真正就绪（健康检查通过）。
解法：应用侧加重试逻辑，或 compose 用 healthcheck + depends_on condition: service_healthy。

坑 7：改了 YAML 忘了 apply，或 apply 了没验证 rollout 结果
结论：以为更新了实际集群还是旧版本，出问题找不到原因。
原因：改 YAML 后没执行 kubectl apply，或 apply 后没看 rollout status。
解法：apply 后必跑 kubectl rollout status 确认滚动完成，再验证接口版本。
```
