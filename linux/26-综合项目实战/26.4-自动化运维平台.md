## 概述

本项目目标：把「手工 SSH 到每台机器敲命令」的重复劳动，替换成一套可复用、可排期的自动化运维平台。四个能力：Ansible 批量管理（一次操作多台机器）、巡检脚本（定期体检）、定时任务（cron/systemd timer 排期）、发布流水线（代码构建到上线自动化）。

技术栈：Ansible（无代理批量管理）、Shell 脚本（巡检）、cron + systemd timer（定时调度）、Git（版本管理与发布源）。

前置条件：完成 26.1 基础环境；一台控制节点（`ops`，IP `192.168.1.100`，装 Ansible）+ 2 台受管节点（`server01` `192.168.1.11`、`server02` `192.168.1.12`，Ubuntu/RHEL 均可）；控制节点已能用密钥登录所有受管节点。

```text
交付物：Ansible 一键批量管理 + 每日自动巡检 + 定时执行 + 发布流水线（构建→部署→健康检查）
```

## 核心概念

本项目涉及的技术点：

1. **Ansible 批量管理**：无代理（agentless）架构——控制节点通过 SSH 连接受管节点执行任务，不需要在受管节点装任何客户端，靠 inventory 清单 + playbook 描述「对哪些机器做什么」。
2. **inventory 清单**：受管节点的分组清单（如 webservers/dbservers），支持分组变量、连接参数（用户、私钥、端口）。
3. **playbook**：YAML 描述的任务剧本，由多个 play（针对某组主机）+ 多个 task（调用 module 执行）组成，声明式（描述期望状态，不是执行步骤）。
4. **巡检脚本**：Shell 脚本定期检查 CPU/内存/磁盘/服务/进程等健康指标，输出报告，异常告警。
5. **定时任务**：cron（传统，按分时日月周排期）与 systemd timer（新式，可持久化、支持随机延迟、日志进 journal）。
6. **发布流水线**：代码提交 → 构建产物 → 推送到受管节点 → 重启服务 → 健康检查，用 Ansible playbook 串起来，一条命令完成发布。

```text
核心概念：
Ansible 批量管理（inventory + playbook）→ 巡检脚本（Shell 体检）→ 定时任务（cron/systemd timer 排期）→ 发布流水线（构建→部署→验证）
```

## 工作原理

1. **Ansible 执行原理**：控制节点解析 inventory 和 playbook → 为每台受管节点建立 SSH 连接 → 把 task 对应的 module 代码和参数打包上传到受管节点临时目录 → 在受管节点本地执行 → 回收结果并删除临时文件。全程无持久化代理。
2. **幂等性**：module 设计为幂等——比如 `apt: state=present` 检查包已装就跳过，重复执行不产生副作用，这是「配置管理」和「一次性脚本」的本质区别。
3. **定时任务**：cron 由 cron 守护进程每分钟读一次 crontab，匹配当前时间就执行；systemd timer 由 systemd 调度，`OnCalendar` 定义触发时间，`Persistent=true` 补跑错过的任务，日志进 journald。
4. **发布流水线**：本地构建（或拉取产物）→ Ansible 把产物同步到受管节点（copy/synchronize）→ 更新配置/重启服务（service module）→ 健康检查（uri 探测）→ 失败回滚到上一版本。

```text
链路汇总：
Ansible：inventory + playbook → SSH 连接 → 上传 module → 受管节点执行 → 回收结果
定时：cron 每分钟匹配 / systemd timer 按 OnCalendar 触发
发布：构建 → 同步产物 → 重启服务 → 健康检查 → 失败回滚
```

## 常用命令与配置

```shell
# Ansible 常用命令
ansible --version                       # 版本与环境
ansible all -m ping                     # 连通性测试（受管节点装 python 才能过）
ansible all -m shell -a "uptime"        # 在所有节点执行 shell 命令（ad-hoc）
ansible webservers -m apt -a "name=nginx state=present" -b   # 单模块批量装软件（-b 提权）
ansible-playbook -i inventory.ini site.yml          # 执行 playbook
ansible-playbook --check site.yml                  # 演练模式（dry-run，不真正执行）
ansible-playbook --syntax-check site.yml           # 语法检查
ansible-inventory -i inventory.ini --list          # 查看解析后的清单
ansible-doc -l | grep -E 'apt|copy|service'        # 查 module 用法

# 定时任务
crontab -l                             # 查看当前用户 crontab
crontab -e                             # 编辑
systemctl list-timers                  # 查看所有 timer 和下次触发时间
systemctl status <name>.timer          # 看 timer 状态

# 发布流水线相关
git -C /opt/app pull                   # 拉取最新代码
curl -s -o /dev/null -w '%{http_code}\n' http://localhost/health   # 健康检查
```

```text
配置要点：
1. ad-hoc（ansible -m）用于一次性命令，重复任务写成 playbook 进版本库
2. 幂等性优先用专用 module（apt/yum/copy/service），少用 shell 裸命令
3. 定时任务重载后要验证（cron 看日志、timer 看 systemctl list-timers）
```

## 配置文件解析

### /etc/ansible/hosts 或自定义 inventory.ini（主机清单）

```ini
[webservers]
web01 ansible_host=192.168.1.11
web02 ansible_host=192.168.1.12

[dbservers]
db01 ansible_host=192.168.1.21

[all:vars]
ansible_user=admin
ansible_ssh_private_key_file=/home/admin/.ssh/id_ed25519
ansible_become=true
ansible_become_method=sudo
```

### site.yml（批量管理 playbook 骨架）

```yaml
---
- name: 批量安装基础软件
  hosts: all
  become: true
  vars:
    pkgs:
      - vim
      - curl
      - htop
  tasks:
    - name: 更新软件源缓存
      apt:
        update_cache: yes
        cache_valid_time: 3600
      when: ansible_os_family == "Debian"

    - name: 安装基础软件包
      package:
        name: "{{ pkgs }}"
        state: present
```

### 巡检脚本 /opt/scripts/check.sh（骨架）

```bash
#!/bin/bash
# 巡检脚本：CPU / 内存 / 磁盘 / 服务 / 进程
THRESHOLD_DISK=80
THRESHOLD_CPU=80

echo "===== $(date '+%F %T') 巡检报告 $(hostname) ====="
echo "[磁盘]"
df -h | awk -v t=$THRESHOLD_DISK 'NR>1 {use=$5; gsub(/%/,"",use); if (use>t) print "  [告警] "$6" 使用率 "$5}'
echo "[内存]"
free -h | awk 'NR==2 {print "  总 "$2" 已用 "$3" 可用 "$7}'
echo "[CPU 负载]"
uptime
echo "[关键服务]"
for s in ssh nginx; do
  systemctl is-active --quiet $s && echo "  $s 正常" || echo "  [告警] $s 未运行"
done
```

### /etc/cron.d/ops-inspection（cron 排期）

```text
# 每天凌晨 2 点巡检，结果追加到日志
0 2 * * * root /opt/scripts/check.sh >> /var/log/inspection.log 2>&1
```

### /etc/systemd/system/inspection.timer + inspection.service（systemd timer）

```ini
# inspection.timer
[Unit]
Description=Run inspection daily

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

```ini
# inspection.service
[Unit]
Description=Inspection script

[Service]
Type=oneshot
ExecStart=/opt/scripts/check.sh
```

```text
关键字段：
hosts                play 针对的主机组（all/组名/通配）
become               是否提权执行（对应 sudo）
package              跨发行版包管理 module（自动选 apt/dnf/yum）
when                 条件执行（按 os_family 区分 Debian/RedHat）
OnCalendar           systemd 日历事件语法，*-*-* 02:00:00 = 每天 2 点
Persistent=true      错过触发时间后补跑（如关机期间）
```

## 应用场景实战

目标：控制节点 `ops` 装 Ansible，批量管理 `server01`/`server02` 两台受管节点，配上每日巡检（cron + systemd timer 双方案）、发布流水线（构建→部署→健康检查→回滚）。共 8 步。

### 步骤一：环境准备与 SSH 免密

控制节点 `ops` 生成密钥并分发到受管节点：

```shell
# 控制节点生成 ed25519 密钥（若已有可跳过）
ssh-keygen -t ed25519 -C "ops@ops-node"
# 分发公钥到两台受管节点
ssh-copy-id -i ~/.ssh/id_ed25519.pub admin@192.168.1.11
ssh-copy-id -i ~/.ssh/id_ed25519.pub admin@192.168.1.12
# 验证免密登录
ssh admin@192.168.1.11 'hostname'
```

示例输出：

```text
server01
```

解释：Ansible 走 SSH 连接，必须先配好免密（或用 `ansible_ssh_password`，但密钥更安全）。受管节点需有 Python（Ubuntu 22.04/RHEL 9 默认带 python3），Ansible 靠它在远端执行 module。

### 步骤二：安装 Ansible 并配置 inventory

```shell
# Debian/Ubuntu 控制节点
sudo apt update && sudo apt install -y ansible
# RHEL 系：sudo dnf install -y epel-release && sudo dnf install -y ansible

ansible --version | head -n 1
```

写 inventory 文件 `~/ansible/inventory.ini`：

```ini
[webservers]
web01 ansible_host=192.168.1.11
web02 ansible_host=192.168.1.12

[all:vars]
ansible_user=admin
ansible_ssh_private_key_file=/home/admin/.ssh/id_ed25519
ansible_become=true
ansible_become_method=sudo
```

```shell
# 连通性测试（ping module 走 python，非 ICMP）
ansible -i ~/ansible/inventory.ini all -m ping
```

示例输出：

```text
web01 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}
web02 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}
```

解释：inventory 用 `[webservers]` 分组，`[all:vars]` 定义全部节点通用变量（登录用户、私钥、提权方式）；`ansible all -m ping` 是标准连通性测试，返回 `pong` 即 SSH + Python 链路通了。

### 步骤三：编写批量管理 playbook（site.yml）

写 `~/ansible/site.yml`，做三件事：装基础软件、创建统一运维账户、配置 nginx 开机自启：

```yaml
---
- name: 批量基础配置
  hosts: all
  become: true
  vars:
    pkgs:
      - vim
      - curl
      - htop
      - ntp
  tasks:
    - name: 更新软件源缓存（Debian 系）
      apt:
        update_cache: yes
        cache_valid_time: 3600
      when: ansible_os_family == "Debian"

    - name: 安装基础软件包
      package:
        name: "{{ pkgs }}"
        state: present

    - name: 创建统一运维账户 ops
      user:
        name: ops
        groups: sudo
        shell: /bin/bash
        append: yes

    - name: 确保 nginx 安装并开机自启
      package:
        name: nginx
        state: present
      notify: restart nginx

  handlers:
    - name: restart nginx
      service:
        name: nginx
        state: restarted
        enabled: yes
```

```shell
ansible-playbook -i ~/ansible/inventory.ini --syntax-check ~/ansible/site.yml
ansible-playbook -i ~/ansible/inventory.ini --check ~/ansible/site.yml   # 演练
ansible-playbook -i ~/ansible/inventory.ini ~/ansible/site.yml          # 真执行
```

示例输出：

```text
PLAY RECAP *********************************************************************
web01 : ok=5    changed=3    unreachable=0    failed=0    skipped=1    rescued=0
web02 : ok=5    changed=3    unreachable=0    failed=0    skipped=1    rescued=0
```

解释：`package` module 跨发行版自动选 apt/dnf/yum，`when: ansible_os_family == "Debian"` 让 apt 更新只跑在 Debian 系；`notify` + `handlers` 实现「只有 nginx 装了/变了才重启」；`--check` 演练不真正改系统，先看会改哪些，再真执行。PLAY RECAP 汇总每台结果，`changed=3` 表示真改了 3 项。

### 步骤四：编写巡检脚本

写 `/opt/scripts/check.sh`，检查磁盘、内存、CPU 负载、关键服务、僵尸进程：

```bash
#!/bin/bash
# 巡检脚本：磁盘 / 内存 / 负载 / 服务 / 僵尸进程
THRESHOLD_DISK=80
THRESHOLD_LOAD=4

echo "===== $(date '+%F %T') 巡检报告 $(hostname) ====="

echo "[磁盘使用率 > ${THRESHOLD_DISK}%]"
df -hP | awk -v t=$THRESHOLD_DISK 'NR>1 {use=$5; gsub(/%/,"",use); if (use>t) print "  [告警] 分区 "$6" 使用率 "$5}'

echo "[内存]"
free -h | awk 'NR==2 {print "  总 "$2" / 已用 "$3" / 可用 "$7}'

echo "[CPU 负载（1/5/15 分钟）]"
uptime | awk -F'load average:' '{print "  "$2}'

echo "[关键服务状态]"
for s in ssh nginx; do
  systemctl is-active --quiet "$s" && echo "  $s: 正常" || echo "  [告警] $s: 未运行"
done

echo "[僵尸进程]"
Z=$(ps -eo stat | grep -c '^Z')
[ "$Z" -gt 0 ] && echo "  [告警] 存在 $Z 个僵尸进程" || echo "  无僵尸进程"

echo "===== 巡检结束 ====="
```

```shell
sudo chmod +x /opt/scripts/check.sh
/opt/scripts/check.sh
```

示例输出：

```text
===== 2026-08-19 02:00:01 巡检报告 server01 =====
[磁盘使用率 > 80%]
[内存]
  总 3.8Gi / 已用 1.2Gi / 可用 2.1Gi
[CPU 负载（1/5/15 分钟）]
   0.08, 0.12, 0.09
[关键服务状态]
  ssh: 正常
  nginx: 正常
[僵尸进程]
  无僵尸进程
===== 巡检结束 =====
```

解释：`df -hP` 用 `-P` 保证一行一个分区（POSIX 格式，避免换行破坏 awk 解析）；`gsub` 去掉 `%` 号再数值比较；`ps -eo stat` 列出进程状态，`^Z` 匹配僵尸进程；每个检查项异常就打 `[告警]` 前缀，方便后续 grep 告警行做通知。

### 步骤五：配置定时任务（cron 与 systemd timer）

方案 A：cron（写 `/etc/cron.d/ops-inspection`）：

```text
# 每天凌晨 2 点巡检，追加日志
0 2 * * * root /opt/scripts/check.sh >> /var/log/inspection.log 2>&1
```

```shell
sudo systemctl status cron        # Debian/Ubuntu 服务名 cron
sudo systemctl status crond       # RHEL 系服务名 crond
```

方案 B：systemd timer（写 `/etc/systemd/system/inspection.service` 和 `inspection.timer`）：

```ini
# inspection.service
[Unit]
Description=Inspection script

[Service]
Type=oneshot
ExecStart=/opt/scripts/check.sh
```

```ini
# inspection.timer
[Unit]
Description=Run inspection daily

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true
RandomizedDelaySec=300

[Install]
WantedBy=timers.target
```

```shell
sudo systemctl daemon-reload
sudo systemctl enable --now inspection.timer
systemctl list-timers inspection.timer --no-pager
# 手动触发一次验证
sudo systemctl start inspection.service
journalctl -u inspection.service -n 10
```

示例输出：

```text
NEXT                        LEFT       LAST                        PASSED    UNIT
Wed 2026-08-20 02:00:00 CST 18h left   n/a                         n/a       inspection.timer
```

解释：cron 按分时日月周五段排期，`0 2 * * *` 每天 2 点；systemd timer 用 `OnCalendar` 日历语法，`RandomizedDelaySec=300` 加最多 5 分钟随机延迟（避免所有机器同一秒巡检打满负载），`Persistent=true` 补跑错过的时间点，日志进 journald 可用 `journalctl` 查。

### 步骤六：发布流水线（构建→部署→健康检查→回滚）

写发布 playbook `~/ansible/deploy.yml`，把本地应用目录同步到受管节点、重启服务、健康检查：

```yaml
---
- name: 发布应用
  hosts: webservers
  become: true
  vars:
    app_dir: /opt/app
    app_version: "1.2.3"
    deploy_root: /var/www/app
  tasks:
    - name: 确保部署目录存在
      file:
        path: "{{ deploy_root }}"
        state: directory
        owner: www-data
        group: www-data

    - name: 同步应用代码到目标节点
      synchronize:
        src: "{{ app_dir }}/"
        dest: "{{ deploy_root }}/"
        delete: yes
        rsync_opts:
          - "--exclude=.git"
          - "--exclude=.env"

    - name: 重启应用服务
      service:
        name: app
        state: restarted

    - name: 健康检查
      uri:
        url: "http://localhost/health"
        status_code: 200
        timeout: 10
      register: health
      until: health.status == 200
      retries: 6
      delay: 5

    - name: 记录本次发布版本
      copy:
        content: "{{ app_version }}"
        dest: "{{ deploy_root }}/RELEASE_VERSION"
```

```shell
# 构建产物（这里以静态站为例：本地构建后打包）
cd /opt/app && tar czf /tmp/app-1.2.3.tar.gz .

# 执行发布
ansible-playbook -i ~/ansible/inventory.ini ~/ansible/deploy.yml
# 验证：看各节点版本文件和健康检查
ansible webservers -i ~/ansible/inventory.ini -m shell -a 'cat /var/www/app/RELEASE_VERSION && curl -s -o /dev/null -w "%{http_code}\n" http://localhost/health'
```

示例输出：

```text
web01 | CHANGED | rc=0 >>
1.2.3
200
web02 | CHANGED | rc=0 >>
1.2.3
200
```

解释：`synchronize` 用 rsync 增量同步（只传差异，比整包 copy 快），`delete: yes` 清掉目标端多余文件保证一致性，`--exclude` 排除 git 元数据和敏感配置；`uri` + `until/retries/delay` 做带重试的健康检查（最多 6 次、每次间隔 5 秒，等应用启动完成）；写 `RELEASE_VERSION` 文件记录版本，回滚时据此判断。

### 步骤七：发布回滚机制

把上一版本保留，失败一键回滚：

```shell
# 发布前先备份当前版本（在目标节点上）
ansible webservers -i ~/ansible/inventory.ini -m shell -b -a \
  'cp -a /var/www/app /var/www/app.bak.$(date +%s)'

# 若新版本发布失败（健康检查不过），回滚
ansible webservers -i ~/ansible/inventory.ini -m shell -b -a \
  'ls -dt /var/www/app.bak.* | head -1 | xargs -I{} sh -c "rm -rf /var/www/app && mv {} /var/www/app" && systemctl restart app'
```

解释：发布前对目标目录做带时间戳的整目录备份；失败时取最近一份备份恢复并重启。生产环境更规范的做法是把「备份」和「回滚」也写成 playbook 任务（`when: health.status != 200` 触发），避免手工敲命令出错。

### 步骤八：整体验证清单

```shell
# 1. 批量管理：ping + ad-hoc 一次命令跑两台
ansible -i ~/ansible/inventory.ini all -m ping
ansible -i ~/ansible/inventory.ini all -m shell -a 'uptime'

# 2. 巡检脚本：手动跑一遍，确认告警逻辑生效
/opt/scripts/check.sh

# 3. 定时任务：cron 服务在跑 / timer 已激活、下次触发时间正确
systemctl status cron && crontab -l   # 或 systemctl list-timers inspection.timer

# 4. 发布流水线：deploy.yml 演练通过 + 健康检查 200
ansible-playbook -i ~/ansible/inventory.ini --check ~/ansible/deploy.yml
curl -s -o /dev/null -w '%{http_code}\n' http://localhost/health

# 5. 幂等性：site.yml 再跑一遍，changed=0（全部已是期望状态）
ansible-playbook -i ~/ansible/inventory.ini ~/ansible/site.yml
```

解释：第 5 步「重跑 changed=0」是检验 playbook 幂等性的标准手段——第二次执行应无任何变更，说明任务写成了「声明式」而非「一次性脚本」，这是 Ansible 配置管理价值的直接体现。

## 性能与调优

```text
1. 增大并发 —— 默认 5 台并行，机器多时用 -f 20 提升批量执行速度（SSH 连接有上限）
2. 关闭 fact 采集 —— 不依赖 ansible_facts 时 gather_facts: false，省一次全量信息收集
3. 长命令用 script 而非 shell 内联 —— 复杂脚本打成文件用 script module，避免转义和维护问题
4. 同步优先 rsync —— synchronize 增量传输比 copy 整包快，大目录发布差距明显
5. SSH 长连接复用 —— 配置 ControlPersist，复用 SSH 连接减少握手开销
6. 定时任务错峰 —— RandomizedDelaySec 或 cron 里加随机 sleep，避免多机同时巡检打满负载
```

```ini
# ansible.cfg 里开 SSH 长连接复用 + 调并发
[defaults]
forks = 20
[ssh_connection]
pipelining = True
control_path = /tmp/ansible-%%r@%%h:%%p
control_path_dir = /tmp/ansible
```

## 安全与权限

```text
1. 控制节点是核心 —— 私钥和 playbook 都在上面，单独防护、限制登录、定期备份
2. 密钥专用 —— Ansible 用独立密钥对，不和生产个人密钥混用，泄露可单独吊销
3. 最小提权 —— playbook 只对需要的 task 加 become，不要整个 play 无条件提权
4. 敏感数据不落地 —— 密码/token 用 ansible-vault 加密，别明文写进 playbook 或 inventory
5. 巡检脚本只读 —— 巡检脚本设只读权限，防止被篡改后借定时任务提权
6. 发布可追溯 —— playbook 和 inventory 进 git，发布记录 RELEASE_VERSION，审计有据可查
```

```shell
# 用 ansible-vault 加密敏感变量文件
ansible-vault encrypt ~/ansible/secrets.yml
# 执行时带密码解密
ansible-playbook -i inventory.ini --ask-vault-pass site.yml
# 巡检脚本只读
sudo chmod 755 /opt/scripts/check.sh && sudo chown root:root /opt/scripts/check.sh
```

## 故障排查

### ansible ping 不通（unreachable）

```shell
# 1. 手动 SSH 确认链路
ssh admin@192.168.1.11 'echo ok'
# 2. 看具体报错
ansible -i inventory.ini all -m ping -vvv
# 常见原因：私钥路径错、受管节点没装 python、ansible_user 写错、SSH 端口非 22 没在 inventory 标 ansible_port
```

### playbook 执行失败（failed）

```shell
# 1. 语法检查
ansible-playbook -i inventory.ini --syntax-check site.yml
# 2. 演练看会改什么、哪步报错
ansible-playbook -i inventory.ini --check site.yml
# 3. 定位失败 task（-v 增加输出）
ansible-playbook -i inventory.ini -v site.yml
# 常见原因：module 参数拼错、目标目录不存在、become 没提权导致权限不足
```

### 定时任务没跑

```shell
# cron：看 cron 日志和任务输出
sudo grep CRON /var/log/syslog | tail        # Debian/Ubuntu
sudo tail /var/log/cron                      # RHEL 系
tail /var/log/inspection.log                 # 任务自己的日志
# systemd timer：看 timer 和最近一次执行
systemctl list-timers inspection.timer
journalctl -u inspection.service -n 20
# 常见原因：timer 没 enable、OnCalendar 写错、脚本无执行权限
```

### 发布后服务起不来

```shell
# 1. 看健康检查失败原因
curl -v http://localhost/health
# 2. 看应用日志
sudo journalctl -u app -n 50
# 3. 直接回滚上一版本
ls -dt /var/www/app.bak.* | head -1
# 常见原因：新版本配置缺文件、依赖没装、环境变量没注入、健康检查路径写错
```

## 常见问题

```text
Q1: Ansible 是 agentless，原理上怎么在远端执行？
A: 控制节点通过 SSH 连接受管节点，把 module 代码和参数打包上传到临时目录，在远端用 python 执行后回收结果删除临时文件，不需要预装 agent。

Q2: ad-hoc 命令和 playbook 什么时候用哪个？
A: ad-hoc（ansible -m）适合一次性、临时操作（查状态、重启一个服务）；playbook 适合可重复、要进版本库、多步骤的流程（部署、批量配置）。重复两次以上的操作就该写成 playbook。

Q3: 什么是幂等性？为什么重要？
A: 幂等 = 重复执行结果不变。Ansible 的 module 都是幂等的（包已装就跳过、文件已一致就不改），playbook 可以反复跑不产生副作用，这是它比一次性脚本可靠的根本原因。

Q4: cron 和 systemd timer 选哪个？
A: 简单的一次性排期 cron 够用；需要「补跑错过的任务」「随机延迟」「日志进 journald」「和 service 绑定」时用 systemd timer。现代发行版建议新任务优先 timer。

Q5: 发布流水线如何保证失败能回滚？
A: 发布前备份当前版本（带时间戳），健康检查不过就恢复备份 + 重启服务；版本写 RELEASE_VERSION 文件记录，配合 git tag 让「当前线上是哪个版本」可追溯。
```

## 面试题

```text
1. Ansible 和 shell 脚本批量管理有什么区别？
   答：Ansible 是声明式配置管理——描述「期望状态」（包要装、文件要这个内容），幂等可重复执行；shell 脚本是命令式——描述「执行步骤」，重复执行可能有副作用、也不易维护。Ansible 还带 inventory 分组、变量、模板、错误处理。

2. Ansible 的执行流程和通信方式？
   答：agentless，通过 SSH 连接受管节点；把 module 打包上传远端用 python 执行，回收结果。控制节点只需 SSH 免密 + 受管节点有 python，无需装 agent。

3. 如何设计一个每日巡检方案？
   答：巡检脚本检查磁盘/内存/负载/服务/僵尸进程 → systemd timer（OnCalendar 每天 2 点 + Persistent + 随机延迟）排期 → 结果写日志 + 异常行告警（配合 26.3 的 Alertmanager 或邮件）。定时任务错峰避免多机同时打满。

4. 一条完整的发布流水线包含哪些环节？
   答：代码提交 → 构建产物 → 同步到目标节点（rsync 增量）→ 更新配置 → 重启服务 → 健康检查（带重试）→ 成功后记录版本、失败回滚到上一版本。

5. Ansible 怎么处理不同发行版（Debian/RHEL）差异？
   答：用 `when: ansible_os_family == "Debian"` 条件执行 apt 专属任务；或直接用跨发行版的 `package` module（自动选 apt/dnf/yum）；变量里按 os_family 定义不同软件包名。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 重复两次以上的操作写成 playbook 进 git，别一直用 ad-hoc 硬敲
2. 优先用专用 module（package/copy/service/user），少用 shell 裸命令，保证幂等
3. 执行前 `--syntax-check` + `--check` 演练，确认要改什么再真跑
4. 敏感信息用 ansible-vault 加密，inventory 和 playbook 进版本库
5. 定时任务错峰 + Persistent，巡检脚本只读权限
6. 发布流水线必带健康检查 + 回滚，失败能一键恢复
7. 用 `changed=0` 二次执行验证幂等性，作为 playbook 质量门槛

### 踩坑记录

```text
坑 1：受管节点没装 python，ansible ping 一直 unreachable
结论：ping 模块报错，ad-hoc 全失败。
原因：Ansible 靠受管节点 python 执行 module，极简系统/容器镜像常不带 python。
解法：受管节点先装 python3（apt install -y python3 / dnf install -y python3）。

坑 2：整个 play 无条件 become，误改了不该改的
结论：批量执行时普通任务也提权，权限过大误操作风险高。
原因：play 级 `become: true` 让所有 task 都以 root 跑。
解法：play 级不提权，只在需要的 task 上加 `become: true`，最小提权。

坑 3：密码明文写进 inventory/playbook，泄露到 git
结论：数据库密码、token 被提交进版本库。
原因：图省事把敏感值直接写在配置文件里。
解法：敏感值用 ansible-vault 加密（secrets.yml），或用环境变量/配置管理注入，绝不进明文 git。

坑 4：巡检脚本没加执行权限，定时任务静默失败
结论：cron/timer 显示跑了，但日志里一直没输出。
原因：脚本没 chmod +x，定时任务调用时报 permission denied，重定向到日志里却没人看。
解法：写脚本后 chmod +x，配好后手动触发一次验证，再看日志确认真的执行了。

坑 5：多机同一时刻巡检，打满负载
结论：定时任务一到点，几十台机器同时跑巡检，CPU/IO 尖峰。
原因：所有机器 OnCalendar 或 cron 设了同一时刻，无错峰。
解法：systemd timer 加 RandomizedDelaySec，或 cron 里加随机 sleep，把执行时间打散。

坑 6：发布用整包 copy，大项目慢且目标残留旧文件
结论：发布慢、目标目录残留已删除的文件，环境不一致。
原因：copy 整包覆盖，不清理目标端多余文件。
解法：用 synchronize（rsync）增量同步 + `delete: yes` 清掉多余文件，发布快且目录干净。
```
