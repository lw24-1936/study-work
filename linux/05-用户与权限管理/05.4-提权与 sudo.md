## 概述

提权是「普通用户临时获得更高权限」的机制。su 切换用户（su - 完整切到 root），sudo 以 root 身份执行单条命令。生产环境的标准做法是：禁用 root 直接登录，普通用户用 sudo 提权——因为 sudo 能做细粒度授权（谁能在哪台机器跑什么命令）和留审计日志。sudoers 是授权配置，visudo 是安全编辑它的工具，sudo 日志在 /var/log/auth.log。
```text
提权机制全景：
1. su —— 切换用户身份，su - 完整切到目标用户环境
2. sudo —— 以 root（或指定用户）执行单条命令，细粒度授权 + 审计
3. sudoers —— /etc/sudoers 定义谁能在哪跑什么
4. visudo —— 安全编辑 sudoers（带语法检查）
5. Polkit —— 桌面/服务层的权限框架，非命令行场景用
```
## 核心概念

提权的五个核心概念：su、sudo、sudoers、visudo、Polkit。下面逐一展开。
### su 与 sudo

**是什么**：su（switch user）是「切换用户」，切过去就一直以目标用户身份操作；sudo（superuser do）是「借 root 身份执行单条命令」，执行完回到原身份。

**为什么**：su 需要 root 密码（或目标用户密码），密码要分发，切过去风险大、无法审计具体命令；sudo 用当前用户自己的密码提权，能按「谁 + 在哪 + 跑什么命令」细粒度授权，且每一条都有日志。所以生产环境统一用 sudo，禁用 root 直接登录。

**怎么用**：`su -` 切到 root 的完整登录环境（需要 root 密码），`su - 用户名` 切到指定用户，`su -c '命令' 用户` 以某用户身份执行单条命令。sudo 则 `sudo 命令` 用自己密码提权，`sudo -u deploy` 指定以谁的身份跑。

**边界/易错点**：`su`（不带 `-`）不加载目标用户环境，PATH 还是原来的，可能找不到命令或残留环境变量；`sudo echo $VAR` 里 `$VAR` 由当前用户 shell 展开（不是 root），要让 root 展开得 `sudo bash -c 'echo $VAR'`。
```shell
su -                  # 切到 root（输 root 密码）
su - deploy           # 切到 deploy 用户
su -c 'id' deploy     # 以 deploy 身份执行单条命令后返回
su -s /bin/bash alice # 指定切换后的 shell
sudo systemctl restart nginx    # 用自己密码提权执行单条命令
sudo -u deploy whoami           # 以 deploy 身份执行
sudo -i                # 获得 root 交互 shell（等价 su - 但走 sudo）
```
```text
# 实测
$ sudo --version | head -1
Sudo 版本 1.9.15p5
```
### sudoers 配置

**是什么**：sudoers（/etc/sudoers + /etc/sudoers.d/*）是 sudo 的授权配置文件，定义「谁、在哪台机器、能以谁的身份、执行什么命令」。

**为什么**：sudo 本身只是一个提权工具，具体谁有权限完全由 sudoers 决定。没有 sudoers 条目，sudo 直接报「not in the sudoers file」。它是 sudo 细粒度授权的核心。

**怎么用**：核心语法 `用户 主机=(以谁的身份) 命令列表`。`deploy ALL=(ALL) NOPASSWD: /usr/bin/systemctl` 允许 deploy 免密执行 systemctl。细分条目放 /etc/sudoers.d/ 下（用 visudo 编辑），别直接改主文件。常用占位符 ALL、NOPASSWD 免密、%组名 表示组。

**边界/易错点**：命令要写绝对路径（写 `systemctl` 不写 `/usr/bin/systemctl` 会被拒绝）；通配符 `*` 匹配过多会变成提权漏洞（`/usr/bin/cat *` 等于允许读任意文件）；sudoers.d 里的文件名不能含 `.` 或以 `~` 结尾（会被 sudo 忽略）；同一条目多次出现时**最后匹配的条目生效**。
```text
sudoers 语法拆解：
deploy ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx
│      │    │       │        └─ 允许的命令（可逗号分隔多条）
│      │    │       └─ NOPASSWD 免密，省略则要输密码
│      │    └─ 以谁的身份执行（ALL=任意用户，含 root）
│      └─ 在哪些主机生效（ALL=所有主机）
└─ 授权给谁（用户，%dev 表示 dev 组）
```
### visudo 安全编辑

**是什么**：visudo 是编辑 sudoers 的专用工具，保存前做语法检查，语法错误会提示而不写入。

**为什么**：sudoers 语法严格，一个语法错误（漏了冒号、写错占位符）会让 sudo 整体解析失败、所有提权通道锁死。直接 `vi /etc/sudoers` 改坏就是生产事故。visudo 在写入前校验，写坏了它直接拒绝保存，保护提权通道。

**怎么用**：`visudo` 编辑主文件，`visudo -f 文件` 编辑指定文件，`visudo -c` 只做语法检查不改内容，`visudo -s` 严格模式（对老旧语法告警）。visudo 用 `$EDITOR` 指定的编辑器，且有锁文件防止两个管理员同时编辑。

**边界/易错点**：visudo 只管语法检查，不管「授权是否合理」（给了 `ALL ALL` 它照样通过）；visudo 默认编辑 /etc/sudoers，编辑 sudoers.d 要显式 `-f`；改完务必 `visudo -c` 复检。
```shell
visudo                          # 编辑 /etc/sudoers（带语法检查）
visudo -f /etc/sudoers.d/dev    # 编辑某个 sudoers.d 文件
visudo -c                       # 检查语法（不改内容）
visudo -s                       # 严格模式检查（对不规范语法告警）
```
```text
# 实测
$ visudo -c
/etc/sudoers：解析正确
/etc/sudoers.d/README：解析正确
```
### sudo 日志与审计

**是什么**：sudo 的每次提权都会记录到 /var/log/auth.log（Debian/Ubuntu）或 /var/log/secure（Red Hat 系），记录「谁、什么时候、在哪、提权执行了什么命令、成功还是失败」。

**为什么**：sudo 之所以能替代直接 root 登录，关键就是它留审计痕迹。出事故能回溯「谁在什么时间动了什么」，安全审计、合规、排查「谁删了文件」都靠它。

**怎么用**：`grep sudo /var/log/auth.log` 查提权记录；日志格式为 `sudo: 用户 : TTY=pts/0 ; PWD=... ; USER=root ; COMMAND=...`；配 `log_output` 还能把命令的标准输出也记下来，实现「连执行结果都能审计」。

**边界/易错点**：auth.log 默认权限 640、属主 syslog 属组 adm，普通用户读不到，要 root 或 adm 组；默认只记「命令名」不记「命令输出」，要输出审计得显式开 log_output；日志量大要配 logrotate 轮转。
```text
# 实测（本机 sudo 审计日志）
$ ls -l /var/log/auth.log
-rw-r----- 1 syslog adm 152972  8月 18 22:28 /var/log/auth.log
# 权限 640，属主 syslog、属组 adm——只有 root 和 adm 组能读
```
```shell
# 审计 sudo 使用记录
grep 'sudo' /var/log/auth.log | tail
# 查看某用户的提权历史
grep 'sudo.*alice' /var/log/auth.log
# 排查失败的 sudo 尝试
grep 'sudo.*FAILED' /var/log/auth.log
```
```text
# sudo 日志条目字段（真实格式）
sudo:   alice : TTY=pts/0 ; PWD=/home/alice ; USER=root ; COMMAND=/usr/bin/systemctl restart nginx
        │       │           │                 │                 └─ 实际执行的命令
        │       │           │                 └─ 以谁的身份执行（USER=root 即提权到 root）
        │       │           └─ 发起命令时的目录
        │       └─ 终端
        └─ 提权的用户
```
### Polkit

**是什么**：Polkit（原名 PolicyKit）是「非命令行场景」的权限框架——桌面程序、systemd 服务、图形界面里的授权弹窗（「输入管理员密码」那个框）都走 Polkit。它是「进程间授权」的中间层。

**为什么**：sudo 只覆盖命令行提权，桌面程序（如软件更新、磁盘管理 GUI）要临时要 root 权限时，不能弹一个终端让人敲 sudo——Polkit 提供统一的授权请求机制，让 GUI 弹窗申请、由策略决定是否放行。

**怎么用**：动作定义在 /usr/share/polkit-1/actions/*.policy（XML），自定义规则写在 /etc/polkit-1/rules.d/*.rules（JavaScript）；`pkaction --list` 列出全部动作，`pkexec 命令` 是 Polkit 的命令行提权入口（类似 sudo 但走 Polkit）。

**边界/易错点**：服务器场景几乎不碰 Polkit（只有 systemd 的少数操作如 shutdown/挂载会经过它），桌面/图形环境才常用；pkexec 和 sudo 是两套独立授权，互不共享 sudoers；Polkit 规则用 JavaScript 写，语法错会导致授权失效。
```text
sudo vs Polkit：
1. sudo —— 命令行提权，配置在 sudoers，日志在 auth.log
2. Polkit —— 进程间授权（桌面弹窗、systemd 服务操作），动作定义在 polkit-1/actions
3. 场景 —— 服务器主要用 sudo，桌面/图形环境才常碰 Polkit
```
```shell
# 查看 Polkit 支持的动作
pkaction --list | head
# Polkit 的命令行提权入口（类似 sudo）
pkexec whoami
# 自定义授权规则目录（JavaScript 语法）
ls /etc/polkit-1/rules.d/
```
```text
四种提权方式对比：
su        切换用户，需目标用户密码，切换后一直是该用户，无细粒度授权、无命令级审计
sudo      借 root 执行单条命令，用自己密码，sudoers 细粒度授权 + auth.log 审计
sudoedit  安全编辑 root 文件（sudo -e），编辑器以普通用户身份跑，只对目标文件提权
pkexec    Polkit 的命令行提权入口，走 Polkit 策略（rules.d），与 sudoers 两套独立授权
```
## 工作原理

sudo 能提权的底层是 **setuid 位**：/usr/bin/sudo 这个二进制文件属主是 root 且带 setuid 位，任何用户执行它时，进程的 euid 会临时变成 root。流程是：

1. 用户运行 `sudo 命令`，sudo 进程以 root 的 euid 启动（靠 setuid）。
2. sudo 读 /etc/sudoers（+ sudoers.d）判断「当前用户 + 主机 + 命令」是否被授权。
3. 授权通过后，sudo 通过 PAM（/etc/pam.d/sudo）验证用户密码（默认用用户自己的密码，因为 sudo 是「证明你是本人」）。
4. 验证通过，sudo 把命令以 root（或指定 runas 用户）身份 fork+exec 执行，并把结果返回。

su 则不同：su 靠「输入目标用户的密码」来证明你被授权切换，然后启动一个目标用户的登录 shell。

sudo 的「免密窗口」机制：第一次输密码后，sudo 会写入一个时间戳文件（/var/run/sudo/ts/<用户名>），在 timestamp_timeout（默认 15 分钟）内再次 sudo 不用再输密码。`sudo -v` 手动刷新这个时间戳，`sudo -k` 让它立即失效。
```text
sudo 提权流程：
用户 → sudo 命令 → setuid 使进程 euid=root
  → 读 sudoers 判断授权（谁/主机/命令）
  → PAM 验证用户密码（/etc/pam.d/sudo）
  → fork+exec 以 root 执行命令 → 记录到 auth.log
setuid 位：ls -l /usr/bin/sudo 会看到 -rwsr-xr-x，属主 root 的 s 位
```
```text
免密时间戳机制：
第一次 sudo 输密码 → 写时间戳文件 /var/run/sudo/ts/<用户>
timestamp_timeout=15 分钟内再次 sudo 免密
sudo -v 刷新时间戳（延长窗口）/ sudo -k 立即使其失效
tty_tickets 开启时：时间戳按「终端」隔离，一个终端免密不影响另一个
```
```text
setuid 的局限与 capabilities：
setuid 是「全有或全无」——进程拿到 root 的 euid 就是完整 root 权限
capabilities 把 root 权限拆成几十个小权（CAP_NET_BIND_SERVICE 绑低端口、CAP_SYS_ADMIN 等）
现代做法倾向「给程序授最小 capability」而非 setuid 全量 root（systemd 的 CapabilityBoundingSet）
sudo 本身仍靠 setuid 启动：提权语义就是「临时完整 root」，授权面由 sudoers 收敛
```
## 常用命令与配置
```shell
# 提权执行
sudo 命令                          # 以 root 执行单条命令
sudo -u deploy 命令                # 以 deploy 身份执行
sudo -g dev 命令                   # 以 dev 组身份执行
sudo -i                            # root 交互登录 shell
sudo -s                            # root shell（不加载登录环境）
sudo -E 命令                       # 保留当前用户环境变量
sudo -b 命令                       # 后台执行（放回后台）
sudo -n 命令                       # 非交互：需要密码就直接失败（脚本里用）
sudo -e /etc/nginx/nginx.conf      # 安全编辑 root 文件（sudoedit，编辑器以普通用户跑）
# 查询与授权
sudo -l                            # 列出当前用户可执行的 sudo 命令
sudo -ll                           # 更详细列出（含具体条目来源）
sudo -l -U alice                   # 列出 alice 可执行的命令
sudo -v                            # 刷新凭据时间戳（延长免密窗口）
sudo -k                            # 失效当前凭据时间戳（下次必须再输密码）
# 编辑与校验
visudo                             # 安全编辑 /etc/sudoers
visudo -f /etc/sudoers.d/dev       # 编辑某个 sudoers.d 文件
visudo -c                          # 只做语法检查，不改内容
```
```text
常用配置开关（sudoers 里的 Defaults）：
1. env_reset —— 重置环境变量（默认开启，安全）
2. secure_path —— sudo 下的 PATH，防止用户注入恶意命令路径
3. timestamp_timeout=N —— 免密窗口时长（分钟），默认 15
4. log_output —— 把提权执行的命令输出也记进日志
5. !lecture —— 关闭首次使用 sudo 的提示
6. tty_tickets —— 时间戳按终端隔离（默认开启）
7. mail_badpass —— 密码输错时给 root 发邮件告警
```
## 配置文件解析

sudoers 的完整语法（/etc/sudoers + /etc/sudoers.d/*）：
```ini
# /etc/sudoers 结构
Defaults        env_reset,timestamp_timeout=15   # 全局默认（重置环境、免密 15 分钟）
Defaults        secure_path="/usr/local/sbin:/usr/sbin:/sbin:/usr/bin:/bin"
root    ALL=(ALL:ALL) ALL                       # root 全权限（含所有组）
@includedir /etc/sudoers.d                       # 加载 sudoers.d 下的细分条目
# 别名定义（可读性）
User_Alias  ADMINS = alice,bob                  # 用户别名
Runas_Alias WEBUSER = www-data,deploy           # runas 目标别名
Host_Alias  WEBSRV = web01,web02                # 主机别名
Cmnd_Alias  SERVICES = /usr/bin/systemctl        # 命令别名
# 授权条目语法：用户 主机=(runas用户:runas组) 标签: 命令
ADMINS  ALL=(ALL) NOPASSWD: SERVICES            # ADMINS 免密执行 systemctl
deploy  web01=(root) /usr/bin/systemctl restart nginx   # 只在 web01 上可执行
%dev    ALL=(ALL) ALL                           # dev 组全权限
alice   ALL=(ALL) /usr/bin/cat /var/log/*.log, !/var/log/auth.log   # 允许读日志、排除敏感日志
```
```text
字段含义（授权条目 = 谁 在哪 以谁 跑什么）：
用户/组        %dev 表示组，裸用户名表示单个用户
主机          ALL 所有主机，或具体主机名/IP（多机共用一个 sudoers 时用）
(runas:组)    以谁的身份执行，(ALL) 任意用户，(root) 只 root
标签          NOPASSWD: 免密，PASSWD: 要密码（默认）
              还有 NOEXEC:（禁 exec）、SETENV:（允许改环境）、LOG_INPUT/LOG_OUTPUT:
命令          绝对路径，逗号分隔多条；!命令 表示排除；* 通配，"" 匹配空参数
```
```text
sudoers.d 文件的三个规则：
1. 文件名不能含 . 或以 ~ 结尾（如 dev.conf~ 这种备份会被 sudo 直接忽略）
2. 文件权限必须 440、属主 root，权限松了 sudo 拒绝解析并告警
3. 按文件名字典序加载，同一条目后加载的覆盖先加载的
```
```text
Defaults 常用选项速查：
env_reset             重置环境变量（默认开启，安全）
secure_path="..."     固定 sudo 的 PATH
timestamp_timeout=15  免密窗口分钟数（0 = 每次都要密码）
tty_tickets           时间戳按终端隔离（默认开启）
log_output            记录提权命令的输出；log_input 记录输入
mail_badpass          密码输错时给 root 发邮件
rootpw / targetpw     改验 root / 目标用户密码（默认验当前用户，慎改）
Defaults:user !requiretty   针对单用户关闭 requiretty（允许无 tty 时 sudo，脚本场景）
```
## 应用场景实战
### 场景一：给运维同事配置最小化 sudo 权限
```shell
# 只允许重启 nginx 和查看系统状态，其它都不给
cat > /etc/sudoers.d/ops <<'EOF'
ops ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx
ops ALL=(ALL) NOPASSWD: /usr/bin/systemctl status nginx
ops ALL=(ALL) NOPASSWD: /usr/bin/journalctl
EOF
chmod 440 /etc/sudoers.d/ops      # 权限必须是 440，否则 sudo 拒绝解析
visudo -c                      # 校验语法
# 用 ops 用户验证授权结果
sudo -l -U ops
```
### 场景二：审计「谁用 sudo 干了什么」
```shell
# 查今天的 sudo 记录
grep 'sudo' /var/log/auth.log | tail -20
# 查是否有失败的提权尝试（可能被暴力破解）
grep -i 'sudo.*failed\|authentication failure' /var/log/auth.log | tail
# 查特定用户某时段的提权历史
grep 'sudo.*alice' /var/log/auth.log
# 只看「命令」字段，快速还原操作轨迹
grep 'sudo' /var/log/auth.log | grep -o 'COMMAND=.*'
```
### 场景三：给自动化部署账号配「白名单 + 排除危险命令」
```shell
# 场景：CI/CD 部署账号 deployer 只允许操作 nginx 和 systemctl，但禁止执行 rm 和 shell
cat > /etc/sudoers.d/deployer <<'EOF'
# 命令别名：把部署相关命令归类，可读性和解析都更好
Cmnd_Alias DEPLOY = /usr/bin/systemctl restart nginx, /usr/bin/systemctl status nginx, \
                    /usr/bin/nginx -t, /bin/systemctl reload nginx
# deployer 免密执行部署命令，但明确排除「用 systemctl 启动任意 shell/程序」的危险用法
deployer ALL=(ALL) NOPASSWD: DEPLOY, !/usr/bin/rm, !/bin/bash, !/bin/sh
EOF
chmod 440 /etc/sudoers.d/deployer
visudo -c
# 验证 deployer 的授权清单
sudo -l -U deployer
```
```text
场景三要点：
1. Cmnd_Alias 把命令归类，后续增删只需改别名定义处
2. !/usr/bin/rm、!/bin/bash 是「排除」——先允许 DEPLOY，再显式排除危险命令
3. sudoers 匹配顺序：最后匹配的条目生效，排除项写在允许项之后才可靠
```
## 性能与调优
```text
1. timestamp_timeout —— 免密窗口调太短频繁输密码影响效率，太长有风险；运维建议 5~15 分钟
2. sudo 本身开销极小（一次 setuid + PAM 校验），性能瓶颈不在提权而在被提权的命令
3. 高频提权脚本 —— 别在循环里反复 sudo，一次性 sudo 执行整段（或 sudo -i 后跑批）
4. 审计日志量大 —— auth.log 里 sudo 记录多时配日志轮转（logrotate），别让它塞满 /var
5. sudo 命令解析 —— 命令列表太长会拖慢解析，用 Cmnd_Alias 归类可读性和解析都更好
6. 免密窗口的代价 —— timestamp_timeout 太长等于「一次密码换长时间 root」，攻击者拿到终端可乘虚而入
```
## 安全与权限
```text
1. sudoers 文件权限 —— /etc/sudoers 和 sudoers.d/* 必须 440、属主 root，权限松了会被告警/拒绝解析
2. 禁止 root 直接 SSH 登录 —— /etc/ssh/sshd_config 配 PermitRootLogin no，统一走 sudo
3. secure_path —— 固定 sudo 的 PATH，防止用户在 PATH 里塞恶意同名命令
4. env_reset —— 默认开启，防用户通过环境变量注入（LD_PRELOAD 等）劫持提权命令
5. 最小授权 —— 给具体命令绝对路径，别 ALL=(ALL) ALL；能用免密就别给宽命令
6. sudo 日志审计 —— log_output 记录命令输出，定期 grep auth.log 找异常提权
7. wheel/sudo 组 —— 传统做法把管理员加进 wheel（RH）或 sudo（Debian）组，组授权 %wheel ALL=(ALL) ALL
8. 通配符风险 —— /usr/bin/cat * 等于允许读任意文件，通配符命令要配合 !排除 收敛范围
```
## 故障排查
```shell
# 1. "xxx is not in the sudoers file" —— 用户没被授权
sudo -l -U alice                     # 看 alice 到底授权了啥
# 2. 报语法错误 —— sudoers 改坏了
visudo -c                            # 定位语法错误在哪一行
# 3. sudoers.d 文件权限不对导致不生效
ls -l /etc/sudoers.d/                # 必须是 440、属主 root
# 4. NOPASSWD 配了还要密码
grep -n 'NOPASSWD' /etc/sudoers.d/*  # 确认 NOPASSWD 紧跟 (runas) 之后、命令之前
# 5. sudo 后环境变量丢了
sudo -E 命令                          # 保留环境；或 sudoers 加 env_keep
# 6. sudoers.d 里写的条目没生效
ls -l /etc/sudoers.d/                # 文件名不能含 . 或 ~ 结尾，权限要 440
# 7. sudo 报 "command not found"
which 命令                           # sudo 用 secure_path，普通用户的 PATH 未必一致
```
```text
排查顺序：
sudo -l -U 用户 确认授权 → visudo -c 确认语法 → ls -l 确认权限 → 看 auth.log 看实际报错
```
```shell
# 7. sudo 报 "a terminal is required to read the password"（无 tty 场景）
sudo -S 命令 < /path/to/password   # 从 stdin 读密码（脚本里慎用，密码别硬编码）
# 8. 授权给某用户但 sudo -l 看不到（组授权 vs 用户名授权混淆）
id alice                            # 确认用户实际属于哪个组，再核对 %组 授权
```
## 常见问题
```text
Q1: sudo 和 su 的区别？
A: su 切到目标用户（要目标用户密码），切过去就是那个用户；sudo 用自己密码借 root 执行单条命令，可细粒度授权 + 审计。
Q2: sudo 为什么要输自己的密码而不是 root 密码？
A: sudo 的语义是「证明你是本人」，所以默认验当前用户密码（PAM 的 pam_unix 验）。这避免把 root 密码分发给多人。
Q3: NOPASSWD 和 ALL 的区别？
A: NOPASSWD 是「免密」标签，ALL 是「所有命令/主机/身份」的占位符。NOPASSWD: ALL = 免密执行任意命令 = 形同 root。
Q4: 改了 sudoers 后所有 sudo 都报错，怎么救？
A: 用 pkexec 或切到 root（su -，如果 root 能登录）或救援/单用户模式，跑 visudo 修复语法。
Q5: sudo -i 和 su - 有啥区别？
A: 都是得到 root 登录 shell，sudo -i 走 sudoers 授权（用自己密码），su - 用 root 密码。sudo -i 有审计记录，su - 没有 sudo 那套授权控制。
Q6: sudoers.d 里的文件名有什么要求？
A: 文件名不能含 . 或以 ~ 结尾（如 dev.conf~ 备份会被忽略），权限必须 440 属主 root，否则 sudo 拒绝解析该文件。
Q7: sudoers 里的通配符 * 有风险吗？
A: 有。`/usr/bin/cat *` 等于允许 cat 读任意文件（包括 /etc/shadow），形同任意文件读取。用通配符要配合 !排除（如 !/var/log/auth.log）收敛范围，或改用具体路径。
Q8: 怎么让 sudo 也记录「命令的输出」，而不只是命令名？
A: sudoers 里加 `Defaults log_output`，sudo 会把提权命令的标准输出也写进日志（需配合 log_input 记输入）。注意输出可能含敏感信息，日志要收紧权限并轮转。
```
## 面试题
```text
1. sudo 提权的底层原理？
   答：/usr/bin/sudo 属主 root 且带 setuid 位，执行时进程 euid 临时变 root；然后读 sudoers 判断授权，经 PAM 验密码，再以 root fork+exec 命令。
2. sudoers 的授权条目怎么理解？
   答：用户 主机=(runas) 命令。谁、在哪台机器、以谁的身份、跑什么命令。NOPASSWD 免密，%组 表示组，ALL 是通配。
3. 为什么推荐 sudo 而不是直接 su 到 root？
   答：sudo 细粒度授权（只给需要的命令）、有审计日志（谁在何时跑了什么）、不共享 root 密码、可随时收回权限。
4. visudo 和 vi 直接改 sudoers 的区别？
   答：visudo 保存前做语法检查，语法错误不写入（防锁死提权通道）；vi 直接改一个语法错就整体解析失败，所有 sudo 失效。
5. 怎么防 sudo 被滥用？
   答：最小授权（具体命令绝对路径）、禁用 root 登录、secure_path 固定 PATH、env_reset 重置环境、log_output 记录输出、定期审计 auth.log。
6. sudo 的免密时间戳机制是什么？
   答：第一次 sudo 输密码后写时间戳文件 /var/run/sudo/ts/<用户>，timestamp_timeout（默认 15 分钟）内再次 sudo 免密。sudo -v 刷新、sudo -k 失效。tty_tickets 让时间戳按终端隔离。
7. Polkit 和 sudo 有什么区别？
   答：sudo 管命令行提权（sudoers 配置、auth.log 审计），Polkit 管进程间授权（桌面弹窗、systemd 服务操作），动作定义在 polkit-1/actions、规则写在 rules.d。服务器主要 sudo，桌面才常碰 Polkit。
8. sudoers 的通配符 * 怎么安全使用？
   答：通配符会让命令匹配范围扩大（/usr/bin/cat * 可读任意文件），要配合 !排除危险路径（!/etc/shadow），或用 "" 匹配空参数、写具体绝对路径收敛授权面。
```
## 最佳实践与踩坑记录
### 最佳实践

1. 生产环境禁用 root 直接 SSH 登录，统一走 sudo 提权
2. 编辑 sudoers 永远用 visudo，改完 visudo -c 校验
3. sudo 授权按最小权限给，只给需要的命令，别用 ALL ALL
4. 细分授权放 /etc/sudoers.d/ 独立文件，主 sudoers 保持默认
5. 定期审计 auth.log 里的 sudo 记录，排查异常提权
6. 编辑 root 文件用 sudoedit（sudo -e），别 sudo vim（编辑器以 root 跑、风险大）
7. 通配符授权务必配合 !排除，把范围收敛到最小
### 踩坑记录
```text
坑 1：直接 vi 改 sudoers 改坏语法，所有 sudo 失效
结论：手改 sudoers 留了语法错误，之后 sudo 全部报错、提权通道锁死。
原因：sudoers 语法严格，一个错就整体解析失败。
解法：永远用 visudo（带语法检查），改完 visudo -c 校验。
坑 2：sudo 授权给了 ALL ALL 等于给了 root
结论：deploy ALL=(ALL) ALL 让 deploy 能执行任何命令，形同 root。
原因：命令字段 ALL 表示所有命令，授权过宽。
解法：按最小权限只列具体命令，能 systemctl 就别 ALL。
坑 3：NOPASSWD 放在错误位置导致不生效
结论：以为配了免密，执行还是要密码。
原因：NOPASSWD 必须紧跟 (ALL) 之后，位置错了被当命令解析。
解法：语法顺序 用户 主机=(身份) NOPASSWD: 命令，NOPASSWD 在命令前。
坑 4：sudo 后环境变量没带过去导致程序找不到配置
结论：sudo cmd 报找不到环境变量/配置，普通用户跑正常。
原因：sudo 默认重置环境（env_reset），PATH 等变量不传递。
解法：sudo -E 保留环境，或 sudoers 里配 env_keep，或写绝对路径。
坑 5：visudo 检查通过但授权不生效
结论：visudo -c 显示正确，但用户还是 sudo 不了。
原因：用户不在授权条目匹配范围（如组没加、主机不匹配），或文件权限不对。
解法：确认用户实际属于哪个组（id 命令），sudoers.d 文件权限必须是 440。
坑 6：sudoers.d 文件名带 . 或 ~ 结尾，条目被静默忽略
结论：把备份文件 dev.conf~ 留在 sudoers.d，里面配的授权一条都不生效。
原因：sudo 会忽略文件名含 . 或以 ~ 结尾的文件（备份文件不被加载）。
解法：清理 sudoers.d 里的备份/临时文件，文件名只用字母数字和下划线。
坑 7：sudo echo $VAR 拿到的是用户自己的变量，不是 root 的
结论：想用 sudo 读 root 环境变量，结果读到普通用户的旧值。
原因：shell 先展开 $VAR（在普通用户 shell 里），再执行 sudo。
解法：sudo bash -c 'echo $VAR'，让变量在 root 的 shell 里展开。
```
