## 概述

资源限制防止单个进程/用户占满系统资源。三个层次：ulimit（shell 会话级，限制单进程的资源）、limits.conf（登录时通过 PAM 持久化限制）、cgroups（内核级，按进程组/容器精确限制 CPU/内存/IO）。它们从「命令临时设」到「登录自动设」到「内核强制隔离」递进，容器（Docker）的资源限制底层就是 cgroups。
```text
三个层次的资源限制：
1. ulimit —— shell 会话级，限制单进程资源（文件数/进程数/内存），临时生效
2. limits.conf —— 登录时由 pam_limits 应用，持久化 per-user 限制
3. cgroups —— 内核级，按进程组精确限制 CPU/内存/IO，容器隔离的基础
```
## 核心概念

四个核心概念：ulimit、limits.conf、cgroups、Docker 容器资源限制。下面逐一展开。
### ulimit

**是什么**：ulimit 是 shell 内置命令，设置当前 shell 及其子进程的资源上限。关键项：-n 打开文件数（默认 1024，高并发服务常要调大）、-u 最大进程数、-c core 文件大小（默认 0，即不生成 core）、-s 栈大小。ulimit 分软限制（soft，可自行调高但不能超硬限制）和硬限制（hard，只能 root 调）。

**为什么**：单进程能开的 fd 数、能占的栈/内存都是有限的，ulimit 给它们设上限，防止失控进程（fd 泄漏、死循环开进程）拖垮系统。「Too many open files」这类错误本质就是触发了 nofile 上限。

**怎么用**：`ulimit -a` 看全部，`ulimit -n 65535` 临时调大，`ulimit -Sn` 看软限制、`ulimit -Hn 65535`（root）调大硬限制。设的值只对当前 shell 及之后启动的子进程生效，关掉 shell 就失效。

**边界/易错点**：ulimit 不持久化，重启/新 shell 就回默认；普通用户只能调软限制且不能超过硬限制；`ulimit -n 65535` 若超过硬限制（默认硬限制常是 1048576）能调，但 nproc 之类可能受限制；在 systemd 服务里 ulimit 会被服务的 LimitNOFILE 等覆盖。
```text
# 实测（本机默认）
$ ulimit -a | head
core file size   (blocks, -c) 0          # core 文件默认关闭
open files       (-n) 1024               # 打开文件数上限 1024
stack size       (kbytes, -s) 8192
max user processes (-u) 70250
```
```shell
ulimit -a            # 查看所有限制
ulimit -n            # 查看打开文件数限制
ulimit -n 65535      # 临时调大（软限制，当前 shell 生效）
ulimit -Sn           # 只看软限制，ulimit -Hn 只看硬限制
```
```text
ulimit 常用项速查（-S 软限制 / -H 硬限制）：
-n  nofile     打开文件数上限（高并发服务必调，默认 1024）
-u  nproc      最大进程/线程数
-c  core       core 文件大小（0 = 不生成）
-s  stack      栈大小（KB）
-m  rss        常驻内存上限（KB，多数新系统已不强制）
-v  as         虚拟内存/地址空间上限（KB）
-l  memlock    可锁定的内存上限（KB，数据库常要调大）
-f  fsize      单个文件最大写入大小（KB）
-t  cpu        CPU 时间上限（秒）
```
### limits.conf

**是什么**：limits.conf（/etc/security/limits.conf）是 ulimit 的持久化版本——登录时由 PAM 的 pam_limits 模块读取并应用。格式：`用户 类型 项 值`，类型 soft/hard/-（同时设），项包括 nofile（文件数）、nproc（进程数）、memlock（锁内存）。改完后重新登录生效。

**为什么**：ulimit 只在当前 shell 临时生效，重启就丢；limits.conf 把限制固化到配置文件，每次登录自动应用，生产上给数据库/高并发服务账号调大 nofile 就靠它，不用每次都手工 ulimit。

**怎么用**：编辑 /etc/security/limits.conf（或 /etc/security/limits.d/*.conf），写 `alice hard nofile 65535`，确认 pam_limits.so 在 common-session 里启用，重新登录（或 `su - 用户`）后 `ulimit -n` 验证。

**边界/易错点**：改完必须重新登录才生效（已登录会话不会重跑 PAM）；domain 用 `@组名` 表示组、`*` 表示所有用户；软限制可被用户自行调高到硬限制，硬限制只有 root 能调；systemd 服务（非登录会话）不走 pam_limits，要用服务的 LimitNOFILE 等指令。
```text
limits.conf 格式：
alice  hard  nofile  65535     # alice 的硬限制：最多打开 65535 个文件
@dev   soft  nproc   4096      # dev 组软限制：最多 4096 进程
*      soft  nofile  65535     # 所有用户
# 类型：soft 软限制 / hard 硬限制 / - 同时设软硬
```
```text
# 实测（本机 limits.conf 无自定义条目，走系统默认）
$ grep -vE '^\s*#|^\s*$' /etc/security/limits.conf
（空）
```
### cgroups 资源限制

**是什么**：cgroups（control groups）是内核级的资源隔离机制，按「进程组」精确限制 CPU、内存、IO 等资源。现代 Linux（Ubuntu 24.04）用 cgroups v2，统一挂在 /sys/fs/cgroup 下，systemd 把每个服务放进独立的 cgroup（user.slice/system.slice）。

**为什么**：ulimit/limits.conf 只限制「单个进程」的 fd/栈/core 这类资源，管不了「一组进程聚合用多少 CPU/内存/IO」。cgroups 按进程组记账并强制隔离，一个容器/服务跑飞了不会吃满整机，是 Docker/K8s 资源限制的底层。

**怎么用**：v2 下写 /sys/fs/cgroup/<层级>/ 下的控制文件（memory.max 内存上限、cpu.max CPU 配额、pids.max 进程数）；systemd 服务用 `systemctl set-property` 或单元里的 MemoryMax/CPUQuota；临时用 `systemd-run --scope -p MemoryMax=512M -- 命令` 给单条命令套限制。

**边界/易错点**：cgroups 限制的是「聚合」，单进程无法用 setrlimit 绕过；v1 和 v2 路径/语法完全不同，脚本要按版本适配；cgroup 写权限只有 root（或授权委托用户），容器内也看不到宿主机的 cgroup 树。
```text
# 实测（本机 cgroups v2）
$ mount | grep cgroup
cgroup2 on /sys/fs/cgroup type cgroup2 (...)
$ cat /proc/self/cgroup
0::/user.slice/user-0.slice/session-4296.scope
# 每个进程都属于一个 cgroup 层级，systemd 按 unit 组织（system.slice/user.slice）
```
```shell
# 查看 cgroup 层级
systemd-cgls              # 树状显示 cgroup 和进程
systemctl status --no-pager nginx   # 看服务的 cgroup 路径
# Docker 容器资源限制（底层就是 cgroup）
docker run --memory 512m --cpus 1 myapp
```
### Docker 容器资源限制

**是什么**：Docker 容器的资源限制命令（--memory、--cpus）不是 Docker 自己实现的，而是把参数翻译成 cgroup 配置——容器启动时，docker/containerd 给容器的 cgroup 写入 CPU/内存限制。

**为什么**：容器本质是「一组进程 + namespace + cgroup」。如果不用 cgroup 限制，容器里的进程能直接吃满宿主机内存/CPU，一个失控容器拖垮整台机器。所以生产上必须给每个容器设资源上限。

**怎么用**：常用参数：--memory 内存上限、--memory-swap 内存+swap 上限、--cpus CPU 核数、--cpuset-cpus 绑定具体核、--pids-limit 进程数上限、--blkio-weight 磁盘 IO 权重。容器内再配 ulimit（--ulimit）则是另一条独立的限制路径。

**边界/易错点**：--memory 只限内存、不自动限 swap，要严格限总内存得同时设 --memory-swap；--cpus 是配额（软上限、按比例），不是硬绑核，绑核用 --cpuset-cpus；Docker 默认不设 --memory 等于无限制。
```shell
# 限制容器最多用 512MB 内存、1 个 CPU
docker run -d --name app --memory 512m --memory-swap 512m --cpus 1.0 myapp:latest
# 限制容器进程数上限 512
docker run -d --name app --pids-limit 512 myapp:latest
# 覆盖容器内 ulimit（文件数）
docker run -d --name app --ulimit nofile=65535:65535 myapp:latest
```
```text
Docker 限制 vs cgroups 的对应关系：
--memory 512m        → cgroup 的 memory.max = 512MB
--cpus 1.0           → cgroup 的 cpu.max = 100000 100000（配额）
--pids-limit 512     → cgroup 的 pids.max = 512
--cpuset-cpus "0,1"  → cgroup 的 cpuset.cpus = 0,1（硬绑核）
```
## 工作原理

三个层次的限制作用在不同位置，机制也不同：

1. **ulimit**：由 shell 通过 setrlimit() 系统调用设置，限制的是「单个进程」的资源（fd 数、栈大小、core 等）。软限制可自行调高到硬限制，硬限制只有 root 能调。子进程继承父进程的 rlimit。
2. **limits.conf**：不直接生效，登录时 PAM 的 pam_limits.so 读 /etc/security/limits.conf，再调 setrlimit() 应用给登录会话——本质是「自动化的 ulimit」。
3. **cgroups**：内核态机制，按「进程组」记账并强制限制。限制的是「一组进程」的聚合资源（CPU 时间、内存、IO），不是单进程。由 cgroup 控制器（cpu/memory/io/pids）在资源分配时实时强制，无法用 setrlimit 绕过。
```text
限制层次对比：
ulimit      用户态 setrlimit()，限制单进程，可被进程自行调整（软限制）
limits.conf PAM 登录时自动 setrlimit()，等价「持久的 ulimit」
cgroups     内核态控制器，限制进程组，强制隔离，Docker/K8s 的基础
```
```text
cgroups v2 控制器工作方式：
cpu 控制器     cpu.max = "$MAX $PERIOD"，限制每周期 CPU 时间配额
               cpu.weight 相对权重（多进程争抢时按比例分）
memory 控制器  memory.max 硬上限（超了 OOM kill），memory.high 软上限（先节流再 OOM）
               memory.swap.max 限制 swap 用量
io 控制器     io.max 限制读写速率（IOPS/BPS），io.weight 相对权重
pids 控制器   pids.max 限制进程/线程总数
这些控制器在内核调度/内存分配时实时执行，进程自己用 setrlimit 无法突破
```
```text
cgroup v1 vs v2 关键差异：
挂载点   v1 每个控制器独立挂载（/sys/fs/cgroup/cpu、/memory、/blkio...）
         v2 统一挂载 /sys/fs/cgroup，控制器通过 cgroup.controllers 声明
CPU 限制 v1: cpu.cfs_quota_us / cpu.cfs_period_us
         v2: cpu.max = "$MAX $PERIOD"（如 "100000 100000" = 1 核配额）
内存限制 v1: memory.limit_in_bytes
         v2: memory.max（硬上限）/ memory.high（软上限）/ memory.swap.max
线程归属 v1 线程可挂在不同 cgroup（复杂），v2 必须与进程同组（更简单清晰）
迁移     v2 是默认且新方向，旧脚本要识别版本（mount | grep cgroup）适配
```
## 常用命令与配置
```shell
# ulimit
ulimit -a              # 查看全部限制
ulimit -n 65535        # 调大打开文件数（软限制）
ulimit -Sn             # 看软限制，-Hn 看硬限制
ulimit -Hn 65535       # root 调大硬限制
# limits.conf（改完重新登录生效）
echo "alice hard nofile 65535" >> /etc/security/limits.conf
grep pam_limits /etc/pam.d/common-session   # 确认已启用
# cgroups
systemd-cgls           # 树状查看 cgroup 与进程
cat /sys/fs/cgroup/memory.max          # 当前 cgroup 内存上限
systemd-run --scope -p MemoryMax=512M -- 命令   # 临时给命令套 cgroup 限制
systemctl set-property nginx MemoryMax=512M CPUQuota=100%   # 运行时改服务限制
# Docker
docker run --memory 512m --cpus 1.0 myapp   # 容器资源限制
docker stats --no-stream app                # 看容器资源使用
docker inspect app --format '{{.HostConfig.Memory}}'   # 看容器内存限制
```
## 配置文件解析

limits.conf 的四个字段（domain / type / item / value）：
```ini
# /etc/security/limits.conf 格式：domain  type  item  value
*       soft    nofile   65535        # 所有用户：打开文件软限制 65535
root    hard    nofile   65535        # root：打开文件硬限制
@dev    soft    nproc    4096         # dev 组：进程数软限制
alice   hard    memlock  102400       # alice：锁定内存上限（KB）
mysql   -       nofile   65535        # mysql：软硬同时设 65535
```
```text
字段含义：
domain   限制对象：用户名 / @组名 / *（所有用户）/ %组名（部分系统用 %）
type     soft 软限制（可自行调高到 hard）/ hard 硬限制（仅 root 可调）/ - 同时设
item     nofile 文件数 / nproc 进程数 / memlock 锁内存 / core / stack / as 地址空间 / fsize
value    数值，或 unlimited 表示不限制
```
```text
systemd 服务的资源限制（非登录会话不走 pam_limits，要在这里设）：
[Service]
LimitNOFILE=65535        # 打开文件数（等价 ulimit -n，服务的默认 1024）
LimitNPROC=4096          # 进程数
MemoryMax=512M           # cgroup 内存硬上限（超了 OOM）
MemoryHigh=400M          # 内存软上限（先节流）
CPUQuota=100%            # CPU 配额（100% = 1 核，200% = 2 核）
TasksMax=512             # 任务数（进程/线程）
```

cgroup v2 层级结构：
```text
/sys/fs/cgroup/                     # cgroup v2 统一挂载点
├── cgroup.controllers              # 启用的控制器（cpu memory io pids ...）
├── cgroup.subtree_control          # 子 cgroup 可用的控制器
├── system.slice/                   # 系统服务（每个 systemd unit 一个子目录）
│   └── nginx.service/              # nginx 的 cgroup，内存/CPU 限制写在这里
├── user.slice/                     # 用户会话（ssh 登录、桌面会话）
└── memory.max / cpu.max / pids.max # 具体限制文件（写入数值即生效）
```
```text
limits.conf 完整 item 清单（value 数值或 unlimited）：
nofile    打开文件数（fd 上限，高并发服务必调）
nproc     进程/线程数
memlock   可锁定内存（KB，数据库/高性能库调大避免 mlock 失败）
core      core 文件大小
stack     栈大小
as        地址空间上限
fsize     单文件最大写入大小
data      数据段大小
rss       常驻内存
cpu       CPU 时间（分钟）
nice      调度优先级（负数需 root）
priority  调度优先级
```
## 应用场景实战
### 场景一：给数据库服务调大打开文件数
```shell
# 编辑 limits.conf，给 mysql 用户调大 nofile
cat >> /etc/security/limits.conf <<'EOF'
mysql  soft  nofile  65535
mysql  hard  nofile  65535
EOF
# 确认 pam_limits 已启用（否则不生效）
grep pam_limits /etc/pam.d/common-session
# 重新登录后验证
su - mysql -c 'ulimit -n'
```
### 场景二：用 Docker 限制容器资源（cgroups 实践）
```shell
# 限制容器最多用 512MB 内存、1 个 CPU
docker run -d --name app --memory 512m --memory-swap 512m --cpus 1.0 myapp:latest
# 查看容器的资源使用和限制
docker stats app --no-stream
# 验证限制已写入 cgroup（宿主机上）
docker inspect app --format '{{.HostConfig.Memory}}'
```
### 场景三：用 systemd 限制服务的 CPU 和内存
```shell
# 场景：某个后端服务内存泄漏，先临时限制它别再吃满整机，再慢慢查泄漏
# 1. 临时给运行中的服务套限制（立即生效，重启失效）
systemctl set-property myapp MemoryMax=512M CPUQuota=100%
# 2. 看是否生效
systemctl show myapp | grep -E 'MemoryMax|CPUQuota'
# 3. 要持久化，写进服务单元文件
mkdir -p /etc/systemd/system/myapp.service.d/
cat > /etc/systemd/system/myapp.service.d/limits.conf <<'EOF'
[Service]
MemoryMax=512M
MemoryHigh=400M
CPUQuota=100%
EOF
systemctl daemon-reload
systemctl restart myapp
# 4. 验证 cgroup 里的实际限制值
cat /sys/fs/cgroup/system.slice/myapp.service/memory.max
```
```text
场景三要点：
1. systemd-run --scope 临时、set-property 运行时、service.d 覆盖文件持久，三种粒度
2. systemd 服务（非登录会话）不走 pam_limits，资源限制要在单元里设 LimitNOFILE/MemoryMax
3. MemoryMax 是硬上限（超了 OOM kill），MemoryHigh 是软上限（先节流再 OOM）
```
```text
systemd 限制服务的三种粒度：
1. 临时    systemd-run --scope -p MemoryMax=512M -- 命令（命令结束限制解除）
2. 运行时  systemctl set-property nginx MemoryMax=512M（立即生效，重启失效）
3. 持久    /etc/systemd/system/<svc>.service.d/override.conf 写 [Service] 段（重启后仍生效）

systemd 资源指令对照（单元 [Service] 段）：
LimitNOFILE=65535   → 等价 ulimit -n（setrlimit 层，进程 fd 数）
LimitNPROC=4096     → 等价 ulimit -u（进程数）
MemoryMax=512M      → cgroup memory.max（硬上限，超了 OOM）
MemoryHigh=400M     → cgroup memory.high（软上限，先节流）
CPUQuota=100%       → cgroup cpu.max 配额（100% = 1 核，200% = 2 核）
TasksMax=512        → cgroup pids.max（任务数）
```
## 性能与调优
```text
1. nofile 不是越大越好 —— 每开一个 fd 有内核开销，无脑 unlimited 会让失控进程耗尽系统 fd
2. 高并发服务标配 —— Nginx/MySQL/Java 的 nofile 调到 65535 起步，否则「Too many open files」
3. 内存限制和 swap —— Docker --memory 单独设时容器可用额外 swap，要严格限内存就 --memory-swap 设成和 --memory 一样
4. CPU 配额 —— --cpus 是「配额」（上限），不是「亲和」；要绑核用 --cpuset-cpus
5. cgroup 记账有开销 —— 每个控制器都增加调度开销，只启用需要的控制器
6. 多租户隔离 —— 用 cgroups 按租户分组限制，防止一个租户吃满整机拖垮其它租户
7. 软上限优先 —— memory.high/MemoryHigh 先节流、比直接 OOM 优雅，内存敏感服务用它代替硬上限
```
## 安全与权限
```text
1. 硬限制只能 root 调 —— 普通用户只能调软限制且不能超过硬限制，这是防用户自行放开的边界
2. 别把 nofile 设 unlimited —— 失控进程会耗尽系统文件描述符，设合理上限（65535）
3. core 文件默认关闭（ulimit -c 0）—— 防止 core 文件泄露内存敏感数据，排障时再临时开
4. cgroup 隔离多租户 —— 容器/服务按组隔离，防一个容器打爆宿主机（Docker 默认 --memory 不设 = 无限制）
5. limits.conf 权限 —— /etc/security/limits.conf 应 root 可写，防普通用户改自己的限制
6. cgroup 写权限 —— /sys/fs/cgroup 由 systemd/cgroupfs 管理，只有 root 或授权的委托用户能写
7. 容器的 root 也受 cgroup 限 —— 即使容器内进程是 root，也突破不了宿主机 cgroup 的限制（但内核漏洞除外）
8. 限制要「够用不浪费」 —— nofile 设太小服务报错、设太大失控进程耗尽 fd，按实际压测值加余量
9. cgroup 委托要显式授权 —— 让普通用户/容器管理子 cgroup 需通过 systemd 的 Delegate 或 cgroupfs 授权，默认只有 root 能写
```
## 故障排查
```shell
# 1. "Too many open files" —— nofile 不够
ulimit -n                              # 看当前限制
lsof -p <pid> | wc -l                  # 看进程实际开了多少 fd
# 2. limits.conf 改了不生效
grep pam_limits /etc/pam.d/common-session   # 确认启用
su - <用户> -c 'ulimit -n'                  # 重新登录（新会话）验证
# 3. 容器内存被 OOM 杀掉
docker inspect app --format '{{.State.OOMKilled}}'   # true 表示被 OOM
docker stats app --no-stream                        # 看内存使用是否逼近 --memory
# 4. cgroup 版本判断
mount | grep cgroup                      # cgroup2 = v2，tmpfs 多挂载点 = v1
cat /proc/self/cgroup                    # 看自己属于哪个 cgroup
# 5. systemd 服务 nofile 限制没生效
systemctl show nginx | grep LimitNOFILE  # 看服务的 LimitNOFILE（默认 1024，不是 pam_limits）
# 6. cgroup 限制写不进去

```

常见默认值与调整依据：
nofile 默认 1024          —— 历史兼容值，高并发服务（Nginx/MySQL）应调到 65535
nproc 默认较大            —— 桌面/登录会话进程多，服务端可按需收紧

## 常见问题
```text
Q1: ulimit 和 limits.conf 的区别？
A: ulimit 是 shell 命令，只对当前会话临时生效；limits.conf 是配置文件，登录时由 pam_limits 自动应用，持久化。
Q2: soft 和 hard 限制的区别？
A: soft 是当前生效值，普通用户可自行调高到 hard；hard 是上限，只有 root 能调。soft ≤ hard。
Q3: 为什么改了 limits.conf 后 ulimit -n 没变？
A: limits.conf 只在「新登录会话」时由 pam_limits 应用，已登录会话不会重跑，重新登录（或 su - 用户）才生效。
Q4: Docker 的 --memory 和容器内 ulimit 什么关系？
A: --memory 走 cgroup（限制整容器内存），容器内 ulimit 走 setrlimit（限制进程 fd/栈等）。两者独立，都从 dockerd 继承默认值，可分别覆盖。
Q5: cgroups v1 和 v2 的区别？
A: v1 每个控制器独立挂载点（/sys/fs/cgroup/cpu、/memory...），v2 统一挂 /sys/fs/cgroup、用 cgroup.controllers 管理。v2 是默认且是新方向，脚本要按版本适配。
Q6: systemd 服务的 nofile 为什么配了 limits.conf 不生效？
A: systemd 服务不是登录会话，不走 pam_limits；要在服务单元里设 LimitNOFILE（默认 1024），或 systemctl set-property 改。
Q7: memory.max 和 memory.high 有什么区别？
A: memory.max 是硬上限，超了直接 OOM kill；memory.high 是软上限，超了先节流（换出/回收），给应用缓冲时间，不会立刻被杀。
```
## 面试题
```text
1. 资源限制有哪几个层次？
   答：ulimit（单进程、会话级）、limits.conf（PAM 登录持久化）、cgroups（进程组、内核级）。三者从临时到持久到内核隔离递进。
2. soft 和 hard 限制是什么？
   答：soft 软限制（当前生效，可自行调高到 hard），hard 硬限制（上限，仅 root 可调）。进程能突破 soft 到 hard，但不能超过 hard。
3. limits.conf 怎么生效的？
   答：登录时 PAM 的 pam_limits.so 读 /etc/security/limits.conf，对登录会话调用 setrlimit() 应用，本质是自动化的 ulimit。
4. cgroups 和 ulimit 的本质区别？
   答：ulimit 限制单个进程的资源（fd/栈/core），cgroups 按进程组聚合限制（CPU/内存/IO），是内核态强制隔离，Docker/K8s 的容器限制底层就是它。
5. Docker 怎么限制容器资源？
   答：--memory/--cpus/--pids-limit 等参数被翻译成 cgroup 配置（memory.max/cpu.max/pids.max），由内核强制，容器内无法绕过。
6. 「Too many open files」怎么定位和解决？
   答：ulimit -n 看限制（默认 1024），lsof -p <pid> 看进程实际 fd 数；解决是持久化调大 limits.conf 的 nofile（或服务单元 LimitNOFILE），重新登录/重启生效。
7. 为什么 systemd 服务改了 limits.conf 的 nofile 没效果？
   答：systemd 服务不是登录会话、不走 pam_limits，limits.conf 对它无效；要在服务单元 [Service] 设 LimitNOFILE=65535。
8. 容器进程是 root，能突破宿主机的 cgroup 内存限制吗？
   答：不能。cgroup 限制由内核在内存分配时强制，容器内 root 只是 namespace 内的 root，没有宿主机内核权限，突破不了 memory.max（内核漏洞除外）。
```
## 最佳实践与踩坑记录
### 最佳实践

1. 高并发服务（Nginx/MySQL/Java）先把 nofile 调大（65535），否则「Too many open files」
2. 持久化限制用 limits.conf + pam_limits，比脚本里 ulimit 统一且不遗漏
3. 容器资源限制用 Docker/K8s 的 --memory/--cpus（底层 cgroups），别靠容器内 ulimit
4. 生产环境 core 文件默认关闭（ulimit -c 0），需要排障时再临时打开
5. 用 cgroups 做多租户资源隔离，防止一个服务拖垮整机
6. systemd 服务的资源限制写在服务单元（LimitNOFILE/MemoryMax），别只改 limits.conf
7. 内存敏感服务用软上限（MemoryHigh/memory.high）先节流，比直接 OOM 优雅
### 踩坑记录
```text
坑 1：ulimit -n 调大了但重启后失效
结论：当前 shell 里 ulimit -n 65535 生效，重启又变回 1024。
原因：ulimit 只在当前会话生效，不持久化。
解法：持久化写 /etc/security/limits.conf，或服务启动脚本里 ulimit。
坑 2：limits.conf 配了不生效
结论：写了 nofile 65535，登录后 ulimit -n 还是 1024。
原因：pam_limits.so 没启用，或改了没重新登录。
解法：确认 common-session 有 session required pam_limits.so，重新登录生效。
坑 3：nofile 设成 unlimited 或超大值导致问题
结论：nofile unlimited 后进程可能耗尽系统文件描述符。
原因：unlimited 是内核上限，进程能开的海量 fd 拖垮系统。
解法：设合理数值（如 65535），别用 unlimited。
坑 4：容器内 ulimit 和宿主机冲突
结论：容器里 ulimit -n 设的值和宿主机/启动参数不一致。
原因：容器默认继承 dockerd 的 ulimit，docker run 可单独覆盖。
解法：用 docker run --ulimit nofile=65535 显式设置容器限制。
坑 5：cgroups v1/v2 语法和路径不同导致脚本失效
结论：老的 cgroup 脚本在 v2 系统上报错（/sys/fs/cgroup/cpu 不存在）。
原因：v2 统一挂载点、用 cgroup.controllers 文件，路径和 v1 完全不同。
解法：识别系统 cgroup 版本（mount | grep cgroup），脚本按版本适配，或改用 systemd-run。
坑 6：systemd 服务的 nofile 改了 limits.conf 不生效
结论：给服务调大 nofile，结果服务里还是 1024，报 Too many open files。
原因：systemd 服务非登录会话，不走 pam_limits，limits.conf 对它无效。
解法：服务单元 [Service] 设 LimitNOFILE=65535，daemon-reload + restart。
坑 7：Docker 只设 --memory 不设 --memory-swap，容器能偷用 swap
结论：以为限死 512M，结果容器内存+swap 能超 512M。
原因：--memory 只限物理内存，swap 单独算，不设 --memory-swap 时容器可额外用 swap。
解法：要严格限总内存，--memory-swap 设成和 --memory 一样（512m），彻底禁额外 swap。
```
