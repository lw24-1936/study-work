## 概述

PAM（Pluggable Authentication Modules，可插拔认证模块）是 Linux 统一的认证框架——login、ssh、sudo、su 这些服务不再各自实现认证逻辑，而是统一调用 PAM。好处是「改一处认证策略，所有服务生效」。每个服务在 /etc/pam.d/ 下有自己的配置文件，里面是一串 PAM 模块，按顺序执行完成认证。理解 PAM 是配置「登录限制、密码策略、资源限制」的前提。

```text
PAM 核心概念：
1. 服务配置 —— /etc/pam.d/<服务名>，每个服务一个配置文件
2. 四类管理 —— auth 认证 / account 账号 / password 密码 / session 会话
3. 模块栈 —— 配置里一串模块按顺序执行，控制标志决定成败影响
4. 控制标志 —— required 必须过 / requisite 失败立即终止 / sufficient 过了就跳过后续
```

## PAM 模块

PAM 模块是编译好的 .so 库，每个负责一种认证能力。Debian/Ubuntu 用 common-auth、common-account、common-password、common-session 四个公共文件，各服务（login/sshd/sudo）include 它们。模块按四类管理分组：auth 验证身份（密码/密钥/指纹）、account 检查账号状态（是否过期/锁定）、password 改密码、session 会话前后处理。

```text
# 实测（本机 /etc/pam.d/ 下的配置）
$ ls /etc/pam.d/
common-auth  common-account  common-password  common-session
login  sshd  sudo  su  cron  passwd  chsh  ...
# Debian/Ubuntu 用 common-* 四个公共文件统一认证，各服务 include 它们
```

## 认证流程

认证流程是「服务 → PAM 配置 → 模块栈依次执行」。以 SSH 登录为例：sshd 调 /etc/pam.d/sshd → include common-auth → common-auth 里的模块依次执行（先 pam_unix 验密码，再可能 pam_deny 拒绝）。模块的控制标志决定流程：required 失败继续但最终失败、requisite 失败立即终止、sufficient 成功就通过（跳过后续）、optional 可选。理解这个栈的执行顺序，才能看懂「为什么登录被拒」。

```text
认证流程（以 SSH 登录为例）：
用户 → sshd → /etc/pam.d/sshd → include common-auth
  → pam_unix.so（验密码）
  → pam_deny.so（兜底拒绝）
四个控制标志：required（必须过，失败不中断）/ requisite（失败立即中断）/ sufficient（过了跳过后续）/ optional（可选）
```

```text
# /etc/pam.d/common-auth 结构（本机，省略注释）
auth    [success=1 default=ignore]  pam_unix.so nullok
auth    requisite                   pam_deny.so
auth    required                    pam_permit.so
# 第一行 pam_unix 验密码，成功跳到 pam_permit 通过，失败继续走 pam_deny 拒绝
```

## 常用模块

三个高频模块：pam_unix（密码认证，最基础）、pam_tally2（登录失败次数限制，防暴力破解）、pam_limits（资源限制，配合 /etc/security/limits.conf）。pam_unix 验证本地密码；pam_tally2 记录失败次数、超阈值锁定；pam_limits 在登录时应用 ulimit 类的资源限制。配置登录安全策略主要就是组合这三个模块。

```text
常用模块：
1. pam_unix —— 本地密码认证，nullok 允许空密码
2. pam_tally2 —— 登录失败计数与锁定，deny=5 失败 5 次锁定
3. pam_limits —— 应用 /etc/security/limits.conf 的资源限制
4. pam_deny / pam_permit —— 无条件拒绝 / 允许（栈的兜底）
```

```shell
# 在 common-auth 加登录失败锁定（防暴力破解）
auth required pam_tally2.so deny=5 unlock_time=300 even_deny_root
# 在 common-session 启用资源限制
session required pam_limits.so
```

## 应用场景实战

### 场景一：限制 SSH 登录失败次数防暴力破解

```shell
# 编辑 PAM 配置，失败 5 次锁定 5 分钟
# /etc/pam.d/common-auth 加一行：
auth required pam_tally2.so deny=5 unlock_time=300
# 查看某用户的失败锁定状态
pam_tally2 --user alice
# 手动解锁
pam_tally2 --user alice --reset
```

### 场景二：通过 PAM 限制用户资源（配 limits.conf）

```shell
# 编辑 /etc/security/limits.conf，限制用户进程数和文件数
# alice hard nproc 1024
# alice hard nofile 4096
# 确认 common-session 里有 pam_limits.so（否则不生效）
grep pam_limits /etc/pam.d/common-session
```

## 最佳实践与踩坑记录

### 最佳实践

1. 改 PAM 配置前先备份，改错会导致所有登录失败（SSH 进不去）
2. 改 PAM 后开另一个 SSH 会话测试，别把唯一会话改挂
3. 登录防暴力破解用 pam_tally2，配合 fail2ban 更完整
4. 资源限制走 limits.conf + pam_limits，比在脚本里 ulimit 统一
5. 理解控制标志（required/requisite/sufficient）再改模块栈，否则行为难预料

### 踩坑记录

```text
坑 1：改 PAM 配错把自己锁在系统外
结论：改 common-auth 语法错，SSH/登录全部失败，进不去了。
原因：PAM 认证是所有登录的必经路径，配错全局瘫痪。
解法：改前备份、开新会话测试；锁死用单用户模式或救援模式改回。

坑 2：pam_tally2 配了不生效
结论：加了 pam_tally2 行，登录失败不计数、不锁定。
原因：模块顺序不对，或没加 required 控制标志，或 pam_tally2 位置在 pam_unix 之前。
解法：pam_tally2 放 pam_unix 之前（先计数再验密），并加对控制标志。

坑 3：limits.conf 配了 nofile 不生效
结论：limits.conf 写了 nofile 65535，登录后 ulimit -n 还是 1024。
原因：pam_limits.so 没在 common-session 里启用，或没重新登录。
解法：确认 session required pam_limits.so 存在，改完重新登录才生效。

坑 4：sufficient 标志导致后续安全检查被跳过
结论：加了一个 sufficient 的模块，后面本该执行的账户检查被跳过了。
原因：sufficient 成功就跳过栈里后续模块。
解法：谨慎用 sufficient，理解它「过了就短路」的语义。

坑 5：直接编辑 common-* 导致所有服务都受影响
结论：改 common-auth 想限制 SSH，结果 sudo/login 也变了。
原因：common-* 被所有服务 include，是全局配置。
解法：只想影响单个服务就改 /etc/pam.d/<服务>，别动 common-*。
```
