## 概述

PAM（Pluggable Authentication Modules，可插拔认证模块）是 Linux 统一的认证框架——login、ssh、sudo、su 这些服务不再各自实现认证逻辑，而是统一调用 PAM。好处是「改一处认证策略，所有服务生效」。每个服务在 /etc/pam.d/ 下有自己的配置文件，里面是一串 PAM 模块，按顺序执行完成认证。理解 PAM 是配置「登录限制、密码策略、资源限制」的前提。
```text
PAM 核心概念：
1. 服务配置 —— /etc/pam.d/<服务名>，每个服务一个配置文件
2. 四类管理 —— auth 认证 / account 账号 / password 密码 / session 会话
3. 模块栈 —— 配置里一串模块按顺序执行，控制标志决定成败影响
4. 控制标志 —— required 必须过 / requisite 失败立即终止 / sufficient 过了就跳过后续
```
## 核心概念

PAM 的三个核心概念：模块、认证流程、常用模块。下面逐一展开。
### PAM 模块

PAM 模块是编译好的 .so 库，每个负责一种认证能力。Debian/Ubuntu 用 common-auth、common-account、common-password、common-session 四个公共文件，各服务（login/sshd/sudo）include 它们。模块按四类管理分组：auth 验证身份（密码/密钥/指纹）、account 检查账号状态（是否过期/锁定）、password 改密码、session 会话前后处理。
```text
# 实测（本机 /etc/pam.d/ 下的配置）
$ ls /etc/pam.d/
common-auth  common-account  common-password  common-session
login  sshd  sudo  su  cron  passwd  chsh  ...
# Debian/Ubuntu 用 common-* 四个公共文件统一认证，各服务 include 它们
```
### 认证流程

认证流程是「服务 → PAM 配置 → 模块栈依次执行」。以 SSH 登录为例：sshd 调 /etc/pam.d/sshd → include common-auth → common-auth 里的模块依次执行（先 pam_unix 验密码，再可能 pam_deny 拒绝）。模块的控制标志决定流程：required 失败继续但最终失败、requisite 失败立即终止、sufficient 成功就通过（跳过后续）、optional 可选。理解这个栈的执行顺序，才能看懂「为什么登录被拒」。
```text
认证流程（以 SSH 登录为例）：
用户 → sshd → /etc/pam.d/sshd → include common-auth
  → pam_unix.so（验密码）
  → pam_deny.so（兜底拒绝）
四个控制标志：required（必须过，失败不中断）/ requisite（失败立即中断）/ sufficient（过了跳过后续）/ optional（可选）
```
```text
# /etc/pam.d/common-auth 结构（本机，省略注释）
auth    [success=1 default=ignore]  pam_unix.so nullok
auth    requisite                   pam_deny.so
auth    required                    pam_permit.so
# 第一行 pam_unix 验密码，成功跳到 pam_permit 通过，失败继续走 pam_deny 拒绝
```
### 常用模块

三个高频模块：pam_unix（密码认证，最基础）、pam_tally2（登录失败次数限制，防暴力破解）、pam_limits（资源限制，配合 /etc/security/limits.conf）。pam_unix 验证本地密码；pam_tally2 记录失败次数、超阈值锁定；pam_limits 在登录时应用 ulimit 类的资源限制。配置登录安全策略主要就是组合这三个模块。
```text
常用模块：
1. pam_unix —— 本地密码认证，nullok 允许空密码
2. pam_tally2 —— 登录失败计数与锁定，deny=5 失败 5 次锁定
3. pam_limits —— 应用 /etc/security/limits.conf 的资源限制
4. pam_deny / pam_permit —— 无条件拒绝 / 允许（栈的兜底）
```
```shell
# 在 common-auth 加登录失败锁定（防暴力破解）
auth required pam_tally2.so deny=5 unlock_time=300 even_deny_root
# 在 common-session 启用资源限制
session required pam_limits.so
```
## 工作原理

PAM 的核心是一套「服务无关的认证中间层」。工作原理拆成三层：

1. **服务调用**：login/sshd/sudo 等程序调 `pam_start(服务名, 用户名, ...)` 初始化会话，指定用哪个服务配置（/etc/pam.d/服务名）。
2. **模块栈执行**：PAM 库读配置文件，得到一串「模块 + 控制标志」，按顺序逐个调用模块的对应接口（auth/account/password/session）。
3. **结果汇总**：每个模块返回成功/失败/忽略，PAM 根据控制标志决定整体结果，最终把「通过/拒绝」返回给服务。

控制标志的判定逻辑是核心：required 失败会记下来但不中断（继续跑完栈再报失败）；requisite 失败立即返回失败；sufficient 成功立即返回成功（跳过栈里剩余模块）；optional 只在「栈里没有其它决定性模块」时才影响结果。
```text
PAM 栈执行判定：
required   失败→记下，继续跑后面的，最终仍失败（跑完全栈）
requisite  失败→立即返回失败（短路）
sufficient 成功→立即返回成功（短路，跳过剩余）
optional   仅当没有 required/requisite/sufficient 决定时，才以它为结果
include    展开另一个文件（如 include common-auth），子文件也是栈
```
## 常用命令与配置
```shell
# 查看某服务用到的 PAM 配置
cat /etc/pam.d/sshd
# 查看某用户当前会话的 PAM 相关资源
ulimit -a                     # 看 pam_limits 应用后的限制
# 查看登录失败计数（pam_tally2）
pam_tally2 --user alice
pam_tally2 --user alice --reset    # 重置/解锁
# 查看 PAM 模块列表
ls /usr/lib/x86_64-linux-gnu/security/     # Debian/Ubuntu
ls /usr/lib64/security/                     # Red Hat 系
```
```text
四个管理类型的常见配置位置：
auth      common-auth      身份验证（密码/密钥）
account   common-account   账号状态（过期/锁定/时间限制）
password  common-password  密码修改规则（强度/历史）
session   common-session   会话前后处理（资源限制/挂载/日志）
```
## 配置文件解析

以 Debian/Ubuntu 的 /etc/pam.d/common-* 结构为例（各服务 include 它们）：
```ini
# /etc/pam.d/common-auth —— 身份验证栈
auth    [success=1 default=ignore]  pam_unix.so nullok
auth    requisite                   pam_deny.so
auth    required                    pam_permit.so
# /etc/pam.d/common-account —— 账号状态检查
account [success=1 new_authtok_reqd=done default=ignore]  pam_unix.so
account requisite                   pam_deny.so
account required                    pam_permit.so
# /etc/pam.d/common-session —— 会话处理（含资源限制）
session [default=1]                 pam_permit.so
session requisite                   pam_deny.so
session required                    pam_permit.so
session required                    pam_unix.so
session optional                    pam_limits.so   # 应用 limits.conf
```
```text
每行格式：类型  控制标志  模块  参数
控制标志两种写法：
1. 简单标志 —— required / requisite / sufficient / optional
2. 扩展语法 —— [value1=action1 value2=action2 ...]
   value 是模块返回值（success/failure/default 等）
   action 是 N（跳过后面 N 行）/ done（结束）/ ignore（忽略继续）
   如 [success=1 default=ignore]：成功跳过 1 行，其它情况忽略继续
include 结构：sshd 里写 @include common-auth，把公共栈内联展开
```
## 应用场景实战
### 场景一：限制 SSH 登录失败次数防暴力破解
```shell
# 编辑 PAM 配置，失败 5 次锁定 5 分钟
# /etc/pam.d/common-auth 加一行：
auth required pam_tally2.so deny=5 unlock_time=300
# 查看某用户的失败锁定状态
pam_tally2 --user alice
# 手动解锁
pam_tally2 --user alice --reset
```
### 场景二：通过 PAM 限制用户资源（配 limits.conf）
```shell
# 编辑 /etc/security/limits.conf，限制用户进程数和文件数
# alice hard nproc 1024
# alice hard nofile 4096
# 确认 common-session 里有 pam_limits.so（否则不生效）
grep pam_limits /etc/pam.d/common-session
```
## 性能与调优
```text
1. 模块栈别堆太多 —— 每个模块都增加认证延迟，SSH 登录慢先查 common-auth 是否塞了一堆模块
2. pam_tally2 计数读 /var/log/tallylog —— 高频登录场景（API 网关）注意它的 IO 开销
3. sufficient 短路 —— 想让「密钥过了就不用再验密码」就用 sufficient，能省后续模块开销
4. 远程认证（LDAP/RADIUS）超时 —— pam_ldap 等模块设好超时，否则认证挂起拖慢所有登录
5. 缓存认证结果 —— 高频服务别每次都打远程认证，用 nscd/sssd 缓存 account 信息
```
## 安全与权限
```text
1. 改 PAM 前备份 —— common-auth 改错会导致所有登录失败，甚至把自己锁在系统外
2. 只影响单服务 —— 想限制 SSH 就改 /etc/pam.d/sshd，别动 common-*（影响全部服务）
3. pam_tally2 防暴力破解 —— deny=5 失败 5 次锁定，配合 fail2ban 更完整
4. 密码策略 —— common-password 里配 pam_pwquality（长度/复杂度/历史）
5. nullok 慎用 —— pam_unix 的 nullok 允许空密码登录，生产环境应去掉
6. even_deny_root —— 锁定策略连 root 一起防，防攻击者绕过普通用户直接打 root
```
## 故障排查
```shell
# 1. 登录失败看 PAM 日志
journalctl -u sshd -n 50            # 或 tail /var/log/auth.log
grep 'pam' /var/log/auth.log | tail
# 2. 确认模块文件存在（拼错模块名会认证失败）
ls /usr/lib/x86_64-linux-gnu/security/ | grep pam_tally2
# 3. 确认控制标志/语法正确
pam_tally2 --user alice             # 看计数是否在涨（不涨说明没生效）
# 4. 改完没生效 —— 多数要重新登录（新会话才走完整 PAM 栈）
# 已登录会话不会重跑 auth，只有新登录才触发
```
```text
排查顺序：
auth.log 看报错 → 确认模块 .so 存在 → 确认控制标志位置 → 重新登录再验证
```
## 常见问题
```text
Q1: 改了 PAM 后所有 SSH 都进不去怎么办？
A: 如果本机还有 root 会话（或用 su 切 root、单用户模式/救援模式），把改错的配置改回来；否则只能控制台/救援盘挂载修复。
Q2: common-auth 和 /etc/pam.d/sshd 的关系？
A: sshd 里 @include common-auth，把公共认证栈内联展开。改 common-auth 影响所有 include 它的服务，改 sshd 只影响 SSH。
Q3: required 和 requisite 的区别？
A: required 失败不中断（跑完栈仍报失败，能收集全部错误），requisite 失败立即返回。安全性检查常用 required，密码错误这种常用 requisite。
Q4: pam_tally2 和 fail2ban 什么关系？
A: pam_tally2 在 PAM 层按账号计数锁定，fail2ban 在防火墙层按来源 IP 封禁。两者互补：一个防单账号爆破，一个防分布式爆破。
Q5: 为什么改 limits.conf 后 ulimit 没变？
A: limits.conf 由 pam_limits.so 在登录时应用，改完要重新登录（新会话），且确认 common-session 里有 session required pam_limits.so。
```
## 面试题
```text
1. PAM 是什么？解决什么问题？
   答：可插拔认证模块，统一的认证框架。让 login/ssh/sudo 等服务共享一套认证逻辑，改一处策略全局生效，不用每个服务自己写认证。
2. PAM 四类管理类型分别管什么？
   答：auth 验证身份、account 检查账号状态（过期/锁定）、password 改密码规则、session 会话前后处理（资源限制/日志）。
3. 控制标志 required/requisite/sufficient/optional 的区别？
   答：required 失败继续但最终失败，requisite 失败立即终止，sufficient 成功立即通过（短路），optional 只在无决定性模块时影响结果。
4. Debian 的 common-* 结构有什么好处？
   答：把认证栈抽成四个公共文件（auth/account/password/session），各服务 include 复用，改认证策略只改一处，避免每个服务重复配置。
5. 怎么用 PAM 防暴力破解？
   答：common-auth 加 pam_tally2.so deny=5 unlock_time=300，失败 5 次锁定 5 分钟；再配合 fail2ban 按 IP 封禁更完整。
```
## 最佳实践与踩坑记录
### 最佳实践

1. 改 PAM 配置前先备份，改错会导致所有登录失败（SSH 进不去）
2. 改 PAM 后开另一个 SSH 会话测试，别把唯一会话改挂
3. 登录防暴力破解用 pam_tally2，配合 fail2ban 更完整
4. 资源限制走 limits.conf + pam_limits，比在脚本里 ulimit 统一
5. 理解控制标志（required/requisite/sufficient）再改模块栈，否则行为难预料
### 踩坑记录
```text
坑 1：改 PAM 配错把自己锁在系统外
结论：改 common-auth 语法错，SSH/登录全部失败，进不去了。
原因：PAM 认证是所有登录的必经路径，配错全局瘫痪。
解法：改前备份、开新会话测试；锁死用单用户模式或救援模式改回。
坑 2：pam_tally2 配了不生效
结论：加了 pam_tally2 行，登录失败不计数、不锁定。
原因：模块顺序不对，或没加 required 控制标志，或 pam_tally2 位置在 pam_unix 之前。
解法：pam_tally2 放 pam_unix 之前（先计数再验密），并加对控制标志。
坑 3：limits.conf 配了 nofile 不生效
结论：limits.conf 写了 nofile 65535，登录后 ulimit -n 还是 1024。
原因：pam_limits.so 没在 common-session 里启用，或没重新登录。
解法：确认 session required pam_limits.so 存在，改完重新登录才生效。
坑 4：sufficient 标志导致后续安全检查被跳过
结论：加了一个 sufficient 的模块，后面本该执行的账户检查被跳过了。
原因：sufficient 成功就跳过栈里后续模块。
解法：谨慎用 sufficient，理解它「过了就短路」的语义。
坑 5：直接编辑 common-* 导致所有服务都受影响
结论：改 common-auth 想限制 SSH，结果 sudo/login 也变了。
原因：common-* 被所有服务 include，是全局配置。
解法：只想影响单个服务就改 /etc/pam.d/<服务>，别动 common-*。
```
