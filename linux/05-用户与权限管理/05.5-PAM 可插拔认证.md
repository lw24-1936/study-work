## 概述

PAM（Pluggable Authentication Modules，可插拔认证模块）是 Linux 统一的认证框架——login、ssh、sudo、su 这些服务不再各自实现认证逻辑，而是统一调用 PAM。好处是「改一处认证策略，所有服务生效」。每个服务在 /etc/pam.d/ 下有自己的配置文件，里面是一串 PAM 模块，按顺序执行完成认证。理解 PAM 是配置「登录限制、密码策略、资源限制」的前提。
```text
PAM 核心概念：
1. 服务配置 —— /etc/pam.d/<服务名>，每个服务一个配置文件
2. 四类管理 —— auth 认证 / account 账号 / password 密码 / session 会话
3. 模块栈 —— 配置里一串模块按顺序执行，控制标志决定成败影响
4. 控制标志 —— required 必须过 / requisite 失败立即终止 / sufficient 过了就跳过后续
```
## 核心概念

PAM 的三个核心概念：模块、认证流程、常用模块。下面逐一展开。
### PAM 模块

**是什么**：PAM 模块是编译好的 .so 库（位于 /usr/lib/x86_64-linux-gnu/security/ 或 /usr/lib64/security/），每个模块负责一种认证能力——验密码、查账号状态、改密码、会话处理。

**为什么**：认证逻辑（密码怎么验证、账号是否锁定、登录后做什么）被抽成独立模块后，服务不用自己写认证，只需要在配置文件里「引用模块」，于是改认证策略 = 改配置文件，不用改服务代码、不用重启服务。

**怎么用**：Debian/Ubuntu 用 common-auth、common-account、common-password、common-session 四个公共文件，各服务（login/sshd/sudo）include 它们。模块按四类管理分组：auth 验证身份（密码/密钥/指纹）、account 检查账号状态（是否过期/锁定）、password 改密码、session 会话前后处理。

**边界/易错点**：模块必须放到正确的管理类型里（把 password 类模块塞进 auth 栈不生效）；模块 .so 文件拼错或不存在，该服务认证直接失败；改公共 common-* 会影响所有 include 它的服务。
```text
# 实测（本机 /etc/pam.d/ 下的配置）
$ ls /etc/pam.d/
common-auth  common-account  common-password  common-session
login  sshd  sudo  su  cron  passwd  chsh  ...
# Debian/Ubuntu 用 common-* 四个公共文件统一认证，各服务 include 它们
```
```text
四类管理类型各自管什么：
auth      验证身份（密码是否正确、密钥是否匹配）—— 你是谁
account   检查账号状态（是否过期/锁定/有时间窗口限制）—— 你还能不能用
password  处理改密码（强度校验、历史检查、密码更新）—— 你改的密码合不合规
session   会话前后处理（挂载、资源限制、日志、环境变量）—— 登录后做什么
```
### 认证流程

**是什么**：认证流程是「服务 → PAM 配置 → 模块栈依次执行」。一个认证请求按配置文件里的模块顺序走一遍，每个模块返回结果，PAM 库根据控制标志汇总成最终的「通过/拒绝」。

**为什么**：理解模块栈的执行顺序和控制标志，才能看懂「为什么登录被拒」「为什么密码对了还进不去」。排障时所有线索都在这个栈里。

**怎么用**：以 SSH 登录为例：sshd 调 /etc/pam.d/sshd → include common-auth → common-auth 里的模块依次执行（先 pam_unix 验密码，再可能 pam_deny 拒绝）。四个控制标志：required 失败继续但最终失败、requisite 失败立即终止、sufficient 成功就通过（跳过后续）、optional 可选。

**边界/易错点**：required 失败「不立即返回」是为了收集全部错误（安全上避免攻击者逐项试探），但这也意味着你把密码输错、后面的模块还会继续跑；sufficient 一旦成功会短路，用它放行后要确认后续没有必须执行的检查。
```text
认证流程（以 SSH 登录为例）：
用户 → sshd → /etc/pam.d/sshd → include common-auth
  → pam_unix.so（验密码）
  → pam_deny.so（兜底拒绝）
四个控制标志：required（必须过，失败不中断）/ requisite（失败立即中断）/ sufficient（过了跳过后续）/ optional（可选）
```
```text
# /etc/pam.d/common-auth 结构（本机，省略注释）
auth    [success=1 default=ignore]  pam_unix.so nullok
auth    requisite                   pam_deny.so
auth    required                    pam_permit.so
# 第一行 pam_unix 验密码，成功跳到 pam_permit 通过，失败继续走 pam_deny 拒绝
```
### 常用模块

**是什么**：三个高频模块：pam_unix（密码认证，最基础）、pam_tally2（登录失败次数限制，防暴力破解）、pam_limits（资源限制，配合 /etc/security/limits.conf）。

**为什么**：配置登录安全策略主要就是组合这三个模块——pam_unix 决定「能不能登录」，pam_tally2 决定「失败几次锁定」，pam_limits 决定「登录后能用多少资源」。它们是「身份验证 + 安全防护 + 资源约束」三件套。

**怎么用**：pam_unix 验证本地密码（nullok 允许空密码、try_first_pass 复用前面输入的密码、remember 记密码历史）；pam_tally2 记录失败次数、超阈值锁定（deny=5 失败 5 次、unlock_time=300 锁 5 分钟）；pam_limits 在登录时应用 ulimit 类的资源限制。三者分别配在 auth / auth / session 栈里。

**边界/易错点**：pam_tally2 在新系统（RHEL8+）正被 pam_faillock 取代，两者别混用；pam_limits 只在新登录会话生效，改完要重新登录；pam_unix 的 nullok 允许空密码，生产环境要去掉。
```text
常用模块：
1. pam_unix —— 本地密码认证，nullok 允许空密码，remember=N 记密码历史
2. pam_tally2 —— 登录失败计数与锁定，deny=5 失败 5 次锁定，unlock_time=300 锁 5 分钟
3. pam_limits —— 应用 /etc/security/limits.conf 的资源限制
4. pam_deny / pam_permit —— 无条件拒绝 / 允许（栈的兜底）
5. pam_pwquality —— 密码复杂度校验（长度/大小写/数字/特殊字符）
6. pam_nologin —— /etc/nologin 存在时禁止非 root 登录（维护时用）
7. pam_wheel —— 限制 su 只允许 wheel 组成员使用
8. pam_faillock —— 新版登录失败锁定（RHEL8+ 替代 pam_tally2）
```
```shell
# 在 common-auth 加登录失败锁定（防暴力破解）
auth required pam_tally2.so deny=5 unlock_time=300 even_deny_root
# 在 common-session 启用资源限制
session required pam_limits.so
# 在 common-password 加密码复杂度（pam_pwquality，pam_cracklib 的继任者）
password requisite pam_pwquality.so retry=3 minlen=12
# 限制 su 只能 wheel 组使用
auth required pam_wheel.so group=wheel
```
```text
更多常用模块（按四类管理类型归类）：
auth     pam_wheel.so group=wheel   限制 su 只能 wheel 组使用
auth     pam_access.so              按 /etc/security/access.conf 做来源/用户访问控制
account  pam_nologin.so             存在 /etc/nologin 时禁止非 root 登录（维护用）
session  pam_mkhomedir.so           首次登录自动创建家目录（skel=/etc/skel）
session  pam_env.so                 从 /etc/security/pam_env.conf 设置环境变量
session  pam_lastlog.so             显示「上次登录」信息
session  pam_systemd.so             把会话注册到 systemd/logind（现代系统必需）
password pam_pwquality.so           密码复杂度校验（长度/大小写/数字/特殊字符）
```
```shell
# pam_faillock 配置示例（RHEL8+ 替代 pam_tally2，配在 system-auth / password-auth）
auth     required  pam_faillock.so preauth silent deny=5 unlock_time=300
auth     required  pam_faillock.so authfail silent deny=5 unlock_time=300
account  required  pam_faillock.so
# 查看/解锁
faillock --user alice
faillock --user alice --reset
```
## 工作原理

PAM 的核心是一套「服务无关的认证中间层」。工作原理拆成三层：

1. **服务调用**：login/sshd/sudo 等程序调 `pam_start(服务名, 用户名, ...)` 初始化会话，指定用哪个服务配置（/etc/pam.d/服务名）。
2. **模块栈执行**：PAM 库读配置文件，得到一串「模块 + 控制标志」，按顺序逐个调用模块的对应接口（auth/account/password/session）。
3. **结果汇总**：每个模块返回成功/失败/忽略，PAM 根据控制标志决定整体结果，最终把「通过/拒绝」返回给服务。

控制标志的判定逻辑是核心：required 失败会记下来但不中断（继续跑完栈再报失败）；requisite 失败立即返回失败；sufficient 成功立即返回成功（跳过栈里剩余模块）；optional 只在「栈里没有其它决定性模块」时才影响结果。
```text
PAM 栈执行判定：
required   失败→记下，继续跑后面的，最终仍失败（跑完全栈）
requisite  失败→立即返回失败（短路）
sufficient 成功→立即返回成功（短路，跳过剩余）
optional   仅当没有 required/requisite/sufficient 决定时，才以它为结果
include    展开另一个文件（如 include common-auth），子文件也是栈
substack   类似 include，但子栈的「决定」不会直接短路整个父栈
```
```text
一个具体例子（common-auth 三行如何跑）：
密码正确：pam_unix 返回 success → [success=1] 跳过 1 行（pam_deny）→ pam_permit 通过
密码错误：pam_unix 返回 failure → [default=ignore] 继续 → pam_deny 返回拒绝 → 登录失败
```
```text
一次完整登录走四个阶段（login/sshd 都按这个顺序）：
1. auth      —— 验身份：pam_unix 验密码、pam_tally2 记失败
2. account   —— 验状态：pam_unix 查账号过期/锁定、pam_nologin 查维护标志
3. password  —— 仅改密码时走：pam_pwquality 校验强度、pam_unix 更新哈希
4. session   —— 会话建立/销毁：pam_limits 设资源限制、pam_systemd 注册、pam_lastlog 记登录
前三个阶段任一失败，会话不会建立；session 阶段决定「登录后做了什么」
```
## 常用命令与配置
```shell
# 查看某服务用到的 PAM 配置
cat /etc/pam.d/sshd
# 查看某用户当前会话的 PAM 相关资源
ulimit -a                     # 看 pam_limits 应用后的限制
# 查看登录失败计数（pam_tally2）
pam_tally2 --user alice
pam_tally2 --user alice --reset    # 重置/解锁
pam_tally2 --user alice -r          # 简写：重置计数
# 查看登录失败计数（新版 pam_faillock，RHEL8+）
faillock --user alice
faillock --user alice --reset
# 查看 PAM 模块列表
ls /usr/lib/x86_64-linux-gnu/security/     # Debian/Ubuntu
ls /usr/lib64/security/                     # Red Hat 系
# 临时禁止非 root 登录（维护窗口用）
touch /etc/nologin && echo "维护中，请稍后登录" > /etc/nologin
# 查看 /etc/nologin 是否生效（pam_nologin 模块）
ls -l /etc/nologin
```
```text
四个管理类型的常见配置位置：
auth      common-auth      身份验证（密码/密钥）
account   common-account   账号状态（过期/锁定/时间限制）
password  common-password  密码修改规则（强度/历史）
session   common-session   会话前后处理（资源限制/挂载/日志）
```
```text
required vs requisite 实例对比：
场景：密码错误时，你希望「先记失败次数、再拒绝」
  用 required  → pam_unix 失败后继续跑 pam_tally2 记数，最后统一报失败
  用 requisite → pam_unix 失败立即返回，后面的 pam_tally2 根本没机会记数
结论：想「记录但继续」用 required，想「失败立即止损」用 requisite
```
```text
改密码的 password 栈怎么跑（new_authtok_reqd 的由来）：
1. 用户执行 passwd，走 password 栈
2. pam_pwquality 先校验新密码强度（不合规直接拒绝，旧密码不被改动）
3. pam_unix 验证旧密码、写新哈希；new_authtok_reqd 表示「需要新密码」的返回态
4. 扩展语法 [success=1 new_authtok_reqd=done] 就是在「新密码已设置」时跳过后续模块
```
## 配置文件解析

以 Debian/Ubuntu 的 /etc/pam.d/common-* 结构为例（各服务 include 它们）：
```ini
# /etc/pam.d/common-auth —— 身份验证栈
auth    [success=1 default=ignore]  pam_unix.so nullok
auth    requisite                   pam_deny.so
auth    required                    pam_permit.so
# /etc/pam.d/common-account —— 账号状态检查
account [success=1 new_authtok_reqd=done default=ignore]  pam_unix.so
account requisite                   pam_deny.so
account required                    pam_permit.so
# /etc/pam.d/common-password —— 改密码（含强度与历史）
password [success=1 default=ignore] pam_unix.so obscure sha512
password requisite                  pam_deny.so
password required                   pam_permit.so
# /etc/pam.d/common-session —— 会话处理（含资源限制）
session [default=1]                 pam_permit.so
session requisite                   pam_deny.so
session required                    pam_permit.so
session required                    pam_unix.so
session optional                    pam_limits.so   # 应用 limits.conf
```
```text
每行格式：类型  控制标志  模块  参数
控制标志两种写法：
1. 简单标志 —— required / requisite / sufficient / optional
2. 扩展语法 —— [value1=action1 value2=action2 ...]
   value 是模块返回值（success/failure/default/new_authtok_reqd 等）
   action 是 N（跳过后面 N 行）/ done（结束）/ ignore（忽略继续）
   如 [success=1 default=ignore]：成功跳过 1 行，其它情况忽略继续
include 结构：sshd 里写 @include common-auth，把公共栈内联展开
```
```text
pam_unix 常用参数：
nullok          允许空密码登录（生产环境应去掉）
try_first_pass  复用前面模块已输入的密码，不再重复询问
remember=N      记住最近 N 个密码，禁止重复使用（密码历史）
sha512          密码哈希算法（默认，比 md5/crypt 强）
pam_tally2 常用参数：
deny=N          失败 N 次后锁定
unlock_time=秒  锁定时长（0 表示永久锁定直到手动 reset）
even_deny_root  连 root 也计数锁定（防攻击者直接打 root）
pam_limits 作用：读 /etc/security/limits.conf + limits.d/*，登录时应用资源限制
```
```ini
# /etc/pam.d/sshd —— 服务自己的配置（通过 @include 复用公共栈）
@include common-auth             # 身份验证（内联展开 common-auth 全部模块）
account required pam_nologin.so  # 有 /etc/nologin 则拒绝非 root（维护窗口）
@include common-account          # 账号状态检查（过期/锁定）
@include common-session          # 会话处理（含 pam_limits 资源限制）
@include common-password         # 改密码规则（sshd 改密码时用到）
# 服务特定的模块直接写在这里，不影响其它服务（这是「单服务定制」的正确位置）
```
```text
@include 的定位：
- 改 common-* 影响所有 include 它的服务（全局策略）
- 改 /etc/pam.d/<服务> 只影响该服务（局部策略）
- 单服务限制（如只对 SSH 限制来源 IP）就写在服务文件里，别动 common-*
```
## 应用场景实战
### 场景一：限制 SSH 登录失败次数防暴力破解
```shell
# 编辑 PAM 配置，失败 5 次锁定 5 分钟
# /etc/pam.d/common-auth 加一行（放 pam_unix 之前，先计数再验密）：
auth required pam_tally2.so deny=5 unlock_time=300 even_deny_root
# 查看某用户的失败锁定状态
pam_tally2 --user alice
# 手动解锁
pam_tally2 --user alice --reset
# 模拟失败登录后确认计数在涨
pam_tally2 --user alice
```
### 场景二：通过 PAM 限制用户资源（配 limits.conf）
```shell
# 编辑 /etc/security/limits.conf，限制用户进程数和文件数
# alice hard nproc 1024
# alice hard nofile 4096
# 确认 common-session 里有 pam_limits.so（否则不生效）
grep pam_limits /etc/pam.d/common-session
# 重新登录后验证
su - alice -c 'ulimit -n'
```
### 场景三：配置密码复杂度与历史（common-password）
```shell
# 场景：企业要求密码至少 12 位、含大小写+数字+特殊字符、且不能重复用最近 5 个
# 1. 加密码复杂度校验（pam_pwquality 是 pam_cracklib 的继任者）
cat >> /etc/pam.d/common-password <<'EOF'
password requisite pam_pwquality.so retry=3 minlen=12 dcredit=-1 ucredit=-1 lcredit=-1 ocredit=-1
EOF
# 2. 让 pam_unix 记录密码历史，禁止重复使用最近 5 个密码
#    在 common-password 的 pam_unix 行加 remember=5（在 sha512 后面）
sed -i 's/obscure sha512/obscure sha512 remember=5/' /etc/pam.d/common-password
# 3. 验证配置
grep -E 'pwquality|remember' /etc/pam.d/common-password
# 4. 用普通用户测试改密码（会触发复杂度校验）
su - alice -c 'passwd'
```
```text
pam_pwquality 参数含义：
retry=3      密码不合规时允许重试 3 次
minlen=12    最短 12 位
dcredit=-1   至少 1 个数字（负数 = 至少，正数 = 最多）
ucredit=-1   至少 1 个大写字母
lcredit=-1   至少 1 个小写字母
ocredit=-1   至少 1 个特殊字符
```
## 性能与调优
```text
1. 模块栈别堆太多 —— 每个模块都增加认证延迟，SSH 登录慢先查 common-auth 是否塞了一堆模块
2. pam_tally2 计数读 /var/log/tallylog —— 高频登录场景（API 网关）注意它的 IO 开销
3. sufficient 短路 —— 想让「密钥过了就不用再验密码」就用 sufficient，能省后续模块开销
4. 远程认证（LDAP/RADIUS）超时 —— pam_ldap 等模块设好超时，否则认证挂起拖慢所有登录
5. 缓存认证结果 —— 高频服务别每次都打远程认证，用 nscd/sssd 缓存 account 信息
6. 密码哈希强度 vs 登录速度 —— sha512 每次验密都要算哈希，登录极高频时成本可感知，权衡强度与延迟
```
## 安全与权限
```text
1. 改 PAM 前备份 —— common-auth 改错会导致所有登录失败，甚至把自己锁在系统外
2. 只影响单服务 —— 想限制 SSH 就改 /etc/pam.d/sshd，别动 common-*（影响全部服务）
3. pam_tally2 防暴力破解 —— deny=5 失败 5 次锁定，配合 fail2ban 更完整
4. 密码策略 —— common-password 里配 pam_pwquality（长度/复杂度/历史）
5. nullok 慎用 —— pam_unix 的 nullok 允许空密码登录，生产环境应去掉
6. even_deny_root —— 锁定策略连 root 一起防，防攻击者绕过普通用户直接打 root
7. pam_permit 别当 required —— 在 auth 栈里放 required pam_permit 等于「无条件通过」，等于免密
8. 远程认证要设超时 —— pam_ldap/pam_sss 等模块配超时参数，否则认证挂起拖慢所有登录
9. 审计 PAM 变更 —— 改 /etc/pam.d/ 纳入配置管理（git 版本化），改错能快速回滚
```
## 故障排查
```shell
# 1. 登录失败看 PAM 日志
journalctl -u sshd -n 50            # 或 tail /var/log/auth.log
grep 'pam' /var/log/auth.log | tail
# 2. 确认模块文件存在（拼错模块名会认证失败）
ls /usr/lib/x86_64-linux-gnu/security/ | grep pam_tally2
# 3. 确认控制标志/语法正确
pam_tally2 --user alice             # 看计数是否在涨（不涨说明没生效）
# 4. 改完没生效 —— 多数要重新登录（新会话才走完整 PAM 栈）
# 已登录会话不会重跑 auth，只有新登录才触发
# 5. 密码策略不生效
grep pwquality /etc/pam.d/common-password    # 确认模块在 password 栈、控制标志正确
# 6. 账号被锁定（tally2 计数满）
pam_tally2 --user alice                       # 看计数，--reset 解锁
```
```text
排查顺序：
auth.log 看报错 → 确认模块 .so 存在 → 确认控制标志位置 → 重新登录再验证
```
```text
PAM 调试技巧：
1. 模块加 debug 参数 —— auth required pam_unix.so debug，日志会输出详细判定过程
2. 看 auth.log —— grep pam_unix /var/log/auth.log 看具体哪个模块拒绝、返回码是什么
3. pam_debug.so —— 专门打印调用参数的调试模块，临时插进栈观察调用
4. 简化控制标志排查 —— 把 [success=1 default=ignore] 暂时改成简单标志隔离问题
5. 分阶段验证 —— 先只留 auth 栈能登录，再逐步加 account/session，定位是哪一阶段拒绝
```
```text
登录限制常用 PAM 组合速查：
限制 su 只能 wheel 组     /etc/pam.d/su 加 auth required pam_wheel.so group=wheel
限制 SSH 来源 IP          /etc/pam.d/sshd 加 account required pam_access.so（配 access.conf）
维护窗口禁登录           touch /etc/nologin（配合 account required pam_nologin.so）
首次登录建家目录         session required pam_mkhomedir.so skel=/etc/skel
按账号记失败锁定         auth required pam_tally2.so deny=5 unlock_time=300
按 IP 封禁（分布式爆破）  fail2ban 读 auth.log 动态封 IP（PAM 之外，互补）
```
## 常见问题
```text
Q1: 改了 PAM 后所有 SSH 都进不去怎么办？
A: 如果本机还有 root 会话（或用 su 切 root、单用户模式/救援模式），把改错的配置改回来；否则只能控制台/救援盘挂载修复。
Q2: common-auth 和 /etc/pam.d/sshd 的关系？
A: sshd 里 @include common-auth，把公共认证栈内联展开。改 common-auth 影响所有 include 它的服务，改 sshd 只影响 SSH。
Q3: required 和 requisite 的区别？
A: required 失败不中断（跑完栈仍报失败，能收集全部错误），requisite 失败立即返回。安全性检查常用 required，密码错误这种常用 requisite。
Q4: pam_tally2 和 fail2ban 什么关系？
A: pam_tally2 在 PAM 层按账号计数锁定，fail2ban 在防火墙层按来源 IP 封禁。两者互补：一个防单账号爆破，一个防分布式爆破。
Q5: 为什么改 limits.conf 后 ulimit 没变？
A: limits.conf 由 pam_limits.so 在登录时应用，改完要重新登录（新会话），且确认 common-session 里有 session required pam_limits.so。
Q6: pam_tally2 和 pam_faillock 有什么区别？
A: pam_faillock 是 pam_tally2 的新版替代（RHEL8+ 默认），功能类似但配置更细（preauth/authfail 分离、目录计数）。新系统用 faillock，别和 tally2 混用。
Q7: pam_unix 的 remember 参数做什么？
A: 记录最近 N 个密码的哈希，改密码时禁止重复使用（密码历史）。需配合 pam_pwquality 的复杂度校验一起用，才形成完整密码策略。
Q8: 怎么临时禁止所有非 root 登录（比如系统维护）？
A: 创建 /etc/nologin 文件并写入提示信息，配合 pam_nologin 模块（common-auth 里 account required pam_nologin.so），维护期间非 root 用户会被拒绝登录。
```
## 面试题
```text
1. PAM 是什么？解决什么问题？
   答：可插拔认证模块，统一的认证框架。让 login/ssh/sudo 等服务共享一套认证逻辑，改一处策略全局生效，不用每个服务自己写认证。
2. PAM 四类管理类型分别管什么？
   答：auth 验证身份、account 检查账号状态（过期/锁定）、password 改密码规则、session 会话前后处理（资源限制/日志）。
3. 控制标志 required/requisite/sufficient/optional 的区别？
   答：required 失败继续但最终失败，requisite 失败立即终止，sufficient 成功立即通过（短路），optional 只在无决定性模块时影响结果。
4. Debian 的 common-* 结构有什么好处？
   答：把认证栈抽成四个公共文件（auth/account/password/session），各服务 include 复用，改认证策略只改一处，避免每个服务重复配置。
5. 怎么用 PAM 防暴力破解？
   答：common-auth 加 pam_tally2.so deny=5 unlock_time=300，失败 5 次锁定 5 分钟；再配合 fail2ban 按 IP 封禁更完整。
6. include 和 substack 的区别？
   答：include 把子文件内联展开，子栈里的 sufficient/requisite 决定会直接短路整个父栈；substack 展开后子栈的「通过/拒绝」只作为父栈一个模块的结果，不直接短路父栈。
7. 怎么用 PAM 限制 su 命令只有 wheel 组能用？
   答：/etc/pam.d/su 加 auth required pam_wheel.so group=wheel（或 use_uid），只有 wheel 组成员能 su，普通用户即使知道 root 密码也切不过去。
8. 密码策略用 PAM 怎么实现？
   答：common-password 里 password requisite pam_pwquality.so（minlen/dcredit/ucredit 等复杂度）+ pam_unix 的 remember=N（密码历史），两者组合实现「强密码 + 不重复」。
```
## 最佳实践与踩坑记录
### 最佳实践

1. 改 PAM 配置前先备份，改错会导致所有登录失败（SSH 进不去）
2. 改 PAM 后开另一个 SSH 会话测试，别把唯一会话改挂
3. 登录防暴力破解用 pam_tally2，配合 fail2ban 更完整
4. 资源限制走 limits.conf + pam_limits，比在脚本里 ulimit 统一
5. 理解控制标志（required/requisite/sufficient）再改模块栈，否则行为难预料
6. 密码策略用 pam_pwquality + pam_unix remember 组合，复杂度与历史一起管
7. 维护窗口临时禁登录用 /etc/nologin + pam_nologin，比改配置更安全可逆
### 踩坑记录
```text
坑 1：改 PAM 配错把自己锁在系统外
结论：改 common-auth 语法错，SSH/登录全部失败，进不去了。
原因：PAM 认证是所有登录的必经路径，配错全局瘫痪。
解法：改前备份、开新会话测试；锁死用单用户模式或救援模式改回。
坑 2：pam_tally2 配了不生效
结论：加了 pam_tally2 行，登录失败不计数、不锁定。
原因：模块顺序不对，或没加 required 控制标志，或 pam_tally2 位置在 pam_unix 之前。
解法：pam_tally2 放 pam_unix 之前（先计数再验密），并加对控制标志。
坑 3：limits.conf 配了 nofile 不生效
结论：limits.conf 写了 nofile 65535，登录后 ulimit -n 还是 1024。
原因：pam_limits.so 没在 common-session 里启用，或没重新登录。
解法：确认 session required pam_limits.so 存在，改完重新登录才生效。
坑 4：sufficient 标志导致后续安全检查被跳过
结论：加了一个 sufficient 的模块，后面本该执行的账户检查被跳过了。
原因：sufficient 成功就跳过栈里后续模块。
解法：谨慎用 sufficient，理解它「过了就短路」的语义。
坑 5：直接编辑 common-* 导致所有服务都受影响
结论：改 common-auth 想限制 SSH，结果 sudo/login 也变了。
原因：common-* 被所有服务 include，是全局配置。
解法：只想影响单个服务就改 /etc/pam.d/<服务>，别动 common-*。
坑 6：防暴力破解忘了 even_deny_root，root 成了突破口
结论：配了 pam_tally2 锁定，但攻击者直接打 root 账号不受限。
原因：pam_tally2 默认不计数 root，攻击者绕过普通账号锁定直接爆破 root。
解法：加 even_deny_root 参数（连 root 一起计数锁定），或干脆禁 root 登录。
坑 7：pam_pwquality 放错栈或忘配，密码策略形同虚设
结论：以为配了复杂度校验，结果随便设个 123456 也能过。
原因：pwquality 模块放错管理类型（应放 password 栈），或控制标志用错（required 被当成 optional）。
解法：确认 password requisite pam_pwquality.so 在 common-password 里，改完用普通用户实际改一次密码验证。
```
