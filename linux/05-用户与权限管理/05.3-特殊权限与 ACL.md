## 概述

基本权限只有「属主/属组/其他人」三类，满足不了「临时提权」「组内共享」「保护他人文件」这些场景，于是有了特殊权限（SUID/SGID/Sticky Bit）和 ACL。特殊权限是三个额外标志位，ACL 是给任意用户/组单独设权限的扩展。它们补上了基本权限模型的三个缺口。

```text
特殊权限 vs ACL：
1. SUID（4xxx）—— 文件以「属主」身份执行，如 passwd 让普通用户改自己密码
2. SGID（2xxx）—— 文件以属组执行；目录里新建文件自动继承目录属组
3. Sticky Bit（1xxx）—— 目录里只有文件属主能删自己的文件（/tmp）
4. ACL —— setfacl/getfacl，给任意用户/组单独授权，突破三类主体的限制
```

## SUID 与 SGID

SUID 让程序以「文件属主」的身份运行，而不是执行者的身份。典型例子 /usr/bin/passwd——普通用户改密码要写 /etc/shadow（只有 root 能写），passwd 程序带了 SUID，执行时以 root 身份运行，普通用户才能改密码。SGID 对目录更常用：目录设 SGID 后，目录里新建的文件自动继承目录的属组，适合团队共享目录。

```text
# 实测（SUID 程序的标志：属主执行位是 s）
$ ls -l /usr/bin/passwd /usr/bin/sudo
-rwsr-xr-x 1 root root  64152  5月 30  2024 /usr/bin/passwd
-rwsr-xr-x 1 root root 277936  3月  2 20:56 /usr/bin/sudo
# 注意权限位是 rws（不是 rwx），s 表示 SUID——这两个程序都以 root 身份运行
```

```shell
# 设置/清除 SUID 和 SGID
chmod u+s /path/to/program    # 设 SUID（数字法 4755）
chmod u-s /path/to/program    # 清 SUID
chmod g+s /opt/shared         # 目录设 SGID（数字法 2775）
```

## Sticky Bit

Sticky Bit 只对目录有意义：设了 sticky bit 的目录里，只有文件属主（或 root、目录属主）能删除/重命名文件，其他人即使有目录写权限也删不了别人的文件。/tmp 就是典型——所有人都能在 /tmp 建文件，但只能删自己的。这防止了「我能写这个目录，就能删掉别人文件」的问题。

```text
# 实测（/tmp 的 sticky bit：其他人执行位是 t）
$ ls -ld /tmp
drwxrwxrwt 129 root root 12288  8月 18 22:28 /tmp
# 最后是 t（不是 x），表示 sticky bit 已设置——所有人可写，但只能删自己的文件
```

```shell
chmod +t /shared_dir       # 设 sticky bit（数字法 1777）
chmod 1777 /shared_dir     # 等价写法
```

## ACL 与 setfacl 与 getfacl

ACL（Access Control List）给「任意指定用户或组」单独设权限，突破了基本权限「只有属主/属组/其他人」的限制。setfacl 设置、getfacl 查看。典型场景：一个文件属主是 A，但想让用户 B 也能读、组 C 能写——基本权限做不到，ACL 一行搞定。设置 ACL 后 ls -l 的权限位末尾会多一个 `+` 号。

```shell
setfacl -m u:alice:rw  report.txt    # 给 alice 单独读写权限
setfacl -m g:dev:r     report.txt    # 给 dev 组读权限
getfacl report.txt                   # 查看 ACL
setfacl -x u:alice     report.txt    # 删除 alice 的 ACL
```

```text
# getfacl 输出结构（示例）
# file: report.txt
# owner: root
# group: root
user::rw-          # 属主权限（基本）
user:alice:rw-     # alice 的额外 ACL
group::r--         # 属组权限
mask::rw-          # 掩码
other::r--         # 其他人
```

## ACL 掩码与默认 ACL

ACL 有两个进阶概念：掩码（mask）和默认 ACL。mask 是「命名用户/组的权限上限」——ACL 里给 alice 设的权限，实际生效时不能超过 mask（所以改了 mask 会连锁影响所有命名用户/组的 ACL）。默认 ACL 是给目录设的「继承模板」，目录里新建的文件自动套用默认 ACL——共享目录配默认 ACL 后，新文件自动带正确的组权限。

```shell
# 给目录设默认 ACL，新建文件自动继承
setfacl -d -m g:dev:rwx /opt/shared
# 查看 mask 并调整
getfacl /opt/shared
setfacl -m m::r-x /opt/shared    # 改 mask，限制命名用户/组上限
```

## 应用场景实战

### 场景一：团队共享目录——SGID + 默认 ACL 组合

```shell
# 1. 建共享目录，设 SGID（新文件继承属组）
mkdir /opt/team
chgrp dev /opt/team
chmod 2770 /opt/team

# 2. 设默认 ACL，新文件自动带组读写
setfacl -d -m g:dev:rwx /opt/team
setfacl -m g:dev:rwx /opt/team

# 3. 验证新文件权限
touch /opt/team/newfile
getfacl /opt/team/newfile
```

### 场景二：给特定用户开放某个日志文件的读权限

```shell
# 日志默认只 root 能看，单独给 alice 读权限（不改属主属组）
setfacl -m u:alice:r /var/log/app/app.log
getfacl /var/log/app/app.log
# 验证：alice 现在能 tail 这个日志，但其他普通用户不行
```

## 最佳实践与踩坑记录

### 最佳实践

1. SUID 谨慎使用——SUID 程序以属主（常是 root）运行，有漏洞就是提权漏洞
2. 团队共享目录用 SGID + 默认 ACL，比改 umask 更精确
3. 临时目录设 sticky bit，防止用户互删文件
4. 用 ACL 做「给特定人额外权限」，别为此复制文件或改属主
5. 定期审计 SUID 程序：find / -perm -4000，排查异常 SUID 二进制

### 踩坑记录

```text
坑 1：给自己写的脚本设 SUID 不生效
结论：脚本设了 SUID，但执行时还是普通权限。
原因：Linux 忽略脚本的 SUID（安全考虑），SUID 只对二进制程序有效。
解法：脚本提权用 sudo，别指望 SUID；或编译成二进制。

坑 2：改了 ACL 的 mask 导致之前的授权失效
结论：setfacl 改 mask 后，之前给 alice 的 rw 变成了 r。
原因：mask 是所有命名用户/组的权限上限，改 mask 会连锁收紧。
解法：改 mask 前先 getfacl 看清影响，mask 一般设成所有命名 ACL 的最大值。

坑 3：ACL 设了但 ls -l 没看到 + 号，以为没生效
结论：getfacl 有 ACL，ls -l 却没显示 +。
原因：+ 只在「存在命名用户/组的扩展 ACL」时显示，纯基本权限不显示。
解法：用 getfacl 确认 ACL 是否生效，别只看 ls -l。

坑 4：find -perm -4000 误报大量 SUID
结论：一堆系统程序都带 SUID，以为被入侵。
原因：passwd/sudo/mount 等系统程序本来就带 SUID，是正常的。
解法：对比已知清单，只排查「不该有 SUID 的异常程序」和「属主异常的」。

坑 5：sticky bit 目录里文件删不掉，误以为权限问题
结论：在 /tmp 里删别人的文件报 Operation not permitted。
原因：sticky bit 目录里只有文件属主能删，这是正常保护。
解法：删别人的文件要先确认属主，或 sudo 提权删除。
```
