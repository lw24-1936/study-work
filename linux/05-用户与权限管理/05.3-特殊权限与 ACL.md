## 概述

基本权限只有「属主/属组/其他人」三类，满足不了「临时提权」「组内共享」「保护他人文件」这些场景，于是有了特殊权限（SUID/SGID/Sticky Bit）和 ACL。特殊权限是三个额外标志位，ACL 是给任意用户/组单独设权限的扩展。它们补上了基本权限模型的三个缺口。

```text
特殊权限 vs ACL：
1. SUID（4xxx）—— 文件以「属主」身份执行，如 passwd 让普通用户改自己密码
2. SGID（2xxx）—— 文件以属组执行；目录里新建文件自动继承目录属组
3. Sticky Bit（1xxx）—— 目录里只有文件属主能删自己的文件（/tmp）
4. ACL —— setfacl/getfacl，给任意用户/组单独授权，突破三类主体的限制
```

## 核心概念

特殊权限与 ACL 围绕 SUID/SGID、Sticky Bit、ACL、掩码与默认 ACL 展开，下面逐一说明。

### SUID 与 SGID

SUID 让程序以「文件属主」的身份运行，而不是执行者的身份。典型例子 /usr/bin/passwd——普通用户改密码要写 /etc/shadow（只有 root 能写），passwd 程序带了 SUID，执行时以 root 身份运行，普通用户才能改密码。SGID 对目录更常用：目录设 SGID 后，目录里新建的文件自动继承目录的属组，适合团队共享目录。

```text
# 实测（SUID 程序的标志：属主执行位是 s）
$ ls -l /usr/bin/passwd /usr/bin/sudo
-rwsr-xr-x 1 root root  64152  5月 30  2024 /usr/bin/passwd
-rwsr-xr-x 1 root root 277936  3月  2 20:56 /usr/bin/sudo
# 注意权限位是 rws（不是 rwx），s 表示 SUID——这两个程序都以 root 身份运行
```

```shell
# 设置/清除 SUID 和 SGID
chmod u+s /path/to/program    # 设 SUID（数字法 4755）
chmod u-s /path/to/program    # 清 SUID
chmod g+s /opt/shared         # 目录设 SGID（数字法 2775）
```

### Sticky Bit

Sticky Bit 只对目录有意义：设了 sticky bit 的目录里，只有文件属主（或 root、目录属主）能删除/重命名文件，其他人即使有目录写权限也删不了别人的文件。/tmp 就是典型——所有人都能在 /tmp 建文件，但只能删自己的。这防止了「我能写这个目录，就能删掉别人文件」的问题。

```text
# 实测（/tmp 的 sticky bit：其他人执行位是 t）
$ ls -ld /tmp
drwxrwxrwt 129 root root 12288  8月 18 22:28 /tmp
# 最后是 t（不是 x），表示 sticky bit 已设置——所有人可写，但只能删自己的文件
```

```shell
chmod +t /shared_dir       # 设 sticky bit（数字法 1777）
chmod 1777 /shared_dir     # 等价写法
```

### ACL 与 setfacl 与 getfacl

ACL（Access Control List）给「任意指定用户或组」单独设权限，突破了基本权限「只有属主/属组/其他人」的限制。setfacl 设置、getfacl 查看。典型场景：一个文件属主是 A，但想让用户 B 也能读、组 C 能写——基本权限做不到，ACL 一行搞定。设置 ACL 后 ls -l 的权限位末尾会多一个 `+` 号。

```shell
setfacl -m u:alice:rw  report.txt    # 给 alice 单独读写权限
setfacl -m g:dev:r     report.txt    # 给 dev 组读权限
getfacl report.txt                   # 查看 ACL
setfacl -x u:alice     report.txt    # 删除 alice 的 ACL
```

```text
# getfacl 输出结构（示例）
# file: report.txt
# owner: root
# group: root
user::rw-          # 属主权限（基本）
user:alice:rw-     # alice 的额外 ACL
group::r--         # 属组权限
mask::rw-          # 掩码
other::r--         # 其他人
```

### ACL 掩码与默认 ACL

ACL 有两个进阶概念：掩码（mask）和默认 ACL。mask 是「命名用户/组的权限上限」——ACL 里给 alice 设的权限，实际生效时不能超过 mask（所以改了 mask 会连锁影响所有命名用户/组的 ACL）。默认 ACL 是给目录设的「继承模板」，目录里新建的文件自动套用默认 ACL——共享目录配默认 ACL 后，新文件自动带正确的组权限。

```shell
# 给目录设默认 ACL，新建文件自动继承
setfacl -d -m g:dev:rwx /opt/shared
# 查看 mask 并调整
getfacl /opt/shared
setfacl -m m::r-x /opt/shared    # 改 mask，限制命名用户/组上限
```

## 工作原理

特殊权限和 ACL 都存储在文件 inode 的权限字段里：

1. **特殊权限位**：三个标志位存在 mode 的高三位——SUID=4000、SGID=2000、sticky=1000。SUID/SGID 只在「执行文件」时生效（内核把 euid/egid 改成文件属主/属组）；sticky bit 只在「目录」上生效（删除/重命名时校验文件属主）。ls -l 里 s/t 显示在对应执行位的位置：属主位 s=SUID、属组位 s=SGID、其他人位 t=sticky。
2. **ACL 存储**：ACL 存在文件扩展属性（xattr）里——访问 ACL 用 system.posix_acl_access、默认 ACL 用 system.posix_acl_default。文件没有扩展 ACL 时只有基本权限，有扩展 ACL 时 ls -l 权限位末尾显示 `+`。

```text
特殊权限位（mode 高三位）：
SUID 4000 → 执行时 euid = 文件属主
SGID 2000 → 执行时 egid = 文件属组；目录：新建文件继承属组
sticky 1000 → 目录：仅文件属主/root 可删

ACL 存储：xattr（system.posix_acl_access / system.posix_acl_default）
有扩展 ACL → ls -l 末尾出现 +
```

## 常用命令与配置

```shell
# 特殊权限
chmod u+s prog          # SUID（4755）
chmod g+s dir           # SGID（2775）
chmod +t dir            # sticky bit（1777）
chmod 4755 prog         # 数字法组合

# ACL
setfacl -m u:alice:rw file        # 给用户加 ACL
setfacl -m g:dev:rx  file         # 给组加 ACL
setfacl -m o::r       file        # 改 others
setfacl -m m::rw      file        # 改 mask
setfacl -x u:alice    file        # 删单条 ACL
setfacl -b            file        # 删全部 ACL（回基本权限）
setfacl -d -m g:dev:rwx dir       # 设默认 ACL（目录）
setfacl -R -m u:alice:rx dir      # 递归设
getfacl file                       # 查看 ACL
```

```text
setfacl 参数速记：
-m  修改/新增（modify）
-x  删除指定条目
-b  删除全部 ACL
-d  设默认 ACL（仅目录，作继承模板）
-R  递归
条目格式：u:用户名:权限 / g:组名:权限 / o:权限 / m:权限
```

## 配置文件解析

特殊权限与 ACL 的「配置」本质是 inode 权限位和扩展属性，没有独立配置文件，下面是它们的存储和表示方式：

```text
特殊权限位在 ls -l 的表示：
-rwsr-xr-x  属主执行位 s（SUID，4）
-rwxr-sr-x  属组执行位 s（SGID，2）
drwxrwxrwt  其他人执行位 t（sticky，1）

大小写含义：
s/t 小写 = 该位有执行权限 + 特殊位
S/T 大写 = 该位无执行权限，只有特殊位（少见）

ACL 存储（xattr，查看方式）：
getfattr -n system.posix_acl_access 文件   # 访问 ACL 原始存储
setfacl/getfacl                           # 高层封装，日常用这个
```

```shell
# 查看文件的扩展属性（ACL 底层存储）
getfattr -d -m - 文件
```

## 应用场景实战

### 场景一：团队共享目录——SGID + 默认 ACL 组合

```shell
# 1. 建共享目录，设 SGID（新文件继承属组）
mkdir /opt/team
chgrp dev /opt/team
chmod 2770 /opt/team

# 2. 设默认 ACL，新文件自动带组读写
setfacl -d -m g:dev:rwx /opt/team
setfacl -m g:dev:rwx /opt/team

# 3. 验证新文件权限
touch /opt/team/newfile
getfacl /opt/team/newfile
```

### 场景二：给特定用户开放某个日志文件的读权限

```shell
# 日志默认只 root 能看，单独给 alice 读权限（不改属主属组）
setfacl -m u:alice:r /var/log/app/app.log
getfacl /var/log/app/app.log
# 验证：alice 现在能 tail 这个日志，但其他普通用户不行
```

## 性能与调优

特殊权限和 ACL 的开销极小，调优重点在「大量 ACL」场景：

```text
1. ACL 存 xattr，每个文件多一次 xattr 读取，大量小文件场景略增开销，但可忽略
2. 递归 setfacl -R 大目录会遍历所有文件，用默认 ACL（-d）比事后递归补更省
3. SUID 程序本身无性能问题，但别滥用——每个 SUID 程序都是潜在攻击面
4. sticky bit 目录（/tmp）写入频繁时注意 inode 占用，定期清理
5. 单个文件 ACL 条目别堆几十条，会影响 getfacl/权限检查，保持精简
```

## 安全与权限

```text
1. SUID 是提权高风险点：SUID 程序以属主（常是 root）运行，有漏洞就是提权漏洞，非必要不设
2. 定期审计 SUID/SGID：find / -perm -4000 -o -perm -2000，对比已知清单排查异常
3. 脚本的 SUID 会被内核忽略（安全考虑），脚本提权用 sudo，别指望 SUID
4. ACL 的 mask 是安全阀：mask 收紧了命名用户/组的实际权限上限
5. sticky bit 防止互删：共享可写目录（/tmp、上传目录）应设 sticky bit
6. ACL 别给「比基本权限更宽」的 others——ACL 是补充不是替代，最小权限原则仍适用
```

## 故障排查

```shell
# 1. SUID 没生效：确认是二进制（脚本 SUID 被忽略）
file 程序
ls -l 程序            # 看属主执行位是不是 s

# 2. ACL 设了但 ls -l 没 + 号
getfacl 文件          # 用 getfacl 确认，别只信 ls -l

# 3. 改了 ACL 后权限反而变严：mask 被改小了
getfacl 文件 | grep mask

# 4. 默认 ACL 不继承：确认文件系统支持 ACL
mount | grep 挂载点
# ext4/xfs 默认支持 ACL，无需显式 acl 选项

# 5. sticky bit 目录删不掉别人文件（属正常）
ls -ld 目录          # 确认 t 位，属主才能删
```

## 常见问题

```text
Q1: SUID 对脚本为什么无效？
A: Linux 内核出于安全考虑忽略脚本的 SUID/SGID 位，只对二进制可执行文件生效。脚本提权用 sudo。

Q2: 目录的 SGID 有什么作用？
A: 目录设 SGID 后，目录里新建的文件自动继承目录的属组（而非创建者的主组），适合团队共享目录。

Q3: sticky bit 有什么用？
A: 设在目录上，只有文件属主/root/目录属主能删除文件，其他人即使有目录写权限也删不了别人的文件（如 /tmp）。

Q4: ACL 的 mask 是什么？
A: mask 是命名用户/组的权限上限，ACL 里给用户设的权限实际生效不能超过 mask。改 mask 会连锁影响所有命名 ACL。

Q5: ls -l 权限位末尾的 + 号是什么？
A: 表示该文件有扩展 ACL。用 getfacl 查看完整 ACL。

Q6: 默认 ACL 和访问 ACL 区别？
A: 默认 ACL（-d）只设在目录上，作「新建文件/子目录的继承模板」；访问 ACL 是当前生效的权限。
```

## 面试题

```text
1. SUID、SGID、sticky bit 分别是什么？
   答：SUID(4) 程序以文件属主身份执行；SGID(2) 程序以属组执行、目录上让新文件继承属组；sticky(1) 目录上只有属主能删自己的文件。

2. 为什么 /usr/bin/passwd 要 SUID？
   答：普通用户改密码要写 /etc/shadow（仅 root 可写），passwd 带 SUID 以 root 身份运行，普通用户才能改自己的密码。

3. ACL 和基本权限的区别？
   答：基本权限只能对 owner/group/other 三类设权限，ACL 能给任意指定用户/组单独设权限，突破三类限制。

4. ACL 的 mask 和 default ACL 是什么？
   答：mask 是命名用户/组的权限上限；default ACL 是目录的继承模板，新文件自动套用。

5. 如何找出系统里所有 SUID 程序？
   答：find / -perm -4000 -type f。再对比已知清单，排查异常（属主异常/不该出现的 SUID）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. SUID 谨慎使用——SUID 程序以属主（常是 root）运行，有漏洞就是提权漏洞
2. 团队共享目录用 SGID + 默认 ACL，比改 umask 更精确
3. 临时目录设 sticky bit，防止用户互删文件
4. 用 ACL 做「给特定人额外权限」，别为此复制文件或改属主
5. 定期审计 SUID 程序：find / -perm -4000，排查异常 SUID 二进制

### 踩坑记录

```text
坑 1：给自己写的脚本设 SUID 不生效
结论：脚本设了 SUID，但执行时还是普通权限。
原因：Linux 忽略脚本的 SUID（安全考虑），SUID 只对二进制程序有效。
解法：脚本提权用 sudo，别指望 SUID；或编译成二进制。

坑 2：改了 ACL 的 mask 导致之前的授权失效
结论：setfacl 改 mask 后，之前给 alice 的 rw 变成了 r。
原因：mask 是所有命名用户/组的权限上限，改 mask 会连锁收紧。
解法：改 mask 前先 getfacl 看清影响，mask 一般设成所有命名 ACL 的最大值。

坑 3：ACL 设了但 ls -l 没看到 + 号，以为没生效
结论：getfacl 有 ACL，ls -l 却没显示 +。
原因：+ 只在「存在命名用户/组的扩展 ACL」时显示，纯基本权限不显示。
解法：用 getfacl 确认 ACL 是否生效，别只看 ls -l。

坑 4：find -perm -4000 误报大量 SUID
结论：一堆系统程序都带 SUID，以为被入侵。
原因：passwd/sudo/mount 等系统程序本来就带 SUID，是正常的。
解法：对比已知清单，只排查「不该有 SUID 的异常程序」和「属主异常的」。

坑 5：sticky bit 目录里文件删不掉，误以为权限问题
结论：在 /tmp 里删别人的文件报 Operation not permitted。
原因：sticky bit 目录里只有文件属主能删，这是正常保护。
解法：删别人的文件要先确认属主，或 sudo 提权删除。

坑 6：设默认 ACL 但新文件还是没继承
结论：给目录设了 -d 默认 ACL，新建文件却没有对应权限。
原因：默认 ACL 只影响「之后新建」的文件，已存在文件不受影响，且要确认文件系统支持 ACL。
解法：先设默认 ACL 再建文件；已存在文件用 setfacl -R 或重新设置。
```
