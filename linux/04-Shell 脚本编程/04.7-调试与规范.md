## 概述

脚本写完不等于能用，调试和规范决定它能不能稳定跑在生产上。调试靠 set 系列选项（-x 追踪、-e 遇错即停、-u 未定义变量报错、-o pipefail 管道错误），规范靠 shellcheck 静态检查 + 编码约定。一个规范的脚本应该「开头 set -euo pipefail、通过 shellcheck、遵循可移植写法」——这套标准能拦住 80% 的脚本 bug。

```text
调试规范四件套：
1. set -x —— 打印每条命令及展开结果，追踪执行过程
2. set -e —— 命令失败立即退出，不让错误滚雪球
3. set -u —— 引用未定义变量报错，暴露拼写错误
4. set -o pipefail —— 管道任一命令失败都算失败
```

## set -x 与 -e 与 -u 与 -o pipefail

四个 set 选项各有分工：`-x` 在每条命令执行前打印它（带 `+` 前缀，变量已展开），适合追踪脚本卡在哪；`-e` 遇到命令返回非零就立即退出，防止错误继续执行；`-u` 引用未定义变量直接报错，抓拼写错误；`-o pipefail` 让管道里任一命令失败都返回失败（默认只看最后一个）。生产脚本开头一行 `set -euo pipefail` 是标配。

```bash
set -x
name="debug"; echo "hello $name"
set +x
```

```text
# 实测
+ name=debug
+ echo 'hello debug'
hello debug
+ set +x
# + 号开头的是即将执行的命令，已展开变量，一眼看出执行了什么
```

```shell
# set -e：false 失败后立即停止，后面的不会执行
bash -c 'set -e; echo 步骤1; false; echo 这行不会执行'
```

```text
# 实测（只输出「步骤1」，false 之后停止）
步骤1
```

```shell
# set -u：引用未定义变量立即报错
bash -c 'set -u; echo $UNDEFINED_VAR'
```

```text
# 实测
bash: 行 1: UNDEFINED_VAR: 未绑定的变量
```

## shellcheck

shellcheck 是 shell 脚本的静态检查工具，能抓出「未加引号的变量、错误的 test 用法、可疑的语法」等常见 bug——这些 set 选项抓不到（它们只在运行时暴露）。写法是 `shellcheck script.sh`，配合 CI 可以自动检查每个脚本。它给出的告警分 error/warning/info 三级，每条都带 SC 编号和修复建议，是写 shell 脚本的「编译器」。

```shell
shellcheck script.sh          # 检查脚本
shellcheck -S warning script.sh   # 只报 warning 级别以上
```

```text
# 实测（本机）
$ command -v shellcheck || echo "shellcheck 未安装"
shellcheck 未安装（需 apt install shellcheck）
# 安装：apt install shellcheck（Debian/Ubuntu）
```

## 编码规范与可移植性

规范让脚本可读、可维护、可移植。核心约定：shebang 用 `#!/usr/bin/env bash`（比写死路径可移植）、变量引用加双引号、函数名小写下划线、缩进统一、注释解释「为什么」不解释「是什么」。可移植性注意：bash 特性（数组、[[ ]]、进程替换）在 sh/dash 里没有，要跨平台就跑 POSIX 写法或用 bash 声明。写脚本前想清楚「这个脚本要跑在哪些系统上」。

```text
编码规范清单：
1. Shebang 用 #!/usr/bin/env bash，不写死路径
2. 变量引用加双引号 "$var"，防止空值/空格拆断
3. 脚本开头 set -euo pipefail，失败即停
4. 函数名/变量名小写下划线（log_info、max_retry）
5. 用 bash 特性就声明 bash，要 POSIX 兼容就别用数组/[[]]/进程替换
```

## 应用场景实战

### 场景一：给现有脚本加上调试开关

```bash
#!/usr/bin/env bash
set -euo pipefail

# 传 DEBUG=1 时开启逐条追踪
if [[ "${DEBUG:-0}" == "1" ]]; then
    set -x
fi

echo "开始处理..."
name="${1:?用法: $0 <名字>}"
echo "处理对象: $name"
```

### 场景二：提交脚本前跑 shellcheck 自检

```shell
# 安装 shellcheck 后，对目录下所有脚本做静态检查
for f in scripts/*.sh; do
    echo "检查 $f"
    shellcheck "$f" || echo "  $f 有问题"
done
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产脚本开头统一 `set -euo pipefail`，失败即停、未定义即报错
2. 调试时临时加 `set -x`，定位到问题后记得去掉
3. 提交脚本前跑 shellcheck，把告警清零
4. 注释写「为什么这么做」，别写「这行是赋值」这种废话
5. 用 bash 特性就声明 bash，别在 sh 里硬用数组/[[]] 导致不可移植

### 踩坑记录

```text
坑 1：set -e 下用了预期会失败的命令导致脚本中断
结论：grep 找不到匹配返回 1，脚本直接退出。
原因：set -e 把非零退出码当致命错误。
解法：预期会失败的命令加 || true，或用 if ! cmd; then ... 显式处理。

坑 2：set -u 下 ${var:-default} 和 ${var-default} 行为不同
结论：set -u 时 ${var-default}（单冒号）不兜底，报未定义错误。
原因：- 和 :- 的区别：单冒号只认「未定义」，双冒号认「未定义或空」。
解法：统一用 ${var:-default}（双冒号）兜底，配合 set -u 最稳。

坑 3：set -o pipefail 让原本「能跑」的管道突然失败
结论：cat file | grep x 在 file 不存在时报错退出。
原因：pipefail 让管道里任一命令失败都返回失败，cat 的失败也被算。
解法：理解 pipefail 语义，预期某段可能失败时显式处理该段。

坑 4：set -x 把敏感信息（密码/token）打到日志
结论：调试时 set -x 打印了含密码的命令行，泄露到日志。
原因：set -x 打印展开后的完整命令，包括敏感变量。
解法：调试完去掉 set -x，或敏感操作前 set +x、之后恢复。

坑 5：脚本没 shebang，用 sh 执行时 bash 语法报错
结论：脚本里用了 [[ ]] 数组，用 sh script.sh 执行报错。
原因：没 shebang 时默认用 sh 解释，sh 不支持 bash 扩展。
解法：加 #!/usr/bin/env bash 声明，用 ./script.sh 或 bash script.sh 执行。
```
