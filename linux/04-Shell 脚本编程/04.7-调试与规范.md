## 概述

脚本写完不等于能用，调试和规范决定它能不能稳定跑在生产上。调试靠 set 系列选项（-x 追踪、-e 遇错即停、-u 未定义变量报错、-o pipefail 管道错误），规范靠 shellcheck 静态检查 + 编码约定。一个规范的脚本应该「开头 set -euo pipefail、通过 shellcheck、遵循可移植写法」——这套标准能拦住 80% 的脚本 bug。

```text
调试规范四件套：
1. set -x —— 打印每条命令及展开结果，追踪执行过程
2. set -e —— 命令失败立即退出，不让错误滚雪球
3. set -u —— 引用未定义变量报错，暴露拼写错误
4. set -o pipefail —— 管道任一命令失败都算失败
```

## 核心概念

三个主题：set 系列调试选项、shellcheck 静态检查、编码规范与可移植性。下面逐一展开。

### set -x 与 -e 与 -u 与 -o pipefail

四个 set 选项各有分工：`-x` 在每条命令执行前打印它（带 `+` 前缀，变量已展开），适合追踪脚本卡在哪；`-e` 遇到命令返回非零就立即退出，防止错误继续执行；`-u` 引用未定义变量直接报错，抓拼写错误；`-o pipefail` 让管道里任一命令失败都返回失败（默认只看最后一个）。生产脚本开头一行 `set -euo pipefail` 是标配。

```bash
set -x
name="debug"; echo "hello $name"
set +x
```

```text
# 实测
+ name=debug
+ echo 'hello debug'
hello debug
+ set +x
# + 号开头的是即将执行的命令，已展开变量，一眼看出执行了什么
```

```shell
# set -e：false 失败后立即停止，后面的不会执行
bash -c 'set -e; echo 步骤1; false; echo 这行不会执行'
```

```text
# 实测（只输出「步骤1」，false 之后停止）
步骤1
```

```shell
# set -u：引用未定义变量立即报错
bash -c 'set -u; echo $UNDEFINED_VAR'
```

```text
# 实测
bash: 行 1: UNDEFINED_VAR: 未绑定的变量
```

每个选项的「是什么→为什么→怎么用→边界」，逐个展开：

```text
set -x（xtrace）：
  是什么 —— 每条命令执行前，把「变量已展开」的命令打印到 stderr，前缀 +（可用 PS4 改前缀）
  为什么 —— 脚本不报错但结果不对时，看实际执行了什么命令、变量被展开成什么
  怎么用 —— 脚本开头 set -x，定位到问题后 set +x 关掉；或 bash -x script.sh 一次性追踪
  边界 —— 会打印敏感变量值（密码/token），生产别开；输出走 stderr

set -e（errexit）：
  是什么 —— 命令返回非零就立即退出脚本
  为什么 —— 防止前面的错误被后面的命令掩盖、错误滚雪球
  怎么用 —— 脚本开头 set -e；预期会失败的命令加 || true 或 if 包裹
  边界 —— 只作用于「非条件位置」：if/while/until/&&/||/! 后面的命令失败不退出；管道默认只看最后一段

set -u（nounset）：
  是什么 —— 展开未定义变量（不是空，是根本没定义）时报错退出
  为什么 —— 抓变量名拼写错误（$PATH 写成 $PTAH 这种），避免静默用空值
  怎么用 —— set -u；兜底用 ${var:-默认}
  边界 —— 只对「未定义」报错，${var-default} 单冒号只兜底未定义、${var:-default} 双冒号兜底未定义和空

set -o pipefail：
  是什么 —— 管道 a|b|c 里任一命令失败，整个管道就返回失败（默认只看 c）
  为什么 —— 否则 cat 不存在文件 | grep x 这种，cat 失败但 grep 成功，管道照样返回 0
  怎么用 —— set -o pipefail 和 -e 一起用，让管道错误也能触发退出
  边界 —— 会暴露「原本被默认行为掩盖」的管道中段失败，预期失败的段要显式处理
```

```shell
# PS4 改追踪前缀：加行号、函数名，长脚本里定位更快
PS4='+ ${BASH_SOURCE}:${LINENO}: ' bash -x -c 'echo hi'
```

```text
# 示例输出
+ -c:0: echo hi
hi
```

### shellcheck

shellcheck 是 shell 脚本的静态检查工具，能抓出「未加引号的变量、错误的 test 用法、可疑的语法」等常见 bug——这些 set 选项抓不到（它们只在运行时暴露）。写法是 `shellcheck script.sh`，配合 CI 可以自动检查每个脚本。它给出的告警分 error/warning/info 三级，每条都带 SC 编号和修复建议，是写 shell 脚本的「编译器」。

```shell
shellcheck script.sh          # 检查脚本
shellcheck -S warning script.sh   # 只报 warning 级别以上
```

```text
# 实测（本机）
$ command -v shellcheck || echo "shellcheck 未安装"
shellcheck 未安装（需 apt install shellcheck）
# 安装：apt install shellcheck（Debian/Ubuntu）
```

shellcheck 的「是什么→为什么→怎么用→边界」：它不执行脚本，而是解析语法 + 套用几百条规则（每条带 SC 编号）做静态分析。为什么需要它——set 系列只在运行时抓错，很多 bug（未加引号变量、`[ $x = 1 ]` 空值炸、`echo $x` 该用 printf）根本跑不到或跑到了才炸，shellcheck 在提交前就拦住。

```text
高频 SC 告警编号（记这几个就够用）：
SC2086 —— 变量未加引号，空格/空值会拆断或消失（改 "$var"）
SC2164 —— cd 失败没退出（改 cd dir || exit）
SC2006 —— 反引号做命令替换（改 $( )）
SC2034 —— 变量赋值了但没用（删除或用掉）
SC2155 —— 声明和赋值分开导致作用域/退出码问题（declare 和赋值同行）
SC2046 —— 命令替换未加引号（改 "$( )"）
```

```shell
# 典型：一个会被 shellcheck 抓的问题脚本
cat > /tmp/bad.sh <<'EOF'
#!/bin/bash
name=$1
if [ $name = "admin" ]; then
    echo hello $name
fi
EOF
# shellcheck /tmp/bad.sh 会报：
#   SC2086: 变量 $name 未加引号（空值时 [ = admin ] 语法错）
#   SC2046/SC2086: echo 里的 $name 未加引号
```

### 编码规范与可移植性

规范让脚本可读、可维护、可移植。核心约定：shebang 用 `#!/usr/bin/env bash`（比写死路径可移植）、变量引用加双引号、函数名小写下划线、缩进统一、注释解释「为什么」不解释「是什么」。可移植性注意：bash 特性（数组、[[ ]]、进程替换）在 sh/dash 里没有，要跨平台就跑 POSIX 写法或用 bash 声明。写脚本前想清楚「这个脚本要跑在哪些系统上」。

```text
编码规范清单：
1. Shebang 用 #!/usr/bin/env bash，不写死路径
2. 变量引用加双引号 "$var"，防止空值/空格拆断
3. 脚本开头 set -euo pipefail，失败即停
4. 函数名/变量名小写下划线（log_info、max_retry）
5. 用 bash 特性就声明 bash，要 POSIX 兼容就别用数组/[[]]/进程替换
```

可移植性是最容易踩的一环——「能跑」和「到处能跑」是两回事。核心分界是 bash 扩展 vs POSIX 标准：

```text
bash 扩展（sh/dash 没有，跨平台脚本要避开）：
- 数组 arr=(...)、关联数组 declare -A
- [[ ]] 双中括号测试、== 匹配、=~ 正则
- 进程替换 <(...) >(...)
- ${var^^} ${var,,} 大小写转换、${s//x/y} 全替换
- <<< Here String、&> 重定向简写、let、C 风格 for ((;;))

POSIX 安全写法（到处能跑）：
- [ ] 单中括号测试（-eq -ne -lt 数字比较、= != 字符串比较）
- $( ) 命令替换、${var:-x} 默认值、${var#x} 去前后缀（这些都 POSIX）
- 无数组用位置参数 "$@" 或 while read 代替
```

```shell
# 可移植 vs 不可移植 对比
# 不可移植（bash 专有）：
[[ $a == $b ]] && echo same
arr=(1 2 3); echo "${arr[0]}"
cat < <(echo hi)

# 可移植（POSIX）：
[ "$a" = "$b" ] && echo same
set -- 1 2 3; echo "$1"
echo hi | cat
```

## 工作原理

set 选项本质是改变 bash 的执行行为：`-x` 打开 xtrace（每条命令执行前打印到 stderr），`-e` 在「非条件位置」的命令返回非零时让 shell 立即退出，`-u` 在展开未定义变量时直接报错，`-o pipefail` 把管道返回值改成「最后一个非零退出码」。shellcheck 不执行脚本，而是解析脚本语法 + 套用几百条规则做静态分析。

```text
set 选项的作用边界（重要）：
set -e   只作用于「非条件位置」——if/while/&&/|| 条件里的失败不触发退出
         所以 grep 找不到匹配（返回 1）在 if 里不会退，裸用会退
set -u   只有「展开未定义变量」才报错，${var:-default} 双冒号可兜底
set -o pipefail   管道 a|b|c 里 a 失败也会让整个管道失败，而非只看 c
set -x   输出走 stderr，可 2> 单独重定向到调试日志
```

`set -e` 的「条件位置」判定是理解它的关键——同一条命令，放 if 条件里和裸用，行为完全不同：

```shell
# 裸用 grep：没匹配（返回1）→ set -e 触发退出
bash -c 'set -e; grep nonexist /etc/hostname; echo 不会执行'

# 放 if 里：grep 返回 1 不触发退出，走 else 分支
bash -c 'set -e; if grep -q nonexist /etc/hostname; then echo 找到了; else echo 没找到; fi'
```

```text
# 示例输出（第一段只到报错即停，第二段正常走 else）
（第一段：无输出，脚本在 grep 处退出）
没找到
```

## 常用命令与配置

```shell
set -x              # 开启命令追踪
set +x              # 关闭追踪
set -e              # 遇错即停
set -u              # 未定义变量报错
set -o pipefail     # 管道失败传播
set -euo pipefail   # 生产脚本标配（一行全开）
bash -n script.sh   # 语法检查（不执行）
bash -x script.sh   # 执行并逐条追踪
shellcheck script.sh    # 静态检查
shellcheck -e SC2034 script.sh   # 忽略指定告警编号
```

```text
辅助命令：
- PS4='+ ${LINENO}: '  改 xtrace 前缀，加行号定位
- trap 'echo "$BASH_COMMAND"' DEBUG  执行前打印每条命令（比 -x 更细）
- shellcheck -s bash -S warning -e SC1090 script.sh  指定 shell 方言、告警级别、忽略编号
- shfmt -w script.sh  格式化脚本（和 shellcheck 搭配，自动缩进）
```

## 配置文件解析

shellcheck 支持配置文件控制规则开关，bash 启动文件则决定了「脚本在什么环境下运行」——理解二者才能让规范落地。

```text
shellcheck 配置：
.shellcheckrc              项目根目录，shellcheck 默认读取，放 disable=SC2034 等
# shellcheck disable=SC2034  脚本内行注释，忽略单行告警
# shellcheck source=xxx      指定被 source 的文件，避免误报

bash 启动文件（规范脚本不该依赖的环境）：
~/.bashrc           交互式 shell 读，放别名/函数（脚本里别名默认失效）
~/.bash_profile     登录 shell 读，通常 source ~/.bashrc
/etc/profile        系统级登录 shell 配置
# 非交互式脚本不读这些文件，脚本要自包含，别依赖登录环境
```

```text
.shellcheckrc 示例（项目根目录放一个，全项目生效）：
# 忽略「变量未使用」和「source 找不到」两类告警
disable=SC2034,SC1090
# 指定默认 shell 方言
shell=bash

脚本内行内禁用（只对下一行生效）：
# shellcheck disable=SC2086
echo $myvar   # 这里明确知道 $myvar 不含空格
```

## 应用场景实战

### 场景一：给现有脚本加上调试开关

```bash
#!/usr/bin/env bash
set -euo pipefail

# 传 DEBUG=1 时开启逐条追踪
if [[ "${DEBUG:-0}" == "1" ]]; then
    set -x
fi

echo "开始处理..."
name="${1:?用法: $0 <名字>}"
echo "处理对象: $name"
```

### 场景二：提交脚本前跑 shellcheck 自检

```shell
# 安装 shellcheck 后，对目录下所有脚本做静态检查
for f in scripts/*.sh; do
    echo "检查 $f"
    shellcheck "$f" || echo "  $f 有问题"
done
```

### 场景三：生产脚本的完整标准模板

```bash
#!/usr/bin/env bash
# 生产脚本标准模板：严格模式 + 调试开关 + 清理陷阱
set -euo pipefail          # 严格模式：失败即停、未定义报错、管道失败传播

# 可选调试开关
[[ "${DEBUG:-0}" == "1" ]] && set -x

# 日志函数：统一走 stderr，方便重定向分离
log() { echo "[$(date +%H:%M:%S)] $*" >&2; }

# 清理陷阱：任何退出路径都执行
tmpdir=$(mktemp -d)
trap 'rm -rf "$tmpdir"; log "清理临时目录"' EXIT

# 参数校验
input="${1:?用法: $0 <输入文件>}"

log "开始处理 $input"
# ... 业务逻辑 ...
log "处理完成"
```

```text
这个模板把前几节的东西串起来：set -euo pipefail 严格模式、DEBUG 环境变量开关追踪、
log 走 stderr 分离输出、trap EXIT 清理临时目录、${1:?} 强制参数非空。
新脚本照着这个骨架写，能直接避开一大半常见坑。
```

## 性能与调优

```text
1. set -x 每条命令都多一次打印，调试完必须关掉（生产开 -x 会拖慢 + 刷爆日志）
2. 循环里反复 fork 子进程慢——能一次算完的提到循环外，减少进程创建
3. set -e 配合 || true 显式处理「预期会失败」的命令，避免误退出又保住严谨
4. shellcheck 进 CI 后告警清零，别累积告警（久了没人看）
5. bash -n 只查语法不执行，比真跑一遍快，提交前先跑
6. 用 shellcheck 的 -S error 只拦 error 级，避免 warning 噪音挡住提交
```

## 安全与权限

```text
1. set -x 会打印展开后的完整命令，含密码/token 的命令会泄露到日志——敏感操作前 set +x
2. 调试日志里别打明文密码，用环境变量 + 引用变量名而非值
3. 脚本加 set -u 抓未定义变量，能提前暴露「拼错变量名导致用了空值」的隐患
4. 通过 shellcheck 的脚本能拦住「未加引号变量」这类注入入口
5. set -euo pipefail 里 ${var:?} 强制参数非空，能拦住「空值拼进路径/命令」的注入
6. 别把敏感信息写进 shellcheck 报错输出（它会贴出问题行原文，含该行变量值）
```

## 故障排查

```shell
# 脚本不报错但结果不对：开 -x 追踪执行路径
bash -x script.sh 2>trace.log

# 脚本执行到一半退出了：看是不是 set -e 遇错即停
bash -n script.sh && echo "语法 OK"    # 先查语法

# 脚本里用了 bash 特性但报语法错：看是不是被 sh 解释
head -1 script.sh                       # 看 shebang

# 查 shellcheck 具体告警
shellcheck script.sh
```

```text
排错思路：
1. 脚本「不报错但结果不对」→ bash -x 2>trace.log，看实际执行的命令和变量展开值
2. 脚本「跑一半就停」→ 是不是 set -e 遇错即停；grep 没匹配返回 1 这类「预期失败」要加 || true
3. 脚本「语法错但看着没问题」→ bash -n 先查语法；看 shebang 是不是被 sh 解释（数组/[[]] 报错）
4. set -u 报「未绑定变量」→ 变量名拼错，或没加 ${var:-默认} 兜底
5. pipefail 让原本能跑的管道失败 → 定位是哪一段返回非零，预期失败的段加 || true
6. shellcheck 报一堆告警 → 逐个看 SC 编号，先修 error 级，warning 用 disable 或改写法
```

## 常见问题

```text
Q1: set -e 下 grep 找不到匹配脚本就退了？
A: grep 没匹配返回 1，被 set -e 当致命错误。预期会失败的命令加 || true 或 if 包裹。

Q2: 为什么脚本里别名（alias）不生效？
A: 非交互式脚本默认不展开别名，用函数或直接写完整命令。

Q3: set -x 的输出为什么带 + 号？
A: + 前缀是 xtrace 的标记，后面是即将执行、变量已展开的命令。

Q4: shellcheck 和 bash -n 的区别？
A: bash -n 只查语法（能不能解析），shellcheck 查语义（未加引号变量、错误用法等更深层 bug）。

Q5: ${var:-default} 和 ${var-default} 有什么区别？
A: 双冒号「未定义或为空」都兜底，单冒号只兜底「未定义」；配 set -u 统一用双冒号。

Q6: set -e 为什么在 if 条件里不生效？
A: set -e 只作用于「非条件位置」，if/while/&&/||/! 后面的命令失败不算致命，这是设计行为。

Q7: 怎么让 set -x 的输出带行号？
A: 设置 PS4='+ ${LINENO}: '，xtrace 前缀就带行号了。

Q8: shellcheck 报了 SC1090（source 找不到文件）怎么办？
A: 用 # shellcheck source=路径 指定被 source 的文件，或在 .shellcheckrc 里 disable=SC1090。
```

## 面试题

```text
1. set -euo pipefail 分别做什么？
   答：-e 命令失败即退、-u 未定义变量报错、-o pipefail 管道失败传播，生产脚本标配。

2. set -e 的盲区是什么？
   答：只作用于非条件位置，if/&&/|| 条件里的失败不触发；且管道默认只看最后一段（要 pipefail 补）。

3. shellcheck 能抓出哪些 bash -n 抓不到的问题？
   答：未加引号的变量、错误的 test 写法、可疑的语法结构、误用命令等语义级 bug。

4. 怎么让脚本跨 sh/bash 都兼容？
   答：只用 POSIX 特性（不用数组/[[]]/进程替换），或用 #!/usr/bin/env bash 声明。

5. set -x 泄露敏感信息怎么处理？
   答：调试完关掉，敏感操作前 set +x、之后恢复；或用 trap 清理调试日志。

6. bash -n 和 bash -x 分别干什么？
   答：-n 只做语法检查不执行，-x 执行并逐条打印命令（追踪）。

7. shellcheck 告警里的 SC 编号是什么？
   答：每条规则的唯一编号（如 SC2086 未加引号变量），可用来 disable 忽略或在文档里检索。

8. 为什么推荐 set -o pipefail 而不只 set -e？
   答：set -e 只认管道最后一段的退出码，中段失败会被掩盖；pipefail 让任一命令失败都传播，两者配合才完整。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产脚本开头统一 `set -euo pipefail`，失败即停、未定义即报错
2. 调试时临时加 `set -x`，定位到问题后记得去掉
3. 提交脚本前跑 shellcheck，把告警清零
4. 注释写「为什么这么做」，别写「这行是赋值」这种废话
5. 用 bash 特性就声明 bash，别在 sh 里硬用数组/[[]] 导致不可移植
6. 预期会失败的命令显式加 || true 或 if 包裹，别靠「反正能跑」
7. 新脚本用标准模板（严格模式 + 调试开关 + 清理陷阱 + 参数校验）起手

### 踩坑记录

```text
坑 1：set -e 下用了预期会失败的命令导致脚本中断
结论：grep 找不到匹配返回 1，脚本直接退出。
原因：set -e 把非零退出码当致命错误。
解法：预期会失败的命令加 || true，或用 if ! cmd; then ... 显式处理。

坑 2：set -u 下 ${var:-default} 和 ${var-default} 行为不同
结论：set -u 时 ${var-default}（单冒号）不兜底，报未定义错误。
原因：- 和 :- 的区别：单冒号只认「未定义」，双冒号认「未定义或空」。
解法：统一用 ${var:-default}（双冒号）兜底，配合 set -u 最稳。

坑 3：set -o pipefail 让原本「能跑」的管道突然失败
结论：cat file | grep x 在 file 不存在时报错退出。
原因：pipefail 让管道里任一命令失败都返回失败，cat 的失败也被算。
解法：理解 pipefail 语义，预期某段可能失败时显式处理该段。

坑 4：set -x 把敏感信息（密码/token）打到日志
结论：调试时 set -x 打印了含密码的命令行，泄露到日志。
原因：set -x 打印展开后的完整命令，包括敏感变量。
解法：调试完去掉 set -x，或敏感操作前 set +x、之后恢复。

坑 5：脚本没 shebang，用 sh 执行时 bash 语法报错
结论：脚本里用了 [[ ]] 数组，用 sh script.sh 执行报错。
原因：没 shebang 时默认用 sh 解释，sh 不支持 bash 扩展。
解法：加 #!/usr/bin/env bash 声明，用 ./script.sh 或 bash script.sh 执行。

坑 6：set -e 配命令替换，命令替换里失败被吞掉
结论：local x=$(false) 这种，函数返回码变成 local 的（0），set -e 不触发。
原因：赋值/声明语句的退出码取「最后执行的赋值/声明命令」的，命令替换的失败被掩盖。
解法：声明和赋值分开写（x=$(false); local x），让失败能被 set -e 抓到。

坑 7：shellcheck 告警全用 disable 压掉，等于没检查
结论：项目 .shellcheckrc 里 disable 了一堆 SC 编号，真正的问题被掩盖。
原因：disable 是「全局关规则」，滥用会失去检查意义。
解法：只在确实误报处用行内 # shellcheck disable=SCxxxx 精准忽略，全局 disable 只放少数确定无用的。
```
