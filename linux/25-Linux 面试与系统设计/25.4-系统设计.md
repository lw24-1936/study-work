## 概述

系统设计是 Linux 面试的压轴环节，考察的不是「会用什么工具」，而是「面对一个模糊需求，能不能拆解出架构」。本章围绕四道高频设计题展开：高并发架构、可观测性平台、CICD 流水线、容器平台。每道题的答法有固定套路——先明确需求和非功能指标（QPS、可用性、延迟），再画分层架构，逐层说技术选型，最后讲取舍和演进路径。核心原则：没有银弹，只有「在当前约束下最合适的折中」。

```text
系统设计四道题：
高并发架构   → 分层 + 缓存 + 异步 + 水平扩展
可观测性平台 → 采集 + 存储 + 查询 + 告警（三支柱 logs/metrics/traces）
CICD 流水线  → 提交 → 构建 → 测试 → 部署（自动化 + 可回滚）
容器平台     → 调度 + 编排 + 网络 + 存储 + 服务发现

答题套路：澄清需求 → 定指标 → 画架构 → 选型 → 讲取舍 → 谈演进
```

## 核心概念

1. **垂直扩展 vs 水平扩展**：垂直（scale up）= 换更大的机器，简单但有上限、单点；水平（scale out）= 加更多机器，无限但引入分布式复杂度（一致性、负载均衡、数据分片）。高并发架构默认走水平扩展。
2. **可用性 / 一致性 / 分区容错（CAP）**：分布式系统三者最多同时满足两个。实际工程里 P（分区容错）必须满足，所以在 C 和 A 之间取舍——金融支付选 C（强一致），社交/购物选 A（最终一致）。
3. **缓存**：把热点数据放离用户更近/更快的存储，削峰、降延迟。分层：CDN → 本地缓存 → 分布式缓存（Redis）→ 数据库。核心难题是缓存一致性（Cache Aside、读写穿透、过期策略）。
4. **异步与削峰**：用消息队列（Kafka/RabbitMQ）把同步链路变异步，解耦生产者消费者，扛流量洪峰。代价是系统更复杂、要处理消息积压和重复消费。
5. **限流 / 降级 / 熔断**：高并发三件套——限流（超过阈值拒绝，令牌桶/漏桶/滑动窗口）、降级（关非核心功能保核心）、熔断（下游故障时快速失败，防止级联雪崩）。
6. **可观测性三支柱**：日志（Logs，离散事件）、指标（Metrics，聚合数值）、追踪（Traces，请求链路）。三者互补，日志定位「发生了什么」、指标发现「哪里异常」、追踪还原「一次请求怎么走的」。
7. **CICD**：持续集成（频繁合并、自动构建测试）+ 持续交付/部署（自动发布到生产）。核心是「小步快跑、自动化、可回滚」，降低发布风险和成本。
8. **容器平台**：以 Kubernetes 为代表，提供调度（Pod 放哪台机器）、编排（副本/滚动更新/自愈）、网络（服务发现 + 负载均衡）、存储（持久卷）四层能力。

```text
关键权衡（面试加分项）：
强一致 vs 最终一致（CAP）
同步 vs 异步（延迟 vs 解耦）
缓存命中率 vs 一致性
平台自建 vs 用云服务（成本 vs 可控性）
```

## 工作原理

### 高并发架构的分层

```text
用户 → DNS → CDN（静态加速）→ 负载均衡（LVS/HAProxy/Nginx）
     → 网关（限流/鉴权/路由）→ 应用层（无状态，水平扩展）
     → 缓存（Redis）→ 消息队列（异步削峰）→ 数据库（读写分离/分库分表）

核心思想：
1. 静态资源前置到 CDN，动态请求才回源
2. 应用无状态，才能随意水平扩展
3. 读多写少 → 缓存扛读；写流量大 → 队列异步化
4. 数据库是最后一道，读写分离 + 分库分表才扛得住
```

### 可观测性平台的流水线

```text
数据源（应用/主机/中间件）
  → 采集（日志 Filebeat/Promtail、指标 node_exporter、追踪 OpenTelemetry）
  → 传输（Kafka 缓冲削峰）
  → 存储（日志 ES/Loki、指标 Prometheus、追踪 Jaeger/Tempo）
  → 查询（Kibana/Grafana）
  → 告警（Alertmanager 规则 + 分级通知）

三支柱分别解决：
Logs   —— 发生了什么（明细，排查单点问题）
Metrics —— 哪里异常（聚合，发现趋势和告警）
Traces —— 怎么走的（链路，定位慢请求和依赖）
```

### CICD 流水线的阶段

```text
代码提交（Git）→ 触发（Webhook/定时）
  → 构建（编译、依赖、镜像）
  → 测试（单元/集成/安全扫描）
  → 制品（推镜像仓库/制品库）
  → 部署（滚动发布/蓝绿/金丝雀）
  → 验证（健康检查/冒烟测试）→ 回滚（失败自动回退）

关键设计点：
1. 流水线即代码（Pipeline as Code），版本化管理
2. 每一步幂等可重跑，失败快速反馈
3. 制品不可变（镜像构建一次，各处复用）
4. 部署要能回滚，发布要灰度
```

### 容器平台的架构

```text
控制面（Master）：API Server / etcd / Scheduler / Controller Manager
数据面（Node）：kubelet + 容器运行时（containerd）+ kube-proxy
网络：CNI（Calico/Flannel）—— Pod 互通 + Service 服务发现
存储：CSI —— 持久卷动态供给

调度流程：Pod 提交 → API Server 写 etcd → Scheduler 打分选节点 → kubelet 拉起容器
自愈：Controller 持续对比「期望状态 vs 实际状态」，不一致就调谐
```

## 常用命令与配置

```shell
# 压测 / 验证（设计高并发架构时用来测 QPS 上限）
wrk -t 12 -c 400 -d 30s http://example.com/   # 12 线程 400 并发压 30 秒
ab -n 10000 -c 100 http://example.com/        # ApacheBench 简单压测

# 可观测性（Prometheus 生态）
promtool check rules.yml      # 校验告警规则
promql 'rate(http_requests_total[5m])'   # 查询 QPS 速率
kubectl logs -f <pod>         # 看容器日志
kubectl exec -it <pod> -- sh  # 进容器排查

# CICD / 容器
docker build -t app:v1 .     # 构建镜像
docker push registry/app:v1  # 推制品
kubectl apply -f deploy.yaml # 部署
kubectl rollout status deploy/app   # 看发布进度
kubectl rollout undo deploy/app     # 回滚
kubectl get pods -o wide     # 看 Pod 分布
kubectl top pods             # 看资源占用（需 metrics-server）
```

```text
系统设计面试「动手验证」常用：
wrk/ab 压测 → 验证架构 QPS 上限
Prometheus + Grafana → 验证可观测性
kubectl → 验证容器平台部署和回滚
```

## 配置文件解析

```yaml
# nginx 反向代理 + 限流（高并发架构入口）
http {
    limit_req_zone $binary_remote_addr zone=api:10m rate=100r/s;  # 每 IP 100 QPS
    upstream backend {
        server 10.0.0.1:8080 weight=3;   # 加权轮询
        server 10.0.0.2:8080 weight=1;
        keepalive 64;                     # 长连接复用
    }
    server {
        location /api/ {
            limit_req zone=api burst=200 nodelay;   # 突发 200，超限直接拒
            proxy_pass http://backend;
        }
    }
}

# Prometheus 采集配置（可观测性平台）
scrape_configs:
  - job_name: 'node'
    static_configs:
      - targets: ['10.0.0.1:9100', '10.0.0.2:9100']  # node_exporter
  - job_name: 'app'
    static_configs:
      - targets: ['10.0.0.1:8080']                    # 应用暴露 /metrics

# Kubernetes Deployment（容器平台）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  replicas: 3                          # 副本数，自愈 + 水平扩展
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0                # 滚动更新不停服
  template:
    spec:
      containers:
        - name: app
          image: registry/app:v1
          resources:
            limits: {cpu: "1", memory: 1Gi}   # 资源限制（防抢占）
          readinessProbe:                     # 就绪探针（服务发现）
            httpGet: {path: /health, port: 8080}
```

```text
配置解读：
limit_req_zone  —— 限流（令牌桶，rate=100r/s + burst 突发）
replicas: 3     —— 高可用的最小副本数（消除单点）
readinessProbe  —— 只有就绪才进 Service 流量，避免发布打到未就绪 Pod
resources.limits —— 容器平台资源隔离的关键，防止单容器吃垮节点
```

## 应用场景实战

本节是「面试场景题」——面试官给一个具体设计需求，答出方案。

### 场景一：设计一个短链接服务（URL Shortener）

```text
需求拆解：
写：长链接 → 生成短码 → 存映射
读：短码 → 查映射 → 302 重定向（读远大于写，读多写少典型）

设计：
1. 生成短码：发号器（全局唯一 ID）转 62 进制，或对长链接哈希 + 冲突解决
2. 存储：短码 → 长链接映射，写量小用 MySQL，读量大加 Redis 缓存热点短码
3. 高并发读：CDN 或 Redis 缓存热点，命中率极高（短链接 80/20 定律）
4. 重定向：应用返回 302 + Location，无状态可水平扩展

关键数字：
发号器（如雪花算法/Redis INCR）保证短码唯一不重复
62 进制 6 位 = 62^6 ≈ 568 亿个短链接
```

### 场景二：设计一个秒杀系统

```text
核心矛盾：瞬时海量并发（如 10 万 QPS）冲击库存（热点商品库存有限）

分层削峰：
1. 前端/网关：限流（令牌桶），超阈值直接拒，防穿透到后端
2. 缓存预热：库存、商品信息提前加载到 Redis，不打数据库
3. 库存扣减：Redis 原子操作（DECR/ Lua 脚本），预扣库存防超卖
4. 异步下单：扣减成功的请求丢消息队列，异步创建订单
5. 数据库：只扛「扣减成功」后的落库流量，压力已被削掉 99%

防超卖三板斧：
- Redis Lua 原子扣减（if stock > 0 then DECR）
- 数据库乐观锁（update ... where stock > 0）
- 消息队列串行化最终落库

取舍：用「最终一致 + 异步」换「极端并发下的可用性」
```

### 场景三：设计一个日志监控平台

```text
规模假设：100 台机器、每台每天 10GB 日志

架构：
采集层：Filebeat/Promtail 读日志，打标签（主机/应用）
缓冲层：Kafka 削峰，防止存储写入抖动丢日志
存储层：Elasticsearch（全文检索）或 Loki（低成本按标签存储）
查询层：Kibana（ES）/ Grafana（Loki）
告警层：基于查询规则 + Alertmanager 分级通知

取舍：
ES 检索强、贵、重；Loki 便宜、轻、检索弱（按标签过滤 + 少量全文）
日志量大且要复杂检索 → ES；只要 grep 式查询 → Loki
```

### 场景四：设计一个自动化发布平台

```text
流程：
开发者提交代码 → 触发流水线 → 构建镜像 → 跑测试 → 推镜像仓库
→ 部署到 K8s（滚动/灰度）→ 健康检查 → 失败自动回滚

关键能力：
1. 流水线可视化 + 可重跑（失败能快速定位哪一步）
2. 环境隔离（dev/test/prod 不同集群和权限）
3. 发布策略：滚动更新（默认）/ 蓝绿（新旧并存切换）/ 金丝雀（按比例灰度）
4. 审计：谁、何时、发布了什么版本，可追溯可回滚
5. 审批：生产发布加人工审批闸门（权限控制）
```

## 性能与调优

系统设计中的性能，本质是「在每一层都找到并消除瓶颈」：

```text
高并发架构的性能杠杆：
1. 缓存命中率 —— 每提升 1%，数据库压力下降一档，是性价比最高的优化
2. 连接复用 —— 上游 keepalive、连接池，减少 TCP 握手开销
3. 异步化 —— 非核心链路（发通知、记日志）走队列，不阻塞主流程
4. 水平扩展 —— 应用无状态化，加机器线性扩容
5. 数据库 —— 读写分离扛读、分库分表扛写、慢查询优化

可观测性平台的性能关键：
- 采集端资源开销要低（agent 轻量化，别影响业务）
- Kafka 缓冲防抖动，存储按时间分层（热数据 SSD/冷数据归档）
- 查询性能决定体验：索引设计、数据保留策略（TTL 过期）
```

```text
性能设计口诀：
能缓存就缓存，能异步就异步，能无状态就无状态，能水平扩展就不垂直扩展。
瓶颈往往在数据库和网络 IO，先优化它们，再谈应用层。
```

## 安全与权限

```text
高并发架构安全：
1. 网关统一鉴权（JWT/OAuth2），应用层不再各自鉴权
2. 限流本身也是安全手段（防 CC/DDoS、防暴力破解）
3. 敏感接口加密（HTTPS 全链路），密钥托管（Vault/KMS）
4. 输入校验在网关 + 应用双层做，防注入

可观测性平台安全：
1. 日志脱敏——手机号/身份证/密码打码，合规（GDPR/个保法）
2. 查询权限——分级访问，开发只能看自己服务的日志
3. 审计——谁查了什么日志留痕

CICD / 容器平台安全：
1. 镜像安全扫描（漏洞、恶意代码），只用可信基础镜像
2. 密钥不进镜像——用 Secret 挂载（K8s Secret/外部密钥管理）
3. 最小权限——容器用非 root 运行、Pod 安全上下文限制
4. 网络策略——Pod 间默认隔离，白名单放行
```

## 故障排查

系统设计面试也常被追问「你设计的系统出问题了怎么办」：

```text
高并发系统故障排查：
1. 雪崩（下游挂 → 上游级联挂）→ 熔断隔离 + 降级保核心 + 限流兜底
2. 缓存击穿/穿透/雪崩 → 热点 key 不过期 + 空值缓存 + 随机过期时间
3. 消息积压 → 扩容消费者 + 提升消费速度，排查消费慢的根因
4. 数据不一致 → 核对链路 + 补偿机制（对账、重试、人工修复）

可观测性平台排查（平台自身的可观测性）：
- 监控系统自己也要被监控（自监控），采集/存储/查询各组件健康
- 日志丢失 → 查 Filebeat 采集延迟、Kafka 积压、ES 拒绝写入

容器平台排查：
1. Pod 起不来 → kubectl describe pod 看事件（镜像拉取/资源/调度失败）
2. 服务访问不到 → Service/Endpoints 是否就绪，网络策略是否拦截
3. 资源不足 → 节点资源监控 + 调度策略调整 + 自动扩缩容
```

## 常见问题

**问题 1：系统设计面试的开场，应该先做什么？**

先澄清需求，别急着画架构。问清楚：目标用户量/QPS、数据量级、读写比例、延迟和可用性要求、一致性要求、预算是云还是自建。这些约束直接决定架构选型——100 QPS 和 100 万 QPS 的设计完全不同，MySQL 单机就能扛的规模没必要上分库分表。先对齐指标，再谈方案，是系统设计面试的第一分。

**问题 2：高并发系统为什么应用层要做「无状态」？**

因为只有无状态才能水平扩展。状态（如 session）存在应用进程里，负载均衡就没法把同一用户的请求发到不同机器（否则 session 丢失），扩展时还要做 session 同步。把状态外置（session 存 Redis、用户数据存数据库），应用进程变纯计算单元，加机器即扩容、挂一台无损失，负载均衡器随意分发。这是高并发架构「可水平扩展」的前提。

**问题 3：缓存穿透、击穿、雪崩分别是什么？怎么解决？**

穿透——查询不存在的 key（如 id=-1），缓存和数据库都没有，每次都打到数据库。解法：缓存空值、布隆过滤器拦截非法 key。击穿——某个热点 key 过期瞬间，大量请求同时打到数据库。解法：热点 key 不过期/逻辑过期、互斥锁（只有一个请求去加载）。雪崩——大量 key 同时过期，或缓存宕机，数据库被打垮。解法：过期时间加随机值（错峰）、缓存集群高可用、限流降级兜底。三者核心都是「保护数据库不被缓存失效击穿」。

**问题 4：什么是可观测性三支柱？为什么日志、指标、追踪都要？**

日志（Logs）是离散的明细事件，回答「发生了什么」，适合单点深挖；指标（Metrics）是聚合的数值（QPS、延迟、错误率），回答「哪里异常」，适合趋势和告警；追踪（Traces）记录一次请求跨服务的完整链路，回答「怎么走的」，适合定位慢请求和依赖问题。三者互补：告警靠指标发现问题，追踪定位到具体服务，日志还原现场细节。只有日志没有指标，异常要靠人肉翻日志；只有指标没有追踪，慢请求定位不到是哪个下游。

**问题 5：CICD 和 CD 的区别？持续交付和持续部署区别？**

CI（持续集成）= 代码频繁合并 + 自动构建测试，保证主干始终可发布。CD 有两个含义：持续交付（Continuous Delivery）= 自动构建测试后，发布到生产是「一键手动触发」，发布时机由人决定；持续部署（Continuous Deployment）= 通过测试后自动发布到生产，无人干预。多数公司到「持续交付」就够——生产发布保留人工审批（合规/风险控制），真正的「持续部署」只适合高度自动化和低风险团队。

**问题 6：蓝绿部署、滚动更新、金丝雀发布有什么区别？**

滚动更新——逐步用新版本替换旧实例，零停机但新旧并存期有版本不一致风险；蓝绿部署——准备两套完整环境（蓝旧绿新），流量一次性切换，回滚快（切回去即可）但资源翻倍；金丝雀——先让一小部分流量（如 5%）走新版本，观察指标正常再逐步放大，最稳妥但发布周期长。选择：一般服务滚动更新够用，关键服务用金丝雀，需要瞬时回滚的场景用蓝绿。

**问题 7：为什么高并发系统要用消息队列，而不是直接同步调用？**

三个价值：(1) 削峰——把瞬时高并发请求缓冲到队列，下游按自己能力消费，避免被打垮；(2) 解耦——生产者和消费者不直接依赖，一方故障/升级不影响另一方；(3) 异步——非核心链路（发短信、记日志、更新索引）不阻塞主流程，降低响应延迟。代价是引入一致性问题（消息丢失/重复/顺序）和系统复杂度，需要幂等消费 + 消息确认 + 死信队列兜底。

**问题 8：限流算法有哪些？令牌桶和漏桶的区别？**

固定窗口（简单但有临界突刺问题）、滑动窗口（更平滑）、漏桶（固定速率流出，强行平滑，超过桶容量丢弃）、令牌桶（固定速率生成令牌，请求拿令牌，允许一定突发）。区别：漏桶强制匀速输出，突发流量被压平；令牌桶允许「桶里攒了多少令牌就放多少突发」，更灵活。网关限流常用令牌桶（nginx limit_req 就是漏桶变体，配 burst 允许突发）。

**问题 9：熔断、降级、限流的区别？**

三者都是高并发保护手段，但目标不同：限流是「入口控制」，超过阈值直接拒绝，保护系统不被流量冲垮；熔断是「下游保护」，下游服务故障时快速失败（不傻等超时），防止级联雪崩；降级是「能力取舍」，资源紧张或故障时关掉非核心功能（如推荐、排行榜），保核心链路。通常组合用：限流在网关挡洪峰，熔断在调用链防雪崩，降级在故障时保核心。

**问题 10：如何设计系统的容量评估？**

先明确核心指标（峰值 QPS、日均请求量、数据量增长），再逐层算：(1) 单机能力——压测得出单实例能扛多少 QPS，反推需要多少实例；(2) 缓存——估算热数据量和命中率，定缓存容量；(3) 数据库——读写比定读写分离，数据量定分库分表；(4) 网络带宽——请求大小 × QPS 算带宽需求。留余量（通常 30%-50%），考虑峰值是均值的 3-5 倍。核心是「用数据说话」，压测基线是容量评估的依据。

```text
澄清需求：
QPS 峰值 10 万、读多写少（读写比 9:1）、可用性 99.99%、延迟 < 200ms

架构分层（自上而下）：
1. DNS 智能解析 + 多机房/多活，就近接入
2. CDN 扛静态资源（图片/CSS/JS），回源率压到 1% 以下
3. 负载均衡：LVS（四层，扛高吞吐）+ Nginx（七层，做路由/限流/缓存）
4. 网关：统一鉴权、限流（令牌桶）、灰度路由、熔断降级
5. 应用层：无状态微服务，容器化，水平自动扩缩容

8. 数据库：MySQL 读写分离 + 分库分表，冷热数据分层

技术选型：
LVS/Nginx/HAProxy 做入口，Redis 做缓存，Kafka 做异步，

- 用「最终一致 + 缓存」换「极致读性能」（读多写少场景）
- 用「异步削峰」换「写链路的实时性」（下单可异步确认）
- 分库分表带来跨库查询难 → 用冗余/异构（ES 搜、数仓分析）补偿
```

**设计题三：设计一套 CICD 流水线**

```text
澄清需求：
微服务 50+、每天多次发布、要自动化测试 + 灰度 + 一键回滚

流水线阶段（Pipeline as Code）：
1. 提交触发：Git Push → Webhook 触发（或合并到主干触发）
2. 构建：编译 + 依赖缓存（加速）+ 打 Docker 镜像（多阶段构建瘦身）

关键设计：
- 流水线即代码（.gitlab-ci.yml），版本化、可评审、可复用模板
- 制品不可变 + 签名，保证「测试过的就是部署的」
- 环境隔离（dev/staging/prod 独立集群 + 权限），生产加审批闸门
- 失败快速反馈（尽早跑快测试），每次提交都能得到构建结果

取舍：
- 全量测试慢 → 测试分层（快测试前置、慢测试并行）
```

**设计题四：设计一个容器平台（简化版 Kubernetes）**

```text
澄清需求：
管理 1000+ 容器、自动调度、服务发现、自愈、滚动更新

架构分层：
1. 控制面（Master）：
   - API Server：统一入口，所有操作走 API（声明式）
   - etcd：分布式 KV 存储，保存期望状态（强一致）
   - Scheduler：调度器，为 Pod 选节点（资源/亲和性打分）
   - Controller Manager：控制器，调谐「实际状态 → 期望状态」
2. 数据面（Node）：
   - kubelet：节点代理，按 API Server 指令拉起容器
   - 容器运行时：containerd/CRI-O
   - kube-proxy：实现 Service 负载均衡
3. 网络（CNI）：Calico/Flannel，Pod 互通 + 网络策略
4. 存储（CSI）：动态持久卷，Pod 迁移数据不丢

核心机制：
- 声明式：只描述期望状态（我要 3 副本），控制器自动达成
- 调谐循环：持续对比期望 vs 实际，不一致就修正（自愈的本质）
- Service + Endpoints：Pod 是临时 IP，通过 Service 抽象稳定入口
- 探针：liveness（挂了重启）+ readiness（就绪才进流量）

技术选型：
K8s 编排 + etcd 状态 + containerd 运行时 + Calico 网络 + CSI 存储

取舍：
- 自建 vs 云托管（EKS/ACK）→ 中小团队用托管省运维，大厂自建要可控
- 控制面高可用 → 3 节点 etcd 多数派（脑裂靠仲裁）
- 有状态服务难编排 → StatefulSet + 持久卷，但复杂度高，能无状态化就无状态化
```

**问题 1：设计系统时，如何保证高可用？**

三个层次：(1) 消除单点——每个组件至少 2 副本，负载均衡器、数据库、消息队列都做主备或集群；(2) 故障自动转移——主挂了自动切备（心跳 + 仲裁），而不是等人手动切；(3) 故障隔离——熔断、限流、超时，防止一个模块故障拖垮全局。再加「可观测」（故障能发现）和「可恢复」（备份、回滚、演练）。衡量标准是可用性「几个 9」，99.99% 意味着全年停机不到 1 小时，需要全自动恢复。

**问题 2：CAP 理论在实际系统设计中怎么用？**

CAP 说分布式系统在「一致性、可用性、分区容错」三者中最多满足两个。实际中「分区容错」是必然要面对的（网络一定会分区/故障），所以真正的选择是「CP 还是 AP」：金融支付、订单这类要强一致的选 CP（分区时宁可不可用，也不能出现脏数据）；社交动态、商品列表这类要用户体验的选 AP（分区时先保证可用，数据最终一致）。面试要能结合业务场景说清「为什么这个系统选 CP/AP」。

**问题 3：如何设计系统的水平扩展？**

关键是让每个组件都能「加机器就扩容」：应用层无状态化（状态外置）+ 负载均衡分发；缓存层分片（Redis Cluster，一致性哈希）；数据库分库分表（按业务/用户 id 分片）+ 读写分离；消息队列分区（Kafka partition 并行消费）。难点在「有状态的数据怎么分片」——分片键选择决定数据分布均匀性和跨片查询成本。扩展要提前规划分片键，避免后期数据倾斜和迁移痛苦。

**问题 4：怎么保证系统的一致性（缓存和数据库）？**

缓存一致性经典方案是 Cache Aside：读先查缓存，未命中查库并回填缓存；写先更新数据库，再删除缓存（而不是更新缓存），下次读时重新加载。为什么删缓存不更新缓存：更新缓存可能写脏（并发下覆盖），删除缓存让下次读重建更安全。进阶用「延迟双删」「订阅 binlog 异步刷新」。本质是「用最终一致换性能」，强一致场景就别用缓存或加分布式锁。

**问题 5：设计系统时如何做技术选型？**

考虑四维：(1) 业务匹配——读多写少用缓存，异步链路用队列，别为用而用；(2) 团队熟悉度——团队会 Java 就别硬上 Go，维护成本也是成本；(3) 生态和成熟度——选有社区、有踩坑经验沉淀的技术，别当小白鼠；(4) 演进空间——当前规模选轻量方案，但要留扩展路径（单机 MySQL → 主从 → 分库分表）。核心是「合适 > 先进」，能讲清「为什么选 A 不选 B」的取舍。

**问题 6：如何设计一个系统的监控告警？**

分四层：(1) 指标采集——主机（CPU/内存/磁盘/网络）+ 应用（QPS/延迟/错误率）+ 业务（订单量/成功率）；(2) 告警规则——基于基线设阈值（磁盘 85% 警告、90% 严重），用同环比检测突变；(3) 告警分级通知——P0 电话、P1 短信、P2 群消息，聚合去重防告警风暴；(4) 可观测联动——指标告警 → 追踪定位 → 日志还原。核心是「告警要准，不要狼来了」，误报多会让人麻木。

**问题 7：容器平台为什么要「声明式」而不是「命令式」？**

命令式（docker run 起一个容器）= 告诉系统「做什么动作」；声明式（yaml 描述我要 3 副本）= 告诉系统「期望状态是什么」。声明式的优势：系统自己对比「期望 vs 实际」做调谐，天然支持自愈（Pod 挂了自动补）和幂等（重复 apply 无害）；用户只需描述目标，不用关心怎么达到。这是 Kubernetes 设计的核心哲学，面试常考。

**问题 8：如何设计系统的降级方案？**

降级是「故障时保核心」：先给系统功能分级（核心链路 vs 非核心，如支付 vs 推荐），再设计每级的降级策略——非核心功能关掉、读缓存降级为静态数据、写库降级为异步积压、甚至页面降级为静态页。降级要可配置（开关）、可自动触发（结合监控指标）、可恢复。核心是「提前设计」，故障来临时才想降级已经来不及了。

**问题 9：单体架构什么时候该拆成微服务？**

拆不拆看规模和痛点，不是越拆越好。该拆的信号：单体发布互相阻塞、某模块需要独立扩容、团队大到要解耦、技术栈要分化。不该拆的信号：业务简单、团队小、流量低——微服务引入分布式复杂度（网络调用、一致性、运维成本），小规模纯属自找麻烦。演进路径：单体 → 模块化单体 → 按业务边界拆微服务，拆之前先理清服务边界（DDD 限界上下文）。

**问题 10：如何保证系统「可回滚」？**

可回滚是发布安全的前提：制品不可变（镜像/包构建一次，版本化存储，不覆盖旧版本）；配置版本化（配置变更也留版本，能回退）；数据库变更向前兼容（加字段不删字段，先加后删，避免回滚时数据不兼容）；发布策略支持快速回退（滚动更新回滚到上一版本、蓝绿切回旧环境）。核心是「每一次变更都能回到上一个已知良好状态」，而不是「出了问题再想怎么办」。

## 最佳实践与踩坑记录

### 最佳实践

1. 系统设计先对齐指标（QPS/延迟/可用性），再画架构，避免过度设计或设计不足
2. 应用层无状态化 + 状态外置，是水平扩展的前提，从第一天就做好
3. 缓存、限流、熔断、降级「高并发四件套」提前设计，别等故障了再加
4. 制品不可变 + 配置版本化，保证可回滚，发布才敢自动化
5. 可观测性三支柱（日志/指标/追踪）一起建，只建日志后期补链路成本翻倍
6. 技术选型「合适 > 先进」，能讲清取舍比堆新技术重要

### 踩坑记录

```text
坑 1：过度设计，小规模上微服务
结论：单体能扛的规模硬拆微服务，复杂度暴增、开发变慢。
原因：盲目跟风微服务，没评估团队规模和业务复杂度。
解法：按规模和痛点演进，单体 → 模块化单体 → 按边界拆微服务。

坑 2：缓存只加不管理，一致性成灾
结论：缓存数据错乱，用户看到旧数据或脏数据。
原因：更新数据库后没删缓存，或并发下缓存和库不一致。
解法：Cache Aside（写库后删缓存），热点 key 防击穿，过期策略设计好。

坑 3：CICD 没做回滚，出问题只能手工救
结论：发布失败后无法快速回退，故障时间拉长。
原因：制品不可变、配置没版本化，没有回滚路径。
解法：镜像/配置版本化，K8s rollout undo 或蓝绿切换秒级回退。

坑 4：告警规则一刀切，误报淹没真告警
结论：告警天天响，没人看，真故障被忽略。
原因：阈值不基于基线、不分组分级、不聚合去重。
解法：基于基线设多级阈值，分级通知 + 聚合降噪，定期复盘告警质量。

坑 5：日志不脱敏，踩合规红线
结论：敏感信息（手机号/密码）进日志，泄露 + 违规。
原因：只关注日志采集，没做脱敏和权限控制。
解法：采集/写入侧脱敏，查询分级权限，保留策略合规。

坑 6：容器没设资源限制，单容器吃垮节点
结论：一个容器内存泄漏，整个节点所有服务受影响。
原因：Deployment 没配 resources.limits，资源隔离失效。
解法：所有容器设 CPU/内存 limits + requests，关键服务设 QoS 保障。
```
