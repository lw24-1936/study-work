## 概述

Linux 面试的第一关通常是「基础与命令」——面试官用几个高频命令和基础概念快速判断候选人有没有真正在生产环境摸过机器。这一篇覆盖六个主题：文件系统（inode、链接、挂载）、权限（rwx、umask、特殊权限）、进程（状态、僵尸/孤儿、线程）、内存（buffer/cache、OOM）、网络（协议栈、连接排查）、常用命令（top/ps/df/du/ss 等）。重点不是背命令参数，而是讲清楚「为什么」：为什么删除文件能释放空间、为什么 df 和 du 数字对不上、为什么 load average 高但 CPU 不高。

```text
基础与命令六大主题：
文件系统 → inode / 硬链接软链接 / 挂载
权限     → rwx / umask / setuid / sticky
进程     → 状态机 / 僵尸孤儿 / 线程
内存     → buffer cache / OOM
网络     → 协议栈 / 连接与排查
常用命令 → top ps df du ss 等高频工具
```

## 核心概念

### 文件系统

1. **inode**：文件的元数据（大小、权限、属主、时间戳、数据块指针），不含文件名。文件名存在目录项（dentry）里，目录项指向 inode。删除文件的本质是「目录项断开 + inode 链接数减 1」，链接数归 0 且无进程占用时数据块才真正回收。
2. **硬链接**：多个目录项指向同一个 inode，`ln a b`。共享 inode，删一个不影响另一个，链接数不变。不能跨文件系统（inode 号只在同一文件系统内唯一），不能给目录建（防循环）。
3. **软链接（符号链接）**：独立文件，内容是目标路径字符串，`ln -s a b`。可跨文件系统、可指向目录，目标删除后链接悬空（broken link）。
4. **挂载**：把设备/分区挂到目录树某一点，`mount`。文件系统是树状单一结构，挂载点就是把另一棵子树「嫁接」进来。

### 权限

1. **rwx 三组**：owner / group / other，各三位。文件：r 读、w 写、x 执行；目录：r 列目录（ls）、w 增删改名（touch/rm/mv）、x 进入（cd + 访问路径）。
2. **umask**：新建文件/目录的默认权限遮罩。文件默认 666、目录默认 777，减去 umask 得最终权限（实际是「按位取反后与」）。默认 022 → 文件 644、目录 755。
3. **特殊权限**：setuid（执行时以文件属主身份运行，如 /usr/bin/passwd）、setgid（继承目录属组）、sticky bit（/tmp，只有属主能删自己的文件）。

### 进程

1. **进程 vs 线程**：进程是资源分配单位（独立地址空间、文件描述符表），线程是 CPU 调度单位（共享进程地址空间）。Linux 内核不区分，都用 task_struct 表示，线程本质是共享资源的轻量级进程（clone 共享 mm、fd）。
2. **进程状态**：R 运行/就绪、S 可中断睡眠、D 不可中断睡眠（等 IO，kill 不掉）、T 停止、Z 僵尸、X 退出。
3. **僵尸进程**：子进程退出后，父进程未调用 wait() 回收，进程表项（task_struct）残留。僵尸不占内存但占 PID。
4. **孤儿进程**：父进程先退，子进程被 init/systemd（PID 1）收养并回收。

### 内存

1. **物理内存 vs 虚拟内存**：进程看到的是连续虚拟地址，经页表映射到物理页，缺页时分配。
2. **buffer/cache**：buffer 是块设备元数据缓存，cache 是文件内容页缓存（page cache）。它们占用的内存是「可回收」的，应用需要时内核会回收，free 里的 available 才是真实可用量。
3. **OOM**：内存耗尽时内核启动 OOM killer，按 oom_score 选进程杀掉释放内存。

### 网络

1. **协议栈分层**：应用层（HTTP/DNS）→ 传输层（TCP/UDP）→ 网络层（IP/路由）→ 链路层（ARP/以太网）。
2. **三次握手 / 四次挥手**：连接建立与断开，SYN/ACK/FIN 语义。
3. **连接状态**：LISTEN、ESTABLISHED、TIME_WAIT、CLOSE_WAIT 等，用 ss/netstat 查看。

### 常用命令

1. **top/htop**：动态进程视图，CPU/内存/load。
2. **ps**：进程快照，`ps aux` / `ps -ef`。
3. **df/du**：df 看文件系统整体使用，du 看目录实际占用。
4. **ss/netstat**：网络连接与监听端口。
5. **lsof/fuser**：查文件被谁占用。

## 工作原理

这一节讲透几个最常被追问的「原理」，面试官往往顺着命令往下问。

1. **删除文件为什么能释放空间**：rm 只断开目录项、inode 链接数减 1。若还有进程持有该文件的 fd（如日志被 `rm` 了但进程还开着），inode 不回收、磁盘不释放，直到进程关闭 fd。这正是「df 满了、删了日志却没释放」的根因——进程还攥着已删除文件。

2. **df 和 du 为什么对不上**：df 读超级块里的块统计（文件系统整体）；du 遍历目录项累加文件大小。两个方向：删了文件但进程还开着 → df 满、du 小；稀疏文件/快照 → du 大、df 小（或相反，取决于是否含已删除但仍占块的文件）。

3. **load average 是什么**：1/5/15 分钟平均的「可运行 + 不可中断（D 状态）任务数」。它衡量的是「系统有多忙、任务排队多长」，不是 CPU 使用率。单核 load=1 表示正好满载，load 高但 CPU 低通常是「D 状态 IO 等待」或「大量线程排队等锁」。

4. **进程内存 VIRT/RES/SHR**：VIRT 虚拟地址空间总量（含映射未使用的库）；RES 常驻物理内存；SHR 共享内存（共享库、mmap）。真实「进程独占」约等于 RES − SHR。

5. **Linux 收包过程（简述）**：网卡收帧 → 硬中断 → 软中断（NAPI）→ 网络层（IP）→ 传输层（TCP/UDP）→ 套接字队列 → 唤醒应用进程 read。理解这条链，排查丢包就知道从「网卡 ring buffer / 软中断 CPU / socket 队列」逐层看。

```text
删除文件 ≠ 释放空间：
rm 只断目录项、链接数减 1 → 还有进程持 fd → inode 不回收 → 磁盘不释放

load average ≠ CPU 使用率：
它统计「R 可运行 + D 不可中断」任务数，衡量排队长度
load 高 + CPU 低 = 大概率 D 状态 IO 等待
```

## 常用命令与配置

高频命令及关键参数，面试常考「这个命令怎么用、参数什么意思」。

```shell
# 进程
ps aux                 # 所有进程，含 CPU/MEM/状态
ps -ef                 # 全格式，含 PPID（父进程）
top -p <pid>           # 只看某进程
pgrep -f nginx         # 按名字找 PID
kill -9 <pid>          # 强杀（SIGKILL，进程无法捕获）
kill -TERM <pid>       # 温和终止（SIGTERM，可被捕获做清理）

# 内存
free -h                # 看 total/used/free/buff/cache/available
cat /proc/meminfo      # 内存详细

# 磁盘
df -h                  # 文件系统整体使用率
du -sh /var/log        # 目录实际占用
du -h --max-depth=1 /  # 一级目录大小排序

# 网络
ss -tlnp               # 监听中的 TCP 端口（-l 监听 -n 不解析 -p 进程）
ss -s                  # 连接统计
netstat -anp | grep :80 # 传统写法（已逐步被 ss 取代）
ip addr                # IP 地址
ip route               # 路由表

# 文件与 fd
lsof -p <pid>          # 进程打开的所有文件
lsof /var/log/xx.log   # 谁在占用该文件
ls -l /proc/<pid>/fd   # 进程 fd 列表
```

```text
命令选择速记：
查进程全貌 → ps aux
动态观察   → top / htop
查端口占用 → ss -tlnp
查文件占用 → lsof / fuser
查磁盘占用 → df（整体）/ du（明细）
```

## 配置文件解析

基础面试常让候选人「说出这些文件里存什么」。

```text
/etc/passwd        用户账户（用户名:x:UID:GID:描述:家目录:shell），x 表示密码在 shadow
/etc/shadow        密码哈希 + 过期策略（只有 root 可读）
/etc/group         组信息
/etc/fstab         开机自动挂载的设备/分区（设备、挂载点、类型、选项、dump、fsck 顺序）
/etc/hosts         静态主机名→IP 映射（先于 DNS 查询，取决于 nsswitch）
/etc/resolv.conf   DNS 服务器地址与搜索域
/etc/sysctl.conf   内核参数（net.ipv4.*、vm.*、kernel.*），sysctl -p 生效
/proc/cpuinfo      CPU 信息（型号、核数）
/proc/meminfo      内存统计（MemTotal/MemAvailable/Buffers/Cached）
/proc/<pid>/status 进程状态（含 VmRSS、Threads）
/proc/<pid>/fd     进程打开的文件描述符
```

```shell
# 查看与临时修改内核参数
sysctl net.ipv4.ip_forward           # 查看

```

## 应用场景实战

面试场景题——面试官给一个真实现场，考察分析思路。答题框架：先定位（用什么命令拿证据），再解释（为什么是这个结果），最后处理（怎么解决）。

### 场景一：线上机器磁盘满了，怎么处理

```text
面试官：一台线上服务器磁盘 100%，你怎么处理？

分析思路（边做边讲）：
1. 确认是哪个分区满：df -h，锁定挂载点。
2. 定位大目录：du -h --max-depth=1 / 逐层下钻，找到占用最大的目录。
3. 定位大文件：ls -lSh 或 find / -size +1G，看是不是日志。
4. 常见根因三种：
   a. 日志没轮转，文件持续增长 → 清空或轮转（logrotate）
   b. 文件删了但进程还开着，空间不释放 → lsof +L1 找 deleted 文件，
      重启进程或 truncate -s 0 /proc/<pid>/fd/<n>
   c. 大量小文件吃 inode → df -i 看 inode 是否先满
5. 处理：先扩容/清日志止血，再补日志轮转 + 监控告警。

关键点：df -i 检查 inode，lsof 查 deleted 文件，这是两个高频加分项。
```

### 场景二：CPU 突然飙到 100%，怎么定位

```text
面试官：服务器 CPU 100%，你如何找到是哪个进程、哪段代码？

分析思路：
1. top 按 CPU 排序，锁定高 CPU 进程 PID。
2. top -Hp <pid> 看是哪个线程（TID）在烧 CPU。
3. 把 TID 转十六进制，jstack <pid>（Java）里找 nid=0x<TID> 的线程栈；
   或 strace -p <pid> / perf top -p <pid> 看系统调用与热点函数。
4. 判断：是业务代码死循环、GC 频繁、还是内核态开销（si 高 = 软中断）。
5. 临时处理：调低优先级（renice）或 kill 重启，根因靠堆栈定位修复。

关键点：区分「用户态 us」还是「内核态 sy」高——us 高是应用问题，sy 高可能是
系统调用风暴或驱动/中断问题。
```

## 性能与调优

```text
1. load average 高但 CPU 不高 → 查 D 状态进程（ps aux 找 D），根因在 IO/存储
2. 内存紧张先看 available，别只看 free（free 小但 available 足说明都被 cache 占了，可回收）
3. 磁盘 IO 慢 → iostat -x 看 %util、await；iotop 找高 IO 进程
4. 网络延迟高 → ping 测 RTT、mtr 定位丢包跳点、ss -s 看连接堆积
5. 文件描述符耗尽 → ulimit -n 调大，或查程序 fd 泄漏（ss -s 里 close_wait 堆积）
6. 进程优先级 → nice/renice 调静态优先级，chrt 调实时调度
```

```shell
# 常用性能查看
iostat -x 1 3          # 磁盘 IO 利用率/等待时间
vmstat 1 5             # CPU/内存/IO/上下文切换
sar -u 1 5             # 历史 CPU 采样
```

## 安全与权限

```text
1. 最小权限原则：服务用普通用户跑，别 root 常驻
2. setuid 风险：有 setuid 位的程序若被攻破即提权到属主（常是 root），
   审计用 find / -perm -4000 查所有 setuid 文件
3. /tmp 安全：必须设 sticky bit（1777），否则任何用户能删别人的临时文件
4. umask 收紧：共享服务器设 027，限制组外可读
5. shadow 只 root 可读：密码哈希不暴露给普通用户，防离线爆破
6. 进程安全：ps 看异常进程、/proc/<pid>/exe 看真实二进制路径，防被改名伪装
```

```shell
# 找 setuid/setgid 程序
find / -perm -4000 -type f 2>/dev/null   # setuid
find / -perm -2000 -type f 2>/dev/null   # setgid
# 找无属主文件（账号被删留下的文件，可能是隐患）
find / -nouser -o -nogroup 2>/dev/null
```

## 故障排查

```text
排查三板斧：
1. 看负载：uptime / top —— 系统整体忙不忙
2. 看资源：free / df -h / iostat —— 内存/磁盘/IO 哪个是瓶颈
3. 看日志：journalctl -xe / tail -f /var/log/... —— 有没有明确报错
```

```shell
# 磁盘满排查链
df -h                       # 哪个分区满
df -i                       # inode 是否也满（大量小文件）
du -h --max-depth=1 /       # 下钻找大目录
lsof +L1                    # 已被删除但仍被进程占用的文件
# 内存排查链
free -h                     # 概览
ps aux --sort=-%mem | head  # 内存 TOP 进程
dmesg | grep -i oom         # 是否有 OOM 记录
# 网络排查链
ip addr                     # IP 是否正常
ping <网关>                 # 网关通不通
ss -tlnp                    # 端口监听是否正常
```

## 常见问题

**问题 1：`free -h` 里 free 很小但系统没报内存不足，为什么？**

Linux 会尽量把空闲内存用作 page cache（缓存文件内容）和 buffer，加速 IO。这些是「可回收」的，应用真正需要时内核立即回收。判断真实可用量要看 `available` 字段，它已经扣掉了不可回收部分、加回了可回收的 cache。free 小 + available 充足 = 内存被 cache 占着但随时可让出，不构成问题。

**问题 2：为什么 `df` 显示磁盘 100%，但删了一堆文件后还是满？**

因为那些文件被进程打开着。`rm` 只断开目录项、链接数减 1，进程还持有 fd 时 inode 和磁盘块不回收。用 `lsof +L1` 或 `ls -l /proc/*/fd | grep deleted` 找出 deleted 文件，重启进程释放，或 `truncate -s 0 /proc/<pid>/fd/<n>` 就地清空。

**问题 3：僵尸进程越来越多怎么办？**

僵尸是子进程退出后父进程没 wait() 回收导致的，进程表项残留、占 PID 不占内存。根因是父进程代码没处理 SIGCHLD 或没有回收逻辑。处理：找到僵尸的父进程（`ps -ef` 看 PPID），让父进程调用 wait/waitpid，或直接 kill 父进程让僵尸被 init/systemd 收养回收。kill -9 僵尸本身无效（它已死，只是在等回收）。

**问题 4：进程杀不掉（kill -9 也没用）？**

看进程是否处于 D 状态（不可中断睡眠）——它正阻塞在内核态等待 IO（通常是坏盘/网络存储/NFS），信号无法投递，只有等 IO 返回或硬件恢复。另一个情况是进程成了孤儿但被 systemd 收养后仍在跑，或挂在不可杀的内核线程上。`ps aux | awk '$8=="D"'` 定位，根因在存储层。

**问题 5：`ss -s` 里 TIME_WAIT 一堆，有问题吗？**

TIME_WAIT 是主动关闭方在挥手后保留 2MSL 的必然状态，用于保证最后的 ACK 可达、让旧连接的分组在网络里消失。大量 TIME_WAIT 本身通常无害（占内存极小），但如果短连接并发极高会耗尽端口。高并发场景用连接池复用、调 `net.ipv4.tcp_tw_reuse=1`（谨慎，需理解副作用）、或改为长连接。

## 面试题

**问题 1：inode 是什么？为什么 Linux 删除文件能释放空间？**

inode 是文件的元数据结构，存大小、权限、属主、时间戳、数据块指针，但不存文件名。文件名在目录项（dentry）里，通过「目录项 → inode」关联。删除文件（rm/unlink）实际做两件事：断开目录项、把 inode 的链接计数减 1。当链接数归 0 且没有任何进程打开该文件时，内核才回收 inode 和数据块。所以「能释放空间」的前提是：没有硬链接残留、没有进程还持着 fd——否则删了也不释放，这就是 df 满的经典陷阱。

**问题 2：硬链接和软链接的区别？为什么硬链接不能跨文件系统？**

硬链接是同一个 inode 的多个目录项，`ln a b` 后 a、b 共享 inode，删一个另一个还在（链接数减 1 而已），内容完全同步，不占额外空间；软链接是独立的 inode，内容是「目标路径」字符串，删了目标就变成悬空链接（broken）。硬链接不能跨文件系统是因为 inode 号只在单个文件系统内唯一，跨文件系统无从指向同一个 inode；也不能给目录建（防止目录树成环）。软链接无此限制，可跨文件系统、可指向目录。

**问题 3：目录的 rwx 权限分别代表什么？**

目录的 r、w、x 语义和文件不同：r 是「列目录」权限（能 ls 看文件名，但看不到文件的 inode 属性）；w 是「增删改目录项」权限（能创建/删除/重命名文件，即便文件本身不属于你）；x 是「进入/通过」权限（能 cd 进去，也能把它当作路径前缀访问其下文件）。三者独立：有 x 无 r 能进但列不了目录；有 r 无 x 能列名但打不开文件。删除文件的判断依据是「所在目录的 w」，与文件自身的 w 无关。

**问题 4：umask 怎么算？默认 022 下新建文件/目录的权限是多少？**

umask 是「新建文件/目录默认权限的遮罩」，实际是 `默认权限 & ~umask`（按位取反再与）。文件默认 666、目录默认 777。umask 022 → 文件 `666 & ~022 = 644`（rw-r--r--），目录 `777 & ~022 = 755`（rwxr-xr-x）。因为文件默认就没有 x，所以 022 对文件等于去掉 group/other 的 w，对目录等于去掉 group/other 的 w 和 x。

**问题 5：setuid、setgid、sticky bit 分别有什么作用？各自的安全风险？**

setuid：程序执行时以「文件属主」的身份运行而非执行者身份（典型 /usr/bin/passwd，普通用户改密码要写 /etc/shadow，所以临时以 root 运行）。setgid：对可执行文件是执行时继承文件属组；对目录是「该目录下新建文件继承目录的属组」（团队协作共享目录常用）。sticky bit：只对目录有效，如 /tmp（1777），限制「只有文件属主（或 root、目录属主）能删除/改名该文件」。安全风险：带 setuid 的 root 程序一旦有漏洞即被提权到 root，所以要审计 `find / -perm -4000`；sticky 缺失则 /tmp 下任何用户可互删文件，可能被用于攻击或投毒。

**问题 6：Linux 进程有哪些状态？D 状态和 Z 状态分别是什么、为什么重要？**

主要状态：R（运行/就绪）、S（可中断睡眠，等事件可被信号唤醒）、D（不可中断睡眠，通常阻塞在内核态等 IO，此时不响应信号、kill -9 也杀不掉）、T（停止，SIGSTOP/Ctrl-Z）、Z（僵尸，已退出但父进程未回收）、X（退出中）。D 状态重要是因为它通常是存储故障信号（坏盘/NFS 卡住），且无法 kill，只能等 IO 返回；Z 状态说明父进程代码有 bug（没 wait），会泄漏 PID，积累多了无法 fork 新进程。

**问题 7：僵尸进程怎么产生、怎么处理？孤儿进程又是什么？**

僵尸：子进程先退出，父进程没调用 wait()/waitpid() 回收，子进程的退出状态和 task_struct 残留，变成僵尸。它不占内存但占 PID，数量多了会耗尽 PID 上限（`/proc/sys/kernel/pid_max`）。处理：让父进程补 wait 逻辑，或 kill 掉父进程，让僵尸被 init/systemd（PID 1）收养并回收（PID 1 会定期 wait 收养的孤儿）。孤儿：父进程先退出，子进程仍在跑，被 PID 1 收养，由它负责回收——孤儿是正常机制，僵尸才是问题。

**问题 8：进程和线程的区别？Linux 内核是怎么实现线程的？**

进程是资源分配单位（独立虚拟地址空间、独立 fd 表、独立信号处理），线程是 CPU 调度单位（同进程内共享地址空间、fd、代码段）。Linux 内核不区分两者——都用 task_struct 表示，所谓线程就是「通过 clone 系统调用以共享 mm（地址空间）、files（fd 表）等标志创建的任务」，本质是共享资源的轻量级进程。所以 Linux 里线程也叫 LWP（轻量级进程），`ps -L` 能看到同一进程的多个线程，内核调度器一视同仁调度 task_struct。

**问题 9：top 里 VIRT、RES、SHR 分别是什么？进程真实占用多少内存？**

VIRT 是虚拟地址空间总量，包含代码、数据、栈、堆、以及所有映射的共享库（哪怕只用了库的一个函数也整库映射进来），所以通常远大于真实占用。RES 是常驻物理内存，即当前真正占用的物理页。SHR 是共享内存（共享库、mmap 共享段），可能被多个进程共享。单个进程「独占」内存约等于 RES − SHR。判断内存泄漏要看 RES 是否随时间单调增长，而不是看 VIRT。

**问题 10：buffer 和 cache 有什么区别？free 命令各字段怎么理解？**

传统上 buffer 是块设备（磁盘）的元数据缓存，cache 是文件内容的页缓存（page cache）；现代内核里两者界限已模糊，统一算作「可回收内存」。free -h 的字段：total 总内存、used 已用（不含 cache）、free 完全空闲、buff/cache 缓存占用、available 真实可用（= free + 可回收的 cache 部分，这是判断内存是否紧张的准绳）。所以看到 free 很小别慌，看 available——只要 available 充足，内存就是被 cache 合理占用、随时可回收。

**问题 11：OOM killer 是什么？它怎么选择杀哪个进程？**

内存耗尽且无法回收时，内核触发 OOM killer 强制杀进程释放内存。选择依据是 oom_score（由 /proc/<pid>/oom_score 可见）：内核综合进程占用的内存量、运行时长、nice 值、是否为特权进程等打分，分数越高越先被杀。用户可设 /proc/<pid>/oom_score_adj 调整（设为 -1000 表示「永不杀」，如关键服务）。OOM 发生后 dmesg 有记录，`dmesg | grep -i oom` 可查。注意 OOM 时可能先杀「内存大户」，未必是导致泄漏的那个进程——这是排查时的常见误解。

**问题 12：简述 Linux 网络收包流程，以及一次 TCP 连接是怎么建立的？**

收包：网卡收到帧 → 触发硬中断 → 内核用软中断（NAPI）轮询收包 → 校验后交给网络层（IP 协议，做路由判断）→ 传输层（TCP/UDP，查连接、放入对应 socket 接收队列）→ 唤醒阻塞在 read/recv 的应用进程。TCP 建立连接走三次握手：客户端发 SYN（seq=x）→ 服务端回 SYN+ACK（seq=y, ack=x+1）→ 客户端回 ACK（ack=y+1），连接进入 ESTABLISHED。三次握手是为了双方都确认「自己能发、对方能收」，并同步初始序列号，防止旧连接的分组干扰新连接。

**问题 13：load average 高但 CPU 使用率不高，可能是什么原因？**

load average 统计的是「处于可运行状态（R）+ 不可中断状态（D）的任务数」的平均值，不是 CPU 使用率。它高而 CPU 低，常见三种：(1) 大量进程/线程阻塞在 D 状态等 IO（磁盘慢、NFS 卡、坏盘），任务排队但 CPU 闲着；(2) 大量线程排队等锁或等资源，处于可运行队列但没真正上 CPU；(3) 短时任务风暴，瞬时并发高导致 R 队列堆积。排查：`ps aux | awk '$8=="D"'` 找 D 进程，`iostat` 看 IO 是否瓶颈，`vmstat 1` 看 r/b 列（r 可运行数、b 阻塞数）。

**问题 14：`ps aux` 和 `top` 有什么区别？STAT 列的 D/S/Z/R 怎么读？**

ps 是「某一时刻的进程快照」，一次性输出；top 是「动态实时刷新」的交互式监控，还能排序、看负载、看每核 CPU。两者互补：定位问题先用 top 看趋势，再用 ps 拿精确字段（PPID、STAT、启动时间等）。STAT 列：R 运行/就绪、S 可中断睡眠、D 不可中断睡眠、Z 僵尸、T 停止、+ 前台进程组、l 多线程、< 高优先级、N 低优先级、s 会话领导者。

**问题 15：df 和 du 的区别？为什么 df 显示满但 du 统计出来没那么多？**

df 读文件系统的超级块，报告「整个分区的块使用情况」（全局、快）；du 遍历目录项，逐文件累加大小（局部、慢）。两者对不上有两个经典方向：(1) df 满、du 小——有文件被删除但进程还开着（deleted 文件），df 眼里块还被占着、du 遍历时却看不到这些文件的目录项，用 `lsof +L1` 找；(2) du 大、df 小——稀疏文件（逻辑大小大、实际占块少），或文件系统有快照/配额差异。

**问题 16：一个进程 CPU 100%，怎么定位到具体是哪段代码？**

`top` 找到进程 PID → `top -Hp <pid>` 找到具体线程 TID → 根据语言拿堆栈：Java 用 `jstack <pid>` 并把 TID 转十六进制（printf '%x'）去匹配 nid；C/C++ 用 `perf top -p <pid>` 看热点函数，或 `gdb -p <pid> bt`；也可 `strace -p <pid>` 看系统调用卡在哪。定位到函数后判断是死循环、算法复杂度问题还是频繁 GC。补充：看 top 里 us/sy——us 高是用户态代码，sy 高是系统调用/内核开销。

**问题 17：文件描述符（fd）是什么？ulimit -n 是做什么的？**

文件描述符是进程访问文件/套接字/管道的整数句柄，0/1/2 固定是 stdin/stdout/stderr。每次 open/socket/pipe 都分配一个 fd，存在进程的 fd 表里（/proc/<pid>/fd 可见）。ulimit -n 限制单进程可打开的最大 fd 数（默认常 1024），高并发服务（Nginx、数据库）很容易触顶，报 "Too many open files"。症状是「连接建立失败、日志报 EMFILE」。处理：调高 ulimit -n（临时 ulimit -n 65535，永久改 /etc/security/limits.conf），同时排查是否有 fd 泄漏（代码忘了 close）。

**问题 18：/proc 是什么？列出几个常用 /proc 文件及其内容。**

/proc 是内核提供的「伪文件系统」（procfs），不占磁盘，内容在读取时由内核实时生成，是观察内核和进程状态的窗口。常用：/proc/cpuinfo（CPU 型号、核数、缓存）、/proc/meminfo（内存统计 MemTotal/MemAvailable）、/proc/loadavg（1/5/15 分钟负载）、/proc/<pid>/status（进程状态、VmRSS、线程数）、/proc/<pid>/fd（进程 fd）、/proc/<pid>/exe（进程真实二进制路径）、/proc/sys/（内核参数，可写）。注意它也是攻击者常用的信息源和 rootkit 藏身处。

**问题 19：数字权限 644、755、777 分别代表什么？`chmod` 还有哪些用法？**

数字权限是八进制，r=4、w=2、x=1，三位分别对应 owner/group/other。644 = rw-r--r--（属主读写，其他只读）；755 = rwxr-xr-x（属主全权，其他读+执行）；777 = rwxrwxrwx（所有人全权，生产环境几乎不推荐，尤其对可写目录）。chmod 还支持符号模式：`chmod u+x file`（给属主加执行）、`chmod go-w file`（去掉组和其他的写）、`chmod -R 755 dir`（递归）。特殊位用第四位：`chmod 4755`（setuid）、`chmod 2775`（setgid）、`chmod 1777`（sticky）。

**问题 20：如何找出一台机器上内存占用最高的 10 个进程？如何实时看某个进程的 IO？**

内存 TOP：`ps aux --sort=-%mem | head -11` 或 `top` 按 M 排序。更准的是按 RSS 排序：`ps -eo pid,ppid,cmd,%mem,rss --sort=-rss | head`。看某进程 IO：`pidstat -d -p <pid> 1`（每进程 IO 统计）或 `iotop -p <pid>`。看磁盘整体：`iostat -x 1`（%util、await、r/s、w/s）。找 IO 大户（D 状态）：`ps aux | awk '$8=="D"'`。

## 最佳实践与踩坑记录

### 最佳实践

1. 服务用普通用户运行，用 systemd 的 User= 指定，别让业务进程常驻 root
2. 生产机器开日志轮转（logrotate），磁盘满 80% 就告警，别等 100% 再处理
3. 高并发服务检查并调高 ulimit -n，防止 "Too many open files"
4. 关键进程设 oom_score_adj=-1000，避免被 OOM killer 误杀
5. 监控看 available 而非 free，看 load 结合 CPU 一起判断
6. 排查磁盘先 df -h 再 df -i，两个维度都看（块 vs inode）
7. 给 /tmp、共享目录设 sticky bit，防互删
8. 删大日志文件用 `: > file` 或 `truncate -s 0 file` 而非 rm（避免进程还占 fd 导致不释放）

### 踩坑记录

```text
坑 1：rm 删了日志但磁盘没释放
结论：df 还是满的，空间没回来。
原因：进程还开着这个文件的 fd，rm 只断了目录项、链接数减 1，inode 和数据块不回收。
解法：lsof +L1 找 deleted 文件，重启进程释放，或 truncate -s 0 /proc/<pid>/fd/<n> 就地清空。

坑 2：只查 df -h 不查 df -i，磁盘明明有空间却报「No space left on device」
结论：df -h 显示空间够，但写文件报错。
原因：inode 用完了——大量小文件（邮件、缓存、session 文件）耗尽 inode，块空间还没满。
解法：df -i 确认，清理小文件或扩 inode（mkfs 时调大 inode 密度）。

坑 3：kill -9 杀不掉进程，以为系统出问题
结论：kill -9 后进程还在。
原因：进程处于 D 状态（不可中断睡眠），阻塞在内核态等 IO（坏盘/NFS），信号无法投递。
解法：ps 看 STAT 是否 D，根因在存储层，恢复存储/等 IO 返回，不是进程本身的问题。

坑 4：看 free 里 free 很小就以为内存不够、去加内存
结论：误判内存不足，白花钱扩容。
原因：Linux 用空闲内存做 page cache，free 小是正常现象，available 才是真实可用量。
解法：看 free -h 的 available 字段，available 充足说明内存健康。

坑 5：把「load 高」直接等同于「CPU 高」去查 CPU
结论：CPU 利用率很低，但 load 一直很高，查 CPU 白费功夫。
原因：load 统计 R+D 任务数，D 状态 IO 等待会推高 load 而 CPU 空闲。
解法：ps aux 找 D 状态进程，iostat/vmstat 看 IO 和阻塞队列，根因在磁盘/存储。

坑 6：生产环境直接 chmod 777 解决权限问题
结论：权限「问题」是解决了，但开了安全口子。
原因：777 让任何用户可读可写可执行，web 目录被 777 后易被上传 webshell。
解法：按最小权限授权，用属主/属组 + 需要时 setgid 共享目录，别一上来 777。

坑 7：改 /etc/sysctl.conf 后直接以为生效
结论：改完内核参数没变化。
原因：sysctl.conf 不会自动加载，需 sysctl -p 重新读取（或用 sysctl -w 临时改）。
解法：改完执行 sysctl -p，或写 /etc/sysctl.d/*.conf 后 sysctl --system 统一加载。
```
