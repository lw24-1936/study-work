## 概述

这一篇是 Linux 面试的「深度关」——基础命令答得好只能说明会用，原理题才决定能走多远。六个主题：系统调用（用户态/内核态切换）、虚拟内存（页表、缺页、mmap）、TCP（三次握手、拥塞控制、TIME_WAIT）、IO（阻塞/非阻塞、多路复用、epoll）、调度（CFS、上下文切换）、内核机制（中断、内核锁、零拷贝、写时复制）。核心是讲清「为什么」：为什么要有内核态/用户态之分、为什么三次握手不是两次、epoll 为什么比 select 快、上下文切换开销到底花在哪。

```text
原理深入六大主题：
系统调用 → 用户态/内核态切换、fork/COW
虚拟内存 → 页表/TLB/缺页/mmap/brk
TCP      → 三次握手/拥塞控制/TIME_WAIT
IO       → 阻塞非阻塞/select/poll/epoll
调度     → CFS/nice/vruntime/上下文切换
内核机制 → 中断/内核锁/零拷贝/写时复制
```

## 核心概念

### 系统调用

1. **用户态与内核态**：CPU 特权级划分。用户态只能访问受限地址、执行受限指令；内核态拥有完整权限，能访问硬件、任意内存。应用要操作硬件（读写文件、发网络包、分配内存）必须「陷入内核」。
2. **系统调用**：内核暴露给用户态的受控入口，用户态通过 `int 0x80`（老 x86）、`syscall` 指令（x86-64）或 `sysenter` 切入内核执行，完成后返回。是用户态访问内核能力的唯一合法通道。
3. **切换开销**：保存/恢复现场（寄存器）、切换页表与栈、CPU 特权级切换、可能的 TLB 刷新。一次系统调用约几百纳秒到微秒级。

### 虚拟内存

1. **虚拟地址空间**：每个进程看到独立、连续的地址空间（如 64 位下 128TB 用户空间），与实际物理内存解耦，靠页表映射。
2. **页表与页**：内存按固定大小分页（通常 4KB），页表记录「虚拟页 → 物理页」映射。多级页表（x86-64 四级：PGD→PUD→PMD→PTE）用稀疏结构省内存。
3. **TLB**：页表的硬件缓存（Translation Lookaside Buffer），缓存最近翻译的虚拟→物理映射，命中则跳过页表遍历。
4. **缺页中断**：访问的虚拟页没有有效映射时触发，内核按需分配物理页（或换入、或报段错误）。

### TCP

1. **连接状态机**：LISTEN → SYN_RECV → ESTABLISHED → FIN_WAIT → TIME_WAIT → CLOSED 等。
2. **拥塞控制**：慢启动、拥塞避免、快重传、快恢复，核心是拥塞窗口 cwnd 的动态调整。
3. **TIME_WAIT**：主动关闭方在最后 ACK 后等 2MSL，确保挥手完成、旧分组消亡。

### IO

1. **阻塞 vs 非阻塞**：阻塞 IO 调用会挂起进程直到数据就绪；非阻塞立即返回（EAGAIN），应用轮询。
2. **IO 多路复用**：一个线程同时监视多个 fd 的可读/可写事件，select/poll/epoll。
3. **epoll**：Linux 的高性能多路复用，基于红黑树 + 就绪链表 + 回调，事件驱动，O(1) 获取就绪事件。

### 调度

1. **CFS**：完全公平调度器（Completely Fair Scheduler），用红黑树按 vruntime（虚拟运行时间）选最小者运行，追求公平。
2. **nice**：静态优先级，-20（最高）到 +19（最低），影响 vruntime 增长速度。
3. **上下文切换**：CPU 从一个任务切到另一个，保存/恢复寄存器、栈、页表，刷新 TLB，是调度和性能的核心概念。

### 内核机制

1. **中断**：硬件异步信号（硬中断）让 CPU 停下当前工作处理紧急事件；软中断是延后处理机制（收包下半部）。
2. **内核锁**：spinlock（忙等，用于不能睡眠的上下文）、mutex（可睡眠）、RCU（读多写少的无锁读）。
3. **零拷贝**：数据不经过用户态缓冲，直接从内核/设备拷到目标，减少 CPU 拷贝与上下文切换（sendfile、mmap）。
4. **写时复制 COW**：fork 后父子共享同一物理页，谁要写才复制，避免无谓拷贝。

## 工作原理

1. **系统调用全过程**：用户态调 `read(fd, buf, n)` → glibc 把参数装进寄存器（rax=系统调用号，rdi/rsi/rdx=参数）→ 执行 `syscall` 指令 → CPU 切到内核态、跳转到内核入口（entry_SYSCALL_64）→ 内核查系统调用表分派到 `sys_read` → 内核完成读取 → 结果写回 rax → 返回用户态继续执行。整个过程用户态只发指令，具体实现全在内核。

2. **fork 与写时复制**：fork 创建一个新进程，传统做法是完整拷贝父进程地址空间，代价大。现代 Linux 用 COW：父子共享同一批物理页（只读），谁先写谁触发缺页中断，内核这时才复制那一页。所以 fork 本身很快，子进程 exec 时更是直接换新地址空间，几乎不浪费拷贝。

3. **缺页中断流程**：进程访问某虚拟地址 → MMU 查页表发现映射无效（缺页）→ 触发 page fault → 内核判断：合法访问（如 malloc 后首次写、栈增长、mmap 文件页）则分配物理页并更新页表，返回重试；非法访问（空指针、越界）则发 SIGSEGV 杀进程。所以「按需分配」是虚拟内存高效的关键。

4. **TCP 三次握手**：客户端 SYN(seq=x) → 服务端 SYN+ACK(seq=y, ack=x+1) → 客户端 ACK(ack=y+1)。两次为什么不够：若是两次，服务端收到 SYN 就认为连接建立并分配资源，而客户端可能根本没收到 ACK 或早已放弃，造成服务端资源浪费（SYN flood 放大）；三次让「连接建立」依赖客户端明确回应，服务端在收到最后 ACK 前只放半连接队列（SYN queue），可被 SYN cookie 保护。

5. **epoll 原理**：epoll_create 建一个 eventpoll 对象（内含红黑树 rbtree + 就绪链表 rdllist）→ epoll_ctl 把 fd 加进红黑树，并在该 fd 的等待队列注册回调（事件到来时回调把 fd 挂进就绪链表）→ epoll_wait 只遍历就绪链表返回事件。和 select/poll 的「每次轮询全部 fd」不同，epoll 是事件驱动，fd 越多优势越明显。

6. **CFS 调度**：维护一个按 vruntime 排序的红黑树，调度时选 vruntime 最小的任务运行。vruntime = 实际运行时间 × (1024 / 权重)，nice 越低权重越大、vruntime 增长越慢，从而获得更多 CPU。每个任务运行一个「时间片」后重新入树，保证公平。

```text
系统调用路径：
用户态 read() → 装寄存器(rax=号) → syscall 指令 → 内核入口 → 系统调用表分派 → 内核实现 → 返回

fork + COW：
fork 不真拷贝 → 父子共享只读物理页 → 谁写谁触发缺页复制 → 省内存、加速进程创建
```

## 常用命令与配置

排查原理层问题的常用命令，面试常问「怎么观察这些机制」。

```shell
# 系统调用追踪
strace -c ls                    # 统计某命令的系统调用次数与耗时
strace -p <pid>                 # 追踪运行中进程的系统调用
strace -e trace=network curl -s http://x  # 只看网络相关调用

# 虚拟内存与缺页
cat /proc/<pid>/maps            # 进程内存映射（各区段、库、堆栈）
cat /proc/<pid>/smaps           # 各映射的详细内存（含 Rss、Pss）
vmstat 1                        # si/so 换入换出、上下文切换
pidstat -r 1                    # 每进程内存与缺页

# TCP 与网络
ss -s                           # 连接统计（含 TIME_WAIT 数）
ss -tanp | awk '{print $1}' | sort | uniq -c   # 各状态连接数
sysctl net.ipv4.tcp_tw_reuse    # TIME_WAIT 复用参数

# 调度与上下文
cat /proc/<pid>/status | grep -i ctx   # 自愿/非自愿上下文切换
pidstat -w 1                    # 每进程上下文切换速率
chrt -p <pid>                   # 查看进程实时调度策略与优先级

# 中断
cat /proc/interrupts            # 各 CPU 中断计数
cat /proc/softirqs              # 软中断计数
```

```text
原理层排查命令速记：
系统调用 → strace
缺页/内存 → vmstat si/so、/proc/<pid>/smaps
TCP 状态 → ss -tanp 按状态统计
上下文切换 → pidstat -w
中断     → /proc/interrupts、/proc/softirqs
```

## 配置文件解析

```text
/proc/sys/kernel/         内核核心参数（pid_max、threads-max 等）
/proc/sys/net/ipv4/       IPv4 网络栈参数（tcp_*、ip_forward）
/proc/sys/vm/             虚拟内存参数（swappiness、overcommit_memory）
/etc/sysctl.conf          内核参数持久化配置（sysctl -p 生效）
/etc/security/limits.conf 资源限制（nofile、nproc、memlock）
/proc/<pid>/maps          进程内存映射布局
/proc/<pid>/status        进程状态（含上下文切换、线程数、VmRSS）
/proc/interrupts          各 CPU 硬中断计数
/proc/softirqs            软中断计数
```

```shell
# 内核参数查看与修改
sysctl vm.swappiness               # 查看 swap 倾向（默认 60）
sysctl -w vm.swappiness=10         # 临时调低（减少换页）
sysctl net.ipv4.tcp_tw_reuse       # TIME_WAIT 复用开关
```

## 应用场景实战

面试场景题——给一个现场，考察候选人能否用原理定位问题。

### 场景一：高并发服务大量连接处于 TIME_WAIT，端口不够用

```text
面试官：你们服务是短连接，压测时大量 TIME_WAIT，端口耗尽报错，怎么解决？

分析思路：
1. 先讲清楚 TIME_WAIT 为什么存在：主动关闭方在挥手后等 2MSL，
   保证最后的 ACK 可达、让旧连接分组消亡，是 TCP 正常机制，不是 bug。
2. 确认是「谁主动关闭」：短连接若由服务端主动 close，服务端会积压 TIME_WAIT。
3. 解决方向（按优劣排序）：
   a. 首选：改长连接 / 连接池复用，从根上减少连接建立关闭次数
   b. 让客户端主动关闭，把 TIME_WAIT 转移到客户端
   c. 调内核参数：tcp_tw_reuse=1（复用 TIME_WAIT 给新的发起连接，注意
      仅对客户端发起方向安全），谨慎用 tcp_tw_recycle（已被废弃，有 NAT 误伤）
4. 加分：说明 tw_recycle 为什么被废弃（NAT 下时间戳不一致导致误丢包）。

关键点：面试官要的不是「调个参数就行」，而是你理解 TIME_WAIT 的本质、
知道参数改动的副作用。
```

### 场景二：应用内存持续增长疑似泄漏，怎么用原理定位

```text
面试官：服务内存一直涨，怀疑内存泄漏，你如何定位并判断是「真泄漏」还是「正常缓存」？

分析思路：
1. 先区分「进程内存」和「系统内存」：free -h 看 available，
   如果 available 充足，可能只是内核 page cache 增长（正常）。
2. 定位进程：top 按 RES 排序，锁定嫌疑进程；/proc/<pid>/status 看 VmRSS 趋势。
3. 看进程内存映射：cat /proc/<pid>/maps + smaps，确认增长的是堆（heap）、
   匿名 mmap 还是共享库——堆/匿名 mmap 持续增长才是泄漏主嫌疑。
4. 分析工具：valgrind（重、慢，测 C/C++）、heaptrack、或语言自带（Go pprof、
   Java jmap/jstat 看堆与 GC）。看 GC 后堆是否回落：回落说明是短期峰值，不回说明泄漏。
5. 结合原理判断：malloc/free 不配对、或持有引用不释放（引用计数/缓存无界）。

关键点：把「系统缓存增长」误判成「进程泄漏」是新手常见错误，先分层定位。
```

## 性能与调优

```text
1. 减少系统调用 → 批量 IO（readv/writev）、零拷贝（sendfile）、缓冲聚合
2. 减少上下文切换 → 减少线程数、避免频繁唤醒、CPU 亲和（taskset/绑核）
3. 减少缺页 → 大页（THP/hugepage）、内存池预分配、madvise 预读
4. 网络性能 → 调大 socket 缓冲、开 tcp_tw_reuse、用 epoll 替代 select
5. swap 倾向 → 调低 vm.swappiness（数据库/缓存服务常设 10 或 0）
6. 实时性需求 → chrt 用实时调度策略（SCHED_FIFO/RR），但别乱用（会饿死其他任务）
7. 中断开销 → 网卡多队列 + 中断亲和（irqbalance / smp_affinity），软中断绑核
```

```shell
# 观察上下文切换与中断
vmstat 1 5               # cs 列 = 每秒上下文切换、in 列 = 每秒中断
pidstat -w 1 5           # 每进程 cswch/s（自愿） nvcswch/s（非自愿）
mpstat -P ALL 1          # 每核 CPU，看 %irq %soft（中断/软中断占比）
```

## 安全与权限

```text
1. 内核态/用户态隔离本身就是安全边界：用户态无法直接碰内核内存/硬件，
   攻破用户态程序 ≠ 攻破内核（除非有提权漏洞）
2. 系统调用是攻击面：内核漏洞大多通过「构造恶意系统调用参数」触发，
   内核需定期打补丁（CVE 修复）
3. 提权攻击：内核/驱动漏洞（如 Dirty COW——利用写时复制的竞争条件写只读内存）
   是经典提权路径，所以要关注内核版本安全公告
4. ASLR / NX / KASLR：地址随机化 + 不可执行栈 + 内核地址随机化，增加利用难度
5. 权限校验在内核完成：access/open 等调用在内核态核对 uid/gid/capability，
   用户态设置的结果不可信，安全判断必须落内核
6. 资源限制防滥用：limits.conf 设 nproc/nofile/memlock，防 fork 炸弹、
   fd 耗尽类 DoS
```

## 故障排查

```text
原理层故障排查链：
1. 系统调用卡住 → strace -p <pid> 看卡在哪个调用（如 read/connect/futex）
2. 缺页/换页频繁 → vmstat 看 si/so，高说明内存不足在换页
3. 上下文切换过高 → pidstat -w 找高频切换进程，通常线程太多或锁竞争
4. 连接异常堆积 → ss -tanp 按状态统计，SYN_RECV 多查半连接（syn flood）、
   CLOSE_WAIT 多查应用没 close、TIME_WAIT 多查短连接
5. 中断过高 → mpstat 看 %soft，高说明网络/磁盘软中断繁忙，查 /proc/softirqs
6. 内核报错 → dmesg -T | tail 看 OOM、page fault、hung task 等
```

```shell
# 连接状态快速统计
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn
# 内核最近报错
dmesg -T | tail -50
# 观察 hung task / OOM
dmesg -T | grep -iE 'oom|hung'
```

## 常见问题

**问题 1：为什么要有内核态和用户态之分？**

安全和稳定。用户态程序如果可以直接执行特权指令、访问任意物理内存，一个 bug 就能把整机搞崩、一个恶意程序就能读走所有进程的数据。CPU 特权级 + 内存保护（页表）把「危险操作」限制在内核，用户态只能通过系统调用这种受控入口请求内核代劳，内核在入口处校验参数和权限。这就是「隔离 + 受控通道」的设计。

**问题 2：一次系统调用为什么有开销？开销主要花在哪？**

主要三部分：(1) 特权级切换——从 ring3 切到 ring0，涉及保存用户态寄存器、加载内核栈；(2) 内核入口的额外工作——查系统调用表、参数拷贝（用户缓冲拷到内核）、可能的页表/地址空间相关操作；(3) 缓存失效——内核态和用户态用不同地址空间/栈，指令和数据缓存、TLB 可能失效。相比普通函数调用（纳秒级、不切特权级），系统调用通常几百纳秒到微秒级。高吞吐系统因此要「减少系统调用次数」，用批量操作（readv/writev）、缓冲、零拷贝。

**问题 3：malloc 出来的内存，物理内存是立刻分配的吗？**

不是。malloc 只是 libc 层的堆管理操作——它要么从已有的空闲堆里切一块返回，要么通过 brk/mmap 向内核「申请虚拟地址空间」，此时只改了进程的虚拟内存映射，物理页并未分配。真正写这块内存时才触发缺页中断，内核才分配物理页。所以「malloc 大块内存后 free -h 里 used 没变」是正常现象——虚拟地址有了，物理页还没摸过。

**问题 4：TIME_WAIT 为什么是 2MSL 而不是别的值？**

MSL 是报文段最大生存时间（Maximum Segment Lifetime，Linux 默认 60 秒）。2MSL 保证两点：(1) 主动关闭方最后发的 ACK 若丢失，对端会重传 FIN，2MSL 内能等到并重新回 ACK，确保挥手可靠完成；(2) 让本连接的所有分组在网络中彻底消亡，避免「旧连接的分组」干扰「相同四元组的新连接」。2MSL 是「最坏情况下往返 + 存活」的安全下界。

**问题 5：select 和 epoll 的本质区别？为什么 epoll 更快？**

select/poll 是「轮询型」：每次调用都要把整个 fd 集合从用户态拷进内核，内核 O(n) 遍历所有 fd 检查状态，返回后应用还要遍历一遍才知道谁就绪——fd 越多，每次调用开销越大，且 fd 数有上限（select 默认 1024）。epoll 是「事件驱动型」：epoll_ctl 把 fd 注册进内核红黑树（一次注册），事件到来时通过回调直接把 fd 挂进就绪链表，epoll_wait 只把就绪的 fd 拷出来（O(就绪数)），不随 fd 总数增长。所以海量连接、少量活跃的场景下 epoll 碾压 select。

**问题 6：什么是上下文切换？它的开销到底花在哪里？**

上下文切换是 CPU 从一个任务（进程/线程）切到另一个任务。开销分「直接」和「间接」：直接开销是保存当前任务寄存器、栈指针、程序计数器，加载新任务的；切换内核栈和页表（跨进程切换要换 CR3 寄存器，导致 TLB 失效，后续访问内存频繁缺页重翻译）。间接开销是缓存局部性被破坏——CPU 的 L1/L2 缓存、TLB 里全是上一个任务的数据，切完新任务全 miss，要重新从内存加载。所以切换不只是「保存恢复寄存器」那点事，真正的代价在缓存失效。减少手段：减少线程数、绑核、避免频繁唤醒。

## 面试题

**问题 1：什么是系统调用？用户态和内核态是怎么切换的？**

系统调用是内核暴露给用户态程序的受控接口，是用户态访问硬件和内核能力的唯一合法通道（读文件、发网络、分配内存、创建进程都要走它）。切换过程：用户态调用 glibc 包装函数 → 把系统调用号放 rax、参数放 rdi/rsi/rdx → 执行 `syscall` 指令（x86-64）→ CPU 切到内核态、跳转内核入口 → 内核查 sys_call_table 分派到对应实现 → 完成后结果写回 rax → `sysret` 返回用户态。整个过程对用户态透明，但涉及特权级切换、现场保存恢复、缓存失效，故有固定开销。

**问题 2：系统调用和普通函数调用有什么区别？**

普通函数调用：同一地址空间、同一特权级，只压栈保存少量寄存器、跳转，纳秒级，无权限切换。系统调用：跨用户态/内核态，要切特权级（ring3→ring0）、换内核栈、查系统调用表、拷贝参数（用户缓冲 ↔ 内核缓冲）、可能有 TLB/缓存失效，几百纳秒到微秒级。本质区别是「是否越过特权边界」——函数调用只是跳转，系统调用是一次受控的权限提升。

**问题 3：fork 是怎么实现的？什么是写时复制（COW）？**

fork 创建子进程：内核复制父进程的 task_struct（含寄存器、fd 表、内存描述符），但地址空间不真拷贝——用 COW，父子共享同一批物理页并把页表标记为只读。之后谁先写这些页，谁触发缺页中断，内核这时才为该页做一份真实拷贝。所以 fork 很快（只建控制结构 + 复制页表），且子进程若紧接着 exec（换新程序）几乎不浪费拷贝。COW 是「延迟拷贝」思想：不确定要改之前，先共享，改了再复制。

**问题 4：什么是虚拟内存？为什么现代操作系统都需要它？**

虚拟内存让每个进程看到独立、连续的虚拟地址空间，与实际物理内存通过页表映射解耦。三大好处：(1) 隔离——进程 A 无法访问进程 B 的内存，一个进程崩溃不影响其他进程；(2) 抽象——进程不用关心物理内存碎片、多进程地址冲突，链接器和程序可假设固定布局；(3) 按需分配 + 换页——物理内存不够时把冷页换到 swap，虚拟空间可以比物理内存大。代价是页表翻译开销，靠 TLB 缓存缓解。

**问题 5：多级页表解决什么问题？TLB 是什么？**

单级页表的问题是「浪费」：若用一个连续数组映射整个 4GB 地址空间（4KB 页 = 100 万项），每个进程都要常驻这么大一张表。多级页表（x86-64 四级）按需建立：只给实际用到的地址区间建中间级表，未使用的区间不占内存，稀疏高效。代价是翻译要多级查表（4 次内存访问），所以引入 TLB——页表缓存的硬件结构，缓存最近翻译过的「虚拟页 → 物理页」，命中则一次完成翻译，大大加速。

**问题 6：缺页中断（page fault）是什么？什么时候触发？**

CPU 访问某虚拟地址时，MMU 查页表发现该页没有有效映射（或权限不符），硬件触发缺页异常，交给内核处理。触发场景：malloc 后首次写（按需分配）、栈增长、访问 mmap 的文件页（首次读时从磁盘载入）、访问被换出到 swap 的页（换入）、以及真正的非法访问（空指针、越界）。前几种是「正常缺页」，内核分配物理页/换入后返回重试；最后一种内核发 SIGSEGV 杀掉进程。

**问题 7：malloc/free 的原理？brk 和 mmap 分配内存有什么区别？**

malloc 是 libc 的用户态堆管理器：小内存从堆（heap）的空闲块链/空闲列表里切；堆不够了向内核申请。内核层两种方式：brk——移动堆顶指针（program break），扩展堆区，适合小块的连续增长；mmap——直接映射一段匿名内存，适合大块（一般超过 MMAP_THRESHOLD，默认 128KB）。free 只是把块标记为空闲、放回空闲列表，一般不立即归还内核（归还了下次 malloc 又得向内核申请）。brk 的内存是「增长后可整体归还」，mmap 的可以「整段 munmap 释放」。

**问题 8：mmap 和 read/write 的区别？mmap 适合什么场景？**

read/write 走「内核缓冲 → 用户缓冲」的拷贝：磁盘数据先读进 page cache（内核），再拷一份到用户缓冲，两次拷贝（磁盘→内核→用户）。mmap 把文件直接映射进进程地址空间，访问映射区就是访问 page cache，缺页时从磁盘载入，省掉「内核→用户」那次拷贝，且省一次系统调用（映射后直接指针读写）。适合：大文件随机访问、频繁读写的文件、需要零拷贝的场景。注意：mmap 对小文件、一次性顺序读未必更快（缺页开销 + 建立映射开销），且文件被截断会触发 SIGBUS。

**问题 9：详细讲 TCP 三次握手和四次挥手，为什么握手是三次、挥手是四次？**

握手三次：C 发 SYN(x) → S 回 SYN+ACK(y, x+1) → C 回 ACK(y+1)。三次才能让双方都确认「我能发、对方能收」，并同步初始序列号。两次不够：若两次，S 收到 SYN 就认为连接建立并分配资源，但 C 可能没收到 S 的 SYN+ACK、或早已放弃，S 却一直等，资源被浪费，也放大了 SYN flood 攻击面。挥手四次：因为 TCP 是全双工，两个方向要分别关闭。主动方发 FIN（我不发了）→ 对端 ACK（知道了）→ 对端发 FIN（我也不发了）→ 主动方 ACK。中间「对端 ACK 和 FIN」通常分开发（对端可能还有数据要发完），所以是四次。若对端没数据，ACK 和 FIN 可合并，实际也会出现三次挥手。

**问题 10：TIME_WAIT 状态有什么用？大量 TIME_WAIT 会有什么问题、怎么处理？**

TIME_WAIT 是主动关闭方在挥手最后 ACK 后保持 2MSL 的状态，作用：(1) 保证最后 ACK 丢失时能重传，让挥手可靠结束；(2) 让旧连接的分组在网络里彻底消亡，避免串到相同四元组的新连接。问题：短连接高频场景，主动关闭方积压大量 TIME_WAIT，每个占一个端口（四元组），耗尽可用的本地端口导致连不上。处理：改长连接/连接池（根本）、让客户端主动关闭、调 tcp_tw_reuse=1（复用，仅对发起方向安全）。tcp_tw_recycle 因 NAT 时间戳问题已被废弃，不要提它当正解。

**问题 11：TCP 拥塞控制有哪些阶段？慢启动和拥塞避免怎么切换？**

四个核心阶段：慢启动（cwnd 从 1 指数增长，每收到 ACK 翻倍，快速探测带宽）、拥塞避免（cwnd 超过慢启动阈值 ssthresh 后转为线性增长，每 RTT +1，谨慎逼近）、快重传（收到 3 个重复 ACK 立即重传丢失段，不等超时）、快恢复（快重传后不降到 1，而是 cwnd 减半进入拥塞避免）。切换逻辑：慢启动 → 拥塞避免的触发点是 cwnd 达到 ssthresh；发生超时（严重拥塞）→ ssthresh = cwnd/2、cwnd 归 1 重进慢启动；快重传（轻度拥塞）→ ssthresh = cwnd/2、cwnd = ssthresh 直接拥塞避免。核心思想：加法增大、乘法减小（AIMD）。

**问题 12：TCP 和 UDP 的区别？各自适用什么场景？**

TCP：面向连接（三次握手）、可靠（序号/确认/重传）、有序、流量控制 + 拥塞控制、面向字节流，开销大、有延迟；UDP：无连接、不可靠、不保证顺序、无拥塞控制、面向报文，开销小、延迟低。适用：TCP 用于需可靠传输的场景（HTTP、文件传输、数据库）；UDP 用于实时性优先、容忍丢包的场景（视频通话、直播、DNS、游戏、QUIC 的底层）。选型核心：数据完整性重要选 TCP，延迟敏感且能容忍部分丢失选 UDP。

**问题 13：select/poll/epoll 的区别？各自的应用场景？**

select：fd 集合用位图，默认上限 1024，每次调用整体拷贝进内核、O(n) 遍历，返回后应用再遍历。poll：用链表结构，去掉了 1024 上限，但仍是轮询、O(n)。epoll：事件驱动，红黑树 + 就绪链表，注册一次、事件回调，epoll_wait 只返回就绪 fd（O(活跃数)），且支持 ET/LT 两种触发模式。场景：连接少、简单场景 select/poll 够用且可移植；Linux 高并发服务器（Nginx、Redis、Java NIO）一律 epoll。ET（边缘触发）需非阻塞 fd + 一次性读空，效率更高；LT（水平触发）更易用、不易漏事件。

**问题 14：阻塞 IO、非阻塞 IO、IO 多路复用、异步 IO 的区别？**

阻塞 IO：read 阻塞直到数据就绪，期间线程啥也干不了，最简单但并发靠多线程。非阻塞 IO：read 立即返回 EAGAIN，应用不断轮询重试，忙等浪费 CPU。IO 多路复用：一个线程用 select/epoll 同时监视多个 fd，谁就绪处理谁，单线程高并发的基础（但读数据本身仍是同步的）。异步 IO（AIO）：发起 read 后立即返回，数据就绪后内核通过回调/信号通知，全程不阻塞——Linux 原生 AIO 主要用于磁盘（io_uring 是新一代高性能异步 IO）。区别核心：前三种「读数据」这一步都还是同步的，只有异步 IO 连读取都交给内核完成。

**问题 15：Linux 进程调度器是怎么演进的？CFS 的核心思想是什么？**

演进：早期 O(1) 调度器（2.6 引入，按优先级维护运行队列）→ CFS（2.6.23 起默认，完全公平调度）→ 现在还有针对多核/能耗的改进。CFS 核心是「公平」：理想模型下每个任务应分得均等的 CPU 时间。实现上维护一棵按 vruntime（虚拟运行时间）排序的红黑树，每次调度选 vruntime 最小的任务；vruntime = 实际运行时间 × (1024 / 权重)，权重由 nice 决定——nice 越低（优先级越高）权重越大、vruntime 增长越慢，就能多占 CPU。每个任务跑完一个时间片重新入树，如此循环实现近似公平。

**问题 16：nice 值怎么影响调度？vruntime 是什么？**

nice 是用户可设的静态优先级，范围 -20（最高优先级）到 +19（最低），默认 0。它不直接决定运行顺序，而是映射成权重（nice 每降一级，权重约增加 10%），权重又决定 vruntime 的增长速度。vruntime 是「经过权重修正的运行时间」：权重越大的任务，跑同样真实时间 vruntime 涨得越少，在红黑树里就越靠前，获得更多调度机会。所以 nice 是通过「改变 vruntime 增长速度」间接影响 CPU 份额，而不是简单的「谁 nice 低谁一直跑」。

**问题 17：什么是上下文切换？怎么减少它带来的性能损耗？**

上下文切换是 CPU 从一个任务切到另一个任务，保存当前任务的寄存器/栈/PC，恢复新任务的，并切换内核栈、页表（跨进程）。代价除了直接保存恢复，更贵的是缓存局部性破坏——TLB、L1/L2 缓存全失效，切完大量 cache miss。减少手段：(1) 减少线程数，用事件驱动/epoll 替代「一连接一线程」；(2) 减少锁竞争，避免线程频繁阻塞唤醒；(3) CPU 亲和性（taskset/绑核），让线程固定在某核减少跨核迁移；(4) 避免不必要的系统调用和中断（软中断绑核、网卡多队列）。

**问题 18：硬中断和软中断有什么区别？Linux 为什么要有软中断？**

硬中断：硬件（网卡、磁盘、时钟）异步发信号，CPU 停下当前工作进入中断处理程序，处理紧急、短小的部分。软中断：不是硬件触发的「中断」，而是内核延后执行机制（bottom half），把中断处理中「不那么紧急、耗时」的部分（如收包后的协议栈处理）推迟到合适时机执行。要有软中断是因为硬中断处理要「快」，不能长时间占用 CPU、不能睡眠，否则影响系统响应；把重活丢给软中断/下半部，硬中断只做「清中断、标记、唤醒下半部」。观察：/proc/interrupts（硬）、/proc/softirqs（软）、mpstat 的 %soft。

**问题 19：什么是零拷贝？sendfile 是怎么减少拷贝的？**

传统文件发送：磁盘 → 内核 page cache → 拷贝到用户缓冲（read）→ 拷回内核 socket 缓冲（write）→ 网卡，共 4 次拷贝 + 2 次系统调用 + 上下文切换。零拷贝核心是「让数据不经过用户空间」：sendfile 让内核直接把数据从 page cache 拷到 socket 缓冲（或配合网卡 scatter-gather 只传描述符），省掉「内核→用户→内核」两次拷贝和用户态的介入。典型场景：Nginx 静态文件、文件下载。相关技术还有 mmap（省一次拷贝）、splice、以及 io_uring。核心收益：降低 CPU 拷贝开销 + 减少上下文切换，高吞吐 IO 服务必备。

**问题 20：内核里的 spinlock、mutex、RCU 分别是什么？各自适用什么场景？**

spinlock（自旋锁）：拿不到锁就忙等（自旋），不睡眠。适用于「临界区极短、且不能睡眠」的上下文（中断处理、软中断）。缺点：自旋期间空耗 CPU，所以临界区必须短，且单核下要配合关抢占/关中断防死锁。mutex（互斥锁）：拿不到锁就睡眠让出 CPU，适用于「临界区长、进程上下文、可以睡眠」的场景。RCU（Read-Copy-Update）：读多写少的无锁机制，读者完全无锁、零开销，写者通过「复制-修改-发布」+ 延迟回收（宽限期 grace period）保证读者安全。适用于路由表、内核配置、数据结构「读极频繁、写极少」的场景。

## 最佳实践与踩坑记录

### 最佳实践

1. 高并发网络服务用 epoll + 非阻塞 IO + 事件循环，别用「一连接一线程」
2. 高频小 IO 用批量系统调用（readv/writev）或零拷贝（sendfile），减少 syscall 次数
3. 数据库/缓存服务调低 vm.swappiness，避免热数据被换到 swap 导致延迟抖动
4. 大内存页（THP/hugepage）适合大块内存访问的负载，能减少 TLB miss
5. 理解参数副作用再改内核参数（tcp_tw_reuse 等），别照抄网上「优化大全」
6. 性能优化先 profile（strace/perf/vmstat）定位瓶颈，再对症下药，别凭感觉
7. 关键服务设 oom_score_adj 保护，并监控缺页、上下文切换、连接状态等内核指标

### 踩坑记录

```text
坑 1：照抄网上的内核「优化参数」，结果更糟
结论：改了一堆 net.ipv4 参数后性能反而下降或出现诡异丢包。
原因：很多「优化」有前提和副作用，如 tcp_tw_recycle 在 NAT 下因时间戳不一致误丢包（已废弃）。
解法：理解每个参数的作用和副作用，逐项验证，别一次性堆叠。

坑 2：把「内存用满」当成内存泄漏
结论：看到 free 很小就以为泄漏，查了半天进程没毛病。
原因：Linux 用空闲内存做 page cache，free 小是正常现象，available 才是真实可用量。
解法：先看 free -h 的 available，再看具体进程 RES 是否单调增长，分层判断。

坑 3：select 的 FD_SETSIZE 默认 1024，fd 超了没报错却监控不到
结论：连接数上千后新连接「失联」，select 静默漏掉 fd。
原因：select 用位图、默认上限 1024，超限的 fd 被忽略且不报错。
解法：改用 poll（去上限）或 epoll（高并发首选），并检查返回值。

坑 4：非阻塞 IO 忘了处理 EAGAIN，忙等烧 CPU
结论：改成非阻塞后 CPU 飙到 100%。
原因：read/accept 返回 EAGAIN 时应用立即重试，形成忙等空转。
解法：非阻塞 IO 必须配合 epoll/select 等事件通知，EAGAIN 时去等事件，别自旋。

坑 5：调 vm.swappiness=0 以为完全禁用 swap，结果还是有换页
结论：设 0 后仍观察到少量 swap in/out。
原因：swappiness=0 只是「尽量不用 swap」，内存真不够时内核仍会换页。
解法：要彻底禁 swap 用 swapoff，或接受「0 是倾向而非禁止」的事实。

坑 6：大量线程频繁上下文切换拖垮性能，以为 CPU 不够去加核
结论：CPU 使用率不高但系统很卡，加核没改善。
原因：线程数远多于核数，频繁切换 + 锁竞争，时间都耗在切换和 cache miss 上。
解法：减少线程数、用事件驱动、排查锁竞争（pidstat -w 看切换率）。

坑 7：忽略 D 状态进程，把存储问题当成进程问题去杀进程
结论：进程 kill -9 杀不掉，以为是进程 bug。
原因：D 状态（不可中断睡眠）进程阻塞在内核态等 IO（坏盘/NFS），信号无法投递。
解法：ps 看 STAT 是否 D，根因在存储层，恢复存储而不是折腾进程。
```
