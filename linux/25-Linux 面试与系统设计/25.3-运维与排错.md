## 概述

运维与排错是 Linux 面试里最「实战」的一环，面试官不给标准答案，只给场景——「磁盘满了你怎么查」「CPU 100% 了」「网站突然访问慢」，考的是排查思路和方法论，不是背命令。核心四块：常见故障（磁盘满、OOM、CPU 飙高、网络不通）、性能优化（定位瓶颈、针对性调优）、高可用（冗余、故障转移、负载均衡）、安全（基线、加固、入侵排查）。四条主线共用同一套底层逻辑：先定位、再分析、后修复、最后复盘防复发。

```text
运维与排错四块 + 共同排查逻辑：
常见故障 → 定位故障点（日志/指标/现场）
性能优化 → 找瓶颈（USE 方法：利用率/饱和度/错误）
高可用   → 消除单点（冗余 + 故障转移 + 仲裁）
安全     → 纵深防御（最小权限 + 基线 + 审计）

通用排查路径：定位 → 复现 → 根因 → 修复 → 复盘
```

## 核心概念

1. **MTBF / MTTR / 可用性**：MTBF（平均无故障时间）、MTTR（平均修复时间），可用性 = MTBF / (MTBF + MTTR)。缩短 MTTR 比拉长 MTBF 更实际，所以「快速定位 + 快速恢复」比「从不故障」更有价值。
2. **平均负载 load average**：单位时间内「处于可运行状态 + 不可中断睡眠状态」的平均进程数。它和 CPU 使用率不是一回事——高负载 + 低 CPU 通常意味着大量进程在等 IO（D 状态）。
3. **上下文切换 context switch**：CPU 在进程/线程间切换的开销。频繁切换（cs 值高）会吃掉 CPU 时间片，是性能优化常被忽略的隐形瓶颈。
4. **内存水位与 page cache**：Linux 用 free 内存做 page cache（缓存文件），「free 很低」不一定是内存不够，要看 available。真正内存不足的信号是 swap 频繁换入换出、OOM Killer 触发。
5. **IOPS / 吞吐 / 时延**：IOPS 是每秒 IO 次数（随机小 IO 场景）、吞吐是每秒数据量（顺序大 IO 场景）、时延是单次 IO 耗时。三者权衡，不同业务关注点不同。
6. **单点故障 SPOF / 冗余 / 故障转移 / 脑裂**：高可用三件套，脑裂是网络分区时主备都抢资源的经典问题，靠仲裁（多数派）解决。
7. **最小权限 / 安全基线 / 纵深防御**：安全三原则——权限给到刚好够用、系统按基线加固、多层防护（网络/主机/应用/数据）互相兜底。

```text
关键区分（面试常考）：
load average 高 ≠ CPU 高（可能是 IO 等待，D 状态进程）
free 低 ≠ 内存不足（可能是 page cache，看 available）
磁盘 util 100% ≠ 磁盘瓶颈（SSD/RAID 并发时 util 高但还有余量）
```

## 工作原理

排查的本质是把「故障现象」翻译成「资源/配置/代码的异常」，再顺着依赖链往下钻。几个高频问题的底层原理：

1. **磁盘满的机制**：文件系统 inode 或数据块耗尽。两种满法——`df` 报 100%（数据块满）或 `df` 没满但报 No space left on device（inode 满，小文件太多）。还有第三种：进程还开着已删除的文件句柄，`df` 满但 `du` 统计不到，删除文件不释放空间。
2. **OOM 的机制**：物理内存 + swap 都耗尽，内核触发 OOM Killer，按 `oom_score`（基于内存占用、进程属性、可调权重）挑一个进程杀掉。容器环境下 OOM 往往先表现为容器被杀、RestartCount 增长。
3. **高可用的机制**：心跳检测 → 故障判断 → 故障转移三步循环，难点在区分「机器真挂」和「网络分区」，靠仲裁多数派 + fence 隔离解决。
4. **安全的机制**：认证（你是谁）→ 授权（你能干什么）→ 审计（你干了什么）三段式，加固就是缩小每一段的暴露面。

```text
排查优先级（从快到慢、从外到内）：
1. 先看现象：报错信息、告警、用户反馈
2. 再看日志：journalctl / 应用日志 / dmesg
3. 再看指标：CPU/内存/IO/网络 四个维度
4. 再看现场：进程状态、连接、句柄、磁盘
5. 复现 + 最小化验证根因，再修复 + 复盘
```

## 常用命令与配置

排错高频命令，按维度分组：

```shell
# CPU / 负载
top -c                 # 实时进程，按 P 排 CPU
htop                   # top 增强版，直观
uptime                 # 看 1/5/15 分钟平均负载
mpstat -P ALL 1        # 每核 CPU 使用率
pidstat -u 1           # 每个进程 CPU 占用
vmstat 1 5             # 上下文切换 cs / 换入换出 si so

# 内存
free -h                # 重点看 available，不是 free
vmstat -s              # 内存统计汇总
cat /proc/meminfo      # 内存水位原始数据
slabtop                # 内核 slab 内存占用

# IO
iostat -xz 1           # 设备利用率 %util、await、r/s w/s
pidstat -d 1           # 每个进程 IO
iotop                  # 按进程看读写量（需 root）

# 网络
ss -s                  # socket 统计
ss -tanp               # TCP 连接 + 进程
sar -n DEV 1           # 网卡流量
iftop / nload          # 实时流量（需装）
ping / mtr             # 连通性 / 路由追踪
traceroute             # 逐跳路由

# 磁盘 / 句柄
df -h                  # 数据块使用
df -i                  # inode 使用（小文件满）
du -sh <dir>           # 目录大小
lsof | wc -l           # 打开的文件句柄数
lsof -i :<port>        # 端口被谁占用
ss -tan | grep <port>  # 端口占用（更快）

# 进程 / 现场
ps aux --sort=-%mem    # 按内存排序
ps -eo pid,ppid,stat,cmd  # 进程状态（D 状态排查）
strace -p <pid>        # 跟踪进程系统调用
pstack <pid>           # 进程栈（Java 用 jstack）
journalctl -u <svc> -n 50  # 服务日志
dmesg -T | tail -50    # 内核日志（OOM 记录）
```

```text
命令选择速记：
看整体 → top / vmstat / iostat（先定位哪个维度）
看进程 → pidstat / ps（锁定具体进程）
看现场 → strace / lsof / ss（看它在等什么/占什么）
看历史 → sar / journalctl / dmesg（事后回溯）
```

## 配置文件解析

排错和调优经常要动这些配置：

```ini
# /etc/sysctl.conf —— 内核参数（sysctl -w 即时生效，写入文件持久化）
net.ipv4.ip_local_port_range = 1024 65535   # 本地端口范围（高并发短连接）
net.core.somaxconn = 65535                  # listen backlog 上限
net.ipv4.tcp_tw_reuse = 1                   # 复用 TIME_WAIT 连接
fs.file-max = 6553560                       # 系统级最大句柄数
vm.swappiness = 10                          # 倾向少用 swap（0-100，越小越不用）

# /etc/security/limits.conf —— 进程资源限制（ulimit）
* soft nofile 65535      # 软限制：打开文件句柄数
* hard nofile 65535      # 硬限制
* soft nproc 65535       # 进程数

# /etc/fstab —— 挂载表（排查磁盘/启动问题）
UUID=xxx /data ext4 defaults,noatime 0 2    # noatime 减少读 IO

# /etc/resolv.conf / /etc/hosts —— 解析顺序
# hosts 文件优先于 DNS（排查「解析到错误 IP」）
```

```text
排查配置类问题套路：
1. 服务起不来 → 先看配置语法（nginx -t / sshd -t / systemctl status）
2. 句柄耗尽 → 查 ulimit -n 和 /proc/sys/fs/file-max
3. 端口不够用 → 查 ip_local_port_range 和 TIME_WAIT 数量
4. 解析错 → 查 /etc/hosts、/etc/resolv.conf、/etc/nsswitch.conf 顺序
```

## 应用场景实战

本节是「面试场景题」——面试官抛一个故障，你要答出排查步骤。

### 场景一：磁盘满了怎么查

```text
排查步骤（自顶向下）：
1. df -h 看哪个分区满了（根分区 / /var /data 最常见）
2. df -i 看 inode 是否也满（小文件多导致）
3. du -sh /* 逐层定位大目录（注意 --exclude 跳过挂载点）
4. 定位到具体目录后 ls -lhS 按大小排，找大文件
5. 若是「df 满但 du 统计不到」→ lsof | grep deleted 找已删除未释放的文件句柄

处理：
- 大日志文件 → 清空（> file 而非 rm，避免句柄问题）或 logrotate
- 已删除未释放 → 重启占用句柄的进程
- 真需要空间 → 迁移到 /data 或扩容
```

### 场景二：CPU 100% 怎么查

```shell
# 1. 先看是不是单进程吃满
top -c                    # 按 P 排序，找 %CPU 最高的进程
# 2. 单进程高 → 看它的线程
top -Hp <pid>             # 看该进程内哪个线程高
# 3. Java 进程 → 转十六进制线程号，jstack 看栈定位代码
printf '%x\n' <tid>
jstack <pid> | grep -A 20 <hex_tid>
# 4. 系统整体高但无单进程高 → 看上下文切换 / 中断 / 软中断
vmstat 1 5                # cs 高 = 上下文切换频繁；si 高 = 内存压力
mpstat -P ALL 1           # 看是否单核打满（单线程程序只吃一个核）
```

```text
CPU 高的三类根因：
1. 计算密集 → 代码死循环 / 大计算，定位到线程栈
2. 上下文切换频繁 → 线程/进程太多，或锁竞争严重
3. 中断/软中断高 → 网络小包风暴（网卡软中断吃满单核）
```

### 场景三：网站访问慢怎么排查

```text
从用户到后端逐层排查：
1. 先定位慢在哪一层：DNS 解析？网络？应用？数据库？
2. 网络层：ping 看 RTT、mtr 看丢包、ss -tan 看连接队列是否堆积
3. 应用层：看响应时间监控、查慢日志、strace 看卡在哪个系统调用
4. 资源层：CPU/内存/IO 四维度（top/iostat/free）
5. 数据库：慢查询日志、连接数、锁等待

常见根因：
- 磁盘 IO 打满（await 高）→ 慢在磁盘
- 内存不足频繁 swap → 慢在换页
- 数据库锁等待 / 慢 SQL → 慢在后端
- 连接池耗尽 → 请求排队
```

## 性能与调优

性能优化按「USE 方法」拆：对每个资源（CPU/内存/IO/网络），检查利用率（Utilization）、饱和度（Saturation）、错误（Errors），哪个到顶优化哪个。

```text
CPU 调优：
1. 计算密集 → 优化算法 / 并行化 / 换语言热点
2. 上下文切换 → 减少线程数、合并非关键线程、绑核（taskset）
3. 中断风暴 → 网卡多队列（RPS/RFS）、irqbalance 均衡中断

内存调优：
1. 先确认是否真缺：free -h 看 available，而不是 free
2. 频繁 swap → 调低 vm.swappiness、加内存、优化缓存
3. 内存泄漏 → 用 pmap / valgrind / Java heap dump 定位

IO 调优：
1. iostat -xz 看 %util 和 await，定位瓶颈盘
2. 随机小 IO → 换 SSD / 加内存做缓存
3. 顺序大 IO → 加大预读 / 换吞吐更高的盘
4. 内核参数：vm.dirty_ratio（脏页比例）、I/O 调度器

网络调优：
1. 先分带宽/延迟/丢包，mtr 定位
2. 短连接高并发 → 调 tcp_tw_reuse、扩端口范围、somaxconn
3. 长连接 → 调 TCP 窗口、开启 BBR 拥塞控制
```

```text
性能优化「先测量再优化」铁律：
别拍脑袋优化——先用工具拿到瓶颈证据（哪个资源饱和、哪个进程消耗），
再针对性优化，优化后重测验证。盲目调内核参数是运维大忌。
```

## 安全与权限

安全这块面试偏「基线 + 加固 + 入侵排查」三问：

```text
系统加固（安全基线）：
1. 最小权限：用非 root 用户跑服务、sudo 精确授权、文件权限收紧
2. 账户安全：禁用空密码、限制 root 远程登录、密码策略、密钥登录
3. 服务最小化：关掉不用的服务、防火墙只开必要端口（白名单）
4. 系统更新：及时打安全补丁（yum/apt 安全更新）
5. 审计日志：开启 auditd，关键操作留痕

入侵排查思路：
1. 看异常账户：/etc/passwd 有无新增用户、UID 0 异常
2. 看异常进程：ps 找陌生进程、启动项 /etc/rc.local、crontab -l
3. 看异常连接：ss -tanp 查可疑外联、last 查登录记录
4. 看异常文件：find 最近被修改的可疑文件（webshell 特征）
5. 看日志：/var/log/secure 暴力破解、journalctl 异常登录
```

```text
纵深防御（多层兜底）：
网络层（防火墙/ACL）→ 主机层（基线/加固/HIDS）→ 应用层（WAF/输入校验）→ 数据层（加密/备份）
一层被突破还有下一层，单点防护必然失效。
```

## 故障排查

几个高频故障的完整排查链：

### 故障一：内存不足 / OOM

```shell
# 1. 确认是不是真 OOM
dmesg -T | grep -i "out of memory"    # 内核 OOM 记录
journalctl -k | grep -i oom           # 或从日志看
# 2. 看当前内存状态
free -h                               # available 是否接近 0
cat /proc/meminfo | grep -E 'MemFree|MemAvailable|SwapFree'
# 3. 找吃内存的大户
ps aux --sort=-%mem | head -20
# 4. 看是否有内存泄漏（RES 持续增长）
pidstat -r 1 10                       # 观察某进程 RSS 变化
```

```text
OOM 处理：
- 真不够 → 加内存 / 减少并发 / 优化缓存
- 泄漏 → 修代码（Java 用 jmap -heap、golang 用 pprof）
- 容器场景 → 看 cgroup 限制（docker stats / kubectl top），可能是 limit 设太小
```

### 故障二：网络不通

```shell
# 分层排查（自底向上）
ip addr                    # 1. IP 配了吗
ip route                   # 2. 路由对吗
ping <网关>                # 3. 局域网通吗
ping <外网IP>              # 4. 出网通吗（不通 = 路由/防火墙）
nslookup <域名>            # 5. DNS 解析（解析不出 = DNS 问题）
ss -tanp | grep <port>     # 6. 服务监听了吗
```

```text
网络不通口诀：
IP → 路由 → 网关 → 外网 → DNS → 服务端口，逐层 ping/trace，哪层断哪层查。
ping 不通不等于服务挂，可能是 ICMP 被防火墙禁（用 telnet/nc 测端口）。
```

### 故障三：平均负载高

```shell
uptime                              # 负载多少（对比 CPU 核数）
top -c                              # 看是 CPU 高还是 IO 等
vmstat 1 5                          # r 列（运行队列）、b 列（阻塞队列）
# r 高 + CPU 高 → CPU 密集
# b 高 + CPU 低 → IO 密集（D 状态进程）
ps -eo pid,stat,cmd | awk '$2 ~ /D/'   # 找 D 状态（不可中断睡眠）进程
```

## 常见问题

**问题 1：load average 很高但 CPU 使用率很低，为什么？**

load average 统计的是「可运行 + 不可中断睡眠」状态的平均进程数，包含在等 IO 的进程。CPU 使用率低说明 CPU 不忙，但大量进程卡在等磁盘/网络 IO（D 状态），这些进程也算进 load，所以负载高、CPU 低。典型场景：磁盘故障变慢、NFS 卡住、大量进程读写慢盘。排查用 `vmstat 1` 看 `b` 列（阻塞进程数）和 `iostat -xz` 看 `%util`/`await`。

**问题 2：free -h 显示 free 很低，是不是内存不够？**

不一定。Linux 会把空闲内存用作 page cache（缓存文件读写），`free` 字段低是正常的。判断内存是否真紧张看 `available` 字段——它估算「还能分配给新进程多少内存」。只要 available 充足就没问题；available 接近 0 且 swap 频繁换入换出（`vmstat` 的 `si`/`so` 高）才是真不够。也可以 `cat /proc/meminfo` 看 `MemAvailable`。

**问题 3：删了文件但磁盘空间没释放？**

因为还有进程持有该文件的句柄。Linux 里删除文件只是删掉目录项，如果某个进程还打开着它，inode 和磁盘块不会被释放，直到进程关闭句柄或退出。排查：`lsof | grep deleted` 找到占用句柄的进程，重启该进程即可释放。所以清日志用 `> file`（清空内容）而不是 `rm`，避免正在写日志的进程句柄悬空。

**问题 4：df 和 du 统计的磁盘使用对不上？**

两个方向：(1) `df` 满但 `du` 统计小——上面说的已删除未释放句柄，空间被「幽灵文件」占着；(2) 挂载点遮蔽——某目录下又挂载了别的分区，`du` 默认统计会跨挂载点，或反之统计不到。用 `du -x`（不跨文件系统）对照。

**问题 5：端口被占用怎么处理？**

```shell
ss -tanp | grep :8080        # 看谁监听
lsof -i :8080                # 备选
# 确认是误占用后
kill <pid>                   # 或 kill -9 <pid>
# 若是 TIME_WAIT 堆积（连接关闭后残留），是短连接多的正常现象
ss -tan | grep TIME_WAIT | wc -l
```

**问题 6：进程处于 D 状态（不可中断睡眠）是什么？**

进程在等某个不可中断的内核操作，通常是磁盘 IO（读写慢盘、NFS 挂载卡死）。D 状态的进程杀不掉（`kill -9` 无效），只能等 IO 返回或重启机器。排查：`ps -eo pid,stat,wchan,cmd` 看它卡在哪个内核函数，`iostat` 看磁盘是否异常。

**问题 7：Linux 服务器时间不对 / 时钟漂移？**

用 NTP/chrony 同步时间。漂移会导致日志时间错乱、证书校验失败、分布式系统乱序。排查：`chronyc sources -v` 看同步源、`timedatectl` 看当前状态。生产环境必须配时间同步，且注意时区（`timedatectl set-timezone Asia/Shanghai`）。

**问题 8：Too many open files 报错？**

句柄耗尽。分两级：进程级 `ulimit -n`（默认 1024）和系统级 `fs.file-max`。解法：改 `/etc/security/limits.conf` 提高 nofile，改 `/etc/sysctl.conf` 的 `fs.file-max`，重启服务生效。排查句柄泄漏用 `lsof -p <pid> | wc -l` 观察是否持续增长。

**问题 9：系统变慢但各项指标都正常？**

隐藏瓶颈排查：(1) 上下文切换（`vmstat` 的 `cs`）——线程过多；(2) 中断/软中断（`mpstat` 的 `%soft` 或 `/proc/interrupts`）——网卡小包；(3) 单个 CPU 核打满但整体不高（`mpstat -P ALL`）——单线程程序；(4) 内核态 CPU 高（`top` 的 `sy`）——系统调用过多。这些都不在常规「CPU/内存/IO」表面指标里。

**问题 10：怎么判断是网络问题还是应用问题？**

`curl -w` 看各阶段耗时：DNS 解析、TCP 连接、TLS 握手、首字节（TTFB）、传输时间。TTFB 大 = 应用慢，传输时间长 = 带宽/网络问题，连接时间长 = 网络延迟或连接队列满。

## 面试题

**问题 1：一台 Linux 服务器突然 CPU 飙到 100%，你如何定位？**

分三步：先看全局，再看进程，最后看现场。`top -c` 按 CPU 排序找罪魁进程；若单进程吃满，`top -Hp <pid>` 定位到线程，Java 进程用 `jstack` 看线程栈定位代码热点；若无明显高进程，`vmstat 1` 看 `cs`（上下文切换）和 `si/so`（内存压力），`mpstat -P ALL` 看是否单核打满，`cat /proc/interrupts` 或 `mpstat` 的 `%soft` 看软中断（网卡小包风暴）。定位到根因后再决定是优化代码、减少线程还是绑核/网卡多队列。

**问题 2：平均负载（load average）是什么？三个数值分别代表什么？多少算高？**

load average 是单位时间内「可运行状态 + 不可中断睡眠状态」进程的平均数，三个数值分别是 1 分钟、5 分钟、15 分钟的平均值。判断高低要看 CPU 核数：单核机器 load=1 表示刚好满载，8 核机器 load=8 才满载。三个数能看出趋势：1 分钟 > 15 分钟 = 负载在上升；反之在下降。关键：load 高不一定 CPU 高，可能是 IO 等待。

**问题 3：内存使用率高，如何判断是真的内存不足还是 page cache 占用？**

看 `available`（或 `/proc/meminfo` 的 `MemAvailable`），它是内核估算的可分配内存，扣除了 page cache。free 低但 available 充足 = page cache 占着，属于正常，内存紧张时内核会自动回收 cache。真正不足的标志：available 接近 0、swap 频繁换入换出（`vmstat` 的 `si`/`so` 持续非零）、触发 OOM Killer。cache 本身不释放也不影响新分配，不用手动 `echo 3 > /proc/sys/vm/drop_caches`（那是测试用的）。

**问题 4：OOM Killer 是什么？它怎么挑选进程杀掉？**

当物理内存和 swap 都耗尽，内核调用 OOM Killer 结束一个进程释放内存。挑选依据是 `oom_score`（越高越容易被杀），分数由内存占用、进程类型等因素计算，root 进程和 init 有保护（`oom_score_adj` 可调）。容器/云环境 OOM 常表现为容器被杀重启。排查看 `dmesg -T | grep -i oom` 或 `journalctl -k`。预防：设好内存限制、监控可用内存、避免内存泄漏。

**问题 5：磁盘 IO 高的排查思路？**

`iostat -xz 1` 看三个关键指标：`%util`（设备忙碌度，接近 100% 可能瓶颈）、`await`（平均 IO 等待时间，高 = 慢）、`r/s`/`w/s`（读写次数）。再 `pidstat -d 1` 或 `iotop` 定位哪个进程在读写。区分场景：随机小 IO（数据库）看 IOPS 和 SSD，顺序大 IO（日志、备份）看吞吐。根因可能是慢盘、缺缓存、脏页频繁刷盘、或某进程异常狂写。解法：换 SSD、加缓存、优化应用 IO 模式、调 `vm.dirty_ratio`。

**问题 6：什么是 TIME_WAIT？TIME_WAIT 过多怎么办？**

TCP 主动关闭方在发送最后一个 ACK 后进入 TIME_WAIT 状态，持续 2MSL（约 60 秒），作用是确保对方收到最后 ACK、让旧连接的分组自然消亡（防止串扰新连接）。短连接多的服务（如频繁 HTTP 请求）会堆积大量 TIME_WAIT，耗尽端口导致无法新建连接。解法：调 `net.ipv4.tcp_tw_reuse=1`（复用）、扩 `ip_local_port_range`、`somaxconn`，更根本的是改长连接或连接池，而不是粗暴调小 `tcp_fin_timeout`。

**问题 7：一台服务器能建多少 TCP 连接？受哪些限制？**

受四类限制：(1) 文件句柄数 `fs.file-max` 和进程级 `ulimit -n`，每个 socket 占一个句柄；(2) 本地端口数 `ip_local_port_range`（客户端主动连接时每个连接要一个本地端口，约 6 万）；(3) 内存，每个 socket 占内核内存（缓冲区等）；(4) `somaxconn`/backlog 影响监听队列。作为服务端（被动）主要受句柄和内存限制，作为客户端（主动）还受端口范围限制。

**问题 8：如何排查内存泄漏？**

区分进程类型：Java 用 `jstat -gcutil <pid>` 观察 Full GC 后老年代是否持续增长，增长即泄漏，`jmap -dump` 导出 heap 用 MAT 分析；原生进程（C/Go）看 `ps` 的 RSS 是否随时间单调增长，`pmap -x <pid>` 看内存映射，`valgrind`（C）或 `pprof`（Go）定位分配点；容器看 `docker stats` / `kubectl top` 配合 cgroup 限制。核心思路是「采样对比」——隔一段时间看内存是否只增不减。

**问题 9：高可用中的脑裂是什么？怎么避免？**

脑裂（split-brain）指主备节点因网络分区互相以为对方挂了，都抢资源成为「主」，导致双主同时写数据、数据冲突。避免：(1) 仲裁——引入奇数节点多数派投票（如 etcd/zk），谁拿到多数票谁做主，少数派降级；(2) fence/STONITH——把疑似故障节点隔离（断电/剥夺资源），防止它继续写；(3) 心跳走独立链路，降低误判概率。本质是「用更可信的第三方裁决代替双方互相猜测」。

**问题 10：网站访问突然变慢，你怎么系统排查？**

从客户端到后端逐层定位：先确认是普遍慢还是个例（全局 = 后端/网络，个例 = 用户侧）；`ping`/`mtr` 看网络延迟丢包；`curl -w` 看各阶段耗时定位慢在哪层；服务器上 `top`/`iostat`/`free` 看四维资源；应用日志看慢请求；数据库看慢查询和锁；最后按「USE 方法」锁定饱和资源再优化。核心是分层排除，不要上来就重启服务掩盖问题。

**问题 11：如何做故障复盘（post-mortem）？**

复盘不是追责，是防复发。结构：(1) 时间线——故障何时发生、何时发现、何时恢复，精确到分；(2) 影响——影响范围、时长、用户；(3) 根因——5 why 追问到最深一层（是配置错、代码 bug 还是流程缺位）；(4) 改进——针对根因的 action item，每项有负责人和期限；(5) 沉淀——补监控告警、补文档、补演练。核心产出是「下次同类故障能更快发现、更快定位」。

**问题 12：swap 是什么？生产环境该不该开 swap？**

swap 是磁盘上划出的交换空间，内存不足时把不活跃内存页换到磁盘。争议点：开 swap 能防 OOM（内存峰值有缓冲），但 swap 到磁盘 IO 慢，性能抖动。生产实践：(1) 数据库类服务建议关或设很小的 swappiness，避免关键数据被换出；(2) 一般服务设 `vm.swappiness=10`（低值，尽量不用 swap）；(3) 容器/K8s 节点通常建议关 swap（kubelet 要求）。判断是否该开，取决于「要不要用性能换稳定性」。

**问题 13：怎么排查「服务能启动但端口不通」？**

层层检查：服务是否真的监听（`ss -tanp | grep <port>`，看 LISTEN）；监听在哪个地址（127.0.0.1 只有本机能连，0.0.0.0 对外）；防火墙是否放行（`firewall-cmd --list-all` / `iptables -L`）；SELinux 是否拦截；如果是容器，端口是否映射到宿主机。用 `telnet/nc` 从外部测端口连通性，区分「服务没起」和「网络/防火墙挡了」。

**问题 14：日志文件过大如何处理？**

`logrotate` 做日志轮转：按大小/时间切分、压缩、保留 N 份、轮转后重启或发信号让进程重新打开日志文件。配置在 `/etc/logrotate.d/`。关键点：轮转后进程要能重新打开文件（copytruncate 或 postrotate 发 HUP 信号），否则进程还在写旧文件句柄。排查日志爆盘先 `du -sh /var/log/*` 定位哪个日志，再检查为何快速增长（攻击、异常、debug 级别没关）。

**问题 15：如何做系统级性能基准测试 / 压测？**

先明确测什么维度：(1) CPU 计算——`sysbench cpu` 或 `stress`；(2) 内存——`sysbench memory`；(3) 磁盘 IO——`fio`（最专业，可配 IOPS/吞吐/随机/顺序）；(4) 网络——`iperf3` 测带宽、`wrk`/`ab` 测 HTTP 并发。压测要点：控制变量（一次只压一个维度）、预热、多次取中位数、记录基线对比优化前后。别在生产高峰期压测。

**问题 16：内核参数调优有什么坑？**

三大坑：(1) 盲目照抄网上参数——不同内核版本、不同业务，参数最优值不同，先测再调；(2) 只改不验证——调完要看指标有没有真改善，甚至更差；(3) 持久化不一致——`sysctl -w` 只改运行时，重启丢失，要同步写 `/etc/sysctl.conf` 或 `/etc/sysctl.d/`。调内核参数的原则：理解每个参数的含义和副作用，一次改一个，留基线对比。

**问题 17：怎么保证系统安全 / 做安全加固？**

按「最小权限 + 基线 + 纵深防御」：(1) 账户——禁用 root 远程登录、密钥替代密码、sudo 精细授权、定期清理离职账号；(2) 服务——最小化安装、关无用服务、防火墙白名单只开必要端口；(3) 系统——及时打补丁、开启 auditd 审计、配置 logrotate 保留日志；(4) 数据——敏感数据加密、定期备份并验证可恢复。加固完用基线扫描工具（如 CIS benchmark、lynis）核对。

**问题 18：如何做性能优化的「四维」快速判断？**

拿到「系统慢」先跑四条命令各看一眼：`top`（CPU 和负载）、`free -h`（内存和 swap）、`iostat -xz`（磁盘）、`sar -n DEV` 或 `ss -s`（网络）。哪个维度饱和（利用率到顶或有错误）就先优化哪个。多数「慢」是磁盘 IO 或内存换页导致的，CPU 反而不是最先到顶的。判断要快、方向要对，避免在错误维度上浪费时间。

**问题 19：uptime 的 load 值比 CPU 核数还大很多，一定是问题吗？**

不一定，要结合趋势和阻塞进程判断。load 是「排队进程数」，瞬时高可能是短时间任务洪峰（如启动时并发编译），关键看是否持续。用 `vmstat 1` 观察 `r`（运行队列）和 `b`（阻塞队列）：`r` 持续大于核数 = CPU 确实忙不过来；`b` 大 = IO 等待。趋势上 1 分钟 > 15 分钟说明正在恶化，需介入；反过来说明高峰已过。

**问题 20：作为运维，你如何设计一套故障预警？**

核心是「指标 + 阈值 + 分级 + 通知」：(1) 采集——用监控系统（Prometheus/Zabbix）采集 CPU/内存/磁盘/网络/应用指标；(2) 阈值——基于基线设多级阈值（警告/严重），关键指标（磁盘 85%/90%、可用内存、磁盘 await）优先；(3) 分级——按影响面分 P0-P3，P0 立即通知（电话/短信），低级别聚合后通知；(4) 通知——告警去重、降噪，避免告警风暴；(5) 联动——关键告警可触发自动恢复（如磁盘满自动清理、服务挂了自动重启）。预警的价值在「故障前发现」而非「故障后通知」。

## 最佳实践与踩坑记录

### 最佳实践

1. 排错先看日志和指标，别上来就重启——重启会销毁现场，掩盖根因
2. 建立性能基线，优化前后对比，否则不知道改没改好
3. 用 logrotate + 集中日志，避免日志爆盘、便于事后追溯
4. 关键服务配高可用（消除单点）+ 监控告警（故障可发现），定期演练验证切换
5. 安全加固按基线执行并定期扫描，别「装完就忘」
6. 故障复盘沉淀成文档和 action item，同类问题不犯第二次

### 踩坑记录

```text
坑 1：把 free 低当成内存不足，盲目加内存
结论：free 低往往是 page cache 占用，加内存浪费钱。
原因：只看 free 字段，没看 available 和 swap 活动。
解法：判断内存看 available + vmstat 的 si/so，cache 不用手动清。

坑 2：清日志用 rm，导致磁盘空间不释放
结论：rm 删了文件但空间没回来，df 还是满。
原因：进程还持有被删文件的句柄，inode 没释放。
解法：清日志用 > file（清空）或 logrotate，已删未释放用 lsof | grep deleted 找进程重启。

坑 3：重启服务掩盖故障现场
结论：重启后服务恢复了，但根因没找到，问题会再犯。
原因：没有先保留现场（日志、状态、栈）就重启。
解法：先抓 jstack/pstack/日志/dmesg 留证，再重启恢复。

坑 4：盲目调内核参数
结论：照抄网上 sysctl 参数，性能反而更差或引发新问题。
原因：参数值和内核版本/业务强相关，不理解含义就乱改。
解法：理解每个参数副作用，一次改一个，改后测指标验证。

坑 5：内存泄漏排查只看 ps 的 VSZ
结论：VSZ（虚拟内存）大不代表泄漏，误判。
原因：VSZ 包含共享库映射，RSS（常驻内存）才是真实占用。
解法：看 RSS 随时间趋势，Java 看 Full GC 后老年代增长。

坑 6：磁盘满了只 df 不 df -i
结论：df 显示还有空间，但写文件报 No space left on device。
原因：inode 耗尽（小文件太多），数据块没满。
解法：同时看 df -h 和 df -i，inode 满要清理小文件或调整 inode 分配。
```
