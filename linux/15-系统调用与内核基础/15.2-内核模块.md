## 概述

内核模块（Loadable Kernel Module，LKM）是「可动态加载的内核代码」——设备驱动、文件系统、网络协议、安全模块（LSM）都能做成模块，需要时加载（modprobe）、不用时卸载（rmmod），**不必重新编译整个内核**。这样内核保持精简、启动快、内存省，功能按需扩展；厂商驱动（NVIDIA、网卡）也以模块形式分发，用户换内核后重编译即可，不用等发行版重新打包内核。

```text
内核模块四要素：
1. 加载/卸载 —— modprobe 加载、modprobe -r/rmmod 卸载，动态增减内核功能
2. 依赖 —— 模块之间有依赖链，modprobe 自动按序加载，insmod 不会
3. 存放 —— /lib/modules/<内核版本>/ 下，每个内核版本一套（.ko 或 .ko.zst）
4. 生命周期 —— module_init 初始化、module_exit 清理，内核引用计数防止误卸
```

本机实测环境：Ubuntu 24.04.4 LTS，内核 `7.0.0-28-generic`（x86_64），kmod 31（modprobe/depmod 同版本），内核头文件已装（`/usr/src/linux-headers-7.0.0-28-generic`），可现场编译加载 hello.ko。

## 核心概念

### 1. 命令族分工

| 命令 | 作用 | 依赖处理 | 适用场景 |
|---|---|---|---|
| `lsmod` | 列出已加载模块（含 Size/Used by） | — | 日常查看 |
| `modprobe <名>` | 按名字加载模块 | **自动**（读 modules.dep） | **推荐**，日常加载 |
| `modprobe -r <名>` | 按名字卸载 | 反向处理依赖 | **推荐**，日常卸载 |
| `insmod <路径>.ko` | 直接加载指定文件 | 不处理 | 加载自编译/特定路径模块 |
| `rmmod <名>` | 直接卸载 | 不处理 | 卸载简单模块 |
| `depmod` | 生成/更新 modules.dep | — | 装新模块后运行 |
| `modinfo <名>` | 查看模块元信息 | — | 查依赖/参数/vermagic |
| `modprobe --show-depends` | 预演会加载的依赖链 | 只显示不加载 | 排查依赖 |

### 2. 模块依赖与引用计数

模块之间可以互相引用符号（函数/变量），A 用到 B 导出的符号，A 就依赖 B。内核为每个模块维护**引用计数**（`lsmod` 的 Used by 列）：引用数非 0 时拒绝卸载，防止「正在被用的代码被卸掉导致内核崩溃」。

```text
实测（本机 lsmod 节选）：
nvidia_drm        139264  1
nvidia_modeset   1683456  1 nvidia_drm
nvidia         105349120  3 nvidia_uvm,nvidia_drm,nvidia_modeset
# nvidia 是最大的模块（约 105MB），被 3 个模块引用；
# 想卸载 nvidia 必须先卸载 nvidia_uvm / nvidia_drm / nvidia_modeset
```

### 3. vermagic：模块与内核的「指纹匹配」

每个模块编译时写入构建它的内核版本与特性（`modinfo -F vermagic` 可查），加载时内核逐项比对：

```text
vermagic（本机实测）：
7.0.0-28-generic SMP preempt mod_unload modversions
```

版本号、SMP、preempt、modversions 任何一项不匹配，加载直接失败（`Invalid module format`）——这是「升级内核后驱动失效」的根本原因。

### 4. DKMS 与 akmod：跨内核自动重编译

DKMS（Dynamic Kernel Module Support）：注册模块源码，内核升级后自动为新内核重新编译，保证驱动跟手。典型场景：NVIDIA 驱动、VirtualBox 内核模块、ZFS。

```text
DKMS 生命周期：dkms add（注册源码）→ dkms build（编译）→ dkms install（装进 /lib/modules）
内核升级时 dkms 自动为新内核 build + install（通过 /etc/kernel/postinst.d/dkms 钩子）
```

Red Hat 系对应物是 **akmod**（akmods 服务自动编译出 kmod 包）——机制类似，命令不同（见下文 Red Hat 差异对照表）。

### 5. 模块签名与 Secure Boot

内核可配置只加载「带有效签名的模块」：模块文件尾部附加签名（`modsign` 工具链），加载时用内嵌公钥验签。UEFI Secure Boot 开启时，Ubuntu 强制所有模块签名（用 shim/MOK 签名的第三方模块）。本机实测 `mokutil --sb-state` 输出 `SecureBoot disabled`，所以可以加载未签名模块（加载后内核被标记 tainted）。

### 6. taint（内核被「污染」标记）

加载了非 GPL、树外、未签名的模块后，内核打上 taint 标记，体现在 `/proc/sys/kernel/tainted` 位图和 `dmesg` 的 "Tainted" 字样——**内核出问题时官方维护者会先怀疑 tainted 模块**。

```text
实测（本机加载自编译 hello.ko 后）：
$ cat /proc/sys/kernel/tainted
12289          # = 1（专有/非GPL？） + 4096（树外模块） + 8192（未签名模块）
$ cat /sys/module/hello/taint
OE             # O = Out-of-tree（树外），E = unsigned（未签名）
```

### 7. 模块参数

模块可以声明参数（`module_param`），加载时通过 `modprobe <模块> 参数=值` 或 `/etc/modprobe.d/*.conf` 的 `options` 行传入，运行时可在 `/sys/module/<名>/parameters/` 查看/修改（若权限位允许）。

## 工作原理

### 模块加载完整流程

```text
modprobe nvidia_drm
  ├─ 1. 解析命令行与 /etc/modprobe.d/*.conf（blacklist/options/alias/install 指令）
  ├─ 2. 查 /lib/modules/$(uname -r)/modules.dep 得到依赖链（本机 nvidia_drm 依赖 6 个模块）
  ├─ 3. 按依赖顺序逐个 insmod 加载 .ko（压缩的 .ko.zst 先解压）
  ├─ 4. 每个模块走内核 init_module/finit_module 系统调用（这就是 [[15.1-系统调用]] 里的系统调用！）
  │      └─ 内核：校验 vermagic/签名 → 分配模块内存 → 解析符号（undefined→已加载模块导出表）→
  │              执行 module_init 函数（如注册驱动、创建 /dev 节点）→ 引用计数=1
  └─ 5. 全部成功后返回；任一失败则回滚已加载的依赖
```

```text
实测（本机）：
$ modprobe --show-depends nvidia_drm
insmod /lib/modules/7.0.0-28-generic/kernel/drivers/platform/wmi/wmi.ko.zst
insmod /lib/modules/7.0.0-28-generic/kernel/drivers/acpi/video.ko.zst
insmod /lib/modules/7.0.0-28-generic/kernel/drivers/gpu/drm/ttm/ttm.ko.zst
insmod /lib/modules/7.0.0-28-generic/kernel/drivers/gpu/drm/drm_ttm_helper.ko.zst
insmod /lib/modules/7.0.0-28-generic/kernel/nvidia-580/nvidia.ko NVreg_PreserveVideoMemoryAllocations=1 NVreg_TemporaryFilePath=/var
insmod /lib/modules/7.0.0-28-generic/kernel/nvidia-580/nvidia-modeset.ko
# 注意：nvidia.ko 后面的参数来自 /etc/modprobe.d/ 的 options 配置——modprobe 自动带入
```

卸载是反向流程：`modprobe -r` 检查引用计数（Used by 非 0 拒绝）→ 执行 module_exit → 释放资源 → 从内核符号表摘除。

### modules.dep 与 depmod

`depmod` 扫描 `/lib/modules/<ver>/kernel/` 下所有模块，解析每个模块的 `.modinfo` 段里的 depends 字段，生成依赖索引：

```text
# 实测：/lib/modules/7.0.0-28-generic/modules.dep（本机共 6908 行）
$ head -c 400 /lib/modules/$(uname -r)/modules.dep
kernel/arch/x86/events/amd/amd-uncore.ko.zst:
kernel/arch/x86/events/intel/intel-cstate.ko.zst:
kernel/arch/x86/events/rapl.ko.zst:
kernel/arch/x86/kernel/cpu/mce/mce-inject.ko.zst:
kernel/arch/x86/kernel/msr.ko.zst:
kernel/arch/x86/kernel/cpuid.ko.zst:
kernel/arch/x86/crypto/twofish-x86_64.ko.zst: kernel/crypto/twofish_common.ko.zst
kernel/arch/x86/crypto/twofish-x86_64-3way.ko.zst: kernel/arch/x86/crypto/twofish_common.ko.zst
# 格式：模块路径 : 它依赖的模块路径（冒号分隔）
# 无依赖的模块后面直接跟冒号（空依赖）
```

手写/安装第三方 .ko 到 `/lib/modules/$(uname -r)/extra/` 后必须跑 `depmod -a` 更新索引，否则 modprobe 按名字找不到。

### 符号解析与 EXPORT_SYMBOL

模块引用其他模块/内核导出的符号。内核只导出显式声明过的符号（`EXPORT_SYMBOL` / `EXPORT_SYMBOL_GPL`），`/proc/kallsyms` 可查看。加载时未解析符号会报 `Unknown symbol`。

### 自动加载：modules.alias 与 udev

模块除了手动加载，还能按**设备热插拔**自动加载：模块声明 alias（如 `alias char-major-10-234`、PCI ID 通配），`modules.alias` 索引了这些映射；udev 检测到新设备时用设备属性查 alias → 调用 modprobe。所以插上 U 盘、网卡，驱动「自动」就位。

```text
实测（本机 modules.alias 头部）：
# Aliases extracted from modules themselves.
alias cpu:type:x86,ven0000fam0012mod0003:feature:* intel_cstate
alias cpu:type:x86,ven0000fam0006mod00CC:feature:* intel_cstate
# 格式：alias <设备匹配模式> <模块名>
```

### 模块文件：压缩与目录结构

现代 Ubuntu（kmod 31）模块默认 ZSTD 压缩（`.ko.zst`），省磁盘、加载时解压：

```text
实测（本机）：
$ find /lib/modules/$(uname -r) -name '*.ko' | wc -l        # 未压缩：5 个
$ find /lib/modules/$(uname -r) -name '*.ko.zst' | wc -l    # ZSTD 压缩：6903 个
```

```text
/lib/modules/$(uname -r)/ 目录（实测）：
build/              → 符号链接到 /usr/src/linux-headers-<ver>（编译模块用）
kernel/             → 模块本体（按 arch/fs/drivers/net/... 分类）
modules.dep(.bin)   → 依赖索引（modprobe 读 .bin 二进制版）
modules.alias(.bin) → 设备别名→模块索引（udev 自动加载用）
modules.builtin     → 编译进内核的模块列表（这些「模块」无法卸载）
modules.devname     → 模块创建的 /dev 设备名映射
modules.softdep     → 软依赖（加载顺序提示）
modules.symbols     → 符号→模块索引（Unknown symbol 排查用）
initrd/             → initramfs 里的模块副本
```

## 常用命令与配置

### 命令速查

```shell
lsmod                              # 查看已加载模块 + 依赖
modprobe nvidia                    # 加载（自动处理依赖，推荐）
modprobe -r nvidia                 # 卸载（反向处理依赖，推荐）
insmod /path/to/hello.ko           # 直接加载 .ko 文件（不管依赖）
rmmod hello                        # 按名字卸载
modinfo nvidia                     # 模块全部信息
modinfo -F depends btrfs           # 只看依赖
modinfo -F vermagic btrfs          # 只看内核指纹
modprobe --show-depends nvidia_drm # 预演依赖链（不实际加载）
depmod -a                          # 重建 modules.dep（装新模块后必须）
modprobe -c | grep -i blacklist    # 查看生效的黑名单/配置
```

### Red Hat 系差异对照

| 项目 | Ubuntu（实测） | Red Hat / Fedora |
|---|---|---|
| 内核包 | `linux-image-<ver>` / `linux-image-generic` | `kernel` / `kernel-core` |
| 内核头文件包 | `linux-headers-<ver>`（/usr/src/linux-headers-...） | `kernel-devel`（/usr/src/kernels/...） |
| 模块编译目标目录 | `/lib/modules/$(uname -r)/build`（符号链接） | 同左（指向 kernel-devel） |

| 模块压缩 | `.ko.zst`（ZSTD，kmod 31 实测） | RHEL9 同样 ZSTD |
| 强制访问控制 | AppArmor（默认启用） | SELinux（默认 enforcing） |

## 配置文件解析

### /etc/modprobe.d/*.conf —— modprobe 行为配置

Ubuntu 默认就有十几个配置文件（实测列表）：`alsa-base.conf`、`blacklist.conf`、`blacklist-rare-network.conf`、`iwlwifi.conf`、`nvidia-graphics-drivers-kms.conf` 等。核心指令：

```text
blacklist <模块名>      # 黑名单：阻止自动/按名加载（如 blacklist nouveau）
options <模块> <参数>   # 给模块传固定参数（如 options nvidia NVreg_DynamicPowerManagement=0x02）
alias <别名> <模块>     # 别名映射（设备名 → 模块）
install <模块> <命令>   # 加载该模块时执行自定义命令
softdep <模块> pre/post: <其他模块>   # 声明软依赖/加载顺序
```

```text
实测（/etc/modprobe.d/alsa-base.conf 节选——install 指令的真实用法）：
# autoloader aliases
install sound-slot-0 /sbin/modprobe snd-card-0
install sound-slot-1 /sbin/modprobe snd-card-1
...
install snd /sbin/modprobe --ignore-install snd $CMDLINE_OPTS && { /sbin/modprobe --quiet --use-blacklist snd-ioctl32 ; ... }
# install 指令可做「加载 A 时顺带加载 B」「对参数做条件处理」等复杂编排
```

```text
实测（/etc/modprobe.d/nvidia-graphics-drivers-kms.conf）：
# 内容是 nvidia_drm modeset=1 的 options 行（KMS 支持），
# 这就是 modprobe --show-depends 里看到 NVreg_* 参数之外的另一个 options 来源
```

### /etc/modules 与 /etc/modules-load.d/ —— 开机加载

```text
实测（/etc/modules，Ubuntu 已废弃但仍兼容）：
# /etc/modules is obsolete and has been replaced by /etc/modules-load.d/.
# Please see modules-load.d(5) and modprobe.d(5) for details.

实测（/etc/modules-load.d/modules.conf，cups 装的并行打印机驱动）：
lp
ppdev
parport_pc
# 开机时按此列表加载（每行一个模块名，可带参数）
```

### /lib/modules/<ver>/ —— 模块索引文件

见「工作原理」一节的目录结构。关键文件用途：`modules.dep`（依赖）、`modules.alias`（自动加载）、`modules.builtin`（编译进内核的「伪模块」）、`modules.softdep`（软依赖）。**这些文件由 depmod 生成，新装 .ko 后必须 `depmod -a` 重建**。

### initramfs —— 启动早期要用的模块

根文件系统所在的驱动（磁盘控制器、文件系统、LUKS 解密）必须放进 initramfs，否则内核挂不上根分区。相关文件：`/etc/initramfs-tools/`（Ubuntu），`update-initramfs -u` 重建；Red Hat 用 `dracut -f`。

```text
实测（本机 /boot）：
initrd.img-6.17.0-14-generic
initrd.img-6.17.0-40-generic
initrd.img-7.0.0-28-generic
# 每个内核版本一个 initrd.img；改动黑名单后要 update-initramfs -u 让它生效
```

## 应用场景实战

### 场景一：加载/卸载一个驱动模块（NVIDIA 示例）

```shell
# 1. 当前状态
lsmod | grep nvidia
# 2. 加载（自动处理依赖，参数来自 modprobe.d）
modprobe nvidia
# 3. 验证：已加载 + 依赖链 + 参数生效
lsmod | grep nvidia
modinfo -F depends nvidia_drm
cat /sys/module/nvidia/parameters/NVreg_PreserveVideoMemoryAllocations
# 4. 卸载（反向卸载依赖，先卸引用它的）
modprobe -r nvidia_drm nvidia_modeset nvidia_uvm nvidia
```

### 场景二：编写、编译、加载一个 Hello World 模块（本机完整实测）

本机内核头文件已装（`/usr/src/linux-headers-7.0.0-28-generic`），以下全部真实执行成功。

```shell
# 1. 源码 hello.c（带一个 int 参数 hello_count）
```

```c
#include <linux/init.h>
#include <linux/module.h>
#include <linux/kernel.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Study Notes");
MODULE_DESCRIPTION("A simple Hello World kernel module");
MODULE_VERSION("1.0");

static int hello_count = 1;
module_param(hello_count, int, 0644);
MODULE_PARM_DESC(hello_count, "how many times to print hello");

static int __init hello_init(void)
{
    int i;
    for (i = 0; i < hello_count; i++)
        pr_info("Hello, kernel! (init, count=%d)\n", hello_count);
    return 0;
}

static void __exit hello_exit(void)
{
    pr_info("Goodbye, kernel! (exit)\n");
}

module_init(hello_init);
module_exit(hello_exit);
```


要点：模块代码运行在**内核态**，`printk`/`pr_info` 只能进 dmesg；`__init`/`__exit` 标记的函数加载/卸载后即释放；`MODULE_LICENSE("GPL")` 影响可用的内核符号范围（GPL-only 符号）。

### 场景三：模块参数传递（modprobe options 两种途径）

```shell
# 方式 1：命令行临时传参
modprobe hello hello_count=5
# 方式 2：配置文件固定传参（开机/每次 modprobe 都生效）
echo 'options hello hello_count=7' > /etc/modprobe.d/hello.conf
modprobe hello && cat /sys/module/hello/parameters/hello_count   # 显示 7
# 方式 3：运行时修改（模块声明参数时权限位 0644 才允许）
echo 9 > /sys/module/hello/parameters/hello_count
```

注意：**insmod 不读 /etc/modprobe.d/options**——只有 modprobe 会合并配置文件参数（实测 `modprobe --show-depends nvidia_drm` 输出里 NVreg_* 参数就是 modprobe 带入的）。

### 场景四：禁用冲突驱动（blacklist + initramfs）

```shell
# 场景：装了闭源 NVIDIA 驱动，开源 nouveau 老是先加载抢设备
echo 'blacklist nouveau' > /etc/modprobe.d/blacklist-nouveau.conf
# 若 nouveau 在 initramfs 里被提前加载，还要重建 initramfs
update-initramfs -u        # Ubuntu
# dracut -f                # Red Hat
# 验证：
modprobe -c | grep -i nouveau   # 能看到 blacklist nouveau
reboot && lsmod | grep nouveau  # 重启后不再加载
```

### 场景五：DKMS 管理第三方驱动（显卡场景）

```shell
# 1. 查看 DKMS 状态（实测本机：无输出 = 当前无 DKMS 注册模块）

# 4. NVIDIA 驱动包（nvidia-driver-580）自带 dkms.conf，/usr/src/nvidia-580.173.02 是源码位置（本机实测）
```

## 性能与调优

```text
1. 按需加载 —— 内核保持精简，常驻内存小；模块用到才加载（本机 nvidia 模块约 105MB，不用 GPU 可省下）
2. 禁用无用模块 —— blacklist 掉用不到的驱动（声卡/读卡器/无线网卡），减少启动时间与内存占用
3. 模块参数调优 —— options 调整驱动行为：网卡中断合并（如 igb 的 InterruptThrottleRate）、
   显卡功耗管理（NVreg_DynamicPowerManagement=0x02 省电）、NVMe 队列数等
4. 压缩模块 —— .ko.zst 省磁盘省启动读取时间（解压比读盘快），Ubuntu/RHEL9 默认已开
5. 减少 initramfs 体积 —— 只放启动必需模块（磁盘/文件系统/LUKS），加快开机
6. 驱动选型 —— 同一设备多驱动（nouveau vs nvidia）时 blacklist 冲突方，避免反复 probe 浪费启动时间
7. 热插拔自动加载 —— 依赖 udev + modules.alias 按需自动加载，别把全部驱动写进开机加载列表
```

调优前先量化：`systemd-analyze blame` 看启动慢在哪；`dmesg` 看模块初始化耗时（`[时间戳]` 前缀）。

## 安全与权限

```text
1. 加载/卸载模块要 root —— init_module/delete_module 是特权系统调用（[[15.1-系统调用]]），
   普通用户无法加载模块（这是内核的底线防线之一：恶意模块 = 内核级后门）
2. 模块签名校验 —— 内核可开启 CONFIG_MODULE_SIG_FORCE：只加载带有效签名的模块；
   Secure Boot 开启时（mokutil --sb-state 可查，本机实测 disabled）强制签名，
   第三方模块需用 MOK（Machine Owner Key）签名进 firmware 信任链
3. taint 标记 —— 非 GPL/树外/未签名模块加载后内核标记 tainted（实测 12289/OE），
   出问题官方不背锅；生产环境尽量用发行版签名模块
4. 只加载可信来源 —— 模块是内核态代码，来源不明的 .ko 能读全部内存、装 rootkit；
   /proc/modules 检查异常模块、rkhunter/chkrootkit 可辅助排查
5. 缩小攻击面 —— blacklist 不需要的驱动（如各种 usb 存储/网络驱动），
   防止「插上恶意设备自动加载驱动」类攻击（BadUSB 场景）
6. AppArmor/SELinux 差异 —— Ubuntu 默认 AppArmor；RHEL 默认 SELinux enforcing，
   SELinux 可能阻止加载特定模块/访问 /sys/module，出现诡异权限错误先查
   audit2why / ausearch（RHEL）或 aa-status（Ubuntu）
7. 内核崩溃风险 —— 模块代码 bug（空指针、越界）直接 oops/panic 整个系统，
   开发调试模块用虚拟机，别在生产机直接 insmod
```

## 故障排查

### 案例一：modprobe 报 FATAL: Module xxx not found

```shell
modprobe xxx
# modprobe: FATAL: Module xxx not found in directory /lib/modules/7.0.0-28-generic
# 排查顺序：
# 1. 模块确实存在吗？（名字/路径）
find /lib/modules/$(uname -r) -name 'xxx*'
# 2. 存在但 modprobe 找不到 → depmod 索引过期（手放 .ko 没跑 depmod）
depmod -a && modprobe xxx
# 3. 不存在 → 模块没装/内核版本不对：装对应包（如 linux-modules-extra-$(uname -r)）
apt install linux-modules-extra-$(uname -r)    # Ubuntu
# dnf install kernel-modules-extra              # RHEL
# 4. 被 blacklist 了 → modprobe -c | grep xxx
```

### 案例二：加载报 Unknown symbol（依赖/符号缺失）

```text
$ insmod ./mymod.ko
insmod: ERROR: could not insert module mymod.ko: Unknown symbol in module
# 原因：模块引用了未加载模块导出的符号（insmod 不处理依赖），或符号不存在/未导出
# 排查：
modinfo -F depends mymod.ko        # 看它声明依赖谁
modprobe --show-depends mymod      # 让 modprobe 算依赖链（应优先用 modprobe 加载）
grep <符号名> /proc/kallsyms       # 符号是否已加载/导出（exported 标记）
# 解法：用 modprobe 代替 insmod；缺依赖模块先加载；符号未导出则改源码用 EXPORT_SYMBOL
```

### 案例三：vermagic 不匹配 / Invalid module format

```text
$ insmod ./hello.ko
insmod: ERROR: could not insert module hello.ko: Invalid module format
# 内核日志（dmesg）会给出具体差异：
version magic '6.8.0-45-generic SMP preempt mod_unload modversions' should be '7.0.0-28-generic ...'
# 原因：模块编译时的内核版本 ≠ 当前内核（升级内核后旧 .ko 直接失效）
# 排查/解法：
uname -r                     # 当前内核
modinfo -F vermagic ./hello.ko   # 模块编译时内核
# 重新编译：make clean && make（用当前内核头文件）
# 第三方驱动：装 dkms/akmod 版，自动跟随内核重编译
```

### 案例四：模块加载成功但设备不工作

```shell
# 1. 确认模块状态
lsmod | grep <mod>
# 2. 内核日志里模块的初始化输出（有没有 probe 失败、firmware 缺失）
dmesg | grep -i <mod>
# 常见错误：firmware 文件缺失（iwlwifi 需要 .ucode）、
#          参数错误（options 拼错名被忽略）、设备被别的驱动占用
# 3. 设备节点/硬件识别
ls -l /dev/<设备>
lspci -k | grep -A2 <设备名>      # 看哪个驱动绑定了 PCI 设备
# 4. udev 没触发 → 手动 modprobe 后看 /sys/bus/<bus>/devices/ 下 binding
```

### 案例五：rmmod 失败 Device or resource busy

```text
$ rmmod nvidia
rmmod: ERROR: Module nvidia is in use by: nvidia_uvm,nvidia_drm,nvidia_modeset
# 解法：按依赖反向卸载（先卸引用它的）
modprobe -r nvidia_drm nvidia_modeset nvidia_uvm nvidia
# 或强制（危险，仅调试）：rmmod -f —— 会撕裂依赖，内核可能崩溃，生产禁用
# 查引用者：lsmod | grep <mod>；/sys/module/<mod>/holders/ 里是持有者
```

### 案例六：模块签名校验失败（Secure Boot 环境）

```text
$ insmod ./mymod.ko
insmod: ERROR: could not insert module mymod.ko: Required key not available
# 原因：Secure Boot 开启 + 内核强制签名校验，未签名/未入信任链的模块被拒
# 排查：
mokutil --sb-state                 # 确认 Secure Boot 状态（本机实测 disabled）
mokutil --list-enrolled            # 看已登记的 MOK 公钥
# 解法（三选一）：
# 1. 给模块签名并登记 MOK：/usr/src/linux-headers-*/scripts/sign-file sha256 <key> <cert> mymod.ko
#    （MOK 登记需在固件界面/ MokManager 完成）
# 2. 关闭 Secure Boot（本机已关闭，实测可加载未签名模块）
# 3. 用发行版仓库里的签名模块
```

## 常见问题

```text
Q1: insmod 加载模块报 Unknown symbol？
A: 模块有依赖，insmod 不处理依赖。用 modprobe（自动加载依赖链）；
   仍失败则查 /proc/kallsyms 确认符号是否已加载且被导出。

Q2: modprobe 报 Module not found？
A: 模块不在当前内核的 /lib/modules 目录。确认 uname -r 与模块所属内核版本一致；
   手放 .ko 后记得 depmod -a；发行版模块装对应 linux-modules-extra 包。

Q3: 卸载正在使用的模块会怎样？
A: rmmod 会直接拒绝（Device or resource busy）；强卸（rmmod -f）可能导致
   内核崩溃/数据损坏。lsmod 看 Used by，先卸载引用它的模块。

Q4: 升级内核后驱动模块失效？
A: 模块与内核版本强绑定（vermagic 指纹）。用 dkms/akmod 版驱动自动重编译，
   或等厂商适配后装新版本。内核升级后 /lib/modules/ 下是全新一套。

Q5: blacklist 了模块还是被加载？
A: ① 模块可能被编译进内核（modules.builtin，无法 blacklist）；
   ② initramfs 里提前加载了它 → update-initramfs -u（Ubuntu）/ dracut -f（RHEL）；
   ③ 配置文件没生效 → modprobe -c 确认能看到 blacklist 行。

Q6: 编译模块报 linux/init.h 找不到？
A: 没装内核头文件。Ubuntu：apt install linux-headers-$(uname -r)；
   RHEL：dnf install kernel-devel-$(uname -r)。装完确认 /lib/modules/$(uname -r)/build
   存在（符号链接到头文件目录）。

Q7: modprobe 传的参数没生效？
A: ① 参数名拼错（大小写敏感），modprobe 会警告 ignored；
   ② 用 insmod 加载时不读 /etc/modprobe.d/options（只有 modprobe 读）；
   ③ 参数权限位（module_param 第三参 0644）决定能否运行时改；
   ④ 验证：cat /sys/module/<mod>/parameters/<参数>。

Q8: dmesg 看不到模块的 printk 输出？
A: ① dmesg_restrict=1 时普通用户被限制（用 root）；
   ② 输出被日志级别过滤：pr_debug 默认不打印（需动态调试）；
   ③ 看错了内核：dmesg 是当前内核的日志，模块输出时间戳在加载时刻附近。
```

## 面试题

```text
1. 什么是内核模块（LKM）？为什么需要它？
   答：可动态加载/卸载的内核代码，用于扩展驱动、文件系统、网络协议等功能。
   好处：内核保持精简、按需加载省内存、驱动可独立于内核版本分发
   （配合 DKMS 自动重编译），不必每次加功能都重新编译整个内核。

2. modprobe 和 insmod 的区别？
   答：modprobe 按名字加载，自动读 /lib/modules/$(uname -r)/modules.dep 解析依赖链、
   按序加载全部依赖，并合并 /etc/modprobe.d/ 的 options/blacklist 等配置；
   insmod 直接加载指定 .ko 文件，不处理依赖、不读配置，通常只用于自编译模块调试。
   卸载同理：modprobe -r 反向处理依赖，rmmod 不管。

3. lsmod 的 Used by 列是什么？有什么用？
   答：模块的引用计数来源（哪些模块在引用它）。为 0 表示无人使用可安全卸载；
   非 0 时卸载会被拒绝。依赖它的模块必须先卸。内核靠引用计数防止
   「正在执行的模块代码被卸载」导致崩溃。

4. 模块加载失败 Invalid module format / vermagic mismatch 是怎么回事？
   答：模块编译时写入构建内核的 vermagic（版本 + SMP/preempt/modversions 等特性），
   加载时与当前内核逐项比对，不一致即拒绝。常见于升级内核后使用旧 .ko。
   解法：用当前内核头文件重新编译，或用 DKMS/akmod 自动跟随内核重建。

5. 怎么编写一个最简单的内核模块？
   答：hello.c 里包含 linux/module.h，用 module_init()/module_exit() 注册
   初始化/清理函数，MODULE_LICENSE("GPL") 声明许可证；
   Makefile 用 obj-m += hello.o + KDIR=/lib/modules/$(uname -r)/build
   调用内核 Kbuild 编译出 hello.ko；insmod 加载（printk 输出进 dmesg）、
   rmmod 卸载（执行 module_exit）。

6. 模块加载的完整流程是什么？
   答：modprobe 解析配置 → 查 modules.dep 得依赖链 → 按序 insmod 各 .ko →
   内核 init_module 系统调用：校验 vermagic/签名 → 分配内存、解析未定义符号
   （从已加载模块的导出表）→ 执行 module_init → 注册设备/文件系统/协议 →
   引用计数置 1；任一环节失败则回滚已加载的依赖模块。

7. DKMS 和 akmod 是什么？解决什么问题？
   答：都解决「内核升级后第三方驱动失效」问题：源码注册后，每次内核升级自动
   为新内核重新编译安装模块。DKMS 是通用方案（dkms 命令，Ubuntu 常见，
   NVIDIA/VirtualBox 用它）；akmod 是 Fedora/RHEL 生态方案（akmods 服务自动
   把源码编译成 kmod 包安装）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 加载/卸载用 `modprobe` / `modprobe -r`（自动处理依赖），insmod 仅用于自编译模块调试
2. 查依赖用 `modinfo -F depends`，预演加载用 `modprobe --show-depends`
3. 模块加载失败先看 `dmesg`——真正的报错（vermagic、符号、firmware）都在内核日志里
4. 手放 .ko 后必须 `depmod -a`，否则 modprobe 按名字找不到
5. 每个内核版本一套模块：升级内核后统一重装/重编驱动（DKMS/akmod 自动）
6. 卸载前先 `lsmod | grep` 看 Used by，按依赖反向卸载，绝不 `rmmod -f`
7. 生产机只加载发行版签名模块；自编译模块先虚拟机验证再上生产
8. 改 blacklist/options 后：`modprobe -c` 验证 → 涉及 initramfs 的模块 `update-initramfs -u`（RHEL：`dracut -f`）

### 踩坑记录

```text
坑 1：insmod 加载模块报 Unknown symbol
结论：insmod 加载模块报未知符号错误，加载失败。
原因：模块有依赖，insmod 不处理依赖，依赖模块没加载。
解法：用 modprobe（自动加载依赖链）；仍失败查 /proc/kallsyms 确认符号已导出。

坑 2：modprobe 报 Module not found
结论：modprobe 加载模块提示找不到。
原因：模块不在当前内核的 /lib/modules 目录（内核版本不对/模块没装/索引过期）。
解法：uname -r 核对版本；手放 .ko 后 depmod -a；发行版模块装 linux-modules-extra。

坑 3：rmmod 正在使用的模块导致系统异常
结论：强行卸载被引用的模块，功能消失甚至内核崩溃。
原因：模块被使用（Used by 非 0），强卸撕裂依赖。
解法：lsmod 看 Used by，先卸载依赖它的模块；绝不 rmmod -f（调试机也别养成习惯）。

坑 4：升级内核后模块加载失败（Invalid module format）
结论：升级内核后，某些驱动模块加载不了。
原因：vermagic 指纹不匹配——旧 .ko 是旧内核编译的。
解法：确认驱动支持新内核；装 dkms/akmod 版本自动重编译；或等厂商适配。

坑 5：blacklist 没生效，模块还是加载了
结论：改了 /etc/modprobe.d/blacklist.conf，模块依旧被加载。
原因：模块在 initramfs 里被提前加载，或模块被编译进内核（modules.builtin）。
解法：update-initramfs -u（RHEL：dracut -f）重建 initramfs 后重启；
     内置模块无法 blacklist，只能换内核配置。

坑 6：编译模块报 linux/init.h 找不到
结论：make 报错找不到内核头文件。
原因：没装与当前内核匹配的 headers 包。
解法：Ubuntu 装 linux-headers-$(uname -r)；RHEL 装 kernel-devel-$(uname -r)；
     确认 /lib/modules/$(uname -r)/build 符号链接存在。

坑 7：模块参数没生效
结论：modprobe 传了参数，模块行为没变化。
原因：参数名拼错（被忽略）；用 insmod 加载（不读 /etc/modprobe.d/options）；
     参数权限位限制运行时修改。
解法：modprobe -c 确认 options 行；cat /sys/module/<mod>/parameters/<参数> 验证；
     用 modprobe 加载并核对参数名（module_param 声明名）。

坑 8：modprobe 的 options 和 insmod 加载行为不一致
结论：同一模块，modprobe 加载和 insmod 加载表现不同。
原因：只有 modprobe 合并 /etc/modprobe.d/ 的 options/install 配置。
解法：生产用 modprobe；调试 insmod 时参数显式写在命令行（insmod hello.ko hello_count=3）。

坑 9：dmesg 看不到模块输出，以为模块没执行
结论：insmod 成功但 dmesg 里没有模块的 printk。
原因：dmesg_restrict=1 限制普通用户读内核日志；pr_debug 默认不打印；
     或看错了时间段的日志。
解法：root 执行 dmesg；用 pr_info 而非 pr_debug 便于排查；dmesg --time-format iso 定位。

坑 10：SELinux 环境下模块相关操作报诡异权限错误
结论：RHEL 上加载模块/访问 /sys/module 报权限错误，root 也不行。
原因：SELinux enforcing 策略阻止（Ubuntu 是 AppArmor，一般不管模块加载）。
解法：ausearch -m avc 查拒绝记录；确认模块在允许列表；临时 setenforce 0 验证定位。
```
