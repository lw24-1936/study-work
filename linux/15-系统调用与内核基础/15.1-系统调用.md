## 概述

系统调用（system call，syscall）是「用户程序请求内核服务的唯一入口」。程序不能直接操作硬件（读磁盘、发网络包、申请内存页），必须通过系统调用把请求交给内核，由内核在最高特权级（内核态）代为完成。系统调用是用户态与内核态之间唯一的、受控的通道——没有它，任何用户程序都触碰不到硬件。

理解系统调用，是理解 Linux 的钥匙：程序「卡在哪」「慢在哪」「为什么打不开文件」「偷偷连了哪个服务器」——strace 一追便知。系统调用也是内核与用户空间的「契约」：系统调用号一旦分配就永不改变（ABI 稳定），所以 20 年前编译的二进制今天还能跑。

```text
系统调用三要素：
1. 用户态/内核态 —— CPU 特权级隔离：用户程序跑在 ring3（用户态），内核跑在 ring0（内核态）
2. 系统调用机制 —— 用户态通过 syscall 指令切入内核态请求服务，内核执行完再切回
3. strace —— 基于 ptrace 追踪程序发起的每个系统调用，定位卡点/失败/隐藏行为
```

本机实测环境：Ubuntu 24.04.4 LTS，内核 `7.0.0-28-generic`（x86_64），kmod 31，strace/ltrace 等工具可用（ltrace 未安装）。

## 核心概念

### 1. 用户态与内核态（特权级）

x86 CPU 有 4 个特权级（ring 0~3），Linux 只用两个：

```text
ring0 内核态 —— 能执行特权指令（in/out 端口、cli 关中断、写 CR3 页表基址），能访问全部内存和硬件
ring3 用户态 —— 普通程序运行的地方，只能访问自己的地址空间，特权指令直接执行会触发 #GP 异常被内核杀掉
```

当前特权级记录在 CS 段寄存器的低 2 位（CPL）。用户态程序一旦试图执行特权指令，CPU 抛出异常、陷入内核、内核检查权限后决定杀不杀——**权限检查在内核态完成，用户程序无法绕过**。

### 2. 系统调用机制

用户态→内核态的受控跳转有三种历史形态：

```text
int 0x80      —— 32 位时代的软中断方式，慢（要查中断门、压栈切栈）
sysenter/sysexit —— 早期快速系统调用指令（P4 时代）
syscall/sysret  —— 现代 x86-64 使用的快速系统调用指令
```

`syscall` 指令由 CPU 硬件完成：保存用户态 RIP 到 RCX、加载 MSR 里的内核入口地址（`MSR_LSTAR`）、切换特权级到 ring0、跳到内核统一入口 `entry_SYSCALL_64`。整个过程不再经过 IDT（中断描述符表），比 `int 0x80` 快一个数量级。

### 3. libc 封装（wrapper）

程序员几乎不会直接写 `syscall` 指令，而是调用 glibc 的封装函数：

```text
printf()  →  glibc stdio 缓冲  →  write() 封装  →  系统调用 write
read()    →  glibc 封装（直接对应系统调用 read，1:1）
fork()    →  glibc 封装（x86-64 上实际调 clone 系统调用）
malloc()  →  glibc 内部  →  brk/mmap 系统调用（不透明，程序员无感）
```

凡是「1:1 对应系统调用」的库函数（read/write/open/close/stat 等），glibc 封装只做一件事：把参数放进寄存器、执行 `syscall` 指令、把内核返回的负数错误码转成 `errno` 并返回 -1。凡是「比系统调用高一层」的库函数（printf/malloc/pthread 等），内部会组合、缓存、优化多次系统调用。

### 4. 系统调用号与 ABI

每个系统调用有固定编号（x86-64 从 0 开始），内核用编号查 `sys_call_table` 分发。编号定义在头文件里：

```text
/usr/include/x86_64-linux-gnu/asm/unistd_64.h   —— x86-64 系统调用号（用户态编译时用）
arch/x86/entry/syscalls/syscall_64.tbl          —— 内核源码里的编号表
```

**ABI 契约**：编号一旦分配永不修改、永不删除（最多标记 obsolete 不再使用），新调用只追加新号。这是 Linux 二进制向后兼容的根基——所以老程序在新内核上还能跑。

### 5. 返回值与 errno

内核返回值约定：成功返回非负值（0 或结果）；失败返回**负的 errno**（如 -2 = ENOENT）。glibc 封装负责：`如果 rax 在 [-4095, -1] 区间，把 -rax 写入 errno，函数返回 -1`。所以 C 代码里常见的 `if (fd < 0) perror(...)` 模式，错误细节在 errno 里。

### 6. vDSO / vsyscall

部分高频、只读不写的系统调用被内核直接映射到用户态地址空间（vDSO，virtual Dynamic Shared Object），**根本不陷入内核**：

```text
gettimeofday() / clock_gettime() / time() / getcpu()
```

进程地址空间的 `[vdso]` 映射就是它。实测验证：strace 追踪 `date`（内部调用 gettimeofday）时**看不到任何 gettimeofday 系统调用**——它由 vDSO 在用户态直接读内核共享的内存（含时钟源）算出，开销从 ~100ns 降到 ~20ns。

### 7. strace 与 ptrace

strace 不是内核功能，而是基于 ptrace 系统调用的用户态调试器：ptrace(PTRACE_TRACEME/PTRACE_SYSCALL) 让被追踪进程在每个系统调用的**进入和退出**时各停一次，strace 趁机读取寄存器（参数）和返回值。代价：被追踪进程慢 10~100 倍，生产环境慎用。

### 8. seccomp（安全过滤）

内核提供的系统调用过滤器：进程可以安装 BPF 规则，声明「我只允许调用 read/write/exit 等 N 个系统调用」，其余调用直接返回 EPERM 或被杀死。容器运行时（Docker 默认 profile）、浏览器沙箱（Chrome/Chromium）、systemd 服务（`SystemCallFilter=`）都用它收窄攻击面。

## 工作原理

### 一次系统调用的完整调用链

以 `printf("hello\n")` 为例，完整链路：

```text
用户程序 printf("hello\n")
  → glibc stdio：写入用户态缓冲区（此时无系统调用！）
  → 行缓冲刷出：调用 glibc write() 封装
      → 参数装入寄存器：rax=1（write 号） rdi=1（fd=stdout） rsi=buf rdx=6（长度）
      → 执行 syscall 指令（CPU 切到 ring0，跳到 MSR_LSTAR 指向的 entry_SYSCALL_64）
  → 内核：保存用户寄存器 → 查 sys_call_table[1] = __x64_sys_write
      → 执行 sys_write：找到 fd=1 对应文件对象 → 拷贝用户缓冲区 → 驱动/终端写出
  → 内核返回：rax=6（写入字节数）→ sysret 切回用户态
  → glibc 检查 rax：正常则 printf 返回
```

```text
流程图（竖版）：
┌─ 用户态 ─────────────────────────────┐
│ printf → glibc 缓冲 → write() 封装      │
│ rax=1, rdi=1, rsi=buf, rdx=6          │
│ syscall 指令 ────────────────┐        │
└──────────────────────────────┼────────┘
                               ▼
┌─ 内核态 ─────────────────────────────┐
│ entry_SYSCALL_64（保存寄存器）          │
│ sys_call_table[1] → __x64_sys_write   │
│ sys_write：fd→文件对象→拷贝→写出        │
│ 恢复寄存器，rax=6，sysret              │
└──────────────────────────────────────┘
```

### x86-64 传参约定（syscall ABI）

| 用途 | 寄存器 | 说明 |
|---|---|---|
| 系统调用号 | `rax` | 如 0=read、1=write、59=execve |
| 第 1 参数 | `rdi` | |
| 第 2 参数 | `rsi` | |
| 第 3 参数 | `rdx` | |
| 第 4 参数 | `r10` | **注意不是 rcx**（rcx 被 syscall 指令用于保存返回地址） |
| 第 5 参数 | `r8` | |
| 第 6 参数 | `r9` | |
| 返回值 | `rax` | 成功：非负；失败：负 errno（-2=ENOENT 等） |
| 入口地址 | `MSR_LSTAR` | syscall 指令跳转目标，内核启动时写入 |

普通函数调用约定用 rdi/rsi/rdx/**rcx**/r8/r9，系统调用第 4 个参数换成 r10——面试常考这个差异。

```text
4    stat          文件      取文件状态
5    fstat         文件      取 fd 状态
8    lseek         文件      移动读写位置
```

### vDSO 免陷入机制

```text
进程地址空间（/proc/self/maps，本机实测）：
77a61b98c000-77a61b990000 r--p ... [vvar]           ← 内核共享的只读数据（时钟源等）
77a61b990000-77a61b992000 r--p ... [vvar_vclock]
77a61b992000-77a61b994000 r-xp ... [vdso]           ← 可执行的 vDSO 代码
```

glibc 启动时检测到 vDSO 就把 `gettimeofday` 等函数指针指向 vDSO 实现。vDSO 代码只能做「读共享数据+简单计算」这类无副作用操作，所以只有时间类、getcpu 等少数调用受益。

### 系统调用开销

每次系统调用包含：特权级切换、寄存器保存/恢复、进入/退出内核路径（含 Meltdown 缓解后的 CR3/PCID 处理、retpoline 等）、可能的 TLB 和缓存污染。量级：**单次约 100ns~1μs**（远慢于普通函数调用的几 ns）。程序性能优化的一大主题就是「减少系统调用次数」。

## 常用命令与配置

### strace 常用选项

| 选项 | 作用 | 示例 |
|---|---|---|
| `-c` | 统计各系统调用次数/耗时占比 | `strace -c ls` |
| `-t` / `-tt` | 每行带时间戳（秒/微秒） | `strace -t -p 1234` |
| `-f` | 跟踪 fork/clone 出的子进程 | `strace -f ./server` |
| `-e trace=xxx` | 按类过滤：file/network/process/memory/signal/desc/ipc | `strace -e trace=network curl x` |
| `-e trace=openat,close` | 过滤指定调用（逗号分隔） | `strace -e trace=openat,connect app` |
| `-o 文件` | 输出写文件（避免刷屏） | `strace -o /tmp/trace.log app` |
| `-p PID` | 附加到运行中的进程 | `strace -p 1234` |
| `-s N` | 字符串参数截断长度（默认 32） | `strace -s 200 app` |
| `-T` | 显示每个调用耗时 | `strace -T -c app` |
| `-x` | 非 ASCII 字符串按十六进制显示 | `strace -x app` |
| `-y` | 打印 fd 对应的路径 | `strace -y app` |

```text
$ strace -e trace=gettimeofday,clock_gettime,clock_gettime64 date 2>&1 | head -6
2026年 08月 19日 星期三 13:00:52 CST
```

date 明明调用了 gettimeofday，但 strace 里一个相关系统调用都没有——全部被 vDSO 在用户态消化了。想验证「确实调了」要装 ltrace（本机未安装，包名 ltrace，RHEL 在 EPEL 仓库）。

```text
$ strace -e trace=connect,socket curl -s -o /dev/null https://example.com 2>&1 | grep AF_INET | head -3

socket(AF_INET6, SOCK_STREAM, IPPROTO_TCP) = 5
```

curl 优先走 IPv6（AF_INET6）、TCP 连接 443；`EINPROGRESS` 是非阻塞 connect 的正常返回（连接在后台继续），不是错误。

## 配置文件解析

系统调用本身没有「配置文件」，但它依赖的接口文件、策略文件都在下面，调试时按需查看：

```text
/usr/include/x86_64-linux-gnu/asm/unistd_64.h   系统调用号定义（用户态编译依赖）
/usr/include/asm-generic/unistd.h               通用编号（部分架构）
/proc/<pid>/syscall                             进程当前阻塞的系统调用（调试神器）
/proc/sys/kernel/yama/ptrace_scope              ptrace 权限策略（影响 strace 能否附加）
/proc/sys/kernel/                               ostype/osrelease/pid_max 等内核参数
/etc/sysctl.d/*.conf                            sysctl 参数持久化文件
```

### 实测：系统调用号头文件（本机）

```text
$ grep -E '__NR_(read|write|open|mmap|fork|execve|connect|openat)' \
      /usr/include/x86_64-linux-gnu/asm/unistd_64.h
#define __NR_read 0
#define __NR_write 1
#define __NR_open 2
#define __NR_close 3
#define __NR_mmap 9
#define __NR_connect 42
#define __NR_fork 57
#define __NR_execve 59
#define __NR_openat 257
```

### 实测：/proc/<pid>/syscall（本机 shell）

```text
$ cat /proc/self/syscall
0 0x3 0x7d4094c45000 0x20000 0x22 0x0 0x7d4094cbb440 0x7fff60487ec8 0x7d4094b1bb91
# 格式：系统调用号 参数1~6 栈指针 指令指针
# 第 1 个字段是 0 = read，即本 shell 正阻塞在 read(3, 0x7d4094c45000, 0x20000) 等输入
```

进程卡住时看这个文件，一行就知道它在等什么。注意：进程**空闲**时通常也阻塞在 read（等终端/管道），别看到 read 就以为卡了，要结合 wchan/fd 判断。

### ptrace_scope 策略值

```text
/proc/sys/kernel/yama/ptrace_scope（本机实测 = 1，Ubuntu/Debian 默认）
0 = 任意进程可被任意进程追踪（不推荐）
1 = 只能追踪自己的后代（默认；strace -p 别人的进程会 Permission denied）
2 = 仅 root（CAP_SYS_PTRACE）可追踪
3 = 完全禁止附加（连 root 也受限）
```

### 实测：/proc/sys/kernel/ 相关参数（本机）

```text
$ cat /proc/sys/kernel/ostype
Linux
$ cat /proc/sys/kernel/osrelease

$ cat /proc/sys/kernel/pid_max

$ sysctl kernel.pid_max kernel.hostname
```

## 应用场景实战

### 场景一：程序启动慢，定位瓶颈

```shell
# 1. 统计启动期间的系统调用分布
strace -c ./myapp
# 2. 看哪类调用多/耗时（实测 ls 的结果：getdents64 占 57% 时间、brk 占 26%）
# 3. 针对热点深入：getdents64 多 = 目录项读取（目录文件太多）
#    brk/mmap 多 = 内存分配频繁（动态库加载/对象创建）
#    openat 多 = 配置文件/库文件反复打开（可考虑合并配置、缓存句柄）
```

### 场景二：程序读了哪个配置文件（读取顺序排查）

```shell
# 追踪所有 open 类调用，看配置文件的实际查找路径和顺序
strace -e trace=openat,open ./myapp 2>&1 | grep -E '\.(conf|json|ini|yaml|toml|xml)'
# 输出按时间顺序排列，就是配置文件的「探测顺序」
# 注意：很多程序会先探测多个候选路径（ENOENT 是正常的），最后才命中
```

典型例子：nginx 启动时读 `/etc/nginx/nginx.conf` 里的 include 再展开读子配置；Java 程序读 `-Duser.home` 下的一堆 `.properties`。strace 一追，实际路径与顺序一目了然——「我以为它读 /etc/app.conf，其实它读的是 $HOME/.app.conf」。

### 场景三：程序隐藏的网络请求（连了谁、连了哪）

```shell
# 只看网络相关系统调用
strace -e trace=network ./myapp
# 或者只看 connect，快速看连了哪些地址
strace -e trace=connect ./myapp 2>&1 | grep -E 'sin_port|AF_INET'
# 实测 getent 的例子：DNS 查 127.0.0.53:53（systemd-resolved）
# 实测 curl 的例子：AF_INET6 连 2606:4700:10::ac42:93f3:443
```

排查「软件偷偷上传数据」「莫名其妙访问了某个 IP」就用这招：`strace -e trace=connect,openat -f ./可疑程序`，把地址全抓出来。

### 场景四：程序报「文件打不开」，找真实路径

```shell
strace -e trace=openat,open ./myapp 2>&1 | grep -i 'ENOENT'
```

```text
# 实测（本机）
$ strace -e trace=openat,open cat /nonexistent-file-xyz 2>&1 | grep nonexistent
openat(AT_FDCWD, "/nonexistent-file-xyz", O_RDONLY) = -1 ENOENT (没有那个文件或目录)
```

程序报错信息可能含糊（「无法打开资源」），但 strace 会精确给出它尝试的**完整路径**——经常发现是相对路径 + 工作目录不对，或权限不够（EACCES）。

### 场景五：附加到运行中的进程（定位卡点）

```shell
# 1. 看进程当前阻塞的系统调用（零开销，先来这步）
cat /proc/<PID>/syscall
# 2. 需要看历史调用再 strace 附加
strace -p <PID>
# 3. 带时间戳 + 只看某一类，减少干扰
strace -t -e trace=network -p <PID>
# 4. 看完 Ctrl-C 退出，进程不受影响
```

## 性能与调优

### 系统调用开销为什么贵

```text
一次系统调用 ≈ 100ns ~ 1μs，是普通函数调用（几 ns）的 10~100 倍：
1. 特权级切换（用户态↔内核态，MSR 读写、栈切换）
2. 寄存器保存/恢复（约 20+ 个寄存器）
3. 内核入口/出口路径（Meltdown 缓解后还要处理 CR3 切换、PCID、retpoline）
4. 缓存污染（内核代码/数据挤掉用户态缓存行）
5. 若被 strace 跟踪：每次调用停 2 次，直接慢 10~100 倍
```

### 减少系统调用次数的常用手段

```text
1. 缓冲（最有效）—— printf/fwrite 攒一批再 write：终端是行缓冲，重定向到文件是全缓冲（4K/8K 一批）
2. 大 buffer I/O —— read/write 一次 64KB 比 64 次 1KB 快得多
3. mmap 替代 read —— 大文件直接映射进地址空间，访问即读，省掉 read 调用（见 [[08.1-虚拟内存]]）
4. 零拷贝 sendfile/splice —— 文件→socket 数据不经过用户态，一次调用完成（Nginx 静态文件默认开启）
5. vDSO 时间类调用 —— gettimeofday/clock_gettime 已免陷入，别自己造轮子
6. io_uring —— 批量提交+批量收割，一次 enter 处理成百上千个 I/O，高并发存储场景（数据库/存储引擎）用
```

### 实测数据参考

```text
本机 ls /tmp：77 次系统调用，纯系统调用时间仅 0.000171s —— 单次调用 ~2μs 平均
（含 mmap/brk 等重调用；实际瓶颈通常在磁盘/网络等待，而不是调用本身）
```

优化前先 `strace -c` 摸清「调用次数最多、等待最久」的调用，别盲目优化。

## 安全与权限

```text
1. ptrace 限制 —— /proc/sys/kernel/yama/ptrace_scope（本机 = 1）：默认只能追踪自己的
   子进程；strace 别人的进程要 root 或改策略。容器里通常受限更严。
2. seccomp 过滤 —— 进程可安装 BPF 过滤器限制「能调用哪些系统调用」：
   容器运行时（Docker 默认 profile 禁掉 ~44 个危险调用）、Chrome 沙箱、systemd
   SystemCallFilter= 都是典型场景。本机实测 /proc/self/status 的 Seccomp = 0（未过滤）。
3. 内核态权限校验不可绕过 —— open 的权限检查、capability 检查都在内核里做，
   用户程序无法伪造；「提权漏洞」的本质就是利用内核 bug 绕过这些检查。
4. strace 会泄露敏感数据 —— strace 输出含缓冲区内容（密码、密钥、Token），
   排查完及时清理输出文件，别把 strace.log 传到公共平台。
5. 系统调用 ABI 稳定性本身是安全属性 —— 编号不重排，恶意程序无法通过「撞号」
   意外调用到特权功能；新增调用必须走完整审计流程。
```

## 故障排查

### 案例一：程序卡住，定位卡点

```shell
# 1. 零开销先看：当前阻塞在哪个系统调用（本机实测格式见「配置文件解析」）
cat /proc/<PID>/syscall
# 2. 内核视角：进程在内核里等什么
cat /proc/<PID>/wchan          # 如 pipe_read、sock_alloc_send_pskb
# 3. 动态视角：strace 附加看最近在干什么
strace -p <PID> 2>&1 | tail
# 4. 配合文件描述符判断在等哪个文件/连接
ls -l /proc/<PID>/fd/
```

判断经验：卡在 `read` = 等数据（网络/管道/终端）；卡在 `futex` = 等锁（线程死锁嫌疑）；卡在 `nanosleep` = 主动睡眠；卡在 `connect` = 等对端。

### 案例二：strace 附加报 Permission denied

```shell
$ strace -p 1234
strace: attach: ptrace(PTRACE_SEIZE, 1234): Operation not permitted
# 排查顺序：
sysctl kernel.yama.ptrace_scope    # 本机 = 1：别人的进程追不了
# 解法：root 运行（root 不受 scope=1 限制）；或临时改 scope=0（改完记得改回）
# 容器内：--cap-add=SYS_PTRACE 或 --privileged 才允许
```

### 案例三：strace 输出巨大刷屏，找不到重点

```shell
# 解法 1：按类过滤
strace -e trace=file ./app
# 解法 2：只统计
strace -c ./app
# 解法 3：输出到文件再 grep
strace -o /tmp/trace.log ./app && grep -E 'connect|ENOENT' /tmp/trace.log
# 解法 4：只看特定调用
strace -e trace=connect,openat,read,write ./app
```

### 案例四：子进程行为没追踪到

```shell
# 症状：程序 fork 了一堆 worker，strace 只看到主进程
# 原因：没加 -f，子进程的跟踪随 fork 被剥离
strace -f ./server            # -f 跟踪所有子进程
strace -ff -o /tmp/trace      # 每个进程一个文件：trace.<pid>
```

### 案例五：程序报错但 strace 里全是成功

```shell
# 症状：程序打印「内存不足」，但 strace -e trace=mmap 全是成功
# 原因：错误发生在库函数层（glibc 内部的 malloc 策略），没到系统调用层
# 解法：strace 只覆盖系统调用；库函数层错误用 ltrace（追踪动态库函数调用），
#       或加 glibc 调试环境变量（MALLOC_CHECK_=3、GLIBC_TUNABLES）
```

## 常见问题

```text
Q1: strace 全量输出太大看不过来？
A: 用 -e trace=xxx 按类过滤（file/network/process/memory），或 -c 看统计，
   或 -o 输出到文件再 grep。别裸跑全量。

Q2: strace 生产进程导致性能下降？
A: strace 基于 ptrace，每个系统调用停两次，进程慢 10~100 倍。生产环境：
   先用 /proc/<PID>/syscall 零开销查看；必须 strace 时短期使用、优先 -c 统计、
   只跟踪关键进程；严重场景考虑 eBPF（perf trace、bpftrace，见 [[24.3-eBPF]]）。

Q3: strace 报 ptrace 权限不足？
A: YAMA ptrace_scope=1 时只能追自己子进程。用 root 运行 strace，或临时
   echo 0 > /proc/sys/kernel/yama/ptrace_scope（排查完改回）。容器里需 SYS_PTRACE 能力。

Q4: strace 显示 ENOENT 就是程序坏了吗？
A: 不一定。程序经常「探测」文件/设备在不在（如 ld.so.preload、nscd socket），
   ENOENT 是探测的正常结果。看「关键调用的返回值」和错误上下文，别被无关 ENOENT 吓到。

Q5: 为什么 strace 看不到我预期的系统调用？
A: 常见原因：① 用了等价新接口（open→openat、stat→statx、fork→clone、exit→exit_group）；
   ② 调用被 vDSO 消化（gettimeofday/clock_gettime，根本不陷入内核）；
   ③ 静态编译程序不经过动态 libc 封装，但系统调用仍会出现；
   ④ 过滤条件写窄了（-e trace=open 看不到 openat）。

Q6: 系统调用号会变吗？
A: 不会。Linux ABI 契约：编号一旦分配永不修改，新功能只追加新号。
   所以旧二进制在新内核上依然兼容。跨架构编号不同（x86-64 与 arm64 各自编号）。

Q7: 系统调用和库函数有什么区别？
A: 系统调用是内核提供的服务入口（有特权级切换、按编号分发）；库函数是用户态代码
   （可能缓冲、组合多次系统调用）。printf 是库函数（攒缓冲），write 是系统调用封装。
   同名的 read/write 是 1:1 封装，printf/malloc 是高层封装。

Q8: 怎么查看一个进程一共发起了多少系统调用？
A: strace -c 统计；或 /proc/<PID>/syscall 只看当前阻塞的；perf trace 也可以
   （perf record -e syscalls:sys_enter_* -p PID 采样）。
```

## 面试题

```text
1. 什么是系统调用？为什么需要它？
   答：系统调用是用户程序请求内核服务的受控入口。用户程序无法直接操作硬件
   （特权指令会触发异常），必须把请求交给内核态执行。它同时是安全边界：
   内核统一做权限校验，用户程序无法绕过。

2. 用户态和内核态的区别？如何切换？
   答：用户态（ring3）权限低，只能访问自己的地址空间，不能执行特权指令；
   内核态（ring0）权限高，能访问所有内存和硬件。切换靠 syscall/sysret 指令
   （x86-64；老接口是 int 0x80 软中断），由 CPU 硬件完成特权级升降和寄存器保存。
   中断和异常（缺页、除零）也会从用户态陷入内核态。

3. 一次系统调用的完整流程（x86-64）？
   答：① 参数装入寄存器（rax=调用号，rdi/rsi/rdx/r10/r8/r9=6 个参数）；
   ② 执行 syscall 指令，CPU 切到 ring0 并跳到 MSR_LSTAR 指向的内核入口；
   ③ 内核保存寄存器，按 rax 查 sys_call_table 得到处理函数；
   ④ 执行（如 sys_read），做权限检查、拷贝数据；
   ⑤ 返回值放 rax（失败为负 errno），sysret 切回用户态，glibc 把负值转成 errno。

4. 系统调用和库函数的区别？举例。
   答：系统调用有特权级切换、按编号分发、由内核执行；库函数在用户态执行，
   可缓冲、可组合多个系统调用。printf 是库函数（先写用户态缓冲区，攒满或换行
   才触发 write 系统调用）；write 是系统调用封装。fork 的封装实际调 clone，
   exit 的封装实际调 exit_group。

5. strace 的原理是什么？为什么慢？
   答：基于 ptrace 系统调用。strace 用 ptrace 让被追踪进程在每个系统调用的
   进入和退出各停一次，自己读取寄存器里的参数和返回值。每个系统调用被打断两次、
   还要进行进程间通信，所以被追踪进程慢 10~100 倍。开销来自 ptrace 机制本身，
   与输出多少无关。

6. 如何降低程序的系统调用开销？
   答：① 缓冲——printf/fwrite 攒批，减少 write 次数；
   ② 大 buffer 读写——减少 read/write 调用次数；
   ③ mmap 大文件——访问即读，免 read；
   ④ sendfile/splice 零拷贝——文件到 socket 不过用户态；
   ⑤ 时间类走 vDSO——gettimeofday 不陷入内核；
   ⑥ io_uring——批量提交/收割，一次 enter 处理大量 I/O。

7. vDSO 是什么？哪些调用走 vDSO？
   答：内核把少量无副作用的只读系统调用实现直接映射进用户态地址空间
   （/proc/self/maps 里的 [vdso]），用户态直接调用，不陷入内核。
   主要是时间类：gettimeofday、clock_gettime、time、getcpu。
   判断方法：strace 里看不到这些调用，不代表程序没调。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 程序卡住/失败，先 `cat /proc/<PID>/syscall`（零开销），再考虑 strace
2. strace 按类过滤：`-e trace=file/network/process`，别裸跑全量
3. 优先 `-c` 看统计（哪个调用最多/最耗时），再针对性深入
4. 追多进程程序必须 `-f`，`-ff -o` 可按进程分文件
5. 输出写文件（`-o`）而不是刷终端，长 trace 配合 grep 分析
6. 生产环境 strace 要短、要窄、要 root 谨慎授权；长时间观察用 eBPF
7. 理解「探测型 ENOENT」：ld.so.preload、nscd socket 等都是正常探测
8. 排查网络行为用 `-e trace=connect,socket`，注意本机 DNS 走 systemd-resolved（127.0.0.53）

### 踩坑记录

```text
坑 1：strace 全量输出太大，看不过来
结论：strace 程序输出刷屏，找不到重点。
原因：没过滤，程序系统调用太多。
解法：strace -e trace=xxx 过滤（file/network/process），或 -c 看统计，或 -o 写文件。

坑 2：strace 生产进程导致性能下降
结论：strace -p 生产进程，服务明显变慢甚至超时。
原因：ptrace 机制导致每个系统调用停两次，进程慢 10~100 倍。
解法：先用 /proc/<PID>/syscall 零开销看；必须 strace 时短期、窄过滤、root 谨慎；
     长期观察改用 perf trace / bpftrace。

坑 3：strace 报 ptrace 权限不足
结论：strace -p 别人的进程报 Operation not permitted。
原因：YAMA ptrace_scope=1（默认）只允许追踪自己的后代。
解法：root 运行；或临时 sysctl kernel.yama.ptrace_scope=0（排查完恢复 1）；
     容器里加 --cap-add=SYS_PTRACE。

坑 4：把 strace 输出当「程序日志」误读
结论：看到 ENOENT 就以为程序坏了，排查半天。
原因：很多 ENOENT 是正常的探测（ld.so.preload、nscd socket、候选配置路径）。
解法：关注「关键调用 + 返回值」，结合程序逻辑判断，别被无关失败误导。

坑 5：忘了 -f，子进程行为全没追踪到
结论：程序 fork 的 worker 出问题，strace 里一片空白。
原因：默认只跟踪主进程，fork/clone 出的子进程被剥离跟踪。
解法：strace -f 追所有子进程；-ff -o trace 按进程分文件。

坑 6：strace 里看不到 gettimeofday，误以为程序没调时间函数
结论：追踪时间相关逻辑，strace 里什么都没有。
原因：gettimeofday/clock_gettime 走 vDSO，在用户态完成，不陷入内核。
解法：用 ltrace 验证库函数调用；或 strace 时间类不适用，直接看 vDSO 映射确认。

坑 7：strace 输出长期写盘，磁盘被占满
结论：strace -o trace.log 挂着没管，几个小时后磁盘满，服务全挂。
原因：高系统调用进程的 trace 文件增长极快（每秒几万行）。
解法：-o 文件要限大小（配合 logrotate/定时清理），或只跑短时间，或用 -c 统计代替。

坑 8：容器里 strace 受限或看不到其他容器进程
结论：容器内 strace 自己进程都报错，或 strace 看不到宿主其他进程。
原因：容器默认无 SYS_PTRACE 能力；pid namespace 隔离看不到别的进程。
解法：docker run --cap-add=SYS_PTRACE 或 --privileged；宿主上以 root 追踪。

坑 9：用 strace 追到了「正常」的卡顿，但没看到真正的阻塞
结论：程序间歇性卡顿，strace -p 附加后啥也没输出，以为没卡。
原因：卡顿发生在 strace 附加之前的瞬间；或阻塞在用户态锁（futex 前的自旋）。
解法：多次短周期附加采样；配合 /proc/<PID>/wchan、off-cpu 分析（eBPF）；
     用户态锁问题用 perf / ltrace / gdb 而非 strace。
```
