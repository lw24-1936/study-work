## 概述

系统调用（syscall）是「用户程序请求内核服务的接口」——程序不能直接操作硬件（读文件、发网络、分配内存），必须通过系统调用来让内核代劳。核心：用户态与内核态（权限隔离）、系统调用机制（软中断/指令切换到内核）、strace（追踪程序发起的系统调用）。理解系统调用，才能看懂「程序卡在哪」——strace 能看到它在等哪个系统调用。

```text
系统调用三要素：
1. 用户态/内核态 —— 程序跑在用户态（权限低），内核跑在内核态（权限高）
2. 系统调用机制 —— 用户态通过 syscall 指令切入内核态，请求服务
3. strace —— 追踪程序发起的每个系统调用，定位卡点/失败
```

## 核心概念

1. **用户态与内核态**：CPU 分两个特权级别——用户态（权限低，只能访问自己的内存）和内核态（权限高，能访问硬件和所有内存）。
2. **系统调用机制**：用户态通过 syscall 指令切入内核态请求服务，内核执行完返回，涉及上下文切换。
3. **libc 库函数**：程序通常调用 libc 的 read()/write() 等封装，libc 再发起真正的系统调用。
4. **strace**：追踪程序发起的每个系统调用（调用名、参数、返回值、耗时），排查卡点/失败。

```text
用户态 vs 内核态：
1. 用户态 —— 权限低，程序运行的地方，只能访问自己的地址空间
2. 内核态 —— 权限高，内核运行的地方，能访问硬件和所有内存
3. 切换 —— 系统调用/中断/异常触发用户态→内核态切换（有开销）
```

## 工作原理

系统调用的流程：程序调用库函数（如 read()）→ 库函数把系统调用号放进寄存器、设置参数 → 执行 syscall 指令切入内核态 → 内核根据调用号查系统调用表，执行对应内核函数（sys_read）→ 返回结果 → 切回用户态。每次系统调用都有「上下文切换」开销，所以频繁系统调用影响性能。Linux 有几百个系统调用（read/write/open/fork/mmap 等），每个有固定编号。

```text
系统调用流程：
用户程序 read() → libc 库 → syscall 指令（切入内核态）→ 内核执行 sys_read → 返回 → 切回用户态
```

## 常用命令与配置

```shell
strace ls                       # 追踪 ls 的全部系统调用
strace -p 1234                  # 追踪运行中的进程
strace -c ls                    # 统计系统调用（哪个调用最多）
strace -e trace=file ls         # 只看文件相关系统调用
strace -e trace=network curl example.com   # 只看网络相关
man syscalls                    # 系统调用列表
cat /proc/sys/kernel/osrelease  # 内核版本
```

```text
# 实测（strace 统计 ls 的系统调用）
$ strace -c ls /tmp 2>&1 | tail
% time  seconds  usecs/call  calls  errors syscall
------  -------  -----------  -----  ------  ----------------
  ...   ...      ...           ...    ...    prlimit64
  ...   ...      ...           ...    ...    getrandom
  ...   ...      ...           75     ...    total
# 一个简单的 ls 就发起了 75 次系统调用（statx/getrandom/rseq 等）
```

## 配置文件解析

系统调用本身没有配置文件，但有几个「接口文件」可以查看和限制：

```text
/proc/sys/kernel/osrelease    内核版本号
/proc/<pid>/syscall           进程当前阻塞的系统调用（调试用）
/usr/include/asm/unistd*.h    系统调用号定义（架构相关）
```

```text
ptrace 权限控制（影响 strace 能否追踪他人进程）：
/proc/sys/kernel/yama/ptrace_scope
0 = 完全允许 | 1 = 只允许父进程追踪子进程（默认）| 2 = 仅 root | 3 = 完全禁止
```

## 应用场景实战

### 场景一：程序卡住不动，strace 看它在等什么

```shell
# 1. 追踪卡住的进程
strace -p <PID>
# 输出末尾会显示它卡在哪个系统调用（如 read 等数据、connect 等连接）
# 2. 看时间消耗（-c 统计）
strace -c -p <PID>
```

### 场景二：程序报「文件打不开」，strace 找真实路径

```shell
# 1. 追踪程序，看它实际尝试打开哪个文件
strace -e trace=open,openat ./myapp 2>&1 | grep -i 'no such'
# 输出会显示 ENOENT 的文件路径，就是它找不到的文件
```

## 性能与调优

```text
1. 减少系统调用 —— 系统调用有上下文切换开销，频繁调用拖慢程序（如逐字节 read 改为批量 read）
2. 批量 I/O —— read/write 用大 buffer 减少调用次数
3. mmap 替代 read —— 大文件映射内存访问，减少 read/write 调用
4. strace 开销 —— strace 本身显著拖慢被追踪进程，生产慎用
```

## 安全与权限

```text
1. ptrace 限制 —— /proc/sys/kernel/yama/ptrace_scope 限制能否追踪他人进程
2. 系统调用过滤 —— seccomp 过滤器限制进程能用的系统调用（容器安全常用）
3. 权限检查 —— 系统调用在内核态做权限校验，用户态程序无法绕过
4. strace 泄露 —— strace 能看到敏感数据（密码/密钥），追踪结果别外传
```

## 故障排查

### 程序卡住定位卡点

```shell
# 1. 看进程当前阻塞的系统调用
cat /proc/<PID>/syscall
# 2. strace 追踪看最后卡在哪个调用
strace -p <PID> 2>&1 | tail
# 3. 看等待的文件描述符/网络连接
ls -l /proc/<PID>/fd/
```

### strace 权限不足

```shell
# 报 Permission denied
strace -p <别的用户的PID>
# 看 ptrace_scope 限制
sysctl kernel.yama.ptrace_scope
```

## 常见问题

```text
Q1: strace 全量输出太大看不过来？
A: 用 strace -e trace=xxx 过滤（file/network/process），或 -c 看统计。

Q2: strace 生产进程导致性能下降？
A: strace 会跟踪每个系统调用，有显著开销。生产短期追踪，或先用 -c 快速定位。

Q3: strace 报 ptrace 权限不足？
A: ptrace 有 YAMA 限制。用 root，或调整 /proc/sys/kernel/yama/ptrace_scope。

Q4: strace 显示 ENOENT 就是程序坏了吗？
A: 不一定。很多 ENOENT 是正常的（程序探测文件在不在），关注关键调用 + 返回值。
```

## 面试题

```text
1. 什么是系统调用？
   答：用户程序请求内核服务的接口，程序不能直接操作硬件，必须通过系统调用让内核代劳。

2. 用户态和内核态的区别？
   答：用户态权限低、只能访问自己的内存；内核态权限高、能访问硬件和所有内存。系统调用触发两者切换。

3. 一次系统调用的完整流程？
   答：程序调库函数 → libc 设调用号和参数 → syscall 指令切入内核态 → 内核查表执行 → 返回切回用户态。

4. strace 能干什么？
   答：追踪程序发起的每个系统调用（名称/参数/返回值/耗时），定位程序卡点、权限不足、文件打不开等问题。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 程序卡住/失败先 strace，看它在等哪个系统调用
2. strace -e trace=xxx 过滤关注点（file/network/process），别全量看
3. strace -c 统计系统调用，看「哪个调用最多/最耗时」
4. 追踪运行中进程用 strace -p PID（不影响程序运行）
5. 注意 strace 有性能开销，生产环境慎用（短期追踪可以）

### 踩坑记录

```text
坑 1：strace 全量输出太大，看不过来
结论：strace 程序输出刷屏，找不到重点。
原因：没过滤，程序系统调用太多。
解法：strace -e trace=xxx 过滤（file/network/process），或 -c 看统计。

坑 2：strace 生产进程导致性能下降
结论：strace -p 生产进程，服务变慢。
原因：strace 会暂停/跟踪每个系统调用，有显著开销。
解法：生产环境短期追踪，或先用 -c 统计快速定位。

坑 3：strace 报 ptrace 权限不足
结论：strace -p 别的用户的进程报 Permission denied。
原因：ptrace 有权限限制（YAMA 安全模块）。
解法：用 root，或调整 /proc/sys/kernel/yama/ptrace_scope。

坑 4：把 strace 输出当「程序日志」误读
结论：strace 显示 ENOENT 就以为程序坏了。
原因：很多 ENOENT 是正常的（程序探测「文件在不在」）。
解法：关注「关键调用 + 返回值」，别被正常的探测失败误导。

坑 5：strace 没显示预期系统调用，以为是编译问题
结论：追踪不到某系统调用。
原因：程序可能用了别的等价调用（open 和 openat），或静态编译绕过 libc。
解法：strace -e trace=file 看所有文件调用，openat 是 open 的新版本。
```
