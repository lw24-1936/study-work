## 概述

软件源（repository）是「软件包存放在哪、从哪下载」的配置。官方源（在软件官方服务器）和镜像源（第三方镜像站，如阿里云/清华，内容一样但更快）是两种选择。生产环境常见需求：换镜像源加速下载、自建本地源（内网离线装包）、密钥签名校验（防止包被篡改）。理解软件源的配置和签名校验，才能安全、高效地装软件。

```text
软件源三件事：
1. 官方源 vs 镜像源 —— 内容一样，镜像源在国内更快
2. 自建本地源 —— 内网环境离线装包（本地目录或内网 HTTP 服务器）
3. 密钥签名 —— GPG 签名校验，确保包来源可信、未被篡改
```

```text
# 实测（本机 Debian 系源配置）
$ ls /etc/apt/sources.list.d/
docker.list  tailscale.list  ubuntu.sources  ubuntu.sources.curtin.orig
# Ubuntu 24.04 用新的 deb822 格式 .sources 文件，第三方源（docker/tailscale）单独放
```

软件源这套机制贯穿「下载、校验、安装」全链路，是包管理器的数据来源。Debian 系和 Red Hat 系术语略不同（`apt`/`sources.list` vs `dnf`/`yum.repos.d`），但原理一致：客户端从源拉索引 → 解析依赖 → 下载包 → 验签 → 安装。

## 核心概念

### 官方源与镜像源

1. **软件源（repository）**：一个「软件包 + 索引」的集合，客户端从源下载包和元数据。源里分多个组件（component），如 Ubuntu 的 main/universe/restricted/multiverse。
2. **镜像源（mirror）**：第三方镜像站同步官方源的副本，内容一致但地理位置近、访问快。国内常用阿里云、清华、中科大镜像。
3. **索引（index）**：源里的包清单文件（Packages/repodata），客户端先拉索引才知道「源里有什么、版本是多少」，装包前必须刷新。
4. **GPG 签名**：源用私钥给索引和包签名，客户端用公钥验证，防止中间人篡改。
5. **本地源（local repo）**：把官方源同步到本地目录或内网 HTTP 服务器，供内网离线环境装包。

```text
核心概念速查：
repository   软件包 + 索引的集合
mirror       官方源的镜像副本，地理位置近、下载快
index        包清单（Packages/repodata），装包前要刷新
GPG 签名     源签名 + 客户端验签，防篡改
local repo   本地/内网源，离线装包
```

**官方源 vs 镜像源（是什么→为什么→怎么用→边界/易错点）**：

- 是什么：官方源是发行版/软件官方维护的服务器，镜像源是第三方同步官方内容的副本。
- 为什么：官方源通常在国外，国内访问慢、易超时；镜像源地理近、带宽足，内容靠签名保证一致。
- 怎么用：把源地址里的域名换成镜像站域名（`archive.ubuntu.com` → `mirrors.aliyun.com`），再 `apt update`。
- 边界/易错点：镜像源有同步延迟（通常几小时到一天），可能短暂拿不到刚发布的新包；换源后必须 `apt update` 刷新索引，否则源地址变了索引还是旧的。

### 自建本地源

**是什么→为什么→怎么用→边界/易错点**：

- 是什么：用 apt-mirror（Debian 系）/ reposync + createrepo（Red Hat 系）把官方源完整同步到本地目录，再通过本地路径或内网 HTTP 提供给内网机器。
- 为什么：内网/隔离网段无法访问外网，或要统一控制内网机器的软件版本，本地源是标准解法。
- 怎么用：有外网的机器同步 → 内网机器把源指向本地目录（`deb [trusted=yes] file:/...`）或内网 HTTP 地址 → 刷新装包。
- 边界/易错点：同步的是「元数据 + 包」，缺了索引文件（Packages/repodata）客户端就找不到包；Red Hat 系同步后必须 `createrepo` 重建元数据。

### 密钥签名校验

**是什么→为什么→怎么用→边界/易错点**：

- 是什么：官方用 GPG 私钥给索引签名，客户端预置/导入公钥验签，签名不符拒绝安装。
- 为什么：防止「中间人替换包/投毒」，保证从镜像源下载的包和官方一致。
- 怎么用：Debian 系把公钥放进 `/etc/apt/trusted.gpg.d/`，Red Hat 系 `rpm --import` 或 `gpgkey=` 指定，保持 `gpgcheck=1` 开启。
- 边界/易错点：报 NO_PUBKEY 是「缺公钥」不是「源坏了」，按提示导入即可；导入前必须确认密钥来源可信，导入来路不明的公钥等于主动信任攻击者。

## 工作原理

装包的完整链路：客户端先「刷新索引」（从源拉 Packages/repodata 清单）→ 根据清单解析依赖 → 从源下载 .deb/.rpm 包 → 校验签名 → 安装。

签名校验的原理是「非对称加密」：官方持有私钥给索引和包签名，客户端预置/导入公钥，验签通过才安装，签名不符直接拒绝。索引（而非单个包）被签名是关键——索引里记录了每个包的校验和，客户端拿到索引后能核对每个包是否被篡改。

```text
装包链路：
刷新索引 → 解析依赖 → 下载包 → 验签 → 安装

签名校验原理：
1. 签名 —— 官方用私钥给索引/包签名
2. 验证 —— 客户端用公钥验签，不符拒绝
3. 导入密钥 = 建立信任 —— 只导可信来源的密钥
```

```text
两级校验（为什么索引被签名、包只记校验和）：
1. 索引被 GPG 签名 —— 客户端验签索引，确保「清单本身可信」
2. 索引含每个包的 SHA256 —— 下载后按校验和核对包，任何改动都会失配
3. 效果 —— 篡改索引或替换包，验签/校验必失败，无需给每个包单独签名
```

Debian 系和 Red Hat 系的元数据格式不同，但链路一致：Debian 系拉 `Packages`（二进制包清单，通常 gzip 成 `Packages.gz`），Red Hat 系拉 `repodata/`（含 `primary.xml` 等，记录包名/版本/依赖/校验和）。`apt update` / `dnf makecache` 就是刷新这些清单。

## 常用命令与配置

```shell
# Debian 系
apt update                     # 刷新索引
apt-cache policy <pkg>         # 看包来自哪个源
apt-get --print-uris install <pkg>  # 看下载地址
sed -i 's/archive.ubuntu.com/mirrors.aliyun.com/g' /etc/apt/sources.list   # 换源
apt update

# Red Hat 系
dnf makecache                  # 刷新索引
dnf repolist                   # 列出仓库
dnf config-manager --add-repo <url>   # 添加仓库
sed -i 's/mirror.centos.org/mirrors.aliyun.com/g' /etc/yum.repos.d/CentOS-*.repo
dnf makecache

# 自建本地源
apt-mirror                     # Debian 系同步（配置 /etc/apt/mirror.list）
reposync --repoid=baseos --download-metadata -p /var/www/repo   # Red Hat 系同步
createrepo /var/www/repo/baseos
```

```shell
# Debian 系密钥管理
apt-key list                                   # 列出已导入的密钥（老式）
ls /etc/apt/trusted.gpg.d/                     # 新式公钥环（Ubuntu 22.04+ 推荐）
curl -fsSL <key-url> | gpg --dearmor -o /etc/apt/trusted.gpg.d/<name>.gpg   # 导入第三方源公钥

# Red Hat 系密钥管理
rpm --import /etc/pki/rpm-gpg/RPM-GPG-KEY-xxx  # 导入公钥
rpm -qa gpg-pubkey*                            # 列出已导入的公钥
dnf repolist -v                                # 看每个仓库的 gpgcheck 状态
```

## 配置文件解析

```text
Debian 系源位置：
/etc/apt/sources.list         老式 one-line 格式
/etc/apt/sources.list.d/*.list 第三方源（一个源一个文件）
/etc/apt/sources.list.d/*.sources Ubuntu 24.04 deb822 新格式
/etc/apt/trusted.gpg.d/       公钥环（.gpg 文件）

Red Hat 系源位置：
/etc/yum.repos.d/*.repo       仓库定义（baseurl/gpgcheck）
/etc/pki/rpm-gpg/             RPM-GPG 公钥
```

```text
Debian 系源格式（Ubuntu 24.04 deb822 格式）：
Types: deb
URIs: http://mirrors.aliyun.com/ubuntu/
Suites: noble noble-updates noble-security
Components: main universe restricted multiverse

Red Hat 系源格式（/etc/yum.repos.d/aliyun.repo）：
[baseos]
name=Aliyun baseos
baseurl=https://mirrors.aliyun.com/centos-stream/9-stream/BaseOS/x86_64/os/
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-centosofficial
```

```text
老式 one-line 格式（/etc/apt/sources.list）字段含义：
deb http://archive.ubuntu.com/ubuntu noble main restricted
类型  源地址/发行版路径        发行代号  组件（component）

字段解释：
deb/deb-src   —— 二进制源 / 源码源
发行代号       —— noble（24.04）、jammy（22.04）等，必须和系统一致
组件           —— main（官方支持）/ universe（社区）/ restricted / multiverse
```

Ubuntu 24.04 从 one-line 迁到 deb822 格式（`.sources` 文件），但老式 `.list` 仍然兼容。改源时注意别混用两种格式导致同一源被重复定义——`apt update` 会报重复条目警告。

## 应用场景实战

### 场景一：国内服务器换镜像源加速

```shell
# Ubuntu 换阿里云源
cp /etc/apt/sources.list /etc/apt/sources.list.bak
sed -i 's/archive.ubuntu.com/mirrors.aliyun.com/g' /etc/apt/sources.list
apt update
# 验证：apt update 应该明显变快
```

### 场景二：内网服务器自建本地源

```shell
# 1. 有外网的机器同步官方源
apt-mirror        # 配置 mirror.list 后同步到 /var/spool/apt-mirror
# 2. 内网机器配置指向本地目录
echo "deb [trusted=yes] file:/mnt/apt-mirror/mirror/archive.ubuntu.com/ubuntu noble main" > /etc/apt/sources.list
apt update
apt install nginx
```

### 场景三：给第三方源导入公钥解决 NO_PUBKEY

加了第三方源（如 Docker、Tailscale）后 `apt update` 报 NO_PUBKEY，需要导入该源对应的公钥建立信任。

```shell
# 1. apt update 报 NO_PUBKEY <16 位 Key ID>
apt update
# W: GPG error: ... NO_PUBKEY 0EBFCD88

# 2. 从密钥服务器或源官网下载公钥（以 Docker 官方为例）
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | \
  sudo gpg --dearmor -o /etc/apt/trusted.gpg.d/docker.gpg

# 3. 重新刷新，验签通过
apt update
apt install docker-ce

# 4. Red Hat 系同理：rpm --import 公钥，或 .repo 里配 gpgkey=
rpm --import https://download.docker.com/linux/centos/gpg
```

### 场景四：Red Hat 系内网自建本地源（reposync + createrepo + nginx）

Debian 系用 apt-mirror，Red Hat 系对应的完整链路是 reposync 同步 + createrepo 重建元数据 + nginx 提供 HTTP 访问。

```shell
# 1. 有外网的机器：同步官方源到本地目录（以 CentOS Stream 9 的 baseos 为例）
dnf install createrepo dnf-utils
reposync --repoid=baseos --download-metadata -p /var/www/repo
# 2. 重建元数据（reposync 拿到包后必须 createrepo，否则客户端找不到索引）
createrepo /var/www/repo/baseos
# 3. 用 nginx 把 /var/www/repo 暴露成内网 HTTP 源
dnf install nginx
# nginx 配置：root /var/www/repo; autoindex on;
systemctl enable --now nginx
# 4. 内网机器配置指向这个本地源
cat > /etc/yum.repos.d/local.repo <<'EOF'
[local-baseos]
name=Local BaseOS
baseurl=http://192.168.1.10/repo/baseos/
enabled=1
gpgcheck=0
EOF
dnf clean all && dnf makecache
dnf install nginx
```

## 性能与调优

```text
1. 镜像选择 —— 国内服务器用阿里云/清华镜像，下载速度差数倍，先测速再定
2. 并行下载 —— apt 的 Acquire::http::Pipeline-Depth 提高并发，加速多包下载
3. 索引缓存 —— 保留 apt 的索引缓存（/var/lib/apt/lists），避免每次全量拉
4. 本地缓存代理 —— 内网多机可架 apt-cacher-ng，一次下载多机复用
5. 增量同步 —— 自建镜像用 rsync 增量同步，比全量 apt-mirror 省带宽
```

```shell
# 提高 apt 并行下载（/etc/apt/apt.conf.d/99parallel）
echo 'Acquire::http::Pipeline-Depth "10";' > /etc/apt/apt.conf.d/99parallel
echo 'Acquire::Retries "3";' >> /etc/apt/apt.conf.d/99parallel

# 架 apt-cacher-ng 内网缓存代理（多机复用下载）
apt install apt-cacher-ng
# 客户端指向缓存代理
echo 'Acquire::http::Proxy "http://192.168.1.10:3142";' > /etc/apt/apt.conf.d/01proxy
```

镜像源并非永远比官方源快：如果服务器就在国外（如海外节点），官方源可能更近。换源前先用 `curl -o /dev/null -s -w '%{speed_download}\n' <源地址>/...` 实测下载速度，别想当然。

## 安全与权限

```text
1. 保持 gpgcheck=1 / 签名校验开启 —— 别为了省事关掉，关掉等于放弃防篡改
2. 密钥来源可信 —— 导入第三方源公钥前确认来源，别乱导来路不明的密钥
3. 走 HTTPS —— 优先 https:// 源，防传输层篡改
4. 内网本地源 —— 用 [trusted=yes] 绕过签名时要明白这是「信任本机文件」的取舍
5. 供应链 —— 官方源 + 官方签名是基线，第三方 PPA/仓库要评估可信度
```

```shell
# 检查当前源是否都开启了签名校验
grep -r 'gpgcheck' /etc/yum.repos.d/      # Red Hat 系：确认都是 gpgcheck=1
apt-get -o Debug::Acquire::gpgv=true update 2>&1 | grep -i gpg   # Debian 系：看验签过程

# 查看包的来源与签名（装之前确认）
apt-cache policy <pkg>        # Debian 系：包来自哪个源、优先级
```

签名校验的「信任锚」是公钥：公钥一旦导入就默认信任该源，所以导入公钥 = 建立信任，这步必须谨慎。第三方 PPA/仓库的安全取决于维护者，加之前评估其可信度和更新频率，加完及时导入正确公钥，别用 `[trusted=yes]` 或 `gpgcheck=0` 一关了事。

## 故障排查

### apt update 报错 / 装不上包

```shell
# 1. 看具体报错（404 / NO_PUBKEY / 网络超时）
apt update
# 2. 404：源地址或发行版本不匹配
lsb_release -cs          # 确认系统版本代号
cat /etc/apt/sources.list.d/*.list   # 检查源里的版本号
# 3. NO_PUBKEY：缺密钥，按报错提示导入
curl -fsSL <key-url> | gpg --dearmor -o /etc/apt/trusted.gpg.d/xxx.gpg
# 4. 网络：测试源可达性
curl -I http://mirrors.aliyun.com/ubuntu/
```

### Red Hat 系换源后 dnf 报错

```shell
# 1. 仓库元数据损坏 / 不匹配
dnf clean all          # 清空缓存
dnf makecache          # 重建索引缓存
# 2. 检查仓库配置语法
dnf repolist -v        # 看每个仓库的 baseurl/gpgkey 是否正确
# 3. 包校验失败
rpm -qa gpg-pubkey*    # 确认公钥已导入
# 4. 重建本地源元数据（自建源时）
createrepo --update /var/www/repo/baseos
```

## 常见问题

```text
Q1: 换源后 apt update 报 404？
A: 源里的发行版本代号和系统不一致（如 focal vs noble）。用 lsb_release -cs 确认代号，改成匹配的。

Q2: apt update 报 NO_PUBKEY 怎么办？
A: 第三方源缺公钥，按报错提示的 key ID 导入对应公钥到 trusted.gpg.d。

Q3: 本地源能访问但装不了包？
A: 缺索引文件（Packages.gz）或 Red Hat 系没 createrepo。确认索引齐全。

Q4: 自建源用 [trusted=yes] 有风险吗？
A: 有，等于跳过签名校验。内网可控环境下可接受，但要确保源目录本身不被篡改。

Q5: 镜像源的包和官方源一定完全一致吗？
A: 内容一致（靠签名和校验和保证），但存在同步延迟，镜像站刚发布的新包可能要等几小时到一天才同步过来，短暂装不到最新版是正常现象。

Q6: 换源换错了怎么回滚？
A: 换源前先 cp 备份原配置文件，出问题直接 cp 回备份文件再 apt update 即可；没备份就重新写回正确的源地址。

Q7: 导入了公钥还是报 NO_PUBKEY 怎么办？
A: 常见原因是导错密钥（Key ID 不匹配）或没刷新。核对报错的 Key ID 和导入的公钥指纹（gpg --show-keys），确认一致后 apt update 重试。
```

## 面试题

```text
1. 官方源和镜像源有什么区别？
   答：内容完全一致，镜像源是官方源的同步副本，地理位置近、下载快。换镜像源只改下载地址，不影响包内容（靠签名保证一致）。

2. 软件源的签名校验是怎么防篡改的？
   答：官方用私钥给索引签名，索引记录每个包的校验和。客户端用公钥验签索引，再按校验和核对每个包，任何篡改都会导致验签/校验失败。

3. 内网离线环境怎么装软件？
   答：自建本地源——有外网的机器用 apt-mirror/reposync 同步官方源到本地，内网机器指向本地目录或内网 HTTP 源。

4. 为什么装包前必须先 apt update？
   答：apt update 刷新索引（包清单），不刷新客户端不知道源里有什么新包/新版本，装包会报找不到或装旧版。

5. 为什么是「签名索引」而不是「签名每个包」？
   答：索引里记录了每个包的 SHA256 校验和，验签索引后就能用校验和核对每个包，实现等效的逐包校验，还避免了给成千上万个包逐个签名的开销。篡改索引或替换包都会失配。

6. Debian 系和 Red Hat 系的源元数据分别是什么？
   答：Debian 系是 Packages（二进制包清单，常压缩成 Packages.gz）；Red Hat 系是 repodata/（含 primary.xml 等），记录包名、版本、依赖和校验和。apt update / dnf makecache 刷新这些清单。

7. 怎么判断一个第三方源是否可信？
   答：看维护者背景（官方项目 > 知名组织 > 个人 PPA）、更新频率、是否提供签名公钥，导入公钥前确认来源；生产环境优先官方源和官方推荐源，避免随意添加来路不明的 PPA。

8. 自建本地源有哪些方式？
   答：Debian 系用 apt-mirror 全量同步（或 rsync 增量）；Red Hat 系用 reposync 同步 + createrepo 重建元数据；提供方式可以是本地目录（file:）或内网 HTTP 服务器。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 国内服务器换阿里云/清华镜像源，下载速度差好几倍
2. 改源前备份原配置，改完必须 apt update / dnf makecache
3. 加第三方源务必导入对应密钥并确认来源可信，别乱导密钥
4. 内网/离线环境自建本地源（apt-mirror/reposync），别一台台手动拷包
5. 保持 gpgcheck=1 / 密钥校验开启，别为了省事关掉签名校验
6. 换源前先测速（curl 实测下载速度），别想当然认为镜像一定比官方快
7. 优先走 https:// 源，降低传输层被篡改的风险

### 踩坑记录

```text
坑 1：换源后没 update 就装包报错
结论：改了源直接 install，报 Unable to locate package。
原因：索引还是旧的，不知道新源有什么。
解法：换源后先 apt update（或 dnf makecache）刷新索引。

坑 2：镜像源和系统版本不匹配
结论：换了源后 apt update 报 404 或签名错误。
原因：源里的发行版本（如 focal/bionic）和系统版本（noble）不匹配。
解法：确认源的发行版本号和自己系统一致（lsb_release -cs）。

坑 3：加第三方源没导入密钥，报 NO_PUBKEY
结论：apt update 报 NO_PUBKEY 某某。
原因：第三方源有签名校验，但本机没导入它的公钥。
解法：按报错提示导入对应公钥（apt-key 或 trusted.gpg.d）。

坑 4：自建本地源缺了 Packages 索引文件
结论：本地源目录能访问，但 apt update 报找不到 Packages。
原因：同步时没生成/没同步索引文件（Packages.gz）。
解法：确认索引文件齐全，Red Hat 系要 createrepo 生成。

坑 5：为了省事关掉 gpgcheck 导致安全风险
结论：源里 gpgcheck=0 或 [trusted=yes]，包被篡改也照装。
原因：关闭签名校验，无法发现被替换的恶意包。
解法：保持签名校验开启，密钥正确导入即可。

坑 6：换源没备份，改错后难恢复
结论：sed 直接改了 /etc/apt/sources.list，源地址写错导致装不了包，原配置也没了。
原因：原地 sed 覆盖，没先备份原文件。
解法：改源前先 cp 备份，出问题 cp 回备份文件再 apt update；用 sources.list.d/ 加新源比改主文件更安全。

坑 7：镜像源同步延迟，装不到刚发布的新包
结论：官方刚发布的版本，镜像源上 apt update 后还看不到。
原因：镜像站和官方源之间有同步延迟（几小时到一天），索引还没更新。
解法：确认镜像站同步完成再试，或临时切回官方源装最新版，装完切回镜像源。
```
