## 概述

Debian 系（Debian/Ubuntu/Linux Mint）用 apt + dpkg 管理软件包。dpkg 是底层工具（直接装/卸 .deb 包，不处理依赖），apt 是上层封装（自动解析依赖、从软件源下载）。日常几乎都用 apt（`apt install/remove/update/upgrade`），dpkg 只在「装本地 .deb」「查包详情」时用。理解两者的分工，才能看懂「apt 报依赖错误」时该去哪排查。

```text
Debian 系包管理分层：
1. dpkg —— 底层，直接装/卸 .deb 包，不自动处理依赖
2. apt —— 上层，自动解析依赖、从软件源下载、更新索引
3. 软件源 —— /etc/apt/sources.list(.d/)，定义从哪下载包
4. 依赖解析 —— apt 自动算依赖关系，缺啥补啥
```

Debian 系包管理要把握一条主线：**元数据驱动 + 分层解耦**。所有已装包的状态（版本、依赖、配置文件）都记在 /var/lib/dpkg/status 里，dpkg 直接操作它，apt 在它之上做「决策」——算出要装哪些包、从哪个源下载、按什么顺序配置。所以「apt 决策、dpkg 执行」这句话要落到「apt 改的是下载和依赖计划，真正改系统状态的是 dpkg」。

## 核心概念

### apt 与 dpkg 的分工

**是什么**：apt 和 dpkg 是上下层关系：apt 负责「决定装什么、从哪下载、解析依赖」，dpkg 负责「真正安装/卸载/配置 .deb 包」。所以 `apt install` 实际是「apt 下载 + 解析依赖 → dpkg 逐个安装」。

**为什么**：dpkg 不处理依赖——装一个包若缺依赖库，dpkg 照样装上但系统处于「依赖破损」状态，后续 apt 操作都会报错。apt 的存在就是解决「依赖地狱」，自动算出完整安装集合并按顺序配置。

**怎么用**：日常全用 apt；dpkg 单独用只做「本地 .deb 的安装」和「查询」——`dpkg -i 本地包.deb`（不装依赖）、`dpkg -l`（列包）、`dpkg -L`（包的文件清单）、`dpkg -S`（文件属于哪个包）。

**边界/易错点**：`dpkg -i` 装本地包不装依赖，装完要用 `apt install -f` 补依赖；`dpkg -l` 第一列状态码（ii=已安装、rc=已卸载但残留配置、un=未知）能看出包状态；`dpkg -S` 查「文件属于哪个包」依赖 /var/lib/dpkg/info/*.list 索引，只对已装包有效。

```text
# 实测（本机 apt/dpkg 版本）
$ apt --version
apt 2.8.3 (amd64)
$ dpkg --version | head -1
Debian dpkg 软件包管理程序 1.22.6 (amd64) 版
```

```shell
apt install nginx          # 上层：下载 + 解析依赖 + 安装
dpkg -i ./local.deb        # 底层：只装本地包，不管依赖
dpkg -l                    # 列出所有已装包
dpkg -L nginx              # 某包安装了哪些文件
dpkg -S /usr/sbin/nginx    # 某文件属于哪个包
```

```shell
# dpkg 完整操作面
dpkg -i package.deb        # 安装本地包（不处理依赖）
dpkg -r nginx              # 卸载（保留配置）
dpkg -P nginx              # 彻底卸载（删配置）
dpkg -s nginx              # 包状态详情（版本/依赖/描述）
dpkg -c package.deb        # 看 .deb 包里有哪些文件（未安装前）
dpkg -l 'linux-*'          # 按通配符列包
dpkg --get-selections      # 导出所有包的选择状态（可备份/迁移）
dpkg --set-selections < list.txt   # 恢复包选择状态
```

```text
dpkg -l 状态码（第一列）：
ii  已安装（installed）
rc  已卸载但残留配置（removed + config-files）
un  未知/未安装
iF  安装了一半（失败，需 dpkg --configure -a 修复）
```

### 软件源

**是什么**：软件源是「从哪下载包」的定义，写在 /etc/apt/sources.list 和 /etc/apt/sources.list.d/*.list（或新版 .sources）。每行一个「源」，指定仓库类型（deb 二进制 / deb-src 源码）、URL、发行版代号（如 noble、bookworm）和组件（main/contrib/non-free）。

**为什么**：apt 本身不带任何包，它靠源里的「索引」（Packages 文件）知道有哪些包、什么版本、依赖什么。换源、加第三方源（Docker、Tailscale、Google Chrome 等）本质就是加一行源地址 + 导入它的 GPG 公钥，让 apt 能看到并信任它的包。

**怎么用**：主源在 sources.list，第三方源建议放 sources.list.d/ 下单独一个文件（一个源一个文件，好管理）。改完源必须 `apt update` 刷新索引才生效。国内镜像（阿里云、清华）把 URL 换成对应镜像地址即可。

**边界/易错点**：发行版代号不能乱填（Ubuntu 22.04 是 jammy、24.04 是 noble，Debian 12 是 bookworm），填错会 404 或拉到错误版本；main/contrib/non-free 组件决定「自由软件 / 依赖非自由软件 / 非自由软件」三类，Ubuntu 默认只有 main，装某些闭源驱动要加 non-free；混用两个不同版本的源会拉高版本冲突风险。

```shell
# 查看当前生效的源
cat /etc/apt/sources.list
ls /etc/apt/sources.list.d/
# 各源的可用版本和仓库
apt policy nginx          # 看某包在所有源里的候选版本
```

```text
sources.list 行格式（老格式）：
deb  URL  发行版代号  组件1 组件2 ...
deb-src URL 发行版代号 组件      # 源码包

例：deb https://mirrors.aliyun.com/ubuntu noble main restricted universe multiverse
    ^   ^                                  ^     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    类型 镜像地址                           代号   组件（main/restricted/universe/multiverse）
```

```text
Ubuntu 组件（对应 Debian 的 main/contrib/non-free 语义有差异）：
main        官方支持的自由软件
restricted  官方支持但非自由（如闭源驱动）
universe    社区维护的自由软件
multiverse  非自由软件
```

### 依赖解析

**是什么**：.deb 包的 control 元数据里声明了依赖关系字段，apt 用 SAT 求解器（libapt 的 pkgProblemResolver）算出「要装这个包需要先装哪些包」，再按拓扑顺序安装。

**为什么**：一个 nginx 可能依赖几十个库，人工逐个装不现实。依赖解析让 `apt install nginx` 一条命令自动补齐所有依赖；反过来，依赖关系冲突（A 依赖 libv1、B 依赖 libv2 且互斥）就是 apt 报「依赖不满足」的根源。

**怎么用**：安装前用 `apt-cache depends/rdepends` 看依赖与被依赖关系，用 `apt install --dry-run`（或 -s）模拟安装看会装什么。

**边界/易错点**：依赖字段分强弱——Depends（必须满足）、Recommends（默认装但可跳过）、Suggests（建议、不装）、Pre-Depends（先于本包配置）、Conflicts（与谁互斥）、Provides（虚拟包，替代实现）。`apt install` 默认装 Recommends，用 `--no-install-recommends` 跳过（镜像里常用，减小体积）。

```text
# 实测（apt-cache 查包的依赖关系）
$ apt-cache depends nginx | head
nginx
  依赖: nginx-core
  依赖: nginx-full
  依赖: nginx-light
  依赖: nginx-extras
```

```text
依赖字段强弱（control 元数据）：
Depends      硬依赖，必须满足，否则装不上
Pre-Depends  必须满足且先于本包完成配置
Recommends   推荐，默认安装，--no-install-recommends 跳过
Suggests     建议，从不自动装
Conflicts    与指定包互斥，不能共存
Provides     声明「我也提供这个虚拟能力」（如 mail-transport-agent）
```

### apt-get 与 apt-cache

**是什么**：apt-get 和 apt-cache 是 apt 的「老一代」命令，apt 是它们的统一简化版。apt-get 做「变更类」操作（install/remove/upgrade/dist-upgrade），apt-cache 做「查询类」操作（search/show/depends/policy）。2014 年 apt 1.0 推出后把两者常用功能合并到一个命令。

**为什么**：apt 命令交互友好（有进度条、自动提示），但输出格式不稳定（可能随版本改）；apt-get 输出稳定、无交互依赖，适合写脚本。apt-cache 只读不改系统，用它查信息不会误触发变更。

**怎么用**：日常交互用 apt；脚本/CI 里用 `apt-get update && apt-get install -y`（稳定、可无人值守）；查询用 apt-cache（或 apt 的 search/show 子命令）。

**边界/易错点**：apt 和 apt-get 有细微差异——`apt upgrade` 和 `apt-get upgrade` 都只升级现有包，但 `apt full-upgrade` 等价 `apt-get dist-upgrade`（允许增删包以解决依赖）；`apt-get` 是稳定接口，`apt` 官方声明「CLI 不保证稳定」，脚本别依赖 apt 的输出格式。

```shell
apt-get install nginx        # 等价 apt install
apt-get update && apt-get upgrade   # 脚本里常见写法
apt-get dist-upgrade         # 升级 + 允许增删包解决依赖（apt full-upgrade）
apt-cache search 'web server'      # 按描述搜包
apt-cache show nginx               # 包详情
apt-cache policy nginx             # 各源里的候选版本
```

```text
apt vs apt-get vs apt-cache：
1. apt —— 统一命令，交互友好，日常首选（CLI 不保证稳定，别在脚本里依赖输出格式）
2. apt-get —— 老命令，脚本/自动化里常用（输出稳定）
3. apt-cache —— 只查询（搜索/依赖/详情），不修改系统
```

## 工作原理

apt 的核心能力是「自动解析依赖」——安装一个包时，自动算出它依赖哪些库、那些库又依赖什么，一并下载安装。这就是为什么 `apt install` 一个软件能装一堆东西。依赖关系由 .deb 包里的 Depends/Recommends 字段声明，apt 用 SAT 求解器算出完整安装集合。依赖问题（如「依赖冲突」「依赖不可满足」）通常源于：软件源不对/不完整、手动 dpkg -i 装过本地包、混用了第三方源。

```text
# 实测（apt-cache 查包的依赖关系）
$ apt-cache depends nginx | head
nginx
  依赖: nginx-core
  依赖: nginx-full
  依赖: nginx-light
  依赖: nginx-extras
```

```text
apt 依赖解析原理：
1. .deb 包声明 Depends/Recommends 依赖字段
2. apt 用 SAT 求解器算出完整安装集合（缺啥补啥）
3. 依赖问题来源 —— 源不完整、dpkg -i 手动装过、混用第三方源
```

完整执行链：`apt update` 下载各源根下的 Packages 索引（含所有包的版本、依赖、大小）到 /var/lib/apt/lists/ → `apt install pkg` 在本地索引里算依赖集合 → 从源下载对应 .deb 到 /var/cache/apt/archives/ → 逐个调用 dpkg 解包、配置。`apt upgrade` 是「对已装包找更高版本并升级」，`apt full-upgrade`/`dist-upgrade` 额外允许「为满足依赖增删包」。dpkg 配置阶段会跑包自带的维护脚本（preinst/postinst/prerm/postrm），执行服务启动、用户创建等动作。

```text
apt 执行链：
apt update（下载索引）
  → apt 在 /var/lib/apt/lists/ 里算依赖集合
  → 下载 .deb 到 /var/cache/apt/archives/
  → dpkg 解包 + 跑 preinst/postinst 等维护脚本
```

## 常用命令与配置

apt 的日常操作就几条：`apt update`（更新软件源索引）、`apt upgrade`（升级已装包）、`apt install`（安装）、`apt remove`（卸载，保留配置）、`apt purge`（卸载+删配置）、`apt autoremove`（清理不再需要的依赖）、`apt search`（搜索）。记一个原则：update 是「刷新源索引」（改源后必须先 update），upgrade 是「升级包」（生产环境谨慎，可能引入兼容问题）。

```text
# 实测（本机已装包数量）
$ apt list --installed 2>/dev/null | wc -l
1846
```

```shell
apt update                # 刷新软件源索引（改源后必做）
apt upgrade -y            # 升级所有已装包
apt full-upgrade          # 升级 + 允许增删包解决依赖（慎用）
apt install nginx         # 安装
apt install nginx=1.24.0-1   # 安装指定版本
apt remove nginx          # 卸载（留配置）
apt purge nginx           # 卸载 + 删配置
apt autoremove            # 清理无用依赖
apt search 'nginx'        # 搜索包
apt show nginx            # 包详情
apt list --upgradable     # 列出可升级的包
apt download nginx        # 只下载 .deb 不安装
```

```shell
apt-cache depends nginx      # 查看某包的依赖
apt-cache rdepends nginx     # 查看哪些包依赖它
apt install -f               # 修复破损的依赖
apt-cache show nginx         # 看包详情（版本/依赖/描述）
apt-cache policy nginx       # 各源里的候选版本
```

```text
apt 命令语义速记：
update        刷新索引（改源后必做）
upgrade       升级已装包（不增删包）
full-upgrade  升级 + 增删包解决依赖
install       安装（默认带 Recommends）
remove        卸载留配置
purge         卸载 + 删配置
autoremove    清理「不再被依赖」的包
```

## 配置文件解析

apt 的配置分几处：软件源（/etc/apt/sources.list + /etc/apt/sources.list.d/*.list，Ubuntu 24.04 起用 deb822 格式的 .sources 文件）、全局配置（/etc/apt/apt.conf.d/*）、包状态数据库（/var/lib/dpkg/status，记录已装包状态）、下载缓存（/var/cache/apt/archives/）。

```shell
cat /etc/apt/sources.list               # 软件源（老格式）
ls /etc/apt/sources.list.d/             # 第三方源（docker/tailscale 等单独放）
ls /etc/apt/apt.conf.d/                 # apt 全局配置片段
cat /var/lib/dpkg/status | head         # 已装包状态数据库
```

```text
apt 配置位置：
1. sources.list(.d/) —— 软件源，定义从哪下载
2. apt.conf.d/ —— 全局配置（代理、并发、默认选项）
3. /var/lib/dpkg/status —— 包状态数据库（已装包、依赖、版本）
4. /var/cache/apt/archives/ —— 下载的 .deb 缓存
```

```text
# /etc/apt/apt.conf.d/ 常用配置项
Acquire::http::Proxy "http://proxy:8080";   # 代理
Acquire::Languages "none";                  # 不下载翻译索引（加快 update）
APT::Get::Install-Recommends "false";       # 默认不装 Recommends
Dpkg::Options { "--force-confold"; }        # 配置文件冲突时保留旧配置
```

```text
deb822 格式（Ubuntu 24.04+ 的 .sources 文件，多行 key: value）：
Types: deb
URIs: https://mirrors.aliyun.com/ubuntu/
Suites: noble noble-updates noble-backports
Components: main restricted universe multiverse
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
```

## 应用场景实战

### 场景一：安装软件前先查依赖和版本

```shell
# 1. 刷新索引
apt update
# 2. 查包信息（版本、依赖）
apt-cache show nginx | grep -E 'Version|Depends'
# 3. 查依赖关系
apt-cache depends nginx
# 4. 模拟安装（不真正装，看会装什么）
apt install --dry-run nginx
```

### 场景二：清理系统、修复破损依赖

```shell
# 1. 清理无用依赖和缓存
apt autoremove
apt autoclean
# 2. 修复破损依赖
apt install -f
# 3. 排查「apt 报依赖错误」
apt update && apt upgrade --dry-run
```

### 场景三：离线环境搭建本地源（无外网时给内网机器装包）

```shell
# 1. 外网机器下载包及依赖到本地目录
apt-get download nginx
# 2. 用 apt-rdepends 拿完整依赖，批量下载（或用 apt-get install --download-only）
apt-get install --download-only nginx
# 3. 把 /var/cache/apt/archives/ 里的 .deb 拷到离线机器，建立本地索引
dpkg-scanpackages /opt/localrepo /dev/null | gzip > /opt/localrepo/Packages.gz
# 4. 离线机器加本地源
echo "deb [trusted=yes] file:/opt/localrepo ./" > /etc/apt/sources.list.d/local.list
apt update
# 5. 正常安装
apt install nginx
```

```text
离线源关键点：
1. 只拷单个 .deb 不够，要连同依赖一起（--download-only 最省事）
2. dpkg-scanpackages 生成 Packages 索引，apt 才认识这个目录
3. file: 协议 + trusted=yes 免签名校验（内网自建源常用）
4. 正式做法是建 apt-mirror/reprepro 镜像仓库，小规模用上面即可
```

## 性能与调优

apt 的性能调优主要是「下载加速」：换镜像源（国内用阿里云/清华）、开启并发下载（apt 默认单线程，可用 apt-fast 或配置多并发）、清理缓存（autoclean/autoremove）。apt 的缓存机制：下载的 .deb 缓存在 /var/cache/apt/archives，可做本地源复用。

```text
apt 性能要点：
1. 换镜像源 —— 国内用阿里云/清华镜像，下载快好几倍
2. 并发下载 —— apt 默认单线程，apt-fast 或配置并发
3. 清理缓存 —— apt autoclean / autoremove 释放空间
4. 缓存复用 —— /var/cache/apt/archives 的 .deb 可做本地源
```

update 慢的优化：`apt update` 默认会下载各源的翻译索引（Translation-zh_CN 等）和 Contents 文件，实际装包用不到。设 `Acquire::Languages "none";` 跳过翻译索引，update 能快一截。换源后如果 update 报 hash sum mismatch 或慢，通常是镜像没同步完，等一会儿或换另一个镜像。

```shell
# 并发下载配置（/etc/apt/apt.conf.d/76download）
# Acquire::Queue-Mode "access";   # 每个 host 建立多个连接
# Acquire::Retries "3";
# 跳过翻译索引加快 update
echo 'Acquire::Languages "none";' > /etc/apt/apt.conf.d/99translations
```

## 安全与权限

apt 的安全核心是「包签名校验」：软件源索引和 .deb 包都有 GPG 签名，apt 用密钥环（/etc/apt/trusted.gpg.d/）里的公钥验证，防止包被篡改。添加第三方源要导入它的公钥（建立信任），但别随意导入来路不明的密钥。操作权限上，apt/dpkg 都要 root（或 sudo）。

```text
apt 安全要点：
1. 包签名校验 —— .deb 和索引都有 GPG 签名，公钥验证防篡改
2. 密钥环 —— /etc/apt/trusted.gpg.d/ 存公钥
3. 加第三方源先导密钥 —— 建立信任，别乱导来路不明的密钥
4. 权限 —— apt/dpkg 要 root/sudo
```

现代做法（Ubuntu 22.04+）推荐把第三方源公钥存成 .asc 文件放 /etc/apt/trusted.gpg.d/，并在 .sources 里用 `Signed-By:` 指向它，而不是 `apt-key add`（已废弃，会把密钥塞进全局 trusted.gpg 失去按源隔离）。`apt-key list` 能看到现有信任的公钥。供应链安全上，任何「curl xxx | bash」式的安装脚本都绕过 apt 签名校验，比加第三方源风险更高。

```shell
# 给第三方源加公钥（现代做法）
curl -fsSL https://example.com/KEY.gpg | gpg --dearmor -o /usr/share/keyrings/example.gpg
# .sources 里 Signed-By: /usr/share/keyrings/example.gpg
# 查看已信任密钥
apt-key list          # 旧方式（已废弃但仍可用）
```

## 故障排查

### 依赖破损（dpkg 报错、apt 报依赖不满足）

```shell
# 1. 修复破损依赖
apt install -f
# 2. 重新配置未配置完成的包
dpkg --configure -a
# 3. 看具体哪个包有问题
dpkg --audit
```

### 锁被占用（Could not get lock）

```shell
# 1. 看谁占用了锁
lsof /var/lib/dpkg/lock-frontend
# 2. 是残留进程就杀掉（确认不是正在运行的 apt）
ps aux | grep -E 'apt|dpkg'
kill <PID>
# 3. 重试
apt update
```

### 源里找不到包（Unable to locate package）

```shell
# 1. 确认索引已刷新
apt update
# 2. 确认包名正确、在哪个组件（main/universe）
apt search <关键字>
# 3. 确认源是否包含该组件（universe 未开时很多包搜不到）
grep -r 'universe' /etc/apt/sources.list /etc/apt/sources.list.d/
# 4. 需要则加组件/加第三方源（如 Docker 官方源），再 update
```

## 常见问题

```text
Q1: apt update 和 apt upgrade 的区别？
A: update 刷新软件源索引（改源后必做），upgrade 升级已装包（版本更新）。

Q2: apt remove 和 purge 的区别？
A: remove 卸载程序保留 /etc 配置，purge 卸载+删配置。要彻底卸载用 purge。

Q3: dpkg -i 和 apt install 装本地包的区别？
A: dpkg -i 只装不处理依赖（容易依赖破损），apt install ./xxx.deb 自动处理依赖。

Q4: 改了源 install 还报找不到包？
A: 没 apt update 刷新索引，先 update 再 install。

Q5: apt full-upgrade 和 upgrade 区别？
A: upgrade 只升级现有包、不增删包；full-upgrade 允许增删包以满足依赖（更激进，跨大版本升级用）。

Q6: 如何安装指定版本的包？
A: apt install <包名>=<版本号>，可用 apt-cache policy <包名> 看有哪些候选版本。

Q7: 装包时怎么跳过推荐的依赖（Recommends）？
A: apt install --no-install-recommends <包名>，能显著减小安装体积（Docker 镜像里常用）。

Q8: 怎么查一个文件属于哪个包、一个包装了哪些文件？
A: dpkg -S <文件路径> 查归属，dpkg -L <包名> 查文件清单（只对已装包有效）。
```

## 面试题

```text
1. apt 和 dpkg 的分工？
   答：dpkg 底层直接装/卸 .deb 不处理依赖，apt 上层自动解析依赖、从源下载；apt install = 下载+解析依赖+dpkg 安装。

2. apt 怎么处理依赖？
   答：.deb 包声明 Depends 字段，apt 用 SAT 求解器算出完整安装集合，缺的依赖一并下载安装。

3. apt remove 和 purge 区别？
   答：remove 保留配置（/etc 下的配置还在），purge 连配置一起删。重装想清配置用 purge。

4. 遇到依赖破损怎么办？
   答：apt install -f 修复，dpkg --configure -a 重新配置未完成的包，dpkg --audit 看哪个包有问题。

5. apt update 到底更新了什么？
   答：下载各软件源的 Packages 索引（包的版本、依赖、描述）到 /var/lib/apt/lists/，让本地知道「源里现在有什么」，不改系统已装包。

6. apt、apt-get、apt-cache 三者的关系和各自适用场景？
   答：apt 是统一简化版（日常交互用），apt-get 是老命令（脚本用，输出稳定），apt-cache 只查询不修改系统。

7. .deb 包的依赖字段有哪几种？强弱如何分？
   答：Depends（硬依赖，必须满足）、Recommends（默认装、可跳过）、Suggests（建议、不装）、Conflicts（互斥）、Provides（虚拟能力）。Depends 不满足直接装不上。

8. 如何排查「apt 锁被占用」？
   答：lsof /var/lib/dpkg/lock-frontend 看占用进程，确认非正常运行的 apt 后 kill 掉，再重试。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 改软件源后必须先 apt update 刷新索引，否则装不到新包
2. 生产环境 upgrade 要谨慎，先 --dry-run 预览、灰度升级
3. 卸载想彻底就用 purge（删配置），只 remove 会留配置文件
4. 装本地 .deb 优先用 apt install ./xxx.deb（会自动处理依赖），别用 dpkg -i
5. 定期 apt autoremove 清理无用依赖，防止包越积越多
6. 第三方源一个放一个 .list/.sources 文件，公钥存 .gpg 文件用 Signed-By 引用，别用 apt-key add

### 踩坑记录

```text
坑 1：改源后没 update 就 install 报找不到包
结论：加了新源，install 还是报 Unable to locate package。
原因：没刷新索引，apt 不知道新源里有什么。
解法：先 apt update 再 install。

坑 2：dpkg -i 装本地包后依赖破损
结论：dpkg -i xxx.deb 装上了，但 apt 报依赖破损。
原因：dpkg 不处理依赖，缺的依赖没装。
解法：用 apt install ./xxx.deb（自动处理依赖），已破损用 apt install -f 修复。

坑 3：apt remove 后配置还在，重装配置不更新
结论：remove 卸载后重装，老配置还在、改的配置没生效。
原因：remove 只删程序、保留 /etc 下的配置。
解法：要彻底卸载用 apt purge，删掉配置再重装。

坑 4：apt upgrade 升级后服务异常
结论：批量 upgrade 后某个服务起不来。
原因：升级引入了不兼容的新版本，或依赖变化。
解法：生产环境升级前 --dry-run 预览 + 灰度，关键服务单独 pin 版本。

坑 5：autoremove 误删了还在用的包
结论：apt autoremove 把某个「以为没用」的包删了，结果程序报缺库。
原因：apt 按依赖关系判断「不再需要」，有时判断不准。
解法：autoremove 前看清单（--dry-run），确认无误再删。

坑 6：Ubuntu 源里搜不到包，其实是没开 universe 组件
结论：apt search 某包搜不到，但明明官网说有。
原因：该包在 universe/community 组件，默认源只开了 main。
解法：在 sources.list 加 universe 组件，apt update 后再装。

坑 7：apt-key add 导入第三方密钥后源隔离失效
结论：用 apt-key add 加密钥，所有源共用全局 trusted.gpg。
原因：apt-key 已废弃，密钥塞进全局环，任何源都能用这把密钥验证，失去按源隔离。
解法：公钥 dearmor 成 .gpg 放 /usr/share/keyrings/，.sources 里 Signed-By 指向它。
```
