## 概述

「邮件与消息」涵盖两大体系：

1. **邮件服务（Email）**：系统「发信」能力——应用通知、告警、cron 任务报告都靠邮件。Postfix 是 Linux 最主流的邮件服务器（MTA，替代老牌 Sendmail）。核心协议：SMTP（发信）、POP3/IMAP（收信）。生产环境自建「完整」邮件服务器很复杂（反垃圾、认证、TLS、域名信誉），所以常见做法是「Postfix 只做发信（中继到第三方 SMTP），收信用第三方」。
2. **消息服务（Message Queue / Pub-Sub）**：进程间、微服务间异步通信。主流选型：RabbitMQ（AMQP，功能全、路由灵活）、Kafka（高吞吐日志流）、Redis Pub/Sub 与 Stream（轻量）、MQTT（IoT 场景）。本机恰好运行着 RabbitMQ 与 Redis 容器，可做大量实测。

两者共用一条运维主线：**队列（mailq / 消息队列）→ 积压 → 重试 → 死信 → 审计日志**，掌握一套排障思路可互相迁移。

## 核心概念

### 邮件域概念

1. **MUA（邮件用户代理）**：邮件客户端，如 Outlook、Thunderbird、Foxmail、`mail`/`mailx` 命令行。
2. **MSA（邮件提交代理）**：接收 MUA 提交的邮件，通常带认证（587 端口），Postfix 的 `submission` 服务即 MSA。
3. **MTA（邮件传输代理）**：负责邮件的传输/路由，如 Postfix、Sendmail、Exim，是「发信」的核心。
4. **MDA（邮件投递代理）**：把邮件投递到用户邮箱（本地 mailbox/maildir，或转给 Dovecot 等）。
5. **MRA（邮件取件代理）/收信服务器**：Dovecot 等，提供 POP3/IMAP 给 MUA 取信。
6. **SMTP**：简单邮件传输协议，「发信 + 服务器间转发」。明文 25 端口，提交 587（STARTTLS），隐式 TLS 465（SMTPS）。
7. **POP3 / IMAP**：收信协议。POP3（110，下载到本地，多设备不同步）、IMAP（143，服务器端管理，多设备同步，现代主流）；SSL 版 995/993。
8. **MX 记录**：DNS 中声明「谁收这个域名的信」，MTA 投递前先查 MX。
9. **中继（relay）**：把邮件转发到别的服务器——如自建 Postfix 把邮件中继给企业邮箱/第三方 SMTP，避免自建完整邮件体系的复杂度。
10. **别名（alias）**：`/etc/aliases` 把地址映射到本地用户、文件、命令或外部地址（如 `root: admin@example.com`）。

```text
邮件链路：MUA → MSA(587 认证) → MTA(25 路由) → 对方 MTA → MDA → 邮箱 → MUA(POP3/IMAP)
端口速记：25=服务器间 SMTP、587=客户端提交 STARTTLS、465=隐式 TLS、110/143=收信、995/993=收信 SSL
```

### 消息服务概念

1. **消息队列（Message Queue）/ 消息中间件**：生产者把消息交给 Broker，消费者异步拉取/订阅，实现解耦、削峰、异步化。
2. **Broker**：消息服务端（RabbitMQ 节点 / Kafka 集群 / Redis / mosquitto）。
3. **生产者 / 消费者（Producer / Consumer）**：发消息的一方 / 收消息的一方。
4. **Exchange（交换机）**：RabbitMQ 路由中枢，消息先进交换机，按类型和 routing key 路由到队列；类型：direct / topic / fanout / headers。
5. **Queue（队列）**：消息存储地，消费者从这里取消息；可设置持久化（durable）、TTL、死信。
6. **Binding（绑定）**：交换机与队列的关联关系，含 routing key。
7. **ACK / NACK**：消费者处理完回执；nack/不确认则消息重回队列或进死信。
8. **prefetch**：消费者一次最多预取多少条未确认消息（限流，防积压失衡）。
9. **持久化**：交换机/队列/消息三重持久化后，Broker 重启不丢消息。
10. **死信队列（DLX/DLQ）**：被拒、过期、超限的消息转入的死信交换机/队列。
11. **Topic / Partition / Offset（Kafka）**：主题按分区并行存储，消费者组内每个分区同一时刻只由一个成员消费，offset 记录消费进度。
12. **Pub/Sub（Redis）**：发布订阅，消息即发即焚，无存储、无历史；**Stream** 是 Redis 5.0+ 的持久化消息结构，支持消费组与 ACK。
13. **MQTT**：面向 IoT 的轻量发布订阅协议，基于 topic 层级（`sensor/room1/temp`），QoS 0/1/2 三级可靠性。
14. **QoS（服务质量）**：MQTT 消息投递可靠性级别；也泛指 RabbitMQ 的投递确认语义。

## 工作原理

### 邮件发送全流程（一次完整投递）

```text
发件人 MUA → [SMTP 587 提交] → 发件方 MSA/Postfix → 队列 → 查 MX 记录
→ [SMTP 25 服务器间投递] → 收件方 MTA → 过滤/反垃圾 → MDA → 本地邮箱
→ 收件人 MUA 通过 [POP3/IMAP] 取信
```

1. 发件人 MUA（客户端）通过 SMTP 提交（submission，587，带认证）把信交给发件人域的 MTA（Postfix）。
2. Postfix 将邮件放入队列，查 DNS 的 MX 记录确定收件人域名对应的邮件服务器地址。
3. Postfix 用 SMTP（25 端口）与对方 MTA 建连，投递邮件。
4. 对方 MTA 收信后交给 MDA 投递到用户邮箱（mailbox/maildir，或交给 Dovecot 管理）。
5. 收件人用 MUA 通过 POP3/IMAP 从 Dovecot 取信。

**自建发信（Postfix 中继）的简化流程**：应用/系统 → Postfix → 中继到第三方 SMTP（企业邮箱/Gmail/QQ 邮箱）→ 对方收件人。第三方替你解决反垃圾、反向解析、域名信誉问题，这是中小团队的标配做法。

### SMTP 会话原理（telnet 手工测试）

SMTP 是基于文本行的协议，一条命令一行，服务器以三位数字状态码应答。可以用 telnet 直接模拟一次发信（这也是排障的杀手锏）：

```shell
# 手工 SMTP 会话测试（本机未装 postfix 时连 smtp.qq.com:25 亦可，但公网 25 常被云厂商封禁）
telnet mail.example.com 25
```

```text
220 mail.example.com ESMTP Postfix
HELO client.example.com
250 mail.example.com
MAIL FROM:<sender@example.com>
250 2.1.0 Ok
RCPT TO:<receiver@example.com>
250 2.1.5 Ok
DATA
354 End data with <CR><LF>.<CR><LF>
Subject: test

hello world
.
250 2.0.0 Ok: queued as 4F1A2B3C4D
QUIT
221 2.0.0 Bye
```

关键应答码：`220` 就绪、`250` 成功、`354` 等待数据、`421` 服务不可用、`450/451` 临时失败（稍后重试）、`550/554` 永久失败（退信）。

### RabbitMQ 消息流转原理

```text
Producer → Exchange →（按 type + routing key 匹配 Binding）→ Queue → Consumer
                 ↑                                    ↑
            direct/topic/fanout/headers           ACK/NACK、prefetch、TTL、DLX
```

- **direct**：routing key 完全匹配才投递（点对点）。
- **topic**：routing key 支持通配 `*`（匹配一个词）和 `#`（匹配零或多个词），适合按事件类型路由。
- **fanout**：广播给所有绑定队列，忽略 routing key。
- **headers**：按消息头（键值对）匹配，最灵活也最慢，实际用得少。

消息确认：消费者处理完必须回 ACK，否则 Broker 认为未处理完（basic.ack 未回、连接断开、nack/requeue），消息会被重新投递——这是「至少一次」语义的保证。

### Redis Pub/Sub 与 Stream 原理

- **Pub/Sub**：`SUBSCRIBE ch` 订阅、`PUBLISH ch msg` 发布。消息**不落盘**，发送时没有订阅者则消息直接丢弃；订阅者掉线期间的消息也丢失。适合实时广播、缓存失效通知。
- **Stream**：`XADD` 追加、`XRANGE` 读取、`XREAD` 阻塞读、`XGROUP` 消费组、`XACK` 回执。数据持久化在内存/磁盘（按配置），支持消费者组（类似 Kafka 分区消费）与 ACK，可做轻量消息队列。

### Kafka 原理简述

- Topic 分为多个 Partition，Partition 内消息有序，分区可并行消费、横向扩展。
- 消费者组内，一个分区同一时刻只分配给组内一个消费者；组内成员变动触发 rebalance。
- 消费进度用 offset 记录（自动提交或手动提交）；`__consumer_offsets` 内部主题保存 offset。
- 高吞吐秘诀：顺序写磁盘 + 页缓存 + 零拷贝 + 批量/压缩。

### MQTT 原理简述

- 轻量发布订阅协议（TCP 1883，TLS 8883），基于 topic 层级 `a/b/c`，`+` 匹配单层、`#` 匹配多层。
- QoS 0：至多一次（可能丢）；QoS 1：至少一次（可能重复）；QoS 2：恰好一次（四段握手，开销最大）。
- 适合 IoT：传感器上报、设备控制；mosquitto 是最常用的开源 Broker。

### 消息服务选型对比表

| 维度 | RabbitMQ | Kafka | Redis Pub/Sub | Redis Stream | MQTT(mosquitto) |
|---|---|---|---|---|---|
| 协议 | AMQP 0-9-1 | 自定义（二进制） | RESP | RESP | MQTT |
| 吞吐 | 万级/秒 | 百万级/秒 | 高 | 较高 | 低（IoT 场景够用） |
| 延迟 | 微秒~毫秒 | 毫秒级 | 亚毫秒 | 亚毫秒 | 毫秒级 |
| 消息模型 | 队列 + 交换机路由 | 分区日志（可回放） | 即发即焚广播 | 流 + 消费组（可回放） | topic 发布订阅 |
| 可靠性 | ACK/持久化/死信 | 副本 + offset | 无（会丢） | ACK/持久化 | QoS 0/1/2 |
| 典型场景 | 业务异步、延迟任务、RPC | 日志、埋点、事件流 | 缓存失效广播、聊天 | 轻量队列、时序采集 | 智能家居、传感器 |
| 运维成本 | 中 | 高（依赖 ZK/KRaft） | 极低 | 低 | 极低 |

## 常用命令与配置

### 邮件相关命令

```shell
# 安装（Debian/Ubuntu；Red Hat 系：dnf install postfix mailx）
apt install postfix mailutils

# 发送邮件
echo "内容" | mail -s "主题" user@example.com
echo "内容" | mailx -s "主题" -a /path/附件 user@example.com

# 查看队列
mailq                     # 等价 postqueue -p，列出待发/卡住的邮件
postqueue -p -v           # 更详细（含重试原因）

# 队列管理
postqueue -f              # 强制冲刷队列（立即重试所有邮件）
postqueue -c /etc/postfix # 指定配置目录
postsuper -d ALL          # 删除队列全部邮件（危险！）
postsuper -d 4F1A2B3C4D   # 删除指定邮件
postsuper -r ALL          # 重新排队（重新进入队列处理流程）
postcat -q 4F1A2B3C4D     # 查看队列中某封邮件的完整内容/错误原因

# 别名与认证
newaliases                # 编译 /etc/aliases 为 aliases.db
postmap /etc/postfix/sasl_passwd   # 编译认证密码文件为 hash 库

# 服务与日志
systemctl restart postfix
journalctl -u postfix -n 50
tail -f /var/log/mail.log          # Ubuntu；Red Hat 系为 /var/log/maillog

# 手工 SMTP 测试与 DNS 检查
telnet mail.example.com 25         # 见「工作原理」的会话示例
dig MX example.com                 # 查邮件服务器
dig TXT example.com                # 查 SPF/DKIM/DMARC 记录
dig -x 1.2.3.4                     # 查反向解析 PTR
```

### Redis 消息命令

### Postfix 主配置 /etc/postfix/main.cf（发信中继到第三方 SMTP 的典型配置）


### 场景三：RabbitMQ 延迟队列 + 死信队列（订单超时取消）

本机 RabbitMQ 上恰好跑着真实的 `orjuice.order.delay` / `orjuice.order.dlx` 模式，可直接对照。

```shell
# 思路：消息先进「延迟队列」（TTL 30 分钟，无消费者），过期后被 RabbitMQ 转入死信交换机
# 死信交换机按 routing key 投递到真正的业务队列，消费者只消费业务队列即可
# 1. 声明延迟交换机 + 延迟队列（TTL 参数），队列设置 x-dead-letter-exchange
docker exec rabbitmq4.3.4 rabbitmqctl list_queues name arguments   # 查看现有参数
# 2. 生产者：把「订单超时检查」消息发到延迟交换机，routing key=order.cancel
# 3. 30 分钟后消息过期 → 自动进入 orjuice.order.cancel.queue.actual
# 4. 消费者：处理订单取消（对照本机 binding：orjuice.order.dlx → actual，routing key=order.cancel.dlx）
```

```text
本机对照（list_exchanges + list_bindings 实测输出见「常用命令与配置」）：
orjuice.order.delay (direct) --TTL--> 过期消息 → orjuice.order.dlx (direct)
  --routing key: order.cancel.dlx--> orjuice.order.cancel.queue.actual（真正被消费的队列）
```

要点：延迟队列必须有消费者以外的投递路径；死信交换机的 routing key 用「原 routing key」还是「死信消息属性中的 routing key」取决于声明参数（`x-dead-letter-routing-key`）。

## 性能与调优

### Postfix 发信性能

```text
1. 队列管理 —— 大量邮件时队列堆积：postqueue -f 冲刷；调大并发投递参数
2. 并发控制 —— main.cf：
   default_process_limit = 100        # 同时运行的投递进程数上限
   smtp_destination_concurrency_limit = 20   # 到同一目标的最大并发连接
   smtp_destination_recipient_limit = 50     # 单封邮件最多收件人数
3. 连接复用 —— 中继到同一 SMTP 复用连接（keepalive），减少握手开销
4. 别用自建 Postfix 群发 —— 营销邮件用专业 ESP（SendGrid/阿里云邮件推送），
   第三方 SMTP 有频率限制，群发会触发对方限流/封号
5. 队列重试 —— 失败邮件自动指数退避重试（默认 5 分钟起步递增），
   长时间失败会生成退信（bounce）通知发件人
```

### RabbitMQ 调优

```text
1. prefetch —— basic.qos(prefetch_count=N)：消费者限流关键，
   处理慢/耗时长任务设小（如 1~10），防止消息堆积在单个消费者内存
2. 持久化权衡 —— durable 队列 + persistent 消息最稳但最慢；
   可丢场景用 transient 换吞吐
3. 内存/磁盘水位 —— vm_memory_high_watermark、disk_free_limit，
   超限 broker 会阻塞生产者（connection.blocked），监控 alert 要接上
4. 惰性队列 —— lazy queue（4.x 内建）落盘换内存，适合长队列/突发积压
5. 集群 —— 镜像队列（3.x）/Quorum 队列（4.x 推荐），
   跨节点复制防单点；见 [[19.5-集群与一致性]]
```

### Kafka / Redis Stream / MQTT 调优要点

```text
Kafka：分区数 = 目标并行度（消费者数 ≤ 分区数才吃得满）；
       acks=all + min.insync.replicas 保不丢；批量大小/压缩（lz4/zstd）提吞吐
Redis Stream：XTRIM MAXLEN 定期裁剪；消费组并发 = 组内消费者数（同组竞争不同消息）；
       maxmemory-policy 必须 noeviction，否则队列消息会被淘汰丢失
MQTT：QoS 1 + 持久会话（clean_session=false）平衡可靠性与开销；
      大量小消息优先压缩与合并上报（网关聚合）
```

## 安全与权限

### 邮件安全

```text
1. 绝不做 open relay —— 中继来源限制 mynetworks + 587 认证，
   否则任何人可借你的服务器群发垃圾邮件，IP 秒进黑名单
2. TLS 全链路 —— 提交口 smtpd_tls_security_level=encrypt；
   出站中继 smtp_tls_security_level=encrypt；465/587 优先
3. 认证凭据 —— sasl_passwd 权限 600，只允许 root 读；
   用授权码而非登录密码，泄露后立即轮换
4. SPF —— 发信域名 DNS TXT 记录声明「哪些 IP 允许以本域发信」：
   example.com.  TXT  "v=spf1 ip4:1.2.3.4 include:_spf.qq.com ~all"
5. DKIM —— 签名私钥（opendkim 生成），DNS 发布公钥：
   default._domainkey.example.com.  TXT  "v=DKIM1; k=rsa; p=MIGfMA0G..."
6. DMARC —— 声明验签失败策略 + 收报告邮箱：
   _dmarc.example.com.  TXT  "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com"
7. 反向解析 PTR —— 发信 IP 必须能反解且与 HELO/域名匹配，否则大概率被 554 拒收
8. 端口收敛 —— 25 只对公网 MTA 开放；内部服务器只用 587 提交，减少暴露面
```

```shell
# 检查 SPF/DKIM/DMARC（本机 dig 可用）
dig TXT example.com | grep spf
dig TXT default._domainkey.example.com
dig TXT _dmarc.example.com
dig -x <发信IP>          # PTR 反解检查
```

### 消息服务安全

```text
1. 认证 —— RabbitMQ 必须给 guest 设 loopback 限制/删 guest；
   本机实测已只剩 admin 用户（list_users 见上文），生产再配独立账号 + 密码策略
2. vhost 隔离 —— 不同业务/环境用不同 vhost，权限按 vhost 粒度下发
3. 权限粒度 —— RabbitMQ 每个用户每 vhost 有 configure/read/write 三组正则权限
4. TLS —— AMQPS 5671、管理 UI 15671；Redis 开启 requirepass（本机实测已开启），
   Redis 6+ 可用 ACL（user xxx on >pass ~keys* +@all）
5. 网络暴露 —— 6379/5672 只允许内网/生产网段；切勿映射公网
   （Redis 无认证 + 公网 = 挖矿蠕虫最爱，见 [[23.1-系统加固]]）
6. SELinux（Red Hat 系）—— 消息服务监听/连接被 SELinux 拦截是常见坑：
   setsebool -P httpd_can_network_connect 1（应用连 RabbitMQ/Redis）
   setsebool -P postfix_can_network 1（Postfix 出站）；拒绝日志查 /var/log/audit/audit.log
7. firewalld（Red Hat 系）—— 放行邮件与消息端口：
   firewall-cmd --permanent --add-service=smtp --add-port=587/tcp --add-port=465/tcp
   firewall-cmd --permanent --add-port=5672/tcp --add-port=15672/tcp
   firewall-cmd --reload
```

### 案例三：RabbitMQ 消息堆积，消费者不消费

```shell
# 症状：list_queues 显示 messages 持续增长

# 4. 确认没有被阻塞（连接被限流）：list_connections 看 blocked/flow 状态
docker exec rabbitmq4.3.4 rabbitmqctl list_connections name state
# 5. 确认内存/磁盘水位：rabbitmqctl status 看 memory/disk alarms
docker exec rabbitmq4.3.4 rabbitmqctl status | grep -A5 alarms
```

## 常见问题

```text
Q1: 自建邮件服务器还是用第三方？
A: 完整自建（收+发+反垃圾+域名信誉）成本很高。常规做法：
   「Postfix 发信（中继第三方 SMTP）+ 第三方收信」即满足 90% 的运维需求；
   有独立收发需求且预算充足才考虑全套自建（Postfix+Dovecot+SPF/DKIM/DMARC）。

Q2: SMTP、POP3、IMAP 有什么区别？
A: SMTP 负责发信（推），POP3/IMAP 负责收信（拉）。
   POP3 把邮件下载到本地、服务器不留（多设备不同步）；
   IMAP 邮件留在服务器端管理，多设备状态同步，是现代主流。

Q3: 邮件明明发出去了，对方却在垃圾箱？
A: 三件套没配齐：SPF 未覆盖发信 IP、无 DKIM 签名、DMARC 策略缺失；
   另发信 IP 无 PTR 反解或 IP 信誉差（共享 IP 被他人拖累）。
   解法：配齐 SPF/DKIM/DMARC + PTR + 固定发信 IP，用独立域名发业务邮件。

Q4: mailq 里邮件卡住怎么办？
A: 先 postcat -q <ID> 看卡住原因（认证失败/连接超时/被拒）；
   可修复则 postqueue -f 立即重试；确认永久失败的用 postsuper -d 删除，
   避免队列无限膨胀拖垮 qmgr。

Q5: 邮件被 554 拒收，常见的 554 有哪几种？
A: 554 5.7.1 Relay access denied（对方拒绝你的中继/来源 IP）；
   554 5.7.1 Sender address rejected（SPF/DMARC 失败）；
   554 5.4.0 投递超时/链路问题。逐类对应：修中继限制/配 SPF/查网络。

Q6: RabbitMQ 消息会不会丢？怎么保证不丢？
A: 可能丢的三个环节：生产者发送（publisher confirm）、Broker 存储
   （队列+消息都要 durable 持久化）、消费者处理（手动 ACK，不自动 ack）。
   三者全配齐才是不丢的最小集合；还要注意内存/磁盘水位告警。

Q7: RabbitMQ 和 Kafka 怎么选？
A: 业务异步、任务队列、延迟任务、RPC、路由灵活 → RabbitMQ；
   海量日志/埋点/事件流、需要重放、超高吞吐 → Kafka；
   两者都能做队列，但 Kafka 不适合复杂路由和低频小消息（延迟和成本都吃亏）。
   Redis Stream 是「轻量、可回放、运维零成本」的中间派；MQTT 专供 IoT。

Q8: Redis Pub/Sub 和 Stream 什么区别？什么时候用哪个？
A: Pub/Sub 即发即焚、无存储、无历史、订阅者掉线即丢，适合缓存失效广播、
   实时通知；Stream 持久化、可回放、支持消费组和 ACK，适合做轻量消息队列、
   采集暂存。需要「不丢、可重放、多消费者分工」就用 Stream。
```

## 面试题

```text
1. MTA、MSA、MDA、MUA 分别是什么？各自在邮件链路中干什么？
   答：MUA 是客户端（Outlook/mail 命令），负责写信收信；
   MSA 接收客户端提交（587 带认证）；MTA 负责传输路由（Postfix，查 MX 投递）；
   MDA 把邮件投递到本地邮箱（或交给 Dovecot）。链路：
   MUA→MSA→MTA→MX→对方 MTA→MDA→邮箱→MUA(POP3/IMAP)。

2. 为什么企业邮件一般建议「Postfix 中继第三方 SMTP」而不是全自建？
   答：全自建需要处理 SPF/DKIM/DMARC、PTR 反解、IP 信誉、反垃圾、
   黑名单申诉等一堆与协议无关但决定送达率的事，成本高且易翻车；
   中继第三方把送达率问题外包，自己只管把信交给第三方（587+TLS+SASL）。

3. 什么是 open relay？如何防止？
   答：MTA 允许任何来源任意目标转发邮件即为开放中继，会被垃圾邮件滥用、
   导致 IP 进黑名单。防：mynetworks 限制可信网段、submission 口强制 SASL 认证、
   拒绝匿名（smtpd_sasl_security_options=noanonymous）、连接数限制。

4. SPF、DKIM、DMARC 各解决什么问题？记录长什么样？
   答：SPF 用 DNS TXT 声明允许哪些 IP 以该域发信（防伪造发件域）；
   DKIM 对邮件签名、DNS 发布公钥（防内容篡改、验证发件域真实性）；
   DMARC 声明验签失败后的策略（none/quarantine/reject）并收报告。
   例：v=spf1 ip4:1.2.3.4 ~all；v=DKIM1; k=rsa; p=...；v=DMARC1; p=quarantine。

5. RabbitMQ 四种交换机类型及典型用途？
   答：direct——routing key 精确匹配，点对点任务队列；
   topic——通配匹配（* 一个词、# 多个词），按事件类型路由；
   fanout——广播给所有绑定队列，通知扇出；
   headers——按消息头匹配，最灵活少用。

6. 如何保证 RabbitMQ 消息不丢？生产者/消费者两个视角分别怎么做？
   答：生产者：publisher confirm（confirm.select + 等待 ack）+ mandatory 参数
   兜底路由失败；消费者：关闭自动 ack，处理成功后手动 basic.ack，
   失败有限重试后 nack 进死信队列；Broker：durable 队列 + persistent 消息，
   集群用 Quorum 队列/镜像队列。

7. Kafka 中 Partition 和 Consumer Group 是什么关系？为什么 lag 会增长？
   答：Topic 分成多个 Partition 并行存储；同组消费者共同消费整个 Topic，
   一个分区同一时刻只分配给组内一个消费者（分区数≥消费者数才能吃满并行）。
   lag=消息生产速度大于消费速度或消费者不足/处理慢/rebalance 频繁。

8. 邮件服务器被拒收（554）的排查顺序？
   答：先看退信/日志确认拒绝码；查 PTR 反解是否匹配 HELO；
   查 SPF 是否覆盖发信 IP；查 DKIM 验签；查黑名单（mxtoolbox）；
   修复后用 telnet 25 手工会话复测；确认 DNS 记录生效（dig TXT）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 发信用 Postfix 中继第三方 SMTP，别轻易自建完整邮件服务器；收信交给专业服务。
2. 发信域名必须配齐 SPF + DKIM + DMARC + PTR 反解，这是送达率的生死线。
3. 认证密码文件权限 600，中继与提交口全程 TLS；绝不做开放中继。
4. 监控三件套：mailq 队列长度、/var/log/mail.log 错误、RabbitMQ 队列积压与内存/磁盘水位告警。
5. RabbitMQ 生产标配：publisher confirm + durable 队列 + 手动 ACK + 死信队列 + prefetch 限流。
6. Redis 做消息必须开 requirepass + 禁公网暴露 + maxmemory-policy noeviction（队列场景）。
7. 需要可回放/不丢的场景用 Stream/Kafka，别用 Pub/Sub（即发即焚）。
8. 消息幂等：消费端处理必须幂等（重投是常态，不是异常）。
9. cron/脚本告警走邮件，但先验证发信链路（echo | mail 自测），别等故障时才发现收不到。
10. 运维文档化：把本机 RabbitMQ 队列/交换机清单（rabbitmqctl list_*）纳入巡检脚本。

### 踩坑记录

坑 1：配成 open relay 被垃圾邮件滥用
结论：服务器被利用群发垃圾邮件，IP 被各大反垃圾组织拉黑，正常邮件全被拒收。
原因：没限制中继来源（mynetworks 空/过宽，或 smtpd 默认允许任意来源任意目标转发）。
解法：mynetworks 只留可信网段 + 587 强制 SASL 认证 + noanonymous；开放前先自查（telnet 25 试发外部地址）。

坑 2：邮件进了垃圾箱，查不出原因
结论：发信状态 sent，但对方收件箱里没有（在垃圾箱），业务方以为丢了。
原因：没配 SPF/DKIM，或发信 IP 无 PTR、信誉差（共享 IP 被他人拖累）。
解法：配 SPF + DKIM + DMARC + PTR，业务邮件用独立域名和固定 IP；用 mxtoolbox 验证。

坑 3：cron 设了 MAILTO 但收不到告警
结论：任务失败时没收到任何邮件，故障静默。
原因：没装/没配邮件服务（Postfix），本地投递都失败；或 MAILTO 地址写错域。
解法：先 apt install postfix 配好中继发信，echo 自测通过后再设 MAILTO；/etc/aliases 里 root 转运维邮箱。

坑 4：中继第三方 SMTP 认证失败（535/454）
结论：Postfix 日志刷 535 Authentication failed，邮件卡队列。
原因：密码/授权码写错（QQ/163 必须用授权码不是登录密码）；或改了 sasl_passwd 没执行 postmap。
解法：确认授权码正确；改完 sasl_passwd 必须 postmap 生成 hash 并 reload；权限 600。

坑 5：邮件卡在队列无限重试，队列爆炸
结论：mailq 上千封邮件堆积，qmgr 处理变慢，系统磁盘被 /var/spool/postfix 撑满。
原因：中继服务器长时间不可达/认证持续失败，邮件按退避策略无限重试，没人清理。
解法：postcat 定位根因；可修复则 postqueue -f；永久失败用 postsuper -d ALL 清空；加队列长度监控告警。

坑 6：RabbitMQ 消费者异常 nack 死循环，消息永远处理不了
结论：队列消息数不降反升，消费者日志疯狂刷异常，CPU 飙高。
原因：消费代码没 catch 异常就 nack 且 requeue=true，坏消息无限重投。
解法：try/catch + 有限重试（重试 N 次后 requeue=false），配死信交换机收容坏消息；本机 kb.doc.index.dlq 即此模式。

坑 7：Redis Pub/Sub 消息「丢失」被当成故障
结论：发布端返回 1（有订阅者），但业务说数据没同步。
原因：Pub/Sub 即发即焚——订阅者掉线/重启瞬间发布的消息直接丢弃；或发布时机早于订阅建立。
解法：需要不丢就换 Redis Stream（消费组+ACK）或 RabbitMQ；Pub/Sub 只用于可容忍丢失的实时广播；重连后必须重新 SUBSCRIBE。

坑 8：RabbitMQ 服务「假死」——连接被阻塞（blocked）
结论：生产者 publish 超时，应用大面积报错，rabbitmqctl 却显示节点正常。
原因：内存/磁盘水位告警触发，broker 主动阻塞连接（connection.blocked），等水位恢复。
解法：看 list_connections 的 state（blocked/flow）；降低内存水位、清理积压队列；监控 alarms 并扩容/加磁盘。

坑 9：Red Hat 系 SELinux 拦截 Postfix/消息服务网络
结论：服务明明启动了，邮件发不出、应用连不上 RabbitMQ，查日志全是 Permission denied。
原因：SELinux 默认策略拦截进程网络出站/监听（postfix_can_network、httpd_can_network_connect 未开）。
解法：setsebool -P postfix_can_network 1 / httpd_can_network_connect 1；拒绝详情看 /var/log/audit/audit.log；别图省事 setenforce 0。
