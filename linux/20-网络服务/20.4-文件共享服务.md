## 概述

文件共享服务让「多台机器/多个用户」访问同一份数据，按需求分五类：**NFS**（Linux 间文件级共享，挂载即用）、**Samba/SMB**（跨平台，Linux 与 Windows 互访的事实标准）、**FTP/FTPS**（传统传输协议，明文已弃用）、**SFTP**（基于 SSH 的加密文件传输，FTP 的现代替代）、**WebDAV**（基于 HTTP 的分布式文件协议，适合跨平台挂载）。另有 rsync 做增量同步（复制而非挂载），见 [[18.3-文件同步]]。

选型速记：**纯 Linux 环境用 NFS；要接 Windows 用 Samba；传文件优先 SFTP（别用 FTP）；跨公网/异构用 SFTP 或 WebDAV；备份同步用 rsync**。

```text
# 实测（本机）——Ubuntu 24.04.4 LTS（内核 7.0.0-28-generic），共享服务现状
```

## 核心概念

1. **NFS**（Network File System）：Linux 间文件级共享协议，服务端把目录「导出」（export），客户端 `mount` 后像本地目录一样访问；基于 RPC（Sun RPC）传输，NFSv4 起整合了挂载协商，端口收敛为 2049 单端口。
2. **NFS 版本**：v3（多 RPC 端口 + rpcbind，兼容老系统）、v4/v4.1（单端口 2049、有状态、支持锁与 Kerberos 认证）、v4.2（稀疏文件、克隆等增强）。现代环境默认 v4.2。
3. **Samba**：SMB/CIFS 协议的开源实现，让 Linux 目录以「网络共享」形式被 Windows/macOS/Linux 访问；含 smbd（文件共享，445/tcp）、nmbd（NetBIOS 名称解析，137/138/139）。
4. **SMB 协议版本**：SMB1（Win98~XP 时代，有 EternalBlue/WannaCry 等漏洞，**必须禁用**）、SMB2/2.1（Vista/2008）、SMB3/3.1.1（Win8/2012+，支持端到端加密，当前主流）。
5. **FTP**：传统文件传输协议，**双通道**（控制连接 21/tcp + 数据连接另开），密码与数据默认明文，主动/被动两种模式，NAT 环境兼容性差，已被 SFTP 取代。
6. **SFTP**：不是 FTP 的加密版，而是「**SSH 的文件传输子系统**」——走 22 端口、复用 SSH 认证（密码/密钥）、单连接全加密。无需额外服务端（sshd 自带 sftp-server）。
7. **WebDAV**：HTTP 的扩展（PUT/DELETE/PROPFIND/MKCOL 等方法），通过 nginx/apache 模块提供，客户端（davfs2、Windows 映射驱动器、macOS Finder）可直接挂载。
8. **root_squash**：NFS 的权限映射机制——默认把客户端 root 映射为匿名用户 nobody，防止客户端 root 在服务端拥有 root 权限（文件系统级共享的安全基石）。
9. **导出（export）与挂载（mount）**：服务端 `exports` 声明「谁可以挂哪个目录、什么权限」；客户端 `mount` 建立访问关系。导出选项（rw/ro、sync/async、root_squash）决定共享边界。

```text
五种方式一句话：
NFS     Linux↔Linux 挂载共享（文件级，RPC）
Samba   Linux↔Windows 挂载共享（SMB 协议）
FTP     老式传输（双通道+明文，弃用）
SFTP    SSH 通道加密传输（现代替代）
WebDAV  HTTP 上的文件协议（跨平台挂载）
rsync   增量同步（复制，非挂载）→ 见 18.3
```

## 工作原理

### NFS：导出 → 挂载 → RPC 访问

```text
NFS 服务端                                  NFS 客户端
/etc/exports 声明导出                          mount -t nfs 服务器:/data /mnt/data
   /data 192.168.1.0/24(rw,sync)  ────────▶   挂载后 /mnt/data 就是 /data
        │                                        │
        └─ rpcbind(111) 端口协商 ←───────────────┤  （NFSv3 需要；v4 固定 2049）
        └─ nfsd(2049/tcp+udp) ←──────────────────┘  文件读写经内核 NFS 客户端
                                                      直连 nfsd，走 RPC 协议
```

- **NFSv3**：挂载前客户端先问 rpcbind（111）拿到 mountd/nlockmgr/statd 等服务的端口，之后多端口通信，防火墙配置繁琐。
- **NFSv4**：把挂载协商并入协议本身，**只用 2049 端口**（及可选 rpcbind 做兼容），穿透防火墙简单，支持锁、ACL、Kerberos（sec=krb5/krb5p）。现代环境一律 v4。
- **权限叠加**：客户端能否访问 = exports 选项（rw/ro、网段白名单）**AND** 服务端目录的 Unix 权限（owner/group/mode）**AND** 用户映射结果（root_squash 等）。任何一层拒绝都表现为 Permission denied。

### Samba：SMB 会话 + 共享认证

```text
Windows 客户端                                        Linux smbd
  连接 \\192.168.1.100\share ── TCP 445 ──▶  SMB 协商（协议版本）
  输入用户名/密码 ──────────── SMB 会话建立 ─▶  passdb 校验（smbpasswd/tdbsam）
  访问 share ───────────────── 打开句柄 ─────▶  映射到 /data/share + Unix 权限检查
```

SMB 报文经 445/tcp（SMB over TCP）；老客户端/NetBIOS 场景走 139/tcp（445 失败时回退）。认证默认 `security = user`，用 Samba 自己的密码库（smbpasswd -a 创建，与系统密码相互独立，但账号必须是系统已有用户）。

### FTP：双通道的两种模式

```text
主动模式（Active，服务器连客户端）              被动模式（Passive，客户端连服务器）
客户端:1025 ──21──▶ 服务器:21   控制通道       客户端:1025 ──21──▶ 服务器:21   控制通道
客户端:1026 ◀──20── 服务器:20   数据通道       客户端:2000 ──40000─▶ 服务器:40000  数据通道
  服务器主动连客户端 → 被 NAT/防火墙挡 ❌         服务器开随机端口等客户端连 ✅（NAT 友好）
```

被动模式下服务器必须开放一段数据端口（vsftpd 配 `pasv_min_port`/`pasv_max_port`，如 40000~40100），防火墙/NAT 需同时放行控制端口 21 与数据端口段，这是 FTP 部署最常见的坑。FTPS 在控制通道上用 TLS（AUTH TLS）加密。

### SFTP：SSH 子系统

SSH 登录后由 `sftp-server` 子系统处理文件操作，**单连接、单端口（22）、全加密**，认证与 SSH 完全一致（密码/密钥/双因素），天然穿透 NAT。这也是「SFTP 优于 FTP」的根本原因：不需要第二通道、没有被动端口问题、没有明文风险。

```text
原理速记：
NFS = exports 导出 + mount 挂载 + RPC（v4 单端口 2049）
Samba = SMB 445 协商 + passdb 认证 + Unix 权限双保险
FTP = 21 控制 + 数据通道（主动 20/被动随机端口）→ NAT 噩梦
SFTP = SSH 22 单通道加密，无需额外服务端
```

## 常用命令与配置

```shell
# ---------- NFS 服务端 ----------
apt install nfs-kernel-server        # Red Hat 系：dnf install nfs-utils
echo '/data 192.168.1.0/24(rw,sync,no_subtree_check)' >> /etc/exports
exportfs -ra                         # 重新加载导出（不用重启服务）
exportfs -v                          # 查看当前导出及选项
showmount -e 127.0.0.1               # 查看本机导出列表（客户端视角用服务器 IP）
systemctl restart nfs-server         # Red Hat 系同为 nfs-server

# ---------- NFS 客户端 ----------
apt install nfs-common               # Red Hat 系：nfs-utils 已含
mount -t nfs -o rw,sync,soft,noatime 192.168.1.100:/data /mnt/data
mount | grep nfs                     # 查看挂载
umount /mnt/data
# fstab 持久化（_netdev：网络就绪后再挂，避免开机卡死）
echo '192.168.1.100:/data /mnt/data nfs rw,sync,soft,noatime,_netdev 0 0' >> /etc/fstab

# ---------- Samba ----------
apt install samba                    # Red Hat 系：dnf install samba（服务名 smb/nmb）
testparm                             # 语法检查 smb.conf
smbpasswd -a alice                   # 创建 samba 用户（alice 须是系统用户）
systemctl restart smbd               # Red Hat 系：systemctl restart smb
smbclient -L //192.168.1.100 -U alice    # 列出服务器共享
smbclient //192.168.1.100/share -U alice # 交互式访问（get/put/ls）
smbstatus -b                         # 当前连接
mount -t cifs //192.168.1.100/share /mnt -o username=alice,uid=1000,gid=1000,vers=3.0

# ---------- vsftpd ----------
apt install vsftpd                   # Red Hat 系：dnf install vsftpd（同名）
systemctl restart vsftpd
ss -tlnp | grep :21                  # 确认监听
curl -u alice ftp://192.168.1.100/   # 命令行测试
lftp -u alice 192.168.1.100          # 交互式客户端（Ubuntu 常用 lftp）

# ---------- SFTP（无需额外服务，sshd 自带） ----------
sftp alice@192.168.1.100             # 交互：get 下载 / put 上传 / ls / cd
sftp -oPort=2222 alice@host          # 非标准端口
scp app.jar alice@host:/opt/app/     # 同体系批量拷贝（scp/sftp/rsync 共用 SSH）

# ---------- WebDAV（nginx 模块示例） ----------
apt install nginx davfs2             # 客户端挂载工具 davfs2
mount -t davfs http://webdav.example.com/ /mnt/dav
```

## 配置文件解析

### NFS：/etc/exports（逐行解析）

```text
# 格式：导出目录  客户端(选项1,选项2,...)
/data    192.168.1.0/24(rw,sync,no_subtree_check,no_root_squash)
/backup  *.example.com(ro,sync)
/home    *(rw,sync)              # * 表示所有主机（仅测试环境用，生产禁止）

常用选项：
rw / ro            读写 / 只读
sync / async       sync 数据确认落盘后才返回（安全）；async 先回成功再落盘（快但有丢数据风险）
root_squash        客户端 root 映射为 nobody（默认，安全）
no_root_squash     客户端 root 保留 root 权限（共享文件系统管理场景才用，慎用）
all_squash         所有客户端用户都映射为 nobody（公开只读共享）
anonuid=65534 / anongid=65534   指定映射后的匿名 UID/GID（配合 all_squash 用）
no_subtree_check   关闭子树检查（避免「文件被改名/移动时挂载访问报错」，现代默认建议加）
fsid=0             NFSv4 伪根导出标记（多导出时给根目录用）
sec=krb5p          Kerberos 加密挂载（高安全场景）
```

NFSv4 权限映射提示：v4 默认按**用户名**（idmapd，/etc/idmapd.conf）而不是数字 UID 映射；跨机器 UID 不一致时配 idmapd 或统一账号体系（LDAP/NIS）。

### Samba：/etc/samba/smb.conf（逐段解析）

```ini
[global]
    workgroup = WORKGROUP          # 工作组名（Windows 域场景填域 NetBIOS 名）
    server string = %h server      # 服务器描述
    security = user                # 认证模式：user 本机密码库 / ads 域认证 / share(已废弃)
    map to guest = Bad User        # 错误用户映射为 guest（配合 guest ok 开放匿名）
    server min protocol = SMB2     # 最低协议 SMB2，禁用 SMB1（安全基线，必配）
    log file = /var/log/samba/log.%m   # 按客户端分开日志（排错友好）
    max log size = 1000

[share]                            # 共享名：Windows 里看到的就是它
    comment = 团队共享目录
    path = /data/share             # 映射到 Linux 目录
    browseable = yes               # 是否出现在「网络」浏览列表
    read only = no                 # 可写（等价 writable = yes）
    valid users = alice, bob       # 白名单：只允许这些用户访问
    write list = alice             # 可写用户（只读用户留在 valid users 即可）
    create mask = 0664             # 新建文件权限
    directory mask = 0775          # 新建目录权限
    force user = share             # 强制以该系统用户身份读写（文件属主统一）
    guest ok = no                  # 是否允许匿名
```

要点：**Samba 用户 ≠ 系统用户密码**——账号必须是系统存在的用户（`useradd alice`），再用 `smbpasswd -a alice` 单独设 Samba 密码（存 tdbsam 库）。权限检查 = 共享段选项（valid users/write list）AND Linux 目录权限 AND force user 映射。

### vsftpd：/etc/vsftpd.conf（逐项解析）

```ini
# ---- 基本 ----
listen=YES                          # 独立监听（systemd 部署时可选 NO 走 socket 激活）
anonymous_enable=NO                 # 禁匿名（安全）
local_enable=YES                    # 允许本地系统用户登录
write_enable=YES                    # 允许写（上传/删除/改名）
local_umask=022                     # 上传文件权限掩码

# ---- 用户限制 ----
chroot_local_user=YES               # 把用户禁锢在自家 home（安全基线，否则可逛全盘）
allow_writeable_chroot=YES          # home 目录可写时也允许 chroot（Ubuntu 默认 home 755 会报错）
userlist_enable=YES                 # 启用用户名单
userlist_file=/etc/vsftpd.user_list # 名单文件
userlist_deny=NO                    # NO=名单内才允许登录（白名单模式，推荐）

# ---- 被动模式（NAT/防火墙场景必须配） ----
pasv_enable=YES
pasv_min_port=40000                 # 数据端口范围下限
pasv_max_port=40100                 # 上限（防火墙/安全组需放行此段）
pasv_address=203.0.113.10           # NAT 外网环境：通告给客户端的公网 IP

# ---- TLS 加密（FTPS，可选但推荐） ----
ssl_enable=YES
rsa_cert_file=/etc/ssl/certs/vsftpd.pem   # 证书（openssl req -x509 自签即可）
rsa_private_key_file=/etc/ssl/private/vsftpd.key
force_local_data_ssl=YES            # 数据通道强制 TLS
force_local_logins_ssl=YES          # 登录凭据强制 TLS
```

### WebDAV（nginx 配置片段示例）

```nginx
location /dav/ {
    dav_methods PUT DELETE MKCOL COPY MOVE;   # 启用 WebDAV 方法
    dav_access user:rw group:rw all:r;        # 权限
    client_max_body_size 1G;                  # 大文件上传限制
    auth_basic "dav";                         # 建议叠加 HTTP 认证
    auth_basic_user_file /etc/nginx/dav.passwd;
}
```

```text
配置速记：
exports：目录 + 网段白名单 + (rw/sync/root_squash)，exportfs -ra 生效
smb.conf：[global] 禁 SMB1 + [share] path/valid users/write list/create mask
vsftpd：禁匿名 + chroot + pasv 端口段 + （可选 TLS）
```

## 应用场景实战

### 场景一：多台 Linux 共享数据目录（NFS）

```shell
# —— 服务端（192.168.1.100）——
apt install nfs-kernel-server
mkdir -p /data && chown nobody:nogroup /data
cat >> /etc/exports <<'EOF'
/data 192.168.1.0/24(rw,sync,no_subtree_check)
EOF
exportfs -ra && exportfs -v        # 生效并核对
# —— 客户端（每台要访问的机器）——
apt install nfs-common
mkdir -p /mnt/data
mount -t nfs 192.168.1.100:/data /mnt/data
# 验证
df -h /mnt/data                    # 看到服务端 /data 的空间
touch /mnt/data/test.txt && ls -l /mnt/data/test.txt   # 读写正常（属主 nobody）
# 持久化
echo '192.168.1.100:/data /mnt/data nfs rw,sync,soft,noatime,_netdev 0 0' >> /etc/fstab
# 说明：客户端 root 默认被 root_squash 映射为 nobody，属主显示 nobody 是正常现象；
# 多机共享同一份数据，配合 18.1/18.2 做快照与备份。
```

### 场景二：Windows 访问 Linux 共享（Samba）

```shell
# 1. 安装 + 建系统用户 + 建 samba 用户
apt install samba
useradd -m alice && smbpasswd -a alice
# 2. 配置共享（见 smb.conf 解析：[share] path=/data/share ...），
#    并确保共享目录属主/权限对 alice 开放：chown -R alice:alice /data/share
testparm && systemctl restart smbd
# 3. Windows 侧访问：资源管理器地址栏输入 \\192.168.1.100\share
#    输入 alice + Samba 密码（注意：是 smbpasswd 设的密码，不是系统登录密码）
# 4. Linux 客户端同样可挂载
apt install cifs-utils
mount -t cifs //192.168.1.100/share /mnt/smb -o username=alice,uid=1000,vers=3.0
# 5. 查看在线连接与锁
smbstatus -b
# Red Hat 系差异：dnf install samba；systemctl start smb nmb；
```

## 性能与调优

```text
1. NFS 读写块大小（rsize/wsize）
   内核默认按协议协商（v4.2 一般 1MB 级），老内核/显式挂载可调：
   -o rsize=1048576,wsize=1048576 适合大文件吞吐；小文件密集场景保持默认。
2. sync vs async 取舍
   sync 每写必落盘（数据安全，吞吐下降）；async 写缓存后即返回（性能高，
   但断电/崩溃可能丢已确认数据）。数据库文件等关键数据用 sync；缓存/临时目录可 async。
3. NFSv4 优先
   相比 v3：单端口（防火墙简单）、有状态锁、无 rpcbind 协商开销、支持 Kerberos；
   性能与安全性全面占优，新环境一律 v4。
4. SMB 协议版本
   客户端/服务端都支持时用 SMB3.1.1（Windows 10+/Samba 4.15+），吞吐与安全最佳；
   禁用 SMB1（既慢又是漏洞温床）。Samba 端 server min protocol = SMB2。
5. Samba 性能要点
   大文件共享避免「SMB 加密 + 慢盘」组合（CPU 成瓶颈）；多核机器 smbd 多线程
   默认并发良好；vfs_fruit/streams 模块按需启用（macOS 兼容会增加开销）。
6. FTP 被动模式端口规划
   pasv 端口段按并发连接数规划（每连接占一个端口），40000~40100 支持 100 并发；
   端口段过大增加防火墙暴露面，过小限制并发，按峰值×1.5 配置。
7. rsync/SFTP 传输
   rsync 加 -z 压缩（文本/日志收益大，已压缩文件反而拖慢）、-P 断点续传；
   SFTP 单连接大文件受 TCP 窗口限制，超大文件用 rsync 或并行分片更优。
8. 网络与存储底座
   所有共享服务的吞吐上限 = 存储 IO + 网络带宽。NFS 高并发场景优先万兆 +
   SSD；Samba 大文件关注协议协商结果（testparm -v | grep protocol）。
```

## 安全与权限

```text
1. 一律弃用明文 FTP
   FTP 密码与数据明文传输，可被抓包窃听。改用 SFTP（SSH 加密）或 FTPS（TLS）。
   这是文件共享第一安全原则。
2. NFS 权限三层检查
   ① exports 网段白名单（别写 *，只给业务网段）；② root_squash 保持默认
   （no_root_squash 仅限可信管理场景）；③ 目录本身 Unix 权限（属主/mode）。
   高安全场景加 sec=krb5p（Kerberos 加密传输，RHEL 系常用）。
3. Samba 认证与暴露面
   独立 smbpasswd 密码库（不暴露系统密码）；security = user 逐用户授权；
   valid users 白名单 + write list 细分读写；禁用 SMB1（server min protocol = SMB2）；
   不要轻易 guest ok = yes（匿名共享仅限内网只读场景）。
4. SELinux / AppArmor
   Red Hat 系：Samba 共享非默认路径需 setsebool -P samba_export_all_rw on，
   否则客户端挂载成功但读写 Permission denied（SELinux 拒绝）；
   Ubuntu：AppArmor 对 smbd 有路径限制（/etc/apparmor.d/usr.sbin.smbd），
   共享目录若不在允许列表需追加规则并 aa-reload，否则同样被拒。
5. 防火墙放行最小化
   NFS：2049/tcp（v4）+ 111/tcp,udp（v3 兼容/挂载协商）；Samba：445/tcp（+137-139 按需）；
   FTP：21/tcp + pasv 端口段；SFTP：22/tcp（复用 SSH，天然最小）。
   Red Hat 系用 firewalld 预定义服务：nfs/samba/ftp/ssh。
6. 传输加密
   公网/半信任网络：SFTP/rsync-over-SSH/FTPS 加密；NFS 走 VPN 或 sec=krb5p；
   SMB3 自带加密（smb.conf: server smb encrypt = required）。
7. 日志审计
   NFS：/var/log/messages（mountd/nfsd）；Samba：log.smbd/log.access（按 %m 分文件）；
   vsftpd：/var/log/vsftpd.log（xferlog_enable 记录传输审计）；SFTP 复用 auth.log。
   共享服务日志纳入集中采集（见 13.2），异常访问可追溯。
```

## 故障排查

### 案例一：NFS 挂载卡死/服务器挂了客户端 hang

```shell
# 现象：NFS 服务器宕机后，客户端 df/ls/cat 全部卡住无响应
# 原因：默认 hard 挂载 = 无限重试，内核 NFS 客户端阻塞在 IO 等待
# 1. 确认阻塞（D 状态进程）
ps aux | grep -E 'D' | grep -v grep      # 大量 D 状态 = 卡在 IO
# 2. 强制卸载（先救业务）
umount -l /mnt/data                      # -l lazy：立即断开挂载关系，后台清理
# 3. 服务器恢复后重挂
mount -t nfs -o rw,sync,soft,timeo=50,retrans=2 192.168.1.100:/data /mnt/data
#    soft：超时返回错误而不是无限等；timeo=50（0.5s 超时）× retrans=2 重试
# 4. 从源头排查服务器为什么挂
showmount -e 192.168.1.100               # 服务器导出了吗
rpcinfo -p 192.168.1.100                 # rpcbind 活着吗（v3 场景）
ss -tlnp | grep 2049                     # nfsd 在听吗
journalctl -u nfs-server -n 50           # 服务端日志
```

### 案例二：Samba 认证失败/能认证但没权限

```shell
# 现象 A：Windows 提示「用户名或密码错误」
# 1. 确认系统用户存在 + samba 密码已设
id alice && pdbedit -L | grep alice       # pdbedit -L 列出 samba 账号
smbpasswd -a alice                        # 没设就设（密码≠系统密码）
# 2. 看 smbd 日志（客户端独立日志文件）
tail -50 /var/log/samba/log.smbd
#    常见：NT_STATUS_LOGON_FAILURE = 密码错 / 账号未建
# 现象 B：能登录但看不到共享/目录空
# 3. 检查共享段与目录权限
testparm -v | grep -A8 '\[share\]'        # valid users / browseable 是否正确
ls -ld /data/share                        # 目录属主与 mode（alice 需要对应权限）
# 4. Red Hat 系专属：SELinux 拦截（目录能看、读写全被拒）
getenforce                                # Enforcing 时检查审计
ausearch -m avc -ts recent | grep smbd    # SELinux 拒绝记录
setsebool -P samba_export_all_rw on       # 开放 Samba 读写共享目录
```

### 案例三：FTP 被动模式连接失败

```shell
# 现象：控制通道登录成功，ls/get 卡住或报 425/500 错误
# 原因：数据通道连不上——被动端口段未放行 / NAT 环境 pasv_address 未配
# 1. 客户端确认连的是哪个端口（verbose 模式看 PASV 响应）
lftp -d -u alice 192.168.1.100           # -d 调试：看到 Entering Passive Mode (192,168,1,100,156,64)
#    156*256+64 = 40000 → 数据端口 40000，检查该端口连通性
# 2. 本机测端口段
nc -zv 192.168.1.100 40000-40100          # 全段通不通
ss -tlnp | grep -E ':(40000|40001)'       # 服务端是否在监听数据端口
# 3. 防火墙/安全组放行 pasv 段（服务端）
iptables -I INPUT -p tcp --dport 40000:40100 -j ACCEPT
firewall-cmd --add-port=40000-40100/tcp --permanent && firewall-cmd --reload
# 4. 公网 NAT 场景：服务端通告内网 IP，客户端连不上 → 配 pasv_address=公网IP
# 5. 实在搞不定双通道：直接换 SFTP（单端口 22，没有数据通道问题）
```

### 案例四：挂载成功但读写报 Permission denied

```shell
# NFS：三层权限任一不过都报这个
showmount -e 192.168.1.100                # ① 导出白名单是否含本机网段
grep -E '/data' /etc/exports              # ② 选项是否 rw（ro 只读）
ls -ld /data && id                         # ③ 目录权限 vs 当前用户映射
#   root 访问被拒 → root_squash 生效（映射成 nobody），检查目录对 nobody 开放与否
#   UID 不一致（v3）→ 两端统一 UID 或配 idmapd（v4）
# Samba：共享段 + 目录权限 + force user 三层
testparm -s | grep -A6 '\[share\]'
ls -ld /data/share
# Red Hat 系先排除 SELinux（ausearch -m avc -ts recent）
```

## 常见问题

```text
Q1: FTP 和 SFTP 到底什么关系？用哪个？
A: 没有继承关系。FTP 是独立协议（21 控制 + 数据双通道、明文）；
   SFTP 是 SSH 的文件传输子系统（22 单端口、全加密、复用 SSH 认证）。
   一律优先 SFTP：无需额外服务端、没有被动端口/NAT 问题、天然加密。

Q2: NFS 和 Samba 怎么选？
A: 纯 Linux 环境用 NFS（内核级、性能好、配置简单）；
   需要 Windows/macOS 访问用 Samba（SMB 是跨平台事实标准）。
   混合环境常见组合：Linux 之间 NFS，对外 Windows 用 Samba 指向同一目录。

Q3: NFS 挂载卡死怎么办？
A: 默认 hard 挂载无限重试导致 IO 阻塞。用 soft,timeo=50,retrans=2 挂载
   让超时返回错误；已卡死用 umount -l 强制卸载。生产建议 hard+intr 或
   soft 按业务容忍度选，并监控服务端健康。

Q4: Samba 用户密码和系统密码什么关系？
A: 账号必须是系统用户，但密码独立（smbpasswd 存于 tdbsam）。
   改系统密码不会同步 Samba 密码，两者各自维护；域环境（security=ads）
   则统一走域控。

Q5: root_squash 是干什么的？为什么默认开启？
A: 客户端 root 访问 NFS 时被映射为匿名用户 nobody，防止客户端管理员
   在共享文件系统上以 root 权限读写/删除服务端文件。这是 NFS 的安全基石，
   只有共享整个文件系统做管理场景才考虑 no_root_squash。

Q6: FTP 主动/被动模式区别？
A: 主动：服务器主动从 20 端口连客户端数据端口（被 NAT/防火墙挡，基本废弃）；
   被动：客户端连服务器开放的随机端口（pasv 段），NAT 友好、主流方式。
   部署要点：放行 21 + pasv 端口段，公网 NAT 补 pasv_address。

Q7: WebDAV 什么时候用？
A: 需要「HTTP 上做文件共享」时：跨平台（Win/mac/Linux/移动端）统一走
   HTTPS 访问、与 Web 服务同域、只读下载为主。比 SMB 穿透性好，比 SFTP
   对普通用户友好（浏览器直接下载），但写场景性能一般。

Q8: SMB1 为什么必须禁用？
A: 协议老旧且存在严重漏洞（EternalBlue/WannaCry 蠕虫即经 SMB1 传播），
   Windows 10/Server 2019 起默认禁用。Samba 侧 server min protocol = SMB2
   即可拒绝 SMB1 客户端。
```

## 面试题

```text
1. NFS 与 Samba 的区别？
   答：NFS 是 Linux 生态的文件共享协议（RPC 传输，NFSv4 单端口 2049），
       客户端 mount 后内核级访问，性能好、配置简单，但 Windows 支持弱；
       Samba 实现 SMB/CIFS 协议，是跨平台（尤其 Windows）的事实标准，
       提供用户认证、共享名、ACL 等会话级能力。选型：纯 Linux 用 NFS，
       跨平台用 Samba。

2. NFS 的 root_squash 机制？
   答：默认开启——客户端 root 访问服务端导出目录时，UID 被映射为匿名
       用户（nobody/nfsnobody），防止客户端管理员以 root 身份操作服务端
       文件。可配 no_root_squash（保留 root）或 all_squash（全部映射为
       nobody），anonuid/anongid 可指定映射目标。

3. FTP 为什么被 SFTP 取代？两者技术差异？
   答：FTP 双通道（21 控制 + 数据连接）、密码与数据明文、主动模式被
       NAT/防火墙阻断、被动模式要开放端口段，运维与安全成本高；
       SFTP 是 SSH 文件传输子系统，单端口 22、全加密、复用 SSH 认证
       （密码/密钥/双因素）、无需额外服务端。安全性、穿透性、部署成本
       全面占优。

4. NFS 挂载卡死的原理与对策？
   答：默认 hard 挂载在服务器不可达时内核无限重试，进程阻塞在 IO 等待
       （D 状态），df/ls 卡住。对策：挂载选项 soft（超时返回错误）或
       hard,intr（可中断）；已卡死 umount -l 强制卸载；生产环境对
       关键共享加监控告警，服务端故障快速感知。

5. Samba 共享的权限体系有几层？排错顺序？
   答：三层：① smb.conf 共享段（valid users/write list/browseable/read only）；
       ② Linux 文件系统权限（目录属主与 mode）；③ Samba 账号认证
       （pdbedit/smbpasswd）。排错顺序：先确认账号可登录（pdbedit -L）→
       testparm 核对共享段 → ls -ld 核对目录权限；Red Hat 系还要查
       SELinux（ausearch -m avc）与 firewalld。

6. FTP 被动模式部署要点？
   答：服务端配 pasv_enable=YES + pasv_min_port/pasv_max_port 固定数据
       端口段；防火墙/安全组放行 21/tcp 与数据端口段；NAT 外网环境在
       服务端配 pasv_address 通告公网地址。客户端（lftp/curl）默认被动
       模式，登录成功但 ls/get 卡住基本就是数据端口不通。

7. SMB1 协议有什么问题？如何禁用？
   答：SMB1 存在远程代码执行漏洞（EternalBlue，WannaCry 蠕虫利用），
       且功能老旧、性能差，Windows 10 起默认禁用。Samba 侧在 [global]
       配 server min protocol = SMB2（或 SMB3），客户端同样禁 SMB1。
       安全基线要求全网无 SMB1 流量。

8. 多个用户共享目录，如何保证权限隔离？
   答：目录规划 + Samba 三层权限组合：共享段 valid users 白名单 + write
       list 细分读写；Linux 侧按组授权（group 目录 + setgid 保持组属主 +
       0664/0775 掩码）；敏感数据分目录共享而非一个大共享；配合强制
       force user 统一属主时注意不要绕过隔离意图。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 传文件用 SFTP/rsync-over-SSH（加密、单端口），明文 FTP 一律弃用
2. 纯 Linux 环境共享用 NFSv4（单端口 2049 + root_squash + 网段白名单）
3. 跨 Windows 共享用 Samba，`server min protocol = SMB2` 禁 SMB1
4. NFS 挂载 fstab 持久化必带 `_netdev`（网络就绪后再挂，开机不卡死）
5. exports 白名单最小化：只写业务网段，不写 `*`；no_root_squash 不用
6. Samba 用户独立密码（smbpasswd），权限用 valid users + write list 细分
7. vsftpd 配 chroot_local_user + userlist 白名单 + pasv 端口段固定
8. 共享服务日志（smbd/nfs/vsftpd/sshd）接入集中日志，异常访问可审计
9. Red Hat 系部署 Samba/NFS 先处理 SELinux 布尔值与 firewalld 放行

### 踩坑记录

```text
坑 1：NFS 服务器挂了，客户端 df/ls 全卡住
结论：NFS 服务器不可达，所有访问挂载点的命令/进程卡死（D 状态）。
原因：默认 hard 挂载无限重试，内核阻塞在 IO 等待，业务进程排队挂起。
解法：umount -l 强制卸载先救业务；重新挂载用 soft,timeo=50,retrans=2
      （或 hard,intr）；关键共享加服务端健康监控。

坑 2：NFS 客户端 root 访问权限不足
结论：客户端 root 访问 NFS 文件报 Permission denied，业务脚本跑不起来。
原因：root_squash 把客户端 root 降为 nobody，服务端目录没给 nobody 权限。
解法：目录对 nobody 开放（chown nobody:nogroup 或加 other 读权限）；
      确需 root 语义时服务端配 no_root_squash（仅可信环境，慎用）。

坑 3：FTP 明文密码被窃听
结论：FTP 登录密码泄露，文件被下载。
原因：FTP 控制通道明文传输，抓包即可看到 USER/PASS。
解法：改用 SFTP（SSH 加密）；如必须 FTP 则上 FTPS（ssl_enable=YES +
      force_local_logins_ssl=YES），并禁匿名。

坑 4：Samba 老协议 SMB1 连不上/安全扫描报漏洞
结论：Windows 10+ 连不上老 Samba，或等保扫描报 SMB1 高危漏洞。
原因：SMB1 已被 Windows 禁用（EternalBlue/WannaCry 系列漏洞），
      老 smb.conf 未限制协议版本。
解法：server min protocol = SMB2（或 SMB3）+ 重启 smbd + testparm 验证。

坑 5：NFS 重启后客户端挂载丢失
结论：客户端重启后挂载点空了，应用启动失败。
原因：mount 是临时行为，没写 /etc/fstab。
解法：写 fstab 持久化并带 _netdev（避免网络未就绪时挂载阻塞开机）；
      或改用 autofs 按需自动挂载。

坑 6：Samba 挂载成功但读写全被拒（SELinux）
结论：客户端能挂载、能列目录，读写却 Permission denied，目录权限没问题。
原因：RHEL 系 SELinux 默认策略禁止 smbd 导出非默认目录（/data 等）。
解法：getenforce 确认 → ausearch -m avc -ts recent 查拒绝记录 →
      setsebool -P samba_export_all_rw on；Ubuntu 同类问题查 AppArmor
      （/etc/apparmor.d/usr.sbin.smbd 的路径白名单）。

坑 7：FTP 被动模式连接失败
结论：登录成功但 ls/get 卡住，报 425/500 Failed to open data connection。
原因：数据通道端口（pasv 段）没放行，或 NAT 环境通告了内网地址。
解法：固定 pasv_min_port/pasv_max_port 并放行该段；外网场景配
      pasv_address=公网IP；实在搞不定直接换 SFTP。

坑 8：NFSv3 挂载报 rpc 1000003 / 端口协商失败
结论：mount -t nfs 报 RPC: Unable to receive / mount.nfs: rpc 1000003。
原因：v3 挂载依赖 rpcbind（111）与 mountd 协商端口，rpcbind 没起或被防火墙挡。
解法：起 rpcbind 并放行 111/tcp+udp；现代环境直接改用 NFSv4
      （mount -t nfs4 或 -o vers=4.2），单端口 2049 免协商。

坑 9：跨 UID 机器共享，文件属主错乱
结论：A 机的用户 UID 1000 在 B 机是另一个人，NFS 文件属主显示错乱。
原因：NFSv3 按数字 UID 传递；v4 默认走 idmapd 用户名映射，配置不当同样错。
解法：统一账号体系（LDAP/集中认证），或两端 idmapd 域配置一致；
      临时方案：服务端固定 anonuid/anongid 并 all_squash 映射到共享账号。
```
