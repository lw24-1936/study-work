## 概述

DNS（Domain Name System）把「域名」解析成「IP 地址」，是互联网的「电话簿」——没有 DNS，浏览器只能靠 IP 访问网站。对运维而言，自建 DNS 的典型场景：**内网域名解析**（内网主机名、服务发现，告别记 IP）、**DNS 缓存加速**（减少外网查询、降低延迟）、**权威域名服务器**（自管域名记录，如邮件 SPF/DKIM 验证的基础）。

主流实现四类：**BIND**（老牌权威 + 递归，功能最全，互联网上绝大多数权威服务器是它）、**dnsmasq**（轻量，DNS 缓存 + 内网域名 + DHCP 三合一，适合小内网）、**Unbound**（专注递归解析，性能与安全见长，openSUSE 默认）、**CoreDNS**（云原生，K8s 默认集群 DNS，插件化）。选型一句话：**内网轻量选 dnsmasq，自管域名/正式权威选 BIND，追求递归性能选 Unbound，K8s 里用 CoreDNS**。

本机是 Ubuntu 24.04：DNS 客户端走 **systemd-resolved**（stub 监听 127.0.0.53，上游是路由器 192.168.1.1），装了 dig/nslookup/host 全套查询工具；dnsmasq 二进制存在但服务未启用；BIND 未安装（apt 源可用）。下文实测全部来自本机真实执行。

## 核心概念

1. **区域（zone）**：一个域名（如 `example.com`）的「命名空间」，包含该域名下全部记录，是 DNS 管理的基本单位。权威服务器按 zone 存储与响应。
2. **记录类型**：**A**（域名→IPv4）、**AAAA**（域名→IPv6）、**CNAME**（别名→另一域名）、**MX**（邮件服务器，带优先级）、**NS**（本域的权威域名服务器）、**TXT**（任意文本，SPF/DKIM/域名验证都用它）、**PTR**（反向：IP→域名）、**SOA**（Start of Authority，zone 的元数据：主服务器、管理员邮箱、序列号、各 TTL 参数）。
3. **权威（authoritative）vs 递归（recursive）**：权威服务器存「自己域名」的记录，直接回答关于自己域名的查询；递归服务器帮客户端查「任意域名」，逐级问完并缓存结果。一台 BIND 可以同时兼任两者，但生产上应分离。
4. **正向 vs 反向解析**：正向（域名→IP，A/AAAA 记录）；反向（IP→域名，PTR 记录，配合 `in-addr.arpa` 特殊 zone；IPv6 用 `ip6.arpa`）。反向解析是邮件服务器防垃圾邮件的验证手段之一。
5. **TTL（Time To Live）**：记录在递归/客户端缓存的秒数。TTL 越长查询越快但变更生效越慢；越短变更快但查询多。紧急变更前先把 TTL 调低（见踩坑记录）。
6. **DNS 服务器类型按职能划分**：权威服务器（存记录）、递归服务器（替客户端查）、缓存服务器（递归 + 缓存）、转发服务器（自己不递归，把查询转给上游）。dnsmasq 默认是「缓存 + 转发」型，BIND 可配成任意型。
7. **根服务器与层级**：全球 13 组根服务器（a-m.root-servers.net，任播部署数百台物理机）→ 顶级域（com/net/org/cn…）→ 二级域（example.com）→ 子域。解析从根开始逐级向下。
8. **DNSSEC**：给 DNS 记录加数字签名（DNSKEY/DS/RRSIG），客户端/递归可验证记录「确实来自权威且未被篡改」。防缓存投毒的根本手段，但部署复杂度高、普及率仍在爬坡（本机实测 DNSSEC=no/unsupported，见「安全与权限」）。

```text
核心概念速记：
zone（域名记录集合）+ 记录类型（A/AAAA/CNAME/MX/NS/TXT/PTR/SOA）
权威（管自己的域名）vs 递归（帮查任意域名 + 缓存）
TTL（缓存时长，变更生效速度的关键）
DNSSEC（签名验证，防投毒）
```

## 工作原理

### 一次完整解析：递归 + 迭代

客户端查询 `www.example.com` 的完整路径：

1. **客户端本地缓存**：浏览器缓存 → 操作系统缓存 → `/etc/hosts`（本机实测 hosts 里就手工写了 github.com，优先级最高）。
2. **递归查询**：客户端把查询丢给「本地递归服务器」（本机是 systemd-resolved stub → 上游 192.168.1.1；一般家庭是路由器，公网是 8.8.8.8/114.114.114.114）。递归服务器**全权负责**查到底并返回最终答案。
3. **迭代过程**（递归服务器视角）：向根服务器问「www.example.com 的 A 记录？」→ 根回答「去问 com 的权威服务器（不直接给答案，给下一步地址）」→ 问 com 服务器 → 回答「去问 example.com 的权威」→ 问 example.com 权威 → **返回最终 IP**。
4. **缓存**：递归服务器按 TTL 缓存结果，下次同域查询直接命中（本机实测 TTL 131 秒，命中时 query time 仅 7ms）。

「递归」= 客户端委托服务器全查（自己省事）；「迭代」= 服务器一步步问上级（每次都只拿到下一步的地址）。**权威服务器不做递归**（回答自己的 zone），**递归服务器不做权威**（避免缓存与权威数据混淆）。

```text
# 实测（本机）——dig +trace 展示从根开始的真实迭代过程
$ dig example.com +trace | head -16

; <<>> DiG 9.18.39-0ubuntu0.24.04.5-Ubuntu <<>> example.com +trace
;; global options: +cmd
.           47570   IN   NS   b.root-servers.net.     # 第 1 步：根服务器列表
.           47570   IN   NS   h.root-servers.net.
.           47570   IN   NS   j.root-servers.net.
.           47570   IN   NS   a.root-servers.net.
...（13 组根服务器）
;; Received 239 bytes from 127.0.0.53#53(127.0.0.53) in 5 ms   # 从 stub 拿到根列表

com.        172800  IN   NS   a.gtld-servers.net.     # 第 2 步：问根 → 得到 com 的权威
com.        172800  IN   NS   b.gtld-servers.net.
com.        172800  IN   NS   c.gtld-servers.net.
...（.com 顶级域服务器）
```

```text
# 实测（本机）——常规查询：stub 解析器的完整应答
$ dig example.com
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 6238
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1
;; ANSWER SECTION:
example.com.    131   IN   A   104.20.23.154        # TTL 131 秒（还剩的缓存时间）
example.com.    131   IN   A   172.66.147.243
;; Query time: 7 msec
;; SERVER: 127.0.0.53#53(127.0.0.53) (UDP)
# flags 含义：qr=响应  rd=客户端要求递归  ra=服务器允许递归（说明走的是递归路径）
# SERVER 行显示真实应答来源：本机 systemd-resolved stub
```

### 传输协议：UDP 53 为主，TCP 53 为辅

- **UDP 53**：绝大多数查询（快，一问一答，无握手）。
- **TCP 53**：zone 传输（主从同步，数据量大必须可靠）、大响应（EDNS 超 512 字节、DNSSEC 签名响应）、部分运营商/防火墙对 UDP 限制时的回退。
- 排查时 `nc -zvu 8.8.8.8 53` 测 UDP、`nc -zv 8.8.8.8 53` 测 TCP，两者都要通（曾踩过「UDP 通 TCP 被防火墙拦 → 主从 zone 传输失败」的坑）。

### 主从同步（zone transfer）

主 DNS 的 zone 变化后，从 DNS 通过 **AXFR（全量）/ IXFR（增量）** 从主服务器拉取区域文件：从服务器按 SOA 记录的 **serial 序列号**判断主服务器是否有新版本（serial 更大则拉取）。所以：**改记录必须递增 serial**，否则从服务器永远不更新——这是主从架构最经典的坑。

### DNS 劫持与缓存投毒原理（理解才能防）

- **DNS 劫持**：中间环节篡改解析结果——运营商/路由器 DNS 劫持（把域名指向广告页）、恶意 DNS 服务器返回假 IP。防护：用可信 DNS（8.8.8.8/1.1.1.1）、DoT/DoH 加密查询（本机 systemd-resolved 支持 DNSOverTLS）、DNSSEC。
- **缓存投毒（DNS spoofing）**：攻击者伪造 DNS 响应，抢在真响应前发给递归服务器，让递归缓存「假记录」。传统防护是随机化查询 ID 与源端口（BIND 默认已做）；根治是 **DNSSEC**——签名验证使伪造响应无法通过校验。
- 内网场景最实际的风险：**公共 DNS 不可控 + 内网域名泄漏**。内网域名（如 `gitlab.internal`）绝不应出现在公共 DNS 可查询的 zone 里，应自建内网 DNS 权威（见「应用场景实战」）。

## 常用命令与配置

```shell
# ---------- 安装（Ubuntu） ----------
apt install bind9              # BIND9（权威/递归），服务名 bind9（named 是兼容别名）
apt install dnsmasq            # dnsmasq（轻量 DNS 缓存 + DHCP），服务名 dnsmasq
apt install unbound            # Unbound（纯递归）

# ---------- dig 查询（首选，信息最全） ----------
dig example.com                      # 查 A 记录（完整应答，看 SERVER/flags/TTL）
dig example.com +short               # 只要结果（脚本里用）
dig example.com A                    # 显式指定类型（A/AAAA/MX/NS/TXT/CNAME/SOA/ANY）
dig qq.com MX                        # 查邮件服务器
dig -x 8.8.8.8                       # 反向解析（IP → 域名）
dig @8.8.8.8 example.com             # 指定 DNS 服务器查询（绕过本地，测上游）
dig @192.168.1.1 example.com +short  # 内网指定服务器
dig example.com +trace               # 从根开始追踪完整迭代过程（排错利器）
dig example.com +norecurse           # 非递归查询（只问权威层，看服务器是否开放递归）
dig example.com +tcp                 # 强制走 TCP 53（测 TCP 是否被拦）
dig +dnssec example.com              # 看 DNSSEC 签名记录（RRSIG）

# ---------- nslookup / host（快速查询） ----------
nslookup example.com                 # 经典查询（显示 Server 与 Non-authoritative）
nslookup -type=PTR 8.8.8.8           # 反向解析
host example.com                     # 极简输出（A/AAAA/MX 一把梭）
host -t MX qq.com

# ---------- BIND 管理 ----------
named-checkconf                      # 校验 named.conf 语法
named-checkzone example.com /etc/bind/db.example.com   # 校验 zone 文件
systemctl restart bind9              # Ubuntu 服务名；RHEL 是 named
rndc reload                          # 重载配置/区域（无需重启）
rndc reload example.com              # 只重载某个 zone
rndc status                          # 查看运行状态
rndc flush                           # 清空递归缓存
rndc stats                           # 统计信息（/var/cache/bind/named.stats）

# ---------- systemd-resolved（Ubuntu 客户端默认） ----------
resolvectl status                    # 查看各网卡上游 DNS
resolvectl flush-caches              # 清空本地 DNS 缓存
resolvectl dns wlp0s20f3 8.8.8.8     # 临时改某网卡上游
```

## 配置文件解析

### BIND9 配置结构（权威 + 递归 混合示例）

BIND 主配置在 Ubuntu 是 `/etc/bind/named.conf`（include 三个子文件），RHEL 是 `/etc/named.conf`。核心是 `options {}` 全局参数 + `zone {}` 区域声明 + 区域文件（记录数据）。

```text
# /etc/bind/named.conf（Ubuntu）——主配置只做 include 组装
include "/etc/bind/named.conf.options";   # 全局参数
include "/etc/bind/named.conf.local";     # 本地 zone 声明（最常改）
include "/etc/bind/named.conf.default-zones";  # 内置根/回环 zone
```

```nginx
# /etc/bind/named.conf.options（逐行解析）
options {
    directory "/var/cache/bind";          # 工作目录（区域文件相对路径的基准）

    recursion yes;                        # 允许递归（作为递归服务器时开；
                                          # 纯权威服务器应设 no 防放大攻击）
    allow-recursion { 192.168.1.0/24; 127.0.0.1; };  # 递归只对可信网段开放！
    allow-query { any; };                 # 权威查询（自己 zone 的查询）可对所有人

    forwarders { 8.8.8.8; 114.114.114.114; };  # 上游转发（混合模式常见）
    forward only;                         # 只转发不自查（内网缓存型推荐，快且可控）

    dnssec-validation auto;               # DNSSEC 验证（auto=信任根密钥）
    listen-on port 53 { 192.168.1.10; 127.0.0.1; };  # 监听地址（只绑内网卡）
    listen-on-v6 { none; };

    version "not disclosed";              # 隐藏版本号（防针对性攻击探测）
};
```

```text
# /etc/bind/named.conf.local（区域声明）
zone "example.com" {
    type master;                          # 本服务器是该 zone 的主服务器
    file "/etc/bind/db.example.com";      # 区域文件路径
    allow-transfer { 192.168.1.11; };     # 只允许从服务器做 zone 传输（安全关键）
};

zone "1.168.192.in-addr.arpa" {           # 反向 zone（IP 段倒写）
    type master;
    file "/etc/bind/db.192.168.1";
};
```

### 区域文件逐行解析（正向 db.example.com）

```text
; /etc/bind/db.example.com —— 正向区域文件
$TTL 3600                        ; 默认 TTL：没写 TTL 的记录都用 3600 秒
@   IN  SOA  ns1.example.com. admin.example.com. (
        2026081901   ; serial 序列号：改记录必须递增（格式 YYYYMMDDNN）
        7200         ; refresh：从服务器多久查一次主服务器（2 小时）
        3600         ; retry：同步失败后多久重试（1 小时）
        1209600      ; expire：从服务器数据 14 天过期作废
        300 )        ; negative TTL：NXDOMAIN 的缓存时间（5 分钟）
    IN  NS   ns1.example.com.   ; NS：本域的权威服务器（必须与上级注册一致）
    IN  NS   ns2.example.com.
    IN  A    192.168.1.10       ; 裸域 A 记录（@ 代表裸域）
    IN  MX   10 mail.example.com.   ; MX：邮件服务器，优先级 10
ns1 IN  A    192.168.1.10       ; 权威服务器自己的 A 记录（必须配！）
ns2 IN  A    192.168.1.11
www IN  A    192.168.1.20       ; www.example.com → 192.168.1.20
mail IN A    192.168.1.21
gitlab IN  CNAME  www.example.com.   ; CNAME 别名（指向已有域名）
```

区域文件要点：
- **域名必须写全（FQDN）并带结尾点**：`ns1.example.com.` 有尾点 = 绝对域名；没尾点 = 相对域名（会自动拼 zone 名，`ns1` 会被解析成 `ns1.example.com.`——但容易出错，建议一律写全）。
- **`@` 代表 zone 名本身**（裸域）。
- **SOA 是 zone 的灵魂**：serial 不递增 = 从服务器永远不同步（主从第一大坑）；refresh/retry/expire 控制从服务器同步节奏。
- **CNAME 不能与 A 记录同名、不能用于裸域**（CNAME 处不能再有别的记录类型）。
- **NS 记录必须在父域（上级）也有一份**：你自建 `example.com` 权威，需要在域名注册商处把 NS 指向你的服务器，否则公网查不到。

```text
; /etc/bind/db.192.168.1 —— 反向区域文件（IP → 域名）
$TTL 3600
@   IN  SOA  ns1.example.com. admin.example.com. (
        2026081901 7200 3600 1209600 300 )
    IN  NS   ns1.example.com.
10  IN  PTR  ns1.example.com.    ; 192.168.1.10 → ns1.example.com.
20  IN  PTR  www.example.com.    ; 192.168.1.20 → www.example.com.
```

反向 zone 名字规则：`192.168.1.0/24` 网段 → zone 名 `1.168.192.in-addr.arpa`（IP 倒写 + in-addr.arpa）。PTR 记录的「主机号」不写全 IP（10 = 192.168.1.10）。

### dnsmasq 配置解析（/etc/dnsmasq.conf，轻量缓存 + 内网域名 + DHCP）

```ini
# /etc/dnsmasq.conf（关键行解析，默认全部注释）
port=53                    # DNS 端口（与 systemd-resolved 冲突点，见踩坑记录）
listen-address=127.0.0.1,192.168.1.10   # 只监听本机 + 内网卡（别暴露公网）
bind-interfaces            # 与 listen-address 配合，避免 0.0.0.0 全监听
cache-size=1000            # 缓存条目数（默认 150，内网建议 1000+）
domain-needed              # 无点域名不转发上游（防隐私泄漏）
bogus-priv                 # 私有 IP 反向查询不转发上游

# 内网域名静态解析（hosts 风格，无需 zone 文件）
address=/gitlab.internal/192.168.1.20
address=/registry.internal/192.168.1.21
# 通配：整个内网域都解析到内网 DNS 再分发
server=/internal/192.168.1.10
# 通配：查询 internal 域直接给权威（不再递归）
server=/corp.example.com/192.168.1.10

# 上游 DNS（默认读 /etc/resolv.conf；显式指定更稳）
server=8.8.8.8
server=114.114.114.114

# DHCP 服务（dnsmasq 的另一半功能，详见 [[20.3-DHCP 与时间同步]]）
dhcp-range=192.168.1.100,192.168.1.200,12h
dhcp-option=option:router,192.168.1.1
```

```text
dnsmasq 配置速记：
address=/域名/IP    内网域名静态解析（最常用）
server=/域名/权威IP  特定域转发给指定权威（不递归）
server=IP           全局上游（转发）
cache-size=N        缓存条数
listen-address+bind-interfaces   防端口冲突、防暴露
```

### Unbound 简述（纯递归，性能与安全向）

Unbound 只做递归不做权威（职责单一），配置 `/etc/unbound/unbound.conf`：`interface: 192.168.1.10`、`access-control: 192.168.1.0/24 allow`、`cache-max-ttl` 调缓存、默认 DNSSEC 验证开启。适合做「内网缓存 + 验证层」，前面再挂 dnsmasq 做内网域名分发，是常见的内网 DNS 架构组合。

**Red Hat 系差异对照表**：

| 项目 | Ubuntu/Debian | RHEL/CentOS/Fedora |
|---|---|---|
| 包名 | `bind9` | `bind` |
| 服务名 | `bind9`（`named` 是兼容别名） | `named` |
| 主配置 | `/etc/bind/named.conf`（include 拆分 3 文件） | `/etc/named.conf`（单文件为主） |
| 区域文件目录 | `/etc/bind/` | `/var/named/`（zone 文件在 `/var/named/`） |
| 默认 chroot | 无 | RHEL 6/7 默认 chroot 到 `/var/named/chroot/`（RHEL 8+ 默认关闭，但升级老系统仍常见） |
| 递归/转发 | 默认配置偏保守 | 默认配置即开放递归（需手动收紧） |
| SELinux | 无（AppArmor 对 named 有配置） | enforcing 下 named 读写 zone 需正确标签（named_zone_t），`semanage` 调端口 |
| 客户端 | systemd-resolved（stub 127.0.0.53） | RHEL 9 也是 systemd-resolved；老版本 /etc/resolv.conf 直配 |

### 场景二：BIND9 搭建权威域名服务器（自管域名 + 主从）

需求：公司域名 `corp.example.com` 完全自管（解析、邮件验证），并做主从高可用。

```shell
# 1. 安装 bind9
apt install bind9

# 2. 写区域声明 /etc/bind/named.conf.local（见「配置文件解析」）
# 3. 写区域文件 /etc/bind/db.corp.example.com
# 4. 校验（BIND 特有的两道检查，必做）
named-checkconf
named-checkzone corp.example.com /etc/bind/db.corp.example.com
# 5. 启动并验证
systemctl restart bind9
dig @127.0.0.1 corp.example.com A
dig @127.0.0.1 www.corp.example.com +short
# 6. 公网生效：在域名注册商处把 corp.example.com 的 NS 记录指向本机公网 IP
```

主从配置（从服务器 /etc/bind/named.conf.local）：

```text
zone "corp.example.com" {
    type slave;                                   ; 从服务器类型
    file "/var/cache/bind/db.corp.example.com";   ; 从主服务器拉下来的副本
    masters { 192.168.1.10; };                    ; 主服务器 IP
};
```

配合主服务器 `allow-transfer { 192.168.1.11; };` 完成 zone 传输。**关键纪律：主服务器每次改记录，serial 必须递增**，否则从服务器不更新（踩坑记录有专坑）。

### 场景三：内网 DNS 架构设计（dnsmasq 分发 + BIND 权威 + 递归分层）

中小公司标准内网 DNS 三层架构：

```text
客户端（/etc/resolv.conf → 内网 DNS）
   │
   ▼
① 内网接入层：dnsmasq（192.168.1.10）
   - 缓存 + 内网域名静态解析（address=/gitlab.internal/...）
   - 特定域转发：server=/corp.example.com/192.168.1.50（内网权威）
   - 其余域名转发上游
   │
   ▼
② 内网权威层：BIND master + slave（192.168.1.50 / .51）
   - 只管辖 corp.example.com 与反向 zone
   - 关闭递归（防放大攻击），allow-transfer 只给 slave
   │
   ▼
③ 公网递归层：8.8.8.8 / 114.114.114.114（或自建 Unbound 缓存）
```

要点：**内外 DNS 分离**——内网域名（internal/corp 后缀）只在内网解析，不注册到公网；公网域名由云厂商 DNS 或自建公网权威负责。递归只开在接入层，权威层严格关闭递归。

### 场景四：dnsmasq 与 systemd-resolved 共存（Ubuntu 常见需求）

Ubuntu 22.04+ 默认 systemd-resolved 占用 127.0.0.53:53，直接装 dnsmasq 会端口冲突。共存方案：

```text
方案 A（推荐）：dnsmasq 只绑内网卡，不动系统 stub
   /etc/dnsmasq.conf:
     listen-address=192.168.1.10     # 不写 127.0.0.1！
     bind-interfaces
   → 系统程序继续走 127.0.0.53（systemd-resolved），
     内网机器走 192.168.1.10（dnsmasq）

方案 B：停用 systemd-resolved 的 stub，让 dnsmasq 接管本机
   systemctl stop systemd-resolved && systemctl disable systemd-resolved
   rm /etc/resolv.conf 后写静态: nameserver 127.0.0.1
   /etc/dnsmasq.conf: listen-address=127.0.0.1,192.168.1.10
   → 本机与内网都走 dnsmasq（注意：会失去 systemd-resolved 的
     按网卡多上游/DoT 能力，需 dnsmasq 配置兜底）
```

方案 A 是本机实操推荐：互不干扰、各司其职（详见踩坑记录「坑 6」）。

## 性能与调优

```text
1. 缓存开大 —— dnsmasq cache-size 1000+；BIND 递归缓存默认即大，rndc stats 看命中率
2. TTL 策略 —— 稳定记录 TTL 86400（1 天）+ 变更前先降 TTL；动态记录 300~600 秒
3. 上游选择 —— 递归/转发上游选响应快的（多上游并行，dnsmasq 默认挑最快响应者）
4. 转发 vs 自递归 —— 内网缓存层用「转发到上游」比「自己从根递归」快一个量级
   （上游已有缓存；自己递归每次都要走根 → 顶级 → 权威）
5. 就近权威 —— 权威服务器放用户近的机房，Anycast 更佳（CDN/公共 DNS 通用做法）
6. 关闭不用的功能 —— 关 IPv6 查询（listen-on-v6 none）、关不必要的日志（log-queries 生产慎开）
7. 并发 —— BIND 默认多线程；查询量大可加 CPU/内存（递归缓存吃内存，每百万条记录约 1GB）
8. 压测 —— dnsperf / queryperf（BIND 自带）测 QPS，配合 [[16.6-综合调优工具]]
```

```text
# 实测（本机）——缓存效果对比
$ dig example.com | grep 'Query time'
;; Query time: 7 msec          # 首次/未命中：7ms（stub → 路由器 → 公网）
$ dig example.com | grep 'Query time'
;; Query time: 0 msec          # 再次查询：0ms（systemd-resolved 缓存命中）
# TTL 剩余时间也在变化：131 → 130 → ...（TTL 递减 = 缓存倒计时）
```

## 安全与权限

```text
1. 关闭开放递归 —— 权威服务器 recursion no / allow-recursion 限定网段
   （开放递归 = 被用来做 DNS 放大攻击的肉鸡，UDP 放大倍数可达 50+ 倍）
2. DNSSEC —— 权威侧签名（dnssec-signzone）+ 递归侧 dnssec-validation auto；
   防缓存投毒的根本手段；本机实测 DNSSEC=no/unsupported（见下）
3. 限制 zone 传输 —— allow-transfer 只给从服务器 IP（否则任何人可 AXFR 拖走全部记录）
4. TSIG 签名 —— 主从 zone 传输用 TSIG 密钥认证（防中间人伪造传输）
5. 隐藏版本 —— version "not disclosed"（防针对版本漏洞的定向攻击）
6. 端口与监听 —— 只绑内网卡（listen-on），防火墙只放行内网 53（[[12.3-firewalld-ufw]]）
7. 区域文件权限 —— chown bind:bind + 640；RHEL 注意 SELinux 标签（named_zone_t）
8. 系统层面 —— 运行用户低权限（bind 用户）、chroot（RHEL 老版本默认）、
   补丁跟进（BIND 历史上 CVE 多，及时升级）
```

```text
# 实测（本机）——当前 DNSSEC 状态与 stub 的非递归拒绝
$ resolvectl status | grep -i dnssec
         Protocols: -LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
# 本机 DNSSEC 未开启（家庭网络典型状态；开启需上游支持 + resolv.conf 配 trust-ad）

$ dig +norecurse example.com @127.0.0.53 | grep -E 'status|flags'
;; ->>HEADER<<- opcode: QUERY, status: REFUSED, id: 17873
;; flags: qr ra; QUERY: 1, ANSWER: 0
# stub 只做递归，拒绝非递归查询（REFUSED）——这是 stub 解析器的正常防御行为
```

**DNS 放大攻击原理**：攻击者伪造受害者 IP 为源地址，向开放递归服务器发送小体积查询（如 ANY 类型），服务器返回的大响应（可放大数十倍）打向受害者 → 受害者带宽被打满。防护核心就是**不让陌生人用你的递归服务器**（allow-recursion/recursion no）+ 限制 ANY 查询（BIND 9.16+ 默认限制）。

### 案例 1：域名解析失败（分层定位法）

## 常见问题

```text
Q1: 改了 DNS 记录为什么不生效？
A: 因为 TTL 缓存——旧记录在各级缓存（浏览器/系统/递归服务器）里存到 TTL 过期才失效。
   验证「记录到底改没改」用 dig @权威服务器IP 域名 绕过缓存直查权威；
   紧急变更前先把 TTL 调低（如 300 秒），等旧缓存过期再改。

Q2: 递归查询和迭代查询的区别？
A: 递归：客户端委托服务器全权查询，服务器返回最终结果（客户端省事）；
   迭代：服务器一步步问上级（根 → 顶级 → 权威），每次只拿到「下一步去哪问」的地址。
   客户端 → 递归服务器是递归；递归服务器 → 各级权威是迭代。权威服务器只响应迭代。

Q3: A 记录和 CNAME 记录的区别？
A: A 记录：域名直接指向 IP（www.example.com → 1.2.3.4）；
   CNAME：域名是别名，指向另一个域名（www → example.com），解析时再查目标域名的 A。
   CNAME 不能用于裸域（根域），不能与 A/其他记录同名同存（CNAME 处只能有 CNAME）。

Q4: 内网 DNS 用 dnsmasq 还是 BIND？
A: 按规模与职责：小内网（几台到几十台）要缓存 + 内网域名 + DHCP → dnsmasq（一条 address= 搞定）；
   要自管正式域名、主从、动态更新、DNSSEC 签名 → BIND（完整权威能力）；
   要纯递归性能与 DNSSEC 验证 → Unbound。常见组合：dnsmasq 接入层 + BIND 权威层。

Q5: DNS 用什么协议、什么端口？
A: 默认 UDP 53（查询，快）；TCP 53 用于 zone 传输（AXFR/IXFR）、大响应（DNSSEC/EDNS 超长）和
   UDP 受限时的回退。排查要 UDP/TCP 都测（nc -zvu / nc -zv），TCP 被拦会导致主从同步失败。

Q6: 什么是 DNS 劫持？和缓存投毒什么关系？
A: 劫持是「中间环节篡改」——运营商/路由器/恶意服务器把查询结果换成假的（广告页/钓鱼站）；
   缓存投毒是劫持的一种技术手段——伪造响应骗过递归服务器把假记录缓存下来（源端口随机化、
   查询 ID 随机化可缓解，DNSSEC 签名验证可根治）。防护：可信上游 + DoT/DoH + DNSSEC。

Q7: 正向解析和反向解析是什么？
A: 正向：域名 → IP（A/AAAA 记录，日常访问用）；
   反向：IP → 域名（PTR 记录，存于 in-addr.arpa / ip6.arpa 反向 zone）。
   反向解析典型用途：邮件服务器反查发信 IP 是否为声明的域名（防垃圾邮件）。

Q8: 自建权威服务器后，公网为什么还是解析不了我的域名？
A: 权威服务器只负责「回答」，公网要知道「去哪问」——必须在域名注册商处把该域名的 NS 记录
   指向你的权威服务器（并配好对应的 glue A 记录），注册商把 NS 注册到上级（如 .com），
   公网递归才能找到你。只在自己服务器上建 zone 是不够的。
```

## 面试题

```text
1. 从输入 URL 到页面显示，DNS 做了什么？
   答：浏览器查自身缓存 → 查操作系统缓存与 hosts → 交给本地递归服务器（systemd-resolved/路由器/
       8.8.8.8）→ 递归服务器从根开始迭代查询（根 → .com → example.com 权威）→ 权威返回 IP →
       递归缓存并返回 → 浏览器拿到 IP 建立 TCP/TLS 连接。全链路有 TTL 控制的各级缓存。

2. 权威 DNS 和递归 DNS 的区别？
   答：权威服务器存储并回答「自己域名」的记录（来源是区域文件，数据最可信），不做递归；
       递归服务器替客户端查询任意域名，逐级迭代并把结果按 TTL 缓存（缓存可能不是最新）。
       判断响应是否权威：dig 结果的 AUTHORITY 段 / aa（authoritative answer）标志位。

3. 如何让内网机器都能用 gitlab.internal 访问内网服务？
   答：自建内网 DNS（dnsmasq 或 BIND）：dnsmasq 用 address=/gitlab.internal/192.168.1.20
       一条配置；BIND 建 zone 文件写 A 记录。然后客户端 DNS 指向这台内网 DNS
       （dhcp 下发或手动改 resolv.conf）。内网域名用 internal/corp 等非公网后缀，
       避免与公网域名冲突，且不必注册到公网。

4. 什么是 DNS 缓存投毒？如何防护？
   答：攻击者伪造 DNS 响应，抢在真实响应前发给递归服务器，诱导其缓存恶意记录，之后所有
       客户端都被指向假 IP（钓鱼/中间人）。防护：① 递归服务器随机化查询 ID 与源端口
       （BIND 默认）；② 限制允许递归的网段；③ 根治用 DNSSEC——权威侧对记录签名
       （RRSIG），递归侧验签（dnssec-validation auto），伪造响应无法通过验签。

5. DNS 放大攻击的原理与防御？
   答：原理：攻击者以受害者 IP 为源地址向「开放递归」服务器发小体积查询（如 ANY），
       服务器返回的大响应被放大数十倍打向受害者，形成流量攻击。
       防御：权威/递归分离，递归只对可信网段开放（allow-recursion/recursion no），
       限制 ANY 查询，防火墙限速 53 端口，监控异常 UDP 53 流量。

6. BIND 主从同步原理？为什么改了记录从服务器不更新？
   答：从服务器周期性（refresh 间隔）向主服务器查询 SOA，比较 serial：主服务器的 serial
       更大 → 触发 AXFR（全量）/IXFR（增量）zone 传输拉取新数据。
       从服务器不更新的头号原因：改了记录忘了递增 serial（serial 是判断「有没有新版本」
       的唯一依据）；其次：allow-transfer 没配、TCP 53 被拦、主服务器没 reload（rndc reload）。

7. TTL 有什么作用？生产变更如何利用 TTL？
   答：TTL 决定记录在递归/客户端缓存的秒数。作用：缓存命中减少查询量（性能）vs 变更传播
       速度的平衡。变更流程：提前（如 1~2 天）把 TTL 调低（300~600 秒）→ 等旧缓存过期 →
       改记录 → 生效后视需要把 TTL 调回。紧急变更直接改，但旧 IP 缓存最长还要等原 TTL 过期。

8. systemd-resolved 是什么？和 dnsmasq 冲突怎么处理？
   答：systemd-resolved 是 Ubuntu/RHEL9 的系统 DNS 客户端：监听 127.0.0.53 stub，按网卡管理
       上游 DNS，支持 DoT/DoH。它占着 127.0.0.53:53，dnsmasq 默认绑 127.0.0.1:53 会冲突。
       解法：dnsmasq 只绑内网卡（listen-address=内网IP + bind-interfaces），本机继续走 stub；
       或停用 systemd-resolved 让 dnsmasq 全权接管（写静态 resolv.conf）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. **内网服务一律用内网域名**（`gitlab.internal`），别记 IP——IP 会变，域名不变（[[11.4-DNS 与主机名]]）。
2. **递归只对可信网段开放**：`allow-recursion` / dnsmasq `listen-address` 限定，防放大攻击。
3. **权威与递归分离**：正式环境 BIND 权威（关递归）+ 独立递归/缓存层（dnsmasq/Unbound）。
4. **改记录必递增 serial** + `rndc reload` 或重启；主从配置配好 `allow-transfer`。
5. **用 dig 排错**（不是 nslookup）：`@指定服务器` 绕过缓存、`+trace` 看全链路、`+short` 看结果。
6. **TTL 管理**：稳定记录长 TTL、变更前先降 TTL；监控 DNS 查询量决定缓存大小。
7. **内外 DNS 分离**：内网域名不注册公网、公网域名不上内网 DNS，防止内网拓扑泄漏。
8. **DNS 服务纳入监控**：53 端口连通性、解析成功率、QPS、serial 一致性，告警走 [[13.3-系统监控]]。

### 踩坑记录

```text
坑 1：改了记录不生效，以为配置错了
结论：明明改了区域文件，客户端还是解析到旧 IP。
原因：TTL 缓存——旧记录被浏览器/系统/递归服务器按 TTL 缓存，没到时间不会重新查询；
      或改了文件但没递增 serial / 没 reload，权威自己都没加载新数据。
解法：dig @权威IP 域名 直查权威验证数据本身；改前先降 TTL 等过期；
      BIND 改完 rndc reload，serial 必须递增。

坑 2：开放递归被滥用，流量暴涨
结论：服务器突然出网流量暴涨，被打成 DNS 放大攻击的帮凶。
原因：recursion yes 且没限制 allow-recursion，任何人可借服务器递归（含伪造源 IP 放大）。
解法：allow-recursion { 内网网段; 127.0.0.1; }; 或纯权威设 recursion no；
      用 dig +norecurse @服务器 外部地址 验证已拒绝。

坑 3：CNAME 配在裸域（根域）上
结论：example.com 配了 CNAME 指向别处，解析异常/报错。
原因：裸域已隐式承载 SOA/NS 等记录，CNAME 要求「该名字下只有 CNAME」，两者冲突，标准禁止。
解法：裸域用 A 记录；CNAME 只用于子域名（www、gitlab 等）。

坑 4：反向解析没配 PTR，邮件被拒
结论：发出去的邮件对方拒收/进垃圾箱。
原因：对方邮件服务器对发信 IP 做反向解析（PTR），查不到或 PTR 与声明域名不符则拒信。
解法：找 IP 归属方（云厂商/机房）配置 PTR；自建反向 zone 时确保 in-addr.arpa 写法正确
      （网段倒写，主机号不写全 IP）。

坑 5：dig 和 nslookup 结果不一致，误判
结论：dig 查到新 IP，nslookup 还是旧 IP，怀疑系统出问题。
原因：两者走不同解析路径/缓存（nslookup 默认用系统 resolver，dig 直连 /etc/resolv.conf
      指定的服务器，行为与缓存状态可能不同）；或系统里多个 resolver 缓存不一致。
解法：以 dig 为准（最直接）；要排缓存干扰用 dig @权威IP；
      统一用 resolvectl flush-caches 清系统缓存后复测。

坑 6：装了 dnsmasq 起不来：端口 53 被占
结论：dnsmasq 启动报 failed to create listening socket for port 53: Address already in use。
原因：Ubuntu 默认 systemd-resolved 已占 127.0.0.53:53，dnsmasq 默认还要绑 127.0.0.1:53
      甚至全监听 0.0.0.0:53。
解法：dnsmasq 配 listen-address=内网IP + bind-interfaces（本机继续走 stub）；
      或停用 systemd-resolved 由 dnsmasq 接管（注意失去 DoT/按网卡多上游能力）。

坑 7：主从同步不生效，从服务器永远旧数据
结论：主服务器改了记录，从服务器查还是旧 IP。
原因：serial 没递增（最常见）——从服务器靠 serial 判断版本；或 allow-transfer 没配、
      TCP 53 被防火墙拦（AXFR 必须 TCP）。
解法：每次改记录 serial +1；主服务器配 allow-transfer { 从IP; }；
      nc -zv 从服务器→主服务器 53 测 TCP；dig @主IP 域名 AXFR 验证传输。

坑 8：search 域配置导致解析奇慢/结果不对
结论：ping 个短主机名（如 gitlab）要好几秒才出结果，或解析到错误地址。
原因：resolv.conf 配了 search 域（本机 tailc6bb9f.ts.net）时，解析器先试
      gitlab.tailc6bb9f.ts.net 再试 gitlab.，多轮查询；域写错就解析到无关地址。
解法：确认 search 域正确（resolvectl status 查看）；内网域名用全称查询；
      查私有域名时在 dnsmasq 配 domain-needed 避免无点域名泄漏上游。

坑 9：firewalld/SELinux 放行后 DNS 还是不通（RHEL）
结论：RHEL 上 named/dnsmasq 启动正常，但内网其他机器查不到。
原因：firewalld 默认挡 53/tcp+udp（需 firewall-cmd --add-service=dns --permanent）；
      SELinux enforcing 下 named 监听非默认端口或写区域文件被拒（AVC 拒绝日志可见）。
解法：firewall-cmd --permanent --add-service=dns && firewall-cmd --reload；
      SELinux 查 journalctl | grep -i avc，semanage port -a -t dns_port_t -p udp 5353 等按需放行。
```
