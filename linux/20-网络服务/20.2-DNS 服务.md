## 概述

DNS 服务把「域名」解析成「IP 地址」，是互联网的「电话簿」。自建 DNS 服务的场景：内网域名解析（内网主机名、服务发现）、域名缓存加速、权威域名服务器。三种实现：BIND（老牌权威+递归，功能最全）、dnsmasq（轻量，DNS+DNS 缓存+DHCP）、CoreDNS（云原生，K8s 默认，插件化）。核心：区域（zone，一个域名的记录集合）、记录类型（A/AAAA/CNAME/MX/NS 等）、解析流程（递归 vs 迭代）。

```text
# 实测（本机 DNS 相关）
$ command -v dnsmasq dig && echo "dnsmasq/dig 有"
dnsmasq/dig 有
$ dig -v | head -1
DiG 9.18.39-...-Ubuntu
# 本机装了 dnsmasq（轻量 DNS/DHCP）+ dig（DNS 查询工具）
```

## 核心概念

1. **区域（zone）**：一个域名（如 example.com）的「命名空间」，含该域名下所有记录，是 DNS 管理的基本单位。
2. **记录类型**：A（域名→IPv4）、AAAA（域名→IPv6）、CNAME（别名）、MX（邮件服务器）、NS（域名服务器）、TXT（文本/验证）、PTR（反向解析 IP→域名）。
3. **权威 vs 递归**：权威服务器（存域名记录，负责回答「自己的域名」），递归服务器（帮客户端查任意域名，会缓存）。
4. **正向 vs 反向解析**：正向（域名→IP），反向（IP→域名，PTR 记录）。

```text
核心概念：
区域 zone（域名记录集合）+ 记录类型（A/AAAA/CNAME/MX/NS/TXT/PTR）
权威（管自己的域名）vs 递归（帮查任意域名）
```

## 工作原理

DNS 解析流程（客户端查 www.example.com）：

1. **查缓存**：客户端先查本地 DNS 缓存（浏览器/系统/递归服务器），命中直接返回。
2. **递归查询**：本地递归服务器（如 8.8.8.8）帮客户端查，它从根服务器开始逐级问：根（.）→ com → example.com → www.example.com 的 A 记录。
3. **迭代过程**：根服务器告诉「去问 com 服务器」，com 告诉「去问 example.com 服务器」，example.com 权威服务器返回最终 IP。
4. **缓存**：递归服务器把结果缓存（按 TTL），下次直接返回。

「递归」是客户端让服务器全权查，「迭代」是服务器一步步问上级。

```text
解析流程：
客户端 → 本地缓存 → 递归服务器 → 根服务器 → .com 服务器 → example.com 权威 → 返回 IP
（递归 = 客户端委托全查；迭代 = 逐级问上级）
```

## 常用命令与配置

```shell
# 安装
apt install bind9            # BIND（权威/递归）
apt install dnsmasq          # dnsmasq（轻量 DNS+DHCP）

# dig 查询
dig example.com              # 查 A 记录（完整解析过程）
dig example.com +short       # 只返回结果
dig example.com MX           # 查 MX 记录
dig -x 8.8.8.8               # 反向解析
dig @8.8.8.8 example.com     # 指定 DNS 服务器查

# 服务管理
systemctl status named       # BIND（named 进程）
systemctl status dnsmasq
```

## 配置文件解析

dnsmasq 配置（轻量，适合内网 DNS 缓存 + 内网域名）：

```ini
# /etc/dnsmasq.conf
listen-address=127.0.0.1,192.168.1.10   # 监听地址
# 内网域名解析（本地 hosts 风格）
address=/gitlab.internal/192.168.1.20
address=/jenkins.internal/192.168.1.21
# 上游 DNS（本机解不了的转发到上游）
server=8.8.8.8
server=114.114.114.114
# 缓存大小
cache-size=1000
```

BIND 权威区域配置（/etc/bind/named.conf.local + 区域文件）：

```text
# named.conf.local 声明区域
zone "example.com" {
    type master;
    file "/etc/bind/db.example.com";
};

# db.example.com 区域文件（记录）
$TTL 3600
@     IN  SOA  ns1.example.com. admin.example.com. (...)
@     IN  NS   ns1.example.com.
@     IN  A    192.168.1.10
www   IN  A    192.168.1.10
mail  IN  A    192.168.1.11
@     IN  MX   10 mail.example.com.
```

```text
dnsmasq 配置：
address=/域名/IP  内网域名静态解析
server=IP         上游 DNS（转发）
BIND 配置：
zone 声明 + 区域文件（SOA/NS/A/CNAME/MX 记录）
```

## 应用场景实战

### 场景一：内网 DNS（dnsmasq 解析内网服务名）

```shell
# 1. 配置内网域名
# /etc/dnsmasq.conf 加：
#   address=/gitlab.internal/192.168.1.20
#   address=/registry.internal/192.168.1.21
# 2. 重启 dnsmasq
systemctl restart dnsmasq
# 3. 客户端指向这台 DNS，就能用域名访问内网服务
dig @127.0.0.1 gitlab.internal
```

### 场景二：用 BIND 建权威域名服务器

```shell
# 1. 装 bind9，配置区域（named.conf.local + 区域文件）
# 2. 检查配置
named-checkconf
named-checkzone example.com /etc/bind/db.example.com
# 3. 启动
systemctl restart named
# 4. 测试
dig @localhost example.com
```

## 性能与调优

```text
1. 缓存 —— 递归服务器开大缓存（cache-size），命中率高查询快
2. TTL —— 合理设 TTL（太长变更慢、太短查询多），平衡一致性和性能
3. 上游 DNS —— 递归服务器配多个上游，选响应快的（如 8.8.8.8/114.114.114.114）
4. 转发 vs 递归 —— 内网 DNS 用「转发到上游」比「自己递归」更快（上游有缓存）
```

## 安全与权限

```text
1. 防缓存投毒 —— DNSSEC 签名验证，防伪造 DNS 响应
2. 限制递归 —— 权威服务器关闭开放递归（防被用于 DNS 放大攻击）
3. 限制查询来源 —— 只对可信网段提供递归，防被滥用
4. 更新安全 —— 区域文件改动走 TSIG 签名（动态更新），防篡改
5. 别暴露版本 —— BIND 隐藏版本号（version 配置），防针对漏洞攻击
```

## 故障排查

### 域名解析不了

```shell
# 1. 分层排查：本地 hosts → 递归服务器 → 权威
cat /etc/hosts                    # 本地 hosts 有没有错误映射
dig example.com                   # 看解析过程（哪一步失败）
dig @8.8.8.8 example.com          # 绕过本地 DNS，测上游
# 2. 看 DNS 服务日志
journalctl -u named -n 50         # BIND
journalctl -u dnsmasq -n 50       # dnsmasq
# 3. 测 DNS 端口
nc -zvu 8.8.8.8 53                # UDP 53 通不通
```

## 常见问题

```text
Q1: 改了 DNS 记录不生效？
A: 缓存（TTL）——旧记录缓存到 TTL 过期。可 flush 缓存或等 TTL。

Q2: 递归和迭代查询区别？
A: 递归=客户端委托服务器全查（服务器给最终结果），迭代=服务器一步步问上级（给下一步的地址）。

Q3: A 和 CNAME 区别？
A: A 是域名直接到 IP，CNAME 是别名（指向另一个域名）。CNAME 不能用于裸域（根域）。

Q4: 内网 DNS 用 dnsmasq 还是 BIND？
A: 内网简单解析/缓存/DHCP 用 dnsmasq（轻量），完整权威服务器用 BIND（功能全）。
```

## 面试题

```text
1. 从输入 URL 到页面显示，DNS 做了什么？
   答：浏览器查缓存 → 系统查 hosts → 递归服务器逐级查询（根→顶级→权威）→ 拿到 IP → 建立连接。

2. DNS 用什么协议、什么端口？
   答：UDP 53（查询，快），TCP 53（区域传输、大响应）。

3. 什么是 DNS 缓存投毒？
   答：伪造 DNS 响应把域名指向恶意 IP。防护：DNSSEC 签名验证。

4. 权威和递归服务器的区别？
   答：权威存自己域名的记录（回答自己域名的查询），递归帮客户端查任意域名（会缓存）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 内网服务用内网 DNS（域名访问），别硬记 IP
2. 递归服务器开大缓存 + 选快上游，查询提速
3. 权威服务器关闭开放递归，防 DNS 放大攻击
4. 改记录后注意 TTL 缓存，紧急变更先调低 TTL
5. 用 dig（不是 nslookup）排错，信息最全

### 踩坑记录

```text
坑 1：改了记录不生效，以为是配置错了
结论：改了 DNS 记录，客户端还是解析到旧 IP。
原因：TTL 缓存，旧记录被缓存到过期。
解法：调低 TTL 或等缓存过期，测试用 dig @服务器 直查权威。

坑 2：权威服务器开着开放递归被滥用
结论：服务器被用于 DNS 放大攻击，流量暴涨。
原因：开放递归（任何人都能查），攻击者伪造源 IP 放大攻击。
解法：关闭开放递归，只对可信网段提供递归。

坑 3：CNAME 配在裸域（根域）上
结论：example.com 配 CNAME 指向别的域名，解析异常。
原因：裸域不能配 CNAME（会和 SOA/NS 冲突）。
解法：裸域用 A 记录，CNAME 用在子域名（www 等）。

坑 4：反向解析没配 PTR，邮件被拒
结论：发邮件被对方拒，因为 IP 反向解析失败。
原因：没配 PTR（反向）记录，对方做反向解析验证失败。
解法：配 IP 的反向解析（PTR 记录），邮件服务必备。

坑 5：dig 和 nslookup 结果不一致，误判
结论：dig 查到新 IP，nslookup 还是旧 IP。
原因：两者走不同的缓存/解析路径。
解法：以 dig 为准（最直接），dig @权威 排除缓存干扰。
```
