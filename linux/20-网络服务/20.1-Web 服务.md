## 概述

Web 服务是「对外提供 HTTP/HTTPS 服务的软件」，两大主流：Nginx（高性能、事件驱动、反向代理强，现在是首选）和 Apache（老牌、模块丰富、.htaccess 灵活）。核心能力：虚拟主机（一台机器多个站点）、反向代理（转发到后端）、TLS 证书（HTTPS 加密）。Nginx 因「高并发 + 低内存 + 反向代理强」成为现代 Web 服务的默认选择。

```text
# 实测（本机 nginx）
$ nginx -v
nginx version: nginx/1.24.0 (Ubuntu)
$ ls /etc/nginx/sites-enabled/
default  deepseek-harness.conf  new-admin.conf
# 本机 nginx 1.24.0，跑了 3 个站点（虚拟主机）
```

## 核心概念

1. **虚拟主机（virtual host）**：一台机器跑多个站点，按域名（server_name）或端口（listen）区分。
2. **反向代理**：代理「服务端」，客户端请求代理，代理转发到后端（隐藏后端、负载均衡）。
3. **TLS 证书**：HTTPS 的加密 + 身份认证，证书（cert）+ 私钥（key）配对。
4. **Nginx vs Apache**：Nginx 事件驱动（异步非阻塞，高并发强），Apache 进程/线程模型（.htaccess 灵活）。
5. **location 匹配**：Nginx 按 URL 路径匹配处理规则（前缀/正则/精确）。

```text
核心概念：
虚拟主机（server_name/listen 区分站点）+ 反向代理（转发后端）+ TLS（HTTPS）
Nginx 事件驱动高并发，Apache 模块丰富灵活
```

## 工作原理

Nginx 的工作模型是「Master-Worker + 事件驱动」：

1. **Master 进程**：读取配置、管理工作进程（fork/重启），不处理请求。
2. **Worker 进程**：每个 worker 是单线程事件循环，用 epoll 异步非阻塞处理成千上万的并发连接（一个 worker 能扛几万连接）。
3. **请求处理**：请求进来 → 匹配 server（域名/端口）→ 匹配 location（URL 路径）→ 静态文件直接返回 / 动态请求转发后端（proxy_pass）。

Apache 则是「每连接一个进程/线程」（prefork/worker 模型），高并发时内存开销大，这是 Nginx 取代 Apache 的核心原因。

```text
Nginx 模型：Master（管理）→ Worker（事件循环 epoll，单进程扛几万连接）
Apache 模型：每连接一进程/线程（高并发内存开销大）
```

## 配置文件解析

Nginx 配置结构（本机真实风格）：

```nginx
# /etc/nginx/nginx.conf 主配置
user www-data;
worker_processes auto;          # worker 数 = CPU 核数
events {
    worker_connections 1024;    # 每个 worker 的连接数
}
http {
    include /etc/nginx/sites-enabled/*;   # 引入站点配置
}

# 站点配置（虚拟主机 + 反向代理）
server {
    listen 80;
    server_name api.example.com;     # 虚拟主机：按域名区分

    location / {
        proxy_pass http://127.0.0.1:8080;   # 反向代理到后端
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    location /static/ {
        root /var/www;               # 静态文件直接返回
    }
}

# HTTPS 站点
server {
    listen 443 ssl;
    server_name example.com;
    ssl_certificate     /etc/ssl/cert.pem;   # 证书
    ssl_certificate_key /etc/ssl/key.pem;    # 私钥
    ssl_protocols TLSv1.2 TLSv1.3;           # 只留新协议
}
```

```text
关键配置：
server_name   虚拟主机域名（区分站点）
listen        端口（80/443）
location      按 URL 路径匹配规则
proxy_pass    反向代理目标
ssl_certificate 证书 + 私钥（HTTPS）
```

## 应用场景实战

### 场景一：一台机器跑多个站点（虚拟主机）

```nginx
server { listen 80; server_name a.example.com; root /var/www/a; }
server { listen 80; server_name b.example.com; root /var/www/b; }
# 按域名分发到不同目录，一台机器多个网站
```

### 场景二：反向代理 + TLS 终结（本机 deepseek-harness 场景）

```nginx
server {
    listen 8082 ssl;
    server_name _;
    ssl_certificate /etc/ssl/dsh.pem;
    ssl_certificate_key /etc/ssl/dsh.key;
    location / {
        proxy_pass http://127.0.0.1:3080;   # 后端服务只绑 127.0.0.1
    }
}
# 外部 HTTPS 访问 → nginx 解密 → 转发到内网 HTTP 后端
```

## 性能与调优

```text
1. worker_processes = CPU 核数，worker_connections 调大（高并发）
2. 开启 gzip 压缩（减小传输体积，省带宽）
3. 静态资源配缓存头 + proxy_cache（减轻后端）
4. 开启 HTTP/2（listen 443 ssl http2，多路复用）
5. sendfile on + tcp_nopush on（零拷贝发静态文件，减少 CPU）
```

## 安全与权限

```text
1. 隐藏版本号 —— server_tokens off，别暴露 nginx 版本
2. TLS 只用新协议 —— ssl_protocols TLSv1.2 TLSv1.3，禁老版本
3. 限制请求体大小 —— client_max_body_size，防超大上传攻击
4. 目录遍历防护 —— 禁止访问隐藏文件（location ~ /\. { deny all; }）
5. 反向代理时清理/覆盖 X-Forwarded-For，防伪造
```

## 故障排查

### 配置报错 / 启动失败

```shell
# 1. 测试配置语法（必做，报错会指出哪行）
nginx -t
# 2. 看错误日志
tail -f /var/log/nginx/error.log
# 3. 看端口是否被占用
ss -tlnp | grep :80
```

### 站点访问 403/404

```shell
# 403：权限问题（目录/文件权限、index 缺失）
ls -l /var/www/站点目录
# 404：路径不对（root/location 匹配错误）
nginx -T | grep -A10 'server_name 站点'
```

## 常见问题

```text
Q1: reload 和 restart 的区别？
A: reload 平滑重载配置（不中断连接），restart 停止再启动（短暂中断）。改配置用 reload。

Q2: 虚拟主机怎么区分多个站点？
A: 按 server_name（域名）或 listen（端口/不同 IP）区分，Nginx 按请求的 Host 头匹配。

Q3: 反向代理和正向代理区别？
A: 反向代理代理服务端（客户端不知道后端），正向代理代理客户端（服务端不知道客户端）。

Q4: 静态资源和动态请求怎么分离？
A: location 匹配：静态路径（/static/）直接 root 返回，动态路径 proxy_pass 转发后端。
```

## 面试题

```text
1. Nginx 为什么比 Apache 高并发？
   答：Nginx 事件驱动（epoll 异步非阻塞，单 worker 扛几万连接），Apache 每连接一进程/线程（内存开销大）。

2. 虚拟主机的工作原理？
   答：按请求的 Host 头（域名）匹配 server_name，分发到不同站点。一台机器多个域名多个站点。

3. Nginx 怎么做到平滑升级/重载？
   答：Master 进程读新配置、fork 新 worker，旧 worker 处理完现有连接后退出，实现无中断 reload。

4. 502 和 504 区别？
   答：502 后端无响应（挂了/端口不对），504 后端超时（处理太久，超过 proxy_read_timeout）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 改配置先 nginx -t 测试，再 reload（不中断服务）
2. 静态资源配缓存头 + gzip，减轻后端压力
3. TLS 在 Nginx 层终结，后端走内网 HTTP
4. worker_processes = CPU 核数，充分利用多核
5. 用 nginx -T 看「实际生效的完整配置」（含所有 include）

### 踩坑记录

```text
坑 1：改了配置没 nginx -t 直接 reload，起不来
结论：配置有语法错误，reload 失败服务中断。
原因：没先测试语法，错误配置直接加载。
解法：改完先 nginx -t，通过再 reload。

坑 2：proxy_pass 路径结尾的 / 写错
结论：proxy_pass http://backend 和 http://backend/ 转发路径不同。
原因：结尾 / 影响「是否拼接 location 匹配到的路径」。
解法：理解 proxy_pass 路径拼接规则，按需加/去 /。

坑 3：server_name 配了但不生效
结论：访问域名还是匹配到 default 站点。
原因：请求的 Host 头和 server_name 不匹配，落到默认站点。
解法：确认域名解析正确 + server_name 和实际访问域名一致。

坑 4：静态文件 403，权限问题
结论：静态资源访问 403。
原因：目录/文件权限不对（nginx 用户没读权限），或 index 文件缺失。
解法：确认 nginx 运行用户（www-data）对目录有读权限。

坑 5：HTTPS 证书配了浏览器还报不安全
结论：证书配了但浏览器报证书错误。
原因：证书和域名不匹配、证书过期、或用了自签证书。
解法：确认证书 CN/SAN 匹配域名、未过期，生产用正规 CA 证书。
```
