## 概述

Web 服务是「对外提供 HTTP/HTTPS 服务的软件」，是 Linux 运维的核心技能。主流实现三大类：**Nginx**（高性能、事件驱动、反向代理强，现代首选）、**Apache**（老牌、模块丰富、`.htaccess` 灵活，存量大量存在）、**Caddy**（自动 HTTPS，新兴轻量方案）。核心能力四件套：**虚拟主机**（一台机器跑多个站点）、**反向代理**（转发到后端并做负载均衡）、**TLS 证书**（HTTPS 加密与身份认证）、**静态资源服务**（高并发文件分发）。

选型结论一句话：**高并发 + 低内存 + 反向代理强选 Nginx；深度依赖 `.htaccess`/模块生态的存量系统留在 Apache；追求零配置 HTTPS 的小型项目试 Caddy。**

本机（Ubuntu 24.04）就跑着 nginx 1.24.0，共 3 个站点：默认站点（80 端口）、deepseek-harness（443 TLS 反代 + WebSocket）、new-admin（8082 端口 SPA + API 反代），下文大量配置解析直接以本机真实文件为素材。

## 核心概念

1. **虚拟主机（virtual host）**：一台机器跑多个站点，靠 `listen`（IP/端口）和 `server_name`（域名）区分。Nginx 收到请求后先按 IP/端口定位 server 块，再按请求的 Host 头匹配 `server_name`。
2. **反向代理（reverse proxy）**：代理「服务端」。客户端只知道代理的地址，代理把请求转发给后端（隐藏后端拓扑、集中做 TLS/限流/缓存/负载均衡）。对应概念**正向代理**代理「客户端」（如公司上网代理），服务端不知道真实客户端。
3. **TLS 证书**：HTTPS 的加密 + 身份认证。证书（cert，公钥 + 域名 + CA 签名）与私钥（key）配对，私钥必须保密（权限 600）。生产用 Let's Encrypt 等正规 CA，内网可自签。
4. **Nginx vs Apache**：Nginx 事件驱动（异步非阻塞，单 worker 扛数万连接），Apache 进程/线程模型（prefork/worker，每连接一进程或一线程，内存开销大）。Apache 优势在模块化生态与 `.htaccess` 目录级配置。
5. **location 匹配**：Nginx 按 URL 路径选择处理规则，匹配优先级：**`=` 精确 > `^~` 前缀（命中后不再查正则）> `~`/`~*` 正则 > 普通前缀（最长匹配）**。
6. **upstream 负载均衡**：一组后端服务器组成 upstream，proxy_pass 转发时按轮询/权重/IP hash 等策略分发，是实现高可用的基础（详见 [[19.4-HAProxy 与 Nginx]]）。
7. **Master-Worker 架构**：master 进程管配置与 worker 生命周期（不处理请求），worker 进程各自独立事件循环处理连接，`worker_processes auto` = CPU 核数。
8. **Caddy**：Go 写的 Web 服务器，最大特点是「自动申请/续期 HTTPS 证书」，配置极简（Caddyfile），适合中小型项目；生态和定制能力弱于 Nginx。

```text
核心概念速记：
虚拟主机（listen + server_name 区分站点）
反向代理（proxy_pass 转发后端，客户端只见代理）
TLS（cert 公钥 + key 私钥配对，HTTPS 加密认证）
location 优先级：= > ^~ > ~* > 最长前缀
Nginx 事件驱动高并发；Apache 模块丰富 .htaccess 灵活
```

## 工作原理

### Nginx 的 Master-Worker + 事件驱动模型

1. **Master 进程**：以 root 启动，读取/校验配置、fork worker、监听 worker 心跳（异常自动拉起）、处理 `reload`/`upgrade` 信号。**不处理任何请求**。
2. **Worker 进程**：以低权限用户（本机 `www-data`）运行，每个 worker 是**单线程事件循环**，用 epoll（Linux）异步非阻塞管理大量连接——一个 worker 理论可扛数万并发连接（受 `worker_connections` 限制）。8 核机器 `worker_processes auto` 会起 8 个 worker，实测见下。
3. **请求处理流水线**：连接进来（accept）→ 解析请求行/头 → 按 `listen` 选 server 块 → 按 Host 头匹配 `server_name` → 按 URL 匹配 `location` → 静态文件直接返回（sendfile 零拷贝）/ 动态请求 `proxy_pass` 转发后端 → 记录 access_log。
4. **reload 原理**：master 收到 HUP 信号后读取新配置，语法通过则 fork 新 worker，**旧 worker 处理完当前连接后优雅退出**——这就是「平滑重载不中断连接」的实现机制（实测 `systemctl reload nginx` 就是这么做的）。

### location 匹配优先级（高频考点）

匹配顺序与优先级从高到低：

| 优先级 | 写法 | 含义 | 示例 |
|---|---|---|---|
| 1 | `location = /path` | 精确匹配，命中即停 | `location = /login` |
| 2 | `location ^~ /path` | 前缀匹配，命中后不再查正则 | `location ^~ /static/` |
| 3 | `location ~ 正则`（区分大小写）/ `~*`（不区分） | 正则匹配，按文件内出现顺序 | `location ~* \.(jpg\|png)$` |
| 4 | `location /path` | 普通前缀，取**最长**的那个 | `location /api/` |

规则要点：先看 `=` 精确；再看 `^~` 前缀（命中直接结束）；然后按顺序试所有正则（第一个命中的生效）；最后普通前缀取最长匹配。正则之间**有顺序性**，前缀之间**无顺序性（取最长）**。

### proxy_pass 的 URI 传递规则（最容易踩坑）

`proxy_pass` 带不带末尾 `/`，决定是否把 location 匹配到的路径**拼接**到后端 URI 上：

```nginx
# 情况 1：proxy_pass 不带 URI（无路径部分）→ 原样转发完整 URI
location /api/ {
    proxy_pass http://127.0.0.1:8081;        # 请求 /api/user → 后端 /api/user
}

# 情况 2：proxy_pass 带 URI（有路径）→ location 匹配部分被替换
location /api/ {
    proxy_pass http://127.0.0.1:8081/;       # 请求 /api/user → 后端 /user（/api 被剥掉）
}

# 情况 3：location 是正则时，proxy_pass 不能带 URI（只能写 host:port）
location ~ ^/api/(.*)$ {
    proxy_pass http://127.0.0.1:8081/$1;     # 用捕获组手动拼
}
```

本机 new-admin 站点就是「情况 2」：`location /api/` + `proxy_pass http://127.0.0.1:8081/`，前端调 `/api/xxx` 会被剥掉 `/api` 前缀后转发给 8081 后端。

### server_name 匹配规则

- 多个 server 同端口时，Nginx 按请求 Host 头与 `server_name` 匹配：精确匹配 > 通配符（`*.example.com`）> 正则（`~^www\.`）> 都不中则落 **default_server**（本机 default 站点 `server_name _;` 就是兜底）。
- 匹配不到且没标 default_server 时，取该端口第一个 server 块。
- `server_name _;` 是「通配任意域名」的惯例写法（`_` 本身不是特殊字符，只是不像真实域名的名字）。

### Apache 与 Caddy 的工作原理简述

- **Apache**：prefork（每连接一进程，稳但吃内存）/ worker（每连接一线程）/ event（事件驱动，2.4 起可用）。请求先按 `<VirtualHost>` 匹配域名，再按 `<Directory>`/`.htaccess` 逐目录叠加权限与重写规则——灵活但每请求都要解析配置，性能上限低于 Nginx。
- **Caddy**：Go 原生并发模型，自动从 Let's Encrypt/ZeroSSL 申请证书并续期，配置即 Caddyfile（`example.com { reverse_proxy localhost:8080 }` 一行搞定反代+HTTPS）。

### TLS 握手简要过程

客户端发起 ClientHello（含 SNI 域名）→ 服务端按 SNI 选证书返回 ServerHello + 证书链 → 双方协商密钥（TLS1.3 用 1-RTT）→ 校验证书（域名/有效期/CA 信任链）→ 建立加密通道。**SNI（Server Name Indication）让一台服务器一个 IP 能按域名提供不同证书**——虚拟主机 + HTTPS 的前提，本机 443 就是靠 SNI 服务 deepseek-harness 域名的。

## 配置文件解析

Nginx 配置是**块（block）嵌套结构**：全局块 → `events {}` → `http {}` → `server {}` → `location {}`。下面逐层解析本机真实配置。

### 主配置 /etc/nginx/nginx.conf（本机真实内容 + 逐行注释）

```nginx
user www-data;                        # worker 运行用户（低权限，安全）
worker_processes auto;                # worker 数 = CPU 核数（本机 8 核 → 8 个 worker）
pid /run/nginx.pid;
error_log /var/log/nginx/error.log;
include /etc/nginx/modules-enabled/*.conf;   # 动态模块（Ubuntu 特色目录）

events {
    worker_connections 768;           # 单 worker 最大并发连接数（默认 768）
    # multi_accept on;                # 一次 accept 多个连接（高并发可开）
}

http {
    # ---- 基础 ----
    sendfile on;                      # 零拷贝发静态文件，省 CPU
    tcp_nopush on;                    # 与 sendfile 配合，攒够包再发
    types_hash_max_size 2048;
    # server_tokens off;              # ← 默认注释掉！所以响应头暴露 nginx/1.24.0
    include /etc/nginx/mime.types;    # 文件扩展名 → Content-Type 映射
    default_type application/octet-stream;

    # ---- SSL 全局默认 ----
    ssl_protocols TLSv1 TLSv1.1 TLSv1.2 TLSv1.3;   # ← Ubuntu 默认还留着 TLSv1/1.1，生产应收紧
    ssl_prefer_server_ciphers on;

    # ---- 日志 ----
    access_log /var/log/nginx/access.log;

    # ---- gzip ----
    gzip on;                          # 只开开关，gzip_types 被注释 → 只压缩默认的 text/html
    # gzip_vary on;
    # gzip_proxied any;
    # gzip_comp_level 6;              # 建议打开并设 5~6
    # gzip_types text/plain text/css application/json application/javascript ...;  # 建议打开

    # ---- 站点引入（Ubuntu 两个都 include） ----
    include /etc/nginx/conf.d/*.conf;      # ← deepseek-harness.conf、new-admin.conf 在这
    include /etc/nginx/sites-enabled/*;    # ← default 在这（软链接）
}
```

**Red Hat 系差异对照表**：

| 项目 | Ubuntu/Debian | RHEL/CentOS/Fedora |
|---|---|---|
| 站点目录 | `/etc/nginx/sites-available/` + `sites-enabled/`（软链接启停） | 无此目录，全部放 `/etc/nginx/conf.d/*.conf` |
| nginx.conf 引入 | `include /etc/nginx/sites-enabled/*;` | `include /etc/nginx/conf.d/*.conf;` |
| 默认站点 | `sites-available/default` | `conf.d/default.conf` |
| 默认用户 | `www-data` | `nginx` |
| 防火墙 | ufw（[[12.3-firewalld-ufw]]） | firewalld（`firewall-cmd --add-service=http`） |
| SELinux | 无（AppArmor 对 nginx 默认不限制） | **SELinux enforcing 默认挡 nginx 出网反代**（需 `setsebool -P httpd_can_network_connect 1`） |

### 站点配置 /etc/nginx/sites-available/default（本机 80 端口默认站点）

```nginx
server {
    listen 80 default_server;        # 80 端口的兜底站点
    listen [::]:80 default_server;

    root /var/www/html;              # 站点根目录（index 等相对它找）
    index index.html index.htm index.nginx-debian.html;

    server_name _;                   # 匹配任意域名（兜底）

    location / {
        try_files $uri $uri/ =404;   # 先找文件 → 再找目录 → 都没有返回 404
    }
    # 被注释的模板：~ \.php$ 走 fastcgi_pass unix:/run/php/php-fpm.sock（PHP 站点参考）
}
```

### 反向代理站点 conf.d/deepseek-harness.conf（本机 443 TLS + WebSocket 反代）

```nginx
# WebSocket 升级头映射：有 Upgrade 头就转发 upgrade 连接，否则保持 close
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 100.71.112.119:443 ssl;        # 只绑 Tailscale 内网 IP 的 443
    server_name lw-vostro-7580.tailc6bb9f.ts.net;

    ssl_certificate     /etc/nginx/ssl/lw-vostro-7580.tailc6bb9f.ts.net.crt;
    ssl_certificate_key /etc/nginx/ssl/lw-vostro-7580.tailc6bb9f.ts.net.key;
    ssl_protocols TLSv1.2 TLSv1.3;        # 已收紧（比主配置的全局默认更严）

    location / {
        proxy_pass http://127.0.0.1:3080;         # 后端只绑回环，外部不可直连
        proxy_http_version 1.1;                   # 反代必须 1.1（keepalive/Upgrade 需要）
        proxy_set_header Host 127.0.0.1:3080;     # 后端按 Host 判断时用
        proxy_set_header X-Real-IP $remote_addr;  # 真实客户端 IP
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;   # 告诉后端「原始协议是 https」
        proxy_set_header Upgrade $http_upgrade;       # WebSocket 三件套
        proxy_set_header Connection $connection_upgrade;
        proxy_buffering off;                  # 流式响应（SSE/长连接）必须关
        proxy_read_timeout 3600s;             # 长连接超时放宽（默认 60s）
    }
}
```

### SPA 站点 conf.d/new-admin.conf（本机 8082 端口）

```nginx
server {
    listen 8082;
    server_name _;

    root /opt/project-work/new-Project/new-admin/dist;   # Vue3 构建产物目录
    index index.html;

    # history 路由回退：前端路由刷新时路径不存在，统一回 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 后端 API 反向代理：/api/* → 127.0.0.1:8081/*
    location /api/ {
        proxy_pass http://127.0.0.1:8081/;    # 带斜杠 → 剥掉 /api 前缀
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 60s;
        proxy_read_timeout 300s;
    }

    # 静态资源长缓存（构建产物带 hash，可放心 immutable）
    location /assets/ {
        expires 7d;
        add_header Cache-Control "public, immutable";
    }
}
```

```text
# 实测（本机）——/api/ 前缀被剥离后转发到 8081 后端，后端 java 正常响应
$ ss -tlnp | grep ':8081'
LISTEN 0  100  *:8081  *:*  users:(("java",pid=3691570,fd=13))
$ curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://localhost:8082/api/nonexistent
HTTP 200
# 后端对未知路径返回 200（业务行为），但链路是通的：nginx 8082 → java 8081
```

### log_format 自定义日志格式（生产常用）

```nginx
http {
    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for" "$upstream_addr" '
```

`$request_time`（nginx 处理总耗时）与 `$upstream_addr`/`$upstream_response_time`（后端 IP 与耗时）是排查慢请求的关键字段，日志分析可配合 [[13.5-日志分析实战]]。

## 应用场景实战

### 场景一：一台机器跑多个站点（虚拟主机，本机 3 站点实例）

原理：按 `listen`（端口/IP）分流 server 块，再按 `server_name` 匹配域名。本机三个站点互不干扰：

```text
# 实测（本机）——3 个站点并存
$ nginx -T 2>/dev/null | grep -E '^\s*(listen|server_name)' | grep -v '#'
    listen 100.71.112.119:443 ssl;
    server_name lw-vostro-7580.tailc6bb9f.ts.net;   # 站点1：deepseek-harness (TLS)
    listen 100.71.112.119:3080;
    server_name _;                                  # 站点1 的 HTTP 兜底
    listen 8082;
    server_name _;                                  # 站点2：new-admin (8082)
    listen 80 default_server;
    listen [::]:80 default_server;
    server_name _;                                  # 站点3：default (80)
```

新增站点三步走（Ubuntu 风格）：① 在 `sites-available/` 写配置 → ② `ln -s /etc/nginx/sites-available/xx /etc/nginx/sites-enabled/xx` 启用 → ③ `nginx -t && systemctl reload nginx`。**Red Hat 系跳过软链接，直接放 `conf.d/`**。

### 场景二：反向代理 + TLS 终结 + WebSocket（deepseek-harness 完整场景）

需求：后端服务只监听 127.0.0.1:3080（对外不可达），需要外部通过 HTTPS 访问，且后端有 WebSocket/SSE 长连接。方案：Nginx 做 TLS 终结 + 反代，配置见上文 deepseek-harness.conf。关键点：

- **TLS 终结**：证书/加解密都在 Nginx，后端只走内网 HTTP（明文在内网传播，安全边界由 Nginx 守住）。
- **WebSocket 支持**：必须 `proxy_http_version 1.1` + 显式转发 `Upgrade`/`Connection` 头（map 指令按需切换）。
- **流式响应**：SSE 等场景 `proxy_buffering off`，否则数据攒到缓冲满才推给客户端，表现为「接口迟迟不返回」。
- **长超时**：`proxy_read_timeout 3600s`，否则 60s 无数据就被 Nginx 掐断连接。

```text
# 实测（本机）——反代链路 curl 验证
$ curl -skI --resolve lw-vostro-7580.tailc6bb9f.ts.net:443:100.71.112.119 \
    https://lw-vostro-7580.tailc6bb9f.ts.net/ | grep -E 'HTTP|Content-Type'
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
# 外部 HTTPS → Nginx(443) 解密 → 转发 http://127.0.0.1:3080 → 后端
```

### 场景三：SPA 前端 + API 反向代理 + 静态资源缓存（new-admin 场景）

需求：Vue3 前端（history 路由）与 Java 后端（8081）分离部署，前端构建产物由 Nginx 托管。配置见上文 new-admin.conf，三个要点：

1. **history 路由回退**：`try_files $uri $uri/ /index.html` —— 前端路由是伪路径（如 `/users`），服务器没有这个文件，必须回退 index.html 交给前端路由处理；漏了这条，刷新子页面会 404。
2. **API 前缀剥离**：`location /api/ { proxy_pass http://127.0.0.1:8081/; }` 把 `/api/xxx` 转成 `/xxx` 发给后端（见「工作原理」的 URI 规则）。
3. **带 hash 的静态资源长缓存**：构建产物文件名带内容 hash（`app.abc123.js`），可以放心 `expires 7d` + `Cache-Control: public, immutable`；入口 `index.html` 保持短缓存/不缓存，否则发版后用户拿到旧 HTML 引用旧资源。

```text
# 实测（本机）——SPA 首页与静态资源缓存头
$ curl -sI http://localhost:8082/ | grep -E 'HTTP|Content-Type'
HTTP/1.1 200 OK
Content-Type: text/html
$ curl -sI http://localhost:8082/assets/ 2>/dev/null | head -2 || true
# /assets/ 目录若存在则响应头含：Cache-Control: public, immutable / Expires: ...7d
```

### 场景四：upstream 负载均衡（多后端）

```nginx
upstream backend_pool {
    # 默认轮询；可加 weight=3（权重）、backup（备机）、down（摘除）
    server 10.0.0.11:8080 weight=3;
    server 10.0.0.12:8080;
    server 10.0.0.13:8080 backup;          # 前两台挂了才启用
    keepalive 32;                          # 与后端的长连接池
}

server {
    listen 80;
    server_name api.example.com;
    location / {
        proxy_pass http://backend_pool;    # 转发到 upstream 组
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

策略：轮询（默认）/ `weight`（权重）/ `ip_hash`（同 IP 固定后端，会话保持）/ `least_conn`（最少连接）。健康检查：被动（连续失败 N 次自动摘除，`max_fails` + `fail_timeout`）；主动健康检查是商业版/OpenResty 功能。高可用编排见 [[19.4-HAProxy 与 Nginx]] 与 [[19.1-高可用基础]]。

### 场景五：完整 HTTPS 站点配置（HTTP/2 + 跳转 + 安全头）

```nginx
# HTTP → HTTPS 跳转
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;   # 301 永久跳转（保留路径参数）
}

server {
    listen 443 ssl http2;                    # Ubuntu 1.24 写法；1.25.1+ 推荐 listen 443 ssl;  + http2 on;
    server_name example.com www.example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;           # 禁用 TLSv1/1.1（POODLE/BEAST 漏洞）
    ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:...';
    ssl_prefer_server_ciphers on;
    ssl_session_cache shared:SSL:10m;        # TLS 会话缓存，减握手开销
    ssl_session_timeout 10m;

    add_header Strict-Transport-Security "max-age=31536000" always;  # HSTS
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-XSS-Protection "1; mode=block" always;

    root /var/www/example.com;
    index index.html;
    location / { try_files $uri $uri/ =404; }
}
```

## 性能与调优

```text
1. worker_processes = CPU 核数（auto 即可）；worker_connections 按需调大（默认 768，高并发提到 1024~4096）
2. 开 gzip 压缩：gzip on + gzip_types（text/plain text/css application/json application/javascript ...）+ gzip_comp_level 5~6
3. 静态资源缓存：expires/Cache-Control 长缓存 + proxy_cache 缓存后端响应（减轻后端压力）
4. HTTP/2：listen 443 ssl http2（多路复用，一个连接并发多个请求，显著减延迟）
5. sendfile on + tcp_nopush on（零拷贝发文件）；keepalive_timeout 65 保持客户端连接复用
6. upstream keepalive 32（nginx 与后端的长连接池，避免反复建连）
7. 日志：access_log off 静态资源路径（图片/视频），或 log_format 精简，减少磁盘 IO
8. 压测验证：ab -n 10000 -c 100 / wrk / 配合 [[16.5-网络性能]] 与 [[16.6-综合调优工具]]
```

**keepalive 详解**：`keepalive_timeout 65`（客户端→Nginx 连接保持 65s，同一页面多资源复用连接）；`upstream 块内 keepalive 32`（Nginx→后端连接池，需 `proxy_http_version 1.1` + `proxy_set_header Connection ""`，否则连接用完即关，keepalive 无效——这是最常见的「配了没生效」坑）。

**gzip 详解**：`gzip on` 只压缩默认的 `text/html`；要让 CSS/JS/JSON 也压缩必须显式 `gzip_types`；`gzip_min_length 1k`（太小的响应压缩反而更慢）；`gzip_vary on`（响应头加 Vary: Accept-Encoding，利于中间缓存）。

```text
# 实测（本机）——gzip 开关对比（默认站点 text/html）
$ curl -sI http://localhost | grep -iE 'content-encoding|content-length'
Content-Length: 615                        # 未请求压缩 → 原样 615 字节
$ curl -sI -H 'Accept-Encoding: gzip' http://localhost | grep -iE 'content-encoding|content-length'
Content-Encoding: gzip
# gzip on 对 text/html 默认生效；注意本机 gzip_types 被注释，
# 所以 text/css / application/json 等类型实际不会压缩（常见调优点）
```

**缓存分层**：浏览器缓存（`expires`/`Cache-Control`，静态资源）→ Nginx `proxy_cache`（后端动态响应缓存，`proxy_cache_path` + `proxy_cache_key` + `proxy_cache_valid`）→ 后端应用缓存。命中率可用 `$upstream_cache_status` 字段记录到日志统计。

## 安全与权限

```text
1. 隐藏版本号 —— server_tokens off（响应头不再暴露 nginx/1.24.0）
2. TLS 收紧 —— ssl_protocols TLSv1.2 TLSv1.3；禁用弱密码套件；证书私钥 chmod 600
3. 请求体限制 —— client_max_body_size 10m（防超大上传拖垮服务）
4. 目录遍历防护 —— 禁止访问隐藏文件/敏感文件（location ~ /\. { deny all; }）
5. 反代头防伪造 —— 只信任上游代理的 X-Forwarded-For，或直接覆盖
6. 安全响应头 —— HSTS / X-Content-Type-Options / X-Frame-Options / CSP
7. 运行权限 —— worker 用 www-data 低权限用户，站点文件权限收紧（755 目录/644 文件）
8. 访问控制 —— 敏感路径加 allow/deny、basic auth（auth_basic）、限速 limit_req
9. 防暴力破解 —— limit_req_zone 对登录接口限速（如 10r/s），配合 fail2ban
```

```text
# 实测（本机）——版本号暴露问题（server_tokens 未关）
$ curl -sI http://localhost | grep -i '^server:'
Server: nginx/1.24.0 (Ubuntu)
# 生产环境应 nginx.conf 打开 server_tokens off;，响应头只剩 "Server: nginx"
```

**隐藏文件防护配置**：

```nginx
location ~ /\. {
    deny all;                      # 拒绝访问 .git/.env/.htaccess 等点开头文件
}
# 或按文件名精确拒：
location = /.env        { deny all; }
location = /.git/config { deny all; }
```

**Red Hat 系 SELinux 注意**（[[23.2-强制访问控制]]）：RHEL 系 nginx 默认 SELinux enforcing，反代出网会被拦（`connect()` 到后端报 502），必须放行：

```shell
setsebool -P httpd_can_network_connect 1      # 允许 nginx 作为反向代理连后端
# 非默认端口（如 8082）还要把端口加进 http_port_t：
semanage port -a -t http_port_t -p tcp 8082
# 排查：ausearch -m avc -ts recent 或 journalctl | grep -i avc
```

Ubuntu（AppArmor）默认对 nginx 无此类限制；防火墙用 ufw（[[12.3-firewalld-ufw]]）：`ufw allow 80,443/tcp`。

### 案例 2：502 Bad Gateway / 504 Gateway Timeout（反代后端问题）

```shell
# 502：nginx 连不上后端（后端没起/端口错/防火墙/后端崩溃）
```

## 常见问题

```text
Q1: nginx reload 和 restart 的区别？
A: reload 是平滑重载——master 读新配置、fork 新 worker，旧 worker 处理完存量连接后退出，期间不中断服务；
   restart 是 stop + start，会短暂断连。改配置用 reload（先 nginx -t），只有改监听端口/模块等大动作用 restart。

Q2: 虚拟主机怎么区分多个站点？
A: 两层区分：listen（IP/端口）先圈定 server 块范围；同端口内再按请求 Host 头匹配 server_name
   （精确 > 通配符 > 正则 > default_server 兜底）。一台机器可以跑任意多个站点。

Q3: 反向代理和正向代理的区别？
A: 反向代理代理「服务端」——客户端只认识代理，代理把请求转发给隐藏的后端（TLS 终结、负载均衡、缓存）；
   正向代理代理「客户端」——服务端只看到代理，代理替客户端去访问（翻墙、上网审计）。判断标准：代理在谁那边。

Q4: 静态资源和动态请求怎么分离？
A: 用 location 分流：静态路径（/static/、/assets/、图片扩展名正则）直接 root/alias 返回并加缓存头；
   动态路径（/api/、.php$）proxy_pass/fastcgi_pass 转发后端。动静分离是性能优化的基本功。

Q5: 502 和 504 有什么区别？
A: 502 Bad Gateway = nginx 连不上后端（后端没起、端口错、SELinux 拦截、后端崩溃）；
   504 Gateway Timeout = 连上了但后端超时（处理超过 proxy_read_timeout，默认 60s）。看 error.log 的
   connect() failed（502）vs upstream timed out（504）即可区分。

Q6: proxy_pass 后面带不带 / 有什么区别？
A: 不带 URI（proxy_pass http://host:port）→ 完整 URI 原样转发；
   带 URI（proxy_pass http://host:port/）→ location 匹配到的部分被替换为 URI。
   例：location /api/ + proxy_pass http://x:8081/ → 请求 /api/user 到后端变成 /user。
   配错会导致后端 404 或路径重复（/api/api/xxx）。

Q7: server_name _ 是什么意思？
A: 表示「匹配任意未匹配到的域名」，用作兜底（default_server 的常规搭档），
   防止未知域名请求落到错误站点。注意 _ 不是通配符语法，只是约定俗成的名字。

Q8: 为什么改了 nginx 配置后要 reload 而不是 restart？
A: reload 不中断在线连接（平滑），restart 会瞬间断所有连接；
   且 reload 有配置校验兜底（语法错时保持旧配置运行），restart 配错就直接起不来了。
```

## 面试题

```text
1. Nginx 为什么比 Apache 高并发？
   答：Nginx 是事件驱动模型（epoll 异步非阻塞 + 单线程事件循环），一个 worker 进程可同时管理数万连接，
       内存占用与连接数无关；Apache 传统 prefork/worker 是「每连接一进程/线程」，高并发时进程数暴涨、
       内存与上下文切换开销巨大。所以同硬件下 Nginx 能扛的并发量高一个数量级。

2. 虚拟主机的工作原理？（一台服务器多个网站）
   答：所有站点共享一个 Nginx 进程，配置里多个 server 块。请求进来后：按 listen（IP/端口）选 server
       范围 → 按 HTTP 请求的 Host 头匹配 server_name（精确 > 通配 > 正则 > 默认站点）→ 进入对应
       server 块的 root/location 处理。对外表现就是「一个 IP 上按域名提供不同网站」。

3. Nginx 怎么实现平滑重载/平滑升级？
   答：master 进程收到 HUP 信号后 fork 新配置的 worker，新 worker 开始 accept 新连接；
       旧 worker 被标记为不再接收新连接，处理完当前请求后自动退出，全程无连接中断。
       平滑升级（换二进制）用 USR2 信号起新 master + WINCH 退旧 worker，实现 0 停机升级。

4. location 匹配优先级？
   答：= 精确匹配（最高）→ ^~ 前缀匹配（命中即停，不再查正则）→ ~ / ~* 正则匹配（按配置顺序，
       第一个命中的生效）→ 普通前缀匹配（取最长）。规则速记：先精确、再 ^~、再正则、最后最长前缀。

5. 如何给一个站点配置 HTTPS？（从申请到生效）
   答：① 用 certbot（Let's Encrypt）或购买 CA 证书，得到 fullchain.pem（证书链）+ privkey.pem（私钥）；
       ② server 块 listen 443 ssl; 配置 ssl_certificate / ssl_certificate_key；
       ③ ssl_protocols 只留 TLSv1.2 TLSv1.3；
       ④ 80 端口 return 301 https://$host$request_uri 跳转；
       ⑤ nginx -t && reload；⑥ certbot renew 配置自动续期（90 天有效期）。

6. 502/504 排查思路？
   答：502（连接失败）：确认后端进程在不在（ss -tlnp 看端口）→ 直接 curl 后端地址测通不通 →
       看 error.log 的 connect() failed（含端口/权限/SELinux 提示）→ 按原因修复；
       504（超时）：先确认后端处理时间（upstream_response_time），确属慢业务就调大
       proxy_read_timeout/proxy_send_timeout，或优化后端。后端恢复后 Nginx 无需重启自动恢复。

7. Nginx 如何做动静分离与缓存？
   答：动静分离：location 按路径/扩展名分流，静态走 root 直出（sendfile 零拷贝）+ expires 长缓存头，
       动态走 proxy_pass/fastcgi_pass 到后端；缓存：静态资源靠浏览器缓存（Cache-Control），
       后端响应用 proxy_cache（nginx 层缓存）、upstream keepalive 减少建连开销。

8. Apache 和 Nginx 怎么选？
   答：新项目高并发/反代/网关场景选 Nginx（性能好、配置轻）；存量系统依赖 .htaccess、
       mod_rewrite 目录级配置、或特定模块生态的留在 Apache（兼容性优先）；追求自动 HTTPS
       的小项目可考虑 Caddy。二者也可以共存：Nginx 做前端反代，后面挂 Apache 跑老应用。
```

## 最佳实践与踩坑记录

### 最佳实践

1. **改配置三件套**：`nginx -t` → `systemctl reload nginx` → `curl -I` 验证。绝不跳过语法测试直接 reload。
2. **用 `nginx -T` 看生效配置**：include 层层展开后的完整配置才是「真相」，排查时以它为准。
3. **站点文件分离**：每个站点一个配置文件（Ubuntu 放 sites-available + 软链接启停），禁止全塞 nginx.conf。
4. **TLS 统一在 Nginx 层终结**：后端走内网 HTTP，证书只配一份，加密解密集中管理（本机 deepseek-harness 即此模式）。
5. **静态资源动静分离 + 长缓存 + gzip**：构建产物带 hash 的配 immutable 长缓存，CSS/JS/JSON 开 gzip。
6. **日志记录关键字段**：自定义 log_format 带上 `$request_time`、`$upstream_response_time`、`$upstream_addr`，慢请求可回溯。
7. **worker_processes auto + worker_connections 按需调大**，配合压测（ab/wrk）验证而不是拍脑袋。
8. **证书自动续期**：Let's Encrypt 证书 90 天有效，必须 certbot renew（systemd timer）自动化，并做 renew --dry-run 演练。

### 踩坑记录

```text
坑 1：改了配置没 nginx -t 直接 reload，站点全挂
结论：reload 后所有站点 502/无法访问，服务异常。
原因：配置有语法错误，reload 时 master 加载失败，保持旧配置但连接被重置，甚至服务退出。
解法：养成铁律——改完先 nginx -t，通过再 reload；线上环境可先在测试机验证。

坑 2：proxy_pass 结尾 / 写错，后端一直 404
结论：接口 404，后端日志里路径多了一截或少了前缀。
原因：proxy_pass 带不带 URI 决定 location 路径是否被替换（详见「工作原理」）。
解法：先明确后端期望的路径：要剥前缀就用带 / 的（proxy_pass http://x:8081/），
      要原样转发就不带 /。正则 location 里 proxy_pass 不能带 URI。

坑 3：server_name 配了但访问还是进 default 站点
结论：明明配了 server_name a.example.com，访问却显示默认站点的内容。
原因：请求的 Host 头与 server_name 不匹配（域名解析到别的 IP、或访问 IP 直连），落到 default_server。
解法：dig 确认域名指向本机；curl -H 'Host: a.example.com' http://IP 直接带 Host 头测试；
      server_name 与访问域名必须完全一致（含 www 与不带 www 是两个名字）。

坑 4：静态文件 403，权限问题
结论：图片/JS 访问 403 Forbidden。
原因：目录或文件权限不足——nginx worker（www-data 用户）对路径没有读/执行权限；
      典型场景：文件放在 /root 下或目录权限 700。
解法：站点目录放 /var/www 等公共路径，目录 755、文件 644、属主可设 www-data；
      用 namei -l 逐层查权限；selinux（RHEL）还需检查 httpd_sys_content_t 标签。

坑 5：HTTPS 配了浏览器还报不安全
结论：证书配了，浏览器仍显示「您的连接不是私密连接」。
原因：证书与域名不匹配（CN/SAN 不含访问域名）、证书过期、自签证书、证书链不完整（缺中间证书）。
解法：openssl s_client 查看 subject/issuer/dates；确保证书 SAN 含域名；生产用 Let's Encrypt；
      证书链不完整时 nginx 配 fullchain.pem 而不是单证书文件。

坑 6：SPA 子路由刷新 404
结论：Vue/React 项目点链接正常，F5 刷新子页面就 404。
原因：history 路由的 URL 是前端伪路径，服务器找不到对应文件，又没有 try_files 回退。
解法：location / { try_files $uri $uri/ /index.html; } 让未知路径回退 index.html。

坑 7：反代 WebSocket 一直连接失败/立即断开
结论：WebSocket 通过 nginx 反代连不上，或连上秒断。
原因：反代默认 HTTP/1.0 + 不转发 Upgrade/Connection 头，WebSocket 握手失败。
解法：proxy_http_version 1.1 + 用 map 转发 Upgrade/Connection 头（见 deepseek-harness 配置），
      长连接类接口同步调大 proxy_read_timeout。

坑 8：gzip 开了但 CSS/JS 没被压缩
结论：curl 看响应头没有 Content-Encoding: gzip，带宽没省下来。
原因：gzip on 只压缩默认的 text/html；gzip_types 未配置时其他类型一律不压缩
      （本机 Ubuntu 默认配置就注释着 gzip_types）。
解法：显式 gzip_types text/plain text/css application/json application/javascript
      application/xml image/svg+xml; + gzip_comp_level 5~6 + gzip_min_length 1k。

坑 9：配了 upstream keepalive 但后端连接还是反复建
结论：后端看到来自 nginx 的连接频繁建立/关闭，keepalive 没生效。
原因：keepalive 需要 proxy_http_version 1.1 + proxy_set_header Connection "" 配合，
      默认 HTTP/1.0 协议下连接用完即关，keepalive 形同虚设。
解法：location 里加 proxy_http_version 1.1; proxy_set_header Connection "";
```
