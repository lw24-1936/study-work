## 概述

firewalld 和 ufw 是「iptables/nftables 的高层封装」——用更简单的概念（区域/服务）管理防火墙，底层还是 iptables/nftables。firewalld 是 Red Hat 系默认（CentOS/RHEL/Fedora），用「区域 zone」管理；ufw 是 Ubuntu 的简化前端，用「放行/拒绝端口」管理。两者都降低了直接用 iptables 的复杂度。

```text
# 实测（本机两者都没用）
$ ufw status
状态：不活动
$ command -v firewall-cmd || echo "firewalld 未安装"
firewalld 未安装
# 本机直接用 iptables/nftables（Docker/tailscale/1Panel 管理），没启用高层封装
```

```text
firewalld vs ufw：
1. firewalld —— Red Hat 系默认，区域 zone + 服务 service 概念
2. ufw —— Ubuntu 简化前端，放行/拒绝端口，命令极简
3. 共同点 —— 都是 iptables/nftables 的封装，底层一样
```

## firewalld 与区域 zone

firewalld 用「区域（zone）」组织规则——每个 zone 是一组规则（如 public、home、internal、dmz），网卡归属某个 zone，就应用该 zone 的规则。默认 zone 是 public（只放行 SSH 等）。用「服务（service）」概念（预定义的端口组合，如 ssh=22、http=80）放行。firewall-cmd 是管理命令，--permanent 持久化 + --reload 生效。

```shell
firewall-cmd --state                     # 状态
firewall-cmd --get-default-zone          # 默认区域
firewall-cmd --list-all                  # 看当前区域规则
firewall-cmd --add-service=http --permanent   # 放行 http 服务
firewall-cmd --add-port=8080/tcp --permanent  # 放行端口
firewall-cmd --reload                    # 重载生效
```

```text
firewalld 概念：
1. 区域 zone —— public/home/internal/dmz，网卡绑定区域
2. 服务 service —— 预定义端口组合（ssh=22、http=80、https=443）
3. --permanent + --reload —— 持久化配置并重载
```

## ufw

ufw（Uncomplicated Firewall）是 Ubuntu 的极简防火墙前端，命令简单到「ufw allow 22」「ufw enable」。默认策略：拒绝入站、放行出站。日常用 `ufw allow 端口/服务` 放行、`ufw status` 查看。适合「只想放行几个端口」的简单场景，复杂规则还是得用 iptables/nftables。

```shell
ufw status                  # 状态（inactive 未启用）
ufw enable                  # 启用（默认拒绝入站）
ufw allow 22                # 放行 SSH
ufw allow 80,443/tcp        # 放行 Web
ufw allow from 192.168.1.0/24   # 放行某网段
ufw delete allow 22         # 删除规则
ufw disable                 # 停用
```

```text
ufw 特点：
1. 极简 —— 命令直白（allow/deny），适合简单场景
2. 默认策略 —— 拒绝入站、放行出站
3. 局限 —— 复杂规则（NAT/端口转发）还得用 iptables
```

## 富规则与直接规则

firewalld 的高级功能：富规则（rich rule）——用更细的条件（源地址 + 端口 + 动作）写规则，比 service/port 更灵活；直接规则（direct rule）——直接透传 iptables 规则，用于 firewalld 表达不了的情况。富规则适合「特定源 IP 访问特定端口」，直接规则是「最后的逃生舱」（firewalld 管不了就直接写 iptables）。

```shell
# 富规则：允许 192.168.1.100 访问 3306 端口
firewall-cmd --add-rich-rule='rule family="ipv4" source address="192.168.1.100" port protocol="tcp" port="3306" accept' --permanent
# 直接规则：透传 iptables
firewall-cmd --direct --add-rule ipv4 filter INPUT 0 -p tcp --dport 8443 -j ACCEPT
```

```text
firewalld 三层规则：
1. service/port —— 简单（放行服务或端口）
2. 富规则 rich rule —— 灵活（源 + 端口 + 动作组合）
3. 直接规则 direct —— 透传 iptables，最后手段
```

## 应用场景实战

### 场景一：CentOS 用 firewalld 放行 Web 和 SSH

```shell
# 1. 启用并放行服务
systemctl enable --now firewalld
firewall-cmd --add-service=ssh --permanent
firewall-cmd --add-service=http --permanent
firewall-cmd --add-service=https --permanent
firewall-cmd --reload
# 2. 验证
firewall-cmd --list-all
```

### 场景二：Ubuntu 用 ufw 放行服务端口

```shell
# 1. 启用（默认拒绝入站）
ufw enable
# 2. 放行 SSH 和 Web
ufw allow 22
ufw allow 80,443/tcp
# 3. 验证
ufw status verbose
```

## 最佳实践与踩坑记录

### 最佳实践

1. 简单场景用 ufw（Ubuntu）/firewalld（CentOS），复杂规则直接 iptables/nftables
2. firewalld 改规则用 --permanent + --reload，否则重启丢失
3. 远程改防火墙先放行 SSH 再启用，否则把自己锁外面
4. 默认区域（public）只放行必要服务，别全放
5. 理解 firewalld/ufw 都是 iptables 封装，底层规则用 iptables -L 能看到

### 踩坑记录

```text
坑 1：firewalld 改规则没 --permanent，重启后丢失
结论：firewall-cmd --add-port 后重启，端口又没了。
原因：没加 --permanent，规则是临时的（运行时）。
解法：加 --permanent 持久化，再 --reload 生效。

坑 2：ufw enable 后 SSH 断了
结论：启用 ufw 后远程 SSH 连不上。
原因：ufw 默认拒绝入站，没先放行 22 端口。
解法：先 ufw allow 22，再 ufw enable。

坑 3：firewalld 和 iptables 手动规则混用冲突
结论：手动 iptables 规则和 firewalld 规则打架。
原因：firewalld 自己管理 iptables，手动改会和它冲突。
解法：统一用 firewalld 管理，别绕过它手动改 iptables。

坑 4：ufw 和 Docker 冲突
结论：启用 ufw 后 Docker 容器网络异常。
原因：ufw 和 Docker 都管 iptables，规则可能互相干扰。
解法：理解 Docker 的 iptables 行为，或用 DOCKER-USER 链自定义。

坑 5：firewalld --reload 把运行时规则清了
结论：--reload 后没加 --permanent 的运行时规则没了。
原因：--reload 重新加载永久规则，运行时临时规则丢失。
解法：所有要保留的规则都加 --permanent。
```
