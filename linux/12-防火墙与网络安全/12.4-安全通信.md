## 概述

安全通信解决传输中的三大问题：**不被窃听（机密性）、不被篡改（完整性）、身份可信（认证）**。Linux 运维中的安全通信主要落在四块：

| 技术 | 解决什么 | 典型场景 |
|---|---|---|
| SSH | 远程登录的加密与认证 | 服务器管理、文件传输（scp/sftp）、隧道 |
| OpenSSL | 加密算法库 + 证书工具链 | 生成密钥/证书、查看/验证 TLS 证书 |
| TLS/HTTPS | 传输层加密与身份验证 | Web 服务、API 网关、邮件、数据库连接 |
| VPN（WireGuard 等） | 公网上建立加密隧道 | 远程办公、跨地域内网互通、云上安全组替代 |

核心思想是「**先认证、再加密**」：SSH 用密钥挑战-应答认证身份后用对称加密传数据；TLS 用 CA 证书验证服务器身份后协商对称密钥；VPN 用双方公钥做身份绑定后加密全部隧道流量。**加固 SSH（密钥认证 + 禁密码 + 禁 root）是服务器安全的第一步**，绝大多数公网服务器被攻破都是因为 SSH 密码爆破成功。

## 核心概念

### 1. SSH（Secure Shell）

- 加密的远程登录协议（端口 22），用「**非对称加密做密钥交换和认证 + 对称加密传数据**」。
- 认证方式：密码（可被爆破）、公钥（挑战-应答，不可爆破）、证书（CA 签发的密钥，企业级）。
- 生态：`ssh` 登录、`scp/sftp` 传文件、`ssh -L/-R/-D` 隧道、`ssh-agent` 管理密钥。
- 配置文件：服务端 `/etc/ssh/sshd_config`、客户端 `~/.ssh/config`、授权密钥 `~/.ssh/authorized_keys`。

### 2. OpenSSL

- 开源加密库（TLS 的参考实现）兼命令行工具：生成密钥/证书/CSR、查看证书、测试 TLS 连接。
- 是 Linux 上加密生态的底座：Nginx/Apache/PostgreSQL/curl 的加密都依赖它（或它的后继 OpenSSL 3.x / LibreSSL / GnuTLS）。
- 证书相关核心动作：`genrsa` 生成私钥、`req` 生成 CSR/自签证书、`x509` 查看证书、`s_client` 测试对端 TLS。

### 3. TLS（Transport Layer Security）

- 传输层安全协议，HTTPS 的加密层，核心三保障：**加密（机密性）、完整性校验（MAC）、证书认证（防中间人）**。
- 演进：SSL 2/3 → TLS 1.0 → 1.1 → 1.2 → 1.3。现在只应使用 **TLS 1.2 / 1.3**（1.0/1.1 已废弃，1.3 于 2018 年发布，握手更快更安全）。
- 证书链：**叶子证书（域名）← 中间 CA ← 根 CA**，客户端信任根 CA 即可信任整条链。
- 免费证书：Let's Encrypt（90 天，certbot 自动续期）。

### 4. VPN

- 在公网上建立加密隧道，让远程设备像在局域网一样安全访问内网资源。
- 三大流派：**WireGuard**（现代极简、内核实现、性能最好）、**OpenVPN**（成熟稳定、基于 TLS、兼容性强）、**IPsec/IKEv2**（协议级、企业站点互联标准）。
- Tailscale/Headscale 是基于 WireGuard 的组网产品：自动 NAT 穿透 + 密钥分发 + 节点发现。

### 5. 加密基础

- **对称加密**：同一把密钥加密解密。快，适合大数据量（AES-128/256、ChaCha20）。问题：密钥怎么安全送达对端。
- **非对称加密**：公钥加密/私钥解密（或私钥签名/公钥验签）。慢，适合小数据量（RSA-2048/4096、ECDSA P-256、Ed25519）。解决密钥分发问题。
- **哈希函数**：单向不可逆，用于完整性校验与指纹（SHA-256、SHA-3；MD5/SHA-1 已不安全）。
- **数字签名**：私钥对内容哈希签名，公钥验签——证明「内容没被改 + 确实出自持私钥者」。
- **证书体系（CA）**：CA 用自己的私钥给「公钥 + 域名 + 有效期」签名，形成 X.509 证书；客户端用 CA 公钥验签，确认公钥确实属于该域名（防中间人伪造）。
- **密钥交换**：DH/ECDHE 在不传输密钥本身的情况下协商出共享密钥；**ECDHE 前向保密**（即使私钥泄露，历史流量也无法解密）。

## 工作原理

### SSH 握手与认证流程

```text
阶段一：TCP 连接（:22）
阶段二：版本协商（SSH-2.0-OpenSSH_9.6 等）
阶段三：密钥交换（KEX）—— 协商算法 + ECDHE 生成会话密钥（对称加密密钥）
阶段四：服务器身份验证 —— 客户端核对服务器主机公钥（known_hosts 指纹）
阶段五：用户认证 —— 密码 / 公钥挑战-应答：
        客户端：发送公钥标识
        服务器：用 authorized_keys 里的公钥加密一个随机挑战
        客户端：私钥解密并回传结果 → 验证通过
阶段六：建立加密通道，开始传输
```

公钥认证为什么安全：**私钥永远不离开客户端**，服务器只持有公钥；挑战-应答过程中即使流量被截获也无法重放（挑战是随机的）。密码认证的私密信息直接暴露在可爆破面里，所以生产环境必须禁用。

### TLS 握手流程（TLS 1.2 vs 1.3）

```text
TLS 1.2（两次往返，RTT×2）：
1. ClientHello —— 客户端发支持的协议版本、密码套件、随机数
2. ServerHello —— 服务器选版本/套件，发随机数
3. Certificate —— 服务器发证书链（叶子 + 中间 CA）
4. ServerKeyExchange —— ECDHE 公钥参数（前向保密）
5. ServerHelloDone
6. ClientKeyExchange —— 客户端发自己的 ECDHE 公钥参数
7. 双方各自计算预主密钥 → 主密钥 → 会话密钥（对称）
8. ChangeCipherSpec + Finished（双方确认切换加密）
→ 之后所有数据用会话密钥对称加密

TLS 1.3（一次往返，RTT×1）：
1. ClientHello —— 直接带上客户端支持的 ECDHE 公钥参数
2. ServerHello —— 服务器选参数并直接发自己的 ECDHE 公钥 + 证书 + Finished
3. 客户端立即算出会话密钥，发 Finished
→ 更少的往返、删除了 RSA 密钥交换和弱套件、强制前向保密
```

关键点：**证书验证发生在握手阶段**——客户端用系统 CA 信任库（/etc/ssl/certs/）逐级验证证书链，验证域名（SAN）、有效期、签名；验证失败则握手终止（浏览器显示「不安全」，curl/openssl 报 verify error）。TLS 1.3 只保留 ECDHE 类密钥交换，彻底杜绝 RSA 密钥交换（无前向保密）和降级攻击。

### WireGuard 原理

- 基于 **Noise 协议框架**（curve25519 密钥交换 + ChaCha20-Poly1305 加密），内核态实现（Linux 5.6+ 合入内核），配置极简：每个节点一对密钥，加上 `AllowedIPs` 路由声明即完成组网。
- 数据面：所有 UDP 包（默认 51820 端口）用对端公钥加密；**加密身份 = 公钥**，无需证书体系。
- 控制面极薄：无连接状态机、无握手重协商，靠「加密的 keepalive + 重放窗口」维持隧道。
- `AllowedIPs` 语义：**告诉本机「去往哪些目标 IP 的流量走这条隧道」**，同时作为对端来源地址过滤（对端只能用它声明的地址段发数据）——这是 WireGuard 同时充当「路由表 + 访问控制」的巧妙设计。

### Tailscale 与 WireGuard 的关系

Tailscale 是「WireGuard + 控制平面」的组网产品：控制平面（登录认证、密钥分发、节点发现、ACL 策略）在 Tailscale 服务端，数据平面仍是标准的 WireGuard 隧道。它解决的难题是 **NAT 穿透**：两个都在 NAT 后面的设备无法直接建立 WireGuard 隧道时，通过 STUN 类探测 + DERP 中继（加密中继，数据仍端到端加密）兜底。本机实测有 tailscale0 网卡（见常用命令与配置），说明正是这种组网形态。

### 攻击模型与防御

```text
中间人攻击（MITM）：攻击者插入客户端与服务器之间，伪造双方身份。
  防御：TLS 证书链验证（CA 签名的证书无法伪造）、SSH known_hosts 指纹核对
       （首次连接时核对服务器指纹）、VPN 公钥锁定（配置里写死对端公钥）。

重放攻击：截获合法数据包后原样重发，让服务器重复执行操作。
  防御：TLS 1.3 的随机 nonce + 序列号、WireGuard 的滑动重放窗口、
       SSH 挑战随机数（每次挑战不同）、时间戳 + nonce 机制。

爆破攻击：对密码/密钥不断尝试。
  防御：禁用密码登录、ufw limit / fail2ban、MaxAuthTries 限制、密钥认证。

降级攻击：迫使客户端用弱协议/弱算法。
  防御：服务端配置只允许 TLS 1.2+、禁用旧套件（ssl_protocols 配置）。
```

## 常用命令与配置

### SSH 密钥管理

```shell
# 生成密钥对（推荐 ed25519，比 RSA 更快更短更安全）
ssh-keygen -t ed25519 -C "user@host-2026" -f ~/.ssh/id_ed25519
# 传统 RSA（兼容老设备/老系统时才用；2048 起步，4096 更稳）
ssh-keygen -t rsa -b 4096 -C "user@host" -f ~/.ssh/id_rsa
# 查看公钥指纹（核对服务器身份用）
ssh-keygen -lf ~/.ssh/id_ed25519.pub
# 查看私钥指纹
ssh-keygen -lf ~/.ssh/id_ed25519
# 修改私钥口令
ssh-keygen -p -f ~/.ssh/id_ed25519

# 把公钥安装到服务器（自动追加到 authorized_keys 并设置权限）
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server
# 手动安装
cat ~/.ssh/id_ed25519.pub | ssh user@server "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

# 密钥代理（免输入口令 + 多密钥管理）
eval "$(ssh-agent -s)"      # 启动代理
ssh-add ~/.ssh/id_ed25519   # 把私钥加入代理（输入一次口令）
ssh-add -l                  # 列出代理中的密钥
ssh -A user@server          # 转发代理（跳板机链式登录用；慎用）

# 测试连接（verbose 级别）
ssh -v user@server
ssh -vvv user@server        # 最详细，排障用

# 主机指纹核对（首次连接出现指纹提示时）
ssh-keyscan server.example.com   # 获取服务器主机公钥
ssh-keygen -lf <(ssh-keyscan server.example.com 2>/dev/null)
```

### OpenSSL 命令体系

```shell
# ---- 密钥 ----
openssl genrsa -out key.pem 2048                 # RSA 私钥（传统格式）
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out key.pem   # 新式
openssl genpkey -algorithm ED25519 -out key.pem  # Ed25519 私钥
openssl ecparam -genkey -name prime256v1 -out key.pem   # ECDSA P-256

# ---- 证书请求与自签 ----
openssl req -new -key key.pem -out req.csr -subj "/C=CN/ST=Beijing/L=Beijing/O=MyOrg/CN=example.com"
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes -subj "/CN=localhost"   # 自签（-nodes 表示私钥不加密）
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes -subj "/CN=example.com" -addext "subjectAltName=DNS:example.com,DNS:www.example.com,IP:192.168.1.10"  # 带 SAN（浏览器必需！）

# ---- 查看证书 ----
openssl x509 -in cert.pem -noout -text            # 完整信息
openssl x509 -in cert.pem -noout -subject -issuer -dates -serial -fingerprint -sha256
openssl x509 -in cert.pem -noout -ext subjectAltName   # 看 SAN（域名是否匹配）

# ---- 测试 TLS 连接 ----
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -dates -subject
echo | openssl s_client -connect example.com:443 -servername example.com -showcerts   # 看完整证书链
echo | openssl s_client -connect example.com:443 -tls1_3 -brief                     # 只看握手摘要
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | grep -E 'Protocol|Cipher|Verify'

# ---- 格式转换 ----
openssl pkcs12 -export -in cert.pem -inkey key.pem -out bundle.p12    # PEM → PFX（Windows/IIS）
openssl pkcs12 -in bundle.p12 -nodes -out combined.pem                # PFX → PEM
openssl x509 -in cert.pem -outform der -out cert.der                  # PEM → DER
```

## 配置文件解析

### /etc/ssh/sshd_config（服务端核心）

| 配置项 | 推荐值 | 作用 |
|---|---|---|
| `Port` | 22（或改高位端口） | 监听端口，改端口减少扫描噪音（不是安全手段） |
| `PermitRootLogin` | **no** | 禁止 root 直接登录（用普通用户 + sudo，见 [[05.4-提权与 sudo]]） |
| `PasswordAuthentication` | **no** | 禁用密码登录，只留密钥（防爆破核心） |
| `PubkeyAuthentication` | yes | 开启公钥认证（默认开） |
| `MaxAuthTries` | 3 | 单连接最大认证尝试次数 |
| `MaxSessions` | 10 | 单连接最大会话数 |
| `AllowUsers alice bob` | 按需 | 白名单用户（黑名单用 DenyUsers） |
| `AllowGroups` | 按需 | 白名单组 |
| `ClientAliveInterval` | 300 | 服务端保活探测间隔（防空闲断开） |
| `ClientAliveCountMax` | 2 | 未响应多少次后断开 |
| `LoginGraceTime` | 60 | 认证超时（防慢速爆破占连接） |
| `Protocol` | 2 | 只允许 SSHv2 |
| `KbdInteractiveAuthentication` | no | 关闭键盘交互认证（含密码类） |
| `PermitEmptyPasswords` | no | 禁空密码（默认禁） |
| `UseDNS` | no | 不反查 DNS（加快连接速度） |
| `X11Forwarding` | no | 生产环境关闭 |
| `AllowTcpForwarding` | 按需 | 需要隧道时保持 yes，否则 no |
| `LogLevel` | VERBOSE | 详细日志（配合审计，见 [[23.3-安全审计]]） |

### 实测（本机）——当前 sshd 配置存在安全隐患

```text
$ grep -iE '^(port|permitrootlogin|passwordauthentication|maxauthtries|pubkeyauthentication)' /etc/ssh/sshd_config
PermitRootLogin yes              # 安全隐患：允许 root 直接登录
PasswordAuthentication yes       # 安全隐患：允许密码登录（可被爆破）

$ sshd -T | grep -E '^(port|permitrootlogin|passwordauthentication)'
port 22
permitrootlogin yes
passwordauthentication yes
```

本机 sshd 是「出厂默认」状态，`PermitRootLogin yes` + `PasswordAuthentication yes` 属于公网服务器高危配置，按场景一加固。注意 `sshd -T` 输出的是**生效配置**（合并了 Include 文件和默认值），比直接看文件更可信。

### ~/.ssh/authorized_keys 与权限要求

```text
权限要求（权限过宽 SSH 直接拒绝使用）：
  ~/.ssh/          目录  700（drwx------）
  authorized_keys  文件  600（-rw-------）
  私钥 ~/.ssh/id_*       600
  公钥 ~/.ssh/*.pub      644（可公开）

authorized_keys 每行一个公钥，可带 options 前缀：
  no-port-forwarding,no-agent-forwarding,no-X11-forwarding,command="/usr/bin/backup" ssh-ed25519 AAAAC3... user@host
  from="192.168.1.0/24" ssh-ed25519 AAAAC3... user@host     # 限制来源
  restrict ssh-ed25519 AAAAC3... user@host                  # 一键禁用所有转发
```

### 场景二：SSH 隧道三种模式与加密数据库连接

```text
模式一：本地转发 -L（访问远端内网服务）

  ssh -R 8080:localhost:3000 -N user@server   # 服务器 8080 → 本机 3000
```

### 场景四：WireGuard 快速上手（服务器-客户端组网）

```shell
# 服务器（10.0.0.1，公网 1.2.3.4）
wg genkey | tee /etc/wireguard/server.key | wg pubkey > /etc/wireguard/server.pub
cat > /etc/wireguard/wg0.conf <<'EOF'
[Interface]
Address = 10.9.0.1/24
PrivateKey = <server.key 内容>
ListenPort = 51820
PostUp = iptables -A FORWARD -i wg0 -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

[Peer]
PublicKey = <client.pub 内容>
AllowedIPs = 10.9.0.2/32
EOF
chmod 600 /etc/wireguard/*.key
wg-quick up wg0 && systemctl enable wg-quick@wg0

# 客户端（笔记本）
wg genkey | tee client.key | wg pubkey > client.pub
cat > /etc/wireguard/wg0.conf <<'EOF'
[Interface]
Address = 10.9.0.2/24
PrivateKey = <client.key 内容>

[Peer]
PublicKey = <server.pub 内容>
Endpoint = 1.2.3.4:51820
AllowedIPs = 10.9.0.0/24, 192.168.0.0/16   # 隧道内网 + 远端内网段都走隧道
PersistentKeepalive = 25                   # NAT 后面保活，维持隧道
EOF
wg-quick up wg0

# 验证
wg show                      # 两端都能看到对端，handshake 时间在更新
ping 10.9.0.1                # 隧道通
```

要点：`AllowedIPs = 0.0.0.0/0` 表示全流量走隧道（全局代理模式）；只写内网段则是「分流模式」。服务器注意防火墙放行 UDP 51820（ufw allow 51820/udp 或 firewalld --add-port=51820/udp，见 [[12.3-firewalld-ufw]]）。

## 性能与调优

### 加密算法强度对比表

| 算法 | 类型 | 密钥长度 | 等效安全强度 | 状态 | 用途 |
|---|---|---|---|---|---|
| AES-256-GCM | 对称 | 256 bit | 256 bit | ✅ 推荐 | TLS 数据加密、磁盘加密 |
| ChaCha20-Poly1305 | 对称 | 256 bit | 256 bit | ✅ 推荐 | 移动端/无 AES 硬件加速场景（WireGuard 默认） |
| RSA | 非对称 | 2048/4096 bit | 112/128 bit | ⚠️ 逐步弃用 | 旧系统兼容；签名仅限 3072+ |
| ECDSA (P-256) | 非对称 | 256 bit | 128 bit | ✅ 推荐 | TLS 证书签名 |
| Ed25519 | 非对称 | 256 bit | 128 bit | ✅ 推荐 | SSH 密钥、签名（快、短、恒定时间） |
| SHA-256 | 哈希 | — | 128 bit | ✅ 推荐 | 完整性、指纹 |
| MD5/SHA-1 | 哈希 | — | 已破解 | ❌ 禁用 | 仅指纹显示用 |
| DH/ECDHE | 密钥交换 | 2048+/P-256 | 前向保密 | ✅ ECDHE 推荐 | TLS 握手密钥协商 |

要点：**混合体系**——握手用非对称（ECDHE 交换密钥 + ECDSA 签名验证身份），数据传输用对称（AES-GCM），哈希保完整性。ed25519 密钥 256 bit 长度、64 字符公钥，比 RSA 2048 短得多且签名/验证快数倍，SSH 新密钥一律 ed25519。

```text
1. SSH 连接复用 —— ControlMaster/ControlPersist 复用 TCP 连接，省掉重复握手
   （频繁 scp/ssh 的脚本场景提速明显）。
2. TLS 会话复用 —— ssl_session_cache shared:SSL:10m + session tickets，
   TLS 1.3 0-RTT（early data）进一步减少握手往返（有重放风险，需评估）。
3. 证书链裁剪 —— 服务器只发「叶子 + 中间 CA」，不要带根 CA（浏览器本地有），
   减少握手字节；用 Let's Encrypt 的 fullchain.pem 即可。
4. OCSP Stapling —— 服务器代客户端查证书吊销状态并缓存在握手里，
   省去客户端单独请求 OCSP 的延迟（Nginx ssl_stapling on）。
5. WireGuard 性能 —— 内核态实现 + ChaCha20 原生指令，吞吐远超用户态 OpenVPN；
   隧道 MTU 1280（实测 tailscale0），避免 IP 分片。
6. 算法选择 —— Nginx ssl_ciphers 优先 ECDHE+AES-GCM；ssh 用 ed25519 + aes256-gcm；
   不要为了兼容老客户端留一整套弱套件。
7. 硬件加速 —— 现代 CPU 的 AES-NI 指令让 AES-GCM 基本免费；禁用 AES 反而更慢。
```

## 安全与权限

```text
1. SSH 密钥权限铁律 —— 私钥 600、~/.ssh 700、authorized_keys 600；
   权限过宽 SSH 直接拒绝使用该密钥（StrictModes 默认开启）。
2. 私钥即身份 —— 私钥泄露 = 身份被冒充；生成带口令的密钥（ssh-keygen -p），
   配合 ssh-agent 免重复输入；服务器上不要存放私钥副本（跳板机除外且需审计）。
3. 禁用弱算法 —— sshd_config：KexAlgorithms/HostKeyAlgorithms 去掉 ssh-rsa；
   TLS：只留 TLSv1.2 TLSv1.3；密码套件只要 ECDHE + GCM。
4. 防爆破组合拳 —— 禁密码登录（根本）、ufw limit 22/tcp、fail2ban、
   MaxAuthTries 3、LoginGraceTime 60。
5. 证书私钥保护 —— /etc/letsencrypt/live/ 默认 700，证书私钥 600；
   私钥泄露要立即吊销（CA 吊销/重新签发）。
6. 隧道收敛暴露面 —— 数据库/Redis 等服务只监听 127.0.0.1 或内网 IP，
   需要远程访问时走 SSH 隧道/WireGuard，而不是直接暴露公网。
7. 中间人防御 —— TLS 验证证书链与域名（SAN）、SSH 首次连接核对指纹
   （known_hosts 被污染要清）、WireGuard 配置写死对端公钥。
8. 重放防御 —— TLS 1.3 强制 ECDHE + 随机 nonce；WireGuard 重放窗口；
   密钥定期轮换（SSH 一年一换、WireGuard 按策略换、Let's Encrypt 90 天自动换）。
9. 双因素 —— 生产环境建议 sshd 加 TOTP（Google Authenticator + PAM，
   见 [[05.5-PAM 可插拔认证]]），密码/密钥 + 动态码双因子。
10. 最小权限 —— AllowUsers 白名单 + 普通用户 + sudo（[[05.4-提权与 sudo]]），
    root 禁止直接登录；sudo 操作留审计日志（[[23.3-安全审计]]）。
```

## 故障排查

### 案例一：SSH 连不上（认证失败/超时/被拒）

```shell
# 1. 先分清「连不上」的类型：TCP 不通 / 认证失败 / 被防火墙拒
ssh -vvv user@server 2>&1 | tail -20      # verbose 看卡在哪一步
nc -vz server 22                          # 端口通不通
# 2. 服务端看监听与日志
ss -tlnp | grep :22
tail -50 /var/log/auth.log | grep -E 'sshd|Failed|Accepted'   # Ubuntu
journalctl -u sshd -n 50 --no-pager                            # systemd 通用
# 常见报错解读：
#   "Permission denied (publickey)" —— 密钥没配对/权限不对（检查 authorized_keys 与 600/700）
#   "Connection refused" —— sshd 没起来或端口不对
#   "Connection timed out" —— 防火墙/安全组拦了
#   "REMOTE HOST IDENTIFICATION HAS CHANGED" —— known_hosts 指纹变化（服务器重装过），
#     确认非劫持后 ssh-keygen -R server 清除旧指纹
# 3. 配置改动后先测语法再重载
sudo sshd -t && sudo systemctl reload sshd
```

### 案例二：TLS 证书报错三连（自签名/过期/域名不匹配）

```shell
# 现象 1：浏览器报「您的连接不是私密连接 / NET::ERR_CERT_AUTHORITY_INVALID」
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | grep -E 'Verify return code|subject|issuer'
# → "self-signed certificate" / "unable to get local issuer certificate"
#   原因：证书没被信任的 CA 签发 → 换 Let's Encrypt/正规 CA，或导入自建 CA 到信任库

# 现象 2：报证书过期（NET::ERR_CERT_DATE_INVALID）
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -dates
# → notAfter 已过 → 续期：certbot renew --force-renewal，或手动换证

# 现象 3：报域名不匹配（NET::ERR_CERT_COMMON_NAME_INVALID）
openssl x509 -in <(echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null) -noout -ext subjectAltName
# → 证书 SAN 里没有 example.com → 重新签发带正确 SAN 的证书
#   （2020 年后浏览器只看 SAN，不再看 CN）

# 通用检查：证书链是否完整（只发叶子没发中间 CA 也会报错）
echo | openssl s_client -connect example.com:443 -showcerts 2>/dev/null | grep -c 'BEGIN CERTIFICATE'
# ≥2 说明发了叶子+中间 CA；=1 则链不完整，Nginx 需改用 fullchain.pem
```

### 案例三：WireGuard 隧道建不起来

```shell
# 1. 接口状态与握手时间
wg show wg0          # latest handshake 一直为空 → 握手失败
# 2. UDP 端口通不通（WireGuard 是 UDP 51820）
nc -vuz 1.2.3.4 51820
# 3. 防火墙放行（常见坑：只开了 TCP）
#    ufw allow 51820/udp；firewall-cmd --add-port=51820/udp --permanent && --reload
# 4. 密钥是否配对（最常见错误：PrivateKey/PublicKey 不匹配）
wg pubkey < client.key    # 应与服务器 wg show 里 Peer 的 PublicKey 一致
# 5. NAT 后面 PersistentKeepalive —— 没有 keepalive 时 NAT 映射会过期，
#    隧道 5 分钟没流量就断；客户端加 PersistentKeepalive = 25
# 6. 路由问题：AllowedIPs 写错 → 包没进隧道
ip route | grep wg0
# 7. 服务器 IP 转发没开（做网关时）
sysctl net.ipv4.ip_forward   # 应为 1；PostUp 的 MASQUERADE 也要生效
```

## 常见问题

```text
Q1: 为什么生产环境必须禁用密码登录，只留密钥？
A: 密码是可爆破的（字典/暴力，全球扫描器 7×24 在扫 22 端口）；密钥认证是
   非对称挑战-应答，私钥不离开客户端、每次挑战随机，无法离线爆破，且密钥熵
   远超密码。禁用密码 = 掐断 99% 的自动爆破攻击。

Q2: 自签证书为什么浏览器报「不安全」？生产能用吗？
A: 自签证书没有受信任 CA 的签名，浏览器不认可其身份（无法证明公钥属于该
   域名）。生产必须用 Let's Encrypt（免费 90 天自动续）或商业 CA；
   自签只用于内网测试/开发环境，且要手动把自签 CA 导入客户端信任库。

Q3: TLS 1.0/1.1 为什么必须禁用？
A: 有已知漏洞（POODLE 填充攻击、BEAST、Lucky13 等），且不支持现代密码套件，
   已被 RFC 8996 废弃。现在只留 TLS 1.2/1.3（Nginx ssl_protocols TLSv1.2 TLSv1.3）。

Q4: WireGuard 和 OpenVPN 怎么选？
A: WireGuard：现代、内核态、配置极简、性能最好，适合新项目/云环境；
   OpenVPN：成熟、兼容老系统、基于 TLS、可审计性好，适合企业合规场景；
   IPsec：协议标准、设备（防火墙/VPN 网关）互操作，适合站点互联。
   新部署无历史包袱 → 优先 WireGuard（或 Tailscale 免运维）。

Q5: SSH 端口转发（隧道）和 VPN 有什么区别？
A: SSH 隧道是「应用级转发」：只转发指定端口/协议的流量，走 22 端口，
   无需服务端额外装软件；VPN 是「网络层隧道」：整个网段的路由流量都进隧道，
   全局透明。管理单服务用 SSH 隧道，连整个内网用 WireGuard。

Q6: 怎么确认一个 HTTPS 站点真的用了 TLS 1.3 和强加密？
A: echo | openssl s_client -connect 域名:443 -servername 域名 -tls1_3 2>/dev/null |
   grep -E 'New|Protocol|Cipher'；或 -brief 看摘要；Nginx 侧 curl -vI https://... 看
   ssl_protocol/ssl_cipher 行；在线可用 ssllabs.com 评分。

Q7: 服务器重装后 SSH 报 host key 变化怎么办？
A: 这是 known_hosts 里旧指纹与新主机公钥不匹配（重装/重签了主机密钥）。
   确认服务器确实重装/重建（排除 DNS 劫持/中间人），然后
   ssh-keygen -R <server> 清除旧指纹，下次连接重新确认新指纹。

Q8: 私钥泄露了怎么办？
A: 立即：从 authorized_keys 删除对应公钥、停用该密钥（所有服务器）；
   若私钥带口令，泄露的是密文文件，还有时间换新密钥；同时排查有没有
   被登录过（auth.log）；生成新密钥对并全网替换；审计日志（[[23.3-安全审计]]）。
```

## 面试题

```text
1. SSH 密钥认证为什么比密码安全？具体流程是什么？
   答：密码可被在线爆破且传输中可能被截获；密钥认证是「非对称挑战-应答」：
   客户端声明公钥 → 服务器用公钥加密随机挑战 → 客户端私钥解密回传 →
   验证通过。私钥不出客户端、挑战每次随机，无法爆破无法重放，密钥熵也远大于
   密码。流程前提：密钥交换（ECDHE）先建立加密通道，认证在加密通道内进行。

2. TLS 握手做了什么？TLS 1.3 相比 1.2 改进了什么？
   答：握手 = 协商参数 + 验证身份 + 协商会话密钥：ClientHello/ServerHello
   协商版本与套件 → 服务器发证书链 → 客户端用 CA 信任库验证证书与域名 →
   ECDHE 交换公钥参数计算会话密钥 → Finished 确认。TLS 1.3：握手从 2 RTT 降到
   1 RTT（0-RTT 可选）、删除 RSA 密钥交换（强制前向保密）、删除弱套件和
   老版本协商、简化密码套件（AEAD 为主）。

3. 证书是什么？为什么需要 CA？证书链是怎么验证的？
   答：X.509 证书 = 「公钥 + 主体身份（域名）+ 有效期 + CA 签名」的绑定，
   证明该公钥确实属于该域名。CA 是可信第三方，其根证书预装在客户端
   （/etc/ssl/certs）。验证链：叶子证书 ← 中间 CA 证书 ← 根证书，逐级用上级
   公钥验签，最终根证书在本地信任库中 → 整条链可信。任一环签名失败、
   过期、域名（SAN）不匹配都判失败。没有 CA 就无法防止中间人伪造「假公钥」。

4. HTTPS 用的是对称加密还是非对称加密？为什么混合？
   答：两者都用。握手阶段用非对称（证书签名验证身份 + ECDHE 协商密钥），
   数据阶段用对称（AES-GCM 等）。原因：非对称安全但慢（RSA 2048 签名数百微秒
   级），对称快（AES-NI 硬件加速）但不解决密钥分发；混合 = 非对称安全地协商
   出对称密钥，对称高效地加密大数据量。ECDHE 保证前向保密：即使长期私钥泄露，
   历史会话密钥也无法恢复。

5. 什么是中间人攻击？SSH/TLS/WireGuard 分别怎么防御？
   答：中间人插入客户端与服务器之间，冒充双方窃听/篡改。防御本质是「验证
   对端身份」：TLS 靠 CA 签名的证书链 + 域名验证；SSH 靠首次连接指纹核对
   （known_hosts）+ 后续指纹一致性；WireGuard 靠配置中写死的对端公钥
   （密码学身份绑定）。三者共同点：把「对端身份」锚定在不可伪造的密码学材料上。

6. WireGuard 的 AllowedIPs 是什么意思？隧道路由怎么工作？
   答：双向语义：① 路由——告诉本机「去往这些网段的数据包走这条隧道」；
   ② 过滤——隧道只接受对端以这些地址为源的数据包。0.0.0.0/0 表示全流量走
   隧道（全局代理），写具体内网段是分流。工作方式：wg 接口收到目标 IP 匹配
   AllowedIPs 的包 → 按对端公钥加密封装成 UDP 发往 Endpoint → 对端解密后
   按内部路由交付。

7. SSH 隧道三种转发模式各是什么？适用什么场景？
   答：本地转发 -L local:remote:port（访问远端内网服务，如加密连数据库）；
   远程转发 -R remote:local:port（把本机服务暴露给远端，如内网调试）；
   动态转发 -D port（本机起 SOCKS5 代理，浏览器/工具走代理访问远端可达网络）。
   三者数据都封装在 SSH 加密通道内，相当于「应用级 VPN」。

8. 如何设计一个安全的远程服务器登录方案（综合题）？
   答：① 密钥认证 ed25519 + 禁密码 + 禁 root（普通用户 + sudo）；
   ② AllowUsers 白名单 + MaxAuthTries 3 + fail2ban/ufw limit 防爆破；
   ③ 双因素（TOTP）可选加强；④ 跳板机/堡垒机集中入口 + 审计日志；
   ⑤ 密钥权限 600/700、私钥加密存放、定期轮换；⑥ 防火墙只放行管理网段/
   WireGuard 网段访问 22；⑦ 登录日志告警（auth.log/journald 监控）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. SSH 加固清单（新服务器上机第一步）：密钥认证 → 禁密码 → 禁 root → AllowUsers 白名单 → fail2ban/ufw limit → 定期轮换密钥。
2. 改 sshd_config 永远 `sshd -t` 语法检查 + `systemctl reload`（不中断现有会话），改完另开窗口验证再关旧会话。
3. 密钥一律 ed25519，带口令 + ssh-agent；私钥只放客户端，服务器只存公钥。
4. TLS 只留 1.2/1.3，证书用 Let's Encrypt + certbot 自动续期；证书私钥 600、fullchain.pem 保证链完整。
5. 数据库/Redis 等内部服务监听 127.0.0.1 或内网，远程访问走 SSH 隧道/WireGuard，公网零暴露。
6. 远程访问方案优先 WireGuard/Tailscale（网络层、全局透明、性能好）；单服务临时访问用 SSH 隧道。
7. 证书/密钥变更走变更流程：先备份、先验证（openssl 检查）、再切换、留回滚手段。
8. 首次连接 SSH 核对指纹（ssh-keyscan 对比）；known_hosts 变化先确认再清除（防中间人）。

### 踩坑记录

```text
坑 1：先关密码登录再配密钥，把自己锁在门外
结论：执行 PasswordAuthentication no 后，SSH 再也连不上。
原因：密钥还没装好（或没测试过），唯一的密码认证被禁用，无认证方式可用。
解法：控制台/救援模式恢复 PasswordAuthentication yes，先 ssh-copy-id 配好密钥、
     新窗口验证能登录，再关密码登录（场景一的顺序不可颠倒）。

坑 2：PermitRootLogin no 之后发现没有可用的普通用户
结论：禁了 root 登录，普通用户没建或没 sudo，直接进不去系统。
原因：只做了「禁」，没做「建用户 + 授权」配套动作。
解法：先 useradd + usermod -aG sudo + 配好密钥，再禁 root；
     已翻车则用控制台单用户/救援模式恢复。

坑 3：自签证书上生产，客户端/监控全报警
结论：HTTPS 部署了自签证书，浏览器报「不安全」，监控平台握手失败。
原因：自签证书没有受信任 CA 签名，且常常没有 SAN 扩展（浏览器 2020 年后
     只认 SAN）。
解法：生产用 certbot 签 Let's Encrypt；测试自签必须带 -addext subjectAltName
     （场景三），并导入自建 CA 到信任库。

坑 4：TLS 版本太老被安全扫描报漏洞
结论：扫描器报 POODLE/BEAST/TLS1.0 漏洞。
原因：Nginx 还开着 TLS 1.0/1.1（默认配置或老配置遗留）。
解法：ssl_protocols TLSv1.2 TLSv1.3；ssl_ciphers 只留 ECDHE+GCM 套件；
     改完 nginx -t && systemctl reload nginx，再扫描复测。

坑 5：SSH 改了配置没重载/重启，不生效
结论：改了 sshd_config，客户端行为没变化（还是能密码登录）。
原因：sshd 不会热读配置文件，需要 reload/restart。
解法：sshd -t && systemctl reload sshd；注意 restart 会断开现有连接，
     reload 不会——运维习惯用 reload。

坑 6：Nginx 配了证书但 HTTPS 打不开（链不完整/权限不对）
结论：访问 443 报 SSL 握手错误，日志 ssl_error。
原因：① ssl_certificate 用了 cert.pem 而非 fullchain.pem（缺中间 CA）；
     ② 证书私钥权限过宽或路径错误（Nginx worker 读不了）。
解法：用 fullchain.pem；chmod 600 私钥；nginx -t 先验证配置；
     openssl s_client -showcerts 检查链完整性（案例二）。

坑 7：SSH 隧道 -N -f 后台运行，过一阵就断
结论：ssh -L ... -N -f 建的隧道几小时后失效，scp/数据库连不上。
原因：NAT/防火墙空闲超时掐断了空闲 TCP；客户端没有保活。
解法：加 -o ServerAliveInterval=60 -o ServerAliveCountMax=3（或配置
     ClientAliveInterval）；用 autossh 自动重连。

坑 8：WireGuard 服务器配好了，客户端一直连不上（handshake 超时）
结论：wg show 里 latest handshake 永远是空。
原因：最常见是防火墙只放行了 TCP、没放 UDP 51820（WireGuard 是 UDP）；
     其次是 NAT 后的客户端没配 PersistentKeepalive。
解法：ufw allow 51820/udp（[[12.3-firewalld-ufw]]）；客户端加
     PersistentKeepalive = 25；nc -vuz 验证 UDP 通。

坑 9：tailscale/wireguard 全流量模式后本机失联
结论：AllowedIPs = 0.0.0.0/0 或 tailscale exit node 开全局代理，SSH 断开。
原因：全流量进了隧道，而隧道对端没把流量转发回来（或出口节点策略）。
解法：控制台进入后 wg-quick down / tailscale down；改成分流模式
     （AllowedIPs 只写内网段）；exit node 场景先确认路由与 ACL。

坑 10：服务器重装后 SSH 报 host key 变化，误以为是攻击一顿排查
结论：known_hosts 报 REMOTE HOST IDENTIFICATION HAS CHANGED。
原因：服务器重装/重建，主机密钥（/etc/ssh/ssh_host_*）重新生成。
解法：确认服务器确实是重建的（对比 IP/续期记录），ssh-keygen -R 清旧指纹，
     重新连接核对新指纹；若没重建过，按中间人攻击处理（立即断连排查）。
```
