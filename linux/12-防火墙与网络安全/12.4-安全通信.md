## 概述

安全通信确保数据在传输中「不被窃听、不被篡改、身份可信」：SSH（远程登录加密）、OpenSSL（加解密工具 + 证书）、TLS（传输层加密，HTTPS 基础）、VPN（加密隧道，跨网络安全通信）。核心是「加密 + 认证」：SSH 用密钥认证代替密码、TLS 用证书验证身份、VPN 用隧道加密流量。加固 SSH（关闭密码登录、禁 root 登录）是服务器安全的第一步。

```text
安全通信四块：
1. SSH 加固 —— 密钥认证、禁 root 登录、防爆破
2. OpenSSL —— 加解密工具、证书生成与查看
3. TLS —— HTTPS 的加密层、证书验证
4. VPN —— WireGuard/OpenVPN/IPsec，加密隧道
```

## 核心概念

1. **SSH**：加密的远程登录协议，用「非对称加密协商 + 对称加密传输」，密钥认证代替密码登录（更安全，密码可被爆破）。
2. **OpenSSL**：加解密工具和证书库——生成密钥、证书、签名请求，查看证书信息。证书是「身份证明」，由 CA 签发。
3. **TLS**：传输层安全协议，HTTPS 的加密层，核心三保障——加密（不可窃听）、完整性（不可篡改）、认证（证书验证身份）。
4. **VPN**：在公网上建立加密隧道，让远程设备安全访问内网。主流 WireGuard（现代极简）、OpenVPN（成熟）、IPsec（企业标准）。

```text
三种 VPN 对比：
1. WireGuard —— 现代极简、性能好、内核集成，配置简单
2. OpenVPN —— 成熟稳定、兼容性好、基于 SSL/TLS
3. IPsec —— 老牌、协议级、企业站点互联标准
```

## 工作原理

安全通信的本质是「先认证、再加密」两步：

1. **SSH 认证流程**：客户端发公钥 → 服务器用 authorized_keys 里的公钥验证 → 挑战-应答（用私钥签名，服务器用公钥验签）→ 通过后建立加密通道。密码登录则是「密码验证 + 密钥交换」，密码可被暴力破解，所以生产要禁用。
2. **TLS 握手**：客户端和服务端握手协商加密参数 → 服务器出示证书 → 客户端用 CA 验证证书（确认「这个域名/服务器的公钥可信」）→ 建立对称加密通道。证书验证防「中间人攻击」。
3. **VPN 隧道**：把内网数据包封装进加密的外层包，在公网上传输，对端解密还原。WireGuard 用密钥对做身份 + 加密，配置极简。

```text
安全通信的两步：
认证（确认对方身份）→ 加密（保护数据不被窃听/篡改）
SSH：密钥挑战-应答认证 + 加密通道
TLS：CA 证书验证身份 + 对称加密传输
```

## 常用命令与配置

SSH 密钥管理：

```shell
# 生成密钥对
ssh-keygen -t ed25519 -C "user@host"
# 把公钥拷到服务器（免密登录）
ssh-copy-id user@server
# 测试连接
ssh user@server
```

OpenSSL 操作：

```shell
openssl genrsa -out key.pem 2048            # 生成私钥
openssl req -new -key key.pem -out req.csr  # 生成证书请求
openssl x509 -in cert.pem -noout -text      # 查看证书
openssl s_client -connect example.com:443   # 测试 TLS 连接
openssl s_client -connect example.com:443 -servername example.com | openssl x509 -noout -dates  # 看证书有效期
```

```text
# 实测（本机 OpenSSL 版本）
$ openssl version
OpenSSL 3.0.13 30 Jan 2024
```

TLS 测试：

```shell
# 测试某站点的 TLS 版本和证书
openssl s_client -connect example.com:443 -tls1_3   # 测试 TLS 1.3
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -subject -issuer
```

## 配置文件解析

SSH 加固核心在 /etc/ssh/sshd_config（服务器端）：

```text
# 实测（本机 SSH 配置，存在安全隐患）
$ sshd -T | grep -E '^(port|permitrootlogin|passwordauthentication)'
port 22
permitrootlogin yes              # 安全隐患：允许 root 直接登录
passwordauthentication yes       # 安全隐患：允许密码登录（可被爆破）
# 建议加固：PermitRootLogin no + PasswordAuthentication no（改用密钥）
```

```text
SSH 加固要点（/etc/ssh/sshd_config）：
1. PasswordAuthentication no —— 禁用密码登录，只用密钥
2. PermitRootLogin no —— 禁止 root 直接登录（用普通用户+sudo）
3. Port 2222 —— 改默认端口（减少扫描）
4. 密钥认证 —— 公钥放 ~/.ssh/authorized_keys
```

TLS 证书配置（Nginx 里引用证书 + 私钥）：

```nginx
server {
    listen 443 ssl;
    server_name example.com;
    ssl_certificate     /etc/ssl/cert.pem;   # 证书（公钥 + 身份）
    ssl_certificate_key /etc/ssl/key.pem;    # 私钥（加密用）
    ssl_protocols TLSv1.2 TLSv1.3;           # 只留新协议
}
```

## 应用场景实战

### 场景一：加固 SSH（关闭密码登录 + 禁 root）

```shell
# 1. 先配好密钥免密（确认能登录再改配置）
ssh-keygen -t ed25519
ssh-copy-id user@server
# 2. 改 sshd_config
sudo sed -i 's/^#PasswordAuthentication yes/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo sed -i 's/^#PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
# 3. 重启生效
sudo systemctl restart sshd
```

### 场景二：生成自签证书测试 HTTPS

```shell
# 1. 生成私钥和自签证书
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes -subj "/CN=localhost"
# 2. Nginx 配置引用证书
# ssl_certificate cert.pem; ssl_certificate_key key.pem;
# 3. 测试 TLS
openssl s_client -connect localhost:443
```

## 性能与调优

```text
1. 密钥算法 —— ed25519 比 RSA 2048 更快更短，新密钥优先 ed25519
2. SSH 连接复用 —— ControlMaster 复用连接，减少握手开销（频繁 SSH 时明显）
3. TLS 会话复用 —— 开启 session cache/ticket，减少完整握手次数
4. 证书链 —— 别发太长的证书链，增加握手开销
5. WireGuard 性能 —— 内核态加密 + 极简协议，比 OpenVPN 吞吐高
```

```shell
# SSH 连接复用（~/.ssh/config）
# Host *
#     ControlMaster auto
#     ControlPath ~/.ssh/control-%r@%h:%p
#     ControlPersist 60
```

## 安全与权限

```text
1. SSH 密钥权限 —— 私钥 600，~/.ssh 目录 700，authorized_keys 600（权限不对 SSH 拒绝用）
2. 禁用弱算法 —— 禁用老 TLS 版本（1.0/1.1）和弱密码套件
3. 证书私钥保护 —— 私钥文件 600，别泄露（私钥泄露 = 身份被冒充）
4. VPN 密钥轮换 —— WireGuard/OpenVPN 密钥定期轮换
5. 防爆破 —— SSH 配 fail2ban，自动封禁爆破源 IP
```

## 故障排查

### SSH 连不上

```shell
# 1. 看 sshd 在不在、监听没
ss -tlnp | grep :22
# 2. 看认证日志（关键）
tail -f /var/log/auth.log
# 3. 测试配置语法（改配置后先测再重启）
sshd -t
# 4. 客户端 verbose 看握手卡在哪
ssh -vvv user@server
```

### TLS 证书报错

```shell
# 1. 看证书有效期和域名
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -dates -subject
# 2. 看证书链是否完整
openssl s_client -connect example.com:443 -showcerts
# 3. 看服务器用的协议版本
openssl s_client -connect example.com:443 -tls1_3
```

## 常见问题

```text
Q1: 为什么禁用密码登录，只留密钥？
A: 密码可以被暴力破解（爆破），密钥是「非对称加密挑战-应答」，几乎无法暴力破解。禁用密码登录是 SSH 加固第一步。

Q2: 自签证书为什么浏览器报不安全？
A: 自签证书没有受信任的 CA 签名，客户端不认可它的身份。生产用 Let's Encrypt 或正规 CA，自签只用于测试。

Q3: TLS 1.0/1.1 为什么必须禁用？
A: 老版本有已知漏洞（POODLE/BEAST），已被废弃。现在只留 TLS 1.2/1.3。

Q4: WireGuard 和 OpenVPN 怎么选？
A: 现代轻量、性能要求高用 WireGuard；兼容性好、环境复杂（老系统/企业策略）用 OpenVPN。
```

## 面试题

```text
1. SSH 密钥认证为什么比密码安全？
   答：密钥认证是非对称加密挑战-应答，私钥不离开客户端，无法被暴力破解；密码可以被爆破。且密钥长度远大于密码熵。

2. TLS 握手做了什么？
   答：协商加密参数 → 服务器出示证书 → 客户端用 CA 验证证书身份 → 协商对称密钥 → 建立加密通道。核心是「验证身份 + 协商密钥」。

3. 证书是什么？为什么需要 CA？
   答：证书是「公钥 + 身份信息 + CA 签名」的绑定。CA 是可信第三方，用它签名证明「这个公钥确实属于这个域名」，防止中间人伪造身份。

4. HTTPS 用对称加密还是非对称加密？
   答：都用。握手阶段用非对称加密（证书验证、密钥协商），数据传输用对称加密（性能好）。非对称负责安全，对称负责性能。
```

## 最佳实践与踩坑记录

### 最佳实践

1. SSH 必加固：禁用密码登录 + 禁 root 登录，只用密钥
2. 公网暴露的服务（SSH/Web）配 fail2ban 防爆破
3. 证书用 Let's Encrypt 免费自动续期，别用长期自签证书上生产
4. TLS 用 1.2/1.3，别用已废弃的 1.0/1.1
5. VPN 选型：现代轻量用 WireGuard，兼容成熟用 OpenVPN，企业站点互联用 IPsec

### 踩坑记录

```text
坑 1：先关密码登录再配密钥，把自己锁外面
结论：改了 PasswordAuthentication no，没先配好密钥，SSH 连不上。
原因：密码登录关了但密钥没配好，没有认证方式。
解法：先 ssh-copy-id 配好密钥、确认能登录，再关密码登录。

坑 2：PermitRootLogin 改成 no 后 sudo 用户没建
结论：禁了 root 登录，又没建普通用户，进不去系统。
原因：root 进不去、普通用户也没有。
解法：先建普通用户 + sudo 权限，再禁 root 登录。

坑 3：自签证书上生产，客户端报不安全
结论：自签证书部署 HTTPS，浏览器报「不安全」。
原因：自签证书没被信任的 CA 签名，客户端不认。
解法：生产用 Let's Encrypt 或正规 CA 证书，自签只用于测试。

坑 4：TLS 版本太老被扫描器报漏洞
结论：还开着 TLS 1.0/1.1，安全扫描报警。
原因：老 TLS 有已知漏洞（如 POODLE/BEAST），应禁用。
解法：Nginx 配 ssl_protocols TLSv1.2 TLSv1.3，禁用老版本。

坑 5：SSH 改了配置没重启，不生效
结论：改了 sshd_config，配置没生效。
原因：改完没重启 sshd 服务。
解法：systemctl restart sshd（改配置后必重启）。
```
