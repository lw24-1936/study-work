## 概述

nftables 是 netfilter 框架的**新一代用户态配置工具**，由内核的 nf_tables 子系统 + 用户态 `nft` 命令组成，目标是取代 iptables/ip6tables/arptables/ebtables 四件套。它用**一套语法**统一管理 IPv4、IPv6、ARP、桥接（bridge）的包过滤，表名/链名可自由定义，支持集合（set）、映射（map）、区间匹配、动态更新等 iptables 时代很难实现的能力。

```text
nftables 三要素：
1. 表 table —— 按地址族（family）划分：inet（IPv4+IPv6 通吃）/ ip / ip6 / arp / bridge，表名可自定义
2. 链 chain —— type（filter/nat/route）+ hook（input/forward/output/prerouting/postrouting）+ priority（同钩子下的执行顺序）
3. 规则 rule —— 匹配条件（ip saddr / tcp dport / ct state）+ 动作（accept/drop/counter/jump/log...），用 handle 唯一标识
```

现代系统（Ubuntu 20.04+、RHEL/CentOS 8+、openSUSE 15+）默认使用 nftables：即使你敲的是 `iptables` 命令，实际执行的也是 **iptables-nft 兼容层**——iptables 语法被翻译成 nft 规则存进内核。所以「新系统上 iptables 命令还能用」只是表象，真正的规则都是 nft 规则（实测见下）。

```text
# 实测（本机：Ubuntu 24.04.4 LTS，内核 7.0.0-28-generic）
$ nft --version
nftables v1.0.9 (Old Doc Yak #3)

$ nft list ruleset | head -12
# Warning: table ip filter is managed by iptables-nft, do not touch!
table ip filter {
	chain INPUT {
		type filter hook input priority filter; policy accept;
		counter packets 14528406 bytes 6048343669 jump ts-input
	}

	chain FORWARD {
		type filter hook forward priority filter; policy drop;
		counter packets 2461879 bytes 717294560 jump ts-forward
		counter packets 3255984 bytes 864871560 jump DOCKER-USER
# 解读：第一行 Warning 是 nftables 对 iptables-nft 管理表的保护提示——
# Docker/tailscale 通过 iptables 命令创建的规则，在内核里就是这些 nft 表（ip filter 等）
```

**与 iptables 的本质区别**：iptables 的「五张固定表 + 五条内置链 + 字符串规则」是写死在内核里的；nftables 把「表、链、规则」全部变成**可编程对象**——内核只提供 nf_tables 虚拟机，规则被编译成字节码后在内核里执行，用户态可以自由定义表/链/集合，匹配用「表达式」组合。这是架构级升级，不是语法糖。

## 核心概念

1. **地址族 family 与表 table**：表必须属于某个地址族——`ip`（仅 IPv4）、`ip6`（仅 IPv6）、`inet`（IPv4+IPv6 双栈，**推荐**）、`arp`（ARP 过滤）、`bridge`（桥接过滤）。表名自由命名（如 `inet filter`、`inet myfirewall`），不像 iptables 只有固定 5 张表。同一族下可以有多张表，互不干扰。

2. **链 chain**：分两类。
   - **基链（base chain）**：`type` + `hook` 定义挂到 netfilter 哪个钩子点（input/forward/output/prerouting/postrouting），`priority` 决定同钩子下多条链的执行顺序（数值小先执行，默认 `filter` 即 0）。`policy` 定义链默认策略（accept/drop）。
   - **常规链（regular chain）**：没有 hook，只被 `jump`/`goto` 调用，相当于 iptables 的自定义链，用于规则分组。

3. **规则 rule**：由「匹配表达式 + 语句」组成，如 `ip saddr 192.168.1.0/24 tcp dport 22 counter accept`。每条规则有**句柄（handle）**唯一标识，`nft -a list ruleset` 查看，删除规则按 handle 操作（行号会因插入/删除漂移，handle 稳定）。

4. **集合 set 与映射 map**：把多个元素打包成一个对象，一条规则批量匹配。
   - `set`：无序集合（`{22, 80, 443}`、IP 列表、CIDR 区间），可加 `flags interval`（区间匹配）和 `timeout`（元素自动过期，**动态封禁神器**）。
   - `map`：键值映射，命中后执行「查表得到的结果」，如按端口映射到不同动作。

5. **句柄与事务**：`nft -f 文件` 按事务提交整个规则集，要么全部生效、要么全部失败（原子替换），这是 iptables 逐条下发做不到的。

```text
# 实测（nft list ruleset 中 Docker 的链，规则表达比 iptables 清晰得多）
$ nft list ruleset | grep -A6 'chain DOCKER {'
chain DOCKER {
	ip daddr 172.22.0.2 iifname != "br-c61daaf2859b" oifname "br-c61daaf2859b" tcp dport 9848 counter packets 0 bytes 0 accept
	ip daddr 172.18.0.7 iifname != "br-49cfcba0160f" oifname "br-49cfcba0160f" tcp dport 5672 counter packets 82 bytes 4920 accept
	ip daddr 172.18.0.6 iifname != "br-49cfcba0160f" oifname "br-49cfcba0160f" tcp dport 3306 counter packets 19239 bytes 1154340 accept
	ip daddr 172.18.0.4 iifname != "br-49cfcba0160f" oifname "br-49cfcba0160f" tcp dport 5432 counter packets 0 bytes 0 accept
	ip daddr 172.17.0.2 iifname != "docker0" oifname "docker0" tcp dport 2379 counter packets 0 bytes 0 accept
	...
}
# 解读：ip daddr 容器IP + iifname/oifname 方向限定 + tcp dport 容器端口 → accept，
# 语义一眼可读；同一规则在 iptables 里是 -d 172.18.0.6/32 ! -i br-49... -o br-49... -p tcp --dport 3306 -j ACCEPT
```

**Red Hat 系差异**：RHEL 8+ 默认 firewalld 管理防火墙，firewalld 的后端就是 nftables（`/usr/lib/firewalld/` 下存 nft 规则片段）；RHEL 7 及更早用 firewalld 的 iptables 后端或直接 iptables-services。Ubuntu 桌面/服务器常见组合是 ufw（底层也是 nftables，见 [[12.3-firewalld-ufw]]）。

## 工作原理

### 内核虚拟机的字节码匹配

nftables 的规则不是字符串，而是被 `nft` 编译成**字节码**，通过 netlink（nfnetlink + nf_tables 协议）下发到内核。数据包到达钩子点后，内核的 nf_tables 虚拟机按优先级遍历该钩子上的基链，逐条执行规则的字节码（加载字段 → 比较 → 跳转/动作）。相比 iptables 在内核里维护「字符串规则表」逐条解析，nft 的字节码一次编译、多次执行，规则多时性能优势明显。

### hook + priority 决定执行顺序

链通过 `type filter hook input priority 0` 挂到 netfilter 钩子点。同一钩子点上，priority 数值小的链先执行（`-300` 的 raw 类处理先于 `0` 的 filter，`100` 的 nat 类靠后）。同 priority 的多条链按创建顺序执行。这就是 nftables 里「同时存在多个防火墙工具（Docker 的 ip filter 表、用户自己的 inet 表）却不打架」的机制——**不同 priority 错开，相同 priority 先建先执行**。

```text
# 实测（本机 nft 中所有表，iptables-nft 兼容层按旧表名创建）
$ nft list tables
table ip filter
table ip nat
table ip6 filter
table ip6 nat
table ip mangle
table ip6 mangle
table ip raw
# 解读：ip/ip6 族 + filter/nat/mangle/raw 旧表名 = iptables-nft 兼容层为
# iptables 命令创建的翻译表（Docker、tailscale 在用）；纯 nft 风格会用 inet 族自定义表名
```

### iptables-nft 兼容层原理

iptables 命令（v1.8.x）有三个后端：`iptables-legacy`（直接操作 ip_tables 内核模块）、`iptables-nft`（翻译成 nft 规则）、`iptables-restore-translate`（把规则文件翻译成 nft 语法）。Ubuntu 通过 update-alternatives 把 `/usr/sbin/iptables` 指向 `iptables-nft`。翻译规则：

- `-t filter` → `table ip filter`，链 `INPUT` → `chain INPUT { type filter hook input priority filter; }`，规则逐条翻译成 nft 表达式，并自动附加 `counter`；
- **兼容层表被 nft 工具标记为「受管」**——`nft list ruleset` 第一行会输出 `# Warning: table ip filter is managed by iptables-nft, do not touch!`，`nft flush ruleset` 会连带清掉这些表（实测确认：本机 flush 后 Docker 规则全没，需重启 docker 重建）。

```text
# 实测（iptables 命令确实是 nft 后端）
$ iptables --version
iptables v1.8.10 (nf_tables)
$ update-alternatives --display iptables | grep '链接目前指向'
  链接目前指向 /usr/sbin/iptables-nft
# 实测（nft list ruleset 中 iptables 规则自动带 counter）
$ nft list ruleset | grep -B1 'jump DOCKER-FORWARD'
	chain FORWARD {
		type filter hook forward priority filter; policy drop;
		counter packets 3255984 bytes 864871560 jump DOCKER-FORWARD
```

### 与 conntrack 的协作

nftables 通过 `ct` 表达式访问连接跟踪状态：`ct state established,related accept`。conntrack 本身仍是 netfilter 内核框架的一部分（模块 nf_conntrack，实测本机已加载），nftables 只是换了个更简洁的访问语法，与 iptables 的 `-m conntrack --ctstate` 等价。set 元素配合 `timeout` 还能实现「连接级动态封禁」（见场景二）。

## 常用命令与配置

### 查看

```shell
nft list ruleset                # 查看全部规则（等价 iptables-save）
nft -a list ruleset             # 带 handle（删规则必用；注意 -a 必须放在命令前！）
nft list tables                 # 列出所有表
nft list table inet filter      # 只看某张表
nft list chain inet filter input   # 只看某条链
```

```text
# 实测（-a 放错位置的报错，很多人第一次就踩）
$ nft list ruleset -a
Error: syntax error, options must be specified before commands
nft list ruleset -a
   ^             ~~
# 正确姿势：nft -a list ruleset（全局选项在命令之前）
```

### 建表建链

```shell
nft add table inet myfilter                                  # 建表（inet 族，双栈）
nft delete table inet myfilter                               # 删表（连带删链和规则）
nft add chain inet myfilter input '{ type filter hook input priority 0; policy drop; }'   # 建基链
nft add chain inet myfilter ssh_guard                        # 建常规链（规则分组用）
```

### 增删规则

```shell
nft add rule inet myfilter input tcp dport 22 accept         # 追加到链尾
nft insert rule inet myfilter input tcp dport 22 accept      # 插入到链首
nft add rule inet myfilter input handle 5 ...                # 指定位置插入
nft -a list chain inet myfilter input                        # 看 handle
nft delete rule inet myfilter input handle 3                 # 按 handle 删规则（不是行号！）
nft flush chain inet myfilter input                          # 清空某链
nft flush table inet myfilter                                # 清空某表（保留表结构）
nft flush ruleset                                            # 清空所有表（慎用！Docker 规则也没了）
```

### 规则集文件

```shell
nft -f /etc/nftables.conf          # 从文件加载（原子提交：语法错误则整体不生效）
nft -c -f /etc/nftables.conf       # -c 只检查语法不应用（相当于 iptables-restore --test）
nft list ruleset > /etc/nftables.conf   # 导出当前规则为文件
```

### iptables ↔ nft 逐条对照

| 操作 | iptables | nft |
|---|---|---|
| 看规则 | `iptables -L -n -v` | `nft list ruleset` |
| 建表 | （固定五表） | `nft add table inet filter` |
| 建 INPUT 链 | （内置） | `nft add chain inet filter input '{ type filter hook input priority 0; policy drop; }'` |
| 放行 SSH | `iptables -A INPUT -p tcp --dport 22 -j ACCEPT` | `nft add rule inet filter input tcp dport 22 accept` |
| 放行已建连接 | `iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT` | `nft add rule inet filter input ct state established,related accept` |
| 放行回环 | `iptables -A INPUT -i lo -j ACCEPT` | `nft add rule inet filter input iif lo accept` |
| 多端口 | `iptables -A INPUT -m multiport --dports 80,443 -j ACCEPT` | `nft add rule inet filter input tcp dport {80,443} accept` |
| 封 IP | `iptables -A INPUT -s 1.2.3.4 -j DROP` | `nft add rule inet filter input ip saddr 1.2.3.4 drop` |
| 默认策略 | `iptables -P INPUT DROP` | 链定义里的 `policy drop;` |
| 删规则 | `iptables -D INPUT 3`（行号） | `nft delete rule inet filter input handle 3` |
| 清空 | `iptables -F` | `nft flush ruleset` |
| 计数 | `-v` 查看 | 规则里显式写 `counter` |
| 日志 | `-j LOG --log-prefix "X"` | `log prefix "X"` |
| 保存/恢复 | `iptables-save/restore` | `nft list ruleset > f` / `nft -f f` |

## 配置文件解析

nftables 的配置文件就是 `nft` 脚本本身（无独立格式），默认路径 `/etc/nftables.conf`，由 `nftables` systemd 服务开机执行 `nft -f /etc/nftables.conf` 加载。

```text
# 实测（本机 /etc/nftables.conf，Ubuntu 24.04 默认模板，仅 243 字节）
#!/usr/sbin/nft -f

flush ruleset

table inet filter {
	chain input {
		type filter hook input priority filter;
	}
	chain forward {
		type filter hook forward priority filter;
	}
	chain output {
		type filter hook output priority filter;
	}
}
```

```text
字段含义：
#!/usr/sbin/nft -f    shebang：本文件用 nft -f 执行
flush ruleset         先清空现有规则（保证幂等，避免重复叠加）
table inet filter     定义 inet 族表（同时管 IPv4+IPv6）
chain input {...}     定义基链：type filter（过滤型）hook input（入站钩子）priority filter（默认优先级 0）
policy drop/accent    链默认策略（未写则默认 accept）——注意 Ubuntu 模板故意不写 policy，保持全放行
```

**Ubuntu 模板的坑**：默认模板的链没有 `policy`（默认 accept）、也没有任何规则，等于「空防火墙」——它存在的意义是让 `nftables` 服务有一个可加载的规则集占位。真正要启用防火墙，需要在这个文件里补规则和策略（见场景一），或直接导入 `nft list ruleset` 的导出结果。

```shell
# 持久化流程
nft list ruleset > /etc/nftables.conf      # 导出当前规则（覆盖模板）
nft -c -f /etc/nftables.conf && echo OK    # 语法预检
systemctl enable --now nftables            # 开机自启 + 立即加载
```

```text
# 更完整的规则文件示例（含变量、集合、日志链）：
#!/usr/sbin/nft -f

flush ruleset

define LAN = 192.168.1.0/24          # 变量，nft 1.0+ 支持

table inet filter {
    chain input {
        type filter hook input priority filter; policy drop;
        ct state established,related accept
        iif "lo" accept
        iifname "docker0" accept      # 容器网络放行（按需）
        tcp dport { ssh, http, https } accept   # 用服务名代替端口号
        ip saddr $LAN accept          # 内网放行
        jump log-drop                 # 其余进日志链
    }
    chain forward {
        type filter hook forward priority filter; policy drop;
        ct state established,related accept
    }
    chain output {
        type filter hook output priority filter; policy accept;
    }
    chain log-drop {                  # 日志链：记录后丢弃
        log prefix "NFT-DROP: " flags all counter drop
    }
}
```

**Red Hat 系差异**：RHEL 8+ 直接使用 nftables 时，规则文件是 `/etc/sysconfig/nftables.conf`（或 `/etc/nftables.conf` 软链），用 `systemctl enable --now nftables` 管理；但更常见的做法是让 firewalld 管理（`firewall-cmd`），firewalld 在后台把规则翻译成 nftables 规则，用户不需要直接写 nft 语法。

## 应用场景实战

### 场景一：用 inet 族配一套基础防火墙（IPv4+IPv6 通吃）

```shell
# 1. 建表建链（inet 族一套规则管双栈）
nft add table inet filter
nft add chain inet filter input  '{ type filter hook input  priority filter; policy drop; }'
nft add chain inet filter forward '{ type filter hook forward priority filter; policy drop; }'
nft add chain inet filter output '{ type filter hook output  priority filter; policy accept; }'
# 2. 入站放行：已建连接、回环、SSH、Web
nft add rule inet filter input ct state established,related accept
nft add rule inet filter input iif lo accept
nft add rule inet filter input tcp dport { ssh, http, https } accept
# 3. 显式丢弃非法状态
nft add rule inet filter input ct state invalid drop
# 4. 查看效果
nft -a list table inet filter
```

```text
# 实测（按上面命令在本机临时演示后的输出，含 counter）
$ nft list table inet filter
table inet filter {
	chain input {
		type filter hook input priority filter; policy drop;
		ct state established,related accept
		iif "lo" accept
		tcp dport { ssh, http, https } accept
		ct state invalid drop
	}
	...
}
# 对比 iptables：同样效果需要 iptables + ip6tables 两套命令各配一遍，
# inet 族是 nftables 最核心的日常收益
```

### 场景二：set 区间匹配 + 动态封禁（防暴力破解）

```shell
# 1. 建 interval 集合（放被拉黑 IP，支持 CIDR 区间）
nft add table inet blacklist
nft add set inet blacklist blocked '{ type ipv4_addr; flags interval; }'
# 2. 封禁规则：命中集合直接丢
nft add rule inet blacklist input ip saddr @blocked drop
# 3. 动态加元素（脚本检测到爆破来源后执行）
nft add element inet blacklist blocked '{ 203.0.113.66 }'
nft add element inet blacklist blocked '{ 203.0.113.0/24 }'    # 区间也支持
# 4. 查看/删除
nft list set inet blacklist blocked
nft delete element inet blacklist blocked '{ 203.0.113.66 }'
```

```text
# 实测（本机临时演示：无 hook 链的表，不影响任何流量）
$ nft add table inet __demo__
$ nft add set inet __demo__ ports  '{ type inet_service; }'
$ nft add set inet __demo__ blocks '{ type ipv4_addr; flags interval; }'
$ nft add element inet __demo__ ports '{ 22, 80, 443 }'
$ nft list table inet __demo__
table inet __demo__ {
	set ports {
		type inet_service
		elements = { 22, 80, 443 }
	}

	set blocks {
		type ipv4_addr
		flags interval
	}
}
$ nft delete table inet __demo__    # 用完即删，规则集恢复原状
```

**动态封禁进阶（元素自动过期）**：给 set 加 `timeout 10m`，元素到期自动移除，无需脚本清理——配合 fail2ban 类逻辑，把「检测到 N 次失败登录的源 IP」动态 `add element` 进集合，实现自动解封。

```shell
nft add set inet blacklist blocked '{ type ipv4_addr; flags interval, timeout; timeout 10m; }'
nft add element inet blacklist blocked '{ 203.0.113.66 timeout 5m }'   # 单元素可覆盖超时
```

### 场景三：limit 限速 + 日志链（防 SYN flood / 爆破基础版）

```shell
# 1. 限速：每源 IP 每秒最多 3 个新 TCP 连接，超出 drop
nft add rule inet filter input tcp dport 22 ct state new \
    limit rate 3/second accept
nft add rule inet filter input tcp dport 22 ct state new drop
# 2. 全局限速（防 SYN flood 基础版）：入站 SYN 总速率限制
nft add rule inet filter input tcp flags syn limit rate 100/second burst 200 accept
nft add rule inet filter input tcp flags syn drop
# 3. 日志链：记录被丢弃的包（配合日志分析定位攻击源）
nft add chain inet filter logdrop
nft add rule inet filter logdrop log prefix "NFT-DROP: " flags all counter drop
nft add rule inet filter input jump logdrop    # 链尾跳转（前面没命中才到这）
# 日志落点：内核日志（journalctl -k 或 /var/log/kern.log）
```

### 场景四：nftables 做 NAT（网关/端口转发）

```shell
# 1. 建 nat 表与链（注意：nat 链类型必须是 type nat）
nft add table ip nat
nft add chain ip nat postrouting '{ type nat hook postrouting priority 100; }'
nft add chain ip nat prerouting  '{ type nat hook prerouting  priority -100; }'
# 2. 源 NAT（内网出外网）
nft add rule ip nat postrouting ip saddr 192.168.1.0/24 oifname "eth0" masquerade
# 3. 目标 NAT（外网 8080 → 内网 10.0.0.5:80，配合 forward 放行）
nft add rule ip nat prerouting tcp dport 8080 dnat to 10.0.0.5:80
nft add rule inet filter forward ip daddr 10.0.0.5 tcp dport 80 accept
# 4. 开启内核转发
sysctl -w net.ipv4.ip_forward=1
```

**Red Hat 系差异（firewalld 场景）**：RHEL 8+ 上不推荐直接写 nft 规则与 firewalld 并存（两者都会操作 nftables 且互不感知，容易互相覆盖）。firewalld 环境用 `firewall-cmd --add-forward-port`、`--add-masquerade`、`--add-rich-rule` 管理；直接管理 nftables 时先 `systemctl stop firewalld` 或让 firewalld 使用 nftables 后端并避免同时手改。

## 性能与调优

```text
1. 集合 set —— 多个端口/IP 放一个 set，一条规则完成批量匹配（内核哈希/区间树查找），
   比几十条顺序规则快得多；IP 黑名单场景优先 set 而非逐条 add rule。
2. 规则顺序 —— 命中率高的放前面：ct state established 放链首，可让大多数包
   一次匹配就结束，避免后续几十条规则的空匹配。
3. inet 族 —— 一套规则管 IPv4+IPv6，规则量减半（iptables 时代要配两遍）。
4. counter 开销 —— counter 会统计每个包的计数，高吞吐纯过滤链可省略 counter
   （只留关键规则计数用于排障），减少一点原子操作开销。
5. 避免大规则集 —— nft 字节码匹配本身快，但规则/集合元素过多仍有缓存压力；
   K8s 大规模场景注意 iptables 规则风暴问题，nft 已大幅缓解（一次原子更新）。
6. priority 规划 —— 多个工具共存的系统，用不同 priority 错开链的执行顺序，
   避免同优先级下「后建链先执行」的顺序不确定性。
7. 硬件卸载 —— 支持网卡的 flowtable 特性可把 established 流卸载到硬件快速路径
   （需网卡驱动支持，普通云主机基本用不上）。
```

```shell
# 性能验证：对比 iptables 与 nft 规则集规模（本机 Docker 场景）
nft list ruleset | wc -l          # nft 规则总行数
iptables-save | wc -l             # iptables 视角行数
# 实测本机：两者数值接近（因为 Docker 规则本来就是 iptables-nft 翻译的），
# 但纯 nft 建的规则集通常比等价 iptables 简洁 30-50%
```

## 安全与权限

```text
1. 默认策略 —— 基链 policy drop，只放行必要端口（最小权限）；inet 族把 IPv6 一起管住，
   避免「只配了 IPv4 防火墙、IPv6 裸奔」的经典漏洞。
2. 状态匹配 —— ct state established,related 放行已建连接，new 连接才走明细规则；
   ct state invalid 显式 drop（伪造状态攻击）。
3. 限速 —— limit/hashlimit 防爆破与 SYN flood；动态 set + timeout 实现自动解封。
4. 持久化 —— 规则写 /etc/nftables.conf + systemctl enable nftables，重启不丢。
5. 权限模型 —— nft 需要 root / CAP_NET_ADMIN；sudoers 可授权特定 nft 命令；
   非 root 用户查看规则可用 sudo nft list ruleset（或配只读权限）。
6. 原子提交 —— 用 nft -f 批量下发（语法错误整体回滚），避免逐条 add 半途失败
   留下残缺规则集；生产变更先 nft -c -f 预检。
7. 与 Docker/firewalld 共存 —— 别 flush ruleset 裸奔式清空；理解谁在管理哪些表。
8. 规则审计 —— 规则文件入 git 仓库，配合 nft -c 语法检查进 CI。
```

```shell
# sudoers 最小授权示例（/etc/sudoers.d/nft）
# 允许 ops 用户只读查看规则
ops ALL=(root) NOPASSWD: /usr/sbin/nft list *
# 生产变更流程：备份 → 预检 → 应用 → 验证 → 持久化
nft list ruleset > /root/nft-backup-$(date +%F).conf
nft -c -f /etc/nftables.conf && systemctl reload nftables
nft list ruleset | head -20        # 确认变更生效
```

## 故障排查

### 案例一：规则语法报错，怎么定位

```text
# 实测（本机复现：给不存在的链加规则）
$ nft add rule inet __demo__ input tcp dport 22 accept
Error: No such file or directory; did you mean chain 'ts-input' in table ip 'filter'?
add rule inet __demo__ input tcp dport 22 accept
                       ^^^^^
exit=1
```

```text
定位方法：
1. 报错会带 ^^^^^ 精确指向出错 token（本例是链名 input 不存在）
2. 先确认表/链存在：nft list tables；nft list table inet xxx
3. 选项顺序错误（如 nft list ruleset -a）会报 "options must be specified before commands"
4. 批量文件用 nft -c -f 预检，语法错误时整批不生效（原子性），不会留下半套规则
```

### 案例二：flush ruleset 后网络全断 / Docker 容器网络全挂

```shell
# 现象：执行 nft flush ruleset 后，SSH 还在但容器全不通、外部访问全被拒
# 原因：flush ruleset 清空了所有表——包括 iptables-nft 兼容层里 Docker/tailscale 的规则
# 恢复步骤：
# 1. 恢复之前导出的规则集
nft -f /root/nft-backup.conf
# 2. 若没备份：重启 Docker 让 daemon 重建规则（容器网络恢复）
systemctl restart docker
# 3. 若 SSH 也断了（自己把 input 链也 flush 了，默认 policy accept 反而恢复网络）
#    控制台登录后立即 nft list ruleset 评估损失
# 4. 教训：flush 前先 nft list ruleset > backup.conf
```

### 案例三：iptables 和 nft 混用，规则「看不见、不生效」

```shell
# 现象：用 nft add rule inet filter input ... 加了规则，但 iptables -L 看不到；
#       或 iptables 加了规则，nft 里明明有却不起作用
# 排查：
# 1. 确认表归属：nft list tables —— ip filter（iptables-nft 翻译表）vs inet filter（纯 nft 表）
# 2. 确认 iptables 后端：iptables --version 应显示 (nf_tables)
#    —— 若显示 (legacy)，iptables 与 nft 各管一套互不可见，必冲突
# 3. 确认优先级：同 hook 上 priority 相同的链，先创建的先执行；
#    规则「在但没生效」多半是另一个工具的链 priority 更小先执行了
# 4. 统一策略：全系统只用 nft（推荐）或只用 iptables-nft，不要两套混写
```

### 案例四：规则在，但流量不匹配（地址族 / 接口名写错）

```shell
# 现象：ip 族的规则没拦到 IPv6 流量；iif "eth0" 匹配不到实际接口
# 排查：
# 1. 地址族：ip 族只匹配 IPv4；IPv6 流量需要 ip6 或 inet 族
nft list tables                        # 看有没有 ip6 表
nft list table ip6 filter
# 2. 接口名：nft 用 iifname "eth0"（字符串）或 iif "eth0"（引用已存在接口），
#    接口不存在时 iif 报错而 iifname 不报（静默不匹配！）—— 优先用 iifname
ip link show                           # 确认真实接口名（云主机常见 ens3/eth0 混用）
# 3. 用计数器验证命中：规则加 counter，nft list 看 packets 是否增长
nft add rule inet filter input iifname "eth0" counter accept
```

## 常见问题

```text
Q1: iptables 和 nft 命令混用会怎样？
A: 现代系统上 iptables 就是 iptables-nft 后端，两者操作同一内核（nf_tables），
   不会「各存一套」——但混用容易造成逻辑混乱：iptables 语法翻译出来的规则和
   纯 nft 规则混在 ruleset 里，管理视角分裂、易重复。规范做法：新系统统一用
   nft；必须用 iptables 时记住它只是 nft 的翻译层。

Q2: nft 删规则为什么用 handle 不用行号？
A: 行号是「显示位置」，插入/删除会漂移；handle 是规则创建时的唯一标识，稳定不变。
   先 nft -a list ruleset（-a 在前！）看 handle，再 nft delete rule 表 链 handle N 删除。

Q3: inet 族和 ip 族有什么区别？为什么推荐 inet？
A: ip 族只匹配 IPv4 流量，ip6 族只匹配 IPv6，inet 族同时匹配两者。用 inet 一套规则
   管双栈，避免「只配了 IPv4 防火墙、IPv6 裸奔」的漏洞，也省一半规则量。
   需要区分协议族做不同处理时（如 NAT 必须分族）才用 ip/ip6。

Q4: flush ruleset 会清掉 Docker 的规则吗？
A: 会。实测本机 flush ruleset 后，iptables-nft 兼容层的 ip filter/ip nat 等表全部清空
   （Docker 容器网络立即失效）。恢复：重启 docker 服务重建规则；更稳妥的是
   flush 前 nft list ruleset > backup.conf 备份。

Q5: nftables 的 NAT 链为什么 type 是 nat 而 filter 链 type 是 filter？
A: 链的 type 决定它挂在 netfilter 的哪个处理阶段：filter 链在过滤阶段执行，
   nat 链在 NAT 阶段执行（priority -100/100 附近，且只有 nat 链能执行
   dnat/snat/masquerade 语句）。type 写错（如 filter 链里写 dnat）会直接报错。

Q6: 服务重启后 nft 规则丢了怎么办？
A: 检查 nftables 服务是否启用并加载了 /etc/nftables.conf：
   systemctl is-enabled nftables；规则持久化 = nft list ruleset > /etc/nftables.conf
   + systemctl enable --now nftables。注意：若规则里有 Docker 的翻译表，
   持久化整个 ruleset 意义不大（Docker 重启会重建），应只持久化自己管理的表。

Q7: 新系统上还有必要学 iptables 吗？
A: 有必要但要分清层次：大量存量文档、脚本、工具（Docker、K8s、fail2ban）仍在用
   iptables 语法；理解 iptables 就是理解 netfilter 的钩子/表/链模型（见
   [[12.1-netfilter 框架]]），这个模型 nftables 完全继承。学 iptables 理解模型，
   学 nft 用于新配置——两者是同一框架的两种语法。
```

## 面试题

```text
1. nftables 相比 iptables 有哪些优势？
   答：① 语法统一：一套语法管 IPv4/IPv6/ARP/桥接，取代四套工具；② 架构升级：
   规则编译成字节码由内核虚拟机执行，比 iptables 逐条解析字符串更快、支持原子
   更新；③ 更灵活：表/链可自定义、支持集合 set 与映射 map、区间匹配、动态元素
   超时；④ inet 族一套规则管双栈，减少配置量。

2. nftables 的表和 iptables 的表有什么不同？
   答：iptables 是内核写死的五张固定表（filter/nat/mangle/raw/security），表名和
   用途绑定；nftables 的表按地址族（inet/ip/ip6/arp/bridge）划分、名字可自定义，
   同一族下可建多张表，表内链的 type/hook/priority 决定其职责，概念更统一。

3. 为什么新系统的 iptables 命令还能用？它和 nft 是什么关系？
   答：新系统（Ubuntu 20.04+、RHEL 8+）的 iptables 命令实际是 iptables-nft 兼容层：
   iptables 语法被翻译成 nft 规则存入内核的 nf_tables 框架，nft list ruleset 能看到
   这些规则（表名形如 ip filter），且带 "managed by iptables-nft" 警告。所以
   iptables 是语法层，nft 是内核规则的唯一真实形态。

4. nft 规则的 priority 是什么？为什么重要？
   答：priority 决定同一钩子（hook）下多条基链的执行顺序，数值小的先执行
   （如 -300 先于 0 先于 100）。它让多个工具（Docker、firewalld、用户规则）可以
   共存于同一钩子而互不覆盖——不同工具用不同 priority 错开执行阶段。
   同 priority 的链按创建顺序执行。

5. nftables 的 set 解决了什么问题？举一个应用场景。
   答：把大量匹配对象（IP 列表、端口组、CIDR 区间）打包成一个集合，一条规则完成
   批量匹配，性能远好于几十条顺序规则；支持 flags interval 做 CIDR 区间匹配、
   timeout 让元素自动过期。典型场景：动态黑名单——检测到暴力破解源 IP 后
   nft add element 进集合立即封禁，timeout 到期自动解封。

6. 用 nftables 实现「只允许内网访问 SSH、其余拒绝」的完整步骤？
   答：① nft add table inet filter；② 建 input 基链 type filter hook input priority 0
   policy drop；③ ct state established,related accept；④ iif lo accept；
   ⑤ ip saddr 192.168.1.0/24 tcp dport 22 accept；⑥ 导出持久化 nft list ruleset
   > /etc/nftables.conf + systemctl enable nftables。要点：policy drop 兜底、
   状态匹配放行回程、inet 族覆盖 IPv6。

7. nft -f 加载规则集为什么是「原子」的？好处是什么？
   答：nft -f 把整个文件作为一个事务提交到内核：任何一条规则语法/语义错误，
   整批规则都不生效，内核保持原规则集不变（配合 -c 可只做预检）。好处是
   生产变更不会出现「前一半生效、后一半失败」的中间态，配合备份可快速回滚。
```

## 最佳实践与踩坑记录

### 最佳实践

1. **新系统优先用 nft**：iptables 只是兼容层；新配置一律 `nft` 语法，读文档/教程时注意区分新旧写法。
2. **一律用 inet 族**：一套规则管 IPv4+IPv6，防止 IPv6 裸奔。
3. **规则文件化 + 原子加载**：规则写 /etc/nftables.conf，变更走 `nft -c -f` 预检 → 应用 → 验证，别在生产上逐条 `nft add rule`。
4. **改前备份**：任何 flush/大改前先 `nft list ruleset > backup.conf`。
5. **理解「谁在管哪些表」**：Docker/tailscale/firewalld 各管各的表，别 flush 全局、别改别人的链（`# Warning: ... do not touch!`）。
6. **set 优先于规则堆叠**：端口组、IP 黑名单用 set；动态封禁用带 timeout 的 set。
7. **关键规则留 counter**：排障靠计数器看命中，纯性能敏感链再考虑去掉。
8. **注意选项位置**：`nft -a list ruleset`（-a 在命令前），`nft list ruleset -a` 直接报语法错误。

### 踩坑记录

坑 1：iptables 和 nft 命令混用，规则「看不见」
结论：一会儿 `iptables -A` 一会儿 `nft add rule`，两边看到的东西对不上。
原因：iptables 规则翻译成 nft 后表名是 `ip filter` 这类，纯 nft 规则表名自定义；若 iptables 是 legacy 后端则两套内核框架完全隔离。
解法：统一用 nft；必须用 iptables 时先 `iptables --version` 确认是 (nf_tables) 后端。

坑 2：`nft flush ruleset` 把 Docker 规则全清了
结论：flush 后容器网络全挂，外部访问也全断。
原因：flush ruleset 清空所有表，包括 iptables-nft 兼容层中 Docker 自动生成的规则。
解法：flush 前备份；误清后 `systemctl restart docker` 重建；日常清理用 `nft flush table 自己的表` 而不是全局 flush。

坑 3：`nft list ruleset -a` 报语法错误
结论：照着文档敲 `nft list ruleset -a`，报 "options must be specified before commands"。
原因：`-a/--handle` 是全局选项，必须放在命令之前。
解法：`nft -a list ruleset`。

坑 4：规则没持久化，重启后消失
结论：`nft add rule` 配好的防火墙，重启后全没了。
原因：nft 命令只改内核运行时规则，没写入 /etc/nftables.conf，nftables 服务也未启用。
解法：`nft list ruleset > /etc/nftables.conf` + `systemctl enable --now nftables`。

坑 5：删规则用行号思路，删错规则
结论：想删第 3 条规则，`nft delete rule ... ` 却删了别的。
原因：nft 没有行号概念，删除必须按 handle；`nft list ruleset` 默认不显示 handle。
解法：`nft -a list ruleset` 确认 handle 后 `nft delete rule 表 链 handle N`。

坑 6：ip 族和 inet 族搞混，规则没生效
结论：加了一堆 ip 族规则，IPv6 流量照样进。
原因：ip 族只匹配 IPv4，IPv6 走 ip6/inet 族；只配 IPv4 防火墙等于 IPv6 裸奔。
解法：统一用 inet 族；确需分族时 ip/ip6 各建一套并都验证。

坑 7：接口名用 iif 写错，规则静默不匹配
结论：`iif "eth0"` 的规则永远不命中（计数器为 0）。
原因：iif 要求接口对象存在（云主机接口名可能是 ens3/enp1s0），接口不存在时报错/不匹配；iifname 是字符串比较更宽容。
解法：用 `iifname` 匹配接口名，先 `ip link show` 确认真实接口名。

坑 8：Ubuntu 默认 /etc/nftables.conf 是「空防火墙」
结论：启用了 nftables 服务，以为有防火墙了，其实什么都没拦。
原因：Ubuntu 模板只建了三个无 policy、无规则的链（本机实测 243 字节模板），默认全放行。
解法：按场景一补 policy drop 和规则；启用后 `nft list ruleset` 验证真的有规则。

坑 9：与 firewalld 并存互相覆盖（Red Hat 系）
结论：RHEL 8+ 上手写 nft 规则，过一会儿不见了或和 firewalld 冲突。
原因：firewalld 也在操作 nftables，双方不感知对方，重启/重载会互相覆盖。
解法：二选一——firewalld 环境用 firewall-cmd 管理；直接管理 nftables 时停用 firewalld。

坑 10：`nft -f` 加载带 `flush ruleset` 的配置文件把 Docker 规则冲掉
结论：每次 `systemctl reload nftables` 后容器网络就挂一次。
原因：配置文件开头 `flush ruleset` 会清空所有表（包括 Docker 的），再加载自己的规则。
解法：配置文件开头只 flush 自己管理的表（`flush table inet filter`），或与 Docker 共存时把 Docker 的规则一并导出合并，或不用全局 flush。
