## 概述

定时任务在生产环境要「可靠」——任务没跑完不能重复跑（任务锁）、失败要能发现（日志）、失败要能重试（重试）、关键任务要通知（邮件）。裸 cron 任务没有这些保障，要靠脚本自己实现。核心四件事：锁（flock 防并发）、日志（重定向留痕）、重试（失败重试）、通知（邮件/webhook）。这是「定时任务能用」到「定时任务可靠」的关键。

```text
任务可靠性四件事：
1. 任务锁 flock —— 防止上次没跑完、这次又启动（并发冲突）
2. 日志重定向 —— 记录执行结果，失败可查
3. 失败重试 —— 失败后重试，提高成功率
4. 邮件通知 —— 关键任务失败/完成时通知
```

## 核心概念

1. **任务锁（flock）**：文件锁，执行前先拿锁，拿不到就退出（或等待），防止「上次没跑完，这次又启动」。
2. **日志重定向**：任务输出重定向到文件（>> log 2>&1），留痕可查，否则失败也看不到。
3. **失败重试**：任务因临时故障（网络抖动、依赖没就绪）失败时重试，设上限和间隔，避免疯狂重试。
4. **邮件/webhook 通知**：关键任务失败/完成时通知到人，邮件（mail/MAILTO）或 webhook（钉钉/微信）。

```text
可靠任务 = 锁（防并发）+ 日志（留痕）+ 重试（提成功率）+ 通知（可发现）
```

## 工作原理

一个可靠的定时任务脚本，执行流程是「拿锁 → 执行（带重试）→ 记录结果 → 失败通知」：

1. **拿锁**：flock 抢文件锁，抢不到说明上次还在跑，立即退出（-n）。
2. **执行 + 重试**：执行核心逻辑，失败则按间隔重试 N 次。
3. **记录**：每步用带时间戳的日志函数记录，输出重定向到日志文件。
4. **通知**：最终失败时发 webhook/邮件告警。

cron 只负责「按时触发」，可靠性全靠脚本内部这四步保证；systemd timer 则把「重试」下沉到 service 的 Restart 配置。

```text
可靠任务流程：
拿锁（flock）→ 执行（失败重试 N 次）→ 记录（时间戳日志）→ 失败通知（webhook/邮件）
```

## 常用命令与配置

```shell
# flock 防止并发执行
flock -n /var/lock/backup.lock /opt/scripts/backup.sh
# 放进 cron：
# */30 * * * * flock -n /var/lock/backup.lock /opt/scripts/backup.sh

# cron 任务重定向日志（标准写法）
0 3 * * * /opt/scripts/backup.sh >> /var/log/backup.log 2>&1

# cron 里设 MAILTO（输出发邮件）
MAILTO=admin@example.com
0 3 * * * /opt/scripts/backup.sh
```

```text
# 脚本内用 flock 的完整写法
#!/bin/bash
exec 9>/var/lock/mytask.lock
flock -n 9 || { echo "已在运行，退出"; exit 1; }
# ... 任务逻辑 ...
```

## 配置文件解析

可靠任务没有统一配置文件，关键「配置点」散落在脚本和 cron 条目里：

```text
1. 锁文件路径 —— /var/lock/xxx.lock（flock 的锁，建议放 /var/lock）
2. 日志文件路径 —— /var/log/xxx.log（重定向目标）
3. 重试参数 —— 次数上限（如 3）+ 间隔（如 60 秒）
4. 通知渠道 —— MAILTO（邮件）或 webhook URL（钉钉/微信）
```

```text
# systemd 方式的重试配置（service 单元）
[Service]
ExecStart=/opt/scripts/sync.sh
Restart=on-failure
RestartSec=60
```

## 应用场景实战

### 场景一：做一个可靠的定时备份任务

```bash
#!/bin/bash
# /opt/scripts/reliable-backup.sh
exec 9>/var/lock/backup.lock
flock -n 9 || { echo "$(date) 已在运行"; exit 1; }

log() { echo "[$(date '+%F %T')] $*"; }
log "备份开始"

for i in 1 2 3; do
    if mysqldump -uroot mydb | gzip > /backup/mydb-$(date +%F).sql.gz; then
        log "备份成功"
        exit 0
    fi
    log "第 $i 次失败，重试"
    sleep 60
done

log "备份失败"
curl -X POST https://webhook -d '{"msg":"备份失败"}'   # 告警
exit 1
```

```shell
# cron 配置
0 3 * * * /opt/scripts/reliable-backup.sh >> /var/log/backup.log 2>&1
```

### 场景二：检查任务是否在可靠运行

```shell
# 1. 看任务日志
tail -f /var/log/backup.log
# 2. 看锁文件（任务是否在跑）
ls -l /var/lock/backup.lock
# 3. 看任务是否有失败记录
grep '失败' /var/log/backup.log
```

## 性能与调优

```text
1. 重试间隔 —— 间隔太短（如 1 秒）疯狂重试刷日志，60 秒左右合理
2. 日志轮转 —— 任务日志也要配 logrotate，否则长期累积占磁盘
3. 锁粒度 —— 锁文件按任务分开，别多个任务共用一把锁互相阻塞
4. 重试上限 —— 重试设上限（3 次），超限后告警退出，别无限循环
```

## 安全与权限

```text
1. 锁文件权限 —— /var/lock/xxx.lock 别全局可写，防其他进程乱拿锁
2. 通知凭证 —— webhook URL 是敏感信息，别硬编码在可读脚本里
3. 日志脱敏 —— 任务日志可能含敏感数据，权限收紧
4. 执行身份 —— 可靠任务脚本用最小权限用户跑，别一律 root
```

## 故障排查

### 任务重复执行（并发冲突）

```shell
# 1. 看锁文件是否被正确持有
ls -l /var/lock/backup.lock
# 2. 看是否多个进程在跑
ps aux | grep backup.sh
# 3. 确认 flock 参数正确（-n 拿不到锁立即退出）
```

### 任务失败但没告警

```shell
# 1. 看日志确认失败
grep '失败' /var/log/backup.log
# 2. 确认通知逻辑（webhook/邮件）是否真的触发
# 3. 手动触发一次通知验证渠道可用
curl -X POST https://webhook -d '{"msg":"test"}'
```

## 常见问题

```text
Q1: 任务跑太久，下次触发又跑一个怎么办？
A: 加 flock -n 锁文件，拿不到锁就退出，防止并发。

Q2: 任务失败没日志，不知道挂了？
A: 输出没重定向。>> log 2>&1 重定向，定期看日志/配告警。

Q3: 重试没设上限会怎样？
A: 失败后无限重试，刷爆日志/资源。重试设上限（如 3 次）+ 间隔，超限告警退出。

Q4: 任务不幂等，重试导致重复执行？
A: 任务设计成幂等（唯一键/先查后做），或加锁防重入。
```

## 面试题

```text
1. 定时任务为什么需要 flock 锁？
   答：防止上次任务没跑完、下次触发又启动一个，导致并发冲突（资源耗尽/数据错乱）。

2. 定时任务的输出为什么要重定向到日志？
   答：cron 的 stdout/stderr 不重定向会丢（或发到没人看的邮件），失败看不到原因。

3. 失败重试要注意什么？
   答：设上限和间隔，避免疯狂重试；任务要幂等，避免重试重复副作用。

4. 关键任务怎么保证失败能被发现？
   答：日志留痕 + 失败通知（邮件 MAILTO 或 webhook 钉钉/微信）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 定时任务必配 flock 锁，防止并发冲突
2. 任务输出重定向到日志（>> log 2>&1），失败可查
3. 关键任务加失败重试（设上限和间隔）
4. 关键任务失败要通知（邮件/webhook）
5. 任务脚本要幂等（重复执行结果一致），配合锁更安全

### 踩坑记录

```text
坑 1：任务跑太久，下次触发又跑一个，并发冲突
结论：备份任务跑 1 小时，cron 每 30 分钟触发，同时跑两个。
原因：没加任务锁，cron 不管上次跑没跑完。
解法：flock -n 锁文件，拿不到锁就退出。

坑 2：任务失败没日志，不知道挂了
结论：任务静默失败，没人发现。
原因：输出没重定向，报错丢了。
解法：>> log 2>&1 重定向，定期看日志/配告警。

坑 3：重试没设上限，失败就疯狂重试
结论：任务失败后无限重试，刷爆日志/资源。
原因：重试循环没设次数上限。
解法：重试设上限（如 3 次）+ 间隔，超限后告警退出。

坑 4：任务不幂等，重试导致重复执行
结论：任务重试后数据重复（如重复插入、重复发送）。
原因：任务不是幂等的，重试会重复副作用。
解法：任务设计成幂等（用唯一键/先查后做），或加锁防重入。

坑 5：邮件通知没配，MAILTO 写了也收不到
结论：cron 的 MAILTO 设了，但收不到邮件。
原因：系统没配邮件服务（MTA 没装/没配置）。
解法：装 postfix 或用 webhook（钉钉/微信）替代邮件通知。
```
