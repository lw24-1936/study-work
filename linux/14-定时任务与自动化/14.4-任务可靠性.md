## 概述

定时任务在生产环境要「可靠」——任务没跑完不能重复跑（任务锁）、失败要能发现（日志）、失败要能重试（重试）、关键任务要通知（告警）。裸 cron 任务没有这些保障，要靠脚本自己实现。核心四件事：锁（flock 防并发）、日志（重定向留痕）、重试（失败重试）、通知（邮件/webhook）。这是「定时任务能用」到「定时任务可靠」的关键。

```text
任务可靠性四件事：
1. 任务锁 flock —— 防止上次没跑完、这次又启动（并发冲突）
2. 日志重定向 —— 记录执行结果，失败可查
3. 失败重试 —— 失败后重试，提高成功率
4. 邮件/webhook 通知 —— 关键任务失败/完成时通知到人

再加三件进阶：
5. 超时控制 —— 任务挂死要能杀掉（timeout / TimeoutStartSec）
6. 幂等设计 —— 重复执行结果一致，无重复副作用
7. 依赖管理 —— 前置条件检查，依赖不满足不硬跑
```

本机（Ubuntu）实测验证了 flock 锁、timeout 超时、日志模板等核心机制，实测输出见各节「实测（本机）」。

## 核心概念

### 任务锁（flock）

**flock**：基于文件的锁。执行前先拿锁，拿不到就退出（-n 非阻塞）或等待（默认阻塞），防止「上次没跑完，这次又启动」。flock 锁由内核管理：**持有锁的进程退出（无论正常还是被杀），锁自动释放**——这是 flock 相比「pidfile + kill -0 检查」最可靠的地方，不会有锁残留。

```text
flock 关键参数：
flock -n 锁文件 命令    非阻塞：拿不到锁立即失败（返回码 1）
flock -x 锁文件 命令    排他锁（默认就是 -x，可省略）
flock -s 锁文件 命令    共享锁（多个读者可同时持有）
flock -w 10 锁文件 命令 最多等 10 秒，超时失败
锁文件位置：/var/lock/（传统）、/run/lock/（systemd 时代）、
           或任务自己的目录（如 /var/lib/<app>/xxx.lock）
```

### 幂等性

**幂等**：同一个任务重复执行 N 次，结果和只执行 1 次完全一致。定时任务天然会重复触发（cron 触发 + 手动补跑 + 重试），不幂等的任务会重复插入数据、重复发通知、重复扣费。幂等的实现手段：唯一键、先查后做、增量同步、状态文件标记。

### 重试与超时

**重试**：任务因临时故障（网络抖动、依赖服务没就绪）失败时，按间隔重试 N 次，提高成功率。要点：设次数上限 + 间隔，避免疯狂重试刷爆日志。

**超时**：任务挂死（网络 hang、锁等待、死循环）时要能强制终止。shell 层用 `timeout` 命令；systemd 层用 service 的 `TimeoutStartSec` / `TimeoutStopSec`。

### 日志与可观测性

任务输出重定向到日志文件（>> log 2>&1），带时间戳、记录退出码；关键步骤打点。systemd timer 方式的任务输出天然进 journald，`journalctl -u xxx` 可查。日志同样要配 logrotate 轮转（[[13.2-日志轮转与集中]]）。

### 通知与告警

关键任务失败要通知到人：邮件（MAILTO / mail 命令）或 webhook（钉钉、企业微信、Slack 机器人）。webhook 是生产主流——不依赖本地 MTA 配置，直接 HTTP 推送。

### 依赖管理

任务之间有依赖（备份依赖数据库健康、同步依赖网络通）时，先检查前置条件：脚本开头 ping/探活/检查状态文件/锁标记，不满足就跳过或告警，别硬跑。

### 分布式场景的任务唯一性

多台机器同时抢同一个任务（如多节点 cron 都配了同一条），要保证「全局只有一台执行」：分布式锁（Redis SETNX / etcd lease）、数据库行锁（SELECT ... FOR UPDATE）、或 Scheduler 选主。单机场景 flock 足够。

## 工作原理

一个可靠的定时任务脚本，执行流程是「拿锁 → 检查前置 → 执行（带超时与重试）→ 记录结果 → 失败通知」：

```text
可靠任务标准流程：
1. 拿锁：flock -n 抢文件锁，抢不到说明上次还在跑，立即退出（返回码 1）
2. 检查前置：依赖服务/状态文件检查，不满足按策略跳过或告警
3. 执行：核心逻辑包在 timeout 里（防挂死），失败按间隔重试 N 次
4. 记录：每步带时间戳写日志，记录退出码
5. 通知：最终失败时发 webhook/邮件告警（带任务名、时间、错误摘要）
6. 退出码：成功 0，失败非 0 —— cron/timer 靠退出码判断成败
```

cron 只负责「按时触发」，可靠性全靠脚本内部这六步保证；systemd timer 则把「重试/超时/资源限制」下沉到 service 的 Restart / TimeoutStartSec 配置，脚本可以更薄。推荐组合：**systemd timer 负责调度与进程管理，脚本负责业务逻辑与幂等**。

```text
可靠任务流程（精简版）：
拿锁（flock -n）→ 前置检查 → 执行（timeout + 重试 N 次）
→ 记录（时间戳日志 + 退出码）→ 失败通知（webhook/邮件）
```

```text
# 实测（本机）：可靠任务模板完整跑一遍
$ /tmp/reliable-demo.sh; echo "脚本退出码: $?"
[2026-08-19 12:50:55] 任务开始
[2026-08-19 12:50:57] 任务成功完成，退出码 0
脚本退出码: 0
# 并发冲突演示：第一个实例还持有锁时启动第二个
[2026-08-19 12:51:23] 已有任务在运行，退出
第二个实例退出码: 1          # -n 拿不到锁立即退出，防重入生效
# 超时演示：任务超过 timeout 上限被杀死
[2026-08-19 12:51:26] 任务失败（超时/错误），退出码 124   # 124 = timeout 杀死
```

## 常用命令与配置

### flock 锁（实测）

```shell
# 直接包住命令（最常用，适合 cron 条目）
flock -n /var/lock/backup.lock /opt/scripts/backup.sh

# 放进 cron：每 30 分钟触发，跑不完/未完成就跳过本次
# */30 * * * * flock -n /var/lock/backup.lock /opt/scripts/backup.sh >> /var/log/backup.log 2>&1

# 脚本内拿锁（拿锁后执行多步逻辑）
exec 9>/var/lock/mytask.lock
flock -n 9 || { echo "已在运行，退出"; exit 1; }
# ... 任务逻辑（fd 9 持锁直到脚本结束）...
```

```text
# 实测（本机）：flock -n 非阻塞 —— 锁被占用时立即失败
$ flock -n /tmp/test.lock -c 'echo "拿到锁"'
拿锁失败，返回码 1 —— -n 非阻塞立即退出

# 实测（本机）：不带 -n 阻塞等待 —— 等 22 秒直到锁释放
$ time flock /tmp/test.lock -c 'echo "阻塞等待后拿到锁"'
阻塞等待后拿到锁
real	0m22.185s
```

### timeout 超时（实测）

```shell
# 超时杀死（返回码 124 表示超时被杀）
timeout 30 /opt/scripts/sync.sh
# 超时后发信号（默认 TERM，可换 KILL）
timeout -s KILL 30 /opt/scripts/sync.sh
# 超时后按命令退出码判定（命令返回 124 时不误判为超时）
timeout --preserve-status 30 /opt/scripts/sync.sh
```

```text
# 实测（本机）
$ timeout 2 sleep 10; echo "timeout 返回码: $?"
timeout 返回码: 124 （124=超时杀死）
$ timeout 5 sleep 1; echo "返回码: $?"
返回码: 0 （0=正常完成）
# 脚本里判断：$? -eq 124 表示任务超时，区别于任务自身失败
```

### cron 条目标准写法

```shell
# 重定向日志（标准写法，必配）
0 3 * * * /opt/scripts/backup.sh >> /var/log/backup.log 2>&1

# cron 里设 MAILTO（输出发邮件，需系统有 MTA）
MAILTO=admin@example.com
0 3 * * * /opt/scripts/backup.sh
```

```text
# 实测（本机）：无 mail 命令 = 无 MTA，MAILTO 邮件发不出去
$ command -v mail
mail 未安装
# 结论：生产上输出重定向到日志 + webhook 告警，别只依赖 MAILTO
```

### systemd service 的可靠性配置

```text
# /etc/systemd/system/mytask.service —— 重试 + 超时 + 资源限制
[Unit]
Description=My reliable task
After=network-online.target mysql.service

[Service]
Type=oneshot
ExecStart=/opt/scripts/mytask.sh
Restart=on-failure        # 失败自动重启（重试下沉到 systemd）
RestartSec=60             # 重启间隔 60 秒
TimeoutStartSec=300       # 启动超时 5 分钟，超时 SIGKILL
TimeoutStopSec=30
User=taskuser             # 最小权限运行
StandardOutput=journal    # 输出进 journald（可观察性）

[Install]
WantedBy=multi-user.target
```

```text
Restart 取值：
no            失败不重启（默认）
on-failure    非正常退出（非 0）才重启
always        任何退出都重启（含手动 stop）
on-abnormal   信号/超时/看门狗等异常才重启
```

### 任务状态与锁文件查看


## 配置文件解析

可靠任务没有统一配置文件，关键「配置点」散落在脚本、cron 条目和 systemd 单元里。建议把可变参数集中在脚本头部，便于统一调整：

```text
# 脚本头部集中配置（推荐做法）
LOCK_FILE=/var/lock/backup.lock    # 锁文件路径
LOG_FILE=/var/log/backup.log       # 日志文件路径
MAX_RETRY=3                        # 重试次数上限
RETRY_INTERVAL=60                  # 重试间隔（秒）
TASK_TIMEOUT=1800                  # 超时上限（秒）
WEBHOOK_URL=...                    # 告警地址（从密钥管理读取，别硬编码）
```


### systemd service 单元字段

| 字段 | 作用 | 典型值 |
|---|---|---|
| Restart | 失败重启策略 | on-failure |
| RestartSec | 重启间隔 | 60 |
| TimeoutStartSec | 启动超时（超时 SIGTERM→SIGKILL） | 300 |
| TimeoutStopSec | 停止超时 | 30 |
| StartLimitIntervalSec / StartLimitBurst | 防止无限重启风暴 | 60 / 5 |
| StandardOutput=journal | 输出进 journald | journal |
| User / Group | 最小权限运行 | taskuser |
| OnFailure= | 失败时触发另一个 unit（告警） | notify.service |

```text
注意：Restart 只对「非正常退出」生效；Type=oneshot 的任务 ExitCode 非 0
即触发 on-failure 重启。配合 StartLimitBurst 防止任务每次失败都立刻重启、
无限循环把系统打满（重试上限在 systemd 层的体现）。
```

### 任务日志的 logrotate 配置

```text
# /etc/logrotate.d/mytask —— 任务日志同样要轮转
/var/log/backup.log {
    weekly
    rotate 12
    compress
    missingok
    notifempty

```

## 应用场景实战

### 场景一：完整可靠的定时备份任务（锁+日志+超时+重试+告警）

```bash
#!/bin/bash
# /opt/scripts/reliable-backup.sh —— 可靠任务完整模板
set -uo pipefail                      # 不静默吞错（不用 -e，因为要自己处理重试）

LOCK_FILE=/var/lock/backup.lock
LOG_FILE=/var/log/backup.log
MAX_RETRY=3
RETRY_INTERVAL=60
TASK_TIMEOUT=1800
WEBHOOK_URL="${WEBHOOK_URL:-}"        # 从环境/密钥管理注入

# 1. 拿锁（防重入）
exec 9>"$LOCK_FILE"
if ! flock -n 9; then
    echo "[$(date '+%F %T')] 已有备份任务在运行，本次跳过" >> "$LOG_FILE"
    exit 1
fi

# 2. 日志函数（带时间戳，tee 保证日志文件与 stdout 双写）
log() { echo "[$(date '+%F %T')] $*" | tee -a "$LOG_FILE"; }

# 3. 告警函数（webhook 优先，失败再降级邮件）
alert() {
    local msg="$1"
    [ -n "$WEBHOOK_URL" ] && curl -fsS -m 10 -X POST "$WEBHOOK_URL" \
        -H 'Content-Type: application/json' \
        -d "{\"msg\":\"$msg\",\"host\":\"$(hostname)\",\"time\":\"$(date '+%F %T')\"}" \
        >/dev/null 2>&1
}

# 4. 核心任务（可重试，包在 timeout 里）
do_backup() {
    mysqldump -uroot mydb | gzip > /backup/mydb-$(date +%F).sql.gz
}

log "备份任务开始"
ok=0
for ((i=1; i<=MAX_RETRY; i++)); do
    if timeout "$TASK_TIMEOUT" do_backup; then
        ok=1
        break
    fi
    code=$?
    log "第 $i 次尝试失败（退出码 $code），$RETRY_INTERVAL 秒后重试"
    sleep "$RETRY_INTERVAL"
done

# 5. 结果处理
if [ "$ok" -eq 1 ]; then
    log "备份成功"
    exit 0
else
    log "备份失败，已重试 $MAX_RETRY 次"
    alert "备份任务失败：$(hostname) 重试 $MAX_RETRY 次仍失败"
    exit 1
fi
```

```shell
# cron 配置（输出重定向到日志，脚本自己再记一份也无妨）
0 3 * * * /opt/scripts/reliable-backup.sh >> /var/log/backup.log 2>&1
# 或 systemd timer 方式（Restart=on-failure 让 systemd 兜底重试）
# systemctl edit --force --full backup-task.service 后 enable --now backup-task.timer
```

```text

[2026-08-19 12:50:55] 任务开始
[2026-08-19 12:50:57] 任务成功完成，退出码 0
# ② 并发冲突：第二个实例拿不到锁，立即退出（返回码 1）
[2026-08-19 12:51:23] 已有任务在运行，退出
# ③ 超时杀死：timeout 生效，退出码 124

# ④ 日志累积：每次执行都有时间戳留痕，可追溯
```

### 场景二：systemd timer + service 的可靠任务（重试/超时交给 systemd）

```text
# /etc/systemd/system/sync-task.service
[Unit]
Description=Sync task
After=network-online.target
OnFailure=sync-task-fail@%n.service     # 失败触发告警单元

[Service]
Type=oneshot
ExecStart=/opt/scripts/sync.sh
Restart=on-failure
RestartSec=60
TimeoutStartSec=600
User=syncuser
StandardOutput=journal

# /etc/systemd/system/sync-task.timer
[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true                          # 错过补跑
RandomizedDelaySec=300                   # 错峰，避免和别的任务挤

[Install]
WantedBy=timers.target
```

```shell
systemctl daemon-reload
systemctl enable --now sync-task.timer
systemctl list-timers sync-task
journalctl -u sync-task -n 50            # 可观测性：输出全在 journald
```

```text
# 实测（本机）：systemd timer 生态现状（apt-daily、logrotate、anacron 都是这套）
```

### 场景三：失败告警到钉钉/企业微信 webhook

```shell
# 1. 企业微信机器人（群机器人 webhook 地址）
curl -s -X POST "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx" \
  -H 'Content-Type: application/json' \
  -d '{"msgtype":"text","text":{"content":"备份任务失败: host1"}}'

# 2. 钉钉机器人
curl -s -X POST "https://oapi.dingtalk.com/robot/send?access_token=xxx" \
  -H 'Content-Type: application/json' \
  -d '{"msgtype":"text","text":{"content":"备份任务失败: host1"}}'

# 3. 脚本里集成（失败时调，带任务名/时间/退出码）
alert() {
  curl -fsS -m 10 -X POST "$WEBHOOK_URL" \
    -d "{\"msgtype\":\"text\",\"text\":{\"content\":\"$1\"}}" || true
}
alert "备份失败: $(hostname) 退出码 $?"
```

```text
要点：
- webhook URL 是敏感信息：放环境变量/密钥管理（[[22.4-配置与密钥管理]]），
  别硬编码进脚本仓库
- 告警要带上下文：任务名、主机、时间、退出码/错误摘要，否则收到也难定位
- 告警本身要防抖：连续失败只发一次或限频（状态文件记录上次告警时间），
  避免每 30 分钟失败就轰炸群
- 没有 webhook 时兜底：邮件（需 MTA）+ 日志留痕；本机实测无 mail 命令，
  说明邮件方案在精简环境默认不可用，webhook 是更可靠的通道
```

### 场景四：多机抢任务时的分布式锁（唯一执行）

多台服务器都跑同一个 cron，只允许一台实际执行（如定时全量索引重建、批量通知发送）：

```shell
# 方案 A：Redis 分布式锁（SETNX + 过期时间，防锁悬挂）
redis-cli SET task:index_rebuild lock_$(hostname) NX EX 1800
# 返回 OK 才执行；执行完 DEL；EX 过期兜底（进程挂了锁自动过期）

# 方案 B：数据库唯一锁（MySQL）
INSERT INTO task_lock(task_name, owner, locked_at)
  VALUES ('index_rebuild', 'host1', NOW())
  ON DUPLICATE KEY UPDATE owner=IF(locked_at < NOW() - INTERVAL 30 MINUTE,
  VALUES(owner), owner);
# 受影响行数为 1 才执行（拿到锁）

# 方案 C：etcd lease（选主）
# etcdctl lease grant 1800 && etcdctl put /tasks/index_rebuild --lease=<id> $(hostname)
```

```text
分布式锁三原则：
1. 必须有过期时间（TTL/lease），防止持有者崩溃后锁悬挂
2. 执行完必须显式释放（DEL/revoke），提前释放可能造成并发
3. 幂等兜底：即使锁失效并发执行了，任务本身要幂等（见场景五）
单机/同机多实例用 flock 就够了；跨机器才上 Redis/etcd/数据库锁。
```

### 场景五：幂等任务设计（重复执行无副作用）

```shell
# 幂等三招：
# ① 先查后做 —— 已处理过的唯一键直接跳过
mysql -e "INSERT IGNORE INTO sync_log(id, status) VALUES('20260819', 'done')"
[ $? -eq 0 ] && 执行同步 || echo "当天已同步，跳过"

# ② 状态文件标记 —— 文件存在即已执行（配合时间戳）
MARK=/var/lib/mytask/done-$(date +%F)
[ -f "$MARK" ] && { echo "今日已完成，跳过"; exit 0; }
# ... 任务逻辑 ...
touch "$MARK"

# ③ 增量/覆盖式 —— 全量快照 + 唯一键 UPSERT，天然幂等
mysqldump | mysql --replace   # 覆盖导入，跑几次结果一致
```

```text
幂等 + 锁的关系：
锁防「同时执行」（并发），幂等防「重复执行」（顺序重放）。
两者都重要：锁保证同一时刻一个实例，幂等保证即使重放也没副作用。
```

### 场景六：任务依赖管理（前置条件检查）

```shell
#!/bin/bash
# 依赖检查函数：不满足即跳过并告警，不硬跑
check_dep() {
    # 1. 依赖服务探活
    systemctl is-active mysql || { echo "mysql 未运行，跳过"; return 1; }
    # 2. 网络探活（远端依赖）
    curl -fsS -m 5 http://api.internal/healthz || { echo "api 不健康，跳过"; return 1; }
    # 3. 磁盘空间（备份类任务的硬前置）
    avail=$(df --output=avail /backup | tail -1)
    [ "$avail" -gt 1073741824 ] || { echo "备份盘空间不足，跳过"; return 1; }
    # 4. 上游任务完成标记（状态文件）
    [ -f /var/lib/upstream/done-$(date +%F) ] || { echo "上游未完成，跳过"; return 1; }
}
check_dep || exit 0
```

```text
依赖检查的策略：缺依赖时「跳过 + 记录 + 可选告警」，而不是无限重试——
依赖是长时间的（服务没起、磁盘没空间），重试也白搭，等下一个周期更合理。
重试只适合「瞬时抖动」类故障（网络闪断、连接池满）。
```

## 性能与调优

```text
1. 重试间隔 —— 间隔太短（如 1 秒）疯狂重试刷日志，60 秒左右合理；
   瞬时抖动类故障可 30 秒，依赖未就绪类故障重试无意义，直接跳过
2. 重试上限 —— 设上限（3 次），超限后告警退出，别无限循环；
   systemd 层再配 StartLimitBurst 防重启风暴
3. 日志轮转 —— 任务日志也要配 logrotate（weekly + rotate 12 + compress），
   否则长期累积占磁盘；journald 设 SystemMaxUse 上限
4. 锁粒度 —— 锁文件按任务分开，别多个任务共用一把锁互相阻塞；
   同一任务的多个并发窗口才需要共享一把锁
5. 错峰 —— 大批任务用 RandomizedDelaySec（systemd timer）或随机 sleep，
   避免整点/整分集中执行打爆数据库和网络
6. 超时值 —— timeout 比任务最长耗时多留 20-50% 余量；
   备份类大任务 30-60 分钟，同步类 5-10 分钟，别一刀切
7. 锁开销 —— flock 是内核级，开销微秒级，可忽略；
   真正开销在任务本身，别为「省锁」牺牲可靠性
8. 并发度 —— 需要并行跑多份的任务（分区处理）用共享锁 -s 或
   按分区建锁文件（lock-分区1、lock-分区2），别一把锁串行化全部
```

## 安全与权限

```text
1. 锁文件权限 —— /var/lock/xxx.lock 别全局可写，防其他进程乱拿锁/伪造锁；
   建议 0644 root 或任务专属用户，锁目录 0775
2. 通知凭证 —— webhook URL/密钥是敏感信息，别硬编码在可读脚本里；
   从环境变量或密钥管理系统注入（[[22.4-配置与密钥管理]]）
3. 日志脱敏 —— 任务日志可能含敏感数据（SQL、账号、路径），权限收紧
   （640），集中日志链路同样注意（[[13.2-日志轮转与集中]]）
4. 执行身份 —— 可靠任务脚本用最小权限用户跑（User=taskuser），别一律 root；
   只有需要特权操作的（如 systemctl 管理服务）才用 root + sudoers 白名单
5. 脚本防注入 —— set -uo pipefail 防未定义变量静默；输入参数校验；
   不要在脚本里 eval 外部输入
6. 锁的劫持 —— 锁文件被删后新进程能立刻拿锁造成并发：
   用 flock 打开 fd 后不要删锁文件（删除 = 解除保护）；
   共享目录（/tmp）的锁文件用固定权限 + 属主校验
7. 告警信息泄露 —— webhook 推送内容别带完整凭据/内网拓扑细节，
   只给任务名、主机、错误码等最小信息
```

## 故障排查

### 案例一：任务重复执行（并发冲突）

```shell
# 1. 看锁是否被持有、谁持有
lslocks | grep -E 'backup|mytask'
fuser /var/lock/backup.lock
# 2. 看是否有多个实例同时在跑
ps -ef | grep -E 'backup\.sh|mytask'
pgrep -af backup.sh | wc -l
# 3. 检查 flock 参数：-n 没有？→ 默认阻塞等待，排队的实例会堆积
# 4. 检查锁文件是否被误删（删除 = 锁保护失效）
ls -l /var/lock/backup.lock
```

```text
# 实测（本机）：flock -n 冲突时立即失败，返回码 1
拿锁失败，返回码 1 —— -n 非阻塞立即退出
# 对比：不带 -n 会阻塞排队，real 0m22.185s 等到锁释放
# 判断标准：cron 场景必须 -n（错过就跳过），队列场景才考虑阻塞
```

### 案例二：任务失败但没日志

```shell
# 1. 日志文件是否存在、是否有内容
ls -l /var/log/backup.log
# 2. cron 里是否重定向（没重定向 = 输出丢给邮件黑洞）
grep backup /etc/crontab /var/spool/cron/crontabs/* 2>/dev/null
# 3. systemd 方式看 journald
journalctl -u mytask -n 50 --no-pager
# 4. 手动执行脚本复现，对比退出码
/opt/scripts/backup.sh; echo "退出码: $?"
```

```text
排查顺序：先确认「有没有跑」→ 再确认「跑得怎么样」。
有没有跑：日志/时间戳/系统日志；跑得怎么样：日志内容 + 退出码。
本机 anacron 时间戳（/var/spool/anacron/cron.daily）就是「有没有跑」的证据。
```

### 案例三：任务挂死（超时未生效）

```shell
# 1. 确认进程还在（任务挂死 = 进程长期存在不退出）
ps -ef | grep mytask
# 2. 看运行时长（超过预期 = 疑似挂死）
ps -o pid,etime,cmd -p <PID>
# 3. 检查 timeout 是否包住了真正耗时的命令
#    常见错误：timeout 只包了管道前半段，如 timeout 30 mysqldump | gzip ——
#    timeout 只管 mysqldump，gzip 可能还在等输入
#    正确写法：timeout 30 bash -c 'mysqldump | gzip > out.gz'
# 4. systemd 方式检查 TimeoutStartSec 是否配置
systemctl show mytask -p TimeoutStartSec -p Restart
# 5. 手动杀 + 排查原因（网络 hang / 死锁 / 等待不可达资源）
kill -9 <PID> && 查日志定位 hang 点
```

### 案例四：失败后没收到告警

```shell
# 1. 手动触发一次告警验证渠道
curl -X POST "$WEBHOOK_URL" -d '{"msg":"test from host1"}'
# 2. 看脚本里告警条件是否正确（只有最终失败才告警？中间重试也告警？）
grep -n 'alert\|curl' /opt/scripts/backup.sh
# 3. 检查 WEBHOOK_URL 是否注入成功（环境变量空 = 静默跳过告警）
echo "${WEBHOOK_URL:-未设置}"
# 4. 检查告警防抖逻辑是否误伤（上次告警时间戳太新导致本次不发）
# 5. 邮件兜底：确认 MTA 存在（本机实测 mail 未安装 = 邮件通道不可用）
command -v mail
```

### 案例五：重启后任务不执行/不补跑

```shell
# 1. cron 系：cron 不补跑，确认是否走了 anacron
ls /etc/cron.daily/ | grep mytask
cat /var/spool/anacron/cron.daily   # 时间戳是否更新

```

## 常见问题

```text
Q1: 任务跑太久，下次触发又跑一个怎么办？
A: 加 flock -n 锁文件，拿不到锁就退出，防止并发。cron 场景必须 -n
   （错过就跳过），需要排队等执行的场景才考虑不带 -n 阻塞。

Q2: 任务失败没日志，不知道挂了？
A: 输出没重定向。cron 条目加 >> /var/log/xxx.log 2>&1；
   systemd 方式 StandardOutput=journal，journalctl -u xxx 查；
   定期看日志 + 配失败告警。

Q3: 重试没设上限会怎样？
A: 失败后无限重试，刷爆日志/资源，甚至拖垮依赖服务。
   重试设上限（如 3 次）+ 间隔（如 60 秒），超限告警退出；
   systemd 层再配 StartLimitBurst 防重启风暴。

Q4: 任务不幂等，重试导致重复执行？
A: 任务设计成幂等（唯一键/先查后做/状态文件标记/覆盖式导入），
   或加锁防重入。锁防并发，幂等防重放，两者都要。

Q5: 任务挂死怎么防？
A: 命令包 timeout（timeout 1800 cmd），超时返回 124 可识别；
   systemd 方式配 TimeoutStartSec；注意 timeout 要包住整条管道，
   用 timeout N bash -c 'a | b' 的形态。

Q6: 任务失败怎么通知到人？
A: 首选 webhook（钉钉/企业微信/Slack 机器人），不依赖本地 MTA；
   次选邮件 MAILTO（需系统装 MTA，本机实测默认没有 mail 命令）；
   告警带任务名/主机/时间/错误摘要，并做防抖（连续失败限频）。

Q7: 多台机器都跑同一个任务，怎么保证只执行一次？
A: 分布式锁：Redis SETNX+EX、etcd lease、数据库唯一锁；
   锁必须有 TTL 防悬挂，执行完显式释放，任务本身幂等兜底。
   同机多实例用 flock 就够。

Q8: 任务依赖别的服务，服务没起来怎么办？
A: 脚本开头前置检查（探活/状态文件/磁盘空间），不满足就跳过 + 记录 +
   可选告警，别无限重试；瞬时抖动类故障才适合重试。

Q9: 大量任务同时到点，全挤在一起执行？
A: 错峰：systemd timer 用 RandomizedDelaySec=300；
   cron/anacron 用延迟字段或脚本内随机 sleep；
   batch 交给负载调度。

Q10: 任务日志一直涨，磁盘被占满？
A: 任务日志配 logrotate（weekly + rotate N + compress）；
   journald 设 SystemMaxUse 上限；集中日志配保留期。
```

## 面试题

```text
1. 定时任务为什么需要 flock 锁？
   答：防止上次任务没跑完、下次触发又启动一个，导致并发冲突
       （资源耗尽/数据错乱）。flock -n 拿不到锁立即退出，
       锁由内核管理，进程退出自动释放，不会有锁残留。

2. 定时任务的输出为什么要重定向到日志？
   答：cron 的 stdout/stderr 不重定向会丢（或发到没人看的邮件），
       失败看不到原因。重定向到日志（>> log 2>&1）+ 配 logrotate，
       才可观测、可追溯。

3. 失败重试要注意什么？
   答：设上限和间隔，避免疯狂重试刷爆日志；任务要幂等，避免重试
       产生重复副作用；重试只适合瞬时抖动类故障，依赖类故障直接跳过。

4. 任务挂死怎么处理？
   答：timeout 命令包住任务（超时返回 124），systemd 方式配
       TimeoutStartSec；注意 timeout 要包住整条管道命令。

5. 幂等任务怎么设计？
   答：先查后做（唯一键判断）、状态文件标记（done-日期）、
       覆盖式/增量式操作（UPSERT、--replace）、幂等键约束。
       核心：重复执行 N 次结果与执行 1 次一致。

6. 多机任务怎么保证唯一执行？
   答：分布式锁（Redis SETNX + TTL、etcd lease、数据库唯一锁），
       锁带过期时间防悬挂，执行完释放，任务幂等兜底；
       单机场景 flock 足够。

7. systemd timer 比 cron 强在哪（可靠性角度）？
   答：Persistent=true 补跑错过的任务；Restart=on-failure + RestartSec
       把重试下沉到 systemd；TimeoutStartSec 超时控制；RandomizedDelaySec
       错峰；StandardOutput=journal 可观测性；OnFailure 失败联动告警单元。

8. 失败告警方案怎么选？
   答：webhook（钉钉/企业微信/Slack）为主，不依赖本地 MTA；
       邮件为辅（需装 postfix 等）；告警带上下文（任务名/主机/时间/错误）
       并防抖限频；敏感信息不放告警内容。

9. 任务执行结果怎么验证？
   答：退出码（0=成功，非 0=失败，124=超时）+ 日志内容 + 状态文件/
       时间戳（anacron 的 /var/spool/anacron/ 就是例子）+
       数据侧校验（备份文件完整性、行数对比、checksum）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 定时任务必配 flock 锁（-n 非阻塞），防止并发冲突
2. 任务输出重定向到日志（>> log 2>&1），失败可查；日志配 logrotate 轮转
3. 关键任务加失败重试（设上限和间隔），瞬时抖动类故障才重试
4. 任务包 timeout（或 TimeoutStartSec），挂死要能杀
5. 关键任务失败要通知（webhook 优先，邮件兜底），告警带上下文 + 防抖
6. 任务脚本要幂等（重复执行结果一致），配合锁更安全
7. 脚本头部集中配置（锁路径/日志路径/重试参数/超时），`set -uo pipefail`
8. 前置依赖检查（探活/状态文件/磁盘空间），不满足跳过不硬跑
9. 大批任务错峰：RandomizedDelaySec 或随机 sleep
10. 生产任务优先 systemd timer + service（Persistent/Restart/Timeout/journald）
11. 多机抢任务用分布式锁（TTL 防悬挂），任务幂等兜底
12. 验证任务真的成功了：退出码 + 日志 + 数据校验（备份要能恢复，见 [[18.2-数据备份与恢复]]）

### 踩坑记录

```text
坑 1：任务跑太久，下次触发又跑一个，并发冲突
结论：备份任务跑 1 小时，cron 每 30 分钟触发，同时跑两个，数据库被拖垮。
原因：没加任务锁，cron 不管上次跑没跑完。
解法：flock -n 锁文件，拿不到锁就退出；-n 是 cron 场景的必选项。

坑 2：任务失败没日志，不知道挂了
结论：任务静默失败，几天后才发现没备份。
原因：输出没重定向，报错丢了（默认进邮件黑洞）。
解法：>> log 2>&1 重定向，定期看日志/配告警；systemd 方式看 journald。

坑 3：重试没设上限，失败就疯狂重试
结论：任务失败后无限重试，日志暴涨、依赖服务被压垮。
原因：重试循环没设次数上限。
解法：重试设上限（如 3 次）+ 间隔（如 60 秒），超限后告警退出。

坑 4：任务不幂等，重试导致重复执行
结论：任务重试后数据重复（重复插入、重复发邮件）。
原因：任务不是幂等的，重试会重复副作用。
解法：任务设计成幂等（唯一键/先查后做/状态文件），或加锁防重入。

坑 5：邮件通知没配，MAILTO 写了也收不到
结论：cron 的 MAILTO 设了，但收不到邮件。
原因：系统没配邮件服务（MTA 没装/没配置）。本机实测：command -v mail 为空。
解法：装 postfix，或改用 webhook（钉钉/企业微信）告警。

坑 6：timeout 没包住整条管道，超时形同虚设
结论：timeout 30 mysqldump | gzip，mysqldump 被杀但 gzip 还在挂等。
原因：timeout 只作用于管道第一个命令，后面的命令不在控制内。
解法：timeout 30 bash -c 'mysqldump | gzip > out.gz'，包住整条管道。

坑 7：锁文件被删，锁保护失效
结论：任务脚本里顺手 rm 锁文件，下次直接并发跑。
原因：flock 锁绑定的是打开的文件描述符；文件被删后新进程打开新文件
     即拿到「新锁」，旧进程的锁保护作废。
解法：锁文件只创建不删除（留一个空文件占位），或放 /var/lock 由系统管理。

坑 8：多个任务共用一把锁，互相阻塞
结论：任务 A 和任务 B 用同一个 lock 文件，A 跑 2 小时 B 一直被跳过。
原因：锁粒度太大，无关任务互相影响。
解法：每个任务独立锁文件（/var/lock/任务名.lock），锁粒度按任务隔离。

坑 9：Restart=always 配错，服务无限重启风暴
结论：任务脚本 bug 每秒退出，systemd 疯狂拉起，系统负载打满。
原因：Restart=always 任何退出都重启，且没配重启次数限制。
解法：Type=oneshot 用 Restart=on-failure；配 StartLimitIntervalSec/
      StartLimitBurst（如 60 秒内最多 5 次）防风暴。

坑 10：任务补跑没有边界，重放大量旧数据
结论：Persistent=true 补跑时，把停机 3 天积压的数据全重放了一遍。
原因：任务不是增量/幂等的，补跑 = 全量重放。
解法：任务按周期增量（处理「上次到本次」区间），补跑只补缺失区间；
      全量类任务加状态文件/唯一键防重放。

坑 11：多机 cron 都配了同一条任务，重复执行
结论：3 台机器都执行了同一条数据同步任务，数据翻倍。
原因：多机 cron 没有全局唯一性保证。
解法：分布式锁（Redis SETNX+TTL / etcd lease），任务幂等兜底；
      有条件用集中调度器（如 ansible + 单点 cron）。

坑 12：脚本用了 set -e，某步失败整个脚本静默退出
结论：脚本某行返回非 0（如 grep 没匹配），set -e 直接退出，
     后续清理/告警都没执行。
原因：set -e 遇到任何非 0 立即退出，重试/告警逻辑被跳过。
解法：set -uo pipefail（不强制 -e），关键步骤显式 if 判断；
      需要 -e 时对可能失败的命令加 || true 或 if 包裹。
```
