## 概述

cron 是「周期任务」，at 是「一次性任务」——在指定时间执行一次，执行完就没了。at 适合「定时执行一次」的场景（如「30 分钟后重启服务」「今晚 11 点跑一次迁移」）。batch 是 at 的变体（系统负载低时执行）。anacron 是「补跑错过的周期任务」（机器关机没跑的任务，开机后补）。systemd-run 是 systemd 系的「一次性任务」方案（临时 unit），现代系统上比 at 更值得优先考虑。

```text
任务体系全景：
1. cron —— 周期任务（每天/每小时重复）
2. at  —— 一次性任务（指定时间执行一次）
3. batch —— at 变体（系统负载低时执行）
4. anacron —— 补跑错过的周期任务（关机期间没跑的任务）
5. systemd-run —— systemd 的一次性/定时任务（临时 unit）
```

```text
# 实测（本机，Ubuntu，at 未安装）
$ command -v at && echo 已安装 || echo "at 未安装"
at 未安装
$ command -v atq atrm batch || echo "atq/atrm/batch 同样未安装"
atq/atrm/batch 同样未安装
$ systemctl status atd
Unit atd.service could not be found.
# at 不是 Ubuntu 默认安装，用前需 apt install at
$ apt-cache policy at
at:
  已安装：(无)
  候选： 3.2.5-2.1ubuntu3
```

本机 at 未安装，因此本笔记中 at/atq/atrm/batch 的命令输出标为「示例」，systemd-run 相关全部为真实实测输出。

## 核心概念

### at 与 atd

**at**：在指定时间执行一次命令。`at 时间` 进入交互模式输入命令，或用管道/文件传入命令，到点执行，执行完任务就从队列消失。at 适合「精确到分钟的一次性调度」。

**atd 守护进程**：at 的后台服务（atd.service），负责维护队列、到点派发任务。at 命令只是「提交端」，真正干活的是 atd。atd 没启动，at 任务提交后永远不会执行。

### batch

**batch**：at 的变体，不指定时间，在「系统负载低时」执行（默认系统平均负载低于 1.5 时触发），适合不紧急的耗时任务（如凌晨的批量压缩、数据归档）。Ubuntu 上 batch 是 at 包提供的符号链接。

### 队列字母与优先级

at 的队列以字母区分，a 队列优先级最高，z 最低。默认队列是 a：

```text
队列字母：a（默认，最高）→ b → c → … → z（最低）
-l 小写字母队列优先级高于大写；大写字母队列在低优先级用户使用时受限
用途：-q 参数指定队列，如 at -q b 15:00
高优先级队列的任务先执行；队列字母也影响 batch（默认队列 b）
```

### anacron

**anacron**：解决 cron 的缺陷——机器关机错过了任务不补跑。anacron 记录上次执行时间（/var/spool/anacron/ 下的时间戳文件），开机时检查并补跑错过的任务。因此 anacron 只支持「每天/每周/每月」粒度（分钟级没意义，因为只在开机时检查）。

### systemd-run 与临时 unit（Transient Unit）

**systemd-run**：不用写 unit 文件，直接在命令行定义一个临时 unit（transient unit）执行命令。配合 `--on-active=` / `--on-calendar=` 可以创建「一次性/定时」任务：

```text
systemd-run 一次性任务的两大用法：
--on-active=1h  在 1 小时后执行一次（相对时间，类似 at now + 1 hour）
--on-calendar="..."  按日历时间执行（类似 at 的绝对时间）
```

临时 unit 活在内存（/run/systemd/transient/），不写磁盘配置；`--collect` 让执行完的 unit 自动回收。与 at 最大的区别：**at 的队列在重启后丢失（除非持久化），systemd-run 创建的 timer 也会随重启丢失（除非写成正式 unit 文件）**——需要跨重启的任务应该写正式的 .timer/.service 文件（见 [[14.2-systemd timer]]）。

### at 时间语法

```text
at 时间格式（核心）：
now + 30 minutes      30 分钟后（minutes/hours/days/weeks 均支持）
now + 2 hours         2 小时后
23:00                 今晚 23 点（如果已过，则为明天 23 点）
02:00 08/20           8 月 20 号 2 点（月/日）
midnight / noon / teatime   午夜 / 正午 / 下午 4 点
tomorrow / tomorrow 10:00   明天 / 明天上午 10 点
next week             下周同一天
08/20/2026            2026 年 8 月 20 日 00:00
```

## 工作原理

### atd 的调度流程

at 任务提交后，命令被序列化（命令 + 环境变量 + 工作目录 + umask 等）存成 /var/spool/at/ 下的队列文件；atd 每分钟醒来检查一次队列，把「到点」的任务取出来，以**提交时的用户身份**在新 shell 中执行，执行完删除队列文件。

```text
at 工作流程：
提交 at 任务 → 序列化存 /var/spool/at/ 队列文件 → atd 每分钟轮询
→ 到点 → 以提交用户身份执行 → 删除队列文件

at 队列文件内容（序列化）：
- 要执行的命令（保存在队列文件头部）
- 环境变量快照（PATH、HOME、SHELL、LOGNAME、umask、当前工作目录）
- 邮件通知设置
```

### at 任务的执行环境

at 任务执行时的工作目录是**提交时的当前目录**，环境是提交时的环境快照（不是 atd 的环境）。所以脚本里依赖的相对路径、环境变量要谨慎——建议在命令里用绝对路径或显式 cd。

### anacron 的补跑机制

anacron 不追求精确时间：它记录每个任务上次执行的时间戳（/var/spool/anacron/），开机时检查「哪些任务距离上次执行已超过周期」，超过就补跑。Ubuntu 上 anacron 由 anacron.timer（每小时）或 /etc/cron.d/anacron 触发；RHEL 系由 cronie-anacron 通过 /etc/cron.hourly/0anacron 触发。

```text
anacron 补跑流程：
开机/每小时触发 → 对比上次执行时间戳 → 超过周期的任务补跑 → 更新时间戳
```

### systemd-run 临时 unit 的生命周期

```text
systemd-run --on-active=3s --unit=xxx --collect '命令'
→ 创建 xxx.timer（Transient）+ xxx.service（Transient）
→ 时间到 → 启动 xxx.service 执行命令
→ 执行完 → service 进入 dead → --collect 自动回收 unit
→ 期间输出进 journald，可用 journalctl -u xxx 查看
```

### at 与 systemd-run 的持久性对比

| 维度 | at（atd） | systemd-run 临时 unit | 正式 .timer 文件 |
|---|---|---|---|
| 定义方式 | at 命令提交 | 命令行即建即用 | 写 unit 文件 |
| 执行精度 | 分钟级 | 秒级（--on-active） | 秒级 |
| 重启后 | 队列丢失 | 临时 unit 丢失 | **保留并继续调度** |
| 输出去向 | 邮件（默认） | journald | journald |
| 权限控制 | at.allow/at.deny | 需要 root 或 systemd 权限 | 文件权限 |
| 适合场景 | 一次性临时任务 | 临时/脚本化一次性任务 | 生产级周期任务 |

## 常用命令与配置

### at 提交任务

```shell
# 交互式提交（输入命令后 Ctrl+D 结束）
at 23:00
at> /opt/scripts/maintenance.sh
at> <Ctrl+D>

# 管道传命令（脚本化推荐）
echo "systemctl restart nginx" | at now + 30 minutes

# 从文件读命令
at 02:00 < /tmp/job-commands.txt

# 指定队列和参数
at -q b -m 23:00 <<< "/opt/scripts/cleanup.sh"   # -m：即使无输出也发邮件
```

```text
# 示例（本机未安装 at，以下为典型输出形态）
$ echo "echo hello > /tmp/at-test.txt" | at now + 1 minute
warning: commands will be executed using /bin/sh
job 5 at Wed Aug 19 12:55:00 2026
```

### atq 查看队列

```text
# 示例：atq 输出字段解读（job 编号 / 执行时间 / 队列）
$ atq
5	Wed Aug 19 12:55:00 2026 a root
7	Wed Aug 19 23:00:00 2026 b root
# 字段：任务号  执行时间  队列字母  提交用户
# atq -q b 只看 b 队列；atq -o 只看已过期的任务
```

### atrm 删除任务

```shell
atrm 5          # 删除 5 号任务
atrm 5 7        # 同时删除多个
# 只想删自己队列的：atrm 只允许删除自己提交的任务（root 可删全部）
```

### batch 提交

```shell
echo "/opt/scripts/big-compress.sh" | batch   # 负载低于阈值时执行
# 交互式：直接输 batch 回车
```

### systemd-run 一次性任务（本机实测）

```shell
# 3 秒后执行一次（实测，--collect 执行完自动回收）
systemd-run --on-active=3s --unit=test-once-job --collect \
    /bin/sh -c 'echo "one-shot job ran at $(date)"'

# 按日历时间执行一次（实测：几秒后的绝对时间）
systemd-run --on-calendar="2026-08-19 12:49:12" --unit=test-cal-job --collect \
    /bin/sh -c 'echo "calendar job ran at $(date)"'

# 查看临时 timer
systemctl list-units --type=timer | grep test-once
# 查看任务输出
journalctl -u test-once-job
```

## 配置文件解析

### /etc/at.allow 与 /etc/at.deny

at 的权限控制就两个文件，逻辑（man at 的标准行为）：

```text
优先级从高到低：
1. /etc/at.allow 存在 → 只有名单内的用户能用 at（白名单）
2. at.allow 不存在，/etc/at.deny 存在 → 名单内的用户不能用（黑名单）
3. 两个文件都不存在 → 默认行为（多数实现仅 root 可用，
   部分发行版编译配置为所有用户可用）
```

```text
# 实测（本机 Ubuntu，at 未安装，但可确认默认不带权限文件）
$ ls /etc/at.deny /etc/at.allow
ls: 无法访问 '/etc/at.deny': 没有那个文件或目录
ls: 无法访问 '/etc/at.allow': 没有那个文件或目录
```

### /var/spool/at/ 队列目录

```text
/var/spool/at/        atd 的任务队列目录（每个任务一个文件）
/var/spool/at/.SEQ    at 任务编号计数器
权限：目录 700 root，普通用户不可读，防任务内容泄露
系统重启后 atd 会清空该队列（一次性任务不跨重启）
```

### /etc/anacrontab

anacron 的配置在 /etc/anacrontab（Ubuntu 与 RHEL 格式一致）：

```text
# 实测（本机 /etc/anacrontab 原文）
SHELL=/bin/sh
HOME=/root
LOGNAME=root

# These replace cron's entries
1	5	cron.daily	run-parts --report /etc/cron.daily
7	10	cron.weekly	run-parts --report /etc/cron.weekly
@monthly	15	cron.monthly	run-parts --report /etc/cron.monthly
```

```text
字段含义（周期 延迟 任务名 命令）：
周期（天）   超过这个天数没跑就补跑（1 = 每天；7 = 每周；@monthly = 每月）
延迟（分钟） 开机后延迟多久执行（避免开机瞬间集中跑打爆 IO）
任务名      时间戳文件名（/var/spool/anacron/任务名）
命令        执行什么（通常 run-parts 跑目录下脚本）
```

```text
# 实测（本机 /etc/cron.d/anacron：每小时触发一次 anacron 检查）
30 7-23 * * *	root	[ -x /etc/init.d/anacron ] && if [ ! -d /run/systemd/system ]; then /usr/sbin/invoke-rc.d anacron start >/dev/null; fi
# systemd 环境下由 anacron.timer 触发（见前面 list-timers 实测），此条目是 SysV 兼容路径
```

```text
# 实测（本机 /var/spool/anacron/：时间戳文件，记录每个任务上次执行）
$ ls -la /var/spool/anacron/
-rw------- 1 root root    9  8月 19 07:39 cron.daily
-rw------- 1 root root    9  8月 18 07:49 cron.monthly
-rw------- 1 root root    9  8月 16 07:44 cron.weekly
# 权限 600，只有 root 可读写；内容就是上次执行的时间戳
```

### Red Hat 系差异

```text
1. 包名：Ubuntu/Debian 用 apt install at；RHEL/CentOS 用 dnf install at（服务同为 atd）。
   老资料里出现的「atd 包」是不同发行版/时代的历史命名，以本发行版仓库为准。
2. batch：两系都由 at 包提供（/usr/bin/batch 是符号链接），行为一致。
3. at.allow/at.deny 默认策略：Ubuntu 默认不带这两个文件（按编译配置决定默认权限）；
   RHEL 系同样默认不带，但生产环境建议显式创建 /etc/at.allow 白名单，
   消除「两个文件都不存在时默认仅 root 可用」的歧义。
4. anacron 触发机制差异：
   - Ubuntu/Debian：独立 anacron 包，由 systemd 的 anacron.timer（每小时）触发；
     非 systemd 环境走 /etc/cron.d/anacron。
   - RHEL/CentOS：cronie-anacron 随 cronie 安装，由 crond 开机时执行
     /etc/cron.hourly/0anacron 脚本调用 /usr/sbin/anacron -s。
   - 两者都读 /etc/anacrontab，格式完全一致。
```

## 应用场景实战

### 场景一：数据库维护窗口（at 定时执行一次）

数据库每周日凌晨有维护窗口，用 at 提交一次性维护任务：

```shell
# 1. 写维护脚本（绝对路径 + 日志重定向）
cat > /opt/scripts/db-maintain.sh <<'EOF'
#!/bin/bash
log=/var/log/db-maintain.log
echo "[$(date '+%F %T')] 开始重建索引" >> $log
mysql -uroot mydb -e "OPTIMIZE TABLE orders, users;" >> $log 2>&1
echo "[$(date '+%F %T')] 结束" >> $log
EOF
chmod +x /opt/scripts/db-maintain.sh

# 2. 提交到周日凌晨 2 点执行
echo "/opt/scripts/db-maintain.sh" | at 02:00 Sunday

# 3. 确认队列
atq

# 4. 改主意了直接删除
atrm <任务号>
```

```text
要点：
- 脚本里用绝对路径，因为 at 执行时的工作目录是「提交时目录」
- 输出重定向到日志文件，别依赖 at 的默认邮件
- 周一检查 atq 确认任务已消失（执行完成），并看日志验证结果
```

### 场景二：发布窗口临时放行 / 定时重启服务（systemd-run）

上线发布时，用 systemd-run 安排「30 分钟后自动重启服务」的临时任务，发布完成手动取消：

```shell
# 1. 30 分钟后重启 nginx（相对时间，--on-active）
sudo systemd-run --on-active=30min --unit=release-restart-nginx \
    --collect systemctl restart nginx

# 2. 发布提前完成，取消任务
sudo systemctl stop release-restart-nginx.timer
sudo systemctl reset-failed release-restart-nginx

# 3. 用 --on-calendar 安排绝对时间（今晚 23:00）
sudo systemd-run --on-calendar="23:00:00" --unit=night-cleanup \
    --collect /opt/scripts/cleanup.sh

# 4. 查看任务输出
journalctl -u release-restart-nginx
```

```text
systemd-run 时间单位速记：
--on-active=30min / 1h / 90s     相对时间（类似 at now + N）
--on-calendar="23:00:00"         绝对时间（类似 at 23:00）
--on-calendar="Mon *-*-* 02:00:00"  每周一凌晨 2 点
--on-active 精度到秒，比 at 的分钟级更精确
```

### 场景三：批量机器上一次性执行（ssh + at）

多台服务器都要在今晚跑一次清理，不用一台台登进去：

```shell
# 1. 对每台机器提交 at 任务（先确保 at 已安装且 atd 在跑）
for host in web1 web2 web3; do
    ssh "$host" "echo '/opt/scripts/clear-tmp.sh' | at 23:30"
done

# 2. 统一验证（所有机器 23:30 各有一单）
for host in web1 web2 web3; do
    ssh "$host" "atq"
done

# 3. 次日确认全部执行完（队列应为空）
for host in web1 web2 web3; do
    ssh "$host" "atq | wc -l"
done
```

```text
注意：ssh 提交 at 时，命令里的环境是 ssh 会话环境；
批量场景建议把任务封装成脚本文件分发，避免环境不一致。
```

### 场景四：batch 做低峰期耗时任务

不紧急的耗时任务（批量压缩、数据归档），用 batch 等系统空闲时执行：

```shell
# 1. 提交 batch 任务（默认负载低于 1.5 时执行）
echo "/opt/scripts/compress-archives.sh" | batch

# 2. 查看 batch 队列（默认在 b 队列）
atq -q b

# 3. 想快点跑：把队列优先级调高
echo "/opt/scripts/compress-archives.sh" | at -q a -t batch
```

```text
batch 判定：系统平均负载（loadavg 1 分钟值）低于阈值（默认 1.5）就执行；
生产环境负载常年 >1.5 时 batch 任务会一直积压，用 atq -q b 检查积压量。
```

### 场景五：anacron 保证「每天必跑」的周期任务

备份这类「必须每天执行、错过要补」的任务，放 /etc/cron.daily/ 交给 anacron：

```shell
# 1. 写脚本
cat > /opt/scripts/daily-backup.sh <<'EOF'
#!/bin/bash
tar czf /backup/data-$(date +%F).tar.gz /data 2>> /var/log/backup.log
EOF
chmod +x /opt/scripts/daily-backup.sh

# 2. 放到 /etc/cron.daily/（anacron 保证每天执行，关机错过开机补跑）
cp /opt/scripts/daily-backup.sh /etc/cron.daily/

# 3. 验证：看 anacron 时间戳是否每天更新
cat /var/spool/anacron/cron.daily
```

```text
anacron 的「保证执行」不等于「准点执行」：开机补跑有延迟（/etc/anacrontab 的
延迟字段），且只到天级粒度；对执行时间敏感的任务别用 anacron。
```

## 性能与调优

```text
1. 延迟执行 —— anacron 的「延迟」字段让任务错开开机瞬间，避免集中跑打爆 IO；
   大批任务建议错开 5-30 分钟
2. batch 择机 —— 耗时不紧急的任务用 batch，系统空闲时再跑，不抢业务资源；
   负载阈值可调（部分实现支持 -l 参数或编译时阈值）
3. 队列清理 —— at 队列文件执行完自动删，无需手动维护；
   长期不清理的唯一情况：atd 挂了任务积压，先救 atd
4. 任务合并 —— 多个一次性任务别拆太碎，能合并成一个脚本一次执行，
   减少 atd 轮询和队列文件开销
5. 错峰 —— 大批量一次性任务（发布窗口、批量机器）用 atq 检查是否有积压，
   积压时按优先级队列（-q）排队，避免同一时刻打爆目标服务
6. atd 轮询 —— atd 每分钟轮询一次队列，任务精确度是分钟级；
   需要秒级精度的用 systemd-run（--on-active 精确到秒）
```

## 安全与权限

```text
1. at.allow/at.deny —— 控制谁能用 at：
   生产环境建议显式建 /etc/at.allow（白名单，至少含 root），
   比依赖「两个文件都不存在」的默认行为更可控
2. 执行身份 —— at 任务以提交时的用户身份执行，别用 root 提交不必要任务；
   systemd-run 默认以 root 运行（系统服务），非 root 用户用需要授权
3. 队列文件权限 —— /var/spool/at/ 权限 700 且属 root，任务内容防泄露；
   at 提交的命令会以明文序列化存储在队列文件里，别放密码/token
4. 敏感命令 —— 队列文件里能看到命令全文，含密钥的命令别走 at；
   密钥放受限权限的文件里，脚本运行时读取
5. systemd-run 的权限 —— 创建系统级临时 unit 需要 root；
   普通用户默认只能创建自己的 user 级 unit（systemctl --user）
6. 邮件泄露 —— at 任务输出默认发邮件，输出里可能有敏感信息；
   统一重定向到权限收紧的日志文件
```

```text
Red Hat 系差异：RHEL 的 man at 明确两个文件都不存在时默认仅 root 可用；
Ubuntu 系历史上默认带空 /etc/at.deny（= 所有用户可用），新版不带。
生产环境按「白名单优先」原则显式创建 at.allow，两系行为就一致了。
```

## 故障排查

### 案例一：at 任务没执行

```shell
# 1. 确认 atd 服务在跑（最常见原因：atd 没启动）
systemctl status atd
systemctl enable --now atd

# 2. 看任务是否还在队列（在队列 = 没到点；不在 = 已执行或已丢失）
atq

# 3. 看 atd 日志
journalctl -u atd -n 50

# 4. 确认提交的时间解析是否正确（回显的 job 时间对不对）
echo "cmd" | at now + 5 minutes
# 如果回显时间不对，说明时间语法写错，先 atrm 再重新提交
```

```text
# 实测（本机 Ubuntu 未装 at）：atd 服务不存在
$ systemctl status atd
Unit atd.service could not be found.
# 需要先 apt install at，安装后 atd 会自动启用；安装后确认：
# systemctl status atd 显示 active (running)
```

### 案例二：at 任务执行了但看不到结果

```shell
# 1. at 输出默认发邮件（系统可能没配 MTA），改重定向到日志
echo "cmd > /var/log/at-task.log 2>&1" | at now + 5 minutes
# 2. 确认任务已执行（队列中消失）
atq
# 3. 检查输出文件
tail -20 /var/log/at-task.log
# 4. 检查邮件队列（如果配了 MTA）
mailq
```

```text
# 实测（本机）：系统无 mail 命令，无 MTA —— 依赖邮件收 at 输出必然失败
$ command -v mail
mail 未安装
# 结论：at/batch 任务输出一律重定向到日志文件，别指望邮件
```

### 案例三：at 权限被拒（Permission denied）

```shell
# 1. 复现
echo "cmd" | at now + 5 minutes
# 报错：You do not have permission to use at.
# 2. 检查权限文件
cat /etc/at.allow /etc/at.deny
# 3. 判断：at.allow 存在但当前用户不在名单 → 加白名单
echo "appuser" >> /etc/at.allow
# 4. 或 at.deny 里有当前用户 → 从 at.deny 移除
sed -i '/^appuser$/d' /etc/at.deny
```

### 案例四：系统重启后 at 队列丢失

```shell
# 现象：重启后 atq 为空，之前提交的任务全没了
# 原因：atd 的一次性队列不持久化，重启即清空（设计如此）
# 排查：journalctl -b -1 -u atd  看上次启动时的清理日志
# 解法：跨重启的任务改用正式 systemd timer 文件（Persistent=true 可补跑）
#       或把 at 任务放进系统启动后自动重新提交的机制（如 rc.local）
```

```text
判断原则：
- 只在本机运行期内执行一次 → at / systemd-run --on-active 均可
- 重启后还要执行 / 错过要补跑 → 正式 .timer + Persistent=true（[[14.2-systemd timer]]）
```

### 案例五：batch 任务一直不执行

```shell
# 现象：batch 提交了，队列里一直有，就是不执行
# 1. 看 batch 队列积压
atq -q b
# 2. 看系统负载（batch 要负载 < 1.5 才执行）
uptime
# 3. 负载常年高 → batch 永远轮不到；改用 at 指定低峰时间
echo "cmd" | at 04:00
# 4. 负载正常却不执行 → 查 atd 是否在跑、日志有无报错
systemctl status atd && journalctl -u atd -n 50
```

## 常见问题

```text
Q1: at 命令不存在？
A: at 不是默认安装。Ubuntu: apt install at；RHEL: dnf install at。
   安装后确认 atd 服务已启动（systemctl status atd）。

Q2: at 任务提交成功但到点没执行？
A: 依次查：atd 服务是否在跑；atq 任务是否还在（在=没到点/没到执行条件）；
   journalctl -u atd 有无报错；时间语法是否写错（回显时间对不对）。

Q3: at 任务执行了但看不到结果？
A: at 输出默认发邮件（系统没配 MTA 就丢了）。命令里重定向输出到日志
   （> /var/log/xxx.log 2>&1），并确认日志文件权限可写。

Q4: 系统重启后 at 任务没了？
A: 正常。atd 的一次性队列不持久化，重启即清空。需要跨重启的任务用
   正式 systemd timer 文件（Persistent=true），别用 at。

Q5: 笔记本/服务器关机错过 cron 任务，开机后没补跑？
A: cron 不补跑错过的任务。用 anacron（/etc/cron.daily/ 等）或
   systemd timer 的 Persistent=true。

Q6: anacron 能配分钟级任务吗？
A: 不能。anacron 只在开机/每小时检查一次，只支持每天/每周/每月粒度。
   分钟级用 cron 或 systemd timer。

Q7: at 和 systemd-run 怎么选？
A: 临时、一次性、分钟级精度 → at（或 systemd-run --on-active 秒级）；
   需要日志进 journald、可 scriptable → systemd-run；生产级持久任务 → 正式 timer 文件。

Q8: batch 和 at 的区别？
A: batch 是 at 的变体：不指定具体时间，系统负载低于阈值（默认 1.5）时执行，
   适合不紧急的耗时任务；at 指定精确时间，适合有明确时间要求的一次性任务。
```

## 面试题

```text
1. at 和 cron 的区别？
   答：cron 是周期任务（按分钟/小时/天重复执行）；at 是一次性任务
       （指定时间执行一次，执行完即从队列删除）。cron 靠 crond，at 靠 atd。

2. at 任务的执行流程是什么？
   答：at 提交命令序列化到 /var/spool/at/ 队列文件；atd 每分钟轮询队列，
       到点以提交用户的身份在新 shell 中执行；执行完删除队列文件。
       输出默认通过邮件发给提交用户。

3. at 的权限控制怎么实现？
   答：/etc/at.allow 白名单优先：存在则只有名单内用户可用；
       否则查 /etc/at.deny 黑名单，名单内用户被拒绝；
       两个文件都不存在时默认行为取决于发行版（多数仅 root 可用）。

4. anacron 解决什么问题？为什么它不支持分钟级任务？
   答：解决机器关机错过 cron 周期任务不补跑的问题——它记录上次执行时间戳，
       开机时对比并补跑超期任务。因为只在开机/每小时检查，所以只支持
       每天/每周/每月粒度，分钟级精度没有意义。

5. batch 和 at 有什么区别？
   答：batch 是 at 的变体，不指定具体时间，系统平均负载低于阈值
       （默认 1.5）时才执行，适合不紧急的耗时任务；at 指定精确时间。

6. 系统重启后 at 任务会怎样？怎么保证任务不丢？
   答：atd 的一次性队列不持久化，重启后 at 队列清空。跨重启的任务
       要写成正式的 systemd timer + service 文件，用 Persistent=true
       支持错过补跑（见 [[14.2-systemd timer]]）。

7. systemd-run 怎么实现一次性任务？和 at 相比有什么优势？
   答：systemd-run --on-active=1h 'cmd' 创建临时 timer+service unit，
       --collect 执行完自动回收。优势：秒级精度、输出进 journald 可查、
       与 systemd 生态统一（cgroup 管理、依赖控制）；劣势：临时 unit 不持久。

8. at 任务输出默认去哪？生产上怎么处理？
   答：默认通过邮件发给提交用户；系统没配 MTA 时输出丢失。
       生产上在命令里重定向输出到日志文件（>> /var/log/xxx.log 2>&1），
       并用日志轮转管理（见 [[13.2-日志轮转与集中]]）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 「精确执行一次」用 at 或 systemd-run，「周期执行」用 cron，「保证执行」用 anacron，「持久+补跑」用 systemd timer（Persistent=true）
2. at 不是默认安装，用前 apt/dnf install at，并确认 atd 服务在跑
3. at 命令用管道传（echo "cmd" | at time）比交互式更适合脚本化
4. at 命令全部用绝对路径（脚本路径、输出重定向路径），因为执行环境是提交时快照
5. at 任务输出一律重定向到日志文件（> /var/log/xxx.log 2>&1），别依赖邮件
6. 桌面/笔记本（常关机）的周期任务放 /etc/cron.daily/ 用 anacron 保证补跑
7. 一次性任务优先考虑 systemd-run：秒级精度、journald 留痕、可脚本化
8. 生产环境显式创建 /etc/at.allow 白名单（含 root），权限控制不靠默认行为
9. 敏感信息（密码/token）不进 at 命令文本，放受限文件运行时读取
10. 跨重启必须执行的任务写成正式 unit 文件，不用 at/临时 systemd-run

### 踩坑记录

```text
坑 1：at 命令不存在
结论：敲 at 报 command not found。
原因：at 不是 Ubuntu/RHEL 默认安装。
解法：apt install at 或 dnf install at，装完确认 atd 服务启动。

坑 2：at 任务到点没执行
结论：atq 显示任务还在，时间到了也不执行。
原因：atd 服务没跑（装完 at 后没启动，或被 stop/disable）。
解法：systemctl enable --now atd，再看 journalctl -u atd 有无报错。

坑 3：at 任务执行了但看不到结果
结论：at 到点执行了，但不知道成功还是失败。
原因：at 输出默认发邮件，系统没配 MTA 输出直接丢。
解法：at 命令里重定向输出到日志（> /var/log/at.log 2>&1），别依赖邮件。

坑 4：at 权限被拒
结论：echo "cmd" | at time 报 You do not have permission to use at.
原因：at.allow 白名单没有当前用户，或 at.deny 黑名单里有。
解法：按白名单优先原则，把需要的用户加进 /etc/at.allow。

坑 5：系统重启后 at 队列全丢
结论：重启后 atq 为空，之前提交的任务一个没执行。
原因：atd 的一次性队列不持久化，重启即清空（设计如此）。
解法：跨重启任务写正式 systemd timer 文件；重启后需要自动补的执行
      安排进开机启动流程。

坑 6：cron 任务在关机时错过，以为会补跑
结论：笔记本关机错过 cron 任务，开机后没补跑。
原因：cron 不补跑错过的任务（这是 anacron 的职责）。
解法：用 anacron（/etc/cron.daily/ 等），或 systemd timer 的 Persistent=true。

坑 7：anacron 不支持分钟级任务
结论：想在 anacron 里配「每 5 分钟」任务，不生效。
原因：anacron 只在开机/每小时检查，只支持每天/每周/每月粒度。
解法：分钟级任务用 cron 或 systemd timer。

坑 8：at 时间写错，任务在错误时间执行
结论：任务提前/延后执行，或执行时间完全不对。
原因：at 的时间解析有规则（23:00 已过会顺延到明天等），写错不报错。
解法：提交时看回显的 job 时间确认，atq 复核，错了 atrm 重提。

坑 9：脚本里用相对路径，at 执行时找不到文件
结论：任务执行失败，报 No such file or directory。
原因：at 执行时工作目录是提交时目录的快照，可能和预期不同。
解法：脚本和命令全部用绝对路径，必要时脚本开头显式 cd。

坑 10：batch 任务一直积压不执行
结论：batch 提交的任务在队列里躺了几天。
原因：生产负载常年高于 batch 阈值（默认 1.5），batch 永远轮不到。
解法：atq -q b 查积压；紧急的直接 atrm 改 at 指定低峰时间；
      常态化的挪到 cron/timer 低峰时段。
```
