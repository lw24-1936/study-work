## 概述

cron 是 Linux 最经典的定时任务系统：按「分 时 日 月 周」时间表周期执行命令（每天备份、每小时清理、每分钟心跳）。它由一个常驻守护进程 crond 驱动，每分钟醒来一次，把「当前分钟匹配」的任务取出来执行。

配置分两大类：**用户级**（`crontab -e`，每个用户维护自己的任务，以该用户身份执行）和**系统级**（`/etc/crontab`、`/etc/cron.d/`、`/etc/cron.hourly|daily|weekly|monthly/`，可指定执行用户）。crontab 语法是「五段式时间 + 命令」，另有 `@daily`/`@reboot` 等特殊字符串快捷写法。

cron 最需要记住的三个特性：环境变量极简（不读 .bashrc，PATH 精简）、输出默认发邮件（没配 MTA 就丢）、只按墙钟匹配（无补跑机制，错过就错过）。

```text
cron 定时任务系统：
1. 用户级 —— crontab -e 编辑自己的任务，crontab -l 查看
2. 系统级 —— /etc/crontab、/etc/cron.d/*、/etc/cron.daily/ 等
3. 语法 —— 分 时 日 月 周 + 命令（五段式）
4. 特殊字符串 —— @daily/@hourly/@reboot 快捷写法
5. 机制 —— crond 每分钟扫描一次，匹配则 fork 子进程执行
```

## 核心概念

### crontab 五段式语法

每一行 crontab 是「五段式时间 + 命令」，顺序固定为「分 时 日 月 周」：

```text
分  时  日  月  周   命令
*   *   *   *   *   /usr/bin/command args
```

| 字段 | 位置 | 取值范围 | 说明 |
|---|---|---|---|
| 分 minute | 第 1 段 | 0-59 | 允许步长，如 */5 = 每 5 分钟 |
| 时 hour | 第 2 段 | 0-23 | 0 点是 00，24 非法 |
| 日 day of month | 第 3 段 | 1-31 | 与「周」同时非 * 时是 OR 关系（见下文坑） |
| 月 month | 第 4 段 | 1-12 或 JAN-DEC | 支持英文缩写 jan,feb,... |
| 周 day of week | 第 5 段 | 0-7 或 SUN-SAT | 0 和 7 都表示周日 |

周字段是新手最常踩的：**0 和 7 都是周日**（0-6 是周日到周六，7 是周日的别名），不是「7 = 周六」。月/周字段支持英文缩写（JAN-DEC、SUN-SAT），大小写不敏感。

```text
crontab 五段式示例：
0  3  *  *  *      每天 3:00
*/5 * * * *        每 5 分钟
0  9  *  *  1-5    工作日（周一至周五）9:00
30 2  1  *  *      每月 1 号 2:30
0  0  *  *  0      每周日 0:00
```

### 通配符、列表、范围与步长

五个字段都支持四种取值方式：

```text
*      任意值            * 在分钟字段 = 每分钟
1,3,5  列举（逗号分隔）   分字段 1,3,5 = 第 1、3、5 分钟
1-5    范围（连字符）     时字段 1-5 = 1 点到 5 点
*/N    步长（斜杠）      分钟字段 */15 = 0,15,30,45（从范围起点起跳）
```

注意三点：

- `*/N` 等价于「范围起点到终点按 N 步进」。分钟字段 `*/15` 展开为 `0,15,30,45`，不是「从当前时刻起每 15 分钟」。
- 步长可以和范围组合，如 `1-30/5` = 1,6,11,16,21,26。
- 列举、范围、步长**不能混用在同一字段**（如 `1,*/15` 非法），这是语法错误。

### 用户级与系统级 crontab

```text
用户级（crontab 命令管理）：
  crontab -e  编辑；存 /var/spool/cron/crontabs/<用户名>（Debian）
              或 /var/spool/cron/<用户名>（RHEL）；权限 600
  以该用户身份执行，格式 = 五段式 + 命令（没有用户列）

系统级（root 直接写文件）：
  /etc/crontab           系统主表，格式多一列「执行用户」
  /etc/cron.d/*          系统级任务目录（推荐放自定义系统任务）
  /etc/cron.hourly/      每小时任务脚本目录
  /etc/cron.daily/       每天任务脚本目录
  /etc/cron.weekly/      每周任务脚本目录
  /etc/cron.monthly/     每月任务脚本目录
```

系统级任务由 root 维护，脚本放在目录里（配合 run-parts 依次执行），可以明确指定以哪个用户身份运行——这是用户级做不到的（用户级只能以自己身份跑）。

### 特殊字符串

五段式的快捷别名，写在时间字段位置：

| 特殊字符串 | 等价于 | 含义 |
|---|---|---|
| @reboot | （无） | crond 守护进程启动时执行一次（不是每次用户登录） |
| @yearly / @annually | `0 0 1 1 *` | 每年 1 月 1 日 0:00 |
| @monthly | `0 0 1 * *` | 每月 1 日 0:00 |
| @weekly | `0 0 * * 0` | 每周日 0:00 |
| @daily / @midnight | `0 0 * * *` | 每天 0:00 |
| @hourly | `0 * * * *` | 每小时整点 |

`@reboot` 是「crond 启动时」，不是「系统启动时」：重启后 crond 由 systemd 拉起，任务在 crond 起来后执行，因此**依赖网络/数据库等服务的 @reboot 任务经常失败**（见踩坑记录）。

> 实测（本机 Debian cron 3.0pl1）：网上流传的 `@every_minute`、`@every_second` 特殊字符串**不是标准语法**，Debian/Ubuntu 的 cron 直接报错拒绝安装：
>
> ```text
> $ printf '@every_minute echo test\n' > /tmp/cron-test.txt
> $ crontab /tmp/cron-test.txt
> "/tmp/cron-test.txt":0: bad time specifier
> errors in crontab file, can't install.
> ```
>
> 它是某些第三方 cron 实现（如部分 Vixie cron 补丁版）的扩展，**不要依赖**；每 1 分钟直接用 `* * * * *` 即可。

### 环境变量模型

cron 执行任务时**不加载任何登录环境**：不读 .bashrc / .profile / .bash_profile，继承的 PATH 极简（Vixie cron 传统默认 `PATH=/usr/bin:/bin`，不含 /usr/local/bin、/sbin 系）。Ubuntu 24.04 的 cron 3.0pl1 由 systemd 启动时，PATH 会继承自启动环境（/etc/crontab 头部注释有说明），但无论如何**都与你手动登录 shell 的环境不同**。

这就是「手动能跑、定时不跑」的头号原因。三个对策：

1. 命令和脚本用**绝对路径**（`/usr/bin/rsync` 而非 `rsync`）；
2. 在 crontab 顶部**显式设置环境变量**（PATH/HOME/SHELL/MAILTO）；
3. 脚本内部自己定义环境（脚本开头 `export PATH=...` 或 source 自己的配置）。

crontab 中环境变量行格式为 `NAME = value`（等号两边可以有空格，值里的空格要小心），必须在任务行之前：

```text
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=ops@example.com
HOME=/root

0 3 * * * /opt/scripts/backup.sh
```

### cron 与 anacron

anacron 是 cron 的「补跑」补充：cron 只按墙钟匹配，机器关机错过的时间**不会补跑**；anacron 按「距上次执行间隔天数」判断，检测到错过就补跑，且自带随机延迟避免开机瞬间任务扎堆。

```text
cron 与 anacron 对比：
           cron                  anacron
触发粒度    分钟级                 天级（周期按天计）
补跑机制    无，错过就错过          检测到错过自动补跑
适用场景    精确到分钟的任务         每日/每周/每月的例行任务
常驻方式    守护进程 crond          由 cron 或 systemd timer 定期唤醒
配置文件    crontab / /etc/crontab  /etc/anacrontab
```

两者是配合关系不是替代关系：Ubuntu 的 /etc/crontab 里 `test -x /usr/sbin/anacron || run-parts /etc/cron.daily` 意思是「有 anacron 就让 anacron 管 daily 任务，没有才由 cron 直接跑」；anacron 本身又由 systemd 的 anacron.timer（或 /etc/cron.d/anacron）每天唤醒。RHEL 的 cronie 则把 anacron 逻辑内置（见下文 Red Hat 系差异）。

## 工作原理

cron 由守护进程 crond 驱动，核心是一个「每分钟醒来扫描一次」的循环：

```text
crond 启动
  → 读取所有 crontab（用户级 /var/spool/cron/crontabs/* + 系统级 /etc/crontab、/etc/cron.d/*）
  → 进入睡眠，每分钟醒来一次
  → 对每条任务判断「当前 分时日月周 是否匹配」
  → 匹配则 fork 一个子进程执行（以任务属主身份）
  → 子进程 stdout/stderr 收集后 mail 给属主（MAILTO 指定收件人，没配 MTA 则丢弃）
```

要点：

1. **时间精度是分钟级**：cron 没有秒级能力（除了 @reboot 这类事件型），`* * * * *` 每分钟执行一次，但具体落在哪一秒取决于 crond 扫描时机，可能偏差数秒。
2. **执行环境是 sh**：cron 用 `/bin/sh`（或 crontab 里 SHELL= 指定的 shell）执行命令，不是用户的登录 shell。
3. **输出邮件机制**：任务产生的 stdout/stderr 会被 cron 捕获，通过本地邮件（sendmail/postfix 等 MTA）发给属主；服务器没装 MTA 时输出直接丢弃——所以**必须手动重定向到日志文件**，否则报错无从查起。
4. **时区与时间跳变**：cron 按**本地时区**匹配（读 /etc/localtime）。系统时间被 NTP 大步进拨快时，中间分钟的任务不会补跑；拨慢时可能出现重复执行。中国没有夏令时，欧美系统在 DST 切换日会出现「2:30 不存在（跳过）」或「2:30 出现两次（跑两次）」。
5. **@reboot 的语义**：crond 启动时执行。systemd 重启机器 → crond 随 multi-user.target 启动 → 任务执行；如果服务依赖的组件还没就绪，任务失败。

```text
cron 工作流程：
crond 每分钟醒来 → 检查所有 crontab → 匹配当前分钟的任务 → fork 子进程执行（最小化环境）→ 输出邮件/丢弃
```

## 常用命令与配置

| 命令 | 作用 |
|---|---|
| `crontab -e` | 编辑当前用户的定时任务（首次会选编辑器） |
| `crontab -l` | 查看当前用户的定时任务 |
| `crontab -r` | 删除当前用户**所有**定时任务（慎用，无确认） |
| `crontab -u alice -l/-e/-r` | 管理指定用户的任务（仅 root） |
| `crontab /path/file` | 用文件整体替换当前 crontab（批量导入） |
| `crontab -i -r` | 删除前交互确认（安全习惯） |
| `systemctl status cron` | 确认 crond 服务状态（Debian/Ubuntu） |
| `systemctl status crond` | 同上（RHEL/CentOS） |
| `grep CRON /var/log/syslog` | 查看 cron 执行日志（Debian） |
| `grep CRON /var/log/cron` | 查看 cron 执行日志（RHEL，cronie 专用文件） |

# 常用操作序列
crontab -l > crontab-backup.txt      # 先备份再改
crontab -e                            # 编辑
crontab -l | tail -n 20               # 确认改动

## 配置文件解析

### /etc/crontab（系统主表）

系统级 crontab 比用户级**多一列「执行用户」**，且编辑后不需要 crontab 命令安装（crond 每次扫描都重新读）：

```text
# 实测（本机 /etc/crontab，Ubuntu 24.04）
# /etc/crontab: system-wide crontab
# ... 头部注释给出了五字段图解 ...
SHELL=/bin/sh
#PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin   # 默认继承环境

17 *    * * *   root  cd / && run-parts --report /etc/cron.hourly
25 6    * * *   root  test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.daily; }
47 6    * * 7   root  test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.weekly; }
52 6    1 * *   root  test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.monthly; }
```

```text
字段含义：
五段式时间（分 时 日 月 周）+ 执行用户 + 命令
run-parts —— 依次执行目录下的所有脚本（/etc/cron.daily 等）
--report  —— 有脚本失败时输出报告（Debian 的 run-parts 支持）
test -x /usr/sbin/anacron || ... —— 有 anacron 时交给 anacron 管，否则 cron 直接跑
```

### /etc/cron.d/（系统级任务目录）

目录下每个文件都是一份「带用户列的 crontab」，crond 每分钟扫描。Ubuntu 推荐把自定义系统任务放这里（root 可写、可指定用户、随系统 cron 一起管理）：

```text
# 实测（本机 /etc/cron.d/）
$ ls /etc/cron.d/
anacron  dsh-cert-renew  e2scrub_all  sysstat

$ cat /etc/cron.d/dsh-cert-renew     # 自定义任务示例：每月 4:00 续期证书
# Renew DeepSeek Harness TLS certificate monthly (Tailscale certs last ~90 days)
0 4 1 * * root /usr/local/bin/dsh-cert-renew.sh > /var/log/dsh-cert-renew.log 2>&1

$ cat /etc/cron.d/sysstat            # 系统任务示例：每 10 分钟采集一次性能数据
PATH=/usr/lib/sysstat:/usr/sbin:/usr/sbin:/usr/bin:/sbin:/bin
5-55/10 * * * * root command -v debian-sa1 > /dev/null && debian-sa1 1 1
59 23 * * * root command -v debian-sa1 > /dev/null && debian-sa1 60 2

$ cat /etc/cron.d/anacron            # 兼容路径：非 systemd 环境由 cron 唤醒 anacron
30 7-23 * * * root [ -x /etc/init.d/anacron ] && if [ ! -d /run/systemd/system ]; then \
  /usr/sbin/invoke-rc.d anacron start >/dev/null; fi
```

注意：/etc/cron.d/ 文件名**不能含点号**（如 `foo.bar` 会被忽略，crond 只读不含点的文件）。

### /etc/cron.daily/ 等脚本目录

按周期执行的脚本目录，由 run-parts 依次执行：

```text
# 实测（本机）
$ ls /etc/cron.hourly/          # 空目录
$ ls /etc/cron.daily/
0anacron  apport  apt-compat  dpkg  logrotate  man-db  sysstat
$ ls /etc/cron.weekly/
0anacron  man-db
$ ls /etc/cron.monthly/
0anacron
```

脚本要求：**可执行权限 + 以 #! 开头的 shebang**（run-parts 会跳过没有 shebang 的文件）；文件名不能含点号；执行身份是 root（由 /etc/crontab 里的 run-parts 行决定）。logrotate 就在这里（`/etc/cron.daily/logrotate`），所以装 logrotate 不用自己写 crontab。

### /var/spool/cron/crontabs/（用户级任务存储）

```text
# 实测（本机，Debian 布局）
$ ls -la /var/spool/cron/crontabs/
总计 8
drwx-wx--T 2 root crontab 4096  3月 31  2024 .
```

- 目录权限 `drwx-wx--T`（1730：root 所有、crontab 组，sticky），**只有 root 能读**，用户只能通过 crontab 命令访问自己的文件；
- 每个用户一个文件，文件名 = 用户名，权限 600；
- **不要手改这些文件**，一律用 crontab 命令（直接写文件 crond 不会重新加载，且绕过权限校验）。

### /etc/anacrontab（anacron 配置）

```text
# 实测（本机 /etc/anacrontab）
SHELL=/bin/sh
HOME=/root
LOGNAME=root

# 格式：周期(天)  延迟(分钟)  任务名  命令
1       5       cron.daily      run-parts --report /etc/cron.daily
7       10      cron.weekly     run-parts --report /etc/cron.weekly
@monthly 15     cron.monthly    run-parts --report /etc/cron.monthly
```

含义：每 1 天检查一次 cron.daily，如果错过（上次执行时间戳距今超过周期）则补跑，补跑前随机延迟 0-45 分钟（RANDOM_DELAY，默认 45）错峰。执行时间戳记录在 /var/spool/anacron/ 下。

## 应用场景实战

### 场景一：每天凌晨 3 点备份数据库

```shell
# 1. 写备份脚本（绝对路径 + 日志重定向 + 错误退出）
cat > /opt/scripts/db-backup.sh <<'EOF'
#!/bin/bash
set -euo pipefail
TS=$(date +%F)
/usr/bin/mysqldump --single-transaction -uroot mydb \
  | /usr/bin/gzip > /backup/mydb-${TS}.sql.gz
echo "$(date) backup done: /backup/mydb-${TS}.sql.gz" >> /var/log/backup.log
EOF
chmod +x /opt/scripts/db-backup.sh

# 2. 加入 crontab（先备份现有任务）
crontab -l > /root/crontab-backup-$(date +%F).txt
(crontab -l 2>/dev/null; echo "0 3 * * * /opt/scripts/db-backup.sh") | crontab -

# 3. 验证
crontab -l
# 4. 手动先跑一次验证脚本本身
/opt/scripts/db-backup.sh && ls -lh /backup/
```

要点：脚本开头 `set -euo pipefail` 让任何一步失败都能体现出来；输出重定向到日志；先手动跑通再加 crontab。

### 场景二：日志清理（保留 7 天）

```shell
cat > /opt/scripts/clean-logs.sh <<'EOF'
#!/bin/bash
# 删除 /var/log/app/ 下 7 天前的 .log 文件
find /var/log/app/ -name '*.log' -mtime +7 -delete
# 超过 500M 的日志文件压缩
find /var/log/app/ -name '*.log' -size +500M -exec gzip {} \;
echo "$(date) log clean done" >> /var/log/clean-logs.log
EOF
chmod +x /opt/scripts/clean-logs.sh
# 每天 4:20 执行
(crontab -l 2>/dev/null; echo "20 4 * * * /opt/scripts/clean-logs.sh") | crontab -
```

生产环境更推荐用 logrotate 管轮转（见 [[13.2-日志轮转与集中]]），cron 适合管「非标准格式」的临时文件清理。

### 场景三：健康检查 + 失败告警

```shell
cat > /opt/scripts/health-check.sh <<'EOF'
#!/bin/bash
# 每分钟检查 Web 服务，失败写告警文件（由监控系统/另一任务收集）
if ! curl -fsS http://127.0.0.1:8080/health > /dev/null 2>&1; then
  echo "$(date) web service DOWN" >> /var/log/health-alert.log
  # 有 MTA 的话直接发邮件
  # echo "web down" | mail -s "ALERT" ops@example.com
fi
EOF
chmod +x /opt/scripts/health-check.sh
# 每分钟一次（任务必须极轻量）
(crontab -l 2>/dev/null; echo "* * * * * /opt/scripts/health-check.sh") | crontab -
```

高频任务的原则：只做检测和记录，不做重活；告警通过文件/邮件/Webhook 三条路之一出去。

### 场景四：跨机数据同步（rsync 拉取）

```shell
# 每天 2:00 从远端拉取数据目录
cat > /opt/scripts/sync-data.sh <<'EOF'
#!/bin/bash
set -euo pipefail
/usr/bin/rsync -avz --delete \
  -e "ssh -i /root/.ssh/sync_key -o StrictHostKeyChecking=no" \
  syncuser@10.0.0.5:/data/ /data/ >> /var/log/sync.log 2>&1
EOF
chmod +x /opt/scripts/sync-data.sh
(crontab -l 2>/dev/null; echo "0 2 * * * /opt/scripts/sync-data.sh") | crontab -
```

注意：ssh 密钥文件权限必须 600，否则 ssh 拒绝使用；`--delete` 要确认源端目录真实存在，防止误删本地数据。

## 性能与调优

```text
1. 触发密度 —— 别设 * * * * * 的高频任务做重活；每分钟任务只放
   健康检查/指标采集等极轻量操作，重活（备份/压缩/同步）放低频时段
2. 错峰执行 —— 多个任务别堆在同一分钟同一秒（如所有任务都 0 3 * * *），
   用不同分钟错开（0 3、5 3、10 3...），避免瞬间 CPU/磁盘/网络峰值；
   同机器大量任务可参考 systemd timer 的 RandomizedDelaySec 思路错峰
3. 日志重定向 —— 所有任务输出重定向到文件（>> log 2>&1），
   否则 cron 每次执行都要 fork 邮件进程，任务多了拖慢 crond；
   日志文件记得配合 logrotate 轮转，防占满磁盘
4. 任务时长 —— 任务运行时间要远小于触发间隔；间隔 5 分钟的任务若
   平均跑 4 分钟，稍有抖动就会重叠（见「定时任务加锁」）
5. crond 自身开销 —— crond 本身内存占用极小（本机实测约 1M），
   性能瓶颈从来不在 crond，而在任务脚本本身
6. 大目录扫描 —— 每分钟任务里避免 find / 全盘扫描、避免遍历大目录，
   高频任务的时间复杂度必须 O(1) 或接近
```

## 安全与权限

```text
1. cron.allow / cron.deny —— 控制谁能使用 crontab：
   - /etc/cron.allow 存在 → 只有列出的用户能用（白名单，优先）
   - 否则 /etc/cron.deny 存在 → 列出的用户不能用
   - 两个都不存在 → 默认所有用户可用（Ubuntu 24.04 实测两个都没有）
   安全基线：系统装好后创建 /etc/cron.allow，只放需要的人
2. 最小权限 —— 任务能用普通用户跑就别用 root；
   系统级任务在 /etc/cron.d/ 里指定 User= 降权执行
3. 脚本文件权限 —— cron 脚本只允许属主/root 可写（chmod 755 或 700），
   防止被其他用户篡改注入恶意命令（配合 600 的 ssh key 同理）
4. 敏感信息 —— 脚本里别硬编码密码/密钥；用 EnvironmentFile、密钥文件
   （权限 600）、或凭据管理（见 [[22.4-配置与密钥管理]]）
5. 命令注入 —— 从外部输入拼进 cron 命令时要校验（如文件名带空格/分号），
   防止注入执行任意命令
6. 审计 —— cron 执行记录在 syslog（Debian）或 /var/log/cron（RHEL），
   安全审计时 grep CRON 核对任务清单与执行时间（见 [[23.3-安全审计]]）
7. 定期审查 —— 定期 crontab -l -u <user> 全量核对任务清单，
   删除离职人员/废弃任务，防止「幽灵任务」长期运行
```

## 故障排查

### 案例一：任务完全没执行

```shell
# 1. 确认 crond 服务在跑（Debian/Ubuntu）
systemctl status cron
# 2. 看 cron 执行日志（Debian 在 syslog，RHEL 在 /var/log/cron）
grep CRON /var/log/syslog | tail
# 3. 确认 crontab 语法与内容
crontab -l
# 4. 语法错误会报错：手动编辑时 crontab -e 保存会提示
#    "errors in crontab file, can't install."
# 5. 检查系统时间是否正常（时间错了任务全乱）
date; timedatectl
```

# 实测（本机 /var/log/syslog 里的 CRON 记录）

### 案例二：手动能跑、定时不跑（环境差异）

```shell
# 1. 手动执行对比
/opt/scripts/backup.sh && echo OK
# 2. 用「干净环境」模拟 cron 的执行环境（关键！）
env -i /bin/sh -c '/opt/scripts/backup.sh'
#   如果这一步报 command not found / 依赖缺失，就是环境问题
# 3. 检查脚本里的命令是否都是绝对路径
grep -nE '(^|[^/])[a-z-]+ ' /opt/scripts/backup.sh | head
# 4. 修复：脚本内 export PATH 或 crontab 顶部设 PATH
```

### 案例三：任务执行了但结果不对 / 输出丢失

```shell
# 1. 看重定向的日志
tail -50 /var/log/backup.log
# 2. 没配重定向？看邮件（root 的邮箱 /var/mail/root，或 MAILTO 指定的人）
tail -50 /var/mail/root
# 3. 检查 % 转义（date +%F 里的 % 会被 cron 当换行！）
#    crontab 里必须写 date +\%F
# 4. 检查脚本是否真的可执行（权限 + shebang）
ls -l /opt/scripts/backup.sh
head -1 /opt/scripts/backup.sh
```

### 案例四：时间跳变/时区问题导致任务乱跑

```shell
# 1. 确认系统时区与时间同步状态
timedatectl
#    Time zone: Asia/Shanghai (CST, +0800)
#    System clock synchronized: yes
# 2. NTP 大步进导致任务跳过/重复：检查 chrony 或 timesyncd 日志
journalctl -u systemd-timesyncd | tail
# 3. 需要指定时区时：crontab 里设 TZ 环境变量
#    TZ=Asia/Shanghai
#    0 3 * * * /opt/scripts/backup.sh
# 4. 夏令时切换日（欧美系统）：2:30 可能不存在或出现两次，
#    把任务挪到整点/避开 DST 切换时段，或用 UTC 时间规划
```

## 常见问题

```text
Q1: cron 任务手动能跑，定时不跑？
A: cron 执行环境极简（PATH 不含 /usr/local/bin 等、不读 .bashrc）。
   命令/脚本用绝对路径，或 crontab 顶部显式设 PATH。

Q2: cron 任务失败看不到任何报错？
A: stdout/stderr 没重定向，输出发邮件（没 MTA 就丢）。命令后加
   >> /var/log/xxx.log 2>&1，或设 MAILTO=自己邮箱。

Q3: 周字段 0 和 7 什么区别？
A: 没区别，都表示周日。0-6 = 周日到周六，7 是周日的别名。
   五段式顺序是「分 时 日 月 周」，别把顺序记错。

Q4: crontab -r 把任务全删了怎么办？
A: -r 直接删除全部任务且无确认。平时先 crontab -l > backup 备份；
   或养成用 crontab -i -r（删除前确认）的习惯。有备份就 crontab backup 恢复。

Q5: 命令里有 % 符号（如 date +%F）为什么报错？
A: % 在 crontab 里是特殊字符，会被 cron 当作换行（% 后内容作为命令
   stdin）。字面 % 必须转义为 \%（date +\%F）。

Q6: 日和周字段都写了（如 0 0 15 * 1），是「每月15号且周一」吗？
A: 不是！Vixie cron 的语义是 OR：任一字段匹配就执行。0 0 15 * 1 是
   「每月 15 号或每周一」都执行。要表达 AND 只能写两行分别判断或脚本内判断。

Q7: 服务器重启后，错过的任务会补跑吗？
A: cron 不会（错过就错过）。每日/每周例行任务想补跑要用 anacron
   （/etc/cron.daily 等目录由 anacron 托管）或 systemd timer 的 Persistent=true。

Q8: 服务器时间被 NTP 拨快/拨慢，cron 任务会怎样？
A: cron 按墙钟匹配：拨快则中间分钟任务跳过（不补跑），拨慢可能重复执行。
   生产环境用 chronyd/timesyncd 的 slewing（缓慢微调）避免大步进。
```

## 面试题

```text
1. crontab 五段式分别代表什么？取值范围？
   答：分（0-59）、时（0-23）、日（1-31）、月（1-12 或 JAN-DEC）、
   周（0-7，0 和 7 都是周日，或 SUN-SAT）。顺序「分时日月周」。

2. 为什么 cron 任务手动能跑、定时不跑？
   答：cron 用最小化环境执行（默认 PATH=/usr/bin:/bin、不读 .bashrc、
   不加载登录环境），命令或依赖找不到。解法：绝对路径、crontab 显式
   设 PATH、脚本内 export 环境。

3. 用户级和系统级 crontab 的区别？
   答：用户级用 crontab 命令管理，存 /var/spool/cron/crontabs/<用户>，
   以该用户身份执行，五段式+命令；系统级在 /etc/crontab、/etc/cron.d/，
   多一列执行用户，由 root 维护；/etc/cron.daily/ 等目录由 run-parts 执行。

4. cron 和 anacron 的区别？什么场景用 anacron？
   答：cron 精确到分钟、按墙钟匹配、错过不补跑；anacron 按天粒度、
   检测到错过自动补跑、带随机延迟。笔记本/非 7x24 机器上
   每日每周例行任务（日志轮转、man-db）适合 anacron 托管。

5. 日和周字段同时非 * 时是什么语义？
   答：OR（或）关系，任一匹配即执行。这是 Vixie cron 的传统行为，
   与直觉的 AND 相反，是经典面试陷阱。要 AND 用脚本内判断。

6. 如何保证 cron 任务同一时间只有一个实例在跑（防重入）？
   答：用 flock 文件锁：脚本开头 flock -n /var/lock/task.lock 抢锁，
   抢不到直接退出；或用 mkdir 原子性做互斥。详见 [[14.4-任务可靠性]]。

7. 如何监控 cron 任务是否失败？
   答：三层：① 任务内 set -euo pipefail + 输出重定向日志；
   ② 失败写标记文件/发邮件（MAILTO）/调 Webhook 告警；
   ③ 外部兜底：独立监控任务检查「上次成功时间戳」是否过期
   （如任务成功时 touch /var/run/task.ok，监控查 mtime 超过 2 倍间隔告警）。

8. 服务器重启后 @reboot 任务依赖的服务还没起来怎么办？
   答：脚本里加「等依赖就绪」逻辑（循环探测端口/文件 + 超时），
   或改用 systemd service 的 After= 声明依赖（见 [[10.3-编写 Service Unit]]）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 所有命令和脚本用绝对路径，脚本开头 `#!/bin/bash` + `set -euo pipefail`
2. 任务输出一律重定向到日志（`>> /var/log/xxx.log 2>&1`），并配 logrotate 防占满
3. 改 crontab 前先 `crontab -l > backup`，删除用 `crontab -i -r`
4. 备份/清理/同步类重活放凌晨业务低谷，且多任务错峰（不同分钟）
5. 系统级任务放 /etc/cron.d/（可指定用户、集中管理），个人任务用 crontab -e
6. 新任务先手动跑通、再设成 `*/1` 分钟观察几次、确认无误后改成正式周期
7. 任务成功时更新时间戳文件（`touch /var/run/xxx.ok`），供外部监控检查「是否还活着」
8. 定时任务脚本放到统一目录（如 /opt/scripts/），版本管理，禁止散落各处
9. 依赖网络的 cron 任务要处理「网络未就绪」：重试 + 超时，别裸跑
10. 非 7x24 机器用 anacron 托管每日任务；新项目优先考虑 systemd timer（见 [[14.2-systemd timer]]）

### 踩坑记录

```text
坑 1：cron 任务手动能跑，定时不跑
结论：脚本手动执行正常，cron 定时执行失败（command not found 或依赖缺失）。
原因：cron 执行环境极简——默认 PATH 只有 /usr/bin:/bin，不读 .bashrc/.profile，
     登录 shell 里能用的命令（如 /usr/local/bin 下的）cron 找不到。
解法：命令/脚本用绝对路径；crontab 顶部显式设 PATH；脚本内 export PATH。

坑 2：cron 任务没输出，报错看不到
结论：任务失败了，但日志里什么都没有，无从排查。
原因：stdout/stderr 没重定向，cron 把输出发给本地邮件；服务器没装 MTA 时直接丢弃。
解法：命令后加 >> /var/log/xxx.log 2>&1；或设 MAILTO=ops@example.com。

坑 3：命令里的 % 被 cron 吃掉，date +%F 输出不对
结论：crontab 里写 date +%F，执行时 %F 变成了换行，文件名/日志格式全乱。
原因：% 在 crontab 中是特殊字符，cron 把 % 当作换行处理（% 后内容作为 stdin）。
解法：字面 % 写成 \%：date +\%F；需要多行 stdin 时才用 % 特性。

坑 4：日和周字段同时设置，任务在预料外的日子执行
结论：写了 0 0 15 * 1 期望「每月 15 号的周一」才跑，结果每周一都跑。
原因：Vixie cron 中日和周字段是 OR 关系，任一匹配即执行，不是 AND。
解法：脚本内判断（[ "$(date +%d)" = 15 ] && [ "$(date +%u)" = 1 ]），
     或拆成两行分别处理。

坑 5：crontab -r 误删所有任务
结论：手滑执行 crontab -r，所有定时任务瞬间清空。
原因：-r 是删除（remove），-l 才是查看；-r 无确认直接删。
解法：平时 crontab -l > backup 定期备份；用 crontab -i -r 带确认；
     误删后从备份恢复（crontab backup 文件）。

坑 6：脚本没执行权限或没有 shebang，run-parts 直接跳过
结论：脚本放进 /etc/cron.daily/ 了，但从来没被执行过。
原因：run-parts 要求脚本可执行（+x）且第一行是 #! 开头，
     否则静默跳过，不报任何错误。
解法：chmod +x；确认 head -1 脚本 是 #!/bin/bash。

坑 7：@reboot 任务在开机时依赖的服务还没起
结论：@reboot 脚本执行失败，因为数据库/网络还没就绪。
原因：@reboot 是「crond 启动时」执行，早于业务服务就绪。
解法：脚本里加「等依赖服务就绪」逻辑（循环探测 + 超时），
     或改用 systemd service + After=（见 [[10.3-编写 Service Unit]]）。

坑 8：任务没跑完下一次又启动，任务重叠堆积
结论：慢任务（同步/备份）互相叠加，CPU 打满、数据竞争。
原因：cron 不检查上次实例是否还在运行，到点就再 fork 一个。
解法：脚本开头 flock -n 抢锁，抢不到退出：
     exec 9>/var/lock/task.lock && flock -n 9 || exit 0
     详见 [[14.4-任务可靠性]]。

坑 9：NTP 大步进后 cron 任务跳过/重复
结论：时间被拨快 30 分钟，中间的任务全没跑；或拨慢后任务跑了两次。
原因：cron 按墙钟匹配，对时间跳变无感知、无补跑。
解法：chronyd/timesyncd 用 slewing 微调；关键任务用 anacron 或
     systemd timer Persistent=true 补跑（见 [[14.2-systemd timer]]）。
```
