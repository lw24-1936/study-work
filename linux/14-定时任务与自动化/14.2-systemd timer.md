## 概述

systemd timer 是 systemd 原生的定时任务机制，被认为是 cron 的现代化替代方案。核心思想：**一个 .timer 单元负责「什么时候触发」，一个同名的 .service 单元负责「执行什么」**——触发与执行彻底分离。

相比 cron 的优势：与 systemd 生态深度集成（日志自动进 journald、状态可查、失败可重试、单元间依赖管理）、时间表达式更灵活可读（OnCalendar）、触发更精确（到点精确唤醒，非每分钟轮询）、天然支持补跑（Persistent）与错峰（RandomizedDelaySec）。现代发行版已把大量系统任务从 cron 迁到 timer（Ubuntu 的 apt-daily.timer、logrotate.timer 等）。

```text
systemd timer 原理：
1. .timer 单元 —— 定义触发时间（OnCalendar/OnBootSec/OnUnitActiveSec）
2. .service 单元 —— 定义执行的任务
3. 配合 —— timer 触发时自动激活同名 service（foo.timer → foo.service）
4. 日志 —— 执行结果进 journald，journalctl -u 服务名 可查
```

## 核心概念

### timer 与 service 的同名配对

timer 通过**同名自动关联**找到要激活的服务：`foo.timer` 触发时激活 `foo.service`。不用写任何关联配置，名字相同即可；也可以显式用 `Unit=` 指定其他名字的单元。service 通常是 `Type=oneshot`（执行完即退出，适合定时任务），也可以是有状态的长驻服务。

```text
foo.timer   （触发条件）            foo.service  （执行内容）
[Timer]                             [Service]
OnCalendar=daily                    Type=oneshot
Persistent=true                     ExecStart=/opt/scripts/foo.sh
```

### 两种时钟：Monotonic 与 Realtime

timer 支持两类触发时间，分别基于两种时钟：

```text
单调时钟 Monotonic（从开机起计时，不受改时间/NTP 影响）：
  OnBootSec=      开机后 N 秒/分钟（如 5min）
  OnStartupSec=   systemd 启动后 N 秒（与 OnBootSec 基本等价）
  OnActiveSec=    timer 单元被激活后 N 秒（常配成循环：每次触发后重新计时）
  OnUnitActiveSec= 对应 service 上次激活后 N 秒
  OnUnitInactiveSec= 对应 service 上次停止后 N 秒

墙钟时钟 Realtime（日历时间，受时区/时间同步影响）：
  OnCalendar=     日历表达式（如 daily、Mon..Fri 09:00:00、*-*-* 03:00:00）
```

单调时间适合「相对事件」的周期任务（服务挂掉 30 秒后重启、上次执行后 1 小时再跑）；墙钟时间适合「绝对时刻」的业务任务（每天凌晨 3 点备份）。**两者可以在同一个 timer 里混用**，满足任一条件即触发。

### OnCalendar 日历表达式

OnCalendar 是比 cron 五段式更灵活、可读的日历表达式，格式为「[星期] 日期 时间」，三段都可省略部分：

```text
基本格式：   星期  年-月-日  时:分:秒
示例：
daily                                  每天 0:00（等价 *-*-* 00:00:00）
hourly                                 每小时整点（*-*-* *:00:00）
weekly                                 每周一 0:00（Mon *-*-* 00:00:00）
monthly                                每月 1 号 0:00（*-*-01 00:00:00）
*-*-* 03:00:00                         每天 3:00
Mon..Fri 09:00:00                      工作日 9:00
Mon,Wed,Fri 22:30:00                   周一三五 22:30
*-*-15 04:30:00                        每月 15 号 4:30
2026-*-* 00:00:00                      2026 年每天 0:00
*:0/15                                 每 15 分钟（秒字段省略）
*-*-* 03:00:00 Asia/Shanghai           指定时区（等效 Timezone=）
```

字段语法：`*` 任意、`a..b` 范围（含端点）、`a,b,c` 列举、`a/b` 步长、`a..b/c` 范围步长；日期支持 `*`、`YYYY`、`YYYY-MM`、`YYYY-MM-DD`、`MM-DD`；时间支持 `HH:MM:SS`、`HH:MM`、`HH`，步长写法如 `*:0/15`（每 15 分钟）、`00:00/2:00`（每 2 小时）。秒字段在 systemd v232+ 才支持。

### Persistent 持久化补跑

`Persistent=true` 让 timer 记住「上次应该触发但没触发的时间点」（写入 /var/lib/systemd/timers/ 的 stamp 文件），系统开机后如果发现错过，**立即补跑一次**，然后回到正常周期。典型场景：笔记本/虚拟机经常关机，每天 3 点的备份任务靠它开机补跑。

```text
Persistent=false（默认）：关机期间错过的触发直接丢弃，开机后不补跑
Persistent=true：         开机后检测到错过 → 立即触发一次 → 恢复正常周期
注意：Persistent 只对 OnCalendar（墙钟）生效，
     单调时间触发（OnBootSec 等）没有「错过」的概念
```

### AccuracySec 精度与 RandomizedDelaySec 错峰

```text
AccuracySec=1min（默认）  允许触发时间在目标点前后 1 分钟内浮动，
                          systemd 借此把多个 timer 合并唤醒，省电省资源。
                          设 1us 可做到精确触发（代价是系统频繁唤醒）
RandomizedDelaySec=5min   在触发点基础上再随机延迟 0~5 分钟，
                          用于错峰：多台机器/多个任务避免同时打爆资源
                          实测：Ubuntu 的 fstrim.timer 用它错峰（100min）
```

两者语义不同：AccuracySec 是「允许偏差窗口」，RandomizedDelaySec 是「主动随机延迟」；可以同时使用（随机延迟在精度窗口内生效）。

### 与 cron 对比：什么时候用哪个

| 维度 | cron | systemd timer |
|---|---|---|
| 触发精度 | 分钟级（每分钟轮询） | 秒级（精确唤醒） |
| 日志 | 邮件/手动重定向 | 自动进 journald |
| 状态查看 | 无标准接口 | systemctl list-timers/status |
| 失败重试 | 无 | Restart= 可配（service 单元） |
| 错过补跑 | 无（靠 anacron） | Persistent=true |
| 随机错峰 | 无 | RandomizedDelaySec |
| 依赖管理 | 无 | After=/Requires= 完整依赖图 |
| 环境变量 | 极简、易踩坑 | ExecStart 明确、可 EnvironmentFile= |
| 学习成本 | 低，生态成熟 | 中（要理解 unit 体系） |
| 适用场景 | 用户级个人任务、遗留环境 | 系统级任务、新部署、需要监控的任务 |

结论：**新写的系统级任务优先用 timer**（Ubuntu 自己都把 logrotate、apt-daily 迁到了 timer）；用户级个人任务、要在 crontab 语法里快速写一行的小任务、或兼容老发行版时用 cron。两者可共存，互不干扰。

## 工作原理

timer 单元本质上是一个「会唤醒 systemd 的闹钟」。启用后 timer 注册进 `timers.target`，systemd 的 PID 1 在内存里为每个 timer 计算并维护**下次触发时间点**（由 OnCalendar/OnBootSec 等 + AccuracySec 窗口推导）。到点后：

```text
timer 到点
  → systemd 激活同名的 .service 单元（新建 transient 实例）
  → service 按 [Service] 定义执行（Type=oneshot 跑完即退）
  → 执行日志写入 journald（journalctl -u xxx.service 可查）
  → 更新 timer 的 LAST 记录，计算下一次 NEXT
  → Persistent=true 时同时更新 stamp 文件（记录「已执行到哪个时间点」）
```

与 cron 的关键差异：

1. **精确唤醒而非轮询**：cron 每分钟醒来扫描所有任务；timer 由 systemd 事件驱动，到点才动作，空闲时零开销（不占用常驻进程）。
2. **触发≠执行**：timer 只负责唤醒，真正的执行者是对应的 service；所以能复用 systemd 的完整能力——日志、状态、依赖、资源限制（CPUQuota/MemoryMax）、重启策略（Restart=on-failure）。
3. **开机时序**：timer 由 timers.target 拉起（multi-user.target 之前），比 cron 的 @reboot 更可控；且能用 `After=` 声明「等网络/数据库就绪再触发」。
4. **时间跳变处理**：OnCalendar 基于墙钟，NTP 大步进后 systemd 会重算 next elapse（不补跑过去的点，Persistent=true 才补）；单调时间触发不受墙钟跳变影响——这也是「时间同步影响定时任务」问题上 timer 优于 cron 的一点（见 [[14.1-cron]] 中时间跳变坑）。

```text
timer 工作流程：
timer 注册到 timers.target → systemd 维护下次触发时间 → 到点激活同名 service → 日志进 journald → 更新 NEXT/LAST
```

## 常用命令与配置

| 命令 | 作用 |
|---|---|
| `systemctl list-timers` | 查看所有已激活的 timer（NEXT/LEFT/LAST/ACTIVATES） |
| `systemctl list-timers --all` | 含已加载但未激活的 |
| `systemctl list-timers foo.timer` | 只看指定 timer |
| `systemctl status foo.timer` | 状态、下次触发时间、关联 service |
| `systemctl start foo.timer` | 立即激活 timer（开始计时） |
| `systemctl enable --now foo.timer` | 开机自启 + 立即激活 |
| `systemctl disable foo.timer` | 取消开机自启（已激活的继续跑） |
| `systemctl daemon-reload` | 修改单元文件后重载（必须） |
| `systemd-analyze calendar "表达式"` | 解析验证 OnCalendar，显示下次触发时间 |
| `systemd-analyze timespan "1h 30min"` | 解析验证时间跨度（OnBootSec 等） |
| `systemd-analyze verify 文件` | 校验单元文件语法 |
| `journalctl -u foo.service` | 查看 service 执行日志 |

```shell
# 完整操作序列（新建一个 timer）
cat > /etc/systemd/system/backup.service <<'EOF'
[Unit]
Description=Daily backup

[Service]
Type=oneshot
ExecStart=/opt/scripts/backup.sh
EOF

cat > /etc/systemd/system/backup.timer <<'EOF'
[Unit]
Description=Run backup daily at 03:00

[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true

[Install]
WantedBy=timers.target
EOF

systemctl daemon-reload
systemctl enable --now backup.timer      # 开机自启 + 立即开始计时
systemctl list-timers backup.timer       # 验证下次触发时间
journalctl -u backup.service             # 查看执行日志
```

## 配置文件解析

### 文件位置与优先级

```text
/etc/systemd/system/      管理员自定义（优先级最高，覆盖发行版默认）
/run/systemd/system/      运行时生成（重启即失，优先级第二）
/usr/lib/systemd/system/  发行版软件包安装（优先级最低）
/lib/systemd/system/      Debian 系到 /usr/lib 的兼容链接
```

同名单元**高优先级目录覆盖低优先级**（如 /etc/systemd/system/foo.timer 覆盖 /usr/lib 里的同名文件），`systemctl cat foo.timer` 会显示最终生效的内容及来源路径。自定义 timer 一律放 /etc/systemd/system/。

### timer 单元字段速查

```ini
[Unit]
Description=xxx                    # 描述
After=network-online.target        # 触发前保证网络就绪（配合 Wants=）

[Timer]
OnCalendar=daily                   # 墙钟触发（可多个，任一满足即触发）
OnBootSec=5min                     # 开机后 5 分钟
OnUnitActiveSec=1h                 # 上次激活后 1 小时（循环周期任务）
OnActiveSec=1h                     # timer 激活后 1 小时
Unit=backup.service                # 显式指定激活的单元（默认同名）
Persistent=true                    # 错过补跑（仅 OnCalendar 生效）
AccuracySec=1min                   # 触发精度窗口（默认 1min）
RandomizedDelaySec=5min            # 随机延迟错峰
Timezone=Asia/Shanghai             # 指定时区（OnCalendar 按此时区解析）
WakeSystem=true                    # 触发时唤醒休眠的机器（需硬件支持）

[Install]
WantedBy=timers.target             # 开机自启挂到 timers.target
```

### 对应的 service 单元

```text
# 实测：systemctl cat logrotate.service（节选）
[Unit]
Description=Rotate log files
RequiresMountsFor=/var/log
ConditionACPower=true          # 仅交流供电时运行（笔记本省电）

[Service]
Type=oneshot                   # 定时任务标准类型：执行完即退出
ExecStart=/usr/sbin/logrotate /etc/logrotate.conf

# performance options
Nice=19                        # 低优先级，不抢业务任务
IOSchedulingClass=best-effort
IOSchedulingPriority=7
# hardening options（systemd 沙箱加固）
PrivateDevices=true
PrivateTmp=true
ProtectSystem=strict
...
```

## 应用场景实战

### 场景一：用 timer 做每天凌晨备份（完整流程）

```ini
# 1. 备份脚本（绝对路径 + 日志）
#    /opt/scripts/backup.sh  —— 内容同 [[14.1-cron]] 场景一

# 2. /etc/systemd/system/backup.service
[Unit]
Description=Daily Backup

[Service]
Type=oneshot
User=backupuser                # 降权执行，不默认 root
ExecStart=/opt/scripts/backup.sh
Nice=19

# 3. /etc/systemd/system/backup.timer
[Unit]
Description=Run backup daily at 03:00

[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true                # 机器关机错过则开机补跑
RandomizedDelaySec=10min       # 多机部署时错峰

[Install]
WantedBy=timers.target
```

```shell
# 4. 启用并验证
systemctl daemon-reload
systemctl enable --now backup.timer
systemctl list-timers backup.timer        # 确认 NEXT 是明天 03:00
systemd-analyze calendar "*-*-* 03:00:00" # 独立验证表达式
# 5. 手动触发一次验证脚本本身（不会影响 timer 周期）
systemctl start backup.service
journalctl -u backup.service -n 20        # 看执行结果
```


### 场景三：把现有 cron 任务迁移到 timer（对照表）

| cron | systemd timer | 说明 |
|---|---|---|
| `0 3 * * *` | `OnCalendar=*-*-* 03:00:00` | 每天 3 点 |
| `*/5 * * * *` | `OnCalendar=*:0/5` | 每 5 分钟（注意不是 `*/5 * * * *`） |
| `0 9 * * 1-5` | `OnCalendar=Mon..Fri 09:00:00` | 工作日 9 点 |
| `@reboot` | service 的 `After=` + `WantedBy=multi-user.target`，或 `OnBootSec=2min` | 开机任务改用依赖声明更可靠 |
| `@daily` | `OnCalendar=daily` | 每天 0 点 |
| 命令里的环境变量 | `Environment=` / `EnvironmentFile=` | 显式注入，不再依赖 PATH |
| 输出重定向 | journald 自动收集 | 无需 `>> log 2>&1` |
| anacron 补跑 | `Persistent=true` | 错过补跑 |
| 无错峰 | `RandomizedDelaySec=` | 随机延迟 |
| `MAILTO=` | `OnFailure=` 指向通知单元 | 失败通知（见场景四） |

迁移步骤：写 service 单元 → 写 timer 单元 → `daemon-reload` → `enable --now` → 验证 list-timers 与 journalctl → 从 crontab 删除原条目（保留备份）。

### 场景四：定时任务加锁防重入 + 失败通知

慢任务（同步/备份）可能上次没跑完又触发，两个方案叠加使用：

```ini
# /etc/systemd/system/sync.service
[Unit]
Description=Data sync
OnFailure=notify-fail@%n.service      # 失败时激活通知单元（%n=本单元名）

[Service]
Type=oneshot
ExecStart=/opt/scripts/sync.sh
```

```shell
# /opt/scripts/sync.sh 开头用 flock 防重入（详见 [[14.4-任务可靠性]]）
#!/bin/bash
exec 9>/var/lock/sync.lock
flock -n 9 || { echo "another instance running, exit"; exit 0; }
# ... 任务主体 ...
```

```text
失败通知单元 notify-fail@.service（模板单元，@ 后参数是失败单元名）：
[Unit]
Description=Notify on failure of %i

[Service]
Type=oneshot
ExecStart=/usr/local/bin/notify.sh %i
# notify.sh 里发邮件/钉钉/Webhook 告警即可
```

## 性能与调优

```text
1. 精确触发 —— timer 到点精确唤醒（秒级），无常驻轮询进程，
   空闲零开销；cron 每分钟要 fork 扫描，任务多了有可测差异
2. AccuracySec 调优 —— 默认 1min 允许偏差，systemd 可把多个 timer
   合并到同一唤醒点省电；要求精确执行（如对账任务）设 AccuracySec=1us，
   代价是系统频繁唤醒，电池设备慎用
3. 触发间隔 —— 别设秒级高频 timer（OnCalendar=*:*:0/5 每 5 秒），
   systemd 调度与 journald 写入都有开销；秒级需求应改为常驻服务 +
   内部循环，而不是 timer
4. RandomizedDelaySec —— 大批量机器/任务用随机延迟错峰，
   避免「整点风暴」：所有机器同时打爆备份服务器/API
5. 日志量控制 —— journald 默认限额（SystemMaxUse），高频 timer 日志
   多时要配合 journald 限额配置（见 [[13.1-系统日志]]）
6. 资源限制 —— service 里用 CPUQuota=/MemoryMax= 限制定时任务资源，
   防止备份任务把业务进程挤垮（logrotate.service 就设了 Nice=19 低优先级）
7. 单调时间任务 —— 需要「固定间隔」的循环任务优先 OnUnitActiveSec
   而非 OnCalendar：不受时间同步跳变影响，且从上次执行结束算起不重叠
```

## 安全与权限

```text
1. 单元文件权限 —— /etc/systemd/system/*.timer|*.service 属主 root、
   权限 644（root 可写），防被篡改注入恶意 ExecStart
2. 执行身份 —— service 里显式 User=/Group= 降权，别默认 root；
   日志文件权限配合（备份脚本输出目录属主匹配）
3. 环境隔离 —— ExecStart 用绝对路径；EnvironmentFile= 引配置文件时
   该文件权限收紧（600），别把密钥写进单元文件（systemctl cat 人可见）
4. 沙箱加固 —— 复用 systemd 的加固选项收窄攻击面：
   PrivateTmp=true、ProtectSystem=strict、ProtectHome=true、
   NoNewPrivileges=true（参考 logrotate.service 的完整加固列表）
5. 失败通知 —— OnFailure= 指向通知单元，失败要能第一时间告警，
   别让定时任务静默失败
6. 审计 —— timer/service 状态与日志都进 journald，审计可查
   （journalctl -u xxx.timer）；配合 [[23.3-安全审计]] 核对任务清单
7. 最小启用 —— 只 enable 需要的 timer；list-timers --all 定期审查，
   清理残留/废弃 timer（见故障排查案例三的幽灵单元）
```

## 故障排查

### 案例一：timer 不触发（改了配置、启用了就是不跑）

```shell
# 1. 确认 timer 已启用且激活（enable 是开机自启，start 是开始计时）
systemctl is-enabled backup.timer      # enabled
systemctl is-active backup.timer       # active（waiting 表示在等触发）
# 2. 看下次触发时间是否合理
systemctl list-timers backup.timer
# 3. 表达式对不对（最常见的坑：cron 语法直接抄）
systemd-analyze calendar "你的表达式"
# 4. 改过文件？必须重载
systemctl daemon-reload
# 5. 看 timer 自身日志
journalctl -u backup.timer -n 20
```

```text
# 实测：systemctl status 的状态解读
# ACTIVE 列常见值：
#   waiting   —— timer 正常运行，正在等待下一次触发（健康状态）
#   active    —— 正在触发/服务运行中（瞬时）
#   elapsed   —— 一次性 timer 已执行完（不再有 NEXT）
#   inactive  —— 未激活（没 start 或已被 stop）
# 注意：对应 service 是 oneshot，跑完即退，service 显示 dead 是正常的
```

### 案例二：timer 触发了但 service 报错

```shell
# 1. 看 service 执行日志（最关键一步）
journalctl -u backup.service -n 50
# 2. 手动跑一次 service，区分「脚本问题」和「timer 问题」
systemctl start backup.service
echo $?                              # 看退出码
# 3. 确认 service 与 timer 同名配对
ls /etc/systemd/system/backup.*
# 4. 脚本本身的问题（权限/shebang/路径），按 cron 那套排（见 [[14.1-cron]]）
```

### 案例三：list-timers 里出现「幽灵 timer」（本机实测）

```text
# 实测（本机）：list-timers --all 里有一行 test-once-job.timer，
# 但 ACTIVATES 列是空的，systemctl status 也找不到文件：
$ systemctl status test-once-job.timer
Unit test-once-job.timer could not be found.
$ systemctl cat test-once-job.timer
No files found for test-once-job.timer.
# 成因：某次实验创建后未清理（enable 的符号链接残留在
# /etc/systemd/system/timers.target.wants/ 或已加载进 systemd 内存）
```

```shell
# 处理：先 disable 再确认，必要时 daemon-reload 清内存
systemctl disable test-once-job.timer 2>&1 || true
systemctl daemon-reload
ls -la /etc/systemd/system/timers.target.wants/   # 检查残留软链
# 教训：实验用 timer 用完要 disable + 删文件，别留垃圾单元
```

### 案例四：时区/时间问题导致触发时间不对

```shell
# 1. 确认系统时区
timedatectl
#    Time zone: Asia/Shanghai (CST, +0800)
#    System clock synchronized: yes
# 2. 对比 UTC：systemd-analyze calendar 输出里有 (in UTC) 行
systemd-analyze calendar "Mon..Fri 09:00:00"
# 3. 跨时区部署：显式 Timezone= 或表达式尾缀时区，别依赖服务器本地时区
# 4. NTP 大步进后 OnCalendar 会重算，Persistent=true 才补跑
journalctl -u systemd-timesyncd | tail
```

## 常见问题

```text
Q1: 改了 timer 文件为什么不生效？
A: systemd 缓存旧配置。改完必须 systemctl daemon-reload，
   再 systemctl list-timers xxx.timer 确认 NEXT 已更新。

Q2: timer 配了但触发时报 unit not found？
A: timer 靠同名自动关联激活 service（foo.timer → foo.service）。
   检查同名 service 是否存在、是否拼写一致；也可用 Unit= 显式指定。

Q3: 关机错过触发时间，开机后没补跑？
A: Persistent 默认 false。加 Persistent=true 后，开机检测到错过
   立即补跑一次（仅对 OnCalendar 生效，单调时间触发无此概念）。

Q4: oneshot service 状态显示 dead，是失败了吗？
A: 不是。Type=oneshot 执行完即退出，dead/inactive 是正常终态。
   看 journalctl -u xxx.service 里的 "Finished" 确认成功。

Q5: 我把 cron 的 */5 * * * * 抄进 OnCalendar 为什么报错？
A: OnCalendar 不是 cron 语法，五字段顺序和含义都不同。
   每 5 分钟应写 OnCalendar=*:0/5（或 *-*-* *:0/5:00）。
   先用 systemd-analyze calendar 验证再写。

Q6: 怎么让 timer 任务在指定时区触发？
A: 两种方式：timer 里 Timezone=Asia/Shanghai，或表达式尾缀
   OnCalendar=*-*-* 03:00:00 Asia/Shanghai。系统时区由 timedatectl 管理。

Q7: 任务执行时间超过触发间隔，会重叠吗？
A: 会，timer 不管上次实例是否结束。脚本开头 flock -n 抢锁防重入，
   或 service 用 Type=oneshot + RemainAfterExit 组合判断。

Q8: systemd 版本太老，某些字段不支持？
A: OnCalendar 秒字段与 RandomizedDelaySec 需 systemd v232+（RHEL 8 起）；
   RHEL 7（systemd 219）只支持到分钟精度，无随机延迟。
   老系统确认版本：systemd --version。
```

## 面试题

```text
1. systemd timer 和 cron 的区别？什么时候用哪个？
   答：timer 集成 systemd：日志进 journald、状态可查、依赖管理、
   失败重试、Persistent 补跑、RandomizedDelaySec 错峰，触发精确到秒；
   cron 简单成熟、语法轻量。系统级/新部署任务用 timer，
   用户级小任务或兼容老环境用 cron，两者可共存。

2. timer 的两种触发方式？
   答：单调时钟（OnBootSec/OnStartupSec/OnActiveSec/OnUnitActiveSec，
   从开机或上次事件起算，不受改时间影响）和墙钟时钟（OnCalendar
   日历表达式，按本地时间/指定时区）。可混用，任一满足即触发。

3. Persistent=true 的作用和限制？
   答：记录「上次应触发未触发」的时间点，开机后补跑一次再恢复正常
   周期。只对 OnCalendar 生效；单调时间触发没有错过概念。
   适合笔记本/关机频繁机器的每日任务。

4. timer 和 service 怎么配合？
   答：同名自动关联：foo.timer 触发时激活 foo.service，无需显式配置；
   可用 Unit= 指定其他单元。service 通常 Type=oneshot 执行完退出。

5. AccuracySec 和 RandomizedDelaySec 的区别？
   答：AccuracySec 是允许触发时间偏离目标点的窗口（默认 1min），
   让 systemd 合并唤醒省电，设 1us 可精确触发；
   RandomizedDelaySec 是主动随机延迟用于错峰，避免多机同时执行。

6. 如何把现有 cron 任务迁到 timer？举例 */5 分钟任务。
   答：写 service（Type=oneshot + ExecStart）+ timer（OnCalendar=*:0/5）
   → daemon-reload → enable --now → journalctl 验证 → 删除 crontab 条目。
   注意 OnCalendar 语法与 cron 不同，先用 systemd-analyze calendar 验证。

7. 如何保证 timer 任务失败能被发现？
   答：三层：① journalctl -u 查看执行日志与退出码；
   ② service 配 OnFailure=notify-fail@%n.service 失败即告警；
   ③ 外部监控检查「上次成功时间戳」是否过期（成功时 touch 标记文件）。

8. timer 任务如何防重入（上次没跑完又触发）？
   答：脚本内 flock -n 文件锁，抢不到直接退出；或依赖 systemd
   资源限制 + 单调时间触发（OnUnitActiveSec 从上次结束起算）。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 系统级/服务级定时任务优先用 timer，用户级小任务才用 cron
2. 单元文件放 /etc/systemd/system/，改完必 `daemon-reload`
3. 配 `Persistent=true`（错过补跑）+ `RandomizedDelaySec`（错峰）
4. 所有表达式先 `systemd-analyze calendar` 验证，别凭感觉写
5. service 用 `Type=oneshot` + 绝对路径 ExecStart + 显式 `User=` 降权
6. 慢任务 flock 防重入；失败用 `OnFailure=` 告警
7. 定时任务资源受限：Nice=19 / CPUQuota= / MemoryMax=，参考 logrotate.service
8. 复用 systemd 沙箱加固选项（PrivateTmp/ProtectSystem）收窄攻击面
9. 实验 timer 用完 disable + 删文件，定期 `list-timers --all` 审查清理
10. 需要精确秒级执行时 AccuracySec=1us，否则保持默认省电

### 踩坑记录

```text
坑 1：改了 timer 文件没 daemon-reload，不生效
结论：改了 OnCalendar，NEXT 还是旧时间，任务照旧时间跑。
原因：systemd 缓存了旧单元文件，不会自动重读。
解法：改完 systemctl daemon-reload，再 list-timers 确认 NEXT 更新。

坑 2：把 cron 语法直接抄进 OnCalendar，报错或语义全错
结论：OnCalendar=*/5 * * * * 直接报 "Failed to parse"，或者
     把五字段当成日期解析，触发时间完全不对。
原因：OnCalendar 是「星期 日期 时间」三段式，不是 cron 的「分时日月周」。
解法：每 5 分钟写 *:0/15；所有表达式先 systemd-analyze calendar 验证。

坑 3：timer 配了但没写同名 service，触发报 unit not found
结论：timer 到点触发，journald 报 "Unit xxx.service could not be found"。
原因：timer 默认激活同名 service，service 不存在或名字拼错。
解法：确认 foo.timer ↔ foo.service 同名；或用 [Timer] Unit= 显式指定。

坑 4：没配 Persistent，关机期间的任务没补跑
结论：机器关机错过触发时间，开机后任务没执行，备份漏了一天。
原因：Persistent 默认 false，错过即丢弃。
解法：OnCalendar 任务加 Persistent=true；注意它只对墙钟触发生效。

坑 5：AccuracySec 默认 1 分钟，任务比预期晚跑
结论：设了 03:00:00，结果 03:00:40 才跑，以为系统有问题。
原因：AccuracySec 默认 1min，允许在目标点前后 1 分钟内浮动，
     这是特性不是 bug（省电合并唤醒）。
解法：要求精确就显式 AccuracySec=1us。

坑 6：时区不对，触发时间差 8 小时
结论：跨时区部署后任务在 UTC 时间触发，跟本地差 8 小时。
原因：OnCalendar 默认按系统本地时区解析；服务器时区被改/不一致。
解法：timer 里 Timezone=Asia/Shanghai 显式指定；
     systemd-analyze calendar 输出里的 (in UTC) 行用来核对。

坑 7：oneshot service 反复显示 dead/failed，以为任务失败
结论：list-timers 里 service 状态 dead，怀疑执行失败，手动 start 又正常。
原因：Type=oneshot 执行完即退出，dead 是正常终态；真失败会显示 failed
     并在 journald 有 error 日志。
解法：看 journalctl -u xxx.service 的 "Finished" 行和退出码判断。

坑 8：慢任务重叠执行，数据竞争/资源打满
结论：同步任务跑 40 分钟，间隔 30 分钟，两个实例叠在一起。
原因：timer 不管上次实例是否结束，到点就再激活。
解法：脚本 flock -n 抢锁防重入；或用 OnUnitActiveSec 从上次结束起算。

坑 9：list-timers 出现幽灵 timer（本机实测 test-once-job.timer）
结论：list-timers --all 里有残留 timer，ACTIVATES 为空，
     status 报 "Unit could not be found"。
原因：实验时 enable 过但没清理，符号链接残留在 timers.target.wants/。
解法：systemctl disable 清理 + daemon-reload；实验单元用完即删。
```
