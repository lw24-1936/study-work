## 概述

信号是进程间「异步通知」的机制——一个进程（或内核）给另一个进程发信号，通知它「发生了一件事」。信号是 kill 命令的本质（kill 就是发信号），也是 Ctrl+C、进程崩溃（段错误）、子进程退出等事件背后的机制。理解常用信号（SIGTERM/SIGKILL/SIGINT/SIGHUP）和 trap 捕获信号，才能优雅地管理进程和写健壮的脚本。

```text
信号核心概念：
1. 机制 —— 异步通知，内核/进程发送，目标进程可捕获处理或忽略
2. 常用 —— SIGTERM(15) 优雅终止、SIGKILL(9) 强杀、SIGINT(2) 中断、SIGHUP(1) 挂断
3. 捕获 —— trap 在 shell 里捕获信号执行清理，实现优雅退出
```

## 核心概念

### 信号机制

信号的完整流程：发送方（内核或进程用 kill）→ 目标进程收到 → 三种响应之一（默认动作 / 捕获执行 handler / 忽略）。信号是异步的，进程在执行任何指令时都可能收到。两个特殊信号不能捕获也不能忽略：SIGKILL（9）和 SIGSTOP（19）。每个信号有默认动作（终止、忽略、终止+core dump、停止）。

```text
# 实测（信号完整列表）
$ kill -l
 1) SIGHUP   2) SIGINT   3) SIGQUIT   4) SIGILL   5) SIGTRAP
 9) SIGKILL 10) SIGUSR1 15) SIGTERM 17) SIGCHLD 18) SIGCONT 19) SIGSTOP
...
# 1-31 是标准信号，34+ 是实时信号（SIGRTMIN~SIGRTMAX）
```

```text
信号响应三选一：
1. 默认动作 —— 每个信号有默认行为（终止/忽略/core dump/停止）
2. 捕获处理 —— 进程注册 handler，收到信号执行自定义逻辑
3. 忽略 —— 显式忽略（但 SIGKILL/SIGSTOP 不能捕获也不能忽略）
```

按「是什么 → 为什么 → 怎么用 → 边界」把信号机制拆开看：

- 是什么：信号是「软中断」，一种短小的异步事件通知，携带的信息只有信号编号（少数实时信号可附带数据）。
- 为什么：进程是被动执行的，需要一种机制让「外部事件」能打断它——比如 Ctrl+C 停止前台任务、父进程得知子进程退出、内核告知「你访问了非法内存」。
- 怎么用：发信号用 kill/pkill/raise()；处理信号用 trap（shell）或 signal()/sigaction()（C）；查看全部信号用 `kill -l`。
- 边界/易错点：信号不排队（标准信号重复发送会合并）、handler 里不能随意调用非异步安全函数、SIGKILL/SIGSTOP 无法捕获/忽略/屏蔽。

### 常用信号（SIGTERM / SIGKILL / SIGINT / SIGHUP）

几个信号必须记住：SIGTERM（15，优雅终止，默认 kill 发的）、SIGKILL（9，强杀，不可捕获）、SIGINT（2，Ctrl+C 中断）、SIGHUP（1，终端挂断，常用来让服务重载配置）、SIGQUIT（3，退出+core dump）、SIGSTOP/SIGCONT（19/18，暂停/继续）。约定「杀进程先 15 后 9」，因为 SIGTERM 给进程清理机会，SIGKILL 直接强杀不留情。

```text
常用信号速查：
SIGHUP  1   终端挂断，服务常用来「重载配置」（nginx -s reload 就是发 HUP）
SIGINT  2   Ctrl+C 中断前台进程
SIGQUIT 3   退出并产生 core dump（Ctrl+\）
SIGKILL 9   强制终止，不可捕获/忽略，最后手段
SIGTERM 15  优雅终止（默认 kill），给进程清理机会
SIGSTOP 19  暂停，不可捕获
SIGCONT 18  继续
SIGUSR1/2 10/12  用户自定义信号
SIGCHLD 17  子进程退出通知父进程
```

```shell
kill -15 1234        # SIGTERM 优雅终止（默认）
kill -TERM 1234      # 等价写法
kill -9 1234         # SIGKILL 强杀
kill -HUP 1234       # SIGHUP，让服务重载配置
kill -USR1 1234      # 自定义信号
```

四个最常用信号逐个看，理解它们的「默认动作 + 典型用途 + 边界」：

**SIGTERM（15）——优雅终止的默认选择**

- 是什么：请求进程「请你自己退出」。
- 为什么：给进程一个清理窗口——刷盘、关闭连接、释放锁，之后体面退出。
- 怎么用：`kill <PID>` 不写信号默认就是 SIGTERM；systemctl stop 也是先发 SIGTERM。
- 边界：进程可以捕获它执行收尾逻辑；如果进程选择忽略 SIGTERM，就只能升级到 SIGKILL。约定先 15 后 9。

**SIGKILL（9）——最后手段的强杀**

- 是什么：内核直接把进程终止，进程完全无法干预。
- 为什么：当进程卡死、忽略 SIGTERM、处于无法中断的状态时，必须有一个「保证能杀掉」的手段。
- 怎么用：`kill -9 <PID>`。只在 SIGTERM 无效后再用。
- 边界/易错点：不可捕获、不可忽略、不可屏蔽；进程来不及刷盘/关连接，可能丢数据、留垃圾文件。杀数据库进程尤其危险。

**SIGINT（2）——Ctrl+C 中断**

- 是什么：用户在终端按 Ctrl+C，终端驱动向前台进程组广播 SIGINT。
- 为什么：交互式场景下给用户「停下来」的控制权。
- 怎么用：`Ctrl+C` 直接触发；脚本里 `trap ... INT` 捕获。
- 边界：只发给「前台进程组」；后台任务（& 启动）收不到 Ctrl+C；进程处于 D 状态（不可中断睡眠）时 SIGINT 被挂起。

**SIGHUP（1）——挂断，兼作「重载配置」约定**

- 是什么：控制终端挂断（SSH 断开、终端窗口关闭）时，内核发给会话首进程的信号。
- 为什么：终端没了，依附它的进程应该知道「你的终端消失了」。守护进程常用它做「重新读配置」——因为守护进程没有终端，SIGHUP 这个信号就空出来被借用作 reload。
- 怎么用：`kill -HUP <PID>`、`nginx -s reload`（内部就是发 HUP）；nohup 的原理就是让进程忽略 SIGHUP。
- 边界：SIGHUP 的默认动作是终止，所以 SSH 断开后普通前台进程会被杀；只有忽略它（nohup）或捕获它（做 reload）的进程才不受影响。

### signal 与 trap

trap 是 shell 捕获信号的命令：`trap '命令' 信号` 指定收到信号时执行什么。最常见的 `trap 'rm -f "$tmpfile"' EXIT`（脚本退出时清理临时文件）、`trap 'echo 收到中断' INT TERM`（收到中断/终止时执行）。trap 让脚本能「优雅退出」——收到 Ctrl+C 或 kill 时先清理再退出，不留垃圾文件、不破坏数据。EXIT 是伪信号，脚本退出（无论正常还是异常）都触发。

```bash
#!/usr/bin/env bash
trap 'echo "收到 SIGINT，执行清理..."; exit 1' INT
trap 'echo "脚本退出，收尾清理"' EXIT

echo "按 Ctrl+C 可测试信号捕获"
sleep 10
```

```text
# 实测（trap EXIT 在退出时触发）
$ bash -c 'trap "echo 捕获到 EXIT 信号" EXIT; echo 主逻辑'
主逻辑
捕获到 EXIT 信号
```

trap 的完整用法：

```bash
trap 'echo 收到中断' INT TERM      # 多个信号绑定同一个 handler
trap 'echo 忽略挂断' '' HUP        # 空字符串 = 忽略该信号
trap - INT                        # 恢复 INT 的默认处理
trap -p                           # 打印当前所有 trap 设置
trap 'cleanup' EXIT               # EXIT 伪信号，退出（含正常/异常）都触发
```

```text
trap 易错点：
1. 单引号延迟展开 —— trap 'echo $PID' EXIT 打印的是退出时的值，双引号才是定义时快照
2. EXIT 会覆盖 —— 脚本里只能有一个 trap EXIT，后写的覆盖先写的
3. 子 shell 不继承 —— 管道/子 shell 里的 trap 不影响父 shell
4. trap 绑定的信号在执行 handler 期间，同一信号默认被忽略（防重入）
```

C 语言层面的 signal 处理（signal() 与 sigaction()）：

```c
// signal_demo.c —— 捕获 SIGINT/SIGTERM，优雅退出
#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <unistd.h>

// handler 里只能用 volatile sig_atomic_t，保证异步安全
static volatile sig_atomic_t stop = 0;

void handler(int sig) {
    stop = 1;              // 只置标志位，不做重活
}

int main(void) {
    struct sigaction sa;
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);   // 处理期间不额外屏蔽其它信号
    sa.sa_flags = SA_RESTART;   // 被打断的慢系统调用自动重启
    sigaction(SIGINT,  &sa, NULL);
    sigaction(SIGTERM, &sa, NULL);

    printf("PID=%d 等待信号（Ctrl+C 或 kill -TERM）...\n", getpid());
    while (!stop)
        pause();                 // 挂起直到收到信号

    printf("收到信号，开始收尾清理...\n");
    // 这里放刷盘、关闭连接等清理逻辑
    return 0;
}
```

```shell
gcc -o signal_demo signal_demo.c   # 编译
./signal_demo &                    # 后台运行，记下 PID
kill -TERM <PID>                   # 触发优雅退出
```

## 工作原理

信号在内核层的投递分三步：发送方调用 kill()/raise() 系统调用 → 内核在目标进程的 task_struct 里设置「挂起信号」位图 → 目标进程被调度运行时，内核在从内核态返回用户态前检查挂起信号，决定执行默认动作还是调用用户注册的 handler。信号不排队（标准信号），同一种信号在挂起期间重复发送会合并。

```text
信号投递流程：
发送方 kill() → 内核设置目标进程挂起信号位 → 目标进程调度运行
→ 内核态返回用户态前检查信号 → 默认动作 / 执行 handler / 忽略

关键点：
1. 信号是异步的，进程在执行任意指令时都可能被打断
2. handler 在用户态执行，执行完回到被打断的位置继续
3. 标准信号不排队，重复发送会合并（实时信号可排队）
```

每个进程在 task_struct 里有两张 64 位的信号位图（标准 1-31 + 实时 34-64），分别记录「哪些信号被屏蔽（blocked）」和「哪些信号挂起待处理（pending）」。发送信号 = 内核往 pending 位图里置位；进程从内核态返回用户态时，挑一个「未屏蔽且挂起」的信号来处理。

```text
三个概念必须分清：
1. 默认动作（default）—— 没注册 handler 时内核按信号默认行为处理（终止/忽略/core/停止）
2. 屏蔽（block）—— 信号到达后先挂起不投递，解除屏蔽后才处理；SIGKILL/SIGSTOP 不能屏蔽
3. 忽略（ignore）—— 信号到达直接丢弃；与「屏蔽后解除」不同，忽略的不会再补投递

屏蔽 vs 忽略的区别：屏蔽是「暂时不处理，稍后补」，忽略是「直接扔了，不再处理」
```

handler 执行的安全边界（为什么 handler 里要极简）：

```text
handler 是在「进程正在执行任意代码的某个瞬间」插入执行的，可能打断 malloc、
printf、加锁等非原子操作。如果在 handler 里再次调用这些函数（重入），可能：
1. malloc 内部结构被打断 → 死锁或堆损坏
2. printf 拿不到内部锁 → 死锁
3. errno 被覆盖 → 主流程读到错误值

所以 handler 里只做「最少的异步安全操作」：写 volatile sig_atomic_t 标志、
调用 write()/_exit() 等 async-signal-safe 函数，其余交给主流程轮询处理。
```

## 常用命令与配置

```shell
kill -l                 # 列出所有信号
kill -TERM <PID>        # 优雅终止（默认）
kill -9 <PID>           # 强杀
kill -HUP <PID>         # 重载配置
kill -0 <PID>           # 发「信号 0」：只检查进程是否存在（不真发信号）
pkill -TERM nginx       # 按名字发信号
pkill -f 'python.*app'  # 按完整命令行匹配发信号
killall -HUP nginx      # 给所有同名进程发 HUP
kill -USR1 <PID>        # 自定义信号（如日志切割）
timeout 30 slow_cmd     # 30 秒后发 SIGTERM，超时自动终止
timeout -k 5 30 cmd     # SIGTERM 后再给 5 秒，不退则 SIGKILL
```

```text
信号发送的工具：
kill     按 PID 发信号（负数 PID 表示进程组，如 kill -TERM -1234）
pkill    按进程名/模式发信号，支持 -f 匹配完整命令行
killall  按进程名发信号（给所有同名进程）
timeout  给命令加时间上限，超时自动发 SIGTERM（-k 后升级 SIGKILL）
fuser    -k 给「占用某文件/端口」的进程发信号（如 fuser -k 8080/tcp）
```

```text
kill -0 的实际用途：判断进程是否存活（脚本里常用）
if kill -0 "$pid" 2>/dev/null; then
    echo "进程 $pid 还活着"
else
    echo "进程 $pid 不存在（或没有权限）"
fi
```

## 配置文件解析

信号本身没有配置文件，但服务怎么响应「终止信号」在 systemd 单元里可配：

```text
# /etc/systemd/system/xxx.service —— 控制服务停止时收到的信号
[Service]
KillSignal=SIGTERM      # systemctl stop 时发的信号（默认 SIGTERM）
TimeoutStopSec=10       # 发信号后等多久，超时才 SIGKILL
KillMode=control-group  # 杀整个 cgroup 还是只杀主进程
SuccessExitStatus=143   # 把 SIGTERM 退出码(128+15)当正常退出
```

```text
内核相关（/proc/sys/kernel/core_pattern）：
收到 SIGQUIT/SIGSEGV 等会触发 core dump，core_pattern 决定 dump 文件生成路径
```

进程当前「屏蔽/捕获了哪些信号」在 /proc 里可直接看：

```text
# /proc/<PID>/status 里的信号位图字段
SigPnd   —— 挂起待处理的信号（进程级）
SigBlk   —— 被屏蔽的信号（blocked）
SigIgn   —— 被忽略的信号
SigCgt   —— 被捕获的信号（注册了 handler）

# 位图是 16 进制，bit0 对应信号 1（SIGHUP），bitN 对应信号 N+1
$ grep '^Sig' /proc/self/status
```

```text
core dump 大小限制（/etc/security/limits.conf 或 ulimit）：
ulimit -c unlimited   # 允许生成 core dump
ulimit -c 0           # 禁止生成 core dump（生产常用，防敏感信息泄露+占磁盘）
```

## 应用场景实战

### 场景一：优雅重启 nginx（重载配置不中断服务）

```shell
# nginx 收到 HUP 信号会重新加载配置（不中断连接）
kill -HUP $(cat /var/run/nginx.pid)
# 或直接
nginx -s reload
# 对比：SIGTERM 是停止，HUP 是重载
```

### 场景二：脚本捕获中断信号做清理

```bash
#!/usr/bin/env bash
tmpfile=$(mktemp)
trap 'rm -f "$tmpfile"; echo "已清理，退出"; exit 1' INT TERM EXIT

echo "生成数据..."
echo "processing" > "$tmpfile"
sleep 60    # 期间 Ctrl+C 会触发清理
```

### 场景三：用 trap 写一个「可优雅停止」的长驻脚本

生产里常见的模式：脚本跑一个 while 循环干活，收到 SIGTERM/SIGINT 时先把手头的活收尾再退出，而不是被硬杀在半路。

```bash
#!/usr/bin/env bash
# worker.sh —— 收到终止信号后优雅退出
stop=0
trap 'echo "收到终止信号，收尾中..."; stop=1' TERM INT

process_task() {
    echo "处理一批数据..."
    sleep 2   # 模拟耗时任务
}

while (( stop == 0 )); do
    process_task
done
echo "已完成收尾，正常退出"
```

```shell
# 测试：后台跑起来，发 SIGTERM，观察它走完当前循环再退出
./worker.sh &          # 记下 PID
kill -TERM <PID>       # 不会立刻死，走完当前循环体面退出
```

配合 systemd 的 StopTimeoutSec，这套「先 SIGTERM 优雅停、超时再 SIGKILL」就是服务的标准停法。

## 性能与调优

```text
1. 优雅停止 —— 服务用 SIGTERM 做收尾（flush 缓冲、关闭连接），比 SIGKILL 更「干净」
2. 信号风暴 —— 大量进程同时收到信号，处理开销大，注意别在循环里狂发信号
3. 重载用 SIGHUP —— nginx 等用 HUP 重载配置，比 restart 快且不中断连接
4. 自定义信号做运维 —— SIGUSR1 触发日志切割，比 cron 定时更实时
5. 慢系统调用被信号打断 —— read/sleep 等被打断会返回 EINTR，高性能服务要处理 SA_RESTART 或重试
6. 减少 kill 轮询 —— 用 kill -0 判断存活比 ps | grep 快得多，脚本循环里优先用它
```

## 安全与权限

```text
1. 发信号要权限 —— 只能给同 UID 的进程发信号，跨用户/给 root 发要 root 权限
2. SIGKILL/SIGSTOP 不可捕获 —— 别指望进程收到 KILL 还能做清理
3. 核心转储可能泄露敏感信息 —— core dump 含内存内容（可能有密码），生产谨慎开启
4. 别用信号做敏感控制 —— 自定义信号（USR1/USR2）无鉴权，能发信号的用户都能触发
5. 信号可能被用于拒绝服务 —— 疯狂发信号打断进程正常逻辑（信号风暴），可限制进程的资源使用
6. handler 权限 —— 信号 handler 以进程自身权限执行，别在 handler 里做提权相关操作
```

## 故障排查

### 进程收不到信号 / 杀不掉

```shell
# 1. 看进程状态（D 状态信号被挂起）
ps -o pid,stat,comm -p <PID>
# 2. 看信号是否被进程忽略/阻塞
cat /proc/<PID>/status | grep -i sig
# 3. D 状态等 IO，信号要等 IO 返回才处理
cat /proc/<PID>/wchan
```

### 服务 stop 卡住很久

```shell
# 1. systemctl stop 卡住，多半是服务没响应 SIGTERM
systemctl status <服务>
# 2. 看单元的超时配置
systemctl show <服务> -p TimeoutStopUSec
# 3. 确认服务是否正确处理 SIGTERM，超时后 systemd 会发 SIGKILL
```

### 大量僵尸进程（父进程没处理 SIGCHLD）

```shell
# 1. 看僵尸进程（STAT 带 Z）
ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/'
# 2. 找父进程
ps -o pid,ppid,stat,comm -p <僵尸的PPID>
# 3. 根因：父进程没捕获 SIGCHLD、没调用 wait 回收子进程
```

## 常见问题

```text
Q1: SIGTERM 和 SIGKILL 的本质区别？
A: SIGTERM 可被捕获，进程能做清理后优雅退出；SIGKILL 不可捕获，内核直接终止，不清理。约定先 15 后 9。

Q2: 为什么 Ctrl+C 有时杀不掉前台进程？
A: 进程可能处于 D 状态（不可中断睡眠等 IO），信号被挂起，要等 IO 返回才处理；或进程显式忽略了 SIGINT。

Q3: SIGHUP 的常见用途？
A: 终端挂断通知（SSH 断开），以及让守护进程重载配置（nginx -s reload、很多服务收到 HUP 就重新读配置）。

Q4: trap EXIT 和 trap INT 有什么区别？
A: EXIT 是伪信号，脚本无论正常还是异常退出都触发；INT 只在收到 SIGINT（Ctrl+C）时触发。清理收尾常用 EXIT。

Q5: 信号能被「屏蔽」吗？和「忽略」有什么区别？
A: 能，用 sigprocmask（C）把信号加入屏蔽集，信号到达后挂起、解除屏蔽后再投递；忽略是直接丢弃不补。SIGKILL/SIGSTOP 两者都无效。

Q6: SIGCHLD 是干什么的？
A: 子进程退出/停止时，内核给父进程发 SIGCHLD。父进程应在 handler 里调用 wait/waitpid 回收子进程，否则产生僵尸进程。

Q7: kill -0 真的会发信号吗？
A: 不会。信号编号 0 是「空信号」，内核只做存在性和权限检查，不发任何信号，脚本用它判断进程是否存活。
```

## 面试题

```text
1. 哪些信号不可捕获、不可忽略？
   答：SIGKILL(9) 和 SIGSTOP(19)，内核强制处理，进程无法干预。

2. 怎么让一个脚本「优雅退出」（清理临时文件）？
   答：用 trap '清理命令' EXIT INT TERM，脚本退出或收到中断/终止信号时先执行清理再退出。

3. 进程收到信号的三种响应？
   答：默认动作（终止/忽略/core dump/停止）、捕获执行 handler、显式忽略。SIGKILL/SIGSTOP 只能默认动作。

4. 为什么 SIGKILL 杀数据库进程危险？
   答：SIGKILL 不给清理机会，缓冲区的脏数据没刷盘就丢失，可能导致数据损坏。应先用 SIGTERM 优雅停。

5. 信号屏蔽（block）和忽略（ignore）的区别？
   答：屏蔽是「暂时挂起不投递」，解除屏蔽后信号会补投递；忽略是「直接丢弃不再处理」。屏蔽用 sigprocmask，忽略用 SIG_IGN。

6. signal() 和 sigaction() 有什么区别？
   答：signal() 行为跨平台不一致、handler 执行期间信号可能被重置为默认；sigaction() 更可靠，能指定屏蔽集、SA_RESTART 等标志，推荐用 sigaction。

7. 什么是僵尸进程？它和信号有什么关系？
   答：子进程退出后父进程没调用 wait 回收，子进程残留为僵尸（STAT 为 Z）。内核通过 SIGCHLD 通知父进程，父进程应处理 SIGCHLD 并 wait 回收。

8. 标准信号和实时信号的区别？
   答：标准信号（1-31）不排队，同信号挂起期间重复发送会合并；实时信号（SIGRTMIN~SIGRTMAX）可排队、能附带数据、支持优先级。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 杀进程先 SIGTERM（优雅），等一会不退再 SIGKILL（强杀）
2. 服务重载配置用 SIGHUP（nginx -s reload），别粗暴 restart 中断服务
3. 脚本写临时文件必须 trap 'rm -f ...' EXIT 清理，异常退出也不留垃圾
4. 用 SIGUSR1/SIGUSR2 做自定义触发（如日志切割、状态切换）
5. 记住 SIGKILL/SIGSTOP 不可捕获，别指望进程「收到 KILL 还能清理」
6. 信号 handler 里保持极简，只置 volatile sig_atomic_t 标志，重活交给主流程轮询
7. 长时间任务用 timeout 加超时，避免进程卡死一直占资源

### 踩坑记录

```text
坑 1：kill -9 杀进程不留清理机会
结论：kill -9 后数据库/文件缓冲没刷盘，数据损坏。
原因：SIGKILL 不可捕获，进程来不及清理就死。
解法：先 SIGTERM 优雅停，超时再 -9。

坑 2：Ctrl+C 杀不掉正在等的进程
结论：前台进程卡在等 IO，Ctrl+C（SIGINT）没反应。
原因：进程处于 D 状态（不可中断睡眠），信号被挂起。
解法：等 IO 返回，或另开终端 kill；D 状态 kill 也无效。

坑 3：trap 里用单引号变量延迟展开
结论：trap 'echo $PID' EXIT 打印的是退出时的值，不是定义时的。
原因：单引号延迟展开，trap 触发时才解析。
解法：要定义时快照用双引号 trap "echo $PID" EXIT。

坑 4：nohup 没挡住 SIGHUP 之外的信号
结论：nohup 只能挡 HUP，进程还是会被 SIGTERM/SIGINT 杀。
原因：nohup 只忽略 SIGHUP，不忽略其他终止信号。
解法：要完全脱离用 setsid 或 systemd 托管。

坑 5：SIGUSR1 被程序当成别的用途
结论：给程序发 USR1 没反应或行为异常。
原因：SIGUSR1 是自定义信号，不同程序用途不同（有的做日志轮转、有的做其它）。
解法：发自定义信号前查程序文档，确认它的信号约定。

坑 6：kill -TERM 后进程没立刻退出，误判为杀不掉
结论：发了 SIGTERM 进程还在，以为没生效又去 kill -9。
原因：进程收到 SIGTERM 正在做清理（刷盘、关连接），需要时间。
解法：发 SIGTERM 后给个观察窗口（如 systemd 的 TimeoutStopSec），确实不退再升级 -9。

坑 7：C 程序 handler 里调用非异步安全函数导致死锁
结论：handler 里调用 printf/malloc，程序偶发死锁或数据损坏。
原因：handler 可能打断正在执行 printf/malloc 的主流程，重入这些函数导致锁/结构损坏。
解法：handler 里只做极简异步安全操作（置标志、write），重活回主流程。
```
