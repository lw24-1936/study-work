## 概述

守护进程（daemon）是「后台长期运行、不依赖终端」的进程，提供持续服务（nginx、mysql、sshd 都是守护进程）。特征：后台运行、脱离控制终端、PPID 通常是 1（systemd）、生命周期长。管理方式：临时用 nohup 脱离、标准用 systemd 托管（开机自启、崩溃重启、日志收集）。守护进程的输出要重定向（文件或 syslog），否则日志会丢失。

```text
守护进程三件事：
1. 特征 —— 后台运行、脱离终端、PPID=1、长期存活
2. 托管 —— nohup 临时脱离 / systemd 标准托管（自启、重启、日志）
3. 日志 —— 输出重定向到文件或 syslog，不重定向就丢
```

## 核心概念

### 守护进程特征

守护进程区别于普通进程的几个特征：后台运行（不占终端）、脱离控制终端（关 SSH 不影响它）、父进程是 init/systemd（PPID=1，因为原父进程退出后被 systemd 收养）、无标准输入输出（或重定向到日志）。`ps -ef` 里 TTY 是 `?`、STAT 带 `s`（会话领导）的多半是守护进程。名字习惯以 `d` 结尾（sshd、nginx 的 daemon、mysqld）。

```text
守护进程识别特征：
1. TTY 是 ? —— 不绑定终端，ps -ef 的 TTY 列是问号
2. PPID=1 —— 父进程是 systemd（被收养）
3. 名字带 d —— sshd、mysqld、dockerd（约定，非强制）
```

```text
# 实测（本机运行的守护进程服务）
$ systemctl list-units --type=service --state=running | head
1panel-agent.service    loaded active running 1Panel ...
1panel-core.service     loaded active running 1Panel ...
containerd.service      loaded active running containerd container runtime
# 这些服务都是 systemd 托管的守护进程，后台常驻
```

### nohup

nohup 让命令「忽略 SIGHUP 信号」——终端挂断（SSH 断开）时，普通进程会收到 SIGHUP 被终止，nohup 的进程不受影响、继续跑。典型用法 `nohup 命令 > log 2>&1 &`：后台运行 + 忽略挂断 + 输出重定向。适合「临时跑个长任务、不想被 SSH 断开影响」，但不如 systemd 可靠（不自动重启、不开机自启）。

```shell
nohup ./long_task.sh > task.log 2>&1 &
# 拆解：nohup 忽略 SIGHUP、& 后台、> 重定向 stdout、2>&1 合并 stderr
disown        # 把后台作业从 shell 脱离（可选）
```

```text
nohup 的局限：
1. 不自动重启 —— 进程挂了不会拉起
2. 不开机自启 —— 重启系统后要手动再跑
3. 不管理依赖 —— 不保证启动顺序
# 要这些能力就用 systemd
```

### systemd 托管

systemd 是守护进程的标准托管方式：写一个 service 单元文件（ExecStart 指定启动命令），就能获得开机自启、崩溃自动重启、日志收集（journalctl）、依赖管理（After/Requires）。这是生产环境跑服务的标准做法——比 nohup 可靠得多。service 文件的编写见 10.3 编写 Service Unit。

```shell
# 写 service 单元
cat > /etc/systemd/system/myapp.service <<'EOF'
[Unit]
Description=My App
After=network.target

[Service]
ExecStart=/opt/myapp/bin/myapp
Restart=always

[Install]
WantedBy=multi-user.target
EOF

# 启用并启动
systemctl daemon-reload
systemctl enable --now myapp
systemctl status myapp
```

### 日志重定向

守护进程没有终端，标准输出/错误必须重定向，否则日志丢失。三种去向：重定向到文件（`> /var/log/app.log 2>&1`）、交给 syslog/journal（systemd 自动收集）、用日志库写文件。systemd 托管的服务，stdout/stderr 自动进 journald（journalctl -u 服务名 查看）。传统 daemon 常用 `>> /var/log/xxx.log` 追加日志。

```shell
# 方式一：重定向到文件
nohup ./app >> /var/log/app.log 2>&1 &

# 方式二：systemd 托管，日志自动进 journald
systemctl start myapp
journalctl -u myapp -f        # 实时看服务日志
journalctl -u myapp --since "1 hour ago"
```

## 工作原理

守护进程「脱离终端」靠一组标准步骤：调用 setsid 创建新会话（脱离原控制终端）、fork 出子进程并让父进程退出（子进程 PPID 变成 1）、切换工作目录到 /、关闭或重定向标准输入输出。传统 daemon 常做「double-fork」确保进程不会重新获得控制终端；现代的 systemd 直接把服务作为自己的子进程拉起，天然脱离终端，无需程序自己 double-fork。

```text
传统 daemon 化步骤：
1. fork 子进程，父进程退出（子进程被 init/systemd 收养，PPID=1）
2. setsid 创建新会话，脱离原控制终端
3. chdir("/") 切换工作目录，避免占用挂载点
4. 关闭 stdin/stdout/stderr 或重定向到日志文件

现代做法：systemd 直接 fork 服务进程，进程无需自己 daemon 化
（Type=simple 时 systemd 认为主进程就是守护进程本身）
```

## 常用命令与配置

```shell
systemctl status <服务>       # 看服务状态
systemctl enable --now <服务> # 开机自启 + 立即启动
systemctl restart <服务>      # 重启
journalctl -u <服务> -f       # 实时看服务日志
nohup ./app > app.log 2>&1 &  # 临时脱离终端后台跑
```

```text
守护进程管理两条路：
1. systemd —— 生产标准，自启/重启/日志/依赖一站式
2. nohup/setsid —— 临时任务，跑完就扔
```

## 配置文件解析

守护进程的「配置」就是 systemd service 单元文件，核心段如下：

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My App              # 描述
After=network.target            # 依赖：网络就绪后才启动

[Service]
Type=simple                     # 启动类型（simple/forking/notify/oneshot）
ExecStart=/opt/myapp/bin/myapp  # 启动命令
Restart=always                  # 崩溃自动重启
RestartSec=5                    # 重启间隔
StandardOutput=append:/var/log/myapp.log   # stdout 落盘
StandardError=append:/var/log/myapp.log    # stderr 落盘

[Install]
WantedBy=multi-user.target      # 开机自启目标
```

```text
关键字段：
Type=simple   主进程即服务进程（最常见）
Type=forking  程序自己 fork 后台，systemd 等父进程退出（传统 daemon）
Restart       always/on-failure，控制崩溃重启
StandardOutput  不配则 stdout 进 journald
```

## 应用场景实战

### 场景一：把自研服务做成 systemd 守护进程

```shell
# 1. 写 service 文件
cat > /etc/systemd/system/myapp.service <<'EOF'
[Unit]
Description=My Application
After=network.target

[Service]
Type=simple
ExecStart=/opt/myapp/bin/myapp
Restart=always
RestartSec=5
StandardOutput=append:/var/log/myapp.log
StandardError=append:/var/log/myapp.log

[Install]
WantedBy=multi-user.target
EOF
# 2. 启用自启 + 启动
systemctl daemon-reload
systemctl enable --now myapp
# 3. 验证
systemctl status myapp
```

### 场景二：临时后台跑脚本并用 nohup 保活

```shell
# 后台跑一个长任务，SSH 断开也不停
nohup ./data_sync.sh > /var/log/data_sync.log 2>&1 &
echo "PID: $!"
# 查看进度
tail -f /var/log/data_sync.log
```

## 性能与调优

```text
1. Type 选对 —— simple 适合前台程序，forking 适合自 daemon 化的老程序，选错 systemd 会误判退出
2. RestartSec 别太小 —— 崩溃服务短间隔反复重启会刷爆日志、占资源
3. 日志落盘用 StandardOutput —— 比让进程自己写文件更统一，journald 还能轮转
4. 限制服务资源 —— 用 MemoryMax/CPUQuota 防止单个守护进程吃满整机
5. 大量守护进程用 LimitNOFILE 调大文件描述符，避免 too many open files
```

## 安全与权限

```text
1. 别用 root 跑服务 —— systemd 单元里用 User=/Group= 降权运行，最小权限原则
2. 服务日志防泄露 —— 日志文件权限收紧，别让普通用户读到敏感信息
3. systemd 单元文件可被篡改 —— 只 root 可写 /etc/systemd/system/
4. 提权服务要隔离 —— 需要特定能力的服务用 CapabilityBoundingSet= 而非直接 root
5. nohup 临时任务注意清理 —— 跑完确认退出，别留僵尸后台进程
```

## 故障排查

### systemd 服务起不来

```shell
# 1. 看状态和退出码
systemctl status myapp
# 2. 看服务日志（启动失败的具体报错）
journalctl -u myapp -n 50 --no-pager
# 3. 手动跑 ExecStart 的命令验证
/opt/myapp/bin/myapp
```

### 服务反复重启（Restart 循环）

```shell
# 1. 确认是否在疯狂重启
systemctl status myapp | grep -E 'Active|Main PID'
# 2. 看每次退出的原因
journalctl -u myapp -n 100 --no-pager | grep -iE 'error|fail|exit'
# 3. 临时停止排查，别让它继续刷日志
systemctl stop myapp
```

## 常见问题

```text
Q1: nohup 和 systemd 托管怎么选？
A: 临时跑一次的任务用 nohup，正式服务用 systemd（要自启、崩溃重启、日志管理）。

Q2: 为什么守护进程的 PPID 是 1？
A: 原父进程退出后，孤儿进程被 systemd（PID 1）收养。传统 daemon double-fork 主动让父进程退出，也是为了让进程变成 PPID=1。

Q3: Type=simple 和 Type=forking 有什么区别？
A: simple 认为 ExecStart 启动的进程就是服务主进程；forking 认为程序会自己 fork 到后台，systemd 等原进程退出后跟踪子进程。老式 daemon 用 forking。

Q4: systemd 服务的日志去哪了？
A: stdout/stderr 默认进 journald（journalctl -u 服务 查看）；配了 StandardOutput= 则落到指定文件。
```

## 面试题

```text
1. 什么是守护进程？有哪些特征？
   答：后台长期运行、脱离控制终端、PPID=1、不依赖终端的进程。ps 里 TTY 是 ?、名字常带 d。

2. 传统 daemon 化的步骤？
   答：fork 父进程退出、setsid 脱离终端、chdir 切工作目录、重定向/关闭标准 IO。现在常用 systemd 托管替代。

3. nohup 的原理？
   答：让进程忽略 SIGHUP 信号，终端挂断（SSH 断开）时进程不被杀，配合 & 后台运行。

4. systemd 相比 nohup 的优势？
   答：开机自启、崩溃自动重启（Restart=）、日志收集（journald）、依赖管理（After/Requires）、资源限制。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产服务一律 systemd 托管，别用 nohup（要自启、重启、日志管理）
2. 守护进程日志必须重定向，systemd 服务用 StandardOutput 或交给 journald
3. service 文件里配 Restart=always，崩溃自动拉起
4. nohup 只用于「临时跑一次」的任务，正式服务别用
5. 守护进程输出别依赖终端，写日志到文件/syslog，方便事后排查

### 踩坑记录

```text
坑 1：nohup 用了但 SSH 断开进程还是死了
结论：nohup 命令 2>&1 & 顺序写错，或没加 & 后台。
原因：nohup 只挡 SIGHUP，不加 & 进程还在前台、终端关了照样受影响。
解法：完整写法 nohup 命令 > log 2>&1 &，注意 & 在最后。

坑 2：守护进程日志没重定向，全丢了
结论：后台跑的进程 stdout 没重定向，日志找不到了。
原因：守护进程脱离终端后，标准输出无处可去，数据丢失。
解法：> log 2>&1 重定向，或 systemd 的 StandardOutput=append:。

坑 3：systemd 服务 Restart=always 导致疯狂重启
结论：服务起不来，systemd 反复重启，日志刷屏。
原因：Restart=always 遇到启动即崩溃的服务会无限重启。
解法：配 RestartSec 间隔，排查启动失败原因，或临时 systemctl mask 停掉。

坑 4：nohup 进程重启后没了，以为会自动拉起
结论：重启系统后 nohup 的任务没自动启动。
原因：nohup 不做开机自启，进程生命周期不托管。
解法：要持久运行就写 systemd service，nohup 只做临时任务。

坑 5：daemon 进程父进程是 1 但资源没回收
结论：守护进程的父进程是 systemd（PID 1），子进程变僵尸没人管。
原因：守护进程 fork 出子进程，子进程退出后守护进程不 wait 回收。
解法：守护进程里正确处理 SIGCHLD、wait 回收子进程，或 double-fork 避免。
```
