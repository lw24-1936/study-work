## 概述

守护进程（daemon）是「后台长期运行、不依赖终端」的进程，提供持续服务（nginx、mysql、sshd 都是守护进程）。特征：后台运行、脱离控制终端、PPID 通常是 1（systemd）、生命周期长。管理方式：临时用 nohup 脱离、标准用 systemd 托管（开机自启、崩溃重启、日志收集）。守护进程的输出要重定向（文件或 syslog），否则日志会丢失。

```text
守护进程三件事：
1. 特征 —— 后台运行、脱离终端、PPID=1、长期存活
2. 托管 —— nohup 临时脱离 / systemd 标准托管（自启、重启、日志）
3. 日志 —— 输出重定向到文件或 syslog，不重定向就丢
```

## 核心概念

### 守护进程特征

守护进程区别于普通进程的几个特征：后台运行（不占终端）、脱离控制终端（关 SSH 不影响它）、父进程是 init/systemd（PPID=1，因为原父进程退出后被 systemd 收养）、无标准输入输出（或重定向到日志）。`ps -ef` 里 TTY 是 `?`、STAT 带 `s`（会话领导）的多半是守护进程。名字习惯以 `d` 结尾（sshd、nginx 的 daemon、mysqld）。

```text
守护进程识别特征：
1. TTY 是 ? —— 不绑定终端，ps -ef 的 TTY 列是问号
2. PPID=1 —— 父进程是 systemd（被收养）
3. 名字带 d —— sshd、mysqld、dockerd（约定，非强制）
```

```text
# 实测（本机运行的守护进程服务）
$ systemctl list-units --type=service --state=running | head
1panel-agent.service    loaded active running 1Panel ...
1panel-core.service     loaded active running 1Panel ...
containerd.service      loaded active running containerd container runtime
# 这些服务都是 systemd 托管的守护进程，后台常驻
```

按「是什么 → 为什么 → 怎么用 → 边界」拆开：

- 是什么：长期在后台运行、不依附任何终端、持续提供服务的进程。
- 为什么：像 nginx/数据库/SSH 这类服务必须 7x24 常驻，不能因为「启动它的终端关了」就死掉，也不能占用终端挡住交互。
- 怎么用：`ps -ef` 看 TTY 列（?）和 PPID 列（1）识别；启动要么 nohup/setsid 临时脱离，要么交给 systemd 托管。
- 边界/易错点：守护进程没有终端，stdout/stderr 必须显式重定向否则日志丢失；「PPID=1」不是守护进程的充分条件（普通孤儿进程也会被收养）。

```shell
# 识别本机的守护进程
ps -eo pid,ppid,tty,stat,comm | awk '$3=="?"' | head   # TTY 是 ? 的进程
ps -eo pid,ppid,tty,stat,comm | awk '$2==1' | head     # PPID=1 的进程
```

### nohup

nohup 让命令「忽略 SIGHUP 信号」——终端挂断（SSH 断开）时，普通进程会收到 SIGHUP 被终止，nohup 的进程不受影响、继续跑。典型用法 `nohup 命令 > log 2>&1 &`：后台运行 + 忽略挂断 + 输出重定向。适合「临时跑个长任务、不想被 SSH 断开影响」，但不如 systemd 可靠（不自动重启、不开机自启）。

```shell
nohup ./long_task.sh > task.log 2>&1 &
# 拆解：nohup 忽略 SIGHUP、& 后台、> 重定向 stdout、2>&1 合并 stderr
disown        # 把后台作业从 shell 脱离（可选）
```

```text
nohup 的局限：
1. 不自动重启 —— 进程挂了不会拉起
2. 不开机自启 —— 重启系统后要手动再跑
3. 不管理依赖 —— 不保证启动顺序
# 要这些能力就用 systemd
```

nohup 只解决了「挡 SIGHUP」这一件事，脱离终端的完整手段是组合拳：

```text
三种「脱离终端」的临时手段对比：
1. nohup 命令 &   —— 忽略 SIGHUP + 后台，最简单，但仍是当前会话的子进程
2. setsid 命令    —— 创建新会话、彻底脱离控制终端（比 nohup 更彻底）
3. disown        —— 把已在跑的后台作业从 shell 的作业表移除，退出 shell 不再收到 SIGHUP
```

```shell
setsid ./long_task.sh > /tmp/task.log 2>&1 < /dev/null &   # 新会话，完全脱离终端
```

### systemd 托管

systemd 是守护进程的标准托管方式：写一个 service 单元文件（ExecStart 指定启动命令），就能获得开机自启、崩溃自动重启、日志收集（journalctl）、依赖管理（After/Requires）。这是生产环境跑服务的标准做法——比 nohup 可靠得多。service 文件的编写见 10.3 编写 Service Unit。

```shell
# 写 service 单元
cat > /etc/systemd/system/myapp.service <<'EOF'
[Unit]
Description=My App
After=network.target

[Service]
ExecStart=/opt/myapp/bin/myapp
Restart=always

[Install]
WantedBy=multi-user.target
EOF

# 启用并启动
systemctl daemon-reload
systemctl enable --now myapp
systemctl status myapp
```

systemd 托管的核心是「进程生命周期由 systemd 接管」：

```text
Type 决定 systemd 怎么判断「服务起来了」：
Type=simple    ExecStart 启动的进程就是主进程（现代程序最常见，默认）
Type=forking   程序自己 fork 到后台，systemd 等父进程退出后跟踪子进程（传统 daemon）
Type=notify    程序启动就绪后发 sd_notify("READY=1")，systemd 据此判定
Type=oneshot   ExecStart 跑完即视为完成（常用于一次性初始化任务）
```

```text
Restart 策略（崩溃自动拉起）：
Restart=no          不自动重启（默认）
Restart=always      任何原因退出都重启（含正常退出）
Restart=on-failure  仅非正常退出（退出码非 0/被信号杀）才重启
Restart=on-abnormal 仅信号杀/超时等异常才重启
# 配 RestartSec=N 设置两次重启之间的间隔，防止疯狂重启刷爆日志
```

### 日志重定向

守护进程没有终端，标准输出/错误必须重定向，否则日志丢失。三种去向：重定向到文件（`> /var/log/app.log 2>&1`）、交给 syslog/journal（systemd 自动收集）、用日志库写文件。systemd 托管的服务，stdout/stderr 自动进 journald（journalctl -u 服务名 查看）。传统 daemon 常用 `>> /var/log/xxx.log` 追加日志。

```shell
# 方式一：重定向到文件
nohup ./app >> /var/log/app.log 2>&1 &

# 方式二：systemd 托管，日志自动进 journald
systemctl start myapp
journalctl -u myapp -f        # 实时看服务日志
journalctl -u myapp --since "1 hour ago"
```

```text
三种日志去向选型：
1. 直接写文件 —— 简单直观，但要自己处理轮转（配 logrotate），否则文件无限增长
2. 交给 journald —— systemd 托管默认方式，journalctl 查询/过滤，systemd 自动轮转
3. 交给 syslog —— logger 命令或 syslog() 接口，集中到 /var/log/ 由 rsyslog 分类落盘
```

```shell
# 用 logger 把脚本日志交给 syslog
logger -t myapp "服务启动成功"        # 写入 /var/log/syslog（或 journald）
journalctl -t myapp -e              # 按 tag 查询刚才写的日志
```

```text
# systemd 单元里显式指定日志落盘位置
[Service]
StandardOutput=append:/var/log/myapp.log   # stdout 追加到文件
StandardError=append:/var/log/myapp.log    # stderr 也追加到同一文件
# 不配这两行则 stdout/stderr 默认进 journald
```

## 工作原理

守护进程「脱离终端」靠一组标准步骤：调用 setsid 创建新会话（脱离原控制终端）、fork 出子进程并让父进程退出（子进程 PPID 变成 1）、切换工作目录到 /、关闭或重定向标准输入输出。传统 daemon 常做「double-fork」确保进程不会重新获得控制终端；现代的 systemd 直接把服务作为自己的子进程拉起，天然脱离终端，无需程序自己 double-fork。

```text
传统 daemon 化步骤：
1. fork 子进程，父进程退出（子进程被 init/systemd 收养，PPID=1）
2. setsid 创建新会话，脱离原控制终端
3. chdir("/") 切换工作目录，避免占用挂载点
4. 关闭 stdin/stdout/stderr 或重定向到日志文件

现代做法：systemd 直接 fork 服务进程，进程无需自己 daemon 化
（Type=simple 时 systemd 认为主进程就是守护进程本身）
```

为什么必须 setsid 和 double-fork，得先理解「会话/进程组/控制终端」：

```text
三个概念：
1. 进程组（process group）—— 一组相关进程，前台进程组能读终端输入
2. 会话（session）—— 一个或多个进程组的集合，一个会话有一个控制终端
3. 控制终端（controlling terminal）—— 会话首进程打开的终端；终端挂断时，
   内核向会话首进程发 SIGHUP，进而影响整个会话

setsid() 的作用：让调用进程成为「新会话的首进程」，脱离原来的控制终端。
限制：调用 setsid 的进程不能是进程组组长（组长的 PGID 等于自己的 PID）。
```

```text
为什么 double-fork（两次 fork）：
1. 第一次 fork + 父进程退出：子进程不是进程组组长，满足 setsid 的前提
2. setsid 创建新会话，成为会话首进程（脱离终端）
3. 第二次 fork + 父进程退出：孙进程不再是会话首进程（PGID != SID），
   即使日后误打开终端，也不会被当作会话首进程重新获得控制终端

两次 fork 保证进程彻底、永久地脱离任何控制终端。
```

传统 daemon 化的 C 代码骨架：

```c
// daemon_demo.c —— 传统 daemon 化步骤
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/stat.h>

int main(void) {
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); exit(1); }
    if (pid > 0) _exit(0);               // 1. 父进程退出，子进程被 init 收养

    if (setsid() < 0) { perror("setsid"); exit(1); }   // 2. 新会话，脱离控制终端

    pid = fork();
    if (pid < 0) { perror("fork"); exit(1); }
    if (pid > 0) _exit(0);               // 3. 第二次 fork，确保不再获得控制终端

    chdir("/");                          // 4. 切到根目录，避免占用挂载点
    umask(0);                            // 5. 重置 umask

    int fd = open("/tmp/daemon.log", O_WRONLY | O_CREAT | O_APPEND, 0644);
    dup2(fd, STDOUT_FILENO);             // 6. 重定向 stdout/stderr，关闭 stdin
    dup2(fd, STDERR_FILENO);
    close(STDIN_FILENO);

    while (1) {                          // 守护进程主循环
        sleep(5);
    }
    return 0;
}
```

```shell
gcc -o daemon_demo daemon_demo.c        # 编译
./daemon_demo &                          # 跑起来后立即返回（父进程已退出）
ps -o pid,ppid,tty,stat,comm -C daemon_demo   # 看 PPID=1、TTY=?
```

```shell

守护进程管理两条路：
1. systemd —— 生产标准，自启/重启/日志/依赖一站式

```

## 配置文件解析

守护进程的「配置」就是 systemd service 单元文件，核心段如下：

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My App              # 描述
After=network.target            # 依赖：网络就绪后才启动

[Service]
Type=simple                     # 启动类型（simple/forking/notify/oneshot）
ExecStart=/opt/myapp/bin/myapp  # 启动命令
Restart=always                  # 崩溃自动重启
RestartSec=5                    # 重启间隔
StandardOutput=append:/var/log/myapp.log   # stdout 落盘
StandardError=append:/var/log/myapp.log    # stderr 落盘

[Install]
WantedBy=multi-user.target      # 开机自启目标
```

```text
关键字段：
Type=simple   主进程即服务进程（最常见）
Type=forking  程序自己 fork 后台，systemd 等父进程退出（传统 daemon）
Restart       always/on-failure，控制崩溃重启
StandardOutput  不配则 stdout 进 journald
```

```text
[Service] 段更多常用字段：
ExecStartPre=/usr/bin/mkdir -p /run/myapp   # 启动前执行的准备命令
ExecStartPost=...                           # 启动成功后执行
User=myapp / Group=myapp                    # 降权运行（生产必备）
WorkingDirectory=/opt/myapp                 # 工作目录
Environment="APP_ENV=production"            # 环境变量
LimitNOFILE=65536                           # 文件描述符上限
MemoryMax=512M                              # 内存上限
TimeoutStopSec=10                           # 停止超时（超时 SIGKILL）
```

## 应用场景实战

### 场景一：把自研服务做成 systemd 守护进程

```shell
# 1. 写 service 文件
cat > /etc/systemd/system/myapp.service <<'EOF'
[Unit]
Description=My Application
After=network.target

[Service]
Type=simple
ExecStart=/opt/myapp/bin/myapp
Restart=always
RestartSec=5
StandardOutput=append:/var/log/myapp.log
StandardError=append:/var/log/myapp.log

[Install]
WantedBy=multi-user.target
EOF
# 2. 启用自启 + 启动
systemctl daemon-reload
systemctl enable --now myapp
# 3. 验证
systemctl status myapp
```

### 场景二：临时后台跑脚本并用 nohup 保活

```shell
# 后台跑一个长任务，SSH 断开也不停
nohup ./data_sync.sh > /var/log/data_sync.log 2>&1 &
echo "PID: $!"
# 查看进度
tail -f /var/log/data_sync.log
```

### 场景三：写一个可 systemd 托管的 Python 守护进程

生产里自研服务多是「前台程序 + systemd 托管」（Type=simple），程序自己不做 daemon 化、不写日志文件，由 systemd 统一管进程和日志。

```python
# myapp.py —— 前台运行，交给 systemd 托管（Type=simple）
import signal
import sys
import time

stop = False

def handler(signum, frame):
    global stop
    stop = True                     # 收到 SIGTERM 优雅收尾

signal.signal(signal.SIGTERM, handler)
signal.signal(signal.SIGINT, handler)

print("myapp 启动", flush=True)     # stdout 直接进 journald
while not stop:
    time.sleep(1)

print("myapp 收到停止信号，正常退出", flush=True)
sys.exit(0)
```

```ini
# /etc/systemd/system/myapp.service —— 托管上面的 Python 程序
[Unit]
Description=My Python App
After=network.target

[Service]
Type=simple
ExecStart=/usr/bin/python3 /opt/myapp/myapp.py
Restart=on-failure
User=nobody                     # 降权，别用 root 跑
StandardOutput=journal          # 默认，stdout 进 journald

[Install]
WantedBy=multi-user.target
```

```shell
systemctl daemon-reload
systemctl enable --now myapp
journalctl -u myapp -f          # 实时看「myapp 启动」这条日志
systemctl stop myapp            # 触发 SIGTERM，程序打印「正常退出」后停止
```

## 性能与调优

```text
1. Type 选对 —— simple 适合前台程序，forking 适合自 daemon 化的老程序，选错 systemd 会误判退出
2. RestartSec 别太小 —— 崩溃服务短间隔反复重启会刷爆日志、占资源
3. 日志落盘用 StandardOutput —— 比让进程自己写文件更统一，journald 还能轮转
4. 限制服务资源 —— 用 MemoryMax/CPUQuota 防止单个守护进程吃满整机
5. 大量守护进程用 LimitNOFILE 调大文件描述符，避免 too many open files
6. 日志轮转别忘 —— 直接写文件的服务要配 logrotate，否则日志文件无限膨胀占满磁盘
```

## 安全与权限

```text
1. 别用 root 跑服务 —— systemd 单元里用 User=/Group= 降权运行，最小权限原则
2. 服务日志防泄露 —— 日志文件权限收紧，别让普通用户读到敏感信息
3. systemd 单元文件可被篡改 —— 只 root 可写 /etc/systemd/system/
4. 提权服务要隔离 —— 需要特定能力的服务用 CapabilityBoundingSet= 而非直接 root
5. nohup 临时任务注意清理 —— 跑完确认退出，别留僵尸后台进程
6. 守护进程的 umask 要显式设置 —— 否则生成的文件权限可能过宽（默认继承），泄露数据
```

## 故障排查

### systemd 服务起不来

```shell
# 1. 看状态和退出码
systemctl status myapp
# 2. 看服务日志（启动失败的具体报错）
journalctl -u myapp -n 50 --no-pager
# 3. 手动跑 ExecStart 的命令验证
/opt/myapp/bin/myapp
```

### 服务反复重启（Restart 循环）

```shell
# 1. 确认是否在疯狂重启
systemctl status myapp | grep -E 'Active|Main PID'
# 2. 看每次退出的原因
journalctl -u myapp -n 100 --no-pager | grep -iE 'error|fail|exit'
# 3. 临时停止排查，别让它继续刷日志
systemctl stop myapp
```

### nohup 后进程还是没了 / 找不到输出

```shell
# 1. 确认进程是否还在
pgrep -af long_task
# 2. 确认日志文件是否存在、是否被重定向
ls -l /var/log/data_sync.log
# 3. nohup 的默认输出：没重定向时写 ~/nohup.out，重定向错了可能写到别处
```

## 常见问题

```text
Q1: nohup 和 systemd 托管怎么选？
A: 临时跑一次的任务用 nohup，正式服务用 systemd（要自启、崩溃重启、日志管理）。

Q2: 为什么守护进程的 PPID 是 1？
A: 原父进程退出后，孤儿进程被 systemd（PID 1）收养。传统 daemon double-fork 主动让父进程退出，也是为了让进程变成 PPID=1。

Q3: Type=simple 和 Type=forking 有什么区别？
A: simple 认为 ExecStart 启动的进程就是服务主进程；forking 认为程序会自己 fork 到后台，systemd 等原进程退出后跟踪子进程。老式 daemon 用 forking。

Q4: systemd 服务的日志去哪了？
A: stdout/stderr 默认进 journald（journalctl -u 服务 查看）；配了 StandardOutput= 则落到指定文件。

Q5: 什么是 double-fork？为什么要做两次 fork？
A: 第一次 fork 让子进程成为非进程组组长（满足 setsid 前提），setsid 后脱离终端；第二次 fork 让孙进程不再是会话首进程，确保日后不会重新获得控制终端。

Q6: setsid 和 nohup 有什么区别？
A: nohup 只忽略 SIGHUP，进程仍在原会话里；setsid 创建全新会话、彻底脱离控制终端，比 nohup 更彻底。临时脱离终端优先 setsid。

Q7: 守护进程的日志不重定向会怎样？
A: stdout/stderr 无处可去（终端已脱离），数据直接丢失。所以要么重定向到文件，要么交给 journald/syslog。
```

## 面试题

```text
1. 什么是守护进程？有哪些特征？
   答：后台长期运行、脱离控制终端、PPID=1、不依赖终端的进程。ps 里 TTY 是 ?、名字常带 d。

2. 传统 daemon 化的步骤？
   答：fork 父进程退出、setsid 脱离终端、chdir 切工作目录、重定向/关闭标准 IO。现在常用 systemd 托管替代。

3. nohup 的原理？
   答：让进程忽略 SIGHUP 信号，终端挂断（SSH 断开）时进程不被杀，配合 & 后台运行。

4. systemd 相比 nohup 的优势？
   答：开机自启、崩溃自动重启（Restart=）、日志收集（journald）、依赖管理（After/Requires）、资源限制。

5. setsid 的作用是什么？为什么调用它的进程不能是进程组组长？
   答：setsid 创建新会话并让调用进程成为会话首进程，从而脱离原控制终端。若调用者是进程组组长，它的 PGID 等于 PID，setsid 后会导致新会话 ID 与已有进程组冲突，所以内核禁止组长调用。

6. 什么是会话、进程组、控制终端？它们和守护进程什么关系？
   答：进程组是一组相关进程，会话是进程组的集合，控制终端是会话首进程关联的终端。终端挂断时内核向会话首进程发 SIGHUP。守护进程通过 setsid 建立新会话、不关联任何控制终端，从而摆脱终端挂断的影响。

7. 守护进程的日志应该怎么处理？
   答：三种去向——重定向到文件（配 logrotate 轮转）、交给 journald（systemd 托管默认）、交给 syslog（logger/syslog()）。不重定向日志会丢失。

8. systemd 的 Type=forking 和 Type=notify 分别解决什么问题？
   答：forking 兼容「自己 fork 后台」的传统 daemon（systemd 等父进程退出后跟踪子进程）；notify 让程序启动就绪后主动发 sd_notify，systemd 能精确知道服务何时真正就绪，避免依赖它的服务过早启动。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产服务一律 systemd 托管，别用 nohup（要自启、重启、日志管理）
2. 守护进程日志必须重定向，systemd 服务用 StandardOutput 或交给 journald
3. service 文件里配 Restart=always，崩溃自动拉起
4. nohup 只用于「临时跑一次」的任务，正式服务别用
5. 守护进程输出别依赖终端，写日志到文件/syslog，方便事后排查
6. systemd 单元里用 User=/Group= 降权，别用 root 直接跑服务
7. 直接写文件的服务配 logrotate，防止日志无限增长占满磁盘

### 踩坑记录

```text
坑 1：nohup 用了但 SSH 断开进程还是死了
结论：nohup 命令 2>&1 & 顺序写错，或没加 & 后台。
原因：nohup 只挡 SIGHUP，不加 & 进程还在前台、终端关了照样受影响。
解法：完整写法 nohup 命令 > log 2>&1 &，注意 & 在最后。

坑 2：守护进程日志没重定向，全丢了
结论：后台跑的进程 stdout 没重定向，日志找不到了。
原因：守护进程脱离终端后，标准输出无处可去，数据丢失。
解法：> log 2>&1 重定向，或 systemd 的 StandardOutput=append:。

坑 3：systemd 服务 Restart=always 导致疯狂重启
结论：服务起不来，systemd 反复重启，日志刷屏。
原因：Restart=always 遇到启动即崩溃的服务会无限重启。
解法：配 RestartSec 间隔，排查启动失败原因，或临时 systemctl mask 停掉。

坑 4：nohup 进程重启后没了，以为会自动拉起
结论：重启系统后 nohup 的任务没自动启动。
原因：nohup 不做开机自启，进程生命周期不托管。
解法：要持久运行就写 systemd service，nohup 只做临时任务。

坑 5：daemon 进程父进程是 1 但资源没回收
结论：守护进程的父进程是 systemd（PID 1），子进程变僵尸没人管。
原因：守护进程 fork 出子进程，子进程退出后守护进程不 wait 回收。
解法：守护进程里正确处理 SIGCHLD、wait 回收子进程，或 double-fork 避免。

坑 6：systemd Type=forking 配了但程序没 fork，服务被判失败
结论：service 写 Type=forking，但程序是前台运行，systemd 等父进程退出等不到，报服务失败/超时。
原因：Type=forking 期望程序自己 fork 后台并让父进程退出；前台程序不这么做，systemd 就卡住。
解法：前台程序用 Type=simple（默认），只有真正自 daemon 化的老程序才用 forking。

坑 7：nohup 没加 & ，命令在前台卡住终端
结论：只写 nohup 命令 没写 &，命令仍在前台跑，终端被占用。
原因：nohup 只忽略 SIGHUP，不负责后台化，& 才是把进程放到后台。
解法：完整写法必须带 & —— nohup 命令 > log 2>&1 &。
```
