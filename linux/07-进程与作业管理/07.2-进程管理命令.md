## 概述

进程管理命令分四组：查看（ps/top/htop）、查找（pgrep）、结束（kill/pkill/killall）、后台作业（jobs/fg/bg/nohup）。日常「看进程 → 找进程 → 杀进程 → 后台跑」的完整链路全靠这几条命令。ps 看快照、top 看实时、pgrep 按名字找、kill 按 PID 杀，配合起来就是进程管理的全套工具。

```text
进程管理命令分组：
1. 查看 —— ps 快照、top 实时、htop 增强版 top
2. 查找 —— pgrep 按名字/模式找 PID
3. 结束 —— kill（按 PID）、pkill（按名字）、killall（按名字）
4. 后台 —— jobs 看作业、fg/bg 前后台切换、nohup 脱离终端
```

## 核心概念

1. **快照 vs 实时**：ps 是「某一瞬间的进程快照」，top 是「持续刷新的实时监控」——看谁占资源用 top，看某个具体进程详情用 ps。ps 适合脚本里取数（可精确控制输出列），top 适合人盯屏。边界：ps 的输出是取到的瞬间数据，高并发下连续两次 ps 结果可能不一致。
2. **按名 vs 按 PID**：按 PID 操作（kill）精确但要知道 PID；按名操作（pgrep/pkill/killall）方便但有误伤同名进程的风险。pkill 的匹配比 killall 更灵活（支持 -f 匹配完整命令行、正则、-u 限定用户），killall 只匹配进程名（最多 15 字符，超长会被截断）。
3. **信号与优雅终止**：kill 的本质是发信号，默认 SIGTERM（优雅）、-9 是 SIGKILL（强杀），约定「先 15 后 9」。SIGTERM 可被进程捕获做清理（刷盘、释放锁、通知下游），SIGKILL 不可捕获直接杀。数据库、写文件的服务尤其不能一上来就 -9。
4. **作业控制与脱离终端**：jobs/fg/bg 管理当前 shell 的前后台作业；nohup/setsid 让进程脱离终端，SSH 断开不被杀。边界：nohup 只挡 SIGHUP，挡不住 SIGTERM；& 只是后台运行不脱离终端；真正托管长期服务用 systemd。

```text
命令选择原则：
看资源占用 → top；看进程树/父进程 → ps -ef --forest
按名字找 PID → pgrep；杀进程 → 先 kill（TERM）再 kill -9（KILL）
远程长任务 → nohup ... & 或 systemd 托管
```

## 工作原理

这些命令背后都读 Linux 内核的数据源：ps/top 读 /proc 伪文件系统（每个进程一个目录，实时反映内核 task_struct 的信息）；kill 通过 kill() 系统调用向目标进程发送信号；nohup 让进程忽略 SIGHUP 信号从而不被终端挂断杀死。

```text
命令 → 数据源：
ps/top    → 读 /proc/<pid>/stat、/proc/<pid>/status（内核 task_struct 的暴露）
kill      → kill() 系统调用，向进程发送信号（默认 SIGTERM）
nohup     → 忽略 SIGHUP 信号，终端关闭时不被杀
pgrep     → 扫描 /proc，匹配进程名/命令行
```

补几个机制细节：top 默认每 3 秒刷新一次，读的是 /proc 的增量数据，自身也占用一定 CPU（`top -b -n 1` 批量模式适合脚本取数，一次输出就退出）；kill 发信号时若目标进程是你自己的（同 UID）才能发，跨用户需要 root（内核检查 real/effective uid）；SIGHUP 的触发点是「控制终端关闭/挂断」，所以 SSH 断开时 shell 会把 SIGHUP 发给它启动的前台/后台作业，nohup 就是让进程忽略这个信号。

```text
信号优先级约定（终止进程）：
SIGTERM(15) → 优雅停，给进程清理机会（首选）
SIGINT(2)   → 相当于 Ctrl+C，前台交互式停
SIGKILL(9)  → 强杀，不可捕获，最后手段
```

## 常用命令与配置

### ps 查看进程

ps 是进程快照查看工具。两种常用格式：`ps aux`（BSD 风格，含 %CPU %MEM VSZ RSS）和 `ps -ef`（System V 风格，含 PPID）。配合 `-o` 自定义输出列、`--sort` 排序、`--forest` 树状显示。排查「哪个进程占资源」用 aux，「看进程树/父进程」用 -ef。

```text
# 实测（ps aux 列含义）
$ ps aux | head -3
USER  PID  %CPU %MEM   VSZ   RSS TTY STAT START TIME COMMAND
root    1   0.0  0.0 24336 14776 ?   Ss   7月27 5:21 /usr/lib/systemd/systemd ...
# %CPU/%MEM 资源占用、VSZ 虚拟内存、RSS 物理内存、STAT 状态、TIME 累计 CPU 时间
```

```shell
ps aux                 # 全部进程 + 资源占用
ps -ef                 # 全部进程 + PPID
ps aux --sort=-%mem | head    # 按内存倒序找大户
ps aux --sort=-%cpu | head    # 按 CPU 倒序找大户
ps -eo pid,ppid,stat,comm     # 自定义列
ps -ef --forest        # 树状显示父子关系
ps -C nginx            # 按命令名精确匹配（比 grep 干净）
ps -L -p 1234          # 看某进程的线程
ps auxww               # w 重复取消命令行截断
```

```text
ps 输出列速查：
PID 进程号 | PPID 父进程 | %CPU 累计 CPU 占用 | %MEM 物理内存占比
VSZ 虚拟内存 | RSS 物理内存 | STAT 状态 | START 启动时间 | TIME 累计 CPU 时间
COMMAND 命令（aux 默认截断，加 w 取消截断）
```

```text
实用组合命令：
ps -eo pid,ppid,%cpu,%mem,comm --sort=-%cpu | head   # 按 CPU 倒序取前 10
ps -ef | grep -v grep | awk '{print $2, $8}'          # 提取 PID + 命令
pgrep -f <关键词> | xargs -r kill -TERM               # 批量按关键词优雅终止
```

### top 与 htop 实时监控

top 是实时动态监控：顶部是系统汇总（负载 load average、CPU、内存），下面是按 CPU 排序的进程列表。交互键：P 按 CPU 排、M 按内存排、k 杀进程、q 退出。htop 是 top 的增强版（彩色、可鼠标、可树状显示），但通常要单独装（apt install htop）。看「现在系统什么状态、哪个进程在飙 CPU」用 top。

```shell
top                    # 实时监控，q 退出
top -u alice           # 只看某用户的进程
top -p 1234            # 只看某 PID
top -b -n 1            # 批量模式：输出一次就退出（脚本取数用）
top -H -p 1234         # 看某进程的线程
htop                   # 增强版（需安装）
```

```text
top 顶部指标：
1. load average —— 1/5/15 分钟平均负载（几核几以内算健康）
2. us/sy/id/wa —— 用户态/内核态/空闲/等待 IO 的 CPU 占比
3. Mem/Swap —— 内存和交换空间使用
```

top 交互键速查：P 按 CPU 排序、M 按内存排序、T 按运行时间排序、k 输入 PID 杀进程、r 改 nice 值、c 显示完整命令行、1 展开看每核 CPU、u 按用户过滤。htop 的优势是可鼠标点击、F6 图形化选排序列、F5 树状显示父子关系，视觉更友好但功能本质和 top 相同。

```shell
# 脚本化取数：批量模式输出一次就退出，配合 head/grep 做监控
top -b -n 1 | head -20                   # 一次性快照
top -b -n 1 -o %CPU | head -20           # 按 CPU 排序输出一次
# 循环采样：每 5 秒记录一次 CPU 最高的进程
while true; do top -b -n 1 | sed -n '8,15p'; sleep 5; done
```

### pgrep 与 pkill 查找杀进程

pgrep 按名字/模式找 PID（`pgrep nginx` 输出所有 nginx 的 PID），pkill 按名字/模式发信号杀进程（`pkill nginx`）。比 `ps | grep` 干净——不会把 grep 自己匹配进去，还能用 -f 匹配完整命令行、-u 限定用户。这俩是「按名字操作进程」的现代替代，比手动 ps+grep+kill 高效。

```text
# 实测（pgrep nginx）
$ pgrep -a nginx
565634 nginx: master process /usr/sbin/nginx ...
1406300 nginx: worker process
1406301 nginx: worker process
...
# nginx 是 master + 多个 worker 的典型模型
```

```shell
pgrep nginx              # 找 nginx 的 PID
pgrep -a nginx           # 带完整命令行
pgrep -u alice           # 某用户的进程
pgrep -f 'python.*app'   # 按完整命令行匹配
pgrep -x nginx           # 精确匹配进程名（不匹配 nginxplus 之类）
pgrep -P 1234            # 找某父进程的子进程
pkill nginx              # 按名字杀（发 SIGTERM）
pkill -f 'python.*app'   # 按完整命令行匹配杀
pkill -u alice           # 杀某用户的所有进程
pkill -9 -x java         # 精确匹配名字并强杀
```

```text
边界/易错点：
1. pgrep/pkill 默认只匹配进程名（comm，最长 15 字符），匹配不到命令行参数 —— 要匹配参数加 -f
2. -f 匹配「完整命令行」范围大 —— 先 pgrep -af 预览，确认无误再 pkill，避免误杀
3. pkill 匹配自己所在脚本时要小心 —— 脚本命令行若含关键字，pkill 可能把脚本自己也杀了
```

### kill 与 killall

kill 按 PID 发信号（默认 SIGTERM 15），killall 按进程名发信号。`kill 1234` 优雅终止（给进程清理的机会），`kill -9 1234` 强制杀（不清理，慎用）。约定：先用 SIGTERM 优雅停，等一会还不退再用 SIGKILL。kill -9 是最后手段，因为它不给进程任何清理机会，可能留下脏数据。

```shell
kill 1234               # 发 SIGTERM（优雅终止）
kill -9 1234            # 发 SIGKILL（强制，慎用）
kill -15 1234           # 等价 kill 1234
kill -0 1234            # 不发信号，只探测进程是否存在（脚本判断存活用）
kill -HUP 1234          # 发 SIGHUP，很多服务用它重载配置（nginx 等）
killall nginx           # 按名字杀所有 nginx
killall -i nginx        # 逐个确认再杀
killall -u alice        # 杀某用户的所有进程
kill -l                 # 列出所有信号
```

```text
kill 的信号几类：
1. 终止类 —— TERM(15) 优雅、KILL(9) 强杀、INT(2) 中断（Ctrl+C）
2. 重载类 —— HUP(1) 很多守护进程用它热重载配置、USR1/USR2(10/12) 应用自定义
3. 探测类 —— 0 不真发信号，只判断权限和进程是否存在
```

### jobs 与 fg 与 bg 与 nohup

作业控制管理当前 shell 的前后台任务：jobs 列作业、fg 把后台调到前台、bg 让暂停的作业后台跑、Ctrl+Z 暂停。nohup 让命令「脱离终端」——关掉 SSH 会话后进程继续跑（配合 & 后台 + 输出重定向）。远程跑长任务的标准写法：`nohup 命令 > log 2>&1 &`。

```shell
jobs                    # 看当前 shell 的作业
fg %1                   # 1 号作业调到前台
bg %1                   # 1 号作业后台继续
nohup ./long_task.sh > task.log 2>&1 &   # 脱离终端后台跑
disown                  # 把作业从 shell 脱离
setsid ./long_task.sh   # 新建会话彻底脱离终端（比 nohup 更彻底）
```

```text
后台运行的三层手段：
1. 命令 &           —— 后台运行，但还挂在当前 shell，退出 shell 可能收到 SIGHUP
2. nohup 命令 &     —— 忽略 SIGHUP，SSH 断开不死，但进程组/会话仍关联
3. setsid / systemd —— 新建会话完全脱离，或交给 systemd 托管（生产首选）
```

作业（job）是 shell 层面的概念：一个「作业」可能是一个进程，也可能是一个管道（`a | b` 是一个作业、两个进程）。作业号（%1、%2）只在当前 shell 有效，和 PID 是两套编号——kill 用的是 PID，fg/bg 用的是作业号。

## 配置文件解析

进程管理的「配置」主要是资源限制类，集中在 /etc/security/limits.conf 和 /proc/sys：

```text
# /etc/security/limits.conf（用户级资源限制，改完重新登录生效）
*    soft    nofile    65535      # 软限制：最多打开文件数
*    hard    nofile    65535      # 硬限制：root 才能调高
*    soft    nproc     4096       # 最大进程数
```

```text
相关内核参数（/proc/sys/kernel/）：
pid_max         系统最大 PID（默认 32768，可调大）
threads-max     系统最大线程数
core_pattern    core dump 文件生成路径
```

```shell
ulimit -n            # 看当前 shell 的文件描述符上限
ulimit -u            # 看当前用户最大进程数
ulimit -a            # 看全部资源限制
cat /proc/sys/kernel/pid_max   # 看系统最大 PID
```

limits.conf 改完要重新登录（或对已运行进程用 prlimit 调整）才生效；容器里这些限制常被 cgroup 和 runc 覆盖，宿主机 limits.conf 不一定作用到容器内进程。

## 应用场景实战

### 场景一：找到并优雅重启一个服务

```shell
# 1. 找进程
pgrep -a nginx
# 2. 优雅终止（SIGTERM，让 nginx 完成当前请求）
kill $(pgrep nginx | head -1)   # 杀 master
# 3. 确认退出
pgrep nginx || echo "已退出"
# 4. 重新启动
systemctl start nginx
```

### 场景二：排查 CPU 飙高的进程

```shell
# 1. top 看谁在飙 CPU
top
# 2. 定位到 PID 后看详情
ps -o pid,ppid,stat,cmd -p <PID>
# 3. 看它的线程（找具体哪个线程）
top -H -p <PID>
# 4. 确认后处理（kill 或排查代码）
```

### 场景三：后台跑长任务并监控，SSH 断开也不中断

```shell
# 1. 用 nohup 后台启动长任务，输出重定向到日志
nohup ./data_sync.sh > /var/log/data_sync.log 2>&1 &
# 2. 记录 PID，方便后续管理
echo $! > /var/run/data_sync.pid
# 3. 用 jobs 确认作业在跑，或 tail 日志看进度
jobs
tail -f /var/log/data_sync.log
# 4. 要停时按 PID 优雅终止
kill $(cat /var/run/data_sync.pid)
```

## 性能与调优

```text
1. top 里 wa（等待 IO）高 —— 磁盘瓶颈，别急着怪 CPU
2. load average 持续高于核数 —— 进程排队等 CPU，看是 CPU 不够还是 IO 拖累
3. 频繁上下文切换（vmstat cs 高）—— 线程开太多，考虑合并或减少
4. RSS 持续上涨 —— 进程内存泄漏信号，配合 08.4 内存泄漏排查
5. top -H -p 看线程 —— 定位是哪个线程吃满单核（java 多线程场景常用）
6. ps aux --sort=-%cpu --sort=-%mem 批量取数 —— 脚本监控比盯 top 高效
```

## 安全与权限

```text
1. 普通用户 kill 不了别人的进程 —— 只能 kill 自己的（同 UID）或 root 才可跨用户
2. pkill/killall 按名字杀 —— 先 pgrep -af 预览匹配结果，确认无误再杀，避免误伤
3. kill -9 慎用 —— 不给清理机会，可能数据损坏，先 SIGTERM
4. ps 会暴露命令行参数 —— 别把密码写进启动参数（mysql -p密码），用配置文件
5. nohup 只挡 SIGHUP —— 挡不住 SIGTERM/SIGKILL，要完全托管用 systemd
6. 杀进程要确认身份 —— killall/pkill 可能匹配到同名的关键系统进程（如误杀 systemd-journald）
```

## 故障排查

### 服务杀不掉 / 反复重启

```shell
# 1. 先看进程状态（D 状态杀不掉）
ps -o pid,ppid,stat,cmd -p <PID>
# 2. 看是不是有父进程在拉起（supervisor/systemd Restart）
ps -o pid,ppid,cmd -p <PID>
# 3. systemd 托管的服务先停服务再杀
systemctl stop <服务名>
```

### 端口被占用，找不到进程

```shell
# 1. 看端口被哪个进程占用
ss -tlnp | grep :8080
# 2. 找到 PID 后看详情
ps -o pid,ppid,cmd -p <PID>
# 3. 该杀杀、该停停
kill <PID>
```

### 进程陷入死循环，CPU 100% 且 kill 不掉

```shell
# 1. top 确认是哪个 PID 吃满单核
top -b -n 1 | head -20
# 2. 看它到底在干嘛（D 状态还是纯 CPU 空转）
ps -o pid,stat,%cpu,cmd -p <PID>
# 3. 若是普通用户进程，先 SIGTERM 再 SIGKILL
kill <PID> && sleep 3 && kill -9 <PID>
# 4. 若是 D 状态，查 IO（iostat）而不是硬杀
```

### 僵尸进程堆积

```shell
# 1. 统计僵尸进程数量
ps -eo stat | grep -c '^Z'
# 2. 找出僵尸进程和它们的父进程
ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/'
# 3. 找到父进程，看它为什么不回收
ps -o pid,ppid,stat,cmd -p <父进程PID>
# 4. 让父进程回收（重启父进程或发信号），父进程也死了就等 systemd 代劳
```

## 常见问题

```text
Q1: ps aux 和 ps -ef 有什么区别？
A: aux 是 BSD 风格（列 %CPU/%MEM/VSZ/RSS），-ef 是 System V 风格（列 PPID）。看资源用 aux，看父子关系用 -ef。

Q2: 为什么 ps | grep 会多出一行 grep？
A: grep 进程的命令行本身含关键字，把自己也匹配了。用 pgrep，或 ps aux | grep '[n]ginx' 字符类技巧。

Q3: kill 和 pkill 的区别？
A: kill 按 PID 精确杀，pkill 按名字/模式杀。pkill 方便但可能误伤同名进程。

Q4: nohup 和 & 的区别？
A: & 只是后台运行，终端关闭仍可能收到 SIGHUP 被杀；nohup 忽略 SIGHUP，SSH 断开不受影响。两者通常一起用。

Q5: kill -9 杀不掉进程怎么办？
A: 先看 ps 的 STAT 是不是 D（不可中断睡眠，等 IO，信号被挂起）；是就查 iostat 解决 IO。若是 Z 僵尸，本来就杀不掉，找父进程回收。都不是再确认权限（跨用户要 root）。

Q6: jobs 里的作业号和 PID 是一回事吗？
A: 不是。作业号（%1、%2）只在当前 shell 有效，是 shell 给「作业」的编号，一个作业可能含多个进程（管道）；PID 是系统全局的进程号。fg/bg 用作业号，kill 用 PID。

Q7: pgrep 匹配不到我想找的进程，为什么？
A: 默认只匹配进程名（comm，最长 15 字符），匹配不到命令行参数。用 pgrep -af 看完整命令行，或加 -f 匹配完整命令行。
```

## 面试题

```text
1. 怎么找占用某个端口的进程？
   答：ss -tlnp | grep :端口 找到 PID，再 ps -o pid,ppid,cmd -p PID 看详情。

2. SIGTERM 和 SIGKILL 的区别？
   答：SIGTERM(15) 可被捕获，进程能做清理后优雅退出；SIGKILL(9) 不可捕获，直接强杀不清理。约定先 15 后 9。

3. 后台进程 SSH 断开后怎么保活？
   答：nohup 命令 > log 2>&1 &（忽略 SIGHUP + 后台 + 重定向），或用 setsid、systemd 托管。

4. 怎么快速定位 CPU 占用最高的进程？
   答：top 按 P 排序（默认就按 CPU），或 ps aux --sort=-%cpu | head。进一步 top -H -p PID 看线程。

5. pgrep 和 ps | grep 的区别？
   答：pgrep 直接扫描 /proc 匹配进程，不会把 grep 自己匹配进去，还支持 -f/-u/-x 等过滤；ps | grep 会多出一行 grep，要字符类技巧规避。

6. nohup 和 systemd 托管长任务有什么区别？
   答：nohup 只是忽略 SIGHUP，进程崩了不会自动拉起、开机不会自启、没有日志轮转和资源限制；systemd 能自启、崩溃重启、日志、资源限制，生产长任务首选 systemd。

7. 怎么批量杀掉某用户的所有进程？
   答：pkill -u 用户名，或 killall -u 用户名。注意先 pgrep -u 用户名预览确认，避免误杀该用户的关键会话。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 杀进程先 SIGTERM 优雅停，等一会不退再 SIGKILL，别上来就 kill -9
2. 找进程用 pgrep，别 ps | grep（grep 自己会混进结果）
3. 远程长任务用 nohup ... & + 日志重定向，防止 SSH 断开进程被杀
4. 看资源占用用 ps aux --sort=-%mem，看进程树用 ps -ef --forest
5. 实时监控用 top，交互排序 P（CPU）M（内存）能快速定位
6. pkill/killall 杀之前先 pgrep -af 预览，确认匹配范围再动手
7. 脚本里取进程数据用 ps -o 自定义列 + top -b -n 1，输出可控、方便解析

### 踩坑记录

```text
坑 1：ps | grep 把 grep 自己匹配进去
结论：ps aux | grep nginx 结果里多一行 grep nginx。
原因：grep 进程的命令行含 nginx，把自己也匹配了。
解法：用 pgrep，或 ps aux | grep '[n]ginx'（字符类技巧）。

坑 2：kill -9 滥用导致数据损坏
结论：kill -9 杀数据库/写文件进程，数据没刷盘就没了。
原因：SIGKILL 不给进程清理机会，缓冲区数据丢失。
解法：先 SIGTERM 优雅停，确认不退再 -9。

坑 3：SSH 断开后后台进程被杀
结论：nohup 没用对，SSH 断开后长任务中断。
原因：终端关闭时 shell 退出，后台任务收到 SIGHUP 被终止。
解法：nohup 命令 > log 2>&1 & 完整写法，或 systemd 托管。

坑 4：killall 按名字杀误伤
结论：killall java 把所有 java 进程都杀了，包括不该杀的。
原因：killall 按进程名匹配，同名进程全中招。
解法：用 pkill -f 精确匹配，或 pgrep 先确认 PID 再 kill。

坑 5：pgrep 匹配到 PID 1 或关键进程
结论：pkill -f 模式太宽，误杀 systemd 或关键服务。
原因：-f 匹配完整命令行，模式宽会误伤。
解法：先用 pgrep -af 预览匹配结果，确认无误再 pkill。

坑 6：kill 命令发错信号号
结论：kill -15 写成 kill -1（SIGHUP），服务没停反而重载了配置。
原因：信号号记混，1 是 SIGHUP 不是 SIGTERM。
解法：用名字 kill -TERM/kill -s TERM 代替数字，或 kill -l 先查对照表。

坑 7：nohup 输出没重定向，进程卡住
结论：nohup 命令 & 没加重定向，nohup 自动写 nohup.out，日志失控或无输出导致没法排错。
原因：stdout/stderr 没显式重定向，进程可能因写 nohup.out 或管道阻塞。
解法：nohup 命令 > /path/to.log 2>&1 & 显式重定向，日志路径可控。
```
