## 概述

IPC（Inter-Process Communication，进程间通信）是进程之间交换数据的机制。六种主要方式：管道（匿名，父子进程）、命名管道（FIFO，无亲缘进程）、信号量（同步互斥）、共享内存（最快）、消息队列（结构化消息）、socket（网络/本地）。它们各有适用场景：管道适合流水线、共享内存适合大数据量、socket 适合跨机通信。查看当前系统的 IPC 用 ipcs。

```text
六种 IPC 对比：
1. 管道 |          —— 匿名单向，父子进程，shell 流水线
2. 命名管道 mkfifo —— 有名字的管道文件，无亲缘关系进程
3. 信号量           —— 同步互斥、计数，防止竞争
4. 共享内存         —— 映射同一块物理内存，速度最快
5. 消息队列         —— 结构化消息，按类型收发
6. socket          —— 网络通信，跨主机/本地
```

```text
# 实测（本机当前无在用 IPC）
$ ipcs
--------- 消息队列 -----------
（空）
------------ 共享内存段 --------------
（空）
--------- 信号量数组 -----------
（空）
# 系统里没进程在用 System V IPC（消息队列/共享内存/信号量），属正常
```

选型速记：同机父子进程流水线用管道；同机无亲缘进程用命名管道/socket；同机大数据量高频通信用共享内存；结构化消息、多消费者用消息队列；跨机一律 socket。

## 核心概念

### 管道与命名管道

管道分两种：匿名管道（shell 的 `|`，连接父子进程，单向、随进程结束消失）和命名管道（FIFO，mkfifo 创建的文件，有名字、可被无亲缘关系的进程读写）。匿名管道是 shell 流水线的基础，命名管道让「不相关的两个进程」也能通过文件路径通信。命名管道的读写会阻塞——没写入方读会等，没读方写会等。

```shell
# 匿名管道（父子进程，单向）
ls -l | wc -l

# 命名管道（FIFO，无亲缘进程）
mkfifo /tmp/myfifo
# 终端 A 写入
echo "hello" > /tmp/myfifo
# 终端 B 读取
cat /tmp/myfifo      # 输出 hello
rm /tmp/myfifo
```

```text
匿名管道 vs 命名管道：
1. 匿名管道 | —— 父子进程间，单向，进程结束即消失
2. 命名管道 FIFO —— 有文件名，无亲缘进程可通信，读写阻塞等待对方
```

按「是什么 → 为什么 → 怎么用 → 边界」拆开：

- 是什么：管道是内核维护的一段环形缓冲区，一头写、一头读，数据是「字节流」。
- 为什么：shell 流水线（`a | b | c`）是最自然的进程协作方式，管道把命令的输出直接接到下一个命令的输入，不用落盘。
- 怎么用：匿名管道用 `|`；命名管道用 `mkfifo` 建文件、再像普通文件一样读写；代码里匿名管道对应 `pipe()`+`fork()`。
- 边界/易错点：单向（要双向建两根）；无消息边界（字节流，接收方要自己切分）；匿名管道随进程结束消失；命名管道读写默认阻塞，没对端会卡住。

```shell
# 匿名管道的变体用法
ls | tee /tmp/list.txt | wc -l        # tee 把数据分两路：落盘 + 继续传
diff <(sort a.txt) <(sort b.txt)      # 进程替换：把命令输出当「文件」接给 diff
```

```shell
# 命名管道：非阻塞读（没数据就立即返回，不卡住）
timeout 3 cat /tmp/myfifo            # 3 秒内没数据就超时退出
```

### 信号量

信号量（semaphore）用于进程间的「同步和互斥」——本质是一个计数器，控制「同时最多几个进程访问某资源」。它不传输数据，只协调顺序、防止竞争（比如两个进程同时写一个文件）。信号量的经典应用是「互斥锁」和「限制并发数」。System V 信号量用 semget/semop 操作，POSIX 信号量用 sem_open/sem_wait。

```text
信号量要点：
1. 本质 —— 计数器，P 操作减一（获取）、V 操作加一（释放）
2. 用途 —— 互斥（二进制信号量=锁）、限制并发（计数信号量）
3. 不传数据 —— 只协调，配合共享内存一起用
```

- 是什么：一个内核维护的整数计数器，P/V（wait/post）操作是原子的。
- 为什么：多个进程并发访问同一资源（共享内存、文件、设备）时会竞争，需要一种「跨进程」的互斥/限流机制——进程内的锁（mutex）管不了别的进程。
- 怎么用：互斥场景初值设为 1；限流场景初值设为并发上限。POSIX 命名信号量可跨无亲缘进程使用。
- 边界/易错点：P/V 必须成对，忘了 post 会造成死锁；信号量不传数据，得配共享内存；进程异常退出不会自动释放已持有的信号量。

```c
// sem_demo.c —— POSIX 命名信号量：两个进程互斥访问临界区
#include <stdio.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <semaphore.h>
#include <unistd.h>

int main(void) {
    // 初值 1 = 二进制信号量（互斥锁）；设 3 则同时允许 3 个进程进入
    sem_t *sem = sem_open("/demo_sem", O_CREAT, 0644, 1);
    if (sem == SEM_FAILED) { perror("sem_open"); return 1; }

    for (int i = 0; i < 3; i++) {
        sem_wait(sem);               // P 操作：减一，为 0 时阻塞等待
        printf("PID=%d 进入临界区 %d\n", getpid(), i);
        sleep(1);                    // 模拟独占访问共享资源
        sem_post(sem);               // V 操作：加一，唤醒等待者
        sleep(1);
    }
    sem_close(sem);
    return 0;
}
```

```shell
gcc -o sem_demo sem_demo.c -lpthread   # 编译（sem_* 在 glibc/pthread 里）
./sem_demo & ./sem_demo                # 同时跑两个实例，观察互斥（一次只一个进临界区）
```

```shell
# shell 里最常用的「互斥」其实是文件锁 flock，比裸信号量更省事
flock -n /tmp/app.lock -c 'echo 只有一个进程能执行这段'
```

### 共享内存

共享内存是最快的 IPC——多个进程把同一块物理内存映射到各自的地址空间，直接读写、不经过内核拷贝（相比管道/socket 要拷贝数据）。适合大数据量、高频通信（如数据库进程共享缓存）。缺点是要自己处理同步（配合信号量防竞争）。System V 用 shmget/shmat，POSIX 用 shm_open/mmap。查看用 ipcs -m。

```text
共享内存要点：
1. 最快 —— 直接映射同一物理内存，无内核拷贝
2. 场景 —— 大数据量、高频通信（进程共享缓存）
3. 缺点 —— 需自己同步（配合信号量），管理复杂
```

- 是什么：内核把同一块物理内存页映射进多个进程的地址空间，大家读写的是同一片内存。
- 为什么：管道/socket 每次收发都要「用户态 → 内核 → 用户态」拷贝一遍，大数据量时拷贝开销大；共享内存零拷贝，是最快的 IPC。
- 怎么用：System V 用 shmget+shmat+shmdt；POSIX 用 shm_open+mmap；Python 有 `multiprocessing.shared_memory` 高层封装。
- 边界/易错点：本身不提供同步，并发写会竞争（必须配信号量/锁）；进程退出后 System V 共享内存不会自动释放（残留需 ipcrm）；无边界保护，越界写会踩其它进程数据。

```python
# shm_demo.py —— 两个进程通过共享内存交换数据（零拷贝）
import multiprocessing as mp
from multiprocessing import shared_memory

def writer(name):
    shm = shared_memory.SharedMemory(name=name)   # 挂载已创建的共享内存
    shm.buf[:5] = b'hello'                         # 直接写共享内存
    shm.close()

def reader(name):
    shm = shared_memory.SharedMemory(name=name)
    print('读到的数据:', bytes(shm.buf[:5]).decode())
    shm.close()

if __name__ == '__main__':
    shm = shared_memory.SharedMemory(create=True, size=64)  # 创建 64 字节共享内存
    p1 = mp.Process(target=writer, args=(shm.name,))
    p2 = mp.Process(target=reader, args=(shm.name,))
    p1.start(); p2.start()
    p1.join(); p2.join()
    shm.close()
    shm.unlink()   # 释放共享内存段
```

```shell
python3 shm_demo.py                 # 运行：reader 读到 writer 写的数据
# 对比：手动创建 System V 共享内存段，再用 ipcs 查看
ipcmk -M 1024                       # 建一个 1KB 的 System V 共享内存
ipcs -m                             # 查看（能看到 key/owner/bytes）
ipcrm -m <shmid>                    # 用完删除
```

### 消息队列

消息队列是「有结构的消息传递」——进程把一条条有类型、有边界的消息放进队列，另一个进程按类型取。和管道（字节流、无边界）不同，消息队列是「一条条消息」的，天然有边界。适合「生产者-消费者」模式。System V 用 msgget/msgsnd/msgrcv，POSIX 用 mq_open/mq_send。

```text
消息队列 vs 管道：
1. 消息队列 —— 结构化、有边界、按类型收发，可多对多
2. 管道 —— 字节流、无边界、单向，一对多需配合
```

- 是什么：内核维护的一个「消息链表」，每条消息有类型（mtype）和内容，进程按类型入队/出队。
- 为什么：有些场景需要「按消息类型区分处理」「多消费者各取所需」「消息有边界」，字节流管道做不到这些。
- 怎么用：System V 用 msgget/msgsnd/msgrcv；POSIX 用 mq_open/mq_send/mq_receive；查看用 ipcs -q。
- 边界/易错点：单条消息受 msgmax 限制（默认 8192 字节）；队列总量受 msgmnb 限制；System V 队列进程退出不自动释放；按类型取时类型写 0 表示取任意一条。

```c
// mq_demo.c —— System V 消息队列：生产者 / 消费者
#include <stdio.h>
#include <string.h>
#include <sys/ipc.h>
#include <sys/msg.h>

struct msgbuf {
    long mtype;      // 消息类型，必须 > 0
    char mtext[64];  // 消息内容
};

int main(int argc, char **argv) {
    key_t key = ftok("/tmp", 'M');            // 生成 key（同一路径+字符得同一 key）
    int mq = msgget(key, IPC_CREAT | 0644);   // 打开/创建队列
    struct msgbuf msg;

    if (argc > 1 && strcmp(argv[1], "send") == 0) {
        msg.mtype = 1;                        // 类型 1
        strcpy(msg.mtext, "hello from producer");
        msgsnd(mq, &msg, strlen(msg.mtext) + 1, 0);   // 发送（按消息内容长度）
        printf("已发送: %s\n", msg.mtext);
    } else {
        msgrcv(mq, &msg, sizeof(msg.mtext), 0, 0);    // 接收任意类型（0）
        printf("已接收: %s\n", msg.mtext);
    }
    return 0;
}
```

```shell
gcc -o mq_demo mq_demo.c              # 编译
./mq_demo send                        # 终端 A：发送
./mq_demo recv                        # 终端 B：接收（mtype 0 收任意类型）
ipcs -q                               # 查看消息队列（key/owner/字节数）
ipcrm -q <msgid>                      # 用完清理
```

### socket

socket 是最通用的 IPC——既能本地进程通信（Unix domain socket，如 /run/mysqld.sock），也能跨主机网络通信（TCP/UDP）。它是网络编程的基础，几乎所有服务间通信（HTTP、MySQL、Redis、微服务 RPC）都基于 socket。本地 socket 比网络 socket 快（不走网络栈），同一台机器上的进程间通信用 Unix socket 更高效。

```shell
# 查看本机的 socket（本地 + 网络）
ss -lntup | head
# 本地 Unix domain socket
ss -xl | head
```

```text
socket 两种类型：
1. Unix domain socket —— 本地进程通信，路径形如 /run/xxx.sock，快
2. 网络 socket —— TCP/UDP，跨主机，IP:端口
```

- 是什么：socket 是「网络/本地通信的端点」，本地用 AF_UNIX（Unix domain socket，文件路径寻址），跨机用 AF_INET（IP:端口寻址）。
- 为什么：它是唯一能「跨主机」的 IPC，也是微服务/数据库/缓存通信的通用底座；同机场景用 Unix socket 比 TCP 少一层网络栈，更快。
- 怎么用：服务端 bind+listen+accept，客户端 connect，然后 read/write（或 send/recv）。数据库、Redis、Docker daemon 都用 /run 下的 .sock 做本地通信。
- 边界/易错点：Unix socket 路径约 108 字节上限；socket 是字节流，同样无消息边界（要应用层协议/长度前缀切分）；服务端要处理 accept 后的并发。

```python
# unix_socket_server.py —— 本地进程间通信（Unix domain socket）
import socket, os

SOCK_PATH = "/tmp/demo.sock"
if os.path.exists(SOCK_PATH):
    os.remove(SOCK_PATH)

srv = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
srv.bind(SOCK_PATH)
srv.listen(1)
print(f"监听 {SOCK_PATH}")

conn, _ = srv.accept()
print("收到:", conn.recv(1024).decode())
conn.sendall(b"pong")
conn.close()
srv.close()
```

```python
# unix_socket_client.py
import socket

cli = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
cli.connect("/tmp/demo.sock")
cli.sendall(b"ping")
print("回复:", cli.recv(1024).decode())
cli.close()
```

```shell
python3 unix_socket_server.py &      # 先起服务端（后台）
python3 unix_socket_client.py        # 再跑客户端，打印「回复: pong」
```

## 工作原理

六种 IPC 的底层数据流分两类：「数据拷贝型」和「直接映射型」：

1. **数据拷贝型**（管道/消息队列/socket）：数据从发送方用户态 → 内核缓冲区 → 接收方用户态，至少一次内核拷贝，安全但慢。
2. **直接映射型**（共享内存）：多个进程把同一块物理页映射进各自地址空间，直接读写、零拷贝，最快但要自己同步。

信号量是特例——它不传数据，只维护一个内核计数器，靠原子加减实现互斥和限流。

```text
IPC 数据流对比：
管道/socket/消息队列：发送方 → 内核缓冲区 → 接收方（有拷贝，慢但安全）
共享内存：           双方直接映射同一物理页（零拷贝，最快）
信号量：             内核计数器 P/V 操作（不传数据，只协调）
```

各机制的底层支撑：

```text
管道/命名管道   —— 内核 pipe 缓冲区（环形缓冲，默认 64KB），pipe()/mkfifo 创建
消息队列       —— 内核消息链表，每条带 mtype，msgget 创建
共享内存       —— mmap 把同一物理页映射到多进程地址空间，页表指向同一物理页
信号量         —— 内核原子计数器，P/V 用原子指令（futex/自旋）保证不被打断
socket         —— 内核 socket 结构 + 协议栈（本地走 AF_UNIX 直接队列，网络走 TCP/IP）
```

```text
mmap 为什么能零拷贝：
普通 read/write 要经过「用户缓冲区 ↔ 内核缓冲区」两次拷贝；mmap 让用户虚拟地址
直接映射文件/内存的物理页，读写即操作物理页本身，省掉内核态到用户态的拷贝。
```

## 配置文件解析

System V IPC 的资源上限由内核参数控制（/proc/sys/kernel/），可在 /etc/sysctl.conf 调整：

```text
# /etc/sysctl.conf —— System V IPC 内核参数
kernel.shmmax = 68719476736      # 单个共享内存段最大字节数（默认 32G）
kernel.shmall = 16777216         # 系统共享内存总页数上限
kernel.shmmni = 4096             # 系统最大共享内存段数
kernel.msgmax = 8192             # 单条消息最大字节数
kernel.msgmnb = 16384            # 单个消息队列最大字节数
kernel.sem = 250 32000 32 128    # 信号量：数组数/总量/单次操作/最大信号量
```

```shell
sysctl -w kernel.shmmax=68719476736   # 临时调整（重启失效）
sysctl -p                              # 从 /etc/sysctl.conf 加载
```

```text
POSIX 消息队列（mq_open/mq_send）有独立的挂载点和限制：
/proc/sys/fs/mqueue/msg_max       # 单条消息最大字节数（默认 8192）
/proc/sys/fs/mqueue/msgsize_max   # 队列中消息总字节数上限
/proc/sys/fs/mqueue/queues_max    # 系统最大队列数（默认 256）
# 要使用 POSIX mq，需挂载 mqueue 文件系统：mount -t mqueue none /dev/mqueue
```

```text
每进程的消息队列资源限制（/etc/security/limits.conf）：
@student  soft  msgqueue  819200    # POSIX mq 字节数软限制
@student  hard  msgqueue  819200    # 硬限制
# 超出时报 mq_open 失败，配合 ulimit -q 查看
```

## 应用场景实战

### 场景一：用命名管道做两个独立脚本间的数据传递

```shell
# 1. 建命名管道
mkfifo /tmp/data_pipe
# 2. 生产脚本写入（后台）
(while true; do date; sleep 1; done) > /tmp/data_pipe &
# 3. 消费脚本读取
cat /tmp/data_pipe | head -3
# 4. 清理
rm /tmp/data_pipe
```

### 场景二：查看数据库的本地 socket 通信

```shell
# MySQL/Redis 等本地连接走 Unix socket（比 TCP 快）
ss -xl | grep -E 'mysql|redis|docker'
ls -l /var/run/mysqld/mysqld.sock 2>/dev/null
```

### 场景三：两个进程用共享内存传大量数据（Python）

需要「高性能地传一大块数据、又不想走网络/文件」时，共享内存是最快的选择——这里用 Python 的 shared_memory 演示完整读写流程，并验证数据确实跨进程可见。

```python
# shm_transfer.py —— 进程 A 写共享内存，进程 B 读，零拷贝
import multiprocessing as mp
import time
from multiprocessing import shared_memory

DATA = b"x" * 64        # 模拟一块要传的数据

def writer(name):
    shm = shared_memory.SharedMemory(name=name)
    shm.buf[:len(DATA)] = DATA          # 整块写入共享内存
    shm.close()

def reader(name):
    shm = shared_memory.SharedMemory(name=name)
    assert bytes(shm.buf[:len(DATA)]) == DATA   # 读到一模一样的数据
    print(f"进程 B 读到了 {len(DATA)} 字节，内容一致")
    shm.close()

if __name__ == '__main__':
    shm = shared_memory.SharedMemory(create=True, size=128)
    p1 = mp.Process(target=writer, args=(shm.name,))
    p2 = mp.Process(target=reader, args=(shm.name,))
    p1.start(); p1.join()      # 先写完
    p2.start(); p2.join()      # 再读
    shm.close(); shm.unlink()  # 释放
    print("共享内存已释放")
```

```shell
python3 shm_transfer.py      # 运行：进程 B 读到进程 A 写的数据
# 生产里这套模式用于：进程间共享大缓存、Web 服务器 worker 共享会话、数据库共享缓冲池
```

## 性能与调优

```text
1. 同机通信用 Unix domain socket —— 比 TCP 网络栈少一层，快
2. 大数据量高频通信用共享内存 —— 零拷贝，但要配信号量同步
3. 调整 shmmax/shmall —— 数据库（PostgreSQL 共享缓存）需要大共享内存，默认太小要调
4. 管道适合流式小数据 —— 大文件传输别硬走管道，考虑共享内存或文件
5. 消息队列注意消息大小 —— msgmax 默认 8K，大消息要调大参数
6. 信号量 P/V 要成对且短 —— 临界区尽量短，长临界区会拖累并发、易死锁
7. 减少 IPC 次数 —— 高频小数据通信应批量合并成一次大传输，降低系统调用和拷贝开销
```

## 安全与权限

```text
1. IPC 对象有权限位 —— 共享内存/消息队列/信号量有自己的 owner/group/mode（ipcs 的权限列）
2. 命名管道/socket 文件权限 —— 权限设错（其它用户可读写）会泄露数据
3. Unix socket 路径长度限制 —— 约 108 字节，太深路径会失败，放 /run/ 短路径
4. 残留 IPC 对象 —— 进程异常退出不清理，用 ipcrm 及时回收，防止占满 shmmni
5. 共享内存是「裸内存」 —— 无内核保护，进程越界写会踩其他进程数据，务必严格同步
6. 命名管道/Unix socket 可被窃听 —— 权限放太宽时，其它用户能读到进程间通信的数据
```

### IPC 对象残留 / 连接失败

# 1. 查看残留的 System V IPC 对象
ipcs
# 2. 确认属主和权限

# 3. 清理残留对象

## 常见问题

```text
Q1: 共享内存为什么最快？
A: 多个进程直接映射同一块物理内存，读写不经内核拷贝（管道/socket 都要从用户态拷贝到内核缓冲区）。

Q2: 信号量传数据吗？
A: 不传。信号量只是计数器，负责同步互斥、限制并发，数据要配合共享内存或其它方式传递。

Q3: Unix domain socket 和 TCP socket 选哪个？
A: 同机进程通信用 Unix socket（快、路径寻址）；跨主机用 TCP socket。数据库本地连接默认走 Unix socket。

Q4: ipcs 和 ss 看的 IPC 一样吗？
A: 不一样。ipcs 看 System V IPC（共享内存/消息队列/信号量），ss 看 socket（Unix domain + 网络）。

Q5: 管道为什么不能双向通信？
A: 匿名管道是单向的（一头读一头写）。要双向可以建两根管道（pipe() 返回两个 fd，父子各自复用），或用 socket（天然全双工）。

Q6: 进程异常退出后，各种 IPC 对象会怎样？
A: 管道/socket 随进程退出自动释放；System V IPC（共享内存/消息队列/信号量）不自动释放，会残留，需 ipcrm 清理；POSIX 命名信号量/共享内存（shm_open/sem_open）也会残留，需 shm_unlink/sem_unlink。

Q7: 消息队列的「消息类型 mtype」有什么用？
A: 消费者可以按类型选择性接收（如类型 1 是「紧急」、类型 2 是「普通」），msgrcv 传具体类型只取该类型，传 0 取任意一条，实现多路分流。
```

## 面试题

```text
1. 六种 IPC 方式分别是什么？各自适用场景？
   答：管道（父子流水线）、命名管道（无亲缘进程）、信号量（同步互斥）、共享内存（大数据量最快）、消息队列（结构化消息）、socket（跨机/本地）。

2. 共享内存为什么需要信号量配合？
   答：共享内存本身不同步，多进程并发写同一块内存会竞争、数据错乱，需要信号量做互斥保护临界区。

3. 消息队列和管道有什么区别？
   答：消息队列是结构化的「一条条消息」、有边界、可按类型收发；管道是字节流、无边界、单向。

4. 进程异常退出后 IPC 对象会怎样？
   答：System V IPC（共享内存/消息队列/信号量）不随进程退出自动释放，会残留，需 ipcrm 清理；管道/socket 随进程退出释放。

5. 共享内存为什么「零拷贝」、比管道快在哪？
   答：管道/socket 收发要走「用户态 → 内核缓冲区 → 用户态」至少一次拷贝；共享内存通过 mmap 让多个进程直接映射同一物理页，读写即操作物理页本身，无拷贝开销。

6. POSIX IPC 和 System V IPC 的区别？
   答：System V 用整数 key/id 标识（ipcs/ipcrm 管理）；POSIX 用文件路径标识（shm_open/mq_open/sem_open），接口更简洁、支持进程间命名，但不体现在 ipcs 里。

7. 为什么同机进程通信用 Unix domain socket 而不是 TCP？
   答：Unix socket 不走 TCP/IP 协议栈（不经过网络层、不校验和、不拆包），寻址用文件路径，延迟更低、吞吐更高；TCP 要经过完整网络栈，还占端口。

8. 信号量的 P/V 操作为什么必须原子？
   答：如果「检查值-减一-写回」不是原子操作，两个进程可能同时读到同一值、同时进入临界区，互斥失效。内核用原子指令（或 futex）保证 P/V 不可分割。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 同机进程通信用 Unix socket，比走 TCP 网络栈快
2. 共享内存是最快但最难管的，只在性能关键场景用（配信号量同步）
3. 命名管道注意「读写阻塞」——没对端会卡住，用超时或非阻塞
4. 消息队列适合生产者-消费者，天然有消息边界
5. 跨机通信一律 socket（TCP/UDP），别用本地 IPC 方式硬套
6. 用完的 System V IPC 对象及时 ipcrm，别让残留对象堆积占满内核配额
7. 信号量临界区保持短小，P/V 严格成对，避免死锁和并发瓶颈

### 踩坑记录

```text
坑 1：命名管道读写没对端导致阻塞
结论：cat fifo 没写入方，命令卡住不动。
原因：FIFO 读写是阻塞的，没对端就等。
解法：用超时（timeout 5 cat fifo），或打开时加 O_NONBLOCK 非阻塞。

坑 2：共享内存没配信号量导致数据竞争
结论：两进程同时写共享内存，数据错乱。
原因：共享内存本身不同步，并发写会竞争。
解法：配信号量或互斥锁保护临界区。

坑 3：消息队列和管道混淆，按字节流读消息队列
结论：把消息队列当字节流读，消息边界丢了。
原因：消息队列是「一条条消息」，按消息收发，不是字节流。
解法：理解消息队列的 msgrcv 按类型收，别当管道用。

坑 4：ipcs 看到大量残留的共享内存/信号量
结论：ipcs 一堆进程退出了却没清理的 IPC 对象。
原因：进程异常退出没释放 IPC 资源，残留占用。
解法：ipcrm -m/-s/-q 手动清理残留对象。

坑 5：Unix socket 路径太长或权限不对导致连接失败
结论：socket 文件路径过长（超 108 字节）或权限错，连不上。
原因：Unix socket 路径有长度限制，且 socket 文件权限要放行。
解法：socket 放 /run/ 或短路径，权限设对（属主属组匹配服务）。

坑 6：System V 消息队列传大消息报 EINVAL
结论：msgsnd 发超过 msgmax 的消息，调用失败。
原因：单条消息受 kernel.msgmax 限制（默认 8192 字节）。
解法：调大 kernel.msgmax + kernel.msgmnb，或把大消息拆成多条小消息发送。

坑 7：POSIX 消息队列 mq_open 报「Too many open files」或失败
结论：mq_open 创建队列失败。
原因：POSIX mq 独立受 /proc/sys/fs/mqueue 限制（queues_max 默认 256），且需要挂载 mqueue 文件系统。
解法：检查并挂载 mqueue（mount -t mqueue none /dev/mqueue），调大 queues_max 或清理旧队列。
```
