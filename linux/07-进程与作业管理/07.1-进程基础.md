## 概述

进程是「正在运行的程序」，是 Linux 资源分配和调度的基本单位。每个进程有 PID（唯一标识）和 PPID（父进程 PID），有运行状态（运行/睡眠/僵尸等），进程的诞生靠 fork（复制）+ exec（替换）两个系统调用。理解进程的父子关系、状态、创建机制，是后面进程管理、信号、守护进程的基础。

```text
进程四要素：
1. 进程/线程 —— 进程是资源分配单位，线程是调度单位，一个进程可多线程
2. PID/PPID —— PID 唯一标识进程，PPID 是父进程，进程树从 PID 1（systemd）开始
3. 状态 —— R 运行 / S 睡眠 / D 不可中断 / Z 僵尸 / T 停止 / I 空闲
4. fork/exec —— fork 复制出子进程，exec 用新程序替换进程映像
```

## 核心概念

### 进程与线程与任务

进程是「运行中的程序」，拥有独立的地址空间、文件描述符、资源；线程是进程内的执行流，共享进程的地址空间、更轻量。Linux 里线程和进程在调度上统一叫「任务」（task），都用 task_struct 描述，所以 ps 能看到线程。一个进程（如 nginx）可以有多个线程，但日常运维把「进程」当一个整体看，线程细节用 top -H 看。

```text
进程 vs 线程：
1. 进程 —— 独立地址空间、独立资源，隔离性好、创建开销大
2. 线程 —— 共享进程地址空间，轻量、切换快，但一个崩可能影响同进程其它线程
3. 任务 —— Linux 内核统一把进程/线程当 task 调度
```

要理解这组概念，关键是「为什么要有线程」：进程隔离性好但创建、切换开销大（要复制页表、切换地址空间），线程共享地址空间所以轻量。多线程适合 IO 密集（一个线程等 IO 时其它线程继续跑），多进程适合要强隔离的场景（如 nginx worker 崩一个不影响其它）。Linux 内核里线程就是「共享内存空间、共享文件描述符的 task」，用 `ps -eLf` 能看到线程的 LWP（轻量级进程号，即线程 ID）。

```shell
# 看进程的线程：LWP 是线程号，NLWP 是该进程线程总数
ps -eLf | head -5
# 看某进程的线程及各自 CPU
top -H -p <PID>
# 看线程在 /proc 里的对应目录（每个线程一个 task 子目录）
ls /proc/<PID>/task/
```

```text
边界/易错点：
1. 线程共享地址空间 —— 一个线程野指针/栈溢出可能带崩整个进程，多进程隔离性更强
2. 线程不是越多越好 —— 线程过多上下文切换开销反而变大，IO 密集才适合多线程
3. ps 默认一行一个进程 —— 要看线程必须加 -L，否则看不到 LWP
```

### PID 与 PPID

每个进程有唯一 PID（进程号），PPID 是它的父进程 PID。所有进程构成一棵树：根是 PID 1（systemd），它 fork 出所有其他进程，所以 PPID=0 的只有 systemd 和内核线程。查看用 `ps -ef`（含 PPID）或读 /proc/<pid>/status。理解父子关系才能解释「父进程死了子进程变孤儿」「僵尸进程要父进程回收」。

```text
# 实测（进程树根）
$ ps -ef | head -5
UID   PID  PPID  CMD
root    1     0  /usr/lib/systemd/systemd ...
root    2     0  [kthreadd]
root    3     2  [pool_workqueue_release]
# PID 1 是 systemd（PPID 0，树的根），PID 2 是内核线程 kthreadd
```

```text
# 实测（/proc/self/status 看自己的进程信息）
$ head -8 /proc/self/status
Name:   head
State:  R (running)
Pid:    1081279
PPid:   1081226
# 每个进程在 /proc/<pid>/ 下都有自己的目录，status 里是进程元信息
```

PID 的两个关键特性：一是「唯一但会复用」——进程退出后 PID 会被回收、之后新建的进程可能分到同一个 PID，所以别靠 PID 判断「是不是同一个进程」（要配合启动时间判断）；二是「PPID 会变」——父进程先死，子进程 PPID 变成 1（被 systemd 收养成孤儿进程）。按 PID 找进程用 `pidof`、按父进程找子进程用 `pgrep -P`。

```shell
# 按名字找 PID
pidof nginx
# 找某父进程的所有子进程
pgrep -P <PPID>
# 看进程的父进程是谁
ps -o pid,ppid,comm -p <PID>
```

```text
边界/易错点：
1. PID 会复用 —— 脚本里缓存 PID 后进程可能已退出、PID 被别的进程占用，操作前先确认
2. PPID=1 不代表「是 systemd 拉起的」—— 也可能是父进程死了被收养，看 cmdline 判断
3. 内核线程（cmd 带 [] 的）PPID 是 0 或 2（kthreadd），不是 1，别和普通进程混
```

### 进程状态

进程有六种主要状态（ps 的 STAT 列）：R 运行中/就绪、S 可中断睡眠（最常见，等事件）、D 不可中断睡眠（等 IO，kill 不掉）、Z 僵尸（已退出但父进程没回收）、T 停止（被信号暂停）、I 空闲内核线程。`ps -eo pid,stat,comm` 看状态，STAT 后缀还有额外信息（s=会话领导、< =高优先级、+=前台进程组）。

```text
# 实测（进程状态）
$ ps -eo pid,ppid,stat,comm | head -6
PID   PPID STAT COMMAND
  1      0 Ss   systemd       # S 睡眠 + s 会话领导
  2      0 S    kthreadd      # S 睡眠（内核线程）
  4      2 I<   kworker/...   # I 空闲内核线程 + < 高优先级
```

```text
进程状态速查（STAT 首字符）：
R 运行/就绪 | S 可中断睡眠 | D 不可中断睡眠 | Z 僵尸 | T 停止 | I 空闲
```

六种状态里最容易混淆的是 S / D / Z 三个：S 是「主动睡」（等 socket、等锁，能被信号唤醒），D 是「被动睡」（在内核态等磁盘/网络 IO 返回，信号也被挂起，所以 kill -9 都杀不掉），Z 是「死透但没被收尸」（已 exit，只剩 task_struct 占着 PID 等父进程 wait）。后缀标志里 `s`（会话领导）和 `+`（前台进程组）在写「后台作业」和「信号发给进程组」时有用。要看实时状态变化可以用 `top`（STAT 列），要制造一个 T 状态进程可以用 Ctrl+Z 或 kill -STOP。

```shell
# 制造 T 状态：前台跑 sleep，Ctrl+Z 暂停，看 STAT 变 T
sleep 300
# 按 Ctrl+Z 后：
ps -o pid,stat,comm -p $(pgrep -x sleep)   # STAT=T
bg                                          # 后台继续，STAT 回 S/R
# 用信号直接停/续
kill -STOP <PID>     # 暂停（STAT=T）
kill -CONT <PID>     # 继续
```

```text
边界/易错点：
1. D 状态杀不掉 —— 不是 bug，是进程在内核态等 IO，先查磁盘/网络 IO 瓶颈
2. Z 状态杀不掉 —— 僵尸已退出，只能靠父进程 wait 回收或父进程退出
3. S 状态不代表「没干活」—— 绝大多数进程平时都在 S 态等事件，正常
```

### fork 与 exec

进程的诞生靠两个系统调用：fork 复制当前进程（得到一个几乎一样的子进程），exec 用新程序替换当前进程的内存映像（PID 不变、程序变了）。shell 执行一条命令就是「fork 一个子进程 + 子进程 exec 该命令」。理解 fork/exec 能解释「为什么 shell 里执行命令后 shell 还在」——shell fork 出子进程去 exec 命令，自己等待子进程结束。

```text
fork / exec 机制：
1. fork —— 复制当前进程，父进程得到子进程 PID，子进程从 fork 处继续执行
2. exec —— 用新程序替换当前进程，PID 不变，内存映像全新
3. 组合 —— shell 跑命令 = fork 子进程 + 子进程 exec 命令 + 父进程 wait
```

fork 不是「从头再跑一遍」，而是从 fork 调用点继续执行，靠返回值区分父子：父进程拿到子进程 PID（>0），子进程拿到 0。现代 Linux 的 fork 用「写时复制（COW）」优化——父子先共享同一份内存页，只有一方要写时才复制，所以 fork 很快。exec 则彻底：把进程的代码段、数据段、堆栈全换成新程序的，只保留 PID、已打开的文件描述符（除非设了 O_CLOEXEC）、进程关系等。exec 是「替换」不是「新建」，所以 PID 不变。C 语言里 exec 是一族函数（execl/execv/execle/execve 等），底层都是 execve 系统调用。

```shell
# 观察 fork：一个进程 fork 出子进程
bash -c 'echo "父进程 $$"; (sleep 1; echo "子进程完成") & wait'
```

```c
// fork_exec_demo.c：观察 fork 返回值 + exec 替换
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main() {
    pid_t pid = fork();                 // 调用一次，父子各返回一次
    if (pid < 0) {
        perror("fork");
        return 1;
    } else if (pid == 0) {
        // 子进程：exec 替换成 /bin/echo，PID 不变
        printf("子进程 PID=%d，即将 exec\n", getpid());
        execl("/bin/echo", "echo", "exec 后还是这个 PID", (char *)NULL);
        perror("execl");                // exec 成功不会走到这里
        return 1;
    } else {
        printf("父进程 PID=%d，fork 出子进程 PID=%d\n", getpid(), pid);
        wait(NULL);                     // 回收子进程退出状态，防止僵尸
    }
    return 0;
}
```

```shell
gcc fork_exec_demo.c -o fork_exec_demo && ./fork_exec_demo
```

```text
边界/易错点：
1. fork 会复制文件描述符/锁 —— 子进程不关闭会导致资源泄漏，exec 前对 fd 设 O_CLOEXEC 可防
2. exec 后 PID 不变但程序变了 —— 别以为 exec 是「新建进程」，它是替换
3. 子进程没被 wait 会变僵尸 —— 父进程要 wait/waitpid 回收退出状态
```

## 工作原理

进程的生命周期是「创建 → 就绪/运行 → 睡眠/阻塞 → 退出 → 回收」的状态循环，内核调度器负责在就绪进程间分配 CPU：

1. **创建**：父进程调用 fork 复制自己，子进程再调用 exec 装载新程序，得到一个全新进程。
2. **调度**：内核 CFS 调度器从就绪队列挑进程上 CPU，运行中的进程耗尽时间片或被抢占就切走。
3. **睡眠与唤醒**：进程等 IO/事件时进入 S 睡眠态，事件就绪后被唤醒回到就绪队列等待调度。
4. **退出与回收**：进程 exit 后进入 Z 僵尸态，父进程调用 wait 读取退出状态后才真正释放资源；父进程先死则子进程被 systemd 收养（PPID 变 1）。

```text
进程生命周期：
fork(创建) → exec(装载) → R 运行 → S 睡眠(等事件) → exit(退出) → Z 僵尸 → 父进程 wait 回收

状态迁移：
就绪/运行(R) → 睡眠(S/D) → 就绪(R) → 运行 → 退出 → 僵尸(Z)
```

这里补两个机制细节，解释「为什么 fork 快、exec 慢」和「为什么有僵尸」：

1. **写时复制（Copy-on-Write）**：fork 后父子进程并不立即复制全部内存，而是共享同一份物理页并标记为只读；任何一方要写时才触发缺页、复制那一页。所以 fork 一个几百 MB 内存的进程几乎是瞬时完成，真正复制发生在「写」的那一刻。这也解释了为什么 fork 后马上 exec 最划算——子进程还没来得及写就 exec 换掉了，几乎没复制成本。
2. **僵尸与 wait**：子进程 exit 后，内核保留它的 task_struct（PID、退出状态、CPU 时间），进入 Z 态，等父进程调用 wait/waitpid 读取退出状态后才彻底释放。父进程一直不 wait，僵尸就一直占着 PID；父进程自己也死了，子进程变孤儿被 systemd 收养，systemd 会代劳 wait 回收。所以「大量僵尸」的根因通常是某个父进程没正确 wait，而不是内核问题。

```text
写时复制 vs 直接复制：
fork 直接复制 —— 慢、占内存翻倍，早期 Unix 做法
fork 写时复制 —— 共享 + 写时才复制，现代 Linux 默认，fork 后 exec 成本最低
```

## 常用命令与配置

```shell
ps aux                 # 全部进程 + 资源占用（BSD 风格）
ps -ef                 # 全部进程 + PPID（System V 风格）
ps -ef --forest        # 树状显示父子关系
ps -eo pid,ppid,stat,ni,comm   # 自定义输出列
ps -eLf                # 看线程（LWP/NLWP 列）
pstree -p              # 进程树（带 PID）
pstree -ap nginx       # 看 nginx 的进程树 + 完整命令行
top -H -p <PID>        # 看某进程的线程
pgrep -a <name>        # 按名字找进程 + 完整命令行
pgrep -P <PPID>        # 找某父进程的子进程
pidof <name>           # 按名字输出 PID（空格分隔）
ls /proc/<pid>/        # 看某进程的内核信息目录
```

```text
看进程的两个角度：
1. ps aux —— 看资源占用（%CPU/%MEM/RSS），排查谁在吃资源
2. ps -ef —— 看父子关系（PID/PPID），理解进程树
```

## 配置文件解析

进程的运行时信息不靠配置文件，而靠 /proc 伪文件系统——每个进程一个目录，实时反映内核态信息：

```text
/proc/<pid>/status     进程元信息（State/Pid/PPid/线程数/内存）
/proc/<pid>/cmdline    完整启动命令（\0 分隔，ps -ef 的来源）
/proc/<pid>/environ    环境变量
/proc/<pid>/fd/        打开的文件描述符
/proc/<pid>/limits     资源限制（ulimit）
/proc/<pid>/stat       状态 + 累计 CPU 时间
/proc/<pid>/task/      该进程的所有线程（每个线程一个子目录）
/proc/<pid>/maps       内存映射（代码段/堆/栈/动态库）
/proc/<pid>/exe        指向可执行文件的符号链接
/proc/<pid>/cwd        指向当前工作目录的符号链接
```

```text
/proc 是「内核向用户态暴露的窗口」：
不是磁盘上的真实文件，读取时才由内核动态生成，所以能实时反映进程当前状态
```

几个常用读取姿势：`tr '\0' ' ' < /proc/<pid>/cmdline` 把 NUL 分隔的命令行还原成空格可读形式；`readlink /proc/<pid>/exe` 看进程实际运行的是哪个二进制（删了原文件后这里会显示 " (deleted)"）；`ls -l /proc/<pid>/fd/` 等价于 lsof，看进程打开了哪些文件/socket。

```shell
# 还原完整命令行（cmdline 用 \0 分隔）
tr '\0' ' ' < /proc/<pid>/cmdline
# 看进程的可执行文件路径
readlink /proc/<pid>/exe
# 看进程打开的文件描述符
ls -l /proc/<pid>/fd/
```

## 应用场景实战

### 场景一：查看进程树，理解父子关系

```shell
# 1. 看完整进程树（含父子关系）
ps -ef --forest | head -20
# 2. 或按树显示某个服务的进程
pstree -p nginx
# 3. 查看某进程的父进程
ps -o pid,ppid,cmd -p <PID>
# 4. 顺藤摸瓜：找某进程的所有子进程
pgrep -P <PID>
```

### 场景二：排查僵尸进程

```shell
# 1. 找僵尸进程（STAT 是 Z）
ps -eo pid,ppid,stat,comm | grep ' Z '
# 2. 找到僵尸的父进程，让它回收
# 僵尸进程无法 kill，要父进程 wait 回收或父进程退出
ps -o ppid= -p <僵尸PID>
# 3. 看父进程是谁、能不能安全重启
ps -o pid,comm,args -p <父进程PID>
```

### 场景三：查某进程的启动方式与打开的文件

```shell
# 1. 拿到一个 PID 后，看它到底怎么启动的（完整命令行）
tr '\0' ' ' < /proc/<PID>/cmdline
# 2. 看它的可执行文件路径（判断是不是被删了还在跑）
readlink /proc/<PID>/exe
# 3. 看它打开了哪些文件/socket（等价 lsof -p）
ls -l /proc/<PID>/fd/
# 4. 看它的环境变量（排查依赖的 PATH、语言等）
tr '\0' '\n' < /proc/<PID>/environ | head
```

## 性能与调优

```text
进程相关性能点：
1. 上下文切换 —— cs 过高（vmstat 看）说明进程频繁换入换出，CPU 花在切换上
2. 线程数 —— 进程线程过多（top -H 看）反而切换开销大，不是越多越好
3. 文件描述符 —— ulimit -n 太小会报 too many open files，按需调大
4. 僵尸进程 —— 堆积占用 PID 和少量资源，找到父进程及时回收
5. fork 频率 —— 短命进程过多会放大 fork/exec 开销，考虑常驻进程或进程池
```

```shell
vmstat 1 5          # 看 cs（上下文切换）和 in（中断）
ulimit -n           # 看当前进程的文件描述符上限
cat /proc/sys/kernel/pid_max   # 系统最大 PID
# 数当前进程总数，接近 ulimit -u 或 pid_max 要警惕
ps -e --no-headers | wc -l
```

## 安全与权限

```text
进程安全要点：
1. 进程权限继承 —— 进程的 UID/GID 继承自启动它的用户，权限以「运行用户」为准
2. real/effective uid —— setuid 程序运行时 effective uid 可能高于 real uid（如 passwd 是 root）
3. /proc 权限 —— /proc/<pid>/ 默认只有属主和 root 可读，敏感信息不外泄
4. 隐藏参数 —— cmdline 可能含密码（如 mysql -p密码），ps 会暴露，用环境变量或配置文件替代
5. 内核线程 —— 名字带 [] 的是内核线程，不对应可执行文件，别试图 kill
6. hidepid 挂载选项 —— mount -o remount,hidepid=2 /proc 可对其他用户隐藏 /proc/<pid>，多租户机器常用
```

```shell
# 看进程的 UID/GID 和 setuid 位
ps -o pid,user,uid,gid,comm -p <PID>
# 看可执行文件的 setuid 位（s 表示 setuid，如 /usr/bin/passwd）
ls -l /usr/bin/passwd
```

## 故障排查

### 进程卡在 D 状态

```shell
# 1. 找 D 状态进程（不可中断睡眠，多半在等 IO）
ps -eo pid,ppid,stat,comm | awk '$3 ~ /D/'
# 2. 查 IO 瓶颈（D 状态通常是磁盘/网络 IO 卡住）
iostat -x 1 3
# 3. 查进程在等什么（/proc/<pid>/stack 或 wchan）
cat /proc/<pid>/wchan
```

### 进程数超限 / PID 用尽

```shell
# 1. 看当前进程数
ps -e | wc -l
# 2. 看 PID 是否快到上限
cat /proc/sys/kernel/pid_max
# 3. 检查 cgroup 的 pids 限制（容器常因这个报 fork 失败）
cat /sys/fs/cgroup/pids.max 2>/dev/null
```

### fork 失败（Resource temporarily unavailable）

```shell
# 1. 看是不是单用户进程数超限（ulimit -u）
ulimit -u
# 2. 看系统级线程/进程上限
cat /proc/sys/kernel/threads-max
# 3. 看是不是 cgroup pids 限制（容器内 fork 失败的头号原因）
cat /sys/fs/cgroup/pids.max /sys/fs/cgroup/pids.current 2>/dev/null
# 4. 看内存是否耗尽（fork 需要分配 task_struct + 内核栈）
free -h
```

## 常见问题

```text
Q1: 父进程死了，子进程会怎样？
A: 子进程被 systemd（PID 1）收养，PPID 变成 1，成为「孤儿进程」，继续运行。

Q2: 僵尸进程占内存吗？要处理吗？
A: 僵尸进程本身几乎不占内存，但占 PID 号，大量堆积会耗尽 PID 导致无法新建进程。找到父进程让它 wait 回收即可。

Q3: 进程和线程到底什么关系？
A: 进程是资源分配单位（独立地址空间），线程是进程内的调度单位（共享地址空间）。Linux 内核都用 task 描述，调度时按 task 粒度。

Q4: 为什么 ps 看到的命令和实际启动参数不一样？
A: ps 默认读 /proc/<pid>/cmdline，若进程启动后改写了 argv（如 MySQL 隐藏密码），cmdline 会变。用 /proc/<pid>/environ 或进程自身日志确认。

Q5: 什么时候用多线程，什么时候用多进程？
A: IO 密集、需要共享数据用多线程（切换快、共享内存方便）；要强隔离、一个崩溃不影响其它用多进程（nginx worker 模型）。CPU 密集单线程任务线程再多也压不满多核，要配合多进程/多实例。

Q6: 进程的 PPID 变成 1 了，是怎么回事？
A: 两种情况：一是父进程正常退出、子进程被 systemd 收养；二是它本来就是 systemd 拉起的服务。看 cmdline 和 systemctl status 区分。

Q7: PID 会被复用吗？脚本里缓存 PID 安全吗？
A: 会。进程退出后 PID 被回收，之后新进程可能分到同一个 PID。脚本里缓存 PID 后操作前要先用 kill -0 或查 /proc/<pid> 确认进程还活着，且启动时间一致。
```

## 面试题

```text
1. 进程有哪些状态？各是什么含义？
   答：R 运行/就绪、S 可中断睡眠、D 不可中断睡眠、Z 僵尸、T 停止、I 空闲内核线程。D 是等 IO 杀不掉，Z 是退出后父进程未回收。

2. fork 和 exec 的区别？
   答：fork 复制当前进程（父子几乎一样，PID 不同），exec 用新程序替换进程映像（PID 不变、代码变了）。shell 跑命令是 fork + exec。

3. 僵尸进程是怎么产生的？怎么清理？
   答：子进程退出后父进程没调用 wait 回收退出状态，子进程残留为僵尸。清理：让父进程 wait 回收，或杀掉/重启父进程。

4. 孤儿进程和僵尸进程的区别？
   答：孤儿是父进程先死、子进程被 systemd 收养；僵尸是子进程先死、父进程未回收。孤儿会被收养继续运行，僵尸要等父进程回收。

5. fork 时子进程继承了父进程的哪些资源？
   答：地址空间副本（写时复制）、打开的文件描述符、环境变量、信号处理方式、当前工作目录、进程组关系等。注意锁和 fd 也会复制，子进程要处理避免泄漏。

6. 什么是写时复制（Copy-on-Write）？
   答：fork 后父子共享同一份物理内存页并标记只读，任一方要写才复制该页。好处是 fork 快、省内存，尤其 fork 后马上 exec 时几乎零复制。

7. 为什么 D 状态进程 kill -9 也杀不掉？
   答：D 是不可中断睡眠，进程正在内核态等 IO（磁盘/网络），信号被挂起直到 IO 返回。先解决 IO 瓶颈（iostat 定位），进程自然恢复。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 看进程用 ps -ef（含 PPID 和完整命令）或 ps aux（含资源占用）
2. 理解进程树：从 PID 1 往下找父子关系，别孤立地看单个进程
3. 僵尸进程要看父进程——子进程死了父进程不回收才变僵尸
4. 查进程详情读 /proc/<pid>/ 目录，比 ps 更全（status/fd/cmdline/environ）
5. D 状态进程是等 IO，kill 不掉别硬杀，先查 IO 瓶颈
6. 看线程用 ps -eLf 或 top -H，别把「进程」和「线程」混为一谈
7. 脚本里操作 PID 前先确认进程还活着（kill -0 或查 /proc/<pid>），防 PID 复用误伤

### 踩坑记录

```text
坑 1：僵尸进程 kill 不掉
结论：kill -9 僵尸进程无效，它还在 ps 里。
原因：僵尸进程已退出，只是等父进程回收，不响应任何信号。
解法：找到父进程（PPID），让父进程 wait 回收或重启父进程。

坑 2：D 状态进程杀不掉还拖累系统
结论：进程卡在 D 状态，kill -9 无效。
原因：D 是不可中断睡眠，进程在等 IO（磁盘/网络），信号被挂起。
解法：先查 IO 瓶颈（iostat），解决 IO 问题进程自然恢复。

坑 3：误以为 PID 1 可以随便 kill
结论：kill PID 1（systemd）会导致系统崩溃。
原因：PID 1 是所有进程的祖先、内核特殊对待，杀了它系统就挂了。
解法：永远别对 PID 1 动手，重启系统用 reboot。

坑 4：fork 出的子进程继承了父进程的资源导致泄漏
结论：子进程继承了父进程的文件描述符、锁，父进程退出后资源没释放。
原因：fork 会复制父进程的资源句柄，子进程不关就泄漏。
解法：子进程用完的资源及时关闭，或用 exec 替换（exec 会重置）。

坑 5：用 ps 只看到进程名看不到完整命令，定位不到
结论：ps 默认截断长命令，看不到完整参数。
原因：终端宽度或 ps 默认格式截断了 COMMAND 列。
解法：ps auxww（w 重复取消截断）或 ps -ef --width 200。

坑 6：容器里 fork 报 Resource temporarily unavailable
结论：进程/线程创建失败，报资源不可用。
原因：多半是 cgroup 的 pids.max 限制到了，或 ulimit -u 进程数上限，不是内存真不够。
解法：查 /sys/fs/cgroup/pids.max 和 ulimit -u，按需调高或减少进程数。

坑 7：把 PPID=1 的进程误当成 systemd 服务
结论：看到某进程 PPID=1 就以为是系统服务。
原因：PPID=1 也可能是父进程死后被收养的孤儿进程，和「systemd 拉起的服务」是两回事。
解法：用 systemctl status <名> 或看 cmdline 判断，别只看 PPID。
```
