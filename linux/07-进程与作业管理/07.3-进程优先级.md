## 概述

进程优先级决定「CPU 时间片怎么分配」——优先级高的进程更先、更多地被调度。调整手段分三层：nice/renice（进程级，调 nice 值）、调度器（内核 CFS 根据优先级公平分配）、cgroups（组级，精确限制 CPU 配额）。nice 值范围 -20（最高优先级）到 19（最低），默认 0。日常「让批量任务别抢资源」「给关键服务调高优先级」就用 nice/renice。

```text
优先级三层控制：
1. nice/renice —— 进程级，nice 值 -20~19（越小优先级越高），默认 0
2. 调度器 —— 内核 CFS 完全公平调度器，按优先级分配 CPU 时间片
3. cgroups —— 组级，给进程组设 CPU 配额/上限，容器限制的底层
```

## nice 与 renice

nice 在启动进程时设优先级，renice 修改运行中进程的优先级。nice 值越小优先级越高：-20 最高、19 最低、默认 0。普通用户只能调高自己的 nice 值（降优先级），只有 root 能调低（升优先级）。典型用法：`nice -n 10 批量任务` 让重任务别抢 CPU，`renice -n -5 -p PID` 给关键进程提优先级。

```text
# 实测（内核高优先级线程 nice 是 -20）
$ ps -eo pid,ni,comm | sort -k2 -n | head -5
   101 -20 kworker/R-acpi_thermal_pm
    10 -20 kworker/0:0H-kblockd
   106 -20 kworker/R-mld
# 内核线程 nice=-20（最高优先级），普通进程默认 0
```

```shell
nice -n 10 ./backup.sh          # 启动时降优先级
nice -n -5 ./critical.sh        # 启动时升优先级（需 root）
renice -n 10 -p 1234            # 修改运行中进程
renice -n -5 -p 1234            # 提升优先级（需 root）
```

## 调度器与优先级

Linux 默认用 CFS（Completely Fair Scheduler，完全公平调度器），核心思想是「公平分配 CPU 时间」——每个进程按优先级获得权重，优先级高的权重高、分到的时间片多。CFS 不按「先来先服务」，而是维护一个按虚拟运行时间排序的红黑树，总是调度虚拟时间最小的进程。nice 值影响的是权重（nice 差一级，权重差约 10%），不是绝对的先后顺序。

```text
CFS 调度器要点：
1. 公平 —— 所有进程按权重公平分 CPU，nice 值影响权重
2. 权重 —— nice 每降 1 级，权重约增 10%，分到更多 CPU
3. 实时 —— 实时进程（SCHED_FIFO/SCHED_RR）优先于普通进程
```

```shell
chrt -p 1234              # 查看进程的调度策略
chrt -f -p 50 1234        # 设为实时 FIFO 策略（需 root，慎用）
```

## cgroups CPU 限制

cgroups 能按「进程组」精确限制 CPU：cpu.max 设配额（如 50% 的 CPU）、cpu.weight 设权重（组间按权重分）。这是容器（Docker --cpus）和 systemd 服务（CPUQuota=）资源限制的底层。相比 nice（只是「建议」优先级），cgroups 的 CPU 配额是硬限制——进程最多用那么多 CPU，用不完也不超。做多租户隔离、限制某个服务别吃满 CPU 就用 cgroups。

```shell
# systemd 服务级 CPU 限制
systemctl set-property nginx CPUQuota=200%    # 最多 2 核
systemctl set-property nginx CPUWeight=500     # 权重（相对）

# Docker 容器 CPU 限制（底层 cgroups）
docker run --cpus 1.5 myapp       # 最多 1.5 核
docker run --cpuset-cpus 0-1 myapp  # 绑定到 CPU 0 和 1
```

```text
nice vs cgroups：
1. nice —— 进程级「建议」，影响调度权重，不保证上限
2. cgroups —— 组级「硬限制」，CPU 配额是硬上限，容器/服务级隔离
```

## 应用场景实战

### 场景一：批量备份任务降优先级，别影响线上服务

```shell
# 备份是重 IO/CPU 任务，降优先级避免抢线上服务的 CPU
nice -n 19 tar czf /backup/data.tar.gz /data
# 或对已运行的备份进程降级
renice -n 19 -p $(pgrep -f 'tar.*backup')
```

### 场景二：用 cgroups 限制某个服务别吃满 CPU

```shell
# 1. 限制服务最多用 1 个核
systemctl set-property myapp.service CPUQuota=100%
# 2. 验证生效
systemctl show myapp.service -p CPUQuotaPerSecUSec
# 3. 压测确认 CPU 不超限
top -p $(pgrep -f myapp)
```

## 最佳实践与踩坑记录

### 最佳实践

1. 批量任务（备份/日志压缩）用 nice 降优先级，别和线上抢 CPU
2. 普通用户只能降优先级（调高 nice），升优先级要 root
3. 硬性限制 CPU 用 cgroups（systemd CPUQuota / docker --cpus），nice 只是建议
4. 数据库/关键服务别乱动 nice，默认 0 即可，用 cgroups 隔离更可控
5. 实时调度策略（chrt）慎用，配错会让系统卡死

### 踩坑记录

```text
坑 1：普通用户 renice 提优先级报 Operation not permitted
结论：renice -n -5 报权限不足。
原因：只有 root 能提升优先级（降 nice 值），普通用户只能降优先级。
解法：提优先级用 sudo，或接受只能降不能升的限制。

坑 2：nice 调了但 CPU 还是被抢
结论：nice 19 的进程还是占了不少 CPU。
原因：nice 只是「建议权重」，CPU 空闲时低优先级进程照样跑满。
解法：要硬限制用 cgroups（CPUQuota/--cpus），nice 做不到硬上限。

坑 3：chrt 设实时策略导致系统卡死
结论：进程设 SCHED_FIFO 实时策略，整个系统响应迟钝。
原因：实时进程优先级高于一切，跑死循环会饿死其他进程。
解法：别轻易用 chrt 设实时策略，确需也设 CPU 亲和性隔离核心。

坑 4：cgroups 配了 CPUQuota 不生效
结论：systemctl set-property 设了 CPUQuota，服务还是跑满。
原因：改了没 reload/restart 服务，或没配 CPUAccounting。
解法：确认 CPUAccounting=yes，重启服务后再验证。

坑 5：把 nice 值理解成「越大优先级越高」
结论：nice 19 的进程反而更慢，和直觉相反。
原因：nice 值语义是「谦让度」，越大越谦让、优先级越低。
解法：记「nice 越小优先级越高，-20 最高，19 最低」。
```
