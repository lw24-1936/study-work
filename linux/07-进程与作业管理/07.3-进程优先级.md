## 概述

进程优先级决定「CPU 时间片怎么分配」——优先级高的进程更先、更多地被调度。调整手段分三层：nice/renice（进程级，调 nice 值）、调度器（内核 CFS 根据优先级公平分配）、cgroups（组级，精确限制 CPU 配额）。nice 值范围 -20（最高优先级）到 19（最低），默认 0。日常「让批量任务别抢资源」「给关键服务调高优先级」就用 nice/renice。

```text
优先级三层控制：
1. nice/renice —— 进程级，nice 值 -20~19（越小优先级越高），默认 0
2. 调度器 —— 内核 CFS 完全公平调度器，按优先级分配 CPU 时间片
3. cgroups —— 组级，给进程组设 CPU 配额/上限，容器限制的底层
```

## 核心概念

### nice 与 renice

nice 在启动进程时设优先级，renice 修改运行中进程的优先级。nice 值越小优先级越高：-20 最高、19 最低、默认 0。普通用户只能调高自己的 nice 值（降优先级），只有 root 能调低（升优先级）。典型用法：`nice -n 10 批量任务` 让重任务别抢 CPU，`renice -n -5 -p PID` 给关键进程提优先级。

```text
# 实测（内核高优先级线程 nice 是 -20）
$ ps -eo pid,ni,comm | sort -k2 -n | head -5
   101 -20 kworker/R-acpi_thermal_pm
    10 -20 kworker/0:0H-kblockd
   106 -20 kworker/R-mld
# 内核线程 nice=-20（最高优先级），普通进程默认 0
```

```shell
nice -n 10 ./backup.sh          # 启动时降优先级
nice -n -5 ./critical.sh        # 启动时升优先级（需 root）
renice -n 10 -p 1234            # 修改运行中进程
renice -n -5 -p 1234            # 提升优先级（需 root）
renice -n 5 -u alice            # 修改某用户所有进程的优先级
renice -n 10 -g $(pgrep -d' ' -g web)   # 修改某进程组的优先级
```

nice 是「谦让度」的语义：值越大越谦让（把 CPU 让给别人）、优先级越低，这跟直觉「数字大优先级高」相反，是新手最容易记反的点。还要区分「nice 值」和「调度优先级（pri）」——top 里 NI 列是 nice 值，PR 列是实际调度优先级（内核按 nice 换算，普通进程 PR ≈ 20 + nice）。nice 只影响「竞争 CPU 时的分配比例」，CPU 空闲时 nice 19 的进程照样能跑满，它不是一个硬上限。

```text
边界/易错点：
1. nice 是「建议」不是「上限」—— CPU 空闲时低优先级进程也能占满
2. 普通用户只能降优先级（nice 变大），升优先级（nice 变小）要 root
3. nice 值 ≠ top 的 PR 列 —— PR 是内核换算后的调度优先级，别混
```

### 调度器与优先级

Linux 默认用 CFS（Completely Fair Scheduler，完全公平调度器），核心思想是「公平分配 CPU 时间」——每个进程按优先级获得权重，优先级高的权重高、分到的时间片多。CFS 不按「先来先服务」，而是维护一个按虚拟运行时间排序的红黑树，总是调度虚拟时间最小的进程。nice 值影响的是权重（nice 差一级，权重差约 10%），不是绝对的先后顺序。

```text
CFS 调度器要点：
1. 公平 —— 所有进程按权重公平分 CPU，nice 值影响权重
2. 权重 —— nice 每降 1 级，权重约增 10%，分到更多 CPU
3. 实时 —— 实时进程（SCHED_FIFO/SCHED_RR）优先于普通进程
```

调度策略分「普通」和「实时」两大类：普通策略是 SCHED_OTHER（默认，CFS 调度），还有 SCHED_BATCH（批处理，少抢占、适合后台批量）和 SCHED_IDLE（空闲才跑，优先级最低）；实时策略是 SCHED_FIFO（先来先服务、不抢到不释放）和 SCHED_RR（轮转，每个实时进程轮着跑固定时间片）。实时进程优先级永远高于普通进程，一个实时死循环能饿死所有普通进程，所以设实时策略需要 CAP_SYS_NICE 权限且生产慎用。

```shell
chrt -p 1234              # 查看进程的调度策略
chrt -f -p 50 1234        # 设为实时 FIFO 策略（需 root，慎用）
chrt -o -p 0 1234         # 改回普通 SCHED_OTHER 策略
chrt -b -p 0 1234         # 设为批处理 SCHED_BATCH
```

```text
调度策略速查：
SCHED_OTHER(0) 默认 CFS 普通调度 | SCHED_BATCH(3) 批处理 | SCHED_IDLE(5) 空闲才跑
SCHED_FIFO(1)  实时先来先服务 | SCHED_RR(2) 实时轮转 —— 实时策略优先级高于一切普通进程
```

### cgroups CPU 限制

cgroups 能按「进程组」精确限制 CPU：cpu.max 设配额（如 50% 的 CPU）、cpu.weight 设权重（组间按权重分）。这是容器（Docker --cpus）和 systemd 服务（CPUQuota=）资源限制的底层。相比 nice（只是「建议」优先级），cgroups 的 CPU 配额是硬限制——进程最多用那么多 CPU，用不完也不超。做多租户隔离、限制某个服务别吃满 CPU 就用 cgroups。

```shell
# systemd 服务级 CPU 限制
systemctl set-property nginx CPUQuota=200%    # 最多 2 核
systemctl set-property nginx CPUWeight=500     # 权重（相对）

# Docker 容器 CPU 限制（底层 cgroups）
docker run --cpus 1.5 myapp       # 最多 1.5 核
docker run --cpuset-cpus 0-1 myapp  # 绑定到 CPU 0 和 1
```

cgroup v2 的 CPU 控制器有两个核心文件：`cpu.max`（配额+周期，写成 `$MAX $PERIOD`，如 `200000 100000` 表示每 100ms 周期最多用 200ms = 2 核；写成 `max 100000` 表示不限配额）、`cpu.weight`（组间按权重比例分 CPU，默认 100，范围 1~10000）。systemd 的 CPUQuota/CPUWeight、Docker 的 --cpus/--cpu-shares 最终都落到这两个文件上。cgroup 是「组级」控制——一整组进程共享一个配额，组内进程再互相竞争。

```text
nice vs cgroups：
1. nice —— 进程级「建议」，影响调度权重，不保证上限
2. cgroups —— 组级「硬限制」，CPU 配额是硬上限，容器/服务级隔离
```

```text
边界/易错点：
1. cpu.max 是硬上限 —— 用不完也不超，和 nice 的「建议」本质不同
2. cgroup 是组级 —— 配额是整组共享，组内进程多了一个个分到的就少
3. CPUQuota 改了要确认服务用了对应 cgroup（systemd 自动，手动写文件要自己建目录放 PID）
```

## 工作原理

CFS 调度器的核心是「按虚拟运行时间（vruntime）公平分配」。每个进程有一个 vruntime，等于实际运行时间按权重折算后的值；调度器维护一棵按 vruntime 排序的红黑树，每次挑 vruntime 最小的进程上 CPU。nice 值越低、权重越大，同样跑 1 秒真实时间，其 vruntime 增长越慢，于是它「显得」运行得少，被调度器优先照顾，从而分到更多 CPU。

```text
CFS 调度流程：
1. 计算每个进程权重（由 nice 值映射，nice 每降 1 权重约 +10%）
2. vruntime = 实际运行时间 × (基准权重 / 进程权重)
3. 红黑树按 vruntime 排序，调度器总选 vruntime 最小（最「吃亏」）的进程
4. 进程上 CPU 后 vruntime 增长，逐渐让位给其他进程
```

nice 值和权重的映射是一张内核内置表（对应内核 `sched_prio_to_weight[]`）：nice=0 权重 1024，nice=1 约 820，nice=-1 约 1277，相邻 nice 的权重比约 1.25 倍（即「nice 差一级，权重差约 25%」的精确说法——常见教材写 10% 是旧经验值，内核实际约 1.25）。权重只在「竞争」时起作用：两个进程权重 1024 和 820，同时要 CPU 时按 1024:820 的比例分时间片；只有一个进程在跑时，它独占整核，权重无意义。

```text
nice → 权重（内核近似值，基准 1024）：
nice=-1 → 1277 | nice=0 → 1024 | nice=1 → 820 | nice=5 → 335 | nice=10 → 110 | nice=19 → 15
规律：nice 每降 1 级，权重约 ×1.25，对应能多分到的 CPU 份额
```

cgroups 的 CPU 限制原理则是「带宽控制」：CFS 之上再套一层配额，`cpu.max` 规定每个周期（默认 100ms）内该组进程最多能占用的 CPU 时间，超了就强制节流（throttle，进程被暂停到下一个周期）。这跟 nice 的「权重分配」是两套机制：nice 决定「竞争时怎么分」，cgroup 决定「总量最多用多少」。`/sys/fs/cgroup/cpu.stat` 里能看到 throttled 计数，判断是否触发了节流。

```text
nice（权重分配）vs cgroup（带宽上限）：
nice   —— 争抢时按权重分，空闲时都能跑满，无硬上限
cgroup —— 周期内最多用 cpu.max 规定的时长，超了节流，是硬上限
```

## 常用命令与配置

```shell
nice -n 10 命令          # 启动时降优先级（-20~19）
renice -n 5 -p PID       # 修改运行中进程优先级
renice -n 5 -u alice     # 修改某用户所有进程
ps -eo pid,ni,comm       # 查看 nice 值
ps -eo pid,ni,pri,comm   # 同时看 nice 和调度优先级 pri
top                      # top 里 NI 列就是 nice 值
chrt -p PID              # 查看调度策略
chrt -m                  # 查看支持的调度策略和优先级范围
```

```shell
# 临时给一条命令限 CPU/优先级，不写单元文件（systemd-run 起临时 unit）
systemd-run --scope -p CPUQuota=50% ./heavy_task.sh   # 最多 0.5 核
systemd-run --scope -p Nice=19 ./backup.sh            # 临时降优先级跑
```

```text
nice 值记忆：越小优先级越高，-20 最高、19 最低、默认 0
普通用户只能降优先级（nice 变大），升优先级（nice 变小）要 root
```

## 配置文件解析

优先级相关的配置分散在几处：

```text
# /etc/security/limits.conf —— 限制用户能用的优先级/资源
*    soft    priority    0      # 允许用户把 nice 调到的最低值（负数为升优先级）
*    hard    priority    -10

# systemd 服务单元 —— 服务级 CPU 限制
[Service]
CPUQuota=200%          # CPU 配额（200% = 2 核）
CPUWeight=500          # 权重（默认 100，越大分得越多）
Nice=5                 # 服务的 nice 值
```

```text
cgroup v2 对应文件（/sys/fs/cgroup/）：
cpu.max        "200000 100000" 形式 = 每 100ms 周期里最多用 200ms（2 核）
cpu.weight     权重值，组间按比例分配
cpu.stat       配额/节流统计（nr_throttled 看是否触发节流）
```

```text
systemd 属性 → cgroup 文件映射：
CPUQuota=200%   → cpu.max = "200000 100000"
CPUWeight=500   → cpu.weight = 500
Nice=5          → 启动进程时传 nice 值
```

systemd 的属性可以用 `systemctl set-property <服务> <属性>=<值>` 运行时改（写入 /run/systemd 的 drop-in），也可以直接写在服务单元文件 `[Service]` 段里持久化。Docker 的 `--cpus` 等价于写 cpu.max，`--cpu-shares` 等价于 cpu.weight，`--cpuset-cpus` 等价于 cpuset.cpus（绑定具体核）。

```text
cgroup v1 vs v2（排查前先确认是哪个版本，路径不同）：
cgroup v2（现代发行版默认）—— 统一挂载 /sys/fs/cgroup/，CPU 控制器文件是 cpu.max / cpu.weight
cgroup v1（老发行版/部分容器运行时）—— 每控制器单独挂载，CPU 路径是
  /sys/fs/cgroup/cpu,cpuacct/ 下的 cpu.cfs_quota_us（配额，微秒）、cpu.cfs_period_us（周期，微秒）、cpu.shares（权重）
判断方法：cat /proc/<pid>/cgroup 看进程归属，或 mount | grep cgroup 看挂载方式
```

## 应用场景实战

### 场景一：批量备份任务降优先级，别影响线上服务

```shell
# 备份是重 IO/CPU 任务，降优先级避免抢线上服务的 CPU
nice -n 19 tar czf /backup/data.tar.gz /data
# 或对已运行的备份进程降级
renice -n 19 -p $(pgrep -f 'tar.*backup')
# 确认 nice 值已生效
ps -o pid,ni,comm -p $(pgrep -f 'tar.*backup')
```

### 场景二：用 cgroups 限制某个服务别吃满 CPU

```shell
# 1. 限制服务最多用 1 个核
systemctl set-property myapp.service CPUQuota=100%
# 2. 验证生效
systemctl show myapp.service -p CPUQuotaPerSecUSec
# 3. 压测确认 CPU 不超限
top -p $(pgrep -f myapp)
```

### 场景三：手动用 cgroup v2 限制一组进程的 CPU

```shell
# 1. 建一个 cgroup 并设配额（1 核 = 100%）
mkdir -p /sys/fs/cgroup/limitcpu
echo "100000 100000" > /sys/fs/cgroup/limitcpu/cpu.max
# 2. 把目标进程的 PID 写进去，让它们受该组限制
echo <PID> > /sys/fs/cgroup/limitcpu/cgroup.procs
# 3. 用 dd 压测，对比限制前后的 CPU 占用
#    限制前：dd if=/dev/zero of=/dev/null 能吃到接近 100% 单核
#    限制后：同一进程被节流，top 看 CPU 明显下降
# 4. 用完删除 cgroup
echo <PID> > /sys/fs/cgroup/cgroup.procs   # 先把进程移回根组
rmdir /sys/fs/cgroup/limitcpu
```

## 性能与调优

```text
1. 批量任务（备份/压缩/重建索引）统一 nice 19，别和线上服务抢 CPU
2. 关键服务用 cgroups CPUQuota 设硬上限，防止单个服务吃满拖垮整机
3. 多租户/容器环境用 cgroup 隔离，比 nice 更可控（nice 只是建议）
4. 别轻易用 chrt 设实时调度策略——实时进程会饿死普通进程，导致系统卡死
5. 观察 top 的 %CPU 和 load，确认优先级调整是否生效
6. CPU 敏感型服务和 IO 型服务区分对待——IO 型调优先级意义不大，瓶颈在磁盘不在 CPU
```

```text
优先级手段选型速查：
「批量备份/重建索引别拖累线上」 → nice 19（进程级建议，够用）
「多租户/容器隔离、保证不超配」 → cgroup CPUQuota / docker --cpus（硬上限）
「服务权重倾斜、高峰期谁先让步」 → cgroup cpu.weight / docker --cpu-shares（按比例）
「某进程要绝对实时（音视频/控制）」 → chrt 实时策略（慎用，需 root + 核心隔离）
「关键服务临时提优先级」 → renice -n -5 -p PID（需 root）
```

## 安全与权限

```text
1. 普通用户只能降优先级 —— renice 提优先级（nice 变小）要 root，防止抢占
2. chrt 设实时策略需 root 或 CAP_SYS_NICE —— 实时进程能饿死系统，权限收口
3. cgroup 限制也要权限 —— 改 systemd 属性/容器配额通常需 root
4. 别给不可信进程提优先级 —— 高优先级进程可能抢占关键服务
5. limits.conf 的 priority 可限制用户能降到的 nice 下限 —— 防止普通用户用 nice 抢占
```

## 故障排查

### nice 调整了但不生效

```shell
# 1. 确认 nice 值是否真的改了
ps -eo pid,ni,comm | grep <PID>
# 2. 确认 CPU 是否空闲（空闲时低优先级进程照样跑满，属正常）
top
# 3. 要硬限制换 cgroups（nice 只是权重建议，不是上限）
systemctl set-property <服务> CPUQuota=100%
```

### 进程优先级异常高 / 系统卡顿

```shell
# 1. 找是否有实时策略进程（SCHED_FIFO/RR 优先级高于一切）
ps -eo pid,stat,cls,comm | grep -E 'FF|RR'
# 2. 查看它的调度策略
chrt -p <PID>
# 3. 是误设就改回普通策略
chrt -o -p 0 <PID>
```

### cgroup 设置了配额但 CPU 还是超标

```shell
# 1. 确认进程真的在目标 cgroup 里
cat /proc/<PID>/cgroup
# 2. 看 cpu.max 是否写对（"MAX PERIOD" 两段）
cat /sys/fs/cgroup/<组>/cpu.max
# 3. 看节流统计，确认是否真的触发过 throttle
cat /sys/fs/cgroup/<组>/cpu.stat | grep throttled
# 4. systemd 服务确认属性是否挂到对应 service 上
systemctl show <服务> -p CPUQuotaPerSecUSec -p ControlGroup
```

### 确认优先级/配额调整是否真正生效

```shell
# 1. 一次性看 nice + 调度优先级 + 调度类别
ps -o pid,ni,pri,cls,comm -p <PID>
# 2. 看调度策略详情
chrt -p <PID>
# 3. 看进程归属哪个 cgroup（限制作用在哪个组）
cat /proc/<PID>/cgroup
# 4. 看该组的 CPU 配额（v2 路径，v1 看 cpu.cfs_quota_us）
cat /sys/fs/cgroup/system.slice/<服务>.service/cpu.max 2>/dev/null
```

## 常见问题

```text
Q1: nice 值越大优先级越高吗？
A: 反了。nice 是「谦让度」，越大越谦让、优先级越低。-20 最高，19 最低，默认 0。

Q2: nice 和 cgroups 限制 CPU 有什么区别？
A: nice 是权重建议（CPU 空闲时低优先级也跑满），cgroups 是硬上限（最多用多少）。要硬限制用 cgroups。

Q3: 为什么普通用户不能给进程提优先级？
A: 防止用户抢占其他用户的 CPU。提优先级（nice 变小）需要 root，降优先级（nice 变大）谁都可以。

Q4: CPU 空闲时，nice 19 的进程会占满 CPU 吗？
A: 会。nice 只影响「竞争时的分配比例」，CPU 空闲没有竞争者，低优先级进程照样跑满。

Q5: nice 值和 top 里 PR 列什么关系？
A: PR 是内核换算后的实际调度优先级，普通进程 PR ≈ 20 + nice（nice 0 → PR 20，nice -20 → PR 0）。看 nice 用 NI 列，看实际调度优先级用 PR 列。

Q6: SCHED_FIFO 和 SCHED_RR 有什么区别？
A: 都是实时策略、优先级高于普通进程。FIFO 是同一优先级先来先服务、跑完或阻塞才让出；RR 是同一优先级轮转、每个进程跑固定时间片轮流。实时策略需 root，生产慎用。

Q7: Docker 的 --cpus 和 --cpu-shares 有什么区别？
A: --cpus 是硬上限（对应 cgroup cpu.max，最多用多少核）；--cpu-shares 是权重（对应 cpu.weight，竞争时按比例分）。一个是「封顶」，一个是「抢份额」。

Q8: SCHED_BATCH 和 SCHED_IDLE 有什么用？
A: SCHED_BATCH 面向批处理任务，减少抢占频率、适合后台跑批；SCHED_IDLE 是「系统完全空闲才跑」、优先级最低，适合完全不着急的后台任务。用 chrt -b / chrt -i 设置，两者都比普通 nice 更能「让路」。
```

## 面试题

```text
1. CFS 调度器的核心思想？
   答：按 vruntime（虚拟运行时间）公平分配 CPU。nice 值影响权重，权重高 vruntime 增长慢，分到更多 CPU。总选 vruntime 最小的进程调度。

2. nice 值 -20 和 19 分别代表什么？
   答：-20 最高优先级，19 最低优先级，默认 0。nice 每降 1 级权重约增 10%。

3. 怎么限制一个服务最多用 1 核 CPU？
   答：systemctl set-property 服务 CPUQuota=100%，或 Docker --cpus 1。底层都是 cgroups cpu.max。

4. 实时进程和普通进程调度有什么区别？
   答：实时进程（SCHED_FIFO/RR）优先级高于一切普通进程，会饿死普通进程，需 root 设置，生产慎用。

5. nice 和 cgroups 的 CPU 限制本质区别？
   答：nice 是调度器内的权重建议，只在竞争时影响分配比例、无硬上限；cgroups 是带宽控制硬上限，超过配额直接节流。要保证「最多用多少」用 cgroups。

6. 为什么普通用户不能 renice 提优先级？
   答：防止普通用户抢占其他用户或系统的 CPU。降优先级（nice 变大）谁都可以，升优先级（nice 变小）需要 root 或 CAP_SYS_NICE 能力。

7. 进程为什么会被「节流」（throttle）？
   答：cgroup 的 cpu.max 规定了周期内的 CPU 配额，进程组在周期内用完配额就被节流（暂停），等下一个周期再继续，/sys/fs/cgroup/cpu.stat 的 nr_throttled 能看到节流次数。
```

## 最佳实践与踩坑记录

### 最佳实践

1. 批量任务（备份/日志压缩）用 nice 降优先级，别和线上抢 CPU
2. 普通用户只能降优先级（调高 nice），升优先级要 root
3. 硬性限制 CPU 用 cgroups（systemd CPUQuota / docker --cpus），nice 只是建议
4. 数据库/关键服务别乱动 nice，默认 0 即可，用 cgroups 隔离更可控
5. 实时调度策略（chrt）慎用，配错会让系统卡死
6. 多租户/容器环境统一用 cgroup 做 CPU 隔离，nice 只做进程级微调
7. 调完优先级用 ps -eo pid,ni,comm 或 top 的 NI 列验证生效

### 踩坑记录

```text
坑 1：普通用户 renice 提优先级报 Operation not permitted
结论：renice -n -5 报权限不足。
原因：只有 root 能提升优先级（降 nice 值），普通用户只能降优先级。
解法：提优先级用 sudo，或接受只能降不能升的限制。

坑 2：nice 调了但 CPU 还是被抢
结论：nice 19 的进程还是占了不少 CPU。
原因：nice 只是「建议权重」，CPU 空闲时低优先级进程照样跑满。
解法：要硬限制用 cgroups（CPUQuota/--cpus），nice 做不到硬上限。

坑 3：chrt 设实时策略导致系统卡死
结论：进程设 SCHED_FIFO 实时策略，整个系统响应迟钝。
原因：实时进程优先级高于一切，跑死循环会饿死其他进程。
解法：别轻易用 chrt 设实时策略，确需也设 CPU 亲和性隔离核心。

坑 4：cgroups 配了 CPUQuota 不生效
结论：systemctl set-property 设了 CPUQuota，服务还是跑满。
原因：改了没 reload/restart 服务，或没配 CPUAccounting。
解法：确认 CPUAccounting=yes，重启服务后再验证。

坑 5：把 nice 值理解成「越大优先级越高」
结论：nice 19 的进程反而更慢，和直觉相反。
原因：nice 值语义是「谦让度」，越大越谦让、优先级越低。
解法：记「nice 越小优先级越高，-20 最高，19 最低」。

坑 6：CPUQuota 设了 100% 以为「单个进程 100%」，实际是「整组共享 1 核」
结论：服务里多线程/多进程，设 CPUQuota=100% 后整组加起来才 1 核，单进程远低于 100%。
原因：cgroup 配额是组级，组内所有进程共享，不是每个进程各 1 核。
解法：按「整组需要的总核数」设配额，不是按单进程设。

坑 7：容器里 --cpus 设了但负载还是高
结论：容器 --cpus 1 后宿主 load 仍高，怀疑限制没生效。
原因：--cpus 限制的是 CPU 使用上限，不等同于降低就绪队列里的任务数，IO 等待等也会拉高 load；且要确认容器运行时用的 cgroup 版本。
解法：top 看容器进程实际 %CPU 是否被封顶，load 高另查 IO/排队，别只看 load。
```
