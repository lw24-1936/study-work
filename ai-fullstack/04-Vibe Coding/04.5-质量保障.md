## 概述

AI 写代码的速度远快于人类审查的速度，这个剪刀差就是质量风险的全部来源。质量保障和传统写码的目标相同，但有两个关键差异：**必须把门槛前移到提交之前**（因为 AI 可以一天产出几十个提交），以及**必须专门检查 AI 特有的缺陷模式**（编译通过但逻辑近似、测试全绿但断言为空、依赖突然多出三个）。可行的做法是三道闸门：格式化与静态检查（机器兜底风格）、测试与变异冒烟（行为兜底）、人工审查（语义兜底）。

```text
三道闸门，从便宜到昂贵：
1. 格式化 + 静态检查 —— 秒级，消灭风格与常见错误，机器判定
2. 类型检查 + 测试 + 变异冒烟 —— 分钟级，验证行为而不是验证代码长相
3. 人工审查 —— 只聚焦语义：边界条件、并发、错误处理、安全与数据一致性
```

## 测试先行在 AI 协作中的可行性

结论：可行，而且是 AI 协作中收益最大的实践。原因在于角色可以互换——**测试由人或由 AI 先写，实现由 AI 写，但两者必须由不同轮次产生**。如果让同一次生成同时产出实现和测试，模型会让测试迁就实现（甚至写出永远为真的断言）。所以正确顺序是：先固定测试（作为约束），再让实现去满足它。

```python
# tests/test_pagination.py：先写测试，覆盖边界（空页、越界、正好整除、不整除）
import pytest

from src.api.pagination import paginate


def test_first_page():
    assert paginate(list(range(100)), page=1, size=10) == list(range(10))


def test_last_page_partial():
    # 100 条、每页 30 条：最后一页只有 10 条
    assert paginate(list(range(100)), page=4, size=30) == list(range(90, 100))


def test_out_of_range_returns_empty():
    assert paginate(list(range(100)), page=99, size=10) == []


def test_size_must_be_positive():
    with pytest.raises(ValueError):
        paginate([1, 2, 3], page=1, size=0)
```

模型「迁就实现」的典型表现，以及为什么必须禁止：

```python
# 反例：AI 同轮生成的测试，断言与实现同构，等于没测
def test_paginate_tautology():
    items = list(range(100))
    result = paginate(items, page=1, size=10)
    assert result == items[0:10]       # 复刻了实现逻辑，实现错了它也错

# 正例：断言用独立计算或写死的期望值
def test_paginate_independent():
    items = list(range(100))
    assert paginate(items, page=4, size=30) == [90, 91, 92, 93, 94, 95, 96, 97, 98, 99]
```

```shell
# 骨架先红，实现后绿：这是测试先行有效的判据

codex exec "实现 src/api/pagination.py，让 tests/test_pagination.py 全绿。
不要修改测试文件，不要新增依赖。"

pytest tests/test_pagination.py -q          # 期望：4 passed
```

## 自动格式化与静态检查

格式化的意义在于把「风格争论」从人工评审里彻底移除。只要格式化器是确定性的，就不该有人再评论缩进与引号。Python 侧主流是 ruff（同时做格式化与 lint，速度快，可替代 flake8/isort/black 的大部分场景）；JavaScript / TypeScript 侧是 prettier 加 eslint，注意 ESLint 9 起默认使用扁平配置 `eslint.config.js`，旧版 `.eslintrc.*` 仍受支持，具体以官方文档为准。CI 里必须用 `--check` 模式，让不一致直接失败，而不是自动改写后静默提交。

```toml

line-length = 100
target-version = "py311"

[tool.ruff.lint]
# E/W 风格、F 逻辑错误、I 导入排序、B bugbear 常见陷阱、S 安全、UP 语法升级
select = ["E", "W", "F", "I", "B", "S", "UP"]
ignore = ["S101"]          # 允许 assert（测试文件常用）

[tool.ruff.lint.per-file-ignores]
"tests/*" = ["S105", "S106"]   # 测试里允许假密码常量
```

## AI 代码的常见缺陷

模型生成的代码有一些高频缺陷模式，知道清单就能定向检查。最常见的五类是：**测试无断言或断言同构**（绿得很安心，什么都没测）、**静默吞异常**（`except Exception: pass`）、**边界近似**（分页差一、时区没处理、空集合没考虑）、**硬编码臆造的 API**（方法名看起来对但库里没有）、**性能陷阱**（循环里查库、一次性加载全表）。这些缺陷编译器和类型检查都抓不到，必须靠测试设计与人工审查。

```text
高频缺陷清单（审查时逐条对照）：
1. 测试：无 assert、断言复刻实现、只测 happy path、mock 掉被测对象本身
2. 错误处理：except: pass、把异常转成 None 让问题静默、日志里没有上下文
3. 边界：分页越界、空列表/None、时区、浮点比较、并发下的 TOCTOU
4. 幻觉 API：不存在的库方法、参数名写错、臆造的配置字段
5. 性能：N+1 查询、循环内 IO、全量加载后内存过滤、缺少索引的查询
6. 安全：拼接 SQL、日志打印敏感字段、硬编码密钥、宽松的 CORS
```

把「测试是否真的有效」变成可执行检查：先扫出没有断言的测试，再做一次变异冒烟（故意改坏实现，看测试会不会失败）。

```python
# test_quality_scan.py：扫描测试文件里没有断言函数的测试用例
# 用法：python3 test_quality_scan.py tests/
import ast
import sys
from pathlib import Path


def tests_without_assert(path: Path):
    tree = ast.parse(path.read_text(encoding="utf-8"))
    for node in ast.walk(tree):
        if not isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
            continue
        if not node.name.startswith("test_"):
            continue
        has_assert = any(isinstance(n, ast.Assert) for n in ast.walk(node))
        # pytest.raises / pytest.fail 等也算有效断言
        calls = [n for n in ast.walk(node) if isinstance(n, ast.Call)]
        has_expect = any(
            "raises" in ast.unparse(c.func) or "fail" in ast.unparse(c.func)
            for c in calls
        )
        if not has_assert and not has_expect:
            yield node.name, node.lineno


def main():
    root = Path(sys.argv[1] if len(sys.argv) > 1 else "tests")
    bad = 0
    for path in sorted(root.rglob("test_*.py")):
        for name, lineno in tests_without_assert(path):
            print(f"{path}:{lineno} 无断言测试: {name}")
            bad += 1
    print(f"共发现 {bad} 个无断言测试")
    sys.exit(1 if bad else 0)


if __name__ == "__main__":
    main()
```

```python
# mutation_smoke.py：变异冒烟——把实现改坏，看测试是否失败
# 用法：python3 mutation_smoke.py src/api/pagination.py tests/test_pagination.py
import pathlib
import re
import subprocess
import sys

MUTATIONS = [
    (r">= *0", "> 0"),          # 边界比较翻转
    (r"\+ 1", "+ 2"),           # 差一错误
    (r"return \[\]", "return None"),
]


def run_tests(test_file: str) -> bool:
    r = subprocess.run(
        [sys.executable, "-m", "pytest", test_file, "-q"], capture_output=True, text=True
    )
    return r.returncode == 0


def main():
    src, test = pathlib.Path(sys.argv[1]), sys.argv[2]
    original = src.read_text(encoding="utf-8")

    if not run_tests(test):
        print("基线测试未通过，先修测试")
        return 1

    killed = 0
    try:
        for pattern, repl in MUTATIONS:
            mutated, n = re.subn(pattern, repl, original)
            if n == 0:
                print(f"skip  未命中模式 {pattern}")
                continue
            src.write_text(mutated, encoding="utf-8")
            survived = run_tests(test)
            print(f"{'SURVIVED' if survived else 'KILLED  '} {pattern} -> {repl}")
            if survived:
                print("  测试未能发现该变异，怀疑断言不足")
            else:
                killed += 1
    finally:
        src.write_text(original, encoding="utf-8")   # 无论成败都还原

    print(f"killed={killed}")
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

```shell
python3 test_quality_scan.py tests/
python3 mutation_smoke.py src/api/pagination.py tests/test_pagination.py
# KILLED   >= 0 -> > 0
# KILLED   \+ 1 -> + 2
# SURVIVED return \[\] -> return None     <- 说明越界用例断言不足，需要补测
```

## 依赖与版本核对

AI 最容易在两个地方引入风险：一是**顺手新增依赖**（你说「加个日期格式化」它给你装一个包），二是**臆造版本号与 API**。核对动作分三步：检查 lockfile 是否被动过、检查新依赖的出处与体积、检查生成的代码是否用了该依赖真实存在的 API。Python 侧用 `pip-audit` 或 `osv-scanner` 扫已知漏洞，Node 侧用 `npm audit`，注意 `npm audit` 只覆盖有 CVE 编号的问题，对刚发布的恶意包无能为力。

```shell
# 1) 依赖是否被意外改动（AI 擅自加包最常见的信号）
git diff --stat HEAD -- package.json pnpm-lock.yaml requirements.txt uv.lock pyproject.toml

# 2) 新依赖的来源与元信息（维护者、发布时间、是否有安装脚本）
npm view some-package name version maintainers time.modified
npm view some-package scripts     # 有 postinstall 就要提高警惕
pip index versions some-package --index-url https://pypi.tuna.tsinghua.edu.cn/simple

# 3) 漏洞扫描
npm audit --audit-level=high
pip install pip-audit --index-url https://pypi.tuna.tsinghua.edu.cn/simple
pip-audit -r requirements.txt
osv-scanner scan source -r .       # 需先安装 osv-scanner

# 4) 锁文件一致性（CI 里必跑，失败即拒绝提交）
npm ci                            # 与 package.json 不一致会直接失败
uv lock --check                   # Python（uv）
poetry check --lock               # Python（Poetry）
```

## 代码审查要点

AI 产出的 PR 审查要换一套关注点：不再纠结命名与缩进（机器已管），而是聚焦语义与风险。经验做法是给 PR 模板加一个「AI 参与度」区块，让作者显式声明哪些代码由 AI 生成、验证方式是什么，评审者据此决定抽查深度。审查清单可以做成模板，直接贴进仓库。

```markdown
<!-- .github/PULL_REQUEST_TEMPLATE.md -->
## 本次改动

- 一句话说明：
- AI 参与度：全部由 AI 生成 / AI 起草 + 人工修改 / 人工手写
- 基线提交：

## 验证（必须贴真实输出，不要写"已测试"）

- [ ] 单元测试通过（粘贴 pytest / vitest 摘要）
- [ ] 类型检查通过
- [ ] 静态检查零新增告警
- [ ] 变异冒烟：至少杀死 1 个变异（可选，高风险模块必做）

## 评审重点

- [ ] 错误处理：没有 `except: pass` 式静默吞噬
- [ ] 边界：空值、越界、并发、时区已考虑
- [ ] 依赖：没有未申报的新依赖
- [ ] 安全：无密钥、无字符串拼接 SQL、日志不含敏感字段
- [ ] 测试：断言不是实现逻辑的复刻
```

## 应用场景实战

### 场景一：给一个 Python 服务搭起完整的质量门禁

需求：一个 FastAPI 服务，团队三人，AI 参与度高，要求「任何 AI 产出的代码在合并前必须过四道检查」。方案：ruff（格式+lint）+ mypy（类型）+ pytest（测试+覆盖率）+ 变异冒烟（高风险模块），全部装进 pre-commit 与 CI。

```yaml
# .github/workflows/quality.yml
name: Quality
on: [push, pull_request]

jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: 安装依赖（锁定版本 + 国内镜像）
        run: |
          pip install -r requirements.txt --index-url https://pypi.tuna.tsinghua.edu.cn/simple
          pip install ruff mypy pytest pytest-cov pip-audit \
            --index-url https://pypi.tuna.tsinghua.edu.cn/simple

      - name: 格式化检查
        run: ruff format --check .

      - name: 静态检查
        run: ruff check .

      - name: 类型检查
        run: mypy src

      - name: 测试与覆盖率门槛
        run: pytest --cov=src --cov-fail-under=85 -q

      - name: 依赖漏洞扫描
        run: pip-audit -r requirements.txt

      - name: 无断言测试扫描
        run: python3 scripts/test_quality_scan.py tests/
```

```ini
# pytest.ini：把覆盖率门槛写进配置，本地与 CI 一致
[pytest]
addopts = -q --cov=src --cov-report=term-missing --cov-fail-under=85
testpaths = tests
```

```shell
# 本地复现 CI 的每一步（失败顺序与 CI 一致，便于定位）
ruff format --check . && ruff check . && mypy src \
  && pytest -q && pip-audit -r requirements.txt \
  && python3 scripts/test_quality_scan.py tests/
```

### 场景二：审查一段 AI 产出的高风险代码，逐条落地检查项

需求：AI 生成了一段「账户余额扣减」代码，涉及资金，必须逐行审查。

```python
# 待审查代码（AI 产出）——请先自己找问题再看下面的清单
async def deduct(account_id: str, amount: float) -> bool:
    acct = await db.fetch_one("SELECT balance FROM accounts WHERE id = %s", (account_id,))
    if acct is None:
        return False
    if acct["balance"] >= amount:
        await db.execute(
            "UPDATE accounts SET balance = balance - %s WHERE id = %s", (amount, account_id)
        )
        return True
    return False
```

```text
# 逐条对照（这段代码至少 5 个问题）

1. 并发安全（阻断级）
   结论：读余额与写余额之间没有事务与锁，两个并发请求可同时通过检查。
   正确做法：单条原子 SQL + 余额约束
     UPDATE accounts SET balance = balance - %s
     WHERE id = %s AND balance >= %s
   然后按受影响行数判断结果。

2. 金额类型（阻断级）
   结论：用 float 表示金额会带来精度误差。
   正确做法：整数分（int）或 Decimal，库里用 NUMERIC。

3. 静默失败（建议级）
   结论：返回 bool，调用方无法区分「账户不存在」与「余额不足」。
   正确做法：返回明确的结果枚举或抛领域异常。

4. 幂等性（阻断级）
   结论：重复调用会重复扣款，没有 request id / 幂等键。
   正确做法：以 idempotency key 建唯一索引，重复请求返回首次结果。

5. 可观测性（建议级）
   结论：失败路径没有任何日志，线上无法定位。
   正确做法：记录 account_id、amount、结果与 request_id（注意脱敏）。
```

-- 修正后的原子扣减 + 余额非负约束（PostgreSQL）
BEGIN;

UPDATE accounts
   SET balance = balance - :amount_cents
 WHERE id = :account_id
   AND balance >= :amount_cents;      -- 条件不满足则影响 0 行，天然防超扣

-- 应用层按受影响行数判断：0 行表示余额不足或账户不存在
-- 迁移里再加一道硬约束，防止任何路径写出负余额
ALTER TABLE accounts ADD CONSTRAINT balance_non_negative CHECK (balance >= 0);

COMMIT;

## 最佳实践与踩坑记录

### 最佳实践

1. 测试与实现分轮次产出：先固定测试作为约束，再让 AI 实现，禁止同轮生成后又让测试迁就实现
2. 格式化与 lint 必须跑 `--check` 模式进 CI，本地用 pre-commit 自动修，团队零争论
3. 对高风险模块做变异冒烟：杀死不了变异的测试等于没有测试
4. 依赖新增必须写理由（为什么标准库不行），并用锁文件一致性检查卡住擅自加包
5. PR 模板强制填写「AI 参与度 + 真实验证输出 + 评审重点」，评审聚焦语义而不是风格
6. 用工具扫描无断言的测试用例，把「测试全绿」的可信度量化
7. 覆盖率门槛写进配置文件（如 `--cov-fail-under=85`），不要把门槛留在人脑里

### 踩坑记录

```text
坑 1：实现和测试同一轮产出，测试永远为真
结论：CI 全绿上线后仍出故障，回溯发现测试没有任何有效断言。
原因：模型为了让结果"通过"，会让测试迁就实现，甚至写出恒真断言。
解法：测试先行且由独立轮次产生；用 AST 扫描 + 变异冒烟验证测试有效性。

坑 2：CI 里跑 ruff format（自动改写）而不是 --check
结论：流水线把未格式化的代码静默修好并提交，评审者看到的是格式化后的 diff。
原因：命令写错，把本地修复命令放进了 CI。
解法：CI 一律 --check，本地才允许 --fix / --write。

坑 3：AI 顺手新增依赖且未申报
结论：锁文件多出三个传递依赖，其中一个有安装脚本，安全评审被卡。
原因：模型优先满足功能，不关心依赖治理成本。
解法：CI 检查 package.json / requirements.txt 是否与基线一致，新增依赖必须走申请模板。

坑 4：只看"测试通过"就合并高风险改动
结论：金额扣减在并发下超扣，事后对账才发现。
原因：测试只覆盖了单线程 happy path，AI 不知道业务侧并发约束。
解法：资金类改动强制人工设计 + 并发测试 + 数据库约束双保险。

坑 5：把覆盖率当成质量指标，为了达标写空测试
结论：覆盖率 90%，缺陷率没有下降。
原因：覆盖率只说明执行过，不说明断言有效。
解法：覆盖率作为下限门槛，配合变异冒烟与审查清单使用，不单独作为质量结论。

坑 6：依赖扫描只看 npm audit，漏掉刚发布的恶意包
结论：一个刚发布两天、尚无 CVE 的包带着 postinstall 脚本进了仓库。
原因：npm audit 依赖 CVE 数据库，对新攻击没有覆盖。
解法：结合安装脚本检查、发布时间检查与行为分析类工具，并尽量走 allowlist。
```
