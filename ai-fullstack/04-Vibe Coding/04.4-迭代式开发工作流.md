## 概述

AI 编码的效率来自「快速试错」，但试错的前提是**能立刻回退、能立刻验证**。所以迭代式工作流的三个支点是：骨架先定接口、小步提交配即时验证、失败能干净回退。没有这三样，AI 的高速产出会变成不可逆的混乱：改动叠改动，谁也不知道哪一步引入了问题。

```text
工作流的四个动作，循环执行：
1. 定骨架 —— 先写接口/签名/测试，把「做完的样子」固定下来
2. 小步做 —— 一次一个可验证变更，AI 执行，人看结果
3. 立即验 —— 同一套命令跑一遍，绿了才提交
4. 干净退 —— 不对就整体回退，不要在错误基础上叠加修补
```

## 从骨架到实现

人写骨架、AI 填实现，是分工效率最高的一种方式。原因很简单：骨架是**接口与约束**，属于人类的判断力范围；实现是**在约束内写代码**，属于模型的强项。骨架包含四样东西：接口签名、数据契约、错误语义、以及一份现在必然失败、做完必然通过的测试。这份失败的测试非常关键——它是整个迭代循环的验收信号。

```python
# src/orders/service.py：人类写的骨架，函数体一律 raise NotImplementedError
from dataclasses import dataclass
from decimal import Decimal
from typing import Protocol


class OrderRepo(Protocol):
    def get(self, order_id: str) -> "Order | None": ...
    def save(self, order: "Order") -> None: ...


@dataclass
class Order:
    id: str
    status: str          # CREATED / PAID / SHIPPED / CANCELLED
    amount: Decimal


class OrderService:
    """取消订单的领域服务。骨架由人写，实现交给 AI。"""

    def __init__(self, repo: OrderRepo) -> None:
        self._repo = repo

    def cancel(self, order_id: str) -> Order:
        # 验收要求：不存在 -> OrderNotFound；已发货 -> IllegalState
        raise NotImplementedError

    def cancel_idempotent(self, order_id: str) -> Order:
        # 验收要求：重复取消返回同一结果，不报错、不重复写审计
        raise NotImplementedError
```

```python
# tests/test_order_service.py：先写测试，此时必然失败（红）
import pytest

from src.orders.service import IllegalState, OrderNotFound, OrderService


class FakeRepo:
    def __init__(self, order):
        self._order = order
        self.saved = []

    def get(self, order_id):
        return self._order if self._order and self._order.id == order_id else None

    def save(self, order):
        self.saved.append(order)


def make_order(status="CREATED"):
    from decimal import Decimal

    from src.orders.service import Order

    return Order(id="o1", status=status, amount=Decimal("10.00"))


def test_cancel_created():
    repo = FakeRepo(make_order("CREATED"))
    out = OrderService(repo).cancel("o1")
    assert out.status == "CANCELLED"


def test_cancel_shipped_rejected():
    repo = FakeRepo(make_order("SHIPPED"))
    with pytest.raises(IllegalState):
        OrderService(repo).cancel("o1")


def test_cancel_missing_raises():
    with pytest.raises(OrderNotFound):
        OrderService(FakeRepo(None)).cancel("nope")


def test_cancel_is_idempotent():
    repo = FakeRepo(make_order("CREATED"))
    svc = OrderService(repo)
    assert svc.cancel_idempotent("o1").status == "CANCELLED"
    assert svc.cancel_idempotent("o1").status == "CANCELLED"
    assert len(repo.saved) == 1     # 只落库一次
```


## 小步提交与即时验证

「小步」的判据不是行数，而是**能否用一个信号判断对错**。一个提交只做一件事：加一个接口、修一个缺陷、重构一个函数。这样做的收益在出问题时才显现：`git bisect` 能快速定位，`git revert` 能精准回滚，评审能看清意图。AI 协作场景下这一点尤其重要，因为一次 AI 产出往往是几百行，混在同一个提交里就没法拆。

```shell
# 提交前必跑的固定检查（把命令写死，避免凭记忆）
pnpm typecheck && pnpm lint && pnpm test -- --run

# 查看本次改动规模，超过 8 个文件要先怀疑粒度
git diff --stat
git diff --name-only | wc -l

# 分块提交：只挑这次任务相关的文件，避免把无关改动卷进来
git add src/domain/order.ts tests/test_order_service.py
git commit -m "feat(orders): 支持取消未发货订单

- Order 增加 cancel()，已发货抛 IllegalState
- cancel 幂等：重复调用不重复落库
- 单测覆盖 4 条路径"

# 查看提交历史，确认粒度合理
git log --oneline -10
```

用脚本自动检查「最近一次提交是否够小、信息是否规范」，把规范变成门禁。

```bash
#!/usr/bin/env bash
# commit_guard.sh：检查最近一次提交的粒度与信息格式
set -uo pipefail
fails=0

files=$(git show --pretty=tformat: --name-only HEAD | grep -c . || true)
lines=$(git show --pretty=tformat: --numstat HEAD | awk '{a+=$1; d+=$2} END {print a+d+0}')
msg=$(git log -1 --pretty=%s)

echo "files=$files changed_lines=$lines msg=$msg"

[ "$files" -le 12 ] || { echo "警告：单次提交文件数 $files 偏大，建议拆分"; fails=1; }
[ "$lines" -le 500 ] || { echo "警告：单次提交改动 $lines 行偏大，建议拆分"; fails=1; }

if echo "$msg" | grep -qE '^(feat|fix|docs|refactor|test|chore|perf|build|ci)(\(.+\))?: .+'; then
  echo "PASS 提交信息符合 Conventional Commits"
else
  echo "FAIL 提交信息不符合规范：$msg"
  fails=1
fi

exit "$fails"
```

```shell
chmod +x commit_guard.sh
./commit_guard.sh
# files=3 changed_lines=186 msg=feat(orders): 支持取消未发货订单
# PASS 提交信息符合 Conventional Commits
```

## 失败回退与重来

AI 协作里最需要养成的习惯是：**发现方向不对就整体回退，而不是在错误基础上打补丁**。原因有二：错误的实现会成为后续推理的上下文，把模型越带越偏；补丁式修补会让 diff 混入不相干的改动，评审时无法判断哪些是有效代码。回退的层次从粗到细有四种，按需选择，不要一上来就 `reset --hard`。

| 场景 | 命令 | 影响范围 |
| --- | --- | --- |
| 丢弃未提交改动（保留新增文件） | `git restore .` | 工作区 |
| 丢弃未提交改动（含新增文件） | `git clean -fd` + `git restore .` | 工作区 + 未跟踪文件 |
| 撤销最近一次提交但保留改动 | `git reset --soft HEAD~1` | 本地历史 |
| 撤销已推送的提交 | `git revert <sha>` | 生成反向提交，历史保留 |
| 找回归档点/误删分支 | `git reflog` + `git reset --hard <sha>` | 本地历史 |
| 并行试两种方案互不污染 | `git worktree add` | 独立目录 |

部分终端 Agent 还提供内置回退：OpenCode 的 `/undo` 与 `/redo` 会还原文件并恢复你的原始消息，便于改完提示词重试。内置回退方便，但**不要**把它当唯一的安全网——提交点的保护是工具无关的。

```shell
# 方案一失败，干净回退到上一次提交（先确认没有想保留的改动）
git status --short
git stash push -u -m "wip: 方案一，可能弃用"
git log --oneline -3

# 用 worktree 并行试两个方案，互不干扰
git worktree add ../proj-solution-a -b try/solution-a
git worktree add ../proj-solution-b -b try/solution-b
git worktree list

# 选定方案后清理另一个
git worktree remove ../proj-solution-b
git branch -D try/solution-b

# 误删提交的兜底：从 reflog 找回
git reflog -20
git reset --hard HEAD@{3}
```

```text
# 回退决策树
改动未提交？
  是 -> 想保留一部分？  git add -p 挑拣，其余 git restore .
                      不想保留  -> git restore . && git clean -fd
  否 -> 已提交未推送？
        是 -> git reset --soft HEAD~1（想改） / --hard（全丢）
        否 -> git revert <sha> 生成反向提交，不要重写公共历史
```

## 重构与增量改造

让 AI 做「重构」是高风险动作，因为它会顺手改行为。可行做法是**绞杀者模式 + 特征测试**：先用测试锁住现有行为（哪怕是丑陋的、包含 bug 的行为），再做小步替换，每步都跑测试。替换过程分三段：加新实现（旧代码不动）→ 让调用方切过去（一次一个调用点）→ 删除旧实现。任何一步测试变红就回退这一步，整体始终处于可运行状态。

```python
# tests/test_legacy_characterization.py：特征测试，锁住现状（含已知怪癖）
import pytest

from src.legacy.pricing import legacy_total


def test_legacy_free_shipping_threshold():
    # 现状：满 99 免运费，恰好 99 也免（浮点比较的边界行为要保留）
    assert legacy_total([99.0])["shipping"] == 0.0
    assert legacy_total([98.99])["shipping"] == 8.0


def test_legacy_rounds_half_up():
    # 现状：金额保留两位，四舍五入（不是银行家舍入），先锁住
    assert legacy_total([1.005])["total"] == 1.01


def test_legacy_empty_order_raises():
    with pytest.raises(ValueError):
        legacy_total([])
```

```python
# src/pricing/new.py：新实现，先与旧实现并行存在
def total(items: list[float]) -> dict:
    """与 legacy_total 行为等价的干净实现，浮点比较改用整数分。"""
    if not items:
        raise ValueError("empty order")
    cents = [round(i * 100) for i in items]
    sub = sum(cents)
    shipping = 0 if sub >= 9900 else 800
    return {"total": (sub + shipping) / 100, "shipping": shipping / 100}
```

```python
# tests/test_pricing_equivalence.py：等价性测试，两套实现随机对拍
import random

from src.legacy.pricing import legacy_total
from src.pricing.new import total


def test_equivalence_fuzz():
    random.seed(20261014)
    for _ in range(2000):
        items = [round(random.uniform(0.01, 200.0), 2) for _ in range(random.randint(1, 8))]
        assert legacy_total(items) == total(items), items
```

```shell
# 每次替换一个调用点，跑一次等价性测试
rg -n "legacy_total" src --type py
rg -l "legacy_total" src --type py | xargs -n1 -I{} echo "待改：{}"

pytest tests/test_legacy_characterization.py tests/test_pricing_equivalence.py -q
# 期望：全部通过，且每次只改一个调用点，提交一次
git commit -am "refactor(pricing): 订单入口改用新计价实现"
```

```text
# 增量改造的三条铁律
1. 先锁现状：特征测试写下来，允许它固化既有 bug，只求可观测
2. 新旧并行：新实现上线前，旧实现一行都不删
3. 一次一个调用点：每切一个就提交并跑测试，随时可以停
```

## 与版本控制配合

AI 协作把版本控制的作用从「存档」升级为「安全网」。三条最低要求：**每个任务开始前有干净的基线提交**、**每个可验证变更一个提交**、**回退路径随时可用**。Codex 的官方最佳实践也建议在任务前后建立 Git checkpoint，原因一致：有了明确的还原点，才敢让 Agent 自由探索。进阶做法是用 worktree 让多个 Agent 并行工作，互不干扰；用 `git add -p` 把 AI 产出与手写改动分开提交。

```shell
# 任务开始前的标准动作：确认基线干净、建分支
git status --short          # 必须为空，否则先处理
git switch -c feat/cancel-order
git commit --allow-empty -m "chore: 开始 cancel-order 任务的基线标记"

# 与 AI 协作时的提交节奏
git add -p                  # 逐块挑选，把 AI 产出与手写改动分开
git commit -m "feat(orders): 领域层取消逻辑"
git commit -m "feat(api): 暴露取消接口"

# 并行两个 Agent：各自一个 worktree，互不污染工作区
git worktree add ../proj-agent-a -b agent/task-a
git worktree add ../proj-agent-b -b agent/task-b
git worktree list

# 合并前先看整体差异，再决定是否 squash
git diff main...agent/task-a --stat
git log --oneline main..agent/task-a
```

```bash
#!/usr/bin/env bash
# ai_session_log.sh：给每次 AI 会话留一条可追溯记录
set -euo pipefail
note="${1:?用法: ai_session_log.sh \"本次任务一句话\"}"
msg=$(git log -1 --pretty=%s 2>/dev/null || echo "无提交")

printf '%s | %s | 基线=%s\n' \
  "$(date '+%Y-%m-%d %H:%M:%S')" "$note" "$msg" >> .ai-sessions.log

echo "已记录到 .ai-sessions.log（建议在 PR 描述里贴上最近几条）"
tail -5 .ai-sessions.log
```

```shell
# 使用示例：每次会话结束记一行，PR 里就能说明「哪些代码由 AI 产出、基线在哪」
./ai_session_log.sh "实现取消订单领域逻辑与接口"
./ai_session_log.sh "补幂等路径测试"
```

## 应用场景实战

### 场景一：给一个老服务加缓存，用骨架-迭代-回退走完全程

需求：商品详情接口 QPS 高、数据库压力大，需要加一层缓存。风险点：缓存键设计错会导致串号，缓存穿透会打垮数据库。用骨架先固定接口与验收，再交给 AI 实现。

```python
# src/cache/port.py：人类先写骨架（接口 + 错误语义 + 返回契约）
from typing import Protocol


class CachePort(Protocol):
    def get(self, key: str) -> str | None: ...
    def set(self, key: str, value: str, ttl_seconds: int) -> None: ...
```

```python
# tests/test_product_cache.py：验收标准，覆盖串号与穿透两条风险
import pytest

from src.product.service import ProductService


class MemCache:
    def __init__(self):
        self.data = {}

    def get(self, key):
        return self.data.get(key)

    def set(self, key, value, ttl_seconds):
        self.data[key] = value


class CountingRepo:
    """假仓储：记录被打了几次，用于断言缓存是否真的生效。"""

    def __init__(self):
        self.calls = 0

    def fetch(self, product_id):
        self.calls += 1
        return {"id": product_id, "name": f"p{product_id}"}


def test_cache_hit_avoids_db():
    repo, cache = CountingRepo(), MemCache()
    svc = ProductService(repo, cache)

    svc.detail("p1")
    svc.detail("p1")
    assert repo.calls == 1, "第二次应命中缓存"


def test_no_cross_tenant_hit():
    """串号防护：不同租户不能命中彼此缓存。"""
    repo, cache = CountingRepo(), MemCache()
    svc = ProductService(repo, cache)

    svc.detail("p1", tenant="t1")
    svc.detail("p1", tenant="t2")
    assert repo.calls == 2, "不同租户必须各自回源"


def test_null_cache_prevents_penetration():
    """穿透防护：不存在的商品也要缓存空值。"""
    repo, cache = CountingRepo(), MemCache()
    svc = ProductService(repo, cache, null_ttl=30)

    with pytest.raises(Exception):
        svc.detail("missing")
    assert cache.get("t0:product:missing") == "__NULL__"
```

```shell
# 1) 红：跑一遍确认测试有效
pytest tests/test_product_cache.py -q

# 2) 交给 AI 实现，约束写死
codex exec "阅读 tests/test_product_cache.py 与 src/cache/port.py，
实现 src/product/service.py 的 ProductService.detail，让 3 条测试通过。
约束：缓存键必须包含租户；不存在的商品写 __NULL__ 哨兵值；只改 service.py。"

# 3) 绿：验证
pytest tests/test_product_cache.py -q
pnpm typecheck

# 4) 提交；若不满意就整体回退重来
git add src/product/service.py tests/test_product_cache.py
git commit -m "feat(product): 商品详情加缓存，含租户隔离与空值防护"
```

### 场景二：用 worktree 并行试两种重构方案，选优后合并

需求：一个 800 行的 God Service 需要拆分，两种拆法各有道理（按领域拆 vs 按读写拆）。用两个 worktree 让 Agent 各做一个方案，跑同一套测试与基准，再选优。

```bash
#!/usr/bin/env bash
# parallel_refactor.sh：并行试两个方案并收集结果
set -euo pipefail
base="$(git rev-parse --abbrev-ref HEAD)"

git worktree add -b refactor/by-domain   ../try-domain   "$base"
git worktree add -b refactor/by-readwrite ../try-readwrite "$base"

for wt in ../try-domain ../try-readwrite; do
  ( cd "$wt" && echo "== $wt 基线测试 ==" && pnpm test -- --run | tail -5 )
done

# 让两个 Agent 各自在自己目录里干活（互不干扰工作区）
( cd ../try-domain && codex exec "按领域拆分 src/service/god.ts，只做移动与重命名，不改行为。写完运行 pnpm test" ) &
( cd ../try-readwrite && codex exec "按读写拆分 src/service/god.ts，只做移动与重命名，不改行为。写完运行 pnpm test" ) &
wait

# 对比：改动量、文件数、测试耗时
for wt in ../try-domain ../try-readwrite; do
  echo "---- $wt ----"
  ( cd "$wt" && git diff --stat "$base"...HEAD | tail -1 \
    && git diff --name-only "$base"...HEAD | wc -l \
    && /usr/bin/time -f 'test_time=%es' pnpm test -- --run >/dev/null )
done
```

```shell
chmod +x parallel_refactor.sh
./parallel_refactor.sh

# 选优后合并：保留胜者，清理败者
git switch main
git merge --no-ff refactor/by-domain
git worktree remove ../try-readwrite
git branch -D refactor/by-readwrite
git worktree list
```

## 最佳实践与踩坑记录

### 最佳实践

1. 人写接口与测试、AI 写实现：骨架阶段故意让测试跑出红，作为验收信号有效性的证明
2. 一次提交只做一件事，用脚本（commit_guard.sh）给文件数与改动行数设阈值告警
3. 每个任务开始前建分支并留基线提交，任何时刻都能一键回到已知良好状态
4. 失败就整体回退，不在错误实现上打补丁；需要保留部分改动时用 `git add -p` 挑拣
5. 重构先写特征测试锁住现状（含既有怪癖），新旧并行、一次切一个调用点
6. 多方案探索用 git worktree 并行，避免在同一工作区反复 stash 造成的状态混乱
7. 把验证命令写死成脚本（verify.sh），人和 AI 跑的是同一套标准

### 踩坑记录

```text
坑 1：在错误的实现上继续打补丁
结论：改动越叠越多，最后没人能判断哪些代码还有用，只能整体重写。
原因：错误实现进入了后续上下文，模型顺着错误前提继续推理。
解法：发现方向不对立即 git restore 或回退到基线，重新组织提示词再试。

坑 2：直接 reset --hard 丢掉本该保留的改动
结论：一次回退把同事的未提交改动一起删了，返工两小时。
原因：回退前没有确认工作区状态与未跟踪文件。
解法：回退前先 git status --short，需要保留的先 git stash push -u，共同工作区禁用 hard reset。

坑 3：一次 AI 产出几百行全部塞进一个提交
结论：出问题只能整体回滚，无法定位具体是哪几行引入的。
原因：没有分块提交，diff 里混了实现、格式化、无关文件。
解法：用 git add -p 逐块提交，并让 AI 产出与格式化改动分开提交。

坑 4：重构顺手改了行为，测试没覆盖到
结论：上线后对账差异出现，回滚又发现改动已扩散到多个提交。
原因：没有先写特征测试锁住现状，重构与行为变更混在一起。
解法：先补特征测试，再做纯移动/重命名的重构，行为变更另开提交。

坑 5：多个 Agent 在同一工作区并行跑，互相覆盖文件
结论：两个任务的文件互相写坏，排查成本极高。
原因：终端 Agent 都直接操作同一目录的同一批文件。
解法：用 git worktree 给每个 Agent 独立目录与分支，完成后分别评审合并。
```
