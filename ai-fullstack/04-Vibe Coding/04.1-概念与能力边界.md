## 概述

Vibe Coding 指用自然语言描述意图、由大模型直接生成并修改代码、开发者把注意力放在「结果是否可用」而非「每一行怎么写」的一种编码方式。它不是语言也不是框架，而是一种把提示词、上下文与验证手段当作主要工程材料的工作方式。理解它的能力边界，决定了它是把效率放大三倍，还是把技术债放大三倍。

```text
本篇回答四个问题：
1. 概念从哪来 —— 2025 年 2 月 Andrej Karpathy 提出，随后被词典与媒体收编
2. 和传统写码差在哪 —— 交互媒介、审查粒度、验证方式、错误成本四条主线
3. 什么时候能用 —— 低风险、可验证、可回滚的任务；以及什么时候不能用
4. 边界在哪 —— 上下文窗口、不可验证需求、隐式知识、知识截止
```

## 概念的来源与定义

「Vibe Coding」由 AI 研究者 Andrej Karpathy 于 2025 年 2 月 2 日发布于 X 的推文提出，原意是：这是一种新的编码方式，你完全交给「感觉」，拥抱指数增长，忘记代码本身的存在。背景是当时 Cursor Composer 搭配 Sonnet 级模型已经足够好用，他可以直接口述需求、一路 Accept、不再逐行读 diff。此后该词在 2025 年 3 月被 Merriam-Webster 列为 slang & trending 词条，并被 Collins 词典评为 2025 年度词汇。

需要区分两种用法：一种是**原始定义**（不问代码细节，只验收行为），另一种是后来业界泛化的用法（任何用 AI 写代码都叫 vibe coding）。本知识库采取严格定义，把「用 AI 辅助但保留工程纪律」的部分归入「AI 辅助工程」，两者在不同章节分别讨论。

```text
定义的三个核心要素：
1. 输入媒介 —— 自然语言意图（口语、文本、截图、草图），而不是 API 与语法
2. 生成主体 —— 由 LLM 生成可执行代码，人类负责意图与验收
3. 审查粒度 —— 从逐行代码审查退化为行为级验收，这既是效率来源也是风险来源
```

量出项目的实际上下文体量，这是判断「忘记代码存在」在物理上是否可行的第一步。

```shell
# 统计仓库规模：文件数、总字节数、最大的 10 个文件
git ls-files | wc -l
git ls-files -z | xargs -0 wc -c | tail -1
git ls-files -z | xargs -0 wc -c | sort -rn | head -10
```

```text
提示：英文代码大致 1 token 等于 4 字节，中文注释比例高的文件更密。
把上一步的总字节除以 4，即可粗估把整个仓库塞进上下文需要的 token 数。
大多数超过 20 万行的仓库都放不下，这正是能力边界的物理来源。
```

## 与传统写码的区别

差别不在「谁打字」，而在四条主线：交互媒介、审查粒度、验证方式、错误成本。传统写码中人类是唯一的语义来源，代码是人类的直接产出；Vibe Coding 中人类给出的是意图与验收标准，代码是模型的统计推断产物，可能在任何一处包含看似合理但错误的内容。因此工程重心从「怎么写得优雅」迁移到「怎么把任务定义清楚、怎么快速发现错误」。

| 维度 | 传统写码 | Vibe Coding |
| --- | --- | --- |
| 输入 | 语法与 API | 自然语言意图 |
| 主要产出 | 代码 | 可运行的行为 + 代码 |
| 审查粒度 | 逐行 diff | 行为验收、抽样读码 |
| 错误形态 | 语法与编译错误为主 | 语义错误、幻觉 API、逻辑近似 |
| 错误暴露时机 | 编译期 | 可能推迟到运行期甚至生产期 |
| 复用单元 | 函数、库、模板 | 提示词、规则文件、技能包 |
| 瓶颈 | 编码速度 | 需求表述质量与验证速度 |
| 核心技能 | 语法、算法、架构 | 拆解、上下文供给、验证设计 |

用 git 客观跟踪「AI 单次产出规模」，长期观察审查粒度是否退化。

```shell
# 单次提交的改动规模（AI 一次产出常常是几百行）
git show --stat HEAD

# 统计最近 20 次提交的增删行数总量
git log -20 --pretty=tformat: --numstat | awk '{add+=$1; del+=$2} END {print "added:", add, "deleted:", del}'
```

## 从纯 Vibe Coding 到 AI 辅助工程的谱系

现实中极少有人只用最纯粹的形式（全程不读代码），绝大多数团队处在谱系中间。按人类介入方式可分四档，效率与风险随档位反向变化：越靠左越快、越适合原型；越靠右越慢、越适合长期维护的生产系统。选档位应当是显式决策，而不是随心情摇摆。

| 档位 | 人类做什么 | 交付物 | 适合场景 |
| --- | --- | --- | --- |
| 纯 Vibe | 只说需求、只验收结果 | 可跑的原型 | 一次性脚本、周末项目、演示 |
| 对话式辅助 | 给上下文、逐轮纠偏 | 功能可用的代码 | 内部工具、探索性功能 |
| 规格驱动 | 先写规格与验收标准，再让 AI 实现 | 带测试与文档的模块 | 生产代码、团队协作 |
| 智能体编排 | 拆解任务、编排多个 Agent、审阅产物 | 可合并的 PR | 规模化改造、多模块工程 |

两个档位的提示词模板差异很大，可直接落地成文件放进仓库。

```markdown
<!-- prompts/prototype.md：原型档，重速度 -->
目标：在 30 分钟内做出可演示的登录页。
约束：单文件 HTML + CDN，不要构建工具，不要后端。
验收：浏览器打开能输入、能提交、有 loading 状态。
不需要：测试、错误处理、持久化。
```

```markdown
<!-- prompts/spec-driven.md：生产档，重正确性 -->
任务：为 orders 模块新增「取消订单」能力。
先做：阅读 src/orders/ 与现有测试，输出实现计划，等我确认后再改代码。
约束：不改动公共 API 签名；沿用现有 Repository 模式；错误统一用 AppError。
验收标准：
1. 新增单测覆盖「已发货订单不可取消」与「重复取消幂等」两条路径
2. npm test 全绿，npm run lint 无新增告警
3. 提交信息遵循 Conventional Commits
```

## 适用场景与不适用场景

判断标准可以压成三个问题：结果是否容易验证、失败是否容易回滚、需求是否能用语言说清。三者都是「是」时收益最大；任意一项是「否」，收益会被验证成本吃回去。特别提醒：涉及资金、隐私、权限与不可逆数据操作的任务，即使看起来简单，也不在适用区。

| 场景 | 适合度 | 理由 |
| --- | --- | --- |
| 一次性脚本、数据清洗 | 高 | 结果可肉眼验证，失败无成本 |
| 原型与演示 | 高 | 需求本身在探索，代码可丢弃 |
| 有完整测试覆盖的内部工具 | 高 | 测试即验收标准，可安全快跑 |
| 前后端 CRUD 样板代码 | 高 | 模式固定，模型训练充分 |
| 数据迁移与 schema 变更 | 中 | 必须先备份，且要有回滚脚本 |
| 支付、鉴权、加密逻辑 | 低 | 错误代价不可接受，需要人工设计 |
| 性能敏感的底层优化 | 低 | 需要真实基准数据反复测量 |
| 遗留系统的隐式约定 | 低 | 关键知识不在代码里，模型无从得知 |

落地区分方式：在仓库里用 CODEOWNERS 标记高风险路径，强制走人工评审。

```text
# .github/CODEOWNERS
# 高风险路径：任何改动必须由对应责任人人工评审
src/billing/            @payments-team
src/auth/               @security-team
migrations/             @dba-team

# 低风险路径：允许 AI 评审 + 抽样人工检查
src/components/         @frontend-team
scripts/                @frontend-team
```

```shell
# 校验 CODEOWNERS 语法（需要 gh CLI 与仓库权限）
gh api repos/{owner}/{repo}/codeowners/errors

# 本地粗查：列出所有 pattern
grep -v '^#' .github/CODEOWNERS | awk '{print $1}'
```

## 能力边界与预期管理

模型的边界不是「聪明程度」问题，而是四个结构性限制：上下文放不下、需求里存在不可言说的知识、模型无法真正验证自己的输出、知识与训练数据有时间截止。预期管理的关键，是把「AI 应该能做」这种模糊期待，换成对每类任务提前标注的验证方式。凡是无法在几分钟内验证的任务，都不该让 AI 直接改主干分支。

```text
四类结构性边界：
1. 上下文 —— 窗口有限，超大仓库必须靠检索、规则文件与渐进披露
2. 隐式知识 —— 团队口头约定、历史决策、线上特殊配置，代码里看不到
3. 无自验证 —— 模型不会真正运行你的系统，只能生成「看起来对」的东西
4. 知识截止 —— 新版本 API 与刚发布的库，模型可能给出过时或臆造的用法
```

用可运行的脚本把上下文预算变成数字。

```python
# context_budget.py：粗估一个目录能否塞进模型上下文窗口
# 用法：python3 context_budget.py /path/to/project
import os
import sys

# 只统计常见源码与文档后缀，避免把二进制和依赖算进去
EXTS = {".py", ".js", ".ts", ".tsx", ".jsx", ".go", ".java", ".rs",
        ".md", ".json", ".yaml", ".yml", ".toml", ".sql", ".sh"}
SKIP_DIRS = {".git", "node_modules", "dist", "build", ".venv", "__pycache__"}


def walk(root):
    for dirpath, dirnames, filenames in os.walk(root):
        dirnames[:] = [d for d in dirnames if d not in SKIP_DIRS]
        for name in filenames:
            if os.path.splitext(name)[1] in EXTS:
                yield os.path.join(dirpath, name)


def main():
    root = sys.argv[1] if len(sys.argv) > 1 else "."
    total_bytes = 0
    files = 0
    biggest = []
    for path in walk(root):
        try:
            size = os.path.getsize(path)
        except OSError:
            continue
        total_bytes += size
        files += 1
        biggest.append((size, path))

    # 英文代码经验值约 4 字节每 token；中文注释多的仓库会更密，仅作数量级判断
    est_tokens = total_bytes // 4
    print(f"files={files} bytes={total_bytes} est_tokens~{est_tokens}")
    for size, path in sorted(biggest, reverse=True)[:5]:
        print(f"{size:>10}  {path}")


if __name__ == "__main__":
    main()
```

```shell
# 实测：对一个小型前端仓库运行，判断能否整体投喂
python3 context_budget.py ./web-app
# files=42 bytes=187432 est_tokens~46858
# 结论：小仓库可整体给上下文；超过 20 万 token 就必须改用检索 + 规则文件
```

## 应用场景实战

### 场景一：给一次性项目划定 vibe coding 的安全边界

真实场景：团队要在周六做一次内部数据看板演示，唯一的硬约束是周一必须能删掉。先写一份边界声明，明确哪些东西可以放手让 AI 生成、哪些必须人工把住。

```markdown
<!-- VIBE-SCOPE.md：一次性项目的边界声明，放仓库根目录 -->
项目性质：一次性 Demo，演示后归档，不进主干、不进生产。

可以完全交给 AI：
- 前端页面与图表（数据源为本地 JSON 快照）
- 一次性数据清洗脚本
- 文案、样式、交互细节

必须人工确认：
- 任何写入生产数据库的操作 -> 禁止，改用只读快照
- 任何密钥 -> 只用演示账号，且通过环境变量注入
- 任何依赖 -> 只允许已在 lockfile 中的包

归档条件：
- 演示结束当天，仓库标记 archived，云资源全部释放，演示凭据轮换
```

```shell
# 建立边界并让 AI 遵守：把声明文件纳入上下文，要求它先复述规则
git checkout -b demo/dashboard-saturday
printf '%s\n' 'VIBE-SCOPE.md 的约束优先于任何临场要求。' >> AGENTS.md
git add AGENTS.md VIBE-SCOPE.md
git commit -m "chore: 声明一次性项目的 vibe coding 边界"

# 越界检查：本次分支是否碰过高风险目录
git diff --name-only main...HEAD | grep -E '^(migrations|src/billing|src/auth)/' || echo "未触碰高风险目录"
```

### 场景二：用验证成本给真实任务做准入判定

生产项目的常见诉求：「把订单导出接口改成流式返回，避免大订单超时」。这类任务风险中等但可验证，属于可交给 AI 的范围，前提是先把验收标准写成可执行脚本，再让 AI 动手。

```python
# acceptance_check.py：把验收标准写成脚本，AI 的产出必须通过
# 依赖：pip install requests --index-url https://pypi.tuna.tsinghua.edu.cn/simple
import time

import requests

BASE = "http://127.0.0.1:8000"


def test_streaming_export():
    # 1. 记录首字节时间，证明是流式而不是一次性攒齐再返回
    start = time.time()
    with requests.get(f"{BASE}/orders/export", stream=True, timeout=60) as resp:
        assert resp.status_code == 200, resp.status_code
        first_chunk_at = None
        rows = 0
        for chunk in resp.iter_content(chunk_size=8192):
            if first_chunk_at is None:
                first_chunk_at = time.time()
            rows += chunk.count(b"\n")
    total = time.time() - start
    ttfb = (first_chunk_at or total) - start
    print(f"ttfb={ttfb:.3f}s total={total:.3f}s lines={rows}")
    # 2. 断言：10 万行导出场景下，首字节不应超过 2 秒
    assert ttfb < 2.0, f"不是流式：首字节耗时 {ttfb:.2f}s"
    # 3. 断言：行数符合预期，避免静默截断
    assert rows > 1000, f"导出行数异常：{rows}"


if __name__ == "__main__":
    test_streaming_export()
    print("验收通过")
```

```shell
# 运行方式：先起服务，再跑验收脚本
uvicorn app.main:app --port 8000 &
sleep 2
python3 acceptance_check.py
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先给任务定档位（纯 Vibe / 对话式 / 规格驱动 / 智能体编排），写进仓库文档并让 AI 读到，避免同一项目内标准漂移
2. 把「可验证」当准入条件：无法在几分钟内验证的任务，不允许 AI 直接改主干
3. 用 CODEOWNERS 标记高风险目录，让评审流程自动兜底而不是靠人自觉
4. 每次 AI 产出都要求一份「验证步骤」，人类照着跑一遍，并把它固化成可复用脚本
5. 原型代码与生产代码物理隔离（不同目录或不同仓库），归档时明确删除
6. 给上下文量体：先用脚本量出仓库 token 量级，再决定整体投喂还是检索投喂

### 踩坑记录

```text
坑 1：把 Vibe Coding 当成「不用懂技术」的捷径
结论：原型跑得飞快，进入维护期后没人能改，返工成本远超手写。
原因：原始定义里人类退出了代码审查，但没有退出责任；不懂技术就无法判断产出是否安全。
解法：明确档位与边界，生产代码至少用规格驱动档，保留测试与评审。

坑 2：用 AI 直接改生产环境的高风险代码
结论：一次「小重构」改坏了鉴权幂等逻辑，故障持续数小时。
原因：模型对隐式的业务约束（如重放攻击防护）没有信息来源，只能按通用模式推断。
解法：鉴权、支付、加密、迁移类路径严格人工设计 + 人工评审，AI 只做辅助。

坑 3：一次性项目忘归档，云资源与凭据长期留存
结论：半年后审计发现测试库仍在公网可达，账号密钥从未轮换。
原因：Vibe 项目往往没有仓库规范，也没写归档条件。
解法：开工当天写 VIBE-SCOPE.md 并包含归档条件，交付日执行删除与密钥轮换。

坑 4：只看结果不看日志，模型幻觉 API 被带上线
结论：调用了一个并不存在的方法名，本地不报错因为走了宽松的动态分支。
原因：模型对 API 的记忆有截止期，新版本的改动它并不知道。
解法：对每个外部 API 调用用官方文档核对一次，依赖版本写进 lockfile 并在 CI 校验。
```
