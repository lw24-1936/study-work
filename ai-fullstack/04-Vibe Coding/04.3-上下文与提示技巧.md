## 概述

同一个模型、同一个需求，提示质量不同会导致产出质量差一个数量级。所谓「提示技巧」在工程上其实只有五件事：把上下文喂对、把任务切小、给参考实现、写清约束与验收、让模型先读代码再改。这五件事都不是玄学，都可以沉淀成文件放进仓库、被 review、被复用。

```text
提示质量的五个抓手：
1. 上下文 —— 先给「是什么」，再提「要什么」；用文件引用代替口述回忆
2. 粒度 —— 一次一个可验证的变更，宁可五轮小改，不要一轮大改
3. 样例 —— 给一个已有的同类实现，让模型照猫画虎而不是重新发明
4. 约束 —— 说清不能动什么、必须用什么、怎么算做完
5. 顺序 —— 先探索读码出计划，确认后再动文件
```

## 上下文优先：先给资料再提需求

模型对项目的了解只来自两处：训练数据里的通用模式，以及你这次对话里给它的内容。前者只知道「一般项目长什么样」，不知道你的目录约定、你的错误类型、你的历史决策。因此正确顺序是：先投喂事实（目录结构、关键文件、约定文件），再提需求；而不是先抛需求、等它猜错、再逐个纠正。

代价可以量化：如果你手上是 12 万行的仓库，整仓投喂不可能，只能「选文件」。所以上下文技巧的第一步是**建立项目地图**——用一两条命令生成骨架与关键文件清单，再决定投喂什么。

```shell
# 生成项目地图：目录骨架（忽略依赖与构建产物）
git ls-files | grep -vE '^(node_modules|dist|build|\.venv)/' | awk -F/ '{print $1"/"$2}' | sort -u | head -30

# 列出核心源码文件及其行数，判断哪些值得整文件投喂
rg --files -g '!node_modules' -g '!dist' -g '*.ts' | head -40
git ls-files '*.ts' | grep -vE '(node_modules|dist|test|spec)' | xargs wc -l | sort -rn | head -15

# 找约定与配置文件（这些几乎永远应该投喂）
ls -la AGENTS.md CLAUDE.md README.md package.json tsconfig.json .env.example 2>/dev/null
```

```text
# 投喂顺序模板（粘贴进对话的开头，比「帮我加个功能」有效得多）
1. 项目是什么：一句话
2. 技术栈与版本：Node 22 / TypeScript 5 / vitest / pnpm
3. 目录结构：src/api、src/domain、src/infra 各自的职责
4. 相关文件：用 @ 引用具体路径，而不是描述「那个处理订单的文件」
5. 约定：错误类型、命名风格、测试位置（或直接说「见 AGENTS.md」）
6. 需求与验收：见下一节
```

带上下文的实际调用示例（把约定文件与目标文件一起喂进去）：

```shell
# Claude Code 非交互模式：把项目约定与目标文件拼进提示
claude -p "$(cat AGENTS.md)

任务：为 src/api/orders.ts 的 createOrder 补一条失败路径单测。
只改 src/api/__tests__/orders.test.ts，不要动实现文件。" \
  --permission-mode plan

# Codex CLI：同样思路，先让它只读地给出方案
codex exec "阅读 AGENTS.md 与 src/api/orders.ts，输出实现计划，先不要改文件"
```

## 任务粒度控制

粒度是提示技巧里最容易被忽视、影响却最大的一项。经验规则是：**一次对话只推进一个能被单独验证的变更**。粒度太大的典型症状是模型改了 14 个文件，其中 11 个是对的，你无法判断剩下 3 个哪错了，回退又会丢掉对的改动。粒度太小（例如让模型逐个改 import 语句）则浪费上下文与时间。合适的粒度是「一个有明确验收信号的功能切片」。

```text
粒度自检三问：
1. 这个变更能否用一条命令验证通过或失败？（不能 -> 太模糊）
2. 如果它改错了，我能否只回退这一部分而不丢其他改动？（不能 -> 太大）
3. 我能否用一句话说清「做完的样子」？（不能 -> 需求本身没想清楚）
```

拆解示例（把一个模糊的大需求拆成三次可验证的小任务）：

```markdown
<!-- 原始需求（粒度过大，不要直接提） -->
帮我把订单模块所有地方都改成支持取消和退款，还要加审计。

<!-- 拆成三次可独立验证的任务 -->
任务 A（可验证：新增单测通过）
只做「取消」：为 Order 增加 CANCELLED 状态与 cancel() 方法，
禁止已发货订单取消。改动限定 src/domain/order.ts 与其单测。

任务 B（可验证：接口返回 409）
在 API 层暴露 POST /orders/:id/cancel，把领域错误映射为 409 + 错误码。
改动限定 src/api/orders.ts 与其单测。

任务 C（可验证：audit 表出现一条记录）
退款与取消各写一条审计记录，字段复用现有 AuditLog 表。
改动限定 src/infra/audit.ts 与其单测。依赖 A、B 已完成并合并。
```

```shell
# 每次任务前后都跑同一套验证，让「做没做完」不需要争论
pnpm test -- --run src/domain/order.test.ts
pnpm typecheck
git diff --stat

# 用改动文件数作为粒度告警：超过 8 个文件就该考虑是否该拆
git diff --name-only | wc -l
```

## 样例驱动与参考实现

与其描述「按我们的代码风格来」，不如直接给一份同类实现。模型在「照抄结构」这件事上非常强，在「猜你没说出口的约定」上非常弱。样例驱动有三种常见形态：给一个已有文件照抄结构、给一对「输入-输出」示例、给一份参考实现链接要求对齐。这一节的核心动作是**先在仓库里找到最近似的实现**，再把路径交给模型。

```shell
# 找最近似的实现：已有路由里怎么处理鉴权与错误
rg -n "router\.(post|put)" src/api --type ts | head -20
rg -n "AppError" src -l | head -10
rg -n "zod|z\.object" src/api -l | head -10

# 找测试的写法样例
rg --files -g '*.test.ts' src | head -10
sed -n '1,40p' "$(rg --files -g '*.test.ts' src | head -1)"
```

把上面找到的样例直接放进提示词：

```text
需求：新增 PUT /orders/:id/ship 接口。

参考实现（照抄这套结构，包括错误处理与校验方式）：
- 路由与校验：@src/api/orders.ts 的 createOrder
- 领域调用：@src/domain/order.ts
- 单测结构：@src/api/__tests__/orders.test.ts

硬性要求：
1. 入参校验用 zod，与 createOrder 完全一致的写法
2. 领域错误统一映射为 AppError，不要抛原始 Error
3. 单测至少覆盖：正常流转、状态非法（409）、订单不存在（404）
4. 不要新增依赖，不要改公共类型定义
```

少样本示例同样适用于格式类任务（例如批量生成迁移文件、生成测试数据）：

```python
# sample_driven.py：用「输入-输出」示例喂给模型，约束输出格式
# 依赖：pip install openai --index-url https://pypi.tuna.tsinghua.edu.cn/simple
import json
import os

from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

FEW_SHOT = [
    {"role": "user", "content": '把这句话转成提交信息：修了登录页在小屏幕下按钮错位'},
    {"role": "assistant", "content": "fix(ui): 修复登录页小屏下按钮错位"},
    {"role": "user", "content": '把这句话转成提交信息：给订单接口加了幂等键支持'},
    {"role": "assistant", "content": "feat(orders): 下单接口支持 Idempotency-Key"},
]

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "你是提交信息生成器，只输出一行 Conventional Commits 格式，不加解释。"},
        *FEW_SHOT,
        {"role": "user", "content": "把这句话转成提交信息：开始用 pnpm 替换 npm"},
    ],
    temperature=0,
)
print(resp.choices[0].message.content)
# 期望输出形如：chore: 构建工具从 npm 迁移到 pnpm
```

## 约束与验收标准

约束是「负向清单」，验收是「正向信号」。两者缺一不可：只给约束，模型不知道什么算做完；只给验收，模型会为了通过断言而牺牲架构（例如把逻辑塞进测试文件）。写约束时优先用**可检查的表述**（文件路径、命令、版本），少用形容词（「优雅」「高性能」）。

```text
约束与验收的写法对照：
写得差：代码要健壮、性能好、符合项目风格、改完记得测试。
写得好：
  约束 —— 只改 src/domain/**，不改公共 API；不新增依赖；不写 console.log
  验收 —— pnpm test 全绿；pnpm lint 零告警；取消重复调用返回同一结果（幂等）
```

把验收标准写成可执行脚本，是这一节最有价值的一步：它同时服务于 AI（模型可自己跑）与人类评审（不靠感觉）。下面是一个真实可用的验收脚本骨架。

```bash
#!/usr/bin/env bash
# verify.sh：一条命令回答「这次 AI 的产出到底行不行」
set -uo pipefail
FAIL=0

run() {
  local name="$1"; shift
  if "$@" >/tmp/verify_out 2>&1; then
    echo "PASS  $name"
  else
    echo "FAIL  $name"
    tail -20 /tmp/verify_out
    FAIL=1
  fi
}

run "类型检查"  pnpm typecheck
run "静态检查"  pnpm lint
run "单元测试"  pnpm test -- --run
run "依赖未漂移" git diff --exit-code --quiet pnpm-lock.yaml
run "未改高风险目录" bash -c \
  '! git diff --name-only | grep -qE "^(migrations|src/billing|src/auth)/"'

if [ "$FAIL" -eq 0 ]; then
  echo "全部通过：可以提交"
else
  echo "存在失败项：先修再提交"
  exit 1
fi
```

```shell
chmod +x verify.sh
./verify.sh
```

```text
# 实测输出形态
PASS  类型检查
PASS  静态检查
PASS  单元测试
PASS  依赖未漂移
PASS  未改高风险目录
全部通过：可以提交
```

## 让 AI 先读代码再动手

直接让模型改代码，它只能按「通用最佳实践」猜你的结构；先让它读、复述、出计划，再改，命中率会高得多。这也是 Plan 模式（OpenCode 用 Tab 切换、Claude Code 用 `--permission-mode plan`、Codex 用审批模式限制写入）存在的意义：把「只读探索」和「写入执行」分成两个阶段，让人类在中间有一次否决机会。

```shell
# 阶段一：只读探索，要求输出「结构复述 + 计划 + 风险点」
codex exec "只读分析，不要修改任何文件：
1. 复述 src/orders 的数据流：从路由到领域到仓储
2. 列出取消订单需要改动的文件清单与原因
3. 指出三处最可能踩坑的地方（并发、幂等、状态机）"

# 阶段二：确认计划后再执行（计划已经写进仓库，直接引用）
codex exec "按 docs/plans/cancel-order.md 执行任务 A，只改 src/domain/order.ts 与其单测"
```

```text
# 要求模型先读再动手的提示骨架（可直接复用）
第一步（只读）：
  读 @<关键文件1> @<关键文件2>，用 5 行以内说明当前是如何实现的。
  不要写代码，不要修改文件。

第二步（计划）：
  给出改动计划：涉及文件、每处改动理由、可能的副作用。
  标出你不确定的点，让我确认。

第三步（执行）：
  按确认后的计划改代码，只改计划内的文件。
  完成后运行 <验证命令>，把真实输出贴出来。
```

计划文件本身也可以被 AI 生成并被人类 review，这比口头确认更可追溯。

```markdown
<!-- docs/plans/cancel-order.md：先由 AI 起草，人类改过再执行 -->
# 取消订单实现计划

## 现状（来自只读分析）
- 路由 src/api/orders.ts 直接操作仓储，未经过领域层
- 状态字段为字符串枚举，无状态机约束
- 审计写入集中在 src/infra/audit.ts

## 改动
1. src/domain/order.ts 增加 CANCELLED 状态与 cancel()，禁止 SHIPPED 取消
2. src/api/orders.ts 新增 POST /orders/:id/cancel，映射 409
3. src/infra/audit.ts 复用 record() 写审计

## 风险
- 并发取消需要幂等：同一订单重复取消必须返回同一结果
- 迁移：已有订单状态字符串是否需要数据订正（待确认）

## 不做
- 退款流程（另开任务）
```

## 应用场景实战

### 场景一：给陌生仓库加一个功能，从零建立上下文

需求：接手一个没人维护的 Node 服务，需要新增「导出订单 CSV」接口。你不知道代码结构，所以要先用命令建立地图，再按「先读后写」推进。

```bash
#!/usr/bin/env bash
# context_pack.sh：为一次任务打包上下文清单（打印，不产生文件）
set -euo pipefail

echo "== 1. 仓库规模 =="
git ls-files | wc -l
git ls-files -z | xargs -0 wc -c | tail -1

echo "== 2. 目录骨架 =="
git ls-files | awk -F/ 'NF>1 {print $1"/"$2}' | sort -u

echo "== 3. 约定文件 =="
for f in AGENTS.md CLAUDE.md README.md package.json; do
  [ -f "$f" ] && echo "found: $f ($(wc -l < "$f") 行)"
done

echo "== 4. 与任务最相关的文件（按关键词命中） =="
rg -l --type ts -g '!node_modules' -g '!dist' 'orders|export|router' src | head -15

echo "== 5. 测试写法样例 =="
rg --files -g '*.test.ts' src | head -5

echo "== 6. 建议投喂顺序 =="
cat <<'TXT'
  1) AGENTS.md + package.json（约定与技术栈）
  2) src/api/orders.ts（最近似的路由实现）
  3) src/api/__tests__/orders.test.ts（测试结构样例）
  4) 本次需求 + 验收标准
TXT
```

```shell
chmod +x context_pack.sh
./context_pack.sh

# 带着打包好的上下文进入只读探索阶段
codex exec "阅读 AGENTS.md、src/api/orders.ts、src/api/__tests__/orders.test.ts，
输出新增 CSV 导出接口的实现计划与文件清单，先不要改代码"
```

### 场景二：把「模糊抱怨」转成可执行的缺陷修复提示

需求：用户反馈「导出大订单时页面转圈很久，有时候还 504」。这类描述无法直接交给模型，必须先转成可复现、可验证的提示。

```text
# 转换前（不要这样提）
导出有问题，帮我修一下。

# 转换后（可直接执行）
环境：本地起服务 uvicorn app.main:app --port 8000
复现：对 12 万行订单执行 GET /orders/export，观察 60 秒
现象：约 42 秒后返回 504，服务端日志出现 "Timeout reading from upstream"
已知：导出实现为一次性 SELECT 全量 + json.dumps 后再返回（见 @app/orders.py 第 88 行）
目标：改为流式返回，首字节时间 < 2 秒，总量不截断
约束：不改动 SQL 的过滤条件；不新增依赖；保持现有响应头字段
验收：
  1. python3 acceptance_check.py 通过（断言首字节 < 2s 且行数 > 1000）
  2. 内存占用峰值不超过 300MB（用 /usr/bin/time -v 观察 Maximum resident set size）
  3. 现有单测全绿
```

```shell
# 用真实测量确认「修好了」，而不是靠感觉
/usr/bin/time -v python3 acceptance_check.py 2>&1 | grep -E 'Maximum resident|Elapsed'
curl -s -o /dev/null -w 'ttfb=%{time_starttransfer}s total=%{time_total}s\n' \
  http://127.0.0.1:8000/orders/export
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每次对话开头固定投喂「项目一句话 + 技术栈 + 相关文件路径 + 约定入口」，顺序不要颠倒
2. 用文件引用（`@path`）代替描述，模型读文件比猜文件名可靠得多
3. 一次任务只推进一步，并用 `git diff --name-only | wc -l` 给粒度设阈值（超过 8 个文件就该拆）
4. 找最近的同类实现当样例，明确说「照抄这套结构」，比描述风格有效
5. 验收标准写成脚本（verify.sh），模型可自跑、人类可复核，避免争论
6. 强制两阶段：先只读出计划、人类确认、再执行；计划写成文件留痕
7. 上下文不是越多越好：只投喂相关文件，噪声文件会稀释注意力并挤占窗口

### 踩坑记录

```text
坑 1：一次提一个跨 14 个文件的大需求
结论：模型改对了大部分，但错的那几处无法定位，回退又会丢正确改动。
原因：改动边界不清，验证信号被淹没。
解法：按「可单独验证」切片，一次一个变更，每个变更后立即跑 verify.sh。

坑 2：用「按我们的风格来」当约束
结论：产出风格与仓库不一致，评审时被要求重写。
原因：风格是隐式知识，模型无从获取，只能按通用惯例猜。
解法：给一份同类文件当样例，或把风格写进 AGENTS.md 并纳入上下文。

坑 3：只给验收标准不给负向约束
结论：为了通过断言，模型改了公共 API 或在测试里写特殊分支。
原因：优化目标单一，模型会走最短路径达标。
解法：同时给出「不许改什么」，并在验收脚本里加「未改高风险目录」这类断言。

坑 4：计划阶段和实现阶段混在一轮里
结论：模型直接开改，方向错了才发现，浪费大量上下文。
原因：没有把只读探索与写入执行分开，缺少人类否决点。
解法：第一阶段显式声明「不要修改文件」，确认计划后再进入执行阶段。

坑 5：把整个仓库塞进上下文期待「它自己会找到重点」
结论：响应变慢、成本上升，产出反而更差。
原因：无关内容稀释注意力，长上下文还会触发摘要压缩丢细节。
解法：用项目地图 + 关键词检索挑出 5 至 10 个相关文件，再进对话。
```
