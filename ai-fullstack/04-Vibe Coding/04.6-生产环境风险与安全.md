## 概述

AI Agent 与传统工具最大的安全差异是：它**有写权限、有网络、会主动执行命令**，而且它的动作来自概率推断而不是你的明确指令。因此风险不再是「代码有 bug」，而是「它刚刚在你的生产库上执行了什么」。五类风险最需要单独设防：密钥泄漏、依赖投毒、许可证合规、不可逆操作、权限过宽。共同原则只有一句：**最小权限 + 默认拒绝 + 动作前可见**。

```text
五类风险与对应防线：
1. 密钥泄漏    -> 扫描 + 环境变量 + 密钥轮换
2. 供应链投毒  -> 锁文件 + 禁用安装脚本 + 依赖审查
3. 许可证合规  -> 自动生成清单 + 法务白名单
4. 不可逆操作  -> 先备份 + dry-run + 事务 + 拒绝高危命令
5. 权限过宽    -> 沙箱 + 只读默认 + 可写目录白名单
```

行业框架可作对照：OWASP 的 GenAI Security Project 在 2025 版（2024 年 11 月发布）给出了 LLM 应用十大风险，其中 LLM03 供应链、LLM06 过度自主（Excessive Agency）、LLM10 无界消耗与编码 Agent 的场景直接相关。

| OWASP LLM 风险 | 在编码 Agent 场景中的表现 | 对应防线 |
| --- | --- | --- |
| LLM01 提示注入 | 读取的恶意文件/网页里藏着指令 | 不把不可信内容当指令来源 |
| LLM02 敏感信息泄露 | 把 `.env` 内容贴进对话或提交 | 读取 deny 规则 + 扫描 |
| LLM03 供应链 | 偷偷引入被投毒的依赖 | 锁文件 + 脚本禁用 + 审计 |
| LLM06 过度自主 | 无人值守地跑破坏性命令 | 沙箱 + 审批 + 只读默认 |
| LLM10 无界消耗 | 递归调用工具刷爆账单 | 超时、步数上限、预算告警 |

## 凭据与密钥泄漏

密钥泄漏是 AI 协作中最常见、也最容易补救但补救成本最高的一类事故。发生路径有三条：模型把你的 `.env` 内容复述进对话、写进代码或配置文件、或者生成一条把密钥打进日志的语句。防线分三层：**读取层**（让 Agent 根本读不到敏感文件）、**写入层**（提交前扫描 + pre-commit 拦截）、**运营层**（密钥可轮换、不长期有效）。

```shell
# 读取层：在 Agent 配置里显式拒绝敏感路径（Claude Code 示例）
mkdir -p .claude
cat > .claude/settings.json <<'JSON'
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Read(./**/*.pem)",
      "Read(./**/id_rsa*)",
      "Read(./.aws/**)"
    ]
  }
}
JSON

# .gitignore 兜底（.env.example 要保留并提交）
printf '%s\n' '.env' '.env.*' '!.env.example' 'secrets/' '*.pem' '*.key' >> .gitignore
sort -u .gitignore -o .gitignore
```

```shell
# 写入层：扫描历史与工作区里的疑似密钥
# gitleaks：https://github.com/gitleaks/gitleaks
gitleaks detect --source . --redact -v
gitleaks protect --staged            # 只扫暂存区，适合 pre-commit

# trufflehog：https://github.com/trufflesecurity/trufflehog
trufflehog filesystem . --only-verified --no-update

# 没有工具时的兜底 grep（会误报，但比漏报好）
git grep -nE '(AKIA[0-9A-Z]{16}|sk-[A-Za-z0-9]{20,}|-----BEGIN [A-Z ]*PRIVATE KEY-----)' \
  -- . ':!*.md' || echo "未发现明显密钥模式"
```

```yaml
# .pre-commit-config.yaml：把密钥拦截放在提交前（片段）
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.4
    hooks:
      - id: gitleaks
```

```text
# 三个必守规则
1. 永不把真实密钥写进任何提交过的文件；配置示例一律用占位符与 .env.example
2. 密钥一律来自环境变量或密钥管理服务（Vault / KMS / Secrets Manager），不落盘
3. 一旦泄漏，第一动作是轮换而不是删除文件（git 历史不会因为删除而干净）
```

```shell
# 事故处置顺序（先止血再清理）
# 1) 立即轮换：在服务商控制台吊销并重发
# 2) 清理仓库：改写历史需要强推，务必先通知协作者
git filter-repo --path path/to/leaked.file --invert-paths    # 需安装 git-filter-repo
# 3) 强制更新远端（--force-with-lease 比 --force 安全，避免覆盖他人提交）
git push --force-with-lease origin main
# 4) 复盘：把该文件加入 deny 规则与 .gitignore，并在 CI 增加 gitleaks 全量扫描
```

## 依赖投毒与供应链风险

AI 引入依赖的成本极低，这正好踩在供应链攻击的舒适区上。主要攻击面有四类：**安装脚本**（`preinstall` / `postinstall` 在安装时以你的权限执行任意代码）、**名称抢注**（与热门包一字之差的包名）、**维护者账号被接管**（合法包发布恶意版本）、**依赖混淆**（内网私有包名与公网重名，公网高版本被优先解析）。防线是确定性与可验证性：锁文件提交、CI 用冻结安装、安装脚本默认关闭、新依赖必须人工审核。

```shell
# 1) 确定性安装：CI 一律用冻结模式，不用 npm install
npm ci                              # 与 package.json 不一致时直接失败
pnpm install --frozen-lockfile
yarn install --immutable
uv sync --frozen                    # Python（uv）
pip install -r requirements.txt --require-hashes   # 带 hash 的严格安装

# 2) 关闭安装脚本（.npmrc 放项目根目录）
printf '%s\n' 'ignore-scripts=true' >> .npmrc
# 需要编译的包显式重建（只有确认过来源的包才列在这里）
npm ci --ignore-scripts
npm rebuild esbuild sharp

# 3) 列出传递依赖里带安装脚本的包，逐个确认
node -e '
const lock = require("./package-lock.json");
for (const [p, v] of Object.entries(lock.packages || {})) {
  const s = v.scripts || {};
  const hit = ["preinstall", "install", "postinstall", "prepare"].filter(k => k in s);
  if (hit.length) console.log(p || "(root)", hit.join(","));
}'
```

```shell
# 4) 新依赖上架前的四问四查
npm view <pkg> name version maintainers time.modified repository.url
npm view <pkg> scripts                 # 有 postinstall 就问"为什么需要"
npm view <pkg> dist.tarball            # 确认来源域名是官方 registry
npm audit --audit-level=high

# 5) Python 侧：锁定 + 审计
uv lock --check
pip-audit -r requirements.txt
```

```text
# 依赖治理的四条底线
1. package-lock.json / pnpm-lock.yaml / uv.lock 必须提交，并在 PR 里 review 变化
2. CI 使用冻结安装，任何人跑 CI 得到字节级一致的依赖树
3. 新依赖走申请表：用途、为什么标准库不行、体积、许可证、有无安装脚本
4. 定期（建议每月）集中升依赖，一次一个包，升级前后各跑一次审计
```

## 许可证与合规风险

AI 生成的代码可能整体或片段地接近训练数据中的既有实现，而依赖清单也可能被 AI 悄悄改宽。合规关注三点：**依赖许可证类型**（宽松 vs 传染性）、**是否引入 AGPL 类条款**（对 SaaS 有特殊性）、**是否包含生成的代码片段风险**。工程上能做的就是自动产出清单、与白名单比对、把结论交给法务，不要在工程层自行判断合规结论。生成代码的著作权归属与合规认定在不同司法辖区仍有不确定性，遇到具体问题以法务意见与各服务商的官方条款为准。

```shell
# Python：生成依赖许可证清单
pip install pip-licenses --index-url https://pypi.tuna.tsinghua.edu.cn/simple
pip-licenses --format=markdown --with-version --with-urls > docs/licenses.md

# 只列出强传染性许可证，便于法务重点看
pip-licenses --format=csv | grep -iE 'GPL|AGPL|SSPL|EUPL|CC-BY-SA'

# Node：生成许可证清单
npx license-checker --summary
npx license-checker --json > docs/licenses-node.json

# 生成 SBOM（软件物料清单），便于审计与漏洞跟踪
# Syft：https://github.com/anchore/syft
syft dir:. -o spdx-json > sbom.spdx.json
syft dir:. -o cyclonedx-json > sbom.cdx.json
```

```yaml
# .licenserc：许可证白名单（在 CI 里比对，不在白名单内即失败）
allowed:
  - MIT
  - Apache-2.0
  - BSD-2-Clause
  - BSD-3-Clause
  - ISC
  - Python-2.0
  - MPL-2.0

review_required:
  - LGPL-2.1
  - LGPL-3.0
  - EPL-2.0

forbidden:
  - AGPL-3.0
  - AGPL-3.0-only
  - AGPL-3.0-or-later
  - SSPL-1.0
  - BUSL-1.1
  - UNLICENSED
```

```bash
#!/usr/bin/env bash
# license_gate.sh：许可证门禁（Python 侧示例）
set -euo pipefail
python3 - <<'PY'
import csv
import io
import subprocess
import sys

out = subprocess.run(["pip-licenses", "--format=csv", "--with-version"],
                     capture_output=True, text=True, check=True).stdout
FORBIDDEN = ("AGPL", "SSPL", "BUSL")
REVIEW = ("LGPL", "EPL", "CC-BY-SA")

bad, review = [], []
for row in csv.DictReader(io.StringIO(out)):
    lic = row.get("License", "")
    if any(k in lic.upper() for k in FORBIDDEN):
        bad.append((row["Name"], row["Version"], lic))
    elif any(k in lic.upper() for k in REVIEW):
        review.append((row["Name"], row["Version"], lic))

for name, ver, lic in bad:
    print(f"FORBIDDEN {name} {ver} -> {lic}")
for name, ver, lic in review:
    print(f"REVIEW    {name} {ver} -> {lic}")

print(f"forbidden={len(bad)} review={len(review)}")
sys.exit(1 if bad else 0)
PY
```

```shell
chmod +x license_gate.sh
./license_gate.sh
```

```text
# 许可证类别的工程处理口径（最终解释权归法务）
宽松型（MIT / Apache-2.0 / BSD / ISC）：可在白名单，正常使用，保留版权声明
弱传染（LGPL / MPL / EPL）：需确认是否动态链接与修改，进 review 队列
强传染（GPL / AGPL）：AGPL 对网络服务有额外义务，默认禁止，需书面批准
不可商用/自定义（SSPL / BUSL / 自定义 EULA）：默认禁止，需书面批准
```

## 误删数据与不可逆操作

Agent 最危险的动作集中在几条命令上：`rm -rf`、`DROP TABLE`、`DELETE` 无 `WHERE`、`TRUNCATE`、`git push --force`、`kubectl delete`、`terraform destroy`、`chmod -R`。防护不是「小心点」，而是**改动前先备份、先 dry-run、把破坏性操作放进事务与审计表**。数据库侧的通用模式是「先归档再删除」，让删除本身变成可逆动作。

```bash
#!/usr/bin/env bash
# dangerous_cmd_guard.sh：在 shell 层面拦截高危命令（示例：包一层 wrapper）
# 用法：把 alias/function 注入到交互式 shell，或用于 Agent 的执行白名单校验
set -euo pipefail

INPUT="${1:?请传入待检查的命令}"

pattern='(^|[ ;|&])(rm[[:space:]]+-[a-zA-Z]*r[a-zA-Z]*f|mkfs|dd[[:space:]]+if=|DROP[[:space:]]+(TABLE|DATABASE)|TRUNCATE[[:space:]]+TABLE|git[[:space:]]+push[[:space:]]+.*--force[^ ]*|kubectl[[:space:]]+delete|terraform[[:space:]]+destroy|chmod[[:space:]]+-R[[:space:]]+777)'

if printf '%s' "$INPUT" | grep -Eq "$pattern"; then
  echo "BLOCKED 高危命令，需要人工执行：$INPUT"
  exit 2
fi
echo "ALLOWED $INPUT"
```

```shell
# 测试守卫生效（BLOCKED 会返回退出码 2）
./dangerous_cmd_guard.sh 'rm -rf /var/lib/postgresql'
./dangerous_cmd_guard.sh 'DROP TABLE orders;'
./dangerous_cmd_guard.sh 'git push --force origin main'
./dangerous_cmd_guard.sh 'git status'
# BLOCKED 高危命令，需要人工执行：rm -rf /var/lib/postgresql
# BLOCKED 高危命令，需要人工执行：DROP TABLE orders;
# BLOCKED 高危命令，需要人工执行：git push --force origin main
# ALLOWED git status
```

数据库侧：删除改成「先归档、再删除、可回滚」。

```sql
-- safe_purge.sql：安全清理 180 天前的订单（PostgreSQL）
\set ON_ERROR_STOP on          -- 任何错误立即中止，避免半途状态

BEGIN;

-- 1) 归档表只建一次，结构沿用原表
CREATE TABLE IF NOT EXISTS orders_archive (LIKE orders INCLUDING ALL);

-- 2) 先数清楚要删多少（人工核对量级是否合理）
SELECT count(*) AS will_purge
  FROM orders
 WHERE created_at < now() - interval '180 days';

-- 3) 归档（先备份再删除，删除本身就是可逆的）
INSERT INTO orders_archive
SELECT * FROM orders
 WHERE created_at < now() - interval '180 days';

-- 4) 删除，并校验归档行数与删除行数一致
WITH purged AS (
  DELETE FROM orders
   WHERE created_at < now() - interval '180 days'
  RETURNING 1
)
SELECT count(*) AS purged_rows FROM purged;

COMMIT;
```

```shell
# 迁移前必备份，备份文件命名带时间戳，并验证可读
pg_dump -Fc -d appdb -f "backup_$(date +%Y%m%d_%H%M%S).dump"
pg_restore --list "$(ls -t backup_*.dump | head -1)" | head -20

# 危险迁移先跑 dry-run：用事务包住然后回滚
psql -d appdb -v ON_ERROR_STOP=1 -c "BEGIN; \\i migration.sql; ROLLBACK;"

# 用 trash-cli 替代 rm，给自己留后悔药（https://github.com/andreafrancia/trash-cli）
trash-put build/ temp/
```

## 权限与沙箱隔离

权限设计的目标是：**即使 Agent 判断错误，损失也被物理隔离在容器或可写目录里**。三个手段：容器化运行（工作目录挂载，其余只读）、文件系统只读 + 可写白名单、网络默认关闭（需要时按需开）。工具侧各自有权限模型：Claude Code 用 allow/ask/deny 规则加沙箱；Codex 用审批模式与可写根目录限制；OpenCode 通过配置声明权限并提供只读的 Plan 模式；Pi 明确不内置权限弹窗，官方建议在容器内运行，用扩展自行实现确认流程。

```yaml
# .claude/settings.json：最小权限的完整示例
{
  "permissions": {
    "allow": [
      "Read(./src/**)",
      "Read(./tests/**)",
      "Bash(pnpm test:*)",
      "Bash(pnpm lint:*)",
      "Bash(git status)",
      "Bash(git diff:*)"
    ],
    "ask": [
      "Write(./src/**)",
      "Bash(git commit:*)",
      "Bash(pip install:*)",
      "Bash(npm install:*)"
    ],
    "deny": [
      "Read(./.env*)",
      "Read(./secrets/**)",
      "Bash(sudo:*)",
      "Bash(curl:* | bash)",
      "Bash(rm -rf:*)",
      "Bash(git push --force:*)",
      "WebFetch"
    ]
  }
}
```

```shell
# 在容器里跑 Agent：只挂载项目目录，其余只读，默认无网络
docker run --rm -it \
  --network none \
  --read-only \
  --tmpfs /tmp:rw,size=512m \
  --user "$(id -u):$(id -g)" \
  -v "$PWD":/work \
  -w /work \
  node:22-bookworm bash

# 需要联网装包时再单独开网络（用完即弃的容器）
docker run --rm -it --network bridge -v "$PWD":/work -w /work node:22-bookworm bash

# 用只读文件系统 + 单目录可写的方式限制破坏范围
docker run --rm -it \
  --read-only \
  --mount type=bind,src="$PWD",dst=/work \
  --mount type=tmpfs,dst=/tmp \
  -w /work node:22-bookworm bash
```

```text
# 权限收敛的四个动作（按顺序做）
1. 默认只读：先给读取与测试权限，写权限走 ask
2. 明确拒绝：密钥路径、sudo、force push、管道执行远程脚本
3. 物理隔离：容器 + 只读根 + 挂载白名单，让越权在文件系统层面失败
4. 审计留痕：记录 Agent 执行的每条命令（bash history / 会话日志），事后可追溯
```

## 应用场景实战

### 场景一：给一个 Agent 建立「不可越界」的执行环境并验证

需求：让 Agent 帮忙改一个外包交付的遗留项目，代码不可信（可能含恶意脚本），要求「即使项目里有恶意 postinstall 也伤不到主机」。方案：容器 + 无网络 + 只读根 + 项目目录可写，并在启动前用脚本验证隔离确实生效。

```bash
#!/usr/bin/env bash
# sandbox_run.sh：受控容器中运行 Agent
set -euo pipefail

IMG=node:22-bookworm
WORKDIR="$PWD"

echo "1) 拉起沙箱（无网络、只读根、仅项目目录可写）"
docker run --rm -it \
  --name agent-sandbox \
  --network none \
  --read-only \
  --tmpfs /tmp:rw,size=1g \
  --user "$(id -u):$(id -g)" \
  --mount "type=bind,src=$WORKDIR,dst=/work" \
  -w /work \
  "$IMG" bash -lc '
    set -e
    echo "容器内：$(id -un)@$(hostname)"
    echo "---- 隔离自检 ----"
    # 1) 根文件系统应只读
    if touch /root-write-test 2>/dev/null; then
      echo "FAIL 根文件系统可写（隔离失效）"; exit 1
    else
      echo "PASS 根文件系统只读"
    fi
    # 2) 网络应不可达
    if timeout 3 bash -c "echo > /dev/tcp/1.1.1.1/443" 2>/dev/null; then
      echo "FAIL 网络可达（隔离失效）"; exit 1
    else
      echo "PASS 网络不可达"
    fi
    # 3) 项目目录应可写（正常干活的前提）
    touch /work/.sandbox-write-test && rm /work/.sandbox-write-test \
      && echo "PASS 项目目录可写"
    echo "进入交互 Shell，退出后容器自动销毁"
    bash
  '
```

```shell
chmod +x sandbox_run.sh
./sandbox_run.sh
# PASS 根文件系统只读
# PASS 网络不可达
# PASS 项目目录可写

# 容器销毁后确认主机没有被留下东西
docker ps -a --filter name=agent-sandbox
ls -la .sandbox-write-test 2>/dev/null || echo "主机无残留文件"
```

### 场景二：密钥泄漏后的完整止血流程

需求：安全扫描发现一个数据库密码在三个月前被提交进了私有仓库，且该分支还在活跃开发。要求按顺序止血、清理、加固，每一步都可验证。

```bash
#!/usr/bin/env bash
# secret_incident.sh：泄漏处置的分步脚本（需要人工确认关键步骤）
set -euo pipefail

cat <<'MSG'
== 处置顺序（不要跳步） ==
步骤 1  轮换密钥：到数据库/服务商控制台吊销旧密码并生成新密码
步骤 2  更新运行环境：在部署平台与本地 .env（不提交）写入新凭据
步骤 3  确认新凭据生效：跑一次连通性检查
步骤 4  清理仓库历史：git filter-repo 后强推（先通知全体协作者）
步骤 5  加固：加 deny 规则、.gitignore、CI 全量扫描
MSG

read -rp "步骤 1-3 是否已完成并验证？(yes/no) " ok
[ "$ok" = "yes" ] || { echo "先完成轮换与验证，再清理历史"; exit 1; }

echo "== 步骤 4：扫描当前工作区与历史中残留的密钥模式 =="
git grep -nE 'AKIA[0-9A-Z]{16}|password[[:space:]]*=[[:space:]]*["'"'"'][^"'"'"']{8,}' \
  -- . ':!*.md' ':!*test*' || echo "工作区未发现明显残留"

gitleaks detect --source . --redact -v || true

echo "== 步骤 5：确认防复发措施已就位 =="
test -f .gitignore && grep -q '^\.env$' .gitignore && echo "PASS .gitignore 含 .env"
grep -q '"deny"' .claude/settings.json 2>/dev/null && echo "PASS Agent deny 规则存在"
test -f .pre-commit-config.yaml && grep -q gitleaks .pre-commit-config.yaml \
  && echo "PASS pre-commit 已接入 gitleaks"
```

# 验证历史清理是否彻底（对目标模式应为空）

## 最佳实践与踩坑记录

### 最佳实践

1. 密钥只从环境变量或密钥管理服务读取，任何提交过的文件里只有占位符与 `.env.example`
2. Agent 的配置里显式 deny 敏感路径（`.env`、`secrets/`、`*.pem`），读取层拦截比事后清理便宜得多
3. 提交前跑 gitleaks 类扫描（pre-commit）+ CI 全量扫描，双层拦截
4. 锁文件必须提交、CI 用冻结安装、安装脚本默认关闭，新依赖走人工批准
5. 删除类操作一律「先归档再删除」，删除语句带明确 `WHERE` 与行数校验
6. 破坏性命令（`rm -rf`、`DROP`、`force push`、`kubectl delete`）走命令守卫或人工执行
7. Agent 在容器里跑：只读根 + 仅项目目录可写 + 默认无网络，越权在文件系统层失败
8. 许可证与 SBOM 自动生成，白名单在 CI 里比对，合规结论交由法务

### 踩坑记录

```text
坑 1：以为删掉文件就等于清理了密钥
结论：密钥仍留在 git 历史里，任何人 clone 都能翻出来。
原因：git 历史不可变，删除只是新增一次提交。
解法：先轮换密钥（第一优先级），再用 git filter-repo 改写历史并 --force-with-lease 强推。

坑 2：为了跑通项目在 Agent 环境里开了 sudo
结论：Agent 一次误操作改了系统配置，影响整台开发机。
原因：把容器内的权限需求误当成宿主机需求。
解法：容器 + 非 root 用户 + 只读根；确实需要提权的操作由人工在容器外执行。

坑 3：CI 用 npm install 而不是 npm ci
结论：依赖树每次构建都可能漂移，投毒版本可能自动进入流水线。
原因：npm install 会按 semver 范围重新解析并可能改写 lockfile。
解法：CI 一律冻结安装（npm ci / --frozen-lockfile），lockfile 变化必须在 PR 里 review。

坑 4：让 Agent 直接执行清理脚本，脚本里 DELETE 漏掉了 WHERE
结论：整表数据被清空，只能靠备份恢复，业务中断数小时。
原因：破坏性 SQL 没有归档、没有行数校验、没有人工确认。
解法：归档 + 事务 + dry-run + 行数校验；删除语句必须由人 review，或由守卫脚本拦截。

坑 5：忽略 AGPL 类依赖，直到客户合规审计
结论：被迫在两周内替换核心依赖，排期被打乱。
原因：依赖引入时没有许可证门禁，AI 加包只看功能。
解法：CI 跑许可证白名单比对，AGPL/SSPL 默认禁止，例外需书面批准。

坑 6：把不可信的第三方仓库交给 Agent 在本机跑测试
结论：项目的 postinstall 脚本在宿主机执行，窃取了环境变量中的凭据。
原因：在主机上直接 npm install，安装脚本以当前用户权限运行。
解法：不可信代码先进容器（无网络、只读根），确认安全后再在本机操作。
```
