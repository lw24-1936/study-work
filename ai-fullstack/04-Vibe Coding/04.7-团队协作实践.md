## 概述

个人用 AI 写代码，瓶颈是能力；团队用 AI 写代码，瓶颈是**一致性**：同一个仓库，五个人的提示方式不同、规范文件不同、评审尺度不同，结果就是代码质量随作者波动，新人上手靠口口相传。解决路径只有一条——把一切都变成仓库里的文件：提示词、规范、评审清单、决策记录。资产化的东西才能被 review、被继承、被改进。

```text
团队协作的四个资产化对象：
1. 提示词与规范 —— prompts/ 与 AGENTS.md，进 git，随代码演进
2. 责任归属     —— 提交 trailer 与 CODEOWNERS，明确"谁签字谁负责"
3. 评审流程     —— PR 模板 + 风险分级 + 自动预评审
4. 知识沉淀     —— ADR、技能库、复盘记录，让经验可复用而不是口口相传
```

## 提示词与规范资产化

在个人场景里，提示词是一次性的对话；在团队场景里，提示词必须变成**有版本、有归属、可被引用的文件**。落地形态有三种：项目级约定（`AGENTS.md` / `CLAUDE.md`）、任务级提示模板（`prompts/` 目录）、能力级技能包（Skill，见技能篇章）。三种资产的分工是：约定回答「这个项目怎么做」，模板回答「这类任务怎么提」，技能回答「这套流程怎么复用」。

```text
# 推荐的目录结构（进 git，全部可 review）
AGENTS.md                     # 项目级唯一约定入口，其他工具软链接或兼容读取
prompts/
  prototype.md                # 一次性的快速原型提示模板
  spec-driven.md              # 生产代码的规格驱动模板
  refactor.md                 # 重构任务模板（含特征测试先行）
  review.md                   # 代码审查提示模板
docs/
  adr/                        # 架构决策记录
  runbooks/                   # 运维与故障处理手册
.claude/settings.json         # 团队共享权限（allow/ask/deny）
.cursor/rules/*.mdc           # 按文件作用域的规则（可选，与 AGENTS.md 不冲突）
.github/CODEOWNERS            # 责任归属
.github/PULL_REQUEST_TEMPLATE.md
```

```markdown
<!-- prompts/refactor.md：团队共用的重构提示模板，任何人直接引用 -->
# 重构任务提示模板

前置条件（缺一不可）：
- 已为该模块补齐特征测试，且当前全绿（粘贴测试命令与输出）
- 已建独立分支，基线提交：<sha>

任务：<一句话说明重构目标，例如"把 OrderService 按领域拆成三个类">

硬性约束：
- 只做移动与重命名，禁止改变任何行为（行为变更另开任务）
- 不新增依赖，不改公共 API 签名
- 一次只改一个调用点，每改一处提交一次

验收：
- 特征测试全绿
- 等价性测试（新旧实现随机对拍）全绿
- git diff --stat 显示只有移动与重命名，无逻辑变化
```

```shell
# 资产化后的检查动作：新增文件是否都进 git、模板是否能被找到
ls -la AGENTS.md prompts/ docs/adr/ 2>/dev/null
git add AGENTS.md prompts/ .github/
git commit -m "docs: 沉淀团队提示模板与评审流程资产"

# 让不同工具的约定入口指向同一份文件，避免多份规范漂移
```

用 CI 检查「约定资产是否被合规使用」，把资产化从倡议变成门禁。

```bash
#!/usr/bin/env bash
# docs_gate.sh：检查必需资产存在且被引用（放 CI 里跑）
set -uo pipefail
fail=0

require() {
  if [ -e "$1" ]; then echo "PASS 存在 $1"; else echo "FAIL 缺失 $1"; fail=1; fi

require .github/PULL_REQUEST_TEMPLATE.md

  if grep -q "$section" AGENTS.md; then
    echo "PASS AGENTS.md 含小节：$section"
  else
    echo "FAIL AGENTS.md 缺少小节：$section"
    fail=1
  fi
done

exit "$fail"
```

## 代码归属与责任划分

AI 不承担责任，所以**提交者与评审者必须承担**。团队需要明确三条：谁提交谁负责（AI 产出不豁免责任）、谁评审谁签字（高风险路径必须由 CODEOWNERS 指定的人评审）、以及**AI 参与度要可追溯**。可追溯的意义不止合规：它让评审者知道该抽查多深，也让事后复盘能定位「是提示词问题还是评审问题」。落地手段是提交信息 trailer 与 CODEOWNERS 分层。

```text
# Conventional Commits + trailer 示例（Assisted-by 记录 AI 参与）
feat(orders): 支持取消未发货订单

- Order 增加 cancel()，已发货抛 IllegalState
- cancel 幂等：重复调用不重复落库

Assisted-by: codex-cli
Reviewed-by: @alice
Baseline: 3f9c1a2
```

```shell
# 强制 trailer：commit-msg 钩子校验（本地）
cat > .git/hooks/commit-msg <<'HOOK'
#!/usr/bin/env bash
# 校验提交信息符合 Conventional Commits；若声明了 AI 参与则必须带 Assisted-by
set -euo pipefail
msg_file="$1"
head_line="$(head -1 "$msg_file")"

if ! grep -qE '^(feat|fix|docs|refactor|test|chore|perf|build|ci)(\(.+\))?: .{4,}' <<<"$head_line"; then
  echo "提交信息不符合 Conventional Commits：$head_line"
  exit 1
fi

if grep -qiE 'ai[- ]?(generated|assisted)|copilot|codex|claude|opencode' "$msg_file"; then
  grep -q '^Assisted-by: ' "$msg_file" || {
    echo "声明了 AI 参与，必须补 Assisted-by: <工具名>"
    exit 1
  }
fi
exit 0
HOOK
chmod +x .git/hooks/commit-msg

# 验证钩子生效（应失败）
git commit --allow-empty -m "改了点东西"
# 提交信息不符合 Conventional Commits：改了点东西
```

```text
# .github/CODEOWNERS：按风险分级，把签字责任落到人
# 高风险：任何改动必须由对应团队人工评审，且禁止无人评审自动合并
src/billing/            @payments-team
src/auth/               @security-team
migrations/             @dba-team
infra/terraform/        @platform-team

# 中风险：至少一人评审，可以是相邻团队
src/api/                @backend-team
src/domain/             @backend-team

# 低风险：AI 预评审 + 抽样人工
src/components/         @frontend-team
docs/                   @frontend-team
```

```shell
# 校验 CODEOWNERS 是否覆盖了关键目录（本地粗查）
for d in src/billing src/auth migrations src/api; do
  grep -q "^$d/" .github/CODEOWNERS && echo "PASS 有归属：$d" || echo "FAIL 无归属：$d"
done

# 用 gh 校验语法与匹配情况（需要仓库权限）
gh api repos/{owner}/{repo}/codeowners/errors
```

## 评审流程调整

AI 让提交量上升、单次改动变大，传统的「小 PR 慢评审」流程会堵死在评审环节。调整方向有四条：**自动预评审先跑**（用非交互模式出第一轮意见，人只看语义）、**按风险分级设置评审深度**（低风险抽样、高风险逐行）、**给 PR 规模设上限**（超限自动要求拆分）、**用清单代替自由发挥**（评审者按清单核对，减少漏项）。

```text
# 评审深度分级（团队共识，写进 CONTRIBUTING.md）
一级（低风险：样式、文案、组件）
  自动预评审 + 一人抽查 10 分钟，关注：是否引入无关改动
二级（中风险：业务逻辑、接口）
  自动预评审 + 至少一人完整评审，关注：边界、错误处理、测试有效性
三级（高风险：资金、鉴权、迁移、基础设施）
  CODEOWNERS 指定两人评审，逐行读，必须贴真实验证输出，必须有人工设计说明
```

用脚本给 PR 规模设红线，超过阈值直接要求拆分。

```bash
#!/usr/bin/env bash
# pr_size_gate.sh：PR 规模门禁（本地或 CI 均可）
set -uo pipefail
base="${1:-origin/main}"
files=$(git diff --name-only "$base"...HEAD | wc -l)
lines=$(git diff --numstat "$base"...HEAD | awk '{a+=$1; d+=$2} END {print a+d+0}')
risky=$(git diff --name-only "$base"...HEAD | grep -cE '^(src/billing|src/auth|migrations|infra/terraform)/' || true)

echo "files=$files lines=$lines risky_files=$risky"

status=0
if [ "$lines" -gt 600 ] && [ "$risky" -eq 0 ]; then
  echo "要求拆分：非高风险改动超过 600 行"
  status=1
fi
if [ "$risky" -gt 0 ] && [ "$lines" -gt 300 ]; then
  echo "要求拆分：高风险路径改动超过 300 行（三级评审必须小步）"
  status=1
fi
exit "$status"
```

```shell
chmod +x scripts/pr_size_gate.sh
./scripts/pr_size_gate.sh origin/main
# files=9 lines=486 risky_files=0      -> 通过
# files=22 lines=1180 risky_files=2    -> 要求拆分
```

把「AI 预评审」作为评审前的固定步骤（详见质量保障篇的 `ai_pr_review.sh`），评审者的时间只花在语义判断上。

```shell
# 提交 PR 前的固定动作：本地先跑自动预评审并把结论贴进描述
./scripts/ai_pr_review.sh origin/main > /tmp/review.md
gh pr create --title "feat(orders): 支持取消未发货订单" \
             --body-file /tmp/review.md
```

## 知识沉淀与复用

团队最贵的资产是「踩过的坑」与「做过一次的决策」，而这两样在 AI 场景下损失得更快——因为新人可以让 AI 重新生成一遍错误方案。沉淀方式是三个轻量载体：**ADR**（记录为什么这样选）、**技能库**（把可复用流程固化成 Skill）、**复盘记录**（记录事故与教训）。它们要满足两个条件才有用：放在仓库里、有模板且简短（超过两屏没人读）。

```markdown
<!-- docs/adr/0007-ai-generated-code-review-policy.md：架构决策记录模板 -->
# ADR-0007：AI 参与代码的评审策略

- 状态：已接受
- 日期：2026-10-14
- 决策者：backend-team

## 背景
团队 8 人中 7 人日常使用 AI 编码工具，提交量与单次改动规模上升，评审成为瓶颈，
且出现两次「测试全绿但逻辑错误」的合并事故。

## 决策
1. 所有提交必须声明 AI 参与度（Assisted-by trailer）
2. 高风险路径（billing/auth/migrations）强制两人评审并逐行读
3. CI 增加变异冒烟与无断言测试扫描，作为合并必要条件
4. 非高风险 PR 超过 600 行自动要求拆分

## 后果
- 正面：评审聚焦语义，缺陷逃逸率下降
- 负面：单次交付周期平均增加半天（拆分与验证的成本）
- 需要重新评估的触发条件：缺陷逃逸率连续两个月为 0 时可放宽第 4 条
```

```shell
# 沉淀为技能（Skill）：把可复用流程变成可被 Agent 自动加载的能力包
mkdir -p ~/.hermes/skills/ai-code-review
cat > ~/.hermes/skills/ai-code-review/SKILL.md <<'MD'
---
name: ai-code-review
description: Use when reviewing an AI-generated PR. Runs the team checklist.
---

# AI 代码评审清单

按顺序检查，发现阻断级问题立即停止并把结论写进 PR：

1. 错误处理：是否存在 except: pass / 静默返回成功
2. 边界：空值、越界、并发、时区
3. 测试有效性：断言是否复刻实现（复刻即无效）
4. 依赖：是否有未申报新增；锁文件是否变化
5. 安全：密钥、字符串拼接 SQL、日志含敏感字段
6. 数据：是否有不可逆操作缺备份与回滚
MD

# 验证技能被发现（具体命令以你所用工具的官方文档为准）
ls -la ~/.hermes/skills/ai-code-review/SKILL.md
```

```text
# 沉淀的三个判断标准（不满足就别写文档）
1. 是否会被重复问？只有一次的问题写进对话，会重复的写进仓库
2. 是否可执行？能变成命令、脚本或清单的，就不要写成散文
3. 是否有归属与保鲜期？每个资产标注负责人与复核周期
```

## 度量与持续改进

没有度量，协作实践会退化成口号。团队场景只需要关注少量指标，且这些指标都能从 git 与 CI 里自动算出来，不需要额外埋点：**提交规模**（粒度是否失控）、**回退率**（质量是否下滑）、**评审延迟**（流程是否堵塞）、**测试与实现的比例**（是否真的在测试先行）。这些指标只用于发现问题，不要用来给人打分——一旦用于考核，数据必然失真。

```bash
#!/usr/bin/env bash
# team_metrics.sh：从 git 计算团队协作指标（最近 30 天）
set -uo pipefail

SINCE="30 days ago"

echo "== 提交规模分布（改动行数）=="
git log --since="$SINCE" --pretty=tformat: --numstat \
 | awk '{s+=$1+$2; n++} END {printf "commits=%d avg_lines=%.1f\n", n, (n?s/n:0)}'

echo "== 单次提交超过 500 行的比例 =="
git log --since="$SINCE" --pretty=format:'%h' --numstat \
 | awk '/^[0-9a-f]{7,}/{if(t>500)big++; t=0; c++} /^[0-9]/{t+=$1+$2} END \
        {printf "commits=%d big=%d ratio=%.1f%%\n", c, big, (c?100*big/c:0)}'

echo "== 回退/修复类提交占比（质量信号）=="
total=$(git log --since="$SINCE" --oneline | wc -l)
fixes=$(git log --since="$SINCE" --oneline --grep='^fix' -i | wc -l)
reverts=$(git log --since="$SINCE" --oneline --grep='^revert' -i | wc -l)
echo "total=$total fix=$fixes revert=$reverts"

echo "== 测试同改比例（测试先行的粗信号）=="
with_tests=0
with_src=0
for sha in $(git log --since="$SINCE" --pretty=format:'%h'); do
  files=$(git show --pretty=tformat: --name-only "$sha")
  echo "$files" | grep -qE '(^|/)(tests?|__tests__)/|\.test\.|_test\.' && with_tests=$((with_tests+1))
  echo "$files" | grep -qE '^src/' && with_src=$((with_src+1))
done
echo "commits_touching_src=$with_src commits_touching_tests=$with_tests"
if [ "$with_src" -gt 0 ]; then
  awk -v a="$with_tests" -v b="$with_src" 'BEGIN{printf "test_ratio=%.1f%%\n", 100*a/b}'
fi
```

```shell
chmod +x scripts/team_metrics.sh
./scripts/team_metrics.sh
# commits=142 avg_lines=118.3
# commits=142 big=7 ratio=4.9%
# total=142 fix=31 revert=3
# commits_touching_src=88 commits_touching_tests=57
# test_ratio=64.8%
```

```text
# 指标读法与行动（只用于发现问题，不用于考核）
avg_lines 持续上升        -> 粒度失控，收紧 PR 规模门禁
big ratio > 10%           -> 强制拆分，检查是否有人绕过了清单
revert 出现且成因是评审漏项 -> 补评审清单条目，而不是追责个人
test_ratio 长期 < 50%     -> 测试先行没落地，检查是否存在"实现测试同轮生成"
fix 占比 > 40%            -> 需求理解或验证环节有系统性缺口，回看复盘记录
```

## 应用场景实战

### 场景一：给一个 20 人团队落地 AI 协作规范（含仓库资产与技术手段）

需求：团队 20 人、6 个服务仓库、刚开始大规模用 AI 编码，出现三类问题：规范不统一、评审积压、事故复盘无记录。目标是在两周内建立可执行的最小体系。

```bash
#!/usr/bin/env bash
# roll_out_ai_practice.sh：把资产铺到当前仓库（幂等，可重复执行）
set -euo pipefail

echo "1) 建目录"
mkdir -p prompts docs/adr docs/runbooks scripts .github

echo "2) 项目约定（唯一入口）"
if [ ! -f AGENTS.md ]; then
  cat > AGENTS.md <<'MD'
# 项目约定

## 技术栈
<填写语言与版本、包管理器、测试框架>

## 常用命令
- 安装：<命令>
- 检查：<命令>
- 测试：<命令>

## 禁止事项
- 不修改 migrations/ 与 src/billing/、src/auth/
- 不写任何密钥，使用环境变量
- 不新增依赖，除非在 PR 描述里说明理由
MD
fi

echo "3) PR 模板"
[ -f .github/PULL_REQUEST_TEMPLATE.md ] || cat > .github/PULL_REQUEST_TEMPLATE.md <<'MD'
## 本次改动
- 一句话说明：
- AI 参与度：（全部由 AI 生成 / AI 起草 + 人工修改 / 人工手写）
- 基线提交：

## 验证（贴真实输出）
- [ ] 测试通过
- [ ] 类型检查通过
- [ ] 静态检查零新增告警

## 评审重点
- [ ] 错误处理无静默吞噬
- [ ] 边界（空值/越界/并发/时区）已考虑
- [ ] 无未申报新依赖
- [ ] 无密钥与敏感日志
- [ ] 测试断言不是实现复刻
MD

echo "4) CODEOWNERS（按你的真实团队填写）"
[ -f .github/CODEOWNERS ] || cat > .github/CODEOWNERS <<'TXT'
# 高风险：人工逐行评审
src/billing/     @payments-team
src/auth/        @security-team
migrations/      @dba-team
# 低风险：AI 预评审 + 抽样
src/components/  @frontend-team
TXT

echo "5) 提交并推一个示例 PR 流程"
git add AGENTS.md .github prompts docs scripts
git status --short
git commit -m "chore: 落地 AI 协作规范资产（约定/PR 模板/CODEOWNERS）"
```

```shell
chmod +x roll_out_ai_practice.sh
./roll_out_ai_practice.sh

# 两周后的检查：资产是否真的被用起来
git log --oneline --since='14 days ago' -- .github/ AGENTS.md prompts/ docs/adr/ | wc -l
ls docs/adr/ | wc -l
./scripts/team_metrics.sh
```

### 场景二：事故复盘后把教训转成可执行资产

需求：一次 AI 生成的数据导出接口在生产上把内存打满（一次性加载全表），服务重启。要求：复盘不只是写检讨，而是产出**能阻止同类问题再发生的资产**。

```python
# tests/perf/test_export_memory.py：把"峰值内存"变成可断言的验收条件
# 依赖：pip install psutil --index-url https://pypi.tuna.tsinghua.edu.cn/simple
import subprocess
import sys
import time

import psutil
import requests

BASE = "http://127.0.0.1:8000"
LIMIT_MB = 300


def test_export_streaming_memory():
    proc = next(
        (p for p in psutil.process_iter(["cmdline"]) if p.info["cmdline"]
         and any("app.main:app" in c for c in p.info["cmdline"])),
        None,
    )
    assert proc is not None, "未找到被测服务进程"

    t0 = time.time()
    with requests.get(f"{BASE}/orders/export", stream=True, timeout=300) as resp:
        assert resp.status_code == 200
        peak = 0
        for _ in resp.iter_content(chunk_size=65536):
            peak = max(peak, proc.memory_info().rss)
    peak_mb = peak / 1024 / 1024
    print(f"peak_rss={peak_mb:.1f}MB elapsed={time.time() - t0:.1f}s")
    assert peak_mb < LIMIT_MB, f"峰值内存超限：{peak_mb:.1f}MB >= {LIMIT_MB}MB"


if __name__ == "__main__":
    test_export_streaming_memory()
    sys.exit(0)
```

## 最佳实践与踩坑记录

### 最佳实践

1. 约定只维护一份（AGENTS.md），其他工具通过软链接或原生兼容机制指向它，CI 检查必需小节是否存在
2. 提示词模板进 git、按任务类型分文件、每份带「前置条件 / 约束 / 验收」三段
3. 提交必须可追溯 AI 参与度（Assisted-by trailer），用 commit-msg 钩子强制校验
4. CODEOWNERS 按风险分级，高风险路径禁止无人评审自动合并
5. PR 规模设红线并按风险区分阈值（高风险更小），超限自动要求拆分
6. 自动预评审作为人评审的前置步骤，把人类时间集中到语义判断
7. 复盘必须产出可执行资产（脚本、清单条目、模板条款、告警），而不是承诺
8. 度量只用少量可从 git/CI 自动计算的指标，且只用于改进流程，不用于个人考核

### 踩坑记录

```text
坑 1：规范写在 Wiki 里，没人看也没人改
结论：仓库里的实际行为与 Wiki 描述脱节，新人照着 Wiki 做反而出错。
原因：Wiki 不在代码评审路径上，无法随代码演进被更新。
解法：规范进仓库（AGENTS.md / prompts/），改动走 PR，CI 校验必要小节存在。

坑 2：把 AI 产出的问题算在"工具头上"
结论：事故复盘变成争论"是不是 AI 写的"，无人对修复负责。
原因：没有责任归属机制，提交者以为 AI 生成就不算自己写的。
解法：明确「谁提交谁负责」，Assisted-by 只记录参与度，不转移责任。

坑 3：为了压低评审压力，直接自动合并低风险 PR
结论：低风险路径里也混进了接口契约变更，破坏了上游调用方。
原因：风险分级靠目录划分，而目录划分与真实风险不完全一致。
解法：分级加入"改动类型"维度（是否改公共 API/配置/依赖），契约类改动一律升级评审。

坑 4：把度量指标用于个人考核
结论：数据迅速失真（拆分提交、改写历史、回避高风险任务）。
原因：指标与激励绑定后，人必然优化指标而不是优化结果。
解法：指标只用于流程改进，看趋势不看个人，且只在团队层面通报。

坑 5：技能库与提示模板只建不管，半年后全是过时内容
结论：Agent 按过期模板产出，比没有模板更糟。
原因：没有归属与复核周期，资产腐烂无人察觉。
解法：每个资产标注负责人与复核周期（建议季度），把复核写进团队例行事项。

坑 6：不同人用不同工具，规则文件各写一份
结论：同一仓库的 AI 行为不一致，评审标准也无法统一。
原因：每个工具默认读取自己的规则文件，团队没有指定唯一来源。
解法：以 AGENTS.md 为唯一事实来源，其他工具用软链接或原生兼容读取（如 Cursor 也读 AGENTS.md/CLAUDE.md）。
```
