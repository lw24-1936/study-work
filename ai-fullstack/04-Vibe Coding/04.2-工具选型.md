## 概述

AI 编码工具已经分成两条主线：**编辑器类**（Cursor、Windsurf）把 AI 嵌进 IDE，强在交互与可视化 diff；**终端类**（Claude Code、Codex CLI、OpenCode、Pi）把 Agent 放进 shell，强在可脚本化、可编排、可进 CI。第三类**本地模型方案**（Ollama 等）解决的是数据不出内网与成本可控的问题，代价是长链路任务的稳定性下降。选型不是挑最强的那个，而是按任务类型组合。

```text
选型的三条轴：
1. 交互位置 —— 编辑器内（可视化、适合手写+补全）还是终端内（可脚本化、适合批处理）
2. 自主程度 —— 补全/问答、单轮编辑、多轮 Agent、可进 CI 的非交互模式
3. 运行位置 —— 云 API（能力最强）还是本地模型（数据不出内网、成本固定）
```

## 工具分类与选型维度

把这几个工具放在同一张表上比，比逐个看宣传材料有效。三个维度最影响日常体感：**上下文怎么进去**（规则文件、自动检索还是手动 @ 引用）、**权限怎么管**（沙箱、审批弹窗、allow/ask/deny 规则）、**能不能非交互跑**（能不能进 CI 与脚本）。前两项决定日常体验，第三项决定它能不能进入工程流水线。

```text
按任务类型的第一刀：
- 手写为主、AI 补全为辅 -> 编辑器类
- 需求驱动、一次改多文件 -> 终端类 Agent
- 数据不能出内网 -> 本地模型 + 终端类 Agent
- 要进 CI、要批量跑 -> 必须有非交互模式（-p / exec / run）
```

## 编辑器类工具 Cursor 与 Windsurf

编辑器类工具把模型放在「写代码的现场」：光标位置、打开的文件、最近的 diff 都是天然上下文，因此补全与局部重构体验最好。它们的定制入口都是**可版本化的规则文件**，而不是藏在设置面板里的一次性配置——这一点很重要，它让团队规范可以随代码一起 review。两者的规则机制在激活方式上高度相似，都是「常驻 / 模型自判 / 按文件匹配 / 手动引用」四档。

Cursor 的项目规则放在 `.cursor/rules/`，用 `.mdc` 扩展名并带 frontmatter；它同时读取 `AGENTS.md` 与 `CLAUDE.md`，适合已有其他 Agent 的项目共用一份约定。Windsurf 的规则放在工作区 `.windsurf/rules/*.md`（新版文档已迁移到 `.devin/rules/*.md`，以官方文档为准），全局规则是单文件且有条数上限；每条规则通过 `trigger` 字段声明 `always_on` / `model_decision` / `glob` / `manual` 四种激活方式。

```text
# .cursor/rules/api-validation.mdc：只在写接口文件时激活
---
description: 接口入参校验规范
globs: [src/api/**/*.ts]
alwaysApply: false
---

- 所有入参使用 zod schema 校验，schema 与类型同源（z.infer）
- 校验失败返回 400 + { code, message }，不要抛原始 ZodError
- 新增接口必须在 src/api/__tests__ 下补一条失败路径用例
```

```text
# .windsurf/rules/tests.md：按文件匹配激活（旧版 .windsurf 目录，新版为 .devin/rules）
---
trigger: glob
globs: **/*.test.ts
---

- 测试使用 describe/it 结构，禁止 it.skip 提交
- 外部 HTTP 调用一律 mock，不打真实网络
- 每个测试文件必须至少包含一条失败路径断言
```

```shell
# 校验规则文件是否会被工具读取到：列出目录与文件
ls -la .cursor/rules/ 2>/dev/null || echo "无 Cursor 项目规则"
ls -la .windsurf/rules/ 2>/dev/null || echo "无 Windsurf 项目规则"
ls -la .devin/rules/ 2>/dev/null || echo "无 Devin 工作区规则"

# 规则文件是否已纳入版本控制（团队共享的前提）
git ls-files .cursor/rules .windsurf/rules .devin/rules
```

## 终端类工具 Claude Code Codex OpenCode Pi

终端类工具的共同特征是：在项目根目录启动，自己读写文件、执行命令、跑测试，然后汇报结果。差异主要在**定制机制**与**是否内置权限体系**。它们的项目级约定文件基本收敛到 `AGENTS.md`（Codex 用 `/init` 生成，OpenCode 用 `/init` 生成，Pi 从 `~/.pi/agent/`、父目录与当前目录逐层加载），Claude Code 使用 `CLAUDE.md`。

各工具的关键路径：

| 工具 | 安装方式（官方） | 项目约定 | 权限与沙箱 | 非交互模式 |
| --- | --- | --- | --- | --- |
| Claude Code | `curl -fsSL https://claude.ai/install.sh \| bash` | `CLAUDE.md` | `.claude/settings.json` 的 allow/ask/deny + 沙箱 | `claude -p "..."` |
| Codex CLI | `curl -fsSL https://chatgpt.com/codex/install.sh \| sh` | `AGENTS.md`（`/init`） | `/permissions` 审批模式 + 沙箱与可写根目录 | `codex exec "..."` |
| OpenCode | `curl -fsSL https://opencode.ai/install \| bash` 或 `npm i -g opencode-ai` | `AGENTS.md`（`/init`） | 配置文件中声明权限；Plan 模式禁用写入 | `opencode run "..."` |
| Pi | `npm install -g @mariozechner/pi-coding-agent` | `AGENTS.md` + `SYSTEM.md` | 不内置弹窗，建议在容器内运行 | `pi -p "..."` |

Pi 的设计取向值得单独说明：它刻意不做 MCP、子代理、Plan 模式、权限弹窗与内置 todo，把这些留给 TypeScript 扩展或第三方包，官方给出的理由是「保持核心最小、让使用者组装工作流」。因此 Pi 更适合愿意自己写扩展、或者在容器里裸跑的用户，而不是开箱即用的团队。

```shell
# Claude Code：安装、验证、查看诊断信息
curl -fsSL https://claude.ai/install.sh | bash
claude --version
claude doctor

# Codex CLI：安装后初始化项目约定
curl -fsSL https://chatgpt.com/codex/install.sh | sh
codex --help

# OpenCode：用脚本安装
curl -fsSL https://opencode.ai/install | bash
opencode --version

# Pi：通过 npm 全局安装
npm install -g @mariozechner/pi-coding-agent
pi --version
```

权限收敛是终端类工具上生产前的必做项。Claude Code 用 JSON 规则表达「什么不用问」，Codex 用审批模式选择粒度，OpenCode 在配置里声明。

```json
// .claude/settings.json：团队共享项目设置（提交进 git，队友默认继承）
{
  "permissions": {
    "allow": [
      "Bash(npm test:*)",
      "Bash(npm run lint:*)",
      "Bash(git status)",
      "Bash(git diff:*)"
    ],
    "ask": [
      "Bash(git push:*)",
      "Bash(npm install:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(rm -rf:*)",
      "Bash(curl:* | bash)"
    ]
  }
}
```

```text
设置优先级（Claude Code，官方文档）：托管设置 > 项目共享 .claude/settings.json
> 项目本地 .claude/settings.local.json > 用户 ~/.claude/settings.json。
团队规范放「项目共享」，个人偏好放「项目本地」，安全红线放「托管设置」。
```

## 本地模型方案

本地模型的动机有三个：数据不出内网、成本可预测、离线可用。代价同样明确：在长链路 Agent 任务（多文件改造、需要反复跑测试纠错）上，本地中等规模模型的稳定性显著低于云上大模型，常见表现是提前宣布完成、循环重复同一次修改、或在工具调用格式上出错。可行的组合是「本地模型做补全、摘要、简单重命名，云模型做多文件改造」。

Ollama 是最省事的本地运行时：`ollama pull` 拉模型、`ollama run` 交互、默认在 `http://localhost:11434` 暴露 API，并提供 OpenAI 兼容端点 `/v1/chat/completions`，因此支持 OpenAI 协议的 Agent 可以直接接。它还能用 `ollama launch claude|codex|opencode` 把已装好的编码 Agent 直接切到本地模型。

```shell
# 安装并启动（Linux 上 Ollama 服务默认监听 127.0.0.1:11434）
curl -fsSL https://ollama.com/install.sh | sh
ollama --version

# 拉取并运行一个模型（模型体积与显存需求以官方模型页为准）
ollama pull qwen3-coder
ollama run qwen3-coder

# 用 OpenAI 兼容接口验证服务可用（不要打印任何密钥）
curl -s http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3-coder",
    "messages": [{"role": "user", "content": "用一句话说明什么是依赖注入"}]
  }' | jq -r '.choices[0].message.content'

# 把终端类 Agent 切到本地模型
ollama launch opencode
```

```text
本地部署前必查的四项：
1. 显存/统一内存是否够放模型与上下文（上下文越长占用越多，超出会退化到内存并变慢）
2. 驱动是否可用：nvidia-smi 能正常输出，否则先修驱动再谈部署
3. 工具调用（tool calling）能力：Agent 依赖它，能力弱的模型会频繁格式错误
4. 上下文窗口：至少 32K 起步，多文件改造场景建议更高，以模型卡为准
```

本机 GPU 自检脚本（把「能不能跑」变成一条命令）：

```bash
#!/usr/bin/env bash
# gpu_check.sh：本地大模型前置检查
set -u

echo "== 1. GPU 设备与驱动 =="
if command -v nvidia-smi >/dev/null 2>&1; then
  nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv || \
    echo "nvidia-smi 执行失败：驱动与内核模块可能不匹配（本机即为此情况）"
else
  echo "未安装 nvidia-smi"
fi

echo "== 2. 设备节点 =="
ls /dev/nvidia* 2>/dev/null || echo "无 /dev/nvidia* 设备节点"

echo "== 3. 内存与 CPU =="
free -h | head -2
nproc

echo "== 4. Ollama 服务 =="
curl -s -o /dev/null -w "ollama http_status=%{http_code}\n" http://127.0.0.1:11434/api/tags \
  || echo "Ollama 未运行"
```

```text
# 本机实测结果（Ubuntu 24.04）
/dev/nvidia0 等设备节点存在，但 nvidia-smi 报：
  Failed to initialize NVML: Driver/library version mismatch
  NVML library version: 580.178
结论：本机当前状态下不适合直接跑 GPU 推理，需先修复驱动/内核模块版本；
      驱动修复步骤见 NVIDIA 驱动修复相关主题，不在本篇范围内。
```

## 选型对比与组合使用

把工具按「任务生命周期」组合，比强行统一成一个更实用：探索阶段用编辑器类（当天就能上手、可视化 diff 降低误改风险），实现阶段用终端类 Agent（一次改多文件、可跑测试自纠），流水线阶段只用有非交互模式的工具。团队层面还要加一条硬约束：**选一个规则文件位置**（`AGENTS.md` 优先，兼容性最好），别让 Cursor、Windsurf、Claude Code 各维护一份互相漂移的规范。

| 需求 | 首选 | 原因 |
| --- | --- | --- |
| 逐行补全、局部重构 | 编辑器类 | 光标上下文最全，延迟低 |
| 不熟代码库的探索 | 编辑器类 + 终端类只读提问 | 可视化引用、便于人工核对 |
| 一次改动多文件 + 跑测试 | 终端类 Agent | 有命令执行与自纠循环 |
| 进 CI 做自动评审 | Codex CLI / Claude Code 非交互模式 | 有 exec / -p 等非交互入口 |
| 跑批量脚本、定时任务 | 终端类非交互 + JSON 输出 | 便于被脚本与调度器驱动 |
| 数据不得出内网 | 本地模型 + 终端类 Agent | 全链路本地，代价是稳定性 |
| 需要自建工作流 | Pi + TypeScript 扩展 | 核心最小、扩展自由度最高 |

统一约定文件的最小落地形态：

```markdown
<!-- AGENTS.md：多工具共用的第一优先级约定 -->
# 项目约定

## 技术栈
- Node 22 + TypeScript 5，包管理用 pnpm（禁止 npm install 提交 lockfile 变更）
- 测试用 vitest，命令：pnpm test

## 常用命令
- 安装：pnpm install --frozen-lockfile
- 检查：pnpm lint && pnpm typecheck
- 测试：pnpm test -- --run

## 禁止事项
- 不要修改 migrations/ 与 src/billing/ 下的代码
- 不要在代码或注释里写任何密钥，用环境变量
- 不要新增依赖，除非在 PR 描述里说明理由
```

```shell
# 让多个工具指向同一份约定：软链接而不是复制，避免内容漂移
ln -sf AGENTS.md CLAUDE.md

# 校验链接与文件确实存在
ls -l AGENTS.md CLAUDE.md
git add AGENTS.md CLAUDE.md
git commit -m "docs: 统一 AI 编码工具的项目约定入口"
```

## 应用场景实战

### 场景一：为一个 8 人团队落地「编辑器 + 终端 + CI」三层工具链

需求：前端团队 8 人，代码库 12 万行 TypeScript，需要通过安全评审（禁止把源码整仓上传给未经批准的模型），且要求 PR 必须有自动评审。方案：日常用 Cursor 写码，多文件改造用终端类 Agent，PR 自动评审放进 CI 用非交互模式。

```yaml
# .github/workflows/ai-review.yml：PR 自动评审（非交互模式，需配置 API Key 到仓库 Secrets）
name: AI Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0          # 需要完整历史才能算 diff 基准

      - name: 安装 Codex CLI
        run: curl -fsSL https://chatgpt.com/codex/install.sh | sh

      - name: 生成 diff 供评审
        run: git diff origin/${{ github.base_ref }}...HEAD > /tmp/pr.diff

      - name: 非交互评审
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
        run: |
          # 只读评审：把 diff 交给模型，输出结构化结论，不改工作区
          codex exec "阅读 /tmp/pr.diff，按以下格式输出：\
          1) 阻断级问题（安全、数据丢失、并发）2) 建议级问题 3) 测试缺口。\
          不要修改任何文件。" > /tmp/review.md

      - name: 回贴到 PR
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh pr comment ${{ github.event.pull_request.number }} --body-file /tmp/review.md
```

```shell
# 本地验证同样的流程（不依赖 CI）
git fetch origin main
git diff origin/main...HEAD > /tmp/pr.diff
wc -l /tmp/pr.diff
codex exec "阅读 /tmp/pr.diff，列出阻断级问题与测试缺口，不要改文件"
```

### 场景二：内网环境用本地模型跑编码 Agent

需求：一家金融机构的内网开发机不能访问公网 API，需要可用的编码 Agent。方案：Ollama + OpenCode，全部本地；并写一个启动检查脚本，把「驱动是否正常、模型是否就位、服务是否可达」固化成流水线的一步。

```bash
#!/usr/bin/env bash
# local_agent_up.sh：内网编码 Agent 启动前置检查
set -euo pipefail

MODEL="${MODEL:-qwen3-coder}"
HOST="${OLLAMA_HOST:-http://127.0.0.1:11434}"

echo "1) 检查 Ollama 服务"
curl -sf "$HOST/api/tags" >/dev/null || { echo "Ollama 未就绪：先执行 ollama serve"; exit 1; }

echo "2) 检查模型已在本地"
ollama list | awk 'NR==1 || $1 ~ /'"${MODEL%%:*}"'/' | grep -q "$MODEL" \
  || { echo "缺少模型：ollama pull $MODEL"; exit 1; }

echo "3) 冒烟测试：一次工具调用能力探测"
RESP=$(curl -s "$HOST/v1/chat/completions" -H 'Content-Type: application/json' -d '{
  "model": "'"$MODEL"'",
  "messages": [{"role": "user", "content": "只回复两个字：就绪"}]
}')
echo "$RESP" | jq -r '.choices[0].message.content'
echo "$RESP" | jq -e '.choices[0].message.content | length > 0' >/dev/null \
  || { echo "模型响应异常，需检查模型是否支持当前 prompt 模板"; exit 1; }

echo "4) 启动 OpenCode（本地模型）"
exec ollama launch opencode
```

```shell
chmod +x local_agent_up.sh
./local_agent_up.sh
```

## 最佳实践与踩坑记录

### 最佳实践

1. 项目约定只维护一份，首选 `AGENTS.md`，其他工具用软链接或原生兼容机制指向它，杜绝多份规则漂移
2. 规则文件必须进 git，随代码一起被 review；藏在本地设置里的规范等于没有规范
3. 先跑 `--version` 与官方诊断命令（如 `claude doctor`）确认安装健康，再排查使用问题
4. 权限规则先只读后放行：`allow` 从测试与 lint 命令开始，写操作与安装类命令保留 `ask`
5. 团队统一口径：密钥、密钥路径与 `rm -rf` 类命令写进 `deny`，不依赖个人自觉
6. 本地模型只用于数据不出内网的场景，并在启用前跑一次工具调用能力冒烟测试
7. 价格、额度与模型可用性随时在变，做决策时看官方定价页与文档，不看二手总结

### 踩坑记录

```text
坑 1：Cursor、Windsurf、Claude Code 各维护一份规范，三份内容互相矛盾
结论：同一个仓库里 AI 的行为时好时坏，新同学不知道该信哪份。
原因：每个工具都有自己默认的规则位置，团队没有指定唯一入口。
解法：以 AGENTS.md 为唯一入口，其他文件软链接过去，并在 CI 里检查一致性。

坑 2：把本地模型当作云模型的等价替代
结论：简单改动能跑，多文件改造频繁提前宣布完成或陷入重复修改，效率反而更低。
原因：中小参数模型在长链路工具调用上稳定性差，容易出现格式错误与自我纠偏失败。
解法：本地模型做补全与摘要，多文件改造走云模型；如必须全本地，缩小任务粒度。

坑 3：CI 里用交互模式跑 Agent，Job 挂死到超时
结论：流水线经常卡到 6 小时上限被强杀，账单还照付。
原因：交互式 Agent 等待人类输入，无人应答就一直等。
解法：CI 只用非交互入口（codex exec / claude -p / pi -p），并设置显式超时与只读权限。

坑 4：安装脚本直连失败被误判为工具故障
结论：curl | bash 卡住或超时，以为工具挂了。
原因：网络受限（本机 github.com 直连被限速是常见情况），不是工具问题。
解法：先单独执行 curl 确认可达性，必要时用镜像源；npm 类安装加国内镜像参数。

坑 5：把 API Key 写进工具配置文件并提交
结论：密钥进 git 历史，只能全部轮换。
原因：配置示例里常见明文 Key，照抄即中招。
解法：统一用环境变量或系统密钥环，CI 用 Secrets；提交前用 gitleaks 类工具扫描。
```
