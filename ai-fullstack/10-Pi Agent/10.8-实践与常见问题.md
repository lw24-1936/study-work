## 概述

Pi 的问题大体分三类：**凭据类**（模型不出现、调用直接失败）、**上下文类**（压缩触发、历史丢失、成本飙升）、**集成类**（无人值守时项目资源不生效、MCP 连不上）。这三类的排查入口各不相同，但都能用几个稳定的命令把范围缩小到一层。

这一篇把「怎么问出根因」和「怎么调参」放在一起：先给出报错到原因的对照与诊断命令，再给压缩、成本、性能三组可调参数与推荐取值，最后是无人值守场景的安全落地方式与一份使用建议清单。

```text
本篇要解决的问题：
1. 常见报错分别对应哪一层问题，第一条诊断命令该跑什么
2. 自动压缩什么时候触发、保留多少、怎么按模型单独调
3. 成本花在哪、提示缓存怎么开、哪些设置会悄悄让成本翻倍
4. 响应速度与交互体验相关的参数与快捷键
5. 无界面/无人值守场景下必须显式处理的安全与信任项
6. 一份可以直接贴到团队规范里的使用建议清单
```

本篇命令与实际输出以本机安装的 `@earendil-works/pi-coding-agent@1.2.0` 实测为准（`pi --version` 输出 `1.2.0`）；官方文档见 `https://pi.dev/docs/latest/compaction`、`https://pi.dev/docs/latest/settings`、`https://pi.dev/docs/latest/environment-variables`、`https://pi.dev/docs/latest/security`、`https://pi.dev/docs/latest/usage`。

## 常见报错与逐条排查

报错的第一个分岔点是「Pi 有没有拿到模型」。有模型之后的报错多半是上下文或工具层的问题。下面三行是本机真实输出（环境未配置任何 provider 凭据）：

```text
$ pi -p "say hi"
No API key found for the selected model.

Use /login to log into a provider via OAuth or API key. See:
  /root/.hermes/tools/node-26.7.0-linux-x64/lib/node_modules/@earendil-works/pi-coding-agent/docs/providers.md
  /root/.hermes/tools/node-26.7.0-linux-x64/lib/node_modules/@earendil-works/pi-coding-agent/docs/models.md
exit=1

$ pi --list-models
No models available. Use /login to log into a provider via OAuth or API key. See:
  /root/.hermes/tools/node-26.7.0-linux-x64/lib/node_modules/@earendil-works/pi-coding-agent/docs/providers.md
  /root/.hermes/tools/node-26.7.0-linux-x64/lib/node_modules/@earendil-works/pi-coding-agent/docs/models.md

$ pi auth check --provider openai --json
{"status":"not_ready","provider":"openai","reason":"credentials_not_configured"}
```

对照表（症状 → 首判定 → 处理方向）：

| 症状 | 首判定 | 处理方向 |
| --- | --- | --- |
| `No API key found for the selected model.` | 选中的模型没有可解析凭据 | `/login`，或设对应环境变量，或 `models.json` 补 `apiKey` |
| `No models available. Use /login ...` | 没有任何 provider 可用 | 先 `/login`；确认 `auth.json` 或环境变量在该进程里存在 |
| `auth check` 返回 `not_ready` / `invalid` | 凭据缺失或失效 | `not_ready` 补凭据；`invalid` 重新登录或检查 token 有效期 |
| 模型在 `/model` 里找不到 | 目录未刷新，或自定义模型无凭据 | `pi update --models` 刷新目录；检查 `models.json` 中该 provider 能否解析凭据 |
| 项目扩展/技能/模板全部没生效 | 项目未获信任 | 交互模式确认信任或用 `/trust`；自动化里加 `--approve` |
| `pi mcp list` 退出码为 1 | 有配置非法的条目或启用的服务器未连接 | 读 `pi mcp list --json` 的错误字段，逐条修 |
| 压缩失败（provider 不可用或拒绝摘要请求） | 摘要请求本身失败 | 先修 provider 问题再 `/compact`；关闭自动压缩不关闭手动命令 |
| 会话中渲染错乱或状态异常 | 终端渲染层问题 | `/debug` 写 `pi-debug.log` 到 agent 目录，再对照分析 |
| 需要提 issue | 需要可复现材料 | `/bug [description]`，选择是否附带会话记录，上传到 `radius.pi.dev` 或导出 zip |

一条好用的体检命令组合（无会话也能跑）：

```shell
# 版本
pi --version

# 凭据与服务健康
pi auth check --provider anthropic --json
pi auth check --provider openai --json

# MCP 连接状态（有非法配置或未连接时退出码 1）
pi mcp list --json

# 已安装的包与资源
pi list

# 仅排查上下文来源：关掉全部上下文文件
pi -nc --list-models
```

在被 Shell 工具执行的命令里，Pi 会注入会话元信息，这让「到底跑的是哪个模型」这类问题不需要猜：

```bash
# 让模型在 bash 工具里执行（或在扩展的 tool 里跑）时会拿到这些变量
printf 'provider=%s model=%s reasoning=%s\n' "$PI_PROVIDER" "$PI_MODEL" "$PI_REASONING_LEVEL"
printf 'session=%s file=%s\n' "$PI_SESSION_ID" "$PI_SESSION_FILE"

# 子进程可以用这两个标记判断自己在 Pi 里运行
echo "AI_AGENT=$AI_AGENT PI_CODING_AGENT=$PI_CODING_AGENT"
```

注意：这些 `PI_*` 变量只注入给 LLM 可调用的 `bash` / `powershell` 工具，**不会**注入用户自己输入的 `!` / `!!` 命令。

```text
常见报错要点：
1. 先分岔：有没有模型可用（pi --list-models / pi auth check）
2. credentials_not_configured 是凭据问题，不是模型目录问题
3. 项目资源不生效先查项目信任，而不是查扩展代码
4. pi mcp list 非零退出码表示「有配置非法或服务器未连上」，配合 --json 看字段
5. 压缩失败通常是 provider 侧问题，修好后手动 /compact 即可
6. PI_PROVIDER / PI_MODEL / PI_REASONING_LEVEL 只在 bash/powershell 工具里可见
```

## 上下文与自动压缩调优

自动压缩的触发条件是固定公式：

```text
contextTokens > contextWindow - reserveTokens
```

默认 `reserveTokens` 是 16384，作用是给模型回复留出空间。压缩过程是：从最终会话投影往回走，累加 token 估算直到达到 `keepRecentTokens`（默认 20000）确定切点；把上一次保留边界（或会话开头）到切点之间的消息抽出来交给 LLM 生成结构化摘要；把带摘要和 `firstKeptEntryId` 的 `CompactionEntry` 写回会话；之后重建上下文时使用「摘要 + 从 `firstKeptEntryId` 起的消息」。**原始条目不会被删除**，只是不再进入后续请求。

多轮运行中，Pi 在工具执行完、结果追加之后、下一次助手回复之前检查投影上下文，越过阈值就在 `prepareNextTurn` 阶段压缩，然后再做一次追赶式 steering 轮询；新用户提示之前也会检查一次，底层运行结束后还有一次最终的溢出恢复尝试。Provider 报上下文溢出，或最终 `stopReason: "length"` 时，可以选择一次「压缩后重试」。

按模型单独调参走 `compaction.modelOverrides`，键是精确大小写的 `provider/modelId`：

```json
{
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000,
    "modelOverrides": {
      "some-provider/big-model": {
        "reserveTokens": 400000
      }
    }
  }
}
```

上面这份配置对一个 1M 上下文窗口的模型意味着：超过约 600K token 才触发压缩，同时仍然保留常规的 20000 个近期 token；其他模型继续用 16384 的预留。取值规则要记住三点：每个 `reserveTokens` / `keepRecentTokens` 独立回退（模型覆盖 → 普通设置 → 内置默认）；值必须是非负安全整数；`enabled` 是全局开关，**不能**按模型设置。

手动压缩与分支摘要是另外两个入口：`/compact [instructions]` 手动压缩并可带聚焦指令（比如「保留最近的数据库迁移决策」）；`/tree` 导航离开一个分支时，Pi 可以给被放弃的分支生成摘要并挂在进入的分支上，这样「另一条路试过什么」不会整段丢失。

```shell
# 会话里查看当前上下文用量与成本（底部状态栏也会实时显示）
/session

# 手动压缩并指定摘要重点
/compact 只保留接口契约与失败原因

# 探索另一条实现路线；离开分支时可生成摘要
/tree

# 关闭自动压缩（手动命令仍然可用）
# settings.json: { "compaction": { "enabled": false } }
```

```text
压缩调优要点：
1. 触发公式：contextTokens > contextWindow - reserveTokens，默认 reserveTokens=16384
2. 保留窗口：keepRecentTokens 默认 20000，切点由此确定
3. 压缩只影响后续请求，原始条目仍留在会话文件里，可回溯
4. compaction.modelOverrides 按 provider/modelId 精确覆盖，enabled 不能按模型设
5. 溢出与 length 截断各有一次「压缩后重试」机会
6. 长上下文模型必须配 modelOverrides，否则会在远未用满窗口时就压缩
```

## 成本与提示缓存

成本信息在两处可见：交互模式底部状态栏，以及 `/session` 给出的会话统计（文件、ID、消息数、token 用量与成本）。想避免「账单和直觉不符」，得知道成本主要来自三块：**上下文长度**（每轮都重发系统提示与历史）、**缓存命中率**（命中缓存的前缀比未命中便宜得多）、**不必要的模型调用**（重试、摘要、路由判断）。

缓存相关设置都在 `settings.json` 的模型与思考组里：

| 设置 | 默认 | 作用 |
| --- | --- | --- |
| `cacheWarming` | `"streaming"` | 运行中保持兼容 provider 的提示缓存热；`"idle"` 表示在两次运行之间保温，`"off"` 关闭 |
| `showCacheMissNotices` | `false` | 显示明显的缓存未命中、缓存成功预热、压缩用量与 provider 恢复提示 |
| `thinkingBudgets` | 内置预算 | `minimal` / `low` / `medium` / `high` 各等级的 token 预算 |
| `defaultThinkingLevel` | `"medium"` | 启动思考等级；简单任务降到 `low` 或 `off` 能显著省钱 |

缓存预热只在模型声明了缓存寿命、且 Pi 估算至少能省下 $0.05 的未命中成本时才运行；预热产生的用量计入会话总量但**不进入模型上下文**。`/session` 会显示下一次预热决策，扩展可以用 `cache_warming_decision` 覆盖它。开启 `showCacheMissNotices` 是排查缓存问题最直接的手段。

让缓存命中率崩掉最常见的原因是**系统提示整段替换**：在 `before_agent_start` 里返回 `systemPrompt` 或设置 `forceSystemPrompt` 会替换整个提示；官方文档说明，每次变化都是一次缓存未命中，而改 `sections` / `selectedTools` / `promptGuidelines` 只会追加一个补丁片段。另一个杠杆是 provider 的缓存保留档位：

```shell
# 支持扩展缓存保留的 provider 上启用长档位
export PI_CACHE_RETENTION=long
pi

# 更省的做法：简单任务降思考等级、把路由器判断交给便宜的分类模型
# settings.json: { "defaultThinkingLevel": "low" }
```

分类模型（classifier）只回答 JSON 状态的类型化问题（多选、是否、打分），很适合做请求路由与廉价的判定；图像模型同理。它们不进 `/model`，通过 `codemode` 脚本调用，用量会计入 codemode 工具结果并进入会话成本。

```text
成本与缓存要点：
1. 成本三来源：上下文长度、缓存命中率、多余调用（重试/摘要/路由）
2. /session 与底部状态栏是成本与用量的第一手来源
3. cacheWarming 默认 streaming；预热只在估算省下 $0.05 以上时才跑
4. showCacheMissNotices 是排查缓存命中的开关，排查完记得关
5. 整段替换系统提示 = 每次变化一次缓存未命中；优先改片段
6. PI_CACHE_RETENTION=long 在支持的 provider 上启用长档位缓存
```

## 性能与交互体验

网络与重试参数都在设置的 network/retry 组里，默认值对绝大多数场景够用，只有在「网络抖动频繁」或「provider 有配额限制」时才需要动：

| 设置 | 默认 | 说明 |
| --- | --- | --- |
| `transport` | `"auto"` | 支持多传输的 provider 的可选传输：`sse` / `websocket` / `websocket-cached` |
| `httpIdleTimeoutMs` | `300000` | HTTP 头与体的空闲超时；`0` 表示禁用 |
| `websocketConnectTimeoutMs` | `15000` | WebSocket 连接超时；`0` 表示禁用 |
| `retry.enabled` | `true` | 瞬态失败时的 agent 级自动重试 |
| `retry.maxRetries` | `3` | agent 级最大重试次数 |
| `retry.baseDelayMs` | `2000` | 指数退避的初始延迟 |
| `retry.provider.maxRetries` | `0` | provider 级重试次数，官方建议保持 0 |

关于 `retry.provider.maxRetries` 要保持默认 0 的原因值得单独说：provider 级重试会推迟 Pi 自己去处理配额与用量限制类错误，反而把「该停下来告诉你」的情况变成「一直重试」。

交互体验上最省心的三组能力：

```text
输入与打断（官方 usage 文档的定义）：
1. Enter        —— 调整当前任务：等当前回复与工具调用结束后引导下一次回复（steering）
2. Alt+Enter    —— 追加工作：等当前任务彻底结束后再进入（follow-up）
3. Alt+Up       —— 把排队的消息退回编辑器
4. Escape       —— 中止当前任务；被中止时排队消息会回到编辑器

显示与查看：
5. Ctrl+O       —— 展开/折叠工具输出
6. Ctrl+T       —— 显示/隐藏思考块
7. !command     —— 执行命令并把输出带进对话；!!command 只看结果不发给模型
8. Ctrl+G       —— 用外部编辑器写长提示（externalEditor 未设时回退 $VISUAL / $EDITOR）

终端相关：
9. --tui-mode fullscreen|regular —— 全屏固定编辑器，或复用终端自身回滚缓冲
10. PI_TUI_ESC_TIMEOUT —— 单独按 Esc 的判定等待毫秒数；Alt 键被误判为 Esc 时调大
```

工具输出体积也会影响体感与成本：MCP 工具超过 20 KB 的文本结果在到达模型前会被去掉中间部分并留下 `…N chars truncated…` 标记，完整内容存到临时文件并在结果里给出路径；图片在发送给模型前默认会缩放到不超过 2000x2000（`images.autoResize`，`images.blockImages` 可以整体禁止发图）。而 `codemode` 脚本能拿到完整的 MCP 结果，先在脚本里裁剪再返回给模型，是处理大结果集的标准做法。

```text
性能与体验要点：
1. 默认网络与重试参数够用；retry.provider.maxRetries 保持 0
2. steering（Enter）与 follow-up（Alt+Enter）语义不同，选错会打乱节奏
3. 大输出用 codemode 在脚本里裁剪，比直接塞给模型更省更准
4. Ctrl+O / Ctrl+T 是观察工具输出与思考过程的标准开关
5. tuiMode 用 fullscreen 保编辑区固定，用 regular 复用终端回滚
6. Alt 键被误读为 Escape 时调大 PI_TUI_ESC_TIMEOUT
```

## 无人值守与安全落地

把 Pi 放进 CI、定时任务或服务里之前，有五件事必须显式处理，否则会在最不方便的时候出问题：

1. **信任决策**：print / JSON / RPC 都无法显示内置信任提示，`defaultProjectTrust` 为 `"ask"` 或 `"never"` 时会跳过受保护的项目资源。用 `--approve` / `--no-approve` 明确表态。
2. **凭据来源**：用环境变量或 `auth.json` 的 `!command`，不要把明文密钥落进镜像或仓库；`auth.json` 必须保持私密。
3. **隔离边界**：需要强边界就整个放进容器/虚拟机，只暴露任务需要的目录、凭据与服务；官方立场很明确——项目信任不是沙箱，工具用的是 Pi 进程的操作系统权限。
4. **会话处理**：无人值守任务通常不需要会话持久化，用 `--no-session` 避免在机器上堆积会话文件；反过来，需要审计时保留会话并纳管它们（会话里可能含凭据）。
5. **降噪与离线**：用环境变量关掉不必要的网络活动，减少在受控环境里的意外出网。

```shell
# 无人值守一次运行：显式授权 + 不落会话 + 结构化事件 + 关掉额外网络活动
pi --approve --no-session --mode json --offline \
   "运行测试，汇总失败用例与最可能的原因" > run.jsonl

# 等价的环境变量写法
export PI_OFFLINE=1            # 等价于 --offline，禁用启动期网络操作与模型目录刷新
export PI_SKIP_VERSION_CHECK=1 # 跳过 pi.dev 的版本检查
export PI_TELEMETRY=0          # 关闭安装/更新遥测与 provider 归属头
pi --approve -p "生成变更摘要"

# 在容器里跑：只挂载工作目录，凭据通过环境注入
docker run --rm -v "$PWD:/work" -w /work \
  -e ANTHROPIC_API_KEY -e PI_OFFLINE=1 \
  --network none \
  my-pi-image --approve -p "检查依赖是否有已知的高危版本"
```

其它与运行环境相关的变量按需使用：`PI_CODING_AGENT_DIR` 换配置目录、`PI_CODING_AGENT_SESSION_DIR` 换会话目录、`PI_PACKAGE_DIR` 覆盖包目录（Nix/Guix 场景）、`HTTP_PROXY` / `HTTPS_PROXY` 走代理、`PI_IMAGE_PROTOCOL` / `PI_TRUE_COLOR` / `PI_HYPERLINKS` 覆盖终端能力探测。在容器或 Nix 这类环境里，把 `PI_CODING_AGENT_DIR` 显式指到一个可写的挂载点，能避免配置写在镜像层里。

```text
无人值守与安全要点：
1. 无界面模式必须显式给信任决策，否则项目资源静默跳过
2. 凭据走环境变量或延迟取值命令，绝不写进镜像与仓库
3. 强边界靠容器/虚拟机 + 只暴露必需目录与凭据，不靠信任提示
4. 无人值守默认 --no-session；需要审计时再保留并纳管会话
5. PI_OFFLINE / PI_SKIP_VERSION_CHECK / PI_TELEMETRY=0 控制出网与遥测
6. 容器里把 PI_CODING_AGENT_DIR 指到可写挂载点，避免配置写进镜像层
```

## 使用建议清单

把下面这些当成默认动作，能挡掉大部分「用着不舒服」的体验问题：

1. **会话命名并定期清理。** 开工先 `/name`，收工用 `/session` 看一眼用量；`~/.pi/agent/sessions/` 按工作目录分堆，定期清理旧 `.jsonl`（`/resume` 里 `Ctrl+D` 走回收站更安全）。

2. **探索方案时用 `/tree`、`/fork`、`/clone` 而不是重开。** `/tree` 在同一会话文件里换分支，`/fork` 从某条用户消息切出独立会话，`/clone` 复制当前分支。分支切换前让 Pi 给被放弃的分支生成摘要，能保住试错信息。

3. **规则与知识分开写：AGENTS.md 放约束，技能放过程。** 前者每轮都进上下文，只写「不写就会犯错」的几条；后者按需加载，可以写得很详细，并带脚本与参考文档。

4. **长任务先让 Pi 出计划。** 在真正改代码前要求「先给出步骤与验证方式」，能在最便宜的位置发现方向错误。

5. **换模型先看上下文窗口，再调压缩参数。** 上大窗口模型但不改 `compaction.modelOverrides`，会让压缩在远未用满窗口时就触发，白白丢掉历史。

6. **改动规则、扩展、主题后 `/reload`。** 加载与热重载都基于「自动发现位置」，路径写对了这一步才有效。

7. **把「成本可观测」当成例行动作。** 定期看 `/session` 的 token 与成本，打开一次 `showCacheMissNotices` 排查缓存，确认后关掉。

```text
使用建议要点：
1. 会话命名 + 定期清理，避免会话目录膨胀与信息泄露面扩大
2. 探索用 /tree /fork /clone，别用重开会话的方式丢历史
3. AGENTS.md 写约束、技能写过程、模板管输出格式，三者别混用
4. 长任务先要计划，再要实现
5. 换模型必须同步调 compaction.modelOverrides
6. 规则/扩展/主题改动后 /reload
```

## 应用场景实战

### 场景一：新机器或 CI 的一次性体检脚本

换到一台新机器、或在 CI 里第一次引入 Pi 时，与其一条条试，不如跑一个体检脚本把「装了没、凭什么模型、能不能连 MCP、项目资源是否会被信任」一次问清楚，并把结论写进日志。

```bash
#!/usr/bin/env bash
# pi-doctor.sh —— Pi 环境体检；不产生会话文件，可安全重复执行
set -uo pipefail

echo "== 1. 版本与安装位置 =="
pi --version
command -v pi

echo
echo "== 2. 凭据健康（0=ready 1=not_ready 2=invalid）=="
for provider in anthropic openai google; do
  out="$(pi auth check --provider "$provider" --json 2>&1)"
  echo "$out"
  printf '  exit=%s provider=%s\n' "$?" "$provider"
done

echo
echo "== 3. 可用模型（前 10 条）=="
pi --list-models 2>&1 | head -10

echo
echo "== 4. MCP 服务器状态（退出码 1 表示有配置非法或服务器未连上）=="
pi mcp list --json 2>&1 | head -40

echo
echo "== 5. 项目资源是否会被加载 =="
if [ -d .pi ]; then
  echo "存在 .pi 目录，检查受信任保护的内容："
  find .pi -maxdepth 2 -type f -o -type d | head -20
  echo "无界面模式下需要显式 --approve，否则这些资源会被跳过"
else
  echo "无 .pi 目录，项目资源无需信任决策"
fi

echo
echo "== 6. 上下文文件 =="
for f in AGENTS.md AGENTS.override.md CLAUDE.md; do
  [ -f "$f" ] && echo "找到：$f（$(wc -l < "$f") 行）"
done

echo
echo "== 7. 已安装的包 =="
pi list

echo
echo "体检结束。若第 2 步全部 not_ready，先跑 pi 执行 /login。"
```

```text
$ bash pi-doctor.sh
== 1. 版本与安装位置 ==
1.2.0
/root/.hermes/tools/node-26.7.0-linux-x64/bin/pi

== 2. 凭据健康（0=ready 1=not_ready 2=invalid）==
{"status":"not_ready","provider":"openai","reason":"credentials_not_configured"}
  exit=0 provider=openai
```

注意这里 `exit=0` 的原因：命令被包在命令替换 `$(...)` 里，`$?` 取到的是 `echo` 的返回值而不是 `pi auth check` 的。要按退出码分支时应当直接运行命令再取 `$?`（或用 `if` 直接判断）：

```bash
if pi auth check --provider openai --json > /dev/null; then
  echo "openai 凭据就绪"
else
  case $? in
    1) echo "openai 凭据缺失，先执行 /login 或设置 OPENAI_API_KEY" ;;
    2) echo "openai 凭据无效，重新登录或检查 token 有效期" ;;
    *) echo "openai 检查未预期失败" ;;
  esac
fi
```

### 场景二：长会话项目的成本与上下文治理

一个需要长时间跟进的仓库，典型症状是「越聊越慢、越聊越贵、关键决策还会被压缩掉」。治理办法是把压缩、缓存、思考等级三处参数一起配置，并把「该记在文件里的东西记进文件」。

## 最佳实践与踩坑记录

1. **先分岔再排查。** 第一条命令永远是 `pi --list-models` 或 `pi auth check --provider X --json`：能拿到模型，问题就在上下文或工具层；拿不到，问题在凭据或目录。

2. **把 `showCacheMissNotices` 当排查开关而不是常开设置。** 打开它能看到明显的缓存未命中与预热决策，确认缓存行为正常后关掉，避免长期刷屏掩盖真正的问题。

3. **压缩参数跟着模型走。** 换到大窗口模型时同步更新 `compaction.modelOverrides`，否则压缩会在窗口远未用满时触发，导致历史被提前摘要掉。

4. **`retry.provider.maxRetries` 保持 0。** 官方明确建议：provider 级重试会延迟 Pi 自己处理配额与用量限制错误。

5. **无人值守同时锁定三件事：信任、凭据、会话。** `--approve`（或明确 `defaultProjectTrust`）+ 环境变量凭据 + `--no-session`，是 CI 里的最小安全组合。

6. **规则文件保持短小，知识放技能。** AGENTS.md 每轮都进上下文；技能只在命中时加载。把长文档塞进 AGENTS.md 是成本失控与指令被忽略的常见起点。

坑 1：`pi -p` 直接报 `No API key found for the selected model.` 并退出码 1。
结论：该模型没有可解析的凭据，属于配置问题而不是 Pi 故障。
原因：Pi 按 `--api-key` → `auth.json` → `models.json` 的 `apiKey` → provider 环境变量的顺序解析凭据，全部落空时连请求都不会发出。
解法：交互模式用 `/login` 登录一次，或在启动 Pi 的进程里设置对应环境变量（注意环境变量必须在启动 Pi 的那个进程里），`pi auth check --provider X --json` 确认变成 `ready`。

坑 2：在命令替换里取退出码，健康检查永远显示成功。
结论：`out="$(pi auth check ...)"` 之后 `$?` 是赋值语句的返回值，不是被调用命令的。
原因：Shell 的 `$?` 只反映最近一条命令；命令替换本身是一条赋值命令时，退出码会被覆盖。
解法：直接 `if pi auth check --provider x --json; then ...; else case $? in ...` 或用 `pi auth check ...; rc=$?` 保存后再判断。

坑 3：以为关闭自动压缩就能保住全部历史。
结论：`compaction.enabled: false` 只关闭自动压缩，手动 `/compact` 仍然可用；而真正的历史仍受模型窗口限制。
原因：压缩只是「不再进入后续请求」的摘要机制，原始条目一直在会话文件里；关掉自动压缩意味着窗口撑满后由 provider 报溢出或出现 `length` 截断。
解法：需要保历史就按模型调大 `reserveTokens`，或使用 `/tree` 在分支之间切换；真正长期的事实写进 `AGENTS.md` 或技能文件，而不是指望会话历史。

坑 4：把 `PI_*` 会话变量写进用户自己的 `!command` 里。
结论：这些变量只注入 LLM 可调用的 `bash` / `powershell` 工具。
原因：官方文档明确这些变量注入的是工具调用，不是用户输入的 `!` / `!!` 命令；`AI_AGENT=pi` 与 `PI_CODING_AGENT=true` 是进程标记，由 CLI / RPC 入口设置且不被 SDK 嵌入场景自动设置。
解法：要在自己的 shell 里拿到会话信息，直接从 `$PI_SESSION_FILE` 之外的方式取（`/session` 或 `--session <path>`）；在扩展或工具里用 `PI_PROVIDER` / `PI_MODEL` 判断当前模型。

坑 5：为了省钱把思考等级全局设成 `off`，结果工具调用质量下降、往返次数增加。
结论：总成本由「token 单价 × 轮数」共同决定，降等级有时反而更贵。
原因：思考等级过低会让模型在复杂任务上多试错、多调用工具，最终消耗的输入 token 与轮数上升；缓存命中率也可能因为提示变化更频繁而下降。
解法：按任务类型分级——简单改动用 `low`/`off`，复杂重构保留 `medium`/`high`；把稳定不变的项目事实写进 AGENTS.md 或技能，减少每轮的重复解释。
