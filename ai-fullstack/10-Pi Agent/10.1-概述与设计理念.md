## 概述

Pi 是一个**极简的终端编码 harness**（官方英文定位：minimal terminal coding harness）。它把大模型接到你当前的工作目录上，让模型读文件、改代码、跑命令，再把真实结果回填上下文继续下一步。与 Codex、Claude Code 这类功能齐备的 agent 不同，Pi 的设计取向是**内核保持很小，把工作流差异交给用户自己扩展**：官方口号是 adapt Pi to your workflows, not the other way around（让 Pi 适应你的流程，而不是反过来）。

本文回答三个问题：Pi 到底是什么、它的设计取舍是什么、以及在什么场景下它比功能更全的 agent 更合适。具体的安装、交互、自动化用法分别见本篇章 10.2~10.4。

```text
Pi 入门三件事：
1. 小内核 —— 默认工具只有 read / bash / edit / write，其余能力按需加载
2. 可扩展 —— TypeScript 扩展、技能、提示模板、主题四类资源，可打包成 pi package 分发
3. 四接口 —— 交互 TUI、print/JSON、RPC、TypeScript SDK，共用同一套 agent 与 session 机制
```

本机实测环境（2026-10-15，Ubuntu 24.04）：

```text
$ node --version
v26.7.0
$ npm --version
11.19.0
$ npm install -g --ignore-scripts @earendil-works/pi-coding-agent
changed 118 packages in 5s
$ which pi
/root/.hermes/tools/node-26.7.0-linux-x64/bin/pi
$ pi --version
1.2.0
```

Pi 已在本机安装成功，因此本文的命令、参数与输出均为真实执行结果，不是照抄文档。Pi 自身的模型调用需要先 `/login` 或设置 API key，未配置凭据时的真实报错见 10.2。

## Pi 是什么与定位

Pi 的官方 npm 包是 `@earendil-works/pi-coding-agent`（早期包名 `@mariozechner/pi-coding-agent`，同一作者 Mario Zechner，新版由 Earendil Works 发布），源码在 `github.com/earendil-works/pi` 的 `packages/coding-agent` 目录，许可证 MIT，要求 Node.js 22.19 或更新。包元数据里 `bin` 指向 `dist/bundle/cli.js`，也就是安装后得到一个 `pi` 可执行文件。

定位上有三个明确特征：

1. **终端优先**：`pi` 是一个 TUI 程序，在你的 shell 里运行；工作目录既是文件发现范围，也是会话分组依据。
2. **agent 而非聊天**：它有自己的 agent loop（模型请求 → 工具调用 → 结果回填 → 下一轮），会话以树结构持久化，可随时回退到任一历史节点继续。
3. **harness 而非产品**：官方只保证内核能力，重型特性（子代理、plan mode、权限确认弹窗、内置 todo、后台 bash）刻意不内置，鼓励你用扩展或第三方 package 补上。

```shell
# 看内核默认暴露给模型的工具（真实输出见下）
pi --help | sed -n '/Built-in Tool Names/,/^$/p'

# 看当前机器上可用的模型（未登录时为空）
pi --list-models
```

上面两条命令在本机的真实结果：

注意最后三行：`grep`、`find`、`ls` 三个只读工具**默认关闭**，默认开启的只有 `read`、`bash`、`edit`、`write`（与 SDK 实测的 `session.getActiveToolNames()` 返回值完全一致，见 10.4）。这个默认值本身就是设计取向的证据：内核给出最小可用的读写能力，搜索类能力要你显式打开。

```text
定位要点：
1. 包名 —— @earendil-works/pi-coding-agent，命令名 pi，MIT，Node >= 22.19
2. 工作单元 —— 一个工作目录 + 一份会话树，会话自动保存到 ~/.pi/agent/sessions/
3. 默认工具 —— read / bash / edit / write；grep / find / ls 默认关闭
4. 不只本地 —— 支持 15+ provider（Anthropic、OpenAI、Google、Bedrock、OpenRouter、Ollama 等）
5. 文档位置 —— 在线 https://pi.dev/docs，离线随包附在 <包目录>/docs/
```

## 核心设计理念极简内核与扩展边界

Pi 的运行时概念只有四个：**agent loop、session 树、context 组装、interface**。理解这四件事，就理解了这个 harness 为什么长这样。

- **Agent loop**：提交的消息进入当前分支 → Pi 用「系统提示 + 当前分支历史 + 可用工具 + 模型设置」组装请求 → provider 流式返回文本与工具调用 → Pi 执行工具并记录结果，这算一个 turn → 若还有工具结果或排队消息需要模型，再开一个 turn，否则 run 结束。
- **Session 树**：会话是 JSONL 文件，每个条目有 ID 并指向父条目，最后一条即当前活跃分支。回到历史节点继续，等于在同一文件里长出新分支，旧分支不会被删除。
- **Context 组装**：模型只收到「活跃分支」而不是整棵会话树；系统提示由基础指令 + 发现的上下文文件构成；技能只先暴露名字和描述，完整指令按需加载；自动 compaction 在接近上下文上限时插入摘要条目，原始条目仍留在文件里。
- **Interface**：交互 TUI、print、JSON、RPC 四种接口共用同一套 agent 与 session 机制，所以「交互里怎么跑，脚本里就怎么跑」。

这套设计的直接后果是：Pi **没有 plan mode、没有内置 todo、没有子代理、没有权限弹窗、没有后台 bash**。官方的建议不是「等我们做」，而是「写进文件、用 tmux、写扩展、装 package」。MCP 则以内置扩展 `builtin:mcp` 的形式提供（本机 `pi mcp --help` 可见，`pi --help` 也把 `pi mcp <command>` 列在 Commands 里）——先在扩展层实现，被证明必要后才进内核，这条路子本身就是它扩张的方式。

```shell
# 两个系统提示层级的落点（用户级 / 项目级）
export PI_CODING_AGENT_DIR=~/.pi/agent   # 默认值，可用环境变量改

# 项目级：替换系统提示（存在即生效，且项目文件优先于 agent 目录同名文件）
$EDITOR .pi/SYSTEM.md

# 项目级：在默认系统提示之后追加指令
$EDITOR .pi/APPEND_SYSTEM.md

# 每次启动从工作目录、父目录、agent 目录加载的指令文件
$EDITOR AGENTS.md
```

```json
{
  "$schema": "https://pi.dev/schemas/settings.schema.json",
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  },
  "branchSummary": {
    "reserveTokens": 16384,
    "skipPrompt": false
  }
}
```

上面这段是 `~/.pi/agent/settings.json` 的片段：compaction（自动摘要旧历史）默认开启，默认给模型回复预留 16384 token、最近 20000 token 不参与摘要；离开一个分支时还能生成 branch summary 附到你进入的分支上。这些默认值可以在项目 `.pi/settings.json` 里覆盖，项目设置优先于 agent 目录设置，但资源列表是两边合并的。

```text
内核设计要点：
1. 四概念 —— agent loop / session 树 / context 组装 / interface，没有第五个
2. 分支即实验 —— /tree 在同一文件内切换，/fork 与 /clone 才另起文件
3. 上下文可控 —— 真正的请求内容 = 活跃分支 + 系统提示 + 工具定义 + 技能描述
4. 默认不做决策 —— 不弹权限确认，不替你判断"能不能上线"；隔离要靠容器
5. 扩展先于内核 —— MCP 就是以内置扩展 builtin:mcp 落地的例子
```

## 四层扩展点扩展技能提示模板与主题

官方给了一张「按需选最小机制」的选择表，这是 Pi 扩展体系的核心：能用 `AGENTS.md` 解决的不要写技能，能用技能解决的不要写扩展，因为每往上一层的成本与风险都更高。

| 你的需求 | 应该先用 | 为什么 |
|---|---|---|
| 给某个目录固定的长期指令 | `AGENTS.md` | 零代码，启动即加载 |
| 复用一段提示词，出现在 `/` 菜单里 | 提示模板（prompt template） | 一个 Markdown 文件即可 |
| 增加任务专属指令 + 附带脚本/参考文件 | 技能（skill） | 按需加载，不占常驻上下文 |
| 增加可执行工具、命令、事件处理 | 扩展（extension） | 进程内代码，能力最大 |
| 自定义终端界面组件 | TUI 组件（tui） | 扩展的 UI 子集 |
| 接入 Pi 不支持的模型服务 | 自定义 provider | models.json 或 provider 扩展 |
| 一次分发多种资源 | pi package | npm/git 安装，统一版本 |

四类资源的落点如下（用户级在 agent 目录，项目级在 `.pi/` 下；项目级资源要过了项目信任才会加载，唯一例外是 `sessionDir`，它在信任判定之前就要读）：

```text
~/.pi/agent/extensions/   用户扩展（.ts/.js 单文件，或含 index.ts/index.js 的目录）
~/.pi/agent/skills/       用户技能（含 SKILL.md 的目录）
~/.pi/agent/prompts/      用户提示模板（Markdown，直接成为 /name 命令）
~/.pi/agent/themes/       用户主题（终端配色）

.pi/extensions/  .pi/skills/  .pi/prompts/  .pi/themes/     项目级同名目录
```

最小可运行的三份资源示例（放进用户级目录即生效）：

```typescript
// ~/.pi/agent/extensions/hello.ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerCommand("hello", {
    description: "Show a greeting",
    handler: async (name, ctx) => {
      ctx.ui.notify(`Hello, ${name || "world"}!`, "info");
    },
  });
}
```

```markdown
<!-- ~/.pi/agent/prompts/review.md：输入 /review 即展开为提示 -->
Review the staged diff. Report findings by severity with file:line references.
```

```markdown
---
name: pdf-tools
description: Extract text and tables from PDF files. Use when reading, converting, or inspecting PDFs.
---

# PDF tools

Read `references/formats.md` before converting a document.
```

三者的加载时机完全不同，这是最容易踩错的地方：扩展在进程内运行、能力最大也最危险；技能只在模型判断相关或你显式 `/skill:name` 时才读取完整指令；提示模板在你回车那一刻就展开成用户消息。开发期用命令行开关单次加载即可，不必先改配置：

```shell
# 单次加载一个扩展（本地 TS 无需编译，Pi 用 jiti 直接加载）
pi --extension ./hello.ts

# 单次加载技能 / 提示模板 / 主题
pi --skill ./skills/pdf-tools
pi --prompt-template ./prompts/review.md
pi --theme ./themes/my-theme.json

# 反向控制：禁用某类资源的发现（显式路径仍然生效）
pi --no-extensions --extension builtin:mcp
pi --no-skills
```

```text
扩展点要点：
1. 从最小做起 —— AGENTS.md < 提示模板 < 技能 < 扩展 < 自定义 provider
2. 技能是渐进披露 —— 启动只注入 name 与 description，完整 SKILL.md 按需读取
3. 扩展信任等同代码执行 —— 它在 Pi 进程内跑，权限与 Pi 相同，只装可信来源
4. 单次加载 —— -e / --skill / --prompt-template / --theme 不改配置即可试
5. 改完用 /reload —— 运行中改了资源文件，/reload 重新加载（扩展运行时会被整体替换）
```

## Pi packages 与分发共享

当你需要把扩展、技能、提示模板、主题一起分发时，用 pi package：一个 npm 包或 git 仓库，声明自己的资源目录，用同一个命令安装、更新、列举。这是 Pi 生态里第三方能力的正规通道，npm 上带 `pi-package` 关键词的即为此类包。

```shell
# 从 npm / git / 本地路径安装
pi install npm:@example/pi-tools@1.0.0
pi install git:github.com/example/pi-tools@v1
pi install ./local-package

# 只对当前项目生效（写入 .pi/settings.json，需要项目信任）
pi install npm:@example/pi-tools@1.0.0 --local

# 不改配置，单次试用
pi -e npm:@example/pi-tools

# 管理
pi list                          # 列出已配置的包
pi remove npm:@example/pi-tools  # 移除包与对应设置项
pi update --extensions           # 更新所有已装包
pi config                        # TUI 里勾选启用哪些包资源（Tab 切作用域）
```

四种来源的行为差异值得记住：npm 包装进 Pi 的 npm 目录；git 源按 ref 克隆并校准到该 ref；版本化的 npm 规格与 git tag/commit 都是**钉住**的，`pi update` 只校准检出、不会移动你配置的 ref；本地目录直接按解析后的路径加载，不复制。个人安装写入 `~/.pi/agent/settings.json`，加 `--local` 写入 `.pi/settings.json`，而项目包**只有在项目信任解决之后才会安装和加载**。

```text
包分发要点：
1. 一个包多类资源 —— extensions / skills / prompts / themes 可打在一个包里统一版本
2. 来源钉住 —— npm@1.0.0、git@v1、git@<commit> 都被固定，更新不会偷偷换 ref
3. 作用域明确 —— 默认个人级，--local 才写项目文件，且受项目信任门控
4. 先试后装 —— pi -e <source> 单次加载，确认可用再 install
5. 第三方包即代码 —— 包里的扩展会在 Pi 进程内执行，装之前先读源码
```

## 四种接口形态

「同一个内核、多种接口」不是营销话术，而是实现层面的复用：所有接口都走同一套 agent 与 session 机制，区别只在输入怎么进来、输出怎么暴露、进程是否存活。

| 接口 | 输入输出 | 生命周期 | 适用 |
|---|---|---|---|
| Interactive | 终端 TUI | 到用户退出 | 人直接与 Pi 协作 |
| Print | stdout 上的最终文本 | 一次调用 | 脚本只要最终回答 |
| JSON | stdout 上的 JSONL 事件 | 一次调用 | 需要结构化进度 |
| RPC | stdin/stdout 双向 JSONL | 长驻 | 进程隔离的集成、IDE、自定义客户端 |
| SDK | 进程内 TypeScript API | 宿主进程决定 | Node.js / Bun 里直接嵌入 |

本机真实执行结果（未配置凭据，因此只验证协议与输出通道）：

```text
$ pi -p "say hi"; echo "exit=$?"
No API key found for the selected model.

Use /login to log into a provider via OAuth or API key. See:
  .../pi-coding-agent/docs/providers.md
exit=1

$ pi --mode json "say hi" > out.jsonl 2> err.txt; echo "exit=$?"
exit=1
$ cat out.jsonl          # stdout 只写协议记录：第一条就是 session header
{"type":"session","version":3,"id":"01a13d63-c83e-75a4-b0b5-a57f9f8fe5b9","timestamp":"2026-10-15T02:28:31.935Z","cwd":"/root/.hermes/cache/scratch"}
$ head -2 err.txt        # 诊断与错误走 stderr
No API key found for the selected model.
```

这段真实输出验证了两条结论：**stdout 保留给协议数据，诊断日志走 stderr**；`-p` 在模型侧出错时以非零状态退出，方便 CI 判断成败。RPC 模式的真实握手与 SDK 的真实调用见 10.4。

```text
接口要点：
1. 模式选择 —— 未指定模式且 stdin/stdout 不是终端时，Pi 自动退化为 print 模式
2. 通道纪律 —— stdout 只放协议记录，stderr 放诊断；读端必须持续消费避免背压阻塞
3. 一次 vs 长驻 —— print/JSON 是一次调用；要连续下命令用 RPC 或 SDK
4. SDK 不是模式 —— 它把 agent 嵌进 Node.js/Bun 进程，没有子进程边界
5. 选项通用 —— 无论哪种模式，工作目录、模型、工具、资源、会话开关传法都一样
```

## 与重型 Agent 的取舍对比

选型的核心问题不是「谁功能多」，而是「你要的是开箱即用的完整工作流，还是一块可塑的内核」。下面按能力维度对比 Pi 与重型 agent 的取向差异（具体产品参数随版本变化，这里只比设计取向）。

| 维度 | Pi（极简内核） | 重型 agent（典型形态） |
|---|---|---|
| 默认工具集 | read / bash / edit / write | 通常还默认开搜索、todo、任务管理 |
| 子代理 | 不内置，用扩展或 tmux 自建 | 常内置并行子代理 |
| plan mode | 不内置，写进文件或装扩展 | 常内置 |
| 权限确认 | 不内置弹窗，靠容器或扩展 | 常内置审批与沙箱策略 |
| MCP | 以内置扩展 `builtin:mcp` 提供 | 常作为一等公民内建 |
| 扩展形态 | TypeScript 进程内扩展 | 多为 hook / 插件 / 配置式 |
| 会话模型 | JSONL 树，可分支可回退 | 多为线性会话 + 历史搜索 |
| 上下文控制 | 活跃分支 + 极小系统提示 + 按需技能 | 系统提示较长，工具描述常驻 |
| 上手成本 | 低（但工作流要自己拼） | 低（工作流已给定） |
| 定制上限 | 高（可改行为、可换 UI） | 中（受插件接口限制） |

判断规则可以压成一句话：**如果你认同「工作流应该由团队自己定义」，选 Pi；如果你要的是「今天就能按既定最佳实践跑起来」，先选重型 agent，等它开始限制你时再换 Pi。**

```shell
# 用真实命令验证"内核小"这件事，比读文档可靠
pi --help | grep -E '^\s+--(tools|exclude-tools|no-tools|no-builtin-tools)'
pi --help | grep -iE 'todo|plan|subagent|approval'
```

第二条命令在本机 1.2.0 上**没有任何匹配输出**，也就是 CLI 层不存在 todo、plan、subagent 这类内置特性的开关，与官方「不内置、自己造」的定位一致（扩展仍可注册自己的参数，例如 plan-mode 扩展的 `--plan`）。

```text
取舍要点：
1. 内核小换来可预测 —— 你确切知道模型被暴露了哪几个工具，上下文里没有隐藏常驻项
2. 自建有成本 —— 权限确认、子代理、todo 都要自己写或装包，这是拿自由度换工作量
3. 会话树是差异化能力 —— /tree 回退 + /fork 分叉，比线性历史更适合多方案探索
4. 重型特性可迁移 —— 用扩展实现一次，再用 pi package 在团队内分发
5. 判断依据是你的流程 —— 流程固定用重型，流程还在变用 Pi
```

## 适用与不适用的场景

**适合**：

- 终端重度用户，希望 agent 完全落在自己的 shell 工作流里（管道、tmux、脚本）。
- 需要**上下文工程**：系统提示可替换（`SYSTEM.md`）、可追加（`APPEND_SYSTEM.md`）、可按目录注入（`AGENTS.md`），技能按需加载不长期占用上下文。
- 需要在 CI 或服务里嵌入 agent：print 模式给文本、JSON 模式给事件流、RPC 给双向控制、SDK 给进程内调用，工作流不用为它改设计。
- 需要可复现的实验：会话是 JSONL，可 `/export` 导出，可用 `--session-dir` 归档。
- 团队愿意写几十行 TypeScript，换一个贴合自己流程的工具。

**不适合**：

- 需要开箱即用的权限审批 UI 与沙箱策略（Pi 明确不做权限弹窗，要自己用容器或扩展补）。
- 团队完全不想维护任何扩展代码，只想要「安装、登录、开工」。
- 需要内置子代理并行编排、内置计划模式、内置 todo 的产品级流程。
- 在不可信仓库里无人值守直接跑 `pi`：项目资源（扩展、技能、package）会执行代码，必须先读再信任。

```text
选型速查：
1. 要上下文可控 → Pi；要开箱工作流 → 重型 agent
2. 要嵌进自有系统 → Pi（四种接口 + SDK）
3. 要审批弹窗与沙箱 → 先用容器，或选内置这些能力的产品
4. 团队能写 TS → Pi 的收益随时间放大
5. 只是偶尔问两句代码 → 任意工具都行，别过度选型
```

## 应用场景实战

### 场景一：一小时内完成 Pi 的能力盘点与选型结论

场景：团队要决定是否在内部推广 Pi，需要一份基于本机实测的能力清单，而不是抄官网。目标是在评审机上装好、跑通无凭据探针、记录关键参数，最后把输出贴进选型文档。

```shell
#!/usr/bin/env bash
# pi-audit.sh —— 在评审机器上生成 Pi 能力盘点
set -euo pipefail

echo "== 1. 环境 =="
node --version
npm --version

echo "== 2. 安装（不执行依赖生命周期脚本） =="
npm install -g --ignore-scripts @earendil-works/pi-coding-agent

echo "== 3. 版本与可执行文件 =="
which pi
pi --version

echo "== 4. 默认工具集 =="
pi --help | sed -n '/Built-in Tool Names/,/^$/p'

echo "== 5. 是否存在内置 todo/plan/subagent 开关（预期：无输出） =="
pi --help | grep -iE 'todo|plan|subagent' || echo "(none)"

echo "== 6. 未登录状态下的模型列表 =="
pi --list-models || true

echo "== 7. 凭据探针（结构化、可进 CI） =="
pi auth check --provider anthropic --json || echo "exit=$?"
```

关键片段的真实执行结果：

```text
== 3. 版本与可执行文件 ==
/root/.hermes/tools/node-26.7.0-linux-x64/bin/pi
1.2.0
== 5. 是否存在内置 todo/plan/subagent 开关（预期：无输出） ==
(none)
== 7. 凭据探针（结构化、可进 CI） ==
{"status":"not_ready","provider":"anthropic","reason":"credentials_not_configured"}
exit=1
```

```text
要点：
1. auth check --json 是给机器看的 —— ready / not_ready / invalid 对应退出码 0 / 1 / 2
2. 默认工具集可用 --help 直接取证，不必翻文档
3. "没有内置重型特性"本身可验证，写进结论才有说服力
4. 盘点脚本不要写死版本号，输出里带版本，结论才可追溯
5. 评审机不需要真实 provider 凭据，探针加帮助输出足以支撑选型
```

### 场景二：把 Pi 削成只读检索器，用于代码库问答

场景：新人问「这个仓库某模块怎么组织的」，你不想让 agent 有写权限，也不想它执行命令。Pi 的默认工具集可以整体替换成只读组合，这是极简内核最实用的一个用法。

```shell
cd /path/to/repo

# 只保留只读工具：能读、能搜、能找、能列目录，不能改文件、不能跑命令
pi --tools read,grep,find,ls -p "说明 src/scheduler 的组织方式，列出关键文件与调用链"

# 需要审查 diff 时，把内容通过管道喂进去（只给 read 工具）
git diff main...HEAD | pi --tools read -p "审查这次改动，按严重程度列出问题"
```

预期结果：

```text
1. 启动 header 的 Tools 一行只列出 read / grep / find / ls 四项
2. 模型只做读取与搜索，任何写文件或执行命令的尝试都会因工具不可用而失败
3. stdout 只有最终回答（print 模式），中间过程不输出，便于再接 grep / jq 处理
4. 若未配置凭据，会以非零状态退出并在 stderr 打印 "No API key found..."
```

```text
要点：
1. 最小权限靠工具集 —— --tools 是白名单，写全你想要的，其余一律不可用
2. 加禁用更稳妥 —— --exclude-tools 'bash,write,edit' 在所有选择项之后统一生效
3. 注意 --tools 默认保留 MCP 工具，除非参数里出现带 mcp__ 前缀的条目
4. 只读组合不需要项目信任，但仍会加载 AGENTS.md（加 -nc / --no-context-files 可关）
5. 做成 shell alias 后，团队所有人的"问答模式"行为就一致了
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先用最小机制：给目录写 `AGENTS.md`，需要复用的提示写成模板，任务专属流程写成技能，只有要执行代码时才写扩展。层级越低，成本与风险越低。
2. 定期用 `pi --help` 取证：Pi 迭代快（本机为 1.2.0），工具名、参数、默认值都可能变，任何结论以本机帮助输出为准。
3. 把内核能力当成契约：默认只有 `read/bash/edit/write`，脚本里要用搜索能力就显式 `--tools` 打开，不要假设它们默认存在。
4. 用 package 固化团队实践：把团队自己的扩展、技能、提示模板打成 pi package 并钉住版本（`npm:@scope/pkg@1.0.0`），避免每人手工复制。
5. 项目资源一律先读再信任：项目级 `.pi/` 下的扩展、技能、包会执行代码或指示模型执行命令，代码评审通过后再 `/trust`。
6. 自动化里区分 stdout 与 stderr：`-p` 只把最终文本写 stdout、错误写 stderr，脚本应同时判断退出码与输出通道。

### 踩坑记录

```text
坑 1：以为 Pi 有权限确认弹窗，直接在生产仓库里无人值守跑
结论：Pi 默认不询问就直接执行工具调用，危险操作不会有二次确认。
原因：官方设计上砍掉了 permission popups，工具调用使用 Pi 进程的操作系统权限。
解法：用容器或沙箱隔离运行；确实需要确认流程就自己写扩展（如仓库 examples 里的 permission-gate）。

坑 2：把内置的 grep/find/ls 当默认能力，脚本换台机器就失败
结论：同样的命令在一台机器有搜索结果，在另一台报工具不可用。
原因：这三个只读工具默认关闭，只有 read/bash/edit/write 默认开启。
解法：显式声明 pi --tools read,bash,edit,write,grep,find,ls，或写进 defaultTools 设置。

坑 3：改了扩展或技能文件，行为却没变化
结论：编辑磁盘上的资源后，当前会话仍在跑旧实现。
原因：资源在启动或上次 reload 时已加载进进程，扩展运行时还持有旧状态。
解法：在交互里执行 /reload；注意 reload 会替换扩展运行时，await ctx.reload() 之后不能复用旧状态。

坑 4：把项目 .pi/ 目录当普通配置，克隆陌生仓库后直接启动
结论：启动 Pi 时项目扩展代码在本机进程内被执行。
原因：项目级扩展、技能、package 在项目信任通过后会加载并运行。
解法：用 -na / --no-approve 忽略本项目级资源，或先只读审查 .pi/ 与相关包源码再 /trust。

坑 5：用"内置了多少功能"做选型比较，得出错误结论
结论：按功能数量对比时 Pi 显得弱，但推广后反而更贴合团队流程。
原因：Pi 的定位是内核加扩展，功能数量不是它的评价指标，定制上限才是。
解法：按"需求能否在几十行扩展内满足""上下文是否可控""能否嵌入现有系统"三条评估。
```
