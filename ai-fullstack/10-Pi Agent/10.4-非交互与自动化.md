## 概述

Pi 有四种「不用人盯着」的用法：**print 模式**（只要最终文本）、**JSON 事件流模式**（要结构化过程）、**RPC 模式**（要双向控制的常驻进程）、**TypeScript SDK**（要进程内嵌入）。四者共用同一套 agent、会话、工具与资源，区别只在输入怎么进、输出怎么出、进程活多久。正因为内核一致，交互模式里调好的模型、工具白名单、`AGENTS.md`，在脚本里一行不改地复用。

本文的每个模式都有本机实测输出（Pi 1.2.0，2026-10-15）。因为本机未配置 provider 凭据，涉及「模型真正回答」的环节不可跑通，但**协议帧、输出通道、退出码、SDK 初始化**这些与凭据无关的部分全部是真实验证过的。

```text
四种非交互用法怎么选：
1. 只要最终文本（进文件、进管道）           → pi -p "..."          （print 模式）
2. 要结构化进度（进日志、进看板、做断言）    → pi --mode json "..." （JSON 事件流）
3. 要连续下命令、要进程隔离（IDE、服务）     → pi --mode rpc        （RPC 模式）
4. 要进程内调用、要完全控制（Node 服务）     → SDK: createAgentSession()
```

```text
$ pi --version
1.2.0
$ pi --help | grep -E '^\s+--(mode|print)'
  --mode <mode>                  Output mode: text (default), json, or rpc
  --print, -p                    Non-interactive mode: process prompt and exit
```

## print 模式与退出码

print 模式跑完给定提示后，把**最终助手文本**写入 stdout 然后退出，中间过程不暴露。它是 shell 管道与命令替换的默认搭档。还有一个方便之处：当你没有显式指定模式，而 stdin 或 stdout 之一不是终端时，Pi 会自动退化为 print 模式，所以 `git diff | pi "..."` 这种写法不用加任何参数。

```bash
# 基本用法
pi -p "总结这个仓库的结构"

# 官方示例写法（--print 与 -p 等价）
pi --print "Summarize the changes in this repository"

# 管道输入 + print 模式（无需显式指定模式）
git diff | pi --print "审查这次改动"

# 结果重定向到文件供后续步骤消费
pi -p "根据最近 10 个 commit 生成发布说明，只输出 Markdown" > release-notes.md
```

退出码与输出通道的契约是本机真实验证过的：

```text
$ pi -p "say hi"; echo "exit=$?"
No API key found for the selected model.

Use /login to log into a provider via OAuth or API key. See:
  .../pi-coding-agent/docs/providers.md
exit=1
```

| 情况 | stdout | stderr | 退出码 |
|---|---|---|---|
| 正常完成 | 最终助手文本 | 空 | 0 |
| 提供者出错或回复被中止（stop reason 为 `error` / `aborted`） | 无有效最终文本 | 错误信息 | 非 0 |
| 回复被模型输出上限截断（stop reason 为 `length`） | 打印已产出的部分文本 | 警告 | 非 0 |
| 未配置凭据 | 空 | `No API key found for the selected model.` | 1 |

**被截断也算失败**这一点很关键：CI 里如果只判断 stdout 非空，截断的回复会被当成成功结果发出去。正确做法是同时判断退出码。

```text
print 模式要点：
1. 只有最终文本 —— 中间事件不暴露，要看过程就用 JSON 模式
2. 错误走 stderr —— stdout 可以放心交给下游程序解析
3. length 截断非零退出 —— 别只判 stdout 是否非空，必须判退出码
4. 自动降级 —— 管道场景不写 --print 也会走 print 模式
5. 管道输入会拼进首个提示 —— stdin 内容前置到你的提示之前
```

## JSON 事件流模式

JSON 模式为**一次调用**输出结构化事件：第一条记录是 session header，随后是会话事件，提示跑完即退出。它不是「把回复包成 JSON」，而是完整的运行过程流——消息增量、工具执行生命周期、队列变化、压缩、重试，全都以 JSONL 一行一条写出。

```bash
# 基础用法：事件流写文件
pi --mode json "检查这个仓库" > events.jsonl

# 只挑完成态的消息（官方的典型用法）
pi --mode json "列出文件" 2>/dev/null | jq -c 'select(.type == "message_end")'

# 统计工具调用了多少次
pi --mode json "跑一遍测试" 2>/dev/null | jq -r 'select(.type=="tool_execution_start") | .toolName' | sort | uniq -c
```

本机真实输出（未配置凭据，验证的是帧格式与通道纪律）：

```text
$ pi --mode json "say hi" > out.jsonl 2> err.txt; echo "exit=$?"
exit=1

$ cat out.jsonl
{"type":"session","version":3,"id":"01a13d63-c83e-75a4-b0b5-a57f9f8fe5b9","timestamp":"2026-10-15T02:28:31.935Z","cwd":"/root/.hermes/cache/scratch"}

$ cat err.txt
No API key found for the selected model.
...
```

注意这里与 print 模式的一个差别：**JSON 模式下，助手回复失败或中止本身就出现在事件流里，不必然导致非零退出码**（这次退出码 1 是因为整个调用在建立模型时就抛错了）。所以消费 JSON 流时，成败要看事件内容，而不是只看退出码。

帧格式有三条硬约束，写客户端时必须遵守：

1. **严格 JSONL**：一条记录一个 JSON 对象，以 LF（`\n`）结尾；只在 LF 处切分，容忍可选的 `\r`。
2. **不要用会额外切分的行读取器**：Node.js 的 `readline` 还会在 Unicode 行分隔符（`U+2028`、`U+2029`）处断行，而它们在 JSON 字符串里是合法内容。用字节流或 UTF-8 流解码器。
3. **持续读 stdout**：读端停止消费会让管道缓冲区填满，从而阻塞 Pi；stdout 只放协议记录，诊断日志走 stderr。

事件类型（JSON 与 RPC 共享同一套会话事件）：

| 事件 | 关键字段 | 含义 |
|---|---|---|
| `agent_start` | 无 | 一次底层 agent run 开始 |
| `agent_end` | `messages`、`willRetry` | 该底层 run 结束；之后仍可能有重试、压缩恢复或排队工作 |
| `agent_settled` | `aborted` | Pi 不会再有自动续跑工作，可以判定"真的干完了" |
| `turn_start` / `turn_end` | `turn_end` 带 `message`、`toolResults` | 一个助手回合的开始与结束（回合 = 回复 + 其触发的工具调用与结果） |
| `message_start` / `message_update` / `message_end` | `message`、`usage`、`assistantMessageEvent` | 消息生命周期；`message_end.message` 才是权威最终消息 |
| `tool_execution_start` / `_update` / `_end` | `toolCallId`、`toolName`、`args`、`result`、`isError`、`durationMs` | 工具执行生命周期，用 `toolCallId` 关联 |
| `queue_update` | `steering`、`followUp` | 排队消息变化（字段是当前完整队列） |
| `compaction_start` / `compaction_end` | `reason`、`result` | 压缩开始与结果（`reason` 为 `manual` / `threshold` / `overflow`） |
| `auto_retry_start` / `auto_retry_end` | `attempt`、`maxAttempts`、`success` | 助手回合自动重试 |
| `extension_error` | `extensionPath`、`event`、`error` | 扩展处理器抛错（仅 RPC） |

流式消息要靠增量自己拼：`message_update` 是**纯增量**的，只带 `assistantMessageEvent`，其 `type` 可能是 `text_start` / `text_delta` / `text_end`、`thinking_*`、`toolcall_*`。做法是用 `contentIndex` 定位内容块、累加 `delta` 做实时显示，收到 `text_end` / `thinking_end` / `toolcall_end` 时用其中的权威内容替换，最后整体以 `message_end.message` 覆盖。

```text
JSON 模式要点：
1. 第一条是 session header —— 用它拿会话 ID、时间戳与工作目录
2. agent_end 不等于干完 —— 判定完工要等 agent_settled
3. 增量要拼、不要信快照 —— message_update 只有 delta，message_end 才权威
4. 帧只认 LF —— 别用 Node readline 之类会按 Unicode 分隔符断行的读取器
5. 成败看事件 —— 模型失败会在流里体现，未必改变退出码
```

## RPC 模式与协议帧

RPC 模式把 Pi 跑成一个**长驻子进程**，用 stdin 收命令、stdout 发响应与事件，一行一个 JSON 记录。它适合语言无关的集成、需要进程隔离的场景、IDE 和自定义客户端。协议共四类记录：stdin 上的**命令**、stdout 上的**响应**、stdout 上的**会话事件**、双向的**扩展 UI 记录**。

```bash
# 启动 RPC 模式（常驻；--no-session 表示不落盘）
pi --mode rpc --no-session

# 仍然可以传常规 CLI 选项来固定工作目录、模型、工具与会话
pi --mode rpc --no-session --provider anthropic --model sonnet:high \
   --tools read,bash,edit,write --session-dir /data/pi-sessions
```

RPC 模式**拒绝 `@file` 参数**，文件引用要通过 `prompt` 命令的内容表达。命令与响应用可选的 `id` 字段配对；命令处理是异步的，客户端必须**按 ID 关联而不是按响应顺序**。本机真实握手：

```text
$ cat rpc_probe.py
import json, subprocess
process = subprocess.Popen(["pi", "--mode", "rpc", "--no-session"],
                           stdin=subprocess.PIPE, stdout=subprocess.PIPE,
                           stderr=subprocess.PIPE, text=True)
process.stdin.write(json.dumps({"id": "req-1", "type": "get_state"}) + "\n")
process.stdin.flush()
print(process.stdout.readline().strip())
process.stdin.close(); process.wait(timeout=20)

$ timeout 60 python3 rpc_probe.py
{"id":"req-1","type":"response","command":"get_state","success":true,"data":{"model":{"id":"unknown","name":"unknown","api":"unknown","provider":"unknown","baseUrl":"","reasoning":false,"input":[],"cost":{"input":0,"output":0,"cacheRead":0,"cacheWrite":0},"contextWindow":0,"maxTokens":0},"thinkingLevel":"off","isStreaming":false,"isCompacting":false,"steeringMode":"one-at-a-time","followUpMode":"one-at-a-time","sessionId":"01a13d63-c36f-769a-bd74-f60a3a1870b3","autoCompactionEnabled":true,"messageCount":0,"pendingMessageCount":0}}
EXIT: 0
```

这条真实响应同时验证了几件事：响应里回带了请求的 `id`；`success: true` 表示命令被处理；未登录时 `model` 是占位对象（`id: "unknown"`）；`sessionId` 即使没有落盘也存在。

下一条命令（发提示）与它的语义：

```json
{"id":"req-2","type":"prompt","message":"Review this repository"}
{"id":"req-2","type":"response","command":"prompt","success":true,"data":{"disposition":"started"}}
```

`data.disposition` 说明提示的去向：`started`（接受并启动了一次 run）、`queued`（运行中排队）、`handled`（被扩展命令或输入处理器消费，不会有 run）。**`success: true` 只表示提示被接受，不表示模型干完了**；要等 `agent_settled` 事件才算结束。流式期间再发提示必须带 `streamingBehavior`：`"steer"`（当前回合工具跑完后插入）或 `"followUp"`（等 agent 停下来再投递）；不指定会直接报错。

常用命令族（完整参考见官方 RPC Commands 页）：

| 类别 | 命令 |
|---|---|
| 提示控制 | `prompt`、`steer`、`follow_up`、`abort`、`clear_queue`、`new_session` |
| 状态查询 | `get_state`、`get_messages`、`get_session_stats`、`get_last_assistant_text` |
| 模型与思考 | `set_model`、`cycle_model`、`get_available_models`、`set_thinking_level`、`cycle_thinking_level` |
| 压缩与重试 | `compact`、`set_auto_compaction`、`set_auto_retry`、`abort_retry` |
| 直接执行 shell | `bash`、`abort_bash`（`bash` 的每段输出会以 `bash_execution_update` 事件流式返回） |
| 会话管理 | `switch_session`、`fork`、`clone`、`get_tree`、`get_entries`、`set_session_name` |
| 发现能力 | `get_commands`（列出当前会话可用的命令） |

错误处理同样简单：失败命令返回一条 `success: false` 的响应，例如 `{"id":"req-3","type":"response","command":"set_model","success":false,"error":"Model not found: invalid/model"}`；收到无法解析的 JSON 时，Pi 会返回一条没有请求 ID 的 `command: "parse"` 响应。**关闭子进程的 stdin 请求有序退出**，Pi 会先清理活动运行时再退出；客户端仍要处理进程信号与意外退出，并且不要试图解析 stderr（那是诊断信息，不是协议数据）。

```text
RPC 模式要点：
1. 长驻双向 —— 命令进 stdin，响应与事件出 stdout，一行一条
2. 按 ID 关联 —— 命令处理异步，响应顺序不可依赖
3. success 不等于完成 —— prompt 的 success 只表示被接受，等 agent_settled
4. 流中插话要声明 —— streamingBehavior 取 steer 或 followUp，否则报错
5. 优雅关闭 —— 关 stdin 让 Pi 有序退出，同时仍要兜住进程信号与异常退出
```

## TypeScript SDK 嵌入

SDK 不经过 CLI，直接把 agent 嵌进 Node.js 或 Bun 进程：`@earendil-works/pi-coding-agent` 包导出 `createAgentSession`、`SessionManager` 等 API。需要进程内完全控制（自定义存储、自定义资源加载、把 Pi 当作库）时选它；需要语言无关或进程隔离，仍然用 RPC。

```typescript
import { createAgentSession, SessionManager } from "@earendil-works/pi-coding-agent";

const { session } = await createAgentSession({
  cwd: process.cwd(),                    // 工作目录：资源发现、上下文文件、会话分组
  sessionManager: SessionManager.inMemory(), // 不落盘的会话历史
});

// 先订阅再发提示，否则可能漏掉快速完成的事件
const unsubscribe = session.subscribe((event) => {
  if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});

try {
  await session.prompt("这个目录里有哪些文件？");
  console.log(session.getLastAssistantText());
} finally {
  unsubscribe();
  session.dispose();   // 中止活动工作、失效扩展上下文、解绑监听
}
```

本机真实冒烟测试（不调用模型，只验证 SDK 能创建会话并读出默认状态）：

```text
$ cat pi-sdk-probe.mjs
import { createAgentSession, SessionManager } from ".../pi-coding-agent/dist/index.js";
const { session } = await createAgentSession({
  cwd: "/root/.hermes/cache/scratch",
  sessionManager: SessionManager.inMemory(),
});
try {
  console.log("model:", session.model?.id ?? "(none)");
  console.log("thinkingLevel:", session.thinkingLevel);
  console.log("tools:", session.getActiveToolNames().join(","));
  console.log("messages:", session.messages.length);
} finally { session.dispose(); }

$ timeout 60 node pi-sdk-probe.mjs
model: unknown
thinkingLevel: off
tools: read,bash,edit,write
messages: 0
exit=0
```

输出里 `tools: read,bash,edit,write` 与 CLI 的默认工具集完全一致——同一套内核在这里得到了印证；`model: unknown` 说明没有可用凭据时 SDK 照样能建会话，只是模型是占位对象。

SDK 的关键契约：

| 主题 | 行为 |
|---|---|
| 会话所有权 | `createAgentSession()` 返回的 `AgentSession` 拥有一个会话及其模型、工具、排队消息、压缩状态与扩展运行时 |
| 状态读取 | `session.messages`、`session.model`、`session.thinkingLevel`、`session.systemPrompt`、`session.getActiveToolNames()` |
| 持久化 | 默认持久化；`SessionManager.inMemory()` 提供纯内存会话；分支只移动活跃叶子，不删除被放弃的分支 |
| 发提示 | `prompt()` 会先处理扩展命令与提示模板；流式期间发提示必须声明 steer 还是 follow；`steer()` / `followUp()` 返回 `"queued"` 或 `"handled"` |
| 中断与等待 | `abort()` 停止当前操作并等待空闲；`waitForIdle()` 只等待不中断 |
| 事件 | `session.subscribe()`；`message_end` 是权威消息，`agent_end` 不代表干完，`agent_settled` 才是 |
| 可替换的服务 | `modelRuntime` / `model` / `thinkingLevel` / `scopedModels`、`settingsManager`、`sessionManager`、`resourceLoader`、`tools` / `noTools` / `excludeTools` / `customTools` |
| 会话运行时切换 | `AgentSessionRuntime` 提供 `newSession()`、`switchSession()`、`fork()`、`importFromJsonl()`，它会替换掉活动的 `AgentSession`，旧订阅必须重绑 |
| 与 CLI 的差异 | CLI 默认加载 `codemode`、`tool_search` 与 MCP 三个内置扩展；SDK 会话不加载，需要自己把对应工厂加进 `DefaultResourceLoader` 的 `extensionFactories` |

```text
SDK 要点：
1. 先 subscribe 再 prompt —— 否则快速完成的事件可能看不到
2. dispose 必做 —— 它中止活动工作、失效扩展上下文并解绑监听
3. 会话历史归 SessionManager —— 直接改 session.agent.state.messages 不会替换持久化上下文
4. 默认工具与 CLI 相同 —— read / bash / edit / write，可用 tools / excludeTools 收窄
5. 内置扩展要自己挂 —— codemode、tool_search、MCP 在 SDK 里不是自动加载的
```

## 非交互场景的凭据与配置

自动化里最容易出问题的不是模式选择，而是凭据与作用域。三条经验：**用环境变量而不是 `auth.json`**（不落盘、作用域可控）、**用探针先验证再干活**（`pi auth check --json` 比跑一次真实请求便宜）、**把工作目录与会话目录显式写出来**（CI 里 `cd` 的语义和本地不同）。

```bash
# 1. 凭据：环境变量（在启动 pi 之前 export，或在 CI 的 step env 里给）
export ANTHROPIC_API_KEY=sk-ant-...

# 2. 探针：先确认 provider 就绪，再决定是否继续（退出码 0/1/2 可直接判断）
pi auth check --provider anthropic --json

# 3. 一次性覆盖（不落盘；需配合 --model 或 --models）
pi --model sonnet:high --api-key "$CI_TEMP_KEY" -p "生成变更摘要"

# 4. 关掉启动期网络行为（离线 runner、气隙环境）
pi --offline -p "基于本地文件回答"
# 等价写法：export PI_OFFLINE=1

# 5. 会话与工作目录显式化
cd "$GITHUB_WORKSPACE"
pi --session-dir "$RUNNER_TEMP/pi-sessions" --no-session -p "只读分析"
```

一个常被忽略的细节：**pi 的凭据优先级是 `--api-key` > `auth.json` > `models.json` 的 `apiKey` > 环境变量**。所以「我在 CI 里 export 了 key」并不意味着它会被使用——如果 runner 上残留了一份 `auth.json`，实际走的是那份。无状态 runner 通常没这个问题，但自建 runner 一定要检查。

```text
凭据与配置要点：
1. 环境变量优先于文件 —— 自动化中不要依赖 auth.json
2. 先探针后干活 —— pi auth check --json 失败就别调用模型
3. --api-key 需配 --model —— 它只是临时覆盖凭据，不负责选 provider
4. --no-session 用于一次性任务 —— 不落盘，避免并发任务互相污染
5. --offline / PI_OFFLINE 关网络 —— 但会跳过模型目录刷新，气隙环境需预置目录
```

## 脚本与 CI 集成

把 Pi 放进流水线的关键是把「不确定性」收窄：固定版本、固定模型、固定工具白名单、固定输出通道，并且**永远判断退出码**。另外，fork 源码时可以通过 `package.json` 改 CLI 名字与配置目录，这对企业内部分发很有用。

```yaml
# .github/workflows/pi-review.yml
name: Review with Pi
on:
  workflow_dispatch:

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0

      - uses: actions/setup-node@v4
        with:
          node-version: "22.19"          # Pi 要求 >= 22.19

      - name: Install Pi (pinned)
        run: npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.2.0

      - name: Credential probe
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: pi auth check --provider anthropic --json

      - name: Generate review notes (print mode)
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          git diff origin/main...HEAD \
            | pi -p --tools read,grep,find,ls "审查这次改动，按严重程度列出问题，只输出 Markdown" \
            > review-notes.md

      - name: Collect structured events (JSON mode)
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          pi --mode json --tools read,grep,find,ls "统计测试目录的规模并给出三条建议" \
            > events.jsonl 2> pi-stderr.log
          jq -r 'select(.type=="message_end") | .message.role' events.jsonl | sort | uniq -c

      - uses: actions/upload-artifact@v4
        with:
          name: pi-review
          path: |
            review-notes.md
            events.jsonl
```

**自定义 CLI 名字与配置目录**（源码 fork 场景）——改 `package.json` 即可影响横幅、配置路径与派生出的环境变量名：

```json
{
  "piConfig": {
    "name": "my-agent",
    "configDir": ".my-agent"
  }
}
```

```text
CI 集成要点：
1. 钉版本 —— @1.2.0 让流水线行为可复现
2. 先探针 —— auth check 失败就早停，别把密钥问题留到模型调用时报错
3. 工具白名单 —— 审查类任务给只读工具，减少"它顺手改了文件"的风险
4. 通道分离 —— 结果写文件、诊断写 stderr，别让两股内容混在一起
5. 退出码与事件双判 —— print 看退出码，JSON 看事件内容
```

## 应用场景实战

### 场景一：在 CI 里用 print 模式生成发布说明

场景：每次发版前需要一份人类可读的发布说明，内容只能来自真实提交历史，且不能给 agent 写权限。

```bash
#!/usr/bin/env bash
# .ci/release-notes.sh —— 生成发布说明（只读工具 + print 模式 + 退出码判断）
set -euo pipefail

: "${ANTHROPIC_API_KEY:?请在 CI 中提供 ANTHROPIC_API_KEY}"

# 1. 前置探针：凭据不行就直接失败，避免白跑
pi auth check --provider anthropic --json > /dev/null

# 2. 组装输入：最近 20 个提交的完整信息
git log -20 --pretty=format:'%h %ad %an %s' --date=short > "$RUNNER_TEMP/recent-commits.txt"

# 3. print 模式：只读工具、结果写文件、stderr 单独留档
cat "$RUNNER_TEMP/recent-commits.txt" | \
  pi -p --tools read,grep,find,ls \
     "根据上面的提交记录写发布说明，按 feat/fix/refactor/docs 分组，只输出 Markdown" \
     > release-notes.md 2> pi-print.log

# 4. 兜底判断：退出码非 0 或产物为空都视为失败
test -s release-notes.md
head -5 release-notes.md
```

```text
预期结果：
1. 探针通过后才会真正调用模型
2. release-notes.md 只包含 Markdown 正文（print 模式不会混入过程事件）
3. 若模型回复被输出上限截断，退出码非 0，set -e 会让这一步直接失败
4. pi-print.log 里保存了 stderr 诊断，便于复盘
```

```text
要点：
1. 只读工具白名单 —— 发布说明任务不需要写文件或跑命令
2. 输入来自命令输出 —— 提交记录由 git 提供，不是让模型凭记忆写
3. 空的产物算失败 —— test -s 拦住"退出码 0 但内容为空"的边界情况
4. stderr 留档 —— print 模式的错误信息是排障第一手材料
5. 探针放在最前 —— 凭据问题在几秒内暴露，不用等到模型调用
```

### 场景二：用 Python 服务通过 RPC 长驻驱动 Pi

场景：内部平台要用 Python 写后端，但想复用 Pi 的能力（读文件、跑命令、开会话）。RPC 模式提供语言无关的边界，进程隔离还带来了「Pi 崩了不影响主服务」的好处。

```python
# pi_driver.py —— 长驻 RPC 客户端：发提示、流式收文本、等 agent_settled、优雅关闭
import json
import subprocess
import sys

class PiDriver:
    def __init__(self, cwd: str, tools: str = "read,grep,find,ls"):
        self.proc = subprocess.Popen(
            ["pi", "--mode", "rpc", "--no-session", "--tools", tools],
            cwd=cwd,
            stdin=subprocess.PIPE,
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE,
            text=True,
            bufsize=1,            # 行缓冲：协议是严格 JSONL
        )
        self.seq = 0

    def _send(self, record: dict) -> str:
        self.seq += 1
        record["id"] = f"req-{self.seq}"
        self.proc.stdin.write(json.dumps(record) + "\n")
        self.proc.stdin.flush()
        return record["id"]

    def prompt_and_wait(self, message: str, timeout_s: int = 300) -> str:
        """发送提示，聚合流式文本，直到 agent_settled"""
        req_id = self._send({"type": "prompt", "message": message})
        buffer = []
        for line in self.proc.stdout:          # 逐行读，只按 LF 切分
            event = json.loads(line)
            etype = event.get("type")
            if etype == "message_update":
                inner = event["assistantMessageEvent"]
                if inner["type"] == "text_delta":
                    buffer.append(inner["delta"])
            elif etype == "message_end":
                msg = event["message"]
                if msg.get("role") == "assistant":
                    buffer = [msg.get("content", [{}])[0].get("text", "")] if msg.get("content") else buffer
            elif etype == "agent_settled":      # 真正干完
                break
        return "".join(buffer)

    def close(self):
        self.proc.stdin.close()                # 关 stdin 请求有序退出
        self.proc.wait(timeout=30)


if __name__ == "__main__":
    driver = PiDriver(cwd=".", tools="read,grep,find,ls")
    try:
        print(driver.prompt_and_wait("列出当前目录最大的 5 个文件并解释用途"))
    finally:
        driver.close()
```

```python
# 最小握手（本机已实测这段的输出，见上文 get_state 真实响应）
import json, subprocess
p = subprocess.Popen(["pi", "--mode", "rpc", "--no-session"],
                     stdin=subprocess.PIPE, stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True)
p.stdin.write(json.dumps({"id": "req-1", "type": "get_state"}) + "\n")
p.stdin.flush()
print(p.stdout.readline().strip())   # {"id":"req-1","type":"response","command":"get_state","success":true,...}
p.stdin.close(); p.wait(timeout=20)
```

```text
要点：
1. 按 ID 关联 —— 高并发时多条命令同时在飞，绝不能依赖响应顺序
2. 等 agent_settled —— prompt 的 success 只代表被接受，agent_end 之后仍可能有重试
3. 行读取只按 LF —— Python 的 text 模式 + bufsize=1 足够；不要引入会按 Unicode 分隔符断行的解析器
4. 收尾要关 stdin —— 这是官方认可的优雅退出方式，同时给 wait 设超时
5. 读 stderr 另起线程或留到异常时 —— stderr 是诊断，不是协议数据
```

### 场景三：在 Node 服务里用 SDK 嵌入一个只读问答端点

场景：给内部文档站加一个「问这个仓库」的接口，要求进程内调用、不落盘会话、工具只读、每个请求独立。

```typescript
// pi-endpoint.ts —— SDK 嵌入示例：只读工具 + 内存会话 + 逐请求隔离
import { createAgentSession, SessionManager } from "@earendil-works/pi-coding-agent";

export async function answer(repoDir: string, question: string): Promise<string> {
  const { session } = await createAgentSession({
    cwd: repoDir,
    sessionManager: SessionManager.inMemory(),     // 不落盘，请求之间不共享
    tools: ["read", "grep", "find", "ls"],         // 只读白名单
    thinkingLevel: "low",                          // 问答场景压低推理预算
  });

  const unsubscribe = session.subscribe((event) => {
    if (event.type === "tool_execution_start") {
      console.error(`[pi] ${event.toolName}`);     // 可观测性：日志走 stderr
    }
  });

  try {
    await session.prompt(question);                // 不接受流式输入时无需 streamingBehavior
    return session.getLastAssistantText() ?? "";
  } finally {
    unsubscribe();
    session.dispose();                             // 每个请求结束后彻底释放
  }
}
```

```text
要点：
1. 内存会话 —— SessionManager.inMemory() 避免并发请求写同一份 JSONL
2. 工具白名单 —— tools 收窄到只读四个，端点无法改文件
3. 逐请求 dispose —— dispose 会中止活动工作并解绑监听，防止泄漏
4. 观察工具调用 —— 订阅 tool_execution_start 就能做审计日志
5. 差异要记住 —— CLI 默认带 codemode/tool_search/MCP，SDK 不带，需要时自己挂
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优先 print 模式解决 90% 的自动化需求：只要最终文本就用 `-p`，需要过程再升级到 JSON，需要交互式控制才上 RPC 或 SDK。
2. 永远判断退出码：`-p` 在出错、被中止、被输出上限截断时都会非零退出，只看 stdout 会把截断结果当成成功。
3. 用 `--tools` 显式收窄权限：自动化任务一律显式列出需要的工具，审查类任务只给只读工具，别依赖默认值。
4. JSON 流要用字节级读取器：只按 LF 切分、持续消费、用 `agent_settled` 判定结束。
5. RPC 客户端按 `id` 关联响应：命令处理是异步的，响应顺序不可依赖；关闭时关 stdin 而不是杀进程。
6. 探针前置：流水线第一步跑 `pi auth check --provider <name> --json`，凭据问题在最便宜的阶段暴露。

### 踩坑记录

```text
坑 1：用 print 模式却只检查 stdout 是否为空
结论：被输出上限截断的回复照样有文本，流水线把它当成完整结果发出去。
原因：stop reason 为 length 时 Pi 会打印部分文本，只把警告写到 stderr 并设非零退出码。
解法：同时判断退出码与产物非空（例如 test -s 或 shell 的 set -e），必要时再读 stderr 警告。

坑 2：用 Node 的 readline 消费 JSON 事件流，偶发解析失败
结论：解析在看似随机的行上抛异常，长文本回复时更容易复现。
原因：JSONL 只以 LF 为记录边界，而 readline 还会在 U+2028、U+2029 处断行，这两个字符在 JSON 字符串里合法。
解法：改用字节流或 UTF-8 流解码器，只按 LF 切分并容忍可选的 \r。

坑 3：看到 agent_end 就认为任务完成，结果漏掉后续内容
结论：客户端提前返回，用户看到不完整的回答。
原因：agent_end 只结束一次底层 run，之后还可能有自动重试、溢出恢复、压缩恢复、steering 或排队工作。
解法：等 agent_settled 事件再判定结束；agent_end 只用于观察单次 run。

坑 4：在模型还在流式时发第二条 prompt，RPC 返回错误
结论：命令失败，日志里出现关于 streamingBehavior 的错误。
原因：流式期间发送的提示必须声明是 steer 还是 followUp，否则 Pi 直接拒绝而不是替你猜。
解法：给 prompt 加 "streamingBehavior": "steer" 或 "followUp"；不需要插话就先 abort 或等 agent_settled。

坑 5：CI runner 上 export 了 key，Pi 却用了别的凭据
结论：调用成功但走的是错误账号，或反过来报"未配置凭据"。
原因：凭据优先级为 --api-key > auth.json > models.json 的 apiKey > 环境变量；自建 runner 上常残留 auth.json。
解法：用 pi auth check --json 确认实际来源；一次性任务用 --api-key 显式覆盖，并定期清理 runner 上的 ~/.pi/agent。

坑 6：SDK 里没等 subscribe 就先 prompt，漏掉首批文本
结论：流式输出开头缺失，最终消息却不缺。
原因：订阅晚于事件产生，快速完成的事件已经发出去了。
解法：先 session.subscribe() 再调用 prompt()；RPC 侧同理，先装监听再发提示（RpcClient.promptAndWait() 内部就是这么做的）。
```
