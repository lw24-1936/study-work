## 概述

Pi 是一个「最小 harness + 可扩展」的终端 Agent：它本身不预设你的工程习惯，而是把规则文件、系统提示、技能描述、工具定义，按固定顺序拼进每一次模型请求。理解这套上下文装配顺序，才能解释「为什么我写的 AGENTS.md 没生效」「为什么项目里的扩展被跳过了」「为什么上下文突然被压缩」。

规则与上下文在 Pi 里分成三层，职责不重叠：上下文文件（AGENTS.md / CLAUDE.md）是跨目录继承的长期约束，SYSTEM.md / APPEND_SYSTEM.md 只影响系统提示本身，项目信任（project trust）决定一个目录下的可执行资源能不能被加载。

```text
本篇要解决的问题：
1. AGENTS.md 与 CLAUDE.md 从哪里加载、谁覆盖谁、与项目信任是什么关系
2. SYSTEM.md / APPEND_SYSTEM.md 如何替换或追加系统提示
3. 一次模型请求到底由哪些部分组成（分支历史、系统提示、工具、技能描述）
4. 项目信任保护哪些资源、trust.json 存在哪、无人值守模式怎么决策
5. Pi 的权限模型：什么时候会问你、扩展怎么加确认、为什么它不是沙箱
6. 会话以什么形式、存在哪个目录、怎么换位置和清理
```

本篇命令与实际输出以本机安装的 `@earendil-works/pi-coding-agent@1.2.0` 实测为准（`pi --version` 输出 `1.2.0`）；官方文档见 `https://pi.dev/docs/latest/configuration`、`https://pi.dev/docs/latest/security`、`https://pi.dev/docs/latest/sessions`、`https://pi.dev/docs/latest/how-pi-works`。

## 上下文文件的发现与加载

上下文文件是「随目录生效的长期指令」。Pi 从 agent 目录、当前工作目录、以及当前目录的所有父目录里查找这些文件名：`AGENTS.override.md`、`AGENTS.md`、`AGENTS.MD`、`CLAUDE.md`、`CLAUDE.MD`。一个上下文文件只要 Pi 运行在它所在目录或其任何子目录下就会生效——也就是说放在仓库根目录的 `AGENTS.md`，在 `packages/api/` 里跑 Pi 时同样会被加载。

`AGENTS.override.md` 只在**同一个目录内**替换 `AGENTS.md` 或 `CLAUDE.md`，它不会压制 agent 目录或其他目录里的上下文文件。多个目录同时存在上下文文件时，它们会被一起收集进系统提示，而不是只取最近的一个。

```shell
# 项目根目录放一份团队通用规则
/opt/app/AGENTS.md

# 子包放一份更具体的补充规则，父子两份都会被加载
/opt/app/packages/api/AGENTS.md

# 临时改用 override 文件替换同目录的 AGENTS.md（不改原文件）
/opt/app/AGENTS.override.md

# 完全关闭上下文文件加载（排查「指令是否来自 AGENTS.md」时很有用）
pi -nc
pi --no-context-files
```

用 `pi --help` 确认该开关确实存在（本机实测输出节选）：

```text
--no-context-files, -nc        Disable AGENTS.md and CLAUDE.md discovery and loading
```

上下文文件的发现**不需要项目信任**：官方文档明确写了 context-file discovery does not require project trust。这意味着一个不可信仓库里的 `AGENTS.md` 内容仍会进入模型上下文，它属于「不可信输入」，不是被信任的配置。

```text
上下文文件要点：
1. 搜索范围：agent 目录 + 当前目录 + 所有父目录，落在哪一层，就对那层及以下生效
2. 文件名集合：AGENTS.override.md、AGENTS.md、AGENTS.MD、CLAUDE.md、CLAUDE.MD
3. AGENTS.override.md 只在同目录替换 AGENTS.md / CLAUDE.md，不压制其他目录
4. 多个目录的上下文文件会同时进入系统提示
5. 不加载只需要一个开关：--no-context-files 或 -nc
6. 上下文文件的发现不受项目信任保护，文件内容一律当不可信输入看待
```

## 系统提示的替换与追加

上下文文件是「往默认提示里加料」，`SYSTEM.md` 与 `APPEND_SYSTEM.md` 则是直接改写系统提示本身。它们有两套位置：agent 目录（`~/.pi/agent/SYSTEM.md`、`~/.pi/agent/APPEND_SYSTEM.md`）与项目目录（`.pi/SYSTEM.md`、`.pi/APPEND_SYSTEM.md`）。`SYSTEM.md` 替换 Pi 的默认系统提示，`APPEND_SYSTEM.md` 在系统提示后追加内容；被信任的项目文件优先于 agent 目录的同名文件，两者**不会被合并**。

一次性覆盖可以走命令行，`--system-prompt` 与 `--append-system-prompt` 都接受文本或文件路径，并且可以重复使用：

```shell
# 用文件替换整个系统提示（比如公司统一的评审规范）
pi --system-prompt ./company-prompt.md

# 追加两条独立规则，同一开关可重复
pi --append-system-prompt "所有回复用中文" --append-system-prompt ./team-style.md
```

项目级配置写文件更稳，改完用 `/reload` 让它生效：

```shell
mkdir -p .pi
cat > .pi/APPEND_SYSTEM.md << 'EOF'
# 项目附加规则

- 技术栈：Python 3.12 + FastAPI + PostgreSQL 16
- 提交信息遵循 Conventional Commits
- 任何数据库迁移必须先给出可回滚方案
EOF

pi
```

交互模式下输入 `/reload`，Pi 会重新加载 keybindings、extensions、skills、templates、themes 和上下文文件——这是改完规则文件后不重启 Pi 的标准做法。

扩展层还有更细的控制：`before_agent_start` 事件里可以拿到 `event.systemPromptOptions`，它包含 `customPrompt`（来自 `--system-prompt`、`SYSTEM.md` 或自定义模板的提示前缀）、`selectedTools`、`toolSnippets`、`promptGuidelines`、`sections`、`appendSystemPrompt`、`cwd`、`contextFiles`、`skills`。官方文档特别强调两点：优先修改 `sections`、`selectedTools` 或 `promptGuidelines`，因为 Pi 会 diff 出变化的片段并只追加一个补丁系统消息，保持前缀缓存有效；而直接返回 `systemPrompt` 或用 `forceSystemPrompt` 会替换整个提示，每次变化都是一次缓存失效。

```text
系统提示要点：
1. SYSTEM.md 替换默认系统提示，APPEND_SYSTEM.md 追加，二者不合并
2. 位置有两套：~/.pi/agent/ 与项目 .pi/，项目文件优先（需项目信任）
3. 命令行临时覆盖用 --system-prompt 与 --append-system-prompt（可重复）
4. 改完文件在交互模式执行 /reload，不必重启进程
5. 扩展里优先改 systemPromptOptions.sections / toolGuidelines，避免整段替换导致缓存失效
```

## 一次请求的上下文拼装

模型每次请求拿到的不是「整个会话文件」，而是**活动分支**加上一组运行时输入。把会话看成树：每个条目有 `id` 和 `parentId`，从根走到当前条目的那条路径就是活动分支（active branch），它提供对话历史。分支之外的条目仍留在文件里，只是不进上下文。

系统提示由 Pi 的基础指令加发现到的上下文文件构成；请求里还携带工具定义和技能描述。技能只有**描述**进入系统提示，完整指令在任务匹配时才由模型读取 `SKILL.md`，这正是不把上下文一次性撑爆的关键设计。

```text
一次模型请求的组成：
1. system prompt   = 基础指令 + 上下文文件（+ SYSTEM.md / APPEND_SYSTEM.md 的改写）
2. 工具定义         = 已启用工具的名称、描述、参数 schema
3. 技能描述         = 每个技能的 name + description（完整 SKILL.md 按需读取）
4. 对话历史         = 活动分支转成 user / assistant / tool-result 消息
5. 本次输入         = 提示模板展开后的文本、@ 选中的文件、图片、粘贴文本、! 命令输出
```

交互模式里，编辑器输入到用户消息之间还有一段展开逻辑：提示模板先展开（`/name`），`@` 选中的文件、图片、粘贴文本、以及 `!command` 的 shell 输出都会成为消息内容。会话底部状态栏显示当前上下文用量，`/session` 给出更完整的文件路径、ID、消息数、token 用量与成本。

```shell
# 查看当前会话的统计信息（交互模式）
/session

# 手动压缩上下文，可带聚焦指令
/compact 保留最近的数据库迁移决策

# 回到树上的某个用户消息重新编辑，形成新的分支
/tree
```

如果要把这些状态看清楚，可以走 RPC 模式用机器可读的方式观察。下面这段是本机真实执行的结果（工作目录 `/root/.hermes/cache/scratch/pitest`，无关的 model 字段已省略）：

```text

{"id":"1","type":"response","command":"get_state","success":true,"data":{"model":{...},
 "thinkingLevel":"off","isStreaming":false,"isCompacting":false,"steeringMode":"one-at-a-time",
```

`autoCompactionEnabled: true` 说明自动压缩默认开启；`sessionFile` 直接给出了会话落盘位置（见本篇后面的「会话持久化与存储位置」）。

```text
上下文拼装要点：
1. 模型只看见活动分支，树里被放弃的分支不占上下文
2. 技能以 name + description 常驻系统提示，完整指令按需读取
3. 提示模板在输入变成用户消息之前展开，属于纯文本替换
4. @ 文件、图片、粘贴文本、! 命令输出都会变成消息内容
5. 输入框下方的状态栏与 /session 是判断上下文压力的第一手依据
```

## 项目信任与资源加载边界

项目信任（project trust）解决的是一个具体问题：一个陌生仓库里可能存在可执行的项目资源，Pi 不应该在你没同意前就把它们加载进进程。以下资源一旦在**当前工作目录**被发现，Pi 就要求一个信任决策：

```text
需要信任决策的资源：
1. .pi/settings.json
2. .pi/mcp.json
3. .pi/extensions、.pi/skills、.pi/prompts、.pi/themes
4. .pi/SYSTEM.md 或 .pi/APPEND_SYSTEM.md
5. 当前目录或祖先目录里的项目 .agents/skills
```

只有一个空的 `.pi` 目录（不含上述内容）不需要信任。拒绝信任时，这些资源被跳过，但**上下文文件照样加载**。

决策顺序是固定的：命令行 `--approve` / `--no-approve` 优先级最高；其次由用户级或命令行扩展处理 `project_trust` 事件（第一个返回 yes/no 的扩展拥有决定权，并会抑制内置的信任提示）；都没有时查已保存的决策；最后落到 `defaultProjectTrust`，默认值是 `"ask"`。已保存的决策用规范化目录路径，存在 `~/.pi/agent/trust.json`，交互模式里用 `/trust` 保存。


## 权限与确认提示

Pi **不是**「每个工具调用都弹窗确认」的设计。官方安全文档的原话是：Pi can read, change, and execute files with the permissions of the account that started it, and it does not ask for approval before every tool call。所以确认提示是**由扩展按需添加**的能力，而不是内置的逐调用审批层。

自定义权限门（permission gate）的标准写法是监听 `tool_call` 事件，返回 `{ block: true, reason }` 阻断调用。下面这个扩展在每次 `bash` 调用前检查是否包含危险片段，命中就询问用户：

```typescript
// ~/.pi/agent/extensions/guard.ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

const DANGEROUS = [/\brm\s+-rf\b/, /\bsudo\b/, /git\s+push\s+--force/];

export default function (pi: ExtensionAPI) {
  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName !== "bash") return;
    const command = String(event.input.command ?? "");
    if (!DANGEROUS.some((re) => re.test(command))) return;

    // ctx.hasUI 在无界面模式下为 false，此时应直接阻断而不是等待输入
    if (!ctx.hasUI) return { block: true, reason: "非交互模式，危险命令已阻断" };

    const ok = await ctx.ui.confirm("危险命令", `确认执行？\n${command}`);
    if (!ok) return { block: true, reason: "用户拒绝" };
  });
}
```

MCP 工具同样走这条管道：每次 MCP 调用都要经过 Pi 的工具管线，扩展的 `tool_call` / `tool_result` 处理器（包括权限门）对 MCP 工具一样生效；从 codemode 脚本里发起的调用会带上 codemode 的 call ID 作为 `parentToolCallId`。MCP 服务器声明的注解（`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint`）可以通过 `pi.getAllTools()` 读到，权限扩展可以据此决定哪些调用需要确认。

真正的隔离不来自确认弹窗，而来自运行环境本身。官方给出的三档运行方式：

| 运行方式 | 仍然暴露的东西 |
| --- | --- |
| 直接用当前操作系统用户的权限运行 | 只有该用户权限之外的东西被保护；专用低权账号能缩小范围 |
| 整个放进容器 / 虚拟机 / 沙箱 | 宿主文件与进程（未暴露的部分）；凭据与网络服务若被放进去就仍可访问，通常是最强的实用选项 |
| Pi 在隔离环境外，只有内置工具在里跑 | 通过那些工具发起的动作受限；Pi 自身与其他扩展仍在边界外，属更窄的隔离 |

```text
权限与确认要点：
1. 默认不逐调用审批，确认提示需要自己用扩展的 tool_call 实现
2. 阻断用 return { block: true, reason }，ctx.hasUI 为 false 时不要等待输入
3. MCP 工具走同一条工具管线，权限门和 tool_call / tool_result 对它同样有效
4. 工作目录只控制资源发现与工具默认路径，不阻止命令访问进程可达的其他路径
5. 安全边界来自容器 / 虚拟机 / 低权账号，不来自「看着它干活」
6. 扩展与项目资源在 Pi 进程内执行，使用与 Pi 相同的系统权限
```

## 会话持久化与存储位置

默认情况下 Pi 会自动保存会话，除非用 `--no-session` 启动。会话是 JSONL 文件，每一行一个 JSON 对象，条目通过 `id` / `parentId` 组成树。默认目录结构是：

```text
~/.pi/agent/sessions/--<path>--/<timestamp>_<session-id>.jsonl
```

`<path>` 的生成规则：去掉开头的路径分隔符，把 `/`、`\`、`:` 全部替换成 `-`。`<session-id>` 默认是 UUID，SDK 或 `--session-id` 可以指定。本机实测的路径完美印证了这条规则（工作目录 `/root/.hermes/cache/scratch/pitest`）：

```text
/root/.pi/agent/sessions/--root-.hermes-cache-scratch-pitest--/2026-10-15T02-21-34-850Z_01a13d5d-6b02-7052-83bb-cee08f3362b7.jsonl
```

换成别的位置有三条路，优先级从高到低是命令行、环境变量、设置项：

```shell
# 1) 命令行：一次性指定（优先级最高）
pi --session-dir /data/pi-sessions

# 2) 环境变量
export PI_CODING_AGENT_SESSION_DIR=/data/pi-sessions
pi

# 3) settings.json（相对路径按工作目录解析）
cat > ~/.pi/agent/settings.json << 'EOF'
{
  "$schema": "https://pi.dev/schemas/settings.schema.json",
  "sessionDir": "/data/pi-sessions"
}
EOF
```

定位与继承会话的开关各司其职：`--continue` / `-c` 打开当前工作目录最近的会话，`--resume` / `-r` 打开会话选择器，`--session <path|id>` 指定已有会话，`--session-id <id>` 指定确切的会话 ID（不存在就创建），`--fork <path|id>` 从已有会话派生出新会话。`--fork` 不能与 `--session`、`--continue`、`--resume`、`--no-session` 同时使用；`--session-id` 不能与 `--session`、`--continue`、`--resume` 组合，但可以和 `--fork` 一起用来指定新 ID。

```shell
# 继续最近一次工作，并为它起一个可读名字
pi --continue --name "api-refactor"

# 从某个会话派生新分支，探索另一条实现路线
pi --fork 01a13d5d --name "api-refactor-alt"

# 一次性任务，不落盘（无法再恢复）
pi --no-session -p "总结这个仓库的目录结构"
```

清理会话有两种方式：直接删 `~/.pi/agent/sessions/` 下的 `.jsonl` 文件，或在 `/resume` 选择器里选中一条按 `Ctrl+D` 再确认（本机装有 `trash` 命令时走回收站而不是永久删除）。会话头里带版本字段：v1 是线性条目序列，v2 引入 `id` / `parentId` 树结构，v3 把 `hookMessage` 角色改名为 `custom`；旧会话在加载时会自动迁移到当前版本 v3。

```text
会话持久化要点：
1. 默认路径 ~/.pi/agent/sessions/，按工作目录分组，目录名把 / 与 : 换成 -
2. 换位置：--session-dir > PI_CODING_AGENT_SESSION_DIR > sessionDir 设置
3. --no-session 是一次性会话，进程退出后不可恢复
4. 会话文件是 JSONL 的树结构，回到旧节点不会删除离开的分支
5. 删除会话可以直接删 .jsonl，或在 /resume 里 Ctrl+D（可能进回收站）
6. /session 一次性给出文件路径、ID、消息数、token 用量与成本
```

## 应用场景实战

### 场景一：给一个多包仓库建立分层的规则体系

一个 monorepo 有多个子项目，团队通用规则、包级规则、以及这一周临时生效的覆盖规则需要分层共存。做法是用目录层级表达优先级：仓库根写通用规则，包目录写具体规则，需要用 override 时只在对应目录放 `AGENTS.override.md`。

```shell
# 目录结构
# /opt/app/
# ├── AGENTS.md                          团队通用规则（全仓库生效）
# ├── packages/api/AGENTS.md              API 包补充规则
# ├── packages/web/AGENTS.md              Web 包补充规则
# └── packages/api/AGENTS.override.md     临时替换 API 包的 AGENTS.md

cat > /opt/app/AGENTS.md << 'EOF'
# 团队通用规则

- Node 22，包管理器统一用 pnpm
- 提交信息遵循 Conventional Commits
- 任何改动必须附带可运行的测试
EOF

cat > /opt/app/packages/api/AGENTS.md << 'EOF'
# API 包规则

- 框架：FastAPI + SQLAlchemy 2.x
- 所有新接口必须写 OpenAPI 描述
- 数据库迁移放在 migrations/，命名遵循 Alembic revision 规范
EOF

cat > /opt/app/packages/api/AGENTS.override.md << 'EOF'
# 本周临时规则（替换同目录 AGENTS.md）

- 冻结新接口开发，只修 bug
- 所有改动需在 PR 描述里关联 incident 编号
EOF

# 在 API 包里启动：根 AGENTS.md + 本目录 override 生效
cd /opt/app/packages/api
pi

# 想确认是否被上下文文件干扰时的对照实验
pi -nc --print "列出这个目录的测试命令"
```

验证方式：把三份文件里各写一条独有规则，然后在 `/opt/app/packages/api` 里让 Pi 复述「当前生效的规则」。根规则与 override 规则都应出现，本目录的 `AGENTS.md` 因被 override 替换而不应出现。

### 场景二：给不可信仓库加一层权限门，并在 CI 里安全使用

接手一个第三方仓库做审计时，需要「能读、能跑测试、但绝不能碰凭据文件和 git 历史改写」。做法是写一个保护路径的扩展，把不可信路径直接阻断，同时在 CI 里用无界面模式运行。

```typescript
// ~/.pi/agent/extensions/protected-paths.ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

// 敏感路径一律禁止写入
const DENY_WRITE = [
  /(^|\/)\.env(\.|$)/,
  /(^|\/)\.git\//,
  /(^|\/)node_modules\//,
  /(^|\/)\.ssh\//,
  /id_rsa/,
];

export default function (pi: ExtensionAPI) {
  pi.on("tool_call", async (event, ctx) => {
    const writeTools = ["write", "edit"];
    if (!writeTools.includes(event.toolName)) return;

    const path = String(event.input.file_path ?? event.input.path ?? "");
    if (DENY_WRITE.some((re) => re.test(path))) {
      ctx.ui.notify(`已阻断对 ${path} 的写入`, "warning");
      return { block: true, reason: `受保护路径：${path}` };
    }
  });
}
```

```shell
# 交互审计：扩展来自 agent 目录，不需要项目信任
cd /tmp/untrusted-repo
pi -e ~/.pi/agent/extensions/protected-paths.ts

# CI 无界面模式：print / JSON / RPC 都无法弹出信任提示
# defaultProjectTrust 是 "ask" 或 "never" 时会跳过受保护的项目资源，
# 需要显式一次性授权时用 --approve
cd /opt/app
pi --approve -p "运行测试并总结失败项" > report.txt
echo "exit=$?"

# 结构化事件交给下游处理
pi --mode json --approve "审查这个 PR 的 diff" > events.jsonl
```

print 模式对自动化是友好且诚实的：最终文本写 stdout、诊断写 stderr；以 `error` 或 `aborted` 结束的运行返回非零退出码；被输出 token 上限截断（`length`）的运行仍会打印部分文本并返回非零。JSON 模式则要注意——失败或中止的回复会出现在事件流里，但本身**不会**让退出码变非零，需要读事件判断成败。

```text
实战要点：
1. 规则分层用目录层级表达，临时覆盖用 AGENTS.override.md，不删原文件
2. 判断「谁在生效」时用 -nc 做对照，或让 Pi 复述当前规则清单
3. 扩展放 ~/.pi/agent/extensions/ 可绕过项目信任直接生效，适合审计场景
4. 无人值守必须显式做信任决策：--approve / --no-approve / defaultProjectTrust
5. print 模式用退出码判断成败，JSON 模式必须读事件流判断
```

## 最佳实践与踩坑记录

1. **AGENTS.md 只写「不写就会犯错」的规则。** 上下文文件每次请求都进系统提示，越长越贵、越容易被忽略。建议控制在 50 行以内，只保留技术栈、常用命令、明确禁忌三类信息，其余交给技能按需加载。

2. **把「跨项目通用规则」放 agent 目录，把「项目规则」放仓库。** `~/.pi/agent/AGENTS.md` 对所有工作目录生效，项目 `.pi/` 与仓库根 `AGENTS.md` 只对项目生效。混在一起会在其他仓库里误伤。

3. **改完规则文件立刻 `/reload`。** `/reload` 会重新加载 keybindings、extensions、skills、templates、themes 和上下文文件。不 reload 时你会看到「文件改了但行为没变」，进而误判 Pi 有缓存 bug。

4. **自动化一律显式处理项目信任。** 交互模式有弹窗，print / JSON / RPC 没有。把 `--approve` / `--no-approve` 写进脚本，或在 agent 目录把 `defaultProjectTrust` 设成明确值，别依赖 `"ask"` 在无人值守下的隐式行为。

5. **权限门必须同时考虑 `ctx.hasUI`。** 只写 `ctx.ui.confirm` 的扩展在无界面模式下会挂住或失效；正确做法是无 UI 时返回 `block`，把决策权交回启动脚本。

6. **别把项目信任当成沙箱。** 信任只控制项目资源的加载，不限制工具访问范围。要真隔离就上容器 / 虚拟机或专用低权账号，并只暴露任务需要的文件与凭据。

坑 1：在 print / JSON / RPC 模式下项目扩展「莫名其妙没加载」。
结论：这不是 bug，是信任决策在无界面模式下的既定行为。
原因：三种模式无法显示内置信任提示；当没有命令行覆盖、没有扩展处理 `project_trust`、也没有保存的决策时，`defaultProjectTrust` 为 `"ask"` 或 `"never"` 会直接跳过受保护的项目资源。
解法：给自动化命令加 `--approve`（一次性授权），或在 agent 目录设置 `defaultProjectTrust: "always"`；需要反向保证时显式用 `--no-approve`。

坑 2：写了 `AGENTS.override.md`，以为它能屏蔽所有上级规则。
结论：override 只作用于「同目录」的 `AGENTS.md` / `CLAUDE.md`。
原因：官方文档写明它只替换同目录文件，不会压制 agent 目录和其他目录的上下文文件，多个目录的上下文文件会一起进入系统提示。
解法：要分层控制就用目录结构表达——把不该生效的规则从上层目录拿掉，或在某次运行用 `-nc` 关闭全部上下文文件加载做验证。

坑 3：把 `.env`、密钥、CI token 放进工作目录，以为「Pi 会问我才动」。
结论：Pi 默认不会对每次工具调用做确认，凭据可能被读取并进入会话记录。
原因：工具使用 Pi 进程的操作系统权限；扩展、包安装器与语言服务器等子进程同样如此；工作目录只影响资源发现与工具默认路径，不构成访问限制。
解法：凭据放环境变量或用短时凭据、并移出工作目录；对敏感路径用 `tool_call` 扩展做写入/读取门；需要强边界时把 Pi 放进容器或虚拟机并只暴露必需目录。

坑 4：把会话文件当成「可以随便分享的日志」。
结论：会话内容可能包含提示词、工具参数、命令输出、文件内容，以及对话过程中暴露过的凭据。
原因：会话是完整的 JSONL 记录，`/export` 与 `/share` 会把它们整份导出或上传；`/share` 在未配置 Radius 认证时创建私有 GitHub gist，但内容已经离开本机。
解法：导出或分享前先自查会话；用 `sessionShareDestination` 明确指定 `gist` 或 `radius`；把会话目录纳入备份策略，并定期清理旧 `.jsonl`。
