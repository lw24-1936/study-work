## 概述

Pi 把「定制」拆成四种资源，各自解决不同粒度的问题：**扩展**（extension）是可执行集成，能注册工具、命令、快捷键、Provider，并拦截生命周期事件；**技能**（skill）是按需加载的专门指令与配套文件；**提示模板**（prompt template）是可复用的提示文本，输入 `/name` 展开；**主题**（theme）只管终端配色。四者可以通过 **Pi 包**（package）用 npm 或 git 一次性分发。

选择原则是最小机制优先：只需要复用一段提示词就用模板，需要一整套「怎么干」的说明与脚本用技能，需要新的可执行能力（新工具、新 Provider、权限门）才写扩展，只想换配色就写主题。

```text
本篇要解决的问题：
1. 扩展放在哪、什么时候被加载、怎么热重载
2. 扩展能挂哪些事件，生命周期顺序是什么
3. 怎么写一个带自定义工具、命令与持久化状态的扩展
4. 技能如何做到「描述常驻、正文按需加载」，放在哪些目录
5. 提示模板与主题的格式与加载位置
6. 如何把扩展 + 技能 + 模板 + 主题打包成 npm/git 包分发给团队
```

本篇命令与实际输出以本机安装的 `@earendil-works/pi-coding-agent@1.2.0` 实测为准；官方文档见 `https://pi.dev/docs/latest/extensions`、`https://pi.dev/docs/latest/skills`、`https://pi.dev/docs/latest/prompt-templates`、`https://pi.dev/docs/latest/themes`、`https://pi.dev/docs/latest/packages`。

## 扩展机制与运行位置

扩展是 TypeScript 模块，默认导出（default export）一个工厂函数，函数收到 `ExtensionAPI` 对象。工厂可以是同步的也可以是异步的；如果返回 Promise，Pi 会在继续启动前 await 它——这意味着异步初始化在 `session_start`、`resources_discover` 以及 `pi.registerProvider()` 注册的 Provider 生效之前就完成了。扩展通过 `jiti` 加载，**TypeScript 不需要预编译**。

位置的规则决定了两件事：能不能热重载，以及需不需要项目信任。

| 位置 | 作用域 | 说明 |
| --- | --- | --- |
| `~/.pi/agent/extensions/*.ts` | 全局 | 所有项目生效，自动发现，`/reload` 可热重载 |
| `~/.pi/agent/extensions/*/index.ts` | 全局 | 多文件扩展的入口 |
| `.pi/extensions/*.ts` | 项目 | 需项目信任后才加载 |
| `.pi/extensions/*/index.ts` | 项目 | 同上 |
| `settings.json` 的 `extensions` 数组 | 用户 / 项目 | 额外路径，支持文件与目录 |
| `pi -e ./path.ts` | 单次运行 | 只适合快速试跑，不能热重载 |

```shell
# 全局扩展目录（推荐：能热重载、不需要项目信任）
mkdir -p ~/.pi/agent/extensions

# 项目扩展目录（团队共享，需项目信任）
mkdir -p .pi/extensions

# 临时试跑一个扩展，不写任何配置
pi -e ./my-extension.ts

# 改完扩展后，在交互模式里热重载（auto-discovered 位置才生效）
/reload

# 关闭全部扩展发现与内置扩展（显式 -e 仍会加载）
pi -ne
```

扩展能用的导入是固定的几组：`@earendil-works/pi-coding-agent` 提供类型（`ExtensionAPI`、`ExtensionContext`、事件类型），`typebox` 定义工具参数 schema，`@earendil-works/pi-ai` 提供 AI 工具函数（例如 Google 兼容枚举要用的 `StringEnum`），`@earendil-works/pi-tui` 提供自定义渲染用的 TUI 组件。Node 内置模块（`node:fs`、`node:path` 等）也可直接用；需要 npm 依赖时，在扩展目录（或某个父目录）放 `package.json` 并执行 `npm install`，`node_modules/` 里的导入会被自动解析。

```text
扩展机制要点：
1. 入口是 default export 的工厂函数，参数是 ExtensionAPI，TypeScript 免编译
2. 异步工厂会被 await，适合启动时拉取远程配置或动态注册模型
3. 自动发现位置（~/.pi/agent/extensions 与 .pi/extensions）支持 /reload 热重载，-e 不支持
4. 项目扩展在项目信任之后才加载；全局扩展与 -e 扩展不依赖信任
5. 工厂可能在不启动会话的调用里执行，不要在工厂里开后台进程/监听/定时器
6. npm 依赖放扩展目录旁的 package.json，host 提供的包不要打包进依赖
```

## 事件与生命周期

Pi 的事件覆盖「启动 → 会话 → 单轮 → 工具 → 收尾」全过程。最常用的是 `session_start`、`input`、`before_agent_start`、`context`、`tool_call`、`tool_result`、`agent_end`、`agent_settled`、`session_shutdown`。理解两个边界点很重要：`agent_end` 只表示一次底层 agent 运行结束，之后 Pi 仍可能自动重试、自动压缩后重试、或继续处理排队的后续消息；`agent_settled` 才表示 Pi 不会再自动继续。

```text
生命周期主线（官方文档的精简版）：

pi 启动
  ├─► project_trust          （仅用户级/CLI 扩展参与）
  ├─► session_start          { reason: "startup" }
  └─► resources_discover     { reason: "startup" }

用户提交提示
  ├─► input                  （可拦截、改写或直接处理掉）
  ├─► before_agent_start     （可注入消息、修改系统提示）
  ├─► agent_start
  ├─► message_start / message_update / message_end
  │     ┌── turn 循环（模型调用工具时重复）──┐
  │     ├─► turn_start
  │     ├─► context                      （可修改消息）
  │     ├─► before_provider_headers      （可改请求头）
  │     ├─► before_provider_request      （可检查/替换请求体）
  │     ├─► after_provider_response
  │     ├─► tool_execution_start
  │     ├─► tool_call                    （可阻断）
  │     ├─► tool_execution_update
  │     ├─► tool_result                  （可修改）
  │     ├─► tool_execution_end
  │     └─► turn_end
  ├─► agent_end
  └─► agent_settled          （重试、压缩、后续消息都已排空）

/new 或 /resume：session_before_switch → session_shutdown → session_start
/fork 或 /clone：session_before_fork  → session_shutdown → session_start
/compact 或自动压缩：session_before_compact → session_compact / session_compact_failed
/tree 导航：session_before_tree → session_tree
退出：session_shutdown
```

下面这个扩展把「事件挂钩」的四种典型用法放在一起：启动时提示、拦截输入、给系统提示注入运行环境信息、以及在会话结束时清理自己启动的资源。

```typescript
// ~/.pi/agent/extensions/telemetry.ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { execSync } from "node:child_process";

let started = false;

export default function (pi: ExtensionAPI) {
  // 1) 会话开始时初始化（不要在工厂里做，工厂可能没有会话）
  pi.on("session_start", async (event, ctx) => {
    started = true;
    ctx.ui.notify(`会话已启动（${event.reason}）`, "info");
  });

  // 2) 拦截用户输入：命中内部命令则自己处理，不发给模型
  pi.on("input", async (event, ctx) => {
    if (event.text === "/whoami-debug") {
      ctx.ui.notify(`cwd=${ctx.cwd}`, "info");
      return { handled: true };
    }
  });

  // 3) 每轮开始前注入一段环境信息（改 sections 而不是整段替换系统提示）
  pi.on("before_agent_start", async (event) => {
    const branch = execSync("git rev-parse --abbrev-ref HEAD").toString().trim();
    return {
      message: {
        customType: "git-branch",
        content: `当前分支：${branch}`,
        display: true,
      },
    };
  });

  // 4) 会话销毁时清理会话级资源（必须幂等）
  pi.on("session_shutdown", async (_event, ctx) => {
    if (!started) return;
    ctx.ui.notify("会话结束，已清理", "info");
    started = false;
  });
}
```

事件处理器可以返回控制指令：`tool_call` 返回 `{ block: true, reason }` 阻断，`input` 返回 `{ handled: true }` 表示已被扩展消化，`session_before_switch` / `session_before_fork` / `session_before_tree` 返回 `{ cancel: true }` 取消操作，`before_agent_start` 返回 `{ message, systemPrompt }` 注入消息或改写提示。

```text
事件与生命周期要点：
1. 启动阶段只有用户级与 -e 扩展能看到 project_trust；项目扩展在信任后才加载
2. agent_end 之后可能还有自动重试、压缩或排队消息，要等 agent_settled 才算真结束
3. tool_call 用 { block: true, reason } 阻断，tool_result 可修改结果内容
4. before_agent_start 优先改 sections / selectedTools / promptGuidelines，保住前缀缓存
5. /fork、/resume、/tree 会重建扩展实例，清理放 session_shutdown、重建放 session_start
6. 会话级资源（进程、socket、watcher、定时器）在 session_start 之后启动，并在 session_shutdown 幂等关闭
```

## 编写一个完整扩展

一个能用的扩展通常包含三件东西：一个 LLM 可调用的工具、一个人工触发的命令、以及需要跨重启保留的状态。工具用 `pi.registerTool()` 注册，参数 schema 用 `typebox` 描述，执行函数签名是 `(toolCallId, params, signal, onUpdate, ctx)`，返回值需要 `content` 数组与 `details` 对象。命令用 `pi.registerCommand()` 注册，处理器可以拿到 `ExtensionCommandContext`，它比普通 `ExtensionContext` 多出会话控制方法（`newSession()`、`fork()`、`switchSession()`、`navigateTree()`、`waitForIdle()`），这些方法只能在命令里用——在事件处理器里调用会死锁。

```typescript
// ~/.pi/agent/extensions/todo-scan.ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";
import { readFileSync } from "node:fs";

const PATTERN = /\b(TODO|FIXME|HACK)\b/;

export default function (pi: ExtensionAPI) {
  // 让模型可以调用的自定义工具
  pi.registerTool({
    name: "todo_scan",
    label: "TODO Scan",
    description: "扫描一个文件里的 TODO / FIXME / HACK 注释，返回带行号的清单",
    parameters: Type.Object({
      file: Type.String({ description: "要扫描的文件路径" }),
    }),
    async execute(_toolCallId, params, _signal, _onUpdate, _ctx) {
      const hits: string[] = [];
      readFileSync(params.file, "utf8")
        .split("\n")
        .forEach((line, i) => {
          const m = line.match(PATTERN);
          if (m) hits.push(`${i + 1}: ${m[1]} ${line.trim().slice(0, 120)}`);
        });

      const text = hits.length === 0 ? "没有找到待办注释" : hits.join("\n");
      return {
        content: [{ type: "text", text }],
        details: { count: hits.length, file: params.file },
      };
    },
  });

  // 人工触发的命令：把扫描结果记到会话里（跨重启保留）
  pi.registerCommand("todo-report", {
    description: "扫描给定文件并把结果写入会话条目",
    handler: async (args, ctx) => {
      const file = args.trim();
      if (!file) {
        ctx.ui.notify("用法：/todo-report <file>", "warning");
        return;
      }
      const hits = readFileSync(file, "utf8")
        .split("\n")
        .filter((l) => PATTERN.test(l)).length;

      // appendEntry 保存的状态能跨重启存活
      pi.appendEntry("todo-report", { file, hits, at: Date.now() });
      ctx.ui.setStatus("todo-report", `${file}: ${hits} 条`);
      ctx.ui.notify(`已记录 ${hits} 条待办`, "info");
    },
  });
}
```

注册完用 `/reload` 或 `-e` 验证。本机真实执行了「项目扩展 + 项目模板 + 项目技能」的发现流程，`hello.ts` 里的 `pi.registerCommand("hello", ...)` 会出现在命令列表里（来自 `get_commands` 命令的真实响应，字段未改动，路径已换行）：

```text
$ printf '{"id":"1","type":"get_commands"}\n' | pi --mode rpc --no-session --approve
{"id":"1","type":"response","command":"get_commands","success":true,"data":{"commands":[
 {"name":"hello","description":"Say hello from the demo extension","source":"extension",
  "sourceInfo":{"path":"/root/.hermes/cache/scratch/pitest/.pi/extensions/hello.ts",
  "source":"auto","scope":"project","origin":"top-level",
  "baseDir":"/root/.hermes/cache/scratch/pitest/.pi"}},
 ...]}}
```

`source: "extension"` 表示它由 `pi.registerCommand()` 注册；`scope: "project"` 表示来自项目目录；`origin: "top-level"` 表示直接加载而非来自包。另外 Pi 自身用同样机制实现内置扩展，名字是 `builtin:mcp`、`builtin:llama.cpp`、`builtin:codemode`、`builtin:tool-search`，可以在 `pi config` 里看到并单独禁用。

```text
扩展编写要点：
1. registerTool 的参数用 typebox 描述，execute 返回 { content, details }
2. registerCommand 的处理器才有会话控制方法（newSession/fork/switchSession/navigateTree）
3. 跨重启状态用 pi.appendEntry()，一次性提示用 ctx.ui.notify() / setStatus() / setWidget()
4. 用户交互统一走 ctx.ui（select / confirm / input / notify / custom）
5. 内置扩展以 builtin:<name> 命名，可用 -builtin:mcp 这类写法在 extensions 设置里禁用
6. 调试走 -e ./x.ts 与 /reload，发布走 Pi 包
```

## 技能加载与按需注入

Pi 实现 Agent Skills 规范：一个技能就是一个包含 `SKILL.md` 的目录，可以附带脚本、参考文档与资源。启动时 Pi 只把每个技能的 **name、description、路径** 加进系统提示，正文不加载；任务匹配时模型自己去读 `SKILL.md`。这样既能给模型大量专门知识，又不让上下文提前爆掉。

```text
pdf-tools/
├── SKILL.md
├── scripts/
│   └── extract.sh
├── references/
│   └── formats.md
└── assets/
    └── template.json
```

```markdown
---
name: pdf-tools
description: Extract text and tables from PDF files. Use when reading, converting, or inspecting PDFs.
---

# PDF tools

Read `references/formats.md` before converting a document. Run scripts relative to this skill directory.
```

`description` 决定模型什么时候想起加载这个技能，所以它必须同时说清「做什么」和「什么时候用」。官方文档点名了反例：`Helps with PDFs` 这种写法缺少路由信息，模型不知道该在什么场景用它。技能内引用配套文件时用相对路径，Pi 会告诉模型技能所在目录，模型据此解析。

技能目录的位置与加载规则：

| 位置 | 作用域 | 说明 |
| --- | --- | --- |
| `~/.pi/agent/skills/` | 用户 | 所有项目可用 |
| `.pi/skills/` | 项目 | 需项目信任 |
| `~/.agents/skills/` | 用户 | Agent Skills 规范目录 |
| `.agents/skills/` | 项目 | 从当前目录向上发现，遇到仓库根停止 |
| `settings.json` 的 `skills` 数组 | 用户 / 项目 | 额外文件或目录 |
| `--skill <path>` | 单次运行 | 临时加载 |

包含 `SKILL.md` 的目录会被递归发现；Pi 也接受独立的 Markdown 技能文件，但「目录 + SKILL.md」才是可移植形态，应优先使用。别人写的技能可能指示模型运行脚本或改文件，加载前应审查其配套文件。

调用方式有两种：让模型自己决定加载，或用 `/skill:name` 强制加载。命令后面的参数会作为用户请求追加到已加载的指令之后；把 `disable-model-invocation: true` 写进 frontmatter，技能就只响应显式命令；`enableSkillCommands` 设置控制技能命令是否出现在交互命令发现列表里（手动输入 `/skill:name` 仍然有效）。

```shell
# 强制加载技能并把参数作为用户请求追加
/skill:pdf-tools extract report.pdf

# 关闭技能发现（排查「这条指令是不是技能带来的」时用）
pi -ns

# 临时加载一个技能目录
pi --skill ./team-skills/pdf-tools
```

扩展还可以在 `resources_discover` 事件里补充技能路径，这是给团队技能库做「动态目录」的标准做法：

```typescript
pi.on("resources_discover", async (_event, _ctx) => ({
  skillPaths: ["/opt/team/skills"],
  promptPaths: ["/opt/team/prompts"],
  themePaths: ["/opt/team/themes"],
}));
```

```text
技能加载要点：
1. 技能 = 含 SKILL.md 的目录，启动时只注入 name / description / 路径
2. description 必须同时说明「做什么」与「什么时候用」，否则模型不会路由过来
3. 目录递归发现；.agents/skills 从当前目录向上找，遇到仓库根停止
4. /skill:name 强制加载，其后参数作为用户请求追加
5. disable-model-invocation: true 让技能只响应显式命令
6. 扩展可在 resources_discover 里追加 skillPaths / promptPaths / themePaths
```

## 提示模板与主题

提示模板是「输入 `/name` 就展开的 Markdown 片断」。文件名（去掉 `.md`）就是命令名，`review.md` 对应 `/review`。frontmatter 里 `description` 可选（缺省时用第一个非空行），`argument-hint` 可选且会显示在自动补全下拉里——`<尖括号>` 表示必填参数，`[方括号]` 表示可选。模板支持位置参数与简单切片：`$1`、`$2` 是位置参数，`$@` 或 `$ARGUMENTS` 是全部参数拼接，`${@:N}` 是从第 N 个开始的参数，`${@:N:L}` 是从第 N 个开始取 L 个。

```markdown
---
description: Review staged git changes
argument-hint: "<path>"
---

审查暂存的改动（`git diff --cached` $1）。重点关注：

- 逻辑与边界错误
- 安全问题
- 错误处理缺口

补充上下文：$@
```

```shell
# 模板的加载位置
~/.pi/agent/prompts/*.md      # 用户级
.pi/prompts/*.md              # 项目级（需项目信任）
# 也可来自包的 prompts/ 目录、settings 的 prompts 数组、或 --prompt-template

# 使用
/review
/review src/api

# 关闭模板发现
pi -np
```

主题是定义 TUI 颜色的 JSON 文件。`name` 必填且不含 `/`；`vars` 可选，用来定义可复用的颜色再在 `colors` 里引用；`colors` 必须定义全部 53 个必需 token（`thinkingMax` 与两个搜索高亮 token 可选，分别回退到 `thinkingXhigh`、`selectedBg`、`text`）。颜色值支持四种格式：6 位十六进制（`"#ff0000"`）、xterm 256 色索引（`39`）、`vars` 变量名、以及空串 `""`（终端默认色）。

```json
{
  "$schema": "https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/src/modes/interactive/theme/theme-schema.json",
  "name": "my-theme",
  "vars": {
    "primary": "#00aaff",
    "secondary": 242
  },
  "colors": {
    "accent": "primary",
    "border": "primary",
    "text": "",
    "muted": "secondary"
  }
}
```

主题文件放在 `~/.pi/agent/themes/*.json` 或 `.pi/themes/*.json`（后者需项目信任），也可以用 `themes` 设置数组、`--theme <path>`、`--no-themes` 控制。编辑当前生效的自定义主题文件时 Pi 会**热重载**，可以直接看到配色变化。选择主题走 `/settings` 或 `settings.json` 的 `theme` 字段；`pi --use-theme light` 只改这次运行的初始主题，`--use-theme light/dark` 表示跟随终端明暗。

```shell
# 只看这次运行的初始主题，不改保存的设置
pi --use-theme light

# 跟随终端外观
pi --use-theme light/dark

# 检查终端是否支持真彩色（现代终端大多支持）
echo $COLORTERM   # 期望输出 truecolor 或 24bit
```

```text
提示模板与主题要点：
1. 文件名即命令名，/name 展开；frontmatter 支持 description 与 argument-hint
2. 模板支持 $1 / $@ / $ARGUMENTS / ${@:N} / ${@:N:L}
3. prompts/ 目录的发现是非递归的，子目录里的模板要在设置或包清单里显式列出
4. 主题必须定义全部 53 个必需颜色 token，可选 token 有既定回退值
5. 编辑当前生效的自定义主题会热重载，适合边调边看
6. --use-theme 只影响本次运行，/settings 里的选择会被保存
```

## 包分发与共享

当一个定制包含扩展 + 技能 + 模板 + 主题时，把它们打成 **Pi 包**（Pi package）用 npm 或 git 分发，比让每个人各自复制文件可靠得多。包就是一个普通目录或 npm 包：可以是约定目录结构，也可以用 `package.json` 的 `pi` 字段显式声明路径。

```shell
# 从 npm、git、URL 或本地路径安装
pi install npm:@example/pi-tools@1.0.0
pi install git:github.com/example/pi-tools@v1
pi install ./local-package

# 查看已配置的包
pi list

# 移除一个包及其设置项
pi remove npm:@example/pi-tools

# 让包安装与声明对齐 / 更新所有包
pi update --extensions

# 只在这次运行里试用一个包，不写进设置
pi -e npm:@example/pi-tools
```

本机实测（尚未安装任何包）：

```text
$ pi list
No packages installed.
```

个人安装写进 `~/.pi/agent/settings.json`，加 `--local`（`-l`）则写入 `.pi/settings.json`，而项目声明只在项目信任授予后才被读取。包可以执行扩展代码，也可以带上指示模型运行程序的技能——安装第三方包前应审查源码。

约定式包布局与显式清单：

```text
my-pi-package/
├── package.json
├── extensions/
├── skills/
├── prompts/
└── themes/
```

```json
{
  "name": "my-pi-package",
  "keywords": ["pi-package"],
  "pi": {
    "extensions": ["./src/extension.ts"],
    "skills": ["./resources/skills"],
    "prompts": ["./resources/prompts/*.md"],
    "themes": ["./resources/themes/*.json"]
  }
}
```

没有 `pi` 清单时，Pi 会从上述约定目录里发现 TypeScript/JavaScript 扩展、技能目录、Markdown 模板与 JSON 主题。`keywords` 里的 `pi-package` 让 npm 包有资格出现在 Pi 包画廊（`https://pi.dev/packages`），`pi.image` 与 `pi.video` 可选，用于画廊预览。

依赖规则是最容易踩的一条：扩展运行时真正 `import` 的第三方包放 `dependencies`；Pi 宿主已经提供的包必须放 `peerDependencies` 且版本范围写 `"*"`，并且**不要**打包它们。宿主提供的包是 `@earendil-works/pi-ai`、`@earendil-works/pi-agent-core`、`@earendil-works/pi-coding-agent`、`@earendil-works/pi-tui`、`typebox`。把宿主包写进 `dependencies` 会产生物理副本，绕过扩展的模块映射，造成重复的类与注册表，Pi 会在检测到这种清单配置时给出警告。

安装后还可以按资源类型筛选加载内容，对象形式比数组形式更精确：省略某属性表示加载该类型全部允许的资源，`[]` 表示不加载该类型任何资源，`!pattern` 排除 glob 命中，`+path` 精确包含，`-path` 精确排除。筛选只能收窄包自身的声明，不能凭空暴露包没声明的资源。`pi config` 是可视化的开关面板（Tab 切换个人/项目作用域，`pi config --local` 直接进项目覆盖）。

```json
{
  "packages": [
    {
      "source": "npm:@example/pi-tools",
      "extensions": ["extensions/*.ts", "!extensions/legacy.ts"],
      "skills": [],
      "prompts": ["prompts/review.md"]
    }
  ]
}
```

```text
包分发要点：
1. 安装来源支持 npm:、git:、URL 与本地路径；版本化 npm 规格与 git tag/commit 都是钉住的
2. 个人安装写 ~/.pi/agent/settings.json，--local 写 .pi/settings.json（需项目信任）
3. 约定目录 extensions/ skills/ prompts/ themes/，或用 package.json 的 pi 清单显式声明
4. 宿主提供的包放 peerDependencies（"*"）且不打包，运行时依赖放 dependencies
5. 筛选语法：省略=全部、[]=不要、!pattern 排除、+path 包含、-path 排除
6. 项目条目默认替换个人条目；带 autoload: false 时改为对个人包做筛选增量
```

```typescript
// extensions/guard.ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName !== "bash") return;
    const cmd = String(event.input.command ?? "");
    if (/(^|\s)git\s+push\s+--force/.test(cmd) || /(^|\s)git\s+reset\s+--hard/.test(cmd)) {
      if (!ctx.hasUI) return { block: true, reason: "ACME 规范：非交互模式禁止改写远端历史" };
      const ok = await ctx.ui.confirm("ACME 规范", `该命令改写历史，确认执行？\n${cmd}`);
      if (!ok) return { block: true, reason: "用户拒绝" };
    }
  });
}
```

### 场景二：给数据分析项目做一套「报表 → 结构化表格」技能与模板

数据分析场景要反复做同一件事：把 PDF/Excel 报表里的表格抽出来、按固定口径清洗、再落成 CSV。做法是把操作步骤写成技能（附带脚本），把提示写成模板，让模型按需加载技能、用模板保证输出格式一致。

```text
/opt/bi/.pi/
├── skills/
│   └── report-to-table/
│       ├── SKILL.md
│       ├── scripts/
│       │   └── extract.sh
│       └── references/
│           └── schema.md
└── prompts/
    └── to-csv.md
```

```markdown
---
name: report-to-table
description: 把 PDF/Excel 报表里的表格抽取为结构化 CSV。当用户提到报表、月报、对账、抽取表格、转 CSV 时使用。
---

# 报表转表格

## 步骤

1. 先读 `references/schema.md`，确认目标列名与单位口径
2. 运行 `scripts/extract.sh <输入文件>`，产物写在 `out/` 目录
3. 按 schema 校验列名、类型与单位，单位不一致时先换算再落盘
4. 输出 `out/<原名>.csv`，并在回复里给出记录数与异常行清单

## 约束

- 金额统一保留两位小数，不要做四舍五入以外的换算
- 缺失值写空字符串，不要写 0 或 N/A
- 任何单位换算都要在回复里显式说明
```

```bash
#!/usr/bin/env bash
# scripts/extract.sh —— 抽取 PDF 表格为中间格式
set -euo pipefail
in_file="$1"
mkdir -p out
# 使用项目自己装好的工具链，不假设全局环境
python3 -m pip show pdfplumber >/dev/null 2>&1 || {
  echo "缺少依赖：python3 -m pip install pdfplumber" >&2
  exit 1
}
python3 - "$in_file" << 'PY'
import sys, json, pdfplumber

path = sys.argv[1]
tables = []
with pdfplumber.open(path) as pdf:
    for page_no, page in enumerate(pdf.pages, start=1):
        for table in page.extract_tables() or []:
            tables.append({"page": page_no, "rows": table})

with open("out/raw.json", "w", encoding="utf-8") as fh:
    json.dump(tables, fh, ensure_ascii=False, indent=2)
print(f"pages_with_tables={len(tables)}")
PY
```

```markdown
---
description: 把上一个抽取结果落成符合口径的 CSV

---

按 `$1` 口径把 `out/raw.json` 转成 CSV。要求：

- 列顺序与 `references/schema.md` 中 $1 的定义完全一致
- 金额保留两位小数，缺失值留空
- 输出 `out/final.csv`，并报告记录数与异常行数

补充说明：$@
```

```text
1. 团队规范用「包」分发，别指望每个人手动复制 extensions/ 与 prompts/
2. 宿主提供的包写进 peerDependencies 并写 "*"，否则会出现重复注册表
```

## 最佳实践与踩坑记录

1. **按最小机制选型。** 复用一段提示词用提示模板；一套过程知识加脚本用技能；只有需要新工具、新 Provider 或事件拦截时才写扩展。多数「我想要个扩展」的需求其实是技能或模板。

2. **扩展放 `~/.pi/agent/extensions/`，本地路径只用 `-e` 试跑。** 自动发现位置支持 `/reload` 热重载，`-e` 不行。把还在调的扩展写成 `-e` 会让你不断重启进程。

3. **技能描述当路由用，不当简介写。** description 同时说清「做什么」和「什么时候用」，官方明确点名 `Helps with PDFs` 这类描述会让模型找不到加载时机。

4. **`before_agent_start` 里只改片段，不整段替换。** 改 `sections` / `selectedTools` / `promptGuidelines` 时 Pi 只追加差异补丁，前缀缓存继续命中；返回 `systemPrompt` 或 `forceSystemPrompt` 会整段替换，每次变化都造成缓存失效。

5. **包依赖严格分区。** 运行时第三方依赖放 `dependencies`，宿主提供的五个包放 `peerDependencies` 且范围写 `"*"`，绝不打包宿主包——否则会出现重复的类、注册表与初始化开销。

6. **会话级资源遵守「后开先关」。** 不要在扩展工厂里启动进程、socket、watcher 或定时器；改到 `session_start`（或首次需要时）启动，并在 `session_shutdown` 里幂等关闭，因为 `/fork`、`/resume`、`/new` 都会重建扩展实例。

坑 1：把扩展放进 `.pi/extensions/`，结果在 CI 里完全没生效。
结论：项目扩展要先通过项目信任才会加载，无界面模式不会弹信任提示。
原因：项目信任保护 `.pi/settings.json`、`.pi/mcp.json`、`.pi/extensions`、`.pi/skills`、`.pi/prompts`、`.pi/themes` 等资源；print / JSON / RPC 模式无法显示内置信任提示，`defaultProjectTrust` 为 `"ask"` 或 `"never"` 时直接跳过。
解法：需要项目级扩展同时也能在 CI 生效时，把扩展装到用户作用域（`~/.pi/agent/extensions/`），或在自动化命令里加 `--approve` / 设置 `defaultProjectTrust: "always"`。

坑 2：改了扩展文件，行为不变，以为扩展坏了。
结论：只有自动发现位置的扩展才能热重载。
原因：官方对 `/reload` 的说明限定在 `~/.pi/agent/extensions/` 或 `.pi/extensions/`；用 `pi -e ./path.ts` 加载的扩展不参与热重载。
解法：日常开发把扩展放到 `~/.pi/agent/extensions/`，改完执行 `/reload`；临时验证一个第三方包时才用 `-e`。

坑 3：技能放在 `prompts/` 子目录里，Pi 完全没发现。
结论：`prompts/` 的模板发现是非递归的。
原因：模板只在 `prompts/` 目录这一层扫描，子目录不会自动下沉；技能目录的发现是递归的，但模板不是。
解法：模板平铺在 `prompts/` 下，或用 `prompts` 设置项 / 包清单把子目录显式列出来。

坑 4：扩展里 `import` 了 `@earendil-works/pi-coding-agent` 并写进了 `dependencies`。
结论：这会造成重复的类与注册表，Pi 检测到会告警。
原因：Pi 宿主已经提供这些包；物理副本会绕过扩展的模块映射，让同一模块出现两份实例。
解法：宿主提供的包（`@earendil-works/pi-ai`、`@earendil-works/pi-agent-core`、`@earendil-works/pi-coding-agent`、`@earendil-works/pi-tui`、`typebox`）写成 `peerDependencies` 且范围 `"*"`，并且不要打包；真正的第三方运行时依赖才放 `dependencies`。

坑 5：在事件处理器里调用 `ctx.newSession()` / `ctx.fork()`，会话卡死。
结论：会话控制方法只能在命令处理器里调用。
原因：`ExtensionCommandContext` 才带这些方法，它们从事件处理器调用会死锁；命令处理器里也要先 `await ctx.waitForIdle()` 再改会话。
解法：把会话切换逻辑放进 `pi.registerCommand` 的 handler，先等空闲再操作；事件处理器只做观察与轻量改写。
