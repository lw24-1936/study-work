## 概述

装 Pi 只有两步：装包、登录。装包有三条路（官方安装脚本、npm、Nix），登录有两条路（交互式 `/login`，或在启动前设好 provider 的 API key）。真正的坑不在安装本身，而在三处细节：**Node 版本下限是 22.19**、**官方脚本与 npm 的依赖固定策略不同**（影响 CI 可复现性）、**卸载不会清理 `~/.pi/agent/` 下的配置与凭据**。

本文所有命令与真实输出均来自本机实测（2026-10-15，Ubuntu 24.04，Node v26.7.0 / npm 11.19.0，Pi 1.2.0）。

```text
安装与登录三步：
1. 装 —— npm install -g --ignore-scripts @earendil-works/pi-coding-agent（或官方脚本 / Nix）
2. 验 —— pi --version 输出 1.2.0，which pi 指向真实路径
3. 登 —— 交互里 /login 选 provider，或启动前 export ANTHROPIC_API_KEY=...
```

```text
$ npm install -g --ignore-scripts @earendil-works/pi-coding-agent
changed 118 packages in 5s
$ which pi
/root/.hermes/tools/node-26.7.0-linux-x64/bin/pi
$ pi --version
1.2.0
```

## 系统要求与安装方式

Pi 对运行时的硬要求来自包元数据：`engines.node` 为 `>=22.19.0`，也就是说 **Node.js 22.19 或更新**。官方安装脚本在 macOS、Linux、Windows 上会在缺少 Node 时自动帮你装一个；npm 路径则需要你先自备满足版本的 Node。除此之外没有 Python、Rust 之类的额外依赖，包本身是纯 JavaScript（MIT）。

三种官方安装方式：

| 方式 | 命令 | 依赖固定 | 适用 |
|---|---|---|---|
| 官方脚本 | `curl -fsSL https://pi.dev/install.sh \| sh` | 固定全部依赖 | 个人机器、无 Node 环境 |
| npm | `npm install -g --ignore-scripts @earendil-works/pi-coding-agent` | 不固定传递依赖 | CI、已有 Node 工具链 |
| Nix | `nix profile add github:earendil-works/pi/stable` | 由 flake 锁定 | NixOS / 声明式环境 |

```shell
# 方式一：官方安装脚本（macOS / Linux；脚本会固定依赖版本，升级用 pi update）
curl -fsSL https://pi.dev/install.sh | sh

# 方式二：npm 全局安装（本机实测路径）
npm install -g --ignore-scripts @earendil-works/pi-coding-agent

# 方式三：Nix（从源码构建，pi update 无法更新它）
nix profile add github:earendil-works/pi/stable
# 较老的 Nix 用：nix profile install github:earendil-works/pi/stable

# 验证
pi --version
```

Windows 原生环境用 PowerShell 安装脚本：

```powershell
powershell -c "irm https://pi.dev/install.ps1 | iex"
```

`--ignore-scripts` 的作用是禁掉依赖包的生命周期脚本。官方明确说明：Pi 正常 npm 安装**不需要**依赖的 install 脚本，加上它等于砍掉一条供应链攻击面，企业环境建议始终带上这个参数。

```text
安装方式要点：
1. Node 下限 22.19 —— 低于这个版本 npm 路径会失败或行为不保证
2. 脚本 vs npm —— 脚本固定依赖（可复现），npm 不固定传递依赖（更灵活）
3. --ignore-scripts 是好习惯 —— Pi 不依赖 install 脚本，禁用可减少供应链风险
4. Nix 由 flake 管版本 —— pi update 不能更新 Nix 安装，要用 nix profile upgrade pi
5. Windows 走 install.ps1 —— 本机是 Linux，PowerShell 路径未实测
```

## 安装脚本、npm 与 Nix 的对比

三条路的外观差别很小，但升级与锁版本的行为差别很大，选错会在 CI 里付出代价。

| 行为 | 官方脚本 | npm | Nix |
|---|---|---|---|
| 是否自动装 Node | 是（缺则装） | 否 | 否（由 flake 环境提供） |
| 依赖是否固定 | 固定全部依赖 | 不固定传递依赖 | 固定 |
| 升级 Pi | `pi update` | `pi update` | `nix profile upgrade pi` |
| 固定版本 | 不支持参数，需改用 npm | `@1.2.0` 指定版本号 | `github:earendil-works/pi/v1.0.0` |
| 卸载 | 重跑脚本选 Uninstall Pi | `npm uninstall -g ...` | `nix profile remove pi` |
| 适合 CI | 可以，但版本跟随最新 | 最适合（钉版本号） | 适合（声明式锁定） |

```shell
# 官方脚本升级：重跑同一条命令即可（脚本内部会调 pi update 逻辑）
curl -fsSL https://pi.dev/install.sh | sh

# npm 升级 / 固定版本（CI 里应当显式钉版本）
npm install -g --ignore-scripts @earendil-works/pi-coding-agent@latest
npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.2.0

# Nix：升级与锁 tag
nix profile upgrade pi
nix profile add github:earendil-works/pi/v1.0.0
```

```text
选择要点：
1. 个人机器 → 官方脚本，省心且自带 Node
2. CI / 团队 → npm 并写死版本号，保证可复现
3. 声明式环境 → Nix，但记住 pi update 管不到它
4. 需要降级 → 只有 npm 路径能一条命令换版本
5. 混装有害 —— 同一台机器上只保留一种安装方式，否则 which pi 会指向意外的那个
```

## 验证安装与目录结构

装完先做三件验证：可执行文件在 PATH、版本号正确、凭据状态明确。第三条尤其重要，因为 Pi 在**没有凭据时不会假装能干活**——它会直接报错并以非零状态退出，这正好可以当作环境探针。

```shell
# 1. 可执行文件与版本
which pi
pi --version

# 2. 帮助（含真实工具清单与全部环境变量说明）
pi --help

# 3. 凭据探针：结构化输出 + 明确退出码
pi auth check --provider anthropic --json; echo "exit=$?"

# 4. 未登录时试图跑任务：必须失败且错误走 stderr
pi -p "say hi"; echo "exit=$?"
```

本机真实输出：

```text
$ pi --version
1.2.0

$ pi auth check --provider anthropic --json; echo "exit=$?"
{"status":"not_ready","provider":"anthropic","reason":"credentials_not_configured"}
exit=1

$ pi -p "say hi"
No API key found for the selected model.

Use /login to log into a provider via OAuth or API key. See:
  /root/.hermes/tools/node-26.7.0-linux-x64/lib/node_modules/@earendil-works/pi-coding-agent/docs/providers.md
exit=1
```

Pi 的用户级数据全部集中在**代理目录**（agent directory），默认 `~/.pi/agent`，可用环境变量 `PI_CODING_AGENT_DIR` 改到别处。下面是这个目录的职责表，排查问题时基本都在这里找文件：

| 路径 | 职责 |
|---|---|
| `<agent-dir>/settings.json` | 用户级设置：偏好、默认值、资源路径、pi package 声明 |
| `<agent-dir>/keybindings.json` | 自定义快捷键 |
| `<agent-dir>/mcp.json` | 所有项目共用的 MCP server |
| `<agent-dir>/models.json` | 兼容端点、模型定义与模型覆盖 |
| `<agent-dir>/auth.json` | 保存的 API key 与 OAuth 凭据（等同密码） |
| `<agent-dir>/AGENTS.md` 等 | 跨工作目录生效的用户指令（也识别 `CLAUDE.md`、`AGENTS.override.md`） |
| `<agent-dir>/SYSTEM.md` | 替换 Pi 默认系统提示 |
| `<agent-dir>/APPEND_SYSTEM.md` | 追加到系统提示 |
| `<agent-dir>/extensions/`、`skills/`、`prompts/`、`themes/` | 用户级扩展、技能、提示模板、主题 |
| `<agent-dir>/sessions/` | 会话文件（JSONL），按工作目录分组 |

```shell
# 默认位置确认（本机未改过，即 ~/.pi/agent）
export PI_CODING_AGENT_DIR=~/.pi/agent
ls -la "$PI_CODING_AGENT_DIR"

# 把配置放到别处做隔离（例如按项目或按沙箱）
PI_CODING_AGENT_DIR=/tmp/pi-sandbox/agent pi --version

# 会话存储位置的三级覆盖（CLI 优先级最高）
pi --session-dir /data/pi-sessions
export PI_CODING_AGENT_SESSION_DIR=/data/pi-sessions
# 或在 settings.json 里写 sessionDir
```

```text
安装验证要点：
1. 三个探针 —— which pi / pi --version / pi auth check --json，一分钟内确定环境可用
2. 退出码即契约 —— auth check 的 ready / not_ready / invalid 对应退出码 0 / 1 / 2
3. 配置集中 —— 所有用户级数据在 ~/.pi/agent，备份与清理只需处理这一个目录
4. 目录可迁移 —— PI_CODING_AGENT_DIR 指向别处即可做到"一人多套环境"
5. 会话分级覆盖 —— --session-dir > PI_CODING_AGENT_SESSION_DIR > sessionDir 设置
```

## 内置 Provider 登录与凭据管理

Pi 内置 15 个以上的 provider（Anthropic、OpenAI、Google、Azure、Bedrock、Mistral、Groq、Cerebras、xAI、OpenRouter、Ollama、Hugging Face、Kimi For Coding、MiniMax 等）。多数宿主 provider 支持两种认证方式：浏览器/设备码 OAuth 登录，或直接给 API key；Bedrock 与 Google Vertex AI 还能使用云平台的 ambient 凭据。

```text
# 交互式登录：在 Pi 里输入（不是 shell 命令）
/login               # 选择 provider，Pi 引导完成 OAuth 或录入 API key
/login radius        # 直接指定 provider
/model               # 登录后选择具体模型
/logout              # 移除某个 provider 的凭据（不清环境变量、不在服务端吊销）
```

登录成功后凭据写入 `<agent-dir>/auth.json`。在远程或无头机器上，OAuth 回调可能回不到本机进程，此时 Pi 会提示你把最终的重定向 URL 或授权码粘贴回来。持续集成里更推荐用环境变量而不是写文件：

```shell
# 环境变量认证（CI / 不想落盘时用），必须在启动 pi 之前 export
export ANTHROPIC_API_KEY=sk-ant-...
pi

# 常见 provider 的变量名（官方完整列表更长，见 pi --help 的 Environment Variables 段）
#   ANTHROPIC_API_KEY / OPENAI_API_KEY / GEMINI_API_KEY / DEEPSEEK_API_KEY
#   OPENROUTER_API_KEY / XAI_API_KEY / GROQ_API_KEY / CEREBRAS_API_KEY
#   COPILOT_GITHUB_TOKEN / HF_TOKEN / MINIMAX_API_KEY / KIMI_API_KEY
# Azure OpenAI 还需要 base URL 或资源名：
export AZURE_OPENAI_API_KEY=...
export AZURE_OPENAI_BASE_URL=https://your-resource.ai.azure.com
```

需要在不落盘的前提下使用密钥管理器时，可以在 `auth.json` 里把 key 写成一个以 `!` 开头的命令，Pi 首次需要该凭据时执行它并缓存标准输出：

```json
{
  "anthropic": {
    "type": "api_key",
    "key": "!security find-generic-password -ws 'anthropic'"
  }
}
```

自动化场景（CI、外部客户端、跑在别的程序里的 Pi）还可以用 `pi auth` 子命令直接取凭据。注意：**打印类命令会把密钥写到 stdout**，不要把它接进日志。

```shell
# 检查某个 provider 或模型是否可用（推荐写法：带 --json）
pi auth check --provider openai --json
pi auth check --model sonnet:high --json

# 取凭据给外部客户端用（会输出明文密钥，慎用）
pi auth print-api-key --provider openai
pi auth print-bearer-token --provider openai-codex --min-expiry 30m
```

```text
登录要点：
1. 两条路都行 —— /login 适合人，环境变量适合机器；CI 优先环境变量
2. auth.json 等同密码 —— 含 API key 与 OAuth token，不提交、不贴工单、不进日志
3. 无头机器兜底 —— 把重定向 URL 或授权码粘回 Pi 的提示里即可完成登录
4. logout 不彻底 —— 它只删本地凭据，环境变量、models.json 里的 key、服务端授权都还在
5. 子命令给机器用 —— pi auth check 的结构化输出可做健康检查，退出码可直接判断
```

## 环境变量与凭据优先级

同一个模型可能有多处凭据来源，Pi 的解析顺序是固定的：**运行时 `--api-key` → `auth.json` 中保存的凭据 → `models.json` 里的 `apiKey` → provider 的环境变量 / ambient 云凭据**。provider 扩展还可以定义自己的认证行为。理解这个顺序，才能在「明明 export 了变量却没生效」时快速定位。

```shell
# 一次性覆盖（优先级最高，不落盘，且必须配合 --model 或 --models 使用）
pi --model sonnet:high --api-key "$MY_TEMP_KEY"

# 查看某 provider 当前是否就绪（真实输出）
pi auth check --provider anthropic
```

```text
$ pi auth check --provider anthropic
{"status":"not_ready","provider":"anthropic","reason":"credentials_not_configured"}
```

与进程相关的常用环境变量（完整清单在 `pi --help` 末尾）：

| 变量 | 作用 |
|---|---|
| `PI_CODING_AGENT_DIR` | 配置目录，默认 `~/.pi/agent` |
| `PI_CODING_AGENT_SESSION_DIR` | 会话存储目录（被 `--session-dir` 覆盖） |
| `PI_OFFLINE` | 设为 1/true/yes 时禁用启动期网络操作（等价 `--offline`） |
| `PI_TELEMETRY` | 覆盖安装遥测开关（1/true/yes 或 0/false/no） |
| `PI_PACKAGE_DIR` | 覆盖包目录（Nix/Guix 场景） |
| `PI_SHARE_VIEWER_URL` | `/share` 生成的查看链接前缀，默认 `https://pi.dev/session/` |

```json
{
  "cloudflare-workers-ai": {
    "type": "api_key",
    "key": "...",
    "env": {
      "CLOUDFLARE_ACCOUNT_ID": "account-id"
    }
  }
}
```

上面这种写法说明：**保存的凭据里可以带一个 `env` 对象，其值对该 provider 优先于进程环境**。反过来，如果你在 CI 里 export 了变量却被 `auth.json` 里一份过期凭据遮住，`pi auth check` 会显示 ready，实际却用错账号——这类问题只能靠优先级表排查。

```text
凭据优先级要点：
1. 顺序固定 —— --api-key > auth.json > models.json 的 apiKey > 环境变量/ambient
2. 环境变量最"弱" —— 只要 auth.json 里有凭据，export 的变量可能根本不会被使用
3. --api-key 需配 --model —— 它只是覆盖 key，不负责在多个 provider 之间做选择
4. env 对象反向覆盖 —— 凭据里带 env 时，这些值对该 provider 优先于进程环境
5. 排查靠探针 —— 一律先用 pi auth check --json 确认实际生效的凭据来源
```

## 更新与版本固定

`pi update` 管三样东西：Pi 自身、已安装的 package、模型目录。不带目标时只更新 Pi 自己；团队环境里更常见的是分开执行，便于定位是哪一环出了变化。

```shell
# 查看更新命令的完整约束（本机真实输出见下）
pi update --help

# 更新 Pi
pi update

# 只更新已装包 / 只刷新模型目录 / 两者都更新
pi update --extensions
pi update --models
pi update --all

# 强制重装 Pi（即使当前已是最新）
pi update --force

# 固定版本（npm 路径）：CI 里应当写死版本号
npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.2.0
```

本机 `pi update --help` 的真实输出（关键部分）：

```text
Usage:
  pi update [source|self|pi] [--self|--extensions|--models|--all] [--extension <source>] [--approve|--no-approve] [--force]

Options:
  --self                  Update pi only (default when no target is given)
  --extensions            Update installed packages only
  --models                Refresh model catalogs only
  --all                   Update pi and installed packages
  --extension <source>    Update one package only
  --force                 Reinstall pi even if the current version is latest
```

如果你想在开新会话时不被打断，可以关掉更新与遥测相关的设置：

```json
{
  "$schema": "https://pi.dev/schemas/settings.schema.json",
  "collapseChangelog": true,
  "enableInstallTelemetry": false,
  "enableAnalytics": false
}
```

```text
更新与固定版本要点：
1. pi update 三件事 —— Pi 自身（默认）、--extensions 装好的包、--models 模型目录
2. Nix 例外 —— Nix 安装的 Pi 无法用 pi update 升级，需 nix profile upgrade pi
3. CI 钉版本 —— npm 装 @1.2.0 这类精确版本，避免 runner 上版本漂移
4. 模型目录也会变 —— 新模型只在刷新目录后出现；--offline 或 PI_OFFLINE 会跳过刷新
5. 设置可控 —— collapseChangelog / enableInstallTelemetry 让更新过程更安静
```

## 卸载与残留清理

三种安装方式各有对应的卸载命令，但**没有一种会删除 `~/.pi/agent/` 下的配置、凭据、会话与已装 pi package**。这是设计使然（重装后你能立刻回到原状态），也意味着「彻底清理」必须手动做，而手动删之前请先确认里面没有你还要的会话。

```shell
# npm 安装
npm uninstall -g @earendil-works/pi-coding-agent

# 官方脚本安装：重跑脚本并选择 Uninstall Pi
curl -fsSL https://pi.dev/install.sh | sh

# Nix 安装
nix profile remove pi

# 清理用户级数据（危险：凭据与会话一并删除，先备份！）
mv ~/.pi/agent ~/.pi/agent.bak.$(date +%F)
```

```text
卸载要点：
1. 先卸载二进制 —— 再处理数据目录，顺序反了 pi 可能仍在 PATH 里
2. 数据不会被自动删 —— auth.json、settings.json、sessions/、已装包都留在 ~/.pi/agent
3. 备份优于删除 —— mv 成 .bak 目录，确认无用后再删，避免误删历史会话
4. package 目录另算 —— 通过 pi install 装的包声明写在 settings.json，卸载 Pi 后声明仍在
5. 环境变量要检查 —— CI 变量、shell rc 里 export 的 key 与 PI_* 都要一并清理
```

## 应用场景实战

### 场景一：开发机上从零装好 Pi 并完成登录

面向刚拿到一台干净 Ubuntu 开发机（已有 Node 22.19+、Git）的场景，目标是脚本化安装、确认版本、登录一个 provider 并跑通第一个任务。

```shell
#!/usr/bin/env bash
# setup-pi.sh —— 开发机初始化 Pi
set -euo pipefail

# 1. 前置检查：Node 版本必须 >= 22.19
node --version

# 2. 安装（忽略依赖生命周期脚本）
npm install -g --ignore-scripts @earendil-works/pi-coding-agent

# 3. 验证
which pi
pi --version

# 4. 准备一个练习仓库（Pi 以工作目录为文件发现范围与会话分组依据）
mkdir -p ~/code/hello-pi
cd ~/code/hello-pi
git init -q
printf 'def add(a, b):\n    return a + b\n' > calc.py
git add -A && git commit -qm "chore: 初始化练习仓库"

# 5. 启动交互式会话（首次会询问是否信任该目录）
pi
```

在 Pi 里完成登录与第一个任务：

```text
/login                        # 选 provider → 完成 OAuth 或粘贴 API key
```

### 场景二：CI runner 上固定版本、用环境变量认证并做非交互任务

企业流水线要求可复现、无交互、密钥不落盘。做法是 npm 钉版本、把 key 放在单步环境变量里、用 print 模式产出文件。

```yaml
# .github/workflows/pi-review.yml
name: Review with Pi
on:
  workflow_dispatch:

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0

      - uses: actions/setup-node@v4
        with:
          node-version: "22.19"        # Pi 要求 >= 22.19

      - name: Install Pi (pinned)
        run: npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.2.0

      - name: Check credentials
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          pi --version
          pi auth check --provider anthropic --json

      - name: Generate review notes
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          git diff origin/main...HEAD | pi -p "审查这次改动，按严重程度列出问题，只输出 Markdown" \
            > review-notes.md

      - uses: actions/upload-artifact@v4
        with:
          name: pi-review
          path: review-notes.md
```

```text
要点：
1. 版本钉死 —— @1.2.0 让 runner 上行为可复现，不随发布漂移
2. key 作用域最小 —— 只放在需要它的 step 的 env 里，不要提到 job 级
3. 先探针后干活 —— pi auth check --json 在真正调用模型前失败，省时省钱
4. 用 print 模式 —— -p 只把最终文本写 stdout，直接重定向成文件即可
5. 退出码要判 —— 模型侧错误会让 -p 以非零状态退出，CI 会自然失败而不是静默产出空文件
```

## 最佳实践与踩坑记录

### 最佳实践

1. 始终带上 `--ignore-scripts`：Pi 不需要依赖生命周期脚本，禁用可减少供应链风险，企业环境应写进标准安装命令。
2. 用 `pi auth check --provider <name> --json` 做环境健康检查：结构化输出加明确的退出码（0/1/2），比让脚本跑一次真实调用便宜得多。
3. 自动化里只走环境变量：CI 不要把 `auth.json` 落盘，`ANTHROPIC_API_KEY` 之类的变量只在需要的那一步可见。
4. 固定版本：团队与流水线都用 `@1.2.0` 这类精确版本，升级作为一次显式变更而不是随机发生。
5. 备份 `~/.pi/agent`：凭据、设置、会话、已装包全在里面，换机或误删时的恢复成本远高于一次备份。
6. 本地环境用 `PI_CODING_AGENT_DIR` 隔离：给实验性配置单开一个目录，避免污染日常环境。

### 踩坑记录

```text
坑 1：Node 版本不够，npm 安装后 pi 启动报错
结论：pi --version 直接失败或行为异常。
原因：包元数据要求 engines.node >= 22.19.0，低于该版本不受支持。
解法：升级 Node（nvm/官方脚本均可）；或改用官方安装脚本，它会在缺失时自动装 Node。

坑 2：以为卸载干净了，重装后旧凭据和会话还在
结论：卸载后 ~/.pi/agent/ 里的 auth.json、sessions/、设置与包声明原封不动。
原因：官方明确说明三种卸载方式都不会清理代理目录下的数据。
解法：确认无需保留后用 mv ~/.pi/agent ~/.pi/agent.bak 归档再删，不要直接 rm -rf。

坑 3：export 了 ANTHROPIC_API_KEY，Pi 却用了别的账号
结论：pi auth check 显示 ready，但实际请求走的是 auth.json 里的旧凭据。
原因：凭据优先级为 --api-key > auth.json > models.json 的 apiKey > 环境变量。
解法：用 /logout 清掉不需要的 provider，或用 pi auth check --json 确认实际生效来源。

坑 4：Nix 装的 Pi 执行 pi update 没反应
结论：pi update 无法把 Nix 安装的 Pi 升到新版本（包与模型目录仍可更新）。
原因：该 Pi 由 Nix 提供，pi update 不能替换由其它包管理器管理的安装。
解法：用 nix profile upgrade pi；要锁版本就用 tag，如 github:earendil-works/pi/v1.0.0。

坑 5：把 pi auth print-api-key 的输出接进了日志
结论：明文密钥出现在 CI 日志或工单里，等同于泄漏。
原因：print-api-key / print-bearer-token 的作用就是把密钥写到 stdout。
解法：只在管道内即时消费，绝不重定向到文件或日志；优先用 pi auth check 做探测。
```
