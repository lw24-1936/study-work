## 概述

Pi 的集成面可以概括成三层：**模型层**用 15+ provider 与 `models.json` 接入任何兼容端点，**工具层**用 MCP 与扩展把外部系统接进来，**进程层**用 interactive / print / JSON / RPC 四种模式加 TypeScript SDK 把 Pi 塞进脚本、CI 或另一个应用。四者共享同一套 agent、会话、资源与工具，换的只是输入输出的通道。

理解这一点之后，集成工作就变成选择题：需要最终文本就 print，需要结构化进度就 JSON，需要双向控制就 RPC，想省掉进程边界就让 SDK 直接嵌进 Node 进程。

```text
本篇要解决的问题：
1. 凭据从哪来、多个来源冲突时谁优先、怎么在 CI 里不落盘
2. 如何用 models.json 接入 Ollama / LM Studio / vLLM / 自建代理等兼容端点
3. interactive / print / JSON / RPC / SDK 各自的适用边界与真实行为差异
4. MCP 服务器怎么加、工具怎么命名、工具曝光如何控制
5. 会话导出与分享的目标与注意事项
6. 和 Claude Code、Codex、OpenCode 等同类工具的可控维度对比
```

本篇命令与实际输出以本机安装的 `@earendil-works/pi-coding-agent@1.2.0` 实测为准；官方文档见 `https://pi.dev/docs/latest/providers`、`https://pi.dev/docs/latest/models`、`https://pi.dev/docs/latest/cli-integration`、`https://pi.dev/docs/latest/mcp`、`https://pi.dev/docs/latest/sdk`。

## 多 Provider 与凭据解析

登录方式有两种：用 `/login [provider]` 走 OAuth 或 API key 流程，凭据保存到 `auth.json`；或者用 provider 的环境变量在进程里提供。`/logout` 只删除 Pi 存储的凭据，它**不会**取消环境变量、不会移除 `models.json` 里的认证、也不会在 provider 侧吊销凭据。`auth.json` 里可能有 API key 与 OAuth token，必须保持私密。

环境变量适合 CI 与不想让 Pi 落盘密钥的场景：

| Provider | 环境变量 |
| --- | --- |
| Anthropic | `ANTHROPIC_API_KEY`（也识别 `ANTHROPIC_OAUTH_TOKEN`、`ANTHROPIC_AUTH_TOKEN`） |
| OpenAI | `OPENAI_API_KEY` |
| Google Gemini | `GEMINI_API_KEY` |
| DeepSeek | `DEEPSEEK_API_KEY` |
| Groq | `GROQ_API_KEY` |
| Mistral | `MISTRAL_API_KEY` |
| xAI | `XAI_API_KEY` |
| OpenRouter | `OPENROUTER_API_KEY` |
| GitHub Copilot | `COPILOT_GITHUB_TOKEN` |
| NVIDIA NIM | `NVIDIA_API_KEY` |
| Hugging Face | `HF_TOKEN` |
| Azure OpenAI | `AZURE_OPENAI_API_KEY` + base URL 或资源名 |
| Amazon Bedrock | `AWS_PROFILE` / `AWS_ACCESS_KEY_ID` 等，或 `AWS_BEARER_TOKEN_BEDROCK` |
| Google Vertex AI | `GOOGLE_CLOUD_API_KEY`，或用 ADC + `GOOGLE_CLOUD_PROJECT`/`GOOGLE_CLOUD_LOCATION` |

多个凭据来源同时存在时，Pi 的解析顺序是：运行时 `--api-key` > `auth.json` 里存储的凭据 > `models.json` 的 `apiKey` > provider 的环境变量或云环境凭据。Provider 扩展可以定义自己的认证行为。

不想把解析后的密钥写到磁盘时，可以把 `auth.json` 里的 `key` 设成以 `!` 开头的命令，让 Pi 在第一次需要时执行它并缓存标准输出：

```json
{
  "anthropic": {
    "type": "api_key",
    "key": "!security find-generic-password -ws 'anthropic'"
  }
}
```

命令输出为空、超时或退出码非零时，密钥在该进程内保持未解析状态，直到重启 Pi。需要注意：`models.json` 里以 `!` 开头的命令是**在请求时执行**且不被缓存，两者行为不同。

诊断凭据状态推荐用 `pi auth` 系列命令，它们在没有会话的情况下也能跑：

```shell
# 检查某个 provider 是否就绪（退出码 0=ready、1=not_ready、2=invalid）
pi auth check --provider openai --json

# 打印解析后的 API key / OAuth bearer token（会把密钥写到 stdout）
pi auth print-api-key --provider openai
pi auth print-bearer-token --provider openai --min-expiry 30m
```

本机实测（未配置任何凭据）：

```text
$ pi auth check --provider openai --json
{"status":"not_ready","provider":"openai","reason":"credentials_not_configured"}

$ pi --list-models
No models available. Use /login to log into a provider via OAuth or API key. See:
  /root/.hermes/tools/node-26.7.0-linux-x64/lib/node_modules/@earendil-works/pi-coding-agent/docs/providers.md
  /root/.hermes/tools/node-26.7.0-linux-x64/lib/node_modules/@earendil-works/pi-coding-agent/docs/models.md
```

`not_ready` 加 `credentials_not_configured` 说明问题不在模型目录，而在凭据本身——这是排查「模型选不到」的第一刀。

```text
Provider 与凭据要点：
1. 认证两条路：/login 写入 auth.json，或 provider 的环境变量（CI 首选）
2. 优先级：--api-key > auth.json > models.json 的 apiKey > 环境变量 / 云环境凭据
3. auth.json 的 key 支持 !command 延迟取密钥；models.json 的 !command 在请求时执行且不缓存
4. /logout 只删 Pi 里的凭据，不取消环境变量、不改 models.json、不吊销远端
5. 自动化里用 pi auth check --provider X --json 做健康检查，退出码三段式更好判断
6. Azure / Bedrock / Vertex 需要额外变量（base URL、资源名、region、项目与位置）
```

## models.json 与自定义端点

Pi 内置了主流 provider 与模型目录，只有在「Pi 没包含这个 provider 或端点」时才需要自己配。`models.json` 位于 agent 目录（`~/.pi/agent/models.json`），用来声明兼容端点与模型覆盖。Ollama、LM Studio、vLLM、SGLang 以及各类代理部署，只要能说 Pi 已支持的 API，都可以用它接进来。

```json
{
  "$schema": "https://pi.dev/schemas/models.schema.json",
  "providers": {
    "ollama": {
      "baseUrl": "http://localhost:11434/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "models": [
        { "id": "qwen2.5-coder:7b" }
      ]
    }
  }
}
```

`apiKey` 写个占位值是为了让模型在 `/model` 里可见，Ollama 本身不校验它。需要认证的端点上，`apiKey` 与 header 值支持三种写法：`$NAME` / `${NAME}` 环境变量插值、字面量、或以 `!` 开头的命令（请求时执行）。打开 `/model` 会重新加载该文件；`models` 里同 ID 的条目会新增或替换该 provider 的同名模型；想改内置或扩展提供的模型元数据而不替换模型列表时用 `modelOverrides`，未知 ID 会被忽略。

采样参数与缓存生命周期也可以按模型声明。`samplingParams` 是默认值，`samplingParamsByThinkingLevel` 按 Pi 的思考等级（`off`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max`）覆盖；合并顺序是先夹取模型不支持的等级，再依次合入模型默认值、等级覆盖、请求级 `samplingParams`，后写入的键胜出。`promptCache` 声明 provider 的尽力而为缓存寿命（秒），用于决定模型是否有资格做缓存预热：

```json
{
  "id": "qwen-thinking-model",
  "reasoning": true,
  "samplingParams": { "temperature": 1.0, "top_p": 0.95 },
  "samplingParamsByThinkingLevel": {
    "off": { "temperature": 0.7, "top_p": 0.8 },
    "high": { "top_k": 20 }
  },
  "promptCache": { "short": 300, "long": 3600 }
}
```

启用任何兼容性开关前，官方建议先确认端点在请求或响应行为上确实存在差异——不要因为对方宣称「兼容 OpenAI / Anthropic」就打开。这些采样字段只对 `openai-completions`、`openai-responses`、`azure-openai-responses` 生效，其他 API 会忽略。

本地模型的另一条路是 llama.cpp router：Pi 直接集成它，router 发现 GGUF 文件并按需加载模型，`/llama` 管理 router，`/model` 选择已加载的模型。OpenRouter 这类聚合商还可以把 base URL 指到区域端点：

```json
{
  "providers": {
    "openrouter": { "baseUrl": "https://us.openrouter.ai/api/v1" }
  }
}
```

分类模型（classifier）与图像模型不进 `/model`，而是通过 `codemode` 工具在脚本里调用：`models.getAvailableOfType("classifier")`、`models.classify(...)`、`models.generateImages(...)`。它们在没有 MCP 服务器激活 codemode 时需要手动打开：在 `settings.json` 写 `"defaultTools": ["+codemode"]`。

```text
models.json 要点：
1. 只在 Pi 没内置该 provider/端点时才需要写；路径是 agent 目录下的 models.json
2. 关键字段：baseUrl、api、apiKey、models[]；modelOverrides 只改元数据不换模型列表
3. apiKey 与 header 支持 $NAME / ${NAME} 插值与 !command，前者在请求时求值且不缓存
4. samplingParams 与 samplingParamsByThinkingLevel 只对 openai 系 API 生效
5. promptCache 声明 short / long 缓存寿命，决定缓存预热资格
6. classifier / image 模型不进 /model，通过 codemode 脚本调用，需要时先启用 codemode
```

## 四种运行模式与外部集成

同一个 agent，四种输入输出通道。选择依据是「谁在驱动、需要什么形状的输出、进程要不要常驻」：

| 模式 | 接口 | 生命周期 | 适用场景 |
| --- | --- | --- | --- |
| Interactive | 终端 UI | 用户退出为止 | 人直接和 Pi 协作 |
| Print | stdout 上的最终文本 | 单次调用 | 脚本只需要最终回复 |
| JSON | stdout 上的 JSONL 事件 | 单次调用 | 需要一个运行过程的结构化进度 |
| RPC | JSONL 命令 / 响应 / 事件 | 长驻 | 需要双向控制 |
| SDK | 进程内 TypeScript API | 由宿主进程决定 | 直接嵌进 Node / Bun 应用 |

```shell
# print 模式：只取最终文本，适合命令替换与管道
pi --print "总结这个仓库最近的改动" > summary.txt

# 没有显式指定模式时，非 TTY 的 stdin/stdout 也会自动落到 print 模式
git diff | pi "review this diff"

# JSON 事件流：一个会话头 + 后续 agent/session 事件
pi --mode json "审查这个仓库" > events.jsonl

# RPC：常驻进程，stdin 收命令、stdout 出响应与事件
pi --mode rpc --no-session
```

print 模式的退出码语义值得记牢：最终回复带 `error` 或 `aborted` 结束原因时返回非零；被输出 token 上限截断（`length`）的回复仍打印部分文本到 stdout、往 stderr 写警告、并返回非零。JSON 模式相反——失败或中止的回复会出现在事件流里，但**本身不会**让退出码非零，所以消费 JSON 事件时必须读事件判断成败，不能只看退出码。

JSON 事件流有一个重建规则：`message_update` 里是**增量**而不是累积快照，实时输出要自己累加 delta，收到 `message_end` 后用其中的权威消息替换；`agent_end` 之后可能还有自动恢复或排队工作，判断「当前运行真的结束」要看 `agent_settled`。stdout 只放 JSONL，诊断与应用日志都在 stderr。

Node / TypeScript 集成优先用官方的 RPC 客户端，它负责启动子进程、关联请求与响应、提供类型化的命令方法，并把会话事件投递给监听器：

```typescript
// rpc-client.ts —— 发一条提示，流式打印文本，等空闲后关闭子进程
import { RpcClient } from "@earendil-works/pi-coding-agent";

const client = new RpcClient({ cliPath: "/path/to/pi/dist/cli.js" });
await client.start();

client.on("event", (event) => {
  if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});

// promptAndWait 会先装好监听器再发提示，避免与快速完成竞争
await client.promptAndWait("解释一下这个仓库的结构");
await client.shutdown();
```

如果不想有进程边界，就用 SDK 在进程内建会话。`createAgentSession()` 会读工作目录、发现资源、加载设置与凭据：

```typescript
// sdk-demo.ts
import { createAgentSession } from "@earendil-works/pi-coding-agent";

const { session } = await createAgentSession({ cwd: "/opt/app" });

const unsubscribe = session.subscribe((event) => {
  if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});

try {
  await session.prompt("列出这个目录里的测试入口");
  console.log("\n---\n", session.getLastAssistantText());
} finally {
  unsubscribe();
  session.dispose(); // 中止活动工作、失效扩展上下文、断开事件监听
}
```

SDK 侧有几个和 CLI 不同的默认：SDK 会话**不加载**内置扩展，需要 `createCodemodeExtension()`、`createToolSearchExtension()`、`createMcpExtension()` 时得自己加进 `DefaultResourceLoader`；不想落盘时用 `SessionManager.inMemory()`；`session.dispose()` 之后订阅失效，`AgentSessionRuntime` 的 `newSession()` / `switchSession()` / `fork()` 会替换活动会话，订阅需要重新绑定。

```text
运行模式与集成要点：
1. 非 TTY 会自动选 print 模式，脚本里可以省掉 --print
2. print 用退出码判断成败；JSON 必须读事件流判断，失败不会让退出码非零
3. message_update 是增量，message_end 才是权威消息；agent_settled 才代表真结束
4. RPC 用 RpcClient 更稳，promptAndWait 内建了监听器先于提示安装的顺序保证
5. SDK 不加载内置扩展，codemode / tool_search / MCP 需要显式添加
6. 会话替换后旧订阅失效，必须重新绑定
```

## MCP 与外部工具接入

Pi 通过 stdio 或 streamable HTTP 连接 MCP 服务器，把它们的工具与资源暴露给模型。用户级配置在 `~/.pi/agent/mcp.json`，项目级在 `.pi/mcp.json`（只在项目信任后读取）；同名条目下项目配置会替换用户配置。有一条例外很好用：一个项目条目如果只写 `enabled` / `exposure` / `toolExposure`、不写 `command`、`url`、`type`，它就只覆盖用户级同名服务器的这几个字段，其余（含 `env`、`headers`、`auth`）保持不变——这正是「在某个项目里临时关掉一个服务器」的写法。

```shell
# 添加一个本地 stdio 服务器（默认写用户级 mcp.json）
pi mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem .

# 添加远端 HTTP 服务器，token 从环境变量取
pi mcp add docs --url https://example.com/mcp --bearer-token-env-var DOCS_TOKEN

# 写进项目配置（-l / --local）
pi mcp add -l tools --env API_KEY='${TOOLS_KEY}' -- uvx tools-mcp

# 检查连接状态；有未连接或配置非法的条目时退出码为 1
pi mcp list
pi mcp list --json

# OAuth 服务器的登录 / 登出
pi mcp login docs --timeout 300
pi mcp logout docs
```

本机真实执行结果（先添加再检查）：

```text
$ pi mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem .
Added global MCP server "filesystem" in /root/.pi/agent/mcp.json.
Check it with: pi mcp list

$ cat /root/.pi/agent/mcp.json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "."
      ]
    }
  }
}

$ pi mcp list
filesystem: connected, 14 tools (codemode, global)
  npx -y @modelcontextprotocol/server-filesystem .
  tools: read_file, read_text_file, read_media_file, read_multiple_files, write_file, edit_file, create_directory, list_directory, list_directory_with_sizes, directory_tree, move_file, search_files, get_file_info, list_allowed_directories

$ pi mcp list            # 未配置任何服务器时
No MCP servers configured. Add them to /root/.pi/agent/mcp.json or .pi/mcp.json.
```

注意输出里的 `(codemode, global)`：每个服务器工具都注册为 `mcp__<server>__<tool>`，而 `exposure` 决定模型怎么够到它。默认是 `codemode`——工具能被 codemode 脚本调用，但既不出现在模型的工具声明里，也不列在 codemode 描述里，脚本要用 `searchTools()`、`describeTool()` 或 `ALL_TOOLS` 去发现。四种曝光方式的取舍：

| exposure | 行为 | 适合 |
| --- | --- | --- |
| `codemode`（默认） | 只能从 codemode 脚本调用，脚本自己发现工具 | 通用服务器，尤其想在脚本里组合、过滤调用时 |
| `deferred` | 直到 `tool_search` 为下一次模型调用匹配到它才声明 | 工具很多、希望被发现后再直接调用的服务器 |
| `direct` | 像内置工具一样声明给模型，同时也能从 codemode 调用 | 数量少、使用频繁的工具集 |
| `hidden` | 已注册但不可达 | 需要临时禁用的服务器或工具 |

`toolExposure` 可以按工具名或 `*` 模式覆盖服务器级设置，精确名优先于模式，模式之间先匹配者胜出：

```json
{
  "mcpServers": {
    "github": {
      "url": "https://api.githubcopilot.com/mcp/",
      "exposure": "deferred",
      "toolExposure": {
        "search_code": "direct",
        "get_*": "codemode",
        "delete_*": "hidden"
      }
    }
  }
}
```

其它几个实用行为：服务器连接时会自动激活 `codemode`（`codemode` 曝光）或 `tool_search`（`deferred` 曝光），不想要可以用 `"autoEnableCodemode": false`；`--no-mcp` 单次运行禁用 MCP；`pi --tools read,codemode,'mcp__radius__*'` 这种模式可以只保留某个服务器的工具；服务器提供 MCP resources 时 Pi 会加三个工具（`list_mcp_resources`、`list_mcp_resource_templates`、`read_mcp_resource`）；超过 20 KB 的文本结果在到达模型前会被中间截断，完整内容存到临时文件并在结果里给出路径，而 codemode 脚本拿到的是完整结果，可以先自己裁剪。

```text
MCP 接入要点：
1. 用户级 ~/.pi/agent/mcp.json，项目级 .pi/mcp.json（需信任）；同名条目项目替换用户
2. 只写 enabled/exposure/toolExposure 的项目条目是「覆盖增量」，其余字段沿用用户级
3. 工具命名 mcp__<server>__<tool>，默认 codemode 曝光，直接可见要显式给 direct
4. stdio 用 command/args/env/cwd，HTTP 用 url/headers/oauth，不支持旧的 SSE 传输
5. MCP 工具走同一条工具管线，权限门与 tool_call / tool_result 对它同样生效
6. 加完服务器在会话里用 /mcp 查看，在外面加完要 /reload
```

## 会话导出与分享

会话既是工作记录也是交付物料。`/export [path]` 可以把当前会话导出为 HTML 或 JSONL，`/share` 上传会话并返回一个查看链接。默认目标由认证状态决定：配置了 Radius 认证时用 Radius artifact（对所在的 Radius 组织可见），否则用 GitHub CLI 创建一个私有 gist；`sessionShareDestination` 设置可以强制成 `gist` 或 `radius`（`radius` 在没有 Radius 认证时不会回退到 gist）。

```shell
# 交互模式里导出与分享
/export ./session.html
/export ./session.jsonl
/share

# 把导出的 HTML 当离线交付物料带上，不需要模型凭据
pi --export ./session.jsonl    # 命令行形式：导出会话文件为 HTML 后退出

# 强制分享目标（settings.json）
# { "sessionShareDestination": "gist" }
```

导出与分享前必须自查内容：会话里可能有提示词、模型回复、工具参数、命令输出、文件内容，以及对话过程中暴露过的凭据。这条在官方文档里被反复强调（安全页、sessions 页、usage 页都写了），因为它是唯一无法用技术手段撤销的泄露。

## 与同类编码 Agent 的对比

选择 Pi 的理由通常不是「功能更多」，而是「定制成本更低」：扩展是普通 TypeScript 模块，四类资源可以用一个 npm 包整体分发，四种运行模式覆盖从人工到 CI 的全场景。下表只列与本篇「生态与集成」相关的可控维度，且各工具版本演进很快，具体行为请以各自官方文档为准。

| 维度 | Pi | Claude Code | Codex | OpenCode |
| --- | --- | --- | --- | --- |
| 定位 | 最小 harness，鼓励自行适配 | 开箱即用的编码 Agent | 编码 Agent，强调审批与沙箱 | 开源的编码 Agent + 服务端 |
| 项目规则文件 | AGENTS.md / CLAUDE.md / AGENTS.override.md | CLAUDE.md 与记忆层级 | AGENTS.md | AGENTS.md 与规则文件 |
| 系统提示改写 | SYSTEM.md 替换、APPEND_SYSTEM.md 追加 | 由配置与记忆机制承载 | 由配置与 AGENTS.md 承载 | 由配置与规则文件承载 |
| 扩展形式 | TypeScript 扩展 + 技能 + 模板 + 主题 | Hooks、子代理、斜杠命令 | MCP 与配置扩展 | 插件与自定义命令 |
| 技能体系 | 原生支持 Agent Skills 规范 | 技能与子代理组合 | 以 AGENTS.md 与 MCP 为主 | 以插件与命令为主 |
| MCP | 内置，支持 stdio / streamable HTTP 与 OAuth | 内置 MCP 集成 | 内置 MCP 集成 | 内置 MCP 集成 |
| 无界面模式 | print / JSON / RPC 三档 | `--print` 等非交互模式 | `codex exec` 等非交互模式 | `run` 与服务端 API |
| 程序化集成 | TypeScript SDK，进程内嵌 Pi | Agent SDK | SDK 与 CLI | HTTP 服务端 + `@opencode-ai/sdk` |
| 资源分发 | Pi 包（npm / git）+ `pi install` | 插件市场与配置 | 配置仓库 | 插件与 npm 包 |
| 长驻服务 | RPC 模式（JSONL over stdio） | 以 SDK 为主 | 以 CLI 为主 | 原生 server + attach |

```text
对比要点：
1. Pi 的差异点在「可定制成本」而非功能数量：扩展即 TS 模块，资源可打包分发
2. 规则文件生态正在收敛，AGENTS.md 是多家共同认的约定，Pi 同时兼容 CLAUDE.md
3. 无界面能力是集成分水岭：Pi 提供 print / JSON / RPC 三档且语义有明确定义
4. 需要长驻服务时，Pi 走 RPC（stdio JSONL），OpenCode 走 HTTP server，两者思路不同
5. 需要进程内集成时，Pi 的 SDK 与 Claude Code 的 Agent SDK 目标一致
6. 表格只作选型参考，工具演进快，落地前应以各自官方文档核对当前行为
```

## 应用场景实战

### 场景一：把 Pi 接进 CI 做结构化代码审查

目标：MR 流水线里跑一次审查，既要把结论贴到评论里，又要把过程事件存档以便复盘。做法是用 JSON 模式拿事件流，用一个包装脚本判断成败并提取最终文本。

```bash
#!/usr/bin/env bash
# ci-review.sh —— 在 CI 中对当前 diff 做审查并产出结论
set -euo pipefail

# 1) 凭据来自 CI secret，不写 auth.json
export ANTHROPIC_API_KEY="${CI_ANTHROPIC_KEY:?缺少 CI_ANTHROPIC_KEY}"

# 2) 无人值守：显式授权项目资源，避免信任提示被跳过
#    --no-session 让这次运行不污染会话目录
pi --approve --no-session --mode json \
   "审查 git diff --cached 的内容，输出 JSON：{risks:[], tests:[], verdict:'pass'|'fail'}" \
   > review-events.jsonl

# 3) 用 Python 从事件流里取权威消息（JSON 模式失败不会让退出码非零）
python3 - << 'PY'
import json, sys

final_text, errors = [], []
with open("review-events.jsonl", encoding="utf-8") as fh:
    for line in fh:
        line = line.strip()
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "message_end":
            msg = event.get("message", {})
            if msg.get("role") == "assistant":
                for block in msg.get("content", []):
                    if block.get("type") == "text":
                        final_text.append(block["text"])
                if msg.get("stopReason") in ("error", "aborted", "length"):
                    errors.append(msg.get("stopReason"))

if errors:
    print(f"审查未正常完成：{errors}", file=sys.stderr)
    sys.exit(1)

print("\n".join(final_text))
PY
```

```yaml
# .github/workflows/review.yml（节选）
name: pi-review
on: [pull_request]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - name: 安装 Pi
        run: npm install -g @earendil-works/pi-coding-agent

      - name: 运行审查
        env:
          CI_ANTHROPIC_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: ./ci-review.sh

      - name: 存档事件流
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: pi-review-events
          path: review-events.jsonl
```

需要注意 print 模式与 JSON 模式的退出码差异：如果这一步只关心「有没有拿到文本」，用 `--print` 更省事（非零退出码直接让 job 失败）；如果要在评论里展示过程，JSON 事件流配合上面的解析脚本更合适。

### 场景二：用 SDK 把 Pi 嵌入内部平台，并接内部工具（MCP）

内部发布平台想让工程师在网页上点一下就跑「升级依赖并验证」的流程，同时要调用公司内部的工单 MCP 服务器。做法是用 SDK 建会话、订阅事件推流到前端，并在 SDK 里显式加载 MCP 与 codemode 扩展。

```typescript
// platform/pi-service.ts
import {
  createAgentSession,
  SessionManager,
  DefaultResourceLoader,
  createCodemodeExtension,
  createMcpExtension,
} from "@earendil-works/pi-coding-agent";

export async function runUpgradeJob(repoDir: string, ticketId: string, onDelta: (t: string) => void) {
  // SDK 会话不加载内置扩展，需要自己把 codemode 与 MCP 装进资源加载器
  const resourceLoader = new DefaultResourceLoader({
    extensionFactories: [createCodemodeExtension(), createMcpExtension()],
    additionalExtensionPaths: ["builtin:tool-search"],
  });

  const { session } = await createAgentSession({
    cwd: repoDir,
    resourceLoader,
    sessionManager: SessionManager.inMemory(), // 平台自己管理持久化，不落本地会话文件
    tools: ["read", "bash", "edit", "write", "codemode", "tool_search"],
  });

  const unsubscribe = session.subscribe((event) => {
    if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
      onDelta(event.assistantMessageEvent.delta);
    }
  });

  try {
    // MCP 扩展在 session_start 时连接服务器，因此需要显式绑定扩展
    await session.bindExtensions();
    await session.prompt(
      `执行本次升级：把依赖升到最新兼容版本，运行测试，` +
        `完成后通过内部 MCP 工具把结果写回工单 ${ticketId}。` +
        `遇到需要人工确认的破坏性操作就停下来并说明原因。`,
    );
    return session.getLastAssistantText();
  } finally {
    unsubscribe();
    session.dispose(); // 中止活动工作并释放扩展资源
  }
}
```

## 最佳实践与踩坑记录

1. **CI 用环境变量，不要用 `auth.json`。** 环境变量不落盘、易轮换、能在 secret 管理里授权；`auth.json` 一旦进容器镜像或缓存就难以收回。需要临时取密钥时用 `auth.json` 的 `!command` 形式，而不是把明文写进去。

2. **凭据问题先跑 `pi auth check --provider X --json`。** 它给出 `ready` / `not_ready` / `invalid` 与稳定退出码（0/1/2），能把「没配凭据」和「模型目录过期」两类问题分开，省掉大量猜测。

3. **自动化显式声明信任决策。** print / JSON / RPC 无法弹信任提示，`defaultProjectTrust` 为 `"ask"` 或 `"never"` 时会静默跳过项目资源。CI 脚本里写 `--approve`，或把 `defaultProjectTrust` 设成明确值。

4. **自定义端点从最小配置开始。** 先用 `baseUrl` + `api` + `apiKey` + 一个模型打通，再逐项加 `modelOverrides`、`inputLimits`、`samplingParams`。兼容性开关要有验证依据再开——对方宣称兼容不等于请求字段真的支持。

5. **MCP 默认别给 `direct`。** 默认的 `codemode` 曝光让模型通过脚本发现工具，工具多时系统提示不会被塞爆；只把高频、小集合的工具给 `direct`，破坏性工具用 `hidden` 或 `toolExposure` 收紧。

6. **分享前审查会话。** 会话可能包含凭据、私有文件内容和内部命令输出。用 `sessionShareDestination` 明确分享目标，导出物按敏感数据处理，必要时只导出脱敏后的片段。

坑 1：本地 Ollama 模型在 `/model` 里看不到。
结论：兼容端点必须先在 `models.json` 声明，且该 provider 的凭据要能解析。
原因：自定义模型即使已经从 `models.json` 加载，只有 Pi 能解析到凭据时才会出现在 `/model`；对 llama.cpp，只有 router 当前已加载的模型才会出现。
解法：确认 `~/.pi/agent/models.json` 的 `providers.<id>.models` 里有该 `id`，并为它提供 `apiKey`（本地端点可写任意占位值）；打开 `/model` 会重新加载该文件。

坑 2：密钥在交互 shell 里可用，在 CI 或 systemd 服务里就失效。
结论：环境变量必须在启动 Pi 的那个进程环境里存在。
原因：环境变量不是 Pi 的持久化凭据，`auth.json` 才是；换了一个进程或不同的服务单元，环境就没有那两个变量。
解法：CI 在 step 的 `env` 里显式传递，服务用 `EnvironmentFile=` 或容器 env 注入；长期使用则 `/login` 写入 `auth.json`（并确保它不被提交）。

坑 3：CI 脚本用 `--mode json`，模型出错却被当成成功。
结论：JSON 模式下失败或中止的回复不会让退出码变非零。
原因：JSON 模式的设计是「暴露事件」，成败信息在事件里（`stopReason` 等），只有调用本身抛错才返回非零；这跟 print 模式的语义不同。
解法：解析事件流，检查 assistant 消息的 `stopReason` 是否为 `error` / `aborted` / `length`，自行决定退出码；只需要成败判断时改用 print 模式。

坑 4：把半径不明的第三方 MCP 服务器加了 `direct` 曝光。
结论：工具被直接声明给模型，等于把能力面完全展开，也放大了提示注入的风险。
原因：`direct` 会把服务器工具像内置工具一样写进模型可见的工具声明；MCP 服务器返回的内容可以反过来影响模型行为。
解法：默认保留 `codemode` 或先给 `deferred`，只对少量高频只读工具用 `toolExposure` 开 `direct`；写操作与删除类工具设 `hidden`；必要时用 `--no-mcp` 或 `-builtin:mcp` 整体关掉。

坑 5：把 `/share` 的链接直接贴进公开频道。
结论：会话内容可能包含内部代码、命令输出与凭据。
原因：`/share` 上传整份会话（默认 Radius artifact 或私有 GitHub gist），可见范围由目标服务决定；共享的是完整记录而不是摘要。
解法：分享前通读会话，必要时只导出片段；用 `sessionShareDestination` 固定目标并在团队内约定分享流程；把「会话审查」写进发布检查清单。
