## 概述

前几篇讲的是「怎么把模型训好」，本篇讲**怎么让模型在线上稳定地活着**：标注数据怎么质检、实验怎么复现、模型怎么部署、批量与缓存怎么省成本、线上怎么发现掉点。这些环节的共同特点是——它们不提升离线指标，但决定了项目能不能持续迭代；而且出问题的形式往往是「指标没掉但业务坏了」或者「指标掉了但查不出原因」。

本机实测环境：Python 3.14.7、scikit-learn 1.9.1、jieba 0.42.1、numpy 2.5.4、joblib 1.6.0、scipy 1.18.1；推理服务用标准库 `http.server` 搭建（无第三方 Web 框架依赖），所有延迟数字都是本机 CPU 真实测量。

```text
本篇主线：
1. 数据标注与质检 —— 三人标注 kappa 0.8355~0.8889，多数投票 0.9933；抽检 100 条算出分歧率 7% 的置信区间
2. 训练流水线与可复现性 —— 同 seed 完全一致，样本顺序不同就差 0.0067，环境指纹要一起存
3. 训练与推理部署 —— 常驻模型 p50 0.908ms，每条请求重新加载 2.228ms（慢 2.5 倍）
4. 批量推理与缓存 —— 批量 32 提速 20.2 倍；LRU 缓存在 Zipf 流量上命中 0.9760
5. 监控与漂移 —— 同分布流量 PSI 0.0399，脏数据流量 PSI 2.3488
6. 常见坑 —— 推理侧截断前后差 15.5 个点，但整体指标「看起来只掉了 0.5 个点」
```

## 数据标注与质检

标注是 NLP 项目里最贵的一环，质检的目标是用最小成本估计「这批标注的错误率」以及「问题集中在哪」。三个必备动作：**规范先写**（边界与类型判定规则，附正反例）、**多人标注重叠**（通常 10%-30% 的样本双标）、**一致性指标**（Cohen kappa / Krippendorff alpha / 实体级 F1）。

Cohen kappa 的定义是 `κ = (p_o - p_e) / (1 - p_e)`，`p_o` 是实际一致率，`p_e` 是随机猜测的期望一致率（`sklearn.metrics.cohen_kappa_score` 的官方文档：https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html）。用 kappa 而不是一致率，是因为类别不均衡时一致率会虚高。本机用 300 条 4 类样本、3 名不同水平的标注员（错误率 4%/7%/12%）实测：

```python
import numpy as np
from sklearn.metrics import accuracy_score, cohen_kappa_score

truth = np.array([random.randint(0, 3) for _ in range(300)])       # 金标准
anno = {}                                                          # 三名标注员的标注
for name, err, hs in (("A", 0.04, 11), ("B", 0.07, 22), ("C", 0.12, 33)):
    lab = truth.copy()
    flip = np.random.RandomState(hs).rand(len(truth)) < err        # 固定随机种子，结果可复现
    lab[flip] = np.random.RandomState(hs + 1).randint(0, 4, flip.sum())
    anno[name] = lab

print("准确率:", {k: round(accuracy_score(truth, v), 4) for k, v in anno.items()})
print("kappa:", {("%s-%s" % (a, b)): round(cohen_kappa_score(anno[a], anno[b]), 4)
                 for a, b in (("A", "B"), ("A", "C"), ("B", "C"))})
votes = np.stack([anno["A"], anno["B"], anno["C"]])
majority = np.array([np.bincount(votes[:, i], minlength=4).argmax() for i in range(votes.shape[1])])
print("多数投票 vs 金标准:", round(accuracy_score(truth, majority), 4))
```

```text
== 标注质检：3 名标注员 + 100 条重复抽检
  标注员与金标准的准确率: A 0.9700，B 0.9367，C 0.9400
  两两 Cohen kappa: A-B 0.8889，A-C 0.8845，B-C 0.8355
  三取二多数投票 vs 金标准 acc 0.9933（单人最高 0.9700）
  抽检 100 条重复题（占 33.3%），发现 A/B 分歧 7 条，分歧率 0.0700（95% Wilson 区间 0.0343 ~ 0.1375）
  若真想卡「错误率 < 2%」：按二项抽样，抽检 80 条才有 80% 把握至少抓到一条错误（1-0.98^n）
```

四点可直接照搬的经验：**多数投票几乎免费提点**（0.9700 -> 0.9933，但代价是 3 倍标注量，只对核心集划算）；**kappa 0.8355 与准确率 0.9367 是两个不同信息**——kappa 排除了「蒙对」的成分，用来横向比较标注员比准确率更公平；**抽检 100 条发现 7 条分歧，置信区间宽到 3.4%-13.8%**，说明小样本抽检只能做「发现严重问题」而不是「验收精确错误率」；**要验收「错误率 < 2%」至少抽 80 条**（在错误率真为 2% 时有 80% 概率至少抓到一条），真实项目通常按「抽 200-300 条」设计质检批次。

```text
要点：
- 规范先行并附正反例；边界歧义（人名是否含称谓、机构是否含地名前缀）是最主要的分歧来源
- 用 kappa 而不是一致率评估一致性：类别不均衡时一致率会虚高
- 多数投票能显著提点（本机 0.9700 -> 0.9933），但只在核心集上做，成本是标注量翻倍
- 小样本抽检只能发现严重问题；要验收具体错误率，先按二项分布算样本量（本机需 >= 80 条才能有 80% 把握抓到 2% 错误）
- 分歧样本必须回看：一半是标注规范没写清，一半是模型标注与人工标注都对的「多标签真值」
- 标注工具的随机抽检比例、返工记录、标注员维度统计要能导出，否则质检无法闭环
```

## 训练流水线与可复现性

「训练不可复现」是迭代效率的最大隐形杀手：同一个脚本两次跑出不同数字，于是无法判断改动是否有效。可复现需要固定四类东西：**数据**（版本 + 顺序）、**随机性**（各类 seed）、**环境**（依赖版本 + 硬件）、**代码**（git 提交号）。本机实测这几项各自的影响：

```python
import hashlib, numpy as np
from sklearn.linear_model import LogisticRegression
from sklearn.neural_network import MLPClassifier

def run_once(seed, shuffle=True):
    r = np.random.RandomState(seed)
    X, y = Xtr.copy(), ytr.copy()
    if shuffle:                                   # 样本顺序是一个独立的随机源
        idx = r.permutation(len(y)); X, y = X[idx], y[idx]
    m = LogisticRegression(max_iter=300, random_state=seed).fit(X, y)
    return accuracy_score(yte, m.predict(Xte_clean))

print("同一 seed 两次:", run_once(0), run_once(0))
print("换 seed:", run_once(1))

fprint = "python %s | numpy %s | sklearn %s | train_md5 %s" % (
    sys.version.split()[0], np.__version__, __import__("sklearn").__version__,
    hashlib.md5("".join(Xtr_txt).encode()).hexdigest()[:12])
print("环境指纹:", fprint)
```

```text
== 3. 可复现性：种子 / 顺序 / 版本
  同一 seed 跑两次: 0.740000 vs 0.740000（差 0.00e+00）
  换 seed:         0.740000（与 seed=0 差 0.000000）
  MLP 样本顺序打乱 vs 不打乱: 0.7433 vs 0.7367（差 0.0067，说明记录「数据顺序」和记录 seed 一样重要）
  环境指纹: python 3.14.7, numpy 2.5.4, sklearn 1.9.1, 训练集 md5 c666eab7ed5c
```

`LogisticRegression` 在这个数据上对 seed 不敏感（0.74 完全一致），但把 MLP 的训练样本顺序打乱，同一 seed 下结果差了 0.0067——**顺序是独立的随机源，只固定 seed 不够**。工程做法是把「数据顺序」也固化：用固定 seed 的 shuffle 生成索引并落盘，或者干脆按稳定键（id）排序。环境指纹（Python/库版本 + 训练集哈希）要写进实验记录，否则「上周还能复现的脚本今天跑不出来了」只能靠猜。

```text
要点：
- 四类随机源：Python/numpy/框架 seed、数据顺序、数据切分、模型的初始化；漏一个就不可复现
- 数据顺序的影响量与超参相当（本机 0.0067），shuffle 索引要落盘或按稳定键排序
- 环境指纹（python/numpy/sklearn 版本 + 训练集 md5 + 硬件）与模型一起存档
- 每次实验只改一个变量，配置用文件（yaml/json）管理并进 git，不要靠命令行记忆
- 训练脚本要能「一条命令复现」：数据路径、配置、seed 都从配置文件读，写死路径的脚本三个月后就跑不动了
- 把「复现自检」做成 CI 任务：用同配置跑两次，断言指标完全一致
```

## 训练与推理部署

部署的最小可用形态是「模型常驻内存 + 一个 HTTP 接口」。三件事决定线上质量与成本：**进程模型**（常驻 vs 每条请求重新加载）、**批处理**（单条 vs 批量）、**预处理一致性**（训练与推理必须是同一套清洗逻辑）。本机用标准库 `http.server` 搭了一个最小的意图分类服务（模型 `joblib` 落盘 21.0 KB）：

```python
import json, time, joblib, socket, threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

joblib.dump((vec, clf), "s169_model.joblib")        # 向量器与模型一起存盘，避免加载错配
serve_model = joblib.load("s169_model.joblib")

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        n = int(self.headers.get("Content-Length", 0))
        body = json.loads(self.rfile.read(n) or b"{}")
        t0 = time.perf_counter()
        pred = serve_model[1].predict(serve_model[0].transform(body.get("texts", [])))
        ms = (time.perf_counter() - t0) * 1000
        payload = json.dumps({"labels": pred.tolist(), "infer_ms": round(ms, 4)}).encode()
        self.send_response(200); self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(payload))); self.end_headers()
        self.wfile.write(payload)

srv = ThreadingHTTPServer(("127.0.0.1", 0), Handler)         # 端口 0 = 让内核分配空闲端口
threading.Thread(target=srv.serve_forever, daemon=True).start()
```

```text
== 4. 模型落盘与加载
  模型文件 21.0 KB；冷启动一次性加载耗时 2.04 ms
  常驻模型 逐条推理: p50 0.908 ms, p95 1.045 ms, 200 条总耗时 173.4 ms
  常驻模型 批量(32)推理: 200 条总耗时 8.6 ms，单条均摊 0.043 ms（提速 20.2x）
  每条请求都重新 joblib.load: p50 2.228 ms（比常驻慢 2.5x）

== 6. 本地 HTTP 服务（stdlib http.server + joblib 常驻模型）
  单条       端到端 p50 1.53 ms  p95 3.50 ms  服务端推理 p50 0.71 ms  (n=30)
  批量 16    端到端 p50 1.86 ms  p95 2.86 ms  服务端推理 p50 0.89 ms  (n=10)
  批量 128   端到端 p50 4.25 ms  p95 4.52 ms  服务端推理 p50 3.54 ms  (n=10)
```

**常驻 vs 每条重载差 2.5 倍**，而端到端延迟里 HTTP 开销（约 0.8ms）比推理本身（0.71ms）还大——这提示两件事：小模型上「优化模型」的收益不如「优化服务链路」（连接复用、序列化、批处理）；而**批量是数量级收益**（20.2 倍）。生产环境用 `uvicorn + FastAPI` 或 `gunicorn` 多 worker 时，要点是 worker 数与 CPU 核数匹配、模型在每个 worker 内初始化一次（不要在请求处理里加载）。

```text
要点：
- 模型在进程启动时加载一次并常驻；每条请求重新 load 会让 p50 从 0.908ms 涨到 2.228ms
- 端到端延迟 = HTTP/序列化 + 预处理 + 推理；小模型上服务链路开销常常大于推理本身
- 批量推理是数量级收益（批量 32 提速 20.2 倍）；接口设计要允许一次传多条文本
- 向量器/分词器与模型一起存盘、一起加载，避免版本错配（joblib/pickle 只保证同一环境可加载）
- 多 worker 部署时核对 worker 数 <= 可用核数，并确认每个 worker 只加载一次模型（注意内存成倍增长）
- 有 GPU 时再考虑显存共享与动态批处理；本机 CPU 环境不涉及
```

## 批量推理与缓存

线上流量有两个可利用的规律：**成批到达**（一次请求里多篇文档）和**高度重复**（同一句问题被问很多次）。前者用批处理解决，后者用缓存解决。

缓存要处理三个工程细节：**key 归一化**（大小写、空白、全半角必须归一，否则命中率虚低）、**容量与淘汰**（LRU 在 Zipf 分布的流量上表现最好）、**版本隔离**（key 里必须包含模型版本与预处理版本，否则换模型后命中旧结果）。本机用 50 种 query、Zipf 分布生成 2000 次请求测缓存效果：

```python
class LRUCache:
    def __init__(self, cap=256):
        self.cap, self.d, self.hit, self.miss = cap, {}, 0, 0
    def get_or_compute(self, key, fn):
        if key in self.d:
            self.hit += 1
            return self.d[key]
        self.miss += 1
        v = fn()
        if len(self.d) >= self.cap:
            self.d.pop(next(iter(self.d)))        # 简化版：按插入顺序淘汰最老的一条
        self.d[key] = v
        return v

weights = np.array([1.0 / (i + 1) for i in range(50)]); weights /= weights.sum()
traffic = np.random.RandomState(1).choice(base50, 2000, p=weights)   # Zipf 流量：头部 query 占大头
cache = LRUCache(256)
for q in traffic:
    cache.get_or_compute(q, lambda q=q: predict_single([q]))         # key 必须是归一化后的文本 + 模型版本
print("命中率 %.4f（命中 %d / 未命中 %d）" % (cache.hit / (cache.hit + cache.miss), cache.hit, cache.miss))
```

```text
== 5. 推理缓存（LRU 256，Zipf 流量 2000 请求 / 50 种 query）
  命中率 0.9760（命中 1952 / 未命中 48），p50 0.001 ms，p95 0.001 ms
  不做缓存的 p50 是 0.908 ms（缓存把平均延迟压到 0.001 ms，但注意缓存 key 必须包含模型版本）
```

命中率 0.9760 是「50 种 query + Zipf 分布 + 容量 256」的理想情况；真实流量的尾部更长，命中率通常落在 0.4-0.8。三个必须守住的原则：缓存 key 用归一化后的文本 + 模型版本（换模型必须换 key 或清缓存）；缓存只缓存**幂等的纯函数结果**（分类、抽取、检索可以缓存；带随机采样的生成要谨慎）；给缓存加命中率与陈旧率监控，命中率突然上升/下降都是信号。

```text
要点：
- 批量推理是数量级收益（本机 20.2 倍）；把「一次多条」做成接口能力而不是调用方自行循环
- 缓存 key 必须归一化（大小写/空白/全半角）+ 带模型与预处理版本号
- LRU + 合理容量（按工作集大小设，本机 256 >= 50 种 query）在 Zipf 流量上命中率 0.9760
- 只缓存幂等纯函数的结果；带随机采样的生成结果缓存会让输出「冻住」，要按业务决定
- 监控缓存命中率、陈旧率与内存占用；命中率的突变往往对应上游输入分布变化
- 动态批处理（等一小段时间凑批）能把延迟换吞吐，实时性要求高的场景要设超时上限
```

## 线上监控与漂移检测

线上掉点有两种形态：**指标型**（有真值回传，直接算准确率/F1）与**无真值型**（没有实时标注，只能看输入/输出分布）。后者靠分布漂移检测：输入侧看文本长度、关键词命中率、字符集分布；输出侧看预测类别分布与置信度分布。两个常用指标：**PSI**（Population Stability Index，经验阈值 <0.1 稳定、0.1-0.25 观察、>0.25 重训）与 **KS 检验**（两样本分布是否同源，看 p 值）。

```python
import numpy as np
from scipy.stats import ks_2samp

def psi(a, b, bins=10):
    edges = np.quantile(a, np.linspace(0, 1, bins + 1))       # 按基线分位切桶
    edges[0], edges[-1] = -np.inf, np.inf
    pa = np.histogram(a, edges)[0] / len(a) + 1e-6            # 加极小量避免除零/取对数出 inf
    pb = np.histogram(b, edges)[0] / len(b) + 1e-6
    return float(np.sum((pb - pa) * np.log(pb / pa)))

base_scores = clf.predict_proba(Xtr)[:, 1]                    # 基线（训练分布）的正类分数
for name, s in (("同分布流量", clf.predict_proba(Xte_clean)[:, 1]),
                ("脏数据流量", clf.predict_proba(Xte_dirty)[:, 1])):
    ks, p = ks_2samp(base_scores, s)
    print("%-12s PSI %.4f  KS %.4f (p=%.2e)  均值 %.4f -> %.4f"
          % (name, psi(base_scores, s), ks, p, base_scores.mean(), s.mean()))
```

```text
== 7. 上线监控：预测分数分布漂移（PSI / KS）
  同分布流量(清洗一致)            PSI 0.0399  KS 0.0496 (p=1.85e-01)  均值 0.2534 -> 0.2450
  脏数据流量(未清洗)             PSI 2.3488  KS 0.4083 (p=2.55e-72)  均值 0.2534 -> 0.2299
  判定口径（经验值）: PSI<0.1 稳定，0.1~0.25 需观察，>0.25 建议重训；KS p<0.05 提示分布变了
```

注意这里最有价值的对比是**均值几乎没变**（0.2534 -> 0.2299）而 PSI 高达 2.3488：只看预测均值或整体准确率会漏掉「分布在变形」的事实。所以监控面板要把「分布形状指标（PSI/KS）」与「业务指标（人工采纳率、申诉率、平均处理时长）」并排放，前者负责早期预警，后者负责确认影响。

```text
要点：
- 无真值场景靠输入/输出分布漂移（PSI、KS）预警；PSI<0.1 稳、0.1-0.25 观察、>0.25 重训
- 不要只看均值：本机脏数据流量均值只差 0.0235，而 PSI 2.3488（分布形状已大变）
- 输入侧监控文本长度、OOV/未登录词比例、特殊字符比例；输出侧监控类别分布与置信度
- 漂移告警要能定位到「哪一类、哪一段文本」，否则只有告警没有行动
- 有真值回传时（人工复核结果）把真值指标也接进面板，错峰评估（如 T+1 天）
- 告警阈值按业务定，并在上线前用历史流量回放验证「不误报、不漏报」
```

## 常见坑与规避

预处理不一致是 NLP 服务里最常见、最难查的一类事故：模型没变、代码没动，只是**推理侧的清洗逻辑和训练侧不一样**（少过滤了停用词、多了截断、tokenizer 配置不同），指标就静默掉点。本机用一个「推理侧截断到前 6 字符」的模拟实验演示它有多隐蔽：

```python
TRUNC = 6
def clean(s):                                  # 训练与推理都该走的清洗
    return re.sub(r"\s+", " ", s.replace("\u3000", " ")).strip()
def buggy_clean(s):
    return clean(s)[:TRUNC]                     # 线上某次「性能优化」加了截断，训练侧没有

Xte_clean = vec.transform([clean(s) for s in Xte_txt])         # 与训练一致
Xte_dirty = vec.transform([buggy_clean(s) for s in Xte_txt])   # 推理侧被截断
print("acc %.4f -> %.4f" % (accuracy_score(yte, clf.predict(Xte_clean)),
                            accuracy_score(yte, clf.predict(Xte_dirty))))
info = ~te_amb                                  # 只看措辞明确的样本（不受 35% 含糊样本稀释）
print("只看措辞明确的 %d 条: %.4f -> %.4f" % (info.sum(),
      accuracy_score(yte[info], clf.predict(vec.transform([clean(s) for s in np.array(Xte_txt)[info]]))),
      accuracy_score(yte[info], clf.predict(vec.transform([buggy_clean(s) for s in np.array(Xte_txt)[info]])))))
```

```text
== 1. 预处理一致性（同一个模型，两种推理路径）
  与训练一致的清洗: acc 0.7400；推理侧截断到前 6 字符: acc 0.5850；差距 0.1550
  每条样本命中的特征数：清洗后 25.64，截断后 12.59（少 50.9%）
  截断长度 TRUNC=6；训练集最长样本 20 字
  分意图 recall（清洗一致 -> 截断）: 查订单 0.7383 -> 0.6711，退款 0.7554 -> 0.3525，投诉 0.7413 -> 0.5175，咨询 0.7278 -> 0.7574
  只看措辞明确的 394 条: 清洗一致 acc 1.0000 -> 截断后 acc 0.7538（整体 acc 只差 0.1550，把问题掩盖了）
```

三点结论值得记在工程手册里：**整体指标会掩盖局部崩塌**——「退款」意图的 recall 从 0.7554 掉到 0.3525（一半以上），但整体 acc「只」掉 15.5 个点，因为含糊样本稀释了差异；**在信息量充足的样本上看** 从 1.0000 掉到 0.7538，问题立刻显形；**特征命中数（25.64 -> 12.59）是最灵敏的探针**，比准确率更早报警，适合做线上监控指标。

```text
要点：
- 训练与推理必须共用同一份预处理代码（模块级函数 + 单测），禁止在服务里重写一遍清洗
- 整体指标会掩盖局部崩塌（本机退款类 recall 掉一半，整体只掉 15.5 个点），必须分类型监控
- 「特征命中数/平均 token 数」是最灵敏的线上探针，能比准确率更早发现预处理不一致
- 截断、停用词、大小写、全半角、tokenizer 配置、padding 策略都是不一致的来源，逐项做对照测试
- 发版前跑「金丝雀流量 + 双跑对比」（新旧预处理各算一遍，比对不一致率），别等用户投诉
- 把模型、向量器、预处理版本打成一个 artifact 一起发布，禁止单独升级其中一部分
```

## 应用场景实战

### 场景一：意图分类服务上线与容量估算

业务背景：把前几篇训好的意图分类模型部署成内部服务，QPS 峰值 200，平均每篇文本 20 字，需要给出 CPU 核数估算与缓存策略，并提供发版前的验收流程。

```python
import json, statistics, time
from urllib.request import urlopen, Request

def bench(port, texts, n=30):
    lat = []
    for _ in range(n):
        body = json.dumps({"texts": texts}).encode()
        t0 = time.perf_counter()
        with urlopen(Request("http://127.0.0.1:%d/predict" % port, data=body,
                             headers={"Content-Type": "application/json"}), timeout=10) as r:
            resp = json.loads(r.read())
        lat.append((time.perf_counter() - t0) * 1000)
    return statistics.median(lat), sorted(lat)[int(0.95 * len(lat))], resp["infer_ms"]

for name, texts in (("单条", [QUERIES[0]]), ("批量 16", QUERIES[:16]), ("批量 128", QUERIES[:128])):
    p50, p95, infer = bench(port, texts, 30 if name == "单条" else 10)
    print("%-8s 端到端 p50 %.2f ms  p95 %.2f ms  服务端推理 p50 %.2f ms" % (name, p50, p95, infer))
```

```text
本机输出：
单条       端到端 p50 1.53 ms  p95 3.50 ms  服务端推理 p50 0.71 ms  (n=30)
批量 16    端到端 p50 1.86 ms  p95 2.86 ms  服务端推理 p50 0.89 ms  (n=10)
批量 128   端到端 p50 4.25 ms  p95 4.52 ms  服务端推理 p50 3.54 ms  (n=10)

容量估算（按本机单条 p95 3.50 ms、每请求 1 条文本）：
  单 worker 理论上限 ~285 QPS；压到 60% 水位留余量 -> ~170 QPS/worker
  目标 200 QPS -> 2 个 worker（或 4 worker 跑 50% 水位更稳）
  若客户端支持批量 16 条/请求，同样 QPS 下请求数降到 1/16，HTTP 开销大幅摊薄
  注：本机多次测量单条 p95 在 1.4 ~ 3.5 ms 之间波动（线程调度与循环导入的影响），
      容量估算必须用「多轮测量的最大 p95 + 水位」，不要用最好的一次
```

容量估算的规矩是**按 p95 而不是 p50 排容量**，并留 40% 左右水位给流量尖峰与 GC；批量接口把「每请求一条」变成「每请求多条」，在同样 QPS 下请求数下降一个数量级，是最省资源的优化。上线验收清单：金丝雀 5% 流量跑 30 分钟 -> 比对新旧模型的不一致率与延迟分位 -> 无异常再全量。

```text
场景一要点：
1. 容量按 p95 排（本机单条 p95 3.50 ms -> 单 worker 理论 ~285 QPS，60% 水位取 ~170）
2. 优先做批量接口而不是加机器：批量 16 让请求数降到 1/16，HTTP 开销被摊薄
3. 发版走金丝雀：5% 流量跑 30 分钟，比对不一致率、p95 延迟、错误率
4. 服务要暴露 /health 与 /metrics（QPS、p50/p95、缓存命中率、平均 token 数）
5. 模型与预处理版本号写进响应头与日志，出问题能立刻定位到是哪个版本
```

### 场景二：发版回归门禁与漂移告警联动

业务背景：模型每周迭代一次，需要一套「发版前拦截 + 上线后监控」的闭环：发版前用黄金集比对新旧模型，线上用 PSI/KS 监控分布，任一环节触发就回滚。

```python
import numpy as np
from sklearn.metrics import accuracy_score, f1_score

def gate(v_old, v_new, gold_txt, gold_y, max_f1_drop=0.005):
    p_old = v_old.predict(vec.transform([clean(s) for s in gold_txt]))
    p_new = v_new.predict(vec.transform([clean(s) for s in gold_txt]))
    f_old, f_new = f1_score(gold_y, p_old, average="macro"), f1_score(gold_y, p_new, average="macro")
    flip = (p_old != p_new)
    report = {"acc_old": round(accuracy_score(gold_y, p_old), 4),
              "acc_new": round(accuracy_score(gold_y, p_new), 4),
              "macroF1_old": round(f_old, 4), "macroF1_new": round(f_new, 4),
              "flip": int(flip.sum()),
              "new_right_old_wrong": int(((p_new == gold_y) & (p_old != gold_y)).sum()),
              "old_right_new_wrong": int(((p_old == gold_y) & (p_new != gold_y)).sum()),
              "pass": bool(f_new >= f_old - max_f1_drop)}
    return report

print(gate(v1, v2, gold_txt, gold_y))
```

```text
本机输出（黄金集 300 条人工核对样本）：
  v1(当前线上)     acc 0.7067  macroF1 0.7048
  v2(待发布)      acc 0.7067  macroF1 0.7043
  两版预测不一致 9/300 条；其中新版对、旧版错 1 条，旧版对新版错 1 条
  门禁判定: macroF1 差 0.0005 < 阈值 0.005 -> 放行；同时记录「9 条翻转样本」供人工抽查
```

门禁的价值在于**同时给出「放不放行」和「为什么」**：macroF1 差 0.0005 远小于 0.005 的阈值，可以放行；但 9 条翻转样本说明两版行为确有差异，抽查这 9 条能确认差异都落在模糊样本上（而不是漏了某个业务子类）。上线后的漂移告警则是同一逻辑的在线版本：PSI 超 0.25 或 KS 的 p 值 < 0.05 就触发「重训评估」而不是直接重训——**先看是模型问题还是数据问题**（比如线上混入了没清洗的数据）。

```text
场景二要点：
1. 发版门禁用固定黄金集 + 明确阈值（本机 macroF1 允许下降不超过 0.005），并把判定结果落库
2. 除了聚合指标，还要报「翻转样本数」与「谁对谁错」，这是抽查定位的输入
3. 线上漂移告警触发的是「评估流程」而不是自动重训：先判断是数据问题还是模型问题
4. 回滚要能在分钟级完成：模型 artifact 版本化，回滚 = 切换版本号 + 重启 worker
5. 把「黄金集回归 + 漂移告警 + 回滚预案」写成一页运维手册，值班同学按图执行
```

## 最佳实践与踩坑记录

最佳实践：

1. 标注质检用 kappa + 抽检样本量计算，别用「感觉差不多」验收；分歧样本回看是规范迭代的主要输入。
2. 固定四类随机源并保存环境指纹（版本 + 数据 md5 + 硬件），训练脚本要能一条命令复现。
3. 模型在进程启动时加载并常驻；向量器/分词器与模型打包成一个 artifact，禁止单独升级。
4. 接口支持批量（本机批量 32 提速 20.2 倍），缓存 key 带版本号并做文本归一化。
5. 监控面板同时放「分布漂移（PSI/KS）」与「业务指标（采纳率/申诉率）」，前者预警、后者确认。
6. 发版走「黄金集门禁 + 金丝雀 + 分钟级回滚」三件套，判定结果与翻转样本都落库。

坑 1：训练与推理的预处理不一致（推理侧多了截断）。

结论：同一个模型，训练一致的清洗 acc 0.7400，推理侧截断到 6 字符后 0.5850；「退款」类 recall 从 0.7554 掉到 0.3525，而整体只掉 0.1550。
原因：服务里重写了清洗逻辑并「顺手」加了截断，特征命中数从 25.64 掉到 12.59，模型输入分布与训练不一致。
解法：预处理做成模块级函数（训练与推理共用）+ 单元测试；线上监控「平均命中特征数/平均 token 数」这类灵敏探针；发版做双跑不一致率对比。

坑 2：只固定随机种子，不固定数据顺序。

结论：同一 seed 下把 MLP 训练样本顺序打乱，指标从 0.7367 变到 0.7433（差 0.0067），与一次超参调优的收益同量级。
原因：样本顺序（shuffle 的随机源）与模型初始化是两个独立随机源，只固定后者不够。
解法：shuffle 索引用固定 seed 生成并落盘，或按稳定键排序；实验记录里同时记录 seed 与数据顺序版本。

坑 3：每条请求重新加载模型（或在请求里 `joblib.load`）。

结论：常驻模型 p50 0.908 ms，每条请求重新 `joblib.load` 后 p50 2.228 ms（慢 2.5 倍），并发一上来直接雪崩。
原因：磁盘 IO + 反序列化被算进了每次请求的延迟里，而且没有连接/对象复用。
解法：模型在进程启动时加载一次；多 worker 部署时确认每个 worker 只加载一次，并把 worker 数控制在核数以内。

坑 4：缓存 key 不做归一化、不带模型版本。

结论：key 用原始文本时，「你好」与「你好」（尾部空格）会算两次未命中，命中率虚低；换模型后不清缓存会命中旧结果，看起来「新模型没生效」。
原因：缓存是按字符串精确匹配的，任何非语义差异都会分裂 key；模型版本变化后旧结果仍满足 key。
解法：key = 归一化文本 + 模型/预处理版本号；换模型时带新版本号自然隔离；监控命中率与陈旧率。

坑 5：只看聚合指标，漏掉分类型崩塌。

结论：整体 acc 只掉 0.1550，但退款类 recall 掉了一半（0.7554 -> 0.3525）；在信息量充足的样本上评估 从 1.0000 掉到 0.7538。
原因：含糊样本（无类别信息）稀释了指标差异，聚合指标对局部崩塌不敏感。
解法：监控与评估都按类别/业务线拆分；上线前用「信息量充足的子集」做一次严口径评估，两个口径都留档。
