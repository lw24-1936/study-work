## 概述

Skill 的目录结构只有一条硬约束：必须有 `SKILL.md`，且它的 `name` 等于目录名；其余文件与子目录随便放。约定俗成的三类子目录分别是 `references/`（给人读的补充文档）、`scripts/`（给机器执行的代码）、`assets/`（模板、样例数据等静态资源），它们对应渐进式披露的第三级——**在被读到或被执行前不占任何上下文**。目录设计的目标只有一个：让 Agent 用最短的路径找到当前任务需要的那一小块内容。

```text
全篇主线：
1. 布局 —— 必需 SKILL.md，可选 references / scripts / assets，其余按需
2. 引用 —— references 只放一层，SKILL.md 直达每个文件，超过 100 行加目录
3. 代码 —— scripts 讲清「执行」还是「当参考读」，assets 放模板与样例数据
4. 拆分 —— 500 行是分界线，正文留路由与判定，细节外移
5. 复用 —— 命名与版本统一规则，同一份目录跨工具复用而不复制
```

## 标准目录布局

规范给出的最小结构就是「目录 + `SKILL.md`」，官方推荐的三类可选目录对应三种内容形态：文档、代码、资源。除此之外「任意文件与目录」都是允许的，但每引入一个非约定目录，就等于给 Agent 增加一次猜测——它不知道该不该读、什么时候读。所以非约定目录要么在 `SKILL.md` 里明确写出用途（例如 `data/` 里放样例输入），要么干脆别建。

```text
csv-report/
├── SKILL.md                  # 必需：frontmatter + 流程
├── references/               # 可选：给人读的补充文档
│   └── SCHEMA.md
├── scripts/                  # 可选：给机器执行的代码
│   ├── build_plan.py
│   ├── validate_plan.py
│   └── apply_plan.py
├── assets/                   # 可选：模板、样例数据等静态资源
│   └── report-template.md
├── data/                     # 非约定目录：启用时必须在 SKILL.md 里写明用途
│   ├── orders.csv
│   └── changes.csv
└── .gitignore                # 运行时产物不入库
```

各目录的职责与加载方式：

| 目录 | 内容 | 谁读它 | 加载方式 | 上下文成本 |
|------|------|--------|----------|------------|
| （根）`SKILL.md` | frontmatter + 流程与判定 | Agent | 触发时整读 | 每轮触发都计费 |
| `references/` | 详细规范、字段表、FAQ、判例 | Agent 按需 | 被引用到时才读 | 读到才计费 |
| `scripts/` | 可执行脚本（Python/Shell 等） | 由 Agent 执行 | 只回 stdout/stderr | 代码不进上下文 |
| `assets/` | 输出模板、样例、字体、图片 | Agent 或脚本 | 被引用到或被脚本读取时 | 读到才计费 |

目录骨架可以用两条命令核对，不需要额外的工具链：

```shell
# 只列文件（排除运行时产物），确认骨架与预期一致
find skills/csv-report -type f -not -path '*/.git/*' | sort

# 版本库视角：确认没有把数据库、临时计划文件提交进去
cd skills-repo && git ls-files csv-report
```

```text
csv-report/.gitignore

csv-report/assets/report-template.md
csv-report/data/changes.csv
csv-report/data/changes_bad.csv
csv-report/data/orders.csv

csv-report/scripts/apply_plan.py
csv-report/scripts/build_plan.py
csv-report/scripts/validate_plan.py
```

```text
标准布局要点：
1. SKILL.md 是唯一必需文件；目录名必须等于 frontmatter 的 name
2. 三类约定目录的划分依据是「内容形态」：文档进 references、代码进 scripts、静态资源进 assets
3. 非约定目录（data/、examples/）允许存在，但必须在 SKILL.md 里说明用途与用法
4. 运行时产物（数据库、缓存、临时计划文件）用 .gitignore 排除，别让它们进版本库和分发包
5. 目录结构本身就是给 Agent 的路标：层级越浅、名字越具体，被正确使用的概率越高
```

## references 目录与渐进式披露

`references/` 是渐进式披露的主要落点：把「只在某些子场景才需要」的内容外移，正文只留路由。两条硬经验值来自官方最佳实践：**引用层级只保留一层**（每个参考文件都直接从 `SKILL.md` 链到，不要 `SKILL.md -> A.md -> B.md`），以及**超过 100 行的参考文件在顶部加一个目录**。前者是因为 Agent 读嵌套文件时倾向于只读前若干行（`head -100` 一类），导致信息不完整；后者是因为它可能只预览开头，有目录才能让它知道全文有什么。

```text
csv-report/
├── SKILL.md                       # 只写「什么时候读哪个文件」
└── references/
    ├── SCHEMA.md                  # 字段定义与取值域
    ├── FAQ.md                     # 业务方常问
    └── TROUBLESHOOTING.md         # 校验失败怎么修
```

```markdown
<!-- SKILL.md 里的路由写法：每个参考文件都从 SKILL.md 直达 -->
字段定义见 [references/SCHEMA.md](references/SCHEMA.md)。
校验报错的处理办法见 [references/TROUBLESHOOTING.md](references/TROUBLESHOOTING.md)。
```

引用链路能机械检查出来。下面这个脚本把「SKILL.md 直引的文件」「references/ 下没被直引的文件」「references 之间的嵌套引用」全部列出来，本机实测输出如下：

```python
#!/usr/bin/env python3
"""检查 Skill 的引用深度：SKILL.md 直引的文件、references/ 下未被直引的文件、以及 references 之间的嵌套引用。

用法：python3 ref_depth.py <skills 目录>
退出码：0 无错误，1 存在死链或未直引（嵌套引用只报 warning）。
"""
from __future__ import annotations

import re
import sys
from pathlib import Path

LINK_RE = re.compile(r"\]\(([^)\s]+)\)")


def links(path: Path) -> list[str]:
    out = []
    for target in LINK_RE.findall(path.read_text(encoding="utf-8")):
        if target.startswith(("http://", "https://", "#", "mailto:")):
            continue
        out.append(target.split("#", 1)[0])
    return [t for t in out if t]


def check(skill: Path) -> dict:
    md = skill / "SKILL.md"
    direct = set(links(md))
    errors: list[str] = []
    warnings: list[str] = []
    for target in sorted(direct):
        if not (skill / target).exists():
            errors.append(f"死链: SKILL.md -> {target}")
    ref_files = []
    for sub in ("references", "assets"):
        if (skill / sub).exists():
            ref_files.extend(p.relative_to(skill).as_posix() for p in (skill / sub).rglob("*") if p.is_file())
    ref_files.sort()
    unlinked = [r for r in ref_files if r not in direct]
    for r in unlinked:
        warnings.append(f"未被 SKILL.md 直接引用: {r}")
    nested: list[str] = []
    for r in ref_files:
        for target in links(skill / r):
            nested.append(f"{r} -> {target}")
    return {"skill": skill.name, "direct_links": sorted(direct), "resource_files": ref_files,
            "unlinked": unlinked, "nested_refs": nested, "errors": errors, "warnings": warnings}


def main(argv: list[str]) -> int:
    root = Path(argv[1] if len(argv) > 1 else ".")
    skills = sorted(p.parent for p in root.rglob("SKILL.md"))
    bad = 0
    for skill in skills:
        r = check(skill)
        bad += 1 if r["errors"] else 0
        print(f"== {r['skill']}")
        print(f"   SKILL.md 直引: {r['direct_links']}")
        print(f"   资源文件    : {r['resource_files']}")
        print(f"   未被直引    : {r['unlinked'] or '无'}")
        print(f"   嵌套引用    : {r['nested_refs'] or '无'}")
        print(f"   错误        : {r['errors'] or '无'}")
    print(f"结论: 检查 {len(skills)} 个 skill，{bad} 个存在死链")
    return 1 if bad else 0


if __name__ == "__main__":
    raise SystemExit(main(sys.argv))
```

```shell
python3 tools/ref_depth.py skills
```

```text
== bad-skill
   SKILL.md 直引: ['references/missing.md']
   资源文件    : []
   未被直引    : 无
   嵌套引用    : 无
   错误        : ['死链: SKILL.md -> references/missing.md']
== csv-report
   SKILL.md 直引: ['assets/report-template.md', 'references/SCHEMA.md']
   资源文件    : ['assets/report-template.md', 'references/SCHEMA.md']
   未被直引    : 无
   嵌套引用    : 无
   错误        : 无
== db-migration-check
   SKILL.md 直引: ['references/MIGRATION_RULES.md']
   资源文件    : ['references/DETAILS.md', 'references/MIGRATION_RULES.md']
   未被直引    : ['references/DETAILS.md']
   嵌套引用    : ['references/MIGRATION_RULES.md -> DETAILS.md']
   错误        : 无
结论: 检查 3 个 skill，1 个存在死链
```

```text
references 组织要点：
1. 一个参考文件一个主题，文件名写成 form_validation_rules.md 这种自解释形式，别用 doc2.md
2. 每个参考文件都从 SKILL.md 直接链到，嵌套引用会被 Agent 的「预览式读取」截断
3. 超过 100 行的参考文件在开头放目录（TOC），让预览也能看到全文范围
4. 按域拆文件（reference/finance.md、reference/sales.md），让单次任务只加载相关域
5. 正文里只写「什么时候读哪个文件」，不复制参考文件的内容，避免两处不一致
```

## scripts 与 assets 目录

`scripts/` 放确定性逻辑（校验、转换、调用外部命令），`assets/` 放不需要执行的静态资源（输出模板、样例输入、字体、图标）。这里有个容易被忽略的表述要求：**指令里必须说清是「执行脚本」还是「把脚本当参考读」**——「运行 `analyze_form.py` 提取字段」与「参考 `analyze_form.py` 里的字段提取算法」对 Agent 是两种完全不同的动作，前者的代码不会进上下文，后者会。

```shell
csv-report/scripts/
# 1) 脚本自解释：参数、默认值都有 help
python3 scripts/build_plan.py --help

# 2) 需要直接执行的脚本给上可执行位，并加 shebang（uv 版用 --script 子命令）
chmod +x scripts/validate_plan.py
head -1 scripts/validate_plan.py

# 3) 带第三方依赖的脚本用 PEP 723 内联元数据声明依赖，执行时自动建环境
uv run --script scripts/check_migration.py --dir migrations
```

```text
usage: build_plan.py [-h] --data DATA --changes CHANGES --out OUT

生成变更计划

options:
  -h, --help            show this help message and exit
  --data DATA
  --changes CHANGES
  --out OUT
#!/usr/bin/env python3
```

```python
# 带依赖的脚本：内联元数据写在文件顶部，uv 会自动准备环境（规范见 packaging.python.org 的 Inline script metadata）
#!/usr/bin/env -S uv run --script
# /// script
# requires-python = ">=3.11"
# dependencies = ["requests>=2.32"]
# ///
import requests

print(requests.get("https://example.com", timeout=10).status_code)
```

`assets/` 的典型用途是把「输出格式」固化成文件而不是写成一大段说明：模板放进来，正文只写「按 assets/report-template.md 的字段与顺序输出，不要自增列」。这样做的好处是模板可以被脚本直接读取，也能被人工评审。

```text
csv-report/assets/
└── report-template.md     # 输出模板：字段、顺序、结论段写法
```

```text
scripts 与 assets 要点：
1. 指令里明确「执行」还是「参考」：执行省 token（代码不进上下文），参考适合让 Agent 理解复杂算法
2. 路径一律相对 skill 根目录、正斜杠；不要写绝对路径，也不要写 Windows 反斜杠（见 07.3 反模式）
3. 依赖用 PEP 723 内联元数据或 requirements 声明，配合 uv run --script 执行，避免「在我机器上能跑」
4. 脚本失败要能自己说清原因（退出码 + stderr），不要把判断推回给模型（见 07.4）
5. 模板与样例数据放 assets/，让「输出长什么样」有唯一事实来源
```

## 单文件与多文件拆分决策

官方给出的篇幅经验值是 `SKILL.md` 正文控制在 500 行以内、内容接近上限就拆。拆分的分界线不是「文件大小」，而是「这份内容是不是每次触发都要读」：每次都要用的判据与步骤留在正文，只在某个子场景出现的内容外移。反过来也要防过度拆分——把三行说明也拆成一个文件，会让 Agent 多出几次无谓的文件读取。

| 情况 | 留在 SKILL.md | 外移到 references/ 或 scripts/ |
|------|---------------|--------------------------------|
| 每次触发都要执行的步骤 | 是 | 否 |
| 只在特定分支出现的详细规则 | 只写「见 xx」 | 是 |
| 字段表、取值域、枚举 | 关键的几个 | 完整表 |
| 可机械判定的逻辑 | 只写调用命令 | 写成脚本 |
| 输入输出样例 | 最多一组 | 多组样例 |
| 历史判例、FAQ | 否 | 是 |

拆分动作可以按固定顺序做，避免边拆边改逻辑：

```shell
# 1) 先量：正文行数与各段体积
wc -l SKILL.md

# 2) 再切：把「按需内容」整段剪到 references/，正文留下路由句
#    例如把「字段定义」整段移到 references/SCHEMA.md，正文只留：
#    字段定义见 [references/SCHEMA.md](references/SCHEMA.md)

# 3) 后验：引用链路完整、无死链、无嵌套引用
python3 tools/ref_depth.py skills

# 4) 复验：正文回到 500 行以内
wc -l SKILL.md
```

```text
拆分决策要点：
1. 500 行是建议阈值不是硬限制，超了先看能不能删冗余，再考虑拆
2. 拆分的单位是「主题」，不是「行数」：同一主题的内容不要切成两个文件
3. 正文始终保留「路由」：什么时候读哪个文件、什么时候跑哪个脚本
4. 拆分后必须重跑引用检查，死链比长正文更致命
5. 拆完再评估一次元数据成本：description 不会因为正文变大而变大，但触发准确率可能与篇幅无关地下降（正文太长会稀释关键规则）
```

## 命名与版本管理

命名规则在规范里是硬约束：目录名 = `name` = 小写字母/数字/连字符，1-64 字符，不得首尾连字符或连续连字符。命名风格上官方建议用动名词（gerund）形式（`processing-pdfs`、`analyzing-spreadsheets`），或名词短语/动词短语（`pdf-processing`、`process-pdfs`），避免 `helper`、`utils`、`tools` 这类无法判断用途的名字。版本信息规范没有强制字段，实践上有两种落法：放进 `metadata`（跨工具安全），或作为工具自有的顶层字段——本机 Hermes 技能库里的 skill 就使用顶层 `version`、`author`、`license`、`platforms` 加 `metadata.hermes.*`，这套写法在严格实现下会因多余顶层键被拒，取舍取决于你的分发范围。

```yaml
---
# 跨工具安全写法：标准字段 + metadata 放版本
name: csv-report
description: Builds validated CSV-to-report pipelines from business data files. Use when the user mentions CSV exports or monthly reports.
license: Apache-2.0
compatibility: Requires Python 3.11 or newer; no network access needed.
metadata:
  author: data-platform-team
  version: "1.2"
---
```

```yaml
---
# 本机 Hermes 技能库中真实存在的写法（hermes-agent/SKILL.md）：顶层扩展字段 + metadata.hermes
name: hermes-agent
description: "Configure, extend, or contribute to Hermes Agent."
version: 2.1.0
author: Hermes Agent + Teknium
license: MIT
platforms: [linux, macos, windows]
metadata:
  hermes:
    tags: [hermes, setup, configuration, multi-agent, spawning, cli, gateway, development]
    related_skills: [claude-code, codex, opencode]
---
```

版本推进用 git 标签表达，标签名带上 skill 名以免库大了分不清；发布包的文件名也带版本号：

```shell
# 打标签（本机实测输出）
git tag -a csv-report-v1.2.0 -m "csv-report 1.2.0"
git tag -l
git log --oneline
```

```text
=== git tag -l ===
csv-report-v1.2.0
=== git log --oneline ===
309230f feat(csv-report): 拆分正文并接入校验脚本
```

```shell
# 发布包命名：<name>-<version>.zip，排除运行时产物
zip -r csv-report-1.2.0.zip csv-report -x 'csv-report/*.db' -x 'csv-report/plan*.json'
```

```text
命名与版本要点：
1. 目录名就是 name，改名等于改标识：调用方（用户口令、CI、文档）全都要跟着改
2. 用动名词或名词短语命名，禁止 helper / utils / tools 这类零信息名字
3. 版本号放 metadata.version（跨工具安全）；只在单一工具内分发时可用顶层字段，但要接受严格实现报错
4. 用 git tag 表达发布版本（如 csv-report-v1.2.0），包名与标签保持一致
5. 破坏性改动（改流程判据、改脚本参数）必须抬 minor 以上版本，并在 CHANGELOG 里写清迁移方式
```

## 跨工具兼容性

同一份目录能被多个工具使用，前提是只依赖标准字段与相对路径；各工具的差异集中在「装在哪里」和「有哪些扩展能力」上。下面这张表只列已核实的行为，其余实现以各自文档为准：

| 工具 | 加载路径 | 分发方式 | 备注 |
|------|----------|----------|------|
| Claude Code | 个人级 `~/.claude/skills/`，项目级 `.claude/skills/` | 版本库随项目走，或 Claude Code 插件 | 支持扩展字段如 `disable-model-invocation`、`allowed-tools`；前端命令与 Skill 已统一（`/skill-name`） |
| Claude API | 通过 `/v1/skills` 上传，在 `container` 参数里用 `skill_id`，需配代码执行工具 | Skills API 上传，工作区内共享 | 沙箱内无网络访问、不能在运行时安装包，依赖只能是预装包 |
| claude.ai | 由设置里上传 zip（Settings > Features） | 手动上传 zip | 每个用户各自安装，不做组织级统一分发 |
| Hermes | `~/.hermes/skills/<分类>/<name>/SKILL.md`（本机实测路径） | 目录放入或用技能管理工具写入 | 会话里只暴露 name + description，触发后用 `skill_view` 读正文与 linked_files |

跨工具兼容的写法收敛成四条：**只用标准 frontmatter 字段、路径用相对 skill 根目录的正斜杠、不依赖某个工具特有的工具名、把环境要求写进 `compatibility`**。装好后两个工具都验一次触发，是最省事的兼容性测试。

```shell
# 1) 同一份目录接入两个工具（软链，避免多副本）
ln -s ~/team-skills/csv-report ~/.claude/skills/csv-report
mkdir -p ~/.hermes/skills/data
ln -s ~/team-skills/csv-report ~/.hermes/skills/data/csv-report

# 2) 兼容性自检：字段与引用
python3 tools/validate_skills.py ~/team-skills/csv-report
python3 tools/ref_depth.py ~/team-skills

# 3) 用同一组问题在两个工具里各触发一次，记录是否命中
```

```text
兼容性要点：
1. 顶层只用标准字段；工具专属能力（预授权工具、手动调用开关）写在一眼能看出「非标准」的地方
2. 路径全部相对 skill 根目录、正斜杠：Windows 反斜杠在 Unix 上直接失效
3. 环境要求写进 compatibility（≤500 字符）：目标产品、系统依赖、是否需要网络
4. API 环境可能无网络、不能装包，脚本依赖要控制在预装范围内，否则 Skill 在那边直接不可用
5. 跨工具分发时用软链或包管理器指向同一份源，禁止手工复制出多份
```

## 应用场景实战

### 场景一：把 800 行的 SKILL.md 拆成「正文 + 参考 + 脚本」

背景：某个「月度报表」Skill 半年里被不断追加规则，正文涨到 800 多行，触发后上下文被占满，反而更容易漏掉关键判据。处理方式是按主题拆：字段定义、FAQ、排错步骤三份参考文档外移，可机械判定的逻辑改写成脚本，正文只保留流程与路由。

```text
拆分前（800+ 行，全部常驻某次触发的上下文）
monthly-report/SKILL.md        # 流程 + 字段表 + FAQ + 排错 + python 片段

拆分后
monthly-report/
├── SKILL.md                   # 约 120 行：流程、判据、路由
├── references/
│   ├── SCHEMA.md              # 字段定义与取值域（带 TOC）
│   ├── FAQ.md                 # 业务方常问
│   └── TROUBLESHOOTING.md     # 校验失败处理（带 TOC）
├── scripts/
│   ├── build_plan.py
│   ├── validate_plan.py
│   └── apply_plan.py
├── assets/
│   └── report-template.md
└── .gitignore
```

```shell
# 1) 量：确认确实超过建议上限
wc -l monthly-report/SKILL.md
# 2) 切：按主题整段迁移，正文留下路由句（见下方正文片段）
# 3) 验：引用链路与死链
python3 tools/ref_depth.py skills
# 4) 复量
wc -l monthly-report/SKILL.md
```

```markdown
<!-- 拆分后 SKILL.md 的关键片段：只讲「什么时候做什么」 -->
## 流程

1. 生成计划：`python3 scripts/build_plan.py --data data/orders.csv --changes data/changes.csv --out plan.json`
2. 校验计划：`python3 scripts/validate_plan.py --plan plan.json`（退出码非 0 时不要继续）
3. 应用计划：`python3 scripts/apply_plan.py --plan plan.json --db orders.db --seed data/orders.csv`
4. 渲染报表：按 [assets/report-template.md](assets/report-template.md) 的字段与顺序输出

字段定义与取值域见 [references/SCHEMA.md](references/SCHEMA.md)。
校验报错的处理见 [references/TROUBLESHOOTING.md](references/TROUBLESHOOTING.md)。
```

真实检查结果（本机实测，`ref_depth.py` 同时抓出死链与嵌套引用）：

```text
== csv-report
   SKILL.md 直引: ['assets/report-template.md', 'references/SCHEMA.md']
   资源文件    : ['assets/report-template.md', 'references/SCHEMA.md']
   未被直引    : 无
   嵌套引用    : 无
   错误        : 无
== db-migration-check
   SKILL.md 直引: ['references/MIGRATION_RULES.md']
   资源文件    : ['references/DETAILS.md', 'references/MIGRATION_RULES.md']
   未被直引    : ['references/DETAILS.md']
   嵌套引用    : ['references/MIGRATION_RULES.md -> DETAILS.md']
   错误        : 无
结论: 检查 3 个 skill，1 个存在死链
```

```text
拆分落地要点：
1. 先量再拆：用 wc -l 与检查脚本定位真正的体积来源（多数时候是字段表和 FAQ）
2. 参考文件按主题拆，文件名自解释，超过 100 行加 TOC
3. 所有参考文件从 SKILL.md 直达，禁止 A.md 里再链 B.md
4. 把「可机械判定」的部分改成脚本，正文只写调用命令与失败处理
5. 拆完重跑引用检查与行数复量，两步都过再提交
```

### 场景二：把 Skill 打包成分发包并接进流水线

背景：团队要把 Skill 分发给三个项目组，有的用 Claude Code 的项目级目录，有的用 Hermes 的技能目录。做法是版本库出源码，CI 打 zip 包（排除运行时产物），项目组解压到各自目录并跑一次校验。

```shell
# 1) 打包含版本号，排除数据库与临时计划文件
zip -r csv-report-1.2.0.zip csv-report -x 'csv-report/*.db' -x 'csv-report/plan*.json'

# 2) 看包内容，确认没有运行时产物、没有多余层级
unzip -l csv-report-1.2.0.zip
```

## 最佳实践与踩坑记录

### 最佳实践

1. 目录名与 `name` 严格一致，其余文件都放进三类约定目录，非约定目录必须在 `SKILL.md` 里写明用途。
2. `references/` 只保留一层引用，每个文件都从 `SKILL.md` 直达，超过 100 行加目录。
3. 参考文件按主题/域命名（`SCHEMA.md`、`TROUBLESHOOTING.md`），不按序号命名（`doc2.md`）。
4. 可机械判定的逻辑写进 `scripts/`，指令里用「运行」而不是「参考」来表述；依赖用 PEP 723 内联元数据声明。
5. 输出格式固化成 `assets/` 里的模板文件，而不是正文里的一大段格式说明。
6. 正文超过 500 行就按主题拆分，拆分后必须重跑引用检查。
7. 版本放进 `metadata.version` 并用 git 标签表达发布；分发包名与标签一致。
8. 运行时产物写进 `.gitignore`，并在打包命令里显式排除，避免夹带数据库与临时文件。
9. 同一份 Skill 用软链接入多个工具目录，禁止手工复制多份。

### 踩坑记录

```text
坑 1：把详细规范写成 references/A.md 里的链接再指向 B.md
结论：Agent 往往只读到 A.md 的前几十行，B.md 里的关键判据从未生效。
原因：嵌套引用会让读取退化成预览式读取（只读头部），信息不完整。
解法：所有参考文件都从 SKILL.md 直达；确需保留历史链接时，把 B.md 的内容并回 A.md 或拆成两个平级文件。
```

```text
坑 2：references/ 里放了文件但 SKILL.md 从没引用
结论：这份文件永远不进入上下文，等于白写；维护者还以为规则已经生效。
原因：三级加载不会主动扫描目录，只有被引用到才会读。
解法：用 ref_depth.py 一类检查脚本把「未被直引」列出来当 warning，CI 里定期看。
```

```text
坑 3：把运行时产物提交进技能仓库
结论：git ls-files 里出现 orders.db、plan.json，分发包里带出生产数据与临时结果。
原因：脚本默认在 skill 目录下生成文件，没有 .gitignore，打包也没排除。
解法：加 .gitignore（*.db、plan*.json、__pycache__/），打包命令显式 -x 排除，并把产物目录改到工作目录外（见 07.4 的 --db/--out 参数）。
```

```text
坑 4：拆出了十几个只有一个段落的小文件
结论：Agent 为了干活连开五六个文件，token 花得比拆分前还多，且容易只读一半。
原因：拆分的单位搞错成「行数」而不是「主题」，把同一主题切碎了。
解法：按主题拆，一个文件一个完整主题；正文里给出明确的读取条件（什么时候需要这份文件）。
```

```text
坑 5：脚本里用绝对路径或 Windows 反斜杠
结论：换机器或换操作系统直接跑不起来，Agent 报了错还得靠人猜。
原因：路径写成了写死的主机路径或反斜杠形式，脱离 skill 目录后就失效。
解法：统一用相对 skill 根目录的正斜杠路径；调用时以 skill 目录为工作目录（见 07.4 的参数化约定）。
```

```text
坑 6：把工具专属 frontmatter 字段当成通用字段用
结论：在自家工具里正常，换到严格实现上报 Unexpected key(s) in SKILL.md frontmatter，Skill 直接不可用。
原因：标准只定义少数几个字段，各实现的扩展字段不互通。
解法：版本、作者、平台等信息放 metadata 下；必须用扩展能力时在文档里注明它只对哪个工具生效。
```
