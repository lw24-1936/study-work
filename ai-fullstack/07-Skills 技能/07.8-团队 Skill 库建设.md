## 概述

个人技能库可以靠手感维护，团队技能库不行：**技能是被执行的指令**，写错了会稳定地做错事，而且往往过了几周才有人发现。团队建库要解决的是四个工程问题——盘得清（有多少条、谁负责、还在不在用）、审得住（进库与改库有闸门）、量得出（用没用、有没有改善）、沉得下（把踩坑变成规则而不是留在聊天记录里）。四件事都落地，技能库才会像代码库一样产生复利；缺任何一件，半年后它就会变成一个没人敢动、也没人真用的文本坟场。

```text
全篇主线：
1. 盘点 —— 台账（条目、来源、owner、版本、使用、闲置）是其它一切决策的输入
2. 评审 —— 分级评审 + CODEOWNERS + CI 闸门 + 试用期晋升，防的是"语义错误"而不只是格式
3. 度量 —— 采用度、触发质量、维护成本三组指标；不看"技能条数"这类虚荣指标
4. 沉淀 —— 三类输入源（事故复盘、重复提问、新流程上线）各有固定的沉淀动作与时限
5. 节奏 —— 周（回写与上游更新）、月（自检脚本）、季（盘点、度量、归档）三级例行
```

## 资产盘点

盘点不是"数一数有几个文件"，而是产出一张能支撑决策的台账：**每条技能是谁写的、什么版本、来自哪里、最近有没有用、附带哪些支持文件**。这张表的字段要和维护动作一一对应：`origin` 决定谁能自动改它、`state/idle_days` 决定归档候选、`patch` 决定是否需要重写、`lines` 与支持文件数决定它是不是万能技能。

Hermes 自带一份使用遥测（`~/.hermes/skills/.usage.json`），字段包括 `created_by`、`state`、`use_count`、`view_count`、`patch_count`、`last_used_at`、`last_viewed_at`，盘点脚本直接读它即可，不需要额外埋点。本机实测的原始结构：

盘点脚本（只读，输出 CSV 台账 + 汇总；本机可跑）：

```python
#!/usr/bin/env python3
"""团队技能库盘点：输出台账 CSV + 汇总统计。只读。"""
import argparse
import csv
import json
import os
from collections import Counter
from datetime import datetime, timezone
from pathlib import Path


def days_since(ts):
    if not ts:
        return None
    return round((datetime.now(timezone.utc) - datetime.fromisoformat(ts)).total_seconds() / 86400, 1)


def front_fields(text: str) -> dict:
    """取 SKILL.md 顶部的 frontmatter 简单键值（够用即可，复杂结构用 pyyaml）。"""
    fields, in_front = {}, False
    for line in text.splitlines():
        if line.startswith("---"):
            in_front = not in_front
            continue
        if not in_front:
            if line.strip():
                break
            continue
        if ":" in line and not line.startswith(" "):
            k, v = line.split(":", 1)
            fields[k.strip()] = v.strip().strip('"').strip("'")
    return fields


def walk(root: Path):
    for skill_md in root.rglob("SKILL.md"):
        rel = skill_md.relative_to(root)
        if any(p in (".archive", ".curator_backups", ".hub") for p in rel.parts):
            continue
        yield skill_md


def main() -> None:
    ap = argparse.ArgumentParser()
    ap.add_argument("--skills-root", default=os.path.expanduser("~/.hermes/skills"))
    ap.add_argument("--out", default="inventory.csv")
    args = ap.parse_args()
    root = Path(args.skills_root).expanduser()
    usage_file = root / ".usage.json"
    usage = json.loads(usage_file.read_text(encoding="utf-8")) if usage_file.exists() else {}

    rows, by_category, support = [], Counter(), Counter()
    for skill_md in walk(root):
        text = skill_md.read_text(encoding="utf-8", errors="ignore")
        meta, fm = usage.get(skill_md.parent.name, {}), front_fields(text)
        cat = skill_md.parent.parent.name if skill_md.parent.parent != root else "-"
        by_category[cat] += 1
        for kind in ("references", "scripts", "templates", "assets"):
            d = skill_md.parent / kind
            support[kind] += len(list(d.glob("*"))) if d.is_dir() else 0
        rows.append({
            "name": skill_md.parent.name,
            "category": cat,
            "version": fm.get("version", ""),
            "author": fm.get("author", ""),
            "origin": meta.get("created_by") or "",
            "state": meta.get("state") or "",
            "use": meta.get("use_count", ""),
            "view": meta.get("view_count", ""),
            "patch": meta.get("patch_count", ""),
            "idle_days": days_since(meta.get("last_used_at") or meta.get("last_viewed_at")) or "",
            "lines": len(text.splitlines()),
        })

    out = Path(args.out)
    with out.open("w", newline="", encoding="utf-8") as fh:
        writer = csv.DictWriter(fh, fieldnames=list(rows[0].keys()))
        writer.writeheader()
        writer.writerows(sorted(rows, key=lambda r: r["name"]))

    print(f"技能树：{root}")
    print(f"技能条目：{len(rows)}    台账已写入：{out}")
    print(f"\n来源分布：{dict(Counter(r['origin'] or '(无标记)' for r in rows))}")
    print(f"状态分布：{dict(Counter(r['state'] or '(无遥测)' for r in rows))}")
    print(f"有 version 字段：{sum(1 for r in rows if r['version'])} / {len(rows)}")
    print(f"有 author 字段：{sum(1 for r in rows if r['author'])} / {len(rows)}")
    print(f"支持文件合计：{dict(support)}")
    print(f"\n分类 Top 8：{by_category.most_common(8)}")


if __name__ == "__main__":
    main()
```

盘点结果怎么用（四条固定动作）：

| 盘点信号 | 含义 | 动作 |
|----------|------|------|
| `author` 为空 | 没人负责，坏了没人修 | 补 owner 或在 PR 模板里要求必填 |
| `origin` 为 `(无标记)` | 维护工具不敢自动管它 | `hermes curator adopt <name>` 明确交管 |
| `idle_days` 很大且 `state=active` | 大概率已失效 | 进季度归档候选（会周期性使用的用 `pin` 保护） |
| `lines` 很大 + 支持文件很多 | 万能技能嫌疑 | 按「独立验收标准」拆分 |

## 评审流程

评审要拦两类问题：**格式问题**（机械可查，交给 CI）和**语义问题**（必须人看：description 是否够窄、流程是否与真实系统一致、脚本是否会做危险操作）。把这两类混在一次评审里，结果是两个都没做好。

先定分级，不同改动用不同强度的评审：

| 改动类型 | 评审强度 | 必查项 |
|----------|----------|--------|
| 新增技能 | 2 人评审（其中 1 名领域 owner） | 触发条件、边界、验收标准、脚本安全 |
| 修改现有技能 | 1 人评审（该技能 owner 或后备） | 行为差异 + CHANGELOG 条目 + 版本号 |
| 新增/修改附带脚本 | 按代码评审标准 | 命令安全性、幂等、dry-run 分支 |
| 归档/合并 | 1 人评审（技术负责人） | 支持文件去向、引用方是否更新 |
| 仅错别字/排版 | 自助合并 | CI 通过即可 |

```markdown
## 这个技能解决什么问题

<!-- 一句话：用户说什么/做什么时应该触发它 -->

## 检查项

- [ ] `description` 含触发场景 + 不适用范围 + 交付物
- [ ] 已用真实 prompt 复测触发（至少 3 条应触发、2 条不应触发）
- [ ] 附带的脚本已人工读过，无 `curl | bash`、无对 `~/.ssh`、`~/.aws`、`.env` 的读取
- [ ] 涉及写操作的步骤有 dry-run 或确认分支
- [ ] 相对引用（references/、scripts/、templates/）逐条点开存在
- [ ] 新增技能已标 `author`（owner）与 `version`
- [ ] 修改技能已更新版本号与 CHANGELOG
- [ ] 搜索过仓库，确认不是与既有技能重复的第二份实现

## 归档或合并（如涉及）

- [ ] 内容去向已写明（并入哪条技能 / 哪些文件）
- [ ] 引用方已更新
- [ ] 旧技能先归档、不删除
```

CI 闸门用前一节脚本即可，关键是**别让闸门产生噪音**：引用检查必须豁免 `references/<module>/SKILL.md` 这类模板占位符，否则 CI 常红、团队会集体绕过它。

「试用期晋升」是控制入库质量最有效的机制：新技能先进作者自己的用户级目录（`~/.hermes/skills/`），用两周、有真实使用记录，再提 PR 晋升进团队库。Hermes 的遥测天然支持这个判据：晋升 PR 里附上 `use_count` 与真实触发记录。

```text
晋升判据（两条满足其一即可提 PR）：
1. 两周内被真实使用 >= 3 次，且没有因这条技能改写过流程
2. 解决了团队级重复问题（多人问同一件事），且 owner 明确

不晋升的情况：
- 只有作者一个人用的个人偏好流程（留在用户级目录即可）
- 与既有技能高度重叠（先合并再谈晋升）
```

## 效果度量

度量要能回答一个具体问题：**这条技能值不值得继续维护**。因此指标分三组，缺一组就会得出错误结论：

| 组 | 指标 | 数据来源 | 用途 |
|----|------|----------|------|
| 采用度 | `use_count`、`view_count`、覆盖人数 | 使用遥测 | 判断有没有人在用 |
| 触发质量 | 误触发/漏触发次数、触发准确率 | 人工标注 prompt 集 + 例会反馈 | 判断 description 写得好不好 |
| 维护成本 | `patch_count`、正文行数、支持文件数、上下文占用 | 遥测 + 台账 | 判断是资产还是负债 |

**不要用「技能条数」当成绩**：条数增长既可能来自沉淀，也可能来自重复造第二份实现。真正的健康信号是「被使用的技能条数占比」与「单条技能的平均补丁次数」。

触发质量可以用一个最小评测集量化，成本很低（半小时就能建起来）：

```yaml
# evals/trigger-cases.yaml
# expected: 期望被触发的技能；空表示不应触发任何技能
- prompt: "把 order-service 发到生产，灰度 10%"
  expected: deploy-service
- prompt: "刚才那次发布回滚一下"
  expected: deploy-service
- prompt: "orders 表要加个索引，帮我评审下变更"
  expected: db-change-review
- prompt: "这条告警是什么意思？"
  expected: ""          # 不应该触发整篇运维流程
- prompt: "帮我写一份上周的工作总结"
  expected: weekly-report
```

评测过程只有三步，不需要框架：按 prompt 逐条真实执行，记录实际加载了哪些技能，与 `expected` 对比，算出准确率并把误判样本回写成 description 的修正。每条技能至少覆盖 3 条应触发 + 2 条不应触发，低于 80% 准确率就回去改 description。

季度度量报告（脚本 + 真实输出形态）——把上面的遥测聚合成一页 Markdown，直接进季度会：

```python
#!/usr/bin/env python3
"""季度技能库度量报告（Markdown）。只读，读取 Hermes 使用遥测。"""
import argparse
import json
import os
from collections import Counter
from datetime import datetime, timezone
from pathlib import Path


def days(ts):
    return None if not ts else round((datetime.now(timezone.utc) - datetime.fromisoformat(ts)).total_seconds() / 86400, 1)


def main() -> None:
    ap = argparse.ArgumentParser()
    ap.add_argument("--skills-root", default=os.path.expanduser("~/.hermes/skills"))
    args = ap.parse_args()
    root = Path(args.skills_root).expanduser()
    usage = json.loads((root / ".usage.json").read_text(encoding="utf-8"))
    live = [p for p in root.rglob("SKILL.md")
            if not any(x in (".archive", ".curator_backups", ".hub") for x in p.relative_to(root).parts)]

    used = {k: v for k, v in usage.items() if v.get("use_count", 0) > 0}
    patched = {k: v for k, v in usage.items() if v.get("patch_count", 0) > 0}
    top = sorted(used.items(), key=lambda kv: -kv[1]["use_count"])[:5]
    hot_patch = sorted(patched.items(), key=lambda kv: -kv[1]["patch_count"])[:5]
    idle = sorted([(k, days(v.get("last_used_at") or v.get("last_viewed_at")))
                   for k, v in usage.items() if days(v.get("last_used_at") or v.get("last_viewed_at"))], key=lambda x: -x[1])[:5]

    print(f"# 技能库季度度量报告（{datetime.now(timezone.utc).date()}）\n")
    print(f"- 技能条目：{len(live)}")
    print(f"- 有使用记录：{len(used)}（{len(used) / max(len(live), 1):.1%}）")
    print(f"- 被补丁修改过：{len(patched)}")
    print(f"- 状态分布：{dict(Counter(v.get('state') for v in usage.values()))}\n")
    print("## 使用最多（Top 5）\n")
    print("| 技能 | use | view | patch | 最近使用 |")
    print("|------|-----|------|-------|----------|")
    for k, v in top:
        print(f"| {k} | {v['use_count']} | {v['view_count']} | {v['patch_count']} | {days(v.get('last_used_at'))} 天前 |")
    print("\n## 补丁最多（漂移信号，Top 5）\n")
    print("| 技能 | patch | use | 最近打补丁 |")
    print("|------|-------|-----|------------|")
    for k, v in hot_patch:
        print(f"| {k} | {v['patch_count']} | {v['use_count']} | {days(v.get('last_patched_at'))} 天前 |")
    print("\n## 最久未用（Top 5）\n")
    for k, d in idle:
        print(f"- {k}：{d} 天")


if __name__ == "__main__":
    main()
```

## 知识沉淀机制

技能库的输入必须固定下来，否则它会随作者热情波动。三个固定输入源对应三种不同动作：

| 输入源 | 典型场景 | 沉淀动作 | 时限 |
|--------|----------|----------|------|
| 事故复盘 | 同类问题第二次发生 | 把根因写成规则与判定条件，补机器校验 | 复盘会后 3 个工作日内 |
| 重复提问 | 同一问题被问第三次 | 直接把答案写成技能（含触发词） | 第三次被问的当天 |
| 新流程上线 | 新发布通道、新评审规范 | 技能与流程同一个 PR 落地 | 与流程上线同步 |

「第三次被问」是个好用且不依赖自觉的触发条件：第一次回答，第二次回答并观察，第三次就是信号——写进技能并告诉提问者以后直接调用。

要分清技能与相邻载体的分工，避免同一内容两处维护：

| 载体 | 适合装什么 | 谁读 |
|------|-----------|------|
| Skill | 多步流程、判定条件、可执行脚本 | Agent 执行时按需加载 |
| Runbook / Wiki | 参考手册、术语、架构说明 | 人查资料时 |
| AGENTS.md / CLAUDE.md | 每次都要遵守的少量硬规则 | Agent 常驻上下文 |
| ADR | 为什么这样决策、放弃了什么 | 人做新决策时 |

owner 制是沉淀能持续的前提：每条技能有 `author`（负责人）+ 归属小组（CODEOWNERS）。责任人变更时随 PR 一起改，季度盘点时把「无 owner 的技能」单独列出来处理。

```text
季度节奏（三级例行，能写进日历就不要靠记性）：
周：回写本周踩的坑（patch），跑 hermes skills check / update 处理上游更新
月：跑反模式自检（description、引用文件、同名分叉），处理红灯项
季：跑盘点与度量报告 -> 决策会（留/改/合/档）-> 执行并台账留痕 -> 更新 README 规范
```

新人上手路径要写进 README，让第一周就能用上而不是第五周：

```shell
# 新人 onboarding（写进 README 的"第一天"章节）
hermes skills tap add my-company/company-skills         # 加入内部技能源
hermes skills browse --source my-company/company-skills # 看有什么
hermes skills install my-company/company-skills/deploy-service --category ops
hermes skills list --source hub                          # 确认已装
hermes skills trust                                      # 仓库内技能授权（按仓库执行）
```

## 应用场景实战

### 场景一：从零搭一个团队技能库并接入流水线

背景：一个 30 人的研发组织（3 个小组：平台、业务、数据），有 15 条反复讲的口头流程，散落在 wiki、聊天记录和个人笔记里。目标是三个月内建成一个有评审、有台账、有度量的技能库。

第一步，建仓库与规范（README 是契约，不是介绍页）：

```text
company-skills/
├── README.md

```

```markdown
<!-- README.md 的"收录标准"一节（节选） -->
## 收录标准

进库的技能必须满足：

1. 面向团队（>= 2 人会用），不是个人偏好流程
2. `description` 含触发场景、不适用范围、交付物
3. 有明确验收标准（`## 验证` 段），判据可观察
4. 至少 3 条应触发、2 条不应触发的真实 prompt 复测通过
```

```yaml
# 数据库变更评审

## 何时使用

- 有 DDL 或大表数据回填要上生产，需要评审
- 不适用：临时查询、只读报表、测试库随意改动

## 步骤

1. 用 references/table-size-check.md 的查询确认表规模（行数、写入 QPS）
2. 大表加索引必须 CREATE INDEX CONCURRENTLY，例外见 references/concurrently-caveats.md
3. 生成回滚脚本；无回滚路径的变更直接拒绝
4. 长事务回填改批处理，给出批大小与限速

## 验证

- 变更脚本通过 ci/check_index_ddl.py
- 回滚脚本在预发环境实测过一次
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先建台账再谈治理：没有 `use/state/idle/owner` 这四类字段，所有清理决策都是凭印象。
2. 格式问题交给 CI，语义问题交给人：CI 管 frontmatter、引用存在性、同名分叉；人只看「这个流程是否符合真实系统、脚本是否会做危险操作」。
3. 新技能先进个人目录试用两周，有真实使用记录再提 PR 晋升；这条规则能挡掉大部分一次性流程。
4. 每条技能必须有 owner（`author` + CODEOWNERS 归属小组），无 owner 的技能在季度盘点里单独列出并限期处理。
5. 度量至少三组指标（采用度、触发质量、维护成本），不要用技能条数当成绩，也不要用单次使用次数定生死。
6. 沉淀有固定触发条件与时限：事故复盘 3 个工作日内、同一问题第三次被问当天、新流程与技能同一个 PR。
7. 归档永远先备份（`hermes curator backup`），并把「内容去向」写进 PR；归档不是删除，`restore` 随时能回来。
8. 把节奏写进日历：周（回写 + 上游更新）、月（自检）、季（盘点 + 度量 + 决策 + 归档）。

### 踩坑记录

```text
坑 1：把"技能条数"当 KPI，团队开始批量造技能
结论：半年后库里有 200 条技能，真正被用的还是那 20 条，且出现大量近义重复。
原因：条数是虚荣指标，录入成本低、清理成本高，指标本身在鼓励错误行为。
解法：改用"被使用占比 + 触发准确率 + 平均补丁次数"；新增技能要走试用期晋升，不设条数目标。

坑 2：评审只看正文写得漂不漂亮
结论：一次合并把"用 CONCURRENTLY 建索引"的关键步骤删掉了，两周后生产锁表。
原因：语义问题不看 diff 就对不出来，尤其"删除"比"新增"更不显眼。
解法：评审清单要求逐条对照真实系统验证（命令、环境名、判据），并明确标出"删除了哪条边界条款"。

坑 3：CI 引用检查太严，团队集体绕过
结论：检查被加进 allow_failure，真死链接也一起溜了过去。
原因：模板占位符（references/<module>/SKILL.md）被当成缺失文件，红灯常亮。
解法：豁免含 <>、{}、*、... 的占位符，只对具体路径报错；预发布时用一个小 repo 验证误报率。

坑 4：没有 owner 的技能没人敢改也没人敢删
结论：盘点时列出了 30 条无 owner 技能，一年后它们还在，且行为已失效。
原因：责任真空——改动需要背责任，删除需要背风险，于是默认不动。
解法：把"无 owner"当成明确的状态来处理：季度盘点限期指定 owner 或归档；用 curator adopt 交管。

坑 5：把 wiki 里的长手册整篇搬成技能
结论：技能加载后占满上下文，模型反而抓不住关键步骤。
原因：技能是"执行时的流程"，不是"资料手册"；载体错配。
解法：必须执行的多步流程进 SKILL.md，参考资料留在 wiki，两边互相引用；常驻硬规则进 AGENTS.md。

坑 6：度量报告只发给管理者，团队看不到自己的数据
结论：报告发了两季，技能库质量没有变化。
原因：指标没有落到具体 owner 的可执行动作上，团队只把它当考核材料。
解法：报告里每条决议都到 owner + 截止日期，且把与 owner 相关的片段单独发给他们；下次开会只复查上次决议的完成情况。
```
