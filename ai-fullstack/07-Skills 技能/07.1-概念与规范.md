## 概述

Skill（Agent Skills）是把「某个领域的多步流程、判定标准、可执行脚本」打包成文件系统目录的开放规范：一个目录里放一个必需的 `SKILL.md`，再加可选的脚本与参考资料，Agent 平时只看到一句 `description`，判断相关时才把正文读进上下文。它解决的是「程序型知识」的复用问题——同一套评审流程、发布流程、数据校验规则，不必每次对话重新粘贴，也不必让常驻的 `AGENTS.md` 一直占着上下文。

```text
全篇主线：
1. 来源 —— Agent Skills 由 Anthropic 提出并开源，现由 agentskills.io 作为跨工具规范维护
2. 结构 —— 目录 + 必需 SKILL.md；frontmatter 只有 name / description 是必填
3. 加载 —— 三级渐进式披露：元数据常驻、正文按需、资源用时才读，脚本只回输出
4. 触发 —— description 是唯一触发依据，必须同时写「做什么」和「何时用」
5. 边界 —— Skill 只给流程，工具能力来自工具集与 MCP；两者正交，不要混用
```

## Agent Skills 规范来源与定位

Agent Skills 最初随 Claude Code 与 Claude API 落地，随后作为开放规范发布，规范正文放在 agentskills.io，并配套参考校验工具（`skills-ref`）用于检查 frontmatter 与命名规则；采用同一目录约定的产品包括 Claude Code、Claude API、claude.ai，以及把该规范纳入自身技能机制的 agent 工具。各家在标准之外还有自己的扩展字段与加载目录，这一点必须以对应工具的文档为准。它的定位与 MCP 正交：**MCP 解决「Agent 能连上什么外部能力」，Skill 解决「Agent 该按什么流程做事」**，一个连满 MCP Server 的 Agent 依然不知道你们团队的需求评审要几步、哪一步必须留证据。

最小可用形态就是「一个目录 + 一个 SKILL.md」，没有构建步骤，也不需要注册中心：

```shell
# 最小 Skill：目录名必须与 frontmatter 里的 name 一致
mkdir -p ~/.claude/skills/csv-report
cat > ~/.claude/skills/csv-report/SKILL.md <<'EOF'
---
name: csv-report
description: Builds validated CSV-to-report pipelines that turn business data files into Markdown reports. Use when the user mentions CSV exports, monthly reports, or bulk field updates.
---

# CSV 报表流水线

先生成变更计划，校验通过后再应用，最后按模板渲染报表。
EOF

# 目录树长这样（没有任何必需的其他文件）
find ~/.claude/skills/csv-report -type f
```

```text
/home/user/.claude/skills/csv-report/SKILL.md
```

```text
规范来源与定位要点：
1. 规范的核心只有一条：目录 + SKILL.md，frontmatter 提供发现信息，正文提供流程
2. 与 MCP 正交：能力（工具）走 MCP，流程（怎么做）走 Skill，二者常配合使用
3. 元数据在启动时就进系统提示，正文要等触发才读——这是「多装几十个 skill 也不炸上下文」的原因
4. 开放标准意味着同一份目录可以被多个工具复用，但扩展字段与加载路径各家不同
5. 具体字段约束与校验方式以 agentskills.io 的 specification 页为准，本文按其当前版本整理
```

## SKILL.md 结构与 frontmatter 字段

`SKILL.md` 由 YAML frontmatter 加 Markdown 正文组成，`name` 与 `description` 是唯二必填字段，其余字段用于声明许可证、环境要求、任意元数据与预授权工具。`name` 的约束比想象的严格：只能小写字母、数字、连字符，不能首尾是连字符、不能出现连续连字符，最长 64 字符，并且**必须与父目录名一致**——很多实现直接按目录名索引 skill，不一致会导致加载失败或索引错乱。`description` 必须非空且不超过 1024 字符，它是唯一的触发依据，写法详见后文。

| 字段 | 必填 | 约束与用途 |
|------|------|------------|
| `name` | 是 | 1-64 字符，仅 `a-z`、`0-9`、`-`，不得首尾为 `-`、不得连续 `-`，必须等于目录名 |
| `description` | 是 | 1-1024 字符，非空，写清「做什么 + 何时用」，第三人称 |
| `license` | 否 | 许可证名或指向随包 LICENSE 文件的说明 |
| `compatibility` | 否 | 最长 500 字符，声明环境要求：目标产品、系统依赖、是否需网络 |
| `metadata` | 否 | 任意字符串键值对，如 `author`、`version`；工具自定义字段建议放这里 |
| `allowed-tools` | 否 | 空格分隔的预授权工具列表，实验性字段，各实现支持度不同 |

字段约束可以直接用一段脚本验证，下面是本机实测结果（Python 3.14.7，标准库 `re`）：

```python
#!/usr/bin/env python3
"""检查 name 字段是否符合规范：长度 1-64、仅小写字母/数字/连字符、不首尾连字符、无连续连字符。"""
import re

NAME_RE = re.compile(r"^[a-z0-9]+(?:-[a-z0-9]+)*$")

for name in ("csv-report", "data-analysis", "PDF-Processing", "-pdf", "pdf--processing"):
    ok = bool(NAME_RE.match(name)) and 1 <= len(name) <= 64
    print(f"{name:16} {'✓ 合法' if ok else '✗ 非法'}")
```

```text
csv-report       ✓ 合法
data-analysis    ✓ 合法
PDF-Processing   ✗ 非法
-pdf             ✗ 非法
pdf--processing  ✗ 非法
```

规范还提供了参考校验工具 `skills-ref`，用来一次性检查 frontmatter 与命名（安装与调用方式以官方仓库说明为准）：

```shell
# 规范中给出的用法
skills-ref validate ./my-skill
```

```text
SKILL.md 结构要点：
1. frontmatter 只有 name / description 必填，能少写就少写，写多了只增加常驻成本
2. name 必须等于父目录名，改写目录时记得同步 frontmatter
3. 工具自定义字段优先塞进 metadata，顶层多余字段在严格实现下会报 unexpected key
4. description 上限 1024 字符，写满不代表好——它的成本是每个会话都在付
5. 正文没有格式限制，只要求「Agent 读一遍就能照做」：步骤、判定、边界情况
```

## 渐进式披露的三级加载

渐进式披露（progressive disclosure）是 Skill 能在有限上下文里装下大量知识的根本机制：内容按「什么时候需要」分成三级，前一级只放索引，后一级用时才付 token。规范给的经验值是元数据约 100 tokens/skill、正文建议不超过 5000 tokens、资源文件在被读取前零成本；脚本更特殊——**只把执行结果放进上下文，代码本身不进去**，这也是「写脚本比让模型现写代码」更省更稳的原因。

| 级别 | 内容 | 何时加载 | 上下文成本 |
|------|------|----------|------------|
| Level 1 元数据 | frontmatter 的 `name`、`description` | 会话启动时全部加载 | 约 100 tokens/skill |
| Level 2 指令 | `SKILL.md` 正文 | Skill 被触发时 | 建议 < 5000 tokens（正文 < 500 行） |
| Level 3 资源 | `references/`、`assets/`、`scripts/` | 正文引用到、或需要执行时 | 读文件才计费，脚本只计输出 |

本机 Hermes 技能库里同时存在 1116 个 skill 目录（`ls /root/.hermes/skills | wc -l`），仍然能正常工作，靠的就是同一套分层：会话里只列出 `name` + `description`，需要时才用 `skill_view` 读 `SKILL.md`，再按 `linked_files` 去取里面的参考文件。三级加载的成本可以用脚本量出来：

```python
#!/usr/bin/env python3
"""统计每个 SKILL.md 的元数据（frontmatter）与正文体积，用于估算渐进式披露的上下文成本。"""
from __future__ import annotations

import sys
from pathlib import Path


def est_tokens(text: str) -> int:
    # CJK 字符约 1 字符 = 1 token，ASCII 其他字符约 4 字符 = 1 token（粗略量级，用于横向比较）
    cjk = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff" or "\u3000" <= ch <= "\u303f"
              or "\uff00" <= ch <= "\uffef")
    return cjk + (len(text) - cjk) // 4


def split(text: str) -> tuple[str, str]:
    lines = text.splitlines()
    if not lines or lines[0].strip() != "---":
        return "", text
    end = next((i for i, line in enumerate(lines[1:], start=1) if line.strip() == "---"), None)
    if end is None:
        return "", text
    return "\n".join(lines[: end + 1]), "\n".join(lines[end + 1:])


def main(argv: list[str]) -> int:
    root = Path(argv[1] if len(argv) > 1 else ".")
    total_meta = 0
    print(f"{'skill':28} {'meta 字符':>9} {'meta≈tok':>9} {'正文行':>7} {'正文≈tok':>9}")
    for md in sorted(root.rglob("SKILL.md")):
        meta, body = split(md.read_text(encoding="utf-8"))
        total_meta += est_tokens(meta)
        print(f"{md.parent.name:28} {len(meta):>9} {est_tokens(meta):>9} "
              f"{len(body.splitlines()):>7} {est_tokens(body):>9}")
    print(f"常驻成本合计: ≈ {total_meta} tokens（假设每个 skill 只把 frontmatter 放进系统提示）")
    return 0


if __name__ == "__main__":
    raise SystemExit(main(sys.argv))
```

```text
skill                          meta 字符  meta≈tok     正文行    正文≈tok
bad-skill                           53        13      14       108
csv-report                         443       110      25       398
db-migration-check                 527       131      20       201
常驻成本合计: ≈ 369 tokens（假设每个 skill 只把 frontmatter 放进系统提示）
```

```text
三级加载要点：
1. 常驻的是元数据不是正文：把「触发关键词」写进 description，把流程留在正文
2. 正文接近 500 行就拆到 references/，正文只留路由与判定，不搬整段规范
3. 脚本优于现场生成代码：代码不进上下文，只回 stdout/stderr，既省 token 又稳定
4. 资源文件之间不要互相嵌套引用：一级引用读得全，嵌套引用容易被 head 截断（详见 07.2）
5. 常驻成本随 skill 数量线性增长，库越大越要在 description 上做减法
```

## 触发机制与 description 设计

触发有两个入口：**模型读 `description` 自行判断相关性**（默认路径），以及用户显式调用（Claude Code 里的 `/skill-name`）。既然自动触发完全依赖那一句描述，写法就有硬性要求：第三人称（它会被注入系统提示，写「我可以帮你」会让判断主体错位）、同时包含「做什么」与「何时用」、带上业务方会说的关键词（用户不会说「CSV 报表流水线」，他会说「这个月的报表」）。Claude Code 另外提供了 `disable-model-invocation` 之类的扩展字段，用来把某些 Skill 限制为只能手动调用。

```yaml
# 好：做什么 + 何时用 + 关键词，第三人称
name: csv-report
description: Builds validated CSV-to-report pipelines from business data files and applies bulk field updates idempotently. Use when the user mentions CSV exports, monthly reports, spreadsheet-driven updates, or asks to fill in missing report columns.
```

```yaml
# Claude Code 扩展字段示例：手动调用 + 预授权工具（标准之外的字段，其他实现可能报 unexpected key）
name: release-checklist
description: Runs the pre-release checklist for the payments service, covering migration verification, canary thresholds, and rollback proof. Use when preparing a production release or when the user asks whether a release is ready.
disable-model-invocation: true
allowed-tools: Bash(git:*) Read Grep
```

Claude Code 的文档明确列出了它接受的 frontmatter 属性：`allowed-tools`、`compatibility`、`description`、`license`、`metadata`、`name`；出现其他键时的报错形如 `Unexpected key(s) in SKILL.md frontmatter: argument-hint`。这条约束决定了「跨工具可移植」的写法：**标准字段放顶层，工具专属字段放 `metadata` 下或接受它只对某一个工具生效**。

| 写法 | 例子 | 结果 |
|------|------|------|
| 只说做什么 | `Helps with PDFs.` | 触发不可预测，相关性判断没有依据 |
| 只有泛化词 | `Handles data tasks.` | 几乎不触发，或者在任何数据话题上误触发 |
| 第一人称 | `I can help you process Excel files.` | 与系统提示的陈述语气冲突，容易被忽略 |
| 做什么 + 何时用 + 关键词 | `Extracts text and tables from PDF files... Use when the user mentions PDFs, forms, or document extraction.` | 触发稳定，误触发少 |

```text
description 设计要点：
1. 一句话里同时回答「做什么」和「何时用」，后半句用 Use when 开头写触发场景
2. 用第三人称动词开头（Processes / Builds / Validates / Extracts），不要用「我可以」
3. 塞进真实关键词：业务名词、文件后缀、动作动词，用户怎么说就怎么写
4. 上限 1024 字符，但常驻成本是每个会话都在付，能 200 字符说清就别写 800
5. 需要「只能手动调用」时用实现的扩展字段（如 Claude Code 的 disable-model-invocation），别指望描述写模糊
```

## Skill 与相邻概念的边界

同一份知识可以放进 prompt、`CLAUDE.md`/`AGENTS.md`、Skill、子代理或 MCP 工具，选错位置要么费钱要么失效。判定依据是「这份知识的形态」：事实型约定（技术栈、目录、命令别名）适合常驻的规则文件；**程序型知识（三步以上的流程、带判定的处理链）适合 Skill**；需要隔离上下文或大规模并行时用子代理；需要真的动外部系统时用 MCP 工具或内置工具。一个实用的判定信号是：**你在同一次会话里把同一段步骤粘贴第二次了，它就该变成 Skill**。

| 机制 | 加载时机 | 生命周期 | 适合承载 | 不适合承载 |
|------|----------|----------|----------|------------|
| 对话里的 prompt | 每次手工粘贴 | 单次会话 | 一次性任务背景 | 反复使用的流程 |
| `AGENTS.md` / `CLAUDE.md` 规则文件 | 每次会话常驻 | 项目级长期 | 事实、约定、边界 | 长流程、大量示例 |
| Skill | 触发时才读正文 | 跨会话、可分发 | 程序型知识、脚本 | 高频变更的事实 |
| 子代理 | 独立上下文里执行 | 单次任务 | 并行、隔离、长任务 | 需要与用户频繁往返的小步骤 |
| MCP 工具 | 连接后进工具表 | 连接级 | 外部系统动作与数据 | 流程与判定标准 |

```shell
# 判断边界的小实验：数一数同一段指令在本周会话里出现过几次
hermes sessions search "发布前检查" 2>/dev/null | wc -l
# 出现两次以上 → 抽成 Skill；只是一次性的背景 → 继续留在 prompt 里
```

```text
边界划分要点：
1. Skill 不注册工具、不申请权限：它只是指令，能力仍然来自工具集与 MCP
2. 事实型知识留常驻规则文件，程序型知识进 Skill，两者不要互相塞
3. 需要「Agent 先做一堆事再回来」时才用子代理，Skill 本身不隔离上下文
4. 涉及外部系统的动作写进 Skill 时，要显式写清该用哪个工具（MCP 工具用全限定名，见 07.4）
5. 一份 Skill 只承载一条流程；把「数据校验」和「发布审批」塞进同一个目录，触发会互相干扰
```

## 应用场景实战

### 场景一：把「数据库变更评审」流程沉淀成 Skill 并接入两个工具

背景：团队的 schema 变更评审有固定流程——检查命名、检查注释头、检查破坏性语句、在临时库验证幂等、把结论贴回 PR。这段流程以前写在 PR 模板里，靠人自觉执行。改成 Skill 后，Agent 在有人提到迁移文件时自动加载流程并按脚本产出结论。Skill 放在版本库里维护，两份路径分别软链到 Claude Code 与 Hermes 的 skill 目录，避免多副本漂移。

```text
db-migration-check/
├── SKILL.md
├── references/
│   └── MIGRATION_RULES.md
└── scripts/
    └── check_migration.py
```

```shell
# 1) 在版本库里维护 Skill（目录名 = frontmatter 的 name）
mkdir -p ~/team-skills/db-migration-check/references
mkdir -p ~/team-skills/db-migration-check/scripts
# 写入 SKILL.md、references/MIGRATION_RULES.md、scripts/check_migration.py（内容见 07.2 与 07.4）

# 2) 接入 Claude Code（个人级与项目级）
ln -s ~/team-skills/db-migration-check ~/.claude/skills/db-migration-check
ln -s ~/team-skills/db-migration-check .claude/skills/db-migration-check

# 3) 接入 Hermes（本机目录约定：~/.hermes/skills/<分类>/<name>/SKILL.md）
mkdir -p ~/.hermes/skills/database
ln -s ~/team-skills/db-migration-check ~/.hermes/skills/database/db-migration-check

# 4) 装完立刻验证：必填字段齐全、name 与目录一致、引用文件存在
python3 tools/validate_skills.py ~/team-skills/db-migration-check
```

```text
[
  {
    "skill": "/root/team-skills/db-migration-check",
    "ok": true,
    "errors": [],
    "warnings": [],
    "body_lines": 20
  }
]
校验结论: 全部通过
```

```text
落地要点：
1. Skill 放版本库统一维护，工具目录用软链指向，避免多份副本各改各的
2. 目录名与 name 一起改，改完跑一次校验脚本再提 PR
3. 流程里凡是能脚本化的判定（命名、注释头、幂等）都下沉到 scripts/，正文只写「什么时候跑哪个脚本」
4. 触发词写业务方实际会说的话语：迁移文件、schema 变更、升级脚本
5. 装好后用真实提问验一遍（一句该触发、一句不该触发），别假设它一定被加载
```

### 场景二：给团队 skill 库加一条 CI 校验

背景：Skill 库一多，最典型的退化是「name 与目录名不一致、引用文件被删了、正文膨胀到 800 行」。这些都能机械判定，做成校验脚本挂进 CI，比靠评审记忆可靠。脚本检查四件事：`SKILL.md` 存在、必填字段齐全、`name` 合规且等于目录名、正文里引用的相对路径真实存在。

```python
#!/usr/bin/env python3
"""Agent Skills 合规校验：SKILL.md 存在性、frontmatter 必填字段、name 命名规则、正文行数、引用文件是否存在。

用法：python3 validate_skills.py <skill 目录> [<skill 目录> ...]
退出码：0 全部通过，1 存在错误。
"""
from __future__ import annotations

import json
import re
import sys
from pathlib import Path

NAME_RE = re.compile(r"^[a-z0-9]+(?:-[a-z0-9]+)*$")
LINK_RE = re.compile(r"\]\(([^)\s]+)\)")
MAX_NAME = 64
MAX_DESC = 1024
MAX_BODY_LINES = 500


def split_frontmatter(text: str) -> tuple[dict[str, str], str]:
    """只解析 SKILL.md 需要的 YAML 子集：标量、折叠块（>）、字面块（|）。"""
    lines = text.splitlines()
    if not lines or lines[0].strip() != "---":
        return {}, text
    end = next((i for i, line in enumerate(lines[1:], start=1) if line.strip() == "---"), None)
    if end is None:
        return {}, text
    data: dict[str, str] = {}
    key: str | None = None
    buf: list[str] = []
    for line in lines[1:end]:
        if key is not None and (line.startswith((" ", "\t")) or not line.strip()):
            buf.append(line.strip())
            continue
        if key is not None:
            data[key] = " ".join(p for p in buf if p)
            key, buf = None, []
        if not line.strip() or line.lstrip().startswith("#"):
            continue
        k, _, v = line.partition(":")
        v = v.strip()
        if v in (">", "|", ">-", "|-", ">+", "|+"):
            key = k.strip()
        else:
            data[k.strip()] = v.strip().strip('"').strip("'")
    if key is not None:
        data[key] = " ".join(p for p in buf if p)
    return data, "\n".join(lines[end + 1:])


def validate(skill_dir: Path) -> dict:
    report: dict = {"skill": str(skill_dir), "ok": False, "errors": [], "warnings": []}
    md = skill_dir / "SKILL.md"
    if not md.is_file():
        report["errors"].append("缺少 SKILL.md")
        return report
    fm, body = split_frontmatter(md.read_text(encoding="utf-8"))
    name, desc = fm.get("name", ""), fm.get("description", "")
    if not name:
        report["errors"].append("frontmatter 缺少必填字段 name")
    else:
        if len(name) > MAX_NAME:
            report["errors"].append(f"name 超过 {MAX_NAME} 字符: {len(name)}")
        if not NAME_RE.match(name):
            report["errors"].append("name 只能包含小写字母/数字/连字符，不得以连字符开头结尾或出现连续连字符")
        if name != skill_dir.name:
            report["errors"].append(f"name 与目录名不一致: name={name} dir={skill_dir.name}")
    if not desc:
        report["errors"].append("frontmatter 缺少必填字段 description")
    elif len(desc) > MAX_DESC:
        report["errors"].append(f"description 超过 {MAX_DESC} 字符: {len(desc)}")
    body_lines = body.splitlines()
    if len(body_lines) > MAX_BODY_LINES:
        report["warnings"].append(
            f"SKILL.md 正文 {len(body_lines)} 行，超过建议上限 {MAX_BODY_LINES} 行，考虑拆到 references/"
        )
    for target in LINK_RE.findall(body):
        if target.startswith(("http://", "https://", "#", "mailto:")):
            continue
        rel = target.split("#", 1)[0]
        if rel and not (skill_dir / rel).exists():
            report["errors"].append(f"引用文件不存在: {rel}")
    report["body_lines"] = len(body_lines)
    report["ok"] = not report["errors"]
    return report


def main(argv: list[str]) -> int:
    reports = [validate(Path(a)) for a in argv[1:]]
    print(json.dumps(reports, ensure_ascii=False, indent=2))
    bad = [r["skill"] for r in reports if not r["ok"]]
    print("校验结论:", "全部通过" if not bad else f"不通过: {bad}")
    return 1 if bad else 0


if __name__ == "__main__":
    sys.exit(main(sys.argv))
```

```text
CI 落地要点：
1. 校验脚本用退出码表达结果（有问题非 0），直接挂进 pre-commit 或流水线
2. 硬错误只保留规范里明确禁止的项（name 规则、必填字段、引用缺失），其余作为 warning，避免 CI 噪声
3. 正文行数用 warning 而非 error：它是建议阈值，不是规范硬约束
4. 把「引用文件是否存在」一起检查——渐进式披露的链路断了，正文里的路由就是死链
5. 校验脚本本身进版本库并配一条自测用例（故意写坏的样例目录），保证规则不被改松
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一句话能说清的知识不要做成 Skill：事实型约定放常驻规则文件，程序型多步流程才抽成 Skill。
2. `description` 用第三人称写「做什么 + 何时用」，并把业务方真实使用的关键词写进后半句的 Use when 里。
3. 目录名与 `name` 保持一致，改名时一起改，并在 CI 里加校验。
4. 自定义字段一律放 `metadata` 下，顶层只保留标准字段，保证同一份 Skill 在多个工具里都能加载。
5. 正文控制在 500 行以内，超了就按「路由留正文、细节进 references」拆分。
6. 能脚本化的判定下沉到 `scripts/`，正文只写「何时跑、判据是什么、失败了怎么办」；脚本代码不进上下文，只回输出。
7. 每个 Skill 装好后用一组真实提问验证触发（一句该触发、一句不该触发），不要假设描述写得够好。
8. 需要预授权工具或只能手动调用的行为，用实现提供的扩展字段表达，而不是把描述写模糊来间接控制。

### 踩坑记录

```text
坑 1：description 写成泛化短语，Skill 永远不触发
结论：明明装了 Skill，问相关问题时 Agent 完全不按流程走，也没有任何报错。
原因：自动触发唯一的依据就是 description，模型只能拿用户的问题和这一句话做相关性判断，泛化词匹配不到具体场景。
解法：改成「做什么 + 何时用 + 关键词」的句式，写完用带业务名词的真实问题试触发。
```

```text
坑 2：frontmatter 的 name 与目录名不一致
结论：某些实现里 Skill 直接不出现，另一些能加载但索引名字混乱。
原因：规范要求 name 与父目录名一致，很多实现按目录名建索引、按 name 做去重。
解法：把目录名当唯一真名，改名前先跑校验脚本；CI 里把这项设为硬错误。
```

```text
坑 3：把工具专属字段写在 frontmatter 顶层
结论：在某个工具里能加载，换一个工具就报 Unexpected key(s) in SKILL.md frontmatter。
原因：标准只定义 name / description / license / compatibility / metadata / allowed-tools，各实现另加的字段互不认账。
解法：版本、平台、作者一类信息放 metadata 下；确实需要工具专属字段时，接受它只对一个工具生效并在文档里注明。
```

```text
坑 4：正文里写「当前最新版本是 X」「截至某年推荐」
结论：Skill 半年后开始给出过时结论，而且没人知道该改哪一句。
原因：时间敏感信息被写进了长期复用的资产。
解法：把易变内容挪到 references/ 并标注核对日期，或改成「以官方文档为准 + 核对步骤」的形式。
```

```text
坑 5：以为装了 Skill 就有了权限
结论：流程跑到一半调用某个工具被拒，或者工具列表里根本没有它。
原因：Skill 只是指令，不注册工具、不授予权限；工具能力来自工具集与 MCP 连接。
解法：Skill 里显式写明用哪个工具（MCP 工具用全限定名），权限与连接在工具侧解决；需要预授权时用 allowed-tools 一类扩展字段，且只对有该字段的实现有效。
```

```text
坑 6：同一份流程同时维护三份副本
结论：Claude Code 里的 Skill 改了，Hermes 里的还是老版本，行为不一致且长期没人发现。
原因：每个工具各有自己的 skill 目录，直接复制粘贴必然漂移。
解法：源头放版本库，工具目录用软链指向同一份；校验脚本在 CI 里跑一份，装完用同一组问题对两个工具各验一次。
```
