## 概述

技能写不好通常不是因为内容不专业，而是因为踩了四个反复出现的结构性错误：把太多东西塞进一个技能、没写清什么时候该用它、同一个任务有两条技能在讲、以及技能正文与磁盘上真实存在的脚本和文件脱节。它们的共同特征是**不报错**——技能照常加载，模型照常执行一条错误或过时的流程，直到某次任务失败才被发现。这一篇逐个拆开这四类反模式，给出识别方法与改法。

```text
全篇主线：
1. 万能 Skill —— 一个技能包住整条业务线，代价是触发歧义与上下文膨胀
2. 触发条件 —— description 是唯一触发依据，缺"何时用/何时不用"就等于随机触发
3. 冲突 —— 同名与语义重叠两类，检测要机械、处置要明确优先级
4. 脱节 —— 引用的文件、命令、版本与磁盘现实不一致，靠 CI 兜住
5. 自检 —— 四类反模式都能用只读脚本筛出候选，再人工判断
```

## 万能 Skill：越包越不可用

**症状**：一个技能叫 `ops-everything` / `dev-workflow` / `通用助手`，正文覆盖发布、回滚、告警、值班、周报、数据库、环境搭建；description 里出现「anything」「所有」「各种」这类词；正文用二级标题硬分成十几节。

代价有三层，而且都能量化：

| 代价 | 机制 | 可观察现象 |
|------|------|-----------|
| 触发歧义 | description 无法同时覆盖所有场景，模型只能按最像的那个词匹配 | 该触发时不触发，不该触发时触发 |
| 上下文膨胀 | 技能被加载时整篇进上下文；常驻的清单部分也占预算 | 加载后可用上下文变少，长任务更容易压缩 |
| 无法验证 | 十几节流程没有共同的成功判据 | 执行完没人知道是否做对 |

上下文预算是硬约束，各工具都有明确机制：Claude Code 里每个技能的 listing 每轮都进上下文（用 `/skill-doctor` 看每条技能的成本与使用次数）；Codex 的技能列表最多占模型上下文窗口的约 2%（窗口未知时按 8000 字符算），技能多的时候**先截断 description**；Hermes 的技能索引常驻、正文按需加载（渐进式披露）。所以「一个技能什么都干」在任何一个工具上都会先撞到预算墙。

改法是把「业务线」拆成「可判定的流程」。拆的判断标准：**能各自回答"做完的验收标准是什么"**。

```markdown
# 反例：一个技能包整条业务线

---
name: ops-everything
description: "Use for anything related to operations: deployments, rollbacks, alerts, on-call, weekly reports, database, environment setup."
---

## 发布
...
## 回滚
...
## 告警处理
...
## 值班交接
...
## 周报
...
## 数据库变更
...
```

```text
拆成（每个都有独立触发条件与验收标准）：
- deploy-service        何时用：发版/回滚；验收：指标回到基线 + 回滚路径演练过
- incident-response     何时用：告警触发/线上故障；验收：影响面收敛 + 复盘归档
- oncall-handover       何时用：交接班；验收：未决事项有承接人
- weekly-report         何时用：写周报；验收：按模板字段齐备
- db-change-review      何时用：schema 变更评审；验收：清单 8 项 + 行数判定
```

拆完之后，跨技能共享的稳定规则（术语、环境名、通用检查）单独抽到一个窄技能里，让其它技能用 `related_skills` 引它，而不是各自复制：

```yaml
---
name: platform-conventions
description: "Use when any platform workflow needs the shared naming, environment and approval conventions of this org."
version: 1.0.0
metadata:
  hermes:
    tags: [conventions]
---
```

## 缺少触发条件：description 失效

**症状**：description 只写「做什么」（`发布服务`、`Helps with Docker`），不写「何时用/何时不用」；或者写成一句业务介绍（`本技能沉淀了团队多年的运维经验`）。结果是模型无法判断何时加载它。

规范层面，`description` 是**唯一**的自动触发依据：模型平时只看到 name + description，判断相关才读正文。所以 description 必须回答三个问题：

```text
1. 触发场景：用户说什么/做什么时该用它（含用户可能用的词）
2. 边界：什么情况看似相关但不该用它（防止抢别的技能的活）
3. 交付物：用它之后能得到什么（帮助模型判断"值不值得加载"）
```

写法对照：

| 反例 | 改后 | 差别 |
|------|------|------|
| `帮助处理 Docker 相关任务` | `Use when building, debugging or optimizing Dockerfiles and Compose stacks: multi-stage build, layer caching, image size. Not for Kubernetes manifests.` | 有了关键词、边界与交付物 |
| `发布流程` | `Use when deploying or rolling back a backend service in the prod cluster: pre-flight checks, staged rollout, rollback. Do not use for infra change or DB migrations.` | 明确了动作与不适用范围 |
| `数据库相关最佳实践` | `Use when reviewing a schema change before it ships: lock risk, index strategy, rollback script, backfill plan.` | 从"知识主题"变成"任务" |

**验证触发最省事的办法是拿真实 prompt 试**：写三条「应该触发」、两条「不该触发」的 prompt，逐条看技能是否被选中。Codex 文档给的建议也是同一条：拿测试 prompt 对着 description 验证触发行为。别只读着觉得"应该能触发"。

批量筛出可疑 description 用只读脚本即可，本机实测（扫描 `~/.hermes/skills`）：

```python
#!/usr/bin/env python3
"""反模式自检：description 缺触发词/缺否定边界/超长，以及正文引用文件是否存在。只读。"""
import argparse
import os
import re
from collections import Counter
from pathlib import Path

# 触发导向词：英文技能写 Use when，中文技能写"当…时/需要…时"
TRIGGER_HINTS = ("use when", "when the user", "use this", "use for", "trigger",
                 "当用户", "需要", "时使用", "时调用")
REF_RE = re.compile(r"`((?:references|templates|scripts|assets)/[^`\s]+)`")


def read_front_description(text: str) -> str:
    in_front = False
    for line in text.splitlines():
        if line.startswith("---"):
            in_front = not in_front
            continue
        if in_front and line.startswith("description:"):
            return line.split(":", 1)[1].strip().strip('"').strip("'")
    return ""


def walk_skills(root: Path):
    for skill_md in root.rglob("SKILL.md"):
        rel = skill_md.relative_to(root)
        if any(p in (".archive", ".curator_backups", ".hub") for p in rel.parts):
            continue
        yield skill_md


def main() -> None:
    ap = argparse.ArgumentParser()
    ap.add_argument("--skills-root", default=os.path.expanduser("~/.hermes/skills"))
    ap.add_argument("--limit", type=int, default=8)
    args = ap.parse_args()
    root = Path(args.skills_root).expanduser()

    stats = Counter()
    no_trigger, no_negative, broken_refs, long_desc = [], [], [], []
    total = 0
    for skill_md in walk_skills(root):
        total += 1
        text = skill_md.read_text(encoding="utf-8", errors="ignore")
        desc = read_front_description(text)
        name = skill_md.parent.name
        stats["无 description"] += (not desc)
        if desc:
            low = desc.lower()
            if not any(h in low for h in TRIGGER_HINTS):
                no_trigger.append((name, len(desc)))
            if not re.search(r"not for|do not use|don't use|不适用|不要用于", low):
                no_negative.append(name)
            if len(desc) > 1024:
                long_desc.append((name, len(desc)))
        for ref in set(REF_RE.findall(text)):
            if not (skill_md.parent / ref).exists():
                broken_refs.append((name, ref))

    print(f"技能树：{root}")
    print(f"扫描 SKILL.md：{total}")
    print(f"其中无 description：{stats['无 description']}")
    print(f"\n[1] description 缺触发导向词（Use when / 当…时）：{len(no_trigger)}")
    for name, ln in no_trigger[: args.limit]:
        print(f"    {name:44} desc_len={ln}")
    print(f"\n[2] description 缺否定边界（not for / 不适用）：{len(no_negative)}")
    for name in no_negative[: args.limit]:
        print(f"    {name}")
    print(f"\n[3] description 超长（> 1024 字符，可能被截断）：{len(long_desc)}")
    for name, ln in long_desc[: args.limit]:
        print(f"    {name:44} desc_len={ln}")
    print(f"\n[4] 正文引用的相对支持文件不存在：{len(broken_refs)}")
    for name, ref in broken_refs[: args.limit]:
        print(f"    {name:44} -> {ref}")


if __name__ == "__main__":
    main()
```

读这份报告要注意两点：`[1]`、`[2]` 是**启发式**统计，命中率高是词典窄导致的（很多中文技能用别的措辞写触发条件），它的用途是从上千条里挑出最可疑的几十条人工复核，不是自动判罚；`desc_len=1`、`desc_len=2` 这类极短 description 才是真问题（同一技能在不同工具里可能连 name 都识别不出）。`[4]` 里也会混入形如 `references/<module>/SKILL.md`、`references/lang-{language}.md` 的模板占位符，属于正常写法，需要人工区分。

## 多个 Skill 冲突：谁赢谁输

**症状**：同一个任务被两条技能同时命中；或者模型一会儿按 A 流程执行、一会儿按 B 流程执行；或者你改了技能但行为没变（因为生效的是另一个作用域里的同名技能）。

冲突分四类，处置方式完全不同：

| 类型 | 例子 | 检测方式 | 处置 |
|------|------|----------|------|
| 同名覆盖 | 项目和全局各有一个 `deploy` | 跨作用域比名字 | 明确优先级，或改名加前缀 |
| 同义重叠 | `database-design` 与 `database-design-hardened` | description 关键词归并 | 合并成一条，另一条归档 |
| 上下游重叠 | `deploy-service` 里也写了「先做数据库变更评审」 | 正文关键词交叉 | 只保留引用，步骤留在原技能 |
| 版本分叉 | `deploy-service` 与 `deploy-service-legacy` | 名字后缀 + 更新时间 | 保留新版，旧版内容并入 references 后归档 |

**覆盖优先级必须先背下来**，否则排查会绕远路：

```text
Hermes      : project（仓库内，需 trust） > local（~/.hermes/skills/） > skills.create_dir > 外部目录
Claude Code : enterprise > personal(~/.claude/skills/) > project(.claude/skills/)
Codex       : 同名技能不合并，两个都可能出现在选择器里（同名即歧义，不会自动裁决）
```

也就是说，**同名冲突在 Hermes 里会静默按优先级裁决，在 Codex 里会变成"两个都出现"**，同一个仓库名在两边的表现不一样，所以最稳的做法是不制造同名：技能名带领域或仓库前缀。

机械检测只需要两步：先按名字跨目录比，再按 description 关键词归并。本机真实跑出来的同义重叠候选（取自前一节脚本的归并段）：

```text
database design              -> database-design, database-design-hardened
expert kubernetes            -> kubernetes, kubernetes-architect
code refactoring             -> code-refactoring-refactor-clean, codebase-cleanup-refactor-clean
delegate coding              -> blackbox, coding-agent, coding-agent-claude-print, coding-agent-local
```

前三条是典型的「同一件事两份实现」，最后一条是「恰好共享词但职责不同」——判断标准始终是：**两条技能被同一个请求同时命中时，会不会给出互相矛盾的步骤**。会矛盾就必须处置；不矛盾但高度重叠，也应当合并以减少触发噪音。

跨作用域同名检测（只读）：

```shell
# 用户级与项目级的同名技能
comm -12 \
  <(find ~/.hermes/skills -name SKILL.md -printf '%h\n' | xargs -n1 basename | sort -u) \
  <(find ./.hermes/skills ./.agents/skills -name SKILL.md -printf '%h\n' 2>/dev/null | xargs -n1 basename | sort -u)
```

处置决策树：

```text
两条技能冲突
├─ 名字相同？
│   ├─ 是 → 是"同名但不同职责" → 改名加前缀；是"新旧版本" → 保留新、归档旧
│   └─ 否 → 看触发是否重叠
│       ├─ 重叠且矛盾 → 合并为一条（整包处理支持文件）
│       ├─ 重叠但不矛盾 → 抽公共规则进窄技能，两边引用
│       └─ 只是共享词 → 保持，两边都补"不适用"边界
└─ 无论哪种 → 处置后必须用真实 prompt 复测触发，确认只命中预期的技能
```

## 文档与实现脱节

**症状**：技能写于三个月前，正文里的脚本已被重写、命令参数已改、引用的 `references/` 文件已删、示例输出早就不匹配。这类问题最隐蔽，因为 SKILL.md 读起来完全自洽。

四种常见形态与对应的机械检查：

| 形态 | 检查方法 |
|------|----------|
| 引用文件不存在 | 正则抓正文里的 `references/`、`scripts/`、`templates/`、`assets/` 路径，逐个查文件是否存在 |
| 命令/工具不存在 | 抽取正文提到的工具名，对照本机 `which`（注意：只在需要时才装工具不算错） |
| 参数已变 | 对可执行的脚本做冒烟运行，或用 `--help` 比对正文写的参数 |
| 版本号没抬 | 有内容改动但 `version` 未变，或缺 CHANGELOG 条目 |

引用与命令检查可以合成一个 CI 闸门（在上面自检脚本的 `[4]` 段基础上加豁免规则）：

```python
#!/usr/bin/env python3
"""CI: 技能正文引用的支持文件必须真实存在；模板占位符豁免。"""
import re
import sys
from pathlib import Path

REF_RE = re.compile(r"`((?:references|templates|scripts|assets)/[^`\s]+)`")
# 形如 references/<module>/SKILL.md、references/lang-{language}.md 的是模板占位符，豁免
PLACEHOLDER = re.compile(r"[<>{}*]|\.\.\.|\\$")

bad = []
for skill_md in sorted(Path(".").rglob("SKILL.md")):
    rel_parts = skill_md.relative_to(".").parts
    if any(p in (".git", ".archive", ".curator_backups") for p in rel_parts):
        continue
    text = skill_md.read_text(encoding="utf-8", errors="ignore")
    for ref in sorted(set(REF_RE.findall(text))):
        if PLACEHOLDER.search(ref):
            continue
        if not (skill_md.parent / ref).exists():
            bad.append(f"{skill_md}: 引用不存在 {ref}")

if bad:
    print("\n".join(bad))
    sys.exit(1)
print("技能引用检查通过")
```

```text
$ python3 ci/check_skill_refs.py
skills/<skill-a>/SKILL.md: 引用不存在 references/crd_design.md
skills/<skill-b>/SKILL.md: 引用不存在 scripts/fetch_player_photos.py
（补齐文件或删除引用后通过）
```

（这是该脚本在本机真实报出过的同类问题：上面自检输出 `[4]` 段列出的 `kubernetes-operator`、
`worldcup-2026-scores` 等条目；CI 里的技能库不同，报出的条目随之不同。）

「文档与实现脱节」还有一个反向版本：**技能正文讲的流程已经改了，但技能没改**。这类删不掉也查不出，唯一可行的手段是把「流程变更必须同步改技能」写进变更流程（例如 CI 改了发布命令时，同一个 PR 必须动到对应技能），靠制度和评审兜住。

## 反模式速查与自检清单

| 反模式 | 症状 | 机械检测 | 改法 |
|--------|------|----------|------|
| 万能 Skill | 一个技能覆盖整条业务线，正文十几个二级标题 | 正文长度 + 二级标题数超阈值 | 拆成若干「有独立验收标准」的技能 |
| 无触发条件 | description 只写主题，不含"何时用" | `[1]` 缺触发词统计 | 补触发场景 + 用户可能用的词 |
| 无边界 | description 没有"不适用" | `[2]` 缺否定边界统计 | 加 `Not for ...` / `不适用于 ...` |
| 同名冲突 | 跨作用域同名，行为随目录变 | `comm -12` 跨目录同名 | 改名加前缀，或明确优先级 |
| 语义重叠 | 两条技能讲同一件事 | description 关键词归并 | 合并，并把支持文件整包处理 |
| 死链接 | 正文引用文件不存在 | `[4]` 引用检查 | 补文件或删引用，进 CI |
| 叙事化 | 正文是事故经过/历史故事 | 命中"上周/某次/经过"等词 | 压成规则 + 一句机制 |
| 无验证 | 没有"怎么确认成功"这一段 | 缺 `## 验证` / `## Verification` | 补可观察的验收判据 |
| 密钥入库 | SKILL.md 或示例里出现真实 token | grep 常见前缀（`sk-`、`ghp_`、`AKIA`） | 改用 `required_environment_variables` 声明 |

一次性自检可以这样跑（只读、无副作用）：

```shell
# 1) description 与引用文件自检
python3 tools/skill_lint.py --skills-root ~/.hermes/skills

# 2) 跨作用域同名技能
comm -12 \
  <(find ~/.hermes/skills -name SKILL.md -printf '%h\n' | xargs -n1 basename | sort -u) \
  <(find ./.hermes/skills ./.agents/skills -name SKILL.md -printf '%h\n' 2>/dev/null | xargs -n1 basename | sort -u)

# 3) 疑似密钥（示例，不含真实值）
grep -rEn 'sk-[A-Za-z0-9]{20,}|ghp_[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}' ~/.hermes/skills --include=SKILL.md

# 4) 超长技能（正文行数）
find ~/.hermes/skills -name SKILL.md -exec wc -l {} + | sort -rn | head -10
```

## 应用场景实战

### 场景一：把「万能运维技能」拆成三个可判定的技能

背景：团队有一条 380 行的 `ops-everything`，实际只用其中三段，且常常在「只是问个告警含义」的时候被整篇加载。目标是把常用三段拆出来，其余内容保留可查。

第一步，先量化问题（拆之前留证据，拆之后对比）：

```shell
wc -l ~/company-skills/skills/ops-everything/SKILL.md
grep -c '^## ' ~/company-skills/skills/ops-everything/SKILL.md
```

```text
<总行数>
<二级标题数>
```

```text
拆之前的代价（可观察）：
- description 覆盖十余个主题，模型按最像的词匹配，经常只问告警含义也触发整篇
- 加载一次正文几百行，长任务里明显占用上下文
- 十几段没有共同验收标准，执行完无法判断对错
```

第二步，按「独立验收标准」切成三个技能，其余内容下沉到 references：

```text
company-skills/skills/
├── deploy-service/                 # 发布与回滚
│   ├── SKILL.md
│   ├── scripts/deploy_check.sh
│   └── references/rollback-history.md
├── incident-response/              # 告警与故障处理
│   ├── SKILL.md
│   └── references/alert-catalog.md  # 原 ops-everything 的"告警含义"一节
└── oncall-handover/                # 值班交接
    ├── SKILL.md
    └── references/handover-template.md
```

拆分后的 `deploy-service` 只保留一条主流程与验收标准：

```yaml
---
name: deploy-service
description: "Use when deploying or rolling back a backend service in the prod cluster: pre-flight checks, staged rollout, rollback. Not for infra change or DB migrations."
version: 2.0.0
---

# 服务发布与回滚

## 前置条件

- 已确认目标版本镜像与配置 diff
- 依赖服务健康度检查通过

## 步骤

1. `bash ${HERMES_SKILL_DIR}/scripts/deploy_check.sh <service> <version>`
2. 生成发布计划（灰度比例、观察窗口、回滚阈值）交负责人确认
3. 按计划灰度，每阶段贴关键指标
4. 阈值突破立即回滚，并在复盘记录触发原因

## 验证

- 发布后 10 分钟 P99 与错误率回到基线
- 回滚路径在预发环境演练过至少一次
```

第三步，迁移与验证。拆分属于结构性重写，用整篇替换而不是 patch；旧技能先归档不删除，给一个季度的找回窗口：

```shell
git -C ~/company-skills mv skills/ops-everything/skills/deploy-service skills/deploy-service
git -C ~/company-skills add -A
git -C ~/company-skills commit -m "refactor: 拆分 ops-everything 为 deploy-service / incident-response / oncall-handover"

# 旧目录只留索引说明，引用已迁移内容，避免"看似还在用"
hermes curator archive ops-everything     # 归档（可 restore）
hermes curator list-archived | grep ops-everything
```

```text
拆分后的验收（逐条勾）：
- [ ] 三条技能的 description 都含"何时用"与"不适用"
- [ ] 用 5 条真实 prompt 复测触发，只命中预期的那一条
- [ ] 每条技能都有 ## 验证 段，且判据可观察
- [ ] 相对引用（references/、scripts/）逐条点开存在
- [ ] 旧技能归档且 CHANGELOG 记录了内容去向
```

### 场景二：把冲突与脱节检测接进 CI

背景：技能库 60 条技能，多人维护，最近两次事故都源于「技能里写的命令早就变了」。目标是让这类问题在合并前就被拦住。

第一步，仓库里放两个检查脚本（引用检查、跨作用域同名检查），并写进 CI：

```yaml
# .github/workflows/skills-ci.yml
name: skills-ci
on:
  pull_request:
    paths:
      - "skills/**"
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install pyyaml
      - name: frontmatter 与目录名校验
        run: python3 ci/check_skills.py
      - name: 正文引用文件存在性
        run: python3 ci/check_skill_refs.py
      - name: 跨作用域同名检测
        run: python3 ci/check_duplicate_names.py
```

第二步，`check_duplicate_names.py` 用纯标准库实现同名与近似重复检测，避免依赖外部服务：

```python
#!/usr/bin/env python3
"""CI: 同一技能库内出现同名或高度重叠的技能名时失败。"""
import re
import sys
from collections import defaultdict
from pathlib import Path


def norm(name: str) -> str:
    """去掉常见的新旧版本后缀，用于发现 legacy / hardened / v2 这类分叉。"""
    return re.sub(r"(-legacy|-hardened|-v\d+|-old|-new|-free|-pro)$", "", name.lower())


buckets = defaultdict(list)
for skill_md in sorted(Path("skills").glob("*/SKILL.md")):
    buckets[norm(skill_md.parent.name)].append(skill_md.parent.name)

dups = {k: v for k, v in buckets.items() if len(v) > 1}
if dups:
    for key, names in sorted(dups.items()):
        print(f"疑似同名或分叉：{key} -> {', '.join(sorted(names))}")
    sys.exit(1)
print("技能命名检查通过")
```

```text
$ python3 ci/check_duplicate_names.py
疑似同名或分叉：database-design -> database-design, database-design-hardened
（人工确认后合并或改名，CI 才通过）
```

第三步，处理结论必须落到仓库里，不能只在 Slack 上说。合并或改名的 PR 里附一张对照表：

```markdown
| 检出 | 类型 | 决策 | 依据 |
|------|------|------|------|
| database-design / database-design-hardened | 同义重叠 | 合并到 database-design，hardened 内容并入 references/enforcement.md | 两者对同一任务给出不同检查项 |
| deploy-service-legacy | 版本分叉 | 归档，回滚细节并入 deploy-service/references/rollback-history.md | 旧流程对应服务已下线 |
```

```text
这套 CI 拦住的三类问题（合并前可见）：
1. 引用不存在（死链接）：check_skill_refs.py
2. 命名分叉与同名：check_duplicate_names.py
3. frontmatter 缺失或目录名不一致：check_skills.py
仍然拦不住的：description 写得不够窄（需人工评审 + 真实 prompt 复测）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一个技能只做一件事，判据是「能不能写出独立、可观察的验收标准」；写不出来的内容不属于这个技能。
2. description 三段式：触发场景（含用户可能用的词）+ 不适用范围 + 交付物，尽量把关键词前置，以应对各工具的截断策略。
3. 技能名带领域或仓库前缀，从命名层面避免跨作用域同名；同名在 Hermes 会静默按优先级裁决，在 Codex 会两个都出现。
4. 用真实 prompt 复测触发：三条应命中、两条不该命中，改完 description 就复测，别只靠读。
5. 把「引用文件存在」「目录名与 name 一致」「疑似同名分叉」三类检查写进 CI，机械问题不靠人眼。
6. 正文里的命令与示例输出标注来源与时间，工具升级后优先检查这几处，它们是脱节的高发区。
7. 常见反模式自检脚本放进工具目录、只读运行，每月跑一次；脚本报出的是候选，处置仍需人工判断。
8. 结构性改写（拆分、合并）走整篇替换 + 归档旧技能，不要一边 patch 一边搬文件，容易出现半迁移状态。

### 踩坑记录

```text
坑 1：把「万能技能」按主题拆成十几条
结论：触发点反而更多更乱，模型在不同任务间来回误触发。
原因：拆分依据用了"主题"而不是"可判定的流程"，同一个任务会同时命中多条。
解法：按"验收标准"拆（发布 / 回滚 / 告警处置各一条），跨技能的公共规则抽到独立的窄技能里被引用。

坑 2：description 只写主题不写场景，测试时"看着挺合理"
结论：上线后该触发时不触发，团队以为"模型不听话"。
原因：description 是唯一触发依据，主题词与用户实际说的话对不上。
解法：把用户会说的动作词写进 description（deploy、rollback、告警、值班交接），再用真实 prompt 复测。

坑 3：跨作用域同名技能，改了不生效
结论：项目里改了流程，agent 仍按旧流程执行，排查半天找不到生效的那份文件。
原因：作用域优先级（project > local > 外部目录）静默裁决，被覆盖的那份照样在磁盘上、看着也是最新的。
解法：先做跨目录同名检测（comm -12 或 CI 里的同名检查），技能名加前缀，从根本上不制造同名。

坑 4：CI 引用检查把模板占位符当死链接
结论：CI 一直红，团队索性把检查关掉，真死链接也一起溜了过去。
原因：`references/<module>/SKILL.md`、`references/lang-{language}.md` 这类占位符不是真实路径。
解法：检查脚本加占位符豁免（含 <>、{}、*、... 的跳过），只对具体文件路径报错，避免闸门被噪音废掉。

坑 5：清理"文档与实现脱节"时只改了正文，没动脚本
结论：正文写"脚本会先做 dry-run"，脚本里根本没有 dry-run 参数，执行即生效。
原因：技能是整包，正文与脚本、references 是一组契约。
解法：把它当代码评审：改命令就同步改脚本与示例输出，最省事的办法是给关键脚本写一个只读冒烟检查接进 CI。

坑 6：脚本自检报了几百条就大规模整改
结论：花了一周改 description，触发行为并没有变好，反而把一些正常技能改坏。
原因：启发式统计命中率高不等于都是问题（词典窄、中文措辞差异、模板占位符都会命中）。
解法：先抽最可疑的几十条（极短 description、超长、明确同名）人工复核，改完复测触发；
      把它当"筛选器"而不是"判罚器"。
```
