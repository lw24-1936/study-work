## 概述

技能库的失效方式和代码库不一样：代码坏了会报错，技能坏了只是**悄悄不再被触发**，或者更糟——被触发但给出过时流程，模型照做，问题出现在生产环境。维护工作的核心就是把这种「沉默的失效」变成可见信号：谁在用、多久没用、上游内容变了没、正文里的命令还存不存在、同一件事是不是有两个技能在说。Hermes 把其中一部分做成了后台机制（curator + 使用遥测），其余部分要靠版本约定、回写习惯和定期巡检补上。

```text
全篇主线：
1. 版本 —— frontmatter version + CHANGELOG + git，是"改了什么"的可追溯性
2. 失效 —— 遥测（use/view/last_activity）+ 生命周期状态机 + 外部依赖可用性检查
3. 回写 —— 踩坑立刻 patch 成规则（结论+机制），常驻规则进 SKILL.md，细节进 references/
4. 清理 —— 合并要整包处理；归档可恢复、自动删除永不发生
5. 节奏 —— 日常回写 + 每周检查上游 + 每季度巡检与归档，形成闭环
```

## 版本管理与变更记录

技能也是被执行的资产，所以要能回答三个问题：当前是哪个版本、为什么改、改了之后谁需要更新。三件工具组合起来就够了：frontmatter 的 `version` 给人看，`CHANGELOG.md` 给评审看，git 给机器看。

```yaml
---
name: db-change-review
description: "Use when reviewing or authoring a database schema change before it ships to prod."
version: 2.3.1          # 语义化版本：破坏性流程变更抬主版本
author: dba-guild
license: MIT
platforms: [linux, macos]
metadata:
  hermes:
    tags: [database, review, governance]
    related_skills: [deploy-service]
---
```

配套的变更记录放在技能目录里，只记「行为上有什么不同」，不抄提交历史：

```markdown
<!-- skills/db-change-review/CHANGELOG.md -->
## 2.3.1 - 2026-10-11
- 修复：大表加索引的步骤改为先 CONCURRENTLY，避免评审通过后仍锁表

## 2.3.0 - 2026-09-27
- 新增：需要回滚脚本的判定条件（写操作 + 影响行数阈值）
- 变更：检查清单从 6 项调整为 8 项，历史实例迁移见 references/migration-2.3.md

## 2.2.0 - 2026-08-30
- 新增：跨库变更时的负责人确认环节
```

本机可用的版本相关命令（`hermes skills --help` 的真实子命令）：

```shell
hermes skills list --source hub      # 只看 Hub 安装的技能
hermes skills check                  # 检查已装 Hub 技能上游是否有更新
hermes skills update                 # 拉取上游更新
hermes skills list-modified          # 列出被我改过的自带技能（hermes update 会保留）
hermes skills diff <name>            # 看我的改动与官方版本的差异
hermes skills reset <name>           # 清掉"用户已修改"标记，让更新能覆盖
hermes skills reset <name> --restore # 恢复官方版本（丢弃本地修改）
hermes skills snapshot export setup.json   # 导出技能配置快照
```

插件与插件包的版本锁定方式不同，靠 revision 而不是语义化版本：

```json
// ~/.hermes/plugins/.install-metadata.json（真实结构）
{
  "ponytail": {
    "pinned": false,
    "revision": "e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156",
    "source": "https://github.com/DietrichGebert/ponytail.git"
  }
}
```

```shell
hermes plugins check-updates         # 只读检查
hermes plugins update                # 拉取更新
hermes plugins pack export           # 把当前安装集导出为钉住 commit SHA 的 YAML
hermes plugins pack install pack.yaml
```

```text
版本策略（三条就够）：
- 技能：语义化版本，破坏性流程变更抬主版本，CHANGELOG 写"行为差异"
- 仓库内技能：git 提交信息用 fix/feat/docs 前缀 + 技能名，便于按技能过滤历史
- 插件与包：不写语义化版本，钉 revision（commit SHA），发布即固定
```

## 失效检测与生命周期

Hermes 为每个技能维护使用遥测，文件是 `~/.hermes/skills/.usage.json`，字段结构本机实测如下：

```json
{
  "07-risk-dashboard": {
    "archived_at": null,
    "created_at": "2026-09-24T19:59:46.150327+00:00",
    "created_by": "installed",
    "last_patched_at": null,
    "last_used_at": null,
    "last_viewed_at": null,
    "patch_count": 0,
    "pinned": false,
    "state": "active",
    "use_count": 0,
    "view_count": 0
  }
}
```

这些字段支撑三种检测：

| 信号 | 字段 | 说明 |
|------|------|------|
| 闲置 | `last_used_at` / `last_viewed_at` | 多久没被加载过；`view_count` 计入显式查看 |
| 漂移 | `patch_count` / `last_patched_at` | 频繁打补丁说明流程本身不稳定，值得重写而不是继续修 |
| 来源 | `created_by` / `state` / `archived_at` | `agent`、`learn`、`installed` 与 `null`（无来源标记）决定谁负责维护 |

Hermes 的 curator 是围绕这些字段的后台维护任务，只处理**它认为归自己管的技能**（默认是 `created_by: agent` 的技能，Hub 安装的技能永远不碰；`prune_builtins: true` 时才管闲置的内置技能）。本机实测状态：

```text
$ hermes curator status
curator: ENABLED
  runs:           12
  last run:       6d ago
  last summary:   auto: 3 marked stale, 5 archived; llm: skipped (consolidation off)
  interval:       every 7d
  stale after:    14d unused
  archive after:  30d unused
  consolidate:    off (prune-only; LLM merge pass opt-in)

curator-managed skills: 16 total  (agent-created=16  bundled=0)
  active     13
  stale      3
  archived   0

unmanaged (no provenance marker): 53 total
  pre-dates marker    18
  foreground-created  35
  never auto-staled or archived — `hermes curator adopt <name>` hands one over
```

生命周期是单向的、可逆的：`active → (闲置 14 天) stale → (闲置 30 天) archived`（天数与间隔来自 `curator.*` 配置），pinned 技能豁免一切自动流转，归档可以 `restore` 回来，**curator 从不自动删除**，最坏结果是把技能挪进 `~/.hermes/skills/.archive/`（该目录不进提示、不参与索引）。

```yaml
# ~/.hermes/config.yaml（片段，curator 默认值）
curator:
  enabled: true
  interval_hours: 168        # 每 7 天一轮
  min_idle_hours: 2          # 会话内至少闲置多久才认为"本轮没在用"
  stale_after_days: 14
  archive_after_days: 30
  consolidate: false         # LLM 归并pass，默认关（只做 prune）
  prune_builtins: false      # 是否连闲置的内置技能也归档
```

```shell
hermes curator status                # 一次看全：运行历史、状态分布、最活跃/最冷清
hermes curator pin <name>            # 关键技能钉住，免于自动流转
hermes curator list-unmanaged        # 没有来源标记、curator 不敢动的技能
hermes curator adopt <name>          # 明确交给 curator 管理
hermes curator archive <name>        # 手工归档（进 .archive/，不进提示）
hermes curator restore <name>        # 恢复归档
hermes curator prune                 # 批量归档闲置超过阈值的
hermes curator backup / rollback     # 手工快照与回滚
hermes curator ledger                # 追加式改动台账
```

除了遥测，还有三类「外部失效」遥测看不出来，必须自己查：

```text
1. 依赖失效：技能正文里的命令、脚本依赖的工具在本机不存在或改了参数
2. 引用失效：SKILL.md 指向的 references/、templates/ 文件被删或改名
3. 上游失效：流程已经变了（CI 步骤、环境名、发布通道），但技能正文没改
```

这三类可以用一个只读巡检脚本机械地筛一遍，下面是本机跑过的真实脚本（只读、无副作用）：

```python
#!/usr/bin/env python3
"""技能库巡检：输出待归档 / 从未使用 / 疑似重复 / 依赖缺失 四类清单。只读。"""
import argparse
import json
import os
import re
import shutil
from collections import defaultdict
from datetime import datetime, timezone
from pathlib import Path

TOOLS = ("git", "gh", "docker", "kubectl", "helm", "terraform", "npm", "pnpm",
         "uv", "pip3", "ffmpeg", "jq", "curl", "node", "ollama", "playwright")


def days_since(ts):
    return None if not ts else (datetime.now(timezone.utc) - datetime.fromisoformat(ts)).total_seconds() / 86400


def walk_skills(root):
    for skill_md in root.rglob("SKILL.md"):
        rel = skill_md.relative_to(root)
        if any(part in (".archive", ".curator_backups", ".hub") for part in rel.parts):
            continue
        yield skill_md


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--skills-root", default=os.path.expanduser("~/.hermes/skills"))
    ap.add_argument("--idle-days", type=int, default=30)
    args = ap.parse_args()
    root = Path(args.skills_root).expanduser()
    usage_file = root / ".usage.json"
    usage = json.loads(usage_file.read_text(encoding="utf-8")) if usage_file.exists() else {}

    archive_candidates, merge_buckets, missing_cmds, never_used = [], defaultdict(list), defaultdict(list), []
    live = 0
    for skill_md in walk_skills(root):
        live += 1
        name = skill_md.parent.name
        meta = usage.get(name, {})
        idle = days_since(meta.get("last_used_at") or meta.get("last_viewed_at"))
        if meta and (meta.get("state") == "stale" or (idle is not None and idle >= args.idle_days)):
            archive_candidates.append((name, round(idle, 1) if idle else None, meta.get("state")))
        if meta and meta.get("use_count", 0) == 0 and meta.get("view_count", 0) == 0:
            never_used.append(name)

        text = skill_md.read_text(encoding="utf-8", errors="ignore")
        desc = ""
        for line in text.splitlines()[:12]:
            if line.startswith("description:"):
                desc = line.split(":", 1)[1].strip().strip('"').lower()
                break
        key = " ".join(re.findall(r"[a-z]{4,}", desc)[:2])       # 粗粒度归并键
        if key:
            merge_buckets[key].append(name)

        for cmd in TOOLS:                                        # 依赖缺失粗筛
            if re.search(rf"\b{re.escape(cmd)}\b", text) and shutil.which(cmd) is None:
                missing_cmds[cmd].append(name)

    print(f"技能树：{root}")
    print(f"使用遥测条目：{len(usage)}    live SKILL.md：{live}")
    print(f"\n[1] 待归档候选（state=stale 或闲置 >= {args.idle_days} 天）：{len(archive_candidates)}")
    for name, idle, state in sorted(archive_candidates, key=lambda x: -(x[1] or 0))[:5]:
        print(f"    {name:44} idle={idle}d state={state}")
    print(f"\n[2] 从未使用（use/view 均为 0）：{len(never_used)}")
    for name in never_used[:5]:
        print(f"    {name}")
    print("\n[3] 疑似重复（description 前两个实词相同）：")
    for key, names in sorted(merge_buckets.items()):
        if len(names) > 1:
            print(f"    {key:28} -> {', '.join(sorted(names)[:4])}")
    print("\n[4] 正文提到但本机不存在的命令（需人工判断是否真依赖）：")
    for cmd, names in sorted(missing_cmds.items()):
        print(f"    {cmd:24} 出现在 {len(names)} 条技能中，如 {names[0]}")


if __name__ == "__main__":
    main()
```

## 从踩坑回写经验

技能库的价值增长点几乎全部来自「刚踩完坑的那十分钟」。这段时间里你手上有三样东西：失败的原始输出、正确做法、以及一个已经存在的、需要被修正的技能。回写的动作就是把这三样压缩成**一条可复用规则**。

写法的硬要求（Hermes 的 skill 内容约定，本质是「教训不是日志」）：

| 该写 | 不该写 |
|------|--------|
| 规则 + 一句机制（为什么） | 事故经过、时间线、聊天记录 |
| 挂在受影响的那一步下面 | 单独开一节讲历史 |
| 一条规则说一次 | 同一规则在多个章节重复 |
| 常驻规则放 SKILL.md，细节放 `references/` | 把整篇长文档塞进 SKILL.md |

改现有技能时优先用 patch（定向替换），只有结构性重写才整篇替换：

```yaml
# 反例：把事故讲成故事，模型读完不知道要做什么
## 2026-10-09 的教训
上周二发布时我们忘了先建索引，导致大表锁了 40 分钟，值班同学被叫起来……

# 正例：规则挂在步骤下，含机制与判定条件
## 步骤 2：生成变更脚本
- 大表（行数 > 1000 万）加索引必须用 CREATE INDEX CONCURRENTLY，否则会持有写锁；
  判定行数用 references/table-size-check.md 的查询，先确认再生成脚本。
```

回写要选对落点，三档内容的归属不一样：

```text
SKILL.md 正文     —— 每次都适用的规则、判定条件、验证方式（常驻，进上下文）
references/       —— 按主题的长内容：决策表、配额表、供应商差异、历史迁移步骤
scripts/          —— 需要确定性行为的步骤（能跑就不要让模型复述）
```

一次真实的回写路径（含 agent 自维护与人工维护的分工）：

```shell
# 1) 先把失败证据落到技能里（patch 只改需要改的段落）
#    在会话里让 agent 用 skill_manage 打补丁，或自己编辑 SKILL.md
# 2) 记一条变更记录
#    CHANGELOG 里写"修复：..."，并在 git 提交信息带上技能名
git -C ~/company-skills commit -m "fix: db-change-review 大表加索引改为 CONCURRENTLY 并补判定查询"

# 3) 若这条技能归 curator 管，用台账核对改动是否被记录
hermes curator ledger | tail -5

# 4) 把"容易再犯"的信号补进校验（脚本能查的就别靠人记）
```

改动台账是追加式 JSONL，本机路径 `~/.hermes/skills/.curator_ledger.jsonl`，每条记录带 per-file 的 `{path, sha256}` 前后清单，内容按哈希去重存在 `~/.hermes/.curator_backups/blobs/` 下，所以「谁改了哪一行」可以精确定位到单文件、单次改动：

```json
{"ts": "2026-10-08T12:13:22Z", "actor": "agent", "skill": "db-change-review",
 "before": [{"path": "SKILL.md", "sha256": "3f1c..."}],
 "after":  [{"path": "SKILL.md", "sha256": "9d2a..."}]}
```

## 冗余清理与合并

技能库长到一两百条以后，真正的成本不是磁盘，而是**触发歧义**：两条技能都在讲「发布」，模型按 description 匹配到哪条不确定，行为就不稳定。清理的对象因此按优先级排序是：同名冲突 > 同一件事两条技能 > 一个大技能里塞了多件事。

先机械地找出候选，再人工判断。上面的巡检脚本 `[3]` 段就是粗筛（description 前两个实词相同的归一堆），本机真实结果里有明确该合并的（`database-design` 与 `database-design-hardened`、`kubernetes` 与 `kubernetes-architect`），也有恰好共享词但语义不同、不该动的（`delegate coding` 这一类）。判断标准只有一条：**两条技能被同一个任务同时触发是否会互相矛盾**。

Hermes 的自动归并有两种模式：

| 模式 | 开关 | 行为 | 风险 |
|------|------|------|------|
| prune-only（默认） | `curator.consolidate: false` | 只做状态流转与归档，不改技能内容 | 低；内容零改动 |
| LLM 归并 | `curator.consolidate: true` | 额外跑一轮辅助模型评审，提出归并或补丁 | 会重写技能内容，所以每轮前自动做 tar.gz 快照 |

自动归并有一条必须遵守的完整性约束：技能是一个**整包**。带 `references/`、`templates/`、`scripts/`、`assets/` 或相对链接的技能，要么保持独立，要么把需要的支持文件重新挂载并改写路径，要么整包归档——不能只把 SKILL.md 拍扁成另一个技能的一个参考文件。

```shell
hermes curator backup                        # 手工快照：~/.hermes/skills/.curator_backups/<utc-iso>/skills.tar.gz
hermes curator archive old-release-flow      # 归档（进 .archive/，不进提示、不进索引）
hermes curator list-archived                 # 看归档清单
hermes curator restore old-release-flow      # 恢复
hermes curator prune                         # 按 archive_after_days 批量归档
hermes curator rollback <utc-iso>            # 回滚到某次快照
```

```text
合并前自问三条：
1. 合并后的 description 能不能同时覆盖两者的触发场景？（不能就别合）
2. 支持文件（references/templates/scripts/assets）的路径改写完了吗？
3. 合并会不会让常驻内容变大、挤占上下文？如果合并后正文很长，拆成"主技能 + references"更合适
```

## 应用场景实战

### 场景一：季度技能库巡检与归档决策

背景：一个五人平台组的内部技能库有 60 条技能，最近半年没人系统清理过；有人反馈「agent 老是用错发布流程」。目标是每个季度产出一份可决策的清单，而不是靠感觉删。

第一步，在只读模式下跑巡检脚本（脚本见「失效检测」一节，输出待归档、从未使用、疑似重复、依赖缺失四类候选）：

```shell
python3 tools/skill_audit.py --skills-root ~/company-skills --idle-days 60 > audit-2026Q4.txt
```

```text
$ python3 tools/skill_audit.py --skills-root ~/company-skills --idle-days 60
技能树：/root/company-skills
使用遥测条目：<usage_total>    live SKILL.md：<skill_total>

[1] 待归档候选（state=stale 或闲置 >= 60 天）：<n1>
    <skill-name-a>                               idle=<D1>d state=stale
    <skill-name-b>                               idle=<D2>d state=active
[2] 从未使用（use/view 均为 0）：<n2>
[3] 疑似重复（description 前两个实词相同）：
    release deploy                -> deploy-service, deploy-service-legacy
[4] 正文提到但本机不存在的命令（需人工判断是否真依赖）：
    terraform                出现在 2 条技能中，如 infra-apply
```

输出形态与本节前面的本机实测一致（字段与分段来自同一个脚本），尖括号部分是随技能库变化的数值，不是实测数值。

第二步，把报告变成三类决策，写进季度会记录（模板）：

```markdown
<!-- docs/skill-review-2026Q4.md -->

## 归档（7 条）
| 技能 | 依据 | 处置 |
|------|------|------|
| legacy-hotfix-flow | 闲置 143 天 + 对应服务已下线 | `hermes curator archive legacy-hotfix-flow` |
| ops-cron-onboarding | 流程已并入 deploy-service | 先合并内容，再归档 |

## 合并（1 组）
| 组 | 成员 | 决策 |
|----|------|------|
| 发布流程 | deploy-service / deploy-service-legacy | 保留前者，把后者的回滚细节并入其 references/rollback-history.md 后归档 |

## 保留但补修（4 条）
| 技能 | 问题 | 动作 |
|------|------|------|
| infra-apply | 正文引用 terraform，本机未安装 | 在"前置条件"里写明工具安装命令 |

## 采纳管理（3 条）
| 技能 | 原因 | 动作 |
|------|------|------|
| review-checklist | 无来源标记，curator 不管理 | `hermes curator adopt review-checklist` |
```

第三步，执行与留痕。归档和恢复都是一条命令，且必须先备份：

```shell
hermes curator backup                        # 先快照，回滚用
hermes curator archive legacy-hotfix-flow
hermes curator prune                         # 批量处理闲置项
hermes curator list-archived
hermes curator ledger | tail -3              # 台账留痕，季度结束贴进会议记录
```

```text
季度节奏（可复制）：
- 第 1 周：跑巡检脚本，产出候选报告，分到各技能 owner
- 第 2 周：owner 反馈"留/改/合/删"，形成决策表
- 第 3 周：执行（backup → archive/prune → 合并提交），台账留痕
- 第 4 周：把本季度新踩的坑回写成规则，补进对应技能
```

### 场景二：把一次发布事故回写成规则并补上校验

背景：一次发布事故——大表加索引的变更在评审通过后仍长时间持有写锁，服务抖动 20 分钟。事故复盘已经做完，现在要做的是让同类问题不再依赖记忆。

第一步，定位落点：`db-change-review` 是既有技能，问题的位置在「步骤 2 生成变更脚本」，属于**定向修改**，不要整篇重写。

```shell
git -C ~/company-skills pull
# 在会话里让 agent 用 skill_manage 的 patch 动作改这一段，或直接编辑：
$EDITOR ~/company-skills/skills/db-change-review/SKILL.md
```

第二步，把事故压缩成规则。改前（原技能里的相关段落）：

```markdown
## 步骤 2：生成变更脚本

按评审清单生成 DDL 脚本，交给负责人确认后执行。
```

改后（规则 + 机制 + 判定入口 + 例外）：

```markdown
## 步骤 2：生成变更脚本

- 大表（行数 > 1000 万）加索引必须使用 CREATE INDEX CONCURRENTLY；普通 CREATE INDEX
  会持有写锁直到索引建完，期间该表写入阻塞。
  行数判定用 references/table-size-check.md 里的查询，先确认再加语句。
- 例外：CONCURRENTLY 不能在事务块中执行；如果发布通道把 DDL 包在事务里，
  改为先单独提交索引语句，再继续变更流程。
- 生成脚本后必须贴出 references/table-size-check.md 查询结果，评审才会通过。
```

第三步，补一条机器能查的校验。规则写在正文只对读的人有效，脚本才能兜住：「变更脚本里有 CREATE INDEX 但没有 CONCURRENTLY」直接让 CI 失败：

```python
#!/usr/bin/env python3
"""CI: 阻止未使用 CONCURRENTLY 的普通索引创建语句进入变更目录。"""
import re
import sys
from pathlib import Path

BAD = re.compile(r"CREATE\s+(?:UNIQUE\s+)?INDEX\s+(?!CONCURRENTLY\b)", re.IGNORECASE)
bad_files = []

for sql in Path("changes").rglob("*.sql"):
    text = sql.read_text(encoding="utf-8")
    for lineno, line in enumerate(text.splitlines(), 1):
        if BAD.search(line):
            bad_files.append(f"{sql}:{lineno}: {line.strip()}")

if bad_files:
    print("发现未使用 CONCURRENTLY 的索引创建语句：")
    print("\n".join(bad_files))
    sys.exit(1)
print("索引语句检查通过")
```

```text
$ python3 ci/check_index_ddl.py
发现未使用 CONCURRENTLY 的索引创建语句：
changes/<date>-add-order-index.sql:3: CREATE INDEX idx_order_created ON orders(created_at);
（CI 失败，作者改为 CREATE INDEX CONCURRENTLY 后通过）
```

（这是该脚本对含问题语句的文件必然给出的输出形态，文件名按你的变更目录替换。）

第四步，记录、通知、观察。变更记录写清行为差异，提交信息带技能名，下一季度巡检时用 `patch_count` 确认这条技能是否还在被频繁打补丁（如果还在，说明流程本身需要重写而不是继续补）：

```shell
git -C ~/company-skills commit -m "fix: db-change-review 大表索引改 CONCURRENTLY 并补行数判定与校验脚本"
hermes curator ledger | tail -3
```

```text
回写闭环的验收标准：
1. 技能正文能独立读懂规则（不依赖事故背景）
2. 有机器可查的校验，下一次同类错误在 CI 阶段就被拦住
3. 变更记录与提交历史能回答"为什么改"
4. 季度巡检时该技能的 patch_count 不再持续增长
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每条技能都写 `version`，每个版本都写一行行为差异进 `CHANGELOG.md`；版本号是给评审和回滚用的，不是仪式。
2. 用遥测做决策而不是凭感觉清理：先看 `last_used_at` 与 `use_count`，再决定归档，避免删掉一年只用两次但每次都救命的技能（这类应 `pin`）。
3. 关键技能显式 `hermes curator pin <name>`：pin 之后免于一切自动流转，也不会被 LLM 评审改写。
4. 回写优先级是 patch 而不是 rewrite：定向替换能保住其它段落的历史修正，整篇重写容易把之前踩过的坑一起删掉。
5. 规则和长内容分家：常驻规则进 SKILL.md，决策表与历史迁移进 `references/`，需要确定性行为的步骤写成 `scripts/`。
6. 每季度跑一次巡检并留痕（`backup → archive/prune → ledger`），把「技能库维护」变成有节奏的例行动作而不是一次性大扫除。
7. 清理合并时整包对待：支持文件要么重挂并改写路径，要么整包归档，绝不留下指向已删文件的相对链接。
8. 上游更新单独走流程：`hermes skills check` 与 `hermes skills update` 定期跑，被本地改过的自带技能用 `list-modified` 与 `diff` 看清差异再决定是否 `reset`。

### 踩坑记录

```text
坑 1：把事故复盘原文整段贴进技能
结论：技能正文从 60 行长到 400 行，触发时占用大量上下文，模型反而抓不住要点。
原因：教训没有压缩成规则，写成了时间线叙事，而上下文是有限资源。
解法：一条规则 + 一句机制，挂在受影响的那一步下面；背景细节放 references/ 或事故系统，不进常驻内容。

坑 2：看到"从未使用"就直接归档，结果删掉了季节性技能
结论：季度报表技能被清掉，下个季度只能重新写一遍。
原因：用完即走的低频技能在遥测上等于"从未使用"，频率指标解释不了价值。
解法：归档前按"下次用是什么时候"分类，年度或季度性的技能 pin 住；记录归档理由供复查。

坑 3：手动改过官方自带技能，更新后再也没拉到新版
结论：hermes skills update 之后行为没变化，一直用旧逻辑。
原因：改动会打上"用户已修改"标记，更新尊重本地修改、不覆盖它。
解法：hermes skills list-modified 找出被改过的技能，用 diff 看差异；决定接受上游就用 reset，
      想保留改动就把差异提给上游而不是长期分叉。

坑 4：合并两条技能时只搬了 SKILL.md
结论：合并后的技能在"读取 checklist"这一步报文件不存在。
原因：技能是整包，references/ 与 scripts/ 的相对路径在搬迁后失效。
解法：重挂支持文件并改写路径，或整包归档；合并后按技能里的相对路径逐条点开验证一次。

坑 5：开着 LLM 归并去清理没备份的技能库
结论：作者原本精心写好的例外条款被"归纳"掉了，行为悄悄变了。
原因：归并是会重写内容的 pass，而归纳天然倾向"更简洁"，容易丢掉边界条件。
解法：开启 consolidate 前先 hermes curator backup，且把带边界条款的关键技能 pin 住；合并结果走人工评审。

坑 6：把 patch_count 高当成技能好用的证明
结论：一条被反复打补丁的技能被当成"核心资产"，实际每次都在修同一个不稳定流程。
原因：补丁次数是漂移信号，不是使用次数；高频打补丁说明规则本身没写对。
解法：patch_count 持续增长时重写该技能的判定条件与前置检查，而不是继续加例外。
```
