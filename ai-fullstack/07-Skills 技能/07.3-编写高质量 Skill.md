## 概述

写 Skill 和写代码的取舍方向相反：代码追求表达完整，Skill 追求**在够用的前提下尽可能短**。原因是它的成本结构——`description` 每个会话都在付，`SKILL.md` 正文每次触发都在付，只有 `references/` 与 `scripts/` 是免费的，所以「把该省的话省掉、把该外移的内容外移、把能脚本化的判定交给脚本」是三条主线。默认假设是「模型已经很聪明」：凡是模型本来就会的（什么是 PDF、什么是 diff、怎么写 for 循环），写进 Skill 只是花 token 买噪声。

```text
全篇主线：
1. description —— 触发唯一依据：第三人称 + 做什么 + 何时用 + 关键词
2. 正文 —— 500 行以内，先问「这句值不值它的 token」，再问「该不该外移」
3. 自由度 —— 脆弱流程给死步骤（低自由度），开放任务给判据（高自由度）
4. 示例与清单 —— 输入输出对照、可勾选的 checklist、显式的反馈循环
5. 脚本与评测 —— 能机械判定的下沉成脚本，改动用评测而不是拍脑袋验证
```

## description 的写法

`description` 是唯一决定「Skill 会不会被触发」的文本，因此它要同时承担索引与判据两个角色。三条约束来自官方最佳实践：**第三人称陈述**（它被注入系统提示，视角必须一致）、**同时写「做什么」和「何时用」**、**带上具体关键词**（用户实际会说的名词、动作、文件类型）。反面例子是「这个 skill 帮你处理数据」——没有名词、没有场景、视角还错位，命中率完全靠运气。

```yaml
# 反面：泛化、第一人称、没有触发场景
name: data-helper
description: This skill helps you process data files, and you can use it whenever you need help with data.
```

```yaml
# 正面：动作 + 对象 + 触发场景 + 关键词
name: csv-report
description: Builds validated CSV-to-report pipelines from business data files and applies bulk field updates idempotently. Use when the user mentions CSV exports, monthly reports, spreadsheet-driven updates, or asks to fill in missing report columns.
```

关键词选择上有个实用做法：把过去一周里触发这类任务的**原始说法**抄进描述。用户说「帮我跑一下这个月的报表」「把这张表的字段补上」，那么 `monthly reports`、`bulk field updates`、`fill in missing columns` 都应该出现；而「数据治理」这类内部术语如果业务方从不说，写进去只会稀释匹配。

| 检查项 | 通过标准 |
|--------|----------|
| 人称 | 第三人称（`Builds` / `Validates` / `Extracts`），不出现「我」「你」 |
| 做什么 | 一句话说清产出物（产物是什么、喂进去什么） |
| 何时用 | 有 `Use when ...` 段，落到具体场景而非「需要时」 |
| 关键词 | 含业务名词、文件后缀、动作动词，用户真实说法优先 |
| 长度 | 200 字符内能说清就不写 800（上限 1024 字符） |
| 禁用词 | 不含 `anthropic`、`claude`（规范保留字），不含 XML 标签 |

```text
description 写作要点：
1. 先写触发场景，再回头补「做什么」，多数人写反了顺序导致描述空泛
2. 用动词开头（Builds/Validates/Runs），让「能力」在语法上就成立
3. 关键词从真实对话里抄，不从术语表里抄
4. 一个 Skill 只描述一类任务，描述里出现「以及」通常意味着该拆成两个 Skill
5. 写完就用两个问题测：一句该触发的、一句不该触发的，都不对就改描述而不是改正文
```

## 正文组织与篇幅控制

正文的目标是「Agent 读一遍就能照做」，因此结构应该像操作手册而不是教程：先给最短路径（Quick start 或流程），再给判据，最后给边界情况与失败处理。官方给的经验值是正文 500 行以内、内容接近上限就外移；判断某一段是否该留的唯二问题是「Does this paragraph justify its token cost?」和「Can I assume the model knows this?」。一个实测对比能说明差距：同一个「代码评审」Skill 的啰嗦版与精简版，按 CJK 感知的粗估，正文分别约 420 与 290 tokens（`meta_budget.py` 实测）：

```text
skill                          meta 字符  meta≈tok     正文行    正文≈tok
review-verbose                     200        50      24       420
review-concise                     261        65      28       290
```

啰嗦版的典型写法是「解释概念 + 铺垫背景」，精简版把同样的功能压缩成流程 + 判据 + 输出格式：

```markdown
<!-- 啰嗦版：24 行，讲了一堆模型本就知道的事 -->
## 第一步：获取变更

首先，你需要获取待评审的代码变更。代码变更通常以 diff 的形式呈现，diff 是一种描述文件差异的格式，
它由若干行组成，每一行前面有特定的符号表示这行是新增、删除还是上下文。

## 第二步：阅读变更

接下来要仔细阅读这些变更。阅读时要注意以下几个方面：第一，变更的意图是什么；第二，变更的实现是否正确……
```

```markdown
<!-- 精简版：流程 + 判据 + 输出格式 + 边界情况，28 行，信息量更大但更短 -->
## 流程

复制下面清单到回复里逐项打勾，未完成的不写结论：

- [ ] `git diff <base>...HEAD` 拿到完整变更（别只看最后一次提交）
- [ ] 按下面判据逐条过
- [ ] 输出阻塞项与非阻塞项两组，阻塞项必须给出复现路径

## 判据

只报能指出具体行与影响的问题；风格偏好归入非阻塞项。

- 正确性：边界值、空输入、并发写、错误路径是否有测试覆盖
- 安全：外部输入是否校验、凭据是否硬编码、日志是否打印敏感字段
- 兼容性：接口字段是否删改、迁移是否幂等
```

**自由度**是正文里最容易被忽略的一维：任务越脆弱、错误代价越高，步骤就该写得越死；任务越开放，就该给判据让模型自己判断。

| 自由度 | 形式 | 适用 | 例子 |
|--------|------|------|------|
| 高 | 文字判据、原则 | 多路径都可行、依赖上下文判断 | 代码评审的关注点清单 |
| 中 | 伪代码 / 带参数的脚本 | 有推荐做法但允许变体 | 生成报表的模板调用 |
| 低 | 固定脚本、明确顺序 | 操作脆弱、必须按序执行 | 数据库迁移、发布步骤 |

```text
正文组织要点：
1. 结构固定成「流程 -> 判据 -> 输出格式 -> 边界情况」，读者（含模型）按同一顺序找信息
2. 删掉概念解释：模型知道 diff 是什么、知道什么是 CSV，写了只增加噪声
3. 500 行是建议阈值：先删冗余，再考虑外移到 references/
4. 按脆弱程度定自由度：迁移/发布给死步骤，评审/分析给判据
5. 关键规则用 MUST 这类强约束词突出，避免混在铺垫文字里被忽略
```

## 示例与检查清单

两个对输出质量提升最明显的手段是**输入输出对照示例**和**可复制的检查清单**。前者的作用与提示工程里给 few-shot 一样：与其描述格式，不如给一组真实输入与期望输出，模型照着对齐；后者让多步流程有可追踪的进度，官方建议复杂流程给出能复制到回复里打勾的 checklist，这样「漏了第三步」会立刻暴露出来。第三个常用模式是模板：输出格式要求严格时给死模板，要求灵活时给骨架并说明必填字段。

```markdown
## 示例

输入：`changes.csv` 里 `A1001` 的 `new_priority` 从 3 改成 4，`A1002` 的状态要改成 `shipped`。

期望输出（模板见 assets/report-template.md）：

| 订单号 | 状态 | 优先级 | 上次变更 |
|--------|------|--------|----------|
| A1001 | shipped | 4 | 2026-10-14 |

结论：变更 2 条，跳过 1 条（值已相同），校验失败 0 条。
```

```markdown
## 检查清单（复制到回复里逐项打勾）

- [ ] 计划里的 `plan_id` 已记录，重复执行可对账
- [ ] `validate_plan.py` 退出码为 0
- [ ] 应用后重跑一次，`changed=0`
- [ ] 报表字段与模板一致，没有自创列
```

**反馈循环**是把「质量问题」变成「可收敛过程」的手段：让 Agent 先生成中间产物，跑校验脚本，按报错修，再重跑，直到通过。这个模式对格式严格、字段众多的任务（表单填写、迁移脚本、批量更新）几乎是必需品，也是后面 07.4 里 plan-validate-execute 的写作基础。

```text
示例与清单要点：
1. 示例要给「输入 -> 期望输出」的成对样本，不要只给一段输出
2. 多组示例放 references/，正文最多留一组
3. 复杂流程给可复制的 checklist，让遗漏变成可见事件
4. 严格格式给死模板（assets/），灵活格式给骨架 + 必填字段说明
5. 质量关键步骤配反馈循环：生成中间产物 -> 校验 -> 按报错修 -> 重跑
```

## 可执行脚本的接入

把确定性逻辑写成 `scripts/` 里的脚本，比让模型现场生成代码更可靠、更省 token，也更容易被评审。接进 Skill 时要做三件事：**在指令里明确「运行」还是「参考」**、**脚本自己处理错误而不是把判断推回给模型**、**参数与常量都要有理由**（不要出现无法解释的魔法数字）。官方最佳实践里给这类脚本的三条要求是：solve, don't punt（失败要给出可执行的报错信息）、no voodoo constants（每个阈值都能说出依据）、utility scripts 优先于现场生成。

```markdown
## 校验计划

运行 `scripts/validate_plan.py` 得到结论，不要自己逐行读 CSV 判断：

```bash
python3 scripts/validate_plan.py --plan plan.json
```

- 退出码 0：可以继续执行下一步。
- 退出码 2：把 errors 逐条列给用户，不要自行修数据后重跑。
```

```python
# 反面：失败时把问题推回给模型，等于没写脚本
def check(row):
    if not row.get("order_id"):
        print("数据有问题，请检查")
        return
```

```python
# 正面：报错具体到行与字段，并给可用取值范围，模型能自己修
ALLOWED = {"pending", "shipped", "cancelled"}
MAX_PRIORITY = 5  # 业务规则：优先级 1-5，见 references/SCHEMA.md

def check(row, lineno):
    errors = []
    if not row.get("order_id"):
        errors.append(f"第 {lineno} 行缺少必填字段 order_id")
    if row.get("new_status") and row["new_status"] not in ALLOWED:
        errors.append(f"第 {lineno} 行 status={row['new_status']!r} 越界，允许值 {sorted(ALLOWED)}")
    if row.get("new_priority") and not 1 <= int(row["new_priority"]) <= MAX_PRIORITY:
        errors.append(f"第 {lineno} 行 priority 越界，允许范围 1-{MAX_PRIORITY}")
    return errors
```

**中间产物**是这套写法的关键：让脚本产出可校验的中间文件（如 `plan.json`、`changes.json`），先校验再执行，出错时能改计划而不动数据。官方把这个模式称为「plan-validate-execute」，并建议校验脚本的报错尽量啰嗦——报错越具体，Agent 一次修对的概率越高。

```text
脚本接入要点：
1. 指令里写清「运行 scripts/x.py 得到结论」还是「参考 scripts/x.py 的算法」，两者上下文成本完全不同
2. 报错要具体到行号、字段、当前值、允许值，不要把判断题推回给模型
3. 常量必须有依据（阈值、枚举值），写不清依据的常量就是待爆炸的地雷
4. 用中间产物把「改数据」和「定计划」分开：先 plan.json 校验通过，再执行
5. 脚本假设的工具要显式声明：需要 git / jq / uv 时写进 compatibility 并在正文里给出检查命令
```

## 常见写作反模式

反模式大多不是「写错」，而是「写对了但会随时间腐化」。最典型的是**时间敏感信息**：把「目前最新版本是 2.x」「截至某年推荐用 A 方案」写进正文，半年后 Skill 会自信地给出过时结论，而没人知道该改哪一句。处理办法是把易变内容集中到「旧做法」小节或 references/，并标注核对日期。第二类是**为模型写它已经知道的东西**：解释什么是 API、什么是 diff、for 循环怎么写。第三类是**并列多方案**：给出 A、B、C 三种做法，模型无从选择，这类内容应筛选出唯一推荐做法，其余进 references/。

| 反模式 | 症状 | 修正 |
|--------|------|------|
| 时间敏感表述 | 「当前最新版本是」「截至某年」 | 移入「旧做法」小节或 references/ 并标日期，正文改成「以官方文档为准」 |
| 过度解释 | 铺垫三段才进入步骤 | 删掉定义与背景，直接给流程与判据 |
| 并列多方案 | 列出 A/B/C 让模型自己挑 | 只留一个推荐做法，其余进 references/ |
| Windows 路径 | `scripts\run.ps1`、`C:\path` | 统一正斜杠相对路径 `scripts/run.py` |
| 术语不一致 | 同一概念混用 field / 字段 / 列 | 一个概念一个词，全文统一 |
| 魔法常量 | `if row_count > 37:` | 每个常量给出处，写进注释或 references/ |
| 绝对路径 | `/home/alice/skills/...`、`~/x` | 相对 skill 根目录，保证跨机器可用 |
| 占位文本 | `TODO`、`待补充` | 发布前补齐，或从正文删掉 |

这些反模式大部分能机械检查。下面这个 lint 脚本把「时间敏感表述、Windows 路径、绝对路径引用、占位文本、并列多方案」五类规则跑成报告，本机实测输出：

```python
#!/usr/bin/env python3
"""SKILL.md 正反模式检查：时间敏感表述、Windows 路径、绝对路径引用、占位文本、并列多方案。

用法：python3 lint_skill_body.py <SKILL.md 或 skill 目录> [...]
退出码：0 干净，1 命中任何规则。
"""
from __future__ import annotations

import re
import sys
from pathlib import Path

RULES: list[tuple[str, re.Pattern[str], str]] = [
    ("时间敏感表述", re.compile(r"(截至|目前最新|当前最新|最新的)\s*20\d\d|20\d\d\s*年\s*(最新|版本)|(今天|本周|上个月)"), "改为「旧做法」小节，或只写不随时间失效的规则"),
    ("Windows 路径", re.compile(r"[A-Za-z0-9_./-]\\[A-Za-z0-9_./-]"), "统一改成正斜杠的相对路径"),
    ("绝对路径引用", re.compile(r"\]\((?:/|~/|[A-Za-z]:[/\\])"), "改成相对 skill 根目录的路径"),
    ("占位文本", re.compile(r"TODO|FIXME|待补充|待完善|XXX"), "发布前补齐或删除"),
    ("并列多方案", re.compile(r"方案 ?[ABC]|选项 ?[123]|Alternatively|You can also"), "只留一个推荐做法，其余放 references/"),
]


def lint(path: Path) -> list[str]:
    hits: list[str] = []
    for lineno, line in enumerate(path.read_text(encoding="utf-8").splitlines(), start=1):
        for rule, pattern, advice in RULES:
            m = pattern.search(line)
            if m:
                hits.append(f"{path}:{lineno} [{rule}] 命中 {m.group(0)!r} -> {advice}")
    return hits


def main(argv: list[str]) -> int:
    targets: list[Path] = []
    for arg in argv[1:]:
        p = Path(arg)
        targets.extend(sorted(p.rglob("SKILL.md")) if p.is_dir() else [p])
    total: list[str] = []
    for t in targets:
        hits = lint(t)
        total.extend(hits)
        print(f"{t}: {'干净' if not hits else str(len(hits)) + ' 处命中'}")
    for h in total:
        print(h)
    print(f"检查结论: 共 {len(targets)} 个 SKILL.md，命中 {len(total)} 处")
    return 1 if total else 0


if __name__ == "__main__":
    sys.exit(main(sys.argv))
```

python3 tools/lint_skill_body.py skills
```

```text
反模式治理要点：
1. 时间敏感内容一律外移：正文只留不随时间失效的判据与步骤
2. 删掉「模型已经知道」的解释，是压缩篇幅见效最快的一招
3. 同一概念全文一个词，模型不需要处理同义词
4. 路径统一正斜杠相对路径，禁止绝对路径与反斜杠
5. 把可机械检查的反模式写成 lint 脚本挂进 CI，比靠评审记忆可靠
```

## 评测驱动迭代

官方推荐的顺序是**先建评测再写文档**：拿几个真实任务在不加载 Skill 的情况下跑一遍，记录具体的失败点；为这些失败点写三条评测场景；再写刚好能通过的指令。这样写出来的 Skill 解决的是真实缺口，而不是想象中的需求。迭代时的另一个有效做法是「用模型帮写、用另一个实例实测」：一个实例负责把流程整理成指令（它知道 Agent 需要什么信息），另一个实例在真实任务里用这份指令，观察它在哪一步卡住、读了哪些文件、跳过了哪些规则，再回头改文本。

| 观察到的信号 | 可能原因 | 动作 |
|--------------|----------|------|
| Agent 读了意想不到的文件顺序 | 目录结构不直观 | 在正文里给出更明确的读取条件或改结构 |
| 关键规则被忽略 | 规则埋在铺垫里 | 用 MUST 强约束或前置到流程顶部 |
| 反复读同一个文件 | 该内容其实每次都要用 | 从 references/ 并回 SKILL.md |
| 某个参考文件从不被读 | 引用信号太弱或文件无用 | 提高引用显著性，或删掉该文件 |
| 触发不准 | description 关键词与真实说法不匹配 | 改 description，用真实提问复测 |

```text
评测驱动要点：
1. 先记录「没有 Skill 时失败在哪」，再写恰好覆盖这些缺口的指令
2. 每条评测给出「任务描述 + 通过标准」，至少要三条，覆盖主线与边界
3. 评测结果与改动一起进版本库，改坏了能立刻看到差异
4. 跨模型测试：小模型需要更显式的步骤，大模型更怕啰嗦，指标要分模型看
5. 团队反馈是评测的一部分：收集「该触发没触发」「读了文件还是做错」的具体案例
```

## 应用场景实战

### 场景一：重写一个啰嗦的代码评审 Skill

背景：团队第一个 Skill 是「代码评审」，24 行正文里有一半在解释 diff 是什么，实际规则混在铺垫里，评审结果时好时坏。重写方式是：删掉概念解释、把判据改成条目、要求输出阻塞项/非阻塞项两组、补上边界情况（超大变更、生成文件）。重写后用同一组任务在两个版本上各跑三次，对比遗漏项数量与 token 成本。

```text
review-verbose/SKILL.md      24 行，正文 ≈ 420 tokens：概念铺垫占一半，规则埋在段落里
review-concise/SKILL.md      28 行，正文 ≈ 290 tokens：流程 + 判据 + 输出格式 + 边界情况
```

```markdown
<!-- 重写后的完整正文（review-concise/SKILL.md） -->
## 流程

复制下面清单到回复里逐项打勾，未完成的不写结论：

- [ ] `git diff <base>...HEAD` 拿到完整变更（别只看最后一次提交）
- [ ] 按下面判据逐条过
- [ ] 输出阻塞项与非阻塞项两组，阻塞项必须给出复现路径

## 判据

只报能指出具体行与影响的问题；风格偏好归入非阻塞项。

- 正确性：边界值、空输入、并发写、错误路径是否有测试覆盖
- 安全：外部输入是否校验、凭据是否硬编码、日志是否打印敏感字段
- 兼容性：接口字段是否删改、迁移是否幂等

## 输出格式

阻塞项：`文件:行 — 问题 — 影响 — 修复方向`
非阻塞项：一行一条，不展开。

## 边界情况

- 变更超过 400 行：先给整体风险判断，再要求拆成小 PR
- 二进制或生成文件：跳过，只确认是否应该入库
```

重写落地要点：
1. 先删概念解释与铺垫，再压缩段落为条目，最后才考虑拆文件
2. 规则写进判据列表，每条都能指出「具体行 + 影响」
3. 输出格式写死（阻塞项 / 非阻塞项），减少评审结果的随机性
4. 补边界情况：超大变更、二进制文件、生成代码
5. 重写前后用同一组任务对比遗漏项，用数字而不是感觉证明改好了
```

### 场景二：把反模式检查接进 CI 门禁

背景：Skill 库由多个团队维护，常见退化是「正文里出现 TODO」「路径写成了本地绝对路径」「一句描述里塞了三种方案」。这些都是文本层面的可检测特征，做成 lint 脚本挂在 PR 上，比人工评审更稳定。脚本对每个 `SKILL.md` 跑五类规则，命中任何一处即非 0 退出。

```python
#!/usr/bin/env python3
"""反模式 lint：把 07.3 表里的规则实现成可执行检查，命中即失败，便于挂进 CI。"""
from __future__ import annotations

import re
import sys
from pathlib import Path

RULES = {
    "时间敏感表述": re.compile(r"(截至|目前最新|当前最新|最新的)\s*20\d\d|(今天|本周|上个月)"),
    "Windows 路径": re.compile(r"[A-Za-z0-9_./-]\\[A-Za-z0-9_./-]"),
    "绝对路径引用": re.compile(r"\]\((?:/|~/|[A-Za-z]:[/\\])"),
    "占位文本": re.compile(r"TODO|FIXME|待补充|待完善|XXX"),
    "并列多方案": re.compile(r"方案 ?[ABC]|选项 ?[123]|Alternatively|You can also"),
}


def scan(path: Path) -> list[str]:
    out = []
    for no, line in enumerate(path.read_text(encoding="utf-8").splitlines(), 1):
        for name, pat in RULES.items():
            hit = pat.search(line)
            if hit:
                out.append(f"{path}:{no} [{name}] {hit.group(0)!r}")
    return out


def main(argv: list[str]) -> int:
    root = Path(argv[1] if len(argv) > 1 else ".")
    files = sorted(root.rglob("SKILL.md"))
    hits = [h for f in files for h in scan(f)]
    print(f"扫描 {len(files)} 个 SKILL.md，命中 {len(hits)} 处")
    for h in hits:
        print(h)
    return 1 if hits else 0


if __name__ == "__main__":
    sys.exit(main(sys.argv))
```

# CI 里的三个门禁：结构合规、引用完整、反模式干净
python3 tools/validate_skills.py skills     # name/必填字段/死链
python3 tools/ref_depth.py skills           # 嵌套引用与未被直引
python3 tools/lint_skill_body.py skills     # 反模式
```

skills/csv-report/SKILL.md: 干净
skills/db-migration-check/SKILL.md: 干净
skills/review-concise/SKILL.md: 干净
skills/review-verbose/SKILL.md: 干净

```

```text
CI 落地要点：
1. 规则要能给出「文件:行 + 命中内容」，否则修起来比手查还慢
2. 硬规则（路径、占位文本、name 规则）设成 error，风格类规则设 warning
3. lint 脚本配一个「故意写坏的样例 skill」当自测，防止规则被改松后无人察觉
4. 三件事分三个脚本：结构合规、引用完整、反模式，输出各自独立，失败原因一眼可见
5. 检查脚本只读不写：CI 只报警，改由作者改，避免自动改写破坏语义
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用「值不值它的 token」筛每一段：删掉模型已知的概念解释，只留它不知道的判据与边界。
2. 正文按「流程 -> 判据 -> 输出格式 -> 边界情况」组织，读者能按同一顺序定位信息。
3. 按任务脆弱程度调自由度：迁移/发布给固定步骤，评审/分析给判据让模型判断。
4. `description` 从真实对话里抄关键词，写完用一句该触发、一句不该触发的问题测一次。
5. 复杂流程给可复制的 checklist，质量关键步骤配「生成中间产物 -> 校验 -> 修 -> 重跑」的反馈循环。
6. 能机械判定的判定一律下沉成脚本，脚本失败给出具体行号与允许值，不要把判断推回给模型。
7. 时间敏感内容集中外移并标注核对日期，正文只留不随时间失效的规则。
8. 先写三条评测再写指令，改动与评测结果一起进版本库。
9. 把可机械检查的反模式写进 CI（结构、引用、反模式三类），减少对人工评审记忆的依赖。

### 踩坑记录

```text
坑 1：把「当前最新版本」「截至今年推荐」写进正文
结论：Skill 半年后给出过时建议，且没人说得清该怎么修。
原因：时间敏感信息被固化进长期复用的资产，正文里也没有核对日期。
解法：易变内容集中到「旧做法」小节或 references/ 并标注日期，正文改成「以官方文档为准 + 核对步骤」。
```

```text
坑 2：正文里塞满定义与背景铺垫
结论：触发一次就吃掉大量上下文，关键判据反被稀释，漏项变多。
原因：把「教人」的写法搬进了 Skill，而模型已经具备这些常识。
解法：删铺垫，改成条目与判据；用两版正文做 A/B，按遗漏项数量与 token 成本决定取舍。
```

```text
坑 3：一口气列出 A/B/C 三种方案让模型挑
结论：输出在不同会话里漂移，同一份输入给出不同做法，团队无法沉淀标准。
原因：Skill 的职责是「定标准」，并列方案等于把标准决策交回给模型。
解法：只保留一个推荐做法，把其余方案连同适用条件移进 references/，并在正文说明切换条件。
```

```text
坑 4：脚本失败时只打印「数据有问题，请检查」
结论：Agent 反复猜、反复改，最后往往改动数据而不是修数据。
原因：报错缺少定位信息，模型只能靠猜；这属于官方说的 punt 给模型。
解法：报错写到行号、字段、当前值、允许值；脚本自己判断该失败就失败，用退出码表达结果。
```

```text
坑 5：反模式 lint 脚本的正则转义写错，规则静默失效
结论：脚本一直报「干净」，直到人工评审才发现 Windows 路径早就混进来了。
原因：正则里把反斜杠多转义了一层（`\\\\` 匹配两个反斜杠），规则永远匹配不到单反斜杠的路径。
解法：修成 `\\` 后重新对「故意写坏的样例 skill」跑一遍，确认能抓到；lint 脚本必须带自测样例，否则失效无声。
```

```text
坑 6：评测只在最强的模型上做
结论：Skill 在主力模型上表现正常，切到小模型或换供应商后步骤被跳过。
原因：不同模型对隐含步骤的补全能力差异很大，同一份文本的「够用程度」不同。
解法：至少在两个档次的模型上各跑一遍；小模型上显式补步骤，大模型上删冗余，取交集要求。
```

```text
坑 7：把 Skill 当文档写，越长越「专业」
结论：正文涨到八百行，触发后上下文被占满，反而更容易漏掉关键规则。
原因：把「完整」当目标，忽略了上下文是共享资源。
解法：以 500 行作为检查点，超过就按主题拆分；每次改动后量一次正文与元数据成本。
```
