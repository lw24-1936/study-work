## 概述

Skill 是「一个目录 + 一个 SKILL.md」的文件形态资产，分发问题因此比软件包简单也更容易做错：简单在于没有构建、没有依赖解析、拷贝目录即可生效；容易做错在于**加载目录、覆盖优先级、信任级别**这三件事各家工具都不一样，而且默认行为通常是「不加载来历不明的技能」。这一篇讲的是：技能放哪里才会被看见、怎么按团队规模分发、以及把外部技能装进本机之前该做的审查。

```text
全篇主线：
1. 目录 —— 用户级 / 项目级 / 系统级三档，各工具的路径不同但语义一致
2. 安装 —— Hub 与直链安装（hermes skills install）会做安全扫描，项目技能需要显式 trust
3. 插件 —— skill 是内容单元，plugin 是安装单元，插件内技能走 plugin:skill 命名空间
4. 共享 —— 小团队用项目内 .agents/skills + git，跨团队用 tap 仓库，个人用快照导出
5. 边界 —— 装之前审查、装之后限定权限；技能正文是给模型执行的指令，等同代码
```

## 各工具的 skills 目录

Agent Skills 的目录约定由 agentskills.io 开放规范定义，但**加载位置是各家自己的实现**：规范只说「目录里有 SKILL.md」，没说去哪找。实际使用中先记住一个心智模型——三档作用域，优先级从低到高通常是「系统/内置 < 用户级 < 项目级」，同名技能由高优先级覆盖。

| 工具 | 用户级（本机全部项目） | 项目级（随仓库走） | 备注 |
|------|------------------------|--------------------|------|
| Hermes Agent | `~/.hermes/skills/`（唯一权威目录） | `./.hermes/skills/`、`./.agents/skills/` | 项目技能默认**不加载**，需 `hermes skills trust` 授权 |
| Claude Code | `~/.claude/skills/` | `.claude/skills/`（含子目录内的 `apps/web/.claude/skills/`） | 另有企业级与企业托管设置；同名优先级：企业 > 个人 > 项目 |
| Codex CLI | `$HOME/.agents/skills/` | `.agents/skills/`（从 CWD 逐级向上直到仓库根） | 另有 `ADMIN` 级 `/etc/codex/skills` 与内置 SYSTEM 技能 |
| OpenCode | `~/.config/opencode/skills/`，兼容读取 `~/.claude/skills/` 与 `~/.agents/skills/` | `.opencode/skills/`，兼容 `.claude/skills/`、`.agents/skills/` | v2 还支持在配置里声明额外 `skills` 源（本地路径或 URL） |

Hermes 侧的作用域优先级在官方文档里写得很明确：`project → local(~/.hermes/skills/) → skills.create_dir → 外部目录`。项目技能是最高优先级，这正是「仓库自带的技能在其主场覆盖同名全局技能」的设计目的，项目技能在技能索引里会带 `[project]` 标记以便溯源。本机实测的授权流程如下：

```shell
# 在仓库里放一个项目技能（注意目录名与 frontmatter 的 name 一致）
mkdir -p ./.hermes/skills/deploy-demo
cat > ./.hermes/skills/deploy-demo/SKILL.md <<'EOF'
---
name: deploy-demo
description: "Use when deploying the demo service."
---

# Deploy demo

Run make deploy.
EOF

# 第一次在仓库里跑 Hermes 时不会加载，需要显式授权
hermes skills trust                 # 授权当前仓库
hermes skills trust /path/to/repo   # 或显式指定仓库路径
hermes skills untrust               # 撤销授权
```

```text
Trusted: /root/.hermes/cache/scratch/proj-demo
1 project skill(s) will load in sessions started inside this repo (they take precedence over same-named profile skills).
```

撤销授权后，本机 `~/.hermes/config.yaml` 里的记录回到空列表，实测配置行与输出如下：

```yaml
# ~/.hermes/config.yaml（片段）
skills:
  trusted_project_dirs: []       # hermes skills trust 写入这里，untrust 后清空
  # project_discovery: false     # 设为 false 可整体关闭项目技能扫描与提示
```

```text
Untrusted: /root/.hermes/cache/scratch/proj-demo
Project skills from this repo will no longer load.
```

另外两处需要知道的位置：

- **外部共享目录**：Hermes 支持把 `~/.agents/skills/` 这类目录登记为外部技能目录，规则是「新建的技能写到 `~/.hermes/skills/`，已存在的技能就地修改」，适合与别的 agent 工具共用一份技能树。
- **多 profile**：每个 profile 有独立的 `~/.hermes/profiles/<name>/skills/`，`hermes -p <profile> <cmd>` 运行指定 profile 的命令；动手前先确认自己在操作哪个 home。

## 从 Hub 与直链安装

Hermes 把技能来源统一成「Hub」概念：官方可选技能、skills.sh 目录、网站 well-known 端点、GitHub 仓库路径、社区市场都走同一套 install/inspect/audit 管线。`hermes skills --help` 列出的子命令在本机实测如下：

```text
$ hermes skills --help
{trust,untrust,browse,search,install,inspect,list,check,update,audit,uninstall,
 reset,list-modified,diff,opt-out,opt-in,repair-official,publish,snapshot,tap,config}

Search, install, inspect, audit, configure, and manage skills from skills.sh,
well-known agent skill endpoints, GitHub, ClawHub, and other registries.
```

标识符形态决定来源，几种常见写法：

```shell
hermes skills browse                              # 浏览全部（官方优先）
hermes skills browse --source official            # 只看官方可选技能
hermes skills search kubernetes                   # 跨来源搜索
hermes skills search react --source skills-sh     # 只搜 skills.sh 目录
hermes skills inspect openai/skills/k8s           # 先预览，别急着装
hermes skills install openai/skills/k8s           # 装（含安全扫描）
hermes skills install official/security/1password # 官方可选技能
hermes skills install well-known:https://mintlify.com/docs/.well-known/skills/mintlify
hermes skills install https://sharethis.chat/SKILL.md                # 直链装 SKILL.md
hermes skills install https://example.com/SKILL.md --name my-skill   # frontmatter 无 name 时兜底
hermes skills list --source hub                   # 只看 Hub 装进来的
hermes skills check && hermes skills update       # 检查 / 拉取上游更新
hermes skills uninstall k8s                       # 卸载 Hub 技能
```

`hermes skills install` 的参数在本机实测为：

```text
usage: hermes skills install [-h] [--category CATEGORY] [--name NAME]
                             [--force] [--yes]
                             identifier

positional arguments:
  identifier           Skill identifier (e.g. openai/skills/skill-creator) or
                       a direct HTTP(S) URL to a SKILL.md file
options:
  --category CATEGORY  Category folder to install into
  --name NAME          Override the skill name
  --force              Install despite blocked scan verdict
  --yes, -y            Skip confirmation prompt (needed in TUI mode)
```

几个容易踩的点：`--category` 决定装到 `~/.hermes/skills/` 下的哪个分类目录；`--yes` 在 TUI 模式下必须加，否则会卡在确认提示；`--force` 只在扫描结论是「非危险但需确认」时能绕过，**危险（dangerous）结论不能被绕过**。安装完成的技能会出现在 `skills_list` 里并自动变成一个斜杠命令，但**只对新会话生效**（`/reset` 之后可用；`--now` 可以立即失效提示缓存，代价是下一轮 token 变多）。

技能目录结构本身保持不变，`scripts/`、`references/`、`templates/`、`assets/` 会随 SKILL.md 一起落地（这也是后面审查时最需要看的地方）：

```text
~/.hermes/skills/
├── autonomous-ai-agents/hermes-agent/SKILL.md
│   └── references/qqbot-config.md
├── productivity/ocr-and-documents/
│   ├── SKILL.md
│   ├── scripts/
│   └── references/
└── ...
```

## 插件形式分发

Skill 是「内容单元」，插件是「安装单元」。一个团队流程可能同时需要技能、斜杠命令、钩子和自定义工具，这种情况下把它们打进一个插件比让用户手工摆目录稳妥：一次安装拿到全套，一次升级一起更新。

Hermes 插件的清单文件是 `plugin.yaml`，其中 `provides_skills` 声明本插件提供哪些技能；本机已装插件 ponytail 的真实清单如下：

```yaml
# ~/.hermes/plugins/ponytail/plugin.yaml
name: ponytail
version: 4.10.0
description: Lazy senior dev mode for Hermes Agent, always-on context, bundled skills, and slash commands.
author: Dietrich Gebert
provides_hooks:
  - pre_llm_call
  - pre_gateway_dispatch
provides_commands:
  - ponytail
  - ponytail-review
provides_skills:
  - ponytail
  - ponytail-review
  - ponytail-audit
```

插件技能的加载语义与普通技能**故意不同**，这决定了它适合什么样的内容：

| 维度 | 普通技能（`~/.hermes/skills/`） | 插件技能（plugin） |
|------|-------------------------------|--------------------|
| 是否进系统提示的技能索引 | 是 | 否（不占常驻 token） |
| 是否出现在 `skills_list` | 是 | 否 |
| 加载方式 | 自动触发或被索引提示 | 显式加载：`skill_view("plugin:skill")` |
| 可否被 `skill_manage` 编辑 | 可以 | 只读，不可改 |
| 同名冲突 | 与其它技能按作用域竞争 | 命名空间隔离，裸名不受影响 |

插件管理的真实命令面：

```shell
hermes plugins list                 # 已装插件（含 enabled/disabled、source）
hermes plugins install owner/repo   # 从目录、Git URL 或 owner/repo 安装
hermes plugins update               # 拉取最新
hermes plugins capabilities         # 看每个插件声明了什么、被授予了什么
hermes plugins doctor               # 用真实运行时契约校验插件
hermes plugins pack export          # 导出一份固定到 commit SHA 的插件集合
hermes plugins pack install pack.yaml   # 按包安装（逐插件仍各自确认能力）
```

```text
$ hermes plugins list
┏━━━━━━━━━━━━━━━━━━━━━━┳━━━━━━━━━┳━━━━━━━━━┳━━━━━━━━━┓
┃ Name                 ┃ Status  ┃ Version ┃ Source  ┃
┡━━━━━━━━━━━━━━━━━━━━━━╇━━━━━━━━━╇━━━━━━━━━╇━━━━━━━━━┩
│ browser-browser-use  │ enabled │ 1.0.0   │ bundled │
└──────────────────────┴─────────┴─────────┴─────────┘

$ hermes plugins show ponytail
ponytail v4.10.0
Status: enabled
Source: git
Key: ponytail

```

插件安装来源与版本被记录在 `~/.hermes/plugins/.install-metadata.json`，可以据此审计「这个插件从哪来、钉在哪个 revision」：

```json
{
  "ponytail": {
    "pinned": false,
    "revision": "e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156",
    "source": "https://github.com/DietrichGebert/ponytail.git"
  }
}
```

其它工具的插件路线可以作为对照，思路一致、载体不同：

| 工具 | 插件载体 | 技能如何随插件分发 |
|------|----------|--------------------|
| Hermes | `plugin.yaml` + `register(ctx)`，Python | `provides_skills` 声明，加载为 `plugin:skill` |
| Claude Code | 插件目录 / 插件市场，含 `skills/`、`hooks/`、`.mcp.json` | 插件技能与本地技能同列，但不受 `skillOverrides` 影响，用 `/plugin` 管理 |
| Codex | 插件（plugin）作为可安装分发单元 | 技能用 `$skill-creator` 编写，用插件分发给工作区其他人 |
| OpenCode | npm 形态插件 | 由插件注册技能相关工具，另有 v2 配置里声明 `skills` 源 |

## 团队共享方式

按团队规模选，别一步到位：两三个人的小组用项目内技能就够了，跨团队再上 tap 仓库，插件只在需要钩子或工具一起分发时才值得引入。

| 方式 | 适用规模 | 落地做法 | 升级路径 |
|------|----------|----------|----------|
| 项目内技能随仓库走 | 单仓库或小队 | 技能放 `.agents/skills/<name>/SKILL.md` 或 `./.hermes/skills/`，提交进仓库；成员首次运行 `hermes skills trust` | 成员变多、出现跨仓库需求时改 tap |
| tap 仓库（内部技能库） | 多仓库、多团队 | 建一个 GitHub 仓库，根下 `skills/<name>/SKILL.md`，成员 `hermes skills tap add myorg/skills-repo` | 需要钩子或工具时打包成插件 |
| 插件包（pack） | 需要锁定版本 | `hermes plugins pack export` 产出钉住 commit SHA 的 YAML，交给新环境安装 | 保持为发布单元 |
| 快照导出与导入 | 个人换机、临时对齐 | `hermes skills snapshot export setup.json`，需要时导入 | 长期协作回到 tap |

tap 的约定在本机与官方文档一致：默认路径是仓库根的 `skills/`，目录名即安装 slug，每个技能目录必须有带标准 frontmatter 的 `SKILL.md`，`references/`、`templates/`、`scripts/`、`assets/` 会随主文件一起下载，`.` 或 `_` 开头的目录被忽略。tap 记录写在 `~/.hermes/skills/.hub/taps.json`：

```shell
hermes skills tap list                 # 列出当前来源
hermes skills tap add myorg/skills-repo
hermes skills tap remove myorg/skills-repo
hermes skills search internal --source myorg/skills-repo
```

```text
$ hermes skills tap list
No custom taps configured. Using default sources only.
```

```json
// ~/.hermes/skills/.hub/taps.json（结构，按需手改 path）
{
  "taps": [
    { "repo": "my-org/platform-docs", "path": "internal/skills/" }
  ]
}
```

对外发布走同样的路径：`hermes skills publish <skill_dir> --to github --repo owner/repo`，把内部打磨好的技能推到一个 GitHub 仓库，别人再用 install 或 tap 接进来。

## 安全审查与信任边界

技能正文会被模型当成要执行的指令，`scripts/` 里的脚本可能被真的运行，所以**装技能的信任模型必须按「装代码」对待**，而不是按「下载文档」对待。

Hermes 的信任级别分四档，来源决定初始信任，扫描结论决定放行与否：

| 信任级别 | 来源 | 行为 |
|----------|------|------|
| `builtin` | 随 Hermes 自带 | 始终信任 |
| `official` | 官方 `optional-skills/` | 内置信任，无第三方警告 |
| `trusted` | openai/skills、anthropics/skills、huggingface/skills | 视为可信来源 |
| `community` | 其它 tap、社区市场 | 走完整扫描并显示第三方警告面板；非危险发现可用 `--force` 覆盖，危险结论一律拦下 |

审查工具链（均为本机可跑的真实命令）：

```shell
hermes skills inspect openai/skills/k8s    # 装之前先看一眼正文与附带文件
hermes skills audit                        # 重扫所有 Hub 技能
hermes skills audit my-skill --deep        # 对 Python 文件做 AST 级分析（诊断用，开销更大）
hermes security audit                      # 供应链扫描：venv / 插件声明的依赖 / 钉住的 npx、uvx MCP 服务
hermes plugins capabilities                # 插件声明能力 vs 实际授予能力
```

`hermes skills audit` 与 `hermes security` 的覆盖面在本机实测为：

```text
$ hermes skills audit --help
usage: hermes skills audit [-h] [--deep] [name]
  --deep      Run AST-level analysis on Python files (opt-in diagnostic)

$ hermes security --help
On-demand vulnerability scan against OSV.dev. Covers the Hermes venv
(installed PyPI dists), Python deps declared by plugins under
~/.hermes/plugins/, and pinned npx/uvx MCP servers in config.yaml.
Does NOT scan globally-installed packages or editor/browser extensions.

$ hermes plugins capabilities
No plugins declare or hold capabilities.
```

两类自动防线值得记住：

- **Hub 安装扫描**：所有 Hub 安装都过安全扫描器，检查提示注入指令、凭据外泄命令、隐藏文本等模式；新 tap 默认是 `community` 信任，来源级提权要改核心仓库里的 `TRUSTED_REPOS`（`tools/skills_guard.py`），不是配置项。
- **项目技能扫描期隔离**：`trust` 是仓库级决定，但仓库内容会随 `git pull` 变。所以每个项目技能进索引前都跑与 Hub 相同的扫描器，结论为危险时**隔离**：不出现在技能索引、`skills_list` 和斜杠命令里，按名加载会被拒绝并给出说明。扫描按内容哈希缓存在 `~/.hermes/cache/project_skill_scans/`，内容变化自动重扫，缓存刻意不放进你的仓库。

给团队的审查清单（评审 PR 时逐条看）：

```text
1. 触发范围：description 是否写得足够窄，不会在无关任务上被触发
2. 外部输入：SKILL.md 是否出现「读取某个 URL 的内容并照做」这类转发式指令
3. 脚本行为：scripts/ 里每条命令做什么，有没有 curl | bash、写 ~/.ssh、读 .env
4. 凭据：需要密钥的技能走 required_environment_variables / required_credential_files，
   不允许把密钥写进 SKILL.md 或示例里
5. 网络出口：脚本访问的域名是否属于预期范围
6. 写操作：涉及删除、发布、改生产数据的步骤是否有二次确认或 dry-run 分支
7. 来源与版本：source / revision 是否记录，能否复现安装
```

## 应用场景实战

### 场景一：把内部技能库做成 tap，让新同事一条命令装齐

背景：一个 20 人后端团队，有 8 条反复讲不清的流程（服务发布、数据库变更评审、灰度回滚、告警处理、周报、故障复盘、值班交接、本地环境搭建）。目标是新同事入职当天就能用上，且流程更新只改一处。

第一步，建技能库仓库，约定布局：

```text
company-skills/
├── README.md                 # 收录标准与评审方式
├── CODEOWNERS                # skills/** 由平台组评审
└── skills/
    ├── deploy-service/
    │   ├── SKILL.md
    │   └── scripts/deploy_check.sh
    ├── db-change-review/
    │   ├── SKILL.md
    │   └── references/checklist.md
    └── oncall-handover/
        └── SKILL.md
```

第二步，写一个合格技能的骨架（`deploy-service`），把「何时用、何时不用、怎么验证」写进正文，而不是指望模型自己猜：

```yaml
---
name: deploy-service
description: "Use when deploying or rolling back a backend service in the prod cluster: pre-flight checks, staged rollout, rollback. Do not use for infra change (terraform) or DB migrations."
version: 1.2.0
author: platform-team
metadata:
  hermes:
    tags: [deploy, release, ops]
---

# 服务发布与回滚

## 何时使用

- 需要把某个后端服务发到生产集群，或把正在进行的发布回滚
- 不适用：基础设施变更（走 terraform 流程）、数据库变更（走 db-change-review）

## 步骤

1. 跑预检脚本，确认目标版本镜像、配置 diff、依赖服务健康度
   `bash ${HERMES_SKILL_DIR}/scripts/deploy_check.sh <service> <version>`
2. 生成发布计划给负责人确认（灰度比例、观察窗口、回滚阈值）
3. 按计划灰度，每阶段贴出关键指标
4. 出现阈值突破立即回滚，并在复盘里记录触发原因

## 验证

- 发布后 10 分钟核心接口 P99 与错误率回到基线
- 回滚演练：在预发环境至少验证过一次回滚路径
```

### 场景二：把仓库自带技能、信任流程与 CI 扫描串起来

背景：单仓库团队希望把「本仓库特有的发布方式」写在仓库里，而不是塞进每个人的全局技能目录；同时要防止别人往仓库塞一份带提示注入的技能。

第一步，技能进仓库（用 `.agents/skills/`，让 Codex、OpenCode、Hermes 都能读到同一份）：

```text
repo/
├── .agents/
│   └── skills/
│       └── repo-release/
│           ├── SKILL.md
│           └── scripts/release.sh
└── src/
```

SKILL.md 的要点是**限定在仓库语义内**，避免与全局同名技能互相干扰：

```yaml
---
name: repo-release
description: "Use only inside this repository when cutting a release branch, bumping versions, or writing the release note. Not for other repos."
version: 0.4.0
---

# 本仓库发布流程

1. `bash ${HERMES_SKILL_DIR}/scripts/release.sh --dry-run <version>` 生成变更集
2. 人工确认变更集后去掉 --dry-run 执行
3. 发布说明按 references/changelog-template.md 输出
```

第二步，开发机首次授权（一次即可，记录在配置里）：

```shell
cd ~/work/our-repo
hermes skills trust
```

```text
Trusted: /root/work/our-repo
1 project skill(s) will load in sessions started inside this repo (they take precedence over same-named profile skills).
```

第三步，CI 里加两道闸门。格式校验不依赖 agent，直接用 Python 检查 frontmatter 必需字段与目录名一致性：

```python
#!/usr/bin/env python3
"""CI: 校验 .agents/skills 下每个技能的目录名、必需字段与 description 长度。"""
import sys
from pathlib import Path

import yaml

REQUIRED = ("name", "description")
root = Path(".agents/skills")
bad = []

for skill_md in sorted(root.glob("*/SKILL.md")):
    front = skill_md.read_text(encoding="utf-8").split("---")[1]
    meta = yaml.safe_load(front) or {}
    for field in REQUIRED:
        if not str(meta.get(field, "")).strip():
            bad.append(f"{skill_md}: 缺少必需字段 {field}")
    if meta.get("name") != skill_md.parent.name:
        bad.append(f"{skill_md}: name={meta.get('name')} 与目录名 {skill_md.parent.name} 不一致")
    if len(str(meta.get("description", ""))) < 30:
        bad.append(f"{skill_md}: description 过短，无法作为触发依据")

if bad:
    print("\n".join(bad))
    sys.exit(1)
print("skills 校验通过")
```

```text
$ python3 ci/check_skills.py
skills 校验通过
```

安全扫描这一侧，安装与更新时 Hermes 会自己做，CI 里额外在合并前跑一次审查并把结论写进 PR：

```shell
hermes skills inspect my-company/company-skills/deploy-service   # 输出正文供评审
hermes skills audit --deep                                       # 本地已装技能的深扫
hermes security audit                                            # 供应链面（含插件与 MCP）
```

```text
合并前 PR 检查项（写进 PR 模板）：
- [ ] SKILL.md 的 description 含"何时用"与"何时不用"
- [ ] scripts/ 里没有 curl | bash，没有对 ~/.ssh、~/.aws、.env 的读取
- [ ] 版本号已按语义化版本递增，CHANGELOG 有对应条目
- [ ] 涉及写操作的步骤有 dry-run 或确认分支
- [ ] CI 的技能校验脚本通过
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先定作用域再动手：个人易变的技能放用户级，团队共享、必须随代码演进的放项目级，只有需要钩子或工具时才升级为插件。
2. 项目技能目录统一用 `.agents/skills/`：它是 Codex 与 OpenCode 也在扫描的约定路径，一份文件多处可用，比各工具各存一份好维护。
3. 装之前先 `inspect`，装之后跑一次 `audit`：Hub 扫描是自动防线，但「这个流程是否符合团队规范」只有人能判断。
4. 分发单元按团队规模选：小队用仓库内技能，多团队用 tap 仓库，需要锁定版本或带上钩子与工具时用插件包（pack 钉 commit SHA）。
5. 技能里的脚本一律通过模板变量引用自身目录（如 `${HERMES_SKILL_DIR}/scripts/`、Claude Code 侧的 `${CLAUDE_SKILL_DIR}`），不要写绝对路径，否则换个人、换个作用域就失效。
6. 密钥不进技能：需要密钥用 `required_environment_variables` 或 `required_credential_files` 声明，让工具在加载时做安全配置，别把值写进 SKILL.md。
7. 内部技能库要有 CODEOWNERS 与 PR 模板：技能是被模型执行的指令，评审强度应与脚本相当，而不是按文档处理。
8. 更新有节奏：`hermes skills check` 定期跑，技能仓库单独发布、单独回滚，避免「某次全局更新顺带改了三条发布流程」。

### 踩坑记录

```text
坑 1：把技能提交进仓库后，同事那边"看不到"
结论：文件在，git 状态干净，但 agent 从来不加载这条技能。
原因：Hermes 不自动加载克隆来的仓库技能，首次必须显式信任，且信任是仓库级而非会话级。
解法：在仓库里跑 hermes skills trust（或 hermes skills trust <path>），信任写入
      ~/.hermes/config.yaml 的 skills.trusted_project_dirs；确认后再排查其它原因。

坑 2：用 --force 装下了扫描结论为危险的技能
结论：本以为"顶多是个警告"，结果技能正文里有"读取外部 URL 并严格照做"的转发指令。
原因：--force 只能覆盖非危险的确认项，危险结论本应被拦下；把绕过机制当常规开关用就失去了防线。
解法：默认不用 --force；确需处理时先本地 inspect 出正文，把外部指令整段删除后再走正常评审装进来。

坑 3：更新技能后当前会话没变化，以为安装失败
结论：反复重装、反复查目录都没用，开新会话后才生效。
原因：系统提示里的技能索引在会话开始时构建，运行中的会话不会重建。
解法：开新会话（/reset）或用 /skill <name> 显式加载；批量改动后先确认"新会话生效"再验证。

坑 4：同名技能互相覆盖，行为忽左忽右
结论：仓库里改了流程，agent 仍按老流程执行，或反过来把全局技能当成本仓库的。
原因：作用域优先级（project > local > 外部目录）与各工具自己的覆盖规则不同，同名即冲突。
解法：先按作用域查同名项（hermes skills list 加各目录对比），再给技能名加仓库或领域前缀，
      不要指望"谁后装谁生效"。

坑 5：技能脚本写死绝对路径，别人一装就报错
结论：作者本机跑得通，同事装上直接失败。
原因：脚本路径按作者的家目录写死，作用域或机器一变就找不到。
解法：改用技能目录模板变量引用同级 scripts/，并把脚本的文件权限一起提交（工具通常只做调用不做赋权）。

坑 6：把内部技能 tap 建成了公开仓库
结论：内部流程、内网域名、值班群 ID 一起公开了。
原因：私有仓库与 tap 是两件事，tap 只要求"能被 git 读到"，不注意就把它建在了公开仓库上。
解法：内部 tap 用私有仓库并加访问控制；发布前 grep 内网域名、token 前缀、真实人名，确认无敏感信息再推。
```
