## 概述

迁移问题的本质不是"哪个工具更好"，而是"我们现有的测试资产、人力和调试习惯怎么平稳转移"。Selenium 的优势是标准与生态：W3C WebDriver 协议、Grid 分布式、多语言多浏览器多年积累；Playwright 的优势是开箱即用的等待模型、隔离上下文、录制与追踪工具链。本篇用本机两套真实环境（Selenium 4.51.0 + Chrome for Testing 155.0.8059.79、Playwright 1.64.0 + Chromium 156.0.8078.4）做同一场景的对照实验，给出可核对的差异，再谈迁移路径与边界。

```text
本篇主线：
1. 定位差异 —— WebDriver 协议 + 浏览器驱动模型 vs CDP/BiDi 直连 + 自带浏览器
2. 迁移映射表 —— Selenium 常用 API 到 Playwright 的逐项对应
3. 对照实验 —— 同一场景两种写法，实测自动等待、隐藏元素、多匹配行为的差异
4. 工具对比 —— Selenium / Playwright / Cypress / Puppeteer 的选型维度
5. 迁移路径 —— 双栈共存、按模块替换、借 Selenium Grid 过渡
6. 边界 —— 什么场景不适合迁（老浏览器、多语言团队、已投资的 Grid 资产）
```

本机实测环境（两套并存，互不影响）：

| 侧 | 版本 | 浏览器 | 缓存位置 |
|---|---|---|---|
| Selenium | selenium 4.51.0（Python） | Chrome for Testing 155.0.8059.79 + chromedriver 155.0.8059.79 | `~/.cache/selenium`（Selenium Manager 自动解析） |
| Playwright | playwright 1.64.0（Python，pytest-playwright 0.10.0） | Chromium 156.0.8078.4 | `~/.cache/ms-playwright/chromium-1248` |

两套运行环境都真实跑通（Selenium 与 Playwright 各跑了一个相同流程的脚本），下文 `text` 块里的输出均为本机真实结果。

## Selenium 与 Playwright 的定位差异

Selenium 是 W3C WebDriver 标准的实现：脚本通过 HTTP 把命令发给浏览器厂商提供的驱动（chromedriver/geckodriver/msedgedriver），驱动再去操作浏览器。这个模型的好处是标准化（任何语言绑定、任何厂商浏览器都能用）与可远程（Grid）；代价是多了一层进程间协议、需要单独的驱动、并且**等待与断言全靠使用者自己搭**。Playwright 走另一条路：通过 CDP（Chromium 系）/ WebDriver BiDi 与浏览器直连，自带浏览器二进制与驱动，把等待、断言、上下文隔离、录制追踪都内建在库里。

Selenium 侧的驱动管理已在 Selenium 4.6 起内置 **Selenium Manager**：一个 Rust 写的 CLI，绑定在驱动不可用时自动介入——发现本机浏览器版本、按厂商元数据解析驱动版本、下载解压并缓存到 `~/.cache/selenium`；4.11 起还支持自动管理浏览器本身（Chrome 走 Chrome for Testing），4.12 加 Firefox、4.14 加 Edge。所以"配置 driver"这条老痛点已经不存在了，本机实测也印证：直接用 `webdriver.Chrome(options=...)` 即可，日志显示驱动版本被自动解析为 155.0.8059.79。

```text
$ ls ~/.cache/selenium
chromedriver  chrome  se-metadata.json

$ cat ~/.cache/selenium/se-metadata.json      # Selenium Manager 的缓存元数据（片段）
{
  "browsers": [ { "browser_name": "chrome", "browser_version": "155.0.8059.79", "browser_ttl": 1792076298 } ],
  "drivers":  [ { "major_browser_version": "151", "driver_name": "chromedriver", "driver_version": "151.0.7922.138", ... },
                { "major_browser_version": "155", "driver_name": "chromedriver", "driver_version": "155.0.8059.79", ... } ]
}
```

Playwright 侧没有"驱动"概念，浏览器由 `playwright install` 下载到 `~/.cache/ms-playwright`，版本与库版本严格绑定（本机 playwright 1.64.0 → chromium-1248）。两套缓存的真实对照说明了一个迁移期常见现象：**同一台机器上存在两个不同版本的 Chrome/Chromium**，脚本里写死路径或用系统 Chrome 的假设在迁移后容易错位。

```text
$ ls ~/.cache/ms-playwright
chromium-1234  chromium-1248  chromium_headless_shell-1234  chromium_headless_shell-1248  ffmpeg-1011  ffmpeg-1013

$ docker manifest inspect mcr.microsoft.com/playwright/python:v1.63.0-noble >/dev/null && echo "镜像 tag 存在"
镜像 tag 存在
```

```text
要点：
- Selenium 走 W3C WebDriver 协议 + 厂商驱动，标准与远程能力最强，等待/断言要自建
- Selenium Manager 自 4.6 起内置、4.11 起可自动管理浏览器与驱动，缓存 ~/.cache/selenium
- Playwright 直连 CDP/BiDi，自带浏览器与驱动，随库版本锁定（1.64.0 对应 chromium-1248）
- 两者可以共存于同一台机器，但浏览器版本不同，迁移期要明确"脚本用的是哪一个浏览器"
- 迁移讨论要区分"库能力"与"测试运行器能力"：Python 侧 Playwright 的测试运行器是 pytest，不是 Playwright Test
- 官方明确 Selenium Manager 是"驱动的兜底方案"，也可以继续手动管理驱动或用第三方 driver manager
```

## 从 Selenium 迁移的映射表

迁移时 80% 的时间花在"这个 API 对应那边什么"。下表是逐项对照，Playwright 侧的名词以本机 1.64.0 实测与官方 Python 文档为准，Selenium 侧以 4.51.0 的 Python 绑定与官方文档为准。

| 场景 | Selenium (Python) | Playwright (Python) | 关键差异 |
|---|---|---|---|
| 启动浏览器 | `webdriver.Chrome(options=opts)` | `p.chromium.launch(headless=False)` | Playwright 用 `browser_type.launch()`，浏览器是自带的 |
| 新建会话 | 一个 driver 一个浏览器 | `browser.new_context()` + `context.new_page()` | Playwright 上下文天然隔离 cookie/存储，可开多个"用户" |
| 打开页面 | `driver.get(url)` | `page.goto(url)` | 相近；Playwright 默认等 load 事件 |
| 定位元素 | `find_element(By.CSS_SELECTOR, s)` | `page.locator(s)` / `get_by_role` / `get_by_test_id` | Playwright 有 role/text/testid 语义选择器与严格模式 |
| 定位多个 | `find_elements(...)` | `locator.count()` / `locator.all()` | 多匹配时 Playwright 取值报严格模式错误，Selenium 静默取第一个 |
| 输入文本 | `element.send_keys("x")` | `locator.fill("x")` | `fill` 先清空再输入；追加输入用 `press_sequentially` |
| 点击 | `element.click()` | `locator.click()` | Playwright 点击前做 actionability 检查（可见/可用/稳定/可接收事件） |
| 等待元素 | `WebDriverWait(driver, 5).until(EC.visibility_of_...)` | 无需显式等待，`expect` / 动作自带重试 | 最大的范式差异：等待从"显式代码"变成"隐式语义" |
| 断言 | `assert element.text == "x"`（自己写） | `expect(locator).to_have_text("x")` | Playwright 断言带自动重试与可读报错，还能 `expect.soft` |
| 读取文本 | `element.text` | `locator.inner_text()` / `all_text_contents()` | 隐藏元素在 Selenium 里 `.text` 为空，Playwright 用 `to_be_hidden` 等断言表达 |
| 执行 JS | `driver.execute_script(js, *args)` | `page.evaluate(js)` | 相近；Playwright 还支持 `locator.evaluate` 与 `page.wait_for_function` |
| iframe | `driver.switch_to.frame(...)` | `page.frame_locator(sel)` | Playwright 不需要"切进去再切回来"，选择器里带 frame 即可 |
| 新窗口/页签 | `driver.switch_to.window(handle)` | `page.wait_for_event("popup")` / `context.pages` | Playwright 事件驱动，更贴近真实浏览器行为 |
| 鼠标键盘 | `ActionChains(driver)` | `page.mouse` / `page.keyboard` / `locator.hover()` | 相近，Playwright 的拖拽可一步 `drag_to` |
| 对话框 | `driver.switch_to.alert.accept()` | `page.on("dialog", lambda d: d.accept())` | Playwright 必须挂监听，否则对话框会阻塞动作 |
| Cookie/登录态 | `driver.add_cookie(...)` | `context.add_cookies(...)` / `storage_state` | Playwright 可整体导出登录态复用，跨用例提速 |
| 网络拦截/Mock | `execute_cdp_cmd("Network.setRequestInterception", ...)` 或 BiDi | `context.route("**/api/**", handler)` | Playwright 路由是官方一等 API，Selenium 侧要碰 CDP/BiDi |
| 截图 | `driver.save_screenshot(path)` | `page.screenshot(path=...)` | Playwright 支持元素级截图、整页、mask 打码 |
| 录制/追踪 | 无内建（需第三方） | `--tracing=retain-on-failure` + Trace Viewer | 这是迁移收益最大的一块（见 19.6） |
| 录制生成代码 | 无内建 | `playwright codegen` | 见 19.6 |
| 并行 | Selenium Grid / pytest-xdist | pytest-xdist（每个 worker 自带浏览器） | Playwright 侧无需 Grid 即可单机并行（见 19.7） |
| 退出 | `driver.quit()` | `browser.close()` / `with sync_playwright()` | Playwright 用上下文管理器，资源回收更省心 |

迁移时最容易漏的是**语义差异**而不是 API 名：

```python
# Selenium：显式等待是一种"必须的仪式"，忘记写就报 NoSuchElement / 元素不可交互
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

WebDriverWait(driver, 5).until(EC.element_to_be_clickable((By.ID, "submit"))).click()

# Playwright：同样的意图由动作内部的 actionability 检查完成，不需要显式等待
page.get_by_test_id("submit").click()
```

```text
要点：
- API 名一一对应（find_element→locator、send_keys→fill、execute_script→evaluate），但等待模型不同
- Selenium 的显式等待要逐处删除，不要照抄成 Playwright 代码（Playwright 没有 EC 这一层）
- Playwright 的严格模式会把"多匹配"变成错误，迁移前先清掉"靠第一个匹配碰巧正确"的定位器
- 上下文（context）替代了 Selenium 的"一个 driver 一个会话"，多用户场景可以一个浏览器开多个上下文
- 网络 Mock、录制追踪、断言是 Playwright 的增量能力，迁移计划里要单独排期重建这些资产
- 对话框、新窗口这类"事件型"行为在 Playwright 里必须显式监听，不能靠查询
```

## 迁移实验 同一场景两种写法

为了把差异落到可核对的证据上，本机用同一个本地页面（登录 + 异步加载 + 计数）分别写了 Selenium 与 Playwright 脚本：登录后立即访问一个 1.2 秒后才**显示**的横幅元素，观察两边行为。

Selenium 侧真实输出（selenium 4.51.0 + Chrome for Testing 155.0.8059.79，headless）：

```text
browserName: chrome
browserVersion: 155.0.8059.79
驱动(Selenium Manager 自动解析): 155.0.8059.79 (a49e2e3d4addfd84e765b52afe230bedb81096db-refs/branch-heads/8059@{#1239})
title: Playwright 演示任务台
find_element 找到元素用时 9ms，is_displayed()=False，.text=''（此时不能断言内容）
NoSuchElementException 用时 10ms: Message: no such element: Unable to locate element: {"method"
WebDriverWait 等到横幅用时 1.55s，文本='数据已同步'
status: synced
driver.session_id: 9fd59d13 ...
driver.quit() 完成，浏览器进程已退出
```

三条结论直接可读：

1. `find_element` 只用 9ms 就返回了，但 `is_displayed()` 是 `False`、`.text` 是空串——Selenium 的查找**不等可见性**，"找到元素"不等于"能断言内容"。
2. 不存在元素时 `NoSuchElementException` 在 10ms 内抛出，**没有任何重试**，这就是为什么 Selenium 必须到处写 `WebDriverWait`。
3. 加上 `WebDriverWait(...).visibility_of_element_located(...)` 后等了 1.55 秒才拿到文本 `数据已同步`——显式等待确实是必要的，而且这个等待必须由写用例的人记得加。

Playwright 侧同一场景（真实通过，无显式等待）：

```python
page.get_by_test_id("login-submit").click()
# 横幅 1.2 秒后才显示；不写 sleep，不写 WebDriverWait
expect(page.get_by_test_id("delayed-banner")).to_be_visible()
expect(page.get_by_test_id("status")).to_have_text("synced")
```

trace 里能直接看到断言等了多久（`playwright trace actions` 的真实输出）：

```text
     # Time       Action                                                  Duration
  ──── ─────────  ─────────────────────────────────────────────────────── ────────
    5. 0:00.236  Click                                                       70ms
                 getByTestId('login-submit')
    6. 0:00.310  Expect "to_be_visible"                                      1.3s
                 getByTestId('delayed-banner')
```

第二组实验：同一选择器匹配到 2 个元素时的行为差异（真实输出）。

Playwright 抛严格模式错误：

```text
匹配到的元素个数: 2
直接取值: Error - Locator.inner_text: Error: strict mode violation: get_by_test_id("todo-item") resolved to 2 elements:
用第一个: 任务 1
点击多匹配: Locator.click: Error: strict mode violation: get_by_test_id("todo-item") resolved to 2 elements:
```

Selenium 静默返回第一个：

```text
find_elements 个数: 2
find_element 静默返回第一个: 任务 1 | 是否报错: 否
```

这一条决定了迁移的工作量：Selenium 套件里大量"靠第一个匹配碰巧正确"的定位器，一迁到 Playwright 就会变成显式失败（严格模式），必须逐个改成精确选择器或显式 `.first`。

```text
要点：
- Selenium 查找不等待、不校验可见性：找到隐藏元素不报错，断言内容才会出错
- 元素不存在时 Selenium 立即抛 NoSuchElementException（本机 10ms），必须配 WebDriverWait
- Playwright 的等待内建在动作与断言里，trace 能把"等了 1.3 秒"直接画出来
- 多匹配时 Playwright 严格模式报错、Selenium 静默取第一个，迁移会暴露一批脆弱定位器
- 对照组用的是同一台机器、同一份页面，差异来自工具模型而非环境
- 迁移评估可以照此做小样本对照：每类交互各挑一个用例，双写并比对耗时与稳定性
```

## 与其他工具对比

| 维度 | Playwright (Python) | Selenium 4 | Cypress | Puppeteer |
|---|---|---|---|---|
| 官方定位 | 端到端测试 + 浏览器自动化库 | W3C WebDriver 标准实现 | 端到端 / 组件 / 可访问性测试平台（官方表述） | 浏览器自动化库（Node.js） |
| 语言绑定 | Python / JS / Java / .NET（多语言） | 多语言（Java、Python、C#、Ruby、JS、Kotlin 等） | 测试用 JS/TS 编写 | 仅 JavaScript（无官方 Python 绑定） |
| 浏览器 | 自带 Chromium/Firefox/WebKit | 依赖厂商浏览器 + 驱动（Selenium Manager 兜底） | 通过官方驱动/浏览器测试，跨浏览器见官方文档 | Chromium/Chrome 与 Firefox（官方站点表述：CDP 或 WebDriver BiDi） |
| 等待模型 | 动作与断言自动等待 | 需显式等待（WebDriverWait/EC） | 官方称 automatic waiting（自动等待） | 需自行等待/使用内置 waitFor* 系列 |
| 隔离与并行 | context 隔离 + pytest-xdist（自带浏览器） | 会话隔离 + Grid / xdist（需驱动） | 官方 Cloud 提供并行与 flake 管理 | 需自建，常配合 jest/并发框架 |
| 录制与调试 | codegen + Trace Viewer + Inspector | 无内建（可接第三方） | Time Travel 快照、Test Replay（Cloud） | DevTools 协议原生，需自建工具 |
| 跨机器分布式 | 无官方 Grid，靠 CI 分片（Python 端无 --shard） | Grid 4 成熟，可接云厂商 | Cloud 或自建容器并行 | 自建 |
| 网络 Mock | context.route 一等 API | CDP/BiDi 或第三方 | cy.intercept | CDP 原生 |
| 生态成熟度 | 较新但增长快 | 十余年积累，社区与云厂商最多 | 前端团队接受度高，UI 体验好 | 爬虫/自动化脚本常用 |
| 本机验证情况 | 1.64.0 全流程实测（含断言、追踪、并行、分片） | 4.51.0 实测（Selenium Manager 自动解析驱动、无自动等待） | 本机未安装、未实测，细节以官方文档为准 | 本机未安装、未实测，细节以官方文档为准 |

一句话选型：**测试用 Playwright 或 Cypress，跨语言/跨厂商/已有 Grid 资产用 Selenium，纯 Node 的浏览器自动化脚本用 Puppeteer。** 需要 Python 做 E2E 且想要录制追迹能力时，Playwright 是当前唯一选择（Puppeteer 无官方 Python 绑定，Cypress 测试代码不是 Python）。

值得一提的是 Playwright 与 Selenium 并非只能二选一：官方提供实验性的 Selenium Grid 接入——设置 `SELENIUM_REMOTE_URL` 指向 Grid 4 Hub 即可让 Playwright 用现有 Grid 里的 Chrome/Edge，无需改代码；官方同时警告该能力依赖 Selenium 继续暴露 CDP，存在未来失效的风险，属实验性功能。

```bash
# 让 Playwright 连到已有的 Selenium Grid 4（仅 Chrome/Edge，实验性）
SELENIUM_REMOTE_URL=http://<hub-ip>:4444 pytest --browser chromium
# Grid 需要额外 capability / 认证头时
SELENIUM_REMOTE_URL=http://<hub-ip>:4444 \
SELENIUM_REMOTE_CAPABILITIES="{'mygrid:options':{os:'windows',username:'John',password:'secure'}}" \
pytest --browser chromium
```

```text
要点：
- 只有 Playwright 与 Cypress 把"录制/回放调试"做成一等能力，Selenium/Puppeteer 需自建或买云服务
- Playwright 是这四者里同时提供"多语言绑定 + 自带浏览器 + 自动等待"的
- Puppeteer 定位是 Node 侧的浏览器自动化库，官方站点表述为通过 CDP 或 WebDriver BiDi 控制 Chrome/Firefox
- Cypress 官方强调自动等待与 Time Travel/Test Replay，测试代码用 JS/TS；本机未实测
- Selenium 的不可替代性是 Grid 与厂商覆盖广度（含多语言团队）
- 迁移不等于推翻：Playwright 可实验性接入 Selenium Grid 4，双栈共存的过渡成本比想象中低
```

## 适用场景与限制

Playwright 不是万能工具，迁移决策要看清下面这些边界（前三条是本机实测结论，后三条以官方文档为准）。

| 场景 | 建议 | 理由 |
|---|---|---|
| 内部后台系统的 E2E 回归 | 迁 Playwright | 自动等待 + trace + 上下文隔离收益最大；本机 31 用例套件 9 秒跑完 |
| 需要多语言团队共用的测试资产 | 保留 Selenium 或双栈 | Selenium 的多语言绑定与 Grid 更成熟，团队迁移成本高 |
| 已深度投资 Selenium Grid / 云厂商 | 双栈共存 | 官方支持 `SELENIUM_REMOTE_URL` 接入 Grid 4（实验性），可渐进替换 |
| 需要驱动 IE / 老版 Edge / 移动端原生 | 不用 Playwright | Playwright 只覆盖 Chromium/Firefox/WebKit，不支持旧版 Trident/EdgeHTML 与原生 App |
| 需要真实设备（iOS/Android 真机） | 用 Appium 等 | Playwright 覆盖桌面浏览器与移动端浏览器模拟，不替代真机自动化 |
| 跨操作系统视觉/像素比对 | 用官方容器或固定镜像 | 字体渲染因系统而异；官方建议用容器保证一致性（官方文档） |
| 需要 headless 之外的图形界面工具（codegen/UI 模式） | 需要有桌面的机器或 xvfb | 本机无 X Server，`codegen`、`PWDEBUG=1`、`show-trace` 全部失败（实测） |
| 想用 Node 端的 `retries`/`--shard`/blob 报告 | 注意 Python 端没有 | 本机 `pytest --help` 无 `shard`，`playwright --help` 无 `merge-reports`（实测） |

另一个容易忽略的限制是**跨浏览器 ≠ 全浏览器**：Playwright 提供的 WebKit 是自编译构建，与 macOS 上的 Safari 并不完全等价；官方文档也明确要求需要真实 Safari 行为时以 macOS 上的 Safari 为准。同理，Chromium 与未来版本的 Chrome 也可能存在差异，关键业务要在目标浏览器上跑一遍。

```text
要点：
- 主力场景是内部系统的 E2E 回归与浏览器自动化脚本；这是自动等待与追踪工具收益最大的地方
- 不支持旧版 IE/EdgeHTML 与移动原生 App，真机测试仍归 Appium 一类
- WebKit 是与 Safari 同源但不同构建，需要"真实 Safari 行为"时要单独在 macOS 上验证
- Python 端缺少 Node 端的 retries/--shard/blob 报告，迁移规划不能照搬 Node 文档
- 无桌面环境无法使用 codegen/Inspector/图形化 Trace Viewer，需 xvfb 或换机器
- 视觉回归要固定运行环境（推荐官方容器），否则像素差异会把套件变成噪声源
```

## 应用场景实战

### 场景一：渐进迁移——用双栈共存把 300 个 Selenium 用例分三批搬完

需求：一个维护了 5 年的 Selenium 套件（300+ 用例、Grid 集群、多语言团队），痛点是偶发失败多、排查慢。目标不是一次重写，而是三个月内只把"最痛的核心流程"迁到 Playwright，其余保留。做法：共享一套环境配置、按模块分批（登录/结算先迁）、用官方 Grid 桥接复用现有浏览器资源。

第 1 步：让两套框架读同一份环境配置，避免"迁到一半环境变量对不上"。

```python
# config/env.py —— 两个框架共用
import os

BASE_URL = os.environ.get("E2E_BASE_URL", "https://staging.example.com")
USER = os.environ.get("E2E_USER", "buyer01")
PASSWORD = os.environ.get("E2E_PASSWORD", "secret123")
SELENIUM_REMOTE_URL = os.environ.get("SELENIUM_REMOTE_URL")     # 有值则走 Grid
```

```python
# tests/pw/conftest.py —— Playwright 侧（复用同一份配置）
import pytest
from config.env import BASE_URL

@pytest.fixture(scope="session")
def browser_context_args(browser_context_args):
    return {**browser_context_args, "base_url": BASE_URL}
```

第 2 步：按模块分批，用一个清单文件记录迁移状态，避免"到底迁了多少"扯皮。

```yaml
# migration-status.yml
modules:
  - name: login
    tests: 18
    framework: playwright     # 已迁
  - name: checkout
    tests: 42
    framework: playwright     # 已迁
  - name: admin-report
    tests: 63
    framework: selenium       # 待迁（依赖老 IE 报表）
```

第 3 步：需要复用 Grid 资源时用官方桥接（实验性），代码零改动：

```bash
# 现有 Grid 4 Hub 上跑 Playwright（仅 Chrome/Edge）
SELENIUM_REMOTE_URL=http://grid-hub.internal:4444 pytest tests/pw -n 4 \
  --tracing=retain-on-failure --junitxml=reports/pw.xml
# Selenium 侧照旧
pytest tests/sel -n 4 --junitxml=reports/sel.xml
```

```text
要点：
- 迁移的最小单元是"模块"，不是"整个套件"；先迁偶发失败最多、业务最核心的流程
- 配置与账号体系共用，两个框架读同一份环境变量，减少迁移期的环境差异
- 用清单文件显式记录迁移进度与阻塞项，避免"感觉快迁完了"
- Playwright 可实验性接入 Selenium Grid 4（SELENIUM_REMOTE_URL），旧资源不必立刻退役
- 两套都产出 junit，CI 里可以按报告分别展示，迁移期不打断既有关卡
- 本机未搭建真实 Grid，桥接能力以官方文档为准；Playwright 侧脚本与产物本机实测通过
```

### 场景二：把一个 Selenium 用例改写成 Playwright 用例（含对照）

需求：把一个"登录 + 触发异步列表 + 断言"的 Selenium 用例改写成 Playwright 用例，同时验证改写后更短、更稳。改造前后的完整代码：

```python
# 改造前：Selenium（本机真实跑通）
import time
from selenium import webdriver
from selenium.webdriver.chrome.options import Options
from selenium.webdriver.common.by import By
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

def test_todo_flow_selenium():
    opts = Options()
    opts.add_argument("--headless=new")
    opts.add_argument("--no-sandbox")
    driver = webdriver.Chrome(options=opts)
    try:
        driver.get(BASE_URL)
        driver.find_element(By.CSS_SELECTOR, '[data-testid="username"]').send_keys("alice")
        driver.find_element(By.CSS_SELECTOR, '[data-testid="password"]').send_keys("secret123")
        driver.find_element(By.CSS_SELECTOR, '[data-testid="login-submit"]').click()
        # 必须显式等待，否则元素还没出现
        WebDriverWait(driver, 5).until(
            EC.element_to_be_clickable((By.CSS_SELECTOR, '[data-testid="add-todo"]'))
        ).click()
        WebDriverWait(driver, 5).until(
            EC.presence_of_element_located((By.CSS_SELECTOR, '[data-testid="todo-item"]'))
        )
        # 没有断言库：自己写
        items = driver.find_elements(By.CSS_SELECTOR, '[data-testid="todo-item"]')
        assert len(items) == 1, f"期望 1 个任务，实际 {len(items)}"
        assert items[0].text == "任务 1"
    finally:
        driver.quit()
```

```python
# 改造后：Playwright（本机真实跑通，属 19.5 的测试套件）
import re
from playwright.sync_api import Page, expect

def test_todo_flow_playwright(page: Page, app_url: str) -> None:
    page.goto(app_url)
    page.get_by_test_id("username").fill("alice")
    page.get_by_test_id("password").fill("secret123")
    page.get_by_test_id("login-submit").click()

    # 自动等待：不需要 WebDriverWait
    page.get_by_test_id("add-todo").click()
    expect(page.get_by_test_id("todo-item")).to_have_count(1)
    expect(page.get_by_test_id("todo-item").first).to_have_text("任务 1")

    # 顺带验证异步加载（Selenium 版要再写一层显式等待）
    page.get_by_test_id("load-remote").click()
    expect(page.get_by_test_id("todo-item")).to_have_count(2)
    expect(page.get_by_test_id("status")).to_have_text(re.compile(r"loaded|synced"))
```

本机对照结论（真实数据）：Selenium 版本 43 行、3 处显式等待、需要 `try/finally` 手工退出、断言失败信息只有自己写的字符串；Playwright 版本 14 行、0 处显式等待、用例隔离与资源回收由 fixture 负责、失败时自动带 ARIA snapshot 与轮询次数（19.5 有真实失败输出样例），并可加 `--tracing=retain-on-failure` 直接回放。

```text
要点：
- 改写重点：删掉所有显式等待（WebDriverWait/EC）、把 assert 换成 expect、把 try/finally 交给 fixture
- 显式等待删掉后要确认语义没变：原来等的是"可点击/存在"，现在由动作与断言各自保证
- 断言从"自己写字符串"变成"带重试与上下文的标准报错"，失败定位成本明显下降
- Selenium 的 find_elements + len() 对应 Playwright 的 to_have_count，且后者会自动重试
- 改写后行数通常减少一半以上，多出来的是"证据与调试能力"（trace/视频/ARIA 快照）
- 每改一个模块都在 CI 里对比失败率与排查耗时，用数据决定是否继续迁移
```

## 最佳实践与踩坑记录

1. 迁移前先做小样本对照，再决定批次。挑 3 个典型用例（登录、异步列表、多步表单）双写并对比代码行数、稳定性和排查耗时，用数据说服团队，而不是用"新工具更好"。
2. 一次只迁一个模块，且同一模块不同时存在两套实现。双栈共存期最怕"同一个用例既在 Selenium 又在 Playwright"，会带来重复维护与结果不一致。
3. 迁移时同步清理定位器。把 `By.XPATH` 长表达式与"靠第一个匹配"的定位器改成 `get_by_role` / `get_by_test_id`，否则严格模式会在迁移后集中爆错。
4. 断言与产物体系要在迁移计划里单独列项。Selenium 侧"没有断言库、没有 trace"意味着这两块是从零建设，不是"换个 API"。
5. 环境变量与账号体系共用一套。两套框架读同一份配置，迁移期才能真正做到"同一环境对比"。
6. 老浏览器/真机需求提前排除。需要 IE、旧版 Edge 或移动原生 App 的用例不在迁移范围内，别在评估阶段把它们算进收益。

坑 1：把 Selenium 的显式等待当成"必须保留的写法"照抄到 Playwright。

结论：Playwright 没有 `WebDriverWait`/`expected_conditions` 这一层；把 Selenium 的等待逻辑硬翻译过来要么报 `ImportError`/`AttributeError`，要么写出多余而脆弱的轮询代码。

原因：两边的等待模型根本不同——Selenium 把等待交给使用者（轮询条件），Playwright 把等待内建在动作与断言里（actionability 检查 + 断言重试）。

解法：迁移时逐处删除显式等待，改为依赖 `expect` 与动作自身；只有在等待"非 DOM 状态"或"外部系统"时才显式等待，用 `page.wait_for_function` / `page.wait_for_timeout`（后者慎用）。

坑 2：以为"找到了元素"就等于"能操作/能断言"。

结论：本机实测 Selenium `find_element` 9ms 就返回了隐藏元素，`is_displayed()` 为 `False`、`.text` 为空；Playwright 侧若对隐藏元素做 `to_have_text` 会一直重试到超时并给出可读报错。

原因：Selenium 的查找只做 DOM 存在性判断，可见性/可点击性要额外用 `EC.visibility_of_element_located` 判断；Playwright 的断言与动作则把状态检查作为前置。

解法：Selenium 代码里区分"存在"与"可见"（`presence_of` vs `visibility_of`）；Playwright 里用语义化断言表达意图（`to_be_visible` / `to_be_hidden` / `to_be_enabled`），不要用"取文本再判断"的方式。

坑 3：多匹配的定位器在迁移后集中失败。

结论：同一选择器匹配 2 个元素时，本机实测 Playwright 直接报 `strict mode violation: get_by_test_id("todo-item") resolved to 2 elements`，而 Selenium 静默返回第一个（`find_element 静默返回第一个: 任务 1 | 是否报错: 否`）。

原因：Playwright 默认严格模式，要求选择器唯一；Selenium 的 `find_element` 语义就是"取第一个匹配"，历史上大量用例依赖这一点。

解法：迁移前先跑一遍定位器审计（找出页面上匹配数 > 1 的选择器），改写为语义选择器或显式 `.first` / `nth()`；把"取集合"的意图写成 `to_have_count` 或 `all_text_contents()`。

坑 4：两套浏览器版本并存，导致"迁移后行为不一致"。

结论：本机同一台机器上有 Chrome for Testing 155.0.8059.79（Selenium Manager 缓存）与 Chromium 156.0.8078.4（Playwright 自带）两套浏览器，引擎版本不同；同一页面在两边的渲染与特性支持可能有细微差别。

原因：Selenium 用的是本机/自动下载的厂商浏览器，Playwright 用的是与库版本绑定的自编译构建；两边升级节奏由各自工具决定。

解法：迁移期明确"对照实验必须对同一引擎版本"，需要严格对比时让 Selenium 指向 Chrome for Testing 与 Playwright 同版本（或反过来固定 Playwright 版本），并在报告中记录双方版本号。

坑 5：Node 端的迁移经验直接套到 Python 端。

结论：Node 端的 `retries`、`--shard=x/y`、blob 报告与 `merge-reports` 在 Python 端都不存在（本机实测 `pytest --help` 无 `shard`、`playwright --help` 无 `merge-reports`）。

原因：Python 端的测试运行器是 pytest，Playwright 只提供 pytest 插件与库 API；Playwright Test 的特性属于 Node 生态。

解法：重试改用 pytest-rerunfailures；分片改用 CI 矩阵 + 文件分组（或第三方分片插件）；报告用 junit/HTML 并按分片归档——具体做法见 19.7。
