## 概述

Playwright 的稳定性主要来自两件事：一是 `Locator` 这种「惰性定位器」——它保存的是查找规则而不是 DOM 句柄，每次使用都会重新解析；二是**自动等待**——点击、填充、断言之前先做可操作性检查（可见、稳定、可交互、启用、可编辑），任何一项不满足就自动重试直到超时。理解了这两点，就不会再写出「先 sleep 两秒再点」的用例。本篇讲清内置定位器的选择顺序、定位器 API 的组合用法、自动等待到底检查什么、断言式等待的失败日志怎么读，以及与显式等待的取舍。

```text
本篇主线：
1. 定位器优先级 —— 角色 > 标签 > 占位符/文本/alt/title > test id > CSS/XPath
2. 选择器语法 —— CSS 与 XPath 可自动识别，但不要用于跑长链式结构
3. 惰性求值 —— Locator 每次动作重新解析 DOM，元素重建后同一定位器依然可用
4. 严格模式 —— 动作类 API 命中多个元素直接报错，count()/all() 例外
5. 自动等待 —— visible / stable / receives events / enabled / editable 五类检查
6. 断言式等待 —— expect() 自动重试，失败日志会打印重试次数与 aria 快照

官方文档：
- 定位器：https://playwright.dev/python/docs/locators
- 其它定位器（CSS/XPath/Shadow）：https://playwright.dev/python/docs/other-locators
- 自动等待：https://playwright.dev/python/docs/actionability
- 断言：https://playwright.dev/python/docs/test-assertions
```

本机实测环境：playwright 1.64.0 + Chromium 156.0.8078.4，目标页面是本机 `python3` 起的实验台（`http://127.0.0.1:8811`）。下文所有 `text` 块均为本机真实输出。

## 内置定位器与选择器语法

官方推荐按「用户如何感知页面」来定位，因此优先级是：`get_by_role()`（无障碍角色与可访问名）> `get_by_label()`（表单控件）> `get_by_placeholder()` / `get_by_text()` / `get_by_alt_text()` / `get_by_title()` > `get_by_test_id()`（显式测试契约）> `locator("css=...")` / `locator("xpath=...")`（最后手段）。角色定位器依托 W3C ARIA 与 HTML 的隐式角色映射，改了样式和层级它照样能用；CSS 长链一旦 DOM 结构调整就会失效。

```python
import re

from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("http://127.0.0.1:8811/index.html")

    # 推荐：角色（含可访问名）与 label 定位
    page.get_by_role("heading", level=1)                       # 隐式角色
    page.get_by_label("用户名").fill("alice")                    # 关联 label 文本
    page.get_by_role("button", name=re.compile("登录")).click()  # 自动等到按钮可用

    # 没有 label 时的补充手段
    page.get_by_placeholder("请输入用户名").fill("alice")
    page.get_by_alt_text("playwright logo")
    page.get_by_title("Issues count")
    page.get_by_test_id("item-apple").click()

    # 最后手段：CSS / XPath（可省略 css= / xpath= 前缀自动识别）
    print("css 按钮数:", page.locator("css=button").count())
    print("xpath 按钮数:", page.locator("xpath=//button").count())
    browser.close()
```

上面这段在本机真实运行输出（`css` 与 `xpath` 都能命中同一批元素）：

```text
css 按钮数: 4
xpath 按钮数: 4
```

本机真实运行结果（含 `get_by_*` 各家族与 CSS/XPath 的命中情况）：


```text
选择器要点：
- 交互元素（button/a/input）优先用 role；非交互元素（div/span/p）用 text
- 按文本匹配会规范化空白：多空格压成一个、换行变空格、忽略首尾空白
- exact=True 才是严格相等，默认是子串匹配
- get_by_test_id 默认匹配 data-testid，可用 selectors.set_test_id_attribute 改成 data-pw 等
- CSS/XPath 只应在无法用用户视角定位时使用，禁止写 #tsf > div:nth-child(2) 这类长链
- 角色定位器不替代无障碍审计，它只是更贴近用户视角的定位方式
- 官方定位器优先级说明：https://playwright.dev/python/docs/locators
```

## 定位器 API 惰性求值与严格模式

`page.get_by_role(...)` 返回的 `Locator` 不是元素句柄，而是一段**查找规则**。每次动作都会用最新 DOM 重新解析，所以前端重渲染、列表刷新之后，同一个 `Locator` 变量依然指向「当前符合条件的那个元素」。这也意味着定位器是**严格**的：动作类 API 一旦命中多个元素就直接报错，避免「点错元素但用例通过」这种最危险的假绿。

```python
# 严格模式：页面上有 3 个同名按钮
page.get_by_role("button", name="加入购物车").click()   # 抛 Error，不会“点第一个”
page.get_by_role("button", name="加入购物车").count()   # 3，多元素操作合法
```

本机真实报错（异常类与首行原样）：

```text
异常类: Error
首行: Locator.click: Error: strict mode violation: get_by_role("button", name="加入购物车") resolved to 3 elements:
count() 对多元素合法: 3
```

```python
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()

    # 1) 惰性：DOM 重建后同一定位器依然可用
    page.set_content("<div id='box'><button>旧</button></div>")
    loc = page.get_by_role("button")          # 只保存规则，不锁定元素
    print(loc.inner_text())                   # -> 旧
    page.evaluate("document.getElementById('box').innerHTML = '<button>新</button>'")
    print(loc.inner_text())                   # -> 新

    # 2) 组合与收敛：先定位行，再在行内定位按钮
    page.goto("http://127.0.0.1:8811/index.html")
    rows = page.get_by_role("listitem")
    rows.filter(has_text="橙子").get_by_role("button").click()
    print("橙子行标记:", rows.filter(has_text="橙子").get_attribute("data-cart"))
    print("含按钮的行数:", rows.filter(has=page.get_by_role("button")).count())
    print(rows.nth(1).inner_text().replace("\n", " "), "|",
          rows.first.inner_text().split("\n")[0], "|",
          rows.last.inner_text().split("\n")[0])
    print([r.inner_text().split("\n")[0] for r in rows.all()])
    print(rows.evaluate_all("ls => ls.map(e => e.dataset.testid)"))
    browser.close()
```

本机真实输出：

```text
== 块 A：惰性求值与组合收敛 ==
旧
新
橙子行标记: 1
含按钮的行数: 3
香蕉加入购物车 | 苹果加入购物车 | 橙子加入购物车已加入
['苹果加入购物车', '香蕉加入购物车', '橙子加入购物车已加入']
['item-apple', 'item-banana', 'item-orange']
```

```text
定位器 API 要点：
- Locator 惰性重解析，不要担心 DOM 重建让变量失效；ElementHandle 才需要当心
- 动作类 API 严格匹配；count() / all() / evaluate_all() 属于多元素操作，不报错
- 收敛手段优先级：唯一角色名 > filter(has_text/has/not_) > nth/first/last
- nth/first/last 依赖顺序，页面一变就指向别的元素，官方明确不推荐长期使用
- all() 会一次性解析成列表；需要持续监听时用 count() + nth(i) 循环
- evaluate_all 在页面上下文里跑，适合批量取属性，比逐元素 inner_text 快
- 严格模式是保护而非障碍，报错说明定位器不够精确，去修定位器而不是加 .first
```

## 自动等待与可操作性检查

每个动作在执行前都会做可操作性检查，全部通过才真正执行，否则在超时时间内轮询重试，超时抛 `TimeoutError`。`locator.click()` 会依次确认：定位器精确命中一个元素、元素可见、元素稳定（至少两帧内包围盒不变）、元素能接收事件（该坐标的命中目标不是别的元素遮挡）、元素处于启用状态。

| 动作 | Visible | Stable | Receives Events | Enabled | Editable |
|---|---|---|---|---|---|
| locator.check() | 是 | 是 | 是 | 是 | - |
| locator.click() | 是 | 是 | 是 | 是 | - |
| locator.dblclick() | 是 | 是 | 是 | 是 | - |
| locator.set_checked() | 是 | 是 | 是 | 是 | - |
| locator.tap() | 是 | 是 | 是 | 是 | - |
| locator.uncheck() | 是 | 是 | 是 | 是 | - |
| locator.hover() | 是 | 是 | 是 | - | - |
| locator.drag_to() | 是 | 是 | 是 | - | - |
| locator.screenshot() | 是 | 是 | - | - | - |
| locator.fill() | 是 | - | - | 是 | 是 |
| locator.clear() | 是 | - | - | 是 | 是 |
| locator.select_option() | 是 | - | - | 是 | - |
| locator.select_text() | 是 | - | - | - | - |
| locator.scroll_into_view_if_needed() | - | 是 | - | - | - |
| locator.blur() / focus() / press() / press_sequentially() | - | - | - | - | - |
| locator.dispatch_event() | - | - | - | - | - |
| locator.set_input_files() | - | - | - | - | - |

各项判定的精确定义：

| 判定 | 定义 |
|---|---|
| visible | 有非空包围盒，且计算样式不是 `visibility:hidden`。零尺寸不算可见，`opacity:0` **算**可见 |
| stable | 连续两个动画帧内包围盒没有变化 |
| enabled | 不是 disabled；`button/select/input/textarea/option/optgroup` 带 `[disabled]`、或处于带 `[disabled]` 的 `fieldset` 内、或祖先有 `aria-disabled=true` 都算 disabled |
| editable | 既 enabled 又没有 `readonly`（`select/input/textarea` 带 `[readonly]`，或有 `aria-readonly=true` 且角色支持） |
| receives events | 在该动作坐标上，指针事件的命中目标就是它自己（不被遮罩层截走） |

本机实测：可见性定义的四个边界情况，以及「按钮 500ms 后才从 disabled 变可用」时 `click()` 自动等待的真实耗时。

```text
== 2. 可见性定义（自动等待的依据之一） ==
#zero.is_visible(): False
#opacity.is_visible(): True
#hidden.is_visible(): False
#none.is_visible(): False

== 6. 自动等待 enabled：按钮在 500ms 后才可用 ==
fill 耗时(秒): 0.484
click 耗时(秒): 0.996
到断言通过耗时(秒): 0.803
状态文本: 欢迎回来，ALICE

== 7. 超时错误长什么样（元素不存在） ==
耗时(秒): 1.5
异常类: TimeoutError
首行: Locator.click: Timeout 1500ms exceeded.
日志行数: 3

== 8. force 跳过可见性 / 接收事件检查 ==
默认 click 失败: Locator.click: Timeout 1200ms exceeded.
force=True 点击成功，耗时(秒): 0.005
```

`force=True` 会跳过非必要的可操作性检查（例如「能接收事件」），本机实测常规 `click()` 在被遮罩层挡住时超时失败，加 `force=True` 后 5 毫秒即完成——这类写法只适合明确知道自己在做什么的场景，否则会把「点不到」的真实缺陷掩盖掉。

```text
自动等待要点：
- 五类检查：visible / stable / receives events / enabled / editable，按动作取子集
- 判定标准来自官方表，别凭直觉：opacity:0 可见、零尺寸不可见
- 等待逻辑内建，不需要手写 sleep；也意味着用例不需要「等页面稳定」的前置步骤
- force=True 跳过非必要检查，会掩盖遮挡类缺陷，只在必要时用
- 检查不通过的最终表现是 TimeoutError，msg 里会写清卡在哪一步
- 与网络相关的等待（响应、空闲）是另一套机制，见 19.4
- 官方检查明细：https://playwright.dev/python/docs/actionability
```

## 断言式等待与超时解读

`expect()` 提供的是**自动重试断言**：条件不满足就每轮重新求值，直到满足或超时（默认 5000ms）。这与普通 `assert` 的区别是：普通断言在元素还没渲染出来时立刻失败，`expect` 会等。失败时抛 `AssertionError`，日志里有重试次数、实际值、以及一份 aria 快照——不用截图就能大致还原页面状态。

```python
from playwright.sync_api import expect

expect(page).to_have_title("Playwright 实验台")
expect(page.locator("#status")).to_contain_text("欢迎回来")
expect(page.locator("#goods li")).to_have_count(3)
expect(page.get_by_role("button", name="登录")).to_be_enabled()
expect(page.get_by_role("button", name="登录")).to_have_attribute("type", "submit")
expect(page.get_by_role("button", name="登录")).to_be_visible()
```

本机真实输出（通过路径与故意失败路径的日志）：

```text
== 10. expect 断言式等待（通过 + 失败日志） ==
to_contain_text 通过
to_have_count(3) 通过
to_be_enabled 通过
to_have_attribute 通过
故意失败断言耗时(秒): 2.0
异常类: AssertionError
  Locator expected to have count '3'
  Actual value: 1
  Call log:
    - Expect "to_have_count" locator("#goods") with timeout 2000ms
    - waiting for locator("#goods")
      21 × locator resolved to 1 element
```

失败日志的读法：第一行是断言意图，`Actual value` 是最后一次取到的值，`Call log` 里的 `21 × locator resolved to 1 element` 表示重试了 21 轮、每轮都拿到 1 个元素——说明**定位器没问题、数据不对**；如果写的是 `waiting for locator(...)` 而没有 resolved，则说明元素根本没出现，那要查定位器或页面报错。`expect` 还有 `expect.soft()`（失败不中断，最后统一报）与 `expect.configure(timeout=...)`（批量改超时）两种用法。

```text
断言式等待要点：
- expect 默认 5000ms 超时，重试间隔由框架控制，不要自己写循环
- 失败日志区分「定位器没解析出来」与「解析出来了但值不对」，这是排错分水岭
- to_be_visible 用的就是自动等待的 visible 判定，与动作前检查同源
- 软断言 expect.soft() 适合一次跑完所有校验再汇总失败
- 断言超时不要盲目调大，先确认是应用慢还是断言写错
- 断言清单与参数以官方文档为准：https://playwright.dev/python/docs/test-assertions
```

## 显式等待与反模式对比

自动等待覆盖了绝大多数场景，但仍有几类情况需要显式等待：等待 DOM 节点出现或消失、等待 URL 变化、等待某个状态机转移。`locator.wait_for(state=...)` 支持 `attached` / `detached` / `visible` / `hidden`（默认 `visible`），`page.wait_for_url()`、`page.wait_for_function()` 用于其它条件。反模式则是 `time.sleep()`：它既慢又不可靠——页面快了白等，页面慢了还是会失败。

```python
import time
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("http://127.0.0.1:8811/index.html")
    page.get_by_label("用户名").fill("bob")
    page.get_by_role("button", name="登录").click()

    # 反模式：固定睡 2 秒，慢且不可靠
    time.sleep(2)

    # 正确：等到真正关心的状态
    page.get_by_text("欢迎回来").wait_for(state="visible", timeout=5000)
    page.locator("#status").wait_for(state="attached")
    page.get_by_role("button", name="登录").wait_for(state="visible")
    browser.close()
```

本机真实输出：

```text
== 9. wait_for 系列 ==
wait_for(state='visible') 通过: 欢迎回来，BOB
is_visible(): True
attached 状态可等待: 1
wait_for 默认 state 为 visible
```

```text
== 块 B：wait_for 系列 ==
wait_for visible 通过，含 2 秒 sleep 共耗时(秒): 2.01
attached / visible 均通过
```

```text
等待策略对比：
- 优先顺序：断言式等待 expect > 动作自动等待 > wait_for 显式状态 > wait_for_function
- time.sleep 是反模式：既拖慢用例又无法覆盖更慢的情况
- wait_for(state="hidden") 适合等加载遮罩消失；"detached" 适合等弹窗从 DOM 移除
- 默认 state 是 "visible"，省略参数时行为与 to_be_visible 一致
- 等待 URL 与网络载荷用 wait_for_url / expect_response（后者见 19.4）
- 等待条件越具体越好，避免用「页面完全空闲」这类粗粒度条件
```

## Shadow DOM 与链式定位

Playwright 的定位器**默认穿透 Shadow DOM**：页面里有自定义 Web Component 时，不需要写特殊的 shadow 选择器，按普通规则定位即可。两个例外是 XPath 不穿透 shadow root，以及 `closed` 模式的 shadow root 无法进入。链式定位则用于层层收敛：先定位容器，再在其内部定位子元素，定位器可在 `Page`、`Locator`、`FrameLocator` 上继续链式调用。

```python
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content("""
      <x-details role=button aria-expanded=true aria-controls=inner-details>
        <div>Title</div>
        <template id="tpl"><div id="inner-details">Details</div></template>
      </x-details>
      <script>
        const host = document.querySelector('x-details');
        const root = host.attachShadow({mode: 'open'});
        root.append(document.getElementById('tpl').content);
      </script>
    """)
    print("穿透 shadow root:", page.get_by_text("Details").inner_text())

    # 链式：先收敛到列表行，再在行内定位按钮
    page.set_content("<ul><li>John<button>Say hello</button></li><li>Mary<button>Say goodbye</button></li></ul>")
    row = page.get_by_role("listitem").filter(has_text="Mary")
    print("行内按钮文本:", row.get_by_role("button").inner_text())
    browser.close()
```

本机真实输出（自定义元素 + open shadow root）：

```text
穿透 shadow root: Details
行内按钮文本: Say goodbye
```

```text
Shadow DOM 与链式要点：
- 定位器默认穿透 shadow root，直接按角色/文本写即可
- 例外：XPath 不穿透；closed 模式的 shadow root 无法访问
- 链式定位让定位器更精确，同时天然规避严格模式冲突
- Locator 上的 get_by_* 与 filter 会缩小搜索范围到该元素子树
- iframe 内的定位要换 FrameLocator，属于跨文档边界（详见 19.3）
- 官方其它定位器说明：https://playwright.dev/python/docs/other-locators
```

## 应用场景实战

### 场景一：把脆弱选择器重写成稳定定位器

后台改版后老用例大面积失败，原因是选择器写成了 DOM 层级链。做法是先用新页面复现「脆弱写法命中 0 个元素」，再换成角色/标签定位器，并把结果断言换成断言式等待。

```python
# rewrite_locator.py —— 脆弱选择器与稳定定位器对比
from playwright.sync_api import sync_playwright, expect

BASE = "http://127.0.0.1:8811"

# 脆弱写法：依赖 body > form > div 层级与 nth-of-type 序号
FRAGILE = "body > form#login > div:nth-child(1) > input:nth-of-type(1)"

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto(BASE + "/index.html")

    print("== 脆弱写法 ==")
    print("命中数:", page.locator(FRAGILE).count())      # 结构一变就是 0
    print("说明: 依赖 DOM 层级与序号，加一个 div 就断")

    print("\n== 稳定写法 ==")
    stable = page.get_by_label("用户名")                  # 按表单标签定位
    print("get_by_label('用户名') 命中数:", stable.count())
    print("对应元素 id:", stable.get_attribute("id"))
    print("aria 名字来源:", stable.evaluate("e => e.labels[0].textContent.trim()"))

    print("\n== 断言式等待：登录后异步出现的结果 ==")
    page.get_by_label("用户名").fill("qa-01")
    page.get_by_label("密码").fill("secret")
    page.get_by_role("button", name="登录").click()
    expect(page.locator("#status")).to_contain_text("欢迎回来，QA-01", timeout=5000)
    print("状态:", page.locator("#status").inner_text())
    expect(page.get_by_role("button", name="登录")).to_be_enabled()
    browser.close()
```

本机真实运行输出：

```text
== 脆弱写法 ==
命中数: 0
说明: 依赖 DOM 层级与序号，加一个 div 就断

== 稳定写法 ==
get_by_label('用户名') 命中数: 1
对应元素 id: username
aria 名字来源: 用户名

== 断言式等待：登录后异步出现的结果 ==
状态: 欢迎回来，QA-01
```

### 场景二：列表行内操作与行级断言

商品列表里每行都有同名按钮，「直接点按钮」会触发严格模式报错。做法是先用文本过滤出行，再在行内定位按钮，最后断言行内出现的结果标记——这也是把 `filter(has_text=...)` 与 `filter(has=...)` 组合起来的典型写法。

```python
# row_action.py —— 行内定位与自动等待断言
from playwright.sync_api import sync_playwright, expect

BASE = "http://127.0.0.1:8811"

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto(BASE + "/index.html")

    rows = page.get_by_role("listitem")
    expect(rows).to_have_count(3)

    # 先按文本过滤行，再在行内定位按钮（避免命中 3 个同名按钮）
    orange = rows.filter(has_text="橙子")
    orange.get_by_role("button", name="加入购物车").click()

    # 自动等待：点击后行内出现「已加入」标记
    expect(orange.get_by_text("已加入")).to_be_visible()
    print("橙子行 cart 标记:", orange.get_attribute("data-cart"))
    print("橙子行文本:", orange.inner_text().replace("\n", " / "))

    # 未点击的行不应有标记，行级断言天然避免了串行污染
    apple = rows.filter(has_text="苹果")
    print("苹果行 cart 标记:", apple.get_attribute("data-cart"))

    # 顺序相关定位用 nth()，仅用于确实与顺序绑定的断言
    print("第 2 行文本:", rows.nth(1).inner_text().replace("\n", " / "))
    browser.close()
```

本机真实运行输出：

```text
橙子行 cart 标记: 1
橙子行文本: 橙子加入购物车 / 已加入
苹果行 cart 标记: None
第 2 行文本: 香蕉加入购物车
```

## 最佳实践与踩坑记录

1. 定位器优先级从角色开始：写之前先问「用户怎么找到这个元素」，能写出可访问名就别用 CSS。
2. 给稳定的测试契约加 `data-testid`，仅在角色与文本都不合适时使用，并在项目规范里固定命名。
3. 用 `filter()` / 链式定位收敛，不要用 `.first` / `.nth()` 兜住严格模式报错——那只是把不确定性往后推。
4. 断言用 `expect()`，不要用裸 `assert` 加 `sleep`；失败日志里的重试次数是判断「定位器问题还是数据问题」的关键线索。
5. 只对真正关心的状态显式等待（`wait_for(state=...)`），不要用「等页面完全空闲」这种粗粒度条件。
6. 遇到超时先看错误消息里的具体检查项（visible / stable / enabled / receives events），它对应用例失败的真实原因。

坑 1：点击时报 strict mode violation，提示命中多个元素
结论：动作类 API 要求唯一命中，`get_by_role("button", name="加入购物车")` 在 3 行列表里会直接报错，而不是「点第一个」。
原因：Playwright 用严格模式避免点到不可预期的元素。
解法：用 `filter()` 或链式定位收敛到唯一元素；`count()` / `all()` / `evaluate_all()` 属于多元素操作，不会报错。

```text
异常类: Error
首行: Locator.click: Error: strict mode violation: get_by_role("button", name="加入购物车") resolved to 3 elements:
count() 对多元素合法: 3
```

坑 2：元素「明明在页面上」却点不动，一直超时
结论：可见不等于可点。本机实测被绝对定位遮罩覆盖的按钮，常规 `click(timeout=1200)` 直接超时，`force=True` 才在 5 毫秒内完成。
原因：`click()` 还会检查「接收事件」——该坐标上的指针事件命中目标不能是别的元素。
解法：先排查遮罩层/动画/未关闭的弹窗，修页面或先关闭遮罩；确认无副作用时才用 `force=True`，因为它会掩盖真实缺陷。

```text
默认 click 失败: Locator.click: Timeout 1200ms exceeded.
force=True 点击成功，耗时(秒): 0.005
```

坑 3：用 `opacity:0` 或零尺寸元素做判断，预期与实际相反
结论：`opacity:0` 的元素**算**可见，宽高为 0 的元素**不算**可见；`visibility:hidden` 与 `display:none` 都不可见。
原因：官方的 visible 定义是「有非空包围盒且计算样式不是 visibility:hidden」。
解法：断言可见性时看清是哪种「隐藏」；用透明度做动画时，等它变成非零透明度或改用 `to_have_css("opacity", "1")` 这类更具体的断言。

```text
#zero.is_visible(): False
#opacity.is_visible(): True
#hidden.is_visible(): False
#none.is_visible(): False
```

坑 4：把 `Locator` 当成元素句柄缓存起来后失效
结论：`Locator` 是惰性规则，DOM 重建后同一定位器依然可用（实测「旧」变「新」）；但如果你把它换成了 `element_handle()`，重建后句柄会指向已脱离文档的节点。
原因：`Locator` 每次动作重新解析，`ElementHandle` 绑定具体节点。
解法：统一用 `Locator`；确实需要句柄时，用完即弃，不要跨导航或跨重渲染缓存。

```text
定位文本: 旧
重建 DOM 后同一定位器: 新
```
