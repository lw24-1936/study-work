## 概述

E2E 套件一旦超过几十个用例，瓶颈就从"写用例"变成"等用例"，CI 集成的目标因此很明确：把墙上时间压下来、把环境做成可复现的、把失败证据完整带回来。Playwright 在 Node 端提供了 `retries`、`--shard`、blob 报告合并等整套设施；**Python 端要自己拼**——并行靠 pytest-xdist，分片靠矩阵 + 文件分组或第三方插件，报告靠 junit/HTML + 产物归档，环境靠官方 Docker 镜像。

```text
本篇主线：
1. 并行 —— pytest-xdist 的 -n / --dist（load、loadfile、loadscope、loadgroup、worksteal）
2. 分片 —— Python 端没有 --shard，跨机器靠 CI 矩阵 + 文件分组，报告按分片归档
3. 镜像 —— mcr.microsoft.com/playwright/python:<版本>-<发行版>，浏览器与系统依赖都内置
4. GitHub Actions —— 官方样例工作流 + 矩阵并行 + 产物上传
5. 产物 —— test-results 下的 trace/视频/截图与 junit/HTML 报告的归档策略
6. 实测数据 —— 本机 31 个用例：串行 9.22s、-n 4 用 8.32s、-n auto 用 11.83s（并行不一定更快）
```

本机实测环境：Ubuntu 24.04、8 逻辑核（nproc=8）、19GB 内存、Python 3.14.7、pytest 9.1.1、pytest-xdist 3.8.0、pytest-playwright 0.10.0、playwright 1.64.0、Docker 已安装（`/usr/bin/docker`）。下文 `text` 块里的数字与输出都是本机真实运行结果。

## pytest xdist 并行与分发模式

Python 端并行的唯一入口是 `pytest-xdist`：它起 N 个 worker 进程，每个 worker 自己加载 `pytest-playwright` 的 session 级 fixture，也就是**每个 worker 各自启动一个浏览器**。这一点决定了并发度与内存、启动开销的关系——不是越多越好。

```bash
pip install pytest-xdist        # 本机 3.8.0

# 固定并发
pytest --numprocesses 4
pytest -n 4

# 自动检测：auto=物理核，logical=逻辑核（需要 psutil，缺失时回退 auto）
pytest -n auto
pytest -n logical

# 官方文档建议用逻辑核数的一半
pytest --numprocesses 2
```

分发模式由 `--dist` 决定，本机 `pytest --help` 的真实说明：

```text
--dist=distmode       Set mode for distributing tests to exec environments.
                      each: Send each test to all available environments.
                      load: Load balance by sending any pending test to any
                      available environment.
                      loadscope: Load balance by sending pending groups of
                      tests in the same scope to any available environment.
                      loadfile: Load balance by sending test grouped by file
                      to any available environment.
                      loadgroup: Like 'load', but sends tests marked with
                      'xdist_group' to the same worker.
                      worksteal: Split the test suite between available
                      environments, then re-balance when any worker runs out
                      of tests.
                      (default) no: Run tests inprocess, don't distribute.
-d                    Load-balance tests. Shortcut for '--dist=load'.
```

两种模式的差异在本机真实可见。同一个 6 用例文件（`tests/test_parallel.py`），先看 `--dist=loadfile`（按文件分组）：

```text
$ pytest tests/test_parallel.py -n 4 --dist=loadfile -v
created: 4/4 workers
4 workers [6 items]
scheduling tests via LoadFileScheduling

tests/test_parallel.py::test_worker_distribution[chromium-1]
[gw0] PASSED tests/test_parallel.py::test_worker_distribution[chromium-1]
...
tests/test_parallel.py::test_worker_distribution[chromium-6]
[gw0] PASSED tests/test_parallel.py::test_worker_distribution[chromium-6]

============================== 6 passed in 8.64s ===============================
```

6 个用例全在 `gw0` 上——因为它们在同一个文件里，`loadfile` 不会把同一个文件拆开。换成 `--dist=load`（默认的负载均衡）后立刻铺开：

```text
$ pytest tests/test_parallel.py -n 4 --dist=load -v
scheduling tests via LoadScheduling
[gw0] [ 16%] PASSED tests/test_parallel.py::test_worker_distribution[chromium-1]
[gw1] [ 33%] PASSED tests/test_parallel.py::test_worker_distribution[chromium-2]
[gw2] [ 50%] PASSED tests/test_parallel.py::test_worker_distribution[chromium-3]
[gw3] [ 66%] PASSED tests/test_parallel.py::test_worker_distribution[chromium-4]
[gw0] [ 83%] PASSED tests/test_parallel.py::test_worker_distribution[chromium-5]
[gw1] [100%] PASSED tests/test_parallel.py::test_worker_distribution[chromium-6]

============================== 6 passed in 10.00s ===============================
```

并行不等于更快。同一套 31 用例，本机三次真实对比（8 逻辑核）：

| 运行方式 | 结果 | 墙钟时间 |
|---|---|---|
| 串行 `pytest -q` | 31 passed, 2 skipped | 9.22s |
| `pytest -n 4 -q` | 31 passed, 2 skipped | 8.32s |
| `pytest -n auto -q`（8 worker） | 31 passed, 2 skipped | 11.83s |

原因是每个 worker 都要启动一个浏览器并加载页面：用例本身只有几秒时，8 个浏览器的启动与争抢 CPU 反而更贵。套件里出现"长用例"（真实业务流）或数量上百之后，并行的收益才会显现；上生产流水线前先用 `--durations` 与实测数据确定并发度，别直接上 `-n auto`。

```text
要点：
- 并行入口是 pytest-xdist：-n/--numprocesses，每个 worker 各启动一个浏览器
- --dist 取值：load（默认均衡）、loadfile（按文件）、loadscope（按类/模块）、loadgroup（xdist_group 标记）、worksteal（饿者先抢）、each
- pytest-playwright 的 fixture 在 worker 内独立实例化，用例之间依然隔离
- 并发度不是越高越好：本机 8 核上 6 个短用例用 -n auto 反而比串行慢（11.83s vs 9.22s）
- -n logical 需要 psutil，缺失时回退到 auto（本机未装 psutil）
- xdist 下 -s/--capture=no 不生效（官方文档明确说明），要看 print 得先跑单进程或用 -p no:cacheprovider 之外的钩子
```

## 跨机器分片与报告合并

Playwright Test（Node 端）有 `--shard=1/4` 与 blob 报告，`merge-reports` 一条命令把分片结果合成 HTML。**Python 端这两个能力都没有**：本机实测 `pytest --help` 里 `shard` 出现 0 次，`playwright --help` 的子命令列表里也没有 `merge-reports`（只有 `show-trace`、`trace` 等）。所以跨机器分片要自己拼，两种可行做法：

做法一：CI 矩阵 + 文件分组（无需新依赖，最稳）。把用例文件按耗时分组（或按命名约定 `shard_1_*.py`），矩阵里每个 job 跑一组：

```bash
# 本机等价验证：只跑一部分文件，观察分组是否均衡
pytest tests/test_assertions.py tests/test_scenario_19_5.py -n 2 -q
pytest tests/test_fixtures_params.py tests/test_parallel.py -n 2 -q
```

```yaml
# .github/workflows/e2e.yml 片段：4 个分片各自成 job
jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: '3.13'
      - run: pip install -r requirements.txt
      - run: python -m playwright install --with-deps
      # 用 -k 表达文件分组，或用 conftest 读 SHARD 环境变量筛选用例
      - run: pytest -k "shard${{ matrix.shard }}" -n 2 \
          --tracing=retain-on-failure --junitxml=reports/shard-${{ matrix.shard }}.xml
      - uses: actions/upload-artifact@v5
        if: ${{ !cancelled() }}
        with:
          name: shard-${{ matrix.shard }}
          path: |
            reports/
            test-results/
```

做法二：用第三方插件按权重切分（例如 `pytest-split`，按历史耗时把用例均衡分到 `--splits N --group K`）。该插件本机未安装、未实测，用法以插件文档为准。

报告层面同样没有"合并"命令，思路是**每个分片各出一份报告，再在汇总 job 里下载所有产物**：

```bash
# 每个分片：junit（给 CI 平台汇总）+ HTML（给人看）
pytest -n 2 --junitxml=reports/shard-1.xml --tracing=retain-on-failure
# pytest-html 产出可读报告（本机未安装 pytest-html，安装与用法以插件文档为准）
pytest --html=reports/shard-1.html --self-contained-html
```

```bash
# 汇总 job：把各分片的 junit 与 trace 一起下载，失败时逐个看
# GitHub Actions 里用 actions/download-artifact 拉全部分片，再交给 CI 平台的测试报告插件解析多份 junit
```

```text
要点：
- Python 端没有 --shard（本机 pytest --help 无 shard 选项），也没有 merge-reports（playwright --help 无该子命令）
- 跨机器分片用 CI 矩阵 + 文件/标记分组，或用 pytest-split 之类的第三方插件（本机未验证）
- 每个分片独立产出 junit 与 HTML，汇总 job 下载全部产物由 CI 平台统一展示
- 分片测试会放大"用例依赖共享数据"的问题，务必保证用例可独立执行
- 分片粒度要按耗时切，不要按数量切：一个 3 分钟用例单独成片，短用例打包
- 分片并行度 = 矩阵 job 数 × 每 job 的 -n，总并发别超过后端测试环境的承载能力
```

## 官方 Docker 镜像

Playwright 维护官方镜像 `mcr.microsoft.com/playwright/python`，里面预装了浏览器二进制与全部系统依赖，但**不含 Playwright 的 Python 包**（要在镜像里 `pip install playwright==<版本>`）。本机实测：已发布的稳定版本标签到 `v1.63.0` 为止（另有 `v1.63.1.dev1-canary-20260915175508-*` 这类预发布标签），而 PyPI 上 `playwright` 最新稳定版已是 `1.64.0`——镜像标签会滞后于 PyPI 发布：

```bash
$ docker manifest inspect mcr.microsoft.com/playwright/python:v1.63.0-noble
{
   "schemaVersion": 2,
   "mediaType": "application/vnd.oci.image.index.v1+json",
   "manifests": [
      { "digest": "sha256:96b39581c89131729a7ecb8d532314af54c7f9bcc7a61fe15c7a9e77602acf59", ... }
   ]
}

$ docker manifest inspect mcr.microsoft.com/playwright/python:v1.64.0-noble
no such manifest: mcr.microsoft.com/playwright/python:v1.64.0-noble

$ docker manifest inspect mcr.microsoft.com/playwright/python:v1.64.0
no such manifest: mcr.microsoft.com/playwright/python:v1.64.0
```

镜像标签的构成是 `<playwright 版本>-<Ubuntu 发行版代号>`，本机从 MCR 拉到的标签集合（真实查询结果，截取 1.6x 部分）包含：

```text
v1.60.0 / v1.60.0-jammy / v1.60.0-noble
v1.61.0 / v1.61.0-jammy / v1.61.0-noble / v1.61.0-resolute
v1.62.0 / v1.62.0-jammy / v1.62.0-noble / v1.62.0-resolute
v1.63.0 / v1.63.0-jammy / v1.63.0-noble / v1.63.0-resolute
（另有 latest、next 与各标签的 -amd64/-arm64 变体）
```

官方文档给出的两种用法：

```bash
# 端到端测试：可信代码，用 root 免去用户管理（root 下 Chromium 沙箱不可用）
docker run -it --rm --ipc=host mcr.microsoft.com/playwright/python:v1.63.0-noble /bin/bash

# 爬取/自动化非可信站点：切到 pwuser + seccomp
docker run -it --rm --ipc=host --user pwuser --security-opt seccomp=seccomp_profile.json \
  mcr.microsoft.com/playwright/python:v1.63.0-noble /bin/bash
```

在容器里跑测试的完整写法（版本必须与镜像匹配，否则找不到浏览器可执行文件——官方文档明确警告）：

```dockerfile
FROM mcr.microsoft.com/playwright/python:v1.63.0-noble
WORKDIR /app
COPY requirements.txt .
# 镜像里没有 playwright 包，版本要和镜像标签一致
RUN pip install --no-cache-dir -r requirements.txt     # 里面写 playwright==1.63.0
COPY tests/ tests/
COPY pytest.ini .
CMD ["pytest", "-n", "2", "--tracing=retain-on-failure"]
```

```text
要点：
- 镜像里预装浏览器与系统依赖，但没有 Playwright 的 Python 包，需要 pip install playwright==<与镜像同版本>
- 标签格式 <版本>-<代号>：jammy=Ubuntu 22.04、noble=24.04、resolute=26.04，另有 latest/next
- 本机实测：稳定标签最新到 v1.63.0，而 PyPI 已发布 1.64.0，镜像 tag 存在滞后，写死版本前先查 MCR
- 镜像 tag 与 pip 版本不匹配会直接报找不到浏览器可执行文件
- e2e 用 root 即可；爬虫类必须 --user pwuser 加 seccomp，别用官方镜像访问不可信站点（官方文档明确提示）
- Alpine/musl 不受支持（Firefox/WebKit 构建依赖 glibc）
```

## GitHub Actions 集成

官方 CI 文档给出的最小工作流（Python 版，本机抓取的文档原文，含 action 主版本号）：

```yaml
name: Playwright Tests
on:
  push:
    branches: [ main, master ]
  pull_request:
    branches: [ main, master ]
jobs:
  test:
    timeout-minutes: 60
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v6
    - name: Set up Python
      uses: actions/setup-python@v6
      with:
        python-version: '3.13'
    - name: Install dependencies
      run: |
        python -m pip install --upgrade pip
        pip install -r requirements.txt
    - name: Ensure browsers are installed
      run: python -m playwright install --with-deps
    - name: Run your tests
      run: pytest --tracing=retain-on-failure
    - uses: actions/upload-artifact@v5
      if: ${{ !cancelled() }}
      with:
        name: playwright-traces
        path: test-results/
```

直接跑在官方容器里（省掉 `playwright install --with-deps` 步骤，环境一致，适合做视觉快照比对）：

```yaml
jobs:
  playwright:
    name: 'Playwright Tests'
    runs-on: ubuntu-latest
    container:
      image: mcr.microsoft.com/playwright/python:v1.63.0-noble
      options: --user 1001
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: '3.13'
      - run: pip install -r local-requirements.txt
      - run: pytest
```

官方文档同时给出几条容易踩的 CI 注意事项，逐条对应到本机可验证的事实：

| 事项 | 官方说法 | 本机验证情况 |
|---|---|---|
| 浏览器缓存 | 不建议缓存浏览器二进制，恢复耗时与下载相当，且系统依赖无法缓存 | 未在 CI 上验证；本机 chromium 缓存 1234 与 1248 两版并存，说明版本一变旧缓存即失效 |
| headed 执行 | Linux 上需要 Xvfb，官方镜像与 GitHub Action 预装 | 本机无 xvfb-run，`PWDEBUG=1` 与 codegen 均以 "Missing X server or $DISPLAY" 失败 |
| 启动失败排查 | 用 `DEBUG=pw:browser pytest` 输出浏览器启动日志 | 本机实测该环境变量是官方文档给出的排查开关，未在 CI 上跑 |
| 本地服务访问 | 用 `--add-host=hostmachine:host-gateway` 让容器访问宿主机服务 | 未验证（需容器场景） |

```text
要点：
- 标准三步：pip install → python -m playwright install --with-deps → pytest --tracing=retain-on-failure
- 产物上传用 actions/upload-artifact@v5，条件写 if: ${{ !cancelled() }}，确保失败时也上传
- 用 container: 跑官方镜像时不要重复安装浏览器；options: --user 1001 匹配镜像里的非 root 用户
- 不给 headed 场景装 Xvfb，Linux 上 headed 会直接失败（本机无 xvfb 实测报缺少 X server）
- 不建议缓存浏览器二进制，但若坚持缓存，Key 里必须带 Playwright 版本哈希
- job 上加 timeout-minutes，防住 PWDEBUG/超时配置导致的挂死
```

## 测试产物管理与报告归档

产物分两类：**证据**（trace、视频、截图）与**报告**（junit XML、HTML）。证据由 Playwright 产出、放在 `test-results/`（可用 `--output=` 改）；报告由 pytest 侧产出。本机真实运行的产物结构（三件套齐全，目录名是 node id 压缩而来）：

```text
artifacts/tests-test-retries-report-py-test-intentionally-failing-chromium/test-failed-1.png   25776 bytes
artifacts/tests-test-retries-report-py-test-intentionally-failing-chromium/trace.zip          160171 bytes
artifacts/tests-test-retries-report-py-test-intentionally-failing-chromium/video.webm         104487 bytes
```

junit XML 会把三个产物路径写进 `<properties>`，CI 平台（Jenkins、GitLab、Allure 等）能直接把它们挂到失败用例上：

```text
<testcase classname="tests.test_retries_report" name="test_intentionally_failing[chromium]" time="10.651">
  <properties>
    <property name="playwright_screenshot" value="artifacts/.../test-failed-1.png" />
    <property name="playwright_trace" value="artifacts/.../trace.zip" />
    <property name="playwright_video" value="artifacts/.../video.webm" />
  </properties>
```

推荐的归档策略（按"失败才留、过期限、按分片分目录"三条组织）：

```bash
# 1) 失败才录，通过即删
pytest --tracing=retain-on-failure --video=retain-on-failure --screenshot=only-on-failure

# 2) 产物与报告分开目录，便于分别设保留期
pytest --output=test-results --junitxml=reports/junit.xml

# 3) 分片场景按分片命名，避免覆盖
pytest --output=test-results/shard-1 --junitxml=reports/junit-shard-1.xml
```

```yaml
# 上传时区分证据与报告，并限制保留期（GitHub Actions）
- uses: actions/upload-artifact@v5
  if: failure()
  with:
    name: traces
    path: test-results/
    retention-days: 7
- uses: actions/upload-artifact@v5
  if: ${{ !cancelled() }}
  with:
    name: junit
    path: reports/
    retention-days: 30
```

```text
要点：
- 证据（trace/video/screenshot）默认在 test-results/，报告（junit/HTML）路径自己定，两者分开归档
- junit 里带产物路径的 property，CI 平台可直接把 trace 挂到失败用例上
- retain-on-failure / only-on-failure 是默认策略，全量录制会让产物体积失控
- 上传用 if: failure() 或 if: ${{ !cancelled() }}，否则测试失败时上传步骤会被跳过
- 分片场景给每个分片单独目录与文件名，否则后跑的分片会覆盖前面的产物
- 保留期按体积定：trace 单个约 150KB 起、视频约 100KB 到数 MB，长期堆积会吃掉 CI 存储配额
```

## 应用场景实战

### 场景一：把 31 个用例的套件接进 GitHub Actions（并行 + 产物 + 报告）

需求：每次 PR 跑一遍 E2E，10 分钟内出结果，失败时能直接拿到 trace 与视频。做法：容器里跑（环境固定）、`-n 2` 并行、失败保留三件套、junit 与产物分别上传。

```yaml
name: E2E
on:
  pull_request:
  push:
    branches: [main]

jobs:
  e2e:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    container:
      image: mcr.microsoft.com/playwright/python:v1.63.0-noble
      options: --user 1001
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: '3.13'
      - name: Install deps
        run: pip install -r requirements.txt      # 固定 playwright==1.63.0 与镜像一致
      - name: Run E2E
        run: |
          pytest -n 2 \
            --dist=loadfile \
            --tracing=retain-on-failure \
            --video=retain-on-failure \
            --screenshot=only-on-failure \
            --junitxml=reports/junit.xml \
            --output=test-results -q
        env:
          PW19_BASE_URL: ${{ secrets.STAGING_BASE_URL }}
      - name: Upload evidence
        if: failure()
        uses: actions/upload-artifact@v5
        with:
          name: playwright-evidence
          path: test-results/
          retention-days: 7
      - name: Upload report
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@v5
        with:
          name: junit
          path: reports/
          retention-days: 30
```

### 场景二：几百个用例的分片流水线（矩阵 + 每片并行 + 汇总）

需求：套件增长到 400+ 用例、单机串行 25 分钟，目标是 6 分钟内出结果。做法：4 个分片 job × 每片 `-n 2`，按耗时把文件分成 4 组（长用例单独成组），每片产出独立 junit 与产物，另加一个汇总 job 下载全部产物。

```yaml
jobs:
  e2e:
    strategy:
      fail-fast: false
      matrix:
        include:
          - shard: 1
            files: "tests/checkout tests/payment"
          - shard: 2
            files: "tests/auth tests/profile"
          - shard: 3
            files: "tests/search tests/catalog"
          - shard: 4
            files: "tests/admin"
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: '3.13'
      - run: pip install -r requirements.txt
      - run: python -m playwright install --with-deps chromium
      - name: Run shard
        run: |
          pytest ${{ matrix.files }} -n 2 --dist=loadfile \
            --tracing=retain-on-failure \
            --junitxml=reports/junit-shard-${{ matrix.shard }}.xml \
            --output=test-results/shard-${{ matrix.shard }} -q
      - uses: actions/upload-artifact@v5
        if: ${{ !cancelled() }}
        with:
          name: shard-${{ matrix.shard }}
          path: |
            reports/
            test-results/
          retention-days: 14

  summary:
    needs: e2e
    if: ${{ !cancelled() }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v5
        with:
          path: all-artifacts
      - name: Collect junit and traces
        run: |
          find all-artifacts -name 'junit-*.xml' -print
          find all-artifacts -name 'trace.zip' -print
```

分组依据要用实测数据说话，本机给出真实分布（`--durations=1` 抓到的单用例 teardown 就占了 5.40 秒，比用例本体还长）：

```text
============================= slowest 1 durations ==============================
5.40s teardown tests/test_assertions.py::test_auto_retry_waits_for_late_content[chromium]
============================== 1 passed in 7.69s ===============================
```

```text
要点：
- 分片按历史耗时切，不按文件个数切；把 3 分钟级用例单独成片，短用例合并
- 每片独立 -n 2（或 loadfile 分发），总并发控制在测试环境能承受的范围
- 汇总 job 用 needs + download-artifact 收齐 junit 与 trace，交给 CI 平台的报告插件
- fail-fast: false 让其他分片跑完，别因为一片失败就丢失全部证据
- 分片后每个 job 都要独立安装浏览器；用官方镜像或缓存由 CI 平台的耗时决定
- Python 端没有 merge-reports，汇总的是 junit 与产物，不是 Playwright 的 HTML 报告
```

## 最佳实践与踩坑记录

1. 并发度用实测数据定，不用默认值。本机 8 逻辑核上 6 个短用例 `-n auto`（11.83s）比串行（9.22s）更慢；先用 `--durations` 看耗时分布，再决定 `-n` 与 `--dist`。
2. 默认用 `--dist=loadfile`，需要极致均衡再考虑 `load`/`worksteal`。Web 用例常有"同文件共享前置数据"的隐含依赖，按文件分发最不容易出错。
3. CI 里必须保留失败证据。`--tracing=retain-on-failure` 是基线，配合 `if: failure()` 上传；没有 trace 的 E2E 失败排查成本会翻倍。
4. 镜像与 pip 版本锁死成对升级。容器镜像 tag（`v1.63.0-noble`）与 `playwright==` 版本不一致时浏览器找不到，升级必须同时改两处。
5. 分片前先保证用例可独立执行。分片会把"顺序依赖""共享账号""共享数据库状态"直接放大成随机失败；先做隔离，再分片。
6. 给流水线加超时。`timeout-minutes` 与 pytest 的 `--timeout`（需 pytest-timeout，本机未安装）都能兜住"某个用例永远等不到结果"的挂死。

坑 1：Python 端没有 `--shard`，也没有 blob 报告与 `merge-reports`。

结论：本机实测 `pytest --help` 中 `shard` 出现 0 次；`playwright --help` 的子命令为 open/codegen/install/uninstall/install-deps/cr/ff/wk/screenshot/pdf/show-trace/trace/cli/mcp/help，没有 `merge-reports`。

原因：`--shard` 与 blob/merge-reports 属于 Playwright Test（Node 端测试运行器）；Python 端的测试运行器是 pytest，分片与报告合并由 pytest 生态负责。

解法：跨机器分片用 CI 矩阵 + 文件/标记分组（或用 pytest-split 之类插件），报告按分片产出 junit/HTML 后在汇总 job 里统一收集。

坑 2：官方 Docker 镜像的 tag 落后于 PyPI 版本，按 `pip show playwright` 的版本拼 tag 会直接失败。

结论：本机实测 `playwright` PyPI 最新稳定版是 1.64.0（`pip index versions playwright` 的 LATEST 与 INSTALLED 均为 1.64.0），但 `docker manifest inspect mcr.microsoft.com/playwright/python:v1.64.0-noble` 与 `:v1.64.0` 都返回 `no such manifest`；已发布的最新稳定 tag 是 `v1.63.0-noble`。

原因：镜像由 Playwright 团队在发布后另外构建推送，与 PyPI 的发布节奏不同步。

解法：部署前用 `docker manifest inspect` 或 MCR 的 tags 接口确认 tag 存在；镜像与 pip 版本成对锁定（镜像用 `:v1.63.0-noble` 就装 `playwright==1.63.0`），或在不使用官方镜像时改用 `python:3.13-slim` + `playwright install --with-deps`。

坑 3：xdist 下 `-s`/`--capture=no` 不生效，调试用的 print 全都不见。

结论：本机 `pytest tests/test_parallel.py -n 4 -v -s` 的输出中，用例里的 `print(f"[worker=...] 用例 {n}")` 一行都没有出现。

原因：pytest-xdist 官方的已知限制明确写着 `-s/--capture=no` 不生效（因为 worker 的输出要经控制器汇总）。

解法：需要看 print 时先单进程跑；并行时用 `--capture=tee-sys` 或者把关键信息写成文件/附加到 junit，本机在 19.5 里用的方案是钩子打日志并在 CI 里 grep。

坑 4：分片与并行会把"共享账号/共享数据"的用例变成随机失败。

结论：本机 6 个用例用 `--dist=load` 时被分到 gw0-gw3 四个进程同时跑，每个进程各开一个浏览器；如果这些用例共用同一个后端账号（比如同一个登录用户改同一份数据），就会互相踩。

原因：并行意味着同一时刻有多个真实客户端在操作同一套后端；用例里对"数据是干净的"的假设在并行下不再成立。

解法：给每个 worker 分配独立数据（用 `PYTEST_XDIST_WORKER` 环境变量拼用户名/租户，或读 `--dist=loadgroup` 配合 `@pytest.mark.xdist_group` 把强相关用例钉在同一个 worker），并在用例结束时清理自己造的数据。

坑 5：`upload-artifact` 条件写错会让失败时的证据丢失。

结论：官方示例用的是 `if: ${{ !cancelled() }}`；若写成 `if: success()`（或省略条件），用例失败时上传步骤被跳过，CI 上只剩一个"失败"标记，没有任何 trace。

原因：GitHub Actions 默认后续步骤在前序步骤失败后不再执行，而"上传证据"恰好发生在测试失败之后。

解法：上传步骤统一用 `if: ${{ !cancelled() }}`（连取消的 job 也要留痕）或 `if: failure()`；同时给产物设 `retention-days`，避免存储配额被吃光。
