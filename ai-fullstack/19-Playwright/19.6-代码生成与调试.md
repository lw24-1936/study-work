## 概述

写 Web 自动化最贵的成本不是断言，是**定位与复现**：选择器写错、页面慢了一拍、CI 上偶发失败——这些问题的调试手段决定了整个套件的维护成本。Playwright 把这部分做成了独立工具链：`codegen` 把浏览器操作直接录成代码，`trace` 把一次执行完整录下来（DOM 快照 + 网络 + 控制台 + 源码），`PWDEBUG` 的 Inspector 提供单步与实时改选择器，`--video`/`--screenshot` 留下面向人的证据。

```text
本篇主线：
1. codegen —— 录制生成 python / python-pytest / python-async 代码，录制时挑最佳选择器
2. Trace Viewer —— test-results 里的 trace.zip，本地 show-trace 或 trace.playwright.dev 打开
3. trace 命令行 —— playwright trace open/actions/errors/requests/console 在无桌面环境看追踪
4. UI 模式 —— Python 端没有 UI 模式，用 Inspector + trace + --headed 组合替代
5. Inspector 调试 —— PWDEBUG=1 单步、PWDEBUG=console 用选择器引擎、DEBUG=pw:api 看协议日志
6. 录制产物 —— 视频/截图/trace 三个开关与程序化 tracing.start/stop
```

本机实测环境：Ubuntu 24.04（**无桌面环境、无 X Server、无 xvfb-run**）、Python 3.14.7、playwright 1.64.0、pytest-playwright 0.10.0、Chromium 156.0.8078.4。这一点对本篇很关键：凡是需要弹窗（codegen 的录制窗口、Inspector、UI 模式、show-trace 的浏览器页签）的功能，本机只能验证命令行行为并如实标注；不依赖桌面的（`trace` 子命令、`playwright screenshot` CLI、程序化追踪）全部真实跑通并贴出原始输出。

## codegen 录制生成代码

`playwright codegen <url>` 会打开两个窗口：一个浏览器供你操作，一个 Playwright Inspector 显示生成中的代码。它边操作边"看"页面，优先给出 role / text / test id 这类稳定选择器；一个选择器匹配到多个元素时会自动改进成唯一标识。生成的语言由 `--target` 决定，本机 1.64.0 支持 `python`（默认）、`python-async`、`python-pytest`、`javascript`、`playwright-test`、`csharp-*`、`java-*`。

```bash
# 录制 Python 脚本（同步 API）
playwright codegen https://demo.example.com/login

# 直接录成 pytest 用例（pytest-playwright 的 page fixture 用法）
playwright codegen --target=python-pytest -o tests/test_login.py https://demo.example.com/login

# 指定 test id 属性名（前端用 data-qa 之类的约定时）
playwright codegen --test-id-attribute=data-qa https://demo.example.com

# 带设备模拟、时区、语言、地理位置一起录
playwright codegen --device="iPhone 13" --timezone="Asia/Shanghai" --lang="zh-CN" \
  --geolocation="31.2304,121.4737" https://demo.example.com

# 录登录一次，把 storage state 存下来，后面直接复用（不要提交到仓库）
playwright codegen --save-storage=auth.json https://github.com/login
playwright codegen --load-storage=auth.json https://github.com/settings/profile

# 固定用户数据目录（复用已有浏览器 profile 的登录态）
playwright codegen --user-data-dir=/tmp/pw-profile https://demo.example.com

# 顺手存 HAR，用于后续 mock 或排查接口
playwright codegen --save-har=login.har https://demo.example.com
```

```python
from playwright.sync_api import sync_playwright

    context = browser.new_context()
    context.route("**/*", lambda route: route.continue_())
    page = context.new_page()
    page.goto("https://demo.example.com")
    page.pause()      # 打开 codegen 面板，可继续录制、挑选择器
```

## Trace Viewer 追踪查看器

trace 是 Playwright 的"黑匣子"：一次运行录下每个动作前后的 DOM 快照、动作日志、网络请求、控制台输出、源码位置与 screencast 帧。把 trace 命名为"调试生产力"的核心原因是——失败不用复现，直接回放。

```bash
# 录制：pytest 三个取值 on / off / retain-on-failure（默认 off，产物在 test-results/）
pytest --tracing=retain-on-failure

# 图形界面打开（需要桌面环境；本机实测在无桌面时报错，见下）
playwright show-trace test-results/<case>/trace.zip

# 在线版：拖拽上传，数据只在浏览器本地解析，不上传服务器
# https://trace.playwright.dev
```

`show-trace` 在本机真实失败（它是"起一个本地服务并打开浏览器页签"的模式，`--host`/`--port` 也依赖浏览器）：

```text
$ playwright show-trace artifacts/.../trace.zip
Error: Protocol error (Browser.getVersion): Internal server error, session closed.
```

无桌面环境看 trace 的正确姿势是 1.64.0 提供的 `playwright trace` 子命令（本机真实跑通的完整流程）：

```bash
# 1) 打开一个 trace 到工作目录（后续命令在当前目录读它）
```

不使用 pytest 时可以在代码里手动开关追踪，这是库模式（`sync_api`）下的标准写法，本机真实跑通（`trace 文件: ... 大小(bytes): 59935`）：

```python
from playwright.sync_api import expect, sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    context = browser.new_context(viewport={"width": 1024, "height": 768})
    # screenshots=screencast 帧，snapshots=DOM 快照，sources=源码
    context.tracing.start(screenshots=True, snapshots=True, sources=True)
    page = context.new_page()
    page.goto(url)
    page.get_by_test_id("username").fill("alice")
    page.get_by_test_id("password").fill("secret123")
    page.get_by_test_id("login-submit").click()
    expect(page.get_by_test_id("delayed-banner")).to_be_visible()
    context.tracing.stop(path="trace.zip")      # 必须放在 context 关闭之前
    browser.close()
```

```text
要点：
- pytest 侧 --tracing=on/off/retain-on-failure，产物是 test-results/<case>/trace.zip
- 库模式手动开关：context.tracing.start(screenshots=, snapshots=, sources=) 与 stop(path=)
- 图形界面用 playwright show-trace，在线版 trace.playwright.dev 本地解析不上传
- 无桌面环境用 playwright trace open + actions/errors/requests/console 子命令（本机实测）
- trace 里的 Actions 面板能直接看到断言等了多久（Expect ... 1.3s），定位慢在哪一步
- trace 体积与耗时都不小，CI 上默认 retain-on-failure，只在需要时全量录制
```

## UI 模式与交互式调试

Playwright Test（Node 端）有一个完整的 UI 模式：`npx playwright test --ui`，可以时间旅行、watch 重跑、逐个用例交互。**Python 端没有对应的 UI 模式**——本机 1.64.0 的 `playwright --help` 列出的子命令为 `open / codegen / install / uninstall / install-deps / cr / ff / wk / screenshot / pdf / show-trace / trace / cli / mcp / help`，没有任何 `ui` 命令。所以 Python 侧的"交互式调试"要由三个工具拼出来：

```bash
# 1) 交互式跑：headed 浏览器 + Inspector，可单步、可实时改选择器
PWDEBUG=1 pytest -s                # 全部
PWDEBUG=1 pytest -s tests/test_login.py
PWDEBUG=1 pytest -s -k test_checkout

# 2) 慢放：看清楚每一步到底点了哪里（100ms/动作）
pytest --headed --slowmo=100

# 3) 回放：失败后用 trace 在 trace.playwright.dev 或 playwright trace 里看
playwright trace open test-results/<case>/trace.zip && playwright trace actions
```

`PWDEBUG=1` 的两个副作用需要知道：浏览器强制 headed（本机无桌面因此直接失败，报错就是上面 codegen 那段 XServer 提示）、超时被设为 0（等于不超时）。

```bash
# 想让测试在 CI 上也"可调试"，别用 PWDEBUG，改用 trace
pytest --tracing=retain-on-failure --video=retain-on-failure
```

需要在开发时反复跑一个用例，用 pytest 原生能力就够：`pytest --lf`（只跑上次失败）、`pytest --sw`（步进式：失败处停下，下次从那里继续）、`pytest -x`（首个失败即停）、`-k`/`-m` 定向。这些在调试循环里比 UI 模式更省事。

```text
要点：
- Python 端没有 UI 模式（playwright --help 无 ui 子命令，本机 1.64.0 实测），它属于 Playwright Test/Node
- 替代组合：PWDEBUG=1（Inspector 单步 + 实时改选择器）、--headed --slowmo、trace 回放
- PWDEBUG=1 会强制 headed 并把超时设为 0；无桌面环境需要 xvfb-run
- 调试循环用 pytest -x / -k / -m / --lf / --sw，比反复点 UI 快
- CI 上不保留 PWDEBUG（会把超时设成 0 导致卡死），改为保留 trace 与视频
```

## Playwright Inspector 与调试技巧

Inspector 是 `PWDEBUG=1` 打开的调试面板：顶部工具栏控制 play / pause / step，当前动作在测试代码里高亮，匹配元素在浏览器里高亮；"Pick Locator"可以把鼠标悬停到的元素换成一个稳定选择器；日志里能看到 actionability 检查过程（元素是否可见、可用、稳定，是否滚动进视口），这正是"为什么点不中"的答案。

```bash
# 单步并在日志里看 actionability 与协议调用
PWDEBUG=1 pytest -s -k test_checkout

# 把 playwright 对象注入浏览器控制台：用真实选择器引擎在 DevTools 里查元素
PWDEBUG=console pytest -s
# 然后在 DevTools 控制台里：
#   playwright.$('.auth-form >> text=Log in')
#   playwright.$$('li >> text=John')
#   playwright.inspect('text=Log in')
#   playwright.selector($0)

# 协议级日志（不弹窗，CI 与无桌面环境可用）：定位超时、启动失败、事件丢失
DEBUG=pw:api pytest -s
DEBUG=pw:browser pytest -s          # 浏览器启动相关，排查 "Failed to launch browser"
```

在代码里下断点比一步步点更高效：用 Python 原生 `breakpoint()` 直接进 pdb，此时浏览器还活着，可以在 pdb 里执行 `page.locator(...)` 观察状态；也可以开一个交互式 Python 快速试验 API（官方文档的 REPL 用法）：

```python
# pytest 用例里：断在你想看的位置，然后在 pdb 里操作 page
def test_bug(page, app_url):
    page.goto(app_url)
    page.get_by_test_id("login-submit").click()
    breakpoint()          # 进 pdb，可执行 page.locator("#login-error").inner_text()
    assert page.title() == "任务台"
```

```text
$ python
>>> from playwright.sync_api import sync_playwright
>>> playwright = sync_playwright().start()
>>> browser = playwright.chromium.launch()
>>> page = browser.new_page()
>>> page.goto("https://playwright.dev/")
>>> page.screenshot(path="example.png")
>>> browser.close()
>>> playwright.stop()
```

```text
要点：
- PWDEBUG=1 打开 Inspector：单步、实时改选择器、看 actionability 日志
- PWDEBUG=console 把 playwright 对象注入 DevTools 控制台，可用真实选择器引擎查元素
- DEBUG=pw:api 看协议级日志（无桌面环境可用），DEBUG=pw:browser 排查浏览器启动失败
- 断点优先用 Python 的 breakpoint()+pdb，浏览器保持存活，可在断点处直接查页面
- Inspector 的 "Pick Locator" 生成的 locator 可直接粘贴进代码，比自己猜 CSS 稳
- 远程/容器环境没有 DevTools 时，用 trace 的 Console/Network 面板替代
```

## 视频与截图录制

视频与截图是给"人"看的证据：失败报告里放一段视频，评审和产品也能看懂出了什么问题。pytest 侧两个开关：`--video=on|off|retain-on-failure`、`--screenshot=on|off|only-on-failure`，配合 `--output=` 指定目录。本机真实运行（故意失败的用例）：

```bash
pytest tests/test_retries_report.py::test_intentionally_failing \
  --video=retain-on-failure --screenshot=only-on-failure \
  --output=artifacts --tracing=retain-on-failure
```

```text
-rw-r--r-- 1 root root  25776  test-failed-1.png
-rw-r--r-- 1 root root 160171  trace.zip
-rw-r--r-- 1 root root 104487  video.webm
```

库模式下视频通过 context 参数开启，注意**视频是在 context 关闭时才写盘**的，所以必须关闭（或依赖 pytest 插件帮你关）：

```python
context = browser.new_context(record_video_dir="videos/")
# ... 操作 ...
context.close()       # 不 close 就没有视频文件
```

视频与截图也能按需手工采集，这样只在真正需要的时刻留证据（比如关键业务单据）：截图支持整页、元素级、蒙版与超时设置。

```python
# 整页截图
page.screenshot(path="artifacts/home-full.png", full_page=True)
# 单个元素截图（比如订单卡片），带蒙版隐藏手机号
page.get_by_test_id("order-card").screenshot(
    path="artifacts/order.png",
    mask=[page.get_by_test_id("phone")],
)
# 无头环境下临时留证据（本机实测可用，生成 10KB 左右的 PNG）
```

不写代码也能截：`playwright screenshot` 是无头 CLI，可以在排查线上页面时直接用，并支持等待条件。本机真实运行（对本地演示页截图并核对渲染结果）：

```text
要点：
- pytest 开关 --video=on|off|retain-on-failure 与 --screenshot=on|off|only-on-failure
- 库模式用 browser.new_context(record_video_dir=...)，必须 context.close() 才会落盘
- 截图支持 full_page、元素级，以及 mask= 对敏感区域打码

- 只看失败的组合（retain-on-failure / only-on-failure）最实用，全量录制会明显拖慢套件
```

## 应用场景实战

### 场景一：CI 失败后用 trace 定位（无桌面环境的完整流程）

需求：流水线上一批用例失败，本地没有桌面环境，需要在不复现的情况下定位到"哪一步、等了多久、页面当时长什么样"。做法：CI 上保留 trace 并作为产物上传，本地下载后用 `playwright trace` 子命令读。

```yaml
# .github/workflows/e2e.yml 片段：只在失败时上传产物
- name: Run tests
  run: pytest --tracing=retain-on-failure --video=retain-on-failure --output=artifacts -q
- uses: actions/upload-artifact@v5
  if: ${{ !cancelled() }}
  with:
    name: playwright-artifacts
    path: artifacts/
    retention-days: 7
```

本地打开并定位（本机真实输出见上文"Trace Viewer"章节）：

```bash
# 解压下载的产物
unzip playwright-artifacts.zip -d artifacts
# 打开 trace（放在当前目录，后续命令读同一个工作目录）
playwright trace open artifacts/tests-test-retries-report-py-test-intentionally-failing-chromium/trace.zip
playwright trace errors     # 直接给出失败的断言与源码行
playwright trace actions    # 看哪一步慢：Expect "to_have_text" 5.0s ✗
playwright trace requests   # 看接口是否 500 或超时
playwright trace console    # 看前端报错
```

本机实测的定位结论示例：`trace errors` 指向 `test_retries_report.py:27`，`trace actions` 显示第 7 个动作 `Expect "to_have_text"` 耗尽 5.0 秒（`✗`），`trace requests` 只有一次 `GET index.html 200`——说明不是接口问题，而是断言期望值写错（页面实际是"欢迎，alice"）。这条链路在无桌面环境下完整可用。

```text
要点：
- CI 上只保留失败产物（retain-on-failure）并设置 retention-days，避免产物无限堆积
- 本地用 playwright trace open + errors/actions/requests/console 四步定位，无需桌面
- 先看 errors 定位失败断言，再看 actions 判断是慢还是错，最后看 requests/console 区分前后端责任
- trace 里带 src/ 源码，可以直接看到当时的测试代码版本
- show-trace 的图形界面在有桌面时体验更好；无桌面时不要耗在开图形界面上
```

### 场景二：给关键业务流留视频与截图证据（含失败自动归档）

需求：结算、下单这类高价值流程，除了断言通过，还要留下"当时界面确实对了"的证据，失败时自动归档视频与截图给非技术同事看。做法：CI 上用 `--video=retain-on-failure --screenshot=only-on-failure`，用例内部对关键页面再手工截图存档。

```python
import re
from playwright.sync_api import Page, expect

def test_checkout_evidence(page: Page, app_url: str, tmp_path) -> None:
    """关键流程：断言 + 存档证据。tmp_path 由 pytest 提供，产物随报告一起归档。"""
    page.goto(app_url)
    page.get_by_test_id("username").fill("buyer01")
    page.get_by_test_id("password").fill("secret123")
    page.get_by_test_id("login-submit").click()

    # 关键节点 1：登录态确认（断言会自动重试，不用 sleep）
    expect(page.get_by_test_id("welcome")).to_have_text("欢迎，buyer01")
    page.screenshot(path=str(tmp_path / "01-login.png"))

    # 关键节点 2：下单动作 + 结果存档（元素级截图 + 列表断言）
    page.get_by_test_id("add-todo").click()
    page.get_by_test_id("load-remote").click()
    expect(page.get_by_test_id("todo-item")).to_have_count(2)
    expect(page.get_by_test_id("status")).to_have_text(re.compile(r"loaded|synced"))
    page.get_by_test_id("todo-list").screenshot(path=str(tmp_path / "02-result.png"))

    # 关键节点 3：写清"证据在哪"，方便 CI 里顺着报告找
    print(f"证据目录: {tmp_path}")
```

配套命令（本机实测的产物形态）：

```bash
pytest tests/test_checkout_evidence.py \
  --video=retain-on-failure \
  --screenshot=only-on-failure \
  --tracing=retain-on-failure \
  --output=artifacts -v
```

```text
artifacts/tests-...-test-checkout-evidence-chromium/test-failed-1.png     # 失败瞬间的整页截图
artifacts/tests-...-test-checkout-evidence-chromium/video.webm            # 整个用例的录像（失败时保留）
artifacts/tests-...-test-checkout-evidence-chromium/trace.zip             # 可回放的黑匣子
```

```text
要点：
- 高价值流程固定存档关键页面截图，路径给到 pytest 的 tmp_path，随报告一起归档
- 视频只在失败时保留（retain-on-failure），避免每跑一次都产出上百 MB
- 元素级截图 + mask 可以在外发截图前遮掉手机号、身份证等敏感字段
- 视频与截图只是证据，不要用截图比对代替断言（视觉回归是另一套工具）
- 归档目录名与用例 id 对应，报告里能一键回溯到具体用例
```

## 最佳实践与踩坑记录

1. codegen 只用来"起手"，不用来交付。录完的代码要人工改成 fixture + 参数化 + `expect` 断言，否则会留下一堆 `page.click("#id-2")` 式的脆弱代码和硬编码等待。
2. 生产环境的调试一律靠 trace，不靠复现。CI 默认开 `--tracing=retain-on-failure`，失败就能回放，比"本地再跑一遍看看"稳定得多。
3. 选择器在 Inspector 里挑，不在代码里猜。Inspector 的 Pick Locator 使用的是真实选择器引擎，挑出来的 locator 通常比自己写的 CSS 更稳、更短。
4. PWDEBUG 只用于本地，CI 上一律关掉。它会把超时设成 0 并强制 headed，CI 上会导致卡死或直接失败。
5. 视频与截图按需录制。`retain-on-failure` / `only-on-failure` 组合已经覆盖 95% 的排查需求，全量录制会把套件拖慢数倍。
6. 调试日志按需打开：`DEBUG=pw:api` 定位协议级问题，`DEBUG=pw:browser` 定位浏览器启动问题，长期开启只会淹没有效信息。

坑 1：`codegen`、`PWDEBUG=1`、`show-trace` 在没有桌面环境的机器上全部不能直接跑。

结论：本机（无 X Server、无 xvfb-run）实测三者都失败：codegen 报 `Looks like you launched a headed browser without having a XServer running`，`PWDEBUG=1 pytest -s` 同样失败，`playwright show-trace` 报 `Error: Protocol error (Browser.getVersion): Internal server error, session closed.`。

原因：它们都是"启动 headed 浏览器"的工具；codegen 与 Inspector 需要真实窗口交互，show-trace 默认把追踪界面开在浏览器页签里。

解法：无桌面环境用 `playwright trace open` + `actions/errors/requests/console` 子命令排查（本机实测可用），采集页面证据用 `playwright screenshot`（本机实测生成了正确的 PNG）；确实要录制时在有桌面的机器上操作，或用 `xvfb-run` 包裹（本机未安装 xvfb，未验证）。

坑 2：`page.pause()` 与 `PWDEBUG` 都会把超时改成 0，忘了删会挂死 CI。

结论：`PWDEBUG=1` 的官方行为是"默认超时设为 0（等于不超时）"，配合忘记删除的 `page.pause()`，CI 上会一直等到 job 级超时被杀。

原因：调试时希望永远等下去，CI 上希望尽快失败——两者诉求相反，而这两个开关是全局的。

解法：提交前用 `grep -rn "page.pause()" tests/` 检查；CI 上用 `timeout-minutes` 兜底（GitHub Actions 的 `jobs.<id>.timeout-minutes`），并禁止在 CI 环境变量下开启 PWDEBUG。

坑 3：trace 里的动作耗时容易被误读为"页面慢"，实际是断言在等。

结论：本机通过用例的 trace 显示 `Expect "to_be_visible" 1.3s`，而同一份 trace 里 `Click 70ms`、`Fill 23ms`——慢的是断言轮询，不是点击。

原因：`expect` 的耗时包含轮询等待时间，与页面自身响应时间无关；`Click`/`Fill` 的耗时含 actionability 检查，但通常只有几十毫秒。

解法：看动作类型再下结论；要区分"页面慢"还是"断言等得久"，对照 `Navigate`/网络面板的耗时，或者把断言换成"先 `wait_for` 再断言"来观察差异。

坑 4：视频文件不会立刻出现，用例中途去找必然找不到。

结论：本机实测视频只在 context 关闭时才写盘；用 pytest 插件时它会在用例结束（fixture teardown）后落盘，用例体内 `os.listdir(videos)` 是空的。

原因：视频由浏览器进程边录边缓存，`context.close()` 时才 flush 成文件；Python 侧没有"强制立即落盘"的公开 API。

解法：把视频当产物看待，只在 teardown 之后（或报告里）读取；断言"视频有没有生成"要写在 session/module 级的收尾钩子里，而不是用例本体。

坑 5：`--save-storage` 生成的 auth.json 是明文凭据，容易误提交。

结论：`playwright codegen --save-storage=auth.json` 会把 cookies、localStorage、IndexedDB 一起写成 JSON，官方文档明确要求"只在本地使用，加入 .gitignore 或用完即删"。

原因：storage state 是登录态的直接拷贝，等同于凭据；它落在仓库目录时极易被 `git add .` 带进去。

解法：把 auth.json 放进 CI secret / 临时目录 / `.gitignore`；需要入库时只提交结构示例（把真实值清空），并在 CI 里用环境变量注入后再 `--load-storage`。
