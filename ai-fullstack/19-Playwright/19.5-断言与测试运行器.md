## 概述

Python 端的 Playwright 测试运行器不是自研框架，而是 pytest 加官方插件 `pytest-playwright`：pytest 负责收集、参数化、重试、报告，Playwright 通过一组 fixture（`page`、`context`、`browser`、`browser_context_args` 等）把浏览器交给用例，并用 `expect` 提供带自动重试的 Web 断言。这条分工决定了本篇的两个重点：断言怎么写（`expect` 会轮询到超时，不需要手写 sleep），以及测试怎么组织和跑（fixture、参数化、重试、报告）。

```text
本篇主线：
1. expect 断言 —— 自动重试 + 5 秒默认超时 + 自定义消息，替代 sleep 与 WebDriverWait
2. 断言清单 —— 26 个 Locator 断言 + 3 个 Page 断言（本机实测），以及软断言 expect.soft
3. 测试组织 —— pytest-playwright 内置 fixture、自定义 fixture、作用域与隔离
4. 参数化 —— pytest.mark.parametrize 与 --browser 多浏览器矩阵
5. 失败重试 —— pytest-rerunfailures 的 --reruns / @pytest.mark.flaky
6. 报告与产物 —— -v/-rA、--junitxml、--durations，以及失败时的 trace/screenshot/video
```

本机实测环境：Ubuntu 24.04、Python 3.14.7（venv 内）、playwright 1.64.0、pytest 9.1.1、pytest-playwright 0.10.0、pytest-xdist 3.8.0、pytest-rerunfailures 16.7、Chromium 156.0.8078.4（Chrome for Testing，随 playwright 1.64.0 安装到 `/root/.cache/ms-playwright/chromium-1248`）。下文所有 `text` 块中的输出都是本机真实运行结果，包括失败与异常也原样保留。

## expect 断言与自动重试

`playwright.sync_api.expect` 包装的是"会自己等"的断言。它拿到 locator 后不会只查一次，而是持续重新解析元素、重新计算条件，直到条件满足或超时（默认 5000ms，可用 `expect.set_options(timeout=...)` 全局改、也可逐条传 `timeout=`）。这解决的是 Web 测试最经典的假失败：页面数据还没回来、动画还没结束、接口慢了 300ms。

```python
from playwright.sync_api import Page, expect

def test_login_banner(page: Page, app_url: str) -> None:
    page.goto(app_url)
    page.get_by_test_id("username").fill("alice")
    page.get_by_test_id("password").fill("secret123")
    page.get_by_test_id("login-submit").click()
    # 演示站点的横幅在登录后 1.2 秒才显示；不写 sleep，不写 WebDriverWait
    expect(page.get_by_test_id("delayed-banner")).to_be_visible()
    expect(page.get_by_test_id("status")).to_have_text("synced")
```

这条用例在本机真实通过，耗时 2.3 秒——其中约 1.2 秒花在断言内部轮询上。失败时的报错信息里能直接看到轮询次数，这正是"它在等"的证据（真实输出，故意断言错的名称）：

```text
>       expect(logged_in_page.get_by_test_id("welcome")).to_have_text("欢迎，root")
E       AssertionError: Locator expected to have text '欢迎，root'
E       Actual value: 欢迎，alice
E       Call log:
E         - Expect "to_have_text" get_by_test_id("welcome") with timeout 5000ms
E         - waiting for get_by_test_id("welcome")
E           14 × locator resolved to <p data-testid="welcome">欢迎，alice</p>
E              - unexpected value "欢迎，alice"
E       Aria snapshot:
E       - paragraph: 欢迎，alice
```

`14 × locator resolved to` 表示 5 秒内重解析了 14 次；最后附带的 ARIA snapshot 是 Playwright 自动生成的页面可访问性快照，调试时比打印 HTML 有用得多。其余几种用法：

```python
from playwright.sync_api import expect

def test_expect_options(page) -> None:
    # 全局改断言超时，适合放在 conftest.py 里
    expect.set_options(timeout=10_000)

    # 单条断言覆盖超时
    expect(page.get_by_test_id("app-title")).to_have_text("任务台", timeout=15_000)

    # 自定义失败消息：报错第一行就是它，CI 日志里定位更快
    expect(page.get_by_test_id("app-title"), "首页标题应渲染完成").to_be_visible()

    # 反向断言同样会重试：等它消失（比如 loading 转轮）
    expect(page.get_by_test_id("spinner")).not_to_be_visible()
```

```text
要点：
- expect 的默认断言超时是 5000ms；expect.set_options(timeout=) 改全局，timeout= 参数改单条
- 失败信息包含重试次数（14 × locator resolved to）与自动生成的 ARIA snapshot
- expect(locator, "消息") 的第二个参数是自定义失败消息，只在失败时出现
- not_to_* 系列与正向断言同等的自动重试语义
- expect 只做断言，不做操作；等待元素可交互是 click/fill 内部的 actionability 检查负责的（见 19.2）
- 本机 expect.configure 不存在（实测 AttributeError），TS 版的 configure 不能照搬
```

## 断言清单与软断言

Playwright 的断言按目标分三类：`LocatorAssertions`（元素状态）、`PageAssertions`（页面状态）、`APIResponseAssertions`（接口响应，配合 `APIRequestContext` 使用）。本机实测 `LocatorAssertions` 提供 26 个正向断言，`PageAssertions` 提供 3 个，完整列表如下——这是照抄官方文档最容易漏掉细节的地方，以本机 `dir()` 的真实结果为准：

```text
LocatorAssertions 正向断言数量: 26
to_be_attached, to_be_checked, to_be_disabled, to_be_editable, to_be_empty,
to_be_enabled, to_be_focused, to_be_hidden, to_be_in_viewport, to_be_visible,
to_contain_class, to_contain_text, to_have_accessible_description,
to_have_accessible_error_message, to_have_accessible_name, to_have_attribute,
to_have_class, to_have_count, to_have_css, to_have_id, to_have_js_property,
to_have_role, to_have_text, to_have_value, to_have_values, to_match_aria_snapshot
PageAssertions: to_have_title, to_have_url, to_match_aria_snapshot
```

（`to_be_in_viewport`、`to_match_aria_snapshot`、`to_have_values` 等是较新版本才加入的，用老版本会直接 AttributeError；升级前先对照 release notes。）

常用的几类写法与实测结果：

```python
import re

def test_assertion_matrix(page, app_url: str) -> None:
    page.goto(app_url)

    # 页面级：标题与 URL，都支持字符串或正则
    expect(page).to_have_title("Playwright 演示任务台")
    expect(page).to_have_title(re.compile(r"演示.*台$"))
    expect(page).to_have_url(re.compile(r"127\.0\.0\.1:\d+/index\.html$"))

    # 元素状态
    username = page.get_by_test_id("username")
    expect(username).to_be_visible()
    expect(username).to_be_editable()
    expect(username).to_be_enabled()
    expect(username).to_be_empty()          # input 没有值时
    expect(page.get_by_test_id("remember")).not_to_be_checked()

    # 文本、属性、计数
    page.get_by_test_id("username").fill("alice")
    expect(username).to_have_js_property("value", "alice")
    expect(page.get_by_test_id("login-submit")).to_have_attribute("type", "submit")
    expect(page.get_by_test_id("login-submit")).to_have_text("登录")
    expect(page.get_by_test_id("todo-item")).to_have_count(0)

    # 列表整体文本
    page.get_by_test_id("password").fill("secret123")
    page.get_by_test_id("login-submit").click()
    page.get_by_test_id("add-todo").click()
    items = page.get_by_test_id("todo-item")
    expect(items).to_have_text(["任务 1"])
    assert items.all_text_contents() == ["任务 1"]

    # ARIA 快照（>= 1.60）：本机实测可用，比断言整段 HTML 稳定
    expect(page.get_by_test_id("app-title")).to_match_aria_snapshot('- heading "任务台" [level=1]')
```

软断言（`expect.soft`）用于"一次跑完所有检查再统一汇报"：失败不中断用例，但最终仍然把用例标记为失败。它需要 pytest-playwright `0.8.0` 以上（官方文档明确说明），本机 0.10.0 可用。

```python
def test_soft_assertions(page, app_url: str) -> None:
    page.goto(app_url)
    # 这几条都失败也不会中断
    expect.soft(page.get_by_test_id("app-title")).to_have_text("任务台")
    expect.soft(page.get_by_test_id("login-submit")).to_be_enabled()
    expect.soft(page.get_by_test_id("login-error")).to_be_hidden()
    # 后面的硬断言仍然照常执行
    expect(page.get_by_test_id("password")).to_have_attribute("type", "password")
```

```text
要点：
- 断言分三类：LocatorAssertions（26 个）/ PageAssertions（3 个）/ APIResponseAssertions
- to_have_text 是全等匹配（支持正则与列表），to_contain_text 是子串匹配，别混用
- to_have_attribute 读 HTML 属性，to_have_js_property 读 JS 属性/DOM 属性（dataset、value 等）
- expect.soft 收集所有失败，需要 pytest-playwright >= 0.8.0；本机 0.10.0 实测可用
- 断言元素不存在用 to_have_count(0)；断言元素隐藏用 to_be_hidden()/not_to_be_visible()
- ARIA 快照断言 to_match_aria_snapshot 在 1.60+ 提供，写错的快照只需按提示覆盖
```

## 测试组织与 Fixture

`pytest-playwright` 把浏览器生命周期做成 fixture 链，粒度从粗到细是：`playwright`（session，进程级）→ `browser_type`（session）→ `browser`（session）→ `browser_context_args`（session）→ `context`（function）→ `page`（function）。`browser` 是 session 作用域，所以一个 worker 只启动一次浏览器；`context`/`page` 是 function 作用域，每个用例都是全新上下文，cookie、localStorage、网络拦截互不串味——这就是"用例之间天然隔离"的来源。

可覆写的配置型 fixture 与标记（本机 0.10.0 实测）：

```python
# conftest.py
import pytest

@pytest.fixture(scope="session")
def browser_context_args(browser_context_args):
    """全局覆写上下文参数：视口、时区、语言、忽略 HTTPS 错误。"""
    return {
        **browser_context_args,
        "viewport": {"width": 1440, "height": 900},
        "locale": "zh-CN",
        "ignore_https_errors": True,
    }

@pytest.fixture
def logged_in_page(page, app_url):
    """自定义 fixture：把"登录"这一前置步骤封装掉，用例只写业务。"""
    page.goto(app_url)
    page.get_by_test_id("username").fill("alice")
    page.get_by_test_id("password").fill("secret123")
    page.get_by_test_id("login-submit").click()
    page.get_by_test_id("welcome").wait_for()
    return page
```

按用例粒度覆写上下文参数用 marker（真实通过）：

```python
@pytest.mark.browser_context_args(timezone_id="Asia/Shanghai", locale="zh-CN")
def test_context_args_marker(page, app_url: str) -> None:
    page.goto(app_url)
    assert page.evaluate("Intl.DateTimeFormat().resolvedOptions().locale") == "zh-CN"
```

其他常用 fixture 与标记：`browser_name`（当前浏览器名字符串，用于按浏览器分支）、`new_context`（在一个用例里开第二个隔离上下文）、`@pytest.mark.skip_browser("firefox")`、`@pytest.mark.only_browser("chromium")`、`--base-url` 配合 `page.goto("/path")`（由 pytest-base-url 提供）。多个上下文互不共享存储，本机真实通过：

```python
def test_two_contexts_isolated(page, app_url: str) -> None:
    page.goto(app_url)
    second = page.context.browser.new_context()
    try:
        page2 = second.new_page()
        page2.goto(app_url)
        assert page.evaluate("localStorage.length") == page2.evaluate("localStorage.length") == 0
    finally:
        second.close()
```

```text
要点：
- 作用域链：playwright/browser/browser_type/browser_context_args 是 session，context/page 是 function
- 配置型 fixture 覆写：browser_context_args、browser_type_launch_args、connect_options
- 每用例自动新上下文，跨用例不共享 cookie 与 localStorage，不需要手动清理
- browser_context_args 也可作为 marker 只覆盖单个用例（timezone_id/locale/viewport 等）
- CLI 参数只作用于默认 fixture；自己用 API 创建的 context/page 不受 --tracing 等影响（官方文档明确说明）
- 大量用例反复登录会拖慢套件：把登录状态存成 storage_state 复用（见 19.3）
```

## 参数化与浏览器矩阵

参数化有两层。第一层是 pytest 原生的 `@pytest.mark.parametrize`，负责数据维度（账号、环境、金额）；第二层是 `--browser` 参数，负责浏览器维度，它由插件自动展开——`pytest --browser chromium --browser webkit` 会把同一批用例在每个浏览器上各跑一遍，用例 id 自动带上 `[chromium]`/`[webkit]` 后缀。

```python
import pytest
from playwright.sync_api import expect

@pytest.mark.parametrize(
    ("username", "password", "should_pass"),
    [
        ("alice", "secret123", True),
        ("bo", "secret123", False),   # 用户名过短
        ("carol", "123", False),      # 密码过短
        ("", "secret123", False),
    ],
    ids=["ok", "short-user", "short-pass", "empty-user"],
)
def test_login_data_driven(page, app_url, username, password, should_pass):
    page.goto(app_url)
    page.get_by_test_id("username").fill(username)
    page.get_by_test_id("password").fill(password)
    page.get_by_test_id("login-submit").click()
    if should_pass:
        expect(page.get_by_test_id("welcome")).to_be_visible()
    else:
        expect(page.get_by_test_id("login-error")).to_be_visible()
```

本机真实输出（用例 id 里同时带浏览器维度与数据维度；中文 id 会被转义，样子见"踩坑记录"）：

```text
tests/test_fixtures_params.py::test_select_parameterized[chromium-low] PASSED [ 71%]
tests/test_fixtures_params.py::test_select_parameterized[chromium-mid] PASSED [ 85%]
tests/test_fixtures_params.py::test_select_parameterized[chromium-high] PASSED [100%]
======================= 7 passed, 5 deselected in 8.41s ========================
```

运行浏览器矩阵与设备模拟：

```bash
# 默认只跑 chromium；装了几个浏览器就写几次 --browser
pytest --browser chromium --browser firefox --browser webkit

# 走真实 Chrome/Edge（channel 需要本机装了该浏览器）
pytest --browser-channel chrome

# 设备模拟：视口 + UA + 触摸一起换
pytest --device "iPhone 13"

# 定向跑某一个参数化组合
pytest -k "mid"
```

```text
要点：
- --browser 可重复传，插件为每个浏览器生成一份用例；未安装的浏览器会报错提示 playwright install
- 一个用例内要跑多浏览器只能用 --browser，不能靠参数化（参数化里拿不到 browser_type 实例）
- --device / --browser-channel 只对默认 page/context fixture 生效
- ids 用英文可读性最好；中文 id 会被转义（见踩坑 3）
- 数据量大时把参数表外置成 tests/data/*.json，别把同一个用例复制 20 遍
- 参数化 + xdist 并行是提速主力，每个参数组合都要能独立跑（见 19.7）
```

## 失败重试与不稳定用例

Python 端没有 Playwright Test 的 `retries` 配置项，重试交给 pytest 生态：`pytest-rerunfailures` 提供 `--reruns`（命令行）、`@pytest.mark.flaky(reruns=...)`（用例级）和 ini 配置，三者的优先级是标记 > 命令行 > 配置文件，另外 `--force-reruns` 可以覆盖一切。本机 16.7 版本实测输出：

```bash
pip install pytest-rerunfailures            # 本机安装版本 16.7（需要 pytest >= 8.1）
pytest --reruns 2 --reruns-delay 1          # 失败用例最多重跑 2 次，每次间隔 1 秒
pytest --reruns 3 --only-rerun AssertionError    # 只对特定异常重试
pytest --reruns 3 --rerun-except OSError         # 排除特定异常
```

```python
@pytest.mark.flaky(reruns=2, reruns_delay=1)
def test_intentionally_flaky(page, app_url: str) -> None:
    """演示：第一次失败、第二次成功的用例。"""
    ...
```

```text
tests/test_retries_report.py::test_intentionally_flaky[chromium] RERUN   [100%]
tests/test_retries_report.py::test_intentionally_flaky[chromium] PASSED  [100%]

========================== 1 passed, 1 rerun in 7.79s ==========================
```

注意"1 passed, 1 rerun"的语义与 Playwright Test 的 flaky 分类一致：**最终通过**的报告只显示 passed + rerun，不会失败退出，所以重试会掩盖真实缺陷——必须同时统计 rerun 次数并在超阈值时告警（CI 里 grep 输出或看测试报告的 rerun 列）。

重试前清理状态是必须的，否则第二次跑的还是脏环境。Python 端的做法是 hooks 里读取执行次数（`pytest-rerunfailures` 会给 test item 挂 `execution_count` 属性，官方文档示例即用 `item.execution_count`）：

```python
# conftest.py
import pytest

@pytest.hookimpl(tryfirst=True)
def pytest_runtest_setup(item):
    """重试时打日志，便于在 CI 里量化不稳定用例。"""
    count = getattr(item, "execution_count", 1)
    if count > 1:
        print(f"[RERUN {count}] {item.nodeid}")
```

```text
要点：
- Python 端重试用 pytest-rerunfailures：--reruns / --reruns-delay / --only-rerun / --rerun-except
- @pytest.mark.flaky(reruns=N, condition=...) 支持条件重试（如只在 Windows 上重试）
- 优先级：标记 > 命令行 > pyproject/pytest.ini > --force-reruns 全局覆盖
- 与 pytest-xdist 的 --looponfail 和核心 --pdb 不兼容（官方文档明确列出）
- 重试通过只说明"用例不稳定"，要在报告里统计 rerun 次数，别把重试当修复
- 重试前清理服务端/数据库状态，否则后一次跑的是脏数据
```

## 测试报告与产物

报告用 pytest 原生的那套就够了：`-v` 看用例名、`-rA` 打印所有非通过结果、`--junitxml` 出给 CI 消费的 XML、`--durations` 找慢用例。Playwright 侧的价值在于**失败产物**：`--tracing`、`--video`、`--screenshot` 三个开关，取值都是 `on` / `off` / `retain-on-failure`（screenshot 是 `only-on-failure`），产物默认落在 `test-results/`，可用 `--output=` 改。本机真实运行（故意失败的用例 + 三个开关 + 自定义输出目录）：

```bash
pytest tests/test_retries_report.py::test_intentionally_failing \
  --tracing=retain-on-failure \
  --video=retain-on-failure \
  --screenshot=only-on-failure \
  --output=artifacts \
  --junitxml=junit.xml
```

```text
artifacts/tests-test-retries-report-py-test-intentionally-failing-chromium/test-failed-1.png
artifacts/tests-test-retries-report-py-test-intentionally-failing-chromium/trace.zip
artifacts/tests-test-retries-report-py-test-intentionally-failing-chromium/video.webm

-rw-r--r-- 1 root root  25776 test-failed-1.png
-rw-r--r-- 1 root root 160171 trace.zip
-rw-r--r-- 1 root root 104487 video.webm
```

产物目录名是把 node id 里的非字母数字压成 `-`（`tests/test_retries_report.py::test_intentionally_failing[chromium]` → `tests-test-retries-report-py-test-intentionally-failing-chromium`），`retain-on-failure` 会在用例通过时删掉产物，所以目录通常只在失败时出现。junit.xml 里插件会把三个产物路径塞进 `<properties>`，CI 上可以直接点开（真实片段）：

```text

  <properties>
    <property name="playwright_screenshot" value="artifacts/.../test-failed-1.png" />
    <property name="playwright_trace" value="artifacts/.../trace.zip" />
    <property name="playwright_video" value="artifacts/.../video.webm" />
  </properties>
```

套件全绿时的真实统计（30 个用例：28 passed、2 skipped）：

```text
SKIPPED [1] tests/test_retries_report.py:13: 演示用不稳定用例，需 PW19_DEMO_FLAKY=1
```

```text
要点：
- --tracing / --video / --screenshot 都支持 on、off、retain-on-failure（screenshot 是 only-on-failure）
- 产物默认在 test-results/；retain-on-failure 会在通过时清除，失败才留下
- junitxml 里带 playwright_trace / playwright_video / playwright_screenshot 三个 property，CI 可直接链接
- trace 的查看方式见 19.6；视频是 context 关闭时才写盘的，别在用例中途去找文件
- --durations=10 找慢用例比看总耗时有用；本机实测 teardown（关闭浏览器、落盘产物）才是大头
- Python 端没有 Playwright 官方 HTML 报告与 blob 报告，要 HTML 报告用 pytest-html 或 allure
```

## 应用场景实战

### 场景一：下单流程回归，用软断言一次暴露所有界面问题

需求：每天跑一遍关键流程回归，失败时希望**一次看到页面上所有不对的地方**，而不是修一个跑一次。做法是把"页面应该长什么样"的检查全部换成软断言，业务流程用硬断言——业务流程断了后面不用跑，UI 细节错了要一次看全。本机真实通过（`3 passed in 6.64s`）：

```python
import re
import pytest
from playwright.sync_api import Page, expect

@pytest.fixture
def checkout_page(page: Page, app_url: str):
    """模拟已登录的下单页。"""
    page.goto(app_url)
    page.get_by_test_id("username").fill("buyer01")
    page.get_by_test_id("password").fill("secret123")
    page.get_by_test_id("login-submit").click()
    page.get_by_test_id("priority").select_option("high")
    return page

def test_checkout_regression_soft(checkout_page: Page) -> None:
    page = checkout_page
    # 第一批：页面元素与文案，全部软断言，失败也继续
    expect.soft(page.get_by_test_id("welcome"), "问候语应包含登录名").to_have_text("欢迎，buyer01")
    expect.soft(page.get_by_test_id("status")).to_have_text("logged-in")
    expect.soft(page.get_by_test_id("priority-out")).to_have_text("高")
    expect.soft(page.get_by_test_id("login-error")).to_be_hidden()

    # 第二批：真正的业务流程，硬断言，断了立即报错
    page.get_by_test_id("add-todo").click()
    page.get_by_test_id("add-todo").click()
    expect(page.get_by_test_id("todo-item")).to_have_count(2)
    expect(page.get_by_test_id("todo-item").first).to_have_text("任务 1")
    page.get_by_test_id("load-remote").click()
    expect(page.get_by_test_id("todo-item")).to_have_count(3)   # 异步项 900ms 后到达
    expect(page.get_by_test_id("status")).to_have_text(re.compile(r"loaded|synced"))
```

运行 `pytest tests/test_scenario_19_5.py -v` 的真实输出：

```text
tests/test_scenario_19_5.py::test_checkout_regression_soft[chromium] PASSED [ 33%]
tests/test_scenario_19_5.py::test_multi_env_data_driven[chromium-staging] PASSED [ 66%]
tests/test_scenario_19_5.py::test_multi_env_data_driven[chromium-prod] PASSED [100%]

============================== 3 passed in 6.64s ===============================
```

这里有个真实踩坑：`status` 在异步项加载后会经历 `loading → loaded → synced`（登录成功 1.2 秒后的定时器把状态改成 `synced`），第一版用例硬断言 `"loaded"` 直接失败。断言"会变的状态"要么用正则接受中间态，要么断言最终稳态，不要断言瞬时值。

### 场景二：多环境数据驱动的冒烟套件 + 归档报告

需求：同一套用例在 staging 与 prod 两个环境跑，环境地址、账号从外部注入，结果产出 junit 报告给 CI 归档。做法：`--base-url` 传环境地址、环境变量传账号、`--junitxml` 出报告、`--reruns` 兜住偶发抖动。

```bash
# staging：直接对预发环境跑冒烟
PW19_ENVS=staging pytest tests/test_scenario_19_5.py \
  --base-url https://staging.example.com \
  --reruns 2 --reruns-delay 1 \
  --tracing=retain-on-failure \
  --junitxml=reports/staging.xml -q

# prod：只跑只读用例，禁止写操作
PW19_ENVS=prod pytest -m "smoke and not write" \
  --base-url https://www.example.com \
  --junitxml=reports/prod.xml -q
```

配套用例只读环境变量，代码不随环境改；`app_url` 这类 fixture 在有 `--base-url` 时应优先用它（本机 conftest 的实现是 `PW19_BASE_URL` 环境变量优先于本地站点）：

```python
@pytest.mark.parametrize(("env", "expected_status"),
                         [("staging", "logged-in"), ("prod", "logged-in")],
                         ids=["staging", "prod"])
def test_multi_env_data_driven(checkout_page, env, expected_status):
    expect(checkout_page.get_by_test_id("status")).to_have_text(expected_status)
    assert env in os.environ.get("PW19_ENVS", "staging,prod")
```

CI 侧只需三行：安装依赖、跑 pytest 带上 `--junitxml` 与 `--tracing`、上传 `test-results/` 与报告目录（完整流水线见 19.7）。

```text
要点：
- 环境差异全部走 CLI 参数与环境变量，用例代码保持不变
- --reruns 只用于兜住偶发抖动，报告里要统计 rerun 次数，出现 rerun 就要跟进
- 冒烟套件用 -m smoke 圈定，生产环境跑之前先确认没有写操作用例
- 断言瞬时状态会随机失败：改用正则接受中间态或断言最终稳态
- junit 报告与 trace 产物一起归档，失败时不用重新复现就能定位
```

## 最佳实践与踩坑记录

1. 断言 DOM 状态只用 `expect`，不用裸 `assert`。`assert page.inner_text("#x") == "ok"` 不会重试，页面慢 100ms 就失败；只有断言非 DOM 状态（JS 变量、接口返回值）时才退回 `assert`。
2. 用例必须可独立运行且顺序无关。每个用例拿到全新 context，不要依赖"上一个用例点了登录"这类隐式状态；共享状态会让并行（19.7）与重试都失效。
3. 前置步骤封装成 fixture，不封装成函数调用链。把登录、建单、清数据做成 fixture 后，失败点、耗时、依赖关系在报告里一目了然，也方便按用例覆写。
4. 参数化用例的 id 用英文，或显式传 `ids=[...]`。中文 id 在 pytest 9 里会被转义成 `\uXXXX`，CI 日志与报告里基本没法看。
5. 重试只兜抖动，不掩盖缺陷。给 `@pytest.mark.flaky` 加上 `condition=` 限制平台范围，并统计 rerun 次数；一个用例连续多次需要重试就是缺陷，不是配置问题。
6. 失败产物只留失败的那一份。`retain-on-failure` 组合（trace + video + screenshot）是默认选择，全量记录会显著拖慢套件并让产物目录爆炸。

坑 1：Python 端没有 `expect.poll`，从 TS 文档照抄会直接报错。

结论：`expect.poll(lambda: ...)` 在 Python API 里不存在，本机 1.64.0 实测报 `AttributeError: 'Expect' object has no attribute 'poll'`。

原因：`expect.poll` 是 Playwright Test（Node 端测试运行器）的独有 API，Python 这边的 `expect` 只是 `LocatorAssertions`/`PageAssertions` 的工厂，没有非 DOM 轮询能力。

解法：需要轮询非 DOM 状态时用 `page.wait_for_function("window.__app.getLoggedIn() === true")`（默认超时 30s，可传 `timeout=`），再对 DOM 状态用 `expect` 断言，本机实测通过。

坑 2：`to_have_class` 对没有 class 属性的元素会失败，即使正则看起来能匹配空串。

结论：`expect(button).to_have_class(re.compile(r"\b"))` 在本机实测失败，报错为 `Locator expected to have class ... Actual value:`（实际值是空）。

原因：元素根本没有 class 属性时实际值是空字符串，断言是把期望值与实际值做匹配，正则里的 `\b` 在空串上不成立，而且报错信息不会告诉你"元素压根没有这个属性"。

解法：只对确实有 class 的元素断言 class；判断"有没有某个 class"用 `to_contain_class("todo-item")`，判断状态属性改用 `to_have_attribute("data-state", "open")`。

坑 3：中文参数化 id 在终端与 junit 报告里都被转义成 `\uXXXX`。

结论：`ids=["正常登录", ...]` 跑起来 id 是 `test_login_parameterized[chromium-\u6b63\u5e38\u767b\u5f55]`，终端、`--junitxml` 输出、xdist 输出里全是转义形式。

原因：pytest 出于"避免非 ASCII 的 node id 破坏下游消费者"的考虑，默认对非 ASCII 节点 id 做 unicode 转义；本机 pytest 9.1.1 实测如此。

解法：优先用英文 id；确实要中文时用 `pytest -o disable_test_id_escaping_and_forfeit_all_rights_to_community_support=true`（或写进 `pytest.ini`），本机实测 id 恢复为 `[chromium-正常登录]`，但该开关的名字本身说明官方不担保生态兼容，需自行评估。

坑 4：`--tracing=on` 会让套件明显变慢，且产物目录会积累大量 trace。

结论：本机同一批用例关掉 tracing 时 30 个用例 14.55 秒；打开 `--tracing=on` 后每个用例都录 screencast 与 DOM 快照，套件耗时与磁盘占用都成倍上升。

原因：trace 默认带 `screenshots=True`（screencast 帧）与 `snapshots=True`（每个动作前后各一份 DOM 快照），并且对每个动作都记录。

解法：日常跑用 `retain-on-failure`（通过时不留产物），需要全量追踪时只在临时分支开 `on`；CI 上再给产物目录加保留天数或只在失败时上传（见 19.7）。

坑 5：套件变慢的大头往往不是测试本身，而是 fixture 的 teardown。

结论：本机实测单个用例 `1 passed in 7.69s`，其中 `5.40s` 记在 teardown（`--durations=1` 的原始输出：`5.40s teardown tests/...::test_auto_retry_waits_for_late_content[chromium]`）。

原因：`browser` 是 session 作用域，浏览器进程在 session 结束时才关闭；用例自身操作只占 1-2 秒，其余时间花在上下文销毁、录屏落盘与浏览器退出上。

解法：用 `--durations=10` 看清时间分布，别急着优化断言；录屏/追踪按需开启，长套件用 xdist 并行摊开（见 19.7）。
