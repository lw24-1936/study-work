## 概述

Playwright 是 Microsoft 开源的端到端测试与浏览器自动化工具，同一套 API 覆盖 Chromium、Firefox、WebKit 三种渲染引擎，Python、JavaScript/TypeScript、Java、.NET 四种语言绑定。它要解决的问题是「真实浏览器里的交互为什么不可靠」：官方把自动等待（actionability checks）、浏览器上下文隔离、网络拦截、trace 追踪做成了框架内建能力，而不是让使用者自己写 sleep 和重试。本篇讲清楚它是什么、装到哪里、第一段代码怎么写，以及浏览器二进制的版本管理规则。

```text
本篇主线：
1. 定位 —— 与 Selenium / Cypress 的差异落在自动等待、上下文隔离、多引擎、网络拦截
2. 模型 —— BrowserType -> Browser -> BrowserContext -> Page 四层，隔离边界在上下文
3. 安装 —— venv + pip（内网换清华镜像）+ playwright install 下浏览器二进制
4. 版本绑定 —— Playwright 版本与浏览器 build 号强绑定，升级包必须重跑 install
5. 两种 API —— sync_api 与 async_api，异步版必须 await，混用会直接报错
6. 工程入口 —— 测试场景走 pytest-playwright 插件，脚本/爬虫走 sync_playwright()

官方文档：
- 安装：https://playwright.dev/python/docs/intro
- 浏览器管理：https://playwright.dev/python/docs/browsers
- 库模式（当通用自动化工具用）：https://playwright.dev/python/docs/library
```

本机实测环境：Ubuntu 24.04、Python 3.14.7、独立 venv 位于 `/root/.hermes/cache/scratch/pwvenv`、playwright 1.64.0、实际运行的 Chromium 156.0.8078.4（build 1248）。下文所有 `text` 块中的输出都是本机真实运行结果，包含失败与异常的地方也按原样保留。

## 定位与核心优势

Playwright 的官方定位是「为端到端测试而生」，同时它的库模式（`sync_playwright()` / `async_playwright()`）也可以当通用浏览器自动化工具使用。它和另外两个常见选择的差异可以粗略这样理解：

| 维度 | Playwright | Selenium | Cypress |
|---|---|---|---|
| 驱动协议 | 与浏览器内核直连，无额外 driver 进程 | 走 W3C WebDriver 协议，需要 driver 程序 | 在浏览器内运行，靠注入 |
| 自动等待 | 内建，动作前做可见/稳定/可交互/启用检查 | 需自行封装显式等待 | 内建重试，但命令排队语义不同 |
| 多标签 / 多窗口 | 原生支持，新页面句柄直接暴露 | 需切换窗口句柄 | 对多标签支持受限 |
| 多上下文隔离 | 一个浏览器进程内多份互相隔离的上下文 | 一般靠新建 session | 每个 spec 一个实例 |
| 网络拦截 / Mock | 内建 `route()`，可改请求、改响应、录放 HAR | 有限，多依赖代理工具 | 有 intercept，能力较窄 |
| 多引擎一致性 | Chromium / Firefox / WebKit 同一 API | 支持，但差异需自行兜底 | 以 Chromium 系为主 |

```text
选型要点：
- 需要多引擎验证、网络 Mock、多标签/多上下文 -> Playwright
- 已深度绑定 WebDriver 生态或需要远程真机网格 -> Selenium
- 组件级测试、偏好浏览器内调试体验 -> Cypress
- 三者差异是工程取舍，不是绝对优劣；具体能力以各自官方文档与项目实测为准
- Playwright 的 trace（快照 + 网络 + 日志一体）是它调试体验上最突出的部分
- Python 侧做爬虫/自动化脚本时，库模式不需要测试框架即可运行
- 官方安装与系统要求：https://playwright.dev/python/docs/intro
```

## 三层模型 浏览器 上下文 页面

Playwright 的对象模型是 `BrowserType` → `Browser` → `BrowserContext` → `Page` 四层。`BrowserType` 是引擎入口（`p.chromium` / `p.firefox` / `p.webkit`），`Browser` 是一个浏览器进程，`BrowserContext` 是**隔离边界**——每个上下文有自己的 cookie、localStorage、缓存、权限设置，相当于一个独立的隐身窗口，`Page` 是上下文里的一个标签页。

```python
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)   # 启动一个浏览器进程
    ctx = browser.new_context()                  # 隔离环境：cookie / localStorage 独立
    page = ctx.new_page()                        # 上下文里的一个标签页
    page.goto("http://127.0.0.1:8811/index.html")
    print(page.title())
    ctx.close()       # 关上下文，cookie 与存储随之丢弃
    browser.close()   # 关浏览器进程
```

本机实测的隔离效果（`browser.new_page()` 是「新建上下文 + 新建页面」的语法糖，写法和上下文显式创建的隔离语义不一样）：

```text
browser.contexts 数量: 2
ctx_a.pages 数量: 1
两个 page 是否同一对象: False
ctx_a localStorage: tok-ctx-a
ctx_b localStorage: None
ctx_a cookies: ['sid']
ctx_b cookies: []
同上下文新建页面共享 localStorage: tok-ctx-a
```

```text
层级与隔离：
- BrowserType（p.chromium / p.firefox / p.webkit）：引擎入口，负责 launch 与设备描述符
- Browser：一个进程；browser.new_page() 会隐式创建一个新上下文，用完即弃
- BrowserContext：隔离单位，cookie/存储/权限/代理/时区都在这一层配置
- Page：一个标签页；page.context 可以反查所属上下文
- 同一上下文内的多个 Page 共享 cookie 与 localStorage（上表第 7 行已实测）
- 上下文之间完全隔离，这是并行测试互不干扰的基础（细节见 19.3）
```

## 第一个脚本 同步与异步

Python 侧有 `sync_api` 与 `async_api` 两套等价 API，选哪套取决于调用方：脚本、爬虫、CLI 工具用同步版最省心；已经在 asyncio 生态里（FastAPI、aiohttp、异步任务队列）就用异步版。两套 API 方法名一一对应，同步版不加 `await`，异步版必须 `await`，混用会直接报错。

```python
# first_sync.py —— 同步版：最常用的形态
import re
from playwright.sync_api import sync_playwright, expect

with sync_playwright() as p:
    browser = p.chromium.launch()          # 默认 headless=True，不开窗口
    page = browser.new_page()
    page.goto("http://127.0.0.1:8811/index.html")
    expect(page).to_have_title(re.compile("Playwright"))
    expect(page.get_by_role("heading", level=1)).to_have_text("Playwright 实验台")
    print(page.title(), page.url, page.viewport_size)
    browser.close()
```

```python
# first_async.py —— 异步版：已在使用 asyncio 时用
import asyncio
from playwright.async_api import async_playwright


async def main():
    async with async_playwright() as p:
        browser = await p.chromium.launch()
        page = await browser.new_page()
        await page.goto("http://127.0.0.1:8811/index.html")
        print("async page.title():", await page.title())
        await browser.close()


asyncio.run(main())
```

```text

- with sync_playwright() as p 是上下文管理器，退出时自动清理驱动进程
- p.chromium.launch() 默认 headless=True；要看得见窗口就传 headless=False
- 资源按 page -> context -> browser 顺序关；生产脚本建议用 try/finally 保证关闭
- expect() 是断言式等待，条件不满足会自动重试到超时（详见 19.2）
- 异步版必须 await，且不能与同步版在同一线程混用
- 库模式不需要 pytest；测试场景才引入 pytest-playwright（详见 19.5）
- 官方库模式说明：https://playwright.dev/python/docs/library
```

## 启动参数与设备模拟

启动参数分两处：`launch()` 管浏览器进程本身（headless、args、channel、proxy、慢速动画、可执行文件路径），`new_context()` 管这个隔离环境的属性（locale、timezone_id、viewport、user_agent、geolocation、permissions）。设备模拟把官方设备描述符直接展开进上下文，不用手抄屏幕尺寸。

```python
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    # 1) 进程级参数
    browser = p.chromium.launch(headless=True, args=["--lang=zh-CN"])
    # 2) 上下文级参数：语言、时区、视口
    ctx = browser.new_context(
        locale="zh-CN",
        timezone_id="Asia/Shanghai",
        viewport={"width": 1280, "height": 720},
    )
    page = ctx.new_page()
    page.goto("http://127.0.0.1:8811/index.html")
    print(page.evaluate("navigator.language"),
          page.evaluate("Intl.DateTimeFormat().resolvedOptions().timeZone"))

    # 3) 移动端设备：官方描述符直接展开
    iphone = browser.new_context(**p.devices["iPhone 13"], locale="zh-CN")
    m = iphone.new_page()
    m.goto("http://127.0.0.1:8811/index.html")
    print(m.viewport_size, m.evaluate("matchMedia('(pointer: coarse)').matches"))
    browser.close()
```

```text
参数要点：
- launch(args=[...]) 是内核级开关；new_context(...) 是环境级开关，别混用
- locale / timezone_id 决定页面看到的语言与时区，测国际化必设
- p.devices 是官方设备描述符字典，按 key 展开即可，不必手抄 viewport
- 设备描述符会带 is_mobile、has_touch、device_scale_factor、user_agent
- 每次都显式设 viewport，否则不同机器上布局断言结果会漂移
- 需要系统品牌浏览器时用 launch(channel="chrome"|"msedge")
- 设备清单与字段以官方注册表为准：https://playwright.dev/python/docs/browsers
```

## 应用场景实战

### 场景一：上线后关键路径冒烟自检

发布后自动跑一遍关键路径：打开首页、断言标题、填表单、等到异步结果出现、存一张全页截图作为发布凭据。只用标准库与 playwright，可直接在 CI 或跳板机上运行，失败以退出码 1 结束。

```python
# smoke_check.py —— 上线后冒烟：真实浏览器、真实接口、产物落盘
import os
import sys
from datetime import datetime

from playwright.sync_api import sync_playwright, expect

BASE = os.environ.get("SMOKE_BASE_URL", "http://127.0.0.1:8811")
ARTIFACTS = os.environ.get("SMOKE_ARTIFACTS", "./artifacts")
os.makedirs(ARTIFACTS, exist_ok=True)
stamp = datetime.now().strftime("%Y%m%d-%H%M%S")

with sync_playwright() as p:
    browser = p.chromium.launch()
    ctx = browser.new_context(locale="zh-CN", timezone_id="Asia/Shanghai",
                              viewport={"width": 1440, "height": 900})
    page = ctx.new_page()
    failures = []

    def step(name, fn):
        try:
            fn()
            print(f"[PASS] {name}")
        except Exception as exc:                      # 单步失败不中断，最后统一退出
            failures.append((name, str(exc).splitlines()[0]))
            print(f"[FAIL] {name}: {str(exc).splitlines()[0]}")

    step("首页可打开", lambda: page.goto(BASE + "/index.html", wait_until="load"))
    step("标题正确", lambda: expect(page).to_have_title("Playwright 实验台"))
    step("一级标题存在", lambda: expect(page.get_by_role("heading", level=1)).to_be_visible())

    def login():
        page.get_by_label("用户名").fill("smoke-bot")
        page.get_by_role("button", name="登录").click()      # 自动等待按钮变为可用
        expect(page.locator("#status")).to_contain_text("欢迎回来，SMOKE-BOT", timeout=5000)

    step("登录关键路径", login)
    page.screenshot(path=os.path.join(ARTIFACTS, f"smoke-{stamp}.png"), full_page=True)
    print("截图已保存:", os.path.join(ARTIFACTS, f"smoke-{stamp}.png"))
    browser.close()

if failures:
    print("冒烟失败项:", failures)
    sys.exit(1)
print("冒烟通过")
```

本机真实运行输出：

```text
[PASS] 首页可打开
[PASS] 标题正确
[PASS] 一级标题存在
[PASS] 登录关键路径
截图已保存: ./artifacts/smoke-20261015-220743.png
冒烟通过
```

### 场景二：多设备多视口批量截图归档

给设计评审或客户准备「桌面 + 手机 + 平板」三套页面截图。同一个浏览器进程开多个上下文即可，比反复启动浏览器快得多，而且各设备环境的 cookie、视口互不影响。

```python
# multi_viewport_shots.py —— 一次启动、多设备归档
import os

from playwright.sync_api import sync_playwright

TARGETS = {
    "prod": "http://127.0.0.1:8811/index.html",
}
DEVICES = ["Desktop Chrome HiDPI", "iPhone 13", "Pixel 7"]
OUT = "./artifacts/viewports"
os.makedirs(OUT, exist_ok=True)

with sync_playwright() as p:
    browser = p.chromium.launch()
    for env, url in TARGETS.items():
        for device in DEVICES:
            ctx = browser.new_context(**p.devices[device], locale="zh-CN")
            page = ctx.new_page()
            page.goto(url, wait_until="load")
            page.get_by_role("heading", level=1).wait_for(state="visible")
            safe = device.replace(" ", "-")
            path = os.path.join(OUT, f"{env}-{safe}.png")
            page.screenshot(path=path, full_page=True)
            print(f"{env}/{device} -> {path} ({page.viewport_size})")
            ctx.close()
    browser.close()
```

本机真实运行输出：

```text
prod/Desktop Chrome HiDPI -> ./artifacts/viewports/prod-Desktop-Chrome-HiDPI.png ({'width': 1280, 'height': 720})
prod/iPhone 13 -> ./artifacts/viewports/prod-iPhone-13.png ({'width': 390, 'height': 664})
prod/Pixel 7 -> ./artifacts/viewports/prod-Pixel-7.png ({'width': 412, 'height': 839})
```

## 最佳实践与踩坑记录

1. 每个项目一个独立 venv，`playwright` 包与浏览器二进制一起锁版本。升级包之后第一件事是重跑 `playwright install`，否则运行时报的可执行文件路径会和实际缓存对不上。
2. CI 用 `playwright install --with-deps chromium` 一条命令搞定系统依赖；本地开发用 `--only-shell` 可以少下约 190 MiB 的完整 Chromium。
3. 环境参数（locale、timezone_id、viewport、设备描述符）统一放在 `new_context()` 一处，不要在用例里零散设置，这样本地与 CI 行为一致。
4. 断言里不要依赖宿主机的默认窗口尺寸；用 `p.devices[...]` 显式固定渲染环境，避免布局断言在别人机器上漂移。
5. 库模式脚本判断成败要靠异常与退出码（`sys.exit(1)`），只打印日志会让 CI 永远显示绿色。
6. 截图、trace、视频统一落到 `artifacts/` 并写进 `.gitignore`，CI 里作为 artifact 上传，方便失败复盘。

坑 1：装完 pip 包直接跑脚本，报找不到浏览器内核
结论：`pip install playwright` 只装 Python 包，不含浏览器二进制，必须再执行 `playwright install`。
原因：Playwright 与浏览器 build 号强绑定，二进制按版本下载到 `~/.cache/ms-playwright`，不在 wheel 里。
解法：执行 `playwright install chromium`（CI 用 `--with-deps`）；升级包后同样要重跑一次。用 `playwright install --dry-run chromium` 可以提前看到本版本需要的 build 号与目标路径。

```text
Chrome for Testing 156.0.8078.4 (playwright chromium v1248)
  Install location:    /root/.cache/ms-playwright/chromium-1248
```

坑 2：缓存目录里明明有浏览器，却仍提示可执行文件不存在
结论：缓存里可能同时存在多份浏览器（本机 1234 与 1248 两套并存），当前版本的驱动只认自己那套 build 号。
原因：`playwright install --list` 会按安装来源分组列出，不同包版本各自引用不同 build。
解法：先 `playwright install --list` 确认当前安装引用了哪一份，再对它执行 `playwright install chromium`；不要手工改目录名去「对齐」版本。

```text
Playwright version: 1.62.1
  Browsers:
    /root/.cache/ms-playwright/chromium-1234
  References:
    /root/home/e2e-test/node_modules/playwright-core
```

坑 3：同步 API 与异步 API 混用
结论：`sync_api` 与 `async_api` 不能在同一线程里混用，在已运行的 asyncio loop 里调用同步版会被框架直接拒绝。
原因：同步版内部用 greenlet 接管事件循环，与已存在的 asyncio loop 冲突。
解法：项目里二选一。已有 asyncio 生态（FastAPI、aiohttp）就用 `async_playwright()`，普通脚本与爬虫用 `sync_playwright()`。

坑 4：系统缺少共享库导致浏览器启动即崩
结论：Linux 上常见 `libnss3`、`libatk`、`libgbm` 等系统库缺失，表现为启动阶段直接失败。
原因：浏览器二进制是标准 Chrome 构建，依赖一批系统动态库，最小化容器镜像里通常没有。
解法：`playwright install-deps chromium` 或 `playwright install --with-deps chromium`；内网走代理时按官方文档用 `sudo HTTPS_PROXY=... playwright install-deps`，否则 sudo 会丢掉环境变量。
