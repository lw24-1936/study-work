## 概述

LangGraph 是一个低层编排框架与运行时，专治「长时间运行、有状态」的 Agent 工作流：把流程建模成状态图（State = 共享状态，Node = 干活，Edge = 决定下一步），在图上提供持久化、流式、人在回路、时间旅行这些 Agent 必需但 LangChain 层不该管的能力。它最大的价值是能把**确定性的手写步骤**和**模型驱动的步骤**混在同一张图里——退款走规则分支、疑难走模型推理，边界清晰可审计。它不是 LangChain 的替代品，可以单独使用（不用 LangChain 的模型与工具抽象也行），但实践中常常搭配使用。

```text
本篇主线：
1. 状态图 —— TypedDict 状态、reducer（Annotated[list, operator.add] / add_messages）、super-step 语义
2. 节点与边 —— add_node / add_edge / START / END，节点返回「部分更新」而不是完整状态
3. 分支 —— add_conditional_edges 路由函数、Command(goto=...)、Send 做 map-reduce fan-out
4. 持久化 —— InMemorySaver / SqliteSaver(checkpoints + writes) / PostgresSaver，thread_id 隔离
5. 时间旅行 —— get_state / get_state_history / update_state / 用 checkpoint_id 回放
6. 人在回路 —— interrupt() + Command(resume=...)，必须有 checkpointer
7. 多智能体 —— supervisor 模式（Command 调度）、子图嵌套与状态键冲突
8. 流式 —— stream_mode 的 updates / values / messages / custom 与 get_stream_writer
```

本机实测环境：Ubuntu 24.04、Python 3.14.7，独立 venv `/root/.hermes/cache/scratch/lcvenv-b`，langgraph 1.2.15、langgraph-checkpoint 4.3.0、langgraph-checkpoint-sqlite 3.1.2、langchain-core 1.6.10。**本机没有 API key**，凡涉及模型的节点都用假模型或纯函数节点；下文 `text` 块全部是本机真实输出（含真实报错）。

## 状态图模型

状态是图里所有节点共享的数据结构，用 `TypedDict` 定义最直观。关键概念是 **reducer**：状态字段默认「后写覆盖前写」，如果多个节点（或同一节点的多次执行）要往同一个字段追加内容，就用 `Annotated[类型, reducer函数]` 声明合并方式。`add_messages` 是官方给消息列表准备的 reducer：它会按 id 去重、把新消息追加到末尾，是 `MessagesState` 的核心。

```python
import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

class ReviewState(TypedDict):
    text: str
    score: int
    audit: Annotated[list[str], operator.add]   # 追加而不是覆盖的 reducer

def check_length(state: ReviewState) -> dict:
    return {"score": len(state["text"]), "audit": ["check_length"]}   # 只返回要改的字段

def tag(state: ReviewState) -> dict:
    return {"audit": ["tag"]}

builder = StateGraph(ReviewState)
builder.add_node("check_length", check_length)
builder.add_node("tag", tag)
builder.add_edge(START, "check_length")
builder.add_edge("check_length", "tag")
builder.add_edge("tag", END)
graph = builder.compile()
print(graph.invoke({"text": "订单发货延迟", "audit": []}))
```

本机真实输出：

```text
节点: ['__end__', '__start__', 'check_length', 'tag']
边: [('__start__', 'check_length', False), ('check_length', 'tag', False), ('tag', '__end__', False)]
invoke: {'text': '订单发货延迟', 'score': 6, 'audit': ['check_length', 'tag']}
```

执行语义受 Google Pregel 启发：按「super-step」推进，同一 super-step 内可并行的节点一起跑，节点完成后沿边把更新发给下游节点；所有节点都不活跃且没有在途消息时图结束。这套模型解释了后面所有现象：为什么并行分支的写法是 super-step（而不是 `asyncio.gather`）、为什么循环要用条件边收口、为什么检查点能精确到某一步。

```text
要点：
- 状态用 TypedDict；要给字段加合并逻辑就写 Annotated[T, reducer]，operator.add 与 add_messages 是最常用的两个
- 节点返回「部分更新」字典（不要返回整个状态），框架按 reducer 合并
- MessagesState 等价于 {"messages": Annotated[list[AnyMessage], add_messages]}，对话类应用直接用
- compile() 不是可选项：它做结构校验（孤立节点等）并挂载 checkpointer / breakpoints
- 图是有向图不是树：允许环（条件边回到上游），但必须有退出条件
```

## 节点与边

节点是普通 Python 函数（也能是 Runnable），签名固定为「状态进、更新出」；`START` 与 `END` 是虚拟节点，分别代表入口和终点。边分两种：`add_edge` 是固定跳转，`add_conditional_edges` 由路由函数决定下一步。节点名会出现在状态、流式事件和 mermaid 图里，建议用动词短语命名（`classify`、`approve`、`summarize`），别用 `node1`。

```python
from langgraph.graph import StateGraph, START, END

b = StateGraph(Ticket)
b.add_node("classify", classify)      # 可以第二个参数传名字
b.add_node("handle", handle)
b.add_edge(START, "classify")         # 入口
b.add_conditional_edges("handle", route_after_handle, {"approve": "approve", "close": "close"})
b.add_edge("approve", "close")
b.add_edge("close", END)
graph = b.compile()

graph.get_graph().nodes           # 结构自检
graph.get_graph().draw_mermaid()  # 可直接贴文档的可视化
```

本机真实输出（含一个真实的多执行坑）：

```text
普通工单: {'ticket_id': 'T-100', 'text': '登录报错 401', 'category': 'account', 'need_approval': False, 'replies': ['[account] 已自动回复知识库答案', '工单已关闭']}
批准后结果: {'ticket_id': 'T-101', 'category': 'refund', 'need_approval': True, 'decision': 'approved', 'replies': ['已受理退款申请', '审批完成', '工单已关闭']}
```

```text
（错误写法，同时给 handle 加固定边与条件边时）
批准后结果 replies: ['已受理退款申请', '审批完成', '工单已关闭', '工单已关闭']
```

```text
要点：
- 节点函数可以同步也可以 async，返回值必须是状态字段的子集；返回 None 表示不改状态
- 同一对节点之间只用一种边：add_edge 与 add_conditional_edges 并存会让目标节点在同一 super-step 里被触发多次
- 边只是「数据流」，不要在边里写业务副作用；副作用全放节点，便于重放与测试
- 用 graph.get_graph().nodes / edges 做结构断言，能在 CI 里拦住「删节点忘删边」这类错误
- 复杂图按业务拆子图（见「多智能体编排」），不要把所有逻辑塞一张图里
```

## 条件分支与 Command Send

路由函数读状态、返回下一个节点名（或 `END`）。除了「边」，LangGraph 还提供两种图内控制流：`Command(goto=..., update=...)` 让**节点自己**决定跳转并同时更新状态（适合分类、调度类节点）；`Send(node, arg)` 由路由函数返回一个列表，实现 map-reduce 式的并行 fan-out（每个 `Send` 带着自己的 payload 进入同一节点的多个实例）。

```python
from langgraph.types import Command, Send

# 1) Command：节点内决定去向并更新状态（分类节点最典型）
def classify(state: RouterState) -> Command:
    return Command(goto="refund" if "退" in state["intent"] else "faq")

# 2) 条件边 + 路由表
b.add_conditional_edges("step", keep_going, {"step": "step", "done": "done"})

# 3) Send：由路由函数返回，注意不能由节点返回
def fan_out(state: MapState) -> list[Send]:
    return [Send("research", {"topic": t}) for t in state["topics"]]

mb.add_conditional_edges("plan", fan_out, ["research"])
```

本机真实输出：

```text
3 次循环: {'n': 3, 'log': ['step->1', 'step->2', 'step->3', 'done']}
条件边路由表: [('__start__', 'step', None), ('step', 'done', None), ('step', 'step', None), ('done', '__end__', None)]
无限循环（默认上限）-> GraphRecursionError : Recursion limit of 10007 reached without hitting a stop condition.
recursion_limit=10 而需要 50 步 -> GraphRecursionError : Recursion limit of 10 reached without hitting a stop condition.
recursion_limit=60 -> 跑完 50 轮, n = 50 , log 长度 = 51

Command 路由（退款）: {'intent': '我要退款', 'answer': '进入退款流程'}
Command 路由（咨询）: {'intent': '怎么开发票', 'answer': '命中知识库回答'}
Send 并行 fan-out: ['a: OK', 'b: OK', 'c: OK']
```

| 控制流手段 | 谁决定去向 | 典型用途 | 注意 |
|---|---|---|---|
| `add_edge` | 图结构（固定） | 顺序步骤 | 无法表达分支 |
| `add_conditional_edges` | 路由函数（读状态） | if/else、循环收口 | 路由表要覆盖所有返回值 |
| `Command(goto=...)` | 节点自己 | 分类、调度、动态跳转 | 与 `Command(update=...)` 可同时用 |
| `Send(...)` | 路由函数返回列表 | map-reduce 并行 | **不能由节点返回**，否则报 InvalidUpdateError |
| 子图 | 父图调用 | 复用一段流程 | 状态键同名会互相写入 |

```text
要点：
- 循环必须写退出条件；默认 recursion_limit 是 10007（本机实测，不是旧教程里的 25），别指望默认值帮你兜住
- 真正需要收紧时显式设 config={"recursion_limit": N}，把 N 设在「正常流程步数上限的 2 倍」左右
- Command 让你省掉一堆只有两条边的路由函数，但会让控制流散落在节点里，图大时反而难读
- Send 的 payload 会成为该节点实例的状态（不是完整图状态），节点里按需取字段即可
- 路由函数必须是纯函数：只读状态、不做副作用，否则重放与时间旅行会得到不同结果
```

## 检查点与持久化

检查点（checkpointer）把每一步的图状态落盘，`thread_id` 决定隔离粒度：同一 `thread_id` 的多次 `invoke` 共享历史，不同 `thread_id` 完全独立。`InMemorySaver` 适合开发与测试；`SqliteSaver` 落本地文件，重启不丢；`PostgresSaver` 用于生产与多副本。注意检查点保存的是「状态」，不是「业务数据」——业务数据该落库还是落库。

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.checkpoint.sqlite import SqliteSaver
import sqlite3

graph = cb.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "t-1"}}
graph.invoke({"messages": [HumanMessage("hello")], "turns": 0}, cfg)
graph.get_state(cfg)                       # 最新状态
list(graph.get_state_history(cfg))         # 全部快照（时间旅行用）

conn = sqlite3.connect("ckpt.sqlite", check_same_thread=False)
sgraph = cb.compile(checkpointer=SqliteSaver(conn))
```

本机真实输出：

```text
thread t-1 快照数: 6
thread t-2 快照数: 3
最新状态 turns: 1 消息: ['hello', '收到第 1 条', '再来一条', '收到第 1 条']
注意 turns 仍是 1：第二次 invoke 又把 turns=0 传了进去，输入会覆盖检查点里的值
thread t-3 不重复传 turns 时: 2
状态里的 checkpoint 元数据 key: ['parents', 'source', 'step']

sqlite 表: ['checkpoints', 'writes']
checkpoints 行数: 3
PostgresSaver 导入失败（需额外依赖）: ModuleNotFoundError
```

| Checkpointer | 存储 | 作用域 | 适用 |
|---|---|---|---|
| `InMemorySaver` | 进程内存 | 单进程 | 开发、测试、演示 |
| `SqliteSaver` | 本地文件 | 单机 | 单副本服务、桌面应用 |
| `PostgresSaver` | PostgreSQL | 多副本 | 生产环境、需要高可用 |
| 自定义 | 任意存储 | 任意 | 特殊合规要求（数据不出内网等） |

```text
要点：
- thread_id 是「会话主键」：前端会话 ID 直接映射它，注意长度限制（PostgresSaver 建议 < 255 字符）
- 检查点存的是图状态快照，业务实体（订单、工单）仍要落自己的库，别把 checkpointer 当数据库用
- 传进 invoke 的输入会覆盖检查点里的同名键（本机实测 turns 一直是 1 就是这个原因），想续算就别重复传
- 快照数量随步数增长，长期会话要配清理策略（按 thread 归档或删除），否则 sqlite/PG 会被撑大
- SqliteSaver 需要 check_same_thread=False 才能在多线程服务里用；生产别用 sqlite 做并发写
```

## 人在回路与时间旅行

人在回路只有两个动作：节点里调用 `interrupt(payload)` 主动暂停，外部用 `Command(resume=value)` 带上人工决策继续执行。暂停的前提是配置了 checkpointer，因为「现场」必须被存下来。时间旅行则是检查点带来的额外红利：可以拿到任意历史快照、指定 `checkpoint_id` 从某一刻重放、`update_state` 手工修正状态（例如人工改一个字段后重跑下游）。

```python
from langgraph.types import interrupt, Command

def approve_node(state: ApprovalState) -> dict:
    d = interrupt({"question": "是否批准？", "amount": state["amount"]})
    return {"decision": d}

agraph = ab.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "ap-1"}}
res = agraph.invoke({"amount": 8000}, cfg, version="v2")
print(res.interrupts[0].value)                       # 暂停，交给人工
res2 = agraph.invoke(Command(resume="approved"), cfg, version="v2")

# 时间旅行
history = list(graph.get_state_history(cfg))
first = history[-1]
graph.invoke(None, {"configurable": {"thread_id": "t-1", "checkpoint_id": first.config["configurable"]["checkpoint_id"]}})
graph.update_state(cfg, {"turns": 99}, as_node="chat")
```

本机真实输出：

```text
第一次调用中断: {'question': '是否批准 8000 元报销？', 'amount': 8000}
resume 后: {'amount': 8000, 'decision': 'approved'}
最早快照 turns: <无，初始快照> next: ('__start__',)
从最早快照重放（checkpoint_id 指定）后 turns: 1
update_state 后 turns: 99
```

```text
要点：
- interrupt 的返回值和 Command(resume=...) 的入参是「同一个值」，值的形状由业务约定（字典最灵活）
- 未配置 checkpointer 时 interrupt 无法恢复；InMemorySaver 重启即丢，生产必须换持久化实现
- invoke(None, cfg) 表示「从检查点继续，不提供新输入」，与传 input 的语义不同
- update_state 的 as_node 很重要：它决定这次更新被记在哪个节点的账上，进而影响后续路由
- 时间旅行适合排障与「改一处重跑下游」，但副作用（发消息、转账）会真的重放，写操作要幂等
```

## 多智能体编排

多智能体的常见形态是 supervisor：一个调度节点读状态决定派给哪个子智能体，子智能体干完回到 supervisor，直到收尾。用 `Command(goto=...)` 实现最直接。另一种复用手段是子图：把一张编译好的图作为节点塞进父图（`add_node("team", subgraph)`），可组合性更强，但要小心状态键冲突——本机实测父图与子图同名的 `log` 字段会被两边同时写入。

```python
def supervisor(state: SupState) -> Command:
    # 用状态里的显式标记判断，别用"消息里有没有 ToolMessage"这类隐式条件，容易死循环
    if "researcher" not in state["log"]:
        return Command(goto="researcher", update={"next_worker": "researcher", "log": ["supervisor->researcher"]})
    return Command(goto="writer", update={"next_worker": "writer", "log": ["supervisor->writer"]})

sb = StateGraph(SupState)
sb.add_node("supervisor", supervisor)
sb.add_node("researcher", researcher)
sb.add_node("writer", writer)
sb.add_edge(START, "supervisor")
sb.add_edge("researcher", "supervisor")   # 干完回到调度器
sb.add_edge("writer", END)
team = sb.compile()

ob = StateGraph(OuterState)
ob.add_node("team", team)                  # 子图当节点
```

本机真实输出：

```text
执行轨迹: ['supervisor->researcher', 'researcher', 'supervisor->writer', 'writer']
最终消息: ['写一份报告', '[researcher] 找到 3 篇资料', '[writer] 报告已生成']
子图嵌套 outer.log: ['kick', 'kick', 'supervisor->researcher', 'researcher', 'supervisor->writer', 'writer'] 消息数: 3
```

父图里 `kick` 只执行了一次，但 `outer.log` 里出现了两次 —— 父图与子图都有同名的 `log` 字段（同为 `Annotated[list, operator.add]`），子图的写入会合并到父图。命名空间不隔离是子图最容易踩的地方。

| 编排形态 | 结构 | 优点 | 代价 |
|---|---|---|---|
| supervisor | 中心调度 + 若干工人 | 控制集中、易审计、容易加审批 | 调度器是瓶颈，状态要携带「谁做过了」 |
| 子图嵌套 | 图中有图 | 复用成熟流程、可单独测试 | 状态键冲突、跨层传递参数麻烦 |
| 并行 fan-out | Send map-reduce | 天然并发、适合批量 | 汇聚结果要自己写 reducer |
| 分层 | 上级 supervisor 管下级团队 | 贴近组织结构、可扩展 | 延迟与调试成本随层数上升 |

```text
要点：
- 调度条件必须是状态里的显式标记（做过什么、还剩什么），不要用消息内容猜，「隐形条件」是死循环的头号来源
- 工人节点干完统一回到 supervisor，出口只在 supervisor 判断，这样终止条件只有一个地方要维护
- 子图与父图的状态键尽量加前缀（team_log / outer_log）避免互相写入
- 每个子智能体最好有独立的工具集与提示词，职责重叠会让调度判断失去意义
- 多智能体的最大成本是 token 与延迟（调度本身也是模型调用），能用单 Agent + 好工具解决就别上多智能体
```

## 流式与可视化

流式是 Agent 体验的关键：用户不等最终答案，先看到 token 与工具调用。`stream()` / `astream()` 的 `stream_mode` 决定你收到什么：`updates` 是每个节点执行后的状态更新（做进度条）、`values` 是每一步的完整状态、`messages` 是 `(token, metadata)` 元组（做打字机效果）、`custom` 是节点内 `get_stream_writer()` 推的自定义事件。`draw_mermaid()` 能把图导成 mermaid 图，直接贴进设计文档。

```python
from langgraph.config import get_stream_writer

def produce(state):
    w = get_stream_writer()          # 节点内向客户端推自定义进度
    w({"progress": "1/2"})
    return {"n": state["n"] + 1}

for chunk in graph.stream(inputs, stream_mode="updates"):
    print(chunk)
for token, meta in graph.stream(inputs, stream_mode="messages"):
    print(meta["langgraph_node"], token.content)
```

本机真实输出：

```text
stream_mode="updates": [{'produce': {'n': 1, 'log': ['produce']}}]
stream_mode="values": [0, 1]
stream_mode="custom": [{'progress': '1/2'}, {'progress': '2/2'}]
stream_mode=["updates","custom"] 首块: ('custom', {'progress': '1/2'})
stream_mode="messages"（无 LLM 节点，应无输出）: []
ainvoke 轨迹 / astream 块数: (['supervisor->researcher', 'researcher', 'supervisor->writer', 'writer'], 1)
```

## 应用场景实战

### 场景一：带检查点与人工审批的工单处理流程

场景：客服工单自动分类并回复，退款类工单需要主管审批。要求：普通工单一次跑完；退款工单暂停等审批；审批结果落库；服务重启后仍能查到每张工单的处理过程。

```python
"""15.8 场景一：工单流程（规则分支 + 人工审批 + SQLite 检查点）"""
import operator, sqlite3, os
from typing import Annotated, TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.types import Command, interrupt

DB = "tickets.sqlite"
if os.path.exists(DB):
    os.remove(DB)
conn = sqlite3.connect(DB, check_same_thread=False)


class Ticket(TypedDict):
    ticket_id: str
    text: str
    category: str
    need_approval: bool
    decision: str
    replies: Annotated[list[str], operator.add]


KEYWORDS = {"退款": "refund", "发票": "invoice", "登录": "account", "报错": "bug"}


def classify(state: Ticket) -> Command:
    """规则分类（确定性步骤，不花 token），再用 Command 跳转"""
    cat = next((v for k, v in KEYWORDS.items() if k in state["text"]), "other")
    return Command(goto="handle", update={"category": cat})


def handle(state: Ticket) -> dict:
    if state["category"] == "refund":
        return {"replies": ["已受理退款申请"], "need_approval": True}
    return {"replies": [f"[{state['category']}] 已自动回复知识库答案"], "need_approval": False}


def route_after_handle(state: Ticket) -> str:
    return "approve" if state["need_approval"] else "close"


def approve(state: Ticket) -> dict:
    d = interrupt({"ticket": state["ticket_id"], "question": "退款是否批准？", "category": state["category"]})
    return {"decision": str(d), "replies": ["审批完成"]}


def close(state: Ticket) -> dict:
    return {"replies": ["工单已关闭"]}


b = StateGraph(Ticket)
b.add_node("classify", classify)
b.add_node("handle", handle)
b.add_node("approve", approve)
b.add_node("close", close)
b.add_edge(START, "classify")
b.add_conditional_edges("handle", route_after_handle, {"approve": "approve", "close": "close"})
b.add_edge("approve", "close")
b.add_edge("close", END)

graph = b.compile(checkpointer=SqliteSaver(conn))

# 普通工单
print(graph.invoke({"ticket_id": "T-100", "text": "登录报错 401", "replies": []},
                   {"configurable": {"thread_id": "T-100"}}))

# 退款工单：中断 -> 批准
cfg = {"configurable": {"thread_id": "T-101"}}
paused = graph.invoke({"ticket_id": "T-101", "text": "申请退款 8000 元", "replies": []}, cfg, version="v2")
print("中断 payload:", paused.interrupts[0].value)
done = graph.invoke(Command(resume="approved"), cfg, version="v2")

# 退款工单：中断 -> 拒绝
cfg2 = {"configurable": {"thread_id": "T-102"}}
graph.invoke({"ticket_id": "T-102", "text": "申请退款 99999 元", "replies": []}, cfg2, version="v2")
rej = graph.invoke(Command(resume="rejected"), cfg2, version="v2")

# 运行期自检：审批类工单必须留下 decision
assert graph.get_state(cfg).values["decision"] == "approved"
assert rej.value["decision"] == "rejected"
```


### 场景二：并行 fan-out 批量处理（Send map-reduce）

场景：一批文档要并行处理（抽取、校验、转换），单个失败不能拖垮整批，最后要给出成功/失败汇总。用 `Send` 把每份文档分发到 `process` 节点的独立实例，结果用 reducer 汇聚。

```python
"""15.8 场景二：批量并行处理"""
import operator
from typing import Annotated, TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.types import Send


class Batch(TypedDict):
    docs: list[str]
    results: Annotated[list[str], operator.add]
    failed: Annotated[list[str], operator.add]


def dispatch(state: Batch) -> dict:
    return {}


def fan_out(state: Batch) -> list[Send]:
    # 必须由条件边的路由函数返回 Send，节点返回 Send 会被当成状态更新而报错
    return [Send("process", {"doc": d}) for d in state["docs"]]


def process(payload: dict) -> dict:
    d = payload["doc"]
    if d == "bad":
        return {"failed": [d]}                     # 单点失败不影响其他分支
    return {"results": [f"{d} -> {len(d)} chars"]}


def summarize(state: Batch) -> dict:
    return {"results": [f"共成功 {len(state['results'])} 个，失败 {len(state['failed'])} 个"]}


b2 = StateGraph(Batch)
b2.add_node("dispatch", dispatch)
b2.add_node("process", process)
b2.add_node("summarize", summarize)
b2.add_edge(START, "dispatch")
b2.add_conditional_edges("dispatch", fan_out, ["process"])
b2.add_edge("process", "summarize")
b2.add_edge("summarize", END)
g2 = b2.compile()

out = g2.invoke({"docs": ["制度A", "制度B", "bad", "制度D"], "results": [], "failed": []})
print(out["results"], out["failed"])
```

本机真实输出：

```text
### 场景二：并行 fan-out 批量处理（Send map-reduce）

并行结果: ['制度A -> 3 chars', '制度B -> 3 chars', '制度D -> 3 chars', '共成功 3 个，失败 1 个']
失败清单: ['bad']
执行顺序（updates 流）: [['dispatch'], ['process'], ['process'], ['summarize']]
```

`updates` 流里能看到两个独立的 `process` 块——同一个节点被 fan-out 成了两个实例，说明并行生效；`summarize` 在它们都结束后才执行（汇聚点天然同步）。

## 最佳实践与踩坑记录

### 最佳实践

1. 先画图再写代码：把状态字段、节点、边、退出条件列清楚，LangGraph 的 bug 九成出在「图结构」而不是「节点实现」。
2. 状态字段用 reducer 声明合并方式，尤其是并行分支与循环体里的列表字段；默认的覆盖语义在并行时会静默丢数据。
3. 确定性的步骤（规则分类、格式校验、金额判断）一律写成普通节点，别交给模型——既省钱又可审计。
4. 会话粒度用 `thread_id`，并在网关层限制单个 thread 的最大轮数与最大检查点数，防止存储无限增长。
5. 副作用节点（发消息、写库、转账）必须幂等：时间旅行与重放会真的再执行一遍。
6. 上线前跑三件事：`get_graph().draw_mermaid()` 人工 review 拓扑、`updates` 流打点统计每节点耗时、用一套固定输入做回归对比。

### 踩坑记录

```text
坑 1：节点里 return [Send(...)] 直接报 InvalidUpdateError
结论：以为 Send 用法写错了，反复改 payload 结构。
原因：节点返回值被当作「状态更新」处理，而列表不是合法更新（本机实测报错原文：
      InvalidUpdateError: Expected dict, got [Send(node='research', arg={'topic': 'a'}), ...]）。
      Send 只能由 add_conditional_edges 的路由函数返回。
解法：把 fan-out 拆成「空节点 + 条件边」：节点只做前置准备并返回 {}，
      条件边的路由函数返回 list[Send]（本文场景二就是这么写的）。

坑 2：supervisor 写错判断条件，图静默跑到 10007 步才报错
结论：以为本地卡死或 langgraph 有 bug。
原因：默认 recursion_limit 是 10007（本机实测，不是旧教程常说的 25），调度条件用了「消息里有没有
      ToolMessage」这类隐式判断，而工人节点只追加 AIMessage，条件永远不翻转。
解法：调度条件一定基于状态里的显式标记（如 "researcher" not in state["log"]），
      并把 config={"recursion_limit": N} 设在合理值，让错误尽早暴露。

坑 3：多轮对话里自定义计数字段一直不增长
结论：以为检查点没生效，反复换 checkpointer 实现。
原因：每次 invoke 都把 turns=0 一起传了进去，输入值会覆盖检查点里的同名键（本机实测
      t-1 的 turns 一直是 1；改用「只在第一轮传 turns」后变成 2）。
解法：只有首轮传初始值，后续轮次只传新增字段（如 messages）；或者把该字段改成带 reducer 的累加语义。

坑 4：一个节点被执行两次，业务重复发通知
结论：以为框架重试或并发重复调度。
原因：同一个源节点同时声明了 add_edge 和 add_conditional_edges 指向同一目标，
      两条路径各触发一次（本机实测 replies 里 "工单已关闭" 出现两次）。
解法：同一对节点只保留一种边；用 get_graph().edges 打印路由表自检，
      并在有副作用的节点里加幂等键。

坑 5：子图嵌进父图后日志字段出现重复记录
结论：以为子图被执行了两次。
原因：父图与子图存在同名字段（都叫 log，且 reducer 都是 operator.add），
      子图的写入会合并进父图（本机实测父图 kick 只执行一次，但 outer.log 里 "kick" 出现两次）。
解法：父子图的状态字段加前缀区分（team_log / outer_log），或让子图使用独立的状态类型，
      不要跨层复用同名字段。

坑 6：用 interrupt 做人工审批，重启服务后审批会话就没了
结论：以为 Command(resume=...) 语义有问题。
原因：checkpointer 用的是 InMemorySaver，进程退出即丢；中断现场存在内存里，
      重启后 thread_id 已无法恢复。
解法：HITL 场景换持久化 checkpointer（SqliteSaver / PostgresSaver），
      并在服务启动时扫描「处于中断状态」的 thread 重建待审批列表。
```
