## 概述

模型本身是无状态的，多轮对话的本质是「把历史消息重新拼进本次请求」。LangChain 里这件事有两代方案：**第一代**是 `langchain_core.chat_history` 的存储基类 + `RunnableWithMessageHistory`，手工维护「按 session_id 存取消息」；**第二代**（1.x 官方推荐）是 LangGraph 的 checkpointer，把整段会话状态交给状态机持久化，调用时只给一个 `thread_id`。需要特别注意的是：本机实测 `langchain-core 1.6.10` 已经给前一代方案打了弃用警告，新项目应当直接走 checkpointer。

```text
本篇主线：
1. 历史管理 —— BaseChatMessageHistory 抽象 + 自实现存储；InMemoryChatMessageHistory 已弃用
2. 自动读写 —— RunnableWithMessageHistory 按 session_id 自动存取历史（同样已弃用）
3. 会话隔离 —— session_id / thread_id 是会话主键，隔离靠「键不同」而不是靠代码分支
4. 持久化 —— SQLite 是最小可用的落地方案；表格对比内存/文件/关系库/Redis
5. 上下文预算 —— trim_messages 按 token 裁剪 + 摘要压缩，两者组合使用
6. 推荐路径 —— create_agent + checkpointer + thread_id
```

本机实测环境：Python 3.14.7、`langchain 1.4.6`、`langchain-core 1.6.10`、`langgraph 1.2.15`，venv 在 `/root/.hermes/cache/scratch/lcvenv-a`。本机无 API key，模型侧用 `FakeListChatModel`（按顺序返回预置文本）；因此下文的「模型回复」都是假模型按调用顺序吐出的预置内容，不具备任何理解历史的能力——**这恰好能说明：会话记忆是框架在拼消息，而不是模型在记忆**。所有 `text` 块均为本机真实运行结果。

## 消息历史管理

历史存储的抽象是 `BaseChatMessageHistory`：只要实现 `messages` 属性与 `add_messages` / `clear` 方法，就能替换任何后端（内存、SQLite、Redis、Postgres）。它提供的便利方法包括 `add_user_message` / `add_ai_message`，往历史里塞消息时框架会自动按角色包装。

```python
from langchain_core.chat_history import BaseChatMessageHistory, InMemoryChatMessageHistory
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage, trim_messages

h = InMemoryChatMessageHistory()
h.add_user_message("我叫 alice，负责支付组")
h.add_ai_message("收到，已记录")
h.add_message(SystemMessage("风格：简洁"))
print("messages 类型:", [type(m).__name__ for m in h.messages])
print("最后一条:", h.messages[-1].content)
```

本机真实输出（注意第一行的弃用警告，不要忽略）：

```text
/root/.hermes/cache/scratch/s155_memory.py:19: LangChainDeprecationWarning: The class `InMemoryChatMessageHistory` was deprecated in LangChain 1.6.4 and will be removed in 2.0.0 See the short-term memory documentation for recommended alternatives: https://docs.langchain.com/oss/python/langchain/short-term-memory

=== 1. InMemoryChatMessageHistory：最基础的历史容器 ===
```

历史最终要变成提示词的一部分，用 `MessagesPlaceholder` 把消息列表整段插进模板：


```text
5. 历史里的消息顺序就是送给模型的顺序，别在中间插入无关内容
6. 自己实现存储时，清空（clear）与按序读取要一起实现，否则会出现「删不干净」
```

## RunnableWithMessageHistory

`RunnableWithMessageHistory` 把「读历史 → 渲染模板 → 调用链 → 写回历史」这一套自动完成。使用要点：链路里必须有一个 `MessagesPlaceholder`；`input_messages_key` 指出哪一项是本次输入；`get_session_history` 是会话 ID 到存储对象的工厂函数——**框架不关心你怎么存，只关心你按 session_id 返回不同的对象**。

```python
from langchain_core.chat_history import BaseChatMessageHistory, InMemoryChatMessageHistory
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables.history import RunnableWithMessageHistory

store: dict[str, InMemoryChatMessageHistory] = {}


def get_session_history(session_id: str) -> BaseChatMessageHistory:
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]


prompt = ChatPromptTemplate.from_messages(
    [("system", "你是运维助手"), MessagesPlaceholder(variable_name="history"), ("human", "{input}")]
)
model = FakeListChatModel(responses=["已记录", "你叫 alice", "支付组", "好的"])
conversation = RunnableWithMessageHistory(
    prompt | model | StrOutputParser(),
    get_session_history,
    input_messages_key="input",
    history_messages_key="history",
)
cfg_a = {"configurable": {"session_id": "session-a"}}
print(conversation.invoke({"input": "我叫 alice，负责支付组"}, config=cfg_a))
print(conversation.invoke({"input": "我叫什么"}, config=cfg_a))
print("session-a 历史条数:", len(store["session-a"].messages))
```

本机真实输出（同时打印了弃用警告）：

```text
<sys>:0: LangChainDeprecationWarning: RunnableWithMessageHistory is deprecated. Use LangGraph's built-in persistence instead.
=== 3. RunnableWithMessageHistory：自动读写历史 ===
已记录
你叫 alice
session-a 历史条数: 4
```

第一轮调用后历史变成了 4 条（1 条 human 输入 + 1 条 ai 回复，但框架会把每次调用的输入与输出各记一条，两轮共 4 条）——这就是「自动写入」的证据：调用方从没手动 add 过消息。

```text
1. RunnableWithMessageHistory 自动完成「读历史 -> 渲染 -> 调用 -> 写回」四步
2. 链路里必须存在 MessagesPlaceholder，否则历史无处注入
3. get_session_history(session_id) 返回该会话的存储对象，是唯一需要自己写的部分
4. input_messages_key 指出输入字典里哪一项是本次用户输入
5. 该组件在本机已打印弃用警告，新项目推荐直接用 LangGraph checkpointer
6. 老项目继续用也行，但要规划迁移（存储接口可复用，只是换成 checkpointer 管理）
```

## 会话隔离

会话隔离的本质是**键隔离**：每个请求带一个 `session_id`（或 LangGraph 的 `thread_id`），框架按这个键取各自的历史，不同的键互不可见。本机实测两个会话交错请求时，各自的存储对象不同、历史条数互不影响。

```python
cfg_b = {"configurable": {"session_id": "session-b"}}
print(conversation.invoke({"input": "我叫什么"}, config=cfg_b))
print("session-b 历史条数:", len(store["session-b"].messages))
print("两个会话的对象不同:", store["session-a"] is not store["session-b"])
```

本机真实输出：

```text
支付组
session-b 历史条数: 2
两个会话的对象不同: True
```

`session-b` 只有 2 条消息（它只被问过一次），而 `session-a` 有 4 条——同一个链路、同一个模型对象，仅靠 config 里的键就实现了隔离。上例中 `session-b` 得到「支付组」这个答案，并不是因为它知道 alice 的信息，而是假模型按顺序吐出了第 3 条预置文本；真实模型在没有历史的情况下会回答「不知道你是谁」。

LangGraph 侧对应的键是 `thread_id`：

```python
agent.invoke(
    {"messages": [{"role": "user", "content": "我叫什么"}]},
    {"configurable": {"thread_id": "t-1"}},   # 同 thread = 同一段对话
)
```

```text
1. 会话主键：LangChain 侧叫 session_id，LangGraph 侧叫 thread_id，语义相同
2. 隔离靠「键不同」实现，不要用 if/else 在代码里区分用户
3. 键要从认证上下文里取（如 JWT 的 sub），绝不能由客户端随意传入，否则可越权读他人历史
4. 同一个 session 的并发请求会争用同一份历史，需要加锁或改用 checkpointer
5. 假模型不会「记住」任何东西，它能答对只是预置文本的顺序巧合，别用它验证记忆逻辑
6. 会话键同时是成本归集维度：按 session 统计 token 与调用次数最自然
```

## 持久化存储

内存存储进程一重启就丢，生产必须落库。最小可用方案是 SQLite：一张表存 `session_id / seq / role / content`，实现 `BaseChatMessageHistory` 的三个成员即可。

```python
import sqlite3

from langchain_core.chat_history import BaseChatMessageHistory
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage

DB = "/root/.hermes/cache/scratch/lc_memory_demo.db"
conn = sqlite3.connect(DB)
conn.execute(
    "CREATE TABLE IF NOT EXISTS message_store ("
    " session_id TEXT NOT NULL, seq INTEGER NOT NULL, role TEXT NOT NULL, content TEXT NOT NULL)"
)
conn.commit()


class SqliteChatMessageHistory(BaseChatMessageHistory):
    """最小可用的 SQLite 历史存储。"""

    def __init__(self, session_id: str, path: str = DB):
        self.session_id = session_id
        self.path = path

    @property
    def messages(self):
        conn = sqlite3.connect(self.path)
        rows = conn.execute(
            "SELECT role, content FROM message_store WHERE session_id = ? ORDER BY seq",
            (self.session_id,),
        ).fetchall()
        conn.close()
        mapping = {"human": HumanMessage, "ai": AIMessage, "system": SystemMessage}
        return [mapping[r](content=c) for r, c in rows]

    def add_messages(self, messages) -> None:
        conn = sqlite3.connect(self.path)
        for m in messages:
            next_seq = conn.execute(
                "SELECT COALESCE(MAX(seq), 0) + 1 FROM message_store WHERE session_id = ?",
                (self.session_id,),
            ).fetchone()[0]
            conn.execute(
                "INSERT INTO message_store (session_id, seq, role, content) VALUES (?, ?, ?, ?)",
                (self.session_id, next_seq, m.type, m.content),
            )
        conn.commit()
        conn.close()

    def clear(self) -> None:
        conn = sqlite3.connect(self.path)
        conn.execute("DELETE FROM message_store WHERE session_id = ?", (self.session_id,))
        conn.commit()
        conn.close()
```

本机真实输出：

```text
=== 6. SQLite 持久化：进程重启后历史仍在 ===
写入后条数: 2
重新打开（模拟新进程）读到: [('human', '我叫 bob，负责订单组'), ('ai', '收到')]
另一会话 user-99 读到: []
```

把它接到 `RunnableWithMessageHistory` 上只改一行 `get_session_history` 的返回类型：

```python
sessions: dict[str, SqliteChatMessageHistory] = {}


def get_sql_history(session_id: str) -> BaseChatMessageHistory:
    if session_id not in sessions:
        sessions[session_id] = SqliteChatMessageHistory(session_id)
    return sessions[session_id]


conv_sql = RunnableWithMessageHistory(
    prompt | model | StrOutputParser(), get_sql_history,
    input_messages_key="input", history_messages_key="history",
)
conv_sql.invoke({"input": "我叫 bob"}, config={"configurable": {"session_id": "user-99"}})
conv_sql.invoke({"input": "再看一遍历史"}, config={"configurable": {"session_id": "user-99"}})
```

本机真实落库内容：

```text
=== 7. RunnableWithMessageHistory 接 SQLite 存储 ===
user-99 落库内容:
  human   我叫 bob
  ai      好的
  human   再看一遍历史
  ai      已记录
```

对比 `sqlite3.connect` 的开销，另一种常见做法是直接用 `langchain_community.chat_message_histories.SQLChatMessageHistory`（基于 SQLAlchemy），但本机实测它在缺少 `greenlet` 时导入直接失败：

```text
FAIL langchain_community.chat_message_histories -> ImportError: The SQLAlchemy asyncio module requires that the Python 'greenlet' library is installed. In order to ensure this dependency is available, use the 'sqlalchemy[asyncio]' install target: 'pip install sqlalchemy[asyncio]'
```

装 `sqlalchemy` 与 `greenlet` 之后即可正常导入。各存储方案的取舍：

| 方案 | 依赖 | 持久 | 适用场景 | 注意点 |
| --- | --- | --- | --- | --- |
| 内存 dict | 无 | 否 | 单测、本地调试 | 进程重启即丢，多实例不共享 |
| SQLite（自实现） | `sqlite3`（标准库） | 是 | 单机部署、中小流量 | 需要自己处理并发写与索引 |
| `SQLChatMessageHistory` | `sqlalchemy` + `greenlet` | 是 | 已有关系库的项目 | 社区包已 sunset，注意长期维护 |
| Redis / MongoDB | 对应驱动 | 是 | 多实例共享、低延迟 | 需要过期策略，历史会无限增长 |
| LangGraph checkpointer | `langgraph-checkpoint-*` | 是 | 1.x 推荐方案 | 存的是图状态，不是单纯消息列表 |

```text
1. BaseChatMessageHistory 只要能「按 session 顺序读」与「追加写」，就能接任何后端
2. SQLite 用标准库即可，适合单机；多实例部署换 Postgres / Redis
3. message_store 表建议加 (session_id, seq) 联合索引，历史长了以后读取性能靠它
4. SQLChatMessageHistory 需要 sqlalchemy[asyncio]（greenlet），本机实测缺 greenlet 时导入即失败
5. 历史是无界增长的，落库时必须配清理策略（按时间/条数）或摘要压缩
6. 持久化存的是明文对话，涉及个人信息时要加密或脱敏后再落库
```

## 摘要记忆与上下文裁剪

长会话的核心矛盾是「context 装不下」与「丢了信息质量下降」。两种手段必须组合使用：**裁剪**（`trim_messages`，硬性按 token 上限保留最近或用最早的若干条）与**摘要**（把老消息压缩成一段事实，替代原文）。

`trim_messages` 的签名（本机 `inspect.signature` 确认）包含 `max_tokens`、`token_counter`、`strategy`（`last` / `first`）、`allow_partial`、`start_on` / `end_on`、`include_system`、`text_splitter`。两个实测发现很关键：

```python
from langchain_core.messages import AIMessage, HumanMessage, trim_messages

long_history = []
for i in range(10):
    long_history.append(HumanMessage(f"第 {i} 个问题：这是一段用于占位的较长文本内容"))
    long_history.append(AIMessage(f"第 {i} 个回答：同样是一段占位文本"))


def count_tokens(msgs):
    """trim_messages 会把「整个消息列表」传进 token_counter，所以函数要处理列表而非单条。"""
    if isinstance(msgs, list):
        return sum(len(m.content) for m in msgs)
    return len(msgs.content)


trimmed = trim_messages(long_history, max_tokens=120, token_counter=count_tokens,
                        strategy="last", include_system=False, start_on="human")
print("strategy=last ->", len(trimmed), [m.content[:6] for m in trimmed])
print("错误示范 token_counter=len 的结果:", len(trim_messages(long_history, max_tokens=120, token_counter=len)))
```

本机真实输出：

```text
=== 4. trim_messages：按 token 上限裁剪 ===
裁剪前: 20 条 | 总字符数: 400
max_tokens=120 strategy=last -> 6 条: ['第 7 个问', '第 7 个回', '第 8 个问', '第 8 个回', '第 9 个问', '第 9 个回']
max_tokens=120 strategy=first -> 6 条: ['第 0 个问', '第 0 个回', '第 1 个问', '第 1 个回', '第 2 个问', '第 2 个回']
错误示范 token_counter=len 的结果: 20
strategy=first 传 start_on 报错: start_on parameter is only valid with strategy='last'
```

两条实测结论：**`token_counter=len` 完全不生效**（`len` 拿到的是「消息列表」的长度，恒等于消息条数 20，永远小于 `max_tokens=120`）；**`start_on` 只能与 `strategy="last"` 搭配**，否则抛 `ValueError`。

摘要压缩用一次额外的模型调用换取更短的上下文，本机的完整实现与输出：

```python
from langchain_core.messages import BaseMessage, SystemMessage

summarize_prompt = ChatPromptTemplate.from_template(
    "把下面的客服对话压缩成不超过 80 字的事实摘要，必须保留：用户姓名、订单号、当前诉求、已承诺的动作。\n"
    "对话：\n{history}"
)
summarizer = summarize_prompt | FakeListChatModel(
    responses=["张先生，订单 1001 未发货已催单，承诺今晚 18:00 前揽收；曾询问延迟赔付规则。"]
) | StrOutputParser()


def budget(messages: list[BaseMessage]) -> int:
    return sum(len(m.content) for m in messages)


def build_context(messages, max_chars: int = 120, keep_recent: int = 4):
    """超预算时：老消息摘要 + 最近 keep_recent 条原文。"""
    original = budget(messages)
    if original <= max_chars or len(messages) <= keep_recent:
        return messages, {"compressed": False, "before_chars": original, "after_chars": original}
    older, recent = messages[:-keep_recent], messages[-keep_recent:]
    summary = summarizer.invoke({"history": "\n".join(f"{m.type}: {m.content}" for m in older)})
    rebuilt = [SystemMessage(f"此前对话摘要：{summary}")] + recent
    return rebuilt, {
        "compressed": True, "before_chars": original, "after_chars": budget(rebuilt),
        "summarized_messages": len(older), "kept_messages": len(recent),
    }
```

本机真实输出：

```text
原始会话：9 条消息，共 174 字符
压缩统计: {'compressed': True, 'before_chars': 174, 'after_chars': 119, 'summarized_messages': 5, 'kept_messages': 4}

送给模型的消息：
  system  此前对话摘要：张先生，订单 1001 未发货已催单，承诺今晚 18:00 前揽收；曾询问延迟赔付规则。
  human   张先生：先登记吧
  ai      已登记补偿申请，工单 20261015-08
  human   张先生：现在能查一下物流吗
  ai      运单号 SF1234567890，当前状态：待揽收

=== 与 trim_messages 的对比（只截断、不摘要，信息会丢）===
trim_messages 后 6 条： ['张先生：如果超时有没有赔', '超过承诺时效可申请 5 ', '张先生：先登记吧', '已登记补偿申请，工单 2', '张先生：现在能查一下物流', '运单号 SF123456']
丢失的事实：订单号 1001 与 18:00 承诺是否还在 -> False

自检通过：摘要保留了订单号与承诺时效，且总长度下降
```

对比很直白：纯裁剪后「订单号 1001 与 18:00 承诺」已经不在上下文里（`False`），而摘要方案把它们保留了下来，同时字符数从 174 降到 119。

```text
1. token_counter 收到的是「消息列表」，写 sum(len(m.content) for m in msgs) 才有效；token_counter=len 恒不生效
2. start_on / end_on 只能配 strategy="last"；strategy="first" 传 start_on 会直接抛 ValueError
3. strategy="last" 保留最近对话（聊天场景默认），"first" 保留最早内容（长文档摘要场景）
4. include_system=True 可保证 system 指令不被裁掉，聊天场景通常要开
5. 摘要是「一次额外模型调用」换「更短的上下文」，要把它计入成本
6. 摘要提示词必须显式列出不能丢的字段（人名、单号、金额、承诺），否则模型会丢关键事实
```

## LangGraph checkpointer

1.x 的推荐做法：把整段会话状态交给 LangGraph 的 checkpointer，调用时给一个 `thread_id`。换后端只改 `checkpointer` 参数（`InMemorySaver` 用于开发，生产用 Postgres/SQLite 的 checkpoint 实现）。

```python
from langchain.agents import create_agent
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=FakeListChatModel(responses=["已记录：alice 负责支付组"]),
    tools=[],
    system_prompt="你是运维助手",
    checkpointer=InMemorySaver(),
)
out1 = agent.invoke(
    {"messages": [{"role": "user", "content": "我叫 alice，负责支付组"}]},
    {"configurable": {"thread_id": "t-1"}},
)
print("thread t-1 第一条:", out1["messages"][-1].content)
out2 = agent.invoke(
    {"messages": [{"role": "user", "content": "我叫什么"}]},
    {"configurable": {"thread_id": "t-1"}},
)
print("thread t-1 累计消息数:", len(out2["messages"]))
out3 = agent.invoke(
    {"messages": [{"role": "user", "content": "我叫什么"}]},
    {"configurable": {"thread_id": "t-2"}},
)
print("thread t-2 消息数（会话隔离）:", len(out3["messages"]))
```

本机真实输出：

```text
=== 8. LangGraph checkpointer：1.x 官方推荐的会话记忆 ===
thread t-1 第一条: 已记录：alice 负责支付组
thread t-1 累计消息数: 4
thread t-2 消息数（会话隔离）: 2
```

关键差别：`t-1` 第二次调用返回的 `messages` 里已经有 4 条（前一轮的历史 + 本轮），而 `t-2` 只有 2 条——**历史由 checkpointer 按 thread 自动装配，业务代码完全不用碰消息列表**。这是它与前一代方案最本质的区别，也是它替代 `RunnableWithMessageHistory` 的原因。

| 维度 | RunnableWithMessageHistory | LangGraph checkpointer |
| --- | --- | --- |
| 存储内容 | 消息列表 | 整个图状态（消息 + 自定义字段） |
| 会话键 | `config["configurable"]["session_id"]` | `config["configurable"]["thread_id"]` |
| 与 Agent 协作 | 需要手工包装 | `create_agent(..., checkpointer=...)` 原生支持 |
| 断点续跑 / 人工介入 | 不支持 | 支持（interrupt、恢复同一 thread） |
| 长会话裁剪 | 自己实现 | 内置摘要中间件，也可自定义 |
| 官方状态 | 已弃用 | 推荐 |

```text
1. 新项目直接用 checkpointer + thread_id，不要再写 get_session_history 工厂
2. InMemorySaver 只适合开发与测试；生产换持久化后端的 checkpointer
3. checkpointer 存的是图状态，除了消息还能存自定义字段（用户画像、待办）
4. 同一 thread_id 天然支持断点续跑与人工介入，这是老方案给不了的
5. 历史由框架装配，业务代码只传「本次新消息」，减少漏传/重复传的可能
6. 迁移时存储接口（BaseChatMessageHistory）可复用于自定义中间件，不必推翻重写
```

## 应用场景实战

### 场景一：多用户多会话客服机器人

客服系统的真实形态：多个用户同时在线、请求交错、历史必须落库且按用户隔离。下面的实现用 SQLite 存储 + `RunnableWithMessageHistory`，两侧会话交替提问验证互不串台。

```python
"""service_desk.py —— 多用户客服会话（SQLite 持久化 + 会话隔离）"""
import os
import sqlite3

from langchain_core.chat_history import BaseChatMessageHistory
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables.history import RunnableWithMessageHistory

DB = "/root/.hermes/cache/scratch/lc_service_desk.db"
if os.path.exists(DB):
    os.remove(DB)
sqlite3.connect(DB).execute(
    "CREATE TABLE IF NOT EXISTS message_store ("
    " session_id TEXT NOT NULL, seq INTEGER NOT NULL, role TEXT NOT NULL, content TEXT NOT NULL)"
).connection.commit()


class SqliteHistory(BaseChatMessageHistory):
    """按 session_id 隔离的 SQLite 消息历史。"""

    def __init__(self, session_id: str, path: str = DB):
        self.session_id = session_id
        self.path = path

    @property
    def messages(self):
        conn = sqlite3.connect(self.path)
        rows = conn.execute(
            "SELECT role, content FROM message_store WHERE session_id=? ORDER BY seq", (self.session_id,)
        ).fetchall()
        conn.close()
        cls = {"human": HumanMessage, "ai": AIMessage, "system": SystemMessage}
        return [cls[r](content=c) for r, c in rows]

    def add_messages(self, messages) -> None:
        conn = sqlite3.connect(self.path)
        for m in messages:
            seq = conn.execute(
                "SELECT COALESCE(MAX(seq),0)+1 FROM message_store WHERE session_id=?", (self.session_id,)
            ).fetchone()[0]
            conn.execute(
                "INSERT INTO message_store (session_id, seq, role, content) VALUES (?,?,?,?)",
                (self.session_id, seq, m.type, m.content),
            )
        conn.commit()
        conn.close()

    def clear(self) -> None:
        conn = sqlite3.connect(self.path)
        conn.execute("DELETE FROM message_store WHERE session_id=?", (self.session_id,))
        conn.commit()
        conn.close()


prompt = ChatPromptTemplate.from_messages(
    [
        ("system", "你是客服助手，称呼用户为 {customer}，回答不超过两句。"),
        MessagesPlaceholder("history"),
        ("human", "{input}"),
    ]
)
model = FakeListChatModel(
    # 本地假模型按固定顺序循环返回，不具备任何「理解历史」的能力：顺序对应 4 次调用的先后
    responses=[
        "张先生您好，已为您登记，工单号 20261015-01。",
        "李女士您好，退款会在 3 个工作日到账。",
        "您的订单 1001 今晚 18:00 前揽收。",
        "已为您重新发起退款审核。",
    ]
)
chain = prompt | model | StrOutputParser()

_history_cache: dict[str, SqliteHistory] = {}


def get_session_history(session_id: str) -> BaseChatMessageHistory:
    if session_id not in _history_cache:
        _history_cache[session_id] = SqliteHistory(session_id)
    return _history_cache[session_id]


chat = RunnableWithMessageHistory(
    chain, get_session_history, input_messages_key="input", history_messages_key="history"
)


def ask(session_id: str, customer: str, text: str) -> str:
    return chat.invoke(
        {"customer": customer, "input": text},
        config={"configurable": {"session_id": session_id}},
    )


print("=== 两个用户交错提问（真实场景里是两个浏览器会话同时在线）===")
print("user-1001:", ask("user-1001", "张先生", "我的订单 1001 还没发货"))
print("user-2002:", ask("user-2002", "李女士", "我的退款什么时候到"))
print("user-1001:", ask("user-1001", "张先生", "那什么时候能到"))
print("user-2002:", ask("user-2002", "李女士", "能帮我催一下吗"))

print("\n=== 落库结果（每个 session 独立成行）===")
for row in sqlite3.connect(DB).execute("SELECT session_id, COUNT(*) FROM message_store GROUP BY session_id"):
    print(f"  {row[0]}: {row[1]} 条消息")

print("\n=== 直接读回 user-1001 的历史（模拟新进程/新实例）===")
for m in SqliteHistory("user-1001").messages:
    print(f"  {m.type:7s} {m.content}")
```

本机真实输出（回复内容为本地假模型按调用顺序返回）：

```text
=== 两个用户交错提问（真实场景里是两个浏览器会话同时在线）===
user-1001: 张先生您好，已为您登记，工单号 20261015-01。
user-2002: 李女士您好，退款会在 3 个工作日到账。
user-1001: 您的订单 1001 今晚 18:00 前揽收。
user-2002: 已为您重新发起退款审核。

=== 落库结果（每个 session 独立成行）===
  user-1001: 4 条消息
  user-2002: 4 条消息

=== 直接读回 user-1001 的历史（模拟新进程/新实例）===
  human   我的订单 1001 还没发货
  ai      张先生您好，已为您登记，工单号 20261015-01。
  human   那什么时候能到
  ai      您的订单 1001 今晚 18:00 前揽收。
```

### 场景二：长会话的上下文预算管理

第二个场景处理「对话越来越长」：给上下文设一个字符（或 token）预算，超预算就把老消息摘要成一条 `SystemMessage`，只保留最近若干条原文。相比纯裁剪，摘要能保住关键事实。

```python
"""context_budget.py —— 超预算先摘要、再保留最近若干条"""
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.messages import AIMessage, BaseMessage, HumanMessage, SystemMessage, trim_messages
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate

summarize_prompt = ChatPromptTemplate.from_template(
    "把下面的客服对话压缩成不超过 80 字的事实摘要，必须保留：用户姓名、订单号、当前诉求、已承诺的动作。\n"
    "对话：\n{history}"
)
summarizer = (
    summarize_prompt
    | FakeListChatModel(responses=["张先生，订单 1001 未发货已催单，承诺今晚 18:00 前揽收；曾询问延迟赔付规则。"])
    | StrOutputParser()
)


def budget(messages: list[BaseMessage]) -> int:
    return sum(len(m.content) for m in messages)


def build_context(messages, max_chars: int = 120, keep_recent: int = 4):
    original = budget(messages)
    if original <= max_chars or len(messages) <= keep_recent:
        return messages, {"compressed": False, "before_chars": original, "after_chars": original}
    older, recent = messages[:-keep_recent], messages[-keep_recent:]
    summary = summarizer.invoke({"history": "\n".join(f"{m.type}: {m.content}" for m in older)})
    rebuilt = [SystemMessage(f"此前对话摘要：{summary}")] + recent
    return rebuilt, {
        "compressed": True, "before_chars": original, "after_chars": budget(rebuilt),
        "summarized_messages": len(older), "kept_messages": len(recent),
    }


history: list[BaseMessage] = [SystemMessage("你是客服助手，回答不超过两句。")]
turns = [
    "张先生：我的订单 1001 还没发货，什么时候能到",
    "订单 1001 预计今晚 18:00 前揽收，已为您催单",
    "张先生：如果超时有没有赔付",
    "超过承诺时效可申请 5 元无门槛券，我可以代为登记",
    "张先生：先登记吧",
    "已登记补偿申请，工单 20261015-08",
    "张先生：现在能查一下物流吗",
    "运单号 SF1234567890，当前状态：待揽收",
]
for i, text in enumerate(turns):
    history.append(HumanMessage(text) if i % 2 == 0 else AIMessage(text))

rebuilt, stats = build_context(history, max_chars=120, keep_recent=4)
print("压缩统计:", stats)
for m in rebuilt:
    print(f"  {m.type:7s} {m.content}")

# 自检：压缩后必须仍能看到关键事实（订单号与承诺时效）
assert "1001" in rebuilt[0].content and "18:00" in rebuilt[0].content, "摘要未保留关键事实"
assert stats["after_chars"] < stats["before_chars"], "压缩后长度未下降"
print("\n自检通过：摘要保留了订单号与承诺时效，且总长度下降")
```

本机真实输出：

```text
原始会话：9 条消息，共 174 字符
压缩统计: {'compressed': True, 'before_chars': 174, 'after_chars': 119, 'summarized_messages': 5, 'kept_messages': 4}

送给模型的消息：
  system  此前对话摘要：张先生，订单 1001 未发货已催单，承诺今晚 18:00 前揽收；曾询问延迟赔付规则。
  human   张先生：先登记吧
  ai      已登记补偿申请，工单 20261015-08
  human   张先生：现在能查一下物流吗
  ai      运单号 SF1234567890，当前状态：待揽收

自检通过：摘要保留了订单号与承诺时效，且总长度下降
```

## 最佳实践与踩坑记录

1. **会话键从认证信息取，不由客户端传**：`session_id` / `thread_id` 必须绑定已验证的用户身份，否则改一个 ID 就能读别人的历史，这是越权漏洞而不仅仅是 bug。
2. **新项目直接用 LangGraph checkpointer**：本机实测 `RunnableWithMessageHistory` 与 `InMemoryChatMessageHistory` 都已打印弃用警告；老项目迁移时存储层可复用，但入口换成 checkpointer。
3. **历史要有清理与压缩策略**：落库的历史会无限增长，必须配置「按时间/条数清理」或「超预算摘要」，否则数据库和上下文窗口一起爆。
4. **摘要提示词显式列出不可丢字段**：人名、订单号、金额、时间承诺这类事实必须写进摘要指令，并在测试里断言它们仍然存在（本机示例用 `assert` 做了这件事）。
5. **把摘要调用计入成本**：摘要是额外的模型调用，长会话里它的开销会累计，建议用便宜模型（本地小模型）承担。
6. **会话历史要脱敏后再落库**：对话里常含手机号、身份证、地址，落库前脱敏或加密，日志与 trace 里同理。

坑 1：`trim_messages` 传 `token_counter=len`，以为会按长度裁剪，结果一条都没裁掉。

结论：本机实测 `trim_messages(long_history, max_tokens=120, token_counter=len)` 返回全部 20 条，因为 `len` 收到的是**整个消息列表**，返回的「20」表示消息条数而不是 token 数。

原因：`token_counter` 的签名允许传入「整个消息列表 -> 整数」的可调用对象，框架按列表调用一次；`strategy="last"` 的实现也依赖这个总量判断。

解法：写成 `token_counter=lambda msgs: sum(len(m.content) for m in msgs)`（或直接用模型的 `get_num_tokens_from_messages`），并在改造后断言条数确实减少。

坑 2：`strategy="first"` 时传了 `start_on`，直接抛 `ValueError`。

结论：本机实测报错信息为 `start_on parameter is only valid with strategy='last'`。

原因：`start_on` / `end_on` 是「从哪条消息开始/结束保留」的语义，只对从尾部往前保留的 `last` 策略有意义。

解法：只用 `first` 时去掉 `start_on` / `end_on`；需要「保留最近若干轮且从人类消息开始」就用 `strategy="last"` + `start_on="human"`。

坑 3：以为假模型能验证「记忆是否生效」，结果被误导。

结论：本机 `FakeListChatModel` 只是按顺序吐出预置文本，两个会话得到不同答案完全是因为调用顺序不同（`session-b` 拿到第 3 条预置文本「支付组」），它根本看不到历史。

原因：假模型没有理解能力，不会因历史变化而改变输出。

解法：验证记忆逻辑要看**送给模型的消息列表**（`MessagesPlaceholder` 渲染结果、`len(store[...].messages)`、`prompt_value.to_messages()`），而不是看模型回答；模型回答层面的验证交给真实模型的集成测试。

坑 4：多实例部署时历史「时有时无」。

结论：用进程内的 dict 缓存存储对象（如 `_history_cache`）时，请求打到不同实例会读到不同的历史。

原因：内存缓存不跨进程；即使存储后端是数据库，缓存层的键空间也是按进程独立的。

解法：多实例部署时把存储对象做成无状态包装（每次从数据库读，或引入 Redis 等共享缓存）；或直接用 checkpointer 配共享后端，把一致性问题交给框架。
