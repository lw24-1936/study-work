## 概述

LLM 应用没法靠「看日志猜」来维护：一次回答背后有多次模型调用、检索、工具执行，任何一步的输入差异都会改变结果。可观测性解决「这次为什么这么答」，评估解决「改了 Prompt/模型/参数之后到底变好了还是变差了」。LangChain 的可观测性有两个层次：**LangChainTracer + LangSmith 平台**（托管式追踪、数据集、评估器、成本面板），以及**回调（Callback）接口**（自己实现 `BaseCallbackHandler`，本地就能拿到完整调用树，不依赖任何云服务）。评估则统一落在「数据集 + 评估器 + 报告」这三件套上，人工评估、规则评估、模型评估都只是评估器的不同实现。

```text
本篇主线：
1. 追踪渠道 —— LangSmith（环境变量 + @traceable）与本地回调（BaseCallbackHandler）
2. 调用树 —— 用回调把 chain / chat_model / tool 事件拼成树，看耗时与 token
3. 用量与成本 —— AIMessage.usage_metadata，按模型单价折算，按租户/功能聚合
4. 数据集与评估器 —— 打标集、规则评估器、忠实度（grounded）粗筛、拒答边界
5. 单元测试 —— pytest + 假模型，断言消息序列、工具 Schema、检索器条数
6. 回归与门禁 —— 版本对比、通过率门禁、延迟与成本阈值
```

本机实测环境：Ubuntu 24.04、Python 3.14.7，独立 venv `/root/.hermes/cache/scratch/lcvenv-b`，langchain 1.4.6、langchain-core 1.6.10、langsmith 0.14.8、pytest 9.1.1。**本机没有 `LANGSMITH_API_KEY` 也没有模型 API key**，所以：LangSmith 的上传能力只做到「验证失败路径」；评估流水线用假模型 + 假嵌入跑通，所有涉及质量的结论都会标明「不代表真实效果」。

## LangSmith 追踪

LangSmith 是 LangChain 官方的追踪/评估平台，接入方式极简：设三个环境变量，之后所有 LangChain/LangGraph 调用自动上报。它按 Project 组织数据，支持在 `RunnableConfig` 里挂 `tags` / `metadata` / `run_name` 来分区与检索（子 run 会继承父 run 的标签）。不想全局开启时可用 `langsmith.tracing_context()` 精确控制哪些调用被追踪，或用 `@traceable` 把非 LangChain 函数也纳入同一条 trace。

```bash
export LANGSMITH_TRACING=true                 # 开关
export LANGSMITH_API_KEY=lsv2_pt_xxx          # API key
export LANGSMITH_PROJECT=my-agent-prod        # 项目名（不设则为 default）
```

```python
import langsmith as ls
from langsmith import traceable, Client
from langchain_core.tracers.langchain import wait_for_all_tracers

@traceable(run_type="chain", name="retrieve_and_answer", tags=["prod"], metadata={"env": "prod"})
def retrieve_and_answer(question: str) -> str:
    return chain.invoke({"question": question})

# 只追踪这一段
with ls.tracing_context(enabled=True, project_name="debug-run"):
    chain.invoke({"question": "..."})

# 自定义标签/名称（会写进 trace，方便按租户、功能检索）
chain.invoke({"question": "..."}, {"run_name": "policy-qa", "tags": ["tenant:acme"], "metadata": {"user_id": "u-1"}})

wait_for_all_tracers()   # 进程退出前确保上报完成（serverless 场景必须）
```

本机真实输出（无 key 时的行为，这是排查「trace 没上去」的第一步）：

注意 `@traceable` 在没配 key 时不报错、不追踪，`get_current_run_tree()` 返回 `None`——这是最容易误判「追踪已开启」的地方。

| 目的 | 环境变量 / API | 说明 |
|---|---|---|
| 全局开关追踪 | `LANGSMITH_TRACING=true` | 缺省不开 |
| 认证 | `LANGSMITH_API_KEY=lsv2_pt_...` | 没有 key 时静默不追踪 |
| 分区 | `LANGSMITH_PROJECT` 或 `tracing_context(project_name=...)` | 按项目/环境隔离数据 |
| 打标签 | config 的 `tags` / `metadata` / `run_name` | 子 run 继承，便于按租户检索 |
| 自定义函数入图 | `@traceable(run_type=...)` | 非 LangChain 代码也能进同一条 trace |
| 保证上报 | `wait_for_all_tracers()` | 后台线程上报，进程退出前调用 |

```text
要点：
- 没配 key 时 LangChain 不会报错，只是不上报；上线前用 get_current_run_tree() 做一次自检
- tags / metadata 是检索的抓手：把 tenant_id、功能名、Prompt 版本号打进去，出问题能秒定位
- retriever / tool / model 是不同 run_type，排查时先看哪一类 run 耗时最长、报错最多
- 生产把 trace 采样率与脱敏策略一起考虑（PII 不要进 trace），这是合规前提
- Deep Agents / LangGraph Server 部署时可自动带 LangSmith 集成，自托管场景才需要手工配置
```

## 本地回调与调用树

不依赖任何云服务也能做可观测：实现 `BaseCallbackHandler`，在 `on_chain_start` / `on_chat_model_start` / `on_llm_end` / `on_tool_start` / `on_tool_end` / `on_*_error` 里收集事件，用 `run_id` / `parent_run_id` 拼出调用树。这套机制在本地开发、CI 与私有化部署里最实用：能拿到耗时、输入输出、token，也能在离线环境里做断言。

```python
import time
from langchain_core.callbacks import BaseCallbackHandler

class TraceCollector(BaseCallbackHandler):
    def __init__(self):
        self.nodes, self.roots = {}, []
        self.tokens = {"input": 0, "output": 0}
        self.errors = []

    def _new(self, run_id, parent_run_id, name, kind):
        node = {"name": name, "kind": kind, "children": [], "t0": time.perf_counter(), "ms": None}
        self.nodes[run_id] = node
        (self.nodes[parent_run_id]["children"] if parent_run_id in self.nodes else self.roots).append(node)

    def on_chain_start(self, serialized, inputs, run_id, parent_run_id=None, **kw):
        self._new(run_id, parent_run_id, (serialized or {}).get("name", "chain"), "chain")

    def on_chat_model_start(self, serialized, messages, run_id, parent_run_id=None, **kw):
        self._new(run_id, parent_run_id, f"chat_model({sum(len(m) for m in messages)} msgs)", "llm")

    def on_tool_start(self, serialized, input_str, run_id, parent_run_id=None, **kw):
        self._new(run_id, parent_run_id, (serialized or {}).get("name", "tool"), "tool")

    def on_llm_end(self, response, run_id, **kw):
        self._finish(run_id)
        u = getattr(response.generations[0][0].message, "usage_metadata", None) or {}
        self.tokens["input"] += u.get("input_tokens", 0)
        self.tokens["output"] += u.get("output_tokens", 0)

agent.invoke({"messages": [HumanMessage("查一下 ORD-1")]}, config={"callbacks": [cb], "run_name": "order-qa"})
```

本机真实输出（一次「模型 -> 工具 -> 模型」的 Agent 调用）：

```text

  - chain chain (2.958 ms)
    - llm   chat_model(1 msgs) (0.598 ms)
  - chain chain (1.864 ms)

  - chain chain (0.916 ms)
    - llm   chat_model(3 msgs) (0.227 ms)
累计 token: {'input': 285, 'output': 30} | 错误数: 0 | 事件节点数: 7
```

```text
要点：
- 回调是同步/异步双份（`on_*` 与 `on_*` 的 async 版本），Web 服务里要一起实现，否则部分事件收不到
- run_id / parent_run_id 是拼树的唯一依据，不要靠事件顺序猜层级（并行调用会打乱顺序）
- 回调里抛异常会被框架捕获并打印（见踩坑记忆），不能用来做拦截，只能用来记录
- on_llm_end 里读的是 `response.generations[0][0].message.usage_metadata`，注意可能为 None
- 本地回调适合做成中间件式的「统一埋点」，避免在每个业务函数里手写计时
```

## 数据集与评估器

评估的最小闭环是：**数据集（输入 + 期望）+ 评估器（打分函数）+ 报告（通过率/延迟/成本）**。数据集可以是 LangSmith 上的（`Client().create_dataset()` / `create_examples()`，需要 key），也可以就是仓库里的一个 JSON 文件——后者更适合 CI，评审时能直接看到样本变更。评估器必须做到「不看生成模型的内部状态」，只吃 `(输入, 期望, 输出, 上下文)`，这样才能既评规则也评模型。官方推荐的 RAG 评估维度：答案正确性（correctness）、相关性（relevance）、忠实度（groundedness）、检索质量（retrieval）。

```python
# LangSmith 托管数据集（需要 LANGSMITH_API_KEY，本机未实测上传）
from langsmith import Client, evaluate
client = Client()
ds = client.create_dataset("policy-qa-regression")
client.create_examples(
    dataset_id=ds.id,
    examples=[{"inputs": {"question": "年假多少天"}, "outputs": {"answer": "满一年 10 天"}}],
)
results = evaluate(lambda inputs: rag.invoke(inputs), data="policy-qa-regression", evaluators=[correctness_evaluator])

# 本地数据集 + 评估器（CI 里跑，无需 key）
DATASET = [{"q": "年假有几天", "expect_src": "handbook", "expect_kw": "年假", "answer": "满一年 10 天，满三年 15 天。"}]
EVALUATORS = {"retrieval_hit": ev_retrieval, "keyword_present": ev_keyword, "grounded": ev_grounded, "concise": ev_length}
```

本机真实输出（本地评估流水线，假嵌入 + 假答案，只看机制）：

这里的 60% / 40% 完全不可信——假嵌入检索本身就是错的，评估器只是忠实地报告了这件事。这正是评估的价值之一：**它连「你的检索根本没在按语义工作」都能暴露出来**。

| 评估维度 | 数据来源 | 评估器实现 |
|---|---|---|
| 检索质量 | 期望命中的来源/文档 id | 比对检索结果的 metadata |
| 答案正确性 | 参考答案 | 规则匹配、LLM-as-judge、人工标注 |
| 忠实度（grounded） | 检索到的上下文 | 检查答案里的数字/实体是否都在上下文中出现 |
| 格式合规 | JSON/字段约束 | Pydantic 解析 + 字段断言 |
| 拒答边界 | 负样本（语料里没有的问题） | 断言输出为「未提及」类兜底话术 |
| 延迟与成本 | 运行时埋点 | 统计 p50/p95 与每千次调用成本 |

```text
要点：
- 数据集是资产：放进仓库、走 code review，样本变更与 Prompt 变更一起评审
- 每个评估器只做一件事，返回 {key, score, comment}，方便聚合与定位失败样本
- 负样本（应有拒答）必须占 10%~20%，否则系统会养成「什么问题都硬答」的坏习惯
- 忠实度粗筛用「数字/实体是否出现在上下文」这类便宜规则，比每次调模型便宜几个数量级
- LLM-as-judge 好用但要固定评委模型版本与提示词，并抽样人工校准
```

## 单元测试

单元测试解决的是另一类问题：链路结构是否正确（消息序列、工具 Schema、检查点、状态字段），而不是回答质量。关键手段是用假模型（`ScriptedToolChatModel` / `FakeListChatModel`）与假嵌入把外部依赖全部消掉，让测试变成纯内存、毫秒级、可重复。这样 CI 里既不需要 API key，也不会因为模型 temperatue 波动而随机失败。

```python
# tests/test_agent.py —— 结构断言，跑在 CI 里
def test_agent_runs_tool_loop():
    agent = _agent([
        AIMessage(content="", tool_calls=[{"name": "add", "args": {"a": 2, "b": 3}, "id": "1"}]),
        AIMessage(content="结果是 5"),
    ])
    out = agent.invoke({"messages": [HumanMessage("2+3")]})
    msgs = out["messages"]
    assert len(msgs) == 4                                   # Human + AI(tool_calls) + Tool + AI
    assert isinstance(msgs[2], ToolMessage) and msgs[2].content == "5"
    assert msgs[2].tool_call_id == "1"

def test_plain_exception_in_tool_crashes_the_agent():
    with pytest.raises(ValueError, match="a 不能超过 1000"):
        _agent([...]).invoke({"messages": [HumanMessage("5000+1")]})
```

本机真实输出：

```text
- 结构断言优先：消息条数、类型、tool_call_id、状态字段、检查点数量——这些改动最容易回归
- 假模型让「模型行为」变成测试夹具，能精确构造边界（不调工具、调用工具、工具报错、超轮数）
- 检索器断言「返回 k 条」「metadata 字段齐全」，比断言具体命中哪条更稳定
- 每个失败分支都要有一条回归测试（本文把「普通异常炸穿 agent」写成了一条断言当前行为的测试）
- 测试文件与 Prompt/工具定义同目录进版本库，评审时一起看
```

## 回归与成本分析

回归 = 用同一份数据集跑新版本，和基线对比通过率、延迟、成本。成本要能在调用点记账：`AIMessage.usage_metadata` 里有 `input_tokens` / `output_tokens` / `total_tokens`（不同供应商字段名以官方为准），乘以单价就是本次成本；再用 config 的 `tags` 区分租户/功能来聚合。注意一个真实约束：**回调里抛异常不会中断调用**（本机实测），所以预算拦截不能写在回调里。

```python
PRICE = {"gpt-4o-mini": (0.15, 0.60), "gpt-4o": (2.50, 10.00)}   # 美元/百万 token，仅演示计算方式
class CostLedger(BaseCallbackHandler):
    def on_llm_end(self, response, run_id, parent_run_id=None, tags=None, **kw):
        u = getattr(response.generations[0][0].message, "usage_metadata", None) or {}
        ledger.append({"tags": tuple(tags or ()), **u})

agent.invoke(..., config={"callbacks": [CostLedger()], "tags": ["prod", "order"]})
```

本机真实输出：

```text
每条模型消息的 usage_metadata: [{'input_tokens': 120, 'output_tokens': 18, 'total_tokens': 138}, {'input_tokens': 165, 'output_tokens': 12, 'total_tokens': 177}]

v1 (size=64, k=2) 检索命中率 = 60%
```

```text
要点：
- 回归要有基线：把上一版的报告（JSON）存进仓库，新版本 diff 通过率、p95 延迟、单次成本
- 门禁指标要选可稳定的：格式合规率、拒答准确率、p95 延迟通常比「答案好不好」更稳定
- 成本按 tags 聚合到租户/功能/环境，才能回答「这个功能一个月烧多少钱」
- usage_metadata 不一定存在（流式路径、部分供应商），取不到时要有兜底估算与告警
- 预算拦截放中间件或网关前置检查，不要放回调（回调异常会被吞，本机实测）
```

## 应用场景实战

### 场景一：RAG 离线评估流水线（数据集 + 多评估器 + 门禁）

场景：每次改切分参数、嵌入模型或 Prompt 之前，先在 CI 上跑一遍离线评估，任何一个评估器低于阈值就卡住合并。

```python
"""15.9 场景一：RAG 离线评估 + 门禁"""
import re, time
from langchain_core.documents import Document
from langchain_core.embeddings import DeterministicFakeEmbedding
from langchain_core.vectorstores import InMemoryVectorStore

CORPUS = {
    "handbook": "年假：入职满一年 10 天，满三年 15 天，最多结转 5 天。报销：行程结束后 15 个自然日内提交发票。",
    "security": "密码不少于 12 位，每 90 天轮换。内部系统必须开启双因素认证。",
    "release": "灰度发布先发 5% 流量，观察 30 分钟，错误率超 0.5% 自动回滚。",
}
store = InMemoryVectorStore(embedding=DeterministicFakeEmbedding(size=64))   # 线上换成真实嵌入
store.add_documents([Document(page_content=v, metadata={"src": k}) for k, v in CORPUS.items()])
retriever = store.as_retriever(search_kwargs={"k": 2})

DATASET = [
    {"q": "年假有几天", "expect_src": "handbook", "expect_kw": "年假", "answer": "入职满一年 10 天，满三年 15 天。"},
    {"q": "报销时限", "expect_src": "handbook", "expect_kw": "报销", "answer": "行程结束后 15 个自然日内。"},
    {"q": "密码多久换", "expect_src": "security", "expect_kw": "90 天", "answer": "每 90 天轮换。"},
    {"q": "灰度比例", "expect_src": "release", "expect_kw": "5%", "answer": "先发 5% 流量。"},
    {"q": "食堂菜单", "expect_src": None, "expect_kw": None, "answer": "资料中未提及。"},   # 负样本
]

def ev_retrieval(ex, pred, hits, **kw):
    return 1.0 if ex["expect_src"] is None or ex["expect_src"] in [h.metadata["src"] for h in hits] else 0.0

def ev_keyword(ex, pred, hits, **kw):
    return 1.0 if (("未提及" in pred) if ex["expect_kw"] is None else (ex["expect_kw"] in pred)) else 0.0

def ev_grounded(ex, pred, hits, **kw):
    ctx = " ".join(h.page_content for h in hits)
    return 1.0 if not [n for n in re.findall(r"\d+", pred) if n not in ctx] else 0.0

def ev_concise(ex, pred, hits, **kw):
    return 1.0 if len(pred) <= 60 else 0.0

EVALUATORS = {"retrieval_hit": ev_retrieval, "keyword_present": ev_keyword, "grounded": ev_grounded, "concise": ev_concise}

def evaluate(version, answer_fn, threshold=0.8):
    rows = []
    for ex in DATASET:
        t0 = time.perf_counter()
        hits = retriever.invoke(ex["q"])
        pred = answer_fn(ex["q"], " ".join(h.page_content for h in hits), hits)
        rows.append({"q": ex["q"], **{n: f(ex, pred, hits) for n, f in EVALUATORS.items()}})
    pass_rate = {n: sum(r[n] for r in rows) / len(rows) for n in EVALUATORS}
    return {"version": version, "pass_rate": pass_rate, "gate": all(v >= threshold for v in pass_rate.values())}

print(evaluate("v1-raw", lambda q, ctx, hits: ctx if ctx else "资料中未提及。"))
print(evaluate("v2-truncated", lambda q, ctx, hits: ctx[:40] if ctx else "资料中未提及。"))
```

门禁是 `False`：`retrieval_hit` 与 `keyword_present` 没到 80%，流水线会拦住这次合并。这是正确行为——因为用的是假嵌入，检索根本没有语义能力。真实项目里这两项的基线应该先测出来（比如 85%/90%），再设门禁值。

### 场景二：按租户记账与预算告警（含一个反例）

场景：多租户 SaaS 需要知道每个租户烧了多少钱，并在超预算时阻断请求。这里先演示「用回调做拦截」为什么无效，再给出正确实现。

```python
"""15.9 场景二：成本记账 + 预算拦截"""
from langchain_core.callbacks import BaseCallbackHandler
from langchain_core.messages import HumanMessage
from langchain.agents import create_agent
from langchain.agents.middleware import AgentMiddleware

PRICE = {"input": 0.15 / 1e6, "output": 0.60 / 1e6}
BUDGET_USD = 0.00002


class BudgetGuard(BaseCallbackHandler):
    """反例：在回调里 raise 拦不住调用"""

    def __init__(self, tenant, budget):
        self.tenant, self.budget, self.records = tenant, budget, []

    def on_llm_end(self, response, run_id, parent_run_id=None, tags=None, **kw):
        u = getattr(response.generations[0][0].message, "usage_metadata", None) or {}
        cost = u.get("input_tokens", 0) * PRICE["input"] + u.get("output_tokens", 0) * PRICE["output"]
        self.records.append({"tenant": self.tenant, **u, "usd": cost})
        if sum(r["usd"] for r in self.records) > self.budget:
            raise RuntimeError(f"租户 {self.tenant} 超出预算 ${self.budget}")


LEDGER = {"usd": 0.0}

class BudgetBlockingMiddleware(AgentMiddleware):
    """正解：在模型调用前拦截，超预算直接拒绝"""

    def wrap_model_call(self, request, handler):
        if LEDGER["usd"] > BUDGET_USD:
            raise RuntimeError(f"预算已耗尽（已用 ${LEDGER['usd']:.6f}，上限 ${BUDGET_USD}）")
        resp = handler(request)
        LEDGER["usd"] += 0.001
        return resp


agent = create_agent(model=scripted_model(), tools=[], middleware=[BudgetBlockingMiddleware()])
for i in range(3):
    try:
        agent.invoke({"messages": [HumanMessage(f"hi {i}")]})
        print(f"  第 {i + 1} 次调用成功，累计 ${LEDGER['usd']:.6f}")
    except RuntimeError as e:
        print(f"  第 {i + 1} 次调用被拦截 -> {e}")
        break
```

本机真实输出：

```text
### 场景二：按租户记账与预算告警

Error in BudgetGuard.on_llm_end callback: RuntimeError('租户 acme 超出预算 $2e-05')
acme: 记录 1 次，累计 $0.00036000 -> 正常
Error in BudgetGuard.on_llm_end callback: RuntimeError('租户 globex 超出预算 $2e-05')
globex: 记录 1 次，累计 $0.00010800 -> 正常
Error in BudgetGuard.on_llm_end callback: RuntimeError('租户 acme 超出预算 $2e-05')
acme: 记录 1 次，累计 $0.00129000 -> 正常
按租户汇总: {'acme': 0.00165, 'globex': 0.000108}

以 callback 做预算拦截是无效的（上面每次 invoke 都成功了），正确做法是放进中间件：
  第 1 次调用成功，累计 $0.001000
  第 2 次调用被拦截 -> 预算已耗尽（已用 $0.001000，上限 $0.0002）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 可观测性从第一天就上：trace 里带 `tenant_id` / 功能名 / Prompt 版本号，出问题时能按维度切片定位，事后补埋点的成本高得多。
2. 数据集进仓库、走评审；每次线上 badcase 都回填成新样本，评估集才会越用越准。
3. 评估器分两层：便宜的规则层（格式、关键词、数字忠实度）每次提交都跑，贵的模型评委层按发布节奏跑。
4. 单元测试用假模型 + 假嵌入，让 CI 无 key、无网络、毫秒级；测试只断言结构，不断言「模型输出必须等于某句话」。
5. 成本与延迟都要设门禁（p95 延迟、单次成本），并挂到 tags 上分租户/功能看趋势。
6. 预算与配额类拦截放在中间件或网关前置检查，绝不放回调；写操作再叠一层幂等与审计。

### 踩坑记录

```text
坑 1：在回调里 raise 想拦截超预算调用，结果每次调用都成功
结论：以为拦截生效了，直到账单暴涨才发现。
原因：LangChain 会捕获回调里的异常，只打印一行 "Error in BudgetGuard.on_llm_end callback: ..."
      到日志，invoke 本身正常返回（本机实测三次调用全部成功，明细也都记上了）。
解法：拦截逻辑放中间件（本机实测 wrap_model_call 里 raise 会真的抛给调用方）或网关前置检查；
      回调只用于记账、上报、告警这类「旁路」职责。

坑 2：设了 LANGSMITH_API_KEY 却看不到 trace，@traceable 也不报错
结论：以为追踪已开启，反复检查装饰器写法。
原因：缺 LANGSMITH_TRACING=true 时不会上报；没配 key 时 @traceable 只是原样执行函数，
      get_current_run_tree() 返回 None（本机实测），全程静默。
解法：启动时做一次自检（打一条测试 trace 并检查 run tree 不为 None），把这三件套写进部署清单：
      LANGSMITH_TRACING / LANGSMITH_API_KEY / LANGSMITH_PROJECT。

坑 3：serverless 里 trace 丢了一部分
结论：以为 LangSmith 平台有问题。
原因：上报走后台线程，函数计算环境在返回响应后可能立刻回收实例，未发完的 trace 丢失。
解法：在请求收尾处调用 langchain_core.tracers.langchain.wait_for_all_tracers()，
      或改用批量/异步上报并在容器退出钩子里 flush。

坑 4：统计 token 时 KeyError: 'input_tokens'
结论：以为 usage_metadata 一定有这两个键。
原因：不同供应商字段名不同，流式路径与部分模型根本不返回 usage（本机实测：假模型的 _generate 未设置
      usage_metadata 时，服务端 /metrics 里 tokens 一直是 0，补上该字段后才变成 847）。
解法：一律用 `(getattr(msg, "usage_metadata", None) or {}).get("input_tokens", 0)` 取值，
      取不到时走本地估算（字符数/4）并打点告警，避免成本面板静默失真。

坑 5：拿假嵌入跑出来的通过率当基线，上线后发现真实效果差很多
结论：以为有 60%~80% 的检索命中率，实际上线一测完全不对。
原因：假嵌入没有语义，检索结果基本是随机排序，评估器只是如实记录（本机实测 retrieval_hit 60%、
      v2 参数一改变 80%，全是噪声）。评估基线与线上必须用同一个嵌入模型。
解法：评估环境的嵌入/模型/切分参数与线上保持一致，并在报告里记录「嵌入模型 + 维度 + 切分参数」，
      参数不一致的报告不允许作为基线。
```
