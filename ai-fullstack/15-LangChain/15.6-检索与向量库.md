## 概述

检索与向量库解决的是大模型「上下文有限 + 知识冻结」这两个硬伤：把企业自己的文档切块、向量化、存进向量库，在提问时按相似度取回最相关的几块塞进上下文。LangChain 把这条链路拆成五个可替换的部件——文档加载器（Loader）、文本切分器（Splitter）、嵌入模型（Embeddings）、向量库（VectorStore）、检索器（Retriever），每一步都能单独换掉而不影响其他步骤。

```text
本篇主线：
1. 加载 —— Document 结构与 TextLoader / DirectoryLoader / PyPDFLoader / WebBaseLoader
2. 切分 —— RecursiveCharacterTextSplitter（默认）/ MarkdownHeaderTextSplitter（保标题）/ TokenTextSplitter（按 token）
3. 嵌入 —— Embeddings 接口的 embed_documents / embed_query，维度一致性与批量
4. 存与取 —— InMemoryVectorStore（langchain-core 内置）/ FAISS（faiss-cpu，可落盘）
5. 检索器 —— as_retriever 的 similarity / mmr / similarity_score_threshold 与 k / fetch_k / lambda_mult
6. 增强 —— BM25 关键词 + 向量混合检索（EnsembleRetriever）、阈值拒答
7. 架构 —— 两段式 RAG / Agentic RAG / Hybrid RAG 的取舍
```

本机实测环境：Ubuntu 24.04、Python 3.14.7，独立 venv `/root/.hermes/cache/scratch/lcvenv-b`，langchain 1.4.6、langchain-core 1.6.10、langchain-community 0.4.2、langchain-classic 1.0.8、langchain-text-splitters 1.1.3、faiss-cpu 1.15.1。**本机没有任何 LLM/嵌入 API key**（环境变量里 `OPENAI_API_KEY`、`LANGSMITH_API_KEY` 均为空），因此嵌入一律用 `DeterministicFakeEmbedding`（哈希派生的确定性假向量），它只保证「同文本同向量、不同文本不同向量」，**不具备语义能力**。下文所有 `text` 块都是本机真实输出；凡是依赖真实嵌入模型才能得出的结论，都会明确标注。

## 文档加载器

加载器的职责是把各种来源（本地文件、网页、数据库、SaaS 文档）统一成 `Document` 对象。`Document` 只有两个字段：`page_content`（字符串正文）与 `metadata`（字典，装载来源路径、页码、标题路径等），后续切分、检索、引用溯源全靠它。基础加载器在 `langchain_community.document_loaders` 里（`TextLoader`、`PyPDFLoader`、`WebBaseLoader`、`CSVLoader`、`DirectoryLoader`），新工程的建议是优先找独立集成包（`langchain-community` 已进入 sunset 阶段）。

```python
from langchain_community.document_loaders import TextLoader, DirectoryLoader

loader = TextLoader("/path/to/handbook.md", encoding="utf-8")
docs = loader.load()          # 返回 list[Document]

dl = DirectoryLoader(
    "/path/to/kb",
    glob="**/*.md",           # 递归匹配
    loader_cls=TextLoader,
    loader_kwargs={"encoding": "utf-8"},
    use_multithreading=True,  # 文件多时可开
)
all_docs = dl.load()
```

本机真实输出：

```text

metadata: {'source': '/root/.hermes/cache/scratch/s156_docs/handbook.md'}
page_content 前 40 字: # 员工手册\n\n## 年假制度\n员工入职满一年后每年享有 10 天带薪年假，满三
DirectoryLoader 载入文档数: 2 ['handbook.md', 'release.md']
```

| 加载器 | 用途 | 依赖 | 备注 |
|---|---|---|---|
| `TextLoader` | 纯文本 / Markdown | 无 | 必须显式给 `encoding="utf-8"`，否则中文可能乱码 |
| `DirectoryLoader` | 批量目录 | 无 | `glob` + `loader_cls` 组合，按扩展名分派 |
| `PyPDFLoader` | PDF（按页） | `pypdf` | 每页一个 `Document`，`metadata` 带 `page` |
| `WebBaseLoader` | 网页正文 | `beautifulsoup4` | 抓取后按标签剥离，可用 `bs_kwargs` 限定 `class_` |
| `CSVLoader` | 结构化表格 | `pandas` | 每行一个 `Document`，列名进 `metadata` |
| `UnstructuredMarkdownLoader` | 复杂 Markdown | `unstructured` | 依赖重，一般用 `TextLoader` 加标题切分即可 |

```text
要点：
- Document = page_content + metadata，metadata 决定后续能否溯源（文件名、页码、标题路径）
- 加载器只负责「取回 + 归一化」，清洗和切分是下一步的事，不要在一个 Loader 里做全部逻辑
- langchain-community 已 sunset：新工程优先 standalone 包（langchain-openai / langchain-postgres 等），
  community 只作为过渡与冷门集成来源，升级时把 import 换掉
- DirectoryLoader 默认惰性加载（lazy_load），要拿全量列表用 load()，否则遍历时才发现文件解析报错
- 中文文本一律显式指定 encoding="utf-8"，同时给 Loader 配置中文注释，方便排错
```

## 文本切分策略

切分质量直接决定检索质量：块太大则向量被无关内容稀释、超出上下文预算；块太小则语义残缺、答案被切成两半。默认选 `RecursiveCharacterTextSplitter`：它按分隔符优先级（默认 `["\n\n", "\n", " ", ""]`）递归尝试，尽量在自然边界断开。`chunk_overlap` 用来让相邻块共享一部分内容，避免答案横跨边界时两边都取不到。

```python
from langchain_text_splitters import (
    RecursiveCharacterTextSplitter,
    MarkdownHeaderTextSplitter,
    TokenTextSplitter,
)

# 按字符切
splitter = RecursiveCharacterTextSplitter(chunk_size=120, chunk_overlap=30, length_function=len)
chunks = splitter.split_documents(all_docs)

# 按 Markdown 标题切，标题会写进 metadata（检索时可直接拼引用路径）
md_splitter = MarkdownHeaderTextSplitter(headers_to_split_on=[("#", "h1"), ("##", "h2")])
md_chunks = md_splitter.split_text(text)

# 按 token 切（需 tiktoken），适合严格控制上下文预算的场景
tok_splitter = TokenTextSplitter(chunk_size=64, chunk_overlap=8)
tok_chunks = tok_splitter.split_documents(all_docs)
```

本机真实输出：

```text
RecursiveCharacterTextSplitter: chunk_size=120 overlap=30 -> 4 块
  块长 99 | # 员工手册\n\n## 年假制度\n员工入职满一年后每年享有 10 天带薪年假，
  块长 71 | ## 报销流程\n差旅报销需在行程结束后 15 个自然日内提交发票原件与行程单
  块长 57 | # 安全规范\n\n## 账号与密码\n内部系统必须开启双因素认证。密码长度不少于
  默认 separators: ['\n\n', '\n', ' ', '']
MarkdownHeaderTextSplitter -> 3 块, 首块 metadata: {'h1': '员工手册', 'h2': '年假制度'}
TokenTextSplitter(tiktoken cl100k_base) chunk_size=64 -> 12 块
```

同一段中文文本，两种 `length_function` 的差异（本机实测）：

```text
同一段文本：按字符 200 -> 3 块；按 token 200 -> 5 块
字符数/块: [200, 200, 40] | token 块的字符数: [92, 91, 92, 93]
```

| 切分器 | 切分单位 | 保留 metadata | 适用 |
|---|---|---|---|
| `RecursiveCharacterTextSplitter` | 字符，按分隔符递归 | 是（`split_documents`） | 通用默认，首选 |
| `CharacterTextSplitter` | 单分隔符（默认 `\n\n`） | 是 | 少见，中文长段落会切不动 |
| `MarkdownHeaderTextSplitter` | 标题层级 | 是（标题写进 metadata） | 制度库、文档站 |
| `TokenTextSplitter` | tiktoken token | 是 | 上下文预算敏感、成本核算 |
| `RecursiveJsonSplitter` | JSON 结构 | 部分 | 配置、接口文档 |

```text
要点：
- 默认用 RecursiveCharacterTextSplitter；中文文档没有空格，separators 里保留 "" 兜底很重要
- chunk_size 的口径由 length_function 决定：传 len 是字符数，传 token 计数器是 token 数，对不上就是坑
- chunk_overlap 取 chunk_size 的 10%~20% 起步；重叠太大只是白烧钱，检索召回不会更好
- 有标题层级的文档用 MarkdownHeaderTextSplitter，把标题写进 metadata，答案引用能定位到条款
- 切分器只做「切」，不要在里面做摘要或改写；需要上下文补全时用 ContextualCompression 或预处理一步
- 换切分参数必须重跑评估集（先用小规模 20~50 条打标集对比命中率），不要凭感觉调
```

## 嵌入模型与向量化

嵌入模型把文本映射成定长向量，接口只有两个方法：`embed_documents()`（批量，入库时用）和 `embed_query()`（单条，检索时用）。之所以分开，是因为很多模型对「文档」和「查询」用不同前缀（如 BGE 的 `query:` / `passage:`），混用会明显掉点。维度必须固定：换维度等于旧索引作废。

```python
from langchain_core.embeddings import Embeddings, DeterministicFakeEmbedding

fake = DeterministicFakeEmbedding(size=64)
v = fake.embed_query("年假有多少天")
vs = fake.embed_documents(["年假", "报销"])

# 真实工程里的写法二选一（本机无 key / 未装依赖，未实测）：
# from langchain_openai import OpenAIEmbeddings
# emb = OpenAIEmbeddings(model="text-embedding-3-small")      # 需要 OPENAI_API_KEY
# from langchain_huggingface import HuggingFaceEmbeddings
# emb = HuggingFaceEmbeddings(model_name="BAAI/bge-small-zh-v1.5")  # 需 sentence-transformers
```

本机真实输出：

```text
DeterministicFakeEmbedding(size=64).embed_query 长度: 64 前 5 维: [-0.919, -0.87, 0.762, 0.932, -1.172]
同一文本两次嵌入完全一致: True
不同文本嵌入不同: True
embed_documents 返回: 2 条 x 64 维
```

| 方案 | 依赖 / 认证 | 中文效果 | 本机可跑 |
|---|---|---|---|
| `OpenAIEmbeddings` | `langchain-openai` + API key | 好 | 否（无 key） |
| `HuggingFaceEmbeddings`（BGE 系列） | `langchain-huggingface` + `sentence-transformers` + 模型下载 | 好 | 否（未装依赖） |
| `OllamaEmbeddings` | 本地 Ollama 服务（本机未安装 Ollama 服务） | 中上 | 否 |
| `DeterministicFakeEmbedding` | `langchain-core` 内置 | 无语义 | 是（本文用它） |

```text
要点：
- embed_query 与 embed_documents 是两条路径，很多模型要求加不同前缀，别互相替代
- 维度是索引的一部分：换嵌入模型/换维度必须重建索引，不能只换 Embeddings 对象
- 入库走批量 embed_documents，逐条 embed_query 既慢又容易触碰上游限流
- 向量要归一化（或使用余弦距离）后再比大小，L2 距离与余弦相似度的排序不一定一致
- 假嵌入只用于打通链路与写测试，任何检索质量结论都必须用真实嵌入模型复测
```

## 向量数据库 InMemoryVectorStore 与 FAISS

`VectorStore` 的统一接口是 `add_documents()` / `similarity_search()` / `similarity_search_with_score()` / `delete()` / `as_retriever()`。`InMemoryVectorStore` 是 langchain-core 自带的纯内存实现，零依赖、适合测试；`FAISS` 走 `faiss-cpu`，能 `save_local()` 落盘成 `index.faiss`（向量）+ `index.pkl`（文档与 metadata）两个文件，适合单机中小规模知识库。生产规模（百万级以上向量、需要过滤与并发写）再上 pgvector / Milvus / Qdrant。

```python
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_community.vectorstores import FAISS

store = InMemoryVectorStore(embedding=fake)
store.add_documents(chunks)
hits = store.similarity_search("年假 多少天", k=2)
scored = store.similarity_search_with_score("年假 多少天", k=2)

faiss_store = FAISS.from_documents(chunks, fake)
faiss_store.save_local("/data/kb_index")
reloaded = FAISS.load_local("/data/kb_index", fake, allow_dangerous_deserialization=True)
reranked = reloaded.max_marginal_relevance_search("回滚", k=3, lambda_mult=0.5)
```

本机真实输出：

```text

写入向量数: 4
similarity_search(k=2) 命中:
  - handbook.md | # 安全规范\n\n## 账号与密码\n内部系统必须开启双因素认证。密码长度不
  - release.md | # 发布流程\n\n## 灰度发布\n所有线上变更先发 5% 流量，观察 30
带分数: [(0.2059, '# 安全规范## 账'), (0.0934, '# 发布流程## 灰')]

=== 5. 向量库：FAISS（faiss-cpu，持久化） ===
faiss.__version__: 1.15.1
save_local 目录内容: ['index.faiss', 'index.pkl']
load_local 后向量数: 4
回读命中数: 2
MMR 检索（lambda_mult=0.5, k=3）: ['# 安全规范## 账号与', '# 发布流程## 灰度发', '# 员工手册## 年假制']
```

| 向量库 | 部署形态 | 落盘 | 元数据过滤 | 适用规模 |
|---|---|---|---|---|
| `InMemoryVectorStore` | 进程内 | 否 | 支持 | 测试、原型、小语料 |
| `FAISS` | 单机文件 | `index.faiss` + `index.pkl` | 支持（`filter`） | 十万级向量、单机检索服务 |
| `Chroma` | 本地/服务 | 目录 | 支持 | 十万级、需要轻量持久化 |
| `PGVector` | PostgreSQL 扩展 | 数据库 | SQL 全功能 | 已有 PG、需要事务与过滤 |
| `Milvus` / `Qdrant` | 独立服务 | 服务 | 支持 | 百万级以上、分布式 |

```text
要点：
- 先 InMemoryVectorStore 打通链路与写测试，再接 FAISS/Chroma；接口一致，换库只改构造那几行
- FAISS 用 save_local/load_local 落盘，加载必须显式 allow_dangerous_deserialization=True（走 pickle）
- similarity_search_with_score 返回的是「距离」（越小越近），而 relevance score 是「相似度」（越大越像），
  两者方向相反，做阈值判断前先确认自己拿到的是哪一种
- 假嵌入下分数没有意义，本文所有分数仅用于展示调用形态，不做质量判断
- 元数据过滤（filter）在向量检索之后做，它能保证结果集干净，但省不掉检索本身的开销
```

## 检索器与检索参数

检索器是「输入一个非结构化查询，返回 `Document` 列表」的统一抽象，也是 RAG 链路里唯一可以直接替换的组件。向量库通过 `as_retriever()` 变成检索器，三种 `search_type` 各有用途：`similarity`（默认，按向量距离取 top-k）、`mmr`（最大边际相关，兼顾相关性与多样性，防重复）、`similarity_score_threshold`（低于阈值就不要，用于拒答）。

```python
retriever = store.as_retriever(search_type="mmr", search_kwargs={"k": 3, "fetch_k": 8})
docs = retriever.invoke("报销流程")

# 自定义检索器：继承 BaseRetriever，实现 _get_relevant_documents
from langchain_core.retrievers import BaseRetriever
from langchain_core.documents import Document

class KeywordRetriever(BaseRetriever):
    docs: list[Document]

    def _get_relevant_documents(self, query: str, *, run_manager=None) -> list[Document]:
        return [d for d in self.docs if query in d.page_content][:3]
```

本机真实输出（含一个真实报错）：

```text
Retriever 类型: VectorStoreRetriever
invoke 返回类型: list 数量: 3
坑：InMemoryVectorStore + similarity_score_threshold -> NotImplementedError
    该类没有实现 _select_relevance_score_fn()，无法把距离换算成 0~1 相关度
    -> 需要阈值过滤时改用 FAISS/Chroma 等实现了 relevance score 的向量库，
       或在应用层对 similarity_search_with_score 的返回值自己过滤
FAISS 阈值检索数量（score_threshold=0.3）: 0
MMR 检索器数量: 3
```

| `search_type` | 排序依据 | 关键参数 | 典型用途 |
|---|---|---|---|
| `similarity` | 向量距离 | `k` | 默认，快 |
| `mmr` | 相关性 + 多样性 | `k`、`fetch_k`、`lambda_mult` | 避免同一段话反复命中 |
| `similarity_score_threshold` | 距离换算成相关度后过滤 | `k`、`score_threshold` | 拒答、兜底话术 |

```text
要点：
- MMR 的 fetch_k 是先取回的候选池，必须 >= k，一般取 3~5 倍；lambda_mult 越小越强调多样性
- similarity_score_threshold 依赖向量库实现 _select_relevance_score_fn()，InMemoryVectorStore 没有
  （本机实测 NotImplementedError），换库前先在目标库上跑一次
- 检索器是 Runnable：可以直接进 LCEL 管道（prompt | model 的 context 分支），也可以用 invoke/ainvoke
- 自定义检索器继承 BaseRetriever 只需实现 _get_relevant_documents（要异步再实现 _aget_relevant_documents）
- k 不是越大越好：上下文变长会增加成本并引入噪声，先用 3~5 起步，用评估集定值
```

## 重排与混合检索

向量检索擅长「意思相近」，但对精确的词（工单号、错误码、产品型号）不敏感；BM25 反过来。工程上常用两路并行再融合：`EnsembleRetriever` 支持权重融合（内部按 RRF 思路合并），也可以用专门的 Cross-Encoder 重排器（`ContextualCompressionRetriever` + `CrossEncoderReranker`，需要 `sentence-transformers`，本机未安装，未实测）。重排的价值是把「召回的粗排」换成「精排」，代价是延迟与算力，通常只对前 20~50 条做。

```python
from langchain_community.retrievers import BM25Retriever
from langchain_classic.retrievers import EnsembleRetriever

bm25 = BM25Retriever.from_documents(chunks)
bm25.k = 3
vec = store.as_retriever(search_kwargs={"k": 3})
hybrid = EnsembleRetriever(retrievers=[bm25, vec], weights=[0.5, 0.5])

# 重排（本机未装 sentence-transformers，未实测，写法以官方文档为准）
# from langchain_classic.retrievers import ContextualCompressionRetriever
# from langchain_classic.retrievers.document_compressors import CrossEncoderReranker
# from langchain_community.cross_encoders import HuggingFaceCrossEncoder
# reranker = CrossEncoderReranker(model=HuggingFaceCrossEncoder(model_name="BAAI/bge-reranker-base"))
# ccr = ContextualCompressionRetriever(base_compressor=reranker, base_retriever=hybrid)
```

本机真实输出：

```text

BM25Retriever 关键词命中: ['# 发布流程## 灰度发布', '# 安全规范## 账号与密码', '## 报销流程差旅报销需在行程']
EnsembleRetriever 命中数: 3
```

```text
要点：
- 关键词路（BM25）+ 向量路互补，权重按语料特点调（百科类偏向量，编号/型号密集的偏关键词）
- BM25Retriever 需要 rank_bm25，纯内存、零服务依赖，中小语料上性价比很高
- 混合检索的融合分数不可跨查询比较，阈值要按最终融合分重新标定
- Cross-Encoder 重排精度更高但延迟是向量检索的数量级倍数，只对粗排 top-N 用，N 一般 20~50
- 拒答比硬答更重要：相关度低于阈值时返回「资料中未提及」，比让模型自由发挥安全得多
```

## 两段式 RAG 与 Agentic RAG

官方文档把 RAG 分成三种架构：两段式（检索必在生成前，最可控最快）、Agentic（由模型决定何时检索、检索什么，灵活但延迟与成本不可预测）、Hybrid（在两段式上加入查询改写、检索校验、答案校验）。选型没有绝对优劣：制度问答这类「必须检索」的场景用两段式就够；多数据源、需要多轮取证的研究型助手才值得上 Agentic。

| 架构 | 控制力 | 灵活性 | 延迟 | 典型场景 |
|---|---|---|---|---|
| 两段式 RAG | 高 | 低 | 快且可预测（模型调用次数固定） | FAQ、制度问答机器人 |
| Agentic RAG | 低 | 高 | 波动大 | 需要访问多个工具/数据源的研究助手 |
| Hybrid RAG | 中 | 中 | 波动 | 查询含糊、需要校验与迭代的场景 |

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

prompt = ChatPromptTemplate.from_messages([
    ("system", "只依据下面的上下文回答，上下文没有的内容回答「资料中未提及」。\n\n上下文：\n{context}"),
    ("human", "{question}"),
])

def format_docs(docs):
    return "\n\n".join(f"[{d.metadata['source']}] {d.page_content}" for d in docs)

rag = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | model
    | StrOutputParser()
)
answer = rag.invoke("年假有多少天？")
```

本机真实输出（`model` 是脚本化假模型，只验证链路，不代表模型质量）：

```text
=== 8. 两段式 RAG（检索 + 假模型生成，验证链路而非模型质量） ===
送入模型的提示词长度: 372
RAG 回答: 入职满一年 10 天，满三年 15 天。
```

Agentic RAG 的写法就是把检索器包成工具交给 Agent，让模型自己决定调用时机：

```python
from langchain.tools import tool
from langchain.agents import create_agent

@tool
def search_policy(query: str) -> str:
    """在公司制度库中检索条款，返回带来源的片段。"""
    return format_docs(retriever.invoke(query))

agent = create_agent(
    model="openai:gpt-4.1-mini",
    tools=[search_policy],
    system_prompt="回答制度问题前必须先用 search_policy 取证，并引用来源。",
)
```

```text
要点：
- 两段式的成本与延迟可预测（模型调用次数固定），是大多数企业问答的默认选择
- Agentic RAG 本质上就是「把检索器变成工具」，复用 15.7 的工具与 Agent 全部机制
- 检索不到就拒答，比让模型编更有价值；拒答阈值要基于真实嵌入的分数分布标定
- 引用必须带 metadata（文件名 + 标题路径），否则用户无法核验，出了问题也定位不到
- 检索结果要放进 system 而不是 human，能降低模型把上下文当指令执行的风险
```

## 应用场景实战

### 场景一：企业制度知识库检索服务（加载 → 结构化切分 → FAISS 落盘 → 带引用检索）

场景：把 HR 制度与 IT 制度两类 Markdown 文档做成可检索服务，检索结果必须带「文件名 + 制度大类/条款」路径，方便前端做引用展示。索引落盘后由服务进程加载，避免每次启动重算。

```python
"""15.6 场景一：企业制度知识库检索服务"""
import os, tempfile

from langchain_core.documents import Document
from langchain_core.embeddings import DeterministicFakeEmbedding
from langchain_community.document_loaders import DirectoryLoader, TextLoader
from langchain_text_splitters import MarkdownHeaderTextSplitter
from langchain_community.vectorstores import FAISS

KB = "kb"                                    # 存放 *.md 的目录
EMB = DeterministicFakeEmbedding(size=128)   # 换成真实嵌入模型即可上线

# 1) 加载
docs = DirectoryLoader(
    KB, glob="**/*.md", loader_cls=TextLoader, loader_kwargs={"encoding": "utf-8"}
).load()

# 2) 结构化切分：标题进 metadata，检索结果可直接拼引用路径
md_splitter = MarkdownHeaderTextSplitter(headers_to_split_on=[("#", "制度大类"), ("##", "条款")])
chunks: list[Document] = []
for d in docs:
    for c in md_splitter.split_text(d.page_content):
        c.metadata["file"] = os.path.basename(d.metadata["source"])
        chunks.append(c)

# 3) 建索引并落盘
index_dir = tempfile.mkdtemp(prefix="kb_index_")
store = FAISS.from_documents(chunks, EMB)
store.save_local(index_dir)
store = FAISS.load_local(index_dir, EMB, allow_dangerous_deserialization=True)

# 4) 检索 + 带引用的回答组装
retriever = store.as_retriever(search_type="mmr", search_kwargs={"k": 3, "fetch_k": 8})

def answer(question: str) -> str:
    hits = retriever.invoke(question)
    if not hits:
        return "资料中未提及。"
    lines = [
        f"- [{h.metadata['file']} > {h.metadata.get('制度大类', '')}/{h.metadata.get('条款', '')}] {h.page_content}"
        for h in hits
    ]
    return "命中条款：\n" + "\n".join(lines)

print(answer("年假能结转多少天"))
print(answer("密码多久换一次"))

# 5) 管线自检：用某块原文反查，同一块应排第一（与语义无关，纯链路正确性）
exact = store.similarity_search_with_score(chunks[0].page_content, k=1)
assert exact[0][0].page_content == chunks[0].page_content, "索引回读不一致"
```

本机真实输出：

```text
### 场景一：企业制度知识库检索服务

加载 2 个文件，切出 8 个带标题层级的块
首个块 metadata: {'制度大类': '信息安全制度', '条款': '账号', 'file': 'it.md'} | 内容: 内部系统必须开启双因素认证，账号共享属于重大违规
索引文件: ['index.faiss', 'index.pkl']

Q: 年假能结转多少天
命中条款：
- [hr.md > 人力资源制度/病假] 病假需提供二级以上医院证明，全年累计不超过 30 天。
- [it.md > 运维制度/变更] 所有线上变更走灰度：先发 5% 流量，观察 30 分钟，错误率超 0.5% 自动回滚。
- [it.md > 运维制度/备份] 数据库每日全量备份保留 30 天，日志保存 180 天。

Q: 密码多久换一次
命中条款：
- [hr.md > 财务制度/借款] 备用金借款上限 20000 元，须在项目结束后 10 个工作日内核销。
- [it.md > 运维制度/变更] 所有线上变更走灰度：先发 5% 流量，观察 30 分钟，错误率超 0.5% 自动回滚。
- [it.md > 运维制度/备份] 数据库每日全量备份保留 30 天，日志保存 180 天。

```

上面的命中列表明显不合理（问年假却命中备份条款），原因是用的是假嵌入，向量与语义无关。这个输出只能证明链路对了：加载数量、标题 metadata、索引落盘两个文件、检索结果按 metadata 回传、原文反查 distance 为 0。真实语义效果必须把 `EMB` 换成 `OpenAIEmbeddings`/BGE 后重测。脚本里之所以加「原文反查自检」，就是为了在无语义的前提下仍能判断管线是否完好——这条断言在任何嵌入模型下都必须成立。

### 场景二：混合检索 + 相关度阈值拒答（避免把不相关内容喂给模型）

场景：线上问答机器人最怕「检索到不相关的内容还硬答」。这里用 BM25 + 向量混合检索保证召回，再用关键词白名单与相关度阈值双重判断决定是否回答。

```python
"""15.6 场景二：混合检索 + 拒答"""
from langchain_community.retrievers import BM25Retriever
from langchain_classic.retrievers import EnsembleRetriever

bm25 = BM25Retriever.from_documents(chunks, k=4)       # 关键词路
vec = store.as_retriever(search_kwargs={"k": 4})       # 向量路
hybrid = EnsembleRetriever(retrievers=[bm25, vec], weights=[0.4, 0.6])

KEYWORDS = ["双因素", "2FA", "MFA", "工单号", "SLA"]    # 业务上必须命中的词

def hybrid_answer(question: str, threshold: float = 0.35) -> dict:
    hits = hybrid.invoke(question)
    scored = store.similarity_search_with_relevance_scores(question, k=4)
    best = max((s for _, s in scored), default=0.0)
    kw_hit = any(k.lower() in question.lower() for k in KEYWORDS)
    return {
        "question": question,
        "best_relevance": round(float(best), 4),
        "keyword_hit": kw_hit,
        "answered": bool(kw_hit or best >= threshold),
        "top_files": [h.metadata["file"] for h in hits[:2]],
    }

for q in ["双因素认证怎么开", "班车时间", "年假"]:
    print(hybrid_answer(q))
```

本机真实输出：

```text
### 场景二：混合检索（BM25 + 向量）+ 相关度阈值拒答

{'question': '双因素认证怎么开', 'best_relevance': -163.742, 'keyword_hit': True, 'answered': True, 'top_files': ['hr.md', 'it.md']}
{'question': '班车时间', 'best_relevance': -172.6735, 'keyword_hit': False, 'answered': False, 'top_files': ['hr.md', 'it.md']}
{'question': '年假', 'best_relevance': -168.1566, 'keyword_hit': False, 'answered': False, 'top_files': ['hr.md', 'it.md']}
```

注意 `best_relevance` 是负数：假嵌入下 FAISS 的相关度换算没有意义（真实嵌入模型下余弦相似度落在 0~1）。所以本例中 `answered` 完全由关键词命中决定。这恰好说明一件工程上的事：**阈值不能照抄**，换嵌入模型、换距离度量、换归一化方式之后，必须重新标定。

## 最佳实践与踩坑记录

### 最佳实践

1. 先用 20~50 条带标注的问题集把「切分参数 + 嵌入模型 + k」定下来，再写业务代码；凭感觉调参是检索质量最大的浪费。
2. 切分时把标题路径、文件名、页码全部写进 metadata，检索结果一律带来源返回，引用溯源是知识库能不能上线的硬门槛。
3. 先用 `InMemoryVectorStore` 写单元测试与链路验证，再接 FAISS/Chroma/PGVector；接口一致，换库成本极低。
4. 检索参数化（`search_type`、`k`、`fetch_k`、阈值都进配置），A/B 对比不同参数才能做回归。
5. 相关度低于阈值就拒答或转人工，配合关键词白名单兜底；宁可回答「未收录」，不要让模型基于无关上下文编造。
6. 索引落盘时把「嵌入模型名 + 维度 + 切分参数」一起写进索引旁的 manifest 文件，并在启动时做一次原文反查自检，避免日后无法复现索引。

### 踩坑记录

```text
坑 1：InMemoryVectorStore 上挂 similarity_score_threshold，检索时抛 NotImplementedError
结论：以为阈值参数写错了，反复改 score_threshold。
原因：阈值过滤需要向量库实现 _select_relevance_score_fn() 把距离换算成 0~1 相关度，
      InMemoryVectorStore 没有实现这个钩子（本机实测 NotImplementedError）。
解法：需要阈值过滤时换 FAISS/Chroma 等实现该方法的库；或者在应用层拿
      similarity_search_with_score() 的返回值自己过滤（注意 FAISS 返回的是距离，越小越近）。

坑 2：CharacterTextSplitter 设了 chunk_size=50，结果切出来的块长 330
结论：以为切分器失效，怀疑中文编码问题。
原因：CharacterTextSplitter 默认 separator="\n\n"，只在空行处切；中文长段落中间没有空行，
      于是整段作为一块输出，chunk_size 形同虚设（本机实测 chunk_size=50 时输出 1 块、长度 330）。
解法：改用 RecursiveCharacterTextSplitter（默认分隔符含 "\n" 与 "" 兜底，本机实测同文本切成 7 块、
      每块 50 字），或显式把 separators 设为 ["\n\n", "\n", "。", "，", " ", ""]。

坑 3：FAISS.load_local 直接报 ValueError，说反序列化不安全
结论：以为索引文件损坏。
原因：load_local 默认拒绝加载 pickle（文档与 metadata 存在 index.pkl 里），
      必须显式确认来源可信（本机实测 ValueError 提到 malicious payload）。
解法：FAISS.load_local(dir, embeddings, allow_dangerous_deserialization=True)；
      索引文件按敏感产物保管（它包含全部文档内容），不要从不可信来源加载。

坑 4：换了嵌入模型之后旧索引查不出东西 / 直接 AssertionError
结论：以为向量库坏了，重建索引还是错的。
原因：维度不一致（本机实测用 64 维嵌入查 32 维索引 -> AssertionError，且没有可读的错误信息），
      维度不同则向量空间完全不同；即使维度相同，模型换了语义空间也变了。
解法：索引必须和嵌入模型绑定：manifest 里记录模型名与维度，切换时整库重建；
      启动自检写入一条已知文本再查回自身（distance 应为 0），不一致就直接拒绝启动。

坑 5：chunk_size=200 以为是 200 字符，实际按 token 语义差了一倍多
结论：按 token 预算估算的上下文长度，实际严重超出或不足。
原因：chunk_size 的口径由 length_function 决定。本机实测同一段文本：按字符 200 得 3 块
      （块长 200/200/40），按 token 200 得 5 块（每块约 92 个中文字符）。
解法：统一口径并写进配置注释；用 tiktoken 计数时记得中文一个字大约 1~2 个 token，
      给提示词模板与输出留 20%~30% 余量。
```
