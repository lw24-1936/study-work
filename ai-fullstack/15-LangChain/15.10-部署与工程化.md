## 概述

把 LangChain/LangGraph 应用从脚本变成服务，要解决的都是「非功能性」问题：接口怎么定义（同步/流式/会话）、超时与限流怎么设、缓存怎么用才安全、健康怎么探、日志与指标怎么上报。LangGraph 应用本质上是一张可编译、可持久化的图，所以服务化只有两条路：**自己用 FastAPI 之类托管**（控制力最强，本文主线），或者**交给 LangGraph Server**（`langgraph.json` + `langgraph dev/build` 的标准运行时，托管部署由 LangSmith 平台提供）。两条路的工程关注点一致，区别只在「谁来管检查点、队列与并发」。

```text
本篇主线：
1. 服务化 —— FastAPI + Pydantic 请求模型 + lifespan 启动自检 + 配置走环境变量
2. 流式 —— SSE（text/event-stream）推 token 与节点事件，首 token 延迟是关键指标
3. 会话 —— thread_id 贯穿请求与检查点；会话数据与业务数据分离
4. 缓存 —— InMemoryCache 进程内、SQLiteCache 落盘、键的组成与失效风险
5. 并发与限流 —— asyncio.Semaphore 控制模型并发、InMemoryRateLimiter / 令牌桶控制 QPS
6. 可靠性 —— with_retry 重试、超时、熔断；写操作不重试
7. 可观测 —— /healthz /readyz /metrics、访问日志、按会话排查状态
8. 清单 —— 上线前逐项确认（配置、密钥、限流、超时、成本、回滚）
```

本机实测环境：Ubuntu 24.04、Python 3.14.7，独立 venv `/root/.hermes/cache/scratch/lcvenv-b`，langchain 1.4.6、langgraph 1.2.15、fastapi 0.143.1、uvicorn 0.54.0、httpx 0.28.1、pydantic-settings 2.16.0。**本机没有模型 API key**，服务里的模型换成 token 级流式的假模型；`text` 块全部是本机真实输出——服务是真的用 `uvicorn` 起过、真的用 `httpx` 发过 HTTP 与 SSE 请求、真的做过 8 路并发。

## 服务化部署

服务化的最小骨架是「一个 FastAPI 应用 + 一个编译好的图 + 一份配置」。三个原则：配置全部走环境变量（用 `pydantic-settings` 在启动时校验，缺配置直接起不来）；图与检查点在 `lifespan` 里初始化，启动即自检；对外接口只用 Pydantic 模型收参，把校验交给框架，业务代码不写 `if not message`。

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    model_name: str = "fake-chat"
    max_concurrency: int = 4
    request_timeout_s: float = 30.0
    max_input_chars: int = 4000
    class Config:
        env_prefix = "APP_"          # APP_MAX_CONCURRENCY=8 覆盖

SETTINGS = Settings()

class ChatRequest(BaseModel):
    message: str = Field(min_length=1, description="用户输入")
    thread_id: str = Field(default="default", description="会话 ID，用于复用检查点")

class ChatResponse(BaseModel):
    answer: str
    thread_id: str
    elapsed_ms: float

CHECKPOINTER = InMemorySaver()          # 生产换 PostgresSaver / SqliteSaver
AGENT = create_agent(model=..., tools=[...], system_prompt="...", checkpointer=CHECKPOINTER)

@asynccontextmanager
async def lifespan(app: FastAPI):
    print(f"[startup] model={SETTINGS.model_name} max_concurrency={SETTINGS.max_concurrency}")
    yield
    print("[shutdown] bye")

app = FastAPI(title="Enterprise Policy Assistant", version="1.0.0", lifespan=lifespan)

@app.post("/chat", response_model=ChatResponse)
async def chat(req: ChatRequest):
    if len(req.message) > SETTINGS.max_input_chars:
        raise HTTPException(status_code=413, detail="输入过长")     # 业务上限用 413
    cfg = {"configurable": {"thread_id": req.thread_id}}
    async with SEM:                                                # 控制模型并发
        out = await asyncio.wait_for(AGENT.ainvoke({"messages": [HumanMessage(req.message)]}, cfg),
                                     SETTINGS.request_timeout_s)
    return ChatResponse(answer=out["messages"][-1].content, thread_id=req.thread_id, elapsed_ms=0.0)
```

本机真实输出（uvicorn 启动 + httpx 请求）：

```text
=== 1. 探针 ===
GET /healthz -> {'status': 'ok', 'settings': {'model_name': 'fake-chat', 'max_concurrency': 4, 'request_timeout_s': 30.0, 'max_input_chars': 4000}}
GET /readyz  -> {'status': 'ready', 'nodes': ['__end__', '__start__', 'model', 'tools']}

=== 2. 非流式接口 + 会话复用 ===
POST /chat #1 -> 200 {"answer": "已收到你的问题，我按制度说明：年假满一年 10 天，满三年 15 天。", "thread_id": "t-9", "elapsed_ms": 6.544618867337704} x-elapsed-ms=8.2
POST /chat #2 -> 200 {"answer": "已收到你的问题，我按制度说明：年假满一年 10 天，满三年 15 天。", "thread_id": "t-9", "elapsed_ms": 2.37151887267828} x-elapsed-ms=2.9
GET /debug/thread/t-9 -> {'thread_id': 't-9', 'messages': 4, 'checkpoints': 6}

=== 3. 参数校验与输入上限 ===
空 message -> 422 {"detail":[{"type":"string_too_short","loc":["body","message"],"msg":"String should have at least 1 character","input":"","ctx":{"min_length":1}}]}
超长 message -> 413 {"detail":"输入过长"}
```

| 关注点 | 做法 | 说明 |
|---|---|---|
| 配置 | `pydantic-settings` + `env_prefix` | 启动时校验，缺项即失败，不留运行期惊喜 |
| 会话 | `thread_id` 透传进 config | 与检查点绑定，前端会话 ID 直接映射 |
| 超时 | `asyncio.wait_for` + 客户端 `timeout=` | 图本身没有墙钟超时，必须外层兜 |
| 错误码 | 校验失败 422、超限 413、上游超时 504、内部错误 500 | 让前端能区分「改输入」还是「重试」 |
| 启动自检 | `lifespan` 里断言图结构/检查点可用 | 起不来比带病运行好 |
| 会话排查 | `/debug/thread/{id}` 读 `get_state` | 线上排查「这轮为什么这么答」 |

```text
要点：
- 全部配置走环境变量（容器里注入），代码里只留安全默认值；密钥走密钥管理，不进镜像
- 图与检查点是进程级单例，在模块加载或 lifespan 里建好，别每个请求重建（重建=丢历史+慢）
- 每个请求都要有超时与并发上限，否则一次上游抖动会把整个进程的连接池占满
- InMemorySaver 只适合单副本演示；多副本必须用 PostgresSaver（共享存储），否则会话在不同副本间丢失
- 会话状态不等于业务数据：订单、工单该落业务库；检查点只负责「对话现场」
```

## 流式接口

流式是 Agent 体验的分水岭：用户先看到第一个 token，感知延迟从「十几秒」变成「一秒内」。技术上是 `astream(stream_mode=[...])` 把图的事件转成 SSE（`text/event-stream`）帧推给客户端。常见事件设计：`start`（回显 thread_id）、`token`（增量文本）、`node`（节点完成/工具调用）、`error`、`done`（含耗时）。做流式必须处理三件事：首 token 延迟、断开感知（客户端断开要停止生成，别继续烧 token）、以及反向代理缓冲。

```python
from fastapi.responses import StreamingResponse

def sse(event: str, data) -> str:
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"

@app.post("/chat/stream")
async def chat_stream(req: ChatRequest):
    async def gen():
        cfg = {"configurable": {"thread_id": req.thread_id}}
        yield sse("start", {"thread_id": req.thread_id})
        async with SEM:
            async for mode, payload in AGENT.astream(
                {"messages": [HumanMessage(req.message)]}, cfg, stream_mode=["messages", "updates"]
            ):
                if mode == "messages":
                    token, meta = payload
                    if token.content:
                        yield sse("token", {"text": token.content, "node": meta.get("langgraph_node")})
                elif mode == "updates":
                    for node, upd in payload.items():          # 节点完成事件（工具调用在这里可观测）
                        yield sse("node", {"node": node})
        yield sse("done", {"elapsed_ms": 0.0})

    return StreamingResponse(gen(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

本机真实输出（客户端逐行读取 SSE）：

```text
=== 4. SSE 流式接口（逐 token） ===
响应头 content-type: text/event-stream; charset=utf-8
  [start] {"thread_id": "s-1"}
  [node] {"node": "model", "type": "AIMessage", "content": "已收到你的问题，我按制度说明：年假满一年 10 天，满三年 15 天。"}
  [done] {"elapsed_ms": 723.2}
事件序列: ['start', 'token', 'token', ..., 'token', 'node', 'done']
token 数: 35
首 token 延迟: 31 ms，整体 732 ms
拼接结果: 已收到你的问题，我按制度说明：年假满一年 10 天，满三年 15 天。
```

```text
要点：
- 首 token 延迟（TTFT）比总耗时更能反映体验，必须单独埋点：它是网关超时与用户耐心之间的真正边界
- SSE 帧结构是 `event:` + `data:` + 空行，代理与客户端都依赖这个格式，别自己发明
- 反向代理（Nginx 等）可能缓冲响应导致「流式变一次性」，需要显式关闭缓冲（如 X-Accel-Buffering: no），具体配置以所用代理文档为准
- 客户端断开要能停止生成：FastAPI 的生成器被取消时应让上游调用一并终止，否则白烧 token
- token 级流式与「工具调用事件」是两类事件，前端要分别渲染（前者打字机，后者进度提示）
```

## 缓存

缓存能显著降低成本与延迟，但 LLM 场景的缓存有三个陷阱：**键的组成**（同样的提示词但模型/参数不同不能复用）、**数据泄漏**（把带个人上下文的回答缓存给另一个用户）、**失效**（Prompt 一改，旧缓存全变噪声）。LangChain 提供全局 LLM 缓存：`set_llm_cache(InMemoryCache())` 进程内、`SQLiteCache` 落盘可跨重启；缓存键由提示词与模型标识组成，所以「同一句话」命中，改一个字就 miss。

```python
from langchain_core.globals import set_llm_cache
from langchain_core.caches import InMemoryCache
from langchain_community.cache import SQLiteCache

set_llm_cache(InMemoryCache())                       # 进程内，重启即失效
set_llm_cache(SQLiteCache(database_path="llm_cache.db"))   # 落盘，多进程可共享
set_llm_cache(None)                                  # 关闭（测试之间务必清掉，避免串味）

# 部分模型还支持在模型上开关：ChatOpenAI(..., cache=True, ...)
```

本机真实输出：

```text
未开缓存时，两次相同请求的模型调用次数: 2
开缓存后，两次相同请求的模型调用次数: 1
第三次换不同问题: 调用次数变为 2
SQLiteCache: 两次相同请求的模型调用次数: 1
缓存表结构: CREATE TABLE full_llm_cache ( prompt VARCHAR NOT NULL, llm VARCHAR NOT NULL, idx INTEGER NOT NULL, response VARCHAR, PRIMARY KEY (prompt, llm, idx) )
缓存行数: 1 | 主键: ['prompt', 'llm', 'idx', 'response']
```

| 缓存层 | 命中范围 | 存储 | 适用 |
|---|---|---|---|
| `InMemoryCache` | 单进程 | 内存 | 同进程内的重复请求、演示 |
| `SQLiteCache` | 单机多进程 | 文件 | 单机服务、批处理任务去重 |
| Redis / 自建缓存 | 多副本 | 外部 | 生产多副本、需要 TTL 与隔离 |
| 检索结果缓存 | 查询级 | 任意 | 热点问题降延迟（注意语料更新要失效） |

```text
要点：
- 缓存键包含提示词与模型标识：任何影响输出的因素（系统提示、温度、工具集合）变了都必须换键
- 不要把含用户私有上下文的提示纳入共享缓存：命中别人的缓存等于数据泄漏
- 落地实现优先选带 TTL 与命名空间的方案（Redis），sqlite 只适合单机
- 打开缓存后一定用「模型调用次数」验证生效（本机实测：2 -> 1），别只看延迟
- 测试之间必须 set_llm_cache(None)，否则上一个用例的缓存会让断言静默通过（假阳性）
```

## 并发与限流

并发控制解决两个反向的问题：**对外**要限制打到模型供应商的并发与 QPS（避免 429 与账单失控），**对内**要限制单进程的并发请求数（避免内存与连接池被打满）。LangChain 侧可用 `InMemoryRateLimiter` 做 QPS 限制，`Runnable.batch(..., config={"max_concurrency": N})` 做批量并发上限；服务侧用 `asyncio.Semaphore` 在请求入口收口。重试要用 `with_retry` 精确指定可重试异常，写操作不重试。

```python
import asyncio
from langchain_core.rate_limiters import InMemoryRateLimiter

SEM = asyncio.Semaphore(4)                                   # 进程内模型并发上限
rl = InMemoryRateLimiter(requests_per_second=5, check_every_n_seconds=0.05, max_bucket_size=2)

retryable = model.with_retry(stop_after_attempt=3, wait_exponential_jitter=False,
                             retry_if_exception_type=(RuntimeError,))
results = model.batch([...], config={"max_concurrency": 2})   # 批量并发上限
```

本机真实输出：

```text
=== 5. 并发 8 个请求（信号量上限 4） ===
状态码统计: {200: 8} 总耗时 44 ms
GET /metrics -> {'requests': 18, 'errors': 0, 'inflight': 1, 'max_inflight': 8, 'tokens': 847}

=== 3. 令牌桶限流（异步，控制对上游的 QPS） ===
InMemoryRateLimiter: (*, requests_per_second: 'float' = 1, check_every_n_seconds: 'float' = 0.1, max_bucket_size: 'float' = 1) -> 'None'
has acquire: True | has aacquire: True
InMemoryRateLimiter(5 rps, max_bucket_size=2) 6 次 acquire 的时刻(ms): [200, 403, 607, 808, 1008, 1209]
  -> 首次也要先等一个间隔（初始令牌桶是空的），max_bucket_size 只决定后续能攒多少

=== 1. 重试与退避：with_retry ===
不加重试 -> RuntimeError 上游 503（第 1 次）
with_retry(stop_after_attempt=3) -> 内容: 终于成功了 | 实际调用次数: 3
上限不足时仍抛错 -> 上游 503（第 2 次） | 尝试次数: 2

=== 4. 批量与并发上限：abatch / batch ===
5 条串行约 500 ms；abatch 全并发 53 ms；max_concurrency=2 约 153 ms
```

```text
要点：
- 并发闸门要分层：请求级（网关/信号量）、模型级（供应商配额）、批量级（max_concurrency），别只做一个
- InMemoryRateLimiter 的初始令牌桶是空的，第一次 acquire 也要等待（本机实测首个放行时刻是 200ms）
- 重试必须指定异常类型与次数上限，并对写操作关闭重试；重试要带抖动退避（wait_exponential_jitter）
- 超时预算要分层：网关 < 服务 < 上游单次调用，保证最外层先超时并返回可读错误
- 限流被触发时要可观测（计数 + 429/503 事件），否则「偶发变慢」永远查不出原因
```

## 可观测与探针

服务要有三类端点：存活探针（`/healthz`，只检查进程）、就绪探针（`/readyz`，检查依赖与图结构，用于摘流量）、指标端点（`/metrics`，供 Prometheus 抓取）。再加上访问日志中间件（耗时、状态码、请求 ID），以及会话排查端点（读检查点）。这里的原则是：探针要便宜（不能每次都打模型）、要能区分「我活着」和「我能干活」。

```python
@app.middleware("http")
async def access_log(request: Request, call_next):
    STATS["requests"] += 1
    STATS["inflight"] += 1
    STATS["max_inflight"] = max(STATS["max_inflight"], STATS["inflight"])
    t0 = time.perf_counter()
    try:
        resp = await call_next(request)
    finally:
        STATS["inflight"] -= 1
    resp.headers["x-elapsed-ms"] = f"{(time.perf_counter() - t0) * 1000:.1f}"
    return resp

@app.get("/readyz")
async def readyz():
    ok = AGENT is not None and "model" in AGENT.get_graph().nodes
    if not ok:
        raise HTTPException(status_code=503, detail="agent not ready")
    return {"status": "ready", "nodes": sorted(AGENT.get_graph().nodes.keys())}
```

本机真实输出：

```text
GET /healthz -> {'status': 'ok', 'settings': {...}}
GET /readyz  -> {'status': 'ready', 'nodes': ['__end__', '__start__', 'model', 'tools']}
GET /metrics -> {'requests': 18, 'errors': 0, 'inflight': 1, 'max_inflight': 8, 'tokens': 847}
x-elapsed-ms 响应头: 8.2 / 2.9
```

```text
要点：
- /healthz 只看进程；/readyz 才检查图与依赖，编排系统用前者重启、后者摘流量
- 探针绝不能调模型：一次探针一次推理会把成本和配额全部吃掉
- 指标至少要有：请求数、错误数、并发数、p95 延迟、token 数、限流次数、缓存命中率
- 请求 ID（或 trace_id）要从入口贯穿到日志与 LangSmith trace，否则排查时对不上
- 「按 thread_id 查状态」是 Agent 服务特有的排障入口，比翻日志高效得多
```

## 生产检查清单

| 类别 | 检查项 | 通过标准 |
|---|---|---|
| 配置与密钥 | 全部配置走环境变量；密钥来自密钥管理 | 镜像里搜不到任何 key；缺配置启动即失败 |
| 模型 | 超时、重试次数、并发上限显式设置 | `ChatOpenAI(timeout=..., max_retries=..., ...)` 有明确取值 |
| 会话 | thread_id 生成规则与长度；检查点存储 | 多副本时用共享存储（PostgresSaver）；thread_id < 255 字符 |
| 限流 | 入口并发、QPS、批量并发三层都有闸门 | 压测下无 429 雪崩；限流次数有指标 |
| 超时 | 网关 / 服务 / 上游单次超时逐层收紧 | 最外层先超时并返回 504 与可读错误 |
| 成本 | 按租户/功能记账 + 预算告警 + 拦截 | 超预算能真正阻断（中间件/网关，不是回调） |
| 缓存 | 键含模型与提示词版本；有 TTL 与命名空间 | 不含用户私有上下文的提示才进共享缓存 |
| 可观测 | /healthz /readyz /metrics + trace 三件套 | LangSmith 三变量就位；探针不调模型 |
| 安全 | 输入长度、工具白名单、HITL、PII 脱敏 | 写操作全部有人审或幂等键；trace 内无 PII |
| 发布 | 灰度、回滚、回归评估门禁 | 评估通过率不低于基线；5 分钟内可回滚 |

```text
要点：
- 清单要在 PR 模板里逐项打勾，不能只存在于本文档
- 每条「通过标准」都必须是可验证的客观事实（有取值、有端点、有指标），不能写「尽量」
- 成本与延迟门禁进 CI，把「上线才发现账单翻倍」变成「合并前就被拦住」
- 回滚预案要包含「检查点是否兼容」：状态结构变了要能向前兼容或允许丢会话
- 灰度期把新旧两版 Prompt 的评估报告放在一起对比，别只看线上指标
```

## 应用场景实战

### 场景一：带 SSE 流式的制度问答服务（FastAPI + uvicorn 真实运行）

场景：企业内部制度问答，前端要打字机效果，需要会话续聊、健康探针与会话排查接口。下面两个文件一起构成完整服务：`app.py` 是服务，`drive.py` 负责起服务、发请求、读 SSE、做并发压测。

```python
"""app.py —— 用 uvicorn app:app --host 127.0.0.1 --port 18731 启动"""
import asyncio, json, time
from contextlib import asynccontextmanager

from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import StreamingResponse
from pydantic import BaseModel, Field
from pydantic_settings import BaseSettings

from langchain_core.messages import HumanMessage
from langchain_core.tools import tool
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver


class Settings(BaseSettings):
    model_name: str = "fake-chat"
    max_concurrency: int = 4
    request_timeout_s: float = 30.0
    max_input_chars: int = 4000
    class Config:
        env_prefix = "APP_"


SETTINGS = Settings()
SEM = asyncio.Semaphore(SETTINGS.max_concurrency)
STATS = {"requests": 0, "errors": 0, "inflight": 0, "max_inflight": 0, "tokens": 0}


@tool
def get_policy(topic: str) -> str:
    """查询公司制度库中的主题（年假 / 报销 / 密码）"""
    db = {"年假": "满一年 10 天，满三年 15 天。", "报销": "15 个自然日内提交发票。", "密码": "不少于 12 位，每 90 天轮换。"}
    return db.get(topic, "未收录该主题")


class ChatRequest(BaseModel):
    message: str = Field(min_length=1)
    thread_id: str = Field(default="default")


AGENT = create_agent(model=streaming_model(), tools=[get_policy], checkpointer=InMemorySaver())


@asynccontextmanager
async def lifespan(app: FastAPI):
    print(f"[startup] model={SETTINGS.model_name} max_concurrency={SETTINGS.max_concurrency}")
    yield
    print("[shutdown] bye")


app = FastAPI(lifespan=lifespan)


@app.get("/healthz")
async def healthz():
    return {"status": "ok", "settings": SETTINGS.model_dump()}


@app.get("/readyz")
async def readyz():
    if AGENT is None or "model" not in AGENT.get_graph().nodes:
        raise HTTPException(status_code=503, detail="agent not ready")
    return {"status": "ready", "nodes": sorted(AGENT.get_graph().nodes.keys())}


@app.get("/metrics")
async def metrics():
    return STATS


@app.get("/debug/thread/{thread_id}")
async def debug_thread(thread_id: str):
    cfg = {"configurable": {"thread_id": thread_id}}
    snap = AGENT.get_state(cfg)
    return {"thread_id": thread_id, "messages": len(snap.values.get("messages", [])),
            "checkpoints": len(list(AGENT.get_state_history(cfg)))}


@app.post("/chat")
async def chat(req: ChatRequest):
    if len(req.message) > SETTINGS.max_input_chars:
        raise HTTPException(status_code=413, detail="输入过长")
    cfg = {"configurable": {"thread_id": req.thread_id}}
    try:
        async with SEM:
            out = await asyncio.wait_for(AGENT.ainvoke({"messages": [HumanMessage(req.message)]}, cfg),
                                         SETTINGS.request_timeout_s)
    except asyncio.TimeoutError:
        raise HTTPException(status_code=504, detail="模型超时")
    except Exception:
        STATS["errors"] += 1
        raise HTTPException(status_code=500, detail="内部错误")
    return {"answer": out["messages"][-1].content, "thread_id": req.thread_id}


def sse(event: str, data) -> str:
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"


@app.post("/chat/stream")
async def chat_stream(req: ChatRequest):
    async def gen():
        cfg = {"configurable": {"thread_id": req.thread_id}}
        yield sse("start", {"thread_id": req.thread_id})
        async with SEM:
            async for mode, payload in AGENT.astream({"messages": [HumanMessage(req.message)]}, cfg,
                                                     stream_mode=["messages", "updates"]):
                if mode == "messages":
                    token, meta = payload
                    if token.content:
                        yield sse("token", {"text": token.content, "node": meta.get("langgraph_node")})
                else:
                    for node, upd in payload.items():
                        msgs = (upd or {}).get("messages") if isinstance(upd, dict) else None
                        if msgs:
                            yield sse("node", {"node": node, "content": str(msgs[-1].content)[:80]})
        yield sse("done", {"elapsed_ms": 0.0})

    return StreamingResponse(gen(), media_type="text/event-stream",
                            headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

```python
"""drive.py —— 起服务、发请求、读 SSE、并发压测（真实运行输出见下）"""

import httpx

try:
    for _ in range(60):                                    # 就绪探测，不做盲等

    print("readyz :", httpx.get(f"{BASE}/readyz").json())
    for i in (1, 2):
        r = httpx.post(f"{BASE}/chat", json={"message": f"年假怎么算（第 {i} 次）", "thread_id": "t-9"}, timeout=30)
        print(f"POST /chat #{i} ->", r.status_code, r.json()["answer"])
    print("thread:", httpx.get(f"{BASE}/debug/thread/t-9").json())

    tokens = []
    with httpx.stream("POST", f"{BASE}/chat/stream", json={"message": "年假", "thread_id": "s-1"}, timeout=30) as r:
        for line in r.iter_lines():
            if line.startswith("data: "):
                data = json.loads(line[6:])
                if "text" in data:
                    tokens.append(data["text"])
    print("SSE token 数:", len(tokens), "拼接:", "".join(tokens))

    with concurrent.futures.ThreadPoolExecutor(max_workers=8) as ex:
        codes = list(ex.map(lambda i: httpx.post(f"{BASE}/chat", json={"message": f"c{i}", "thread_id": f"c-{i}"},
                                                timeout=60).status_code, range(8)))
    print("并发 8 请求状态码:", {c: codes.count(c) for c in set(codes)})
    print("metrics:", httpx.get(f"{BASE}/metrics").json())
finally:
    proc.send_signal(signal.SIGINT)
    out, _ = proc.communicate(timeout=10)
    print("server log:", out.strip())
```

### 场景二：缓存 + 重试 + 限流的工程化加固

场景：批量任务要重复调用模型（同一批问题每天重跑），希望相同问题不重复计费、上游抖动自动恢复、并且不给供应商打爆配额。

```python
"""15.10 场景二：缓存 + 重试 + 限流"""
import asyncio, os, sqlite3, time
from langchain_core.caches import InMemoryCache
from langchain_core.globals import set_llm_cache
from langchain_core.messages import AIMessage
from langchain_core.rate_limiters import InMemoryRateLimiter
from langchain_community.cache import SQLiteCache

from s15_fake import ScriptedToolChatModel, COUNTER

# 1) 缓存：同一提示词只调一次模型
set_llm_cache(InMemoryCache())
model = ScriptedToolChatModel(script=[AIMessage(content="缓存答案")])
COUNTER["calls"] = 0
model.invoke("同一个问题"); model.invoke("同一个问题")
print("开缓存后模型调用次数:", COUNTER["calls"])          # 1

# 落盘缓存：跨进程复用
set_llm_cache(SQLiteCache(database_path="llm_cache.db"))
# 2) 重试：只对可重试异常
attempts = {"n": 0}
class Flaky(ScriptedToolChatModel):
    def _generate(self, messages, stop=None, run_manager=None, **kw):
        attempts["n"] += 1
        if attempts["n"] < 3:
            raise RuntimeError(f"上游 503（第 {attempts['n']} 次）")
        return super()._generate(messages, stop=stop, run_manager=run_manager, **kw)

flaky = Flaky(script=[AIMessage(content="终于成功了")])
res = flaky.with_retry(stop_after_attempt=3, wait_exponential_jitter=False,
                       retry_if_exception_type=(RuntimeError,)).invoke("hi")
print("重试后成功:", res.content, "| 实际调用次数:", attempts["n"])

# 3) 限流：内置限流器 + 批量并发上限
rl = InMemoryRateLimiter(requests_per_second=5, check_every_n_seconds=0.05, max_bucket_size=2)
t0 = time.monotonic(); stamps = []
for _ in range(6):
    rl.acquire()
    stamps.append(round((time.monotonic() - t0) * 1000))
print("限流器 6 次放行时刻(ms):", stamps)
set_llm_cache(None)     # 测试/任务结束务必清掉，避免污染后续调用
```

## 最佳实践与踩坑记录

### 最佳实践

1. 配置、密钥、模型名全部环境变量化，代码里不留可运行的默认密钥；缺配置就启动失败。
2. 超时分三层设：网关 < 服务（`asyncio.wait_for`）< 上游单次调用，保证最外层先返回可读错误。
3. 把并发闸门做成配置项（`APP_MAX_CONCURRENCY`），压测时能调、事故时能一键调小保护上游。
4. 缓存只在「提示词不含用户私有数据」时共享，且必须带 TTL 与命名空间；打开后用调用次数验证生效。
5. 流式接口必须埋 TTFT 指标并处理客户端断开，别让用户关页面后还继续烧 token。
6. 上线前把「生产检查清单」当 PR 模板逐项打勾；回滚预案里要写清检查点兼容性怎么处理。

### 踩坑记录

```text
坑 1：服务脚本用 `python drive.py > out.log` 跑，日志文件一直是空的，以为服务没起来
结论：以为 uvicorn 启动失败或卡在导入，反复重启。
原因：Python stdout 在重定向到文件时是块缓冲，进程被 SIGINT 结束时缓冲区未必落盘，
      运行期间看不到任何进度（本机实测：同一脚本带 -u 立即可见，不带 -u 直到超时才看到文件内容）。
解法：容器与非交互场景统一用 `python -u` 或设 PYTHONUNBUFFERED=1；
      uvicorn 用 --log-level 控制自身日志，业务日志走结构化 logger 并 flush。
      另外不要靠 sleep 等启动：用探针轮询 /healthz 判断就绪（本机 drive 脚本就是这么做的）。

坑 2：并发 8 个请求，/metrics 里 max_inflight=8 而信号量设的是 4，以为信号量失效
结论：以为 asyncio.Semaphore 没起作用，准备换成线程池。
原因：两个指标量的不是同一件事——中间件统计的是 HTTP 请求并发（8 个请求都已进入应用），
      信号量限制的是模型调用并发（它们都在 async with SEM 处排队）。本机实测 8 个请求全部 200，
      max_inflight=8、tokens=847。
解法：指标命名与文档要写清口径（request_inflight vs model_inflight），
      分别暴露两个计数器，别用一个 inflight 表示所有并发。

坑 3：缓存打开后本地测试全绿，上线发现串了别人的回答
结论：以为缓存键包含了用户信息，实际上没有。
原因：缓存键由提示词与模型标识组成（SQLiteCache 的主键是 prompt + llm + idx，本机实测表结构），
      如果提示词里带了「当前用户 X 的历史」，不同用户可能拼出相同提示，或者命中同一份过期回答。
解法：含用户私有上下文的调用不要走共享缓存；需要缓存就按 tenant 分命名空间并设 TTL；
      上线前用「两次不同用户、相同问题」的用例验证不会互相命中。

坑 4：重试配到写操作上，一笔转账被执行了三次
结论：以为框架会做幂等处理。
原因：with_retry 只认「异常」，不知道业务语义；上游超时但实际已成功时，重试就是重复执行
      （本机实测 with_retry(stop_after_attempt=3) 会真实调用 3 次）。
解法：写操作不配置自动重试；必须重试时带幂等键（业务侧唯一请求号），
      并把重试范围限制在读取类与幂等的计算类调用上。

坑 5：InMemoryRateLimiter 设了 max_bucket_size=2，以为前两次调用能立刻通过
结论：以为初始桶是满的，怪限流器不准。
原因：初始令牌桶为空，第一次 acquire 也要等一个间隔（本机实测 5 rps 下单次放行时刻是
      200/403/607/808/1008/1209 ms，间隔稳定 200ms，没有前两次的突发放行）。
解法：把「首次等待」计入超时预算；需要突发额度就用自己实现的令牌桶按业务配额发放
      （本文 15.10 的 TokenBucket 示例：3 个突发额度 + 每秒 10 个补充），
      或选支持初始令牌配置的自定义限流器。
```
