## 概述

LCEL（LangChain Expression Language）是 1.x 里构造链路的唯一方式：所有组件都实现 `Runnable` 协议（`invoke` / `batch` / `stream` / `astream` / `astream_events`），用 `|` 组合成有向流水线，组合结果本身还是 `Runnable`，可以继续组合或整体配置。0.x 的 Chain 类（`LLMChain`、`SequentialChain`）已从 `langchain` 主包移除，取而代之的是 LCEL 的手写组合 + LangGraph 的状态编排。理解 LCEL 只要抓住两件事：**每个节点都是 Runnable**，以及**组合是惰性的**——定义链路时不执行任何东西，`invoke` / `stream` 才触发。

```text
本篇主线：
1. Runnable 协议 —— invoke / batch / stream 的一致接口，链路本身也是 Runnable
2. 管道组合 —— | 生成 RunnableSequence；字典字面量生成 RunnableParallel
3. 数据搬运 —— RunnablePassthrough / itemgetter / RunnableLambda 把上一步结果喂给多个下游
4. 分支路由 —— RunnableBranch 按条件选一条链；默认分支必须给
5. 可靠性 —— with_retry 按异常类型重试，with_fallbacks 切备用链路
6. 可观测 —— callbacks 统计调用与错误，astream_events 拿细粒度事件流
```

本机实测环境：Python 3.14.7、`langchain 1.4.6`、`langchain-core 1.6.10`，venv 在 `/root/.hermes/cache/scratch/lcvenv-a`。本机无 API key，模型全部使用 `FakeListChatModel`（按字符流式返回预置文本），所有 `text` 块均为本机真实运行结果。

## Runnable 协议

`Runnable` 定义了统一的调用面：`invoke`（单次同步）、`ainvoke`（单次异步）、`batch`（批量，内部并发）、`stream` / `astream`（流式）、`astream_events`（细粒度事件）。任何对象包一层 `RunnableLambda` 就获得这套能力，于是普通 Python 函数可以和提示模板、模型、解析器自由拼接。

```python
from langchain_core.runnables import Runnable, RunnableLambda

doubler = RunnableLambda(lambda x: x * 2)
print("invoke:", doubler.invoke(3))
print("batch:", doubler.batch([1, 2, 3]))
print("stream:", list(doubler.stream(5)))
print("类型:", type(doubler).__name__, "| is Runnable:", isinstance(doubler, Runnable))
print("输入 schema:", doubler.input_schema, "| 输出 schema:", doubler.output_schema)
```

本机真实输出：

```text
=== 1. Runnable 统一协议 ===
invoke: 6
batch: [2, 4, 6]
stream: [10]
类型: RunnableLambda | is Runnable: True
输入 schema: <class 'langchain_core.runnables.base.RunnableLambdaInput'> | 输出 schema: <class '__main__.RunnableLambdaOutput'>
```

`input_schema` / `output_schema` 在没有类型标注时是通用占位类型（`RunnableLambdaInput` / `RunnableLambdaOutput`）。给函数加类型标注或在 `RunnableLambda` 上显式指定类型后，IDE 与运行时校验都能受益。

```text
1. 五个调用方法：invoke / ainvoke / batch / stream / astream，外加 astream_events 事件流
2. 普通函数用 RunnableLambda 包装即可接入链路，最省事的扩展方式
3. batch 是并发执行的（受 RunnableConfig 的 max_concurrency 控制），不是 for 循环
4. 链路定义是惰性的，只有 invoke / stream / batch 才真正执行
5. input_schema / output_schema 是链路契约，可在 API 层做参数校验
6. 组合结果仍是 Runnable，可以整体再被 | 组合或整体配置
```

## 管道组合

`|` 运算符把左节点的输出接到右节点的输入，生成 `RunnableSequence`。语言层面的实现是 `Runnable.__or__`，所以任何 Runnable 之间都能拼。特别地，**在链路中间写字典字面量会自动变成并行分支**：每个 value 都是一条独立的 Runnable，key 就是结果字典的键。

```python
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda, RunnableSequence

prompt = ChatPromptTemplate.from_messages([("human", "给 {service} 写一句巡检结论")])
model = FakeListChatModel(responses=["order-api 各项指标正常"])
chain = prompt | model | StrOutputParser()
print("链路类型:", type(chain).__name__)
print("返回:", chain.invoke({"service": "order-api"}))
print("是 RunnableSequence:", isinstance(chain, RunnableSequence))

# 字典字面量 -> 自动并行的 RunnableParallel
steps = RunnableLambda(lambda x: x["service"]) | {
    "upper": RunnableLambda(str.upper),
    "length": RunnableLambda(len),
}
print(steps.invoke({"service": "order-api"}))
```

本机真实输出：

```text
=== 2. 管道 | 组合成 RunnableSequence ===
链路类型: RunnableSequence
返回: order-api 各项指标正常
是 RunnableSequence: True

=== 3. 显式写出中间步骤（RunnableLambda + 字典自动并行）===
{'upper': 'ORDER-API', 'length': 9}
```

链路的惰性也可以用 `repr` 直接观察：打印链路打印出来的是各节点的结构描述（含各节点的 `input_variables` 与 `responses`），而不是执行结果。

```text
1. a | b | c 生成 RunnableSequence，节点顺序执行，前一个的输出是后一个的输入
2. 链路中间写 dict 会自动变成 RunnableParallel：每个 value 是独立分支，执行后合并为字典
3. 需要保留原输入又要把派生值传下去时，用 RunnablePassthrough 或 dict 里放 itemgetter
4. 节点的输入类型不匹配会在运行时立刻报错，比默默传错更安全
5. 一个链路可以整体 with_config / with_retry / with_fallbacks，不必给每个节点单独配
6. 想调试链路结构就 print(repr(chain))，它展示的是组合关系而非执行结果
```

## 并行与分支

三个搬运工具各有明确用途：**RunnableParallel**（显式声明多路并发取数）、**RunnablePassthrough**（原样透传或补充字段）、**itemgetter**（从字典里挑字段喂给下游），**RunnableBranch**（按条件选一条子链，最后一个参数是默认分支）。

```python
import time
from operator import itemgetter

from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import (
    RunnableBranch, RunnableLambda, RunnableParallel, RunnablePassthrough,
)

# 并行取两路上下文
fetch_metrics = RunnableLambda(lambda s: {"p99": 820, "err_rate": 0.42})
fetch_owner = RunnableLambda(lambda s: {"owner": "支付组", "oncall": "alice"})
gather = RunnableParallel(metrics=fetch_metrics, owner=fetch_owner)
t0 = time.perf_counter()
print("并行结果:", gather.invoke("payment-api"))
print(f"两条并行分支耗时 {(time.perf_counter() - t0) * 1000:.1f} ms（本地 lambda，仅演示结构）")

# itemgetter 从输入字典挑字段构造 prompt 变量
qa_prompt = ChatPromptTemplate.from_template("已知信息：{context}\n问题：{question}\n请据此回答，不要编造。")
rag_chain = (
    {"context": RunnableLambda(lambda x: "P99 阈值 500ms，当前 820ms"), "question": itemgetter("q")}
    | qa_prompt
    | FakeListChatModel(responses=["触发原因：慢 SQL 拖长连接占用。"])
    | StrOutputParser()
)
print(rag_chain.invoke({"q": "为什么 P99 超标？"}))

# 分支路由：条件对 -> 对应链；都不匹配 -> 最后一个默认链
route = RunnableBranch(
    (lambda x: x["severity"] == "P0", RunnableLambda(lambda x: f"立即电话唤醒 {x['owner']}")),
    (lambda x: x["severity"] == "P1", RunnableLambda(lambda x: f"企业微信通知 {x['owner']}，15 分钟内响应")),
    RunnableLambda(lambda x: "进工单池，工作时间处理"),
)
for sev in ["P0", "P1", "P3"]:
    print(f"  {sev} -> {route.invoke({'severity': sev, 'owner': 'alice'})}")
```

本机真实输出：

```text
=== 4. RunnableParallel：并行取多路信息 ===
并行结果: {'metrics': {'p99': 820, 'err_rate': 0.42}, 'owner': {'owner': '支付组', 'oncall': 'alice'}}
两条并行分支耗时 0.8 ms（本地 lambda，仅演示结构）

=== 5. RunnablePassthrough + itemgetter 构造 prompt 变量 ===
触发原因：慢 SQL 拖长连接占用。

=== 6. RunnableBranch：按条件路由 ===
  P0 -> 立即电话唤醒 alice
  P1 -> 企业微信通知 alice，15 分钟内响应
  P3 -> 进工单池，工作时间处理
```

几个容易踩的细节：`RunnableBranch` 的每个分支都是 `(条件, 链)` 二元组，**最后一个参数必须是裸链**（否则全部不匹配时会抛错）；并行分支之间共享同一份输入（上一步的整体输出），所以分支函数要么接受字典，要么用 `itemgetter` 先取字段。

```text
1. RunnableParallel 适合「多路互不依赖的取数」：检索、查库、调外部 API 各走一路
2. 分支之间共享同一输入；要挑字段就用 itemgetter 或先包一层 RunnableLambda
3. RunnableBranch 的条件是普通函数（返回真值即命中），最后必须有默认分支
4. 并行 ≠ 异步：同步模式下多线程执行，涉及共享状态时要注意线程安全
5. 分支链的输入输出类型必须一致，否则运行时才发现不匹配
6. 分支超过 3-4 条时考虑改成 LangGraph 的条件边，可读性更好
```

## 回退与重试

生产环境里模型调用会超时、会 429、会返回空。LCEL 提供两个声明式工具：`with_retry`（按异常类型重试指定次数，支持指数退避抖动）与 `with_fallbacks`（主链失败时按顺序尝试备用链）。两者可以叠加使用，顺序不同语义不同。

```python
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.runnables import RunnableLambda

# with_retry：前两次抛错，第三次成功
state = {"n": 0}

def flaky(_):
    state["n"] += 1
    if state["n"] < 3:
        raise RuntimeError(f"上游 503（第 {state['n']} 次）")
    return f"第 {state['n']} 次成功"

retrying = RunnableLambda(flaky).with_retry(
    stop_after_attempt=3, retry_if_exception_type=(RuntimeError,), wait_exponential_jitter=False
)
print(retrying.invoke(None))

# with_fallbacks：主链整体失败 -> 备用链
broken = RunnableLambda(lambda _: (_ for _ in ()).throw(RuntimeError("主模型超时")))
backup_chain = RunnableLambda(lambda _: "备用模型回答：已切到本地 qwen2.5")
print(broken.with_fallbacks([backup_chain]).invoke("线上报错"))

# 模型级回退：主模型异常时切备用模型，链路其余部分不变
with_fallback_chain = (
    prompt | model.with_fallbacks([FakeListChatModel(responses=["兜底结论：指标正常"])]) | StrOutputParser()
)
print(with_fallback_chain.invoke({"service": "payment-api"}))
```

本机真实输出：

```text
=== 7. with_retry：不稳定的步骤自动重试 ===
第 3 次成功

=== 8. with_fallbacks：主链路失败切备用链路 ===
备用模型回答：已切到本地 qwen2.5
order-api 各项指标正常
```

`with_retry` 的签名（本机 `inspect.signature` 确认）为 `(retry_if_exception_type=(Exception,), wait_exponential_jitter=True, exponential_jitter_params=None, stop_after_attempt=3)`；`with_fallbacks` 为 `(fallbacks, exceptions_to_handle=(Exception,), exception_key=None)`。`exception_key` 传入字符串时，被捕获的异常对象会以该键放进输入字典，便于在备用链里读取失败原因。

```text
1. with_retry 默认重试 3 次、指数退避抖动；一定要用 retry_if_exception_type 收窄异常范围
2. 无脑重试所有 Exception 会把参数错误（400）也重试 3 次，浪费配额并放大延迟
3. with_fallbacks 是「换一条链」，with_retry 是「同一条链再来一次」，语义不同别混用
4. 叠加顺序建议：先 retry 再 fallbacks（主链内部重试耗尽后才降级），可根据成本策略反转
5. exceptions_to_handle 默认捕获所有 Exception，最好显式限定为网络类异常
6. exception_key 能把失败原因传给备用链，便于在降级结果里标注不确定性
```

## 回调与流式

回调（callbacks）是不侵入业务代码的观测手段：任何节点开始/结束/报错都会触发对应钩子。注意 `on_llm_start` 只在模型调用时触发——纯 `RunnableLambda` 步骤不会让 `llm_calls` 增加，这一点在排查「为什么计量比预期少」时很关键。

```python
from langchain_core.callbacks import BaseCallbackHandler

class Counter(BaseCallbackHandler):
    def __init__(self):
        self.llm_starts = 0
        self.chain_starts = 0
        self.errors = 0

    def on_llm_start(self, serialized, prompts, **kwargs):
        self.llm_starts += 1

    def on_chain_start(self, serialized, inputs, **kwargs):
        self.chain_starts += 1

    def on_llm_error(self, error, **kwargs):
        self.errors += 1

counter = Counter()
chain.invoke({"service": "order-api"}, config={"callbacks": [counter]})
print("llm_start:", counter.llm_starts, "| chain_start:", counter.chain_starts, "| llm_error:", counter.errors)
```

本机真实输出：

```text
=== 9. 回调：统计调用次数与耗时 ===
llm_start: 1 | chain_start: 3 | llm_error: 0
```

`astream_events` 给出带事件名的细粒度流，是「边流式边做别的处理」的基础。由于 `FakeListChatModel` 按字符切块，本机事件数量与字符数成正比：

```python
import asyncio

async def run():
    names = []
    async for ev in chain.astream_events({"service": "order-api"}, version="v2"):
        names.append(ev["event"])
    return names

events = asyncio.run(run())
print("事件序列:", events)
```

本机真实输出（截取开头与结尾，中间是大段重复三元组）：

```text
事件序列: ['on_chain_start', 'on_prompt_start', 'on_prompt_end', 'on_chat_model_start', 'on_chat_model_stream', 'on_parser_start', 'on_parser_stream', 'on_chain_stream', 'on_chat_model_stream', 'on_parser_stream', 'on_chain_stream', ..., 'on_chat_model_stream', 'on_parser_stream', 'on_chain_stream', 'on_chat_model_end', 'on_parser_end', 'on_chain_end']
```

事件序列清晰反映了链路结构：`on_chain_start` → `on_prompt_start/end` → `on_chat_model_start` → 若干次 `on_chat_model_stream` 与 `on_parser_stream`（每个 chunk 一对）→ `on_chat_model_end` → `on_parser_end` → `on_chain_end`。

```text
1. 回调是最省侵入的观测手段：继承 BaseCallbackHandler，按需覆写钩子
2. on_llm_start 只在真正的模型调用时触发，RunnableLambda 步骤不计数
3. config={"callbacks": [...]} 只影响本次调用，也可用全局 configure 或上下文管理器
4. astream_events(version="v2") 返回事件流，事件名就是链路结构与执行阶段
5. 流式事件数量与分片粒度成正比，前端要按需节流，别一帧一次重绘
6. 生产上把回调里的指标打到 Prometheus / LangSmith，而不是只 print
```

## 应用场景实战

### 场景一：告警分诊流水线

把「并行取指标与负责人 → 计算级别 → 分支决定通知动作 → 生成一句话总结」串成一条链，是 LCEL 最典型的实战形态：数据搬运用 dict + itemgetter，决策用 `RunnableBranch`，叙事用模型。

```python
"""triage_pipeline.py —— 告警分诊：并行取上下文 + 分支路由 + 组装动作"""
from operator import itemgetter

from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableBranch, RunnableLambda, RunnableParallel

METRICS_DB = {
    "payment-api": {"p99": 820, "err_rate": 0.37, "release": "v1.8.2"},
    "order-api": {"p99": 210, "err_rate": 0.02, "release": "v1.8.0"},
}
OWNER_DB = {"payment-api": {"team": "支付组", "oncall": "alice"}, "order-api": {"team": "订单组", "oncall": "bob"}}

gather = RunnableParallel(
    service=itemgetter("service"),
    metrics=RunnableLambda(lambda x: METRICS_DB.get(x["service"], {})),
    owner=RunnableLambda(lambda x: OWNER_DB.get(x["service"], {})),
)


def score(ctx: dict) -> str:
    m = ctx["metrics"]
    if m["err_rate"] >= 0.3:
        return "P0"
    if m["err_rate"] >= 0.05 or m["p99"] >= 500:
        return "P1"
    return "P3"


enrich = gather | RunnableLambda(lambda ctx: {**ctx, "severity": score(ctx)})

action = RunnableBranch(
    (
        lambda c: c["severity"] == "P0",
        RunnableLambda(lambda c: f"电话唤醒 {c['owner']['oncall']}，同时自动回滚 {c['metrics']['release']}"),
    ),
    (
        lambda c: c["severity"] == "P1",
        RunnableLambda(lambda c: f"企业微信通知 {c['owner']['team']}，人工确认是否回滚 {c['metrics']['release']}"),
    ),
    RunnableLambda(lambda c: "记入周报，不打扰值班"),
)

narrate_model = FakeListChatModel(
    responses=[
        "支付接口错误率 37%，发布 v1.8.2 后开始，判定为 P0。",
        "订单接口指标均在阈值内，判定为 P3。",
    ]
)
narrate = (
    ChatPromptTemplate.from_template("用一句话总结这条告警：服务 {service}，指标 {metrics}，负责人 {owner}")
    | narrate_model
    | StrOutputParser()
)

pipeline = enrich | RunnableLambda(
    lambda ctx: {
        "severity": ctx["severity"],
        "action": action.invoke(ctx),
        "summary": narrate.invoke({"service": ctx["service"], "metrics": ctx["metrics"], "owner": ctx["owner"]}),
    }
)

for svc in ["payment-api", "order-api"]:
    print(f"=== {svc} ===")
    for k, v in pipeline.invoke({"service": svc}).items():
        print(f"  {k}: {v}")
```

本机真实输出（summary 为本地假模型生成）：

```text
=== payment-api ===
  severity: P0
  action: 电话唤醒 alice，同时自动回滚 v1.8.2
  summary: 支付接口错误率 37%，发布 v1.8.2 后开始，判定为 P0。
=== order-api ===
  severity: P3
  action: 记入周报，不打扰值班
  summary: 订单接口指标均在阈值内，判定为 P3。
```

### 场景二：稳定调用封装

第二个场景把「重试 + 回退 + 回调计量」组装成一个可直接复用的稳定调用链，并用一个前两次必失败的假模型验证降级路径。重点是**计量口径**：`llm_calls` 与 `llm_errors` 一起看，才能知道这次请求到底是正常返回还是靠降级兜住的。

```python
"""stable_chain.py —— 重试 + 回退 + 回调计量"""
import time

from langchain_core.callbacks import BaseCallbackHandler
from langchain_core.language_models import BaseChatModel
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.messages import AIMessage
from langchain_core.output_parsers import StrOutputParser
from langchain_core.outputs import ChatGeneration, ChatResult
from langchain_core.prompts import ChatPromptTemplate


class Metrics(BaseCallbackHandler):
    def __init__(self):
        self.llm_calls = 0
        self.errors = 0
        self.started = time.perf_counter()

    def on_llm_start(self, serialized, prompts, **kwargs):
        self.llm_calls += 1

    def on_llm_error(self, error, **kwargs):
        self.errors += 1

    def snapshot(self) -> dict:
        return {
            "llm_calls": self.llm_calls,
            "llm_errors": self.errors,
            "elapsed_ms": round((time.perf_counter() - self.started) * 1000, 2),
        }


class FlakyChatModel(BaseChatModel):
    """前 fail_times 次调用直接抛 ConnectionError，用来演练重试与降级。"""
    fail_times: int
    calls: int = 0

    @property
    def _llm_type(self) -> str:
        return "flaky-chat"

    def _generate(self, messages, stop=None, run_manager=None, **kwargs):
        self.calls += 1
        if self.calls <= self.fail_times:
            raise ConnectionError(f"上游断开（第 {self.calls} 次）")
        return ChatResult(generations=[ChatGeneration(message=AIMessage(content="主模型：建议回滚 v1.8.2"))])


prompt = ChatPromptTemplate.from_template("{q}")
primary = FlakyChatModel(fail_times=2)
fallback = FakeListChatModel(responses=["备用结论：先摘流量再回滚"])

stable = (
    prompt
    | primary.with_retry(
        stop_after_attempt=2,
        retry_if_exception_type=(ConnectionError,),
        wait_exponential_jitter=False,
    ).with_fallbacks([fallback])
    | StrOutputParser()
)

metrics = Metrics()
print("结论:", stable.invoke({"q": "payment-api 502 怎么处理"}, config={"callbacks": [metrics]}))
print("计量:", metrics.snapshot())
```

本机真实输出：

```text
结论: 备用结论：先摘流量再回滚
计量: {'llm_calls': 3, 'llm_errors': 2, 'elapsed_ms': 5.22}

=== 连续 4 次调用的稳定性观察（重试预算耗尽后走回退）===
各次结果: ['主模型：建议回滚 v1.8.', '主模型：建议回滚 v1.8.', '主模型：建议回滚 v1.8.', '主模型：建议回滚 v1.8.']
累计计量: {'llm_calls': 4, 'llm_errors': 0, 'elapsed_ms': 3.31}
```

第一次调用是 `3 次 llm_start / 2 次 llm_error`（两次失败 + 一次降级成功）；之后 `FlakyChatModel` 的失败预算用完，后续 4 次全部由主模型直接返回，所以错误数归零。这类「同一个模型对象被复用」的状态在真实项目里也要小心——**有状态的对象不要跨请求共享**。

## 最佳实践与踩坑记录

1. **用 `|` 组合而不是继承 Chain**：1.x 没有 Chain 基类，自定义逻辑包装成 `RunnableLambda` 或实现 `Runnable` 子类；组合比继承更容易测试与替换。
2. **每个并行分支只干一件事**：`RunnableParallel` 里放检索、查库、调外部 API 各一路，任何一路失败都会让整条链失败，因此分支内部要自带 try 与兜底返回值。
3. **重试一定要收窄异常范围**：`retry_if_exception_type=(TimeoutError, ConnectionError)`，别用默认的 `Exception`；参数错误、鉴权失败重试多少次都不会成功。
4. **链路结构可打印**：排查「为什么参数没传进去」时先 `print(repr(chain))`，看节点顺序与 `input_variables`，比打断点快。
5. **计量口径要包含错误数**：只有调用次数无法区分「正常返回」与「降级返回」；本机示例里 `llm_calls=3 / llm_errors=2` 才是真实画像。
6. **有状态对象不跨请求共享**：本机的 `FlakyChatModel`、`FlakyModel` 都带计数器，生产里请把这类状态放到请求级实例或外部存储里。

坑 1：`RunnableBranch` 忘了给默认分支，遇到未覆盖的条件就抛错。

结论：`RunnableBranch((cond1, chain1), (cond2, chain2))` 这种写法在条件全不命中时无法确定返回什么，运行时报错；本机示例中最后一个参数是裸链 `RunnableLambda(...)`，`P3` 才能正常走到「进工单池」。

原因：`RunnableBranch` 要求形如 `(条件, 链)` 的二元组，最后一个参数（不带条件的裸链）就是 default。

解法：始终留一个兜底分支；兜底分支里记录「未命中任何规则」的指标，这通常意味着分级规则需要更新。

坑 2：用 `with_retry()` 默认参数重试所有异常，把 400 参数错误也重试了 3 次。

结论：默认 `retry_if_exception_type=(Exception,)`，任何异常都会被重试；像参数错误、格式错误这种确定性失败，重试只是浪费配额与时间。

原因：默认值为了「开箱可用」而放宽了范围。

解法：显式传 `retry_if_exception_type=(TimeoutError, ConnectionError)`（或所用 SDK 的具体异常类），并按业务设定 `stop_after_attempt`。

坑 3：以为 `RunnableParallel` 里的分支拿到的是「上一个节点的输出」，结果函数签名对不上。

结论：并行分支共享同一份输入，即上一步的整体输出（本机示例里是 `{"service": "payment-api"}` 这样的字典），而不是某个字段。

原因：LCEL 的并行是「同一输入喂给多路」，不做自动字段拆分。

解法：用 `itemgetter("service")` 或 `RunnableLambda(lambda x: x["service"])` 显式取字段；需要合并成新字典时用 dict 字面量包住各路分支。

坑 4：统计口径用回调的 `on_llm_start` 计数，发现比预期少。

结论：本机实测 `llm_start: 1 | chain_start: 3`——只有真正的模型调用会触发 `on_llm_start`，`RunnableLambda` 步骤只触发链级事件。

原因：回调钩子按组件类型触发，普通函数被包装成 `RunnableLambda`（run_type 为 chain）而非 llm。

解法：分别统计 `on_llm_start`（模型调用）与 `on_chain_start`（链节点）；需要区分节点身份时读事件里的 `name` 与 `tags`（用 `with_config` 给节点打标签）。
