## 概述

LangChain 里的「模型」统一指实现 `BaseChatModel` 接口的 chat 模型：输入是一个消息列表（或一个字符串），输出是一条 `AIMessage`。这套接口把不同供应商的差异（OpenAI 的 `choices`、Anthropic 的 `content blocks`、Ollama 的流式 JSON）抹平成同一组属性：`content`、`content_blocks`、`tool_calls`、`usage_metadata`、`response_metadata`。消息则是上下文的基本单位，分 `SystemMessage` / `HumanMessage` / `AIMessage` / `ToolMessage` 四类角色，并支持「dict 写法」与「消息对象写法」互相转换。理解这两层（模型接口 + 消息协议）之后，切换供应商、加流式、做多模型路由都只是改参数。

```text
本篇主线：
1. 模型 —— 1.x 主推 chat 模型（BaseChatModel），init_chat_model 是统一入口
2. 消息 —— system / human / ai / tool 四类角色，dict 与对象两种写法等价
3. 内容块 —— content_blocks 是 1.x 新增的跨供应商标准化内容视图
4. 流式 —— .stream() 返回 AIMessageChunk，chunk 之间可用 + 拼接
5. 切换 —— configurable_alternatives 按 config 换模型，bind 给单次调用加参数
6. 本地 —— Ollama / vLLM / 任何 OpenAI 兼容端点都用 ChatOpenAI(base_url=...) 接入
```

本机实测环境：Python 3.14.7、`langchain 1.4.6`、`langchain-core 1.6.10`、`langchain-openai 1.7.2`，独立 venv `/root/.hermes/cache/scratch/lcvenv-a`。本机**没有 API key**，所有模型调用都用 `FakeListChatModel` / `GenericFakeChatModel` 这两个本地假模型完成，涉及内容生成的地方均已标注「本地假模型生成」；`ChatOpenAI` 只做「构造对象 + 读回参数」的静态验证，未发起任何网络请求。

## Chat 模型与补全模型

1.x 只保留一条主路：**chat 模型**。补全模型（老的 `BaseLLM` / `OpenAI` 类，输入输出都是纯字符串）在 1.x 已经从 `langchain` 主包中移除，OpenAI 兼容的补全端点也不再是推荐用法——因为绝大多数供应商现在只提供 chat 接口，而 chat 接口能表达 system 指令、多轮历史、工具调用与多模态，纯文本补全做不到。

两类模型的接口差异：

| 维度 | Chat 模型（BaseChatModel） | 补全模型（旧 BaseLLM） |
| --- | --- | --- |
| 输入 | `list[BaseMessage]` 或字符串（自动包成一条 HumanMessage） | 纯字符串 |
| 输出 | `AIMessage`（含 content / tool_calls / usage_metadata） | 纯字符串 |
| 系统指令 | 用 `SystemMessage` 表达 | 只能拼进 prompt 文本 |
| 工具调用 | 原生支持（`bind_tools` / `tool_calls`） | 不支持 |
| 流式 | `AIMessageChunk`，可累加 | 字符串片段 |
| 1.x 状态 | 推荐，`init_chat_model` 统一入口 | 主包已移除，不建议使用 |

统一入口是 `langchain.chat_models.init_chat_model`，它的签名（本机 `inspect.signature` 真实输出）为：

```text
(model: 'str | None' = None, *, model_provider: 'str | None' = None,
 configurable_fields: "Literal['any'] | list[str] | tuple[str, ...] | None" = None,
 config_prefix: 'str | None' = None, **kwargs: 'Any') -> 'BaseChatModel | _ConfigurableModel'
```

也就是说模型名与供应商可以分开给：`init_chat_model("openai:gpt-4o-mini")` 与 `init_chat_model("gpt-4o-mini", model_provider="openai")` 等价，其余 `**kwargs`（`temperature`、`timeout`、`max_retries`、`api_key` 等）直接透传给具体集成类。

```python
from langchain.chat_models import init_chat_model

# 真实项目写法（本机无 key，未执行）
model = init_chat_model(
    "openai:gpt-4o-mini",
    temperature=0,
    timeout=30,
    max_retries=2,
)

# 本机可执行写法：本地假模型
from langchain_core.language_models.fake_chat_models import FakeListChatModel

fake = FakeListChatModel(responses=["df -h 看挂载点，du 定位大目录。"])
print(type(fake.invoke("磁盘满了怎么排查？")).__name__)
```

本机真实输出：

```text
返回类型: AIMessage | type: ai
text: df -h 看挂载点，du 定位大目录。
content_blocks: [{'type': 'text', 'text': 'df -h 看挂载点，du 定位大目录。'}]
usage_metadata: None
response_metadata: {}
```

注意 `usage_metadata` 为 `None`：假模型不产生 token 计数。真实模型（OpenAI / Anthropic / Gemini 等）会在这一字段里给出 `input_tokens` / `output_tokens` / `total_tokens`，计费与成本核算就读它。

```text
1. 1.x 只有一条主路：BaseChatModel（chat 模型），补全模型已从主包移除
2. 优先用 init_chat_model，字符串 "provider:model" 或 model_provider 参数二选一
3. 输入字符串会被自动包成一条 HumanMessage，输入消息列表则原样透传
4. 输出永远是 AIMessage，取文本优先用 .text，取结构化内容用 .content_blocks
5. usage_metadata 需要真实供应商返回，假模型上是 None
6. temperature / timeout / max_retries 等参数直接透传给具体集成类
```

## 消息类型与内容块

消息是上下文的原子单位，四个角色对应四种职责：`SystemMessage` 定行为与约束（只在开头出现一次），`HumanMessage` 是用户输入，`AIMessage` 是模型输出（同时承载 `tool_calls`），`ToolMessage` 是工具执行结果（必须带 `tool_call_id` 与对应的调用配对）。写法有两种：消息对象与 OpenAI chat completions 风格的 dict，`convert_to_messages` 负责把 dict 转成对象。

```python
from langchain_core.messages import (
    AIMessage, HumanMessage, SystemMessage, ToolMessage, convert_to_messages,
)

sys_msg = SystemMessage("你是运维助手，只回答与线上故障相关的问题。")
hum_msg = HumanMessage("订单服务 502 了，怎么办？", name="alice", id="msg_001")
ai_msg = AIMessage("先看网关错误率和上游超时日志。")
tool_msg = ToolMessage(content='{"error_rate": 0.42}', tool_call_id="call_abc")
for m in [sys_msg, hum_msg, ai_msg, tool_msg]:
    print(f"{m.type:9s} id={str(m.id)[:12]:13s} content={m.content!r}")

dict_msgs = [
    {"role": "system", "content": "你是运维助手。"},
    {"role": "user", "content": "磁盘满了怎么排查？"},
]
for m in convert_to_messages(dict_msgs):
    print(type(m).__name__, "|", m.content)
```

本机真实输出：

```text
=== 1. 核心消息类型 ===
system    id=None          content='你是运维助手，只回答与线上故障相关的问题。'
human     id=msg_001       content='订单服务 502 了，怎么办？'
ai        id=None          content='先看网关错误率和上游超时日志。'
tool      id=None          content='{"error_rate": 0.42}'

=== 2. dict 写法 -> 消息对象 ===
SystemMessage | 你是运维助手。
HumanMessage | 磁盘满了怎么排查？
```

`id` 是可选的：不传时为 `None`（真实模型返回的 `AIMessage` 会带上供应商给的响应 id，`HumanMessage` 的 `id` 主要用于追踪）。`name` 用来区分同一会话里的不同用户，但并非所有供应商都支持该字段。

四类消息的字段与典型用途：

| 消息类 | `type` | 关键字段 | 用途与注意点 |
| --- | --- | --- | --- |
| `SystemMessage` | `system` | `content` | 定行为、角色、输出格式约束；一般放列表首位 |
| `HumanMessage` | `human` | `content`、`name`、`id` | 用户输入；`name` 可标注发言人，供应商支持度不一 |
| `AIMessage` | `ai` | `content`、`content_blocks`、`tool_calls`、`usage_metadata` | 模型输出；手动构造可往历史里插「假装的」模型回复 |
| `ToolMessage` | `tool` | `content`、`tool_call_id` | 工具结果，必须与 `AIMessage.tool_calls[i]["id"]` 配对 |
| `AIMessageChunk` | `AIMessageChunk` | 同 `AIMessage` | 流式分片，可与同类 chunk 用 `+` 相加 |

`content_blocks` 是 1.x 新增的标准化内容视图：它不替代 `content`，而是把各家格式（Anthropic 的 block 数组、OpenAI 的 parts）归一化成 `{"type": "text", "text": ...}` 这样的结构，便于统一处理文本、图片、推理、引用等混合内容。

```text
1. 四类角色：system（定行为）/ human（用户）/ ai（模型）/ tool（工具结果）
2. 消息对象与 {"role": ..., "content": ...} 的 dict 写法等价，后者用 convert_to_messages 转换
3. ToolMessage 必须带 tool_call_id，且要与对应 AIMessage.tool_calls 的 id 一致
4. 取文本用 .text，需要结构化内容（多模态、推理块）用 .content_blocks
5. usage_metadata / response_metadata 只在真实模型返回时有意义
6. 模型是无状态的：多轮对话要把历史消息显式拼进 messages 列表
```

## 流式输出

流式的意义是首 token 时间（TTFT）而不是总时长：用户看到第一个字就开始读，感知延迟可以从 3 秒掉到 300 毫秒。接口层面，任何 Runnable 都实现 `stream()`，chat 模型返回的是 `AIMessageChunk` 序列，相邻分片可以用 `+` 拼回完整消息。

```python
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage

streamer = GenericFakeChatModel(messages=iter([AIMessage(content="定位顺序为 网关 应用 数据库")]))
chunks = []
for chunk in streamer.stream("排查顺序？"):
    chunks.append(chunk)
    print(f"  chunk[{len(chunks)}] {type(chunk).__name__} content={chunk.content!r}")

merged = chunks[0]
for c in chunks[1:]:
    merged = merged + c
print("拼接后:", merged.content, "| 拼接结果类型:", type(merged).__name__)
```

本机真实输出：

```text
=== 5. 流式输出（AIMessageChunk 逐块）===
  chunk[1] AIMessageChunk content='定位顺序为'
  chunk[2] AIMessageChunk content=' '
  chunk[3] AIMessageChunk content='网关'
  chunk[4] AIMessageChunk content=' '
  chunk[5] AIMessageChunk content='应用'
  chunk[6] AIMessageChunk content=' '
  chunk[7] AIMessageChunk content='数据库'
拼接后: 定位顺序为 网关 应用 数据库 | 拼接结果类型: AIMessageChunk
```

两个假模型的切块策略不同，本机实测确认（用来理解「分片边界由后端起决定，前端不能假设每个 chunk 是一个字」）：

```text
带空格的 content 流式结果:
   '定位顺序为'
   ' '
   '网关'
   ' '
   '应用'
   ' '
   '数据库'
无空格的 content 流式结果: ['没有空格的句子']
FakeListChatModel 流式结果: ['A', 'B']
```

`GenericFakeChatModel` 按空白切块（把空格也单独作为一个 chunk），内容里没有空白时只产出 1 个 chunk；`FakeListChatModel` 按字符切块。真实供应商的分片粒度同样各不相同，因此**只能靠 `+` 累加，不能靠切片索引**。

流式与回调组合起来能看到完整事件序列：

```python
import asyncio

async def run():
    async for ev in chain.astream_events({"service": "order-api"}, version="v2"):
        print(ev["event"])

asyncio.run(run())
```

```text
1. stream() 返回 AIMessageChunk 序列，用 + 累加得到完整消息，不要按索引切片
2. 分片粒度由后端起决定：本机 GenericFakeChatModel 按空白切、FakeListChatModel 按字符切
3. 流式的收益是首 token 时间，不是总时长；服务端要把它转成 SSE 或 WebSocket 帧
4. astream_events 给出带事件名的细粒度流（on_chat_model_stream、on_parser_stream 等）
5. 流式与结构化输出、工具调用可以共存，但解析器要能处理分片
6. 关闭流式用模型参数 streaming=False（LangChain 1.x 中集成类支持）
```

## 多模型切换

线上常见两种需求：按请求切换「便宜模型 / 强模型」，以及给同一次调用附加不同参数。前者用 `configurable_alternatives`（声明式，切换点写在链路上，运行时由 config 决定），后者用 `bind`（只在这一次调用生效）。

```python
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.runnables import ConfigurableField

cheap = FakeListChatModel(responses=["[小模型] 结论：重试一次即可。"])
strong = FakeListChatModel(responses=["[大模型] 结论：先回滚 v1.8.2，再查连接池。"])
router = cheap.configurable_alternatives(
    ConfigurableField(id="tier"), default_key="cheap", strong=strong
)
print(router.invoke("线上 502，怎么处理？", config={"configurable": {"tier": "cheap"}}).content)
print(router.invoke("线上 502，怎么处理？", config={"configurable": {"tier": "strong"}}).content)
```

本机真实输出（内容为本地假模型生成）：

```text
=== 2. 可配置模型：同一条链按 config 切换模型 ===
[小模型] 结论：重试一次即可。
[大模型] 结论：先回滚 v1.8.2，再查连接池。
```

同一份代码，只改 `config`，模型就换了——这是把「模型选择」从业务逻辑里抽出来的关键手法，配合配置中心或请求头即可做灰度。

常用模型参数与读回方式（本机构造对象、未发请求）：

```python
from langchain_openai import ChatOpenAI

oai = ChatOpenAI(
    model="gpt-4o-mini",
    api_key="sk-placeholder-never-use",  # 仅为构造对象，本机未发起任何网络调用
    temperature=0.2, max_tokens=512, timeout=30, max_retries=2,
)
print(oai.model_name, oai.temperature, oai.max_tokens, oai.request_timeout, oai.max_retries)
```

本机真实输出：

```text
model_name: gpt-4o-mini
temperature: 0.2 | max_tokens: 512
request_timeout: 30.0 | max_retries: 2
openai_api_base: None
streaming 默认: False

=== 5. bind()：给单次调用附加参数 ===
bind 后类型: _ChatModelBinding
```

`bind()` 返回 `_ChatModelBinding`（本质是 `RunnableBinding`），可以继续用 `|` 组合；`with_config` / `configurable_fields` 则用于把参数提升为运行时配置。

| 场景 | 写法 | 生效范围 |
| --- | --- | --- |
| 换模型（便宜/强） | `model.configurable_alternatives(ConfigurableField(id="tier"), ...)` | 运行时按 config |
| 单次调用改参数 | `model.bind(temperature=0.9, stop=["\n\n"])` | 仅该次调用 |
| 全部参数可配置 | `model.configurable_fields(temperature=ConfigurableField(id="temp"))` | 运行时按 config |
| 按条件路由到不同链 | `RunnableBranch`（见 LCEL 篇） | 整条链路 |
| 主模型失败切备用 | `model.with_fallbacks([backup])` | 异常时 |

```text
1. 多模型切换优先用 configurable_alternatives + config，别把 if/else 写进业务代码
2. bind() 只影响单次调用，适合临时调 temperature、stop 序列
3. configurable_fields 把参数暴露成运行时配置，配合配置中心做灰度
4. 模型参数名在各集成包里基本一致：model / temperature / max_tokens / timeout / max_retries
5. 构造 ChatOpenAI 时即使不发请求也会校验密钥，占位 key 必须在构造时显式传入
6. 回退链（with_fallbacks）与可配置切换解决的是两件事：可用性 vs 成本策略
```

## 本地模型接入

本地或私有化部署的模型服务（Ollama、vLLM、LM Studio、TGI、自建网关）几乎都提供 OpenAI 兼容的 `/v1/chat/completions` 接口，因此**统一用 `ChatOpenAI` 加 `base_url` 接入**是最省事的做法：不用为每个服务装一个集成包，参数与流式行为也一致。

```python
from langchain_openai import ChatOpenAI

# Ollama 默认端口 11434；api_key 只做非空校验，随便填
local = ChatOpenAI(
    model="qwen2.5:7b-instruct",
    base_url="http://127.0.0.1:11434/v1",
    api_key="ollama",
    temperature=0,
)
print(local.model_name, local.openai_api_base)

# vLLM / LM Studio / 自建网关同理，只换 base_url
vllm = ChatOpenAI(
    model="Qwen/Qwen2.5-7B-Instruct",
    base_url="http://127.0.0.1:8000/v1",
    api_key="EMPTY",
    timeout=120,
)
```

本机真实输出（仅构造对象；本机未启动 ollama 服务，因此未做真实推理）：

```text
model_name: qwen2.5:7b-instruct
openai_api_base: http://127.0.0.1:11434/v1
api_key 已设置: True
```

各种接入方式的取舍：

| 方式 | 依赖 | 适用 | 注意点 |
| --- | --- | --- | --- |
| `ChatOpenAI(base_url=...)` | `langchain-openai` | Ollama / vLLM / LM Studio / 自建网关 | 通用性最好；供应商专有字段（如 Ollama 的 `options`）需透传 |
| `langchain-ollama` 的 `ChatOllama` | 额外装包 | 需要 Ollama 专有参数（`num_ctx`、`keep_alive`） | 多一个依赖，但参数最贴服务端 |
| `init_chat_model("ollama:qwen2.5")` | 对应集成包 | 想统一走字符串入口 | 需要已安装对应集成包，否则报错提示装包 |
| 自建 HTTP 适配器 | 无 | 网关鉴权、多租户路由、审计 | 要自己维护流式协议与错误码映射 |

```text
1. 本地模型首选 ChatOpenAI(base_url=...)，一套代码通吃 Ollama / vLLM / LM Studio
2. api_key 通常只做非空校验，填 "ollama" 或 "EMPTY" 即可
3. 需要 Ollama 专有参数（num_ctx 等）时再换 langchain-ollama 的 ChatOllama
4. 本地模型上下文窗口普遍偏小，长历史要配合裁剪（见记忆与会话篇）
5. 本地服务没有真实并发保护，压测前先确认服务端并发与显存
6. 部署形态与运维细节见 Ollama 篇章，不在本篇展开
```

## 应用场景实战

### 场景一：多模型降级链

企业场景里最常见的可靠性设计：主模型（云端强模型）超时就自动切到备用模型（本地部署的小模型），保证「降级但不断服」。下面的实现把「重试 2 次 + 降级到备用」串成一条链，并用一个会抛错的假模型模拟超时。

```python
"""fallback_chain.py —— 主模型超时自动切备用模型"""
import time

from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda

prompt = ChatPromptTemplate.from_template("用一句话给出处置建议：{incident}")


class FlakyModel:
    """把「第 N 次调用必定失败」的假模型包装成 Runnable，用于演练降级。"""

    def __init__(self, fail_times: int):
        self.fail_times = fail_times
        self.calls = 0

    def __call__(self, _input):
        self.calls += 1
        if self.calls <= self.fail_times:
            raise TimeoutError(f"主模型第 {self.calls} 次调用超时")
        return "主模型：回滚 v1.8.2"


primary = RunnableLambda(FlakyModel(fail_times=2))
# 备用：本地 Ollama 通过 OpenAI 兼容端点接入（本机未启动 ollama，这里用假模型代表其返回值）
backup = FakeListChatModel(responses=["备用模型（本地 qwen2.5）：先摘流量，再回滚 v1.8.2"])

resilient = primary.with_retry(stop_after_attempt=2, wait_exponential_jitter=False).with_fallbacks([backup])
chain = prompt | resilient | StrOutputParser()

t0 = time.perf_counter()
print("最终结论:", chain.invoke({"incident": "payment-api 502 突增，发布 v1.8.2 后开始"}))
print(f"整条链路耗时 {(time.perf_counter() - t0) * 1000:.1f} ms（含 2 次超时重试 + 1 次降级）")

print("\n=== 只保留回退、不做重试时的行为 ===")
no_retry = prompt | RunnableLambda(FlakyModel(fail_times=1)).with_fallbacks([backup]) | StrOutputParser()
print("第一次调用:", no_retry.invoke({"incident": "x"}))
```

### 场景二：把模型输出转成 SSE 帧

第二个场景是服务端最常见的交付形态：把 `stream()` 的输出转成 SSE 帧推给前端，同时给出首 token 延迟（TTFT）与总字符数，作为可观测指标上报。

```python
"""sse_stream.py —— 把模型流式输出转成 SSE 数据帧"""
import json
import time

from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_template("{question}")
model = FakeListChatModel(responses=["建议先回滚到 v1.8.1，再排查连接池配置与慢 SQL。"])


def sse_stream(question: str):
    """生成 SSE 数据帧；真实服务里把这个生成器交给 StreamingResponse 即可。"""
    t0 = time.perf_counter()
    first_token_ms = None
    full = []
    for chunk in (prompt | model).stream({"question": question}):
        text = chunk.text
        if not text:
            continue
        if first_token_ms is None:
            first_token_ms = (time.perf_counter() - t0) * 1000
        full.append(text)
        yield f"data: {json.dumps({'delta': text}, ensure_ascii=False)}\n\n"
    yield "data: " + json.dumps(
        {
            "_meta": {
                "ttft_ms": round(first_token_ms or 0, 2),
                "total_ms": round((time.perf_counter() - t0) * 1000, 2),
                "chars": len("".join(full)),
            }
        },
        ensure_ascii=False,
    ) + "\n\n"
    yield "data: [DONE]\n\n"


frames = list(sse_stream("payment-api 大面积 502，第一步做什么？"))
print("前 6 帧：")
for f in frames[:6]:
    print(f.rstrip())
print("...")
print("最后 2 帧：")
for f in frames[-2:]:
    print(f.rstrip())
print("\n总帧数:", len(frames))
```

本机真实输出（内容为本地假模型生成，且假模型按字符切块，真实模型分片更大）：

```text
前 6 帧：
data: {"delta": "建"}
data: {"delta": "议"}
data: {"delta": "先"}
data: {"delta": "回"}
data: {"delta": "滚"}
data: {"delta": "到"}
...
最后 2 帧：
data: {"_meta": {"ttft_ms": 11.92, "total_ms": 13.52, "chars": 29}}
data: [DONE]

总帧数: 31
```

## 最佳实践与踩坑记录

1. **统一用 `init_chat_model` 或 `ChatOpenAI(base_url=...)` 两种入口**：前者管多供应商切换，后者管所有 OpenAI 兼容端点；不要为每个服务引入一个集成包，依赖越少越稳。
2. **消息列表里只放「模型真需要看」的内容**：system 定约束、最近若干轮对话给上下文、工具结果按需回填；把整段日志塞进去不仅贵，还会让模型跑偏。
3. **流式接口一定要带 TTFT 与字符数指标**：只测总耗时无法定位「模型慢」还是「网络慢」；本机示例里 TTFT 与总时长都打在最后一帧的 `_meta` 里。
4. **模型参数集中在配置层管理**：`temperature`、`max_tokens`、`timeout`、`max_retries` 走配置中心，用 `configurable_fields` 暴露，避免散落在代码里。
5. **本地模型当作「降级选项」而非替代**：小模型的指令跟随与格式稳定性明显弱于云端大模型，凡是要求严格 JSON 的场景都要加解析校验与修复（见提示与输出解析篇）。
6. **把消息序列化后再落库**：`langchain_core.load` 的 `dumpd` / `load` 能把消息对象与普通 dict 互转，落库/回放都方便；但 `load()` 会实例化 Python 对象，**绝不要对不可信来源的数据调用它**。

坑 1：以为补全模型还能用，照着老例子写 `from langchain.llms import OpenAI`。

结论：1.x 的 `langchain` 主包不再提供补全模型入口，本机实测 `langchain.prompts` / `langchain.chains` / `langchain.memory` 全部 ImportError，`langchain` 顶层只导出 `['agents', 'chat_models', 'messages', 'tools']`。

原因：供应商侧基本只提供 chat 接口，1.x 把两条路收敛成一条。

解法：统一改用 `init_chat_model` 或具体 chat 集成类；确实需要老式补全行为，就用 `SystemMessage` + 单条 `HumanMessage` 模拟，不要再找 `BaseLLM`。

坑 2：前端按「每个 chunk 一个字」做打字机动画，遇到真实模型就显示卡顿或整段蹦出。

结论：分片粒度由后端起决定。本机实测 `GenericFakeChatModel` 按空白切块（连空格都单独成块）、`FakeListChatModel` 按字符切块，真实供应商又各不相同。

原因：各供应商的流式协议与缓冲策略不同，LangChain 只做归一化为 `AIMessageChunk`，不保证切分边界。

解法：前端只做字符串累加（`merged = merged + chunk`）后整体渲染，或按时间节流刷新；任何依赖 chunk 长度或索引的逻辑都要去掉。

坑 3：构造 `ChatOpenAI` 时以为不发请求就不需要 key，结果在 import 阶段就抛 `OpenAIError: Missing credentials`。

结论：本机实测，`ChatOpenAI(model="gpt-4o-mini", temperature=0.2)` 会直接抛 `openai.OpenAIError: Missing credentials. Please pass an api_key ... or set the OPENAI_API_KEY`。

原因：集成类在 `validate_environment` 中就会初始化 `openai.OpenAI` / `AsyncOpenAI` 客户端，构造即校验。

解法：构造时显式传 `api_key`（真实 key 走环境变量，或 `api_key="ollama"` 这类占位值用于本地端点）；在 CI 里用 `FakeListChatModel` 而不是构造真实集成类。

坑 4：把多轮对话直接拼字符串，结果 system 指令被历史淹没、模型开始跑偏。

结论：消息角色是模型判断优先级的重要信号，拼成一个大字符串后 system / user / assistant 的边界消失。

原因：chat 模型的训练与对齐都建立在角色化消息上，供应商侧也会对 system 位置做特殊处理。

解法：始终用消息列表，`SystemMessage` 只放在开头且只放一条，历史消息原样保留角色，超出窗口的部分用裁剪或摘要（见[[15.5-记忆与会话]]）。
