## 概述

Agent 的本质是「模型在循环里调用工具，直到任务完成」；LangChain 官方的说法是 **Agent = Model + Harness**，harness（外壳）是循环之外的一切：提示词、工具、中间件。LangChain 1.x 把入口收敛成一个 `create_agent()`，它返回的是一张编译好的 LangGraph 图（`CompiledStateGraph`，节点为 `model` 与 `tools`），所以 Agent 的持久化、流式、人在回路、时间旅行这些能力全部来自 LangGraph，而不是另一套独立实现。

```text
本篇主线：
1. 工具定义 —— @tool 装饰器、args_schema（Pydantic）、返回类型、ToolException
2. 调用循环 —— create_agent 的消息序列（AIMessage(tool_calls) -> ToolMessage -> AIMessage）
3. 类型选型 —— create_agent（1.x）/ langgraph.prebuilt.create_react_agent / langchain_classic.AgentExecutor
4. 错误处理 —— 普通异常 vs ToolException、handle_tool_error、ToolRetryMiddleware / ToolErrorMiddleware
5. 上下文注入 —— ToolRuntime（context_schema）而不是 langgraph 的 InjectedState
6. 人在回路 —— HumanInTheLoopMiddleware + interrupt + Command(resume=...)
```

本机实测环境：Ubuntu 24.04、Python 3.14.7，独立 venv `/root/.hermes/cache/scratch/lcvenv-b`，langchain 1.4.6、langchain-core 1.6.10、langgraph 1.2.15、langchain-classic 1.0.8。**本机没有任何模型 API key**，所有涉及模型的输出都由一个脚本化假模型（`ScriptedToolChatModel`，按预设脚本依次返回 `AIMessage`，实现 `bind_tools`）驱动——它验证的是编排、消息类型、状态流转是否正确，不代表模型能力。下文 `text` 块均为本机真实输出，包含真实的报错。

## 工具定义与 Schema

工具是「带类型签名和文档字符串的 Python 函数」。类型签名会被转成 JSON Schema 发给模型，docstring 变成模型看到的工具描述，所以两者的质量直接决定模型会不会用、能不能用对。LangChain 1.x 里 `@tool` 可从 `langchain.tools` 或 `langchain_core.tools` 导入（本机两者都可用，`langchain.tools` 是 1.x 的推荐入口）；参数名建议只用小写字母、数字、下划线，官方明确提示含空格或特殊字符的工具有供应商会拒绝。

```python
from typing import Literal
from pydantic import BaseModel, Field
from langchain.tools import tool
from langchain_core.tools import ToolException

@tool
def get_weather(city: str, units: Literal["celsius", "fahrenheit"] = "celsius") -> str:
    """查询指定城市当前天气。

    Args:
        city: 城市名，例如 Beijing
        units: 温度单位
    """
    return f"{city} 晴，26 {units}"

# 复杂参数用 Pydantic 模型 + Field 约束（正则、枚举、默认值都会进 Schema）
class RefundInput(BaseModel):
    """退款单查询参数"""
    order_id: str = Field(description="订单号，形如 ORD-2026-0001", pattern=r"^ORD-\d{4}-\d{4}$")
    reason: str = Field(default="", description="退款原因")

@tool("query_refund", args_schema=RefundInput, description="按订单号查询退款状态")
def query_refund(order_id: str, reason: str = "") -> str:
    return f"订单 {order_id} 的退款状态：处理中"
```

本机真实输出：

```text

description: 查询指定城市当前天气。  Args:     city: 城市名，例如 Beij ...
args (JSON Schema): {"city": {"title": "City", "type": "string"}, "units": {"default": "celsius", "enum": ["celsius", "fahrenheit"], "title": "Units", "type": "string"}}
直接调用: Beijing 晴，26 celsius

  String should match pattern '^ORD-\d{4}-\d{4}$
```

| 定义方式 | 写法 | 适用 |
|---|---|---|
| `@tool` 普通函数 | 类型注解自动生成 Schema | 参数少、结构简单 |
| `@tool(args_schema=Model)` | Pydantic 模型定义入参 | 参数多、需要正则/枚举/描述 |
| `StructuredTool.from_function()` | 不写装饰器，显式构造 | 动态生成工具、包装已有函数 |
| 继承 `BaseTool` | 自己实现 `_run` | 需要状态、需要异步与同步双实现 |
| 传 dict / callable 给 `create_agent` | `tools=[{"name": ..., "parameters": {...}}]` | 从外部配置动态装配工具 |

```text
要点：
- 类型注解是协议的一部分：缺注解 -> Schema 报错；注解与实际行为不符 -> 模型按错误的约定调用
- docstring 是给模型看的「使用说明书」，写清「什么时候用、返回什么、有什么限制」
- 参数名用 snake_case、纯 ASCII；name 默认取函数名，重命名用 @tool("new_name")
- 参数校验（pattern/enum/范围）尽量放在 args_schema 里，模型看不到的校验放到函数体内并抛 ToolException
- 工具返回建议是 str 或可序列化对象：返回结构给模型看时可 json.dumps 成字符串，便于模型解析
```

## 工具调用循环

`create_agent()` 编译出的图只有两个业务节点：`model` 与 `tools`。`model` 节点调用模型；如果 `AIMessage.tool_calls` 非空就转到 `tools` 节点执行，工具结果以 `ToolMessage` 回填消息列表，再回到 `model`，直到模型不再请求工具（或触发中间件限制）。这个循环是理解一切 Agent 行为的基础：多轮工具调用、并行工具调用、循环上限、审批中断都发生在这里。

```python
from langchain.agents import create_agent
from langchain_core.messages import HumanMessage

agent = create_agent(
    model=model,                 # 字符串 "provider:model" 或已初始化的模型实例
    tools=[get_weather, query_refund],
    system_prompt="你是运维助手。",
)
result = agent.invoke({"messages": [HumanMessage("上海和北京天气怎么样？")]})
print(result["messages"][-1].content)
```

本机真实输出：

```text
最终消息数: 5
  HumanMessage: 上海和北京天气怎么样？
  AIMessage: tool_calls=[('get_weather', {'city': 'Shanghai'}), ('get_weather', {'city': 'Beijing', 'units': 'fahrenheit'})]
  ToolMessage(get_weather): Shanghai 晴，26 celsius  tool_call_id=call_1
  ToolMessage(get_weather): Beijing 晴，26 fahrenheit  tool_call_id=call_2
  AIMessage: 上海 26 celsius，北京 26 fahrenheit。
模型实际被绑定的工具: ['get_weather', 'query_refund']
agent 是编译后的图: CompiledStateGraph
图的节点: ['__end__', '__start__', 'model', 'tools']
```

一次模型回复里的多个 `tool_calls` 会被并行执行（本机两条 `ToolMessage` 的 `tool_call_id` 分别对应 `call_1`/`call_2`）；`tools=[]` 时图里不会有 `tools` 节点，等价于「只有一次模型调用」：

```text
无工具时节点: ['__end__', '__start__', 'model']
tools=[] 仍可正常调用: ok
显式传 middleware=None -> TypeError: 'NoneType' object is not iterable （默认值是空元组，不能传 None）
```

```text
要点：
- 消息序列固定为 Human -> AI(tool_calls) -> ToolMessage* -> AI(final)，调试时先看 ToolMessage 数量对不对
- tool_call_id 把请求和结果配对，并行调用时靠它区分，不要自己拼字符串去匹配
- 工具执行失败时错误文本会作为 ToolMessage 回到模型（前提是错误类型被框架接住，见下一节）
- Agent 是编译后的 LangGraph 图，可以用 get_graph().nodes 检查结构，也能塞进更大的图当子图
- 循环次数要有上限：默认图没有硬上限（中间件 ModelCallLimitMiddleware / ToolCallLimitMiddleware 负责收口）
```

## Agent 类型与选型

LangChain 1.x 只保留一个通用入口 `create_agent`，老版本的 ReAct、OpenAI Functions、XML Agent、`initialize_agent` 全部移到了 `langchain-classic`（`langchain_classic.agents`），React 预置实现则在 `langgraph.prebuilt.create_react_agent`。本机实测的导入可用性如下，迁移时以这张表为准。

| 入口 | 包 | 状态 | 说明 |
|---|---|---|---|
| `create_agent` | `langchain.agents` | 1.x 推荐 | 返回 `CompiledStateGraph`，配中间件扩展 |
| `create_react_agent` | `langgraph.prebuilt` | 可用 | LangGraph 侧预置 ReAct，不依赖 LangChain 的 Agent 层 |
| `AgentExecutor` / `create_tool_calling_agent` | `langchain_classic.agents` | 旧版 | 0.x 写法，`langchain.agents` 已不再导出 |
| `ToolNode` / `tools_condition` | `langgraph.prebuilt` | 可用 | 手写图时复用的工具执行节点与条件边 |

```python
# 1.x（推荐）
from langchain.agents import create_agent
agent = create_agent(model="openai:gpt-4.1-mini", tools=[get_weather], system_prompt="...")

# LangGraph 预置
from langgraph.prebuilt import create_react_agent
agent2 = create_react_agent(model=model, tools=[get_weather])

# 旧版（迁移参考，新代码不要再用）
from langchain_classic.agents import AgentExecutor, create_tool_calling_agent
```

本机真实输出：

```text
langchain.agents 导出: ['AgentState', 'create_agent', 'factory', 'middleware', 'structured_output']
langchain_classic.agents 可用: AgentExecutor, create_tool_calling_agent, create_react_agent, create_openai_tools_agent, ...
langchain.agents.AgentExecutor -> ImportError: cannot import name 'AgentExecutor' from 'langchain.agents'
```

```text
要点：
- 新代码统一用 langchain.agents.create_agent；看到 AgentExecutor 的教程基本是 0.x，导入会直接 ImportError
- 需要精细控制循环结构时用 LangGraph 手写 StateGraph + ToolNode，不要用中间件去模拟控制流
- create_agent 的 model 可以传字符串（走 init_chat_model 解析）或已初始化实例，后者才能自定义超时/重试参数
- checkpointer 决定是否有短期记忆：不传则每次 invoke 都是全新对话（连 thread_id 也没意义）
- 0.x -> 1.x 迁移主要是三件事：导入路径、Agent 入口、中间件替代回调
```

## 中间件与错误处理

工具出错是常态（上游 503、参数非法、权限不足），处理方式决定 Agent 是「优雅降级」还是「整轮崩掉」。关键区别只有一条：**只有 `ToolException` 会被默认的 `handle_tool_error` 机制接住；其他异常会直接抛穿整个 agent 运行**。LangChain 1.x 用中间件承载重试、限流、PII 脱敏、摘要等横切逻辑，`langchain.agents.middleware` 下有一批现成的。

```python
from langchain.agents.middleware import ToolRetryMiddleware, ModelCallLimitMiddleware, ToolCallLimitMiddleware
from langchain_core.tools import ToolException

# 1) 工具内抛 ToolException + 三种 handle_tool_error 写法
@tool
def divide(a: float, b: float) -> float:
    """做除法"""
    if b == 0:
        raise ToolException("除数不能为 0")
    return a / b

divide.model_copy(update={"handle_tool_error": "计算失败，请检查除数"})     # 固定文案
divide.model_copy(update={"handle_tool_error": lambda e: f"失败：{e}"})     # 由函数生成
divide.model_copy(update={"handle_tool_error": False})                     # 继续向上抛

# 2) 中间件兜住瞬时故障与失控循环
agent = create_agent(
    model=model,
    tools=[flaky_api],
    middleware=[
        ToolRetryMiddleware(max_retries=4, backoff_factor=0.0, retry_on=(RuntimeError,)),
        ModelCallLimitMiddleware(run_limit=6, exit_behavior="end"),
        ToolCallLimitMiddleware(run_limit=10, exit_behavior="end"),
    ],
)
```

本机真实输出：

```text
默认（不处理）: ToolException -> 除数不能为 0
handle_tool_error=函数: 工具执行失败：除数不能为 0
handle_tool_error=字符串: 计算失败，请检查除数
handle_tool_error=False -> 抛给调用方: 除数不能为 0

ModelCallLimitMiddleware: (*, thread_limit: 'int | None' = None, run_limit: 'int | None' = None, exit_behavior: "Literal['end', 'error']" = 'end') -> 'None'
ToolRetryMiddleware: (*, max_retries: 'int' = 2, tools: 'list[BaseTool | str] | None' = None, retry_on: 'RetryOn' = <function default_retry_on ...>, on_failure: 'OnFailure' = 'continue', ...)
工具实际被调用次数: 3
工具消息: ['第 3 次成功：x']
```

普通异常会炸穿整个运行（本机 pytest 实测，`test_plain_exception_in_tool_crashes_the_agent` 通过）：

```text
ValueError: a 不能超过 1000
E           During task with name 'tools' and id '35ac191b-04ce-8494-f424-d30be0a4825d'
```

| 场景 | 推荐做法 | 效果 |
|---|---|---|
| 业务性失败（订单不存在、余额不足） | 抛 `ToolException` + `handle_tool_error` | 错误文本回给模型，模型能换个说法继续 |
| 参数非法 | 交给 `args_schema` 校验 | 模型收到校验错误，通常会自动重试一次 |
| 上游瞬时故障（503、超时） | `ToolRetryMiddleware(retry_on=...)` | 自动重试并退避，业务代码不用写 try |
| 模型无限绕圈 | `ModelCallLimitMiddleware` / `ToolCallLimitMiddleware` | 到上限后按 `exit_behavior` 结束或报错 |
| 需要统一错误口径 | 自定义中间件 `wrap_tool_call` | 在一处收口日志、埋点、脱敏 |

```text
要点：
- 工具里只该抛 ToolException（或让 middleware 接管的异常类型），其他异常会中断整轮对话
- handle_tool_error 支持字符串/函数/False 三种取值，False 表示「继续往上抛」，不是「不处理」
- 重试只对幂等操作做：转账、发消息这类写操作不要配置自动重试，改成人机确认或幂等键
- 中间件按声明顺序嵌套执行，限流类放外层、日志类放内层，排错时才能看到真实调用次数
- create_agent(middleware=None) 会报 TypeError（默认是空元组），要清空就直接不传该参数
```

## 状态与运行时注入

工具经常需要「对话状态」或「本次调用的上下文」（用户 ID、租户、API key、功能开关），这些不能交给模型填。LangChain 1.x 的机制是给工具加一个 `runtime: ToolRuntime[Ctx]` 参数：它会被自动从 Schema 里剔除（模型看不到），运行时注入真实对象，`runtime.context` 就是调用方传入的 `context`，`runtime.state` 是当前图状态。注意 `langchain.tools.InjectedState` 实际来自 `langgraph.prebuilt.tool_node`，那是 LangGraph `ToolNode` 的标记，**`create_agent` 不识别它**（本机实测直接失败）。

```python
from dataclasses import dataclass
from langchain.agents import create_agent
from langchain.tools import ToolRuntime, tool

@dataclass
class Ctx:
    user_id: str

@tool
def whoami(runtime: ToolRuntime[Ctx]) -> str:
    """返回当前调用者身份与状态字段"""
    return f"user={runtime.context.user_id} state_keys={sorted(runtime.state.keys())}"

agent = create_agent(model=model, tools=[whoami], context_schema=Ctx)
agent.invoke({"messages": [HumanMessage("我是谁")]}, context=Ctx(user_id="u-42"))
```

本机真实输出：

```text
ToolRuntime: <class 'langgraph.prebuilt.tool_node.ToolRuntime'>
带 ToolRuntime 参数的工具，对外 JSON Schema: {} (runtime 参数被自动剔除，模型看不到它)
ToolRuntime 注入结果: ["user=u-42 state_keys=['messages']"]

langchain.tools.InjectedState 的真实来源: langgraph.prebuilt.tool_node
InjectedState 工具生成 JSON Schema 失败: PydanticInvalidForJsonSchema -> Cannot generate a JsonSchema for core_schema.IsInstanceSchema (InjectedState)
```

```text
要点：
- 用户身份、租户、密钥一律走 context/context_schema，不要让模型有机会编造或篡改
- ToolRuntime 参数会从 JSON Schema 中自动剔除，模型完全看不见，注入发生在框架内部
- runtime.state 是只读快照；要改状态就返回状态更新字典（由图的 reducer 合并）
- create_agent 不认 langgraph 的 InjectedState（本机实测 PydanticInvalidForJsonSchema），手写图用 ToolNode 时才用它
- thread_id 管会话（消息历史），context 管本次运行的业务数据，二者经常一起传，但职责不同
```

## 人在回路

高危操作（转账、删库、发邮件、下单）必须有人把关。LangChain 1.x 的 `HumanInTheLoopMiddleware(interrupt_on={...})` 在工具执行前中断，通过 LangGraph 的 `interrupt()` 把「工具名 + 参数 + 说明」抛给调用方；人工用 `Command(resume={"decisions": [...]})` 回到原处，决策类型由中断 payload 里的 `allowed_decisions` 给出（本机实测为 `approve` / `edit` / `reject` / `respond`）。这套机制要求 agent 配了 checkpointer，否则中断后无法恢复。

```python
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

agent = create_agent(
    model=model,
    tools=[send_email, transfer_funds],
    middleware=[HumanInTheLoopMiddleware(interrupt_on={"send_email": True, "transfer_funds": True})],
    checkpointer=InMemorySaver(),
)
cfg = {"configurable": {"thread_id": "pay-1"}}

paused = agent.invoke({"messages": [HumanMessage("给老板发月报")]}, cfg, version="v2")
print(paused.interrupts[0].value)             # action_requests / review_configs

agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}), cfg, version="v2")
agent.invoke(Command(resume={"decisions": [{"type": "reject", "message": "金额超权限"}]}), cfg, version="v2")
```

本机真实输出：

```text
中断对象: (Interrupt(value={'action_requests': [{'name': 'send_email', 'args': {'to': 'boss@corp.com', 'body': '月报'}, 'description': "Tool execution requires approval\n\nTool: send_email\nArgs: {'to': 'boss@corp.com', 'body': '月报'}"}], 'review_configs': [{'action_name': 'send_email', 'allowed_decisions': ['approve', 'edit', 'reject', 'respond']}]}, id='5f487182c1ea72db3dbae0a8d40f57df', response_schema=None),)
批准后最后一条消息: 邮件已发出。
线程状态快照数: 7
```

```text
要点：
- 中断前必须落检查点（checkpointer），否则 resume 找不到现场；InMemorySaver 只适合单进程调试
- 只对写操作配 interrupt_on，读操作也拦会让用户体验变差、也会放大延迟
- 中断 payload 里务必带足够上下文（工具名、参数、发起人），审批页面才能不做二次查询
- 审计日志写在真实执行路径上（工具函数内部），被拒绝的调用不应留下任何写入记录
- 超时要兜底：审批可能几小时没人处理，会话线程要能过期回收，别把状态无限期挂在那里
```

## 旧版 AgentExecutor 与迁移

0.x 时代的写法是「先造 Agent（`create_tool_calling_agent`），再包一层 `AgentExecutor`」，配置项散落在 `max_iterations`、`early_stopping_method`、`handle_parsing_errors`、`return_intermediate_steps` 上。1.x 用图 + 中间件替代了这些开关，行为更可组合。迁移时不必一次改完，但要知道两边语义的对应关系。

| 0.x | 1.x 对应 | 说明 |
|---|---|---|
| `AgentExecutor(agent, tools)` | `create_agent(model, tools)` | 返回编译图，直接 invoke |
| `max_iterations` | `ModelCallLimitMiddleware(run_limit=...)` | 循环/模型调用上限 |
| `max_execution_time` | 外层 `asyncio.wait_for` 或网关超时 | 图本身没有墙钟超时 |
| `handle_parsing_errors=True` | 工具抛 `ToolException` + `handle_tool_error` | 错误回到模型继续推理 |
| `return_intermediate_steps=True` | 直接读 `result["messages"]` | 中间消息本来就在状态里 |
| `AgentExecutor.stream_log` | `stream_mode="updates"` / `"messages"` | 流式语义统一到 LangGraph |

```text
要点：
- langchain.agents 在 1.x 只导出 create_agent / AgentState / middleware，AgentExecutor 已移到 langchain-classic
- 迁移顺序建议：先换导入与入口（跑通），再补中间件（限流、重试），最后清掉回调式埋点
- 旧代码里靠 callbacks 统计 token 的，1.x 直接读消息的 usage_metadata 更可靠
- return_intermediate_steps 的替代就是读 state，别再造一套中间结果结构
- create_react_agent（LangGraph 预置）在 1.x 仍可用，适合不想引入 Agent 层抽象的场景
```

## 应用场景实战

### 场景一：订单客服 Agent（参数校验 + 工具重试 + 多工具并行）

场景：客服机器人需要查订单（参数必须符合订单号格式）和查物流（上游不稳定，偶发 503）。要求：参数非法时让模型收到明确校验错误；瞬时故障自动重试；一次回复里并行调用两个工具以减少延迟。

```python
"""15.7 场景一：订单客服 Agent"""
import json
from typing import Literal

from pydantic import BaseModel, Field
from langchain_core.messages import HumanMessage
from langchain_core.tools import ToolException, tool
from langchain.agents import create_agent
from langchain.agents.middleware import ToolRetryMiddleware

ORDERS = {
    "ORD-2026-0001": {"status": "已发货", "amount": 399, "buyer": "u-1"},
    "ORD-2026-0002": {"status": "待发货", "amount": 1288, "buyer": "u-2"},
}


class OrderQuery(BaseModel):
    """订单查询参数"""
    order_id: str = Field(description="订单号，形如 ORD-2026-0001", pattern=r"^ORD-\d{4}-\d{4}$")
    detail: Literal["basic", "full"] = Field(default="basic", description="basic 只返回状态，full 含金额")


@tool("lookup_order", args_schema=OrderQuery, description="按订单号查询订单状态与金额")
def lookup_order(order_id: str, detail: str = "basic") -> str:
    o = ORDERS.get(order_id)
    if not o:
        raise ToolException(f"订单 {order_id} 不存在")     # 业务失败：交给框架转成 ToolMessage
    if detail == "basic":
        return f"{order_id} 状态：{o['status']}"
    return json.dumps({"order_id": order_id, **o}, ensure_ascii=False)


FAILS = {"n": 0}

@tool
def query_logistics(order_id: str) -> str:
    """查询物流轨迹（上游不稳定，前两次会 503）"""
    FAILS["n"] += 1
    if FAILS["n"] < 3:
        raise RuntimeError(f"物流上游 503（第 {FAILS['n']} 次）")
    return f"{order_id} 物流：已到上海分拨中心"


AGENT = create_agent(
    model=model,                       # 线上换成 ChatOpenAI 等真实模型
    tools=[lookup_order, query_logistics],
    system_prompt="你是订单客服，先查订单再查物流，不要说没查到就直接结束。",
    middleware=[ToolRetryMiddleware(max_retries=3, backoff_factor=0.0, retry_on=(RuntimeError,))],
)

out = AGENT.invoke({"messages": [HumanMessage("帮我查 ORD-2026-0001 的物流")]})
assert len([m for m in out["messages"] if m.__class__.__name__ == "ToolMessage"]) == 2
print(out["messages"][-1].content)
```

本机真实输出：


### 场景二：高危操作人在回路（审批 / 拒绝 + 审计）

场景：转账类工具必须人工审批。要求：审批人在中断 payload 里能看到工具名、参数与说明；批准后真实执行并落审计；拒绝时不产生任何写入，模型要能正常收尾。

```python
"""15.7 场景二：高危操作审批"""
from langchain_core.messages import AIMessage, HumanMessage, ToolMessage
from langchain_core.tools import tool
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

AUDIT = []

@tool
def transfer_funds(to_account: str, amount: int) -> str:
    """向指定账户转账（高危写操作，必须人工审批）"""
    AUDIT.append({"action": "transfer", "to": to_account, "amount": amount})
    return f"已向 {to_account} 转账 {amount} 元"


def build(script):
    return create_agent(
        model=scripted_model(script),
        tools=[transfer_funds],
        middleware=[HumanInTheLoopMiddleware(interrupt_on={"transfer_funds": True})],
        checkpointer=InMemorySaver(),          # 中断必须能落检查点
    )


# 批准路径
agent = build([...])
cfg = {"configurable": {"thread_id": "pay-1"}}
paused = agent.invoke({"messages": [HumanMessage("给供应商转 5 万")]}, cfg, version="v2")
print("审批项:", paused.interrupts[0].value["action_requests"][0])
print("允许的决策:", paused.interrupts[0].value["review_configs"][0]["allowed_decisions"])
agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}), cfg, version="v2")

# 拒绝路径
agent.invoke(Command(resume={"decisions": [{"type": "reject", "message": "金额超出权限，请走线下审批"}]}), cfg, version="v2")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 工具颗粒度按「一次业务动作」切，不按 API 切：一个 `refund_order(order_id, reason)` 比 `http_post(url, body)` 对模型友好得多。
2. 所有写操作工具都要有幂等键与审计日志，并把自动重试关掉——重试一次转账的代价远高于失败一次。
3. 给模型能用的工具越少越好（3~7 个起步），工具一多就上 `LLMToolSelectorMiddleware` 或拆子 Agent，否则选错率飙升。
4. 工具错误统一成 `ToolException` + `handle_tool_error`，前端拿到的错误口径一致，模型也能据此换策略。
5. 循环与成本都要有硬上限：`ModelCallLimitMiddleware` / `ToolCallLimitMiddleware`，再叠一层网关级超时。
6. 调试 Agent 先看消息序列（Human -> AI(tool_calls) -> ToolMessage* -> AI），再怀疑模型；90% 的「模型不听话」其实是工具 Schema 或错误处理写错了。

### 踩坑记录

```text
坑 1：工具里抛 ValueError，整个 agent.invoke 直接炸掉
结论：以为框架会像处理异常一样把错误交给模型，结果调用方拿到未捕获异常。
原因：默认的 handle_tool_error 只接住 ToolException（本机实测 pytest：ValueError 直接冒到顶层，
      错误信息里带着 "During task with name 'tools'"），普通异常不走这条路。
解法：工具内业务性失败一律 raise ToolException(...)，再按需配 handle_tool_error（字符串/函数/False）；
      外部依赖异常用 ToolRetryMiddleware(retry_on=(RuntimeError,)) 在框架层兜住。

坑 2：给工具加了 langgraph 的 InjectedState，create_agent 里报 PydanticInvalidForJsonSchema
结论：以为注入参数写错了名字，反复改类型注解。
原因：langchain.tools.InjectedState 实际来自 langgraph.prebuilt.tool_node，那是 LangGraph ToolNode 的标记，
      create_agent 生成工具 Schema 时无法为它生成 JSON Schema（本机实测报错原文：
      Cannot generate a JsonSchema for core_schema.IsInstanceSchema (InjectedState)）。
解法：create_agent 场景用 ToolRuntime[Ctx] 参数注入（本机实测 args 为 {}、runtime.context 可读）；
      只有手写 StateGraph + ToolNode 时才用 InjectedState。

坑 3：工具调用次数莫名其妙变多，以为是模型重复调用
结论：排查模型提示词与 temperature，忽略中间件配置。
原因：ToolRetryMiddleware 在「工具抛异常」时会重试，日志里看到的是重试后的成功记录，
      业务代码没有计数就以为是一次调用（本机实测一个前两次 503 的工具，最终被调用 3 次）。
解法：在工具函数里对每次真实执行打点计数（本文场景一就是这么统计的），
      并区分「业务失败（不应重试）」与「瞬时故障（应重试）」，用 retry_on 精确指定异常类型。

坑 4：给 create_agent 显式传 middleware=None，构造阶段直接 TypeError
结论：以为不传中间件等价于传 None。
原因：create_agent 的 middleware 默认值是空元组，函数体直接迭代它（本机实测
      TypeError: 'NoneType' object is not iterable）。
解法：不需要中间件就不要传这个参数；要给空列表用 middleware=[]。

坑 5：Agent 配了 interrupt 却没配 checkpointer，resume 时找不到中断现场
结论：以为 Command(resume=...) 用法写错了。
原因：中断与恢复依赖检查点（thread + checkpoint），没有 checkpointer 就没有可恢复的状态，
      InMemorySaver 也只能在单进程内有效。
解法：HITL 场景一律 compile(checkpointer=...) 并在 invoke 时带 thread_id；
      生产用持久化 checkpointer（SqliteSaver / PostgresSaver），重启后仍能恢复待审批会话。
```
