## 概述

LangChain 是构建 LLM 应用的 Python 框架，1.x 版本把自己重新定位成「Agent 框架」：官方文档一句话概括为 `Agent = Model + Harness`，即模型加上提示词、工具、中间件组成的运行时外壳，入口是 `langchain.agents.create_agent`。它向下依赖 **langchain-core**（Runnable 协议、消息、提示模板、输出解析器等稳定抽象），由 **LangGraph** 提供持久化与图执行，由 **LangSmith** 提供追踪与评测。理解 1.x 的关键是：**旧教程里的 `langchain.chains` / `langchain.memory` / `langchain.prompts` 已经不存在**，链式编排统一走 LCEL（`|` 组合 Runnable），会话持久化统一走 LangGraph checkpointer。

```text
本篇主线：
1. 定位 —— 1.x 是 Agent 框架（create_agent），不是「链的集合」；0.x 的 Chain 概念已让位给 LCEL 与 LangGraph
2. 包结构 —— langchain（薄壳，导出 agents/chat_models/messages/tools）/ langchain-core（抽象）/ 集成包（langchain-openai 等）/ langgraph
3. 版本 —— 本机实测 langchain 1.4.6 + langchain-core 1.6.10 + langgraph 1.2.15，Python 3.14.7
4. 分工 —— LangChain 写业务、LangGraph 管状态与持久化、LangSmith 管追踪评测
5. 迁移 —— langchain.prompts / langchain.chains / langchain.memory 等旧路径已移除，必须改导入
6. 生态 —— 与 LlamaIndex / Haystack / DSPy / smolagents / 原生 SDK 的边界
```

本机实测环境：Ubuntu 24.04、Python 3.14.7、独立 venv `/root/.hermes/cache/scratch/lcvenv-a`，包从清华镜像安装。本机**没有任何 LLM API key**，因此下文所有链路都用 `FakeListChatModel` / `GenericFakeChatModel` 等本地假模型（`langchain_core.language_models.fake_chat_models`）跑通，`text` 块中的输出全部是本机真实运行结果，凡是用假模型生成的内容都会标注，未在本机验证的部分也会写明。

## LangChain 定位与设计取舍

1.x 的核心变化是「不再鼓励你自己拼 Chain 类」。历史上 `LLMChain`、`SequentialChain`、`ConversationChain` 这类封装把提示词、模型、内存和输出解析绑在一起，参数互相打架且难以替换组件；1.x 的做法是只留两类东西：**可组合的组件**（提示模板、模型、解析器、检索器，全都实现 Runnable 协议）和**Agent 运行时**（`create_agent`）。想把多个组件串起来就用 LCEL 的 `|`；需要循环、分支、断点重放、人工介入就用 LangGraph；两者可以互相嵌套。

一个最小的 LCEL 链路只用了三段：提示模板 → 模型 → 解析器。

```python
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate

# FakeListChatModel: 按顺序返回预置字符串的本地假模型，不发起任何网络请求
model = FakeListChatModel(responses=["服务 A 的 P99 延迟为 820ms，高于阈值 500ms。"])

prompt = ChatPromptTemplate.from_messages(
    [
        ("system", "你是 SRE 值班助手，回答要给出可执行的结论。"),
        ("human", "请判断这条告警是否需要立刻处理：{alert}"),
    ]
)
chain = prompt | model | StrOutputParser()

env = {"alert": "service_a_p99_latency 820ms > 500ms 持续 5 分钟"}
print(chain.invoke(env))
```

本机真实输出（内容为本地假模型生成）：

```text
=== 最小链路（本地假模型生成）===
服务 A 的 P99 延迟为 820ms，高于阈值 500ms。

=== 链路结构 ===
ChatPromptTemplate(...messages=[SystemMessagePromptTemplate(prompt=PromptTemplate(template='你是 SRE 值班助手，回答要给出可执行的结论。')...), HumanMessagePromptTemplate(prompt=PromptTemplate(input_variables=['alert'], template='请判断这条告警是否需要立刻处理：{alert}'))])
| FakeListChatModel(metadata={'lc_versions': {'langchain-core': '1.6.10', 'langchain': '1.4.6'}}, responses=['服务 A 的 P99 延迟为 820ms，高于阈值 500ms。'])
| StrOutputParser()
输入 schema: ['alert']
输出 schema: <class 'langchain_core.output_parsers.string.StrOutputParserOutput'>
```

`chain.input_schema` 只暴露 `alert` 一个变量，`output_schema` 是解析器的输出类型——这是 1.x 的一个实用之处：链路自带输入输出契约，可以在服务层直接做参数校验。

另一个方向是 Agent：同一个模型，加上工具和中间件，就得到一个能自己决定「要不要再调用一次工具」的循环。

```python
from langchain.agents import create_agent
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=FakeListChatModel(responses=["收到，已记录"]),  # 真实项目：model="openai:gpt-4o-mini"
    tools=[],
    system_prompt="你是运维助手",
    checkpointer=InMemorySaver(),
)
out = agent.invoke(
    {"messages": [{"role": "user", "content": "帮我登记一条告警"}]},
    {"configurable": {"thread_id": "demo"}},
)
print(sorted(out.keys()), out["messages"][-1].content)
```

本机真实输出：

```text
create_agent 返回类型: CompiledStateGraph
MRO: ['CompiledStateGraph', 'Pregel', 'PregelProtocol', 'Runnable', 'ABC']
可用方法（Runnable 协议）: ['invoke', 'stream', 'batch', 'ainvoke', 'astream']
state keys: ['messages']
最后一条: AIMessage 收到，已记录

=== stream_mode='updates' 的块结构 ===
chunk keys: ['model'] -> ['dict']
```

`create_agent` 返回的 `CompiledStateGraph` 继承自 `Pregel`，而 `Pregel` 又是 `Runnable`——所以 Agent 本身也能被 `|` 组合进 LCEL 链路，这是 1.x 里「LangChain 与 LangGraph 不是两套东西」的直接证据。

```text
1. 1.x 的抽象只有两层：可组合组件（Runnable）+ Agent 运行时（create_agent）
2. 组件间用 | 组合成 RunnableSequence，链路本身仍是 Runnable，可继续被组合
3. 需要状态、循环、断点重放时用 create_agent 或自建 LangGraph 图，而不是自己写 while 循环
4. chain.input_schema / output_schema 给出链路契约，可在 API 层做校验
5. 0.x 的 Chain 类（LLMChain 等）在 1.x 已移除，不要照抄旧教程
6. 链路与 Agent 都是惰性的：定义时不执行，invoke / stream / batch 才触发
```

## 包结构与版本矩阵

1.x 的包边界很清楚：**langchain** 是薄壳，只导出 `agents`、`chat_models`、`messages`、`tools` 四个命名空间；**langchain-core** 放所有稳定抽象与基类，业务代码里 `from langchain_core.xxx import ...` 才是常态；**第三方集成**拆成独立包（`langchain-openai`、`langchain-anthropic`、`langchain-ollama` 等），按需安装；**langchain-community** 是历史遗留的社区集成集合，官方已宣布进入收尾阶段。

```text
3. 集成必须单独装包：langchain-openai / langchain-ollama / langchain-anthropic 等
4. langchain-community 已进入 sunset 阶段，仅作过渡
5. 用 pip show <pkg> 而不是用记忆确认版本，1.x 各包版本号并不对齐（1.4.6 / 1.6.10 / 0.4.2 / 1.7.2）
6. 安装走镜像可显著提速：pip install -i https://pypi.tuna.tsinghua.edu.cn/simple
```

## LangGraph 与 LangSmith 的分工

三个东西常被混为一谈，边界其实很清晰：**LangChain** 提供组件与 Agent 外壳，管「一次调用怎么拼提示、怎么解析输出」；**LangGraph** 提供有状态的图执行引擎，管「多步之间状态怎么存、断了怎么续跑、要不要停下来等人审批」；**LangSmith** 是外部服务，管的是一条请求从入口到出口每一步的追踪、数据集与评测。

从实测可以看出这层关系不是比喻：`create_agent` 返回的 `CompiledStateGraph` 的 MRO 里就有 `Pregel` 与 `Runnable`，状态放在 `{"messages": [...]}` 里，持久化由 checkpointer 负责。

```python
# 同一个 Agent：换 checkpointer 就换了持久化后端
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(model=model, tools=[], checkpointer=InMemorySaver())
agent.invoke(
    {"messages": [{"role": "user", "content": "我叫 alice"}]},
    {"configurable": {"thread_id": "t-1"}},   # thread_id 就是会话身份
)
```

本机真实输出（thread 隔离验证，内容为本地假模型生成）：

```text
=== 8. LangGraph checkpointer：1.x 官方推荐的会话记忆 ===
thread t-1 第一条: 已记录：alice 负责支付组
thread t-1 累计消息数: 4
thread t-2 消息数（会话隔离）: 2
```

LangSmith 的开关是环境变量，不改代码即可开启追踪：

```bash
export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY="lsv2_..."       # 从 smith.langchain.com 获取
export LANGSMITH_PROJECT="payment-agent"  # 可选，默认 default
```

| 维度 | LangChain | LangGraph | LangSmith |
| --- | --- | --- | --- |
| 形态 | Python 库 | Python 库（LangChain 的依赖） | 托管服务（也有自托管版） |
| 解决的问题 | 组件组装与 Agent 外壳 | 有状态编排、持久化、人工介入 | 追踪、数据集、评测、监控 |
| 关键 API | `create_agent`、`|` 组合、`init_chat_model` | `StateGraph`、`checkpointer`、`thread_id` | 环境变量 + SDK，无侵入 |
| 是否联网 | 否（除模型调用本身） | 否 | 是（上报 trace） |
| 最小依赖 | langchain-core | langgraph | langsmith（随 core 安装） |

```text
1. LangChain 管「一次调用怎么拼」，LangGraph 管「多步之间状态怎么存」，LangSmith 管「出了什么事」
2. create_agent 本身就是 LangGraph 的 CompiledStateGraph，MRO 含 Pregel 与 Runnable
3. thread_id 是 LangGraph 里的会话主键，换个 thread_id 就是另一段对话
4. LangSmith 通过环境变量开启，不改业务代码；未配置 key 时 SDK 静默跳过
5. 只想跑通本地开发时不需要 LangSmith，但线上排查离了它基本没戏
6. 三者版本独立演进，升级时用 pip show 各自确认
```

## 生态与替代方案

LangChain 的优势是集成面最广、抽象层最厚；代价是抽象多、版本变化快，容易在「框架用法」上花掉本该用在业务上的时间。选型时按实际需求挑最薄的工具往往更划算。

| 方案 | 核心抽象 | 适合场景 | 不适合场景 |
| --- | --- | --- | --- |
| LangChain + LangGraph | Runnable / Agent / 图 | 需要多模型、多工具、有状态流程、人工介入 | 只调一次模型就完事 |
| 原生 SDK（openai / anthropic） | 直接 HTTP 客户端 | 单一供应商、逻辑简单、要极致可控 | 要在多家模型间切换、要统一流式与工具调用 |
| LlamaIndex | 索引与检索为中心 | 文档问答、RAG 为主的应用 | 复杂 Agent 循环、状态机 |
| Haystack | Pipeline 组件图 | 传统 NLP 流水线 + 检索 | 需要 LLM Agent 自动决策 |
| DSPy | 声明式程序 + 自动优化提示 | 有可量化指标、想自动调提示/权重 | 一次性脚本、无评测数据 |
| smolagents | 极简 Code Agent | 想让模型直接写代码调工具、依赖越少越好 | 需要复杂中间件与持久化 |

```text
1. 选型先看「需要几层」：单供应商单调用 -> 原生 SDK；多供应商 + 工具 -> LangChain
2. RAG 为主、Agent 为辅 -> LlamaIndex 更省事；Agent 为主 -> LangChain + LangGraph
3. 有明确评测指标、想自动优化提示词 -> DSPy，但先准备数据集
4. LangChain 的全部价值都在「组件可替换」上；如果项目永远不换模型，它带来的抽象成本大于收益
5. 生态差异不是排他的：LangChain 可以只用 langchain-core 的组件，不引入 Agent
6. 无论选哪个，先统一消息与工具调用的数据格式，迁移成本主要在这里
```

## 安装与首个可运行示例

推荐做法是给每个项目建独立 venv 并锁定版本，避免全局环境污染与版本漂移。下面是本机的真实安装过程（含镜像加速）。

```bash
# 1. 建独立环境（本机 python3 为 3.14.7，LangChain 1.x 要求 Python 3.10+）
python3 -m venv /root/.hermes/cache/scratch/lcvenv-a

# 2. 用清华镜像安装核心包与 OpenAI 集成（国内直连 pypi 很慢）
/root/.hermes/cache/scratch/lcvenv-a/bin/pip install -q \
  -i https://pypi.tuna.tsinghua.edu.cn/simple \
  langchain langchain-core langchain-community langchain-openai

# 3. 确认版本（不要凭记忆，用 pip show）
/root/.hermes/cache/scratch/lcvenv-a/bin/pip show langchain langchain-core langgraph
```

本机真实输出：

```text
DONE
Name: langchain
Version: 1.4.6
Name: langchain-core
Version: 1.6.10
Name: langchain-community
Version: 0.4.2
Name: langchain-openai
Version: 1.7.2
```

官方推荐的应用骨架（接真实模型时把假模型换成 `init_chat_model`）：

```python
# app.py —— 最小可用骨架：提示模板 + 模型 + 解析器 + 环境变量取 key
import os

from langchain.chat_models import init_chat_model
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate

model = init_chat_model(
    "openai:gpt-4o-mini",             # provider:model 写法；也可用 model_provider= 参数指定
    temperature=0,
    timeout=30,
    max_retries=2,
    api_key=os.environ["OPENAI_API_KEY"],  # 不要把 key 写进代码或提交进仓库
)

prompt = ChatPromptTemplate.from_messages(
    [("system", "你是运维助手，回答不超过三句。"), ("human", "{question}")]
)
chain = prompt | model | StrOutputParser()

if __name__ == "__main__":
    print(chain.invoke({"question": "P99 延迟告警第一步查什么？"}))
```

```text
1. 永远给项目建独立 venv；本机 3.14.7 可用，LangChain 1.x 最低要求 Python 3.10
2. 国内装包走清华镜像，命令里显式写 -i https://pypi.tuna.tsinghua.edu.cn/simple
3. API key 走环境变量或密钥管理服务，绝不硬编码
4. 先跑 langchain-core 的最小链路（prompt | model | parser），确认环境没问题再引入 Agent
5. 没有 key 时用 FakeListChatModel 验证链路结构，能覆盖 90% 的编排 bug
6. 版本以 pip show 为准写进 requirements；LangChain 各子包版本号不对齐
```

## 版本迁移要点

从 0.x 迁到 1.x 的主要工作量在**导入路径**：`langchain.prompts`、`langchain.chains`、`langchain.memory`、`langchain.output_parsers`、`langchain.schema` 全部不存在了。下表是实测确认可用的映射关系。

| 0.x 导入 | 1.x 写法 | 说明 |
| --- | --- | --- |
| `langchain.prompts` | `langchain_core.prompts` | 提示模板移入 core |
| `langchain.schema` / `langchain.schema.messages` | `langchain_core.messages` | `langchain.messages` 也可（便捷导出） |
| `langchain.schema.runnable` | `langchain_core.runnables` | Runnable 协议 |
| `langchain.output_parsers` | `langchain_core.output_parsers` | 解析器移入 core |
| `langchain.callbacks` | `langchain_core.callbacks` | 回调基类 |
| `langchain.chains` | `langchain.agents.create_agent` 或自行用 LCEL 组合 | Chain 类已移除 |
| `langchain.memory` | LangGraph checkpointer（如 `InMemorySaver`） | 记忆改由状态机承载 |
| `langchain.vectorstores` | 独立集成包（如 `langchain-chroma`） | 向量库也拆包了 |
| `langchain.chat_models.ChatOpenAI` | `langchain_openai.ChatOpenAI` | 或 `langchain.chat_models.init_chat_model` |
| `langchain.embeddings.OpenAIEmbeddings` | `langchain_openai.OpenAIEmbeddings` | 同上 |

迁移前先用脚本扫一遍存量代码，比逐个文件人肉查要可靠得多。

## 应用场景实战

### 场景一：CI 环境自检脚本

上线前最常见的故障是「本地能跑、CI 跑不起来」，根因基本是版本漂移或缺依赖。把这个脚本挂进流水线的第一步，能在几秒内定位是环境问题还是代码问题。它的价值在于**不依赖任何 API key**，因此可以在不花钱、不联外网的 CI 里跑。

```python
"""ci_selfcheck.py —— CI 第一步：校验版本矩阵并跑通最小链路，失败退出非零码"""
import sys
import importlib.metadata as md

PINNED = {
    "langchain": "1.4.6",
    "langchain-core": "1.6.10",
    "langchain-community": "0.4.2",
    "langchain-openai": "1.7.2",
}


def check_versions() -> list[str]:
    problems = []
    for pkg, expected in PINNED.items():
        try:
            actual = md.version(pkg)
        except md.PackageNotFoundError:
            problems.append(f"缺少依赖 {pkg}")
            continue
        if actual != expected:
            problems.append(f"{pkg} 版本不一致：期望 {expected}，实际 {actual}")
        else:
            print(f"[ok] {pkg}=={actual}")
    return problems


def check_smoke() -> list[str]:
    """不依赖任何 API key：用本地假模型跑通 prompt -> model -> parser 三段链路。"""
    from langchain_core.language_models.fake_chat_models import FakeListChatModel
    from langchain_core.output_parsers import StrOutputParser
    from langchain_core.prompts import ChatPromptTemplate

    chain = (
        ChatPromptTemplate.from_template("ping {who}")
        | FakeListChatModel(responses=["pong"])
        | StrOutputParser()
    )
    got = chain.invoke({"who": "langchain"})
    if got != "pong":
        return [f"冒烟链路返回异常：{got!r}"]
    print("[ok] 冒烟链路 prompt | model | parser 通过")
    return []


def main() -> int:
    problems = check_versions() + check_smoke()
    if problems:
        print("\n自检失败：")
        for p in problems:
            print(" -", p)
        return 1
    print("\n自检通过：环境可用于构建 LangChain 1.x 应用")
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

### 场景二：存量项目迁移扫描

第二个场景是迁移前的一次性盘点：老项目里通常散落着几十处旧导入，人工排查既慢又容易漏。用下面的扫描器一次性列出「文件:行号 旧路径 → 新路径」，可以直接作为改造清单派给不同的人。

```python
"""migrate_scan.py —— 递归扫描 .py 文件里的 0.x 导入路径并输出 1.x 映射"""
import re
import sys
from pathlib import Path

MIGRATION_MAP = {
    "langchain.prompts": "langchain_core.prompts",
    "langchain.schema": "langchain_core.messages",
    "langchain.schema.runnable": "langchain_core.runnables",
    "langchain.output_parsers": "langchain_core.output_parsers",
    "langchain.callbacks": "langchain_core.callbacks",
    "langchain.chains": "langchain.agents.create_agent（或直接用 LCEL 组合）",
    "langchain.memory": "LangGraph checkpointer（如 InMemorySaver）",
    "langchain.indexes": "langchain_core.indexing / langchain.agents 检索中间件",
    "langchain.chat_models.openai": "langchain_openai",
    "langchain.embeddings.openai": "langchain_openai",
}
IMPORT_RE = re.compile(r"^\s*(?:from|import)\s+([\w\.]+)", re.M)


def scan(path: Path) -> list[tuple[int, str, str]]:
    hits = []
    for lineno, line in enumerate(path.read_text(encoding="utf-8").splitlines(), 1):
        m = IMPORT_RE.match(line)
        if not m:
            continue
        module = m.group(1)
        for old, new in MIGRATION_MAP.items():
            if module == old or module.startswith(old + "."):
                hits.append((lineno, module, new))
    return hits


def main(target: str) -> int:
    root = Path(target)
    files = sorted(root.rglob("*.py"))
    total = 0
    print(f"扫描目录：{root}（共 {len(files)} 个 .py 文件）")
    for f in files:
        for lineno, module, new in scan(f):
            total += 1
            print(f"{f}:{lineno}: {module}  ->  {new}")
    print(f"\n发现 {total} 处需要迁移的导入")
    return 0
```

## 最佳实践与踩坑记录

1. **先确认版本再写代码**：`pip show langchain langchain-core langgraph`，把真实版本写进 `requirements.txt`。LangChain 各子包版本号并不对齐（1.4.6 / 1.6.10 / 0.4.2 / 1.7.2），凭记忆写版本必然踩坑。
2. **导入路径按「抽象在 core、集成在独立包」记忆**：`langchain_core.*` 放稳定抽象，`langchain_openai` / `langchain_ollama` 放供应商集成，`langchain.*` 只有 `agents`、`chat_models`、`messages`、`tools`。
3. **用假模型做单元测试与 CI 冒烟**：`FakeListChatModel`、`GenericFakeChatModel`、`FakeEmbeddings` 都不联网、输出确定，能把「编排逻辑」与「模型输出质量」彻底解耦，测试稳定且免费。
4. **业务代码尽量只依赖 core 抽象**：消息、Runnable、解析器都用 `langchain_core` 的类型，把供应商 SDK 收敛到少量适配层，换模型时改动面最小。
5. **日志与密钥分离**：模型 key、LangSmith key 一律走环境变量或密钥服务；开启 `LANGSMITH_TRACING=true` 之后 trace 里会带上提示词全文，注意别把敏感数据塞进 prompt。
6. **升级前先看 changelog 再动 lock 文件**：1.x 仍在快速演进（例如 streaming 在较新版本引入了 v2 输出格式），跨小版本升级也可能改行为。

坑 1：照抄 0.x 教程的导入路径，一运行就 ImportError。

结论：`langchain.prompts`、`langchain.chains`、`langchain.memory`、`langchain.indexes` 在 1.x 全部不存在，本机实测均抛 `ModuleNotFoundError`。

原因：1.x 做了结构性重构，Chain / Memory 这两个概念被 LCEL 与 LangGraph 取代，稳定抽象下沉到 langchain-core，集成拆成独立包。

解法：按本节映射表改导入；用迁移扫描脚本定位存量代码；写代码前先用 `python -c "import langchain.prompts"` 一句话验证模块是否存在，不要相信教程里的路径。

坑 2：装了 `langchain-community` 之后依赖树爆炸，容器镜像变大、构建变慢。

结论：`langchain-community` 会带入 aiohttp、sqlalchemy、numpy、pydantic-settings 等一批依赖，而 `langchain` 本身并不依赖它。

原因：社区包是历史集成的大集合，官方已声明进入 sunset 阶段（导入时会打印 DeprecationWarning）。

解法：需要哪个集成就装哪个独立包（`langchain-openai`、`langchain-ollama`）；确实需要社区包时把它放到单独的构建阶段，或 `pip install --no-deps` 后显式补依赖。

坑 3：以为 `create_agent` 是纯 LangChain 的东西，不敢用 LangGraph 的持久化 API。

结论：`create_agent` 返回 `CompiledStateGraph`，MRO 为 `CompiledStateGraph -> Pregel -> PregelProtocol -> Runnable`，checkpointer、`thread_id` 都是 LangGraph 的概念。

原因：1.x 的 Agent 就是构建在 LangGraph 之上的图，LangChain 只提供组装壳。

解法：做会话记忆直接传 `checkpointer=InMemorySaver()`（生产换持久化后端），调用时用 `config={"configurable": {"thread_id": ...}}` 指定会话，不要再去找 0.x 的 `ConversationBufferMemory`。

坑 4：本机没有 API key，就以为无法验证链路是否写对。

结论：`FakeListChatModel` / `GenericFakeChatModel` 可以完整跑通提示模板、消息、解析器、LCEL 组合、重试回退等全部编排逻辑，本机验证期间链路一次都没联网。

原因：假模型实现的是 `BaseChatModel` 接口，对上层完全透明。

解法：单元测试与 CI 固定用假模型；只有「模型输出质量」类验证才需要真实 key，把它单独放到集成测试或人工验收环节。
