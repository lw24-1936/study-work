## 概述

提示模板负责把「变量 + 历史消息 + 格式指令」组装成模型能吃的消息列表，输出解析器负责把模型的自由文本变回程序可用的数据结构，两者是 LLM 应用里唯一必须自己写的部分。1.x 里提示模板与解析器全部住在 `langchain_core.prompts` 与 `langchain_core.output_parsers`（注意：不是 `langchain.prompts`，那个模块已不存在）。工程上的重点是**结构优先**：能用 `with_structured_output` 约束模型输出成 Pydantic 对象，就不要写正则去抠文本；实在要解析自由文本，也必须准备解析失败后的修复与降级路径。

```text
本篇主线：
1. 提示模板 —— PromptTemplate（纯文本）/ ChatPromptTemplate（角色化）/ MessagesPlaceholder（插历史）/ partial（预填变量）
2. 少样本 —— FewShotChatMessagePromptTemplate 把「输入-输出」样例渲染成多轮消息
3. 结构化输出 —— with_structured_output(Pydantic)，底层是把 schema 作为工具强制调用
4. 输出解析器 —— Str / Json / Pydantic / 逗号列表，各自返回类型与失败形态
5. 失败处理 —— 解析失败先重试、再用「错误信息 + 修复指令」二次提问
6. 降级 —— include_raw 拿到原始输出，解析失败时转人工复核而不是整条链崩掉
```

本机实测环境：Python 3.14.7、`langchain 1.4.6`、`langchain-core 1.6.10`、`pydantic 2.14.1`，venv 在 `/root/.hermes/cache/scratch/lcvenv-a`。本机无 API key，模型侧用 `FakeListChatModel` 与自写的 `FakeToolCallingModel`（后者返回预置的 `tool_call`，用于在无 key 环境下验证结构化输出链路），所有输出均为本机真实运行结果并已标注。

## 提示模板

`PromptTemplate` 面向纯文本场景（补全式用法），`ChatPromptTemplate` 面向对话场景。后者用 `("角色", "模板")` 二元组声明消息，变量用 `{name}` 占位；`MessagesPlaceholder` 用来把已有的消息列表（历史、检索结果）整段插进模板，`partial` 用来预填固定变量（例如把公司名、角色写死，只留问题给运行时）。

```python
from langchain_core.prompts import (
    ChatPromptTemplate, MessagesPlaceholder, PromptTemplate,
)
from langchain_core.messages import AIMessage, HumanMessage

# 1. 纯文本模板
pt = PromptTemplate.from_template("把下面的日志按级别分类：\n{log}\n分类：")
print(pt.invoke({"log": "ERROR db timeout"}).text)

# 2. 角色化模板
cp = ChatPromptTemplate.from_messages(
    [("system", "你是 {role}，输出必须包含结论与依据。"), ("human", "问题：{question}")]
)
for m in cp.invoke({"role": "SRE", "question": "P99 从 200ms 涨到 820ms"}).messages:
    print(f"  {m.type:7s} {m.content}")
print("input_variables:", cp.input_variables)

# 3. 插入历史消息
with_hist = ChatPromptTemplate.from_messages(
    [("system", "你是客服助手。"), MessagesPlaceholder("history"), ("human", "{input}")]
)
msgs = with_hist.invoke(
    {
        "history": [
            HumanMessage("我的订单 1001 还没发货"),
            AIMessage("已为您催单，预计今天 18:00 前揽收"),
        ],
        "input": "那什么时候能到？",
    }
).messages

# 4. partial 预填变量
base = ChatPromptTemplate.from_messages(
    [("system", "你是 {company} 的 {role}。"), ("human", "{question}")]
)
sre_bot = base.partial(role="SRE")
print("剩余变量:", sre_bot.input_variables)
```

本机真实输出：

```text
=== 1. PromptTemplate：纯字符串模板 ===
把下面的日志按级别分类：
ERROR db timeout
分类：

=== 2. ChatPromptTemplate：角色化模板 + 变量 ===
  system  你是 SRE，输出必须包含结论与依据。
  human   问题：P99 从 200ms 涨到 820ms
input_variables: ['question', 'role']

=== 3. MessagesPlaceholder：把历史消息插进模板 ===
  system  你是客服助手。
  human   我的订单 1001 还没发货
  ai      已为您催单，预计今天 18:00 前揽收
  human   那什么时候能到？

=== 4. partial：预填固定变量 ===
剩余变量: ['company', 'question']
  system  你是示例科技 的 SRE。
  human   怎么排查 502
```

注意 `input_variables` 是模板声明的**全部**变量（`['question', 'role']`），`partial` 之后被预填的变量会从待填列表里消失（`['company', 'question']` 里已经没有 `role`），这是判断「模板还缺哪些参数」最可靠的依据。

```text
1. 对话场景一律用 ChatPromptTemplate.from_messages，用 ("角色", "模板") 二元组声明
2. MessagesPlaceholder 用来插历史或检索结果，值必须是消息列表
3. partial 预填固定变量，返回的新模板 input_variables 会相应减少，可用于校验
4. 变量名有冲突或缺失时，invoke 会直接抛错，比运行时才发现少参数要早
5. 提示模板是 Runnable，可放进 | 链路，也可单独 invoke 检查渲染结果
6. 模板里写格式指令（如「只输出 JSON」）不如用解析器的 get_format_instructions()
```

## 少样本提示

少样本（few-shot）是把「输入-输出」示例对渲染成多轮对话，让模型模仿格式与判断标准。1.x 的写法是 `FewShotChatMessagePromptTemplate`：给它一个 `example_prompt`（单条样例如何排版）和一个 `examples` 列表，它在渲染时展开成多条 human/ai 消息。

```python
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate, FewShotChatMessagePromptTemplate

examples = [
    {"input": "p99=820ms 阈值 500ms", "output": "P1"},
    {"input": "磁盘使用率 91% 阈值 95%", "output": "P3"},
    {"input": "支付成功率 83% 阈值 99%", "output": "P0"},
]
example_prompt = ChatPromptTemplate.from_messages([("human", "{input}"), ("ai", "{output}")])
few_shot = FewShotChatMessagePromptTemplate(example_prompt=example_prompt, examples=examples)
few_shot_chat = ChatPromptTemplate.from_messages(
    [
        ("system", "你是告警分级器，只输出 P0/P1/P2/P3。"),
        few_shot,
        ("human", "{input}"),
    ]
)
rendered = few_shot_chat.invoke({"input": "订单创建接口错误率 37% 阈值 1%"})
print("渲染出的消息条数:", len(rendered.messages))
for i, m in enumerate(rendered.messages):
    print(f"  [{i}] {m.type:7s} {m.content}")

chain = few_shot_chat | FakeListChatModel(responses=["P0"]) | StrOutputParser()
print("分级结果:", chain.invoke({"input": "订单创建接口错误率 37% 阈值 1%"}))
```

本机真实输出（生成内容为本地假模型）：

```text
=== 5. 少样本：FewShotChatMessagePromptTemplate ===
渲染出的消息条数: 8
  [0] system  你是告警分级器，只输出 P0/P1/P2/P3。
  [1] human   p99=820ms 阈值 500ms
  [2] ai      P1
  [3] human   磁盘使用率 91% 阈值 95%
  [4] ai      P3
  [5] human   支付成功率 83% 阈值 99%
  [6] ai      P0
  [7] human   订单创建接口错误率 37% 阈值 1%

=== 6. 少样本 + 假模型跑完整链路 ===
分级结果: P0
```

三个示例渲染成 6 条消息，加上 system 与真实输入共 8 条。实践中的经验值：**样例 2 到 5 条、格式与目标输出完全一致、边界样例（最容易判错的）优先放**；样例过多会挤占上下文，收益递减。

```text
1. FewShotChatMessagePromptTemplate = example_prompt（单条排版） + examples（样例列表）
2. 样例渲染成真实的多轮 human/ai 消息，不是拼进一个字符串
3. 样例数量控制在 2-5 条，优先放边界与易错样例
4. 样例的输出格式必须与真实期望的输出格式逐字一致，否则模型学歪
5. 少样本能显著提升格式稳定性，但替代不了输出解析器的校验
6. 动态选样例（按相似度检索）时，把 examples 换成运行时变量即可
```

## 结构化输出

结构化输出的目标是「模型必须按我给的 schema 返回」。1.x 的实现路径是：把 Pydantic schema 转成工具定义，用 `tool_choice="any"` 强制模型调用该工具，再从 `tool_calls[0]["args"]` 里取参数并用 Pydantic 校验（本机源码确认：`with_structured_output` 内部走 `bind_tools([schema], tool_choice="any", ls_structured_output_format=...)` 加 `PydanticToolsParser`）。

```python
from typing import Literal
from pydantic import BaseModel, Field
from langchain_core.language_models import BaseChatModel
from langchain_core.messages import AIMessage
from langchain_core.outputs import ChatGeneration, ChatResult
from langchain_core.utils.function_calling import convert_to_openai_tool


class Ticket(BaseModel):
    """工单结构化抽取结果。"""
    service: str = Field(description="受影响的服务名")
    severity: Literal["P0", "P1", "P2", "P3"] = Field(description="严重级别")
    need_rollback: bool = Field(description="是否需要回滚")
    root_cause: str = Field(description="可能根因，一句话")


class FakeToolCallingModel(BaseChatModel):
    """本地假模型：不联网，直接返回预置的 tool_call，用于无 key 环境验证结构化输出链路。"""
    payloads: list[dict]
    index: int = 0

    @property
    def _llm_type(self) -> str:
        return "fake-tool-calling"

    def bind_tools(self, tools, **kwargs):
        names = []
        for t in tools:
            if isinstance(t, dict):
                names.append(t.get("function", {}).get("name", "Ticket"))
            else:
                names.append(convert_to_openai_tool(t).get("function", {}).get("name", "Ticket"))
        self._bound_tool_names = names
        return self

    def _generate(self, messages, stop=None, run_manager=None, **kwargs):
        payload = self.payloads[self.index % len(self.payloads)]
        self.index += 1
        name = (getattr(self, "_bound_tool_names", None) or ["Ticket"])[0]
        return ChatResult(
            generations=[
                ChatGeneration(
                    message=AIMessage(
                        content="",
                        tool_calls=[{"name": name, "args": payload, "id": f"call_{self.index}"}],
                    )
                )
            ]
        )


structured_model = FakeToolCallingModel(
    payloads=[
        {
            "service": "payment-api",
            "severity": "P0",
            "need_rollback": True,
            "root_cause": "发布 v1.8.2 后连接池配置错误",
        }
    ]
)
result = structured_model.with_structured_output(Ticket).invoke("把这条告警抽取成工单")
print(type(result).__name__, result.model_dump())
```

本机真实输出：

```text
=== 6. with_structured_output：自定义本地假模型提供 tool_call ===
类型: Ticket
{'service': 'payment-api', 'severity': 'P0', 'need_rollback': True, 'root_cause': '发布 v1.8.2 后连接池配置错误'}
```

返回的就是 `Ticket` 实例，字段已按 schema 校验过。几个关键细节：

- `Field(description=...)` 会进入工具描述，是**唯一能让模型理解字段含义**的地方，必须写。
- 用 `Literal["P0", ...]` 这类类型约束能挡住绝大多数枚举越界；`include_raw=True` 可以同时拿到 `raw` / `parsed` / `parse_error`。
- 如果模型不支持工具调用，`with_structured_output` 会直接抛 `NotImplementedError`（本机源码：`type(self).bind_tools is BaseChatModel.bind_tools` 时抛错）。

```text
1. 结构化输出优先用它，不要用正则抠 JSON：schema 即约束，校验发生在返回之前
2. Field 的 description 会作为工具描述送给模型，是提示词的一部分，必须写清楚
3. 枚举、必填、类型都用 Pydantic 声明，模型返回越界值会被当场拦住
4. 支持 schema 的三种形态：Pydantic 类（返回实例）/ TypedDict / JSON Schema（后两者返回 dict）
5. 底层是把 schema 当工具强制调用，因此模型必须支持 tool calling
6. include_raw=True 可同时拿到原始消息与解析错误，用于降级与排障
```

## 输出解析器

解析器的职责是把 `AIMessage` 转成程序要的类型，常见四种：`StrOutputParser`（取文本）、`JsonOutputParser`（解析成 dict）、`PydanticOutputParser`（解析并校验成模型实例）、`CommaSeparatedListOutputParser`（逗号分隔列表）。

```python
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import (
    CommaSeparatedListOutputParser, JsonOutputParser, PydanticOutputParser, StrOutputParser,
)

m = FakeListChatModel(responses=["结论：需要回滚。"])
print(repr((m | StrOutputParser()).invoke("?")))

json_model = FakeListChatModel(
    responses=['{"service": "order-api", "severity": "P0", "need_rollback": true, "root_cause": "连接池耗尽"}']
)
jp = JsonOutputParser()
print(type((json_model | jp).invoke("?")).__name__, (json_model | jp).invoke("?"))
print("格式指令片段:", jp.get_format_instructions().replace("\n", " ")[:110])

pp = PydanticOutputParser(pydantic_object=Ticket)
ticket = (json_model | pp).invoke("?")
print("类型:", type(ticket).__name__, "| json:", ticket.model_dump_json())

lst = FakeListChatModel(responses=["网关,应用,数据库,连接池"])
print((lst | CommaSeparatedListOutputParser()).invoke("?"))
```

本机真实输出：

```text
=== 1. StrOutputParser：只取文本 ===
'结论：需要回滚。'

=== 2. JsonOutputParser：拿到 dict ===
类型: dict | 内容: {'service': 'order-api', 'severity': 'P0', 'need_rollback': True, 'root_cause': '连接池耗尽'}
格式指令片段: Return a JSON object.

=== 3. PydanticOutputParser：拿到模型实例 + 校验 ===
类型: Ticket
service: order-api | severity: P0 | 回滚: True
格式化后的 json: {"service":"order-api","severity":"P0","need_rollback":true,"root_cause":"连接池耗尽"}

=== 5. 列表解析器 ===
['网关', '应用', '数据库', '连接池']
```

一个容易被忽略的点：`JsonOutputParser().get_format_instructions()` 在 langchain-core 1.x 里只返回 `Return a JSON object.`——**格式说明非常短**，因此不要指望它把 schema 写进提示词，需要 schema 描述时用 `PydanticOutputParser`（它会生成包含字段名与类型的完整说明）。

解析失败时的异常形态（本机实测）：

```text
=== 4. 非法 JSON / 非法枚举 -> 抛出校验错误 ===
JsonOutputParser 失败: OutputParserException Invalid json output: 服务是 order-api，级别 P0
解析器异常: OutputParserException -> Failed to parse Ticket from completion {"service": "order-api", "severity": "URG
底层异常: ValidationError | 错误条数: 1
错误定位: ('severity',) | 类型: literal_error
```

也就是说：非法 JSON 抛 `OutputParserException`；JSON 合法但字段越界时，`OutputParserException.__cause__` 是 Pydantic 的 `ValidationError`，可以用 `error_count()` 与 `errors()[0]["loc"]` 精确定位到字段——这正是自动修复链需要的信息。

| 解析器 | 返回类型 | 失败时 | 典型用途 |
| --- | --- | --- | --- |
| `StrOutputParser` | `str` | 基本不失败 | 只要文本，最常见 |
| `JsonOutputParser` | `dict` | `OutputParserException` | 需要键值对但不想建模型 |
| `PydanticOutputParser` | Pydantic 实例 | `OutputParserException`（cause 为 `ValidationError`） | 需要强校验 + 字段描述 |
| `CommaSeparatedListOutputParser` | `list[str]` | 不会失败（切不开就单个元素） | 标签、关键词列表 |

```text
1. 只要文本就用 StrOutputParser，它是链路结尾的默认选择
2. 需要键值对但字段少、校验弱 -> JsonOutputParser；需要强校验与字段描述 -> PydanticOutputParser
3. JsonOutputParser 的 get_format_instructions() 在 1.x 只有一句 "Return a JSON object."，别指望它描述 schema
4. 解析失败统一抛 OutputParserException；字段越界时 e.__cause__ 是 pydantic ValidationError
5. ValidationError 的 errors()[0]["loc"] 能定位到具体字段，是自动修复链的关键输入
6. 解析器是 Runnable，既能挂在链路尾部，也能单独调用 parse_result
```

## 解析失败与修复

解析失败在生产里是常态（模型偶尔加 markdown 围栏、用单引号、多写一句解释）。处理策略按代价递增排列：**先原样重试**（同提示再问一次，成本最低、成功率意外地高），**再用「错误信息 + 修复指令」二次提问**（把 `OutputParserException` 的文本塞回提示词），最后才降级为人工复核。

```python
import json
from langchain_core.exceptions import OutputParserException
from langchain_core.output_parsers import JsonOutputParser
from langchain_core.prompts import ChatPromptTemplate

parser = JsonOutputParser()
ask = ChatPromptTemplate.from_template(
    "抽取 {field} 字段，只输出 JSON。\n输入：{text}\n{format_instructions}"
)


class FlakyJsonModel:
    """第一次返回带 markdown 围栏的脏 JSON，第二次才返回干净 JSON。"""

    def __init__(self):
        self.calls = 0

    def __call__(self, messages):
        self.calls += 1
        if self.calls == 1:
            return "```json\n{'service': 'order-api', 'severity': 'P1'}\n```"  # 单引号 + 围栏，非法 JSON
        return json.dumps({"service": "order-api", "severity": "P1"}, ensure_ascii=False)


def extract_with_repair(model, text: str, max_attempts: int = 3) -> dict:
    """三级修复：直接解析 -> 原样重试 -> 追加上一次的错误信息重问。"""
    last_error = None
    prompt_value = ask.invoke(
        {"field": "工单信息", "text": text, "format_instructions": parser.get_format_instructions()}
    )
    for attempt in range(1, max_attempts + 1):
        raw = model(prompt_value.to_messages())
        try:
            return {"attempt": attempt, "data": parser.parse(raw)}
        except OutputParserException as e:
            last_error = str(e).splitlines()[0]
            print(f"  第 {attempt} 次解析失败：{last_error[:60]}")
            if attempt == max_attempts:
                break
            prompt_value = ask.invoke(
                {
                    "field": "工单信息",
                    "text": text,
                    "format_instructions": "上一次输出无法解析，错误信息："
                    + last_error
                    + "\n请只输出合法 JSON，不要加 markdown 围栏，字符串一律用双引号。",
                }
            )
    raise RuntimeError(f"修复 {max_attempts} 次仍失败：{last_error}")
```

本机真实输出：

```text
=== 带修复的抽取 ===
  第 1 次解析失败：Invalid json output: ```json
结果: {'attempt': 2, 'data': {'service': 'order-api', 'severity': 'P1'}}

=== 无修复策略（直接失败）===
输出解析失败（未做修复）: Invalid json output: ```json
```

修复提示里必须带上三样东西：**上一次的错误文本**（让模型知道错在哪）、**具体的格式要求**（双引号、不要围栏）、**目标 schema 的描述**。只写「请重新输出」几乎没用。

```text
1. 修复顺序：原样重试 -> 带错误信息重问 -> 降级人工复核，代价递增
2. 错误信息要原样回填给模型，它是模型自我纠正的最强信号
3. 修复指令里同时给出「错在哪」与「应该怎样」，只写「请重试」无效
4. 设置最大尝试次数（常见 2-3 次），避免一次失败把整个请求拖成超时
5. 解析失败要计入监控指标，它通常提示模型或提示词已经退化
6. 能用 with_structured_output 就别走自由文本解析，从源头消灭这类问题
```

## 应用场景实战

### 场景一：告警工单结构化抽取

真实告警文本经常不规范，模型也不是每次都能给出合规的 `tool_call`。生产做法是**结构化优先 + 失败降级到人工复核**：用 `include_raw=True` 同时拿到原始输出与解析结果，只要解析失败就标记为人工复核并把原始文本一起返回，绝不让整条链抛异常。

```python
"""extract_ticket.py —— 结构化成功就入库，失败就转人工复核"""
from typing import Literal

from langchain_core.language_models import BaseChatModel
from langchain_core.messages import AIMessage
from langchain_core.outputs import ChatGeneration, ChatResult
from langchain_core.utils.function_calling import convert_to_openai_tool
from pydantic import BaseModel, Field


class Alert(BaseModel):
    """告警工单。"""
    service: str = Field(description="受影响服务")
    severity: Literal["P0", "P1", "P2", "P3"] = Field(description="级别")
    metric: str = Field(description="触发的指标名")
    need_rollback: bool = Field(description="是否建议回滚")


class StubModel(BaseChatModel):
    """本地假模型：直接返回预置 tool_call 或纯文本，用于演示两条分支。"""
    tool_payload: dict | None = None
    plain_text: str = ""

    @property
    def _llm_type(self) -> str:
        return "stub"

    def bind_tools(self, tools, **kwargs):
        name = convert_to_openai_tool(tools[0]).get("function", {}).get("name", "Alert")
        self._tool_name = name
        return self

    def _generate(self, messages, stop=None, run_manager=None, **kwargs):
        if self.tool_payload is None:
            msg = AIMessage(content=self.plain_text)
        else:
            msg = AIMessage(
                content="",
                tool_calls=[
                    {"name": getattr(self, "_tool_name", "Alert"), "args": self.tool_payload, "id": "call_1"}
                ],
            )
        return ChatResult(generations=[ChatGeneration(message=msg)])


def extract(model, alert_text: str) -> dict:
    """返回 {'status': 'structured'|'manual_review', ...}"""
    structured = model.with_structured_output(Alert, include_raw=True)
    raw = structured.invoke(f"把这条告警抽取成工单：{alert_text}")
    if raw.get("parse_error") is not None or raw.get("parsed") is None:
        err = raw.get("parse_error")
        return {
            "status": "manual_review",
            "reason": type(err).__name__ if err is not None else "模型未返回 tool_call（parsed 为空）",
            "raw_text": raw["raw"].text,
        }
    return {"status": "structured", "ticket": raw["parsed"].model_dump()}


good = StubModel(
    tool_payload={
        "service": "payment-api",
        "severity": "P0",
        "metric": "http_5xx_rate",
        "need_rollback": True,
    }
)
print("=== 结构化成功分支 ===")
print(extract(good, "payment-api 5xx 比例 37%，阈值 1%，发布 v1.8.2 后开始"))

bad = StubModel(plain_text="支付接口大面积报错，看起来挺严重的")
print("\n=== 结构化失败分支 ===")
print(extract(bad, "支付接口大面积报错，看起来挺严重的"))
```

本机真实输出：

```text
=== 结构化成功分支 ===
{'status': 'structured', 'ticket': {'service': 'payment-api', 'severity': 'P0', 'metric': 'http_5xx_rate', 'need_rollback': True}}

=== 结构化失败分支 ===
{'status': 'manual_review', 'reason': '模型未返回 tool_call（parsed 为空）', 'raw_text': '支付接口大面积报错，看起来挺严重的'}
```

### 场景二：解析失败自动修复

第二个场景把修复链做成可复用函数，并对比「有修复」与「无修复」两种策略的结果差异。关键实现点：第一次失败后不换提示，而是把错误信息与更严格的格式要求拼进第二次提问。

```python
"""repair_extract.py —— 三级修复的抽取函数（extract_with_repair / FlakyJsonModel / ask / parser 的定义见上文）"""
from langchain_core.exceptions import OutputParserException
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import JsonOutputParser
from langchain_core.prompts import ChatPromptTemplate

parser = JsonOutputParser()
ask = ChatPromptTemplate.from_template(
    "抽取 {field} 字段，只输出 JSON。\n输入：{text}\n{format_instructions}"
)

# 第 1 次：脏 JSON（markdown 围栏 + 单引号）-> 解析失败
# 第 2 次：把错误信息与格式要求拼进提示 -> 解析成功
print("结果:", extract_with_repair(FlakyJsonModel(), "order-api 错误率升高，级别 P1"))

# 对照：同样的脏输出，不做任何修复
try:
    dirty = FakeListChatModel(responses=["```json\n{'service': 'order-api'}\n```"])
    (ask | dirty | parser).invoke(
        {
            "field": "工单信息",
            "text": "order-api 错误率升高",
            "format_instructions": parser.get_format_instructions(),
        }
    )
except OutputParserException as e:
    print("输出解析失败（未做修复）:", str(e).splitlines()[0][:60])
```

结果: {'attempt': 2, 'data': {'service': 'order-api', 'severity': 'P1'}}

=== 无修复策略（直接失败）===
输出解析失败（未做修复）: Invalid json output: ```json

## 最佳实践与踩坑记录

1. **结构优先**：需要程序可用的数据就上 `with_structured_output`；只有确实要自然语言的地方才用自由文本 + `StrOutputParser`。
2. **字段描述当提示词写**：`Field(description=...)` 直接进入工具描述，写清单位、取值范围、示例值，能显著降低字段错配率。
3. **模板与解析器成套设计**：提示里要求的格式必须与解析器期望的格式一致（例如要求「纯 JSON 对象」就不要同时让模型输出解释）。
4. **解析失败必须可观测**：把 `OutputParserException` 计入指标并按模型/提示词版本分组，它是最早暴露「模型换版本后行为变了」的信号。
5. **修复链设置上限并统计次数**：`max_attempts=2~3`，把「第几次修复成功」作为指标，长期偏高说明提示词该重写。
6. **样例少而准**：少样本 2-5 条，样例的输出格式与目标格式逐字一致，别在里面混用不同风格。

坑 1：从 0.x 教程复制 `from langchain.prompts import ChatPromptTemplate`，直接 ImportError。

结论：1.x 的提示模板在 `langchain_core.prompts`，`langchain.prompts` 模块不存在（本机 `ModuleNotFoundError`），解析器同理在 `langchain_core.output_parsers`。

原因：稳定抽象统一下沉到 langchain-core，`langchain` 顶层只保留 `agents`、`chat_models`、`messages`、`tools`。

解法：把导入改成 `langchain_core.prompts` / `langchain_core.output_parsers`；`OutputFixingParser` 这类 0.x 辅助类在 1.x 的 core 里也不存在，需要自己实现修复链（本节的 `extract_with_repair`）。

坑 2：以为 `get_format_instructions()` 会把 schema 写进提示词，结果模型完全不知道字段要求。

结论：本机实测 `JsonOutputParser().get_format_instructions()` 只返回 `Return a JSON object.`。

原因：JsonOutputParser 不做 schema 描述；`PydanticOutputParser` 才会生成包含字段名、类型与描述的完整说明。

解法：需要 schema 描述时用 `PydanticOutputParser`，或直接上 `with_structured_output`（工具描述天然带上 `Field(description=...)`）。

坑 3：模型返回带 markdown 围栏的 JSON（` ```json ... ``` `），解析器直接抛错导致接口 500。

结论：本机实测这类输出抛 `OutputParserException: Invalid json output: ```json`，整条链中断。

原因：模型被大量 markdown 语料训练过，倾向于给代码块加围栏；而 JSON 解析器只接受纯 JSON 文本。

解法：优先用结构化输出从源头规避；保留自由文本解析时实现修复链（错误信息 + 「不要围栏、字符串用双引号」的指令重问），并设好 `max_attempts` 与降级分支。

坑 4：把「请输出 JSON」写进提示词就不再管格式，结果字段名随机变化（有时 `service` 有时 `service_name`）。

结论：自然语言里的格式要求约束力弱，字段名级别的偏差必须在 schema 层解决。

原因：模型对提示词里的格式描述是「概率性遵守」，对工具 schema 的约束是「结构性强约束」。

解法：用 Pydantic 模型定义字段，走 `with_structured_output`；必须走文本时，至少要 `model_validate` 校验并留修复分支。
