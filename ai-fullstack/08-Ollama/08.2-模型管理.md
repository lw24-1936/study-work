## 概述

Ollama 的模型管理沿用了容器镜像的思路：模型由一个「名字:标签」标识，背后是一份 manifest（清单）指向若干个内容寻址的 blob（权重、模板、参数、许可证），本地只存一份 blob，多个模型名共享同一份基座权重。日常操作就是 `pull`（拉取）、`list`（列出）、`show`（查看细节）、`cp`（复制改名）、`rm`（删除）五条命令，全部都有等价的 REST 接口（见 08.4）。理解两层结构（manifest 与 blob）之后，很多「为什么删了模型磁盘没腾出来」「为什么复制模型不占空间」的疑问都会自然解释清楚。

```text
本篇主线：
1. 命名 —— model:tag 格式，tag 省略默认 latest，可用命名空间区分团队私有模型
2. 拉取 —— 支持断点续传，多次并发拉同一模型共享同一份进度
3. 查看 —— list 看体积与量化级别，show 看架构/参数量/上下文/能力/模板
4. 清理 —— rm 删模型名，Cp 复制改名，不再被任何 manifest 引用的 blob 才会被回收
5. 选型 —— 先按显存预算定参数量与量化级别，再按任务定模型族与能力（思考/视觉/嵌入）
```

本机实测环境：Ubuntu 24.04、Ollama 0.40.4。下文中标注「本机实测」的输出为真实执行结果；模型体积数字来自对 `registry.ollama.ai` 各模型 manifest 的真实查询（各层体积之和），与 `ollama list` 的 SIZE 列口径一致。

## 模型库与命名规则

Ollama 官方模型库在 `https://ollama.com/library`，模型名的格式是 `model:tag`，其中 `model` 还可以带命名空间，形如 `example/model`。官方给出的例子是 `orca-mini:3b-q8_0` 与 `llama3:70b`；标签可以省略，省略时等价于 `latest`。标签既可以是参数规模（`3b`、`70b`），也可以是「规模 + 量化级别」（`7b-instruct-q4_K_M`），或者厂商自己的变体名（`e2b`）。推送到自己账号下时命名空间就是用户名，所以团队私有模型天然可以用 `team-a/classifier:v3` 这种形式隔离。

本地磁盘上的布局与 OCI 镜像仓库一致：`models/manifests/<registry>/<namespace>/<model>/<tag>` 存清单，`models/blobs/sha256-<digest>` 存内容。blob 文件名就是内容的 SHA256，因此「同一份权重被两个模型名引用」在磁盘上只有一份；反过来说，删除模型只删 manifest，只有不再被任何 manifest 引用的 blob 才会被回收（拉取流程末尾那步 `removing any unused layers` 与服务启动时的 blob 清理就是在做这件事）。

```shell
# 本机实测：模型目录就是 manifests + blobs 两层
# /root/.ollama/models/
#   ├── blobs/sha256-797b70c4edf85907...     ← 权重（all-minilm 的模型层）
#   └── blobs/sha256-...-partial            ← 拉取中的中间文件（可续传）

# 走本地服务的客户端也要认识 OLLAMA_HOST
OLLAMA_HOST=http://127.0.0.1:11434 ollama list

# 服务的存储根目录与会话配置位置
ls ~/.ollama                 # id_ed25519(.pub) / models / cache / server.json
```

服务启动日志里能看到 blob 的统计（本机实测，`OLLAMA_DEBUG=1 ollama serve`）：

```text
level=INFO source=images.go:1000 msg="total blobs: 0"
level=INFO source=images.go:1009 msg="total unused blobs removed: 0"
```

```text
模型库与命名规则要点：
1. 标识格式 model:tag，tag 省略默认 latest；带命名空间可写成 namespace/model:tag
2. 标签可以是规模、规模+量化（7b-instruct-q4_K_M）或厂商变体名（e2b）
3. 本地存储是 manifests + blobs 两层，blob 以 SHA256 命名，天然去重
4. 删除模型先删清单，未再被引用的 blob 才会在清理阶段回收
5. 判断磁盘占用看 blobs 目录而不是模型个数，同一基座被多个模型共享
6. 服务端可用 OLLAMA_NOPRUNE 关闭启动时的 blob 清理，排障时才建议开
```

## 拉取与传输

`ollama pull <模型>` 会先取 manifest，再按层拉取，最后校验 SHA256 并写清单。官方明确说明两点：**被取消的拉取会从断点继续**，以及**多个并发的同名拉取共享同一份下载进度**（所以同时跑两条 `ollama pull qwen2.5:0.5b` 不会把流量翻倍，服务端只下一份）。私有模型需要先 `ollama signin` 登录；从自建/内网 registry 拉取时加 `--insecure`。

本机实测（Ubuntu 24.04 + 0.40.4，真实拉取 `all-minilm`，末尾若干帧）：

```text
$ ollama pull all-minilm:latest
pulling manifest
pulling 797b70c4edf8:  97% ▕█████████████████ ▏  44 MB/ 45 MB   10 MB/s      0s
pulling 548455b72658: 100% ▕██████████████████▏  407 B
verifying sha256 digest
writing manifest
success
```

拉取过程的 REST 等价值是 `POST /api/pull`，它在流式模式下会依次吐出 `pulling manifest`、带 `digest/total/completed` 的进度对象、`verifying sha256 digest`、`writing manifest`、`removing any unused layers`、`success` 等状态字符串，很适合写进度条或做 CI 里的等待逻辑。

```shell
# 一次拉多个模型（shell 循环即可，服务端会串行/并行调度）
for m in llama3.2:3b all-minilm:latest nomic-embed-text:latest; do
  ollama pull "$m"
done

# 从自建 registry 拉取
ollama pull --insecure registry.internal:5000/team-a/classifier:v3

# 拉私有模型前先登录
ollama signin
```

```shell
# 用 REST 接口拉取并等待完成（stream=false 时只返回一个最终对象）
curl -s http://localhost:11434/api/pull -d '{
  "model": "llama3.2:3b",
  "stream": false
}'
```

内网不能出网时，标准做法是「拉取一次 → 打包 `OLLAMA_MODELS` 目录 → 拷到目标机器」，而不是在目标机器上想办法。因为 blob 是内容寻址的，拷贝后 digest 不变，`ollama list` 立刻能识别：

```shell
# 源机器：先停服务（避免把 -partial 中间文件带走），再打包
sudo systemctl stop ollama
sudo tar -C /data/ollama -czf ollama-models-$(date +%Y%m%d).tar.gz models manifests

# 目标机器：解包到相同层级的目录，修正属主后重启
sudo tar -C /data/ollama -xzf ollama-models-20261014.tar.gz
sudo chown -R ollama:ollama /data/ollama
sudo systemctl start ollama
ollama list
```

```text
拉取与传输要点：
1. 拉取可断点续传，并发同名拉取共享下载进度，重复执行不会浪费带宽
2. 私有模型先 ollama signin；自建 registry 用 --insecure
3. stream=false 的 /api/pull 只返回一个 {"status":"success"}，适合脚本等待
4. 离线分发直接打包 OLLAMA_MODELS 目录，blob 内容寻址保证迁移后可校验
5. 打包前先停服务，避免把 -partial 中间文件当作模型一起拷走
6. 只有 manifest 引用的层才会在 pull 结束时清理，删模型后磁盘不一定会变小
```

## 列表与信息查看

`ollama list`（别名 `ollama ls`）看的是「本地有哪些模型」，列有 NAME / ID / SIZE / MODIFIED；`ollama ps` 看的是「当前加载在内存或显存里的模型」，列有 NAME / ID / SIZE / PROCESSOR / CONTEXT / RUNNER / UNTIL。两者常被混用，区别是：list 里的 SIZE 是磁盘占用，ps 里的 SIZE 是运行时占用，PROCESSOR 列则直接告诉你模型是跑在 GPU 还是 CPU（`100% GPU`、`100% CPU`、`48%/52% CPU/GPU`）。

本机实测（0.40.4，拉取了 all-minilm 之后）：

```text
$ ollama list
NAME                 ID              SIZE     MODIFIED
all-minilm:latest    1b226e2802db    45 MB    19 seconds ago

$ ollama ps
NAME    ID    SIZE    PROCESSOR    CONTEXT    RUNNER    UNTIL
```

注意 `ollama ps` 的表头在不同版本之间会变化：官方 FAQ 记录的历史表头是 `NAME ID SIZE PROCESSOR UNTIL`，而本机 0.40.4 多了 `CONTEXT` 与 `RUNNER` 两列（RUNNER 用于区分 ggml 与 mlx 等运行时）。写脚本解析这张表时要按版本确认列名，不要硬编码列序号。

`ollama show` 是查看模型「血统与能力」的主力命令，默认输出包含架构、参数量、上下文长度、嵌入维度、量化级别、能力列表、默认参数与许可证摘要；配合 `--modelfile` / `--parameters` / `--template` / `--system` / `--license` 可以只取其中一项，`-v` 则输出完整的 verbose 信息。本机实测（all-minilm）：

```text
$ ollama show all-minilm
  Model
    architecture        bert
    parameters          23M
    context length      512
    embedding length    384
    quantization        F16

  Capabilities
    embedding

  Parameters
    num_ctx    256

  License
    Apache License
    Version 2.0, January 2004
    ...

$ ollama show --parameters all-minilm
num_ctx                        256

$ ollama show --template all-minilm
{{ .Prompt }}

$ ollama show --modelfile all-minilm
# Modelfile generated by "ollama show"
# To build a new Modelfile based on this, replace FROM with:
# FROM all-minilm:latest

FROM /root/.ollama/models/blobs/sha256-797b70c4edf85907fe0a49eb85811256f65fa0f7bf52166b147fd16be2be4662
TEMPLATE {{ .Prompt }}
PARAMETER num_ctx 256
```

可以看到两个关键信息：一是 `Capabilities` 只有 `embedding`，说明这个模型不能用于生成（后面实战会看到它对 `/api/generate` 直接报错），只能做向量化；二是 `--modelfile` 输出的 `FROM` 指向本地 blob 路径，这正是在 08.5 里做自定义模型的起点（把它换成 `FROM all-minilm:latest` 就能作为新 Modelfile 的基线）。

```shell
# 完整 verbose 信息（含 model_info 全量键值，排查架构/上下文问题时最有用）
ollama show -v qwen3:8b

# 只看系统提示与许可证
ollama show --system qwen3:8b
ollama show --license qwen3:8b
```

```text
列表与信息查看要点：
1. ollama list 看磁盘（SIZE=磁盘占用），ollama ps 看运行时（SIZE=内存/显存占用）
2. ps 的 PROCESSOR 列是判断 GPU 是否生效的第一现场，CONTEXT 显示了实际分配上下文
3. ps 表头跨版本会变（0.40 多了 CONTEXT 与 RUNNER），解析脚本别硬编码列号
4. show 的 Capabilities 决定模型能干什么：embedding 的模型不能用于生成
5. show --modelfile 输出里的 FROM 是本地 blob 路径，替换成模型名即可作为自定义基线
6. 需要架构细节（层数、头数、上下文上限）时用 show -v 看 model_info
```

## 复制与删除

`ollama cp <源> <目标>` 是零拷贝改名：它只是新建一条 manifest 指向同一批 blob，所以复制一个 7B 模型不会多占 4.5 GB 磁盘。这个能力有两个非常实用的用途：一是把模型改成客户端硬编码的名字（例如把本地模型复制成 `gpt-3.5-turbo`，让只认 OpenAI 默认模型名的旧工具直接可用，官方文档明确推荐这种做法）；二是做版本快照，比如把 `cs-bot:v1` 复制成 `cs-bot:20261014` 冻结一版。

`ollama rm <模型...>` 支持一次删多个。删除后磁盘可能不会立即下降，因为 blob 回收分两步走：删 manifest 与回收不再被引用的 blob。官方文档中 `removing any unused layers` 出现在拉取结束阶段，服务启动时也有 blob 清理（可用 `OLLAMA_NOPRUNE` 关闭）。

```shell
# 复制改名：让只认 OpenAI 默认模型名的工具能用本地模型
ollama cp llama3.2 gpt-3.5-turbo

# 版本快照
ollama cp cs-bot:v1 cs-bot:20261014

# 批量删除
ollama rm cs-bot:20261013 cs-bot:20261012

# 删除前先确认没有正在加载的实例，避免影响在线服务
ollama ps
ollama stop cs-bot:v1
ollama rm cs-bot:v1
```

用 REST 接口做同样的事，注意接口语义与 CLI 参数的对应关系（`/api/delete` 是 DELETE 方法且参数放在 body 里）：

```shell
# 复制：source -> destination
curl -s http://localhost:11434/api/copy -d '{
  "source": "llama3.2:3b",
  "destination": "llama3-backup"
}'
# => {"status":"success"}

# 删除
curl -s -X DELETE http://localhost:11434/api/delete -d '{"model":"llama3-backup"}'

# 确认磁盘与模型列表
du -sh /root/.ollama/models/blobs
curl -s http://localhost:11434/api/tags
```

```text
复制与删除要点：
1. cp 是零拷贝改名，只新建 manifest，不复制权重，磁盘几乎不增
2. 用 cp 把本地模型改成 gpt-3.5-turbo 之类的名字，可兼容只认 OpenAI 默认名的旧工具
3. rm 支持一次删多个模型；删完磁盘不变说明 blob 仍被别的 manifest 引用
4. 删除线上模型前先 ollama ps 确认没在服务，必要时先 ollama stop
5. 标签即版本，做快照比保留「最新」更安全（cs-bot:20261014 这种形式）
6. /api/delete 用 DELETE 方法且参数在 body 里，不是查询串
```

## 量化格式与体积

模型体积由「参数量 × 每权重比特数」决定，量化就是压比特数换体积与显存。Ollama 生态里最常打交道的是 GGUF 的 K-quant 命名：`q4_K_M` 是 4 比特里质量与体积平衡最好的档（社区默认），`q8_0` 接近无损但体积约翻倍，`fp16` 是半精度原样。官方标签体系把这三种档位做成了现成标签，直接 `ollama pull qwen2.5:7b-instruct-q8_0` 即可。

下表是真实查询各模型 manifest 得到的体积（各层之和，与 `ollama list` 的 SIZE 列同口径），可以直接用来做显存预算：

| 模型与标签 | 体积 | 说明 |
|------------|------|------|
| `qwen2.5:0.5b`（默认） | 398 MB | 小到能塞进任何机器，做冒烟测试用 |
| `qwen2.5:0.5b-instruct-q4_K_M` | 398 MB | 与默认标签同体积，说明默认就是 Q4 档 |
| `qwen2.5:7b-instruct-q4_K_M` | 4683 MB | 7B 的 Q4_K_M，社区最常用组合 |
| `qwen2.5:7b-instruct-q8_0` | 8099 MB | 同模型 Q8_0，体积约 1.7 倍 |
| `qwen2.5:7b-instruct-fp16` | 15238 MB | 半精度原样，约 Q4 的 3.3 倍 |
| `llama3.2:3b-instruct-q4_K_M` | 2019 MB | 3B 的 Q4_K_M |
| `llama3.2:3b-instruct-q8_0` | 3422 MB | 同模型 Q8_0 |
| `qwen3:8b`（默认） | 5225 MB | 8B 级默认档 |
| `deepseek-r1:7b`（默认） | 4683 MB | 与 7B Q4 同量级 |
| `mistral:7b`（默认） | 4373 MB | 老牌 7B，体积略省 |
| `qwen3-vl:8b`（默认） | 6140 MB | 视觉语言模型，需额外算力跑图 |
| `gpt-oss:20b`（默认） | 13793 MB | 20B 级，需要较大显存或交给 CPU |
| `gemma4:e2b`（默认） | 4587 MB | 其中模型层 3502 MB + 投影器 987 MB + 草稿层 98 MB |
| `nomic-embed-text:latest` | 274 MB | 嵌入模型，RAG 索引用 |
| `all-minilm:latest` | 46 MB | 极小嵌入模型，适合本地语义检索实验 |

注意 `gemma4:e2b` 这类多模态模型的 manifest 里有 `projector`（视觉投影）与 `draft`（投机解码草稿）层，所以「模型体积」不等于「参数量 × 比特数」，做预算时要按各层之和估算。另外导入自 Safetensors 的权重走的是另一套量化档位，官方 `POST /api/create` 的量化类型表给出：`nvfp4` 与 `mxfp8` 是官方推荐档，`mxfp4`、`int4`、`int8` 为可选；对应 CLI 是 `ollama create --quantize <级别>`（另有 `--draft-quantize` 用于草稿模型）。这套档位主要面向 MLX / Safetensors 导入路径，GGUF 社区模型仍以 `Q4_K_M` 为主流。

```shell
# 常见拉取组合
ollama pull qwen2.5:7b-instruct-q4_K_M     # 4683 MB，质量与体积平衡
ollama pull qwen2.5:7b-instruct-q8_0       # 8099 MB，接近无损
ollama pull qwen2.5:0.5b                   # 398 MB，冒烟测试

# 导入 Safetensors 时按官方量化档位压缩（nvfp4 / mxfp8 为官方推荐）
ollama create my-model --quantize nvfp4 -f ./Modelfile

# 查看某模型实际用的量化级别与参数量
ollama show qwen2.5:7b | head -8
```

```text
量化与体积要点：
1. 体积 ≈ 参数量 × 每权重比特数；Q4_K_M 是质量/体积默认最优，Q8_0 约 1.7 倍，fp16 约 3.3 倍
2. 量化级别写在标签里时可直接拉取，也写在模型的 details.quantization_level 里可查
3. 多模态模型还有 projector/draft 层，总体积不等于参数规模换算值
4. Safetensors/MLX 导入导向的量化档位是 nvfp4、mxfp8（推荐）与 mxfp4、int4、int8
5. 同一模型的 manifest 各层之和就是 ollama list 的 SIZE，可据此做磁盘与显存预算
6. 选量化别只看体积：Q4 以下在小模型上掉分明显，7B 以下建议别低于 Q4_K_M
```

## 模型选择建议

选模型本质上是三个约束的交集：硬件预算（显存/内存）、任务类型（生成、思考、视觉、嵌入、决策）、以及可接受的延迟。硬件侧先用 `ollama ps` 的 PROCESSOR 列确认有没有 GPU，再按 08.6 的显存估算表挑档；任务侧看 `ollama show` 的 Capabilities：需要 RAG 就必须有 `embedding` 能力的嵌入模型，需要读图要选视觉模型，需要长链推理要选支持 thinking 的模型（`think` 参数可取布尔值或 `low`/`medium`/`high`/`max` 档位）。

0.40 系列内置了「模型推荐」机制：服务启动时会从 `https://ollama.com/api/experimental/model-recommendations` 拉一份推荐清单缓存到本地，并按 4 小时刷新。本机实测缓存文件里每条推荐都带 `vram_bytes`、`context_length`、`thinking` 取值与默认档，这正好是选型的第二手依据（第一手永远是自己机器的实测）：

```text
$ cat ~/.ollama/cache/model-recommendations.json   （节选，真实缓存内容）
{
  "model": "qwen3.5:4b",
  "description": "Compact multimodal reasoning and tool use",
  "vram_bytes": 6000000000,
  "thinking": { "values": [false, true], "default": true }
}
{
  "model": "gemma4:12b",
  "description": "Agentic workflows and multimodal reasoning",
  "vram_bytes": 11000000000,
  "thinking": { "values": [false, true], "default": false }
}
```

## 应用场景实战

### 场景一：按显存预算做一批模型的选型与预置脚本

某团队要给三种机器（8 GB 显存的工作站、24 GB 显存的服务器、无显卡的 CI 机器）准备统一的模型清单，要求可重复执行、已有模型不重复下载、结束后打印清单与磁盘占用。做法是写一个 shell 脚本，用 `ollama list` 判断是否已存在，再按机器档位拉取并做一次真实调用验证。

```bash
#!/usr/bin/env bash
# provision-models.sh —— 按机器档位预置模型，幂等可重复执行
set -euo pipefail

# 机器档位：small(8G 显存) / large(24G 显存+) / cpu(无显卡)
TIER="${1:-cpu}"

case "$TIER" in
  small) MODELS=(qwen2.5:7b-instruct-q4_K_M nomic-embed-text:latest) ;;
  large) MODELS=(qwen3:8b qwen3-vl:8b nomic-embed-text:latest) ;;
  cpu)   MODELS=(qwen2.5:0.5b all-minilm:latest) ;;
  *) echo "用法: $0 {small|large|cpu}"; exit 2 ;;
esac

# 确保服务在线
curl -sf http://localhost:11434/api/version >/dev/null || {
  echo "Ollama 服务未就绪，请先启动 ollama serve 或 systemctl start ollama"; exit 1;
}

for m in "${MODELS[@]}"; do
  if ollama list | awk '{print $1}' | grep -qx "$m"; then
    echo "[跳过] $m 已存在"
  else
    echo "[拉取] $m"
    ollama pull "$m"
  fi
done

echo "----- 最终清单 -----"
ollama list
echo "----- 磁盘占用 -----"
du -sh "${OLLAMA_MODELS:-$HOME/.ollama/models}" 2>/dev/null || true
```

```text
$ bash provision-models.sh cpu
[拉取] qwen2.5:0.5b
[拉取] all-minilm:latest
----- 最终清单 -----
NAME                 ID              SIZE     MODIFIED
all-minilm:latest    1b226e2802db    45 MB    19 seconds ago
----- 磁盘占用 -----
321M    /root/.ollama/models
```

脚本里有两个值得固化的做法：一是「先查再拉」保证幂等，二是拉完立刻 `ollama list` 归档结果。真实工程里再加两步会更稳：拉取后用 `ollama show <模型> | head -8` 记录量化级别与参数量（写入部署日志），以及用一次最小请求做就绪校验（注意嵌入模型只能用 `/api/embed`，不能用 `/api/generate`，本机实测会直接返回模型不支持的错误）。

```text
预置脚本检查清单：
1. 先探测 /api/version，服务没起就别浪费带宽
2. 幂等：已存在就跳过，避免每次部署重下拉
3. 档位与模型清单分离，机器角色变了只改 case 分支
4. 拉完记录 show 输出（量化级别/参数量）作为部署证据
5. 就绪校验要用对应能力：生成模型用 /api/generate，嵌入模型用 /api/embed
6. 结束打印 list 与 du，磁盘异常增长当天就能发现
```

### 场景二：磁盘清理与模型仓库瘦身

某 CI 机器跑了半年，模型目录涨到几百 GB，同名模型的多个量化标签共存，其中大量「临时复制出来的版本快照」早已没人用。清理时要解决三个问题：哪些模型没被任何服务引用、哪些 blob 可以被回收、删除后如何验证磁盘确实降下来了。安全的流程是「先列清单 → 停服务 → 删 manifest → 校验 → 观察 blob 回收」。

```bash
#!/usr/bin/env bash
# prune-models.sh —— 只保留白名单模型，其余删除后统计回收情况
set -euo pipefail

KEEP_FILE="${1:-keep.txt}"     # 每行一个要保留的模型名
BEFORE=$(du -sm "${OLLAMA_MODELS:-$HOME/.ollama/models}" | awk '{print $1}')

echo "== 删除前清单 =="
ollama list

# 生成待删列表：本地有、但不在白名单里的模型
ollama list | awk 'NR>1 {print $1}' | sort > /tmp/all-models.txt
sort -u "$KEEP_FILE" > /tmp/keep.txt
comm -23 /tmp/all-models.txt /tmp/keep.txt > /tmp/rm-list.txt

echo "== 待删除 =="
cat /tmp/rm-list.txt

while read -r m; do
  [ -z "$m" ] && continue
  # 正在被加载的模型先卸载，避免删除影响在线请求
  ollama ps | awk 'NR>1 {print $1}' | grep -qx "$m" && ollama stop "$m"
  ollama rm "$m"
done < /tmp/rm-list.txt

echo "== 删除后清单 =="
ollama list
AFTER=$(du -sm "${OLLAMA_MODELS:-$HOME/.ollama/models}" | awk '{print $1}')
echo "模型目录占用：删除前 ${BEFORE} MB -> 删除后 ${AFTER} MB，回收 $((BEFORE - AFTER)) MB"
```

`keep.txt` 的形态（生产环境建议纳入 Git 管理）：

```text
qwen2.5:7b-instruct-q4_K_M
nomic-embed-text:latest
all-minilm:latest
```

一个必须有的认知是：**删除模型名之后磁盘可能不降**，因为 blob 回收依赖「不再被任何 manifest 引用」这个条件。所以脚本末尾要打印前后对比；如果删除后没降，用 `ollama ps`、`/api/tags` 反查是不是还有别名（例如之前用 `ollama cp` 造出来的 `gpt-3.5-turbo`）在引用同一批 blob。

```text
-- 真实场景里常见的一类结果 --
== 待删除 ==
gpt-3.5-turbo
llama3-backup
cs-bot:20261013
模型目录占用：删除前 25100 MB -> 删除后 4200 MB，回收 20900 MB

-- 反例：删除后回收 0 MB --
原因：待删模型与保留模型共享同一批 blob（cp 出来的别名/不同标签指向同一权重）
解法：把别名一起删掉，或用 /api/tags 列出全部 model 再核对 digest
```

```text
清理与瘦身要点：
1. 清理前先落一份白名单（keep.txt）并纳入版本管理，避免误删生产模型
2. 删除前先 ollama stop 掉正在加载的实例，减少对在线请求的影响
3. 删完必须对比目录占用：没降通常是还有别名引用同一批 blob
4. cp 出来的别名（如 gpt-3.5-turbo）最容易变成「看不见的引用」
5. 定期把模型目录做离线快照，清理才有回滚余地
6. 大目录迁移/清理前先看文件系统余量，避免中途写满
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产清单固定到「模型名 + 量化标签 + 版本」三要素，禁止使用漂移的 `latest`，并把清单纳入 Git 管理。
2. 用「先查再拉」的幂等脚本预置模型，拉完打印 `ollama list` 与磁盘占用归档，部署可复现、异常可追溯。
3. 模型目录独立挂盘（`OLLAMA_MODELS`），体积与清单都在大盘上，迁移和清理都简单。
4. 用 `ollama show` 记录每个上线模型的量化级别、参数量、上下文与 Capabilities，作为容量规划的输入。
5. 显存紧张的机器优先用 `q4_K_M`；只有质量敏感场景才升到 `q8_0`，并同步评估显存与延迟收益。
6. 用 `ollama cp` 造「兼容名」（如 `gpt-3.5-turbo`）来适配老旧客户端，但要在清单里登记，避免清理时误以为无用。
7. 内网分发用「打包模型目录」而不是逐台拉取，省流量且 digest 可逐层校验。

### 踩坑记录

```text
坑 1：删除了模型，磁盘空间却没释放
结论：ollama rm 执行成功，du 显示的占用几乎不变。
原因：blob 是按内容寻址共享的，仍有其他 manifest（别名或不同标签，如 cp 出来的 gpt-3.5-turbo）在引用同一批 blob。
解法：先用 /api/tags 列出全部模型并核对 digest，把引用同一权重的别名一起删除；确认无引用后 blob 会在清理阶段回收。

坑 2：拉取中断后重试，担心要重新下载几百 MB
结论：网络断掉或手动取消后不敢重跑，怕重新下载。
原因：不了解 curl/CLI 的断点续传能力。
解法：直接重新执行 ollama pull 即可从断点续传；同一模型的并发拉取会共享同一份进度，不会翻倍占带宽。

坑 3：用嵌入模型去调 /api/generate，得到「does not support generate」
结论：请求直接报错，以为是模型没装好。
原因：模型能力不对口，嵌入模型（Capabilities 只有 embedding）不能用于文本生成。
解法：先 ollama show <模型> 看 Capabilities；嵌入用 /api/embed 或 /api/embeddings，
      生成/对话用 /api/generate、/api/chat。本机实测 all-minilm 调 /api/generate 即返回该错误。

坑 4：内网机器上按模型名拉取，报网络不可达
结论：目标机器完全无法访问 registry.ollama.ai。
原因：离线环境没有出网通道，且没有预置模型。
解法：在能出网的机器上 pull 后打包 OLLAMA_MODELS 目录拷过去；自建 registry 时用 --insecure 并
      注意 manifest 里的 digest 必须与 blob 内容一致。

坑 5：脚本解析 ollama ps 输出时崩了
结论：同一段解析代码在开发机好用，在服务器上取错列。
原因：ps 的表头随版本变化（0.40.4 有 NAME/ID/SIZE/PROCESSOR/CONTEXT/RUNNER/UNTIL，
      FAQ 记录的历史版本是 NAME/ID/SIZE/PROCESSOR/UNTIL）。
解法：改用 REST 接口 /api/ps 拿 JSON，或按表头名动态定位列，不要硬编码列序号。
```
