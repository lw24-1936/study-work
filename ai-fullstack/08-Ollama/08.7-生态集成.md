## 概述

Ollama 的生态价值在于「本地模型能被现有工具直接调用」，所以它同时提供三套接入面：**原生 REST API**（`/api/*`）、**OpenAI 兼容 API**（`/v1/*`，让已有 OpenAI SDK 一行 `base_url` 改过来）、以及官方的 **Python / JavaScript 客户端库**。在此之上，LangChain、LlamaIndex 这类编排框架、Open WebUI 这类前端、VS Code 与编码代理这类 IDE 侧工具，构成了完整的接入网络。接入本身很简单，难的是知道每一层各自支持哪些能力字段、哪些是 Ollama 尚未实现的（比如 `logprobs`、`tool_choice`），免得在迁移时踩空。

```text
全篇主线：
1. 兼容层 —— /v1 接口让 OpenAI SDK 直接改 base_url 就能用，但有明确的能力缺口
2. 官方库 —— ollama-python / ollama-js 覆盖原生接口全能力，含流式与异步
3. 编排框架 —— langchain-ollama 与 llama-index-llms-ollama 把 Ollama 当一份模型后端
4. 前端 —— Open WebUI 等以「一个 URL」接入，多用户与知识库交给它们
5. IDE —— VS Code 扩展与 ollama launch 把本地模型接进编辑器与编码代理
```

## OpenAI 兼容接口与迁移成本

Ollama 在本地服务上暴露 OpenAI 兼容端点：`/v1/chat/completions`、`/v1/completions`、`/v1/responses`（后者自 **Ollama v0.13.3** 起支持）以及 `/v1/models`。接入时把 `base_url` 指向 `http://localhost:11434/v1/`，`api_key` 必须给一个值但**会被 Ollama 忽略**（社区惯例填 `ollama`）。这意味着任何按 OpenAI 协议写的代码、SDK、编排框架，理论上只要改两行就能指向本地模型。

迁移前必须知道的边界：Ollama 只实现了 OpenAI API 的**子集**，而且明确列在官方文档里。

| `/v1/chat/completions` 支持项 | 不支持项 |
|------------------------------|----------|
| 流式、JSON mode、可复现输出（seed） | `logprobs` |
| 视觉（Base64 图片与图片内容块） | 图片 URL |
| 工具调用（tools） | `tool_choice` |
| reasoning / thinking 控制（部分模型） | `logit_bias`、`user`、`n` |
| `temperature`、`top_p`、`max_tokens`、`stop`、`seed`、`stream_options` | —— |

`/v1/completions` 支持流式、JSON mode、可复现输出；`/v1/responses` 只支持**无状态**用法，`previous_response_id` 与 `conversation` 都不支持。另有一个容易忽略的点：OpenAI 协议里没有设置上下文长度的字段，要改上下文必须在 Modelfile 里写 `PARAMETER num_ctx` 再用 `ollama create` 建一个模型。

```shell
# 用 curl 打一次 /v1/chat/completions，验证兼容层可用
curl -X POST http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5:7b",
    "messages": [{ "role": "user", "content": "用一句话说明本地推理的价值" }]
  }'

# 列出模型（OpenAI 协议风格）
curl http://localhost:11434/v1/models
```

```python
"""OpenAI SDK 直连本地 Ollama，迁移成本就是改两行。"""
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:11434/v1/",
    api_key="ollama",  # 必填但会被 Ollama 忽略
)

resp = client.chat.completions.create(
    model="qwen2.5:7b",
    messages=[{"role": "user", "content": "把这句话翻译成英文：本地推理，数据不出内网。"}],
    temperature=0,
)
print(resp.choices[0].message.content)

# /v1/responses（Ollama v0.13.3+，无状态）
out = client.responses.create(model="qwen2.5:7b", input="用一句话解释 KV cache")
print(out.output_text)
```

老工具链硬编码了 `gpt-3.5-turbo` 之类模型名时，不需要改代码，直接把本地模型复制成那个名字即可：

```shell
# 让硬编码 OpenAI 模型名的工具链直接指向本地模型
ollama cp qwen2.5:7b gpt-3.5-turbo

curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "gpt-3.5-turbo", "messages": [{"role": "user", "content": "Hello!"}]}'

# 需要固定上下文时，OpenAI 协议无法表达，改用 Modelfile
# FROM qwen2.5:7b
# PARAMETER num_ctx 8192
ollama create mymodel -f ./Modelfile
```

```text
OpenAI 兼容层要点：
1. base_url 指向 http://localhost:11434/v1/，api_key 必填但被忽略
2. 只实现协议子集：logprobs、tool_choice、logit_bias、user、n、图片 URL 都不支持
3. /v1/responses 自 v0.13.3 起支持，且只有无状态模式
4. 上下文长度不在 OpenAI 协议里，必须用 Modelfile 的 num_ctx 建专门模型
5. 硬编码模型名的老工具链用 ollama cp 复制出同名模型即可无侵入接入
```

## Python 客户端与异步调用

官方 `ollama` Python 库（`pip install ollama`）是对原生 REST API 的薄封装，用 httpx 做传输、pydantic 做响应模型，覆盖 chat / generate / embed / create / pull 等全部接口，并提供与同步客户端对称的 `AsyncClient`。相比裸 `requests`，它省掉了手写 JSON 与流式解析，且在流式场景下逐块返回带类型的对象。

本机实测：在 Python 3.14 的 venv 里用清华镜像安装，落地版本为 **ollama 0.6.3**，依赖 httpx 0.28.1、pydantic 2.14.1。注意该版本没有 `ollama.__version__` 属性，查版本要用 `pip show ollama` 或读 dist-info。

```shell
# 安装（网络受限时用清华镜像）
python3 -m venv .venv
./.venv/bin/pip install --index-url https://pypi.tuna.tsinghua.edu.cn/simple ollama

# 查版本
./.venv/bin/pip show ollama | head -3
```

```python
"""ollama-python 常用调用：同步、流式、嵌入、结构化输出。"""
import ollama

# 默认客户端连 http://127.0.0.1:11434，可用环境变量或参数改
client = ollama.Client(host="http://localhost:11434")

# 1) 非流式对话
resp = client.chat(
    model="qwen2.5:7b",
    messages=[{"role": "user", "content": "用两句话解释本地推理的优势"}],
    options={"temperature": 0.3, "num_ctx": 4096},
)
print(resp["message"]["content"])

# 2) 流式对话：逐块产出，适合打字机效果
stream = client.chat(
    model="qwen2.5:7b",
    messages=[{"role": "user", "content": "从 1 数到 10"}],
    stream=True,
)
for part in stream:
    print(part["message"]["content"], end="", flush=True)
print()

# 3) 文本嵌入（需要先 ollama pull nomic-embed-text）
emb = client.embed(model="nomic-embed-text", input=["本地推理", "数据不出内网"])
print("向量维度:", len(emb["embeddings"][0]))

# 4) 结构化输出：用 JSON Schema 约束返回结构
schema = {
    "type": "object",
    "properties": {"category": {"type": "string"}, "urgent": {"type": "boolean"}},
    "required": ["category", "urgent"],
}
tagged = client.chat(
    model="qwen2.5:7b",
    messages=[{"role": "user", "content": "把这条工单打标：登录不上，下午就要用。只输出 JSON。"}],
    format=schema,
    options={"temperature": 0},
)
print(tagged["message"]["content"])
```

异步版本在 Web 服务里是刚需，`AsyncClient` 的接口与同步版一一对应：

```python
"""异步并发调用：本地 Ollama 扛得住几十路并发时，用 asyncio 拉满吞吐。"""
import asyncio
from ollama import AsyncClient


async def tag(i: int) -> str:
    resp = await AsyncClient(host="http://localhost:11434").chat(
        model="qwen2.5:7b",
        messages=[{"role": "user", "content": f"给第 {i} 条工单分类，只输出类别名。"}],
        options={"temperature": 0, "num_predict": 16},
    )
    return resp["message"]["content"].strip()


async def main() -> None:
    # 并发 8 路（服务端 OLLAMA_NUM_PARALLEL 需相应调大，见 08.6）
    results = await asyncio.gather(*(tag(i) for i in range(8)))
    for i, r in enumerate(results):
        print(i, r)


if __name__ == "__main__":
    asyncio.run(main())
```

## JavaScript 客户端与浏览器调用

官方 `ollama` npm 包（`npm i ollama`）用法与 Python 版高度对齐：`new Ollama({host})` 建客户端，`chat` / `generate` / `embed` 等方法同名，流式响应是**异步迭代器**，用 `for await` 消费。它同时提供浏览器入口 `ollama/browser`，可以在前端页面里直接调本地 Ollama，前提是 Ollama 允许该页面的来源（CORS 由 `OLLAMA_ORIGINS` 控制，见 08.8）。

```shell
# 安装
npm i ollama

# 启动本地服务（浏览器跨源访问需要允许对应来源）
OLLAMA_ORIGINS=http://localhost:5173 ollama serve
```

```javascript
// chat.mjs —— Node 侧流式对话
import { Ollama } from 'ollama';

const ollama = new Ollama({ host: 'http://127.0.0.1:11434' });

const stream = await ollama.chat({
  model: 'qwen2.5:7b',
  messages: [{ role: 'user', content: '用三句话解释什么是量化' }],
  stream: true,
  options: { temperature: 0.3 },
});

for await (const part of stream) {
  process.stdout.write(part.message.content);
}
process.stdout.write('\n');
```

```javascript
// browser.js —— 前端页面里直连本地 Ollama（Vite/React 示例）
import ollama from 'ollama/browser';

export async function ask(prompt) {
  const resp = await ollama.chat({
    model: 'qwen2.5:7b',
    messages: [{ role: 'user', content: prompt }],
  });
  return resp.message.content;
}

// 带自定义请求头（例如经由反向代理时附带鉴权）
import { Ollama } from 'ollama/browser';
const proxied = new Ollama({
  host: 'https://llm.example.com',
  headers: { Authorization: 'Bearer <your-token>' },
});

// 生成接口与嵌入接口
const gen = await ollama.generate({ model: 'qwen2.5:7b', prompt: '写一句欢迎语' });
console.log(gen.response);

const emb = await ollama.embed({ model: 'nomic-embed-text', input: ['本地推理'] });
console.log(emb.embeddings[0].length);
```

```text
JavaScript 客户端要点：
1. npm i ollama，Node 侧用 { Ollama }，浏览器侧用 ollama/browser 默认导出
2. 流式响应是异步迭代器，用 for await 逐块消费
3. 浏览器直连必须配置 OLLAMA_ORIGINS，默认只放行 127.0.0.1 与 0.0.0.0
4. 经反向代理接入时用 headers 传鉴权，客户端本身不做认证
5. 云模型与本地模型走同一套 API，仅 host 与鉴权头不同
```

## LangChain 与 LlamaIndex

编排框架把 Ollama 视为一个聊天模型 / 嵌入模型后端。LangChain 侧用 `langchain-ollama` 包提供的 `ChatOllama` 与 `OllamaEmbeddings`；LlamaIndex 侧用 `llama-index-llms-ollama` 提供的 `Ollama`。两者都走原生 `/api` 接口，因此能力上没有 OpenAI 兼容层的字段缺口。

官方给出的 `ChatOllama` 能力矩阵如下（摘自 LangChain 文档）：

| 能力 | 是否支持 |
|------|----------|
| 工具调用 | 支持 |
| 结构化输出 | 支持 |
| 图像输入 | 支持 |
| 流式 | 支持（含 token 级） |
| 原生异步 | 支持 |
| token 用量统计 | 不支持 |
| logprobs | 支持 |

本机实测：`langchain-ollama` 落地版本 **1.1.0**（依赖 `langchain-core` 1.6.10）。

```shell
./.venv/bin/pip install --index-url https://pypi.tuna.tsinghua.edu.cn/simple langchain-ollama
# LlamaIndex 侧
./.venv/bin/pip install --index-url https://pypi.tuna.tsinghua.edu.cn/simple llama-index-llms-ollama
```

```python
"""langchain-ollama：聊天模型、结构化输出、流式与嵌入。"""
from langchain_ollama import ChatOllama, OllamaEmbeddings

llm = ChatOllama(
    model="qwen2.5:7b",
    base_url="http://localhost:11434",  # 也可用环境变量 OLLAMA_HOST 指定
    temperature=0,
    num_ctx=8192,          # 直接透传给原生接口，OpenAI 兼容层做不到
    num_predict=512,
)
print(llm.invoke("用一句话解释 LCEL").content)

# 结构化输出：用 pydantic 定义 schema
from pydantic import BaseModel, Field


class Ticket(BaseModel):
    """工单分类结果。"""
    category: str = Field(description="账号问题/支付问题/物流问题/商品质量/其他")
    urgent: bool = Field(description="是否紧急")


structured = llm.with_structured_output(Ticket)
print(structured.invoke("收到货屏幕有划痕，明天出差要用").model_dump())

# 流式
for chunk in llm.stream("从 1 数到 5"):
    print(chunk.content, end="", flush=True)

# 嵌入模型（用于 RAG 检索）
emb = OllamaEmbeddings(model="nomic-embed-text", base_url="http://localhost:11434")
print("向量维度:", len(emb.embed_query("本地推理")))
```

```python
"""llama-index-llms-ollama：完整调用、流式与结构化输出。"""
from llama_index.core.llms import ChatMessage
from llama_index.core.bridge.pydantic import BaseModel
from llama_index.llms.ollama import Ollama

llm = Ollama(
    model="qwen2.5:7b",
    base_url="http://localhost:11434",
    request_timeout=120.0,   # 官方提示默认超时 30 秒，本地慢时要调大
    context_window=8192,     # 手动限制上下文以控制显存
)
print(llm.complete("用一句话说明为什么本地模型适合处理内部数据").text)

# 流式
for r in llm.stream_complete("写一句欢迎语"):
    print(r.delta, end="", flush=True)
print()

# 结构化输出：直接把 pydantic 类交给模型
class Song(BaseModel):
    """一首歌，含名称与艺术家。"""
    name: str
    artist: str


sllm = llm.as_structured_llm(Song)
resp = sllm.chat([ChatMessage(role="user", content="随便说一首歌")])
print(resp.message.content)

# JSON mode（不需要严格 schema 时更省事）
llm_json = Ollama(model="qwen2.5:7b", json_mode=True, context_window=8192)
print(llm_json.complete("把 Paul Graham 的基本信息输出为 JSON 对象").text)
```

```text
编排框架接入要点：
1. LangChain 用 langchain-ollama 的 ChatOllama / OllamaEmbeddings（本机实测 1.1.0）
2. LlamaIndex 用 llama-index-llms-ollama 的 Ollama，request_timeout 默认 30 秒要按需调大
3. 两者都走原生接口，可以传 num_ctx 等参数，不受 OpenAI 兼容层字段缺失影响
4. 结构化输出优先用框架的 with_structured_output / as_structured_llm，别手写 JSON 解析
5. 嵌入模型要单独 pull（如 nomic-embed-text），RAG 检索质量取决于嵌入模型选型
```

## 前端与桌面应用集成

前端类应用的价值是把「多用户、会话管理、知识库、权限」这些工程件从零补齐，Ollama 只需提供一个 URL。Open WebUI 是其中最主流的选择，官方支持的接入方式是通过 `OLLAMA_BASE_URL` 指向 Ollama 服务；Docker 部署时 Ollama 必须监听 `0.0.0.0` 才能被容器访问，本地主机名在容器内要用 `host.docker.internal` 并加 `--add-host=host.docker.internal:host-gateway`。

```shell
# Open WebUI 单容器接入宿主机上的 Ollama（官方推荐的 Docker 路径）
# WEBUI_SECRET_KEY 用 openssl rand -hex 32 生成，固定不变，否则重建容器后所有人被登出
docker run -d -p 3000:8080 \
  --add-host=host.docker.internal:host-gateway \
  -v open-webui:/app/backend/data \
  -e WEBUI_SECRET_KEY=your-secret-key \
  --name open-webui --restart always \
  ghcr.io/open-webui/open-webui:main

# 让 Ollama 监听所有网卡，容器才能连上（本机开发谨慎：等于局域网可访问）
OLLAMA_HOST=0.0.0.0:11434 ollama serve

# 生产部署锁定版本，别用浮动 tag
docker pull ghcr.io/open-webui/open-webui:vX.Y.Z
```

```shell
# 指向远端 Ollama（例如内网的推理服务器，经反向代理暴露）
docker run -d -p 3000:8080 \
  -e OLLAMA_BASE_URL=https://llm.internal.example.com \
  -v open-webui:/app/backend/data \
  -e WEBUI_SECRET_KEY=your-secret-key \
  --name open-webui --restart always \
  ghcr.io/open-webui/open-webui:main
```

其它常见形态：Open WebUI 的 `:ollama` 镜像把 Ollama 与前端打在一个容器里，适合单机一体化部署；`:cuda` 变体自带 CUDA 12.8 运行时，需要配 `--gpus all`；`:main-slim` 把本地嵌入、语音、向量库全部剥离，要求 `RAG_EMBEDDING_ENGINE` 指向外部服务，否则文档上传与检索会返回 503。接入时最容易出错的是「模型列表为空」，官方排障文档给出的原因就是 Ollama 没有监听 `0.0.0.0`。

```text
前端集成要点：
1. 前端只认 URL，Ollama 侧必须监听 0.0.0.0（OLLAMA_HOST）才能被容器访问
2. Docker 内访问宿主用 host.docker.internal + --add-host 映射
3. WEBUI_SECRET_KEY 必须固定，否则容器重建后所有会话失效
4. 生产锁定版本 tag，:main / :latest 是滚动镜像，会随开发推进变化
5. 「模型列表为空」先查网络监听，再查 OLLAMA_ORIGINS 的跨源放行
```

## IDE 插件与编码代理接入

IDE 侧有两条路线。轻量路线是官方 VS Code 扩展（`Ollama.ollama`），装完即可在 VS Code Chat 里选用本地模型；重量路线是用 `ollama launch` 把本地模型接给编码代理（Claude Code、OpenCode 等）或个人助理 Agent，让它们把请求打到本地推理而不是云 API。

```shell
# 1) 启动本地服务
ollama serve

# 2) 交互式选择并启动一个编码代理（官方 integrations 文档里的入口）
ollama launch

# 3) 拉一个适合写代码的模型
ollama pull qwen2.5-coder:7b
ollama pull qwen2.5-coder:14b
```

VS Code 侧的操作路径：扩展市场搜索并安装 Ollama 扩展 → 打开 Chat 视图 → 在模型选择器里选 Ollama → 选择本地已拉取的模型。官方文档提示扩展需要本机 Ollama 服务在运行，且模型必须已经 `ollama pull` 到本地。把本地模型接给 Continue 这类第三方插件时，本质是配置一个 OpenAI 兼容的 provider：

```json
{
  "models": [
    {
      "title": "本地 Qwen2.5 Coder",
      "provider": "openai",
      "model": "qwen2.5-coder:7b",
      "apiBase": "http://localhost:11434/v1",
      "apiKey": "ollama",
      "contextLength": 8192
    }
  ]
}
```

```text
IDE 接入要点：
1. VS Code 用官方 Ollama 扩展，模型必须先 pull 到本地
2. ollama launch 是编码代理与个人助理的统一入口，按提示选代理即可
3. 第三方插件按 OpenAI 兼容 provider 配置：apiBase 指向 /v1，apiKey 随便填
4. 代码补全类场景要限制 num_ctx 与 num_predict，否则显存与延迟都会失控
5. 代理类工具会并发发长提示，务必按 08.6 的并发章节调好 OLLAMA_NUM_PARALLEL
```

## 应用场景实战

### 场景一：把已有 OpenAI 应用零改造切到本地模型并做灰度

某团队有个内部工单打标服务，代码基于 OpenAI SDK，出于数据合规要求需要把推理迁到内网。做法是让 `base_url` 与 `model` 变成配置项，本地跑 Ollama + 同款开源模型，用固定回归集对比准确率后灰度切流。

```python
"""双后端打标服务：配置决定走 OpenAI 还是本地 Ollama，便于灰度与回滚。"""
import json
import os

from openai import OpenAI

BACKEND = os.getenv("LLM_BACKEND", "local")  # local | openai

if BACKEND == "local":
    client = OpenAI(base_url="http://localhost:11434/v1/", api_key="ollama")
    MODEL = "qwen2.5:7b"
else:
    client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])
    MODEL = "gpt-4o-mini"

SCHEMA = {
    "type": "json_schema",
    "json_schema": {
        "name": "ticket_tag",
        "schema": {
            "type": "object",
            "properties": {
                "category": {
                    "type": "string",
                    "enum": ["账号问题", "支付问题", "物流问题", "商品质量", "其他"],
                },
                "urgent": {"type": "boolean"},
            },
            "required": ["category", "urgent"],
        },
    },
}

CASES = [
    ("登录不上，提示密码错误", "账号问题"),
    ("付款后订单一直没生成", "支付问题"),
    ("快递三天没动", "物流问题"),
    ("收到货屏幕有划痕", "商品质量"),
]


def tag(text: str) -> dict:
    resp = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role": "system", "content": "你是工单分类器，只输出 JSON。"},
            {"role": "user", "content": text},
        ],
        response_format=SCHEMA,
        temperature=0,
    )
    return json.loads(resp.choices[0].message.content)


if __name__ == "__main__":
    hit = 0
    for text, expect in CASES:
        got = tag(text)
        ok = got["category"] == expect
        hit += ok
        print(f"[{'OK ' if ok else 'BAD'}] 期望={expect} 实际={got}")
    print(f"后端={BACKEND} 分类准确率 {hit}/{len(CASES)} = {hit / len(CASES):.0%}")
```

灰度切换时，用环境变量把本地与云端按比例分流：先在本地实例上把回归集跑到与云端持平，再逐步提高本地流量比例。若上游工具链硬编码了模型名，用 `ollama cp qwen2.5:7b gpt-3.5-turbo` 做同名映射，代码一行不改。

```shell
# 准备本地后端
ollama cp qwen2.5:7b gpt-3.5-turbo          # 兼容硬编码模型名的旧工具链
OLLAMA_NUM_PARALLEL=2 OLLAMA_CONTEXT_LENGTH=8192 ollama serve

# 跑回归集：先在本地后端上验证准确率
LLM_BACKEND=local python3 tag_service.py

# 确认达标后按比例切流（应用层读环境变量或配置中心）
# LLM_BACKEND=local 的比例从 10% 逐步提到 100%
```

```text
迁移落地要点：
1. base_url 与 model 做成配置项，本地与云端同代码切换，出问题秒回滚
2. 迁移前先跑固定回归集，准确率持平再切流，别拿线上流量做实验
3. 结构化输出用 response_format/JSON Schema，本地小模型也能稳定产出字段
4. 硬编码模型名的老工具链用 ollama cp 做同名映射，零侵入
5. 灰度期间同时看本地与云端的延迟分位，本地吞吐上限由 NUM_PARALLEL 决定
```

### 场景二：用 LlamaIndex + Ollama 搭一个内网文档问答（RAG）服务

需求：把内网 PDF/Markdown 手册做成问答服务，数据不能出内网，检索与大模型都用本地 Ollama。做法是 LlamaIndex 做切分与向量索引，`nomic-embed-text` 做嵌入，生成模型用 `qwen2.5:7b`。

```shell
# 依赖与所需模型
./.venv/bin/pip install --index-url https://pypi.tuna.tsinghua.edu.cn/simple \
  llama-index-llms-ollama llama-index-embeddings-ollama llama-index-vector-stores-chroma

ollama pull nomic-embed-text
ollama pull qwen2.5:7b
```

```python
"""内网文档问答：本地嵌入 + 本地生成，全链路不出网。"""
from llama_index.core import Settings, SimpleDirectoryReader, VectorStoreIndex
from llama_index.embeddings.ollama import OllamaEmbedding
from llama_index.llms.ollama import Ollama

DOCS_DIR = "./docs"          # 手册目录：PDF / Markdown / txt
PERSIST_DIR = "./storage"    # 索引持久化目录

# 1) 全局模型配置：嵌入与生成都指向本地 Ollama
Settings.llm = Ollama(
    model="qwen2.5:7b",
    base_url="http://localhost:11434",
    request_timeout=180.0,   # 本地 CPU/低端 GPU 上首字可能很慢
    context_window=8192,
)
Settings.embed_model = OllamaEmbedding(
    model_name="nomic-embed-text",
    base_url="http://localhost:11434",
)

# 2) 建索引（首次会逐块调嵌入接口，耗时可观）
documents = SimpleDirectoryReader(DOCS_DIR, recursive=True).load_data()
index = VectorStoreIndex.from_documents(documents)
index.storage_context.persist(persist_dir=PERSIST_DIR)

# 3) 检索问答：带来源引用
query_engine = index.as_query_engine(similarity_top_k=4)
answer = query_engine.query("退换货的时效是怎么规定的？")
print(answer)
for node in answer.source_nodes:
    print("来源:", node.metadata.get("file_name"), "得分:", round(node.score or 0, 3))
```

```shell
# 常驻服务化：让嵌入与生成模型不反复卸载
OLLAMA_KEEP_ALIVE=-1 OLLAMA_CONTEXT_LENGTH=8192 ollama serve

# 单条查询的计时观测（嵌入与生成各占多少时间）
curl -s http://localhost:11434/api/embed -d '{"model":"nomic-embed-text","input":"退换货时效"}' | head -c 120
ollama ps
```

```text
RAG 集成要点：
1. 嵌入与生成模型分开选型：嵌入用小模型（nomic-embed-text），生成按显存选
2. 首次建索引会逐块调嵌入接口，先估算条数再决定是否加批处理与并发
3. 索引持久化到磁盘，重启不要重建；文档更新时做增量索引
4. 回答必须带来源引用（source_nodes），否则内网场景无法审计
5. 上下文长度与 top_k 一起决定显存与准确率，两者都要按硬件余量调
```

## 最佳实践与踩坑记录

### 最佳实践

1. 新项目直接用官方客户端（`ollama` / `ollama` npm 包）或编排框架，只有「已有 OpenAI 代码要迁移」时才走 `/v1` 兼容层，避免继承兼容层的能力缺口。
2. 迁移前把 `/v1` 支持与不支持字段列成清单核对一遍，特别是 `tool_choice`、`logprobs`、`n` 这三类常用但 Ollama 未实现的字段。
3. `base_url` 与模型名做成配置项，本地/云端同代码切换，灰度与回滚都只是改环境变量。
4. 结构化输出统一用框架能力（`with_structured_output`、`as_structured_llm`、`format`/`response_format`）声明 schema，不要写正则去抠模型输出。
5. 前端与 IDE 接入前先确认网络可达性：容器访问宿主用 `host.docker.internal`，浏览器直连要配 `OLLAMA_ORIGINS`。
6. 客户端并发上限对齐服务端 `OLLAMA_NUM_PARALLEL`，压测前按 08.6 的方法先估算显存，别把客户端并发当成免费吞吐。
7. 依赖版本钉死并记录（本机实测 ollama 0.6.3、langchain-ollama 1.1.0、langchain-core 1.6.10），框架升级常常改变默认参数与结构化输出行为。

### 踩坑记录

```text
坑 1：OpenAI SDK 迁移后工具调用报错，说参数不支持
结论：代码在 OpenAI 上跑得好好的，切到本地后 tool_choice 或并行工具调用直接失败。
原因：Ollama 的 /v1 只实现协议子集，官方明确列为不支持：logprobs、tool_choice、logit_bias、user、n、图片 URL。
解法：迁移前列出用到的字段逐条核对官方兼容性表；把 tool_choice 改成提示词约束或改用原生 /api/chat 的 tools。

坑 2：通过 OpenAI 协议改不动上下文长度
结论：长文档问答总是被截断，调 max_tokens 没有用。
原因：OpenAI 协议里没有上下文长度字段，num_ctx 只能由模型自身（Modelfile）或原生接口 options 决定。
解法：写一个 Modelfile 里带 PARAMETER num_ctx <N> 的模型，ollama create 后用它；或直接改走原生接口传 options.num_ctx。

坑 3：VS Code / 前端里模型列表是空的
结论：插件连上了但选不到模型，或前端一直报连接失败。
原因：Ollama 默认只监听 127.0.0.1；容器访问宿主机的 0.0.0.0 需要 OLLAMA_HOST，浏览器跨源需要 OLLAMA_ORIGINS 放行，且模型必须已 pull 到本地。
解法：以 OLLAMA_HOST=0.0.0.0:11434 启动，Docker 场景加 --add-host=host.docker.internal:host-gateway，跨源时配置 OLLAMA_ORIGINS；确认 ollama list 里有目标模型。

坑 4：浏览器直连本地 Ollama 报 CORS 错误
结论：前端 fetch 被浏览器拦截，控制台提示跨源请求被拒绝。
原因：Ollama 默认只允许来自 127.0.0.1 与 0.0.0.0 的跨源请求，开发服务器（如 localhost:5173）不在白名单。
解法：启动服务时设置 OLLAMA_ORIGINS=http://localhost:5173（多个来源用逗号分隔）；浏览器扩展需显式放行 chrome-extension://* 等来源。

坑 5：LlamaIndex 查询频繁超时
结论：请求在大文档上稳定失败，日志显示超时。
原因：官方文档说明 Ollama 集成默认 request_timeout 为 30 秒，本地低端 GPU 或 CPU 推理 prefill 很容易超过这个时间。
解法：显式设置 request_timeout=180.0（或按实测的最长查询耗时设），并用 context_window 限制上下文以降低显存压力。

坑 6：并发调用本地模型时大量请求排队甚至 503
结论：客户端同时发 16 路请求，延迟雪崩，部分返回 503。
原因：服务端 OLLAMA_NUM_PARALLEL 默认 1，其余请求进队列，队列上限 OLLAMA_MAX_QUEUE 默认 512；并行数还会按倍数放大上下文与显存。
解法：按显存余量把 OLLAMA_NUM_PARALLEL 调到 2~4 并同步降 num_ctx；客户端侧限流 + 指数退避，不要用无限重试放大压力。
```
