## 概述

Ollama 是一个把「本地大模型推理」打包成单文件可执行程序的运行时：装好之后会常驻一个 HTTP 服务（默认 `127.0.0.1:11434`），命令行 `ollama` 只是这个服务的客户端，模型权重以内容寻址（content-addressable）的 blob 形式落在本地磁盘上，按需拉取、按需加载进内存或显存。它同时提供原生 REST API、OpenAI 兼容接口与 Anthropic 兼容接口，因此既适合个人在笔记本上跑模型，也适合在服务器上做私有化部署。本篇覆盖四件事：怎么装（Linux / macOS / Windows / Docker）、装完是什么样（端口、目录、配置文件）、GPU 能不能加速（驱动与算力要求）、以及怎么把它做成开机自启的服务。模型本身的管理见 08.2，性能与显存估算见 08.6，运维加固见 08.8。

```text
本篇主线：
1. 安装 —— 官方脚本 / 手工解压 / 桌面安装包 / 容器镜像四条路径
2. 布局 —— 11434 端口、OLLAMA_MODELS 目录、blobs 与 manifests 分层、server.json
3. 加速 —— NVIDIA（驱动 550+）、AMD ROCm v7、Apple Metal、Vulkan 四条后端
4. 常驻 —— 手跑 ollama serve 只适合调试，生产用 systemd 或容器管理
5. 排障 —— 先看服务日志，再看 ollama ps 的 PROCESSOR 列是否落到 CPU
```

下面的命令输出均来自本机实测环境：Ubuntu 24.04、`ollama` 0.40.4，安装在 `/usr/local/bin/ollama`。本机 NVIDIA 驱动与内核模块版本不匹配（`nvidia-smi` 报 `Failed to initialize NVML: Driver/library version mismatch`），因此 GPU 相关行为只按官方文档描述，并单独标注哪些是本机实测、哪些未在本机验证。

## 各平台安装方式

Ollama 官方提供了四条安装路径，选择依据是「是否要集成到系统服务」与「是否要控制版本」。Linux 服务器推荐官方脚本（自带 systemd 单元创建逻辑），需要离线分发或固定版本时用手工解压的 tarball；macOS 与 Windows 用桌面安装包，它会同时装好 CLI、托盘应用并注册开机自启；不想污染宿主机则用 Docker 镜像。

| 平台 | 安装方式 | 适用场景 | 备注 |
|------|----------|----------|------|
| Linux | `curl -fsSL https://ollama.com/install.sh \| sh` | 服务器 / 开发机 | 自动识别 GPU 并解压对应库 |
| Linux | 手工下载 `ollama-linux-amd64.tar.zst` 解压到 `/usr` | 离线分发、固定版本 | 需自己建 systemd 单元 |
| Linux (ARM) | `ollama-linux-arm64.tar.zst` | ARM64 服务器 | 同上 |
| Linux (AMD) | 额外解压 `ollama-linux-amd64-rocm.tar.zst` | AMD 显卡 | ROCm 库与主包分开 |
| macOS | `ollama.dmg` 拖入 Applications | 桌面开发 | 要求 macOS Sonoma (14) 或更新 |
| Windows | `OllamaSetup.exe` | 桌面开发 | 支持 WSL2 内 GPU 加速 |
| 容器 | `ollama/ollama` / `ollama/ollama:rocm` | 服务器、K8s | 见下节 Docker 部署 |

Linux 官方脚本会检测发行版并创建 `ollama` 用户与 systemd 服务；升级就是重跑同一条脚本。需要固定版本时用 `OLLAMA_VERSION` 环境变量（官方示例 `OLLAMA_VERSION=0.5.7 sh`，版本号可在 GitHub releases 页查询）。手工解压的方式如下，注意升级时官方建议先清掉旧库再解压，避免新旧 `.so` 混用：

```shell
# 方式一：官方安装脚本（推荐，会同时创建 ollama 用户与 systemd 服务）
curl -fsSL https://ollama.com/install.sh | sh

# 方式二：手工下载解压（离线分发 / 固定版本）
# 升级前按官方文档先清掉旧库，避免新旧库混用
sudo rm -rf /usr/lib/ollama
curl -fsSL https://ollama.com/download/ollama-linux-amd64.tar.zst \
    | sudo tar x -C /usr

# 指定版本安装（例：0.5.7，版本号以 releases 页面为准）
curl -fsSL https://ollama.com/install.sh | OLLAMA_VERSION=0.5.7 sh

# AMD 显卡额外解压 ROCm 库
curl -fsSL https://ollama.com/download/ollama-linux-amd64-rocm.tar.zst \
    | sudo tar x -C /usr

# 验证：先起服务，再用 -v 看客户端版本
ollama serve &
ollama -v
```

本机实测的版本输出只有一行（0.40.4）：

```text
$ ollama -v
ollama version is 0.40.4
```

macOS 侧的硬性要求是 macOS Sonoma（v14）或更新，Apple M 系列可同时用 CPU 与 GPU（Metal），x86 机器只有 CPU。安装方式是挂载 `ollama.dmg` 后把应用拖进 `Applications`；首次启动若 PATH 中没有 `ollama` CLI，应用会请求权限在 `/usr/local/bin` 建软链。模型与配置统一在 `~/.ollama`，日志在 `~/.ollama/logs`（`app.log` 是 GUI 日志，`server.log` 是服务端日志）。

Windows 侧用安装包安装，安装器会把二进制目录加入用户 PATH，服务端日志在 `%LOCALAPPDATA%\Ollama`（当次为 `server.log`，历史为 `server-#.log`），模型目录在 `C:\Users\<用户名>\.ollama\models`。GPU 加速在 WSL2 里可用，但 Docker Desktop for macOS 不支持 GPU 直通，这条边界要提前和团队说清楚。

```text
各平台安装要点：
1. Linux 生产用官方脚本，它顺带创建 ollama 用户与 systemd 单元；桌面用安装包
2. 升级 = 重跑安装脚本；手工解压升级前先删旧库目录，防新旧 .so 混用
3. 固定版本用 OLLAMA_VERSION 环境变量，值以 GitHub releases 页为准
4. macOS 要求 Sonoma (14)+，x86 机器只能走 CPU；模型在 ~/.ollama/models
5. Windows 模型目录在用户目录下；Docker Desktop(macOS) 无 GPU，WSL2 才支持
6. 桌面版默认注册开机自启，不需要可在「登录项 / 启动应用」里关闭
```

## 服务端口与模型目录

Ollama 的架构是「一个常驻服务 + 多个客户端」。服务默认只监听 `127.0.0.1:11434`，用 `OLLAMA_HOST` 改变监听地址（形如 `0.0.0.0:11434` 或 `http://0.0.0.0:11434`）；本地 API 不需要任何鉴权，因此把它暴露到网络前务必清楚后果（见 08.8）。客户端（`ollama` 命令行、SDK、Playwright 之外的任何 HTTP 调用方）都通过 `OLLAMA_HOST` 指向服务地址。

模型存放位置由 `OLLAMA_MODELS` 决定，各平台默认值不同：Linux 用官方脚本安装时是 `/usr/share/ollama/.ollama/models`，macOS 是 `~/.ollama/models`，Windows 是 `C:\Users\<用户名>\.ollama\models`。目录内部是标准 OCI 分层结构：`manifests/` 记录「某个模型名:标签 → 一堆 blob」的映射，`blobs/` 存实际内容（权重、模板、参数、许可证），文件名是 `sha256-<digest>`。多个模型共享同一份基座 blob，所以复制一个模型基本不占额外磁盘。

```shell
# 查看当前服务的监听地址与版本（默认 127.0.0.1:11434）
curl http://localhost:11434/api/version

# 改变监听地址，让局域网内其他机器可用
OLLAMA_HOST=0.0.0.0:11434 ollama serve

# 客户端指向远端服务（所有子命令都会读这个变量）
OLLAMA_HOST=http://10.0.0.12:11434 ollama list

# 自定义模型目录（迁移磁盘时最常用）
OLLAMA_MODELS=/data/ollama/models ollama serve
# Linux 用官方脚本安装时，模型目录必须对 ollama 用户可写
sudo chown -R ollama:ollama /data/ollama/models
```

本机实测：在 `/root/.ollama/models` 下能看到 `blobs/` 与内容寻址的文件名，拉取过程中还会出现 `-partial` 中间文件；同一份存储根目录里另有 `id_ed25519(.pub)`（用于 push / 拉私有模型 / 云模型）与 `cache/model-recommendations.json`（模型推荐缓存）。

```text
$ curl http://localhost:11434/api/version
{"version":"0.40.4"}

$ find /root/.ollama/models -maxdepth 1
/root/.ollama/models
/root/.ollama/models/blobs
```

除环境变量外，0.40 系列还支持一个服务端配置文件 `~/.ollama/server.json`，官方 FAQ 用它来关闭云功能（等价于 `OLLAMA_NO_CLOUD=1`）：

```json
{
  "disable_ollama_cloud": true
}
```

```text
服务端口与目录要点：
1. 默认监听 127.0.0.1:11434，本地 API 无鉴权，改 OLLAMA_HOST 暴露前三思
2. 模型默认目录：Linux(脚本安装) /usr/share/ollama/.ollama/models，macOS ~/.ollama/models
3. OLLAMA_MODELS 决定模型落盘位置，迁移前先把目录属主改成 ollama
4. 存储是 manifests + blobs 两层内容寻址结构，同基座模型共享 blob，cp 几乎不占空间
5. 服务端开关优先看 ~/.ollama/server.json，其次才是环境变量
6. ollama serve --help 会打印全部可用环境变量，是排障时的第一手清单
```

## GPU 支持与驱动要求

Ollama 的算力后端按平台自动选择：NVIDIA 走 CUDA 库，AMD 走 ROCm（部分场景走 Vulkan），Apple 走 Metal，其余走 Vulkan 或纯 CPU。NVIDIA 的硬性门槛是**算力（compute capability）5.0 及以上、驱动 550 及以上**；算力落在 5.0 到 6.2 之间的老卡要求驱动 570 及以上。AMD 在 Linux 上要求 ROCm v7 驱动，Windows 上要求 ROCm v7 / HIP7 的驱动栈；官方明确说明 Ollama 内置的是 ROCm 7 库，如果系统驱动还是 ROCm 6.x，GPU 发现阶段会挂到超时再退回 CPU。

多卡机器可以用设备可见性变量限制 Ollama 用哪几张卡：NVIDIA 用 `CUDA_VISIBLE_DEVICES`（官方建议优先用 UUID，数字 ID 顺序可能变化），AMD 用 `ROCR_VISIBLE_DEVICES`，Vulkan 用 `GGML_VK_VISIBLE_DEVICES`。想强制只跑 CPU，官方给的做法是把设备 ID 设成无效值（例如 `-1`）。

```shell
# 确认显卡型号、驱动版本与算力（NVIDIA）
nvidia-smi
nvidia-smi -L          # 打印 UUID，多卡限流时优先用 UUID

# 只让 Ollama 用第 0、2 张卡
CUDA_VISIBLE_DEVICES=0,2 ollama serve

# 强制走 CPU（设备 ID 设为无效值）
CUDA_VISIBLE_DEVICES=-1 ollama serve

# 显存不够时常用的两个开关：Flash Attention 与 KV cache 量化
OLLAMA_FLASH_ATTENTION=1 OLLAMA_KV_CACHE_TYPE=q8_0 ollama serve
```

上下文长度与显存直接挂钩：官方文档给出按显存分档的默认上下文（显存 < 24 GiB 给 4k，24-48 GiB 给 32k，≥ 48 GiB 给 256k），可用 `OLLAMA_CONTEXT_LENGTH` 覆盖。注意官方 FAQ 与 Modelfile 参考里对 `num_ctx` 默认值的表述不完全一致（FAQ 写 4096，Modelfile 表写 2048），实际以运行版本为准，最可靠的办法是看服务启动日志里那一行 `vram-based default context`。

本机实测（Ubuntu 24.04 + 0.40.4）：GPU 未能被发现，服务退化为纯 CPU 推理。两个证据都来自真实输出：

```text
$ nvidia-smi
Failed to initialize NVML: Driver/library version mismatch
NVML library version: 580.178

# OLLAMA_DEBUG=1 ollama serve 的启动日志（截取）
level=DEBUG msg="GPU bootstrap discovery took" duration=997.84µs
level=INFO  msg="failure during llama-server GPU discovery"
            error="llama-server binary not found (checked: /usr/local/lib/ollama/llama-server, ...)"
level=INFO  msg="inference compute" id=cpu library=cpu ... total="19.2 GiB" available="9.6 GiB"
level=INFO  msg="vram-based default context" total_vram="0 B" default_num_ctx=4096
```

也就是说：在本机既能观察到「NVML 驱动/库版本不匹配」这个典型症状，也能看到 Ollama 自己的兜底逻辑——发现不到任何 GPU 设备时按 `total_vram=0 B` 自动把默认上下文设成 4096，仍可运行，只是慢。修复顺序按官方 troubleshooting：确认驱动是最新的，重载 `nvidia_uvm`（`sudo rmmod nvidia_uvm && sudo modprobe nvidia_uvm`），容器场景先用 `docker run --gpus all ubuntu nvidia-smi` 验证运行时，仍不行就重启。本节未在本机验证的部分：GPU 加速后的 `ollama ps` 应显示 `100% GPU`、以及显存分档对应的默认上下文 32k / 256k 两档。

```text
GPU 与驱动要点：
1. NVIDIA 要求算力 5.0+ 与驱动 550+；算力 5.0~6.2 的老卡要求驱动 570+
2. AMD 在 Linux 需要 ROCm v7 驱动，内置 ROCm 7 库与老驱动不匹配会退回 CPU
3. 多卡限流：CUDA_VISIBLE_DEVICES / ROCR_VISIBLE_DEVICES / GGML_VK_VISIBLE_DEVICES
4. 上下文按显存分档：<24GiB→4k，24-48GiB→32k，≥48GiB→256k，可用 OLLAMA_CONTEXT_LENGTH 覆盖
5. 判断是否真的用了 GPU：先看服务日志的 inference compute 行，再看 ollama ps 的 PROCESSOR 列
6. num_ctx 的默认值在官方 FAQ 与 Modelfile 参考中表述不一致，以启动日志为准
```

## Docker 部署

容器化部署的价值在于「把运行时和模型存储解耦」：镜像里只有运行时，模型放在命名卷或宿主机目录，升级镜像不丢模型。CPU 版本一条命令即可；NVIDIA 版本需要先装 NVIDIA Container Toolkit 并让 docker 认识到 nvidia runtime；AMD 版本换 `:rocm` 标签并把 `/dev/kfd`、`/dev/dri` 传进去。Vulkan 在 `ollama/ollama` 镜像里默认启用，容器能访问 GPU 设备时就会生效，可用 `OLLAMA_VULKAN=0` 关掉。

```shell
# 1) CPU 版本：命名卷持久化模型
docker run -d -v ollama:/root/.ollama -p 11434:11434 --name ollama ollama/ollama

# 2) NVIDIA 版本：先装 NVIDIA Container Toolkit，再配置 docker runtime
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
docker run -d --gpus=all -v ollama:/root/.ollama -p 11434:11434 --name ollama ollama/ollama

# 3) AMD 版本：换 rocm 标签并透传设备
docker run -d --device /dev/kfd --device /dev/dri \
  -v ollama:/root/.ollama -p 11434:11434 --name ollama ollama/ollama:rocm

# 4) 模型目录放宿主机（迁移 / 备份更直观），注意属主
docker run -d --gpus=all -v /data/ollama:/root/.ollama \
  -p 11434:11434 --name ollama ollama/ollama

# 5) 容器内执行 CLI：拉模型、跑会话
docker exec -it ollama ollama pull llama3.2
docker exec -it ollama ollama run llama3.2

# 6) 日志与代理
docker logs -f ollama
docker run -d -e HTTPS_PROXY=https://my.proxy.example.com -p 11434:11434 ollama/ollama
```

企业网络里常见的两个额外动作：一是走 HTTPS 代理，官方 FAQ 明确提醒**只设置 `HTTPS_PROXY`，不要设 `HTTP_PROXY`**（Ollama 拉模型只用 HTTPS，设了 `HTTP_PROXY` 反而可能打断客户端到服务端的连接）；二是自签证书代理，需要把 CA 证书打进镜像：

```dockerfile
FROM ollama/ollama
COPY my-ca.pem /usr/local/share/ca-certificates/my-ca.crt
RUN update-ca-certificates
```

```shell
docker build -t ollama-with-ca .
docker run -d -e HTTPS_PROXY=https://my.proxy.example.com -p 11434:11434 ollama-with-ca
```

Jetson 设备上官方说明 Ollama 无法自动识别 JetPack 版本，需要显式传 `JETSON_JETPACK=5` 或 `JETSON_JETPACK=6`。Docker 里如果一开始能用 GPU、过一段时间莫名退到 CPU，官方 troubleshooting 给的解法是在宿主机 `/etc/docker/daemon.json` 加 `"exec-opts": ["native.cgroupdriver=cgroupfs"]` 关闭 systemd cgroup 管理。

```text
Docker 部署要点：
1. 模型放命名卷（-v ollama:/root/.ollama），升级镜像不丢模型
2. NVIDIA 必须先装 Container Toolkit 并 nvidia-ctk runtime configure --runtime=docker
3. AMD 用 :rocm 标签 + --device /dev/kfd --device /dev/dri；SELinux 环境可能要 setsebool
4. 代理只设 HTTPS_PROXY；自签证书要 update-ca-certificates 打进镜像
5. Jetson 需显式设置 JETSON_JETPACK；GPU 中途掉到 CPU 可改 cgroupdriver 解决
6. 容器里没有 CLI 也一样，docker exec -it ollama ollama ... 即可
```

## 服务进程与开机自启

调试阶段用手跑 `ollama serve` 很舒服（日志直接打在终端上），但生产必须交给进程管理器。官方给出的 Linux 方案是 systemd 单元 + 专用 `ollama` 用户；配置项通过 `systemctl edit ollama` 生成 override 文件，而不是直接改主单元文件，这样升级时自定义配置不会被覆盖。Windows 与 macOS 由桌面应用自己托管服务并注册登录项。

```shell
# 创建专用用户（官方脚本安装时会自动做这一步）
sudo useradd -r -s /bin/false -U -m -d /usr/share/ollama ollama
sudo usermod -a -G ollama $(whoami)
```

```ini
# /etc/systemd/system/ollama.service
[Unit]
Description=Ollama Service
After=network-online.target

[Service]
ExecStart=/usr/bin/ollama serve
User=ollama
Group=ollama
Restart=always
RestartSec=3
Environment="PATH=$PATH"

[Install]
WantedBy=multi-user.target
```

```shell
# 启用并启动
sudo systemctl daemon-reload
sudo systemctl enable ollama
sudo systemctl start ollama
sudo systemctl status ollama

# 用 override 加环境变量（生成 /etc/systemd/system/ollama.service.d/override.conf）
sudo systemctl edit ollama
# 日志跟随
journalctl -e -u ollama
```

override 文件的内容形态如下（示例为开启调试与调整保活时间）：

```ini
# /etc/systemd/system/ollama.service.d/override.conf
[Service]
Environment="OLLAMA_DEBUG=1"
Environment="OLLAMA_HOST=0.0.0.0:11434"
Environment="OLLAMA_KEEP_ALIVE=30m"
Environment="OLLAMA_CONTEXT_LENGTH=8192"
```

Nginx 反代是最常见的「对外只开一个端口」的做法，官方 FAQ 给的最小配置如下（注意 `proxy_set_header Host localhost:11434`，Ollama 对 Host 头敏感）：

```nginx
server {
    listen 80;
    server_name example.com;
    location / {
        proxy_pass http://localhost:11434;
        proxy_set_header Host localhost:11434;
    }
}
```

```text
服务进程与自启要点：
1. 生产别用前台 ollama serve，用 systemd（Linux）或桌面应用托管（macOS/Windows）
2. 自定义配置写进 systemctl edit 的 override，不直接改主单元文件
3. OLLAMA_KEEP_ALIVE 决定模型驻留时长，API 的 keep_alive 参数优先级更高
4. 反代要带上 proxy_set_header Host localhost:11434，否则可能 403/空响应
5. journalctl -e -u ollama 是 Linux 上看服务日志的标准姿势
6. 升级后记得 systemctl daemon-reload；删服务时同时清理 ollama 用户与模型目录
```

## 应用场景实战

### 场景一：把单机部署改造成团队共享的推理服务

某算法小组有台 8 卡机器（本机环境无 GPU，以下步骤中「GPU 生效」需在真机验证），希望把它变成团队共用的 Ollama 服务：局域网可访问、模型目录在大盘上、服务崩溃自动重启、能限制并发与队列长度。做法是改 systemd override 指定监听地址与模型目录，同时用服务端变量约束并发，最后在客户端侧用 `OLLAMA_HOST` 统一接入。

```shell
# 1) 准备大盘目录并交给 ollama 用户
sudo mkdir -p /data/ollama/models
sudo chown -R ollama:ollama /data/ollama

# 2) 写 override：监听、模型目录、并发与保活
sudo mkdir -p /etc/systemd/system/ollama.service.d
sudo tee /etc/systemd/system/ollama.service.d/override.conf > /dev/null <<'EOF'
[Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"
Environment="OLLAMA_MODELS=/data/ollama/models"
Environment="OLLAMA_KEEP_ALIVE=30m"
Environment="OLLAMA_MAX_LOADED_MODELS=3"
Environment="OLLAMA_NUM_PARALLEL=4"
Environment="OLLAMA_MAX_QUEUE=512"
Environment="OLLAMA_FLASH_ATTENTION=1"
Environment="OLLAMA_KV_CACHE_TYPE=q8_0"
EOF

# 3) 生效并观察
sudo systemctl daemon-reload
sudo systemctl restart ollama
sleep 3
journalctl -e -u ollama --no-pager | tail -20

# 4) 健康检查与冒烟测试（在任意能访问该主机的机器上执行）
curl -s http://10.0.0.12:11434/api/version
OLLAMA_HOST=http://10.0.0.12:11434 ollama pull qwen3:8b
OLLAMA_HOST=http://10.0.0.12:11434 ollama run qwen3:8b "用一句话说明你是谁"
```

服务端并发相关的三个变量含义要记牢：`OLLAMA_MAX_LOADED_MODELS` 限制同时加载的模型数，`OLLAMA_NUM_PARALLEL` 限制单个模型的并行请求数（会按倍数放大上下文占用），`OLLAMA_MAX_QUEUE` 是排队上限，超过就返回 503。对共享服务来说，把 `OLLAMA_NUM_PARALLEL` 调大而没同步评估显存，是最常见的「上线半小时后全员变慢」的原因。

```text
共享服务检查清单：
1. 先用 journalctl 确认服务真的监听到了 0.0.0.0:11434（而不是 127.0.0.1）
2. 模型目录属主必须是 ollama，否则 pull 会报权限错误
3. 并发三件套（MAX_LOADED_MODELS / NUM_PARALLEL / MAX_QUEUE）要按显存与业务峰值一起定
4. 对外暴露前必须想清楚鉴权方案：Ollama 本地 API 无鉴权，靠反代或网关补
5. 用 /api/version 做存活探针，用一次真实生成做就绪探针
6. 变更配置一律走 systemctl edit，保证升级不覆盖
```

### 场景二：用 Docker Compose 在内网做一套可复现的推理环境

某项目要在内网（能连外网但受限）跑一批离线推理任务，要求环境可复现、模型可预置、容器内有健康检查。思路是用 Compose 声明服务，模型目录挂宿主机（便于离线预置），`HTTPS_PROXY` 从 `.env` 注入，健康检查直接打 `/api/version`。

```yaml
# docker-compose.yml
services:
  ollama:
    image: ollama/ollama:latest
    container_name: ollama
    restart: always
    ports:
      - "127.0.0.1:11434:11434"      # 只在本机暴露，对外交给网关
    volumes:
      - /data/ollama:/root/.ollama    # 模型与配置持久化到宿主机
    environment:
      OLLAMA_KEEP_ALIVE: "30m"
      OLLAMA_MAX_LOADED_MODELS: "2"
      OLLAMA_NUM_PARALLEL: "2"
      HTTPS_PROXY: "${HTTPS_PROXY:-}" # 只设 HTTPS，不要设 HTTP_PROXY
    healthcheck:
      test: ["CMD-SHELL", "ollama -v >/dev/null 2>&1 || exit 1"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 20s
```

```shell
# 启动
docker compose up -d

# 预置模型（离线分发时把 /data/ollama 整体打包拷到目标机器即可）
docker compose exec ollama ollama pull llama3.2:3b
docker compose exec ollama ollama pull all-minilm:latest

# 巡检
docker compose ps
docker compose exec ollama ollama list
docker compose exec ollama ollama ps
curl -s http://127.0.0.1:11434/api/tags
```

把模型目录整体打包迁移是内网部署里最省事的办法：`blobs` 是内容寻址的，落地到另一台机器后名称不变、digest 可校验，`ollama list` 立刻就能看到模型，连拉取流量都省了。迁移前记得先停服务（避免 `-partial` 中间文件被一起打包），迁移后修正属主与权限。

```text
容器化落地要点：
1. 端口只绑 127.0.0.1，对外统一走网关/反代，避免无鉴权 API 直接裸奔
2. 模型目录挂宿主机目录，内网迁移直接打包该目录，省下拉取流量
3. 只注入 HTTPS_PROXY；自签证书环境要把 CA 打进镜像
4. 健康检查用 ollama -v 或 /api/version，别用重推理请求（会白占算力）
5. 打包迁移前先停容器，避免把 -partial 中间文件当模型带走
6. 镜像标签与模型标签都要固定小版本，才能做到「环境可复现」
```

## 最佳实践与踩坑记录

### 最佳实践

1. 生产环境一律用 systemd（Linux）或容器编排托管服务，不要依赖前台 `ollama serve`；自定义配置写在 `systemctl edit` 的 override 里，升级不丢配置。
2. 模型目录从第一天就放在独立大盘上（`OLLAMA_MODELS`），并保证属主是 `ollama` 用户，避免日后磁盘写满才发现没法迁。
3. 暴露到网络前先明确鉴权方案：本地 API 无鉴权，标准做法是只绑 `127.0.0.1` + 网关/Nginx 反代并加认证。
4. 记录并固化三组参数：监听与目录类（`OLLAMA_HOST` / `OLLAMA_MODELS`）、性能类（`OLLAMA_FLASH_ATTENTION` / `OLLAMA_KV_CACHE_TYPE` / `OLLAMA_CONTEXT_LENGTH`）、并发类（`OLLAMA_MAX_LOADED_MODELS` / `OLLAMA_NUM_PARALLEL` / `OLLAMA_MAX_QUEUE`）。
5. 用 `OLLAMA_DEBUG=1` 只在排障时开启，启动日志里 `inference compute` 与 `vram-based default context` 两行是判断「到底用了什么设备、上下文多大」的权威依据。
6. 容器镜像与模型标签都固定版本，并保留一份模型目录的离线副本，保证内网/断网环境可复现。
7. 驱动与容器运行时升级后，用 `nvidia-smi` 与一次真实推理双重确认，别只看服务起没起来。

### 踩坑记录

```text
坑 1：服务起来了，但推理极慢，ollama ps 显示 PROCESSOR 是 100% CPU
结论：GPU 没被用上，模型全在内存里跑。
原因：驱动版本不达标（NVIDIA 需 550+，算力 5.0~6.2 需 570+），或容器没配 nvidia runtime，
      或 Linux 休眠恢复后 nvidia_uvm 失效导致设备发现失败。
解法：nvidia-smi 确认驱动；容器先跑 docker run --gpus all ubuntu nvidia-smi；
      Linux 上 sudo rmmod nvidia_uvm && sudo modprobe nvidia_uvm；仍不行按官方建议重启并升级驱动。
      本机实测即为此类：nvidia-smi 报 NVML Driver/library version mismatch，日志退化为 id=cpu。

坑 2：局域网访问 11434 被拒或被 Host 头拒绝
结论：同事的机器连不上，或通过反代访问返回 403/空响应。
原因：Ollama 默认只监听 127.0.0.1；反代没把 Host 头改写成 localhost:11434。
解法：服务端设 OLLAMA_HOST=0.0.0.0:11434 并重启；Nginx 加 proxy_set_header Host localhost:11434；
      浏览器扩展等跨源场景还要在 OLLAMA_ORIGINS 里显式加来源（如 chrome-extension://*）。

坑 3：拉模型报磁盘写入失败或权限错误
结论：pull 到一半失败，或模型目录里出现残留的 -partial 文件。
原因：把 OLLAMA_MODELS 指到新目录后没有改属主，Linux 上 ollama 用户无写权限。
解法：sudo chown -R ollama:ollama <目录>；确认所在文件系统未满；清掉 -partial 后重试（拉取可断点续传）。

坑 4：容器里一开始有 GPU，运行一段时间后自动退回 CPU
结论：日志出现 GPU discovery 失败，推理变慢。
原因：Docker 使用 systemd cgroup 驱动时与 NVIDIA runtime 的兼容问题。
解法：宿主机 /etc/docker/daemon.json 加 "exec-opts": ["native.cgroupdriver=cgroupfs"]，重启 docker。

坑 5：手工解压升级后报库加载失败或行为异常
结论：升级后服务起不来，或出现莫名崩溃。
原因：新版本二进制仍在找旧版 /usr/lib/ollama 下的 .so，新旧库混用。
解法：升级前先 sudo rm -rf /usr/lib/ollama 清旧库，再解压新包，然后重启服务。
```
