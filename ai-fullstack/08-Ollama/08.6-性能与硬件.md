## 概述

本地推理的性能由三个变量共同决定：**多少算力**（GPU 还是 CPU、卸载了多少层）、**多少显存被权重和 KV cache 吃掉**、**同时要服务多少请求**。Ollama 自己负责显存调度与卸载层数决策，但它只能在你给出的参数空间里做取舍，所以「跑不动」「跑得慢」「并发一上来就 503」这三类问题，答案都在本篇的参数与硬件账里。这一篇给出的是估算方法、可复制的调参命令与观测手段，而不是某一台机器的固定性能数字。

```text
全篇主线：
1. 卸载 —— GPU 卸载层数决定多少权重进显存，剩下的留在内存里拖慢推理
2. 显存 —— 权重 + KV cache + 计算缓冲三部分之和，决定「能不能装下」
3. 上下文 —— num_ctx 是最常被忽视的显存黑洞，KV cache 随上下文近线性增长
4. 量化 —— 量化级别在体积、速度、质量之间做取舍，Q4_K_M 是通用默认
5. 并发 —— OLLAMA_NUM_PARALLEL 与 OLLAMA_MAX_QUEUE 决定多用户吞吐与 503 边界
```

## 硬件支持与 GPU 卸载层数

Ollama 官方对 NVIDIA 的要求是 **compute capability 5.0 及以上、驱动 550 及以上**；其中 compute capability 5.0 到 6.2 的老卡需要驱动 570 及以上。显卡能力不足时 Ollama 不会报错退出，而是静默回退到 CPU 推理，速度会掉一个数量级，所以「模型跑起来了但很慢」的第一件事是确认它到底跑在哪。

| 计算能力 | 典型显卡 |
|----------|----------|
| 12.0 | GeForce RTX 50 系列（5060 ~ 5090） |
| 9.0 | H100、H200 |
| 8.9 | RTX 40 系列（4060 ~ 4090）、L4、L40 |
| 8.6 | RTX 30 系列（3050 ~ 3090 Ti）、A40、A10 |
| 8.0 | A100、A30 |
| 7.5 | RTX 20 系列、T4、Quadro RTX 系列 |
| 7.0 | V100、TITAN V |
| 6.1 及以下 | GTX 10 系列、Tesla P40/P4、Tesla P100 等（需驱动 570+） |

「卸载层数」是 Ollama 调度的核心概念：Transformer 的每一层都可以选择放在显存还是内存里，显存放得多就快，放得少就慢。Ollama 启动模型时会评估可用显存，自动决定卸载多少层；多张卡时，如果模型能完整装进任意单卡，就加载到那张单卡上（减少 PCIe 数据传输），装不下才跨卡切分。手工干预有两种方式：Modelfile 里的 `PARAMETER num_gpu`（层数，0 相当于强制 CPU），以及用 `CUDA_VISIBLE_DEVICES` 限定可见的卡。CPU 路径则用 `PARAMETER num_thread` 控制线程数，一般设为物理核心数。

```shell
# 1) 查看 NVIDIA 显卡与驱动版本（Ollama 要求驱动 550+）
nvidia-smi

# 2) 查看模型实际加载到哪：PROCESSOR 列就是 CPU/GPU 比例
ollama ps

# 3) 只让 Ollama 看到第 0、1 号卡（要更稳可换成 UUID，用 nvidia-smi -L 查）
CUDA_VISIBLE_DEVICES=0,1 ollama serve

# 4) 强制纯 CPU（用于确认是不是 GPU 路径出的问题）
CUDA_VISIBLE_DEVICES=-1 ollama serve
```

`ollama ps` 的输出里，`PROCESSOR` 列有三类取值，直接说明卸载情况：`100% GPU` 表示全部层在显存中；`100% CPU` 表示全部在内存中；`48%/52% CPU/GPU` 这类表示部分卸载，性能介于两者之间。下面是官方文档给出的输出形态：

```text
NAME        ID            SIZE    PROCESSOR   UNTIL
llama3:70b  bcfb190ca3a7  42 GB   100% GPU    4 minutes from now
```

本机实测：Ollama 客户端已安装但未随系统启动服务，且 NVIDIA 内核驱动与用户态库版本不匹配，GPU 路径**未在本机验证**：

```text
$ which ollama
/usr/local/bin/ollama

$ ollama --version
Warning: could not connect to a running Ollama instance
Warning: client version is 0.40.4

$ nvidia-smi
Failed to initialize NVML: Driver/library version mismatch
NVML library version: 580.178
```

上述 `nvidia-smi` 报错意味着内核里的 `nvidia.ko` 与用户态 `libnvidia-ml.so` 版本不一致，此时任何依赖 NVML 的程序（包括 Ollama 的显存探测）都拿不到显卡信息。修复方式是重装与内核模块匹配的驱动并重启，或按官方 GPU 排障文档重载 `nvidia_uvm`（`sudo rmmod nvidia_uvm` 后 `sudo modprobe nvidia_uvm`）。本篇后续所有 GPU 相关数字均为官方文档与估算公式推导，不是本机实测值。

本机还有第二个限制：安装的 ollama 二进制**缺少 `llama-server` 运行时**，任何真正的推理请求都会以 500 失败，所以本篇的生成速度、`ollama ps` 的 PROCESSOR 行为同样**未在本机验证**。真实报错如下（用 ollama-python 0.6.3 调 `/api/embed` 触发）：

```text
ollama._types.ResponseError: error starting llama-server: llama-server binary not found
(checked: /usr/local/lib/ollama/llama-server, /usr/local/bin/build/lib/ollama/llama-server,
 /usr/local/bin/dist/linux-amd64/lib/ollama/llama-server, /usr/local/bin/dist/linux_amd64/lib/ollama/llama-server)
Run 'cmake -S llama/server --preset cpu && cmake --build --preset cpu' first  (status code: 500)
```

也就是说 `ollama list`、`/api/tags`、`/api/version` 都能正常返回（这些不经过推理运行时），但 `generate` / `chat` / `embed` 全部失败。判断「Ollama 到底装好没有」时只看 `/api/version` 是不够的，必须跑一次真实推理才算数。

```text
硬件与卸载要点：
1. NVIDIA 需要 compute capability 5.0+ 与驱动 550+，老卡（5.0~6.2）需要驱动 570+
2. 驱动不匹配时 Ollama 不会报错，而是静默回退 CPU，用 ollama ps 的 PROCESSOR 列确认
3. num_gpu 手工设定卸载层数，0 等于纯 CPU；不设时由 Ollama 自动评估
4. 模型能装进单卡就优先装单卡，跨卡切分要走 PCIe，吞吐会下降
5. ollama ps 是判断「跑得慢是不是因为卸载不足」的第一手证据
```

## 显存与内存占用估算

一次推理占的内存分三块：**权重**（模型本身）、**KV cache**（上下文缓存，随上下文长度增长）、**计算缓冲**（llama.cpp 的 compute buffer，随批大小与上下文变化）。工程上常用的估算方法是：

权重显存 ≈ 参数量 × 每参数比特数 / 8 × 1.2（预留约 20% 运行时开销）

KV cache ≈ 2 × 层数 × KV 头数 × head_dim × 上下文长度 × 每元素字节数（f16 为 2 字节）

必须强调这是**工程估算**，不是官方承诺值。真实占用受实现（是否开启 Flash Attention、KV cache 量化、批大小）、驱动与框架版本影响，最终以 `ollama ps` 的 `SIZE` 列为准。

| 量化级别 | 每参数约比特 | 7B 权重体积约 | 32B 权重体积约 |
|----------|--------------|---------------|----------------|
| F16 | 16.0 | 13.0 GiB | 60 GiB |
| Q8_0 | 8.5 | 7.0 GiB | 32 GiB |
| Q6_K | 6.6 | 5.5 GiB | 25 GiB |
| Q5_K_M | 5.7 | 4.8 GiB | 22 GiB |
| Q4_K_M | 4.8 | 4.7 GiB | 21.5 GiB |
| Q4_0 | 4.5 | 4.0 GiB | 18 GiB |
| Q3_K_M | 3.4 | 3.3 GiB | 15 GiB |
| Q2_K | 2.6 | 2.7 GiB | 12 GiB |

下面这个脚本把权重与 KV cache 一起估出来，可以按自己的模型架构改参数后直接跑：

```python
"""显存占用估算：权重 + KV cache，单位为 GiB。"""

BITS_PER_WEIGHT = {
    "Q2_K": 2.6, "Q3_K_M": 3.4, "Q4_0": 4.5, "Q4_K_M": 4.8,
    "Q5_K_M": 5.7, "Q6_K": 6.6, "Q8_0": 8.5, "F16": 16.0,
}


def weights_gib(params_b: float, quant: str, overhead: float = 1.2) -> float:
    """权重显存估算，params_b 为十亿参数。"""
    bits = BITS_PER_WEIGHT[quant]
    return params_b * 1e9 * bits / 8 / 1024**3 * overhead


# 各模型架构参数（层数 / KV 头数 / head_dim），取自公开模型卡
ARCH = {
    "qwen2.5:7b": (28, 4, 128),
    "qwen2.5:32b": (64, 8, 128),
    "llama3.1:8b": (32, 8, 128),
    "llama3.1:70b": (80, 8, 128),
}


def kv_cache_gib(model: str, num_ctx: int, elem_bytes: float = 2.0, parallel: int = 1) -> float:
    """KV cache 估算，elem_bytes=2 为 f16，1 为 q8_0，0.5 为 q4_0。"""
    layers, kv_heads, head_dim = ARCH[model]
    return 2 * layers * kv_heads * head_dim * num_ctx * parallel * elem_bytes / 1024**3


if __name__ == "__main__":
    for ctx, elem in ((8192, 2.0), (32768, 2.0), (32768, 1.0)):
        print(f"qwen2.5:7b Q4_K_M num_ctx={ctx} kv_elem={elem}")
        print(f"  权重 {weights_gib(7, 'Q4_K_M'):.2f} GiB  "
              f"KV {kv_cache_gib('qwen2.5:7b', ctx, elem):.2f} GiB")
    print(f"qwen2.5:32b Q4_K_M: 权重 {weights_gib(32, 'Q4_K_M'):.2f} GiB")
    assert weights_gib(7, "F16") > weights_gib(7, "Q4_K_M") > 0
    assert kv_cache_gib("qwen2.5:7b", 32768, 1.0) < kv_cache_gib("qwen2.5:7b", 32768, 2.0)
```

本机真实运行结果（Python 3.14.7）：

```text
qwen2.5:7b Q4_K_M num_ctx=8192
  权重:   4.69 GiB
  KV  :   0.44 GiB
  合计:   5.13 GiB
qwen2.5:7b Q4_K_M num_ctx=32768
  权重:   4.69 GiB
  KV  :   1.75 GiB
  合计:   6.44 GiB
qwen2.5:7b Q4_K_M num_ctx=32768
  权重:   4.69 GiB
  KV  :   0.88 GiB
  合计:   5.57 GiB
qwen2.5:32b Q4_K_M num_ctx=8192
  权重:  21.46 GiB
  KV  :   2.00 GiB
  合计:  23.46 GiB
自检通过：量化等级与 KV 精度、上下文长度的单调关系正确
```

结果里最值得注意的一行：**7B 模型把上下文从 8K 拉到 32K，KV cache 从 0.44 GiB 涨到 1.75 GiB，权重一点没变**。这说明「显存不够」很多时候不是模型太大，而是上下文开太大。反过来，32B Q4_K_M 的权重就要 21.46 GiB，24GB 显存卡上留给 KV cache 与计算缓冲的余量已经不多。

```text
显存估算要点：
1. 占用 = 权重 + KV cache + 计算缓冲，估算完再留 20% 余量给运行时波动
2. 经验公式不是官方承诺值，最终以 ollama ps 的 SIZE 列为准
3. 权重体积只由参数量与量化级别决定，改上下文不会动权重
4. KV cache 随上下文线性增长，是最容易吃爆显存的可调项
5. 显存不足时的取舍顺序：降量化 → 换小模型 → 降 num_ctx → 部分卸载到 CPU
```

## 上下文长度与 KV Cache 影响

Ollama 默认上下文窗口是 **4096 token**，可以用环境变量 `OLLAMA_CONTEXT_LENGTH` 全局改，也可以在 `ollama run` 里用 `/set parameter num_ctx <N>`、在 API 里用 `options.num_ctx` 单次改。上下文调大的代价有两层：一层是显存（KV cache 线性增长，见上一章），另一层是**质量**——超出模型训练时标称的有效上下文后，注意力会失效，表现为答非所问、上下文里的事实被忽略。所以「能塞多少 token」不等于「该塞多少 token」。

Ollama 支持 Flash Attention 与 KV cache 量化来压缩这部分开销。Flash Attention 在现代模型与后端上会被自动启用，也可以强制开：`OLLAMA_FLASH_ATTENTION=1`。KV cache 量化由 `OLLAMA_KV_CACHE_TYPE` 控制，是**全局选项**（所有模型统一生效），可用值与代价如下：

| 取值 | 显存约为 f16 的 | 精度损失 |
|------|-----------------|----------|
| `f16`（默认） | 1 倍 | 无，精度最高 |
| `q8_0` | 约 1/2 | 极小，通常无感知，官方推荐的非默认首选 |
| `q4_0` | 约 1/4 | 小到中等，上下文越长越明显 |

官方特别提示：KV cache 量化的影响与模型架构有关，**GQA 数量高的模型（如 Qwen2）受量化的精度影响可能比低 GQA 的模型更大**，需要按模型与任务实测取舍。另一个常被忽略的乘法关系在并发一章：并行请求会让上下文按并行数倍增。

```shell
# 全局把默认上下文提到 8K，并开启 Flash Attention 与 q8_0 KV cache
OLLAMA_CONTEXT_LENGTH=8192 OLLAMA_FLASH_ATTENTION=1 OLLAMA_KV_CACHE_TYPE=q8_0 ollama serve

# 会话内临时改上下文（只影响当前会话）
ollama run qwen2.5:7b
>>> /set parameter num_ctx 16384

# API 单次覆盖
curl http://localhost:11434/api/generate -d '{
  "model": "qwen2.5:7b",
  "prompt": "把下面这段日志按错误码归类",
  "options": { "num_ctx": 16384 },
  "stream": false
}'
```

```text
上下文与 KV cache 要点：
1. Ollama 默认上下文 4096 token，改它用 OLLAMA_CONTEXT_LENGTH / num_ctx
2. KV cache 显存随上下文线性增长，是显存超支的头号原因
3. OLLAMA_FLASH_ATTENTION=1 与 OLLAMA_KV_CACHE_TYPE=q8_0 是最省显存的组合
4. KV cache 量化是全局选项，所有模型一起生效，无法按模型区分
5. 上下文超过训练有效长度后质量会崩，按模型卡标称值设上限
```

## 量化级别与质量权衡

量化用更少的比特表示每个权重，换来更小的体积、更低的显存要求与更快的推理（内存带宽是本地推理的主要瓶颈），代价是精度损失。Ollama 模型库的默认标签通常已经是「体积与质量平衡」的量化（如 Q4_K_M 或 Q4_0），自建模型时可以在 `ollama create` 请求里用 `quantize` 指定 `nvfp4`、`mxfp8`、`mxfp4`、`int4`、`int8` 等类型（官方 API 文档给出的推荐值是 nvfp4 与 mxfp8，具体可用集合按版本确认）。

经验上的取舍梯度：

| 量化级别 | 体积 | 速度 | 质量 | 适用 |
|----------|------|------|------|------|
| F16 / BF16 | 最大 | 最慢（受带宽限制） | 基准 | 微调基线、精度评测 |
| Q8_0 | 约一半 | 慢 | 与基准几乎无差 | 嵌入、分类、结构化抽取 |
| Q6_K / Q5_K_M | 中 | 中 | 差异很小 | 追求质量且显存够 |
| Q4_K_M | 小 | 快 | 轻微下降 | 通用对话与代码，默认首选 |
| Q4_0 | 最小 | 最快 | 比 Q4_K_M 略差 | 极致压缩 |
| Q3_K_M 及以下 | 极小 | 最快 | 明显下降，长文与推理任务易崩 | 只做演示或极低资源环境 |

「质量下降」必须用你自己的任务评测，不要只看别人的 perplexity 数字：代码补全看单测通过率，抽取看字段准确率，客服看口吻一致性与越界率。做法是固定一组回归用例，对同一模型的 Q8_0 与 Q4_K_M 各跑一遍比对。

```shell
# 1) 看模型实际用的量化级别与参数规模
ollama show qwen2.5:7b

# 2) 为同一基座构建两种量化版本，用同一组回归问题对比
ollama cp qwen2.5:7b qwen25-q4

# 3) 用 API 指定量化类型（示例：int8；可用集合以官方 API 文档为准）
curl http://localhost:11434/api/create -d '{
  "model": "qwen25-int8",
  "from": "qwen2.5:7b",
  "quantize": "int8",
  "stream": false
}'

# 4) 对比耗时与输出一致性（固定 seed 降低噪声）
curl http://localhost:11434/api/chat -d '{
  "model": "qwen25-q4",
  "messages": [{"role": "user", "content": "用一句话解释 KV cache"}],
  "options": {"seed": 42, "temperature": 0},
  "stream": false
}'
```

`ollama show` 会打印 `quantization_level` 与 `parameter_size`，用于确认拿到的是不是你预期的那个量化（下面为输出结构示意，字段名以实际版本为准）：

```text
  Model
    architecture        qwen2
    parameters          7.6B
    context length      32768
    embedding length    3584
    quantization        Q4_K_M
```

```text
量化取舍要点：
1. 量化主要省的是内存带宽，所以本地推理里「更小的量化往往也更快」
2. Q4_K_M 是通用默认；嵌入、分类、结构化抽取这类对精度敏感的任务用 Q8_0
3. Q3 及以下在长文与多步推理上退化明显，不要用在对错敏感的场景
4. 质量必须用自己的回归集评测，跨模型抄 perplexity 数字没有意义
5. 自建量化用 ollama create 的 quantize 字段，可用集合按官方 API 文档与版本确认
```

## 并发与队列管理

Ollama 的并发有两个层级，互相叠加：

- **多模型并发**：显存（或 CPU 推理时的系统内存）够就能同时加载多个模型，由 `OLLAMA_MAX_LOADED_MODELS` 限制，默认是 GPU 数量的 3 倍，纯 CPU 推理时为 3。显存装不下的新模型请求会被排队，等旧模型空闲后卸载腾位置。GPU 推理时，新模型必须能**完整**装进显存才允许并发加载。
- **单模型并行请求**：一个模型能同时处理多少个请求，由 `OLLAMA_NUM_PARALLEL` 控制，默认 1。官方明确说明：并行处理会把该模型的上下文按并行数放大——**2K 上下文 × 4 路并行 = 8K 上下文**，内存需求按 `OLLAMA_NUM_PARALLEL × OLLAMA_CONTEXT_LENGTH` 等比放大。这是「配了并行以后显存突然爆掉」的根本原因。
- **队列**：请求多到处理不过来时进入队列，`OLLAMA_MAX_QUEUE` 控制队列上限，默认 512；队列满了再来的请求直接返回 **503**，表示服务过载。

| 环境变量 | 作用 | 默认值 |
|----------|------|--------|
| `OLLAMA_NUM_PARALLEL` | 每个模型同时处理的并行请求数 | 1 |
| `OLLAMA_MAX_LOADED_MODELS` | 同时加载的模型数量上限 | 3 × GPU 数（CPU 为 3） |
| `OLLAMA_MAX_QUEUE` | 忙时排队请求上限，超出返回 503 | 512 |
| `OLLAMA_CONTEXT_LENGTH` | 默认上下文长度 | 4096 |
| `OLLAMA_KEEP_ALIVE` | 模型在内存中驻留时长 | 5m |

并发调优的现实做法是：先用 `OLLAMA_NUM_PARALLEL` 提到 2~4 提升小请求吞吐，同时把 `num_ctx` 降下来抵消放大效应；显存不够就回调并行数。多用户场景还要开 `OLLAMA_MAX_LOADED_MODELS` 控制换模型的抖动成本，并用 `OLLAMA_KEEP_ALIVE` 让高频模型常驻（`-1` 表示永不卸载，注意会一直占显存）。

```shell
# 单实例服务 4 个并发用户，上下文 4K，最多同时驻留 2 个模型，模型常驻不卸载
OLLAMA_NUM_PARALLEL=4 \
OLLAMA_CONTEXT_LENGTH=4096 \
OLLAMA_MAX_LOADED_MODELS=2 \
OLLAMA_KEEP_ALIVE=-1 \
ollama serve

# 预热：发一个空请求把模型先加载好，避开首个请求的冷启动
curl http://localhost:11434/api/generate -d '{"model": "qwen2.5:7b", "keep_alive": -1}'

# 观察并发下真实驻留情况（SIZE 会随并行数放大）
ollama ps

# 立刻卸载释放显存
curl http://localhost:11434/api/generate -d '{"model": "qwen2.5:7b", "keep_alive": 0}'
```

并发压测脚本（需服务与模型就绪后运行；本机 ollama 缺少 llama-server 运行时、所有推理请求返回 500，故未做实测）：

```python
"""并发压测：固定并发数发 N 个请求，统计吞吐、延迟分位与 503 比例。"""
import concurrent.futures as cf
import json
import statistics
import time
import urllib.error
import urllib.request

BASE = "http://localhost:11434"
MODEL = "qwen2.5:7b"
CONCURRENCY = 4
TOTAL = 40
NUM_CTX = 4096


def one(i: int) -> tuple:
    body = {
        "model": MODEL,
        "prompt": f"第 {i} 个并发请求：用一句话说明什么是 KV cache。",
        "stream": False,
        "options": {"num_ctx": NUM_CTX, "num_predict": 64, "temperature": 0.2},
    }
    req = urllib.request.Request(
        f"{BASE}/api/generate",
        data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json"},
    )
    t0 = time.perf_counter()
    try:
        with urllib.request.urlopen(req, timeout=300) as resp:
            data = json.loads(resp.read().decode())
        return time.perf_counter() - t0, data, None
    except urllib.error.HTTPError as e:
        return time.perf_counter() - t0, None, e.code


if __name__ == "__main__":
    lat, codes, tokens = [], [], 0
    with cf.ThreadPoolExecutor(max_workers=CONCURRENCY) as pool:
        for dt, data, err in pool.map(one, range(TOTAL)):
            lat.append(dt)
            if err:
                codes.append(err)
            else:
                tokens += data["eval_count"]
    lat.sort()
    print(f"请求数 {TOTAL}  并发 {CONCURRENCY}")
    print(f"成功率 {(TOTAL - len(codes)) / TOTAL:.0%}  503 数 {codes.count(503)}")
    print(f"延迟 p50 {statistics.median(lat):.2f}s  p95 {lat[int(len(lat) * 0.95)]:.2f}s")
    print(f"生成 {tokens} token，单请求平均 {tokens / sum(lat):.1f} token/s")
```

```text
并发与队列要点：
1. 两个层级要分开看：多模型并发（MAX_LOADED_MODELS）与单模型并行（NUM_PARALLEL）
2. 并行会按倍数放大上下文与显存，提并行时同步降 num_ctx
3. 队列满返回 503 是过载信号，客户端必须实现重试与退避，不要盲目加重试风暴
4. 多卡时模型能装进单卡更快，跨卡切分要走 PCIe
5. 预热（空请求）与 keep_alive 常驻能把首字延迟从数十秒降到毫秒级
```

## 性能观测与基准测试

Ollama 的每个 API 响应都带计时字段，这是最省事的性能观测手段，不用装任何额外组件：

| 字段 | 含义 |
|------|------|
| `total_duration` | 总耗时（纳秒），含加载与排队 |
| `load_duration` | 模型加载进内存/显存的耗时 |
| `prompt_eval_count` | 输入（提示）的 token 数 |
| `prompt_eval_duration` | 处理输入耗时（prefill） |
| `eval_count` | 生成的 token 数 |
| `eval_duration` | 生成耗时（decode） |

由此可以算出两个关键指标：**prefill 速度** = `prompt_eval_count / (prompt_eval_duration / 1e9)`，反映长提示处理能力；**生成速度（token/s）** = `eval_count / (eval_duration / 1e9)`，是用户感知最直接的数字。注意 `total_duration` 里包含了首次加载时间，做基准时要么先预热，要么直接看 `eval_duration`。

```shell
# 单次请求的原始计时数据（先预热过一次，避免把加载时间算进去）
curl http://localhost:11434/api/generate -d '{
  "model": "qwen2.5:7b",
  "prompt": "写一个 50 行的 Python 快排",
  "stream": false,
  "options": {"num_predict": 512}
}'

# 需要在服务端日志里看更细的调度与卸载决策时开调试日志
OLLAMA_DEBUG=1 ollama serve

# Linux 上用 systemd 部署时的日志
journalctl -u ollama --no-pager --follow --pager-end

# GPU 侧观测（本机驱动不匹配，未验证）
nvidia-smi dmon -s um
```

```python
"""把 API 计时字段换算成 prefill 与 decode 速度。"""
import json
import urllib.request

body = {
    "model": "qwen2.5:7b",
    "prompt": "用三句话解释为什么量化能加速本地推理。",
    "stream": False,
    "options": {"num_predict": 256},
}
req = urllib.request.Request(
    "http://localhost:11434/api/generate",
    data=json.dumps(body).encode(),
    headers={"Content-Type": "application/json"},
)

with urllib.request.urlopen(req, timeout=300) as resp:
    d = json.loads(resp.read().decode())

prefill = d["prompt_eval_count"] / (d["prompt_eval_duration"] / 1e9)
decode = d["eval_count"] / (d["eval_duration"] / 1e9)
print(f"输入 {d['prompt_eval_count']} token，prefill {prefill:.1f} token/s")
print(f"输出 {d['eval_count']} token，decode {decode:.1f} token/s")
print(f"加载 {d['load_duration'] / 1e9:.2f}s，总耗时 {d['total_duration'] / 1e9:.2f}s")
```

基准测试的正确姿势是把变量钉死：同一 prompt、同一 `num_predict`、同一 `num_ctx`、`temperature` 0 加固定 `seed`、先预热一次、每个配置跑 3 次取中位数。对比的维度就是上面那几张表里的旋钮：量化级别、卸载层数、上下文长度、KV cache 类型、并行数。

本机的客户端与服务端连通性实测（服务进程起来后，返回的是真实响应）：

```text
$ curl -s http://localhost:11434/api/version
{"version":"0.40.4"}

$ curl -s http://localhost:11434/api/tags
{"models":[]}

$ curl -s http://localhost:11434/
Ollama is running
```

```text
性能观测要点：
1. 用 eval_count / eval_duration 算生成速度，用 prompt_eval_* 算 prefill 速度
2. total_duration 含加载与排队时间，做基准前务必先预热
3. OLLAMA_DEBUG=1 能看到卸载与调度的详细决策，是排障首选
4. 变量必须钉死（prompt/num_predict/num_ctx/seed），否则跑出来的数字不可比
```

## 应用场景实战

### 场景一：在 24GB 显存单卡上决定「跑哪个模型、上下文开多大」

需求：一台 24GB 显存（如 RTX 4090 / A5000 级别）的推理机，要服务内部知识问答，需要尽量长的上下文，同时留出显存余量给并发。做法是先用估算脚本把候选方案算一遍，再挑一个「权重 + KV cache + 余量 < 24GB」的组合落地。

```shell
# 第一步：估算。直接复用本章的 vram_est.py，把候选算清楚
python3 vram_est.py
```

本机真实输出（同一脚本，7B 与 32B 对比）：

```text
qwen2.5:7b Q4_K_M num_ctx=8192
  权重:   4.69 GiB
  KV  :   0.44 GiB
  合计:   5.13 GiB
qwen2.5:7b Q4_K_M num_ctx=32768
  权重:   4.69 GiB
  KV  :   1.75 GiB
  合计:   6.44 GiB
qwen2.5:7b Q4_K_M num_ctx=32768
  权重:   4.69 GiB
  KV  :   0.88 GiB
  合计:   5.57 GiB
qwen2.5:32b Q4_K_M num_ctx=8192
  权重:  21.46 GiB
  KV  :   2.00 GiB
  合计:  23.46 GiB
```

结论很直接：32B Q4_K_M 合计 23.46 GiB，已经贴着 24GB 上限，没有余量做并发与波动，属于「能跑但不敢用」；7B Q4_K_M 在 32K 上下文下（KV cache 用 q8_0）只要 5.57 GiB，可以把剩下的显存全部用来提并发。于是落地配置选 7B：

```text

PARAMETER num_gpu 999          # 尽可能多卸载层到 GPU（999 视为全部）
PARAMETER temperature 0.3
PARAMETER num_predict 1024
```

```shell

OLLAMA_KV_CACHE_TYPE=q8_0 \
OLLAMA_NUM_PARALLEL=4 \
OLLAMA_MAX_LOADED_MODELS=1 \
OLLAMA_KEEP_ALIVE=30m \

# 构建并验证
ollama create qa-7b -f ./Modelfile.for24g
ollama run qa-7b "用三句话介绍本知识库的定位"

# 第三步：验证真实占用与卸载比例，跟估算对账
ollama ps
```

```text
部署前检查清单：
1. 先算再装：权重 + KV cache + 20% 余量必须小于显存总量，别等 OOM 才回头
2. 上下文要长就开 OLLAMA_KV_CACHE_TYPE=q8_0，省一半 KV cache 且几乎无损
3. 并行数会按倍数放大上下文，提并行必须同步确认显存余量
4. 用 ollama ps 的 PROCESSOR 列确认没有悄悄回退到 CPU，SIZE 列与估算对账

```

### 场景二：夜间批处理任务的速度调优与容量核算

场景：每天凌晨把 20000 条工单跑一遍分类打标，需要在 4 小时内跑完。单请求延迟不是关键，**总吞吐**才是。做法是跑基准拿到该模型在这台机器上的单请求墙钟，再反推需要的并行度。

```python
"""批处理吞吐核算：先测单请求墙钟，再推算总时长与所需并行度。"""
import json
import time
import urllib.request

BASE = "http://localhost:11434"
MODEL = "qwen2.5:7b"
TOTAL_TICKETS = 20_000
AVG_OUTPUT_TOKENS = 40


def timed_call(prompt: str) -> dict:
    body = {
        "model": MODEL,
        "prompt": prompt,
        "stream": False,
        "options": {"num_ctx": 2048, "num_predict": AVG_OUTPUT_TOKENS, "temperature": 0},
    }
    req = urllib.request.Request(
        f"{BASE}/api/generate",
        data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json"},
    )
    t0 = time.perf_counter()
    with urllib.request.urlopen(req, timeout=300) as resp:
        d = json.loads(resp.read().decode())
    d["wall"] = time.perf_counter() - t0
    return d


# 预热，避免把首次加载时间算进基准
timed_call("热身：回复 OK")

samples = [timed_call("把这条工单归类：快递三天没动，只输出类别名。") for _ in range(3)]
decode = sum(s["eval_count"] / (s["eval_duration"] / 1e9) for s in samples) / len(samples)
wall = sum(s["wall"] for s in samples) / len(samples)

hours_1x = TOTAL_TICKETS * wall / 3600
print(f"decode {decode:.1f} token/s，单请求墙钟 {wall:.2f}s")
print(f"单路串行跑完 {TOTAL_TICKETS} 条需要 {hours_1x:.1f} 小时")
for parallel in (2, 4, 8):
    print(f"  OLLAMA_NUM_PARALLEL={parallel} 理论 {hours_1x / parallel:.1f} 小时，"
          f"上下文按 2048 × {parallel} 放大")
```

跑出结果后按「理论时长 × 1.3 安全系数」设并行度，并把 `num_ctx` 压到刚好够放提示的长度（批处理任务通常不需要长上下文，这比加并行更划算）。同时开大 `OLLAMA_MAX_QUEUE` 让突发排队而不是直接 503，客户端按指数退避重试。

```shell
# 批处理专用实例：短上下文 + 高并行 + 长驻留，队列放宽
OLLAMA_CONTEXT_LENGTH=2048 \
OLLAMA_NUM_PARALLEL=4 \
OLLAMA_MAX_QUEUE=2048 \
OLLAMA_KEEP_ALIVE=-1 \
OLLAMA_MAX_LOADED_MODELS=1 \
ollama serve

# 任务跑完立刻释放显存给白天的在线服务
curl http://localhost:11434/api/generate -d '{"model": "qwen2.5:7b", "keep_alive": 0}'
```

```text
吞吐调优要点：
1. 批处理优化目标是吞吐不是延迟，先测单请求墙钟再按并行度线性外推
2. 理论值乘 1.3 安全系数，实际吞吐受排队与内存带宽竞争影响达不到线性
3. 短上下文比高并行更省显存，能用 2K 就别开 32K
4. 队列放宽到 2048 以上，让突发排队而不是返回 503
5. 夜间任务结束后用 keep_alive=0 或 ollama stop 卸载，把显存还给白天服务
```

## 最佳实践与踩坑记录

### 最佳实践

1. 上模型前先用估算脚本算清「权重 + KV cache + 20% 余量」，把 OOM 挡在部署之前，而不是靠试。
2. 长上下文场景一律开 `OLLAMA_FLASH_ATTENTION=1` 与 `OLLAMA_KV_CACHE_TYPE=q8_0`，这是省一半 KV cache 且几乎无质量损失的高性价比组合。
3. 提 `OLLAMA_NUM_PARALLEL` 时同步把 `num_ctx` 降下来，因为并行数会按倍数放大上下文与显存。
4. 部署完成后立刻用 `ollama ps` 看 `PROCESSOR` 列，确认没有静默回退到 CPU；这一步能挡掉最常见的「跑得慢」投诉。
5. 基准测试固定 prompt、`num_predict`、`num_ctx`、`seed` 与 `temperature`，先预热，跑 3 次取中位数，否则数字不可比。
6. 生产实例把最终生效的调优参数写进 systemd unit 的 `Environment=`，别让手工 `ollama serve` 和托管启动两套参数并存。
7. 高频模型用 `OLLAMA_KEEP_ALIVE` 常驻并做预热请求，把冷启动的数十秒从用户体验里彻底删掉。

### 踩坑记录

```text
坑 1：模型明明有独显，速度却像纯 CPU
结论：生成速度只有每秒几个 token，ollama ps 显示 100% CPU。
原因：NVIDIA 内核驱动与用户态库版本不匹配（NVML 初始化失败），或卸载层数为 0，Ollama 静默回退 CPU。
解法：先跑 nvidia-smi 确认驱动可用（本机即为此类故障：Failed to initialize NVML: Driver/library version mismatch）；再查 num_gpu 与 ollama ps 的 PROCESSOR 列；必要时重载 nvidia_uvm 或重装匹配驱动。

坑 2：把 num_ctx 调到 128K 后直接 OOM 或速度暴跌
结论：模型加载失败或开始把层换出到内存，速度掉一个数量级。
原因：KV cache 随上下文线性增长（7B 从 8K 的 0.44 GiB 涨到 32K 的 1.75 GiB），且超出模型训练有效长度后质量也会崩。
解法：按显存余量设 num_ctx（用本篇估算脚本先算），开启 Flash Attention 与 OLLAMA_KV_CACHE_TYPE=q8_0，并参考模型卡标称上下文。

坑 3：配了 OLLAMA_NUM_PARALLEL=4 之后显存突然不够
结论：原本能跑的模型在开并发后加载失败或频繁换出。
原因：官方明确说明并行处理会把上下文按并行数放大（2K × 4 = 8K），内存需求按 NUM_PARALLEL × CONTEXT_LENGTH 等比放大。
解法：提并行时同步降 OLLAMA_CONTEXT_LENGTH 或 num_ctx，并留出并行带来的额外缓冲；或改用更小量化、更小模型。

坑 4：压测时大量 503，以为是服务崩了
结论：客户端拿到 503，日志显示请求无处排队。
原因：请求数超过 OLLAMA_MAX_QUEUE（默认 512）队列上限，Ollama 用 503 表示过载而非故障。
解法：服务端按内存余量放宽 OLLAMA_MAX_QUEUE；客户端实现指数退避重试与限流，避免重试风暴把队列继续灌满。

坑 5：拿网上的 perplexity 数字直接判断量化好坏
结论：换成 Q4 后业务准确率明显下降，但网上数据说「几乎无损」。
原因：量化损失与模型架构（GQA 数量）、上下文长度、任务类型强相关，公开 perplexity 与你的业务指标不是一回事。
解法：自建固定回归集，对同一模型的 Q8_0 与 Q4_K_M 各跑一遍对比业务指标，再决定量化级别。

坑 6：夜间无流量时段的首个请求要等几十秒
结论：第一个请求延迟极高，之后恢复正常。
原因：模型未驻留，该请求触发了完整的权重加载，load_duration 占满了 total_duration。
解法：上线后用空请求预热（curl -d '{"model":"..."}'），并把 OLLAMA_KEEP_ALIVE 设长或 -1 让它常驻。

坑 7：Ollama 装好了、/api/version 正常，但所有推理请求 500
结论：服务存活、模型也列得出来，一 generate/chat/embed 就报 500，看着像模型或参数问题。
原因：安装的 ollama 二进制缺少 llama-server 运行时（从源码或裁剪过的发行包安装时常见），推理后端起不来。本机实测到的正是这个报错。
解法：报错里会明确列出搜索路径与缺失的 llama-server；用官方安装脚本重装（curl -fsSL https://ollama.com/install.sh | sh），或按提示构建 runtime 后再启动。验收标准是跑一次真实推理返回内容，而不是只看 /api/version。
```
