## 概述

Modelfile 是 Ollama 用来「定义并创建一个自定义模型」的蓝图文件，作用等价于 Dockerfile 之于容器镜像：它声明从哪个基座模型出发（`FROM`）、运行时用哪些采样与上下文参数（`PARAMETER`）、套用哪个对话模板（`TEMPLATE`）、注入什么系统提示（`SYSTEM`），也可以挂载 LoRA 适配器（`ADAPTER`）。写好一个 Modelfile 后执行 `ollama create <名字> -f ./Modelfile`，Ollama 会基于它生成一个本地可运行的模型，再用 `ollama run <名字>` 或 REST API 调用。反过来说，任何已存在的模型都可以用 `ollama show --modelfile <模型>` 导出它的 Modelfile，这是学习模板与参数写法最可靠的方式。

```text
全篇主线：
1. 语法 —— 纯文本「指令 参数」结构，指令不区分大小写、顺序无关
2. 参数 —— PARAMETER 控制采样、上下文、随机种子与停止符
3. 模板 —— TEMPLATE 用 Go 模板语法拼提示词，SYSTEM 注入角色设定
4. 落地 —— ollama create 构建、ollama show --modelfile 反向导出迭代
5. 导入 —— FROM 支持已有模型、Safetensors 目录、本地 GGUF 与拆分 GGUF
```

## Modelfile 语法与指令

Modelfile 是一种极简的声明式文本格式，每行是「指令 + 参数」的结构，以 `#` 开头的是注释。官方明确说明 Modelfile **不区分大小写**，指令顺序也无关紧要（示例里习惯把 `FROM` 放最前面只是为了可读）。`FROM` 是唯一必需指令，其余都是可选的覆盖项：没有显式给出的模板与参数会继承基座模型的默认值。

| 指令 | 作用 | 是否必需 | 备注 |
|------|------|----------|------|
| `FROM` | 指定基座模型，可以是模型名、本地 Safetensors 目录或 GGUF 文件 | 必需 | 决定架构与权重，其余指令都是对它做覆盖 |
| `PARAMETER` | 设置运行时参数（采样、上下文、停止符等） | 可选 | 可写多条，`ollama run` 里也能临时覆盖 |
| `TEMPLATE` | 完整的提示词模板，决定对话如何被拼接成模型输入 | 可选 | 使用 Go `text/template` 语法 |
| `SYSTEM` | 注入系统消息（角色设定）到模板的 `{{ .System }}` 位置 | 可选 | 与 `MESSAGE system` 等效 |
| `ADAPTER` | 挂载 (Q)LoRA 适配器权重 | 可选 | 用于在基座模型上叠加微调结果 |
| `LICENSE` | 声明模型使用的法律许可证文本 | 可选 | 分发模型时建议填写 |
| `MESSAGE` | 预置示例对话历史，引导模型的回答风格 | 可选 | 角色支持 system / user / assistant |
| `REQUIRES` | 声明该模型要求的最低 Ollama 版本 | 可选 | 官方文档新增指令，值为合法版本号 |
| `CAPABILITY` | 追加声明模型能力（如 decision） | 可选 | 仅对专门训练的权重使用 |

一个能直接跑起来的最小 Modelfile 如下，它把基座模型包装成一个带角色设定的助手：

```text
# 我的第一个 Modelfile
FROM llama3.2

# 采样温度，越高越有创造性
PARAMETER temperature 0.7

# 上下文窗口大小，单位 token
PARAMETER num_ctx 8192

# 系统提示：角色设定
SYSTEM """你是一名严谨的 Linux 运维助手，回答时先给结论，再给可复制的命令。"""
```

```text
Modelfile 语法要点：
1. 格式固定为「指令 参数」逐行书写，# 开头是注释，空行会被忽略
2. 指令不区分大小写、顺序无关，只有 FROM 是必需的
3. 未显式声明的参数与模板自动继承基座模型
4. 字符串参数推荐用 """...""" 三引号包裹，避免引号与换行被误解
5. 官方提醒 Modelfile 语法仍处于演进中，跨版本行为以官方文档为准
```

## PARAMETER 参数详解

`PARAMETER` 用于覆盖模型运行时的采样与上下文行为。同一参数可以写多条（典型用法是写多个 `stop` 停止序列）。需要特别注意：Modelfile 里写的同名参数会被 `ollama run` 会话中的 `/set parameter` 或 REST API 请求体 `options` 里的值覆盖，所以 Modelfile 提供的是「默认值」而不是「强制值」。下表整理自官方 Modelfile 参考（默认值以官方文档为准）。

| 参数 | 说明 | 类型 | 示例 |
|------|------|------|------|
| `num_ctx` | 生成下一个 token 时使用的上下文窗口大小 | int | `num_ctx 8192` |
| `repeat_last_n` | 向前回看多少 token 来抑制重复，0 关闭，-1 表示等于 `num_ctx` | int | `repeat_last_n 64` |
| `repeat_penalty` | 重复惩罚强度，越大惩罚越强，1.0 表示不惩罚 | float | `repeat_penalty 1.1` |
| `temperature` | 采样温度，越高越有创造性 | float | `temperature 0.7` |
| `seed` | 随机数种子，固定后相同输入可复现相同输出 | int | `seed 42` |
| `stop` | 停止序列，命中即结束生成，可写多条 | string | `stop "<|eot_id|>"` |
| `num_predict` | 单次生成的最大 token 数，-1 表示不限制 | int | `num_predict 512` |
| `draft_num_predict` | 有草稿模型时的每步投机解码 token 数，0 关闭投机 | int | `draft_num_predict 4` |
| `top_k` | 只从概率最高的 K 个 token 中采样，越小越保守 | int | `top_k 40` |
| `top_p` | 核采样，累计概率阈值，越小越聚焦 | float | `top_p 0.9` |
| `min_p` | 相对最高概率的最小概率阈值，兼顾质量与多样性 | float | `min_p 0.05` |

下面是一份「面向代码生成、追求确定性输出」的参数配置，把温度压低、固定种子、限制最大长度以控制单次调用成本：

```text
FROM qwen2.5-coder:7b

PARAMETER temperature 0.2      # 代码任务降低随机性
PARAMETER top_p 0.9            # 核采样，保留主流候选
PARAMETER top_k 20             # 进一步收紧候选集
PARAMETER repeat_penalty 1.05  # 轻微抑制重复
PARAMETER num_ctx 16384        # 给代码上下文留足空间
PARAMETER num_predict 2048     # 单次最多生成 2048 token
PARAMETER seed 42              # 固定种子便于回归测试
PARAMETER stop "<|im_end|>"    # Qwen 系模板的结束符
```

```text
PARAMETER 要点：
1. 它是「默认值」而非「强制值」，命令行 /set 与 API options 会覆盖它
2. num_ctx 直接决定显存/内存占用，调大前先确认硬件余量（见 08.6）
3. 需要复现结果时同时固定 seed 与 temperature，否则回归测试会误判
4. 模板自带结束符的模型（如 Llama 3、Qwen）务必补上对应 stop
5. 官方 Modelfile 参考表与 FAQ 对 num_ctx 默认值的描述存在版本差异，以实际版本为准
```

## TEMPLATE 与 SYSTEM 及模板变量

`TEMPLATE` 是被发送给模型的完整提示词模板，决定了 system、user、assistant 三类消息如何被拼接，以及角色标记用哪种特殊 token。它使用 Go 的 `text/template` 语法，官方提供了三个模板变量。**模板是与模型强绑定的**——Llama 3 用 `<|start_header_id|>` / `<|eot_id|>`，Qwen 用 `<|im_start|>` / `<|im_end|>`，Gemma 又不同，写错模板会让模型「答非所问」甚至不断复读。

| 模板变量 | 含义 |
|----------|------|
| `{{ .System }}` | 系统消息，用来指定自定义行为；由 `SYSTEM` 指令或 API 的 system 角色提供 |
| `{{ .Prompt }}` | 用户这一轮输入的消息 |
| `{{ .Response }}` | 模型生成的回复；生成阶段中，该变量之后的文本会被省略 |

下面是一个仿 Qwen ChatML 风格的模板，展示了如何用 `{{ if }}` 条件判断避免空段落：

```text
FROM qwen2.5:7b

TEMPLATE """{{ if .System }}<|im_start|>system
{{ .System }}<|im_end|>
{{ end }}{{ if .Prompt }}<|im_start|>user
{{ .Prompt }}<|im_end|>
{{ end }}<|im_start|>assistant
"""

SYSTEM """你是一个中文技术文档助手，只输出 Markdown，不要寒暄。"""
PARAMETER stop "<|im_end|>"
```

最稳妥的做法不是手写模板，而是先导出基座模型的真实模板再改：`ollama show --modelfile qwen2.5:7b` 会打印出官方使用的模板与 stop 序列（下面结构源于官方文档示例，实际 FROM 会指向本地 blob 的 sha256 文件名）：

```text
# Modelfile generated by "ollama show"
FROM /usr/share/ollama/.ollama/models/blobs/sha256-00e1317cbf74d901080d7100f57580ba8dd8de57203072dc6f668324ba545f29
TEMPLATE """{{ if .System }}<|start_header_id|>system<|end_header_id|>

{{ .System }}<|eot_id|>{{ end }}{{ if .Prompt }}<|start_header_id|>user<|end_header_id|>

{{ .Prompt }}<|eot_id|>{{ end }}<|start_header_id|>assistant<|end_header_id|>

{{ .Response }}<|eot_id|>"""
PARAMETER stop "<|start_header_id|>"
PARAMETER stop "<|end_header_id|>"
PARAMETER stop "<|eot_id|>"
PARAMETER stop "<|reserved_special_token"
```

```text
TEMPLATE 与 SYSTEM 要点：
1. 模板与模型的特殊 token 强绑定，跨模型抄模板必然出问题
2. 优先 ollama show --modelfile 导出真实模板，在其上做最小修改
3. SYSTEM 只是往 {{ .System }} 位置塞内容，改了模板要注意还有没有该变量
4. 模板里出现特殊 token 时，必须同步把它们写进 stop，否则模型不会停
5. MESSAGE 指令可预置 few-shot 对话历史，比在 SYSTEM 里写示例更贴近训练格式
```

## 创建与迭代自定义模型

从 Modelfile 到可用模型只要一条 `ollama create`。构建完成后模型进入本地模型库，可以像官方模型一样用 `run` / `pull` 管理；`ollama cp` 可以复制出新名字，`ollama rm` 删除。迭代的正确姿势是「导出官方模板 → 改 Modelfile → create 成新名字 → 对比测试」，而不是覆盖原模型。

```shell
# 1) 准备 Modelfile（假设已写好 ./Modelfile）
# 2) 构建自定义模型，名字可带命名空间
ollama create my-coder -f ./Modelfile
# 若不带 -f，默认读取当前目录的 Modelfile
ollama create my-coder

# 3) 运行验证
ollama run my-coder "用 Python 写一个快速排序，带类型标注"

# 4) 查看构建结果：模板、参数、量化级别
ollama show my-coder

# 5) 导出当前 Modelfile，作为下一轮迭代的基线
ollama show --modelfile my-coder > Modelfile.next

# 6) 复制成不同名字做 A/B 对比
ollama cp my-coder my-coder-temp05

# 7) 清理不再需要的模型，释放磁盘
ollama rm my-coder-temp05
```

用 API 做同样的构建，请求体是一个 JSON，`from` 对应 `FROM`，`system` 对应 `SYSTEM`，`parameters` 对应 `PARAMETER`，`template` 对应 `TEMPLATE`：

```shell
curl http://localhost:11434/api/create -d '{
  "model": "my-coder-api",
  "from": "qwen2.5-coder:7b",
  "system": "你是一个只输出代码的助手。",
  "parameters": {
    "temperature": 0.2,
    "num_ctx": 16384,
    "stop": ["<|im_end|>"]
  },
  "stream": false
}'
```

```text
创建与迭代要点：
1. ollama create 的名字即模型标识，可用「命名空间/名字」组织团队私有模型
2. 迭代时用 ollama show --modelfile 导出基线，改一份、建一份新名字，保留可回滚版本
3. 用固定的回归提问集合对比新旧模型（代码任务看正确性，客服任务看口吻一致性）
4. 构建只登记元数据与模板，不复制权重，磁盘占用主要来自共享的 blob
5. 删除模型前先 ollama ps 确认没有正在加载的实例，避免影响在线服务
```

## 导入 GGUF 与微调模型

`FROM` 不限于模型名，官方支持三类来源：已有模型（`FROM llama3.2`）、Safetensors 权重目录（`FROM <model directory>`，目录内需是受支持架构的 Safetensors 权重）、本地 GGUF 文件（`FROM ./ollama-model.gguf`，路径可为绝对路径或相对 Modelfile 所在目录）。对于被拆分成多个分片的 GGUF，官方要求保留原始分片文件名，用通配符匹配所有分片，或对每个分片写一条独立的 `FROM`。微调场景则用 `ADAPTER` 指令挂载 (Q)LoRA 适配器，让基座模型叠加你的微调能力。

```text
# 从社区下载的 GGUF 导入（最常见场景）
FROM ./qwen2.5-7b-instruct-q4_k_m.gguf

# 拆分 GGUF：用通配符匹配全部分片
FROM ./model-*.gguf

# 或者逐个分片列出
# FROM ./model-00001-of-00004.gguf
# FROM ./model-00002-of-00004.gguf

SYSTEM """你是一个中文问答助手。"""
PARAMETER temperature 0.6
PARAMETER stop "<|im_end|>"
```

```text
# 在基座模型上挂载 LoRA 适配器
FROM llama3.2:3b

# ADAPTER 指向微调产出的适配器权重目录
ADAPTER ./my-lora-adapter

PARAMETER temperature 0.4
```

导入后必须**手工核对模板**：GGUF 往往自带 `tokenizer.chat_template`，但导入时不一定被 Ollama 采用，容易表现为「回显问题」或「不说话」。做法是 `ollama show --modelfile <新模型>` 检查模板，必要时删掉自动生成的 `TEMPLATE` 行，改从原训练框架（如 LlamaFactory、Unsloth）导出的 chat template 写入。

```shell
# 导入并立即检查模板与停止符是否正确
ollama create my-gguf -f ./Modelfile
ollama show --modelfile my-gguf | grep -A3 TEMPLATE

# 跑一个回归问题，确认不是复读或截断
ollama run my-gguf "你好，请用一句话介绍你自己"
```

```text
导入 GGUF 与微调模型要点：
1. FROM 支持 模型名 / Safetensors 目录 / GGUF 文件 三种来源
2. 拆分 GGUF 用 FROM ./model-*.gguf，分片文件名必须保持原样
3. ADAPTER 挂载 (Q)LoRA 适配器，基座与适配器必须同架构、同 tokenizer
4. 导入后第一时间核对 TEMPLATE 与 stop，回显与复读几乎都出在这里
5. 量化级别（Q4_K_M 等）直接决定体积与质量，选型见 08.6 一章
```

## 应用场景实战

### 场景一：把开源基座包装成企业客服助手并做版本化管理

某电商团队要一个「只回答本店业务、不闲聊、不编造物流时效」的客服模型。做法是用官方基座 + 定制 SYSTEM + 收紧采样参数构建，并把 Modelfile 纳入 Git 管理，每次改动都构建一个新版本号（`cs-bot:v1`、`cs-bot:v2`）以便灰度与回滚。

```text
# Modelfile.csbot —— 纳入 Git，随业务规则迭代
FROM qwen2.5:7b-instruct

PARAMETER temperature 0.3      # 客服场景要稳，不要发散
PARAMETER top_p 0.8
PARAMETER repeat_penalty 1.1   # 抑制模板化的重复话术
PARAMETER num_ctx 8192
PARAMETER stop "<|im_end|>"

SYSTEM """你是「云栖商城」的在线客服助手。规则：
1. 只回答与本店商品、订单、退换货、发票相关的问题，其余问题礼貌拒答并引导转人工。
2. 不承诺任何具体到达时间，物流时效一律引导用户在订单页查看。
3. 回答控制在 120 字以内，先给结论，再给操作步骤。
4. 涉及金额、赔付、投诉时，回复「已为您转接人工客服」。"""
```

```shell
# 构建带版本号的自定义模型
ollama create cs-bot:v1 -f ./Modelfile.csbot

# 冒烟测试：正常问题 + 越界问题 + 敏感问题
ollama run cs-bot:v1 "我买的耳机还没发货，怎么办？"
ollama run cs-bot:v1 "帮我写一首关于秋天的诗"
ollama run cs-bot:v1 "你们能不能赔我 100 块？"

# 通过 API 接入业务系统（OpenAI 兼容或原生接口均可）
curl http://localhost:11434/api/chat -d '{
  "model": "cs-bot:v1",
  "messages": [{"role": "user", "content": "发票怎么开？"}],
  "stream": false
}'
```

```text
上线检查清单：
1. SYSTEM 里把「能答什么、不能答什么、转人工条件」写成编号规则，别用自然段
2. 温度和 top_p 压低，保证同样问题得到稳定答案，便于审计
3. 构建 v1/v2 多版本，接入层用配置切流量，出问题秒回滚
4. 用固定的边界问题集回归：越界、诱导承诺、敏感金额三类必测
5. 业务规则变更只改 SYSTEM 与参数、重建模型，不动基座权重
```

### 场景二：导入团队自行微调的 LoRA 模型并在本机验证

算法团队用 LoRA 微调了一个「内部工单分类」模型，产物是适配器权重目录。运维侧要做的是把适配器挂到同架构基座上，导入本机 Ollama 做验证，并写一小段脚本批量跑测试用例比对准确率。

```shell
# 目录结构：基座用 ollama pull 提供，适配器来自训练框架导出
ls ./ticket-lora-adapter
# adapter_config.json  adapter_model.safetensors  ...

cat > Modelfile.ticket <<'EOF'
FROM qwen2.5:7b

# 挂载 LoRA 适配器（路径相对 Modelfile 或写绝对路径）
ADAPTER ./ticket-lora-adapter

PARAMETER temperature 0.0   # 分类任务要确定性
PARAMETER num_ctx 4096
PARAMETER stop "<|im_end|>"

SYSTEM """把输入工单归入以下类别之一，只输出类别名：
账号问题 / 支付问题 / 物流问题 / 商品质量 / 其他。"""
EOF

ollama create ticket-cls:v1 -f ./Modelfile.ticket
```

```python
"""批量验证微调模型：读测试集，逐条调 Ollama API，统计准确率。"""
import json
import urllib.request

CASES = [
    ("登录不上，提示密码错误", "账号问题"),
    ("付款后订单一直没生成", "支付问题"),
    ("快递三天没动", "物流问题"),
    ("收到货屏幕有划痕", "商品质量"),
]

LABELS = ["账号问题", "支付问题", "物流问题", "商品质量", "其他"]


def classify(text: str) -> str:
    body = {
        "model": "ticket-cls:v1",
        "prompt": text,
        "stream": False,
        "options": {"temperature": 0.0},
    }
    req = urllib.request.Request(
        "http://localhost:11434/api/generate",
        data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json"},
    )
    with urllib.request.urlopen(req, timeout=60) as resp:
        raw = json.loads(resp.read().decode())["response"].strip()
    # 只保留命中的标签，防止模型带出解释文字
    for label in LABELS:
        if label in raw:
            return label
    return raw


if __name__ == "__main__":
    hit = 0
    for text, expect in CASES:
        got = classify(text)
        ok = got == expect
        hit += ok
        print(f"[{'OK ' if ok else 'BAD'}] 期望={expect} 实际={got} :: {text}")
    print(f"准确率: {hit}/{len(CASES)} = {hit / len(CASES):.0%}")
```

```text
验证落地要点：
1. 适配器与基座必须同架构、同 tokenizer，否则 create 后输出乱码
2. 分类类任务 temperature 设 0，并用标签白名单清洗模型输出
3. 回归集要覆盖每个类别与易混类别，不能只测 happy path
4. 记录每次验证的准确率，微调版本升级时对比是否真的变好
5. 适配器目录不要提交进仓库，用制品库或对象存储分发
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先 `ollama show --modelfile <基座>` 导出官方模板，再在其上做最小改动，别凭记忆手写特殊 token。
2. Modelfile 纳入 Git 版本管理，模型名带语义化版本（`cs-bot:v1`），改动即新建模型，保留回滚能力。
3. SYSTEM 里的行为约束写成编号规则（能答/不能答/触发转人工的条件），比自然段描述更容易被模型遵守。
4. 每个 Modelfile 都配一组固定回归问题（正常、越界、敏感），构建后立刻跑，把「模板坏了」挡在上线前。
5. 字符串参数一律用 `"""..."""` 包裹，避免中文引号、换行与特殊 token 被 shell 或模板解析吃掉。
6. 样本量少时优先用 SYSTEM + MESSAGE 做 few-shot，而不是急着微调；微调前先确认提示工程已到瓶颈。
7. 只在 `FROM` 里引用共享的基座 blob，多个自定义模型共享权重，磁盘不会被重复占用。

### 踩坑记录

```text
坑 1：自定义模型只会复读用户的问题
结论：模型把 Prompt 原样回显，或生成一段就卡住不结束。
原因：TEMPLATE 与该模型训练时的 chat template 不匹配，或缺少结束符 stop。
解法：ollama show --modelfile 导出基座模板对照，补齐 TEMPLATE 与全部 stop 序列。

坑 2：改了 Modelfile 重新 create，行为却没变化
结论：以为参数没生效，反复折腾模板。
原因：ollama create 用了同名模型，但客户端连的还是旧的常驻实例；或参数被请求体 options 覆盖。
解法：create 用新名字区分版本；确认 API 请求体里没有同名字段覆盖，必要时 ollama stop 卸载旧实例。

坑 3：中文 SYSTEM 写进 Modelfile 后报错或角色失效
结论：create 失败，或系统提示没被模板带上。
原因：SYSTEM 内容含未转义的双引号/换行，或自定义 TEMPLATE 里根本没有 {{ .System }}。
解法：用 """...""" 包裹多行文本；检查模板中是否存在 {{ .System }} 占位。

坑 4：导入 GGUF 后显存爆掉或速度极慢
结论：create 成功但一运行就 OOM，或退化到 CPU。
原因：GGUF 的量化级别与声明的参数规模不匹配硬件，或导入的是未量化的大模型。
解法：用 ollama show 看 quantization_level 与 parameter_size，按 08.6 的显存估算换更小量化。

坑 5：num_ctx 调很大后模型答非所问
结论：上下文是变长了，但答案质量下降、开始胡编。
原因：KV cache 挤占了留给权重的显存，部分层被换出到内存，或超出模型训练时的有效上下文。
解法：按硬件余量设 num_ctx，开启 Flash Attention 与 KV cache 量化（见 08.6），并参考模型卡标称的最大上下文。
```
