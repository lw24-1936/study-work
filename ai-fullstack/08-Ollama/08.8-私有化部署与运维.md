## 概述

把 Ollama 从「本机玩具」变成「内网推理服务」，要解决的是四件运维事：**谁能访问**（网络暴露与鉴权）、**怎么访问**（反向代理与 TLS）、**跑在哪、怎么活**（systemd 与资源治理）、**出问题怎么知道**（日志与监控）。Ollama 本身刻意保持简单：默认只听 `127.0.0.1`，**本地 API 不带任何鉴权**，鉴权与 TLS 一律交给前置的代理层。这意味着私有化部署的安全边界完全由你怎么暴露它决定——直接 `OLLAMA_HOST=0.0.0.0` 扔到公网，等于把一台无密码的推理机送人。

```text
全篇主线：
1. 暴露 —— 默认 127.0.0.1，本地 API 无鉴权，公网暴露必须先有代理层
2. 代理 —— Nginx 转发 + 流式关缓冲 + 长超时 + 代理侧鉴权与 TLS
3. 服务 —— systemd 托管、Environment 注入参数、目录与磁盘规划
4. 观测 —— journalctl 看服务日志、OLLAMA_DEBUG 看调度细节、业务侧采集计时字段
5. 升级 —— 版本钉死、灰度并行、失败回滚，模型目录单独备份
```

## 网络暴露与鉴权边界

Ollama 默认绑定 `127.0.0.1:11434`，改绑定地址用 `OLLAMA_HOST`。官方在鉴权文档里第一句话就说清楚了：**本地 API（`http://localhost:11434`）不需要认证**；需要 API key 的是 `ollama.com` 的云服务，与本地部署无关。换句话说，谁能连上 11434 端口，谁就能推理、拉模型、建模型，没有任何账号体系来兜底。

| 使用场景 | 建议暴露方式 | 鉴权 |
|----------|--------------|------|
| 本机自用 | 保持默认 `127.0.0.1:11434` | 不需要 |
| 内网团队共用 | `OLLAMA_HOST=0.0.0.0:11434` + 防火墙限制来源网段 | 内网可信可省，跨部门建议代理层加 token |
| 跨网络/公网访问 | 绝不直接暴露端口，只经反向代理 | 必须：代理层 TLS + 鉴权（Bearer/Basic/SSO） |

除绑定地址外，还有两个与暴露相关的开关：`OLLAMA_ORIGINS` 控制 CORS 白名单（默认只放行来自 `127.0.0.1` 与 `0.0.0.0` 的跨源请求，浏览器扩展需要显式加上 `chrome-extension://*` 这类来源）；`OLLAMA_NO_CLOUD=1`（或 `~/.ollama/server.json` 里设 `disable_ollama_cloud: true`）关闭所有云功能，让实例变成纯本地模式——数据合规场景下这一项应当显式打开，关闭后服务日志会打印 `Ollama cloud disabled: true`。

```shell
# 1) 内网暴露：监听所有网卡（务必配合防火墙或代理层）
OLLAMA_HOST=0.0.0.0:11434 ollama serve

# 2) 纯本地模式：关闭云功能，适合数据不出内网的合规要求
OLLAMA_NO_CLOUD=1 ollama serve
# 或者写进配置文件（重启生效）
# cat ~/.ollama/server.json
# { "disable_ollama_cloud": true }

# 3) 允许指定前端来源跨源访问（多个用逗号分隔）
OLLAMA_ORIGINS=http://localhost:5173,https://webui.internal.example.com ollama serve

# 4) 验证暴露范围：本机与另一台机器分别探测
curl -s http://127.0.0.1:11434/api/version
curl -s http://<内网IP>:11434/api/version
```

```text
网络与鉴权要点：
1. 本地 API 无鉴权是官方明确的设计，安全边界等于网络边界
2. 默认监听 127.0.0.1，改成 0.0.0.0 之前先想清楚谁能访问
3. 公网访问一律走代理层，TLS 与鉴权都在代理上做
4. 合规场景开 OLLAMA_NO_CLOUD=1，日志会确认云功能已关闭
5. OLLAMA_ORIGINS 只管 CORS，不是鉴权，别把它当安全措施
```

## 反向代理与 TLS 配置

Ollama 官方给出的 Nginx 最小配置就是把请求转给 `localhost:11434`，并**显式设置 Host 头**——因为 Ollama 会校验 Host 头做 DNS 重绑定防护，Host 不匹配时请求会被拒绝。这也是官方用 ngrok / Cloudflare Tunnel 时都要加 `--host-header="localhost:11434"` 的原因。生产配置在此基础上要补三件事：**流式响应必须关缓冲**（否则打字机效果变成一次性吐出）、**超时必须放大**（长提示 prefill 可能几十秒）、**鉴权与 TLS 加在代理层**。

```nginx
# /etc/nginx/conf.d/ollama.conf
upstream ollama_backend {
    server 127.0.0.1:11434;
    keepalive 32;                     # 复用后端连接，降低每请求握手开销
}

server {
    listen 80;
    server_name llm.internal.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name llm.internal.example.com;

    ssl_certificate     /etc/letsencrypt/live/llm.internal.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/llm.internal.example.com/privkey.pem;

    # 图片 base64 与长上下文请求体可能很大
    client_max_body_size 64m;

    location / {
        # 简单 Bearer 鉴权：请求头必须带 Authorization: Bearer <token>
        if ($http_authorization != "Bearer change-me-token") {
            return 401;
        }

        proxy_pass http://ollama_backend;
        proxy_http_version 1.1;

        # Ollama 校验 Host 头，必须与本地地址一致
        proxy_set_header Host localhost:11434;
        proxy_set_header Connection "";

        # 流式推理：关闭缓冲，否则会攒满才一次性返回
        proxy_buffering off;
        proxy_cache off;
        chunked_transfer_encoding on;

        # 长提示 prefill 与长生成：超时要给够
        proxy_connect_timeout 10s;
        proxy_send_timeout    600s;
        proxy_read_timeout    600s;
    }
}
```

口令方式更适合给人用的界面，`auth_basic` 一行即可，配合 `htpasswd` 生成口令文件：

```shell
# 生成口令文件（供 auth_basic 使用）
sudo htpasswd -c /etc/nginx/.htpasswd ollama-user
```

```nginx
    location / {
        auth_basic "Ollama";
        auth_basic_user_file /etc/nginx/.htpasswd;
        proxy_pass http://ollama_backend;
        proxy_set_header Host localhost:11434;
        proxy_buffering off;
        proxy_read_timeout 600s;
    }
```

```shell
# 配置语法检查与生效
sudo nginx -t
sudo systemctl reload nginx

# 经代理访问验证（注意：流式响应应逐块返回，而不是等全部生成完）
curl -N https://llm.internal.example.com/api/generate \
  -H "Authorization: Bearer change-me-token" \
  -d '{"model":"qwen2.5:7b","prompt":"数到 10","stream":true}'

# 没走公网的临时隧道方案（官方文档写法，注意 Host 头）
ngrok http 11434 --host-header="localhost:11434"
cloudflared tunnel --url http://localhost:11434 --http-host-header="localhost:11434"
```

```text
反向代理要点：
1. Ollama 校验 Host 头，代理必须把 Host 设成 localhost:11434，否则请求被拒
2. 流式响应必须 proxy_buffering off，否则 API 的流式体验会退化成一次性返回
3. proxy_read_timeout 要给到分钟级，长提示 prefill 与长生成都可能超过 60 秒
4. TLS 与鉴权都落在代理层，Ollama 自身不提供这两项
5. 隧道工具（ngrok/cloudflared）是临时方案，生产用自建反代 + 正式证书
```

## 系统服务与资源治理

用官方安装脚本部署后，Ollama 以 systemd 服务运行，服务用户是 `ollama`。改配置的正确方式是 `systemctl edit ollama.service` 追加 `Environment` 行，再 `daemon-reload` + `restart`——直接改 `/etc/systemd/system/ollama.service` 会在下次升级时被覆盖。资源治理的重点是磁盘与显存两处：模型默认存放于 `/usr/share/ollama/.ollama/models`，换目录要设 `OLLAMA_MODELS` 并把目录属主改给 `ollama` 用户；显存与并发参数按 08.6 的结论注入，保证「托管启动」与「手工启动」参数一致。

```ini
# systemctl edit ollama.service 追加的内容
[Service]
# 暴露与跨源
Environment="OLLAMA_HOST=0.0.0.0:11434"
Environment="OLLAMA_ORIGINS=http://localhost:5173"
# 推理参数（与 08.6 的显存估算结论一致）
Environment="OLLAMA_CONTEXT_LENGTH=8192"
Environment="OLLAMA_FLASH_ATTENTION=1"
Environment="OLLAMA_KV_CACHE_TYPE=q8_0"
Environment="OLLAMA_MAX_LOADED_MODELS=2"
Environment="OLLAMA_NUM_PARALLEL=2"
Environment="OLLAMA_KEEP_ALIVE=30m"
# 纯本地模式（合规场景）
Environment="OLLAMA_NO_CLOUD=1"
# 模型目录迁到独立磁盘
Environment="OLLAMA_MODELS=/data/ollama/models"
# 资源限制：限制 CPU 配额与内存上限，避免影响同机其它服务
CPUQuota=1500%
MemoryMax=48G
```

```shell
# 生效流程（顺序不能错）
sudo systemctl daemon-reload
sudo systemctl restart ollama
systemctl show ollama -p Environment | tr ' ' '\n'   # 核对注入的参数
systemctl is-active ollama

# 迁移模型目录：属主必须给 ollama 用户，否则服务无法读写
sudo mkdir -p /data/ollama/models
sudo chown -R ollama:ollama /data/ollama/models
sudo -u ollama rsync -a /usr/share/ollama/.ollama/models/ /data/ollama/models/

# 磁盘规划：模型目录单独挂载并盯住容量
df -h /data
du -sh /data/ollama/models
```

离线环境与代理相关的三个坑值得提前处理：模型拉取走 HTTPS，如需出网代理只设 `HTTPS_PROXY`（官方明确提示**不要**设 `HTTP_PROXY`，会打断客户端到服务的连接）；`/tmp` 带 `noexec` 时用 `OLLAMA_TMPDIR` 指定可执行的临时目录；容器里跑 GPU 需要 `nvidia-container-toolkit`，且 GPU 从容器里消失的经典原因是 Docker 的 cgroup 驱动，需要在 `/etc/docker/daemon.json` 加 `"exec-opts": ["native.cgroupdriver=cgroupfs"]`。

```text
服务与资源治理要点：
1. 改配置用 systemctl edit 追加 Environment，别直接编辑 service 文件
2. 服务用户是 ollama，迁模型目录必须 chown -R ollama:ollama
3. 推理参数写进 unit，避免手工启动与托管启动两套参数不一致
4. 只设 HTTPS_PROXY，别设 HTTP_PROXY；noexec 的 /tmp 用 OLLAMA_TMPDIR 绕开
5. 模型目录单独挂载并监控容量，模型缓存能轻易吃掉几十到几百 GB
```

## 日志与监控

排障的第一手资料是服务日志：Linux + systemd 下用 `journalctl -u ollama`，容器里用 `docker logs <容器名>`，手工 `ollama serve` 则直接看终端输出。默认日志量克制，需要看卸载决策、GPU 探测、请求调度细节时开 `OLLAMA_DEBUG=1`（会显著增加日志量，只在排障时开）。Ollama 本身**不自带 Prometheus 指标端点**，监控要靠两层拼：外层是代理与系统指标（请求量、状态码、延迟、GPU 利用率），内层是 API 响应里的计时字段（prefill/decode 速度、加载耗时），后者用一个小型 exporter 定时聚合即可。

```shell
# 服务日志（跟随、只看最近若干行、按关键词过滤）
journalctl -u ollama --no-pager --follow --pager-end
journalctl -u ollama --since "1 hour ago" | grep -i -E "error|gpu|oom|panic"

# 详细调试日志（排障完记得关掉）
OLLAMA_DEBUG=1 ollama serve

# 容器部署
docker logs --tail 200 -f ollama

# 版本与模型清单（巡检脚本的两个基础事实）
ollama --version
ollama list
```

下面这个 exporter 只用标准库，暴露 Ollama 的存活状态、模型数量与当前驻留模型及其显存占用，可直接挂到 Prometheus 的抓取目标里：

```python
"""轻量 Prometheus exporter：暴露 Ollama 存活、模型数量与驻留模型显存。"""
import json
import urllib.request
from http.server import BaseHTTPRequestHandler, HTTPServer

OLLAMA = "http://localhost:11434"


def api(path: str) -> dict:
    with urllib.request.urlopen(f"{OLLAMA}{path}", timeout=5) as r:
        return json.loads(r.read().decode())


def render() -> str:
    lines = []
    try:
        models = api("/api/tags").get("models", [])
        lines.append("# HELP ollama_up Ollama 服务是否可达")
        lines.append("# TYPE ollama_up gauge")
        lines.append("ollama_up 1")
        lines.append("# HELP ollama_models_total 本地已拉取的模型数量")
        lines.append("# TYPE ollama_models_total gauge")
        lines.append(f"ollama_models_total {len(models)}")
        lines.append("# HELP ollama_model_size_bytes 单个模型占用的磁盘字节数")
        lines.append("# TYPE ollama_model_size_bytes gauge")
        for m in models:
            name = m["name"].replace('"', "")
            lines.append(f'ollama_model_size_bytes{{model="{name}"}} {m.get("size", 0)}')
        lines.append("# HELP ollama_model_loaded 模型当前是否驻留内存或显存")
        lines.append("# TYPE ollama_model_loaded gauge")
        for m in api("/api/ps").get("models", []):
            name = m["name"].replace('"', "")
            lines.append(f'ollama_model_loaded{{model="{name}"}} 1')
    except Exception:
        lines.append("ollama_up 0")
    return "\n".join(lines) + "\n"


class Handler(BaseHTTPRequestHandler):
    def do_GET(self) -> None:  # noqa: N802
        if self.path != "/metrics":
            self.send_error(404)
            return
        body = render().encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; version=0.0.4")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


if __name__ == "__main__":
    HTTPServer(("0.0.0.0", 9101), Handler).serve_forever()
```

本机真实验证（服务已启动、尚无模型）：

```text
$ curl -s http://localhost:11434/api/version
{"version":"0.40.4"}

$ curl -s http://localhost:11434/api/tags
{"models":[]}

$ curl -s http://localhost:11434/
Ollama is running

$ journalctl -u ollama -n 3 --no-pager
-- No entries --
```

最后一条说明：本机的 ollama 是通过独立二进制运行（`/usr/local/bin/ollama`），并没有注册成 systemd 服务，所以 `journalctl -u ollama` 没有条目。生产部署时应改用官方安装脚本注册服务，或自建 unit 文件，这样才有服务级日志与开机自启。

巡检与告警建议盯这几项：`ollama_up` 是否掉零（服务挂了）、5xx/503 比例（过载，对应 08.6 的队列上限）、请求延迟 p95 的抬升（显存不足导致换出或掉到 CPU）、模型目录剩余空间（拉新模型失败的头号原因）、`/api/ps` 里驻留模型数量是否超出预期（显存泄漏或 keep_alive 配置不当）。

```text
日志与监控要点：
1. journalctl -u ollama 是排障首选；容器用 docker logs，手工启动看终端
2. OLLAMA_DEBUG=1 才能看到卸载与调度决策，只在排障期间开启
3. Ollama 不自带指标端点，用代理/系统指标 + 自定义 exporter 两层覆盖
4. 必须告警：服务存活、503 比例、p95 延迟、模型目录剩余空间
5. 确认服务真的由 systemd 托管，否则重启后不会自动拉起
```

## 多模型管理与版本升级

多模型管理的日常动作是 `ollama list`（who）、`ollama ps`（谁在跑）、`ollama cp/rm`（改名与清理）。生产上建议给模型定命名规范（如 `team/model:版本`），私人实验模型加前缀区分；`ollama rm` 删除后共享的 blob 会被回收，但多个模型引用同一个 blob 时共享空间不会重复占用，所以清理前先 `ls` 一遍别误删线上依赖。

版本升级的原则是**先备份、再升级、后冒烟、能回滚**。Linux 重跑安装脚本即升级到最新版；要装指定版本（含回滚）用 `OLLAMA_VERSION` 环境变量。升级前记录当前版本、备份模型目录（或至少确认模型可重新拉取）、并准备好一台旧版本实例作为灰度对照。

```shell
# 1) 升级前：记录现状并备份模型目录
ollama --version
ollama list
sudo tar -C /usr/share/ollama/.ollama -czf /data/backup/ollama-models-$(date +%F).tgz models

# 2) 升级到最新版
curl -fsSL https://ollama.com/install.sh | sh

# 3) 升级到/回滚到指定版本
curl -fsSL https://ollama.com/install.sh | OLLAMA_VERSION=0.5.7 sh

# 4) 升级后：重启、核对版本、跑冒烟
sudo systemctl restart ollama
curl -s http://localhost:11434/api/version
ollama run qwen2.5:7b "回复 OK 两个字"
ollama ps
```

灰度升级可以用端口并存的方式：旧版本继续听 11434，新版本听 11435（`OLLAMA_HOST=127.0.0.1:11435`），在反向代理里把一小部分流量引到新版本，验证通过再整体切换。这样出问题时只需改回代理配置，不涉及降级安装。

```shell
# 新版本并行实例（同一台机器上灰度）
OLLAMA_HOST=127.0.0.1:11435 ollama serve

# 用两个端口分别验证同一组请求
curl -s http://127.0.0.1:11434/api/version
curl -s http://127.0.0.1:11435/api/version

# 模型目录在多机之间同步（每台机器保留本地副本，不要多机并发写同一目录）
rsync -a --delete /data/ollama/models/ ollama2:/data/ollama/models/
```

```text
多模型与升级要点：
1. list/ps/cp/rm 是日常四件事，删除前确认没有模型共享与线上引用
2. 升级前备份模型目录并记录版本号，升级后立刻跑冒烟请求
3. 回滚用 OLLAMA_VERSION 指定旧版本重新安装，比手工换二进制可靠
4. 灰度用多端口并存 + 代理分流，失败只改配置不降级安装
5. 多机共享模型用 rsync 同步到各机本地目录，别让多台实例共写一份目录
```

## 应用场景实战

### 场景一：把单机 Ollama 变成内网推理服务（systemd + Nginx + 鉴权 + 监控）

需求：一台内网推理服务器，供 20 人左右的团队与两个内部应用使用，需要 HTTPS、简单鉴权、开机自启、异常可观测。做法是按下面的顺序落地，每一步都可验证。

```shell
# 第一步：systemd 托管并注入生产参数
sudo systemctl edit ollama.service
# 写入本章 [Service] 段落的环境变量（HOST=0.0.0.0、NUM_PARALLEL=2 等）
sudo systemctl daemon-reload
sudo systemctl restart ollama
```

## 最佳实践与踩坑记录

### 最佳实践

1. 默认保持 `127.0.0.1`；确需内网共享再改 `OLLAMA_HOST=0.0.0.0`，并同步在防火墙或安全组限制来源网段。
2. 公网/跨网络访问一律经反向代理，TLS 与鉴权都在代理层实现，绝不让 11434 端口直接可达。
3. 反向代理必配三项：`proxy_set_header Host localhost:11434`（Host 校验）、`proxy_buffering off`（流式）、`proxy_read_timeout 600s`（长 prefill）。
4. 所有环境变量通过 `systemctl edit` 注入 unit，并把生效值存档，避免手工启动与托管启动两套参数。
5. 模型目录单独挂载并对 `ollama` 用户可写，纳入磁盘容量告警。
6. 合规场景显式打开纯本地模式（`OLLAMA_NO_CLOUD=1`），并确认日志出现云功能已关闭的提示。
7. 升级遵循「备份 → 灰度 → 冒烟 → 观察 → 再全量」，回滚用 `OLLAMA_VERSION` 指定版本重装，并提前演练一次。
8. 监控覆盖内外两层：外层服务存活、状态码与延迟；内层用计时字段与 exporter 反映真实推理性能。

### 踩坑记录

```text
坑 1：把 OLLAMA_HOST 设成 0.0.0.0 后端口被公网扫到
结论：任何能连上 11434 的人都能推理、拉模、建模型，日志里出现陌生来源的请求。
原因：官方明确说明本地 API 不需要认证，Ollama 自身不提供任何鉴权与 TLS。
解法：改回默认绑定或仅在可信内网暴露；公网访问必须走反向代理，在代理层加 TLS 与 Bearer/Basic 鉴权。

坑 2：经 Nginx 反代后请求被拒，或流式输出变成一次性返回
结论：接口返回错误，或前端「打字机效果」消失，所有 token 在一次响应里涌出。
原因：Ollama 校验 Host 头做 DNS 重绑定防护，Host 不匹配会拒绝；Nginx 默认开启响应缓冲，把流式响应攒起来一次性发出。
解法：代理里显式 proxy_set_header Host localhost:11434，并设 proxy_buffering off 与 chunked_transfer_encoding on，用 curl -N 验证逐块返回。

坑 3：升级后模型目录权限报错，服务起不来
结论：systemctl status ollama 报权限被拒，日志提示无法读写模型目录。
原因：Ollama 以 ollama 用户运行，新目录/新磁盘的属主不是它，或 OLLAMA_MODELS 指向的目录未授权。
解法：sudo chown -R ollama:ollama <目录>，把 Environment="OLLAMA_MODELS=..." 写进 unit，再 daemon-reload 与 restart。

坑 4：改完配置重启服务，参数却没生效
结论：日志与 ollama ps 显示的还是旧参数（例如上下文仍是 4096）。
原因：环境变量写在错误的文件里被覆盖，或只改了 OLLAMA_ / 忘了 daemon-reload + restart，或与手工启动的实例并存（11434 已被旧进程占用）。
解法：用 systemctl edit 写 drop-in 并 daemon-reload + restart，用 systemctl show ollama -p Environment 核对；确认没有手工 ollama serve 占着端口。

坑 5：拉模型失败或客户端连不上，日志没有明显错误
结论：ollama pull 卡住或超时；配置了 HTTP_PROXY 后连 localhost 也失败。
原因：模型拉取走 HTTPS，官方明确提示不要设置 HTTP_PROXY，设了会打断客户端到服务的连接；内网无外网时也拉不到模型。
解法：只设 HTTPS_PROXY（并安装代理证书）；内网环境用 rsync 同步模型目录到各机本地副本，或用内网镜像仓库分发。

坑 6：容器里 GPU 用着用着就掉到 CPU
结论：起始正常，一段时间后日志报 GPU 发现失败，推理退化到 CPU。
原因：官方排障文档列出的经典原因是 Docker 使用 systemd cgroup 管理，导致 GPU 设备在容器内变得不可发现。
解法：在宿主 /etc/docker/daemon.json 加 "exec-opts": ["native.cgroupdriver=cgroupfs"]，重启 Docker 与容器；同时确认容器运行时与 nvidia-container-toolkit 正常。
```
