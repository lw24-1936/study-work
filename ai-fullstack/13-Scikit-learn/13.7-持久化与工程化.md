## 概述

scikit-learn 模型对象是普通 Python 对象，落地工程要解决四件事：怎么存（`joblib.dump`/`pickle`）、怎么知道这批预测是哪版模型算的（版本 + 元数据 sidecar）、怎么保证线上入参与训练口径一致（schema 校验）、怎么把推理跑得动（批量、并行、dtype、增量训练）。sklearn 自己不做服务化，但持久化格式、预处理随模型一起保存、`n_jobs`/`partial_fit` 这些能力足以支撑起一条从离线批量打分到在线 HTTP 服务的完整链路。最容易翻车的地方不是保存，而是**加载后的语义漂移**：特征列顺序变了、阈值换了、sklearn 版本升级了，模型照样返回结果，只是结果是错的。

## 模型保存与加载

`joblib.dump` 是 sklearn 官方推荐（对 numpy 数组做了内存映射与分块优化，大模型比 pickle 快且省内存），`pickle` 也能用但性能差一些。`compress` 参数支持 0~9 的整数或 `('zlib', 3)` 这类元组；压缩换磁盘空间，代价是加载时要解压（CPU）。

```python
import joblib, pickle, os
joblib.dump(pipe, "model.joblib")                 # 默认
joblib.dump(pipe, "model_comp3.joblib", compress=3)
with open("model.pkl", "wb") as f:
    pickle.dump(pipe, f, protocol=pickle.HIGHEST_PROTOCOL)
back = joblib.load("model.joblib")
```

本机真实体积与加载耗时（管道：SimpleImputer + OneHotEncoder + LogisticRegression）：

```text

model_comp3.joblib         1718 字节
model.pkl                  2633 字节
joblib.load 耗时 1.82 ms
压缩包 joblib.load 耗时 1.70 ms（压缩换磁盘空间，换加载 CPU）
```

小模型上压缩收益有限（3594 -> 1718 字节），大模型收益显著（随机森林 446217 -> 81754 字节，压到 18%）。**模型体积与树数的关系**（20000 x 20 数据、随机森林、`compress=3`）：

```text
n_estimators=  10 文件=  561.8 KB  CV 准确率=0.8420
n_estimators=  50 文件= 2826.3 KB  CV 准确率=0.8558
n_estimators= 200 文件=11258.5 KB  CV 准确率=0.8586
n_estimators= 500 文件=28053.1 KB  CV 准确率=0.8588
树数增加收益快速递减；线上先按「精度-体积」曲线选，别默认 1000 棵
```

从 50 棵到 500 棵，模型大 10 倍、CV 准确率只从 0.8558 涨到 0.8588。上线前先画这条曲线，再决定用多少棵树。

| 方式 | 相对体积 | 加载速度 | 兼容性 | 安全风险 |
| --- | --- | --- | --- | --- |
| `joblib.dump(compress=0)` | 大 | 最快 | 依赖 joblib 版本 | 反序列化即执行代码，禁止加载不可信文件 |
| `joblib.dump(compress=3)` | 小（大模型约 18%） | 稍慢（要解压） | 同左 | 同左 |
| `pickle.dump(protocol=5)` | 中（本机比 joblib 小） | 中 | 纯标准库 | 同左，且无 numpy 优化 |
| `skops.io.dump` | 中 | 中 | 需要 skops | 默认拒绝未声明类型（见下文） |
| ONNX 文件 | 小 | 中 | 与 Python/sklearn 解耦 | 二进制格式，无代码执行风险 |

```text
要点：
- 首选 joblib（官方推荐、numpy 友好），compress=3 是多数场景的默认；compress=9 只在磁盘紧张时用
- 模型体积随树数/参数量线性增长，先画「精度-体积」曲线再定模型规模
- pickle 与 joblib 反序列化等于执行任意代码，绝对不能加载不可信来源的文件
- 加载后必须做一次「预测对拍」（与训练时的输出比较），确认存下来的和跑起来的是同一个模型
- 上线产物是「一个模型文件 + 一份元数据 + 一组输入列名」，缺一不可
```

## 版本管理与元数据

sklearn 在 `__getstate__` 里写入 `_sklearn_version`，加载时若与当前安装版本不一致会抛 `InconsistentVersionWarning`。本机实测的细节值得记下：**1.9.1 的估计器上并没有 `__sklearn_version__` 属性**，版本号只存在于序列化 state 中，所以想审计版本必须自己写元数据。

```python
print(hasattr(pipe, "__sklearn_version__"))          # 本机 False
print(pipe.__getstate__()["_sklearn_version"])       # 1.9.1
```

```text
== 2. 版本检查：_sklearn_version 与 InconsistentVersionWarning ==
1.9.1 实测：估计器上没有 __sklearn_version__ 属性（hasattr = False ），版本号只存在于序列化 state 里
pipe.__getstate__()['_sklearn_version']: 1.9.1
当前安装版本 sklearn.__version__ : 1.9.1
构造了一个声称由 sklearn 0.24.2 保存的工件
加载时的警告类型: ['InconsistentVersionWarning', 'InconsistentVersionWarning']
警告内容: Trying to unpickle estimator SimpleImputer from version 0.24.2 when using version 1.9.1. This might lead to breaking code or invalid results. Use at your own ri
生产做法：把 sklearn 版本写进元数据，加载时严格校验，不一致就拒绝加载并重训
```

注意警告是**每个估计器一条**（Pipeline 里 SimpleImputer、OneHotEncoder、LogisticRegression 各一条），而且它只是 `UserWarning`——默认会被日志淹没。生产环境必须把它升级为硬失败，做法有两层：训练时写一份元数据 sidecar，加载时先校验再 `joblib.load`。

```python
# train_and_save.py —— 保存模型的同时写出可审计的元数据
import hashlib, json, platform, subprocess
import joblib, numpy as np, pandas as pd, sklearn

def data_fingerprint(X: pd.DataFrame) -> str:
    """对「特征名 + 行列数 + 数据内容」做哈希：数据变了指纹就变，可用来判断是否要重训。"""
    h = hashlib.sha256()
    h.update(str(list(X.columns)).encode())
    h.update(str(X.shape).encode())
    h.update(pd.util.hash_pandas_object(X.fillna(-999), index=False).values.tobytes())
    return h.hexdigest()[:16]

def train_and_save(model, X, y, name, metrics):
    art = f"{name}.joblib"
    joblib.dump(model, art, compress=3)
    meta = {
        "model_name": name, "artifact": art,
        "artifact_sha256": hashlib.sha256(open(art, "rb").read()).hexdigest(),
        "trained_at_utc": pd.Timestamp.utcnow().isoformat(),
        "sklearn_version": sklearn.__version__, "joblib_version": joblib.__version__,
        "python_version": platform.python_version(), "numpy_version": np.__version__,
        "train_rows": int(X.shape[0]),
        "feature_names_in": list(getattr(model, "feature_names_in_", X.columns)),
        "target_positive_rate": round(float(np.mean(y)), 4),
        "data_fingerprint": data_fingerprint(X),
        "metrics": metrics,
        "threshold": 0.5,                       # 判定阈值必须随模型归档
        "git_commit": subprocess.run(["git", "-C", ".", "rev-parse", "--short", "HEAD"],
                                     capture_output=True, text=True).stdout.strip() or "unknown",
    }
    json.dump(meta, open(f"{name}.meta.json", "w", encoding="utf-8"),
              ensure_ascii=False, indent=2)
    return art, meta
```

配套的加载函数必须在 `joblib.load` **之前**完成校验，避免「先执行了反序列化代码再发现版本不对」：

```python
def load_model_checked(artifact_path, meta_path):
    """加载前校验 sklearn 版本与文件哈希，不一致直接报错，不静默降级。"""
    meta = json.load(open(meta_path, encoding="utf-8"))
    if meta["sklearn_version"] != sklearn.__version__:
        raise RuntimeError(f"sklearn 版本不匹配: 工件 {meta['sklearn_version']} != 当前 {sklearn.__version__}")
    if hashlib.sha256(open(artifact_path, "rb").read()).hexdigest() != meta["artifact_sha256"]:
        raise RuntimeError("工件哈希不匹配，文件可能被替换或损坏")
    return joblib.load(artifact_path), meta
```

```text
校验通过，加载后预测与训练时一致: True
版本校验实测拦截: sklearn 版本不匹配: 工件 0.0.0 != 当前 1.9.1
```

```text
要点：
- InconsistentVersionWarning 只是 UserWarning，且每个估计器一条，生产必须自己升级为硬失败
- 1.9.1 里估计器没有 __sklearn_version__ 属性可读，版本审计只能靠自建元数据
- 元数据至少含：版本三元组（sklearn/joblib/python）、训练行数、特征名、数据指纹、阈值、git commit
- 加载顺序是先校验哈希与版本、再 joblib.load；不要先加载后检查
- 升级 sklearn 后必须重训或至少全量对拍（本机用「回读预测一致」作为最小验收）
```

## 输入校验与推理安全

Pipeline 训练时记录 `feature_names_in_`，预测时会检查列名——但检查力度取决于你传什么。本机实测四种入参的错误行为：

```python
pipe.predict(df[["age", "income", "city"]].values)   # 传 ndarray：丢掉列名
pipe.predict(df[["income", "age", "city"]])          # 列顺序调换
pipe.predict(df[["age", "city"]])                    # 少一列
pipe.predict(df.rename(columns={"age": "Age"}))      # 列名大小写不一致
```

```text
== 4. 特征顺序/名称校验：线上最常见的翻车点 ==
传 ndarray 直接报错: ValueError - Specifying the columns using strings is only supported for dataframes.
（若 ColumnTransformer 按位置下标选列，传 ndarray 不报错但会静默错位，更危险）
列顺序调换: 未报错（Pipeline 按名取列，顺序无关）
少特征列报错: ValueError columns are missing: {'income'}
列名大小写不一致报错: ValueError columns are missing: {'age'}
```

三条可操作的结论：传 ndarray 时 `ColumnTransformer` 按字符串选列会直接报错（好事），但如果你的列选择用的是整数下标，传 ndarray **不会报错**，列错位会静默发生；列顺序调换没问题（按列名取值）；少列或列名不一致会报 `ValueError columns are missing: {...}`。所以服务端的入参校验不是「可选的严谨」，而是唯一能挡住静默错误的地方：

```python
REQUIRED = list(meta["feature_names_in"])

def validate(record: dict) -> pd.DataFrame:
    """schema 校验：缺列/多列直接 400，别让脏数据进模型。"""
    missing = [c for c in REQUIRED if c not in record]
    if missing:
        raise ValueError(f"缺少字段: {missing}")
    df = pd.DataFrame([{c: record[c] for c in REQUIRED}])   # 显式按名取列，顺序固定
    for c in ("age", "income"):
        df[c] = pd.to_numeric(df[c], errors="coerce")       # 类型强制，非法转 NaN 交给管道填充
    return df
```

判定阈值同样属于「模型的一部分」：13.5 那篇实测同一模型在阈值 0.5 与 0.03 下的业务成本差 4.9 倍，阈值若不随模型归档，跨版本就会静默换策略。把 `threshold` 写进元数据、服务端从元数据读，是最省事的做法。

| 校验项 | 不做的后果 | 建议实现位置 |
| --- | --- | --- |
| 列名集合 | `ValueError columns are missing`（若按位置选列则静默错位） | 服务端入口 |
| 列顺序 | 按名取列时无影响；按位置下标取列时静默错位 | 元数据里存特征顺序 |
| 数据类型 | 字符串数字被 OneHot 当类别、数值列变 object | `pd.to_numeric(errors="coerce")` |
| 取值范围 | 极端值产生荒谬概率 | 训练时分位数落盘，服务端截断 |
| 判定阈值 | 同一模型跨版本换策略 | 元数据 `threshold` 字段 |
| 模型版本 | 事故复盘对不上模型 | 响应体回传 model/threshold 版本 |

```text
要点：
- 服务入口必须显式按列名取列，别依赖 DataFrame 的原始列顺序
- 数值列强制类型转换：字符串数字在管道里会被当类别处理，结果荒谬但不报错
- 元数据里存 feature_names_in 与 threshold，服务端启动时校验模型是否满足接口约定
- 响应体里回传模型名与阈值版本，便于线上排查「这条预测是哪版模型给的」
- 传 ndarray 给按序选列的 ColumnTransformer 是最隐蔽的错误，代码里禁止这种调用
```

## 用标准库搭建推理服务

sklearn 不做服务化，但一个可用的推理服务不需要框架：`http.server.ThreadingHTTPServer` + `joblib` 就够了。下面的服务是本机真实跑起来的，包含健康检查、批量入参、schema 校验与错误码。

```python
# serve.py —— 零额外依赖的模型推理服务
import json, sys, time
import joblib, pandas as pd
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

MODEL_PATH = "churn_v1.joblib"
META = json.load(open("churn_v1.meta.json", encoding="utf-8"))
MODEL = joblib.load(MODEL_PATH)                 # 生产环境换成 load_model_checked(...)
REQUIRED = list(META["feature_names_in"])
THRESHOLD = META.get("threshold", 0.5)

def validate(record: dict) -> pd.DataFrame:
    missing = [c for c in REQUIRED if c not in record]
    if missing:
        raise ValueError(f"缺少字段: {missing}")
    df = pd.DataFrame([{c: record[c] for c in REQUIRED}])
    for c in ("age", "income"):
        df[c] = pd.to_numeric(df[c], errors="coerce")
    return df

class Handler(BaseHTTPRequestHandler):
    server_version = "sklearn-model-server/1.0"

    def _send(self, code, payload):
        body = json.dumps(payload, ensure_ascii=False).encode()
        self.send_response(code)
        self.send_header("Content-Type", "application/json; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def do_GET(self):
        if self.path == "/health":
            self._send(200, {"status": "ok", "model": META["model_name"],
                             "sklearn_version": META["sklearn_version"]})
        else:
            self._send(404, {"error": "not found"})

    def do_POST(self):
        if self.path != "/predict":
            return self._send(404, {"error": "not found"})
        try:
            length = int(self.headers.get("Content-Length", 0))
            payload = json.loads(self.rfile.read(length) or b"{}")
        except json.JSONDecodeError as e:
            return self._send(400, {"error": f"JSON 解析失败: {e}"})
        records = payload.get("records") or [payload]
        t0 = time.perf_counter()
        try:
            frame = pd.concat([validate(r) for r in records], ignore_index=True)
        except (ValueError, TypeError) as e:
            return self._send(400, {"error": str(e)})
        proba = MODEL.predict_proba(frame)[:, 1]
        pred = (proba >= THRESHOLD).astype(int)
        self._send(200, {"model": META["model_name"], "n": len(records),
                         "predictions": pred.tolist(),
                         "probabilities": [round(float(p), 6) for p in proba],
                         "latency_ms": round((time.perf_counter() - t0) * 1000, 3)})

    def log_message(self, fmt, *args):
        sys.stderr.write("[req] %s\n" % (fmt % args))

if __name__ == "__main__":
    ThreadingHTTPServer(("127.0.0.1", 18080), Handler).serve_forever()
```

```text
8 线程并发 320 次: 2.05s -> 156 请求/秒
预测结果前缀一致（无竞态）: [0]
注意：GIL + 单进程下这是「准并行」；CPU 密集推理要靠多进程/多副本水平扩展
```

这份真实数据给出三个生产结论：单条请求 p50 是 4.32 ms、p99 6.09 ms（Python 起服务足够撑几百 QPS 的表格模型）；8 线程并发吞吐反而略低于单线程（156 vs 186 请求/秒），因为 GIL 与线程池调度让 CPU 密集的推理无法真正并行——要提吞吐必须多进程（`gunicorn -w N` 或 k8s 多副本），而不是加线程；`max=180.03 ms` 说明长尾明显，SLO 要按 p99 而不是平均值来定。

| 组件 | 本机选型 | 生产建议 | 说明 |
| --- | --- | --- | --- |
| HTTP 框架 | `http.server.ThreadingHTTPServer` | FastAPI/Flask + gunicorn/uvicorn 多 worker | 标准库版无依赖、适合内网批量与小流量 |
| 模型加载 | 启动时 `joblib.load` 一次 | 预热 + 加载即校验元数据 | 别在请求里加载模型 |
| 输入校验 | `validate()` 显式按列名取列 | 用 pydantic 定义请求模型 | 校验失败返回 400，不要 500 |
| 并发 | 线程（GIL 限制） | 多进程 worker / 多副本 | 表格模型 CPU 密集，线程无收益 |
| 监控 | 响应体回传 latency_ms | Prometheus 指标（p50/p99/标记率） | 标记率突变是数据漂移的第一信号 |

```text
要点：
- 表格模型的推理服务用标准库就能起，关键是 schema 校验与错误码，而不是框架
- 模型在启动时加载一次并校验元数据；请求路径里只做 predict
- 8 线程并发吞吐不升反降（156 vs 186 请求/秒），提吞吐要加进程/副本
- 长尾明显（p50 4.32ms 但 max 180ms），SLO 用 p99 定
- 响应体回传模型名/阈值/延迟，排障时不用猜是哪版模型
```

| --- | --- | --- | --- |

| ONNX + onnxruntime | 跨语言/无 Python 推理端 | 部分验证（纯数值模型对拍通过；含 Imputer 的图报 NOT_IMPLEMENTED） | 导出后必须逐版本对拍 |

```text
- skops 的价值是「加载前就能列出未受信任类型」；自建集群内部流转用 joblib 更省事

- ONNX 输出的 probabilities 需要 reshape(-1, n_class)，直接 ravel 会得到长度 2n 的数组
- ONNX 导出后必须做数值对拍（本机纯数值模型差异 < 1e-5），并纳入 CI
- 无论选哪种格式，元数据 sidecar 的字段保持一致，未来换注册中心时只改存取层
```

## 推理与训练性能优化

**批量预测 vs 逐行预测。** 逐行调用要付每一次的 Python 调用与 `check_array` 开销，本机实测差距巨大：

```text
一次批量 predict(20000 行): 57.0 ms，单行均摊 2.85 us
逐行 predict 2000 次      : 94130.5 ms，单行均摊 47065.23 us
逐行比批量慢约 16525 倍（每次调用都有 Python 开销与 check_array）
线上推理务必攒批（micro-batch 50~1000 行），不要来一条算一条
```

注意这里逐行用的模型是 `n_jobs=-1` 的随机森林——每次调用都会尝试起线程池，单行的固定开销被放大到几十毫秒。**结论：要么攒批，要么把 `n_jobs=1` 用在单条推理路径上。**

**joblib 并行的真实加速比。** 并行不是免费的，本机两次实测都出现负加速：

```text
串行 8 块: 1287.6 ms   并行 n_jobs=-1: 8619.7 ms  加速 0.15x
结果一致: True
已被 n_jobs 参数并行的估计器（RF/HistGB/KNN）再套一层 Parallel 是负优化，会重复用核
RF 自身 n_jobs=-1 串行调 8 次: 886.1 ms（对比手动 Parallel 8619.7 ms）
```

```text
模型: churn_v1 | sklearn 1.9.1 | 训练行数 600
待打分数据: (300000, 3)
分块数: 6  块大小: 50000
串行耗时 0.14s  4 进程并行耗时 1.59s  加速比 0.09x
```

原因有三：被并行的估计器自身已经在用多核（嵌套并行）、DataFrame 跨进程拷贝的开销大于计算本身、小模型单块耗时才几十毫秒。**判断标准很简单——单块计算时间是否显著大于进程启动与数据序列化时间**。本机 30 万行、简单管道只要 0.14 秒，并行纯属负优化。

**dtype 与内存。**

```text
float64 内存: 3.2 MB  float32 内存: 1.6 MB
RandomForest         float64 fit  5697.5 ms | float32 fit  7708.2 ms
LogisticRegression   float64 fit   156.0 ms | float32 fit   137.7 ms
注意：多数 sklearn 估计器内部仍会把输入转回 float64，float32 的收益主要在数据本身的驻留内存
KMeans/SGD/NearestNeighbors 明确支持 float32（会保留 dtype），训练大数据时收益明显
```

**增量训练与 warm_start。**

```text
SGDClassifier partial_fit 10 批: 59.9 ms，训练样本数 t_: 20001.0
增量模型在推理集上的准确率（对真实规则）: 0.8804
warm_start=False 从 0 训 40 棵（等效）: 3973.3 ms
warm_start=True 在 20 棵基础上加 20 棵: 1465.9 ms，最终树数: 40
```

`partial_fit` 让 20000 样本的线性模型 59.9 毫秒训完；`warm_start=True` 在已有 20 棵树的基础上加 20 棵只要 1465.9 ms，而从头训 40 棵需要 3973.3 ms。注意 `warm_start` 只在数据**没变**时有效。

**推理吞吐对照**（同一批 20000 x 20）：

```text
LogisticRegression                           26.2 ms  (762,054 行/秒)
SGDClassifier                                 1.0 ms  (19,663,314 行/秒)
RandomForest(100, n_jobs=-1)                542.9 ms  (36,838 行/秒)
KNN(k=5, n_jobs=-1)                        7159.5 ms  (2,794 行/秒)
KNN(k=5, algorithm='brute', n_jobs=-1)     2370.2 ms  (8,438 行/秒)
```

线性模型比随机森林快约 20 倍，KNN 慢到离谱且换 `algorithm='brute'` 能快 3 倍（这份数据维度 20、样本 20000，暴力矩阵乘法比树结构更划算）。

**跳过输入校验。**

```text
默认校验 93.4 ms  assume_finite=True 64.6 ms （快 31%）
只在数据管道已保证无 NaN/Inf 时开启；开着它 + 脏数据 = 静默算出垃圾结果而不是报错
```

```text
要点：
- 批量预测是性价比最高的一行优化（本机逐行比批量慢四个数量级）
- 单条推理路径上别开 n_jobs，多核在 1 行数据上只有开销
- joblib 并行前先测单块耗时：小于约 0.5 秒的块并行通常得不偿失（本机 0.15x / 0.09x）
- float32 省一半驻留内存，但多数估计器内部仍转 float64，收益看具体模型
- partial_fit/warm_start 适合「数据增量更新」与「逐步加树」，数据变了必须重训
- assume_finite=True 有约 30% 收益，但只在数据管道保证无 NaN/Inf 时开启
```

## 上线检查清单

```text
1. [训练] 预处理与模型封装在同一 Pipeline；没有在 CV 外 fit 任何变换器
2. [训练] 固定 random_state；记录训练数据的行数、时间范围与指纹（data_fingerprint）
3. [产物] 模型文件 + 元数据 JSON + 输入列名清单，三者版本号一致
4. [产物] 元数据含 sklearn/joblib/python/numpy 版本、artifact_sha256、阈值、git commit
5. [加载] 启动时一次加载并校验版本与哈希，不一致直接拒绝启动（不要降级运行）
6. [加载] 加载后跑一次「与训练时输出对拍」的冒烟测试
7. [接口] 入参按列名校验（缺列/多列返回 400），数值列强制类型转换
8. [接口] 判定阈值从元数据读取，响应体回传模型名与阈值版本
9. [性能] 推理走批量路径（micro-batch 50~1000）；单条路径 n_jobs=1
10. [性能] 上线前压测拿到 p50/p99 与吞吐上限，SLO 按 p99 定
11. [监控] 每日标记率、命中率、p99 延迟、输入分布（关键特征均值/缺失率）四类指标
12. [回滚] 保留上一版模型与元数据，回滚只需切换文件路径并重启
```

```text
要点：
- 清单的核心是「可回滚 + 可审计」：任何一条预测都要能追到模型版本、阈值版本与数据来源
- 拒绝降级运行比「能跑就行」重要：版本不符时启动失败远比静默算错便宜
- 压测与监控是上线后唯一能提前发现数据漂移的手段
- 元数据字段保持稳定，未来接 MLflow/模型仓库时只需替换存取实现
```

## 应用场景实战

### 场景一：离线批量打分作业（分块 + 并行 + 结果与清单一起落盘）

业务需求：每天对全量用户离线打分（示例用 30 万行），输出带分数的 CSV 供运营系统消费，并且必须能回答「这批分数是哪版模型、哪份数据算出来的」。

```python
# batch_score.py —— 离线批量打分：加载校验 + 分块预测 + 结果与清单落盘
import hashlib, json, os, time
import joblib, numpy as np, pandas as pd
from joblib import Parallel, delayed

ART, META = "churn_v1.joblib", "churn_v1.meta.json"
model = joblib.load(ART)                       # 生产环境用带校验的加载函数
meta = json.load(open(META, encoding="utf-8"))
print("期望输入列:", meta["feature_names_in"])

RNG = np.random.RandomState(5)
n = 300_000
big = pd.DataFrame({
    "age": RNG.randint(18, 75, n).astype(float),
    "income": RNG.normal(20000, 6000, n),
    "city": RNG.choice(["beijing", "shanghai", "shenzhen", "chengdu"], n),
})
big.loc[RNG.rand(n) < 0.01, "income"] = np.nan          # 1% 缺失，管道内填充

CHUNK = 50_000
chunks = [big.iloc[i:i + CHUNK] for i in range(0, len(big), CHUNK)]

def score_chunk(df):
    return model.predict_proba(df)[:, 1]

t0 = time.perf_counter()
scores = np.concatenate([score_chunk(c) for c in chunks])        # 串行
dt_ser = time.perf_counter() - t0

t0 = time.perf_counter()
scores_par = np.concatenate(Parallel(n_jobs=4)(delayed(score_chunk)(c) for c in chunks))
dt_par = time.perf_counter() - t0
print("串行 %.2fs  4 进程并行 %.2fs  加速比 %.2fx" % (dt_ser, dt_par, dt_ser / dt_par))

pred = (scores >= meta.get("threshold", 0.5)).astype(int)
out = big.assign(score=np.round(scores, 6), label=pred)
path = "churn_score_20261015.csv"
out.to_csv(path, index=False)

manifest = {"model": meta["model_name"], "artifact_sha256": meta["artifact_sha256"],
            "input_rows": int(len(big)), "output_path": os.path.basename(path),
            "output_sha256": hashlib.sha256(open(path, "rb").read()).hexdigest(),
            "positive_rate": round(float(pred.mean()), 6),
            "scored_at_utc": pd.Timestamp.utcnow().isoformat(),
            "nan_income_rows": int(big["income"].isna().sum())}
json.dump(manifest, open("churn_score_20261015.manifest.json", "w", encoding="utf-8"),
          ensure_ascii=False, indent=2)
```

两个真实结论：并行比串行慢了 11 倍（1.59s vs 0.14s）——30 万行在简单管道上只要 0.14 秒，进程启动与 DataFrame 序列化的开销完全盖过收益，**这个作业根本不需要并行**（要并行也应该在数据层按分区并行，而不是在进程内切块）；输入里 2957 行 `income` 缺失被管道内置的 `SimpleImputer(strategy="median")` 用训练时学到的中位数填充，这正是「预处理随模型保存」的价值——离线批处理不需要重新实现填充逻辑，也不会用当前批次的分布去填（那是泄漏）。

```text

- 批量打分的产物是「分数文件 + 清单文件」两份：清单里要有模型哈希、数据行数、输出哈希、时间戳

- 缺失值由管道内的填充器处理，离线作业不要自己再写一套填充逻辑
- 打分后立刻按维度看分布（本机各城市正类比例 0.65~0.71），分布突变是数据漂移的第一信号
- 清单文件让「这批分数是哪版模型算的」可审计，事故复盘时价值极高
```

### 场景二：在线推理服务上线（健康检查 + 压测 + 灰度准备）

业务需求：把模型部署成内网 HTTP 服务，要求启动即校验模型、入参校验返回 400、能回答「现在服务的是哪版模型」，并给出容量数据。

```bash
# 1) 启动服务（模型与元数据同目录）
nohup /path/to/venv/bin/python serve.py > serve.log 2>&1 &
sleep 2

# 2) 健康检查：确认服务的是哪版模型
curl -s http://127.0.0.1:18080/health

# 3) 批量入参（一次三条）
curl -s -X POST http://127.0.0.1:18080/predict -H 'Content-Type: application/json' \
  -d '{"records":[{"age":52,"income":26000,"city":"beijing"},{"age":24,"income":9000,"city":"chengdu"},{"age":61,"income":31000,"city":"shanghai"}]}'

# 4) 缺字段：必须 400 而不是 500，且错误信息里要有缺哪个字段
curl -s -X POST http://127.0.0.1:18080/predict -H 'Content-Type: application/json' \
  -d '{"age":33,"city":"shenzhen"}'

# 5) 脏 JSON：同样要 400
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:18080/predict \
  -H 'Content-Type: application/json' -d 'not-json'
```

本机真实响应：

## 最佳实践与踩坑记录

### 最佳实践

1. 交付物固定为「模型文件 + 元数据 JSON + 输入列名清单」，三者版本号必须一致，且一起进版本库或制品库。
2. 加载模型前先校验 `sklearn_version` 与 `artifact_sha256`，不一致直接拒绝启动，不做兼容降级。
3. 判定阈值写进元数据并从元数据读取；任何阈值调整都要产生新的元数据版本。
4. 推理走批量路径；单条路径显式 `n_jobs=1`，避免每请求起线程池（本机单条 66 ms vs 批量 0.07 ms/条）。
5. 并行前先测单块耗时：块耗时小于约 0.5 秒就不要进程并行（本机两次实测加速比 0.15x 与 0.09x）。
6. 上线前压测拿到 p50/p99 与吞吐，并把「每日标记率、命中率、关键特征分布、p99 延迟」纳入监控。

### 踩坑记录

```text
坑 1：joblib.load 加载了版本不匹配的模型，结果照常返回但数值飘了
结论：以为会报错或直接崩溃，结果服务正常运行、指标悄悄变差。
原因：sklearn 只给 InconsistentVersionWarning（UserWarning），而且每个估计器一条，
      默认日志级别下很容易被淹没；1.9.1 里估计器还没有 __sklearn_version__ 属性可查。
解法：自建元数据 sidecar 并在 joblib.load 之前硬校验 sklearn 版本（本机实测校验会拦下
      「工件 0.0.0 != 当前 1.9.1」）；用 warnings.simplefilter("error",
      InconsistentVersionWarning) 把警告升级成异常作为第二道防线。

坑 2：线上把 DataFrame 换成 ndarray 传进 predict，列错位但没报错
结论：以为只要列数对就行，模型不会在意列名。
原因：ColumnTransformer 按字符串选列时传 ndarray 会抛
      ValueError: Specifying the columns using strings is only supported for dataframes；
      但如果列选择用的是整数下标，传 ndarray 不报错，列顺序一变结果就是错的。
解法：服务入口显式按列名构造 DataFrame（本机 validate() 的做法）；元数据里存
      feature_names_in 作为契约；缺列时本机实测报 ValueError columns are missing: {'income'}，
      把它转成 400 并保留字段名，便于上游定位。

坑 3：以为进程并行一定更快，结果离线作业慢了 11 倍
结论：看到分块就加 Parallel，跑完发现比串行还慢。
原因：本机 30 万行、简单管道串行只要 0.14s，4 进程并行要 1.59s（加速比 0.09x）——
      进程启动 + DataFrame 序列化的固定开销远大于计算；另一个例子是 8 块并行 0.15x，
      因为随机森林自身 n_jobs=-1 已经在用多核，嵌套并行互相抢核。
解法：并行前先测单块耗时；块耗时小于几毫秒到几百毫秒的作业不要进程并行；已被 n_jobs
      并行的估计器不要再套一层 Parallel；真要扩展就在数据层按分区并行。

坑 4：skl2onnx 导出成功，onnxruntime 加载后推理直接报 NOT_IMPLEMENTED
结论：以为导出成功就代表 ONNX 链路可用，CI 里只校验了文件生成。
原因：skl2onnx 1.20.0 生成了含 Imputer 节点的图，onnxruntime 1.31.0 没有该算子的实现：
      [ONNXRuntimeError] : 9 : NOT_IMPLEMENTED : Could not find an implementation for Imputer(1)。
解法：CI 里必须跑「导出 + 用同一批样本对拍」；缺失值填充挪到导出前完成，或只导出不含
      Imputer 的数值管道（本机纯数值随机森林对拍差异 < 1e-5，可放心用）。

坑 5：单条推理接 n_jobs=-1 的模型，p99 延迟抖动到几百毫秒
结论：以为模型太小，延迟高是网络问题。
原因：n_jobs=-1 的估计器每次 predict 都会尝试并行（起线程池/进程池），1 行数据的计算量
      远小于调度开销。本机实测单条调用 47 ms、批量均摊 2.85 us；线上服务的首请求 16 ms
      与稳态 4 ms 也是同一回事（懒加载与预热）。
解法：单条/小 batch 路径把 n_jobs 设为 1，并做 micro-batch（50~1000 行）攒批；服务启动后
      预热几条请求；SLO 按 p99 定（本机 p99 6.09 ms，max 180 ms）。

坑 6：assume_finite=True 加上脏数据，模型静默算出垃圾
结论：为了 30% 的性能收益，线上把 assume_finite 打开了，之后指标莫名变差。
原因：assume_finite=True 会跳过输入里的 NaN/Inf 检查，脏数据不会报错，会一路算到底并
      产出无意义的结果（本机实测能快约 31%）。
解法：只在数据管道已保证无缺失/无穷值时开启，并在监控里加「关键特征缺失率」指标；
      更稳的做法是让缺失值在 Pipeline 内被显式填充（本机场景一里 2957 行缺失就是这样处理的）。

坑 7：模型文件被覆盖后无法复盘，只能全部重训
结论：以为模型文件只是个二进制，丢了重训就行。
原因：没有版本信息就无法回答「线上这批预测是哪版模型、用哪份数据、什么阈值算的」；
      重训还会因为数据快照不同而得到不同结果。
解法：用元数据 sidecar 记录 sklearn/joblib/numpy 版本、artifact 与输出的 sha256、训练行数、
      特征名、阈值、git commit、data_fingerprint（本机实测的完整字段见本章示例）；制品库
      里按 model_name + version 存目录，回滚就是切路径重启。
```
