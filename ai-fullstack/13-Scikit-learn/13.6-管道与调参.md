## 概述

`Pipeline` 把「预处理 + 模型」封装成一个 estimator：`fit` 时按顺序对每一折的训练数据做 `fit_transform`，`predict` 时只做 `transform`——这正是避免数据泄漏的结构性保证。`ColumnTransformer` 负责按列分流不同类型的数据（数值列走填充+缩放、类别列走填充+One-Hot），`FeatureUnion` 负责在同一份输入上并行跑多条特征流水线。调参侧，`GridSearchCV` 适合小而离散的空间，`RandomizedSearchCV` 适合连续/高维空间，`HalvingGridSearchCV` 用逐轮增加资源的办法筛候选，`cross_validate` 嵌套在外面就是嵌套交叉验证。

```text
本篇主线：
1. Pipeline —— 命名步骤、切片复用、set_params 双下划线、get_feature_names_out、memory 缓存
2. ColumnTransformer —— 按名/按类型选列、remainder、verbose_feature_names_out、pandas 输出
3. FeatureUnion / make_union —— 同一输入并行多路特征（PCA + SelectKBest），与 ColumnTransformer 的分工
4. Pipeline + CV —— 预处理只在训练折上 fit；memory 缓存中间变换
5. GridSearchCV —— 网格写法、param 键名规则、refit、cv_results_ 解读、多指标与 make_scorer
6. Randomized / Halving —— 分布采样、n_iter 与耗时权衡、Halving 的资源轮次与 experimental 导入
7. 嵌套 CV 与预算 —— best_score_ 的乐观偏差、两阶段（随机定位 + 网格细化）调参方案
```

## Pipeline 把预处理与模型绑成一个对象

步骤名用 `(名字, 估计器)` 二元组给出，或直接用 `make_pipeline` 自动按类名小写生成。`named_steps` 按名取步骤，`pipe[名字]` 也可以，`pipe[:-1]` 切片拿到「除最后一步外的全部」（常用来单独复用预处理器）。所有参数用双下划线串联访问：`pre__num__scaler__with_mean`。

```python
from sklearn.pipeline import Pipeline
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LogisticRegression

num_pipe = Pipeline([("imputer", SimpleImputer(strategy="median")),
                     ("scaler", StandardScaler())])
cat_pipe = Pipeline([("imputer", SimpleImputer(strategy="constant", fill_value="unknown")),
                     ("onehot", OneHotEncoder(handle_unknown="ignore", sparse_output=False))])
pre = ColumnTransformer([("num", num_pipe, ["age", "income", "visits_30d"]),
                         ("cat", cat_pipe, ["city", "channel"])],
                        remainder="drop", verbose_feature_names_out=False)
clf = Pipeline([("pre", pre), ("model", LogisticRegression(max_iter=1000))])
clf.fit(Xtr, ytr)                    # 一步完成填充、缩放、编码、训练
```

`set_params` 对不存在的参数会立刻抛 `ValueError`（本机实测信息是 `Invalid parameter 'Cx' for estimator LogisticRegression(...)`），这是好事——调参脚本写错键名会当场失败，而不是静默用默认值跑完。

`get_feature_names_out()` 是排查「第 37 列是什么特征」的唯一可靠手段；再用 `set_output(transform="pandas")` 让变换结果直接带列名的 DataFrame：

```python
Z = clf[:-1].transform(Xte.head(3))                      # ndarray
set_config(transform_output="pandas")                     # 全局
Zdf = clf[:-1].transform(Xte.head(2))                     # DataFrame
clf.set_output(transform="pandas")                        # 单估计器
```

本机实测这里有一个必踩的坑：OneHotEncoder 默认 `sparse_output=True`，与 pandas 输出不兼容。

```text

单估计器 .set_output(transform='pandas') 类型: DataFrame
```

```text
要点：
- 步骤名就是参数前缀，命名要稳（改名等于破坏所有调参配置与已保存模型的参数路径）
- clf[:-1] 是复用预处理器的标准写法；clf[:] 与 clf 等价
- get_feature_names_out() 排查特征位置；set_output(transform="pandas") 换回 DataFrame
- OneHotEncoder 要 pandas 输出必须 sparse_output=False（默认 True 会直接 ValueError）
- set_params 传错参数名会报错，调参脚本里不要用 try/except 吞掉它
```

## ColumnTransformer 处理混合类型数据

三类选列方式：显式列名列表、`make_column_selector(dtype_include="number")` 按类型自动选、或者不写（`remainder` 决定未处理列怎么走：`'drop'` 默认丢弃、`'passthrough'` 原样保留、也可以传一个估计器）。`verbose_feature_names_out=True`（默认）会给输出特征加上 `步骤名__` 前缀，设为 False 则保留原始列名——后者更干净，但列名冲突时会报错。

```python
from sklearn.compose import make_column_selector
ct_auto = ColumnTransformer([
    ("num", StandardScaler(), make_column_selector(dtype_include="number")),
    ("cat", OneHotEncoder(handle_unknown="ignore"), make_column_selector(dtype_include=object)),
], remainder="passthrough")
```

```text
make_column_selector 自动选列后形状: (400, 11)
verbose_feature_names_out=True（默认）的特征名前 6 个: ['num__age', 'num__income', 'num__visits_30d', 'cat__city_beijing', 'cat__city_chengdu', 'cat__city_shanghai']
verbose_feature_names_out=False 时: ['age', 'income', 'visits_30d', 'city_beijing', 'city_chengdu', 'city_shanghai']
remainder 选项：'drop'（默认）/ 'passthrough'（原样保留未处理的列）/ 一个估计器
  remainder='passthrough' 输出列数: 5 （1 个标准化列 + 4 个原样列）
  columns 属性: {'num': slice(0, 1, None), 'remainder': slice(1, 5, None)}
```

`output_indices_`（本机属性名是 `columns` 打印出来的字典）能定位每个子变换器占据的输出列区间，调试「特征列对不上」时非常有用。注意 `remainder="passthrough"` 会让未处理的列**不经过任何填充**直接进模型——数值列里有 NaN 时下游模型可能直接报错，所以要么显式处理所有列，要么确认模型自己能吃 NaN（`HistGradientBoosting` 可以）。

| 需求 | 写法 | 注意点 |
| --- | --- | --- |
| 数值列填充+缩放 | `Pipeline([SimpleImputer, StandardScaler])` | 缺失比例高时考虑加缺失指示列 |
| 类别列 One-Hot | `OneHotEncoder(handle_unknown="ignore")` | 高基数类别改用 TargetEncoder 或哈希 |
| 按类型自动选列 | `make_column_selector(dtype_include=...)` | object 列混入数字字符串时要先转换 |
| 保留未处理列 | `remainder="passthrough"` | 未处理列不会做缺失填充 |
| 输出带列名 | `set_output(transform="pandas")` | OneHot 要设 `sparse_output=False` |
| 输出特征名不带前缀 | `verbose_feature_names_out=False` | 列名冲突会报错 |

```text
要点：
- 混合类型表格的默认骨架就是 ColumnTransformer([数值 Pipeline, 类别 Pipeline])
- remainder="passthrough" 不会填充缺失值，下游不支持的模型会报错
- 按类型选列时注意 object 列里混着数字字符串的脏数据
- 输出列名用 get_feature_names_out() 核对，调参键名也要用真实的步骤名拼出来
- verbose_feature_names_out=False 让特征名更可读，但重名列会冲突
```

## 特征联合 FeatureUnion 与列变换的取舍

`FeatureUnion`/`make_union` 把同一份输入并行喂给多条流水线，再横向拼接输出——典型用法是「PCA 的成分 + 原始特征的 SelectKBest 子集」同时给模型。`Pipeline` 是串行（上一步输出喂下一步），`FeatureUnion` 是并行（同输入多路输出拼接），两者概念完全不同。

```python
from sklearn.pipeline import make_union, FeatureUnion
from sklearn.decomposition import PCA
from sklearn.feature_selection import SelectKBest, f_regression

fu = make_union(PCA(n_components=2), SelectKBest(f_regression, k=2))
Xu = fu.fit_transform(Xnum, y)          # PCA 2 列 + SelectKBest 2 列 = 4 列
```

```text
make_union(PCA(2), SelectKBest(2)) 输出特征数: 4 (2+2)
FeatureUnion 是并行（同一输入多条流水线），Pipeline 是串行（上一步输出喂下一步）
1.9.1 中 FeatureUnion 仍可用，但与 ColumnTransformer 功能重叠，混合类型表格优先 ColumnTransformer
```

本机验证：1.9.1 里 `sklearn.pipeline.FeatureUnion` 依然存在且可用，但它与 `ColumnTransformer` 的功能重叠（都是「分路处理再拼接」），差别在于 `ColumnTransformer` 按列分流、`FeatureUnion` 按变换分流。混合类型表格一律用 `ColumnTransformer`；只有「同一批特征要同时走降维和选择」时才用 `FeatureUnion`。

```python
# 组合用法：先用 ColumnTransformer 把类别列编码好，再对编码后的特征做多路变换
from sklearn.pipeline import FeatureUnion
combined = Pipeline([
    ("pre", ColumnTransformer([...])),
    ("feat", FeatureUnion([("pca", PCA(n_components=5)),
                           ("sel", SelectKBest(f_classif, k=10))])),
    ("clf", LogisticRegression(max_iter=1000)),
])
```

| 组合器 | 分流依据 | 输入 | 输出 | 典型用法 |
| --- | --- | --- | --- | --- |
| Pipeline | 顺序 | 上一步的输出 | 最后一步的结果 | 填充 -> 缩放 -> 模型 |
| ColumnTransformer | 列名/列类型 | 同一个 DataFrame | 各子变换输出横向拼接 | 混合类型表格预处理 |
| FeatureUnion | 变换器 | 同一批特征 | 各变换输出横向拼接 | 降维 + 特征选择同时用 |

```text
要点：
- 分路处理用 ColumnTransformer（按列），同一批特征多路变换用 FeatureUnion（按变换）
- FeatureUnion 的输出列数 = 各子变换输出列数之和（本机实测 2+2=4）
- 两者可以嵌套：ColumnTransformer 编码后再 FeatureUnion 抽取
- 拼接后的列名要靠 get_feature_names_out() 确认，别猜列顺序
- 1.9.1 里 FeatureUnion 未废弃，但新代码优先考虑 ColumnTransformer + 明确的步骤名
```

## Pipeline 与交叉验证及缓存

Pipeline 与 CV 配合的核心价值：预处理只在每折的训练部分 `fit`，验证部分只 `transform`。本机对拍（CV 外先 fit 标准化器 vs 全放 Pipeline）：

```python
sc_bad = StandardScaler().fit(df[NUM].fillna(0))
leaky = cross_val_score(LogisticRegression(max_iter=1000), sc_bad.transform(df[NUM].fillna(0)), y, cv=5).mean()
ok = cross_val_score(Pipeline([("s", StandardScaler()), ("m", LogisticRegression(max_iter=1000))]),
                     df[NUM].fillna(0), y, cv=5).mean()
```

```text
在 CV 外先 fit 标准化器: 0.8825
全部放进 Pipeline 再 CV  : 0.885
备注：StandardScaler 的泄漏影响通常很小（本例为真实差值），特征选择/目标编码/过采样才会显著虚高
```

注意这里泄漏版反而略低——因为全量 fit 的均值/方差与验证折的分布有微小差异，方向不固定；重点是**标准化造成的偏差很小**，把精力放在真正致命的环节（特征选择、目标编码、过采样）上。

`Pipeline(memory=...)` 会把每个中间步骤 `fit_transform` 的结果按参数哈希缓存到磁盘，重复实验（例如只改最后的模型参数）可以跳过昂贵的特征工程：

```python
from joblib import Memory
import tempfile
cache = tempfile.mkdtemp(prefix="skcache_")
cached = Pipeline([("s", StandardScaler()), ("p", PolynomialFeatures(2)), ("m", Ridge())],
                  memory=Memory(location=cache, verbose=0))
cached.fit(Xnum, y); cached.fit(Xnum, y)     # 第二次命中缓存
```

```text
首次 fit 0.0095s, 第二次（命中缓存）0.0043s
缓存目录内容: ['.gitignore', 'joblib'] （joblib 以参数哈希为目录名）
memory 只对无副作用的 fit/transform 安全；随机变换（如随机投影）缓存会串味，别用
```

```text
要点：
- Pipeline 的价值不在「少写代码」，而在保证 CV 每一折的预处理只用训练折的信息
- 标准化/缩放造成的泄漏影响很小（本机 0.8825 vs 0.885），特征选择类才致命
- memory 缓存按「步骤参数哈希」复用，调参时改模型参数可跳过重复的特征工程
- 缓存目录要纳入清理策略（仓库里放 .gitignore，容器里挂空目录）
- 带随机性的变换（RandomProjection、随机过采样）不要开 memory，缓存会串味
```

## GridSearchCV 网格搜索

`param_grid` 可以是一个 dict，也可以是 dict 的列表（列表之间取并集，用于「互斥参数组」，例如 l1 与 l2 各自的参数）。键名规则就是 `步骤名__参数名`，嵌套再往下加 `__`。`refit=True`（默认）会用最佳参数在**全部训练数据**上重新拟合，之后 `best_estimator_` 就是可直接预测的完整 Pipeline。

```python
param_grid = [
    {"clf__kernel": ["rbf"], "clf__C": [0.1, 1.0, 10.0], "clf__gamma": ["scale", 0.01],
     "pre__num__sc": ["passthrough", StandardScaler()]},
    {"clf__kernel": ["linear"], "clf__C": [0.1, 1.0, 10.0]},
]
gs = GridSearchCV(pipe, param_grid, cv=StratifiedKFold(5, shuffle=True, random_state=0),
                  scoring="f1", n_jobs=-1, refit=True, return_train_score=True)
gs.fit(Xtr, ytr)
```

```text
候选组合数 15, 拟合次数 90（5 折 + refit 1 次）
耗时 5.04s（n_jobs=-1）
best_params_: {'clf__C': 10.0, 'clf__gamma': 'scale', 'clf__kernel': 'rbf', 'pre__num__sc': StandardScaler()}
best_score_ (CV 上的 F1): 0.9957
best_estimator_ 类型: Pipeline | 在留出测试集上的 F1: 0.984 （注意 score 用的是准确率，因为 Pipeline 最后一步是分类器）
refit 后可直接 gs.predict: [1 1 1]  gs.decision_function 也可用: [3.613 2.251 3.874]
```

注意 `best_estimator_` 是完整的 Pipeline（含 `pre` 与 `clf` 两步），所以能直接吃原始 DataFrame——这是「把预处理写进 Pipeline」最实在的收益。另外 `gs.score(...)` 用的是 Pipeline 最后一步的 `score`（分类器就是准确率），与 `scoring="f1"` 无关，别混。`cv_results_` 是诊断过拟合的主战场：

```text
 rank_test_score  mean_test_score  std_test_score  mean_train_score param_clf__kernel  param_clf__C param_clf__gamma
               1         0.995724        0.003491          0.999641               rbf          10.0            scale
               2         0.984417        0.008206          0.992159               rbf           1.0            scale
               3         0.981677        0.005392          0.983739               rbf          10.0             0.01
               4         0.980240        0.008032          0.983658            linear           1.0              NaN
               5         0.979976        0.009513          0.986068            linear          10.0              NaN
训练分数远高于测试分数的候选项就是过拟合区间（看 mean_train_score 与 mean_test_score 之差）
```

评分器可以是字符串、字符串列表/字典（配合 `refit` 指定用哪个指标选模型），或 `make_scorer` 包出来的自定义函数：

```python
gs2 = GridSearchCV(..., scoring={"f1": "f1", "auc": "roc_auc", "neg_rmse": "neg_root_mean_squared_error"},
                   refit="f1", n_jobs=-1)
```

```text
scorer 名字共 58 个，常用: ['accuracy', 'adjusted_mutual_info_score', 'adjusted_rand_score', 'average_precision', 'balanced_accuracy', 'completeness_score', 'd2_absolute_error_score', 'd2_brier_score']
多指标时 best_index_ 指向 refit 的那个指标: 1  best_score_: 0.976
各指标最优值: {'mean_test_f1': 0.976, 'mean_test_auc': 0.9702, 'mean_test_neg_rmse': -0.2105}
自定义 scorer 也可传： make_scorer(fbeta_score, response_method='predict', beta=2)
```

```text
要点：
- 参数键名规则是「步骤名__参数名」，多层就是再串一层，写错会立刻 ValueError
- param_grid 用 dict 列表可以表达互斥参数组（本机 15 个组合里 l1/l2 各自带参数）
- refit=True 后 best_estimator_ 是完整 Pipeline，可直接对原始 DataFrame 预测
- gs.score() 用的是最后一步估计器的 score，不是 scoring= 指定的指标
- 用 cv_results_ 对比 mean_train_score 与 mean_test_score，差值大的区域就是过拟合区
```

## RandomizedSearchCV 与 Halving 搜索

连续参数的网格搜索很低效（取 3 个点等于人为砍掉了 99% 的空间）。`RandomizedSearchCV` 直接吃 scipy 分布（`loguniform`、`randint`、`uniform`），在同样的采样预算下覆盖更广：

```python
from scipy.stats import loguniform, randint
dist = {"clf__C": loguniform(1e-3, 1e2), "clf__gamma": loguniform(1e-4, 1e0), "clf__kernel": ["rbf"]}
rs = RandomizedSearchCV(pipe, dist, n_iter=12, cv=cv, scoring="f1", n_jobs=-1, random_state=0)
```

```text
[随机搜索] n_iter=12 耗时 0.69s, 最好 F1=0.9957
best_params_: {'clf__C': 7.7765, 'clf__gamma': 0.302, 'clf__kernel': 'rbf'}

scipy 分布直接可用 loguniform/randint/uniform；也可传列表（等价于网格的随机子集）
```

`HalvingGridSearchCV` 的思路是「先用少量样本把所有候选跑一遍，每轮淘汰一半，资源翻倍」。本机实测两个关键事实：一是 1.9.1 里它**必须显式导入 experimental 开关**，否则直接 `ImportError`；二是它未必更快。

```python
from sklearn.model_selection import HalvingGridSearchCV
hgs = HalvingGridSearchCV(pipe, param_grid, cv=cv, factor=2, scoring="f1",
                          random_state=0, n_jobs=-1, min_resources="exhaust")
```

在应用场景二那份更大的网格上（73 个候选、随机森林、4000 样本），Halving 耗时反而比完整网格更长：


原因是这份数据规模不大、单次训练很快，Halving 的多轮开销（每轮都要重新切 CV、每轮样本数上限到 2976）盖过了省下来的部分。**Halving 的收益出现在「候选多 + 单次训练慢（大数据/深模型）」时**，小数据上直接用随机搜索更快。

本机运行这些搜索器时还反复出现一条真实警告，说明 `n_jobs` 与 scikit-learn 的并行配置传递有关：

```text
UserWarning: `sklearn.utils.parallel.delayed` should be used with `sklearn.utils.parallel.Parallel`
to make it possible to propagate the scikit-learn configuration of the current thread to the joblib workers.
```

它来自内部用 joblib 起子进程时没有走 `sklearn.utils.parallel` 的那条路径。对结果没有影响，但如果你在 `set_config(assume_finite=True)` 或 `transform_output="pandas"` 之后跑 `n_jobs>1` 的搜索，要注意这些全局配置**可能不会传递到子进程**——需要显式在 `Pipeline` 上用 `.set_output()` 而不是依赖全局 `set_config`。

| 搜索方式 | 适合场景 | 参数预算 | 主要参数 | 本机实测（同数据） |
| --- | --- | --- | --- | --- |
| GridSearchCV | 小离散空间、要完整网格证据 | 组合数 x 折数 | `param_grid` `refit` | 36 组合 69.65s |
| RandomizedSearchCV | 连续/高维空间 | `n_iter` x 折数 | `n_iter` `random_state` | 20 次采样 29.55s |
| HalvingGridSearchCV | 候选多、单次训练慢 | 逐轮减半 | `factor` `min_resources` `resource` | 73 候选 82.19s |

```text
要点：
- 连续参数用分布（loguniform/randint），固定 n_iter 比较不同空间才公平
- n_iter 的经验起点是参数量级的 10~20 倍，然后按剩余预算加
- HalvingGridSearchCV 在 1.9.1 仍需 from sklearn.experimental import enable_halving_search_cv
- Halving 未必更快：小数据/快模型上多轮开销大于收益（本机 82.19s vs 网格 69.65s）
- Halving 用子集训练，best_score_ 与完整网格不可直接比较，最终要用同 CV 复核
```

## 嵌套交叉验证与参数预算

`best_score_` 是「在同一批数据上又搜参又评分」的结果，必然偏乐观。要给出不偏的性能，要么留独立测试集，要么把 `GridSearchCV` 整个塞进外层 `cross_val_score`（嵌套 CV：外层评估、内层调参）。本机实测：

```python
inner = StratifiedKFold(3, shuffle=True, random_state=0)
outer = StratifiedKFold(5, shuffle=True, random_state=0)
nested = cross_val_score(GridSearchCV(sub, grid, cv=inner, n_jobs=-1), Xnum2, y,
                         cv=outer, scoring="f1", n_jobs=-1)
```

```text
嵌套 CV（外层 5 折，每折内部再 3 折调参）: [0.9677 0.973  0.9947 0.9677 0.9892] 均值 0.9785
同一外折上直接调参再评分（会偏乐观）      : [0.9681 0.973  0.9947 0.9787 0.9892] 均值 0.9807
差值 0.0023：用 best_score_ 当最终性能指标总会偏乐观，汇报性能要用嵌套 CV 或独立测试集
```

在这份小数据上差值只有 0.0023（因为空间只有 4 个候选），候选越多、空间越大，乐观偏差越明显。所以调参预算要按「候选数 x 折数」先算清楚：

```text
网格组合数: 24  -> 拟合次数: 120 （5 折）
RandomizedSearchCV(n_iter=12) 只需 60 次拟合，能用上连续分布，通常更快找到好区域
经验做法：先用 n_iter=20~50 随机搜索定位量级，再在附近做小网格细化
```

常用模型在调参中的速度对照（同一数据、5 折 CV、n_jobs=-1）：

```text
LogisticRegression     F1=0.9819 耗时=0.067s
SVC(rbf)               F1=0.9893 耗时=0.057s
RandomForest(200)      F1=0.9873 耗时=0.629s
HistGradientBoosting   F1=0.9850 耗时=0.221s
调参预算有限时优先换更快的模型/降低 CV 折数，而不是压缩搜索空间到看不出差异
```

```text
要点：
- best_score_ 只用于选模型，对外汇报用嵌套 CV 或独立测试集
- 候选数越多，乐观偏差越大（本机 4 个候选时只差 0.0023）
- 预算先算「候选数 x 折数」，再决定用网格还是随机
- 两阶段策略：随机搜索定位量级 + 网格细化（见场景二），比一次性大网格省一半以上时间
- 调参前先看模型速度，慢模型优先降折数或换 HistGradientBoosting
```

### 场景二：调参预算分配（随机定位 + 网格细化 + 分组 CV）

业务需求：给定 4 小时算力预算，把随机森林的 AUC 调到最好；同时数据是「每个用户 10 条记录」的分组结构，必须按用户整体切分。

```python
# tune_rf.py —— 两阶段调参 + Halving 对比 + 分组 CV
from scipy.stats import loguniform, randint
from sklearn.experimental import enable_halving_search_cv   # noqa: F401
from sklearn.model_selection import (RandomizedSearchCV, GridSearchCV, HalvingGridSearchCV,
                                     GroupKFold, StratifiedKFold)

# 阶段一：随机搜索定位量级（连续参数用分布）
space = {"clf__n_estimators": randint(100, 500),
         "clf__max_depth": [None, 4, 8, 16],
         "clf__min_samples_leaf": randint(1, 20),
         "clf__max_features": loguniform(0.1, 1.0)}
rs = RandomizedSearchCV(pipe, space, n_iter=20, cv=StratifiedKFold(5, shuffle=True, random_state=0),
                        scoring="roc_auc", n_jobs=-1, random_state=0).fit(Xtr, ytr)

# 阶段二：在 best_params_ 附近做小网格（离散化 + 上下浮动）
leaf = int(rs.best_params_["clf__min_samples_leaf"])
mf = float(rs.best_params_["clf__max_features"])
grid = {"clf__n_estimators": [300, 400], "clf__max_depth": [12, None],
        "clf__min_samples_leaf": [leaf - 2, leaf, leaf + 2],
        "clf__max_features": [round(mf - 0.15, 2), round(mf, 2), round(min(1.0, mf + 0.15), 2)]}
gs = GridSearchCV(pipe, grid, cv=StratifiedKFold(5, shuffle=True, random_state=0),
                  scoring="roc_auc", n_jobs=-1, refit=True).fit(Xtr, ytr)

# 分组数据必须整组切分：groups 传给 fit，不是构造参数
gcv = GridSearchCV(pipe, {"clf__n_estimators": [200, 400], "clf__max_depth": [None, 8]},
                   cv=GroupKFold(3), scoring="roc_auc", n_jobs=-1).fit(Xtr, ytr, groups=groups[:len(Xtr)])
```

```text
- 单条预测的固定开销远大于批量均摊（66ms vs 0.07ms/条），服务化必须攒批
```

## 最佳实践与踩坑记录

### 最佳实践

1. 任何进模型的预处理都写进 Pipeline；上线只交付「一个 joblib 文件 + 输入列名清单」。
2. 混合类型表格用「ColumnTransformer(数值 Pipeline, 类别 Pipeline)」作为固定骨架，缺失与未知类别都在里面处理。
3. 参数键名按 `步骤名__参数名` 生成，别手抄；步骤名一旦定下就不要改（改名会破坏所有历史配置与已保存模型）。
4. 调参先算预算（候选数 x 折数 x 单次耗时），两阶段走：随机搜索定位 + 网格细化（保留上阶段最优）。
5. 分组/时序数据在 `fit` 时传 `groups`，用 `GroupKFold`/`TimeSeriesSplit`；调参的 CV 与最终评估的 CV 必须一致。
6. 最终性能用嵌套 CV 或独立测试集给出；把 `best_params_`、`best_score_`、`cv_results_` 摘要一并归档。

### 踩坑记录

```text
坑 1：OneHotEncoder 开着默认稀疏输出，set_output(transform="pandas") 直接报错
结论：以为 pandas 输出功能有 bug。
原因：OneHotEncoder 默认 sparse_output=True，pandas 输出不支持稀疏矩阵。
      本机实测 ValueError: Pandas output does not support sparse data.
解法：OneHotEncoder(sparse_output=False)；或对该步骤单独 set_output(transform="default")。
      注意关掉稀疏后高基数类别列会显著膨胀内存，基数大于约 100 时改用哈希或目标编码。

坑 2：调参脚本里的参数键名写错，静默用默认值跑了一整天
结论：以为搜索空间生效了，结果 best_params_ 里根本没有那个参数。
原因：键名少写或写错一层（如 pre__num__scaler__with_mean 写成 pre__scaler__with_mean）
      会抛 ValueError；但如果参数名本身合法、只是层级写错指向了不存在的步骤，很容易被
      try/except 或 verbose=0 掩盖。
解法：调参前先跑 gs.get_params().keys() 与 param_grid 做集合比对；本机实测 set_params
      传非法名会立刻抛 ValueError: Invalid parameter 'Cx' for estimator ...，别吞掉它。

坑 3：两阶段调参里「细化网格」把结果调差了
结论：以为细化总是更精确，看到 0.6207 < 0.6378 以为代码有 bug。
原因：第一阶段的最优 max_depth=4 不在细化网格里（只放了 12 与 None），细化把搜索引向了
      过拟合区域（max_features=1.0 + 深树）。本机实测细化后 AUC 反而降了 0.0171。
解法：把上一阶段 best_params_ 原样加入细化网格作为候选之一；连续参数先离散化成「最优值
      上下各浮 15%」的三个点；两阶段用同一套 CV 与同一评分标准比较。

坑 4：以为 HalvingGridSearchCV 一定更快
结论：候选多就该用 Halving，结果比完整网格还慢。
原因：Halving 的每一轮都要重新切 CV 并按资源上限采样；本机这份 4000 样本、随机森林的
      数据单次训练很快，多轮开销盖过收益（82.19s vs 网格 69.65s）。
解法：先测一次单模型训练耗时；单次训练远小于 CV 切分开销时直接用 RandomizedSearchCV。
      另外 1.9.1 里必须先 from sklearn.experimental import enable_halving_search_cv，否则
      ImportError。

坑 5：分组数据没传 groups，CV 分数虚高
结论：以为 CV AUC 0.62 就是模型的真实水平。
原因：每个用户 10 条记录，随机切分让同一个用户的其他记录出现在训练集里，模型在「认人」。
      本机实测 GroupKFold 只有 0.5996，比随机切分低 0.0211。
解法：GridSearchCV/RandomizedSearchCV 的 groups 传给 fit（不是构造参数），cv 用 GroupKFold；
      同时检查分组字段是否真的代表独立个体（同设备、同 IP 的样本也要考虑分组）。

坑 6：Pipeline 的 memory 缓存把随机变换的结果缓存住了
结论：以为缓存只是加速，不会有副作用。
原因：memory 按「步骤参数 + 输入数据哈希」缓存 fit_transform 结果，带随机性的变换
      （RandomProjection、随机过采样、未固定种子的自定义变换）一旦被缓存，后续实验拿到的
      是同一份缓存而不是新随机结果，调参结论不可信。
解法：随机性变换所在步骤不要放进带 memory 的 Pipeline；必须缓存时先固定 random_state
      并确认「同参数应得同结果」，否则缓存策略本身就是错的。

坑 7：pipeline 步骤改名后，线上加载的老模型 set_params 全部失效
结论：以为改名只是可读性问题。
原因：保存的模型里步骤名是结构的一部分，历史调参配置、监控脚本、`set_params` 路径、
      `named_steps["pre"]` 之类的取用代码全都依赖它。
解法：步骤名当成 API 契约管理（本机实践：用 pre、clf、num、cat 这类稳定短名）；改名要走
      版本升级流程，并同步更新所有引用；发布前跑一次「加载老模型 + 按名取值」的回归测试。
```
