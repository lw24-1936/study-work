## 概述

Selenium 是浏览器自动化的开源工具集，核心是 **WebDriver**：一套由 W3C 标准化的、与语言无关的协议，用来控制真实浏览器。写 Selenium 脚本时最容易出错的地方不在 API，而在「三件东西凑不齐」——语言绑定包（`pip install selenium`）、浏览器驱动（chromedriver / geckodriver）、浏览器本体本身，三者版本必须对得上，缺一样都启动不了会话。本篇解决的就是这三者的安装、版本匹配与第一个可运行脚本。

```text
本篇主线：
1. 组成 —— Selenium IDE / WebDriver / Grid 三件套；语言绑定与驱动是两回事
2. 架构 —— 脚本 -> 语言绑定 -> driver 进程 -> 浏览器，中间走 HTTP + JSON（W3C WebDriver 协议）
3. 驱动管理 —— Selenium Manager（Selenium 4.6 起内置的 Rust CLI），自动探测/下载 driver 与浏览器
4. 版本匹配 —— 浏览器主版本与 driver 主版本必须一致；Chrome 自动升级是最大变量
5. 环境搭建 —— 独立 venv + pip 清华镜像；无 Chrome 时用 binary_location 指向已有浏览器二进制
6. 第一个脚本 —— 八步结构：建会话 / 导航 / 取浏览器信息 / 设等待 / 找元素 / 操作元素 / 读元素信息 / 退出
7. 会话配置 —— Options 与 Capabilities：headless、--no-sandbox、page_load_strategy、timeouts
```

本机实测环境：Ubuntu 24.04、Python 3.14.7、**selenium 4.51.0**、chromedriver 151.0.7922.138、Chrome for Testing 151.0.7922.34（复用 Playwright 缓存里的 Chromium 二进制）。下文所有 `text` 块都是本机真实运行输出，失败与报错也原样保留。

## Selenium 组成

Selenium 项目由几个彼此独立、经常被混为一谈的组件构成。名字里的 "Selenium" 在不同上下文指的其实是不同的东西，这是新手第一个概念坑。

| 组件 | 是什么 | 运行形态 | 本篇章是否使用 |
|---|---|---|---|
| Selenium IDE | 浏览器扩展，录制鼠标键盘操作并回放 | 浏览器插件，图形界面 | 不使用 |
| Selenium WebDriver | W3C 标准协议 + 各语言绑定库 | Python/Java 等库进程 + driver 进程 | 全篇核心 |
| Selenium Grid | 把会话分发到多台机器的服务 | 中心 + 节点服务 | 见 18.7 |
| Selenium Manager | 官方驱动管理器，Rust 实现的 CLI | 随绑定包一起安装，被绑定自动调用 | 本篇与全篇 |

真正干活的只有 WebDriver。它下面又分成三层，装错任何一层都会报错：

| 层 | 安装方式 | 出问题时典型现象 |
|---|---|---|
| 语言绑定（Python 包） | `pip install selenium` | `ModuleNotFoundError: No module named 'selenium'` |
| 浏览器驱动（driver 可执行文件） | Selenium Manager 自动下载，或手动放进 PATH | `session not created: This version of ChromeDriver only supports Chrome version 113` |
| 浏览器本体 | 系统包管理器 / 官网安装（Chrome、Firefox、Edge） | `Unable to locate or obtain driver for chrome` 或路径类异常 |

## WebDriver 架构与驱动管理

WebDriver 是 W3C 标准（<https://w3c.github.io/webdriver/>）：脚本不直接操作浏览器，而是把「点击某个坐标的元素」「读取某个元素的文本」这类命令序列化成 JSON，通过 HTTP 发给一个独立的 **driver 进程**，driver 再用浏览器厂商自己的自动化接口（Chrome DevTools Protocol 等）去执行。这个设计有两个直接后果：驱动是独立进程，所以可以跑在别的机器上（这就是 Selenium Grid 与远程 `webdriver.Remote` 的原理）；以及**协议是语言无关的**，Python、Java、JS 写出来的东西发的是同一套命令。

Selenium 4 全面走 W3C 协议，旧的 JSON Wire Protocol（Selenium 3 时代）已废弃，因此网上大量 Selenium 3 时代的「必须用 `DesiredCapabilities`」类文章已经过时，Selenium 4 用 `Options` 代替。

驱动从哪来由 **Selenium Manager** 决定，它的策略是：

| 场景 | 行为 |
|---|---|
| 浏览器与 driver 都能在 PATH/缓存里找到且版本匹配 | 直接用，不动网络 |
| driver 缺失或版本不匹配 | 联网查询并下载匹配的 driver 到 `~/.cache/selenium` |
| 浏览器也不存在（如 CI 镜像里没有 Chrome） | 连浏览器一起下载（Chrome for Testing） |
| 指定了 `binary_location` / `--browser-path` | 只按这个二进制的主版本找 driver，不下载浏览器 |

## 版本匹配与浏览器选择

版本匹配的规则不长，但违反它几乎必然启动失败。

| 浏览器 | driver | 匹配要求 | 常见陷阱 |
|---|---|---|---|
| Chrome / Chromium | chromedriver | **主版本号必须一致**（151 对 151；补丁号可不同） | Chrome 后台静默升级，driver 还是旧的 |
| Firefox | geckodriver | 宽松，不需要与 Firefox 同版本 | 发行版把 firefox 装成包装脚本而非真二进制 |
| Edge | msedgedriver | 主版本必须一致 | 同 Chrome |
| Safari | safaridriver | 随系统，无需下载 | 仅 macOS，需先 `safaridriver --enable` |

本机的真实情况值得单独说明，因为它是很多 Linux 容器镜像的常态：**没有 `google-chrome`，也没有 PATH 里的 `chromedriver`**，但有一个 snap 包装的 firefox 与 Playwright 缓存的 Chromium：

```bash
which google-chrome chromium chromium-browser chromedriver firefox
```

```text

```

```bash

head -3 /usr/bin/firefox
```

```text

if ! [ -x /snap/bin/firefox ]; then
    echo "Command '$0' requires the firefox snap to be installed." >&2
```


于是有两条可走的路，本篇实测结论如下：

| 方案 | 命令要点 | 本机实测结果 |
|---|---|---|
| 复用已有 Chromium 二进制 | `Options().binary_location = "/root/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome"` | 成功，匹配到 chromedriver 151.0.7922.138，浏览器版本 151.0.7922.34 |
| 让 Selenium Manager 全自动 | 不设 `binary_location` | 成功，自动下载 Chrome for Testing 155.0.8059.79 + chromedriver 155.0.8059.79，缓存命中后启动耗时 1.1 秒 |
| 用 snap Firefox | `webdriver.Firefox()` | **失败**：`InvalidArgumentException: binary is not a Firefox executable`（`/usr/bin/firefox` 是 sh 包装脚本，geckodriver 0.37.1 不认） |

零配置自动下载那条路的真实输出：


结论：本机用 Chrome 系（`binary_location` 指向 Playwright 缓存的 Chromium）最省事也最快；Firefox 需要把 `FirefoxOptions().binary_location` 指向 snap 里真实的 firefox 可执行文件（`/snap/firefox/current/usr/lib/firefox/firefox`）才可能成功，本条未在本机验证，需按实际安装路径确认。

## 第一个脚本

官方「第一个脚本」文档把一次会话拆成八步，这个骨架值得背下来，后面所有篇章都是它的展开。

```python
# first_script.py —— 本机可直接运行
from selenium import webdriver
from selenium.webdriver.chrome.options import Options
from selenium.webdriver.common.by import By

CHROME = "/root/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome"

opts = Options()
opts.binary_location = CHROME        # 指定浏览器二进制，避免 Selenium Manager 联网下载
opts.add_argument("--headless=new")  # 无头模式，CI 必备
opts.add_argument("--no-sandbox")    # 容器/root 下必须，否则 Chrome 起不来
opts.add_argument("--disable-dev-shm-usage")  # 容器 /dev/shm 太小导致崩溃时的对策
opts.add_argument("--window-size=1280,900")

driver = webdriver.Chrome(options=opts)   # 1. 创建会话（同时启动 driver 进程）
try:
    driver.get("http://127.0.0.1:8899/index.html")   # 2. 导航
    print("标题:", driver.title)                      # 3. 取浏览器信息
    driver.implicitly_wait(2)                        # 4. 设等待策略（18.3 详述）
    btn = driver.find_element(By.ID, "submit-btn")    # 5. 找元素
    print("按钮文本:", btn.text)                       # 7. 读元素信息
    print("按钮可见:", btn.is_displayed())
finally:
    driver.quit()                                     # 8. 结束会话（关 driver 进程 + 关浏览器）
```

## 会话配置 Options 与 Capabilities

启动会话时的参数分两层：**Options** 是给绑定库用的方便写法（`binary_location`、`add_argument`、`timeouts`），最终都会被序列化进 **Capabilities**（W3C 规定的会话请求体）发给 driver。用 `to_capabilities()` 可以看到真实发送的内容，这是排查「参数没生效」最快的手段。

```python
from selenium.webdriver.chrome.options import Options

opts = Options()
opts.binary_location = "/root/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome"
opts.add_argument("--headless=new")
opts.add_argument("--lang=zh-CN")
opts.page_load_strategy = "normal"                      # none / eager / normal
opts.timeouts = {"implicit": 5000, "pageLoad": 30000, "script": 30000}  # 单位毫秒
opts.set_capability("acceptInsecureCerts", True)        # 自签名证书的测试环境
print(opts.to_capabilities())
```

本机真实输出：

```text
capabilities 键: ['acceptInsecureCerts', 'browserName', 'goog:chromeOptions', 'pageLoadStrategy', 'timeouts']
goog:chromeOptions: {'excludeSwitches': ['enable-automation'], 'extensions': [], 'binary': '/root/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome', 'args': ['--headless=new', '--no-sandbox', '--disable-dev-shm-usage', '--window-size=1280,900', '--lang=zh-CN']}
timeouts 能力: {'implicit': 5000, 'pageLoad': 30000, 'script': 30000}
implicit 生效: 5.0
```

三个超时在 `driver.timeouts` 上也能读写，Python 绑定里单位是**秒**（capabilities 里是毫秒，注意换算）：

```python
print("implicit_wait:", driver.timeouts.implicit_wait)        # 5.0
driver.timeouts.implicit_wait = 0                             # 关掉隐式等待
driver.timeouts.page_load = 60                                # 页面加载超时
driver.timeouts.script = 30                                   # execute_script 超时
```

浏览器开关（`add_argument`）在工程里最常用的几个：

| 参数 | 作用 | 何时必须 |
|---|---|---|
| `--headless=new` | 新版无头模式 | CI、服务器 |
| `--no-sandbox` | 关掉 Chrome 沙箱 | root / 容器内，否则起不来 |
| `--disable-dev-shm-usage` | 用 /tmp 代替 /dev/shm | Docker 默认 64MB 共享内存 |
| `--window-size=W,H` | 固定视口 | 元素在视口外导致的定位/点击差异 |
| `--lang=zh-CN` | 语言与 Accept-Language | 多语言站点 |
| `--incognito` | 无痕模式 | 需要干净存储状态 |
| `--disable-gpu` | 关 GPU（旧版无头必需） | 老版本 Chrome |

## 应用场景实战

### 场景一：CI 容器内无头跑巡检脚本并把结果落盘

一个真实可跑的例子：对一批 URL 做冒烟巡检，记录标题、耗时与失败原因，输出 JSON 并让进程退出码反映结果。要点是**浏览器只启动一次**（会话昂贵）、每个 URL 用 try/except 隔离失败、无头参数齐备。

```python
# smoke_check.py —— 完整可运行：python smoke_check.py urls.txt
import json
import sys
import time
from pathlib import Path

from selenium import webdriver
from selenium.webdriver.chrome.options import Options
from selenium.common.exceptions import WebDriverException

CHROME = "/root/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome"


def build_driver():
    """构建无头会话：binary_location 固定浏览器版本，避免 CI 里联网下载。"""
    opts = Options()
    opts.binary_location = CHROME
    opts.add_argument("--headless=new")
    opts.add_argument("--no-sandbox")
    opts.add_argument("--disable-dev-shm-usage")
    opts.add_argument("--window-size=1440,900")
    opts.timeouts = {"pageLoad": 30000, "script": 20000}   # 毫秒
    driver = webdriver.Chrome(options=opts)
    driver.set_page_load_timeout(30)                       # 秒，页面加载超时
    return driver


def check(driver, url):
    start = time.perf_counter()
    try:
        driver.get(url)
        return {
            "url": url,
            "ok": True,
            "title": driver.title,
            "elapsed_ms": round((time.perf_counter() - start) * 1000),
            "browser": driver.capabilities.get("browserVersion"),
        }
    except WebDriverException as exc:
        return {
            "url": url,
            "ok": False,
            "error": type(exc).__name__,
            "message": str(exc).splitlines()[0][:200],
            "elapsed_ms": round((time.perf_counter() - start) * 1000),
        }


def main(urls_file: str) -> int:
    urls = [u.strip() for u in Path(urls_file).read_text(encoding="utf-8").splitlines() if u.strip()]
    driver = build_driver()
    try:
        results = [check(driver, u) for u in urls]
    finally:
        driver.quit()                                      # 必须放 finally，否则泄漏 chrome 进程
    report = {"total": len(results), "failed": sum(1 for r in results if not r["ok"]), "results": results}
    Path("smoke_report.json").write_text(json.dumps(report, ensure_ascii=False, indent=2), encoding="utf-8")
    print(json.dumps({k: report[k] for k in ("total", "failed")}, ensure_ascii=False))
    return 1 if report["failed"] else 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1] if len(sys.argv) > 1 else "urls.txt"))
```

### 场景二：内网环境预热并固定驱动版本

内网机器连不上外网时，标准做法是在有网机器上预热缓存、打包目录、拷进内网；同时把浏览器版本固定写死，避免自动升级带来的漂移。

```bash
# 第 1 步：在能联网的机器上，按内网实际浏览器版本预热（--browser-path 指向真实二进制）
SM=/usr/local/lib/python3.12/site-packages/selenium/webdriver/common/linux-x86_64/selenium-manager
$SM --browser chrome --browser-path /opt/chrome/chrome --output JSON > /tmp/sm.json
```

```bash
# 第 2 步：内网机器上校验 driver 与浏览器主版本是否一致，不一致就不许进 CI
python - <<'PY'
import json, re, subprocess
sm = '/usr/local/lib/python3.12/site-packages/selenium/webdriver/common/linux-x86_64/selenium-manager'
r = json.loads(subprocess.check_output(
    [sm, '--browser', 'chrome', '--browser-path', '/opt/chrome/chrome', '--output', 'JSON']))
drv, brw = r['result']['driver_path'], r['result']['browser_path']
print('driver :', drv)
print('browser:', brw)
# driver 的版本号在路径的目录名里，浏览器的版本号只能靠执行二进制拿
browser_ver = re.search(r'(\d+\.\d+\.\d+\.\d+)',
                        subprocess.check_output([brw, '--version'], text=True)).group(1)
driver_ver = drv.split('/')[-2]
print('browser 版本:', browser_ver)
print('driver  版本:', driver_ver)
assert browser_ver.split('.')[0] == driver_ver.split('.')[0], '主版本不一致，禁止进 CI'
print('版本匹配: OK')
PY
```

```bash
# 第 3 步：完全离线时用 Service 显式指定 driver，绕开任何探测逻辑
python - <<'PY'
from selenium import webdriver
from selenium.webdriver.chrome.options import Options
from selenium.webdriver.chrome.service import Service
opts = Options()
opts.binary_location = '/opt/chrome/chrome'
opts.add_argument('--headless=new')
opts.add_argument('--no-sandbox')
svc = Service(executable_path='/root/.cache/selenium/chromedriver/linux64/151.0.7922.138/chromedriver')
d = webdriver.Chrome(service=svc, options=opts)
print('会话内 driver 版本:', d.capabilities['chrome']['chromedriverVersion'].split(' ')[0])
d.quit()
PY
```

本机实测（本地缓存的 151 驱动 + Playwright 的 Chromium，两步都跑通）：

```text

browser: /root/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome

driver  版本: 151.0.7922.138
```

注意：**driver 路径里带版本号目录名，浏览器路径里没有**，所以浏览器版本必须执行一次 `chrome --version` 才能拿到——本机写这段校验时第一版就是直接拿路径目录名比，直接 `AssertionError`，改成正则解析 `--version` 输出才对。

另外可用 `--driver-mirror-url` 指到公司内网镜像（如 Nexus 上转存的 chromedriver 仓库），把下载也留在内网；该参数未在本机验证，以官方文档与内网镜像实际结构为准。

## 最佳实践与踩坑记录

### 最佳实践

1. 每个项目用独立 venv，并把 `selenium==4.x.y` 钉死版本；driver 由 Selenium Manager 管，但浏览器版本要在 CI 镜像里固定下来，不要用 latest 标签。
2. `driver.quit()` 必须写在 `finally` 或 pytest fixture 的 teardown 里。只调 `close()` 只关窗口，driver 进程还在，批量跑起来会把机器堆满僵尸 chrome。
3. 启动参数（headless、no-sandbox、window-size、lang）集中在一个 `build_driver()` 工厂函数里，用例代码不碰 Options；换浏览器只改一处。
4. 每次会话把 `driver.capabilities` 里的 `browserVersion` 与 `chromedriverVersion` 打进日志，版本类故障可以一眼定位，不用复现。
5. CI 构建阶段预热 `~/.cache/selenium`（跑一次 `webdriver.Chrome()` 再 quit），运行阶段就完全不依赖外网，也不会被 Selenium Manager 的网络超时拖死。
6. pip 安装固定用清华镜像 `-i https://pypi.tuna.tsinghua.edu.cn/simple`，内网再加 `--trusted-host`，避免网络抖动让构建随机失败。

### 踩坑记录

```text
坑 1：本机明明没装 Chrome，脚本却卡在 webdriver.Chrome() 不动，最后超时
结论：以为 selenium 装坏了，反复重装绑定包。
原因：不指定 binary_location 时，Selenium Manager 会去联网解析并下载最新 Chrome for Testing
      （本机实测解析出的是 155.0.8059.79），网络受限时表现为长时间无输出，
      Selenium Manager 的网络请求默认超时是 300 秒（--timeout 可调）。
解法：要么设 Options().binary_location 指向已有浏览器二进制；要么在能联网时预热一次，
      之后走缓存；要么用 Service(executable_path=...) 完全绕开探测。
      本机实测：--browser chrome 不指定路径时解析到
      /root/.cache/selenium/chrome/linux64/155.0.8059.79/chrome 与 chromedriver 155.0.8059.79；
      加上 --browser-path 指向 Playwright 缓存里的 Chromium 后，解析到的是 chromedriver
      151.0.7922.138，与本地二进制主版本一致。缓存命中后启动耗时 1.1 秒。

坑 2：CI 里 webdriver.Firefox() 直接抛 InvalidArgumentException: binary is not a Firefox executable
结论：以为 snap 装的 firefox 不算安装，想去 apt 重装（Ubuntu 24.04 的 firefox 已经是 snap 独占）。
原因：Ubuntu 的 /usr/bin/firefox 是一个 shell 包装脚本（本机实测前两行是 #!/bin/sh 与检测
      /snap/bin/firefox 是否可执行），geckodriver 0.37.1 会按可执行文件校验，包装脚本不满足条件。
解法：给 FirefoxOptions().binary_location 指向 snap 里真实的二进制
      （通常为 /snap/firefox/current/usr/lib/firefox/firefox）；或者干脆统一用 Chrome 系。
      本条未在本机验证，需按实际安装路径确认。

坑 3：脚本跑完进程不退，机器上堆了几十个 chrome 进程
结论：以为是无头模式的锅，去加 --disable-gpu 之类的参数。
原因：driver.quit() 没走到。find_element 抛异常后代码直接蹦出函数，quit 那行永远没执行；
      只调 driver.close() 也只关当前窗口，driver 进程与浏览器进程都还在。
解法：quit 放 finally / fixture teardown；CI 里加兜底 pkill -f chromedriver 与
      pgrep -f "chrome --headless" 的监控，进程数异常直接让任务失败。

坑 4：报 session not created: This version of ChromeDriver only supports Chrome version 113
结论：怀疑 Selenium 4 有 bug，去手动下载对应 driver 塞进 PATH。
原因：浏览器被后台自动升级到了新主版本，而缓存里的 driver 还是旧的。官方驱动管理文档举的
      就是 Chrome 113 升到 115 的例子：手动管理 driver 在 evergreen 浏览器上必然漂移。
解法：交给 Selenium Manager（删掉手动 PATH 配置与第三方 webdriver-manager），
      或在 CI 镜像里同时固定浏览器与 driver 版本；排障时先看 capabilities 里的两个版本号。

坑 5：pip install selenium 卡住或超时，装到一半报 SSL 错误
结论：以为包有问题，换了个更老的版本再试。
原因：默认走 PyPI 官方源，国内网络不稳定；selenium 的依赖树（trio、urllib3、wsproto 等）
      十几个包，任何一个超时都会整体失败。
解法：加清华镜像 -i https://pypi.tuna.tsinghua.edu.cn/simple（本机实测 11.8MB 的 wheel
      2 秒下完，整棵树一次装完）；公司内网用私有 PyPI 代理并加 --trusted-host。
```
