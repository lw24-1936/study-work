## 概述

串行跑 UI 用例的成本几乎全部花在「重启浏览器」上：本机实测 9 条轻量用例串行耗时 102.96 秒，其中真正的业务断言不到 3 秒。并行分两个层次解决它——**单机并行**（pytest-xdist 起多个进程、各自开浏览器，见本篇最后一节）和**分布式**（Selenium Grid：多个节点机、多种浏览器版本，客户端只需换一个 URL）。Grid 4 是完全重写的版本，把旧版 Hub/Node 拆成六个可独立部署的组件，天然面向容器与弹性伸缩。

需要先记住两条硬约束，它们决定了容量规划：官方文档指出，**每个浏览器会话大约需要 1 个 CPU 与 1GB 内存**；Node 默认最大并发会话数受 CPU 数限制（`--max-sessions` 默认取可用处理器数），Distributor 创建会话的并发度同样受其所在机器的 CPU 数限制。所以「一台 32 核机器跑 32 个浏览器」不如「32 个小 Node」——后者进程隔离更好，单点故障影响面更小。

```text
本篇主线：
1. Grid 架构 —— Router / Distributor / Session Map / New Session Queue / Event Bus / Node 的职责与默认端口
2. 部署形态 —— standalone（单进程）、Hub + Node、Distributed（六组件分离），以及组件间的启动顺序
3. 节点配置 —— TOML 的 [node]、[[node.driver-configuration]]、stereotype、detect-drivers、max-sessions
4. 能力匹配 —— capabilities 与 slot stereotype 的匹配规则、se: 元数据、/status 查询
5. 容器化 —— docker run 单机、Hub+Node Compose、SE_* 环境变量、--shm-size、动态 Grid
6. 并行与隔离 —— pytest-xdist 实测（串行 102.96s / -n 4 62.03s / -n 8 73.73s）与 worker 级资源隔离
```

本机验证说明（重要）：Ubuntu 24.04、8 核 CPU、Python 3.14.7、selenium 4.51.0、pytest 4.9.1 与 pytest-xdist 3.8.0。**Grid 服务端在本机未验证**——`docker pull selenium/standalone-chrome` 与从 GitHub Releases 下载 `selenium-server-4.51.0.jar`（56MB）在本机网络下都严重限速（前者 35 分钟未完成层解压、后者约 4KB/s），因此涉及 Grid 服务端与容器镜像的章节按 [selenium.dev 官方文档](https://www.selenium.dev/documentation/grid/getting_started/) 与 [docker-selenium 官方仓库](https://github.com/SeleniumHQ/docker-selenium) 编写，**标注为未在本机验证**。客户端行为、xdist 并行、worker 隔离等能跑的都已真跑并附原始输出。

## Grid 4 架构与六种角色

Grid 4 由六个组件构成，官方文档对每个角色的定义如下：

| 组件 | 职责 | 默认端口 |
|---|---|---|
| Router | Grid 的唯一入口。新会话请求转发到 New Session Queue；已有会话的请求按 Session Map 查到 Node 后直连转发 | 4444 |
| Distributor | 维护 Node 与 slot 的注册信息（Grid Model），并按 capabilities 把新会话分配到合适的 Node | 5553 |
| Session Map | 保存 session id 到 Node 地址的映射 | 5556 |
| New Session Queue | 新会话请求的 FIFO 队列，可配置排队超时与重试间隔 | 5559 |
| Event Bus | 组件间的异步消息总线（Node 注册、心跳等） | publish 4442 / subscribe 4443 / 自身 5557 |
| Node | 真正跑 WebDriver 会话的进程，一个 Node 有若干 slot | 5555 |

三个概念要区分清楚：

- **slot**：一个会话可以运行的位置。Node 的 slot 数由 `--max-sessions` 决定。
- **stereotype**：slot 匹配所需的最小 capability 集合，例如 `{"browserName": "chrome"}`。会话请求的 capabilities 必须覆盖它，Distributor 才可能选中该 slot。
- **Grid Model**：Distributor 内部维护的 Grid 状态快照。它优先于逐个查询 Node，因此**可能短暂与现实不一致**——排查「明明有空闲 Node 却排队」时这是第一嫌疑点。

组件间有两类通信：同步的 REST/JSON over HTTP（绝大多数 WebDriver 命令）与异步的 Event Bus 事件（广播类、丢了也不致命的信息）。官方文档给出的启动顺序是：Event Bus 与 Session Map 最先（互不依赖，可并行）；然后是 Session Queue；再是 Distributor；再是 Router；最后启动 Node，注册完成后 Grid 才能对外服务。

Node 注册靠心跳：Node 定期在 Event Bus 上发心跳，Distributor 收到后 HTTP 请求该 Node 的 `/status`，据此建立 Grid Model。因此 **Hub 与 Node 在不同机器时，必须互通 Event Bus 的 4442/4443 端口以及 Node 自己的端口**，这是跨机部署最常见的网络坑。

```text
要点：
- 六个组件：Router / Distributor / Session Map / New Session Queue / Event Bus / Node
- 默认端口：Router 4444、Node 5555、Distributor 5553、Session Map 5556、Session Queue 5559、Event Bus 4442/4443/5557
- slot = 会话位置，stereotype = 匹配所需的最小能力集合，Grid Model 是可能失准的缓存
- 启动顺序：Event Bus + Session Map -> Session Queue -> Distributor -> Router -> Node
- 跨机部署必须放开 Event Bus 端口，否则 Node 注册不上
- 容量参考：每会话约 1 CPU / 1GB 内存，Node 默认 max-sessions 等于 CPU 数
```

## 部署形态 Standalone Hub-Node 与 Distributed

官方文档给出三种形态，按规模选：

**Standalone（单机一体）**——一个进程里跑全部组件，适合本地调试 RemoteWebDriver 和 CI 里的快速回归：

```shell
# 前置：Java 11+、浏览器与驱动（可用 --selenium-manager true 让 Grid 自己拉驱动）
java -jar selenium-server-<version>.jar standalone
# 默认监听 http://localhost:4444，浏览器 UI 打开该地址可看 Grid 状态
java -jar selenium-server-<version>.jar standalone --max-sessions 4 --port 4444
```

**Hub + Node（最常用的分布式形态）**——一个入口、多个可横向扩缩的 Node：

```shell
# Hub 上：Router + Distributor + Session Map + New Session Queue + Event Bus
java -jar selenium-server-<version>.jar hub

# 同机多个 Node 要错开端口
java -jar selenium-server-<version>.jar node --port 5555
java -jar selenium-server-<version>.jar node --port 6666

# 跨机注册：Hub 用默认端口时，--hub 一个参数就够
java -jar selenium-server-<version>.jar node --hub http://<hub-ip>:4444

# Hub 非默认端口时，必须显式给 Event Bus 的发布/订阅地址
java -jar selenium-server-<version>.jar hub \
  --publish-events tcp://<hub-ip>:8886 --subscribe-events tcp://<hub-ip>:8887 --port 8888
java -jar selenium-server-<version>.jar node \
  --publish-events tcp://<hub-ip>:8886 --subscribe-events tcp://<hub-ip>:8887
```

**Distributed（六组件分离）**——组件各自独立部署，适合大规模与需要独立扩缩的场景：

```shell
# 1) Event Bus
java -jar selenium-server-<version>.jar event-bus \
  --publish-events tcp://<event-bus-ip>:4442 --subscribe-events tcp://<event-bus-ip>:4443 --port 5557
# 2) New Session Queue
java -jar selenium-server-<version>.jar sessionqueue --port 5559
# 3) Session Map
java -jar selenium-server-<version>.jar sessions \
  --publish-events tcp://<event-bus-ip>:4442 --subscribe-events tcp://<event-bus-ip>:4443 --port 5556
# 4) Distributor（--bind-bus false 表示只连 Event Bus，不自己起）
java -jar selenium-server-<version>.jar distributor \
  --publish-events tcp://<event-bus-ip>:4442 --subscribe-events tcp://<event-bus-ip>:4443 \
  --sessions http://<sessions-ip>:5556 --sessionqueue http://<new-session-queue-ip>:5559 \
  --port 5553 --bind-bus false
# 5) Router
java -jar selenium-server-<version>.jar router \
  --sessions http://<sessions-ip>:5556 --distributor http://<distributor-ip>:5553 \
  --sessionqueue http://<new-session-queue-ip>:5559 --port 4444
# 6) Node
java -jar selenium-server-<version>.jar node \
  --publish-events tcp://<event-bus-ip>:4442 --subscribe-events tcp://<event-bus-ip>:4443
```

客户端代码在三种形态下完全一致，只是 URL 从本地改成 Grid 地址：

```python
from selenium import webdriver
from selenium.webdriver.chrome.options import Options

GRID_URL = "http://127.0.0.1:4444"     # 三种形态下都是 Router/Hub/Standalone 的地址

opts = Options()
opts.add_argument("--headless=new")
opts.add_argument("--no-sandbox")
opts.add_argument("--disable-dev-shm-usage")   # 容器/小 /dev/shm 环境必加
opts.set_capability("se:name", "订单回归_登录下单")   # 元数据，Grid UI 与 GraphQL 可见
opts.set_capability("se:containerName", "ci-runner-3")  # 可自定义元数据

driver = webdriver.Remote(command_executor=GRID_URL, options=opts)
try:
    print("session_id =", driver.session_id)
    print("capabilities =", driver.capabilities)
finally:
    driver.quit()      # 必须 quit：只有它会通知 Grid 释放 slot
```

本机没有 Grid 可连，所以我把「连不上时到底是什么样」实测了一遍——这是排查配置错误时最先看到的东西：

```text
探测 http://127.0.0.1:4444/status 失败: URLError: <urlopen error [Errno 111] Connection refused>
RemoteWebDriver 连接失败 (0.24s): MaxRetryError
HTTPConnectionPool(host='127.0.0.1', port=4444): Max retries exceeded with url: /session (Caused by NewConnectionError("HTTPConnection(host='127.0.0.1', port=4444): Failed to establish a new connection: [Errno 111] Connection refused"))
```

两点经验：第一，**先探 `/status`** 再怪客户端——端口没通就是网络/未启动问题，客户端重试只是浪费 30 秒；第二，现代 Remote 的 `command_executor` 只写到端口（`http://host:4444`），不要按旧习惯拼 `/wd/hub`。

Grid 上线后有两处查询入口：`http://localhost:4444`（Grid UI）与 `http://localhost:4444/status`（或 GraphQL）。官方文档还特别强调**必须用防火墙保护 Grid**，否则等于把内部网络与「任意二进制执行」能力开放出去。

```text
要点：
- Standalone 一个进程搞定，适合本地与轻量 CI；Hub + Node 是最常用的分布式形态
- 跨机注册要么用 --hub，要么显式给 --publish-events/--subscribe-events
- Distributed 下每个组件都要能连到 Event Bus，端口放开是关键
- 客户端三种形态代码一致，只换 command_executor 地址（现代写法不带 /wd/hub）
- se: 前缀的 capability 是元数据，会在 Grid UI / GraphQL 里显示
- 会话结束必须 quit()，否则 slot 不释放；排查排队问题先看 /status
- Grid 必须限制访问来源，公开暴露等于开放内部网络与任意二进制执行
```

## 节点配置与能力匹配

Node 启动时会从 `PATH` 自动探测可用驱动（`--detect-drivers true` 是默认值）。官方文档**推荐用 TOML 文件做配置**，可读性好、能进版本控制，命令行参数也仍可叠加使用。

```toml
# node.toml —— 只启用 chrome 与 firefox，最多 3 个并发会话
[node]
drivers = ["chrome", "firefox"]
max-sessions = 3
```

自定义驱动（多浏览器版本、非默认安装路径）要关掉自动探测，逐条声明：

```toml
[node]
detect-drivers = false

[[node.driver-configuration]]
display-name = "Chrome Stable"
max-sessions = 4
stereotype = '{"browserName": "chrome", "browserVersion": "139.0", "platformName": "Linux"}'
webdriver-executable = "/usr/local/bin/chromedriver"

[[node.driver-configuration]]
display-name = "Firefox Beta"
max-sessions = 2
stereotype = '{"browserName": "firefox", "browserVersion": "141.0", "platformName": "Linux"}'
webdriver-executable = "/opt/firefox-beta/geckodriver"
```

启动时用 `--config` 指定：

```shell
java -jar selenium-server-<version>.jar node --config /etc/selenium/node.toml
java -jar selenium-server-<version>.jar standalone --config /etc/selenium/node.toml
```

**能力匹配（capability matching）**是这块最需要理解的规则：客户端请求的 capabilities 必须**覆盖**某个 slot 的 stereotype，Distributor 才会把会话放到那个 slot 上。自定义 capability 要遵守 W3C 扩展约定——**键里必须带冒号**（`myApp:version`）。官方文档特别提示：自定义 capability 必须在**所有** Node 配置里出现，并且**每个**会话请求都要带上，否则会话可能匹配到没有该标记的 Node 上。

```toml
[node]
detect-drivers = false

[[node.driver-configuration]]
display-name = "chrome-beta-node"
max-sessions = 5
stereotype = '{"browserName": "chrome", "platformName": "Linux", "myApp:version": "beta"}'
```

```python
# 客户端：把同样的自定义 capability 带上，才会落到 beta 节点
opts = Options()
opts.set_capability("myApp:version", "beta")
driver = webdriver.Remote(command_executor=GRID_URL, options=opts)
```

与 Node 行为相关的常用参数（官方 CLI 选项表）：

| 参数 | 默认 | 作用 |
|---|---|---|
| `--max-sessions` | 可用处理器数 | 单 Node 最大并发会话数 |
| `--override-max-sessions` | `false` | 允许突破「1 会话 / 1 CPU」的推荐上限，稳定性自负 |
| `--session-timeout` | 300 | 会话无活动超过该秒数自动回收，释放 slot |
| `--heartbeat-period` | 60 | Node 向 Distributor 发心跳的间隔 |
| `--register-cycle` / `--register-period` | 10 / 120 | 首次注册的重试节奏与总时长 |
| `--detect-drivers` | `true` | 是否自动探测驱动 |
| `--drain-after-session-count` | 0 | 跑满 N 个会话后优雅下线，K8s 滚动更新常用 |
| `--node-down-failure-threshold` | 0 | 连续失败到该次数后把 Node 标记为 DOWN，0 表示不启用 |
| `--enable-cdp` / `--enable-bidi` | `true` | 是否允许 CDP/BiDi 代理（禁用 WebSocket 的环境要关） |

```text
要点：
- Node 默认自动探测 PATH 上的驱动；自定义版本要 detect-drivers = false 再逐条声明
- 推荐用 TOML（--config）而不是超长命令行
- 会话能力必须覆盖 slot 的 stereotype 才能落上去
- 自定义 capability 的键必须带冒号（W3C 扩展约定），且所有 Node 与会话都要带
- --max-sessions 默认等于 CPU 数；--override-max-sessions 允许突破但不保证稳定
- --session-timeout 默认 300 秒，是卡死会话自动释放 slot 的兜底
```

## 容器化部署

以下内容按 docker-selenium 官方仓库编写，**未在本机跑通**（本机 docker daemon 可用，但 `docker pull selenium/standalone-chrome` 在实际等待 35 分钟后仍未完成镜像层解压，网络限速严重）。

最简单的单机形态是一个容器同时提供 Grid 与浏览器：

```bash
# 官方 Quick start：Standalone Firefox，映射 Grid 端口与 noVNC 端口
docker run -d -p 4444:4444 -p 7900:7900 --shm-size="2g" \
  selenium/standalone-firefox:4.48.0-20260905
# 测试指向 http://localhost:4444 即可
```

`--shm-size="2g"` 是官方 troubleshooting 里明确列出的一条：默认 64MB 的 `/dev/shm` 会让 Chrome 崩溃，容器里要么加大 shm，要么在 capabilities 里加 `--disable-dev-shm-usage`。

Hub + Node 的 Compose 写法（环境变量名取自官方 `ENV_VARIABLES.md`）：

```yaml
# docker-compose.yml
services:
  selenium-hub:
    image: selenium/hub:4.48.0-20260905
    ports:
      - "4442:4442"     # Event Bus 发布
      - "4443:4443"     # Event Bus 订阅
      - "4444:4444"     # Router / Grid 入口
  chrome:
    image: selenium/node-chrome:4.48.0-20260905
    shm_size: 2gb
    depends_on: [selenium-hub]
    environment:
      SE_EVENT_BUS_HOST: selenium-hub
      SE_EVENT_BUS_PUBLISH_PORT: 4442
      SE_EVENT_BUS_SUBSCRIBE_PORT: 4443
      SE_NODE_MAX_SESSIONS: 4          # 默认 1，容器里必须显式调大
      SE_NODE_OVERRIDE_MAX_SESSIONS: "true"   # 不设则 max-sessions 不生效
      SE_START_VNC: "false"            # 不需要看画面就关掉，省资源
      SE_SESSION_REQUEST_TIMEOUT: 300
      SE_SESSION_RETRY_INTERVAL: 5
  firefox:
    image: selenium/node-firefox:4.48.0-20260905
    shm_size: 2gb
    depends_on: [selenium-hub]
    environment:
      SE_EVENT_BUS_HOST: selenium-hub
      SE_EVENT_BUS_PUBLISH_PORT: 4442
      SE_EVENT_BUS_SUBSCRIBE_PORT: 4443
      SE_NODE_MAX_SESSIONS: 2
      SE_NODE_OVERRIDE_MAX_SESSIONS: "true"
```

```bash
docker compose up -d
docker compose up -d --scale chrome=4     # 横向扩容 Chrome 节点
docker compose logs selenium-hub
docker compose down
```

常用环境变量（官方 `ENV_VARIABLES.md`）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `SE_EVENT_BUS_HOST` | 空 | Hub 主机名，跨容器注册必填 |
| `SE_EVENT_BUS_PUBLISH_PORT` / `SE_EVENT_BUS_SUBSCRIBE_PORT` | 4442 / 4443 | Event Bus 端口 |
| `SE_NODE_MAX_SESSIONS` | 1 | 单 Node 最大并发会话数（容器默认只有 1） |
| `SE_NODE_OVERRIDE_MAX_SESSIONS` | false | 不开启则 `SE_NODE_MAX_SESSIONS` 不生效 |
| `SE_NODE_SESSION_TIMEOUT` | 300 | 空闲会话回收秒数 |
| `SE_SESSION_REQUEST_TIMEOUT` / `SE_SESSION_RETRY_INTERVAL` | 300 / 15 | 排队超时与重试间隔 |
| `SE_START_VNC` / `SE_START_NO_VNC` | true / true | 是否启动 VNC / noVNC |
| `SE_NO_VNC_PORT` | 7900 | noVNC 端口，浏览器直接看执行画面 |
| `SE_SCREEN_WIDTH` / `SE_SCREEN_HEIGHT` | 1920 / 1080 | 节点屏幕分辨率，影响截图尺寸 |
| `SE_NODE_STEREOTYPE` / `SE_NODE_STEREOTYPE_EXTRA` | 空 | 覆盖 / 追加 Node 的 stereotype |
| `SE_OPTS` | 空 | 传递没有对应环境变量的 CLI 参数 |
| `SE_DRAIN_AFTER_SESSION_COUNT` | 0 | 跑满 N 个会话后下线，配合 K8s 滚动更新 |
| `SE_OFFLINE` | true | Selenium Manager 离线模式，直接用镜像内预置的浏览器与驱动 |
| `SE_UPDATE_CHROME_COMPONENTS` | 空 | node-chrome / standalone-chrome（amd64）启动时升级 Chrome 与驱动 |

**动态 Grid** 是另一种模式：Node 自己不跑浏览器，每来一个会话就按 `[docker]` 配置起一个浏览器容器，跑完销毁——弹性最好，代价是启动延迟。官方 TOML 配置长这样：

```toml
[node]
detect-drivers = false
max-sessions = 2

[docker]
configs = [
  "selenium/standalone-chrome:latest", "{\"browserName\": \"chrome\", \"browserVersion\": \"139.0\"}",
  "selenium/standalone-firefox:latest", "{\"browserName\": \"firefox\", \"browserVersion\": \"141.0\"}"
]
url = "http://localhost:2375"          # Docker daemon 的 HTTP 端点
video-image = "selenium/video:latest"
```

镜像 tag 建议**固定到具体版本**（形如 `4.48.0-20260905`）而不是 `latest`，避免浏览器/驱动随镜像漂移导致用例某天突然集体失败；升级走显式的版本号变更。

```text
要点：
- 单容器起步：docker run -d -p 4444:4444 --shm-size="2g" selenium/standalone-chrome:<版本>
- --shm-size 或 --disable-dev-shm-usage 必须二选一，否则容器里 Chrome 容易崩
- Hub + Node 的关键环境变量是 SE_EVENT_BUS_HOST 与两个事件端口
- 容器里 SE_NODE_MAX_SESSIONS 默认只有 1，且必须配 SE_NODE_OVERRIDE_MAX_SESSIONS=true
- 动态 Grid 用 [docker] configs 把 stereotype 映射到镜像，按需起容器
- 镜像 tag 固定版本，别用 latest，避免浏览器漂移造成集体失败
- 本节内容按官方文档编写，本机网络受限未能实际跑通
```

## 并行执行与隔离

单机并行用 `pytest-xdist`：它把用例分发给多个 worker 进程，每个 worker 独立执行、独立建驱动。三条实测数据（8 核机器、9 条用例、每条用例一个浏览器会话）：

| 运行方式 | 命令 | 实测耗时 |
|---|---|---|
| 串行 | `pytest -q` | 102.96s |
| 4 个 worker | `pytest -q -n 4` | 62.03s |
| 8 个 worker | `pytest -q -n 8` | 73.73s |

```bash
# 自动按 CPU 数开 worker
python -m pytest -q -n auto
# 固定 4 个 worker，按用例粒度分发
python -m pytest -q -n 4
# 按文件粒度分发，减少同一文件里用例的互相干扰
python -m pytest -q -n 4 --dist loadfile
# 按用例所属 class/module 聚合分发
python -m pytest -q -n 4 --dist loadscope
```

两点值得注意的实测结论：一是 **4 个 worker 比 8 个更快**（62s vs 74s）——浏览器是重资源进程，8 个并行时 CPU 与 I/O 争抢加剧，单会话变慢抵消了并行收益；二是**加速比远非线性**（102.96 / 62.03 ≈ 1.66 倍，而 worker 数翻了 4 倍），因为每条用例都要重启浏览器，进程启动与首屏渲染是纯开销。想继续压缩时间，优化方向应该是「减少会话数」（会话级驱动 + 用例间清理 Cookie）而不是「加 worker」。

**并行下最容易翻车的是隔离**。有三类资源必须按 worker 拆开：

```python
import os
import pathlib

import pytest

ROOT = pathlib.Path("/root/.hermes/cache/scratch/selb_187_workers")


def worker_id(request):
    """xdist 下取 worker 名（gw0/gw1/...）；非 xdist 运行返回 'master'。"""
    if hasattr(request.config, "workerinput"):
        return request.config.workerinput["workerid"]
    return "master"


@pytest.fixture
def isolated_paths(request):
    wid = worker_id(request)
    download_dir = ROOT / wid / "downloads"      # 下载目录按 worker 隔离
    profile_dir = ROOT / wid / "profile"         # 浏览器 profile 按 worker 隔离
    download_dir.mkdir(parents=True, exist_ok=True)
    profile_dir.mkdir(parents=True, exist_ok=True)
    return {"worker": wid, "download": str(download_dir), "profile": str(profile_dir)}
```

本机实测（`pytest -n 2`，每个 worker 写入自己的目录）：

```text
bringing up nodes...

..                                                                       [100%]
2 passed in 0.38s

# 两个 worker 各自落盘的记录
worker=gw0 download=/root/.hermes/cache/scratch/selb_187_workers/gw0/downloads profile=/root/.hermes/cache/scratch/selb_187_workers/gw0/profile pid=65419
again worker=gw1 pid=65422
```

驱动构造时把 worker 目录接上去，就得到天然隔离的会话：

```python
def chrome_options(worker_dirs, headless=True):
    opts = Options()
    opts.add_argument("--headless=new")
    opts.add_argument("--window-size=1440,900")
    opts.add_argument("--user-data-dir=" + worker_dirs["profile"])   # 独立 profile
    opts.add_experimental_option("prefs", {
        "download.default_directory": worker_dirs["download"],       # 独立下载目录
        "download.prompt_for_download": False,
    })
    return opts
```

除了目录隔离，还有几条并行前提必须满足：

- **被测数据的隔离**：并行用例不要在同一个账号 / 同一条订单上写操作，否则互相覆盖。常见做法是给每个 worker 分配独立租户或独立测试账号（`tenant = worker_id`）。
- **唯一化业务标识**：生成的单号、用户名带上 worker 名或 uuid。
- **日志分流**：每条用例的日志文件、截图、报告附件都带 worker 名，否则并发写同一文件会互相截断。
- **服务端限流**：并行会让被测服务承受 N 倍流量，提前确认接口 QPS 与数据库连接池扛得住，必要时 `-n` 降下来。
- **执行顺序假设**：`-n` 之后用例顺序不再可控，任何依赖「上一条用例留下的状态」的用例都要重写成自给自足。

```text
要点：
- pytest-xdist 用 -n 开进程级并行，--dist 控制分发粒度（load / loadfile / loadscope）
- 实测 8 核机器上 -n 4（62s）优于 -n 8（74s），并行收益会被资源争抢吃掉
- 加速比远非线性，因为每条用例重启浏览器是纯开销
- 下载目录、浏览器 profile、日志文件都要按 worker id 隔离
- 业务数据同样要隔离：独立账号/租户，唯一化单号
- -n 之后用例顺序不可控，禁止依赖执行顺序与共享状态
```

## 应用场景实战

### 场景一：CI 里的并行回归（xdist + worker 级隔离）

把「登录 → 下单 → 加购」这类无状态用例做成可并行的套件：每个 worker 独立浏览器、独立 profile、独立下载目录，用 GitHub Actions 的矩阵并行不同浏览器。

```python
# conftest.py（节选）
import pathlib

import pytest
from selenium import webdriver
from selenium.webdriver.chrome.options import Options

WORKDIR = pathlib.Path("/tmp/sel-runs")     # CI 上放 workspace 内即可


def worker_id(request):
    if hasattr(request.config, "workerinput"):
        return request.config.workerinput["workerid"]
    return "master"


@pytest.fixture(scope="session")
def run_root(tmp_path_factory):
    return tmp_path_factory.mktemp("run")


@pytest.fixture
def driver(request, run_root):
    wid = worker_id(request)
    base = run_root / wid
    (base / "downloads").mkdir(parents=True, exist_ok=True)
    (base / "profile").mkdir(parents=True, exist_ok=True)

    opts = Options()
    opts.add_argument("--headless=new")
    opts.add_argument("--no-sandbox")
    opts.add_argument("--disable-dev-shm-usage")
    opts.add_argument("--window-size=1440,900")
    opts.add_argument("--user-data-dir=" + str(base / "profile"))
    opts.add_experimental_option("prefs", {
        "download.default_directory": str(base / "downloads"),
        "download.prompt_for_download": False,
    })
    drv = webdriver.Chrome(options=opts)
    drv.worker_id = wid           # 供失败留证钩子给附件命名
    yield drv
    drv.quit()
```

```yaml
# .github/workflows/e2e.yml

  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5

          python-version: "3.12"

        env:
          BASE_URL: ${{ vars.STAGING_URL }}
```

### 场景二：多环境多浏览器的 Grid 分发

同一套用例要在 staging 的 Chrome 与预发的 Firefox 上跑，用 Grid 一个入口搞定：Node 侧按浏览器与版本声明 stereotype，客户端按环境带 capabilities。

```toml
# grid-node.toml —— 部署在 CI 机器上，两种浏览器分槽
[node]
detect-drivers = false

[[node.driver-configuration]]
display-name = "Chrome Staging"
max-sessions = 4
stereotype = '{"browserName": "chrome", "browserVersion": "139.0", "platformName": "Linux", "env:stage": "staging"}'
webdriver-executable = "/usr/local/bin/chromedriver"

[[node.driver-configuration]]
display-name = "Firefox Canary"
max-sessions = 2
stereotype = '{"browserName": "firefox", "browserVersion": "141.0", "platformName": "Linux", "env:stage": "canary"}'
webdriver-executable = "/opt/firefox-canary/geckodriver"
```

```python
# conftest.py：把「环境」参数化到能力里，同一套用例跑两个环境
import os

import pytest
from selenium import webdriver
from selenium.webdriver.chrome.options import Options
from selenium.webdriver.firefox.options import Options as FirefoxOptions

GRID_URL = os.environ.get("GRID_URL", "http://127.0.0.1:4444")
TARGETS = [
    ("chrome", "staging"),
    ("firefox", "canary"),
]


@pytest.fixture(params=TARGETS, ids=[f"{b}-{e}" for b, e in TARGETS])
def remote_driver(request):
    browser, stage = request.param
    opts = FirefoxOptions() if browser == "firefox" else Options()
    opts.add_argument("--headless=new" if browser == "chrome" else "-headless")
    if hasattr(opts, "add_argument"):
        opts.add_argument("--no-sandbox")
    opts.set_capability("browserName", browser)
    opts.set_capability("env:stage", stage)          # 匹配 Node stereotype 的自定义键
    opts.set_capability("se:name", f"回归_{browser}_{stage}")   # Grid UI 里可读的会话名

    driver = webdriver.Remote(command_executor=GRID_URL, options=opts)
    yield driver
    driver.quit()


def test_login_then_greeting(remote_driver, base_url):
    remote_driver.get(base_url + "login.html")
    # ... 与本地用例完全相同的页面对象逻辑
    assert remote_driver.title == "登录 - 订单系统"
```

这套写法的价值在于：**用例代码零改动**，「换浏览器 / 换环境」变成 capabilities 的事。上线前先确认 Grid 真的有对应 slot：

```bash
curl -s http://127.0.0.1:4444/status | python -m json.tool | head -40
```

## 最佳实践与踩坑记录

1. **按「1 会话 = 1 CPU / 1GB」做容量估算，Node 宁可小而多。** 官方文档明确建议用多个小 Node 而不是一个大 Node：隔离性好，单个 Node 挂掉不影响全局。
2. **镜像 tag 固定到具体版本。** `latest` 会让浏览器与驱动随镜像漂移，前一天全绿的套件第二天集体失败；升级走显式的版本变更提交。
3. **容器里必须显式设置 `SE_NODE_MAX_SESSIONS` 并同时开启 `SE_NODE_OVERRIDE_MAX_SESSIONS=true`。** 前者默认只有 1，后者不开启时前者不生效——这是「容器里跑得比本地慢」的常见原因。
4. **会话结束一律 `quit()`，并在 fixture teardown 里保证执行。** Grid 只有收到 quit 才会释放 slot；泄漏的会话会一直占位，表现为后到的用例排队超时。
5. **跨机部署先验网络，再调配置。** Node 注册依赖 Event Bus 的 4442/4443 与 Node 自身端口；本机实测「连不上」的表现就是 `Connection refused`，用 `/status` 端点做健康检查比看日志快。
6. **并行前先做隔离审计。** 下载目录、profile、日志、业务数据、账号租户五项都要按 worker 隔离；`-n` 之后用例顺序不可控，任何依赖顺序的用例必须重写。

坑 1：`docker pull` 或下载 `selenium-server.jar` 长时间无响应

结论：本机实测 `docker pull selenium/standalone-chrome` 等待 35 分钟仍未完成镜像层解压；从 GitHub Releases 拉 56MB 的 `selenium-server-4.51.0.jar` 速率约 4KB/s，7 分钟只拿到 1.6MB。**这属于网络环境问题，不是配置问题。**

原因：Grid 服务端分发渠道（Docker Hub 与 GitHub Releases）在本机网络下被严重限速，Maven Central 上 `org.seleniumhq.selenium:selenium-server` 的索引同样过期（metadata 停在 2019 年）。

解法：换网络/镜像源（国内可用 Docker 镜像加速器），或直接用 `selenium/standalone-chrome` 的国内镜像仓库；实在装不上就先用本地 `webdriver.Chrome()` 做开发，CI 上再上 Grid。本篇相关章节因此标注为「未在本机验证」。

坑 2：容器里 Node 只跑 1 个会话，并发上不去

结论：`SE_NODE_MAX_SESSIONS=4` 设了但实际并发仍是 1。

原因：官方 `ENV_VARIABLES.md` 说明容器镜像里 `SE_NODE_MAX_SESSIONS` 默认就是 1，且必须配合 `SE_NODE_OVERRIDE_MAX_SESSIONS=true` 才会突破「每 CPU 一会话」的推荐上限。

解法：两个变量一起设；并注意突破推荐上限后稳定性由自己负责，机器资源不足时会表现为随机会话创建失败。

坑 3：跨机 Node 注册不上，Hub 日志只有心跳超时

结论：Node 启动正常但 Grid UI 里看不到该节点。

原因：Node 通过 Event Bus 向 Hub 注册，之后 Distributor 还要反向 HTTP 访问 Node 的 `/status`；只放开 4444 而没放开 4442/4443 或 Node 端口时，注册握手走不完。

解法：按官方说明放开 Event Bus 的发布/订阅端口与 Node 端口；Hub 用非默认端口时显式传 `--publish-events` / `--subscribe-events`，不要依赖默认推导。

坑 4：`-n 8` 比 `-n 4` 更慢

结论：本机实测 8 核机器上 9 条用例 `-n 4` 用 62.03 秒，`-n 8` 用 73.73 秒，worker 变多反而更慢。

原因：每个 worker 都拉起完整浏览器进程，8 个并行时 CPU 与磁盘 I/O 争抢，单会话耗时上升，抵消了并行收益。

解法：worker 数从 CPU 数的一半起步压测（本机甜点是 4），并把优化重心放到「减少浏览器重启次数」上——用会话级驱动 + 用例间清理 Cookie。

坑 5：并行后用例互相串台，随机失败

结论：单独跑全绿，`-n 4` 之后出现随机的元素找不到、金额对不上、文件被覆盖。

原因：下载目录、浏览器 profile、日志文件写的是同一路径；业务数据也可能共用同一账号/订单。

解法：按 `worker_id(request)` 拆出 `gw0/gw1/...` 子目录（本机实测两个 worker 各自落到自己的 downloads 与 profile 目录），业务数据上给每个 worker 分配独立租户或独立账号。
