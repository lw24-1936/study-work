## 概述

UI 自动化的失败有两大类：**真失败**（功能坏了）和**假失败**（时序、环境、隔离问题）。假失败就是 flaky，它比真失败更贵——团队会开始「重跑一次看看」，最终整套用例失去可信度。官方文档把 flaky 的首要原因指向时序：浏览器准备好了、Selenium 代码先执行了，或者反过来。本机实测把这个规律量化得很直白：`implicitly_wait(5)` 与 `WebDriverWait(2)` 混用时，一次 2 秒超时的等待实际花了 **5.07 秒**——等待策略写错不仅不稳，还会成倍拖慢套件。

本篇把稳定性拆成四块：等待策略（时序）、反自动化识别与合规边界（能不能被测）、人类行为模拟（像不像真实用户）、失败重试与诊断（失败之后能不能查）。最后一节是常见报错的排查总表，每一条都有本机复现的真实报错原文。

```text
本篇主线：
1. 等待策略 —— 隐式等待 vs 显式等待 vs 自定义条件，混用会放大耗时（实测 2s 变 5.07s）
2. 反自动化识别 —— navigator.webdriver 等检测面实测数据，以及必须遵守的合规边界
3. 人类行为模拟 —— 随机延迟、逐字符输入、滚动到元素，以及与稳定性的取舍
4. 失败重试 —— 哪些异常可重试、哪些绝不能重试，指数退避的实现
5. 诊断 —— 截图 + DOM + 控制台日志 + 网络日志四件套（本机实测采集结果）
6. 排查总表 —— NoSuchElement / ElementClickIntercepted / Stale / Timeout / SessionNotCreated 等
```

本机验证环境：Ubuntu 24.04、Python 3.14.7、selenium 4.51.0、Chrome for Testing 151.0.7922.34。文中所有 `text` 块均为真实输出，**包含刻意复现的异常原文**。

## 等待策略 隐式 显式与 Fluent

三种等待的定位很清楚：

| 方式 | 写法 | 作用范围 | 建议 |
|---|---|---|---|
| 隐式等待 | `driver.implicitly_wait(5)` | 全局，作用于**所有** `find_element` | 少用；一旦设置就影响全流程 |
| 显式等待 | `WebDriverWait(d, 10).until(EC.xxx, message=...)` | 单点，条件明确 | 主力方案，等待条件必须可读 |
| Fluent 等待 | `WebDriverWait(d, 10, poll_frequency=0.5, ignored_exceptions=(...))` | 单点，可调轮询频率与忽略异常 | 需要控制轮询节奏时用 |

官方文档对 `pageLoadStrategy` 的说明也顺带解释了为什么「导航完成」不等于「页面可用」：`readyState == complete` 只表示 HTML 里的资源加载完了，SPA 之后还会用 JS 继续改 DOM。所以显式等待才是主力。

```python
from selenium.webdriver.common.by import By
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

d.get(BASE)
d.find_element(By.ID, "add-box").click()      # 触发 800ms 后插入 #late-box

# 显式等待：条件明确、超时有意义
el = WebDriverWait(d, 5).until(
    EC.presence_of_element_located((By.ID, "late-box")),
    message="800ms 后应出现 #late-box")
print("拿到:", el.text)

# Fluent：自定义轮询节奏，忽略瞬时异常
wait = WebDriverWait(d, 10, poll_frequency=0.5,
                     ignored_exceptions=(Exception,))
wait.until(lambda drv: len(drv.find_elements(By.CLASS_NAME, "late")) == 1)
```

常用 `expected_conditions` 与适用场景：

| 条件 | 等待的是 | 典型用途 |
|---|---|---|
| `presence_of_element_located` | 元素出现在 DOM | 只关心存在，不关心可见 |
| `visibility_of_element_located` | 元素可见（宽高 > 0 且非 hidden） | 要读文本或截图 |
| `element_to_be_clickable` | 可见且可点击 | 点击前的标准等待 |
| `invisibility_of_element_located` | 元素消失 | 等 loading 遮罩消失 |
| `text_to_be_present_in_element` | 元素文本包含指定串 | 等状态文本变化 |
| `number_of_windows_to_be` | 窗口句柄数量 | 等新标签页打开 |
| `alert_is_present` | 原生弹窗出现 | 处理 alert/confirm |
| `staleness_of` | 元素失效 | 等旧节点被替换 |
| `title_is` / `title_contains` | 标题 | 页面跳转完成 |

**最需要警惕的坑是隐式等待与显式等待混用。** 本机实测一组对照：

```text
implicitly_wait(5) + WebDriverWait(2)：实际耗时 5.07s（预期约 2s，被隐式等待放大）
只用 WebDriverWait(2)：实际耗时 2.05s
```

原因不难理解：W3C 规定显式等待内部也是靠轮询 `find_element` 实现的，而 `find_element` 自己会先吃满 `implicitly_wait`。于是「超时 2 秒」变成了「每次轮询最长 5 秒」，最终耗时由隐式等待主导。另一个后果是**这个坑在慢环境里更明显**：CI 上每次多花几秒，几百条用例就是几十分钟。

同样要避免的还有「用 sleep 兜底」——本机实测里 800ms 插入的元素，用 `WebDriverWait(5)` 只等了 1.09 秒就返回；而固定 `sleep(3)` 在快机器上浪费 2 秒，在慢机器上又可能不够。

```text
要点：
- 等待主力是显式等待，条件必须可读且带 message
- 隐式等待是全局的，与显式等待混用会让超时被放大（实测 2s -> 5.07s）
- Fluent 等待用于需要自定义轮询频率或忽略瞬时异常的场景
- pageLoadStrategy 只保证资源加载完成，SPA 的动态内容仍要显式等待
- 用 invisibility_of_element_located 等 loading 遮罩消失，比等固定秒数可靠
- 条件等待返回元素后可继续链式操作，无需二次查找
```

## 反自动化识别与合规边界

**先把边界说清楚**：本节内容是**防御性知识**——你的被测系统自己会检测「当前是不是自动化浏览器」，测试环境里需要知道有哪些检测点、为什么用例在本地过、在 CI 挂；或你的站点要确认自动化流量能被识别出来。把 Selenium 用来绕过**未授权站点**的风控、ToS 或访问限制去抓取数据，不在本文范围，也不应该做。

浏览器与驱动会留下若干可观测特征，本机实测（同一台机器、同一个 Chrome 151，只改启动参数）：

```text
[默认启动]
    navigator.webdriver = True
    navigator.plugins.length = 5
    navigator.languages = ["zh-CN"]
    window.chrome 存在 = object
    navigator.userAgent = Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) HeadlessChrome/151.0.0.0 Safari/537.36
    window.outerWidth==0 = False
    Notification.permission = default
    navigator.maxTouchPoints = 0
[加 AutomationControlled 关闭开关]
    navigator.webdriver = False
    ... 其余各项完全相同
```

结论很明确：**`navigator.webdriver` 是唯一被这个开关改变的特征**；`userAgent` 里的 `HeadlessChrome` 标记、插件数量、语言列表等其余项都没变。所以「加一个 flag 就伪装成真人」是不成立的——真实的检测体系会同时看 UA、WebGL 指纹、行为时序、IP 与账号画像。

常见的检测面与工程上对应的注意点：

| 检测面 | 自动化下的典型表现 | 说明 |
|---|---|---|
| `navigator.webdriver` | 默认 `true` | W3C 标准字段，规范要求自动化会话置为 `true` |
| User-Agent | 含 `HeadlessChrome` | 无头模式的 UA 标记；可用 `--user-agent` 覆盖，但覆盖行为本身也可被识别 |
| CDP/调试端口 | 存在 `Runtime.enable` 等 CDP 会话 | 页面可通过 `console.debug` 的时间差等方式探测 |
| 事件可信度 | `isTrusted` 为 `false` 的合成事件 | `execute_script` 派发的点击与真实点击可区分 |
| 行为时序 | 精确到毫秒的固定节拍 | 见下一节「人类行为模拟」 |
| 环境一致性 | 无 GPU 渲染的 WebGL 指纹 | 无头容器里 WebGL 指纹与真实设备差异明显 |

```python
# 工程上真正有用的做法：把「被测环境是自动化」显式告知被测方，而不是藏着
opts = Options()
opts.add_argument("--headless=new")
opts.add_argument("--user-agent=MyApp-E2E/1.0 (contact: qa@example.com)")
opts.set_capability("se:name", "E2E_回归_ci")

# 需要时（例如被测站点对自动化有门槛）关闭自动化开关，便于测试环境对齐
opts.add_argument("--disable-blink-features=AutomationControlled")

# CI 日志里能区分自动化流量，出问题好定位
opts.add_experimental_option("prefs", {"credentials_enable_service": False})
```

```text
要点：
- navigator.webdriver 实测默认 true，--disable-blink-features=AutomationControlled 可变为 false
- 该开关只影响这一项；UA 里的 HeadlessChrome 等特征不受影响
- 真实检测体系看 UA、指纹、事件 isTrusted、行为时序、IP 与账号画像
- 合规边界：只对自有/已授权系统使用，不用于绕过他人风控与 ToS
- 更稳的做法是给测试环境开白名单或用专门测试账号，而不是对抗检测
- 把自动化标识显式写进 UA 或 se: 元数据，便于线上排查误伤
```

## 人类行为模拟与稳定性权衡

「像人一样操作」在测试语境下的真实目的通常不是伪装，而是**复现真实用户会触发的边界**：用户会先滚动再点、会在输入框逐字敲、会在点击之间停顿。很多前端缺陷（防抖、快速连点、滚动加载）只在这样的节奏下出现。

```python
import random
import time

from selenium.webdriver.common.action_chains import ActionChains
from selenium.webdriver.common.by import By
from selenium.webdriver.common.keys import Keys

rng = random.Random(20261014)      # 固定种子：可复现，别用全局 random


def human_pause(low=0.15, high=0.45):
    """在动作之间插入随机停顿；固定种子保证同一次 seed 下节奏可复现。"""
    time.sleep(rng.uniform(low, high))


def human_type(element, text, low=0.03, high=0.1):
    """逐字符输入，模拟真实键盘节奏。"""
    for ch in text:
        element.send_keys(ch)
        time.sleep(rng.uniform(low, high))


def human_click(driver, element):
    """先滚动到元素、再悬停、再点击——顺序与真实用户一致。"""
    ActionChains(driver).scroll_to_element(element).perform()
    human_pause()
    ActionChains(driver).move_to_element(element).pause(rng.uniform(0.05, 0.2)).click().perform()
```

**必须同时看到代价**：三次随机停顿就让一条用例多花一秒，几百条用例会把套件拖到不可接受。合理的做法是**只在必要处模拟**，而不是全局开启：

| 场景 | 是否需要人类化节奏 | 理由 |
|---|---|---|
| 常规 CRUD 回归 | 不需要 | 显式等待已足够，随机停顿只增加耗时 |
| 防抖/节流输入框、搜索联想 | 需要逐字符输入 | 一次性 `send_keys` 与真实输入的前端行为不同 |
| 滚动加载、无限列表 | 需要滚动到元素再操作 | 不滚动时元素可能不可交互 |
| 快速连点、双击误触 | 需要控制点击间隔 | 前端可能没有防重逻辑，是真实缺陷 |
| 风控/行为分析相关被测系统 | 需要但**需授权** | 见上一节的合规边界 |

```text
要点：
- 人类化节奏的目的是复现真实用户触发的边界，不是伪装身份
- 随机数必须带固定种子，否则用例不可复现，flaky 无法定位
- 只在必要场景模拟（防抖输入、滚动加载、连点），全局模拟会拖垮套件
- 逐字符输入能暴露一次性 send_keys 触达不到的前端缺陷
- scroll_to_element 后再点击，比直接点击稳定得多
- 模拟带来的额外耗时要用「减少浏览器重启」来抵消，别用增加超时来抵消
```

## 失败重试 日志与诊断

重试的唯一正确用法是**只重试瞬时/环境类异常，绝不重试业务断言**。把 `AssertionError` 也重试，等于把真缺陷藏起来。

```python
import functools
import logging
import time

from selenium.common import exceptions as se

log = logging.getLogger("kb.selenium.retry")

# 可重试：瞬时/环境类
RETRYABLE = (
    se.TimeoutException,                  # 等超时，可能是环境变慢
    se.StaleElementReferenceException,    # 节点被前端重渲染替换
    se.ElementClickInterceptedException,  # 被临时遮罩挡住
    se.WebDriverException,                # 连接类错误（谨慎使用，见坑 3）
)
# 不可重试：业务与契约类
FATAL = (AssertionError, se.NoSuchElementException, se.InvalidSelectorException)


def retry(times=3, delay=0.5, exceptions=RETRYABLE):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*a, **kw):
            for attempt in range(1, times + 1):
                try:
                    return fn(*a, **kw)
                except exceptions as e:
                    if attempt == times:
                        log.error("%s 重试 %s 次仍失败", fn.__name__, times)
                        raise
                    log.warning("%s 第 %s/%s 次失败(%s)，%.1fs 后重试",
                                fn.__name__, attempt, times, type(e).__name__, delay * attempt)
                    time.sleep(delay * attempt)     # 退避：0.5s -> 1.0s
        return wrapper
    return deco
```

本机实测的完整日志（含成功恢复与最终失败两条路径）：

2026-10-15 21:59:22,639 WARNING kb.selenium.retry: 第 2/3 次尝试失败: 第 2 次读到的还是 loading
重试装饰器返回: 第 3 次读到 ready
2026-10-15 21:59:23,239 WARNING kb.selenium.retry: 第 1/2 次尝试失败: 恒定失败

实现上有三个细节：一是**退避不能是固定间隔**，`delay * attempt` 给服务端留恢复时间；二是**重试只包幂等操作**，「提交订单」这种非幂等动作重试可能产生两笔订单，要重试就得先确认业务侧有幂等键；三是**日志里必须带尝试次数与异常类型**，否则线上看到「重试了」却不知道在重试什么。

**失败诊断四件套**：截图、DOM 快照、控制台日志、网络日志。前三个用 WebDriver API 就够，第四个靠 `goog:loggingPrefs` 打开 performance 日志后解析 `Network.responseReceived`。

```python
import json
import pathlib

from selenium import webdriver
from selenium.webdriver.chrome.options import Options

OUT = pathlib.Path("/root/.hermes/cache/scratch/selb_188_diag")


def make_driver():
    opts = Options()
    opts.binary_location = "/root/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome"
    opts.add_argument("--headless=new")
    opts.add_argument("--no-sandbox")
    opts.add_argument("--disable-dev-shm-usage")
    opts.add_argument("--window-size=1440,900")
    # 打开控制台与性能日志通道
    opts.set_capability("goog:loggingPrefs", {"browser": "ALL", "performance": "ALL"})
    return webdriver.Chrome(options=opts)


def collect(driver, name):
    """采集诊断四件套并落盘，返回一份摘要。"""
    OUT.mkdir(parents=True, exist_ok=True)
    png = OUT / f"{name}.png"
    html = OUT / f"{name}.html"
    driver.save_screenshot(str(png))
    html.write_text(driver.page_source, encoding="utf-8")

    browser_logs = driver.get_log("browser")
    severe = [e for e in browser_logs if e["level"] == "SEVERE"]

    network = []
    for entry in driver.get_log("performance"):
        msg = json.loads(entry["message"])["message"]
        if msg["method"] == "Network.responseReceived":
            r = msg["params"]["response"]
            network.append((r["status"], r["url"]))

    return {
        "screenshot": str(png),
        "dom": str(html),
        "dom_bytes": html.stat().st_size,
        "console_entries": len(browser_logs),
        "console_severe": [e["message"][:80] for e in severe],
        "network_responses": len(network),
        "non_2xx": [f"{s} {u}" for s, u in network if not 200 <= s < 300],
    }
```

把这套采集挂进 pytest 的失败钩子（`pytest_runtest_makereport`，**必须写在 `conftest.py`**），失败时自动产出附件，和 18.6 里的截图钩子合成一个：

```python
@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    if report.when != "call" or not report.failed:
        return
    drv = item.funcargs.get("driver")
    if drv is None:
        return
    try:
        summary = collect(drv, item.name.replace("/", "_").replace(" ", "_"))
        report.sections.append(("selenium-diagnostics", json.dumps(summary, ensure_ascii=False)))
    except Exception as exc:
        report.sections.append(("selenium-diagnostics", f"采集失败: {exc}"))
```

```text
要点：
- 只重试瞬时/环境异常，AssertionError 与 NoSuchElement 必须立刻失败
- 退避用 delay * attempt，不要固定间隔；并对非幂等操作额外确认幂等键
- 重试日志必须带尝试次数与异常类型，否则无法判断在重试什么
- 诊断四件套：截图 + page_source + 控制台日志 + 网络日志
- 网络日志靠 goog:loggingPrefs 的 performance 通道解析 Network.responseReceived
- 采集代码要 try/except，浏览器已崩时不能让钩子盖掉原始失败
```

## 常见报错排查总表

下表每一条都在本机复现过，报错原文见 `text` 块。

| 异常 | 触发条件（本机复现方式） | 根因 | 解法 |
|---|---|---|---|
| `NoSuchElementException` | 直接找 800ms 后插入的元素 | 元素尚不存在 / 定位范围错（iframe 内） | 用 `WebDriverWait` + `presence_of_element_located`；先确认是否在 iframe 里 |
| `ElementClickInterceptedException` | 按钮上有 z-index 更高的遮罩 | 命中测试命中了别的元素 | 等遮罩消失（`invisibility_of_element_located`）；确属设计缺陷时用 JS 点击并注明原因 |
| `StaleElementReferenceException` | 节点被前端整段替换后仍用旧引用 | DOM 节点已脱离文档 | 重新定位元素；或封装「存 locator + 用时重新查找」的元素包装器 |
| `TimeoutException` | `WebDriverWait(2)` 等永不出现的元素 | 条件始终不满足 | 检查等待条件是否正确；确认页面真的会进入该状态 |
| `MoveTargetOutOfBoundsException` | 元素在视口外做相对位移 | 指针落点超出视口 | 加大 `--window-size`，或先 `scroll_to_element` |
| `InvalidSelectorException` | `By.CSS_SELECTOR, "div::nth-child(2)"` | 选择器语法非法 | 修正选择器；CSS 里不要写 `::` 伪元素 |
| `NoSuchWindowException` | `close()` 后未切回有效句柄 | 当前句柄已销毁 | `close()` 后立即 `switch_to.window(main)` |
| `UnexpectedAlertPresentException` | 弹窗未处理就执行其它命令 | 原生弹窗阻塞了会话 | 先 `switch_to.alert.accept()/dismiss()` |
| `InvalidCookieDomainException` | 在 `about:blank` 上 `add_cookie` | Cookie 域与当前文档不匹配 | 先导航到目标域再写 Cookie |
| `SessionNotCreatedException` | 驱动与浏览器大版本不匹配 | 驱动/浏览器版本错配 | 让 Selenium Manager 自动匹配；或按官方文档手动对齐版本与可执行权限 |
| `ConnectionRefusedError` / `MaxRetryError` | 指向未启动的 Grid | 服务端未运行或端口不通 | 先探 `/status`，再排查网络与容器端口 |
| `AttributeError: Keys has no attribute 'chord'` | 使用 `Keys.chord` | 该 API 已从 4.51 移除 | 改用 `key_down` / `key_up` |

排查顺序建议固定成一条流水线，避免每次都从头猜：

```text
1. 是环境问题吗？      -> 浏览器是否启动、Grid /status 是否 ready、网络是否通
2. 是上下文问题吗？    -> 是否在 iframe 里、是否切换了窗口、是否有未处理弹窗
3. 是时序问题吗？      -> 换成显式等待、去掉 sleep、检查隐式等待是否在拖后腿
4. 是选择器问题吗？    -> 选择器语法、是否唯一、是否被前端重渲染
5. 是业务问题吗？      -> 到这一步才是真的功能缺陷，把诊断四件套附上提 bug
```

```text
要点：
- 先分类再修：环境 -> 上下文 -> 时序 -> 选择器 -> 业务，顺序不要跳
- NoSuchElement 与 Timeout 的差别在于「等没等」，先看有没有等
- 点击类异常优先怀疑遮罩与命中测试，别急着用 JS 点击
- Stale 用「存 locator 重新查找」解决，比缓存 WebElement 稳
- Grid 相关先探 /status，日志里的 Connection refused 就是端口没通
- 每条报错都在本地复现一次再改代码，改完把复现脚本留作回归
```

## 应用场景实战

### 场景一：显式等待 + 分类重试的稳定下单流程

把「等动态元素、处理被遮挡按钮、连续加购」串成一条流程，等待全部用显式条件，只有可重试异常才进重试。

```python
import functools
import logging
import time

from selenium import webdriver
from selenium.common import exceptions as se
from selenium.webdriver.chrome.options import Options
from selenium.webdriver.common.by import By
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

logging.basicConfig(level=logging.INFO,
                    format="%(asctime)s %(levelname)s %(name)s: %(message)s")
log = logging.getLogger("kb.selenium.flow")

RETRYABLE = (se.TimeoutException, se.StaleElementReferenceException,
             se.ElementClickInterceptedException)


def retry(times=3, delay=0.5, exceptions=RETRYABLE):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*a, **kw):
            for attempt in range(1, times + 1):
                try:
                    return fn(*a, **kw)
                except exceptions as e:
                    if attempt == times:
                        raise
                    log.warning("%s 第 %s/%s 次失败(%s)", fn.__name__, attempt, times,
                                type(e).__name__)
                    time.sleep(delay * attempt)
        return wrapper
    return deco


class Dashboard:
    def __init__(self, driver):
        self.driver = driver
        self.wait = WebDriverWait(driver, 10)

    def open(self):
        self.driver.get(BASE + "dashboard.html?user=admin")
        self.wait.until(EC.title_is("订单看板"))
        return self

    @retry(times=3, delay=0.3)
    def add_to_cart(self, order_id):
        row = self.wait.until(EC.presence_of_element_located(
            (By.CSS_SELECTOR, f'[data-order-id="{order_id}"]')))
        btn = row.find_element(By.CLASS_NAME, "add-btn")
        self.wait.until(EC.element_to_be_clickable(btn)).click()
        return int(self.driver.find_element(By.ID, "cart-count").text)

    def trigger_late_box(self):
        self.driver.find_element(By.ID, "add-box").click()
        return self

    def wait_late_box(self, timeout=5):
        return self.wait.until(
            EC.presence_of_element_located((By.ID, "late-box"))).text
```

本机真实运行结果：

```text
加购一单后购物车: 1
加购两单后购物车: 2
业务断言通过
动态元素文本文案: 迟到的元素
正常点击被拦截（预期）: Message: element click intercepted: Element <button id="covered-btn" o ...
JS 兜底点击结果: 真实按钮被点击
```

这段流程展示了两条实践：**加购这种幂等操作套重试**；**被遮罩的按钮先按正常路径点、命中 `ElementClickInterceptedException` 后再用 JS 兜底，并把兜底原因写进日志**，而不是一上来就用 JS 点击把问题掩盖掉。

### 场景二：失败诊断包（截图 + DOM + 控制台 + 网络日志）

线上/CI 出现偶发失败时，光有一张截图经常定位不了。用 `collect()` 一次性把四类证据落盘，附在 pytest 报告里。

```python
# conftest.py（节选）
import json

import pytest

from diagnostics import collect      # 上文实现的采集函数


@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    if report.when != "call" or not report.failed:
        return
    drv = item.funcargs.get("driver")
    if drv is None:
        return
    try:
        summary = collect(drv, item.name.replace("/", "_").replace(" ", "_"))
        report.sections.append(("selenium-diagnostics",
                                json.dumps(summary, ensure_ascii=False, indent=2)))
    except Exception as exc:
        report.sections.append(("selenium-diagnostics", f"采集失败: {exc}"))
```

## 最佳实践与踩坑记录

1. **显式等待当主力，隐式等待能不设就不设。** 本机实测两者混用会把 2 秒超时放大到 5.07 秒；慢环境里这个放大效应直接决定套件能否跑完。
2. **所有等待都带可读条件与 `message`。** 超时异常里能看到业务语义，比盯着一行 `TimeoutException: Message:` 空消息省太多排查时间。
3. **重试要分类：只重试瞬时/环境异常。** `AssertionError`、`NoSuchElementException` 重试等于掩盖缺陷；非幂等操作重试前先确认业务侧有幂等键。
4. **失败必须留证，且证据要多样。** 截图 + DOM + 控制台 + 网络日志四件套，缺哪一样都会在某个偶发场景下抓瞎。
5. **随机性必须可复现。** 人类化模拟的随机停顿用固定种子的 `random.Random(seed)`，否则 flaky 无法定位到具体节奏。
6. **先分类再动手排查。** 环境 -> 上下文 -> 时序 -> 选择器 -> 业务，按这个顺序排能避免在「其实是 iframe」的问题上改三小时等待时间。

坑 1：`implicitly_wait` 与 `WebDriverWait` 混用，超时时间被悄悄放大

结论：本机实测设定 `implicitly_wait(5)` 后又做 `WebDriverWait(2)`，一次本该 2 秒的等待实际耗时 5.07 秒；去掉隐式等待后同一操作 2.05 秒。

原因：显式等待靠轮询定位元素实现，而每次定位都会先吃满全局隐式等待，最终耗时由隐式等待主导。

解法：二选一——要么完全不设隐式等待、全部用显式等待；要么反过来只依赖隐式等待（不推荐，条件不可读）。仓库级别的最佳实践是禁止 `implicitly_wait`，在评审里拦住它。

坑 2：把 `AssertionError` 也加进重试列表，真缺陷被藏起来

结论：本机实测对恒定失败的函数重试 2 次，最终仍抛出 `AssertionError` 且调用次数为 2——如果重试次数再高一些，或者断言本身依赖随机数据，就会出现「重跑就绿」的假象。

原因：断言失败表达的是业务契约不满足，不是环境抖动；重试只会让它在某次侥幸通过。

解法：重试列表只放 `TimeoutException` / `StaleElementReferenceException` / `ElementClickInterceptedException` 这类瞬时异常；断言失败立刻抛出并留证。

坑 3：`except WebDriverException` 当作通用重试，把致命错误也吞了

结论：`WebDriverException` 是 Selenium 异常体系的基类，包含了 `NoSuchElementException`、`InvalidSelectorException`、`SessionNotCreatedException` 等一票「重试也没用」的错误。

原因：基类捕获的语义是「任何 WebDriver 错误」，与「可恢复的瞬时错误」完全不等价。

解法：显式列举可重试的具体异常类型；确实需要按基类兜底时，先判断子类型再决定是否重试，并在日志里打出具体异常类名。

坑 4：固定 `sleep` 兜底等动态内容，快机器慢、慢机器还是不够

结论：本机实测等待 800ms 后插入的元素，`WebDriverWait(5)` 只用了 1.09 秒就返回；固定 `sleep(3)` 在快机器上白等近 2 秒，在慢 CI 上仍可能不够。

原因：`sleep` 与页面实际状态无关，是纯粹的时间赌注。

解法：换成显式等待（`presence_of_element_located` / `visibility_of_element_located`）；只有「等待没有可观测信号」的场景（例如接口没有回调）才考虑轮询 + 超时，而不是裸 sleep。

坑 5：`execute_script` 点击被当成「解决遮挡」的通用手段

结论：本机实测被遮罩按钮的常规点击会抛 `ElementClickInterceptedException`，改用 JS 点击后按钮回调正常执行、用例变绿——但真实用户根本点不到这个按钮。

原因：JS 点击绕过 WebDriver 的可点击性检查（命中测试、可见性、可交互性），等价于「强制触发」。

解法：优先等遮罩消失（`invisibility_of_element_located`）再点；只有在确认遮罩是测试环境专有（例如 mock 广告位）时才用 JS 兜底，并在代码注释里写明原因。
