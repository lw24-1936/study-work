## 概述

定位是 Selenium 里唯一无法被框架自动处理掉的事情：等待、重试、截图都能封装，但「这个按钮用什么选择器找」必须根据页面的 DOM 结构决定。定位器写得好，用例改版后不用动；写得差，页面加一个广告位就能让全量用例红一片。Selenium 提供 8 种传统定位策略，外加 Selenium 4 引入的相对定位（relative locator），本篇把它们的语义、边界与选型讲清楚。

```text
本篇主线：
1. 八种策略 —— id / name / class name / tag name / link text / partial link text / css / xpath
2. CSS 选择器 —— 后代、属性、^= $= *=、:nth-child、:not()、:has()；浏览器原生支持，速度最快
3. XPath —— 轴（父/子/兄弟）、函数（text()/contains()/starts-with()/normalize-space()）、绝对与相对
4. find_element 与 find_elements —— 返回单个 vs 返回列表、找不到时的两种行为、两种选择器异常
5. 相对定位 —— locate_with(...).above/below/to_left_of/to_right_of/near，near 半径 50px
6. 稳定性 —— 优先 data-testid/id，禁绝对路径与自动生成 id，容器限定 + 数量断言做自检
```

本机实测环境：selenium 4.51.0 + Chrome for Testing 151.0.7922.34（headless），页面为本地 `http.server` 托管的练习页。下文所有 `text` 块都是本机真实运行输出，包含**相对定位命中错元素**这类失败结果，也原样保留。

## 八种定位策略

官方文档把这 8 种称为「传统定位器」（traditional locators）。它们全部挂在 `By` 上，作为 `find_element` 的第一个参数。

| 策略 | 常量 | 语义 | 注意 |
|---|---|---|---|
| id | `By.ID` | `id` 属性完全匹配 | 最稳，优先用 |
| name | `By.NAME` | `name` 属性完全匹配 | 同名元素可能多个 |
| class name | `By.CLASS_NAME` | class 属性**包含**该值 | **传复合类名会报错** |
| tag name | `By.TAG_NAME` | 标签名 | 命中面太广，只适合取集合 |
| link text | `By.LINK_TEXT` | `<a>` 的可见文本完全匹配 | 只对 `<a>` 有效 |
| partial link text | `By.PARTIAL_LINK_TEXT` | `<a>` 可见文本包含 | 多个命中取第一个 |
| css selector | `By.CSS_SELECTOR` | CSS 选择器 | 浏览器原生，性能最好 |
| xpath | `By.XPATH` | XPath 表达式 | 能力最强，也最容易写脆 |

同一组元素上跑一遍八种策略：

```python
from selenium import webdriver
from selenium.webdriver.common.by import By

driver.get("http://127.0.0.1:8899/index.html")

print("By.ID            ->", driver.find_element(By.ID, "title").text)
print("By.NAME          ->", driver.find_element(By.NAME, "username").get_attribute("placeholder"))
print("By.CLASS_NAME    ->", driver.find_element(By.CLASS_NAME, "desc").text)
print("By.TAG_NAME      ->", driver.find_element(By.TAG_NAME, "h1").text)
print("By.LINK_TEXT     ->", driver.find_element(By.LINK_TEXT, "下一页").get_attribute("href"))
print("By.PARTIAL_LINK_TEXT ->", driver.find_element(By.PARTIAL_LINK_TEXT, "下一").text)
print("By.CSS_SELECTOR  ->", driver.find_element(By.CSS_SELECTOR, "#login-form #submit-btn").text)
print("By.XPATH         ->", driver.find_element(By.XPATH, '//button[@id="submit-btn"]').text)
```

本机真实输出：

```text
By.ID            -> Selenium 元素定位练习页
By.NAME          -> 请输入用户名
By.CLASS_NAME    -> 用于验证定位策略与等待机制
By.TAG_NAME      -> Selenium 元素定位练习页
By.LINK_TEXT     -> http://127.0.0.1:8899/page2.html
By.PARTIAL_LINK_TEXT -> 下一页
By.CSS_SELECTOR  -> 登录
By.XPATH         -> 登录
```

`By.CLASS_NAME` 的坑值得单独跑一次看报错原文——它只接受**单个**类名：

```python
driver.find_element(By.CLASS_NAME, "item item")   # 复合类名
driver.find_element(By.CLASS_NAME, "item")        # 单类名
```

```text
复合类名 -> InvalidSelectorException | Message: Compound class names are not allowed.; For documentation on this error, please visit: https://www.selenium.dev/documentation/webdriver/troubl
单类名 OK
```

选型上有个简单的优先级：**id / data-* 属性 > CSS 选择器 > XPath（相对、带稳定属性）> 文本定位 > 绝对 XPath**。官方测试实践文档也建议把定位器与查找动作分开声明（见本篇末尾的 Page Object 写法），而不是散落在用例里。

## CSS 选择器

CSS 选择器由浏览器原生解析，在同一定位器下通常比 XPath 快，语法也比 XPath 短。工程里 80% 的定位可以只用下面这张表里的语法：

| 语法 | 含义 | 示例 |
|---|---|---|
| `#id` | id 选择器 | `#submit-btn` |
| `.cls` | class 选择器 | `.product-card` |
| 空格 | 后代 | `#todo-list .item` |
| `>` | 直接子元素 | `#product-list > li` |
| `[attr]` / `[attr=v]` | 属性存在 / 相等 | `[data-id='2']` |
| `[attr^=v]` / `$=` / `*=` | 前缀 / 后缀 / 包含 | `[data-id^='1']` |
| `:nth-child(n)` | 第 n 个子元素（不看标签） | `#todo-list > li:nth-child(3)` |
| `:nth-of-type(n)` | 同类型中第 n 个 | `#todo-list li:nth-of-type(2)` |
| `:not(sel)` | 排除 | `li:not(.item)` |
| `:has(sel)` | 包含某后代/子元素（较新） | `div.field:has(> label#lbl-name)` |
| `a + b` / `a ~ b` | 相邻兄弟 / 后续所有兄弟 | `#pass + select` |

```python
print(len(driver.find_elements(By.CSS_SELECTOR, "ul#todo-list li.item")))
print(driver.find_element(By.CSS_SELECTOR, "[data-id='2']").text)
print(driver.find_element(By.CSS_SELECTOR, "[data-id^='1']").text)
print(driver.find_element(By.CSS_SELECTOR, "#todo-list > li:nth-child(3)").text)
print(driver.find_element(By.CSS_SELECTOR, "#todo-list li:nth-of-type(2)").text)
print(len(driver.find_elements(By.CSS_SELECTOR, "#todo-list li:not(.item)")))
print(driver.find_element(By.CSS_SELECTOR, "#pass + select").get_attribute("id"))
print(driver.find_element(By.CSS_SELECTOR, "input[type=password]").get_attribute("id"))
```

本机真实输出：

```text
后代选择器 ul#todo-list li.item -> 3
属性选择器 [data-id='2']       -> 跑回归
属性前缀 [data-id^='1']        -> 写测试用例
nth-child(3)                   -> 发报告
nth-of-type(2)                 -> 跑回归
:not(.item) 命中数             -> 0
兄弟组合 input + select        -> role
type 属性选择器 input[type=password] -> pass
```

`nth-child` 与 `nth-of-type` 的区别是 CSS 定位里最常见的一次踩错：前者按「父元素下所有子元素」计数，后者按「同标签的子元素」计数。如果列表项之间有空白文本节点、或者混了别的标签，两者的结果就会不同。

## XPath

XPath 的能力比 CSS 强（可以按文本、按父级、按任意轴定位），代价是可读性差、执行慢一些，而且很容易写成绝对路径那样的脆定位器。工程里按下面的用法分档：

| 用法 | 表达式 | 评价 |
|---|---|---|
| 绝对路径 | `/html/body/h1` | 禁用于业务代码，改一层 DOM 就挂 |
| 相对 + 属性 | `//input[@name='username']` | 推荐 |
| 文本匹配 | `//li[text()='跑回归']` | 可用，但对空白敏感（见下） |
| 文本包含 | `//li[contains(text(),'报告')]` | 推荐，容错好 |
| 前缀匹配 | `//div[starts-with(@id,'sta')]` | 推荐，对付动态 id |
| 位置索引 | `(//li)[2]` | 谨慎，顺序一变就错 |
| 父轴 | `//input[@id='user']/..` | 推荐 |
| 兄弟轴 | `//label[@for='user']/following-sibling::input` | 推荐 |
| 属性包含 | `//li[contains(@class,'item')]` | 推荐，等价于 CSS 多类名 |

```python
print(driver.find_element(By.XPATH, "/html/body/h1").text)
print(driver.find_element(By.XPATH, "//input[@name='username']").get_attribute("id"))
print(driver.find_element(By.XPATH, "//li[text()='跑回归']").get_attribute("data-id"))
print(driver.find_element(By.XPATH, "//li[contains(text(),'报告')]").text)
print(driver.find_element(By.XPATH, "//div[starts-with(@id,'sta')]").text)
print(driver.find_element(By.XPATH, "(//li)[2]").text)
print(driver.find_element(By.XPATH, "//input[@id='user']/..").get_attribute("id"))
print(driver.find_element(By.XPATH, "//label[@for='user']/following-sibling::input").get_attribute("id"))
print(len(driver.find_elements(By.XPATH, "//li[contains(@class,'item')]")))
```

本机真实输出：

```text
绝对路径 /html/body/h1        -> Selenium 元素定位练习页
相对路径 //input[@name='username'] -> user
文本匹配 //li[text()='跑回归'] -> 2
contains()  //li[contains(text(),'报告')] -> 发报告
starts-with() //div[starts-with(@id,'sta')] -> 初始状态
位置索引 (//li)[2]            -> 跑回归
父轴 //input[@id='user']/..   -> login-form
后面兄弟 //label[@for='user']/following-sibling::input -> user
contains(@class) //li[contains(@class,'item')] 命中数 -> 3
```

**`text()` 对空白字符敏感**，这是 XPath 文本定位最容易踩的坑。用两个内容相同、只有换行缩进不同的 `<li>` 实测：

```python
print(len(driver.find_elements(By.XPATH, "//li[text()='跑回归']")))
print(len(driver.find_elements(By.XPATH, "//li[normalize-space()='跑回归']")))
print(len(driver.find_elements(By.XPATH, "//li[contains(text(),'跑回归')]")))
```

```text
text()='跑回归'            命中: 1
normalize-space()='跑回归' 命中: 2
contains(text(),'跑回归')  命中: 2
```

注意 `.text` 属性拿到的仍是干净字符串（实测 `repr(.text)` 为 `'跑回归'`）——**Selenium 会归一化文本，XPath 不会**，所以用 `text()` 做判断时页面里的缩进换行会让它悄悄少命中一个。要么用 `normalize-space()`，要么用 `contains()`。

## find_element 与 find_elements

两个方法的差异不只是「一个还是多个」，还有**找不到元素时的行为截然不同**：

| 方法 | 返回 | 找不到时 | 典型用途 |
|---|---|---|---|
| `find_element` | 单个 `WebElement` | 抛 `NoSuchElementException` | 确定的单元素 |
| `find_elements` | `list[WebElement]`，可能为空 | 返回空列表 `[]`，不抛异常 | 集合、存在性判断 |

```python
items = driver.find_elements(By.CSS_SELECTOR, "#todo-list .item")
print(type(items).__name__, len(items), [e.text for e in items])
empty = driver.find_elements(By.ID, "not-exist")
print(empty, len(empty))
try:
    driver.find_element(By.ID, "not-exist")
except NoSuchElementException as e:
    print(type(e).__name__, str(e).splitlines()[0])
```

本机真实输出：

```text
find_elements 返回类型: list 数量: 3
全部文本: ['写测试用例', '跑回归', '发报告']
找不到时 find_elements 返回: [] 长度: 0
find_element 找不到时抛: NoSuchElementException
异常首行: Message: no such element: Unable to locate element: {"method":"css selector","selector":"[id="not-exist"]"}
```

另一类是**选择器本身写错**，这时抛的是 `InvalidSelectorException`，与「没找到」是两回事，重试等待也救不了：

```python
driver.find_element(By.CSS_SELECTOR, "li:::bad")   # 非法 CSS
driver.find_element(By.XPATH, "//li[")             # 非法 XPath
```

```text
非法 CSS -> InvalidSelectorException
非法 XPath -> InvalidSelectorException
```

判断元素是否存在，推荐用 `find_elements` 而不是 `try/except`——少一层异常处理，也不受隐式等待放大耗时的影响：

```python
def exists(driver, by, value) -> bool:
    return len(driver.find_elements(by, value)) > 0
```

## 相对定位

Selenium 4 引入的相对定位解决的是「这个元素本身没有稳定属性，但它旁边那个元素有」的场景。入口是 `locate_with(by, using)`，后面可以链式挂多个过滤条件：

| 方法 | 语义 | 官方说明 |
|---|---|---|
| `.above(el_or_locator)` | 在参考元素上方 | 基于渲染坐标 |
| `.below(el_or_locator)` | 在参考元素下方 | 基于渲染坐标 |
| `.to_left_of(...)` | 在参考元素左侧 | 基于渲染坐标 |
| `.to_right_of(...)` | 在参考元素右侧 | 基于渲染坐标 |
| `.near(...)` | 距离参考元素 **最多 50px** | 官方文档明确写死 50px，不是猜测值 |

参考元素既可以是已经找到的 `WebElement`，也可以是 `{By.ID: "xxx"}` 这样的定位器字典。

```python
from selenium.webdriver.support.relative_locator import locate_with

# 复选框在「延迟加载」按钮上方
driver.find_element(locate_with(By.XPATH, "//input[@type='checkbox']").above({By.ID: "load-btn"}))
# 段落标题在 h1 下方
driver.find_element(locate_with(By.TAG_NAME, "p").below({By.ID: "title"}))
# 「下一页」链接在「隐藏标题」按钮右侧
driver.find_element(locate_with(By.TAG_NAME, "a").to_right_of({By.ID: "hide-btn"}))
```

本机真实输出：

```text
above  -> remember
below  -> desc
to_right_of -> next-link
```

相对定位有两个必须知道的边界，第一条本机实测会直接失败：

```python
driver.find_element(locate_with(By.TAG_NAME, "p").to_left_of({By.ID: "todo-list"}))
```

```text
selenium.common.exceptions.NoSuchElementException: Message: Cannot locate relative element with: {'tag name': 'p'}
```

第二条更隐蔽：**相对定位判定的是渲染坐标，密集垂直排列的表单里会命中相邻元素**。用一张「label 与 input 上下堆叠、每个 field 一个 div」的真实表单实测，四种写法的结果如下：

```python
for label_id in ["lbl-name", "lbl-idcard", "lbl-phone", "lbl-email"]:
    below = driver.find_element(locate_with(By.CSS_SELECTOR, "input").below({By.ID: label_id}))
    near  = driver.find_element(locate_with(By.CSS_SELECTOR, "input").near({By.ID: label_id}))
    xpath = driver.find_element(By.XPATH, "//label[@id='%s']/following::input[1]" % label_id)
    css   = driver.find_element(By.CSS_SELECTOR, "div.field:has(> label#%s) input" % label_id)
    print("%-11s below=%-11s near=%-11s xpath=%-11s css=%-11s" % (label_id, below.get_attribute("name"),
          near.get_attribute("name"), xpath.get_attribute("name"), css.get_attribute("name")))
```

本机真实输出（`name` 就是命中的输入框）：

```text
lbl-name    below=idCard      near=holderName  xpath=holderName  css:has=holderName
lbl-idcard  below=email       near=holderName  xpath=idCard      css:has=idCard
lbl-phone   below=email       near=email       xpath=mobile      css:has=mobile
lbl-email   below=ERR:NoSuchElementException near=email        xpath=email       css:has=email
```

读法：`lbl-idcard` 应该在它下面的是 `idCard` 输入框，但 `below` 给出的是 `email`，`near` 给出的是最上面那个 `holderName`；只有 XPath 轴与 CSS `:has()` 四次全对。结论很直接——**相对定位是辅助手段（如「表格行里的删除按钮」），不要拿它当密集表单的主力定位器**。

链式组合是官方支持的写法，语义是「同时满足」：

```python
# 在邮箱下方、且在取消按钮右侧的提交按钮
locator = locate_with(By.TAG_NAME, "button").below({By.ID: "email"}).to_right_of({By.ID: "cancel"})
submit = driver.find_element(locator)
```

## 定位稳定性实践

定位器写脆了，后面所有稳定性工作都是白费。按下面这份清单约束自己：

| 优先级 | 定位方式 | 示例 | 说明 |
|---|---|---|---|
| 1 | 专用测试属性 | `[data-testid='login-submit']` | 与样式、文案解耦，前端可专门加 |
| 2 | 稳定 id | `#login-form` | 需要确认不是框架自动生成的 |
| 3 | 带语义的 CSS | `#product-list > li.product-card` | 容器限定 + 结构简单 |
| 4 | 相对 XPath / 轴 | `//label[text()='手机号']/following::input[1]` | 属性都不可靠时的退路 |
| 5 | 文本定位 | `By.LINK_TEXT, "下一页"` | 受 i18n、空白符、A/B 文案影响 |
| 6 | 索引定位 | `(//li)[2]` | 列表顺序会变，禁止进主干用例 |
| 禁用 | 绝对 XPath | `/html/body/div[3]/div[2]/button` | 任何布局调整都会挂 |

几个配套的工程习惯：

1. **限定容器**。同名元素在页面上经常出现多个（实测：模板区块里藏着同名 input），先定位到容器再找子元素，命中数从 2 变 1。

```python
driver.find_elements(By.NAME, "holderName")                              # 2 个（含隐藏模板）
driver.find_elements(By.CSS_SELECTOR, "#account-form input[name='holderName']")  # 1 个
```

```text
By.NAME 命中数: 2 | 第一个可见: True | 第二个可见: False
限定到 #account-form 后命中数: 1
```

2. **定位器集中声明**，用例里只引用常量名，改版时改一处：

```python
class LoginPage:
    """Page Object：定位器与动作分离，用例不直接写选择器。"""
    USERNAME = (By.CSS_SELECTOR, "#account-form input[name='holderName']")
    SUBMIT = (By.CSS_SELECTOR, "[data-testid='login-submit'], #submit-btn")  # CSS 联合备选

    def __init__(self, driver):
        self.driver = driver

    def login(self, user, pwd):
        self.driver.find_element(*self.USERNAME).send_keys(user)
        self.driver.find_element(*self.SUBMIT).click()
```

3. **对集合类定位做数量断言**。`find_element` 静默返回第一个命中，页面插入新节点后不会报错，只会悄悄点到别的元素；改成先 `find_elements` 断言数量，异常会在正确的地方暴露。

```python
cards = driver.find_elements(By.CSS_SELECTOR, "#product-list > li.product-card")
assert len(cards) == 4, "商品卡片数量变化，定位器或页面已改版，当前 %d" % len(cards)
```

4. **每条定位器在 CI 里有独立的冒烟检查**：把关键页面的定位器写成一份清单，每次上线前跑一遍「能否命中且唯一」的校验，比在全量用例里偶发失败要早得多。

## 应用场景实战

### 场景一：列表页批量提取与字段定位

真实工程里最常见的形态：先定位卡片集合，再在每张卡片**内部**定位字段（`card.find_element` 的作用域是卡片子树，这点很重要，否则 `find_element` 会跑到别的卡片去）。下面这个完整脚本还处理了币种换算与可下单判断。

```python
# scrape_products.py —— 完整可运行
import sys
from selenium import webdriver
from selenium.webdriver.chrome.options import Options
from selenium.webdriver.common.by import By

CHROME = "/root/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome"


def build_driver():
    opts = Options()
    opts.binary_location = CHROME
    opts.add_argument("--headless=new")
    opts.add_argument("--no-sandbox")
    opts.add_argument("--disable-dev-shm-usage")
    return webdriver.Chrome(options=opts)


def parse_products(driver):
    """列表页提取：先定位卡片集合，再在每张卡片内部定位字段。"""
    rows = []
    for card in driver.find_elements(By.CSS_SELECTOR, "#product-list > li.product-card"):
        price_el = card.find_element(By.CSS_SELECTOR, ".price")
        rows.append({
            "sku": card.get_attribute("data-sku"),
            "name": card.find_element(By.CSS_SELECTOR, ".name").text,
            "price": float(price_el.text.replace(",", "")),
            "currency": price_el.get_attribute("data-currency"),
            "stock": card.find_element(By.CSS_SELECTOR, ".stock").text,
            "orderable": card.find_element(By.CSS_SELECTOR, ".add-cart").is_enabled(),
        })
    return rows


def to_cny(price, currency, rate=7.15):
    return round(price * rate, 2) if currency == "USD" else price


def main():
    driver = build_driver()
    try:
        driver.get("http://127.0.0.1:8899/products.html")
        rows = parse_products(driver)
        assert len(rows) == 4, "卡片数量变化: %d" % len(rows)          # 结构变了要立刻失败
        for r in rows:
            print("  %-9s %-12s %8.2f %-4s %-4s 可下单=%s"
                  % (r["sku"], r["name"], r["price"], r["currency"], r["stock"], r["orderable"]))
        # 一条 XPath 直接筛出 USD 计价的商品名，避免在 Python 里再过滤一遍
        usd = driver.find_elements(
            By.XPATH, "//li[@class='product-card'][.//span[@data-currency='USD']]//span[@class='name']")
        print("USD 计价商品:", [n.text for n in usd])
        print("人民币合计: %.2f" % round(sum(to_cny(r["price"], r["currency"]) for r in rows if r["orderable"]), 2))
    finally:
        driver.quit()


if __name__ == "__main__":
    sys.exit(main())
```

### 场景二：无 id 表单的三级定位链

银行、保险类后台的表单经常只有 `name`，甚至 `name` 也不稳定（前端框架自动生成）。稳妥做法是写一条**带兜底的定位链**，同时命中多个时靠容器限定收窄。

```python
# locate_field.py —— 完整可运行
from selenium.webdriver.common.by import By


def field_by_label(driver, label_id, fallback_name=None):
    """三级定位链：CSS :has(> label#id) -> XPath following 轴 -> name 属性兜底。"""
    for by, using in [
        (By.CSS_SELECTOR, "div.field:has(> label#%s) input" % label_id),
        (By.XPATH, "//label[@id='%s']/following::input[1]" % label_id),
    ]:
        try:
            return driver.find_element(by, using)
        except Exception:
            continue                      # 这一级没命中就降级，不要在这里吞掉最终失败
    if fallback_name:
        return driver.find_element(By.CSS_SELECTOR, "#account-form input[name='%s']" % fallback_name)
    raise AssertionError("无法定位 " + label_id)


def fill_account_form(driver, data):
    for label_id, value in data.items():
        field_by_label(driver, label_id).send_keys(value)
```

最后两行是个附带发现：示例页面里的 `<label>` **没有 `for` 属性、也没有包住 input**，所以点它不会聚焦输入框（焦点停在 `body`）——用 `label.click()` 来「进入输入框」的写法只对正确关联的 label 有效。真实项目里遇到点不动的情况，先检查 label 与 input 的关联关系，或者干脆直接点输入框。

## 最佳实践与踩坑记录

### 最佳实践

1. 定位器优先级是硬规则：`data-testid` / 稳定 id > 语义化 CSS > 相对 XPath。前端愿意加 `data-testid` 时一定要争取，那是测试与样式解耦成本最低的一步。
2. 所有定位器集中在一个 Page Object 里声明为 `(By.X, "value")` 元组，用例只写 `self.SUBMIT`，不用在业务代码里出现选择器字符串。
3. 对列表类定位先 `find_elements` 再做数量断言，把「页面结构变了」变成明确的失败，而不是静默点到别的元素。
4. 定位集合元素时把作用域限定到容器（先 `find_element` 拿容器，再 `container.find_elements`），既避免跨卡片串味，也减少匹配范围。
5. XPath 里用 `contains()`、`starts-with()`、`normalize-space()` 替代完全匹配，对付动态后缀 id 与缩进换行；不要用绝对路径与位置索引。
6. 关键定位器要有「唯一性校验」：`find_elements` 长度必须等于预期值，多于一个通常是页面新增了重复组件。

### 踩坑记录

```text
坑 1：By.CLASS_NAME 传 "btn btn-primary" 直接抛异常
结论：以为 class name 和 CSS 一样支持空格分隔的多个类名。
原因：官方文档写明 class name 策略「compound class names are not permitted」，只接受单个类名；
      本机实测报 InvalidSelectorException，Message 为 "Compound class names are not allowed."。
解法：多类名一律改用 CSS：By.CSS_SELECTOR, ".btn.btn-primary"（注意 CSS 里多个类是连写、不加空格）；
      或者用 XPath contains(@class,'btn-primary')。

坑 2：相对定位 locate_with(...).below/near 命中的是相邻的另一个输入框
结论：以为相对定位比 XPath 更「语义化」，把整个表单都改成 near(label)。
原因：相对定位判定依据是元素的渲染坐标（矩形位置），不是 DOM 结构；垂直堆叠的密集表单里
      多个候选元素都在参考元素「下方 / 50px 内」，Selenium 返回的可能不是人眼以为的那个。
      本机实测四组 label/input：near 全部只有两组对的，below 四组里错两组、最后一组直接
      NoSuchElementException；而 XPath following 轴与 CSS :has() 四组全对。
解法：密集表单用 DOM 结构定位（CSS :has()、XPath following/following-sibling 轴）；
      相对定位只用在结构松散、候选唯一的场景（例如表格行内的操作按钮），且用 find_elements
      先看命中数量，多于一个就别用。

坑 3：XPath 用 text()='某个中文按钮' 明明页面上有却匹配不到
结论：以为 XPath 不支持中文，改成 contains(@class,...) 绕开。
原因：XPath 的 text() 是字符串全等比，DOM 里标签内部的换行与缩进都会算进去；
      而 Selenium 的 .text 属性做过空白归一化，所以「用 .text 打印出来是干净的」会误导人。
      本机实测：两个内容相同、一个带缩进的 li，text()='跑回归' 只命中 1 个，
      normalize-space()='跑回归' 命中 2 个。
解法：文本判断统一用 //x[normalize-space()='文案'] 或 //x[contains(text(),'文案')]；
      更稳的做法是不要用文案定位，改用 data-testid。

坑 4：By.NAME / By.CSS_SELECTOR 命中的第一个元素是在隐藏模板里的
结论：以为页面上同名元素只有一个，send_keys 打不进去或打到别的元素上。
原因：页面里常有隐藏的模板区块（如 <div style="display:none"> 里放一份待克隆的表单），
      它的 input 与真实表单同名；find_element 返回文档顺序的第一个，不保证是可见的那个。
      本机实测：By.NAME='holderName' 命中 2 个，第一个可见、第二个不可见——
      顺序恰好对了，但换个页面顺序就会反过来。
解法：定位时限定到可见容器（#account-form input[name='holderName']），
      或者配合显式等待的 visibility_of_element_located（只返回可见元素，见 18.3）。

坑 5：find_element 在页面改版后不报错，却点错了元素
结论：用例「通过了」但业务断言失败，排查半天以为是数据问题。
原因：find_element 返回第一个命中，页面在目标元素前面插入了一个结构相似的新元素
      （例如多了一个广告位、多了一个同样的按钮），定位器依然能命中，只是命中了新的那个。
解法：凡是「应该唯一」的定位器，用 find_elements 断言长度等于 1；列表类断言具体数量；
      并把关键页面的定位器唯一性检查放进上线前的冒烟用例。
```
