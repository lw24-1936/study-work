## 概述

`click()`、`send_keys()` 这些元素方法走的是简单命令通道，覆盖不了「按住不放」「移动到坐标」「同时按两个键」「滚轮滚动」这类真实用户操作。Selenium 为此提供了 `ActionChains`——它把动作编译成 W3C 标准的 **actions 序列**（input source + tick + action），一次 `perform()` 整批下发给驱动，由浏览器按时间轴回放。理解这一点很关键：**ActionChains 是「相对当前指针位置的增量序列」，不是「绝对坐标命令」**，前一个动作把指针留在哪里，会直接影响后一个动作。

无头模式（headless）是与交互强耦合的另一个话题：无头浏览器没有真实窗口，视口尺寸、可交互区域、拖拽落点都和默认假设不同。本机实测发现默认无头窗口只有 780×580、视口仅 780×437，元素很容易落在视口之外，直接导致 `MoveTargetOutOfBoundsException`。

```text
本篇主线：
1. ActionChains 与 W3C 动作 —— move_to_element / move_by_offset / pause / perform 的执行语义
2. 鼠标动作 —— 悬停展开菜单、click_and_hold + release 拖拽、drag_and_drop、右键、双击、滚动
3. 键盘 —— Keys 常量、key_down/key_up 组合键、元素级 send_keys、Keys.chord 在 4.51 已不存在

5. 本机实测的硬坑 —— MoveTargetOutOfBounds、Keys.chord 缺失、手动 scrollIntoView 破坏拖拽落点
6. 场景实战 —— 悬停菜单导出 CSV、拖拽归档订单并回读顺序
```

本机验证环境：Ubuntu 24.04、Python 3.14.7、selenium 4.51.0、Chrome for Testing 151.0.7922.34（`/root/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome`）。下文所有 `text` 块均为真实运行输出，**包括真实报错**。

```python
# 后文示例统一使用这两个构造器
from selenium import webdriver
from selenium.webdriver.chrome.options import Options

CHROME = "/root/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome"
BASE = "http://127.0.0.1:8765/"


def make_driver(window_size="1440,900"):
    opts = Options()
    opts.binary_location = CHROME
    opts.add_argument("--headless=new")
    opts.add_argument("--no-sandbox")
    opts.add_argument("--disable-dev-shm-usage")
    opts.add_argument("--window-size=" + window_size)
    return webdriver.Chrome(options=opts)


def make_driver_with_download(download_dir, window_size="1440,900"):
    opts = Options()
    opts.binary_location = CHROME
    opts.add_argument("--headless=new")
    opts.add_argument("--no-sandbox")
    opts.add_argument("--disable-dev-shm-usage")
    opts.add_argument("--window-size=" + window_size)
    opts.add_experimental_option("prefs", {
        "download.default_directory": download_dir,
        "download.prompt_for_download": False,
    })
    return webdriver.Chrome(options=opts)
```

## ActionChains 与 W3C 动作模型

`ActionChains(driver)` 收集动作，`perform()` 才真正执行。链式写法和分步写法等价：

```python
from selenium.webdriver.common.action_chains import ActionChains
from selenium.webdriver.common.by import By

box = d.find_element(By.ID, "draggable")

# 链式：一次 perform 下发整条序列
ActionChains(d).move_to_element(box).click().perform()

# 分步：中间可以插入等待或条件判断
actions = ActionChains(d)
actions.move_to_element(box)
actions.pause(0.2)                 # pause 会生成一个 delay tick
actions.click()
actions.perform()
```

常用动作与语义：

| 动作 | 语义 | 备注 |
|---|---|---|
| `move_to_element(el)` | 指针移到元素**中心** | 元素不在视口内时 ChromeDriver 会先滚动 |
| `move_to_element_with_offset(el, x, y)` | 相对元素定位点偏移 | Selenium 4 以**元素中心**为原点，容易算错 |
| `move_by_offset(x, y)` | 相对**当前位置**增量移动 | 越界直接抛 `MoveTargetOutOfBoundsException` |
| `click(el)` / `click()` | 移动并按下+释放（无参时按在当前位置） | 比 `element.click()` 多了指针移动 |
| `click_and_hold(el)` | 移动并按下不放 | 拖拽的第一步 |
| `release()` | 在当前位置释放 | 必须成对出现，否则浏览器一直处于按下状态 |
| `pause(sec)` | 停顿 | 让前端动画/防抖逻辑跟上 |
| `scroll_by_amount(x, y)` / `scroll_to_element(el)` | 滚轮滚动 | 走 wheel input source，不是 JS 滚动 |

本机实测的一个关键坑：元素还没滚进视口就做相对位移，会直接报错。

```text
draggable rect: {'x': 20, 'y': 793.9375, 'width': 100, 'height': 40}
窗口尺寸: {'width': 780, 'height': 580} 视口: [780, 437]
元素在视口内(是否已滚动到): [793.9375, 833.9375, 437]
[FAIL] move_to_element + move_by_offset(60,40)（未滚动） -> MoveTargetOutOfBoundsException: Message: move target out of bounds
scrollIntoView 之后 rect.top: 198.9375
[OK]   move_to_element + click -> drag-status = released-elsewhere
[OK]   move_to_element + move_by_offset(60,0)（已滚动） -> 无异常
```

注意默认无头窗口的实际尺寸：`get_window_size()` 返回 780×580，而视口只有 **780×437**（多出来的部分是浏览器自身 UI 的占位）。元素 `rect.y = 793.9` 远在视口之外，`move_to_element` 之后指针位置被钳制，再做相对位移就越界了。**只加 `--window-size=1440,900` 就能避免这一整类问题。**

```text
要点：
- ActionChains 是增量序列，perform() 才执行；分步写法便于插入等待
- move_by_offset 是相对当前位置，不是绝对坐标；越界抛 MoveTargetOutOfBoundsException
- move_to_element 会自动把元素滚进视口，通常不需要手动滚动
- click_and_hold 与 release 必须成对，否则浏览器保持按下状态污染后续用例
- pause 生成真实延迟 tick，用于等前端动画与防抖
- scroll_by_amount 走滚轮输入源，与 execute_script 的 scrollTo 语义不同
```

## 鼠标悬停 拖拽与右键

**悬停**解决「菜单要 hover 才展开」的问题。`move_to_element` 之后必须确认子菜单真的可见，再点里面的项——顺序反了会点到不可见元素，报 `ElementNotInteractableException`。

**拖拽**有两套写法：

- `click_and_hold(src)` + `move_to_element(tgt)` + `pause()` + `release()`：可控性最好，能插停顿、能配 `move_by_offset` 走曲线。
- `drag_and_drop(src, tgt)` / `drag_and_drop_by_offset(src, x, y)`：内部就是上面几步的封装，短但不好插入停顿。

本机实测两者的行为差异：

```text
[OK]   move_to_element 悬停 -> hover-status = 已悬停, 子菜单可见 = True
[OK]   click_and_hold -> move_to_element -> release -> drag-status = dropped-on-dropzone
[OK]   drag_and_drop(drag, drop) -> drag-status = pressed
[OK]   context_click 右键 -> drag-status = released-elsewhere
[OK]   double_click -> 无异常
滚动前 scrollY = 595
[OK]   scroll_by_amount(0,500) -> scrollY = 595
[OK]   scroll_to_element(#add-box) -> scrollY = 816
```

第一条 `drag_and_drop` 在小视口（780×437）下拿到的是 `pressed`，而把窗口放大到 1440×900 后同一条动作稳定得到 `dropped-on-dropzone`：

```text
drag_and_drop 立即读取: dropped-on-dropzone
drag_and_drop 0.5s 后读取: dropped-on-dropzone
drag_and_drop_by_offset(120,60): released-elsewhere
```

结论很直接：**拖拽类用例必须显式设置足够大的窗口**。小视口下目标元素被挤出可见区域，释放动作落在别处，而 WebDriver 不会报错——它只会静默点错位置。

右键与双击：

```python
drag = d.find_element(By.ID, "draggable")
ActionChains(d).context_click(drag).perform()        # 右键，触发 contextmenu 事件
ActionChains(d).double_click(drag).perform()         # 双击，触发 dblclick 事件
```

**滚动**用 `scroll_by_amount(dx, dy)` 或 `scroll_to_element(el)`，走的是 wheel 输入源。注意它和 `execute_script("window.scrollTo(...)")` 不是一回事：前者是真的滚轮事件，会触发页面的 scroll 监听与懒加载；后者是直接改滚动位置。

```text
要点：
- 悬停后先断言子菜单可见，再点里面的项，否则容易点空
- 拖拽优先 click_and_hold + move_to_element + pause + release，可控性最好
- drag_and_drop 是上面几步的封装，短但无法插入停顿
- 小视口下拖拽会静默落到错误位置，务必配 --window-size
- context_click / double_click 分别对应 contextmenu 与 dblclick 事件
- scroll_by_amount 触发真实滚轮事件，可用于验证懒加载；scroll_to_element 会先滚到元素
```

## 键盘操作与组合键

特殊键用 `selenium.webdriver.common.keys.Keys` 里的常量，它们在协议层是 Unicode 私有区码点（例如 `Keys.SHIFT == '\ue008'`）。**组合键的标准写法是 `key_down` / `key_up` 成对包裹 `send_keys`。**

```python
from selenium.webdriver.common.action_chains import ActionChains
from selenium.webdriver.common.keys import Keys

inp = d.find_element(By.ID, "combo-input")
inp.click()

# Ctrl+A 全选
ActionChains(d).key_down(Keys.CONTROL).send_keys("a").key_up(Keys.CONTROL).perform()
print("选中区间:", d.execute_script(
    "return [arguments[0].selectionStart, arguments[0].selectionEnd]", inp))

# 继续 Ctrl+A 后删除
ActionChains(d).key_down(Keys.CONTROL).send_keys("a").key_up(Keys.CONTROL) \
               .send_keys(Keys.DELETE).perform()
print("value =", repr(inp.get_attribute("value")))
```

本机真实输出：

```text
combo-input 初始 value: 'Selenium 组合键测试'
[OK]   Ctrl+A 全选（返回 selectionStart/End） -> [0, 14]
[OK]   再 Ctrl+A 后 DELETE -> value = '', keydown 记录 = key=Delete ctrl=false shift=false
[OK]   Keys.ENTER -> value 不变 = 'SO-2026'
[OK]   Keys.BACKSPACE -> value = 'SO-202'
Keys 类是否有 chord 属性: False
key_down(SHIFT)+send_keys('9')+key_up 后 value = 'Selenium 组合SO-2026(键测试'
再 Ctrl+A 选中区间 = [0, 22]
Keys 常量示例: SHIFT='\ue008' CONTROL='\ue009' ENTER='\ue007' ESCAPE='\ue00c' F5='\ue035'
```

两处值得注意：

1. **`Keys.chord` 在 selenium 4.51 里已经不存在**（`hasattr(Keys, "chord")` 为 `False`，直接调用抛 `AttributeError: type object 'Keys' has no attribute 'chord'`）。网上大量旧教程仍在用它，正确替代就是 `key_down` + `send_keys` + `key_up`。我实际读了一遍安装包里的 `selenium/webdriver/common/keys.py`，类里只有常量定义，没有任何方法。
2. **`element.send_keys()` 与 ActionChains 的 `send_keys()` 落点不同**。元素级 `send_keys` 从元素当前光标位置插入；AC 的 `send_keys("a")` 发给**当前焦点元素**，光标位置取决于上一次点击的坐标——实测 `click()` 把光标停在文本中间，于是输入变成了 `'Selenium 组合SO-2026(键测试'`。想稳定「追加到末尾」，先 `clear()` 后重输，或 `execute_script("arguments[0].setSelectionRange(len, len)", inp)`。

元素级特殊键与普通字符：

```python
inp.send_keys("ABC")             # 普通字符直接发，不需要 chord
inp.send_keys(Keys.ESCAPE)       # 关闭弹层
inp.send_keys(Keys.TAB)          # 触发失焦，关闭下拉、触发 blur 校验
```

```text
要点：
- 组合键统一用 key_down -> send_keys -> key_up，不要用已移除的 Keys.chord
- Keys 常量是私有区码点，打印出来是 '\ue008' 这种转义，属正常
- element.send_keys 从光标位置插入；AC.send_keys 发给当前焦点元素
- Keys.TAB 会真的移动焦点并触发 blur 校验，常用于关闭下拉
- Keys.ESCAPE 用于关弹层；发不出去时先确认焦点在页面内
- 无头模式下剪切板组合键（Ctrl+C/V）行为依赖实现，不要依赖它跨浏览器一致
```

## 无头模式与浏览器启动选项

无头模式是无 UI 的浏览器进程，CI 里默认选择。

```python
opts = Options()
opts.add_argument("--headless=new")      # 新版无头，渲染管线与有头一致
# opts.add_argument("--headless=old")    # 旧实现，行为差异多，已不推荐
opts.add_argument("--window-size=1440,900")
opts.add_argument("--no-sandbox")        # 容器/root 用户下常需要
opts.add_argument("--disable-dev-shm-usage")   # /dev/shm 太小导致浏览器崩溃时用
opts.add_argument("--lang=zh-CN")
opts.page_load_strategy = "eager"        # 'normal' | 'eager' | 'none'
```

本机实测窗口尺寸相关行为：

```text
默认无头 视口: [780, 437] get_window_size: {'width': 780, 'height': 580}
--window-size=1440,900 视口: [1440, 757] get_window_size: {'width': 1440, 'height': 900}
--window-size=390,844 视口: [500, 701] devicePixelRatio: 1
page_load_strategy='eager' 下 readyState = complete
```

三条可复用的经验：`--window-size` 设定的是**窗口**尺寸，视口要减去浏览器自身占的高度（900 → 757）；`--window-size=390,844` 这种手机尺寸**不会**真的得到 390 宽视口（实测 500×701），Chrome 有最小窗口限制，真要做移动端模拟得用 CDP 的 `Emulation.setDeviceMetricsOverride` 或设备指标 capability；`page_load_strategy` 三档（`normal` 等 `readyState == complete`、`eager` 等 `DOMContentLoaded`、`none` 只等初始文档）对静态页没有区别，实测三档下 `readyState` 都是 `complete`，它只对「资源加载慢」的站点有提速效果，不能当成规避等待问题的开关。

**文件下载**在无头下不会弹「另存为」对话框，靠 prefs 指定目录即可：

```python
opts.add_experimental_option("prefs", {
    "download.default_directory": "/path/to/downloads",
    "download.prompt_for_download": False,
    "plugins.always_open_pdf_externally": True,   # PDF 不内嵌预览，改为下载
})
```

本机真实结果：

```text
下载目录内容: ['report.csv']
下载文件首行: 订单号,渠道,金额
```

其它高频启动项：

| 参数 | 用途 |
|---|---|
| `--disable-gpu` | 无 GPU 的容器里避免 GL 相关报错 |
| `--incognito` | 无痕会话，天然隔离 Cookie 与磁盘缓存 |
| `--user-data-dir=/tmp/xxx` | 指定独立 profile，隔离性最好，也便于清缓存 |
| `--ignore-certificate-errors` | 忽略自签名证书（配合 `accept_insecure_certs`） |
| `--remote-debugging-port=0` | 让驱动自行分配调试端口，避免多实例端口冲突 |

Firefox 走的是另一套：`webdriver.FirefoxOptions()` + `add_argument("-headless")`，prefs 用 `opts.set_preference(...)`，没有 Chrome 的 `prefs` 概念。

```text
要点：
- 无头用 --headless=new；默认窗口 780x580、视口只有 780x437，务必显式设 --window-size
- --window-size 设的是窗口，视口要减去浏览器 UI 高度
- 小尺寸 --window-size 会被浏览器最小窗口限制抬大，移动端模拟请用设备指标覆盖
- page_load_strategy 只对资源慢的站点有效，页内动态内容仍需显式等待
- 下载靠 prefs 的 download.default_directory，无头下没有另存为对话框
- 容器环境常见组合：--no-sandbox + --disable-dev-shm-usage + --disable-gpu
```

## 应用场景实战

### 场景一：悬停展开菜单并导出报表

「悬停 → 展开二级菜单 → 点导出 → 等文件落地」是后台管理系统最常见的交互链。把等待点放在「子菜单可见」和「文件下载完成」两处，中间不要 sleep。

```python
import glob
import os
import time

from selenium.webdriver.common.action_chains import ActionChains
from selenium.webdriver.common.by import By
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait


def wait_for_download(directory, timeout=20):
    """轮询下载目录，忽略 .crdownload 半成品，直到出现最终文件。"""
    deadline = time.time() + timeout
    while time.time() < deadline:
        files = glob.glob(os.path.join(directory, "*"))
        if files and not any(f.endswith(".crdownload") for f in files):
            return files[0]
        time.sleep(0.3)
    raise AssertionError("下载超时: " + str(os.listdir(directory)))


def export_report_via_menu(driver, download_dir):
    driver.get(BASE)
    menu = driver.find_element(By.ID, "menu")
    ActionChains(driver).move_to_element(menu).perform()          # 悬停才出现子菜单
    wait = WebDriverWait(driver, 5)
    export_link = wait.until(EC.element_to_be_clickable((By.ID, "mi-export")))
    assert driver.find_element(By.ID, "submenu").is_displayed()   # 悬停生效的硬校验
    export_link.click()
    path = wait_for_download(download_dir)
    with open(path, encoding="utf-8") as fh:
        head = fh.readline().strip()
    return os.path.basename(path), head


if __name__ == "__main__":
    import shutil

    download_dir = "/root/.hermes/cache/scratch/selb_dl_scene5"
    shutil.rmtree(download_dir, ignore_errors=True)
    os.makedirs(download_dir, exist_ok=True)
    d = make_driver_with_download(download_dir)
    try:
        print(export_report_via_menu(d, download_dir))
    finally:
        d.quit()
```

本机真实运行结果：

```text
子菜单可见: True
('report.csv', '订单号,渠道,金额')
```

### 场景二：拖拽归档订单并回读列表顺序

看板类页面用拖拽改状态是普遍需求。这里的关键是**用页面自身记录的状态做断言**，而不是只看动作有没有抛异常——DOM 顺序会被前端框架重排，真正的业务状态才是有意义的断言点。

```python
from selenium.webdriver.common.action_chains import ActionChains
from selenium.webdriver.common.by import By
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait


def ids_in(driver, list_id):
    return [e.text for e in driver.find_elements(By.CSS_SELECTOR, f"#{list_id} .item")]


def archive_orders(driver, order_ids):
    driver.get(BASE)
    WebDriverWait(driver, 5).until(EC.visibility_of_element_located((By.ID, "list-a")))
    for oid in order_ids:
        src = driver.find_element(By.CSS_SELECTOR, f"#item-{oid}")
        tgt = driver.find_element(By.ID, "list-b")
        # 关键：不要在这里手动 scrollIntoView，交给 ChromeDriver 自己滚，见坑 3
        ActionChains(driver).click_and_hold(src).move_to_element(tgt).pause(0.3).release().perform()
    return ids_in(driver, "list-a"), ids_in(driver, "list-b")


d = make_driver()                                   # 必须带 --window-size=1440,900
try:
    remaining, archived = archive_orders(d, ["1002", "1003"])
    print("拖拽后 待处理:", remaining)
    print("拖拽后 已归档:", archived)
    print("页面记录的状态:", d.find_element(By.ID, "order-status").text)
    assert archived == ["SO-2026-1002", "SO-2026-1003"]
    assert remaining == ["SO-2026-1001"]
    print("断言全部通过")
finally:
    d.quit()
```

本机真实运行结果：

```text
拖拽后 待处理: ['SO-2026-1001']
拖拽后 已归档: ['SO-2026-1002', 'SO-2026-1003']
页面记录的状态: A: SO-2026-1001 | B: SO-2026-1002,SO-2026-1003
断言全部通过
```

`pause(0.3)` 不是随便加的：真实拖拽组件（SortableJS、react-dnd 之类）在 `mouseup` 之前需要若干次 `mousemove` 才能把元素「提起」，`pause` 让浏览器有时间派发这些中间事件帧。如果换成 `drag_and_drop` 的封装，这个停顿就没有插入点。

## 最佳实践与踩坑记录

1. **无头用例一律显式设置 `--window-size`。** 本机默认无头视口只有 780×437，拖拽、悬停、滚动全部可能静默点错位置；1440×900 是以极低成本消除一整类随机失败的方式。
2. **拖拽统一用 `click_and_hold` + `move_to_element` + `pause` + `release`。** 可控性比 `drag_and_drop` 好，能在中间插停顿和条件判断；只有确认封装够用时才用短写法。
3. **`release()` 绝不能漏。** `click_and_hold` 之后浏览器处于「按键按下」状态，漏掉 `release` 会让后续所有点击变成拖拽或长按，报错位置离真正原因很远。
4. **组合键用 `key_down` / `key_up` 成对包裹。** 历史上流行的 `Keys.chord` 已从 selenium 4.51 的 `Keys` 类里移除，写出来就是 `AttributeError`。
5. **交互前先让元素进入视口，但不要和 `move_to_element` 抢滚动。** 需要滚动时优先用 `ActionChains.scroll_to_element`，或干脆放大窗口；手动 `scrollIntoView` 后再交给 AC 定位，往往会把元素或落点推出视口。
6. **下载用「轮询目录 + 排除 `.crdownload`」判定完成。** 没有可靠的完成事件，固定 sleep 既慢又不稳；带超时的轮询函数是最小成本方案。

坑 1：`MoveTargetOutOfBoundsException: move target out of bounds`

结论：元素不在视口内时，`move_to_element` 之后的 `move_by_offset` 会直接抛异常，整条 actions 序列作废。

原因：W3C actions 要求指针落点必须在视口内；默认无头窗口只有 780×580（视口 437 高），本机实测目标元素 `rect.y = 793.9` 完全在视口外。

解法：加 `--window-size=1440,900`；或先 `ActionChains(d).scroll_to_element(el).perform()` 把元素滚进视口再做相对位移。本机实测滚动后同一动作从 FAIL 变 OK。

坑 2：`AttributeError: type object 'Keys' has no attribute 'chord'`

结论：`Keys.chord` 在 selenium 4.51 里不存在，旧教程的写法直接报错。

原因：该辅助方法已从 Python 绑定的 `Keys` 类中移除（本机实测 `hasattr(Keys, "chord") is False`，安装包源码 `keys.py` 只剩常量定义）。

解法：用 `key_down(Keys.CONTROL).send_keys("a").key_up(Keys.CONTROL)`；单纯想发大写字符直接 `send_keys("ABC")`。

坑 3：手动 `scrollIntoView` 之后，连续拖拽的第二次静默失败

结论：每次拖拽前手动 `scrollIntoView(src)` 时，本机实测第一次拖拽成功、第二次元素没被移动，且**不报任何异常**。

原因：`move_to_element` 自己会把目标元素滚进视口；手动滚动与驱动的滚动互相干扰，释放动作落到了列表之外，页面的 `mouseup` 监听自然不触发。

解法：去掉手动滚动，交给 ChromeDriver；改回纯 AC 动作后，本机实测连续两次拖拽都成功，页面事件序列为 `mousedown -> item-1002 / mouseup -> list-b / mousedown -> item-1003 / mouseup -> list-b`。

坑 4：拖拽动作看起来执行了，但页面状态没变

结论：小视口（780×437）下 `drag_and_drop` 读到的状态是 `pressed`，元素根本没被放下；放大窗口后同一动作稳定得到 `dropped-on-dropzone`。

原因：目标元素被挤出可见区域，指针移动被钳制在视口内，`mouseup` 落在了别的元素上；WebDriver 不会对此报错。

解法：固定较大的 `--window-size`；并在用例末尾断言页面自身的状态文本，而不是只断言「动作没抛异常」——本机实测断言页面记录的状态是最可靠的判定方式。

坑 5：`element.send_keys` 输入内容跑到文本中间

结论：AC 的 `send_keys` 发给当前焦点元素，插入点取决于上一次点击的坐标，实测出现 `'Selenium 组合SO-2026(键测试'` 这种中间插入。

原因：`click()` 把光标留在点击位置而不是文本末尾；`send_keys` 是插入不是替换。

解法：输入前 `clear()`，或先 `execute_script("arguments[0].setSelectionRange(n, n)", el)` 把光标移到末尾；要确定性结果就 `clear()` 后一次性输入完整字符串。
