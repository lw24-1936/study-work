## 概述

元素操作本身很简单——官方文档说得很清楚，能在元素上执行的命令只有 5 个：`click`、`send_keys`、`clear`、`submit`、`select`。真正决定用例稳不稳的是**操作前的等待**：页面是异步渲染的，元素什么时候出现、什么时候可点击、什么时候带上了正确的文本，页面自己知道，脚本不知道。Selenium 给了三种同步手段（隐式等待、显式等待、强制 sleep），用错一种就会让用例时快时慢、随机失败。本篇把操作 API 与等待机制放在一起讲，因为两者在实际代码里从来分不开。

```text
本篇主线：
1. 元素操作 —— click / send_keys / clear / submit 四个动作 + 读取类方法（text、get_attribute、is_*、rect、CSS 值）
2. 自动行为 —— 官方保证 click/send_keys 前会滚动进视口并做可交互性检查；元素不可交互会抛两类异常
3. 表单 —— 下拉框用 Select（三种选择方式 + deselect）、复选框/单选框点击、Keys 组合键与 submit()
4. 文件上传 —— 对 <input type="file"> 直接 send_keys 绝对路径；value 会是 C:\fakepath\xxx，不能用来校验
5. 隐式等待 —— 全局生效、单位秒、默认 0；缺点是「只能等出现，不能等条件」
6. 显式等待 —— WebDriverWait + expected_conditions，按条件轮询（默认 0.5 秒一次），超时抛 TimeoutException
7. 超时与重试 —— 三类超时的区别、哪些异常被 until 忽略、只用重试处理偶发、不掩盖必然失败
```

本机实测环境：selenium 4.51.0 + Chrome for Testing 151.0.7922.34（headless），页面为本地 `http.server` 托管的练习页（含 0.6 到 1.5 秒的模拟后端延迟）。下文所有 `text` 块都是本机真实运行输出，包含失败与耗时数据。

## 常用元素操作

官方把这几个方法称为「一套操作表单控件的高层指令集」，并且明确说了它们会**模拟真实用户行为**：在执行前会先判断元素是否在视口外（是则滚动到视口），再做一次可交互性检查（不可交互就报错）。所以 `click()` 不是「直接在 DOM 上触发事件」，而是接近真人点击。

| 方法 | 适用对象 | 行为 |
|---|---|---|
| `click()` | 任意元素 | 在元素**中心点**点击；中心被遮挡时报 `ElementClickInterceptedException` |
| `send_keys(*keys)` | 文本输入框、可键盘交互元素 | 追加输入；可混入 `Keys` 常量 |
| `clear()` | 文本输入框、contenteditable | 清空已有内容 |
| `submit()` | `<form>` 内的元素 | 提交所属表单 |
| `Select(el)` | `<select>` | 见下一节 |

读取类方法（不改变页面状态，但定位后频繁使用）：

| 方法 | 返回 | 说明 |
|---|---|---|
| `.text` | str | 可见文本（已做空白归一化） |
| `get_attribute(name)` | 属性或 **property** 值 | 对输入框取 `value` 时拿的是**用户输入后**的实时值 |
| `get_dom_attribute(name)` | 仅 DOM 属性 | 与 `get_attribute` 的区别就在这里 |
| `get_property(name)` | 仅 property | |
| `is_displayed()` / `is_enabled()` / `is_selected()` | bool | 可见 / 可用 / 已选中 |
| `.tag_name` | str | 标签名小写 |
| `.rect` | dict | `x/y/width/height`，相对定位就是靠它算的 |
| `value_of_css_property(prop)` | str | 计算后的 CSS 值 |

```python
user = driver.find_element(By.ID, "user")
user.send_keys("qa_zhang")                      # 输入
print("send_keys 后 value:", user.get_attribute("value"))
user.clear()                                    # 清空
print("clear 后 value:", repr(user.get_attribute("value")))
driver.find_element(By.ID, "pass").send_keys("S3cr3t!")
box = driver.find_element(By.ID, "remember")
box.click()                                     # 点击复选框
print("click 后 is_selected:", box.is_selected())
btn = driver.find_element(By.ID, "submit-btn")
print("按钮文本:", btn.text, "| rect:", btn.rect, "| CSS color:", btn.value_of_css_property("color"))
print("get_attribute('id'):", btn.get_attribute("id"),
      "| get_dom_attribute('type'):", btn.get_dom_attribute("type"))
```

本机真实输出：

```text
send_keys 后 value: qa_zhang
clear 后 value: ''
密码框类型: password
tag_name: input
is_displayed: True is_enabled: True is_selected: False
click 后 is_selected: True
按钮文本 .text: 登录
get_attribute('id'): submit-btn | get_dom_attribute('type'): submit
rect: {'height': 25, 'width': 43, 'x': 603.046875, 'y': 129.875}
CSS color: rgba(0, 0, 0, 1)
```

两个高频异常来自「可交互性检查」，看清它们的触发条件能省下大量排查时间：

```python
driver.execute_script("document.getElementById('hide-btn').style.display='none'")
driver.find_element(By.ID, "hide-btn").click()
```

```text
点击隐藏元素: ElementNotInteractableException
   首行: Message: element not interactable
```

`ElementNotInteractableException` = 元素在 DOM 里但不可交互（隐藏、被禁用、尺寸为 0）；`ElementClickInterceptedException` = 元素可交互，但它的中心点被别的元素（弹窗、遮罩、吸顶导航）挡住了。后者的正确处理不是改用 JS 点击绕过，而是先把挡路的东西关掉。

## 表单与文件上传

`<select>` 不能直接用 `click()` 选选项（原生下拉在部分浏览器里不是 DOM 元素），要用 `Select` 包装：

| 方法 | 说明 |
|---|---|
| `select_by_value(v)` | 按 `value` 属性选 |
| `select_by_index(i)` | 按下标选（从 0 开始） |
| `select_by_visible_text(t)` | 按显示文本选 |
| `deselect_by_value/index/visible_text(v)` | 取消选中，仅多选下拉有意义 |
| `deselect_all()` | 清空多选 |
| `options` | 全部选项（list[WebElement]） |
| `all_selected_options` | 全部已选中项 |
| `first_selected_option` | 第一个已选中项（单选下拉就用它读当前值） |
| `is_multiple` | 是否多选（该属性在单选 `<select>` 上取不到时返回 None） |

```python
from selenium.webdriver.support.ui import Select

sel = Select(driver.find_element(By.ID, "role"))
print("默认选中:", sel.first_selected_option.text)
sel.select_by_value("qa")
print("select_by_value('qa') ->", sel.first_selected_option.text)
sel.select_by_visible_text("运维")
print("select_by_visible_text('运维') ->", sel.first_selected_option.get_attribute("value"))
sel.select_by_index(0)
print("select_by_index(0) ->", sel.first_selected_option.get_attribute("value"))
print("全部选项:", [o.text for o in sel.options], "| 是否多选:", sel.is_multiple)
```

本机真实输出：

```text
默认选中: 开发
select_by_value('qa') -> 测试
select_by_visible_text('运维') -> ops
select_by_index(0) -> dev
全部选项: ['开发', '测试', '运维']
是否多选: None
```

复选框与单选框用 `click()` 切换，注意 `click()` 是**切换**语义而不是设置语义——如果元素已经是选中态，再点一次会变成未选中，所以「确保选中」要写成幂等：

```python
box = driver.find_element(By.ID, "remember")
if not box.is_selected():
    box.click()
```

**文件上传**走的是同一套 `send_keys`：对 `<input type="file">` 直接输入**绝对路径**即可，不需要模拟系统文件选择框。

```python
driver.find_element(By.ID, "upload").send_keys("/root/.hermes/cache/scratch/upload_src/report.csv")
print("上传字段 value:", driver.find_element(By.ID, "upload").get_attribute("value"))
```

```text
上传字段 value: C:\fakepath\report.csv
```

`C:\fakepath\` 是浏览器出于安全考虑做的伪装（Windows 与 Linux 的 Chromium 都会这样），它**不是**真实路径，所以不能拿 `value` 校验上传是否成功；要校验就看后端回包或页面提示。上传完成后可以先断言文件在磁盘上存在（`os.path.isfile`），再去点提交。

键盘相关的最小用法是把 `Keys` 常量混进 `send_keys`：

```python
from selenium.webdriver.common.keys import Keys

user.send_keys("qa_zhang", Keys.TAB)              # 输入后按 Tab 移焦
driver.find_element(By.ID, "pass").send_keys("S3cr3t!")
driver.find_element(By.ID, "pass").submit()       # 提交所属表单
```

本机真实输出：

```text
TAB 后焦点元素 id: pass
submit() 后 URL: http://127.0.0.1:8899/index.html?username=qa_zhang&password=S3cr3t%21&role=dev#
```

复杂的组合键、拖拽、悬停属于鼠标键盘高级交互，见 18.5。

## 隐式等待

隐式等待是**会话级全局设置**：一旦设上，本会话内每一次「找元素」在失败前都会先等这么久。单位在 Python 绑定里是**秒**，默认值为 `0`（找不到立刻报错）。

```python
driver.implicitly_wait(2)          # 秒，作用于本会话内所有 find_element / find_elements
try:
    driver.find_element(By.ID, "not-exist")
except NoSuchElementException:
    pass
```

本机实测：找不到元素时耗时 2.03 秒才抛异常，说明等待确实生效了；元素一旦命中就立即返回，不会等满。

```text
找不到元素耗时 2.03 秒 -> NoSuchElementException
```

它的能力边界是硬伤：**只能等「元素出现」，不能等「元素可见/可点击/文本变成某个值」**。SPA 里元素常常早就存在于 DOM（只是 `display:none`），隐式等待会立刻返回，然后 `click()` 报 `ElementNotInteractableException`。官方文档对此的措辞是：`find_element` 只保证元素在 DOM 里存在，不保证它处于可交互状态。

另一个官方明确警告的点：**不要混用隐式等待与显式等待**，否则等待时间不可预测。本机把这条警告量化出来了（隐式 5 秒 + 显式 2 秒）：

```python
driver.implicitly_wait(5)
try:
    WebDriverWait(driver, 2).until(EC.presence_of_element_located((By.ID, "not-exist")))
except Exception as e:
    print("抛出:", type(e).__name__, "实际耗时: %.2f 秒" % (time.perf_counter() - t0))
driver.implicitly_wait(0)
```

```text
implicit=5s + explicit=2s 抛 TimeoutException，实际耗时: 5.04 秒
```

显式等待写了 2 秒，实际等了 5.04 秒——因为 `until` 内部每次调用 `find_element` 都会被隐式等待拦一次。工程上的结论是：**隐式等待设 0，等待全部用显式等待表达**。

## 显式等待与 expected_conditions

显式等待是等待机制的正确答案：你给出一个条件函数，`WebDriverWait` 以固定频率轮询它，条件返回真值就立刻结束，超过 `timeout` 就抛 `TimeoutException`。

```python
WebDriverWait(driver, timeout, poll_frequency=0.5, ignored_exceptions=None)
```

| 参数 | 默认值 | 说明（来自 selenium 4.51.0 源码） |
|---|---|---|
| `timeout` | 必填 | 超时秒数 |
| `poll_frequency` | `0.5` | 两次调用条件之间的间隔秒数（源码常量 `POLL_FREQUENCY = 0.5`） |
| `ignored_exceptions` | `None` | 默认忽略 `NoSuchElementException`（源码 `IGNORED_EXCEPTIONS = (NoSuchElementException,)`） |

`expected_conditions as EC` 是官方预置条件集合，常用的一批如下（本机逐个跑通）：

| 条件 | 参数 | 语义 |
|---|---|---|
| `presence_of_element_located` | locator | 元素出现在 DOM（不要求可见） |
| `visibility_of_element_located` | locator | 元素存在**且可见**，返回该元素 |
| `invisibility_of_element_located` | locator | 元素不可见（或不存在） |
| `element_to_be_clickable` | locator | 可见且可点击，返回该元素 |
| `presence_of_all_elements_located` | locator | 至少一个命中，返回列表 |
| `text_to_be_present_in_element` | locator, text | 元素文本**包含**该字符串 |
| `text_to_be_present_in_element_value` | locator, text | 输入框 value 包含 |
| `element_to_be_selected` | element | 已选中（传入元素本身） |
| `staleness_of` | element | 元素已从 DOM 移除 |
| `number_of_windows_to_be` | n | 窗口数量 |
| `new_window_is_opened` | handles | 出现新窗口 |
| `alert_is_present` | 无 | 出现弹窗，返回 Alert |
| `frame_to_be_available_and_switch_to_it` | locator | iframe 可用并切进去 |
| `title_is` / `title_contains` | str | 标题 |
| `url_to_be` / `url_contains` / `url_matches` / `url_changes` | str/pattern | URL 变化 |
| `any_of` / `all_of` / `none_of` | 多个条件 | 条件组合 |

```python
wait = WebDriverWait(driver, 5, poll_frequency=0.2)

driver.find_element(By.ID, "load-btn").click()          # 点击后 1.5 秒才插入 #late
late = wait.until(EC.visibility_of_element_located((By.ID, "late")))
print("命中文本:", late.text)

driver.find_element(By.ID, "hide-btn").click()
print("不可见:", wait.until(EC.invisibility_of_element_located((By.ID, "title"))))
print("可点击:", wait.until(EC.element_to_be_clickable((By.ID, "submit-btn"))).get_attribute("id"))
print("文本包含:", wait.until(EC.text_to_be_present_in_element((By.ID, "status"), "初始")))
print("命中数量:", len(wait.until(EC.presence_of_all_elements_located((By.CSS_SELECTOR, "#todo-list .item")))))
```

本机真实输出：

```text
visibility_of_element_located 命中，耗时 1.67 秒，文本: 延迟加载内容
presence_of_element_located: div
invisibility_of_element_located: <selenium.webdriver.remote.webelement.WebElement (session="ab98086ac3aca1434a26518d3674a6dc", element="f.DCD035505BCFAF15D1F090E75A605BE6.d.92EF859A6BD9F4ADA2C96213BACB6042.e.106")>
element_to_be_clickable: submit-btn
text_to_be_present_in_element: True
presence_of_all_elements_located 数量: 3
```

注意 `visibility_of_element_located` 的耗时是 1.67 秒，而页面模拟延迟是 1.5 秒——说明轮询是密集且有效的，几乎在条件成立的那一刻就返回了。`invisibility_of_element_located` 在 selenium 4.51.0 里返回的是 WebElement 对象（不是布尔值），所以别写 `assert wait.until(...) is True`。

预置条件覆盖不到的场景（等文本变化、等属性包含、等列表长度稳定），直接传一个返回 `WebElement` 或 `False` 的 lambda / 函数：

```python
def text_is_not(locator, value):
    """自定义条件：文本不再是某个值时返回该元素。"""
    def _predicate(driver):
        elements = driver.find_elements(*locator)
        if elements and elements[0].text != value:
            return elements[0]
        return False
    return _predicate


driver.execute_script("document.getElementById('status').textContent='运行中'")
got = WebDriverWait(driver, 3).until(text_is_not((By.ID, "status"), "初始状态"))
print("自定义等待条件命中:", got.text)
```

```text
自定义等待条件命中: 运行中
```

也可以直接用 `lambda`，配合 `text_to_be_present_in_element` 等现成条件组合使用。写自定义条件时记住一条：**条件函数必须自己捕获「元素还不存在」的情况**（用 `find_elements` 返回空列表判断），否则第一次轮询就会把 `NoSuchElementException` 抛穿。

## 超时 轮询与重试封装

Selenium 里的「超时」不是一个东西，而是四个，各自独立配置：

| 超时 | 设置方式 | 单位（Python） | 超时抛什么 |
|---|---|---|---|
| 隐式等待 | `driver.implicitly_wait(s)` 或 `options.timeouts["implicit"]` | 秒 / 毫秒 | `NoSuchElementException` |
| 显式等待 | `WebDriverWait(driver, timeout)` | 秒 | `TimeoutException` |
| 页面加载 | `driver.set_page_load_timeout(s)` 或 `options.timeouts["pageLoad"]` | 秒 / 毫秒 | `TimeoutException` |
| 脚本执行 | `driver.set_script_timeout(s)` 或 `options.timeouts["script"]` | 秒 / 毫秒 | `TimeoutException` |

```python
t0 = time.perf_counter()
try:
    WebDriverWait(driver, 3, poll_frequency=0.5).until(
        EC.presence_of_element_located((By.ID, "never-appear"))
    )
except TimeoutException as e:
    print("超时耗时 %.2f 秒" % (time.perf_counter() - t0))
    print("异常首行:", str(e).splitlines()[0])
```

```text
超时耗时 3.05 秒
异常首行: Message: 
```

`TimeoutException` 的 message 默认是空的，这在 CI 日志里几乎不可用。`until` 支持 `message` 参数，务必写上：

```python
WebDriverWait(driver, 5).until(
    EC.visibility_of_element_located((By.ID, "result")),
    message="保存结果 5 秒内未出现，检查后端是否超时",
)
```

**重试**与等待是两件事，别混用：

| 手段 | 解决什么 | 不能解决什么 |
|---|---|---|
| 显式等待 | 元素「还没准备好」——必然会在有限时间内出现 | 间歇性的网络抖动、偶发的渲染竞态 |
| 重试装饰器 | 偶发失败（概率低、重试即过） | 必然失败（定位器写错了，重试 100 次也错） |

一个足够用的轻量重试实现（不用引第三方库）：

```python
import functools
import time


def retry(times=3, delay=0.5, exceptions=(Exception,)):
    """轻量重试：只对付偶发失败，第三次还失败就如实抛出去。"""
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            last = None
            for attempt in range(1, times + 1):
                try:
                    return fn(*args, **kwargs)
                except exceptions as exc:
                    last = exc
                    if attempt < times:
                        time.sleep(delay)
            raise last
        return wrapper
    return deco
```

本机实测（让函数前两次故意失败）：

```text
== 重试装饰器 ==
    第 1 次失败: AssertionError
    第 2 次失败: AssertionError
  最终结果: True | 实际调用次数: 3
```

重试范围要克制：**只包住那些真的偶发的动作**（点击、提交、读一次数据），不要包住整条用例。把 `AssertionError` 也放进重试白名单是危险的——业务断言失败被重试会掩盖真 bug，所以 `exceptions` 参数应当显式给成具体的异常元组（如 `(ElementClickInterceptedException, StaleElementReferenceException, TimeoutException)`）。

## 应用场景实战

### 场景一：登录流程的稳定封装

登录接口有 0.6 到 0.8 秒的模拟延迟，且成功与失败走的是**两个不同的页面元素**。朴素写法是「先等欢迎语、没等到再等错误提示」，那样一次失败要等两个超时之和；正确写法是把两个条件用 `any_of` 式的逻辑合并成一次等待。

```python
# login_flow.py —— 完整可运行
from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

USERNAME = (By.ID, "username")
PASSWORD = (By.ID, "password")
LOGIN_BTN = (By.ID, "login-btn")
MSG = (By.CSS_SELECTOR, "#msg")
WELCOME = (By.ID, "welcome")
TIMEOUT = 5


def wait_visible(driver, locator, timeout=TIMEOUT):
    return WebDriverWait(driver, timeout).until(EC.visibility_of_element_located(locator))


def login(driver, user, pwd):
    """填表 -> 提交 -> 等「欢迎」或「错误提示」二者之一出现。"""
    wait_visible(driver, USERNAME).clear()
    driver.find_element(*USERNAME).send_keys(user)
    driver.find_element(*PASSWORD).clear()
    driver.find_element(*PASSWORD).send_keys(pwd)
    wait_visible(driver, LOGIN_BTN).click()

    ok = EC.visibility_of_element_located(WELCOME)
    err = EC.visibility_of_element_located(MSG)
    result = WebDriverWait(driver, TIMEOUT).until(
        lambda d: ok(d) or err(d)          # 先完成的条件胜出，两条等待不串行累计
    )
    if result.get_attribute("id") == "welcome":
        return True, result.text
    return False, result.text
```

本机真实输出：

```text
失败用例: ok=False msg=账号或密码错误 耗时 1.35 秒
成功用例: ok=True msg=欢迎 admin 耗时 1.23 秒

超时异常长这样（等一个永远不出现的元素）:
  TimeoutException，耗时 3.05 秒
  message='Message: '
```

注意失败用例耗时 1.35 秒：它没有等到 5 秒超时，因为错误提示一出现就返回了——这正是「条件等待」相对 `sleep(3)` 的价值。另外示例页面里的 `#msg` 初始是 `display:none`，如果用 `presence_of_element_located` 会在脚本一提交就立刻命中（元素一直在 DOM 里），必须用 `visibility_of_element_located`。

### 场景二：批量录入 + 文件上传 + 结果校验

对账类后台的典型流程：表格逐行填数、上传附件、点保存、等结果提示、根据提示补数据再提交。整个流程零 `sleep`，全部靠条件等待。

```python
# entry_flow.py —— 完整可运行
import os
from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

ROWS = [
    ("ORD-001", "1200.50", "月结"),
    ("ORD-002", "880.00", "月结"),
    ("ORD-003", "", "待确认"),          # 故意留空，触发页面校验失败
]


def fill_rows(driver):
    for order, amount, memo in ROWS:
        row = driver.find_element(By.CSS_SELECTOR, "tr[data-order='%s']" % order)
        amount_input = row.find_element(By.CSS_SELECTOR, ".amt")
        amount_input.clear()
        if amount:
            amount_input.send_keys(amount)
        memo_input = row.find_element(By.CSS_SELECTOR, ".memo")
        memo_input.clear()
        memo_input.send_keys(memo)


def submit_and_wait(driver, wait):
    driver.find_element(By.ID, "save-btn").click()
    return wait.until(EC.visibility_of_element_located((By.ID, "result")))


def run(driver):
    wait = WebDriverWait(driver, 5)
    fill_rows(driver)

    # 文件上传：绝对路径直接 send_keys；先确认文件真的存在，否则报错信息会很难懂
    csv_path = "/root/.hermes/cache/scratch/upload_src/statement.csv"
    assert os.path.isfile(csv_path), "上传文件不存在: " + csv_path
    driver.find_element(By.ID, "attach").send_keys(csv_path)

    result = submit_and_wait(driver, wait)
    if "保存失败" in result.text:
        # 结果元素已经在页面上，第二次要等「文本变化」而不是等「出现」
        row = driver.find_element(By.CSS_SELECTOR, "tr[data-order='ORD-003']")
        row.find_element(By.CSS_SELECTOR, ".amt").send_keys("45.20")
        driver.find_element(By.ID, "save-btn").click()
        wait.until(EC.text_to_be_present_in_element((By.ID, "result"), "保存成功"))
    return driver.find_element(By.ID, "result").text
```

本机真实输出：

```text
== 逐行录入（每行内部定位，避免跨行串味）==
  ORD-001 amount='1200.50' memo='月结'
  ORD-002 amount='880.00' memo='月结'
  ORD-003 amount='' memo='待确认'

== 文件上传 ==
  input.value = C:\fakepath\statement.csv

== 提交并等结果（不用 sleep）==
  第一次结果: 保存失败：缺少金额 ORD-003

== 补上缺失金额后重提交 ==
  第二次结果: 保存成功：共 3 条
```

这段代码里藏着一个必须理解的细节：**第一次提交用「等元素出现」，第二次提交必须改成「等文本变化」**。因为 `#result` 第一次出现后就一直在 DOM 里，第二次如果还用 `visibility_of_element_located` 会立刻返回上一次的旧文本，断言到「保存失败」而误判。这类「同一个元素、反复提交、每次内容变」的场景，`text_to_be_present_in_element` 是正确的条件。

最后是元素过期的真实表现——表格行被替换后，之前拿到的引用会失效：

```text
== 元素过期：替换行后旧引用失效 ==
  旧引用访问 -> StaleElementReferenceException
  重新定位后可用: input
```

## 最佳实践与踩坑记录

### 最佳实践

1. 隐式等待统一设 0，所有等待都用显式等待表达。本机实测隐式 5 秒 + 显式 2 秒会变成实际等 5.04 秒，混用会让耗时不可预测。
2. 条件粒度要选对，并跟着页面状态走：等元素「出现」用 `presence_of_element_located`，等「可操作」用 `visibility_of_element_located` / `element_to_be_clickable`，等「内容变化」用 `text_to_be_present_in_element`，三者不可互相替代；同一元素反复提交时必须从「等出现」换成「等文本或属性变化」。
3. 显式等待一律带 `message=`，否则 `TimeoutException` 的 message 是空的（本机实测就是 `'Message: '`），CI 里只剩一行无信息量的报错。
4. `clear()` + `send_keys()` 成对使用；复选框用 `if not el.is_selected(): el.click()` 的幂等写法，不要无脑 `click()`。
5. 重试只包住真正偶发的动作，`exceptions` 参数显式列出具体异常类型，绝不把业务 `AssertionError` 放进重试白名单——那会把真 bug 变成「重试后通过」。
6. 文件上传前先 `os.path.isfile()` 断言文件存在。上传失败时 Selenium 的报错指向的是 `send_keys`，而不是「文件不存在」，排查方向会被带偏。

### 踩坑记录

```text
坑 1：显式等待设了 2 秒，实测等了 5 秒
结论：以为 WebDriverWait 的超时参数不生效，或者 selenium 4.51 有 bug。
原因：会话上还留着 implicitly_wait(5)。until 内部每次轮询都要调用 find_element，
      每一次调用都会被隐式等待拦一次，两者叠加导致实际耗时远大于显式超时。
      本机实测：implicit=5s + explicit=2s，抛 TimeoutException，实际耗时 5.04 秒。
      官方文档对此有明确警告：Do not mix implicit and explicit waits。
解法：会话创建后立刻 driver.implicitly_wait(0)（或干脆不设），等待全部用显式等待；
      在 fixture 里加一条断言，确保前进用例时代码里没有残留的隐式等待。

坑 2：点提交按钮报 ElementNotInteractableException，换成 JS 点击就"好"了
结论：以为 Selenium 的 click 不可靠，于是全项目改用 execute_script("arguments[0].click()")。
原因：click() 前的可交互性检查发现元素不可交互——本机实测把一个按钮设为 display:none 后点击，
      报的就是 ElementNotInteractableException，Message 为 "element not interactable"。
      JS 点击绕过了检查，元素确实"被点了"，但真实用户点不到，用例通过是假象。
解法：先等元素真正可交互（EC.element_to_be_clickable），再 click；如果元素本来就该显示，
      说明页面状态没到，应该等前置条件；只有在前端确实无法用真实事件触发的极端场景下才用 JS 点击，
      并加注释说明原因。

坑 3：同一个保存按钮点两次，第二次断言读到的还是上一次的结果
结论：以为页面没刷新，去手动加 sleep(2)，时好时坏。
原因：结果元素 #result 第一次提交后就一直留在 DOM 里（只是改文本），
      第二次用 EC.visibility_of_element_located 会在轮询第一轮就命中这个旧元素，
      拿到的是上一次的文本，断言自然错。
      本机实测：第一次结果「保存失败：缺少金额 ORD-003」，补齐后第二次结果才是「保存成功：共 3 条」。
解法：改成等内容变化——EC.text_to_be_present_in_element((By.ID, "result"), "保存成功")；
      更稳的做法是让每次提交都产生可区分的新状态（比如提交后结果区先被清空）。

坑 4：拿上传框的 value 去校验上传是否成功，永远对不上
结论：以为文件上传失败了，反复检查路径写法（斜杠、转义、中文路径）。
原因：浏览器出于安全考虑对 <input type="file"> 的 value 做伪装处理，
      本机实测读到的值是 C:\fakepath\statement.csv，Linux 上也是这个前缀，不是真实路径。
解法：不校验 value。改用「上传前 os.path.isfile 断言文件存在 + 上传后看后端回包或页面提示」；
      如果确实要读文件名，用 el.get_attribute("value").split("\\\\")[-1] 取末段，
      但这条只适用于本地文件选择，远程会话（Grid）会失效。

坑 5：列表刷新后旧引用全部失效，报 StaleElementReferenceException
结论：以为定位器写错了，反复换选择器。
原因：元素引用绑定的是具体的 DOM 节点，页面把那一块重新渲染（列表刷新、行替换、前端框架重绘）后
      旧节点已被移除，原来的 WebElement 就过期了。
      本机实测：拿一行内的输入框引用、移除该节点后访问，直接 StaleElementReferenceException。
解法：重新定位再操作（每次操作前 find_element），把「定位 + 操作」封装进一个函数里循环调用；
      或者用显式等待的 staleness_of 主动等旧元素失效；
      重试装饰器里把 StaleElementReferenceException 列进白名单属于常见兜底，但根因还是重新定位。

坑 6：用 sleep 解决一切等待问题，用例越跑越慢还偶发失败
结论：觉得 sleep(3) 稳，就到处加。
原因：sleep 是固定时长——渲染快的时候白等，渲染慢的时候不够。官方等待文档开篇就说这是
      flaky 用例的首要原因，且时长无法预知。
解法：全部替换为条件等待。本机实测对照：页面模拟延迟 1.5 秒时，
      EC.visibility_of_element_located 在 1.67 秒返回（几乎无浪费），
      而登录失败场景在 1.35 秒就返回，sleep(3) 每次都要多等一倍以上。
```
