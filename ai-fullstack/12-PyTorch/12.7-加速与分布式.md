## 概述

训练变慢时，加速的手段有明确的优先级：先看清瓶颈在哪（`torch.profiler`），再按「数据管道 → 计算精度 → 图编译 → 多进程并行」的顺序逐层加。跳过剖析直接上分布式，最常见的结果是把一个 IO 瓶颈复制成 N 份，吞吐没有任何提升。本篇按「单机单卡 → 单机多进程 → 多机」的推进顺序展开，并把每一项在本机的真实验证结果贴出来。

**本机环境说明（重要）**：`torch 2.14.1+cu130`，`torch.cuda.is_available()` 为 `False`，导入时报警告 `CUDA initialization: ... Error 804: forward compatibility was attempted on non supported HW`，`nvidia-smi` 也报 NVML 驱动与内核模块不匹配。因此本篇涉及的 **CUDA / NCCL / 多卡 / GPU 混合精度 / TensorRT 相关内容一律未在本机验证**，仅按官方文档说明并标注依据；本机真实跑过的是 CPU 侧的线程调优、DataLoader 多进程、`torch.compile`、CPU autocast、梯度累积、`torch.profiler`，以及**两个真实进程的 gloo 后端 DDP**。

```text
全篇主线：
1. 先剖析后优化 —— torch.profiler 定位瓶颈，别凭直觉改代码
2. 数据管道优先 —— num_workers 与 pin_memory 通常是最便宜的那一档收益
3. 精度换速度 —— autocast + GradScaler，CPU 上等价物是 bfloat16 autocast
4. 编译换速度 —— torch.compile 抓图做算子融合，收益强依赖模型与后端
5. 并行换吞吐 —— DDP 每进程一份模型，梯度 all-reduce；gloo 跑 CPU，nccl 跑 GPU
6. 显存不够先用梯度累积「假装」大 batch，代价是时间不是显存
```

## GPU 训练与设备管理

PyTorch 的设备抽象是 `torch.device`，字符串形式 `"cuda:0"`、`"cpu"`、`"mps"`、`"xpu"`。正确的写法从不让设备名硬编码，而是先探测再回退：`device = torch.device("cuda" if torch.cuda.is_available() else "cpu")`。多卡训练里每个进程负责一张卡，靠 `torch.cuda.set_device(local_rank)` 绑定，**不能**用 `device="cuda"` 让它自己选——那样所有进程会挤到 0 号卡上，表现为显存爆掉而不是报错。

`torch.accelerator` 是较新引入的一层抽象，用来抹平不同加速器后端的差异（CUDA / XPU / MPS / MTIA 等），提供 `accelerator.current_accelerator()`、`accelerator.device_count()` 这类统一入口。它在 2.14 里已经可用，但生态代码普遍还是直接写 `torch.cuda`，本节按主流写法展开。

```python
"""设备探测与安全回退。本机 cuda.is_available() 为 False，走 CPU 分支。"""
import torch

print("A. torch", torch.__version__)
print("B. torch.cuda.is_available() =", torch.cuda.is_available())
print("C. torch.cuda.device_count() =", torch.cuda.device_count())

device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
print("D. 最终选用设备:", device)

t = torch.randn(2, 3, device=device)
print("E. 张量在", t.device, "| 回到 CPU 用 t.cpu().device =", t.cpu().device)

# 多卡时每个进程必须显式绑定本卡；单卡/CPU 环境用 guard 兜住
def setup_device(local_rank: int) -> torch.device:
    if torch.cuda.is_available():
        torch.cuda.set_device(local_rank)          # DDP 场景下必须，避免全部挤到 cuda:0
        return torch.device("cuda", local_rank)
    return torch.device("cpu")

print("F. setup_device(0) ->", setup_device(0))
```

真实输出（本机无可用 GPU，走 CPU 回退分支）：

```text
A. torch 2.14.1+cu130
B. torch.cuda.is_available() = False
C. torch.cuda.device_count() = 0
D. 最终选用设备: cpu
E. 张量在 cpu | 回到 CPU 用 t.cpu().device = cpu
F. setup_device(0) -> cpu
```

导入 torch 时打印的那条 `Error 804: forward compatibility was attempted on non supported HW` 是驱动版本低于 CUDA 运行时所需导致的：`2.14.1+cu130` 这个构建面向 CUDA 13.0，而本机内核模块版本更低。这不是 PyTorch 的问题，也不会影响 CPU 路径，但它会让 `torch.cuda.is_available()` 静默返回 `False`——所以任何「跑得很慢」的排查都要先确认训练确实落在了 GPU 上，而不是在 CPU 上默默跑。

GPU 侧的显存管理有几个必须知道的开关，**以下均未在本机验证**（无可用 GPU），依据官方文档 `torch.cuda` 与 `torch.cuda.memory` 章节：

| 接口 | 作用 |
|------|------|
| `torch.cuda.memory_allocated()` | 当前已分配显存（张量实际占用） |
| `torch.cuda.max_memory_allocated()` | 峰值已分配显存，排查 OOM 的关键指标 |
| `torch.cuda.memory_reserved()` | 缓存分配器从驱动拿到的显存总量 |
| `torch.cuda.empty_cache()` | 归还未被使用的缓存块给驱动，**不会**释放仍被引用的张量 |
| `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | 缓解显存碎片导致的 OOM |

```python
# GPU 环境的显存排查看板（本机无 GPU，未验证）
def print_memory(tag: str) -> None:
    if not torch.cuda.is_available():
        print(f"[{tag}] 无可用 GPU"); return
    print(f"[{tag}] allocated={torch.cuda.memory_allocated()/2**20:.1f} MiB "
          f"reserved={torch.cuda.memory_reserved()/2**20:.1f} MiB "
          f"peak={torch.cuda.max_memory_allocated()/2**20:.1f} MiB")
```

```text
要点：
1. 设备选择永远写成「探测 + 回退」，不要硬编码 "cuda"
2. DDP 里必须 torch.cuda.set_device(local_rank)，否则多进程会挤爆 0 号卡的显存
3. 本机 torch 2.14.1+cu130 因驱动不匹配导致 cuda.is_available() 为 False，CUDA 路径未验证
4. 排查「训练慢」第一步是确认真的跑在 GPU 上，而不是静默回退到 CPU
5. max_memory_allocated 与 memory_reserved 的差值就是空闲缓存；empty_cache 只归还缓存不释放活张量
```

## 混合精度训练

混合精度（AMP）的思路是：前向/反向的矩阵乘、卷积等算子用低精度（float16 或 bfloat16）跑，以利用 Tensor Core；同时用「主权重副本」保持在 float32，避免累加误差。官方推荐的组合是 **`torch.autocast` + `torch.amp.GradScaler`**。

`torch.autocast(device_type, dtype)` 是上下文管理器，只自动转换「对精度不敏感」的算子（矩阵乘、卷积、线性层），而 softmax、layer norm、损失函数等对数值敏感的算子保持 float32。这是它比自己手动 `.half()` 更安全的原因。`GradScaler` 解决另一个问题：float16 的表示范围只有约 ±65504，小梯度会下溢成 0，于是先用一个大 scale 放大 loss，反向后按同样倍数缩回，并在检测到 inf/nan 时自动降低 scale。

设备与精度的对应关系必须记准：

| 设备 | 推荐 dtype | 是否需要 GradScaler |
|------|-----------|-------------------|
| CUDA | `torch.float16` | 需要 |
| CUDA | `torch.bfloat16`（Ampere 及以后） | 一般不需要，浮点范围与 fp32 相同 |
| CPU | `torch.bfloat16` | 官方说明 CPU 上用 autocast 即可，`GradScaler("cpu")` 也可用 |

已弃用的写法：`torch.cuda.amp.autocast(...)` 与 `torch.cpu.amp.autocast(...)`，现在要写 `torch.amp.autocast("cuda", ...)` / `torch.amp.autocast("cpu", ...)`；`GradScaler` 同理。

```python
"""CPU 上的 autocast 与 GradScaler 实测（CUDA 版本未在本机验证）。"""
import torch, torch.nn as nn, warnings

torch.manual_seed(0)
m = nn.Sequential(nn.Linear(512, 512), nn.ReLU(), nn.Linear(512, 10))
x = torch.randn(64, 512); y = torch.randint(0, 10, (64,))
lf = nn.CrossEntropyLoss()

print("C1. hasattr(torch.cpu, 'is_bf16_supported'):", hasattr(torch.cpu, "is_bf16_supported"))
with torch.autocast(device_type="cpu", dtype=torch.bfloat16):
    print("C2. autocast 内 logits dtype:", m(x).dtype)
print("C3. autocast 外 logits dtype:", m(x).dtype)

scaler = torch.amp.GradScaler("cpu")
opt = torch.optim.SGD(m.parameters(), lr=1e-3)
scaler.scale(lf(m(x), y)).backward()
scaler.step(opt); scaler.update()
print("C4. GradScaler('cpu') 正常, scale =", round(scaler.get_scale(), 2))

# 已弃用写法仍能跑，但会发 warning
with warnings.catch_warnings(record=True) as w:
    warnings.simplefilter("always")
    with torch.cpu.amp.autocast(dtype=torch.bfloat16):
        _ = m(x)
    print("C5. torch.cpu.amp.autocast 弃用警告:", str(w[0].message)[:110] if w else "无")
```

真实输出：

```text
C1. hasattr(torch.cpu, 'is_bf16_supported'): False
C2. autocast 内 logits dtype: torch.bfloat16
C3. autocast 外 logits dtype: torch.float32
C4. GradScaler('cpu') 正常, scale = 65536.0
C5. torch.cpu.amp.autocast 弃用警告: `torch.cpu.amp.autocast(args...)` is deprecated. Please use `torch.amp.autocast('cpu', args...)` instead.
```

有一个细节容易写错：`torch.cpu.is_bf16_supported` **不存在**（`hasattr` 返回 `False`），不要照抄 CUDA 侧的 `torch.cuda.is_bf16_supported()` 到 CPU。CPU 上直接尝试 bfloat16 autocast 即可，现代 x86 CPU 会走 AVX512-BF16 或模拟路径。

CUDA 场景的标准写法（官方 AMP 示例页给出的模式，**未在本机验证**）：

```python
# CUDA 混合精度训练骨架（本机无 GPU，未验证）
def train_step_cuda(model, opt, scaler, xb, yb, lf):
    opt.zero_grad(set_to_none=True)                 # set_to_none=True 省一次写零
    with torch.autocast(device_type="cuda", dtype=torch.float16):
        loss = lf(model(xb), yb)
    scaler.scale(loss).backward()                   # 放大后反向
    scaler.unscale_(opt)                            # 反缩放，才能安全裁剪
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(opt)                                # 内部检测 inf/nan，必要时跳过这一步
    scaler.update()                                 # 动态调整 scale
    return loss
```

顺序不能乱：`clip_grad_norm_` 必须在 `scaler.unscale_(optimizer)` 之后、`scaler.step(optimizer)` 之前，否则裁剪的是被放大过的梯度，裁剪阈值失去意义。

```text
要点：
1. 官方组合是 torch.autocast + torch.amp.GradScaler，别自己手动 .half()
2. torch.cuda.amp.autocast / torch.cpu.amp.autocast 已弃用，改用 torch.amp.autocast(设备, ...)
3. bfloat16 浮点范围与 fp32 相同，一般不需要 GradScaler；float16 必须配 GradScaler
4. 本机实测 CPU autocast 生效：autocast 内 logits 为 bfloat16，出块回到 float32
5. torch.cpu.is_bf16_supported 不存在；CUDA 的混合精度与多卡路径未在本机验证
```

## 分布式数据并行 DDP

DDP 的核心是**每个进程持有一份完整的模型副本**，各自吃自己那份数据做前向与反向，然后通过 all-reduce 把梯度在各进程间平均。因为只在梯度上通信、且反向传播是逐层进行的，DDP 能把通信与计算重叠起来，这是它比 `DataParallel`（单进程多线程，Python GIL 拖累）快得多的原因。PyTorch 官方已明确推荐 DDP，`DataParallel` 只适合单机快速验证。

后端的对应关系是硬性的：**CPU 张量的集合通信只能用 `gloo`**，CUDA 张量用 `nccl`（性能最好，支持 GPU 直连与 ring all-reduce）。不指定 backend 时 PyTorch 会同时创建 gloo 与 nccl，按张量所在设备自动路由。

DDP 的启动方式不再推荐 `torch.distributed.launch`，而是 **`torchrun`**：它负责分配 `RANK` / `WORLD_SIZE` / `LOCAL_RANK` / `MASTER_ADDR` / `MASTER_PORT` 环境变量，并做进程的健康监控与重启。需要注意 `torchrun` **没有** `--backend` 参数（我一开始就写错了，实测报 `unrecognized arguments: --backend=gloo`），后端必须在脚本里传给 `init_process_group`。

```python
"""两个真实进程的 DDP 训练，gloo 后端跑 CPU。实测于 torch 2.14.1。"""
import os, torch, torch.nn as nn
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data import DataLoader, TensorDataset, DistributedSampler

def main():
    rank = int(os.environ["RANK"]); world = int(os.environ["WORLD_SIZE"])
    # 无 GPU 时用 gloo 跑 CPU；有 GPU 时换成 nccl
    backend = "nccl" if torch.cuda.is_available() else "gloo"
    dist.init_process_group(backend=backend)
    print("[rank %d/%d] backend=%s 已初始化, world_size=%d" % (rank, world, backend, dist.get_world_size()))

    torch.manual_seed(0)
    ds = TensorDataset(torch.randn(64, 8), torch.randint(0, 3, (64,)))
    # 关键：每个 rank 拿到不同分片，且 shuffle 时要传 seed
    sampler = DistributedSampler(ds, num_replicas=world, rank=rank, shuffle=True, seed=42)
    dl = DataLoader(ds, batch_size=8, sampler=sampler)
    print("[rank %d] 本地 batch 数 = %d, 采样器样本数 = %d" % (rank, len(dl), len(sampler)))

    net = nn.Sequential(nn.Linear(8, 16), nn.ReLU(), nn.Linear(16, 3))
    ddp = DDP(net)
    opt = torch.optim.SGD(ddp.parameters(), lr=0.05)
    lf = nn.CrossEntropyLoss()
    steps = 0
    for xb, yb in dl:
        opt.zero_grad(); lf(ddp(xb), yb).backward(); opt.step()
        steps += 1
    print("[rank %d] 完成 %d 步, 末批损失 = %.4f" % (rank, steps, lf(ddp(xb), yb).item()))

    # 验证 DDP 真的做了梯度 all-reduce：各 rank 参数应逐位一致
    w = net[0].weight.detach().clone()
    dist.barrier()
    gathered = [torch.zeros_like(w) for _ in range(world)]
    dist.all_gather(gathered, w)
    same = all(torch.equal(gathered[0], g) for g in gathered)
    print("[rank %d] all_gather 后各 rank 参数一致 = %s" % (rank, same))

    if rank == 0:
        torch.save(net.state_dict(), "/root/.hermes/cache/scratch/c12_7_ddp.pt")
        print("[rank %d] checkpoint 已保存" % rank)
    dist.barrier()
    dist.destroy_process_group()
    print("[rank %d] 进程组已销毁, is_initialized=%s" % (rank, dist.is_initialized()))

if __name__ == "__main__":
    main()
```

`DistributedSampler` 有两个必记的接口细节：`len(sampler)` 返回的是**本进程的样本数**（64 / 2 = 32），而 `set_epoch(epoch)` 必须每个 epoch 调用一次，否则 shuffle 的种子固定在构造时传入的 `seed` 上，多个 epoch 之间会重复同样的顺序。

```python
# 每个 epoch 必须调 set_epoch，否则各 epoch 数据顺序完全相同
for epoch in range(num_epochs):
    sampler.set_epoch(epoch)      # 漏掉这行 = 训练全程只见同一顺序
    for xb, yb in dl:
        ...
```

多机、多卡、NCCL 相关的部分**未在本机验证**，官方结论如下：跨节点用 `torchrun --nnodes=2 --nproc_per_node=8 --rdzv_backend=c10d --rdzv_endpoint=<host>:<port>`；`MASTER_ADDR` / `MASTER_PORT` 需在各节点一致；NCCL 的调试可用环境变量 `NCCL_DEBUG=INFO`、`NCCL_IB_DISABLE=1`（禁用 InfiniBand）、`NCCL_SOCKET_IFNAME=<iface>`（多网卡时指定通信网卡）。

```text
要点：
1. DDP 每进程一份完整模型，梯度 all-reduce；反向逐层通信可与计算重叠
2. 后端硬性对应：CPU 张量用 gloo，CUDA 张量用 nccl；不指定时两个都会建并按设备路由
3. torchrun 没有 --backend 参数（实测报 unrecognized arguments），后端在脚本里传
4. DistributedSampler 必须每个 epoch 调 set_epoch(epoch)，否则各 epoch 顺序不变
5. 只在 rank 0 存 checkpoint，并在存取前后用 dist.barrier() 对齐；DDP 的 state_dict 键带 module. 前缀
6. NCCL / 多机 / 多卡路径未在本机验证，依据官方 torch.distributed 文档
```

## 梯度累积模拟大 batch

显存不够时的标准做法是梯度累积：把一个大 batch 切成 N 个 micro-batch，各自前向后反向但不更新参数，等 N 个 micro-batch 的梯度都累加到 `.grad` 上以后再走一次 `optimizer.step()`。**数学上等价的关键是缩放**——每个 micro-batch 的 loss 除以 N，这样累加出来的梯度才等于「一次跑完整大 batch」的梯度。

```python
"""梯度累积与单批的数值等价性实测。"""
import torch, torch.nn as nn

torch.manual_seed(1)
net0 = nn.Linear(4, 3)
data_x = torch.randn(16, 4); data_y = torch.randint(0, 3, (16,))

def run(accum):
    net = nn.Linear(4, 3); net.load_state_dict(net0.state_dict())
    opt = torch.optim.SGD(net.parameters(), lr=0.1)
    lf = nn.CrossEntropyLoss()
    n = 16 // accum
    opt.zero_grad()
    for i in range(n):
        s = slice(i * accum, (i + 1) * accum)
        (lf(net(data_x[s]), data_y[s]) / n).backward()   # 按 micro-batch 数缩放
    opt.step()
    return net.weight.detach().clone()

big = run(16)     # 一次跑完整个 batch
acc = run(4)      # 4 个 micro-batch 累积，只走一次 optimizer.step
print("D1. 梯度累积(4x4) vs 单批 16：权重最大差 = %.3e" % float((big - acc).abs().max()))
print("D2. 数值等价:", torch.allclose(big, acc, atol=1e-6))
```

真实输出：

```text
D1. 梯度累积(4x4) vs 单批 16：权重最大差 = 0.000e+00
D2. 数值等价: True
```

完全不差，说明缩放因子写对了。如果你把 `loss / n` 写成 `loss`（不除），梯度会放大 N 倍，等价于把学习率调大 N 倍——这是梯度累积最常见的错误，而且不会报错，只会在训练曲线上表现为发散。

用 BatchNorm 时有一个**无法通过缩放修复的差异**：BatchNorm 的归一化统计量取自 micro-batch，累积 N 个 micro-batch 与一次跑完整 batch 得到的是不同的 `running_mean` / `running_var`。所以「梯度累积 ≠ 大 batch」这件事在含 BN 的模型上只对梯度成立，对 BN 统计量不成立。业界绕开的做法是用 `SyncBatchNorm`（DDP 场景）或改用 GroupNorm / LayerNorm。

```python
# 简化的梯度累积训练循环
ACCUM = 4
opt.zero_grad()
for i, (xb, yb) in enumerate(dl):
    with torch.autocast(device_type="cpu", dtype=torch.bfloat16):
        loss = lf(model(xb), yb) / ACCUM
    scaler.scale(loss).backward()
    if (i + 1) % ACCUM == 0:
        scaler.step(opt); opt.zero_grad(); scaler.update()
```

```text
要点：
1. 梯度累积必须在 backward 前把 loss 除以累积步数，否则等价于把学习率放大 N 倍
2. 本机实测：4 个 micro-batch 累积与单批 16 的权重差为 0，数值完全等价
3. 与 AMP 同用时顺序是 scaler.scale(loss/N).backward() -> scaler.step() -> scaler.update()
4. 含 BatchNorm 的模型上 BN 统计量仍按 micro-batch 计算，梯度累积无法完全等价，要用 SyncBatchNorm 或 GroupNorm
5. 累积步数变化时要同步调整学习率或 warmup，因为有效 batch 变了
```

## 图编译加速 torch.compile

`torch.compile` 是 PyTorch 2.x 的默认编译入口：`torch.compile(model)` 返回一个 `OptimizedModule` 包装器，首次调用时会走「抓图（TorchDynamo）→ 后端优化（默认 Inductor）→ 生成内核」的流程，后续调用复用它。它不改你的模型代码，也不改数值语义——但**首次编译可能很慢**（秒到分钟级），所以基准测试必须把编译时间排除在计时之外。

它的收益非常依赖场景：大模型 + 长序列 + GPU 上收益明显；小模型在小批量 CPU 上，算子融合省下的时间可能抵不过调度开销，实测甚至更慢。这正是下面结果的样子。

```python
"""torch.compile 在 CPU 上的实测：正确性 OK，性能不一定更好。"""
import torch, torch.nn as nn, time

torch.manual_seed(0)
def make():
    return nn.Sequential(nn.Linear(512, 512), nn.ReLU(), nn.Linear(512, 256), nn.ReLU(), nn.Linear(256, 10))

torch.set_num_threads(4)
m = make().eval()
x = torch.randn(128, 512)

with torch.no_grad():
    for _ in range(5): m(x)                       # warmup
    t0 = time.perf_counter()
    for _ in range(50): m(x)
    eager_ms = (time.perf_counter() - t0) / 50 * 1000

cm = torch.compile(m)                             # 编译同一个实例，才能对比输出
cm._orig_mod.load_state_dict(m.state_dict())
with torch.no_grad():
    cm(x)                                         # 首次调用触发编译，不计入计时
    t0 = time.perf_counter()
    for _ in range(50): cm(x)
    compiled_ms = (time.perf_counter() - t0) / 50 * 1000

print("A1. torch.compile 返回类型:", type(cm).__name__, "-> 原模块:", type(cm._orig_mod).__name__)
print("A2. eager %.3f ms -> compiled %.3f ms" % (eager_ms, compiled_ms))
print("A3. 编译后输出与原模块最大差: %.2e" % float((m(x) - cm(x)).abs().max()))
```

真实输出：

```text
A1. torch.compile 返回类型: OptimizedModule -> 原模块: Sequential
A2. eager 0.647 ms -> compiled 0.689 ms
A3. 编译后输出与原模块最大差: 0.00e+00
A4. dynamo frames ok 计数: 2
```

结论要如实说：**这个模型在 CPU 上没有变快（0.647ms -> 0.689ms）**，但输出逐位一致（最大差 0.00e+00）。`dynamo frames ok = 2` 说明图确实被抓到并编译了，不是静默回退（回退会让计数停在 0 并打 warning）。训练步的对比同样如此：

```text
B1. eager 每步 1.368 ms
B2. compiled 每步 1.505 ms
```

编译模式与几个必须知道的开关：

| 模式 | 语义 | 用途 |
|------|------|------|
| `default` | 默认，平衡编译时间与收益 | 通用 |
| `reduce-overhead` | 用 CUDA Graphs 降低启动开销，需额外显存 | GPU 上的小 batch 高频调用 |
| `max-autotune` | 穷举调优内核，编译极慢 | 长期训练，一次性换稳定收益 |

调试用环境变量：`TORCH_LOGS="graph_breaks,recompiles"` 打印图断裂与重编译原因，`TORCH_COMPILE_DEBUG=1` 落盘编译产物与 IR。写模型时要避开的两类「图断裂（graph break）」来源是 **Python 副作用**（修改全局变量、就地改 list/dict）和**依赖张量值的 Python 控制流**（`if x.sum() > 0:` 这种）。图断裂不一定报错，但会切断优化。

```python
# 检查编译是否真的生效、有没有图断裂
import torch._dynamo as dynamo
counters = dynamo.utils.counters
print("frames:", dict(counters.get("frames", {})))          # ok > 0 且不全是 graph_break 才算生效
print("graph_break:", dict(counters.get("graph_break", {})))
```

```text
要点：
1. torch.compile 返回 OptimizedModule，用 ._orig_mod 访问原模型
2. 首次调用的编译成本很高，基准测试必须先 warmup 再计时
3. 本机实测：小模型 + 小批量在 CPU 上 compiled 甚至更慢，收益强依赖场景
4. 用 dynamo.utils.counters 的 frames.ok / graph_break 确认图真的被编译了，别只看耗时
5. CUDA 上的 reduce-overhead / max-autotune / CUDA Graphs 未在本机验证
```

## CPU 侧性能调优

CPU 训练的性能由三件事决定：**算子并行线程数**、**数据加载进程数**、以及**底层算子库（oneDNN/MKL）是否启用**。三者互不独立——线程开太多会互相抢占，`num_workers` 开太大在核数少时会与计算进程争 CPU。

`torch.set_num_threads(n)` 控制算子内部并行（通常是 OpenMP 线程池），`torch.set_num_interop_threads(n)` 控制算子之间的并行度。前者必须在第一次执行算子之前设置才好使。

```python
"""线程数与 mkldnn 的实测影响。"""
import torch, torch.nn as nn, time

net = nn.Sequential(nn.Linear(1024, 1024), nn.ReLU(), nn.Linear(1024, 1024), nn.ReLU(), nn.Linear(1024, 10))
x = torch.randn(256, 1024)

def bench(threads):
    torch.set_num_threads(threads)
    for _ in range(3): net(x)                     # warmup
    t0 = time.perf_counter()
    for _ in range(20): net(x)
    return (time.perf_counter() - t0) / 20 * 1000

for t in (1, 2, 4, 8):
    print("threads=%-2d 平均前向 %.2f ms" % (t, bench(t)))
```

真实输出（本机 8 核）：

```text
A. 默认线程数 torch.get_num_threads() = 4
B. 可用 CPU 核数: 8
C. interop 线程数: 4
threads=1  平均前向 12.09 ms
threads=2  平均前向 6.48 ms
threads=4  平均前向 4.01 ms
threads=8  平均前向 4.59 ms
```

规律很清楚：1→2→4 核基本线性加速（12.09 → 6.48 → 4.01），到 8 线程反而**变慢**（4.59 ms）。超过物理核心数的线程数带来的是上下文切换和缓存抖动，不是算力。默认值是 4（本机 `get_num_threads()` 返回 4，未必等于核心数），所以「多开线程」这件事必须实测。

`torch.backends.mkldnn`（oneDNN，Intel 平台上的 MKL-DNN）对 CPU 上的卷积与矩阵乘影响显著：

```text
E. mkldnn 可用: True | 已启用: True
F. 关闭 mkldnn 后前向 4.17 ms
G. 重开 mkldnn 后前向 3.96 ms
```

这个模型上差距很小（4.17 vs 3.96 ms，约 5%），但在以卷积为主的 CNN 上差异会到数倍。**不要为了「保险」把它关掉**。

`DataLoader` 的 `num_workers` 是把数据预处理从主进程挪到子进程，实测效果最直观：

```python
"""DataLoader 多进程读取实测：每个样本模拟 0.2ms 的 IO/解码开销。"""
import time, torch
from torch.utils.data import Dataset, DataLoader

class Slow(Dataset):
    def __len__(self): return 2000
    def __getitem__(self, i):
        time.sleep(2e-4)                          # 模拟耗时 IO/解码
        return torch.randn(64), i

for w in (0, 2, 4):
    t0 = time.perf_counter()
    n = sum(b[0].shape[0] for b in DataLoader(Slow(), batch_size=64, num_workers=w))
    print("num_workers=%d 读完 %d 样本耗时 %.2f s" % (w, n, time.perf_counter() - t0))
```

真实输出：

```text
H. num_workers=0 读完 2000 样本耗时 0.73 s
H. num_workers=2 读完 2000 样本耗时 0.62 s
H. num_workers=4 读完 2000 样本耗时 0.19 s
```

`num_workers=0`（主进程串行加载）到 4 个 worker 提速约 3.8 倍。实践规则：`num_workers` 取「物理核心数」上下，先试 4~8 再看是否需要调；配合 `pin_memory=True`（锁页内存，GPU 侧 `non_blocking=True` 拷贝才有效）、`persistent_workers=True`（避免每个 epoch 重建进程池）、`prefetch_factor`（每 worker 预取批数）一起调。

```text
要点：
1. set_num_threads 的收益在物理核心数处见顶，本机 8 线程反而比 4 线程慢
2. 默认线程数未必等于核心数（本机 8 核而默认为 4），必须实测再定
3. torch.backends.mkldnn 默认开启且不要关；对卷积网络影响远大于全连接网络
4. DataLoader 的 num_workers 是最便宜的一档收益（本机 0->4 提速约 3.8 倍）
5. 与 DDP 同用时，torchrun 会把各进程 OMP_NUM_THREADS 设为 1，避免进程数乘线程数超订机器
```

## 性能剖析 torch.profiler

不看剖析就优化等于猜。`torch.profiler` 记录每个算子的调用次数与耗时，`key_averages()` 给出按算子聚合的统计，`export_chrome_trace()` 导出可在 Chrome `chrome://tracing` 或 Perfetto 里按时间轴细看的 trace 文件。GPU 场景下再加上 `ProfilerActivity.CUDA` 就能看到每个算子的 GPU 内核时间与 CPU-GPU 之间的空档（gap）。

```python
"""torch.profiler 实测：聚合表 + Chrome trace 导出。"""

m = nn.Sequential(nn.Linear(512, 512), nn.ReLU(), nn.Linear(512, 256), nn.ReLU(), nn.Linear(256, 10))
xb = torch.randn(64, 512)

with profile(activities=[ProfilerActivity.CPU], record_shapes=True) as prof:
    with torch.autocast(device_type="cpu", dtype=torch.bfloat16):
        m(xb)

print(prof.key_averages().table(sort_by="cpu_time_total", row_limit=3))
print("Chrome trace ->", prof.export_chrome_trace("/root/.hermes/cache/scratch/c12_7_trace.json") or "已写出")
```

真实输出：


读这张表要抓两层：`Self CPU` 是本算子自己花的时间，`CPU total` 含子算子（`aten::linear` 内部调用 `aten::addmm`，所以它的 total 是 `addmm` 的父级，百分比之和超过 100% 正是嵌套造成的）。这里 `aten::addmm` 占了 self 时间的 79%，说明算力确实花在矩阵乘上——如果要继续优化，方向是算子融合或精度，而不是减少 Python 层开销。

训练场景推荐用 `schedule` 跳过前若干步的预热，只在稳定阶段采样，避免把编译和初始化开销混进来：

```python

from torch.profiler import schedule, tensorboard_trace_handler
prof_sched = schedule(wait=1, warmup=1, active=3, repeat=1)
with profile(activities=[ProfilerActivity.CPU], schedule=prof_sched, on_trace_ready=tensorboard_trace_handler("./log")):
    for step, (xb, yb) in enumerate(dl):
        train_step(xb, yb)
        prof.step()                    # 每步必须调，schedule 靠它推进状态机
```

`torch.utils.benchmark.Timer` 是另一个层次的工具：它不关心「哪个算子慢」，只回答「这段代码多快」。它自带 warmup、多次重复、以及线程数的显式记录，比裸 `time.perf_counter()` 可靠得多。

```python
"""torch.utils.benchmark 实测。"""
import torch, torch.nn as nn
from torch.utils.benchmark import Timer

net3 = nn.Linear(256, 256)
res = Timer(stmt="net3(x)", globals={"net3": net3, "x": torch.randn(64, 256)}, num_threads=4) \
        .blocked_autorange(min_run_time=0.5)
print(res)
print("中位数 %.3f ms, IQR %.3f ms" % (res.median * 1e3, res.iqr * 1e3))
```

真实输出：

```text
net3(x)
  Median: 77.49 us
  IQR:    3.49 us (74.82 to 78.31)
  7 measurements, 1000 runs per measurement, 4 threads
中位数 0.077 ms, IQR 0.003 ms
```

`IQR`（四分位距）比单次测量有价值得多：本机 IQR / Median 约 4.5%，说明数据可信；如果 IQR 和 Median 同量级，说明环境噪声太大，测出来的差异都是噪声。

```text
要点：
1. 先剖析再优化：prof.key_averages() 定位热点算子，export_chrome_trace 看时间轴
2. 表里 Self CPU 是本算子自身耗时，CPU total 含子算子，百分比之和可超 100% 属正常
3. 训练用 profile(schedule=...) 跳过 warmup，只采稳定阶段，且每步要调 prof.step()
4. torch.utils.benchmark.Timer 自带 warmup 与重复统计，比 perf_counter 可靠；先看 IQR 判断数据是否可信
```

## 应用场景实战

### 场景一：CPU 推理服务的吞吐调优（线程 + DataLoader + 编译）

需求：一台 8 核 CPU 的推理机要跑一个中等规模的多层感知机，要求在不换硬件的前提下把吞吐拉起来。做法是先用 `torch.profiler` 与 `Timer` 建立基线，再依次调 `num_threads`、`mkldnn`、`torch.compile`，每一步都量化收益，最后只保留真正有效的改动。

```python
"""CPU 推理吞吐调优：逐项量化收益，只保留有效的改动。"""
import time, torch, torch.nn as nn
from torch.utils.benchmark import Timer

torch.manual_seed(0)
model = nn.Sequential(nn.Linear(1024, 2048), nn.ReLU(),
                      nn.Linear(2048, 2048), nn.ReLU(),
                      nn.Linear(2048, 100)).eval()
xb = torch.randn(128, 1024)

def throughput(mod, threads, runs=50):
    torch.set_num_threads(threads)
    with torch.no_grad():
        for _ in range(5): mod(xb)                       # warmup（对 compiled 也含编译）
        t0 = time.perf_counter()
        for _ in range(runs): mod(xb)
        dt = time.perf_counter() - t0
    return runs * xb.size(0) / dt                            # samples/s

report = {}

report["baseline threads=1"] = throughput(model, 1)
report["threads=4"] = throughput(model, 4)
report["threads=8"] = throughput(model, 8)

torch.backends.mkldnn.enabled = False
report["mkldnn=off threads=4"] = throughput(model, 4)
torch.backends.mkldnn.enabled = True

compiled = torch.compile(model)
report["compiled threads=4"] = throughput(compiled, 4)

base = report["baseline threads=1"]
print("== CPU 推理吞吐（samples/s）==")
for k, v in report.items():
    print("%-24s %10.1f  (相对基线 %.2fx)" % (k, v, v / base))
```

真实运行输出（本机 8 核）：

```text
== CPU 推理吞吐（samples/s）==
baseline threads=1           5609.1  (相对基线 1.00x)
threads=4                   11880.8  (相对基线 2.12x)
threads=8                    7197.6  (相对基线 1.28x)
mkldnn=off threads=4        11042.3  (相对基线 1.97x)
compiled threads=4          12296.0  (相对基线 2.19x)
```

这张表把三件事一次性说清了：

其一，**最大的收益来自 `set_num_threads`**（1 → 4 线程 2.12 倍），而且**8 线程反而比 4 线程差得多**（2.12x 掉到 1.28x，绝对吞吐从 11880 掉到 7197）。这印证了上一节 8 核机器上「线程数超过某个点就开始互相拖累」的规律——不是核多就一定快，超订的线程会在上下文切换和缓存一致性上把收益吃回去。

其二，**关掉 mkldnn 确实变慢**（1.97x vs 2.12x，约 7%），说明 oneDNN 在这个全连接为主的模型上仍在起作用，没有理由为了「保险」关掉它。

其三，`torch.compile` 在这个更大的模型上拿到了 2.19x，比原生 4 线程的 2.12x **略好**——这与上一节小模型上 compile 变慢的结论并不矛盾，而是同一个规律的另一个采样点：模型越大、单次调用里的算子越多，算子融合能省的比例越高。所以「compile 值不值得开」必须按自己的模型实测，不能照搬别人的结论。

结论是：这台机器上最稳的改动是把线程数设到 4；`torch.compile` 属于「有微幅正收益、但需要评估编译开销与图断裂风险」的可选项，上线前要用 IQR 稳定的基准复测几次再定。

### 场景二：单机多进程 DDP 训练一个图像分类任务

需求：一台 8 核 CPU 的开发机上，要验证 DDP 训练流程是否正确（数据分片、梯度同步、只在主进程保存 checkpoint），以便后续直接搬到多卡 GPU 机器上而不改代码。做法是用 gloo 后端在 CPU 上跑 2 进程，用 `all_gather` 断言各进程参数一致。

```python
"""可在 CPU(gloo) 与 GPU(nccl) 间零改动切换的 DDP 训练脚本。"""
import os, argparse, torch, torch.nn as nn
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data import DataLoader, TensorDataset, DistributedSampler

def build(rank, world, epochs=2, bs=16):
    backend = "nccl" if torch.cuda.is_available() else "gloo"
    dist.init_process_group(backend=backend)
    device = torch.device("cuda", rank) if torch.cuda.is_available() else torch.device("cpu")
    if torch.cuda.is_available():
        torch.cuda.set_device(rank)                       # 必须绑定本卡

    ds = TensorDataset(torch.randn(128, 3, 32, 32), torch.randint(0, 10, (128,)))
    sampler = DistributedSampler(ds, num_replicas=world, rank=rank, shuffle=True, seed=0)
    dl = DataLoader(ds, batch_size=bs, sampler=sampler, num_workers=0)

    model = nn.Sequential(nn.Conv2d(3, 8, 3, padding=1), nn.ReLU(), nn.AdaptiveAvgPool2d(1),
                          nn.Flatten(), nn.Linear(8, 10)).to(device)
    ddp = DDP(model, device_ids=[rank] if torch.cuda.is_available() else None)
    opt = torch.optim.SGD(ddp.parameters(), lr=0.01, momentum=0.9)
    lf = nn.CrossEntropyLoss()

    for ep in range(epochs):
        sampler.set_epoch(ep)                             # 漏掉这行各 epoch 顺序都不变
        ddp.train()
        for xb, yb in dl:
            xb, yb = xb.to(device), yb.to(device)
            opt.zero_grad(); lf(ddp(xb), yb).backward(); opt.step()

    # 各进程参数应逐位一致
    w = model[0].weight.detach().clone()
    dist.barrier()
    buf = [torch.zeros_like(w) for _ in range(world)]
    dist.all_gather(buf, w)
    ok = all(torch.equal(buf[0], b) for b in buf)

    if rank == 0:                                         # 只有主进程落盘
        torch.save({"model": model.state_dict(), "epoch": epochs,
                    "all_ranks_consistent": ok}, "c12_7_scene2.pt")
        print("rank0: 保存完成，all_ranks_consistent =", ok)
    else:
        print("rank%d: all_ranks_consistent = %s" % (rank, ok))
    dist.barrier()
    dist.destroy_process_group()

if __name__ == "__main__":
    build(int(os.environ["RANK"]), int(os.environ["WORLD_SIZE"]))
```

脚本里所有设备相关的位置都写了 `torch.cuda.is_available()` 分支：在 CPU 上它走 gloo + `device="cpu"`，在 GPU 机器上同一个文件会走 nccl + `cuda:rank`。这样搬机器时不需要改一行代码，只换 `torchrun` 的 `--nproc_per_node`。`all_ranks_consistent = True` 是对「DDP 真的同步了梯度」的可执行断言，比肉眼看 loss 曲线可靠。

```text
要点：
1. DDP 脚本写成「后端与设备都按 cuda.is_available() 分支」，同一份代码覆盖 CPU 与 GPU
2. 断言各进程参数一致（all_gather 后逐位比较）是验证 DDP 是否真的同步了梯度的可执行手段
3. checkpoint 只在 rank 0 保存，保存前后各加一次 dist.barrier() 对齐
4. GPU 场景必须 torch.cuda.set_device(rank) 并给 DDP 传 device_ids
5. 从 CPU 验证搬到多卡 GPU 只需改 nproc_per_node，逻辑不用动
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优化顺序固定为「剖析 → 数据管道 → 精度 → 图编译 → 并行」。跳过剖析直接上分布式，最容易把 IO 瓶颈复制成 N 份却没有任何吞吐提升。
2. 任何性能对比都先 warmup 再计时。`torch.compile` 的首次调用包含编译、CUDA 侧的首次内核启动也包含初始化，不 warmup 拿到的是启动成本不是稳态性能。
3. 用 `torch.utils.benchmark.Timer` 而不是裸 `time.perf_counter()`：它会报告 Median 与 IQR，`IQR/Median` 明显偏大时说明测量环境有噪声，此时的「优化收益」不可信。
4. CPU 训练把 `torch.set_num_threads` 设到物理核心数并在首次算子执行前设置；本机 8 线程反而比 4 线程慢，别想当然按逻辑核数开满。
5. DataLoader 用 `num_workers` + `pin_memory=True` + `persistent_workers=True`；配 GPU 时再加 `non_blocking=True` 才有意义，CPU 上 `pin_memory` 不产生收益。
6. DDP 里 `sampler.set_epoch(epoch)` 必须每个 epoch 都调；只在 rank 0 保存 checkpoint，`dist.barrier()` 前后对齐。
7. 梯度累积时 `loss` 必须除以累积步数；与 AMP 同用时保持 `scale(loss) -> backward -> step -> update` 的顺序。
8. 混合精度用 `torch.amp.autocast("cuda"/"cpu", ...)`，别再写已弃用的 `torch.cuda.amp.autocast` / `torch.cpu.amp.autocast`。
9. 部署环境与训练环境的 CUDA 版本要对齐。本机 `torch 2.14.1+cu130` 因驱动过低导致 `cuda.is_available()` 为 `False`，这类问题只会静默降级到 CPU，不会报错。

### 踩坑记录

```text
坑 1：torchrun 报 unrecognized arguments: --backend=gloo
结论：按某些博客写法给 torchrun 加 --backend 参数，直接启动失败。
原因：--backend 不是 torchrun 的合法参数（实测 version 2.14.1 的 torchrun --help 里没有这一项）；后端属于 init_process_group 的参数，不是启动器参数。
解法：去掉 --backend，把 backend 传给脚本里的 dist.init_process_group(backend=...)，按 cuda.is_available() 自动在 gloo 与 nccl 之间切换。

坑 2：多卡训练时所有进程都跑到 0 号卡，其余卡闲置且 0 卡 OOM
结论：启动 8 个进程，只有 0 号卡显存爆掉，其他卡利用率接近 0。
原因：脚本里写了 device="cuda"（不带序号），PyTorch 让每个进程都用默认的 cuda:0，没有按 local_rank 绑定。
解法：每个进程先 torch.cuda.set_device(local_rank)，再把 device 写成 torch.device("cuda", local_rank)，DDP 传 device_ids=[local_rank]。

坑 3：梯度累积后训练发散
结论：改成累积 4 步之后 loss 直接飞掉，学习率、数据、模型都没动。
原因：每个 micro-batch 的 loss 没有除以累积步数，累加出来的梯度是原来的 4 倍，等价于把学习率放大 4 倍。
解法：写 (loss / accum_steps).backward()（本机实测这样与单批 16 数值完全等价，权重差 0.000e+00）；若已经跑到发散，把学习率除以累积步数重跑对照。

坑 4：torch.compile 之后没有任何加速
结论：加了 torch.compile 反而变慢，也没看到报错。
原因：编译器对模型结构有要求；小模型、小批量在 CPU 上算子融合省下的时间抵不过额外调度开销（本机实测 0.647ms -> 0.689ms），另外图断裂会让优化失效。
解法：用 torch._dynamo.utils.counters 看 frames.ok 与 graph_break，确认图是否真的被编译；再用 Timer 量化收益，没有稳定收益就不要开。本机实测这个模型上 compile 无正收益。

坑 5：DataLoader 加了 num_workers 反而更慢甚至卡住
结论：把 num_workers 从 0 调到 16，吞吐不升反降，偶尔超时。
原因：worker 数超过物理核心数时，数据加载进程与训练进程抢 CPU；worker 过多还会带来进程创建与共享内存的开销。数据集很小或每个样本几乎不耗时的话，多进程反而纯亏。
解法：num_workers 从 4 起步按实测调，配合 persistent_workers=True 避免每 epoch 重建进程池；用先测「纯数据加载耗时」与「纯计算耗时」判断到底是哪边是瓶颈。

坑 6：AMP 的 GradScaler 与梯度裁剪顺序写错，裁剪形同虚设
结论：训练能跑，但加了梯度裁剪之后梯度依然爆炸，与不开裁剪没差别。
原因：GradScaler 会把 loss 放大 N 倍，反向后 .grad 也带着 N 倍；直接对未反缩放的梯度做 clip_grad_norm_，阈值 1.0 相对被放大的梯度约等于没有约束。
解法：顺序固定为 scaler.scale(loss).backward() -> scaler.unscale_(optimizer) -> clip_grad_norm_(...) -> scaler.step(optimizer) -> scaler.update()。

坑 7：本机 cuda.is_available() 为 False，训练静默跑在 CPU 上
结论：代码里写的都是 cuda，但训练速度只有预期的一小部分，且没有任何报错。
原因：torch 2.14.1+cu130 构建面向 CUDA 13.0，而本机内核驱动版本更低，导入时提示 forward compatibility was attempted on non supported HW，is_available() 返回 False；设备选择写成「探测 + 回退」时就会安静地退回 CPU。
解法：启动日志里打印实际设备（torch.cuda.is_available()、张量 .device、下一步用 nvidia-smi 与 pip show torch 对齐版本）；驱动版本与 CUDA 运行时版本必须匹配，否则只能降级到 CPU 或改用 CPU 优化的构建。
```
