## 概述

训练脚本跑出 `state_dict` 只是开始，部署要解决的是另一个问题：把「依赖 Python 代码 + 动态图」的模型变成「能在没有 PyTorch 开发环境、没有 Python 解释器、甚至没有操作系统的地方跑起来」的产物。PyTorch 提供三条路线：`torch.export` 导出 `ExportedProgram`（.pt2，PT2 生态的正式产物）、**ONNX** 导出成跨框架标准格式（配 ONNX Runtime 推理）、以及 **ExecuTorch** 落成 `.pte` 上手机/边缘设备。TorchScript 是上一代方案，本机实测 `torch.jit.trace/script/freeze` 在 2.14 全部带 `FutureWarning: ... is deprecated. Please switch to torch.compile or torch.export`，Lite Interpreter 也提示迁移到 ExecuTorch——新项目不要再从 TorchScript 起步。

```text
本篇主线：
1. TorchScript 的现状 —— trace/script 的真实差异、freeze 的 eval 前提、Lite Interpreter 已弃用、XNNPACK 缺失导致 optimize_for_mobile 失败
2. torch.export —— ExportedProgram、.pt2 存取、默认静态形状与 Guard failed 报错、Dim/dynamic_shapes 表达动态维
3. ONNX 导出 —— dynamo 已成为默认后端、opset 与 dynamic_axes/dynamic_shapes 的真实行为、onnxruntime 数值对齐
4. 量化与剪枝 —— 动态量化 / 静态 PTQ 的体积与延迟实测、静态量化必须喂量化输入、剪枝的稀疏率与「不会自动加速」
5. 服务化 —— FastAPI + onnxruntime 的完整服务、健康检查、形状校验、串行与并发 QPS
6. 移动端 —— ExecuTorch 的 export -> to_edge_transform_and_lower -> to_executorch -> .pte 流程（本机未安装，按官方文档）
```

本机实测环境：Ubuntu 24.04、Python 3.12.3、**PyTorch 2.14.1+cu130**（CPU，`torch.cuda.is_available()` 为 False）、**onnx 1.23.2、onnxruntime 1.31.0、onnxscript 0.7.2、onnxruntime 可用 provider 仅 CPUExecutionProvider 与 AzureExecutionProvider**。下文所有 `text` 块均为真实运行输出；无法在本机验证的部分（ExecuTorch、NVIDIA GPU 上的 TensorRT）会明确标注。

## TorchScript 的现状与替代路径

TorchScript 用两种方式把 Python 代码变成可脱离解释器运行的图：`torch.jit.trace` 记录一次前向实际执行的张量流（快、但要小心控制流），`torch.jit.script` 直接编译 Python 源码（支持数据依赖的 `if`、标量参数、非张量类型）。本机 2.14.1 上两者都已标记弃用：

```text
FutureWarning: `torch.jit.trace` is deprecated. Please switch to `torch.compile` or `torch.export`.
FutureWarning: `torch.jit.script` is deprecated. Please switch to `torch.compile` or `torch.export`.
FutureWarning: `torch.jit.freeze` is deprecated. Please use `torch.compile` instead.
DeprecationWarning: Lite Interpreter is deprecated. Please consider switching to ExecuTorch.
```

trace 与 script 的本质差别用一个数据依赖分支就能看出来：

```python
import torch
import torch.nn as nn

# trace：控制流被固化
class Branchy(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = nn.Linear(16, 3)

    def forward(self, x):
        if x.size(0) > 1:            # 数据依赖分支
            return self.fc(x) * 2
        return self.fc(x)


b = Branchy().eval()
bt = torch.jit.trace(b, torch.randn(4, 16))

# script：控制流被编译
class ScriptedNet(nn.Module):
    def __init__(self, d=16, h=32, n_cls=3):
        super().__init__()
        self.fc1, self.fc2, self.fc3 = nn.Linear(d, h), nn.Linear(h, h), nn.Linear(h, n_cls)

    def forward(self, x, temperature: float = 1.0):      # 支持非张量参数
        h = torch.relu(self.fc1(x))
        h = torch.relu(self.fc2(h))
        if h.size(0) > 1:                                # 支持数据依赖控制流
            h = h - h.mean(dim=0, keepdim=True)
        return self.fc3(h) / temperature


sm = torch.jit.script(ScriptedNet())
```

几个必须记住的语义：

- `trace` 对同一份输入一定数值一致，但**数据依赖的控制流会被写成常量**（本机 `Branchy` 在 batch=1 下 eager 输出 0.78135、traced 输出 0.2196，因为 `batch>1` 的分支被固化成了 True）。
- `trace` 出来的模块保留样例模型的 `training` 标志（`traced.training = False` 是因为样例传了 `.eval()`），所以导出前务必 `model.eval()`。
- `torch.jit.freeze` 只能用于 eval 模式：把 Dropout/BatchNorm 融进前向的前提是它们不再需要训练态。本机实测在 training 模式且含 Dropout 时报 `RuntimeError: Freezing is currently only implemented for modules in eval mode.`；eval 模式下 freeze 成功，Dropout 被彻底消除（同一输入两次前向结果完全相同）。
- `optimize_for_mobile` 依赖编译期开启的 XNNPACK：本机 PyTorch wheel 未开启，因此该函数直接抛内部断言。要真做移动端部署，转 ExecuTorch 更现实。

```text
要点：
1. 2.14 上 torch.jit.trace / script / freeze 全部带弃用 FutureWarning，新项目直接用 torch.export
2. trace 只适合「无数据依赖控制流 + 固定输入结构」的模型；有 if/循环判断就得上 script
3. freeze 之前必须 model.eval()，否则含 Dropout/BatchNorm 的模型直接报错
4. Lite Interpreter（._save_for_lite_interpreter）已弃用，官方指向 ExecuTorch，别在新项目里用
5. optimize_for_mobile 需要 PyTorch 编译时开启 XNNPACK，官方 pip wheel 不一定带，报 INTERNAL ASSERT 时不要怀疑代码
```

## torch.export 与 pt2 导出

`torch.export.export()` 是 PT2 生态的「导出」入口：它用 TorchDynamo 捕获完整图，产出 `ExportedProgram`（可序列化为 `.pt2`）。与 `torch.compile` 的区别是**AOT 而非 JIT**、**必须拿到完整图**（碰到不可捕获的代码直接报错而不是 graph break），因此产物可以脱离 Python 运行；与 `torch.jit.trace` 的区别是它是 sound 的——会记录必要的形状断言，而不是盲目照抄一次执行。

```python
import torch
import torch.nn as nn

model = nn.Sequential(nn.Linear(64, 256), nn.ReLU(), nn.Linear(256, 256), nn.ReLU(), nn.Linear(256, 10)).eval()
x = torch.randn(8, 64)

ep = torch.export.export(model, (x,))              # 默认 strict=True
print(type(ep).__name__)                            # ExportedProgram
print(str(ep.graph_module.graph).splitlines()[:3])  # 参数被提升为 graph 输入（placeholder）

torch.export.save(ep, "model.pt2")                  # 序列化
ep2 = torch.export.load("model.pt2")                # 反序列化
ep2.module()(x)                                     # 直接调用

# 动态 batch：默认导出的形状是静态的，换 batch 会被 Guard 拦住
batch = torch.export.Dim("batch")
ep_dyn = torch.export.export(model, (x,), dynamic_shapes={"x": {0: batch}})
```

官方文档（pytorch.org/docs/stable/user_guide/torch_compiler/export.html）里几条需要记住的约束：

- 默认 `strict=True`，走 TorchDynamo 逐字节码追踪；遇到不支持的 Python 特性会**报错**而不是降级，此时可先用 `strict=False`（非严格导出）试，或用 `draft_export` 列出所有 graph break 的位置。
- `run_decompositions()` 可以进一步把图变成纯函数式（消除 mutation 与 aliasing），ExecuTorch、量化后端通常要求这一步。
- 图里只有 `torch.ops.aten` 算子与自定义算子；`get_attr` 节点不存在（参数被提升为图输入），这正是 `.pt2` 能自包含权重的原因。
- **数据依赖的控制流**（如 `if x.shape[0] > 2:`）在形状不特化时无法追踪，需要改写为 `torch.cond`/`map`/`scan`/`while_loop` 这类高阶算子；形状相关的判断则由 `Dim` 约束表达。
- 导出失败时先看 ExportDB 与 `draft_export`，比逐行读报错快。

`.pt2` 与 ONNX 的选型：

| 维度 | .pt2（torch.export） | ONNX |
| --- | --- | --- |
| 运行环境 | PyTorch 运行时（Python/C++ libtorch、ExecuTorch） | 任意 ONNX Runtime（Python/C++/Java/C#/JS、移动端） |
| 算子集 | aten（含 Torch 专有算子） | ONNX 标准算子 |
| 动态形状 | `Dim` + `dynamic_shapes` | `dynamic_axes` / `dynamic_shapes` |
| 生态工具 | torch.compile、ExecuTorch、torchao 量化 | onnxruntime、TensorRT、OpenVINO、量化工具链 |
| 典型用途 | 同栈内部署、端侧（ExecuTorch）、量化（torchao） | 跨框架/跨语言部署、给非 Python 服务用 |

```text
要点：
1. torch.export 是 AOT 完整图导出，碰到不可捕获代码直接失败（要靠改写代码而不是等它降级）
2. 默认导出是静态形状：换 batch 会得到 AssertionError: Guard failed，动态维必须用 torch.export.Dim 声明
3. torch.export.save/load 得到 .pt2，权重在图里自包含，接收方不需要原始模型类定义
4. 需要纯函数图（量化、端侧）时补一步 ep.run_decompositions()
5. 需要跨语言/跨框架时选 ONNX，同栈或端侧优先 .pt2
```

## ONNX 导出与算子兼容

`torch.onnx.export` 在 2.14 的默认后端已经是 **dynamo=True**（走 `torch.export` + onnxscript），旧的 TorchScript 路径需要显式写 `dynamo=False`。导出后必须用 `onnx.checker` 做结构校验、用 onnxruntime 做数值对齐——「导出成功」和「结果正确」是两件事。

```python
import numpy as np
import torch
import torch.nn as nn
import onnx
import onnxruntime as ort

model = nn.Sequential(nn.Linear(16, 32), nn.ReLU(), nn.Linear(32, 32), nn.ReLU(), nn.Linear(32, 3)).eval()
x = torch.randn(4, 16)

# 固定 batch 导出
torch.onnx.export(model, (x,), "model.onnx", input_names=["input"], output_names=["logits"], opset_version=17)

# 动态 batch 导出（dynamo 后端的推荐写法）
batch = torch.export.Dim("batch")
torch.onnx.export(model, (x,), "model_dyn.onnx", input_names=["input"], output_names=["logits"],
                  dynamic_shapes={"x": {0: batch}})

mf = onnx.load("model.onnx")
onnx.checker.check_model(mf)
print(mf.ir_version, [(o.domain or "ai.onnx", o.version) for o in mf.opset_import])
print([(i.name, [d.dim_value for d in i.type.tensor_type.shape.dim]) for i in mf.graph.input])
print(sorted(set(n.op_type for n in mf.graph.node)))

sess = ort.InferenceSession("model.onnx", providers=["CPUExecutionProvider"])
out = sess.run(None, {"input": x.numpy()})[0]
with torch.no_grad():
    print(float(np.abs(out - model(x).numpy()).max()))
```

结论与工程建议：

- **`opset_version` 不要凭记忆写**：不传由导出器决定（本机实测 dynamo 路径给 20）；显式写 17 会被抬到 18 并给出可能失败的警告（本机最终仍写出 opset 17，靠 onnx C API 做了版本转换）。目标推理引擎支持哪个 opset，以它的文档为准（ONNX Runtime、TensorRT、OpenVINO 各自的支持矩阵不同）。
- **动态维用 `dynamic_shapes` 而不是 `dynamic_axes`**：dynamo=True 时 `dynamic_axes` 会触发 UserWarning 并可能抛出 `Constraints violated`。
- **dynamo 路径目前与 onnxruntime 的 `quantize_dynamic` 不兼容**（本机实测三个变体全部在形状推断阶段失败），需要 ONNX 侧量化时用 `dynamo=False` 导出，或先在 PyTorch 侧量化（见下一节）。
- 数值误差应在 1e-6 量级（本机 1.49e-08）。若误差大，先查是否在导出前忘了 `eval()`（Dropout 仍在），再查自定义算子是否被拆成了等价算子组合。

```text
要点：
1. 2.14 起 torch.onnx.export 默认 dynamo=True，旧教程里的 dynamic_axes 写法会给出 UserWarning
2. opset 不传由导出器决定（本机 20），显式指定低于实现支持的版本会触发自动转换警告
3. 导出后三件事必做：onnx.checker.check_model、shape_inference、onnxruntime 数值对齐
4. 动态 batch 必须显式声明，否则推理时 batch 不匹配直接 INVALID_ARGUMENT
5. dynamo 导出的模型目前无法直接喂 onnxruntime.quantization.quantize_dynamic，需要 dynamo=False 或改用 torchao
```

## 量化与剪枝

量化把 fp32 权重/激活换成 int8，收益来自**内存与带宽**（体积约 1/4）；剪枝把不重要的权重置零，收益只有在拿到稀疏计算库时才会体现。本机实测（64->256->256->10 的 MLP，CPU 4 线程）：

```python
import torch
import torch.nn as nn

model = nn.Sequential(nn.Linear(64, 256), nn.ReLU(), nn.Linear(256, 256), nn.ReLU(), nn.Linear(256, 10)).eval()

# 动态量化：权重转 int8，激活在推理时动态量化，不需要校准数据
q_dyn = torch.ao.quantization.quantize_dynamic(model, {nn.Linear}, dtype=torch.qint8)
torch.save(q_dyn.state_dict(), "dynq.pt")

# 静态量化 PTQ：prepare -> 用真实数据校准 -> convert
class Small(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1, self.relu, self.fc2 = nn.Linear(64, 128), nn.ReLU(), nn.Linear(128, 10)

    def forward(self, x):
        return self.fc2(self.relu(self.fc1(x)))


fp = Small().eval()
small = copy.deepcopy(fp)                      # prepare(inplace=True) 会改模型，先留一份 fp32 基线
small.qconfig = torch.ao.quantization.get_default_qconfig("fbgemm")
torch.ao.quantization.prepare(small, inplace=True)
with torch.no_grad():
    for _ in range(20):
        small(torch.randn(32, 64))             # 校准：必须与线上同分布
small_int8 = torch.ao.quantization.convert(small.eval(), inplace=False)
xq = torch.quantize_per_tensor(x, scale=0.02, zero_point=128, dtype=torch.quint8)
small_int8(xq)                                 # 静态量化模型要求量化输入
```

```text
  net.2    weight_mask 存在: True, 稀疏率: 0.000
  net.4    weight_mask 存在: True, 稀疏率: 0.000
prune.remove 后第 1 层还是 50% 稀疏: 0.5  是否还有 weight_orig: False
剪枝后输出与原始输出的平均绝对误差: 0.0852

== 5. 全局剪枝 + 结构化剪枝 ==
全局 50% 后整体稀疏率: 0.500
结构化剪枝后第 2 层 (256,256) 整行为 0 的比例: 0.25
```

结论要按事实说：

- **动态量化把体积压到 26.7%，但在这个小模型 + CPU 上延迟反而变慢**（55.3 us -> 141.7 us）：动态量化每次前向都要现场量化激活，只有大模型（尤其 LSTM/Transformer 的 Linear 占主导时）才能摊平这个开销。
- **静态量化体积收益更大（40.0 KB -> 16.7 KB，41.7%），但精度损失也更明显**（max 误差 0.227，因为校准数据与测试数据分布不同）。部署前必须用真实校准集跑精度回归。
- 静态量化后的模型**只接受量化张量**：直接喂 float 会报 `NotImplementedError: Could not run 'quantized::linear' with arguments from the 'CPU' backend`。要么在服务入口做 `torch.quantize_per_tensor`，要么用 `torch.ao.quantization.quantize_fx` 让边界自动插入量化/反量化。
- `torch.ao.quantization` 已被官方标记弃用（本机实测 `DeprecationWarning: torch.ao.quantization is deprecated`，官方迁移方向是 `torchao` 的 `quantize_` / pt2e 流程）。新项目建议直接看 torchao。
- **非结构化剪枝不会自动加速**：`l1_unstructured` 只是插入了 `weight_mask`，值仍参与计算，实测延迟没有下降（稀疏率高但算子仍是稠密 GEMM）。要真正省算力得用结构化剪枝（`ln_structured`，按通道/整行删）或半结构化 2:4 + 支持稀疏的硬件/库。
- `prune.remove(module, "weight")` 把 mask 固化进权重（`weight_orig` 消失、`weight` 变成含零的普通张量），这是导出前的必要一步。

```text
要点：
1. 量化的第一收益是体积与内存带宽，小模型在 CPU 上延迟可能变慢，必须实测再决定
2. 动态量化无需校准、一行可用；静态量化要校准集、精度损失要单独回归
3. 静态量化模型要求量化输入，服务侧要么自行量化，要么用 quantize_fx 自动插边界
4. torch.ao.quantization 已弃用，新项目看 torchao（quantize_ / pt2e）
5. 非结构化剪枝只造零、不省算力；要省算力用结构化剪枝或 2:4 稀疏 + 对应硬件/库
```

## 服务化部署 ONNX Runtime 与 HTTP 接口

服务化的核心是把「加载模型」与「处理请求」分开：模型在启动时加载并预热（第一次推理包含内存分配与算子选择，不能算进 SLA），请求路径只做校验、推理、后处理。下面这份服务用 FastAPI + onnxruntime，包含健康检查、形状校验、异常转 422 与请求级延迟统计：

```python
import os
import time
import numpy as np
import onnxruntime as ort
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

MODEL_PATH = os.environ.get("MODEL_PATH", "model_dyn.onnx")
LABELS = ["cat", "dog", "bird"]
app = FastAPI(title="classifier", version="1.0")


class PredictRequest(BaseModel):
    features: list[list[float]] = Field(..., description="形状 (N, 16) 的二维数组")


class PredictResponse(BaseModel):
    labels: list[str]
    probs: list[list[float]]
    latency_ms: float


@app.on_event("startup")
def load_model():
    opts = ort.SessionOptions()
    opts.intra_op_num_threads = int(os.environ.get("INTRA_THREADS", "4"))
    opts.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
    app.state.sess = ort.InferenceSession(MODEL_PATH, sess_options=opts, providers=["CPUExecutionProvider"])
    app.state.input_name = app.state.sess.get_inputs()[0].name
    app.state.model_version = os.environ.get("MODEL_VERSION", "v1")
    app.state.sess.run(None, {app.state.input_name: np.zeros((1, 16), dtype=np.float32)})  # 预热
    app.state.ready = True


@app.get("/health")
def health():
    return {"status": "ok", "ready": bool(getattr(app.state, "ready", False)),
            "version": getattr(app.state, "model_version", None)}


@app.post("/predict", response_model=PredictResponse)
def predict(req: PredictRequest):
    x = np.asarray(req.features, dtype=np.float32)
    if x.ndim != 2 or x.shape[1] != 16:
        raise HTTPException(status_code=422, detail=f"期望形状 (N,16)，收到 {x.shape}")
    t0 = time.perf_counter()
    try:
        logits = app.state.sess.run(None, {app.state.input_name: x})[0]
    except Exception as e:                      # 形状/类型不满足模型约束时不要裸抛 500
        raise HTTPException(status_code=422, detail=f"推理失败: {str(e).splitlines()[0][:160]}")
    dt = (time.perf_counter() - t0) * 1000
    e = np.exp(logits - logits.max(axis=1, keepdims=True))
    probs = e / e.sum(axis=1, keepdims=True)
    return PredictResponse(labels=[LABELS[i] for i in probs.argmax(1)], probs=probs.tolist(), latency_ms=dt)
```

启动与真实调用（`uvicorn c12_8_service:app --host 127.0.0.1 --port 8123`）：

这组数字最能说明服务化的真实瓶颈：**单次推理只有 0.13~0.17 ms，但一次 256x16 的 JSON 请求端到端要 134.6 ms**——时间几乎全花在 HTTP 与 JSON 序列化上，不是模型。优化顺序因此应该是：先用批量推理摊薄请求开销，再考虑二进制协议（protobuf/msgpack）或 gRPC，最后才是模型本身。

如果换成固定 batch 的模型（没有声明动态维），批量请求会得到 500：

```text

```

这也是服务里要 `try/except` 的原因：把引擎级异常翻译成 422 与可读信息，而不是让调用方收到一坨栈。生产化的其余几件事：

- 版本与灰度：`MODEL_VERSION` 通过环境变量注入并在 `/health` 暴露；模型文件按 `model_v{semver}.onnx` 命名，回滚就是重启指向旧文件。
- 线程与进程：`intra_op_num_threads` 与容器 CPU limit 对齐（一般等于配额核数）；横向扩进程数比单进程堆线程更划算，因为 ONNX Runtime 单会话内部已经并行。
- 无 Python 场景：ONNX Runtime 的 C++/Java/C#/JS API 可以直接加载同一个 `.onnx`，服务层不必是 Python。
- 需要更高吞吐时再考虑 TorchServe / Triton / KServe 这类模型服务器（动态批处理、多模型编排、指标暴露），具体参数以各自官方文档为准。

```text
要点：
1. 模型在 startup 加载并预热，请求路径只做校验+推理+后处理；预热结果不计入 SLA
2. /health 暴露 ready 与模型版本，容器就绪探针用它，避免请求打到未加载完成的实例
3. 引擎异常必须翻译成 4xx 并带上可读原因，固定 batch 模型遇到变长请求会抛 InvalidArgument
4. 先批量推理再谈协议优化：实测推理 0.17 ms、端到端 134.6 ms，瓶颈在 JSON 与 HTTP
5. 线程数对齐容器 CPU 配额，扩进程优先于加线程
```

## 移动端与边缘部署 ExecuTorch

ExecuTorch 是官方面向端侧（Android、iOS、嵌入式、微控制器）的运行时，产物是单文件 `.pte`，流程是 `torch.export` -> `to_edge_transform_and_lower` -> `to_executorch` -> 写文件；推理时用运行时的 `load_program` + `load_method`，或 C++ API。与 TorchScript Lite 相比，它支持更现代的后端划分（XNNPACK、Core ML 等）与更小的运行时体积。

**本机未安装 executorch，以下代码未在本机验证**，按官方文档（docs.pytorch.org/executorch/stable/using-executorch-export.html）整理，实际 API 以文档为准：

```bash
pip install executorch          # 需要 Python 3.10-3.14 与 C++17 工具链
```

```python
import torch
from executorch.backends.xnnpack.partition.xnnpack_partitioner import XnnpackPartitioner
from executorch.exir import to_edge_transform_and_lower
from torch.export import Dim, export


class Model(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.seq = torch.nn.Sequential(
            torch.nn.Conv2d(1, 8, 3), torch.nn.ReLU(),
            torch.nn.Conv2d(8, 16, 3), torch.nn.ReLU(),
            torch.nn.AdaptiveAvgPool2d((1, 1)),
        )
        self.linear = torch.nn.Linear(16, 10)

    def forward(self, x):
        return self.linear(torch.flatten(self.seq(x), 1))


model = Model()                                  # 必须 eval()，除非做端上训练
inputs = (torch.randn(1, 1, 16, 16),)
dynamic_shapes = {"x": {2: Dim("h", min=16, max=1024), 3: Dim("w", min=16, max=1024)}}

exported_program = export(model, inputs, dynamic_shapes=dynamic_shapes)
executorch_program = to_edge_transform_and_lower(
    exported_program, partitioner=[XnnpackPartitioner()]
).to_executorch()

with open("model.pte", "wb") as f:
    f.write(executorch_program.buffer)
```

端侧部署要点（按官方文档口径）：

- 后端按目标硬件选：移动 CPU 用 XNNPACK，iOS 可用 Core ML，未获后端支持的算子会回落到 portable CPU 实现（能跑但性能差，因此导出后要核对 partition 日志）。
- 权重与程序分离：用 `delegate_external_constants_pass_unlifted` 打标后可产出 `.pte` + `.ptd` 双文件（适合权重被单独下发或内存受限场景）。
- 动态控制流只支持 `torch.cond` 表达的 `if`；循环需要把循环体导成单独方法，由应用层驱动（生成式模型的增量解码就是这样处理的）。
- 一个 `.pte` 可以打包多个方法（`to_edge_transform_and_lower({"encode": ep1, "decode": ep2})`），但方法之间不共享可变 buffer 与激活内存规划。

## 应用场景实战

### 场景一：把训练好的模型发布成带版本与批量推理的 HTTP 服务

完整链路：`state_dict` -> 导出动态 batch 的 ONNX -> 数值对齐 -> 包成 FastAPI 服务 -> 压测。每一步都有验收标准，任何一步不达标就不要往下走。

```python
"""export_service.py：离线导出与数值验收（在本机已实测）"""
import os
import numpy as np
import torch
import torch.nn as nn
import onnx
import onnxruntime as ort
from onnx import shape_inference

class Net(nn.Module):
    def __init__(self, d=16, h=32, n_cls=3):
        super().__init__()
        self.net = nn.Sequential(nn.Linear(d, h), nn.ReLU(), nn.Linear(h, h), nn.ReLU(), nn.Linear(h, n_cls))

    def forward(self, x):
        return self.net(x)


def export_and_verify(state_dict_path, out_path, version="v1"):
    model = Net().eval()
    model.load_state_dict(torch.load(state_dict_path, weights_only=True))
    x = torch.randn(1, 16)
    batch = torch.export.Dim("batch")
    torch.onnx.export(model, (x,), out_path, input_names=["input"], output_names=["logits"],
                      dynamic_shapes={"x": {0: batch}}, opset_version=18)
    mf = onnx.load(out_path)
    onnx.checker.check_model(mf)                       # 1. 结构合法
    shape_inference.infer_shapes(mf)                    # 2. 形状可推断
    sess = ort.InferenceSession(out_path, providers=["CPUExecutionProvider"])
    probe = torch.randn(37, 16).numpy()                 # 3. 非样例 batch 也能跑
    got = sess.run(None, {"input": probe})[0]
    with torch.no_grad():
        ref = model(torch.from_numpy(probe)).numpy()
    err = float(np.abs(got - ref).max())
    assert err < 1e-4, f"数值误差过大: {err}"           # 4. 数值对齐才算通过
    print(f"{version} 导出通过: 文件 {os.path.getsize(out_path)/1024:.1f} KB, 最大误差 {err:.2e}, "
          f"支持 batch={{1,37}}")
    return out_path


export_and_verify("srv_sd.pt", "srv_dyn.onnx", "v1.0.3")
```

### 场景二：低算力环境的模型压缩流水线（剪枝 + 量化 + 精度回归）

目标是把一个 fp32 模型压到能放进内存受限设备，同时保住精度。流水线顺序是「先剪枝后量化」（剪枝后的稀疏权重能获得更好的量化 scale 分布），每一步都要有精度回归与体积/延迟报告。

```python
"""compress_pipeline.py：剪枝 -> 动态量化 -> 体积/精度/延迟报告（本机已实测各步骤）"""
import copy
import os
import time
import torch
import torch.nn as nn
from torch.nn.utils import prune


def bench(model, x, n=200):
    with torch.no_grad():
        for _ in range(20):
            model(x)
        t0 = time.perf_counter()
        for _ in range(n):
            model(x)
        return (time.perf_counter() - t0) / n * 1e6


def report(name, model, x, ref, path):
    torch.save(model.state_dict(), path)
    with torch.no_grad():
        out = model(x)
    print("%-22s 体积 %6.1f KB  最大误差 %.5f  平均误差 %.5f  延迟 %6.1f us" % (
        name, os.path.getsize(path) / 1024, float((out - ref).abs().max()),
        float((out - ref).abs().mean()), bench(model, x)))
    return model


x = torch.randn(8, 64)
fp32 = nn.Sequential(nn.Linear(64, 256), nn.ReLU(), nn.Linear(256, 256), nn.ReLU(), nn.Linear(256, 10)).eval()
with torch.no_grad():
    ref = fp32(x)
report("fp32 基线", fp32, x, ref, "p_fp32.pt")

pruned = copy.deepcopy(fp32)
prune.global_unstructured([(m, "weight") for m in pruned.modules() if isinstance(m, nn.Linear)],
                          pruning_method=prune.L1Unstructured, amount=0.5)
for m in pruned.modules():
    if isinstance(m, nn.Linear):
        prune.remove(m, "weight")                    # 固化 mask，导出前必须做
report("全局剪枝 50%", pruned, x, ref, "p_pruned.pt")

q_dyn = torch.ao.quantization.quantize_dynamic(pruned, {nn.Linear}, dtype=torch.qint8)
report("剪枝 + 动态量化", q_dyn, x, ref, "p_pruned_int8.pt")
```

本机实测（各步骤真实数值）：

```text
== 4. 非结构化剪枝 ==
剪枝前稀疏率: 0.000
第 1 层剪 50% 后整体稀疏率: 0.125
prune.remove 后第 1 层还是 50% 稀疏: 0.5  是否还有 weight_orig: False
剪枝后输出与原始输出的平均绝对误差: 0.0852
全局 50% 后整体稀疏率: 0.500

== 2. 动态量化 quantize_dynamic ==
最大绝对误差: 0.00536  平均绝对误差: 0.00127
fp32 state_dict 335.1 KB -> 动态量化 89.5 KB (26.7%)
延迟 fp32 55.3 us -> int8 141.7 us
```

工程结论：

- 体积收益确定（本机 335.1 KB -> 89.5 KB，26.7%）；**延迟收益不确定**：小模型在 CPU 上 int8 反而慢（55.3 -> 141.7 us），必须在目标设备与目标 batch 上实测。
- 剪枝后输出平均误差 0.0852、动态量化后 0.00127——注意这里量化的误差是相对「剪枝后模型」的，流水线的累计误差要用原始 fp32 输出做基准回归。
- 上线前必须有精度回归集：先用业务验证集比对 fp32 / 压缩模型的业务指标（AUC、宏平均 F1），阈值通过才发布压缩版本。
- 如果目标设备支持 int8 或稀疏加速（如部分 ARM CPU 的 VNNI/位运算），收益才能兑现；否则压缩版只省内存，不省时间。

```text
要点：
1. 顺序：剪枝 -> remove mask -> 量化 -> 精度回归；每步都记录体积、精度、延迟三项
2. 精度回归基准始终是原始 fp32 输出，不能拿中间产物当基准
3. 量化与剪枝的延迟收益依赖硬件，小模型 CPU 上可能变慢，必须实测
4. 稀疏模型要真省算力，得有支持稀疏的算子库或结构化剪枝
5. 压缩产物必须带元数据（原始版本、压缩方法、精度回归结果），否则线上问题无法追溯
```

## 最佳实践与踩坑记录

### 最佳实践

1. 导出脚本内置验收：`onnx.checker`（结构）、`shape_inference`（形状）、非样例 batch 推理（动态维）、数值误差阈值（正确性），四道全过才发布。
2. 导出前统一 `model.eval()`，并把这一点写进导出脚本而不是靠调用方记得；训练态导出会静默带上 Dropout/BatchNorm 的训练行为。
3. 动态 batch 用 `torch.export.Dim` + `dynamic_shapes` 声明；只要服务侧可能批量或变长，就不要用静态形状导出。
4. 量化/剪枝前先固化结构：剪枝要 `prune.remove`，量化要确认目标引擎（fbgemm/x86/qnnpack/onednn）与目标设备一致。
5. 服务里模型在 startup 加载并预热，异常翻译成 4xx；`/health` 暴露 ready 与模型版本。
6. 压缩与导出的产物都带版本与验收记录；回滚路径提前演练一次，别等到线上出事才试。

### 踩坑记录

坑 1：导出前忘了 `model.eval()`，Dropout 把线上结果变成随机数
结论：离线数值对齐能过（同一份输入两次都可能不同），线上多次调用同一输入结果不一致。
原因：`nn.Dropout` 在 training 模式下按概率置零；导出不会替你切模式，`torch.jit.freeze` 甚至会因为 training 模式含 Dropout 直接报 `RuntimeError: Freezing is currently only implemented for modules in eval mode`（本机实测）。
解法：导出脚本第一行 `model.eval()`；导出后立刻用同一输入跑两次比对（eval 下必须完全一致）。

坑 2：以为 trace 出来的模型能处理任意 batch，结果线上请求形状一变就报错
结论：本机实测 `torch.jit.trace(model, torch.randn(4, 16))` 的产物在 batch 维度上依赖导出的形状；换到 ONNX 的固定形状导出更直接——`Got invalid dimensions for input: index: 0 Got: 256 Expected: 1`。
原因：导出记录的是样例的形状断言（ONNX 静态形状、`torch.export` 的 Guard），不是「任意形状」。
解法：导出时声明动态维（`dynamic_shapes={"x": {0: Dim("batch")}}`，ONNX 侧 `dynamic_axes` 仅用于 `dynamo=False`）；服务侧再用批量请求压测验证。

坑 3：`torch.ao.quantization` 的静态量化模型直接喂 float 张量
结论：`NotImplementedError: Could not run 'quantized::linear' with arguments from the 'CPU' backend`（本机实测）。
原因：静态量化后的 `Linear` 只接受量化张量；float 输入在导出/服务边界没有自动插入量化节点。
解法：入口显式 `torch.quantize_per_tensor(x, scale, zero_point, torch.quint8)`，或改用 `quantize_fx` 让边界自动补 Quantize/Dequantize；同时注意 `torch.ao.quantization` 已被标记弃用，新项目用 torchao。

坑 4：dynamo 导出的 ONNX 喂给 `onnxruntime.quantization.quantize_dynamic` 就崩
结论：`ShapeInferenceError: Inferred shape and existing shape differ in dimension 0: (16) vs (32)`（本机实测，三个 dynamo 变体全部失败；`dynamo=False` 的产物正常，7.4 KB -> 5.6 KB）。
原因：dynamo 路径导出的 Gemm 权重布局与 onnxruntime 量化工具的形状推断假设不一致。
解法：需要 ONNX 侧量化时用 `dynamo=False` 导出；或改为在 PyTorch 侧量化后再导出；升级 onnxruntime/onnx 后重新验证这条限制是否仍然存在。

坑 5：用 `optimize_for_mobile` 却得到内部断言错误
结论：`RuntimeError: false INTERNAL ASSERT FAILED at xnnpack_rewrite.cpp:506 ... XNNPACK is not enabled. Please build with USE_XNNPACK=1`（本机官方 wheel 实测）。
原因：该优化依赖 PyTorch 编译时开启的 XNNPACK，官方 pip wheel 未开启。
解法：改用 ExecuTorch（XNNPACK delegate 在导出侧生效，不依赖本地 PyTorch 编译选项）；或在源码编译 PyTorch 时加 `USE_XNNPACK=1`。

坑 6：把 `state_dict` 的 `torch.save` 产物当成可部署模型
结论：接收方必须能 import 原始模型类，且仍需要完整的 PyTorch 运行环境，模型文件本身无法自描述网络结构。
原因：`state_dict` 只是参数字典，结构定义在 Python 代码里。
解法：跨环境部署用 `torch.export`（.pt2，自包含）或 ONNX；`state_dict` 只用于同项目内的训练/续训（详见 [[12.6-保存加载与迁移学习]]）。
