## 概述

Claude Code 的权限体系回答两个问题：模型能碰哪些工具，以及在什么条件下需要你点头。它由四层组成——分级审批、`allow` / `ask` / `deny` 规则、权限模式、以及操作系统级的沙箱。四层可以叠加使用：规则决定「是否允许」，模式决定「要不要问你」，沙箱决定「跑起来之后能碰到什么」，钩子则用来表达规则无法描述的复杂策略。权限设置可以提交进版本库供全组复用，每个人再用本地文件覆盖自己的例外。

```text
权限四层模型：
1. 分级审批 —— 只读操作默认不问，写文件、跑命令、联网默认要问
2. 规则 —— allow / ask / deny 三张表，deny 优先级最高，按「写法」匹配命令与路径
3. 权限模式 —— default / acceptEdits / plan / auto / dontAsk / bypassPermissions
4. 沙箱 —— 由操作系统强制执行的文件系统与网络边界，模型改不了
```

## 权限体系与分级

不同工具类型的默认行为差异很大，这张表决定了你平时会被问多少次：

| 工具类型 | 例子 | 是否默认需要批准 | 「Yes, and don't ask again」的效果 |
| :- | :- | :- | :- |
| 只读 | 文件读取、Grep | 否（限工作目录与额外目录内） | 不适用 |
| Bash 命令 | shell 执行 | 是，除内置只读命令集合外 | 按仓库与命令永久保存 |
| 文件修改 | Edit / Write | 是 | 仅本次会话有效 |
| WebFetch | 抓取网页 | 是，除预批准的文档域名外 | 按仓库与域名永久保存 |
| WebSearch | 联网搜索 | 是 | 按仓库永久保存 |

永久保存的批准会写成 `allow` 规则，落到仓库根目录的 `.claude/settings.local.json`（在 worktree 里会解析到主检出目录），对该仓库的后续会话生效，包括在子目录与 worktree 中启动的会话。文件修改的批准不写盘，只在当前会话内有效——这一点常被误解，换个会话就要重新批准。

内置的只读命令集合包含 `ls`、`cat`、`echo`、`pwd`、`head`、`tail`、`grep`、`find`、`wc`、`which`、`diff`、`stat`、`du`、`cd` 以及 git 的只读子命令。这个集合不可配置，想强制提示就给它们加 `ask` 或 `deny` 规则。即便在 Manual 模式下，以下情况仍会提示：

- 命令带可写或可执行标志且出现未加引号的通配符（如 `find -delete`、`sed`、`git`），因为通配符可能展开成标志
- `docker` 带 `-H`、`--context` 或在 Podman 下带 `--url` / `--connection`，指向了另一个守护进程
- `file` 带 `-m` / `--magic-file` / `-f` / `--files-from`，会打开参数里指定的路径
- `ps` 的参数可能被解析为 `e` 选项（如 `ps auxe`），因为它会打印进程环境变量；`ps aux` 与 `ps -ef` 不提示
- 参数里含网络（UNC）路径，如 `\\server\share\file`
- 命令要设置、取消或循环遍历 `PATH`、`IFS` 这类特殊 shell 变量
- 命令无法被完整解析，或长度超过 10000 字符

```text
分级审批的实践含义：
1. 只读操作不需要你操心，真正要设计的是写文件与跑命令的边界
2. 想让某条只读命令也提示，加 ask 规则，别指望改内置集合
3. 文件修改类批准不持久，长期放行必须写进 allow 规则
4. cd 进入工作目录内的路径算只读；cd 后再跑 git 仍会提示，因为新目录的钩子可能被执行
```

## 权限规则语法与工具白名单

规则格式是 `Tool` 或 `Tool(specifier)`，括号内的括号是字面字符，不需要转义。只写工具名匹配该工具的全部用法；带限定符则精细控制；`deny` 与 `ask` 还支持按工具的顶层输入参数匹配 `Tool(param:value)`。

| 规则 | 效果 |
| :- | :- |
| `Bash(npm run build)` | 精确匹配这一条命令 |
| `Bash(npm run *)` | 匹配 `npm run` 开头的各类命令 |
| `Read(./.env)` | 匹配读取当前目录下的 `.env` |
| `WebFetch(domain:example.com)` | 匹配抓取 example.com |
| `Agent(model:opus)` | 匹配请求 Opus 档位的子代理调用（仅 deny / ask） |
| `mcp__*` | 作为 deny 规则匹配所有 MCP 工具 |

通配符的位置很关键，官方给出的对照关系值得记住：`Bash(git log *)` 只放行 git log 系列，`Bash(git *)` 放行所有 git 子命令，`Bash(git * main)` 会把子命令也变成通配从而覆盖 `git -c core.fsmonitor=<script> diff main` 这类可疑写法。带空格结尾的 `*`（如 `Bash(ls *)`）还能匹配裸命令 `ls`，且要求 `ls` 后有空格，所以不会误匹配 `lsof`；`Bash(ls*)` 则会连 `lsof` 一起匹配。`Bash(git * main)` 这种「通配符出现在子命令之前」的 allow 规则，Claude Code 会在启动时警告。

必须清醒认识 Bash 规则能匹配什么：它匹配的是命令**文本**。`Bash(curl http://github.com/ *)` 本意是限制 curl 只能访问 GitHub，但 `curl -X GET ...`、`curl https://...`、`curl -L http://short.example.com/...`、`URL=... && curl $URL` 都能绕过；通过绝对路径调用 `/usr/bin/curl` 或在 `sh -c` 里调用也不匹配。要真正限制出网，只能用 sandbox 的网络白名单，或 PreToolUse 钩子校验 URL。

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)",
      "Read(./docs/**)",
      "WebFetch(domain:docs.anthropic.com)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Bash(rm -rf *)",
      "Bash(curl *)",
      "Bash(wget *)",
      "mcp__*"
    ],
    "additionalDirectories": ["../shared-lib"]
  }
}
```

```text
规则书写要点：
1. deny 优先级高于 allow，命中 deny 直接拒绝，规则冲突时不会「放行」
2. 参数匹配（param:value）只对 deny / ask 有效，allow 仍需用工具自身的限定符语法
3. allow 规则里的工具名通配符只允许出现在字面量 mcp__<server>__ 前缀之后，如 mcp__github__get_*
4. deny 规则里写 mcp__ 带括号的规则会被跳过（会出现在无效设置提示与 claude doctor 输出里）
5. 设置文件是严格 JSON，注释和尾随逗号都会导致 Settings Error
```

## 审批模式

模式决定会话在多大程度上代替你点「允许」。用设置里的 `defaultMode` 改变默认模式，或用 `--permission-mode` 只影响当前会话。

| 模式 | 行为 |
| :- | :- |
| `default` | 每个工具首次使用时提示。UI 上叫 Manual，CLI 也接受 `manual` 作为别名 |
| `acceptEdits` | 自动接受文件编辑，以及 `mkdir`、`touch`、`mv`、`cp` 这类常见文件系统命令（限工作目录与额外目录内） |
| `plan` | 只读探索：读文件、跑只读 shell 命令，不改源码；开启 auto 能力时分类器认可的只读命令也会跑 |
| `auto` | 不做常规提示，但在 shell 命令、网络请求这类动作执行前由后台分类器检查是否与你的请求相符 |
| `dontAsk` | 把「本该提示」的调用一律自动拒绝；工作目录内的文件读取等无需批准的动作照常执行，`--allowedTools` 或 `permissions.allow` 覆盖的动作也照常执行 |
| `bypassPermissions` | 跳过权限提示，但「任何模式都不会自动批准的动作」仍受保护；`.git`、`.claude` 这类受保护路径的写入也会跳过检查 |

```shell
# 只影响当前会话：以 acceptEdits 为基线自动改文件
claude -p "应用 lint 修复" --permission-mode acceptEdits

# 计划阶段只读探索，之后再切到允许编辑
claude --permission-mode plan --allow-dangerously-skip-permissions

# 无人值守：分类器先审，无法判定的一律拒绝，且不重试
claude -p "更新依赖锁并跑测试" --permission-mode auto --permission-prompts none

# 与 --allowedTools 组合：只放行列出的工具
claude -p "跑测试并修失败用例" --allowedTools "Bash,Read,Edit"
```

`bypassPermissions` 只应在容器或虚拟机等隔离环境里用。防止有人切进危险模式，可以在任意设置文件（托管设置里最有效，因为无法被覆盖）写：

```json
{
  "permissions": {
    "disableBypassPermissionsMode": "disable",
    "disableAutoMode": "disable"
  }
}
```

```text
模式选择建议：
1. 本机日常开发 —— default（Manual），配合 allow 规则减少噪音
2. 信任度较高的重构 —— acceptEdits，但 shell 命令仍会被问
3. 只让模型先出方案 —— plan，避免它边想边改
4. CI / 批量任务 —— auto + --permission-prompts none，或 dontAsk 配精确 allow 列表
5. 只在隔离环境里用 bypassPermissions，并在托管设置里把危险模式关掉
```

## 沙箱的文件系统与网络隔离

沙箱是唯一由操作系统强制执行的边界：规则与分类器在命令运行**前**判断，沙箱在命令运行**时**限制它能碰到什么，即使模型跑了一条语义上看起来人畜无害的命令也一样生效。在 Linux 与 WSL2 上依赖 `bubblewrap`（文件系统隔离）与 `socat`（网络代理转发），沙箱构建进 Claude Code，macOS 用内置 Seatbelt，原生 Windows 不支持（需在 WSL2 里跑）。可选安装 `@anthropic-ai/sandbox-runtime` 获得 seccomp 过滤，用于阻断 Unix 域套接字。

```shell
# Ubuntu / Debian 安装依赖
sudo apt-get install bubblewrap socat

# 会话内打开沙箱面板：三个标签页（Mode / Overrides / Config），依赖缺失时多一个 Dependencies
/sandbox
```

本机（Ubuntu 24.04.4，内核 7.0.0-28-generic）实测状态：

```text
$ command -v bwrap
/usr/bin/bwrap
$ command -v socat
（无输出，未安装）
$ sysctl kernel.apparmor_restrict_unprivileged_userns
kernel.apparmor_restrict_unprivileged_userns = 1
$ bwrap --dev-bind / / --chdir /tmp true; echo exit=$?
exit=0
```

也就是说本机 `bubblewrap` 存在且当前能正常创建命名空间（退出码 0），但 `socat` 缺失，`/sandbox` 面板会提示依赖不完整。官方文档指出 Ubuntu 24.04 及以后版本默认的 AppArmor 策略可能阻止 bubblewrap 创建 user namespace，本机 sysctl 值为 1；如果 `/sandbox` 报依赖问题，按官方步骤添加只作用于 `bwrap` 本身的 AppArmor profile 后 `sudo systemctl reload apparmor`。

沙箱默认允许写入工作目录、会话临时目录，以及用 `--add-dir`、`/add-dir`、`permissions.additionalDirectories` 添加的目录。需要放行更多路径就用 `sandbox.filesystem.allowWrite`，需要用 `kubectl`、`terraform`、`npm` 这类子进程写到别处时同理；不要让工具整个跑出沙箱。

```json
{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "allowWrite": ["~/.kube", "/tmp/build"],
      "denyRead": ["~/"],
      "allowRead": ["."]
    },
    "network": {
      "allowedDomains": ["registry.npmjs.org", "*.example.com"],
      "deniedDomains": ["ads.example.com"]
    },
    "excludedCommands": ["docker compose *"]
  }
}
```

网络层面的行为需要清楚边界：沙箱内命令没有直连网络（Linux 走独立网络命名空间），Claude Code 在本机沙箱外运行代理，并用 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 等变量把命令指向它，代理按域名白名单放行。因此**读代理变量的工具**（curl、npm、HTTPS 的 git）能连通白名单域名，**忽略代理变量的工具**（原生 ssh、多数数据库驱动）连白名单域名也连不上，**非 TCP 流量**（UDP、HTTP/3 over QUIC、ICMP）一律出不去。域名白名单初始为空，首次需要新域名时会提示你批准；批准后可用 `allowedDomains` 预放行，`strictAllowlist` 设为 true 时白名单外的域名直接拒绝而不提示（该项只在用户级、托管级或 CLI `--settings` 里生效，写在仓库设置文件里无效），托管设置的 `allowManagedDomainsOnly` 则只认托管来源的白名单。

```text
沙箱要点：
1. 沙箱与权限模式是两件事：/sandbox 不是权限模式，它限制的是命令运行时的可达范围
2. sandbox.filesystem 的路径写法与 Read / Edit 规则不同，`/tmp/build` 是绝对路径，`~/.kube` 相对家目录
3. denyRead 与 allowRead 重叠时取更窄的路径：deny ~/ 配 allow ~/projects 只放开 projects
4. 多个作用域定义同一数组会合并路径而不是覆盖，托管设置的锁可以排除仓库里新增的条目
5. 确实无法在沙箱里跑的工具才放 excludedCommands，且必须确认你信任它拥有完整权限
```

## 钩子与权限的配合

`PreToolUse` 钩子在权限模式检查之前触发，在所有模式下都会触发，包括 `dontAsk`。因此钩子返回 `permissionDecision: "deny"` 时，即使处于 `bypassPermissions` 或带 `--dangerously-skip-permissions` 也会被拦住——这让钩子成为唯一无法被用户切换模式绕过的策略层。反向不成立：钩子返回 `"allow"` 不能突破 deny 规则，也不能让需要交互的 MCP 工具、网络路径读取跳过提示。

优先级链条（从强到弱）：`PreToolUse` 返回 deny 或 `exit 2` 的拦截 → `deny` 规则 → `ask` 规则 → 钩子返回的 allow → 权限模式与分类器。`PreToolUse` 的判定不绕过 `deny` / `ask` 规则，设置文件与插件 `hooks/hooks.json` 里的钩子只能收紧限制，无法把限制放宽到超出权限规则允许的范围。

```json
{
  "permissions": {
    "allow": ["Bash"],
    "deny": ["Read(./.env)", "Read(./secrets/**)"]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/guard-bash.sh"
          }
        ]
      }
    ]
  }
}
```

```text
钩子与规则的分工：
1. 能写成规则的就写规则 —— 声明式、可审计、启动即校验
2. 规则表达不了的（要看命令语义、要跨字段判断、要联网查）交给 PreToolUse 钩子
3. 想让「默认全允许、少数命令拉黑」，用 allow: ["Bash"] 加一个拦截钩子，而不是列一长串 allow
4. 需要企业级不可绕过，把钩子放进托管设置
```

## 工作目录与敏感数据保护

默认情况下模型只能访问启动目录下的文件。扩展访问有三种方式：启动时 `--add-dir <path>`、会话内 `/add-dir`、或在设置里持久化 `permissions.additionalDirectories`。额外目录里的文件适用同样的权限规则：读取默认免提示（网络路径除外），编辑遵循当前权限模式。注意一个细节——`--add-dir` 与 `/add-dir` 添加的目录会加载少量 `.claude/` 配置（技能等），而写进 `permissions.additionalDirectories` 的目录只授予文件访问，不加载任何配置。

要彻底封住「读工作目录之外」的路，用 `permissions.blockReadsOutsideWorkingDirectories`（较新版本），它在所有权限模式下让文件工具拒绝白名单外的路径。会话迁移用 `/cd <path>`，迁移后会加载新目录的 CLAUDE.md、项目设置、`.mcp.json`、插件与技能，并断开旧目录的 MCP 服务器；新目录未受信任时会先弹出信任提示，列出该目录设置将要激活的 allow 规则、额外目录、钩子与辅助命令。

敏感数据的防线要落在具体条目上：

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./**/*.pem)",
      "Read(./secrets/**)",
      "Bash(cat .env*)",
      "Bash(env)",
      "Bash(printenv)"
    ]
  },
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "denyRead": ["~/"],
      "allowRead": ["."]
    }
  }
}
```

```text
为什么要同时配 deny 规则与沙箱：
1. Read(./.env) 只拦「用文件工具读 .env」以及 cat .env 这类显式命名该文件的操作
2. grep -r 扫目录不在拦截范围内，这是规则匹配「写法」的固有边界
3. 沙箱会把 Read deny 路径加入所有沙箱内命令的不可读集合，把上面那个缺口补上
4. 需要遮罩环境变量与凭据文件时，用 /sandbox 的凭据保护与掩码能力（具体字段以官方文档为准）
```

## 提示注入与安全最佳实践

模型读到的每一段外部内容都可能是指令——网页、issue 正文、依赖里的注释、MCP 服务器返回的数据。官方给出的核心防护包括：Manual 模式下敏感操作需要显式批准；`curl`、`wget` 这类联网命令默认不自动批准；WebFetch 对多数页面会先用另一次模型调用做摘要，模型拿到的是摘要答案而非原始页面；交互式会话在未受信任的目录会先弹信任对话框。这些机制降低风险但不消除风险，边界仍然要靠人来划。

```text
安全自查清单：
1. 用 /permissions 定期复核当前生效的 allow / ask / deny，清掉历史遗留的过宽规则
2. 敏感仓库使用项目级权限设置，凭据文件写进 deny，数据库类 MCP 用只读账号
3. 需要更强隔离时把整个 Claude Code 放进沙箱运行时或 dev container
4. 团队用托管设置统一组织标准，把批准的权限配置纳入版本控制
5. 用 OpenTelemetry 指标监控用量，用 ConfigChange 钩子审计设置改动
6. WebFetch 只放行必要域名，其余走沙箱网络白名单，别用 Bash 规则去限制 URL
```

```json
{
  "permissions": {
    "deny": [
      "Bash(curl *)",
      "Bash(wget *)",
      "Read(./.env)",
      "Read(./secrets/**)"
    ],
    "allow": [
      "WebFetch(domain:docs.anthropic.com)",
      "WebFetch(domain:docs.github.com)"
    ]
  },
  "sandbox": {
    "enabled": true,
    "network": {
      "allowedDomains": ["registry.npmjs.org", "docs.anthropic.com"],
      "strictAllowlist": true
    }
  }
}
```

```text
提示注入的防线顺序：
1. 减少暴露面 —— 不接入不需要的外部数据源，WebFetch 只放行必要域名
2. 减少能力 —— 用 deny 规则禁掉 curl / wget / rm，数据库与第三方系统用最小权限凭据
3. 强制边界 —— 打开沙箱，用 allowedDomains 与 filesystem 限制可达范围
4. 人工复核 —— 生成的高危改动（部署脚本、迁移、权限变更）一律人工 review 后再合并
```

## 应用场景实战

### 场景一：生产仓库的项目级权限文件（只读数据、禁破坏性命令）

一个团队仓库要同时满足三件事：日常命令不用反复批准、模型不能读密钥文件、绝不能在生产分支上直推或跑破坏性命令。做法是把声明式规则放进项目设置，把语义判断放进钩子，最后用沙箱兜底。

```json
{
  "permissions": {
    "allow": [
      "Bash(pnpm run *)",
      "Bash(pnpm test *)",
      "Bash(git add *)",
      "Bash(git commit *)",
      "Bash(git status)",
      "Bash(git diff *)",
      "Read(./src/**)",
      "Read(./docs/**)",
      "WebFetch(domain:docs.anthropic.com)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(pnpm publish *)",
      "WebFetch(domain:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Bash(rm -rf *)",
      "Bash(git reset --hard *)",
      "Bash(git clean -fdx*)",
      "Bash(docker system prune*)",
      "Bash(curl *)",
      "Bash(wget *)"
    ],
    "disableBypassPermissionsMode": "disable",
    "additionalDirectories": ["../shared-types"]
  }
}
```

```bash
#!/bin/bash
# .claude/hooks/guard-bash.sh：规则表达不了的语义判断放在这里
input=$(cat)
cmd=$(echo "$input" | jq -r '.tool_input.command // empty')

# 禁止在受保护分支上直接 push
if [[ "$cmd" =~ ^git[[:space:]]+push ]] && [[ "$cmd" =~ (main|master|release) ]]; then
  echo "Blocked: 受保护分支必须先开 PR，禁止直推" >&2
  exit 2
fi

# 用 jq 判断 npm/pnpm 的 publish 之类不可逆动作
if [[ "$cmd" =~ ^pnpm[[:space:]]+publish ]]; then
  echo "Blocked: 发布动作需人工执行" >&2
  exit 2
fi

exit 0
```

```shell
# 验证拦截确实生效（真实终端可跑）
echo '{"hook_event_name":"PreToolUse","tool_name":"Bash","tool_input":{"command":"git push origin main"}}' \
  | .claude/hooks/guard-bash.sh
echo "退出码=$?"

# 校验设置文件是严格 JSON（注释与尾随逗号会导致 Settings Error）
python3 -c "import json;json.load(open('.claude/settings.json'));print('settings.json OK')"
```

```text
场景要点：
1. allow 覆盖高频只读与构建命令，把提示留给真正危险的动作
2. deny 优先于 allow，破坏性命令直接拒绝而不是提示
3. disableBypassPermissionsMode 防止有人用危险模式绕开这些规则
4. 钩子补语义判断，放在项目设置里随仓库分发
```

### 场景二：无人值守 CI 的最小权限运行

CI 里没人能点批准，必须提前把「允许什么、拒绝什么」写死。做法是显式指定设置来源、用 `dontAsk` 或 `auto` 模式、只放行必要工具，并把项目级配置完全排除在外。

```bash
#!/usr/bin/env bash
# ci/claude-check.sh：无人值守下用最小权限跑一次静态检查
set -euo pipefail

# 1. 只加载用户级设置（这里用 --settings 显式给出内联 JSON），排除仓库设置
read -r -d '' SETTINGS <<'JSON' || true
{
  "permissions": {
    "allow": [
      "Read(./src/**)",
      "Bash(pnpm typecheck)",
      "Bash(pnpm test *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(curl *)",
      "Bash(wget *)",
      "Bash(git push *)"
    ],
    "disableBypassPermissionsMode": "disable"
  }
}
JSON

# 2. 无人值守：分类器先审，无法判定的一律拒绝且不重试；不加载仓库设置文件
claude -p "运行类型检查与单元测试，汇总失败原因，不要修改任何文件" \
  --settings "$SETTINGS" \
  --setting-sources "" \
  --permission-mode auto \
  --permission-prompts none \
  --tools "Read,Grep,Bash" \
  --disallowedTools "Edit,Write" \
  --output-format json \
  > /tmp/claude-check.json

# 3. 失败即让流水线红掉
python3 - <<'PY'
import json, sys
data = json.load(open("/tmp/claude-check.json"))
if data.get("is_error"):
    sys.exit("Claude 运行失败")
print(data.get("result", "")[:500])
PY
```

```text
场景要点：
1. --setting-sources "" 彻底排除仓库设置，避免流水线被仓库里的钩子或允许规则影响
2. --permission-prompts none 让「本该提示」的请求直接拒绝，并告诉模型不要重试（较新版本才支持）
3. --tools 限制可用工具集，--disallowedTools 显式禁掉写文件
4. 用 --output-format json 拿结构化结果做门禁，避免解析人类可读文本
5. CI 凭据用仓库 secret 注入环境变量，绝不落盘到工作区
```

## 最佳实践与踩坑记录

### 最佳实践

1. 权限规则写进 `.claude/settings.json` 提交评审，个人例外放 `.claude/settings.local.json`，让边界有据可查
2. 一律用 `deny` 表达不可协商的底线（`.env`、`secrets/**`、`rm -rf`），不要只依赖提示
3. 敏感仓库打开沙箱，并用 `strictAllowlist` 或托管 `allowManagedDomainsOnly` 收紧出网域名
4. 别用 Bash 规则去限制 URL，curl 的写法千变万化；出网限制交给沙箱白名单或 PreToolUse 钩子
5. 规则里保留足够的只读与构建命令 allow，否则开发者会习惯性切到危险模式，反而更不安全
6. 数据库、工单、云平台类 MCP 一律用最小权限凭据，写操作留人工复核
7. 用 `/permissions` 与 `claude doctor` 定期复核生效规则，用 ConfigChange 钩子审计设置改动

### 踩坑记录

```text
坑 1：以为 deny 规则能挡住所有读取，结果敏感文件还是被读到了
结论：.env 没被直接读，但 grep -r 扫目录时内容漏进了上下文。
原因：Read(./.env) 只拦「写明该文件」的操作，递归扫描目录不会被匹配。
解法：同时打开沙箱，让 Read deny 路径进入所有沙箱内命令的不可读集合；凭据一律移出仓库工作区。

坑 2：Bash 规则限制 URL 失败，模型照样访问了外网
结论：curl 白名单形同虚设，数据被发到未授权地址。
原因：Bash 规则匹配的是命令文本，`-X GET`、https、跳转短链、绝对路径调用、sh -c 内调用都能绕过。
解法：禁掉 curl / wget，改用 WebFetch 的 domain 规则；真正的边界用沙箱 allowedDomains 或 PreToolUse 钩子校验。

坑 3：CI 里命令全被拒绝，任务跑不完
结论：流水线里 Claude 几乎什么都做不了，日志显示大量 permission denied。
原因：无人值守环境没人能批准，默认模式下的提示全部变成拒绝；或者用了 dontAsk 却没给 allow 列表。
解法：显式给出 --allowedTools 或 permissions.allow 白名单，配合 --permission-mode auto + --permission-prompts none，按最小必要集放行。

坑 4：有人用 bypassPermissions 绕过了所有守卫
结论：钩子与规则之外的改动照样发生，事后才发现。
原因：bypassPermissions 会跳过权限提示（含受保护路径写入），而多数规则对它不生效。
解法：在托管设置里设 permissions.disableBypassPermissionsMode 为 disable，并用返回 deny 的 PreToolUse 钩子兜住必须执行的策略。

坑 5：设置了 --add-dir 却仍然读不到额外目录
结论：工具报路径不在允许范围内。
原因：把目录写进了 permissions.additionalDirectories 或用了错误路径，或沙箱的写入白名单没同步放行该目录。
解法：读写访问与沙箱能力要分别配置——additionalDirectories 管权限，sandbox.filesystem.allowWrite 管沙箱内的写入范围。

坑 6：改完权限设置没生效，怀疑配置损坏
结论：命令仍然被提示或被拒绝。
原因：设置文件是严格 JSON，注释或尾随逗号导致 Settings Error，整个文件被跳过；少数键只在会话启动时读取。
解法：用 python3 -c "import json;json.load(open(...))" 校验语法，会话内用 /status 看已加载的设置来源，用 claude doctor 看被拒绝的条目。
```
