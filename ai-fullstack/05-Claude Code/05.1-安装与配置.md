## 概述

Claude Code 是 Anthropic 官方的编码智能体，终端 CLI 是它的主形态，同一套设置文件也服务于 VS Code / JetBrains 扩展与桌面端。它装在开发者本机、以当前工作目录为作用域运行，读取一组 JSON 设置文件决定用哪个模型、能自动执行哪些命令、请求走不走代理。本篇只解决「把它正确装上、正确登录、把配置分层放对」这一件事，不涉及交互用法与记忆体系。

```text
本篇的五个抓手：
1. 装 —— 官方安装脚本（推荐的 native 安装）/ Homebrew / WinGet / apt dnf apk / npm 六种方式
2. 登 —— claude.ai 订阅（Pro / Max / Team / Enterprise）或 Anthropic Console（API 计费），凭据优先级共 7 级
3. 配 —— 四层设置文件（user / project / local / managed）加一个 ~/.claude.json，写法是严格 JSON
4. 选 —— 模型别名与全名、五种设置途径的优先级、effort 推理强度的解析顺序
5. 通 —— HTTPS_PROXY 等标准代理变量、自签 CA、mTLS 客户端证书、域名白名单、LLM 网关

本机环境说明：Ubuntu 24.04 + Node 22.23.2，实验机上未安装 claude CLI，因此本篇命令与配置字段均取自官方文档（code.claude.com/docs），
只有网络连通性是本机实测（结论见「代理与网络环境」一节）。版本号与模型矩阵随官方更新，请以官方文档与 /model 选择器为准，不要照抄本篇的版本号。
```

## 安装与登录

Claude Code 的运行要求不高：macOS 13.0+、Windows 10 1809+ / Windows Server 2019+、Ubuntu 20.04+、Debian 10+、Alpine 3.19+，4 GB 以上内存，x64 或 ARM64，Shell 支持 Bash / Zsh / PowerShell / CMD。ripgrep 通常随 CLI 一起提供，搜索能力依赖它，缺失时搜索会失败。官方推荐 native 安装（自更新、单二进制），其余方式用于受控环境或已有包管理体系。

```bash
# 方式一：native 安装（官方推荐，macOS / Linux / WSL）
curl -fsSL https://claude.ai/install.sh | bash

# 装 stable 通道（约落后一周，跳过有重大回归的版本）
curl -fsSL https://claude.ai/install.sh | bash -s stable

# 装指定版本（企业内需要版本一致时）
curl -fsSL https://claude.ai/install.sh | bash -s 2.1.89

# 方式二：Homebrew（macOS / Linux）
brew install --cask claude-code          # 跟随 stable 通道
brew install --cask claude-code@latest   # 跟随 latest 通道

# 方式三：WinGet（Windows）
winget install Anthropic.ClaudeCode

# 方式四：npm 全局包（需要 Node.js 22 或更高；包内是 native 二进制，运行时不用 Node）
npm install -g @anthropic-ai/claude-code
npm install -g @anthropic-ai/claude-code@latest   # 升级；不要用 npm update -g
```

```bash
# 方式五：Linux 包管理器（apt 示例，stable 通道）
# 1. 导入签名公钥（指纹应为 31DDDE24DDFAB679F42D7BD2BAA929FF1A7ECACE）
sudo install -d -m 0755 /etc/apt/keyrings
sudo curl -fsSL https://downloads.claude.ai/keys/claude-code.asc \
  -o /etc/apt/keyrings/claude-code.asc
gpg --show-keys /etc/apt/keyrings/claude-code.asc

# 2. 注册 stable 仓库并安装
echo "deb [signed-by=/etc/apt/keyrings/claude-code.asc] https://downloads.claude.ai/claude-code/apt/stable stable main" \
  | sudo tee /etc/apt/sources.list.d/claude-code.list
sudo apt update
sudo apt install claude-code
# 切换 latest 通道：仓库 URL 与 suite 名都要换成 .../apt/latest latest main
# 后续升级：sudo apt update && sudo apt upgrade claude-code
```

```bash
# 验证安装
claude --version     # 正常输出形如 2.1.211 (Claude Code)
claude doctor        # 只读诊断：安装健康度、设置文件校验错误、更新状态

# 首次登录：直接跑 claude，跟着浏览器提示走
claude

# 非交互地管理认证（适合脚本与排障）
claude auth login --console     # 用 Anthropic Console 账号登录（API 计费）
claude auth status              # 输出 JSON；加 --text 为人读格式，登录返回 0、未登录返回 1
claude auth logout
```

登录支持五类账号：claude.ai 的 Pro / Max 订阅、Claude for Teams / Enterprise、Anthropic Console（可以直接登录，也可以让它替你创建 API key）、云厂商（Amazon Bedrock / Google Cloud 的 Agent Platform / Microsoft Foundry，设好环境变量或登录界面选 `3rd-party platform`）、以及企业自建的 Claude apps gateway（走公司 SSO）。免费版 claude.ai 不含 Claude Code。

```text
登录与凭据要点：
1. 浏览器打不开时按 c 复制登录 URL；浏览器只给了一串 code 时，粘贴到终端的 "Paste code here if prompted"（WSL2 / SSH / 容器里最常见）
2. 多账号（工作 + 个人）用 CLAUDE_CONFIG_DIR 隔离：alias claude-work='CLAUDE_CONFIG_DIR=~/.claude-work claude'，各自拥有设置、历史与登录态
3. CI 与脚本里没有浏览器，用 claude setup-token 生成一年期 OAuth token，写入 CLAUDE_CODE_OAUTH_TOKEN（该 token 只能发模型请求）
4. 凭据优先级（高到低）：云厂商凭据 → ANTHROPIC_AUTH_TOKEN → ANTHROPIC_API_KEY → apiKeyHelper 脚本 → CLAUDE_CODE_OAUTH_TOKEN → Anthropic profile 与联合身份 → /login 的订阅凭据
5. 同时存在订阅登录和环境里的 ANTHROPIC_API_KEY 时，CLI 会用 API key；unset ANTHROPIC_API_KEY 才回落到订阅，用 /status 确认当前生效的是哪一个
6. 登录还剩 3 天过期时启动会提示 "Your login expires in 3 days · run /login to renew"，无人值守的会话必须提前续期
```

```json
// ~/.claude/settings.json：用脚本动态取短期凭据，适合从 vault 拿 token 的场景
{
  "apiKeyHelper": "/usr/local/bin/fetch-claude-key.sh"
}
```

## 订阅与 API 计费

有两条完全不同的付费路径：订阅制（Pro / Max / Team / Enterprise，按座位与用量窗口限流）与 API 计费（Anthropic Console，按 token 用量付费）。选错路径不会报错，但会影响你看的报表和限额提示。Claude Code 按 token 消耗计费；订阅用户的成本数字不计入账单，他们看的是套餐用量条。

| 路径 | 适用 | 账号形态 | 用量查看 | 花费上限 |
| - | - | - | - | - |
| Claude Pro / Max | 个人 | claude.ai 账号 | `/usage` 的套餐用量分解、`/usage-credits` | 套餐用量窗口，可选购 usage credits 与月消费上限 |
| Claude for Teams / Enterprise | 中小到大型团队 | 团队邀请的 claude.ai 账号 | 组织分析的 spend report（按人按模型，可导出 CSV，每日更新） | 座位额度加组织 / 组 / 个人三层 spend limit |
| Anthropic Console（API） | 要按量计费的团队 | Console 账号（可无 key 登录） | Console 的 usage 页、Claude Code Analytics API | workspace 级消费与速率限制 |
| 云厂商与自建网关 | 合规要求高 | Bedrock / Vertex / Foundry / Claude apps gateway | AWS Cost Explorer / GCP Billing / 网关自身指标 | 云侧预算与网关的 per-user spend limit |

```bash
# 会话内查看用量（Pro / Max / Team / Enterprise 会额外给出套餐用量分解）
/usage

# 用量窗口被打满后的两条路
/usage-credits     # 打开 claude.ai 的 Settings > Usage：开启或关闭 usage credits、设月消费上限

# 团队场景：生成个人使用习惯报告（分析本机最近最多 200 个会话，输出 HTML）
/insights          # 报告写到 ~/.claude/usage-data/report.html

# 结构化取数：脚本里直接读本次调用的成本估算
claude -p "总结这个仓库" --output-format json | jq '.total_cost_usd'
```

```text
计费相关要点：
1. 订阅用户 /usage 的 Session 区块给的是按列表价折算的本地估算，不是账单；只有 API 用户才对得上账
2. 限额提示分三种含义：session / weekly limit 是订阅的座位窗口（换模型也解不开）、spend limit 是 usage credits 打顶、context 警告则完全是另一回事（接近自动压缩阈值）
3. 组织若按合同价结算，需要在 managed settings 里配 modelPricing 的 mode，否则 /usage、状态栏、OpenTelemetry 都按列表价显示，与账单不符
4. background token usage 真实存在：命令处理、prompt suggestions 等后台请求也会计入用量
5. 一个长期开着的会话用量陡增，常见原因是缓存失效（间隔超过缓存生命周期后首条消息重算整段上下文）与长上下文，而不是你多打了字
```

## 配置文件层级与优先级

Claude Code 的行为由 JSON 设置键控制。安装它不会自动创建任何设置文件：文件要么来自组织下发（managed），要么是团队提交到仓库的共享配置，要么是你在 `/config` 里改选项、或在权限提示里选「Yes, and don't ask again」时由 CLI 自己写出来的。同名键出现在多层时只有最高层生效，但列表类键（如 `permissions.allow`）是合并而不是覆盖。

| 作用域 | 文件 | 影响谁 | 用途 |
| - | - | - | - |
| User | `~/.claude/settings.json` | 本机所有项目里的你 | 个人偏好：主题、编辑器模式、默认模型、个人权限规则 |
| Shared project | `.claude/settings.json` | 包含该文件的目录里的所有人 | 团队权限、hooks、插件、项目所需环境变量，应提交进 git |
| Project local | `.claude/settings.local.json` | 只在当前项目里的你 | 个人覆盖与试验；CLI 写入时会自动加进你的全局 git 忽略 |
| Managed | `managed-settings.json`、MDM 策略、服务端下发 | 组织部署到的全部机器 | 安全与合规策略，个人文件无法覆盖 |

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "model": "opus",
  "env": {
    "HTTPS_PROXY": "http://proxy.corp.example.com:8080",
    "NODE_EXTRA_CA_CERTS": "/etc/ssl/certs/corp-ca.pem"
  },
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  },
  "autoUpdatesChannel": "stable",
  "minimumVersion": "2.1.100"
}
```

```bash
# 只改一个键并立即生效（多数键热加载，无需重启）
claude --settings '{"model": "claude-opus-5-5"}'     # --settings 覆盖同名键，但覆盖不了 managed

# 确认当前会话加载了哪些来源（Status 页的 Setting sources 行）
/status
claude doctor     # 列出被拒绝的条目与安装问题

# 打开配置面板，或单键覆盖
/config
```

```text
设置优先级与生效规则：
1. 优先级从高到低：Managed settings → --settings 传入的 JSON → .claude/settings.local.json → .claude/settings.json → ~/.claude/settings.json
2. 环境变量不在这条链上：ANTHROPIC_MODEL 这类"有配对变量"的键按各自的成对规则判定，以官方「环境变量参考」的 precedence 一节为准
3. 设置文件是严格 JSON：注释与尾逗号都是语法错误，会在下次启动报 Settings Error
4. 列表类键合并（逐层追加），但 fallbackModel、modelPicker 这类有序键整值取最高优先级的那一层
5. CLI 自己还维护第五个文件 ~/.claude.json（登录态、MCP 配置、项目信任状态），不要手工编辑；要换目录用 CLAUDE_CONFIG_DIR
6. 热加载覆盖 user / project / local / managed 的设置改动并触发 ConfigChange hook，少数键只在会话启动时读一次（如 model 的持久值、effortLevel）
```

## 模型选择与推理强度

模型既可以用别名（不必记版本号）也可以用全名。别名会随时间指向各 provider 的推荐版本，所以想长期钉住某个版本就写全名或设 `ANTHROPIC_DEFAULT_*_MODEL`。推理强度（effort）控制自适应思考的深度：低档位更快更便宜，高档位在复杂任务上思考更久。

| 模型别名 | 行为 |
| - | - |
| `default` | 特殊值：清掉任何模型覆盖，回到账号的运行时默认 |
| `best` | 走 Fable 别名解析到的模型，没有 Fable 时等于 `opus` |
| `fable` | 面向最长、最难的自主任务（Fable 5.1，网关会话里为 Fable 5） |
| `sonnet` | 日常编码任务的默认档 |
| `opus` | 复杂推理任务 |
| `haiku` | 简单任务，最快最省 |
| `sonnet[1m]` / `opus[1m]` | 使用 100 万 token 上下文窗口的长会话变体 |
| `opusplan` | 计划模式用 opus，执行阶段切回 sonnet |

```bash
# 五种设置途径，优先级从高到低
/model sonnet                  # 1) 会话内切换（回车写进 user settings 成为新默认；选择器里按 s 只对本会话生效）
claude --model opus            # 2) 启动参数，只影响本次启动
export ANTHROPIC_MODEL=opus    # 3) 环境变量，覆盖任何文件里的 model
# 4) 设置文件里的 "model": "opus"
export ANTHROPIC_DEFAULT_MODEL=sonnet   # 5) 仅当以上都没设时决定新会话的默认模型

# 钉住具体版本，别依赖别名漂移
/model claude-opus-5-5

# 推理强度：会话内 / 启动参数 / 环境变量 / 设置文件
/effort high
claude --effort xhigh
export CLAUDE_CODE_EFFORT_LEVEL=medium
```

```json
{
  "model": "opus",
  "modelSettings": {
    "claude-opus-5-5": { "effortLevel": "xhigh" }
  },
  "autoCompactWindow": 500000
}
```

```text
模型与强度要点：
1. effort 档位为 low / medium / high / xhigh / max，但可用档位取决于模型；设了模型不支持的档位会回落到不高于它的最高档
2. Opus 5.5 / Sonnet 5.5 / Haiku 5.5 默认 medium，Opus 4.7 默认 xhigh，其余支持 effort 的模型默认 high
3. 用 /model 切换模型会连带影响"继承主会话模型"的子代理，因为它们是在被启动那一刻解析模型的
4. 恢复会话（--resume / --continue / /resume）沿用当时的模型；若模型已退役或被 availableModels 排除，则按正常优先级重新解析
5. 组织可用 managed settings 的 availableModels / deniedModels 限制可选模型，--model 只能在允许范围内选
6. 自动压缩阈值随模型不同：原生 1M 窗口的模型约在 967K token 时压缩，可用 /autocompact、autoCompactWindow 或 CLAUDE_CODE_AUTO_COMPACT_WINDOW 调整
```

## 代理与网络环境

企业网络里 Claude Code 需要穿过代理、信任自签 CA，必要时做 mTLS 双向认证。这些全部通过环境变量配置，而且应该写进设置文件的 `env` 块而不只是 shell 导出——原因见要点第 2 条。官方还列出了一组必须放行的域名，容器和受限网络里最容易漏。

```bash
# 代理（推荐 HTTPS_PROXY；小写变体也支持）
export HTTPS_PROXY=https://proxy.example.com:8080
export HTTP_PROXY=http://proxy.example.com:8080
export NO_PROXY="localhost 192.168.1.1 example.com .example.com"   # 空格或逗号分隔
export HTTPS_PROXY=http://username:password@proxy.example.com:8080 # 需要 Basic 认证时

# 证书：默认信任内置 Mozilla CA 加操作系统证书库
export NODE_EXTRA_CA_CERTS=/etc/ssl/certs/corp-ca.pem   # 自签根证书
export CLAUDE_CODE_CERT_STORE=bundled                   # 只用内置集；system 则只用系统库，默认 bundled,system

# mTLS 客户端证书（启动时读取，请求失败后按需重读）
export CLAUDE_CODE_CLIENT_CERT=/path/to/client-cert.pem
export CLAUDE_CODE_CLIENT_KEY=/path/to/client-key.pem
export CLAUDE_CODE_CLIENT_KEY_PASSPHRASE="your-passphrase"

# 走 LLM 网关或自定义端点：改的是请求地址，不是模型
export ANTHROPIC_BASE_URL=https://llm-gateway.corp.example.com
```

```bash
# 验证配置真的加载了：调试日志写到 ~/.claude/debug/<session-id>.txt
claude --debug
# 日志里应能看到形如下面的行
# CA certs: Appended extra certificates from NODE_EXTRA_CA_CERTS (/etc/ssl/certs/corp-ca.pem)
# mTLS: Loaded client certificate from CLAUDE_CODE_CLIENT_CERT

# 会话内看 /status 的这几行
/status      # Proxy / mTLS client cert / mTLS client key / Additional CA cert(s)
```

```text
网络要点：
1. 代理地址解析失败（例如漏了 http:// 前缀）是少数在启动时就直接报错的环境变量，其余多数只在后续请求失败时才暴露
2. 代理、CA、mTLS 变量要写进 ~/.claude/settings.json 的 env 块而不只是 shell：后台会话由一个共享 supervisor 进程托管，只认 settings 里的配置
3. 不支持 SOCKS 代理；需要 NTLM / Kerberos 等高级认证时，用支持它的 LLM 网关
4. 需放行的域名：api.anthropic.com（模型请求与遥测）、claude.ai 与 claude.com（账号登录）、platform.claude.com（Console 登录与 token 交换）、mcp-proxy.anthropic.com（claude.ai 的 MCP 连接器）、downloads.claude.ai（安装器、自更新、插件下载）
5. 企业防火墙还要按需放行 GitHub 相关域名（GitHub App 与自建 GHES 场景）
6. 本机实测（Ubuntu 24.04）：https://code.claude.com 返回 HTTP 200；https://api.anthropic.com/v1/messages 无凭据返回 HTTP 403 —— 403 说明网络可达、只是缺认证，可用于验证出网链路
```

## 应用场景实战

### 场景一：企业内网开发机初始化（代理 + 自签 CA + 锁版本）

```bash
#!/usr/bin/env bash
# setup-claude.sh：内网机器一键初始化，供 IT 随 MDM / Ansible 下发
set -euo pipefail

# 1) 装 stable 通道（版本一致性比新功能重要）
curl -fsSL https://claude.ai/install.sh | bash -s stable

# 2) 写用户级设置：代理、CA、通道、版本下限集中在这里，而不是塞进每个人的 .bashrc
mkdir -p ~/.claude
cat > ~/.claude/settings.json <<'JSON'
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "autoUpdatesChannel": "stable",
  "minimumVersion": "2.1.100",
  "env": {
    "HTTPS_PROXY": "http://proxy.corp.example.com:8080",
    "HTTP_PROXY": "http://proxy.corp.example.com:8080",
    "NO_PROXY": "localhost,127.0.0.1,.corp.example.com",
    "NODE_EXTRA_CA_CERTS": "/etc/ssl/certs/corp-ca.pem"
  }
}
JSON

# 3) 检验：先看版本，再看诊断，最后确认代理与 CA 行被识别
claude --version
claude doctor
claude --debug -p "回复 ok 即可"     # 在 ~/.claude/debug/<session-id>.txt 里确认 CA 与 Proxy 行
```

### 场景二：CI 流水线里无浏览器登录（长期 token）

```bash
#!/usr/bin/env bash
# 在 CI 里跑一次性代码检查：用订阅的长期 OAuth token，而不是把个人 API key 塞进 Secrets
set -euo pipefail

# 前置：在本地一次性执行 claude setup-token，把打印出来的 token 存进 CI 的 Secret
export CLAUDE_CODE_OAUTH_TOKEN="$CLAUDE_CODE_OAUTH_TOKEN"

# 用 -p 非交互运行，输出 JSON 便于后续步骤判断
claude -p "检查本次 diff 是否存在明显的空指针与未处理异常" \
  --allowedTools "Read,Grep,Glob" \
  --output-format json > /tmp/review.json

# 用 jq 取出结论与花费估算
jq -r '.result' /tmp/review.json
jq -r '"cost_usd=" + (.total_cost_usd | tostring)' /tmp/review.json
```

```text
CI 场景注意：
- --bare 启动更快、不读宿主机的 hooks / MCP / CLAUDE.md，但它同样不读 OAuth 凭据与系统钥匙串：用 --bare 时要改用 ANTHROPIC_API_KEY 或 apiKeyHelper
- token 只打印一次且不落盘，务必立刻存进 CI Secret
- 退出码可用于卡门禁：成功 0、失败非 0；用 SIGTERM 停止会以 143 退出
```

### 场景三：一个开发者同时用工作与个人账号，并区分计费

```bash
# 工作账号走 Console（API 计费），个人账号走 Max 订阅，互不干扰
cat >> ~/.bashrc <<'EOF'
alias claude-work='CLAUDE_CONFIG_DIR=~/.claude-work claude'

# 首次分别登录

# 确认各自生效的凭据
claude auth status --text
```

## 最佳实践与踩坑记录

### 最佳实践

1. 优先用 native 安装脚本：自更新、单二进制，`~/.local/bin/claude` 只是指向 `~/.local/share/claude/versions/` 的符号链接，升级过程可预期
2. 团队统一 release 通道：用 managed settings 固定 `autoUpdatesChannel`，必要时配 `minimumVersion` 设版本下限，避免同一仓库在不同版本上行为不一致
3. 分层放配置：个人偏好进 `~/.claude/settings.json`，团队共享的权限与 hooks 进 `.claude/settings.json` 并提交，个人覆盖进 `.claude/settings.local.json`
4. 凭据一律走环境变量或 `apiKeyHelper`，不要把 key 硬编码进脚本或提交进仓库；CI 用 `claude setup-token` 生成的长期 token
5. 代理、CA、mTLS 变量写进设置文件的 `env` 块，让前台会话与后台会话拿到同一套网络配置
6. 上线前用 `claude doctor` 与 `/status` 双确认：前者看安装与设置错误，后者看当前会话实际加载了哪些来源
7. 试验用 `--settings '<json>'` 做一次性覆盖，确认有效再落到对应层级的文件里

### 踩坑记录

```text
坑 1：把代理写进 .bashrc，后台会话却不受影响
结论：前台会话走代理正常，claude agents 或 --bg 起的后台会话连接模型失败。
原因：后台会话由按需启动的共享 supervisor 进程托管，它继承的是第一个启动它的 shell 的环境。
解法：把 HTTPS_PROXY / NO_PROXY / NODE_EXTRA_CA_CERTS 写进 ~/.claude/settings.json 的 env 块或 managed settings，然后执行 claude daemon stop --any 让新配置生效。

坑 2：settings.json 里写了注释，启动报 Settings Error
结论：加了一行 // 说明后，启动时设置被整体判为无效，Claude 以默认行为运行。
原因：设置文件是严格 JSON，不允许注释和尾逗号，整文件被判为语法错误。
解法：去掉注释与尾逗号，需要说明就写在 CLAUDE.md 里；加 $schema 让编辑器提前报错。

坑 3：订阅用户却设了 ANTHROPIC_API_KEY，用量和账单走错路径
结论：以为是套餐内用量，实际全部计入 API 计费；若 key 属于已停用组织则直接认证失败。
原因：凭据优先级里 ANTHROPIC_API_KEY 高于 /login 的订阅凭据，交互模式下确认一次后就被记住。
解法：unset ANTHROPIC_API_KEY，用 /status 确认生效凭据；要恢复 key 就在 /config 里用 "Use custom API key" 开关。

坑 4：npm 安装后 claude 命令找不到，或升级失败
结论：装完提示 command not found，或升级时提示 npm 全局目录不可写。
原因：npm 全局 bin 目录不在 PATH；用 sudo npm install -g 又会留下 root 属主的目录。
解法：不要用 sudo，把 npm prefix 配到用户目录并加入 PATH；升级用 npm install -g @anthropic-ai/claude-code@latest，不要用 npm update -g。

坑 5：容器里安装脚本报 403 或 syntax error
结论：安装命令直接失败，日志里出现 403 或 "syntax error near unexpected token '<'"。
原因：出网被代理拦截，返回的其实是 HTML 错误页而不是安装脚本；或 Alpine 缺 bash 与 curl。
解法：先在防火墙放行 downloads.claude.ai 并确认企业 CA 已装入系统信任库；Alpine 先 apk add bash curl libgcc libstdc++ ripgrep 并设 USE_BUILTIN_RIPGREP=0。
```
