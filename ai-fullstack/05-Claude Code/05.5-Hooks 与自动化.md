## 概述

Hooks（钩子）是 Claude Code 在生命周期固定节点自动执行的用户自定义动作：shell 命令、HTTP 端点、MCP 工具调用、LLM 提示或子代理。它的价值在于把「必须百分之百发生的规则」从模型判断中剥离出来——格式化、审计、拦截危险命令这类事情交给确定性脚本，而不是指望提示词约束模型行为。无论会话跑在终端、IDE 扩展、桌面应用还是 Web 上，触发的事件名与输入 JSON 结构都一致。

```text
Hooks 的三个关键定位：
1. 确定性 —— 脚本执行由事件触发，不受模型判断影响，模型无法跳过已配置的钩子
2. 双向通道 —— 输入是真 JSON（stdin / POST body），输出可用退出码与 JSON 回写决策
3. 分层可控 —— 用户级 / 项目级 / 本地级 / 企业托管级 / 插件内均可定义，且相互合并不覆盖
```

## Hook 生命周期与事件类型

官方把事件按触发节奏分成三类：每会话一次（`SessionStart`、`SessionEnd`）、每轮对话一次（`UserPromptSubmit`、`Stop`、`StopFailure`）、代理循环内每次工具调用（`PreToolUse`、`PostToolUse`，其中 `EndConversation` 调用两者都会跳过）。理解这个节奏，才能判断某个钩子会不会在一次会话里被调用几百次。

常用事件与触发时机的对应关系如下（完整清单以官方 Hooks reference 为准）：

| 事件 | 触发时机 | 常见用途 |
| :- | :- | :- |
| `SessionStart` | 会话开始或恢复时 | 注入项目上下文、导出环境变量 |
| `Setup` | `--init-only`，或 `-p` 模式下的 `--init` / `--maintenance` | CI 与脚本的一次性准备 |
| `UserPromptSubmit` | 用户提交提示词、Claude 处理之前 | 校验提示、补充上下文、拦截提示 |
| `UserPromptExpansion` | 用户输入的命令展开为提示词时 | 可阻止命令展开 |
| `PreToolUse` | 工具调用执行之前 | 拦截危险命令、重写工具入参 |
| `PermissionRequest` | 某次工具调用需要权限决策时 | 代表用户自动允许或拒绝 |
| `PermissionDenied` | 自动模式拒绝了工具调用时 | 用 `retry: true` 告知模型可重试 |
| `PostToolUse` | 工具调用成功之后 | 自动格式化、跑校验、审计日志 |
| `PostToolUseFailure` | 工具调用失败之后 | 收集失败原因、上报 |
| `PostToolBatch` | 一批并行工具调用全部结束后 | 汇总批量结果 |
| `Notification` | Claude Code 发出通知时 | 桌面提醒、蜂鸣 |
| `SubagentStart` / `SubagentStop` | 子代理启动 / 结束时 | 追踪委派任务 |
| `PreCompact` / `PostCompact` | 上下文压缩前 / 后（matcher 为 `manual` 或 `auto`） | 压缩后重注入关键上下文 |
| `Stop` / `StopFailure` | Claude 完成一次响应 / 因 API 错误结束时 | 收尾检查、通知、失败告警 |
| `SessionEnd` | 会话结束时（matcher 为 `clear`、`resume`、`logout` 等） | 清理临时资源 |
| `FileChanged` | 被监视的文件在磁盘上变化后 | 重新加载环境（不能拦截写入） |
| `ConfigChange` | 配置文件发生变化时 | 审计配置改动 |
| `CwdChanged` / `DirectoryAdded` | 工作目录切换 / 新增目录时 | 同步工具链状态 |

```text
事件选择的三条经验：
1. 想「阻止」某个动作 —— 只能用 PreToolUse / UserPromptSubmit / Stop 这类有决策控制的事件
2. 想「善后」某个动作 —— 用 PostToolUse（此时工具已经执行，无法回滚）
3. 想「跟随文件变化」而不是「跟随工具调用」 —— 用 FileChanged，它无法拦截写入
```

## 配置结构、作用域与匹配器

Hooks 写在 JSON 设置文件里，结构是三层嵌套：先选事件，再加一层 matcher 组做过滤，最后在组内定义若干处理器（handler）。同一事件可以配置多个 matcher 组；所有匹配的处理器会并行执行，同一个处理器写在多个设置文件里也只跑一次。

配置位置决定作用范围：

| 位置 | 作用范围 | 可否随仓库分发 |
| :- | :- | :- |
| `~/.claude/settings.json` | 本机所有项目 | 否 |
| `.claude/settings.json` | 单个项目 | 是，可提交到版本库 |
| `.claude/settings.local.json` | 单个项目、仅自己 | 否，Claude Code 写入时会自动排除 |
| 托管策略设置 | 整个组织 | 是，由管理员控制 |
| 插件的 `hooks/hooks.json` | 插件启用期间 | 是，随插件分发 |
| Skill / 子代理的 frontmatter | 技能调用后的会话 / 该子代理运行期间 | 是 |

matcher 的判定规则取决于它包含的字符，这一点容易踩坑：

| matcher 取值 | 判定方式 | 例子 |
| :- | :- | :- |
| `"*"`、`""` 或省略 | 匹配全部 | 该事件每次都触发 |
| 只含字母、数字、`_`、`-`、空格、`,`、`\|` | 精确字符串，或 `\|` / `,` 分隔的精确字符串列表 | `Edit\|Write` 精确匹配 Edit 或 Write |
| 含其他字符 | 不加锚定的 JavaScript 正则 | `^Notebook` 匹配以 Notebook 开头的工具名 |

对工具类事件，matcher 过滤的是 `tool_name`；MCP 工具名形如 `mcp__<server>__<tool>`，要匹配一个服务器的全部工具必须写成 `mcp__memory__.*` —— 写 `mcp__memory` 只会被当成精确字符串，什么都匹配不到。更细的过滤条件用处理器上的 `if` 字段，它使用权限规则语法，可同时约束工具名与参数，例如 `"Bash(git *)"`、`"Edit(*.ts)"`。`if` 只在工具类事件上生效，其他事件上带 `if` 的处理器永远不会运行。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "mcp__.*__write.*",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git *)",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/validate-mcp-write.sh"
          }
        ]
      }
    ]
  }
}
```

```text
配置要点：
1. 三层结构 —— 事件名 -> matcher 组数组 -> 组内 hooks 数组，事件名是同一个 hooks 对象下的兄弟键
2. 合并而非覆盖 —— 用户级、项目级、本地级、插件、托管策略各自添加自己的钩子，不会互相删除
3. matcher 写正则时必须自己加 ^ 与 $，否则 RegExp.test 是「包含即匹配」
4. 执行顺序不可假设，多个处理器并行执行，别让两个钩子改同一个工具的入参
```

## 处理器字段与脚本约定

处理器有五种类型：`command`（跑 shell 命令）、`http`（POST 事件 JSON 到 URL）、`mcp_tool`（调用已配置的 MCP 服务器工具）、`prompt`（单轮 LLM 评估并返回 JSON 决策）、`agent`（派子代理核实条件，实验特性）。日常绝大多数场景用 `command`。

通用字段与命令型专有字段：

| 字段 | 适用 | 说明 |
| :- | :- | :- |
| `type` | 全部 | `command` / `http` / `mcp_tool` / `prompt` / `agent` |
| `if` | 全部 | 一条权限规则语法，仅工具类事件生效 |
| `timeout` | 全部 | 超时秒数。`command`/`http`/`mcp_tool` 默认 600，`prompt` 默认 30，`agent` 默认 60；`UserPromptSubmit`、`Pre/PostModelSwitch` 降到 30，`MessageDisplay` 降到 10 |
| `statusMessage` | 全部 | 执行期间显示的 spinner 文案 |
| `once` | 技能 frontmatter | 首次成功后移除该钩子，设置文件里被忽略 |
| `command` | `command` | 要执行的可执行文件或 shell 命令 |
| `args` | `command` | 参数数组。存在时走 exec 形式：`command` 按 PATH 解析为可执行文件直接 spawn，不经过 shell |
| `async` | `command` | 后台执行，不阻塞会话 |
| `asyncRewake` | `command` | 后台执行，退出码为 2 时唤醒 Claude 并把 stderr（为空则 stdout）作为系统提醒给它 |
| `shell` | `command` | 取 `bash` 或 `powershell`；设了 `args` 时忽略 |
| `onFailure` | `command` | 钩子失败时的行为：`continue`（默认）或 `block` |

exec 形式（带 `args`）与 shell 形式（不带 `args`）的区别在于是否经过 shell 解析：exec 形式每个 `args` 元素原样作为一个参数传入，`${CLAUDE_PLUGIN_ROOT}` 之类占位符在 `command` 与 `args` 元素里被当作纯字符串替换；shell 形式则可以写管道、`&&`、重定向与通配符。需要在钩子里引用脚本路径时，两种形式都会把 `CLAUDE_PROJECT_DIR`、`CLAUDE_PLUGIN_ROOT`、`CLAUDE_PLUGIN_DATA` 导出为环境变量。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "node",
            "args": ["${CLAUDE_PROJECT_DIR}/scripts/format.js", "--fix"],
            "statusMessage": "正在格式化改动文件",
            "timeout": 60
          }
        ]
      }
    ]
  }
}
```

```text
脚本约定的四件事：
1. 钩子脚本必须可执行，提交到仓库后同事也要能用：chmod +x .claude/hooks/*.sh
2. 用 ${CLAUDE_PROJECT_DIR} 引用仓库内脚本，别写死绝对路径
3. 需要管道 / 重定向就省略 args 走 shell 形式，需要精确传参就用 exec 形式
4. 长耗时动作（跑全量测试、发通知）加 "async": true，避免拖慢每轮对话
```

## 输入结构与退出码

命令型钩子从 stdin 收到一个 JSON 对象，HTTP 型钩子则是在 POST body 里收到同一份 JSON。除各事件专有字段外，通用字段包含 `session_id`、`transcript_path`、`cwd`、`hook_event_name`、`permission_mode`（值为 `default`、`plan`、`acceptEdits`、`auto`、`dontAsk`、`bypassPermissions` 之一；UI 上叫 Manual 的模式传过来是 `default`）。工具类事件额外带 `tool_name`、`tool_input`、`tool_use_id`；MCP 工具的输入里还有 `mcp_server` 对象，含 `name` 与 `source`（`plugin`、`sdk`、`user`、`project` 等），做信任判断要看 `source` 而不是名字前缀。

`UserPromptSubmit` 的输入示例（官方文档给出的结构）：

```json
{
  "session_id": "abc123",
  "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
  "cwd": "/Users/...",
  "permission_mode": "default",
  "hook_event_name": "UserPromptSubmit",
  "prompt": "Write a function to calculate the factorial of a number"
}
```

退出码决定动作是否继续：退出 0 是成功，退出 2 是阻塞错误（在支持拦截的事件上终止动作，stderr 作为原因反馈给 Claude）；其他退出码是非阻塞错误，动作照常执行，只在转录里留下一条 hook error 提示。注意 **不带合法 JSON 输出时，退出 1 不会拦截任何东西** —— 想强制拦截必须用 `exit 2`。

| stdout 内容 | 退出 0 | 退出 2 | 其他退出码 |
| :- | :- | :- | :- |
| 通过 schema 校验的 JSON 对象 | 成功，字段生效 | 阻塞，JSON 字段不能覆盖拦截 | 成功，忽略退出码，字段决定行为 |
| 无法解析或未通过校验的 JSON | 非阻塞错误 | 阻塞，原因取 stderr | 非阻塞错误 |
| 纯文本或空 | 成功 | 阻塞，原因取 stderr | 非阻塞错误，提示带 stderr 首行 |

一个用退出码拦截的完整脚本：

```bash
#!/bin/bash
# .claude/hooks/no-rm.sh：读取 stdin JSON，拦截 rm 开头的命令
input=$(cat)
command=$(jq -r '.tool_input.command' <<<"$input")

if [[ "$command" == rm* ]]; then
  echo "Blocked: rm commands are not allowed" >&2
  exit 2  # 阻塞错误：PreToolUse 会阻止这次工具调用
fi

exit 0  # 不做决策：交给正常权限流程
```

```text
退出码语义：
1. 0 = 成功，JSON 字段生效，动作默认继续
2. 2 = 阻塞，仅在支持拦截的事件上终止动作，stderr 作为反馈
3. 其他 = 非阻塞错误，动作继续，转录里出现 hook error
4. 想强制拦截必须用 2，不要指望 exit 1
5. 钩子超时被取消也算失败，需要严格把关就设 "onFailure": "block"
```

## JSON 输出与决策控制

退出码只能「放行 / 拦截」，JSON 输出能表达更细的决策。字段分三类：通用字段（`continue`、`stopReason`、`systemMessage`、`terminalSequence`）、顶层 `decision` 与 `reason`、以及需要 `hookEventName` 的嵌套对象 `hookSpecificOutput`。要打印 JSON 就必须让 stdout 只有一个 JSON 对象，多一行无关文本会让它退化为纯文本。

不同事件支持的决策方式不一样，写钩子前先查这张表：

| 事件 | 决策方式 | 关键字段 |
| :- | :- | :- |
| `UserPromptSubmit`、`PostToolUse`、`PostToolUseFailure`、`PostToolBatch`、`Stop`、`SubagentStop`、`ConfigChange`、`PreCompact` | 顶层 `decision` | `decision: "block"`、`reason` |
| `PreToolUse` | `hookSpecificOutput` | `permissionDecision`（allow/deny/ask/defer）、`permissionDecisionReason` |
| `PermissionRequest` | `hookSpecificOutput` | `decision.behavior`（allow/deny） |
| `SessionStart`、`SubagentStart`、`PostModelSwitch` | 只加上下文 | `hookSpecificOutput.additionalContext`，`SessionStart` 还接受 `initialUserMessage`、`watchPaths`、`sessionTitle`、`reloadSkills` |
| `Notification`、`SessionEnd`、`PostCompact`、`FileChanged` 等 | 无决策控制 | 只做副作用，如日志与清理 |

`PreToolUse` 还能通过 `hookSpecificOutput.updatedInput` 在工具执行前改写入参，`PostToolUse` 通过 `updatedToolOutput` 替换工具结果 —— 需要脱敏或转换数据时，出站改写打 `PreToolUse`，入站改写打 `PostToolUse`。

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Database writes are not allowed"
  }
}
```

```json
{
  "continue": false,
  "stopReason": "Build failed, fix errors before continuing"
}
```

```text
JSON 输出的边界：
1. stdout 必须是「一个 JSON 对象 + 空白」，否则按纯文本处理
2. continue:false 会让 Claude 停止后续处理，优先级高于事件自身的决策字段
3. additionalContext / systemMessage / initialUserMessage / 纯 stdout 单串上限 10000 字符，超限会落盘并把路径给模型
4. terminalSequence 只能发 OSC 0/1/2/9/99/777 与 BEL，用来发桌面通知，不要写 /dev/tty
```

## 自动格式化与校验

最常见的用法是「Claude 改完文件自动格式化」。做法是监听 `PostToolUse` 的 `Edit|Write`，把事件 JSON 里的 `file_path` 取出来喂给格式化器。这个配置只对内置的 Edit/Write 生效，对 Bash 里用 `sed -i` 之类改的文件不生效。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

如果是多语言仓库，用脚本按扩展名分派更省事：

```bash
#!/bin/bash
# .claude/hooks/format-changed.sh：按扩展名选择格式化器
input=$(cat)
file=$(echo "$input" | jq -r '.tool_input.file_path // empty')
[ -z "$file" ] && exit 0
[ -f "$file" ] || exit 0

case "$file" in
  *.ts|*.tsx|*.js|*.jsx|*.json|*.md)
    npx --no-install prettier --write "$file" >/dev/null 2>&1 ;;
  *.py)
    python3 -m black "$file" >/dev/null 2>&1 ;;
  *)
    exit 0 ;;
esac

exit 0
```

校验类逻辑用同一个事件，但要记住 `PostToolUse` 无法回滚已经发生的修改：如果只是想让 Claude 看到问题，退出 2 会把 stderr 作为反馈给它（即使工具已经执行完），适合「编译不过就让它继续修」的循环。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npx tsc --noEmit || { echo 'TypeScript 类型检查未通过，请先修复类型错误' >&2; exit 2; }",
            "timeout": 120
          }
        ]
      }
    ]
  }
}
```

```text
格式化和校验的三个要点：
1. 只对 Edit/Write 生效，Bash 改的文件不会触发；要覆盖所有写入用 FileChanged（但它不能拦截）
2. PostToolUse 已经执行过工具，退出 2 只能把 stderr 反馈给 Claude，不能撤销改动
3. 跑全量检查会阻塞每轮对话，用 "async": true 或把范围限定在被改的那个文件
```

## 拦截与权限控制

`PreToolUse` 在权限模式检查**之前**触发，并且在所有权限模式下都会触发，包括 `dontAsk`。这意味着返回 `permissionDecision: "deny"` 的钩子能拦住工具调用，即使用户处于 `bypassPermissions` 或加了 `--dangerously-skip-permissions`。反过来不成立：返回 `"allow"` 不能突破设置里的 deny 规则，也不能让需要交互的 MCP 工具或网络路径读取跳过提示 —— 钩子只能收紧限制，不能放宽。

下面这个脚本保护 `.env`、`package-lock.json` 与 `.git/`，被拦截时把原因回传给 Claude，让它换个思路：

```bash
#!/bin/bash
# .claude/hooks/protect-files.sh
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

# 归一化 Windows 反斜杠分隔符，保证下面的模式能匹配
FILE_PATH="${FILE_PATH//\\//}"

PROTECTED_PATTERNS=(".env" "package-lock.json" ".git/")

for pattern in "${PROTECTED_PATTERNS[@]}"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH matches protected pattern '$pattern'" >&2
    exit 2
  fi
done

exit 0
```

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh"
          }
        ]
      }
    ]
  }
}
```

再进一步，可以只放行检查通过的命令。下面的钩子把测试命令改写成「只显示失败项」，既省上下文又保留必要信息：

```bash
#!/bin/bash
# ~/.claude/hooks/filter-test-output.sh
input=$(cat)
cmd=$(echo "$input" | jq -r '.tool_input.command')

if [[ "$cmd" =~ ^(npm test|pytest|go test) ]]; then
  filtered_cmd="$cmd 2>&1 | grep -A 5 -E '(FAIL|ERROR|error:)' | head -100"
  echo "$input" | jq --arg filtered "$filtered_cmd" \
    '{hookSpecificOutput: {hookEventName: "PreToolUse", permissionDecision: "allow", updatedInput: (.tool_input + {command: $filtered})}}'
else
  echo "{}"
fi
```

```text
拦截与权限的关系：
1. PreToolUse 先于权限模式检查执行，deny 决策在 bypassPermissions 下同样生效
2. 钩子不能放宽权限：allow 决策不会覆盖设置里的 deny / ask 规则
3. 退出 2 的拦截优先于 allow 规则，可用来实现「默认全允许、少数命令拉黑」
4. PreToolUse 只在模型真正发起工具调用时触发，提示词里用 @ 引用的文件不会触发（用 Read deny 规则拦）
5. 多个 PreToolUse 同时返回 updatedInput 时，最后完成的生效且顺序不确定，别让多个钩子改同一个入参
```

## 调试与排错

排查钩子问题有三个入口：会话内运行 `/hooks` 打开钩子浏览器，核对当前加载了哪些钩子；用 `claude --debug-file ./claude-debug.txt` 把调试日志写到文件，里面能看到钩子的 stdout、stderr、被改写的工具入参；直接在终端手工回放一次事件，把构造的 JSON 通过管道喂给脚本。

```shell
# 手工回放一次 PreToolUse 事件，验证脚本行为
echo '{"hook_event_name":"PreToolUse","tool_name":"Bash","tool_input":{"command":"rm -rf /tmp/x"}}' \
  | .claude/hooks/no-rm.sh
echo "exit=$?"

# 打开调试日志后观察钩子输出与工具入参改写
claude --debug-file ./claude-debug.txt

# 查看当前会话加载的设置来源与钩子
claude doctor
```

常见故障与定位方式：

| 现象 | 常见原因 | 处理方式 |
| :- | :- | :- |
| 钩子完全没触发 | 路径写错、脚本不可执行、matcher 写成了非法正则 | 看转录里的 hook error 提示，`chmod +x`，matcher 加 `^` 与 `$` |
| JSON 决策不生效 | stdout 里有额外文本（比如 shell 启动脚本 echo 了内容），或字段层级放错 | 清掉 profile 输出，`hookSpecificOutput` 里必须带 `hookEventName` |
| 每轮对话都很慢 | 钩子在等超时，或跑了全量检查 | 检查 `timeout`，把重活改成 `async: true` |
| 拦截没生效 | 用了 `exit 1` 而不是 `exit 2` | 明确 `exit 2`，或设 `onFailure: "block"` |
| 会话结束后钩子不见了 | 用了 `once: true`（只在技能 frontmatter 中生效，且成功后移除） | 需要常驻就设在 settings 文件里 |

```text
排错顺序：
1. /hooks 看钩子有没有被加载，路径与事件对不对
2. 手工用 echo JSON | script 回放，确认脚本本身的退出码与输出
3. 开 --debug-file 看 stdout 是否被解析为 JSON、入参是否被改写
4. 检查 timeout 与 async，确认不是被超时取消
5. 企业环境下检查 allowManagedHooksOnly 是否屏蔽了用户级钩子
```

## 应用场景实战

### 场景一：单体仓库的「提交前守卫 + 改后格式化」钩子链

一个 JS/TS + Python 混合仓库，团队约定：禁止直接改 `.env`、禁止 `git push`（必须走 PR）、改完文件自动格式化、提交信息统一走 Conventional Commits。把这些固化到项目级设置文件里，克隆即可生效。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh",
            "statusMessage": "检查受保护文件"
          }
        ]
      },
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/guard-bash.sh",
            "statusMessage": "检查 Bash 命令"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/format-changed.sh",
            "timeout": 60
          }
        ]
      }
    ]
  }
}
```

```bash
#!/bin/bash
# .claude/hooks/guard-bash.sh：拦截直推与破坏性命令
input=$(cat)
cmd=$(echo "$input" | jq -r '.tool_input.command // empty')

# 直推主干必须走 PR
if [[ "$cmd" =~ ^git[[:space:]]+push ]]; then
  echo "Blocked: 请先开分支并提 PR，禁止直接 push" >&2
  exit 2
fi

# 破坏性命令一律拦截
case "$cmd" in
  *"rm -rf /"*|*"git reset --hard"*|*"git clean -fdx"*)
    echo "Blocked: 破坏性命令需要人工执行" >&2
    exit 2 ;;
esac

# 提交信息格式校验，不合规就反馈给 Claude 让它重写
if [[ "$cmd" =~ ^git[[:space:]]+commit ]]; then
  if echo "$cmd" | grep -qE '(-m|-F)'; then
    if ! echo "$cmd" | grep -qE '(feat|fix|docs|refactor|test|chore)(\(.+\))?:'; then
      echo "提交信息必须符合 Conventional Commits，例如 feat(api): 增加订单查询" >&2
      exit 2
    fi
  fi
fi

exit 0
```

```shell
# 验证：先给脚本执行权限，再手工回放一次事件
chmod +x .claude/hooks/guard-bash.sh .claude/hooks/protect-files.sh .claude/hooks/format-changed.sh

echo '{"hook_event_name":"PreToolUse","tool_name":"Bash","tool_input":{"command":"git push origin main"}}' \
  | .claude/hooks/guard-bash.sh
echo "退出码=$?"   # 期望 2，且 stderr 打印拦截原因
```

### 场景二：会话启动注入上下文 + 压缩后重注入 + 完成通知

长会话里 context 被压缩后，关键的项目约定容易丢；同时在没人盯屏幕时希望 Claude 停下来的瞬间收到提醒。用 `SessionStart`、`PostCompact` 与 `Stop` 三个事件组合解决。

```json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/session-context.sh"
          }
        ]
      }
    ],
    "PostCompact": [
      {
        "matcher": "auto",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/session-context.sh"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "notify-send 'Claude Code' '任务已完成，等待你的确认'",
            "async": true
          }
        ]
      }
    ]
  }
}
```

```bash
#!/bin/bash
# .claude/hooks/session-context.sh：把关键约定作为 additionalContext 注入
# SessionStart 会把它作为可读上下文给模型；PostCompact 用于压缩后重新补齐
cat >/dev/null   # 事件 JSON 只在需要时读取，这里不依赖它

CONTEXT=$(cat <<'EOF'
项目关键约定（自动注入）：
1. 包管理统一用 pnpm，禁止 npm install
2. 所有对外接口改动必须同步更新 docs/api.md
3. 测试命令：pnpm test；类型检查：pnpm typecheck
4. 数据库迁移只允许新增，不允许修改已合入的迁移文件
EOF
)

jq -n --arg ctx "$CONTEXT" \
  '{hookSpecificOutput: {hookEventName: "SessionStart", additionalContext: $ctx}}'
```

```text
场景要点：
1. SessionStart 的 additionalContext 会作为上下文给模型，适合放「每次都必须知道」的约定
2. PostCompact 用于压缩后重新补齐，matcher 取 auto 只在自动压缩时触发
3. Stop 在每轮响应结束时都会触发，不等于任务完成；要发通知就设成 async 避免拖慢
4. 通知也可以走 terminalSequence 的 OSC 序列，不必依赖外部命令
5. PostCompact 在官方决策控制表里属于「无决策控制」的事件，只用它做上下文注入这类副作用
```

## 最佳实践与踩坑记录

### 最佳实践

1. 钩子脚本放进 `.claude/hooks/` 并提交到版本库，用 `chmod +x` 保证克隆即可用，别把逻辑塞进 settings.json 的长字符串里
2. 强制拦截一律用 `exit 2`；只有「想让流程继续但记录问题」时才用其他退出码
3. 解析输入用 `jq` 取字段，别用 `grep` 正则抠 JSON，字段名与嵌套层级会随版本变化
4. 引用仓库内脚本统一用 `${CLAUDE_PROJECT_DIR}`，避免钩子在错误的工作目录里找不到文件
5. 耗时操作加 `"async": true`，会阻塞对话的检查用 `timeout` 收紧到 30 秒以内
6. 团队共享的钩子放 `.claude/settings.json` 提交，个人临时钩子放 `.claude/settings.local.json`（Claude Code 写入时会自动把它排除出版本控制）
7. 用 `if` 字段把触发面收窄到具体命令或文件类型，减少每轮对话的额外开销

### 踩坑记录

```text
坑 1：写了钩子但拦截不生效
结论：转录里出现 hook error，命令照跑，安全隐患被忽略。
原因：脚本用 exit 1 表示失败，而没有合法 JSON 输出时 exit 1 属于非阻塞错误，动作照常执行。
解法：强制拦截改用 exit 2，或在处理器上设 "onFailure": "block"。

坑 2：钩子打印了 JSON，决策却不生效
结论：配置看起来完全正确，但 deny / allow 没作用，日志提示无法解析。
原因：shell 启动脚本（.bashrc / .zshrc）在钩子执行时 echo 了文本，stdout 不再是「纯 JSON 对象」，退化成纯文本；或者字段层级写错，把 hookSpecificOutput 里的字段提到了顶层。
解法：清掉 profile 的输出，保证 stdout 只有一个 JSON 对象，PreToolUse 的决策字段放在 hookSpecificOutput 下并带 hookEventName。

坑 3：会话在临时目录或 worktree，钩子脚本找不到
结论：钩子静默失败，出现 Failed with non-blocking status code 提示。
原因：钩子默认在当前工作目录执行，而该目录可能已被删除或换成 worktree，相对路径解析不到脚本。
解法：脚本路径用 ${CLAUDE_PROJECT_DIR} 拼绝对路径，配置后手工回放一次事件验证。

坑 4：多个钩子一起改工具入参，行为不确定
结论：同一个 Bash 命令有时被改写成 A，有时被改写成 B，排查困难。
原因：所有匹配的处理器并行执行，多个 PreToolUse 返回 updatedInput 时最后完成的生效，顺序不确定。
解法：同一个工具的入参改写只保留一个钩子；需要多步处理就串到一个脚本里顺序执行。

坑 5：以为 PostToolUse 能撤销错误的改动
结论：Claude 已经写坏了文件，钩子报错却拦不住。
原因：PostToolUse 在工具成功执行之后触发，只能反馈信息，不能回滚。
解法：要阻止写入必须放在 PreToolUse；PostToolUse 只做格式化、审计、结果改写这类事后动作。

坑 6：企业环境里用户级钩子全部失效
结论：同事本机配好的钩子在他自己的会话里有效，受管会话里一个都不跑。
原因：托管设置里的 allowManagedHooksOnly 会屏蔽用户级、项目级、本地级与插件钩子（受托管设置强制启用的插件除外）。
解法：把需要全员生效的钩子交给管理员放进托管策略，或确认该设置的例外范围后再排障。
```
