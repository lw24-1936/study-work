## 概述

单机用好 Claude Code 靠个人习惯，团队用好它靠三件事：配置可分发、自动化可复现、成本可度量。配置分发解决「每个人环境不一致」的问题，把权限、钩子、插件写成仓库里的文件随克隆生效；CI 集成把 Claude 放进已有流水线，用 GitHub Actions 响应 `@claude` 或按计划跑任务；无头模式（`-p`）让脚本和流水线能调用它并拿到结构化输出。最后用 `/usage`、控制台与 OpenTelemetry 把花费管起来。

```text
团队落地的三条主线：
1. 分发 —— .claude/settings.json 提交仓库（团队共享），.claude/settings.local.json 留个人，托管设置定底线
2. 自动化 —— GitHub Actions 用 anthropics/claude-code-action@v1，本地脚本用 claude -p 无头模式
3. 治理 —— 用量看 /usage 与组织后台，成本靠模型选择、上下文管理与把重活下放到钩子与技能
```

## 团队配置分发与作用域

Claude Code 从四类位置读取设置，每类对应不同的人群与用途，理解这张表是分发配置的前提：

| 作用域 | 文件 | 影响谁 | 适合放什么 |
| :- | :- | :- | :- |
| 用户 | `~/.claude/settings.json` | 你本机所有项目 | 个人偏好：主题、编辑器模式、默认模型、个人权限规则 |
| 项目共享 | `.claude/settings.json` | 包含该目录的仓库的所有人 | 团队权限、钩子、插件、项目环境变量，提交进版本库 |
| 项目本地 | `.claude/settings.local.json` | 仅你在该项目 | 个人覆盖与试验；Claude Code 写入时会自动排除出版本控制 |
| 托管 | `managed-settings.json` 及 MDM / 服务端托管 | 组织部署到的所有人 | 安全策略与合规要求 |

同名的键出现在多处时按优先级取最高的一处，从高到低是：托管设置、命令行（`--settings`、该键专用 flag、环境变量）、项目本地、项目共享、用户。列表类字段（`permissions.allow` 等）是**合并**而不是覆盖，各作用域各加各的，除非托管设置用 `allowManagedPermissionRulesOnly` 把权限规则限定为只认托管来源。

```shell
# 查看当前会话实际加载了哪些设置来源
claude    # 会话内运行 /status，看 Setting sources 行

# 查看被拒绝的条目与解析后的设置
claude doctor

# 只影响一次会话：内联 JSON 覆盖
claude --settings '{"model": "claude-sonnet-5"}'

# 只加载指定来源（CI 里常用，彻底排除仓库设置）
claude --setting-sources user,project
```

```text
分发要点：
1. 团队想统一的（权限、钩子、插件市场）放 .claude/settings.json 提交
2. 个人想私有的（本地路径、个人 token）放 .claude/settings.local.json
3. 设置文件是严格 JSON，注释与尾随逗号会让 Claude Code 报 Settings Error 并跳过
4. 会话运行中改动设置文件大多会热加载，但少数键只在启动时读取
5. 云会话只读仓库里的 .claude/settings.json，用户级与本地级设置不会带到云上
```

## 可提交的团队设置文件

一个可用的团队文件通常包含四类内容：权限规则、钩子、插件市场与技能来源、沙箱边界。下面这份是官方示例的形态，直接放在仓库根目录的 `.claude/settings.json` 并提交（注意：设置文件不接受注释，下面第二份只是带注释的讲解版）。

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh"
          }
        ]
      }
    ]
  },
  "extraKnownMarketplaces": {
    "acme-tools": {
      "source": {
        "source": "github",
        "repo": "acme-corp/claude-plugins"
      }
    }
  },
  "enabledPlugins": {
    "code-formatter@acme-tools": true
  },
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "allowWrite": ["/tmp/build"]
    },
    "network": {
      "allowedDomains": ["registry.npmjs.org", "*.example.com"]
    }
  },
  "plansDirectory": "./plans"
}
```

```jsonc
{
  "permissions": {
    // 免提示跑构建脚本
    "allow": ["Bash(npm run *)"],
    // 推送前确认
    "ask": ["Bash(git push *)"],
    // 文件工具与读取类命令都拿不到密钥文件
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  },
  // 仓库里的钩子脚本，克隆即可用（记得 chmod +x）
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh" }]
      }
    ]
  },
  // 注册团队插件市场，并启用其中一个插件
  "extraKnownMarketplaces": {
    "acme-tools": { "source": { "source": "github", "repo": "acme-corp/claude-plugins" } }
  },
  "enabledPlugins": { "code-formatter@acme-tools": true },
  // 沙箱：只允许写构建目录，只允许访问 npm 源与内部域名
  "sandbox": {
    "enabled": true,
    "filesystem": { "allowWrite": ["/tmp/build"] },
    "network": { "allowedDomains": ["registry.npmjs.org", "*.example.com"] }
  },
  // 计划文件留在仓库内
  "plansDirectory": "./plans"
}
```

```text
团队文件要注意的四点：
1. allow 规则与 extraKnownMarketplaces 条目要等每个人信任该目录后才生效；deny / ask 规则任何时候都生效
2. 规则按「写法」匹配：Bash(git push *) 不会匹配 git -C . push，Read(./.env) 也拦不住 grep -r 扫目录
3. 仓库设置文件里的 OpenTelemetry 导出变量会被忽略，遥测配置放托管设置或个人设置
4. 云会话从仓库克隆启动，所以这份文件在云端同样生效
```

## 托管设置与企业策略

组织级策略通过 `managed-settings.json`、MDM 或服务端托管设置下发，优先级最高，用户与项目设置无法覆盖。它适合放安全底线与合规要求：强制登录方式与组织、模型白名单、权限规则白名单、MCP 服务器白名单、沙箱强制开启、以及计费口径。

```json
{
  "forceLoginMethod": "claudeai",
  "permissions": {
    "deny": [],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "allowManagedMcpServersOnly": true,
  "allowedMcpServers": [
    { "serverName": "github", "serverUrl": "https://api.githubcopilot.com/mcp/" }
  ],
  "availableModels": ["claude-sonnet-5", "claude-opus-5-5"],
  "enforceAvailableModels": true,
  "modelPricing": {
    "multiplier": 0.9
  },
  "sandbox": {
    "enabled": true,
    "network": {
      "allowedDomains": ["registry.npmjs.org", "*.example.com"]
    }
  }
}
```

```text
托管策略的关键行为：
1. 托管设置优先级最高，--settings 与命令行 flag 都不能覆盖；被托管的 model 只是默认起点，锁死模型靠 availableModels 与 deniedModels
2. allowManagedHooksOnly 可以只允许托管钩子，屏蔽用户级、项目级、本地级与插件钩子
3. allowManagedPermissionRulesOnly / allowManagedMcpServersOnly 把权限与 MCP 白名单收敛到托管来源
4. modelPricing 只放在托管设置里生效，用来把 /usage 与 OpenTelemetry 的成本换算成合同费率
5. 部分「收紧类」键在任何作用域都生效（如 disableClaudeAiConnectors 为 true），设计策略时要一并考虑
```

## GitHub Actions 集成

官方提供 `anthropics/claude-code-action`：在 PR 或 issue 评论里 @claude 即可让它分析代码、改代码、推提交；也可以给 `prompt` 输入让它按任意 GitHub 事件（含 cron 计划）自动执行。两种配置方式：在 Claude Code 里跑 `/install-github-app` 走快速安装（自动装 GitHub App、写入 `ANTHROPIC_API_KEY` 或 `CLAUDE_CODE_OAUTH_TOKEN` secret、准备 workflow PR），或手工安装 App、加 secret、把 workflow 文件复制进仓库。两种方式都需要仓库管理员权限。

```yaml
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
```

这段 workflow 里非模板的部分都有明确作用：`id-token: write` 是 Action 默认 GitHub App 鉴权所必需，`actions: read` 让 Claude 能读 PR 上的 CI 结果，`actions/checkout` 给它一份可操作的代码副本，`if` 避免无关评论也启动 runner。

常用的 `with:` 输入：

| 参数 | 说明 | 是否必需 |
| :- | :- | :- |
| `prompt` | 给 Claude 的指令，可为纯文本或技能调用；省略时按触发短语响应 | 否 |
| `claude_args` | 透传给 Claude Code 的 CLI 参数 | 否 |
| `anthropic_api_key` | Claude API 密钥 | 用 API 计费时必需（也可用 `claude_code_oauth_token`） |
| `claude_code_oauth_token` | 订阅制登录令牌，用 `claude setup-token` 生成 | 否 |
| `github_token` | 执行 GitHub 操作的令牌，省略时用 Claude GitHub App 身份 | 否 |
| `plugin_marketplaces` / `plugins` | 换行分隔的插件市场地址与要安装的插件名 | 否 |
| `settings` | Claude Code 设置，JSON 字符串或设置文件路径 | 否 |
| `trigger_phrase` | 触发短语，默认 `@claude` | 否 |
| `use_bedrock` / `use_vertex` / `use_foundry` | 改用云厂商平台鉴权 | 否 |

`claude_args` 接受任意 Claude Code CLI 参数，常见的有 `--max-turns`、`--model`、`--mcp-config`、`--allowedTools`（别名 `--allowed-tools`）、`--debug`。按计划运行的自动化任务里，如果不走技能而是纯文本 prompt，需要显式用 `--allowedTools` 或 `settings` 里的 `permissions.allow` 授予工具权限。

```yaml
name: Daily Report
on:
  schedule:
    - cron: "0 9 * * *"
jobs:
  report:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      issues: read
      id-token: write
    steps:
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: "汇总昨天的提交与未关闭的 issue"
          claude_args: |
            --model claude-sonnet-5
            --allowedTools "mcp__github__list_commits,mcp__github__list_issues"
```

```text
Actions 集成要点：
1. 密钥只通过 GitHub Secrets 注入，绝不写进仓库文件；按需最小化 workflow permissions
2. 计划任务只在默认分支上跑；公开仓库连续 60 天无活动后 GitHub 会停掉 schedule
3. 公开仓库里来自 fork 的 PR 拿不到 secrets，所以评审类工作流只对同仓库分支生效
4. 代码规范写在仓库根目录的 CLAUDE.md 里，Claude 开 PR 与回答问题时都遵循它
5. 想要每 PR 自动评审又不想维护 workflow，可用内置的 Code Review 能力替代
```

## 无头模式的常用参数

加 `-p`（或 `--print`）让 Claude Code 非交互运行并输出结果后退出，这是脚本与 CI 的基础。不是所有参数都能和 `-p` 组合——例如 `--bg` 会被拒绝，`--cloud` 带任务描述也会被拒绝。运行成功退出码为 0，失败为非 0；参数错误在运行开始前打到 stderr，运行中出错则以 result 形式打到 stdout。

| 参数 | 用途 |
| :- | :- |
| `-p, --print` | 非交互运行，打印结果后退出 |
| `--bare` | 最小启动：跳过钩子、技能、自定义命令、子代理、插件、MCP 服务器、自动记忆与 CLAUDE.md 的自动发现，启动更快 |
| `--output-format` | `text`（默认）、`json`、`stream-json` |
| `--allowedTools` | 免提示执行指定工具，支持规则模式，如 `"Bash(git log *)"` |
| `--disallowedTools` | 拒绝规则；裸工具名会把它从上下文里移除，如 `"Edit"`、`"mcp__*"` |
| `--tools` | 限制可用的内置工具集，`""` 表示全部禁用 |
| `--permission-mode` | 起始权限模式：`default` / `acceptEdits` / `plan` / `auto` / `dontAsk` / `bypassPermissions` |
| `--permission-prompts none` | 无人应答时把「本该提示」的请求直接拒绝，并告知模型不要重试 |
| `--max-turns` | 限制代理轮数，超限报错退出 |
| `--max-budget-usd` | 估算花费达到阈值即停止（客户端估算，不是账单） |
| `--setting-sources` | 只加载指定来源的设置，如 `user,project` |
| `--mcp-config` / `--strict-mcp-config` | 指定 MCP 配置 / 只认指定的 MCP 配置 |
| `--continue` / `--resume` | 继续最近会话 / 恢复指定会话 |
| `--add-dir` | 追加可读写目录（其技能会加载，但 `.claude/commands`、`.claude/agents` 不加载） |

```shell
# 1. 最简单的一次性提问
claude -p "auth 模块负责什么？"

# 2. 管道喂数据
cat logs/app.log | claude -p "找出异常增长的原因"

# 3. CI 里推荐用 bare 模式：跳过自动发现，机器之间结果一致
export ANTHROPIC_API_KEY="sk-xxx"   # bare 模式不读订阅登录与钥匙串
claude --bare -p "总结 README.md" --allowedTools "Read"

# 4. 只读探查 + 自动改文件的两种基线
claude -p "跑测试并修失败用例" --allowedTools "Bash,Read,Edit"
claude -p "应用 lint 修复" --permission-mode acceptEdits

# 5. 结构化输出与轮数/预算上限
claude -p "审查当前改动" --output-format json --max-turns 8 --max-budget-usd 2

# 6. 流式输出，便于边跑边渲染
claude -p "分析这个仓库的结构" --output-format stream-json --verbose

# 7. 继续上一次会话
claude -c -p "把刚才列的问题按优先级排序"
```

```text
无头模式要点：
1. --bare 会跳过钩子、MCP、CLAUDE.md 的自动发现，CI 里行为可预测；需要的东西用参数显式传入
2. -p 会话不弹信任对话框，也不弹项目级 MCP 服务器批准，仓库里的 .mcp.json 会直接加载
3. 退出码是脚本判定的基础：0 成功、非 0 失败；运行中的失败以 result 输出打到 stdout
4. 长任务注意后台等待上限：主对话启动的后台命令仍在跑时，默认空闲等待 10 分钟后停止，可用 CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS 调整
5. 需要并发与隔离时给每次运行独立的 --session-id，用 --fork-session 从已有会话分叉
```

## CI 中的结构化输出与失败判定

`--output-format json` 返回一次性结果对象，`stream-json` 返回逐行事件流，两者都能让流水线用代码而不是正则做判断。stream-json 的 `system/init` 事件里有 `mcp_server_errors` 字段（较新版本），可以据此判定「插件或 MCP 服务器有没有加载成功」；权限被拒的调用会以 `permission_denied` 系统消息出现，最终结果消息的 `permission_denials` 里会列出它们。

```bash
#!/usr/bin/env bash
# ci/ai-review.sh：CI 中跑一次评审，mcp/插件加载失败即视为流水线失败
set -euo pipefail

claude --bare \
  -p "审查这次改动，列出风险点与缺失的测试" \
  --output-format stream-json \
  --allowedTools "Read,Grep" \
  --permission-prompts none \
  --max-turns 10 \
  --setting-sources "" \
  --strict-mcp-config --mcp-config ./ci/mcp.json \
  > /tmp/stream.ndjson

# 解析事件流：检查初始化事件里的服务器错误，以及权限被拒次数
python3 - <<'PY'
import json, sys

init_errors, denials, result = [], [], None
with open("/tmp/stream.ndjson", encoding="utf-8") as fh:
    for line in fh:
        line = line.strip()
        if not line:
            continue
        evt = json.loads(line)
        if evt.get("type") == "system" and evt.get("subtype") == "init":
            init_errors = evt.get("mcp_server_errors") or []
        elif evt.get("type") == "system" and evt.get("subtype") == "permission_denied":
            denials.append(evt)
        elif evt.get("type") == "result":
            result = evt

if init_errors:
    sys.exit(f"MCP 服务器加载失败: {init_errors}")
print("权限被拒次数:", len(denials))
print("结果是否报错:", (result or {}).get("is_error"))
PY
```

```shell
# json 格式：一次拿到结果文本与错误标记
claude -p "生成变更说明" --output-format json > /tmp/out.json
jq -r '.result' /tmp/out.json
jq -e '.is_error == false' /tmp/out.json >/dev/null || { echo "Claude 运行失败"; exit 1; }
```

```text
CI 判定要点：
1. 用 json / stream-json 输出做门禁，别解析人类可读文本
2. 事件名与字段（system/init、mcp_server_errors、permission_denials）随版本演进，升级前先在测试流水线上验证
3. --permission-prompts none 让无人应答的请求确定性拒绝，避免流水线卡在等待上
4. 与 --setting-sources "" 一起用，可以把仓库设置与个人设置完全排除，保证可复现
5. 需要读 CI 结果让 Claude 分析时，用 GitHub Actions 的 actions: read 权限配合官方 MCP 服务器
```

## 成本与配额管理

Claude Code 按 token 计费（订阅制则由套餐额度覆盖）。官方给出的企业部署经验值是：平均每位开发者每活跃日约 13 美元、每月 150 到 250 美元，90% 的用户每活跃日低于 30 美元。先小范围试点，用下面这些工具建立基线再铺开。会话内 `/usage` 展示当前会话的 token 用量与按标价估算的费用（管理员可在托管设置里用 `modelPricing` 配成合同费率，此时 `Total cost` 行会标注按组织配置费率计算）；`/clear` 开始新会话时统计会重置。

组织层的花费取决于接入方式：Claude for Teams / Enterprise 按席位额度计量（滚动 5 小时窗口与周窗口，并与 chat 共享），管理入口在 claude.ai 管理后台；Claude Console 按 token 计费，额度上限在工作区设置里；云厂商接入则看云账单，可用 OpenTelemetry 或 LLM 网关做按用户上报。OpenTelemetry 导出是唯一能把按用户 token 与成本指标近实时推到你自己的可观测栈的方式。

```json
{
  "modelPricing": {
    "multiplier": 0.9,
    "overrides": {
      "claude-sonnet-5": {
        "inputPerMillion": 2.7,
        "outputPerMillion": 13.5
      }
    }
  }
}
```

```shell
# 会话内查看用量与估算花费
# /usage

# 给单次 CI 运行设上限，避免失控
claude -p "生成周报" --output-format json --max-budget-usd 1.5 --max-turns 6

# 降低推理开销：用 /effort 调低难度档位，或在 /config 里关闭扩展思考
```

```text
降本清单（按收益从高到低）：
1. 上下文管理 —— 及时 /clear 与压缩，别让长会话拖着巨量历史；CLAUDE.md 控制在 200 行以内，把长流程说明移到按需加载的技能里
2. 模型选择 —— 简单任务用较小模型，规划与复杂重构才上大模型
3. 把重活下放 —— 用钩子预处理数据（比如只把日志里的 ERROR 行给模型），用技能提供领域知识，省掉探索性读取
4. 减少 MCP 开销 —— 每个服务器都会占用上下文，删掉不用的
5. 调整扩展思考 —— 用 /effort 或 /model 降档，自适应推理模型上改预算无效，非自适应模型可用 MAX_THINKING_TOKENS 限制
6. 委派冗长操作 —— 把大批量读取交给子代理，只把结论带回主会话
7. 提示写得具体 —— 减少来回澄清的轮数，是最直接的省钱手段
```

## 应用场景实战

### 场景一：PR 自动评审工作流，把结论贴回 PR

目标：每个新开的 PR 都自动跑一次评审，发现问题就以行内评论回帖，没问题就留一条总结评论；同时把团队规范作为评审依据。

```yaml
name: Code Review
on:
  pull_request:
    types: [opened, synchronize, ready_for_review, reopened]
jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            按仓库根目录 CLAUDE.md 里的规范评审这次改动。
            重点检查：接口兼容性、缺失的测试、错误处理、日志中的敏感信息。
            发现问题就用行内评论指出，并给出可执行的修改建议。
          claude_args: |
            --model claude-sonnet-5
            --max-turns 12
            --allowedTools "mcp__github_inline_comment__create_inline_comment,Read,Grep,Bash(git diff *)"
```

```text
场景要点：
1. 触发类型覆盖 opened / synchronize / ready_for_review / reopened，草稿与已关闭的 PR 会被自动跳过
2. 回帖到 PR 需要授予发帖用的 MCP 工具，用 --allowedTools 显式列出
3. 评审标准写进 CLAUDE.md，避免把长提示词塞在 workflow 里难以维护
4. 公开仓库里 fork PR 拿不到 secrets，评审只在同仓库分支的 PR 上生效
5. 每个 PR 都会消耗 AI 与 Actions 分钟数，可在组织层设置并发与额度上限
```

### 场景二：夜间定时任务 + 无头门禁，产出可归档报告

目标：每天凌晨汇总仓库活动与测试健康度，产出结构化 JSON 报告并归档；如果 Claude 判定存在阻塞级问题，让流水线失败提醒值班同学。

```yaml
name: Nightly AI Report
on:
  schedule:
    - cron: "17 18 * * *"   # UTC 18:17，即北京时间 02:17
  workflow_dispatch:
jobs:
  report:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            统计昨天合并的 PR、未关闭的 P0/P1 issue、以及最近一次 CI 失败的原因。
            用 JSON 输出：{"merged_prs": n, "open_critical": n, "blockers": ["..."]}
          claude_args: |
            --model claude-sonnet-5
            --max-turns 10
            --allowedTools "mcp__github__list_commits,mcp__github__list_issues,mcp__github__get_workflow_run"
```

本地等价的无头脚本（不依赖 Actions，适合内部定时任务平台）：

```bash
#!/usr/bin/env bash
# ops/nightly-report.sh：本地/内部调度器上的无头报告任务
set -euo pipefail

claude --bare \
  -p $'统计昨天合并的 PR 与未关闭的高优 issue，输出 JSON：{"merged_prs": n, "open_critical": n, "blockers": []}' \
  --output-format json \
  --allowedTools "Read,Grep" \
  --permission-prompts none \
  --max-turns 10 \
  --max-budget-usd 1.0 \
  > /tmp/nightly.json

python3 - <<'PY'
import json, sys
data = json.load(open("/tmp/nightly.json"))
if data.get("is_error"):
    sys.exit("夜间任务执行失败")
text = data.get("result", "")
print(text[:800])
# 有阻塞项时以非 0 退出，交给调度器告警
try:
    payload = json.loads(text[text.index("{"): text.rindex("}") + 1])
except ValueError:
    payload = {}
if payload.get("blockers"):
    sys.exit(f"存在阻塞项: {payload['blockers']}")
PY
```

```text
场景要点：
1. 计划任务只在默认分支生效，且公开仓库 60 天无活动会被 GitHub 停掉 schedule；把关键任务同时挂 workflow_dispatch 便于手工补跑
2. --max-budget-usd 给任务设花费上限，--max-turns 防跑飞
3. 结构化 prompt 加 JSON 解析，让报告能被后续系统消费，而不是只给人看
4. 本地调度版本用 --bare + --setting-sources "" 保证机器之间行为一致
```

## 最佳实践与踩坑记录

### 最佳实践

1. 团队规范写进仓库根目录的 CLAUDE.md（建议 200 行以内），长流程说明移到技能里按需加载
2. 团队共享配置放 `.claude/settings.json` 提交评审，个人例外放 `.claude/settings.local.json`
3. CI 用 `--bare` 加显式参数，避免依赖某台机器上的钩子、插件与 MCP 配置
4. 需要确定性拒绝的无人值守场景，用 `--permission-prompts none` 配合 `--allowedTools` 白名单
5. `--max-turns` 与 `--max-budget-usd` 是流水线的保险丝，所有自动化任务都该设
6. 密钥只用 GitHub Secrets 与 CI 变量注入，工作区里不落明文；数据库类凭据用只读账号
7. 用 OpenTelemetry 或组织后台建立用量基线，先小范围试点再全组推广
8. 升级 Claude Code 或 Action 版本前，先在测试流水线验证事件字段与参数，尤其是结构化输出的字段名

### 踩坑记录

```text
坑 1：提交了 .claude/settings.json，同事克隆后允许规则不生效
结论：deny / ask 规则正常工作，allow 规则与插件市场却没有生效。
原因：仓库里的 allow 规则与 extraKnownMarketplaces 需要每个人先信任该目录本身，只信任父目录不算；deny / ask 规则则始终生效。
解法：首次打开仓库时接受信任提示（提示里会列出将要激活的规则、额外目录与钩子），或在 CI 里显式用 --settings / --permission-mode 传入权限。

坑 2：CI 里 Claude 一直空转直到超时
结论：流水线时间被耗尽，任务没有产出。
原因：无人应答的环境里权限提示无法被批准，或某个 MCP 服务器连不上让首轮一直等；也可能是主对话启动的后台命令让运行停在等待上。
解法：用 --permission-prompts none 让无人应答的请求确定性拒绝，用 --allowedTools 给足必要权限，用 stream-json 的 mcp_server_errors 提前发现服务器加载失败，必要时调整 CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS。

坑 3：Actions 工作流在 fork 的 PR 上什么都不做
结论：外部贡献者的 PR 拿不到任何评审结果。
原因：公开仓库出于安全考虑不给来自 fork 的 workflow 运行注入 secrets，缺少密钥自然无法调用。
解法：评审类工作流只对同仓库分支生效；需要覆盖外部 PR 就改用不依赖仓库 secrets 的方案，或先由维护者在同仓库分支上创建等价 PR。

坑 4：夜间定时任务某天开始不再触发
结论：报告断更，没人发现异常。
原因：GitHub 只从默认分支运行计划工作流，且公开仓库连续 60 天无活动后会自动停用 schedule；也可能默认分支改名导致 cron 不再匹配。
解法：为关键任务同时保留 workflow_dispatch 便于手工补跑，并在外部监控里对「报告缺失」告警。

坑 5：CI 与本地行为不一致，本地能过流水线失败
结论：同一提示词两边结果不同，排查困难。
原因：-p 会话不弹信任对话框、也不弹项目级 MCP 服务器批准，仓库与个人环境里的钩子、插件、MCP 服务器都会影响行为；本地还可能残留旧的 settings.local.json。
解法：CI 固定使用 --bare、--setting-sources ""、--strict-mcp-config 与显式 --mcp-config，把所有输入写在流水线里。

坑 6：账单远超预期，但说不清花在哪
结论：月度费用明显高于试点期，无法定位到人。
原因：缺少按用户上报，多数人只在会话里看 /usage；组织层没设额度与费率换算，也没有并发控制。
解法：启用 OpenTelemetry 导出或组织后台的按用户报表建立基线，在托管设置里配 modelPricing 让报表与合同费率一致，并给工作区或席位设置花费上限与并发限制。
```
