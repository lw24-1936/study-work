## 概述

Hermes 的「记忆」不是向量数据库，而是两个容量很小的纯文本文件：`MEMORY.md`（智能体的环境笔记）与 `USER.md`（用户画像）。它们在会话开始时被整体注入系统提示词，所以能力边界只有一条：必须短。超出容量的写入不会被静默丢弃，而是直接报错，迫使智能体先合并、再写入。跨会话「回忆某次对话的细节」由另一个机制承担——`session_search` 对 SQLite 全量会话做 FTS5 全文检索，不占系统提示词预算。

```text
本节要点：
1. 两种介质 —— MEMORY.md（环境/约定/踩坑，2200 字符）+ USER.md（偏好/身份，1375 字符），都在 ~/.hermes/memories/
2. 注入方式 —— 会话启动时冻结快照写入系统提示词；会话中间改盘不改变本次提示词，下个会话才生效
3. 写入方式 —— memory 工具三个动作 add / replace / remove，target 选 memory 或 user
4. 容量是硬限制 —— 不自动压缩，超限返回错误并附当前条目，要求本轮内合并后重试
5. 检索是另一条路 —— session_search 走 state.db 的 FTS5，无 LLM 调用、不占提示词，覆盖全部历史会话
6. 一个 Hermes home 只允许一个写入方 —— 多进程共享同一 home 会互相污染记忆
```

## 两层记忆与文件布局

Hermes 把「智能体自己的笔记」与「关于用户的画像」拆成两个独立存储，原因很直接：两者的更新频率、失效条件和审查要求完全不同。环境事实（服务器 IP、端口、包管理器怪癖）属于前者；用户偏好（语言、审美、工作节奏）属于后者。把两者混在一个文件里，会让容量和审查边界同时失控。

文件位置与容量（本机 `config.yaml` 实测值）：

```text
memory:
  memory_enabled: true        # MEMORY.md 开关
  user_profile_enabled: true  # USER.md 开关
  memory_char_limit: 2200     # ~800 tokens
  user_char_limit: 1375       # ~500 tokens
  provider: ''                # 空 = 只用内置；填名字 = 启用外部记忆提供方
```

本机两个文件的真实状态（用 `wc -m` 与 `grep -c` 统计，不是估算）：

```bash
$ wc -m /root/.hermes/memories/MEMORY.md /root/.hermes/memories/USER.md
  2131 /root/.hermes/memories/MEMORY.md
  1375 /root/.hermes/memories/USER.md
  3506 总计

$ grep -c '§' /root/.hermes/memories/MEMORY.md /root/.hermes/memories/USER.md
/root/.hermes/memories/MEMORY.md:15
/root/.hermes/memories/USER.md:8
```

```text
$ ls -l /root/.hermes/memories/
-rw------- 1 root root 3294 10月 13 22:42 MEMORY.md
-rw------- 1 root root    0  6月  6 11:47 MEMORY.md.lock
-rw------- 1 root root 2508 9月 25 08:50 USER.md
-rw------- 1 root root    0  8月  2 21:58 USER.md.lock
```

注意字节数与字符数不是一回事：`MEMORY.md` 3294 字节但只有 2131 字符（中文占 3 字节），字符数才是限额的计量单位。`.lock` 文件是写入互斥用的空文件，不需要清理。

条目之间用 `§`（section sign，U+00A7）分隔，单条可以多行。注入时的渲染形式（官方文档给出的形态，含用量百分比）：

```text
══════════════════════════════════════════════
MEMORY (your personal notes) [67% — 1,474/2,200 chars]
══════════════════════════════════════════════
User's project is a Rust web service at ~/code/myapi using Axum + SQLx
§
This machine runs Ubuntu 22.04, has Docker and Podman installed
§
User prefers concise responses, dislikes verbose explanations
```

```text
文件布局与注入要点：
1. 路径 —— ~/.hermes/memories/MEMORY.md 与 USER.md（profile 隔离：不同 profile 各自的 home 下各有一份）
2. 分隔符 —— § 单字符分隔条目，条目内部可换行；文件是纯文本，可直接肉眼审阅
3. 计量单位 —— 字符（不是字节）；中文环境用 wc -m 校验，用 wc -c 会高估约三倍
4. 注入形态 —— 头部带存储名与「百分比 + 已用/上限」，智能体据此判断是否需要整理
5. 冻结快照 —— 注入块在一次会话开始时定格，中途 add/remove 只看得到工具返回值，系统提示词不变
6. profile 隔离 —— 记忆按 profile 分开；要跨 agent 共享记忆得用外部提供方，不要共享同一个 home
```

## memory 工具与写入策略

智能体通过 `memory` 工具管理这两个文件，只有三个动作，没有 `read`（内容已被注入到上下文里，不需要读）：

| 动作 | 参数 | 语义 |
|---|---|---|
| `add` | `target`、`content` | 追加一条新条目；与现有条目完全重复时返回「未新增重复项」 |
| `replace` | `target`、`old_text`、`content` | 用唯一子串定位一条，整条替换为新内容 |
| `remove` | `target`、`old_text` | 用唯一子串定位并删除一条 |

`target` 取 `memory`（MEMORY.md）或 `user`（USER.md）。`old_text` 是**唯一子串匹配**，不需要写全，但匹配到多条会报错要求更精确：

```text
# 记忆里存在 "User prefers dark mode in all editors" 时
memory(action="replace", target="memory",
       old_text="dark mode",
       content="User prefers light mode in VS Code, dark mode in terminal")
```

写入内容本身会经过安全扫描：包含提示词注入、凭据外泄、SSH 后门类模式，或夹带不可见 Unicode 字符的条目会被拒绝——因为它们最终会进入系统提示词，属于可信边界。写入时机由智能体自行判断，典型触发场景：

```text
应当写入 MEMORY（智能体的笔记）：
- 环境事实：操作系统版本、已装工具、项目目录结构、端口占用约定
- 项目约定与配置：包管理器、测试命令、代码风格、CI 触发方式
- 工具坑与绕行方案：某个命令必须加的参数、某网络环境下必须走代理
- 已完成任务的日记式条目：某日完成了什么迁移/部署
- 用户明确的「记住这件事」请求

应当写入 USER（用户画像）：
- 身份与工作背景：角色、时区、技术栈熟悉度
- 沟通偏好：中文/英文、简洁还是详细、是否要编号清单
- 审美与反模式：明确拒绝的样式、明确要求的风格
- 工作习惯：迭代节奏、长任务是否要求后台跑完再通知

不应当写入：
- 过于笼统的信息（"用户问过 Python"）
- 网上随时能查到的通用知识（"Python 3.12 支持 f-string 嵌套"）
- 大段原始数据（日志、代码块、表格）
- 一次性的临时上下文（临时文件路径、单次调试场景）
- 已经在 SOUL.md / AGENTS.md 里的内容（会双重占用预算）
```

条目质量对容量利用率影响极大，官方推荐的写法是「压缩多事实、可执行」：

```text
# 好：一条装下多个相关事实
User runs macOS 14 Sonoma, uses Homebrew, has Docker Desktop and Podman. Shell: zsh with oh-my-zsh. Editor: VS Code with Vim keybindings.

# 好：具体可执行的约定
Project ~/code/api uses Go 1.22, sqlc for DB queries, chi router. Run tests with 'make test'. CI via GitHub Actions.

# 好：带上下文的踩坑结论
The staging server (10.0.1.50) needs SSH port 2222, not 22. Key is at ~/.ssh/staging_ed25519.

# 差：太笼统
User has a project.

# 差：太啰嗦（把发现过程也写进去了）
On January 5th, 2026, the user asked me to look at their project which is
located at ~/code/api. I discovered it uses Go version 1.22 and...
```

同一个项目上的多条零散条目应当定期合并，例如把三条「项目用 X」的条目合并成一条完整的项目描述条目——这是容量管理的核心动作，而不是删掉最老的条目。

```text
memory 工具要点：
1. 只有三个动作 —— add / replace / remove；没有 read，内容已在系统提示词里
2. 定位方式 —— replace/remove 用 old_text 子串匹配，必须唯一，否则报错
3. 双目标 —— target=memory 写智能体笔记，target=user 写用户画像，语义不要混用
4. 去重 —— 完全重复的 add 被拒；近似重复不会自动合并，需要智能体自己 replace
5. 安全扫描 —— 注入/外泄模式与不可见 Unicode 会被拒（内容进系统提示词，属可信边界）
6. 合并优先于删除 —— 满仓时先把同类条目合并成一条信息密度更高的条目
```

## 容量限制与满仓处理

记忆**不会自动压缩**。当一次写入会超过限额时，工具返回错误而不是悄悄丢条目，错误体里附带当前全部条目，让智能体在同一轮里自己腾出空间：

```text
{
  "success": false,
  "error": "Memory at 2,100/2,200 chars. Adding this entry (250 chars) would exceed the limit. Consolidate now: use 'replace' to merge overlapping entries into shorter ones or 'remove' stale or less important entries (see current_entries below), then retry this add — all in this turn.",
  "current_entries": ["..."],
  "usage": "2,100/2,200"
}
```

处理顺序是固定的四步：先看错误里返回的当前条目 → 找出可以合并或已经过期的 → 用 `replace` 把相关条目合并成更短的版本 → 再重试 `add`。注意 `replace` 同样受限额约束：把一条换成更长的内容一样会溢出。

按官方建议，系统提示词头部的用量百分比超过 80% 时就该主动整理，而不是等到报错。本机的 `USER.md` 已经贴着上限（1375/1375 字符，8 条），这是「刚好卡满」的真实样本：此时任何新用户偏好写入都会先失败，必须先合并。

```text
容量管理要点：
1. 限额 —— memory 2200 字符（典型 8-15 条）、user 1375 字符（典型 5-10 条）
2. 超限行为 —— 返回错误 + 当前条目 + 用量，不静默丢弃；必须在同一轮内整理后重试
3. replace 也受限额 —— 换更长的内容同样溢出，改写时要变短或先删一条
4. 阈值 —— 头部用量超过 80% 就提前合并，别等报错
5. 校验手段 —— wc -m 看字符数，grep -c '§' 看条目数
6. 官方文档位置 —— user-guide/features/memory（「What Happens When Memory is Full」一节）
```

## 用户画像的边界

`USER.md` 是最容易被滥用的存储：既然它对每次对话都生效，就很容易把所有「用户说过的话」都塞进去，最后变成一个既超限又无用的偏好清单。判据只有一条——「这条会不会改变我下次的决定」。

正反例对照（写法本身可直接复用）：

| 字段类别 | 应当写 | 不应当写 |
|---|---|---|
| 沟通方式 | 「中文交流」「要求编号清单、逐条实现」 | 「用户今天心情不错」 |
| 审美红绿线 | 「拒绝玻璃拟态/炫彩渐变，图标用 SVG 线性」 | 「用户觉得某个页面挺好看」 |
| 工作节奏 | 「长任务要求后台持久运行、断线不停、完成后通知」 | 「用户当时比较急」 |
| 技术栈 | 「Node 项目统一用 Node 22」 | 「用户问过 Node 版本」 |
| 项目上下文 | 「项目路径 + 端口 + 部署方式」 | 整个 README 的内容 |

画像与项目文档分工要清楚：项目专属事实（构建命令、目录约定）应落在 `AGENTS.md`（项目级、可提交 Git、团队共享），用户级偏好才落 `USER.md`。重复写两处不仅浪费预算，还会在两者冲突时产生歧义。

```text
用户画像边界要点：
1. 判据 —— 「这条会不会改变我下次的行为？」不会就不要写
2. 粒度 —— 写红绿线（明确的偏好与拒绝项），不写单次事件
3. 分工 —— 项目事实进 AGENTS.md，用户偏好进 USER.md，别重复
4. 反例 —— 笼统、可从网上查到、大段数据、一次性上下文都不写
5. 冲突处理 —— 写完发现两处矛盾，优先修 AGENTS.md 或用 replace 合并记忆条目
6. 审查入口 —— 纯文本 + § 分隔，直接用编辑器打开即可逐条核对
```

## 会话检索与历史复用

`session_search` 是记忆的第二条腿，解决「上周我们聊过这个」这类问题。它走 SQLite 的 FTS5 索引，**不调用任何 LLM**，返回的是数据库里的原始消息而不是摘要，所以既准确又免费。本机会话库的真实体量（`hermes sessions stats`）：

```text
$ hermes sessions stats
Total sessions: 521
Total messages: 39203
  cli: 99 sessions
Database size: 842.5 MB
```

工具有四种调用形态，靠传了哪些参数自动推断意图（没有 `mode` 参数）：

```text
# 1) discovery —— 传 query：FTS5 检索，按会话去重后返回前 N 个
session_search(query="auth refactor", limit=3)

# 2) scroll —— 传 session_id + around_message_id：以锚点为中心取 ±window 条
session_search(session_id="20260510_174648_805cc2", around_message_id=590803, window=10)

# 3) read —— 只传 session_id：整段读回（大会话给头部+尾部视图）
session_search(session_id="20260510_174648_805cc2")

# 4) browse —— 不传参数：按时间列出最近会话（用于「我上次在弄什么」）
session_search()
```

检索语法就是 FTS5 语法，另外三个可选参数控制排序与范围：

```text
# 关键词（默认 AND）、短语、布尔、前缀
session_search(query="docker deployment")
session_search(query="\"exact phrase\"")
session_search(query="docker OR kubernetes")
session_search(query="python NOT java")
session_search(query="deploy*")

# sort=newest|oldest（默认按相关度）
session_search(query="study-work 知识库", sort="newest")

# detail=adaptive（默认，只把排名第一的结果完整展开）| full
session_search(query="cron 投递", detail="full")

# role_filter=user,assistant（默认）| 加上 tool 才能搜工具输出
session_search(query="Service is too busy", role_filter="user,assistant,tool")
```

命令行的等价入口用于人工排查：

```bash
hermes sessions list                       # 最近 20 个会话
hermes sessions list --limit 50            # 看更多
hermes sessions list --source telegram     # 按来源平台过滤
hermes sessions list --workspace my-project  # 按工作目录过滤
hermes sessions export backup.jsonl --redact   # 导出并在导出内容里抹掉密钥/token
hermes sessions prune --older-than 30 --yes    # 清理 30 天前的已结束会话
```

记忆与会话检索的分工是官方明确给出的设计意图：

| 维度 | 持久记忆（MEMORY/USER） | 会话检索（session_search） |
|---|---|---|
| 容量 | 约 1300 tokens 总量封顶 | 无上限（全部历史会话） |
| 速度 | 瞬时（已在系统提示词里） | 检索约 20ms，滚动 1-2ms |
| 成本 | 每次请求都付出 token | 免费，无 LLM 调用 |
| 适用 | 必须永远在上下文里的关键事实 | 「上周那次讨论的细节是什么」 |
| 管理 | 智能体手工策展 | 自动全量留存 |

```text
会话检索要点：
1. 四种形态 —— query（检索）/ session_id+around_message_id（滚动）/ session_id（整段）/ 空参（浏览最近）
2. 零 LLM 成本 —— 直接返回库里的原始消息，不摘要、不截断
3. 检索语法 —— FTS5：AND 默认、短语加引号、OR/NOT、前缀 deploy*
4. 细化参数 —— sort=newest|oldest、detail=adaptive|full、role_filter=user,assistant[,tool]
5. 存储位置 —— ~/.hermes/state.db（SQLite + WAL + FTS5）；~/.hermes/sessions/*.json 只是历史遗留快照
6. 清理建议 —— state.db 大不等于该删；先跑 hermes sessions optimize（合并索引 + VACUUM，不动数据）
```

## 长期知识沉淀与外部记忆提供方

「长期沉淀」在 Hermes 里由三件事共同承担：记忆条目（事实）、技能（流程）、以及把两者可视化的 `journey` 时间线。`hermes journey list` 输出的是**节点 id**，记忆条目以 `memory:<来源>:<序号>:<哈希>` 命名，前端 `◆`，技能节点前端 `●`：

```text
$ hermes journey list | head -20
sketch  ● sketch  2 Aug 2026
design-agent  ● design-agent  2 Aug 2026
github-auth  ● github-auth  4 Aug 2026
three-scope-map  ● three-scope-map  9 Aug 2026
...
echarts-dashboard  ● echarts-dashboard  19 Sep 2026
session-librarian  ● session-librarian  24 Sep 2026
linux-service-deployment  ● linux-service-deployment  25 Sep 2026
memory:profile:16:865993d56ee0  ◆ Prefers premium, professional design without
"AI feel." Rejects emoji as UI icon…  25 Sep 2026
memory:profile:17:21a35694907e  ◆ 语言偏好：中文交流。项目位于 …
```

该命令同时是**纠错入口**：删掉错误条目、或直接编辑条目内容：

```bash
hermes journey list                       # 列出节点 id（技能名 与 memory:<source>:<index>）
hermes journey edit memory:profile:17:21a35694907e   # 用 $EDITOR 打开该条记忆
hermes journey delete memory:profile:17:21a35694907e -y   # 删除该条记忆（技能则是归档，可恢复）
hermes journey --json                     # 输出原始图数据，便于自己统计
```

当 2200 字符实在不够时（需要知识图谱、语义检索、自动抽取事实、跨会话用户建模），再叠一层外部记忆提供方——它们是**叠加**而不是替换内置记忆：

```bash
$ hermes memory --help
usage: hermes memory [-h] {setup,status,off,reset} ...

Set up and manage external memory provider plugins. Bundled providers:
holographic, retaindb, byterover. Catalog providers (e.g. honcho, hindsight,
supermemory, mem0, openviking): hermes plugins install <name>. Only one
external provider can be active at a time. Built-in memory (MEMORY.md/USER.md)
is always active.

$ hermes memory status

Memory status
────────────────────────────────────────
  Built-in (MEMORY.md / USER.md):
    Memory injection:   enabled ✓
    User profile:       enabled ✓
    Memory tool:        enabled ✓
  Provider:  (none — built-in only)

  Installed plugins:
    • byterover  (API key / local)
    • holographic  (local)
    • retaindb  (API key / local)
```

关闭与清空的语义要分清：`hermes memory off` 只是停用外部提供方（内置记忆继续工作），`hermes memory reset` 会**擦除**内置记忆：

```bash
$ hermes memory reset --help
usage: hermes memory reset [-h] [--yes] [--target {all,memory,user}]
  --target {all,memory,user}  Which store to reset: 'all' (default), 'memory', or 'user'
```

```text
长期沉淀要点：
1. 三件套 —— 事实进记忆条目、流程进技能、时间线用 hermes journey 审阅与纠错
2. journey 节点 id —— 记忆是 memory:<source>:<index>:<hash>，技能就是技能名
3. 纠错动作 —— journey edit 改内容，journey delete 删记忆（技能是归档，可恢复）
4. 外部提供方 —— 叠加而非替换；内置两文件始终生效；同一时刻只能启用一个外部提供方
5. 命令区分 —— off 停用外部提供方；reset 擦除内置记忆（不可逆，慎用）
6. 官方文档 —— user-guide/features/memory 与 user-guide/features/memory-providers
```

## 写入闸门与通知

默认情况下智能体自由写入记忆（包括每轮结束后那个后台自我改进复盘）。如果你不接受「它自动记下了关于我的错误假设」，就把闸门打开：

```text
# ~/.hermes/config.yaml
memory:
  write_approval: true   # false（默认）= 自由写入；true = 写入前需批准
```

打开后，交互式 CLI 里的前台写入会当场内联提示（条目很短，能完整读）；其它环境（消息平台、脚本、后台复盘）则**暂存待审**：

```text
/memory pending             # 列出暂存的记忆写入（自动产生的标 [auto]）
/memory approve <id>        # 批准一条（或 all）
/memory reject <id>         # 拒绝一条（或 all）
/memory approval on         # 打开闸门（off 关闭）并持久化
```

聊天里那条「记忆已更新」提示的详细程度由 `display.memory_notifications` 控制：

```text
display:
  memory_notifications: on    # off | on（默认）| verbose
```

| 取值 | 行为 |
|---|---|
| `off` | 不显示通知；复盘照常运行、照常写入 |
| `on`（默认） | 只给一行通用提示，如 `Memory updated` |
| `verbose` | 附变更预览，如 `Memory 新增: 用户偏好简洁回复` |

另外两个值得知道的开关：把 `memory_enabled` 与 `user_profile_enabled` **同时**设为 `false` 会彻底关掉内置记忆（`memory` 工具从工具表里消失，提示词里的记忆说明也一并移除）；只关其中一个时工具仍在（它要支撑另一个存储），但只公布仍启用的那个 target。后台复盘可以单独关闭（`auxiliary.background_review.enabled: false`），这样仍保留记忆整理的其它路径，还能省掉一部分 token 开销。

```text
写入闸门要点：
1. 默认自由写入 —— 缓解不适的办法是 write_approval: true，而不是事后删条目
2. 暂存流转 —— /memory pending → approve / reject；CLI 内前台写入是内联批准
3. 通知粒度 —— display.memory_notifications: off|on|verbose（只影响聊天里的提示行）
4. 彻底关闭 —— memory_enabled 与 user_profile_enabled 同时 false，工具与说明一起移除
5. 单侧关闭 —— 只关一个时工具保留，但只公布仍启用的 target，写被禁存储会被拒
6. 后台复盘 —— auxiliary.background_review.enabled: false 可停掉每轮结束的自动复盘
```

## 应用场景实战

### 场景一：给一个项目建立长期记忆 + 用户画像

需求：接手 `/opt/project-work/wechat-auto` 这个项目（Node 22 + 内置 node:sqlite、Web 端口 4000），希望之后每个新会话都不必重新交代环境，同时把用户的两条硬性偏好固化进画像。做法是「先量化现状、再按预算写入、最后校验」，脚本失败即退出，避免写入被限额悄悄卡住。

```bash
#!/usr/bin/env bash
# scripts/seed-memory.sh —— 写入前先量预算，写入后做校验
set -euo pipefail

HOME_DIR="${HERMES_HOME:-$HOME/.hermes}"
MEM="$HOME_DIR/memories/MEMORY.md"
PROF="$HOME_DIR/memories/USER.md"
MEM_LIMIT=2200
PROF_LIMIT=1375

chars() { wc -m < "$1" | tr -d ' '; }

report() {
  local mem_chars prof_chars mem_entries prof_entries
  mem_chars=$(chars "$MEM")
  prof_chars=$(chars "$PROF")
  mem_entries=$(grep -c '§' "$MEM" || true)
  prof_entries=$(grep -c '§' "$PROF" || true)
  echo "MEMORY.md ${mem_chars}/${MEM_LIMIT} 字符, ${mem_entries} 个分隔符"
  echo "USER.md   ${prof_chars}/${PROF_LIMIT} 字符, ${prof_entries} 个分隔符"
  if [ "$mem_chars" -ge $((MEM_LIMIT * 80 / 100)) ]; then
    echo "警告：MEMORY.md 已超 80%，先合并同类条目再新增"
  fi
  if [ "$prof_chars" -ge $((PROF_LIMIT * 80 / 100)) ]; then
    echo "警告：USER.md 已超 80%，先合并同类条目再新增"
  fi
}

echo "[1/3] 写入前预算检查"
report

echo "[2/3] 交给智能体写入（对话里直接说，或用 memory 工具）"
cat <<'EOF'
在对话中下达的指令示例：
记住这台机器上的项目 wechat-auto（公众号 AI 写作 + 封面图生成）：
- 目录 /opt/project-work/wechat-auto，Web 端口 4000
- 内置 node:sqlite 需要 Node 22（/usr/local/bin/node），不能用 /usr/bin/node v18
- 细节见 wechat-article-production 技能
另外记住我的两条偏好：界面禁用 emoji 图标，只用 SVG 线性图标；长任务必须后台跑完再通知我。
EOF

echo "[3/3] 写入后校验"
report
```

写入落到盘上的形态（示意，条目内容按 § 分隔）：

```text
# ~/.hermes/memories/MEMORY.md（节选）
§
wechat-auto（公众号AI写作+封面）在 /opt/project-work/wechat-auto：web 端口 4000，node:sqlite 需 Node22（/usr/local/bin/node）；细节见 wechat-article-production skill
§
K8S：minikube 单节点在 /opt/project-work/k8s/（kubeconfig /root/.kube/config）；minikube start 需 --force，勿随手 stop
```

```text
# ~/.hermes/memories/USER.md（节选）
§
语言偏好：中文交流。
§
拒绝 emoji 作为 UI 图标，使用 SVG 线性图标（24×24、stroke）。
§
长任务要求：后台持久运行（断线不能停）、中间不要停顿；完成后在手机（QQ）上通知。
```

```text
# 实跑效果（本机执行 bash scripts/seed-memory.sh）
$ bash scripts/seed-memory.sh
[1/3] 写入前预算检查
MEMORY.md 2131/2200 字符, 15 个分隔符
USER.md   1375/1375 字符, 8 个分隔符
警告：MEMORY.md 已超 80%，先合并同类条目再新增
警告：USER.md 已超 80%，先合并同类条目再新增
```

这一步的价值就在最后两行：本机两个存储都已接近或贴满上限，直接 `add` 必然报错，必须先合并。如果跳过预算检查，会表现为「告诉它记住某件事，它说记下了，下个会话却查不到」——实际是被限额挡下后智能体自己挑了一条删掉。

### 场景二：从历史会话里捞出上次的结论并沉淀成记忆

需求：两周前讨论过某个部署方案的取舍，现在的会话里没有那段上下文。做法是先用 FTS5 检索定位会话与锚点消息，再滚动补齐上下文，最后把结论固化成一条记忆条目（顺手用 journey 核对该条是否已写入）。

```bash
#!/usr/bin/env bash
# scripts/recall-and-sink.sh —— 检索历史 → 导出证据 → 沉淀记忆
set -euo pipefail

QUERY="${1:?用法: recall-and-sink.sh <检索词> [工作目录过滤]}"
WORKSPACE="${2:-}"
OUT_DIR="${TMPDIR:-/tmp}/hermes-recall"

echo "[1/4] 检索历史会话（FTS5，无 LLM 调用）"
if [ -n "$WORKSPACE" ]; then
  hermes sessions list --workspace "$WORKSPACE" --limit 20
else
  hermes sessions list --limit 20
fi

echo
echo "[2/4] 在对话里让智能体用 session_search 精确检索"
cat <<EOF
对智能体说：
用 session_search 搜 "$QUERY"（sort=newest），找到排名第一的会话；
拿到 session_id 与 match_message_id 后，用 around_message_id 向前后各滚 10 条，
把当时的结论、放弃的方案和原因整理成三条要点。
EOF

echo
echo "[3/4] 需要留档时导出（导出内容自动抹掉密钥/token）"
mkdir -p "$OUT_DIR"
hermes sessions export "$OUT_DIR/recall.jsonl" --title "$QUERY" --redact \
  || echo "（按标题没匹配到，改用智能体给出的 session_id 单条导出）"
# 单条导出示例：
# hermes sessions export "$OUT_DIR/one.jsonl" --session-id 20261001_101500_ab12cd34 --redact

echo
echo "[4/4] 沉淀为记忆条目后，用 journey 核对"
hermes journey list | grep -i 'memory:' | tail -5
```

```text
# 实跑效果（节选：第 1 步真实输出；第 4 步确认真实条目已存在）
$ bash scripts/recall-and-sink.sh "study-work 知识库"
[1/4] 检索历史会话（FTS5，无 LLM 调用）
Title                        Workspace          Last Active   ID
────────────────────────────────────────────────────────────────
创建各AI知识库文档到 /opt/study-wor   root               just now      20261015_083443_00d9c7
在/opt/study-work生成知识库文档      root               8h ago        20261015_003808_1e2899
生成学习目录知识文档                   root               9h ago        20261014_234405_185545

[4/4] 沉淀为记忆条目后，用 journey 核对
memory:profile:16:865993d56ee0  ◆ Prefers premium, professional design without …
memory:profile:17:21a35694907e  ◆ 语言偏好：中文交流。项目位于 …
```

```text
场景二关键点：
1) 先检索再问 —— session_search 免费且返回原文，比让模型猜「上次说过什么」可靠
2) 定位靠锚点 —— discovery 给出 session_id + match_message_id，滚动用 messages[-1].id 继续向前
3) 沉淀要短 —— 结论写成一条信息密度高的条目（含日期与放弃原因），不要把整段对话贴进记忆
4) 先查后写 —— 用 journey list | grep memory: 确认该条还没写过，避免挤占容量
5) 导出加 --redact —— 任何可能外发的导出都加 --redact，抹掉密钥与凭据
```

## 最佳实践与踩坑记录

### 最佳实践

1. 记忆条目按「一条一主题、多事实合并」写：把环境事实、端口、依赖版本、坑的绕行方案压进同一条，容量利用率最高
2. 定期量化预算：`wc -m` 看字符数、`grep -c '§'` 看条目数，超过限额 80% 就先合并再新增
3. 项目事实与用户偏好分流：项目级写 `AGENTS.md`（可提交 Git、团队共享），用户级写 `USER.md`，不要在记忆里重复项目文档
4. 涉及「用户对错判断」的场景把 `memory.write_approval` 打开：自动写入暂存待审，用 `/memory pending` 逐条批准
5. 需要回忆细节时优先 `session_search` 而不是加大记忆容量：检索免费且返回原文，记忆的每一字符都要在每次请求里付费
6. 清空前提早备份：`hermes memory reset` 不可逆，动手前先复制一份 memories 目录
7. 定期用 `hermes journey list` 审阅沉淀效果：能一眼看出最近学到的是流程（技能）还是事实（记忆），不对就 `journey edit/delete`

### 踩坑记录

```text
坑 1：明明让它「记住」，下个会话却查不到
结论：本轮工具调用看起来成功，或它说记下了，但新会话里没有任何相关条目。
原因：记忆有硬限额（memory 2200 / user 1375 字符）且不自动压缩；超限时写入被拒，
      若智能体选择「删一条旧的再写」，被删的往往是你更在意的那条。
解法：写入前先量预算（wc -m），超过 80% 就先 replace 合并同类条目；关键事实写完后
      用 grep 在文件里确认条目真的落盘，而不是只看它口头回复。

坑 2：把对话里大量内容塞进记忆，越记越不好用
结论：记忆很快写满，早期的重要约定被后续的零碎信息挤掉。
原因：把一次性的调试上下文、大段日志、能从文档查到的通用知识当作长期事实写入了。
解法：只写「会改变下次行为」的条目：环境事实、约定、坑的绕行方案、用户红绿线；
      过程性细节留给 session_search 按需检索，不占每次请求的预算。

坑 3：多个 agent 进程指向同一个 HERMES_HOME，记忆互相污染
结论：文件里出现你没写过、也不认识的条目，甚至出现相互矛盾的偏好。
原因：记忆写入是自动的，且会话启动时整体注入系统提示词；两个写入方共享一份文件会互相叠加。
解法：一个 Hermes home 只跑一个 agent；需要第二个 agent 就给它独立 profile（各自 memories/），
      需要共享记忆则改用外部记忆提供方而不是共享目录。

坑 4：改了记忆文件却「不生效」，直到重开会话才生效
结论：在同一会话里 add/remove 后，发现模型的行为没变化。
原因：系统提示词里的记忆块是会话启动时抓的冻结快照，刻意不变以保住 LLM 的前缀缓存；
      工具返回值里显示的是实时状态，两者不一致是设计如此。
解法：需要立刻生效就新开一个会话（/new）；核对当前真实状态直接看
      ~/.hermes/memories/ 下的文件或用 journey list，不要看系统提示词。

坑 5：reset 之后以为「只是关掉记忆」，结果画像和笔记全没了
结论：hermes memory reset 之后 MEMORY.md 与 USER.md 内容被清空。
原因：off 与 reset 语义不同——off 只是停用外部提供方（内置记忆继续工作），
      reset 会擦除内置存储（--target 可选 all/memory/user）。
解法：日常想减负用 off；确要清空则先备份 memories 目录，再执行
      hermes memory reset --target user（只清画像），并在次日会话里核对注入的用量百分比。
```
