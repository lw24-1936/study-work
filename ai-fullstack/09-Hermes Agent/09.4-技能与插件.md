## 概述

Hermes 有两条扩展路径，定位完全不同。技能（skill）是纯文本文档，回答「怎么做事」——它不引入可执行代码，按需加载进上下文，可以手写、可以让 Agent 自己写、可以从 hub 装，官方明确把它列为首选的扩展方式。插件（plugin）是 Python 代码，回答「能做什么新动作、能在哪一步介入」——通过 `register(ctx)` 注册新工具、挂生命周期钩子、加斜杠命令与 CLI 子命令，也可以顺带带上一批只读技能。

本篇把两者讲透：技能放在哪、怎么被加载、frontmatter 能声明什么、装第三方技能时的扫描与信任机制；插件的目录结构、`register(ctx)` 的 API 面、钩子清单与能力（capability）授权，最后用一个真实写出来并跑过 `hermes plugins doctor` 的插件把流程走完。

```text
本节要点：
1. 两条扩展路径 —— 技能（文档，怎么做事）与插件（代码，能做什么 / 在哪介入）
2. 技能是文件 —— ~/.hermes/skills/<分类>/<技能名>/SKILL.md，可 git 管理、可共享、可审计
3. 渐进式披露 —— 只加载名字与描述，需要时才 skill_view 读全文，再需要时才读 references/
4. 插件是 opt-in —— 装完默认不启用，register(ctx) 里能注册工具、钩子、斜杠命令、CLI 子命令、技能、中间件
5. 安全边界 —— 技能安装走隔离区 + 扫描 + lock.json 记录；插件的能力（如覆盖内置工具）需要用户显式授权
6. 本机实测 —— 技能 979 hub-installed / 5 builtin / 227 local（123 enabled，1088 disabled）；插件已启用 ponytail v4.10.0
```

## 技能目录与渐进式披露

技能的单一真源是 `~/.hermes/skills/`。分类目录下每个技能一个子目录，主文件必须叫 `SKILL.md`，可选子目录有 `references/`（按主题拆分的参考文档）、`templates/`、`scripts/`、`examples/`、`assets/`。第三方安装（URL 或 GitHub）只复制 `SKILL.md` 及其真正引用到的文件，不会把整个仓库搬进来。hub 的状态放在 `.hub/` 下，`.bundled_manifest` 记录内置技能的播种情况。

渐进式披露分三层，目的就是把 token 花在真正需要的技能上：第 0 层 `skills_list()` 只返回 `{name, description, category}` 列表（约 3k token 量级）；第 1 层 `skill_view(name)` 读回全文与元数据；第 2 层 `skill_view(name, path)` 只读某个 reference 文件。系统提示词里的 `<available_skills>` 索引就是第 0 层，所以技能描述写得好不好，直接决定它会不会在该用的时候被用上。

```bash
# 本机实测：技能根目录与 hub 状态目录
$ ls ~/.hermes/skills | head -6
07-risk-dashboard
09-ai
100-indicators-analysis
10x-talent-school
1688-common-html-report-generator
3dgs-code-reviewer

$ ls ~/.hermes/skills/.hub
audit.log      # 扫描与审计日志
index-cache    # 注册表索引缓存
lock.json      # 每次安装记录：来源 URL、内容哈希、扫描器版本、发现项、时间戳
quarantine     # 隔离区：扫描中的包先落这里，不直接进 skills/
scan-cache
taps.json      # 已添加的第三方技能源（tap）

# 本机实测：统计口径
$ hermes skills list | tail -1
979 hub-installed, 5 builtin, 227 local — 123 enabled, 1088 disabled

$ ls ~/.hermes/skills | wc -l
1116
```

一个技能的目录形态（官方文档给出的结构）：

```text
~/.hermes/skills/
|-- mlops/                      # 分类目录
|   `-- axolotl/
|       |-- SKILL.md            # 必需：主指令
|       |-- references/         # 可选：按主题拆分的补充文档
|       |-- templates/          # 可选：输出格式模板
|       |-- scripts/            # 可选：技能调用的辅助脚本
|       |-- examples/           # 可选：参考示例输出
|       `-- assets/             # 可选：附属文件
|-- devops/
|   `-- deploy-k8s/             # Agent 创建的技能（created_by: agent）
|       |-- SKILL.md
|       `-- references/
|-- .hub/                       # hub 状态（lock.json / quarantine / audit.log）
`-- .bundled_manifest           # 内置技能的播种记录
```

```text
技能目录与披露要点：
1. 单一真源 —— ~/.hermes/skills/；技能的相对路径解析都以技能自己的目录为基准
2. 三层披露 —— skills_list（名字+描述）→ skill_view(name)（全文）→ skill_view(name, path)（单个 reference）
3. references 要按主题拆 —— 官方 linter 会对超过 60 个 reference 文件、正文超约 24k 字符的 SKILL.md 报警
4. 安装有隔离区 —— 第三方技能先落 .hub/quarantine 扫描，通过后才进 skills/，全过程记进 lock.json
5. 第三方只复制被引用的文件 —— 不是整仓同步，这点影响你写 SKILL.md 时的相对路径
6. 描述就是触发器 —— 第 0 层只有 description，写得含糊等于技能不会被加载
```

## 技能文件格式与条件加载

`SKILL.md` 由 YAML frontmatter 加 Markdown 正文组成。frontmatter 里除了 `name` / `description` / `version` / `author` / `license` 这些元信息，还有一批决定「什么时候才显示这个技能」的条件字段，以及声明密钥、配置项与凭据文件的字段。这套机制让同一个技能库在不同机器上只暴露当前环境真正可用的部分。

```markdown
---
name: my-deploy-runbook
description: 用 git push + 流水线把一个服务发布到预发环境的标准步骤
version: 1.0.0
author: ops-team
license: MIT
platforms: [linux, macos]                 # 可选，限制在特定操作系统加载
metadata:
  hermes:
    tags: [devops, deploy, runbook]
    related_skills: [git-workflow]
    requires_toolsets: [terminal, file]   # 只有这些工具集激活时才展示
    requires_tools: [terminal]            # 只有这些工具可用时才展示
    fallback_for_toolsets: [browser]      # 这些工具集激活时隐藏本技能
    fallback_for_tools: [browser_navigate]
    config:                               # 声明需要用户在 config.yaml 里配的非敏感项
      - key: deploy.project
        description: 目标项目名
        default: ""
        prompt: 要发布的项目名
    blueprint:                            # 可选：让技能同时是一个可运行自动化
      schedule: "0 8 * * *"               # cron 表达式，或 "every 2h" / ISO 时间戳
      deliver: origin
      prompt: 每天早八点检查并汇报昨天的发布结果
required_environment_variables:           # 可选：密钥类变量，存进 ~/.hermes/.env
  - name: DEPLOY_TOKEN
    prompt: 输入部署令牌
    help: 在内部平台 > 令牌 页面生成
    required_for: 触发流水线
required_credential_files:                # 可选：文件形式凭据（OAuth token 等）
  - path: google_token.json
    description: 由 setup 脚本生成的 OAuth 令牌
---

# 服务发布 Runbook

把预发发布拆成可复现的步骤。

## When to Use

用户要求发布、回滚或检查预发环境状态时加载。

## Quick Reference

- 发布：terminal 执行 make deploy ENV=staging
- 回滚：terminal 执行 make rollback ENV=staging
- 验证：web_extract 打开健康检查地址

## Procedure

1. 确认当前分支与目标 tag
2. 跑 make deploy ENV=staging
3. 用健康检查地址验证
4. 失败则 make rollback ENV=staging

## Pitfalls

- 不要在未确认分支的情况下直接发布
- 发布窗口内不要与数据迁移同时进行

## Verification

健康检查返回 200 且版本号与目标 tag 一致。
```

加载与生效的方式有四种：启动时预载（`hermes -s <name>` 或 `--skills a,b`）、会话内显式加载（`/skill <name>`）、扫描目录变更（`/reload-skills`）、以及配置层启停（`skills.disabled` 列表）。技能声明过的 `required_environment_variables` 在技能加载后会自动透传到 `execute_code` 与 `terminal` 沙箱，包括 Docker、Modal 这类远端后端，所以技能里的脚本可以直接用 `$DEPLOY_TOKEN`。

```yaml
# ~/.hermes/config.yaml 实测节选（第 281 行起）
skills:
  external_dirs: []            # 额外的技能搜索目录（团队共享技能库可以挂在这里）
  template_vars: true          # 允许 SKILL.md 里使用 ${HERMES_SKILL_DIR} / ${HERMES_SESSION_ID}
  inline_shell: false          # 内联 shell 片段，默认关闭（打开等于允许 SKILL.md 在宿主上直接执行命令）
  inline_shell_timeout: 10
  guard_agent_created: false   # Agent 写技能时是否做关键字扫描（默认关闭，见官方说明）
  disabled:                    # 逐个技能的启停开关（本机被禁用的一长串就在这里）
    - 10倍人才 · 追求倍速增长的初建学校选育用留体系
    - 1688-common-html-report-generator
    - 3d-wordcloud-visualizer
    - 3dgs-code-reviewer
    - Aider
    ...
```

```bash
# 加载与启停的常用命令
hermes -s hermes-agent                     # 启动时预载一个技能
hermes chat --skills a,b -q "用这两个技能处理任务"
hermes skills config                        # 交互式逐个技能启停
hermes skills list                          # 列出已装技能与状态

# 会话内（斜杠命令）
#   /skill <name>       加载技能
#   /reload-skills      重新扫描 ~/.hermes/skills/
#   /skills             搜索与安装技能
```

```text
技能格式与条件加载要点：
1. frontmatter 是开关 —— platforms / requires_* / fallback_for_* 决定技能在什么环境下才出现
2. 密钥与配置分开 —— 密钥走 required_environment_variables（进 .env，模型看不到明文），非敏感设置走 metadata.hermes.config
3. 配置项的写法 —— 技能声明的设置在 config.yaml 的 skills.config.<key> 下，hermes config migrate 会扫描并提示补齐
4. 脚本路径用模板变量 —— SKILL.md 里写 ${HERMES_SKILL_DIR}/scripts/x.sh，加载时被替换成绝对路径
5. inline_shell 默认关 —— 打开后 SKILL.md 里的内联片段会在宿主上直接跑，只对可信来源开启
6. blueprint —— frontmatter 里带 schedule 的技能同时是自动化，装完后通过 /suggestions 接受或忽略
```

## 技能安装升级与信任审计

技能来源包括官方 hub、skills.sh、各类 well-known agent skill 端点、GitHub 与 ClawHub 等注册表，也支持把一个 GitHub 仓库加为 tap。安装流程不是简单下载：先落到 `.hub/quarantine`，扫描器检查整包内容，把来源 URL、内容哈希、扫描器版本、命中项与时间戳写进 `.hub/lock.json`，通过后才进入 `skills/`。命中阻断（blocked）时需要 `--force` 才能装。

```bash
# 搜索与浏览
hermes skills search "k8s deploy"
hermes skills browse                 # 分页浏览全部可用技能
hermes skills inspect owner/repo/skill-name   # 只看不装

# 安装（标识符来自注册表，或直接给 SKILL.md 的 https URL）
hermes skills install owner/skills/skill-creator
hermes skills install https://example.com/path/SKILL.md --name my-skill --category devops

# 升级与维护
hermes skills check                  # 检查已装 hub 技能是否有更新
hermes skills update                 # 更新过期的
hermes skills audit                  # 重新扫描已装 hub 技能
hermes skills audit --deep my-skill   # 对 Python 文件做 AST 级分析（可选诊断）
hermes skills uninstall <name>

# 仓库级信任（项目内 ./hermes/skills 与 ./.agents/skills 默认不加载）
hermes skills trust /path/to/repo     # 信任某个仓库，之后它的仓内技能才会加载
hermes skills untrust /path/to/repo

# 自定义技能源（tap）
hermes skills tap add owner/repo

# 内置技能被改过时的处理
hermes skills list-modified           # 列出你改过的内置技能（hermes update 会保留）
hermes skills diff <name>             # 与原生版本对比
hermes skills reset <name>            # 清掉 user-modified 标记，恢复可更新
hermes skills opt-out / opt-in        # 停止/恢复向本 profile 播种内置技能
hermes skills repair-official         # 从仓库源回填或恢复官方可选技能
```

本机实测的三个关键子命令帮助（原文，装饰符号已去 emoji）：

```text
$ hermes skills install --help
usage: hermes skills install [-h] [--category CATEGORY] [--name NAME]
                             [--force] [--yes]
                             identifier

positional arguments:
  identifier           Skill identifier (e.g. openai/skills/skill-creator) or
                       a direct HTTP(S) URL to a SKILL.md file

options:
  --category CATEGORY  Category folder to install into
  --name NAME          Override the skill name (useful when installing from a
                       URL whose SKILL.md has no `name:` frontmatter)
  --force              Install despite blocked scan verdict
  --yes, -y            Skip confirmation prompt (needed in TUI mode)

$ hermes skills audit --help

  name     Specific skill to audit (default: all)
  --deep   Run AST-level analysis on Python files (opt-in diagnostic)

```

Agent 自己创建技能也要过一道闸：配置项 `skills.guard_agent_created`（本机为 `false`）打开后，`skill_manage` 新建或修改的技能会被扫描危险关键字模式（凭据窃取、明显的提示词注入、外传指令）。默认关闭是官方的有意选择——真实工作流里合法地提到 `~/.ssh/` 或 `$OPENAI_API_KEY` 太常见，启发式规则误判率高，所以打开它之前先评估自己的技能来源。

```text
安装升级与信任要点：
1. 安装有闸门 —— 隔离区 + 扫描 + lock.json 记录，blocked 的包必须显式 --force 才能装
2. 信任是仓库级的 —— 仓内技能（.hermes/skills、.agents/skills）默认不加载，需 hermes skills trust
3. 升级前先 check —— skills check 只读探测，skills update 才真正写盘；批量更新前建议先 audit
4. 内置技能可改但会被标记 —— 改过的内置技能在 hermes update 时被保留（list-modified / diff / reset 三件套管理）
5. tap 扩展来源 —— hermes skills tap add <repo> 把团队仓库变成技能源，无需发布到公共注册表
6. 供应链审计另有入口 —— hermes security 覆盖 venv、插件与 MCP server（OSV.dev），与技能扫描互补
```

## 插件机制与钩子

插件是 `~/.hermes/plugins/<插件名>/` 下的一个目录：`plugin.yaml` 是清单，`__init__.py` 里必须有 `register(ctx)` 函数，其余文件随你组织（官方示例用 `schemas.py` 存工具 schema、`tools.py` 存处理器）。Hermes 启动时按「内置 → 用户 → 项目 → entry-points」的来源顺序发现插件，解析清单、导入模块、调用 `register(ctx)`。进程里注册的东西立刻生效：模型马上能看到新工具。

```yaml
# 本机已启用插件 ponytail 的真实清单（~/.hermes/plugins/ponytail/plugin.yaml）
name: ponytail
version: 4.10.0
description: Lazy senior dev mode for Hermes Agent, always-on context, bundled skills, and slash commands.
author: Dietrich Gebert
provides_hooks:
  - pre_llm_call
  - pre_gateway_dispatch
provides_commands:
  - ponytail
  - ponytail-review
  - ponytail-audit
  - ponytail-debt
  - ponytail-gain
  - ponytail-help
provides_skills:
  - ponytail
  - ponytail-review
  - ponytail-audit
  - ponytail-debt
  - ponytail-gain
  - ponytail-help
```

清单 v2 还支持 `manifest_version`、`api_version`、`requires_plugins`（插件间依赖，按拓扑序注册）、`python_dependencies`（只声明与提示，Hermes 不会自动安装）、`config_schema`（校验 `plugins.entries.<id>.settings` 下的键）、`license`、`homepage`、`tags`。`requires_env` 支持简单与富格式两种写法，缺变量时插件被禁用而不是崩溃。

`register(ctx)` 能用的 API 面（官方文档列举，均为 `ctx.` 方法或属性）：

| API | 作用 |
| --- | --- |
| `ctx.register_tool(name, toolset, schema, handler)` | 注册新工具，模型立即可见；`override=True` 可覆盖内置工具（需要 capability） |
| `ctx.register_hook(name, callback)` | 订阅生命周期事件，见下表 |
| `ctx.register_command(name, handler, description=...)` | 注册会话内斜杠命令，handler 收到一个原始参数串 |
| `ctx.register_cli_command(...)` | 注册 `hermes <plugin> <subcommand>` 形式的 CLI 子命令 |
| `ctx.register_skill(name, path_to_skill_md)` | 挂载随插件分发的只读技能，以 `plugin:skill` 命名空间加载 |
| `ctx.register_middleware(kind, fn)` | 注册中间件改写请求（`tool_request`、`llm_request` 等） |
| `ctx.dispatch_tool(name, arguments)` | 在插件内部调用任意工具（走正常审批、脱敏与预算管线） |
| `ctx.get_config(...)` / `ctx.set_config(...)` | 读写本插件在 `plugins.entries.<id>.settings` 下的设置 |
| `ctx.state.get/set` | 插件私有运行时数据（profile 级、原子替换、单插件上限 10 MiB） |
| `ctx.has_capability(id)` / `ctx.has_plugin(id)` | 探测授权能力与依赖插件，用于优雅降级 |

钩子是插件介入 Agent 循环的正式方式。多数钩子是只读观察者（返回值被忽略），只有两个例外：`pre_llm_call` 能向当轮注入上下文，`pre_tool_call` 能返回拦截/升级审批的指令。

| 钩子 | 触发时机 | 回调签名要点 | 返回值 |
| --- | --- | --- | --- |
| `pre_tool_call` | 任意工具执行前 | `tool_name, args, task_id` | 可返回 `{"action": "block", ...}` 否决，或 `{"action": "approve", ...}` 升级到人工审批 |
| `post_tool_call` | 任意工具返回后 | `tool_name, args, result, task_id, duration_ms` | 忽略 |
| `pre_llm_call` | 每轮一次，工具循环之前 | `session_id, user_message, conversation_history, is_first_turn, model, platform` | 返回 `{"context": "..."}` 或纯字符串则该内容注入当轮 user message |
| `post_llm_call` | 每轮一次，工具循环之后（仅成功轮） | `session_id, user_message, assistant_response, ...` | 忽略 |
| `pre_api_request` / `post_api_request` / `api_request_error` | 每次原始 Provider 请求前后/报错时 | 带 `turn_id`、`api_request_id`、`api_call_count` 等关联字段 | 忽略（用于追踪、计费、延迟面板） |
| `on_session_start` / `on_session_end` | 新会话首轮 / 每次 run_conversation 结束 | `session_id, model, platform` 等 | 忽略 |
| `on_session_reset` / `on_session_finalize` | 网关换会话键 / 会话拆除 | `session_id, platform` | 忽略 |
| `gateway_platform_event` | 平台原生事件在网关边界被规范化时（目前是 Telegram 反应） | `platform, event_type, payload` | 忽略 |
| `kanban_task_claimed` / `kanban_task_completed` / `kanban_task_blocked` | 看板任务认领/完成/阻塞 | `task_id, board, assignee, run_id, profile_name` 等 | 忽略 |

所有回调都应接受 `**kwargs`：Hermes 会按签名检查投递字段，声明了旧参数的回调拿到旧字段，带 `**kwargs` 的回调拿到完整载荷——这是官方保证的向前兼容契约。回调崩溃会被记录并跳过，不影响其他钩子与 Agent 继续运行。

`pre_llm_call` 注入的上下文有一个容易踩的细节：它被追加到当轮的 **user message**，而不是系统提示词。这是有意的——系统提示词保持逐轮不变才能命中 Provider 侧的 prompt cache（Anthropic / OpenRouter 对系统提示词前缀做缓存，稳定前缀在多轮对话里能显著降低输入成本）。注入内容每轮最多约 10000 字符，超出部分会写到 `$HERMES_HOME/hook_outputs/<session_id>/<uuid>.txt`，模型需要时再去读。

## 编写并加载自定义插件

写一个能跑的插件只要四步：建目录、写清单、写注册代码、用 `hermes plugins doctor` 验证。doctor 会走与 Hermes 本身相同的发现、清单解析、命名空间导入、`register(ctx)`、钩子与工具注册流程，并报告无效钩子名、不接受 `**kwargs` 的回调、注册失败、以及「清单声明了但没注册」的漂移。下面这个示例（`kb-demo`）在本机真实创建并验证通过。

```yaml
# ~/.hermes/cache/scratch/hermes-plugin-demo/plugin.yaml
name: kb-demo
version: 1.0.0
description: Hermes 插件示例 —— 提供一个系统信息工具与一个工具调用日志钩子
provides_tools:
  - sysinfo
provides_hooks:
  - post_tool_call
```

```python
# ~/.hermes/cache/scratch/hermes-plugin-demo/__init__.py
"""kb-demo 插件 —— 注册一个工具和一个钩子。"""

import json
import platform

SCHEMA = {
    "name": "sysinfo",
    "description": (
        "Return basic host information (OS, release, Python version, CPU). "
        "Use it when the user asks what machine the agent is running on."
    ),
    "parameters": {
        "type": "object",
        "properties": {
            "detail": {
                "type": "string",
                "description": "Level of detail: brief or full",
                "enum": ["brief", "full"],
            }
        },
        "required": [],
    },
}

_LOG = []


def sysinfo(args, **kwargs):
    """工具处理器：始终返回 JSON 字符串，不抛异常。"""
    detail = (args.get("detail") or "brief").strip()
    try:
        data = {
            "system": platform.system(),
            "release": platform.release(),
            "python": platform.python_version(),
            "machine": platform.machine(),
        }
        if detail == "full":
            data["processor"] = platform.processor() or "unknown"
            data["node"] = platform.node()
        return json.dumps({"success": True, "data": data}, ensure_ascii=False)
    except Exception as exc:
        return json.dumps({"success": False, "error": str(exc)})


def on_post_tool_call(tool_name, args, result, task_id=None, **kwargs):
    """钩子：记录每一次工具调用（包括其他插件与内置工具）。"""
    _LOG.append(tool_name)
    if len(_LOG) > 100:
        _LOG.pop(0)


def register(ctx):
    ctx.register_tool(
        name="sysinfo",
        toolset="kb_demo",
        schema=SCHEMA,
        handler=sysinfo,
    )
    ctx.register_hook("post_tool_call", on_post_tool_call)
```

### 场景一：从零做一个团队插件（内网健康检查工具）并接进 CI

需求：团队希望 Agent 能查内网服务的健康状态，且这个能力要能版本化、能在 CI 里校验、能分发给同事。做法是写一个插件注册 `health_check` 工具，用 `hermes plugins doctor --ci` 做流水线门禁，并用 `hermes plugins pack` / git 分发。

```yaml

version: 1.0.0
manifest_version: 2
license: MIT
tags: [ops, internal]
description: 内网服务健康检查插件

  - post_tool_call
```

```python
# ~/.hermes/plugins/team-health/__init__.py
"""内网健康检查插件：注册一个只读工具，并记录每次工具调用的耗时。"""

import json
import os
import time
import urllib.error
import urllib.request

_TARGETS = ("api", "web", "queue")

SCHEMA = {
    "name": "health_check",
    "description": (
        "Query the internal health endpoint for one or more services "
        "(api, web, queue) and return their status. Read-only."
    ),
    "parameters": {
        "type": "object",
        "properties": {
            "service": {
                "type": "string",
                "description": "Service name: api, web, queue, or 'all'",
                "enum": ["api", "web", "queue", "all"],
            }
        },
        "required": ["service"],
    },
}


def _probe(endpoint, service, token, timeout=5):
    req = urllib.request.Request(
        f"{endpoint}?service={service}",
        headers={"Authorization": f"Bearer {token}"},
    )
    with urllib.request.urlopen(req, timeout=timeout) as resp:
        return json.loads(resp.read().decode("utf-8"))


def health_check(args, **kwargs):
    """返回 JSON 字符串；任何异常都转成 error 字段，绝不抛出。"""
    service = (args.get("service") or "all").strip().lower()
    targets = _TARGETS if service == "all" else (service,)
    endpoint = kwargs.get("endpoint") or "https://internal.example.com/health"
    token = os.environ.get("TEAM_HEALTH_TOKEN", "")
    if not token:
        return json.dumps({"success": False, "error": "TEAM_HEALTH_TOKEN 未配置"})

    results = {}
    for name in targets:
        started = time.time()
        try:
            results[name] = {"ok": True, "body": _probe(endpoint, name, token)}
        except urllib.error.HTTPError as exc:
            results[name] = {"ok": False, "status": exc.code}
        except Exception as exc:
            results[name] = {"ok": False, "error": str(exc)}
        results[name]["elapsed_ms"] = round((time.time() - started) * 1000, 1)

    total = len(results)
    healthy = sum(1 for r in results.values() if r.get("ok"))
    return json.dumps(
        {"success": healthy == total, "healthy": f"{healthy}/{total}", "services": results},
        ensure_ascii=False,
    )


def on_post_tool_call(tool_name, duration_ms=None, **kwargs):
    """把慢调用打到 stderr，方便在网关日志里 grep。"""
    if duration_ms and duration_ms > 5000:
        print(f"[team-health] slow tool: {tool_name} {duration_ms}ms", flush=True)


def register(ctx):
    endpoint = ctx.get_config("endpoint", default="https://internal.example.com/health")
    ctx.register_tool(
        name="health_check",
        toolset="team_health",
        schema=SCHEMA,
        handler=lambda args, **kw: health_check(args, endpoint=endpoint, **kw),
    )
    ctx.register_hook("post_tool_call", on_post_tool_call)
```

### 场景二：把外部技能来源接进来并走完审计与信任流程

需求：团队有自己的技能仓库 `internal/skills`，希望统一安装到所有开发机，同时满足安全要求——每个技能都记录来源与哈希、扫描通过才进技能目录、且项目内技能不能被随意加载。做法是 tap + inspect + audit + trust 四步走。

```bash
#!/usr/bin/env bash
# install-team-skills.sh —— 团队技能安装与审计
set -euo pipefail

TAP_REPO="internal/skills"
SKILLS=("k8s-deploy-runbook" "log-triage" "incident-postmortem")

echo "[1/5] 添加团队技能源（tap）"
hermes skills tap add "$TAP_REPO"

echo "[2/5] 逐个预览（只看不装）"
for s in "${SKILLS[@]}"; do
  echo "--- inspect: $s"
  hermes skills inspect "$TAP_REPO/$s" || true
done

echo "[3/5] 安装到本项目分类目录"
for s in "${SKILLS[@]}"; do
  hermes skills install "$TAP_REPO/$s" --category team --yes
done

echo "[4/5] 扫描已装 hub 技能（含 Python 文件的 AST 级分析）"
hermes skills audit
hermes skills audit --deep

echo "[5/5] 核对安装记录与状态"
hermes skills list | tail -1
python3 - <<'PY'
import json, pathlib
lock = pathlib.Path.home() / ".hermes/skills/.hub/lock.json"
data = json.loads(lock.read_text(encoding="utf-8"))
print("已记录安装条目：", len(data) if isinstance(data, list) else len(data.keys()))
PY
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先技能后插件：能用文档说清的能力写技能，只有需要访问 API、解析二进制、做网络请求时才写插件——技能零代码、零信任成本、可被任何人审阅
2. 描述写得像触发器：第 0 层只有 `name` + `description`，描述里要写清「什么时候该用」，否则技能再全也不会被加载
3. references 按主题拆而不是按章节堆：官方 linter 会对超过 60 个 reference 文件或正文超约 24k 字符的 SKILL.md 报警，因为全文加载后会一直在上下文里
4. 插件一律跑 `hermes plugins doctor . --ci`：它复用真实运行时契约，能抓出无效钩子名、缺 `**kwargs` 的回调、声明与注册的漂移，是最便宜的回归保护
5. 密钥用声明而不是硬编码：技能用 `required_environment_variables`、插件用 `requires_env`，值进 `.env` 且不会把明文暴露给模型
6. 第三方来源三件套：`inspect` 看、`audit` 扫、`lock.json` 留证据；团队仓内技能另需 `hermes skills trust` 才加载
7. 内置技能改动要显式管理：改过的内置技能被 `list-modified` 标记，用 `diff` 对照、`reset` 恢复可更新状态

### 踩坑记录

```text
坑 1：插件写好了，Hermes 里就是不出现
结论：doctor 能通过，实际启动却看不到工具。
原因：插件是 opt-in，安装后默认不启用；另外目录布局深浅有硬限制（原生包必须是 plugins/<name>/plugin.yaml 或一层分类）。
解法：hermes plugins enable <name>；确认目录层级；用 HERMES_PLUGINS_DEBUG=1 hermes plugins list 看跳过原因（如 not enabled in config）。

坑 2：钩子回调少写了 **kwargs，被 doctor 判为不合规
结论：doctor 直接报 must accept **kwargs for forward compatibility。
原因：Hermes 按回调签名投递字段，声明了旧参数的回调只能拿到旧字段；不带 **kwargs 的回调在新版本加字段时会直接失败。
解法：所有钩子回调签名都以 **kwargs 结尾；本机实测的报错原文为 "hook callback 'on_post_tool_call' ... must accept **kwargs for forward compatibility"。

坑 3：插件清单里声明了工具，register 里忘了注册
结论：doctor 通过但给出 WARN: manifest declares tool 'missing_tool' but registration did not add it。
原因：provides_tools / provides_hooks 是声明，不是自动注册；两边必须手动保持一致。
解法：让清单与 register(ctx) 一一对应；把 doctor --ci 接进流水线，漂移当场失败。

坑 4：把 inline_shell 打开以「让技能更灵活」
结论：某个技能在宿主上直接执行了命令，而你并不知情。
原因：SKILL.md 里的内联 shell 片段（!`cmd`）默认关闭，打开后会在宿主上无审批执行，只应对完全可信的技能源开启。
解法：保持 skills.inline_shell: false；用 ${HERMES_SKILL_DIR}/scripts/xxx.sh 让 Agent 通过 terminal 工具显式执行，走正常审批链路。

坑 5：以为 pre_llm_call 注入的内容会进系统提示词
结论：注入生效了，但多轮对话的成本显著上升。
原因：注入被追加到当轮 user message；若插件每条消息都塞大段文本，会持续推高输入 token，并可能让缓存前缀失效。
解法：注入内容要短、要相关（检索前先过滤）；单次注入上限约 10000 字符，超出会落盘到 hook_outputs/ 由模型按需读取。

坑 6：装了 hub 技能就以为安全
结论：技能目录里多了来源不明的指令文档。
原因：技能是「能被模型阅读并执行的指令」，恶意技能本质是提示词注入；安装流程虽有隔离区与扫描，但扫描不是形式化验证。
解法：装前 hermes skills inspect 看内容；装后 hermes skills audit（必要时 --deep）；只看可信来源；仓内技能必须显式 hermes skills trust。
```
