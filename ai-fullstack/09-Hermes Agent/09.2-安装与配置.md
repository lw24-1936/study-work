## 概述

安装 Hermes 只有两条路径：桌面安装包（macOS / Windows，自带运行时）和命令行安装脚本（Linux / macOS / WSL2 / 原生 Windows / Android Termux）。命令行脚本会克隆源码、自举 uv、并让内置的 PM 工具链提供固定版本的 Python、Node.js、npm、ripgrep 与 FFmpeg，因此不需要事先准备语言环境。装完之后必须做配置才有意义：Hermes 把「设置」和「密钥」严格分开放在 `~/.hermes/config.yaml` 与 `~/.hermes/.env`，另有 `auth.json` 存 OAuth 凭据。

本篇覆盖四块：怎么装、第一次怎么初始化、配置文件长什么样以及解析优先级、以及 Provider/模型/凭据怎么配才不出错。所有命令都在本机实测过，输出里的装饰性 emoji 按本库规范去掉了，其余原样保留。

```text
本节要点：
1. 两条安装路径 —— 桌面安装包（macOS 只支持 Apple Silicon / Windows 走 MSIX）与命令行脚本
2. 脚本做了什么 —— 克隆源码、自举 uv、PM 提供固定版本 Python/Node/npm/ripgrep/FFmpeg，并默认装浏览器与 computer-use 工具
3. 配置三分法 —— config.yaml 放设置、.env 放密钥、auth.json 放 OAuth 凭据
4. 一键起步 —— hermes setup --portal 用一次 OAuth 同时拿到模型与四个 Tool Gateway 工具
5. 自检入口 —— hermes doctor（依赖与环境）、hermes config check（配置版本与缺失项）、hermes status --full
6. 版本敏感 —— 本机实测 v0.21.6+131.g38880bd、config 版本 v50；字段与子命令会随版本变化，以官方文档与本机 --help 为准
```

## 安装方式与平台支持

选安装方式的原则很简单：个人桌面机器用安装包（省去运行时依赖），服务器与 CI 用命令行脚本，Android 用 Termux 的 APT 包。官方文档明确写了两条限制：macOS 安装包仅支持 Apple Silicon（Intel Mac 不是受支持平台），Windows 原生安装包通过 `.appinstaller` 走 MSIX 签名包并记录更新源。

```bash
# 1. 命令行安装（Linux / macOS / WSL2），官方推荐入口
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash

# 2. Windows 原生（PowerShell）
# iex (irm https://hermes-agent.nousresearch.com/install.ps1)

# 3. 安装到一半想加桌面端（需要已有命令行安装）
hermes desktop

# 4. 只想要命令行、不要浏览器工具与 computer-use 驱动
#    curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash -s -- --skip-browser --skip-computer-use
#    Windows 对应 -SkipBrowser / -SkipComputerUse；Hermes 会记住这些选择

# 5. Android / Termux（aarch64），走签名的 APT 仓库，不是脚本安装
#    pkg install hermes-agent
```

安装脚本的行为（官方文档说明，本机是 git 安装因此可通过 `hermes --version` 核对）：克隆源码 → 自举 uv → 把依赖准备交给 PM（PM 提供固定版本的 Python、Node.js、npm、ripgrep、FFmpeg）→ 选择 `all` 这个 Python extra（不是每一个可选 extra）。它还会默认装两项外部工具：`agent-browser` 及其固定版本 Chromium（浏览器工具），以及 `cua-driver`（computer-use 驱动，macOS / Windows / glibc Linux）。下载失败时安装仍会完成，并打印重试命令。

```text
$ hermes --version
Hermes Agent v0.21.6+131.g38880bd (2026.9.24) · upstream 38880bd2
Install directory: /home/lw/.hermes/hermes-agent
Install method: git
Python: 3.14.7
OpenAI SDK: 2.24.0
Update available — run 'hermes update'
```

```text
安装方式要点：
1. 服务器装命令行版 —— 安装脚本是唯一官方推荐路径，自带固定版本运行时
2. 桌面安装包内含运行时 —— 首次启动不构建基础运行时；需要远程后端时用安装包 + Settings 里连网关
3. 平台限制要记住 —— macOS 安装包仅 Apple Silicon；WSL2 需要 systemd=true 才能把网关装成服务
4. 可选组件可跳过 —— --skip-browser / --skip-computer-use，且选择会被记住，后续安装沿用
5. 升级与卸载 —— hermes update 升级，hermes uninstall 卸载（升级前默认会做 quick 状态快照）
6. 备份与恢复 —— hermes backup 打包 HERMES_HOME，hermes import 从 zip 恢复（命令清单见 hermes --help）
```

## 首次初始化与 Setup 向导

首次运行推荐顺序是：`hermes setup`（或更省事的 `hermes setup --portal`）配置模型与基础项 → 需要时就 `hermes model` 换模型 → `hermes doctor` 自检 → `hermes` 进入对话。`setup` 支持单独跑某个小节，也支持非交互模式，适合装机脚本。

```bash
# 交互式向导（已有安装时为「重跑并显示当前值作默认」，--quick 只补缺失项）
hermes setup
hermes setup --quick

# 一键全程：OAuth 登录 Nous Portal，选模型，把 Nous 设为推理 provider 并开通 Tool Gateway
hermes setup --portal

# 只配某一块
hermes setup model
hermes setup terminal
hermes setup gateway
hermes setup tools

# 非交互/脚本化（用默认值与环境变量）
hermes setup --non-interactive

# 重置或重配
hermes setup --reset
```

本机实测的 `hermes setup --help`（原文，去了装饰符号）：

```text
首次初始化要点：

2. 分块配置 —— setup 接受 model/tts/terminal/gateway/tools/telemetry/agent 七个 section，改一块不必重跑全流程
3. 脚本化 —— --non-interactive 走默认值与环境变量，已有安装用 --quick 只补缺失项
4. 顺序建议 —— 先 setup（模型）→ 再 hermes doctor 自检 → 最后 hermes 进入对话
5. 换模型随时可做 —— hermes model 是专门的交互式选择器，不必重跑 setup
6. 网关单独配 —— 消息平台走 hermes gateway setup，与模型配置互不干扰
```

## 配置文件结构与优先级

所有设置都在 `~/.hermes/` 下。`config.yaml` 存设置（模型、终端、压缩、显示、内存、安全等），`.env` 存密钥，`auth.json` 存 OAuth 凭据，`SOUL.md` 是身份文件，`memories/` 是长期记忆，`skills/`、`cron/`、`sessions/`、`logs/` 各管一块。管理配置统一走 `hermes config` 系列命令，不要裸手改 YAML——命令会做键名校验与分流。

```bash
# 查看与管理
hermes config              # 交互式查看/编辑入口
hermes config show         # 打印当前配置摘要（本机实测输出见下）
hermes config edit         # 用 $EDITOR 打开 config.yaml
hermes config get model    # 打印解析后的值
hermes config set terminal.backend docker
hermes config unset terminal.backend
hermes config path         # 配置文件路径
hermes config env-path     # .env 路径
hermes config check        # 检查缺失/过期的配置项
hermes config migrate      # 交互式补齐新版本新增的选项（也会扫描已启用技能声明过的设置）
```

配置解析优先级：官方文档给出的顺序是从高到低解析、最高优先级是 CLI 参数（例如 `hermes -m ...`、`--toolsets ...` 会覆盖配置文件里的对应值）。完整的优先级链条以官方文档的 Configuration 页为准，这里不逐条罗列以免随版本变化失真。

`hermes config set` 有一条非常实用的分流规则：`UPPER_SNAKE` 形式的键名（`OPENROUTER_API_KEY`、`DEEPSEEK_API_KEY`、`HERMES_TIMEZONE` 等）一律写进 `.env`，永远不会写进 `config.yaml`；带点号的键走 `config.yaml`。写错前缀（比如把已知键写成 `gateway.discord.foo`）会被拒绝并给出 did-you-mean 提示，确认要写需加 `--force`。

```text
配置文件要点：
1. 三分法 —— config.yaml 设置、.env 密钥、auth.json 凭据，位置由 hermes config path / env-path 打印
2. 优先用命令改 —— hermes config set/get/unset 会做校验与分流，手改 YAML 容易写进「不生效的死键」
3. 自动分流 —— 大写蛇形键名进 .env，带点号的键进 config.yaml
4. 迁移用 migrate —— 升级后新增的配置项与技能声明的设置，由 hermes config migrate 补齐
5. 优先级 —— CLI 参数最高；完整顺序以官方文档 Configuration 页为准
6. 配置坏了不影响启动 —— config.yaml 解析失败时 Hermes 会回退到最近一份可用副本并每次启动告警，且不会改动坏文件
```

## Provider 与模型配置

Hermes 不绑定厂商，官方支持 20 家以上 Provider，接入方式分三类：API Key 类（写进 `.env`）、OAuth 类（`hermes auth` 或 `hermes model` 走登录）、自定义端点类（在 `config.yaml` 里写 `model.base_url` 与 `model.api_key`）。模型用 `provider/model` 形式标识，切换用 `hermes model`，也可以直接 `hermes config set model.default`。

| Provider | 认证方式 | 环境变量 |
| --- | --- | --- |
| OpenRouter | API Key | `OPENROUTER_API_KEY` |
| Anthropic | API Key | `ANTHROPIC_API_KEY` |
| OpenAI（API） | API Key | `OPENAI_API_KEY` |
| DeepSeek | API Key | `DEEPSEEK_API_KEY` |
| Google Gemini | API Key | `GOOGLE_API_KEY` 或 `GEMINI_API_KEY` |
| xAI / Grok | API Key | `XAI_API_KEY` |
| Kimi / Moonshot | API Key | `KIMI_API_KEY` |
| Alibaba / DashScope | API Key | `DASHSCOPE_API_KEY` |
| Z.AI / GLM | API Key | `GLM_API_KEY` |
| MiniMax（国内） | API Key | `MINIMAX_CN_API_KEY` |
| Nous Portal | OAuth | `hermes auth` / `hermes portal` |
| OpenAI Codex | OAuth | `hermes auth add openai-codex --type oauth` |
| GitHub Copilot | Token | `COPILOT_GITHUB_TOKEN` |
| Hugging Face | Token | `HF_TOKEN` |
| 自定义端点 | 配置 | `model.base_url` + `model.api_key` |

完整 Provider 清单与各自的能力差异以官方文档 integrations/providers 页为准。下面是本机真实的模型配置与切换命令：

```bash
# 本机实测：config.yaml 中的模型段
#   model:
#     default: deepseek-flash
#     provider: deepseek

# 换模型（交互式选择器，会提示可用的 Provider 与凭据状态）
hermes model

# 直接用命令改（脚本化场景）
hermes config set model.default deepseek/deepseek-chat
hermes config set model.provider deepseek

# 自定义 OpenAI 兼容端点
hermes config set model.base_url https://my-gateway.internal/v1
hermes config set model.api_key sk-custom-xxx      # UPPER_SNAKE 才会进 .env，这个键名会落在 config.yaml

# 配置 fallback：主模型失败时按顺序尝试（本机 fallback_providers 为空）
hermes fallback

# Mixture of Agents 多模型协作
hermes moa

# 凭据池：同一 Provider 配多个 Key，失败自动轮转
hermes auth add
hermes auth list
hermes auth reset deepseek
```

`hermes fallback`、`hermes moa`、`hermes auth` 都是 `hermes --help` 里列出的真实子命令（分别对应 "Manage fallback providers (tried when the primary model fails)"、"Configure Mixture of Agents provider/model slots"、"Manage pooled provider credentials"）。

```text
Provider 与模型要点：
1. 三类接入 —— API Key / OAuth / 自定义端点，前两类不需要动 config.yaml
2. 模型标识 —— provider/model 形式；交互式切换首选 hermes model，脚本里用 config set
3. 端点自定义 —— model.base_url + model.api_key 可接任意 OpenAI 兼容网关（含本地 vLLM / Ollama）
4. 高可用 —— fallback providers 处理主模型故障，凭据池处理单 Key 被限流，两者可叠加
5. MoA —— 需要多模型协作时用 hermes moa 配置槽位
6. 清单以官方为准 —— 支持的 Provider 会持续增减，最新列表看官方 integrations/providers 页
```

## 凭据与环境变量管理

凭据分三类，存放位置不同，混放是最常见的故障源：普通 API Key 进 `~/.hermes/.env`；OAuth 令牌与凭据池进 `~/.hermes/auth.json`（由 `hermes auth` / `hermes login` 管理）；外部密码管理器（1Password / Bitwarden）里的凭据由 `hermes secrets` 做来源管理。技能与插件声明的密钥也走 `.env`，并且被声明过的变量在技能加载后会透传到 `execute_code` / `terminal` 沙箱（包括 Docker、Modal 这类远端后端）。

```bash
# 1. 写入密钥：UPPER_SNAKE 键名自动落到 ~/.hermes/.env
hermes config set DEEPSEEK_API_KEY sk-xxxxxxxx
hermes config set OPENROUTER_API_KEY sk-or-xxxxxxxx

# 2. 查看密钥是否被识别（不会打印明文）
hermes config show
hermes config check

# 3. OAuth 与凭据池
hermes auth add                 # 交互式向导
hermes auth list                # 列出已池化的凭据
hermes login --provider nous    # OAuth 登录
hermes logout                   # 清除已存认证

# 4. 外部密码管理器
hermes secrets                  # 管理外部密钥来源（Bitwarden / 1Password）

# 5. 会话内重新载入 .env（改了密钥不想退出重进时）
#    在对话里输入：/reload
```

## 健康检查与故障排查

装机与改配置之后固定跑两条自检：`hermes doctor` 看依赖、配置版本、凭据、目录结构；`hermes config check` 看缺失与过期项。出现行为异常时先按「配置是否被读到」→「凭据是否有效」→「会话是否已重置」的顺序排查，这三步能覆盖绝大多数「改了没反应」。

```bash
# 1. 依赖与环境自检（--fix 可尝试自动修）
hermes doctor
hermes doctor --fix

# 2. 配置检查与迁移
hermes config check
hermes config migrate

# 3. 全量状态
hermes status
hermes status --full

# 4. 诊断包（上传系统信息与日志，返回可分享链接）
hermes dump

# 5. 备份与恢复
hermes backup
hermes import
```

```text
健康检查要点：
1. 两条固定自检 —— hermes doctor（依赖/环境/配置版本）与 hermes config check（缺失与过期项）
2. 区分严重级别 —— ✓ 通过、! 可选未配、✗ 失败；只有失败项需要立刻处理
3. 认证排查 —— hermes model 里看 Provider 状态，OAuth 类用 hermes login 重新登录
4. 版本对齐 —— hermes doctor 会报配置版本（本机 v50）与 Deprecated 键，按提示 migrate
5. 求助材料 —— hermes dump 生成诊断摘要，/debug 上传日志并给分享链接
6. 回滚手段 —— hermes update 前默认做 quick 状态快照；state-snapshots/ 与 backups/ 里可找到副本
```

## 应用场景实战

### 场景一：全新 Ubuntu 服务器一键装机到可用（含接 DeepSeek 与自检）

需求：一台干净的 Ubuntu 24.04 机器，要用 DeepSeek 作为推理 Provider，脚本化完成「安装 → 写密钥 → 设模型 → 自检 → 打印结论」，失败即退出，便于重复执行。

```bash
#!/usr/bin/env bash
# bootstrap-hermes.sh —— 全新机器引导脚本（幂等，可重复执行）
set -euo pipefail

: "${DEEPSEEK_API_KEY:?请先 export DEEPSEEK_API_KEY=sk-xxx}"

echo "[1/5] 安装 Hermes Agent"
if command -v hermes >/dev/null 2>&1; then
  echo "已安装，跳过：$(hermes --version | head -1)"
else
  curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
  export PATH="$HOME/.local/bin:$PATH"
fi
command -v hermes >/dev/null || { echo "hermes 不在 PATH，检查安装输出"; exit 1; }

echo "[2/5] 写入 Provider 密钥（UPPER_SNAKE 键名会自动落到 ~/.hermes/.env）"
hermes config set DEEPSEEK_API_KEY "$DEEPSEEK_API_KEY"

echo "[3/5] 设置默认模型与 Provider"
hermes config set model.default deepseek-flash
hermes config set model.provider deepseek

echo "[4/5] 补齐缺失的配置项"
hermes config migrate || true    # 非交互环境下失败不阻塞

echo "[5/5] 自检"
hermes doctor
hermes config check
echo
echo "模型配置："
hermes config get model

echo "完成。执行 hermes 进入对话，或 hermes chat -q '你好' 做一次非交互验证。"
```

### 场景二：多环境配置管理（开发 / 预发 / 生产）与快速回滚

需求：同一个人维护三套环境，配置差异集中在模型、终端后端和审批模式上；希望配置可版本化、可一键切换、出问题能回滚。做法是把「稳定的基座」放进 git 管理的模板，把「环境差异」用脚本覆盖，用 Hermes 自带的备份做回滚点。

```bash
#!/usr/bin/env bash
# env-switch.sh <dev|staging|prod> —— 切换环境配置
set -euo pipefail
ENV_NAME="${1:?用法: env-switch.sh dev|staging|prod}"

case "$ENV_NAME" in
  dev)
    hermes config set model.default deepseek-flash
    hermes config set terminal.backend local
    hermes config set approvals.mode smart
    ;;
  staging)
    hermes config set model.default deepseek/deepseek-chat
    hermes config set terminal.backend docker
    hermes config set approvals.mode smart
    ;;
  prod)
    hermes config set model.default deepseek/deepseek-chat
    hermes config set terminal.backend ssh
    hermes config set approvals.mode manual     # 生产一律人工审批
    ;;
  *)
    echo "未知环境：$ENV_NAME"; exit 1;;
esac

echo "已切到 $ENV_NAME，当前关键配置："
hermes config get model
hermes config get terminal.backend
hermes config get approvals.mode
```

```bash
# 配套：备份 / 回滚操作
hermes backup                       # 打包 HERMES_HOME 到 zip
hermes import                       # 从 zip 恢复（回滚点）

# 配置目录版本化（只跟踪非敏感文件；.env、auth.json 一律不进 git）
cd ~/.hermes
git init 2>/dev/null || true
printf '%s\n' '.env' 'auth.json' 'state.db*' 'sessions/' 'logs/' 'cache/' > .gitignore
git add config.yaml SOUL.md skills/ && git commit -m "chore: 保存 hermes 配置基线"
```

```text
# 关键点
# 1) 环境差异集中在 model / terminal.backend / approvals.mode 三项，用脚本覆盖而不是维护三份完整 YAML
# 2) 生产环境把 approvals.mode 设回 manual，配合 terminal.backend=ssh 把 Agent 关在自己的代码之外
# 3) 版本化只跟踪 config.yaml、SOUL.md、skills/；.env 与 auth.json 属于密钥材料，必须排除
# 4) ssh 后端需要在 .env 里配 TERMINAL_SSH_HOST / TERMINAL_SSH_USER / TERMINAL_SSH_KEY
```

## 最佳实践与踩坑记录

### 最佳实践

1. 装机脚本固定幂等判断：先 `command -v hermes` 再决定是否安装，重复执行不产生副作用，这一条让运维脚本可以在任意时刻重跑
2. 密钥只走 `hermes config set`：`UPPER_SNAKE` 键名会被写入 `.env`（权限 600），而不是混进 `config.yaml` 被误提交进 git
3. 备份三件套分别对待：`config.yaml` 与 `SOUL.md` 进 git，`skills/` 进 git，`.env` 与 `auth.json` 只做加密备份，永远不进仓库
4. 升级前确认 `updates.pre_update_backup`：默认 `quick` 只快照关键状态文件，关键生产机建议设 `full`（额外打包整个 HERMES_HOME），代价是耗时变长
5. 生产环境收紧两处：`terminal.backend` 换成 `ssh` 或 `docker`（把 Agent 隔离在自己的代码之外），`approvals.mode` 保持 `manual`
6. 多环境用 profile 而不是多个安装目录：`hermes profile create` 各自独立配置与技能，比维护三套 `HERMES_HOME` 干净

### 踩坑记录

```text
坑 1：把 API Key 写进了 config.yaml
结论：密钥出现在会被提交的配置文件里，且 Hermes 未必读它。
原因：手写 YAML 绕过了 hermes config set 的分流逻辑——只有 UPPER_SNAKE 键名才会被路由到 .env。
解法：删掉 YAML 里的明文，改用 hermes config set DEEPSEEK_API_KEY sk-xxx；检查 git 历史并轮换该密钥，因为一旦提交即视为泄漏。

坑 2：Windows 首次运行报 HTTP 400 "No models provided"
结论：模型配置看起来正常，请求仍然被拒。
原因：config.yaml 被写成了带 UTF-8 BOM 的编码（Windows 记事本等工具常见），解析出的首个键名带不可见字符。
解法：用 hermes config edit 或带 BOM 选项的编辑器另存为 UTF-8（无 BOM）；编辑器里确认文件头没有 U+FEFF。

坑 3：改了 .env 里的密钥但模型仍然报认证失败
结论：磁盘上的密钥是新的，运行中的进程用的还是旧值。
原因：环境变量在进程启动时读取，部分安全相关开关在 import 时就快照了，中途修改不生效。
解法：CLI 退出重进，网关 /restart；会话内可用 /reload 重新载入 .env。

坑 4：macOS 用 Intel 机器装桌面安装包
结论：安装失败或应用无法启动。
原因：官方明确说明 macOS 安装包仅支持 Apple Silicon，x86 的 Intel Mac 不在受支持平台内。
解法：Intel Mac 改用命令行安装脚本（Linux/macOS/WSL2 同一条 curl 命令）。

坑 5：WSL2 里 hermes gateway install 之后服务起不来
结论：网关只能用 nohup 前台跑，关掉窗口就死。
原因：WSL2 默认不开 systemd，用户级服务无处托管。
解法：在 /etc/wsl.conf 里写 [boot] systemd=true，wsl --shutdown 重启；再 sudo loginctl enable-linger $USER。

坑 6：升级后出现 Deprecated 配置告警，不敢动
结论：功能可用但每次启动告警，长期会累积成真正的故障。
原因：版本演进会替换键名（例如 display.tool_progress_overrides → display.platforms），旧键被保留但不再推荐。
解法：按 hermes doctor 的提示执行 hermes config migrate（交互式补齐）或手动 hermes config set 新键、hermes config unset 旧键。
```
