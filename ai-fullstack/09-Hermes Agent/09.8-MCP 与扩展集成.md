## 概述

Hermes Agent 自身只内置一组固定工具（终端、文件、Web、浏览器、记忆、委派……）。当你要用的能力已经由别处实现——GitHub、数据库、内部 API、浏览器栈、逆向工程套件——最干净的做法不是再写一个原生工具，而是通过 MCP（Model Context Protocol）把那个外部工具服务器接进来。Hermes 在启动时读 `~/.hermes/config.yaml` 的 `mcp_servers` 段，连接每个服务器、自动发现它暴露的工具，然后把它们与内置工具一视同仁地注册进工具表。

MCP 是 Anthropic 提出的开放协议，官方把它比作「AI 应用的 USB-C 接口」：客户端（这里是 Hermes）与服务端（外部工具进程或远程端点）用统一的 JSON-RPC 约定交换「工具 / 资源 / 提示」三类能力。Hermes 在 MCP 生态里同时扮演三个角色：**客户端**（连别人的 MCP server）、**服务端**（`hermes mcp serve` 把自己的会话与消息平台暴露给别的 agent）、**目录消费者**（从 Nous 审过的 catalog 一键安装）。

```text
本篇要解决的问题：
1. mcp_servers 怎么配：stdio（本地子进程）与 HTTP（远程端点）两种传输的字段差异
2. 工具是怎么被发现并注册进工具表的，怎么按服务器过滤只想暴露的工具
3. 远程 MCP 的 OAuth 授权、mTLS、身份头怎么接
4. 怎么把 Hermes 自己变成 MCP 服务端给 Claude Code / 别的 agent 用
5. hermes mcp list / test / configure 与 mcp-stderr.log 的排错路径
```

本篇的配置字段与命令以本机实测（Hermes 版本见 `~/.hermes/logs/update_receipts/latest.json` 记录的 `0.21.6`，git 安装）为准；官方文档见 `https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp`、`https://hermes-agent.nousresearch.com/docs/reference/mcp-config-reference`，协议本身见 `https://modelcontextprotocol.io/`。

## MCP 与 Hermes 的三种角色

先把角色分清，后面的配置才不混。

| 角色 | 入口 | 谁启动谁 | 典型用途 |
|------|------|----------|----------|
| MCP 客户端 | `mcp_servers` 配置段 | Hermes 拉起 stdio 子进程 / 连远程 URL | 给 Agent 加外部工具 |
| MCP 服务端 | `hermes mcp serve` | 外部 MCP 客户端（Claude Code 等）拉起 Hermes | 让别的 agent 读写你的 Hermes 会话与消息 |
| 目录消费者 | `hermes mcp install <name>` | Hermes 自己 | 一键装 Nous 已审核的 MCP 条目 |

作为客户端时，Hermes 支持的传输只有两种：**stdio**（本地子进程，走 stdin/stdout）与 **HTTP/SSE**（远程端点）。选哪种的判断很简单——服务器跑在本机就用 stdio，托管在别处或组织内部有内部端点就用 HTTP。

```text
三种角色要点：
1. 作为客户端时，Hermes 每启动一个会话就按 mcp_servers 连接所有 enabled 的服务器
2. stdio 服务器是 Hermes 的子进程，URL 服务器是外部服务，两者配置字段完全不同（command/args/env 对 url/headers）
3. hermes mcp serve 是反向用法，Hermes 变成被连接的一方，且目前只提供 stdio 传输
4. 内置工具与 MCP 工具在工具表里地位相同，都可以被 /tools、hermes tools 单独开关
5. MCP 支持随标准安装自带，不需要额外安装步骤
```

## 注册 MCP 服务器：stdio 与 HTTP

配置写在 `~/.hermes/config.yaml` 的顶层 `mcp_servers:` 段，每个键是一个服务器名。本机现网就有一条 stdio 记录（真实 `config.yaml` 节选）：

```yaml
# ~/.hermes/config.yaml
mcp_servers:
  rea:
    command: /root/.hermes/tools/node-26.7.0-linux-x64/bin/rea
    args:
      - mcp
    enabled: true
```

stdio 服务器的字段：`command`（可执行文件）、`args`（参数列表）、`env`（传给子进程的环境变量，常用来放令牌）、`enabled`。HTTP 服务器的字段换成 `url`、`headers`。同一段里两种可以混写：

```yaml
mcp_servers:
  # 本地 stdio：npx 拉起的 filesystem 服务器，只开放一个受限目录
  filesystem:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-filesystem", "/srv/knowledge"]
    env:
      LOG_LEVEL: "info"

  # 远程 HTTP：内部只读查询端点
  company_api:
    url: "https://mcp.internal.example.com/mcp"
    headers:
      Authorization: "Bearer ${COMPANY_MCP_TOKEN}"
    enabled: true
```

完整的字段一览（来自官方 MCP 配置参考）：

| 键 | 类型 | 适用 | 含义 |
|----|------|------|------|
| `command` / `args` / `env` | string / list / mapping | stdio | 可执行文件、参数、子进程环境变量 |
| `url` / `headers` | string / mapping | HTTP | 远程端点与请求头 |
| `transport` | string | HTTP | 置为 `sse` 时用 SSE 传输，否则 Streamable HTTP |
| `ssl_verify` | bool 或 string | HTTP | TLS 校验：`true` 用系统 CA，`false` 关校验（不安全），字符串为自定义 CA bundle 路径 |
| `client_cert` / `client_key` | string 或 list | HTTP | mTLS 客户端证书：单个合并 PEM 路径，或 `[cert, key]`、`[cert, key, password]` |
| `identity_header` | mapping | HTTP | 逐请求身份头：`{name, value_from: static 或 profile, value}` |
| `timeout` | number | both | 工具调用超时（秒，默认 300） |
| `connect_timeout` | number | both | 首次连接超时（秒，默认 60），也约束 MCP `initialize` 握手 |
| `idle_timeout_seconds` | number | both | stdio 服务器空闲这么久后回收（0 = 不回收），下次调用透明重启 |
| `max_lifetime_seconds` | number | both | stdio 服务器总存活上限（0 = 不限） |
| `enabled` | bool | both | 置 `false` 则完全跳过该服务器 |
| `supports_parallel_tool_calls` | bool | both | 允许该服务器工具并发执行 |
| `tools` | mapping | both | 逐服务器工具过滤与 utility 策略（见下节） |

也可以不手写 YAML，用命令写：`hermes mcp add` 接受 `--url`（HTTP）或 `--command`（stdio），`--args` 必须是最后一个选项，另有 `--env KEY=VALUE`、`--auth {oauth,header}`、`--preset`、`--connect-timeout`。

```shell
# 追加一个 stdio 服务器（--args 必须放最后）
hermes mcp add filesystem --command npx --args -y @modelcontextprotocol/server-filesystem /srv/knowledge

# 追加一个远程 HTTP 服务器并走 OAuth
hermes mcp add linear --url https://mcp.linear.app/mcp --auth oauth

# 想少查文档：preset 帮你填好传输细节（目前官方列出 codex 一个 preset）
hermes mcp add codex --preset codex

# 删除
hermes mcp remove filesystem
```

```text
注册要点：
1. stdio 用 command/args/env，HTTP 用 url/headers，互斥不能混填
2. 令牌类字段一律用 ${VAR} 从 .env 引用，不要明文写进 config.yaml
3. timeout 默认 300s、connect_timeout 默认 60s，冷启动慢的服务器（npx、重型二进制）调大
4. 浏览器类 MCP（如 @playwright/mcp）会常驻一整个 Chromium，用 idle_timeout_seconds / max_lifetime_seconds 让它定时回收
5. 改完 config.yaml 后会话内会触发自动重载（30s 超时）；OAuth 这类需要人工授权的操作要在新终端里跑 hermes mcp login
```

## 工具自动发现与工具过滤

Hermes 连接一个 MCP 服务器后，会调用它的 `tools/list`，把返回的每个工具按 `<server>:<tool>` 的命名注册进工具表——例如 `github:create_issue`。`hermes tools` 的说明里明确写了这个记法，所以 MCP 工具可以用和内置工具一样的开关命令管理。

```shell
# 查看全部工具（含 MCP）在各平台的启用状态
hermes tools list

# 只关掉某个 MCP 工具，不动内置工具
hermes tools disable github:delete_repo

# 启用
hermes tools enable github:create_issue
```

如果一个服务器工具太多、其中又混着破坏性操作（删仓库、删工作区），更稳的做法是在服务器层面过滤，只把它暴露给 Agent 需要的子集。配置写在服务器的 `tools` 子块：

```yaml
mcp_servers:
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "${GITHUB_TOKEN}"
    tools:
      include:                 # 白名单：只暴露列出的工具
        - list_issues
        - get_issue
        - create_issue
      exclude: []              # 黑名单：从可暴露集合里剔除
      resources: true          # 是否暴露 MCP resources（服务器支持时）
      prompts: true            # 是否暴露 MCP prompts
```

官方规则是：`include` 非空时只有列出的工具进入注册表；`exclude` 在其后生效。若两者都没写、等于全量暴露。如果 `include` 覆盖了服务器的全部工具，官方会干脆不写过滤（配置形状最干净、行为等价）。另外 `lazy: true` 可以让服务器工具先用磁盘上的 schema 缓存注册，等真正被调用时才连接。

目录安装的交互式清单（`hermes mcp configure`）写的就是同一个 `tools.include`：勾选哪些就写哪些，全选则不写过滤。

```text
工具发现与过滤要点：
1. MCP 工具统一以 server:tool 命名，可以直接用 hermes tools enable/disable 精确开关
2. 工具清单是连接时（启动或重载）拉取的，服务器新增工具后要重连或 /reload-mcp 才可见
3. tools.include 做白名单，tools.exclude 做黑名单，二者都在服务器层面生效，优先于平台级开关
4. 暴露第三方服务器时默认反向选择——先全关，再按需开，而不是先全开后删
5. lazy 让工具先以缓存 schema 注册，避免为一次可能用不到的调用付冷启动代价
```

## OAuth 与远程服务接入

托管的远程 MCP 服务器（Linear、Sentry、Atlassian、Figma、Stripe 等）大多要求 OAuth 2.1，而不是静态 bearer token。在配置里写 `auth: oauth`，Hermes 会用 MCP Python SDK 完成发现、客户端标识、PKCE、令牌交换、刷新与 step-up 授权——全部自动，无需你配任何客户端参数。

```yaml
mcp_servers:
  linear:
    url: "https://mcp.linear.app/mcp"
    auth: oauth
```

首次连接时 Hermes 打印授权 URL，尽量自动开浏览器，并在本地回环端口等回调。令牌缓存在 `~/.hermes/mcp-tokens/<server>.json`，权限 0o600，之后静默复用直到刷新失败。手动触发授权的命令是 `hermes mcp login <server>`，重授权用 `hermes mcp reauth <server>`（或 `--all`）。

三种常见的远程接入变形：

| 场景 | 配置手段 | 说明 |
|------|----------|------|
| 远程 / 无头主机（浏览器在别的机器） | 交互终端里粘贴回调 URL，或 `ssh -N -L <port>:127.0.0.1:<port>` | 回环回调够不到你的笔记本时用 |
| 有公网 HTTPS 反代 / Tailscale Funnel | `oauth.redirect_port` + `oauth.redirect_uri` | 浏览器重定向自己就能回到 Hermes |
| 服务器不支持动态注册（Google Drive、Atlassian） | `oauth.client_id` + `oauth.client_secret` | 自己在厂商控制台建 OAuth 应用后填进来 |

```yaml
mcp_servers:
  myserver:
    url: "https://mcp.example.com/mcp"
    auth: oauth
    oauth:
      redirect_port: 8765                              # 固定端口，便于反代对准
      redirect_uri: "https://oauth.example.ts.net/callback"
  googledrive:
    url: "https://drivemcp.googleapis.com/mcp/v1"
    auth: oauth
    oauth:
      client_id: "${GOOGLE_DRIVE_CLIENT_ID}"
      client_secret: "${GOOGLE_DRIVE_CLIENT_SECRET}"
```

需要 mTLS 的内部端点用 `client_cert` / `client_key`；需要按调用者身份做审计或多租户路由的端点用 `identity_header`，其中 `value_from: profile` 会把当前 Hermes profile 名作为身份发出。若服务器前置了 WAF 且会 403 掉含字面量 `127.0.0.1` 的授权请求，设 `oauth.redirect_host: localhost` 换成 `http://localhost:<port>/callback` 即可（回调监听仍绑 127.0.0.1）。

```text
OAuth 与远程接入要点：
1. auth: oauth 是唯一的远程授权开关，DCR 与 CIMD 客户端标识都是自动的
2. 令牌落在 ~/.hermes/mcp-tokens/，0o600，别手工编辑
3. 无头主机要么粘贴回调、要么 SSH 端口转发、要么配 redirect_uri 走反代
4. 不支持动态注册的服务器必须自带 client_id/client_secret，否则 hermes mcp login 能列出工具但真实调用全部超时
5. identity_header 在 stdio 服务器上会被忽略并告警（stdio 没有 headers）
```

## 把 Hermes 作为 MCP 服务端

`hermes mcp serve` 把 Hermes 变成一个 stdio MCP 服务器，对外暴露 10 个工具，用来读写你的消息平台会话——本质是一个「渠道桥」。生命周期由 MCP 客户端管理，不是你手动跑。

```shell
# 正常模式（客户端拉起，stderr 上打调试日志）
hermes mcp serve

# 调试模式
hermes mcp serve --verbose
```

接进别的 MCP 客户端（以 Claude Code 的配置为例，官方给出的形状）：

```json
{
  "mcpServers": {
    "hermes": {
      "command": "hermes",
      "args": ["mcp", "serve"]
    }
  }
}
```

如果 Hermes 装在特定位置，把 `command` 换成绝对路径，例如 `/home/user/.hermes/hermes-agent/venv/bin/hermes`。

暴露的 10 个工具：

| 工具 | 作用 |
|------|------|
| `conversations_list` | 列出活跃消息会话，可按平台过滤或按名字搜索 |
| `conversation_get` | 按 session key 取单个会话详情 |
| `messages_read` | 读某会话最近的聊天记录 |
| `attachments_fetch` | 从指定消息里取出非文本附件（图片、媒体） |
| `events_poll` | 从游标位置起轮询新事件（非阻塞） |
| `events_wait` | 长轮询 / 阻塞直到下一个事件到达（近实时） |
| `messages_send` | 通过平台发消息，如 `telegram:123456`、`discord:#general` |
| `channels_list` | 列出所有平台上的可用消息目标 |
| `permissions_list_open` | 列出本次桥接会话观察到的待审批请求 |
| `permissions_respond` | 允许或拒绝一个待审批请求 |

事件类型有 `message`、`approval_requested`、`approval_resolved` 三种。事件队列是内存态、桥接连接时开始累积；更早的历史要用 `messages_read` 取。

关键的运行前提：**读操作不需要网关在跑，写操作需要**。读会话、读历史、轮询事件都直接读 `~/.hermes/state.db`；发消息则要平台适配器有活跃连接，也就是网关必须在运行。另外官方明确说明：`hermes mcp serve` 目前只提供 stdio，没有 HTTP 形态；事件轮询大约 200ms 一次，且没有推送通知协议。

```shell
# 服务端侧只保证 stdio 服务能起来；客户端侧连上后应能列出上面 10 个工具
hermes mcp serve --verbose
```

```text
服务端要点：
1. hermes mcp serve 是 stdio-only，要被 MCP 客户端拉起，不要当成常驻服务自己后台跑
2. 10 个工具覆盖「列会话 / 读消息 / 取附件 / 轮询事件 / 发消息 / 回审批」
3. 读走 state.db，不依赖网关；发消息依赖网关与平台连接
4. events_wait 用于近实时唤醒，events_poll 用于批处理，别拿 messages_read 做轮询
5. 发送仅支持文本，附件发送暂不支持
```

## 目录安装与凭据管理

Hermes 自带一份 Nous 审核过的 MCP 目录（仓库里的 `optional-mcps/`），条目默认关闭，只装你要的。三种入口：

```shell
hermes mcp                # 交互式 picker（默认行为）
hermes mcp catalog        # 纯文本列表，可脚本处理
hermes mcp install n8n    # 按名字装一个目录条目
```

本机实测的 `hermes mcp catalog` 输出（节选，真实输出）：

```text
MCP Catalog + configured servers:

  Name               Status                   Description
  ------------------ ------------------------ -----------
  airtable           available                Bases, tables, and records from your Airtable workspace.
  algolia            available                Algolia search: indices, analytics, and settings (read-only).
  atlassian          available                Jira issues and Confluence pages via Atlassian's hosted remote MCP.
  context7           available                Up-to-date, version-specific library docs and code examples.
  deepwiki           available                Ask questions about any public GitHub repo (Devin's DeepWiki).
  figma              available                Official Figma remote MCP — design context, Code Connect, and write-to-canvas via https://mcp.figma.com/mcp (OAuth).
  linear             available                Find, create, and update Linear issues, projects, and comments.
  ...
```

目录条目安装后可能需要凭据：API key 在安装时提示并写进 `~/.hermes/.env`；OAuth 类写成 `auth: oauth`，首次连接开浏览器；第三方 provider（Google/GitHub）会指引你先跑 `hermes auth <provider>`。凭据配好后 Hermes 探测服务器并给出工具勾选清单，勾中的写进 `mcp_servers.<name>.tools.include`。若探测失败（服务器不可达、OAuth 未完成），安装依然成功：套用 manifest 的 `tools.default_enabled`，或干脆不写过滤，之后用 `hermes mcp configure <name>` 补勾。

两个重要事实：

- 条目在 `transport.command`、`transport.args`、`transport.url`、`headers` 里支持 `${VAR}` 占位符，在连接时从环境变量（含 `~/.hermes/.env` 的全部内容）解析；另有一组 Cursor 风格变量 `${userHome}`、`${workspaceFolder}`、`${workspaceFolderBasename}`、`${pathSeparator}`。
- 安装目录条目会执行 manifest 指定的 `git clone` 与 `bootstrap`（`pip install`、`npm install` 等）。manifest 经过 Nous 的 PR 审核，但官方仍建议动手前读一遍 manifest 的 `source:`、`install.bootstrap:` 与 `transport.command:`。

MCP 不会自动升级：Hermes 大版本更新后 manifest 版本可能变化，要重新 `hermes mcp install <name>`。一个已知例外是 GitHub——官方有意不收录：其托管 MCP 要求每个客户端自带 OAuth 应用（通用动态客户端注册被拒），而 Hermes 自带的 `github/*` 技能驱动 `gh` CLI 能力更强。

```shell
# 供应链审计：会扫描 config.yaml 里 pin 的 npx/uvx MCP 服务器
hermes security audit
hermes security audit --fail-on high --json
```

```text
目录与凭据要点：
1. 目录条目默认关闭，装什么开什么；catalog 是纯文本可脚本化，picker 是交互式
2. 凭据分流：密钥进 ~/.hermes/.env，非密钥（base URL 之类）也进同一文件，config.yaml 只用 ${VAR} 引用
3. 安装会执行上游的 clone 与 bootstrap，安装前读 manifest 的 source 与 bootstrap
4. MCP 不自动升级，Hermes 更新后按需重装条目
5. hermes security audit 会把 pin 住的 npx/uvx MCP 服务器纳入 OSV.dev 漏洞扫描
```

## 调试与排错

排错的主线是三步：确认服务器在配置里且 enabled、确认能连上并发现工具、确认工具真的能被调用。

```shell
# 1) 看一眼现在配了哪些服务器
hermes mcp list

# 2) 真实连接一次，打印传输方式、鉴权、连接耗时与发现的工具数
hermes mcp test rea

# 3) 调整某个服务器暴露的工具
hermes mcp configure rea

# 4) 重授权一个（或全部）OAuth 服务器
hermes mcp reauth --all
```

本机实测 `hermes mcp list`（真实输出）：

```text
MCP Servers:

  Name             Transport                      Tools        Status
  ──────────────── ────────────────────────────── ──────────── ──────────
  rea              /root/.hermes/tools/node-...   all          ✓ enabled
```

本机实测 `hermes mcp test rea`（真实输出，节选）：

```text
Testing 'rea'...
  Transport: stdio → /root/.hermes/tools/node-26.7.0-linux-x64/bin/rea
  Auth: none
  ✓ Connected (10313ms)
  ✓ Tools discovered: 170

    annotate_native_function             Atomically update one function name and/or entry commen...
    inspect_native_load_image            Verify the provider's loaded DOS MZ or explicitly selec...
    procedure_pseudo_code                Decompile one analyzed procedure by symbol name or...
    ...
```

注意连接耗时 10313ms —— 重型 stdio 服务器（Node 二进制、要在 `initialize` 里加载大模型/插件的）首次连接就是十秒级，这直接决定 `connect_timeout` 该给多少。

stdio 服务器的 stderr 会落到 `~/.hermes/logs/mcp-stderr.log`，这是服务器崩溃、版本不兼容、认证失败时最直接的证据：

```text
2026-10-14 23:44:08,079 ===== starting MCP server 'rea' =====
2026-10-15 00:33:19,160 ===== starting MCP server 'rea' =====
2026-10-15 08:34:40,050 ===== starting MCP server 'rea' =====
```

同一条服务器名反复出现「starting」而没有任何后续日志，通常意味着进程起来又退出（命令路径不对、缺运行时、依赖缺失）。日志统一入口是 `hermes logs`：

```shell
hermes logs list                      # 列出所有日志文件与大小/时间
hermes logs mcp-stderr -n 100         # 看 MCP 子进程 stderr
hermes logs errors -n 50              # 看错误日志
hermes logs agent --component tools   # 按组件过滤
```

```text
调试与排错要点：
1. 顺序永远是 list → test → 调用；test 会打印传输、鉴权、连接耗时与工具数
2. 工具数为 0 说明连上了但 tools/list 空 —— 一般是服务器侧工具没启用或过滤把它全排掉了
3. stdio 的问题先看 ~/.hermes/logs/mcp-stderr.log，反复 starting 无后续 = 子进程起不来
4. 远程服务器「能列出工具但调用全超时」是动态注册失败的典型症状（见 OAuth 一节）
5. 会话内改 config.yaml 触发的自动重载只有 30s 超时，需要人工授权时改用新终端的 hermes mcp login
```

## 应用场景实战

### 场景一：接入本机一个重型 stdio MCP 服务器并验证工具注册

目标：把一个已在磁盘上的 stdio MCP 服务器（本机是逆向工程套件 `rea`，Node 二进制）写进配置，验证它真的连上并注册了全部工具。这是最典型的「本地工具接入」流程。

```shell
# 1) 先确认可执行文件存在且能跑
ls -l /root/.hermes/tools/node-26.7.0-linux-x64/bin/rea

# 2) 写入配置（也可以直接编辑 ~/.hermes/config.yaml 的 mcp_servers 段）
hermes mcp add rea \
  --command /root/.hermes/tools/node-26.7.0-linux-x64/bin/rea \
  --args mcp
```

```yaml
# 等价的手写配置：重型服务器把超时给足
mcp_servers:
  rea:
    command: /root/.hermes/tools/node-26.7.0-linux-x64/bin/rea
    args:
      - mcp
    enabled: true
    connect_timeout: 120            # 实测首次连接约 10s，给足余量
    timeout: 300
    idle_timeout_seconds: 1800      # 半小时不用就回收，避免常驻进程堆积
```

```shell
# 3) 验证：列出 + 真实连接测试，确认工具数与连接耗时
hermes mcp list
hermes mcp test rea
```

真实输出对照（本机实测）：

```text
$ hermes mcp test rea
Testing 'rea'...
  Transport: stdio → /root/.hermes/tools/node-26.7.0-linux-x64/bin/rea
  Auth: none
  ✓ Connected (10313ms)
  ✓ Tools discovered: 170
```

工具数 170 就是「注册成功」的硬证据——它等于服务器 `tools/list` 的返回条数，也等于这些工具进入工具表的条数。随后在会话里，这些工具可以直接按 `<server>:<tool>` 记法开关：

```shell
hermes tools list
hermes tools disable rea:set_inline_comment      # 不想让 Agent 写汇编注释就关掉
```

关键点：`hermes mcp test` 是唯一能在不进入会话的情况下把「传输 / 鉴权 / 连接耗时 / 工具数」一次打全的命令，接新服务器的第一步就该跑它。若工具数明显少于预期，先看 `mcp-stderr.log` 再怀疑过滤配置。

### 场景二：给 Agent 开放一个受限目录（filesystem MCP + 工具过滤）

目标：让 Agent 能读一个知识库目录，但只通过 MCP 的受控通道，且只暴露读类工具。这个模式适合把「文件访问」和「终端访问」的权限边界分开。

```yaml
# ~/.hermes/config.yaml
mcp_servers:
  kb_fs:
    command: "npx"
    args:
      - "-y"
      - "@modelcontextprotocol/server-filesystem"
      - "/srv/knowledge"          # 只挂载这一个目录，服务器侧就限定了根
    env:
      LOG_LEVEL: "info"
    connect_timeout: 90           # npx 首次要下包，给足时间
    idle_timeout_seconds: 900     # 15 分钟不用就回收子进程
    tools:
      include:                    # 白名单：只给读与检索
        - read_file
        - read_multiple_files
        - list_directory
        - search_files
        - directory_tree
      resources: true
```

```shell
# 1) 先单独验证服务器本身能起来（不依赖 Hermes）
npx -y @modelcontextprotocol/server-filesystem /srv/knowledge --help 2>&1 | head -5

# 2) 通过 Hermes 验证注册
hermes mcp test kb_fs

# 3) 确认白名单生效：这些工具在表里，写类工具不在
hermes tools list | grep kb_fs
```

```text
# 期望形状（实际工具名与条数以该服务器当前版本为准，本机未安装此包）：
$ hermes mcp test kb_fs
Testing 'kb_fs'...
  Transport: stdio → npx
  Auth: none
  ✓ Connected (4210ms)
  ✓ Tools discovered: 12
```

关键点：服务器侧的 `args` 已经把根目录钉死在 `/srv/knowledge`，这是比「让 Agent 自己别乱走」强得多的约束；`tools.include` 是第二道闸，把写类工具从注册表里摘掉——被摘掉的工具不是「禁区」，而是根本不存在于工具表，模型不会去尝试调用。上面这段连接耗时与工具数仅为形状示例，以你自己跑出来的为准。

### 场景三：把 Hermes 作为 MCP 服务端接进 Claude Code

目标：在另一个 agent（Claude Code）里查询和回复你的 Hermes 消息平台会话，避免在两套工具之间切来切去。

```json
{
  "mcpServers": {
    "hermes": {
      "command": "/home/lw/.hermes/hermes-agent/venv/bin/hermes",
      "args": ["mcp", "serve"]
    }
  }
}
```

```shell
# 先用 verbose 在终端里手工验证一次服务端能起来（Ctrl+C 退出）
/home/lw/.hermes/hermes-agent/venv/bin/hermes mcp serve --verbose

# 服务端需要读会话数据：确认 state.db 可读
ls -l /home/lw/.hermes/state.db

# 需要「发消息」能力时，确认网关在跑
systemctl is-active hermes-gateway
```

```text
# 客户端连上后应当能看到这 10 个工具：
conversations_list / conversation_get / messages_read / attachments_fetch
events_poll / events_wait / messages_send / channels_list
permissions_list_open / permissions_respond
```

关键点：读类工具（列会话、读历史、轮询事件）只依赖 `state.db`，网关没跑也能用；`messages_send` 依赖平台适配器有活跃连接，网关必须运行。事件队列是内存态的，桥接进程重启后从零开始累积——需要历史就调 `messages_read`，不要指望 `events_poll` 能翻旧账。

## 最佳实践与踩坑记录

### 最佳实践

1. 新接一个 MCP 服务器，先 `hermes mcp test <name>` 再进会话；连接耗时与工具数是最有价值的两条信息
2. 令牌、base URL 等外部值全部走 `${VAR}` 从 `~/.hermes/.env` 引用，`config.yaml` 里不留明文
3. 第三方服务器默认最小暴露：先 `tools.include` 白名单，再按需放开，而不是全开后再删高危工具
4. 重型 stdio 服务器（Node 二进制、npx 拉包、会常驻浏览器）显式配 `connect_timeout` 与 `idle_timeout_seconds`，否则冷启动会超时、常驻会吃内存
5. 远程 OAuth 服务在无头主机上优先用 `oauth.redirect_uri` + 反代/隧道，退而求其次才用粘贴回调
6. 装目录条目之前读一遍 manifest 的 `source:` 与 `install.bootstrap:`，别把 `git clone` + 安装脚本当黑盒
7. 把 MCP 服务器纳入供应链巡检：`hermes security audit` 会扫 config.yaml 里 pin 住的 npx/uvx 服务器

### 踩坑记录

```text
坑 1：hermes mcp add 的 --args 后面跟其他选项，参数被吃掉
结论：服务器注册了但 args 不完整，启动即失败，mcp-stderr.log 里反复出现 starting 无后续。
原因：--args 是「吃剩余全部参数」的选项，官方文档明确要求它必须放在命令行最后。
解法：--args 永远放最后；要用 --env 之类，把它们写在 --args 之前。

坑 2：远程服务器能列出工具，但每次真实调用都超时
结论：hermes mcp login 看起来成功了（能 list tools），实际一个工具也调不通。
原因：该服务器不支持动态客户端注册（RFC 7591），而它又不带鉴权地响应 tools/list，于是「列工具成功」造成了假象；没有令牌落地，真实调用全部超时。
解法：在厂商控制台自建 OAuth 应用，配置 oauth.client_id / oauth.client_secret 后重新 hermes mcp login；新版 hermes mcp login 会校验令牌是否真的落盘。

坑 3：会话内改 config.yaml 触发了自动重载，OAuth 授权来不及完成
结论：刚加的 OAuth 服务器连接失败，报授权超时。
原因：在运行中的 Hermes 会话里编辑 config.yaml 会触发 MCP 自动重载，而这条路径的超时是 30s；交互式 OAuth 流程远超 30s。
解法：配置写好后不要在会话里等，改在新终端跑 hermes mcp login <server>，它会给满 5 分钟。

坑 4：npx 类 MCP 服务器第一次测试就连接超时
结论：hermes mcp test 报连接失败，但手工跑同样的 npx 命令又能起来。
原因：首次运行要把包下载到 npx 缓存，connect_timeout 默认 60s 在这种场景下不够（且受网络影响）。
解法：给该服务器显式配 connect_timeout（如 120），或先在终端手工跑一次把包预热到缓存。

坑 5：浏览器类 MCP 让机器内存持续上涨
结论：接上 @playwright/mcp 之后，即使不用它，内存也被一个常驻 Chromium 占住。
原因：浏览器 MCP 服务器首次工具调用后会保留整个 Chromium 实例，默认不回收。
解法：配 idle_timeout_seconds 与 max_lifetime_seconds，让它在空闲或超龄后透明回收；下次调用时自动重启，工具保持注册不变。

坑 6：把 hermes mcp serve 当成常驻服务自己后台起来
结论：进程起来了但没有任何客户端能连上，日志也没有握手记录。
原因：MCP 的 stdio 传输必须由客户端拉起并持有管道；独立后台进程没有 stdin/stdout 对端。
解法：让 MCP 客户端在它的配置里用 command/args 拉起 hermes mcp serve，不要手动常驻。
```
