## 概述

Hermes Agent 的核心是一个对话循环加一套工具，它的「前端」则有好几个：终端里的经典 REPL、现代 TUI、编辑器里的 ACP、桌面应用连的后端服务，以及最常用的一种——消息平台。网关（gateway）就是把这套核心接上 Telegram、Discord、Slack、QQ、微信、飞书等平台的那一层：一个后台进程同时连上所有已配置平台，按聊天维护会话，顺带跑 cron 调度与语音投递。

多平台接入的价值在于「同一个 agent 换个界面出现」：同一个系统提示、同一批工具、同一份记忆，你在手机上用 Telegram 发一句话，和你在终端里敲一句话，走的是同一条推理与执行路径。代价是你必须理解会话边界、鉴权与安全策略——一个能被陌生人私聊的 agent 和一个只能被你私聊的 agent，配置差别很大。

```text
本篇要解决的问题：
1. CLI / TUI / ACP / Desktop / 后端服务各是什么形态，什么场景选哪个
2. 网关进程怎么起、怎么常驻、平台凭据放在哪里
3. 平台级配置项（require_mention、allowed_channels、channel_overrides）怎么影响行为
4. 语音（STT/TTS）与媒体附件的能力边界
5. 配对授权、审批弹窗与静默令牌这三道安全闸怎么用
```

本篇命令与配置以本机实测为准（网关以 systemd system 级服务 `hermes-gateway.service` 运行，平台为 QQ Bot）；官方文档见 `https://hermes-agent.nousresearch.com/docs/user-guide/messaging/` 与 `https://hermes-agent.nousresearch.com/docs/reference/cli-commands`。

## 前端形态：CLI 与 TUI

同一套核心，不同外壳。选择依据是你在哪、要不要图形能力、要不要被别的程序驱动。

| 形态 | 启动方式 | 适合 |
|------|----------|------|
| 经典 CLI（REPL） | `hermes` 或 `hermes --cli` | 本地交互开发，依赖 prompt_toolkit 的键位习惯 |
| TUI | `hermes --tui`（或 `display.interface: tui`） | 需要更好的滚动、状态栏、鼠标与多行编辑 |
| 单次问答 | `hermes -z "..."` 或 `hermes chat -q "..." --oneshot` | 脚本 / 管道 / CI |
| ACP 服务 | `hermes acp` | VS Code、Zed、JetBrains 等编辑器集成 |
| 桌面应用后端 | `hermes serve` | 桌面 app 与远程客户端连接的无头后端 |
| Web 控制台 | `hermes dashboard` | 浏览器里管理配置、密钥与会话 |
| 消息平台 | 网关进程 | 手机 / 群里随时喊 agent |

```shell
# 经典 REPL（默认）与 TUI
hermes
hermes --tui
hermes --cli                 # 覆盖 display.interface: tui，强制回经典 REPL
hermes --tui --resume latest --in ./repo    # 在指定目录恢复最近会话

# 脚本化：-z 只打印最终文本，不打印横幅/工具预览/会话 ID
hermes -z "把 /var/log/syslog 里的 ERROR 行按来源统计一下"
hermes -z "总结这次发版" --usage-file /tmp/usage.json

# 编辑器集成（Agent Client Protocol）
hermes acp --check           # 校验 ACP 依赖与适配器导入
hermes acp --setup           # 交互式配置 ACP 用的 provider/model
hermes acp                   # 真正启动 ACP 服务（编辑器来拉起）
```

`hermes serve` 是桌面应用与远程客户端连的后端（JSON-RPC/WebSocket），默认监听 `127.0.0.1:9119`：

```shell
hermes serve                          # 默认 127.0.0.1:9119
hermes serve --port 9119 --host 127.0.0.1
hermes serve --status                 # 看后端状态
# 注意：--insecure 已废弃为 no-op，非回环绑定始终要求认证（密码或 OAuth）
```

```text
前端形态要点：
1. CLI 与 TUI 只是同一会话数据的两个渲染器，--cli / --tui 可逐次切换
2. -z/--oneshot 是给管道用的：只输出最终回答，退出码与 --usage-file 便于计费
3. 编辑器走 ACP（stdio 上的协议），不是 MCP，也不要混淆
4. hermes serve 是无头后端，必须配认证才能对外绑定；--insecure 已失效
5. 前端变了，工具、记忆、skill 都不变——这是「多平台接入」的意义所在
```

## 网关架构与生命周期

网关是单个后台进程，职责有四块：接收各平台消息、按聊天路由到会话存储、派发给 AIAgent 处理、投递回复（含语音）。它同时承担 cron 调度器的角色，每 60 秒 tick 一次执行到期任务。

```shell
hermes gateway run                 # 前台运行（WSL / Docker 里推荐这种）
hermes gateway setup               # 交互式配置消息平台
hermes gateway install             # 装成用户级服务（Linux user service / macOS launchd）
sudo hermes gateway install --system   # 仅 Linux：装成开机启动的系统级服务
hermes gateway start / stop / restart
hermes gateway status              # 看默认服务状态
hermes gateway status --system     # 明确检查系统级服务（仅 Linux）
hermes gateway list                # 列出所有 profile 及其网关状态
```

`hermes gateway install` 的选项是运维要点所在：

| 选项 | 作用 |
|------|------|
| `--system` | 装成 Linux 系统级服务（开机启动） |
| `--run-as-user <user>` | 系统级服务以哪个用户运行 |
| `--start-now` / `--no-start-now` | 装完后是否立刻启动 |
| `--start-on-login` / `--no-start-on-login` | 是否开机/登录时自动启动 |
| `--force` | 强制重装，即使默认 multiplexer 已服务该 profile |
| `--if-missing` | 已经装了就当无事发生 |

系统级服务长什么样——本机 `/etc/systemd/system/hermes-gateway.service` 的真实内容（节选）：

```ini
[Unit]
Description=Hermes Agent Gateway - Messaging Platform Integration
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=0

[Service]
Type=simple
User=lw
Group=lw
WorkingDirectory=/home/lw/.hermes
Environment="HOME=/home/lw"
Environment="HERMES_HOME=/home/lw/.hermes"
Environment="HERMES_SUPERVISED_CHILD=1"
Restart=always
RestartSec=5
TimeoutStopSec=210
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

注意 `HERMES_HOME` 被显式写进 unit——这决定了服务读哪个 config.yaml、哪个 state.db、哪个 skills 目录。多 profile 环境下搞错这一项，表现为「网关在跑但配置不生效」。

网关还能选配 systemd 看门狗，覆盖「asyncio 事件循环整体卡死」这种 platform liveness 任务也救不回来的情况：

```yaml
# ~/.hermes/config.yaml
gateway:
  systemd_watchdog_seconds: 120     # 正数 → 生成的 unit 用 Type=notify + WatchdogSec
```

```shell
# 改了上面这项后必须重新生成 unit，否则 WatchdogSec 不会出现
hermes gateway install --force
```

```text
网关生命周期要点：
1. 单进程多平台：一个网关进程同时连所有已配置平台，不是每平台一个进程
2. hermes gateway run 前台跑（WSL/Docker），install 装服务，start/stop/restart 管服务
3. unit 里的 HERMES_HOME 决定读哪套配置与数据，多 profile 时最容易错在这
4. systemd_watchdog_seconds > 0 才启用 Type=notify 看门狗，改完要 install --force 重生成 unit
5. 网关同时跑 cron ticker（60s 一次），停网关等于停定时任务
```

## 消息平台接入

官方支持的平台很广，能力差异也很大（语音、图片、文件、线程、表情回应、输入状态、流式更新各不相同）。下表按官方平台对比整理，只列常用的：

| 平台 | 语音 | 图片 | 文件 | 线程 | 反应 | 输入中 | 流式 |
|------|------|------|------|------|------|--------|------|
| Telegram | 是 | 是 | 是 | 是 | 否 | 是 | 是 |
| Discord | 是 | 是 | 是 | 是 | 是 | 是 | 是 |
| Slack | 是 | 是 | 是 | 是 | 是 | 是 | 是 |
| WhatsApp | 否 | 是 | 是 | 否 | 否 | 是 | 是 |
| Signal | 否 | 是 | 是 | 否 | 否 | 是 | 否 |
| Email | 否 | 是 | 是 | 是 | 否 | 否 | 否 |
| Matrix | 是 | 是 | 是 | 是 | 是 | 是 | 是 |
| 飞书 / Lark | 是 | 是 | 是 | 是 | 是 | 是 | 是 |
| 企业微信 WeCom | 是 | 是 | 是 | 否 | 否 | 否 | 否 |
| 微信 Weixin | 是 | 是 | 是 | 否 | 否 | 是 | 否 |
| QQ | 是 | 是 | 是 | 否 | 否 | 是 | 是 |
| 元宝 Yuanbao | 是 | 是 | 是 | 否 | 否 | 是 | 是 |
| Microsoft Teams | 否 | 是 | 否 | 是 | 否 | 是 | 否 |

配置入口是交互式向导 `hermes gateway setup`：它用方向键选平台、标出哪些已配置，并在结束时询问是否启动/重启网关。凭据落在 `~/.hermes/.env`，行为开关落在 `~/.hermes/config.yaml` 的对应平台段。本机当前的平台级配置（真实 config.yaml 节选，密钥不在这一段里）：

```yaml
# ~/.hermes/config.yaml
slack:
  require_mention: true
  free_response_channels: ''
  allowed_channels: ''

discord:
  require_mention: true
  free_response_channels: ''
  allowed_channels: ''
  auto_thread: true
  thread_require_mention: false
  history_backfill: true
  history_backfill_limit: 50
  reactions: true
  allow_any_attachment: false
  max_attachment_bytes: 33554432      # 32 MiB，超过的附件不下载

telegram:
  reactions: false
  allowed_chats: ''

mattermost:
  require_mention: true
  free_response_channels: ''
  allowed_channels: ''

matrix:
  require_mention: true
  free_response_rooms: ''
  allowed_rooms: ''
```

几个字段的实际含义：

- `require_mention`：群里是否必须 @ 到才响应。默认 `true`，避免 agent 在群里插话。
- `free_response_channels` / `allowed_channels` / `allowed_chats`：白名单。空表示不限制（配合 `require_mention` 使用）。
- `history_backfill` + `history_backfill_limit`：接入时回溯多少条历史，让 agent 一进来就有上下文。
- `max_attachment_bytes`：单附件上限，默认约 32 MiB；`allow_any_attachment` 关着时只收允许的类型。

也有不经过 agent 的单向发消息通道，适合脚本、CI、监控告警：

```shell
hermes send --to telegram "部署完成"
echo "RAM 92%" | hermes send --to telegram:-1001234567890
hermes send --to discord:#ops --file ./report.md
hermes send --to slack:#eng --subject "[CI]" --file build.log
hermes send --to telegram "MEDIA:./chart.png"      # 发媒体附件
hermes send --list                                 # 列出所有可用目标
hermes send --list telegram                        # 按平台过滤
```

`hermes send` 直接复用网关的平台凭据（`~/.hermes/.env` + `config.yaml`），**不经过 LLM、不经过 agent 循环、对 bot-token 类平台（Telegram/Discord/Slack/Signal）连网关都不用运行**。目标格式支持 `platform`（home channel）、`platform:chat_id`、`platform:chat_id:thread_id`、`platform:#channel-name`。

```text
消息平台接入要点：
1. hermes gateway setup 是唯一推荐的配置入口，凭据进 .env，开关进 config.yaml
2. require_mention 默认 true，群聊里不 @ 不响应；要放开用 free_response_channels
3. 能力差异是平台侧的，不是 Hermes 侧的：无流式的平台只能整条回复
4. hermes send 是无 LLM 的单向通道，bot-token 平台不需要网关在跑
5. 附件大小受 max_attachment_bytes 限制，默认约 32 MiB
```

## 网关配置与渠道覆盖

一个网关可以同时服务多个渠道，并且让不同渠道跑不同的模型与人设——例如 `#daily` 用便宜快的模型、`#dev` 用前沿模型加专家提示词。这个能力叫渠道覆盖（channel overrides）。

```yaml
# ~/.hermes/gateway-config.yaml
platforms:
  discord:
    enabled: true
    channel_overrides:
      "123456789012345678":            # 渠道 / 线程 ID
        model: anthropic/claude-sonnet-4.6
        provider: anthropic
        system_prompt: "你是 #dev 渠道的代码审查专员。"
      "987654321098765432":
        model: openai/gpt-5-mini
```

会话的重置策略默认是「永不自动重置」（除非你手动 `/reset` 或触发上下文压缩）。要自动重置得显式开 `session_reset`：

```yaml
session_reset:
  mode: idle            # idle / daily / both / none（默认 none）
  idle_minutes: 1440    # idle 或 both：闲置多少分钟重置
  at_hour: 4            # daily 或 both：每天几点（本地时间，0-23）
```

按平台覆盖重置策略写在 `~/.hermes/gateway.json`：

```json
{
  "reset_by_platform": {
    "telegram": { "mode": "idle", "idle_minutes": 240 },
    "discord": { "mode": "idle", "idle_minutes": 60 }
  }
}
```

显示噪音也能按平台调。Telegram 的默认值是为手机收件箱调过的：`tool_progress` 默认关、`busy_ack_detail` 默认关、`interim_assistant_messages` 与 `long_running_notifications` 保持开：

```yaml
display:
  platforms:
    telegram:
      tool_progress: new            # 重新打开逐工具进度流
      busy_ack_detail: true         # 心跳/忙碌确认里显示 iteration N/M
      cleanup_progress: true        # 最终回复落地后自动删掉进度气泡
    discord:
      cleanup_progress: true
```

`cleanup_progress` 默认 `false`，且只有实现了 `delete_message` 的适配器才生效（目前是 Telegram 与 Discord）；失败的运行会跳过清理，把气泡留作线索。

另外有一层「投递账本」（delivery ledger，存在 `state.db`）：网关崩溃或重启发生在「已生成回复、平台未确认送达」之间时，下次启动会重投而不是丢消息。语义是诚实的至少一次——从未开始发送的原样重投；发送中途死掉的重投时会带可见前缀（表示可能是重复）。重投有界：3 次尝试、24 小时内、已送达的行 7 天后清理。不想要这个行为可在 config.yaml 里设 `gateway.delivery_ledger: false`。

```text
网关配置要点：
1. channel_overrides 让一个网关同时跑多套模型/人设，键是渠道或线程 ID
2. 会话默认永不自动重置，要自动重置得显式配 session_reset（none 是默认值）
3. 逐平台的显示噪音用 display.platforms.<platform>.* 调，cleanup_progress 只对 Telegram/Discord 生效
4. 投递账本防丢消息，语义是「可能重复但标注出来」，可关但关了崩溃时会丢在途回复
5. 后台进程会保护会话不被重置，超过 bg_process_max_age_hours（默认 24）的进程不再阻止重置，但不会被杀
```

## 语音与媒体能力

语音是网关的一大卖点：平台发来的语音消息会自动转写成文本，再交给 agent；回复也可以用语音回。两半分别是 STT（语音转文本）与 TTS（文本转语音），各自可有不同 provider。

本机当前配置（真实 config.yaml 节选）：

```yaml
stt:
  enabled: true
  local:
    model: base          # tiny / base / small / medium / large-v3
    language: ''
  openai:
    model: whisper-1
  mistral:
    model: voxtral-mini-latest
  provider: local        # local / groq / openai / mistral

tts:
  provider: edge         # edge / elevenlabs / openai / minimax / mistral / neutts
  edge:
    voice: en-US-AriaNeural
  elevenlabs:
    voice_id: pNInz6obpgDQGcFmaJgB
    model_id: eleven_multilingual_v2
  openai:
    model: gpt-4o-mini-tts
    voice: alloy
  xai:
    voice_id: eve
    language: en

voice:
  record_key: ctrl+b     # CLI 里按住说话的键
  max_recording_seconds: 120
```

STT 的 provider 按优先级自动探测：本地 faster-whisper（免费，`pip install faster-whisper`）→ Groq Whisper（免费额度，需 `GROQ_API_KEY`）→ OpenAI Whisper（付费）→ Mistral Voxtral。TTS 的免费档是 Edge TTS（不需要任何密钥，也是默认值）与本地 NeuTTS（`pip install neutts[all]` 加 `espeak-ng`）；付费档有 ElevenLabs、OpenAI、MiniMax、Mistral。

会话内控制语音的斜杠命令是 `/voice on`（语音进语音出）、`/voice tts`（始终语音回）、`/voice off`：

```shell
# 在终端会话里
/voice on
/voice off

# 或者直接生成一段语音文件（TTS 工具本身也可被模型调用）
```

媒体方向：图片与文件走平台适配器（受上一节的 `max_attachment_bytes` 等限制）；`hermes send` 用 `MEDIA:<path>` 语法发附件；`hermes mcp serve` 暴露的 `attachments_fetch` 能把某条消息的图片/媒体取出来。Discord 还有语音频道对话能力，Markdown 表格里那列「语音」包含它。

```text
语音与媒体要点：
1. 语音消息自动转写（STT），回复可带语音（TTS），两半 provider 独立配置
2. STT 默认走本地 faster-whisper，装上就免费；没装则按 Groq / OpenAI / Mistral 顺序探测
3. TTS 默认 Edge TTS，零密钥；本地 NeuTTS 需要额外装包与 espeak-ng
4. /voice on|tts|off 控制当前会话的语音行为
5. 媒体收发受平台能力与附件大小限制约束，不是所有平台都支持文件和线程
```

## 接入安全：配对、审批与静默

把 agent 挂到消息平台上，等于给一个能执行终端命令的东西开了对外入口，所以三道闸必须理解。

**第一道：配对（pairing）。** 陌生人私聊不直接获得使用权，需要配对授权：

```shell
hermes pairing list              # 看待批准 + 已批准的用户
hermes pairing approve           # 批准一个配对请求
hermes pairing revoke            # 撤销某用户访问
hermes pairing clear-pending     # 清空所有待批准码
```

**第二道：审批（approvals）。** 网关里执行危险命令（`rm -rf`、`git reset --hard` 之类）会弹审批，用户在聊天里回 `/approve` 或 `/deny`。默认模式是 `manual`：

```yaml
# ~/.hermes/config.yaml
approvals:
  mode: manual                      # manual（默认）/ smart（辅助模型判风险）/ off
  timeout: 60
  cron_mode: deny                   # cron 触发的运行遇到危险命令时的策略
  mcp_reload_confirm: true
  destructive_slash_confirm: true
```

```shell
# 交互式改（改完重启网关 / 新开会话才生效）
hermes config set approvals.mode smart
hermes config set approvals.mode manual
```

**第三道：静默令牌。** 群聊里 agent 被 @ 了但发现无事可做时，不该发一句「没问题」。如果最终回复**正好**是以下之一，网关会抑制投递、什么都不发：`[SILENT]`、`SILENT`、`NO_REPLY`、`NO REPLY`。大小写与空白会被归一化，但必须整条回复就是这个 token——写「没有变化时用 `[SILENT]`」这种句子会被正常投递。

静默只影响投递，不影响会话记录：这一轮仍然以 assistant 消息存进会话，保证角色交替正常。失败的轮次仍按错误上报，不会因为文本长得像静默令牌而被藏起来。

```text
接入安全要点：
1. 对外开放前先想清楚谁能私聊你：用 hermes pairing 管理授权名单
2. approvals.mode 决定危险命令要不要人工确认，网关里用 /approve 与 /deny 回应
3. cron 触发的运行没人能点审批，cron_mode 默认 deny，要放行得显式改
4. 静默令牌必须是整条回复，且只抑制投递、不改变会话记录
5. 失败轮次不会被静默掩盖——静默是投递决策，不是错误处理
```

## 应用场景实战

### 场景一：把网关装成开机自启的系统服务并验证

目标：在一台常开的服务器上，让 Hermes 网关随系统启动、崩了自动拉起、日志进 journald，并验证它真的在服务目标 profile。

```shell
# 1) 先配平台（交互式，凭据写入 ~/.hermes/.env）
hermes gateway setup

# 2) 装成系统级服务：指定运行用户，装完立即启动，并设为开机自启
sudo hermes gateway install --system \
  --run-as-user lw \
  --start-now \
  --start-on-login
```

```shell
# 3) 验证：unit 存在、服务 active、profile 正确
systemctl is-active hermes-gateway
systemctl list-units --type=service | grep hermes
hermes gateway status --system
hermes gateway list
```

真实输出对照（本机实测，注意 `hermes status` 与 `hermes gateway list` 的视角差异）：

```text
$ systemctl list-units --type=service | grep -i hermes
  hermes-gateway.service   loaded active running Hermes Agent Gateway - Messaging Platform Integration

$ hermes gateway list
Gateways:
  ✗ default (current)        — not running
```

```shell
# 4) 确认 unit 里的 HERMES_HOME 指向正确的那套配置与数据
grep -n 'HERMES_HOME' /etc/systemd/system/hermes-gateway.service

# 5) 看日志确认各平台连上
hermes logs gateway -n 50
```

关键点：`hermes gateway install --system --run-as-user <user>` 是唯一能让网关开机自启的路径；用户级 install 依赖 user manager（SSH 登出就会停，除非 `loginctl enable-linger`）。`hermes gateway status` 在某些版本上会因为 `systemctl` 调用超时而抛 traceback（见踩坑），服务本身没问题——以 `systemctl is-active` 与 `hermes logs gateway` 为准。

### 场景二：一个网关服务多套模型与渠道，顺带接单向下发告警

目标：Discord 的 `#daily` 用便宜模型、`#dev` 用前沿模型加专家人设；同时让一个监控脚本在告警时直接推消息，不消耗任何模型额度。

```yaml
# ~/.hermes/gateway-config.yaml
platforms:
  discord:
    enabled: true
    require_mention: true
    channel_overrides:
      "111111111111111111":            # #daily
        model: openai/gpt-5-mini
      "222222222222222222":            # #dev
        model: anthropic/claude-sonnet-4.6
        provider: anthropic
        system_prompt: "你是 #dev 渠道的代码审查专员，只报结论与证据，不改文件。"
  telegram:
    enabled: true
    allowed_chats: "-1001234567890"
```

```yaml
# 同一份 config.yaml 里调低 Telegram 的噪音、给 #dev 之外的渠道关掉进度流
display:
  platforms:
    telegram:
      tool_progress: 'off'
      cleanup_progress: true
```

```shell
# 重启网关让配置生效（渠道覆盖与显示配置都是进程启动时读的）
hermes gateway restart

# 监控脚本：不经过 agent、不消耗模型额度，失败也不会惊动会话
#!/usr/bin/env bash
set -euo pipefail
ram=$(free -m | awk '/^Mem:/ {print int($3*100/$2)}')
if [ "$ram" -ge 90 ]; then
  hermes send --to telegram:-1001234567890 --subject "[告警]" "内存使用率 ${ram}%"
fi

# CI 里同理：把构建日志当附件发到工程群
hermes send --to slack:#eng --subject "[CI]" --file build.log
hermes send --to telegram "MEDIA:./coverage.png"
```

关键点：`channel_overrides` 的键是渠道或线程 ID，用 Discord 的「复制 ID」拿到；`hermes send` 不启动 agent、不读会话、对 bot-token 平台连网关都不用跑，所以它适合放进告警与 CI 这类不能依赖长驻进程的场景。要发媒体就在正文里写 `MEDIA:<path>`，而不是用 `--file`（`--file` 只发文本正文）。

### 场景三：用配对 + 审批把 agent 安全地放到群里

目标：团队群里所有人都能看到 agent 的产出，但只有授权的人能驱动它执行命令，且危险操作必须人工确认。

```shell
# 1) 收紧响应条件：只有 @ 到才理，且只服务白名单群
hermes config set discord.require_mention true
```

```yaml
# ~/.hermes/config.yaml
discord:
  require_mention: true
  free_response_channels: ''          # 留空：不在任何渠道无条件响应
  allowed_channels: ''                # 需要限定时填渠道 ID 列表
  auto_thread: true                   # 回复开子线程，别把主频道刷屏
  max_attachment_bytes: 33554432

approvals:
  mode: manual                       # 危险命令必须有人点 /approve
  timeout: 60
  cron_mode: deny
```

```shell
# 2) 管理谁能用：查名单、批准、撤销
hermes pairing list
hermes pairing approve
hermes pairing revoke

# 3) 重启网关，然后让群里的助手用静默令牌处理「没事发生」的情况
hermes gateway restart
```

```text
# 群聊里被 @ 但确实无事可做时，助手整条回复应当是这四个之一（大小写与空白会被归一化）：
[SILENT]
SILENT
NO_REPLY
NO REPLY
# 这样网关抑制投递，群里不出现任何消息；但该轮仍会写进会话记录
```

关键点：`require_mention: true` 加空的 `free_response_channels` 是最保守的组合——不 @ 不响应，且不在任何渠道无条件响应；`auto_thread: true` 把长回复挪进线程，避免刷屏；静默令牌是「被叫了但不该说话」时的正确出口，而不是让模型编一句客套话。

## 最佳实践与踩坑记录

### 最佳实践

1. 服务器上优先 `hermes gateway install --system --run-as-user <user>`，别依赖 user manager（SSH 登出即停，除非开了 linger）
2. 装完服务先 `grep HERMES_HOME /etc/systemd/system/hermes-gateway.service`，确认它读的是你想要的那套配置与数据
3. 群里默认保守：`require_mention: true` + 空的 `free_response_channels`，需要放开再逐渠道放
4. 危险命令审批保持 `manual`；cron 触发路径保持 `cron_mode: deny`，因为没人能点弹窗
5. 告警、CI、监控这类单向通知用 `hermes send`，不要为了发一句话把 agent 拉起来
6. 逐平台调显示噪音（Telegram 关 tool_progress、Discord 开 cleanup_progress），别让心跳气泡淹掉真正的回复
7. 用 `channel_overrides` 做成本分层：日常渠道走便宜模型，专家渠道才上前沿模型

### 踩坑记录

```text
坑 1：hermes gateway status 抛 Traceback（subprocess.TimeoutExpired）
结论：命令没给出人类可读的状态，反而打出一串 Python 调用栈，看着像网关坏了。
原因：status 内部调用 systemctl 时给了 10s 超时；系统繁忙或 systemd 响应慢时会超时并把异常抛到顶层。
实测输出（节选）：File ".../hermes_cli/gateway.py", line 2536, in _run_systemctl → subprocess.run → raise TimeoutExpired
解法：改用 systemctl is-active hermes-gateway / systemctl list-units | grep hermes 判断服务状态，再配合 hermes logs gateway 看实际运行情况。

坑 2：hermes gateway list 说没在跑，hermes status 说在跑
结论：两个命令给出相反结论，不知道该信哪个。
原因：两者看的不是同一件事——hermes status 汇总的是 agent 视角的状态，hermes gateway list 枚举的是当前 profile 的网关服务；跨 HERMES_HOME（例如 CLI 用 /root/.hermes、网关服务用 /home/lw/.hermes）时就会分叉。
实测：$ hermes gateway list → "✗ default (current) — not running"，而 $ hermes status → "Gateway: ✓ running"。
解法：判定服务是否在跑一律以 systemctl is-active 为准，并确认自己的 HERMES_HOME 与网关服务的是同一个。

坑 3：装成用户级服务后，SSH 一断开网关就停了
结论：本地测试一切正常，关掉终端十分钟后 Telegram 不再响应。
原因：用户级 systemd 服务的生命周期绑在用户会话上，最后一个会话退出就被停掉。
解法：要么开 linger（sudo loginctl enable-linger $USER），要么直接装系统级：sudo hermes gateway install --system --run-as-user <user>。

坑 4：WSL2 里装了服务却起不来
结论：systemctl 报服务不存在或立刻退出。
原因：WSL2 默认不启用 systemd，服务管理器根本不存在；这时 Hermes 会退化成 nohup 方式启动，会话一关就死。
解法：在 /etc/wsl.conf 里加 [boot] systemd=true 后重启 WSL；临时办法是前台跑 hermes gateway run。

坑 5：改了 config.yaml 的显示/平台配置，聊天行为没变
结论：tool_progress、require_mention 这些开关改了却没生效。
原因：网关进程在启动时读一次配置（只有部分平台配置支持热加载），老进程还拿着旧值。
解法：改完跑 hermes gateway restart；只改了密钥类的 .env 与部分平台配置才免重启。

坑 6：把 hermes send 的 --file 当成发附件
结论：本想发一个 build.log 文件，结果收到的是文件内容拼成的纯文本正文。
原因：--file 的语义是「从文件读消息正文」，官方说明里明确它只发文本；发附件要用 MEDIA: 语法。
解法：正文里写 hermes send --to telegram "MEDIA:./build.log"，或把路径放进消息文本由适配器识别。
```
