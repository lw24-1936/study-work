## 概述

Hermes 的上下文管理解决两个不同的问题：**单次会话内**的上下文窗口不够用（用压缩解决），以及**跨会话**的对话历史要能找回来（用会话存储与检索解决）。压缩是分层的——智能体循环里的 `ContextCompressor` 以真实 token 计数按阈值触发（本机阈值 50%），网关侧还有一道 85% 的逃生网专门兜住「隔夜长会话」。压缩会改写当前会话的消息列表，并把摘要前的原文软归档，因此它**减少活跃上下文，但不是隐私删除**。

```text
本节要点：
1. 两个问题 —— 单会话内的窗口压力（压缩）+ 跨会话的历史复用（session 存储）
2. 两层压缩 —— 智能体循环内 ContextCompressor（默认 50% 触发，真实 token）+ 网关 session hygiene（固定 85%，安全网）
3. 压缩产物 —— 结构化摘要（目标 / 已完成 / 进行中 / 相关文件 / 下一步）替换中段，头部与尾部保留
4. 不删数据 —— 被压缩的轮次软归档（active=0, compacted=1），仍可被 session_search 搜到
5. 预算控制 —— threshold / target_ratio / protect_last_n / tail_mode / min_tail_user_messages
6. 手工干预 —— /compress 立即压缩、/new 开新会话、hermes sessions prune 才是真删除
```

## 两层压缩与触发阈值

为什么是两层？因为两者的可见信息不同。智能体循环内能读到 provider 返回的**真实 token 用量**，所以它做常规管理；网关在把消息交给智能体之前只能做粗估，用于兜住那些「在两次交互之间涨大」的会话（典型场景是 Telegram/Discord 里隔夜累积的长会话）。

```text
                     ┌──────────────────────────┐
  Incoming message   │   Gateway Session Hygiene │  Fires at 85% of context
  ─────────────────► │   (pre-agent, rough est.) │  Safety net for large sessions
                     └─────────────┬────────────┘
                                   │
                                   ▼
                     ┌──────────────────────────┐
                     │   Agent ContextCompressor │  Fires at 50% of context (default)
                     │   (in-loop, real tokens)  │  Normal context management
                     └──────────────────────────┘
```

网关侧 hygiene 的三个硬性条件值得记住：阈值**固定 85%**（不可配，故意高于智能体阈值，早期设成 50% 会导致长会话每轮都提前压缩）、只在前台历史条数不少于 4 且压缩已启用时执行、token 来源优先级为「上一轮 API 实际用量 → 会话行上持久化的用量锚点 → 字符数粗估」。

智能体侧每次判断压缩前先问**用量锚点**（usage anchor）：provider 上一次响应的 `usage.prompt_tokens` 加上「自那次响应之后新增消息」的粗估。锚点用内容指纹标识被计价的那段对话，所以即使网关每轮从数据库重读历史、或进程重启后 `--resume`，锚点依然有效。没有锚点时（首次请求、回退重发）不会凭粗估就压缩，而是**推迟一次请求**等 provider 给出真实计数；但已有真实读数超阈值、粗估远超窗口、或 provider 明确报上下文溢出时立即压缩。

```text
两层压缩要点：
1. 分工 —— 智能体循环内做常规压缩（真实 token），网关 hygiene 只做兜底（固定 85%）
2. 触发条件 —— hygiene 需要历史 ≥ 4 条且压缩开启；否则不介入
3. token 来源 —— 真实用量优先，其次会话行上的持久化锚点，最后才是字符粗估
4. 锚点作用 —— 跨进程重启与网关重读历史都不会让压缩误判
5. 无锚点行为 —— 推迟一次请求等真实用量，而不是按猜测压缩（永不因此禁用压缩）
6. 溢出自救 —— provider 报上下文长度错误时，即使处于冷却期也允许一次有界尝试
```

## 压缩参数与配置项

本机 `config.yaml` 里压缩配置的真实取值：

```yaml
compression:
  enabled: true
  threshold: 0.5              # 达到上下文窗口的 50% 触发压缩
  target_ratio: 0.2           # legacy 尾模式下保留的尾部比例
  protect_last_n: 20          # 至少保护的最近 20 条消息
  hygiene_hard_message_limit: 400   # 硬护栏：消息条数上限
  protect_first_n: 3          # 系统提示词 + 首个来回，永久保留
```

官方文档给出的完整参数面（本机未显式设置的那些取默认值）：

| 参数 | 默认值 | 取值范围 | 作用 |
|---|---|---|---|
| `threshold` | `0.50` | 0.0-1.0 | 提示 token ≥ `threshold × context_length` 时触发 |
| `model_thresholds` | `{}` | map | 按模型名**子串匹配**覆盖 threshold，最长匹配优先 |
| `target_ratio` | `0.20` | 0.10-0.80 | 尾保护 token 预算（仅 legacy 模式） |
| `tail_mode` | `lean` | `lean`、`legacy` | 尾保留策略：lean 保留约 `2.5% × 窗口`（下限 10K、上限 25K）并用摘要承载连续性 |
| `protect_last_n` | `20` | ≥1 | 最近消息最小保留条数 |
| `min_tail_user_messages` | `1` | ≥1 | 未压缩尾部里保证保留的**真实用户消息**条数 |
| `protect_first_n` | `3` | 硬编码 | 系统提示词 + 首个来回 |
| `idle_compact_after_seconds` | `0` | ≥0 | 空闲这么久后恢复会话时先压缩（0 = 关闭） |
| `in_place` | `true` | bool | 在同一 session id 上就地压缩（不轮换新会话） |

按模型分别设阈值是常见需求（模型窗口差异大时尤其明显）：

```yaml
compression:
  threshold: 0.50
  model_thresholds:
    "glm-5.2": 0.40
    "glm-5.2-1M": 0.25      # 更长的 key 优先，1M 窗口的模型可以更晚压缩
    "claude-sonnet": 0.35
```

规则细节：key 对模型名做子串匹配、最长匹配胜出；没命中就用全局 `threshold`；切换 `/model` 时重新解析；**小窗口下限仍生效且只能抬高**——窗口小于 512K 的模型会被抬到 `0.75`，所以 0.40 这类覆盖值对小窗口模型无效（写 0.80 则生效）。

摘要用的模型与 provider 单独配置，避免用主模型做摘要烧钱：

```yaml
auxiliary:
  compression:
    provider: auto      # auto | openrouter | nous | main | 自定义
    model: null         # 留空 = 自动选择
    base_url: null      # 指向自建 OpenAI 兼容端点
```

压缩引擎本身也可替换（`context.engine`）：默认 `compressor` 是内置的有损摘要引擎，插件可提供 `lcm` 一类无损上下文引擎；解析顺序是先看 `plugins/context_engine/<name>/`，再看插件注册表，最后回退内置。插件引擎**不会自动启用**，必须显式配置名字。

```text
压缩配置要点：
1. 主开关 —— compression.enabled（false 则两层压缩都不介入，网关 hygiene 也不动）
2. 阈值 —— threshold 默认 0.50，可用 model_thresholds 按模型覆盖（子串 + 最长匹配）
3. 小窗口下限 —— 窗口 < 512K 的模型阈值被抬到 0.75，低值覆盖无效
4. 尾部策略 —— tail_mode: lean（默认）省 token；legacy 保留大段原文（大窗口模型上可能 100K+）
5. 摘要成本 —— auxiliary.compression 单独指定模型/provider，别让主模型干摘要
6. 引擎可换 —— context.engine: compressor（默认）或插件引擎名；插件不会自动激活
```

## 摘要结构与就地压缩

压缩后的消息列表长这样：系统提示词里加一条说明，摘要替换掉中段的几十轮工具调用，尾部保留最近的对话。摘要模板是结构化的，包含目标、已完成、进行中、相关文件、下一步——这几项恰好是继续干活所需的最小信息集。

```text
# 压缩前（片段）
[0] system:    "You are a helpful assistant..."
[1] user:      "Help me set up a FastAPI project"
[2] assistant: <tool_call> terminal: mkdir project </tool_call>
[3] tool:      "directory created"
   ... 30 more turns of file editing, testing, debugging ...
[38] assistant: <tool_call> terminal: pytest </tool_call>
[39] tool:      "8 passed, 2 failed\n..."  (5KB output)
[40] user:      "Fix the failing tests"
```

```text
# 压缩后
[0] system:    "You are a helpful assistant...
               [Note: Some earlier conversation turns have been compacted...]"
[1] user:      "Help me set up a FastAPI project"
[2] assistant: "[CONTEXT COMPACTION] Earlier turns were compacted...

               ## Goal
               Set up a FastAPI project with tests and error handling

               ## Progress
               ### Done
               - Created project structure: main.py, tests/, requirements.txt
               - Implemented 5 API endpoints in main.py
               - Wrote 10 test cases in tests/test_api.py
               - 8/10 tests passing

               ### In Progress
               - Fixing 2 failing tests (test_create_user, test_delete_user)

               ## Relevant Files
               - main.py — FastAPI app with 5 endpoints
               - tests/test_api.py — 10 test cases
               - requirements.txt — fastapi, pytest, httpx

               ## Next Steps
               - Fix failing test fixtures
               - Add error handling"
[40] user:      "Fix the failing tests"
```

`lean` 尾模式（默认）比 `legacy` 更省：它使用「详细但保留标识符的会话日志 + 机械抽取的锚点索引（PR 号、commit SHA、路径、错误串，用正则而非改写）+ 逐条原样引用的真实用户消息 + 一个 `session_search` 恢复指针」来承载连续性，并把尾部的旧工具结果降级成一行带恢复指针的存根。官方在 50 万 token 的真实会话上给出的对比是约保留 49K 而非 162K，且配合恢复指针时召回率更高。

`in_place: true`（默认）下压缩**不换 session id**：系统提示词重建、摘要换入、压缩前的轮次在同一 id 下软归档（`active=0, compacted=1`），仍可被 `session_search` 检索和恢复，且永远不会被删除。消费方通过 `session:compress` 事件里的 `in_place` 字段判断模式，而不是对比 session id 变化。

压缩失败会触发**每会话的失败冷却**：首轮 60 秒，之后 300 秒、900 秒逐级延长并持久化在 `state.db`。冷却期内常规阈值压缩被推迟（避免坏掉的摘要后端每轮重试），两条路仍会真正尝试：手动 `/compress`（清冷却强制重试），以及 provider 明确报上下文溢出时的有界恢复尝试（不解除冷却）。

```text
摘要与就地压缩要点：
1. 摘要模板 —— Goal / Progress(Done, In Progress) / Relevant Files / Next Steps
2. lean 与 legacy —— lean 默认，尾预算 2.5% 窗口（10K-25K 夹取）+ 摘要承载连续性
3. 不换会话 —— in_place: true 时同一 session id 上就地改写，无 parent_session_id 链、无 #N 重命名
4. 原文可回溯 —— 被压缩轮次软归档，session_search 仍可检索（压缩 != 删除）
5. 失败冷却 —— 60s → 300s → 900s，持久化在 state.db；/compress 可强制重试
6. 溢出自救 —— provider 报超长时忽略冷却做一次有界尝试，否则会话会每轮撞墙
```

## 提示缓存与压缩的相互影响

压缩与提示缓存是一对张力：缓存靠前缀不变来命中，压缩恰恰要改前缀。Hermes 的取舍是「系统提示词永远稳定」，因此缓存断点采用 `system_and_3` 策略（Anthropic 单请求最多 4 个断点）：

```text
Breakpoint 1: System prompt           (stable across all turns)
Breakpoint 2: 3rd-to-last non-system message  ─┐
Breakpoint 3: 2nd-to-last non-system message   ├─ Rolling window
Breakpoint 4: Last non-system message          ─┘
```

TTL 可配（必须是 `5m` 或 `1h`）；本机配置为 5 分钟：

```yaml
prompt_caching:
  cache_ttl: 5m
```

只在「模型是 Anthropic Claude 系列 且 provider 支持 `cache_control`（原生 Anthropic API 或 OpenRouter）」时自动启用，启动时会在 CLI 打印一行状态。三条必须知道的交互规则：

```text
1) 消息顺序决定命中 —— 缓存靠前缀匹配，在中段增删消息会让其后全部缓存失效
2) 压缩的代价范围内 —— 压缩使「被压缩区间」的缓存失效，但系统提示词的缓存仍在；
   滚动 3 条窗口会在 1-2 轮内重新建立缓存
3) 模型身份属于缓存键 —— 会话中途换模型（/model 切换、主模型回退、凭据池轮换到另一个账号）
   会让下一次请求零命中、按原价重读整段对话，这是 provider 侧缓存的性质，Hermes 无法规避
```

```text
提示缓存要点：
1. 断点策略 —— system_and_3：系统提示词 + 最近 3 条非系统消息
2. TTL —— prompt_caching.cache_ttl: 5m | 1h（默认 5m）
3. 生效条件 —— Anthropic 系模型 + 支持 cache_control 的 provider
4. 压缩之后 —— 系统提示词缓存存活，滚动窗口 1-2 轮内重建
5. 别中途换模型 —— 换模型/换凭据池会让缓存整段失效，成本直接上升
6. 官方提醒 —— 不要设计「静默切换模型或凭据」的功能，属于把成本藏起来
```

## 会话历史与回放

会话存储是与压缩互补的另一半：压缩减少活跃上下文，存储保证什么都没丢。所有会话（CLI、TUI、网关平台、cron、batch）都进同一个 SQLite 库 `~/.hermes/state.db`（WAL 模式，多读单写 + FTS5 全文索引）。本机实测体量：

```text
$ hermes sessions stats
Total sessions: 521
Total messages: 39203
  cli: 99 sessions
Database size: 842.5 MB

$ hermes sessions list | head -6
Title                        Workspace          Last Active   ID
────────────────────────────────────────────────────────────────
创建各AI知识库文档到 /opt/study-wor   root               just now      20261015_083443_00d9c7
在/opt/study-work生成知识库文档      root               8h ago        20261015_003808_1e2899
学习 MetaGPT 并继续任务             root               8h ago        20261015_003449_3da58f
```

回放/续跑的主要入口：

```bash
hermes -c                          # 续最近的 CLI 会话（终端感知：同一终端续自己的那条）
hermes -c "my project"             # 按标题续（同名谱系自动取最近一条）
hermes --resume 20261015_083443_00d9c7   # 按 ID 续
hermes --resume latest --in ./my-project  # 续该目录最近的一条并固定会话到该目录
hermes --resume <id> --no-restore-cwd     # 不恢复会话记录的工作目录
hermes sessions rename <id> "重构鉴权模块"   # 给会话改名
hermes sessions export backup.jsonl --redact     # 导出（抹掉密钥）
hermes sessions export --format html --session-id <id> transcript.html  # 单条导出为自包含 HTML
```

会话 ID 形如 `YYYYMMDD_HHMMSS_<hex>`（CLI/TUI 6 位、网关 8 位），可按完整 ID 或唯一前缀续跑。标题唯一、最长 100 字符、自动清洗控制字符；自动标题由辅助模型在后台线程生成，只触发一次。压缩导致的会话谱系编号（`"my project #2"`）只出现在 `in_place: false` 的传统轮换模式下。

```text
会话历史与回放要点：
1. 单一存储 —— 全部会话在 ~/.hermes/state.db（SQLite + WAL + FTS5），sessions/ 下的 json 不是会话列表
2. 续跑入口 —— -c（按终端/最近）、--resume <id|title|latest>、--in <dir> 组合固定目录
3. 会话预览 —— 续跑时展示 recap 面板（可 display.resume_display: minimal 关掉）
4. 导出格式 —— jsonl（默认）/ md / qmd / html / trace，加 --redact 抹密钥
5. 一键省空间 —— hermes sessions optimize 合并 FTS5 段并 VACUUM，不动任何数据
6. 真删除 —— hermes sessions prune（可配 sessions.auto_prune + retention_days，默认关闭）
```

## 长任务处理与循环工具

长任务的上下文压力往往不在「一次回答太长」，而在「同一会话反复轮询直到外部状态变化」。Hermes 给了四个定位不同的工具，选错会浪费上下文或丢失上下文：

| 工具 | 运行位置 | 上下文 | 适用 |
|---|---|---|---|
| `/compress` | 当前会话 | 立即压缩活跃上下文 | 会话变长、响应变慢或开始忘事 |
| `/new`（可带名字） | 新会话 | 干净上下文，旧会话仍可检索 | 换主题、换任务 |
| `/goal` | 当前会话 | 持续同一上下文 | 「做到这个目标为止」的判据驱动任务 |
| `/loop` | 当前会话 | 每轮读最新状态 | 定时轮询外部状态、迭代到绿 |
| `/heartbeat` | 当前会话 | 空闲时注入一轮 | 「顺手盯着 X，有变化告诉我」 |
| `hermes cron` | 独立新会话 | 无任何历史 | 无人值守、要跨重启的固定作业 |

`/loop` 与 `/heartbeat` 的区别值得单独说清，因为它们看着像：

```text
/loop 5m check the deploy status and tell me if it's live yet   # 定时重跑
/heartbeat every 10m Check the deployment and report meaningful changes   # 空闲才注入

/loop 的两种节奏：
- 固定间隔：/loop 2m poll the build at ci.example.com/job/42 and ping me
- 自定节奏：/loop keep an eye on the migration and summarize progress
  （省略间隔后从 1 分钟起步，回复无变化就指数退避到上限 15 分钟，一变即回落）

/heartbeat 的关键语义：只在空闲时注入、是普通 user 消息（不改变系统提示词，缓存安全）、
丢过的 tick 会合并成一次、用户消息优先、由设置它的界面负责投递。
```

长任务真正的「不丢」保障来自存储而非上下文：`/loop` 与 `/heartbeat` 的状态持久化在 SessionDB，网关重启后会恢复活跃的 watched session 与 heartbeat（按当前持久化对话和线程路由恢复）。

```text
长任务处理要点：
1. 会话内 vs 会话外 —— /loop、/heartbeat、/goal 都在当前会话；cron 在隔离的新会话
2. 需要历史就用 loop/heartbeat —— 它们复用同一上下文与提示缓存；cron 不继承任何对话
3. 判据驱动用 /goal —— 「定义完成」的任务；计时驱动用 /loop
4. 缓存安全 —— heartbeat 注入的是普通 user 消息，不改系统提示词、不动工具集
5. 重启恢复 —— loop/heartbeat 状态存 SessionDB，网关重启后按路由恢复
6. 真无人值守 —— 隔夜、跨终端重启、要投递到手机：一律用 cron，别指望会话内循环
```

## 上下文膨胀的治理

上下文增长的第一大来源不是图片或音频，而是**冗长文本**：粘贴的完整日志、大段 diff、重复的状态汇报、把工具输出整段贴进对话。附件本身是一次性的：图片只在那一次调用里进上下文（或预先转成文字描述），音频转写后只保留文本，文档通常只留一个本地路径加一句说明；未来的轮次不会反复携带原始 JPEG/音频字节。

治理顺序按成本从低到高：

```bash
hermes sessions stats                          # 先量化：会话数、消息数、库大小
hermes sessions optimize                       # 合并 FTS5 段 + VACUUM（只省磁盘，不改数据）
hermes sessions optimize-storage               # 迁移搜索索引到紧凑布局（大库省磁盘）
hermes sessions export backup.jsonl --redact   # 要清之前先导出留档
hermes sessions prune --older-than 30 --yes    # 删掉 30 天前的已结束会话（真删除）
```

自动清理默认**关闭**，打开在 `config.yaml`：

```yaml
sessions:
  auto_prune: true             # 默认 false；打开后按留存窗口清理
  retention_days: 90           # 已结束会话的留存天数
  vacuum_after_prune: true     # 清理后回收磁盘
  min_vacuum_interval_days: 30 # 两次 VACUUM 的最小间隔
  min_interval_hours: 24       # 两次清理扫描的最小间隔
```

活跃会话永远不会被自动清理，已结束会话按「最后一条消息」的时间计龄，所以长期使用但最近还在用的对话不会被误删。官方给出的经验值：几百个会话通常只有 10-15 MB；观察到的问题场景是 384 MB / 约 1000 个会话时 FTS5 插入与 `/resume` 列表变慢。本机 842.5 MB / 521 会话明显偏大，属于需要按上面的顺序处理的状态。

```text
膨胀治理要点：
1. 真正的元凶 —— 冗长文本（日志、diff、重复汇报），不是媒体文件本身
2. 先诊断后清理 —— stats → optimize（非破坏）→ 确要删再 prune
3. optimize 与 prune 语义不同 —— 前者只整理索引与回收磁盘，不动任何会话
4. auto_prune 默认关闭 —— 因为会话历史是 session_search 召回能力的来源
5. 活跃会话不会被动 —— 计龄从最后一条消息算，活跃会话免疫
6. 大库的真实阈值 —— 数百 MB 且会话上千时开始影响 FTS5 插入与列表速度
```

## 应用场景实战

### 场景一：长会话变迟钝时的上下文诊断与治理

现象：同一个会话跑了几个小时后，回复变慢、开始忘掉早期的约定，且宿主机磁盘被 `state.db` 吃掉一大块。做法是「先量化、再判断是哪一层的问题、最后做非破坏性处理」，全程不做删除。

```bash
#!/usr/bin/env bash
# scripts/ctx-doctor.sh —— 上下文与存储的一次性体检（只读 + 非破坏性整理）
set -uo pipefail

CFG="${HERMES_HOME:-$HOME/.hermes}/config.yaml"
DB="${HERMES_HOME:-$HOME/.hermes}/state.db"

echo "[1/6] 会话库体量"
hermes sessions stats

echo
echo "[2/6] state.db 物理文件"
ls -lh "$DB" "$DB-wal" "$DB-shm" 2>/dev/null | awk '{print $5, $9}'

echo
echo "[3/6] 压缩配置（只看与阈值相关的键）"
if [ -f "$CFG" ]; then
  grep -n -A8 '^compression:' "$CFG" || echo "未显式配置 compression，使用默认（enabled=true, threshold=0.50）"
  grep -n -A2 '^context:' "$CFG" || true
  grep -n -A2 '^prompt_caching:' "$CFG" || true
else
  echo "找不到 $CFG"
fi

echo
echo "[4/6] 最近的压缩相关日志"
hermes logs --since 24h 2>/dev/null | grep -i -E 'compact|compress' | tail -10 \
  || echo "（近 24 小时没有压缩记录）"

echo
echo "[5/6] 非破坏性整理：合并 FTS5 段并 VACUUM"
hermes sessions optimize

echo
echo "[6/6] 整理后复查"
hermes sessions stats
```

```text
# 实跑效果（节选，本机真实输出）
$ bash scripts/ctx-doctor.sh
[1/6] 会话库体量
Total sessions: 521
Total messages: 39203
  cli: 99 sessions
Database size: 842.5 MB

[3/6] 压缩配置（只看与阈值相关的键）
83:compression:
84:  enabled: true
85:  threshold: 0.5
86:  target_ratio: 0.2
87:  protect_last_n: 20
88:  hygiene_hard_message_limit: 400
89:  protect_first_n: 3
256:context:
257:  engine: compressor
```

```text
诊断结论与动作：
1) 842.5 MB / 521 会话属于「偏大」区间 —— 先做非破坏性 optimize，不要直接 prune
2) threshold 0.5 是默认值，本机没有按模型做覆盖；若主用 1M 窗口模型可考虑调低或调高
3) context.engine = compressor 表示用的是内置有损摘要引擎，非插件引擎
4) 会话变迟钝常见原因不是压缩没开，而是单轮里塞了过多工具输出 —— 检查 process/工具回显策略
5) 压缩不等于删除：它让活跃上下文变小，磁盘占用要靠 optimize/prune 处理
```

### 场景二：为多平台长会话配置压缩与缓存策略

需求：同一台机器上既用 CLI 跑长任务，也通过消息平台接长会话（隔夜累积），模型在不同窗口规模之间切换。做法是把阈值按模型分层、把尾策略与摘要模型固定下来，然后校验配置真的生效。

```bash
#!/usr/bin/env bash
# scripts/ctx-tune.sh —— 应用上下文策略并回读校验
set -euo pipefail
export HERMES_HOME="${HERMES_HOME:-$HOME/.hermes}"

echo "[1/5] 按模型分层设置压缩阈值"
hermes config set compression.threshold 0.55
hermes config set compression.tail_mode lean
hermes config set compression.protect_last_n 24
hermes config set compression.min_tail_user_messages 2

echo
echo "[2/5] 摘要单独走便宜模型（示例值，按自己的 provider 填）"
hermes config set auxiliary.compression.provider auto

echo
echo "[3/5] 提示缓存 TTL（会话间隔较长时选 1h）"
hermes config set prompt_caching.cache_ttl 1h

echo
echo "[4/5] 回读生效值"
grep -n -A8 '^compression:' "$HERMES_HOME/config.yaml"
grep -n -A2 '^prompt_caching:' "$HERMES_HOME/config.yaml"

echo
echo "[5/5] 手工触发一次压缩（在当前会话里执行）"
cat <<'EOF'
在会话中输入：
/compress        # 立即压缩当前会话，不走冷却；用于「感觉快满了」时的手工干预
EOF
```

```yaml
# 分层阈值示例：换模型时自动应用不同触发点
compression:
  threshold: 0.55
  model_thresholds:
    "glm-5.2": 0.40
    "glm-5.2-1M": 0.25
    "claude-sonnet": 0.35
```

```text
场景二关键点：
1) 阈值分两层 —— 全局 threshold + model_thresholds 子串覆盖，切换 /model 时自动重解析
2) 小窗口模型有下限 —— 窗口 < 512K 会被抬到 0.75，别再指望 0.4 生效
3) min_tail_user_messages 抬高 —— 尾部塞满大工具输出时，保证还有真实用户消息可依
4) 缓存 TTL 跟节奏走 —— 用户会离开一会儿再回来就选 1h，密集对话 5m 足够
5) 校验方式 —— 改完必须 grep 回读配置，并观察 /compress 与压缩后响应是否恢复
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用「会话变迟钝 / 忘了早期约定」作为压缩体检的信号；先 `hermes sessions stats` 量化，再决定是调阈值还是清存储
2. 按模型分层设置阈值：大窗口模型可以更晚压缩（省摘要开销），小窗口模型会被内置下限抬到 0.75，不要为它写低值
3. 摘要单独指定便宜模型（`auxiliary.compression`），把主模型额度留给真正的推理
4. 长任务优先把轮询放进 `/loop` 或 `/heartbeat`（复用上下文与缓存），把无人值守作业放进 cron（干净上下文、可跨重启）
5. 把「贴大段日志/diff 进对话」改为写文件 + 用 `read_file` 取片段、或用 `session_search` 回查历史，从源头控制增长
6. 磁盘紧张时先 `hermes sessions optimize`（非破坏）再考虑 `prune`（真删），删之前先 `export --redact` 留档
7. 会话中途不要切模型或凭据池：缓存整段失效会按原价重读全部对话

### 踩坑记录

```text
坑 1：以为「压缩」会把历史删掉，于是不敢让它压缩
结论：长期不敢清会话，上下文窗口反复撞墙，state.db 越滚越大。
原因：把「活跃上下文减少」与「数据删除」混为一谈。压缩只是把中段换成摘要，
      原文在同 session id 下软归档（active=0, compacted=1），session_search 仍能检索到。
解法：放心压缩（/compress 或等阈值触发）；真要减磁盘用 hermes sessions optimize，
      真要删除才用 hermes sessions prune，并且两条命令的语义要分清。

坑 2：把阈值调低以后，短会话每轮都在压缩，响应明显变慢
结论：会话刚开始就频繁出现压缩，摘要开销吃掉大量 token 与时间。
原因：threshold 是「窗口占比」，在窗口很快被填满的会话里低阈值会连续触发；
      另外网关 hygiene 曾有 50% 的版本会导致每轮提前压缩（官方因此把它固定到 85%）。
解法：阈值不要低于模型实际使用节奏（默认 0.5 起步）；不要改动 hygiene（固定 85%、不可配）；
      确实需要更激进就按模型覆盖，并观察日志里的压缩记录条数。

坑 3：会话中途换模型，成本突然飙升、响应变慢
结论：换到新模型后的第一次请求按原价重读整段对话，缓存命中为零。
原因：provider 侧缓存按「模型（以及账号/API key）」隔离，模型身份是缓存键的一部分；
      显式 /model 切换、主模型回退、凭据池轮换到另一个账号都会让缓存失效。
解法：长会话里避免中途换模型；必须换就在合适的边界换（/new 开新会话）；
      需要成本可控就固定单一模型 + 长 TTL（prompt_caching.cache_ttl: 1h）。

坑 4：摘要后端挂了之后，会话每轮都卡在压缩上
结论：出现重复的压缩失败，响应一轮比一轮慢。
原因：每次压缩失败会武装一个失败冷却（60s → 300s → 900s，持久化在 state.db），
      冷却期内常规压缩被推迟；如果没有正确识别，会被误当成「压缩坏了但一直在重试」。
解法：看 agent.log 里的压缩记录与 state.db 的冷却状态；手工 /compress 会清冷却并强制重试；
      provider 报上下文超长时系统会自动做一次有界恢复尝试（忽略冷却），无需人工介入。

坑 5：把「上下文管理」等同于「定时清理 state.db」，误删了召回能力
结论：开了 sessions.auto_prune 之后，早期会话再也搜不到，session_search 召回明显变差。
原因：会话历史正是 FTS5 召回的来源，auto_prune 默认关闭就是为此；删除不可逆。
解法：磁盘压力优先用 optimize / optimize-storage；确需自动清理则把 retention_days 设得保守
      （默认 90 天），并在打开前先 export 一份带 --redact 的归档。
```
