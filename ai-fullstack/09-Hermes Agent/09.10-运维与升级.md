## 概述

Hermes 是长期驻留在机器上的东西：技能会累积、记忆会增长、会话库会膨胀、网关会日夜跑着。运维要处理的就是这四个方向的熵增——日志要看、数据要知道在哪、备份要能恢复、版本要能升且升完真的在跑新代码。

这一篇把运维拆成两条线。**稳态**是日常维护：`hermes doctor` 体检、`hermes logs` 看日志、`hermes backup` 快照、定期清理会话与检查点。**变更态**是升级：`hermes update` 拉代码重装依赖、迁移配置、重启网关，而在 github.com 被限速的网络里，这条路径需要一个可用的镜像方案。两条线共用一个前提——你必须知道 `HERMES_HOME` 是什么、里面哪些文件是数据、哪些是缓存。

```text
本篇要解决的问题：
1. 日志分哪些文件、hermes logs / doctor / dump 各自回答什么问题
2. HERMES_HOME 的完整目录结构，哪些必须备份、哪些可以丢
3. 备份、恢复、快照、检查点四套机制的区别与取舍
4. hermes update 做了什么，怎么判断「升级真的生效了」
5. github.com 被限速时怎么完成升级，以及升级后 gateway unit 与配置迁移的收尾
```

本篇命令与输出以本机实测为准（Hermes 为 git 安装，升级回执记录版本 `0.21.6`）；官方文档见 `https://hermes-agent.nousresearch.com/docs/reference/cli-commands` 与 `https://hermes-agent.nousresearch.com/docs/`。

## 日志体系与诊断

日志是第一手证据，Hermes 把它收拢到一个入口，不用你满目录 `find`。

```shell
hermes logs                       # 默认看 agent.log 最后 50 行
hermes logs -f                    # 实时跟随
hermes logs errors -n 100         # 错误日志最后 100 行
hermes logs gateway -n 100        # 网关日志
hermes logs update                # 升级日志（hermes update 的镜像）
hermes logs list                  # 列出所有日志文件与大小/时间
hermes logs --level ERROR --since 2h
hermes logs --component gateway --session <id>
hermes logs agent    # 位置参数取值：agent（默认）/ errors / gateway / gui / desktop / update / handoff
```

本机实测 `hermes logs list`（真实输出）：

```text
Log files in ~/.hermes/logs/:

  agent.log                    4.1MB   just now
  errors.log                 212.4KB   just now
  gui.log                         0B   2026-09-12
  mcp-stderr.log                819B   1h ago
  scratch-prune.log            6.7KB   4m ago
  update.log                     1.2MB   2026-10-08
```

`hermes logs --help` 里明确列出的日志名与用途：`agent.log`、`errors.log`、`gateway.log`、`gui.log`、`desktop.log`、`update.log`、`desktop-update-handoff.log`。可选过滤器是 `--level`（DEBUG/INFO/WARNING/ERROR）、`--session`、`--since`（`1h`/`30m`/`2d`）、`--component`（gateway/agent/tools/cli/cron/gui）。

三件诊断工具的分工：

| 命令 | 回答什么问题 |
|------|--------------|
| `hermes doctor` | 配置与依赖是否健康，哪些工具的依赖没满足 |
| `hermes doctor --fix` | 能自动修的自动修（配置项、WAL 检查点等） |
| `hermes dump` | 一份可贴进 issue 的纯文本环境快照（版本、模型、密钥是否设置、工具集、MCP 数量、网关状态） |
| `hermes debug` | 上传日志与系统信息，拿到可分享链接 |
| `hermes status --all` | 组件状态总览（模型、provider、网关、平台、任务数） |
| `hermes security audit` | 对 venv、插件依赖、pin 住的 MCP 服务器做 OSV.dev 供应链扫描 |
| `hermes insights --days 7` | 用量/成本/活跃度分析 |

本机实测 `hermes doctor` 的尾部输出（真实输出；原输出里以警告符号开头的行，这里用 `[警告]` 转写）：

```text
  ✓ todo / ✓ tts / ✓ video / ✓ vision / ✓ web search / ✓ web extract
  [警告] a2a (system dependency not met)
  [警告] browser-cdp (system dependency not met)
  [警告] discord (missing DISCORD_BOT_TOKEN)
  [警告] image_gen (image generation unavailable — check the provider selection and its key or SDK with 'hermes tools')

◆ Skills Hub
  ✓ Skills Hub directory exists
  ✓ Lock file OK (1147 hub-installed skill(s))
  [警告] 2 skill(s) in quarantine (pending review)

◆ Memory Provider
  ✓ Built-in memory active (no external provider configured — this is fine)

────────────────────────────────────────────────────────────
  Found 2 issue(s) to address:

  1. Large WAL file — cannot prove state.db is quiet (stop the profile's gateway first, then run 'hermes doctor --fix' to checkpoint)
  2. Run 'hermes setup' to configure missing API keys for full tool access

  Tip: run 'hermes doctor --fix' to auto-fix what's possible.
```

注意最后一条：`state.db` 的 WAL 文件过大时 doctor 会提示先停网关再 `--fix` 做检查点。这是 SQLite WAL 模式的正常现象，但 WAL 无界增长说明长连接把读事务挂住了。

```text
日志与诊断要点：
1. hermes logs 是唯一入口，位置参数选文件、选项做过滤，不用手工 find
2. update.log 是升级过程镜像，升级出问题时第一个看它
3. doctor 看健康与依赖，dump 看环境快照，debug 负责上传取证，三者别混用
4. doctor 报「Large WAL file」要先停网关再 doctor --fix，别在服务运行时硬做检查点
5. mcp-stderr.log 是 MCP 子进程的 stderr，不在这套命名里但同在 logs 目录下
```

## 数据目录结构

一切持久状态都在 `HERMES_HOME`（默认 `~/.hermes`，多 profile 时是 `~/.hermes/profiles/<name>/`）。本机实测的顶层内容（真实 `ls` 输出，节选与归类）：

```text
$ ls -la ~/.hermes/
drwx------  auth.json                     # OAuth 令牌与凭据池（0o600）
-rw-------  config.yaml                   # 主配置（0o600）
-rw-------  .env                          # API key 与密钥（0o600）
drwx------  sessions/                     # 会话记录
-rw-------  state.db                       # SQLite 主库（会话/记忆/投递账本等）
-rw-------  state.db-wal / state.db-shm    # SQLite WAL 与共享内存
drwx------  logs/                          # 日志（见上节）
drwx------  skills/                        # 已安装技能（本机 1122 个条目）
drwxr-xr-x  plugins/                       # 插件
drwx------  cron/                          # 定时任务定义与心跳
-rw-r--r--  hooks/                         # shell 钩子
drwx------  memories/                      # 记忆文件
-rw-------  SOUL.md                        # 人格/身份提示
drwxr-xr-x  cache/                         # 各类缓存（可丢）
drwxr-xr-x  tools/                         # Hermes 管理的运行时（python / node 等）
drwxr-xr-x  installs/                      # 安装记录（按 id 分目录）
drwxr-xr-x  lsp/                           # 语言服务器
drwx------  pairing/                       # 配对授权状态
drwxr-xr-x  checkpoints/                   # /rollback 用的影子存储（如启用）
drwxr-xr-x  backups/                       # 配置备份（hermes backup 的落点之一）
drwxr-xr-x  terminal-sessions/             # 终端会话持久化
drwxr-xr-x  web-ui-build-stamp.json        # Web UI 构建戳
-rw-r--r--  .hermes-update-in-progress.lock # 升级互斥锁
```

按「必须备份 / 可以丢」分两类：

| 类别 | 内容 | 丢了会怎样 |
|------|------|------------|
| 必须备 | `config.yaml`、`.env`、`auth.json`、`state.db`、`SOUL.md`、`cron/`、`skills/`、`memories/`、`plugins/` | 配置、密钥、会话历史、记忆、技能全没了 |
| 可丢 | `cache/`、`logs/`、`state.db-wal`、`*.lock`、`web-ui-build-stamp.json` | 只影响性能与可诊断性，Hermes 会自己重建 |
| 看情况 | `tools/`、`lsp/`、`installs/` | 可以重新下载，但在受限网络下重下代价高 |
| 不在备份里 | `hermes-agent/` 代码本体 | 升级与回滚靠 git，不靠备份 |

`hermes backup --help` 的说明也印证了这个划分：备份 zip 覆盖「配置、技能、会话、数据」，**明确排除 hermes-agent 代码库**。

会话存储的容量控制有两个旋钮：

```yaml
# ~/.hermes/config.yaml
sessions:
  auto_prune: false          # 是否自动清理旧会话
  retention_days: 90         # 保留天数
  vacuum_after_prune: true   # 清理后是否 VACUUM 回收空间
  min_interval_hours: 24     # 自动清理的最小间隔

logging:
  level: INFO
  max_size_mb: 5             # 单个日志文件轮转阈值
  backup_count: 3            # 保留几个轮转文件
```

```shell
hermes sessions list
hermes sessions stats            # 会话库统计：条数、体积
hermes sessions prune --older-than 30
hermes checkpoints                # 检查点状态总览
hermes checkpoints prune
```

```text
数据目录要点：
1. HERMES_HOME 默认 ~/.hermes；多 profile 时在 profiles/<name>/ 下，结构相同
2. 必须备份的是 config.yaml / .env / auth.json / state.db / SOUL.md / cron / skills / memories / plugins
3. cache、logs、*.lock、state.db-wal 不需要备份，重跑会重建
4. hermes-agent 代码本体不进备份，升级与回滚用 git 处理
5. state.db 的体量靠 sessions.retention_days + vacuum_after_prune 控制；日志靠 logging.max_size_mb / backup_count 轮转
```

## 备份与恢复

四套机制容易混，先分清它们的粒度与代价：

| 机制 | 命令 | 粒度 | 用途 |
|------|------|------|------|
| 全量备份 | `hermes backup` | HERMES_HOME 的配置/技能/会话/数据 | 迁移、换机、升级前保险 |
| 快速快照 | `hermes backup --quick` | 关键状态文件（config、state.db、.env、auth、cron） | 升级前几秒钟留一手 |
| 恢复 | `hermes import` | 从一个备份 zip 还原 | 灾难恢复、换机 |
| 文件检查点 | `/rollback`（`hermes checkpoints`） | 单个文件改动前的影子副本 | 误改代码文件时回退 |
| 状态快照 | `/snapshot`（CLI 斜杠命令） | Hermes 配置/状态 | 会话内试验后回退配置 |

```shell
# 全量备份（默认落 ~/hermes-backup-<timestamp>.zip），保留最新 3 份
hermes backup
hermes backup -o /srv/backups/hermes.zip -k 7

# 快速快照：只抓关键状态文件，适合升级前
hermes backup --quick -l "before-upgrade-0.21.6"

# 恢复
hermes import ~/hermes-backup-20261014-120000.zip
```

`hermes backup --help` 的完整选项：`-o/--output`（输出路径）、`-q/--quick`（快速快照）、`-l/--label`（仅与 `--quick` 搭配的标签）、`-k/--keep N`（全量备份后在该目录只保留最新 N 份，默认 3，0 表示全留）。

升级本身也有一层可选的前置备份，写在 `updates` 段：

```yaml
# ~/.hermes/config.yaml
updates:
  pre_update_backup: false     # 升级前是否自动备份
  backup_keep: 5               # 自动备份保留份数
```

本机的升级回执里明确记录了跳过原因（真实 `~/.hermes/logs/update_receipts/latest.json` 节选）：

```json
{
  "skips": [
    {
      "name": "pre_update_backup",
      "reason": "disabled by updates.pre_update_backup (mode: off)",
      "at": "2026-10-08T14:24:56.361109+00:00"
    }
  ]
}
```

也就是说 `updates.pre_update_backup: false` 时，升级不会自动备份——那就得靠你手动先 `hermes backup --quick`。要不要开这个开关是权衡：开了更安全，但每次升级都会多一次全量 zip 的时间与磁盘占用。

```text
备份与恢复要点：
1. hermes backup 给的是「可恢复的整套 Hermes」，不含代码；代码回滚用 git reset --hard <old-sha>
2. 升级前最省事的保险是 hermes backup --quick，几秒钟只抓关键状态
3. -k 控制全量备份保留份数，默认 3；放自动化里要显式给，否则会堆 zip
4. updates.pre_update_backup 默认关，回执会记录 skip 原因——关了就得自己备份
5. /rollback 与 hermes checkpoints 只管文件改动，不是灾难恢复手段，别当备份用
```

## 版本升级流程

`hermes update` 做四件事：拉最新代码、重装依赖、迁移配置、重启相关服务。官方说明的选项是 `--check`（只预览不安装）与 `--backup`（拉取前做一次 HERMES_HOME 快照）。升级过程会写一份结构化回执到 `~/.hermes/logs/update_receipts/`，最新一份在 `latest.json`，里面含起止时间、argv、pid、outcome、pre_update / post_update 的 sha 与版本、每一步与跳过项、网关重启结果、fleet 检查结果。

本机 `latest.json` 的关键字段（真实内容节选）：

```json
{
  "schema": 1,
  "started_at": "2026-10-08T14:24:53.833673+00:00",
  "finished_at": null,
  "argv": ["/home/lw/.hermes/hermes-agent/venv/bin/hermes", "update"],
  "outcome": "running",
  "pre_update": {
    "sha": "cbe5e53e2826b949e4ab33dbd6d045e339fa162b",
    "short_sha": "cbe5e53e",
    "version": "0.21.6",
    "source": "git",
    "commit_date": 1791461176
  },
  "post_update": {},
  "plan": {
    "install_method": "git",
    "updatable_in_place": true,
    "update_mechanism": "hermes update"
  }
}
```

标准流程：

```shell
# 0) 先看有没有新版（不安装）
hermes update --check

# 1) 升级前留一手（不想依赖 updates.pre_update_backup 就手动做）
hermes backup --quick -l "pre-update"

# 2) 升级；--yes 用于非交互（自动接受配置迁移等提示）
hermes update --yes

# 3) 验证：版本、git 状态、日志
hermes --version
git -C /home/lw/.hermes/hermes-agent log -1 --format='%h %s'
git -C /home/lw/.hermes/hermes-agent status --short
hermes logs update -n 50
```

升级后的收尾是这一步里最容易被忽略的：网关的 unit 定义与代码版本绑定，升级后往往提示过时。本机实测状态（真实输出）：

```text
[警告] Installed gateway service definition is outdated
  Run: sudo hermes gateway restart --system  # auto-refreshes the unit
```

```shell
# 刷新 unit 并重启（一条命令同时完成）
sudo hermes gateway restart --system

# 确认配置迁移到位（升级会引入新配置项与默认值）
hermes config check
hermes config migrate
hermes config version 2>/dev/null || true

# 需要时做一次体检
hermes doctor
```

判断「升级真的生效」看三处：`hermes --version` 报的版本、install 目录的 git HEAD、以及网关日志里各平台重新连上的记录。强证据是回执 `latest.json` 里 `post_update.sha` 与 install 目录 HEAD 一致、且 `gateway_restart` 段非空——只有回执被写完整（`finished_at` 有值）才算这一轮升级闭环。

```shell
# 会话库升级后常常有优化空间（官方会在升级末尾提示）
hermes sessions optimize-storage    # 视版本可用；能显著缩小 state.db
```

```text
版本升级要点：
1. 先 --check 预览、再 backup --quick、然后 update --yes，最后验证三处（版本/git HEAD/网关日志）
2. 回执在 ~/.hermes/logs/update_receipts/latest.json；finished_at 为 null 说明这一轮没走完
3. 升级后 sudo hermes gateway restart --system 既刷新 unit 又重启服务，别只重启
4. hermes config check + migrate 处理新引入的配置项，尤其是跨多个版本升级时
5. 不要中途 kill 升级进程——留下半棵树比旧版本更麻烦
```

## 网络受限环境下的升级

`hermes update` 的瓶颈不在 Hermes 自己在 github.com 上的对象传输：被限速时 `git fetch` 会以 1-8 KB/s 的速度爬，或者直接以 `Operation too slow. Less than 2000 bytes/sec transferred the last 120 seconds` 失败。可行的做法是**先用镜像把对象取到本地，再让官方升级器做代码/依赖/配置/重启的活**。

关键事实：被限速的是 github.com 上的 git 协议端点（`...git/info/refs?service=git-upload-pack`），把它代理过去就能跑满带宽。实测 `https://gh-proxy.com/https://github.com/...` 约 1.9 MB/s；`codeload.github.com` 本身也不慢但只发 tarball，不能传 git 对象；ghfast.top、gh.llkk.cc、kkgithub、bgithub.xyz、gitclone.com 等候选实测多为死链/403/超时。

```shell
# 0) 侦察：版本、安装方式、目录归属、工作区是否干净
hermes --version
ls -ld /home/lw/.hermes/hermes-agent /home/lw/.hermes/hermes-agent/venv
git -C /home/lw/.hermes/hermes-agent status --short      # 必须干净

# 1) 用镜像把对象取下来（对象是内容寻址的，等价于从 origin 取，且不动 origin 的 URL）
git -C /home/lw/.hermes/hermes-agent fetch --progress \
  https://gh-proxy.com/https://github.com/NousResearch/hermes-agent.git \
  main:refs/remotes/origin/main
git -C /home/lw/.hermes/hermes-agent rev-list --count HEAD..origin/main   # 0 = 已经是最新

# 2) 先探一下镜像速度，别盲等
curl -sS -o /dev/null -w '%{speed_download}\n' \
  'https://gh-proxy.com/https://github.com/NousResearch/hermes-agent.git/info/refs?service=git-upload-pack'
```

如果升级器自己的 `git fetch origin` 中途挂掉（github.com 的解析 IP 会轮换，前一分钟能连下一分钟就连不上），就临时把 origin 指向镜像、升级完再改回来：

```shell
git -C /home/lw/.hermes/hermes-agent remote -v        # 先记下原始 URL
git -C /home/lw/.hermes/hermes-agent remote set-url origin \
  https://gh-proxy.com/https://github.com/NousResearch/hermes-agent.git
# ... 跑升级 ...
git -C /home/lw/.hermes/hermes-agent remote set-url origin \
  https://github.com/NousResearch/hermes-agent.git
```

真实升级往往要几分钟且**不能被中途杀掉**，所以让它脱离当前终端跑。Hermes 的终端工具不接受 `nohup`/`setsid` 包装，用一次性 systemd 单元：

```ini
# /root/hermes-update.sh（要点：显式导出 HOME / HERMES_HOME / PATH，再 cd 到 install 目录）
#   export HOME=/home/lw HERMES_HOME=/home/lw/.hermes
#   export PATH=/home/lw/.hermes/node/bin:/home/lw/.hermes/hermes-agent/venv/bin:$PATH
#   cd /home/lw/.hermes/hermes-agent
#   venv/bin/python -m hermes_cli.main update --yes
```

```shell
systemd-run --unit=hermes-update --collect \
  /bin/bash -c '/bin/bash /root/hermes-update.sh >> /var/log/hermes-update.log 2>&1'
systemctl is-active hermes-update
tail -30 /var/log/hermes-update.log
# 等日志里出现收尾标记（该实现的 ALL_DONE），而不是等单元存在
```

升级前如果跨了多个版本，先把「小而易备」的文件抓一份，代码回滚是免费的（旧提交还在祖先里，`git reset --hard <old-sha>` 即可）：

```shell
tar czf /srv/backups/hermes-home-$(date +%s).tgz -C /home/lw/.hermes \
  config.yaml auth.json state.db SOUL.md
```

```text
受限网络升级要点：
1. 被限速的是 github.com 的 git-upload-pack，用 gh-proxy.com 代理 git 协议即可跑满
2. 对象是内容寻址的，镜像 fetch 与从 origin fetch 等价，origin 可保持不动
3. 升级器自己的 fetch 失败时，临时把 origin 指向镜像，跑完改回
4. 升级必须脱离终端跑（一次性 systemd 单元），等日志里的收尾标记而不是等单元状态
5. 跨多版本升级前先 tar 一份 config.yaml / auth.json / state.db / SOUL.md
```

## 配置迁移与多 Profile 运维

配置有版本号（config.yaml 末尾的 `_config_version`）。升级引入新配置项后要迁移，命令是 `hermes config migrate`，检查是 `hermes config check`。

```shell
hermes config path               # 打印 config.yaml 路径
hermes config env-path           # 打印 .env 路径
hermes config show               # 看当前配置
hermes config get agent.max_turns
hermes config set approvals.mode smart
hermes config unset some.key
hermes config check              # 缺失/过期的配置项
hermes config migrate            # 补上新配置项
```

多 profile 是这里最容易出错的地方：每个 profile 有自己的 skills / plugins / cron / memories，而 `HERMES_HOME` 决定用哪一套。

```shell
hermes profile list
hermes profile show <name>
hermes profile create <name> --clone          # 克隆当前 profile 的配置
hermes profile use <name>                     # 设为粘性默认
hermes profile export <name>                  # 导出 tar.gz
hermes profile import <file>
```

三个必须知道的迁移事实：

1. **迁移只动「活动 home」。** 同一 home 下的 `profiles/<name>/` 会被自动迁移；完全独立的另一个 `HERMES_HOME`（例如 CLI 用 `/root/.hermes`、网关服务用 `/home/lw/.hermes`）不会被 `hermes update` 顺手迁移，要以该 home 的属主身份单独跑一次迁移。
2. **以属主身份执行，别用 root 代劳。** 让 root 去改别的用户的 config.yaml 会顺手改掉文件属主，之后该用户在网关里读配置就会出权限问题。
3. **升级后可能留下 fleet 重启标记。** 回执里 `finished_at` 为 null、或 `fleet_restart_pending` 标记文件残留时，后续每次 CLI 启动都会警告「上一次升级没有重启运行中的网关」。正确做法不是反复重试，而是核实：唯一在跑的网关状态里 `code_sha` 是否等于新的 HEAD、PID 是否等于该 unit 的 MainPID、`hermes gateway restart --system` 是否已经跑过；三项都成立后手工删掉该标记，再确认新开的 CLI 命令行不再告警。

```shell
# 以属主身份迁移另一个 home（示例形状，路径按实际替换）
runuser -u lw -- env HOME=/home/lw HERMES_HOME=/home/lw/.hermes \
  /home/lw/.hermes/hermes-agent/venv/bin/python -c \
  "from hermes_cli.config import migrate_config; print(migrate_config(interactive=False, quiet=False))"

# 局域网内多机互连：登记对端网关
hermes peer --help
```

```text
配置迁移要点：
1. 升级后跑 config check + migrate，跨多版本时必做
2. 迁移只覆盖活动 home；独立 HERMES_HOME 要以它的属主身份单独迁移
3. 永远以属主身份改配置，root 代劳会改掉文件属主
4. fleet_restart_pending 残留时先核实（gateway_state 的 code_sha、MainPID、restart --system），再手工清标记
5. profile 之间用 export / import 搬运，比手抄目录可靠
```

## 应用场景实战

### 场景一：规划一次可回滚的版本升级

目标：把一台跑着网关的机器从旧版本升到最新，全程可回滚，且升完确认「跑的是新代码」。

```shell
# 1) 侦察：当前版本、安装方式、工作区干净度
hermes --version
git -C /home/lw/.hermes/hermes-agent status --short
git -C /home/lw/.hermes/hermes-agent log -1 --format='%h %s'

# 2) 看有没有新版（不安装）
hermes update --check

# 3) 留退路：小而易备的关键文件 + 一次快速快照
tar czf /srv/backups/hermes-home-$(date +%s).tgz -C /home/lw/.hermes \
  config.yaml auth.json state.db SOUL.md
hermes backup --quick -l "pre-update"

# 4) 记录当前 HEAD，作为回滚锚点
git -C /home/lw/.hermes/hermes-agent rev-parse HEAD    # 记下这个 sha
```

```shell
# 5) 执行升级（非交互，自动接受配置迁移提示）
hermes update --yes

# 6) 验证三处：版本、git、回执
hermes --version
git -C /home/lw/.hermes/hermes-agent log -1 --format='%h %s'
python3 - <<'PY'
import json, os
p = os.path.expanduser("~/.hermes/logs/update_receipts/latest.json")
d = json.load(open(p))
print("outcome =", d.get("outcome"))
print("finished_at =", d.get("finished_at"))     # 为 null 说明这一轮没走完
print("pre  =", d.get("pre_update", {}).get("short_sha"))
print("post =", d.get("post_update", {}).get("short_sha"))
PY

# 7) 收尾：刷新网关 unit 并重启；迁移配置；体检
sudo hermes gateway restart --system
hermes config check
hermes config migrate
hermes doctor
```

```text
# 升级后的期望状态：
#   hermes --version                  → 新版本号
#   git log -1 --format='%h %s'       → 新提交
#   latest.json: finished_at 非空，post_update.sha == 新 HEAD
#   systemctl is-active hermes-gateway → active
#   hermes logs gateway -n 50         → 各平台重新连上（出现 connected 类记录）
```

```shell
# 出问题时的回滚（代码免费回滚到记录的 sha）
git -C /home/lw/.hermes/hermes-agent reset --hard <第 4 步记下的 sha>
sudo hermes gateway restart --system
```

关键点：升级前记录 HEAD 是最便宜的回滚保险（代码在 git 里，回滚零成本）；配置与数据回滚靠第 3 步的 tar 与 `hermes backup --quick`。验证时一定要看回执的 `finished_at` 与 `post_update.sha`——只看到命令退出码为 0 不足以证明升级闭环。

### 场景二：github 被限速时完成升级

目标：在 github.com 直连只有几 KB/s 的网络里，把升级全程跑完，并且验证新代码真的被网关加载。

```shell
# 1) 探镜像速度（别盲等）
curl -sS -o /dev/null -w 'gh-proxy speed = %{speed_download} B/s\n' \
  'https://gh-proxy.com/https://github.com/NousResearch/hermes-agent.git/info/refs?service=git-upload-pack'

# 2) 先手工预取对象（走镜像，不动 origin 的 URL）
git -C /home/lw/.hermes/hermes-agent remote -v
git -C /home/lw/.hermes/hermes-agent fetch --progress \
  https://gh-proxy.com/https://github.com/NousResearch/hermes-agent.git \
  main:refs/remotes/origin/main
echo "落后提交数 = $(git -C /home/lw/.hermes/hermes-agent rev-list --count HEAD..origin/main)"

# 3) 升级脱离终端跑：写成脚本 + 一次性 systemd 单元
```

```ini
# /root/hermes-update.sh 的内容要点（root 启动，但全程切到网关属主的环境）
#   export HOME=/home/lw
#   export HERMES_HOME=/home/lw/.hermes
#   export PATH=/home/lw/.hermes/node/bin:/home/lw/.hermes/hermes-agent/venv/bin:$PATH
#   cd /home/lw/.hermes/hermes-agent
#   venv/bin/python -m hermes_cli.main update --yes
```

```shell
systemd-run --unit=hermes-update --collect \
  /bin/bash -c '/bin/bash /root/hermes-update.sh >> /var/log/hermes-update.log 2>&1'

# 观察进度（等日志收尾标记，不是等单元消失）
sleep 30; tail -30 /var/log/hermes-update.log
systemctl is-active hermes-update
```

```shell
# 4) 验证「新代码真的在跑」：对比网关状态里记录的 code_sha 与 install 目录 HEAD
git -C /home/lw/.hermes/hermes-agent log -1 --format='%h %s'
cat /home/lw/.hermes/gateway_state.json 2>/dev/null | head -20
systemctl is-active hermes-gateway
hermes logs gateway -n 30
ls -l /home/lw/.hermes/cron/ticker_heartbeat    # cron ticker 是否活着

# 5) 恢复 origin 的原始 URL（如果第 3 步前临时改过）
git -C /home/lw/.hermes/hermes-agent remote set-url origin \
  https://github.com/NousResearch/hermes-agent.git
git -C /home/lw/.hermes/hermes-agent remote -v
```

```text
# 判断升级闭环的硬条件：
#   网关状态里的 code_sha == install 目录 HEAD          （最强证据：运行时确实加载了新代码）
#   systemctl is-active hermes-gateway                  → active
#   hermes logs gateway 里有平台 connected 记录
#   cron/ticker_heartbeat 的时间戳是新近的
# 若 origin 仍指向镜像，fleet 检查会显示「与你的 fork 同步（未检查官方仓库）」——恢复 URL 即消失
```

关键点：镜像只解决「对象传输」，升级器自己的 fetch 与代码/依赖/配置/重启步骤照旧。用一次性 systemd 单元脱离终端是硬要求——升级被中途杀掉留下的半棵树比旧版本更难处理。用镜像当 origin 会带来一句正常的副产物提示（未检查官方仓库），恢复 URL 后即恢复。

## 最佳实践与踩坑记录

### 最佳实践

1. 升级三步走：`--check` 预览 → `backup --quick` 留一手 → `update --yes`，然后验证版本 / git HEAD / 回执三处
2. 升级前记录 `git rev-parse HEAD`，代码回滚就变成一条零成本的 `git reset --hard`
3. 升级后必做两件收尾：`sudo hermes gateway restart --system`（刷新 unit + 重启）与 `hermes config check && hermes config migrate`
4. 别在长期无人看管的机器上关掉 `updates.pre_update_backup`，除非你已经有独立备份流水线
5. 判定网关是否在跑一律以 `systemctl is-active` 为准，别拿 `hermes gateway list` 或 `hermes status` 的单一视角下结论
6. 多 home 环境升级以「各 home 的属主」身份分别迁移配置，绝不用 root 代劳
7. 受限网络下先把镜像速度量出来（`curl -w '%{speed_download}'`），再决定是否手工预取对象

### 踩坑记录

```text
坑 1：升级命令退出码是 0，但跑的还是旧代码
结论：版本号变了、日志看起来也正常，网关行为却还是旧的。
原因：回执里 finished_at 仍为 null / post_update 为空，说明这一轮没走完（常见于升级进程被中途打断，或 fleet 重启阶段失败）；网关进程也还持有旧代码。
解法：看 ~/.hermes/logs/update_receipts/latest.json 的 finished_at 与 post_update.sha；再对比网关状态里的 code_sha 与 install 目录 HEAD。不一致就跑 sudo hermes gateway restart --system，必要时重跑 hermes update --yes。

坑 2：升级后每次启动 CLI 都警告「a previous update did not restart running gateways」
结论：警告反复出现，反复重跑升级也不消失。
原因：升级留下的 $HERMES_HOME/fleet_restart_pending 标记没被清掉。两种典型成因：collect_fleet_versions() 扫描的是「调用方 HERMES_HOME」的 profile home，跨 home（CLI 用 /root/.hermes、网关用 /home/lw/.hermes）时看不到对端；或从 systemd 一次单元里跑升级导致 user-scope 单元枚举失败。
解法：核实而非无限重试——(a) 唯一在跑的网关状态里 code_sha == 新 HEAD 且 pid == 该 unit 的 MainPID；(b) hermes gateway restart --system 已跑过；(c) 若存在但被设计性禁用的 user-scope unit 属正常。三项成立后手工删掉 fleet_restart_pending，再开一个新 CLI 确认不再告警。

坑 3：doctor 报「Large WAL file — cannot prove state.db is quiet」
结论：体检给出 1 条待处理项，提示无法确认 state.db 处于静默状态。
原因：SQLite WAL 模式下有长连接（网关进程）持有读事务时，WAL 无法回卷，文件会持续增长。
解法：先停该 profile 的网关，再跑 hermes doctor --fix 做检查点；长期做法是给会话库配 sessions.retention_days 并定期 prune + vacuum 回收空间。

坑 4：升级后网关服务定义过时，平台连接行为异常
结论：hermes gateway status 提示 installed gateway service definition is outdated，某些设置（如 systemd 看门狗）不生效。
原因：unit 文件是安装/上次重生成时的产物，升级后模板变化不会自动套用到已存在的 unit。
解法：sudo hermes gateway restart --system —— 它会刷新 unit 并重启；若手动改过 gateway.systemd_watchdog_seconds 之类的项，用 hermes gateway install --force 明确重生成。

坑 5：升级跨了多个版本，配置项缺失导致启动报错
结论：新版本读不到某些新配置项，行为异常或直接报错。
原因：config.yaml 有版本号（_config_version），跨版本升级需要迁移才能补上新项与默认值。
解法：升级后跑 hermes config check 看缺失项，再 hermes config migrate；完全独立的另一个 HERMES_HOME 要以它的属主身份单独迁移。

坑 6：升级中途被 Ctrl+C / 超时杀掉，仓库变成半棵树
结论：之后 hermes 起不来，git status 一堆脏文件，重新跑升级也失败。
原因：升级要拉代码、装依赖、改配置、重启服务，被杀在中间会留下不一致状态；旧提交虽然还是祖先，但工作区与依赖都已半改。
解法：升级绝不前台跑在会超时的会话里——用一次性 systemd 单元（systemd-run --unit=hermes-update --collect），等日志里的收尾标记。已经半死状态时：先 git status 看脏点，必要时 git reset --hard 到记录的旧 sha，再重跑一次完整升级。
```
