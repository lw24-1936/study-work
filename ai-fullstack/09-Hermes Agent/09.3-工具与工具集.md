## 概述

工具（tool）是 Hermes 里一切能力的统一接口：内置功能、插件注册的功能、MCP server 提供的功能，模型看到的都是同一类「名字 + 描述 + JSON Schema 参数」的函数。工具不是一个个独立开关，而是按「工具集」（toolset）分组管理——工具集才是启用/禁用的粒度，也是平台预设的组成单位。当前官方 registry 约 100 个内置工具，其中浏览器工具就有 10 个核心工具加 2 个 CDP 门控工具与 5 个保管库工具。

本篇讲四件事：内置工具集有哪些、怎么启停、不同入口（CLI / 网关 / webhook / 桌面）为什么工具不一样、以及工具太多时「延期工具检索」怎么把上下文压住。最后讲调用策略：同轮并发、失败护栏、输出截断与审批。

```text
本节要点：
1. 粒度是工具集不是单个工具 —— hermes tools enable/disable 操作的是工具集（如 web、browser、terminal）
2. 平台预设不同 —— hermes-cli 是全集，webhook 触发只有只读子集，桌面来源会多出 desktop_ui / catalog 这类工具集
3. 运行时门控 —— 很多工具带 check_fn，凭据缺失时自动不出现（例如 x_search 需要 xAI 凭据）
4. 延期检索 —— 工具数量大时它们不在初始提示词里，模型先用 tool_search 找、tool_describe 看签名、tool_call 调用
5. 生效时机 —— 工具变更在新会话（/reset）生效，中途改动不生效以保护 prompt caching
6. 本机实测 —— CLI 平台 25 个内置工具集（19 启用 6 禁用）+ 1 个插件工具集 + 1 个 MCP server（rea）
```

## 内置工具集分类

按能力分，内置工具集可以归成八类：Web、X 搜索、终端与文件、浏览器、媒体、Agent 编排、记忆与检索、自动化，另有集成类（MCP 与插件工具）。每一类下面是若干具名工具，例如 `terminal` 工具集里是 `terminal` 与 `process_manage` 两个工具，`skills` 工具集里是 `skill_manage`、`skill_view`、`skills_list` 三个。

| 类别 | 代表工具 | 说明 |
| --- | --- | --- |
| Web | `web_search`、`web_extract` | 联网检索与页面正文抽取 |
| X 搜索 | `x_search` | 通过 xAI 的 Responses 工具只读检索 X 内容；需要 xAI 凭据，默认关闭 |
| 终端与文件 | `terminal`、`process_manage`、`read_file`、`write_file`、`patch`、`search_files` | 执行命令与读写文件 |
| 浏览器 | `browser_navigate`、`browser_click`、`browser_console`、`browser_exec` 等 | 真浏览器自动化，10 个核心工具 + CDP 门控工具 + 保管库工具 |
| 媒体 | `vision_analyze`、`image_generate`、`text_to_speech`、`video_analyze` | 多模态分析与生成 |
| Agent 编排 | `todo_list`、`clarify`、`execute_code`、`delegate_task` | 计划、澄清、沙箱执行、子代理 |
| 记忆与检索 | `memory`、`session_search` | 长期记忆与历史会话检索 |
| 自动化 | `cronjob_manage` | 定时任务管理（投递由 cron 自身与 `hermes send` 负责） |
| 集成 | MCP 工具（`mcp__<server>__<tool>`）、插件工具 | MCP server 与插件带来的工具 |

```text
5. 权威清单 —— 以源码 toolsets.py 与官方 Toolsets Reference 页为准，版本升级会增减条目
6. 工具总数 —— 官方文档口径约 100 个内置工具，单看浏览器就有 10 个核心工具
```

## 工具的启用与禁用

启用/禁用的操作面有三个：交互式 UI（`hermes tools`，需要真终端）、命令行子命令（`hermes tools list|enable|disable`）、以及一次性覆盖（`hermes chat --toolsets "web,terminal"`）。配置层面落在两个地方：`toolsets` 列表声明该平台挂哪几套预设，`agent.disabled_toolsets` 做减法。

```bash
# 1. 交互式配置（curses UI，必须直接在终端里跑）
hermes tools

# 2. 命令行清单与开关
hermes tools list
hermes tools enable web
hermes tools disable browser
hermes tools disable rea:analyze_function   # MCP 工具用 server:tool 记法

# 3. 单次会话覆盖（不写配置，适合脚本与临时任务）
hermes chat -t "web,terminal" -q "查一下 nginx 的常见 502 排查步骤"
hermes chat --toolsets "search,safe" -q "只做资料检索，不要动文件"

# 4. 会话内查看（CLI 斜杠命令）
#    /toolsets   —— 列出当前可用工具集
#    /tools      —— 打开工具管理界面
#    /reload-mcp —— 重新加载 MCP server
```

```yaml
# ~/.hermes/config.yaml 里的真实结构（本机节选）
toolsets:
  - hermes-cli            # 该平台使用 hermes-cli 这套预设

agent:
  max_turns: 90
  disabled_toolsets: []   # 在这里做减法，例如 [browser, image_gen]
```

```bash
# 也可用 config 命令改（等价，但 tools 子命令语义更清楚）
hermes config set toolsets '["hermes-cli"]'
hermes config set agent.disabled_toolsets '["browser"]'
```

```text
启用与禁用要点：
1. 三个面 —— 交互式 hermes tools、命令行 hermes tools enable/disable、单次 hermes chat -t
2. 配置两处 —— toolsets 决定预设整套，agent.disabled_toolsets 做减法；命令行优先
3. MCP 记法 —— MCP 工具用 server:tool 形式（如 github:create_issue）禁用
4. 生效时机 —— 改完要新开会话（/reset）或重启进程，中途不变
5. 交互式 UI 要真终端 —— 在管道/非交互子进程里跑 hermes tools 会直接报错退出
6. 收窄工具是有意义的优化 —— 工具少了提示词更短、模型选择更准、危险面更小
```

## 平台工具集与运行时门控

同一个 Hermes，接到不同入口时挂的工具集并不相同，这是「为什么我的 TG 机器人跑不了命令」这类问题的根源。CLI 是全集；ACP（IDE 集成）刻意去掉 `clarify`、`cronjob`、图像生成、TTS、computer_use 与 kanban；API Server 去掉需要人机交互的几项；webhook 触发只给只读子集；桌面来源会额外获得 `desktop_ui`、`project`、`catalog` 这类操作界面本身的工具集。

| 工具集预设 | 与 hermes-cli 的差异 |
| --- | --- |
| `hermes-cli` | 全集：file、terminal、web、browser、memory、skills、vision、image_gen、todo、tts、delegation、code_execution、cronjob、session_search、clarify、computer_use 与 kanban 类工具（运行时按 check_fn 门控） |
| `hermes-acp` | 去掉 `clarify`、`cronjob`、`image_generate`、`text_to_speech`、`computer_use` 与 kanban 工具，聚焦 IDE 内的编码任务 |
| `hermes-api-server` | 去掉 `clarify`、`text_to_speech`、`computer_use` 与 kanban 工具，保留其余，适合无法与人交互的编程访问 |
| `hermes-telegram` / `hermes-slack` / `hermes-whatsapp` | 与 `hermes-cli` 相同 |
| `hermes-discord` | 在 `hermes-cli` 基础上增加 `discord` 与 `discord_admin` |
| `hermes-webhook` | 受限只读子集：只有 `web_search`、`web_extract`、`vision_analyze`、`clarify`，没有终端、文件与浏览器 |
| `hermes-gateway` | 内部编排用，是所有 `hermes-<platform>` 的并集 |
| `hermes-yuanbao` / `hermes-feishu` | 在 `hermes-cli` 上分别增加 `yb_*` / `feishu_doc_*`、`feishu_drive_*` 工具 |

运行时门控是第二层过滤：工具自带的 `check_fn` 决定它在当前环境是否出现。凭据缺失、平台不支持、依赖未装，都会让工具静默消失而不是报错。比如 `x_search` 需要 xAI 凭据（SuperGrok OAuth 或 `XAI_API_KEY`），`memory` 类工具需要记忆功能开启，桌面专属工具集在 CLI / 网关 / cron 会话里永远不出现——即使配置里写了名字，`all` 也不包含 `catalog` 这类需要显式启用的工具集。

```text
平台工具集与门控要点：
1. 预设不同是特性不是 bug —— 用 hermes tools list 核对目标入口到底挂了多少工具
2. webhook 最窄 —— 只读四件套；需要写操作的自动化不要走 webhook 触发
3. IDE 场景去交互 —— hermes-acp 去掉 clarify/cronjob/computer_use，避免等待人类输入
4. 门控会静默 —— 工具不出现多半是缺凭据或缺依赖，先查 .env 与 hermes doctor
5. 桌面专属 —— desktop_ui / project / catalog 只在桌面来源的会话里存在，且 catalog 默认延期
6. 查看方式 —— 会话里 /toolsets，命令行 hermes tools list，两者反映的都是当前会话/平台的实际结果
```

## 延期工具检索与工具目录

工具一多，把全部 JSON Schema 塞进系统提示词就会吃掉大量上下文，还会让模型选错。Hermes 的做法是「延期工具」（deferred tools）：默认只暴露一小段摘要目录（每个工具的名字加一行描述），模型需要时先用 `tool_search` 按关键词检索、`tool_describe` 拉取完整参数 schema、再用 `tool_call` 执行。官方文档明确说明 `catalog` 工具集默认就处于这种延期加载状态。

```text
延期工具的三段式（工具检索目录的固定结构）：

tool_search(queries=["github create issue", "slack send message"])
  → 返回匹配的工具名，按查询分组，外加一份 name -> description 的映射

tool_describe(names=["mcp__rea__analyze_function"])
  → 返回该工具的完整 JSON Schema（参数、必填项、取值范围）

tool_call(calls=[{name: "mcp__rea__analyze_function", arguments: {...}}])
  → 真正执行；多个调用可放在一个数组里批量提交
```

本机的真实情况：MCP server `rea` 提供 172 个工具，加上内置与插件工具，工具检索目录里有 176 个延期工具条目。`hermes mcp list` 显示 `rea` 的 Tools 列是 `all`（即全部工具可用），但这些工具并不会全部进入初始提示词。

```text
$ hermes mcp list
MCP Servers:

  Name             Transport                      Tools        Status
  ---------------- ------------------------------ ------------ ----------
  rea              /root/.hermes/tools/node-...   all          ✓ enabled

$ hermes mcp configure rea      # 交互式勾选哪些 MCP 工具对本会话可见（工具裁剪）
```

```bash
# MCP 侧的管理命令
hermes mcp list                 # 列出已配置的 server 与工具状态
hermes mcp add NAME --url ...   # 添加 HTTP 型 server
hermes mcp add NAME --command ... # 添加 stdio 型 server
hermes mcp test NAME            # 测试连通性
hermes mcp configure NAME       # 勾选工具子集（裁剪后可显著减少延期条目）
hermes mcp remove NAME          # 移除
```

```text
延期工具检索要点：
1. 动机 —— 工具 schema 是上下文里最贵的东西之一，延期加载把「可选能力」挤出提示词
2. 三段式 —— tool_search 找、tool_describe 看签名、tool_call 执行；批量调用放在一个 calls 数组里
3. 关键词要像工具文本 —— 检索是关键词匹配，用「服务名 + 动作 + 对象」，不要写自然语言问句
4. 哪些默认延期 —— 官方文档点名 catalog 工具集；MCP server 的工具（本机 rea 的 172 个）同样按需加载
5. 减少条目的正解 —— 用 hermes mcp configure 裁剪 MCP 工具子集，而不是把整个 server 关掉
6. 与工具集启停的关系 —— 禁用工具集是不给用，延期加载是「能用但不占位」，两者解决不同问题
```

## 工具调用策略与并发

工具调用的行为由三层控制：模型侧（一轮里能否并发发出多个 tool_calls）、运行时侧（输出截断、失败护栏、后台进程）、安全侧（审批与 sandbox）。并发是默认能力：互相独立的调用应该放在同一轮里批量发出，运行时并发执行；有依赖的调用才必须串行。运行时护栏则由 `tool_output` 与 `tool_loop_guardrails` 两段配置决定。

```yaml
# ~/.hermes/config.yaml 实测节选（第 68-96 行附近）
tool_output:
  max_bytes: 50000        # 单次工具输出上限，超出被截断，完整内容另存文件
  max_lines: 2000
  max_line_length: 2000
tool_loop_guardrails:
  warnings_enabled: true
  hard_stop_enabled: false
  warn_after:
    exact_failure: 2      # 同一失败连续 2 次 -> 提醒模型换方案
    same_tool_failure: 3  # 同一工具连续失败 3 次 -> 提醒
    idempotent_no_progress: 2
  hard_stop_after:
    exact_failure: 5
    same_tool_failure: 8
    idempotent_no_progress: 5
delegation:
  max_concurrent_children: 10   # 子代理并发上限（本机配置）
  max_spawn_depth: 1
agent:
  max_turns: 90                 # 单轮对话最多 90 个迭代回合
  api_max_retries: 3
```

```bash
# 后台进程：长任务不要让工具调用阻塞
# terminal(background=true, notify=true) 返回 {"session_id": "proc_xxx", "pid": 12345}
# 然后用 process_manage 管理：
#   list / poll / wait / log / kill / write

# 审批模式（危险命令是否需要人确认）
hermes config set approvals.mode smart    # manual（默认）/ smart / off
hermes --yolo                             # 单次绕过审批
```

```text
调用策略与并发要点：
1. 并发是默认 —— 独立调用放同一轮批量提交，运行时并发执行；有依赖才串行
2. 输出有上限 —— tool_output 决定单次输出截断点，被截断时完整内容会另存文件供 read_file 翻页
3. 失败有护栏 —— exact_failure / same_tool_failure / idempotent_no_progress 三类计数，先告警后硬停
4. 长任务走后台 —— terminal 的 background 模式 + process_manage，避免一轮里死等
5. 预算可见 —— agent.max_turns 限制迭代次数，跑满会强制收尾；大任务拆成子代理更稳
6. 有副作用的调用要审批 —— approvals.mode 默认 manual，生产环境不要关
```

## 应用场景实战

### 场景一：为「只读资料调研」搭一个最小工具集会话

需求：让 Agent 帮团队做竞品资料调研，只允许联网检索与读网页，禁止写文件、跑命令、生成图片。做法是不改全局配置，而是每次用 `--toolsets` 显式指定只读子集，并把审批模式保持在最严。

```bash
# 1. 只读调研：web + search 足够；safe 是官方定义的只读研究 + 媒体生成预设
hermes chat --toolsets "web,search" -q "检索 2026 年主流 Agent 框架的官方文档入口，输出表格"

# 2. 需要看图但不要动文件时，加上 vision
hermes chat --toolsets "web,vision" -q "读取我给的截图并总结其中的错误信息"

# 3. 校验这次会话的真实工具清单（交互式 UI 需要真终端）
hermes tools list

# 4. 想固定成「调研专用」形态：为它单开一个 profile，写死工具集
hermes profile create research --clone
hermes -p research config set toolsets '["hermes-cli"]'
hermes -p research config set agent.disabled_toolsets '["terminal","file","code_execution","browser","image_gen","spotify"]'
hermes -p research chat -q "现在你只有 web/vision/memory 等工具，请确认后开始调研"
```

```text
# 关键点
# 1) --toolsets 是一次性覆盖，不污染全局配置；适合把「只读任务」和「可写任务」分开
# 2) safe 工具集官方定义：只读研究 + 媒体生成，没有文件写入、没有 terminal、没有代码执行
# 3) disable 做减法时注意依赖关系：禁用 terminal 会连带失去 process_manage 与后台进程能力
# 4) 用 profile 固化策略，比每次手敲参数更不容易漏配；审计时看 config.yaml 的 disabled_toolsets 即可
# 5) 生效验证：hermes tools list 输出的 ✓/✗ 列就是最终答案（改配置后需新会话）
```

### 场景二：裁剪一个 172 工具的 MCP server，只保留本次任务需要的几个

需求：本机接了 `rea` 这个逆向工程 MCP server，提供 172 个工具，日常只需其中 5 个（打开二进制、看概览、列函数、反编译、列字符串）。全量挂着既浪费延期检索的检索成本，也让模型更容易选错工具。做法是用 `hermes mcp configure` 做工具子集裁剪，并在配置里确认。

```bash
# 1. 先看现状：server 名、传输方式、工具数与开关状态
hermes mcp list

# 2. 连通性测试（确认真能连上再谈裁剪）
hermes mcp test rea

# 3. 交互式勾选工具子集（在真终端里执行）
hermes mcp configure rea

# 4. 会话内重载 MCP，无需重启进程
#    在对话里输入：/reload-mcp

# 5. 回到命令行核对结果
hermes mcp list
hermes tools list | tail -5
```

```text
$ hermes mcp list
MCP Servers:

  Name             Transport                      Tools        Status
  ---------------- ------------------------------ ------------ ----------
  rea              /root/.hermes/tools/node-...   all          ✓ enabled

# 裁剪后再看 Tools 列会变成具体数量，例如 5；hermes tools list 末尾的
# "MCP servers:" 段落也会反映该 server 的启用工具情况
$ hermes tools list
MCP servers:
  rea  all tools enabled

# 关键点
# 1) 先 test 再 configure：连不上时裁剪毫无意义，排查要看 server 进程与凭据
# 2) 裁剪立刻降低延期检索的条目数，检索更准、轮次更少
# 3) 改了 MCP 配置在会话内用 /reload-mcp 生效，不必重启网关
# 4. 只想临时排除某个工具用：hermes tools disable rea:<tool_name>
# 5) stdio 型 server 的配置文件在 ~/.hermes/config.yaml 的 mcp_servers 段（本机为 command + args 形式）
```

## 最佳实践与踩坑记录

### 最佳实践

1. 按任务而不是按习惯挂工具集：只读调研用 `web,search` 或 `safe`，编码用默认，临时任务用 `--toolsets` 一次性覆盖，不要为了省事全开
2. 每次新增工具或凭据后跑一次 `hermes tools list`：✓/✗ 列是最终事实，能立刻区分「配置没写对」与「凭据没生效」
3. 大 server 一定要裁剪：MCP 工具按需加载虽省上下文，但检索成本与选错概率随条目数上升，`hermes mcp configure` 是性价比最高的一步
4. 长任务用后台模式加通知：`terminal(background=true, notify=true)` 配 `process_manage`，比让一个 tool call 阻塞十几分钟更可控
5. 生产环境保持 `approvals.mode: manual`：这是 `rm -rf` 一类命令的最后一道闸；`--yolo` 只用于一次性沙箱
6. 把工具上限当预算管理：`agent.max_turns`、`delegation.max_concurrent_children`、`tool_output.max_bytes` 三个数共同决定单次任务的成本上限

### 踩坑记录

```text
坑 1：在脚本/管道里跑 hermes tools 想自动化配置
结论：命令直接报错退出，配置没改。
原因：不带子命令的 hermes tools 是 curses 交互式 UI，检测到非交互终端就拒绝运行。
解法：脚本里只用 hermes tools list / enable / disable 三个子命令，或直接改 config.yaml 的 toolsets 与 agent.disabled_toolsets。

坑 2：禁用 browser 之后 web_search 也没了
结论：本来想只去掉浏览器自动化，结果连简单的网页检索都不可用。
原因：对工具集之间的包含关系不清楚——官方文档说明 web_search 属于 web / search 工具集，而把 browser 关掉不会连带 web；真正让检索消失的，往往是把 web 或整个预设改成了不含它的子集（如 webhook 预设）。
解法：改完立刻 hermes tools list 核对；Minimal 场景直接选 safe / search 这类语义明确的预设，而不是靠禁用拼出来。

坑 3：MCP 的某个工具明明装了却调不到
结论：server 显示 enabled，但模型说没有这个工具。
原因：MCP 工具是延期加载的，模型必须先用 tool_search 检索到才能 tool_describe / tool_call；此外 server 若被裁剪，工具也确实不存在。
解法：确认 hermes mcp list 里 Tools 列包含该工具；会话内 /reload-mcp 重载；提示模型「先用 tool_search 找 xxx」。

坑 4：工具输出太长导致模型看漏关键信息
结论：命令明明跑成功了，模型却基于截断后的片段下结论。
原因：tool_output.max_bytes / max_lines 会截断单次输出，被截断时完整内容另存文件，模型需要主动去读。
解法：把命令本身写得更聚焦（grep/head 过滤），而不是简单加大 max_bytes；需要全文时用 read_file 翻页读另存的完整输出。

坑 5：工具连续失败后整个任务卡住
结论：多轮重试同一个命令，迟迟没有产出。
原因：tool_loop_guardrails 对 exact_failure / same_tool_failure / idempotent_no_progress 计数，触发告警后若模型仍不改变策略，只能等 hard_stop 或 max_turns 耗尽。
解法：把 hard_stop_enabled 视需要打开；从根本上要求模型在失败两次后换方案；长任务拆给子代理，避免单个会话耗到预算上限。

坑 6：改完工具集当前会话立刻验证，误判为「配置无效」
结论：配置写对了，行为没变，于是反复改配置。
原因：工具清单在会话建立时冻结（保护 prompt caching），中途变更不生效。
解法：/reset 或重启后再验证；把「改配置 -> 新会话 -> 验证」当成固定流程。
```
