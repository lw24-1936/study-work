## 概述

「后台运行」在 Hermes 里是两层东西：**调度层**是 cron 子系统（作业定义落在 `~/.hermes/cron/jobs.json`，由常驻的 gateway 每 60 秒 tick 一次，到点就在一个**全新的隔离会话**里跑），**进程层**是 gateway 这个常驻服务本身，以及智能体在单个会话里用 `background=true` 起的终端进程。两者的失败语义完全不同：cron 作业的每次尝试都写进 `executions.db` 执行账本，可查、可审、可自愈；会话里的后台进程只活在那个会话生命周期内。

```text
本节要点：
1. 调度器 —— gateway 每 60 秒 tick 一次；没有 gateway 服务在跑，cron 作业一律不触发
2. 作业存储 —— ~/.hermes/cron/jobs.json（原子写），输出存 ~/.hermes/cron/output/<job_id>/<时间戳>.md
3. 两种模式 —— agent 模式（跑 LLM，可挂技能/脚本）与 no-agent 模式（只跑脚本，stdout 直接投递，零 LLM）
4. 隔离性 —— 每次运行都是干净会话：无历史、无记忆、不能反问，cronjob 工具被禁用（防递归）
5. 可观测 —— 执行账本 executions.db（claimed/running/completed/failed/unknown）+ hermes cron runs/incidents/doctor
6. 后台进程 —— 会话内用 terminal 的 background 模式；要跨重启就用 gateway 服务或 systemd
```

## cron 的存储与执行单元

cron 子系统刻意做得「可审计」：作业定义是磁盘上的普通 JSON，输出是普通 Markdown 文件，执行尝试有一条不可变的账本。三者都在 profile 自己的 home 下，所以备份、迁移、排查都不需要数据库工具。

本机真实目录：

```text
$ ls -la /root/.hermes/cron/
-rw-r--r-- 1 root root 40960 10月 15 00:44 executions.db     # 执行账本（SQLite）
-rw------- 1 root root  1362 9月 25 09:59 jobs.json          # 作业定义（原子写）
-rw-r--r-- 1 root root     0 9月 25 09:59 .jobs.lock         # 作业文件锁
-rw-r--r-- 1 root root     0 8月 13 10:01 .tick.lock         # 调度锁（防重复 tick）
-rw-r--r-- 1 root root 12288 9月 12 11:53 notepad.db         # 作业持久化便签 KV
-rw------- 1 root root  1104 9月 25 00:45 suggestions.json
-rw-r--r-- 1 root root  2777 9月 25 09:59 usage_audit.jsonl  # 用量审计
drwx------ 2 root root  4096 10月 15 09:55 output/            # 每次运行的输出
```

作业记录是一个扁平 JSON（原子写：写临时文件再 rename，所以断电不会留半截文件）。官方文档给出的字段形态：

```json
{
  "id": "a1b2c3d4e5f6",
  "name": "Daily briefing",
  "prompt": "Summarize today's AI news and funding rounds",
  "schedule": { "kind": "cron", "expr": "0 9 * * *", "display": "0 9 * * *" },
  "skills": ["ai-funding-daily-report"],
  "deliver": "telegram:-1001234567890",
  "repeat": { "times": null, "completed": 42 },
  "state": "scheduled",
  "enabled": true,
  "next_run_at": "2025-01-16T09:00:00Z",
  "last_run_at": "2025-01-15T09:00:00Z",
  "last_status": "ok",
  "created_at": "2025-01-01T00:00:00Z",
  "model": null,
  "provider": null,
  "script": null
}
```

作业生命周期状态有四个：`scheduled`（到点会跑）、`paused`（暂停，resume 后重算下次时间）、`completed`（重复次数用尽或一次性已触发）、`running`（瞬态）。老作业里的单数 `skill` 字段在加载时会被规范化为 `skills: [skill]`。

每次运行都是**全新会话**，这一点决定了 prompt 的写法：

```text
# 差：会话里没有上文，代理无法知道「那台服务器」是哪台
"Check on that server issue"

# 好：自包含，含主机、用户、命令、判定标准
"SSH into server 192.168.1.100 as user 'deploy', check if nginx is running with
 'systemctl status nginx', and verify https://example.com returns HTTP 200."
```

写 `jobs.json` 的正确姿势永远是命令（`hermes cron edit` / `/cron` / `cronjob` 工具），不要手改文件：直接编辑可能被文件写入安全策略静默拦下（例如设置了 `HERMES_WRITE_SAFE_ROOT` 时）。当 `model`/`provider` 为 `null` 时，模型在**触发时刻**解析：作业级 pin → `cron.model` → 全局默认（`hermes model`）。

```text
存储与执行单元要点：
1. 三份数据 —— jobs.json（定义）、executions.db（账本）、output/<job_id>/*.md（输出）
2. 原子写 —— 作业文件写临时文件再 rename，无半截文件；jobs.json 直接继承了 hermes update 与重启
3. 定时器身份 —— gateway 进程负责 tick；CLI 模式下只在你主动运行 cron 命令或会话活跃时才可能触发
4. 会话隔离 —— 每次运行全新会话，无历史无记忆，不能反问；prompt 必须自包含
5. 递归防护 —— cron 运行里的 cronjob 工具集被禁用，作业不能创建作业（除非显式打开 allow_agent_scheduling）
6. 别手改 jobs.json —— 用 hermes cron edit / cronjob 工具，手改可能被文件写入策略静默拦下
```

## 调度表达与 tick 机制

调度支持四种写法，覆盖「一次性延迟」到「标准 cron 表达式」：

| 形式 | 示例 | 行为 |
|---|---|---|
| 相对延迟 | `30m`、`2h`、`1d` | 一次性，延迟后触发 |
| 间隔 | `every 2h`、`every 30m` | 循环，按间隔触发 |
| cron 表达式 | `0 9 * * *` | 标准 5 字段（分 时 日 月 周） |
| ISO 时间戳 | `2025-01-15T09:00:00` | 一次性，定点触发 |

每次 tick 的动作序列是固定的：

```text
tick()
1. 取调度锁（防止重叠 tick）
2. 从 jobs.json 加载全部作业
3. 过滤出到期作业（next_run <= now 且 state == scheduled）
4. 对每个到期作业：
   a. 状态置 running
   b. 创建全新的 AIAgent 会话（无历史）
   c. 按顺序加载挂载的技能（作为 user 消息注入）
   d. 跑作业 prompt
   e. 投递结果到配置目标
   f. 更新 run_count，计算 next_run
   g. 重复次数用尽 -> completed；否则 -> scheduled
5. 写回 jobs.json
6. 释放调度锁
```

跨进程用文件锁（Unix 上 `fcntl.flock`）保证同一批到期作业不会被并发跑两次——即使 gateway 的进程内 ticker 和手工 `hermes cron tick` 同时发生；拿不到锁就立即返回 0。触发机制是可插拔的：`cron.provider` 为空时用内置的 `InProcessCronScheduler`（每 60 秒 `tick()`），配置成 `chronos` 这类托管调度器时，空闲网关可以缩到零，由托管方在真实触发时刻回调 `POST /api/cron/fire`；provider 加载失败会回退内置并打警告，**cron 永远不会失去触发器**，因为内置 provider 在核心里而不在插件目录。

本机的真实状态（重点看警告行）：调度器没有服务在跑时，作业不会 fire：

```text
$ hermes cron status

✗ No scheduler is serving profile 'default' — its cron jobs will NOT fire

  Start the ONE host gateway (it multiplexes every profile, this one included):
    hermes --profile default gateway install   # user service
    sudo hermes --profile default gateway install --system  # Linux servers: boot-time service
    hermes --profile default gateway run       # Or run in foreground

  2 active job(s)
  Next run: 2026-10-15T10:25:33.662790+08:00

$ hermes cron doctor
✓ Cron doctor found no issues
  No active jobs configured.
```

注意 `hermes cron doctor` 这里的「No active jobs configured」与 `cron status` 的「2 active job(s)」不一致——原因是本机以 `root` 跑 CLI 时 `HERMES_HOME=/root/.hermes`，而**常驻的 gateway 服务用的是另一个 home**，见下节的实测。

```text
调度与 tick 要点：
1. 四种调度 —— 相对延迟（一次性）/ every N（循环）/ 5 字段 cron 表达式 / ISO 定点
2. tick 频率 —— 内置 provider 每 60 秒一次；到期判定看 next_run <= now 且 state == scheduled
3. 并发安全 —— .tick.lock + fcntl.flock，重叠 tick 会立即返回（不重复跑同一批）
4. 触发方式 —— hermes cron tick 手工跑一轮即退出；hermes cron run <job> 触发指定作业
5. provider 可替换 —— cron.provider 空 = 内置；chronos = 托管（可缩零）；失败总是回退内置
6. 先确认调度器在跑 —— hermes cron status；没有 gateway 服务时作业只是「登记着」，不会触发
```

## 任务创建与管理

命令行是主力入口，子命令覆盖完整生命周期：

```text
$ hermes cron --help
positional arguments:
  {list,create,add,edit,pause,resume,run,remove,rm,delete,status,runs,history,incidents,notepad,doctor,tick}
    list                List scheduled jobs
    create (add)        Create a scheduled job
    edit                Edit an existing scheduled job
    pause               Pause a scheduled job
    resume              Resume a paused job
    run                 Run a job on the next scheduler tick
    remove (rm, delete) Remove a scheduled job
    status              Check if cron scheduler is running
    runs (history)      Show durable execution attempts
    incidents           List or acknowledge durable cron failure incidents
    notepad             Read/write a job's durable notepad (persistent KV across runs)
    doctor              Check scheduled jobs for common health issues
    tick                Run due jobs once and exit
```

创建参数里最关键的几组（本机 `hermes cron create --help` 实测）：

```text
$ hermes cron create --help   # 节选
  schedule              Schedule like '30m', 'every 2h', or '0 9 * * *'
  prompt                Optional self-contained prompt or task instruction
  --name NAME           Optional human-friendly job name
  --deliver DELIVER     Delivery target: origin, local, telegram, discord, signal,
                        platform:chat_id, or bot-chat[:profile]
  --failure-deliver     Override target for FAILURE notices only; 'local' 表示失败不投递
  --repeat REPEAT       Optional repeat count
  --skill SKILLS        Attach a skill. Repeat to add multiple skills.
  --script SCRIPT       Path to a script under ~/.hermes/scripts/
  --no-agent            Skip the LLM entirely — run --script on schedule and deliver its
                        stdout directly. Empty stdout = silent.
  --monitor-script      Monitor mode: cheap source script runs each tick BEFORE the agent;
                         unchanged output suppresses the agent run entirely
  --monitor-url         Same hash-suppression semantics, fetching an http(s) URL
  --workdir WORKDIR     Absolute path for the job to run from (injects AGENTS.md 等)
  --model / --provider / --pin / --reasoning-effort   Inference pin（用户所有）
  --continuity          每轮唤醒时把该作业上一轮的输出注入 prompt（去重/续做）
  --paused / --paused-reason   一次性创建为停用状态（可审计原因）
```

三种运行形态的区别决定了成本与适用场景：

| 形态 | 是否调用 LLM | 适用 |
|---|---|---|
| agent 模式（默认，可挂 `--skill`/`--script`） | 是 | 需要判断、汇总、写文件的作业 |
| `--no-agent`（纯脚本） | 否，零 LLM | 看门狗、磁盘/内存告警、CI 结果播报 |
| `--monitor-script` / `--monitor-url` | 变化时才调 | 盯外部变更（输出未变则整轮跳过） |

本机实测：创建一个 `--no-agent` 巡检作业并**真的跑一轮**。

```bash
# 1) 作业脚本放在 ~/.hermes/scripts/
hermes cron create "every 30m" \
  --name kb-demo-diskcheck \
  --script kb-demo-diskcheck.sh \
  --no-agent \
  --deliver local
```

改动作业不需要删了重建，且 `pause`/`resume`/`run`/`remove`/`edit` 都接受**作业名**（大小写不敏感），id 精确匹配优先；同名歧义会拒绝执行并列出候选 id。注意只读类子命令（`runs` 等）只按 `job_id` 过滤，传名字会静默查不到：

```bash
hermes cron edit <job_id> --schedule "every 4h"
hermes cron edit <job_id> --prompt "Use the revised task"
hermes cron edit <job_id> --add-skill maps        # 追加
hermes cron edit <job_id> --remove-skill blogwatcher
hermes cron edit <job_id> --clear-skills
hermes cron pause  kb-demo-diskcheck              # 按名字，比 hex id 好记
hermes cron resume kb-demo-diskcheck
hermes cron remove kb-demo-diskcheck
```

`--continuity` 与 notepad 解决「作业记不住上一轮」的问题：前者把上一轮输出注入本轮 prompt（用于 scouts/monitors/incremental digest 这类要避免重复播报的作业），后者是作业自己的持久 KV：

```bash
hermes cron notepad <job_id> set last_seen_id 4211    # 存一个跨轮状态
hermes cron notepad <job_id> get last_seen_id
hermes cron notepad <job_id> list
```

```text
创建与管理要点：
1. 三种形态 —— agent（要 LLM）/ --no-agent（零 LLM 看门狗）/ --monitor-*（变化才唤醒）
2. 脚本位置 —— 必须放 ~/.hermes/scripts/ 下；.sh/.bash 走 bash，其它按 Python 跑
3. 按名操作 —— pause/resume/run/remove/edit 接受作业名，歧义会拒绝并列候选；runs/notepad 只认 job_id
4. 编辑不重建 —— edit 改 schedule/prompt/技能/投递；--add-skill 追加、重复 --skill 整体替换
5. 跨轮状态 —— --continuity 注入上轮输出；notepad 存 KV（比写文件更省事）
6. 推理与模型 —— --reasoning-effort 逐作业指定思考档位；--model/--provider/--pin 属用户所有，代理不能设
```

## 结果投递渠道

投递目标用 `平台[:目标[:线程]]` 语法，裸平台名投到该平台的 home channel，目标在**触发时刻**解析（所以可以先建作业、后连平台）：

| 目标 | 语法 | 示例 |
|---|---|---|
| 创建处 | `origin` | 投回创建该作业的会话（消息平台上的默认值） |
| 本地文件 | `local` | 存到 `~/.hermes/cron/output/`（CLI 上的默认值） |
| Telegram | `telegram`、`telegram:<chat_id>[:<thread_id>]`、`telegram:@username` | `telegram:-1001234567890:17585` |
| Discord | `discord`、`discord:#channel`、`discord:<channel_id>[:<thread_id>]` | `discord:#engineering` |
| Slack | `slack`、`slack:#channel`、`slack:<channel_id>:<thread_ts>` | `slack:#engineering` |
| 其它平台 | 通用 `platform:<chat_id>` 形式 | `feishu:oc_abc123`、`qqbot:<chat_id>` |
| Bot Chat | `bot-chat[:profile]` | 注入到本地 profile 的 Bot Chat 当一条消息 |

三条投递语义要记牢：

```text
1. [SILENT] 前缀 —— 响应里带这个前缀会完全抑制投递（适合只写文件/只做副作用的作业）
2. 包装开关 —— cron.wrap_response: true（默认）时投递内容带作业名/任务的头部与「代理看不到该消息」的脚注
3. 失败投递 —— --failure-deliver 单独指定失败通知目标；填 local 则完全不发失败通知
             （运行状态仍能在 hermes cron list 里看到）
```

非 cron 场景下把脚本输出推给消息平台用 `hermes send`（CI、监控脚本都能用，无需 LLM）：

```bash
# 从任意脚本/CI 推一条消息到已配置的平台
hermes send "构建完成：$(git rev-parse --short HEAD)"
```

```text
投递要点：
1. 语法 —— platform[:chat_id[:thread_id]]；裸平台名 = 该平台 home channel
2. 解析时机 —— 触发时解析，因此平台还没连上也能先建作业
3. 静默 —— 响应以 [SILENT] 开头则完全不投递（纯副作用作业的标准写法）
4. 失败通道 —— --failure-deliver 单独路由失败通知；'local' 表示失败静默
5. 不污染会话 —— cron 投递不会写进目标聊天的会话历史（避免消息交替违规）
6. 无 LLM 推送 —— hermes send 供脚本/CI 直接推消息，不必绕 cron
```

## 后台进程与常驻服务

后台运行分三种粒度，选错的话「任务跑完了但结果丢了」或「进程随会话结束被杀」：

| 粒度 | 手段 | 存活范围 | 适用 |
|---|---|---|---|
| 单次工具调用 | terminal 的 `background=true`（返回 session_id） | 该会话进程内 | 跑长命令、起服务后继续干活 |
| 会话内循环 | `/loop`、`/heartbeat` | 会话（状态存 SessionDB，网关可恢复） | 轮询外部状态、期间盯梢 |
| 常驻服务 | gateway（`hermes gateway install/start`）、systemd 单元 | 跨重启 | 消息平台接入 + cron 调度 |
| 隔离作业 | `hermes cron` 作业 | 完全独立的新会话 | 无人值守、跨重启 |

会话内后台进程的管理动作（`process` 工具 / 对应 CLI）：

```text
# 在会话里用 background 模式起一个长任务
terminal(command="python3 scripts/long_task.py", background=true, notify=true)
# -> 返回 session_id；notify=true 会在进程退出时通知一次（有明确终点的任务应当打开）

# 管理动作
process(action="poll",   session_id="proc_ab12")   # 看当前输出与状态
process(action="wait",   session_id="proc_ab12")   # 阻塞等待结束
process(action="write",  session_id="proc_ab12")   # 交互式进程写输入（PTY 模式）
process(action="kill",   session_id="proc_ab12")   # 结束它
```

两条硬规则：**不要用后台进程做等待**（`sleep`/轮询循环要用前台命令配大 timeout，再把结果读出来），**只有需要活过本次对话的才用持久化**（`persist_on_release`，用于过夜批处理、看护型守护进程；服务器类进程应当用 systemd 或 gateway 服务，而不是会话内的后台进程）。

gateway 是 cron 的宿主，也是消息平台的接入进程，本机实测形态（注意它是 systemd 系统服务，且跑在**另一个 HERMES_HOME** 下）：

```text
2. 生命周期 —— 会话内后台进程随会话进程结束而死；要跨重启就交给 systemd 或 cron 作业
3. 别用后台进程等待 —— 固定等待用前台命令 + 大 timeout，后台只用于必须并行的长任务
4. notify 与 persist —— 有终点的任务开 notify；只有要活过对话的才用 persist_on_release
5. 服务先跑起来 —— cron 靠 gateway tick；hermes cron status 是唯一的「会不会触发」判据
6. 紧急停止 —— hermes pause 只挡新工作（在途不杀），hermes resume 解除
```

## 失败可见性与自愈

cron 的可靠性建立在**执行账本**上：每次尝试在派发给执行器之前先落一条记录，状态从 `claimed` → `running`，最终落到三个不可变终态之一——`completed`、`failed`、`unknown`。重启后只有能证明「原 PID 与进程启动指纹都消失」时才把遗留尝试标为 `unknown`，而 `unknown` 只是审计记录，**永不自动重跑**。

本机真实账本（含一次被中断的尝试）：

```text
$ hermes cron runs a7fc3061b85a --limit 3
cb44e6973f82402ea1701492fb569169  running    job=a7fc3061b85a  source=direct  2026-10-15T10:26:01.591481+08:00
b923db4757a74f7b9b54f0b6ac294564  unknown    job=a7fc3061b85a  source=direct  2026-10-15T10:01:16.420592+08:00
    Scheduler restarted after this execution's owner exited before a durable terminal state; whether side effects ran is unknown.

$ hermes cron runs 9c7a369d5543 --limit 5
dd93adcc28f04c19ad7ddd3642b1b641  completed  job=9c7a369d5543  source=direct  2026-10-15T09:55:30.436851+08:00
3def885373124f55b05300c6feefd33e  completed  job=9c7a369d5543  source=direct  2026-10-15T09:52:47.424077+08:00
c9cfa84950bf4aceaaf74e1fc33554ee  completed  job=9c7a369d5543  source=direct  2026-10-15T09:50:51.831972+08:00
```

围绕失败，系统还有几层机制：

```text
1. 预检（cron.preflight，默认开）—— 代理启动前先校验：provider key 能否解析、挂载技能是否就绪、
   投递目标是否有网关凭据；失败则 last_status=blocked_config，只告警一次，且完全不消耗 token
2. 失败连击（failure_streak）—— 连续失败的循环作业在投递里附「已连续失败 N 次」的提醒
   （成功即清零；一次性作业不提醒）；阈值 cron.failure_nudge_threshold（默认 3，0 = 关闭）
3. 模型漂移护栏（cron.model_drift_guard，默认开）—— 未 pin 的作业若全局默认模型变了会
   fail-closed：跳过本轮、零推理调用、只告警一次，直到你 pin 或恢复配置
4. 失败事件（incidents）—— hermes cron incidents 列出/确认持久化的失败事件
5. 巡检（doctor）—— hermes cron doctor 检查作业常见健康问题
6. 断线续跑 —— 作业定义是磁盘 JSON，重启后下次 tick 照常触发；被中断的那次标 unknown 不重跑，
   间歇性作业若需要「接着上次」就配 --continuity 或 notepad
```

超时预算也有两层：`--script` 的前置脚本默认上限 3600 秒（`cron.script_timeout_seconds` / `HERMES_CRON_SCRIPT_TIMEOUT` 可改），而**技能/LLM 驱动的作业**按「无活动」计时（`HERMES_CRON_TIMEOUT`，默认 600 秒无活动），只要持续调用工具或持续输出就不会被杀——所以长作业能跑几小时，只有真正卡死才会被清理。脚本派发到常驻线程池，不占 tick 锁，因此长脚本不会阻塞同批其它到期作业。

```text
失败可见性与自愈要点：
1. 账本就是真相 —— claimed → running → completed | failed | unknown；terminal 状态不可变
2. unknown 不重跑 —— 它是审计记录；需要「接着上次」要靠 --continuity 或 notepad
3. 预检不花钱 —— blocked_config 只告警一次、零推理调用；cron.preflight: false 可关
4. 连击提醒 —— 循环作业连续失败到阈值会在投递里提示 fix/pause/remove
5. 漂移护栏 —— 未 pin 的作业遇到全局模型变更会 fail-closed（防止无人值守误花大模型的钱）
6. 两种超时 —— 前置脚本上限 3600s；LLM 作业按无活动 600s 计时（持续干活可跑很久）
```

## 三种后台路线的选择

同样的「每 10 分钟瞄一眼」，放错位置就会丢上下文或丢可靠性。三条路线按「是否需要当前对话的上下文」和「是否需要跨重启」来选：

| 维度 | `/loop`、`/heartbeat` | `hermes cron` | gateway + webhook |
|---|---|---|---|
| 运行位置 | 当前会话（上下文完整） | 每次全新会话（无历史） | 事件驱动，可无周期 |
| 数量 | 每会话各一个 | 不限 | 不限（订阅制） |
| 跨重启 | 状态存 SessionDB，网关可恢复 | 完全持久 | 需要服务在跑 |
| 投递 | 回当前会话 | 任意平台/本地文件 | 按订阅注册的处理器 |
| 典型用途 | 「我们这个对话里顺手盯着 X」 | 固定作业、报告、看门狗 | 外部系统事件触发智能体 |

判据一句话：**周期性 + 需要对话上下文 → loop/heartbeat；周期性 + 自包含 → cron；非周期 + 外部触发 → webhook 订阅**。

```text
# 需要上下文（轮询同一次讨论里的部署状态）
/loop 5m check the deploy status and tell me if it's live yet
/heartbeat every 10m Check the deployment and report meaningful changes

# 自包含且要跨重启（每天 9 点汇总）
hermes cron create "0 9 * * *" "抓取 Hacker News 上的 AI 新闻并汇总成中文摘要" --name hn-digest --deliver qqbot

# 外部事件驱动（CI 完成、仓库有 push）
hermes webhook --help     # 查看与管理动态 webhook 订阅
```

```text
路线选择要点：
1. 先问两件事 —— 需要当前对话上下文吗？需要跨重启吗？
2. 会话内循环 —— /loop（定时或自定节奏）与 /heartbeat（空闲注入），共享上下文与缓存
3. cron 作业 —— 隔离新会话，prompt 必须自包含；靠 gateway 每 60 秒 tick 触发
4. 事件驱动 —— webhook 订阅把外部事件变成一次智能体运行，不靠轮询
5. 混用是正常的 —— 会话内 loop 用于当下盯梢，cron 用于长期值守，两者互不干扰
6. 都能投递 —— 不要把「必须通知到我手机」当作选型依据，三条路线都能投
```

## 应用场景实战

### 场景一：磁盘与服务巡检看门狗（零 LLM 成本，真跑一轮）

需求：主机跑着一堆自建服务，希望磁盘/内存接近阈值、或 nginx 挂掉时立刻收到消息，正常情况下保持安静、不烧 token。做法是 `--no-agent` 脚本作业：脚本无异常时输出为空（等于静默），有异常才输出告警正文。

```bash
#!/usr/bin/env bash
# ~/.hermes/scripts/kb-demo-diskcheck.sh
# 无人值守巡检脚本：磁盘、内存、关键进程。stdout 直接作为投递内容。
set -uo pipefail

THRESHOLD=85
alert=0

while read -r fs size used avail pct mount; do
  # 跳过表头：只处理使用率形如 NN% 的行（df 输出受 locale 影响，不能匹配 "Filesystem"）
  case "$pct" in
    *%) ;;
    *) continue ;;
  esac
  num=${pct%\%}
  # 只接受纯数字：中文 locale 下表头第 5 列是 "已用%"，必须排除
  case "$num" in
    ''|*[!0-9]*) continue ;;
  esac
  if [ "$num" -ge "$THRESHOLD" ]; then
    echo "DISK HIGH: ${mount} ${pct} (used ${used}, avail ${avail})"
    alert=1
  fi
done < <(df -h --type=ext4 --type=overlay 2>/dev/null)

mem_pct=$(LC_ALL=C free | awk '/^Mem:/ {printf "%d", $3/$2*100}')
if [ "$mem_pct" -ge "$THRESHOLD" ]; then
  echo "MEM HIGH: ${mem_pct}% used"
  alert=1
fi

if ! pgrep -x nginx >/dev/null 2>&1; then
  echo "SERVICE DOWN: nginx not running"
  alert=1
fi

# 无异常时输出为空 —— 配合 --no-agent 即静默，不产生投递
if [ "$alert" -eq 1 ]; then
  echo "---"
  echo "巡检时间: $(date '+%Y-%m-%d %H:%M:%S')"
else
  echo "巡检正常: $(date '+%Y-%m-%d %H:%M:%S') 磁盘/内存均低于 ${THRESHOLD}%，nginx 在运行"
fi
```

```bash
# 本地先跑一遍确认判定逻辑（不要只信部署）
bash ~/.hermes/scripts/kb-demo-diskcheck.sh

# 建作业：每 30 分钟一次，纯脚本，结果落本地
hermes cron create "every 30m" \
  --name kb-demo-diskcheck \
  --script kb-demo-diskcheck.sh \
  --no-agent \
  --deliver local

# 立刻跑一轮（不等下一个 tick）
hermes cron run kb-demo-diskcheck

# 核对执行账本与输出文件
hermes cron runs 9c7a369d5543 --limit 5        # 注意 runs 只认 job_id，不认作业名
ls -la ~/.hermes/cron/output/9c7a369d5543/
```

### 场景二：带门控的 agent 巡检作业（脚本做前置门控 + 跨轮去重）

需求：每 2 小时检查一批外部数据源是否有新条目，有新条目才让智能体读、判断、写日报；没有新条目时整轮跳过，不产生任何推理开销；并且要避免把同一条内容重复播报两次。做法是「门控脚本 + `--continuity` + notepad」三件套。

```python
# ~/.hermes/scripts/kb-demo-gate.py
# 门控脚本：没有新数据时打印 {"wakeAgent": false}，调度器会整轮跳过
import json
import sqlite3
import time

DB = "/opt/project-work/app/data.db"     # 换成你自己的数据源
STATE = "/root/.hermes/scripts/.gate_state"

def last_seen() -> int:
    try:
        with open(STATE, encoding="utf-8") as fh:
            return int(fh.read().strip())
    except Exception:
        return 0

def main() -> None:
    since = last_seen()
    conn = sqlite3.connect(f"file:{DB}?mode=ro", uri=True)
    n = conn.execute(
        "SELECT COUNT(*) FROM items WHERE created_at > ?", (since,)
    ).fetchone()[0]
    conn.close()

    if n < 1:
        print(json.dumps({"wakeAgent": False}))
        return

    with open(STATE, "w", encoding="utf-8") as fh:
        fh.write(str(int(time.time())))
    # 把条数通过 context 交给智能体，省掉一次重复查询
    print(json.dumps({"wakeAgent": True, "context": {"new_items": n}}))

if __name__ == "__main__":
    main()
```

```bash
# 自检：无新数据时必须打印 wakeAgent=false（否则每轮都在烧 token）
python3 ~/.hermes/scripts/kb-demo-gate.py

# 建作业：脚本做门控 + continuity 让本轮看到上一轮的输出（跨轮去重）
hermes cron create "every 2h" \
  "读取门控脚本给的 new_items 数量，查询新增条目，判断是否值得写日报；
   值得写就写成 Markdown 存到 /opt/project-work/reports/$(date +%F-%H).md；
   如果内容与上一轮播报过的重复，只输出 [SILENT]。" \
  --name kb-demo-gate \
  --script kb-demo-gate.py \
  --continuity \
  --deliver local \
  --failure-deliver local
```

上面第二条账本记录是本次写作过程中的真实观测：agent 模式作业在前台执行 `hermes cron run` 时被外部超时中断，进程退出后该次尝试被记为 `unknown`，并明确写明「副作用是否发生未知」——这正是「无人值守作业不要在前台交互式触发」的现场证据。同一作业重新触发后，由于上游 provider 在写作窗口内持续返回 503（`Service is too busy`）并在重试，该轮一直停留在 `running` 且没有任何输出文件；本次写作结束时它仍是一条未终结的 `running` 记录（按官方说明，遗留的 `running` 会在调度器重启并确认原进程指纹已消失后落为 `unknown`）。因此这里**不贴任何推理输出**；agent 模式的完整结果需要在 provider 可用的环境里按下述正道跑：

```bash
# 正道：让调度器自己触发（gateway 在跑）而不是在前台 run
hermes cron resume kb-demo-gate          # 先恢复为 active
hermes gateway status                    # 确认 tick 宿主在跑
hermes cron runs <job_id> --limit 5      # 事后看账本与输出（runs 只认 job_id）
cat ~/.hermes/cron/output/<job_id>/<时间戳>.md
```

```text
场景二关键点：
1) 门控优先 —— 判断「要不要唤醒」用脚本做，比唤醒智能体后让它自己判断便宜几个数量级
2) wakeAgent 契约 —— 打印 {"wakeAgent": false} 抑制本轮；true 时可用 context 传结构化上下文
3) 状态自己存 —— 门控脚本的状态（last_seen）落在脚本侧文件，别去写 Hermes 的 state.db（内部 schema 会变）
4) 跨轮去重 —— --continuity 把上一轮输出注入本轮 prompt；notepad 存更细的 KV
5) 静默与失败 —— 不需要播报就输出 [SILENT]；--failure-deliver local 让失败不打扰（状态仍在 cron list 里）
6) 触发方式 —— 无人值守作业交给调度器；前台 hermes cron run 只用于手工验证一次
```

## 最佳实践与踩坑记录

### 最佳实践

1. 能不用 LLM 就不用：看门狗、阈值告警、CI 播报一律 `--no-agent`，把智能体留给真正需要判断的作业
2. 周期巡检用「门控脚本 + `--continuity`」：没有变化就整轮跳过，有变化才推理，同时避免重复播报同一条内容
3. 作业 prompt 必须自包含：写清主机、账号、命令、判定标准；每次运行都是干净会话，没有上文可依
4. 用户级作业先 pin 模型再交给调度器（`--model`/`--provider` 或全局 `cron.model`），避免无人值守时被全局模型漂移挡下
5. 建完作业先本地手工跑一次脚本、再 `hermes cron run` 验证一次，最后才交给 gateway 周期触发
6. 把「会不会触发」当成独立问题检查：`hermes cron status` 必须显示有调度器服务本 profile；没有就装 gateway 服务
7. 失败要可查也要可静默：用 `hermes cron runs` 看账本、`hermes cron incidents` 看失败事件，同时用 `--failure-deliver local` 控制打扰
8. 会话内后台进程只用于「本次对话需要并行的长任务」，跨重启的一律交给 cron 或 systemd

### 踩坑记录

```text
坑 1：作业建好了、状态是 active，但从来没有触发过
结论：hermes cron list 里作业存在、下次运行时间也合理，但到点没有任何输出。
原因：cron 靠 gateway（或同等的 ticker）每 60 秒 tick 一次；没有服务为该 profile 提供调度时，
      作业只是「登记着」，不会 fire。本机真实输出就是：
      ✗ No scheduler is serving profile 'default' — its cron jobs will NOT fire
解法：确认 hermes cron status；没有调度器就起一个（hermes gateway install /
      sudo hermes gateway install --system / 前台 hermes gateway run）；
      临时验证可以用 hermes cron tick 手工跑一轮到期作业。

坑 2：hermes status 说 gateway 在跑，cron status 却说没有调度器
结论：两个命令结论矛盾，作业照旧不触发。
原因：Hermes home 不同。本机 gateway 是 systemd 服务，其 HERMES_HOME 是 /home/lw/.hermes；
      而 CLI 以 root 运行时用 /root/.hermes。作业表、账本、调度器都是按 home 隔离的，
      在 A home 建的作业不会被 B home 的调度器 tick。
解法：建作业的 home 与跑调度器的 home 必须一致——要么统一 HERMES_HOME/--profile，
      要么为当前 home 单独装一个 gateway 服务；用 hermes cron status 的输出作为唯一判据。

坑 3：前台执行 hermes cron run，等超时被杀，作业卡在 running/unknown
结论：agent 模式作业在前台触发时阻塞很久，超时中断后账本里出现 unknown，
      并提示「whether side effects ran is unknown」。
原因：agent 模式要真的跑一轮 LLM 推理；前台 CLI 会一直等到结束，被外部超时杀掉时，
      进程退出而执行记录没有落到终态，重启后按「owner 已消失」标为 unknown（不自动重跑）。
解法：无人值守作业一律交给调度器（gateway 在跑时到点自动触发）；
      手工验证用后台方式跑或用 hermes cron tick；事后用 hermes cron runs 核对是否落地。

坑 4：脚本在终端里跑得好好的，放进 cron 就报「需要整数表达式」
结论：巡检脚本手工跑正常，作为 cron 作业运行时输出报错行，判定失真。
原因：cron 环境的 locale 可能与终端不同。中文 locale 下 df 的表头第 5 列是「已用%」而不是
      「Filesystem」，用固定字符串跳过表头会漏掉表头行，进而在 [ 比较时把中文当成整数。
解法：脚本不要依赖 locale 相关的表头文本：用 case 判断字段形状（只接受纯数字），
      需要稳定的英文输出就显式设置 LC_ALL=C（例如 LC_ALL=C free）；
      写完后用「与 cron 相同的方式」跑一遍再上线。

坑 5：暂停中的作业直接 run，被拒绝
结论：hermes cron run <job> 返回 "Job is paused/disabled; resume it before running."。
原因：pause 是刻意保留作业但不调度；run 不会隐式恢复它，避免误触发长期停用的作业。
解法：先 hermes cron resume <job> 再 run；只想临时跑一次且不想改状态，就用
      hermes cron edit 调整状态或用变更调度时间的做法，别指望 run 绕过 paused。

坑 6：一次性作业错过了时间点，再也没跑
结论：定点一次性作业（相对延迟或 ISO 时间戳）在某次关机窗口里到期，之后永远不触发。
原因：相对延迟/定点作业语义就是「一次」；过期后没有可计算的下次运行时间。
解法：需要「错过也要补」的作业一律用循环调度（every N 或 cron 表达式），
      并在作业里自己判断「距上次成功执行多久」，需要补做就用 --continuity/notepad 记录进度。

坑 7：hermes cron runs 传了作业名，得到「没有执行记录」
结论：明明作业跑过多次，按名字查账本却输出 "No cron execution attempts recorded."。
原因：runs（以及 notepad 等只读类子命令）只按 job_id 过滤；传一个无法匹配的名字不会报错，
      而是静默当作空结果返回——本机实测用不存在的名字查询会得到完全相同的输出。
解法：查账本一律用 job_id（hermes cron list 里那串 hex）；
      需要按名字操作就用 pause/resume/run/remove/edit 这些会做名字解析的动词。
```
