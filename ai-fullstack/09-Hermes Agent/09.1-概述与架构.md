## 概述

Hermes Agent 是 Nous Research 开源的 AI Agent 框架，与 Claude Code、Codex、OpenCode 属于同一类「工具调用型自主 Agent」，但它不做 IDE 附属，而是把自己定位成可以长期跑在 VPS、云 VM 或服务器上的常驻智能体。它的差异化能力有三条：用技能（skill）实现自改进、用记忆（memory）跨会话保持对用户的认知、用网关（gateway）把同一个 Agent 接到 Telegram / Discord / Slack 等十几个消息平台上，并且拥有完整工具权限而不是只能聊天。

本篇讲清三件事：Hermes 的整体架构由哪几套体系拼成、它能在哪几种形态下运行、以及它和同批次的编码 Agent 到底差在哪里。后面几篇（09.2 安装配置、09.3 工具、09.4 技能与插件、09.5 记忆、09.6 上下文、09.7 定时任务、09.8 MCP、09.9 多平台、09.10 运维）是把本篇的每一块展开。

```text
本节要点：
1. 定位 —— 开源、provider 无关、可常驻的通用自主 Agent，而不是绑定单一 IDE 或单一模型的编码助手
2. 三条差异化 —— 技能带来的自改进、跨会话持久记忆、多平台消息网关（带完整工具权限）
3. 四套扩展面 —— 工具与工具集、技能、记忆、插件与钩子，互不干扰，各自有独立的配置命名空间
4. 运行形态 —— 交互 CLI / TUI、命令行单次执行、消息网关、ACP 服务、Web Dashboard、MCP server
5. 事实来源 —— 本机安装为 git 安装（v0.21.6+131.g38880bd），版本号与路径以 hermes --version 实测为准
6. 系列结构 —— 本篇给架构全景，09.2 起逐块展开，细节以官方文档 hermes-agent.nousresearch.com/docs 为准
```

## 定位与设计理念

Hermes 的设计目标不是「补全代码」，而是「用一个 Agent 接管跨平台、跨会话的长期任务」。官方的表述是 self-improving AI agent，核心机制是学习闭环：Agent 解决了一个复杂问题、摸清了一套工作流、或者被用户纠正之后，可以把它固化成一个技能文档，下次遇到同类任务直接加载；技能使用情况由 curator 后台维护，会标记闲置、归档陈旧的技能，但永不删除。第二条支柱是跨会话记忆：用户是谁、偏好什么、环境长什么样、踩过哪些坑，都会持久化并在后续会话中自动带上。

设计上有几个一以贯之的取舍，理解了它们后面所有配置行为都顺理成章：

第一，能力全部以「工具」为统一接口，模型看到的是一组 JSON Schema 描述的函数，扩展系统也只是往同一个注册表里塞新工具。第二，知识全部以「技能」为统一载体，技能是纯文本文档，不需要写代码，也不需要改 Agent 本体，属于渐进式披露（progressive disclosure）：只有被加载的技能才占用上下文。第三，绝不在会话中途改系统提示词——插件注入的上下文被追加到当轮 user message 上而不是 system prompt，工具与技能的启用变更要等 `/reset` 新开会话才生效，这一切都是为了不破坏 prompt caching。第四，配置与密钥分离：`config.yaml` 放设置，`.env` 放密钥，OAuth 凭据放 `auth.json`。

```text
定位与设计理念要点：
1. 学习闭环 —— 经验固化为技能，curator 负责技能生命周期（标记闲置、归档，永不删除）
2. 记忆跨会话 —— memories/ 目录 + state.db，记住用户画像、环境事实与既有约定
3. 统一接口 —— 内置工具、插件工具、MCP 工具在模型眼里都是同一类 JSON Schema 函数
4. 不改系统提示词 —— 插件注入走当轮 user message，配置变更等 /reset 生效，保护 prompt cache
5. 配置与密钥分离 —— config.yaml 放设置，.env 放密钥，auth.json 放 OAuth 凭据
6. provider 无关 —— 20 家以上 Provider 可随时切换，还有凭据池轮转与 fallback provider
```

## 四大体系：工具、技能、记忆、插件

把架构拆开看，Hermes 由四套彼此独立、各自有配置文件与目录的体系组成。工具（tools / toolsets）决定 Agent「能做什么」；技能（skills）决定 Agent「知道怎么做」；记忆（memory）决定 Agent「记得什么」；插件（plugins）与钩子（hooks）决定 Agent「在哪一步被改写或被观测」。四者的加载时机也不同：工具与工具集在进程启动时确定，技能在用得上时按需加载，记忆每轮注入，插件在启动时注册并挂到事件上。

| 体系 | 载体与位置 | 本机实测证据 | 扩展方式 |
| --- | --- | --- | --- |
| 工具与工具集 | `tools/` 每个工具一个文件，`toolsets.py` 定义分组 | `hermes tools list` 显示 25 个内置工具集 + 1 个插件工具集 + 1 个 MCP server | 插件注册工具、MCP server 提供工具、核心树新增 `tools/*.py` |
| 技能 | `~/.hermes/skills/<分类>/<技能名>/SKILL.md` | `~/.hermes/skills/` 下 1116 个目录，`hermes skills list` 统计 979 hub-installed / 5 builtin / 227 local，其中 123 enabled | 手写 SKILL.md、`hermes skills install`、`/learn` 自动生成 |
| 记忆 | `~/.hermes/memories/`（MEMORY.md、USER.md）+ `state.db` | `memories/` 目录存在；`state.db` 为 SQLite WAL 模式，本机约 841.7 MB | `memory` 工具写入、memory provider 插件（Honcho / Mem0 等） |
| 插件与钩子 | `~/.hermes/plugins/<插件名>/plugin.yaml` + `__init__.py` | `hermes plugins list` 列出 bundled 的 browser-browser-use 等；`plugins.enabled` 中已启用 `ponytail` | `hermes plugins install`、`register(ctx)` 注册工具/钩子/斜杠命令/技能 |

本机 `config.yaml` 中与本篇相关的真实片段（行号取自实际文件）：

```yaml
# ~/.hermes/config.yaml（节选）
model:
  default: deepseek-flash
  provider: deepseek
fallback_providers: []
toolsets:
  - hermes-cli            # 本机 CLI 平台绑定的是 hermes-cli 这一整套预设
agent:
  max_turns: 90
  gateway_timeout: 1800
  restart_drain_timeout: 180
  api_max_retries: 3
  service_tier: ''
  disabled_toolsets: []   # 第 20 行，这里为空即不额外禁用任何工具集
```

```text
四大体系要点：
1. 加载时机 —— 工具/工具集在启动时确定，技能按需加载，记忆每轮注入，插件在 register(ctx) 时挂载
2. 命名空间隔离 —— 技能配置在 skills.config 下，插件配置在 plugins.entries.<id>.settings 下，互不可见
3. 技能是真的文件 —— 就是磁盘上的 SKILL.md，可以被 git 管理、可以被团队共享、可以被审计
4. 记忆有两层 —— 结构化长期记忆（memories/ 里的 Markdown）与会话状态库 state.db 各司其职
5. 插件是 opt-in —— 装完默认不启用，必须 hermes plugins enable，或用 plugins.enabled 显式列出
6. 命名冲突有保护 —— 插件带的技能以 plugin:skill 命名空间加载，不会覆盖内置同名技能
```

## 运行形态 CLI TUI 与网关

Hermes 的入口只有 `hermes` 一个可执行文件，形态由子命令与开关决定。最常用的是交互式 CLI：直接敲 `hermes` 进入对话，这也是官方所说的「无子命令时默认等于 chat」。TUI 是同一套交互循环的全屏界面（`--tui` / `--native`），网关（gateway）则是常驻服务，把消息平台的事件转成会话轮次。此外还有 ACP 服务（给 IDE 用）、Web Dashboard（浏览器界面）、API Server 适配器（给 Open WebUI 一类前端用），以及「Hermes 自己作为 MCP server」的反向模式。

```bash
# 1. 交互式聊天（最常用；无子命令时默认就是 chat）
hermes

# 2. 单次执行，非交互，适合脚本与 CI
hermes chat -q "总结 /var/log/nginx/error.log 里最近 20 条错误"

# 3. 限定模型与工具集（减少上下文开销）
hermes chat -m deepseek/deepseek-chat -t "web,terminal" -q "查一下最新版本号"

# 4. 全屏 TUI
hermes --tui

# 5. 恢复会话
hermes --continue                # 最近一次会话
hermes --resume <session_id>     # 指定会话
hermes -s hermes-agent           # 预加载技能后启动

# 6. 网关（消息平台常驻）
hermes gateway run               # 前台运行，便于看日志
hermes gateway install           # 装成后台服务
hermes gateway status            # 查状态

# 7. 其它外壳
hermes acp                       # 作为 ACP server 给 IDE 用
hermes dashboard                 # Web Dashboard
hermes mcp serve                 # 把 Hermes 当 MCP server 暴露出去
```


网关支持的平台以官方文档为准，包含 Telegram、Discord、Slack、WhatsApp、Signal、Email、SMS、Matrix、Mattermost、Home Assistant、DingTalk、Feishu、WeCom、BlueBubbles（iMessage）、Weixin、QQ Bot、API Server、Webhooks 等；本机 `hermes --help` 里还能看到 `whatsapp`、`whatsapp-cloud`、`slack` 等专门的接入助手子命令。新增平台时先跑 `hermes gateway setup` 做交互式配置，再 `hermes gateway install` 常驻。

```text
运行形态要点：
1. 一个入口 —— 都是 hermes 可执行文件，形态由子命令/开关决定，配置与技能在形态之间完全共享
2. CLI 与 TUI 同循环 —— TUI 只是同一套 run_conversation 循环的全屏前端，行为一致
3. 非交互首选 chat -q —— 脚本、CI、cron 里不要用 TUI，单次执行才是稳定接口
4. 网关是常驻服务 —— gateway run 前台调试，gateway install 装服务，日志在 ~/.hermes/logs/gateway.log
5. 反向集成 —— hermes mcp serve 让别的客户端把 Hermes 当 MCP server 调用
6. 平台能力有差异 —— 各平台的工具集预设不同（如 webhook 触发只有只读子集），详见 09.9
```

## 运行循环与状态存储

一次对话在内部是一次 `run_conversation()`：先构建系统提示词（身份 SOUL.md、环境事实、工具清单、可用技能索引），然后在迭代预算内反复「调用模型 → 若有 tool_calls 则逐个派发并把结果追加回消息 → 继续」。触及 token 阈值时自动压缩上下文；工具连续失败会被 loop guardrails 拦下；每个回合的产物落到 SQLite 状态库与日志目录。理解这条链路，才能解释后面几篇里的所有「为什么改了不生效」——工具与技能的清单是在会话建立时冻结的。

```bash
# 查看状态库与日志的位置
ls -la ~/.hermes/state.db ~/.hermes/logs/

# 本机实测：Doctor 的环境与数据库自检（装饰符号已去 emoji）
hermes doctor
```

```text
$ hermes doctor（节选，已去除装饰性符号）

Security Advisories
  ✓ No active security advisories
MCP Server Security
  ✓ No suspicious MCP stdio commands
Python Environment
  ✓ Python 3.14.7
  ✓ SQLite 3.53.1
    → state.db: WAL journal mode (841.7 MB)
    → cron/executions.db: WAL journal mode (40.0 KB)
  ✓ Runtime venv staged (/root/.hermes/installs/<hash>/environments/<hash>/venv) (active in this process)

  ✓ Config version up to date (v50)
```

与循环相关的真实配置项（`~/.hermes/config.yaml`，第 68-96 行附近）：

```yaml
tool_output:
  max_bytes: 50000        # 单次工具输出上限，超出会被截断（完整内容另存文件）
  max_lines: 2000
  max_line_length: 2000
tool_loop_guardrails:
  warnings_enabled: true
  hard_stop_enabled: false
  warn_after:
    exact_failure: 2       # 同一个失败连续 2 次就提醒模型换思路
    same_tool_failure: 3
    idempotent_no_progress: 2
  hard_stop_after:
    exact_failure: 5
    same_tool_failure: 8
    idempotent_no_progress: 5
compression:
  # 上下文压缩：阈值 50%、保留最近 20 条消息（详见 09.6）
```

```text
运行循环与状态要点：
1. 循环模型 —— 构建提示词 → 调模型 → 派发工具 → 追加结果 → 再调模型，直到产出文本或耗尽 max_turns
2. 冻结原则 —— 工具清单与技能索引在会话建立时确定，中途改动要 /reset 才生效
3. 上下文保护 —— 接近 token 上限时自动压缩；阈值与保留条数见 compression 段
4. 失败保护 —— tool_loop_guardrails 对重复失败先警告、必要时硬停，避免死循环烧 token
5. 状态落地 —— 会话与消息进 state.db（SQLite WAL），运行日志去 ~/.hermes/logs/
6. 可观测性 —— hermes doctor 看依赖与环境，hermes status --full 看各子系统，/debug 上传诊断包
```

## 与其他 Agent 的差异

Hermes 与本批次其它几款 Agent 的差别不在「能不能写代码」，而在「运行边界」与「扩展模型」。Claude Code（见 05 篇章）、Codex（03 篇章）、OpenCode（06 篇章）本质是围绕代码仓库的编码 Agent，核心交互面是终端里对着仓库干活；Pi Agent（10 篇章）偏轻量；Hermes 则把自己放在「常驻 + 多入口 + 自改进」这个位置上，编码只是它的能力之一。

| 维度 | Hermes Agent | 传统编码 Agent（Claude Code / Codex / OpenCode） |
| --- | --- | --- |
| 主要心智模型 | 可常驻的通用自主 Agent，多平台同一实例 | 面向代码仓库的编码助手，围绕单仓库工作 |
| 入口形态 | CLI / TUI / 网关（十几个消息平台）/ ACP / Dashboard / MCP server | 主要以 CLI / TUI / IDE 扩展为主 |
| 扩展模型 | 技能（纯文本文档）+ 插件（Python `register(ctx)`）+ 工具 + MCP | 规则文件 + 子代理 / 命令 + MCP + 插件（各产品不同） |
| 自改进 | 内置学习闭环：技能沉淀 + curator 生命周期管理 | 一般靠人工维护规则与提示词文件 |
| 跨会话记忆 | 内建记忆体系（memories/ + state.db），可换 memory provider | 多为项目级规则文件，跨会话记忆依赖外部手段 |
| 持久任务 | cron 定时任务、Kanban 看板、Webhook 订阅、后台进程 | 多数以单次会话为单位 |
| 隔离 | profiles（配置/会话/技能/记忆全隔离的多实例） | 通常靠多开进程或不同目录 |

需要强调的一点：本机这套 Hermes 的「工具集」是可拆的，`hermes-cli` 只是一份预设清单。这意味着同一份技能与记忆可以在 CLI 上编辑、在 Telegram 上使用、在 cron 里无人值守执行——这正是「不是绑在你笔记本上的 Agent」这句话的工程含义。

```text
差异要点：
1. 边界不同 —— 编码 Agent 服务仓库，Hermes 服务「长期任务 + 多入口」
2. 扩展首选技能 —— Hermes 明确建议先写技能，写不动了再写工具/插件
3. 自改进是内建 —— 不是外挂脚本，而是 skill_manage + curator 的完整闭环
4. 持久性是一等公民 —— cron / kanban / webhook / 后台进程都在核心命令面里
5. 隔离靠 profile —— 多租户或多环境场景用 hermes profile 而不是多份安装
6. 横向对比看各篇章 —— Claude Code 见 [[05.1-安装与配置]]，Codex 见 [[03.1-概览与安装]]，OpenCode 见 [[06.1-安装与快速开始]]
```

## 应用场景实战

### 场景一：把 Hermes 装成一台 VPS 上的常驻多平台助手

需求：一台 Ubuntu VPS，希望 Hermes 通过 Telegram 随时可用，重启机器后自动恢复，并且 SSH 断开也不会被带走。做法是「非交互装好 → 配网关 → 装成 systemd 服务 → 打开 linger → 自检」。下面的脚本可直接保存执行，依赖只有 curl 与 systemd。

```bash
#!/usr/bin/env bash
# setup-hermes-host.sh —— 常驻部署脚本
set -euo pipefail

echo "[1/6] 安装 Hermes Agent（命令行版）"
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash

echo "[2/6] 确认二进制在 PATH 上"
command -v hermes >/dev/null || { echo "hermes 不在 PATH，检查安装输出"; exit 1; }
hermes --version

echo "[3/6] 非交互初始化配置（沿用环境变量里的密钥）"
# 已有 .env 时用 --quick 只补缺失项；全新机器用 --non-interactive 走默认值
hermes setup --quick || hermes setup --non-interactive

echo "[4/6] 配置消息平台"
# 交互式向导：选平台、填 token、设置 home channel
hermes gateway setup

echo "[5/6] 装成 systemd 服务并启动"
hermes gateway install
hermes gateway start
sleep 3
hermes gateway status

echo "[6/6] 打开 linger，保证 SSH 断开后服务仍在"
sudo loginctl enable-linger "$USER"

echo "完成。健康检查：hermes doctor && hermes status --full"
```

```text
# 关键点（本机命令面实测，输出随环境而异）
$ hermes --version
Hermes Agent v0.21.6+131.g38880bd (2026.9.24) · upstream 38880bd2
Install method: git

$ hermes status
  Model:        deepseek-flash
  Gateway:      running
  Platforms:    qqbot

# 1) gateway run 是前台调试用，install 才是常驻；被 SSH 带走是 linger 没开
# 2) 排查网关先看 ~/.hermes/logs/gateway.log，命令行等价物：
#    grep -i "failed to send\|error" ~/.hermes/logs/gateway.log | tail -20
# 3) 服务崩溃循环时：systemctl --user reset-failed hermes-gateway 再 start
```

### 场景二：用 profile 隔离「工作」与「个人」两套环境

需求：同一台机器上，工作账号用公司网关 + 公司模型，个人账号用自己的模型与技能库，两边的会话、技能、记忆、定时任务互不可见。Hermes 的 profile 就是为此设计的：每个 profile 在 `~/.hermes/profiles/<name>/` 下有独立的 config、skills、cron 与 sessions。

```bash
# 1. 以当前配置为模板，克隆出一个完整副本（含配置与技能）
hermes profile create work --clone-all

# 2. 切到新 profile 里改模型与网关凭据（-p 指定 profile）
hermes -p work model
hermes -p work config set model.default company-gateway/llm-large
hermes -p work config set model.provider company-gateway

# 3. 查看与切换
hermes profile list
hermes profile show work
hermes profile use work        # 设为默认（之后裸敲 hermes 就走 work）

# 4. 给 profile 生成便捷别名脚本（可选，多个 profile 并行时很有用）
hermes profile alias work

# 5. 校验隔离是否生效
hermes -p work config path      # 应指向 ~/.hermes/profiles/work/config.yaml
hermes -p work skills list | tail -3
hermes -p default cron list
```

```text
# 预期结果形态（路径实测，条目数随环境变化）
$ hermes profile list
# 列出 default 与 work 两个 profile，work 标记为 cloned-from default

# 关键点：
# 1) --clone-all 会复制配置、技能与记忆；只要配置用 --clone
# 2) 每个 profile 有独立的 cron 与 session，cron 任务不会互相触发
# 3) 用 HERMES_HOME 手工切目录也可以，但 profile 才是官方支持的多实例方式
# 4) 网关要为每个 profile 单独 gateway install，否则只有一个实例在收消息
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先跑 `hermes doctor` 再谈功能：它把依赖、配置版本、凭据、目录结构一次性检查完，本机能直接看到 `Config version up to date (v50)` 这类关键结论，装了坏包也能立刻发现
2. 配置改动走 `hermes config set` 而不是手写 YAML：命令会按 key 形态自动分流（`UPPER_SNAKE` 进 `.env`，带点的键进 `config.yaml`），减少把密钥误写进配置文件的概率
3. 一条实例一个用途，多用 profile 隔离：多环境、多租户、多账号场景使用 `hermes profile create`，而不是装两份 Hermes
4. 常驻场景一律 `gateway install` + `enable-linger`：`gateway run` 只适合调试，SSH 会话结束进程就没了
5. 把「技能」当第一扩展手段：能用文档说清的能力先写技能，只有必须写代码（访问 API、解析二进制）时才做工具/插件
6. 升级前留好回滚面：`hermes update` 本身有 `updates.pre_update_backup`（默认 `quick` 快照关键状态），重要的自定义技能与插件目录另外单独入 git

### 踩坑记录

```text
坑 1：改了工具集或技能，会话里毫无变化
结论：配置确实写进去了，但当前会话仍然用旧清单。
原因：工具与技能索引在会话建立时冻结，中途修改不生效（这是为保护 prompt caching 有意为之）。
解法：在新会话里验证——CLI 用 /reset 或重启 hermes，网关用 /restart；确认 hermes tools list 已反映改动。

坑 2：网关在 SSH 断开后不工作
结论：机器还活着，但 gateway 进程消失了。
原因：以用户级 systemd 服务或 nohup 启动时，会话结束会连带清理；WSL2 下还可能因为没有 systemd 而回退到 nohup。
解法：sudo loginctl enable-linger $USER；WSL2 在 /etc/wsl.conf 里开 systemd=true；崩溃循环用 systemctl --user reset-failed hermes-gateway。

坑 3：把 Hermes 当成「只会聊天的机器人」来设计架构
结论：接进平台后 Agent 只能搜索和澄清，跑不了命令、读写不了文件。
原因：不同入口挂的工具集预设不同，例如 webhook 触发的运行只有 web_search / web_extract / vision_analyze / clarify 这一只读子集。
解法：设计前用 hermes tools list 核对目标平台的工具集；CLI 侧默认 hermes-cli，网关侧按平台预设继承，需要时用 --toolsets 或配置显式调整。

坑 4：直接在 ~/.hermes 里手改 YAML，改出一份「Hermes 不读」的死配置
结论：键写进去了、命令也能跑，但行为没变。
原因：键放在了错误的层级（该在 skills.config 下却写在顶层，或该进 .env 却留在 config.yaml），schema 无法区分「拼错的键」与「运行时读取的键」，只会警告不会拒绝。
解法：优先 hermes config set；核对用 hermes config get <key>（会提示该键可能不被读取）；结构问题用 hermes config check / hermes config migrate 修。

坑 5：以为配置改完立刻生效，包括密钥
结论：.env 里的密钥改了，当前会话仍然用旧值。
原因：进程启动时读取环境，部分开关（如安全相关的开关）在 import 时就快照了。
解法：CLI 退出重进，网关 /restart；会话内可 /reload 重新载入 .env 变量。
```
