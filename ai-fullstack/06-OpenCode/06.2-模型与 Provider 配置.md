## 概述

OpenCode 把「模型」这件事拆成两层：Provider（谁提供模型、走哪个端点、用什么凭据）与 Model（具体调哪个模型、带什么参数）。底层用的是 AI SDK 加 Models.dev 的目录数据，因此内置支持 75+ 家 Provider，并且任何 OpenAI 兼容端点都能通过自定义 Provider 接进来——包括内网网关和本地推理服务。本主题讲清楚凭据怎么存、模型 ID 怎么写、自定义 Provider 怎么配、本地模型怎么接、以及日常怎么切换。

```text
本节要点：
1. 模型 ID 格式 —— <provider_id>/<model_id>，例如 anthropic/claude-sonnet-4-5、opencode/gpt-5.1-codex
2. 凭据存储 —— /connect 或 opencode auth login 写入 ~/.local/share/opencode/auth.json
3. 默认模型 —— 配置里的 model 键；轻量任务（如生成标题）走 small_model
4. 自定义 Provider —— provider.<id> 下配 npm（AI SDK 包）、name、options.baseURL、models
5. 本地模型 —— Ollama、LM Studio、llama.cpp、Atomic Chat 都是「自定义 Provider + 本地 baseURL」
6. 选择策略 —— /models 手动选、-m 显式指定、variant 切档位、per-agent 单独指定模型
```

## Provider 体系与凭据存储

OpenCode 启动时加载两类信息：凭据（谁登录过）与模型目录（各家有哪些模型、上下文多大、价格多少）。凭据来自 `/connect` 或 `opencode auth login`，统一落在 `~/.local/share/opencode/auth.json`；模型目录来自 Models.dev，本地会缓存，可以用 `opencode models --refresh` 强制刷新。除此之外，OpenCode 也会读取环境变量和项目根目录的 `.env` 文件里的 Key。

```bash
# 在 TUI 内接 Provider（推荐新手路径）
/connect

# 无界面环境：交互式登录
opencode auth login
opencode auth login -p anthropic             # 指定 Provider ID 或名称
opencode auth login -p openai -m "ChatGPT"   # 指定登录方式，跳过方式选择

# 查看已登录的 Provider / 注销
opencode auth ls
opencode auth logout
```

```text
# 本机未配置凭据时的真实输出
$ opencode auth list

┌  Credentials ~/.local/share/opencode/auth.json
│
└  0 credentials
```

也可以用环境变量直接给 Key，适合容器与 CI（不用落盘凭据文件）。OpenCode 启动时会读进程环境，也会读项目里的 `.env`：

```bash
# 常见 Provider 的环境变量名（以官方文档为准，各 Provider 可能不同）
export ANTHROPIC_API_KEY=sk-ant-...
export OPENAI_API_KEY=sk-...
export OPENROUTER_API_KEY=sk-or-...

# 把 Key 写进项目的 .env（注意：默认权限规则会拒读 .env 文件，见 06.4）
echo 'OPENAI_API_KEY=sk-...' >> .env
```

```text
凭据与目录要点：
1. 凭据文件 —— ~/.local/share/opencode/auth.json，是唯一的凭据落盘位置，迁移时只搬这一个文件
2. 目录来源 —— 模型清单来自 Models.dev，缓存可通过 opencode models --refresh 刷新
3. 环境变量 —— 进程环境与项目 .env 都会参与装载，适合容器/CI 免落盘
4. 查看与过滤 —— opencode models <provider> 只列某家；--verbose 会带上费用等元数据
5. 注销 —— opencode auth logout 从凭据文件中移除该 Provider
6. 安全提醒 —— 凭据文件与 .env 都属于敏感文件，不要提交进 Git（默认权限规则会拒读 .env）
```

## 内置 Provider 与登录

绝大多数主流 Provider（Anthropic、OpenAI、Google、OpenRouter、DeepSeek、Groq、xAI 等）都已预置，只要凭据存在就会自动出现，无需手写配置。对新手，官方推荐先用 OpenCode Zen：它是官方筛过、验证过与 OpenCode 配合良好的模型清单，按量计费，接入只要一次 `/connect`；另有 OpenCode Go 是低成本的订阅方案。两者都是可选，不影响接别家。

```text
# OpenCode Zen / Go 接入流程（TUI 内）
1. /connect                  → 选择 OpenCode Zen（或 OpenCode Go）
2. 浏览器打开 opencode.ai/auth → 登录、绑定支付方式、复制 API Key
3. 粘贴 API Key
4. /models                   → 从推荐列表里挑一个模型
```

```bash
# 命令行侧：列出当前可用的全部模型（provider/model 形式）
opencode models

# 只看某个 Provider
opencode models anthropic

# 刷新模型目录缓存（新增模型后立刻可见）
opencode models --refresh
```

```text
# 本机实测：已配置一个自定义 Provider 后的模型清单
$ opencode models

opencode/cat-jam-free
opencode/longcat-2.5-preview-free

```

注意最后一行 `mocklocal/mock-gpt`：它是下面「自定义 Provider」章节里配的本地模拟端点，说明自定义 Provider 的模型会与内置 Provider 的模型一起出现在选择器与命令行清单里。

```text
内置 Provider 要点：
1. 预置范围 —— 主流厂商开箱可用，凭据存在即出现在列表里，不必手写 provider 配置
2. 新手路径 —— /connect 选 OpenCode Zen，官方验证过的模型清单，按量计费；Go 为低成本订阅
3. 命令行核对 —— opencode models [provider] 打印 provider/model 形式清单，是排查模型名写错的首选
4. 缓存机制 —— 模型目录本地有缓存，新增模型用 opencode models --refresh 刷新
5. 过滤与隐藏 —— provider.<id>.blacklist 隐藏指定模型，whitelist 只保留指定模型
6. 权限策略 —— experimental.policies 可按 provider.use 动作拒绝某家 Provider，用于合规约束
```

## 模型 ID 与默认模型设置

模型 ID 的格式固定为 `<provider_id>/<model_id>`，凡是写错就会出现 `ProviderModelNotFoundError`。默认模型写在配置文件的 `model` 键；轻量任务（会话标题生成等）用 `small_model`，不配则 OpenCode 自行挑选可用的便宜模型，挑不到就回退主模型。模型选项（推理档位、思考预算等）挂在 `provider.<id>.models.<model>.options` 下，可全局配，也可被 agent 级配置覆盖。

```json
{
  "$schema": "https://opencode.ai/config.json",
  "model": "anthropic/claude-sonnet-4-5",
  "small_model": "anthropic/claude-haiku-4-5"
}
```

```jsonc
// 给内置模型配全局选项：OpenAI 与 Anthropic 各一例
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "openai": {
      "models": {
        "gpt-5": {
          "options": {
            "reasoningEffort": "high",
            "textVerbosity": "low",
            "reasoningSummary": "auto",
            "include": ["reasoning.encrypted_content"]
          }
        }
      }
    },
    "anthropic": {
      "models": {
        "claude-sonnet-4-5-20250929": {
          "options": {
            "thinking": { "type": "enabled", "budgetTokens": 16000 }
          }
        }
      }
    }
  }
}
```

模型加载优先级（启动时按序取第一个命中的）：

```text
1. 命令行参数 --model / -m      例：opencode run -m openai/gpt-4.1 "..."
2. 配置文件里的 model 键       例："model": "anthropic/claude-sonnet-4-5"
3. 上一次使用过的模型
4. 内部优先级排序出的第一个模型
```

```text
模型 ID 与默认值要点：
1. 格式 —— provider/model；内置模型名可在 models.dev 查，自定义 Provider 的 model_id 就是 models 里的键
2. 默认模型 —— 配置文件的 model 键；命令行 -m 优先级更高
3. 轻量模型 —— small_model 用于标题生成一类廉价任务，不配则自动挑选或回退主模型
4. 模型选项 —— 配在 provider.<id>.models.<model>.options，agent 级配置可覆盖全局
5. 查询手段 —— opencode models（列清单）、opencode models --verbose（带费用等元数据）
6. 常见报错 —— ProviderModelNotFoundError 基本都是 provider/model 写错或 Provider 未登录
```

## 自定义 Provider 配置

任何 OpenAI 兼容端点都能作为自定义 Provider 接进来。做法是在配置文件的 `provider` 下新增一个 ID，指定 `npm`（用哪个 AI SDK 包）、`name`（界面显示名）、`options.baseURL`（端点）、可选 `options.apiKey`/`options.headers`，以及 `models` 映射。若模型走 `/v1/chat/completions` 用 `@ai-sdk/openai-compatible`；若走 `/v1/responses` 则要用 `@ai-sdk/openai`。

```json
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "myprovider": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "My AI Provider Display Name",
      "options": {
        "baseURL": "https://api.myprovider.com/v1",
        "apiKey": "{env:MYPROVIDER_API_KEY}",
        "headers": { "Authorization": "Bearer custom-token" }
      },
      "models": {
        "my-model-name": {
          "name": "My Model Display Name",
          "limit": { "context": 200000, "output": 65536 }
        }
      }
    }
  },
  "model": "myprovider/my-model-name"
}
```

配置项含义与常用 Provider 级选项：

| 字段 | 位置 | 作用 |
| --- | --- | --- |
| `npm` | provider 级 | 指定 AI SDK 包，OpenAI 兼容用 `@ai-sdk/openai-compatible`，/v1/responses 用 `@ai-sdk/openai` |
| `name` | provider 级 | UI 中的显示名 |
| `options.baseURL` | provider 级 | 端点地址，代理/网关/本地服务都靠它 |
| `options.apiKey` | provider 级 | 直接写 Key，支持 `{env:VAR}` 与 `{file:path}` 变量替换 |
| `options.headers` | provider 级 | 自定义请求头，网关鉴权常用 |
| `options.timeout` | provider 级 | 请求超时（毫秒，默认 300000，`false` 关闭） |
| `options.chunkTimeout` | provider 级 | 流式分片间隔超时（默认 900000） |
| `models.<id>.name` | model 级 | 模型在选择器里的显示名 |
| `models.<id>.limit` | model 级 | 上下文与输出上限，影响上下文压缩判断 |
| `blacklist` / `whitelist` | provider 级 | 隐藏或只保留部分模型 |
| `disabled_providers` / `enabled_providers` | 顶层 | 全局禁用或只启用某些 Provider（disabled 优先） |

下面是本机实测：写一个最小的 OpenAI 兼容模拟服务（`/v1/models` 与 `/v1/chat/completions`，支持 SSE 流式），把它配成自定义 Provider，然后用 `opencode run` 真跑一次。

```python
# mock_llm.py —— 最小 OpenAI 兼容服务，用于验证自定义 Provider 配置是否生效
import json, http.server, socketserver

class H(http.server.BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"
    def log_message(self, *a): pass

    def _json(self, obj, code=200):
        data = json.dumps(obj).encode()
        self.send_response(code)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_GET(self):
        if self.path.rstrip("/").endswith("/models"):
            self._json({"object": "list", "data": [{"id": "mock-gpt", "object": "model"}]})
        else:
            self._json({"error": "not found"}, 404)

    def do_POST(self):
        n = int(self.headers.get("Content-Length", 0))
        req = json.loads(self.rfile.read(n) or b"{}")
        model, text = req.get("model", "mock-gpt"), "pong from mock model"
        if not req.get("stream"):
            return self._json({
                "id": "1", "object": "chat.completion", "created": 0, "model": model,
                "choices": [{"index": 0, "message": {"role": "assistant", "content": text},
                             "finish_reason": "stop"}],
                "usage": {"prompt_tokens": 1, "completion_tokens": 1, "total_tokens": 2}})
        self.send_response(200)
        self.send_header("Content-Type", "text/event-stream")
        self.send_header("Connection", "close")
        self.end_headers()
        for c in [
            {"id": "1", "object": "chat.completion.chunk", "created": 0, "model": model,
             "choices": [{"index": 0, "delta": {"role": "assistant", "content": ""}, "finish_reason": None}]},
            {"id": "1", "object": "chat.completion.chunk", "created": 0, "model": model,
             "choices": [{"index": 0, "delta": {"content": text}, "finish_reason": None}]},
            {"id": "1", "object": "chat.completion.chunk", "created": 0, "model": model,
             "choices": [{"index": 0, "delta": {}, "finish_reason": "stop"}]},
        ]:
            self.wfile.write(f"data: {json.dumps(c)}\n\n".encode()); self.wfile.flush()
        self.wfile.write(b"data: [DONE]\n\n"); self.wfile.flush()

class S(socketserver.ThreadingTCPServer):
    allow_reuse_address = True
    daemon_threads = True

if __name__ == "__main__":
    with S(("127.0.0.1", 8399), H) as httpd:
        print("mock LLM on http://127.0.0.1:8399/v1")
        httpd.serve_forever()
```

## 接入本地模型

本地推理服务只要提供 OpenAI 兼容接口，就能按「自定义 Provider + 本地 baseURL」接进来。官方文档给出了 Ollama、LM Studio、llama.cpp（llama-server）、Atomic Chat 的配置样例，差别只在端口与模型名；Ollama 还支持自动为 OpenCode 写配置，具体以 Ollama 官方集成文档为准。

```json
// Ollama（默认端口 11434）
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "ollama": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Ollama (local)",
      "options": { "baseURL": "http://localhost:11434/v1" },
      "models": { "llama2": { "name": "Llama 2" } }
    }
  }
}
```

```json
// LM Studio（默认端口 1234）
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "lmstudio": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "LM Studio (local)",
      "options": { "baseURL": "http://127.0.0.1:1234/v1" },
      "models": { "google/gemma-3n-e4b": { "name": "Gemma 3n-e4b (local)" } }
    }
  }
}
```

```json
// llama.cpp 的 llama-server（默认端口 8080），显式声明上下文与输出上限
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "llama.cpp": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "llama-server (local)",
      "options": { "baseURL": "http://127.0.0.1:8080/v1" },
      "models": {
        "qwen3-coder:a3b": {
          "name": "Qwen3-Coder: a3b-30b (local)",
          "limit": { "context": 128000, "output": 65536 }
        }
      }
    }
  }
}
```

启动本地服务并验证端点可用（以 Ollama 为例，命令以官方文档为准）：

```bash
# 拉一个适合写代码的模型并启动服务
ollama pull qwen2.5-coder:7b
ollama serve

# 端点冒烟测试：OpenAI 兼容路径是否响应
curl -s http://localhost:11434/v1/models | head -c 300

# 在 OpenCode 里选中它
# /models → 选择 Ollama (local) 下的模型；或启动时 -m ollama/qwen2.5-coder:7b
```

```text
本地模型要点：
1. 通用做法 —— 都是「自定义 Provider + 本地 baseURL + models 映射」，端口分别是 Ollama 11434、LM Studio 1234、llama-server 8080
2. tool call 问题 —— 本地模型若工具调用不稳定，官方建议调大 Ollama 的 num_ctx（从 16k - 32k 起试）
3. 上下文声明 —— 本地模型真实上下文常小于参数标称值，limit.context 要按实际显存/配置填，否则压缩判定失真
4. 首次连通 —— 用 curl <baseURL>/models 先确认端点活着，再排查 OpenCode 侧配置
5. 自动配置 —— Ollama 支持自动为 OpenCode 生成配置，具体以 Ollama 官方集成文档为准
6. 适用边界 —— 本地模型适合隐私敏感代码与离线场景，复杂重构仍建议接云端强模型
```

## 模型切换与选择策略

日常使用里有三种切换方式：TUI 里 `/models` 手动挑、会话中按快捷键在最近使用/收藏模型间循环、以及用 variant（同一模型的不同推理档位）切档。工程化场景下更常见的是「按 agent 分工指定模型」——比如让代码评审 agent 用强模型、让通用探索 agent 用便宜模型；也可以用 policies 直接禁止某家 Provider。

```text
# TUI 内常用切换动作
/models              → 打开模型选择器（keybind: ctrl+x m）
                      选择器里可切换 Provider 列表（默认 ctrl+a）、收藏模型（ctrl+f）
f2 / shift+f2        → 在最近使用的模型之间前后循环（keybind: model_cycle_recent）
ctrl+t               → 在模型的 variant 之间循环（keybind: variant_cycle）
Tab / shift+tab      → 切换 primary agent（每个 agent 可以绑定不同模型）
```

variant 用来给同一个模型配多档推理强度，不必为每档新建重复条目：

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "openai": {
      "models": {
        "gpt-5": {
          "variants": {
            "thinking": { "reasoningEffort": "high", "textVerbosity": "low" },
            "fast": { "disabled": true }
          }
        }
      }
    }
  }
}
```

内置 variant 的常见档位（不同厂商命名不同，以官方文档与 models.dev 为准）：Anthropic 有 `high`（默认）与 `max`；OpenAI 大致为 `none`/`minimal`/`low`/`medium`/`high`/`xhigh`；Google 为 `low`/`high`。

按 agent 指定模型与按策略禁用 Provider：

```json
{
  "$schema": "https://opencode.ai/config.json",
  "agent": {
    "code-reviewer": {
      "description": "只做评审，不改文件",
      "model": "anthropic/claude-sonnet-4-5",
      "tools": { "write": false, "edit": false }
    }
  },
  "experimental": {
    "policies": [
      { "effect": "deny", "action": "provider.use", "resource": "openai" }
    ]
  }
}
```

```text
模型切换与选择策略要点：
1. 手动选 —— /models（ctrl+x m）；命令行用 -m provider/model 显式指定
2. 快速循环 —— f2 / shift+f2 在最近使用的模型间切换，适合「强模型规划、便宜模型执行」
3. 档位切换 —— ctrl+t 切 variant，比复制多份模型配置更干净
4. 按 agent 分工 —— agent.<name>.model 覆盖全局模型，配合子代理做成本与质量分治
5. 合规约束 —— experimental.policies 以 provider.use 动作禁止指定 Provider
6. 参数微调 —— provider.<id>.models.<model>.options 配全局，agent 级配置优先
```

## 应用场景实战

### 场景一：接企业内部 OpenAI 兼容网关并跑通冒烟测试

很多公司不允许直连外部模型厂商，而是在内网暴露一个 OpenAI 兼容网关（带自己的鉴权头与限流）。做法是把网关配成自定义 Provider，Key 用环境变量注入，接完先做「配置解析 → 端点连通 → 真实对话」三段式验证。

```json
// 项目根目录 opencode.json：接入内网网关
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "corp-gw": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Corp Gateway",
      "options": {
        "baseURL": "https://llm-gw.corp.internal/v1",
        "apiKey": "{env:CORP_GW_KEY}",
        "headers": { "X-Tenant": "platform-team" },
        "timeout": 600000,
        "chunkTimeout": 60000
      },
      "models": {
        "claude-sonnet-4-5": { "name": "Sonnet 4.5 (corp)", "limit": { "context": 200000, "output": 64000 } },
        "qwen2.5-coder-32b": { "name": "Qwen2.5 Coder 32B (corp)", "limit": { "context": 131072, "output": 32768 } }
      }
    }
  },
  "model": "corp-gw/claude-sonnet-4-5",
  "small_model": "corp-gw/qwen2.5-coder-32b"
}
```

```bash
# 三段式验证
export CORP_GW_KEY=sk-corp-xxx

# 1) 配置被正确解析（能看到 provider 与 model 已合并进最终配置）
opencode debug config | head -20

# 2) 模型清单里出现新 Provider（自定义 Provider 的模型会和内置的一起列出）
opencode models corp-gw

# 3) 真实对话（非交互，便于脚本化）
opencode run -m corp-gw/claude-sonnet-4-5 "用一句话说明这个仓库的构建方式"

# 4) 表格化/JSON 化输出便于接监控
opencode run --format json -m corp-gw/qwen2.5-coder-32b "列出所有 TODO"
```

```text
# 本机等价实测（用本地模拟网关替代内网网关）
$ opencode run -m mocklocal/mock-gpt "reply with the word ping"
> build · mock-gpt

pong from mock model

# 服务端看到：GET /v1/models，随后两次 POST /v1/chat/completions
# （一次是标题生成，一次是正式请求）
```

### 场景二：本地模型做私有代码问答，云端模型负责复杂改造

隐私敏感的仓库不允许把源码发到外部，但复杂重构又需要强模型。可行策略是「双 Provider 并存 + 按 agent 分工」：本地 Ollama 处理日常问答与检索，云端模型只在明确授权的任务上使用，并用子代理隔离上下文。

```json
// 同时保留本地与云端两个 Provider，并按 agent 分工
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "ollama": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Ollama (local)",
      "options": { "baseURL": "http://localhost:11434/v1" },
      "models": {
        "qwen2.5-coder:7b": { "name": "Qwen2.5 Coder 7B (local)", "limit": { "context": 32768, "output": 8192 } }
      }
    },
    "anthropic": {
      "models": {
        "claude-sonnet-4-5": { "options": { "thinking": { "type": "enabled", "budgetTokens": 16000 } } }
      }
    }
  },
  "model": "ollama/qwen2.5-coder:7b",
  "agent": {
    "explore": { "model": "ollama/qwen2.5-coder:7b" },
    "refactor": {
      "description": "只在明确授权后执行重构",
      "mode": "subagent",
      "model": "anthropic/claude-sonnet-4-5",
      "permission": { "edit": "ask", "bash": "ask" }
    }
  }
}
```

```bash
# 本地模型处理日常问答（不出网）
opencode run -m ollama/qwen2.5-coder:7b "解释这个模块的数据流，不要改文件"

# 显式授权后的复杂改造，交给云端强模型 + 手工确认
opencode run --agent refactor -m anthropic/claude-sonnet-4-5 "按 docs/refactor-plan.md 重构 payment 模块"

# 出网审计：确认日常会话用的是本地 Provider
opencode stats --models --days 1
```

## 最佳实践与踩坑记录

### 最佳实践

1. Key 只进环境变量或凭据文件：配置里用 `{env:VAR}` / `{file:path}` 变量替换，绝不把明文 Key 提交进 `opencode.json`
2. 自定义 Provider 分环境：把内网网关写进项目级 `opencode.json`（可提交），个人密钥走全局配置或环境变量
3. 接网关先三段式验证：`opencode debug config` 看解析 → `opencode models <provider>` 看清单 → `opencode run` 真跑
4. 按真实能力填 `limit.context`：接代理网关或本地模型时尤其重要，虚报会让上下文压缩时机判断失真
5. 成本分治：`small_model` 配便宜模型，agent 级 `model` 让评审/探索类任务用低成本模型
6. 用 polices 做硬约束：合规要求禁止某家 Provider 时用 `experimental.policies` 显式 deny，而不是靠人自觉

### 踩坑记录

```text
坑 1：ProviderModelNotFoundError 反复出现
结论：模型选择失败，报找不到模型。
原因：模型 ID 写法不对——漏了 provider 前缀、Provider ID 拼错，或自定义 Provider 的 model_id 写成了显示名。
解法：统一使用 provider/model；用 opencode models 确认确切 ID；自定义 Provider 的 model_id 必须是 models 里的键。

坑 2：自定义 Provider 配好了但 /models 里看不到
结论：配置写在 opencode.json 里，模型列表却为空。
原因：配置写在了非生效位置（不在项目根或当前目录到 Git 根的路径上），或 npm 包名写错导致 Provider 初始化失败。
解法：用 opencode debug config 确认配置被读取；确认 npm 值是 @ai-sdk/openai-compatible 或 @ai-sdk/openai；ProviderInitError 时先清 ~/.cache/opencode。

坑 3：网关能用 curl 调通，OpenCode 一发请求就报错
结论：端点本身正常，OpenCode 侧调用失败。
原因：少见但常见的有两种——网关没实现或没放行 GET /v1/models 探测；或只支持非流式而客户端按流式解析。
解法：确认网关放行 /v1/models 与 SSE 流式 chat/completions；否则改用支持流式的端点或换 @ai-sdk/openai（走 /v1/responses 的网关）。

坑 4：本地模型工具调用时好时坏，经常答非所问
结论：能对话但 agent 能力异常，工具调用不稳定。
原因：本地模型可用上下文太小，系统提示与工具定义挤占了窗口；Ollama 默认 num_ctx 偏小。
解法：按官方建议把 Ollama 的 num_ctx 调到 16k - 32k 起；同时把 models.<id>.limit.context 按实际能力如实填写。

坑 5：上下文明明够大，却频繁触发压缩或中途截断
结论：长会话频繁压缩，回答质量骤降。
原因：models.<id>.limit.context 填得比真实能力大（网关/本地模型常见），压缩阈值判定失准。
解法：按端点真实上下文回填 limit；必要时调 compaction.reserved，或换上下文更大的模型跑长任务。
```
