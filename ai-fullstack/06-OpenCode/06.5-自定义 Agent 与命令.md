## 概述

OpenCode 的 agent 是「带独立提示词、独立模型、独立权限规则集」的一等配置对象：可以把「只读代码审查」「只写文档」「快速探索代码库」这类职责拆成不同 agent，各自绑定合适的模型与权限，再通过 Tab 切换或 `@名称` 直接调用。自定义命令则把重复输入的提示词固化成 `/命令名`，配合 `$ARGUMENTS` 参数与 shell 注入，把日常流程收敛成一条命令。

本篇覆盖四件事：内置 agent 有哪些、怎么定义自己的 agent、权限规则怎么写、提示词与命令放在哪里。

```text
本篇要解决的问题：
1. 内置 agent（build / plan / general / explore）各自能做什么、什么时候切
2. 用 Markdown 或 JSON 定义自定义 agent 的完整字段清单
3. 权限规则（allow / ask / deny + 通配符 + 最后匹配优先）怎么写才不出错
4. 子代理怎么被调用、自定义命令与 SKILL.md 提示词放在哪个目录
```

本篇的字段与命令以 opencode `1.19.0` 实测为准（`opencode --version` 输出 `1.19.0`）；官方文档见 `https://opencode.ai/docs/agents/` 与 `https://opencode.ai/docs/commands/`，版本升级后以官方文档与实际 `opencode debug agent <name>` 输出为准。

## Agent 类型与内置 Agent

agent 分两类：**primary（主代理）** 是你直接对话的对象，用 Tab 键轮换；**subagent（子代理）** 由主代理按需调用，或在消息里 `@名称` 手动调用。子代理运行在独立子会话里，中间过程不污染主会话上下文。

本机实测 `opencode agent list` 输出（1.19.0）：

```text
build (primary)
compaction (primary)
explore (subagent)
general (subagent)
plan (primary)
summary (primary)
title (primary)
```

其中 `compaction` / `title` / `summary` 是隐藏系统 agent（自动运行，UI 里选不到）；官方文档还列了 `scout`，它需要实验开关（`OPENCODE_EXPERIMENTAL_SCOUT`）才会出现。常用 agent 的定位：

| Agent | mode | 定位与工具权限 |
|-------|------|----------------|
| `build` | primary | 默认主代理，工具全开，标准开发场景 |
| `plan` | primary | 规划分析专用，默认 `edit` 为 `deny`，不改代码 |
| `general` | subagent | 通用多步骤任务，工具齐全，适合并行跑多份工作 |
| `explore` | subagent | 只读代码库探索，快，不能改文件 |
| `scout` | subagent | 只读外部文档与依赖研究，需实验开关 |

切换与调用方式：

```shell
# TUI 内：Tab 键在 primary agent 之间轮换
opencode

# 启动时直接指定 agent
opencode --agent plan

# 非交互模式指定 agent 与模型
opencode run --agent plan --model opencode/big-pickle "分析这个模块的耦合度并给出重构顺序"

# subagent 也可以在 prompt 里 @ 调用（由主代理发起 task 工具调用）
opencode run "@explore 找出所有调用 payment 的入口文件"
```

```text
内置 agent 要点：
1. primary 用 Tab 轮换，subagent 用 @名称 或由主代理按 description 自动挑
2. plan 默认不写文件，是"先出方案再动手"的低风险模式
3. explore / scout 只读，适合大仓库检索，避免子代理误改文件
4. compaction / title / summary 是隐藏系统 agent，不参与选择
5. 子代理跑在子会话里，可用 session_child_* 键位跳进去查看过程
```

子会话导航键位（TUI 内，键名以 keybind 配置为准）：`session_child_first` 默认 `<Leader>+Down` 进入第一个子会话，进入后用 `session_child_cycle`（Right）与 `session_child_cycle_reverse`（Left）循环，`session_parent`（Up）回到父会话。

## 定义自定义 Agent

agent 有两种定义方式：写进 `opencode.json`，或写成 Markdown 文件。后者更适合非平凡内容，因为正文就是系统提示词，文件还能进 Git 走评审。

Markdown 文件放置位置（单复数目录名都可用）：

```text
项目级：.opencode/agent/<name>.md    或  .opencode/agents/<name>.md
全局级：~/.config/opencode/agent/<name>.md（或 agents/）
```

文件名即 agent 名，`reviewer.md` 生成 `reviewer` agent。下面是一个实测可用的只读审查子代理：

```markdown
---
description: Reviews code for security, performance and maintainability issues
mode: subagent
model: opencode/big-pickle
temperature: 0.1
permission:
  edit: deny
  bash: deny
  webfetch: deny
---

You are in code review mode. Focus on:

- Code quality and best practices
- Potential bugs and edge cases
- Performance implications
- Security considerations

Provide constructive feedback without making direct changes.
```

Markdown frontmatter 允许的顶层字段（依据 1.19.0 内置配置 schema 说明）：

| 字段 | 说明 |
|------|------|
| `description` | 必填。说明这个 agent 做什么、何时用，主代理靠它决定是否自动调用 |
| `mode` | `primary` / `subagent` / `all` |
| `model` | 覆盖模型，格式固定为 `provider/model-id` |
| `variant` | provider 相关的推理档位，如 `high` / `max` / `minimal` |
| `temperature` / `top_p` | 采样参数，代码审查类建议 0.0-0.2 |
| `steps` | 最大 agent 迭代步数，超出后强制转为纯文本总结 |
| `hidden` | 是否在 UI 中隐藏 |
| `color` | UI 颜色，十六进制（如 `#ff6b6b`）或主题色名 |
| `permission` | 权限规则集，见下一节 |
| `disable` | 设为 `true` 关闭该 agent（也可用于关闭内置 agent） |
| `options` | 其余未知字段会被静默收进这里，透传给 provider |

两个官方提示要记住：**正文即 prompt，不要再在 frontmatter 里写 `prompt:`**；`description` 是必填项，缺了会导致 agent 无法被自动选择。

同样的 agent 也可以写在 `opencode.json`：

```json
{
  "$schema": "https://opencode.ai/config.json",
  "agent": {
    "reviewer": {
      "description": "Reviews code for security and performance issues",
      "mode": "subagent",
      "model": "opencode/big-pickle",
      "temperature": 0.1,
      "prompt": "{file:./prompts/code-review.txt}",
      "permission": { "edit": "deny", "bash": "deny" }
    }
  }
}
```

JSON 形式的 `prompt` 支持 `{file:相对路径}` 从文件读取提示词，路径相对该配置文件所在目录——这样全局配置与项目配置都能引用各自目录下的 prompt 文件。想关闭某个 agent，写 `"disable": true` 即可，例如 `agent: { build: { disable: true } }`。

交互式创建 agent 用 CLI：

```shell
# 交互式：依次问存放位置、描述、权限，最后生成 Markdown 文件
opencode agent create

# 非交互式：四个参数齐全时不再提问（--permissions 未列的权限一律 deny）
opencode agent create \
  --path .opencode/agents \
  --description "Review code for security and performance issues" \
  --mode subagent \
  --permissions read,grep,glob \
  --model opencode/big-pickle

# 列出所有 agent（含自定义）
opencode agent list

# 查看某个 agent 解析后的完整配置（字段名、权限展开、prompt 都在这里）
opencode debug agent reviewer
```

`opencode debug agent reviewer` 的输出能直接确认配置生效，自定义字段与权限被展开成一个有序规则数组：

```json
{
  "name": "reviewer",
  "description": "Reviews code for security, performance and maintainability issues",
  "mode": "subagent",
  "native": false,
  "temperature": 0.1,
  "model": { "modelID": "big-pickle", "providerID": "opencode" },
  "permission": [
    { "permission": "read", "pattern": "*", "action": "allow" },
    { "permission": "edit", "pattern": "*", "action": "deny" },
    { "permission": "bash", "pattern": "*", "action": "deny" },
    { "permission": "webfetch", "pattern": "*", "action": "deny" }
  ]
}
```

```text
自定义 agent 要点：
1. Markdown 文件名就是 agent 名，正文就是系统提示词
2. mode 决定它是主代理还是子代理，子代理不会被 Tab 选中
3. model 必须带 provider 前缀，用 opencode models 查可用取值
4. agent create 的 --permissions 是白名单：没列的权限一律 deny
5. 改完 agent 文件必须重启 opencode，配置不会热重载
```

## Agent 权限与工具控制

权限由 `permission` 字段控制，每条规则解析为 `allow`（直接执行）、`ask`（弹窗确认）、`deny`（拦截）。权限按工具名分组，常用键如下：

| 权限键 | 管控的调用 |
|--------|------------|
| `read` | 读文件（匹配文件路径） |
| `edit` | 所有文件修改（覆盖 edit / write / patch） |
| `glob` / `grep` / `list` | 文件匹配、内容搜索、目录列举 |
| `bash` | shell 命令（匹配解析后的命令，如 `git status --porcelain`） |
| `task` | 启动子代理（匹配子代理类型名） |
| `skill` | 加载技能（匹配技能名） |
| `webfetch` / `websearch` | 抓取 URL、联网搜索 |
| `lsp` / `question` | LSP 查询、执行中反问用户 |
| `doom_loop` | 同一工具用完全相同输入连续重复时的兜底 |
| `external_directory` | 任何触碰项目工作目录以外路径的工具调用 |

权限可写成单一动作，也可写成「模式 → 动作」的对象做细粒度控制。规则**按最后匹配者生效**，所以宽规则放前面、窄规则放后面：

```json
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "bash": {
      "*": "ask",
      "git *": "allow",
      "npm test*": "allow",
      "rm *": "deny"
    },
    "edit": {
      "*": "deny",
      "docs/**/*.md": "allow"
    },
    "external_directory": {
      "~/projects/shared/**": "allow"
    }
  }
}
```

`~` 与 `$HOME` 可写在模式开头表示家目录。注意 `external_directory` 只影响「是否允许触碰工作目录之外的路径」，`~` 展开不会把外部路径变成工作区的一部分，所以外部路径必须显式允许。

默认值：绝大多数权限默认 `allow`；`doom_loop` 与 `external_directory` 默认 `ask`；`read` 默认 `allow`，但 `.env` 系列默认拒绝：

```json
{
  "permission": {
    "read": {
      "*": "allow",
      "*.env": "deny",
      "*.env.*": "deny",
      "*.env.example": "allow"
    }
  }
}
```

按 agent 覆盖权限时，agent 规则与全局规则合并，且 agent 规则优先：

```json
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "bash": { "*": "ask", "git *": "allow", "git push *": "deny" }
  },
  "agent": {
    "build": {
      "permission": {
        "bash": { "*": "ask", "git *": "allow", "git push *": "ask" }
      }
    }
  }
}
```

弹窗出现时可选择 `once`（只批这一次）、`always`（本会话内批准同类模式）、`reject`（拒绝）；`always` 的具体模式集合由工具给出，例如 bash 通常给一个安全命令前缀。想整体放开用 `opencode --auto`（自动批准所有未被显式 deny 的请求），`opencode run --auto` 同理。

```text
权限要点：
1. 三个动作：allow 直接跑、ask 弹窗、deny 拦截
2. 对象语法按"最后匹配优先"，宽规则在前、窄规则在后
3. agent 级 permission 覆盖全局 permission，用来给不同 agent 定边界
4. .env 默认被 read 拒绝，doom_loop 与 external_directory 默认 ask
5. --auto 只影响本来会 ask 的请求，显式 deny 依然生效
```

## 子代理与并行任务

子代理的价值有两点：上下文隔离（检索过程不占主会话上下文）与并行（多个 `general` 子代理可同时跑多份互不依赖的工作，官方明确推荐用它并行执行）。调用路径有三条：主代理依据子代理的 `description` 自动选择；用户在消息里 `@名称` 手动调用；自定义命令通过 `agent` / `subtask` 字段指定。

本机实测：在主代理消息里写 `@reviewer`，主代理确实发起了 task 调用（子会话可在 `opencode session list` 中看到）；同时暴露一个真实限制——免费额度模型下子代理可能被拒，日志会提示回落到主代理自己完成：

```text
$ opencode run "@reviewer 用一句话评价这个目录的配置文件结构"
→ Read opencode.json
reviewer 子代理因免费额度限制未能运行，我直接查看了结构。……
```

用 `task` 权限可以控制「哪些子代理允许被调用」。设为 `deny` 时该子代理会从 task 工具的描述里被移除，模型就不会尝试调用它：

```json
{
  "$schema": "https://opencode.ai/config.json",
  "agent": {
    "build": {
      "permission": {
        "task": {
          "*": "deny",
          "orchestrator-*": "allow",
          "reviewer": "ask"
        }
      }
    }
  }
}
```

命令里也能强制子代理行为：`subtask: true` 会把命令执行强制变成子代理调用，即使该 agent 的 `mode` 是 `primary`，好处是命令输出不污染主上下文。

```text
子代理要点：
1. 子代理按 description 自动被选，写好 description 比写长 prompt 更重要
2. @名称 可手动调用；子会话用 session_child_* 键位导航
3. task 权限按子代理名做 glob 控制，deny 会让子代理从工具描述里消失
4. 命令的 subtask: true 强制走子代理，隔离上下文
5. 子代理是否可用还受模型/额度限制，被拒时应回落到主代理
```

## 自定义命令

自定义命令把一段固定提示词固化成一个 `/命令名`，定义方式同样有 Markdown 与 `opencode.json` 两种，存放位置：

```text
项目级：.opencode/command/<name>.md  或  .opencode/commands/<name>.md
全局级：~/.config/opencode/command/<name>.md（或 commands/）
```

Markdown 正文即 `template`（命令发给模型的提示词），frontmatter 提供元信息：

```markdown
---
description: Review recent changes with test results
agent: plan
---

Recent git commits:

!`git log --oneline -5`

Here are the current test results:

!`npm test --silent 2>&1 | tail -20`

Review these changes and suggest improvements for $ARGUMENTS.
```

提示词支持四类动态语法：

| 语法 | 作用 |
|------|------|
| `$ARGUMENTS` | 替换为用户在命令后输入的整串内容 |
| `$1` `$2` `$3` … | 按位置取参数，如 `/create-file config.json src "{}"` |
| shell 注入 | 用反引号加感叹号包裹命令，在项目根目录执行并把输出注入提示词 |
| `@文件路径` | 把文件内容作为引用带入提示词 |

本机实测（1.19.0）：一个同时包含 shell 注入与 `$ARGUMENTS` 的命令，两个占位符都被正确替换。

```markdown
<!-- .opencode/commands/echo-args.md -->
---
description: 验证自定义命令的占位符替换
---

Shell injection result: !`echo injected-by-shell`

User arguments were: $ARGUMENTS

Reply with exactly the two lines above, nothing else.
```

```text
$ opencode run --command echo-args "hello-from-cli"
> build · big-pickle

Shell injection result: injected-by-shell

User arguments were: hello-from-cli
```

等价的 JSON 写法：

```json
{
  "$schema": "https://opencode.ai/config.json",
  "command": {
    "test": {
      "description": "Run tests with coverage",
      "template": "Run the full test suite with coverage report and show any failures.\nFocus on the failing tests and suggest fixes.",
      "agent": "build",
      "subtask": true
    }
  }
}
```

命令的可选字段：`description`（TUI 展示）、`agent`（指定执行该命令的 agent，默认用当前 agent）、`model`、`subtask`（强制走子代理）。内置命令如 `/init`、`/undo`、`/redo`、`/share`、`/help` 依然可用；自定义命令与内置同名时会覆盖内置命令。

```text
自定义命令要点：
1. 正文就是 template，frontmatter 里不再写 template 字段
2. $ARGUMENTS 接整串参数，$1 $2 接位置参数，可混用
3. !`cmd` 在项目根目录执行并把 stdout 注入提示词，适合塞 git log / 测试结果
4. @file 直接把文件内容带进上下文，避免让模型自己去找
5. 指定 agent 可让只读命令跑在 plan 上；subtask: true 隔离上下文
```

## 提示词与 Agent Skills

提示词有三个落点：agent 的 prompt（JSON 用 `{file:...}`，Markdown 用正文）、项目的 `AGENTS.md`（常驻规则，见 [[06.4-规则与上下文]]）、以及按需加载的 **Agent Skills**（`SKILL.md`）。

Skill 的价值是「按需加载」：只在模型判断相关时才由 `skill` 工具载入，因此可以放很长的流程说明而不常驻上下文。目录结构与 frontmatter：

```text
.opencode/skills/<name>/SKILL.md           项目级
~/.config/opencode/skills/<name>/SKILL.md  全局级
.claude/skills/<name>/SKILL.md             Claude 兼容路径（自动扫描）
.agents/skills/<name>/SKILL.md             agent 兼容路径（自动扫描）
```

```markdown
---
name: git-release
description: Create consistent releases and changelogs from merged pull requests
license: MIT
compatibility: opencode
metadata:
  audience: maintainers
  workflow: github
  opencode/slash: "true"
  opencode/autoinvoke: "false"
---

## What I do

- Draft release notes from merged PRs
- Propose a version bump
- Provide a copy-pasteable `gh release create` command

## When to use me

Use this when you are preparing a tagged release.
Ask clarifying questions if the target versioning scheme is unclear.
```

`name` 必填、1-64 字符、小写字母数字加单连字符、必须与目录名一致；`description` 必填，1-1024 字符，要写清「做什么 + 什么时候用」。`metadata` 里有两个 OpenCode 专有键：`opencode/slash: "true"` 把技能同时暴露成 `/name` 命令；`opencode/autoinvoke: "false"` 让它不出现在模型的自动选择列表里，只能手动按名加载。

本机实测 `opencode debug skill` 确认技能被发现，并给出位置：

```json
[
  {
    "name": "customize-opencode",
    "description": "Use ONLY when the user is editing or creating opencode's own configuration: ...",
    "location": "<built-in>"
  },
  {
    "name": "git-release",
    "description": "Create consistent releases and changelogs from merged pull requests",
    "location": "/path/to/project/.opencode/skills/git-release/SKILL.md"
  }
]
```

技能还能用 `skills.paths` 从额外目录（递归扫 `**/SKILL.md`）或 `skills.urls` 远程装载，并用 `skill` 权限做模式级管控：

```json
{
  "$schema": "https://opencode.ai/config.json",
  "skills": {
    "paths": [".opencode/skills", "~/team-skills"]
  },
  "permission": {
    "skill": {
      "*": "allow",
      "internal-*": "deny",
      "experimental-*": "ask"
    }
  }
}
```

```text
提示词与技能要点：
1. 常驻上下文用 AGENTS.md 或 agent prompt，长流程用 SKILL.md 按需加载
2. SKILL.md 必须全大写命名，且 name 与目录名一致
3. description 决定模型是否选它，要写"何时使用"而不是"我是什么"
4. opencode/slash 让技能同时成为一个 /命令
5. skill 权限支持通配符，deny 的技能对模型完全隐藏
```

## 应用场景实战

### 场景一：给企业仓库加只读审查子代理，并接进 CI

目标：让 `reviewer` 只能读不能改，可在 TUI 里 `@reviewer` 调用，也能在 CI 用一条命令跑出审查报告。

```shell
# 1) 建目录
mkdir -p .opencode/agents
```

```markdown
<!-- .opencode/agents/reviewer.md -->
---
description: Reviews code for security, performance and maintainability issues
mode: subagent
model: opencode/big-pickle
temperature: 0.1
steps: 12
permission:
  edit: deny
  bash: deny
  webfetch: deny
  external_directory: deny
---

You are in code review mode for a Go/Python monorepo.

Focus on:
- Security: input validation, injection, secret leakage
- Performance: N+1 queries, unnecessary IO, unbounded loops
- Maintainability: duplicated logic, missing tests, unclear naming

Rules:
- Never modify files. Only report findings.
- Output a Markdown table: severity | file:line | problem | suggested fix
- Use read/grep/glob only when you need repository context.
```

```shell
# 2) 验证配置解析正确（权限是否按预期展开为规则数组）
opencode debug agent reviewer

# 3) TUI 内使用
opencode
#   > @reviewer 审查 src/payment/ 下最近的改动

# 4) CI 里非交互调用（只读 agent 不会改仓库，可直接进 MR 流水线）
opencode run "@reviewer 审查当前工作区未提交的改动，输出 Markdown 表格" > review.md
```

关键点：`steps: 12` 防止审查子代理无限迭代；`external_directory: deny` 让它连仓库外路径都读不到，把权限边界收在仓库内。

### 场景二：把发布流程固化成 /release 命令 + git-release 技能

目标：`/release v1.8.0` 一条命令完成「读最近提交、生成 release notes、给出 gh 命令」，且流程说明不常驻上下文。

```markdown
<!-- .opencode/skills/git-release/SKILL.md -->
---
name: git-release
description: Create consistent releases and changelogs from merged pull requests
metadata:
  opencode/slash: "true"
  opencode/autoinvoke: "false"
---

## What I do

- Draft release notes from merged PRs since the last tag
- Propose a semver bump based on commit types
- Provide a copy-pasteable `gh release create` command

## Steps

1. `git describe --tags --abbrev=0` 取上一个 tag
2. `git log --oneline 上一个tag..HEAD` 取提交
3. 按 Conventional Commits 分组：feat / fix / perf / refactor / docs
4. 给出 `gh release create <tag> --notes-file -` 的完整命令
```

```markdown
<!-- .opencode/commands/release.md -->
---
description: Draft release notes and the gh release command
agent: build
---

Target version: $ARGUMENTS

Use the git-release skill. Output in this order:

1. Draft release notes grouped by commit type
2. A one-line justification for the version bump
3. A single copy-pasteable `gh release create` command

Do not run any git write command; only read.
```

```shell
# 使用：TUI 里输入 /release v1.8.0
opencode
#   > /release v1.8.0

# 或 CLI 一条命令跑完
opencode run --command release "v1.8.0"
```

关键点：技能带 `opencode/slash: "true"` 时 `/git-release` 也能直接触发；`opencode/autoinvoke: "false"` 避免它在无关任务里被自动选中，减少上下文噪音。

## 最佳实践与踩坑记录

### 最佳实践

1. 一个 agent 只干一件事，`description` 写清「何时使用」，这决定主代理能否自动选对子代理
2. 子代理默认给最小权限：审查类 `edit: deny`、文档类 `bash: deny`，只有确实需要的才开
3. 权限规约遵循「宽在前、窄在后」的书写顺序，因为规则是最后匹配者生效
4. 提示词分层：约定放 `AGENTS.md`（常驻）、长流程放 `SKILL.md`（按需）、角色定位放 agent prompt
5. 用 `steps` 给自动化子代理设迭代上限，防止在 CI 里无限循环烧额度
6. 每次改完 agent / 权限 / 命令文件，重启 opencode 后再验证，并用 `opencode debug agent <name>` 核对解析结果

### 踩坑记录

```text
坑 1：opencode agent create 在未配置凭据时生成失败
结论：非交互执行时停在 "Generating agent configuration" 之后报错退出。
原因：该命令会调用模型生成 system prompt，未登录时会走 OpenCode 自有免费额度，而该免费额度只在 OpenCode 客户端内可用。
实测报错：LLM failed to generate agent: OpenCode's free tier can only be used from within OpenCode.
解法：先用 opencode auth login（别名 opencode providers）配置至少一个 provider；或直接手写 Markdown agent 文件，不依赖生成。

坑 2：在 Markdown agent 的 frontmatter 里又写 prompt 字段
结论：正文提示词与 prompt 字段冲突，行为不符合预期。
原因：Markdown 形式的 agent 用文件正文当 prompt，官方 schema 明确提示不要再写 prompt 字段。
解法：Markdown agent 只用正文当提示词；需要从文件读提示词时改用 opencode.json 加 "{file:./prompts/xxx.txt}"。

坑 3：权限对象写成 { "git *": "allow", "*": "ask" }
结论：所有命令都变成 ask，git 的 allow 规则形同虚设。
原因：规则按最后匹配者生效，兜底的 "*" 写在后面把前面的 allow 覆盖了。
解法：把 "*": "ask" 放在最前，具体 allow / deny 规则依次跟在后面。

坑 4：改了 agent 文件后没重启，以为配置没生效
结论：已经在跑的会话仍使用旧配置，TUI 里看不到新 agent。
原因：opencode 的配置（含 agents / commands / skills / plugins）只在启动时加载，不做热重载。
解法：退出并重启 opencode；排错时用 opencode debug agent <name> 确认磁盘配置已被读入。

坑 5：子代理在免费额度模型下被拒，任务"静默"回落
结论：@ 调用的子代理没有运行，结果由主代理自己完成，看起来像子代理没生效。
原因：部分免费/受限模型不允许子代理独立调用，运行时报"免费额度限制"。
解法：给子代理配一个可用的付费或自托管模型（agent 的 model 字段），或改为主代理直接执行并在文档里明确该限制。
```
