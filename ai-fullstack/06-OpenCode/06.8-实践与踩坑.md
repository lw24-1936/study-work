## 概述

这一篇是前面七篇的收口：把「跑不起来」「跑得慢」「跑得太贵」三类问题按可执行的排查路径整理出来，并给出成本统计、上下文优化与工具选型的方法。

排查的核心原则只有一条：**先看日志和数据目录，再改配置**。opencode 的日志、会话数据、缓存、认证凭据都落在固定位置，绝大多数问题看一眼日志就能定位，而不是靠猜。

```text
本篇要解决的问题：
1. 常见故障的定位顺序：日志 → 配置 → 凭据 → 网络/插件
2. 日志、数据、缓存、状态四类目录分别在哪、能删什么、不能删什么
3. 上下文与成本怎么会失控（MCP 工具描述、压缩策略、工具输出、模型选择）
4. opencode 与 Claude Code / Codex CLI / Cursor / Aider 的定位差异
```

本篇命令与输出以 opencode `1.19.0` 实测为准；官方排错文档见 `https://opencode.ai/docs/troubleshooting/`。注意 OpenCode 1 与 OpenCode 2 共用 `opencode` 命令、无法并存安装，v2 文档在 `https://opencode.ai/v2/docs/`，本篇描述的是 1.x。

## 常见问题排查

按「症状 → 先查什么 → 怎么修」的顺序列，排查顺序不要跳步：先确认版本与日志，再动配置。

| 症状 | 优先排查 | 处理 |
|------|----------|------|
| 启动就退 / 一片空白 | 日志与前台输出 | `opencode --print-logs` 看实时输出，`opencode upgrade` 升到最新版 |
| 认证失败 | 凭据与网络 | TUI 里 `/connect` 重新登录，检查 API Key 与出网策略 |
| 模型找不到 | 模型名格式 | 报 `ProviderModelNotFoundError` 基本是模型名写错，必须是 `provider/model-id`，用 `opencode models` 查真名 |
| 配置报错 | 配置结构 | `ProviderInitError` 多为配置损坏：`rm -rf ~/.local/share/opencode` 后重新登录 |
| 调用报 API 错误 | provider 包版本 | 清缓存 `rm -rf ~/.cache/opencode`，重启后会自动重装最新 provider 包 |
| 复制粘贴失效（Linux） | 剪贴板工具 | X11 装 `xclip` 或 `xsel`，Wayland 装 `wl-clipboard` |
| 权限弹窗一直等着 | 会话状态 | 界面里选 once / always / reject；服务端模式可从外部响应权限接口 |
| 桌面端白屏 | 插件 / 服务地址 | 临时移走插件目录或用 `--pure`，再检查是否配了不可用的 server 地址 |

实测两条容易被忽略的失败模式，都跟凭据相关：

```text
# 1) opencode agent create 在未配置 provider 时生成失败
LLM failed to generate agent: OpenCode's free tier can only be used from within OpenCode.

# 2) 免费额度模型下子代理被拒，主代理回落自己完成
reviewer 子代理因免费额度限制未能运行，我直接查看了结构。……
```

诊断命令一览：

```shell
# 打印当前解析后的配置（排查"配置到底生效没有"）
opencode debug config

# 看某个 agent 最终展开的权限规则与 prompt
opencode debug agent build

# 列出所有被发现的技能及其路径
opencode debug skill

# 看四个关键目录（数据/配置/缓存/状态）的真实位置
opencode debug paths

# 启动耗时分段（排查启动慢）
opencode debug startup

# 前台实时日志
opencode --log-level DEBUG --print-logs
```

```text
常见问题排查要点：
1. 先 `opencode --print-logs` 看到实时错误，再去翻文件日志
2. 模型名必须是 provider/model-id，用 opencode models 核对而不是凭记忆
3. ProviderInitError 用清数据目录解决，AI 调用类错误用清缓存解决
4. 配置改了没生效先 `opencode debug config` 确认解析结果，再考虑重启
5. 权限/弹窗类"卡住"不是崩溃，看界面状态与会话状态
```

## 日志与本地数据目录

opencode 把内容分成四类目录：数据（会话、认证）、配置、缓存（插件与依赖）、状态。实测 `opencode debug paths`：

```text
home       /root
data       /root/.local/share/opencode
bin        /root/.cache/opencode/bin
log        /root/.local/share/opencode/log
repos      /root/.local/share/opencode/repos
cache      /root/.cache/opencode
config     /root/.config/opencode
state      /root/.local/state/opencode
tmp        /root/.hermes/cache/scratch/opencode
```

数据目录的内容与用途：

| 路径 | 内容 | 能否删 |
|------|------|--------|
| `<data>/auth.json` | API Key 与 OAuth 令牌 | 删掉等于登出，需重新登录 |
| `<data>/log/` | 日志文件，按时间戳命名，只保留最近 10 个 | 可删，安全 |
| `<data>/project/` | 各项目的会话与消息数据（Git 仓库内按项目 slug 存，非仓库放 `global/storage/`） | 删掉会丢失历史会话 |
| `<data>/repos` | scout 等研究型 agent 克隆的依赖仓库缓存 | 可删 |
| `<cache>/` | provider 包、插件依赖（`node_modules`）、下载的 LSP | 可删，删后自动重装 |
| `<config>/` | `opencode.json`、`agents/`、`commands/`、`skills/`、`plugins/` | 不能删，这是你的配置 |

日志排查的常用姿势：

```shell
# 看最新一份日志
ls -t ~/.local/share/opencode/log | head -1
tail -200 ~/.local/share/opencode/log/$(ls -t ~/.local/share/opencode/log | head -1)

# 更详细的日志级别（DEBUG / INFO / WARN / ERROR）
opencode --log-level DEBUG

# 桌面端/CLI 都适用的插件排错：完全跳过外部插件
opencode --pure

# 清理最容易出问题的缓存（provider 包与插件依赖）
rm -rf ~/.cache/opencode
```

完全卸载（会问确认，可选择保留配置或数据）：`opencode uninstall`。

```text
日志与数据目录要点：
1. 日志在 <data>/log，只保留最近 10 份，先看最新的那份
2. 缓存（provider 包、插件依赖、LSP）可以随便删；配置目录不能删
3. 会话数据在 <data>/project，删了历史会话就没了
4. 凭据在 auth.json，删掉等于登出
5. --print-logs / --log-level DEBUG / --pure 是排查三件套
```

## 性能与上下文成本

三类开销按影响从大到小：**MCP 与工具的上下文占用** > **工具输出体积** > **模型本身的选择**。

MCP 是最容易被低估的一项：每个服务的工具描述都整体进入上下文，工具特别多的服务（官方点名 GitHub MCP server）很容易直接把上下文吃满，表现为「对话刚开始就开始丢早期信息」。控制手段：

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "context7": { "type": "remote", "url": "https://mcp.context7.com/mcp", "enabled": true },
    "playwright": { "type": "local", "command": ["npx", "-y", "@playwright/mcp"], "enabled": true }
  },
  "tools": {
    "playwright*": false
  },
  "agent": {
    "e2e": { "description": "Runs end-to-end browser tests", "mode": "subagent", "tools": { "playwright*": true } }
  },
  "experimental": {
    "mcp_timeout": 30000
  },
  "tool_output": {
    "max_lines": 200,
    "max_bytes": 8192
  },
  "compaction": {
    "auto": true,
    "tail_turns": 15
  }
}
```

几个关键点：`tools` 里按 glob 关闭工具（关掉的工具不会进上下文）；`tool_output` 限制单个工具输出的行数与字节数，防止一条命令的巨量输出把上下文顶爆；`compaction` 控制自动压缩的行为与保留的最近轮数；`mcp_timeout` 给慢 MCP 服务放宽拉取超时，避免启动阶段反复超时重试。

耗时相关的开关：

```shell
# 跳过外部插件（排查"到底是插件还是 opencode 慢"）
opencode --pure

# 跳过 LSP 自动下载（内网环境里这类下载会拖慢首次启动）
OPENCODE_DISABLE_LSP_DOWNLOAD=1 opencode

# 关掉自动压缩（只有明确要手工管理上下文时才用）
OPENCODE_DISABLE_AUTOCOMPACT=1 opencode

# 启动耗时分段，看时间花在哪
opencode debug startup
```

另一个被忽略的性能点是**冷启动**：脚本里反复 `opencode run` 会重复拉起实例、重复启动本地 MCP。正确做法是常驻一个 `opencode serve`，之后用 `opencode run --attach http://localhost:4096` 或 SDK 复用同一实例（见 [[06.7-服务端与 SDK]]）。

```text
性能与上下文要点：
1. MCP 服务数量直接决定基础上下文占用，按需挂、按 agent 开
2. tool_output 的 max_lines / max_bytes 是防"一条命令顶爆上下文"的闸门
3. compaction 保留最近轮数可调，自动压缩一般是省而不是费
4. 批量脚本用常驻 serve + attach，避免 MCP 反复冷启动
5. --pure / 关 LSP 下载 / debug startup 是分离"插件慢"与"本身慢"的手段
```

## 成本统计与控制

成本看两个地方：会话级的 tokens/cost 字段（每条会话记录里都有）和全局统计命令 `opencode stats`。实测在一台只有两次空会话的机器上：

```text
$ opencode stats
┌────────────────────────────────────────────────────────┐
│                       OVERVIEW                         │
├────────────────────────────────────────────────────────┤
│Sessions                                              2 │
│Messages                                              0 │
│Days                                                  1 │
└────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────┐
│                    COST & TOKENS                       │
├────────────────────────────────────────────────────────┤
│Total Cost                                        $0.00 │
│Avg Cost/Day                                      $0.00 │
│Avg Tokens/Session                                    0 │
│Median Tokens/Session                                 0 │
│Input                                                 0 │
│Output                                                0 │
│Cache Read                                            0 │
│Cache Write                                           0 │
└────────────────────────────────────────────────────────┘
```

统计命令的参数（1.19.0 实测 `opencode stats --help`）：`--days N`（只看最近 N 天）、`--tools N`（显示前 N 个工具的使用）、`--models N`（显示模型使用分布，不传数字则显示全部）、`--project`（按项目过滤，空字符串表示当前项目）。

除了汇总统计，单次运行也能拿到明细：`opencode run --format json` 会输出 NDJSON 事件流，`step_finish` 事件里带 tokens 与 cost（实测一次短问答）：

```text
{"type":"step_finish","part":{...,"reason":"stop","tokens":{"total":9425,"input":8124,"output":3,"reasoning":18,"cache":{"write":0,"read":1280}},"cost":0}}
```

```shell
# 最近 7 天的用量与模型分布（放 CI 里做成本巡检）
opencode stats --days 7 --models 5 --project ""

# 导出会话数据做离线分析（--sanitize 会脱敏）
opencode export <sessionID> --sanitize > session.json
```

控制成本的六个杠杆：

| 杠杆 | 做法 | 适用场景 |
|------|------|----------|
| 模型分级 | 主会话用强模型，子代理/小任务用便宜模型（agent 的 `model` 字段） | 长会话、批量任务 |
| 步数上限 | agent 配 `steps`，到顶强制转成总结 | 自动化、CI |
| 上下文瘦身 | 关掉不用的 MCP 工具、限制工具输出、调压缩保留轮数 | 大仓库 |
| 只读模式 | 审查/分析类任务用 `plan` 或只读子代理 | 代码审查、架构分析 |
| 非交互复跑 | `opencode run --format json` 配合脚本，避免反复交互试错 | 批量处理 |
| 凭据隔离 | CI 用独立 Key 并设额度上限，便于按团队/项目核算 | 团队协作 |

```text
成本统计与控制要点：
1. opencode stats --days N --models N 是日常成本巡检入口
2. 会话记录里自带 tokens 与 cost，可用 SDK/HTTP 汇总
3. 主会话强模型 + 子代理便宜模型是最省钱的组合拳
4. steps 上限防止自动化任务无限循环烧钱
5. 上下文瘦身（MCP 与工具输出）通常比换模型更立竿见影
```

## 与同类工具对比

选型不看"谁最强"，看约束条件：能不能换模型、能不能自托管、能不能脚本化、团队协作方式如何。下表按各官方文档整理（2026-10 现状，细节以官方为准）：

| 维度 | OpenCode | Claude Code | Codex CLI | Cursor / Aider |
|------|----------|-------------|-----------|----------------|
| 定位 | 开源终端 agent，可多端（TUI / Web / 桌面 / IDE 扩展） | Anthropic 官方 CLI | OpenAI 官方 CLI，Rust 实现 | Cursor 是编辑器；Aider 是终端结对编程工具 |
| 模型 | 任意 provider（走 models.dev 列表），也可用自带账号 | Claude 系列 | ChatGPT 账号或 API Key | 见各自文档 |
| 开源 | 是 | 否 | 是（github.com/openai/codex） | Cursor 否；Aider 是 |
| 扩展机制 | MCP + 插件（JS/TS 钩子）+ Agent Skills + 自定义 agent/命令 | MCP + Hooks + 子代理 + 技能 | MCP + 配置与审批模式 | 各自不同，见官方文档 |
| 脚本化 | `opencode run`、`serve` + HTTP API、`@opencode-ai/sdk` | `claude -p` 非交互 | `codex` CLI 及非交互模式 | CLI 用法各不相同 |
| 团队/云端协同 | 自身无云服务，靠 attach / serve / SDK 自建 | 有云端 Routines 定时任务 | 有云端托管形态 | 各自有托管方案 |
| 装法 | `curl -fsSL https://opencode.ai/install \| bash` | `curl -fsSL https://claude.ai/install.sh \| bash` | `curl -fsSL https://chatgpt.com/codex/install.sh \| sh` | 各自 README |

选型建议（按约束推，不按喜好推）：

```text
选型判断：
1. 需要换模型/自托管/内网部署 —— OpenCode（provider 无关 + serve 可自建后端）
2. 团队已在 Anthropic 生态、要云端定时任务 —— Claude Code
3. 团队已在 OpenAI 生态、要 Rust 单文件 CLI —— Codex CLI
4. 主要需求是编辑器内补全与内联编辑 —— 编辑器类工具（Cursor 等）
5. 只要终端里的最小结对编程、不想要复杂配置 —— Aider 等轻量工具
```

```text
对比要点：
1. 首要分歧是"锁不锁模型"，OpenCode 是 provider 无关的
2. 第二分歧是"能不能被程序驱动"，OpenCode 的 serve + SDK 覆盖度最高
3. 第三分歧是"后端在哪"，OpenCode 自身不含云服务，需要自己搭
4. 各家的插件/钩子机制都在快速演进，落地前必须复核官方文档
5. 混用是常态：同一个仓库用不同工具处理不同任务，规则文件可共用
```

## 应用场景实战

### 场景一：一次"卡住不动"的完整排查

现象：某位成员的 TUI 发出指令后长时间没有任何反应，也不报错。

```shell
# 第 1 步：确认版本与基本可用性
opencode --version

# 第 2 步：用前台日志复现，直接看实时输出
opencode --log-level DEBUG --print-logs
#   -> 观察到反复出现同一工具的相同调用，随后弹出权限确认，无人应答

# 第 3 步：把插件排除在外（插件异常也会表现为无响应）
opencode --pure
#   -> 现象依旧，说明不是外部插件导致

# 第 4 步：看文件日志里最近的错误
ls -t ~/.local/share/opencode/log | head -1
tail -200 ~/.local/share/opencode/log/$(ls -t ~/.local/share/opencode/log | head -1)
```

定位结果与处理：

```text
结论 A：模型陷入重复调用同一工具（doom_loop 场景），默认会在第三次相同输入时弹确认，
        无人应答就一直等 —— 这不是崩溃，是等待人工决策。
处理：在界面上选择 once / always / reject；或在可信场景用 opencode --auto
      （只自动批准未被显式 deny 的请求，deny 仍然拦截）。

结论 B：会话上下文已接近上限但自动压缩被关掉了（曾经设过 OPENCODE_DISABLE_AUTOCOMPACT=1）。
处理：取消该环境变量，或改用 compaction 配置控制保留轮数：
      { "compaction": { "auto": true, "tail_turns": 15 } }

结论 C：挂了慢 MCP 服务，启动阶段反复超时重试。
处理：调大该服务 timeout 或全局 experimental.mcp_timeout，用 opencode mcp list 确认连接状态。
```

### 场景二：大仓库的上下文与成本优化（前后对比）

现象：在一个多服务 monorepo 里，日常会话经常在中途丢失早期上下文，且成本偏高。

```json
// 优化前（.opencode/opencode.json）
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "github": { "type": "remote", "url": "https://api.githubcopilot.com/mcp/", "headers": { "Authorization": "Bearer {env:GH_TOKEN}" } },
    "context7": { "type": "remote", "url": "https://mcp.context7.com/mcp" },
    "playwright": { "type": "local", "command": ["npx", "-y", "@playwright/mcp"] }
  }
}
```

```json
// 优化后：常驻只留文档检索；重工具按 agent 开；限制工具输出；明确压缩策略
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "github": { "type": "remote", "url": "https://api.githubcopilot.com/mcp/", "headers": { "Authorization": "Bearer {env:GH_TOKEN}" }, "enabled": true },
    "context7": { "type": "remote", "url": "https://mcp.context7.com/mcp", "enabled": true },
    "playwright": { "type": "local", "command": ["npx", "-y", "@playwright/mcp"], "enabled": true }
  },
  "tools": {
    "github*": false,
    "playwright*": false
  },
  "agent": {
    "e2e": { "description": "Runs end-to-end browser tests", "mode": "subagent", "tools": { "playwright*": true } },
    "pr-ops": { "description": "Handles PR metadata and issue triage", "mode": "subagent", "tools": { "github*": true } }
  },
  "tool_output": { "max_lines": 200, "max_bytes": 8192 },
  "compaction": { "auto": true, "tail_turns": 15 },
  "instructions": ["AGENTS.md", "docs/conventions.md"],
  "small_model": "opencode/big-pickle"
}
```

量化验证（用同一批任务跑一周，前后各统计一次）：

```shell
# 优化前：最近 7 天
opencode stats --days 7 --models 5

# 优化后：同样口径再统计一次，对比 Tokens/Session 与模型分布
opencode stats --days 7 --models 5

# 单会话粒度核对：导出会话看 tokens 与 cost
opencode session list --max-count 10
opencode export <sessionID> --sanitize | head -40
```

关键点：用 `tools` 把重 MCP 的上下文代价从日常会话里移出去，只在对应子代理上开；`tool_output` 与 `compaction` 让长会话更稳；`small_model` 让标题生成、压缩这类小任务走便宜模型。

## 最佳实践与踩坑记录

### 最佳实践

1. 建立固定排查顺序：`--print-logs` → 文件日志 → `debug config` → 凭据 → 插件（`--pure`），别一上来就删配置
2. 缓存可以随时清（`~/.cache/opencode`），配置与会话数据不要随手删
3. MCP 服务按「必要 + 按需」分级，重工具统一「全局关、按 agent 开」
4. 设 `tool_output` 上限与 `compaction` 保留轮数，把上下文稳定性做成配置而不是靠运气
5. 每周跑一次 `opencode stats --days 7 --models 5`，成本异常时先看模型分布再改配置
6. 团队共用一份 `AGENTS.md` 与 `.opencode/`，把规则、agent、命令、MCP 一起进 Git 评审

### 踩坑记录

```text
坑 1：以为"没反应"是卡死，其实是权限弹窗在等人
结论：会话看起来僵住，实际是工具调用在等人工批准，无人应答就一直挂起。
原因：ask 类权限（含默认 ask 的 external_directory 与 doom_loop）必须有人点一下。
实测信号：日志里反复出现同一工具的相同输入调用。
解法：界面上选 once / always / reject；可信的自动化场景用 opencode --auto，但保留显式 deny 规则。

坑 2：模型名凭记忆写，报 ProviderModelNotFoundError
结论：请求直接失败，提示找不到模型。
原因：模型必须写成 provider/model-id 的完整形式，少写 provider 或拼错 id 都会报错。
解法：用 opencode models 列出真实可用模型（必要时 opencode models --refresh 刷新缓存）后再填配置。

坑 3：provider 包过期导致 API 调用报错，改配置没用
结论：任何 provider 配置调整都不解决，报 AI 调用类错误。
原因：provider 包是动态安装并缓存到 ~/.cache/opencode 的，旧版本可能不兼容模型参数变化。
解法：rm -rf ~/.cache/opencode 后重启，让 opencode 重新下载最新的 provider 包。

坑 4：一次 grep/bash 的巨量输出把上下文顶爆
结论：单条命令之后上下文立刻接近上限，后续对话开始丢信息。
原因：大仓库里一次 grep 或日志打印的输出可能上万行，全部计入上下文。
解法：配 tool_output 的 max_lines / max_bytes 设上限；提示里要求先过滤再输出（如配合 head/grep -c）。

坑 5：为了"稳定"关掉自动压缩，结果长会话更不稳定
结论：长会话在中途丢失早期上下文，且成本反而升高。
原因：压缩是把历史压成摘要，关掉后历史原始文本全留在上下文里。
解法：保持 compaction.auto 为 true，只用 tail_turns 控制保留最近轮数；确需手工管理时再临时用环境变量关闭。
```
