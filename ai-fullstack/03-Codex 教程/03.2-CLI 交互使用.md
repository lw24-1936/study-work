## 概述

Codex CLI 的日常用法围绕一个交互式终端界面（TUI）展开：你在仓库目录里敲 `codex`，它进入全屏界面，你描述任务、它读文件改代码跑命令，你在同一会话里追问。除此之外还有两条路径：带初始提示词直接启动（`codex "..."`），以及完全非交互的 `codex exec`。本文把这三条路径、常用斜杠命令、会话管理、文件与图片输入、模型与推理档位，按实际操作顺序讲清楚。本文所有命令均在 Codex CLI 0.162.1 上实测（见 03.1 的安装说明），参数以本机 `codex --help` 为准。

```text
CLI 交互的四件事：
1. 启动 —— codex 进 TUI；codex "prompt" 带初始提示词；codex exec "prompt" 非交互
2. 会话 —— resume/fork/archive/delete 管理本地会话，会话文件在 CODEX_HOME 下
3. 斜杠命令 —— /model /permissions /review /compact /init /mcp /status 等
4. 上下文 —— 引用文件、附带图片、带入 IDE 打开的文件
```

## 启动 Codex 与 TUI 概览

`codex` 是交互式入口，不跟子命令时所有选项都转发给 TUI。启动时它会先做几件事：检测当前目录是否是 Git 仓库、加载指令链（AGENTS.md）与配置、按仓库是否受版本控制推荐一个默认权限预设。TUI 顶部显示当前模型与推理档位、工作目录，底部是 composer 输入框与剩余上下文百分比；任务运行中可以直接打字排队，或用 `Tab` 把一个斜杠命令排到当前回合结束后执行。

```shell
# 1. 最常用：在仓库目录里启动全屏 TUI
cd ~/code/my-app
codex

# 2. 带初始提示词启动（仍进入 TUI，只是先自动提交这条提示）
codex "解释这个仓库的结构，指出最可能出问题的三个模块"

# 3. 指定工作根目录启动（不必先 cd）
codex -C ~/code/other-repo

# 4. 在全新 Git worktree 里跑，避免污染当前工作区
codex --worktree "把 Dashboard 组件改成 React Hooks"

# 5. 追加可写目录（默认只有工作区可写）
codex --add-dir ../shared-lib
```

实测的顶层全局参数里，与日常交互最相关的几个：

```text
1. 先 cd 再启动 —— TUI 的工作根目录默认取启动时的当前目录，直接决定沙箱可写范围
2. worktree 隔离 —— --worktree 在托管 Git worktree 里跑，改动不落当前分支，适合大改
3. 别一上来全放行 —— 默认预设已经够用，需要时再 /permissions 调整（见 03.4）
4. 内联模式 —— 终端不兼容全屏时加 --no-alt-screen，保留回滚历史
5. 配置排错 —— 升级后若提示配置字段不识别，用 --strict-config 直接报错定位
```

## 会话的恢复 归档与 fork

Codex 把每次运行持久化到本地（`CODEX_HOME` 下，默认 `~/.codex`），因此可以恢复、分叉、归档、删除。恢复有三档颗粒度：不带参数是选择器（picker，默认只列当前目录的会话），`--last` 直接接最近一次，指定 `SESSION_ID`（UUID 或会话名）精确定位；`--all` 取消当前目录过滤。fork 会基于某个已有会话开一条新分支，保留历史但各自独立演进——适合「在同一个上下文里试两种方案」。非交互会话默认不进选择器，需要时加 `--include-non-interactive`。

```shell
# 恢复：选择器 / 最近一次 / 指定 id
codex resume                       # 打开 recent sessions 选择器
codex resume --last                # 直接接最近一次（当前目录）
codex resume --all                 # 列出所有本地会话，不限当前目录
codex resume 7f9f9a2e-1b3c-4c7a-9b0e-xxxxxxxxxxxx "继续，把测试补上"

# 分叉与归档
codex fork --last                  # 基于最近一次会话开一条新分支
codex archive <SESSION_ID>         # 归档（从活跃列表移除，不删对话）
codex unarchive <SESSION_ID>       # 取消归档
codex delete <SESSION_ID>          # 永久删除

# 非交互会话也要能在选择器里看到
codex resume --include-non-interactive

# 查看会话文件
ls -1 "${CODEX_HOME:-$HOME/.codex}/sessions"
```

实测 `codex resume --help` 关键参数（真实输出，节选）：

```text
Usage: codex resume [OPTIONS] [SESSION_ID] [PROMPT]

Arguments:
  [SESSION_ID]  Session id (UUID) or session name. UUIDs take precedence if it parses.
  [PROMPT]      Optional user prompt to start the session

Options:
      --last  Continue the most recent session without showing the picker
      --all   Show all sessions (disables cwd filtering and shows CWD column)
      --include-non-interactive
              Include non-interactive sessions in the resume picker and --last selection
  -C, --cd <DIR>  Tell the agent to use the specified directory as its working root
```

```text
会话管理要点：
1. 默认按目录过滤 —— resume 只列当前工作目录的会话，跨目录找用 --all
2. 每条会话保留上下文 —— 恢复后带着原 transcript、计划历史与审批记录继续
3. fork 用于试方案 —— 想让 A/B 两个方案共享同一段前期上下文，用 fork 而不是新开会话
4. 归档不等于删除 —— archive 只是从活跃列表移除，对话文件仍在磁盘上
5. 会话落地在磁盘 —— sessions 目录在 CODEX_HOME 下，可备份、可迁移、可清理
```

## 常用斜杠命令

斜杠命令在 composer 里以 `/` 触发，弹出列表后继续输入可过滤。它们管的是「会话内部状态」：切模型、调权限、压上下文、发起审查。任务正在跑时也可以输入斜杠命令并 `Tab` 排队，Codex 会在当前回合结束后才解析执行——所以排队期间命令菜单和报错都在回合结束后才出现。

| 命令 | 作用 | 什么时候用 |
|---|---|---|
| `/init` | 生成 AGENTS.md 草稿 | 新仓库第一次接入 Codex |
| `/status` | 显示当前会话配置与剩余额度 | 想确认模型、沙箱、目录、额度 |
| `/permissions` | 调整权限（Auto / Read Only 等） | 会话中途放宽或收紧 |
| `/model` | 切换模型与推理档位 | 简单任务换便宜模型，难任务升档 |
| `/review` | 打开本地审查预设，对选定 diff 给发现 | 提交前自查 |
| `/compact` | 把可见对话摘要化，腾出上下文 | 长会话上下文快满 |
| `/clear` | 清屏并开始全新对话 | UI 与对话一起重置 |
| `/copy` | 复制最近一条完成的输出 | 想把答案贴到别处 |
| `/init`、`/ide`、`/mcp`、`/apps`、`/plugins`、`/hooks`、`/agent`、`/skills` | 上下文与扩展管理 | 带 IDE 上下文、看 MCP、切子代理线程 |
| `/vim`、`/keymap`、`/raw` | composer 编辑与快捷键定制 | 想用 Vim 键位或看原始输出 |
| `/archive` | 归档当前会话并退出 | 这件事做完了，收尾 |
| `/approve` | 批准一次被自动审查拒绝的重试 | 自动审查误拒了你要的这条命令 |
| `/sandbox-add-read-dir` | 给沙箱加只读目录（仅 Windows 原生） | Windows 上命令读不到工作区外的绝对路径 |

```text
斜杠命令要点：
1. 管会话状态 —— 与命令行参数不同，斜杠命令作用于当前会话，立即生效
2. 可排队 —— 任务运行中 Tab 排队，避免打断当前回合
3. /init 是第一件事 —— 新仓库先 /init 生成 AGENTS.md，再逐条补充规则（见 03.3）
4. /status 是仪表盘 —— 模型、沙箱、工作目录、额度都在这里，出问题先看它
5. 命令随版本增减 —— 以 TUI 里输入 / 弹出的列表为准
```

## 交互模式与一次性执行

三条执行路径的差别在「谁在等谁」：`codex`（TUI）是你与它来回对话；`codex "prompt"` 是带着第一条提示进 TUI，仍然交互；`codex exec "prompt"` 完全不交互，跑完就退出，进度走 stderr、最终消息走 stdout。`codex exec` 的用途是脚本与 CI（详见 03.6），但它同样支持恢复与分叉——`codex exec resume --last "继续"` 能把一次非交互运行接上。

```shell
# 交互式
codex
codex "把这个函数的圈复杂度降下来"

# 非交互：最终消息打到 stdout，可直接重定向
codex exec "总结仓库结构，列出 5 个高风险区域" | tee summary.md

# 非交互 + 恢复上一轮
codex exec resume --last "把刚发现的竞态条件修掉"
codex exec resume <SESSION_ID> "按计划实现"

# 非交互 + 不落盘（不保留 session 文件）
codex exec --ephemeral "评估这个仓库的下一步"

# 非交互 + 允许改工作区（默认是只读沙箱）
codex exec --sandbox workspace-write "把 print 换成 logging"

# 非交互 + 读提示词文件
cat prompt.txt | codex exec -

# 在 Git 仓库外强制运行
codex exec --skip-git-repo-check "只看不写，列出目录结构"
```

```text
执行模式要点：
1. 默认只读 —— codex exec 默认 read-only 沙箱，要它改代码必须显式 --sandbox workspace-write
2. 出口分离 —— 进度在 stderr、最终消息在 stdout，管道里拿到的只有结论
3. 可恢复 —— exec 会话同样能 resume/fork，两阶段流水线就靠这个串起来
4. 不落盘选项 —— --ephemeral 适合一次性检查，避免 sessions 目录堆积
5. 非交互里没有审批 —— 跑不了需要人工批准的步骤，越界动作直接失败并回传错误（详见 03.6）
```

## 文件引用 图片与 IDE 上下文

给 Codex 精确的上下文比给它更多上下文更划算。三种做法：**文件引用**——在 composer 里输入 `@` 触发模糊搜索，选中具体文件（或文件夹）把内容带进这一轮，比让它自己全仓库搜更快更省；**图片输入**——用 `-i/--image` 把截图、设计稿、报错图附在首条提示上，或在交互式 composer 里直接粘贴图片；**IDE 上下文**——`/ide` 把编辑器当前打开的文件、选中片段、诊断信息带进下一条提示。三者常常叠加使用：`/ide` 给出当前位置，`@` 补上关键文件，图片补上现场。

```shell
# 附加图片（多个用逗号分隔或重复该参数）
codex -i ./screenshots/error.png "根据这张报错截图定位问题并给出最小修复"
codex -i ./design/home.png -i ./design/figma-export.pdf "按设计稿实现首页组件"

# 一条提示里组合：初始提示 + 图片
codex --image ./perf-flamegraph.png "这张火焰图里哪个函数是瓶颈，怎么优化"
```

```text
上下文输入要点：
1. @ 引用 —— 在 composer 输入 @ 触发文件模糊搜索，把具体文件带进本轮提示
2. 图片走 -i —— 首条提示要带图就用 -i/--image；交互中直接往 composer 粘贴图片
3. /ide 带编辑器状态 —— 打开的文件、选中片段、诊断信息一次性带入
4. 少即是多 —— 只带相关文件，别把整个仓库塞进上下文，既慢又贵（见 03.7 成本控制）
5. 引用是快照 —— 引用的是当前文件内容，后续改动需要重新引用
```

## 模型与推理档位切换

模型决定能力上限，推理档位（reasoning effort）决定它在回答前想多久——两者共同决定质量、延迟与消耗。会话内用 `/model` 切换，配置文件里用 `model` 与 `model_reasoning_effort` 设默认，命令行用 `-m/--model` 临时覆盖。当任务从「探索」切到「实现」时升档，从「实现」切回「写文档」时降档，是控制成本最直接的手段。另有两个与速度有关的开关：Fast 模式（`/fast on|off|status`，用更高费率换取更快响应）与 Codex-Spark 这类专为实时迭代优化的模型（独立模型选择、独立额度）。

```shell
# 会话内切换（在 TUI 的 composer 里输入）
#   /model          —— 打开模型与推理档位选择器
#   /fast status    —— 查看 Fast 模式状态
#   /status         —— 看当前模型、档位、额度

# 命令行临时覆盖模型
codex -m gpt-5.4 "把这段 SQL 改成等价但不含子查询的写法"

# 用 profile 固化一组"深度审查"配置
codex --profile deep-review
```

```toml
# ~/.codex/config.toml：模型与推理档位的默认值
model = "gpt-5.4"                    # 具体可选值随账号与版本不同，以 /model 列表为准
model_reasoning_effort = "medium"    # 常见档位：low / medium / high（更高档位有 xhigh 等，见官方文档）

# 需要 Fast 模式时（费率更高，注意配额）
# service_tier = "fast"
# [features]
# fast_mode = true
```

```toml
# ~/.codex/deep-review.config.toml：profile 文件只写与基础配置不同的项
model = "gpt-5.5"
model_reasoning_effort = "xhigh"
approval_policy = "on-request"
```

```shell
# 用这个 profile 跑一次审查
codex --profile deep-review
codex exec --profile deep-review "对本次改动做安全审查"
```

```text
模型与档位要点：
1. 两维调节 —— 模型定上限，推理档位定"想多久"，两者都要按任务难度匹配
2. 会话内可切 —— /model 随时改，不必重启会话
3. profile 固化 —— 把"深度审查""快速修 bug"这类组合存成 profile，避免每次手调
4. 加速有代价 —— Fast 模式与 Ultrafast 按更高倍数消耗额度，只在高价值任务上用
5. 值随版本变 —— 可用模型名、档位取值以 /model 选择器与官方文档为准
```

## 应用场景实战

### 场景一：接手一个陌生仓库，用一轮交互式会话完成"理解 + 定位 + 最小修复"

真实场景：线上报了一个 bug，你要在没看过的代码库里快速定位并修掉，同时保持改动可审。

```shell
# 1. 干净基线
cd ~/code/service-a
git status && git pull --ff-only
git rev-parse --short HEAD        # 记下基线 commit

# 2. 带上下文启动：把报错截图和关键日志文件一起带进去
codex -i ./bug-screenshot.png \
  "这是线上 500 的截图。先读仓库结构，定位抛出该异常的调用链，
   说明为什么在并发下会触发，然后只做最小修复，不要顺手重构。"

# 3. 会话内继续追问与验证（在 TUI 里依次输入）
#    解释一下这条调用链的鉴权位置
#    @ internal/handler/order.go 这里是关键路径，先给我一个失败复现用例
#    /model        # 若需要更深推理，切到更高档位
#    /review       # 让独立 reviewer 审查这次 diff
#    /compact      # 上下文接近上限时压缩历史
#    /status       # 确认模型、沙箱与剩余额度

# 4. TUI 内退出后，人工复核
git diff
git add -A && git commit -m "fix: 修复并发下订单状态竞争的 500"
```

```text
为什么这样组织：
1. 先记基线 —— 出问题时可以 git reset 回干净的 HEAD
2. 图片带现场 —— 截图比文字描述"什么报错"精确得多
3. 限定范围 —— 明确"只做最小修复"，避免 AI 顺手重构把 diff 撑大
4. 独立审查 —— /review 用一个不写工作区的 reviewer 给出优先级发现
```

### 场景二：用 resume 与 fork 把一次重构拆成两条并行会话

真实场景：要把一个大模块从回调风格改成 async/await，你想同时试「小步提交」与「一次性重写」两种节奏，但希望两者共享同一份前期调研结论。

```shell
# 1. 先开一条调研会话，产出改造清单
cd ~/code/service-b
codex "调研 internal/worker 目录里所有回调风格代码，产出一份改造清单，
       按文件列出改动点与风险，不要动代码。"
# 会话结束后得到清单，记录会话 id
codex resume --last --dry-run 2>/dev/null || true   # 若无此参数，用 TUI 内 /status 查看会话 id

# 2. 从这条会话 fork 出两条，各自走不同策略
codex fork --last "按清单执行，但每个文件一次提交，改完立刻跑测试。"

# 另一条（新终端）
codex fork <SESSION_ID> "按清单执行，但分三批：先改类型定义，再改实现，最后改调用方，
                          每批结束跑一次全量测试。"

# 3. 挑一条结果保留，另一条直接丢弃
git diff --stat
git stash            # 不满意就丢掉这条分支上的改动

# 4. 会话收尾
codex archive <SESSION_ID>          # 归档已完成的会话
ls -1 "${CODEX_HOME:-$HOME/.codex}/sessions"   # 确认会话文件情况
```

```text
为什么这样组织：
1. 调研一次共享 —— fork 让两条策略复用同一份前期结论，不必重复调研
2. 策略分离 —— 小步提交 vs 分批重写，各自在自己的会话里推进互不干扰
3. 结果可弃 —— 改动都在工作区 diff 里，不满意 stash/checkout 即可
4. 归档不留垃圾 —— archive 把已完成的会话移出活跃列表
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一句任务只说一件事：把「理解 + 定位 + 修复 + 加测试」拆成几步，每步结束看一眼 diff 再继续。
2. 善用 `@` 与 `/ide` 精确投喂上下文：比让模型全仓库搜索更快、更省额度、结论也更准。
3. 长会话及时 `/compact`：上下文快满时先压缩再继续，比硬顶着跑更稳。
4. 大改用 `--worktree` 或 fork：改动不落在你正在工作的分支上，回滚成本接近零。
5. 提交前一律 `/review`：本地审查不写工作区，是零成本的第二双眼睛。
6. 常用配置固化成 profile：`--profile deep-review` 比每次手敲一堆 `-c` 参数可靠。

### 踩坑记录

```text
坑 1：在错误的目录启动，Codex 改到了别的项目
结论：启动时的工作目录决定工作根，改错了地方，diff 出现在不想动的仓库里。
原因：codex 默认以启动目录为工作根，且工作区是该目录下的可写范围。
解法：先 cd 到目标仓库再启动，或用 -C/--cd 显式指定；大改用 --worktree 隔离。

坑 2：任务运行中敲斜杠命令没反应
结论：输入了 /model 或 /permissions，等半天没生效。
原因：任务正在跑时斜杠命令会被排队，Codex 在当前回合结束后才解析并执行。
解法：等当前回合结束，或用 Tab 显式排队；紧急时先中断当前回合再改设置。

坑 3：resume 里找不到刚才的会话
结论：codex resume 的选择器里没有那次运行。
原因：resume 默认按当前工作目录过滤；非交互（codex exec）会话默认不进选择器。
解法：加 --all 取消目录过滤；非交互会话加 --include-non-interactive；也可直接给 SESSION_ID。

坑 4：以为 codex exec 会改代码，结果什么都没变
结论：非交互跑完，仓库纹丝不动。
原因：codex exec 默认运行在 read-only 沙箱里。
解法：需要它改代码就显式加 --sandbox workspace-write；只读检查则保持默认。

坑 5：图片附件没被模型引用
结论：用 -i 带了截图，但回答完全没看图。
原因：--image 只作用于"初始提示"，且路径写错或格式不支持时会静默跳过。
解法：把 -i 与首条提示写在同一行；交互式场景直接往 composer 粘贴图片更可靠。
```
