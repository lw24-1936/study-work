## 概述

Codex 自带的工具（读文件、改文件、跑命令、联网搜索）覆盖了编码的主要场景，但真实工程还需要访问外部系统：查最新文档、看 Sentry 里的报错、开 GitHub PR、读 Figma 设计稿。MCP（Model Context Protocol）就是把这层能力接进来的标准协议——你配置一个 MCP 服务器，Codex 启动时连上它，把它的工具并入自己的工具集。另一条扩展路径是**技能（Skills）**：把可复用的工作流写成带 `SKILL.md` 的目录，让 Codex 按需加载。MCP 接的是「外部系统」，Skills 封装的是「做事的方法」，两者组合就是官方所说的「skills 定义流程、MCP 连接工具」。

```text
工具扩展的三条路：
1. MCP —— 接入外部服务器（本地 STDIO 进程或远端 HTTP），获得它的工具
2. Skills —— SKILL.md + 脚本，把可复用流程与领域知识固化下来
3. 脚本 —— 技能里的 scripts/ 目录，或直接让 Codex 跑你仓库里的脚本
```

本文的命令与配置均在本机 Codex CLI 0.162.1 上实测过（含真实的 `codex mcp add/list/get/remove` 输出）。

## MCP 是什么与 Codex 的支持范围

MCP 把「模型 ↔ 工具」的接口标准化：服务器声明自己有哪些工具，客户端（这里是 Codex）把工具注入模型的工具列表，模型调用后拿到结构化结果。官方明确 Codex 支持的服务器形态有两类：**STDIO 服务器**（本地进程，由命令启动，支持环境变量传递）与 **Streamable HTTP 服务器**（通过地址访问，支持 Bearer token、OAuth、以及受信任一方服务器的 ChatGPT 会话认证）。另外 Codex 会读取服务器在初始化时返回的 `instructions` 字段，把它当作整套服务器的使用说明——所以写 MCP 服务器时，把跨工具的工作流、约束、速率限制放进去，并把最重要的信息压在前 512 个字符内，因为那部分在模型决策时最先被看到。

同一台机器上，ChatGPT 桌面 app、Codex CLI、IDE 扩展**共享同一份 MCP 配置**：配一次，三种客户端都能用。

```text
支持的服务器形态与认证：
1. STDIO —— 本地进程，command + args 启动，可用 env / env_vars 传环境变量
2. Streamable HTTP —— url 访问，支持 bearer_token_env_var、http_headers、env_http_headers
3. OAuth —— 默认认证方式，支持 CIMD 与 DCR 两种客户端注册，用 codex mcp login 触发
4. ChatGPT 会话认证 —— auth = "chatgpt"，用于受信任的一方可信源
5. Server instructions —— 服务器初始化返回的 instructions 会作为全局指引注入
```

```text
MCP 能做什么（官方列举的典型服务器）：
1. OpenAI Docs MCP —— 检索 OpenAI 开发者文档
2. Context7 —— 拉取最新第三方库文档
3. Playwright / Chrome DevTools —— 驱动并检查浏览器
4. Figma（本地或远端）—— 读取设计稿
5. Sentry —— 读取错误日志
6. GitHub MCP —— 超出 git 能力范围的 PR / Issue 操作
```

## 用 CLI 添加 MCP 服务器

最省事的配置方式是用 `codex mcp` 系列子命令，它直接改 `config.toml`。本机实测的真实过程：

```text
$ codex mcp add context7 -- npx -y @upstash/context7-mcp
Added global MCP server 'context7'.

$ codex mcp list
Name      Command  Args                      Env  Cwd  Status   Auth
context7  npx      -y @upstash/context7-mcp  -    -    enabled  Unsupported

$ cat ~/.codex/config.toml
[mcp_servers.context7]
command = "npx"
args = ["-y", "@upstash/context7-mcp"]
```

HTTP 形态同理，`--url` 代替 `-- <命令>`：

```text
$ codex mcp add example-http --url https://mcp.example.com
Added global MCP server 'example-http'.
MCP server may or may not require login. Run `codex mcp login example-http` to login.

$ cat ~/.codex/config.toml
[mcp_servers.context7]
command = "npx"
args = ["-y", "@upstash/context7-mcp"]

[mcp_servers.example-http]
url = "https://mcp.example.com"
```

查看单个服务器详情与清理：

```text
$ codex mcp get context7
context7
  enabled: true
  transport: stdio
  command: npx
  args: -y @upstash/context7-mcp
  cwd: -
  env: -
  remove: codex mcp remove context7

$ codex mcp remove example-http
Removed global MCP server 'example-http'.
```

```text
CLI 用法要点：
1. 加带参数的 STDIO 服务器 —— 用 `--` 分隔：codex mcp add <name> --env K=V -- <命令> [参数]
2. 加 HTTP 服务器 —— 用 --url：codex mcp add <name> --url https://...
3. 查看 —— codex mcp list 看总览，codex mcp get <name> 看单条明细
4. 认证 —— codex mcp login <name> / codex mcp logout <name>，仅 OAuth 服务器需要
5. 会话内查看 —— 在 TUI 里输入 /mcp 看当前会话连着哪些服务器
```

实测 `codex mcp --help` 的子命令集合：`list` / `get` / `add` / `remove` / `login` / `logout`。

## 在配置文件里配置 MCP

CLI 子命令够用，但要细粒度控制（超时、工具白名单、审批模式、OAuth 回调）必须直接写 `~/.codex/config.toml`，或用项目级的 `.codex/config.toml`（仅受信任项目加载）。每个服务器是一个 `[mcp_servers.<name>]` 表。

STDIO 服务器的字段：

```toml
# ~/.codex/config.toml
[mcp_servers.context7]
command = "npx"                       # 必填：启动服务器的命令
args = ["-y", "@upstash/context7-mcp"]
cwd = "/path/to/workdir"              # 可选：服务器的工作目录

# 传给服务器的固定环境变量
[mcp_servers.context7.env]
MY_ENV_VAR = "MY_ENV_VALUE"

# 允许并转发本机已有的环境变量（可为纯名字，或指定来源）
env_vars = ["LOCAL_TOKEN", { name = "REMOTE_TOKEN", source = "remote" }]
```

Streamable HTTP 服务器的字段：

```toml
# ~/.codex/config.toml
[mcp_servers.figma]
url = "https://mcp.figma.com/mcp"                 # 必填
bearer_token_env_var = "FIGMA_OAUTH_TOKEN"        # 从该环境变量取 Bearer token
http_headers = { "X-Figma-Region" = "us-east-1" }  # 静态请求头
# auth = "oauth"    # 默认；auth = "chatgpt" 用当前 ChatGPT 会话（受信任一方服务器）
# env_http_headers = { "X-Trace" = "TRACE_ID" }    # 头名 -> 环境变量名
```

通用控制字段（两种传输都适用）：

```toml
[mcp_servers.chrome_devtools]
url = "http://localhost:3000/mcp"
enabled = true                        # 置 false 可停用而不删除
startup_timeout_sec = 20              # 默认 10：启动超时
tool_timeout_sec = 45                 # 默认 60：单次工具调用超时
enabled_tools = ["open", "screenshot"]  # 工具白名单
disabled_tools = ["screenshot"]         # 工具黑名单（在 enabled_tools 之后生效）
default_tools_approval_mode = "prompt"  # auto | prompt | writes | approve

[mcp_servers.chrome_devtools.tools.open]
approval_mode = "approve"             # 单工具覆盖
output_token_limit = 30000            # 该工具的输出 token 预算

# 顶层设置：等待"可选" MCP 服务器构建初始工具目录的时间（毫秒，默认 1000）
# mcp_optional_startup_grace_ms = 1000
```

```text
配置文件要点：
1. 两种传输两套必填字段 —— STDIO 要 command，HTTP 要 url
2. 超时两层 —— startup_timeout_sec（默认 10）与 tool_timeout_sec（默认 60）
3. 工具可裁剪 —— enabled_tools / disabled_tools 控制暴露给模型的工具集合
4. required 会硬失败 —— 设 required = true 后服务器初始化失败会让本次运行直接报错
5. 项目级需受信任 —— .codex/config.toml 里的 MCP 只在项目被信任时加载
```

## 接入第三方服务与 OAuth

HTTP 类服务器常用 OAuth。官方流程是：`codex mcp add` 时会打印需要注册的**回调地址**，登录时用 `codex mcp login <name>`。对需要预注册客户端（pre-registered client）的授权服务器，加服务器时就提供 client id（机密客户端再加 secret，secret 从环境变量读，落盘在 `config.toml` 里，务必不要提交）：

```shell
# 预注册客户端
codex mcp add example --url https://mcp.example.com \
  --oauth-client-id my-client

# 机密客户端：secret 从环境变量读入
codex mcp add example --url https://mcp.example.com \
  --oauth-client-id my-client \
  --oauth-client-secret "$MCP_CLIENT_SECRET"

# 登录 / 登出
codex mcp login example
codex mcp logout example

# 强制指定本次登录的客户端注册方式（默认 auto）
codex mcp login example --oauth-client-registration cimd
codex mcp login example --oauth-client-registration dcr
```

Codex 会把 client id 与回调地址存进 `config.toml`，供后续登录复用：

```toml
[mcp_servers.example]
url = "https://mcp.example.com"

[mcp_servers.example.oauth]
client_id = "my-client"
callback_url = "http://127.0.0.1/callback"
```

回调地址有自定义需求时，可用顶层键覆盖：

```toml
# ~/.codex/config.toml
mcp_oauth_callback_port = 5555                          # 固定本地监听端口
mcp_oauth_callback_url = "https://devbox.example.internal/callback"  # 代理/远端入口
```

```text
第三方接入要点：
1. 加完先登录 —— HTTP 服务器加完会提示可能需要登录，用 codex mcp login <name>
2. 回调地址要注册 —— 把 codex mcp add 打印的完整回调 URL 登记到你的 OAuth 提供方
3. secret 不入库 —— oauth.client_secret 会写进 config.toml，确保该文件不进版本控制
4. 注册方式可指定 —— CIMD 与 DCR 二选一，默认自动；未绑定 issuer 的服务器会带回调 ID 后缀
5. 环境变量优先 —— bearer token 与 static header 都从环境变量取名，避免明文写进配置
```

## 工具审批与输出控制

MCP 工具和内置工具一样受审批约束，而且官方特别指出：**宣称有破坏性的工具总是需要审批**，即使它同时宣称了只读注解（只读注解优先级更高的情况除外）。控制手段有三层：服务器级的 `default_tools_approval_mode`、单工具的 `tools.<tool>.approval_mode`，以及沙箱/审批策略本身。`approval_mode` 的取值是 `auto`（自动）、`prompt`（每次问）、`writes`（对未标记只读的工具提问）、`approve`（批准）。输出侧的控制是 `tools.<tool>.output_token_limit`：给单个工具设 token 预算，避免它一次吐出海量内容把上下文撑爆——这是挂 MCP 服务器时最实际的调优点之一。

```toml
# ~/.codex/config.toml
[mcp_servers.chrome_devtools]
url = "http://localhost:3000/mcp"
default_tools_approval_mode = "prompt"     # 默认每个工具都问

[mcp_servers.chrome_devtools.tools.screenshot]
approval_mode = "approve"                  # 截图无害，直接放行
output_token_limit = 30000                 # 但限制单次输出预算

[mcp_servers.chrome_devtools.tools.navigate]
approval_mode = "prompt"                   # 导航到新站点要问
```

```text
审批与输出要点：
1. 破坏性工具必问 —— 宣称 destructive 的 MCP/app 工具一定触发审批，注解不能绕过
2. 三层粒度 —— 服务器默认、单工具覆盖、全局审批策略，从粗到细都能调
3. writes 模式很实用 —— 只对非只读工具提问，读操作照旧自动
4. 输出预算必设 —— 大输出工具会迅速吃满上下文，用 output_token_limit 兜住
5. 上下文有成本 —— 每个 MCP 服务器都会往消息里加内容，用不到的服务器就 enabled = false
```

## 自定义工具与脚本

「自定义工具」在 Codex 里有两条落地方式。第一条是**自己写 MCP 服务器**：任何能实现 MCP 协议的程序（本地脚本、内部服务）都能作为 STDIO 或 HTTP 服务器接进来，于是团队内部系统也能变成模型可调用的工具；如果服务器是给 Codex 用的，记得填好 `instructions` 字段，把跨工具的约束与速率限制说清楚，并把关键信息压在前 512 字符里。第二条是**技能里的脚本**：技能的 `scripts/` 目录放可执行代码，`reference/` 放文档，模型按需运行脚本而不是每次现写命令——需要确定性行为或依赖外部工具时优先用脚本而不是自然语言指令。

```text
my-skill/
|-- SKILL.md          必填：说明 + 元数据（name、description）
|-- scripts/          可选：可执行代码
|-- references/       可选：文档
|-- assets/           可选：模板与资源
`-- agents/
    `-- openai.yaml   可选：界面元数据、调用策略、依赖声明
```

```markdown
<!-- my-skill/SKILL.md -->
---
name: db-migration-check
description: 检查数据库迁移脚本的向后兼容性。当任务涉及 schema 变更、ALTER TABLE、或新增迁移文件时使用。不适用于纯查询优化。
---

## 步骤
1. 列出本次改动涉及的所有迁移文件
2. 对每个文件运行 `bash scripts/check_backcompat.sh <file>`
3. 汇总不兼容项，按影响面排序输出

## 输入 / 输出
- 输入：迁移文件路径列表
- 输出：不兼容项清单（文件、语句、原因、建议）
```

```yaml
# my-skill/agents/openai.yaml：界面与依赖声明
interface:
  display_name: "迁移兼容性检查"
  short_description: "检查 ALTER TABLE 的向后兼容性"
  brand_color: "#3B82F6"
  default_prompt: "检查本次改动的迁移脚本兼容性"

policy:
  allow_implicit_invocation: false    # 只允许显式调用，默认是 true

dependencies:
  tools:
    - type: "mcp"
      value: "openaiDeveloperDocs"
      description: "OpenAI Docs MCP server"
      transport: "streamable_http"
      url: "https://developers.openai.com/mcp"
```

```text
自定义扩展要点：
1. 自建 MCP 服务器 —— 内部系统变成工具；用 instructions 说明跨工具工作流与限制
2. 技能优先用说明而非脚本 —— 除非需要确定性行为或外部工具，否则指令比代码好维护
3. 脚本放 scripts/ —— 需要确定性时让模型调用脚本，避免每次现场生成命令
4. 声明依赖 —— 技能依赖某个 MCP 时写进 agents/openai.yaml，可被自动安装与接线
5. 一个技能只做一件事 —— 让 description 能精确匹配触发场景
```

## 技能预设与提示词

技能用**渐进式披露**省上下文：Codex 初始只持有每个技能的 name 与 description（外加文件路径），决定使用某个技能时才加载它的完整 `SKILL.md`。初始清单有预算上限——官方说明默认取模型上下文窗口的 2%，上下文窗口未知时取 8000 字符，可用 `skills.max_context_tokens` 调整（上限 10000 token）；技能太多时 Codex 会先缩短描述，更多时会从清单里省略部分技能并给出提示。调用方式有两种：显式（在 Codex CLI 或 IDE 扩展里用 `/skills` 或输入 `$` 提及技能，例如 `$skill-creator`、`$skill-installer linear`）与隐式（任务与 description 匹配时自动选中）。因此 description 的写法直接决定隐式匹配的准确度——把关键触发词前置，并写清**不适用**的边界。

本机实测：Codex 启动时会向模型注入一段技能清单，内容取自 `CODEX_HOME/skills`。真实输出（节选自 `codex debug prompt-input`）：

```text
<skills_instructions>
## Skills
A skill is a set of local instructions to follow that is stored in a `SKILL.md` file.
Below is the list of skills that can be used. Each entry includes a name, description,
and a short path that can be expanded into an absolute path using the skill roots table.
### Skill roots
- `r0` = `/root/.codex/skills/.system`
### Available skills
- imagegen: Generate or edit raster images when the task benefits from AI-created bitmap visuals...
  (file: r0/imagegen/SKILL.md)
- openai-docs: Use for Codex models/pricing, scheduled tasks, skills, settings, setup,
  troubleshooting, customization, automations, and self-knowledge... (file: r0/openai-docs/SKILL.md)
- skill-creator: Create or update a Codex skill with appropriately scoped instructions
  and any needed supporting resources. (file: r0/skill-creator/SKILL.md)
- skill-installer: Install Codex skills into $CODEX_HOME/skills from a curated list or
  a GitHub repo path... (file: r0/skill-installer/SKILL.md)
</skills_instructions>
```

技能的本地发现位置（官方表格）：

| 作用域 | 位置 | 用途 |
|---|---|---|
| REPO | `$CWD/.agents/skills` | 只与当前工作目录相关的技能（如某个微服务） |
| REPO | `$CWD/../.agents/skills` | 仓库内共享区域的技能 |
| REPO | `$REPO_ROOT/.agents/skills` | 全仓库通用技能 |
| USER | `$HOME/.agents/skills` | 个人技能，任何仓库可用 |
| ADMIN | `/etc/codex/skills` | 机器/容器级共享技能 |
| SYSTEM | 随 Codex 打包 | 官方内置技能（skill-creator、plan 等） |

```toml
# ~/.codex/config.toml：停用某个本地技能（不删除文件）
[[skills.config]]
path = "/path/to/skill/SKILL.md"
enabled = false

# 调整初始技能清单的预算（上限 10000 token）
# skills.max_context_tokens = 6000
```

```shell
# 创建技能：用内置创建器
#   在 Codex 里输入 $skill-creator
# 安装官方精选技能
#   $skill-installer linear
# 在 TUI 里浏览与提及技能
#   /skills

# 技能与 MCP 是互补的：技能定义流程，MCP 提供工具
# 需要分发时打包成 plugin（plugin 可含多个技能与 MCP 服务器配置）
```

```text
技能要点：
1. 渐进式披露 —— 初始只加载 name + description，选中后才读完整 SKILL.md
2. 清单有预算 —— 默认上下文窗口的 2%（未知时 8000 字符），可调到最多 10000 token
3. description 是触发器 —— 隐式调用完全依赖它，写清适用与不适用场景
4. 多看本地目录 —— 技能从 CWD 向上扫描 .agents/skills，加上用户与系统位置
5. 变更自动检测 —— Codex 能自动发现技能变化；没生效就重启
```

## 应用场景实战

### 场景一：给团队项目接一套「文档 + 错误监控 + 浏览器」的 MCP 组合

真实场景：日常既需要查最新库文档、又需要看线上报错、还要验证前端页面。目标是把三个 MCP 服务器一次配好，并控制好上下文与审批成本。

```shell
# 1. 三个服务器：文档、错误监控、浏览器

# 实际使用（在 TUI 里）

为什么这样组织：
1. 三个服务器各有职责 —— 文档查证、线上观测、界面验证，互相不重叠
2. 工具白名单 —— playwright 只放常用的四个工具，减少模型选择面与上下文占用
3. 审批分级 —— 截图直接放行，其余写操作按需提问
4. 输出预算 —— 截图类工具输出大，设 output_token_limit 防止一次吃满上下文
```

### 场景二：把团队的「发布前检查」封装成技能，并让它在 CI 里被显式调用

真实场景：每次发布前有一组固定动作（查迁移兼容性、查变更日志、查回滚脚本）。与其每次口述，不如写成一个技能，脚本放在 `scripts/` 里保证确定性。

```shell
# 目录结构
mkdir -p .agents/skills/release-precheck/scripts
```

```markdown
<!-- .agents/skills/release-precheck/SKILL.md -->
---
name: release-precheck
description: 发布前检查。当任务提到发布、上线、release、发版、回滚演练时使用。不适用于日常开发改动。
---

## 步骤
1. 运行 `bash scripts/list_migrations.sh` 列出本版本涉及的迁移文件
2. 对每个迁移文件运行 `bash scripts/check_backcompat.sh <file>`
3. 运行 `bash scripts/check_changelog.sh` 检查变更日志是否覆盖所有 feat/fix
4. 运行 `bash scripts/check_rollback.sh` 确认回滚脚本存在且可执行
5. 输出一份清单：每项 通过 / 不通过 / 需要人工确认，附证据命令与输出
```

```shell
# 让模型在发布前调用这个技能（显式调用，避免误触发）
codex "用 release-precheck 技能对本版本做一次发布前检查"

# 非交互场景（CI）里也走同一套技能
codex exec --sandbox read-only \
  "用 release-precheck 技能做发布前检查，输出 Markdown 清单" \
  -o precheck-report.md
```

```text
为什么这样组织：
1. 技能放仓库里 —— .agents/skills 随代码走，团队共享同一套流程
2. 脚本承担确定性 —— 检查逻辑写在 scripts/ 里，模型只负责调度与汇总
3. 显式调用 —— description 里写清边界，避免日常对话被误触发
4. 人机共用 —— 交互式与 codex exec 都能调同一个技能，CI 与本地结果一致
```

## 最佳实践与踩坑记录

### 最佳实践

1. 用不到就停用：`enabled = false` 而不是删掉配置，每个 MCP 服务器都在消耗上下文与额度。
2. 先设工具白名单再谈别的：`enabled_tools` 把模型的选择面收窄到真正需要的几个工具。
3. 大输出工具必设 `output_token_limit`：截图、日志类工具的默认输出能一次撑爆上下文。
4. 审批分级而不是一刀切：截图等只读工具 `approve`，写操作 `prompt`，破坏性工具保持提问。
5. 技能 description 写边界：写清「什么时候用」和「不适用于什么」，隐式匹配才可靠。
6. 需要确定性就写脚本：把检查逻辑放进技能 `scripts/`，而不是让模型每次现生成命令。

### 踩坑记录

```text
坑 1：加了 MCP 服务器，模型却完全不用它的工具
结论：配置成功、codex mcp list 也显示 enabled，但模型从不调用。
原因：服务器初始化失败（命令不存在、超时），或工具被 enabled_tools/disabled_tools 裁掉了。
解法：用 codex mcp get <name> 确认 transport 与命令；调大 startup_timeout_sec；先不加白名单验证工具是否可用。

坑 2：OAuth 服务器反复登录失败
结论：codex mcp login 打开授权页后回调失败。
原因：回调地址没有被正确注册到 OAuth 提供方；或本地回环端口被占用/不可达。
解法：把 codex mcp add 打印的完整回调 URL 注册到提供方；用 mcp_oauth_callback_port 固定一个可用端口；远端环境用 mcp_oauth_callback_url 配代理入口。

坑 3：挂了几十个技能后，模型反而不挑技能了
结论：技能越多，隐式触发越不准，甚至部分技能从清单里消失。
原因：初始技能清单有预算上限（约上下文窗口的 2%，未知时 8000 字符），超出会先缩短描述再省略技能。
解法：精简技能数量与描述；必要时调 skills.max_context_tokens（上限 10000）；对关键技能改成显式调用。

坑 4：MCP 服务器就绪但某次运行直接报错退出
结论：非交互运行（codex exec）一开始就失败，提示 MCP 服务器初始化出错。
原因：该服务器被设为 required = true，初始化失败时官方行为是直接报错退出，而不是跳过它继续。
解法：只有"缺了它这次任务就没意义"的服务器才设 required = true；其余保持可选，并调 mcp_optional_startup_grace_ms 控制等待时间。

坑 5：client_secret 被提交进了 Git
结论：config.toml 里的 oauth.client_secret 随仓库泄露。
原因：codex mcp add --oauth-client-secret 会把 secret 存进 config.toml；若该文件被纳入版本控制就泄露了。
解法：确保 CODEX_HOME（默认 ~/.codex）不在任何仓库内并被 .gitignore 覆盖；secret 从环境变量读入；发现泄露立即轮换。
```
