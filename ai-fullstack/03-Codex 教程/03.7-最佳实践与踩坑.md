## 概述

前六篇讲的是怎么用：安装、交互、上下文、权限、扩展、自动化。这一篇讲怎么**用好**——把散落在前面的经验收敛成五条主线：怎么描述与拆解任务、怎么审查 AI 产出的代码、怎么管住长任务、怎么控制成本、出了错怎么排查。核心判断只有一句：Codex 的质量上限由你给的任务质量决定，下限由你的审查与权限边界守住。任务描述决定它做对的事，审查决定错的事不会进主干，权限决定它搞不出不可逆的破坏。

```text
用好的五条主线：
1. 描述与拆解 —— 一句话一件事，能验证的才算完成
2. 审查 —— 每处改动都要有理由，测试是硬门槛
3. 长任务 —— 拆段、压缩上下文、必要时用子代理隔离噪声
4. 成本 —— 模型档位 + 上下文规模 + MCP 数量 是三个主要旋钮
5. 排查 —— 先看 /status 与 codex doctor，再按错误类型定位
```

## 任务描述与拆解方法

官方给的两条提示原则很直接：**Codex 能验证自己工作时产出更好**，所以在提示里带上复现步骤、验证方式、lint 与 pre-commit 检查；**Codex 处理拆小的任务更好**，因为小任务更容易测试、也更容易被你审查；不确定怎么拆就让 Codex 先给一个计划。落到实操，一个好任务的模板是「目标 + 范围 + 验收条件 + 不许做什么」。范围尤其重要——明确「只改哪些文件、不要重构无关代码」，能直接减少审查负担。

```text
一个好任务的四要素：
1. 目标 —— 要达成什么（可观察的结果，不是"优化一下"）
2. 范围 —— 改哪些文件/目录，哪些不许动
3. 验收 —— 用什么命令证明完成（测试、typecheck、lint）
4. 禁令 —— 明确禁止的动作（不改公共 API、不动迁移文件、不顺带重构）
```

对比一份模糊任务与一份可执行任务：

```text
差：帮我优化一下这个项目的性能，顺便把代码整理干净。
   问题：目标不可观测、范围无边界、验收缺失，"整理干净"会引来大规模无关改动。

好：
   目标：把 /api/orders 的 P95 延迟从 800ms 降到 300ms 以内。
   范围：只允许改 internal/order 与 internal/cache 下的文件。
   验收：跑 `go test ./internal/order/...` 全绿；
         跑 `make bench-order` 并贴出前后对比数据。
   禁令：不要改 HTTP 路由、不要改数据库 schema、不要重构无关文件。
```

```shell
# 不确定怎么拆时，先让它出计划（不改代码）
codex --sandbox read-only "为下面这个需求给出实施计划：把订单导出从同步改成异步。
                             计划要分成可独立验证的小步，每步写明涉及文件与验证命令。"

# 按小步执行，每步一提交
git checkout -b feat/async-order-export
codex "实现计划第 1 步：新增导出任务表与数据访问层。只改 internal/export 下的文件，
       完成后跑 go test ./internal/export/...。"
git add -A && git commit -m "feat: 导出任务表与数据访问层"

codex "实现计划第 2 步：把同步导出接口改为投递任务……"
```

```text
任务拆解要点：
1. 目标可观测 —— 用数字或明确状态描述完成，而不是形容词
2. 范围要写死 —— 指明允许改动的目录，并显式列出禁区
3. 验收写命令 —— 让"完成"可被一条命令证明
4. 先计划后执行 —— 不确定时先要一份分步计划，审查计划比审查代码便宜
5. 一步一提交 —— 每步结束提交一次，出问题能精确定位到某一步
```

## AI 产出代码的审查

审查 AI 代码与审查人类代码的原则相同，但重点不同：AI 更容易产生**看似合理但细节错**的代码——边界条件、错误处理、并发安全、以及「顺手改了不该改的地方」。所以审查要盯三件事：**diff 的范围**（有没有超出你授权的文件）、**测试是否真的验证了行为**（而不是断言了自己写的实现）、**失败路径**（异常、超时、空值、并发）。官方提供的工具是 `/review`：启动一个独立 reviewer 读你选定的 diff，输出有优先级的发现，且**不修改工作区**——零成本的第二双眼睛，提交前应该成为默认动作。

```shell
# 1. 先看范围：diff 有没有越界
git status
git diff --stat
git diff            # 逐处看，尤其关注"为什么改这里"

# 2. 用独立 reviewer 审（不动工作区）
#   在 TUI 里输入：/review
#   非交互场景：
codex review --uncommitted          # 审已暂存 + 未暂存 + 未跟踪
codex review --base main            # 审与基线分支的差异
codex review --commit <SHA>         # 审某个提交引入的改动

# 3. 验证测试是真的
npm test
npm run typecheck
```

实测 `codex review --help` 的真实参数（0.162.1）：

```text
$ codex review --help
Run a code review non-interactively

Arguments:
  [PROMPT]  Custom review instructions. If `-` is used, read from stdin

Options:
      --uncommitted   Review staged, unstaged, and untracked changes
      --base <BRANCH> Review changes against the given base branch
      --commit <SHA>  Review the changes introduced by a commit
      --title <TITLE> Optional commit title to display in the review summary
```

```text
审查要点：
1. 先看范围再看内容 —— diff --stat 一眼看出有没有越界改动，这比逐行读更快
2. /review 当默认动作 —— 独立 reviewer 不写工作区，提交前零成本跑一次
3. 测过才算完成 —— 要求每个修复都附可复现的验证命令，并自己跑一遍
4. 盯失败路径 —— 异常、超时、空值、并发是 AI 代码最容易出错的地方
5. 不看"看起来对" —— 断言与实现同源时测试等于没测，要检查断言是否绑定了行为
```

## 长任务与子代理管理

长任务的三个敌人是上下文污染、上下文膨胀、以及并发写冲突。官方的解法是**子代理（subagents）**：把探索、跑测试、读日志这类高噪声、可并行的工作交给子代理，只把摘要带回主线程，主线程继续聚焦需求与决策。官方建议从读多写少的任务开始并行（探索、测试、分诊、汇总），对并行写代码要保持谨慎——多个代理同时改文件会产生冲突并抬高协调成本。要触发子代理就**明确要求**：官方说明当前版本在用户直接要求、或适用的 AGENTS.md / 技能指令要求时才会委派。

本机实测的注入文字印证了这一点（取自 `codex debug prompt-input` 真实输出，节选）：

```text

fulfill the user's goals.

triggering a turn.

You can decide how much context you want to propagate to your sub-agents with the `fork_turns`
parameter.

- All agents use the same current working directory.

```

注意三个来自真实运行的约束：**共享文件系统与工作目录**（所以并行写会互相看见）、**默认并发槽位为 4（含主代理）**、以及**必须显式要求才委派**。另外官方说明子代理**继承当前的沙箱策略**，并且父回合的运行时覆盖（包括会话内用 `/permissions` 做的调整）会被重新施加到子代理上。

```toml
# ~/.codex/config.toml：多代理相关设置
[agents]
enabled = true
# 同时打开的代理线程上限（不含主线程）；不设则由 Codex 决定
# max_concurrent_threads_per_session = 3
# 子代理默认模型与推理档位（显式指定时以显式值为准）
# default_subagent_model = "gpt-5.4"
# default_subagent_reasoning_effort = "medium"
# 中断代理回合时是否记录一条模型可见的消息
# interrupt_message = true
```

```text
# 长任务的组织方式（在 TUI 里）
#   用子代理并行探索：分别调研 auth、billing、search 三个模块的现状，
#                     各自只回摘要，不要贴原始日志
#   用 /compact 压缩主线程上下文
#   用 /agent 切换查看某个子代理线程的工作
#   用 /status 看当前配置与剩余额度
```

```text
长任务管理要点：
1. 读多写少才并行 —— 探索/测试/分诊适合并行，并行改代码容易冲突
2. 只回摘要 —— 子代理的价值在于把噪声挡在主线程之外
3. 显式要求才委派 —— 不明确说，当前版本不会主动开子代理
4. 上下文要主动压 —— 主线程长了就 /compact，别等撞上限
5. 并发有上限 —— 默认 4 个活跃代理（含主代理），编排时按这个预算设计
```

## 成本与配额控制

Codex 的消耗由三个旋钮主导：**模型档位**（强模型与弱模型之间可能差出数十倍额度）、**上下文规模**（提示词、文件、历史、工具输出都算）、**挂载的扩展数量**（每个 MCP 服务器都会往消息里加内容）。官方给出的省额度建议正是围绕这三点：控制提示词大小、只提供相关文件、把输出规格写清（受众、格式、长度）、精简 AGENTS.md（用目录嵌套控制注入量）、**限制 MCP 服务器数量**（不用的就关掉）。另外有两个直接观测手段：会话内 `/status` 看剩余额度，事件流里的 `turn.completed.usage` 看每轮 token 消耗。加速档位要单独算账——Fast 按更高倍数消耗，只在真正需要速度时开。

```shell
# 会话内查看剩余额度与当前配置
#   /status

# 从 JSONL 事件流统计每轮消耗（自动化里做成本看板）
codex exec --json "审查这次改动" \
  | jq -r 'select(.type=="turn.completed") | .usage'

# 临时用便宜模型处理简单任务
codex -m gpt-5.4 "把这三个文件的 import 排序统一一下"

# 快速检查上下文档位
#   /fast status
```

```toml
# ~/.codex/config.toml：把"省"设成默认，把"贵"留给显式调用
model = "gpt-5.4"
model_reasoning_effort = "medium"

# 临时性的服务器用完就停用，避免每次都往消息里加内容
[mcp_servers.playwright]
command = "npx"
args = ["-y", "@playwright/mcp@latest"]
enabled = false          # 不用时不要让它参与每一轮

# 限制技能的初始清单预算，避免技能库把上下文吃掉
# skills.max_context_tokens = 4000
```

| 旋钮 | 便宜的档位 | 何时升级 |
|---|---|---|
| 模型 | 弱模型 / 小模型 | 跨文件推理、复杂重构、疑难 bug |
| 推理档位 | low / medium | 需要权衡多方案、安全审查、架构设计 |
| 上下文 | 只带相关文件 + @ 精确引用 | 确实需要全貌时 |
| MCP | 只留当前任务需要的（其余 enabled = false） | 任务本身依赖该外部系统 |
| 加速档 | 默认关 | 交互式等待成为瓶颈且任务价值高 |
| 会话长度 | 及时 /compact 或新开会话 | 需要保留长链路上下文时 |

```text
成本控制要点：
1. 三旋钮优先 —— 模型、上下文、MCP 数量，先调这三个再谈别的
2. 精确投喂 —— 用 @ 与 /ide 带具体文件，比让模型全仓库搜更快更省
3. 精简 AGENTS.md —— 它是每一轮都注入的，长度直接乘上轮数
4. 关掉不用的 MCP —— 每个服务器都会增加每轮消息体积
5. 用数据而不是感觉 —— /status 与 turn.completed.usage 是唯一的真实依据
```

## 常见报错与排查

排查的顺序建议固定：先 `codex doctor` 拿整体健康结论，再看会话内 `/status` 确认当前模型、沙箱、工作目录与额度，然后按错误文本归类到「认证 / 网络 / 沙箱 / 仓库 / 配置 / 扩展」六类。本机实测收集到的几条真实错误文本与官方给出的对应处置方式整理如下。

| 现象（真实文本或转述） | 根因 | 处置 |
|---|---|---|
| `Not inside a trusted directory and --skip-git-repo-check was not specified.` | 不在 Git 仓库或未受信任目录 | 在仓库内运行，或加 `--skip-git-repo-check` |
| `cannot create new.txt: Read-only file system` | 沙箱为 `read-only` | 改 `--sandbox workspace-write`，或把目录加入可写根 |
| `curl: (6) Could not resolve host` | 沙箱默认关闭网络 | 打开 `sandbox_workspace_write.network_access`，或走审批提权 |
| `{"type":"error","message":"Reconnecting... 2/5 (request timed out)"}` | 到 provider 的网络不通 | 检查代理/VPN/防火墙/DNS/自签 CA（`CODEX_CA_CERTIFICATE`） |
| `failed to refresh available models: request timed out` | 拉取模型列表失败（网络或凭据） | 先解决连通性；确认 `codex login status` |
| 无法开始任务，提示缺凭据 | 未登录 / 凭证失效 | `codex login`、`codex login --device-auth` 或 `printenv OPENAI_API_KEY \| codex login --with-api-key` |
| 配置字段报错 | 版本升级后配置含未知字段 | `--strict-config` 定位；删掉或迁移该字段 |
| 非交互运行起始即失败 | `required = true` 的 MCP 服务器初始化失败 | 该服务器设为可选，或修好它的启动命令/超时 |
| 子代理/多线程里动作失败 | 非交互流程无法产生新的审批 | 提前把动作纳入沙箱边界（`--add-dir`/`writable_roots`）或改用交互式 |

```shell
# 完整健康检查（推荐第一步）
codex doctor

# 认证状态
codex login status

# 当前会话配置与额度（TUI 内）
#   /status

# 配置字段严格校验
codex --strict-config "随便一个任务，用来看配置是否有未知字段"

# 指令链实际注入了什么（排查"规则不生效"）
codex debug prompt-input | head -c 2000

# 沙箱边界是否如你预期（实测而非猜）
codex sandbox cat README.md
codex sandbox sh -c 'echo x > /tmp/probe.txt'

# 真正看模型可用的模型目录
codex debug models | head -40
```

```text
排查要点：
1. 先 doctor 后细查 —— 一条命令就能区分认证、网络、安装三类问题
2. 按错误文本归类 —— 六类问题的处置方式完全不同，别对着沙箱问题去改代理
3. 用 sandbox 子命令实测边界 —— 不要猜沙箱允许什么，直接跑一条命令看
4. debug prompt-input 验证上下文 —— 规则/技能"不生效"时这是唯一可信证据
5. 记住版本差异 —— 命令、参数与默认值随版本变化，以本机 --help 为准
```

## 应用场景实战

### 场景一：给「修一个线上 bug」建立完整的可控流程

真实场景：线上报错，需要快速定位、修复、验证、上线。目标是在速度与可控之间取平衡——AI 加速定位与实现，但每一步都有可验证的边界。

```shell
# 0. 干净基线
cd ~/code/service
git status && git pull --ff-only
git rev-parse --short HEAD
git checkout -b fix/order-race

# 1. 只读定位（不改代码，先搞清楚）
codex --sandbox read-only "线上 500 的堆栈见 /tmp/stack.txt。
  定位抛出该异常的调用链，说明并发下为什么触发，给出最小修复方案与验证方式。
  只输出分析与方案，不要改任何文件。"

# 2. 执行修复（限定范围 + 明确验收）
codex --sandbox workspace-write "按上一步的方案修复，要求：
  1) 只改 internal/order 下的文件
  2) 先写一个能复现该竞态的测试（当前应失败）
  3) 再改实现让该测试通过
  4) 跑 go test -race ./internal/order/... 并贴出结果
  不要重构无关代码。"

# 3. 验证
go test -race ./internal/order/...     # 自己再跑一遍
git diff --stat                        # 范围是否越界
git diff                               # 逐处看理由

# 4. 独立审查（不写工作区）
codex review --base main

# 5. 提交
git add -A && git commit -m "fix: 修复订单状态并发竞争导致的 500"
```

```text
为什么这样组织：
1. 只读定位先行 —— 分析阶段不允许改文件，避免"边查边改"把 diff 搞乱
2. 先写复现测试 —— 测试先失败后通过，才证明修的是对的这个问题
3. 范围写死 —— 只允许改 internal/order，审查面立刻收窄
4. -race 是硬证据 —— 并发问题必须用竞态检测器验证，而不是看代码像对的
5. 独立审查兜底 —— /review 提供第二双眼睛，零额外风险（不写工作区）
```

### 场景二：一个下午的批量升级任务——用计划 + 分批 + 成本看板推进

真实场景：要把 40 个包的依赖主版本升级，逐个跑测试。任务长、消耗大、容易中途迷路。目标是用「计划 → 分批 → 成本与进度看板」把它变成可控的工程动作。

```shell
# 1. 先出计划（只读，几乎不花额度）
codex --sandbox read-only "分析 pnpm-workspace.yaml 下的所有包，
  为每个包列出依赖升级清单与风险等级（主版本跳跃 / 有破坏性变更）。输出一张表。"
```

```bash
# 2. 分批执行脚本：一批一个包，跑测试，记录成本与结果
set -uo pipefail
PKGS=$(pnpm -r list --depth -1 --json | jq -r '.[].name')
LOG="upgrade-progress.tsv"
printf 'pkg\tstatus\tinput_tokens\toutput_tokens\n' > "$LOG"

for p in $PKGS; do
  # 每个包一个独立会话，跑完即弃，避免上下文串味
  OUT=$(codex exec --ephemeral --sandbox workspace-write \
        --ask-for-approval never --json \
        "只处理包 $p：把它 package.json 里的依赖升到最新主版本，
         改完跑 pnpm --filter $p test。
         如果有破坏性变更导致测试失败，只做必要的最小修改。
         不要动其他包。" 2>/dev/null)

  OK=$(printf '%s\n' "$OUT" | jq -r 'select(.type=="turn.completed")' | wc -l)
  IN=$(printf '%s\n' "$OUT" | jq -r 'select(.type=="turn.completed") | .usage.input_tokens' | head -1)
  OUTT=$(printf '%s\n' "$OUT" | jq -r 'select(.type=="turn.completed") | .usage.output_tokens' | head -1)

  if [ "$OK" -gt 0 ] && pnpm --filter "$p" test >/dev/null 2>&1; then
    printf '%s\tok\t%s\t%s\n' "$p" "${IN:-0}" "${OUTT:-0}" >> "$LOG"
    git add -A && git commit -q -m "chore: 升级 $p 依赖"
  else
    printf '%s\tfailed\t%s\t%s\n' "$p" "${IN:-0}" "${OUTT:-0}" >> "$LOG"
    git checkout -- .        # 回滚这个包，稍后单独处理
  fi
done

echo "==== 结果 ===="
column -t "$LOG" | head -50
echo "失败清单："
grep -P '\tfailed\t' "$LOG" | cut -f1
echo "总输入 token：$(awk -F'\t' 'NR>1{s+=$3} END{print s+0}' "$LOG")"
echo "总输出 token：$(awk -F'\t' 'NR>1{s+=$4} END{print s+0}' "$LOG")"
```

```text
为什么这样组织：
1. 计划阶段极便宜 —— 只读分析几乎不消耗写权限风险，却决定了后面 40 步的路线
2. 一个包一个会话 —— --ephemeral 跑完即弃，避免上一个包的错误假设带到下一个
3. 失败即回滚 —— git checkout -- . 保证主干始终是绿的，失败包单独重试
4. 成本有账 —— 用 turn.completed.usage 累加，任务结束就知道这次花了多少
5. 进度可续 —— tsv 进度文件让中断后能接着跑，而不是从头再来
```

## 最佳实践与踩坑记录

### 最佳实践

1. 每轮任务都写清范围与验收：范围收窄审查面，验收让「完成」可被命令证明。
2. `/review` 作为提交前默认动作：独立 reviewer 不写工作区，成本极低而收益明确。
3. 一步一提交、一步一验证：出问题时能精确定位到某一步，而不是回退整个下午。
4. 长任务先要计划再动手：审查一份计划的成本远低于审查一批代码。
5. 用 `--ephemeral` 隔离批量任务的会话：避免前一个任务的不成立假设污染下一个。
6. 把成本当指标看：`/status` 与 `turn.completed.usage` 是唯一的真实依据，别凭感觉。

### 踩坑记录

```text
坑 1：任务描述太宽泛，结果拿到一个巨大的、无法审查的 diff
结论：只是想优化一个函数，最后 diff 里有 30 个文件、包含无关重构。
原因：提示词只说了"优化并整理干净"，没有限定范围与禁令。
解法：在提示里写死允许改动的目录、明确验收命令、列出一句"不要重构无关文件"。

坑 2：测试通过了，但线上还是同一个问题
结论：测试全绿，issue 依旧复现。
原因：测试断言与自己写的实现同源，等于只验证了"代码跑得通"，没验证行为正确。
解法：先写能复现问题的失败测试（红灯），再改实现让它转绿；并发问题用 -race 之类的检测器验证。

坑 3：长任务跑到一半开始"失忆"，前面确认过的约束不见了
结论：会话后半段把已经确定的接口写成了别的形状。
原因：上下文膨胀后触发压缩，冗长历史被摘要化，细节丢失；噪声也让模型更易出错。
解法：硬约束写进 AGENTS.md（每轮重新注入）；长任务拆段并及时 /compact；高噪声工作交给子代理，只回摘要。

坑 4：以为额度还很多，结果半天就撞限额
结论：任务中途触发限额，只能买 credits 或降级模型继续。
原因：消耗由模型档位、上下文规模、MCP 数量共同决定，凭"大概跑了几次"完全估不准。
解法：用 /status 与用量面板看真实消耗；简单任务换便宜模型；精简 AGENTS.md；不用的 MCP 设 enabled = false。

坑 5：排查方向错了，对着网络问题猛改沙箱设置
结论：花很久调沙箱配置，问题其实是到 provider 的网络不通。
原因：没先做整体诊断，看到"请求失败"就往权限上猜。
解法：先跑 codex doctor 拿到分类结论（认证 / 网络 / 安装），再按错误文本归类处置；沙箱边界用 codex sandbox 实测而不是猜。
```
