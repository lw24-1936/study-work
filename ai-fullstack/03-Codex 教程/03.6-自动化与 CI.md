## 概述

把 Codex 从「交互式助手」变成「流水线里的一步」，关键在 `codex exec`：它不打开 TUI，跑完就退出，进度打到 stderr、最终消息打到 stdout，因此可以直接重定向、可以管道传给别的工具、可以在 CI 里当构建步骤用。配合 `--json` 还能把整轮事件变成 JSONL 流，供程序消费；配合 `--output-schema` 能强制最终响应符合你给的 JSON Schema。本文讲清楚 `codex exec` 的用法、非交互环境下的权限设置、机器可读输出，以及两种真实落地：CI 中的自动化与批量重构。

```text
自动化四要素：
1. 入口 —— codex exec "任务"，不交互、跑完退出
2. 权限 —— 默认只读沙箱，要改代码必须显式 --sandbox workspace-write
3. 输出 —— 默认纯文本最终消息；--json 给 JSONL；--output-schema 约束结构
4. 凭证 —— 自动化用 API key（CODEX_API_KEY），不要用个人 ChatGPT 凭证
```

本文的 `codex exec` 参数取自本机 Codex CLI 0.162.1 的真实 `--help` 输出，运行示例的真实输出也一并贴出（本机无外网，模型调用未能完成，相关处已明确标注）。

## codex exec 非交互执行基础

`codex exec` 接受一个任务提示词作为参数；如果 stdin 是管道且同时给了提示词，Codex 把提示词当指令、把管道内容当补充上下文；如果省略提示词或用 `-`，则从 stdin 读整个提示词。默认它跑在**只读沙箱**里——这很重要，意味着不显式加权限它不会改任何文件。它还有几个自动化常用开关：`--ephemeral` 不把会话文件落盘，`--skip-git-repo-check` 允许在非 Git 目录运行，`--ignore-user-config` 不加载用户配置，`--ignore-rules` 跳过规则文件。

本机实测的真实输出：

```text
$ cd ~/nogit-demo && codex exec "列出当前目录文件"
Reading additional input from stdin...
Not inside a trusted directory and --skip-git-repo-check was not specified.
```

即：不在受信任目录里跑时，Codex 会直接拒绝并告诉你加 `--skip-git-repo-check`。

```
$ codex exec --help（节选，真实输出）
Usage: codex exec [OPTIONS] [PROMPT]
       codex exec [OPTIONS] <COMMAND> [ARGS]

Commands:
  resume  Resume a previous session by id or pick the most recent with --last
  fork    Fork a previous session by id into a new session
  review  Run a code review against the current repository

Arguments:
  [PROMPT]
          Initial instructions for the agent. If not provided as an argument (or if `-` is used),
          instructions are read from stdin. If stdin is piped and a prompt is also provided, stdin
          is appended as a `<stdin>` block

Options:
      --skip-git-repo-check   Allow running Codex outside a Git repository
      --ephemeral             Run without persisting session files to disk
      --ignore-user-config    Do not load `$CODEX_HOME/config.toml`; auth still uses `CODEX_HOME`
      --ignore-rules          Do not load user or project execpolicy `.rules` files
      --output-schema <FILE>  Path to a JSON Schema file describing the model's final response shape
      --json                  Print events to stdout as JSONL
  -o, --output-last-message <FILE>
                              Specifies file where the last message from the agent should be written
      --color <COLOR>         [default: auto] [possible values: always, never, auto]
```

```shell
# 最基本：一次非交互任务，最终消息打到 stdout
codex exec "总结仓库结构，列出 5 个高风险区域"

# 允许改代码（默认只读，不加这个不会改任何文件）
codex exec --sandbox workspace-write "把 print 语句换成 logging"

# 不落盘，适合一次性检查
codex exec --ephemeral "评估这个仓库的下一步"

# 读提示词文件（stdin 即完整提示词）
cat prompt.txt | codex exec -

# 在 Git 仓库外强制运行
codex exec --skip-git-repo-check "只看不写，列出目录结构"

# 两阶段流水线：先审查，再按结论修改
codex exec "review the change for race conditions"
codex exec resume --last "fix the race conditions you found"
```

```text
exec 基础要点：
1. 默认只读 —— 不加 --sandbox workspace-write 就不会改文件，这是安全默认
2. 出口分离 —— 进度走 stderr、最终消息走 stdout，管道里拿到的只有结论
3. stdin 两种语义 —— 有提示词时管道内容是补充上下文；用 - 时 stdin 就是提示词
4. 可恢复 —— exec 会话支持 resume 与 fork，适合多阶段流水线
5. Git 检查 —— 非 Git 目录需要 --skip-git-repo-check 显式放行
```

## 权限与安全边界

非交互环境没有人能点「批准」，所以必须提前把沙箱与审批设成「能自己跑完」的组合。官方给的建议是：按工作流需要给**最小**权限——只读检查就留默认 `read-only`；要改文件用 `--sandbox workspace-write`；只有在已经隔离好的环境（独立 CI runner 或容器）里才考虑 `--sandbox danger-full-access`。审批层面非交互场景通常配 `--ask-for-approval never`：不问人，越界动作直接失败并把错误还给模型。想保留一点判断力又不惊动人，可以用 `--approve-for-me`：把审批请求路由到自动审查，边界等同于 `workspace-write`。

需要留意的版本差异：早期文档里的 `codex exec --full-auto` 已不是推荐写法，官方不同页面对它的表述不一致（一处写「不再支持」，一处写「保留为兼容路径并打印警告」），**以你实际版本的 `codex exec --help` 为准**，新脚本统一写显式 `--sandbox`。

```shell
# 只读检查：零审批，安全
codex exec --sandbox read-only --ask-for-approval never \
  "审计依赖：列出存在已知严重漏洞的直接依赖"

# 允许改文件，且不打断流水线
codex exec --sandbox workspace-write --ask-for-approval never \
  "修复 lint 报错，只改报错行"

# 改文件但让自动审查把关越界动作
codex exec --sandbox workspace-write --approve-for-me \
  "升级依赖并修复由此产生的编译错误"

# 受控环境里放开全部（仅限隔离 runner/容器）
codex exec --sandbox danger-full-access --ask-for-approval never \
  "在容器内完成构建与测试"

# 干净的自动化环境：不读用户配置、不读规则
codex exec --ignore-user-config --ignore-rules \
  "总结这次提交的改动"

# 凭证：只作用于这一条命令
CODEX_API_KEY=<api-key> codex exec --json "triage open bug reports"
```

```toml
# ~/.codex/ci-readonly.config.toml：把 CI 用的一组权限固化成 profile
sandbox_mode = "read-only"
approval_policy = "never"
```

```text
权限边界要点：
1. 显式声明沙箱 —— 自动化脚本里永远写清 --sandbox，别依赖默认值随版本变化
2. never 不等于无边界 —— 它只是不问人，沙箱边界依旧生效
3. 最小权限 —— 只读任务就给 read-only；需要写才给 workspace-write
4. 自动审查做折中 —— --approve-for-me 用审查代理替代人工批准
5. 版本差异以 --help 为准 —— 尤其是 --full-auto 这类被废弃的旧写法
```

## 结构化输出与 JSONL 事件流

要让 Codex 的输出能被程序消费，有两条路。第一条是 `--json`：stdout 变成 JSON Lines 流，每一行是一个 JSON 对象，记录运行过程中的每个事件，事件类型包括 `thread.started`、`turn.started`、`turn.completed`、`turn.failed`、`item.*` 与 `error`；item 类型覆盖 agent 消息、推理、命令执行、文件改动、MCP 工具调用、网页搜索与计划更新。第二条是 `--output-schema`：给一个 JSON Schema 文件，要求最终响应符合该结构——适合需要稳定字段的下游流程（任务摘要、风险报告、发布元数据）。只想拿最终消息的话，用 `-o/--output-last-message <文件>`，它把最终消息写入文件（同时也仍打印到 stdout）。

本机实测的真实 JSONL 输出（设置了一个无效 API key，且本机无外网，因此模型调用未完成，但事件流结构是真实的）：

```text
$ CODEX_API_KEY=sk-invalid-for-doc-demo codex exec --json --skip-git-repo-check "说一句 ok"
Reading additional input from stdin...
2026-10-14T16:15:48.833861Z ERROR codex_models_manager::manager: failed to refresh available models: request timed out
{"type":"thread.started","thread_id":"01a13b32-bf72-7e62-b94d-67514bdd3af7"}
{"type":"turn.started"}
{"type":"error","message":"Reconnecting... 2/5 (request timed out)"}
```

官方文档给出的完整事件流样例（正常完成时）：

```text
{"type":"thread.started","thread_id":"0199a213-81c0-7800-8aa1-bbab2a035a53"}
{"type":"turn.started"}
{"type":"item.started","item":{"id":"item_1","type":"command_execution","command":"bash -lc ls","status":"in_progress"}}
{"type":"item.completed","item":{"id":"item_3","type":"agent_message","text":"Repo contains docs, sdk, and examples directories."}}
{"type":"turn.completed","usage":{"input_tokens":24763,"cached_input_tokens":24448,"output_tokens":122,"reasoning_output_tokens":0}}
```

注意 `turn.completed` 里的 `usage` 字段——它给出了这一轮的 token 消耗，是做成本统计的直接数据来源。

```shell
# JSONL 事件流，用 jq 过滤出最终 agent 消息
codex exec --json "总结仓库结构" | jq -r 'select(.type=="item.completed") | .item.text'

# 只要最终消息，写文件（同时仍打印到 stdout）
codex exec "生成发布说明" -o release-notes.md

# 统计 token 消耗
codex exec --json "审查这次改动" \
  | jq -r 'select(.type=="turn.completed") | .usage'
```

```json
// schema.json：要求最终响应符合这个结构
{
  "type": "object",
  "properties": {
    "project_name": { "type": "string" },
    "programming_languages": {
      "type": "array",
      "items": { "type": "string" }
    }
  },
  "required": ["project_name", "programming_languages"],
  "additionalProperties": false
}
```

```shell
# 按 schema 抽取结构化元数据
codex exec "Extract project metadata" \
  --output-schema ./schema.json \
  -o ./project-metadata.json

cat ./project-metadata.json
# {
#   "project_name": "Codex CLI",
#   "programming_languages": ["Rust", "TypeScript", "Shell"]
# }
```

```text
结构化输出要点：
1. --json 给事件流 —— stdout 是 JSONL，每行一个事件，适合程序消费
2. 关键事件 —— thread.started / turn.started / turn.completed / turn.failed / item.* / error
3. --output-schema 约束终态 —— 需要稳定字段就给 JSON Schema，避免解析自由文本
4. -o 拿最终消息 —— 同时写文件与 stdout，两处都能用
5. usage 可统计 —— turn.completed 事件里带 token 用量，可做成本看板
```

## 脚本与管道集成

Codex 的定位是「CLI 工作流里的一个环节」，所以最自然的用法是把别的命令的输出喂给它，再把它的输出喂给下一个命令。官方给的模式分两种：**提示词 + 管道内容**（你自己写指令，管道内容是待分析的素材，适合日志、测试输出、HTTP 详情）；**stdin 即提示词**（用 `codex exec -`，适合提示词由脚本动态生成，或提示词存在文件里）。把这个模式串起来，很多日常运维动作能变得很短。

```shell
# 让失败的测试告诉 Codex 该修什么
npm test 2>&1 | codex exec "总结失败用例，并给出最小可能的修复" | tee test-summary.md

# 日志分诊
tail -n 200 app.log \
  | codex exec "找出最可能的根因，引用关键错误，给出接下来三步排查建议" \
  > log-triage.md

# HTTP/TLS 问题分析
curl -vv https://api.example.com/health 2>&1 \
  | codex exec "解释这个 TLS 或 HTTP 失败，给出最可能的修复方式" \
  > tls-debug.md

# 提示词由脚本生成
generate_prompt.sh | codex exec - --json > result.jsonl

# 把 Codex 结论直接贴到 PR
gh run view 123456 --log \
  | codex exec "用 5 条要点总结这次失败，供 PR 讨论使用" \
  | gh pr comment 789 --body-file -

# 结构化数据 → 格式化输出
curl -s https://jsonplaceholder.typicode.com/comments \
  | codex exec "把前 20 条整理成 markdown 表格" \
  > table.md
```

```text
管道集成的要点：
1. 两种 stdin 语义 —— 有提示词时管道是素材；用 - 时 stdin 是完整提示词
2. tee 保底 —— 用 tee 既看结果又落盘，便于事后审计
3. 出口可接 gh —— 最终消息走 stdout，可直接喂给 gh pr comment 之类
4. 动态提示词 —— 提示词由脚本生成时用 codex exec -
5. 组合 --json 还能拿事件流 —— 需要过程信息时加 --json，需要结论时保持默认
```

## 在 GitHub Actions 里跑 Codex

GitHub Actions 场景下官方推荐直接用 **Codex GitHub Action**（`openai/codex-action@v1`），而不是自己在 shell 步骤里装 CLI 并传 API key——这个 action 会安装 Codex、启动一个 Responses API 代理来隔离你的 key，并按你指定的权限跑 `codex exec`。关键输入包括：`prompt` 或 `prompt-file`（二选一，提示词存放建议 ` .github/codex/prompts/`）、`codex-args`（额外 CLI 参数，JSON 数组或 shell 字符串）、`model` 与 `effort`、`sandbox`（`workspace-write` / `read-only` / `danger-full-access`）、`output-file`、`codex-version`（固定版本）、`codex-home`（复用配置与 MCP）。输出通过 `final-message` 提供。

权限方面有专门的输入：`safety-strategy` 默认 `drop-sudo`（运行前移除 sudo，对本次 job 不可逆，用于保护内存中的密钥；Windows 上必须设 `unsafe`）、`unprivileged-user` 配合 `codex-user` 以特定账号运行、`read-only`（不改文件、不用网络，但仍以高权限运行）、`allow-users` / `allow-bots` 限制谁能触发。

```yaml
# .github/workflows/codex-pr-review.yml
name: Codex pull request review
on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  codex:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    outputs:
      final_message: ${{ steps.run_codex.outputs.final-message }}
    steps:
      - uses: actions/checkout@v5
        with:
          ref: refs/pull/${{ github.event.pull_request.number }}/merge
          fetch-depth: 0
          persist-credentials: false

      - name: Run Codex
        id: run_codex
        uses: openai/codex-action@v1
        with:
          openai-api-key: ${{ secrets.OPENAI_API_KEY }}
          prompt-file: .github/codex/prompts/review.md
          output-file: codex-output.md
          sandbox: read-only            # 审查不需要写权限
          codex-version: "0.143.0"      # 固定版本保证可复现

  post_feedback:
    runs-on: ubuntu-latest
    needs: codex
    if: needs.codex.outputs.final_message != ''
    permissions:
      issues: write
      pull-requests: write
    steps:
      - name: Post Codex feedback
        uses: actions/github-script@v7
        with:
          github-token: ${{ github.token }}
          script: |
            await github.rest.issues.createComment({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.payload.pull_request.number,
              body: process.env.CODEX_FINAL_MESSAGE,
            });
        env:
          CODEX_FINAL_MESSAGE: ${{ needs.codex.outputs.final_message }}
```

```yaml
# .github/workflows/codex-autofix.yml —— CI 失败时自动生成补丁
name: Codex auto-fix on CI failure
on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]

jobs:
  generate_fix:
    if: ${{ github.event.workflow_run.conclusion == 'failure' }}
    runs-on: ubuntu-latest
    permissions:
      contents: read                 # 只读：这一步拿不到写权限
    outputs:
      has_patch: ${{ steps.diff.outputs.has_patch }}
    steps:
      - uses: actions/checkout@v5
        with:
          ref: ${{ github.event.workflow_run.head_sha }}
          fetch-depth: 0
          persist-credentials: false

      - uses: actions/setup-node@v4
        with:
          node-version: "20"

      - name: Install dependencies
        run: |
          if [ -f package-lock.json ]; then npm ci; fi

      - name: Run Codex
        uses: openai/codex-action@v1
        with:
          openai-api-key: ${{ secrets.OPENAI_API_KEY }}
          prompt: |
            CI workflow "${{ github.event.workflow_run.name }}" failed for commit
            ${{ github.event.workflow_run.head_sha }}.

            Run `npm test --silent` to reproduce. Identify the minimal change needed,
            implement only that change, then run `npm test --silent` again.

            Do not refactor unrelated files.

      - name: Create patch artifact
        id: diff
        run: |
          git add -N .
          git diff --binary HEAD > codex.patch
          if [ -s codex.patch ]; then
            echo "has_patch=true" >> "$GITHUB_OUTPUT"
          else
            echo "has_patch=false" >> "$GITHUB_OUTPUT"
          fi

      - uses: actions/upload-artifact@v4
        if: steps.diff.outputs.has_patch == 'true'
        with:
          name: codex-fix-patch
          path: codex.patch
          if-no-files-found: error

  open_pr:
    runs-on: ubuntu-latest
    needs: generate_fix
    if: needs.generate_fix.outputs.has_patch == 'true'
    permissions:
      contents: write
      pull-requests: write
    steps:
      - uses: actions/checkout@v5
        with:
          ref: ${{ github.event.workflow_run.head_sha }}
          fetch-depth: 0
      - uses: actions/download-artifact@v4
        with:
          name: codex-fix-patch
      - name: Apply patch and open PR
        env:
          GH_TOKEN: ${{ github.token }}
          FAILED_HEAD_BRANCH: ${{ github.event.workflow_run.head_branch }}
          RUN_ID: ${{ github.event.workflow_run.run_id }}
        run: |
          git apply --index codex.patch
          branch="codex/auto-fix-$RUN_ID"
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git switch -c "$branch"
          git commit -m "Auto-fix failing CI via Codex"
          git push origin "$branch"
          gh pr create --base "$FAILED_HEAD_BRANCH" --head "$branch" \
            --title "Auto-fix failing CI via Codex" \
            --body "Codex generated this patch after CI failed. Review before merging."
```

关键安全约束（官方明确警告）：**不要在会 checkout 或运行仓库内代码的 workflow 里，把 `OPENAI_API_KEY` / `CODEX_API_KEY` 设成 job 级环境变量**——构建脚本、测试、依赖生命周期钩子或被攻陷的 action 都能读到它。上面第二个示例的做法是：生成补丁的 job 只读、拿不到写权限；开 PR 的 job 有写权限但没有 API key。

```text
CI 集成要点：
1. 优先用官方 Action —— openai/codex-action@v1 用代理隔离 API key，不用自己装 CLI
2. key 只给必需步骤 —— 不要把 key 设成 job 级环境变量，尤其是会跑仓库代码的 job
3. 权限最小化 —— 生成补丁的 job 用 contents: read，开 PR 的 job 才给 write
4. 限制触发者 —— 用 allow-users / allow-bots 控制谁能对仓库跑 Codex
5. 固定版本 —— codex-version 锁定 CLI，避免 runner 上行为漂移
```

## 批量重构场景

批量重构是 `codex exec` 最实用的场景之一：仓库里成百上千个文件要做同一类机械修改，人工做又慢又容易漏。可行做法有两种：**让 Codex 自己在一次 exec 里遍历并批量改**（适合规则明确、文件不多、可由模型自行判断边界的情况）；或者**用 shell 循环逐个文件调 exec**（适合改动可枚举、需要精确控制与可重试的情况），后者更容易做失败重试与进度记录。无论哪种，都应该：先跑一次只读试点、用小样本验证规则、每批结束跑测试、改动走 Git 便于整体回滚。

```shell
# 方案 A：一次性批量任务（先试点，再放开）
# 试点：只读，看它会怎么改
codex exec --sandbox read-only \
  "列出所有仍在使用 moment.js 的文件，以及每个文件需要改动的行"

# 确认规则后执行
codex exec --sandbox workspace-write --ask-for-approval never \
  "把所有 import moment from 'moment' 改为 import dayjs from 'dayjs'，
   并把常用 API 做等价替换（moment() -> dayjs()，.format() 保持），
   不要动非 JS/TS 文件。每改 10 个文件停下来汇报一次。"

# 验证
git diff --stat
npm test
```

```bash
#!/usr/bin/env bash
# 方案 B：逐文件循环 + 失败重试 + 进度记录（适合大仓库、需要精确控制）
set -uo pipefail

PATTERN="${1:-src/**/*.js}"
LOG="refactor-progress.tsv"
: > "$LOG"     # 清空进度文件

while IFS= read -r f; do
  printf '%s\t' "$f" >> "$LOG"
  if codex exec --sandbox workspace-write --ask-for-approval never \
       --ephemeral \
       "只修改这一个文件：$f。把它从 CommonJS 改成 ESM：
        把 require(...) 改为 import，module.exports 改为 export。
        不要改其他文件，不要重构逻辑。" \
       >/dev/null 2>&1
  then
    echo "ok" >> "$LOG"
  else
    echo "failed" >> "$LOG"     # 记录失败，便于稍后单独重跑
  fi
done < <(find . -path ./node_modules -prune -o -name '*.js' -print | head -50)

echo "==== 失败清单 ===="
grep -P '\tfailed$' "$LOG" || echo "（无失败）"
```

```shell
# 每批结束都跑一次测试，不要攒到最后
npm test --silent || { echo "本批引入回归，停止"; exit 1; }

# 用 git 分批提交，便于二分定位
git add -A && git commit -m "refactor: 迁移到 ESM（批次 1）"

# 让 Codex 做一致性总检
codex exec --sandbox read-only \
  "检查仓库里是否还有 require( 或 module.exports 残留，列出文件与行号"
```

```text
批量重构要点：
1. 先只读试点 —— 用 read-only 让模型先列出改动清单，确认规则与你预期一致
2. 限定文件范围 —— 在提示词里明确"只改这一个文件"，避免一次 exec 改出预期外的改动
3. --ephemeral 省磁盘 —— 批量场景不需要保留每条会话
4. 记录进度与失败 —— 逐文件循环时把结果写进度文件，失败可单独重跑
5. 分批验证 —— 每批结束跑测试并提交，问题能定位到具体批次
```

## 应用场景实战

### 场景一：为 PR 自动生成结构化审查报告并回帖

真实场景：团队要求每个 PR 都有审查意见，但人力有限。目标是把审查做成流水线的一步：Codex 只读审查、输出结构化结果、另一个 job 负责回帖（有写权限但没有 API key）。

```yaml
# .github/workflows/pr-review.yml
name: PR review with Codex
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    outputs:
      final_message: ${{ steps.codex.outputs.final-message }}
    steps:
      - uses: actions/checkout@v5
        with:
          ref: refs/pull/${{ github.event.pull_request.number }}/merge
          fetch-depth: 0
          persist-credentials: false

      - name: Run Codex review
        id: codex
        uses: openai/codex-action@v1
        with:
          openai-api-key: ${{ secrets.OPENAI_API_KEY }}
          sandbox: read-only
          codex-version: "0.143.0"
          prompt: |
            审查这次 PR 的 diff。输出 Markdown，分三节：
            ## 阻断问题（必须修）
            ## 建议改进
            ## 已确认良好
            每条注明 文件:行号 与理由。不要评论风格偏好。只输出报告。
          output-file: review.md

      - uses: actions/upload-artifact@v4
        with:
          name: codex-review
          path: review.md

  comment:
    runs-on: ubuntu-latest
    needs: review
    if: needs.review.outputs.final_message != ''
    permissions:
      pull-requests: write
    steps:
      - name: Post review comment
        uses: actions/github-script@v7
        with:
          github-token: ${{ github.token }}
          script: |
            await github.rest.issues.createComment({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.payload.pull_request.number,
              body: process.env.BODY,
            });
        env:
          BODY: ${{ needs.review.outputs.final_message }}
```

```shell
# 本地先用同一条提示词试跑，确认输出格式稳定
codex exec --sandbox read-only \
  "审查当前未提交的改动。输出 Markdown，分三节：阻断问题 / 建议改进 / 已确认良好，每条注明 文件:行号 与理由。" \
  -o local-review.md
head -30 local-review.md
```

```text
为什么这样组织：
1. 只读审查 —— 审查任务不需要写权限，sandbox: read-only 把风险降到最低
2. 两段式回帖 —— 审查 job 有 API key 但无写权限；回帖 job 有写权限但无 key
3. 固定输出格式 —— 提示词里规定三节结构，下游评论可读性稳定
4. 本地先验证 —— 同一条提示词先在本地跑，避免 CI 里反复试错烧额度
```

### 场景二：定时任务里跑「依赖与安全巡检」，结果落成结构化报告

真实场景：每周一早上跑一次巡检，检查依赖漏洞、过期的锁定文件、以及新增的 TODO/FIXME 是否被跟踪。要求结果机器可读，能直接进工单系统。

```shell
# 1. 准备输出 schema
cat > /tmp/audit-schema.json <<'JSON'
{
  "type": "object",
  "properties": {
    "week": { "type": "string" },
    "critical": { "type": "integer" },
    "findings": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "kind": { "type": "string" },
          "path": { "type": "string" },
          "detail": { "type": "string" },
          "severity": { "type": "string" }
        },
        "required": ["kind", "path", "detail", "severity"]
      }
    }
  },
  "required": ["week", "critical", "findings"],
  "additionalProperties": false
}
JSON

# 2. 只读巡检，输出结构化 JSON
cd /srv/app
codex exec --sandbox read-only --ask-for-approval never \
  --output-schema /tmp/audit-schema.json \
  -o /srv/reports/audit-$(date +%Y%W).json \
  "对当前仓库做一次巡检：
   1) 检查 package.json 的直接依赖是否存在已知严重漏洞（可用 npm audit --json 的数据）
   2) 检查锁定文件是否与 package.json 一致
   3) 找出本周新增的 TODO/FIXME 注释
   输出符合给定 schema 的 JSON，week 用 ISO 周号，critical 为阻断性问题数量。"
```

```bash
# 3. 定时任务（crontab 条目：每周一 08:00）
# 0 8 * * 1 cd /srv/app && CODEX_API_KEY_FILE=/etc/codex-bot.key bash /srv/scripts/audit.sh >> /var/log/codex-audit.log 2>&1
```

```bash
#!/usr/bin/env bash
# /srv/scripts/audit.sh —— 巡检脚本，独立 CODEX_HOME 与 API key，不碰人工环境
set -euo pipefail

export CODEX_HOME=/srv/codex-bot
export CODEX_API_KEY="$(cat "${CODEX_API_KEY_FILE:-/etc/codex-bot.key}")"

WEEK="$(date +%Y%W)"
OUT="/srv/reports/audit-${WEEK}.json"
mkdir -p /srv/reports

codex exec --sandbox read-only --ask-for-approval never \
  --ignore-user-config \
  --output-schema /srv/schemas/audit.json \
  -o "$OUT" \
  "对当前仓库做一次依赖与安全巡检，输出符合 schema 的 JSON"

# 4. 质量门：critical 大于 0 就退出非零，让调度器报警
CRITICAL="$(python3 -c "import json,sys; print(json.load(open('$OUT'))['critical'])")"
if [ "$CRITICAL" -gt 0 ]; then
  echo "发现 $CRITICAL 个阻断性问题，报告：$OUT"
  exit 2
fi
echo "巡检通过（$OUT）"
```

```text
为什么这样组织：
1. 结构化落盘 —— --output-schema + -o 让报告字段稳定，工单系统可直接吃
2. 独立 CODEX_HOME —— 自动化用自己的凭证与会话，与人工使用完全隔离
3. --ignore-user-config —— 不受人工环境的配置变化影响，CI 行为可复现
4. 退出码做门禁 —— critical > 0 返回非零，调度器据此报警
5. 只读 + never —— 巡检不需要写权限，也不需要人批准
```

## 最佳实践与踩坑记录

### 最佳实践

1. 自动化脚本里永远显式写 `--sandbox`：别依赖默认值，版本升级可能改变默认。
2. 非交互环境配 `--ask-for-approval never`：没有人能批准，越界必然失败，不如提前设好边界。
3. 需要机器读就用 `--json` 或 `--output-schema`：解析自由文本是长期维护成本的来源。
4. 用 `turn.completed` 的 usage 做成本统计：这是官方事件流里现成的 token 消耗数据。
5. CI 里 key 只给需要它的那一步：会跑仓库代码的 job 尤其不能有 job 级 key。
6. 批量操作先只读试点再放开：先用 `read-only` 让它列出改动计划，确认规则后再给写权限。

### 踩坑记录

```text
坑 1：CI 里 codex exec 跑了但什么都没改
结论：流水线绿色通过，但仓库没有任何改动。
原因：codex exec 默认是 read-only 沙箱，不给写权限它就只能看。
解法：显式加 --sandbox workspace-write（或在 codex-action 里设 sandbox: workspace-write）。

坑 2：在非 Git 目录（或未受信任目录）里 exec 直接失败
结论：报 "Not inside a trusted directory and --skip-git-repo-check was not specified."
原因：Codex 要求命令在 Git 仓库内运行，防止不可控的破坏性改动。
解法：在仓库内运行；确知环境安全时加 --skip-git-repo-check。

坑 3：在同一 job 里既 checkout 仓库代码又把 API key 设成环境变量
结论：构建脚本或依赖的生命周期钩子可以读到 key，等于把密钥交给仓库内的代码。
原因：job 级环境变量对所有步骤可见，而仓库内代码是不可信输入。
解法：用 openai/codex-action（它启动代理隔离 key）；或把 key 只放进执行 Codex 的那一步；绝不在会跑仓库代码的 job 里设 job 级 key。

坑 4：把 --json 的输出直接当纯文本用
结论：下游脚本解析失败或拿到一堆 JSON 噪声。
原因：--json 下 stdout 是 JSONL 事件流，不再是最终消息文本。
解法：用 jq 过滤事件类型（如 select(.type=="item.completed") 取消息）；只要最终消息就不加 --json，用 -o 写文件。

坑 5：沿用旧脚本里的 codex exec --full-auto
结论：行为与预期不符，或打印弃用警告。
原因：--full-auto 已不是推荐写法，官方不同页面对它的表述不一致（不再支持 / 兼容路径打印警告）。
解法：改为显式 --sandbox workspace-write；需要审批折中就用 --approve-for-me。以本机 codex exec --help 为准。
```
