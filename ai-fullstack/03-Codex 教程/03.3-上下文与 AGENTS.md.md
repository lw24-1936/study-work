## 概述

Codex 每次开始干活前会先读两类东西：**指令**（AGENTS.md 构成的指令链）与**配置**（config.toml 构成的多层配置栈）。前者告诉模型「这个仓库的规矩是什么」，后者决定「运行时的参数是什么」。除此之外还有第三条线：会话历史与上下文窗口管理——聊得太长要压缩，跨会话要有记忆，这些状态都落在 `CODEX_HOME` 目录下。本文把这三条线讲清楚，重点在 AGENTS.md 的发现层级与规则的写法，因为这是投入产出比最高的一环。

```text
上下文与规则的三个层次：
1. 指令层 —— AGENTS.md / AGENTS.override.md 构成的指令链，每次运行开始时读取
2. 配置层 —— config.toml 多层叠加（系统/用户/profile/项目/命令行），决定运行参数
3. 状态层 —— 会话、历史、记忆、日志存在 CODEX_HOME 下，决定能否恢复与复用
```

本文的 AGENTS.md 层级结论已在本机实测验证（Codex CLI 0.162.1），实测方法与真实输出见下文。

## AGENTS.md 的作用与发现层级

AGENTS.md 是「给智能体看的 README」：把构建命令、测试命令、代码约定、审查期望写进去，模型在动任何代码之前就会读到。官方推荐的定位是**保持精炼**——写每次都必须遵守的规矩，而不是把整个 wiki 塞进去。发现机制是两层：**全局层**在 Codex home 目录（默认 `~/.codex`，可用 `CODEX_HOME` 改）先看 `AGENTS.override.md`，没有才看 `AGENTS.md`，只取第一个非空文件；**项目层**从项目根（通常是 Git 根）一路走到当前工作目录，每个目录里按 `AGENTS.override.md` → `AGENTS.md` → 配置里声明的备用文件名的顺序取**至多一个**，再按根到叶的顺序用空行拼接。空文件跳过，累计体积达到 `project_doc_max_bytes` 上限（默认 32 KiB）就停止追加。

```text
AGENTS.md 层级规则：
1. 全局在前 —— ~/.codex（或 CODEX_HOME）里放个人通用规矩，形状同项目文件
2. override 优先 —— 同目录下 AGENTS.override.md 压过 AGENTS.md，只取其中一个
3. 沿路径累积 —— 从仓库根到当前目录逐层收集，每目录至多一个文件
4. 拼接顺序 —— 根到叶，用空行连接成一条指令链
5. 有上限 —— 合计 32 KiB（project_doc_max_bytes 默认值）后截断，空文件跳过
```

本机实测：在 `ag-demo2/` 放 `AGENTS.md`，在 `ag-demo2/services/payments/` 放 `AGENTS.override.md`，用 `codex debug prompt-input`（该命令把「模型可见的提示输入」渲染成 JSON）查看实际注入的指令链。

从仓库根运行时，只加载根层文件：

```text

<INSTRUCTIONS>

- 改 JS 后必须跑 npm test

```

进入嵌套目录运行，两层文件被按根到叶顺序拼接：

```text
$ cd ~/ag-demo2/services/payments && codex debug prompt-input | (抽取 AGENTS 段，真实输出)

- 改 JS 后必须跑 npm test

```

## 编写项目规则

规则的质量决定模型的默认行为。官方给的方向很集中：先只写真正重要的（构建、测试、审查期望、约定），把反复出现的 review 意见沉淀进去，把规则放在**最贴近适用范围的那个目录**里。用 `AGENTS.md` 全局文件塑造「模型怎么跟你沟通」（回复风格、详略、默认做法），用仓库根文件约束「团队与代码库的规矩」，用子目录文件描述「这个模块的特殊规矩」。写完之后要形成一个反馈闭环：模型做错了就纠正它，并让它把纠正写回 AGENTS.md，下一次会话才会继承这个修正。

```markdown
# AGENTS.md（仓库根，示例）

## 构建与测试
- 安装依赖：`pnpm install`
- 跑测试：`pnpm test`（改动 JavaScript 后必须跑）
- 类型检查：`pnpm typecheck`

## 代码约定
- TypeScript strict 模式，禁止 `any`
- 提交信息遵循 Conventional Commits（feat/fix/docs/refactor）
- 新增生产依赖需要先确认

## 审查期望
- 改动必须附带测试或说明为什么不需要
- 不要顺手重构与任务无关的文件
```

```markdown
# services/payments/AGENTS.override.md（子目录，覆盖上层同名文件）

## payments 服务规则
- 本目录测试用 `make test-payments`，不要用 `pnpm test`
- 密钥轮换必须先在安全频道通知，禁止在 PR 里改
- 所有金额计算必须使用 decimal 类型，禁止浮点
```

```toml
# ~/.codex/config.toml：允许团队用已有文件名，或放宽体积上限
project_doc_fallback_filenames = ["TEAM_GUIDE.md", ".agents.md"]
project_doc_max_bytes = 65536
```

```text
规则编写要点：
1. 先少后多 —— 只写真正每次都要遵守的，规则越长模型越容易忽略重点
2. 就近放置 —— 规则放在最贴近适用范围的目录，用子目录文件而不是在根文件里堆 if
3. override 用于偏离 —— 子目录要与上层相反的规定，用 AGENTS.override.md 显式覆盖
4. 沉淀 review 意见 —— 反复纠正的同一件事，让它写回 AGENTS.md，形成闭环
5. 分工明确 —— 全局文件管"怎么跟你沟通"，仓库文件管"这个项目的技术规矩"
```

## 指令链与配置的优先级

配置与指令是两套独立的解析规则，容易混淆。**指令链**的优先级由上节所述：全局（override 优先）→ 项目层从根到叶累积（不是覆盖，是拼接，同目录内 override 优先）。**配置栈**则是真正的覆盖关系，官方给出的顺序（高到低）是：命令行参数与 `--config` 覆盖 → 项目级 `.codex/config.toml`（从项目根到当前目录，越近越优先，且仅在项目被信任时加载）→ `--profile` 指定的 profile 文件（`~/.codex/<name>.config.toml`）→ 用户配置 `~/.codex/config.toml` → 系统配置（Unix 上是 `/etc/codex/config.toml`）→ 内置默认值。项目被标记为不受信任时，整个项目级 `.codex/` 层（项目配置、hooks、规则）都被跳过，用户与系统层照常加载。

| 层级 | 位置 | 说明 |
|---|---|---|
| 命令行 | `--model`、`-c key=value` | 单次运行最高优先级 |
| 项目配置 | `<repo>/.codex/config.toml` | 根到当前目录，越近越优先；仅受信任项目 |
| Profile | `~/.codex/<name>.config.toml` | 用 `--profile <name>` 选择 |
| 用户配置 | `~/.codex/config.toml` | 个人默认值，最常改的一层 |
| 系统配置 | `/etc/codex/config.toml`（Unix） | 机器级默认 |
| 内置默认 | 随版本 | 兜底 |

```toml
# ~/.codex/config.toml：把某个项目标记为不受信任，项目级配置与规则全部跳过
[projects."/path/to/untrusted-repo"]
trust_level = "untrusted"
```

```shell
# 命令行覆盖：优先级最高，值按 TOML 解析
codex -c model='"gpt-5.4"' "只改这一处"
codex -c sandbox_workspace_write.network_access=true "需要联网装依赖，我批准"
codex -c 'shell_environment_policy.include_only=["PATH","HOME"]' "收紧环境变量"

# 用 profile 选择一组预置配置
codex --profile deep-review
```

```text
优先级要点：
1. 指令是拼接 —— AGENTS.md 是"累积"，不是覆盖；只有同目录内的 override 才是覆盖关系
2. 配置是覆盖 —— config.toml 各层是逐层覆盖，越靠前优先级越高
3. 项目层要受信任 —— 不受信任的项目，项目级 .codex/（配置/hooks/规则）全部不加载
4. 部分键不接受项目覆盖 —— provider、auth、通知、telemetry 等键在项目级会被忽略
5. 命令行最硬 —— 临时用 -c 或专门的 flag 覆盖，不必改文件
```

## 上下文窗口与自动压缩

上下文窗口是硬约束：会话越长，注入的历史、工具输出、文件内容越多，很快会撞到上限，且模型在噪声中更容易犯错（官方称之为 context pollution 与 context rot）。Codex 的对策是**压缩（compaction）**——把可见对话摘要化，保留关键结论、丢掉冗长的中间输出。你可以显式触发（会话内 `/compact`），配置里可以用 `compact_prompt` 覆盖默认的压缩提示词；官方还提到没有显式配置时也存在自动压缩路径。压缩不是免费的：摘要会丢细节，所以关键约束（接口签名、决策理由）最好显式写进 AGENTS.md 或会话内的简短重申里，而不是指望压缩后仍被记住。

```shell
# 会话内手动压缩（上下文接近上限时）
#   /compact

# 相关：清空 UI 与对话（与压缩不同，这是全新开始）
#   /clear

# 查看剩余上下文与当前配置
#   /status
```

```toml
# ~/.codex/config.toml：自定义压缩提示词
# compact_prompt = "保留：任务目标、已确认的决策、未完成的 TODO、文件路径与接口签名。"

# 压缩后仍要保留的硬约束，写进仓库指令更可靠
# （AGENTS.md 每次运行都会重新注入，不受会话压缩影响）
```

```text
上下文管理要点：
1. 压缩会丢细节 —— 摘要保留结论，不保留逐条过程，关键约束要另行固化
2. AGENTS.md 不受压缩影响 —— 它是每次运行开始时重新注入的，信噪比最高
3. 主动压缩优于硬顶 —— 上下文快满时 /compact，比让模型在噪声里硬写更稳
4. 子代理隔离噪声 —— 把探索、跑测试、读日志这类高噪声工作交给子代理（见 03.5）
5. 长任务分段 —— 把大任务拆成几步，每步结束压一次或新开会话（见 03.7）
```

## 历史 会话与记忆管理

Codex 的本地状态全部落在 `CODEX_HOME`（默认 `~/.codex`）下。本机实测该目录的实际内容（Codex CLI 0.162.1 首次运行后）：

```text
$ ls -1 ~/.codex
goals_1.sqlite
goals_1.sqlite-shm
goals_1.sqlite-wal
installation_id
logs_2.sqlite
logs_2.sqlite-shm
logs_2.sqlite-wal
memories_1.sqlite
memories_1.sqlite-shm
memories_1.sqlite-wal
queue_1.sqlite
queue_1.sqlite-shm
queue_1.sqlite-wal
.sandbox_migration
sessions/
shell_snapshots/
skills/
```

几个稳定的概念：**会话（sessions）** 是每次运行的记录，可 resume/fork/archive/delete；**历史（history）** 在启用历史持久化时写入 `history.jsonl`；**记忆（memories）** 是官方「Customization」里的一层，让 Codex 复用此前工作中得到的上下文（具体行为与开关随版本演进，以官方文档为准）；**技能（skills）** 在 `skills/` 下，是本地可发现的技能目录。日志与诊断在 `logs_*.sqlite`，`codex doctor` 也会读这些状态做健康检查。

```shell
# 会话：列出、恢复、归档
ls -1 "${CODEX_HOME:-$HOME/.codex}/sessions"
codex resume --all
codex archive <SESSION_ID>

# 配置与状态位置说明（官方列举的常见文件）
#   config.toml   —— 本地配置
#   auth.json     —— 使用文件式凭证存储时的登录凭证（等同密码）
#   history.jsonl —— 启用历史持久化时的历史记录

# 用独立 CODEX_HOME 做项目隔离或隔离的自动化用户
CODEX_HOME="$(pwd)/.codex" codex exec "List active instruction sources"
```

```text
历史与状态要点：
1. 一切在 CODEX_HOME —— 会话、日志、记忆、技能都在这个目录下，换目录即换"人格"
2. 会话可管理 —— resume 恢复、fork 分叉、archive 归档、delete 删除
3. auth.json 是密码 —— 文件式凭证含 access token，不要提交也不要外传
4. 记忆是独立一层 —— 官方把 Memories 列为与 AGENTS.md、Skills、MCP 并列的定制层
5. 备份即迁移 —— 复制 CODEX_HOME 就能把会话与配置带到另一台机器
```

## 多项目与全局配置

跨项目工作的痛点有两个：不同项目需要不同的默认值（模型、权限、审查强度），以及不希望项目之间的配置互相污染。Codex 给的三个工具刚好对应：**profile 文件**解决「同一台机器上多套参数」，`--profile <name>` 选择，加载顺序在基础用户配置之上、项目与命令行之下；**项目级 `.codex/config.toml`** 解决「这个仓库需要特殊设置」，但要项目受信任才生效；**`CODEX_HOME` 环境变量**解决更彻底的隔离——不同目录、不同自动化身份各用一套配置与会话，互不可见。注意 profile 的写法有版本差异：官方明确 0.134.0 起 `--profile` 不再读取 `config.toml` 里的 `[profiles.<name>]` 表，profile 必须是独立的 `~/.codex/<name>.config.toml` 文件（顶层键，不要嵌套）。

```shell
mkdir -p ~/.codex

cat > ~/.codex/quick-fix.config.toml <<'EOF'
# 小修小补：便宜模型、低推理、自动跑
model = "gpt-5.4"
model_reasoning_effort = "low"
approval_policy = "on-request"
EOF

cat > ~/.codex/deep-review.config.toml <<'EOF'
# 深度审查：强模型、高推理、逐条审批
model = "gpt-5.5"
model_reasoning_effort = "xhigh"
approval_policy = "on-request"
EOF

codex --profile quick-fix "改掉这个拼写错误"
codex --profile deep-review "对这三个文件做安全审查"
```

```toml
# <repo>/.codex/config.toml —— 项目级设置（仅受信任项目生效）
# 注意：provider、auth、通知、telemetry 这类键在项目级会被忽略，必须放在用户级
approval_policy = "on-request"

[sandbox_workspace_write]
# 这个仓库的测试需要写入构建缓存目录
writable_roots = ["/tmp/build-cache"]
```

```shell
# 彻底隔离：为某个自动化环境使用独立的 CODEX_HOME
export CODEX_HOME=/srv/codex-bot
codex login --device-auth
codex exec "检查这个仓库的依赖是否有已知问题"

# 一次性隔离（不污染当前 shell）
CODEX_HOME="$(pwd)/.codex" codex "在这个项目的独立配置下工作"
```

```text
多项目与全局配置要点：
1. profile 是文件 —— ~/.codex/<name>.config.toml，顶层键，用 --profile 选择
2. 版本差异要留意 —— 0.134.0 起不再支持 config.toml 里的 [profiles.<name>] 与顶层 profile= 选择器
3. 项目配置需信任 —— 不受信任的项目，项目级 .codex/config.toml 不加载
4. 键有作用域 —— provider/auth/通知/telemetry 类键只能在用户级配置
5. CODEX_HOME 是终极隔离 —— 配置、会话、记忆、技能整套切换
```

## 应用场景实战

### 场景一：给一个中型 monorepo 建立分层 AGENTS.md 体系

真实场景：仓库里有多个服务，统一的构建与提交规范，但每个服务的测试命令与领域约束不同。目标是让 Codex 在不同目录下自动遵守对应规矩。

```shell
# 目录结构
tree -L 2 -a -I node_modules
# .
# |-- AGENTS.md
# |-- package.json
# `-- services
#     |-- payments
#     |   |-- AGENTS.override.md
#     |   `-- Makefile
#     `-- search
#         `-- AGENTS.md
```

```markdown
# ./AGENTS.md —— 全仓库通用（会被任何子目录继承）
## 构建与测试
- 安装：`pnpm install`
- 全量测试：`pnpm -r test`
- 提交信息：Conventional Commits

## 通用约定
- TypeScript strict，禁止 any
- 不要重构与任务无关的文件
```

```markdown
# ./services/payments/AGENTS.override.md —— 覆盖本目录继承到的规则
## payments 规则
- 本目录测试用 `make test-payments`（不要用 pnpm test）
- 金额一律用 decimal，禁止浮点
- 不得在 PR 中轮换密钥
```

```markdown
# ./services/search/AGENTS.md —— 本目录的补充规则
## search 规则
- 索引进度相关代码改动必须跑 `pnpm test --filter search:index`
- 查询性能回归用 `pnpm bench:search` 验证
```

```shell
# 验证：在 payments 目录下看实际注入了什么
cd services/payments
codex debug prompt-input > /tmp/prompt.json
python3 - <<'PYEOF'
import json
d = json.load(open("/tmp/prompt.json"))
s = json.dumps(d, ensure_ascii=False)
i = s.find("AGENTS.md instructions")
print(s[i:i+600])
PYEOF
```

```text
为什么这样组织：
1. 通用规矩只写一次 —— 构建、提交规范放在根文件，所有子目录自动继承
2. 特例就近声明 —— 服务专属的测试命令与领域约束写在服务目录里
3. 要压过上层用 override —— payments 的测试命令与根规则冲突，用 AGENTS.override.md
4. 可验证 —— debug prompt-input 能直接看到模型最终读到的指令链，不用猜
```

### 场景二：用 profile 与独立 CODEX_HOME 把「开发」和「自动化机器人」彻底分开

真实场景：一台开发机上既有人工交互式使用，也有一个定时运行的自动化任务。自动化任务的配置、凭证与会话都不应影响人工使用。

```shell
# ---- 人工侧：三个 profile ----
mkdir -p ~/.codex

cat > ~/.codex/quick.config.toml <<'EOF'
model = "gpt-5.4"
model_reasoning_effort = "low"
approval_policy = "on-request"
EOF

cat > ~/.codex/deep.config.toml <<'EOF'
model = "gpt-5.5"
model_reasoning_effort = "xhigh"
approval_policy = "on-request"
EOF

cat > ~/.codex/ci-readonly.config.toml <<'EOF'
# CI 用：只读沙箱、零审批、干净配置
sandbox_mode = "read-only"
approval_policy = "never"
EOF

# 人工日常
codex --profile quick "帮我看看这个报错"
codex --profile deep "审查这次 release 的改动"

# ---- 自动化侧：独立 CODEX_HOME + CI profile ----
export CODEX_HOME=/srv/codex-bot
mkdir -p "$CODEX_HOME"

# 用 API key 登录（自动化推荐路径）
printenv OPENAI_API_KEY | codex login --with-api-key

# 非交互、只读、零审批跑一次检查
CODEX_HOME=/srv/codex-bot \
  codex --profile ci-readonly exec --json \
  "检查 package.json 中是否存在有严重漏洞的直接依赖" \
  > /srv/codex-bot/reports/deps.jsonl

# 两边的会话与配置互不可见
ls -1 /srv/codex-bot/sessions
ls -1 ~/.codex/sessions
```

```text
为什么这样组织：
1. profile 管参数差异 —— 便宜/昂贵、只读/可写，切一行参数即可
2. CODEX_HOME 管身份隔离 —— 自动化用自己的凭证与会话，登录/登出互不影响
3. 自动化用 API key —— 不依赖浏览器，符合官方"自动化默认用 API key"的建议
4. 配置可提交审阅 —— profile 文件是纯文本，可进 Git 走 review
```

## 最佳实践与踩坑记录

### 最佳实践

1. AGENTS.md 先求精炼再求全面：只写每次都必须遵守的规矩，长度本身就是成本。
2. 用 `codex debug prompt-input` 验证指令链：不要猜模型读到了什么，直接看注入内容。
3. 把纠正沉淀成规则：模型做错就纠正，并让它把纠正写回最贴近的 AGENTS.md。
4. 关键约束不要只靠上下文：接口签名、硬性禁令写进 AGENTS.md，它不受会话压缩影响。
5. profile 用独立文件：写成 `~/.codex/<name>.config.toml`，别依赖已废弃的 `[profiles.<name>]` 表。
6. 自动化一律独立 CODEX_HOME：凭证、会话、配置与人工使用完全隔离。

### 踩坑记录

```text
坑 1：AGENTS.md 写了却"没生效"
结论：模型的行为完全没变，像是根本没读规则。
原因：文件放错层级——不在从项目根到当前工作目录的路径上；或名字不在识别范围内。
解法：把规则放在根到 cwd 的路径上；非标准文件名要加进 project_doc_fallback_filenames；用 codex debug prompt-input 确认真实注入内容。

坑 2：规则越写越长，模型反而更不听话
结论：AGENTS.md 涨到几百行后，模型开始漏掉关键约束。
原因：指令链有体积上限（project_doc_max_bytes 默认 32 KiB），且越长越容易被忽略。
解法：精简根文件，把服务专属规则下沉到子目录文件；必要时再调高上限，但优先做减法。

坑 3：项目级 .codex/config.toml 完全不生效
结论：在仓库里放了项目配置，改动毫无效果。
原因：Codex 只在项目被信任时加载项目级 .codex/ 层；该项目被判为不受信任时整层跳过。
解法：确认项目信任状态；不要把 provider/auth/telemetry 类键放进项目配置（项目级会被忽略，必须放用户级）。

坑 4：升级后 --profile 报错或读到旧设置
结论：原本能用的 profile 突然失效。
原因：0.134.0 起 --profile 不再读取 config.toml 里的 [profiles.<name>]，顶层 profile= 选择器也不支持了。
解法：把配置搬进 ~/.codex/<name>.config.toml（顶层键），并删掉 config.toml 里旧的 [profiles.<name>] 表与 profile= 行。

坑 5：长会话后模型"忘了"之前说好的约束
结论：会话前半段确认过的接口签名，后半段被写成了别的样子。
原因：上下文压缩把冗长历史摘要化，细节丢失；噪声也让模型更容易犯错。
解法：把硬约束写进 AGENTS.md（每轮重新注入）或会话中简短重申；长任务拆段，及时 /compact 或新开会话。
```
