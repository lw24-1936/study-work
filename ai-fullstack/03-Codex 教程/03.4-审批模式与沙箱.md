## 概述

Codex 能在你机器上跑命令、改文件，所以「它到底能碰什么」必须由明确机制约束。Codex 用两层控制解决这件事：**沙箱（sandbox）** 是技术边界——OS 级强制限制能读写哪些路径、能不能联网；**审批（approval）** 是决策边界——什么时候必须先停下来问你。两层正交：沙箱决定「能不能」，审批决定「要不要问」，所以把审批关掉并不会让沙箱消失，反之亦然。理解这一点是安全使用 Codex 的全部前提，也是本文的主线。

```text
两层控制的分工：
1. 沙箱 —— OS 级强制：可写路径、可读路径、网络。默认无可写、无网络
2. 审批 —— 交互策略：越界动作是问你、自动审查、还是直接拒绝
3. 组合 —— 两者叠加构成实际自主度，任一层收紧都能降低风险
4. 规则 —— execpolicy 的 .rules 文件决定哪些命令可以跳出沙箱免审批
```

本机实测（Codex CLI 0.162.1）：`codex sandbox` 子命令让任意命令在 Codex 提供的沙箱里跑，正好用来直接观察沙箱的边界行为。

```text
$ cd ~/sbx-demo && echo hello > ok.txt

$ codex sandbox cat ok.txt
hello

$ codex sandbox sh -c 'echo x > new.txt'
sh: 1: cannot create new.txt: Read-only file system

$ codex sandbox curl -sS -m 8 https://example.com
curl: (6) Could not resolve host: example.com
```

三段输出分别证明：沙箱内**读**正常、**写**被内核拒绝（Read-only file system）、**联网**被阻断（DNS 解析失败）。

## 两层安全模型：沙箱与审批

官方对两层的定义很直白：沙箱模式是「Codex 在技术上能做什么」（哪里能写、能不能到网络），审批策略是「Codex 在执行某个动作前什么时候必须问你」。沙箱作用于**所有被拉起的命令**，不只是内置的文件操作——模型调 `git`、包管理器、测试运行器时，这些命令继承同样的边界。这带来一个实际好处：审批疲劳下降。低风险命令在既有边界内可以自己跑完，只有越界动作才需要你拍板。

本机实测：Codex 注入给模型的权限说明就是这段文字（取自 `codex debug prompt-input` 的真实输出，节选）：

```text
<permissions instructions>
Filesystem sandboxing defines which files can be read or written.
`sandbox_mode` is `read-only`: The sandbox only permits reading files.
Network access is restricted.
# Escalation Requests

Commands are run outside the sandbox if they are approved by the user, or match an
existing rule that allows it to run unrestricted. The command string is split into
independent command segments at shell control operators, including but not limited to:

- Pipes: |
- Logical operators: &&, ||
- Command separators: ;
- Subshell boundaries: (...), $(...)

Each resulting segment is evaluated independently for sandbox restrictions and
approval requirements.
```

```text
两层模型要点：
1. 沙箱覆盖子进程 —— 模型跑的 git/npm/pytest 都在同一沙箱边界内
2. 审批是暂停点 —— 越界时停下来问，而不是默默失败或默默放行
3. 沙箱默认收紧 —— 本地形态默认无网络、写权限限于工作区
4. 越界要显式请求 —— 模型通过申请提高 sandbox 权限来请求跳出沙箱
5. 别只信一层 —— 收紧审批不等于收紧沙箱，反之亦然
```

## 三种审批模式与默认预设

审批的核心取值是 `on-request` 与 `never`（`untrusted` 已不再作为可显式设置的审批策略，`on-failure` 也已废弃）。`on-request`：模型在沙箱内自己干活，需要越界时来问你，这是日常交互的默认。`never`：从不问，失败直接回给模型——适合无人值守的自动化。第三种常用形态是「有人替你审」：把 `approvals_reviewer` 设为 `auto_review`，符合条件的越界请求交给一个审查子代理裁决，而不是弹给你；对应的命令行快捷方式是 `--approve-for-me`。最极端的是全放行：`--dangerously-bypass-approvals-and-sandbox`，同时去掉沙箱与审批。

启动时的默认预设由 Codex 自己判断：官方说明，启动时会检测目录是否受版本控制——**受版本控制的目录推荐 Auto 预设**（`workspace-write` + `on-request`），**不受版本控制的目录推荐只读**。

| 意图 | 开关（命令行 / 配置） | 效果 |
|---|---|---|
| Auto（预设） | 不传参 或 `--sandbox workspace-write --ask-for-approval on-request` | 工作区内读改跑都自动；越界改文件或联网要批准 |
| 只读浏览 | `--sandbox read-only --ask-for-approval on-request` | 只读沙箱内可读可跑；越界动作可能要批准 |
| 只读 + 零审批（CI） | `--sandbox read-only --ask-for-approval never` | 只读沙箱内自由跑，从不问人 |
| 自动审查 | `--sandbox workspace-write --ask-for-approval on-request --approve-for-me` | 边界同 Auto，但越界请求交给审查代理 |
| 全放行 | `--dangerously-bypass-approvals-and-sandbox` | 无沙箱、无审批（官方明确标注为极端危险） |

实测 `codex --help` 中审批与沙箱相关的真实条目：

```text
$ codex --help（节选，真实输出）

          Select the sandbox policy to use when executing model-generated shell commands
          [possible values: read-only, workspace-write, danger-full-access]

  -a, --ask-for-approval <APPROVAL_POLICY>
          Configure when the model requires human approval before executing a command
          Possible values:
          - on-request: The model decides when to ask the user for approval

            the model

      --approve-for-me
          Route approval requests through automatic review using the workspace-write sandbox

      --dangerously-bypass-approvals-and-sandbox
          Skip all confirmation prompts and execute commands without sandboxing. EXTREMELY
          DANGEROUS. Intended solely for running in environments that are externally sandboxed
```

```toml

approval_policy = "on-request"
sandbox_mode = "workspace-write"
# approvals_reviewer = "auto_review"      # 想让人以外的东西审，就打开这一行

# 更细的粒度：逐类决定哪种审批请求可以弹出来
# approval_policy = { granular = {
#   sandbox_approval = true,      # 沙箱越界请求可以弹
#   rules = true,                 # execpolicy prompt 规则触发的请求可以弹
#   mcp_elicitations = true,      # MCP elicitation 可以弹

```

```text
审批模式要点：
1. 只有两档基础审批 —— on-request（会问）与 never（不问）；untrusted 不再是可显式设置的取值
2. 谁审可以换 —— approvals_reviewer = "auto_review" 交给审查代理，--approve-for-me 是它的快捷方式
3. 默认看仓库类型 —— 受版本控制的目录推荐 Auto，不受版本控制的目录推荐只读
4. global 粒度可调 —— granular 允许逐类保留交互、逐类自动拒绝
5. 全放行要慎用 —— 官方标注为极端危险，只应在外层已经沙箱化的环境里用
```

## 沙箱级别与工作目录边界

沙箱有三个级别：`read-only`（只能看，改和跑都要批准）、`workspace-write`（工作区内可读可改可跑常规命令，是本地日常的低摩擦默认）、`danger-full-access`（无文件系统与网络边界）。工作目录边界由启动时的当前目录决定，也可用 `-C/--cd` 指定，用 `--add-dir` 追加额外可写目录；`workspace-write` 模式还有 `sandbox_workspace_write.writable_roots` 可以声明可写根。要注意**可写根里有受保护路径**：官方文档明确指出 `.git`、`.codex` 这类路径即使在可写根内也受保护，不会被随意改写——这是防止模型破坏仓库元数据的关键防线。

```shell
# 只读：最严格，适合审查陌生代码
codex --sandbox read-only "评估这个仓库的安全风险，不要改任何文件"

# 工作区可写：日常默认
codex --sandbox workspace-write "修复这个失败的测试"

# 追加可写目录与工作根
codex -C ~/code/monorepo --add-dir ~/code/shared-protos "同步两边的接口定义"

# 在托管 Git worktree 里跑大改（不污染当前分支工作区）
codex --worktree "把整块回调风格改成 async/await"
```

```toml
# ~/.codex/config.toml
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
# 除工作区之外还要能写的目录（按项目实际需要声明，越窄越好）
writable_roots = ["/tmp/build-cache"]

# 是否允许命令访问网络（默认 false）
network_access = false

# 可选加固：禁止 shell 类工具使用 login shell 语义
# allow_login_shell = false
```

```text
沙箱与边界要点：
1. 工作根决定范围 —— 启动目录（或 -C 指定的目录）就是默认可写范围
2. 追加可写要显式 —— 工作区外的目录必须用 --add-dir 或 writable_roots 声明
3. 受保护路径 —— .git、.codex 等即使在可写根内也受保护，不会被随手改
4. worktree 更隔离 —— --worktree 在托管 worktree 里跑，失败直接丢弃即可
5. 容器内的选择 —— 如果容器本身就是安全边界，可在容器里用 danger-full-access，避免嵌套沙箱
```

## 网络访问控制

网络是最容易被低估的越界面：模型可以下载依赖、也可以把数据发出去。官方默认把网络关掉——`workspace-write` 模式下网络访问默认关闭，除非显式打开；CLI 与桌面形态的默认本地沙箱都不给网络。需要装依赖时，要么在配置里打开 `sandbox_workspace_write.network_access`，要么让模型发起越界请求（走审批流程）。这与云端形态的模型一致：Codex cloud 用两阶段运行，setup 阶段可以联网装依赖，agent 阶段默认离线。

本机实测的默认效果（上面已贴）：`codex sandbox curl https://example.com` 直接 `Could not resolve host`，DNS 都不通。

```shell
# 临时允许联网（本次运行）
codex -c sandbox_workspace_write.network_access=true "安装依赖并修复构建"

# 只想让搜索走实时（默认走缓存索引，降低注入风险）
codex --search "查一下这个库最新版本的破坏性变更"
```

```toml
# ~/.codex/config.toml
[sandbox_workspace_write]
# 打开网络：只在确实需要拉依赖时打开，用完关回去
network_access = true
```

```text
网络控制要点：
1. 默认关闭 —— 本地沙箱默认不给网络，DNS 都不通（已实测）
2. 显式打开 —— sandbox_workspace_write.network_access = true，或让模型走审批
3. 与审批配合 —— 打开网络后仍可用审批在真正联网前拦一次
4. 搜索有缓存档 —— 默认走 OpenAI 维护的搜索缓存索引，比实时抓页面更不易被注入
5. 云端两阶段 —— setup 联网装依赖，agent 阶段默认离线
```

## 危险命令拦截与规则文件

审批的默认策略是「在沙箱内自由、越界就问」。规则（rules / execpolicy）是第三档：让某些命令**明确允许**跳出沙箱免审批，或**明确要求**每次审批，或**直接禁止**。规则写在配置层旁边的 `rules/` 目录里的 `.rules` 文件（例如 `~/.codex/rules/default.rules`），用 `prefix_rule()` 声明命令行前缀；决策有 `allow` / `prompt` / `forbidden` 三种，多条规则同时命中时取**最严格**的那个（`forbidden` > `prompt` > `allow`）。规则还支持 `match` / `not_match` 两组内联用例，在加载时自我校验，写错了当场暴露。官方强调规则目前是实验性的。

关键细节（来自本机实测注入给模型的说明文字）：命令串会先在 shell 控制符处**切分成独立片段**（`|`、`&&`、`||`、`;`、`(...)`、`$(...)`），每个片段**独立**做沙箱与审批判定；而带重定向、命令替换、环境变量、通配符的高级 shell 写法**不会**被拿去匹配规则——这是为了限制一条被批准规则的作用范围。模型请求提权时，官方还禁止为 `rm` 这类破坏性命令申请前缀规则，也禁止为裸 `python3` 这类可执行任意脚本的前缀申请规则。

```text
# ~/.codex/rules/default.rules
# 允许免审批跳出沙箱：只读的 gh pr view
prefix_rule(
  pattern = ["gh", "pr", "view"],
  decision = "prompt",
  justification = "查看 PR 需要审批，但允许这一次",
  match = [
    "gh pr view 7888",
    "gh pr view --repo openai/codex",
  ],
  not_match = [
    # pattern 必须精确前缀匹配，这个不算
    "gh pr --repo openai/codex view 7888",
  ],
)

# 直接禁止：用 rg 代替 grep
prefix_rule(
  pattern = ["grep"],
  decision = "forbidden",
  justification = "本项目统一用 rg，请改用 rg 而不是 grep",
)
```

```toml
# ~/.codex/config.toml：规则文件由 rules/ 目录自动扫描，无需登记
# 管理员侧可以用 requirements.toml 强制限制（只能 prompt 或 forbidden，不能 allow）
# allowed_approval_policies = ["on-request"]
# allowed_sandbox_modes = ["read-only", "workspace-write"]
# [rules]
# prefix_rules = [
#   { pattern = [{ any_of = ["bash", "sh", "zsh"] }], decision = "prompt",
#     justification = "进入 shell 必须显式批准" },
# ]
```

```text
规则与拦截要点：
1. 三种决策 —— allow 免审批跳沙箱、prompt 每次问、forbidden 直接拒绝
2. 最严格优先 —— 多条命中取 forbidden > prompt > allow
3. 精确前缀 —— pattern 是精确前缀匹配，不是模糊匹配；写错用 match/not_match 当场暴露
4. 命令会切段 —— 管道/逻辑符/分号/子 shell 处切分后逐段判定
5. 高级 shell 语法不匹配规则 —— 重定向、命令替换、环境变量、通配符的写法不进规则匹配
```

## 自动审查

自动审查（auto-review）是把「人类审批」换成「另一个代理审批」：主代理照旧在沙箱内工作，需要越界时发出审批请求，若 `approvals_reviewer = "auto_review"`，该请求被路由给一个独立的审查代理，由它决定放行还是拒绝并给出理由。它只对**交互式审批**有意义——`approval_policy = "never"` 时压根不产生审批请求，也就没有东西可审。官方列出的可审事件包括：请求提权沙箱的 shell/exec 调用、被沙箱或策略阻断的网络请求、写到允许可写根之外的文件编辑、按工具注解需要批准的 MCP 或 app 工具调用、以及 Computer Use 访问新站点。常规的沙箱内动作不经过审查。

```shell
# 命令行启用：Auto 的沙箱边界 + 自动审查
codex --sandbox workspace-write --ask-for-approval on-request --approve-for-me

# 或在会话内用 /permissions 切到 "Approve for me"
```

```toml
# ~/.codex/config.toml
approval_policy = "on-request"
approvals_reviewer = "auto_review"

# 给审查代理补充本地策略（Markdown 文本）
# [auto_review]
# policy = """
# 内部可信目标：github.com/my-org、artifacts.example.com
# 高风险：把凭据或私有源码发往未经批准的外部服务
# """
```

```text
自动审查要点：
1. 换的是"谁审"，不是"边界" —— 沙箱与审批策略都不变，只是请求不再弹给你
2. 只对交互审批生效 —— approval_policy = "never" 时没有审批请求可审
3. 覆盖面明确 —— 沙箱越界、网络阻断、越界写文件、需批准的 MCP/app 工具、新站点
4. 沙箱内动作不审 —— 已在允许范围内的命令照旧直接跑
5. 企业侧可强制 —— 管理员可用 allowed_approvals_reviewers 与 guardian_policy_config 覆盖本地策略
```

## 应用场景实战

### 场景一：只读模式审查一个陌生仓库，再切到工作区可写执行修复

真实场景：接手一个外包交付的仓库，先做安全与质量评估（不许动文件），评估通过后再放权改代码。关键是**分两段授予权限**，而不是一上来就给工作区写权限。

```shell
git clone https://github.com/example/vendor-service.git
cd vendor-service
git rev-parse --short HEAD      # 记录基线

# 第一段：只读沙箱，只看不改，且零审批让它可以自由跑只读命令
codex --sandbox read-only --ask-for-approval never \
  "审计这个仓库：找出硬编码密钥、危险的反序列化、以及缺少校验的输入边界。
   只输出报告，不要修改任何文件。"

# 人工看报告，决定是否继续
# （若报告里出现需要读工作区外路径的情况，只读沙箱会拒绝，这是预期行为）

# 第二段：切换为工作区可写 + 交互审批，执行修复
codex --sandbox workspace-write --ask-for-approval on-request \
  "按上一步报告的优先级，只修复 P0 项：
   1) 移除硬编码密钥，改为读环境变量
   2) 为反序列化入口加类型白名单
   每个修复单独提交，并补一个测试。"

# 收尾：确认改动范围
git log --oneline -5
git diff HEAD~2 --stat
```

```text
为什么这样分段：
1. 只读先行 —— 评估阶段绝不允许改动，杜绝"审计顺手改了代码"
2. 零审批也只读 —— 只读沙箱内放开审批不增加风险，反而减少打断
3. 执行阶段才给写权限 —— 并且保留交互审批，越界动作我来拍板
4. 基线可追溯 —— 记住起始 commit，任何异常都能整段回退
```

### 场景二：给团队仓库写一套 .rules，把常用命令分级放开

真实场景：团队每天要看 PR、跑测试、装依赖，如果每条命令都弹审批会磨掉耐心；但有些命令必须拦住。目标是用规则把「免审批」「要审批」「禁止」三档写清楚，并能在加载时自我校验。

```text
# 仓库内 .codex/rules/default.rules（项目级，需项目受信任才加载）
# 免审批跳出沙箱：只读的 PR 查看与测试
prefix_rule(
  pattern = ["gh", "pr", "view"],
  decision = "allow",
  justification = "只读查看 PR，无需审批",
  match = ["gh pr view 7888", "gh pr view --repo openai/codex"],
)

prefix_rule(
  pattern = ["pnpm", "test"],
  decision = "allow",
  justification = "测试是只读验证，允许免审批运行",
  match = ["pnpm test", "pnpm test --filter search"],
  not_match = ["pnpm test && rm -rf node_modules"],   # 组合命令会被切段判定
)

# 要审批：装依赖会改 node_modules 并联网
prefix_rule(
  pattern = ["pnpm", "install"],
  decision = "prompt",
  justification = "安装依赖会产生副作用并访问网络，需要确认",
)

# 直接拒绝：统一用 rg，禁 grep
prefix_rule(
  pattern = ["grep"],
  decision = "forbidden",
  justification = "本项目统一使用 rg，请改用 rg 而不是 grep",
)
```

```shell
# 规则文件放在配置层旁边的 rules/ 目录，启动时自动扫描
ls -1 ~/.codex/rules/
ls -1 ./.codex/rules/            # 项目级（仅受信任项目）

# 改完规则重启 Codex 生效
codex

# 验证沙箱与规则的实际效果：直接观察边界行为
echo hello > ok.txt
codex sandbox cat ok.txt                 # 读：正常
codex sandbox sh -c 'echo x > new.txt'   # 写：Read-only file system
codex sandbox curl -sS -m 8 https://example.com   # 网络：Could not resolve host
```

```text
为什么这样组织：
1. 三档分明 —— allow 减少打断、prompt 保留把关、forbidden 硬性拦截
2. 内联用例 —— match/not_match 在加载时验证规则意图，避免"以为拦住了其实没拦"
3. 注意切段语义 —— 组合命令会被拆开逐段判定，规则要按单段命令来写
4. 行为可实测 —— codex sandbox 让沙箱边界变成可观察的事实而非文档承诺
```

## 最佳实践与踩坑记录

### 最佳实践

1. 新仓库先只读审计再放权：分两段授权（read-only 评估 → workspace-write 执行）比一步到位安全得多。
2. 日常停在 Auto 预设：受版本控制的仓库用 `workspace-write` + `on-request` 已足够，别图省事直接全放行。
3. 用最小边界而不是最大便利：可写目录用 `--add-dir` 按需追加，联网用完就关回 `network_access = false`。
4. 把常用命令写进 rules：频繁要用的只读命令用 `allow` 免审批，破坏性命令用 `forbidden` 硬拦。
5. 规则必须带 `match`/`not_match`：这是唯一能在加载期发现「规则写错了」的手段。
6. 自动化一律 `approval_policy = "never"` + 最小沙箱：非交互环境没人能批准越界请求，越界必然失败。

### 踩坑记录

```text
坑 1：以为关掉审批就没有沙箱了，结果命令还是被杀
结论：用 --ask-for-approval never 后，命令依然报 Read-only file system 或解析不了域名。
原因：审批与沙箱是两层独立控制，never 只是不问人，沙箱边界一分不减。
解法：要能写就改沙箱模式（--sandbox workspace-write）；要联网就打开 network_access。两层要分别调。

坑 2：审批放得很宽，模型却依然在写工作区外文件时失败
结论：已把审批设为 on-request 并批准过一次，后续同类操作还是失败。
原因：批准的是单次越界动作；可写根之外的文件编辑每次都要新的批准，非交互流程里无法产生批准就直接失败。
解法：用 --add-dir 或 sandbox_workspace_write.writable_roots 把需要的目录纳入边界，而不是靠一次次批准。

坑 3：规则文件写了，命令照样每次弹审批
结论：.rules 里的 allow 规则毫无效果。
原因：规则放在不生效的层级——项目级 .codex/rules/ 只在项目受信任时加载；或 pattern 不是精确前缀（命令行里参数顺序不同）；或命令含重定向/通配符等不进规则匹配的写法。
解法：把通用规则放到 ~/.codex/rules/；按精确前缀写 pattern；用 match/not_match 验证；避免用高级 shell 语法表达要被放行的命令。

坑 4：以为 auto_review 也能替自己审「全放行」场景
结论：设了 approvals_reviewer = "auto_review" 后，某些危险动作直接跑了，没人审。
原因：自动审查只在交互式审批下生效；若同时用了 approval_policy = "never" 或 danger-full-access，压根不产生越界审批请求，也就没有审查环节。
解法：保持 on-request（或 granular 交互策略）并保留可执行的沙箱边界，自动审查才有意义。

坑 5：在容器里又套一层沙箱，命令报 bwrap 权限错误
结论：Dev Container 里跑 Codex，命令因无法创建内层沙箱而失败。
原因：外层容器可能缺少 bwrap 所需的能力；Codex 默认仍尝试建自己的沙箱。
解法：要么给容器授予所需能力以保留 Linux 沙箱，要么在容器本身就是安全边界时用 --sandbox danger-full-access，不要嵌套两层。
```
