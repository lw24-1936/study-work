## 概述

Codex 是 OpenAI 的编码智能体（coding agent）：它把大模型接到你的本地仓库上，让模型自己读文件、改代码、跑命令、看结果，再继续下一步，直到任务完成或被中止。它与普通的「聊天式写代码」的关键差别在于**闭环**——模型能拿到真实执行结果（编译报错、测试输出、diff），因此可以自我验证与迭代。本文覆盖三件事：Codex 有哪几种形态、各订阅计划的配额规则、以及把 CLI 装好并登录。

```text
Codex 入门三件事：
1. 形态 —— CLI、IDE 扩展、云端 Codex cloud、桌面 app，共享一套配置
2. 配额 —— 订阅计划给「本地消息 + 云任务」的共享额度，API key 走标准 API 计费
3. 落地 —— 安装（install.sh / npm / Homebrew）→ 登录（ChatGPT 或 API key）→ 进仓库 codex
```

本机实测环境（2026-10-14）：

```text
$ node --version
v26.7.0
$ npm --version
11.19.0
$ codex --version
codex: 未找到命令
```

本文写作时本机尚未安装 Codex CLI，因此命令与参数一律以官方文档为准，装好后请用本机 `codex --help` 复核。

## Codex 的定位与能力边界

Codex 的核心循环是「模型输出动作 → Codex 执行 → 结果回填上下文 → 模型继续」。动作包括读文件、编辑文件、执行 shell 命令、调用 MCP 工具、联网搜索等。它的边界由两层安全控制决定：**沙箱**（技术上能碰什么）与**审批策略**（什么时候必须先问你），两者共同限制它能自主走多远；跳过审批不等于跳过沙箱。理解这一点，才不会把 Codex 当成「能替你无脑改全盘」的工具。

```text
Codex 能做什么（官方定位）：
1. 探索与解释 —— 读仓库、回答问题、定位问题代码（"Explain this codebase to me"）
2. 修改代码 —— 编辑工作区文件，产生可 review 的 diff
3. 执行与验证 —— 跑测试、跑 lint、跑构建，用真实输出自我纠正
4. 本地代码审查 —— /review 对 diff 给出有优先级的发现，不动工作区
5. 扩展与自动化 —— MCP 接外部工具、Skills 复用流程、子代理并行、codex exec 进 CI
```

能力边界同样明确：Codex 不做需求决策，也不替你承担「这版能不能上线」的判断；它在权限边界内自行其是，越界才问你。所以「给它多大的边界」是你唯一要持续管理的参数。

## 三种运行形态对比

Codex 有几个使用界面（surface），但共享同一套配置与登录：ChatGPT 桌面 app、Codex CLI、IDE 扩展、Codex cloud。CLI 与 IDE 扩展在本机跑，命令受 OS 级沙箱约束；Codex cloud 在 OpenAI 托管的隔离容器里克隆你的仓库运行，必须用 ChatGPT 账号登录，且需要一个 Git 远端（先 push 到 GitHub）才能用。选型的判断标准很简单：**要在本机跑测试、碰本地文件就选 CLI 或 IDE；要并行跑、或想从其他设备委派任务就选 cloud。**

| 形态 | 运行位置 | 登录方式 | 典型场景 |
|---|---|---|---|
| Codex CLI | 你的终端（本地） | ChatGPT 或 API key | 终端工作流、脚本、CI |
| IDE 扩展 | VS Code / Cursor / Windsurf | ChatGPT 或 API key | 编辑器内改代码、带 IDE 上下文 |
| 桌面 app | macOS / Windows（本地聊天） | ChatGPT 或 API key | 图形化会话、多项目切换 |
| Codex cloud | OpenAI 托管容器 | 仅 ChatGPT | 并行任务、GitHub PR 审查、Slack/Linear 委派 |

```text
形态选择要点：
1. 配置共享 —— CLI、IDE 扩展、桌面 app 在同一台机器上共用 ~/.codex 配置与 MCP 设置
2. 本地形态 —— 命令走 OS 级沙箱，默认无网络、写权限限于工作区
3. 云端形态 —— 两阶段运行：setup 阶段可联网装依赖，agent 阶段默认离线
4. 云端限制 —— 必须 ChatGPT 登录，API key 无法启用云功能
5. 代码来源 —— 云端从 GitHub 克隆仓库，未 push 的本地改动要先委派或先提交
```

## 订阅计划与配额

Codex 的用量有两种计费路径：**订阅计划**（额度内包含，超出可买 credits）与 **API key**（按标准 API 价格付费，无云功能）。官方文档明确：ChatGPT Work 在 ChatGPT 内的用量与 Codex 使用同一套定价、credits 与限额。额度不是「固定消息数」——同一句话，模型档位、上下文大小、推理强度、工具调用与缓存都会影响消耗，所以只能看用量面板（`/status` 或 usage dashboard）而不是凭感觉估。

| 计划 | 价格 | Codex 相关要点 |
|---|---|---|
| Free | $0/月 | 桌面 app 内可体验基础编码任务，受灰度限制 |
| Go | $8/月 | 轻量编码任务 |
| Plus | $20/月 | web / CLI / IDE / iOS 全可用；含云端自动代码审查、Slack 集成；可用 credits 扩展用量 |
| Pro | $100 / $200 / $500 每月 | 含 Plus 全部能力；Pro $500 可用 Ultrafast 模式；当前无 5 小时限额 |
| Business | $20/用户/月（2 人起、按年计费；月付 $25） | 更大的云虚拟机、SSO/MFA、默认不用业务数据训练 |
| Enterprise / Edu | 联系销售 | SCIM、EKM、RBAC、Compliance API 审计、数据驻留与保留控制 |
| API Key | 按 API 价格 | 仅 CLI / SDK / IDE；无 GitHub 代码审查、Slack 等云功能 |

```text
配额规则要点：
1. 共享额度 —— 本地消息与云任务共用同一计划的额度，可能另有周限额
2. 限额估算 —— Plus / 标准 Business 的本地消息（每 5 小时）随模型变化，弱模型可多出数十倍
3. 加速档位 —— Fast 模式按包含额度的 2.5 倍、购买 credits 的 2 倍计；Ultrafast 为 8 倍 / 6 倍
4. 超限行为 —— 达到限额时当前回合可按公平使用原则跑完，之后可购买额外 credits 继续
5. 省额度手段 —— 精确提示词、限定上下文来源、精简 AGENTS.md、少挂 MCP 服务器
```

具体模型名、价格与倍数会随版本调整，**以官方 pricing 页面和你的用量面板为准**。

## 安装 Codex CLI

官方给出四种安装方式：独立安装脚本（macOS/Linux）、Windows PowerShell 脚本、npm、Homebrew。npm 与 Homebrew 路径要求本机已有 Node 或 brew；独立脚本是官方首推方式，升级就是重跑同一条命令。CLI 支持 macOS、Windows、Linux；在 Windows 上可以原生跑 PowerShell（走 Windows 沙箱），也可以在 WSL2 里跑 Linux 实现。

```shell
# 方式一：独立安装脚本（macOS / Linux，官方推荐）
curl -fsSL https://chatgpt.com/codex/install.sh | sh

# 无人值守安装（CI、初始化脚本里用）
curl -fsSL https://chatgpt.com/codex/install.sh | CODEX_NON_INTERACTIVE=1 sh

# 方式二：npm（需已装 Node）
npm install -g @openai/codex

# 方式三：Homebrew（macOS）
brew install --cask codex
```

```powershell
# 方式四：Windows 原生
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"
```

装完先确认可执行、再看帮助，最后进入目标仓库启动：

```shell
# 1. 确认安装
codex --version

# 2. 看命令与全局参数
codex --help
codex exec --help        # 非交互模式的参数

# 3. 进入仓库后启动交互式 TUI
cd ~/code/my-app
git status               # 启动前务必确认工作区干净或已提交
codex
```

```text
安装要点：
1. 首选脚本安装 —— 一条 curl 命令即可，升级复用同一命令，无需 Node
2. npm 路径 —— 适合已有 Node 工具链的机器，升级用 @latest
3. 前置条件 —— Codex 要求命令在 Git 仓库内运行，防止破坏性改动（非交互可用 --skip-git-repo-check 绕过）
4. CODEX_HOME —— 默认 ~/.codex，可用环境变量指向别处，实现「一个项目一套配置」
5. 启动前提交 —— 进仓库前先 commit 或 stash，方便随时回滚 AI 的改动
```

## 登录与认证

Codex 支持两种个人登录方式：**Sign in with ChatGPT**（走订阅额度、受工作区权限与保留策略约束）与 **Sign in with API key**（走 OpenAI Platform 计费，云功能受限）。CLI 默认路径是 `codex login` 打开浏览器完成 OAuth；在无浏览器或回调被拦的机器上改用设备码登录或转发回调端口。凭证缓存位置由 `cli_auth_credentials_store` 决定，默认文件在 `~/.codex/auth.json`——官方反复强调它等同密码，不要提交、不要贴到工单或聊天里。

```shell
# ChatGPT 登录（默认，走浏览器 OAuth）
codex login

# API key 登录（key 从 stdin 读入，不进 shell history）
printenv OPENAI_API_KEY | codex login --with-api-key

# 无浏览器 / 回调被拦的环境：设备码登录（beta）
codex login --device-auth

# 查看当前认证方式 / 退出登录
codex login status
codex logout
```

无头机器的三种兜底（官方顺序）：设备码登录优先；其次在能开浏览器的机器登录后把 `~/.codex/auth.json` 复制过去；再其次用 `ssh -L 1455:localhost:1455 user@remote` 把本地回调端口转发到远端（回调默认 `localhost:1455`）。企业环境还可以用 Codex access token：`printenv CODEX_ACCESS_TOKEN | codex login --with-access-token`。

```toml
# ~/.codex/config.toml：凭证存放与登录限制
# 凭证位置：file 存进 auth.json；keyring 用系统钥匙串；auto 优先钥匙串；ephemeral 只留在内存
cli_auth_credentials_store = "keyring"

# 托管环境里管理员可强制登录方式与工作区（用户无法用 config.toml 覆盖）
# forced_login_method = "chatgpt"        # 或 "api"
# forced_chatgpt_workspace_id = "00000000-0000-0000-0000-000000000000"
```

公司网络走自签 CA 或 TLS 代理时，登录前设置 PEM 证书包，否则浏览器回调会失败：

```shell
export CODEX_CA_CERTIFICATE=/path/to/corporate-root-ca.pem
codex login
```

```text
登录要点：
1. 两条路 —— ChatGPT 登录给订阅额度与云功能；API key 给自动化，云功能不可用
2. 凭证文件 —— file 模式为 ~/.codex/auth.json，含 access token，等同密码
3. 无头环境 —— device-auth 优先，其次复制 auth.json，再其次转发 1455 端口
4. 登录诊断 —— 直接跑 codex login 会写 codex-login.log 到日志目录，排障从这里看
5. 企业自动化 —— Codex access token 用于可信脚本/调度器/私有 runner，通用 API 调用仍用 Platform key
```

## 版本升级与降级

升级路径与安装路径一一对应：脚本安装重跑脚本，npm 安装用 `npm i -g @openai/codex@latest`，Homebrew 用 `brew upgrade --cask codex`；CLI 自身也提供 `codex update` 做自更新检查（取决于当前安装方式是否支持自更新）。降级与固定版本在 npm 路径下最直接：装指定版本号即可；脚本路径没有版本参数，需要锁定版本时改用 npm。可关掉启动时自动检查更新，由团队统一管版本。

```shell
# 升级：与安装方式对应
curl -fsSL https://chatgpt.com/codex/install.sh | sh      # 脚本安装
npm install -g @openai/codex@latest                       # npm 安装
brew upgrade --cask codex                                 # Homebrew
codex update                                              # CLI 自更新（若安装方式支持）

# 固定版本 / 降级（npm 路径）
npm install -g @openai/codex@0.143.0

# 查看当前版本
codex --version
```

```toml
# ~/.codex/config.toml
# 仅在更新被集中管理时关闭（否则会一直提示旧版本）
check_for_update_on_startup = false
```

```text
版本管理要点：
1. 升级即重跑 —— 脚本安装的升级就是把安装命令再执行一次，无需卸载
2. 固定版本 —— 团队/CI 要可复现时用 npm 并写死版本号，锁定 CLI 版本
3. 自更新命令 —— codex update 是否可用取决于安装方式与版本，先看 --help
4. 配置校验 —— 升级后可用 --strict-config 让 Codex 对无法识别的配置字段直接报错
5. 帮助即事实 —— 不同版本命令与参数有增删，判断依据永远是本机 codex --help
```

## 应用场景实战

### 场景一：新开发机 10 分钟内装好 Codex 并跑通第一个任务

适合刚拿到一台干净的 Ubuntu 开发机（已装 Node/Git）的场景，目标是脚本化安装、登录、进仓库验证。

```shell
# 1. 基础前置
git --version
node --version      # 若用 npm 安装路径，需要 Node 18+

# 2. 安装（脚本方式，无需 Node）
curl -fsSL https://chatgpt.com/codex/install.sh | sh
codex --version

# 3. 登录（本机有浏览器）
codex login
codex login status

# 4. 备好一个练习仓库
mkdir -p ~/code/hello-codex
cd ~/code/hello-codex
git init
printf 'print("hello")\n' > main.py
git add .
git commit -m "chore: 初始化练习仓库"

# 5. 启动并下达第一个任务（交互式）
codex "解释这个仓库，并为 main.py 补一个 pytest 用例"
```

```text
预期结果：
1. codex --version 打印版本号，说明二进制在 PATH 中
2. codex login status 显示当前登录的账号/工作区（或 API key 状态）
3. 进入 TUI 后模型会读取仓库、创建测试文件、运行 pytest
4. 任务结束后用 git diff 审查改动，满意再 commit
```

### 场景二：在 CI runner 上安装固定版本并用非交互模式做发布说明

企业 CI 里要可复现，所以固定版本 + 用 API key 认证 + 非交互执行，输出写到文件供后续步骤消费。

```yaml
# .github/workflows/release-notes.yml
name: Generate release notes with Codex
on:
  workflow_dispatch:

jobs:
  notes:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0        # 需要完整历史才能读 commit

      - name: Install Codex CLI (pinned)
        run: npm install -g @openai/codex@0.143.0

      - name: Generate release notes
        env:
          CODEX_API_KEY: ${{ secrets.OPENAI_API_KEY }}   # 只在这一步可见
        run: |
          codex exec --sandbox read-only \
            "根据最近 10 个 commit 生成使用说明，只输出 Markdown" \
            -o release-notes.md

      - uses: actions/upload-artifact@v4
        with:
          name: release-notes
          path: release-notes.md
```

```text
要点：
1. 固定版本 —— npm 装指定版本号，避免 runner 上版本漂移导致输出结构变化
2. 最小权限 —— 只读沙箱 + 只读 job 权限，Codex 不需要写权限
3. key 作用域 —— 把 key 放在执行 Codex 的那一步，不要留在 job 级环境变量
4. 结果落地 —— -o 把最终消息写文件，供 artifact 或后续步骤使用
5. 官方更优解 —— GitHub Actions 场景优先用 openai/codex-action，它用代理隔离 API key
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先提交再让 AI 动手：进仓库前 `git commit` 或 `git stash`，让每次 Codex 改动都有干净的基线可对比、可回滚。
2. 用独立安装脚本而非 npm：脚本安装在升级与排障上最省心，npm 只在需要固定版本或 CI 复现时用。
3. 自动化只用 API key：CI 与脚本走 `CODEX_API_KEY` 或 Platform key，别把个人 ChatGPT 凭证塞进 runner。
4. 把 `~/.codex/auth.json` 当密码对待：不提交、不贴工单、不进日志，能用 keyring 就用 keyring。
5. 版本能力以 `--help` 为准：模型名、参数、默认值随版本变化，文档只作参考，判断依据是本机帮助输出。
6. 定期看用量面板：Codex 消耗受上下文、工具与推理档位影响极大，靠 `/status` 和 usage dashboard 掌握节奏。

### 踩坑记录

```text
坑 1：在非 Git 目录里跑 codex，报仓库检查失败
结论：命令直接退出，提示需要 Git 仓库。
原因：Codex 默认要求命令在 Git 仓库内执行，以避免不可控的破坏性改动。
解法：在目标目录 git init 并至少 commit 一次；确知环境安全时才用 codex exec --skip-git-repo-check。

坑 2：无头服务器上 codex login 卡住或回调超时
结论：浏览器打不开、或 localhost 回调连不回来，登录流程挂死。
原因：登录默认依赖本机浏览器 + 本地回调端口（默认 localhost:1455）。
解法：优先 codex login --device-auth；或用 ssh -L 1455:localhost:1455 转发回调；或从有浏览器的机器复制 ~/.codex/auth.json（注意权限 600）。

坑 3：公司 TLS 代理下登录或请求失败
结论：codex login 直接失败，或后续 HTTPS 请求证书不受信任。
原因：企业自签根证书不在系统信任链里。
解法：export CODEX_CA_CERTIFICATE=/path/to/ca.pem 后再登录（未设置时回退到 SSL_CERT_FILE）。

坑 4：以为 API key 也能用云端功能
结论：接入后发现 GitHub 代码审查、Slack 集成等云功能不可用。
原因：Codex cloud 要求 ChatGPT 登录，API key 不支持云功能。
解法：需要云功能就用 ChatGPT 账号登录；用 API key 时按「本地能力」规划工作流。

坑 5：凭「消息条数」估算额度，实际很快超限
结论：以为还能跑很多次，结果额度早被吃掉。
原因：用量取决于模型档位、上下文大小、推理强度、工具调用与缓存，不是固定消息数。
解法：用 /status 与用量面板看真实消耗；精简 AGENTS.md、少挂 MCP、给弱模型派简单任务。
```
