## 概述

TensorFlow 是 Google 开源的端到端机器学习框架：底层是 C++ 算子运行时与图执行引擎，上层通过 Python 前端暴露张量计算、自动微分与设备管理，再由 Keras 提供建模高层 API。从 TensorFlow 2.16 起，`pip install tensorflow` 默认安装 Keras 3（Keras 3 是重写过的多后端框架，可跑在 TensorFlow / JAX / PyTorch 之上），因此现在写 TensorFlow 代码基本上就是「用 tf 的张量与自动微分 + 用 Keras 3 建模型」。本篇讲清楚三件事：生态里各个包分别干什么、Python 与 CUDA 的版本约束、以及怎么装完就能验证环境是好的。

```text
本篇主线：
1. 生态 —— tensorflow / tensorflow-cpu / tf-nightly / tf-keras / Keras 3 的关系
2. 版本 —— Python 3.9~3.12 区间、TF 2.16 是 Keras 2 与 Keras 3 的分界线
3. 安装 —— venv 隔离 + pip 三选一（CPU / GPU[and-cuda] / 固定版本），国内走清华镜像
4. 验证 —— import + 真跑一次矩阵乘法 + list_physical_devices，三件套缺一不可
5. 配置 —— 设备可见性、显存增长、线程数、构建信息（is_cuda_build）
6. 排障 —— 驱动版本不匹配、wheel 与 Python 版本不匹配、tf.keras 指向 Keras 2 的老代码
```

## TensorFlow 生态组成

TensorFlow 不是单个库，而是一组按「训练 / 部署 / 终端」分层的包。理解分层能避免装错东西：训练与实验只需要 `tensorflow`（含 Keras 3）；线上推理服务走 TensorFlow Serving；端侧走 TensorFlow Lite / LiteRT；浏览器走 TensorFlow.js；生产流水线走 TFX。

| 包 / 组件 | 作用 | 什么时候用 |
|-----------|------|------------|
| `tensorflow` | 核心包，含 CPU 与 GPU(+CUDA) 支持、依赖 Keras 3 | 默认选择；装了它就同时有 `tf` 与 `keras` |
| `tensorflow-cpu` | 只含 CPU 的构建，体积更小 | 明确不上 GPU、或镜像要瘦身 |
| `tf-nightly` | 每日预览构建 | 需要用尚未发布的 API，或复现上游修复 |
| `keras` | Keras 3 本身，可独立升级 | 需要比 TF 自带的更新版本：`pip install --upgrade keras` |
| `tf-keras` | 旧版 Keras 2 的兼容包 | 老代码依赖 Keras 2 行为时，配 `TF_USE_LEGACY_KERAS=1` |
| `tf.data` | 数据管道（`tf.data.Dataset`） | 任何非玩具规模的数据读取与预处理 |
| `tf.function` / XLA | 把 Python 函数编译成图，减少 Python 开销 | 训练热路径提速；XLA 可再融合算子 |
| `tf.distribute` | 多卡 / 多机训练策略 | `MirroredStrategy` 等 |
| TensorFlow Serving | 独立模型服务进程，gRPC / REST | 线上推理服务 |
| TensorFlow Lite / LiteRT | 移动端与嵌入式推理运行时 | 手机、MCU、边缘设备 |
| TensorFlow.js | 浏览器 / Node 端推理与训练 | 前端直接跑模型 |
| TFX | 生产级 ML 流水线框架 | 需要数据校验、模型评估、上线审计 |

需要特别注意的是 `tf.keras` 与 `keras` 的关系：从 TensorFlow 2.16 起，`pip install tensorflow` 装的就是 Keras 3，此时 `from tensorflow import keras` 与 `import keras` 指向**同一个 Keras 3**。本机实测可以直接验证：

```python
import keras
import tensorflow as tf

print(keras.__version__, tf.keras.__version__)   # 3.15.1 3.15.1
print(keras.backend.backend())                   # tensorflow
```

```text
$ /root/.hermes/cache/scratch/aivenv-tf312/bin/python tf_keras.py
keras: 3.15.1
backend: tensorflow
tf.keras is keras: 3.15.1
```

Keras 3 的后端在**导入 Keras 之前**由环境变量 `KERAS_BACKEND` 决定（`jax` / `tensorflow` / `torch`），导入之后无法切换；配置文件在 `~/.keras/keras.json`。这也意味着：网上大量 2023 年前的教程写的是 Keras 2 的 API，照抄会在 Keras 3 上直接报错。

```text
TensorFlow 生态要点：
1. 训练用 tensorflow（含 Keras 3）；部署另算：Serving（服务端）、LiteRT（端侧）、tfjs（浏览器）
2. TF >= 2.16 时 tf.keras 就是 Keras 3，旧代码若依赖 Keras 2 行为需装 tf-keras 并设 TF_USE_LEGACY_KERAS=1
3. Keras 3 是多后端框架，KERAS_BACKEND 必须在 import keras 之前设置，导入后不可切换
4. tf.data 与 tf.function 是「真跑得动」与「只跑得对」的分水岭，别用纯 Python 循环硬扛大数据
5. 国内网络下 pip 装包建议指定清华镜像，否则容易卡在大 wheel 的下载上
```

## 版本与 Python 兼容性

TensorFlow 对 Python 小版本比较敏感：官方安装文档给出的软件要求是 **Python 3.9–3.12**（以官方安装页为准，官方会随版本更新该区间），pip 需要 19.0 以上（Linux/Windows，需 manylinux2014 支持）。Python 太新时 pip 会直接找不到与解释器匹配的 wheel，报 `No matching distribution found for tensorflow`——这不是网络问题，而是版本问题。

版本号本身遵循 `2.<minor>.<patch>`，minor 每季度发布一次。判断一个环境「能干什么」时看三个数：`tf.__version__`、`tf.keras.__version__`、`tf.sysconfig.get_build_info()["is_cuda_build"]`。

| 约束项 | 官方文档要求 | 本机实测 |
|--------|--------------|----------|
| Python | 3.9 – 3.12 | 3.12.3 ✓ |
| pip | >= 19.0（Linux/Windows） | 26.2.1 ✓ |
| 操作系统 | Ubuntu 16.04+ 64 位（官方只正式支持 Ubuntu） | Ubuntu 24.04（内核 7.0.0-28-generic） |
| TensorFlow | 最新稳定版 | 2.20.0 |
| Keras | TF >= 2.16 默认 Keras 3 | 3.15.1 |
| GPU 驱动（仅 GPU 用） | Linux >= 525.60.13 | 无法验证：`nvidia-smi` 报 NVML 驱动/库版本不匹配 |
| CUDA Toolkit（仅 GPU 用） | 官方安装页当前给出 CUDA 12.3 | 未验证（本机为 CPU 环境） |
| cuDNN（仅 GPU 用） | 官方安装页当前给出 cuDNN 8.9.7 | 未验证（本机为 CPU 环境） |

固定版本的做法是显式指定，避免「今天能跑明天不能跑」：

```shell
# 固定 TensorFlow 主次版本（推荐在 requirements.txt 里写这一行）
python -m pip install "tensorflow==2.20.0"

# 只固定到 minor，接受补丁升级
python -m pip install "tensorflow~=2.20.0"

# Keras 想独立升级（会脱离 TF 自带的版本，注意兼容性）
python -m pip install --upgrade keras

# 国内网络加速（清华镜像）
python -m pip install -i https://pypi.tuna.tsinghua.edu.cn/simple "tensorflow==2.20.0"
```

```text
版本与兼容性要点：
1. Python 3.9–3.12 是官方安装页当前给出的区间，超出区间通常表现为 pip 找不到 wheel
2. TF 2.16 是分界线：之前 pip install tensorflow 装 Keras 2，之后装 Keras 3
3. 生产环境用 == 或 ~= 钉死版本；只有做兼容性验证才追最新版
4. 判断 GPU 是否可用不看 tf.__version__，看 list_physical_devices('GPU') 与 is_cuda_build
5. CUDA/cuDNN 的最低要求随 TF 版本变化，升级 TF 前先查官方安装页的 Software requirements
```

## CPU 与 GPU 安装

安装路径只有一条主线：**建独立 venv → 升级 pip → 装包 → 立即验证**。官方文档明确推荐用标准库的 `venv` 而不是全局 pip；不隔离环境的话，不同项目需要的 protobuf / numpy 版本会互相打架，症状往往是 `import tensorflow` 时抛 `ImportError` 或 `AttributeError`。

```shell
# 1) 建 venv（官方推荐方式）
python3 -m venv tf
source tf/bin/activate

# 2) 升级 pip（官方明确要求，旧 pip 可能解析不出正确的 wheel）
python -m pip install --upgrade pip

# 3) 装包：三选一
python -m pip install tensorflow              # CPU 用户
python -m pip install "tensorflow[and-cuda]"  # Linux/WSL2 GPU 用户：连带装 NVIDIA 的 pip 版 CUDA 库
python -m pip install tensorflow-cpu          # 只要 CPU，包更小

# 4) 官方验证命令
python3 -c "import tensorflow as tf; print(tf.reduce_sum(tf.random.normal([1000, 1000])))"
```

GPU 路径要特别注意两点。第一，`tensorflow[and-cuda]` 只是把 CUDA 运行库通过 pip 装进 venv，**显卡驱动仍然必须由系统提供**，且版本满足官方下限（Linux >= 525.60.13）。第二，如果 pip 装的 NVIDIA 库与系统里已有的 CUDA 冲突导致检测不到 GPU，官方给出的办法是在 TensorFlow 包目录里建符号链接：

```shell
# 官方安装文档给出的排障步骤（仅在 list_physical_devices('GPU') 为空时尝试）
pushd $(dirname $(python -c 'print(__import__("tensorflow").__file__)'))
ln -svf ../nvidia/*/lib/*.so* .
popd

# 再给 venv 补一个 ptxas 符号链接
ln -sf $(find $(dirname $(dirname $(python -c "import nvidia.cuda_nvcc;
print(nvidia.cuda_nvcc.__file__)"))/*/bin/) -name ptxas -print -quit) $VIRTUAL_ENV/bin/ptxas
```

Windows 上有一条硬限制：**原生 Windows 在 TF 2.10 之后不再支持 GPU**（官方文档原话是 "Anything above 2.10 is not supported on the GPU on Windows Native"），要用 GPU 只能走 WSL2。macOS 则一直没有官方 GPU 支持。

```text
安装要点：
1. 永远建 venv：TF 依赖 numpy/protobuf/typing_extensions，全局装几乎必然与系统包冲突
2. 装包前先 python -m pip install --upgrade pip，旧 pip 解析 wheel 会出错
3. CPU 用 tensorflow 或 tensorflow-cpu；GPU（Linux/WSL2）用 tensorflow[and-cuda]
4. [and-cuda] 不含驱动：系统驱动必须自己装且满足版本下限（Linux >= 525.60.13）
5. 原生 Windows 在 TF 2.10 之后无 GPU 支持，需要 GPU 请用 WSL2
6. 国内网络加 -i https://pypi.tuna.tsinghua.edu.cn/simple，大 wheel 下载会稳很多
```

上面这段覆盖了排查环境问题的核心信息：物理设备（`physical`）是硬件视角，逻辑设备（`logical`）是 TF 视角，二者在开启设备虚拟化后会产生差异；`inter_op` / `intra_op` 返回 0 表示「由运行时自动决定」，不是「没有线程」；`eager: True` 说明当前处于即时执行模式，可以直接打印任何张量的值。

```python
import tensorflow as tf

# 官方 CPU 验证：真跑一次算子
print(tf.reduce_sum(tf.random.normal([1000, 1000])))

# 官方 GPU 验证：返回非空列表才算 GPU 可用
print(tf.config.list_physical_devices("GPU"))

# 判断装的是不是 CUDA 构建（与本机是否插卡无关，取决于 wheel 本身）
print(tf.sysconfig.get_build_info()["is_cuda_build"])
```

```text
验证要点：
1. 官方验证命令的要点是「跑出张量」，只 import 成功不能证明环境可用
2. physical 是硬件视角、logical 是 TF 视角，开启设备虚拟化后两者会不同
3. inter_op/intra_op 返回 0 表示运行时自动决定并行度，不是禁用并行
4. is_cuda_build 描述「这个 wheel 是否支持 CUDA」，与机器上有没有卡是两件事
5. 第一行的 cpu_feature_guard 是信息级日志，说明 wheel 未针对本机 CPU 指令集编译，不影响功能
```

## 构建信息与运行配置

拿到一个环境后，除了版本号，还应该知道它是怎么编译的、能调哪些运行开关。`tf.sysconfig.get_build_info()` 返回构建配置字典，`tf.config.threading` 与 `tf.config` 系列 API 控制设备可见性和并行度。这些设置有个共同约束：**设备相关配置必须在任何张量运算之前调用**，否则会抛 `RuntimeError`——本机实测就复现了这一点（脚本前面已经跑过算子）。

```python
import tensorflow as tf

# 构建信息：CPU 构建下 CUDA 相关字段为 None，is_cuda_build 为 False
info = tf.sysconfig.get_build_info()
for k in ("cuda_version", "cudnn_version", "is_cuda_build", "is_tensorrt_build"):
    print(k, "=", info.get(k))

# 线程数：必须在跑算子之前设置才有效
tf.config.threading.set_inter_op_parallelism_threads(2)
tf.config.threading.set_intra_op_parallelism_threads(4)
print(tf.config.threading.get_intra_op_parallelism_threads())

# 设备可见性 / 显存增长（GPU 机器上才有意义）
gpus = tf.config.list_physical_devices("GPU")
if gpus:
    tf.config.experimental.set_memory_growth(gpus[0], True)   # 按需增长，不吃满显存
```

本机真实执行设备配置脚本的输出（CPU 环境，逻辑设备切分因「已初始化」而失败，这本身是重要结论）：

```text
=== 2. 按需限制可见设备（必须在任何张量运算之前）===

=== 3. GPU 内存策略（本机无 GPU，走 else 分支，逻辑照旧）===
```

`tf.distribute.get_strategy()` 在没有任何策略作用域时返回默认策略（单设备），`num_replicas_in_sync` 为 1。要点是**在 `strategy.scope()` 里建模型和优化器**，这个习惯在单机单卡上无害，但迁到多卡时能省掉一次重构（详见 11.8）。

```text
构建信息与运行配置要点：
1. 设备配置（可见设备、逻辑设备切分、memory_growth）必须在第一个算子之前调用
2. 报 "Virtual devices cannot be modified after being initialized" 说明调用时机太晚，只能新起进程
3. GPU 机器上默认会按需抢占显存，多进程共用一张卡时应开 memory_growth 或显式限制上限
4. 线程数设置对 CPU 训练吞吐影响明显，设完要实测对比，别凭感觉调
5. 建模型/优化器一律包在 strategy.scope() 里，单设备上无害、多设备上省事
6. 本机无 GPU，"显存策略" 分支未在本机验证，仅保留官方文档路径
```

## 安装与运行常见问题

安装类问题的表现往往离根因很远，几个高频形态与定位手段如下。第一类是**版本不匹配**：Python 版本超出官方区间、pip 太旧、CUDA/cuDNN 与 wheel 不匹配。第二类是**依赖冲突**：numpy 2.x 与老代码、protobuf 版本与 TF 要求的区间。第三类是**驱动问题**：本机就是典型例子，`nvidia-smi` 报 `Failed to initialize NVML: Driver/library version mismatch`，此时即使装了 GPU 构建也不可能用上 GPU，必须先修驱动（内核模块版本与用户态库版本要一致）。

```shell
# 逐项定位环境问题
python -c "import sys; print(sys.version)"            # Python 版本是否在区间内
python -m pip --version                               # pip 是否够新
python -m pip show tensorflow | head -6               # 实际装的版本与位置
python -c "import tensorflow as tf; print(tf.__version__)"
nvidia-smi                                            # 驱动是否健康（GPU 机器）
python -c "import tensorflow as tf; print(tf.config.list_physical_devices())"

# 依赖冲突时先看全局，再钉版本
python -m pip check
python -m pip install -i https://pypi.tuna.tsinghua.edu.cn/simple \
  "numpy<2" "protobuf>=4.21,<5"
```

老代码在 Keras 3 上跑不动时，官方给的过渡方案是装 `tf-keras` 并让 `tf.keras` 指回 Keras 2：

```python
# 必须在 import tensorflow 之前设置环境变量
import os
```

## 应用场景实战

### 场景一：一键搭出可复现的 CPU 训练环境（含 CI 可用的自检脚本）

算法团队要保证「本地跑通、CI 也跑通」，最省事的做法是把依赖钉死在一份 requirements 里，再用一个自检脚本在装完后立刻判定环境合格。自检脚本的价值在于：它把「Python 版本、TF 版本、设备、真跑一次算子」四件事合成一个退出码，CI 里直接以退出码判定失败，不用人去读日志。

```text
# requirements.txt（生产环境建议全部 == 钉死）
tensorflow==2.20.0
numpy==2.5.4
```

```shell
#!/usr/bin/env bash
# setup_env.sh —— 建 venv、装依赖、跑自检，任一步失败即退出
set -euo pipefail

VENV_DIR="${1:-.venv-tf}"
MIRROR="https://pypi.tuna.tsinghua.edu.cn/simple"

python3 -m venv "$VENV_DIR"
# shellcheck disable=SC1091
source "$VENV_DIR/bin/activate"

python -m pip install --upgrade pip
python -m pip install -i "$MIRROR" -r requirements.txt

# 自检脚本失败会让整个脚本以非零码退出（CI 直接能挂失败门禁）
python check_env.py
```

下面是本机真实跑过的自检脚本（`check_env.py`），退出码为 0：

```python
import sys
import tensorflow as tf

REQUIRED = (2, 20)
PY_REQUIRED = (3, 12)


def check():
    problems = []

    if sys.version_info[:2] != PY_REQUIRED:
        problems.append(f"Python 版本 {sys.version_info[:2]} != 期望 {PY_REQUIRED}")

    major_minor = tuple(int(x) for x in tf.__version__.split(".")[:2])
    if major_minor < REQUIRED:
        problems.append(f"TensorFlow {tf.__version__} 低于要求 {REQUIRED}")

    # 真跑一次矩阵运算，确认不是只有 import 成功
    r = tf.reduce_sum(tf.random.normal([1000, 1000]))
    if r.numpy() == 0:
        problems.append("随机张量求和为 0，计算图可能没真正执行")

    info = tf.sysconfig.get_build_info()
    print(f"Python            : {sys.version.split()[0]}")
    print(f"TensorFlow        : {tf.__version__}")
    print(f"Keras             : {tf.keras.__version__}")
    print(f"CPU 设备          : {tf.config.list_physical_devices('CPU')}")
    print(f"GPU 设备          : {tf.config.list_physical_devices('GPU')}")
    print(f"CUDA 构建         : {info.get('is_cuda_build')}")
    print(f"CPU 线程(intra_op): {tf.config.threading.get_intra_op_parallelism_threads()} (=0 表示自动)")
    print(f"1000x1000 求和    : {r.numpy():.4f}")
    print(f"Eager 模式        : {tf.executing_eagerly()}")

    if problems:
        print("\n[FAIL]")
        for p in problems:
            print("  -", p)
        return 1
    print("\n[OK] 环境检查全部通过")
    return 0


if __name__ == "__main__":
    sys.exit(check())
```

脚本里的三个判断值得照抄：Python 版本必须精确匹配（避免不同机器解释器不一致）、`tf.__version__` 只比较主次版本（补丁升级通常无害）、以及**真的执行一次 1000x1000 随机张量求和**并确认结果非 0（只 import 不能证明运行时可用）。注意 `1000x1000 求和` 的数值每次都不同，这里只是证明「算子跑通且非零」，脚本里不做数值断言。

```text

1. 依赖全部写进 requirements.txt 并钉死版本，venv 目录名与项目绑定，别复用全局环境
2. pip 先升级再装包，装完立刻跑自检脚本，让问题在装完的当秒暴露
3. 自检脚本必须真跑算子（如 reduce_sum(tf.random.normal([1000,1000]))），不能只 import

5. 只比较主次版本号可以容忍补丁升级，避免每周被 requirements 锁死
```

### 场景二：同一份代码在 CPU 与 GPU 机器上都跑对

训练脚本经常要在开发机（有卡）和 CI（无卡）之间来回跑，硬编码 `/GPU:0` 会在无卡机器上直接报错。稳妥写法是运行期探测设备，按探测结果决定策略与批大小，并把设备信息打进日志，方便事后对齐「这次跑得快/慢是不是因为换了设备」。

```python
import tensorflow as tf


def build_strategy():
    """按可用设备返回策略与推荐批大小。单卡/单机用默认策略即可，
    这里返回 (strategy, batch_size) 便于训练脚本统一消费。"""
    gpus = tf.config.list_physical_devices("GPU")
    if gpus:
        for g in gpus:
            tf.config.experimental.set_memory_growth(g, True)   # 多进程共用卡时必须
        strategy = tf.distribute.MirroredStrategy()             # 单卡也会正常退化
        batch_size = 256 * strategy.num_replicas_in_sync
    else:
        strategy = tf.distribute.get_strategy()
        batch_size = 64                                          # CPU 上小批更容易跑完
    print(f"[env] GPU={[g.name for g in gpus]} replicas={strategy.num_replicas_in_sync} "
          f"batch_size={batch_size} cuda_build={tf.sysconfig.get_build_info()['is_cuda_build']}")
    return strategy, batch_size
```

```text
双环境兼容要点：
1. 不要硬编码 /GPU:0，用 list_physical_devices 探测后再决定策略与批大小
2. 有 GPU 时先开 memory_growth，多进程共享一张卡不开会被显存抢占拖死
3. 批大小随设备变化是正常的：CPU 上用小批更容易按时完成
4. 把设备信息与 is_cuda_build 打进训练日志，性能差异才有据可查
5. 无 GPU 时也保留分发策略代码路径（默认策略副本数为 1），迁移时零改动
6. 未在本机验证：本机无可用 GPU（NVML 驱动不匹配），上述 GPU 分支未实际执行
```

## 最佳实践与踩坑记录

### 最佳实践

1. 一个项目一个 venv，依赖全部写进 `requirements.txt` 并钉死版本；TF 的依赖树很宽，全局安装迟早冲突。
2. 装完立刻跑自检：Python 版本 + TF 版本 + 真跑一次算子 + 设备列表，四件事都过才算装好。
3. 判断 GPU 是否可用只看 `tf.config.list_physical_devices("GPU")` 与 `is_cuda_build`：同一份 `tensorflow` 包在 CPU 与 GPU 构建之间是可安装的，光看包装没装对不够。
4. GPU 机器上训练前先设 `set_memory_growth(gpu, True)` 或显式 `set_logical_device_configuration` 限制显存上限，避免多进程互相挤。
5. 设备类配置写在脚本最前面（任何张量运算之前），否则会撞上 `Virtual devices cannot be modified after being initialized`。
6. Keras 3 与 Keras 2 的 API 差异很大，读教程先确认年份；迁移老项目优先用 `tf-keras` + `TF_USE_LEGACY_KERAS=1` 过渡而不是逐行改写。
7. 内网/国内环境固定使用清华镜像 `-i https://pypi.tuna.tsinghua.edu.cn/simple`，把镜像写进团队文档而不是每个人自己记。

### 踩坑记录

```text
坑 1：pip install tensorflow 报 "No matching distribution found for tensorflow"
结论：以为网络被墙或源里没有这个包，反复换源无效。
原因：Python 解释器版本不在该 TF 版本支持的区间内（官方安装页当前给出的是 3.9–3.12），
      pip 找遍所有源也不会有匹配的 wheel，和网络无关。
解法：python -c "import sys; print(sys.version)" 先确认解释器版本；用区间内的 Python 建 venv 再装，
      或显式安装与当前 Python 匹配的 TF 版本；不要在这个情况下反复换镜像源，那是浪费时间的错误方向。

坑 2：装了 GPU 构建、nvidia-smi 也认卡，但 list_physical_devices('GPU') 返回 []
结论：认定 TensorFlow 有 bug 或 wheel 装错，开始重装。
原因：GPU 是否可用由三件事共同决定：wheel 是否为 CUDA 构建（is_cuda_build）、系统驱动是否满足
      版本下限（Linux >= 525.60.13）、pip 版 CUDA 库与系统 CUDA 是否冲突。
解法：按顺序排查 is_cuda_build -> 系统驱动版本 -> NVIDIA 库是否有冲突；冲突时按官方文档在
      TensorFlow 包目录里建 .so 符号链接并补 $VIRTUAL_ENV/bin/ptxas。

坑 3：nvidia-smi 报 "Failed to initialize NVML: Driver/library version mismatch"
结论：以为显卡坏了或 TF 装错了，开始折腾 PyPI 上的 CUDA 包。
原因：NVIDIA 内核模块版本与用户态库（libnvidia-ml.so）版本不一致，通常是升级过驱动但没重启，
      或部分组件来自旧版本包。
解法：先 lsmod | grep nvidia 看当前加载的模块版本，再对比驱动包版本；重启或重装同版本驱动，
      两边一致后 nvidia-smi 才可用。这一步没过之前，任何 GPU 框架都不可用（本机即此状态）。

坑 4：在 import tensorflow 之后设置可见设备/逻辑设备，抛 RuntimeError
结论：以为 API 用法写错了，翻文档找不到原因。
原因：设备配置只能在设备初始化之前生效，而「初始化」发生在第一个算子执行时（不是 import 时）。
      本机实测报错原文：Virtual devices cannot be modified after being initialized。
解法：把所有 tf.config 设备设置集中在脚本最开头、任何张量运算之前；已经跑到一半只能新起进程。
      只做实验时也可以在入口处用 CUDA_VISIBLE_DEVICES 或 tf.config.set_visible_devices 统一处理。

坑 5：老教程的 Keras 代码在新环境全线报错（AttributeError / 参数不认识）
结论：怀疑 TensorFlow 2.20 不兼容，考虑降级。
原因：TensorFlow 2.16 起默认安装 Keras 3，而 Keras 3 是重写过的多后端框架，大量 Keras 2 的
      参数名与默认行为已变更。
解法：先确认 keras.__version__；需要 Keras 2 行为时 pip install tf_keras 并设置
      TF_USE_LEGACY_KERAS=1（必须在 import tensorflow 之前），或按 Keras 3 文档改写；
      不要把降级 TensorFlow 当成第一手段。

坑 6：换了台机器训练速度掉了数倍，但代码一行没改
结论：怀疑模型或数据有问题，开始 profiling 找瓶颈。
原因：设备不同（GPU 变 CPU）或批大小未随之调整，也可能是多进程场景下没开 memory_growth 导致
      显存争抢；这类问题在日志里完全看不出来。
解法：把设备信息与 is_cuda_build 打进训练日志，训练前打印 list_physical_devices；
      用「设备探测决定批大小」的写法让脚本自适应，性能差异才可归因。
```
