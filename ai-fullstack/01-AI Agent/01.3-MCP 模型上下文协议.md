## 概述

MCP（Model Context Protocol）是 Anthropic 提出的开放协议，用于把「外部数据与工具」以标准方式接进任意 AI 应用：客户端连上一个 MCP Server 后，就能发现并调用它暴露的工具、读取资源、使用提示词模板，而不必为每个应用各写一套集成代码。它基于 JSON-RPC 2.0，规范由 data layer（协议语义）与 transport layer（stdio / Streamable HTTP）两层组成，思路对标 Language Server Protocol——把 M×N 的对接问题收敛成 M+N。

```text
全篇主线：
1. 定位 —— 统一「AI 应用 ↔ 外部能力」的协议，解决集成爆炸
2. 角色 —— Host 里为每个 Server 起一个 Client，Server 提供三类原语
3. 原语 —— Tools 供模型执行动作、Resources 提供上下文数据、Prompts 提供模板
4. 传输 —— stdio 走本机子进程，Streamable HTTP 走远程单端点
5. 落地 —— 写一个 Server、接一个 Host、用巡检脚本盯住可用性
```

## MCP 定位与解决的问题

没有 MCP 时，每个 AI 应用要支持 N 个外部系统就得写 N 套适配：IDE 一套、桌面客户端一套、自研 Agent 一套，工具定义、鉴权、错误语义各不相同。MCP 把这件事变成协议问题——数据源方实现一次 Server，任何支持 MCP 的 Host 都能用。规范只覆盖「上下文交换」，不管 AI 应用如何使用模型、如何管理上下文，这也是它能同时适配桌面客户端、IDE、自建 Agent 的原因。

规范的关键设计点（以官方规范最新修订版为准）：

| 设计点 | 内容 |
|--------|------|
| 消息编码 | JSON-RPC 2.0，要求 UTF-8 |
| 协议分层 | data layer（语义）+ transport layer（帧格式与鉴权） |
| 会话模型 | 最新修订版为无状态：每个请求在 `_meta` 里携带协议版本与能力；早期版本用 `initialize` 建立连接级会话 |
| 能力发现 | 最新修订版通过 `server/discover` 查询服务端支持的协议版本与能力；早期版本在 `initialize` 握手中协商 |
| 扩展 | 可选扩展（Tasks、Skills over MCP、MCP Apps 等），需双方显式支持 |
| 安全原则 | 用户明确同意、数据隐私、工具调用视为任意代码执行并需确认 |

```text
要解决的问题（按重要性）：
1. 集成爆炸 —— 每个应用对接每个数据源都要写适配，MCP 把它变成实现一次 Server
2. 语义不统一 —— 工具描述、资源结构、错误码各有各的写法定标准
3. 能力发现 —— 客户端可动态列出工具与资源（*/list），服务端变化无需重新发布客户端
4. 上下文分发 —— Resources 让「数据」与「动作」分离，读数据不等于有副作用
5. 复用 —— 同一个 Server 可同时被桌面客户端、IDE、自建 Agent 使用
```

早期版本的握手报文是这样的（本机 SDK 实测，`initialize` 得到服务端能力与协议版本）：

```json
// 请求
{"jsonrpc": "2.0", "id": 1, "method": "initialize",
 "params": {"protocolVersion": "2025-06-18", "capabilities": {},
            "clientInfo": {"name": "curl", "version": "1.0"}}}
```

```json
// 响应（本机 mcp 2.3.0 实测的真实返回）
{"jsonrpc": "2.0", "id": 1,
 "result": {"capabilities": {"prompts": {"listChanged": false},
                             "resources": {"listChanged": false, "subscribe": false},
                             "tools": {"listChanged": false}},
            "protocolVersion": "2025-06-18",
            "serverInfo": {"name": "demo-http-server", "version": "0.1.0"}}}
```

最新修订版（2026-07-28）改成了无状态风格：请求自带协议版本与客户端能力，服务端通过 `server/discover` 暴露支持版本。两代实现的差异需要在接入时按对方声明的版本确认。

```json
// 最新修订版风格：能力与版本随每个请求走（官方规范示例结构）
{"jsonrpc": "2.0", "id": 5, "method": "tools/list",
 "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientInfo": {"name": "example-client", "version": "1.0.0"},
                      "io.modelcontextprotocol/clientCapabilities": {"elicitation": {}}}}}
```

## Host Client 与 Server 三者关系

MCP 是客户端-服务端架构，三个角色边界清晰：**Host** 是 AI 应用本身（桌面客户端、IDE、自研 Agent），负责编排模型与多个数据源；**Client** 是 Host 内部为每个 Server 建立并维护连接的组件，一个 Server 一个 Client；**Server** 是提供上下文与能力的程序，可以跑在本地（stdio）也可以跑在远端（Streamable HTTP）。这种一对一映射是隔离的基础：某个 Server 挂掉或超时，不应影响其他 Server 的连接与工具列表。

| 角色 | 职责 | 典型示例 | 数量关系 |
|------|------|----------|----------|
| Host | 编排模型、聚合多个 Server 的能力、用户同意流程 | Claude Desktop、VS Code、自建 Agent | 1 个 Host |
| Client | 维持与某个 Server 的连接、转发请求与通知 | Host 内部对象，通常不暴露给用户 | 每个 Server 一个 |
| Server | 暴露 Tools / Resources / Prompts，执行实际逻辑 | 文件系统 Server、数据库 Server、内部订单 Server | 1 个 Server 可服务多个 Client（HTTP 除外，stdio 通常一对一） |

Host 侧接入通常就是一段配置：声明用哪个命令启动 Server、传什么参数、给什么环境变量。

```json
// Claude Desktop 配置（Linux: ~/.config/Claude/claude_desktop_config.json；macOS: ~/Library/Application Support/Claude/）
{
  "mcpServers": {
    "weather": {
      "command": "uv",
      "args": ["--directory", "/ABSOLUTE/PATH/TO/PARENT/FOLDER/weather", "run", "weather.py"]
    },
    "orders": {
      "command": "python3",
      "args": ["/opt/mcp-servers/orders/server.py"],
      "env": {"ORDER_DB_DSN": "postgresql://reader@db:5432/orders"}
    }
  }
}
```

```text
角色关系要点：
1. Server 指「提供上下文的程序」，与物理位置无关：本地 stdio 与远端 HTTP 都是 Server
2. 每个 Server 一个 Client 连接，隔离故障域；不要让一个 Server 的异常拖垮 Host
3. stdio Server 通常服务单个 Client（被客户端作为子进程拉起），HTTP Server 服务多个
4. Host 必须实现用户同意流程：调用工具前用户应知情并可拒绝
5. 工具描述与注解应视为不可信输入，除非 Server 本身可信（规范安全原则）
```

## Resources Tools 与 Prompts 三类原语

Server 可以向 Client 暴露三类原语，区分依据是「这是数据、动作还是模板」：**Resources** 是类似文件的数据源，供客户端读取上下文（数据库 schema、配置、文档内容）；**Tools** 是可被模型调用的函数，可能产生副作用，需要用户同意；**Prompts** 是可复用的交互模板，帮助用户组织特定任务（如「生成周报」「排查订单异常」）。每类原语都有对应的发现方法与读取/执行方法，列表是动态的——Server 可以在运行时增删。

| 原语 | 用途 | 主要方法 | 是否有副作用 | 由谁触发 |
|------|------|----------|--------------|----------|
| Resources | 提供上下文数据 | `resources/list`、`resources/read`、`resources/templates/list` | 通常无 | 客户端/用户选择 |
| Tools | 执行动作、取数、改状态 | `tools/list`、`tools/call` | 可能有 | 模型决策 + 用户同意 |
| Prompts | 交互模板 | `prompts/list`、`prompts/get` | 无 | 用户显式选择 |
| Elicitation（客户端原语） | 服务端向用户追问信息或请求确认 | `elicitation/create` | 无 | 服务端发起 |

早期规范里还有 Sampling（服务端反向请求模型补全）等客户端原语，最新修订版已将其标记为废弃；写新代码时不要依赖它。下面是在同一个 Server 里声明三类原语的代码（完整可运行版本见下一节）。

```python
@mcp.tool()
def query_order(order_id: str) -> dict:
    """按订单号查询订单状态。

    Args:
        order_id: 订单号，例如 A1001
    """
    return {"order_id": order_id, "status": "shipped"}


@mcp.resource("config://env")
def env_info() -> str:
    """当前运行环境信息，作为只读 Resource 暴露。"""
    return json.dumps({"python": platform.python_version()})


@mcp.prompt()
def diagnose_order(order_id: str) -> str:
    """订单异常排查提示词模板。

    Args:
        order_id: 订单号
    """
    return f"请先调用 query_order 查询订单 {order_id}，再判断是否需要人工介入。"
```

客户端侧对应的发现与调用（本机实测输出）：

```text
tools: ['add', 'query_order']
resources: ['config://env']
prompts: ['diagnose_order']
```

```text
三类原语要点：
1. 数据用 Resources、动作用 Tools，不要把所有东西都做成 Tool（读数据不该有副作用）
2. 工具的 docstring 与类型标注会被 SDK 转成 JSON Schema，描述质量直接决定调用准确率
3. 列表方法（*/list）是动态的，Server 运行时可变更能力，客户端要能刷新
4. Prompts 适合固化的多步流程，把「怎么问」沉淀成模板，避免用户每次手写
5. 需要向用户追问或确认时，用规范的客户端原语（Elicitation）而不是让工具返回一句「请补充信息」
```

## stdio 与 Streamable HTTP 传输

传输层只管帧格式与连接，协议语义在所有传输上完全一致。**stdio** 由客户端把 Server 作为子进程拉起，通过标准输入输出交换消息：消息以换行分隔，Server 绝对不可以往 stdout 写任何非 MCP 消息（`print` 会直接破坏协议），日志必须走 stderr。**Streamable HTTP** 用于远程场景：客户端对单个 MCP endpoint 发 HTTP POST，响应可以是普通 JSON，也可以是请求级 SSE 流，服务端可分配会话并支持断线续传。它是从协议版本 2024-11-05 的 HTTP+SSE 传输演化而来，官方明确 Streamable HTTP 替代了旧的 HTTP+SSE。

| 维度 | stdio | Streamable HTTP |
|------|-------|-----------------|
| 连接建立 | 客户端拉起子进程，读写其 stdin/stdout | HTTP POST 到 MCP endpoint，可选 GET 开 SSE 流 |
| 消息分隔 | 换行分隔的 JSON-RPC，消息内不得含换行 | 每个消息一次 POST，响应 JSON 或 SSE 流 |
| 日志 | 只能写 stderr | 常规 stdout 日志不影响 HTTP 响应 |
| 并发/共享 | 通常一对一（一个客户端一个子进程） | 一个 Server 服务多个客户端 |
| 会话 | 连接即会话 | 可由服务端分配 `Mcp-Session-Id`，客户端后续请求必须携带 |
| 鉴权 | 依靠进程环境与文件权限 | 支持 HTTP 鉴权（推荐 OAuth 获取令牌）、必须校验 `Origin`、本地部署只绑 127.0.0.1 |
| 适用 | 本地文件、本机数据库、开发调试 | 内网/云端共享服务、多客户端复用 |

用同一份 Server 代码切到 HTTP 只需改 `run` 的传输参数：

```python
"""以 Streamable HTTP 方式运行同一个 MCP Server（监听 127.0.0.1:8765）。"""
import sys

from mcp.server import MCPServer

mcp = MCPServer(name="demo-http-server", version="0.1.0")


@mcp.tool()
def add(a: float, b: float) -> float:
    """两数相加。

    Args:
        a: 第一个加数
        b: 第二个加数
    """
    return a + b


if __name__ == "__main__":
    print("listening on http://127.0.0.1:8765/mcp", file=sys.stderr)
    mcp.run(transport="streamable-http", host="127.0.0.1", port=8765)
```

再用标准库走完整流程：`initialize` 拿到会话 id，通知返回 202，`tools/list` 与 `tools/call` 都通过 SSE 返回（本机实测）。

```python
"""用标准库 urllib 走 Streamable HTTP：initialize -> tools/list -> tools/call。"""
import json
import urllib.request

URL = "http://127.0.0.1:8765/mcp"
HEADERS = {"Content-Type": "application/json", "Accept": "application/json, text/event-stream"}
SESSION: dict[str, str] = {}


def rpc(method: str, params: dict | None = None, id: int | None = 1) -> dict | None:
    body = {"jsonrpc": "2.0", "method": method, "params": params or {}}
    if id is not None:
        body["id"] = id
    req = urllib.request.Request(URL, data=json.dumps(body).encode(), headers={**HEADERS, **SESSION})
    with urllib.request.urlopen(req, timeout=10) as resp:
        sid = resp.headers.get("mcp-session-id")
        if sid:
            SESSION["mcp-session-id"] = sid                 # 服务端分配会话，后续请求必须带上
        raw = resp.read().decode()
        print(f"<- {method}: HTTP {resp.status} content-type={resp.headers.get('content-type')}")
        for line in raw.splitlines():
            if line.startswith("data: "):
                return json.loads(line[6:])
        return None


if __name__ == "__main__":
    print("initialize ->", rpc("initialize", {
        "protocolVersion": "2025-06-18", "capabilities": {},
        "clientInfo": {"name": "stdlib-client", "version": "1.0"}}))
    rpc("notifications/initialized", id=None)               # 通知无 id，服务端返回 202
    tools = rpc("tools/list", id=2)
    print("tools/list ->", [t["name"] for t in tools["result"]["tools"]])
    print("tools/call ->", rpc("tools/call", {"name": "add", "arguments": {"a": 2, "b": 3.5}}, id=3)["result"])
```

```text
<- initialize: HTTP 200 content-type=text/event-stream
initialize -> {'jsonrpc': '2.0', 'id': 1, 'result': {'capabilities': {'prompts': {'listChanged': False}, 'resources': {'listChanged': False, 'subscribe': False}, 'tools': {'listChanged': False}}, 'protocolVersion': '2025-06-18', 'serverInfo': {'name': 'demo-http-server', 'version': '0.1.0'}}}
<- notifications/initialized: HTTP 202 content-type=application/json
<- tools/list: HTTP 200 content-type=text/event-stream
tools/list -> ['add']
<- tools/call: HTTP 200 content-type=text/event-stream
tools/call -> {'content': [{'text': '5.5', 'type': 'text'}], 'isError': False, 'structuredContent': {'result': 5.5}}
```

```text
传输要点：
1. stdio Server 严禁向 stdout 写非协议内容，日志一律 logging 到 stderr
2. HTTP 传输必须校验 Origin、只绑 127.0.0.1（本地）并做鉴权，否则存在 DNS 重绑风险
3. 服务端分配会话后，客户端所有后续请求都要带 Mcp-Session-Id，否则会被拒
4. 通知类消息（无 id）服务端返回 202 Accepted，不要当成错误
5. 旧版 HTTP+SSE（2024-11-05）与新版 Streamable HTTP 并存期，客户端需按端点行为探测后再选定
```

## 实现一个 MCP Server

写 Server 的现代做法是用官方 SDK 的装饰器风格：声明工具、资源、提示词三类原语，类型标注与文档字符串自动转成 Schema。Python SDK 的类在 2.x 里从 FastMCP 改名为 `MCPServer`（`from mcp.server import MCPServer`），官方文档要求使用 2.0.0 及以上版本；本机实测版本是 mcp 2.3.0。stdio 模式下日志必须走 stderr，否则会破坏 JSON-RPC 消息。

```python
"""真实可跑的 MCP Server 示例（mcp 2.x Python SDK）：计算器 + 系统信息工具。"""
import json
import logging
import platform
import sys

from mcp.server import MCPServer

logging.basicConfig(level=logging.INFO, stream=sys.stderr)  # STDIO 下日志必须走 stderr
logger = logging.getLogger("demo-server")

mcp = MCPServer(name="demo-server", version="0.1.0")

# 模拟的业务数据源
ORDERS = {
    "A1001": {"status": "shipped", "amount": 128.5, "carrier": "SF"},
    "A1002": {"status": "pending", "amount": 42.0, "carrier": None},
}


@mcp.tool()
def add(a: float, b: float) -> float:
    """两数相加。

    Args:
        a: 第一个加数
        b: 第二个加数
    """
    return a + b


@mcp.tool()
def query_order(order_id: str) -> dict:
    """按订单号查询订单状态。

    Args:
        order_id: 订单号，例如 A1001
    """
    logger.info("query_order %s", order_id)
    order = ORDERS.get(order_id)
    if order is None:
        return {"error": "not_found", "order_id": order_id}
    return {"order_id": order_id, **order}


@mcp.resource("config://env")
def env_info() -> str:
    """当前运行环境信息，作为只读 Resource 暴露给客户端。"""
    return json.dumps({"python": platform.python_version(), "platform": platform.platform()},
                      ensure_ascii=False)


@mcp.prompt()
def diagnose_order(order_id: str) -> str:
    """订单异常排查提示词模板。

    Args:
        order_id: 订单号
    """
    return f"请先调用 query_order 查询订单 {order_id}，再判断是否需要人工介入，并给出处理建议。"


if __name__ == "__main__":
    mcp.run(transport="stdio")
```

依赖与运行方式（官方推荐用 uv 管理项目，Python 3.10 及以上）：

```shell

```

写完后先用官方 SDK 的客户端连一遍，确认三类原语都能发现与调用（本机实测输出见下）。这段代码用的是会话式客户端 API：`stdio_client` 负责拉起子进程，`ClientSession` 负责协议交互。

```python
"""真实可跑的 MCP Client：以 stdio 方式启动 server.py，列出并调用工具/资源/提示词。"""
import asyncio
import json
import sys

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client


async def main() -> None:
    params = StdioServerParameters(
        command=sys.executable,
        args=[r"/root/.hermes/cache/scratch/mcp_demo/server.py"],
    )
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()

            tools = await session.list_tools()
            print("tools:", [t.name for t in tools.tools])

            res = await session.call_tool("add", {"a": 1.5, "b": 2.25})
            print("call add ->", res.structured_content or res.content)

            res = await session.call_tool("query_order", {"order_id": "A1001"})
            print("call query_order ->", res.content[0].text)

            res = await session.call_tool("query_order", {"order_id": "A9999"})
            print("call query_order(缺失单号) ->", res.content[0].text)

            resources = await session.list_resources()
            print("resources:", [str(r.uri) for r in resources.resources])
            content = await session.read_resource("config://env")
            print("read config://env ->", content.contents[0].text)

            prompts = await session.list_prompts()
            print("prompts:", [p.name for p in prompts.prompts])
            got = await session.get_prompt("diagnose_order", {"order_id": "A1002"})
            print("get_prompt ->", got.messages[0].content.text)


if __name__ == "__main__":
    asyncio.run(main())
```

## MCP 客户端接入与故障排查

把已有 Server 接进 Host，多数情况只改配置；要写自己的 Host 时，官方 SDK 提供了更高层的 `Client`（`async with` 即生命周期，省掉手工握手），这也是官方最新文档的推荐写法。

```python
"""官方最新文档风格的高层 Client 写法（mcp 2.x），本地实测。"""
import asyncio
import sys

from mcp import Client, StdioServerParameters
from mcp.client.stdio import stdio_client

SERVER = r"/root/.hermes/cache/scratch/mcp_demo/server.py"


async def main() -> None:
    params = StdioServerParameters(command=sys.executable, args=[SERVER])
    async with Client(stdio_client(params)) as client:
        tools = await client.list_tools()
        print("tools:", [t.name for t in tools.tools])
        result = await client.call_tool("query_order", {"order_id": "A1002"})
        print("call_tool is_error:", result.is_error)
        print("call_tool content:", result.content[0].text)
        env = await client.read_resource("config://env")
        print("resource:", env.contents[0].text)


if __name__ == "__main__":
    asyncio.run(main())
```

```text
tools: ['add', 'query_order']
call_tool is_error: False
call_tool content: {
  "order_id": "A1002",
  "status": "pending",
  "amount": 42.0,
  "carrier": null
}
resource: {"python": "3.14.7", "platform": "Linux-7.0.0-28-generic-x86_64-with-glibc2.39"}
```

排查顺序建议固定下来：先单独跑 Server 看能否启动，再用官方 Inspector 或自写客户端连一遍，最后才怀疑 Host 配置。常见现象与病因对照如下。

| 现象 | 常见原因 | 处理 |
|------|----------|------|
| Host 里看不到 Server 的工具 | 配置文件语法错误、路径用了相对路径、没完全重启 Host | 校验 JSON、改绝对路径、彻底退出应用再启动 |
| 工具调用静默失败 | Server 崩溃、写 stdout 污染了协议、依赖缺失 | 看 Host 日志目录里的 `mcp-server-<名字>.log`（stderr 内容） |
| 连接超时/首次很慢 | Server 冷启动慢、依赖首次下载 | 预热（提前 uv sync / pip install）、减小启动依赖 |
| HTTP 方式连不上 | 未带会话 id、未校验 Origin、端口未放行、绑在 127.0.0.1 之外被拦 | 检查 `Mcp-Session-Id` 与协议版本头、绑本地、放行端口并加鉴权 |
| 调用报权限/参数错误 | 工具描述不清导致参数编造、鉴权信息未注入 | 补参数描述与枚举、用 env 注入凭据、服务端二次校验 |

```shell
# Claude Desktop 的 MCP 相关日志（Linux）
tail -n 20 -f ~/.config/Claude/logs/mcp*.log

# 彻底重启 Host，仅关闭窗口不会重载配置
pkill -f claude-desktop
```

```text
接入与排查要点：
1. 配置里一律用绝对路径，相对路径在不同启动方式下解析结果不同
2. 改配置后必须完全退出 Host 再启动，窗口关闭不等于进程退出
3. stdio Server 的 stderr 会落到 Host 日志，把关键日志写在 stderr 上便于排查
4. 官方提供 MCP Inspector 用于交互式调试（见 github.com/modelcontextprotocol/inspector，启动命令以官方文档为准）
5. 工具调用失败优先看 `result.is_error`，不要等异常抛出——工具内部错误通常不抛异常
```

## 应用场景实战

### 场景一：把内部订单系统封装成 MCP Server 并接入桌面 Host

订单查询是典型的「数据 + 动作」混合场景：查订单是只读数据，取消订单是有副作用动作。做法是把它拆成 Resource（订单 schema 与枚举定义）、只读 Tool（查询）与 Prompt（异常排查模板），让模型少猜、用户可控。Server 代码即上文「实现一个 MCP Server」一节的完整版本，部署时把数据源换成真实数据库连接。

```shell
# 1) 建项目并安装依赖
uv init orders-mcp && cd orders-mcp
uv add "mcp[cli]" "psycopg[binary]"

# 2) 先单独启动，确认能在 stdio 下正常握手（无输出即为正常，协议消息走管道）
uv run server.py

# 3) 写进桌面 Host 的配置
mkdir -p ~/.config/Claude
cat >> ~/.config/Claude/claude_desktop_config.json <<'EOF'
{
  "mcpServers": {
    "orders": {
      "command": "uv",
      "args": ["--directory", "/opt/mcp-servers/orders-mcp", "run", "server.py"],
      "env": {"ORDER_DB_DSN": "postgresql://reader@db:5432/orders"}
    }
  }
}
EOF

# 4) 完全重启 Host 后验证：日志里应能看到 list_tools 的往返
tail -n 20 ~/.config/Claude/logs/mcp-server-orders.log
```

```text
上线检查清单：
1. 数据源用只读账号，写操作单独开工具并走审批
2. Server 的 Resources 里给出字段枚举与示例，减少模型编造参数
3. 每个工具都返回结构化错误而不是抛异常，Host 才能把错误展示给用户
4. 凭据只通过 env 注入，不写进仓库与配置示例
5. 在 Host 里手动验一次「正常查询」「查询不存在订单」「越权字段」三类调用
```

### 场景二：自建 MCP Client 做批量工具巡检

Server 数量一多，接入方最怕的是「某个 Server 悄悄挂了或改了工具名」。工程做法是把巡检写进 CI 或定时任务：对每个已登记 Server 建立连接，列出三类原语，对无副作用的读工具做一次冒烟调用，输出 JSON 报告，异常直接让任务失败。

```python
"""自建 MCP Client 做工具巡检 —— 连上 server 后列出工具并冒烟调用，输出 JSON 报告。"""
import asyncio
import json
import sys
import time

from mcp import Client, StdioServerParameters
from mcp.client.stdio import stdio_client

SERVERS = {
    "demo": StdioServerParameters(
        command=sys.executable,
        args=[r"/root/.hermes/cache/scratch/mcp_demo/server.py"],
    ),
}


async def probe(name: str, params: StdioServerParameters) -> dict:
    report: dict = {"server": name, "ok": False, "tools": [], "resources": [], "prompts": [], "errors": []}
    started = time.perf_counter()
    try:
        async with Client(stdio_client(params)) as client:
            tools = (await client.list_tools()).tools
            report["tools"] = [t.name for t in tools]
            report["resources"] = [str(r.uri) for r in (await client.list_resources()).resources]
            report["prompts"] = [p.name for p in (await client.list_prompts()).prompts]

            # 冒烟调用：只调用无副作用且必填参数已知的读工具
            res = await client.call_tool("add", {"a": 1, "b": 1})
            report["smoke"] = {"tool": "add", "is_error": res.is_error, "text": res.content[0].text}
            report["ok"] = True
    except Exception as exc:
        report["errors"].append(f"{type(exc).__name__}: {exc}")
    report["latency_ms"] = round((time.perf_counter() - started) * 1000)
    return report


async def main() -> None:
    reports = [await probe(n, p) for n, p in SERVERS.items()]
    print(json.dumps(reports, ensure_ascii=False, indent=2))
    bad = [r["server"] for r in reports if not r["ok"]]
    print("巡检结论:", "全部正常" if not bad else f"异常 server: {bad}")
    sys.exit(1 if bad else 0)


if __name__ == "__main__":
    asyncio.run(main())
```

```text
[
  {
    "server": "demo",
    "ok": true,
    "tools": [
      "add",
      "query_order"
    ],
    "resources": [
      "config://env"
    ],
    "prompts": [
      "diagnose_order"
    ],
    "errors": [],
    "smoke": {
      "tool": "add",
      "is_error": false,
      "text": "2.0"
    },
    "latency_ms": 946
  }
]
巡检结论: 全部正常
```

```text
巡检落地要点：
1. 报告落盘或入库，记录每次的工具清单快照，工具改名/消失时能立刻发现
2. 冒烟调用只挑无副作用的读工具，绝不在巡检里调用写工具
3. 用退出码表达结果（异常时非 0），直接接进 CI 或定时任务
4. 记录连接耗时，冷启动变慢往往是依赖漂移的信号
5. HTTP Server 的巡检另加鉴权与网络连通性检查，不要混在同一条用例里
```

## 最佳实践与踩坑记录

### 最佳实践

1. 数据与动作分开建模：只读数据放 Resources，可能有副作用的操作放 Tools，模板放 Prompts。
2. 工具描述写清用途、参数格式、返回值与不适用场景，它会直接转成 JSON Schema 影响调用准确率。
3. stdio Server 全程用 logging 输出到 stderr，代码里禁止出现 `print`。
4. 本地用 stdio，跨机共享用 Streamable HTTP；HTTP 必须校验 `Origin`、绑定 127.0.0.1（本地）并加鉴权。
5. 配置文件里用绝对路径，改完配置完全重启 Host。
6. 工具内部错误返回结构化结果（`is_error` 或 error 字段），不要依赖异常传递。
7. 给每个 Server 建巡检：列出工具清单快照 + 无副作用冒烟调用，接进 CI。
8. 凭据通过环境变量注入，工具描述与注解在不可信 Server 场景下按提示注入风险对待。

### 踩坑记录

```text
坑 1：在 stdio Server 里 print 调试信息
结论：Host 报解析错误，工具全部不可用，且日志里看不出是打印惹的祸。
原因：stdout 是 JSON-RPC 通道，任何非协议输出都会破坏消息帧。
解法：改用 logging 输出到 stderr；代码评审时禁止 stdio Server 内出现 print。

坑 2：配置里写了相对路径，Host 里看不到 Server
结论：桌面客户端启动 Server 失败，工具列表为空，界面无任何提示。
原因：Host 的工作目录与终端不同，相对路径解析到别处。
解法：一律写绝对路径，先在终端用同一条命令手工跑通，再写进配置。

坑 3：改了配置但没生效
结论：反复改配置无效，以为协议不兼容。
原因：只关闭了窗口，Host 进程还活着，配置未重新加载。
解法：完全退出应用（或 pkill 对应进程）后再启动；排查时先看 Host 日志时间戳。

坑 4：HTTP 传输没带会话 id 或协议版本头
结论：后续请求返回 400/404，工具调用全部失败。
原因：服务端在 initialize 响应里分配了 Mcp-Session-Id，客户端没有回传。
解法：客户端保存会话 id 并在所有后续请求携带；服务端返回 404 时重建会话。

坑 5：把写操作也暴露成工具却没有确认流程
结论：模型一次误判就改了生产数据。
原因：Host 侧未实现用户同意，Server 侧没有权限分级。
解法：Host 必须提供工具调用确认；Server 侧写工具单独开关、用只读账号兜底、加幂等键。

坑 6：Server 冷启动慢导致首次调用超时
结论：第一次工具调用超时，之后正常，用户认为系统不稳定。
原因：子进程首次运行要解析依赖或建连数据库。
解法：预热（提前 uv sync / 连接池预热）、把重型初始化移出请求路径、给 Host 侧超时留足余量。
```
