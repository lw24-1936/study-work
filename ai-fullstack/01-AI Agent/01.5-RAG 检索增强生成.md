## 概述

RAG（Retrieval-Augmented Generation，检索增强生成）在生成之前先检索外部知识，把「检索到的原文片段」拼进提示词，让模型基于事实作答，从而解决大模型的「知识冻结」（训练数据有截止日期）与「上下文有限」（无法一次读入整个语料库）两个硬伤。它是当前企业落地 LLM 最主流、性价比最高的架构，本质是「用检索把私有知识注入上下文」。

```text
RAG 的三条主线：
1. 离线索引 —— 加载 -> 切分 -> 向量化 -> 入库，决定「能不能召回到」
2. 在线检索 —— 查询改写 -> 多路召回 -> 融合重排 -> 组装上下文，决定「召回得多准」
3. 生成与评估 —— 提示组装 -> 生成 -> 事实核对与指标回归，决定「答得对不对」
```

## RAG 流水线与各环节职责

一条完整的 RAG 流水线分「离线索引」和「在线查询」两段。离线段把非结构化文档转成可检索的向量索引，职责是「覆盖度」；在线段把用户问题变成检索请求、再把候选文档喂给模型，职责是「精确度与忠实度」。理解这条流水线的价值在于：任何一次答错，都能定位到是「没召回」「召回错」还是「召回对但没用好」——这是排查 RAG 的唯一起点。

```text
离线索引与在线查询的职责划分：
1. 加载 Document Loader —— PDF/HTML/Markdown/数据库，统一成 Document(text, metadata)
2. 切分 Text Splitter —— 把长文档切成可单独召回、且能塞进上下文窗口的块
3. 向量化 Embedding —— 文本 -> 稠密向量，语义相近的向量距离相近
4. 入库 Vector Store —— 存储向量 + 原文 + 元数据，支持相似度检索与元数据过滤
5. 查询改写 Query Rewrite —— 把口语化问题改成适合检索的查询（可多路）
6. 召回 Retrieve —— 稠密检索 + 稀疏检索并行，各取 Top-K
7. 融合重排 Rerank —— RRF 融合多路结果，再用交叉编码器精排
8. 组装生成 Generate —— 把 Top-N 片段拼进提示词，要求模型「只依据上下文作答」
```

一个最小但完整的流水线骨架（离线建库 + 在线问答），依赖 `langchain-text-splitters` 与 `chromadb`：

```shell
# 依赖安装（Python 3.10+；版本以官方文档为准）
python3 -m venv .venv && source .venv/bin/activate
pip install -U chromadb langchain-text-splitters
```

```python
# pipeline.py：离线索引 + 在线检索的最小骨架
import chromadb
from langchain_text_splitters import RecursiveCharacterTextSplitter

RAW_DOCS = {
    "手册.md": "退款政策：签收后 7 天内可无理由退款。\n\n发票问题请联系财务。",
    "faq.md": "发货时效：现货 24 小时内发出，预售商品以页面为准。",
}

client = chromadb.PersistentClient(path="./chroma_db")
col = client.get_or_create_collection(name="kb")

splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=80)
ids, texts, metas = [], [], []
for name, body in RAW_DOCS.items():
    for i, chunk in enumerate(splitter.split_text(body)):
        ids.append(f"{name}-{i}")
        texts.append(chunk)
        metas.append({"source": name, "chunk": i})
col.add(ids=ids, documents=texts, metadatas=metas)


def retrieve(query: str, k: int = 3, source: str | None = None):
    where = {"source": source} if source else None
    return col.query(query_texts=[query], n_results=k, where=where)


if __name__ == "__main__":
    res = retrieve("多久能退款？", k=2)
    for doc, meta, dist in zip(res["documents"][0], res["metadatas"][0], res["distances"][0]):
        print(f"[{meta['source']}] dist={dist:.4f} {doc}")
```

要点：

- 离线段与在线段必须解耦：索引重建走批处理，在线查询走低延迟路径
- 每个 chunk 必须带元数据（来源、页码/章节、更新时间），否则答错时无法溯源
- 检索与生成是两个可独立优化的模块，别在一次改动里同时动两边
- 上下文窗口不是越大越好：塞入无关片段会引入噪声、拉高成本并诱发幻觉
- 元数据过滤（按租户、按文档类型）是「检索正确性」的第一道闸门，优先于调相似度阈值

## 文档切分策略

切分（chunking）决定召回粒度，是 RAG 中收益最高也最容易被忽视的一环。块太大，一个向量要平均多段语义，相似度被稀释、噪声变多；块太小，一句话被切断，指代丢失、上下文不完整。实践中的默认组合是「递归切分 + 结构化分隔符 + 适度重叠」，对代码、Markdown、表格这类强结构文本，则应按语义边界（函数、标题、表格行）切分。

| 切分器 | 切分依据 | 适用场景 |
| --- | --- | --- |
| CharacterTextSplitter | 单一分隔符 | 结构极简单的纯文本，容易切不好 |
| RecursiveCharacterTextSplitter | 分隔符列表递归下钻 | 通用默认首选（段落/句子/词逐级退化） |
| MarkdownHeaderTextSplitter | Markdown 标题层级 | 文档站、说明手册，保留标题元数据 |
| TokenTextSplitter | token 数 | 需要严格控制上下文占用时 |
| 语义切分（SemanticChunker） | 相邻句向量相似度突变点 | 长文、话题切换频繁的语料，成本较高 |

`RecursiveCharacterTextSplitter` 的默认参数：`chunk_size=4000`、`chunk_overlap=200`、`length_function=len`、`add_start_index=False`；默认分隔符列表为 `["\n\n", "\n", " ", ""]`，即先按空行（段落）切，切不动再按换行、空格、字符逐级退化（以官方文档为准）。

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

# 中文场景：token 与字符不等价，建议按字数并用更细的分隔符列表
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,           # 相邻块重叠，避免语义被硬切断
    length_function=len,
    add_start_index=True,       # 在 metadata 里记录块在原文的起始位置，便于引用
    separators=["\n\n", "\n", "。", "！", "？", " ", ""],  # 中文句子边界补充进分隔符
)
chunks = splitter.create_documents(["..."], metadatas=[{"source": "手册.md"}])
for c in chunks:
    print(c.metadata["start_index"], len(c.page_content), c.page_content[:30])
```

下面是本机实测的递归切分核心算法输出（纯 stdlib 复现，`chunk_size=48`、`chunk_overlap=8`），可以看到它优先在空行处断开：

```text
===== 01.5 RAG：切分 + 混合检索(RRF) =====
切分块数 = 2
  chunk[0] len=46: 'RAG 由检索与生成两个阶段组成。\n\n文档切分决定召回粒度，块太大引入噪声，块太小丢上下文。'
  chunk[1] len=35: '混合检索把稠密向量召回与稀疏 BM25 召回融合，再交给重排模型精排。'
```

要点：

- 中文按字符数而非 token 数控制块长时，`chunk_size` 通常取 300-800 字，英文取 500-1200 字符
- 重叠窗口取块长的 10%-20%，太小接不上语义，太大召回重复、浪费上下文
- 表格、代码、问答对要按结构切（一行/一函数/一问一答一块），通用切分会破坏它们
- 切分时把标题、页码、URL 写进元数据，检索结果才能被引用和追溯
- 切分粒度要用评测而非直觉来定：同一套问题在几种切分下跑一遍，看 Context Recall

## Embedding 模型与向量库

Embedding 模型把文本映射成稠密向量，是「语义相似」的计算基础；向量库负责存储这些向量并做近邻检索。选型看三点：语言覆盖（中英混排是否都强）、维度与成本（维度越高越贵）、是否可私有化部署（数据敏感场景必须本地跑）。向量库则关注是否支持元数据过滤、混合检索、持久化与水平扩展。

| Embedding 模型 | 语言/场景 | 维度（以模型卡为准） | 备注 |
| --- | --- | --- | --- |
| text-embedding-3-small / -large | 多语言，托管 | 1536 / 3072 可调 | OpenAI，需联网与计费 |
| BAAI/bge-m3 | 中英多语言 | 1024 | 开源，支持稠密+稀疏+多向量 |
| BAAI/bge-large-zh-v1.5 | 中文 | 1024 | 开源，中文检索常用 |
| intfloat/multilingual-e5-large | 多语言 | 1024 | 开源，需加 query:/passage: 前缀 |
| Ollama 托管的任意 embedding 模型 | 本地 | 依模型 | 私有化首选，走本地 HTTP |

| 向量库 | 类型 | 强项 |
| --- | --- | --- |
| Chroma | 嵌入式/服务端 | 开箱即用，稠密/稀疏/混合检索 + 元数据过滤 |
| FAISS | 库（非服务） | 本地高性能近邻检索，无持久化服务 |
| Milvus / Qdrant / Weaviate | 独立服务 | 海量数据、分布式、过滤能力强 |
| pgvector | PostgreSQL 扩展 | 复用已有 PG 技术栈，事务与过滤统一 |

Chroma 的最小用法（本地持久化 + 元数据过滤 + 指定 embedding 函数）。注意 Chroma 默认会使用内置的 `all-MiniLM-L6-v2`（ONNX 版）做嵌入，中文场景建议注入自定义 embedding 函数：

```shell
pip install -U chromadb sentence-transformers   # sentence-transformers 用于注入自定义模型
```

```python
import chromadb
from chromadb.utils import embedding_functions

# 用本地 BGE 中文模型替换默认嵌入函数（模型名以官方模型卡为准）
ef = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="BAAI/bge-large-zh-v1.5"
)
client = chromadb.PersistentClient(path="./chroma_db")
col = client.get_or_create_collection(name="kb", embedding_function=ef)

col.add(
    ids=["d1", "d2"],
    documents=["退款需在签收后 7 天内申请", "发票由财务开具"],
    metadatas=[{"tenant": "shop", "type": "policy"}, {"tenant": "shop", "type": "finance"}],
)

# 只在 policy 类文档里检索该租户的内容
res = col.query(
    query_texts=["怎么退款"],
    n_results=3,
    where={"$and": [{"tenant": "shop"}, {"type": "policy"}]},
)
print(res["documents"])
```

要点：

- 入库与查询必须用同一个 embedding 模型与同一套预处理，换模型要整库重建
- 一定把元数据（租户、时间、类型）与向量一起存，检索时先过滤再算相似度
- 中英混排优先多语言模型（bge-m3、multilingual-e5），单语模型在混合语料上会掉点
- 向量库是「可替换件」：先定接口（检索/过滤/返回结构），迁移时只换适配层
- 私有化场景用 Ollama 或 sentence-transformers 本地部署 embedding，避免把原文发往第三方

## 混合检索与重排序

纯向量检索擅长语义相近但会漏掉精确关键词（编号、型号、专有名词），纯 BM25 擅长关键词但不懂同义改写。混合检索把两路召回的结果融合，再用重排模型对候选精排，是目前效果最稳的检索方案。融合常用 RRF（Reciprocal Rank Fusion）：`score = Σ 1/(k + rank)`，只看名次不看绝对分数，因此能天然融合量纲不同的两路结果（k 常取 60）。

```shell
pip install -U rank-bm25 sentence-transformers   # 稀疏召回 + 交叉编码器重排
```

```python
from collections import defaultdict
from rank_bm25 import BM25Okapi


def rrf(rank_lists, k: int = 60):
    """多路召回按名次融合，无需归一化分数。"""
    score = defaultdict(float)
    for ranks in rank_lists:
        for pos, doc_id in enumerate(ranks):
            score[doc_id] += 1.0 / (k + pos + 1)
    return sorted(score.items(), key=lambda kv: kv[1], reverse=True)


def hybrid_search(query, corpus, dense_search, top_k=3, pool=20):
    # 稀疏路：BM25
    bm25 = BM25Okapi([c.lower().split() for c in corpus])
    bm_scores = bm25.get_scores(query.lower().split())
    rank_bm = sorted(range(len(corpus)), key=lambda i: bm_scores[i], reverse=True)[:pool]
    # 稠密路：向量检索（此处由外部传入的函数提供名次）
    rank_de = dense_search(query, corpus, pool)
    fused = rrf([rank_de, rank_bm])[:top_k]
    return [(i, s, corpus[i]) for i, s in fused]
```

本机实测输出的 RRF 融合结果（两路名次一致时，靠前的文档得分更高）：

```text
BM25 分数   = [1.554, 0.0, 0.0, 0.0]
向量名次    = [0, 1, 2, 3]   BM25 名次 = [0, 1, 2, 3]
  RRF doc[0] score=0.03279 -> 混合检索把稠密向量召回与稀疏 BM25 召回融合
  RRF doc[1] score=0.03226 -> 文档切分决定召回粒度 chunk size overlap
  RRF doc[2] score=0.03175 -> RAG 由检索与生成两个阶段组成
  RRF doc[3] score=0.03125 -> 重排模型对候选文档做精排 cross encoder rerank
```

融合得到候选后，用交叉编码器（cross-encoder）对「查询-文档」对逐个打分重排，精度显著高于向量内积，但计算量大，所以只对 Top-K（如 20-50）候选跑：

```python
from sentence_transformers import CrossEncoder

# 交叉编码器逐对打分，比内积慢但更准（模型名以官方模型卡为准）
reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")
scores = reranker.predict([(query, doc) for _, _, doc in fused])
top = [d for _, d in sorted(zip(scores, [f[2] for f in fused]), key=lambda x: -x[0])][:5]
```

要点：

- 混合检索的默认形态：BM25 与向量各取 Top-20 到 Top-50，RRF 融合后交给重排
- RRF 只看名次，避免了两路分数不可比的问题，是第一版融合最省心的选择
- 重排模型只对候选精排，别对全库打分，否则延迟与成本不可接受
- 稀疏路必须分词：中文要接入 jieba 等分词器，否则 BM25 只能命中单字
- 上线前用评测对比「纯向量 / 纯 BM25 / 混合 / 混合+重排」四档，用数据选型

## 查询改写与多跳检索

用户的口语化问题往往不是好的检索查询——它可能缺主语、含指代、或需要一个中间事实才能回答。查询改写把「聊天语言」翻译成「检索语言」：多查询生成（一问变多查）、HyDE（先生成假想答案再用它检索）、查询分解（把多跳问题拆成连续子问题）、Self-Query（从自然语言里抽出结构化过滤条件）。多跳检索则用于「先查 A，再根据 A 的结果查 B」这类必须串行的问题。

```python
# 用 LLM 做查询改写与分解（结构示意；模型与 SDK 以官方文档为准）
REWRITE_PROMPT = """把下面的用户问题改写成 3 条适合检索的关键词查询，每行一条，不要编号：
问题：{q}"""


def rewrite(llm, q: str) -> list[str]:
    return [line.strip() for line in llm(REWRITE_PROMPT.format(q=q)).splitlines() if line.strip()]


def multi_query_search(query, retrieve, llm, top_k=3):
    from collections import defaultdict
    queries = [query] + rewrite(llm, query)      # 原始问题 + 多条改写一起召回
    merged = defaultdict(float)
    for q in queries:
        for rank, (doc_id, _) in enumerate(retrieve(q)):
            merged[doc_id] += 1.0 / (60 + rank + 1)   # 与混合检索共用 RRF 思路
    return sorted(merged.items(), key=lambda kv: -kv[1])[:top_k]


def decompose(llm, q: str) -> list[str]:
    """把多跳问题拆成有序子问题，逐个检索后拼起来再回答。"""
    return [s.strip() for s in llm(f"把问题拆成有序子问题：{q}").splitlines() if s.strip()]
```

```text
多跳检索的执行形态（按子问题串行）：
输入：公司去年营收最高的产品线，它的供应商是谁？
子问题1：公司去年各产品线的营收是多少？      -> 检索 -> 结论：产品线 A 最高
子问题2：产品线 A 的主要供应商是谁？          -> 检索（带子问题1的结论）-> 供应商 X
生成：把两段证据一起交给模型，要求引用来源作答
```

要点：

- 查询改写的收益在「口语化/指代多」的语料上最大，结构化查询上可能是负收益，要评测
- 多查询召回后用 RRF 融合比直接拼接结果更稳，且能顺带做去重
- HyDE 适合稀疏语料，但会引入「假想答案」的偏差，务必让生成阶段仍以真实证据为准
- 多跳检索的每个子问题都要带上前一步的结论作为上下文，否则会问偏
- 改写会增加 LLM 调用，属于「延迟换准确率」，要对延迟敏感型接口单独开关

## RAG 效果评估

RAG 的评估要拆成「检索质量」与「生成质量」两层，否则无法定位问题。检索层看「该召回的有没有召回、召回的相不相关」；生成层看「答案是否忠于证据、是否切题」。RAGAS 提供了对应的现成指标：检索侧有 Context Precision、Context Recall、Context Entities Recall、Noise Sensitivity；生成侧有 Faithfulness、Response Relevancy（答案相关性）。

| 指标 | 维度 | 回答什么问题 |
| --- | --- | --- |
| Context Precision | 检索 | 召回的片段里，相关的排得够不够靠前 |
| Context Recall | 检索 | 标准答案需要的信息，被召回了多少 |
| Noise Sensitivity | 检索 | 答案是否容易被无关噪声片段带偏 |
| Faithfulness | 生成 | 答案是否全部由检索到的证据支撑（抗幻觉） |
| Response Relevancy | 生成 | 答案是否切中用户问题 |
| Factual Correctness | 生成 | 与参考答案的事实一致性 |

```shell
pip install -U ragas   # 需要配置一个 Judge LLM（可用本地 Ollama 或托管模型）
```

```python
# eval_rag.py：离线批量评测（字段名以 ragas 官方文档为准）
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import answer_relevancy, context_precision, context_recall, faithfulness

dataset = Dataset.from_dict({
    "question": ["退款多久到账？"],
    "answer": ["签收后 7 天内可申请退款，审核通过后 3 个工作日到账。"],
    "contexts": [["退款政策：签收后 7 天内可无理由退款。到账时间约 3 个工作日。"]],
    "ground_truth": ["签收后 7 天内可申请，约 3 个工作日到账。"],
})

result = evaluate(
    dataset,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
)
print(result)          # 打印各指标分数，用于版本间回归对比
result.to_pandas().to_csv("rag_eval.csv", index=False)
```

要点：

- 先评检索再评生成：Context Recall 低就先改切分与召回，别急着调提示词
- Faithfulness 是最该盯的指标，它直接对应「幻觉」，低于阈值就不许上线
- 评测集要从真实日志里抽样并人工标注 ground_truth，闭门造车的问题集没意义
- Judge LLM 与被评模型最好不同源，且固定版本，否则分数不可比
- 把指标接进 CI，每次改动（切分/模型/提示词）跑一遍，做版本回归

### 场景一：接入本地 Ollama + Chroma 的企业知识库问答（端到端可运行）

场景：企业内网知识库问答，数据不能出网。用 Ollama 本地跑生成与嵌入，Chroma 本地持久化，混合检索提升召回。下面是一个可运行的最小服务（假设本地已有 `nomic-embed-text` 与一个对话模型，具体模型名以 `ollama list` 为准）。

```shell
# 1) 准备本地模型
ollama pull nomic-embed-text
ollama pull qwen2.5:7b

# 2) 依赖
pip install -U chromadb rank-bm25 requests
```

```python
# kb_service.py：本地 Ollama + Chroma，混合检索后生成
from collections import defaultdict

import chromadb
import requests
from rank_bm25 import BM25Okapi

OLLAMA = "http://localhost:11434"


def embed(texts: list[str]) -> list[list[float]]:
    r = requests.post(f"{OLLAMA}/api/embed",
                      json={"model": "nomic-embed-text", "input": texts}, timeout=60)
    r.raise_for_status()
    return r.json()["embeddings"]


def generate(prompt: str) -> str:
    r = requests.post(f"{OLLAMA}/api/generate",
                      json={"model": "qwen2.5:7b", "prompt": prompt, "stream": False}, timeout=300)
    r.raise_for_status()
    return r.json()["response"]


class KB:
    def __init__(self, path="./kb_db"):
        self.client = chromadb.PersistentClient(path=path)
        self.col = self.client.get_or_create_collection(name="kb")
        self.corpus: list[str] = []

    def index(self, docs: list[str], metas: list[dict]):
        self.corpus = docs
        self.col.add(ids=[f"d{i}" for i in range(len(docs))],
                     documents=docs, metadatas=metas,
                     embeddings=embed(docs))

    def search(self, query: str, top_k=3, pool=10):
        vec = embed([query])[0]
        dense = self.col.query(query_embeddings=[vec], n_results=pool)
        d_ids = [int(i[1:]) for i in dense["ids"][0]]
        bm = BM25Okapi([d.lower().split() for d in self.corpus])
        bm_scores = bm.get_scores(query.lower().split())
        b_ids = sorted(range(len(self.corpus)), key=lambda i: bm_scores[i], reverse=True)[:pool]
        fused = defaultdict(float)
        for ranks in (d_ids, b_ids):
            for rank, i in enumerate(ranks):
                fused[i] += 1.0 / (60 + rank + 1)
        top = sorted(fused.items(), key=lambda kv: -kv[1])[:top_k]
        return [self.corpus[i] for i, _ in top]

    def ask(self, query: str) -> str:
        ctx = "\n\n".join(self.search(query))
        prompt = (f"仅依据以下资料回答，资料中找不到就说不知道，并给出来源。\n\n"
                  f"资料：\n{ctx}\n\n问题：{query}\n答案：")
        return generate(prompt)


if __name__ == "__main__":
    kb = KB()
    kb.index(
        ["退款政策：签收后 7 天内可无理由退款，约 3 个工作日到账。",
         "发货时效：现货 24 小时内发出。",
         "发票由财务在 5 个工作日内开具。"],
        [{"source": "退款"}, {"source": "发货"}, {"source": "发票"}],
    )
    print(kb.ask("退款要多久到账？"))
```

### 场景二：RAG 版本上线前的离线评测回归

场景：把切分参数从 `chunk_size=800` 改成 `500`，上线前先跑离线评测回归，用数据决定是否发布。核心是把「建库 + 评测」脚本化，并对两个版本的结果做对比，设发布门槛。

```python
# regress.py：同一评测集跑两个版本，输出指标差异（结构示意）
import json

from ragas import evaluate
from ragas.metrics import context_recall, faithfulness

CONFIGS = {"v1": {"chunk_size": 800}, "v2": {"chunk_size": 500}}


def build_eval_dataset(config):
    """按该配置重建索引并逐题生成回答，返回评测用 Dataset。"""
    raise NotImplementedError


def run(config):
    ds = build_eval_dataset(config)
    score = evaluate(ds, metrics=[faithfulness, context_recall])
    return {k: float(v) for k, v in score.items()}


if __name__ == "__main__":
    report = {name: run(cfg) for name, cfg in CONFIGS.items()}
    print(json.dumps(report, ensure_ascii=False, indent=2))
    # 发布门槛：faithfulness 不降、context_recall 有提升才放行
    gate = (report["v2"]["faithfulness"] >= report["v1"]["faithfulness"]
            and report["v2"]["context_recall"] > report["v1"]["context_recall"])
    print("放行" if gate else "拦下")
```

## 最佳实践与踩坑记录

### 最佳实践

1. 先做检索、后做生成：Context Recall 不达标时，切分与召回才是瓶颈，改提示词收效甚微
2. 每个 chunk 强制带元数据（来源、页码、时间、租户），检索结果可引用、可按权限过滤
3. 混合检索 + 重排作为默认起点：BM25 与向量各取 Top-20，RRF 融合后精排
4. 入库与查询共用同一 embedding 模型与预处理，换模型时整库重建并回归评测
5. 把 faithfulness（抗幻觉）设为上线硬门槛，并接进 CI 做版本回归
6. 提示词明确要求「只依据上下文作答、找不到就说不知道、给出来源」，降低越界编造

### 踩坑记录

```text
坑 1：切分块过大导致召回不准
结论：向量把多段语义平均了，相似度被稀释，检索命中大量无关片段。
原因：chunk_size 沿用 LLM 上下文窗口的直觉，设得过大（如数万字符）。
解法：中文块长取 300-800 字，重叠 10%-20%，用 Context Precision 验证。

坑 2：只做向量检索，漏掉关键词与编号
结论：查「订单 A12345 的状态」这类含精确串的问题经常召回不到。
原因：稠密向量对专有名词、编号不敏感，语义相似不等于字面命中。
解法：加 BM25 稀疏路做混合检索，中文先接分词器，再用 RRF 融合。

坑 3：换 embedding 模型后没重建索引
结论：线上检索结果突然大面积变差，且距离分数分布异常。
原因：旧向量由旧模型生成，新查询向量与旧库不在同一向量空间。
解法：把 embedding 模型名与版本写入索引元数据，不一致则拒绝查询并触发重建。

坑 4：把整段检索结果无脑塞进上下文
结论：token 成本飙升，且答案被无关片段带偏（Noise Sensitivity 高）。
原因：Top-K 取得过大，且没有重排筛掉低相关片段。
解法：先重排取 Top-N（3-5），再做长度截断与去重，只保留高相关片段。

坑 5：评测集与线上分布不一致
结论：离线分数很高，上线后被用户真实问题打回原形。
原因：评测集靠人工臆造，未覆盖真实的口语化、多跳、含指代问题。
解法：从真实日志分层抽样并标注 ground_truth，定期补充线上失败样本。
```
