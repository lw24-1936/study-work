## 概述

Agent 是把大语言模型从「单次问答」变成「多步任务执行者」的工程结构：模型在循环里调用工具、观察结果、更新状态，直到满足终止条件。本主题先厘清 Agent 的定义与四要素，再划清它与 Chatbot、Workflow 的边界，最后给出可直接运行的循环骨架——后面几篇（函数调用、MCP、记忆与上下文、RAG、多智能体、可观测性、安全）都是围绕这个骨架补零件。

```text
本篇要回答的四个问题：
1. 什么算 Agent —— 四要素（LLM / Tools / Memory / Planner）缺一不可，否则退回 Chatbot 或 Workflow
2. 谁来控制流程 —— 代码预定义路径是 Workflow，模型动态决定是 Agent
3. 循环怎么收敛 —— 规划-执行-反思 + 明确的终止条件（步数、预算、任务判定）
4. 什么时候不该用 —— 单次调用加点检索就能解决的，不要上循环
```

## Agent 四要素与定义

Anthropic 在 Building effective agents 中把所有这类系统统称 agentic systems，并给出一个可操作的区分：**Workflow 是 LLM 与工具由预定义代码路径编排的系统，Agent 是 LLM 动态决定自身过程与工具使用、自主控制如何完成任务的系统**。落到工程实现上，一个 Agent 至少要同时具备四个要素，缺任意一个都会退化：只有 LLM 是 Chatbot，只有 LLM + Tools 是工具调用器，只有 LLM + 固定链路是 Workflow。

| 要素 | 职责 | 工程落点 | 退化后的形态 |
|------|------|----------|--------------|
| Model（LLM） | 理解目标、做决策、生成参数 | 支持 tool calling 的模型接口 | Chatbot |
| Tools | 与外部世界交互的唯一出口 | 函数 + JSON Schema 声明 | 只会说不会做 |
| Memory | 跨步骤、跨会话保留状态 | 消息历史 + 外部存储 | 每轮失忆 |
| Planner | 决定下一步做什么、何时停 | 模型自身的决策 + 步数/预算上限 | 确定性流程 Workflow |

下面这个例子把四个要素放在同一个文件里，只用标准库就能跑通一次完整循环（本机 Python 3.14.7 实测）。

```python
"""四要素最小示例：Model + Tools + Memory + Planner 组成的一次完整循环。"""
from typing import Any

MEMORY: list[str] = []          # Memory：跨轮持久化的少量事实
TOOLS = {                       # Tools：模型可调用的动作
    "calc": lambda a, b: a * b,
    "remember": lambda text: MEMORY.append(text) or "ok",
}


def planner(goal: str, history: list[str]) -> dict[str, Any]:
    """Planner：决定下一步动作。真实场景由 LLM 输出 tool_calls。"""
    if not history:
        return {"tool": "calc", "args": {"a": 3, "b": 4}, "thought": "先算单价乘数量"}
    if "remember" not in " ".join(history):
        return {"tool": "remember", "args": {"text": "客户年采购量 12 台"}, "thought": "把关键事实写入记忆"}
    return {"tool": "__final__", "args": {}, "thought": "信息够了，直接回答"}


def run(goal: str, max_steps: int = 5) -> None:
    history: list[str] = []
    for step in range(1, max_steps + 1):
        decision = planner(goal, history)                 # 1) 规划
        print(f"step{step} thought={decision['thought']} tool={decision['tool']}")
        if decision["tool"] == "__final__":
            print("final answer ->", history[-1], "| memory:", MEMORY)
            return
        observation = TOOLS[decision["tool"]](**decision["args"])   # 2) 执行
        history.append(f"{decision['tool']} -> {observation}")      # 3) 观察入历史
        print(f"step{step} observation={observation}")
    print("达到 max_steps，终止")


if __name__ == "__main__":
    run("算出 12 台设备的总价并记住这个量")
```

```text
step1 thought=先算单价乘数量 tool=calc
step1 observation=12
step2 thought=把关键事实写入记忆 tool=remember
step2 observation=ok
step3 thought=信息够了，直接回答 tool=__final__
final answer -> remember -> ok | memory: ['客户年采购量 12 台']
```

```text
四要素要点：
1. Model 只负责决策与生成参数，不负责执行；执行永远在你的进程里
2. Tools 的 JSON Schema 就是模型与你代码之间的接口契约，参数名要自解释
3. Memory 分两层：循环内的 messages（短期）与外部存储（长期，跨会话）
4. Planner 的产物是「动作 + 参数 + 终止判断」，不是自然语言段落
5. max_steps 这类硬上限是 Agent 的安全带，没有它循环可能永不收敛
```

## Agent 与 Chatbot 的区别

Chatbot 的契约是「一问一答」：输入文本、输出文本，除对话历史外不改变任何外部状态。Agent 的契约是「给定目标，返回结果与过程」，它的每一步都可能读写外部系统（下单、改配置、发邮件），因此必须回答 Chatbot 不需要考虑的问题：权限边界在哪、失败了怎么补偿、动作是否可逆、一轮花多少钱。把这两者混淆是生产事故的常见来源——把具备写权限的工具挂到一个按聊天场景设计的系统上，模型的一次「顺口」调用就是一次真实变更。

| 维度 | Chatbot | Agent |
|------|---------|-------|
| 交互形态 | 单轮/多轮问答 | 目标 → 多步执行 → 结果与过程 |
| 外部副作用 | 无 | 可能写库、下单、改配置 |
| 状态 | 对话历史 | 历史 + 工具观察 + 外部记忆 + 任务状态 |
| 终止条件 | 生成结束 | 任务判定 / 步数上限 / 预算上限 |
| 失败处理 | 重问一次 | 重试、降级、回滚、转人工 |
| 成本特征 | 与轮数线性相关 | 与步数、工具调用次数、上下文长度相关 |
| 必须做的防护 | 内容过滤 | 内容过滤 + 权限最小化 + 审批 + 幂等 + 审计 |

从代码上看，两者的差别就是「有没有循环」以及「循环体里是否落库」。同一个模型接口，Chatbot 只调用一次就返回：

```python
# Chatbot：一次调用即结束，无副作用
resp = client.messages.create(
    model="claude-opus-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "杭州现在天气怎么样？"}],
)
print(resp.content[0].text)
```

Agent 则把工具结果回填进 messages 再来一轮，直到模型不再请求工具——工具定义里带 `input_schema` 的是客户端工具，由你自己的进程执行（参数名与流程以官方文档为准，见文末 URL）。

```python
# Agent：循环，直到模型不再请求工具或触发上限
tools = [{"name": "get_weather",
          "description": "查询指定城市当前天气。",
          "input_schema": {"type": "object",
                           "properties": {"city": {"type": "string"}},
                           "required": ["city"]}}]
messages = [{"role": "user", "content": "杭州现在天气怎么样？"}]

for _ in range(max_steps):
    resp = client.messages.create(model="claude-opus-5", max_tokens=1024,
                                  messages=messages, tools=tools)
    if resp.stop_reason != "tool_use":          # 没有工具请求即为终态
        break
    messages.append({"role": "assistant", "content": resp.content})
    results = []
    for block in resp.content:
        if block.type == "tool_use":
            out = run_tool(block.name, block.input)      # 你的执行逻辑
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": out})
    messages.append({"role": "user", "content": results})
```

```text
边界判定要点：
1. 需要多步、需要工具、需要状态，三者至少满足一个才值得引入 Agent
2. 有外部副作用就必须配权限控制与幂等，Chatbot 时代的纯文本防护不够用
3. 每多一步都可能失败，重试与降级策略要在设计阶段就定好
4. 能一次调用 + 检索解决的，不要上循环（延迟与成本成倍增加）
```

## 规划-执行-反思循环

Agent 的循环可以拆成三个动作：规划（Planning，决定下一步）、执行（Execution，调用工具并拿到观察）、反思（Reflection，判断结果是否满足目标、要不要改策略）。ReAct 论文（arXiv:2210.03629，ICLR 2023 版本）给出的做法是让模型交错生成推理轨迹与动作：推理轨迹帮助模型维持并修正行动计划、处理异常，动作让它去外部环境取信息。论文在 HotpotQA、Fever 上用 Wikipedia API 交互缓解了思维链的幻觉与错误传播，在 ALFWorld 与 WebShop 两个交互式决策任务上，相比模仿学习与强化学习基线成功率绝对提升 34% 与 10%，且只用了一到两个 in-context 示例。

反思环节最容易做成摆设：如果判据只是「模型自己说完成了」，它几乎总会说完成了。可行做法是把判据外部化——规则校验、单元测试、schema 校验、第二个评审模型，任一失败就把反馈写回上下文重规划。

```python
"""规划-执行-反思：执行后由校验器给出反馈，不通过则带着反馈重规划。"""

ACTIONS = {"draft": lambda topic: f"{topic} 的初稿（1200 字）",
           "expand": lambda text: text.replace("1200 字", "2000 字") + " + 补充案例",
           "fix": lambda text: text.replace("初稿", "终稿")}


def verifier(result: str) -> tuple[bool, str]:
    """反思环节的判据：真实场景可由规则、单测或第二个 LLM 评审给出。"""
    if "案例" not in result:
        return False, "缺少真实案例，需要补充"
    if "1200 字" in result:
        return False, "字数不足，需要扩写"
    return True, "通过"


def run(topic: str, max_rounds: int = 4) -> None:
    plan, result, feedback = "draft", "", ""
    for rnd in range(1, max_rounds + 1):
        if rnd == 1:
            result = ACTIONS[plan](topic)
        else:
            action = "expand" if "案例" in feedback else "fix"
            print(f"round{rnd} reflect: {feedback} -> 选动作 {action}")
            result = ACTIONS[action](result)
        ok, feedback = verifier(result)
        print(f"round{rnd} execute: {result} | verify={ok}")
        if ok:
            print("done ->", result)
            return
    print("达到 max_rounds，返回当前最佳结果并标记待人工复核")


if __name__ == "__main__":
    run("向量数据库选型")
```

```text
round1 execute: 向量数据库选型 的初稿（1200 字） | verify=False
round2 reflect: 缺少真实案例，需要补充 -> 选动作 expand
round2 execute: 向量数据库选型 的初稿（2000 字） + 补充案例 | verify=True
done -> 向量数据库选型 的初稿（2000 字） + 补充案例
```

```text
循环收敛要点：
1. 三个动作都要有上限：步数、轮次、token 预算、墙钟时间，任一超限即退出
2. 反思需要外部判据，模型自评只能作为辅助信号
3. 反馈要具体可执行（缺什么、补什么），模糊反馈会让重规划原地打转
4. 达到上限时返回「当前最佳 + 待人工复核」比抛异常更可用
5. 每轮的中间产物要落盘或写日志，否则失败后无法复盘（见可观测性篇）
```

## 反应式 Agent 与规划式 Agent

反应式（Reactive）策略每步只看当前观测，用规则或策略模型直接给出动作，不做前瞻：实现简单、延迟低，但遇到需要顺序约束的任务会来回反复。规划式（Deliberative）先产出一个全局计划再逐步执行：适合步骤间有依赖、有资源约束的任务，代价是计划本身可能一开始就错，需要用执行中的观察去修正。两者不是互斥的，常见形态是「先规划一次拿到骨架，执行中按反应式规则处理异常，必要时重新规划」。

```python
"""反应式 vs 规划式：同一任务用无状态规则和先规划后执行两种策略完成。"""

TOOLS = {"pick": lambda item: item, "pack": lambda item: f"packed({item})"}
TARGET = ["a", "b", "c"]          # 需要按序放入背包的物品


def reactive(items: list[str]) -> list[str]:
    """反应式：每步只看当前观测，不做前瞻。物品乱序时会来回搬运。"""
    log, bag = [], []
    for item in items:
        if item in TARGET:
            if bag and TARGET.index(item) < TARGET.index(bag[-1]):
                bag.pop()                       # 发现顺序错了，先取出
                log.append(f"unpack({item}) 顺序不对")
            bag.append(item)
            log.append(f"pick+pack {item} -> {bag}")
    return log


def deliberative(items: list[str]) -> list[str]:
    """规划式：先排序得到目标序列，再顺序执行（plan -> act）。"""
    order = [i for i in TARGET if i in items]
    plan = " -> ".join(order)
    log = [f"plan: {plan}"]
    for item in order:
        log.append(f"act: {TOOLS['pack'](TOOLS['pick'](item))}")
    return log


if __name__ == "__main__":
    shuffled = ["b", "a", "c"]
    print("items:", shuffled, " target:", TARGET)
    print("\n[反应式]")
    for line in reactive(shuffled):
        print("  ", line)
    print("\n[规划式]")
    for line in deliberative(shuffled):
        print("  ", line)
```

```text
items: ['b', 'a', 'c']  target: ['a', 'b', 'c']

[反应式]
   pick+pack b -> ['b']
   unpack(a) 顺序不对
   pick+pack a -> ['a']
   pick+pack c -> ['a', 'c']

[规划式]
   plan: a -> b -> c
   act: packed(a)
   act: packed(b)
   act: packed(c)
```

```text
两种策略取舍：
1. 单步可判定、无顺序依赖的任务用反应式，实现最简单
2. 步骤间有依赖或资源约束时先规划，能减少无效动作
3. 反应式没有全局视野，乱序输入会反复纠错，注意观测里是否包含足够上下文
4. 规划式的计划要用执行观察持续校正，纯静态计划在动态环境里必错
5. 工程上常见组合：规划一次 + 反应式处理异常 + 失败时重规划
```

## Workflow 与 Agent 的边界

所有 agentic system 的形态可以排成一条复杂度轴：单次 LLM 调用 → 检索增强的单次调用 → 固定 Workflow → Agent。Anthropic 的建议是**先找最简单的解法，只在确实需要时增加复杂度**；Agent 用延迟与成本换任务完成率，这个交换是否划算必须逐场景评估。Workflow 侧的常见模式有五种：Prompt chaining（固定串联，可加校验门）、Routing（分类后分流）、Parallelization（sectioning 拆并行子任务 / voting 多次投票）、Orchestrator-workers（中心模型动态拆解）、Evaluator-optimizer（生成与评审循环）。

判定的关键问题是：**「下一步做什么」这件事能不能在写代码时就确定？** 能确定就用 Workflow——可测试、可预测、成本稳定；不能确定（子任务数量与内容依赖运行时输入）才交给模型。实践中大量所谓 Agent 需求，其实是路由加一段确定性流程。

```text
复杂度轴与选择：
1. 单次调用 —— 分类、抽取、改写，能答就答
2. 单次调用 + 检索 —— 需要外部知识但不需要动作
3. Workflow —— 步骤固定、可加校验门、失败可重试
4. Agent —— 步骤数不可预知、需要动态选工具（如跨多文件改代码、多源调研）
```

同一条链路可以混用两种形态：金额计算、状态机流转这类有明确规则的段落用确定性代码，原因排查这类需要多步取证的段落交给 Agent 循环。下面的例子先用路由把请求分类，再分别进入固定流程或 Agent 循环（本机 Python 3.14.7 实测）。

```python
"""场景：Workflow 与 Agent 混用 —— 先用路由分类，再分别走固定流程或 Agent 循环。"""
from typing import Any


# 固定 Workflow：退款金额计算有明确计算规则，用确定性代码，不让模型自由发挥
def refund_workflow(order: dict[str, Any]) -> str:
    fee = 0 if order["status"] == "shipped" else 5.0
    return f"退款金额 {order['amount'] - fee:.2f} 元（手续费 {fee:.2f}）"


# Agent 循环：原因不明的物流异常需要多步查证
TOOLS = {
    "check_logistics": lambda order_id: {"event": "stuck_at_hub", "hours": 52},
    "check_weather": lambda hub: {"hub": hub, "alert": "typhoon"},
    "escalate": lambda reason: f"已升级人工：{reason}",
}


def agent_loop(order_id: str, max_steps: int = 4) -> list[str]:
    trace, ctx = [], {}
    for step in range(1, max_steps + 1):
        if "logistics" not in ctx:
            action, args = "check_logistics", {"order_id": order_id}
        elif "weather" not in ctx:
            action, args = "check_weather", {"hub": "HGH"}
        else:
            action, args = "escalate", {"reason": f"{ctx['logistics']} + {ctx['weather']}"}
        result = TOOLS[action](**args)
        ctx[action.replace("check_", "")] = result
        trace.append(f"step{step} {action}{args} -> {result}")
        if action == "escalate":
            return trace
    trace.append("达到 max_steps，转人工兜底")
    return trace


def router(query: str) -> str:
    """路由：用关键词/分类模型把请求分给确定性流程或 Agent。真实场景用分类模型或 LLM 判定。"""
    return "workflow" if "退款" in query else "agent"


if __name__ == "__main__":
    orders = [{"order_id": "A1001", "amount": 128.5, "status": "shipped"},
              {"order_id": "A1002", "amount": 42.0, "status": "pending"}]
    tasks = ["订单 A1001 要退款", "订单 A1002 物流两天没动了"]
    for order, task in zip(orders, tasks):
        kind = router(task)
        print(f"\n[task] {task}  -> router 判定: {kind}")
        if kind == "workflow":
            print("  result:", refund_workflow(order))
        else:
            for line in agent_loop(order["order_id"]):
                print("  ", line)
```

```text
[task] 订单 A1001 要退款  -> router 判定: workflow
  result: 退款金额 128.50 元（手续费 0.00）

[task] 订单 A1002 物流两天没动了  -> router 判定: agent
   step1 check_logistics{'order_id': 'A1002'} -> {'event': 'stuck_at_hub', 'hours': 52}
   step2 check_weather{'hub': 'HGH'} -> {'hub': 'HGH', 'alert': 'typhoon'}
   step3 escalate{'reason': "{'event': 'stuck_at_hub', 'hours': 52} + {'hub': 'HGH', 'alert': 'typhoon'}"} -> 已升级人工：{'event': 'stuck_at_hub', 'hours': 52} + {'hub': 'HGH', 'alert': 'typhoon'}
```

```text
边界要点：
1. 能写成确定性代码的段落不要交给模型，可测试性远比「看起来智能」重要
2. 路由本身可以是规则、分类模型或 LLM，选准确率够用且最便宜的那个
3. Workflow 段落要保留校验门（gate），中间产物不合法就不要进入下一步
4. Agent 段落必须有兜底分支：超步数、超预算、工具全失败时转人工
5. 混用时统一日志与 trace id，否则跨形态的问题无法定位
```

## Agent 分类与典型形态

按交互对象与自主程度，工程上常见的 Agent 形态有：对话式助手（会话内多轮，人在环中确认）、任务执行 Agent（编码、运维，长时间多步且有副作用）、检索研究 Agent（多源取证后汇总）、多智能体系统（多个专职 Agent 协作或对抗）、以及嵌入产品的垂直 Agent（客服、导购、风控）。分类的意义在于选默认约束：有副作用的形态默认要审批与幂等，长任务的形态默认要检查点与断点续跑，多源检索的形态默认要引用与去重。

| 形态 | 典型任务 | 主要风险 | 默认约束 |
|------|----------|----------|----------|
| 对话式助手 | 客服、导购、内部问答 | 幻觉、越权查询 | 只读工具优先、会话隔离 |
| 任务执行 Agent | 编码、运维、数据处理 | 破坏性操作不可逆 | 审批、沙箱、幂等、审计 |
| 检索研究 Agent | 调研、竞品分析、尽调 | 来源不可信、成本失控 | 引用来源、步数与预算上限 |
| 多智能体系统 | 复杂工程、模拟评审 | 通信放大、责任不清 | 明确角色与消息协议、防止无限互相调用 |
| 垂直领域 Agent | 风控、医疗、金融流程 | 合规与漏判 | 规则兜底、留痕、可解释输出 |

形态决定技术选型的下一站：需要工具生态就用 MCP 接入标准化协议；上下文撑不住就上记忆与上下文工程；需要外部知识就用 RAG；多个角色分工就上多智能体；上线前必须有可观测性与评估；有写权限就必须做工程化与安全加固。这正好是本章后面几篇的顺序。

```text
选型清单（按顺序问自己）：
1. 目标是否可判定完成 —— 不可判定就加人工确认节点
2. 是否有外部副作用 —— 有则先设计权限与幂等
3. 步骤数是否可预知 —— 可预知优先 Workflow
4. 上下文是否需要跨会话 —— 需要则先设计记忆写入与召回
5. 是否需要多角色 —— 需要再引入多智能体，否则单 Agent + 工具更省
```

## 应用场景实战

### 场景一：同一任务用固定 Workflow 与 Agent 循环分别实现

内部知识库要做一个「摘要翻译加粗」的小功能。用 Workflow 写死三步，路径确定、可测试；用 Agent 循环则让模型自己选工具与终止时机。把两者跑在同一台机器上对比轨迹，是最直观的复杂度对照实验。

```python
"""同一任务分别用「固定 Workflow」和「Agent 循环」实现，对比控制权归属。"""
import json
from typing import Any


# ---------- 场景一：固定 Workflow（代码路径写死，LLM 只做单步变换）----------
def workflow_pipeline(text: str) -> list[str]:
    steps = []
    summary = text[:12] + "..."            # 步骤 1：抽取（这里用规则代替 LLM 调用）
    steps.append(f"extract -> {summary}")
    steps.append(f"translate -> [EN] {summary}")           # 步骤 2：翻译
    steps.append(f"format -> **{summary}**")               # 步骤 3：排版
    return steps


# ---------- 场景二：Agent 循环（模型自己决定调用哪个工具、何时停止）----------
TOOLS = {
    "extract": lambda text: text[:12] + "...",
    "translate": lambda text: "[EN] " + text,
    "format": lambda text: "**" + text + "**",
    "finish": lambda text: text,
}


def fake_llm(task: str, scratch: str, history: list[str]) -> dict[str, Any]:
    """占位模型：真实场景换成 chat.completions 返回的 tool_calls。这里用规则模拟决策。"""
    done = " ".join(history)
    if "extract" not in done:                           # 第一步：抽取
        return {"tool": "extract", "args": {"text": task}}
    if "翻译" in task and "translate" not in done:      # 任务里出现了翻译要求，且还没翻译过
        return {"tool": "translate", "args": {"text": scratch}}
    if "format" not in done:
        return {"tool": "format", "args": {"text": scratch}}
    return {"tool": "finish", "args": {"text": scratch}}


def agent_loop(task: str, max_steps: int = 6) -> list[str]:
    trace: list[str] = []
    scratch = ""
    for step in range(max_steps):
        decision = fake_llm(task, scratch, trace)                 # 1) 规划
        tool, args = decision["tool"], decision["args"]
        trace.append(f"step{step + 1} thought=选择 {tool}")
        if tool == "finish":                                      # 2) 反思/终止条件
            trace.append(f"step{step + 1} finish -> {args['text']}")
            return trace
        scratch = TOOLS[tool](**args)                             # 3) 执行
        trace.append(f"step{step + 1} observation={scratch}")
    trace.append(f"hit max_steps={max_steps}, 强制终止")
    return trace


if __name__ == "__main__":
    task = "把这段中文摘要翻译成英文并加粗"
    print("task:", task)
    print("\n[Workflow] 固定路径：")
    for line in workflow_pipeline(task):
        print("  ", line)
    print("\n[Agent] 动态决策轨迹：")
    for line in agent_loop(task):
        print("  ", line)
    print("\nJSON 轨迹：", json.dumps(agent_loop(task), ensure_ascii=False))
```

```text
task: 把这段中文摘要翻译成英文并加粗

[Workflow] 固定路径：
   extract -> 把这段中文摘要翻译成英文...
   translate -> [EN] 把这段中文摘要翻译成英文...
   format -> **把这段中文摘要翻译成英文...**

[Agent] 动态决策轨迹：
   step1 thought=选择 extract
   step1 observation=把这段中文摘要翻译成英文...
   step2 thought=选择 translate
   step2 observation=[EN] 把这段中文摘要翻译成英文...
   step3 thought=选择 format
   step3 observation=**[EN] 把这段中文摘要翻译成英文...**
   step4 thought=选择 finish
   step4 finish -> **[EN] 把这段中文摘要翻译成英文...**
```

轨迹对比的结论是：Workflow 用三次固定调用完成，成本与延迟可预测，但没有处理「任务里没有翻译要求」这类变化的余地；Agent 每次都重新决策，能适应变化，代价是决策次数不确定、必须配上限。

### 场景二：企业订单异常处理 —— 路由加确定性流程加 Agent 循环

订单系统每天有大量咨询，其中退款金额计算有明确规则（不该让模型算钱），物流异常需要多步取证（查轨迹、查天气、查仓库公告）才能决定是否升级人工。工程做法是把请求先路由：规则清楚的走确定性代码（可单测、金额零误差），原因不明的走 Agent 循环（每步写 trace，超步数转人工）。完整可运行代码见上文 Workflow 与 Agent 的边界一节，输出如下。

```text
[task] 订单 A1001 要退款  -> router 判定: workflow
  result: 退款金额 128.50 元（手续费 0.00）

[task] 订单 A1002 物流两天没动了  -> router 判定: agent
   step1 check_logistics{'order_id': 'A1002'} -> {'event': 'stuck_at_hub', 'hours': 52}
   step2 check_weather{'hub': 'HGH'} -> {'hub': 'HGH', 'alert': 'typhoon'}
   step3 escalate{'reason': ...} -> 已升级人工：...
```

上线要点：退款流程必须有幂等键（`order_id` 加操作类型），避免重试重复打款；Agent 段落的每个工具调用写审计日志，字段至少包含 session_id、tool、args、result、耗时；升级人工时把 trace 一并带给工单系统，客服不需要重问客户。

## 最佳实践与踩坑记录

### 最佳实践

1. 从最简形态起步：单次调用加检索能解决的不要上循环，确实需要动态步骤再用 Agent。
2. 硬上限优先于提示词约束：max_steps、token 预算、墙钟超时写在代码里，不要只写在提示词里。
3. 工具设计当接口设计：参数名自解释、用 enum 排除非法状态、路径统一要求绝对路径（Anthropic 在 SWE-bench 实践中把相对路径改成绝对路径后调用错误消失）。
4. 控制初始工具数量：OpenAI 文档建议单轮初始可用函数保持较少（软性建议 20 个以内），过多工具会让选择准确率下降；用工具检索或分组延后加载。
5. 反思判据外部化：能用规则、单测、schema 校验就不要让模型自评。
6. 全链路可观测：每一步的 thought、tool、args、result、耗时、token 都要落盘，否则线上问题无法复盘。

### 踩坑记录

```text
坑 1：只给了工具没有终止条件，循环烧钱
结论：任务早已完成，模型仍在反复调用工具，token 与延迟双爆。
原因：终止判断完全交给模型，且没有步数与预算上限。
解法：代码层强制 max_steps + token 预算 + 墙钟超时；模型不再请求工具即视为终态。

坑 2：把有副作用的写操作直接暴露给模型
结论：一次误判造成真实数据变更，且无法回滚。
原因：对 Agent 复用了 Chatbot 的权限假设，工具集里混入了写接口。
解法：默认只读，写操作走审批或草稿态；所有写工具带幂等键并记录审计日志。

坑 3：相对路径与隐式上下文导致工具调用失败
结论：模型在多步执行后传入相对路径，工具报文件不存在，循环空转。
原因：工具描述没有约束路径格式，模型自行推断。
解法：工具参数强制绝对路径，描述里给出完整示例；参数校验失败立刻把明确错误回填给模型。

坑 4：反思环节让模型自评，永远得到「已完成」
结论：质量不达标的结果被当成成功返回。
原因：判据主观、无外部信号。
解法：接规则校验或单测作为判据，模型自评只作为辅助，失败时给出具体缺什么。

坑 5：Workflow 能做的场景硬上 Agent
结论：同样的任务，延迟与成本翻数倍，稳定性还下降。
原因：把「看起来更智能」当成技术目标。
解法：按「下一步能否在编码时确定」判定；能确定就用 Workflow，并保留校验门。
```
