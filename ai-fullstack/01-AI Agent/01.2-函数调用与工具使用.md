## 概述

函数调用（Function Calling / Tool Calling）是模型与外部世界之间唯一的标准接口：你用 JSON Schema 声明工具，模型在需要时返回结构化的调用请求，你的代码执行它并把结果回填进对话，循环直到模型不再请求工具。这一篇讲清五件事：调用流程怎么走、Schema 怎么写才准、结果怎么回填、多个调用怎么并发、失败怎么重试与降级——上游是 Agent 的架构（01.1），下游是标准化的工具协议（01.3）。

```text
全篇主线：
1. 流程 —— 声明工具、模型请求调用、本地执行、结果回填、再请求，五步循环
2. Schema —— 参数名与描述就是给模型的接口文档，strict 模式强制结构合法
3. 回填 —— 每次工具结果都要带上调用 id，且一轮里的所有调用都必须有对应结果
4. 并发 —— 一轮可以返回多个调用，用并发执行压延迟，失败项单独降级
5. 可靠 —— 参数校验、瞬时故障退避重试、熔断、幂等、审计日志
```

## Function Calling 原理与流程

OpenAI 官方文档把工具调用描述为应用与模型之间的多步会话，共五步：一是带工具列表发起请求；二是收到模型返回的工具调用；三是应用侧用调用参数执行代码；四是把工具输出作为再次请求的一部分发回；五是收到最终回复（或更多工具调用）。模型本身不执行任何东西——它只产出「调用哪个工具、参数是什么」的结构化意图，执行权始终在你的进程里，这也是权限控制、审计、幂等的落点。

```text
五步循环（所有厂商的形态一致，字段名不同）：
1. 请求：messages + tools(JSON Schema) -> 模型
2. 决策：模型返回 tool_calls / tool_use 块（可能 0 个、1 个或多个）
3. 执行：你的代码按 schema 校验参数后调用真实函数
4. 回填：把结果作为 tool 角色消息（带调用 id）追加到 messages
5. 收敛：再次请求，模型给出最终文本或继续请求工具
```

三家主流接口的字段差异（跨厂商切换时需要一个适配层，别把调用逻辑写死在业务代码里）：

| 维度 | OpenAI | Anthropic | Ollama 本地服务 |
|------|--------|-----------|------------------|
| 工具声明 | `tools[].function` 内嵌 `name` / `description` / `parameters` | `tools[].name` / `description` / `input_schema` | `tools[].function` 内嵌 `name` / `description` / `parameters` |
| 调用请求 | 消息里 `tool_calls[]`，每项带 `id` | 响应 `content` 里的 `tool_use` 块，带 `id`，`stop_reason` 为 `tool_use` | 消息里 `tool_calls[]`，按 `index` 排序 |
| 结果回填 | `{"role": "tool", "tool_call_id": ..., "content": ...}` | `tool_result` 块，字段 `tool_use_id` | `{"role": "tool", "tool_name": ..., "content": ...}` |
| 强制调用 | `tool_choice` 支持 `auto` / `required` / 指定函数 / `allowed_tools` / `none` | `tool_choice` 支持 `auto` / `any` / 指定工具，`disable_parallel_tool_use` 可关并行 | 以官方文档为准，本地模型多为 best effort |
| 严格模式 | `strict: true`（结构化输出），对 schema 有额外约束 | 无同名开关，靠 schema 与描述约束 | 无 |

Anthropic 的接口把工具分成客户端工具与服务端工具两类：客户端工具（含你自己定义的、以及 bash、text_editor 这类 Anthropic 定义 schema 的工具）在你的应用里执行，Claude 返回 `tool_use` 块，你执行后回传 `tool_result`；服务端工具（web_search、web_fetch、code_execution 等）在 Anthropic 侧执行，你直接看到结果。下面这段是官方文档中的客户端工具往返流程（需要 API Key，本机未实测，参数名以官方文档为准）。

```python
# Anthropic 客户端工具的完整往返（官方文档示例结构）
response = client.messages.create(
    model="claude-opus-5",
    max_tokens=1024,
    tools=tools,
    tool_choice={"type": "auto", "disable_parallel_tool_use": True},   # 每轮最多一个调用
    messages=messages,
)
tool_use = next(block for block in response.content if block.type == "tool_use")

messages += [
    {"role": "assistant", "content": response.content},
    {"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": tool_use.id, "content": "执行结果字符串"},
    ]},
]
followup = client.messages.create(model="claude-opus-5", max_tokens=1024,
                                  tools=tools, messages=messages)
```

Ollama 的本地 `POST /api/chat` 采用与 OpenAI 相近的结构，可直接用 cURL 验证链路是否通（本地模型是否支持工具调用取决于模型本身，选型前先用官方文档确认模型能力）。

```shell
# 本地模型单次工具调用（ollama serve 之后）
curl -s http://localhost:11434/api/chat -H "Content-Type: application/json" -d '{
  "model": "qwen3",
  "stream": false,
  "messages": [{"role": "user", "content": "What is the temperature in New York?"}],
  "tools": [{
    "type": "function",
    "function": {
      "name": "get_temperature",
      "description": "Get the current temperature for a city",
      "parameters": {"type": "object", "required": ["city"],
                     "properties": {"city": {"type": "string", "description": "The name of the city"}}}
    }
  }]
}'
```

```text
流程要点：
1. 模型只输出调用意图，执行与副作用全部在你的代码里，权限与审计在这里做
2. 一次响应可能包含零个、一个或多个工具调用，循环要按「多个」来写
3. 一轮里的每个调用都必须有对应的结果消息，否则下一轮请求会因消息不完整被拒
4. 工具定义本身计入输入 token 并计费，工具越多每次请求越贵
5. 消息历史要原样保留 assistant 的 tool_calls 与对应的 tool 结果，不能只留文本
```

## Tool Schema 定义规范

Schema 是模型理解工具的唯一依据，写得含糊模型就会猜参数。OpenAI 的函数定义字段是 `type`（固定 `function`）、`name`、`description`、`parameters`（JSON Schema）、`strict`；开启 `strict: true` 后会走结构化输出通道，要求每个对象都设置 `additionalProperties: false` 且 `properties` 里的字段全部列入 `required`，可选字段用 `type: ["string", "null"]` 这类联合类型表达。`strict` 没写时行为取决于接口：Responses 会尽量把 schema 规范化到严格模式，Chat Completions 默认仍是宽松的 best effort。

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询指定城市的当前天气。仅支持中国境内城市，返回摄氏度。",
    "strict": true,
    "parameters": {
      "type": "object",
      "properties": {
        "city": {"type": "string", "description": "城市名，例如 杭州"},
        "unit": {"type": ["string", "null"], "enum": ["celsius", "fahrenheit"],
                 "description": "温度单位，缺省为 celsius"}
      },
      "required": ["city", "unit"],
      "additionalProperties": false
    }
  }
}
```

参数到达后先本地校验再执行，能把「模型编造的参数」挡在你的业务代码之外。下面用 `jsonschema`（本机 4.26.0）做校验，错误信息可以直接回填给模型让它自我纠正。

```python
from jsonschema import ValidationError, validate

SPEC = {
    "type": "object",
    "properties": {"city": {"type": "string"}, "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}},
    "required": ["city", "unit"],
    "additionalProperties": False,
}

try:
    validate(instance={"city": "杭州"}, schema=SPEC)      # 故意漏掉 unit
except ValidationError as exc:
    print({"error": "invalid_arguments", "detail": exc.message})
```

```text
{'error': 'invalid_arguments', 'detail': "'unit' is a required property"}
```

```text
Schema 编写要点：
1. description 写「什么时候用它、不适用什么场景」，而不是复述工具名
2. 用 enum 与布尔结构排除非法状态，避免 on/off 两个参数互相矛盾的接口
3. 严格模式要求 additionalProperties false 且字段全必填，可选字段用 null 联合类型
4. 不要让模型填你已知的参数（例如上一步已经拿到的 order_id），这类参数放进闭包
5. 单轮初始工具数保持较少（官方软性建议 20 个以内），大工具集用工具检索延后加载
6. 拿「实习生测试」自查：只看描述和参数，一个新人能否正确使用这个工具
```

## 工具结果回填与多轮循环

回填的关键是消息序列完整且可追溯：assistant 消息保留原始的工具调用请求（含 `id`），紧接着追加每个调用的结果消息，两者配对出现。任何一端缺失，下一轮请求都会被接口拒绝或让模型重复调用同一个工具。循环的终止条件是模型不再请求工具——此时它的输出就是最终答案；除此之外还必须叠加步数、token 与时间上限。

下面是一个完整可运行的循环骨架（本机 Python 3.14.7 实测），用规则函数代替模型决策，但消息结构与真实 API 完全一致：`user` 提问、`assistant` 带 `tool_calls`、`tool` 带 `tool_call_id` 回填，直到产出最终答案。

```python
"""Function Calling 多轮循环 + 参数校验 + 失败重试/降级（无需真实 API Key）。"""

import json
import time
from typing import Any

from jsonschema import ValidationError, validate

# 1) 工具注册表：一份 JSON Schema（与 OpenAI tools 字段同构）+ 一个本地实现
TOOLS: dict[str, dict[str, Any]] = {
    "get_weather": {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的当前天气。仅支持中国境内城市。",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名，例如 杭州"},
                    "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]},
                },
                "required": ["city", "unit"],
                "additionalProperties": False,
            },
            "strict": True,
        },
    },
    "get_stock": {
        "type": "function",
        "function": {
            "name": "get_stock",
            "description": "查询商品当前库存。",
            "parameters": {
                "type": "object",
                "properties": {"sku": {"type": "string"}},
                "required": ["sku"],
                "additionalProperties": False,
            },
            "strict": True,
        },
    },
}

CALLS = 0


def _impl_get_weather(city: str, unit: str) -> dict[str, Any]:
    global CALLS
    CALLS += 1
    if CALLS == 1:                     # 模拟第一次调用遇到下游 5xx
        raise RuntimeError("upstream 503")
    temp = {"杭州": 24.0, "北京": 19.0}.get(city)
    if temp is None:
        return {"error": "city_not_supported", "city": city}
    if unit == "fahrenheit":
        temp = temp * 9 / 5 + 32
    return {"city": city, "temp": round(temp, 1), "unit": unit}


def _impl_get_stock(sku: str) -> dict[str, Any]:
    return {"sku": sku, "available": 0}


IMPLS = {"get_weather": _impl_get_weather, "get_stock": _impl_get_stock}


def dispatch(name: str, arguments: dict[str, Any], retries: int = 2) -> dict[str, Any]:
    """校验参数 -> 执行 -> 失败按策略重试 -> 仍失败返回结构化错误（降级而不是抛给模型）。"""
    spec = TOOLS.get(name)
    if spec is None:
        return {"error": "unknown_tool", "name": name}
    try:
        validate(instance=arguments, schema=spec["function"]["parameters"])
    except ValidationError as exc:
        return {"error": "invalid_arguments", "detail": exc.message}   # 交给模型纠正
    for attempt in range(retries + 1):
        try:
            return IMPLS[name](**arguments)
        except Exception as exc:                                       # 瞬时故障
            if attempt == retries:
                return {"error": "tool_unavailable", "detail": str(exc)}
            time.sleep(0.05 * (2 ** attempt))                          # 指数退避
    return {"error": "unreachable"}


# 2) 模拟模型的决策序列（真实场景来自 chat.completions 的 tool_calls 字段）
SCRIPT = [
    {"name": "get_weather", "arguments": {"city": "杭州", "unit": "celsius"}},   # 首次触发 503 重试
    {"name": "get_stock", "arguments": {"sku": "SKU-9"}},                        # 返回 available=0
    {"name": "get_weather", "arguments": {"city": "杭州"}},                      # 缺必填参数 -> 校验失败
    {"name": "final", "arguments": {"text": "杭州 24 度；SKU-9 缺货；建议补货。"}},
]


def run_loop() -> None:
    messages: list[dict[str, Any]] = [{"role": "user", "content": "杭州天气如何？顺便看下 SKU-9 库存。"}]
    for step in SCRIPT:
        if step["name"] == "final":
            messages.append({"role": "assistant", "content": step["arguments"]["text"]})
            print("final:", step["arguments"]["text"])
            break
        call = {"id": f"call_{len(messages)}", "type": "function",
                "function": {"name": step["name"], "arguments": json.dumps(step["arguments"])}}
        messages.append({"role": "assistant", "tool_calls": [call]})
        result = dispatch(step["name"], step["arguments"])
        messages.append({"role": "tool", "tool_call_id": call["id"],
                         "content": json.dumps(result, ensure_ascii=False)})
        print(f"step {len(messages)-1}: {step['name']}({json.dumps(step['arguments'], ensure_ascii=False)}) -> "
              f"{json.dumps(result, ensure_ascii=False)}")
    print("messages:", len(messages), "roles:", [m["role"] for m in messages])


if __name__ == "__main__":
    run_loop()
```

```text
step 2: get_weather({"city": "杭州", "unit": "celsius"}) -> {"city": "杭州", "temp": 24.0, "unit": "celsius"}
step 4: get_stock({"sku": "SKU-9"}) -> {"sku": "SKU-9", "available": 0}
step 6: get_weather({"city": "杭州"}) -> {"error": "invalid_arguments", "detail": "'unit' is a required property"}
final: 杭州 24 度；SKU-9 缺货；建议补货。
messages: 8 roles: ['user', 'assistant', 'tool', 'assistant', 'tool', 'assistant', 'tool', 'assistant']
```

```text
回填要点：
1. assistant 的 tool_calls 与 tool 结果必须成对出现，id 一一对应
2. 工具错误不要抛异常中断循环，用结构化错误（error 字段）回填，让模型自行纠正
3. 参数校验失败的错误信息要具体（哪个字段缺、期望什么），否则模型会重复同样的错误
4. 每次循环都要检查总 token 与消息条数，长会话需要裁剪或摘要（见 01.4）
5. 生产环境把 messages 全量落库（含工具调用），否则无法复盘与计费核对
```

## 并行工具调用

一轮响应里可以同时包含多个工具调用（例如同时查天气、库存、物流），串行执行会白白叠加延迟。OpenAI 侧由 `parallel_tool_calls` 控制：默认允许模型一次返回多个调用，设为 `false` 则保证一轮内零个或一个；文档同时提示内置工具不能出现在并行函数调用批次里（GPT-5 起的模型）。Anthropic 侧用 `tool_choice` 里的 `disable_parallel_tool_use` 关闭并行。Ollama 的本地接口支持一次返回多个调用，回填时按顺序追加多个 tool 消息。不管哪家，工程侧的做法一致：并发执行、单独超时、失败项不影响其他项。

```python
"""并行工具调用：asyncio.gather 并发执行，单个工具超时/失败不影响其他工具。"""
import asyncio
import time

TOOLS = {"get_weather": 0.30, "get_stock": 0.10, "get_logistics": 0.50, "get_coupon": 0.20}
TIMEOUT = 0.35


async def call_tool(name: str, delay: float, fail: bool = False) -> dict:
    await asyncio.sleep(delay)
    if fail:
        raise RuntimeError(f"{name} upstream 500")
    return {"tool": name, "ok": True, "data": f"{name}-result"}


async def call_with_timeout(name: str, delay: float) -> dict:
    try:
        return await asyncio.wait_for(call_tool(name, delay), timeout=TIMEOUT)
    except asyncio.TimeoutError:
        return {"tool": name, "ok": False, "error": "timeout"}
    except Exception as exc:                       # 工具级错误不进全局异常
        return {"tool": name, "ok": False, "error": str(exc)}


async def main() -> None:
    started = time.perf_counter()
    tasks = [call_with_timeout("get_weather", 0.30),
             call_with_timeout("get_stock", 0.10),
             call_with_timeout("get_logistics", 0.50),
             call_with_timeout("get_coupon", 0.20)]
    results = await asyncio.gather(*tasks)
    elapsed = time.perf_counter() - started
    for r in results:
        print(r)
    print(f"wall time = {elapsed:.2f}s（串行需 {sum(TOOLS.values()):.2f}s）")
    ok = [r["tool"] for r in results if r["ok"]]
    bad = [r["tool"] for r in results if not r["ok"]]
    print(f"成功 {len(ok)} 个：{ok}；失败 {len(bad)} 个：{bad} -> 失败项作为 observation 回填，由模型决定是否重试")


if __name__ == "__main__":
    asyncio.run(main())
```

```text
{'tool': 'get_weather', 'ok': True, 'data': 'get_weather-result'}
{'tool': 'get_stock', 'ok': True, 'data': 'get_stock-result'}
{'tool': 'get_logistics', 'ok': False, 'error': 'timeout'}
{'tool': 'get_coupon', 'ok': True, 'data': 'get_coupon-result'}
wall time = 0.35s（串行需 1.10s）
成功 3 个：['get_weather', 'get_stock', 'get_coupon']；失败 1 个：['get_logistics'] -> 失败项作为 observation 回填，由模型决定是否重试
```

```text
并发调用要点：
1. 并发执行同批工具，延迟取最大值而不是求和
2. 每个工具单独设超时，超时结果也作为一种「观察」回填
3. 并发结果按调用 id 归位，不能依赖返回顺序
4. 同一批里的写操作要慎重：可能互相依赖，必要时按依赖图串行
5. 并发数要有上限（信号量），避免一次打爆下游或触发限流
```

## ReAct 范式

ReAct（arXiv:2210.03629）把「推理」与「行动」交错进行：模型先输出 Thought（当前推理），再输出 Action 与 Action Input，程序执行后把 Observation 回填，模型继续下一轮，直至给出 Final Answer。它的价值在可解释性与抗幻觉：推理轨迹让计划可见可纠，外部观察给模型提供事实锚点。在原生支持工具调用的模型上，现代做法通常直接用结构化 tool_calls 代替文本解析，但 ReAct 的文本格式仍然是调试工具与不支持原生调用的模型的通用退路。

```python
"""ReAct 范式：模型输出 Thought/Action/Action Input 文本，程序解析后执行并回填 Observation。"""
import re
from typing import Any

TOOLS: dict[str, Any] = {
    "search": lambda query: {"AI Agent": "2023 年起工具调用成为主流范式"}.get(query, "无结果"),
    "calculator": lambda expr: eval(expr, {"__builtins__": {}}),   # 演示用，生产须用安全求值器
}

SCRIPT = [
    "Thought: 需要先查 Agent 范式的来源\nAction: search\nAction Input: AI Agent\n",
    "Thought: 拿到描述，需要算一个比例\nAction: calculator\nAction Input: 2026 - 2023\n",
    "Thought: 信息够了，可以直接回答\nFinal Answer: 工具调用范式的元年是 2023，距今 3 年。\n",
]


def parse(text: str) -> tuple[str, dict]:
    """解析模型输出：Action/Input 或 Final Answer。"""
    if "Final Answer:" in text:
        return "final", {"answer": text.split("Final Answer:", 1)[1].strip()}
    action = re.search(r"Action:\s*(\w+)", text)
    arg = re.search(r"Action Input:\s*(.+)", text)
    return action.group(1), {"query" if action.group(1) == "search" else "expr": arg.group(1).strip()}


def run(max_steps: int = 5) -> None:
    scratch: list[str] = []
    for step, model_output in enumerate(SCRIPT[:max_steps], start=1):
        thought = model_output.splitlines()[0]
        print(f"[step {step}] {thought}")
        kind, args = parse(model_output)
        if kind == "final":
            print(f"[step {step}] Final Answer: {args['answer']}")
            return
        observation = TOOLS[kind](**args)
        scratch.append(f"Observation: {observation}")
        print(f"[step {step}] Action: {kind} {args}")
        print(f"[step {step}] Observation: {observation}")
    print("达到 max_steps，未产出 Final Answer")
    print("累计 observation:", scratch)


if __name__ == "__main__":
    run()
```

```text
[step 1] Thought: 需要先查 Agent 范式的来源
[step 1] Action: search {'query': 'AI Agent'}
[step 1] Observation: 2023 年起工具调用成为主流范式
[step 2] Thought: 拿到描述，需要算一个比例
[step 2] Action: calculator {'expr': '2026 - 2023'}
[step 2] Observation: 3
[step 3] Thought: 信息够了，可以直接回答
[step 3] Final Answer: 工具调用范式的元年是 2023，距今 3 年。
```

```text
ReAct 要点：
1. 格式约束写进系统提示词，并给出一个完整的 few-shot 样例，否则解析会频繁失败
2. 解析失败不要静默跳过，把解析错误作为 Observation 回填，让模型修正格式
3. 文本格式的表达式求值必须用安全求值器，禁止直接 eval 用户可控输入
4. 原生支持 tool_calls 的模型优先用结构化调用，文本格式作为兼容退路
5. 每步都要有步数上限，ReAct 容易陷入搜索-重试的循环
```

## 工具失败重试与降级

工具失败分两类：瞬时故障（下游 5xx、超时、限流）值得退避重试；确定性错误（参数非法、权限不足、资源不存在）重试无用，应当立即回填错误让模型换路径或转人工。工程上把这三件事组合起来：幂等去重（同一业务键只执行一次副作用）、指数退避重试、熔断保护（连续失败到阈值后直接降级，不再打下游），并把每次尝试写成审计日志。

```python
"""工具执行的可靠性策略：幂等去重 + 指数退避重试 + 熔断 + 降级 + 审计日志。"""
import json
import time
from typing import Any, Callable

AUDIT: list[str] = []
FAIL_COUNTS: dict[str, int] = {}
IDEMPOTENT_CACHE: dict[str, Any] = {}
BREAKER_THRESHOLD = 3          # 连续失败达阈值即熔断，直接走降级


def audit(event: str, **fields: Any) -> None:
    AUDIT.append(json.dumps({"event": event, **fields}, ensure_ascii=False))


def idempotent(key: str, fn: Callable[[], Any]) -> Any:
    if key in IDEMPOTENT_CACHE:                 # 同一业务键只执行一次，避免重试造成重复副作用
        audit("idempotent_hit", key=key)
        return IDEMPOTENT_CACHE[key]
    result = fn()
    IDEMPOTENT_CACHE[key] = result
    return result


class Flaky:
    """前两次抛错、第三次成功，用于演示退避重试。"""

    def __init__(self) -> None:
        self.calls = 0

    def __call__(self) -> str:
        self.calls += 1
        if self.calls < 3:
            raise RuntimeError(f"upstream 503 (call {self.calls})")
        return "invoice-url-ok"


def call_with_policy(name: str, fn: Callable[[], Any], key: str,
                     retries: int = 3, base_delay: float = 0.02) -> Any:
    if FAIL_COUNTS.get(name, 0) >= BREAKER_THRESHOLD:       # 熔断打开
        audit("breaker_open", tool=name)
        return {"degraded": True, "reason": "circuit_open", "tool": name}
    for attempt in range(retries + 1):
        try:
            result = idempotent(key, fn)
            FAIL_COUNTS[name] = 0
            audit("ok", tool=name, attempt=attempt + 1, key=key)
            return result
        except Exception as exc:
            FAIL_COUNTS[name] = FAIL_COUNTS.get(name, 0) + 1
            retryable = "503" in str(exc) or "timeout" in str(exc)   # 分类：瞬时故障才重试
            audit("fail", tool=name, attempt=attempt + 1, retryable=retryable, error=str(exc))
            if not retryable or attempt == retries:
                return {"degraded": True, "reason": str(exc), "tool": name}
            time.sleep(base_delay * (2 ** attempt))
    return {"degraded": True, "reason": "exhausted", "tool": name}


if __name__ == "__main__":
    flaky = Flaky()
    print("1) 瞬时故障 + 退避重试 ->", call_with_policy("make_invoice", flaky, key="order:A1001"))
    print("2) 同键再次调用（幂等命中）->", call_with_policy("make_invoice", flaky, key="order:A1001"))
    print("3) 连续失败触发熔断 ->",
          [call_with_policy("broken_tool", lambda: (_ for _ in ()).throw(RuntimeError("boom")), key=f"k{i}")
           for i in range(4)][-1])
    print("\n审计日志：")
    for line in AUDIT:
        print(" ", line)
```

```text
1) 瞬时故障 + 退避重试 -> invoice-url-ok
2) 同键再次调用（幂等命中）-> invoice-url-ok
3) 连续失败触发熔断 -> {'degraded': True, 'reason': 'circuit_open', 'tool': 'broken_tool'}

审计日志：
  {"event": "fail", "tool": "make_invoice", "attempt": 1, "retryable": true, "error": "upstream 503 (call 1)"}
  {"event": "fail", "tool": "make_invoice", "attempt": 2, "retryable": true, "error": "upstream 503 (call 2)"}
  {"event": "ok", "tool": "make_invoice", "attempt": 3, "key": "order:A1001"}
  {"event": "idempotent_hit", "key": "order:A1001"}
  {"event": "ok", "tool": "make_invoice", "attempt": 1, "key": "order:A1001"}
  {"event": "fail", "tool": "broken_tool", "attempt": 1, "retryable": false, "error": "boom"}
  {"event": "fail", "tool": "broken_tool", "attempt": 1, "retryable": false, "error": "boom"}
  {"event": "fail", "tool": "broken_tool", "attempt": 1, "retryable": false, "error": "boom"}
  {"event": "breaker_open", "tool": "broken_tool"}
```

```text
失败处理要点：
1. 先分类再重试：瞬时故障退避重试，确定性错误立即回填，重试只会浪费时间
2. 带随机抖动的指数退避，避免下游恢复瞬间被重试洪峰打死
3. 有副作用的工具必须幂等（业务键去重或下游幂等接口），否则重试就是重复下单
4. 熔断后返回明确的降级结果而非异常，让上层能继续给用户一个有意义的答复
5. 每次尝试都写审计日志：tool、attempt、retryable、error、耗时，便于定位与容量规划
```

## 应用场景实战

### 场景一：并行取数的订单助手（超时、部分失败、按 id 归位）

用户问「我的订单到哪了、还有没有优惠券、库存够不够」，理想情况下一轮就取完三类信息。下面把三个工具并发执行，物流查询故意设慢超时，验证部分失败时仍能给出可用答复——失败项会作为 observation 回填，模型可以决定重试或如实说明暂时查不到。

```python
"""订单助手：并发调用三个工具，超时的那个不阻塞其余结果，并按调用 id 归位。"""
import asyncio
import json

TOOLS = {
    "get_order":     {"delay": 0.20, "result": {"order_id": "A1001", "status": "shipped"}},
    "get_coupon":    {"delay": 0.15, "result": {"coupon": "满 100 减 20", "expire": "2026-11-01"}},
    "get_logistics": {"delay": 0.90, "result": {"node": "杭州中转", "eta": "2026-10-16"}},
}
TIMEOUT = 0.40


async def call(name: str, spec: dict) -> dict:
    await asyncio.sleep(spec["delay"])
    return {"name": name, "content": json.dumps(spec["result"], ensure_ascii=False)}


async def run_batch() -> list[dict]:
    calls = [{"id": f"call_{i}", "name": n} for i, n in enumerate(TOOLS)]
    results = await asyncio.gather(
        *[asyncio.wait_for(call(c["name"], TOOLS[c["name"]]), timeout=TIMEOUT) for c in calls],
        return_exceptions=True,
    )
    filled = []
    for c, r in zip(calls, results):
        if isinstance(r, Exception):
            filled.append({"role": "tool", "tool_call_id": c["id"],
                           "content": json.dumps({"error": "timeout", "tool": c["name"]}, ensure_ascii=False)})
        else:
            filled.append({"role": "tool", "tool_call_id": c["id"], "content": r["content"]})
    return filled


if __name__ == "__main__":
    for msg in asyncio.run(run_batch()):
        print(msg)
```

```text
{'role': 'tool', 'tool_call_id': 'call_0', 'content': '{"order_id": "A1001", "status": "shipped"}'}
{'role': 'tool', 'tool_call_id': 'call_1', 'content': '{"coupon": "满 100 减 20", "expire": "2026-11-01"}'}
{'role': 'tool', 'tool_call_id': 'call_2', 'content': '{"error": "timeout", "tool": "get_logistics"}'}
```

三个结果都按 `tool_call_id` 归位，物流超时不阻塞其他两项，模型可以据此回答「订单已发货、有满减券，物流详情稍后重试」——这正是并行调用在生产里的实际收益。

### 场景二：带重试、熔断与审计的发票生成工具

财务侧的「生成发票」是典型的有副作用工具：下游会偶发 503，网络抖动会超时，重试还可能重复开票。工程做法是：业务键（`order_id` 加动作名）做幂等去重，瞬时错误退避重试，连续失败触发熔断并返回降级结果，全过程写审计日志。可运行代码与实测输出见上文「工具失败重试与降级」一节，这里补充落库与告警的字段约定。

```sql
-- 工具调用审计表（生产建议按月分区）
CREATE TABLE tool_call_audit (
    id           BIGSERIAL PRIMARY KEY,
    session_id   TEXT        NOT NULL,
    trace_id     TEXT        NOT NULL,
    tool         TEXT        NOT NULL,
    args         JSONB       NOT NULL,
    result       JSONB,
    status       TEXT        NOT NULL,      -- ok / degraded / error
    attempt      SMALLINT    NOT NULL,
    retryable    BOOLEAN     NOT NULL,
    latency_ms   INTEGER     NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_audit_tool_time ON tool_call_audit (tool, created_at DESC);
CREATE INDEX idx_audit_trace     ON tool_call_audit (trace_id);
```

```text
审计与告警约定：
1. 每次工具调用一行记录：session_id、trace_id、tool、args、result、status、attempt、latency_ms
2. 幂等键与审计记录同时落库，重试命中幂等时也记一行（便于核对真实执行次数）
3. 按 tool 维度统计失败率与 P95 延迟，失败率超阈值（例如 5%）直接告警
4. 熔断打开时写一条独立事件，值班能立刻区分「下游挂了」与「调用方参数错」
5. 涉及金额与个人信息的 args 要脱敏或加密后存储
```

## 最佳实践与踩坑记录

### 最佳实践

1. 工具描述按接口文档标准写：用途、参数含义与格式、返回结构、边界（不适用什么场景），并用「实习生测试」自查。
2. 全部工具参数先本地校验（JSON Schema）再执行，校验失败把具体字段错误回填给模型。
3. 开严格模式（OpenAI 的 `strict: true`）并要求 `additionalProperties: false`、字段全必填，减少非法参数；注意严格模式不支持全部 JSON Schema 特性。
4. 一轮多调用一律并发执行，单项超时与失败单独降级，按调用 id 归位结果。
5. 有副作用的工具必须幂等，并全部落审计日志：trace_id、tool、args、status、attempt、latency。
6. 控制单轮工具数量（软性建议 20 个以内），大工具集用工具检索或分组延后加载，降低选择错误率与 token 成本。
7. 循环一定要有硬上限：最大步数、token 预算、墙钟超时，任一触发即返回「当前最佳 + 待人工复核」。

### 踩坑记录

```text
坑 1：工具结果没带调用 id，下一轮请求被拒
结论：接口报消息结构错误，或模型把同一个工具重复调用多次。
原因：回填时只写了 content，丢了 tool_call_id / tool_use_id 的配对关系。
解法：严格成对追加 assistant 的调用请求与 tool 结果，id 一一对应；用消息结构校验做单测。

坑 2：Schema 写得太宽，模型编造参数
结论：下游报参数错误，或写入了不存在的枚举值。
原因：参数没有 description、没有 enum、没有 additionalProperties false。
解法：补齐描述与枚举、开启严格模式、服务端二次校验并返回可纠正的错误信息。

坑 3：把所有工具一次挂上去，选错工具率上升且成本变高
结论：模型经常调用不相关工具，输入 token 也显著增加（工具定义计入输入 token）。
原因：工具数量过多、功能重叠、描述边界模糊。
解法：拆成有限工具集 + 工具检索；合并总是连续调用的函数；把已知参数从 schema 里去掉。

坑 4：对确定性错误做重试，放大故障
结论：重试风暴把下游打穿，且日志里全是同一个必然失败的错误。
原因：没有区分瞬时故障与确定性错误，统一无脑重试。
解法：分类处理——瞬时错误退避重试（带抖动、限次数），确定性错误立即回填；加熔断与并发上限。

坑 5：有副作用的工具重试导致重复执行
结论：同一笔订单开出两张发票，账务需要人工冲销。
原因：重试时没有幂等保护，下游也不支持幂等键。
解法：业务键（order_id 加动作）做本地幂等去重，同时要求下游提供幂等接口，两者都要有。

坑 6：并行调用里混入互相依赖的写操作
结论：并发执行顺序不确定，出现「先扣款后校验」这类脏状态。
原因：把写操作当成普通查询一起并发。
解法：按依赖图分组，写操作串行或加锁；同批并发只用于无依赖的读操作。
```
