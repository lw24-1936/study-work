## 概述

多智能体（Multi-Agent）协作是把一个复杂任务拆给多个职责单一、各自带工具与提示词的 Agent，通过明确的通信与交接协议协同完成。它解决单 Agent 的三个痛点：上下文被无关信息污染、工具集过大导致选错工具、单点提示词难以兼顾多种专业性。代价是延迟与 token 成本成倍上升，所以第一原则是「能用单 Agent + 好的提示词解决，就别上多智能体」。

```text
多智能体协作的四要素：
1. 拓扑 —— 谁调度谁：中心编排、流水线、并行、对等网络、层级
2. 角色 —— 每个 Agent 的职责边界、可用工具、输入输出契约
3. 通信 —— 消息如何传、任务如何交接、状态存放在哪
4. 收敛 —— 冲突怎么裁决、何时终止、超预算怎么办
```

## 多智能体拓扑结构

拓扑决定控制流与信息流，是选型的第一步。Anthropic 在《Building effective agents》中把可复用的模式归纳为 prompt chaining、routing、parallelization（分节与投票）、orchestrator-workers、evaluator-optimizer，并明确区分「workflow（由代码预定义路径编排）」与「agent（LLM 自行决定流程）」——大多数生产系统是两者的混合，而非纯自主 Agent。

| 拓扑 | 结构 | 控制力 | 适用场景 |
| --- | --- | --- | --- |
| 单 Agent | 一个 LLM + 工具循环 | 高 | 任务边界清晰、工具不多 |
| 顺序流水线 | A -> B -> C，固定阶段 | 高 | 阶段固定的加工链（草稿 -> 评审 -> 定稿） |
| 编排者-工作者 | 中心调度分发，汇总结果 | 中高 | 子任务数量不可预知，需统一收口 |
| 并行分节 | 多个 Agent 同时处理独立子任务后聚合 | 中 | 可切分的独立工作，要提速 |
| 并行投票 | 同一任务多 Agent 并行，取多数/加权 | 中 | 审核、分类、需要高置信度 |
| 评估者-优化者 | 生成者与评估者循环迭代 | 中 | 有明确评价标准、可迭代改进 |
| 对等网络（群聊/切换） | Agent 之间互相交接，无中心 | 低 | 灵活但易发散，需强终止约束 |
| 层级编排 | 编排者之下再套编排者 | 中 | 大规模、按业务域分层 |

```text
选型顺序（从简单到复杂，够用即止）：
1. 单 Agent + 好提示词 + 少量工具
2. 顺序流水线（阶段固定）
3. 编排者-工作者（子任务不可预知，需要汇总）
4. 并行分节 / 投票（要提速或要置信度）
5. 评估者-优化者（质量可迭代）
6. 对等网络 / 层级（前几层都撑不住时再考虑，务必带硬终止）
```

要点：

- 优先 workflow 而非自主 Agent：路径可预定义就用代码编排，可预测、可调试、成本可控
- 拓扑选择由「子任务是否可预知」决定：可预知用流水线/并行，不可预知用编排者-工作者
- 每增加一层 Agent，延迟与 token 成本至少翻倍，收益必须用评测证明
- 对等网络最灵活也最难控，必须配硬终止与轮数上限，否则容易陷入来回踢皮球
- 拓扑要能画出图（节点=Agent，边=交接），画不出来说明还没想清楚

## 编排者与工作者模式

编排者-工作者（orchestrator-workers）是生产中最常用的多智能体模式：一个中心 Agent 动态把任务拆成子任务、分发给若干工作者、再综合它们的结果。它与并行分节的关键区别是「子任务不预先定义」，由编排者根据输入现场决定，因此更适合编码、检索综合、多源调研这类子任务数量不确定的任务。

工业界的落地形态以 LangGraph 的 supervisor 为代表：`langgraph_supervisor.create_supervisor` 接收一组已编译的子 Agent，自动为每个子 Agent 生成一个名为 `transfer_to_<agent_name>` 的交接工具，编排者通过调用这些工具把控制权交出去。

```shell
# 依赖（Python 3.10+；版本以官方文档为准）
pip install -U langgraph langgraph-supervisor langchain langchain-openai
```

```python
# supervisor_demo.py：编排者 + 两个工作者
from langchain.agents import create_agent            # 1.x 推荐入口，替代已弃用的 create_react_agent
from langgraph_supervisor import create_supervisor


def add(a: float, b: float) -> float:
    """两数相加。"""
    return a + b


def web_search(query: str) -> str:
    """检索网页，返回相关信息。"""
    return "示例检索结果：..."

# 工作者：各自只带本职工具（工具白名单隔离）
math_agent = create_agent(model="openai:gpt-4o", tools=[add], name="math_expert")
research_agent = create_agent(model="openai:gpt-4o", tools=[web_search], name="research_expert")

# 编排者：不用自己干活，只负责拆解、指派、汇总（参数名以官方文档为准）
workflow = create_supervisor(
    [math_agent, research_agent],
    model="openai:gpt-4o",
    prompt=("你是协调者。把任务拆给 math_expert 或 research_expert，"
            "收到结果后自行汇总作答；能直接回答的不要委派。"),
    handoff_tool_prefix="delegate_to_",   # 交接工具名将变为 delegate_to_<agent>
)
app = workflow.compile()

if __name__ == "__main__":
    result = app.invoke({"messages": [{"role": "user", "content": "12.5 加 7.5 等于多少？"}]})
    print(result["messages"][-1].content)
```

要点：

- 编排者只做「拆解-指派-汇总」，绝不亲自执行子任务，否则会绕过工作者手里的工具与提示词
- 工作者必须工具白名单隔离：数学 Agent 不该拿到检索工具，检索 Agent 不该拿到写库工具
- 交接工具的描述要写清「何时该把控制权交给谁」，这是编排者能否正确路由的关键
- 编排者要能收口：所有子任务结果汇总到编排者，由它产出最终答复，别让工作者直接对外
- 简单任务允许编排者「直接回答」，避免为一句算术题白白拉起一次多轮协作

## 角色划分与提示词设计

角色划分的核心是「单一职责 + 明确契约」：每个 Agent 只做一类事，输入输出格式固定，能用的工具受限。角色提示词不是「你是一个专业助手」这种空话，而要写清四件事：职责边界（做什么、不做什么）、输入契约（收到什么格式）、输出契约（产出什么格式）、升级路径（搞不定交给谁）。工作者越像「一个职责清晰、接口固定的函数」，协作越稳定。

```python
# 角色提示词模板：把 Agent 当函数来定义
ROLE_PROMPTS = {
    "researcher": """你是资料检索员。
职责：根据给定问题检索并整理事实，只输出证据，不做推测、不给建议。
输入：{"question": "..."}
输出：{"facts": ["..."], "sources": ["..."]}
边界：不写结论、不生成最终文案。
做不到时：输出 {"escalate": "缺少 XX 资料"} 交回编排者。""",
    "writer": """你是文案撰写员。
职责：仅依据输入的 facts 撰写答复，不引入 facts 之外的信息。
输入：{"question": "...", "facts": ["..."]}
输出：{"answer": "..."}
边界：不得新增事实，不得省略来源标注。
做不到时：明确指出哪条事实不足以支撑作答。""",
    "reviewer": """你是审校员。
职责：核对 answer 是否全部由 facts 支撑，并给出结论。
输入：{"question": "...", "facts": ["..."], "answer": "..."}
输出：{"verdict": "pass|revise", "issues": ["..."]}
边界：不改写答案，只判定并指出问题。""",
}
```

```python
# 用契约约束工作者的输出：结构化解析 + 失败重试
import json


def call_worker(agent, payload: dict) -> dict:
    raw = agent.invoke({"messages": [{"role": "user", "content": json.dumps(payload, ensure_ascii=False)}]})
    text = raw["messages"][-1].content
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        # 契约违约：把要求重申一遍再要一次，最多重试 1 次
        retry = agent.invoke({"messages": [{"role": "user",
                             "content": "上一次输出不是合法 JSON，请严格按约定的 JSON 结构重新输出。"}]})
        return json.loads(retry["messages"][-1].content)
```

要点：

- 一个 Agent 一件事：角色越窄，提示词越短，行为越可预测，也越容易评测
- 角色提示词必须写「不做什么」和「做不到时交给谁」，否则 Agent 会越界答题
- 输入输出用结构化契约（JSON schema），编排者才能可靠地拼接与校验
- 工作者之间不直接共享上下文，只交换契约字段，避免上下文互相污染
- 角色与工具一一绑定：给错的工具比不给工具更危险（越权风险见安全篇章）

## Agent 间通信与任务交接

Agent 之间的通信有三种主流实现：消息传递（把结果作为消息放进共享的 messages 列表）、任务交接（handoff，把控制权与状态转给另一个 Agent）、共享状态（blackboard，把结构化字段写进全局 state）。LangGraph 的 handoff 用 `create_handoff_tool` 把「交接」建模成一次工具调用，返回值是控制图走向的 `Command`，从而让交接对 LLM 而言只是「调用一个叫 `transfer_to_xxx` 的工具」。

```python
# 自定义交接工具：显式控制交接语义（参数以官方文档为准）
from langgraph_supervisor import create_handoff_tool

# 默认工具名 transfer_to_<agent>，可改成业务语义更清晰的名字
to_writer = create_handoff_tool(
    agent_name="writer",
    name="handoff_to_writer",
    description="当资料已齐全、需要产出最终文案时，交给 writer",
)
```

```text
三种通信方式对比：
1. 消息传递 —— 结果作为 message 追加进共享列表；优点简单、可追溯；缺点上下文会膨胀
2. 任务交接 —— handoff 把控制权与必要状态转出；优点职责清晰；缺点链长了难追溯
3. 共享状态 —— 结构化字段写入 state（如 facts/answer/verdict）；优点契约清晰；推荐默认

任务交接的最小契约（建议随每次交接传递）：
{ "task": "写退款说明", "inputs": {...已确认的事实...}, "expected_output": "answer 字段",
  "deadline": "2026-10-14T18:00", "trace_id": "t-9f2c" }
```

要点：

- 交接必须带 trace_id：否则跨 Agent 的长链路无法在可观测平台里串起来
- 优先用结构化共享状态而非长消息历史：字段级契约比自然语言交接可靠得多
- 交接时只传「必要的输入」，不要把整段上游历史原样转发，否则上下文迅速膨胀
- 交接工具的描述要能从「何时调用」角度写清，这是路由正确性的主要来源
- 每次交接都要能回答三个问题：交给谁、为什么现在是它、期望它返回什么

## 冲突处理与终止条件

多智能体的两个典型失控：冲突（两个 Agent 结论矛盾，无人裁决）与不收敛（Agent 之间反复交接、永远不结束）。冲突有明确解法——投票、仲裁者、证据优先；收敛必须靠确定性约束——轮数上限、预算上限、无进展检测、超时。记住一条铁律：终止条件要由代码强制，不能指望模型「自己想停」。

```python
# 终止条件由代码强制：轮数 + 预算 + 无进展检测，三者任一触发即停
def supervisor_loop(dispatch, aggregate, max_rounds=5, budget=0.10, unit_cost=0.02):
    spent, history = 0.0, []
    for rnd in range(1, max_rounds + 1):
        if spent + unit_cost > budget:
            return aggregate(history), "stop:budget"
        result = dispatch(rnd)                 # 编排者指派 + 工作者执行
        if result is None or result in history:  # 无进展：没有新结果
            return aggregate(history), "stop:no-progress"
        history.append(result)
        spent += unit_cost
        if result.get("done"):                 # 目标达成（由校验者判定）
            return aggregate(history), "stop:goal"
    return aggregate(history), "stop:max-rounds"
```

```python
# 冲突裁决：以「有证据支撑」的一方为准，而非以「谁说得更自信」为准
def resolve_conflict(claims: list[dict]) -> dict:
    """claims 形如 {"agent": "...", "value": ..., "evidence": [...]}"""
    with_evidence = [c for c in claims if c.get("evidence")]
    if len(with_evidence) == 1:
        return with_evidence[0]                       # 只有一方有证据 -> 采纳
    if not with_evidence:
        return {"value": None, "reason": "无证据支撑，升级人工"}   # 都不成立 -> 升级
    return {"value": None, "reason": "证据冲突，提交仲裁者或人工"}    # 都有证据 -> 仲裁
```

本机实测的多智能体终止条件输出（预算充足时任务完成即停，预算受限时在预算处停止）：

```text
===== 01.6 多智能体：终止条件与预算控制 =====
[预算充足] 完成 3/3 花费 $0.06
    round 1: 工作者完成 '查资料' 累计花费 0.02
    round 2: 工作者完成 '写草稿' 累计花费 0.04
    round 3: 工作者完成 '审校' 累计花费 0.06
    round 4: 无待处理任务 -> 终止(任务完成)
[预算受限] 完成 2/5 花费 $0.04
    round 1: 工作者完成 '查资料' 累计花费 0.02
    round 2: 工作者完成 '写草稿' 累计花费 0.04
    round 3: 预算不足(已花 0.04/0.05) -> 终止(预算)
```

要点：

- 终止条件必须由代码强制：轮数上限 + 预算上限 + 超时，缺一不可，别交给模型判断
- 无进展检测（连续 N 轮结果相同或为空）是防死循环的关键，尤其在对等网络拓扑下
- 冲突裁决要有确定规则：有证据优先、其次投票、再不行升级人工，禁止「让双方再吵一轮」
- 校验者（verifier）的结论只用于判断「目标是否达成」，不要让它同时兼任执行者
- 每一次终止都要记录原因（goal/budget/max-rounds/timeout）以便归因

## 多智能体成本控制

多智能体天然贵：一次用户请求可能触发 5-20 次 LLM 调用，token 随 Agent 数量与轮数线性上升。成本控制的手段按性价比排序：路由到合适规模的模型（简单子任务用小模型）、限制轮数与委派深度、并行化可并行的子任务、对工作者结果做缓存、把「是否需要多智能体」本身作为一道判断。

| 手段 | 做法 | 典型收益 |
| --- | --- | --- |
| 模型分级路由 | 编排/汇总用大模型，简单工作者用小模型 | 大幅降低单价 |
| 轮数与深度上限 | 限制 max_rounds 与最大委派层级 | 封顶最坏成本 |
| 结果缓存 | 对确定性工作者按输入哈希缓存 | 复用命中即省一次调用 |
| 并行执行 | 独立子任务并行而非串行 | 降延迟、不增 token 但要控并发 |
| 预算闸门 | 单任务 token/金额预算，超限即降级 | 防单次请求打爆账单 |
| 单 Agent 优先 | 简单任务不启用多智能体 | 直接省掉全部额外调用 |

```python
# 模型分级：按子任务复杂度选模型（配置集中管理，便于调参）
MODEL_TIERS = {
    "orchestrator": "gpt-4o",          # 拆解与汇总，调用次数少，用强模型
    "worker_simple": "gpt-4o-mini",    # 分类、抽取、格式化，用便宜模型
    "worker_hard": "gpt-4o",           # 复杂推理子任务
}


def pick_model(role: str, difficulty: str = "simple") -> str:
    if role == "orchestrator":
        return MODEL_TIERS["orchestrator"]
    return MODEL_TIERS["worker_hard" if difficulty == "hard" else "worker_simple"]


# 结果缓存：对幂等的工作者（同一输入产出同一结果）按输入哈希缓存
import hashlib
import json

_cache: dict[str, str] = {}


def cached_worker(agent, payload: dict) -> str:
    key = hashlib.sha256(json.dumps(payload, sort_keys=True, ensure_ascii=False).encode()).hexdigest()
    if key not in _cache:
        _cache[key] = agent.invoke({"messages": [{"role": "user", "content": json.dumps(payload)}]}
                                   )["messages"][-1].content
    return _cache[key]
```

要点：

- 编排/汇总用强模型、`worker_simple` 类子任务用廉价模型，是降本的第一杠杆
- 给每个会话设 token/金额预算，超限即降级（存证并回复「任务过大」），避免账单失控
- 独立子任务并行化能降延迟，但要用并发上限兜住，防止同时打爆速率限制
- 幂等工作者可缓存：把「输入 -> 输出」按哈希缓存，命中即省一次调用
- 定期用可观测数据回看「收益 vs 成本」，砍掉不产生价值的 Agent 层

## 应用场景实战

### 场景一：编排者-工作者的研究报告生成流水线（LangGraph supervisor）

场景：给定一个研究主题，自动产出「资料 + 撰稿 + 审校」三段式报告。编排者负责拆解与汇总，工作者各自只带本职工具，审校员不通过则打回重写。

```shell
pip install -U langgraph langgraph-supervisor langchain langchain-openai
```

```python
# report_pipeline.py
from langchain.agents import create_agent
from langgraph_supervisor import create_supervisor


def search_docs(query: str) -> str:
    """检索内部文档库，返回相关片段。"""
    return f"[doc] 关于 {query} 的事实片段"


def save_draft(title: str, body: str) -> str:
    """保存草稿。"""
    return f"已保存：{title}"


researcher = create_agent(
    model="openai:gpt-4o-mini",
    tools=[search_docs],
    name="researcher",
    system_prompt=("你是资料检索员。只输出带来源的事实要点，不写结论。"
                   "资料不足时返回 escalate 说明缺什么。"),
)
writer = create_agent(
```

### 场景二：用「并行投票」做代码安全审核

场景：同一份代码交给多个不同角度的审核 Agent 并行检查，任一 Agent 发现问题即标记。这是 Anthropic 推荐的 voting 并行模式，适合「宁可误报不可漏报」的审核场景。

```python
# vote_review.py：并行投票的审核流水线
from concurrent.futures import ThreadPoolExecutor

PERSPECTIVES = {
    "injection": "检查是否存在提示注入/命令注入风险，发现即报告。",
    "secrets": "检查是否硬编码了密钥、令牌、连接串。",
    "authz": "检查是否存在越权访问：未校验的租户/角色边界。",
    "deps": "检查依赖是否包含已知高危版本。",
}


def review_agent(llm, code: str, aspect: str, prompt: str) -> dict:
    ans = llm(f"你是资深安全审核员。{prompt}\n只输出 JSON：{{\"found\": true/false, \"detail\": \"...\"}}\n\n代码:\n{code}")
    return {"aspect": aspect, "result": ans}


def vote_review(llm, code: str, threshold: int = 1) -> dict:
    with ThreadPoolExecutor(max_workers=4) as ex:      # 并行，不增 token，只降延迟
        futures = [ex.submit(review_agent, llm, code, a, p) for a, p in PERSPECTIVES.items()]
        results = [f.result() for f in futures]
    # 投票策略：任一视角发现问题即拦下（审核场景偏保守）
    flagged = [r for r in results if '"found": true' in r["result"]]
    return {"blocked": len(flagged) >= threshold, "details": flagged}
```

## 最佳实践与踩坑记录

### 最佳实践

1. 单 Agent 优先：只有当单 Agent 因上下文污染或工具过多而失效时，才升级到多智能体
2. 每个 Agent 单一职责、工具白名单、输入输出结构化契约，像函数一样可测
3. 终止条件由代码强制：轮数 + 预算 + 超时 + 无进展检测，禁止全交给模型判断
4. 编排者只拆解与汇总，所有子任务结果收回编排者统一收口
5. 模型分级路由 + 结果缓存 + 并行执行，把成本与延迟按性价比逐项优化
6. 每次交接带 trace_id 与任务契约，保证长链路可追溯、可归因

### 踩坑记录

```text
坑 1：没用多久就陷入 Agent 之间来回交接，永不结束
结论：任务超过预期时间仍在 transfer，token 持续消耗。
原因：对等/自主拓扑缺少确定性终止条件，模型倾向于"再确认一次"。
解法：代码层强制 max_rounds 与预算上限，并加无进展检测（连续 N 轮结果不变即停）。

坑 2：两个 Agent 结论矛盾，最终答案随机取了一个
结论：输出不稳定、不可复现，用户质疑可信度。
原因：没有冲突裁决规则，汇总时凭模型自由选择。
解法：定规则——有证据优先，其次投票，再次升级人工；禁止"让双方再吵一轮"。

坑 3：工作者拿到了不该有的工具，越权操作
结论：检索 Agent 竟然写入了数据库，或外发邮件。
原因：工具集全局共享，没有按角色做白名单隔离。
解法：每个 Agent 只挂本职工具；写操作类工具走最小权限 + 人在回路确认。

坑 4：把上游整段历史原样转发给下游 Agent
结论：上下文迅速膨胀，token 成本飙升且下游被无关信息干扰。
原因：交接时传递了完整 messages，而不是结构化契约字段。
解法：只传必要输入的结构化 state，历史留在观测平台而非塞进上下文。

坑 5：简单任务也拉起整套多智能体
结论：一句问候触发 8 次调用，延迟与成本都不可接受。
原因：没有"是否需要多智能体"的门槛判断。
解法：编排者先判断任务复杂度，能直接回答的直接答；只在必要时才委派。
```
